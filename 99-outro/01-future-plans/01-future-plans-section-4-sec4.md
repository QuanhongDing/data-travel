## 4. 关键行动项

§3 回答的是「哪个动作在什么约束下成立、什么条件下失效」，本节只回答执行层的四个问题：**先做哪件、做到什么算做完、它留下什么、你手上已经有的那些东西怎么办**。前两问在 4.1 与 4.2，第三问在 4.3 与 4.5，第四问在 4.4。清单本身（哪些事值得做、时间成本多少、八个族怎么分）在 [§ 7 推荐行动 / 推荐阅读](01-future-plans-section-7-sec7.md)，本节不重复。

本文件面向**已经在做事、但手上的产出还不可检索**的读者——典型画像是 5–10 年经验、背过若干个项目、却拿不出一份能被别人引用的决策记录【经验】。如果你还没有一个能说清约束的项目，4.1 的 Step 1–2 照样成立，但 Step 3 的 0→1 项目要先解决授权问题：那属于 [§ 3](01-future-plans-section-3-sec3.md) 3.2.1 的判断，不在本节展开。

### 4.1 落地步骤

四个步骤对应四个时间尺度（本周 / 3 个月 / 1 年 / 3 年）。步骤标题里的工期是【经验】区间，它随两件事变：你的材料齐不齐（有没有现成的决策记录可补）、以及你手上有没有正在跑的授权（没有授权时 Step 3 会被无限期推迟）。

**Step 1：把定位与决策记录立起来（本周，合计 4–8 小时【经验】）**

- 把 LinkedIn / 简历 / 个人主页的定位改成「AI 时代数据架构师」，并写清你现在能回答的三类问题（哪类数据问题、用什么方法、代价是什么）。
- 给至少 1 位 Mentor 发消息，约一次交流，并把频率固定成季度制——只要没排进日历，它就一定不会发生。
- 把「过去 12 个月做的最有价值的决策」写成一份 1000 字复盘【经验】（字数是本书给出的起点，作用是把「写完整」和「写一段感想」分开）。
- 列出 3 个「想深度学习的 AI 课题」（RAG / Agent / 向量 / 治理任选）。

- **产物**：一句可被外人复述的定位；一份 1000 字复盘；一份 3 个课题的清单；一个已排进日历的季度交流。
- **判据**：把那段定位给一个不认识你项目的同行看 60 秒，他能否说出「你解决的是哪一类数据问题、和一般的数据开发差别在哪」；再翻那份复盘，里面有没有写下**被否决的那个选项和它的代价**——没有，它只是一段结论，不能算资产。
- **为什么必须这一步 / 为什么在第一位**：因为后面三个步骤的每一件产出，都要拿它当参照物——定位决定你选择写什么题、接什么项目；复盘决定你有没有可引用的物证。省掉它，Step 3 的项目在晋升材料里会退化成「做过很多事，说不清哪一次是我拍的板」。
- **谁负责 / 多久见效**：负责人是你自己，没有第二个人能替你完成；唯一的外部依赖是那位 Mentor 的日历。见效时间是**下一次需要举证的场合**——不是三年后，而是最近的考核季、答辩或面试。

**Step 2：把产出放到门外去（3 个月，每周固定投入 4–6 小时【经验】）**

- 完成一个 RAG / 智能体 Demo（个人项目也可以，但要有改前 / 改后的同口径对照）。
- 写 3 篇公开技术博客，每篇 1500 字以上【经验】（篇数与字数是本书给出的起点，不是行业基准；可按你的时间形态下调，但不要降到「有空再写」）。
- 主导一次跨团队的 ADR 评审。
- 申请一次公开分享（公司内 / Meetup / 大会，任一）。

- **产物**：一个能跑通的 Demo；3 篇公开发表的文章；1 次评审的记录（含被否决的方案与理由）；1 次分享的现场提问清单。
- **判据**：打开文章后台，看有没有**非同事**的读者留下过具体问题（不是点赞）；翻评审记录，看有没有「为什么否决了另一个方案」这一栏；翻提问清单，看有没有一个你当场没答上来的问题。三条里至少两条为「有」，才算真的出了门。
- **为什么必须这一步 / 为什么在第二位**：因为公开产出改变的是「机会找到你的概率」，而这件事必须发生在 Step 3 之前——Step 3 要的是别人愿意把范围交给你，而愿意交范围的人是通过 Step 2 的产出物认识你的。换序的代价很具体：先做项目再补公开产出，项目期间形成的判断会随项目结束而散掉，事后补写的材料通常只剩结论。
- **谁负责 / 多久见效**：Demo 与文章由你自己负责；跨团队 ADR 评审要有一位愿意把评审排进会议日程的 Sponsor（通常是你的上级或另一个团队的负责人），没有这个人，这一步会一直停在「想约」。见效时间在**数周到数月**：公开文章与分享的反馈来得比项目快，但被引用、被邀请要更久。

**Step 3：把范围换大（1 年，主要占用本职时间）**

- 主导一个 0→1 的 AI 项目，跑通业务闭环。
- 培养 1–2 个 P5 / P6 晋升到 P6 / P7。
- 建立一个 5 人跨职能小组（含数据 / 算法 / 业务 / 产品）。
- 完成一次大型技术决策（自研 vs 采购 / 集中 vs 联邦 / 上云 vs 下云，任一）。

- **产物**：一份带改前 / 改后同口径的闭环记录；1–2 份晋升材料里你署名的举证部分；一份小组的共同目标对齐表；一份决策记录（含被否决项与「什么条件下重开」）。
- **判据**：三方（数据 / 算法 / 业务）能否对「什么叫成功」说出同一句可验证的话；决策记录里有没有「什么条件下要重开这个决策」这一栏；培养对象的晋升材料「关键项目」一栏里，签字人是不是你。
- **为什么必须这一步 / 为什么在第三位**：因为前两步换到的是「被看见」，这一步换到的才是「被授权」。顺序不能反：没有 Step 2 的产出物，Step 3 只能靠内部关系争取场景，成功率低且不可复制；把 0→1 提前到第一周，最常见的结局是花掉六个月，拿不到任何可对照的口径。
- **谁负责 / 多久见效**：你负责方案与口径，但这一步的四个动作各有第二负责人——0→1 项目的业务方、被培养者的直属上级、小组里的三个职能负责人、以及大型决策的会签人。缺了这些第二负责人，动作会退化成你一个人的工作。见效时间以**年**计：项目闭环当年可见，晋升与授权在下一次评估周期兑现。

**Step 4：把影响放到组织与行业（3 年，无固定工时，靠持续产出累积）**

- 成为某个领域公认的内外部专家（在 GitHub / 技术大会 / 行业报告留名）。
- 主导一次组织变革（团队重组 / 中台建设 / 治理升级，任一）。
- 完成一次跨 BU / 跨公司的影响力输出（开源贡献 / 行业标准 / 公开演讲）。
- 完成 P7 → P8 / 资深 → 准资深的跃迁。

- **产物**：一份外部可检索的署名记录（仓库 / 演讲 / 报告）；一份组织变革前后的对照（改了什么规则、谁的什么行为变了）；一份晋升答辩材料（问题 → 约束 → 决策 → 结果四段式）。
- **判据**：用搜索引擎搜你自己的名字，最近一年有没有组织外的人主动引用过你的产出；翻变革前你写下的那条规则，问「它现在还在被执行吗」——不在，说明变的只是流程文档；答辩材料里四个段落能不能逐段写出，写不出的那一段就是你其实没想清的那一段。
- **为什么必须这一步 / 为什么在最后**：因为组织级的影响是前三步的复利结果，不是第四步单独投入的产出。把传播与头衔放在前面做，得到的是**信号领先能力**的错配——被找来之后答不出细节，一次信任损耗很难修复。
- **谁负责 / 多久见效**：外部影响由你个人负责；组织变革必须有比你高一级的 Sponsor，且你要写在方案的第一页——没有 Sponsor 的变革方案不会被执行到第二周。见效时间【经验】以年计，且不线性：前三步的产出积累到某个量之后，外部邀请与合作机会才会出现，出现之前的那段投入看不到中间反馈。

四个步骤里最常被跳过的是 **Step 1 的那份 1000 字复盘**：它最不紧急，且看不出短期回报。跳过之后第一个出问题的时点通常不是三年后，而是下一个考核季或换工作的窗口——症状是一句很具体的话：评委或面试官问「当时还有别的方案吗，为什么没选它」，你答不上来。同一时点上，Step 2 的「发出去」是第二个高频缺席项：写完放在草稿箱里，等于把反馈通道自己关掉。

### 4.2 关键技术点

下面七条不是「要重视」的提醒，而是让前面四步真的产生复利的机制。每条都能回答同一个问题：**在什么条件下它会失效。**

**同口径对照**

- **做法**：任何一个项目，在动工前先写下「改前怎么量、改后怎么量、口径是什么」，并在项目结束时用同一张表回填。
- **机制**：因为口径是人选的，所以选口径的动作本身就是一次决策；把它写在动工前，改后就不会重新挑一个好看的指标。代价是它会把项目周期拉长一点点，并且经常逼出「这个需求其实量不出来」这个结论。
- **失效条件**：**当项目同时服务多个干系人、每人想看的指标不同时**，这条会退化成「每人一套口径」——表面都有对照，实际互相不可比。症状：同一件事在三个汇报里出现三个不同的改前数值。修法不是加指标，而是砍到一个主口径，其余降为辅助指标。
- **档位**：【经验】（口径的定义方式因业务而异，不给通用阈值）。

**决策记账**

- **做法**：单独维护一份决策清单，每条三栏：当时的不可改约束、被否决的选项及其代价、什么条件下重开。不写过程，只写这三栏。
- **机制**：因为成长的价格由**决策密度**决定而不是年限（主文件 §2.3），所以判断力必须可被计数与引用；写下来是唯一让计数成立的动作。代价是写下判断就要接受质询——没写的东西没人能反驳。
- **失效条件**：**当决策清单只出现在个人笔记里、且不进任何评审场合时**，它从组织资产退化成个人日记。症状：你能想起自己写过，但团队里没人引用过它；新人入职时问「上次为什么这么选」，没人能指向一份文档。
- **档位**：【经验】；ADR 这一做法有公开出处【公开】（Michael Nygard，"Documenting Architecture Decisions"，2011，可按关键词 architecture decision record 检索其当前版本与社区模板）。

**产出的可检索性**

- **做法**：每一件产出物在完成当天，就放到一个「三年后你自己还找得到」的位置，并写一个能被搜到的标题。
- **机制**：因为复利来自**别人引用它**而不是你写完它，所以产出必须进入检索路径；放在即时通讯记录、幻灯片附件、个人电脑里的产出，在组织的信息流里等于不存在。代价是存放位置一旦选定就要长期一致，中途换地方会让索引断档。
- **失效条件**：**当团队的工具栈变更（换 wiki、换代码托管平台）而历史产出没有迁移时**，这条会以「记忆里有、搜不到」的形式坏掉。症状：讨论里出现「我记得之前有人写过一份」，然后所有人开始翻聊天记录。
- **档位**：【经验】。

**覆盖率的定义方式**

- **做法**：任何带覆盖率的 KPI（例如「语义层覆盖 50% 核心指标」「反向映射清单覆盖 80% 核心业务场景」）都先定义分母：按调用频次加权，还是按对象计数。
- **机制**：因为分母的定义方式决定了工作的先后顺序，所以按调用频次加权的 50% 通常只对应少数指标，按对象计数的 50% 可能对应大量长尾——前者的前 20% 就能带来可见收益，后者要到 80% 才看见效果，而后面这段最容易被拖死。
- **失效条件**：**当覆盖率被写进考核、而分母没有写进同一份文件时**，这条会退化成选分母——先把容易覆盖的长尾纳进来冲数字，核心指标反而没人动。症状：覆盖率数字漂亮，但业务方仍在手工提数。
- **档位**：【经验】（百分比是读者的目标值，不是行业基准，按你的调用量分布重算）。

**治理能力挂在流程上**

- **做法**：把 AI 治理的落地拆成三件可检查的事——分级保密（谁在什么级别上能读什么）、全链路审计（谁在何时访问了什么、依据是什么）、输出端防泄露（模型输出不能带出越权内容）；三件分别挂到一次真实上线的门禁上。
- **机制**：因为治理能力的价值只在需要举证的那一刻兑现，所以它必须挂在上线流程上才能被兑现；只做培训不挂流程，能力就停留在培训记录里。代价是门禁会降低上线速度，而这需要先在组织里拿到共识。
- **失效条件**：**当监管适用性没有先判清楚（这套要求管不管我的场景）时**，三件会做成同一套通用模板，落地时与真实业务对不上。症状：审计时能拿出文档，但答不出「这条数据出境是否在评估范围内」。
- **档位**：监管侧依据为公开文本【公开】（欧盟 AI Act（Regulation (EU) 2024/1689）2024 年生效、《生成式人工智能服务管理暂行办法》2023 年 8 月 15 日施行、《个人信息保护法》2021 年 11 月 1 日施行、等保 2.0 对应 GB/T 22239-2019；具体条文与适用时间以文本本身为准）。

**目标先嵌入，小组后成立**

- **做法**：建跨职能小组之前，先把该小组要解决的问题写进各方各自的 OKR，再拉人。
- **机制**：因为小组成员的投入要从自己的考核表里扣，所以只有当目标已经出现在他们的 OKR 上，投入才不需要靠你的个人信用担保。代价是这一步要比「先拉个群」慢两到四周——而它买到的是小组活过第一轮人员变动。
- **失效条件**：**当组织绩效体系只奖励个人产出时**，这条会失效：即使目标写进了 OKR，成员在排序时仍会把小组目标放在末位。症状：例会准时开，交付持续延后，且延期理由都合理。此时正确的动作不是加大协调力度，而是把小组产出改写成各自 OKR 里的一条可交付物。
- **档位**：【经验】。

**发布前的三道判定**

- **做法**：任何要出组织边界的内容（文章、演讲、开源贡献、行业报告），发布前依次过三道：有没有引用内部数据（数据）、有没有暴露内部结构与路线（信息）、组织政策与保密规定允不允许（政策）。三道都过再动手写终稿。
- **机制**：因为公开内容是不可撤回的（会被转载、镜像、缓存），所以判定必须发生在发布**之前**；一旦发出，撤回的只是你的原文，不是别人的副本。代价是涉及内部数据时产出周期会显著拉长【经验】——它把「一周写完」变成「写完再等审」。
- **失效条件**：**当团队里没有人明确负责合规口径时**，这条会以两种相反的方式坏掉：要么什么都发不出去（自我审查过度），要么发出去才发现越界（审查缺失）。判据是「先写完再问能不能发」这个顺序有没有出现过——出现过一次，说明三道判定还没有被当作步骤，只是被当作运气。
- **档位**：【经验】。能发到什么粒度，判据只能来自你所在组织的合规口径与保密规定，不能以「别人发过」为依据；组织口径本身会变，重要节点请以当期规定为准。

### 4.3 工具链与平台

这一节不列「推荐组合」——**选择取决于你被什么约束卡住**。下表按「承载哪类动作的载体」分类，每条给出选型判据与不选它的代价。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 决策与复盘的存放 | 团队 wiki / 代码仓库内的 docs 目录 / 个人笔记软件 | 谁会读它、以及变更时机是否与代码同步：要跟代码一起被评审的，放代码仓库；只给管理层看的，放 wiki；只有你自己回看的，才放个人笔记 | 放错位置的代价是「写了但没人检索到」，等于没写；反过来，把只给自己看的东西塞进评审流程，会在下一次评审被要求补一套格式 |
| 公开产出的发布渠道 | 自建域名的站点 / 技术社区专栏 / 内部知识平台 | 换渠道时读者能否跟你走：有订阅或邮件通道的自建站点可迁移，平台内推荐流带来的读者不可迁移；涉密岗位或受限数据的团队，只能走内部平台 | 把不可迁移的渠道当唯一出口，换公司或换平台时影响力归零；把可迁移渠道当唯一出口，则前 100 个读者要自己一个个找，反馈周期显著变长【经验】 |
| 开源协作平台 | 公共代码托管平台 / 自建 Git 服务 | 你希望谁来参与：要外部贡献者与可核验的公开记录，选公共平台；只在内网使用、或组件含内部依赖，选自建 | 在自建服务上做「开源」，等于把项目锁在没有外部读者的房间里：issue 与 PR 的量级差一到两个数量级【经验】 |
| 团队机制的运行载体 | 目标对齐表 + 固定例会的组织方式 + 决策分层的书面边界 | 先看人数：3–5 人靠每周一次的对齐即可；上到 10–20 人，必须有书面的决策分层（技术细节 / 架构决策 / 业务建议各由谁拍） | 用工具替代机制（买一套 OKR 软件但不定义「什么叫完成」），得到的是填表动作，不是对齐 |
| AI 原生数据栈的基座 | 语义层 / 向量检索 / 图存储 / 编排调度 | 按**已上线的调用方**选：还没有 Agent 或自然语言取数的调用方时，先做语义层与元数据的口径统一；有调用方之后再选向量与图 | 反过来先搭向量与图，常见后果是技术与业务之间没有共同语言，做出来的检索层没人接 |
| 三方协同的运行载体 | 跨部门委员会 + 月度例会 + 反向映射清单 | 按**是否有人被正式指派**选：只有你一个人推动时，别装委员会，先用清单把问题摆到业务方面前；有人被正式指派后，才做成例会制 | 先设委员会再找职责，例会会变成信息通报，缺席率随季度上升【经验】 |
| 度量与回流的载体 | 数据能力到业务结果的指标台账 + 回流评审 | 按**业务方是否认这个指标**选：业务方不认的指标放进台账也没人看，先选一个业务方自己已经在用的业务指标做对照 | 台账变成数据团队的自娱指标，回流评审会上无人对结论负责 |

表里最容易被误选的一项是**决策与复盘的存放位置**：多数人会先挑一个功能最全的个人知识管理工具，把决策记在只有自己能看的地方，再等「有空」搬到团队平台。后果不是丢数据，而是**这份记录从来没有进入过被检索的路径**——半年的决策记录在晋升举证时一条都用不上，因为评审者与后来者根本不知道它存在。正确的顺序是反的：先确定读者与检索入口，再决定用什么工具写。

其次是**发布渠道**：把「粉丝数增长」当渠道好坏的判据，会系统性偏向推荐流平台；而这类增长在你停更三个月后回落得最快【经验】。渠道的第一判据始终是「换平台时读者能不能跟你走」。

### 4.4 存量迁移

这一节面向**已经有存量的人**：你已经做过若干项目、维护着若干张表、带过若干个人。这套行动项在存量上落地，难的不是从零开始，而是**不把历史全部推翻**。

**① 先做什么：立刻见效且可回退**

从「把过去 12 个月最有价值的 3 个决策补写成决策记录」开始，只补三栏（当时的不可改约束、被否决的选项及代价、什么条件下重开），不改动任何历史文档、不动任何系统。它是可回退的：写错了删掉即可。它也是立刻见效的——下一次评审、下一次答辩、下一次面试就能用上。与之并列的第二件事是**给还在被使用的资产补一个能被搜到的标题**，同样零风险。

**② 历史资产怎么分类处理**

不要做全量返工，按下面三类分开：

| 存量类型 | 处理方式 | 判据 |
| --- | --- | --- |
| 还在被多个下游使用的表 / 指标 / 接口 | **只改动的部分**：下一次改动它的时候，顺手补上口径与 Owner，不专门开一次返工 | 这张表下一次被改动距今是否在三个月内 |
| 已经失去调用方、但还在跑的资产（僵尸资产） | **打标挂账**：标成「无下游 / 待确认」，排进清理计划，不投入建模精力 | 过去 12 个月有没有非本人的访问记录 |
| 已完成的项目与决策 | **全部返工只做一件**：补写口径对照与决策记录，不重做技术方案 | 那次决策今天会不会被重新提出一次 |

判断顺序是：先看有没有下游依赖（决定保护还是清理），再看是否即将被改动（决定顺手补还是专门补）。**唯一必须全部返工的是决策记录**——因为它的成本是写作，不是重做系统。

**③ 双轨怎么维持、维持多久**

存量迁移期一定存在两套并行：旧口径的报表与新的语义层 / 新口径，个人笔记与团队可检索的记录。双轨的维持成本主要落在两处——**口径差异的解释成本**与**职责不清时的互相等待**。可行的做法是给每条双轨写一张去向表：

| 双轨 | 谁继续看旧的 | 谁从第一天起只看新的 | 差异由谁解释 | 计划下线时点 |
| --- | --- | --- | --- | --- |
| 旧报表 ↔ 新语义层取数 | 已排期的下游看板与外部报送 | 新建的看板与所有 Agent / 自助取数入口 | 口径负责人（具体到人，不是「数据组」） | 具体日期，或写明退出信号 |
| 个人笔记 ↔ 团队可检索的记录 | 只有你自己 | 所有需要引用这份决策的人 | 你自己（把笔记里的三栏搬进公开位置） | 该决策被引用一次之后 |
| 内部版文档 ↔ 公开版文章 | 内部同事 | 外部读者 | 你自己（脱敏与合规口径以组织规定为准） | 公开版能独立回答 3 个追问之后【经验】 |

维持时长按【经验】设为一个季度到半年，随核心指标的调用方数量增长而缩短。**判断能不能缩短，看的不是时间到了没有，而是上表第三列有没有人真的在解释差异**——这一列空白，双轨就会长期挂着，且每次口径对不上都要重新讨论一次。

**④ 什么信号说明可以退出双轨**

- 核心看板的取数已全部走新链路，且新旧口径对同一天的同一个指标给出相同结果（不是「接近」，是相同）。
- 过去一个季度里，没有人再打开旧的那套（日志可查，而不是靠回忆）。
- 新入职的人在 30 天内能自己找到三个月前的决策记录，且不需要找人问。
- 反向映射清单（见 4.5）上超过八成的核心业务场景，都能指向一个具体的负责人与一个取数入口。

四条都成立就可以下线旧链路。**只满足前两条就下线，是最常见的翻车方式**——旧的还没看，新的还没人能自己找到。

**迁移分几波、每波要谁的授权**

存量迁移最怕的不是慢，而是**一开始就需要别人配合**。按「需要谁的授权」分三波，比按时间排更有效：

- **第一波（你能单独完成的）**：补写决策记录、给还在用的资产改一个有意义的标题、把个人笔记里已经写着的东西搬到可检索的位置。这一波不需要任何人的批准，应在一到两个工作日内做完。
- **第二波（需要一个 Owner 点头的）**：在下次改动某张表 / 某个指标时顺手补口径与责任人、把一条双轨的去向表填出来、把一条口径分歧提交到例会上。这一波的关键是**搭便车**：不专门申请一个项目，而是挂在已经排期的工作里。
- **第三波（需要流程改动的）**：把口径检查挂进变更流程、把治理三件挂进上线门禁、把覆盖率的分母写进考核口径。这一波必须有比你高一级的 Sponsor；没有它就不要开这一波，否则会得到一份没人执行的流程文档。

三波之间的顺序不可换：第一波没做完就推第三波，最常见的结果是「制度发出去了，但底下没有一条真实数据支撑它」——评审时被问一个具体口径，谁也答不上来。

### 4.5 模板 / 示例

**模板一：年度 OKR（可直接抄，含四个目标的完整写法）**

- **O1：成为 AI 时代数据架构领域的内部公认专家**
  - KR1：完成 3 个 RAG / 智能体项目，跑通业务闭环（业务价值 + 影响力）
  - KR2：写 6 篇公开技术博客，每篇 ≥ 1500 字（技术品牌）
  - KR3：在 2 次以上行业大会 / Meetup 上发表演讲（行业影响力）
- **O2：带领团队完成从「集中式中台」到「AI 原生数据栈」的演进**
  - KR1：完成数据语义层（Semantic Layer）的引入与推广，覆盖 50% 核心指标
  - KR2：完成 1 个 AI 治理框架的落地（含分级保密 / 全链路审计 / 输出端防泄露）
  - KR3：培养 2 名 P5 / P6 晋升到 P6 / P7
- **O3：建立「业务 + 数据 + 算法」三方协同机制**
  - KR1：建立跨部门数据治理委员会，月度例会
  - KR2：建立「业务需求 -> 数据能力」的反向映射清单，覆盖 80% 核心业务场景
  - KR3：建立「数据能力 -> 业务结果」的度量与回流闭环

**怎么用**：填的是 KR 里的**分母与判据**，不要照抄数字——三个目标里的百分比与数量都是**读者的目标值【经验】**，不是行业基准。O2-KR1 的 50% 要先写下是按调用频次加权还是按指标个数计（见 4.2「覆盖率的定义方式」）；O3-KR2 的 80% 要写下「核心业务场景」由谁认定。三条 KR 里若有两条的验收方式都是「完成某件事」而没有可查的留痕，把它们改成能拿出物证的写法。

**模板二：1000 字复盘（四个格子，不写流水账）**

```text
标题：<决策名> —— 复盘（<日期>）

[1] 当时的不可改约束（只写事实）
    · 时间 / 人力 / 数据 / 合规上分别卡在哪
[2] 被否决的选项与它的代价（最贵的一段，必须写）
    · 备选 A：<做法> → 代价：<具体代价>
    · 备选 B：<做法> → 代价：<具体代价>
[3] 决策与代价（我付出了什么）
[4] 什么条件下要重开这个决策（写成可判定的条件）
```

**怎么用**：`[2]` 不要写成「也考虑过另一种方案」，要写出**那个方案具体会付出什么代价**；写不出来，说明当时没有真正比较过。`[4]` 是这份文档唯一的触发器，缺了它，复盘会退化成事后合理化。

**模板三：「业务需求 -> 数据能力」反向映射清单**

| 业务动作 | 现在怎么做的 | 需要的数据能力（输入 / 输出） | 现状口径 | 由谁负责 | 取数入口 |
| --- | --- | --- | --- | --- | --- |
| {业务动作} | {手工提数 / 看某张报表} | {需要什么输入，产出什么} | {当前口径与刷新时间} | {具体到人} | {链接 / 表名} |

**怎么用**：从「现在怎么做的」这一列开始填，不要从「需要什么能力」开始——后者的常见写法是把技术方案当需求。`现状口径` 与 `由谁负责` 两列是用来暴露问题的：填不出来的行，就是当前最没人管的那部分业务。

**模板四：大型技术决策记录（自研 vs 采购 / 集中 vs 联邦 / 上云 vs 下云）**

| 维度 | 选项 A | 选项 B | 判据来源 |
| --- | --- | --- | --- |
| 不可改的约束（谁定、期限） | | | |
| 一次性成本 / 持续成本 | | | |
| 最坏情况的代价与可回退路径 | | | |
| 决定它成立的前提（什么一旦变化就要重开） | | | |

**怎么用**：`决定它成立的前提` 一栏是这张表的重点，它让这次决策在未来可被推翻；「谁定、期限」一栏用来区分真约束与偏好——把偏好写在约束栏里，是这类决策最常见的失真。

**模板五：三方协同机制的月度例会议程（30 分钟版）**

```text
跨部门数据治理委员会 · 月度例会（30 分钟）
  0–5  min  上期行动项复查：只过「已关闭 / 仍打开」两态，不讨论原因
  5–15 min  反向映射清单增量：本期新填了哪几行、哪几行的「由谁负责」还空着
  15–25 min 一件具体的口径分歧：由数据方说现状口径、业务方说期望口径、
            业务方与数据方各写一句「谁承担差异的后果」
  25–30 min 决定：本期关闭什么、下期开什么（各写在清单上，不留口头结论）
  ────────────────────────────────────────────────
  入场条件：每一行清单都已经有「业务动作」与「现状怎么做的」两列
  退出条件：连续两次会没有任何口径分歧被提交 → 例会应降频或停办
```

**怎么用**：议程里唯一不可省的是「谁承担差异的后果」这一句——它把口径分歧从技术问题拉回业务决策，也是这个机制能不能持续的关键。如果你的组织里没有人愿意在那一栏写名字，说明例会应该先停，改用一对一沟通把问题摆到具体负责人面前（见 4.3 表里「三方协同的运行载体」的选型判据）。

### 4.6 自检清单

1. 你的简历 / 主页上有没有一个别人能复述的定位？找一个不认识你项目的同行读 60 秒，看他能不能说出你解决哪类问题。
2. 过去 12 个月的决策里，有几条你写下了「被否决的选项及代价」？零条，则 Step 1 未完成。
3. 打开最近一次公开产出（文章 / 分享 / 仓库），有没有一个非同事的人留下过具体问题？没有，则产出还没进信息流。
4. 抽样一份项目材料，改前 / 改后的口径是不是同一个？口径中途换过，这次对照就不成立。
5. 你的决策记录放在哪里，一个新入职的人能不能在 30 天内自己搜到它？搜不到，则存放位置选错了。
6. 带一个 0→1 项目时，三方（数据 / 算法 / 业务）能否说出同一句「什么叫成功」？说不出，则小组还不能成立。
7. 你带的人里，有没有人的晋升材料「关键项目」一栏由你署名？没有，则范围扩张还没有发生。
8. 团队人数超过 10 人后，你有没有写下「技术细节 / 架构决策 / 业务建议」分别由谁拍？没写，则所有决策仍堆在你这一层。
9. 涉及 AI 上的三件治理动作（分级保密 / 全链路审计 / 输出端防泄露），你能不能当场演示一次「哪些数据含个人信息、谁访问过、依据是什么」？
10. 抽查一条带覆盖率的 KR，分母写在哪个文件里、由谁认定？写不出，则这个数字随时可以改口径。
11. 反向映射清单里，「由谁负责」这列填不出来的行有几条？超过两成，则清单还没成为管理工具。
12. 你的存量资产里，有多少张表在过去 12 个月没有非本人的访问记录？有名单（哪怕只是可查的来源），才谈得上下一步清理。

### 4.7 小结

> 本节小结：整个落地过程里唯一决定成败的环节，是 **Step 1 的那份决策记录**——不是因为它最难，而是因为它是**后面每一步的红利能否被兑现的那个前提**：没有它，Step 3 的范围扩张拿不出可追溯的结果，Step 4 的跃迁材料写不出「问题 → 约束 → 决策 → 结果」四段。它的成本最低（一小时内可完成一次）、可回退（写错删掉即可）、且立刻可用，所以它比其余环节都更值得先投入。把它排在第一位、并且坚持每条只写三栏，是这个主题下性价比最高的一个动作。
>
> 💡 **思考锚点**：按 Step 1 的判据翻你自己的「过去 12 个月最有价值的决策」复盘——里面写下了被否决的那个选项和它的代价吗？没有，它就只是结论、不是资产；再往前一步：Step 4 的答辩材料四段（问题 → 约束 → 决策 → 结果），你现在能逐段写出的是哪几段？
