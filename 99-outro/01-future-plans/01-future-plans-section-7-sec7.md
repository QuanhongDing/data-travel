## 7. 推荐行动 / 推荐阅读

### 7.1 先立判据：为什么「推荐清单」会误导

清单的写法天然回避了四个问题：**给谁与在什么阶段、代价是什么、反馈周期有多长、以及不做什么**。

清单的第一个问题：**它给所有人配了同一套权重**。同一份清单，在 P6 的 IC、刚转管理的团队负责人、以及带 30 人团队的架构师手里，权重是相反的。对还缺「判断框架」的人，多做项目只会重复既有经验；对已经能判断但推不动事的人，再读十本书也换不来一次授权——后者缺的不是认知，是别人愿意把范围交给他的那个前提。（[§5 §5.3](01-future-plans-section-5-sec5.md) 的「角色错位」讲的是相邻的另一半：资深 IC 假装 Leader、Tech Lead 假装架构师这类错位，源于用当前生态位的能力去顶下一个位置；本节补的是它的下游——范围本身从哪来。）

清单的第二个问题：**条目的成本被隐藏**。每一条看起来都只是「做一下」，但把它们排进同一张表时，读者会默认它们可以同时进行。第 7.4 节会把这份清单换算成小时数——结论是它需要的时间超过多数人一年可支配的学习时间，**所以清单的正确用法是做减法，不是做加法**。

清单的第三个问题：**反馈周期被隐藏**。读一本书的反馈周期可能是几个月（甚至几年后才发现方向选错），写一篇博客的反馈周期是几天（有没有人读、有没有人反驳）。把两类混在一张清单里，人会不自觉地优先做前者——因为它不需要面对否定。

清单的第四个问题：**只写做什么，不写不做什么**。而时间预算是固定的：任何一项新增，都意味着从另一项里扣。一份有效路线图的标志不是它列了多少，而是它明确放弃了什么。

还有一件常被误解的事：**清单不是路线图**。清单是「别人做过什么」的集合，路线图是「在你的约束下，接下来 12 个月做哪三件」的选择。前者可以很长，后者必须很短——7.4 的时间账会说明为什么。

最后是「推荐」这个词本身的边界：**任何推荐都只相对于推荐者的约束成立**。同一本书对一个正在做选型的人有用，对一个连数据源都没接齐的人就是负担。所以本章在 7.6 给出的是「你的处境 → 首选」，不是「最好的三个动作」。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定取舍 |
| --- | --- | --- |
| 缺口的种类 | 我缺的是判断框架、操作细节、组织授权，还是外部信号 | 四类缺口的解法不通用：认知类读物解决不了授权问题，多做项目也解决不了认知盲区 |
| 反馈周期 | 我多久能知道「这次做错了」 | 长周期投入必须搭配短周期项来校准，否则几年里得不到一次纠错信号 |
| 时间预算形态 | 我的时间是碎片（≤1 小时）还是整块（半天以上） | 与真实时间形态不匹配的清单必然烂尾，与意志力无关 |
| 可验证产出 | 做完之后，别人能看见什么 | 没有产出物，行动就进不了组织的信息流，也换不来更大范围的事 |
| 可迁移性 | 换公司、换行业、换角色后它还成立吗 | 只在当前组织成立的投入是岗位投资；能力投资的判断标准是能否带走 |
| 复制风险 | 这件事是不是同行都在做 | 输入类动作（读书、课程）几乎没有区分度，区分度来自「你做成了什么」 |

**判据怎么用（三步，不是打分）**：

1. 先用「缺口的种类」定位到族——4 类缺口对应不同的族，走错族的话后面做得越努力越偏（7.5 节点 ①）；
2. 再用「时间预算形态」筛掉你根本推不动的条目——碎片时间做不了整块任务，这一条淘汰掉的条目通常最多；
3. 最后用「反馈周期」给留下的条目配判据——**没有判据的长周期投入，一律先砍**（7.3.3）。

### 7.2 候选清单与分族（原清单条目全保留）

先把原清单的条目按时间轴原样列出（含原稿的具名平台与条件从句）——本章的比较以它们为候选，**不删减**：

- **本周**：把个人定位调整为「AI 时代数据架构师」并更新 LinkedIn / 简历 / GitHub；约 3 位同 level 或高一 level 的 Mentor 做一次交流；把过去 12 个月最有价值的 3 个决策写成 3 份 ADR。
- **1 个月内**：完成一个 RAG / 智能体 / 知识图谱个人 Demo；写第 1 篇公开技术博客；加入 1 个开源项目（哪怕只是 issue 回复）。
- **3 个月内**：完成 1 次公开技术分享（公司内 / Meetup / 大会）；主导 1 次跨团队 ADR 评审；完成 1 个 AI 治理 / 数据合规培训（信通院 / DAMA / CDA 任一）。
- **6 个月内**：主导 1 个 0→1 的 AI 项目；培养 1–2 个下属晋升；建立 1 个跨职能小组。
- **1 年内**：完成 P7 → P8 / 资深 → 准资深的跃迁（如果你还没到）；在行业内建立「内外部公认」的专家形象；主导 1 次组织级变革。

**再按机制分族。** 这些条目只属于八族，同族内部可以互换、跨族不能互相替代：

| 族 | 条目 | 它改变的变量 | 反馈周期 | 主要成本 |
| --- | --- | --- | --- | --- |
| 显性化族 | 3 份 ADR、跨团队 ADR 评审、1000 字复盘 | 你的判断被他人复用的概率 | 数周（评审时就能看到反馈） | 一次性 4–20 小时【经验】 |
| 可见产出族 | 定位与主页更新（LinkedIn / 简历 / GitHub）、个人 Demo、公开博客、公开技术分享、开源项目参与 | 你在组织与行业信息流中的可得性 | 数天到数周 | 每件 8–40 小时；定位与主页更新为一次性 4–8 小时【经验】 |
| 组织授权族 | 0→1 AI 项目、培养下属晋升、跨职能小组、组织级变革、P7 → P8 跃迁 | 你可以决策的范围（授权边界） | 1–3 年 | 主要占本职工作时间 |
| 关系与信号族 | 约 3 位 Mentor、行业专家形象、治理 / 合规培训（信通院 / DAMA / CDA） | 外部信息源与背书 | 数周到数月 | 年 10–40 小时【经验】 |
| 认知框架族 | 《第一性原理》相关与《埃隆·马斯克传》、《长期主义》（罗杰·马丁）、《原则》（瑞·达利欧）、《奈飞文化手册》、《Data Mesh》（Zhamak Dehghani）、《Designing Data-Intensive Applications》（Martin Kleppmann） | 你判断问题的起点 | 数月至数年 | 每本 8–20 小时【经验】 |
| 工程细节族 | 《Knowledge Graphs》（Aidan Hogan 等）、《Designing Machine Learning Systems》（Chip Huyen）、《AI Engineering》（Chip Huyen）、《数据中台实战》、《Building the Data Lakehouse》（Bill Inmon 等） | 你落地的具体手法 | 数周到数月（读完即可动手） | 每本 8–20 小时【经验】 |
| 持续信号族 | The Pragmatic Engineer、Byte Byte Go、Import AI、The AI Engineer、Papers With Code | 你的信息更新速度 | 每周 | 每周 0.5–1 小时【经验】 |
| 工具与社区族 | LangChain / LlamaIndex；dbt / Cube；Apache Airflow / Dagster / Prefect；Milvus / Weaviate / Qdrant；Neo4j / NebulaGraph；OpenTelemetry / Grafana / Prometheus；社区 GitHub / Hugging Face / LangChain / dbt / Data Mesh Learning；会议 DataFun / AICon / QCon / ArchSummit / DTCC 与 Strata Data Conference / Spark Summit / KubeCon / ODSC / Ray Summit | 你的动手能力与同行连接 | 数天 | 按项目量级，无固定值 |

表中的书名、专栏名与项目名以公开出版物与仓库为准。**作者只写在对应关系确凿的条目上**（《长期主义》与罗杰·马丁、《原则》与瑞·达利欧、《Data Mesh》与 Zhamak Dehghani、《Designing Data-Intensive Applications》与 Martin Kleppmann，以及 Chip Huyen、Aidan Hogan、Bill Inmon 的几种）；其余条目（《第一性原理》相关与《埃隆·马斯克传》、《奈飞文化手册》、《数据中台实战》）只列书名，具体署名与版次请以你所持版本的版权页信息为准。

**分族之后要看清的一件事**：八族里只有**可见产出族**与**显性化族**能在一年内产出别人看得见的东西；**组织授权族**的时间尺度最长，但它决定后面所有动作的天花板；**读物与信号**是输入，不构成产出。原清单把这三类混在一条时间轴上，读起来像是「本周做三件、一年后做三件」，实际它们的**反馈周期差了近两个数量级**（数天 vs 数年）。

进一步按产出形态分，清单里的条目只有三类，**三类不可以互相替代**：

- **输入类**（读物、专栏、培训）：成本可预算，产出不可见，反馈周期最长；
- **产能类**（ADR、Demo、博客、分享、开源）：产出可见，成本随件数线性增长，反馈周期数天到数周；
- **范围类**（带人、跨职能小组、0→1 项目、组织变革）：产出是「别人交付的东西」，成本超线性，反馈周期以年计。

输入类做得再多也换不来范围类的结果，范围类做得再多也补不上判断盲区——**清单之所以让人焦虑，是因为它把这三类并列成一张勾选表**。

**会议与社区的定位要说清**：7.2 的分族表把会议（DataFun / AICon / QCon / ArchSummit / DTCC，以及 Strata Data Conference / Spark Summit / KubeCon / ODSC / Ray Summit）与社区（GitHub / Hugging Face / LangChain / dbt / Data Mesh Learning）整行放在**工具与社区族**——该族改变的变量是「你的动手能力与同行连接」，与关系与信号族的「外部信息源与背书」（Mentor、专家形象、治理合规培训）不是一回事。它们真正的价值来自 7.3.2 的**信号机制**：见到人、听到别处怎么做。但如果只参会不动手，就等于把它们当输入类动作使用——成本花掉了，产出没有。**判据很简单：一次会议/社区投入之后，你有没有留下一个可被别人检验的产出（一段代码、一篇文章、一次分享）；没有，它就只是输入。**

### 7.3 机制差异：为什么同样的动作，效果差很多（核心节）

#### 7.3.1 显性化机制：把隐性判断变成可被复用的资产

- **机制是什么**：一次决策的价值，只在它被别人复用时才算数。写 ADR / 复盘不是记录，而是把你的判断从「只存在于你的脑子和会议里」变成**组织可检索的资产**。
- **它在各族中的实现差异**：

| 动作 | 显性化的是什么 | 复用者 | 缺少它会怎样 |
| --- | --- | --- | --- |
| ADR（架构决策记录） | 选项、判据、被否决的方案与理由 | 后来的同事、评审会 | 同一个坑几年后被第二拨人重踩 |
| 复盘（1000 字） | 结果与预期的偏差及原因 | 自己、你的上级 | 经验停在「感觉」层面，无法迁移 |
| 跨团队 ADR 评审 | 让判断经受外部质询 | 其他团队 | 判断的边界条件不被发现，直到事故 |

- **由此必然导出的性质**：因为决策的复用依赖它被写下来，**所以**显性化的第一收益不是「显得专业」，而是让同一个判断被用第二次、第三次，**代价是**写下来的判断会被检验——没写的东西没人能反驳，写下来就要接受质询；也**因为**它改变的是信息的存在形式而非你的能力，**所以**这一族的成本最低、见效最快（数周），**代价是**它对能力上限没有提升，只让能力被看见。
- **公开证据**：这种「把决策与理由一并留档」的实践在软件工程中的常见源头是 Michael Nygard 2011 年关于架构决策记录的文章；使用者可按「architecture decision record」这一关键词检索其当前版本与社区模板。本书不对该实践的创始人归属作排他性断言。
- **失效条件**：当组织里没有人读这些文档、评审流程形同虚设时，显性化退化为写作练习——此时正确的动作不是写得更多，而是先争取一个**真的会开会评审**的场合（7.3.4）。
- **判定方法**：翻你过去一年参与过的评审记录，其中有多少份留下了「为什么否决了另一个方案」。没有的话，你所在的流程缺少显性化的位置，先补流程再补写作。

#### 7.3.2 信号机制：公开产出改变的是「被发现」的概率，不是能力

- **机制是什么**：机会（项目、岗位、合作）的分配依赖信息在决策者那里的可得性。公开产出（博客、分享、开源）改变的是这条信息流，而不是你的能力本身。
- **它在各族中的实现差异**：

| 动作 | 放进信息流的是什么 | 生效范围 | 维护代价 |
| --- | --- | --- | --- |
| 公开博客 | 你解决过什么问题、怎么想的 | 组织外为主 | 一旦开始就有持续产出的预期 |
| 开源贡献 | 可被他人直接复用的代码与判断 | 组织外，可验证 | 要跟进 issue 与版本 |
| 内部公开分享 | 你在组织内的可见度 | 组织内 | 低，但换公司即归零 |
| Mentor 交流 | 双向：你获得外部视角，对方获得你的近况 | 小范围、高信噪比 | 年 10 小时量级【经验】 |

- **由此必然导出的性质**：因为信号只影响「被发现」而不影响「能力」，**所以**在能力不足时放大信号会带来反噬——被找来之后答不出细节，一次信任损耗很难修复，**代价是**你必须先有可被追问的内容；反过来，**因为**能力充分而信号为零时机会与你无关，**所以**「做成了」与「被知道做成了」是两件都需要投入的事，**代价是**信号一旦建立就产生持续的产出预期，停下来会在同一条信息流里留下空档。
- **公开证据**：本书能给出的可核验材料只有技能培训与信息类资源本身（如表中专栏与会议），**没有可引用的、把「公开产出」与晋升结果量化关联的公开研究**。这一条按【经验】对待：多数技术组织在评审「影响力」时确实会看外部产出，但权重与口径由各组织自行规定。
- **失效条件**：在只看内部贡献的组织（或涉密岗位）里，外部信号的权重接近于零，此时应把同等时间投入组织授权族；反之，在跳槽或转行的时间窗口里，内部可见度的可迁移性最低。
- **判定方法**：搜索你自己的名字，看最近一年有没有组织外的人主动引用过你的产出。「没有」是可见度问题，不一定是能力问题。**两种错配的修法相反**：能力领先信号的人要补产出，信号领先能力的人要补能力——方向搞反会让错配加深。

#### 7.3.3 反馈周期机制：不同资源的纠错速度差近两个数量级

- **机制是什么**：一项投入的价值，取决于它多快能给你一次「你错了」的信号。输入的反馈周期最长（读的时候没有任何判据检验你理解得对不对），真实项目的反馈周期最短（跑不通就是跑不通）。
- **它在各族中的实现差异**：

| 资源 | 反馈周期 | 反馈来自谁 | 纠错一次的成本 |
| --- | --- | --- | --- |
| 工具 / 开源项目 | 数小时到数天 | 编译器、测试、运行结果 | 低（改一行重跑） |
| 公开产出 | 数天到数周 | 读者、评审、同行 | 中（改观点或补证据） |
| 持续信号（专栏 / 社区） | 每周 | 同行与行业动态 | 低，但信息半衰期短 |
| 工程细节类读物 | 数周到数月 | 自己的实践对照 | 中（要落到一个项目上才成立） |
| 认知框架类读物 | 数月至数年 | 真实决策的结果 | 高（方向选错要重来） |
| 组织授权族 | 1–3 年 | 组织里的实际结果 | 最高（时间不可回收） |

- **由此必然导出的性质**：因为反馈周期长的投入在过程中不产生纠错信号，**所以**它必须挂上一个短周期的判据才能安全投入——每读一本书配一次可验证产出（一次决策、一篇文章、一段代码），把「读完了」改成「用上了」；**代价是**这样做的速度看起来更慢，一年读不完二十本，**换来的是**你能在几周内发现方向错了，而不是几年后才发现。
- **公开证据**：【公开】关于「练习需要及时反馈才有效」的论述，常见源头是 Ericsson 与其合作者 1993 年关于刻意练习的研究（Ericsson, Krampe & Tesch-Römer, 1993）；该书讨论的是技能习得的一般条件，不是「读书无用」的结论，具体结论范围请以原文为准。
- **失效条件**：当你的岗位本身就提供短周期反馈（每天上线、每周复盘）时，额外为阅读设计判据的边际收益下降；反之，在一年只做一两个大决策的岗位上，不加判据的长期投入风险最高。
- **判定方法**：给你今年的每一项学习投入写下「多久之后能知道它对不对」。写不出来的，就是缺判据的那一类。

#### 7.3.4 授权机制：跨过一个层级靠的是可被授权的范围

- **机制是什么**：层级跃迁的门槛通常不是技能指标，而是**你被允许独立决策的范围**。范围扩张来自两件事：有人愿意把人或事交给你，以及你此前交出的结果可被追溯。
- **它在各族中的实现差异**：

| 动作 | 扩张的是哪种范围 | 谁在观察 | 见效时间 |
| --- | --- | --- | --- |
| 主导 0→1 项目 | 从「做模块」到「定方案」 | 项目干系人与上级 | 1 年内 |
| 培养下属晋升 | 从「自己产出」到「他人产出」 | 上级与人力资源流程 | 1–2 年 |
| 建立跨职能小组 | 从「单团队协调」到「跨团队协调」 | 多个团队的负责人 | 1 年内 |
| 主导组织级变革 | 从「跨团队」到「改规则」 | 组织高层 | 2–3 年 |
| 公开产出与行业形象 | 范围之外的影响力（不能替代授权） | 组织外 | 视组织规定 |

- **由此必然导出的性质**：因为授权来自「范围」，**所以**能力强但不带人、不接跨团队的事的人会停在一个位置上——不是被否定，而是没有被交出去过更大范围，**代价是**扩张范围必然切碎你的时间：带人的时间从你的产出时间里扣，跨职能小组的协调成本随人数超线性上升（按协作边数 n(n−1)/2 计，5 人小组是 10 条，8 人升到 28 条），**所以**再高产的 IC 也会在范围扩张后出现个人产出下降，这部分不算「能力退步」。
- **公开证据**：关于管理幅度与授权的研究，在管理学中通常可追溯到 1970–1980 年代对管理者实际工作与授权的实证研究；本书不指定单一出处，仅把它当作【经验】档的判断依据。更可靠的判定入口是你所在组织晋升标准里的「范围」类条款，而不是管理学著作。
- **失效条件**：在扁平化、以专家序列为主的组织里，带人不是必需的扩张路径——此时改走「深度 + 公开产出」的 IC 路线，用「技术方案的最终决定权」替代「团队规模」；反之，在管理序列主导的组织里，不带人的 IC 会在授权环节系统性落后。
- **判定方法**：读你所在组织的晋升标准，「范围」类条款（带人、跨团队、定规则）占几项。管理序列主导的组织里，这一项通常是硬条件。

**四个机制合起来看**，它们锁死四件不同的事：

- 7.3.1 决定**你的判断能不能被别人复用**；
- 7.3.2 决定**机会会不会找到你**；
- 7.3.3 决定**你多久能发现自己错了**；
- 7.3.4 决定**你能拿到多大的范围**。

四件事都不满足时，最容易的做法是继续读书——它成本最低、当下最舒服，而且不会立刻暴露问题。**这正是本节要拦住的那种路径。**

### 7.4 成本结构对比（不是书单，是时间账）

每个族的时间成本**随什么增长**：

```text
年度投入 ≈ 固定投入（书目 / 课程，可预算、一次性）
         + 产能投入（写作、Demo、分享准备，随件数线性）
         + 节奏投入（专栏、社区、开源维护，随周数线性）
         + 组织投入（带人、小组、评审，超线性：协作边数 ~ n(n−1)/2）
         + 隐性投入（读完之后的消化与复用，最常被漏算）
```

**【推算】把原清单换算成小时**：年量按清单要求外推（原清单只要求「第 1 篇博客」，这里按**每两个月一篇**的常见节奏取 6 篇）。单位时间是【经验】区间，括号内是本节为该行取定的**点估值**——13 行里 9 行直接取区间中位（如 ADR 4–8 取 6、Demo 20–40 取 30），4 行取区间内更顺手的整值（分享 12–30 取 20、治理 / 合规培训 20–40 取 28、读物 8–20 取 10、专栏 0.5–1 取 1）；「年投入」一律按括号内的值折算，得到的是一组可以逐行验算的数。之所以不用区间逐行相乘再相加——13 条同时顶格执行并不现实，端点相乘会把区间放大到没有信息量的宽度——所以正文引用点估口径，并在合计后用区间下限做一次对照。

| 条目 | 单位时间【经验】（点估） | 年量 | 年投入（小时，按点估折算） |
| --- | --- | --- | --- |
| 定位与主页更新（LinkedIn / 简历 / GitHub） | 4–8 小时（6） | 1 次 | 6 小时 |
| ADR | 4–8 小时 / 份（6） | 3 份 | 18 小时 |
| 1000 字复盘 | 3–5 小时（4） | 1 份 | 4 小时 |
| RAG / 智能体 Demo | 20–40 小时（30） | 1 个 | 30 小时 |
| 公开博客 | 6–10 小时 / 篇（8） | 6 篇 | 48 小时 |
| 开源项目参与 | 1–3 小时 / 周（2） | 52 周 | 104 小时 |
| 公开技术分享（含准备） | 12–30 小时（20） | 1 次 | 20 小时 |
| 跨团队 ADR 评审 | 6–10 小时（8） | 1 次 | 8 小时 |
| 治理 / 合规培训 | 20–40 小时（28） | 1 次 | 28 小时 |
| 培养下属 | 1–3 小时 / 周（2） | 52 周 | 104 小时 |
| 跨职能小组 | 1–3 小时 / 周（2） | 52 周 | 104 小时 |
| 读物（认知 + 工程各取几本） | 8–20 小时 / 本（10） | 8 本 | 80 小时 |
| 专栏 / Newsletter | 0.5–1 小时 / 周（1） | 52 周 | 52 小时 |

- 合计 ≈ **606 小时 / 年** ≈ **11.7 小时 / 周**（点估口径；13 条全部取下限为 359 小时、全部取上限为 897 小时）。**这个合计只含表内 13 行的显性投入，不含隐性投入**——把读物「读完之后的消化与复用」（见本节末，40–80 小时 / 年）也算进去，量级是 646–686 小时 / 年。
- 其中产生在本职工作时间内、不占个人可支配时间的部分（培养下属 + 跨职能小组 + 内部评审）= 104 + 104 + 8 = **216 小时**
- **落在个人可支配时间内的 = 606 − 216 = 390 小时 / 年 ≈ 7.5 小时 / 周**（同样不含读物的隐性投入；计入后为 430–470 小时 / 年）

对照：一名在职架构师每周可支配的深造时间通常在 **5–8 小时**【经验】，即年 260–416 小时。**390 小时相当于可支配时间的 94%–150%**（显性口径）——照单全收的结果，是几乎把全部可支配时间交给这份清单，且在最紧的情况下还差约 50%。即便退一步，13 条全部按【经验】区间的**下限**计（合计 359 小时，其中本职时间 110 小时），仍有 249 小时落在个人可支配时间里，占预算的 **60%–96%**。**这就是「清单必须做减法」的算术依据**，不是态度问题。

**【推算】反过来看「只做三件事」**：3 份 ADR（18 小时）+ 1 个 Demo（30 小时）+ 6 篇博客（48 小时）= **96 小时 / 年 ≈ 每周 1.8 小时**，落在多数人可支配预算的 **23%–37%** 之间，剩下的时间可以留给组织动作与真实项目。**清单越短，完成率越高——这不是修辞。**

**哪一项可以先砍**：

| 条目 | 砍掉它损失什么 | 什么时候可以先砍 |
| --- | --- | --- |
| 读物（8 本） | 判断框架的输入 | 手上已有真实项目时，项目会给你更贴合的输入 |
| 专栏订阅（5 个） | 信息更新速度 | 正在一线做相关项目时，项目的信息更新更快 |
| 跨职能小组 | 跨团队协调的范围 | 还没有一个稳定交付的项目时，小组会退化成开会 |
| 组织级变革 | 规则层面的范围 | 前一步（跨团队）还没做成时 |
| 公开技术分享 | 外部信号 | 组织内已无可见度问题时，先补内部更划算 |

**原清单把读物单列成一张书单、不给任何时长，而它恰恰是按「读完 + 用上」计价后最重的一项。** 读物的单位成本（每本 8–20 小时）看起来可控，但它的反馈周期最长；8 本 × 10 小时 = 80 小时只是读的时间，加上消化与落到一个项目上按 1.5–2 倍计为 120–160 小时，超过表内其余任何一行（最大的三项是开源参与、培养下属、跨职能小组，各 104 小时），而它挤掉的正是唯一能给你纠错信号的那些短周期动作。**砍清单时先看反馈周期，再看小时数。**

**两个容易被低估的成本**：

- **协调成本随人数超线性**：跨职能小组按协作边数 n(n−1)/2 计，5 人是 10 条、8 人是 28 条；把小组扩到 8 人却不减目标，时间会花在同步上。
- **读物时间必须按「用上」计价**：8 本 × 10 小时只是读完的成本，加上消化与落到一个项目上，实际是 1.5–2 倍【经验】，即额外 40–80 小时/年。

### 7.5 决策树（每个分支都要有阈值依据）

```text
[① 你现在缺的是哪一类？]
   ├── 判断框架（拿不准该不该做） → 认知框架族 1–2 本 + 显性化族（ADR / 复盘）
   ├── 操作细节（知道要做什么，做不出来） → 工程细节族 + 亲手做一个 Demo
   ├── 组织授权（看得清但推不动） → 组织授权族优先（带人 / 跨职能小组 / 0→1 项目），读物降为辅助
   └── 外部信号（做成了没人知道，也找不到人问） → 关系与信号族（外部 Mentor / 会议 / 社区）
          ↓（无论哪一类，都继续回答下面几问）
[② 你的可支配时间是什么形态？]
   ├── 碎片（每天 ≤ 1 小时） → 持续信号族 + 写作（单篇可拆）+ 工具与社区族的小任务
   └── 有整块（每周半天以上） → Demo / 文章成稿 / 分享准备（它们无法拆成 20 分钟一段）
[③ 过去 12 个月有没有 ≥ 3 个值得写下来的决策？]
   ├── 有 → 先写 ADR（成本最低、复用率最高）
   └── 没有 → 先争取一个跨团队任务去「制造决策」，再写
[④ 你的产出物在近 6 个月有没有被 3 个以上组织之外的人引用过？]
   ├── 有 → 维持节奏，不必再加平台
   └── 没有 → 优先补可见产出族，而不是再加输入（书 / 课程）
[⑤ 你现在带人吗？]
   ├── 带 → 加组织授权族的动作（培养下属 / 跨职能小组），它们同时扩张授权范围
   └── 不带 → 走 IC 路线：技术深度 + 可见产出；组织族条目暂缓
[⑥ 你同时并行的「长反馈周期」投入超过 2 项了吗？]
   ├── 没有 → 按当前组合继续
   └── 超过 → 砍到 1–2 项，把腾出的时间给短周期项（工具实操 / 公开产出）
```

**阈值依据**（与树上 ①–⑥ 一一对应）：

- **①**：依据是「四类缺口解法不通用」（7.1 判据一）——判定方法是回想最近一次卡住时的**具体情形**：想不清该不该做（判断框架）、知道要做什么却做不出来（操作细节）、判断对了却推不动（组织授权）、做成了却没人知道也找不到人问（外部信号）。四类分别落到认知框架族、工程细节族、组织授权族、关系与信号族（7.2 分族表）；走错族的话，后面越努力越偏。
- **②**：依据是任务的**可切块性**（7.3.3 表格）：写作与代码可按 1 小时一段推进，Demo、成稿与分享准备需要连续 3 小时以上的区间【经验】；把整块任务放进碎片时间，是最常见的烂尾原因。
- **③**：阈值取 3 个决策，依据是可交付集的最小规模：3 份 ADR 按每份 6 小时计共 18 小时，是一个季度内可完成的量【经验】；少于 3 个说明你手上没有可复用的判断样本，此时该先去制造决策。
- **④**：阈值取「6 个月内 3 次外部引用」，依据是信号机制（7.3.2）：低于这个量级说明问题在可见度不足而不是能力不足【经验】；达到之后继续加平台的边际收益很小，时间应转向组织授权族。
- **⑤**：依据是授权机制（7.3.4）——带人是获得授权最直接的路径；同时注意它占的是本职工作时间（7.4 的账里，培养下属 + 跨职能小组 + 内部评审共 216 小时不计入个人可支配时间）。
- **⑥**：阈值取 2 项，依据是 7.4 的时间账：读物一项按 8 本计已占个人可支配预算的两到三成（80 / 390 ≈ 20.5%，80 / 260 ≈ 31%），再并行第三项长周期投入就会挤掉短周期校准项，你将在几个月内收不到任何纠错信号。

**这棵树的读法**：先走 ① 定位缺口，再用 ② 筛掉推不动的形态，然后用 ③④ 决定先补显性化还是先补可见度，最后用 ⑤⑥ 决定要不要加组织动作、要不要做减法。**每一步只用一条判据**；把 ⑥ 提前（一上手就并行五项）是最常见的崩法。

### 7.6 选型矩阵与组合

| 你的处境 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 拿不准方向，决策时反复摇摆 | 认知框架族 1–2 本 + ADR | 找 Mentor 对话 | 只读书：认知类反馈周期数月至数年，读的时候没有判据检验你理解得对不对 |
| 方向清楚，就是做不出来 | 工程细节族 + 一个 Demo | 参加培训 | 只上培训：输入增加而产出为零，能力不进组织的信息流 |
| 判断清楚但推不动事 | 组织授权族（带人 / 0→1 项目 / 跨职能小组） | 行业形象建设 | 先建外部形象：它换不来内部授权，组织内的事仍然推不动 |
| 时间高度碎片 | 持续信号族 + 博客 + 开源小任务 | 小组负责制 | 整块任务（Demo / 成稿）在碎片时间里烂尾率最高 |
| 每周有整块时间 | Demo + 文章成稿 + 分享准备 | 小组协调 | 把整块时间用于刷专栏：可切块任务在碎片时间也能做，整块时间用在这里是浪费 |
| 组织内没有可交流的人 | 会议 / 社区 + 外部 Mentor | 内部读书会 | 只在内部找：缺少外部视角，判断的边界条件不被发现 |
| 计划换行业或换公司 | 可见产出族 + 工具与社区族 | 内部晋升准备 | 只堆内部可见度：换公司即归零，可迁移性最低 |
| 已带团队，要扩范围 | 培养下属 + 跨职能小组 | 组织级变革 | 直接上组织级变革：协调成本随人数超线性，未验证的小组先撑不住 |

**常见组合**（每条说明职责边界与运维代价）：

- **组合 A：显性化 + 可见产出 + 跨团队评审**（3 份 ADR + 6 篇博客 + 1 次评审）。职责边界：ADR 负责「判断可复用」，博客负责「被组织外看见」，评审负责「让判断接受质询」。运维代价：约 74 小时/年（18 + 48 + 8），属可持续区间；风险是三件都依赖「有真实项目可写」，项目一停三条同时断供。
- **组合 B：持续信号 + Demo + 开源参与**（1 个专栏 + 1 个 Demo + 1 个开源项目）。职责边界：专栏负责信息更新，Demo 负责把输入变成可演示的产出，开源负责可验证的协作记录。运维代价：约 186 小时/年（52 + 30 + 104），其中开源按 7.4 的点估值每周 2 小时计，第一年最容易低估它。
- **组合 C：读物 + 0→1 项目 + 带人**（2–4 本书 + 1 个项目 + 1–2 名下属）。职责边界：项目负责产出与授权，带人负责把「自己产出」换成「他人产出」，读物只做辅助。运维代价：带人按每周 2 小时（同 7.4 的点估值）计，约 104 小时/年，主要落在本职工作时间内；落在个人可支配部分的是读物，约 20–40 小时。
- **组合 D：会议分享 + 社区 + 培训认证**（1 次会议 + 1 个社区 + 1 次信通院 / DAMA / CDA 培训）。职责边界：分享与社区负责外部信号，认证负责治理类岗位的门槛条件。运维代价：约 66–86 小时/年（分享准备 20 + 社区 26 + 培训 20–40），其中社区按每周 0.5 小时计【经验】，即 0.5 × 52 ≈ 26 小时；按 7.4 的点估值计则约 74 小时（20 + 26 + 28）。风险是外部信号丰产而内部授权为零，评审时容易被读成「不聚焦」。

**矩阵的用法**：先用「你的处境」列定位到一行，再重点看「不选它的原因」列——那一列才是路线图里真正要写下来的部分：你放弃了什么、为什么可以放弃。**一份路线图的说服力，来自它写清楚了不做什么。**

组合之间也不互斥：A 与 C 可以叠加（同一年既有产出也有范围扩张），B 与 D 也可以。但**四项全开并不等于 7.4 那笔 606 小时的总账**——按同一点估口径相加，A + B + C + D = 74 + 186 + 134 + 74 = **468 小时/年**（组合 C 的 134 = 读物 30 + 带人 104，其中读物按 2–4 本取 3 本 × 10 小时计），其中 104 小时（带人）计在本职工作时间内，落在个人可支配时间的是 **364 小时/年**，已相当于 7.4 给出的年可支配预算（260–416 小时）的 **88%–140%**。而 7.4 的表里还有三项在 A–D 中没有任何落点——定位与主页更新（6 小时）、1000 字复盘（4 小时）与跨职能小组（104 小时）；组合 C 的读物只按 2–4 本计，总表按 8 本（80 小时）计。**所以 A–D 全开仍不是总账的全部：每一项单看都合理，全开就超预算，这正是清单型建议的典型失效方式。**

### 7.7 选错的代价与迁移成本

- **反模式：收藏式学习** —— 症状：清单收藏、课程买齐、书堆在桌上，每年都有「在学」的状态，但说不出去年做成了什么；后果：输入持续增加而产出为零，组织信息流里没有你，授权范围不变——几年后你会发现判断力确实提升了，但没人知道，也没人把更大的范围交给你；正确的做法：把清单砍到「一样本 + 一产出 + 一组织动作」，先按一年跑完，再决定加什么。
- **反模式：公开产出跑在能力前面** —— 症状：先建个人品牌，发表密度高于真实决策经验；后果：被找来之后答不出细节，一次信任损耗很难修复，而修复成本远高于晚一年再开始写；正确的做法：先有一个真实做成的系统（7.3.2 的失效条件），再写它——写「我做过的」，不是「我读到的」。
- **反模式：用阅读量替代决策密度** —— 症状：把「今年读了 20 本书」当成长证据，把参加过多少场会当影响力证据；后果：读书的反馈周期最长，几年后才发现方向选错，而这段时间本可以做三四个真实决策（[§2 洞察 3](01-future-plans.md)：成长不再靠经验年限，而靠决策密度）；正确的做法：每读一本配一个可验证产出，让长周期投入挂上短周期判据（7.3.3）。
- **反模式：把行动项当成打勾清单** —— 症状：每一条都打了勾，但没有一条在组织里留下痕迹；后果：清单完成度很高、授权范围没变，第二年只能把同一份清单再打一遍勾；正确的做法：给每条行动项写一句「谁会因此改变对你的判断」，写不出人的条目就砍掉。

**换成另一条路线要动什么**（工作量量级为【经验】）：

| 迁移方向 | 可带走的部分 | 不可带走的部分 | 重建期量级 |
| --- | --- | --- | --- |
| 换公司（同行） | 判断框架、工程手艺、公开产出、开源记录 | 内部可见度、内部授权范围 | 3–6 个月重建内部信任 |
| 换行业 | 判断框架、工程手艺、公开产出 | 行业语言与业务直觉、行业内关系 | 6–12 个月 |
| IC → 管理 | 技术判断、公开产出 | 个人产出效率（必然下降）、「自己上手」的习惯 | 1–2 年，期间个人产出下降属正常 |
| 管理 → IC | 组织视角、跨团队协调经验 | 团队规模带来的授权范围 | 6–12 个月重建个人技术可见度 |
| 从零建外部信号 | 已有项目经验 | 无（从零开始的是渠道与读者） | 12 个月以上才可能收到外部引用 |
| 从零建组织授权 | 已有产出记录 | 无（从零开始的是「范围」类机会） | 1–3 年，取决于是否有人愿意先给小范围 |
| 日程从「碎片为主」转为「整块为主」 | 已积累的输入 | 碎片化学习带来的连续感 | 1–2 个月重新分配任务类型 |

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 缺判断框架 | 1–2 本认知书 + 每次读完配一次决策或一篇产出 | 认知类反馈周期数月至数年，必须挂上短周期判据才安全 |
| 缺操作细节 | 工程书 + 一个能演示的 Demo | 只有落在可运行的系统上，工程知识才能被检验 |
| 缺组织授权 | 先做组织动作（带人 / 0→1 项目 / 跨职能小组） | 授权来自「范围」而非技能，读更多书不扩张范围 |
| 缺关系与外部信号 | 会议 / 社区 + 外部 Mentor | 外部信号改变「被发现」的概率，但换不来内部授权 |
| 时间碎片化 | 持续信号 + 写作 + 开源小任务 | 只有可切块任务能在 ≤1 小时的时间里持续推进 |
| 有整块时间 | Demo / 成稿 / 分享准备 | 整块任务是碎片时间做不了的，反过来则不成立 |
| 计划换行业 | 可见产出 + 工具与社区 | 能力可迁走，内部可见度与授权带不走 |
| 手上的决策不足 3 个 | 先争取跨团队任务，后写 ADR | 没有可复用的判断样本时，写作的复用收益为零 |
| 同时并行多项长周期投入 | 砍到 1–2 项 | 读物一项已占可支配预算的两到三成，第三项会挤掉纠错信号 |
| 时间碎片且缺授权 | 先做可切块的可见产出，再谈范围 | 范围类动作需要连续时间与稳定的交付记录 |

> 本节小结：这份清单里**唯一真正起决定作用的差异是「反馈周期」**——每一项的价值由它多久给你一次「你错了」的信号决定。ADR 与可见产出数周就能收到反馈，读物与组织授权要数月至数年。因此可执行的路线图不是「把清单做完」，而是**用短周期项给长周期项装一个判据**：读一本书配一次决策，做一次分享配一条可复用的判断，带一个人配一次范围验证。清单越短、判据越明确，完成率越高。
