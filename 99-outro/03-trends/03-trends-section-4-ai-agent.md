## 4. AI Agent 与人类：取代 / 增强 / 共生

### 4.1 三种关系的本质

#### 关系 1：取代（Replace）

- **定义**：AI 完全替代人类某项任务
- **典型场景**：
  - 重复性 ETL 编写
  - 标准化报表生成
  - 简单数据查询 / 问答
- **时间窗**：2024-2027

#### 关系 2：增强（Augment）

- **定义**：AI 让人做得更快 / 更好 / 更准
- **典型场景**：
  - 数据科学家 + AI：模型选择、特征工程
  - 数据分析师 + AI：洞察发现、决策建议
  - 数据工程师 + AI：架构建议、代码审查
- **时间窗**：2025-2030

#### 关系 3：共生（Symbiosis）

- **定义**：人和 AI 形成"谁也离不开谁"的协同
- **典型场景**：
  - 架构师 + Agent：共同设计数据生态
  - 业务负责人 + AI：共同做业务决策
  - 团队 + Agent：共同完成业务交付
- **时间窗**：2027+

### 4.2 不同岗位的"取代 / 增强 / 共生"分布

| 岗位 | 取代比例（5 年） | 增强比例 | 共生比例 |
| --- | --- | --- | --- |
| 数据分析师（初级） | 60-80% | 20-30% | 5-10% |
| 数据工程师（初级） | 50-70% | 30-40% | 5-10% |
| 数据分析师（资深） | 20-40% | 50-60% | 10-20% |
| 数据工程师（资深） | 20-40% | 50-60% | 10-20% |
| 数据科学家 | 10-30% | 60-70% | 10-20% |
| 数据架构师（资深） | 5-15% | 40-50% | 40-60% |
| 数据架构师（准资深） | 5-10% | 30-40% | 50-70% |

### 4.3 架构师应该主动选择"共生"

#### 为什么？

- **取代**：是被动的，是"被淘汰"
- **增强**：是过渡态，是"被工具化"
- **共生**：是主动的，是"定义未来"

#### 怎么做到"共生"？

1. **让 Agent 做执行**：把"写代码 / 写文档 / 做报表"让给 Agent
2. **让人做决策**：把"选型 / 架构 / 治理 / 风险"留给人
3. **让 Agent 做探索**：把"数据探索 / 假设验证 / AB 测试"让给 Agent
4. **让人做判断**：把"业务价值 / 战略选择 / 长期规划"留给人
5. **让 Agent 做监控**：把"全链路监控 / 异常检测 / 自动化响应"让给 Agent
6. **让人做设计**：把"系统设计 / 生态设计 / 文化设计"留给人

### 4.4 共生关系的具体形态

#### 形态 1：架构师 + Agent = 数据生态"双设计师"

- 架构师定义"业务目标 + 系统边界 + 价值约束"
- Agent 实现"具体方案 + 代码 / 配置 / 文档"
- 共同迭代"目标 → 实现 → 反馈 → 优化"

#### 形态 2：业务团队 + Agent = 业务交付"双引擎"

- 业务团队定义"业务问题 + 业务指标 + 业务优先级"
- Agent 实现"数据查询 + 报告生成 + 决策建议"
- 共同实现"问题 → 数据 → 洞察 → 行动"

#### 形态 3：技术团队 + Agent = 技术交付"双团队"

- 技术团队定义"技术选型 + 架构设计 + 质量标准"
- Agent 实现"代码生成 + 测试执行 + 文档维护"
- 共同实现"设计 → 实现 → 验证 → 沉淀"

> 💡 **思考锚点**：把你自己的职责拆成条目，对照 §4.2 表里你所在岗位那一行——落在「取代」比例里的具体是哪些动作？如果套用「数据分析师（初级）」那一行的 60-80%，你大半时间在写报表 / 查数，那你现在所处的取代 / 增强 / 共生，是主动选定的，还是被推到的？

### 4.5 成本：这套东西的账单

这一节的账单几乎全在**人这一侧**，不在算力侧。§2.4 已把「LLM 推理贵 + 向量存储贵」记在数据栈头上，横切章 `11-cross-cutting/03-data-cost-finops` 讲的是那份账单怎么降；本节只算**把一项工作在人机之间挪动所产生的迁移成本**。

三项里与本主题真正相关的是人力与组织：

- **人力（主项）**：一次「取代」决策的账面成本 = 岗位重置（招 / 转 / 离）+ **该岗位里没被写下来的那部分判断的捕获成本**。捕获成本随「可写比例」下降而上升——初级分析师 / ETL 的产出是规格化的，捕获便宜；资深分析与架构师的产出是判断，只能靠访谈与文档一点点抠【经验】。
- **组织（主项）**：误取代的**回补成本不对称**——裁掉一个岗位很快，回补时市场上未必有同类人，且原岗位的隐性知识已经散掉。所以「取代」的净收益不能只看当季人力节省，要再减掉「回补概率 × 回补成本」。
- **云账单（次项，不重复计）**：本主题不直接产生云账单；它推高的推理与存储账单落在数据栈（§2.4），本节不并入。

【推算】10 人团队按 §4.2 表初级岗 60–80% 可取代估算：账面人力节省 ≈ 10 人 × 60–80% × 单人年成本，量级为「数成人力预算」；扣项是捕获这些人的判断，按每人 3–5 天访谈与文档折算【经验】，量级为「数成人力预算里的个位数百分比」。相减才是真实收益，而扣项最常被漏在预算外。

**为什么贵在这里**：它的成本不按数据量或调用量计费，而按**「要迁移的判断有多难写下来」**计费——这也正是 §4.2 表里同一批岗位取代比例差异那么大的原因：比例越低的行，越贵。

### 4.6 容灾与故障演练

**先说「不适用」**：本主题没有多地域容灾可言——「取代 / 增强 / 共生」是一种工作形态，没有机房、没有主备可切，写成「多云切换」是把别的章的方法论搬错地方。它真实的失效形态有三个，全在人机边界上：

1. **Agent 侧漂移**：模型换代或降级后，原本稳定的产出开始出错、改口。影响面是依赖它的工作流整体不可信；降级策略是人接管。
2. **人侧萎缩（最危险）**：某类判断长期外包给 Agent 后，人不再做它，等 Agent 失效时**降级路径本身已不存在**。这个失效没有告警，是在平静中完成的。
3. **单供应方依赖**：模型 / Agent 平台的停服、改价、合规变更，一次就把共生的一方抽走。

**演练方案（本主题特有的那一个）**：**定期「拔 Agent」**——挑一段工作流，在固定窗口内完全不用 Agent，让流程照跑。看的不是能否跑通，而是**哪一步是人已经不会做的**。注入的对象是「人的能力」，不是故障；通用注入式演练见 `12-architecture/06-chaos-engineering`。

**恢复目标**：两个指标在这里都要换定义——**RTO** = 从 Agent 不可用到人能独立接管一项决策所需的时间【经验，数天到数周，随该判断平时有没有人操练变】；**RPO** = 人上一次独立做过这个决策距今天数，即**能力的保鲜期**【经验，数月量级，随岗位与判断频率变】。跨地域容灾方法见 `12-architecture/07-disaster-recovery`，本主题不适用。

### 4.7 演进路线：0 → 1 → 100

- **0 → 1（最小可用）**：一个岗位把**产出可规格化**的任务（写报表、写 ETL、查数）交给 Agent，人只保留验收。变贵的是**验收时间**——它没消失，只是换了岗位；先坏的是验收本身，很快会被做成走过场。
- **1 → 100（规模化）**：按 §4.2 的分布做编制与角色重定义，团队级出现「人做什么、Agent 做什么」的书面边界与治理规程（§2.2 组件 6）。变贵的是**治理与举证**；先坏的是**责任链**——Agent 的产出谁签字，不写清就会有「没人签字但已经上线」。
- **100 →（下一道坎）**：走向 §2.3 阶段 4 的「自进化系统」时，变贵的是**纠偏与审计**（系统改自己，谁来发现它改错了）；先坏的是**人的判断能力本身**——即 4.6 第 2 条的萎缩，在规模上被放大成组织级风险。

**贯穿三阶段的一条线**：每上一档，被外包出去的东西都更难写下来；所以下一档的门槛不在模型能力，而在**你能不能把那件更难的判断写成规格**。写不出来，规模只会把 4.6 的三个失效形态一起放大。
