## 7. 组织变革

>
> 说明：本节的「候选」不是软件工具，而是**组织形态与治理机制**（分散式 / 集中式中台 / 联邦式数据网格 / 领域型自治团队 / 产品运营型数据组织 / 赋能型平台组织 / AI 平台 + AI 业务双层 / AI 时代数据生态）。因此「机制」指的是**决策权归属、信息流与度量方式、成本由谁承担、激励指向哪一侧**——照同样的「先立判据 → 讲机制 → 给证据 → 给决策」写。

### 7.1 先立判据：为什么「组织先进度」排名会误导

原节的组织方式是：先给一条演进路径（分散式 → 集中式中台 → 联邦式数据网格 → AI 时代数据生态），再列五个变革方向，每个方向配「过去 / 未来 / 代表」，中间夹一节架构师角色的新旧对照，最后给出三个陷阱。作为趋势描述它是准确的；作为选型依据它会误导，因为它隐含两个前提：**路径是单向的，且后一阶段比前一阶段先进**。这两个前提都不成立——组织形态会随业务阶段来回移动，而每一次移动都要重新支付成本。

第一个机制性错误是**把组织当因、把系统当果**。康威定律（Conway，1968）指出系统的结构会复制组织的沟通结构【公开，1968】。这条定律的推论是：**照抄一个组织图，抄到的是别人系统的形状，而不是别人的结果**；而且你抄的时候，你的系统已经长成了你现有组织的形状——改组织之后，效果会先以「系统也要跟着重构」的形式出现，那一段的成本几乎总被漏算。这是本节把「决策权归属」列在第一条判据的原因。

第二个错误是**同一维度在不同约束下权重相反**，而排名把这两件事压成一个序位：

| 维度 | 在「3 个业务域、平台团队 5 人」时 | 在「10 个以上业务域、每域有数据工程」时 |
| --- | --- | --- |
| 域自治 | 是负债：域内没人接口径与质量，自治的结果是几套口径 | 是效率：域最懂自己的数据，决策不必排队 |
| 中央统一 | 是资产：口径天然可比，复用成本最低 | 变成瓶颈：所有需求共用一个队列，中央产能就是公司产能上限 |
| 平台化 | 是提前支付的固定成本，规模摊不薄 | 是必需品：没有平台，协调链路数会把人耗光（7.3.3） |
| 产品化度量 | 纯开销：一次性需求上配 Owner 与 SLA 不划算 | 必需：没有采用率与复用率，团队会优化交付量而不是可用性 |

第三个错误是**暗示这些形态互斥**。真实组织的形态是叠加：中央治理 + 域自治 + 自助平台 + Agent 层是四条不同职责的线，可以同时存在，也可以只上其中两条。一旦接受「可以叠加」，比较的对象就从「哪个更先进」变成「每一条线各自的职责边界在哪、冲突时谁说了算」。

所以本节保留一种排序：**在给定约束下按判据逐条排除**（7.5 决策树），而不是给形态排先后。本主题的判据不能是「先进 / 敏捷 / 高效」这类形容词。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 决策权归属 | 口径、权限、优先级分别由谁定，谁能否决 | 决定冲突在哪一层被解决；不写清归属，冲突会自动上升到最贵的层级（7.3.1） |
| 变更半径 | 改一次口径、换一个上游、加一个域，要协调几方 | 决定交付速度随组织规模衰减的斜率，也是「自治」值不值得付的判据 |
| 协调成本函数 | 参与的域每增加一个，需要多少条沟通链路 | 链路数按 n(n−1)/2 增长，这决定「什么时候必须引入平台与标准」（7.3.3） |
| 度量方式 | 按项目交付验收，还是按产品运营验收 | 度量什么就得到什么：按项目度量会得到「上线了但没人用」（7.3.2） |
| 成本承担 | 口径与质量的人力记在中央账上还是域账上 | 记在中央 ⇒ 中央成为瓶颈；记在域上 ⇒ 前提是域内有能负责的角色 |
| 迁移与再学习成本 | 从现形态换到新形态，要动哪些人、多少时间 | 组织变革的收益滞后于人力的投入，且唯一不可逆的代价是人的信任（7.7） |

判据之间有一条隐含顺序：**第一条决定形态，第二、三条决定要不要加平台，第四、五条决定度量与预算记在谁账上，第六条决定这件事能不能做成。**顺序颠倒，就会在决策权还没定的时候先讨论组织架构图——那正是 7.7 的第一条反模式。

### 7.2 候选方案全景

下表覆盖本章讨论的全部组织形态，**不列打分，只列核心机制**——机制相同则表现必然相同，排名无意义。

| 形态 | 定位（从 X 到 Y） | 核心机制（一句话） | 代表实践 | 成本结构 |
| --- | --- | --- | --- | --- |
| 分散式 | 各域自建数据，无统一标准 | 每个域自付成本与收益：协调成本≈0，复用也≈0 | 多数公司的起点 | 无固定成本；重复建设与口径分叉的代价在各域账上 |
| 集中式中台 | 一个团队建、全公司用 | 把数据能力收成一个共享服务，靠规模摊薄单位成本 | 阿里数据中台一类的集中式建设（2015 年提出「大中台、小前台」）【公开，2015 年前后公开报道】 | 固定成本高、边际成本低；需求排队的时间成本隐性 |
| 联邦式数据网格 | 域自治 + 中央治理 + 跨域联邦查询 | 数据所有权下推给最懂它的域，中央只保留标准与门禁 | Data Mesh（Zhamak Dehghani 于 2019 年提出，2022 年成书）【公开，2019 / 2022】；Netflix 一类平台团队对外分享过的联邦化实践（无单一权威篇目可引，可按其工程博客核验）【经验】 | 中央人数下降、域内人数上升；总量接近（见 7.4 推算） |
| 领域型自治团队 | 从「职能型组织」到「领域型组织」 | 让团队边界与系统边界对齐（康威定律的逆向使用） | Spotify 模型（2012 年公开分享）【公开，2012】；亚马逊的「两个披萨团队」提法【经验】 | 沟通成本下降，重复能力上升；平台团队与使能角色成为必需（Team Topologies，2019）【公开，2019】 |
| 产品运营型数据组织 | 从「项目交付」到「产品运营」 | 把数据资产当产品，用采用率与复用率而非交付量做度量 | 阿里 DataWorks、字节 DataFinder、美团数据平台一类的产品化形态 | 新增产品负责人角色；一次性需求上这笔投入收不回（7.3.2） |
| 赋能型平台组织 | 从「管理型组织」到「赋能型组织」 | 数据团队的产出从「数据集」换成「可自助的工具链与能力」 | Thoughtworks 一类的赋能型实践；Netflix Data Platform 形态【经验】 | 使能角色成效滞后且难度量，预算最先被砍（7.6 组合 3） |
| AI 平台 + AI 业务双层 | 从「每个团队做 AI 项目」到「AI 平台 + AI 业务」 | 把模型能力与业务场景分账，避免每个业务自建模型烟囱 | 阿里通义、百度文心、字节豆包等（2023 年起陆续对外发布，可按厂商名核验各自的公开材料）【经验】 | 平台侧固定投入高、需长期维护接口与评测口径 |
| AI 时代数据生态 | 人 + Agent + 数据 + 模型 + 流程 | 执行下沉给 Agent，决策与边界留给人 | 与主文件 [§2 AI Native 数据架构](03-trends.md)、[§4 AI Agent 与人类](03-trends-section-4-ai-agent.md) 的分工原则一致 | 前置成本是「把口径与权限写成机器可读形式」（7.3.4） |

原节的四阶段演进图（分散式 → 集中式中台 → 联邦式数据网格 → AI 时代数据生态）在表中被展开成八个候选。**它在描述趋势时是好用的，但不要读成能力阶梯**：每一步都要支付新的成本项，而后退也是常见动作——阿里在 2015 年提出「大中台、小前台」之后，组织结构在此后数年多次调整（2023 年公开宣布「1+6+N」组织变革）【公开，2023】，这说明集中与自治之间的平衡点会随业务阶段移动，而不是单向前进。具体时间线可按「阿里巴巴组织架构调整」自行检索核验。

这八个候选分三**族**：**决策结构族**（分散式、集中式中台、联邦式数据网格）——差别只在决策权归属，成本结构都是「协调成本 + 平台成本」；**团队形态族**（领域型自治团队、产品运营型数据组织、赋能型平台组织）——差别在产出定义与度量方式，与决策结构正交；**AI 分工族**（AI 平台 + AI 业务双层、AI 时代数据生态）——差别在「谁执行、谁决策」，与前两族也正交。

分族的操作结论是：**先定决策权（族一），再定度量与产出（族二），最后才谈 AI 分工（族三）**。顺序不能颠倒——度量方式取决于决策权在谁手上（谁定口径，谁就该被度量）；而 AI 分工只有在「谁负责数据质量」明确之后才谈得上，因为 Agent 消费的正是别人定义的口径与权限。

本表保留了原节列出的全部条目：四阶段演进路径（分散式 / 集中式中台 / 联邦式数据网格 / AI 时代数据生态）展开为表中前三个与最后一个候选；五个变革方向分别落在**领域型自治团队**（职能型 → 领域型，Spotify 模型 / 亚马逊两个披萨团队）、**产品运营型数据组织**（项目交付 → 产品运营，阿里 DataWorks / 字节 DataFinder / 美团数据平台）、**联邦式数据网格**（集中式中台 → 联邦，Netflix 数据网格一类实践 / 阿里中台演进）、**AI 平台 + AI 业务双层**（AI 项目 → AI 平台 + AI 业务，阿里通义 / 百度文心 / 字节豆包）与**赋能型平台组织**（管理型 → 赋能型，Thoughtworks / Netflix Data Platform）五行上；原节的「架构师角色」对照落在 7.3.4 表内（系统的设计者 → 生态的设计者）；原节的三个陷阱落在 7.7 的前三条反模式。**没有删减任何一个读者已知的条目，只是把它们放回机制的位置上。**

### 7.3 机制差异：为什么它们表现不同（核心节）

以下四个机制维度覆盖了全部候选，也是「为什么同一套组织做法在两家公司效果相反」的全部原因。每个维度给出机制定义、各形态的实现差异、由机制必然导出的性质（写成「因为 A，所以 B，代价是 C」）以及失效条件。

四个维度的顺序不是任意的：7.3.1 决定谁说了算，7.3.2 决定大家朝什么优化，7.3.3 决定组织规模的上限在哪，7.3.4 决定当 Agent 进场时哪些账要提前结清。前三个维度是经典组织问题，第四个是这一轮变革真正新增的部分。

#### 7.3.1 决策权归属：口径、权限与优先级由谁定

**机制是什么**：把「定义权」（口径怎么算、权限怎么判）与「实现权」（用什么表、怎么加工）分离，看它们分别落在中央还是域。这是本主题的第一机制，也是唯一一条**不能靠工具弥补**的机制。

**各形态的实现差异**：

| 形态 | 口径定义权 | 权限判定权 | 优先级判定权 | 冲突上升到谁 |
| --- | --- | --- | --- | --- |
| 分散式 | 各域自定 | 各域自定 | 各自业务方 | 无法上升（没有可比口径） |
| 集中式中台 | 中央 | 中央 | 中央（按统一队列排期） | 数据负责人 → 业务负责人 |
| 联邦式数据网格 | 域（中央定标准与门禁） | 中央（策略集中、执行在域） | 域（按域内价值排） | 联邦治理委员会 / 标准委员会 |
| 领域型自治团队 | 团队内 | 继承平台策略 | 团队内 | 团队负责人 |
| 产品运营型 | 中央（口径即产品） | 中央 | 按产品路线图排 | 数据产品负责人 |
| 赋能型平台 | 业务方（平台提供工具与默认值） | 平台提供能力、业务方配置 | 业务方 | 业务负责人 |

**由此必然导出的性质**：因为数据网格把「数据的所有权」下推给域，所以域必须**同时接收数据的责任**——口径、质量、SLA 与成本一起下推；代价是中央失去统一口径的强制力，跨域可比性只能靠「标准 + 门禁 + 契约」另行建立，而不是靠行政命令。反过来，因为集中式中台把定义权收在一处，所以口径天生可比、复用成本最低；代价是**所有域的排期共用一个队列，数据团队的产能就是公司数据产能的上限**。这两者的差别不在技术，而在**组织能接受多大程度的不一致**。

**公开证据**：康威定律出自 Melvin Conway 的论文《How Do Committees Invent?》（1968）【公开，1968】；数据网格的四项原则（域所有权、数据即产品、自助平台、联邦计算治理）在公开材料中表述一致（2019 年提出、2022 年成书）【公开，2019 / 2022】；「团队边界与系统边界对齐」以及平台团队 / 使能团队一类角色划分见《Team Topologies》（Skelton & Pais，2019）【公开，2019】。

**失效条件**：当域内没有能承担数据责任的工程角色时（在业务运营型为主的域里很常见），下推会变成「把责任推给接不住的人」：域要么放弃治理、要么把问题退回中央——来回一次，成本高于一直集中。判断方法：问每个核心域「这个域的数据口径由谁负责、他有没有时间做这件事」，答不出人的域，先不要下推。

这条机制在实践里可操作的形式，是把「判定权」与「实现权」分开写下来。**判定权**对应三类问题：这个指标怎么算（口径）、这份数据谁能读（权限）、先做哪一件（优先级）；**实现权**对应：用哪张表、怎么加工、用什么工具。由此可以给出一条很实用的自检：**遇到跨部门争议，先问「这一类问题是按哪条规则判的、规则谁写的」**——答不上规则，说明判定权是悬空的，此时无论把组织画成集中还是联邦，冲突都会继续上升到最贵的那一层（通常是 CEO）。这也是为什么「组织变革从改度量开始」比「从改组织图开始」更容易成功：度量是判定权的公开形式。

#### 7.3.2 度量与激励：按项目交付还是按产品运营

**机制是什么**：验收对象是「交付物完成」还是「被持续使用」。这是中国数据团队过去十年最常被讨论的一次切换，也是**唯一一个可以由组织单方面改变、且立即生效的杠杆**。

**各形态的实现差异**：

| 形态 | 度量对象 | 典型失败信号 | 代表实践 |
| --- | --- | --- | --- |
| 项目交付式 | 上线时间、需求满足率、交付数量 | 上线即终点：使用率低、无人维护、口径无人认领 | 传统数据团队 |
| 产品运营式 | 采用率、复用率、资产可发现性、可核对性 | 指标好看但业务不再提新需求（也可能是真的没需求） | 阿里 DataWorks / 字节 DataFinder / 美团数据平台一类 |
| 赋能型 | 业务方自助完成的比例、使能后域内的独立交付能力 | 平台很强但没人会用（缺使能角色） | Thoughtworks 一类实践、Netflix Data Platform 形态 |
| AI 平台 + AI 业务 | 平台：被复用的模型能力与评测口径；业务：场景效果 | 平台指标好而业务侧无人接入（能力与场景两张皮） | 阿里通义 / 百度文心 / 字节豆包一类双层结构 |

**由此必然导出的性质**：因为度量对象决定团队优化什么，所以按项目验收的组织会得到**更多项目**而不是更好用的数据资产——每上完一个报表，下一个需求在排队，没有人回头修口径。切换到产品验收之后，团队开始关心命名、文档、Owner、SLA 这些东西，而它们恰好是 [§6 LLM + 业务深度融合](03-trends-section-6-llm.md) 里「从功能交付到价值交付」的关键，也是主文件 [§2 AI Native 数据架构](03-trends.md) 把治理重点从「表 / 字段」移到「语义 / 权限 / 审计」的原因：**Agent 消费的正是这些产品化属性，没有它们，Agent 只能靠猜**。代价是产品化度量更容易被美化——采用率可以被「拉人用」推高，复用率可以被重复统计污染，所以度量口径本身必须由中央维护，且要能追溯到原始事件。

**公开证据**：阿里 2015 年提出「大中台、小前台」，其后组织结构多次调整（2023 年公开宣布「1+6+N」组织变革）【公开，2015 / 2023，可按关键词核验】；产品化与平台化的具体形态，可按「DataWorks / DataFinder / 美团数据平台」检索各家的公开技术材料自行核验【经验】。

**失效条件**：当业务处于快速探索期、需求一次性的比例很高时，产品化运营（需要 Owner、SLA、长期维护承诺）会把成本抬到超过收益。判断方法：统计近 20 个需求里，三个月后仍被使用的比例——低于一半时，先按项目交付跑，只对少数确实会长期使用资产配 Owner【经验】。

#### 7.3.3 协调成本：域数增长的代价与平台的引入时点

**机制是什么**：任何「多方要达成一致」的组织形态，其沟通链路数按 **n(n−1)/2** 增长；平台与标准的作用不是「更规范」，而是把这个平方项换成线性项（每个域只与平台约定接口）。

**各规模下的实现差异**（表中数字是域数与链路数，不是评分）：

| 域数 | 两两链路数 n(n−1)/2 | 可行的协调方式 | 形态建议 |
| --- | --- | --- | --- |
| 3 个域 | 3 条 | 口头对齐 + 少量约定 | 集中式，不必建平台 |
| 5 个域 | 10 条 | 定期会 + 一份标准文档 | 集中式 + 一两个域试点 |
| 10 个域 | 45 条 | 必须有人专职维护标准、目录与门禁 | 联邦式（域自治 + 中央治理） |
| 20 个域 | 190 条 | 靠人协调已不可能，必须平台化 + 门禁自动化 | 联邦式 + 自助平台 + 领域型团队 |

**由此必然导出的性质**：因为链路数按平方增长，所以「靠开会协调」的组织会在域数跨过某个量级后突然失控——不是逐渐变慢，而是某一年开始每个决策都要等半个月。**标准的价值由此可以被精确表述**：它把 N 个域之间的 N² 条链路换成 N 条「域 ↔ 标准」的链路（数字见 7.4）。代价是标准本身成为一个需要长期维护的产品——谁定、谁改、如何例外，一旦它僵化，整个组织就被锁在上一代做法里；这正是「集中式中台」被批评的机制根源，也是它的替代方案（领域型自治团队）走另一条路的理由：**与其优化沟通，不如让团队边界与系统边界对齐，使沟通变得不必要**（康威定律的逆向使用）。

**公开证据**：团队与系统边界的匹配、以及平台团队 / 使能团队一类角色划分见《Team Topologies》（2019）【公开，2019】；Spotify 的团队结构见其 2012 年公开分享《Scaling Agile @ Spotify》【公开，2012】。「逆向康威定律（Inverse Conway Maneuver）」这一提法在 2010 年代由 ThoughtWorks 等组织的公开材料中流传，原始出处可按该关键词自行检索核验【经验】。

**失效条件**：当域的划分与业务能力不重合时（例如按技术层次切域，而不是按业务领域切域），让团队边界对齐系统边界只会把错误切分固化，平台与标准的负担反而更重。判断方法：看一个域能否独立交付一个对业务方有意义的数据产品——不能，说明这个域切错了。

#### 7.3.4 AI 引入后新增的一层：执行下沉，决策与边界留给人

**机制是什么**：组织里第一次出现「可以承担执行、但不承担责任」的参与者（Agent）。它以**机器可读**的方式消费语义、权限与流程，因此对组织的第一个要求不是「上模型」，而是把那些原本只存在于人脑与口头共识里的规则写下来。

**人做 vs Agent 参与，组织要求的差异**：

| 事项 | 只有人时 | Agent 加入后 | 不写清楚的后果 |
| --- | --- | --- | --- |
| 口径 | 文档里一致、靠人理解即可 | 必须结构化、有 Owner、进版本控制 | Agent 会给出「看起来合理」的错答案 |
| 权限 | 靠流程与自觉 | 必须是可在执行前判定的策略，且 Agent 身份单列 | 越权不可归因（与 [§5 AI 治理与监管](03-trends-section-5-ai.md) 的结论一致） |
| 流程例外 | 人可以临机处理 | 例外必须显式登记 | Agent 在例外处必然出错，且没人知道它错了 |
| 决策 | 人负责 | 仍由人负责 | 把决策让出去，等于把不可解释的后果让出去 |
| 架构师角色 | 「系统的设计者」：选技术 / 框架 / 工具 | 「生态的设计者」：设计人 + Agent + 数据 + 模型 + 流程的协同边界 | 角色错位，导致 Agent 能力被当成组织问题解决 |

**由此必然导出的性质**：因为 Agent 的输入是机器可读的语义与策略，所以「组织里那些没写下来的规则」第一次变成了**会直接产生错误答案的缺口**——这不是技术问题，而是组织信息的显性化问题；代价是显性化本身很贵（把口径、例外与审批规则写成可判定形式，并长期维护），且它不像上线一个功能那样有可见产出。分工原则与 [§4 AI Agent 与人类](03-trends-section-4-ai-agent.md) 一致：**让 Agent 做执行、探索与监控，让人做决策、判断与设计**。这也解释了「AI 平台 + AI 业务双层」解决的是什么、不解决什么：它解决模型能力重复建设，**不解决口径散落在业务侧**——后者只能靠域侧的语义 Owner。

**公开证据**：「AI 中台 + 业务部门不愿用」是 [§6 LLM + 业务深度融合](03-trends-section-6-llm.md) 已列出的失败形态（挑战 3「从中心化 AI 到业务嵌入 AI」），同章挑战 5「从 AI 项目到 AI 平台」给出了双层结构要解决的问题；这类形态在公开讨论中反复出现，故按经验档处理【经验】。模型侧的工具调用需要权限层兜底这一结论，见 [§5](03-trends-section-5-ai.md) 的提示注入小节。

**失效条件**：当组织尚未解决基本的口径与权限归属时，引入 Agent 只会把已有问题加速暴露——**Agent 不制造错误，它会把组织没写下来的规则抄错**。反过来，若一个组织已经做到了口径有 Owner、权限可在执行前判定，那么 Agent 的引入成本会显著低于预期，因为最难的两件事在前一阶段已经付过了。

### 7.4 成本结构对比（不是价格表，是成本函数）

组织形态的成本不是软件报价，而是四项随规模变化的量之和：

```
组织成本 ≈ 协调成本 + 平台与标准的固定成本 + 语义与权限的维护成本 + 变革的信任与再学习成本
        ≈ a·(域数² ÷ 平台化程度) + b·平台与标准人力 + c·(域数 × 每域角色配置) + d·(切换人数 × 切换时长)
```

各形态的差别不在总量，而在**哪一项是主导项**、哪一项是账面上看不见的：

| 形态 | 主导项 | 隐性成本（当年不计入、两年后计入） | 什么条件下反转 |
| --- | --- | --- | --- |
| 分散式 | 无固定成本 | 重复建设 + 口径分叉的复利（合并时要付一次总账） | 域数少、业务互不相关时，反而比统一更省 |
| 集中式中台 | a 项被压到最低，b 项高 | 需求排队的时间成本；中央产能即公司产能上限 | 域数少、需求同质时最优 |
| 联邦式数据网格 | c 项（域内角色配置） | 标准与门禁的长期维护；下推后域内能力不够时的返工 | 域数 ≥ 5 且每域有责任角色时 |
| 领域型自治团队 | c 项 + 平台团队配置 | 能力重复建设；使能角色难量化，预算最先被砍 | 团队边界与系统边界能对齐时 |
| 产品运营型 | c 项（产品负责人） | 一次性需求上的产品化开销 | 资产会被长期使用时 |
| 赋能型平台 | b 项 | 使能成效滞后，短期看不到产出 | 业务方有自助意愿时 |
| AI 平台 + AI 业务双层 | b 项 + 评测口径维护 | 平台换模型版本时所有业务线要重跑评测 | 模型能力被多条业务线复用时 |
| AI 时代数据生态 | 语义与权限的维护成本（c 项：把口径、权限与例外写成机器可读形式并长期维护） | 显性化没有可见产出——写下来的规则不增加功能，预算最先被质疑；只写一半的规则会让 Agent 给出「看起来合理」的错答（7.3.4） | 已有 Agent 在消费数据、口径与权限必须在执行前判定时 |

三项【推算】示例，推导链全部写出，读者可按自己的域数与成本参数替换重算：

**算例 1 · 协调成本的平方项**：沟通链路数 = n(n−1)/2 ⇒ 5 个域 10 条、10 个域 45 条、20 个域 190 条【推算：n(n−1)/2】。若每条链路每月需要一次对齐、每次平均 2 人时，则 10 个域时月耗 90 人时 ⇒ **年 1,080 人时 ≈ 0.5 人全职当量**（按每人 2,000 人时 / 年折算）【推算：45 × 2 = 90 人时/月，× 12 = 1,080 人时/年，÷ 2,000 ≈ 0.54 人】；20 个域时月耗 380 人时 ⇒ **年 4,560 人时 ≈ 2.3 人全职当量**【推算：190 × 2 = 380 人时/月，× 12 = 4,560 人时/年，÷ 2,000 ≈ 2.28 人】。这就是平台与标准的收益形式：**它不降低单次沟通的成本，它把链路的条数从平方项换成线性项**——平台化把「域与域两两对齐」换成「每个域只与平台对齐」，链路数从 n(n−1)/2 降到 n，省下的就是这中间的差额。同口径代入：10 个域时 45 条降到 10 条，省 35 条 ≈ **840 人时/年 ≈ 0.4 人全职当量，不足 1 个人**【推算：35 × 2 人时 × 12 = 840 人时/年，÷ 2,000 ≈ 0.42 人】；20 个域时 190 条降到 20 条，省 170 条 ≈ **4,080 人时/年 ≈ 2 人**【推算：170 × 2 × 12 = 4,080，÷ 2,000 ≈ 2.04 人】；要到 70 个域以上（省下约 2,300 条链路）才够得上「几十个人」【推算：70 × 69 ÷ 2 − 70 = 2,345 条，× 2 人时 × 12 ≈ 5.6 万人时/年，÷ 2,000 ≈ 28 人】。所以域数不够时建平台是纯投入——**它的收益上限就是那个规模下的全部协调成本**（10 个域时整份协调成本也只有 0.5 人全职当量），省下的不可能超过它。

**算例 2 · 两条路线的人力总量其实接近**：域自治的前提是每个域配「1 名数据产品负责人 + 0.5–1 名数据工程」以承担口径、质量与 SLA，10 个域即 **15–20 人分散在业务侧**，中央留 3–5 人做标准、目录与门禁【推算：10 × (1 + 0.5~1) = 15–20 人】。作为对照，同样规模下集中式中台的典型形态是一支 20–30 人的中央团队【经验】。**两条路线的人力总量接近，差别在人的归属与决策权**——这是本节最重要的一条成本结论：换组织形态并不会自动省钱，它换的是「谁在什么信息条件下做决定」。

**算例 3 · 切换成本的一次性投入**：若一个 20 人的数据团队切换形态，按每人每月被切换工作占用 20%–50% 的时间、持续 3 个月计，约 **12–30 人月**【推算：20 人 × 20%–50% × 3 个月 = 12–30 人月】。它对应的是标准对齐、试点、返工与培训，不包含新角色的招聘周期。经验上，平台与标准的采用要经过 2–3 个发布周期才会成为默认行为【经验】——**所以「组织变革什么时候见效」应以季度为单位估计，而不是以月**。

**成本对比里不该出现的数字**：任何形如「效率提升 30%」「交付周期缩短一半」的结论，若没说清度量口径、基线与观察窗口，就没有可迁移性。组织变革的度量和它的成本一样容易自证——本节三个算例都把参数写了出来，就是为了让读者能用自己的域数、人数与工时替换后重算一遍。

三个算例合起来还说明一件事：**这笔账的收益结构与投入结构是错位的**。投入（算例 3 的切换成本）集中在变革当年的少数人身上，收益（算例 1 省下的协调成本、算例 2 换来的决策质量）分散在未来若干年、由多数人分享，且**最直接的受益者往往是下一个接手的人**。这是组织变革反复失败的第一原因——不是方法论不对，而是它在每一年的预算与考核周期里都排不赢「本季度的交付需求」。可行的对策只有一个：把内层工作的进度做成对外可见的指标（口径覆盖率、域内自助完成比例、跨域争议的平均解决时长），让这笔投入有可验收的中间产物。

### 7.5 决策树（我该走哪条路）

```
开始：为一个数据组织选形态
├─ Q1 域数有多少，每个域内是否有人能承担「数据责任」（口径 / 质量 / SLA）？
│    ├─ 任一核心域内无人能承担 → 集中式中台（先把口径与目录立住，不要下推）
│    ├─ 域数 ≤ 4 → 集中式中台（4 个域也只有 6 条链路，靠人协调仍然可行，不必建平台）
│    └─ 域数 ≥ 5，且每个核心域都有责任角色 → 进入 Q2
├─ Q2 业务是否处于快速探索期（需求一次性的比例高）？
│    ├─ 是 → 集中式 + 少数域试点（暂不支付产品化运营的长期成本）
│    └─ 否 → 走联邦：域所有权 + 数据即产品 + 自助平台 + 联邦计算治理
├─ Q3 对外披露或监管是否要求口径统一且可举证？
│    ├─ 要求 → 口径定义权与权限判定权保留在中央（联邦 ≠ 分散合规）
│    └─ 不要求 → 口径可下推到域，中央只维护标准、目录与门禁
├─ Q4 团队边界与系统边界是否对得上（一个域能否独立交付数据产品）？
│    ├─ 对得上 → 领域型自治团队（团队内自带数据 / 工程 / 产品）
│    └─ 对不上 → 先按团队拓扑补齐平台团队与使能角色，再谈自治
├─ Q5 数据团队的产出目前按什么验收？
│    ├─ 按项目交付 → 并行加一条产品化度量（采用率 / 复用率）跑一段
│    └─ 已按产品运营 → 进入 Q6
├─ Q6 组织里是否已经有 Agent 在消费数据？
│    ├─ 是 → 先把语义与权限做成机器可读（口径 / 例外 / 审批规则），再扩 Agent 范围
│    └─ 否 → 不为此提前建设，但把「口径有 Owner、例外可登记」作为现在的交付标准
└─ Q7 模型能力由业务线各自建设，还是由平台统一提供？
     ├─ 各自建设 → 接受重复投入，但要求接口与评测口径统一
     └─ 平台统一 → AI 平台 + AI 业务双层
```

**阈值依据**（与树上节点一一对应）：

读这棵树的方式是**自上而下**：Q1 决定要不要有自治，Q2 与 Q3 决定自治的边界在哪，Q4 决定团队怎么切，Q5 到 Q7 决定度量、机器可读化与模型能力的归属。前面的答案不会被后面的答案推翻。

- **Q1 的「≤ 4 / ≥ 5」**：依据是算例 1 的链路数与算例 2 的人力配置——4 个域时两两链路只有 6 条，靠人协调仍然可行（3 个域更少，只有 3 条）；5 个域时 10 条、10 个域时 45 条，专职维护标准与门禁开始变成必需。另一半依据是**下推的前提**：每域要有人接住责任（1 名数据产品负责人 + 0.5–1 名数据工程）——这一半是硬条件，**任一核心域内没有人接责任时，无论域数多少都不能下推**。两句合起来才是阈值（两条依据的推导见 7.4）【推算】。
- **Q2**：依据是 7.3.2 的失效条件——需求一次性的比例决定产品化运营的投入能不能收回。判定方法是统计近 20 个需求里三个月后仍被使用的比例，低于一半按探索期处理【经验】。
- **Q3**：结构性判据（是否存在对外举证义务），不是估值。它的机制依据是合规判定权不可分权：一旦口径与权限的判定权下推到域，跨域的可举证性就依赖每个域各自正确——而这正是监管不接受的形式。
- **Q4**：结构性判据（康威定律：团队边界决定系统边界）。判定方法是一个具体问题——「这个域能否独立交付一个对业务方有意义的数据产品」；不能，说明域的划分需要先改，而不是先自治。
- **Q5**：结构性判据（度量对象）。它的依据是 7.3.2 的因果链：度量什么就得到什么，所以切换度量方式本身就是一项可以独立执行、且立即生效的变革动作。
- **Q6**：结构性判据（Agent 是否已在消费数据）。它不是「要不要上 AI」的判断，而是「机器可读化是否已经成为阻塞项」——已经有 Agent 在取数时，口径与权限的显性化就不再是长期建设，而是当期阻塞（7.3.4）。
- **Q7**：结构性判据（能力由谁建设、谁付钱），依据是 [§6](03-trends-section-6-llm.md) 已列出的失败形态「每个团队各自做 AI 烟囱」。

这七个节点里只有 Q1 与 Q2 用了近似阈值，其余五个都是结构性问题（有无举证义务、团队边界能否对齐、按什么度量、Agent 是否已进场、能力由谁建），答案由约束决定，不需要估数。

树上每个节点的判据都能追到 7.3 的一条机制：Q1 与 Q2 追到 7.3.1 与 7.3.2（先有责任角色，再谈自治；需求是否长期使用决定要不要产品化），Q3 追到 7.3.1 的失效面（判定权不可分权），Q4 与 Q7 追到 7.3.3（团队边界、协调链路与重复建设），Q5 与 Q6 追到 7.3.2 与 7.3.4（度量决定优化方向；Agent 进场要求机器可读化）。**如果某条分支的理由追不到 7.3 的任何一条机制，那它就不是选型判断，而是偏好。**

### 7.6 选型矩阵与组合

矩阵按「你的处境」而不是「形态的优劣」组织。每行的「最该避免照搬」都写成机制层面的理由。

| 你的处境 | 最该参考 | 最该避免照搬 | 理由 |
| --- | --- | --- | --- |
| 3 个业务域以内、数据团队 < 5 人 | 集中式中台 | 联邦式数据网格 | 域内无人接责任时，下推等于把问题推给接不住的人（7.3.1） |
| 5 个以上业务域、每域有数据工程能力 | 联邦式数据网格 | 中央大一统中台 | N² 条协调链路会把人耗光，而平台的收益正是把平方项换成线性项（7.3.3） |
| 强监管、口径需可举证 | 中央保留口径定义权与权限判定权，域只做实现 | 把合规判定权下推 | 合规判定不可分权，举证责任不会因为组织变平面而消失 |
| 交付物是报表与看板、需求稳定 | 项目交付制 + 少量产品化度量 | 全面产品化（人人配 Owner 与 SLA） | 一次性需求上产品化投入收不回（7.3.2 失效条件） |
| 数据团队被重复取数淹没 | 产品运营型组织（先给资产配 Owner 与采用率） | 只买工具不改度量 | 不改度量，团队优化的仍是交付量，业务照样排队 |
| 业务方普遍不会用数据 | 赋能型平台 + 使能角色 | 只建平台不配使能 | 平台很强但没人会用，是赋能型最典型的失败形态 |
| 组织里已有 Agent 在取数 | 先把口径与权限做成机器可读 | 先扩 Agent 的权限与范围 | Agent 会把没写下来的规则抄错，扩得越快暴露得越快（7.3.4） |
| 探索期、方向未定 | 集中式 + 域试点 | 一次性重构组织架构 | 组织变革的不可逆成本是人的信任，试错要从小处做 |

四条**常见组合**（把原节的五个方向组合成可以共存的结构），每条说明职责边界与运维代价：

1. **中央治理 + 域自治（联邦）**：中央承担标准、目录、门禁与权限判定；域承担口径实现、质量与 SLA。边界是——**中央不拥有数据，只拥有判定权**（什么算合格、什么能发布、什么能被谁读）。运维代价：两套节奏要同步——标准变更要通知到全部域，域的实现偏差要能被门禁发现；中间必须有人长期维护标准本身，而这份工作在组织图上看不出产出（7.4 算例 1 的收益形式正是这项工作的价值）。
2. **数据中台 + 数据产品负责人（产品运营）**：中台承担共享加工与供给，产品负责人承担「这个数据集被谁用、好不好用、口径谁认领」。边界是——**中台的产能不能被当成唯一入口**，否则它退化为排队窗口。运维代价：中台产能就是公司数据产能上限，必须主动分级限流，把长尾需求交回域。
3. **平台团队 + 使能团队（团队拓扑）**：平台团队做自助能力，使能团队短期嵌入域、教会方法后退出。边界是——**使能团队的产出是域的能力，不是域的交付物**；一旦使能团队长期驻场，它就变成了域的外包团队。运维代价：使能成效滞后且难度量（能力提升不像交付那样有产出物），预算最先被砍——这是赋能型路线最常见的死法。
4. **AI 平台 + AI 业务双层**：平台提供模型、工具协议与评测口径；业务线做场景与语义 Owner。边界是——**平台不定义业务口径，业务线不自建模型底座**。运维代价：接口与评测口径要长期维护；平台侧一次模型版本变更，所有业务线都要重跑评测——这正是「评测集必须留在业务侧」的理由（[§6 挑战 5](03-trends-section-6-llm.md)）。

四条组合的共同代价结构：**每加一层，就多一份需要长期同步的约定**（标准、产品定义、能力边界、评测口径），而每份约定都需要 Owner、版本控制与变更通知。这解释了一条最常见的失败路径——一次把四层全建起来，结果四份约定各自漂移，比只有一层时更难判断谁说了算。**组合的原则是：先定权威层（谁负责口径与权限），再按真实出现的需求逐层追加。**

矩阵里有一行与其他行性质不同：「强监管、口径需可举证」的对策不是换一种形态，而是**把判定权从实现里单独摘出来**——域可以用任何方式实现，但口径与权限的判定规则必须由中央一处维护。这条对策在全部形态下都成立，所以它不该被当成一种形态去选择，而应被当成一个必须满足的约束条件；把它写进 Q3、而不是当成「第 9 种形态」列进候选表，正是为了不让人用「换形态」来回应监管要求。

### 7.7 选错的代价与迁移成本

下面五条反模式中的前三条，就是原节列出的三个陷阱在这里的机制表述——同一件事在变革阶段叫陷阱，在选型阶段就是「选了不该选的形态」。

**反模式：把组织变革当重画组织架构图** —— 症状：一次调整把同级团队拆成三个域，但没有同步改度量方式、没有给域配数据角色、没有改审批流。后果：三个月后新结构退化成旧行为——跨域还是走原来的审批，工单还是在原来的群里排，只有组织图变了。正确的做法：把变革拆成四件可分别验收的事——**决策权归属（谁定）、度量方式（按什么验收）、成本承担（人力记在谁账上）、工具与门禁（什么可以被自动判定）**；画图只是这四件事的载体。

**反模式：用上一个新平台替代组织变革** —— 症状：先采购或自建平台，再指望组织跟着变。后果：平台成为「又一个系统」，业务方仍按旧流程把需求提给中央，自助与人工流程并存，两边成本叠加；[§6](03-trends-section-6-llm.md) 的挑战 3「AI 中台 + 业务部门不愿用」就是这一条在 AI 上的版本。正确的做法：先改度量与决策权，让「用平台自助完成」在验收上被承认，再建设平台能力——**平台是组织形式的下游，不是上游**。

**反模式：把变革做成自上而下的发布会** —— 症状：管理层宣布新组织形态，配套 OKR 与培训，但没有自下而上的反馈通道，也没有例外处理机制。后果：域为了合规而在形式上完成动作（挂牌、写文档、填指标），实质行为不变；真正的问题（口径没有 Owner、版本无人维护）原样留着。正确的做法：**自上而下只定「决策权与度量」，自下而上定「实现与例外」**，并把例外登记做成一等公民——例外不被登记，Agent 进场时就会在例外处出错（7.3.4）。

**反模式：照抄一个有名模型** —— 症状：把 Spotify 模型、数据网格、两个披萨团队当成模板直接落地。后果：抄到的是别人组织的形状，而你的系统已经长成了你现有组织的形状（康威定律），于是要么组织变形后系统跟不上，要么系统重构的量被严重低估。正确的做法：抄它的**约束—机制对**（它面对什么约束、因此把决策权放在哪、为此放弃了什么），并在**你自己的约束**上按 7.5 的 Q1–Q7 重新推一遍。Spotify 相关人员在其后的公开分享中表示该模型并非可直接照搬的模板，这一点可按「Spotify model」相关公开分享自行检索核验【经验】。

**反模式：在域内没有数据角色时就宣布自治** —— 症状：发文宣布域自治，但域里只有业务运营，没有人接口径与质量。后果：数据质量与口径一路下滑，中央被迫重新接手，同时丧失域的信任（「折腾一圈又收回去」），下一次变革的阻力更大。正确的做法：下推与配人同步进行（每域 1 名数据产品负责人 + 0.5–1 名数据工程，见 7.4 算例 2）；没有条件配人的域，先留在中央的供数范围内。

**换成另一个要动什么**：

| 迁移 | 数据与资产 | 标准与度量 | 平台与流程重建 | 人的再学习 |
| --- | --- | --- | --- | --- |
| 集中式中台 → 联邦式数据网格 | 小（数据留在原处，改的是所有权登记与供数接口） | 大（每个域要有契约、SLA 与质量门禁） | 大（自助平台 + 联邦查询 + 门禁自动化） | 大（域内要长出数据角色） |
| 项目交付制 → 产品运营制 | 无 | 大（考核从交付量换成采用率与复用率） | 中（每个数据产品要有 Owner 与 SLA） | 中（数据团队要学会做产品） |
| 集中式 → 赋能型平台 | 小 | 中（度量从「我们交付了什么」换成「业务自助完成多少」） | 中（工具链与文档成为主产品） | 大（要会做使能，而不只是会做数据） |
| 无 Agent → Agent 参与取数 | 小 | 大（口径、例外、审批规则要写成可判定形式） | 中（身份、限额、审计与可观测） | 中（人要学核验而不是学写 SQL） |
| 各业务线自建模型 → AI 平台 + AI 业务 | 中（模型与评测集要能迁出，否则等于重做） | 大（评测口径要在平台与业务线之间对齐） | 大（平台侧接口与版本管理） | 中 |

这张表里最容易被低估的一格是「集中式中台 → 联邦式数据网格」的**标准与度量**列：迁移的难点不是把数据搬到别处（数据留在原处），而是要**为每个域写出契约、SLA 与质量门禁**——这份工作量随域数线性增长，且必须由既懂业务又懂数据的人来做。所以生产中的常见形态是「联邦 + 少数集中共享层」共存：跨域共用的核心指标仍由中央定义，域只负责自己业务的指标。

迁移的通用原则只有一条：**先建新的一层，让新旧两种机制并行跑一段，用同一批指标对账，确认口径一致再切换**（例如新老口径同时产出一段时间，逐日比对差异）。组织形态的迁移不存在「一次性大爆炸」的成功案例——因为它的产物是「谁在什么条件下做决定」，而这件事只能靠并行运行时的行为差异来观察，不能靠发文宣布。

还有一条与预算有关：这笔成本里**唯一可以削减的是「并行期」的长度，但并行期不能被压到零**。在口径尚未对齐时就切换消费端，问题会以「数字不对」的形式暴露，而排查一个数字对不上的代价通常高于多跑一个月并行。要压缩并行期，正确做法是把对账自动化（同一批指标逐日比对、差异超阈值即告警），而不是靠少跑几天。

### 7.8 小结

下表把 7.5 的决策树压成七行（与 Q1–Q7 七个节点一一对应），只保留「处境 → 建议 → 机制理由」。读法是先找到与你最接近的一行，再回看它对应的 7.3 小节确认理由是否成立——若理由不成立，就换行。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 域少、团队小、需求同质 | 集中式中台 | 协调链路少，统一的收益最大而摊薄成本的压力最小 |
| 域多、每域有数据工程能力 | 联邦式数据网格 | N² 条链路必须换成 N 条接口约定，否则协调成本失控 |
| 强监管、口径要可举证 | 中央保留口径与权限的判定权 | 判定权一旦下推，可举证性就依赖每个域各自正确 |
| 资产会被长期使用 | 产品化度量 + 数据产品负责人 | 度量对象决定团队优化什么，改度量立即生效 |
| 业务方不会自助 | 赋能型平台 + 使能角色 | 平台的产出是能力，不是数据集；缺使能就没人会用 |
| 已有 Agent 在取数 | 先把口径、权限、例外写成机器可读 | Agent 会把没写下来的规则抄错，且错误表现为「看起来合理」 |
| 模型能力被多条业务线复用 | AI 平台 + AI 业务双层 | 平台解决重复建设，不解决口径散落——后者靠域侧语义 Owner |

还有一种处境值得单列：**已经在集中式与联邦之间来回动过**。此时第一步不是再选一次形态，而是把上一轮的痛点归到 7.3 的哪一条机制上——若是「什么都排队」，问题在 7.3.1 的优先级判定权；若是「做了很多没人用」，问题在 7.3.2 的度量方式；若是「每次跨域都要开一堆会」，问题在 7.3.3 的协调链路数。**痛点归错了类，换形态只会把成本从一个账户挪到另一个账户。**

> 本节小结：这一组形态里**唯一真正起决定作用的差异**是「口径与权限的判定权放在哪一层」——它同时决定度量方式（谁定口径谁被度量）、成本记在谁账上（中央账还是域账）、以及 Agent 能不能用（Agent 消费的正是机器可读的口径与权限）。演进路径不是单向的：集中与联邦只是「组织能接受多大程度的不一致」这一个变量上的两个取值，会随业务阶段来回移动——所以正确的问题不是「我该进化到哪一阶段」，而是「**在当前阶段，我把判定权放在这一层，会不会产生我付不起的协调成本**」。
>
> 💡 **思考锚点**：按 7.4 的算例算一次：你打算把判定权下推给几个域？每域配「1 名数据产品负责人 + 0.5–1 名数据工程」，乘出来是多少 FTE——配不出人的域按 7.8 先留在中央供数范围内；再定一件事：新旧机制并行跑多久（表里说唯一能削减却不能压到零的是并行期），拿哪几个指标逐日对账、差异超多少就告警？
