## 3. 设计模式与范式

> 原 § 3 共 133 行：8 个模式（每个 4 条要点——模式 1–2 是「核心思想 / 适用 / 优点 / 缺点」，模式 3–8 是「核心思想 / 代表 / 优点 / 缺点」）、1 张「场景 → 推荐模式」表（6 行）、7 条反模式（表现 / 危害 / 对策）。8 个模式都没有结构示意，优缺点停留在形容词，且没有一条写明失效条件。本节重写为约 340 行的模式手册，原 8 个模式名与 7 条反模式名全部保留。

### 3.1 先看约束：模式不是选择题，是约束的产物

原表把八个模式按场景排成一张对照（数据治理用 RACI + Stakeholder + Sponsor、数据中台用 Shared Service + Platform、临时赋能用 Enabling Team……）。这张表读起来像菜单，问题在于它把两件不同层的东西放在了一起：**RACI 与 Stakeholder 是分析工具与沟通协议**——不改变组织结构、不占编制、可以随时采纳或放弃；**Shared Service / Platform / CoE / Enabling 是团队形态**——一动就涉及编制、预算、汇报线与考核口径。把工具与组织实体并排列在一张表里，读者自然会得出「按场景挑一个」的结论，而真实的选择顺序是：**先问这件事的决定权在谁手上，再问能力从哪来**。

决定权这条约束之所以是根约束，是因为它同时筛掉了大半候选。没有有权的共同上级时，RACI 与 Stakeholder 只能改变信息分布，不能产生决定——因为 RACI 的 A 是「对结果负责」，不是「有权决定」（本章 [§7.3.1](04-cross-team-collaboration-section-7-sec7.md)）。同一份约束还会决定能力从哪来：有权力源时可以把能力收进一个共享团队（组织说了算）；没有权力源时只能靠成本与收益的归属去引导（让共享成为理性选择，见 [§7.3.2](04-cross-team-collaboration-section-7-sec7.md)），或者把能力做成不需要协商的默认值。

第二层约束是**成本与收益的归属**。跨团队共享的收益是公共品（多个团队都能用），投入却是本团队独占的工时；收益共享、成本独享时，「理性选择」就是不派人或派最闲的人。这也是为什么号召「要有大局观」在机制上无效——它试图改变动机，而没有改变博弈的支付矩阵（本章 [§6 案例 4.4](04-cross-team-collaboration-section-6-sec6.md) 做的正是改支付矩阵）。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 决策权来源（有没有有权的共同上级或 Sponsor） | 决定候选集合：没有权力源时只能选「定责 / 说服」类，选不了「团队形态」类 | 「RACI 填清楚就能推动」——它能回答谁背锅，不能回答谁拍板 |
| 成本与收益的归属 | 决定共享能不能持续；在「能力从哪来」这一类内部是唯一变量 | 「号召大局观」——收益共享、成本独享时，派来的是最闲的人 |
| 需求能否批量化 | 决定做共享服务（替他们建）还是做平台（让他们自取） | 「有了共享团队就不用重复建设」——每个都定制的共享，只是把重复建设搬进了队列 |
| 信息的流向（多对多 / 一对多 / 多对一） | 决定协调成本随规模的增长方式：多对多按 n(n−1)/2 增长，一对多近似零边际 | 「多开同步会就能对齐」——会议数量会随团队数平方增长 |
| 团队边界与系统边界是否一致（Conway） | 决定协作模式是不是会被架构反向固化 | 「先重组团队，架构会自己变好」——旧边界会在系统里长回来（本章 [§7.3.4](04-cross-team-collaboration-section-7-sec7.md)） |
| 使用方的自服务能力与平台团队的迁移支持 | 决定 Platform 模式能不能成立 | 「平台做完就有人用」——没有迁移工具与默认值，业务方会一边用一边暗中自建 |

这六条共同说明一件事：**模式不是被场景挑出来的，是被约束推出来的**。同一句「我们想推数据治理」，在有共同上级与没有共同上级的两个组织里，正确模式完全不同。

### 3.2 模式逐个拆解（核心节）

八节用同一套模板拆：**被什么约束逼出来 → 结构 → 为什么这样设计有效 → 代价 → 失效点 → 真实使用**。每节的失效点只反转**它自己**的优点，不借用邻座的。

#### 3.2.1 RACI 矩阵模式

- **被什么约束逼出来**：一项工作跨若干团队与角色、活动可以枚举，而「谁对结果负责」在组织里说不清，出现责任真空。
- **结构**：

```text
RACI 矩阵：活动 × 参与方，格子里只放字母（R / A / C / I）
                业务方  数据架构师  数据工程  合规  高管
  数据接入规范    C        A          R       C     I
  血缘系统搭建    C        A          R       C     I
  数据质量监控    I        A          R       I     I
  数据 SLA 报告   I        A          R       I     C
  健康度规则（写进模板、交给自动检查）：每项有且仅有 1 个 A；
    每项 R 控制在约 3–5 人（再多则"共同负责"退化为没人负责）；
    每项 C 控制在约 8–10 人（再多则每次变更的逐个征询往返数随 |C| 上升，
    矩阵的维护成本超过它防住的风险）
    【经验：两条阈值的量级是经验判断、不是统计值，按团队规模与变更频率校准；
    校准方法：数最近三次变更实际征询过的人数与往返轮次，超了先收窄 C，再谈加人】
    参与方写"角色"不写人名（改名要动全表 = 矩阵会先烂在这里）
  关键：A 是"对结果负责"，不是"有权决定" —— 失效点由此而来
```

- **为什么这样设计有效**：因为 A 唯一且被显式写在矩阵上，所以「这件事不归我管」第一次有了可反驳的依据——责任从口头共识变成一张可核对的表，跨团队项目最常见的真空被结构性堵住。
- **代价**：矩阵按「活动数 × 参与方数」增长，活动清单与参与方任何一边变动都要同步改表；表越长，维护成本越可能超过收益，团队会先停更、再弃用。此外它维护的是**责任**，完全不涉及授权与资源。
- **失效点**：当 A 落在没有决定权的人身上时，「责任清晰」会反转成「谁都清楚该背锅、但没人敢拍板」——因为矩阵只分配责任、不转移权力，团队会学会「先别动，等上级」；表现为矩阵填得很完整，而每次跨团队决定都被推迟。
- **真实使用**：【公开】PMBOK 指南把责任分配矩阵列为规划资源管理中的工具（[PMBOK 指南第 6 版, 2017]；该形式在 1960s–70s 的项目管理实践中成型，本章 [§7.2](04-cross-team-collaboration-section-7-sec7.md) 同源）。判定方法：翻出最近一次跨团队决议，看它是「某个 RACI 表让 A 拍板的」，还是「某位 Sponsor 或共同上级拍的」——后者居多时，问题不在矩阵。

#### 3.2.2 Stakeholder 管理模式（4 象限）

- **被什么约束逼出来**：参与方众多而沟通带宽有限，且**否决权不随利益大小走**——一个不关心这件事的高权力方，可以在最后一刻让整件事停下来。
- **结构**：

```text
Stakeholder 4 象限：分类维度是"利益"与"权力"，不是职级
                    权力 高
   ┌──────────────┬──────────────┐   高利益×高权力（密切管理）：
   │ 密切管理      │ 保持满意      │     周会 / 月报 / 1:1，让其进入决策过程
   │ 高利益×高权力 │ 低利益×高权力 │   低利益×高权力（保持满意）：
   ├──────────────┼──────────────┤     季度汇报 / 合规清单，不占用其带宽
   │ 保持告知      │ 最少努力      │   高利益×低权力（保持告知）：
   │ 高利益×低权力 │ 低利益×低权力 │     周报 / 培训，让其在执行期有输出
   └──────────────┴──────────────┘   低利益×低权力（最少努力）：Wiki / 年报
                    权力 低
  ─────────────────────────────────────────────────────────────
  分类依据不是职级，因为"谁能让这件事停下来"与"谁的头衔高"常常不是同一个人
  地基是两个只有当事人掌握的信息：谁在意（组织图里查不到）、
  谁能否决（头衔 ≠ 否决权）；利益与权力都在中间的那批人没有格子可放，
  这是本模式最常见的漏项来源
```

- **为什么这样设计有效**：因为分类维度是「利益 × 权力」而不是「职级」，所以沟通带宽被投给真正能影响结果的人——一个低职级但握着数据口径的人会进「密切管理」，一个高职级但不关心的人只需要「保持满意」，带宽的分配第一次与事实对齐。
- **代价**：象限划分依赖当事人对「谁在意、谁能否决」的私下判断，判断一旦错，整张表的动作也跟着错；此外四格之外总有一批「灰度」干系人（利益与权力都中等）没有归属，投入与否只能靠经验。
- **失效点**：当低利益、高权力的「保持满意」格被当成「不需要参与」时，减少打扰的优点是**在收口那一刻变成否决**——因为不进入决策过程的否决者只会在最后出现，「会而不决」最常见的成因就在这一格。修法不是把所有人都拉进会，而是在该格里提前做一次「能否否决」的确认。
- **真实使用**：【公开】干系人（Stakeholder）这一概念框架出自 Freeman《Strategic Management: A Stakeholder Approach》(1984)（本章 [§7.2](04-cross-team-collaboration-section-7-sec7.md) 记为 1984）；「利益 × 权力」四象限是其后在项目管理实践中通用的分类工具，本章 [§7.5](04-cross-team-collaboration-section-7-sec7.md) 也按「Freeman 之后的通用实践」处理——**两者出处不同，引用时建议分开**，不要把四象限直接归给 Freeman。判定方法：问「谁能让这件事停下来」，而不是「谁是老板」。

#### 3.2.3 Shared Service 模式

- **被什么约束逼出来**：同一项能力被三个以上团队重复建设【经验：2–3 个是可考虑共享的下限，口径见本节 3.6 与本章 [§7.5](04-cross-team-collaboration-section-7-sec7.md)】，且这些需求**可批量化**——需求足够同质，才谈得上收进一个团队统一做。
- **结构**：

```text
Shared Service：把协作从"排期依赖"改成"复用标准件"（多对一，带队列）
  ✗ 服务团队接需求：业务 A / B / C 各提需求 → 排队 → 服务团队成为唯一瓶颈，
    而它离业务最远、最不了解业务语义
  ✓ 服务团队产标准件：产出标准模型 / ID 打通 / 数据服务 / 指标定义 / 权限模型，
    业务方各自取用与组装、互不排队；服务团队只对"标准件质量与复用率"负责
  ─────────────────────────────────────────────────────────────
  成本结构（决定它会不会退化成排队）：产能 = 团队人数 ÷ 单个需求平均人周；
    到达率持续超过产能时，队列随时间线性增长，而不是"稳定在某个长度"
    本章 §7.3.3 的算术【推算】：4 人团队 / 2 人周每需求 → 产能 2 个/周；
    6 个使用方各每周提 0.5 个 → 到达率 3 个/周 → 每周积压 1 个，
    半年约 26 个，平均等待约 13 周
```

- **为什么这样设计有效**：因为服务团队的产出被定义为**标准件**而不是交付物，协作的形态就从「找人办事」变成「取用积木」——业务方不需要排队，服务团队也不再承担自己最不擅长的业务语义判断。这条机制成立的前提是：需求能被批量化成标准件。
- **代价**：它是「多对一 + 队列」结构，协调成本随被服务团队数线性增长，一旦到达率超过产能，队列就会持续积累；此外标准件必须容忍使用方的差异，否则会被退回成定制需求（回到排期模式）。激励上还要额外一层设计——否则共享会因成本独享而衰减【经验，本章 [§7.3.2](04-cross-team-collaboration-section-7-sec7.md) 判为半年到一年量级，按自己的历史投入曲线校准】。
- **失效点**：当使用方各要一套定制时，「复用带来规模经济」会反转成「排队制造瓶颈」——因为定制需求无法批量化，队列以每周（到达率 − 产能）的速度积累；表现为业务方判定「不如自建」，一边继续用一边暗中自建，总成本反而高于各建一套。
- **真实使用**：【公开】阿里 2015 年公开提出「大中台、小前台」，2020–2021 年前后出现「中台变薄」的组织调整口径【经验，公开报道口径不一、无单一权威来源，此处只取方向：共用一套能力的组织形态会随业务节奏被反复重估】；本章 [§6 案例 4.1](04-cross-team-collaboration-section-6-sec6.md) 记录的做法是「只产标准件、KPI 设为复用率与一致性」，[§6 案例 4.4](04-cross-team-collaboration-section-6-sec6.md) 记录的是用贡献分改变共享的支付矩阵。机制侧的公开参照是公共资源治理研究：共享资源可以避免耗竭，但前提是有明确边界、成本分摊规则与监督机制（Ostrom, «Governing the Commons» 1990，本章 [§7.3.2](04-cross-team-collaboration-section-7-sec7.md) 同源）。判定方法：统计共享平台近三个月**实际合并的代码里来自业务团队的比例**，而不是「派人名单」上的比例。

#### 3.2.4 Platform Team 模式

- **被什么约束逼出来**：能力可以被产品化（不需要每次现场判断），而且使用方有能力自助——否则「平台」只是一套要人来教的工具。
- **结构**：

```text
Platform Team：把决策下沉进模板与默认值（一对多，边际成本近似为零）
  平台侧产出（写一次）                      使用方（读多次）
  · 默认路径（脚手架 / 模板 / CI 流水线）
  · 默认值（存储选型、鉴权、配额）   ──▶    新建服务默认就走在这条路上
  · 迁移工具（兼容层 / 自动迁移脚本）──▶    存量改造由平台分担成本
  · 文档与自助入口                  ──▶    遇到问题先查文档，而不是先提需求
  ─────────────────────────────────────────────────────────────
  一对多自服务 → 使用方越多，单位成本越低；平台不靠开会改变行为，
  靠"不按默认值就要付额外成本"改变行为
  三个前提（缺一个就退化成"做了没人用"）：① 能力可产品化；
  ② 有迁移工具与过渡期支持（否则改造成本被转嫁给业务方）；
  ③ 默认值是对的（固化的判断要经得起业务检验）
```

- **为什么这样设计有效**：因为平台的决策被下沉进模板与默认值，所以它不开会也能影响几十个团队的行为——使用方越多，单位成本越低，这是协作模式里唯一一条「规模越大越便宜」的路径（本章 [§7.3.3](04-cross-team-collaboration-section-7-sec7.md) 的机制分析）。
- **代价**：平台必须先把判断规则固化（哪些路径是默认的、偏离要付什么代价），这要求平台团队对业务有足够理解；同时改造成本不会消失，只是从「每个业务方各付一次」变成「平台先付一次」——如果平台不肯承担迁移工具的成本，这笔成本会原封不动回到业务方身上，进而触发绕行。
- **失效点**：当平台团队不懂业务、固化的是错的默认值时，「规模化赋能」会反转成**规模化地做错**——因为默认值一旦成为多数团队的路径，纠错成本从「改一个服务」变成「改所有下游」；表现为平台每发一个新默认值，下游就要排一次改造。
- **真实使用**：【公开】Google 的 SRE 实践在其公开出版的《Site Reliability Engineering》(O'Reilly, 2016) 中有系统描述（可按书名核验），本章主文件 [§1.4](04-cross-team-collaboration.md) 记为 2010 年起推行。【经验】Stripe 一类以 API 为中心的公司常被引用为「平台即产品」的实例，其具体组织形态属公开材料有限的推断——判定方法：看它的公开工程文档是否把开发者体验当作产品指标（上线时长、自助率），而不是只看功能清单。

#### 3.2.5 CoE（Center of Excellence）模式

- **被什么约束逼出来**：某个专业能力（治理、模型工程、MLOps）需要在多个团队之间保持一致，但没有任何一个团队有权给别的团队下标准。
- **结构**：

```text
CoE：只有标准、没有否决权（一对多广播）
  标准与推荐做法 ──▶ 宣贯 / 培训 / 评审清单 ──▶ 各团队自愿采纳
        ▲                                              │
        └──────── 采纳率是唯一的反馈信号 ◀──────────────┘
  成本随"材料量 × 宣贯频次"增长；采纳率不随材料量增长
  → 加发文不会提高一致性，只会增加文件量
  ─────────────────────────────────────────────────────────────
  与 Platform 的分工：平台把判断固化进默认值（有"偏离就付成本"的执行力），
  CoE 把判断写成标准（只有推荐力）；标准层的产出最终必须落到能力层
  （被固化成默认值）或定责层（被写进评审的退出条件），否则只是文件
```

- **为什么这样设计有效**：因为 CoE 不占业务团队的编制、也不背业务交付，所以它能以极低的边际成本把专业判断横向广播出去——一个团队的经验可以变成所有团队都读得到的标准，这是它相对于「每个团队各养一个专家」的规模优势。
- **代价**：没有否决权意味着**收益完全依赖采纳**，而采纳取决于标准与一线处境的贴合度；产出以材料量计量也容易制造虚假的产出感。此外它天然远离业务现场——离得越远，写出来的标准越容易被一线判为「落地不了」。
- **失效点**：当 CoE 脱离一线时，「专业能力沉淀」会反转成「文件变多、采纳率不涨」——因为标准只能被采纳、不能被强制，一旦内容与一线处境脱节，组织就会认定 CoE「没有产出」，投入随之被削减，形成负循环。
- **真实使用**：【经验】CoE 是跨行业通用的组织形态；原清单点到的实例（ThoughtWorks、IBM 一类）多为公开材料中的实践叙述，而非可核验的组织数据——判定方法：看它的产出物有没有进业务指标，以及有没有明确的采纳率口径。若答不出采纳率，说明它还没落到能力层或定责层；本章 [§5.5](04-cross-team-collaboration-section-5-ai.md) 对「某组织某年更新了某组织模型」这类说法的处理口径同样适用。

#### 3.2.6 Enabling Team 模式（Team Topologies）

- **被什么约束逼出来**：能力需要**传递**而不是**承接**（承接会变成永久依赖），同时组织不愿为此长期占用编制，所以赋能必须带时间盒与退出条件。
- **结构**：

```text
Enabling Team：短时、高带宽、双向，带时间盒与退出条件（多对一）
  专家 2 人 ──每周固定接触──┬──▶ 被赋能团队 A（共同做事，不是替它做）
                           ├──▶ 被赋能团队 B
                           └──▶ 被赋能团队 C
  时间盒：边界稳定后切回 X-as-a-Service（一方提供服务、另一方自服务）
  退出条件：被赋能团队能独立完成原先需要专家的那类工作
  上限由接触时间决定（本章 §7.3.3 同一口径）【推算】：
    2 名专家 × 每人每周约 10 小时 ÷ 每团队约 4 小时/周 ≈ 同时服务 5 个团队
  超出后人均接触时间被切成片段，Enabling 退化成"咨询台"
```

- **为什么这样设计有效**：因为它在结构上是「多对一 + 双向高带宽」（专家与业务团队共同做事），所以被传走的不只是交付物，还有判断力——业务团队在共同做事的过程中把方法内化，这正是它与「替他们建」的 Shared Service 的根本区别。
- **代价**：双向高带宽意味着单个团队的接触成本很高，可服务的团队数受可投入接触时间硬性限制；而且它要求业务团队负责人真的愿意接（把决定权留在团队内），否则专家会退化成外援。
- **失效点**：当被赋能团队把决定权交出去时，「能力传递」会反转成「业务团队交出自主权并停止成长」——因为 Enabling 的决定权本就留在被赋能方，一旦被当成指挥者，团队会停止自己判断，撤出之后能力随之消失。
- **真实使用**：【公开】Team Topologies（Skelton & Pais）把 Enabling 定义为**临时角色**（有时间盒与退出条件），并给出 ING 的案例（本章 [§7.2](04-cross-team-collaboration-section-7-sec7.md) 记为 2019；主文件 [§1.4](04-cross-team-collaboration.md) 记为 2017，两处口径不一致，引用时以出版物本身为准，可按书名自行核验）。原清单把 Enabling 的典型使用者记为 **ING Bank 与 Spotify 两家**（本章 [§7.2](04-cross-team-collaboration-section-7-sec7.md) 的候选表同此口径）：ING 一侧可在 Team Topologies 的公开案例中核验；Spotify 一侧属公开材料中的实践叙述，未核到指向 Enabling 这一具体团队形态的确切出处，故只记名单、不记细节【经验】。判定方法：看这个赋能团队有没有写「退出条件」与预计撤离时间——写不出来的，实际上是驻场外包。

#### 3.2.7 Spotify 模型（Squad / Tribe / Chapter / Guild）

- **被什么约束逼出来**：团队需要端到端自治（每个 Squad 自己决定做什么），但组织又不愿意放弃横向的专业标准与人才发展——自治与一致性必须被拆到两个不同的载体上。
- **结构**：

```text
Spotify 模型：自治单元 + 横向社群（两套载体重叠）
  Tribe（多个 Squad 的集合）
  ┌────────────────────────────────────────────────┐
  │ Squad A    Squad B    Squad C  ← 端到端自治      │
  │    └──────────┴──────────┘    决定"做什么"       │
  │ Chapter（同一 Tribe 内的专业条线）→ 决定"按什么标准做" │
  └────────────────────────────────────────────────┘
  Guild（跨 Tribe 的兴趣社群，不承担任何决策）
  Chapter 没有决策权时只是兴趣社区 —— 标准要靠"谁签、不签的后果"才生效
  规模风险：自治度越高，越容易各自写同一份数据、长多套同类实现
```

- **为什么这样设计有效**：因为「做什么」与「按什么标准做」被分到 Squad 与 Chapter 两套载体上，所以团队可以在交付上自治、在专业上对齐——不需要把所有人都叫进一个评审会来维持一致性，这正是它相对职能型组织的机制优势。
- **代价**：两套载体天然会争夺同一批人的时间；Chapter 若没有决策权，它的一致性就只能靠自愿，标准形同建议；自治度越高，跨 Squad 的重复实现越容易发生，而这类重复只有在规模上去之后才会被察觉（重复造轮子）。
- **失效点**：当自治边界与数据归属没被同时定义时，「自治 + 学习社区」会反转成「重复建设 + 口径分裂」——因为每个 Squad 都会为自己的交付去写同一份数据，边界在数据层重新糊在一起（本章 [§7.3.4](04-cross-team-collaboration-section-7-sec7.md) 的 Conway 机制）。可观测的判据：同一份数据的变更要串行经过几个团队。
- **真实使用**：【公开】2012 年由 Spotify 的 Henrik Kniberg 与 Anders Ivarsson 公开的《Scaling Agile @ Spotify》为该描述的主要来源（本章 [§7.2](04-cross-team-collaboration-section-7-sec7.md)；可按标题自行检索核验）。【经验，只采信方向】该描述被对外广泛复制为组织模板，但受到来自当事人的公开质疑；本章 [§5.5](04-cross-team-collaboration-section-5-ai.md) 已按「方向可信、确切出处未核到」处理，因此本节只把它当作「自治与横向社群的一种组合方式」，不当成可照搬的制度。

#### 3.2.8 AI 增强协作模式（2024+）

- **被什么约束逼出来**：协作的上下文存在于会议里，而记录成本由人支付；只要写纪要要有人付工时，规模一大它就会被跳过——没被记下来的决定，只能靠当事人记忆与零散消息追溯。
- **结构**：

```text
AI 增强协作：把"产生一份可用记录"的边际成本压向零
   会议 ──① 转录（原始全文，可回查）─────▶ 留存与同意设置（合规前提）
        ──② 摘要（模型产出，不是人的记录）─▶ 必须显式指定"确认人"
        ──③ 行动项（谁 / 做什么 / 何时）──▶ 写进任务系统才可能被跟踪
        ──④ 翻译与改写（业务↔技术↔数据语言）▶ 只作用于表述层，不解决定义
  ─────────────────────────────────────────────────────────────
  改变的是"记录成本"，不是"谁负责"：
    过去：有人写纪要 → 写的人对正确性负责
    现在：模型出摘要 → 若没人确认，记录量上升而责任仍然悬空
    「AI 不产生 Owner」—— 决定仍然必须有人确认、有人认领
```

- **为什么这样设计有效**：因为转录与摘要把「产生一份可用记录」的边际成本从「一个人 × 一段时间」压到接近零，所以「没被记下来的决定」显著变少——跨团队协作里最难的部分（决定曾经被做过、但没人能说清在何时由谁做的）第一次有了可检索的载体。
- **代价**：摘要的**责任归属变成无人**，必须显式指定确认人，否则一份没人认领的摘要会被当作依据引用；同时引入合规面（留存期、告知与同意、依据可回查），以及模型换代带来的解释力下降——历史摘要由旧模型产出，新读者未必知道它是怎么生成的。
- **失效点**：当记录量增长而消费入口没建立时，「可追溯」会反转成噪声——因为没有人会回看一份没有被任何人引用的纪要；此时增加记录只是增加搜索噪声。判据很直接：观察这些结构化条目被引用的次数。
- **真实使用**：【公开】Microsoft 365 Copilot 于 2023 年 11 月发布面向企业客户的商用公告（Microsoft 官方发布公告，2023-11；本章 [§5.2.1](04-cross-team-collaboration-section-5-ai.md) 同源）。【经验】原清单点到的工具（Otter.ai、Notion AI、Slack AI 一类）能力、限额与计费以各自官方发布说明为准；本章 [§5.1](04-cross-team-collaboration-section-5-ai.md) 把这一族判为 L2——能力与接口可核验，缺第三方非厂商的公开生产案例。判定方法：看会议记录里的「决定」与「行动项」有没有被抽成可被引用的结构化条目，以及有没有指定确认人。

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 一次性跨团队项目、有明确起止（原：跨 BU 项目 / 数据治理） | 章程 + Sponsor + RACI + Stakeholder（裁决权在 Sponsor） | 组建常设团队是用永久组织成本换一次性收益 | Sponsor 能不能在两个 BU 争同一批人时当场裁决 |

| 远程 / 异步为主（原：远程跨团队） | 异步协作 + AI 增强协作（写一次、所有人读） | 靠多开同步会：多对多路径数随团队数平方增长【推算：8 个团队需维护 8×7÷2 = 28 条两两协商路径】 | 跨团队会议小时数里，有多少是为「同步一个本来能写下来的决定」 |
| 有共同上级且只需推进一件事 | 直接汇报 + 一份验收标准 | 有裁决权时，RACI 与 Sponsor 都是多余的事务成本 | 共同上级愿不愿意当场裁决 |

本主题下**最常被误选的一对是 Shared Service 与 Enabling Team**。两者的名字都像「共享团队」，差别在替对方建还是教对方建：**当使用方只有一两个、或需求高度定制时，Shared Service 会把服务团队变成排队瓶颈**（需求无法批量化，队列持续积累），而正确动作本应是「把能力还给业务团队内建，或改成 Enabling」。误选的代价不会立刻显现——服务团队会先加班撑着，**半年到一年**后表现为业务方一边依赖一边自建，双方各投一份钱做同一件事【经验：衰减窗口的口径见本章 [§7.3.2](04-cross-team-collaboration-section-7-sec7.md)，按自己的历史投入曲线校准】。反向误选同样存在：能力已经高度通用，在用的团队数已超过 Enabling 的接触时间上限（本节 3.2.6 的推算约为 5 个【推算，见本章 [§7.3.3](04-cross-team-collaboration-section-7-sec7.md)】），却还在用「驻场赋能」的方式逐个教——此时瓶颈不在方法，该换成平台化的自服务。

### 3.4 组合模式：真实系统不会只用一种

原表的六行场景里有五行落进下面三组，合起来对应的正是本章 [§7.6](04-cross-team-collaboration-section-7-sec7.md) 归纳的四层结构：**定责层、能力层、标准层、介质层**。第五行（业务自治团队 → Spotify 模型）不在这三组里——它选的是**团队内部怎么组织**，而不是「跨团队协作缺了哪一层」；其中 Chapter 这一部件在 §7.6 里与 CoE 同列标准层，Squad 的端到端自治本身不落在四层中的任何一层。

**组合 A：章程 + Sponsor + RACI + Stakeholder（定责层）**

- 各自承担什么：章程锁目标与验收口径，Sponsor 提供裁决权，RACI 分配责任，Stakeholder 4 象限决定沟通带宽投给谁。边界是：RACI 回答「谁做什么、谁对结果负责」，Stakeholder 回答「谁会被影响、谁能让它停下」。四件同属定责层——它们只改变信息与责任的分布，不动编制（本章 [§7.2](04-cross-team-collaboration-section-7-sec7.md) 的「定责与争取」族）。
- 运维代价：两套表必须挂在**同一份活动清单**上，否则活动定义分裂、两边谁都不认；每次范围变更要同步改两处。
- 适合规模：一次性跨团队项目、跨 BU 治理（合规、安全、口径）。
- 失效边界：定责层失效的表现是**决策瘫痪**——章程发了、A 也填了，但没人拍板；此时正确动作是向上要一个决策机制，而不是继续优化矩阵。

**组合 B：Shared Service + Platform（能力层，两种交付形态并存）**

- 各自承担什么：Shared Service 承担需要共同维护、难以完全产品化的能力（标准模型、ID 打通、指标定义）；Platform 承担可以被默认值化的部分（脚手架、流水线、配额与鉴权）。
- 运维代价：两种交付形态在同一批需求上会互相挤压——凡是被做成默认值的，就不该再留在服务团队的队列里，否则队列里塞满「其实可以自助」的请求；这要求两边定期把队列里的通用项下沉成默认值。
- 适合规模：≥ 3 个团队重复建设【经验，见 3.6】、且需求能批量化到一定程度。
- 失效边界：能力层失效的表现是**重复建设**——服务团队还在排队，业务方已经自建；判据是共享平台近三个月实际合并的代码里，来自业务团队的比例。

**组合 C：CoE + Enabling + 异步协作 / AI 增强协作（标准层 + 介质层）**

- 各自承担什么：CoE 出标准与方法论（推荐力），Enabling 把方法带进具体团队并撤离（能力传递），异步协作与 AI 增强协作让「写一次、所有人读」成为默认（介质）。
- 为什么是两层而不是三层：**Enabling 不是四层之外的第五层**——它执行的是 Team Topologies 的**交互契约**（短时高带宽进入、边界稳定后切回 X-as-a-Service），而 §7.6 把交互契约归入**标准层**。所以 CoE 与 Enabling 同层不同形：一个把标准写出来，一个把标准带进团队再撤离。
- 运维代价：三个部件各有失效方式且不能互相替代——CoE 失效表现为口径分裂（文件变多、采纳率不涨），Enabling 失效表现为咨询台（接触时间被切碎），介质层失效表现为重复沟通（同一件事在不同群里各说一遍）。
- 适合规模：跨域能力（MLOps、数据治理）在多个业务域同时推进。
- 失效边界：标准层失效最容易和介质层混淆——**「发了标准」不能替代「有人拍板」，「开了会」也不能替代「能力有人建」**；判断两层是否重叠的方法很直接：看它们是否在处理同一批决策。

三个组合的共同点是：**它们都在把「需要协商的接口」改成「不需要协商的默认值或契约」**。反过来说，如果一个「组合方案」里没有任何一环在减少需要协商的事项，那它大概率只是把几个模式名并排放进了组织图里。

### 3.5 反模式与失效分析

原文件的 7 条反模式全部保留，补上「症状 / 后果 / 成因 / 修法」四段。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「老好人」式协作 | 会议上一片同意，没有人提过反对，问题原封不动留到下一次 | 分歧转入私下，决策质量下降；项目失败后无法复盘是哪一步没被发现 | 把「不得罪人」当成协作的目标，混淆了关系维护与问题解决 | 把反对意见变成流程的一部分：材料先行、书面异议、Pre-mortem 一轮 |
| 「三个和尚没水喝」（RACI 模糊） | 每人都觉得不归自己管，活动清单上没有 A 或有多个人自认是 A | 责任真空，事情卡在无人认领处，且它是**静默**的——没人报警 | 只列活动不分责任，或把 A 挂在无决定权的角色上 | 每项活动有且仅有 1 个 A，且 A 落在有权决定的人身上 |
| 「共享团队沦为工具人」 | 共享团队的排期里全是临时支援与打杂需求，自己负责的标准件长期没进展 | 团队士气与留存下降；标准件质量下滑、复用率随之下降，形成负循环 | 服务边界没定义，谁都能往队列里塞需求；考核按吞吐而非复用 | 明确服务边界与价值主张（标准件的复用率）；客户成功机制定期回访业务方；成员轮岗到业务团队 |
| 「平台做了没人用」 | 平台功能清单很长，但业务方接入量长期上不去，且已有人在自建同类 | 资源浪费；业务方与平台双份投入做同一件事，总成本高于各建一套 | 平台从自己的技术偏好出发，没有迁移工具，默认值脱离业务处境 | 业务方从 0→1 就参与；先做最小可用版本；提供迁移工具与过渡期支持；平台目标与业务方结果挂钩 |
| 「CoE 学术化」 | CoE 的产出是文档与培训，问采纳率答不出，问进过哪些业务指标也答不出 | 组织认定 CoE 没产出，投入被削减，形成负循环 | 远离一线，标准与现场处境脱节；只有推荐权却按「发文量」计量产出 | 强制轮岗（如每年约 30% 时间到业务团队【经验：本书建议的比例，按各组织的轮岗制度校准】）；OKR 包含业务结果；以项目制深入业务 |
| 「跨团队会议 = 撕扯会」 | 会而不议、议而不决、决而不行；同一议题反复上会 | 会议成为主要工作量；多对多路径数按 n(n−1)/2 增长，规模一大就被会拖住 | 没有议程与决策点、主持人同时是当事方、会后无 Action Items、无时效 | 会前发议程并写明决策点；主持人中立；会后 24 小时内出纪要与 Action Items【经验：本书建议的时限，按会议节奏校准】；控制时长 |
| 「Sponsor 缺位」 | 项目无 Sponsor，资源与裁决都要临时找人；争议只能僵持或反复升级 | 推进困难、决策停滞；RACI 的 A 变成背锅位 | 启动时默认「这件事大家都支持」，没有把裁决权显式落到人 | 启动前明确 Sponsor（通常是 +2 级高管）；Sponsor 定期 Review；并在章程里写明裁决时效 |

**最危险的三条，在生产中的典型暴露方式：**

「共享团队沦为工具人」不会以「团队不开心」这种形式暴露，它以**一次共享能力的质量事故**暴露：业务方发现标准件的口径已经半年没人维护，而服务团队的排期表上全是别人的临时需求。它的成因是机制性的——**服务边界没定义 + 考核按吞吐**，于是队列里塞满打杂需求，而标准件（真正产生规模收益的那部分）永远排在后面。

「平台做了没人用」的暴露方式是**双份投入的账单**：平台侧的投入已经发生，业务方一侧又有团队在自建同类能力，两边都在花钱。这条反模式最容易被误诊为「推广不力」，实际成因是平台把改造成本转嫁给了业务方——**没有迁移工具的默认值，等于让对方自费换一套**。

「Sponsor 缺位」的暴露方式最隐蔽：项目前几个月的推进看起来正常，因为大家都在配合；第一个真正有争议的决定出现时，项目直接停住——没有人能裁决，而 RACI 的 A 成了背锅位。它的修法不在项目里，而在项目启动那一刻：**把裁决权显式落到一个人身上，并约定争议的时效**。

这 7 条反模式有一条共性值得单独记住：**它们都在把「有一个机制」当成「机制被挂在有权或有利的位置上」**。RACI 挂在无权者身上会变成背锅表；标准挂在没有被采纳驱动的 CoE 上会变成文件；平台挂在没有迁移支持的团队上是自建的理由；共享挂在成本独享的博弈里会静默退化。判断一个协作模式是否真的生效，只需问一句：**不照它做，会付出什么代价？**答不出代价的机制，只是在描述愿望。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 一次性项目 → 长期共享能力 | 章程 + Sponsor + RACI | 按活动定责的矩阵越来越长，维护成本超过收益；一次性收益消失 | Shared Service（标准件 + 成本与收益归属机制） | 要改编制与考核口径，并接受「拨款容易、撤编难」 |
| 使用方 1–2 个 → 3 个以上重复建设【经验：2–3 个是可考虑共享的下限】 | 各团队自建 | 重复建设的总成本高于协调成本 | Shared Service 或 Platform（需求可批量化时） | 需先批量化需求，否则只是把重复建设搬进队列 |
| 需求高度定制 → 需求可批量化 | Shared Service（接需求） | 队列以每周（到达率 − 产能）的速度积累【推算，见 3.2.3】 | 只产标准件 + 自助通道 | 要把定制需求退还给业务方内建，短期会被判为「不配合」 |
| 专家驻场 → 方法已内化 | Enabling Team | 接触时间上限成为瓶颈，超出后退化成咨询台 | Platform（自服务）或 CoE（标准固化） | 需要先把方法写成默认值与文档，否则撤人即失效 |
| 多对多协商 → 一对多自服务 | 跨团队同步会 + RACI | 路径数按 n(n−1)/2 增长，会议成为主要工作 | 平台默认值 + 写一次所有人读的介质 | 需先定义默认路径；过渡期的迁移工具投入落在平台侧 |
| 内部协作 → 对外取证（合规 / 审计） | 口头约定 + 邮件确认 | 复用方不敢依赖，争议时无凭据 | 契约化 SLA（口径、责任、变更流程）+ 留痕 | 要改流程以产出可导出的记录，并约定争议时效 |
| 无共同上级 → 有明确决策组 | 靠说服与公开承诺 | 说服成本随相关方数量上升，且无法收敛反对意见 | 章程 + Sponsor + RACI（A 落在有权者身上） | 需要上级真的愿意裁决，否则只是多了一层形式 |
| 组织重组 → 系统边界仍不一致 | 调整汇报线 | Conway 定律会把旧边界从系统里长回来，重组变成周期仪式 | 先定数据归属与接口契约，再动团队边界 | 需要先解决「谁写哪张表」，这一步没有技术捷径 |

判据是统一的：**当「多一个团队 / 多一个使用方 / 多一次协商」带来的边际成本开始超过边际收益时，就该换模式**。这个拐点通常不体现在满意度调研里，而体现在两处账单上【经验】：一是**跨团队会议小时数**里有多少是为「同步一个本来能写下来的决定」；二是**共享平台的队列长度**，以及有没有团队在暗中自建。

### 3.7 自检清单

- [ ] 这项工作的决定权在谁手上？说不出一个人或一个机构，就先别谈 RACI——工具产生不了权力。
- [ ] 每项活动是否恰好 1 个 A？多 A 等于无人负责，且这种真空没有任何人会报警。
- [ ] RACI 的 A 是否落在有权决定的人身上？落在无权者身上，它只是背锅表。
- [ ] Stakeholder 里「低利益 × 高权力」这一格有没有人？没有，最后一刻的否决就来自这里。
- [ ] 跨团队协作的路径是几对几？多对多的条数按 n(n−1)/2 算一遍，再决定要不要改成一对多的自服务。
- [ ] 共享能力的队列在变长还是稳定？到达率大于产能时，等待时间会持续增长，加班不是解。
- [ ] 共享 / 平台的贡献在业务团队的 KPI 里可见吗？不可见，投入会在半年到一年内衰减【经验】。
- [ ] 平台的默认路径，新团队能不能在不找人沟通的情况下走通？必须先提问再提需求，就是没做成自服务。
- [ ] 平台为存量迁移提供了什么工具与过渡期？答不出，改造成本就被转嫁给了业务方，绕行是理性选择。
- [ ] 赋能团队有没有写退出条件与预计撤离时间？写不出的是驻场外包，不是 Enabling。
- [ ] 同一份数据的变更要串行经过几个团队？≥ 3 个，说明组织边界与系统耦合不一致【经验：按一次端到端变更实际经过的交接次数数出来】。
- [ ] 最近一次争议是怎么解决的？是某个机制裁决的，还是拖到某位上级出面——后者说明 Sponsor 缺位。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 有共同上级、只需推进一件事 | 直接汇报 + 一份验收标准 | 有裁决权时，定责工具都是多余的事务成本 |
| 无共同上级、需要收敛一个决定 | 章程 + Sponsor + RACI（A 落在有权者身上） | 工具只分配责任、不转移权力 |
| 参与方多、否决权分散 | Stakeholder 4 象限 | 带宽投给「能让事情停下来」的人，而不是职级最高的人 |
| ≥ 3 个团队重复建设【经验，见 3.6】、需求可批量化 | Shared Service + 成本与收益归属机制 | 收益共享、成本独享时，只能靠改博弈结构维持投入 |
| 能力可产品化、使用方能自助 | Platform Team + 迁移工具 | 一对多自服务的边际成本近似为零，是唯一随规模变便宜的模式 |
| 需要跨域标准一致、但无否决权 | CoE，且必须落到默认值或评审退出条件上 | 只有标准没有否决权时，一致性只能靠采纳率 |
| 要把方法留在业务团队 | Enabling Team（时间盒 + 退出条件） | 决定权留在被赋能方，能力才会被内化 |
| 团队自治优先、需要横向标准 | Spotify 模型（Squad + Chapter / Guild） | 把「做什么」与「按什么标准做」分到两套载体 |
| 远程 / 异步为主 | 异步协作 + AI 增强协作 | 记录成本被压向零，但必须显式指定确认人 |
| 团队边界与系统边界长期错位 | 先定数据归属与接口契约 | Conway 定律会让旧边界从系统里长回来 |

> 本节小结：决定这八个模式选哪一个的**唯一那条结构性约束，是「这项协作的决定权归谁」**——它决定你能不能动用「团队形态」类的模式（Shared Service / Platform / CoE / Enabling 都要求有人能改编制与考核），还是只能停在「定责与说服」类（RACI / Stakeholder / 章程）。第二层约束（成本与收益的归属）只在能力层内部起作用，决定共享能撑多久，不决定候选集合。判断一个协作模式是否真的在生效，也只需看一件事：**不照它做，会付出什么代价**。
