### 6.1 阿里巴巴"**中台战略**"8+ 年（2015-2024）

**背景（Why）**

阿里 2015 年面临**跨 BU 重复建设**挑战：
- **淘宝 / 天猫 / 支付宝 / 菜鸟**——**5+ BU**——**「**重复造轮子**」**
- **「**业务复用**」**——**「**标准化**」**

**触发点（What）**

2015 年**阿里启动中台战略**（[阿里 2018 中台白皮书]）——**目标**：「**5 套 → 1 套**」。

**详细做法（How）**

阿里中台的**5 大核心组件**：

1. **抽离共性能力（核心）**
   - 关键设计：**淘宝 / 天猫 / 支付宝**——**抽离**——**「**Shared Service**」**
   - 关键代码：
     ```java
     // 阿里中台抽离
     public class MiddlePlatform {
         // 抽离各 BU 共性
         public Service extractSharedService(BU[] bus) {
             // 1. 找到共性
             Set<Service> common = findCommon(bus);
             // 2. 抽离到中台
             return this.createPlatformService(common);
         }
     }
     ```

2. **数据中台（核心创新）**
   - 关键设计：**OneData / OneID / OneMetric**——**「**全集团**」**
   - 关键能力：**「**数据统一**」**——**5 套数仓 → 1 套**

3. **RACI 矩阵（核心）**
   - 关键设计：**Responsibility 矩阵**——**「**BU vs 中台**」**职责
   - 关键能力：**「**清晰**」**——**「**无重叠**」**

4. **「**业务驱动**」**
5. **「**中台瘦身**」**（核心教训）**

**阿里中台关键数字**（[2018 公开数据]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **业务复用** | 20% | 50%+ | **30% 提升** |
| **代码复用** | 20% | 50%+ | **30% 提升** |
| **数据复用** | 0 | 80%+ | **∞** |
| **「**新业务接入**」** | 6 月 | 6 周 | **4 倍** |
| **「**中台团队**」** | 0 | 200+ 人 | **∞** |
| **「**中台瘦身**」** | 0 | 2019 | **「**回归**」** |

**具体数字（How much）**

- 团队规模：阿里中台团队 200+ 人
- 关键数字（[2018 公开数据]）：
  - **200+ 中台团队**
  - **业务复用 50%+**
  - **新业务接入 4 倍加速**
- 业务影响：覆盖**阿里全集团 + 蚂蚁 + 菜鸟 + 钉钉**

**失败教训**

- **「**中台远离业务**」**——倒逼**「**2019 中台瘦身**」**
- **「**业务方不认**」**——倒逼**「**RACI 清晰**」**
- **「**代码重复**」**——倒逼**「**抽离共性**」**

### 6.2 Google"**SRE + Platform**"20+ 年（2003-2024）

**触发点（What）**

2003 年**Google 建立 SRE 团队**（[Google SRE Book]）——**Ben Treynor 创立**。

**详细做法（How）**

Google SRE + Platform 跨团队的**5 大核心**：

1. **SRE 团队（核心创新）**
   - 关键设计：**SRE**——**「**软件工程方法运维**」**
   - 关键能力：**「**50% 运维 + 50% 开发**」**

2. **SLO + Error Budget（核心创新）**
   - 关键设计：**SLO**——**「**Error Budget**」**——**「**开发与运维的契约**」**
   - 关键能力：**「**避免责任推诿**」**

3. **跨团队 SLO 协商（核心）**
4. **「**平台团队**」**
5. **「**文档 + Runbook**」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选**「**RACI 矩阵**」**（**最简单**）——**明确职责**
- 接入**1 个项目**——**「**跨 BU**」**
- 团队：2-3 人

**1 → 10 阶段：6-12 个月**

- 扩展到**10+ 项目**
- 引入**「**业务 Owner**」**（**必须**）
- 引入**「**资源池化**」**
- 团队：5-10 人

**10 → 100 阶段：12-24 个月**

- 扩展到**100+ 项目**
- 引入**「**数据中台 / 服务中台**」**（**抽离**）
- 引入**「**Error Budget**」**
- 团队：10-30 人

**100 → 1000 阶段：12-24 个月**

- 引入**「**SRE + Platform**」**（**Google 模式**）
- 引入**「**SLO 协商**」**
- 团队：30-100 人

> **本节小结**：
> - 4 个真实案例（阿里 / Google / 字节 / 美团）印证：**跨团队协作不是「**会议**」，是「**RACI + 中台 + SRE + IWA**」**组合。
> - 关键时间线：阿里 8+ 年 / Google 20+ 年 / 字节 5+ 年 / 美团 5+ 年 —— **跨团队协作是 20+ 年长期工程**。
> - 选型第一原则：**RACI 矩阵**（**最简单**）——**明确职责** → **「**业务 Owner**」**（**必须**）→ **「**数据中台 / 服务中台**」**（**生产**）→ **「**SRE + SLO**」**（**全球化**）。
> - 99% 的失败来自「**中台远离业务 + 业务方不认 + SRE 与 Dev 矛盾**」——必须有**业务驱动 + RACI + Error Budget**。
> - 真正的 ROI 来自「**30-65% 业务复用 + 4 倍新业务接入 + 10 倍可用性**」——是**大厂核心组织能力的命脉**。
