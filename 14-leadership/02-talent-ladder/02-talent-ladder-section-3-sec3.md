## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

原文件给的是一个 5 分钟答辩片段：**精通：知识图谱 / RAG / LLM 微调**、**熟悉：多模型编排 / Agent 设计**、**关注：Skills Graph / AI 治理**。这三行是有价值的结构（它把「技术深度与广度」从罗列技术名词变成了分层陈述），但它只是**整个体系最末端的输出**——它假设前面已经存在：一份写下来的等级标准、一套可举证的评估机制、一条被承认的技术通道。本节要补的正是这三件事的结构。

第一个论断：**这一层的差异不在「哪套体系更先进」，而在「组织承认几种成功范式」**。通道数不是流程设计，而是**激励函数**的具象化——它规定「把力气花在哪里，回报最大」。如果「带团队」是唯一的晋升必要条件，那么最强 IC 的理性选择就是转管理或离职；这是激励结构问题，不是「有没有第二条路」的名词问题（机制详见 §7.3.1）。

第二个论断：**同一维度在不同规模下权重相反**。「标准的统一性」在 10 人团队里几乎不需要（口头就能对齐），在上千人的组织里权重最高（不统一则人才无法跨团队流动）；「临机提拔的灵活性」在小团队是优势，在跨 BU 组织里必然带来职级通胀与标准漂移。所以先立约束，再谈模式——同一个岗位，约束不同，正确的模式就不同。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 通道容量（承认几种成功范式） | 最强 IC 留不留得住 | 「给技术牛人加薪就行」——约束是路径而非薪酬（§7.3.1） |
| 举证方式与评委池 | 晋升靠材料还是靠印象 | 「多找几个评委更公平」——评委池不够时，多找的只是更多熟人与更多成本 |
| 能力清单的失效速度 | 用静态 JD 还是动态能力图 | 「把能力写全一点」——写全等于写死，失效后维护成本高于重建 |
| 继任深度（按角色还是按人记账） | 关键岗位断档风险是否可见 | 「每个岗位都有 2 个后备」——若候选人高度重叠，最坏情况是同时空缺 |
| 淘汰与留存的判定结构 | 资源投给谁、退出怎么分析 | 「潜力高就该升」——潜力是预测，不能替代已完成的事实 |
| 组织规模与人力冗余 | 能否做岗位级轮转、能否上委员会 | 「轮转总是好的」——没有冗余时，轮转是把风险转嫁给在岗的人（§7.3.4） |

**读法**：后三行是本节新增的结构（继任、盘点与退出、组织规模），前两行决定「能不能上」，中间一行（能力清单的失效速度）决定「多久要重写一次」。

需要说明本节与原文件的关系：原文件那三行不是被替换掉的，而是被**放回它真正的位置**——它是「技术深度与广度」这一问的陈述结构（3.2.4），而这一问的答案能不能被评委接受，取决于 3.2.1 的标准是否写下来、3.2.3 的举证通道是否存在。把三行单独拿出来看，读者会以为能力清单就是体系；放回位置后才会看到，它只是最末端的输出。

### 3.2 模式逐个拆解（核心节）

下面 8 个模式按同一结构写：**被什么约束逼出来 → 结构（代码块）→ 为什么这样设计有效 → 代价 → 失效点 → 真实使用**。「失效点」是最不可省的一段——它回答的不是「有什么缺点」，而是「在什么条件下优点会反转成缺点，以及为什么（机制）」。

其中 3.2.4 就是原文件那三行的展开：它在本节的定位是**举证结构的一个片段**——它规定「怎么说」，而「说得成不成立」取决于 3.2.1 那份标准有没有写下来。

#### 3.2.1 职级能力锚点（BAR）

- **被什么约束逼出来**：「资深 / 高级 / 专家 / 资深专家」在组织内可以指任何东西；没有可观测锚点，评估只能靠印象与表达能力。
- **结构**：

```sql
-- 能力锚点的最小可校验结构：每格必须给可观测行为 + 证据形态
CREATE TABLE competency_bar (
  level     TEXT,  -- P5 / P6 / P7 / P8
  dimension TEXT,  -- 技术深度 / 系统设计 / 工程素养 / 业务理解 / 协作 / 领导力
  anchor    TEXT,  -- 可观测行为：如「能定义跨模块接口边界并说服上下游」
  evidence  TEXT,  -- 什么算证据：ADR / 评审记录 / 上线结果 / 复盘
  PRIMARY KEY (level, dimension)
);
-- 约束：anchor 写成「精通 X」「熟悉 Y」，该行无效——自陈词无法被第三方核验
```

- **为什么这样设计有效**：因为「差 1 分」这种判断只有在每格都有可观测锚点时才可复核——「P7 的系统设计该写成什么」若只落到一句形容词，这 1 分之差既无法解释也无法举证，评估必然退回印象。
- **代价**：一次性的标准书写成本，且必须长期校准（两人写出的同一格要可比）。成本随维度数 × 等级数增长——6 维 × 4 级 = **24 格**，每格要写锚点与证据形态。
- **失效点**：当标准没写下来（或只写了一句形容词）时，举证式评估反转成表达竞赛——因为讨论对象从「证据是否达标」变成了「材料写得是否漂亮」（§7.3.2）。
- **与相邻模式的边界**：锚点与 IDP 的分工是**共用一份标准、方向相反**——锚点问「这一级要什么」，IDP 问「他离这一级差哪一格」；因此标准一改，IDP 的 `gap` 必须同步重算，否则会出现「按旧标准补满了，按新标准仍不够」。
- **真实使用**：主文件 §2.2 给出 P5–P9 的能力向量（例：P7 记为 (4,3,4,4,4,4,3)）——**本书明确这是示例刻度，不是行业统计**【经验】。Ram Charan 等《The Leadership Pipeline》（2001）的核心论断「每个层级需要不同的领导技能、时间管理与工作价值观，不能跨层级跃迁」是分层锚点的理论来源【公开】。

#### 3.2.2 双通道阶梯（IC / 管理）

- **被什么约束逼出来**：若「带团队」是唯一的晋升必要条件，最强 IC 的最优策略就是转管理或离职——这是激励结构问题，加薪只能延缓不能消除。
- **结构**：

```text
双通道的结构：两条阶梯 + 一处对标（省掉对标，第二条就是纸面的）
  IC 通道  :  P5 ── P6 ── P7 ── P8 ── P9    考核：技术影响力 + 跨团队产出
  管理通道 :  M1 ── M2 ── M3 ── M4         考核：业务结果 + 团队产出 + 人才培养
  对标项（必须有）：① 薪资带宽对等  ② 预算/技术方案参与权  ③ 信息可见性
  切换规则：IC → 管理需意愿 + 能力；管理 → IC 需等级与薪资不被下调
  断链症状：IC 侧最高等级的人无法否决一个他不认可的技术方案
```

- **为什么这样设计有效**：因为通道是激励函数，所以「技术影响力」必须成为被承认的**第二种成功范式**，而不是管理的附属；因为两条路的可比性由对标项承载，所以只在头衔上开第二条路会被员工迅速识别为名义通道（识别信号很具体：能不能参与资源分配、能不能拿到同等级带宽，见 §7.3.1）。
- **代价**：双份标准 + 双份评委 + 常态化的外部对标（薪资带宽、市场定价），这项占用管理者的时间且不会被业务直接看见（§7.4）。
- **失效点**：当第二条通道不给对等的待遇与决策权时，投入全部白花**且比不做更伤信任**——因为员工会把它读成一次敷衍，此后对任何制度性承诺打折。
- **与相邻模式的边界**：双通道与「给个人设一个头衔」的区别在**可复制性**——通道意味着这套标准对任何人成立，特设头衔只对一个人成立；判定方法是有没有第二个、第三个通过同一条 IC 通道晋升的实例。
- **真实使用**：【经验】Microsoft 在 1990 年代推行技术阶梯、阿里 P/M 双序列、Google 的 IC 阶梯自 L3 起（其层级上界的两种写法与取舍见 §7.2 的说明）——均属业内公开通说，本节未逐一核验外部来源。

#### 3.2.3 晋升答辩的举证结构

- **被什么约束逼出来**：「最了解员工的人」与「最中立的人」不是同一个人。决定权与举证权必须分开，否则偏见与留人压力直接进入结果。
- **结构**：

```text
答辩材料的四问骨架（每个关键项目都要回答四问，缺一则材料只停在「做了事」）
  ① 影响范围：影响多少人 / 多少系统 / 多少资金？   ← 对应等级要求的影响范围
  ② 复杂度  ：难在哪？当时有哪些硬约束？          ← 约束越硬，同等产出越难
  ③ 独立性  ：哪部分边界是你自己定义的？          ← 区分「执行」与「定义」
  ④ 对他人的影响：谁因为你变强了？               ← 带人 / 定标准 / 让下游少踩坑
  反规则：只讲结果不讲取舍（放弃了什么、备选方案是什么）→ 无法证明「够下一级」
```

- **为什么这样设计有效**：因为等级要求本身就是按这四问写的（影响范围 / 复杂度 / 独立性 / 对他人的影响），所以材料必须逐项给证据；因为讨论对象从「人」换成了「材料」，评委的中立性才可能成立（对应 §7 的第 4 条判据「决策权归属」）。
- **代价**：引入**新的误差源——表达能力**。会写材料、会答辩的人占优；这不是放弃举证式的理由，而是必须配套材料模板、辅导与预演的原因。
- **失效点**：当组织小到「委员会里所有人都认识候选人」时，中立性不存在，材料与评议的成本白花——此时更实用的是把标准写清楚，由 +1 与 +2 共同评议，并把结论与理由对候选人明说（阈值见 §7.5）。
- **真实使用**：主文件 §2.3 给出五步辅导法（复盘关键产出 → 讲清 trade-off → 预演 Q&A → 打磨材料 → 模拟答辩）。Google 的工程晋升依赖同行反馈与晋升委员会，而非直接经理单独决定【公开】《Software Engineering at Google》（2020，见 §7.3.2）。

#### 3.2.4 技术深度与广度：精通 / 熟悉 / 关注三层陈述

- **被什么约束逼出来**：答辩只有 5 分钟讲技术面，而技术面解释不完。必须有一个「先分层、再给证据形态」的结构，否则会退化成技能名词罗列。
- **结构**（原文件三行的完整形态）：

```text
技术深度与广度的三层陈述（每层都要落到证据形态，否则是自陈）
  精通（能定标准）：知识图谱 / RAG / LLM 微调
        证据形态：你定义的标准被别人引用；你解决过别人解决不了的问题
  熟悉（能独立交付）：多模型编排 / Agent 设计
        证据形态：独立交付过的项目 + 具体取舍（选了什么、放弃了什么）
  关注（能判断趋势）：Skills Graph / AI 治理
        证据形态：你的判断被后续事实印证（提前说过的趋势或失效点）
  反规则：三层全是名词时，一个追问即可击穿——「哪一项是你定过标准的？」
```

- **为什么这样设计有效**：因为「深度」的可信度来自**你能定标准**（别人按你的判断做），「广度」的可信度来自**你能给出取舍**（知道各方案在什么约束下失效）；所以三层结构的作用是把「会什么」强制转成「能做到哪一档 + 证据是什么」。同一批技术名词加上证据形态后，无法被伪造——因为证据形态是可核验的第三方事实，而自陈只是自我评价。
- **代价**：需要持续维护这份清单（核心技能的修订周期已从年为单位压到 1–2 年，见 §7.3.3），且「精通」那一层的举证成本最高：要能找出被引用的标准、被复用的方案。
- **失效点**：当「精通」超出了一位候选人所在组织能验证的范围时（例如自称精通三项，而这三项没有第二个人在同一深度），三层结构反转成弱点——因为无人可验证的声明在评委眼里等于零，此时把「熟悉」那一层讲实，收益高于把「精通」列出更多。
- **与相邻模式的边界**：三层陈述与简历列表的区别在**每一层都带证据形态**——简历列名词，陈述要回答「你定过什么标准、做过什么取舍、判断被哪次事实印证过」。这一差别也解释了为什么三层比十行技能更有说服力：可核验的部分才有信息量。
- **真实使用**：原文件的三层清单（知识图谱 / RAG / LLM 微调；多模型编排 / Agent 设计；Skills Graph / AI 治理）与主文件 §1.4 的能力入册年表一致（2020 ML → 2022 Prompt/RAG → 2023 Agent → 2024–2025 Skills Graph）。本书不评价任何个人的具体技能等级，也不给出「多少人达到某层」这类数字。

#### 3.2.5 IDP（个人发展计划）五元组

- **被什么约束逼出来**：从 P6 到 P7 的能力跃迁跨季度，而人与人的记忆不跨季度。没有书面结构，差距与承诺会在一到两个季度内蒸发【经验】。
- **结构**：

```sql
-- IDP：目标职级与现状都被拆到「维度」，否则差距无法被验证
CREATE TABLE idp (
  person     TEXT,
  target     TEXT,   -- 目标职级 + 期限（例：P7，12 个月）
  current    TEXT,   -- 现状：各维自评与经理评估（例：技术深度 3 / 协作 2）
  gap        TEXT,   -- 必须写维度差：技术深度 3→4、协作 2→3
  action     TEXT,   -- 承接的项目 / 任务名（没有项目承接的行动 = 愿望）
  resource   TEXT,   -- 导师 / 课程 / 项目机会 / 预算
  review_due DATE,
  PRIMARY KEY (person, target)
);
```

- **为什么这样设计有效**：因为「差 1 分」只有被拆到维度并要求写明承接项目，才能变成可执行的计划；把 `gap` 写成维度差（而不是「我需要成长」），使进度可被第三方检查——两到三次 Review 后【经验】要么有产出，要么需要改的是目标而不是努力。
- **代价**：每季度一次结构化校准的维护责任。IDP 的成本从来不在填写，而在**必须有人按时 Review**；发出去就不管的 IDP 比不发更伤信任。
- **失效点**：当组织没有与之对齐的真实项目机会时，`resource` 一列长期为空，IDP 退化为课程清单——因为缺口是「没做过」，而行动项是「上一门课」，两者机制不同（无即时反馈的练习不算刻意练习，见 [§07 辅导与成长 §3.2.3 IDP](../07-mentorship/07-mentorship-section-3-sec3.md)）。
- **真实使用**：【经验】多数科技公司的 IDP 形态是「季度目标 + 半年度校准」，本书不给出任何覆盖率数字。可自行核验的判定方法：抽 3 份 IDP，看 `action` 里有没有项目名。

#### 3.2.6 继任深度台账（Ready-Now / Ready-Later）

- **被什么约束逼出来**：关键岗位的空缺不会等培养完成；「有没有人接得上」必须从印象变成可检查的数字（主文件 §2.2）。
- **结构**：

```text
继任深度台账（主键是「角色 × 人」，不是「角色」）
role_key        person   readiness     evidence              next_gap
--------------  -------  ------------  --------------------  ----------------
arch.payments   p_1032   Ready-Now     主导过支付域重构      跨 BU 协调经历
arch.payments   p_1188   Ready-Later   负责过子域            跨域项目 + 带人
dwh.modeling    p_1032   Ready-Later   设计过核心事实表      带一次跨团队评审
健康线：每个关键角色 ≥ 2 Ready-Now + ≥ 2 Ready-Later（主文件 §2.2）
红灯算法：count(readiness='Ready-Now') < 2 → 该角色列红灯
```

- **为什么这样设计有效**：因为储备的度量单位是「人」而不是「岗位」，所以同一个人出现在多行不是重复登记，而是**风险信号**——它意味着多个关键岗位依赖同一个人（见下方推算）；因为每条记录都要求写 `evidence` 与 `next_gap`，所以「谁是 Ready-Now」不能靠印象，只能靠已发生的事实。
- **代价**：持续维护成本（一个人动了，多行都要改），且必须与绩效、能力评估共用同一份数据，否则会出现「刚做完盘点，Ready-Now 当月离职」这类本可预警的意外（§7.6）。
- **失效点**：当台账按角色记而不按人记时，「同一个人被多个角色同时依赖」这条风险不可见——每一行看起来都达标，最坏情况下却同时空缺（见下方推算）。
- **与相邻模式的边界**：继任台账与人才盘点的分工是**出口不同**——台账回答「岗位有没有人接得住」（面向岗位），盘点回答「资源投给谁」（面向人）；两者共用数据但结论不可互换，用盘点结论直接填台账，会把「潜力高」错当成「现在就能接」。
- **真实使用**：健康标准取自主文件 §2.2（每个关键角色 2 Ready-Now + 2 Ready-Later）；本书把它当作检查线而非行业标准【经验】。

**【推算】为什么台账必须按「角色 × 人」记账**：健康线要求每个关键角色 ≥ 2 Ready-Now + ≥ 2 Ready-Later，即每个关键角色需要 **4** 个后备名额。设关键角色占岗位数的 **20%**（【经验】，取自主文件 §2.1「20% 关键岗位贡献 80% 产出」）→ 100 人组织约有 **20 个关键角色**，需要 20 × 4 = **80 个后备名额**。同一名后备常同时是 2–3 个角色的候选（【经验】）→ 实际所需人头 ≈ 80 ÷ 2.5 = **32 人**，即约 1/3 的人要在多个角色的名单上重复出现。**结论**：按角色逐行看，每个角色都达标；按人去重看，才会发现撑住关键岗位的其实是同几个人。

#### 3.2.7 盘点与退出结构（9 宫格 / Keeper Test / 离职面谈）

- **被什么约束逼出来**：资源（晋升名额、关键项目、薪资带宽）有限，必须有一个把「谁值得投入」变成可讨论结构的机制；同时退出也要有结构，否则离职原因永远不可见。
- **结构**：

```text
盘点矩阵与退出分类（同一份数据的两个出口）
          潜力低        潜力中        潜力高
  绩效高   稳定贡献      核心骨干     ★ 重点投入（晋级 / 关键项目）
  绩效中   需明确期望     主体力量      缺哪一维 → 回到 BAR
  绩效低   改进计划      改进计划      ← 先查环境因素，不直接归因于潜力

  退出分类：Regrettable（想留没留住，含主动离开的关键人才）
            Non-Regrettable（绩效或文化不匹配）
  Keeper Test：此人明天辞职，我会尽力挽留吗？「会」= Keeper
  反规则：用潜力替代当前岗位胜任度作依据 → 潜力是预测，不能替代已完成的事实
```

- **为什么这样设计有效**：因为潜力是预测、绩效是事实，两轴分开后讨论才能落到「缺哪一维、缺什么证据」；因为 Regrettable / Non-Regrettable 的分类把离职变成可分析的信号（哪一类在增加），而不是一次人事流程——它和继任台账共用同一份等级与能力数据。
- **代价**：标签风险（被贴上「低潜力」的人会自我实现，因此结论只能用于资源分配，不能用于定性），以及每年重做的成本——潜力会随岗位与环境变化，一次性的盘点结论必然固化印象。
- **失效点**：当盘点只用潜力、不用当前岗位胜任度作依据时，被提升的人在新岗位上缺少已验证的证据，晋升失败率上升，且一次晋升名额被消耗——而名额是有限资源，消耗后当年的其他候选人都被影响。
- **与相邻模式的边界**：盘点与绩效管理的分工是**时间方向不同**——绩效面向已发生的周期结果，盘点面向未来的资源分配；把两者合并成一次会议，等于用过去的评价替未来的项目分配做决定，且会让当事人无法区分「我被批评」与「我被安排去哪」。
- **真实使用**：Keeper Test 由 Reed Hastings 与 Erin Meyer 在《No Rules Rules》（2020）中记述【公开】（本节未给出页码，读者可自行核验）。9 宫格在业界被广泛使用，本书不追溯单一出处【经验】。离职面谈的五类问题（真实原因 / 组织反馈 / 挽留空间 / 去向 / 后续联系）见主文件 §2.3。

#### 3.2.8 Skills Graph（动态能力图）

- **被什么约束逼出来**：核心技能清单的修订周期已压到 1–2 年，而静态 JD 的校准节奏是多年一次——按年校准的清单会在中途就与现实脱节（§7.3.3）。
- **结构**：

```text
能力图的结构：节点 + 边（边才是「培养路径」的载体）
  (节点) 能力项：知识图谱 / RAG / LLM 微调 / 多模型编排 / Agent 设计 / AI 治理 …
  (边 A) 前置依赖：RAG ← 向量检索基础          → 回答「先补哪个」（IDP 的行动项顺序）
  (边 B) 可迁移  ：LLM 微调 ≈ 多模型编排（部分）  → 回答「哪段经历能折算过来」
  (边 C) 岗位要求：P7 需要哪些节点达到哪一档      → 回答「差在哪一节点」
  (字段) 每个节点：维护人 + 最后更新时间        → 缺这两项，图会在一到两个季度内失真【经验】
  AI 的落点：出草稿（差距汇总 / 路径建议），判断仍由评委做
```

- **为什么这样设计有效**：因为「要长到目标节点、先补哪个前置节点」这个答案只能由边给出，静态 JD 在结构上给不出它——IDP 里「差距 → 行动项」这一步依赖的就是边；因为图可计算，所以「材料里哪一维证据不足」这类问题可以被自动汇总，这是 AI 辅助评估的真实落点。
- **代价**：图的维护是**永久成本**（必须指定一名维护人），且图与通道标准要互相对齐，否则会出现「图说你够格、通道说你不合适」的尴尬（§7.6）。
- **失效点**：当图上没有维护人时，它的过期是**主动误导**——JD 过期只是少一条要求，图上错误的边会给出错误的学习建议，把培养资源导向过时方向（§7.3.3）。
- **与相邻模式的边界**：图与静态 JD 的选择不是「先进 / 落后」，而是**两条成本的比较**——JD 的成本在每次重写（一次性、可预期），图的成本在持续维护（永久、需要指定人）；当技能清单的失效周期短于「重写一次的成本 ÷ 维护一个季度的成本」时，图才开始划算。
- **真实使用**：「节点 + 关系」的能力模型在公开领域有可核验的先例：欧盟 ESCO 分类（v1 发布于 2017 年）与美国劳工部 O*NET 数据库（按年度发布数据库版本，具体版本号可在其官网自行核验），二者差别恰在维护方式——由机构按年批量更新，而不是随项目持续更新【公开】（见 §7.3.3）。本书不声称任何具体厂商产品的效果。

**最常被误选的一对是「双通道 ↔ Skills Graph」**：把「上了能力图」当成「开了第二条通道」。后果是图能算出「谁更接近下一级」，却算不出「组织承认几种成功范式」——于是候选人被告知「证据不足」，而真正的问题是组织只承认一种成功范式，无论补多少证据都无路可走。识别的办法是问一句：**如果这个人技术极强但公开表达一般、也不带人，他在这套体系里能不能到最高等级？**答「不能」，那么通道问题没有被图解决。

诊断误选有一个两步法：**① 问「这个人缺的是承认、证据、还是能力」；② 查上表对应行，看当前实际在用的是不是同一行的模式。**两步之中最常答错的是第 ① 步——「他答辩过不了」常被当成能力问题，实际往往是标准未书写（缺证据形态）或通道容量不足（缺承认），这两类都与本人能力无关。

### 3.4 组合模式：真实系统不会只用一种

1. **双通道 + BAR 锚点 + 答辩举证**——**构成**：通道定义「有几条路」，锚点定义「每级要什么证据」，答辩定义「谁来评、按什么流程评」。**职责边界**：三者引用同一份标准，只是用法不同——通道用它分配激励，锚点用它做 IDP 的目标，答辩用它做判断。**运维代价**：标准一旦改动，三处同时受影响，因此必须有唯一的 Owner 与版本意识（否则会出现培训材料与新标准不一致）。**适合规模**：20–100 人、技术深度是核心竞争力的组织（20–100 人为【经验】场景带，非推导阈值，取自 §7.6 选型矩阵与 §7.8 小结）。
2. **IDP + 导师制 + 季度校准**——**构成**：IDP 是计划（书面、可跟踪），导师是过程（对话、示范、反馈），季度校准是节奏。**职责边界**：只发 IDP 不配导师，计划会在一到两个季度内失效【经验】；只配导师不写 IDP，反馈无法累积成证据。**运维代价**：导师时间是真实成本，必须计入其工作量而不是「额外义务」（§7.6）。**适合规模**：任何有 P5 → P7 培养需求的团队。
3. **继任深度 + 盘点 + 离职分析**——**构成**：继任台账回答「岗位有没有人接」，盘点回答「资源投给谁」，离职分析回答「人为什么走」。**职责边界**：三者共用同一份等级与能力数据，只是出口不同。**运维代价**：数据不打通就会出现「刚做完继任盘点的那个岗位，Ready-Now 人选当月离职」——这类意外本可由离职信号预警。**适合规模**：关键岗位 ≥ 5 个，或已经出现过关键人才主动离职的组织【经验：阈值为本书经验判断，非统计数据】。

**三个组合共有的前提是一份**「写得下来、两个人写得一致」**的等级标准**：通道、材料、图、继任台账都只是这份标准的不同用法，缺它则全部退回凭印象（对应 §7 的第 2、3 条判据）。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| BAR 锚点写成形容词 | 标准里出现「精通 / 熟悉 / 了解」 | 无法举证 → 评估退回印象，「差 1 分」无法解释 | 抄模板最快，写锚点成本最高 | 每格写成可观测行为 + 证据形态（否则该行无效） |
| 三层陈述全是名词 | 材料写「精通 X、熟悉 Y」，追问「哪项你定过标准」答不出 | 深度不可验证 → 评委按表达给分 | 名词清单最好写，也最像「懂技术」 | 每层加证据形态；认为验不过就降一层说 |
| IDP 只发不跟 | `action` 里没有项目名、`review_due` 已过期 | 行动项与项目脱钩 → 缺口仍在，但账面显示「已规划」 | 发计划是「已完成」的动作，Review 不是 | 季度校准，并把 action 与真实项目分配挂钩 |
| 以晋升替代激励 | 所有正反馈都要靠「准备晋升」表达 | 职级通胀，信号价值归零（§7.7） | 晋升是唯一的「官方」认可形式 | 把认可 / 机会 / 薪酬从晋升里拆出来 |
| 继任台账按角色不按人 | 每个角色都写着 2 个 Ready-Now | 候选人重叠不可见 → 最坏情况多个岗位同时空缺 | 按岗位登记符合「岗位继承」的直觉 | 主键改为「角色 × 人」，并看人的被依赖度 |
| 盘点结论一次性 | 上次盘点在两年前，人员已换过一轮 | 标签固化 → 潜力判断退化为印象 | 盘点像年度大作业，做完即归档 | 每年重做；结论只用于资源分配，不用于定性 |
| 答辩只讲结果不讲取舍 | 材料只有指标，没有备选方案与放弃项 | 只能证明「做了事」，不能证明「够下一级」 | 结果比取舍好写 | 每个关键项目必答四问（影响 / 复杂度 / 独立性 / 对他人的影响） |

**最危险的两条**：**「BAR 锚点写成形容词」**与**「继任台账按角色不按人」**。前者的暴露方式是**答辩争议**：当两位候选人的材料都不足、讨论最后落到「感觉」上时，问题不在评委，而在标准里那句形容词无法被任何人复核；这类争议会反复出现，且每一次都在消耗制度的信用。后者的暴露方式是**同月离职**：一份看起来每个岗位都达标的台账，在某次组织变动中同时失去几个候选人时才会暴露——那时才发现「每个岗位 2 个后备」和「有 2 个人可接」是两件不同的事（见 3.2.6 的推算）。

第三条值得单列：**「三层陈述全是名词」的风险在于它把举证责任留给了评委**。候选人列出五个技术名词之后，评委必须自己判断哪一个真正够深——而在一次答辩的 30 分钟里（时长见主文件 §2.3）无法逐一核验【经验】。于是分数会稳定地偏向表达更流畅的人，这不是偏见，是**证据缺位时的必然结果**。

**这些反模式的共同成因**：写结构（锚点、证据形态、台账主键）是**可选的、缓慢的、不产生当期产出的工作**，而做评审、发 IDP、开通道都是当期可见的动作。因此它们被系统性地跳过——直到某次晋升争议或某次离职潮把成本显性化，而此时补结构的成本已经包含了一次已经发生的事故。

**一个共通的识别信号**：如果连续两次评审的争议都发生在「某个人到底够不够」这个问题上，而不是「材料里哪一维证据不足」上，那么问题几乎一定在结构侧（锚点没写下来，或台账主键错了），不在候选人侧。**把争论对象从「人」推到「证据」上，是这套体系唯一真正的改造目标**——做不到这一点，加多少流程都会重新滑回印象判断。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| < 10 人 → 20–100 人（< 10 人端为【经验】阈值，依据见 §7.5；20–100 人端是 §7.6/§7.8 的场景带，非推导阈值） | 单一通道 + 口头对齐 | 高职级 IC 的最优策略退化为转管理或离职，且口头标准无法跨团队解释 | 双通道（待遇与决策权一起给）+ 写下的锚点 | 数季度，且需要至少一次真实的高等级 IC 晋升来证明它是真的【经验】 |
| 技能清单年更 → 1–2 年一换 | 静态 JD + 年度校准 | 上一版清单里已有一半要求不在项目中使用 | Skills Graph + 指定维护人 | 图的维护是永久成本，一到两个季度内若无人更新则大概率已失真【经验】 |
| 关键角色只剩 1 个可继任者 | 外部招聘补缺 | 空缺期业务停摆，组织记忆随外招人员流失 | 继任台账 + 内部培养 | 一个项目周期才能产出可举证的成果（与「6 个月」阈值同源） |
| 单团队 → 跨 BU | 部门内标准 | 标准不统一则人才无法跨团队流动，晋升结论互不可比 | 集团统一标准 + 跨级评委池 | 评委池需 ≥ 3 名跨级且无利益关系的人（【经验】；按「具备跨级评议资格者约占 1:20–50」折算，一般要到 60–150 人规模才凑得齐，【推算】，两项依据见 §7.5） |
| 稳态 → 技能换代期 | 年度校准 | 能力要求连续入册（2020 ML → 2022 Prompt/RAG → 2023 Agent → 2024–2025 Skills Graph），年更跟不上 | 半年校准 + 图（有维护人）+ 更强的影响分析 | 校准频率翻倍意味着人力翻倍，必须有人为此付时间 |
| 反向通道从未发生 | 纸面双通道 | 回退后等级或薪资被下调，反向路径实际不存在 | 先修回退规则，再谈通道 | 需要至少一次真实的反向转岗案例来证明（判定方法见 §7.3.4） |

**跃迁的判据不是人数，而是「约束是否已经变了」**：人数只是约束变化的代理指标。真正触发切换的是三条可观测信号——① 有没有高职级 IC 因「发展空间」离开；② 同一份能力要求在多少项目里还在被使用；③ 关键岗位的 Ready-Now 计数是否掉到 1。三条中任意一条为真，就说明当前模式已经到界，而不是「再忍一忍就会好」。

**迁移有两条不可逆项**，都要在切换前想清楚：**职级含义的膨胀**（一旦为了留人而放宽，恢复它需要「不晋升」的动作，组织代价远高于当初放宽的成本）与**图的失真**（无人维护的图会主动给出错误路径）。因此迁移方向应当是**先收紧标准、再加通道**，反过来做会把两件事的难度叠加（详见 §7.7）。

### 3.7 自检清单

1. 能力标准的锚点列里，是否出现「精通 / 熟悉 / 了解」这类自陈词？出现即该格不可复核。
2. 让两名不同团队的管理者各自写下「P7 与 P8 的差别」，两份答案是否可比？不可比＝标准还没写下来。
3. 最近 3 次晋升，评委是否同时满足「≥ +2 级视角」与「不评议自己的直接下属」两个条件？
4. 有人说自己「精通 RAG」，他能不能指出一项由他定义、且被他人引用的标准？
5. 「熟悉」层的每一项，能否说出一次具体取舍（选了什么、放弃了什么、为什么）？
6. 「关注」层的判断，是否被后续事实印证过（提前判断过某方案在某规模失效）？
7. 每条 IDP 的 `action` 里有没有承接的项目名？`review_due` 是否在过去一个季度内？
8. 继任台账的主键是「角色」还是「角色 × 人」？有没有人被 ≥ 3 个关键角色同时列为后备？
9. 每个关键角色的 Ready-Now 计数是否 ≥ 2？计数为 0 或 1 的角色有几个？
10. 最近一次人才盘点距今多久？超过 12 个月，标签已开始固化。
11. 离职数据里能否回答「今年走的人里，有几类是我们想留的」（Regrettable vs Non-Regrettable）？
12. 能力图上，上周谁改过它？没有人改过，它正在失真（且失真方式是主动误导）。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 只有一种成功范式、规模 ≥ 20 人 | 双通道（待遇与决策权一起给） | 单一激励函数下，最强 IC 的理性选择是离开技术岗 |
| 标准写不下来 | 先补标准，其余全部延后 | 材料、图、答辩、继任台账都只是这份标准的不同用法 |
| 技能清单 1–2 年失效一次 | Skills Graph + 指定维护人 | 静态 JD 的校准节奏跟不上失效速度，但无人维护的图更快失真 |
| 关键岗位只有 1 个可继任者 | 继任台账（按角色 × 人记账）+ 内部培养 | 「有没有人接得上」是硬约束，通道与图都解决不了没人可接 |
| 业务缺口 < 6 个月（【经验】，阈值依据见 §7.5） | 外部招聘 + 同步补继任深度 | 培养需要完整项目周期才能产出可举证成果 |
| 答辩经常落到「感觉」上 | 补锚点与证据形态 | 证据缺位时，评分必然偏向表达流畅的人 |
| 材料里全是技术名词 | 三层陈述加证据形态（3.2.4） | 名词可抄，证据形态不可抄——它指向第三方事实 |
| 目标职级停在纸面上 | IDP 的 `gap` 写成维度差 + 项目承接 | 差距不落到维度与项目，就无法被验证，也无法被校准 |
| 想识别「该留的人」 | 盘点 + Keeper Test + 离职分类 | 资源有限，需要一个可讨论的结构来决定投给谁 |

> 本节小结：决定模式选择的**唯一那条约束是「组织承认几种成功范式」**——它决定最强技术人才能不能留下，其余差异（举证方式、图的动态性、盘点与退出结构）都是在这条确定之后的优化项（详见 §7.8）。原文件那三行（精通 / 熟悉 / 关注）在这套结构里的位置是**举证结构的一个片段**：它解决「怎么说」，而说得成不成立，取决于是否有人先把标准写下来、把证据形态定义清楚。
