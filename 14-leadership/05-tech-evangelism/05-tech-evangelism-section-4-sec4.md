## 4. 工程实现

> §3 解决「选哪种渠道组合」，本节解决「选定之后怎么把它跑起来」：一次分享的完整流程、一条跨渠道的素材搬运链、一份发布前的可验证性自检。目标只有一个——**每次投入都要留下资产，而不是留下一个事件**。

### 4.1 落地步骤

**Step 1：建立内部分享机制（2-4 周搭好，之后长期跑）**

1. **频率与时长**：每两周 1 次，30-45 分钟 + 15 分钟 Q&A；每月留一档讲「一篇论文或一份事故复盘」【经验】。
2. **轮值**：每人每季度至少 1 次；新人从「讲自己刚做完的一个任务」起步——这类选题素材成本最低。
3. **选题规则**：优先讲「自己做过的」和「团队正在踩的」。这两类自带证据（参数、数据、代码），对方的验证成本最低。
4. **录播 + 归档**：一次分享必须留下两样东西——可检索的文档（团队 wiki）与录屏。只有现场的分享属于 §3.5 说的「只放大产量、不放大可验证性」。
5. **反馈闭环**：会后发一张三问表（哪一段可用 / 哪一段太浅 / 下次想听什么），并在下一次分享开场回收结论。

**Step 2：建立跨渠道复用链（持续）**

一次素材多渠道分发，按「搬运成本从低到高」排序：

```text
内部分享 → 长文 → 演讲提案（CFP） → 视频 / 播客 → 开源 README
   ↓          ↓            ↓               ↓            ↓
 团队 wiki   站内可检索    主办方议程      带文字稿      可 clone
```

- 硬规矩：上一环的产物要能直接喂给下一环。分享稿里没有可公开的图表与口径，就写不出长文。
- 反向同样成立：先写长文再讲，讲稿只是长文的删减版（组合模式见 §3.4）。

**Step 3：一次 Conference 演讲（2-4 周 / 次）**

1. **选题三条件同时满足**：听众关心、你能讲清、你有独家素材。缺一条就不要投。
2. **投稿一页纸**：一句话结论 + 三个「可以带走」的清单 + 你的证据来源。没有证据来源的选题，评审第一个砍。
3. **彩排至少 3 次**，其中 1 次控时到秒；把所有「讲不清来源」的数字换成区间或删掉。
4. **会后 72 小时内**：讲稿 → 长文 → 团队转训。一次投入在三处落地，这是布道 ROI 的主要来源。

**Step 4：开源项目运营（立项后长期）**

1. **先有「别人 5 分钟能跑起来」的 README**，再谈功能。
2. **响应目标**：Issue 24 小时内回应（哪怕只是确认收到），PR 7 天内给出结论【经验】。
3. **版本纪律**：SemVer + Release Notes；破坏性变更必须写迁移路径。
4. **把内部高频问题回写进文档**——文档的更新频率是项目还活着的最强信号。

**Step 5：AI 增强（按需）**

1. LLM 用于提纲、初稿、转写与翻译，放大的是**表述产能**；证据产能（数据、口径、代码能不能跑）仍要靠人。
2. 未经核验的数字不进对外材料；核验人要对结论负责。
3. 归档时标注哪些段落由 AI 生成、由谁复核——后续被追问时能追溯。

### 4.2 关键技术点

**1. 分享提纲骨架（30-45 分钟）**

```markdown
# 让业务方主动接入数据平台 —— 内部分享提纲

## 0. 结论先行（2 分钟）
- 一句话结论：平台接入的瓶颈不在能力，在业务方的验证成本
- 适用边界：适合已经有可用能力的团队；平台还不稳定时不要先布道

## 1. 业务背景与约束（5 分钟）
- 业务问题、量级、硬约束（合规、时延、成本）

## 2. 方案与关键决策（15 分钟）
- 决策 1：以哪类受众为第一目标（业务分析师 / 应用研发）
  - 备选：面向所有人 / 面向单一角色
  - 取舍依据：可验证性 —— 单一角色的验证路径能被一个人走完
- 决策 2：渠道先做哪个（可检索长文 / 现场分享）
- 每个决策都要能回答「当时还有哪条路、为什么没走」

## 3. 踩坑与代价（10 分钟）
- 坑 1：现象 → 根因 → 处置 → 现在怎么防
- 明确说出成本：人时、钱、延期，不留悬念

## 4. 可带走的清单（5 分钟）+ Q&A
- 3 条今天就能用上的做法
```

**2. 发布前可验证性自检（4 问）**

1. 每个数字有没有来源与年份？没有就改成区间并写出推导链。
2. 结论背后的样本是什么——几个项目、多大量级、多长时间？
3. 听众能不能在 5 分钟内复现你的一句话结论？复现成本决定采纳速度。
4. 这次留下的东西，明年还能被检索到吗？

### 4.3 工具链与平台

按「要解决的问题」选，而不是按品牌选：

| 要解决的问题 | 可用工具 | 约束 |
| --- | --- | --- |
| 内部分享与归档 | Confluence / Notion / 飞书文档 + 录屏（Loom、飞书妙记） | 录屏不能替代文档：被检索到的是文本，不是视频 |
| 长文发布 | 公司技术博客、知乎、掘金、InfoQ | 只出现在推送型渠道、站内搜不到的长文，半年后基本无人再读 |
| 演讲投稿与传播 | QCon、ArchSummit、DataFun 等会议 CFP | 先看主办方往届议程：听众构成比主题更能决定效果 |
| 视频 / 播客 | B 站、YouTube、小宇宙 | 音频必须配文字稿，否则不可检索 |
| 开源 | GitHub / Gitee | 门槛是 README 与 Issue 响应，不是功能多少 |
| AI 辅助 | 通用 LLM（提纲 / 初稿 / 转写 / 翻译）、AI PPT（Gamma、Tome） | 只放大表述产能；证据部分需人工复核并署名 |

### 4.4 代码 / 示例

**示例 1：内部分享 Runbook**

```markdown
# 内部分享 Runbook（以「每双周一次」为例）

## 会前 48 小时
- [ ] 把主题与一句话结论发到团队频道（让人自己决定来不来）
- [ ] 提纲发到频道，收 3 个真实问题（替代现场冷场）
- [ ] 测试录屏与投屏；确认文档模板已建在 wiki 的目标目录下

## 会中
- [ ] 结论先行，2 分钟内说完
- [ ] 每个决策点停 30 秒收问题
- [ ] 记录现场提出的反例——那是下一次分享的选题

## 会后 24 小时
- [ ] 文档归档进 wiki（标题含可检索的关键词），录屏上传并附链接
- [ ] 回收三问反馈表
- [ ] 把「可带走的清单」单独发一条消息（多数人不在现场）
```

**示例 2：开源项目 README 骨架**

```markdown
# 项目名 —— 一句话说明它解决什么问题

## 它是什么 / 不是什么
## 5 分钟跑起来（前置依赖 + 3 条命令 + 期望输出）
## 它适合谁（场景 / 量级 / 不适用场景）
## 核心概念（不超过 3 个）
## 已知限制
## 如何参与（Issue 模板 / PR 约定 / 响应时间）
## License
```

---

> 本节小结：技术布道的工程化只有两件事——**把素材的搬运成本降到最低**，**把每一次产出的可验证性留到最后**（归档、录播、可 clone 的代码）。渠道会过时，这两条不会。
