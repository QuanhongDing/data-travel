## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

本章 §3 在拆分前的章节正文里是按「模式 1–6 + 核心思想 + 代表 + 优点 + 缺点」逐条列的（HEAD 处的 §3 只剩 7 行占位），其中缺点写的是「需要长期投入」「运营成本高」「需要镜头感」。这些不是缺点，是**约束的读数**——它们真正在说的是「这个模式的成本压在哪一项上」。模式选择的真实约束也从来不是「你想要多大影响力」，而是**六条可测的约束**：分发机制、证据密度、产能、分工与技能、反馈带宽、内容时效。下面逐条说这六条，完整取值与它们各自推翻的直觉见本节末的约束表。

第一条约束是分发机制。§7.3.1 把渠道分成三条收益曲线：检索型是**累计分布**（三年后仍可能被搜到）、推送型随**名单规模线性**、现场型是**脉冲**（散场即归零）。这条约束直接推翻了「哪个渠道效果最好」这个问题——三种曲线的形状不可比，同一个「触达人数」在三种曲线上代表完全不同的东西。金字塔模型之所以有效，不是因为「三种都做」，而是因为它规定了**单向的搬运关系**：底层沉淀一次，向中层与上层再分发。方向不可逆，是因为成本不对称（§7.4：向下压缩约 3–5 人时、向上补齐证据约 6–12 人时，均【推算】）。

第二条约束是证据密度。§7.3.2 的结论是：布道的货币不是观点，而是可复现的证据——采纳发生在「对方的试错成本被压低」的那一刻，而不是在你讲得最好的那一刻。这条约束把渠道按「能承载什么证据」重新排序：可 clone 的仓库 > 带参数与基线的长文 > 演示视频 > 只有结论的演讲。所以「开源项目模式」与「Conference 演讲模式」不是两个并列的可选项，它们在证据链上处于不同位置，各自改变的是不同的东西（一个是「敢在生产用」，一个是「优先级被提高」）。

第三条约束是产能。按 §7.4 的推算，一次 25 分钟演讲是 28–48 人时，一篇深度长文是 7–14 人时（均【推算】§7.4）。这条约束决定了布道的默认形态是**组合**而不是单选：几乎没有团队能靠 Conference 单独支撑布道，因为它是产能单价最高的渠道，而回报是脉冲。

第四条约束是分工与技能：布道者是否岗位化、有没有对外的 DevRel 职责，直接决定这件事是「闲时做」还是「排进排期」——而「闲时做」的产能实际上等于零。同一维度还决定哪些模式能落成长期结构：写作、表达与社区响应是三种不同的技能，缺哪一项，对应那一族渠道就只能做成一次性活动（族划分见 §7.2）。

第五条约束是反馈带宽，也是六条里最容易被忽略的一条。§7.3.3 给出三种不可互换的信任：现场渠道的可追问反馈建立的是**判断信任**，开源的异步反馈建立的是**能力信任**，长文的低反馈只建立**观点可见性**。这条约束的作用是排除法——它告诉你哪种渠道**无法**完成哪个任务：一场精彩的演讲不会让人敢在生产环境用你的库，一个 star 很多的库也不会让人相信你对行业趋势的判断。因此选模式时正确的第一个问题是「我缺的是哪一种信任」，而不是「哪个渠道效果最好」；答错这个问题，后面的产能与节奏安排全都白费。

第六条约束是内容的失效速度。同一条工程结论在不同领域的半衰期差得很远：系统设计的取舍（为什么分片、为什么不走 JOIN）可以稳定三五年；具体版本、价格、额度、模型能力对比通常在几个月内就过期（【经验】）。这条约束决定内容该怎么写——**写方法与约束，不写版本号**：版本号会让三个月前的文章变成错误信息，而约束与机制不会。它也决定哪些内容值得做成沉淀资产：半衰期长的值得投入证据成本写成可被反复引用的长文，半衰期短的只做一次性说明即可。

约束不是一次定死的：业务从内部走向对外、从单一产品走向平台、从一个人讲走向一个团队讲，每一条都会改变上面的取值。因此**布道的模式选择不是一次决策，而是一次随约束变化的重新推导**——这也是本章把它写成「模式手册」而不是「推荐清单」的原因：清单会过期，推导不会。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| ① 分发机制（内容是可被检索的沉淀物还是一次性事件；受众是搜到你、被推给你，还是被请到现场） | 收益曲线的形状：累计 / 线性 / 脉冲；冷启动方式；决定要不要录播与文字稿 | 「做完一场演讲就算完成布道」——散场即归零，除非留了沉淀物；「内容好自然有人看」——检索型要先被索引，推送型要先有名单 |
| ② 证据密度（内容能不能承载可复现的证据） | 对方的验证成本有多高；内容只能改印象还是能改决策 | 「讲得清楚就会被采纳」——采纳发生在对方试错成本被压低的那一刻，不在你讲得最好的那一刻（§7.3.2） |
| ③ 产能（每周可投入人时） | 渠道组合的产能上限；默认形态是「组合」还是单选 | 「先做开源，再做博客」——开源启动成本约 300–500 人时（【推算】§7.4），方向反了 |
| ④ 分工与技能（写作 / 表达 / 社区响应，是否岗位化） | 这件事是「闲时做」还是「排进排期」；哪些模式能落成结构 | 「找个会讲的人就行」——社区响应与代码一样是长期承诺 |
| ⑤ 反馈带宽（反馈是一次性的，还是可追问的） | 能建立哪一种信任（判断 / 能力 / 观点可见性）；哪些渠道无法完成哪些任务 | 「一场精彩的演讲就够了」——现场建立不起「敢在生产用」的能力信任（§7.3.3） |
| ⑥ 内容时效（技术内容多久失效） | 内容该写方法还是写版本号 | 「把参数与版本号写全」——版本号三个月后就是错的，方法不会 |

约束之间还有一条推不动的关系：证据密度决定受众愿不愿意承担采纳风险，分发机制决定这份证据能不能被持续地送到人面前，而两者都由产能换算而来。因此改善布道最有效的动作通常不是「换一个更好的渠道」，而是**把已有内容向成本更低的方向搬运一次**（把长文压成提纲，把演讲补成逐字稿）——这一步不需要新的选题能力，只需要一个搬运习惯，也几乎是唯一能在不增加人时的前提下提高产出的动作。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 金字塔内容模式（Content Pyramid）

- **被什么约束逼出来**：任何单一渠道都缺一块——只做沉淀型冷启动极慢，只做现场型散场归零；而团队总产能固定，所以必须让同一份素材被多次兑换。
- **结构**：

```text
金字塔内容模式：一份素材，三个高度
        顶层  开源项目 / 长期资产        低频、高价值、可被 clone 验证
       ─────
        中层  演讲 / 视频 / Podcast      中频、脉冲型，靠现场与推荐分发
       ─────
        底层  长文 / 博客 / 文档          高频、累计型，靠检索被反复找到
   ────────────────────────────────────────────
   关键不是"三层都做"，而是搬运方向的单向性：
     底层 → 中层：压缩与取舍，约 3–5 人时（【推算】§7.4）
     中层 → 底层：补取数、复现与图表，约 6–12 人时（【推算】§7.4）
   方向相反时成本相差数倍，所以"先写后讲"几乎总是对的
```

- **为什么这样设计有效**：因为同一份素材在向下的边际成本远低于向上（压缩 3–5 人时 vs 补证据 6–12 人时，均【推算】§7.4），所以「先有沉淀物、再向现场与订阅再分发」这一顺序让每次投入被摊薄（§7.4：同一素材被 3 条渠道复用时摊薄到约 2.3–4.7 人时/次，【推算】）；又因为底层是检索型、收益是累计分布，它不需要当期反馈，因而可以不依赖「等一个讲台」而持续产出。
- **代价**：底层产出与可见回报之间有数周到数月的时滞，团队只能靠纪律维持，而不是靠及时的正反馈；三层需要三种不同的表达训练（写作 / 演讲 / 演示），一个人很难都强，因此通常需要一个最小分工，而分工又要求这件事被排进排期——这是「金字塔」在组织里真正的落地门槛，不是内容能力。
- **失效点**：当团队只做底层（长文不停、却从没被人当面追问）时，「先沉淀再分发」会反转成**没有被压力测试过的观点**——因为现场追问是唯一能暴露判断裂缝的反馈通道，缺了它，写下的结论往往在半年后被自己推翻；反过来只做中层时，28–48 人时（【推算】§7.4）的投入只兑换一次脉冲，而且中层内容会因为缺少底层的证据支撑而逐年变薄，最后只剩结论没有依据。
- **真实使用**：Netflix Tech Blog 与 Uber Engineering Blog 都长期维持「长文为底 + 对外演讲 + 开源项目」的三层结构（【经验】——站点存档与其持续发布的事实可自行比对）。渠道结构本身也在变，可核验的痕迹如 O'Reilly 于 2019 年停办 OSCON（【公开】O'Reilly 官方公告, 2019，官网存档可核验）——但一家厂商退出会议业务，动因可能是自身业务重心调整，不足以推出「现场渠道的行业集中度在下降」：同期 KubeCon / QCon / ArchSummit 等会议仍在持续举办（【经验】，可自行比对会议站点存档）。因此判断渠道结构是否变化，看的是你自己内容来源的构成（检索 / 订阅 / 现场各占多少），而不是某一家厂商的动作。
- **怎么自检**：看最近一次演讲的素材从哪来——若答案是「为一篇已有长文做的压缩」，方向是对的；若是「单独为演讲准备的」，说明搬运方向反了，这一次的产能没有沉淀。
- **常见误用**：把「三层都做」理解成「三条生产线并行」——三层是同一份素材的三个高度，不是三个互相独立的选题；一旦变成三条独立生产线，产能立刻不够，最先被砍的就是底层。

#### 3.2.2 Conference 演讲模式

- **被什么约束逼出来**：现场型渠道的听众是主办方聚起来的，讲者带不走听众；因此一次演讲必须被设计成「一句可被二手转述的断言 + 一套经得住追问的证据」。
- **结构**：

```text
Conference 演讲的结构：把一次准备变成可被转述的断言
  （时长按 §7.4 成本推算所标定的 25 分钟档：2+4+14+3+2=25；
    若大会给的是 35–45 分钟档，把「方案」段按比例拉长，其余四段不动）
  开场（2 分钟）   一个真实事故或一个反直觉结论 → 建立注意力（不靠自我介绍）
  问题（4 分钟）   约束是什么：规模 / 变更频率 / 合规边界
  方案（14 分钟）  结构图 + 关键决策与 trade-off + 可复现的证据
  代价（3 分钟）   这个方案在什么条件下失效 ← 最容易被砍、最该保留的一段
  结论（2 分钟）   一句可被二手转述的话（别人复述你时只会复述这一句）
  ────────────────────────────────────────────
  Q&A 是唯一的高带宽反馈通道：现场追问会暴露判断里的裂缝
  会后必须产出沉淀物（录播 / 逐字稿 / 配套长文），否则收益在散场时归零
```

- **为什么这样设计有效**：因为「代价」段与 Q&A 展示的是判断而不是结论，所以它建立的是**判断信任与人格信任**——这是长文与开源都建立不了的（§7.3.3）；又因为听众只会带走一句话，把结论压缩成可转述的断言等于把传播外包给了听众，而这一段是你唯一能事先设计的东西。这也解释了为什么同一套内容「讲得好」与「被传得开」是两件事：前者靠现场表现，后者靠那句结论的可用性。
- **代价**：产能单价最高（约 28–48 人时/次，【推算】§7.4，含选题、素材、制版、三次彩排与差旅；素材现成且同城时约 15–20 人时，同为【推算】）；回报是脉冲，峰值在散场那一刻；且席位不可控——选题再好也要先被录用，投递被拒的沉没成本没法摊薄。
- **失效点**：当演讲**没有留下任何沉淀物**（不录播、无逐字稿、无配套长文）时，「高带宽、高触达」会反转成**一次性消耗**——因为现场型收益曲线的尾部为零，同样的准备成本不能二次兑换；而 §7.3.1 的因果很硬：留不留沉淀物，决定了这 28–48 人时（【推算】§7.4）是资产还是费用。第二个失效方向是「讲得精彩但无证据」：现场印象很好，散场后对方想动手时发现没有任何可复现的东西，于是优先级回到原位。
- **真实使用**：QCon / ArchSummit / KubeCon 这类会议的议程与录播公开可核验（【经验】——以 2024 年前后的会议站点存档为准）；【经验】成熟的讲者会先把内容写成一篇长文，再压缩成提纲，因为这正是成本最低的方向（§7.4），反过来则要先补做取数与复现。
- **怎么自检**：会后一周，把结论讲给一个没到场的人听，看他能否复述出你的核心断言并说出你的「代价」段——复述不出，说明这次只留下了印象，没有留下可传播的东西。
- **常见误用**：把演讲当成一次性的曝光机会，只准备台上的 25 分钟，不准备会后的沉淀与追问渠道；结果是判断信任建立了却没被兑现成任何后续动作。

#### 3.2.3 开源项目模式

- **被什么约束逼出来**：别人凭什么相信你说的东西能跑？只有可执行的代码能承载这种证据；而代码一旦公开，就同时带来一份长期承诺。
- **结构**：

```text
开源项目的结构 = 可运行的最小证据 + 一套接得住人的接口
  README        一段话讲清「它解决什么、不解决什么」（不解决什么更重要）
  Quick Start   5 分钟内能跑通的最短路径
  CONTRIBUTING  扩展点在哪、评审标准是什么
  ISSUE / PR    首次响应与合并时限（这是外部可观测的承诺）
  LICENSE       许可证决定别人能不能商用 ← 选错不可逆
  ────────────────────────────────────────────
  这五项缺任何一项，仓库都会退化成"一个人的代码发布"
```

- **为什么这样设计有效**：因为仓库可以被 clone 并跑通，它把对方的验证成本从「数天」压到「数十分钟」，而采纳就发生在这个成本被压下来的那一刻（§7.3.2）；因为 issue 与 PR 的响应时长是公开可观测的，它同时充当「这个团队可不可靠」的代理指标——能力信任就是这么建立的，而且它的证据来自行为而不是来自声明。
- **代价**：启动成本高——把业务代码抽象成可开源项目需要脱敏、文档、示例、CI、许可证与发布流程，按 1 人 × 2–3 个月推算约 300–500 人时（【推算】§7.4）；此后是长期运维承诺：版本要发、兼容要守、issue 要回，不接 issue 比不开源更伤品牌。此外还要处理「开源边界」问题——哪些代码可以公开、哪些含业务逻辑或密钥，这个判断一旦出错是不可撤回的。
- **失效点**：当项目缺少维护承诺（issue 不回、PR 不合）时，「可执行证据」会反转成**负面证据**——因为外部把响应时长当作能力和可靠性的代理指标，一个没人管的仓库比没有仓库更清楚地说明问题，而且这个判断一旦形成就无法撤回；第二个失效方向是「只开源不文档」，别人在 Quick Start 上卡住十几分钟就会放弃（【经验】，按新手独立跑通的容忍时长估计），此时 300–500 人时（【推算】§7.4）的启动成本无法被任何人回收。
- **真实使用**：TensorFlow、Kubernetes 这类由大厂开源的项目，以及向量库 Milvus、嵌入模型 BGE 系列，都以公开仓库与许可证作为主要传播载体（【经验】——仓库、许可证与发布记录可自行核验，以官方仓库当前内容为准）；【经验】判断一个团队是否真的在做开源只需看两件事：首次 issue 响应时间与 PR 合并时间是否稳定。
- **怎么自检**：找一个没用过这个项目的人，按 Quick Start 独立走一遍并计时——超过 10 分钟（【经验】），说明入门成本还没压下来，而入门成本正是这份证据能否被验证的前提。
- **常见误用**：先用开源建设影响力、再考虑文档与响应——顺序反了：外部恰恰是把文档完整度与响应时长当作「这个项目是否可信」的第一证据。

#### 3.2.4 Newsletter 模式

- **被什么约束逼出来**：检索型渠道要等人来搜，现场型渠道要等主办方邀请；想要「内容主动去找人」，只能靠订阅关系。
- **结构**：

```text
Newsletter 模式：直接触达名单，不依赖平台算法
  名单（订阅关系） ──► 每期内容 ──► 打开 / 点击
        ▲                                 │
        └──── 每期末尾只做一件事：给出下一步 ─┘
   ────────────────────────────────────────────
  与博客的机制差异：博客靠"被检索"（累计分布），
                    Newsletter 靠"被推送"（随名单线性增长）
  因此收益上限由名单规模决定，而不是由单篇质量决定
  断更不会让打开率缓慢下滑，而是直接掉一档
```

- **为什么这样设计有效**：因为触达不经过平台推荐，所以同一批人可以被反复带到内容前，这是维持弱关系成本最低的方式（§7.3.3）——它建立的不是判断信任也不是能力信任，而是「这个人在持续关注这件事」的印象；因为收益上限与名单规模近似线性，它的增长可度量、可预期，比现场型渠道更适合作为节奏的稳定器，也最容易做进个人或团队的固定排期。
- **代价**：持续性成本无法摊薄（每期 3–6 人时，【经验】§7.2），停更即归零、不留存量；反馈带宽极低（打开率是唯一信号），内容改进缺少可用的反馈；名单增长本身依赖其他渠道的导入，它不自己产生受众——一个只有 Newsletter 的布道体系，增长上限在第一天就已经写好了。
- **失效点**：当名单增长停滞而内容仍在产出时，「稳定触达」会反转成**自我循环**——因为不再有新受众进入，内容的影响被锁定在既有的一小群人里，此时继续提高单期质量并不改变触达上限；改变量级的动作只有一个：把内容改造成可被检索的长文，让它从「被推送」变成「被搜到」。第二个失效方向是「收购订阅者」（从别处导入不精准的名单）：名单变大而打开率与点击率同时下降，触达的**有效规模**反而更小。
- **真实使用**：Bytes、Latent Space、The Gradient、TLDR 等技术通讯的订阅页与往期归档公开可核验（【经验】）；【经验】最常见的错误是把这件事当成「必须每周更新」的刊物——真正决定成败的是名单从哪里来（通常由长文、开源与演讲的沉淀物导入），而不是更新频率。
- **怎么自检**：看最近三期有没有带来任何可观测的动作（报名、试用、投递、提问）——一期都没有，说明它没有在扩大有效触达，只是在既有名单里循环。
- **常见误用**：把「更新频率」当作运营指标——频率只影响既有名单的打开率，不改变名单规模这个上限；频率提上去而名单不增长，等于把成本换成了更快的归零。

#### 3.2.5 视频 / 直播模式

- **被什么约束逼出来**：有些内容（上手过程、工具演示、失败现场）用文字承载不了，只有画面能表达；而平台推荐机制能给零受众的内容一次冷启动。
- **结构**：

```text
视频 / 直播：不可替代的是"过程"，不是"结论"
  视频：演示与画面   → 可剪辑、可检索、可长尾分发
  直播：双向且零剪辑 → 真实感换精度，说错的话被永久记录
  ────────────────────────────────────────────
  成本主导项在后期，不在录制：每分钟成片约 1–2 小时（【经验】§7.2）
  因此一条长视频必须能被拆成多条短视频 + 一份文字稿，
  否则产能不可持续，而且内容无法被检索到
```

- **为什么这样设计有效**：因为演示是「过程证据」，观众的验证成本是跟着做一遍（数十分钟），低于读长文后自己复现（数小时），所以它擅长推动「上手」而不是「写进方案」（§7.3.2）；又因为平台会在发布初期给一次曝光，它是零受众团队唯一不依赖既有关系的冷启动路径——这条路径对没有讲台、没有名单、没有存量读者的人尤其重要。
- **代价**：产能单价高（后期与剪辑是主导项，按每分钟成片 1–2 小时推算，一条 20 分钟的视频要 20–40 小时，【推算】§7.2）；门槛真实存在（镜头前表达是独立技能，还需要设备与安静环境）；受众由平台算法决定，无法把观众带到别处——账号与算法规则一变，累计的触达可能一夜之间失效，这是它与长文最大的结构性差别（长文的 URL 与检索权重归你自己）。
- **失效点**：当只做直播、不做剪辑与文字稿时，「零剪辑的真实感」会反转成**不可检索、不可引用**——因为检索型资产的载体是文字索引，直播留下的只有一场已结束的事件，三个月后无法被任何人找到；同理，长视频不做拆条，单条内容的产能永远摊薄不了。直播还有第二个反向风险：即兴说出的未经核实的数字会被永久记录并可能被引用，用可信度换来的真实感并不划算。
- **真实使用**：Stanford CS231n 的公开课程录播（【公开】Stanford CS231n 课程站点, 2015 年起）与 Karpathy 的 zero-to-hero 系列（【公开】Karpathy, YouTube, 2022）被反复引用的原因不是观点，而是内容里从零写下可运行的代码，观众可以自己跑出同样结果（§7.3.2）；【经验】判断方法：看一个技术频道是否配文字稿——有文字稿的内容能被检索，没有的就只在发布当周存在。
- **怎么自检**：关掉声音看一遍——如果内容仍能理解，说明它是「演示型证据」；如果什么都传达不了，那它只是一场谈话，应当补文字稿或拆条再发布。
- **常见误用**：以「更新数量」为目标，于是拆条与文字稿被最先省掉——省掉的恰好是把脉冲变成长尾的那一步，剩下的只有一条会随时间沉底的视频。

#### 3.2.6 AI 增强布道模式（2024+）

- **被什么约束逼出来**：内容需求的增速快于内容产能，而可投入的人时不变；LLM 能压缩的只是生产环节中写作那一段，压缩不了取数与复现。
- **结构**：

```text
AI 增强布道：放大器，不是新渠道
  选题 / 提纲 / 初稿 ──► 交给 LLM        （省的是写作那一段）
  取数 / 复现 / 校验 ──► 必须人工          （AI 帮不了，也正是证据的来源）
  ────────────────────────────────────────────
  §7.4 的推算：一篇 7–14 人时的文章里，写作与校对占 3–6 人时；
  AI 可压缩其中约一半，节省 1.5–3 人时 —— 占总量一到两成
  因此省下的时间必须投回"取数与复现"，而不是"多发一篇"
```

- **为什么这样设计有效**：因为它作用在**边际产能**上而不改变任何一条分发机制，所以它不会把脉冲型渠道变成累计型，只把同样人时的产出抬高约一到两成（【推算】§7.4）；因为它替代不了取数与复现，它天然把「证据」这一环留给了人工，而证据恰好是唯一能推动采纳的东西（§7.3.2）——这条「省下来的时间投回哪里」的纪律，比工具选择重要得多。
- **代价**：多出一道事实校验工序；跳过这道工序的代价不可逆——§7.4 的「可信度折旧」指出，一个被转发过的错误数字会长期留在别人的内容里；此外生成文本的「温度」低，开场与结论通常需要人工重写，而这两段恰恰最影响转述率；最后是文体趋同的风险：同一个模型生成的文本，读者往往能在第三段就认出来。
- **失效点**：当团队用 AI 提高产出**篇数**而不是提高**证据密度**时，「效率高」会反转成**整站可信度下降**——因为读者判断内容价值的标准是可复现性，而 AI 放大的是表述产能、不是证据产能；产量上升而可核验性不变甚至下降，长期拉低的是同一个品牌下所有内容的可信度。第二个失效方向是「用 AI 补证据」：让模型生成看起来合理但未经核实的数字或性能对比，这类错误的传播速度恰好是最快的（因为读起来最顺）。
- **真实使用**：用 LLM 起草初稿、生成演讲提纲已成为 2024 年后的常见做法（【经验】）；【经验】判断一个团队用得好不好，只看一件事——内容里的数字有没有出处、参数是否完整；这与用了什么工具无关。
- **怎么自检**：随机抽一篇内容，逐个核对其中的数字与参数能否追溯到来源——抽查不通过，说明 AI 放大的是产量而不是证据，此时应当减慢发布速度先补校验清单。
- **常见误用**：用 AI 生成数字与对比表——数字属于证据产能而不是表述产能，这恰好是 AI 最不该碰、也最容易出错的部分。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 内部分享 / 平台采纳（受众只在一个封闭渠道里） | 内部分享 + 读书会 + 一份可自读的沉淀文档 | 不选 Conference：外部讲台解决不了组织内部的采纳阻力 | 受众平时在哪看到技术内容 |
| 团队品牌（已有可讲的工程素材） | 金字塔 + Conference | 不选「先做开源」：开源启动约 300–500 人时（【推算】§7.4），此时素材还不存在 | 日常工作中是否已有可抽象的内部工具 |
| 个人品牌（从零开始） | 长文 + Conference + 视频 | 不选 Newsletter 起步：没有存量受众时名单增长极慢，反馈又最弱 | 能否从其他渠道导入第一批订阅者 |
| 行业影响力 | 开源 + Conference | 不选只做长文：行业影响力需要可被验证、可被依赖的产物 | 能否拿出被 clone、被依赖的东西 |
| 业务翻译（对方是决策层） | 内部分享 + 可检索长文 | 不选 Podcast / 直播：业务方不会在音频里找口径，也没法转给同事 | 对方会不会亲手执行 |
| 招聘雇主品牌 | Conference + 开源 + 视频 | 不选 Newsletter：候选人验证的是能力证据，不是名单 | 候选人能否在数十分钟内自己验证你的能力 |
| AI 时代（技术迭代快、内容需求大） | AI 增强 + 以沉淀型为底 | 不选「只靠现场」：模型能力几个月一变，现场内容过期即废 | 这批内容的半衰期是月还是年 |

**最常被误选的一对是「Conference 演讲模式」与「开源项目模式」**。两者都被当成「建立影响力的手段」，但它们在证据链上处于不同位置：演讲建立的是判断信任（对方觉得你讲得对），开源建立的是能力信任（对方敢在生产上用你的东西，§7.3.3），**两者不可互换**。误选的实际后果有两个方向：先冲 Conference 的团队，做完一年后发现没人敢在生产用他们的东西——因为没有任何可 clone 的产物，所有说服都停在印象层；只做开源不做演讲的团队，则常出现「库很受欢迎，但团队没人认识」，招聘与合作转化率远低于同量级的传播。选择依据不是哪个更高级，而是**你缺的是哪一种信任**；代价层面也要看清楚：一次演讲是 28–48 人时、一次开源启动是 300–500 人时（均【推算】§7.4），选错方向的代价是数月的产能投错地方。

**第二对容易误选的是「Newsletter 模式」与「长文（博客）」**，因为两者看起来都是「写东西」。它们的机制差别在于收益上限由谁决定：博客的上限由内容被检索与被引用的次数决定（累计分布，可能超过发布时的受众规模），Newsletter 的上限由名单规模决定（线性，且不增长即封顶）。因此把 Newsletter 当作布道的**起点**是典型误选——它需要名单，而名单需要先有可被检索的资产来导入；正确顺序几乎总是「先长文与开源积累名单，再用 Newsletter 维持节奏」。

**这张表里的场景标签只是近似替代品**。原 §3 按场景给推荐（内部分享 / 团队品牌 / 个人品牌 / 行业影响力 / 业务翻译 / 招聘雇主品牌 / AI 时代），本表保留这些画像，但要清楚它们为什么能用：这些画像其实是通过「产能有多少人时可以投入」「受众是否在封闭渠道里」「有没有可开源的素材」这三条约束起作用的。因此当画像与实际不符时（例如一个 15 人的团队要把工具开源），应当回到约束本身判断，而不是照搬同一行的推荐——**按画像选是入门，按约束选才是可迁移的**。表里真正值得背下来的是「关键判据」那一列：它把每一行压缩成一个可以在五分钟内问出答案的问题。

### 3.4 组合模式：真实系统不会只用一种

**组合一：内部分享 + 可检索长文 + 采纳看板（平台采纳组合）**

- 组合构成：内部分享负责说服组织内的人，长文负责让没来的人自己读完，采纳看板负责把「推得怎么样」变成可对比的数字。
- 职责边界：分享改的是共识，长文改的是可达性，看板改的是优先级——三者不互相替代，只讲不沉淀等于没讲，只看板不分享则无人推动。
- 运维代价：内部分享的准备成本（每次 4–8 人时，【经验】）与录播归档的持续投入；长文要求把内部口径脱敏成可对外复用的版本，于是每篇多一道脱敏与校对工序；看板要求每个团队维护自己的采纳口径，口径对不齐时数字会先失去可比性。
- 适合规模：多团队、跨 BU 的平台型组织（本书 §6 的四家案例都是这个形态）。
- 这条组合的失效点：当分享升级成「必须留痕的正式汇报」时，准备成本会迅速膨胀，人们开始用「先做完手头项目再讲」推掉它，分享频率下降——所以内部分享的形式必须保持轻，重的是沉淀物而不是现场。

**组合二：长文 + Conference + 视频（个人 / 团队品牌组合）**

- 组合构成：长文是证据底座，Conference 做判断信任与主办方背书，视频把「上手过程」补上。
- 职责边界：长文承担可检索、可引用的职责；Conference 承担「谁能当面追问」的职责；视频承担演示与冷启动的职责。任何一条都不能替另一条完成转化。
- 运维代价：三种表达技能与三层产出节奏，通常需要把布道排进排期才能维持；演讲必须配套录播与逐字稿，否则 28–48 人时（【推算】§7.4）只兑换一次脉冲；视频还存在独立的剪辑工序与平台风险，受众不在自己手里。
- 适合规模：个人或 3–10 人的小团队，主战场是行业影响力与招聘。
- 这条组合的失效点：三条渠道同时推进时，最容易牺牲的恰好是最该保留的那一项——证据（因为取数与复现是唯一不能靠表达技巧补齐的环节）。所以它的产能纪律应该是「先保证每月一篇长文的证据密度，再决定这个月要不要讲」。

**组合三：开源 + Newsletter + 社区响应 SLA（生态与开发者组合）**

- 组合构成：开源提供可执行证据，Newsletter 维持关系与节奏，社区响应把「可被依赖」变成外部可测的事实。
- 职责边界：开源负责让能力可被验证，Newsletter 负责把使用者和候选人留在同一批名单里，SLA 负责把承诺变成数字；三者共用同一批受众，但各自改变的东西不同（敢用 / 记得你 / 信你会回应）。
- 运维代价：三项都是长期承诺——仓库要长期维护、Newsletter 断更即归零、SLA 一旦公布就必须守住；叠加后需要的不是一个岗位的业余时间，而是一个能被排期保护的专职角色，这也是三者里唯一需要预算的部分。
- 适合规模：有产品化意图、开发者是主要入口的团队（50 人以上、且已有可开源素材）。
- 这条组合的失效点：当社区响应 SLA 公布后无法守住（大版本发布期间 issue 积压数周），「可被依赖」会以最快速度反转成「不可靠」——因为这项承诺是公开且连续的，单次违约就会被外部观测到，而观测到的结论会被长期引用。

三组组合有一个共同的取舍：**它们都把「证据」放在比「分发」更靠前的位置**。这不是价值观偏好，而是机制必然——分发只决定有多少人看到，证据才决定多少人动手；前者可以用钱和渠道换，后者只能用人时换。因此组合的排布顺序应当是「先定证据从哪来、能撑到什么密度，再为它配渠道」，而不是反过来先选渠道再想内容。

三组之间也不是升级关系，而是**随业务阶段平移**：内部平台期用组合一，对外立品牌用组合二，做开发者生态用组合三。平移的判据只有一条——你希望对方在验证之后做什么动作：改用你的方案（组合一）、招你或与你合作（组合二）、把代码接进自己的系统（组合三）。动作变了，组合就要换。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 布道 = 念 PPT | 全程照读、没有 Q&A、听众低头看手机 | 反馈带宽归零 ⇒ 建立不了任何信任，只留下了「来过」 | 内容是从文档改的、没为听众重写过 | 开场用真实事故、结尾给可转述断言；把 Q&A 排进议程并留足时间 |
| 一次性布道 | 发过 1–2 篇就停更，账号最后更新在半年前 | 收益曲线被打断 ⇒ 未达检索型资产的复利拐点，投入全部沉没 | 靠热情驱动、没有排期与节奏 | 用「先写后讲」的搬运关系把产能固定下来（§3.2.1），把节奏写进个人季度目标 |
| 自嗨式布道 | 内容全是自己关心的技术细节，听众问「所以我们能用它做什么」 | 内容无法被对方映射到自身问题 ⇒ 传播停在场内 | 选题来自自己的兴奋点而不是受众的约束 | 讲前先做一次受众调研；用业务口径重写标题与结论（§7.3.3 的业务翻译） |
| 开源 = 贴代码 | 只有代码、无 README 与 Quick Start，issue 长期无人回 | 可执行证据退化为负面证据 ⇒ 能力信任反向建立 | 把开源当成发布动作而不是长期承诺 | 五项齐备（README / Quick Start / CONTRIBUTING / ISSUE 规则 / LICENSE），并公布响应时限 |
| Conference 演讲应付 | 临场改 PPT、超时、Q&A 答不上来 | 现场型渠道的脉冲收益为负 ⇒ 判断信任被削弱而不是建立 | 把它当成一次性的曝光机会而非数月的工作 | 提前 2 个月准备、彩排 3 次以上（【经验】）、会后回收反馈并沉淀长文 |
| 业务翻译失败 | 业务方听完说「技术很强，但和我们没关系」 | 技术方案无法进入决策 ⇒ 采纳不发生 | 用技术语言讲技术价值，没做口径改写 | 从业务痛点切入、把收益折成时间 / 成本 / 风险口径、先小范围试点再复制 |

六个反模式有同一个结构：**它们都是在某一环上放大了产量，却没有放大可验证性**。

```text
反模式的共同形状：放大的是产量，缺的是可验证性
  布道 = 念 PPT        → 放大了"讲"，    没放大"听众带走的东西"
  一次性布道           → 放大了"开始"，  没放大"累计"
  自嗨式布道           → 放大了"我想讲"，没放大"他要用"
  开源 = 贴代码        → 放大了"发布"，  没放大"接得住"
  Conference 演讲应付  → 放大了"到场"，  没放大"准备"
  业务翻译失败         → 放大了"技术"，  没放大"业务口径"
  ────────────────────────────────────────────
  判据：问一句"这一环放大的到底是谁的产量，对方要付出的验证成本降了吗"
```

**最危险的三个，在生产里的典型暴露方式**：

「**一次性布道**」的暴露方式不是「没人看」，而是**在复利拐点之前停手**：检索型资产的收益要在内容累积到一定量、并被反复索引之后才显现，而停更恰好发生在这个拐点之前，于是团队得到的结论是「写了也没用」。它的机制后果是**用一段不完整的收益曲线去否定这条曲线**，而这个结论通常会被写进下一年的预算与人力决策里，代价比停更本身大得多。修法的关键不在于「逼自己多写」，而在于把节奏绑到一个不依赖热情的机制上——例如把选题绑定到正在做的项目上（写的就是手上这件事），这样单篇的边际成本可从 §7.4 的 7–14 人时回落到 **4–8 人时**（= 7–14 减去取数与复现的 3–6 人时，仍含选题与资料 1–2 人时；均【推算】§7.4）。

「**开源 = 贴代码**」的暴露方式更隐蔽：star 数在一段时间内持续增长（因为项目本身有用），但生产采用者极少、issue 无人应答。能力信任一旦反向建立，修复成本远超重新开源一个项目——因为外部判断的是「这个团队会不会维护」这一件事，而它只能靠新的、持续的行为重新证明，声明无法加速这个过程；重建所需的，恰好是当初没有投入的那部分长期运维产能。

「**自嗨式布道**」的暴露方式是「好评但不采纳」：听众反馈都说内容好，但没有任何人因此改变技术选型或提起试点。机制原因是内容没有落在对方的约束上——**对方要的不是你的技术有多好，而是他自己的问题能不能被解决**；好评是对表达的评价，采纳是对证据与相关性的评价，两者不是一回事。判定方法很直接：复盘最近三次分享，有没有任何一个听众在两周内做了可观测的动作（提试点、改选型、写进方案）——没有，就是自嗨。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 1 个团队 → 10+ 团队 | 靠个人热情的零散分享 | 产能是个人余量，团队一多就覆盖不到，「讲过了」也没人知道 | 布道岗位化 + 采纳看板 + 录播归档 | 需要排期与指标，布道者从「兼职呼吁」变成「背采纳率」 |
| 月更 → 周更 | 每篇精雕细琢 | 精雕的产能单价（7–14 人时/篇，【推算】§7.4）撑不住周更，质量会先崩 | 素材库 + 复用（长文 → 短文 / 分享 / 视频拆条） | 需要一次内容资产化改造，把旧内容索引成可复用素材 |
| 内部 → 对外 | 内部口径直接复用 | 内部内容含未公开数据与内部黑话，对外会同时暴露风险与不可读 | 脱敏流程 + 对外一致性口径 | 每篇多一道脱敏与校对工序；内部 / 对外两套版本需要维护 |
| 无沉淀物 → 有现场需求 | 只做演讲与直播 | 现场是脉冲型，散场归零；再高的触达也换不来累计收益 | 先补沉淀物，再向现场分发 | 短期看是「减速」（多写一篇才去讲），长期才是资产 |
| 单语言受众 → 多语言受众 | 只做一种语言的长文 | 受众规模被语言封顶，而证据本身是可跨语言的 | 双语 / 译文 + 术语一致性维护 | 翻译质量与术语统一的持续成本；译文一旦失真会反噬原文可信度 |
| 个人 IP → 团队品牌 | 靠一两个核心讲者 | 讲者离职或调岗，影响力随人走，团队不继承 | 内容与开源落到团队名下 + 多人轮值 | 需要制度化的轮值与审稿，产出的个性与温度会先下降 |
| 有人工校验 → 引入 AI 辅助 | 全人工写作 | 内容需求增速快于人时，产能成为瓶颈 | AI 增强 + 硬性事实校验清单 | 多一道校验工序；跳过它的代价不可逆（§7.4 可信度折旧） |

**这张表里唯一不能靠加预算解决的一行是「个人 IP → 团队品牌」**：因为影响力天然附在个人身上，把它转移到团队名下需要**改变署名与产出的组织方式**（轮值、审稿、共同署名、团队账号），而不是再多找几个人写。判断方法：如果你最核心的那位讲者明天调岗，你的布道体系是否还剩下什么——剩下的是团队品牌，不剩下的是个人 IP。

另有两行的触发条件值得单独记：**「月更 → 周更」的痛点先出现在质量而不是数量上**——精雕的单篇成本决定了周更必然挤压取数与复现，于是内容会先变成「观点合集」，证据密度下降，而证据正是推动采纳的唯一货币；**「无沉淀物 → 有现场需求」的痛点先出现在复盘里**——一年后统计投入时，会发现所有产能都变成了已结束的事件，没有任何可复用资产，此时再补沉淀物只能从零开始。

**所有跃迁的共同信号是同一个**：当「这件事现在靠谁记得」的答案从「靠习惯」变成「靠某个人」时，就该换模式了。布道的规模跃迁几乎都不是渠道问题，而是**从依赖个人记忆与热情，切换到依赖排期、素材库与可度量指标**——凡是没有完成这一步的组织，都会在核心讲者离开或业务压力上来时，让整条布道曲线回退到起点。

### 3.7 自检清单

- [ ] 每一场演讲 / 直播之后，是否有一份可被检索的沉淀物（录播、逐字稿或配套长文）？
- [ ] 内容的方向是否是「先写后讲」？如果长期是「先讲后写」，说明产能在向成本更高的方向流动（§7.4）。
- [ ] 最近三篇内容里，数字与参数是否都有出处？没有出处的精确数字等于在用可信度换速度。
- [ ] 核心内容有没有被当面追问过？从没被追问过的判断，还没有被压力测试。
- [ ] 渠道组合里是否至少有一条累计分布型渠道（长文 / 开源），而不是全是脉冲型（演讲 / 直播）？
- [ ] 开源仓库的五项（README / Quick Start / CONTRIBUTING / ISSUE 规则 / LICENSE）是否齐备？首次响应与合并时限是否稳定？
- [ ] 是否有为「没来现场的人」准备的入口？只服务到场听众的内容，触达上限由场地决定。
- [ ] 选题是否来自受众的约束（业务痛点 / 规模 / 合规），而不是自己的技术兴奋点？
- [ ] 布道是否被排进了排期并有人对结果负责？「闲时做」的实际产能通常为零。
- [ ] 引入 AI 辅助后，是否增加了事实校验步骤？省下的时间投回了取数与复现，还是投回了篇数？
- [ ] 如果最核心的讲者调岗，这套体系还剩下什么？
- [ ] 对外内容的半衰期是多久？写的是方法（长期有效）还是版本号（三个月即错）？

如果这 12 条只能先做一条，选第 4 条「核心内容有没有被当面追问过」——它同时暴露证据密度与反馈带宽两个约束：没有被追问过，意味着你既没有可被质疑的证据，也没有能质疑你的通道，其余各条多半也只是形式上的完备。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 受众只在一个封闭渠道里 | 内部分享 + 读书会 | 组织内部的内容不走公开检索，走组织记忆 |
| 零受众、想冷启动 | 长文 + 视频 | 检索型收益是累计分布；平台推荐给零受众一次曝光 |
| 已有工程素材、要团队品牌 | 金字塔 + Conference | 素材向现场再分发的边际成本最低（3–5 人时，【推算】§7.4） |
| 要行业影响力、有可开源素材 | 开源 + Conference | 开源给能力信任，演讲给判断信任，不可互换 |
| 决策层受众、要推动采纳 | 业务翻译 + 可检索长文 | 采纳发生在对方验证成本被压低的那一刻 |
| 技术迭代快、内容需求大 | AI 增强 + 以沉淀型为底 | AI 只放大表述产能，证据产能仍须人工 |

三条可迁移的判断：**先定信任类型，再定渠道**；**先按成本最低方向搬运素材，再考虑新选题**；**任何一次投入都问一句「这次留下的是资产还是事件」**。

> 本节小结：本主题下决定渠道组合的**唯一那条约束**是——**你能不能把对方的验证成本压下来，以及能压多久**。「能压多低」由证据密度决定（可 clone 的代码 < 带参数的长文 < 只有结论的演讲），「能压多久」由分发机制决定（检索型累计、推送型线性、现场型脉冲）。其余结论——该不该做录播、该先写还是先讲、要不要岗位化、能不能用 AI 提高产量——都可以从这两问推导出来；而所有反模式的共同点，都是在某一环上**只放大了产量，没有放大可验证性**。
