## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

P6 → P7 的差距记为两条：**系统设计：差 1 分**、**领导力：差 1 分**（出自主文件 §2 的 BAR 自评表，1–5 分制；这是本书给出的示例评分，不是行业统计【经验】）。这两条看起来只是两项待办，其实是**两类性质完全不同的缺口**，而性质决定了哪一族模式在原理上有效：

- **系统设计差 1 分 = 「没做过」**——这是**技能缺口**。它不能被讲会，只能靠做出可被观察的产出：拆过一次接口边界、评审过一次容量方案。对应的模式族是任务族（OJT）与定向 1:1。
- **领导力差 1 分 = 「没当过那个角色」+「没被放进那个位置」**——这是**机会缺口**与角色缺口的混合。再多辅导时长也不会自动产生一次带人经历；它需要的是授权与提名，也就是 Sponsor。

由此得到本节的第一个论断：**辅导模式的差别不在「哪种更有效」，而在「它补的是哪一种缺口」**。三类缺口——信息缺口（不知道口径、流程、规范在哪）、技能缺口（没做过）、机会缺口（绩效已达标但没被放进关键项目）——对应三族不同机制，跨族不可互替（判据与分流顺序见 §7.5 决策树）。把「能力够了却升不上去」的人继续送进 1:1，是在错误维度上加码。

第二个论断：**约束一变，同一场景的正确模式会反转**。Mentor 每周能拿出 3 小时，按单人次实际占用 45–120 分钟（30–60 分钟显性时长 × 1.5–2 倍准备与跟进系数）计，1:1 只够覆盖 **1.5–4 人**【推算】（推导见 §7.5）——待辅导不超过 4 人时，「全覆盖」才成立；同样这 3 小时放到 30 人团队，1:1 从「个性化最优」变成「只能定向投放」，此时覆盖率由人力杠杆（一个 Mentor 小时服务几人）决定，而不是由意愿决定。所以先立约束，再谈模式。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 差距类型（信息 / 技能 / 机会） | 哪一族模式在原理上有效 | 「有卡点就上 1:1」——机会缺口加辅导时长不产生名额（§7.3.3） |
| Mentor 可投入小时数 | 可覆盖人数与形态（1:1 / Group / Cohort） | 「1:1 最有效」——超过容量后它会退化成状态同步，不是效果差，是形态变了 |
| 反馈延迟要求 | 用 OJT 还是用评审 | 「反馈可以攒到季度谈」——延迟超过一周，反馈锚不回具体行为（§7.3.2） |
| 机会分配权归属 | 是否需要 Sponsor | 「找个厉害的人带」等于解决晋升——它只补能力，不补曝光与名额 |
| 知识显式化程度 | AI 辅助辅导的可用上限 | 「先上 AI，知识自然会沉淀」——语料是前序条件，不是 AI 的副产品（§7.3.4） |
| 心理安全水平 | 所有模式的前提是否成立 | 「换一种辅导形式就能收真话」——前提不成立时，任何形式都退化为汇报进展 |

**读法**：表中任何一行与你的直觉冲突时，以该行为准。「1:1 最有效」这条直觉，会被第二行（容量）、第六行（心理安全）中的任意一条直接推翻。

还有一条被忽略的约束：**辅导的产出无法用单一标量排序**。辅导产出是「人的能力增量」，而能力增量与「机会」强耦合——一个被辅导得很好但没人提名的工程师，和一个被辅导得一般但被 Sponsor 推进关键项目的工程师，两年后的职级可能完全相反。所以本节不按「哪种模式更好」组织，而按「哪种缺口由哪族机制补」组织。

差距类型与模式族的对应关系，可以用一张最小的表固定下来（本节的骨架就是它）：

| 缺口 | 一句可自检的症状 | 有效的族 | 无效的投入 |
| --- | --- | --- | --- |
| 信息缺口 | 「这事该问谁 / 口径在哪」 | 关系族（Buddy）+ 机器族（文档 / AI） | 占用 1:1 小时 |
| 技能缺口 | 「没主导过 / 没拆过」 | 任务族（OJT）+ 定向 1:1 | 只给课程 |
| 机会缺口 | 「绩效达标但没被放进关键项目」 | Sponsor + 关键项目分配 | 增加辅导时长 |

**这张表的作用是提前排除**：第三行的无效投入（增加辅导时长）是组织最常做的一件事，因为它是唯一不需要向上争取资源就能启动的动作。

### 3.2 模式逐个拆解（核心节）

下面 8 个模式各按同一结构写：**被什么约束逼出来 → 结构（代码块）→ 为什么这样设计有效 → 代价 → 失效点 → 真实使用**。其中「失效点」是最不可省的一段——它回答的不是「这个模式有什么缺点」（形容词），而是「在什么条件下它的优点会反转成缺点，以及为什么（机制）」。

8 个模式与三类缺口的映射是：信息缺口 → 3.2.7（Buddy）+ 3.2.8（AI）；技能缺口 → 3.2.2（OJT）+ 3.2.1（定向 1:1）；机会缺口 → 3.2.6（Sponsor）。而 3.2.3（IDP）、3.2.4（GROW）、3.2.5（SBI）是**跨缺口复用的协议**——它们不补某一类缺口，而是把「差距 → 行动 → 反馈」这条链路结构化，因此它们的失效方式也不同：不是「选错族」，而是「没有纪律就空转」。

#### 3.2.1 1:1 定期辅导

- **被什么约束逼出来**：成长议题没有截止日期，而交付有。没有固定时段，它永远排在最后。
- **结构**：

```text
1:1 的结构（时间盒 + 闭环，四段缺一段就退化）
  ① 上次 Action Items 回顾    5 min   ← 闭环入口：不回顾 = 上次的承诺作废
  ② 当前进展与卡点           15 min   ← Mentee 主导（约 80% 议程由 Mentee 出【经验】，出处为主文件 §2.3 的 1:1 设计）
  ③ 成长议题 / IDP 进度      10 min   ← 这一段被挤掉，1:1 就变成状态同步
  ④ 个人关心                  5 min
  记录：日期 / 卡点 / 承诺（谁·何时·做什么）/ 下次回顾项
  流向：本次产出 → 下次第 ① 段 → 未闭环项必须显式续期或作废
```

- **为什么这样设计有效**：因为成长议题没有外部截止日期，所以唯一能让它持续发生的机制是「固定时段 + 必须被回顾的承诺清单」；因为议程由 Mentee 主导，所以讨论对象是**他认定的卡点**，而不是 Mentor 关心的进度——后者在部门周会上已经同步过了，重复一次等于浪费 Mentor 小时。
- **代价**：Mentor 小时的线性成本，且真实占用高于显性时长——单次显性 30–60 分钟，含会前准备与会后跟进的系数通常为 **1.5–2 倍**【经验】（推导见 §7.4）。
- **失效点**：当单名 Mentor 承担的 1:1 人数超过容量上界（**1.5–4 人**，推导见 §7.5【推算】）时，第 ② 段会自动吃掉第 ③ 段，1:1 从成长对话退化为状态同步——因为信息类问题永远比成长议题更紧急，会把时间盒优先占满。
- **与相邻模式的边界**：1:1 与 OJT 的分工单位不是「线上 / 线下」，而是**反馈延迟**——同一个话题若能在任务现场谈，就归 OJT；若它必须脱离任务上下文才能谈（方向、取舍、职业选择），才归 1:1。
- **真实使用**：Kram《Mentoring at Work》（1985）把辅导拆成**职业功能**（sponsorship / exposure / coaching）与**心理社会功能**（角色榜样、接纳、友谊），这正对应议程里必须有第 ③ 段与第 ④ 段两件事【公开】；Google 的 Project Oxygen 2018 更新版把「Coaching」列为管理者有效行为之首（【公开】Google re:Work《Project Oxygen》报告，2018 年更新版；本节未附链接，可由 re:Work 公开资料核验）——两处引用均见 §7.3.1。

#### 3.2.2 OJT（在岗训练）

- **被什么约束逼出来**：技能缺口只能由「做过」填平，而反馈只有在行为上下文尚未消失时才可执行。
- **结构**（任务难度阶梯 + 导师配对）：

```text
OJT 的派活阶梯（每一级都配一名当级导师，且必须可观察）
  L1 复现既有流程    例：照既有模板跑一次分层变更     导师：同组 P5/P6
  L2 独立完成子模块  例：独立负责一张 DWD 表的建模     导师：P6/P7
  L3 定义边界与取舍  例：定义跨模块接口 / 出容量评估    导师：P7+
  L4 对人负责        例：带 1 个 P5 完成 L2           导师：P7+ 或经理
  规则：Mentor 的第一反应是提问而不是接手（接手 = 学习终止）
```

- **为什么这样设计有效**：因为反馈的有效性取决于「行为上下文是否还在双方记忆中」，所以把辅导嵌进交付时间线（Mentor 与 Mentee 同任务）天然获得最短的反馈回路；因为任务被显式分成可观察、可分解、可复现的四级，所以「做到哪一级」是可举证的，而不是印象。
- **代价**：返工与 Mentor 的救援成本。OJT 的 Mentor 同时是交付责任人，他有内在动机**顺手替对方做完**——这条成本不会出现在工时表上，只会出现在「这人两年了还不会独立拆需求」。
- **失效点**：当任务**不可观察、不可复现**时（例如「探索性的架构判断」「跨 BU 的政治协调」），OJT 的延迟优势反转成劣势，因为「做对没做对」本身要几个月才知道，反馈无法锚回任何具体动作——此时应退回 1:1 + Sponsor。
- **与相邻模式的边界**：OJT 与课程的分工是**反馈是否即时**——OJT 的产出物会被导师当周看到并纠正，课程的产出物（作业）通常延迟数周；因此技能缺口不能靠「多上几门课」填平。
- **真实使用**：【经验】Microsoft 于 1990 年代系统化导师制度、阿里 2014 年前后推行「师兄文化」、字节「Buddy + Mentor」双轨，均属把辅导嵌进工作的形态（年份见主文件 §1.4 演进年表；本节未逐一给出外部链接，读者可自行核验）。可自行核验的判断方法见 §7.3.2。

#### 3.2.3 IDP（个人发展计划）

- **被什么约束逼出来**：成长是跨季度的，而人与人的记忆不是。没有书面结构，差距与承诺会在三个月内蒸发。
- **结构**：

```sql
-- IDP 的结构：主文件 §2.3 的五要素（goal / current / gap / action / resource）+ 时效字段 review_due；五要素缺一项计划就退化，缺 review_due 则两个月内失效
CREATE TABLE idp (
  person      TEXT,
  goal        TEXT,   -- 6–12 个月的关键目标，与 OKR 对齐
  current     TEXT,   -- 现状：BAR 自评 + 经理评估（例：系统设计 3 / 领导力 2）
  gap         TEXT,   -- 目标 − 现状，必须写到「哪一维差几分」，不给形容词
  action      TEXT,   -- 具体行动，且必须写出「承接的项目/任务名」
  resource    TEXT,   -- 导师 / 课程 / 项目机会 / 预算
  review_due  DATE,   -- 下一次 Review 日期
  PRIMARY KEY (person, goal)
);
```

- **为什么这样设计有效**：因为差距只有落到「哪一维、差几分、由哪个项目承接」才可被验证，所以这五个要素把「我要变强」翻译成一张可检查的表；`action` 里要求写项目名，是因为没有项目承接的行动项等于愿望。
- **代价**：每季度一次的结构化 Review 与维护责任。IDP 的成本不在填写（约数十分钟），而在**它必须有人按时 Review**——发出去就不管的 IDP 比不发更伤信任。
- **失效点**：当组织没有与之对齐的真实项目机会时，`resource` 一列会长期为空，IDP 退化为课程清单——因为缺口是「没做过」而行动项是「上一门课」，两者机制不同（无即时反馈的练习不算刻意练习，见 §7.3.2）。
- **与相邻模式的边界**：IDP 与 OKR 的分工是**驱动方向相反**——OKR 由业务目标向下拆解，问「组织需要什么」；IDP 由个人差距向上对齐，问「他还缺什么」。把 IDP 直接写成 OKR 的个人版，会让「补齐短板」这件事永远排不上号。
- **真实使用**：【经验】IDP 在多数科技公司的形态是「季度目标 + 半年度校准」，主文件 §2.3「IDP 设计（5 个核心元素）」把它记为五要素（目标 / 现状 / 差距 / 行动项 / 资源），本节在其上补一个时效字段 `review_due`；本书不给出「某公司 IDP 覆盖率」这类无法核验的数字。可自行核验的判定方法：抽 3 份 IDP，看 `action` 里有没有项目名。

#### 3.2.4 GROW 教练式对话

- **被什么约束逼出来**：Mentor 的直接给答案会替代对方的判断过程，而判断力只能由本人产出。
- **结构**：

```text
GROW 的对话骨架（顺序固定：先扩选项，再收承诺）
  G(Goal)    「你想达成什么？」            → 例：12 个月内到 P7
  R(Reality) 「现在在哪里？」              → 例：P6，OKR 0.7，主导过 2 个项目
  O(Options) 「有哪些选择？」              → 至少列出 3 条，且互斥（不是同一件事的三种说法）
  W(Will)    「你将做什么？何时？」        → 收敛为 1–3 条，写入 IDP 的 action
  反规则：导师在 O 段之前不给方案；O 段给出的方案若不足 3 条，通常是 R 段没问透
```

- **为什么这样设计有效**：因为「被说服的结论」与「自己推出的结论」在执行力上不同——前者遇到阻力就放弃，后者会自我修正；而 O 段强制列互斥选项，是把「只有一条路」这种判断失误暴露出来的机制。
- **代价**：单次对话耗时更长（比直接给答案多花数倍时间），且要求 Mentor 克制表达欲。这条成本是**刚性**的：只要 Mentor 中途给了答案，R 与 O 的产出立刻作废。
- **失效点**：当问题是**信息型**（「口径定义在哪」）时，GROW 反转成低效——问四轮也问不出一个文档链接，因为对方缺的不是判断而是信息；此时应直接给答案或指向文档（差距类型分流见 §7.5）。
- **与相邻模式的边界**：GROW 与 SBI 的分工是**时间方向**——GROW 面向未来（你要去哪、走哪条路），SBI 面向过去（刚才发生了什么、影响是什么）。把 SBI 塞进 GROW 的 O 段，会把「选项」讨论变成对当事人过往行为的复盘，选项就此收敛到一条。
- **真实使用**：GROW 出自 Whitmore《Coaching for Performance》（1992）【公开】，主文件 §2.3 给出完整示例；本书不声称某公司「全量采用 GROW」，因为这类内部实践难以外部核验。

#### 3.2.5 反馈协议：SBI / COIN / Pendleton

- **被什么约束逼出来**：人对「评价」会防御，对「行为」不会。反馈必须被拆成可观察的部分才能被执行。
- **结构**：

```text
SBI 三要素（缺任一项，反馈就会滑向人格评价）
  S(Situation) 情境：「在昨天的 Code Review 中」
  B(Behavior)  行为：「你没有留评论就 Approve 了」   ← 必须是可观察动作，不是「不认真」
  I(Impact)    影响：「作者不知道质量是否过关，CR 质量被稀释」
  改进型反馈额外加一段：具体请求（「至少留 1 条具体评论」）
  同类协议：COIN 把最后一段显式化为 Next；Pendleton 把「先说自己做得好的部分」放在最前
```

- **为什么这样设计有效**：因为防御反应由「评价对象」触发——说「你不认真」触发的是自我辩护，说「这次 Approve 没留评论」触发的是行为核对；三条协议只是在「谁先说、最后一段叫什么」上不同，机制相同。
- **代价**：即时性成本。SBI 只有在行为上下文还在记忆中时才成立（小时—天量级，见 §7.3.2），所以它要求反馈者**当场写下来或当天说**，这是纪律成本，不能靠事后回忆补。
- **失效点**：当反馈与资源决策（绩效、职级）绑在一起时，S 与 B 会被接收方解读为「定级依据」，对方进入防御状态，真实问题被隐藏，次年复发——所以改进类反馈必须与评审解耦（见 §7.7）。
- **与相邻模式的边界**：三种协议的差别只在**顺序与最后一段的名字**上，机制相同（都强制把评价拆回可观察行为），因此不要同时用两套——同一场对话里换框架，接收方会感到被技巧对待。
- **真实使用**：Radical Candor 把「直接关心」形式化为同时具备「个人关心」与「直接挑战」两个维度（Kim Scott《Radical Candor》，2017）【公开】；Kluger 与 DeNisi 1996 年发表于《Psychological Bulletin》的元分析指出约三分之一的反馈干预反而降低了后续绩效（【公开】Kluger & DeNisi, 1996，见 §7.3.2）——这正是必须把反馈锚回情境与行为的实证理由。

#### 3.2.6 Sponsor 关系

- **被什么约束逼出来**：晋升由名额与提名决定，而名额不由辅导者掌握。能力与曝光是两种资源。
- **结构**（责权分离）：

```text
Mentor 与 Sponsor 是两个位置，不可由同一人默认兼任
  Mentor  ── 掌握：信息与指导       动作：提问 / 反馈 / 示范
  Sponsor ── 掌握：机会分配权       动作：提名 / 举荐 / 争取名额
  交汇点：Sponsor 依赖 Mentor 的判断作为提名依据（所以需要 Mentor 主动向 Sponsor 汇报）
  断链症状：能力达标但无人提名 → 与「找不到 Mentor」是两种病
```

- **为什么这样设计有效**：因为「找不到 Mentor」可以用文档、Group、AI 低成本缓解，而「晋升受阻」无论如何增加辅导时长都不会好转——它需要的是把有能力的人放进有决策权的人的视野里。结构上把两者画成两个位置，是为了让「谁提名」这个问题有具体的人可以指向。
- **代价**：高层注意力是最稀缺资源，Sponsor 的容量由名额与关键项目窗口决定，与小时数无关；此外 Sponsor 关系必须组织可见，低调的 Sponsor 说服力为零。
- **失效点**：当组织没有正式的提名与关键项目分配机制时，Sponsor 关系悬空，只剩情绪价值——因为「赞助制」在只有申领制的组织里不存在（判定方法：回看最近 3 次晋升名单里，谁把每个人放进去的，见 §7.3.3）。
- **与相邻模式的边界**：Sponsor 与直属经理的分工是**视野范围**——经理在本人汇报链内有分配权，而 Sponsor 的价值恰好在其汇报链之外；因此「我的经理就是我的 Sponsor」在跨部门提名场景下往往不成立。
- **真实使用**：Ibarra、Carter 与 Silva 在《哈佛商业评论》2010 年的研究指出，女性获得的辅导往往更多，但在晋升上仍处劣势，关键差异在**赞助的获得**（【公开】HBR, 2010，见 §7.3.3）——这是「辅导不能替代机会」最常被引用的支撑。

#### 3.2.7 配对形态变体：Buddy / Reverse / Group / Cohort

- **被什么约束逼出来**：Mentor 小时是硬约束，而待辅导人数在涨。同一份人力要覆盖更多人，只能改变**配对拓扑**。
- **结构**（拓扑即杠杆）：

```text
四种拓扑，差别只在「谁连谁」与「连成什么形状」
  Buddy    ：新人 ── 同侪（1–2 年资历）        杠杆 1，但单价低 → 承担「问谁」的分发
  Reverse  ：新人 ──→ 资深者（信息流反向）      杠杆 1，方向相反 → 承担新技术反哺
  Group    ：1 主持人 ── N 人（通常 6–12）      杠杆 N → 承担共性内容，个体靠课后 1:1
  Cohort   ：讲师 + N 人同批，叠加同侪互教 N×(N-1) 条有向通道（按有向计）
  分族：关系族（Buddy / Reverse / Sponsor）· 任务族（OJT）· 群体族（Group / Cohort）· 机器族（AI）
```

- **为什么这样设计有效**：因为杠杆是「一个 Mentor 小时能触达几人」，所以 Group 用同一小时服务 N 人的代价必然是**内容取最大公约数**，个体卡点只能靠课后 1:1 补——这就是成熟项目总是「Group 打底 + 1:1 兜尖」而不是二选一的原因；因为 Cohort 的额外收益来自同侪网络密度，所以它比 Group 多一层互教通道。
- **代价**：Group 的协调与议题收敛成本；Cohort 的教研设计固定投入；Reverse 需要资深者的心理安全；Buddy 的价格低但可能把错误做法传递下去。
- **失效点**：当 Group 单场人数超过 **12** 时，60 分钟内人均发言不足 5 分钟，个性化为零，模式退化为讲座【推算：由「单场 60 分钟」与「人均发言窗口 ≥ 5 分钟」两条假设推导，两条假设分别取自本书 §7.5 的阈值依据】；当 Cohort 批次结束即解散时，N×(N-1) 条互教通道在最需要的时候被切断。
- **与相邻模式的边界**：Buddy 与 Mentor 的差别在**任期与内容**——Buddy 有明确终期（入职前 3 个月左右【经验】）、只覆盖「流程与常识」，不承担职业判断；把 Buddy 当 Mentor 用，会让 1–2 年资历的同侪承担超出其训练范围的职责，把错误做法传递下去。
- **真实使用**：Reverse Mentoring 被 GE 自 1999 年起推行（【公开】；本节未核到可引用的公开出处，故只给实践名与年份，不写具体文档路径，可由 GE 公开材料核验，详见 §7.2）；阿里师兄制、字节 Buddy + Mentor 双轨见主文件 §1.4【经验】。

#### 3.2.8 AI 辅助辅导

- **被什么约束逼出来**：同一类问题被不同人反复提问，而 Mentor 小时恒定——重复答疑是纯损耗。
- **结构**：

```text
AI 辅助辅导的链路（上限由语料决定，不由模型决定）
  ① 语料层：Handbook / ADR / 复盘库 / 1:1 记录 / IDP 记录（每份带 Owner + 更新时间）
  ② 检索层：按问题召回本组织文档（不是全网语料）
  ③ 生成层：出草稿（IDP 初稿 / 差距汇总 / 学习路径），人做最终判断
  健康指标：回答中引用「本组织文档」的比例 = 当前显式化覆盖率
  前提：② 的语料若为空，③ 只能复述公开博客
```

- **为什么这样设计有效**：因为 AI 的输出质量 ≈ min(模型能力, 语料覆盖)，而在通用模型能力已不构成瓶颈时，上限完全落在语料上；因为边际成本近似为零，所以只要某类问题每月被重复提出足够多次，文档或 AI 就必然比 1:1 划算——3 次/月是「写文档比继续口答更省」的临界点（推导见 §7.5）。
- **代价**：固定投入高（语料整理 + 权限边界 + 更新 Owner），且引入一项新风险：**一次编造的口径会让整个工具被弃用**，信任损耗不可逆。
- **失效点**：当组织没有书面沉淀时，接入模型只会把公开语料复述一遍——**工具不改变语料，只放大语料**；反过来，当卡点是判断力或情绪问题时，显式化成本极高，AI 只能做前置信息整理，不能承担辅导本身。
- **与相邻模式的边界**：AI 与文档的差别是**交互形式，不是知识来源**——两者共用同一份语料，所以「上 AI」永远不能替代「先把知识写下来」；反过来，语料齐备后文档与 AI 只是同一份内容的两条检索路径。
- **真实使用**：可自行核验的判定方法见 §7.3.4——取 20 个真实卡点问题问现有 AI 助手，统计回答中引用**本组织文档**的比例，这个比例就是当前可用上限；本书不声称任何具体产品的辅导效果。

**贯穿上面 8 个模式的两条纪律**（它们不属于任何单一模式，但不满足就无法成立）：

**纪律一：把判断留在本人手里。** 1:1 的议程归 Mentee、GROW 的选项由本人列、SBI 的改进项由本人提、IDP 的行动项由本人写。这不是理念问题而是机制推论：辅导的产出是对方**可迁移的判断力**，而判断力不能由外部替代产出（见 3.2.4）。一旦 Mentor 越位替对方下结论，这次对话的信息量可能更大，但被替代掉的那次练习机会是不可回收的。

**纪律二：每个模式都要有一份记录和一个 Owner。** 1:1 需要 Action Items 台账、IDP 需要 `review_due`、Group 需要议题库、AI 需要带 Owner 与更新时间的语料。记录不是形式：没有记录的模式，其产出会随人员变动蒸发（§7.3.4）；而带不上 Owner 的记录会在三个月后过期。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 差距＝信息缺口（不知道在哪） | Buddy + 文档 / AI | 不用 1:1：同一问题会被重复问 N 次，吃光 Mentor 小时 | 同类问题是否每月被问 ≥ 3 次 |
| 差距＝技能缺口（没做过） | OJT + 周 1:1 | 不用课程/Cohort：无即时反馈的练习不算刻意练习 | 任务是否同时满足可观察、可分解、可复现 |
| 差距＝机会缺口（没人提名） | Sponsor + 关键项目 | 不加辅导时长：名额不由 Mentor 掌握 | 最近 3 次晋升，谁把每个人放进去的 |
| 待辅导 ≤ 4 人、Mentor 可投入 | 1:1 全覆盖 + IDP/GROW | 不用 Group：群体模式牺牲个体卡点，而容量本够 | 单 Mentor 周投入 ÷ 单人次实际占用 |
| 待辅导 5–20 人 | Group 打底 + 1:1 定向 + AI | 不铺开 1:1：容量见顶后 1:1 会退化成状态同步 | 关键少数名单能否装进 1.5–8 人（总容量推导见 §7.5） |
| 资深者跟不上技术变化 | Reverse Mentoring | 不用 Cohort：让资深者与新人同班易触发地位抵触 | 资深者能否公开说「我不会」 |
| 组织知识只在人脑里 | 先显式化，再接 AI | 不上 AI：语料为空时它等价于搜索引擎 | 回答引用本组织文档的比例 |
| 团队刚经历重组 / 裁员 | 先恢复心理安全 | 不换任何新形式：前提不成立时换形式收不到真问题 | 是否有人愿意先说「我不会」 |
| 单名 Mentor 每周可投入 < 1 小时 | 只做「文档 + 定向 1:1」 | 不上 Group：杠杆不足时群体机制会退化为讲座 | 显性辅导时长占团队工时比 |

**最常被误选的一对是「机会缺口 → 1:1」与「技能缺口 → Sponsor」**。前者的后果是能力涨了、名额没变，人会在**一个晋升周期左右**的窗口内流失（【经验】：行业普遍把「能力已达标却未被提名」的流失窗口描述为一个晋升周期左右，无单一权威来源，故给区间不给精确月份）；后者的后果是辅导成本照付、能力没涨，且被荐上去的人答不出设计取舍，Sponsor 的信用被一次性消耗。

诊断误选有一个三步法，不需要任何工具：**① 把待辅导者的卡点写成一句话；② 问这句话缺的是「信息 / 做过 / 机会」中的哪一项；③ 查上表对应行，看当前实际在用的模式是否落在同一行。**三步里第 ② 步最容易答错——「他推动跨团队协作吃力」看似是能力问题，实际常是机会问题（从没被授权去推动过）。答错这一步，后面所有投入都会打在错误维度上。

### 3.4 组合模式：真实系统不会只用一种

1. **新人接力链：Buddy + OJT + 周 1:1**——**构成**：Buddy 管「问谁」（信息分发，单价低）、OJT 管「做中学」（反馈延迟最短）、1:1 管方向与 IDP。**职责边界**：三类缺口各由一件覆盖，任一缺失都会出现在主文件 §1.2 的痛点里（「入职 3 个月还在摸索」）。**运维代价**：需要 1:1 记录归档 + Buddy 轮换机制，否则 Buddy 变成压在同几个人身上的永久负担。**适合规模**：年新增 1–5 人的团队【经验：规模区间为本书经验判断，非统计数据】。
2. **容量受限线：Group 打底 + 1:1 定向 + AI 答疑**——**构成**：Group 承接共性内容（杠杆 N），1:1 只投给关键少数，AI 承接高频重复问题。**职责边界**：谁承接共性、谁承接个体、谁承接信息，必须写下来，否则三者会互相顶班。**运维代价**：三份记录（Group 议题库、1:1 笔记、语料库）需要统一 Owner；本书的经验成本量级是每周约 1 小时的记录维护（见下方推算），真正的瓶颈不是工时而是「谁对口径负责」。**适合规模**：待辅导 5–20 人。
3. **转型线：Reverse + 1:1 + AI 知识库**——**构成**：Reverse 反转新技术的信息流向，1:1 解决个人适应，AI 库承接重复答疑。**职责边界**：Reverse 只解决「新知识在哪」，不解决「我该怎么改工作方式」，后者必须回 1:1。**运维代价**：成败取决于资深者是否被允许公开「不会」，需要管理层先示范。**适合规模**：技术换代期（模型/平台换代）的任何规模。

**【推算】组合的记录成本量级**：20 人团队中 8 人走 1:1，每次会后记录与 Action Items 维护约 10 分钟【经验】→ 8 × 10 = 80 分钟/周 ≈ 1.3 小时/周；占 1 名工程师 40 小时工时的 **3.3%**（1.3 ÷ 40 = 0.0325）。**这条推算的用途是否定一个借口**：记录成本不是组合的瓶颈，瓶颈是没人对口径负责（详见 §7.6 的组合前提）。

三个组合共有的一个前提：**组合的收益来自各件补不同的机制缺口，成本来自每多一件就多一份记录与一个 Owner**。因此组合数量的上限不由人手决定，而由「谁能对口径负责」决定。判断组合是否过量的方法只有一个问题：新人问「这个口径以哪个为准」时，有没有唯一答案。（各组合的完整成本项与迁移代价见 §7.6、§7.7。）

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 1:1 承载一切 | 议程被「当前进展」占满，成长段连续三次没出现 | 成长议题永不上桌，Mentor 小时被信息类问题吃光 | 1:1 是最顺手的形式，所有问题都塞得进去 | 先按差距类型分流，1:1 只留需要判断的议题 |
| OJT 代劳化 | Mentor 说「我先做掉，你看着」 | 学习终止：反馈被替代为代做，练习机会消失 | Mentor 同时是交付责任人，代做对他是最优解 | 纪律：第一反应是提问不是接手 |
| 反馈年度化 | 全年无改进类反馈，攒到半年度评审一次说 | 延迟以月计，已锚不回具体行为；且绑定资源决策引发防御 | 平时开口有心理成本，评审是「正式场合」 | 改进类反馈拆到日/周粒度（SBI），评审只承担资源决策 |
| Buddy 永久化 | 同一批老员工连续带了 3 届新人 | 同侪时间被隐性占用，Buddy 本人成长被挤压 | Buddy 没有任期与轮换台账 | 给 Buddy 设任期与轮换名单 |
| Group 超员 | 单场 > 12 人，多数人不发言 | 60 分钟服务 20 人 = 人均 3 分钟，退化为讲座 | 人多显得「覆盖率高」 | 拆场次或改 Cohort；不发言者用会前书面提问补偿 |
| AI 先于显式化 | 先上助手，知识仍在人脑与聊天记录里 | 只会复述公开语料，一次答错口径即被全组织弃用 | 「上工具」比「写文档」看起来更像进展 | 高频重复问题清单 → 文档化 → 带 Owner 与更新时间 → 再接检索 |
| Sponsor 缺席却加辅导 | 反复加 1:1 时长，晋升仍不过 | 能力已达标者在一个晋升周期左右流失 | 「找不到 Mentor」与「晋升受阻」被当成同一种病 | 区分「谁教」与「谁提名」，后者归管理链与关键项目分配权 |

**最危险的两条**：**「1:1 承载一切」**与**「Sponsor 缺席却加辅导」**。前者是慢性的——它不会立刻出错，只会让三个季度后的 1:1 记录里全是进度同步，此时「成长没发生」已经无法归因到任何一次事故。后者在生产中的典型暴露方式是**离职面谈**：当事人在面谈里说「能力是涨了，但看不到机会」，而团队复盘时会发现过去半年所有的动作都是「加辅导时长」——诊断错误导致了全部投入打在错误的维度上（判定方法见 §7.3.3）。

第三条值得单列：**「AI 先于显式化」的暴露方式不是效果差，而是信任崩塌**。它的机制是单向的——AI 答对十次不会积累信任（用户认为那是应该的），答错一次编造的口径就会被截图传播，之后连正确的回答也不再被采信。因此它的修法必须在顺序上做，而不是在事后加强审核。

**这些反模式的共同成因**：它们都产生于「用最顺手的形式承接所有问题」。1:1 顺手、加时长顺手、上工具顺手——而正确的动作（分流、区分谁提名、先写文档）都需要先承认一个不舒服的判断，即当前维度的投入不会带来想要的结果。所以在辅导体系里，**诊断能力比辅导技巧更稀缺**。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 待辅导 4 人 → 12 人 | 1:1 全覆盖 + IDP | 容量见顶（单 Mentor 上界 1.5–4 人），1:1 被稀释成状态同步 | Group 打底 + 1:1 定向 | 新增主持人角色与议题收敛；1:1 笔记归档【经验】3–6 个月 |
| 12 人 → 30 人 | Group 打底 | 同一份共性内容被多批次重复讲，讲师杠杆不足 | Cohort + AI 答疑 | 教研设计是固定投入，且批次结束需保留轻量延续机制 |
| 单一团队 → 跨 BU | Buddy 靠熟人指路 | 熟人网络不跨团队，新人找不到人 | 制度化配对 + 轮换台账 | 需要 Owner 与台账；协作成本上台阶 |
| 同处一地 → 远程 / 异步 | 面对面 1:1 与顺手反馈 | 反馈延迟从小时级拉长到天级，OJT 旁听消失 | 书面化用语料 + 异步 1:1 + 更短的 Action Items 周期 | 显式化工作量前置，前期更慢【经验】1–2 个季度 |
| 稳态 → 技术换代 | 培训 / Cohort | 知识来源方向反转（新技术在人更年轻的一侧） | Reverse Mentoring（前提：心理安全已建立） | 双向都要学「公开承认不会」【经验】1–2 个季度 |

**跃迁的判据不是人数本身，而是「瓶颈位置是否已经移动」**：当主导成本从「Mentor 小时」迁移到「同一份知识被重复口头解释的次数」时，继续往 1:1 加人已无边际收益（成本项迁移表见 §7.4）。判断自己在哪一行，用 §7.3.1 的判定方法：数一数有多少主题正被不同 Mentor 分别解释。

**跃迁最好早于临界点发生**。上面表格里的每一档阈值（4 人、12 人、30 人）都是「上界」，而组织在临界点附近的表现是渐变的：1:1 不是在人数到 5 的那一天变质的，而是在某一次议程被进展占满之后再也回不去。因此切换的时机应当留出一个季度的过渡期——**等疼了再换，通常已经付出了一到两个季度的稀释成本**（【经验】：本书把这个过渡期定为一个季度，取自一次完整的 IDP 周期，无外部权威来源）。

### 3.7 自检清单

1. 最近 3 次 1:1 的记录里，「成长议题 / IDP」这一段是否出现过？三次都没出现，1:1 已经是状态同步。
2. 上一次 1:1 的 Action Items，本次是否逐条回顾过？（不回顾 = 承诺零成本）
3. 团队里「同一主题被 ≥2 个 Mentor 分别解释过」的问题清单有几条？（这些就是杠杆最该被抬高的位置）
4. 所有承担辅导角色的人，每周显性辅导时长加起来是否达到团队总工时的 **5%**？（【经验】阈值，见 §7.3.1；不足则任何模式选择都是空谈）
5. 每位 Mentee 的 IDP 五要素（主文件 §2.3）是否都有具体值？`review_due` 是否未过期？`action` 里有没有承接的项目名？
6. 最近 10 条反馈，从行为发生到反馈送达的间隔中位数是多少天？超过 7 天（【经验】：判定方法见 §7.3.2），反馈已难以锚回行为。
7. 每条反馈是否同时含情境、行为、影响三要素（SBI 完整度）？
8. 能力已达标但未被提名的人，除了 Mentor 之外，有没有一个掌握提名权的具体的人？
9. 派出的 OJT 任务是否同时满足**可观察、可分解、可复现**三条？三条缺一，反馈延迟优势不成立。
10. Group 单场人数是否 ≤ 12？超过则人均发言不足 5 分钟，退化为讲座。
11. 每月被问 ≥ 3 次的问题，是否已文档化并带 Owner 与更新时间？（3 次/月是「写文档比继续口答更省」的临界点【推算】，推导见 §7.5）
12. 新人问「这个口径以哪个为准」时，有没有唯一答案？没有唯一 Owner 的组合会在三个月内互相矛盾。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 差距是信息缺口 | Buddy + 文档 / AI | 信息类问题用关系承载会被重复消耗，边际成本为 0 的载体更合适 |
| 差距是技能缺口 | OJT + 周 1:1 | 反馈延迟最短，且「做过哪一级」可举证 |
| 差距是机会缺口 | Sponsor + 关键项目 | 名额不由 Mentor 掌握，加辅导时长不改变结果 |
| Mentor 可投入 ≤ 4 人份 | 1:1 全覆盖 + IDP/GROW | 容量足够时杠杆劣势不体现，个性化收益最大 |
| 待辅导 5–20 人 | Group 打底 + 1:1 定向 + AI | 1:1 容量见顶，必须把信息类问题移出 Mentor 小时 |
| 资深者跟不上技术变化 | Reverse Mentoring（先建心理安全） | 知识来源方向反了，反转信息流向比增加培训更省 |
| 同一问题被反复问 | 先文档化，再接 AI | AI 的上限由显式化覆盖率决定，与模型强弱无关 |
| 刚经历重组 / 裁员 | 先恢复心理安全，再谈模式 | 辅导要求人暴露「不会」，前提不成立时任何形式都退化为汇报 |
| 派出的任务不可观察 / 不可复现 | 退回 1:1 + Sponsor | OJT 的延迟优势依赖「做对没做对」能被及时看到 |
| 反馈总攒到评审才谈 | 拆到日 / 周粒度（SBI） | 延迟以月计则无法锚回行为，且与资源决策绑定会引发防御 |

> 本节小结：跨族看，决定用哪一族模式的**唯一那条约束是差距类型**（信息 / 技能 / 机会）——机会缺口用任何辅导形态都无法解决，选错族之后所有的优化都打在错误维度上；族内看，决定形态的是**人力杠杆与反馈延迟**（详见 §7.3.1、§7.3.2）。这也是那两条差距（系统设计、领导力）给不出的结论：它们不是两项待办，而是两族不同的机制。

> 💡 **思考锚点**：把你现在要辅导的人逐个归一次类——有几个的差距其实是**机会**缺口（缺的是名额和关键项目，不是信息或技能）？对这几个人，无论加多少 1:1 时长都不会改变结果，只有 Sponsor 这一族动得了；再看被反复问的问题是否落在**信息**缺口上，若是，先文档化再接 AI，因为 AI 的上限由显式化覆盖率决定，与模型强弱无关。
