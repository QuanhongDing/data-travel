## 4. 改进措施

[§ 3](11-team-topology-section-3-sec3.md) 讲了四种团队类型的结构：它们各自被什么约束逼出来、代价是什么、什么时候会失效。本节讲的是把结构放进一个真实组织时要动哪些东西——具体到三个问题：**Stream-Aligned Team 的边界怎么切、Platform Team 怎么搭才不变成工单队列、以及三类认知负荷里哪些该降、哪些该投、哪些只能接受。**

先立一个前提，否则后面三条改进措施会被用错地方。认知负荷不是一个总量，它由三部分构成，而三部分对应**三种不同的动作**【经验，三类划分出自 Team Topologies（Skelton & Pais）对 Cognitive Load 的借用，本节沿用其分法；下面「动作」一列是工程落地的归纳，不是原著给的处方】：

| 负荷 | 来源 | 该做什么 | 用错动作的症状 |
| --- | --- | --- | --- |
| **Intrinsic（内在）** | 领域本身的复杂度：一致性语义、口径定义、监管要求 | **接受**它，并为它配人（Complicated-Subsystem Team 或领域专家） | 把它当成"环境复杂"去平台化，结果平台封装了一个本不该被封装的领域判断，业务团队失去解释权 |
| **Extraneous（外在）** | 环境带来的复杂度：部署、权限、环境申请、监控接入、工单流程 | **降低**它，主要手段就是平台化（§3.2.2） | 接受它，于是每个业务团队各自重复一遍——这正是平台团队存在的理由 |
| **Germane（关联）** | 学习与成长本身带来的负荷：理解新机制、建立心智模型 | **投资**它，配 Enabling Team 与轮岗 | 把它当浪费去砍，团队短期交付变快、长期只会照着现有流程做 |

判据很直接：**一件事如果"换一个团队来做还是同样的复杂度"，它是 Intrinsic；如果"换一套工具或换一个平台就没有了"，它是 Extraneous。** 这条判据决定了它该进平台、还是该留在业务团队——把 Intrinsic 塞进平台，等于把领域判断权收了上来；把 Extraneous 留在业务团队，等于让每个团队各交一遍学费。

### 4.1 Stream-Aligned Team 怎么设计

**切分判据只有一条：这个团队能不能独立交付一个用户可感知的变化。** 能，它就是一个 Stream-Aligned Team；不能，它就是一个按技术层划分的功能组，无论它叫什么名字。这条判据比"团队规模多大""叫什么名字"都更能区分真假。

#### 从价值流切，不从技术层切

最常犯的切法错误是**按技术分层**：数仓组、ETL 组、报表组、算法组。这种切法下，任何一个用户可感知的变化（比如"新增一个复购率指标"）都要穿过四个团队，每个团队各自排队、各自排期，最后没有任何一个团队对"这个变化多久能上线"负责。**跨团队交付的排队时间会主导总交付时间**，而排队时间不体现在任何团队的绩效里。

正确的切法是从价值流切：交易域、用户域、风控域、供应链域。每个域内自带建模、加工、指标、服务的能力，端到端对"这个域的数据能不能用"负责。

| 切法 | 一个用户可感知变化的交付路径 | 排队次数 |
| --- | --- | --- |
| 按技术层切（数仓/ETL/报表/算法） | 需求 → 数仓组 → ETL 组 → 报表组 → 上线 | 3–4 次跨团队排队 |
| 按价值流切（交易域/用户域/…） | 需求 → 域团队内部完成 → 上线 | 0–1 次（只在依赖共享平台时） |

#### 必须自带的能力清单

一个 Stream-Aligned Team 要真的端到端，下面每一项都要在团队内部有归属；缺哪一项，就会长出一个外部依赖，而外部依赖的等待时间最终由这个团队承担：

| 能力 | 缺了会怎样 |
| --- | --- |
| 需求理解与优先级 | 变成"接单团队"，做的是别人定义好的任务，无法对自己负责的结果负责 |
| 建模与口径定义 | 口径由外部团队定义，域内只能消费，出现分歧时要跨团队仲裁 |
| 开发 | 核心能力，不能外包 |
| 测试与数据质量校验 | 质量责任转移给下游使用方，问题发现时点推后 |
| 部署与发布 | 每次上线要排队等另一个团队操作，发布频率被外部约束 |
| 运维与 on-call | 出了问题没有责任主体，只能靠"找平台团队看看" |

**on-call 归属是最容易被跳过、也最能说明问题的一项**：如果一个域的数据出了问题，第一个被叫醒的人不在这个团队里，那这个团队就还没有真正对这条价值流负责。

#### 规模

规模没有普适数字，它的上限由两条约束决定：**团队内部的信息传递是否能靠不正式的方式完成**，以及**认知负荷是否超过团队的承载**。规模超过前者，沟通开始需要制度（多一次同步会、多一份周报）；超过后者，团队会自发地内部分裂成子团队，但组织结构图上看不出来——这时的症状是"团队开会总有人不参与"，而不是"团队太大"。

**判断该不该拆的信号，是交付路径而不是人数**：如果一个团队里已经出现了两条互不相关的交付路径（比如同时在做交易域和风控域，且两者没有共同的验收标准），那它就该拆成两个 Stream-Aligned Team，无论现在多少人。

#### 落地步骤

1. **列出当前组织里所有"用户可感知的变化"的交付路径** —— 每一条从提出到上线，标出穿过了哪些团队、在哪一步排队。
2. **找出排队最集中的那一段**：如果多条路径都卡在同一个团队（通常是数仓组或平台组），问题不是团队太小，是切法错了。
3. **按价值流重切边界**，画出目标组织结构，与上一步的路径一一对照：重切之后，每条路径的跨团队次数应该显著下降。
4. **对照"必须自带的能力清单"逐项点名责任人** —— 特别是 on-call。这一步如果跳过，重切只是改了组织结构图。
5. **做一次 Inverse Conway 检查**（见 §4.4）：目标架构的模块边界，与第 3 步切出的团队边界，是不是同构的？不同构的地方，架构会在半年后被组织结构拉回去。
6. **设定回看时点**：重切之后 1–2 个季度，重新走一遍第 1 步。路径有没有缩短是这件事成没成的唯一判据。

#### 常见失败

- **只改组织图，不改能力归属**：团队重切了，但发布仍要等平台团队排队、on-call 仍是全公司轮值。结果是新团队多了一层汇报关系，交付路径没变。
- **按技术层重切**：把"数仓组"改成"数据域一团/二团"，内部仍按建模、加工、报表分工。名字变了，切法没变。
- **把 Intrinsic 也一起切走**：为了让团队边界看起来干净，把口径定义权收归一个中心团队。这恰恰把领域复杂度从业务团队搬到了中心团队——那里的人不具备领域上下文，最终会写成一份所有域都不适用的规则。

### 4.2 Platform Team 怎么搭建

Platform Team 的全部理由是**把 Extraneous 负荷从业务团队搬到平台团队**（§3.2.2）。这个理由同时决定了它的成功判据：**业务团队自己动手能完成的事，是不是变多了。** 不是平台上线了多少功能，也不是平台的调用量。

#### "平台即产品"的三条硬约束

"把内部用户当客户"这句话被引用得太多，以至于失去了可执行性。它落到三个能检查的地方：

| 约束 | 可检查的表现 | 反例（都能观察到） |
| --- | --- | --- |
| **有 Owner 与路线图** | 平台有公开的当前版本、下一版计划，以及明确的功能取舍说明 | 平台的功能列表由各业务团队的需求单拼接而成，没有任何取舍 |
| **有 SLA，且被自己承认** | 平台可用性、工单响应时限写成公开承诺 | 只有"我们会尽快处理"，没有时限，也没有违约记录 |
| **有变更公告与破坏性变更流程** | 破坏性变更提前公告，给出迁移期与迁移工具 | 业务方在故障发生后才知道平台改了行为 |

#### 最小可用平台：先做哪三件事

平台最容易犯的错是**先做功能、后做自助**。功能清单越长，业务团队要走的人工流程越多，Extraneous 反而上升——因为每一件功能都带一套新流程。

顺序应该是反过来的，先把这三件事做掉，它们决定了平台是"降低负荷"还是"新增负荷"：

1. **自助开通**：业务团队能自己在无人协助的情况下把资源开出来（建表、配权限、接监控）。这一条的判据是"新同学能不能在没有任何人帮助下走完一遍"。
2. **状态可观测**：业务团队能自己看到自己那条链路的健康度——而不是先问平台"你们那边是不是有问题"。
3. **明确的兜底通道**：自助走不通时，有一个写清楚了响应时限的人工通道。这条不是可选项：没有它，业务团队遇到自助流程的边界情况时会直接绕过平台。

#### 反模式：工单队列

平台最典型、也最难被发现的失败形态是**退化成工单队列**：业务团队提需求，平台团队排期、开发、交付，业务团队拿到结果——平台在结构上变成了一个外包团队。

它的成因是合理的：**接单比做产品更容易度量，也更容易在短期内让所有人满意**。业务方得到了他们点名要的东西，平台方有了可交付的产出。代价要过很久才显现：

- 平台团队的需求来源变成"谁喊得响"，而不是"哪一类摩擦最普遍"；
- 每个业务团队都为自己的特殊情况提一次需求，平台逐个实现，能力泛化不出去；
- 业务团队不学平台的用法（因为不需要学，提工单就行），Extraneous 实际没有下降，只是**从业务团队转移到了平台团队的队列里**。

**判别信号很具体**：看平台团队过去一个季度的需求列表，如果其中大部分是**单个业务方点名要的特定功能**，而很少有"这一类摩擦在所有团队里都存在、我们一起解决"的条目，那它已经在工单队列上了。

#### 该怎么度量平台团队

| 度量 | 为什么用它 | 为什么不用"平台功能数" |
| --- | --- | --- |
| **自助完成率**：业务方的需求里，有多少比例完全不经过人工协助就完成了 | 直接对应"Extraneous 有没有真的降下来" | 功能数增加时可以完全不自助，甚至更依赖人工 |
| **从需求到上线的时长**（对使用平台的那类需求） | 排队时间是平台价值的最终体现 | 功能数与排队时间没有必然关系 |
| **平台自身的变更频率** | 平台也在演进，还是已经冻结 | 冻结的平台功能数最高 |
| **业务团队绕过平台的比例** | 绕过的部分说明平台在哪些场景下不适用 | 看不到，功能数完全掩盖这一点 |

前两项需要平台团队自己采集并公开——**如果一个平台团队拿不出业务方的自助完成率，它大概率还在工单队列模式**，因为排队模式天然不看这个数。

### 4.3 工具链与平台

**团队拓扑设计阶段**：

- **Team Topologies 官方资料**（Skelton & Pais 的站点与书籍）：四种团队类型与三种交互模式的原始定义，是本节所有术语的来源【公开，Team Topologies, Skelton & Pais】。
- **组织结构图工具**：Miro / FigJam / Excalidraw —— 用于画目标组织结构与交互模式，而不是画汇报关系。**判据**：图上标的是团队之间的交互模式（Collaboration / X-as-a-Service / Facilitating），还是只有汇报线？只有汇报线的图对本节的方法没用。
- **服务目录与开发者门户**：Backstage（Spotify 开源，已进入 CNCF）是这一类里公开材料最完整的一个，它的核心是"服务目录 + 软件模板 + 文档"三件套，与"自助开通"那条约束直接对应【公开，Backstage 公开仓库与文档】。同类还有若干商业内部开发者平台产品，选型判据与 §4.2 的三条约束一致：**能不能自助、状态可不可观测、变更有没有公告流程**，而不看功能清单长度。

**Team API 文档**：

- **API 文档工具**（ReadMe / Mintlify / Redocly 等）：Team API 要写成能被检索的文档，而不是聊天记录里的一句承诺。
- **文档协作平台**（Confluence / Notion / 内部 wiki）：**用途要写清楚才有价值**——如果它承载的是"决策与接口承诺"，它就必须有版本与 Owner；如果只是知识随笔，不要指望它承担接口契约的职责【经验】。

**AI 辅助的边界（2024+）**：

这一类工具确实存在且被广泛使用，但**它们改变的是通道成本，不是判断**（同本章 [§ 5](11-team-topology-section-5-ai.md) 的讨论）：

- **可用于**：把已有的会议记录、文档、工单线程压成摘要；把跨语言的组织资料翻译成可读形式；让新人"先查再问"，把重复问答从人转到检索。
- **不可用于**：替团队判断边界该怎么切、替平台判断某个需求该不该做。这两件事的输入是组织上下文与取舍，不在任何记录里。

**一个常被忽略的前提**：AI 辅助的前提是"记录已经存在"。在团队边界刚重切完、协作模式还没稳定下来的阶段，记录本身是缺失的（新的接口承诺还没写下来、新的决策路径还没形成习惯），此时引入摘要工具会把"空档"压成看起来完整的文本——**空档比错误更难被发现**。

### 4.4 代码 / 示例

#### 示例 1：Inverse Conway Maneuver

Conway's Law 说的是"组织结构决定系统架构"；反演（Inverse Conway Maneuver）是主动利用这条规律：**先设计你想要的架构，再按这个架构去调整组织**，让组织结构把架构推过去，而不是反过来被拉回来。

```text
目标架构：企业级数据湖仓一体
- 数据源层（Kafka / 数据库）
- 数据湖层（Iceberg / Delta）
- 数据仓库层（数仓分层建模）
- 服务层（RAG / BI / 报表）
- 治理层（数据治理 / 安全）

Inverse Conway Maneuver：
1. 识别 Bounded Context：数据源 / 数据湖 / 数仓 / 服务 / 治理
   —— 这一步的产物是"界限在哪"，不是"分几个组"
2. 设计组织结构：让团队边界与上一步的边界同构
   - 数据源     → Stream-Aligned Team（对齐某条业务流）
   - 数据湖     → Platform Team（提供存储与表格式能力，自助开通）
   - 数仓建模   → Complicated-Subsystem Team（建模专家，深但不广）
   - 数据服务   → Stream-Aligned Team（直接对接消费方）
   - 数据治理   → Enabling Team（赋能为主）+ 一个小的治理 Owner 组
3. Team API：每个团队写清楚提供什么、怎么消费、SLA 是什么
4. 持续调整：架构演化时同步调整组织，而不是只调整文档
```

**这张图最容易出错的地方是第 2 步的"数据湖 → Platform Team"**：如果把数据湖做成 Platform Team，而数仓建模做成另一个团队，那么"新增一张宽表"这件事就要跨两个团队，而它恰恰是最频繁的交付。**同构检查的用法正是发现这类错配**：架构上频繁交互的两个模块，如果分属两个团队，就一定会有排队。

#### 示例 2：AI 辅助团队拓扑设计 Prompt

```text
你是资深组织架构专家。请基于以下业务情况，设计 Team Topologies。

业务情况：
- 业务规模：5 个 BU
- 数据规模：PB 级
- 业务流：电商、金融、广告、物流、客服
- 技术栈：关系型库 / 消息队列 / 批处理 / 表格式 / 向量检索 / LLM
- AI 能力：RAG / Agent / 多模型编排

要求：
1. 设计 4 种团队类型（Stream-Aligned / Platform / Enabling / Complicated-Subsystem）
2. 明确每个团队的边界、职责、SLA
3. 设计 Team API
4. 评估 Cognitive Load：逐项判定属于 Intrinsic / Extraneous / Germane，并给出对应动作
5. 指出这份设计里最可能出现的两处错配（哪些高频交互的模块被切到了不同团队）
```

**这个 Prompt 的用法有边界**：它产出的是**一份可被评审的初稿**，不是结论。第 4 步和第 5 步是它真正有用的地方——它们把"这个设计哪里会出问题"显式化出来，供人讨论。把第 1 步的产物直接当成组织结构，等于让一个不掌握组织上下文的工具替你做取舍。

---

> 本节小结：三条改进措施的次序不能颠倒——**先把 Intrinsic 与 Extraneous 分开（否则会改错地方），再切流对齐团队的边界（否则改的是名字），最后搭平台（否则平台会把错误切法固化下来）**。其中最容易漏掉的一步是"能力归属逐项点名"，尤其是 on-call：它不体现在组织结构图上，但它决定了团队是不是真的对这条价值流负责。
