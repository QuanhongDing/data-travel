## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

组织形态没有 release note。这是本主题与数据目录、数据血缘、数据 API 网关那几个主题最大的差别：那里可以用「某版本是否 GA、release note 里有没有列出这个特性」判定成熟度，这里没有版本号可查。

**本节因此新增了一组对照**：Team Topologies 2nd Edition（2024）、MIT Sloan 的 AI 治理团队结构（2024）、Stanford 的 AI 时代 Conway's Law（2024）这类材料属于「有人讲过」；NIST AI RMF 1.0（2023）、ISO/IEC 42001（2023）、EU AI Act（2024 年生效、分阶段适用）属于「有人必须照做」——本章 [§7.5](11-team-topology-section-7-sec7.md) 正是把这些文本作为决策树第 1 层「必须对外举证」那一分支的依据。把两类材料混进同一张「最新进展」清单，读者据此排组织路线图就会踩空——**因为两者对组织行为的约束力差一个数量级**：前者可以在半年后毫无后果地不再被提起，后者会出现在审计清单里。

**本节对 §2.1 的 L1 判据做了如下修正：第①条「已 GA 且有正式 release note」在本主题改为「有正式发布、带年份、可公开检索的正式文本——规范 / 标准 / 监管文本，或该形态的正式出版物（含提出该形态的组织或作者本人的正式著作）」；第②③条（第三方非提出方的公开生产实践、接口稳定）不变，且必须同样写清来源。** 理由是组织形态不存在「GA 时刻」与版本号：若强行套用①，本主题下所有方向都会因为「没有 release note」而无差别地落入 L3，评级失去分辨力；反过来，若只凭「有人在博客里说他们这么做了」就判 L1，任何趋势都能判 L1。**① 允许提出者本人的正式著作不会把评级放水**——独立性由第②条承担：提出者自己的书只能证明「这个形态被正式提出过」，永远不能单独把一行送进 L1。本节 §5.2 的评级与这条修正逐条一致，没有在任何单格里另立标准。

第二个要分清的是**「组织为 AI 而变」与「用 AI 来设计组织」**。前者的产物是团队边界、负荷归属、举证责任，做错了门禁会失效；后者的产物是文档检索、组织图谱、结构建议，做错了没人赔钱。

**两者不能用同一套成熟度语言，也不能排在同一个路线图里**：一类要审的是「谁负责」，另一类要审的是「维护得及不及时」。把后者写进前者的清单，会让一份本该严肃的组织方案看起来像是技术选型。

第三个要分清的是**AI 到底改变了哪条机制**。本主题里只有三条是真的：

- **① 新增了一类「每用一次都要重付」的负荷**——业务侧的提示、口径、领域评测样例。这类负荷**不可平台化**，因为它的成本随业务变化而持续产生，收走它等于收走业务判断。
- **② 新增了一类「付一次就能共享」的负荷**——推理与检索基础设施、评测集、审计留痕。这类负荷**可以平台化**，因为它的建设成本主要由「有没有人建过一次」决定。
- **③ 把举证责任从可选项变成硬约束**——模型行为是概率性的，「我们测过了」不再是可举证的证据，只能靠留痕与影响记录。

凡是落不到这三条上的方向，都只是接口改良，不是架构变化。

判据与评级如下表（**级别栏按 §2.1 的 L1/L2/L3 定义，其中 L1 的第①条已按上文修正；判据栏写的是读者可以自己核验的东西**）：

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| AI 平台团队成为核心枢纽 | L2 | 平台这一**角色**由 Team Topologies（Skelton & Pais, 2019）正式提出；第三方实践存在，但针对的是「平台工程」而不是「AI 平台」这一具体形态（DORA 年度报告近年各期持续观察平台与自服务能力，各年份口径不同；具体从哪一期开始覆盖，请按其官网发布的历年报告清单逐年核验）；接口不统一——同一件事在不同组织里叫 AI 平台 / MLOps 平台 / 算法工程 | PoC：先数「同一 AI 能力被几个团队各实现了一遍」，再决定建不建 |
| AI 治理团队作为 Complicated-Subsystem | L2 | 【公开】①正式规范带年份：NIST AI RMF 1.0（2023）、ISO/IEC 42001（2023）、EU AI Act（2024 年生效、分阶段适用）；③接口稳定：其对外接口是「留痕与评测证据」，内容项（影响评估、风险登记、人工监督、事件记录）由规范本身规定；②不满足——这些文本公开的是**对组织的要求**，而本行评的是**团队形态**，未见指名的第三方组织公开描述其治理团队（ISO/IEC 42001 的认证机构公示名录属组织登记文件，不构成第②条） | PoC：先把门禁与留痕落到发布流程上，再按编制可行性决定设不设常设团队 |
| AI 时代的 Conway's Law 反演 | L3 | 反演方法本身有正式出处（Team Topologies, 2019；主文件 §2.3 给出 5 步法），但那是既有方法；「AI 时代需要一套不同的反演方法」没有正式发布方，也没有第三方实践 | 记录即可；反演的第一步仍然只是「先明确目标架构」 |
| 认知负荷新增「AI 治理 / 合规 / 风险」维度 | L2 | 认知负荷三分法出处明确（Sweller, *Cognitive Load During Problem Solving*, Cognitive Science, 1988）；规范侧间接支持「治理负荷要有独立归属」；但怎么把它测出来没有公开共识 | PoC：先测流对齐团队每月花在 AI 适配与环境类工作上的时间占比 |
| AI Enabling Team 赋能业务 | L2 | Enabling / Facilitating 模式有正式出处（2019）与第三方实践（[§7.2](11-team-topology-section-7-sec7.md) 已列 ING 自 2015 年起的公开转型材料）；「AI 专用 Enabling」的交付物定义没有公开共识 | PoC：交付物定义为「对方能独立复现」，用滞后指标（对方独立完成率）验收 |
| Team API 的 RAG 化 | L3 | 无正式发布方、无第三方生产案例 | 观望；Team API 该写还得写，但不必做成检索系统 |
| 组织结构的 GraphRAG | L3 | 无正式发布方、无第三方生产案例 | 观望 |
| AI 辅助拓扑设计 | L3 | 无正式发布方、无第三方生产案例 | 观望；边界决策仍须由人给目标架构 |
| Team API 标准化成为跨团队协作基础 | L2 | Team API 由 Team Topologies（2019）正式提出，主文件 §2.3 给出示例字段（服务清单 / 每项服务的 SLA 与 owner / 交互模式 / 文档）；跨组织的公开规范不存在，因此标准化只能在自己组织内定义 | 现在就该做：抽查 3 个接口，把 SLA 与责任人补上 |

> 表后说明：本主题下**没有方向能判 L1**。最接近的是「AI 治理团队作为 Complicated-Subsystem」：它的①③都成立（约束来自组织外部、有正式文本带年份；对外接口是规范本身规定的留痕与评测证据，不随任何厂商产品形态变化），卡在第②条——规范公开的是「组织应当建立什么流程、保留什么材料」，而本节评的是**团队形态**（不挂在交付链上、承担对外举证责任）；从「组织获证」推不出「设了这样一个团队」，而指名某个第三方组织公开描述其治理团队形态的材料，本节未核到。其余方向不够格的原因分三类：一类是**形态外延不统一**（AI 平台、AI Enabling），同一句话在不同组织里指的不是同一件事，因而形不成稳定接口；一类是**只有主张没有实践**（AI 时代的反演新方法、三种「用 AI 设计组织」的做法）；第三类是**缺可核验的度量口径或跨组织规范**（认知负荷新增的「AI 治理 / 合规 / 风险」维度卡在「怎么把它测出来没有公开共识」，Team API 的跨组织标准化卡在「跨组织的公开规范不存在」）。三类合起来覆盖其余 8 行。

**「AI 很重要」不是判据，「这件事有没有外部约束、有没有第三方在做、接口稳不稳」才是判据。** 这也解释了为什么本节把 L3 的三种「用 AI 设计组织」的方向留着不删：它们不是错的，只是现在还不能被规划——把它们删掉，读者反而会在别处重新捡起来。

主文件给了三个可观测代理（FlowEfficiency、认知负荷配比、团队类型配比），本节的所有「现在该做什么」都落在这三个代理上，而不是落在主观感受上：

| 代理 | 主文件出处 | 本主题下用它判断什么 |
| --- | --- | --- |
| FlowEfficiency = ValueStreamTime / LeadTime（健康 ≥ 25%，【经验】区间） | 主文件 §2.2 | 平台化之后等待是不是变短了；若变长，说明平台成了新的排队点 |
| 认知负荷配比（Intrinsic 30–50% / Extraneous ≤ 30% / Germane 20–40%，【经验】区间） | 主文件 §2.2 | AI 适配负荷落在哪一类；落进 Extraneous 就该被平台化，落进 Intrinsic 就只能接受 |
| 团队类型配比（Stream-Aligned 60–70% / Platform 10–15% / Enabling 5–10% / Complicated-Subsystem 10–20%，【经验】区间） | 主文件 §2.2 | 有没有足够的编制承载新增的那份责任；凑不出这个比例就不要设常设团队 |

为什么要绕这么远说「接口」？因为本节评的每一项成熟度，最终都要落到同一个可核验对象上：**Team API**。它在本主题里承担的角色，与「字段级血缘」在血缘主题里承担的角色完全相同：

- **它是唯一能被外部核验的东西**：团队边界对不对没人能证明，但「这个接口有没有 SLA、有没有责任人、破坏性变更怎么通知」是可以抽查的（判定方法见 [§7.3.3](11-team-topology-section-7-sec7.md)）。
- **它是「组织形态已落地」与「组织形态只在纸上」的分界线**：没有 Team API 时，跨团队协作事实上仍是 Collaboration，不论文档里叫什么。
- **它不依赖任何 AI 能力**：这是本主题里唯一一件今天做、明天就有收益、且不需要等任何前沿成熟的事。

### 5.2 演进方向逐条拆解（核心节）

本节 9 个方向里，7 个在这里归成 4 组展开，其余 2 个（评级见 §5.1 表第 3、9 行，接口形态与责任归属见 §5.3 接口表）不在此展开。分组口径是「AI 从组织里拿走了什么、又塞进了什么」：前三组是「组织为 AI 而变」，第四组是「用 AI 设计组织」。

每组的机制问题是同一个：**这份负荷由谁承担、它是付一次还是每用一次都要付。** 逐条对照如下：

| 方向 | 它处理的是哪一类负荷 | 付一次还是每用一次 | 评级由什么决定 |
| --- | --- | --- | --- |
| AI 平台团队 | 可共享的基础设施与评测 | 付一次（O(1) + O(消费)） | 形态外延是否统一、有无第三方案例 |
| AI 治理团队 | 举证与留痕 | 付一次，但必须持续运行 | 是否受外部规范约束、能否核验 |
| AI Enabling | 业务侧的适配与口径 | 每用一次都要重付 | 交付物是否可定义为「对方的能力」 |
| 用 AI 设计组织 | 组织信息本身 | 付一次，但会过期 | 有没有人能对新鲜度负责 |

#### 5.2.1 AI 平台团队（Platform 角色）：把「付一次就能共享」的负荷收敛

- **旧做法与它的卡点**：每个业务团队各自接模型、各自搭向量检索、各自维护评测脚本。卡点不是「没人会做」，而是**重复实现成本 ∝ 团队数**：同一件事被 k 个团队各做一遍，而 AI 侧的重复实现比一般基础设施更贵——它还包含持续变化的模型接入方式与评测口径，等于把「会过期的知识」复制了 k 份。
- **AI 改变了什么机制**：它把一部分 AI 负荷的成本函数从 **O(k)（随团队数增长）变成 O(1) + O(消费)**——推理托管、检索、评测基础设施、审计留痕的建设成本主要由「有没有人建过一次」决定，而不是由调用量决定。
- **由此得到的**：因为存在这一半「付一次」的负荷，**流对齐团队可以不再自建它们**，从而腾出带宽去做只有它们能做的事（业务口径、领域评测样例、业务侧适配）。这是平台化在本主题里唯一的机制收益；一致性、复用率都是这条的下游结果。
- **由此付出的**：
  - **① 平台成为新的排队点**：业务侧要为它的优先级等待，而平台的优先级由平台自己的度量决定（[§7.3.4](11-team-topology-section-7-sec7.md)）。
  - **② 平台能收走的只有「付一次」那一半**：如果它把业务口径与提示适配也收走，它就在事实上接管了业务判断，退化成审批部门（[§3.3 反模式 2](11-team-topology-section-3-sec3.md) 与 [§7.7「先建平台，再找消费者」](11-team-topology-section-7-sec7.md) 是同一条失效路径）。
  - **③ 形态不可比**：同名不同物导致跨组织的经验无法被估价与迁移——你无法从别人「建了 AI 平台」这件事推出任何关于投入与产出的结论。
- **证据与来源**：【公开】平台角色由 Team Topologies（Skelton & Pais, 2019）正式提出；平台与自服务能力同交付性能的关联被 DORA 年度报告近年各期持续观察（DORA，各年份的覆盖范围与口径不同，此处不引具体百分比；具体从哪一期开始覆盖平台与自服务，请按其官网历年报告清单逐年核验）。本主题下「AI 平台团队」这一**特定形态**不满足第②条（第三方非提出方生产案例）。
- **成熟度**：**L2** —— 平台角色本身有正式出处与第三方实践，但 AI 专用形态边界不统一、第②条不满足；可做 PoC，不要做核心依赖。
- **判定方法**（自己核验这一步做不做）：统计同一 AI 能力被几个流团队各实现过一遍（记作 k），按 [§7.4 推算 ②](11-team-topology-section-7-sec7.md) 的回本区间决定；k 小于区间下界时，先做共享库（InnerSource）而不是建团队。

平台在这条线上的边界，可以用一张负荷分半图说清（这是示意，不是任何组织的架构图）：

```text
                AI 相关负荷总集
        ┌──────────────┴───────────────┐
   可共享的一半                     不可共享的一半
   推理 / 检索 / 评测集 / 留痕        业务口径 / 提示适配 / 领域评测样例
   成本 ∝ 有没有建过                成本 ∝ 用了多少次 × 业务变化频次
        │                                 │
   收进 Platform（角色）            留在 Stream-Aligned（角色）
   手段：自助入口 + SLA             手段：Enabling 传递能力，代码不代写
        │                                 │
        └────────► 二者都不写业务判断 ◄────┘
   判据：平台的服务清单里是否出现「业务口径」这一类
```

#### 5.2.2 AI 治理团队（Complicated-Subsystem 角色）：把举证责任收敛到「有归属的门禁」

- **旧做法与它的卡点**：治理挂在平台团队里兼职，或摊在每个业务团队身上。卡点不是「没人管」，而是**门禁被业务节奏压过去**——兼职的门禁在冲突时永远让位于交付。AI 场景把这件事放大了：模型行为是概率性的，「我们测过了」不再是可举证的证据。
- **AI 改变了什么机制**：它把治理从**靠内部共识维持的事**变成**由组织外部规范要求、必须留痕举证的事**——约束的来源从「我们觉得该管」变成「有人要求我们证明」。这是本主题唯一一条真正改变了约束来源的机制。
- **由此得到的**：因为外部规范要求组织能回答「风险如何评估、谁批准、上线后如何监控、事件如何记录」，所以**必须有一个不挂在交付链上、且有对外举证责任的团队**——这正是 Complicated-Subsystem 角色的定义（主文件 §2.1），也是 [§7.5 决策树第 1 层](11-team-topology-section-7-sec7.md) 把「必须对外举证」排在第一个分支的原因。
- **由此付出的**：
  - **① 它与业务流的节奏天然冲突**：它的产出是「拦住」而不是「交付」，冲突只能靠制度解决，靠文化解决不了。
  - **② 举证材料若靠人填表，就会退化成填表部门**：填出来的表在真出问题时证明不了什么，而流程成本照付。
  - **③ 它必须长期对抗「这次能不能先上」**：这要求它的汇报路径独立于业务线，而这条路径在组织里通常最不受欢迎。
- **证据与来源**：【公开】NIST AI RMF 1.0（2023）、ISO/IEC 42001（2023）、EU AI Act（2024 年生效、分阶段适用）都是对组织提出角色与留痕要求的正式文本。**但第②条不满足**：这些文本公开的是「组织应当建立什么流程、保留什么材料」，本节评的却是「是否存在一个不挂在交付链上、承担对外举证责任的团队」——从组织获证推不出团队形态；ISO/IEC 42001 的认证机构公示名录属组织登记文件，只能核验「某组织建立了 AI 管理体系」，不能充当第②条。本节未核到指名第三方组织公开描述其 AI 治理团队形态的材料。
- **成熟度**：**L2** —— ①正式规范公开且带年份、③对外接口由规范本身规定（见上）都成立，因此不是 L3；但②不满足（登记文件不是第三方生产案例，获证也不证明团队形态），所以不能排进路线图：可以做门禁与留痕的试点，不要按 L1 设常设独立编制。
- **判定方法**：检查你的门禁判据是否写在**发布流程**里（而不是写在文档里），以及留痕是否是结构化、可自动生成的——两条都不成立，说明举证责任没有真正落地。

治理团队的接口不要写成「与业务协作」，而要写成可核验的三项：

| 接口项 | 形态 | 谁负责失败 |
| --- | --- | --- |
| 变更门禁 | 发布流程中的自动检查（影响评估是否齐备、是否触及高风险用途） | 治理团队定判据；交付团队供材料 |
| 留痕 | 结构化记录（模型版本、评测结果、审批人、上线时间） | 治理团队 |
| 事件回溯 | 按记录重建「这一版为什么会这样」 | 治理团队；无记录即视为门禁失效 |

三个子团队——AI 治理（合规、风险、审计）、AI 安全（Prompt 注入、数据泄露）、AI 公平性（偏见检测、可解释性）——在本节不各占一行，而是全部落在上表的三项接口上：合规与风险审计落在「变更门禁」与「留痕」；Prompt 注入与数据泄露落在「事件回溯」，并在门禁里加一道攻击面检查；偏见检测与可解释性落在「留痕」中的评测结果这一项。**合并的理由是评级本身**：三者在成熟度上卡在同一条——被评的是**团队形态**，而指名第三方组织公开描述其治理 / 安全 / 公平性团队的材料都不存在，分开列只会得到三个完全相同的 L2；而它们在机制上处理的又是同一件事——把「模型行为不可举证」变成可留痕的流程。反过来说，门禁与留痕若不覆盖安全与公平性，留痕就答不上「这一版为什么会这样」。

门禁分流的形态与 [§7.5 决策树第 1 层](11-team-topology-section-7-sec7.md) 给出的判断一致——**治理不挂在业务流的交付链上，而挂在门禁上**：

```text
提交一个使用模型的变更
        │
  ① 自动跑影响与风险检查
      · 用途是否落在高风险清单里
      · 影响评估 / 评测结果 / 数据来源记录是否齐备
        │
  ② 按结果分流（判据要对交付方公开，不能口头解释）
      低风险且材料齐备        → 放行，自动留痕
      高风险或材料缺失        → 阻断，要求补齐材料 + 指定审批人
      用途超出既定适用范围    → 阻断 + 升级（这一档必须由治理团队裁决）
        │
  ③ 上线并写入结构化留痕（模型版本 / 评测结果 / 审批人 / 时间）
──────────────────────────────────────────────
关键：门禁的判据写在流程里 → 每次变更必须正面回答风险
      门禁的判据写在文档里 → 没人看，等于没有治理
      留痕由人填            → 出问题时证明不了什么
```

治理团队**不该**做的事情（三件最容易越界的事）：

- **不接手交付责任**：一旦它替业务团队补材料、改设计，它就变成外包，判据也随之失去独立性。
- **不做业务判断**：它判「风险是否可以接受、材料是否齐备」，不判「这个功能值不值得做」。
- **不靠文化运行**：门禁必须自动化且判据公开；靠「大家自觉」的治理在第一次紧急上线时就会失效。

#### 5.2.3 AI Enabling 与认知负荷：把「每用一次都要重付」的负荷留在流对齐团队，但教会他们付

- **旧做法与它的卡点**：认知负荷总量没变——团队原来管 K8s、权限、观测、容量，现在还要管推理配额、提示适配、护栏、评测样例。卡点是**负荷超限后产出与士气同时下降**（主文件 §2.2 的三分类与经验区间），表现为「AI 功能做出来了，但没人敢让它上线」。
- **AI 改变了什么机制**：它同时做了两件相反的事——把一份**可共享的**负荷从流对齐团队身上拿走（§5.2.1），又把一份**不可共享的**负荷塞给他们。对后者，唯一可行的手段是**把单位成本降下来**，而降低单位成本靠传递能力而不是代劳——这正是 Enabling 模式（Facilitating 交互模式）的定义。
- **由此得到的**：因为 Facilitating 模式的产物是**对方的能力**而不是自己的产出，所以 AI Enabling 的正确交付物不是「帮他们把 Agent 做出来」，而是「业务团队自己能做业务侧的适配与评测」；也正因为如此，**Enabling 的验收必须是滞后指标**（对方独立完成率），否则它会理性地延长赋能期（[§7.3.4](11-team-topology-section-7-sec7.md)）。
- **由此付出的**：
  - **① 收益在季度考核里看不见**：滞后指标天然吃亏，而赋能期的编制要立刻付。
  - **② 编制可能根本凑不出来**：Enabling 在全员中占 5–10%（主文件 §2.2 的配比区间【经验】），50 人以下的组织凑不出这个团队，强行设只会变成「一个人兼职教所有人」。
  - **③ 两种错位的口号都会把负荷推错方向**：「AI 的事都该平台做」会导致平台接管业务判断，「AI 的事都该业务自己做」会导致每个团队重复付那笔本可以付一次的账。
- **证据与来源**：【公开】认知负荷三分法出自 Sweller（Cognitive Science, 1988）；Enabling 与 Facilitating 模式由 Team Topologies（2019）正式提出，ING 的转型实践自 2015 年起有公开材料（[§7.2 候选表](11-team-topology-section-7-sec7.md) 已列）。本主题下「AI 专用 Enabling」不满足第②条。
- **成熟度**：**L2**（本组两个方向分别判）——**AI Enabling**：Enabling 模式有正式出处与第三方实践，但「AI 专用 Enabling」的边界与交付物定义尚无公开共识；**认知负荷新增的「AI 治理 / 合规 / 风险」维度**（§5.1 表第 4 行）：三分法本身有正式出处，但「怎么把它测出来」没有公开共识——这正是该行判据里「规范侧间接支持、但没有公开共识」那半句的展开。两条结论相同：可试点，不要设常设编制。
- **判定方法**：让每个流对齐团队统计最近一个月花在环境类与 AI 适配类工作上的时间占比——这个比例就是 Extraneous 负荷的可见代理，它不依赖任何主观打分（同 [§7.3.2 的判定方法](11-team-topology-section-7-sec7.md)）。

#### 5.2.4 用 AI 设计组织本身：Team API 的 RAG 化 / 组织 GraphRAG / AI 辅助拓扑设计

- **旧做法与它的卡点**：Team API 写在 Wiki 里没人看；组织依赖图只存在于人的记忆与会议纪要里；拓扑设计靠工作坊。卡点是**这些资产没有机器可读形态**——因此既不能被检索，也不能被校验，更不能在有人离职时被继承。
- **AI 改变了什么机制**：**只改变了接口形态**（自然语言可查、图谱可遍历、建议可生成），**没有改变切分维度，也没有改变负荷归属**。这是本组三条的共性，也是它们必须与前三组分开评级的原因：**这是接口改良，不是架构变化。**
- **由此得到的**：因为组织信息一旦被写成结构化形态（团队 / 服务 / SLA / 责任人 / 交互模式），它就能被检索与问答，所以「跨团队找谁」这件事的边际成本会下降；这在团队数多、人员流动快的组织里是真实收益。
- **由此付出的**：
  - **① 这些资产会过期，而组织信息的过期比血缘过期更危险**：它给出的错误信心会让变更找错人。[§6 落地实践](11-team-topology-section-6-sec6.md) 的踩坑表里「共享能力无人负责」与「平台变更不考虑兼容，打断所有依赖方」是同类失败的实例，其修法分别是「设立平台 / 中台承接」与「接口契约化 + 向后兼容」——**修的都是「有没有人对这份信息负责」，而不是「这份信息好不好查」。**
  - **② 把现状图谱喂给模型自动建议边界，等于把「现状」当成「应然」**：Conway 反演的第一步是**先明确目标架构**（主文件 §2.3），这一步是判断，不是检索。
  - **③ RAG 化只解决「找得到」，不解决「找到了也没人负责」**：而后者才是 Team API 真正的失效点。
- **证据与来源**：三条均无公开可核验来源——无正式发布方，无第三方生产案例。
- **成熟度**：**L3** —— 记录，不要在架构里为它预留假设。
- **判定方法**：在决定投入之前，先回答两个问题——（1）组织信息现在有没有明确的维护者？（2）维护者有没有义务在团队边界变化后更新它？两个都是「否」时，检索与图谱只会把过期信息变得更容易被找到，反而更危险。

| 三个方向 | 机制上它改了哪一层 | 评级 | 什么时候值得再看 |
| --- | --- | --- | --- |
| Team API 的 RAG 化 | 检索层（文档 → 可问答） | L3 | 当 Team API 有稳定字段且有人对新鲜度负责时 |
| 组织结构的 GraphRAG | 表示层（列表 → 图谱） | L3 | 当图谱能表达「应有的依赖」而不只是现状时 |
| AI 辅助拓扑设计 | 建议层（人判断 → 模型建议） | L3 | 当输入里包含目标架构而不是只有现状时 |

### 5.3 与本主题既有栈的接口在哪

组织演进不是独立议题，它要接到主文件已有的概念上。下表写清接口边界：谁调用谁、以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| AI 平台 ↔ 流对齐团队 | 自助入口 + SLA（托管能力清单：推理 / 检索 / 评测 / 留痕） | 平台负责可用性、配额与文档；流对齐负责自己的业务口径与提示 | 可做（平台角色 2019 起正式化，L2） |
| AI 治理 ↔ 交付流程 | 发布门禁 + 结构化留痕（影响评估、审批人、评测结果） | 治理团队定判据与门禁；交付团队供材料 | 可做：判据来自外部规范、不随厂商产品变化，但团队形态无第三方案例（L2，判据与核验路径见 §5.2.2） |
| Enabling ↔ 流对齐团队 | Facilitating（赋能计划 + 退出条件），以 6–12 个月为一个周期（主文件 §2.3【经验】） | 赋能方负责「能力留下」，被赋能方负责「独立完成」 | 可做，但验收必须是滞后指标 |
| Team API ↔ 所有消费方 | 文档 + 服务面（服务清单 / SLA / 交互模式 / 责任人） | 提供方负责接口兼容与 SLA | 可做，**成本最低、作用面最广的一步** |
| 组织信息检索（RAG / 图谱）↔ 变更流程 | 只读检索与建议 | **无责任方**——这正是它的问题所在 | 观望（L3） |
| 目标架构 ↔ Conway 反演 | 设计输入（先有目标架构，才谈反演） | 架构负责人 | 观望；反演本身是既有方法，不是 AI 新增 |
| 治理门禁 ↔ 平台 | 平台提供自动化检查的钩子与元数据，治理团队定判据 | 治理团队定判据；平台保钩子可用 | 可做（判据来自外部规范，不随平台产品变化） |
| 认知负荷度量 ↔ 流对齐团队 | 时间占比的定期统计（环境类 + AI 适配类） | 各团队自己报，平台不代报 | 可做（这是本节所有「现在该做什么」的验收口径） |

这张表里接口形态最稳定的是**治理门禁**——它的判据来自组织外部，不随你选哪个模型、哪个厂商而变化（稳定的是这个接口，不是团队编制：编制按 §5.2.2 的 L2 处理）。

这张表里的八个接口各有各的成立条件，不能简化成「先把 Team API 写出来」一句：第 1、4 行确实以 Team API 为前提（平台的自助入口 + SLA、Team API 本身）；第 2、7 行的前提是**门禁判据写在发布流程里**；第 3、8 行的前提是**赋能计划与退出条件、时间占比的统计口径被写死**；第 5 行现在连责任方都没有，第 6 行的责任方是架构负责人但反演本身是既有方法、不是 AI 新增，所以这两行都是观望。不过有一条仍然贯穿全表：**Team API 是其中唯一一件今天做、明天就有收益、且不需要任何 AI 能力的事。**

还要看清一件事：这张表里的八个接口，**没有一个需要「AI 能力」**，它们的形态（门禁、SLA、度量统计）与十年前的数据平台治理完全一样。这是本节反复要说的那句话的具体落点——**AI 换掉的是负荷的种类与判据的来源，不是组织接口的形态**。

### 5.5 被过度宣传的部分

**「AI 平台团队会成为所有 AI 能力的枢纽」** —— 实际是：能收敛的只有「付一次就能共享」的那一半负荷（推理与检索基础设施、评测集、审计留痕）；「每用一次都要重付」的那一半（业务口径、提示适配、领域评测样例）留在流对齐团队。为什么会这样：复杂度不会消失、只会转移（[§7.3.2](11-team-topology-section-7-sec7.md) 的机制推导），而「每用一次都要重付」的负荷无法被一次实现买断。什么时候它才会成真：当业务侧的 AI 适配被证明是可产品化的标准件时——**判定信号是同一个适配能力被 k 个流团队各实现过一遍且 k 达到 [§7.4 推算 ②](11-team-topology-section-7-sec7.md) 的回本区间**，而不是「AI 很重要」。

**「组织结构可以靠 AI 或其图谱自动设计」** —— 实际是：Conway 反演的第一步是明确目标架构，这一步是判断而不是检索；把现状依赖图谱喂给模型，只会得到现状的复述，而且会因为它看起来有依据而更难被推翻。为什么会这样：反演的因果方向是「先定目标架构、再设组织」，而图谱只记录了「现在是谁依赖谁」。什么时候它才会成真：当组织图谱能表达**目标架构**而不只是现状依赖时——判定信号是图谱里存在「应有的依赖」这一类边，且它与「实际依赖」可被分别查询。

**「Team API 写成文档就等于服务化」** —— 实际是：文档只表达意图。判定方法沿用 [§7.3.3](11-team-topology-section-7-sec7.md)：抽查 3 个跨团队接口，看有没有 SLA 与责任人；**没写明的接口在事实上仍是 Collaboration，不论文档里怎么命名**。这一点在 AI 时代没有变化，而把它做成 RAG 知识库也不会改变它——**检索改善的是「找得到」，不是「有人负责」。**

### 5.6 未来 3–5 年：可证伪的预测

每条都写成「预测 + 会成真的信号 + 会证伪的信号」。写不出信号的，不写。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| AI 治理在受监管组织里会成为有独立编制的团队，而不是平台团队的兼职 | 出现「AI 治理」独立编制的组织公告与招聘，且其考核项里含对外举证材料 | 连续 3 年以上仍以「合规 / 风控专员 + 平台兼职」运行，且未出现因治理缺位导致的监管处罚公开案例 |
| AI 平台的范围会收敛，而不是扩张 | 平台的对外服务清单变短，或明确写出「不做业务侧提示与口径」 | 平台开始承接业务口径定义与变更审批权（[§7.7](11-team-topology-section-7-sec7.md) 的失效路径） |
| 「组织图谱 / 文档 RAG」类资产会以「查得到但没人维护」告终 | 图谱或索引的中位更新时间超过一个季度 | 出现把「图谱 / 索引的新鲜度」写成 SLO 的实践，并有团队为其 on-call |
| Enabling 的考核会从「场次 / 覆盖人数」换到滞后指标 | 赋能团队的考核表里出现「对方独立完成率」 | 一年后仍按赋能场次或培训人次考核，且赋能期持续延长 |

四条预测有一个共同点：**它们全都能用一个可观测事实证伪**，不需要等到有人写复盘。这也是它们与「AI 会让组织更好」这类句子的区别——后者永远正确，因而没有信息量。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 全员 < 50 人、刚开始用模型 | 把 Team API 写出来（SLA + 责任人）；把推理与评测放进已有的平台角色 | 同一 AI 能力被几个团队各实现了一遍（记作 k） | **不要**为「AI 治理」专设团队（兼职 + 明确门禁判据即可）；不要建组织图谱或做 Team API 的 RAG 化 |
| 50–200 人、AI 已进生产 | 设最小 AI 平台团队，只做最常被重复实现的那一件事；给治理指定归属 | 消费者自助率、从申请到可用的时长、被绕过的次数 | **不要**把业务口径与提示适配收进平台；不要为每个业务线各建一个「AI 小组」 |
| 受监管 / 需对外举证 | 把举证材料做成机器可读、可自动生成；把治理挂在门禁上而不是交付链上 | 适用规范的版本更新与适用范围变化 | **不要**让治理团队向业务线汇报；不要用「文化」替代留痕 |
| 200 人以上、跨团队知识不再传播 | 4 种团队类型并存 + Team API；Enabling 用滞后指标验收 | 抽查的跨团队接口是否写明 SLA 与责任人 | **不要**用组织调整解决度量问题（先改考核口径，再动边界） |
| 平台已建但没人用 | 把平台度量改到消费者侧（自助完成率、接入时长） | 平台的范围是否在扩张、服务清单是否在变长 | **不要**靠加人；不要靠给平台加 RAG 检索或图谱来「提升体验」 |

**自检清单**（每条都对应上文一个机制，答「否」的地方就是本主题下你的真实风险）：

- [ ] 同一 AI 能力，在你的组织里被几个团队各实现过一遍？（记作 k；k ≤ 2 时不要建平台）
- [ ] AI 相关的负荷里，哪些是「付一次」的、哪些是「每用一次」的？两类是否放在正确的角色上？
- [ ] 平台的服务清单里，有没有出现「业务口径」「提示词模板」这类业务判断？
- [ ] 举证材料是自动生成的结构化记录，还是人填的表格？
- [ ] 治理门禁挂在发布流程里，还是只写在文档里？
- [ ] Enabling 团队的交付物，定义成「我们帮他们做完」还是「他们能独立复现」？
- [ ] 赋能团队的考核项里，有没有任何一项是滞后指标？
- [ ] 抽查 3 个跨团队接口，有几个写明了 SLA 与责任人？
- [ ] 组织信息（Team API / 依赖图）有没有明确的维护者与新鲜度要求？
- [ ] 上一次调整组织边界之前，是先改了考核口径，还是只改了边界？
- [ ] 你给 AI 治理的编制，是按主文件 §2.2 的配比算得出来的，还是「先兼着」？

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**它把认知负荷劈成了两半——「付一次就能共享」的和「每用一次都要重付」的**，组织设计的全部工作就是别把这两半放错地方：放错了就会同时出现「平台做了没人用」和「业务各自重建」。AI 唯一改变了约束来源的地方是治理——它把举证从内部共识变成外部要求；但本节没有方向判到 L1：规范公开的是对组织的要求，而「不挂在交付链上、承担举证责任」的团队形态没有指名的第三方生产案例，所以本主题的评级上限目前停在 L2。而组织形态本身没有变：切分维度（按职能切还是按价值流切）仍然决定协调成本随规模是 n² 量级还是接近常数，这一点与用不用 AI 无关。

> 💡 **思考锚点**：给你的组织数一个 k——同一项 AI 能力被几个团队各实现了一遍？按 §5.7，k ≤ 2 时不该建平台；若你的 k 已到 3 以上，那你准备收进平台的那「最常被重复实现的一件事」，是不是恰好落在「每用一次都要重付」那一半，而非「付一次就能共享」的那一半？
