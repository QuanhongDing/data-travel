## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把组织设计讲成「互联网产品选 Stream-Aligned + Platform，数据基础设施选 Platform + Complicated-Subsystem」，但真实的选择是被约束推着走的。同一条「给业务团队配一个平台团队」的建议，在 3 个流对齐团队的组织里是纯成本，在 20 个流对齐团队的组织里是硬需求——**同一维度的权重在不同规模下方向相反**，而选型表只能给一个数。真实权重至少是两件事的函数：一是**规模**，[§7.1](11-team-topology-section-7-sec7.md) 用 3 个与 20 个流对齐团队的对照给出推导；二是**流程稳定性**，[§7.3.1](11-team-topology-section-7-sec7.md) 指出「当一个组织的流程本身每周都在变时，把团队完全按当前流程切，等于把组织绑死在当前流程上」。这两维都不在打分表里。这就是先立约束、再谈模式的理由。

最硬的约束是**切分维度**：按技能切（职能型）还是按价值流切，决定了一条端到端变更链上要发生几次协商。协商成本不随人数增长而随跨界次数增长，因此把组织从职能切改为流切，买到的不是「沟通更顺畅」，而是「同一条变更链上的协商次数降到接近零」。第二硬的约束是**认知负荷放在谁头上**：主文件 §2.1 把负荷分为 Intrinsic（领域本质，不可消除）、Extraneous（工作环境造成，应降低）、Germane（学习成长，应投资）；复杂度不会消失、只会转移，所以「是否设立 Platform」的实质是「把 N 个团队各自承担的环境复杂度收敛成一次」，而不是「要不要更先进的技术部」。

约束之间还有顺序：**先定切分维度**（它决定协商次数），**再看认知负荷归属**（它决定要不要平台、要几个平台），**最后才是交互模式与度量归属**（它们决定这套结构能不能维持）。顺序颠倒的典型症状是「先设了平台团队，回头才发现没有清晰的价值流可供对齐」——平台能力没有消费者，于是它的存在只能靠行政要求维持。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 切分维度（职能 / 价值流 / 损益） | 一条端到端变更链上的协商次数 | 「业务对齐就是多开同步会」——协调成本是跨界次数的函数，不是会议次数的函数 |
| 认知负荷归属（Intrinsic / Extraneous / Germane） | 环境类复杂度由谁承担 | 「认知过载是人的能力问题」——它是负荷总量问题，超限后的产出下降是非线性的 |
| 交互模式（Collaboration / X-as-a-Service / Facilitating / Sub-subscribing） | 团队之间是持续协作还是按服务消费 | 「接口没定清楚就先多沟通」——协作不可扩展；接口未稳定时强行服务化会把知识交换变成排队 |
| 决策权与度量归属 | 谁对业务结果负责、KPI 边界画在哪 | 「设个平台团队就能解决重复建设」——度量没改，平台的最优策略是把接入成本推给消费者 |
| 团队规模与技能分布 | 一个交付单元能不能端到端 | 「小队自治就是什么都自己做」——端到端指对结果负责，不等于全栈自建 |
| 组织演进成本 | 新增一条业务流要动几个团队 | 「一次性重组就能对齐」——迁移期的交付中断与能力丢失也要计入成本 |

这六条里没有一条问「哪种团队类型更好」。它们只问：在你的约束下，哪种切分是必须的，哪些共享能力载体是负担。先把「我该按什么切」和「我该建哪种团队」分开，能省掉一半的比较——把这两问混成一问，是组织设计里最常见的起点错误。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 Stream-Aligned Team（流对齐团队）

**被什么约束逼出来**：交付要经过多道职能交接，每道交接都带来等待，且端到端结果无人负责。

**结构**：
```text
职能切（一条变更链）：
  需求 → [分析团队] → [开发团队] → [测试团队] → [运维团队] → 上线
         每段交接 = 一次排队 + 一次责任移交（端到端无人负责）

流切（流对齐团队内部闭环）：
  需求 ─► [流对齐团队：含完成该流所需的全部技能] ─► 上线

  边界判据：一次端到端变更需要跨几个团队（越接近 0 越好）
  支撑前提：跨域的共享能力由 Platform 以自助服务提供（§3.2.2）
  失败形态：流对齐团队内部技能不全 → 协商没消失，只是搬进了团队内部
→ 判据：流内闭环 + 平台兜底，缺一个都不成立
```

**与谁交互 / 默认交互模式**：对内 Collaboration（团队内部自治，不需要交互模式），对外随着接口稳定逐步转为 X-as-a-Service；接口没稳定前，对外仍是持续协作。

**为什么这样设计有效**：因为一次变更链上的协商次数降到接近零，所以交付速度的上限不再由等待决定；同时因为团队对业务结果负责，度量与责任落到同一个单元上，[§7.3.4](11-team-topology-section-7-sec7.md) 描述的「责任分裂」不会出现。

**代价**：团队要同时承接业务侧与工程侧两类 Intrinsic 负荷；在没有平台支撑时，K8s、权限、观测、容量这些 Extraneous 负荷也全部落在同一个团队头上，认知负荷总量直接翻倍。

**失效点**：当流对齐团队不具备端到端技能、也没有平台支撑时，「协商次数归零」会反转成「认知过载」，因为原来跨部门的协调成本被搬进了团队内部——表现为小团队什么都要管、交付反而更慢，而且此时加人不会改善（跨界次数不是人数的函数）。

**真实使用**：ING 2015 年起公开的敏捷转型把交付单元重新切成端到端小队（【公开】ING 公开的转型材料与报道, 2015 年起；可按「ING agile transformation squad」等关键词自行检索核验）；Team Topologies 把这一形态系统化为四种团队类型之一（【公开】Skelton & Pais, 2019）。Amazon 的 two-pizza team 与 single-threaded leader 是同一机制的另一种表述（无单一权威出处，可按「single-threaded leader」在历年致股东信与公开访谈中自行检索核验）。

#### 3.2.2 Platform Team（平台团队）

**被什么约束逼出来**：多个流对齐团队各自承担同一份环境复杂度（环境配置、观测、权限、容量），这份复杂度是被重复支付的。

**结构**：
```yaml
# Team API（主文件 §2.3 给出的载体：服务 / SLA / 交互模式 / 文档）
team:
  type: Platform
  interaction_modes: [X-as-a-Service（主）, Collaboration（按需）]
  services:                          # 每个服务 = 一个可自助取用的能力
    - name: 数据管道
      sla: {availability: 99.9%, freshness_p95: 5min}
      owner: <具体到人，不是团队>
  consumers_k: 5                     # k = 同一能力被几个团队各自实现过（§7.4 ② 的 k）
  metrics: {self_service_rate: …, bypass_count: …}   # 度量必须在消费者侧
  docs: [README, Quick Start, API 文档, SLA 报告]
# 判据【推算，推导链见 §7.4 推算 ②】：设同一能力被 k 个团队各自实现过，
#   回本点大致落在 k ≈ 3–5 这一段，且这一段本身带不确定度，不是硬阈值；
#   k ≤ 2 时平台化通常不成立（k = 2 两侧区间重叠，须按单次实现代价复核）
```

**与谁交互 / 默认交互模式**：X-as-a-Service 为主；当某个消费者需要的是新能力而不是已有能力的取用时，临时切回 Collaboration，能力成熟后再收回服务化。

**为什么这样设计有效**：因为 Extraneous 负荷由环境复杂度产生、而不是由业务复杂度产生，所以把它移出流对齐团队才成立——平台化的机制等价于「把 N 个团队各自承担的复杂度收敛成一个团队的一次性复杂度」；又因为能力以 X-as-a-Service 交付，消费者不必与平台保持持续协作，这套结构才可扩展。

**代价**：平台要养文档、SLA、支持轮值与产品化投入；这些成本在消费者数量少时无法摊薄——消费者数 k 越小，重复实现的总代价越低，平台化越不划算。

**失效点**：当平台被按自身技术指标考核、而流对齐团队被按业务结果考核时，「降低他人认知负荷」会反转成「把接入成本推给消费者」，因为平台的最优策略变成了不做产品化（接口不友好、文档缺失、审批变长都是理性选择）。这条「度量错位 → 平台最优策略变成推接入成本」的推导见 [§7.3.4](11-team-topology-section-7-sec7.md)；消费者数一侧的成本学（重复实现数 k ≤ 2 时平台化不成立）见 [§7.3.2](11-team-topology-section-7-sec7.md)。两者合起来，才是「Platform 做了没人用」的完整成本学根因。

**真实使用**：Google 公开的 SRE 系列书籍把「运维复杂度集中到专业团队 + 给业务团队一个自助服务面」写成可扩展的运维形态（【公开】Google SRE 系列书籍，O'Reilly；该书版次年份存疑，此处不写死，请以出版方官方信息为准）；平台工程与 Internal Developer Platform 是这一角色在当代的主要载体（【公开】DORA 年度报告, 2021 起持续观察）；本书 §6 的字节案例把共享能力从「排期交付」改为「标准件自取」【经验】。「阿里巴巴中台」与「Stripe Platform」也列为本模式的代表：按本章口径，平台是**角色**、中台是**载体**（[§7.2](11-team-topology-section-7-sec7.md) 把中台归入「共享能力载体族」；阿里「中台战略」公开提出的年份本书内两处口径不一——主文件 §1.4 的演进历程记 2014、15-case-studies/01 阿里数据中台案例主文件记 2016，此处不锁定具体年份，以阿里公开材料为准【公开】），Stripe 一侧可核验的是其工程博客公开的内部平台方向；两家公司的内部团队边界本节不据此断言，请以各自公开材料的当前版本为准【经验】。

#### 3.2.3 Enabling Team（赋能团队）

**被什么约束逼出来**：某项能力（数据治理、MLOps、AI 集成）在业务团队里长期缺失，但把它常驻在每个业务团队里的成本过高。

**结构**：
```text
Facilitating（辅导）模式 —— 不是代做，是让对方会做
  业务团队（缺口：能力 X）
        ▲  赋能：培训 / Workshop / Pairing
        │
  Enabling Team ── 产出是"对方的能力"，不是自己的交付物
        │
        └─► 退出条件（定义的一部分，不是管理约定）：
            触发：对方能独立完成该类任务
            度量：对方独立完成率（滞后指标），不是赋能场次
            期限：6-12 个月这一量级【经验，主文件 §2.3】

  反例：赋能团队常驻 → 业务团队失去成长动机 → 变成常设二团队
```

**与谁交互 / 默认交互模式**：Facilitating；赋能对象独立之后必须退出，回到 X-as-a-Service（如果它同时还有一个平台角色）或回归自身团队。

**为什么这样设计有效**：因为 Facilitating 的产物是对方的能力而不是自己的产出，所以一旦目标达成，这个团队继续存在的边际价值为零——退出机制因此是定义的一部分，而不是「到时候再说」。同样因为价值体现在「对方不再需要我」，它的度量必须用滞后指标，否则团队会理性地延长赋能期。

**代价**：赋能期内不产生直接交付，业务团队的产出在期内会低于「自己顶上去」的速度；且赋能对业务团队负责人的配合度要求高——负责人不认账时，能力传递不会发生。

**失效点**：当没有明确的退出条件与滞后度量时，「能力传递」会反转成「常设依赖」，因为按赋能场次考核会让延长赋能期成为最优策略——Enabling 团队逐步变成业务团队的常设二团队，对方也不再有能力成长的动机。

**真实使用**：ING Bank 的公开转型材料（2015 年起）里同时存在端到端小队与 Enabling 角色——本章 [§7.2 候选表](11-team-topology-section-7-sec7.md)与 [§8](11-team-topology-section-8-sec8.md) 都把 ING Bank Enabling Team 列为该形态的第三方实践（【公开】ING 公开的转型材料与报道, 2015 年起；可按「ING agile transformation squad」等关键词自行检索核验）。Team Topologies 把 Facilitating 列为三种核心交互模式之一（【公开】Skelton & Pais, 2019）；Spotify 的 Chapter 是这一角色在技能线上的实践变体（【公开】Kniberg & Ivarsson《Scaling Agile @ Spotify》, 2012），但它承担的是技能标准与人才成长，不是交付责任【经验】。

#### 3.2.4 Complicated-Subsystem Team（复杂子系统团队）

**被什么约束逼出来**：某些子系统的 Intrinsic 复杂度极高（数据库内核、安全、合规与 AI 治理），让每个业务团队都掌握它既不经济也不可能。

**结构**：
```text
把最难的 Intrinsic 复杂度集中，其他人按服务消费
  ┌───────────────┐   接口由它单方定义 + 兼容策略（版本 / 兼容窗口）
  │ Complicated-  │◄── Sub-subscribing（消费方按需订阅专业能力）
  │ Subsystem Team│
  └───────────────┘
   业务团队不实现该子系统，只消费；
   成本对照：
     分散实现：N 个团队各学一遍同一份领域知识 → N 份 Intrinsic 负荷
     集中实现：少数专家承担一次  → 1 份 Intrinsic + N 次接口消费
   判据：该类能力是否有必须举证的合规责任（有则必须有归属）
```

**与谁交互 / 默认交互模式**：Sub-subscribing——消费方按需订阅专业能力，接口与兼容策略由子系统团队单方定义（主文件 §2.1 的 Team Interaction Modes；口径说明见下）。

**为什么这样设计有效**：因为复杂度集中在少数专家手上会被一次性解决，其他团队不必重复学习同一份领域知识，组织的总认知负荷因此下降；又因为举证责任（合规、安全、风险）有明确归属，它不会被业务节奏压过去。

**代价**：它是一个知识孤岛——接口由它单方定义，与业务节奏天然可能冲突；集中在少数人手上的能力一旦人员流失，恢复成本很高，因此它通常需要额外的文档化与冗余投入。

**失效点**：当它只按自己的系统指标优化、而业务团队按交付速度考核时，「集中复杂度」会反转成「集中瓶颈」，因为接口的兼容策略与变更节奏由单方决定，业务团队的所有需求都要排进它的队列——严格与可用之间的取舍，在只考核它自己时必然偏向严格。

**真实使用**：数据库团队与安全团队是该形态的经典实例（【公开】Skelton & Pais, 2019 把 Complicated-Subsystem Team 列为四种团队类型之一，本章 [§7.2 候选表](11-team-topology-section-7-sec7.md)同此口径）；AI 治理团队是其当代实例，治理框架本身已有可举证的公开标准（【公开】NIST AI Risk Management Framework 1.0, 2023；ISO/IEC 42001, 2023）。

**口径说明（与本章 [§7.3.3](11-team-topology-section-7-sec7.md) 一致）**：本节把 Sub-subscribing 写成本形态的默认交互模式，依据是**主文件 §2.1 把 Team Interaction Modes 计为 4 种**；公开材料在引述 Team Topologies（2019）时给的是**三种**核心交互模式（Collaboration / X-as-a-Service / Facilitating），第 4 种 **Sub-subscribing** 在原书中的具体出处本书未逐字核实（读者可按原书目录自行核验），因此**不把它归给该书**。两种口径并列而不冲突，本节 §3.2.6 的 AI 治理角色沿用同一口径。

#### 3.2.5 Spotify Squad / Tribe / Chapter / Guild（形态实现）

**被什么约束逼出来**：规模化之后团队既需要自主（否则交付慢、责任分散），又需要对齐（否则重复建设、技术栈分裂、技能孤岛），而把两类需求都挂在一条汇报线上时，这条线必然过载。

**结构**：
```text
不是层级关系，而是四种不同的连接维度
  Squad（小队）    端到端负责一小块产品      → 谁对结果负责
  Tribe（部落）    同业务域内的若干 Squad    → 同一业务方向的协同
  Chapter（分会）  同职能的人跨 Squad 横向   → 技能标准与人才成长
  Guild（行会）    跨部落的兴趣社区，自愿    → 跨领域知识流动
────────────────────────────────────────────────
  传统职能型：一条汇报线同时承担
             业务对齐 + 职能标准 + 技能成长 + 知识流动
             → 必然过载，且业务对齐压过其余三者
  四形态：   把四类需求拆到不同通道，每条通道只解决一类
────────────────────────────────────────────────
  公共约束（不可由小队自行决定）：接口契约、安全基线、合规要求
  其余领域：小队自主（含技术选型与发布节奏）
→ 自主有边界，否则"自主"退化为重复建设与栈分裂
```

**与谁交互 / 默认交互模式**：小队之间为 X-as-a-Service（接口与公共约束除外，那部分走统一规则）；Chapter 与 Guild 是技能线与知识社区，不构成团队之间的交付接口。

**为什么这样设计有效**：因为对齐需求被拆到多条通道上，汇报线只需承担业务对齐，所以「自主」与「对齐」不再是二选一；又因为 Chapter 与 Guild 不承担交付责任，技能标准不会被业务忙季挤掉。

**代价**：同时维护四套结构本身就是开销；横向通道容易被误当成交付单元，于是团队既要交付又要参加横向活动，会议负担上升，而收益并不随结构数量线性增长。

**失效点**：当横向结构被赋予交付责任时，「自主 + 共享」会反转成「额外的会议负担 + 交付责任落回无法独立交付的小队」，因为 Chapter 与 Guild 的设计前提就是只承担技能线与知识社区（[§7.3.3](11-team-topology-section-7-sec7.md) 据 Kniberg & Ivarsson 2012 的公开材料核出：Chapter 与 Guild 对应的是 Germane 负荷，不是交付责任）——2020 年 Spotify 内部人士的公开复盘指出该模型在原公司也未被原样执行，除「横向社区不能当交付团队」这一条，其余形态不宜照抄【经验】。

**真实使用**：Spotify 2012 年公开该模型（【公开】Kniberg & Ivarsson《Scaling Agile @ Spotify》, 2012；Jeremiah Lee《Failed #SquadGoals》, 2020 给出反思性复盘）；本书 §6 的 Spotify 案例记录了小队 6–12 人这一规模量级【经验】。

#### 3.2.6 AI 时代拓扑（AI 平台 + AI Enabling + AI 治理）

**被什么约束逼出来**：AI 给组织加了三类新的认知负荷与举证责任——模型与算力的共享能力、业务团队用 AI 的能力缺口、以及合规与风险举证——这三类都不能靠原拓扑自动承接。

**结构**：
```text
原拓扑的新增扩项（三个角色各承接一类负荷，不是三个层级）：
  ① AI Platform（Platform 角色）：模型服务 / 向量库 / 评测与观测
        —— 把"每用一次都要重付"的负荷收敛成一次
  ② AI Enabling（Enabling 角色）：把用 AI 的方法传给业务团队，传完退出
        —— 把"每教一次才会一次"的负荷传递出去
  ③ AI 治理（Complicated-Subsystem 角色）：合规、评测、风险
        —— 要求有归属，兼职会被业务节奏压过去
  判据：先问"这类负荷是重复付的、要教的、还是要举证的"，再决定角色
  常见的错误组合：三件事都塞进一个"AI 团队" → 度量打架，三者互相挤占
```

**与谁交互 / 默认交互模式**：AI Platform 以 X-as-a-Service 提供自助能力；AI Enabling 用 Facilitating 并在传完后退出；AI 治理以 Sub-subscribing 承接举证类请求，接口由它定义。

**为什么这样设计有效**：因为三类负荷的性质不同，对应的承接方式也不同——重复付的用平台收敛、要教的用赋能传递、要举证的必须有归属——所以按负荷性质分派角色，比笼统设一个「AI 团队」更不容易漏项。

**代价**：三类角色各有自己的度量（平台的消费者自助率、赋能的对方独立完成率、治理的合规事件与红线门禁），度量分离是必需条件，也是运营中最大的摩擦点；同时 AI 能力的载体换代快，平台的自助面要跟着重建。

**失效点**：当治理被当作平台的附属职责时，「集中举证责任」会反转成「举证在业务节奏下被牺牲」，因为治理的产出是「没有发生的事故」，在按交付速度考核的环境里永远排不上优先级——只有把它拆成有归属的独立角色，这条负荷才不会被压过去。

**真实使用**：AI 风险与治理已有可举证的公开框架（【公开】NIST AI RMF 1.0, 2023；ISO/IEC 42001, 2023），某个组织具体设了几个 AI 团队属内部信息，请以该组织公开材料为准；本书 §6 的字节案例显示，平台化能否成立取决于共享能力是否「标准件自取」而非「排期提供」【经验】。OpenAI、Anthropic 与阿里通义也列为本模式的代表：可核验的是这三家在模型能力与治理框架一侧的公开材料，其内部团队如何切分未见公开，本节不作断言，请以各公司公开材料的当前版本为准【经验】。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 单业务、变化快、团队数少（3–5 个流对齐团队这一量级【经验】） | Stream-Aligned（先不设 Platform） | 平台要养文档、SLA 与支持轮值，消费者少时摊不平 | 同一能力被重复实现的团队数 k ≤ 2【推算，§7.4 ②】 |
| 互联网产品、流对齐团队数以十计（[§7.1](11-team-topology-section-7-sec7.md) 的 20 个对照场景，【经验】量级） | Stream-Aligned + Platform | 不设 Platform，环境类复杂度会被复制 N 份 | 环境类工作时间占比持续偏高 |
| 多业务集团、口径可分 | 事业部制（BU）为切分，共享能力另设载体 | 只按价值流切，跨 BU 的口径无法各自闭环 | 各 BU 的损益能独立核算 |
| 数据基础设施 | Platform + Complicated-Subsystem | 让每个业务团队自建数仓与治理，重复且口径分裂 | 同一能力被重复实现的团队数 k ≥ 3【推算，§7.4 ②：回本点 k ≈ 3–5】 |
| AI 平台 | Platform + Enabling | 只设平台不设赋能，业务团队不会自助使用 | 业务侧自助使用率可度量 |
| AI 治理 / 强合规场景 | Complicated-Subsystem（AI 治理） | 兼职承接会被业务节奏压过去 | 存在必须举证的合规责任 |
| 技能稀缺、业务团队长期学不会 | Enabling（Facilitating + 退出条件） | 采购外部培训不改变团队内部的责任归属 | 赋能期结束时对方的独立完成率可度量 |
| 远程 / 多时区团队 | Stream-Aligned + 异步优先的工具承载 | 跨时区同步协作的代价被时区差放大 | 跨团队协作以异步为主、上下文不断链 |
| 只有 1–2 个团队各自实现过同一能力（k ≤ 2） | 先各自实现，暂不平台化 | 只为少数实现者上平台，等于把一个团队的负荷复制成两个 | 重复实现数 k 与单次实现代价一起算【推算，§7.4 ②】 |

表里最常被误选的一对，是**在消费者数不足时先建 Platform**。误选的后果不是「平台没做好」，而是它一旦设立就会永久占用编制与注意力：既摊不薄成本，又会把本该留在流对齐团队里的 Extraneous 负荷变成「等平台排期」的不确定等待，总负荷反而上升——团队最终绕开平台自建，于是组织同时付了平台的成本与重复实现的成本。

需要说明的是，这张表里的判据**优先取可观测事实**（同一能力被重复实现的团队数、环境类工作时间占比、独立完成率、损益能否独立核算、业务侧自助使用率），而不是印象分。表里出现的每一处规模数字都带档位并指向它的推导链：`k ≈ 3–5` 是【推算】（§7.4 推算 ②），「3–5 个 / 20 个团队」这一量级是【经验】。这些数字用来定位「你的处境更接近哪一行」，不是可以照搬的硬阈值——§7.4 明确写了回本点「这一段本身带不确定度」。如果你的场景需要一个更准的门槛，按「新增一条业务流要动几个团队、要等多久」自算——那个数就是你的边际组织成本，它比任何通用阈值都准。

### 3.4 组合模式：真实系统不会只用一种

**组合 1：Stream-Aligned + Platform（平台以 X-as-a-Service 交付标准件）**
- 构成与职责边界：流对齐团队对业务结果负责，平台对能力质量与自助面负责；共享能力以标准件形式提供，平台不承接定制需求。
- 运维代价：Team API（服务清单 / SLA / 责任人 / 变更兼容策略）的持续维护，以及平台与业务方之间的优先级争夺。
- 适合规模：流对齐团队数以十计【经验】，且同一能力被重复实现的团队数 k 已进入 3 以上【推算，§7.4 ②】。
- 什么情况下不该用：流对齐团队数少（3–5 个这一量级【经验】），或同一能力的重复实现数 k ≤ 2【推算，§7.4 ②】——此时各自实现更便宜，平台只会成为等待队列。

**组合 2：Complicated-Subsystem + Enabling（把难的集中，再教会怎么用）**
- 构成与职责边界：子系统团队单方定义接口与兼容策略，Enabling 负责把「怎么用、怎么自证」传到业务团队，传完退出。
- 运维代价：两套完全不同的度量（子系统看系统与风险指标，赋能看对方独立完成率），且赋能退出时业务团队要能接住。
- 适合规模：存在必须举证的合规责任，且该能力不能被所有业务团队各自掌握。
- 什么情况下不该用：该能力其实可以被一次性封装成自助服务——那就不需要 Enabling，只需要把接口做对。

**组合 3：AI Platform + AI Enabling + AI 治理（AI 时代三件套）**
- 构成与职责边界：平台收敛重复负荷、赋能传递使用方法、治理承接举证责任；三者是三种负荷对应三种承接方式，不是三个层级。
- 运维代价：三个角色的度量必须分离，否则「平台做工具不做产品」「赋能变常设」「治理被压过」会同时出现；AI 能力载体换代时平台自助面要跟着重建。
- 适合规模：多条业务线都要用 AI，且其中至少一条有合规举证要求。
- 什么情况下不该用：只有一条业务线在用 AI、且无举证要求——此时把三件事并给一个团队更快，代价是以后拆分时的度量冲突。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 职能孤岛 | 数据 / 应用 / AI 团队各干各的，一条需求要跨 4 个以上团队 | 每次跨界都是一次排队与责任移交，端到端无人负责 | 按技能招人最容易，按价值流切要重新设计汇报线 | 先按价值流切交付单元，再设共享能力载体（§3.2.1、§3.2.2） |
| Platform 做了没人用 | 平台的功能清单很长，业务方仍绕开它自建 | 平台的成本已付、负荷没被移走，总成本反而上升 | 按平台自身技术指标考核，且消费者数不足以摊薄成本 | 度量改到消费者侧（自助率 / 申请到可用时长 / 被绕过次数），并复核消费者数 k（§3.2.2） |
| 认知过载 | 团队承担过多责任，产出下降、士气与留存同步走低 | Extraneous 负荷没有被移走，只是被拆分后仍落在同一批人身上 | 「端到端」被理解成「什么都自己做」 | 把环境类负荷上平台，把学习类负荷当作投资而非消耗（主文件 §2.2 的三分类） |
| Enabling Team 不退出 | 赋能团队存在两年以上，业务团队仍在等它代做 | 能力没有传递，横向团队变成常设二团队，交付责任悬空 | 按赋能场次考核，延长赋能期成了最优策略 | 写明退出条件与期限【经验：6–12 个月这一量级】，度量改为对方独立完成率（§3.2.3） |
| Conway's Law 顺其自然 | 组织结构随意调整、不反推系统架构，团队边界与技术边界长期错位 | 沟通结构会在系统设计上留下等同的缝，跨团队协作成本被固化进架构 | 「组织是 HR 的事」，或边界调整被当作一次性项目 | 用 Inverse Conway Maneuver：先定目标架构，再让团队边界与限界上下文对齐（主文件 §2.3） |

**「Platform 做了没人用」是最典型的自证式失效。** 它不会以故障形式暴露：平台按自己的指标交付了很多能力，看板漂亮，业务方却在自建。暴露点通常在资源盘点——当有人问「同一个能力为什么有三份实现」时才会被翻开。它的机制是度量错位，不是态度问题：把平台的考核换成消费者侧的量（自助完成率、从申请到可用的时长、被绕过的次数），优化方向才会与消费者一致。

**「Enabling Team 不退出」是一条会自我强化的反模式。** 赋能团队的存在感来自业务团队的依赖，而依赖又来自「有人在帮我做」。暴露方式是业务团队负责人答不出「我们团队谁能独立完成这件事」，以及赋能排期表越排越满。因为它按场次考核，延长赋能期是理性的；正确的修法是把度量改为对方的独立完成率（滞后指标），并预先写明退出条件。

**「Conway's Law 顺其自然」的暴露点最晚，代价也最难撤回。** 它通常在架构评审或一次跨团队事故复盘时才被看见：系统里存在一条谁都说不清归属的链路，因为它对应的是「三个团队之间的口头约定」。因为是结构问题，改起来要动组织边界与接口契约，而不能靠加文档解决——这也是为什么它应该在定架构时一并处理，而不是等到事故之后。

### 3.6 规模跃迁时模式何时该换

组织形态不是一劳永逸的：团队数、消费者数、流程稳定性跨过某个阈值时，原来正确的形态会开始产生净成本。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 流对齐团队从 3 个到 10+ 个【经验】量级 | 无平台、靠人协调 | 同一份环境复杂度被复制 N 份，协调界面数按 n(n−1)/2 量级增长【推算】 | 设 Platform，以 X-as-a-Service 交付（§3.2.2） | 平台自身的运营与 SLO 成本；重复实现数 k ≤ 2 时先不成【推算，§7.4 ②】 |
| 同一能力的重复实现数 k 从 2 个到 5+ 个【推算，§7.4 ②】 | 各团队各自实现 | 同一件事被实现多遍，口径开始分裂 | 平台 / 标准件化，平台不承接定制需求 | 迁移期双轨并行，需处理已有实现的下线 |
| 流程本身从稳定到每周在变 | 按当前价值流切 | 改一次流程就要改一次组织，团队被绑死在当前流程上 | 先把可复用能力与接口沉淀，再按较稳定的断裂面切 | 短期组织与价值流不完全对齐，交付略慢 |
| 技能从稀缺到业务团队学会 | Enabling 常驻辅导 | 赋能团队变成常设二团队，交付责任悬空 | 执行退出机制，度量改为对方独立完成率 | 短期交付速度下降，需要业务负责人配合 |
| 从「能靠招聘解决全栈」到「招不到 / 不能招」 | 每个流对齐团队自备全栈 | 招聘补不上，流对齐团队的认知负荷超限 | Complicated-Subsystem 集中 + 平台提供自助面 | 集中团队成为单点，需要冗余与文档化 |
| 从单业务到多业务集团 | 单一中台承载全部共享能力 | 要么口径分裂，要么中心成为唯一瓶颈 | 切分维度改为 BU 损益闭环，共享能力以标准件交付 | 跨 BU 复用率短期下降，编制与考核要同步改 |
| 从「靠人工对齐」到「AI 辅助设计」 | 靠会议与文档约定边界 | 边界信息散落在会议记录里，无法检索也无法复用 | 把 Team API 与边界判据结构化，交给 AI 辅助检查 | 需要先把边界写成机器可读的形式，否则 AI 只能整理会议纪要 |

跃迁的共同特征是触发条件可观测：流对齐团队数、同一能力的消费者数、单位时间内流程变更次数、独立完成率、环境类工作时间占比。所以「要不要换形态」不该靠争论，而该看这几个数里的哪一个已经越界。

还有一条顺序上的约束：**先改度量，再改边界**。当交付慢被归因为「组织不对」时，如果考核口径不变，新边界上的人会继续被旧口径塑形，几个月后行为回到原样，组织却多付了一次变更成本。度量本身不可信时（口径争议大、归因困难），先修度量；否则任何边界调整都会被放大成政治问题。

### 3.7 自检清单

- [ ] 取最近 20 个需求，画出「需求 × 团队」矩阵：多数需求要跨 4 个以上团队吗？
- [ ] 每条跨团队接口，都写明了 SLA、责任人与变更流程吗？没写明的接口在事实上仍是持续协作模式。
- [ ] 每个流对齐团队的成员名单里，是否包含完成其交付所需的全部技能？缺的技能由谁以什么模式提供？
- [ ] 每个流对齐团队统计过最近一个月花在环境类工作（上线、排障、权限、容量、依赖升级）上的时间占比吗？
- [ ] 平台类能力当前有几个消费者？消费者 ≤ 2 时，平台化的成本算过吗？
- [ ] 平台团队的考核表里，有没有「消费者侧采用与自助率」这一项？
- [ ] 每个 Enabling 角色的退出条件写下来了吗？它按什么指标被考核——赋能场次，还是对方的独立完成率？
- [ ] 复杂子系统团队的接口兼容策略是明文规则，还是「找他们商量」？平台或子系统的破坏性变更有没有兼容窗口？
- [ ] 一次端到端变更从提出到上线，实际经过几个团队、几次交接？新增一条业务流要动几个团队？前者是协商成本，后者是组织形态的边际成本。
- [ ] 有必须举证的合规（隐私、安全、AI 风险）责任吗？如果有，它归属于谁——一个角色，还是一个兼职？
- [ ] 各级负责人的考核项画在团队边界上，还是画在价值流上？
- [ ] 上一次组织调整之后，交付是否中断过？过渡期保留原有能力的安排有吗？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 交付被职能切成多段、端到端无人负责 | Stream-Aligned | 一次变更链上的协商次数降到接近零 |
| 同一环境复杂度被多个团队重复承担 | Platform（X-as-a-Service） | 复杂度不消失只转移，收敛成一次才划算 |
| 某项能力业务团队长期不会 | Enabling（Facilitating + 退出条件） | 产物是对方的能力，所以不退出就没有产出 |
| 某子系统复杂度极高或有举证责任 | Complicated-Subsystem | 集中 Intrinsic 负荷，并让责任有归属 |
| 规模化后自主与对齐同时要 | Squad / Chapter / Guild（谨慎借鉴） | 不同对齐需求拆到不同连接维度，避免一条线过载 |
| AI 带来三类新负荷 | AI Platform + AI Enabling + AI 治理 | 重复付的收敛、要教的传递、要举证的给归属 |
| 多业务、口径可分 | 事业部制 + 共享能力载体 | 按损益切分后，跨 BU 复用要靠单独的载体解决 |
| 多时区、同步成本高 | Stream-Aligned + 异步优先 | 跨时区同步协作的代价随时区差放大 |
| 强合规 / 强安全 | Complicated-Subsystem + 门禁 | 举证责任必须有归属，且要挂在流程的某个环节上 |

> 本节小结：本主题下决定形态选择的**唯一那条约束是「一次端到端变更要跨几个团队、以及这些负荷落在谁的头上」**——前者决定协调成本，后者决定认知负荷总量；复用率、业务对齐、专业沉淀都是这两条的衍生结果，而不是可以独立取舍的选项。第二条要一起看的是**度量归属**：边界画在哪，KPI 就画在哪，而人优化被度量的东西——度量不改，任何边界调整都只是换名字。
>
> 💡 **思考锚点**：取你最近 20 个需求，数一遍每个跨了几个团队（多数要跨 4 个以上吗），再数同一个共享能力当前被几个团队各自实现过（k 是 ≤2、还是落在 3–5 的回本区间）——协商次数与 k 这两个数，比任何「要不要设平台团队」的争论都更能决定你这次该改边界、还是先改度量；你的两个数各落在哪一档？
