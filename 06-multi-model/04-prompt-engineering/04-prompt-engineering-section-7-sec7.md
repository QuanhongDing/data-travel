## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"提示写在代码里 / 配置中心 / 提示管理平台 / 供应商的提示控制台 / 微调替代提示 / 自动优化提示"打分是常见做法，但它有三个结构性问题：

① **同一列在不同处境下方向相反**——"编辑便利"对高频迭代的团队是必需，对**判据稳定、改动极少**的团队是**风险**（越容易改，越容易在没有评测的情况下改）。
② **打分表隐含"这些选项互斥"**，而真实做法是组合（**配置中心管版本 + 自建评测门禁 + 供应商的解码层能力**是常见组合）。
③ **最关键的判据不是可打分的维度，而是门槛**——**"改动有没有评测门禁"**与**"版本标识完不完整"**这两条是门槛。**一个编辑体验极好、但没有分组评测的平台，会让你改得更快而判断力更差。**

**本节采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| **评测门禁** | 它能不能在改动时跑一组固定样本、按类型分组报结果？ | **这是门槛不是权重**——没有它，改动无法被判断 |
| **版本标识完整性** | 一次调用能不能记录 `(prompt_version, model_version, decode_params, retrieval_snapshot)`？ | 不完整 → 行为变化无法归因（**最常见的成因是模型版本或检索快照变了**） |
| **可导出** | 提示与评测样本能不能导出成不依赖产品的材料？ | 不能 → 换平台要重写全部提示与评测 |
| **分层能力** | 它支不支持把一个提示按层管理（判据 / 推理引导 / 示例 / 契约）？ | 不支持 → 换代时整份重写 |
| **档位适配** | 它能不能为不同模型档位维护不同渲染配置并各跑评测？ | 不能 → 降级链的正确性无数据支撑 |
| **运维承接** | 谁维护门禁样本、谁在换代后重跑评测？ | 本主题的人力集中在标注与迭代，**没有承接人的方案半年后提示无人敢改** |

**这 6 条里，前两条是门槛（不满足直接出局），后四条是权重的输入。**

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| **硬编码在业务代码里** | 最简 | 提示与逻辑同文件 | 单处调用、判据稳定 | 改提示走发布；**无版本、无评测** |
| **配置中心 + 自建评测** | 现实默认 | 提示进配置（有版本），评测自建（jsonl + 脚本） | 多数团队 | 评测与分区要自己组织；门禁要自己接 CI |
| **提示管理平台** | 成品能力 | 提示编辑、版本、A/B、评测一体交付 | 提示多、非工程角色要改 | **评测口径由产品定**；导出能力要核 |
| **供应商的提示控制台** | 随模型走 | 供应商侧的提示版本与评测 | 单供应商为主 | 与供应商绑定；跨模型适配要自己补 |
| **微调替代提示** | 另一条路 | 把判据固化进权重 | 风格与格式需要强稳定 | **规则会变时成本极高**（重训）；不解决"判据说不清" |
| **自动优化提示** | 前沿 | 按评测指标搜索提示与示例 | 有扎实评测集的团队 | **过拟合到评测集**；可解释性下降 |

**这六个候选其实分三族**：

- **存放族**（硬编码、配置中心、平台、供应商控制台）——**解决"提示放哪、怎么改"**，差别在**版本与评测的归属**。
- **固化族**（微调）——**解决"行为怎么固定"**，代价是**改动成本从分钟级跳到训练级**。
- **搜索族**（自动优化）——**解决"谁来写"**，代价是**把偏差固化**（它优化你给的指标）。

**族内可替换，跨族不可换**：存放族内部换（配置中心 ↔ 平台）代价可控（**前提是提示与评测样本能导出**）；从存放族换到固化族**不是替换而是取舍**（规则会变就别固化）；而**搜索族建在存放族之上**——**没有分组评测时，自动优化只会把偏差固化**。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 评测的归属：你的门禁、产品的口径，还是没有评测

**机制是什么**：评测样本与分组口径归谁——**你的门禁**（样本、分区、放行条件都由你定）、**产品的口径**（它给一个通过率，分组由它的实现决定）、**不存在**。

**它在各候选中的实现差异**：配置中心族**没有评测能力**（要自建，但自建的口径完全可控）；平台族**有评测但口径由产品定**（能不能按你的输入类型分组，取决于它的设计）；供应商控制台**通常只给总体指标**。

**由此必然导出的性质**：因为**"总体通过率会把某类全错平均掉"**（§2.2），所以**评测的归属决定了你能看见什么**——只拿到总体数字时，**你看不见那类会持续出错的输入**，而**团队最先收到的业务反馈恰恰来自它**。**这条性质说明"评测口径"不是功能细节，而是判断力的边界。**

**失效条件**：当业务反馈"某一类请求总是答错"而你的仪表盘一切正常时，说明评测口径不是你的。

#### 7.3.2 版本标识的完整性：能不能归因

**机制是什么**：一次调用的记录里，**行为相关的变量记全了没有**——`(prompt_version, model_name, model_version, decode_params, tool_schema_version, retrieval_snapshot)`。

**它在各候选中的实现差异**：硬编码族**基本没有**（提示在代码里，模型名可能写死）；配置中心族**能记提示版本，但常漏 `model_version` 与 `retrieval_snapshot`**（前者被当成"没变"，后者被当成"数据"）；平台族**通常记提示版本与模型名**。

**由此必然导出的性质**：因为**"提示没改、效果变了"最常见的成因正是 `model_version` 或 `retrieval_snapshot`**，所以**漏记这两项等于放弃了归因能力**——你会知道"行为变了"，但永远查不到为什么。**这条性质解释了一个常见现象**：团队花很大力气调提示，而真正变化的变量没被记录。

**失效条件**：当出现"同一份提示昨天好好的、今天不对"且无法解释时，先查这两项。

#### 7.3.3 存放位置的耦合度：改动的成本与影响

**机制是什么**：提示放在哪决定了**改一次提示的成本**，而**成本决定了改动频率**——改动频率又决定了它需要多少评测来兜底。

**它在各候选中的实现差异**：硬编码族改动走发布（成本高 ⇒ 改动少 ⇒ 但每次改动都是"大改"，影响面最大）；配置中心与平台族改动是分钟级（成本低 ⇒ 改动多 ⇒ **更需要门禁**）；供应商控制台介于两者之间。

**由此必然导出的性质**：因为**改动成本下降会让改动频率上升**，所以**"让提示更好改"这件事本身会放大对评测的需求**——这不是巧合，而是同一件事的两面。**这条性质给出一条排序**：**先把门禁建起来，再让提示好改**；反过来做，你会得到一个"改得飞快、但说不清哪次改坏了"的系统。

**失效条件**：当团队说"我们能当天改、当天上"而拿不出门禁结果时，说明顺序反了。

#### 7.3.4 采样与快照：检索式示例带来的隐藏变量

**机制是什么**：示例是**固定的**（写进提示，随提示版本走），还是**按输入检索出来的**（随索引与快照变化）。

**它在各候选中的实现差异**：硬编码与配置中心族默认是**固定示例**（简单、可复现）；平台族可能支持检索式示例；**自建的检索式示例最灵活，但最容易漏掉快照绑定**。

**由此必然导出的性质**：因为**检索式示例让"示例集"成了提示之外的第二个变量**，所以**不绑快照时，评测与线上看到的不是同一个输入分布**——离线通过、线上不同，且**无法归因**。**这条性质决定了本主题的一个硬要求**：`retrieval_snapshot` 必须进版本标识（§7.3.2）。

**失效条件**：当"重复跑同一条离线样本得到不同结论"时，先检查示例是否被动态检索。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| **存放族** | 评测标注人力 + 迭代人力 | 门禁样本的维护、换代后的重跑、多档位的版本数 | 随**提示数 × 档位数**增长 |
| **固化族**（微调） | 训练与再训练 | 规则变化时的重训成本、评测集要重做、**回滚是"换权重"不是"改指针"** | 随**规则变更频率**增长 |
| **搜索族** | 搜索算力 + 评测集质量 | 过拟合后的线上退化、可解释性下降带来的维护困难 | 随**评测集规模 × 搜索空间**增长 |

**成本函数的三条判据**：

① **存放族是"台阶 + 线性"**——建门禁是台阶，之后每次迭代便宜；**它的规模化压力来自"提示数与档位数的乘积"**。
② **固化族是"高台阶 + 低频"**——训练成本高、回滚成本高；**它的风险不在单次成本，而在"规则变了要重来一遍"**。
③ **搜索族的成本藏在"评测集质量"里**——**评测集差时，它把成本花在了过拟合上**（表面上很省钱，实际上在固化偏差）。

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：P = 提示数   T = 档位数   Q = 月调用量   L = 平均 prompt token
    c_in = 输入单价    h_ann = 门禁样本标注人力（人年）
    f_rule = 规则年变更次数   C_retrain = 单次重训成本

存放族：  Cost_store(P,T,Q,L) = Q × L × c_in + h_ann + P × T × 迭代人力
                                              ↑ 版本数=P×T，评测结果也是 P×T 份
固化族：  Cost_ft(f_rule)      = f_rule × C_retrain + 评测重做成本
                                       ↑ 与 Q 无关，与"规则变更频率"成正比
搜索族：  Cost_search          = 搜索算力 + 过拟合的线上代价（不可直接计）

反直觉的一条【推算】：规则年变更次数 f_rule 越高，固化族越不划算 ——
   当 f_rule × C_retrain > P × T × 迭代人力 时，就该用提示而不是微调；
   而在多数业务里，"业务规则一年变几次"是可估的，因此这个比较是可算的。
```

**这个式子的用法**：**先估 `f_rule`**（业务规则一年变几次）。它不为零且不小的时候，**固化族的成本函数形状（高频重训）与业务的变更节奏是错配的**——这正是"提示改的是输入、微调改的是权重"这句判据（§2.4）的经济含义。

### 7.5 决策树（每个分支都要有阈值依据）

1. **业务规则一年会变几次？**
   - **大于一两次** → **不要固化**（微调不划算，且回滚是换权重而不是改指针）；进入第 2 问。
   - 几乎不变（风格 / 格式固定）→ 可以考虑微调，但仍要保留提示层（判据与格式是两件事）。
2. **有没有一组门禁样本（哪怕 20 条）？**
   - **没有** → **先建这 20 条，再谈任何存放方案**——它是门槛。
   - 有 → 进入第 3 问。
3. **改提示的人是谁？**
   - 只有工程师 → **配置中心 + 自建评测**（最小、口径最可控）。
   - 有非工程角色要改 → 进第 4 问（平台的编辑能力有用）。
4. **提示数与档位数的乘积大概多少（`P × T`）？**
   - **几十以内** → 配置中心 + 脚本评测就够（`P×T` 份版本靠人管还管得住）。
   - 上百 → **需要工具支持**（版本矩阵与评测矩阵要自动化），选平台时**必须压测"能不能按档位各跑评测"**。

**阈值的诚实说明**：上表的"一两次""几十以内"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的变更频率与提示规模校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单处调用、判据稳定 | 硬编码（加版本号） | 配置中心 | 上平台是治理过剩 |
| 提示多、非工程角色要改 | 平台（**核评测分组能力**） | 配置中心 + 自建 | 平台若只给总体通过率，判断力会变差 |
| 多档位（降级链） | 配置中心 + 按档位分版本 | 平台（**核档位适配**） | 不支持按档位各跑评测则降级无法验证 |
| 规则稳定、风格要固化 | 提示 + **可选**微调 | 纯微调 | 纯微调会把判据也固化，规则一变就要重来 |
| 示例需求随输入差异大 | 检索式示例 + **快照绑定** | 固定示例子集 | 不绑快照 ⇒ 离线线上不一致且无法归因 |
| 有扎实的分组评测集 | 可以试自动优化（**生成候选 + 人确认**） | 纯人工迭代 | 没有分组评测时，自动优化会固化偏差 |
| 团队只有 1–2 人 | 配置中心 + 20 条门禁 | 平台 | 平台的门禁口径要自己核，省不了判断力 |

**组合的两条次序原则**：① **先把门禁建起来，再让提示好改**——顺序反了会得到"改得飞快、说不清哪次改坏了"（§7.3.3）；② **先分层，再按档位分版本**——不分层时，档位版本的维护量会成倍上升（每份都要整份重写）。

**第三条原则（方向相反但同样重要）**：③ **先把版本标识记全（含 `model_version` 与 `retrieval_snapshot`），再谈优化**——它是一行字段的事，而**它一旦缺失，之后所有行为变化都无法归因**（不可回填）。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 无门禁 → 有门禁 | 改动说不清是改进还是退化 | 抽真实请求 + 人工标注 + 接 CI | **以周计**（标注是主要工作量） |
| 硬编码 → 配置中心 | 改一个词要等发布 | 抽提示 + 建变量契约 + 改调用点 | 以月计，**与提示数成正比** |
| 平台锁定 → 可导出 | 换平台要重写提示与评测 | 逐提示重写 + 评测样本重建 | **以季度计**，且**历史评测结果不可迁移** |
| 无版本标识 → 有 | 行为变化无法归因 | 补 `model_version` / `retrieval_snapshot` 字段 | **以周计改字段，但历史行为永久不可归因** |
| 单档位提示 → 按档位分版本 | 降级后错一类 | 按层拆分 + 每档渲染配置 + 各跑评测 | 以月计，**版本数变成 `P × T`** |
| 检索式示例无快照 → 有 | 离线线上不一致 | 绑快照 + 记录示例 id | 以周计 |
| 微调固化 → 改回提示 | 规则变更后要重训 | 恢复提示层 + 评测重做 | **以月计**，且期间无法快速改规则 |
| 只靠提示描述结构 → 解码层约束 | 偶发成批解析失败 | 改走约束 + 简化下游 | 以周计（**先确认端点支持**） |

**一条硬结论**：八条里最贵的是**"平台锁定之后的收回"**——不只是提示重写，而是**历史评测结果不可迁移**（样本、分组、每次改动的前后对比都在产品里），因此**你会失去"过去一年的效果基线"**。**所以门槛（评测门禁、版本标识、可导出）必须在第一版就判对。**

**第二条硬结论**：上表里有一项的代价**部分不可逆**——"无版本标识 → 有"里的历史部分：**没有字段，过去的行为变化永远查不出原因**。**其余七项都是"要花时间"，这一项是"花时间也拿不回来"**；这决定优先级：**如果只能做一件事，先把 `model_version` 与 `retrieval_snapshot` 两个字段加上**（成本极低），而不是先优化提示本身。

### 7.8 小结

> 本节小结：六个候选之间的差异，最终都能归到四问——**评测归谁且能不能分组**、**版本标识完不完整（含 `model_version` 与 `retrieval_snapshot`）**、**改动成本与改动频率的耦合**、**示例是固定还是检索（有没有绑快照）**。四问决定了它们的分族（存放族 / 固化族 / 搜索族）与成本曲线（存放族随 `提示数 × 档位数` 增长、固化族随规则变更频率增长、**搜索族的成本藏在评测集质量里**）。**选型顺序不可颠倒**：先用"规则会不会变"筛掉固化族，再用"有没有门禁样本"决定一切的前提，最后才用团队承接能力在剩下的存放族里选——**把"门禁"当权重而不是门槛，是第二年最常见的失效原因**。**本主题有一条与其它主题不同的推论**：**"让提示更好改"会放大对评测的需求**——改动成本下降 ⇒ 改动频率上升 ⇒ 门禁从可选变成必需（§7.3.3），因此**顺序必须是"先门禁、后便利"**。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次**门槛检查**（不是打分）：评测门禁、版本标识完整性、可导出、分层能力、档位适配、运维承接——**哪一条是"不满足"而不是"分数低"**？那一条就是你最可能被迫迁移的方向（§7.7）；而你今天的补救成本，是否还落在"以周计 / 以月计"的那几格里？**另一问更具体**：如果明天换掉现在的模型供应商，**你的提示、评测样本与历史效果基线能不能带走**？答不出，说明你的提示还没有真正掌握在自己手里。
