#### §8.1 你改了一版提示，怎么判断这次改动是改进还是退化？

**1. 考察点**
- 是否知道**"改动必须有门禁样本"**，而不是看几个例子——这是本主题唯一一条几乎没有下限的门槛；
- 是否理解**总体通过率会把某类全错平均掉**，以及为什么被平均掉的那一类正是业务反馈最先到达的地方；
- 有没有"放行条件"的具体表述——是"**无任何分组的违例数上升**"，还是"总体不下降"；
- 是否知道**改动的影响面等于该提示服务的任务数**（一个提示服务 `k` 类任务时，改动者通常只测了其中一类）；
- 知不知道**样本必须从线上日志抽**，而不是照着需求文档构造；
- 加分项：能答出"这次改动由哪一组失败样本驱动、回滚目标是谁"（改动留痕的两个字段）。

**2. 参考答案框架**

**第一层：给出门禁的最小形态。** 一组固定样本（**抽真实请求 + 人工标注期望输出**）+ 一个脚本 + 结果留痕。**20 条就够挡住"反向优化"**，而成本是半小时量级的标注【经验：§6.3 登记的规模收益，随判据变动频率浮动】。这一步**不依赖任何工具**——一份 `jsonl` 就够（字段形态照 §4.2（2））。**为什么"真实请求"这四个字不能换**：构造样本只覆盖"我们想得到的情况"，而从线上日志抽样这个动作本身就在做一次分布校正，这才是它 20 条就有用的原因；换成"照需求文档编 20 条"，同样的工作量挡不住同类事故。

**第二层：说清"按什么分组报"。** 按**任务分区**（一个提示服务几类任务）+ 按**输入类型**（常见 / 边界 / 高危）分组；**只报总体通过率会掩盖某一类的退化**，而业务反馈恰恰来自被掩盖的那一类。报告的形态要满足两个条件——**每个数带分母、按组单列**：§4.2（2）给的样例是"资金 40/40、查询 29/30、边界 9/12"，只有三个数各有分母，才谈得上"哪一组退了"；只报一个总数时，"边界从 9/12 退成 8/12"会被 40/40 的满分吃掉。

**第三层：给出放行条件。** **"无任何分组的违例数上升"**，而不是"总体不下降"。这条差异是本主题最容易被忽略的一处——总体不降可以由一组的改进覆盖另一组的退化。它的作用也不止于放行：**它把"要不要上"变成一次可执行的判定**，因此门禁结果不是一份报表，而是**否决权的载体**（§7.3.1：评测口径归谁，决定了你有没有依据说"这一版不许上"）。

**第四层：说清改动的影响面。** 一个提示服务 `k` 类任务时，改动者通常只测了 1 类，**漏测 `k−1` 类**（§2.2）。因此**准入条件是"`k` 类都没退化"**；这也是"系统提示只放跨任务共用部分"的原因（缩小影响面）。**这一层同时是分层的经济含义**：不分层时，一次改动的成本等于整份重写——三类来源不同的改动撞在同一个发布单元上（§6.1 的机制解释），而分层的直接收益就是把改动范围与影响面对齐（§7.3.5）。

**第五层：留痕，让下一次改动能接上。** 每次改动在资产卡上留两栏——**原因（哪一类样本暴露了问题）与回滚目标（上一版是哪个版本号、回滚是不是改指针）**（§4.5 模板 1）。**留痕的作用不是审计，而是下一个改动者的锚点**：只留"跑过了"而不留"哪一组驱动了它"，半年后团队会把同一个改动再来一遍，并且这次会以为它是新的（§6.1 的③）。**这一层有自己的失效条件**：判据本身还在变时（规则一周一变），固定样本集会在两周内失效【经验：失效快慢随改动频率变】——此时缺的不是留痕，而是稳定的判据。

**3. 常见陷阱**
- **只答"看几个例子的效果"**。它看起来对，因为它确实是现在的做法、也的确能发现一部分退化；**错在验证的对象**——改动者自挑的例子天然偏向本次改动的收益面，而被它伤害的那一类恰好不在他的取样范围里，§6.3 的那次反向优化正是这样发生的。
- **有样本但不分组**。它看起来对，因为"有固定样本"已经比没有强得多；**错在平均**——总体通过率会把"某类全错"平均掉，而这恰恰是唯一一种会让团队在改动当天看不到退化的口径。
- **放行条件写成"总体不下降"**。它看起来对，因为它比"看着更好"严格得多；**错在它允许用一组的改进覆盖另一组的退化**——而业务受影响是按组发生的，不是按总量发生的。
- **答不出一个提示服务几类任务（`k` 答不出）**。它看起来只是个无害的细节；**错在它是影响面的分母**——答不出 `k`，就不知道这次改动该测几类，于是"漏测 `k−1` 类"连发生都不会被察觉。
- **样本是自己构造的，不是从线上日志抽的**。它看起来更省事、也更"干净"；**错在分布**——构造样本只覆盖你想到的情况，而反向优化的受害者正是"没想到的那一类"。

**4. 追问预测**
- "20 条样本怎么抽？随机还是按类型分层？"（要点：抽的动作要做分布校正——按输入类型分层抽；只覆盖一类时，它挡不住跨类型的退化。**20 条这个量级是 §6.3 的【经验】档**，它挡的是"反向优化"，不是精细比较）
- "边界样本谁来标注？"（要点：标注是人力三项里唯一无法自动化的一项；判据由业务方给、脚本由工程方维护）
- "如果这次改动只对一个分组有益、对另一组有害，你怎么办？"（要点：按放行条件就是不放行；然后再区分"有害"是本组的真退化，还是那一组的样本已经过期）
- "评测集要不要随业务演进更新？更新的判据是什么？"（要点：候选样本从日志滚出来——按"线上被判为错"或人工纠错筛候选、人工确认后进样本集；自测判据是"样本集里最近新增的一条是什么时候来的"，§6.3 的做法④）
- "换模型厂商时，这份门禁还要不要重跑？"（要点：要，且要整批重跑——`model_version` 的变化与提示改动会在同一份调用记录里竞争归因，§7.3.2）

**5. 参考资料**

#### §8.2 一个提示服务好几类任务，你怎么组织它？为什么系统提示不能什么都放？

**1. 考察点**
- 是否理解**改动的影响面 = 系统提示服务的任务数**，而不只是"提示写在哪里"；
- 是否知道分层（判据 / 推理引导 / 示例 / 契约）是为了**限定改动范围**，不是为了好看；
- 知不知道**分层的切法不是按语义，而是按"谁会让它变"**（四层的变更来源各不相同）；
- 有没有换代意识（哪一层随模型变、哪一层跨档位可复用）；
- 加分项：能给出"分层后，业务改判据段、工程改推理引导段"这个分工成立的条件。

**2. 参考答案框架**

**第一层：给出分层与归属。**
- **系统提示**：**跨任务共有的判据**（放它的代价：改动会波及 `k` 类任务）；
- **任务提示**：单任务特有的判据与输出要求；
- **示例段**：判定边界的实例（固定示例 = 核心判据；检索式 = 长尾，§3.2.4）；
- **输出契约**：字段、枚举、失败路径。

把四层的**变更来源**摊开，才看得出归属为什么只能这样划：

| 层 | 变更来源（谁会让它变） | 谁该改 | 改一次的影响面 |
| --- | --- | --- | --- |
| 判据段 | 业务规则变 | 业务方（他决定"算不算升级"） | 它服务的全部任务 |
| 推理引导段 | 换模型档位 | 工程方 | 本提示的所有输入 |
| 示例段 | 边界样本暴露出新的混淆 | 业务方给判例、工程方整理 | 只有边界类输入的判定 |
| 输出契约段 | Schema 变更（不兼容变更） | 工程方 + 下游 | 所有消费该输出的代码 |

**这套划法有一条判据**：**四层不是按语义切的，是按"谁会让它变"切的**（§6.1 的"四层划分依据"）。按语义切（角色 / 任务 / 例子 / 格式）读起来更顺，但判据与推理引导常常落在同一层里，于是换模型时仍然要动到判据——**那等于没分层**。

**第二层：说清"分层"的收益是"限定改动范围"。** 业务变 ⇒ 改判据段；换模型 ⇒ 改推理引导段；补边界 ⇒ 改示例段。**不分层时每次改动的影响面都是整份提示**（§6.1 的失败教训）。**这一层的机制解释要一起给出来**：三个来源不同的改动撞在同一个对象上时，"整份重写"不是习惯问题而是结构问题——只要四层的变更来源没有分开，重写就是唯一可行的改法，而重写又必然带进新的措辞差异，这就是"改得越多越说不清"的来源（§6.1）。

**第三层：给出可核查的判据。**
- 同一判据（如"含全渠道"）**只出现一处**——多处即分叉起点；
- **改一句系统提示，需要重测几类任务**——这个数就是影响面；
- 分层后，**换代时只动一层**；
- 最省事的自测：**随便挑一次历史改动，问"它动了哪一层"**——答"整份都动了"，就是这一条要修的地方（§6.1 把它写成了一条可执行判据）。

**第四层：换代意识（加分项）。** 推理型模型把推理主体内化了，因此**推理引导段是换代时最可能被删或重写的一层**（§5.3.1）——**判据段与示例段跨档位可复用，推理引导段不可假定**。这一层还有一条直接的落地形式：**"按档位分版本"从可选变成必需**，因为同一份提示在降级链的相邻两跳上可能连"该写什么"都不同（§5.3.1 与 §3.2.8）。

**第五层：说清分层的两个边界。** ① **分层不省成本，它换的是判断力**——换来"改动可判断"，付出的是分层设计成本与按变更来源维护的纪律（§6.1 把它写成"用常备投入换掉一类无法察觉的失败"）；② **它有一条前提**：提示只有一处调用、判据只有一条且短期不换代时，分层的收益兑现在"下一次变动"上，而它不发生在今天（§7.3.5 的失效条件）。**换句话说，分层是一条"提前布局、成本很低"的动作**——§5.7 把它排在"今年就该做"而不是"可以试点"那一档，理由正是**它不依赖任何采购**。

**3. 常见陷阱**
- **把所有判据都写进系统提示**。它看起来对，因为"共用"确实能少写几遍；**错在影响面**——系统提示服务的任务数就是改动影响面的分母，判据上移一次，以后每次改它都要重测 `k` 类。
- **从单任务扩展时复制一份改改**。它看起来最快；**错在分叉**——同一判据出现两处之后，两处会各自漂移，而"哪一份为准"要等它们给出不同结论时才会被发现。
- **不分层（换代时整份重写）**。它看起来只是"结构化程度低"；**错在它把三类来源不同的改动绑成一个发布单元**，于是任何一次改动的成本都等于整份重写（§6.1）。
- **答不出 `k`（服务几类任务）**。它看起来是记性问题；**错在它是"这次改动该测几类"的唯一依据**——答不出 `k`，影响面就无法被限定。
- **按语义而不是按变更来源分层**。它看起来更自然（按"角色 / 任务 / 例子 / 格式"读起来顺）；**错在层的边界会跟着变**——按语义分出的层里，判据与推理引导常常落在同一层，于是换模型时仍然要动到判据。

**4. 追问预测**
- "系统提示与任务提示的边界怎么划？判据跨几类任务才该上移？"（要点：判据的判据是"它服务的任务数"与"改它要重测几类"；跨任务的共用判据才上移，且上移的代价要写进变更记录）
- "如果两个任务的判据冲突，怎么办？"（要点：冲突说明它本就不是"共用判据"——要么下沉到各自的任务提示，要么把冲突条件写成一个显式的分支判据）
- "多档位时，哪一层按档位分叉、哪一层共享？"（要点：判据段共享、推理引导段与示例密度按档位分叉，§8.6 与 §3.2.8）
- "提示里的某一段你怎么判断它还能不能删？"（要点：问"它由哪一类样本驱动"；答不出依据的段落是 §5.7 那条反直觉动作"先删提示，再写提示"的对象）
- "分层之后，版本号要跟着分层走吗？"（要点：不必——`prompt_version` 是整份渲染配置的版本，"动了哪一层"记在变更记录里，这正是 §4.5 模板 1 的变更记录栏的用途）

**5. 参考资料**
- 本主题内部（逐条可核）：§3.2.1 / §3.2.2（单段与模板）、§3.2.8（按档位分版本）、§4.2（1）（四段实例：`system` / `task` / `examples` / `output_contract` 与失败路径）、§4.5 模板 1（资产卡的"四段"栏与变更记录栏）、§5.3.1（推理主体换位）、§5.3.6（四段化同时是跨供应商可移植的最小版本）、§6.1（四层划分依据 = 谁会让它变）。
- 外部可核验入口：**OpenAI Structured Outputs / Anthropic Tool Use** 一类能力条目可核"输出契约这一层可以交给谁"（`01-modeling/README.md` 的工具清单与 `02-data-science/02-classification` 的 §4.3 都把它们列在"LLM 输出结构化建模 / 要结构化输出选 Function Calling / Tool Use"一栏）。

#### §8.3 Few-shot 示例应该放几条、从哪来？检索式示例有什么坑？

**1. 考察点**
- 是否知道**示例是判据的实例化**，且**必须含反例**；
- 是否理解**示例的边际成本随调用量重复支付**，因此"数量"不是第一优先级；
- 知不知道检索式示例的隐藏变量（快照），以及它与缓存布局的负面耦合；
- 知不知道"判据能不能文字化"决定了示例是可选还是必须（§3.1 的约束 1）；
- 加分项：能给出示例集自己的版本管理与测试动作（"数反例条数"与"数与判据无关的示例条数"）。

**2. 参考答案框架**

**第一层：先说"为什么需要示例"——判据能不能文字化。** 判据能被写成可判定的句子时，示例是可选；**只有"见过才算数"的判据（文风、某类缺陷、边界上的例外）才必须靠示例**（§3.1 的约束 1）。这一层决定了后面所有讨论的位置：**示例不是格式的说明书，它是判据的实例化**——先有判据，才轮到给它配例子；反过来做（先堆例子再猜判据）会让示例集变成一个没人能解释的集合。

**第二层：说清数量与构成。** 数量不是第一优先级，**构成才是**——**必须含边界与反例**；只有典型样例时，模型学到的是"典型样例的形状"，**边界行为完全未被定义**，而边界正是业务追问的地方。判据是两个可数的量——**反例条数为 0** 说明边界未定义；**每条示例对应哪一条文字判据**说不出来，说明这条示例的用途是格式而不是判据。**示例集要有自己的版本号**（§4.2（1）的实例与 §4.5 模板 1 的"示例集版本 examples-v3（与提示版本一同发布）"就是这个形态），否则"提示没改、行为变了"会变成一句无法回答的话。

**第三层：说清成本。** 示例 token **随每一次调用重复支付**（§4.6）——因此"为了展示格式而放的重复示例"是可省的成本；长尾示例应改**检索式**（按需注入）。**成本口径是可算的**：设示例占 prompt 的 `ρ_ex`、月调用量 `Q`、平均 prompt token `L`、输入单价 `c_in`，则示例的月成本 ≈ `Q × L × ρ_ex × c_in`【推算：口径为四者相乘，再按月数放大成年度口径】（§7.4 第 2 条推导是同一形状的式子——那里的 `ρ` 指"系统提示与示例合计"，本处只算示例这一项）。**这条口径的用法是排序**：`ρ_ex` 大时先删与判据无关的示例（不花钱），`ρ_ex` 小时先做缓存布局（同样不花钱）——**换模型要重跑门禁，是这两件事都做完之后才考虑的**。

**第四层：检索式示例的三个坑。** ① **检索误差**（选到不相似的示例比不给更糟）；② **分布漂移**（一个月后同一输入可能取到不同示例 ⇒ **提示没变而行为变**）；③ **破坏缓存**（示例插在稳定前缀里会让前缀缓存失效，§5.3.4）。**修法**：**绑快照 + 记录示例 id + 放在稳定段之后**。**机制上要讲清它为什么比固定示例难**：检索式示例让"示例集"成了提示之外的第二个变量，于是提示从一个对象变成两个对象——**提示版本管"写下来的部分"，快照管"那次调用实际看到的部分"**；只记前者时，快照就是一个不可见的自变量，而它的变化频率通常远高于提示版本（§7.3.4）。

**第五层：说清示例的顺序与更新。** ① 固定示例的**排列顺序会影响结果**，因此它属于提示版本的一部分，改动要重跑门禁；② **示例集会过期**——判据变了而样本没变时，它教的还是旧判据，而**它不会报警，只会让结果看起来正常**（§3.2.8 的失效点②）。**更新的判据是"样本集里最近新增的一条是什么时候来的"**（§6.3 给的自测口径）；候选样本应当**从日志滚出来**——按"线上被判为错"或人工纠错筛候选、人工确认后进集合。

**3. 常见陷阱**
- **只答"多给几条"**。它看起来对，因为示例确实常常"多一点更稳"；**错在优先级**——数量不是第一优先级，构成才是；充满典型样例的示例集，只会让模型把"典型样例的形状"学得更牢。
- **示例全是典型样例（无反例）**。它看起来干净、也更容易标注；**错在边界没有被定义**——而那正是业务追问的地方，也是改动最容易互相伤害的地方。
- **不知道示例是重复支付的**。它看起来像"一次性的编写成本"；**错在它是乘法**——示例 token 随每一次调用重付，因此它与调用量线性放大，而不是与提示数线性放大。
- **用检索式示例但不绑快照**。它看起来更好（长尾覆盖更全）；**错在你多了一个看不见的自变量**——离线通过、线上不同，而且无法归因（§4.4 的迁移表把这一条写得很直：不绑快照时，历史评测结果不可比）。
- **把动态示例插在系统提示后面**。它看起来"重要内容在前"；**错在它把稳定前缀切断**——示例插在前缀里会让前缀缓存失效，换取的收益被成本吃掉（§5.3.4）。

**4. 追问预测**
- "示例的顺序会不会影响结果？怎么处理？"（要点：会；因此顺序属于提示版本的一部分，改动要重跑门禁，固定示例要放在稳定段之前、检索式示例要放在稳定段之后）
- "判据改了，示例集怎么同步？"（要点：示例集有自己的版本号与变更记录；候选从线上错例滚出来、人工确认后进集合，判据与示例在同一份资产卡上登记，§4.5 模板 1）
- "检索式示例的相似度阈值怎么定？"（要点：它是判据问题不是调参问题——先问"取到不相似的示例时，下游会不会更差"；阈值要能用门禁样本演示，否则它只是一个没人能解释的数）
- "固定示例与检索式示例能混用吗？怎么混？"（要点：能——核心判据用固定示例、长尾用检索式，但检索式那部分必须排在固定段之后，且要绑快照、记示例 id，§3.2.4）
- "示例集要多大规模？"（要点：先答"反例有几条"，再答规模；规模由"要分辨多大差异"决定，而这与"挡住反向优化"所需的规模不是一回事，§6.3）

#### §8.4 CoT 什么时候有用？为什么它在某些任务上只是白花成本？

**1. 考察点**
- 是否理解 CoT 的机制（**把一步跳到答案换成多步生成**）；
- 知不知道它的**收益条件**（推理步数 `s` 较大），以及 `s ≈ 1` 时的成本形态；
- 有没有"CoT 中间结果不是真值"的意识，以及它对下游的污染路径；
- 知不知道 CoT 有一条**收益条件已经变了**的情形（推理型模型把推理内化）；
- 加分项：能说出"怎么用一次对照实验判断该不该留它"。

**2. 参考答案框架**

**第一层：给出机制与收益条件。** CoT 让模型在生成中间步骤时**用到更多计算与更多输入信息**；因此收益主要体现在**多步推理任务**上（`s` 较大）。**`s ≈ 1` 的分类 / 抽取任务上，它只增加输出 token 成本**（§2.2 的判据，机制上的直觉是 `p^s`：每一步的正确率都要乘进去）。**这一层的判据是可操作的**：先答"这个任务要几步才能得出答案"，再答"它现在几步"——两问答不出时，CoT 是默认加上去的，不是被选上的。

**第二层：说清代价。** ① **输出 token 上升**（成本与延迟）；② **中间步骤进入上下文，可能反过来污染结论**——一个错误假设会被后续步骤围着展开，最终结论看起来论证充分却建立在错误前提上；③ **失败更难排查**（结论错时，是推理错、前提错，还是判据本身模糊，三者难以区分）。**这三条代价共同决定了它的适用面**：它不是"想得更清楚"的免费开关，而是把"一次判断"换成"一段可被追问的生成"。

**第三层：给出验证动作。** 对 `s ≈ 1` 的任务做一次**"去掉 CoT"的对照实验**——同一批门禁样本跑两遍，比较分组通过率与输出 token 数；若通过率不变而成本下降，就应去掉。**这是最便宜的一次优化**：它不需要任何采购、不需要供应商支持，只需要一份已经存在的样本集（§3.2.5 的判定方法与此一致）。**这一层反过来也是"门禁样本"的一个额外用途**：没有它，这个对照做不了，于是 CoT 只能一直留着。

对照实验要按三个量一起看，只看一个量会得出错结论：

| 判断项 | 留 CoT 的条件 | 去掉 CoT 的条件 |
| --- | --- | --- |
| 分组通过率 | 至少有一组的通过率因它而升 | 各组都不变，或变化落在样本噪声范围内 |
| 输出 token 与延迟 | 上升的幅度是业务能接受的 | 上升明显而通过率不动 |
| 失败形态 | 中间步骤让错误更容易被定位 | 结论错时，多出来的中间步骤反而让"错在哪"更难答 |

**判据的顺序不能倒**：先用分组通过率定"要不要"，再用成本定"值不值"；反过来先看成本，会砍掉一组真正受益的输入。

**第四层：说清两个危险用法。** ① **把中间结果当真值**（写进日志供人查看、甚至被下游消费）——**中间步骤是模型的草稿，不是结论**；一旦落库并被下游依赖，它就变成了一个没有任何保证的字段；② **对推理型模型照搬"请一步步思考"**——推理已经内化，那段引导可能干扰它自己的推理（§5.3.1）。**第二种用法的判别方法是可执行的**：把推理引导段删掉、其余不动，在同一批样本上比一次——**它属于换代时最可能被删或重写的那一层**。

**第五层：把 CoT 放回"分层"里看（加分项）。** CoT 不是一种独立的方案，它是"**推理引导段**"这一层的实现形态；因此它天然有三件事要一起说：**这一层随模型档位变**（§5.3.1）、**它与 ReAct 是两件事不要叠加**（缺推理用 CoT、缺信息用 ReAct，两者都给会互相干扰，§3.4）、**它的收益幅度不给数**（只对"你自己的门禁样本 + 你自己的任务"成立，§5.3.5 对自动优化用的是同一条口径）。**这一层还解释了为什么"用了新模型就不必写提示"是过度宣传**：换代改的是推理主体，不是取消判据（§5.5 的第 1 条）。

**3. 常见陷阱**
- **一律加 CoT（"大家都在用"）**。它看起来稳妥，因为加它几乎不会让结果明显变差；**错在它是一笔持续支出**——输出 token 与延迟都随调用量放大，而收益只在 `s` 大时出现。
- **把 CoT 中间结果写进日志并被下游依赖**。它看起来是"白拿的可解释性"；**错在它把一个没有保证的生成物变成了接口**——中间步骤是草稿，下游一旦依赖，它就成了一条没有门禁的输出路径。
- **从没做过"去掉 CoT"的对照**。它看起来不必要，因为"现在跑得挺好"；**错在"挺好"没有被定义**——没有对照就没有"这一步是不是多余的"这个结论，而这恰恰是成本最小的一次优化机会。
- **对推理型模型仍铺步骤**。它看起来更保险（多给点引导总没坏处）；**错在前提已经变了**——推理主体换位之后，这段引导可能干扰模型自己的推理，而判别方法只是"删掉它、其余不动、比一次"（§5.3.1）。
- **把 CoT 与 ReAct 叠在一起**。它看起来"又想清楚又能查资料"；**错在两者各自解决不同缺口**——缺推理用 CoT、缺信息用 ReAct，叠加会让链路多出一层互相干扰的中间产物（§3.4）。

**4. 追问预测**
- "怎么判断一个任务的 `s` 有多大？"（要点：数"从输入到答案必须经过几个不同的判断"，并对照模型现在实际输出几步；两问答不出时，先补一份最小门禁（§6.3 的 20 条量级【经验】）再谈）
- "CoT 与 ReAct 能一起用吗？"（要点：不要默认叠加——缺推理用 CoT、缺信息用 ReAct；两者都给会互相干扰，且工具结果进上下文本身就是一条注入通道，§4.2（5））
- "中间步骤要不要落库？落库的用途是什么（排障还是别的）？"（要点：排障可以，被下游消费不行；判据是"这个字段被程序读过吗"——被读过它就已经是接口了）
- "推理型模型的思考过程要不要展示给业务？"（要点：要"给出依据"时，让它**额外输出一段摘要**，而不是依赖它的内部思考——可解释性要用一个显式的产物来满足，§5.3.1）
- "去掉 CoT 之后通过率掉了，说明什么？"（要点：说明这个任务确实 `s` 大，或者说明你的判据里有一部分没有被文字化、只能靠中间步骤兜住——两种情况的处置不同：前者保留，后者去补判据）

**5. 参考资料**
- 本主题内部（逐条可核）：§2.1（CoT 的机制与代价）、§2.2（收益条件与 `p^s` 直觉）、§3.2.5（结构、代价与失效点）、§3.4（CoT 与 ReAct 的组合规则）、§5.3.1（推理主体换位）、§5.5（过度宣传的第 1、4 条）。

#### §8.5 输出要求模型返回 JSON，怎么保证它一定可解析？

**1. 考察点**
- 是否知道**"请返回 JSON"是一个请求，不是一个约束**，以及这条区别的后果由谁承担；
- 知不知道按可靠性排序的四条路线，以及每一档的适用条件；
- 有没有"失败路径"的具体设计（重试上界、宁失败不猜、兜底分支的监控）；
- 知不知道 Schema 设计的两条约束（泄压阀字段、Schema 变更是不兼容变更）；
- 加分项：能说清"形状"与"语义"的分工线怎么划，以及这条线由谁负责划。

**2. 参考答案框架**

**第一层：先给出四条路线（按可靠性排序）。** ① **解码层约束**（结构不合法根本生不出来，最可靠）；② 结构 + 校验 + **重试**（有轮次上界，且重试次数要可统计）；③ 校验但不重试（关键链路宁失败不猜）；④ **只靠提示描述**（不该作为生产形态）。**这四条不是四个产品，是四种失效强度**：第 ① 档把"形状"从概率保证变成结构保证；第 ②、③ 档仍是概率保证，差别在于失败时是重试还是失败；第 ④ 档把可靠性交给"模型遵守请求的概率"与"下游解析成功"的乘积（§6.2 的机制解释）。

**第二层：说清第 ④ 条为什么危险。** 它平时看起来能用，**直到某次输出带了 Markdown 围栏或注释**——而这类失败**通常出现在流量最大的那天**（§6.2 的失败教训）。**机制上要讲清两点**：一是"上线一段时间没问题"不等于没问题，它只是**把失败推到了尾部分布上**，而尾部正是流量峰值所在；二是**总体失败率会把这类失败掩盖掉**——因此要看的不是均值，而是**失败集中在哪一类输出上**（§6.2 的自测动作）。

**第三层：说清第 ① 条带来的两个变化。** ① **提示里那段结构描述可以删掉**（省的是每次调用的 token，按调用量放大）；② **下游代码可以简化**（解析失败从常态分支变成兜底分支）。**但兜底分支的触发次数仍要监控**——它仍是健康指标：**不该为零**（为零说明没在统计），**也不该升高**（升高说明约束没覆盖全）。**这一层还有一条反向要求**：形状交给系统之后，**提示里剩的格式描述句数应当收敛到"端点不支持"的那几条**——剩下的每一句都在问同一个问题："这一层为什么没交给解码层？"

**第四层：说清 Schema 设计的两个要点。** ① **留一个自由文本字段**（`reason` / `note`）作为泄压阀——不留时模型会把解释塞进不该塞的字段（例如把解释写进枚举值），**而那种输出在结构上合法、在语义上错乱，比解析失败更难发现**；② **Schema 变更是不兼容变更**，要版本（同工具 Schema 的管理），并且要记住它**与提示改动在同一份调用记录里竞争归因**——§4.2（4）的 `tool_schema_version` 就是为它留的位置，没有它时"这次退化怪提示还是怪 Schema"无法回答。

**第五层：说清它保证不了什么（这条最容易漏）。** **它只保证形状，不保证语义**——JSON Schema 这类机制只能校验"是不是字符串、是不是枚举值"，校验不了"这个客户到底是不是 VIP"（`01-modeling/05-ontology-modeling` 的 §5 把这条边界写得很直）。因此它**不是**"输出可靠"的完整答案：**判据仍在提示里，形状在解码层**，两者分工之后才谈得上闭环。**这一层的落地形式是三次检查**：查端点在不在支持列表、把提示里剩下的格式描述圈出来、把解析失败率作为常驻监控项。

**3. 常见陷阱**
- **只答"提示里写清楚格式"**。它看起来对，因为多数时候确实能解析；**错在它的可靠性是乘积**——模型遵守请求的概率 × 下游解析成功，而写提示的人通常只看前一项。
- **提示里写完整 JSON 示例**。它看起来最保险（"都给样子了"）；**错在两头付钱**：这段描述每次调用重复支付，而它并没有把失败从概率里去掉——**示例展示的是形状，不是约束**。
- **没有解析失败率监控**。它看起来不必要，因为"最近没出过问题"；**错在它把失败推到了尾部**——不监控时，你只能在流量峰值那天第一次看见这个数。
- **Schema 不留自由文本字段**。它看起来更"严格"；**错在压力一定会找出口**——解释会被挤进枚举值、挤进数字字段，或者干脆丢掉，而丢掉解释的那一支最危险（下游看到的是一个完全合法的空结论）。
- **失败后静默降级（把解析失败当成"没有结果"）**。它看起来是"优雅降级"；**错在它把一次硬失败伪装成一次正常返回**——下游会当成"确实没有这个结果"，而这两件事含义完全不同。

**4. 追问预测**
- "端点不支持约束解码怎么办？"（要点：退回第 ② 档"结构 + 校验 + 重试"，并给重试设上界、留可统计的失败计数；同时把提示里剩下的格式描述收敛到"端点不支持"那几条）
- "解析失败时重试几次？重试还失败呢？"（要点：轮次上界要写进配置；关键链路宁失败不猜——§4.2（1）的实例把这条路径写成 `on_parse_failure: retry_once_then_error`）
- "Schema 里的枚举加一个值，算不算不兼容变更？"（要点：对下游解析代码而言通常要动、要版本号；关键是它和提示改动会在同一份调用记录里竞争归因，所以两者必须各有版本）
- "怎么监控解析失败率而不被小样本类型掩盖？"（要点：按输入类型分组报，与门禁同一口径——总体失败率会把集中在小样本类型上的失败掩盖掉，§2.2）
- "什么时候不该上约束解码？"（要点：输出只给人看、或 Schema 还在频繁变形时——Schema 变更是不兼容变更，改一次要动一次版本，此时先稳定判据更划算，§5.3.2）

#### §8.6 你们接了多档位模型做降级，怎么保证降级之后还能用？

**1. 考察点**
- 是否知道**提示与档位耦合是结构性的**，而不是某个产品的缺陷；
- 是否理解**降级链的正确性等于"每一跳的行为可接受"**，而不是"每一跳还能返回结果"；
- 有没有"各档位各跑一遍评测"的实践，以及"先分层、再按档位分版本"这个顺序；
- 知不知道版本数与评测轮次的量级怎么算（`提示数 × 档位数`）；
- 加分项：能把"降级后的行为"写进故障演练，并给出验收动作。

**2. 参考答案框架**

**第一层：先指出问题的根因。** **多档位共用一份提示**时，那份提示通常是**按旗舰模型的遵循能力写的**（长指令、多约束并列、推理步骤铺开）。弱模型的**遵循能力不足**，于是行为不是"差一点"，而是"**错一类**"（§6.4）——输出格式可能不再合契约，判据也整体偏移。**根因要讲清是哪一条机制**：**提示与档位耦合是结构性的**（§5.3.6 的成熟度行把它写作"① 与 ③ 不成立、② 核不到"），因此"一个在 A 上调好的提示在 B 上是否等效"只能实测，不能假定。

**第二层：给出修法。** ① **按档位分版本**：`(prompt_version, model_tier)` 是完整标识；**共享判据段**（业务规则不该因档位而变）、**按档位分叉推理引导段与示例密度**；② **每档各跑一份评测**（同一样本集，分组口径一致）；③ **把"降级后的行为"写进故障演练**——演练时真的切到低档位，看输出是否仍可被下游消费（格式）与业务接受（判据）。**②③ 的判据要一起给出来**：验收动作是"同一份样本集在各档位各跑一遍，比对分组通过率"，而不是"降级后接口还通"。

**第三层：说清成本。** **版本数 = 提示数 × 档位数**——§6.4 给的算例是 20 个提示 × 3 个档位 = 60 份渲染配置与 60 组评测结果【推算：口径为两者相乘】（§7.4 把这条式子写成 `P × T`）。**要顺手把评测那一半也算出来**：门禁样本为 `N` 条时要 `N × T` 次调用才能覆盖一轮——§4.5 模板 1 登记的门禁规模是 82 条、按 3 类分组，代入 3 个档位即每轮上百次量级的调用【推算：口径为 `N × T`】。**这就是它需要工具支持、而不是靠人记的原因。**

**第四层：说清"降级只换端点不换提示"为什么错。** 它保住了可用性却没保住行为；而它背后的假设——**"同一份提示在所有模型上等效"**——与"提示与档位耦合"直接矛盾（§2.1 的 `(prompt_version, model_tier)` 就是这条矛盾的产物）。**这一层要附带说清"先做什么"**：先分层、再按档位分版本——不分层时，每份档位渲染配置都要整份重写，维护量按"份数"而不是"层数"上升（§7.6 的第二条次序原则）。

**第五层：说清它为什么必须进演练（加分项）。** 缺档位的失败形态很特殊：**它不是报错，而是行为变了**——接口正常、结构可能仍合法，只有分组通过率会掉（§6.4 把这种形态描述成"不是差一点，而是错一类"）。因此它的暴露路径与解析失败完全不同：**解析失败有异常可抓，判据偏移没有**。这条性质决定了三件事必须同时做：**各档位各跑一份门禁、把降级写进演练、把"降级后的可接受性"变成一个事先定好的判断**（而不是故障当天临场决定）。**演练的判据是两句问话**：输出格式还能被下游消费吗？业务判据还接受吗？

**3. 常见陷阱**
- **多档位共用一份提示**。它看起来省事，且"降级后还能用"这个现象是真的；**错在"能用"与"行为可接受"是两件事**——弱模型上的偏移是成类的，不测就看不见。
- **降级链的正确性从来没测过（"反正能用"）**。它看起来有依据（线上确实降级过、也没出事）；**错在缺一条对照**——没有各档位的分组通过率，就没有任何证据说降级后的判据还成立。
- **降级只做在端点层、提示不动**。它看起来是对的抽象（"降级是可用性问题，不是提示问题"）；**错在它依赖"同一份提示在所有模型上等效"这个已被否定的假设**（§1.2 的档位耦合与 §5.3.6）。
- **不做降级演练，只在真故障时暴露**。它看起来只是少做一次演练；**错在这类失效没有异常信号**——判据偏移不会报警，只会在故障期间静默地把错误的结论送出去。
- **答不出 `提示数 × 档位数`**。它看起来只是一个算术细节；**错在它是"要不要工具支持"的分叉依据**——`P × T` 在几十以内靠人管得住，进入上百之后靠人记必然出错（§7.5 第 4 问，该阈值为【经验】档）。

**4. 追问预测**
- "哪一段该共享、哪一段该分叉？判据是什么？"（要点：按变更来源分——判据段跨档位共享（业务规则不随档位变），推理引导段与示例密度按档位分叉；判据是"这段换档位后还成立吗"，§5.3.1 与 §5.3.6 给的是同一个动作）
- "弱模型上要不要减示例数量？为什么？"（要点：要按档位分叉示例密度——弱模型的遵循能力更依赖示例来约束边界，但示例又占预算；判据仍然回到"各档各跑一遍分组通过率"，而不是凭直觉增减）
- "降级后输出格式不对，是改提示还是改下游？"（要点：先看契约——形状问题优先交给解码层（§8.5），语义问题回到提示的判据段；"下游放宽解析"通常是最差的选项，它把一次硬失败变成一次静默的错值）
- "三个档位的评测结果差多少才算可接受？"（要点：不给统一阈值——判据是"业务能不能接受这一档的行为"，因此它必须在故障之前定好，而不是当天临场决定；可核的做法是把差值写进降级预案）
- "多档位下缓存布局怎么处理？"（要点：各档位的渲染配置是各自的前缀，稳定段各自前置；模板一动命中率归零，因此档位内的提示要尽量稳定，§5.3.4）

- 本主题内部（逐条可核）：§2.1（`(prompt_version, model_tier)` 的定义）、§1.2（提示与模型档位耦合）、§2.2（版本标识六字段）、§3.2.8（按档位分版本与评测门禁）、§4.2（4）（`call_meta` 六字段）、§4.4（"多档位共用一份提示 → 按档位分版本 + 各自评测；版本数 = 档位 × 任务"）、§4.5 模板 1（适用档位栏与门禁分组结果）、§4.7（降级演练：演练前后两组数字）、§6.4（共用提示导致的断崖与 20 × 3 的算例）、§7.4（`P × T` 的成本函数）、§7.5 第 4 问（`P × T` 的分叉阈值）。
