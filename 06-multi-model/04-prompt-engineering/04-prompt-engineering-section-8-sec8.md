#### §8.1 你改了一版提示，怎么判断这次改动是改进还是退化？

**1. 考察点**
- 是否知道**"改动必须有门禁样本"**，而不是看几个例子；
- 是否理解**总体通过率会把某类全错平均掉**；
- 有没有"放行条件"的具体表述（而不是"总体不下降"）。

**2. 参考答案框架**

**第一层：给出门禁的最小形态。** 一组固定样本（**抽真实请求 + 人工标注期望输出**）+ 一个脚本 + 结果留痕。**20 条就够挡住"反向优化"**，而成本是半小时。

**第二层：说清"按什么分组报"。** 按**任务分区**（一个提示服务几类任务）+ 按**输入类型**（常见 / 边界 / 高危）分组；**只报总体通过率会掩盖某一类的退化**，而业务反馈恰恰来自被掩盖的那一类。

**第三层：给出放行条件。** **"无任何分组的违例数上升"**，而不是"总体不下降"。这条差异是本主题最容易被忽略的一处——总体不降可以由一组的改进覆盖另一组的退化。

**第四层：说清改动的影响面。** 一个提示服务 `k` 类任务时，改动者通常只测了 1 类，**漏测 `k−1` 类**（§2.2）。因此**准入条件是"k 类都没退化"**；这也是"系统提示只放跨任务共用部分"的原因（缩小影响面）。

**3. 常见陷阱**
- 只答"看几个例子的效果"；
- 有样本但不分组；
- 放行条件写成"总体不下降"；
- 不知道一个提示服务几类任务（`k` 答不出）。

**4. 追问预测**
- "20 条样本怎么抽？随机还是按类型分层？"
- "边界样本谁来标注？"
- "如果这次改动只对一个分组有益、对另一组有害，你怎么办？"
- "评测集要不要随业务演进更新？更新的判据是什么？"

**5. 参考资料**
- 本主题 §2.2（分组判据与影响面）、§3.2.8（版本化与门禁）、§4.2（2）（门禁组织）、§6.3（无门禁导致的失败）。

#### §8.2 一个提示服务好几类任务，你怎么组织它？为什么系统提示不能什么都放？

**1. 考察点**
- 是否理解**改动的影响面 = 系统提示服务的任务数**；
- 是否知道分层（判据 / 推理引导 / 示例 / 契约）是为了**限定改动范围**；
- 有没有换代意识（哪一层随模型变）。

**2. 参考答案框架**

**第一层：给出分层与归属。**
- **系统提示**：**跨任务共有的判据**（放它的代价：改动影响 `k` 类任务）；
- **任务提示**：单任务特有的判据与输出要求；
- **示例段**：判定边界的实例（固定示例 = 核心判据；检索式 = 长尾）；
- **输出契约**：字段、枚举、失败路径。

**第二层：说清"分层"的收益是"限定改动范围"。** 业务变 ⇒ 改判据段；换模型 ⇒ 改推理引导段；补边界 ⇒ 改示例段。**不分层时每次改动的影响面都是整份提示**（§6.1 的失败教训）。

**第三层：给出可核查的判据。**
- 同一判据（如"含全渠道"）**只出现一处**——多处即分叉起点；
- **改一句系统提示，需要重测几类任务**——这个数就是影响面；
- 分层后，**换代时只动一层**。

**第四层：换代意识（加分项）。** 推理型模型把推理主体内化了，因此**推理引导段是换代时最可能被删或重写的一层**（§5.3.1）——**判据段与示例段跨档位可复用，推理引导段不可假定。**

**3. 常见陷阱**
- 把所有判据都写进系统提示（影响面最大化）；
- 从单任务扩展时复制一份改改（判据开始分叉）；
- 不分层（换代时整份重写）；
- 答不出 `k`（服务几类任务）。

**4. 追问预测**
- "系统提示与任务提示的边界怎么划？判据跨几类任务才该上移？"
- "如果两个任务的判据冲突，怎么办？"
- "多档位时，哪一层按档位分叉、哪一层共享？"
- "提示里的某一段你怎么判断它还能不能删？"

**5. 参考资料**
- 本主题 §3.2.1 / §3.2.2（单段与模板）、§3.2.8（按档位分版本）、§4.2（1）（四段实例）、§5.3.1（推理主体换位）。

#### §8.3 Few-shot 示例应该放几条、从哪来？检索式示例有什么坑？

**1. 考察点**
- 是否知道**示例是判据的实例化**，且**必须含反例**；
- 是否理解**示例的边际成本随调用量重复支付**；
- 知不知道检索式示例的隐藏变量（快照）。

**2. 参考答案框架**

**第一层：先说"为什么需要示例"——判据能不能文字化。** 判据能被写成可判定的句子时，示例是可选；**只有"见过才算数"的判据（文风、某类缺陷）才必须靠示例**（约束 1）。

**第二层：说清数量与构成。** 数量不是第一优先级，**构成才是**——**必须含边界与反例**；只有典型样例时，模型学到的是"典型样例的形状"，**边界行为完全未被定义**，而边界正是业务追问的地方。

**第三层：说清成本。** 示例 token **随每一次调用重复支付**（§4.6）——因此"为了展示格式而放的重复示例"是可省的成本；长尾示例应改**检索式**（按需注入）。

**第四层：检索式示例的三个坑。** ① **检索误差**（选到不相似的示例比不给更糟）；② **分布漂移**（一个月后同一输入可能取到不同示例 ⇒ **提示没变而行为变**）；③ **破坏缓存**（示例插在稳定前缀里会让前缀缓存失效，§5.3.4）。**修法**：**绑快照 + 记录示例 id + 放在稳定段之后**。

**3. 常见陷阱**
- 只答"多给几条"；
- 示例全是典型样例（无反例）；
- 不知道示例是重复支付的；
- 用检索式示例但不绑快照；
- 把动态示例插在系统提示后面（破坏缓存前缀）。

**4. 追问预测**
- "示例的顺序会不会影响结果？怎么处理？"
- "判据改了，示例集怎么同步？"
- "检索式示例的相似度阈值怎么定？"
- "固定示例与检索式示例能混用吗？怎么混？"

**5. 参考资料**
- 本主题 §3.2.3 / §3.2.4（固定与检索式示例）、§2.2（prompt token 构成）、§4.6（示例的边际成本）、§5.3.4（缓存与顺序）。

#### §8.4 CoT 什么时候有用？为什么它在某些任务上只是白花成本？

**1. 考察点**
- 是否理解 CoT 的机制（**把一步跳到答案换成多步生成**）；
- 知不知道它的**收益条件**（推理步数 `s` 较大）；
- 有没有"CoT 中间结果不是真值"的意识。

**2. 参考答案框架**

**第一层：给出机制与收益条件。** CoT 让模型在生成中间步骤时**用到更多计算与更多输入信息**；因此收益主要体现在**多步推理任务**上（`s` 较大）。**`s ≈ 1` 的分类 / 抽取任务上，它只增加输出 token 成本**（§2.2 的判据）。

**第二层：说清代价。** ① 输出 token 上升（成本与延迟）；② **中间步骤进入上下文，可能反过来污染结论**（一个错误假设会被后续围着展开）；③ **失败更难排查**（结论错，是推理错还是前提错）。

**第三层：给出验证动作。** 对 `s ≈ 1` 的任务做一次**"去掉 CoT"的对照实验**——若通过率不变而成本下降，就应去掉。**这是最便宜的一次优化**。

**第四层：说清两个危险用法。** ① **把中间结果当真值**（写进日志供人查看、甚至被下游消费）——**中间步骤是模型的草稿，不是结论**；② **对推理型模型照搬"请一步步思考"**——推理已经内化，那段引导可能干扰它自己的推理（§5.3.1）。

**3. 常见陷阱**
- 一律加 CoT（"大家都在用"）；
- 把 CoT 中间结果写进日志并被下游依赖；
- 从没做过"去掉 CoT"的对照；
- 对推理型模型仍铺步骤。

**4. 追问预测**
- "怎么判断一个任务的 `s` 有多大？"
- "CoT 与 ReAct 能一起用吗？"
- "中间步骤要不要落库？落库的用途是什么（排障还是别的）？"
- "推理型模型的思考过程要不要展示给业务？"

**5. 参考资料**
- 本主题 §2.2（CoT 的收益条件）、§3.2.5（失效点）、§5.3.1（推理主体换位）、§5.5（过度宣传）。

#### §8.5 输出要求模型返回 JSON，怎么保证它一定可解析？

**1. 考察点**
- 是否知道**"请返回 JSON"是一个请求，不是一个约束**；
- 知不知道按可靠性排序的四条路线；
- 有没有"失败路径"的具体设计。

**2. 参考答案框架**

**第一层：先给出四条路线（按可靠性排序）。** ① **解码层约束**（结构不合法根本生不出来，最可靠）；② 结构 + 校验 + **重试**（有轮次上界）；③ 校验但不重试（关键链路宁失败不猜）；④ **只靠提示描述**（不该作为生产形态）。

**第二层：说清第 ④ 条为什么危险。** 它平时看起来能用，**直到某次输出带了 Markdown 围栏或注释**——而这类失败**通常出现在流量最大的那天**（§6.2 的失败教训）。

**第三层：说清第 ① 条带来的两个变化。** ① **提示里那段结构描述可以删掉**（省的是每次调用的 token，按调用量放大）；② **下游代码可以简化**（解析失败从常态分支变成兜底分支）。**但兜底分支的触发次数仍要监控**——它仍是健康指标。

**第四层：说清 Schema 设计的两个要点。** ① **留一个自由文本字段**（`reason` / `note`）作为泄压阀——不留时模型会把解释塞进不该塞的字段（**结构合法、语义错乱，比解析失败更难发现**）；② **Schema 变更是不兼容变更**，要版本（同工具 Schema 的管理）。

**3. 常见陷阱**
- 只答"提示里写清楚格式"；
- 提示里写完整 JSON 示例；
- 没有解析失败率监控；
- Schema 不留自由文本字段；
- 失败后静默降级（把解析失败当成"没有结果"）。

**4. 追问预测**
- "端点不支持约束解码怎么办？"
- "解析失败时重试几次？重试还失败呢？"
- "Schema 里的枚举加一个值，算不算不兼容变更？"
- "怎么监控解析失败率而不被小样本类型掩盖？"

**5. 参考资料**
- 本主题 §2.3（四条路线）、§3.2.7（结构化契约）、§4.2（1）（契约与失败路径）、§6.2（解码层约束的案例）。

#### §8.6 你们接了多档位模型做降级，怎么保证降级之后还能用？

**1. 考察点**
- 是否知道**提示与档位耦合是结构性的**；
- 是否理解**降级链的正确性等于"每一跳的行为可接受"**；
- 有没有"各档位各跑一遍评测"的实践。

**2. 参考答案框架**

**第一层：先指出问题的根因。** **多档位共用一份提示**时，那份提示通常是**按旗舰模型的遵循能力写的**（长指令、多约束并列、推理步骤铺开）。弱模型的**遵循能力不足**，于是行为不是"差一点"，而是"**错一类**"（§6.4）。

**第二层：给出修法。** ① **按档位分版本**：`(prompt_version, model_tier)` 是完整标识；**共享判据段**（业务规则不该因档位而变）、**按档位分叉推理引导段与示例密度**；② **每档各跑一份评测**（同一样本集）；③ **把"降级后的行为"写进故障演练**——演练时真的切到低档位，看输出是否仍可被下游消费（格式）与业务接受（判据）。

**第三层：说清成本。** **版本数 = 提示数 × 档位数**（§6.4 的算式）——例如 20 个提示 × 3 个档位 = 60 份渲染配置与 60 组评测结果。**这就是它需要工具支持、而不是靠人记的原因。**

**第四层：说清"降级只换端点不换提示"为什么错。** 它保住了可用性却没保住行为；而它背后的假设——**"同一份提示在所有模型上等效"**——与"提示与档位耦合"直接矛盾（§2.2）。

**3. 常见陷阱**
- 多档位共用一份提示；
- 降级链的正确性从来没测过（"反正能用"）；
- 降级只做在端点层，提示不动；
- 不做降级演练（只在真故障时暴露）；
- 答不出 `提示数 × 档位数`。

**4. 追问预测**
- "哪一段该共享、哪一段该分叉？判据是什么？"
- "弱模型上要不要减示例数量？为什么？"
- "降级后输出格式不对，是改提示还是改下游？"
- "三个档位的评测结果差多少才算可接受？"

**5. 参考资料**
- 本主题 §2.2（提示与档位耦合）、§3.2.8（按档位分版本）、§4.7（降级演练）、§6.4（共用提示导致的断崖）、§7.4（成本曲线）。
