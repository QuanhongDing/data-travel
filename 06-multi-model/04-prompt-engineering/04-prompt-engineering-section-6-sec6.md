## 6. 落地实践

> **本节的材料纪律（先说清楚）**：提示工程的公开材料以**供应商的用法文档与最佳实践**为主，而**分组通过率、换代前后对照这类真正有用的数据几乎无人公开**——因为提示是业务判据的载体，公开它就等于公开业务规则。因此本节 4 例的构成是：
>
> - **§6.1–§6.2** 是**公开文档层面的机制复述**（提示怎么被文档化为可评测的接口、结构化输出怎么从"提示描述"移到"解码层"），**不是对任何一家公司内部实现的转述**；方括号内是**来源类型 + 年份**，属**建设方自述**，不构成本书 §5 判据里要求的「第三方（非厂商）公开生产案例」。
> - **§6.3–§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证。
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 Anthropic"**把提示工程文档化：提示是可评测的接口，不是咒语 2+ 年**"（2023-2024）

**背景（Why）**

团队最初把提示当成"调参玄学"：

- **同一条判据在不同人的提示里写法不同**——业务规则在执行层出现了多个版本；
- **改动没有判据**——"改完看着更好"是唯一的验收方式；
- **没人知道"上一版为什么被换掉"**——版本在人的记忆里，不在系统里。

**这三条不是三个毛病，是同一个约束的三种表现**：提示是**判据的载体**，而判据属于业务、不属于写提示的人。这带来一对相反的要求——**它要像代码一样被评审与回滚**（因为它决定行为），**又要像配置一样能被非工程角色改动**（因为判据来自业务）。两条要求指向同一个结论：**提示必须先有结构，才可能被当资产管**。

**代价要一起说清**：把提示文档化**不省钱**。它换来的是"改动可判断"，付出的是**分层设计成本、示例集与门禁样本的常备维护、以及按档位分版本后的版本数乘法**（§4.6 的人力三项）。**它是一笔用常备投入换掉一类"无法察觉的失败"的交易**——不理解这一点时，团队会在第一个季度末砍掉评测维护，然后在下一个季度重新开始"看着更好"。

**触发点（What）**

模型的供应商把提示的**用法与结构**写成了公开文档（[Anthropic 公开材料 2023-2024]，核验入口是其官方文档，**按当前版本核**）。它给出的第一条判断是**"提示是一条接口"**：

- **它有结构**（角色 / 任务 / 示例 / 输出要求），而不是一段随意的话；
- **它可以被评测**（同一份提示在一组固定输入上跑，得到通过率）；
- **它与模型档位相关**（同一份提示在不同能力的模型上表现不同）。

**这条判断在引入时就要接受它的代价**：

- **它把"改提示"从随手一改变成带准入条件的改动**——评测集要有人维护，门禁会挡下紧急改动（§3.2.8 的代价①②）；
- **它要求非工程角色改得动**（判据来自业务），而**分层正是为了让"业务改判据段、工程改推理引导段"成为可能**——不分层时，这个分工无法成立；
- **它不允许"一份提示打天下"**——"与模型档位相关"这一条直接推出 §6.4 的按档位分版本，而那一项的运维成本是按乘法增长的。

**详细做法（How）**

**① 把提示按"层"组织，而不是按"段"排**

- **关键设计**：判据（业务规则）、推理引导（怎么想）、示例（判定边界的实例）、输出契约（什么形状）**分开写**——**分开的直接收益是换代时只动一层**（§5.3.1）。
- **关键性质**：**分层让"改动的范围"与"改动的影响面"可以对齐**——改判据段影响所有任务，改示例段只影响边界行为。**不分层时，任何改动的影响面都是整份提示。**
- **关键能力（为什么层要这么切）**：**这四层的"变更来源"不同**——判据段随业务变、推理引导段随模型档位变、示例段随边界样本变、输出契约段随 Schema 变。**分层不是按语义切，是按"谁会让它变"切**；这也解释了 §4.5 模板 1 的变更记录栏为什么能写出"v6→v7：把'涉及资金'细化为三条列举；原因：边界类违例 3 条集中在'查询 vs 资金'的混淆"——它记的正是"哪一层的哪个来源动了它"。
- **关键示意**：

  ```text
  四层的划分依据 = 谁会让它变（不是语义，是变更来源）
    判据段（业务规则）        ← 业务方改；跨任务共享
    推理引导段（怎么想）      ← 换模型档位时改（§5.3.1）
    示例段（判定边界的实例）  ← 边界样本暴露新混淆时改
    输出契约段（什么形状）    ← Schema 变更时改（不兼容变更）
  判据：随便挑一次历史改动，能否说出"它动了哪一层"
        答不出的改动 = 影响面未限定 = 必然整份重写
  ```

**② 输出要求写清"失败时怎么办"**

- **关键设计**：不只写"返回什么"，还写"信息不足时返回什么"（例如显式的 `need_more_info` 而非猜一个结论）。
- **为什么**：**允许模型说"不知道"是可控性的来源**——不允许时它只能编一个，而**编出来的结论与推测出的结论在下游看起来一样**（同 [Ch9 §05 §3.2.2 的"诚实拒绝"](../../09-data-intelligence-product/05-intelligent-bi-nl2sql/05-intelligent-bi-nl2sql-section-3-sec3.md)）。
- **关键能力（为什么必须是一个字段值，而不是一句嘱咐）**：这条要求能被下游消费，靠的是**一个显式出口**——§4.2（1）的四段实例把失败路径写成 `on_parse_failure: retry_once_then_error`，§4.5 模板 1 的"四段"栏把输出契约与示例并列登记。**"不知道"要有自己的字段值，否则它与"推测出的结论"在下游同形**，而下游无法区分这两者时，等于没有出口。
- **判据**：**抽二十条"信息不足"的输入跑一遍，看返回的是猜测还是显式出口**——这是本单元唯一能自测的判据（见"具体数字"的第三条）。

**③ 让"上一版为什么被换掉"落在系统里，而不是人的记忆里**

- **关键设计**：每次改动在资产卡上留两栏——**原因**（哪一类样本暴露了问题）与**回滚目标**（上一版是哪个版本号，回滚动作是改指针）。§4.5 模板 1 把这两栏写成了 `变更记录 v6→v7：…原因：边界类违例 3 条集中在"查询 vs 资金"的混淆` 与 `回滚：改指针即可；上一版 v6`。
- **为什么**：**"为什么改"是下一次改动的唯一锚点**。没有它时，团队会在半年后把同一个改动再来一遍，而且**这次会以为它是新的**（§6.3 的失败教训正是这一形态：改得越多越说不清）。
- **判据**：**随机抽一次历史改动，问"它由哪一类样本驱动、回滚目标是谁"**——两问答得出来，资产卡就是活的；答不出来时，卡上那些字段只是装饰。

**④ 让版本号出现在调用日志里，而不是只出现在仓库里**

- **关键设计**：每次调用记录 `call_meta`（§4.2（4）的六字段：`prompt_version`、`model_name`、`model_version`、`decode_params`、`tool_schema_version`、`retrieval_snapshot`），并接进网关——§5.4 的接口表写的就是这件事：**本主题产出 `prompt_version`，网关把它带进调用与计量**。
- **为什么**：**提示资产化的收益有一半在排障上**。没有版本标识时，"上周开始变差"只能靠回忆改动时间线；有标识时，它是一个可执行的分组动作——**把这一段时间的调用按 `prompt_version` 分组看同样的指标**。§6.7 把"排障时间"单列一行，量级正是"从小时到天级降到分钟级"【经验：取自 §6.7 表中标着"量级（【经验】）"的那一列】，而这个量级的全部来源就是这条元数据。
- **判据**：随便挑一条线上调用，问"它用的是哪一版提示、当时的示例快照是什么"——**答不出来时，资产卡上的版本号只服务于人，没服务于系统**。

**具体数字（档位标注）**

- 示例的边际成本：示例 token **随每一次调用重复支付**（§4.6）——设示例占 prompt 的 `X%`，则去掉与判据无关的示例可直接省下 `X%` 的输入成本【推算：口径为"示例 token ÷ 总 prompt token"】。**这个占比决定了什么**：它决定了"先删示例还是先换模型"——示例占比高时，删示例是**不需要任何采购**的动作，而换模型要重跑门禁、重发版本。
- 分层的量级：**层数 = 4**（判据 / 推理引导 / 示例 / 输出契约）【经验：按本主题 §4.2（1）与 §5.3.1 的分段口径】。**这个数决定了什么**：它决定了换代的改动面——分层之后一次模型换代只需动其中一层（§5.3.1），没分层时是整份重写；**它同时决定了"谁来改"的分工能不能成立**（四层里有两层是可以交给非工程角色的）。
- 显式出口的形态：**"允许说不知道"对应的是一个字段值**（本主题写作 `need_more_info`，命名随你的契约）【经验】。**这个形态决定了什么**：它决定了"编造"与"推测"在下游能不能被区分——不能区分时，两类错误会被同一段下游代码处理，而其中一类本该被人工接手。
- **自测动作**：数一下你的提示里"与判据无关的示例"有几条（例如为了展示格式而放的重复示例）——**这个数就是可省下的成本**；再抽二十条信息不足的输入，看返回的是显式出口还是猜的结论。

**失败教训**

**第一版把提示写成一整段**——从角色到示例到输出要求混在一起，改动时无法判断影响面。结果是**每次改动都整份重写**，而重写又引入新的不确定。教训：**提示要按"哪些内容会一起变"来分层**——换代变一层、业务变另一层、边界样本变第三层；**分层不是为了好看，是为了让改动可被限定。**

**机制层的解释**：一整段的失败不是"读起来乱"，而是**它把三件本来独立的事绑成了一个不可分割的发布单元**——换模型要动它、业务改判据要动它、边界样本要动它，**三次来源不同的改动撞在同一个对象上**，于是任何一次改动的影响面都等于整份提示。**因此"整份重写"不是习惯问题，而是结构问题**：只要四层的变更来源没有分开，重写就是唯一可行的改法；而重写又必然带进新的措辞差异，这就是"改得越多越说不清"的来源。

### 6.2 OpenAI"**把结构化输出做进解码层：可解析性从概率保证变成结构保证 2+ 年**"（2023-2024）

**背景（Why）**

自动化链路里最隐蔽的一类失败是**解析失败**：

- **它平时不出现**——模型 99 次返回合法 JSON，第 100 次加了个 Markdown 围栏；
- **它出现在最不方便的时候**——通常是流量最大的那一天；
- **而它的根因不是模型不可靠，而是"可解析性"没有被保证**——提示里的"请返回 JSON"是一个**请求**，不是一个**约束**。

**这条约束的强度由下游决定，不由模型决定**：输出要被程序消费（§3.2.7 的约束 3），而"被程序消费"意味着**失败不是降级，是硬失败**——解析不了的输出在下游是异常，不是"差一点的答案"。**因此这条链路的可靠性取的是"模型遵守请求的概率"与"下游解析成功"的乘积中最弱的一环**，而写提示的人通常只看前一项。

**代价一侧**：为了防住它，团队通常在两头付钱——**提示里堆结构描述**（每次调用重复付 token），**下游写重试与兜底**（为一条"本可以不存在"的失败路径长期维护代码）。两笔都是常备成本，且都没有人对着它们问"这一层为什么不能交给系统"。

**触发点（What）**

供应商把**结构化输出**做成正式能力（[OpenAI 公开材料 2023-2024]，核验入口是其 API 文档，**按当前版本核**）：给定 Schema，输出在**解码层**被约束为合法结构。它给出的判断是**"形状"这一层可以交给系统**：

- **它把一条从提示里删掉的内容拿回来了**——那段"请严格按以下 JSON 格式返回"的描述可以大幅缩短（省的是每次调用的 token）；
- **它把下游代码简化的前提建立了**——可以假定结构合法，解析失败处理从常态分支变成兜底分支；
- **它把"结构变更"变成一次显式的版本管理**（Schema 版本，同工具 Schema）。

**引入它的代价，同样要在引入时接受**：

- **"形状"的控制权从提示作者转给了 Schema**——Schema 变更从此是一次**不兼容变更**（要版本号，同工具 Schema 的管理，§3.2.7 的代价③）；
- **它并不覆盖所有输出路径**——端点不支持时仍要回到"结构 + 校验 + 重试"那一档（§2.3 ③ 四条路线里的第二档），因此**它降低的是失败率，不是把这一类失败删掉**；
- **结构约束会挤压表达空间**，而被压掉的那部分是"解释"，正是判据偏移时唯一能被人看见的信号（见做法②）。

**详细做法（How）**

**① 先划清"系统保证的"与"提示要说的"**

```text
可交给系统保证的（移到解码层 / Schema）
  字段存在性、类型、枚举取值、嵌套结构
必须留在提示里的（业务语义）
  每个字段"填什么"、判据是什么、信息不足时填什么
判据：提示里还剩"格式描述"吗？剩多少 ——
      剩下的那部分，正是系统没保证、而你以为保证了的部分
```

- **关键设计**：把输出要求拆成"形状"与"语义"两半，形状那一半整体移交给解码层，语义那一半留在提示里。
- **关键能力（为什么这条线必须自己划）**：**没有任何一方会替你划这条线**——供应商的能力条目只承诺形状，提示作者只知道"我一直这么写"。**划线的动作就是把提示里每一句格式描述圈出来，逐句问"这一层为什么没交给解码层"**：答"端点不支持"是合法答案，答"一直这么写"不是。
- **判据**：提示里剩下的格式描述句数——**它应当收敛到"端点不支持"的那几条**；超出这个范围的部分，是还没被接管的失败来源。

**② 用一个"兜底字段"容纳表达空间**

- **关键设计**：Schema 里留一个自由文本字段（`reason` / `note`）——**结构约束会挤压表达空间**，而这个字段是泄压阀。
- **为什么**：不留它时，模型会把解释塞进不该塞的字段（例如把解释写进枚举值），**而那种输出在结构上合法、在语义上错乱**——比解析失败更难发现。
- **关键能力（为什么一个字段就够）**：**结构约束挤压的是"表达空间"，而压力一定会找出口**——不给合法出口时，它挤进枚举值、挤进数字字段、或者干脆丢掉解释。**一个自由文本字段的作用不是"多存点东西"，而是把这类压力导到一个可被审计的位置**；丢掉解释的那一支最危险，因为下游看到的是一个完全合法的空结论。

**③ 把 Schema 变更当成一次版本变更来做**

- **关键设计**：Schema 有自己的版本号，与提示版本一同进调用元数据——§4.2（4）的 `tool_schema_version` 字段就是为它留的位置；变更时走与提示改动**同一套门禁**（§4.5 模板 2 的放行条件）。
- **为什么**：**结构变更是不兼容变更**，它同时影响解码层的约束与下游的解析代码；更要紧的是，**它与提示改动会在同一份调用记录里竞争归因**——没有各自的版本号时，"这次退化怪提示还是怪 Schema"是无法回答的问题，而两类改动在同一个季度里一定会同时发生。
- **判据**：Schema 版本号在不在调用元数据里；不在时，解析失败率一旦升高就只能靠回忆——**归因能力在改动最密集的时候最需要，也最先丢**。

**具体数字（档位标注）**

- 可省的提示 token：结构描述段通常占系统提示的**一到两成**【经验：随 Schema 复杂度浮动】——**这部分是每次调用都要付的**，因此按调用量放大。**这个占比决定了什么**：它决定了"移交解码层"省的是一次**乘法**而不是一次改动；占比越高，越应先动它，而不是先去压示例。
- 失败形态的量级：**"99 次合法、第 100 次带围栏"**【经验：典型形态，不是实测比例】。**这个形态决定了什么**：它让总体失败率看起来极低（一到两个百分点以内），于是监控上不来告警，**而失败在流量最大的那天成批出现**；因此要看的不是均值，是**失败集中在哪一类输出上**——集中在小样本类型上时，总体失败率会把它掩盖掉。
- 解析失败的下游处理：从"**偶发成批失败**"变为"**兜底分支的低频触发**"【经验】。**这个口径决定了什么**：兜底分支的触发次数从此是一项健康指标——它不该为零（为零说明没在统计），也不该升高（升高说明约束没覆盖全）；§6.7 的 ROI 表把它列为"自动化链路的稳定性"一行的计量口径。
- **自测动作**：查一次你的端点是否支持约束解码；支持的话，**把提示里的结构描述删掉并改走 Schema**，然后观察解析失败率（它应变成兜底分支的触发次数）；不支持的话，先给下游补一条可统计的重试路径。

**失败教训**

**第一版只在提示里写"请返回 JSON"**——上线三个月都没问题，直到一次大促时流量上来了，模型开始在输出前后加解释性文字，**下游解析成批失败**。教训：**"请返回 JSON"是一个请求，不是一个约束**——把形状交给解码层、把语义留在提示里，两者的分工划清之后，这类失败才从"概率事件"变成"可管理分支"。

**机制层的解释**：**请求的兑现是概率性的，而下游的解析是确定性的硬判断**；两者之间没有中间层时，系统的可靠性取的是这两者的乘积，而不是设计者的期望。"上线三个月没问题"不是"没问题"，它只是**把失败推到了尾部分布上**——而尾部正是流量峰值所在，也正是最不能被惊动的那一天。**把形状交给解码层之后，这一项从乘法里消失了**，剩下的失败才是一个有触发次数、可被监控的分支。

### 6.3 某电商"**先建 20 条门禁样本，再谈优化提示 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

推荐理由与商品问答的提示由不同的人维护，改动频繁，而"效果好不好"只能靠人看几个例子。

**这条现状背后有一个结构性约束：提示的维护权与判据的所有权不在同一个人手里。**

- **改的人是业务方或产品**——因为他们知道"这种工单算不算升级"；改动因此频繁（判据随活动、随规则变）；
- **判断影响的人不存在**——一次改动会波及哪些输入类型，写提示的人不知道，看日志的人不看提示；
- **反馈的迟滞是结构性的**——行为变化没有报错，只能等人投诉（§3.2.8 的失效点①）。

**代价一侧同样要摆明**：建门禁不是"顺带做的事"，它是一项**常备投入**——样本要随业务更新，标注要有人做（§4.6 把它列为人力三项里唯一无法自动化的一项）。**这个交换唯一不成立的情形是：判据本身还没稳定**——规则一周一变时，固定样本集会在两周内失效【经验：失效快慢随改动频率变】。

**触发点（What）**

**一次反向优化被当成改进上线了**：某人为了修一个边界问题改了提示，结果**另一类常见请求的准确率下降**，而团队直到一周后收到客服反馈才知道。**根因不是那次改动错，而是没有一组固定的样本能在改动时给出反馈**。

**把它拆成两个动作，缺口才看得清**：

- **改动侧的缺口**：改动者**无法知道自己动了什么**——提示是一个整体，他改的是"边界那一句"，而那一句同时被另几类输入命中；
- **验收侧的缺口**：验收标准是"看着更好"，而**看的是改动者自己挑的例子**（他为了让这次改动通过，自然会挑它有效的例子）。

**这两条合起来说明：问题不在"谁改得差"，而在"改动没有准入条件"**——而准入条件不是靠流程规定能补上的，它需要一组**不随记忆漂移的参照**，这正是 §3.2.8 的门禁。

**详细做法（How）**

**① 先抽 20 条真实请求标注期望输出（半小时的事）**

- **关键设计**：从线上日志抽真实输入，逐条写期望输出或期望判据。**这一步不依赖任何工具**，用一份 jsonl 就够。
- **关键性质**：**它立刻改变团队的行为**——有了它，改动从"看着更好"变成"跑一遍看结论"；**而这一步的价值与其规模无关**，20 条已经能挡住"反向优化"。
- **关键能力（为什么"真实请求"这四个字不能换）**：**样本必须来自线上日志，而不是构造的**——构造样本只覆盖"我们想得到的情况"，而反向优化的受害者正是**没想到的那一类**（本例里是"另一类常见请求"）。**从日志抽样的动作本身就在做一次分布校正**，这是它 20 条就有用的原因；换成"照着需求文档编 20 条"，同样的工作量挡不住同类事故。
- **判据**：二十条里**至少覆盖三个输入类型**；只有一类时，它挡不住跨类型的退化。

  ```text
  门禁样本（jsonl，一行一条，形态照 §4.2（2））
    {"input": "...", "type": "common|edge|high_risk", "expect": "..."}

  分组报告（放行判据的载体，形态照 §4.2（2）的样例）
    组          本版      上版      判断
    资金组      40/40     40/40     =
    查询组      29/30     30/30     −1  ← 有一组退了 → 不放行
    边界组       9/12      9/12     =
  判据：报告里每个数都带分母，且按组单列；只有总数时"−1"会被吃掉
  ```

**② 按输入类型分组，再扩样本**

- **关键设计**：先标类型（常见 / 边界 / 高危），再按类型各扩若干条 —— **分组比规模重要**（§2.2 的分组判据）。
- **为什么**：总体通过率会把"某类全错"平均掉，而**团队最先收到的反馈总是来自被平均掉的那一类**。
- **关键能力（分组是"报什么"的规格，不是分析的装饰）**：报告的最小单位是"组"，因为**放行条件是"无任何分组的违例数上升"**（§4.5 模板 2）。§4.2（2）给出的样例形态是"资金 40/40、查询 29/30、边界 9/12"——**三个数各有分母，才谈得上"哪一组退了"**；只报一个总数时，"9/12 退成 8/12"会被 40/40 的满分吃掉。
- **判据**：报告里每个数**是否带分母**、是否按组单列；两者缺一时，放行条件无法执行（§6.6 坑表第 6、7 行）。

**③ 改动必跑 + 结果留痕**

- **关键设计**：门禁脚本在 CI 里跑；结果按分组打印并留档。
- **判据**：**放行条件是"无任何分组的违例数上升"，不是"总体不下降"。**
- **关键能力（留痕的作用不是审计）**：它是**下一个改动者的锚点**——本次改动由哪一组失败样本驱动、回滚目标是谁，两问答得出来，才不用在半年后把同一个改动再来一遍（§6.1 的③）。**只留"跑过了"而不留"哪一组驱动了它"，留痕的价值损失大半。**

**④ 让候选样本从日志里滚出来，别靠人去编**

- **关键设计**：按"线上被判为错的输出"或"人工纠错"筛出候选样本，人工确认后进样本集——§4.2（2）把常规样本与边界样本分成两个文件（`gate.jsonl` 与 `edge_cases.jsonl`），本身就是为这条流水线准备的落点。
- **为什么**：**样本集的新鲜度决定它的有效期**——判据会变，一年前的样本教的是旧判据，而**样本集不会自己报警**（它只会让通过率虚高，§3.2.8 的失效点②）。**候选从日志滚出来时，样本集跟着业务一起变**，这正是"每类型 30–40 条"能长期维持而不是一次性冲刺的原因。
- **判据**：样本集里**最近新增的那一条是什么时候来的**——答"想不起来了"时，这组样本大概率已经在教旧判据（§3.2.3 的失效点：示例与当前判据不一致）。

**具体数字（档位标注）**

- 门禁样本的规模收益：**20 条 ≈ 半小时标注**，能挡住"反向优化"【经验】；扩到**每类型 30–40 条、共百余条**后可支撑精细比较【经验】——**规模不是第一优先级，分组才是**。**前半句决定了什么**：它决定了这一块的第 1 个可交付物是评测而不是提示（§4.1 的同一条口径），因此它是 §6.5 路径的第 1 步，也是 §4.1 与 §6.5 那两条反面（先优化提示、先按档位分版本）的共同前提；**后半句决定了什么**：要分辨一两个百分点的差异需要每组几十条的量级，而"挡住反向优化"不需要——**用途不同，规模不同，不要用精细比较的门槛去否定 20 条的起步价值**。
- 一次反向优化的代价：本例中该问题存活一周，期间受影响的请求占比由日志可算；**修复成本 ≈ 恢复旧版（改指针）**，**而发现成本远高于修复成本**。**这条不对称决定了什么**：值得投入的地方是**压缩发现时间**（把门禁跑在 CI 里），而不是提高修复速度——修复本来就是改一次指针，快慢无所谓。
- 反馈通道的位置：从"**客服反馈**"提前到"**改动时跑一遍**"【经验】。**这个位移决定了什么**：它把反馈从**不可控的迟到信号**变成**改动者自己触发的即时信号**；迟到信号的问题不只是慢，而是**它与改动之间的因果已经被时间搅乱**（这一周里还上线了别的改动，于是归因只能靠回忆）。
- **自测动作**：数一下你现在有多少条门禁样本、分了几组——**若只有一组且少于 20 条，先把这一件做掉，再谈别的优化**；再查一次"最近一次提示改动的留痕"里有没有写驱动它的失败组。

**失败教训**

**把"优化提示"排在"建评测"之前**——三个月里改了十几版，每一版都用"看着更好"验收。教训：**没有评测的优化不是优化，是换一种方式赌**；而**建评测的成本是半小时**（20 条真实请求 + 人工标注），**它比任何一版提示优化的成本都低**。

**机制层的解释**：没有门禁时，**"改提示"这个动作是不可逆的**——不是技术上不可回滚，而是**无法判断该不该回滚**：行为变化没有报错，只有"感觉不如以前"，而感觉会被最近的坏例子主导。于是团队进入一个循环：改一版 → 感觉不好 → 再改一版 → 感觉好些 → 实际上把第一版的问题带回来了。**20 条样本打断这个循环的原因不是它准，而是它给出了一个不随记忆漂移的参照**；一旦参照存在，"感觉"就不再是唯一的裁判。

### 6.4 某金融科技公司"**按档位分提示版本：降级后质量断崖的根因与修法 2+ 年**"（2022-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证。

**背景（Why）**

为了成本与可用性，系统接了**多档位**（旗舰 + 中档 + 小模型），降级链在端点不可用时自动下切。

**这条架构决策的代价，在引入时通常没有被算进去**：

- **降级链解决的是可用性**（端点不可用时还能答），**它不解决行为一致性**——而后者在用户体验里是同一件事（"刚才还答得对，现在答错了"）；
- **档位越往下，遵循能力越弱**——同一份长指令、多约束并列的提示，旗舰模型能全遵循，中档模型会**选择性遵循**（记住前两条，丢掉第三条）；
- **这就是"降级后质量断崖"的结构性来源**：**降级链的每一跳换掉的是模型，没有换掉提示**，而提示是按旗舰模型的遵循能力写的。

**代价一侧**：按档位分版本使版本数按乘法增长（`提示数 × 档位数`），门禁结果也要按档位各出一份——**这是"降级可接受"这一判断必须付的费用**，它需要工具支持而不是靠人记（§3.2.8 的代价③）。**换句话说，"接了多档位"这个决定本身就给提示运维定了一个乘法级的价签**，而账单上的成本省下来了，这张价签却不在同一张账单上。

**触发点（What）**

**一次端点故障期间质量断崖**：切到中档后，输出格式开始不符合要求、判据也开始偏移。事后排查发现：**三个档位共用同一份提示**，而那份提示是**按旗舰模型的遵循能力写的**（长指令、多个约束并列、推理步骤铺开）。小模型在那种密度下**遵循不全**，于是行为不是"差一点"，而是"错一类"。

**把它拆开，可以看到两件事同时发生**：

- **行为变化是"错一类"而不是"差一点"**——因为小模型丢掉的是某一条约束（例如"涉及资金必须转人工"），而**丢掉一条约束不会让所有输出都变差，它只让命中那条约束的输入全错**；这类退化在总体通过率上通常看不出来（除非样本分组）；
- **失效信号是"格式不合 + 判据偏移"**——前者能被下游发现，后者不能（它仍是一个语法正确、结构合法的答案）。**因此这次故障之所以被发现，靠的是格式那一半**；如果提示里没有可解析的输出契约，它就完全不会被发现（§3.2.7 的价值在这里以"被发现的通道"形式出现）。

**详细做法（How）**

**① 按档位分版本，且版本数与档位数挂钩**

- **关键设计**：`(prompt_version, model_tier)` 是完整标识；每档一份渲染配置，**共享判据段、各自不同地写推理引导段与示例密度**。
- **关键性质**：**共享的是"不要变"的部分，分叉的是"必须随档位变"的部分**——判据段跨档位共享（业务规则不该因档位而变），**推理引导段与示例密度按档位调整**。
- **关键能力（为什么这样切不会两头受损）**：**这个切法与 §6.1 的分层同源，依据都是"变更来源"**——判据段的变更来源是业务，推理引导段的变更来源是模型档位。**分叉错一侧就两头受损**：把判据段也按档位分叉，等于让同一条业务规则在不同档位上含义不同（判据漂移，比质量下降更难查）；把推理引导段跨档共享，等于把旗舰的写法强加给小模型（本例的原始故障）。
- **判据**：`(prompt_version, model_tier)` **是不是完整标识**——只写 `prompt_version` 时，同一次调用在某档位上无法归因（§2.2 的版本标识六字段；`model_version` 也不可省）。

**② 每档各自有一份评测结果**

- **关键设计**：门禁样本按档位各跑一遍（同一样本集，不同档位）。
- **判据**：**"降级后能接受"这条判断必须有一份数据支撑**——没有它时，降级链的正确性只是假设。
- **关键能力（报告要交叉打印，不是各打各的）**：报告的形式是 **"档位 × 输入分组"的交叉表**（§4.2（2）的分组报告形态 × 档位）。**共用一份评测结果时最常见的错是"把某一档的结论当成所有档的结论"**——而那通常是旗舰档的结论，也就是最乐观的那一份；交叉表让"哪一档在哪一组退"成为一行可读的差。
- **判据**：能不能指出"**中档在边界组上的违例数比旗舰高几条**"——答不出，说明只有总的档位结论，没有交叉结论。

  ```text
  档位 × 输入分组 交叉报告（"降级后能接受"的证据形态，数值口径同 §4.2（2））
    档位        资金组     查询组     边界组
    旗舰        40/40      29/30      9/12
    中档        40/40      28/30      6/12   ← 边界组退三条：这就是"错一类"
    小模型      38/40      25/30      4/12
  判据：同一份样本集在每一档各跑一遍；只有一列（不分档）或只有一行（不分组）时，
        降级链的正确性都还是假设
  ```

**③ 把"降级后的行为"写进演练**

- **关键设计**：故障演练时**真的切到低档位**，看输出是否仍可被下游消费（格式）与业务接受（判据）。
- **为什么**：降级链的失效**只在故障时暴露**，而它的失效形态（格式不合、判据偏移）**与"端点不可用"完全不同**——前者更隐蔽。
- **关键能力（演练要检查两层，不是一层）**：**格式层**（输出还能不能被下游消费）可自动判定；**判据层**（业务还接不接受）要人看一眼。**只做前者的演练会给出"降级成功"的假结论**——格式合规、判据偏移的输出，正是本例事后才发现的那一类。

**④ 让档位标识进调用元数据，降级才可归因**

- **关键设计**：调用元数据里记录 `model_name` / `model_version`，并与 `prompt_version` 配对（§4.2（4）的六字段）；降级发生时，**这一次调用落在哪一档是可查的**，而不是只能从时间上猜。
- **为什么**：**降级链的失效是"在故障时发生、在事后被淹没"**——故障期间调用量、报错、告警混在一起，没有档位标识时，"这批坏输出是哪一档产生的"只能靠时间对齐去猜，而时间对齐在有重试与排队时并不可靠。
- **判据**：挑一次历史降级，看**能不能按档位把当时的调用分出来**；分不出来时，做法③的演练也只能给出"感觉还行"，而"感觉还行"正是本例中被打回的那条判断。

**具体数字（档位标注）**

- 版本数的量级：`提示数 × 档位数`【推算：口径为两者相乘；例如 20 个提示 × 3 个档位 = 60 份渲染配置与 60 组评测结果】——**这个乘积决定了什么**：它决定了"按档位分版本"必须靠工具而不是靠人记（§3.2.8 的代价③）；也决定了**档位数不是可以随手加的**——每加一档，渲染配置与评测结果各加一整套，而多出来的那一套同样要有人维护。
- 降级后质量断崖的量级：**不按档位分版本时，降级后的违例率通常显著高于主档位**【经验：随提示对遵循能力的要求差异浮动】——**具体倍数必须自己测**（同一份门禁样本在各档位各跑一遍即可）。**"随提示对遵循能力的要求差异浮动"这一条决定了什么**：提示里并列的约束越多、指令越长，差距越大——**所以这份差距是你自己提示写法的函数，不是模型的固定属性**，它可以靠拆分指令与降低示例密度缩小（做法①）。
- 演练的频次：**与降级链的复杂度挂钩**【经验：本例不给具体频次】。**这条决定了什么**：降级链的失效只在故障时暴露，若演练与真实故障的间隔过长，**"演练通过"就不再是对现状的陈述**——期间提示改过、档位换过、样本也扩过；§4.7 的纪律要求演练前后各有两组数字，正是为了让这句话可核。
- **自测动作**：把门禁样本在**每个档位**各跑一遍，比对分组通过率——**这个对比今天是空白的话，你的降级链正确性就是未验证的**；同时数一遍 `提示数 × 档位数`，看这个数是否还在"靠人记"的范围内。

**失败教训**

**把"降级链"实现成了"换端点"**——它成功地保住了可用性，却没有保住行为。教训：**降级链的正确性等于"每一跳的行为可接受"**，而**行为由提示与档位的组合决定**（§3.2.8）；只换端点而不换提示，等于假设"同一份提示在所有模型上等效"——而这条假设与"提示与档位耦合"直接矛盾。

**机制层的解释**：**降级链的正确性等于"每一跳的行为可接受"，而行为由"提示 × 档位"这个组合决定**——只换端点，等于在系统的两个输入里只改了一个，却假设输出不变。这条矛盾之所以没有在引入时被发现，是因为**成本与可用性都能被立刻观测（账单与故障率），行为一致性不能**：它只在下一次故障时才被观测到，而那时它已经和"故障"混在一起，于是被归因为"端点不稳"，而不是"提示没有按档位分版本"。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条顺序固定的路径，与 §4.1 的八步对应：

1. **先抽 20 条真实请求、人工标注期望输出**（§6.3）——半小时，且它让后续一切可验证。
2. **再按层组织提示，并把"失败时怎么办"写清**（§6.1）——分层让改动可被限定；允许模型说"不知道"是可控性的来源。
3. **然后按输入类型分组扩样本、改动必跑**（§6.3）——**放行条件是"无任何一组上升"**。
4. **把形状交给解码层，把语义留在提示里**（§6.2）——省 token、简化下游、把解析失败变成可管理分支。
5. **最后按档位分版本并各跑一遍评测**（§6.4）——`版本数 = 提示数 × 档位数`，因此需要工具支持。

**顺序的反面**：**先按档位分版本、后建评测**（§6.4 的隐藏前提）——多份版本没有各自的评测结果，等于**把不确定性乘上档位数**。**第二条反面**：**先优化提示、后建门禁**（§6.3）——优化会变成凭感觉改，而**改得越多越说不清哪一步是改进**。

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 提示写成一整段 | 每次改动整份重写 | 影响面不可限定 | 按"会一起变"分层（§6.1） |
| 只说"做什么"，不说"信息不足时怎么办" | 模型编一个结论 | 编造与推测在下游同形 | 允许显式返回"需要更多信息" |
| 只在提示里写"请返回 JSON" | 偶发解析成批失败 | 可解析性未被保证 | 形状交给解码层（§6.2） |
| Schema 不留自由文本字段 | 解释被塞进枚举值 | 结构合法、语义错乱 | 留 `reason` / `note` 泄压阀 |
| 先优化提示、后建门禁 | 改得越多越说不清 | 每次改动都是赌 | 先 20 条门禁样本（§6.3） |
| 评测只报总体通过率 | 某类全错被平均掉 | 高危类别持续出错 | 按输入类型分组（§6.3） |
| 放行条件写"总体不下降" | 某组退化被掩盖 | 反向优化上线 | 改成"无任何一组上升" |
| 多档位共用一份提示 | 降级后错一类 | 降级链正确性未验证 | 按档位分版本 + 各自评测（§6.4） |
| 降级只换端点不换提示 | 可用性保住了、行为没保住 | 假设"提示跨模型等效" | 同上 |
| 降级不做演练 | 只在故障时暴露 | 失效形态与"端点不可用"不同 | 演练时真的切低档位 |
| 示例集与提示分开发布 | 行为忽好忽坏 | 被误判为模型不稳定 | 两者同版本发布 |
| 提示里留一堆无依据的段落 | 没人敢删、关键指令被稀释 | 成本上升、效果下降 | 逐段注明依据，删掉无依据的（§5.7） |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——提示工程的收益形态是"改动可控、成本可省、降级可接受"，前两者可量，第三者只能用"能不能答"来判。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 改动的可判断性 | 能否说出"这次改动是改进还是退化" | 从**说不清**到**分组对比** | 建 20 条门禁样本并跑一遍 |
| 输入成本 | prompt token × 调用量 | 去掉无关示例 + 结构描述移交解码层，通常可省**一到两成 prompt token**【经验】 | 统计"示例 + 结构描述"占 prompt 的比例 |
| 自动化链路的稳定性 | 解析失败率（及其分布） | 从**偶发成批失败**到**兜底分支的低频触发** | 查端点在不在约束解码支持列表 |
| 降级可接受性 | 各档位的分组通过率 | 从**未验证**到**有各档位数据** | 同一样本集在各档位各跑一遍 |
| 排障时间 | 从"行为变化"到"定位到原因"的时长 | 从**小时到天级**降到**分钟级**（版本标识齐全时） | 取最近一次行为变化复盘，记录实际耗时 |
| 版本运维成本 | 提示数 × 档位数（渲染配置与评测结果份数） | **随乘积增长**，是"按档位分版本"的代价 | 数一遍两个乘数 |
| 代价 | 门禁样本标注（唯一无法自动化的一项）+ 迭代人力 | 20 条 ≈ 半小时；百余条 ≈ 数人日 | 实际标一次并记录耗时 |

**读法**：前两项是**可控性与成本收益**（改动可判断、输入成本），第三、四项是**稳定性与可用性收益**（解析稳、降级可接受），第五项是**排障效率**，最后一项是**代价**。**本主题最容易出现的错位是只算"token 省了多少"，不算"改动是否可判断"**——前者是一次性节省，后者决定长期能不能收敛。**另一条读法**：最后一项里"门禁样本标注"是唯一无法自动化的投入，**而它恰恰是其它所有收益的依据**——砍掉它，前面五项都退回到"说不清"。

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**先 20 条门禁样本**（半小时，让一切可验证），**再按层组织提示并写清失败路径**（改动可限定、模型允许说"不知道"），**然后按输入类型分组扩样本、改动必跑**（放行条件是"无任何一组上升"），**把形状交给解码层**（省 token、简化下游），**最后按档位分版本并各跑评测**（`版本数 = 提示数 × 档位数`，需要工具支持）。四次失败教训指向同一件事：**提示工程的失败几乎都不是"提示写得不好"，而是"改动无法被判断、可解析性未被保证、降级未被验证"**——说不清就无法收敛、不保证就会偶发成批失败、不验证就等于假设前提成立。

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你处境最像的案例，只做一件最小的事——按它的"判据"跑一次自测（数提示里与判据无关的示例条数 / 查端点是否支持约束解码 / 抽 20 条真实请求标注 / 同一样本集在各档位各跑一遍）。哪一件**今天就能做**就先做它：**这一块的腐化不会报错，只会让提示越来越长、改动越来越说不清。**
