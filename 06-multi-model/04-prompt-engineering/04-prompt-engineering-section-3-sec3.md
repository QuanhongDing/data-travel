## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

提示的形态由**五条约束**决定，顺序不能颠倒：

1. **判据能不能被文字化**：业务判据是"可判定的句子"（含全渠道、不含已退款），还是"只有见过才算数"（某种文风、某类缺陷）？**不能被文字化的判据，只能靠示例给**——这一条决定 Few-shot 是必需还是可选。
2. **一个提示服务几类任务**：只服务一类，还是被多个任务共用？**共用时，改动的漏测面就是 `k−1` 类**——这一条决定评测集要不要分区，以及系统提示与任务提示的边界怎么划。
3. **输出要不要被程序消费**：下游是人在看，还是代码在解析？**要解析就必须有输出契约**，且必须有"解析失败怎么办"的路径。
4. **任务需要几步推理**：`s ≈ 1`（分类 / 抽取）还是 `s` 较大（多跳归因、方案比较）？**这一条决定 CoT 是收益还是成本**。
5. **有没有评测样本**：有没有一组固定的输入-判据对，能在每次改动时跑一遍？**没有它，任何提示改动都不是改动，是赌博**——这是本主题最现实的前置条件。

> **判据的用法**：先用 1 决定"要不要示例"；用 2 决定结构分层与评测分区；用 3 决定输出契约；用 4 决定 CoT；用 5 决定改动能不能放行。**跳过第 5 条最常见的后果**：提示一直在改、效果一直在变，而**没有任何一次改动能被证明是改进**——团队最后只能靠"感觉这次更好了"来决策。

**每条约束的"过关"是可核查的**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 判据可文字化 | 挑一条判据，问"两个人独立判同一个输入，会得出同一结论吗"——答不出，说明它只能靠示例 |
| 2 服务任务数 | `k` 是已知数；上次改动时测了几类是已知数 |
| 3 输出被谁消费 | 解析失败率有数；失败后的动作是写下来的（重试 / 报错 / 降级） |
| 4 推理步数 | 对 `s ≈ 1` 的任务试过"去掉 CoT"的对照实验吗 |
| 5 有评测样本 | 有一组门禁样本；**改动必跑、结果留痕** |

第 5 条的检查有一个最低成本版本：**从线上真实请求里抽 20 条，人工标注期望输出**——半小时的事，而它**立刻让下一次改动可被验证**。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 单段系统提示（直写）

**被什么约束逼出来**：只有一个任务类型、判据简单、且改的人就是写的人（约束 2 最轻的一档）。

**结构**：一段提示写清角色、任务、输出要求；直接调用。

**为什么这样设计有效**：因为**只有一段时，"改动的影响面"等于"改动的范围"**——不存在漏测的其他任务类型。这条性质是它唯一的优势，也是它不可扩展的原因：**它把"提示的维护成本"压到最低，代价是把"提示的复用"也压掉了。**

**代价**：① 多任务时只能复制粘贴（于是**同一条判据散在多份提示里，改一处漏三处**）；② 没有版本概念时，改动无法回滚；③ 迭代靠人看例子。

**失效点**：**从"一个任务"扩展到"第二个任务"时不做拆分**——直接复制一份改改，于是两条判据开始分叉。**判据**：同一判据（例如"含全渠道"）在几份提示里各出现一次——**大于一时，它就是分叉的起点。**

#### 3.2.2 模板 + 变量（结构与内容的分离）

**被什么约束逼出来**：同一段任务描述要服务多种输入形态（约束 2、3）。

**结构**：**模板**（固定部分：角色、任务、输出要求）＋ **变量**（每次调用注入：输入、参数、约束值）。模板与业务代码分离，由**配置**而非硬编码提供。

**为什么这样设计有效**：因为**它把"改提示"从"改代码"里拿出来**——非工程角色能改内容，工程角色只维护渲染与变量契约。**这条分离的实际收益是"改动成本的数量级下降"**：原本要走一次发布流程的改动，变成一次配置更新（同 [§03 §3.2.3 的"发布指针"](../03-model-gateway/03-model-gateway-section-3-sec3.md) 是同一机制）。

**代价**：① **变量契约要维护**（变量名、类型、缺失时的行为）——**缺失时的默认值是最容易藏 bug 的地方**（"没传限制条件"比"传了错的限制条件"更难发现）；② 模板里的逻辑会悄悄长大（`if` 分支、循环拼示例），**最终变成一段没人敢改的代码**；③ 它只解决"内容与代码分离"，**不解决版本与评测**。

**失效点**：**变量缺省值导致"看起来正常的错答案"**——例如"时间范围"没传时默认"今天"，而调用方以为默认是"最近 7 天"。**判据**：每个变量都有明确的"必填 / 缺省"声明，且**缺省值写在使用方的文档里**，而不是只在模板实现里。

#### 3.2.3 固定 Few-shot（示例即判据）

**被什么约束逼出来**：判据难以文字化（约束 1）——"这种工单算升级"这句话说不清，但给三个例子谁都能看懂。

**结构**：在提示里放 `k` 个 `(输入, 期望输出)` 对，**包含边界与反例**。

**为什么这样设计有效**：因为**示例是判据的实例化**——当"什么算升级"无法用规则表达时，示例给出了**可被模型模仿的判定边界**。**它的有效性还依赖一个不显眼的条件：示例要覆盖边界。** 只有典型样例时，模型学到的是"典型样例的形状"，而**边界输入上的行为完全未被定义**——而边界正是业务会追问的那部分。

**代价**：① **占 prompt 预算**（每次调用重复支付，见 §2.2 的成本式子）；② **示例顺序影响结果**（近因效应）——顺序变了，行为可能变，而这是**一个容易被忽略的隐藏变量**；③ **示例集本身要维护**（业务判据变了，示例要跟着换，否则它教的是旧判据）。

**失效点**：**示例与当前判据不一致**——判据改了但示例没改，于是模型在"文字描述"与"示例"之间被拉扯，**表现是行为变得不稳定**（同一个输入时对时错），而**排查时最容易被归因为"模型不稳定"**。**判据**：示例集有没有版本，且与提示版本一同发布。

#### 3.2.4 检索式 Few-shot（按输入动态选示例）

**被什么约束逼出来**：判据无法文字化，且**示例的需求随输入差异很大**——天气类工单与支付类工单需要的示例不是同一批（约束 1 + 2）。

**结构**：把历史 `(输入, 输出)` 建成索引 → 按当前输入检索最相近的 `k` 个 → 注入提示。

**为什么这样设计有效**：因为**它把"覆盖更多判据"的成本从"塞进提示"转成"检索出来"**——提示长度不变而覆盖的边界更广。这是**上下文预算与覆盖广度之间的一次交换**。

**代价**：① **引入检索误差**（选到不相似的示例比不给示例更糟——它会误导判定）；② **示例分布会随历史累积漂移**：一个月后同一个输入可能取到不同示例，于是**提示没变而行为变了**（这是本模式特有的失效形态）；③ 需要索引与新鲜度管理。

**失效点**：**把检索式示例当成"没有版本的东西"**——评测时用今天的示例集，线上用明天的，于是**离线评测通过而线上表现不同，且无法归因**。**判据**：同一次评测必须绑定一份示例快照（§2.2 的版本标识里要有 `retrieval_snapshot`）；线上也应记录本次用到的示例 id。

#### 3.2.5 思维链（CoT）

**被什么约束逼出来**：任务需要多步推理（约束 4，`s` 较大）。

**结构**：要求模型先给出中间推理，再给结论（或让它先列要点、再判）。

**为什么这样设计有效**：因为**它把"一步跳到答案"换成"多步生成"**——模型在生成中间步骤时**用到了更多计算与更多输入信息**，因此多步任务的正确率显著高于直接给答案（§2.2 的 `p^s` 直觉）。**它的有效性有明确边界：`s ≈ 1` 时它只增加成本**——单步分类任务加 CoT，等于花更多 token 换一个更可能跑偏的中间过程。

**代价**：① **输出 token 上升**（成本与延迟都涨）；② **中间步骤会进入上下文**，可能反过来污染结论（尤其当中间出现一个错误假设时，后续会围着它展开）；③ **它让失败更难排查**——结论错了，是推理错了还是前提错了？

**失效点**：**对 `s ≈ 1` 的任务照搬 CoT**（"因为大家都在用"）——症状是成本上升而通过率不变；**另一条更隐蔽**：把 CoT 的中间结果当真值使用（例如把它写进日志供人查看），而**中间步骤是模型的草稿，不是结论**。**判据**：中间推理有没有被下游消费——有，就是一个不该有的依赖。

#### 3.2.6 ReAct（推理 + 行动）

**被什么约束逼出来**：完成任务**需要外部信息**（工具、数据库、检索），而模型自身没有（约束 4 的极端形态）。

**结构**：`推理 → 行动（工具调用）→ 观察结果 → 推理 …`，直到给出结论；**有轮次上界**，超界升级给人或明确失败。

**为什么这样设计有效**：因为**它把"缺信息"从一个失败原因变成一次可执行的步骤**——模型不需要知道答案，它只需要知道"该问谁"。**这条能力的关键前提是"行动必须有确定性边界"**：工具得是白名单里的、权限已裁剪的、有超时与幂等的（[Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的出口收口）。**没有这层边界时，ReAct 只是把模型的不确定性扩散到了外部系统。**

**代价**：① **轮次成本**（每轮一次调用 + 一次工具执行）；② **错误会复合**（一次工具调用取回错误数据，后续推理全部基于它，且**看起来仍然合理**）；③ **可观测性要求高**（要按步留痕，否则无法回答"它第几步开始错的"）。

**失效点**：**没有轮次上界**——模型会反复尝试直到耗尽预算；**另一条**：把工具结果不加校验地放进上下文（工具返回的内容是**外部输入**，它是一条注入通道，见 §2.3 的⑤）。

#### 3.2.7 结构化输出契约

**被什么约束逼出来**：输出要被程序消费（约束 3）。

**结构**：定义字段与枚举 → 要求模型按结构输出 → **解析 + 校验 + 失败路径**（重试 / 报错 / 降级）。

**为什么这样设计有效**：因为**它把"自然语言输出"变成"接口"**——一旦有契约，下游就能自动处理，且**契约本身成了一个可测试的断言**（能解析、字段齐、枚举合法）。**这条转换是自动化链路的前置条件**；没有它，下游只能靠正则去猜，而那类实现会在模型换一次措辞时静默失效。

**代价**：① **结构约束会挤压表达空间**（复杂结论塞进固定字段时信息会丢）；② **解析失败要有人管**（重试成本、或暴露给上游）；③ **契约变更是不兼容变更**（要版本号，同工具 Schema 的管理）。

**失效点**：**只靠提示描述结构**（§2.3 的③）——平时可用，直到某次输出带了围栏或注释，而**这类失败通常发生在最不方便的时候**。**判据**：解析失败率有数吗？失败后是重试还是猜？

#### 3.2.8 提示版本化与评测门禁（按档位分版本）

**被什么约束逼出来**：提示是生产资产，且**与模型档位耦合**（约束 2 + 5）。

**结构**：提示有版本号、Owner、变更记录；**改动必须过评测门禁**（按任务分区跑固定样本）；**发布与回滚是改指针**；**按模型档位维护不同版本**（`(prompt_version, model_tier)` 才是完整标识）。

**为什么这样设计有效**：因为**它把"改提示"从一个无成本的编辑动作，变成一次有准入条件的发布**——而**准入条件的存在本身就是质量的来源**：改动者必须先想清"我怎么知道这次改进了"，评测集正是这个问题的答案。**第二条机制是"按档位分版本"**：降级链的每一跳有自己的提示版本（[§03 §3.2.7](../03-model-gateway/03-model-gateway-section-3-sec3.md)），否则**降级后质量断崖，而团队会误判为"模型不行"**。

**代价**：① **评测集是常备投入**（要随业务演进而更新）；② **门禁会挡下紧急改动**（要有一条"紧急通道 + 事后补评测"的规则，且**紧急通道的使用要有记录**）；③ **多档位多版本会让版本数乘起来**（`档位数 × 任务数`），需要工具支持而不是靠人记。

**失效点**：① **有版本但没门禁**——改动仍然只靠人看几个例子，版本号只是一个装饰；② **有门禁但样本只覆盖典型样例**——于是通过率虚高，边界输入上持续出错（§2.2 的分组判据）；③ **换模型不重测**——把"模型升级"当成"能力单调变强"，而**提示与档位的耦合会让行为在换档后变化**。**判据**：最近一次换模型有没有重跑评测集。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 必须同时上的部件 | 不选它的原因（反面） | 关键判据（可核查） |
| --- | --- | --- | --- | --- |
| 单任务、判据简单 | 3.2.1 单段提示 | 版本号、变更记录 | 上模板是过度设计 | 服务几类任务（1 类） |
| 多输入形态、要复用 | 3.2.2 模板 + 变量 | 变量契约（必填/缺省）、缺省值文档 | 复制粘贴会让同一判据分叉 | 同一判据出现在几份提示里（应为 1） |
| 判据说不清、只有见过才算 | 3.2.3 固定 Few-shot | **含边界与反例的示例集**、示例集版本、顺序固定 | 只有典型样例 ⇒ 边界行为未被定义 | 示例里有几条是反例 |
| 判据差异随输入变化大 | 3.2.4 检索式 Few-shot | 示例索引、**快照绑定**、相似度阈值 | 不绑快照 ⇒ 提示没变而行为变 | 评测是否绑定同一份示例快照 |
| 多步推理（`s` 较大） | 3.2.5 CoT | 中间结果**不供下游消费**、成本预算 | `s ≈ 1` 时它只涨成本 | 有没有"去掉 CoT"的对照实验 |
| 需要外部信息 | 3.2.6 ReAct | **轮次上界**、工具白名单与出口、按步留痕 | 无边界 ⇒ 把不确定性扩散到外部系统 | 轮次上界是多少；工具结果是否被校验 |
| 输出被程序消费 | 3.2.7 结构化契约 | 字段与枚举、解析失败路径、契约版本 | 只靠提示描述 ⇒ 换一次措辞即静默失效 | 解析失败率与失败后的动作 |
| 提示是生产资产、多档位 | 3.2.8 版本化 + 门禁 | 评测集（**按任务分区**）、发布指针、按档位分版本 | 有版本没门禁 ⇒ 版本号只是装饰 | 最近一次换模型是否重跑评测 |

### 3.4 组合模式：真实系统不会只用一种

1. **基础组合**：3.2.2（模板）+ 3.2.8（版本 + 门禁）——**这两条是"提示资产"的最小充分条件**：结构可维护、改动有准入。
2. **判据组合**：3.2.3（固定示例，覆盖核心判据）+ 3.2.4（检索式示例，覆盖长尾）——**固定的是"必须永远一致"的那几条，检索的是长尾**；全检索会让核心判据也随快照漂移。
3. **推理组合**：3.2.5（CoT）+ 3.2.6（ReAct）——**先想清楚"缺的是推理还是信息"**：缺推理用 CoT，缺信息用 ReAct；**两者都给时会互相干扰**（模型在推理与行动之间反复切换，轮次成本翻倍）。
4. **接口组合**：3.2.7（输出契约）+ 下游校验——契约是"形状"，校验是"内容"；**只有契约没有校验，等于只检查了 JSON 合不合法**。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 有版本号但没评测集 | 改动仍靠"看着更好"，无法证明是改进 |
| 示例集与提示版本不同步 | 行为时对时错，被归因为"模型不稳定" |
| 检索式示例不绑快照 | 离线通过而线上不同，无法归因 |
| `s ≈ 1` 的任务照搬 CoT | 成本上升而通过率不变 |
| 无轮次上界的 ReAct | 反复尝试直到耗尽预算 |
| 工具结果不校验直接入上下文 | 外部输入成为注入通道 |
| 只靠提示描述输出结构 | 某次输出带围栏即解析失败 |
| 换模型不重测 | 行为变化被误判为"模型更强了" |
| 评测集只有典型样例 | 通过率虚高、边界持续出错 |
| 多档位共用一份提示 | 降级后质量断崖，被误判为"模型不行" |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **提示硬编码在业务代码里** | 改提示要走发布流程 | 改动成本高 ⇒ 提示长期不更新 | 一开始只有一处调用 |
| **同一判据散在多份提示里** | 改一处漏三处 | 判据分叉、行为不一致 | 从单段提示复制扩展 |
| **示例与判据不同步** | 行为时对时错 | 被误判为模型不稳定 | 判据改了，示例集没版本 |
| **检索式示例不绑快照** | 离线过、线上差 | 无法归因的漂移 | 示例被视为"数据"而非"提示的一部分" |
| **CoT 用在单步任务上** | 成本涨、通过率不变 | 白花预算 | "大家都在用" |
| **CoT 中间结果被当真值** | 下游依赖模型草稿 | 结论与草稿混淆 | 中间结果好看、易取 |
| **无轮次上界的 ReAct** | 调用次数失控 | 预算耗尽 | 忘记设上界 |
| **只靠提示描述结构** | 偶发解析失败 | 自动化链路静默断 | 省掉校验与重试 |
| **变量缺省值无声明** | "看起来正常的错答案" | 错误被当成数据 | 缺省值只在实现里 |
| **换模型不重测** | 行为变化 | 误判为能力提升 | 把升级当成单调变强 |
| **评测只报总体通过率** | 某类输入全错而总体不低 | 高危输入持续出错 | 分组报需要样本标注 |
| **提示无 Owner** | 半年后没人知道某段为何存在 | 不敢改、只能绕 | 提示被当成草稿 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 单段提示 → 模板 + 变量 | 同一段话被抄到第三处 | 3.2.2 | 变量契约与缺省值声明；存量调用点改造 |
| 无版本 → 有版本 + 门禁 | 改动后说不清是改进还是退化 | 3.2.8 | **建评测集（按任务分区）**是主要工作量 |
| 提示随代码发布 → 配置驱动 | 改一个词要等一次发布 | 3.2.2 + 3.2.8 的发布指针 | 渲染与变量契约；配置的权限与审计 |
| 单档位 → 多档位（降级链） | 降级后质量断崖 | 按档位分版本 | 版本数变成 `档位 × 任务`，需要工具支持 |
| 典型样例评测 → 边界样本评测 | 通过率高但业务持续报错 | 评测集补边界与反例 | 需要人工标注边界样本（**无法自动化**） |
| 静态示例 → 检索式示例 | 长尾判据覆盖不足 | 3.2.4 | 示例索引 + **快照绑定** + 漂移监控 |
| 单步 → 需要外部信息 | 模型答出过时或编造的事实 | 3.2.6 ReAct | 工具出口、轮次上界、按步留痕 |

**一条通用判据**：**跃迁的触发点不是"提示变多了"，而是"某个失效形态第一次出现"**——第一次出现"这次改动是改进还是退化说不清"就该建评测集；第一次出现"同一判据在两处不一致"就该分层；第一次出现"离线过而线上差"就该绑快照。**按提示条数预设跃迁点，几乎一定过早或过晚。**

### 3.7 自检清单

- [ ] 每个提示有版本号、Owner 与变更记录吗？
- [ ] 有一组**门禁样本**吗？改动必跑、结果留痕吗？
- [ ] 评测集**按任务分区**了吗？每个分区有固定的门禁样本吗？
- [ ] 评测按**输入类型分组**报吗（还是只报总体通过率）？
- [ ] 评测集里有**边界与反例**吗？有几条？
- [ ] 一个提示服务几类任务？上次改动时测了几类？
- [ ] 同一判据（如"含全渠道"）在几份提示里各出现一次？（应为一处）
- [ ] 变量都有"必填 / 缺省"声明吗？缺省值在使用方文档里吗？
- [ ] Few-shot 示例集有版本吗？与提示版本一同发布吗？
- [ ] 示例的顺序固定吗？（顺序是隐藏变量）
- [ ] 检索式示例绑定了快照吗？线上记录本次用到的示例 id 吗？
- [ ] 对 `s ≈ 1` 的任务做过"去掉 CoT"的对照实验吗？
- [ ] CoT 的中间结果有没有被下游当数据消费？（不应有）
- [ ] ReAct 有轮次上界吗？工具结果进上下文前校验了吗？
- [ ] 输出契约有字段与枚举吗？解析失败率有数吗？失败后是重试还是猜？
- [ ] 每个模型档位有自己的提示版本吗？
- [ ] 最近一次换模型，重跑评测集了吗？
- [ ] 紧急改动的通道存在吗？用过几次、每次都补评测了吗？

### 3.8 小结

> 本节小结：提示的形态由五条约束按序决定——**判据能否文字化 → 服务几类任务 → 输出被谁消费 → 需要几步推理 → 有没有评测样本**；八种模式里，**模板 + 变量与版本化 + 门禁（3.2.2 / 3.2.8）是"提示资产"的最小充分条件**（结构可维护、改动有准入），**固定示例与检索式示例的分工是"核心判据一致 + 长尾覆盖"**，**CoT 与 ReAct 分别解决"缺推理"与"缺信息"，用错方向只会涨成本**，而**输出契约是可自动化的前提**。判断这一套有没有建成，只看两条：**这次改动是不是改进，说得清吗**；**同一个问题问一百次，行为漂移在可接受区间内吗**。**本主题最容易忽略的一条**：**示例集与检索快照是隐藏的变量**——它们不写在提示里，却会改变行为；**"提示没改、效果变了"最常见的成因就是它们或模型版本变了**。

> 💡 **思考锚点**：从 §3.2 里挑一条你系统已有的做法，问三个问题：它**防的是哪一类失效**（判据分叉 / 边界未定义 / 成本失控 / 解析失败 / 无法归因）？它的**失效形态是什么**？**有没有一个可执行的检查**能证明它此刻生效？第三个问题通常最有价值——**"版本化生效"的证明是"能说出上次改动是哪一版、结果如何"，"门禁生效"的证明是"有过一次改动被挡下"，"示例集同步"的证明是"示例集与提示的版本号一致"**。你打算先补哪一条？
