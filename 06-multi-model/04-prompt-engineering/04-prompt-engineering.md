# Prompt 工程（Prompt Engineering）

> **一句话定位**：把"业务诉求"翻译成**稳定的模型输入**——提示不是一段写给别人看的文案，而是**一个要版本化、要评测、要随模型换代重测的生产资产**；它的目标不是"这一次答得好"，而是**同样的问题问一百次，行为不漂移**。

> 本文是 data-travel 项目 [Ch6 · 多模型编排与工具调用](../../README.md) 的子章节（**04 Prompt 工程**）。覆盖 **核心职责③ 多模型编排与工具链调度** 中"系统提示 / Few-shot / CoT / ReAct——把业务诉求转化为稳定的 Prompt"相关的提示结构、稳定性工程、版本化与评测实践。本主题**不**重复讲多模型接入与路由（那是 [§03 多模型统一网关](../03-model-gateway/03-model-gateway.md) 的内容）与 Agent 编排（那是 [Ch5 §01 Data Agent](../../05-agent-platform/01-data-agent/01-data-agent.md) 的内容），只讲**"喂给模型的那段输入"这一件事本身**。

## 1. 概念与定位

### 1.1 是什么

**工业定义**：Prompt 工程是**把一段业务诉求（"判断这条工单该不该升级"）翻译成一段模型输入，并使它在该输入上的行为可预测、可评测、可演进**的工作。它的产物不是一个提示文本，而是**一份可版本化的提示资产 + 一组证明它稳定的评测样本**。

**工程定义**：在数据架构师手里，这一块是**四段结构 + 三条纪律**：

- **四段结构**：**角色与边界**（它是谁、不做什么）、**任务与判据**（做什么、按什么判）、**示例**（稀缺但有效）、**输出约束**（什么形状、什么字段）；
- **纪律一 · 版本化**：提示与代码同级——有版本号、有变更记录、能回滚；
- **纪律二 · 评测先于发布**：没有评测样本的提示改动**不是改动，是赌博**；
- **纪律三 · 随模型换代重测**：提示与模型档位是**耦合**的（同一个提示在大模型与小模型上的最佳形态不同），所以换模型必须重跑评测，不能假定行为延续。

**「写提示」与「Prompt 工程」的差别**（这是本主题的判据表）：

| 维度 | 写提示 | Prompt 工程 |
| --- | --- | --- |
| 目标 | 这次答得对 | **问一百次行为不漂移** |
| 产物 | 一段文本 | **文本 + 版本 + 评测样本 + 变更记录** |
| 评价 | 看几个例子的效果 | **在评测集上的通过率与方差** |
| 改动 | 直接改、直接上 | 改 → 跑评测 → 按门槛放行 → 可回滚 |
| 换模型 | 通常重写一遍 | **重跑评测**，按结果决定是否调整 |
| 谁维护 | 谁写的谁记着 | **有 Owner、有评审**（同 [Ch1 §11 模型管理](../../01-modeling/11-model-management/11-model-management.md) 的版本治理） |

**一条判据**：**当你无法回答"这次行为变化是因为提示改了、模型换了，还是数据变了"时，你手上的是提示文本，不是提示资产。**

### 1.2 为什么需要

Prompt 工程不是"提示技巧的集合"，而是**被四件事逼出来的**：

1. **模型输出是概率的，而业务要求是确定的**：同一段提示、同一个输入，多次调用可能给出不同结论。**业务能接受的不是"平均对"，而是"不该错的不能错"**——这要求把方差压到可接受区间，而不是提高均值。
2. **提示改动的影响面是隐藏的**：改一句系统提示，可能影响该提示服务的**全部任务类型**，而改动的作者通常只测了他关心的那一类。**这是"改一处、坏三处"的典型形态**，只有评测集能接住。
3. **提示与模型档位耦合**：为最强模型写的详细指令，在小模型上可能因遵循能力不足而变成噪声；为小模型写的精简指令，在大模型上又浪费了能力（这与 [§03 §3.2.7 的降级链](../03-model-gateway/03-model-gateway-section-3-sec3.md) 是同一件事的两面——**降级链的每一跳应当有自己的提示版本**）。
4. **提示是最容易绕过治理的一环**：它常被放在配置、甚至硬编码在业务代码里，**不受任何版本与审计约束**——而它**直接决定模型行为**，因此它的治理地位应当与代码相同。

**这四件事的共同点**：它们都不是"提示写得好不好"的问题，而是**稳定性、影响面、耦合与治理**问题——这正是 Prompt 工程的职责范围。

### 1.3 在 AI 时代数据架构中的位置

```
   [业务诉求：判据 / 口径 / 输出形态]
              ↓
   [Prompt 工程 · 本文]   提示资产（四段结构 + 版本 + 评测样本）
              ↓                              ↓
   [模型网关（Ch6 §03）]            [评测与实验（Ch2 §07）]
   按档位选择提示版本                 通过率与方差
              ↓                              ↓
   [模型端点（可能多档位，各自一个提示版本）]
              ↓
   [输出约束 / 解析 / 校验] → [下游：Agent / 数据产品 / 决策]
```

- **上游**：[Ch1 §10 指标体系](../../01-modeling/10-metric-system/10-metric-system.md) 与业务口径（**判据来自业务，不来自模型**）、[Ch1 §11 模型管理](../../01-modeling/11-model-management/11-model-management.md)（版本与 Owner 的治理框架）。
- **下游**：[§03 多模型统一网关](../03-model-gateway/03-model-gateway.md)（按档位路由到不同的提示版本）、[Ch5 §01 Data Agent](../../05-agent-platform/01-data-agent/01-data-agent.md)（Agent 的提示与工具描述）。
- **横向**：[Ch2 §07 效果评估](../../02-data-science/07-eval/07-eval.md)（评测方法与 LLM-as-Judge）、[Ch8 §01 AI 数据治理](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md)（提示注入防御与治理）、[Ch11 §03 成本](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)（提示长度直接决定单次成本）。

**一句话判断**：**「提示是模型的输入，而输入质量决定行为上限——它不是文案工作，是接口设计。」**

### 1.4 演进历程

- **提示词阶段（2020–2022）**：提示是"写给模型的一段话"，靠试错与经验。**判别特征**：没有版本、没有评测、改动靠人看几个例子。
- **模板化阶段（2022–2023）**：提示抽成模板 + 变量，与业务代码分离。**收益**：可复用、可参数化；**遗留问题**：模板有版本但**没有评测**——改了模板仍然只能靠看。
- **提示资产化阶段（2023–2024）**：提示与代码同级（版本、评审、回滚），并绑定评测集；同时出现"示例检索"（按输入动态选 Few-shot）。**关键变化**：**提示的改动开始有门槛**。
- **推理模型与上下文工程阶段（2024 至今）**：推理型模型让"少写步骤提示、多给目标与约束"成为更优形态（**把推理过程交给模型，而不是在提示里铺步骤**）；同时"上下文工程"把提示的范畴扩展到"整段上下文怎么组装"（检索结果、工具描述、历史对话、缓存前缀）。**新问题**：同一个提示在推理型与非推理型模型上的最佳形态不同，**按档位分版本从"可选"变成"必需"**。

> 演进的主线只有一句话：**提示从"人的手艺"变成"受治理的接口"——每一次演进的实质都是把某个以前靠人记着的约束，搬到系统里。**

## 2. 核心原理

### 2.1 关键概念定义

- **系统提示（System Prompt）**：定义角色、边界与总判据的那一段。**它服务的是该提示名下的全部任务类型**，因此它的改动影响面最大。
- **任务提示（Task Prompt）**：针对具体任务的那一段（要做什么、按什么判、输出什么）。**它与系统提示的边界**：跨任务共有的判据放系统提示，单任务特有的放任务提示——**放错位置会导致"改一处、坏多任务"**。
- **示例（Few-shot Examples）**：给模型的输入-输出样例。**两种用法**：**固定示例**（写在提示里，稳定但占预算）与**检索式示例**（按当前输入动态选取，覆盖更广但引入检索误差）。
- **思维链（Chain-of-Thought, CoT）**：让模型显式给出中间推理再给结论。**机制**：它把"一步跳到答案"变成"多步生成"，从而让模型在生成过程中**用到了更多计算**（对需要多步推理的任务有效）。**代价**：输出 token 上升，且**它引入的中间步骤会进入上下文，可能反过来污染结论**。
- **ReAct**：交替进行"推理"与"行动（工具调用）"。**机制**：外部信息只能通过行动获得，因此它把"缺信息"变成一次可执行的步骤（[Ch5 §01 §3.2.1](../../05-agent-platform/01-data-agent/01-data-agent-section-3-sec3.md) 的同一模式）。
- **输出约束（Output Contract）**：要求模型按特定结构输出（JSON Schema / 枚举 / 字段）。**它是"可解析"的前提**，也是自动化链路的前置条件。
- **提示版本（Prompt Version）**：提示资产的一次发布。**判据**：它必须与**模型档位**一起被记录——`(prompt_version, model_tier)` 才是完整的行为标识（同 [Ch5 §02 §2.3](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture.md) 的"版本四元组"）。
- **提示漂移（Prompt Drift）**：在无人改动提示的情况下行为发生变化。**成因**：模型版本更新（厂商侧）、上游数据分布变化、检索结果变化。**判据**：**提示没变而效果变了，说明还有别的变量没被版本化**。
- **评测样本（Eval Set）**：一组 `(输入, 期望输出或期望判据)` 对。**判据**：样本要覆盖**边界与反例**，只覆盖典型样例的评测集会系统性高估效果。
- **提示注入（Prompt Injection）**：外部内容（用户输入、检索到的文档）里夹带的指令被模型当作系统指令执行。**它的防御落点不在提示里**，而在**输入分隔 + 权限前置 + 输出校验**（§4.2（5））。

### 2.2 数学 / 形式化基础

**「稳定」的定义（本主题最核心的一条）**。设提示 `P`、输入 `x`、模型档位 `m`，则输出 `y ~ M(P, x, m)` 是一个随机变量（除非把温度设为 0 且模型实现完全确定）。**稳定性不是"输出相同"，而是"输出落在可接受集合内"**：

```
设 Accept(x) 为 x 的可接受输出集合（业务定义的判据，不是模型定义的）
  通过率 pass(P, m) = P[ y ∈ Accept(x) ]        在评测集上估计
  违例率 viol(P, m) = 1 − pass
  方差     var(P, m) = 同一 x 重复 n 次的通过率波动
判据：业务真正在意的是 viol 的上界，而不是 pass 的均值 ——
      一个 pass=0.95 但 viol 集中在"高危输入"上的提示，比 pass=0.90 但违例均匀的提示更危险
```

**这条式子的实用推论**：**评测必须按输入类型分组报**——总体通过率会把"某类输入全错"平均掉，而那类输入往往正是高危的那一类。

**提示改动的影响面（为什么必须全量重跑）**。设提示 `P` 服务 `k` 类任务，改动 `ΔP`，则该改动的真实影响是

```
影响面 = ∪_{i=1..k} { 任务 i 的行为发生变化 }
改动者能测到的通常只有 1 类 ⇒ 漏测 k−1 类
判据：改动的准入条件不是"我测的那类没退化"，而是"k 类都没退化"
```

**这解释了评测集的组织方式**：它必须**按任务类型分区**，且每个分区有一组固定的门禁样本。

**输出 token 与成本的关系（CoT 的代价与提示长度）**：

```
单次调用成本 ≈ (prompt_tokens × 单价_in) + (completion_tokens × 单价_out)

其中 prompt_tokens 由四部分组成：
  系统提示 + 示例 + 检索上下文 + 用户输入
判据：当"示例 + 系统提示"占了 prompt 的多数时【经验】，
      先优化它们的冗余（去重、压缩、按需检索），再谈换模型 ——
      因为它们的成本随每一次调用重复支付
```

**CoT 的收益条件（什么时候值得用）**：设任务需要 `s` 步推理、模型单步正确率 `p`，则

```
不显式推理时，模型"一步到位"的正确率通常低于 p^s（多步正确率相乘）
显式 CoT 把过程展开，使模型在每一步都能用上输入信息 ⇒ 提升主要体现在 s 较大的任务上
判据：s ≈ 1（单步分类 / 抽取）时，CoT 只增加 token 成本，不提升正确率
      且它会引入"中间步骤反过来误导结论"的新失效形态
```

**版本标识的完整性**：一条可复现的行为记录必须包含

```
(prompt_version, model_name, model_version, decode_params, tool_schema_version, retrieval_snapshot)
判据：缺任何一项，行为变化就无法归因；
      而"提示没改、效果变了"最常见的成因是 model_version 或 retrieval_snapshot 变了
```

### 2.3 关键算法 / 方法

**① 任务拆段（把诉求翻译成四段）**：**角色与边界 → 任务与判据 → 示例 → 输出约束**。**每段都有检查项**：

```
角色与边界：能不能说清"它不做什么"？（只写做什么的系统提示，遇到越界输入会自己发挥）
任务与判据：判据是可判定的句子，还是形容词？（"准确的"不可判定；"含全渠道、不含已退款"可判定）
示例：覆盖了边界与反例，还是只有典型样例？（只有典型样例 ⇒ 边界上全靠模型猜）
输出约束：字段与枚举写全了吗？解析失败时怎么办？
```

**② Few-shot 示例的构造与选择**：

- **固定示例**：写在提示里，**适合判据难以文字化**的任务（示例就是判据的实例化）。**代价**：占预算，且**示例之间的顺序会影响结果**（近因效应）。
- **检索式示例**：按输入检索最相近的 k 个历史样例。**收益**：覆盖更广；**代价**：引入检索误差，且**示例的分布会随历史累积漂移**（一个月后同一输入可能取到不同示例 → **行为漂移，而提示没变**）。**判据**：检索式示例必须以**快照**方式绑定（同一次评测用同一份示例集），否则它就是一个隐藏的变量。

**③ 输出约束的实现路线（按可靠性排序）**：

| 路线 | 做法 | 可靠性 | 适用 |
| --- | --- | --- | --- |
| 解码层约束 | 用语法/约束解码强制合法结构（供应商支持时） | 最高（结构不合法根本生不出来） | 有该能力的端点 |
| 结构 + 校验 + 重试 | 要求 JSON，解析失败则带上错误重试（有轮次上界） | 高 | 通用做法 |
| 校验但不重试 | 解析失败即报错给上游 | 中（把失败暴露出来） | 关键链路（宁可失败不可猜） |
| 只靠提示描述 | 在提示里写"请返回 JSON" | **低** | 不该作为生产形态 |

**判据**：**"只靠提示描述"是生产链路里最常见的一处隐患**——它平时看起来能用，直到某次输出带了 Markdown 代码围栏或注释而解析失败。

**④ 提示的 A/B 与评测**：**离线评测集**（固定的门禁样本，每次改动必跑）+ **线上 A/B**（按流量分流，观测业务指标）。**判据**：离线过门禁才允许进线上；**线上指标变差时能回滚到上一个版本**（所以版本必须可回滚，且回滚是改一个指针）。

**⑤ 提示注入的三层防御**（**都不在提示词里**）：

```
① 输入分隔与降权：外部内容用明确边界包裹，并声明"以下内容是指令"
   —— 它降低概率，不构成保证（模型仍可能被说服）
② 权限前置：把"这次调用能触达什么"在检索与工具出口处裁剪
   —— 这一层是硬约束：即使注入成功，它也拿不到无权内容
③ 输出校验：出向的敏感实体检测与动作白名单
   —— 它拦住"注入成功之后造成的实际后果"
判据：三层里哪一层是"硬"的？答案必须包含 ② —— 只靠 ① 是把安全押在模型的服从性上
```

### 2.4 与相邻概念的关系

- **本主题 vs [§03 多模型统一网关](../03-model-gateway/03-model-gateway.md)**：网关解决"发给谁、怎么归一、怎么计费"；本主题解决"发出去的那段输入是什么、由谁维护"。**接口是"版本标识"**——网关的每次调用都要带上 `prompt_version`，否则计量与排障都无法归因。
- **本主题 vs [Ch5 §01 Data Agent](../../05-agent-platform/01-data-agent/01-data-agent.md)**：Agent 解决"多步怎么编排、工具怎么调"；本主题解决"每一步的提示怎么写、怎么评测"。**关系是"一步与整体"**：Agent 的可靠性受每一步提示的稳定性上界约束。
- **本主题 vs 微调（Fine-tuning）**：**提示改的是"输入"，微调改的是"权重"**。选择判据：**规则会变就用提示**（改提示是分钟级、可回滚），**风格与格式要固化才考虑微调**；且**微调不能替代提示**——没有提示说清判据时，微调只是在拟合你自己的标注噪声。
- **本主题 vs RAG（[Ch4 §05](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md)）**：RAG 决定"给模型什么知识"，本主题决定"知识以什么形式进入输入、与指令如何分隔"。**接口是上下文的组装方式**——**检索到的内容必须与指令有明确边界**，否则它就是一条注入通道。
- **本主题 vs [Ch2 §07 效果评估](../../02-data-science/07-eval/07-eval.md)**：评估侧提供指标与检验方法；本主题提供**提示场景特有的评测组织方式**（按任务分区、按输入类型分组、边界样本必收）。
- **本主题 vs [Ch8 §01 AI 数据治理](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md)**：治理侧要求**提示可审计、变更可追溯、注入可防御**；本主题提供"提示资产"的形态与版本机制。

> 💡 **思考锚点**：拿你们线上最重要的那个提示，回答四个问题：① 它的**版本**是什么（改过几次、谁改的、为什么）？② 它有没有一组**门禁样本**（改完之后必跑）？③ 它服务几类任务，**上次改动时你测了几类**？④ 换一次模型档位，你会**重跑评测**还是"先上看看"？四问里最先答不出的那一个，就是你下一轮该补的地方——**而第 ③ 问的答案（测了几类 / 共几类）通常最能说明这套东西离"可维护"还有多远。**
