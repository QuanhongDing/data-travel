## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

1. **机制变了**：**正确性或行为稳定性的来源换了位置**（例如从"在提示里铺推理步骤"变成"把推理交给模型、提示只给目标与约束"；或从"人改提示"变成"系统按评测自动搜索提示"）。**这类变化影响架构决策。**
2. **接口标准变了**：提示的结构与输出约束出现跨供应商约定（结构化输出、工具描述、上下文分隔的字段惯例）。**这类变化影响"提示能不能跨模型复用"。**
3. **只多了产品**：厂商把同一套能力包装成新名词（"提示中台""PromptOps""提示优化引擎"）。**这类变化只在选型表里体现。**

判别方法仍然是那一句：**"换一家厂商，这条结论还成立吗？"**——不成立的是第 3 类。

**本主题的三类分布有一条特殊性**：**第 1 类的入口是"推理成本被模型内化"**——当推理型模型把"多想几步"变成模型自己的行为时，**提示里那部分专门用来引导推理的内容就失效了（甚至有害）**。这条变化的实质不是"提示写法变了"，而是**"谁负责推理"这件事换了主体**。**其余方向（结构化输出的一致性、上下文工程、提示缓存、自动优化）都在这一条之外，属加固。**

### 5.2 判据与分级

沿用三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定、可预期**。

| 演进方向 | 级别 | 机制变了什么 | ① 正式条目 | ② 第三方生产案例 | ③ 接口稳定 |
| --- | --- | --- | --- | --- | --- |
| 推理型模型的提示形态（少铺步骤、多给约束） | **L2** | **推理的主体从"提示引导"变成"模型内化"** | 成立（供应商文档明确区分推理型与非推理型的用法） | **核不到**（企业很少公开"换代后提示如何重写"的对照结果） | 部分成立（形态仍在演进） |
| 结构化输出 / 约束解码 | **L2** | 从"提示描述结构 + 事后校验"变成**解码层保证** | 成立（供应商正式能力条目） | 核不到 | 成立（Schema 是稳定接口） |
| 上下文工程（context engineering） | **L2** | 提示的范畴从"一段文本"扩展到"整段上下文怎么组装" | 成立（相关能力均为正式条目） | 核不到 | 部分成立 |
| 提示缓存（prompt caching） | **L2** | 同一前缀的重复计算被复用，**成本结构与提示布局耦合** | 成立（供应商正式能力条目） | 核不到 | 成立 |
| 按评测自动搜索提示（DSPy 一类） | **L3** | 从"人写提示"变成"系统按指标搜索提示与示例组合" | 只有框架与论文 | 核不到 | 不成立（目标函数与搜索空间各家不同） |
| 跨供应商的提示可移植 | **L3** | 提示从"针对某模型调好"变成"可跨模型迁移" | 只有局部实践 | 核不到 | 不成立（**提示与档位耦合是结构性的**） |
| Agent 技能 / 可复用提示包 | **L3** | 提示与其示例、工具描述打包成可分发单元 | 只有产品形态 | 核不到 | 不成立 |
| 提示与评测的自动化闭环 | **L2** | 评测结果自动回流为提示改动的候选 | 成立（评测与提示管理产品均有条目） | 核不到 | 部分成立 |

**本节没有一行达到 L1**——卡点全部在 ②：**提示工程的效果数据（分组通过率、换代前后的对照）几乎全部由建设方自述**。这个空缺有一条具体解释：**提示是业务的判据载体**，公开它就等于公开业务规则。**因此本主题的成熟度判断只能回到内部判据**：**你自己的门禁样本上，分组通过率与不稳定样本数是多少。**

**怎么用这张表（三条动作）**：

- **凡是"推理主体换位"的方向（推理型模型），必须做对照实验**——不是"用新模型会更好"，而是**"原提示在新模型上是否还成立"**（很可能需要删掉一部分）。
- **接口类方向（结构化输出、缓存）优先跟**——它们改的是"能不能连上、成本结构"，且有确定性验收。
- **L3 不进架构约束**——自动搜索提示、跨供应商可移植、技能包分发都还没有通行做法。

### 5.3 演进方向逐条拆解（核心节）

下面七个方向（§5.3.1–§5.3.7）按**同一套六线结构**写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**（判定方法与适用条件另列）。它们各自的级别见 §5.2 的那张表——**表给结论，本节给机制**；只写收益不写代价的方向，在评审时应被直接打回。六线里的第二条有一处要特别说明：**不是每条都与 AI 的能力演进有关**，凡机制本身与 AI 无关的（如 §5.3.3 的组装预算、§5.3.6 的提示与档位耦合、§5.3.7 的闭环前半段），该行会明写"机制与 AI 无关"并解释它为何仍列在本节。**§5.3.8 不是第九个方向，也不按这套六线结构写**——它是把 §5.2 的①栏按方向摊开的具名文献清单，读法见该节自己的说明。

#### 5.3.1 推理型模型的提示形态：推理的主体换位

- **旧做法与它的卡点**：提示里铺推理步骤——"请一步步思考""先列要点再判断"，即把**推理过程当作提示要提供的输入**（§2.1 把 CoT 定义为"让模型显式给出中间推理"，§3.2.5 的结构正是"要求模型先给中间推理再给结论"）。卡点有两条，§2.2 早已写死：**CoT 只在步数 `s` 较大时有效**（`p^s` 直觉），且**中间步骤进入上下文后可能反过来污染结论**。**这两条边界都建立在"步骤由提示提供"这个前提上**——推理型模型把"展开推理过程"变成**模型自身的内部行为**之后，前提没了：提示里那部分**专门用来引导推理步骤**的内容**不再提供额外收益**，而在某些情况下**会干扰模型自己的推理**（它被要求按你给的步骤走，而你的步骤不一定是最优的）。

- **AI 改变了什么机制**：**推理的主体从"提示引导"移到"模型内化"**——这是本主题 §5.1 判为第 1 类的唯一一条方向（§5.2 表第 1 行；其余方向属加固或接口变化）。后果是一句可判定的结论：**同一份提示在不同档位上的最优形态差异，从"量的差异"变成"结构的差异"**——非推理型模型需要提示给步骤，推理型模型需要提示给**目标与约束**。

- **由此得到的**：**"按档位分版本"从可选变成必需**（§3.2.8）——因为现在同一份提示在降级链的相邻两跳上可能连"该写什么"都不同。**换代的动作因此从"重跑一遍评测"变成"重写提示的推理段"**，而这条推论有直接可执行的形式：把提示按"**判据段 / 推理引导段 / 示例段 / 输出契约段**"重新分段，**分段本身就是换代的前置准备**（换代时只动第二段，§6.1 的"按层组织"是同一个动作）。

- **由此付出的**：① **重写成本**（存量提示的推理段要重做，并重跑门禁）；② **可解释性下降**（模型内部推理不一定是可读的，若业务需要"给出推理过程"作为依据，得让它**额外输出摘要**，而不是依赖它的思考）；③ **成本结构变化**（推理 token 通常计入费用，单次成本可能上升而调用次数下降）。

- **证据与来源**：【公开】供应商文档明确区分两类模型的用法（§5.2 表第 1 行的①栏成立），"推理主体换位"这一机制描述由此可取；②**核不到**——企业很少公开"换代后提示如何重写"的对照结果（同表②栏与 §5.2 之后的解释段）；【经验】**重写推理段的收益幅度本节不给数**，它取决于提示里推理引导段占多大比例，请用你自己的门禁样本量。

- **成熟度**：**L2**。① 成立（供应商文档明确区分推理型与非推理型的用法）；② **核不到**（非厂商的生产案例核不到，"换代后提示怎么改"几乎无人公开）；③ 部分成立（提示形态仍在演进，没有可预期的稳定接口）。

- **判定方法**：对同一批门禁样本做一次对照——**原提示在新档位上的分组通过率，与按其形态重写推理段之后的通过率**；同时记下"推理引导段占提示 token 的比例"（它决定重写能省下多少）。**不要用"新模型更好"当结论**——§5.2 的三条动作里第一条就写着"凡推理主体换位的方向必须做对照实验"。

- **什么时候值得做**：提示里推理引导段占比较大，且降级链上确实存在非推理型档位时——不重写就等于让每一跳都跑一份对当前档位不是最优的提示。

- **什么时候不值得做**：只有单一档位、且该档位就是推理型模型时——先把 §3.2.8 的版本标识与门禁做起来，再谈分段重写。


#### 5.3.2 结构化输出与约束解码：从"提示描述"到"解码层保证"

- **旧做法与它的卡点**：在提示里写"请返回 JSON" + 事后解析校验——在 §2.3 ③ 的输出约束四条路线里，这是**可靠性最低的一档**（"只靠提示描述"，不该作为生产形态）。卡点是**失败是概率性的、且集中在流量最大的时候爆发**：多数调用返回合法结构，少数带上围栏或解释文字，而下游的解析是**确定性硬失败**（§6.2 的失败教训与"99 次合法、第 100 次带围栏"【经验：典型形态，不是实测比例】的形态）。

- **AI 改变了什么机制**：从"在提示里请求结构 + 事后校验"变成**在解码层约束输出必须符合 Schema——结构不合法根本生不出来**。它把"可解析性"从**概率保证**变成**结构保证**，等于把"**形状**"这一层从提示里整体搬到解码层；因此它**属 §5.1 的第 2 类（接口标准变了）**而不是第 1 类——第 2 类正是以"结构化输出"为例，它影响的是"提示能不能跨模型复用"，不是"谁负责推理"（§5.2 表第 2 行的"机制变了什么"栏）。

- **由此得到的**：**"解析失败路径"从一个常态分支变成一个兜底分支**——下游可以假定结构合法，因此**代码可以简化、失败处理可以变薄**。它还反向影响提示写法：**一旦有解码层约束，提示里那段"请严格返回以下 JSON"的描述可以大幅缩短**（省的是每次调用的 token，§6.2 触发点里"把一条从提示里删掉的内容拿回来了"那一句）。**今天该做的动作**：查一次你的端点在不在支持列表里——在支持的话，把提示里那段结构描述删掉并改走约束，同时**把解析失败率作为监控项保留**（兜底分支的触发次数仍是健康指标）。

- **由此付出的**：① **结构约束会挤压表达空间**（复杂结论塞进固定字段会丢信息——因此 Schema 要留一个 `note` / `reason` 字段，§6.2 的「兜底字段」）；② **并非所有端点都支持**（不支持时仍要回到"结构 + 校验 + 重试"那一档）；③ **Schema 变更是不兼容变更**（要版本号，同工具 Schema 的管理）；④ **它只保证形状，不保证语义**——全书他处把这条边界写得很直：JSON Schema 只能校验"是不是字符串、是不是枚举值"，校验不了"这个客户到底是不是 VIP"。

- **证据与来源**：【公开】具名能力条目可核——`01-modeling/README.md` 的工具清单把 **OpenAI Structured Outputs / Anthropic Tool Use** 并列在"LLM 输出结构化建模"一栏，`04-data-assetization/10-metric-platform` 的 §8 参考条目列出 **Anthropic 的 Function Calling / Tool Use 官方文档**；形状与语义的边界见 `01-modeling/05-ontology-modeling` 的 §5。【经验】§6.2 给的"结构描述段通常占系统提示一到两成"只有量级，随 Schema 复杂度浮动；②**核不到**（第三方生产案例）。

- **成熟度**：**L2**。① 成立（供应商正式能力条目可核）；② **核不到**（非厂商的生产案例）；③ 成立（Schema 是稳定接口，这也是它比同表其余方向更容易被纳入架构约束的原因）。

- **判定方法**：查端点在不在约束解码的支持列表里；在支持的话，读一遍提示、把"格式描述"的句子圈出来——**圈出来的每一句都在问同一个问题："这一层为什么没交给解码层？"** 答"端点不支持"是合法答案，答"一直这么写"不是（§6.2 的 ASCII 判据）。再统计解析失败率及其分布。

- **什么时候值得做**：输出被程序消费、且能拿到支持约束解码的端点时——它把一整类失败从"偶发成批"降成"兜底低频"。

- **什么时候不值得做**：输出只给人看，或 Schema 还在频繁变形时——**Schema 变更是不兼容变更**，改一次要动一次版本，此时先稳定判据比先上约束更划算。

#### 5.3.3 上下文工程：提示的范畴从"文本"扩展到"组装"

- **旧做法与它的卡点**：把模型输入当成"一段提示文本"——系统提示、示例、检索结果、历史对话各自拼接，**没有位置与预算的概念**。卡点两条：**超预算时砍谁靠现场决定**；**"检索结果与指令的边界"没人负责**（§4.2（5）注入三层里的第 1 层正是为它设的）。

- **AI 改变了什么机制**：**这一条的机制一半与 AI 无关**——"输入要按预算组装"在模板化阶段就已存在（主文件 §1.4 的 2022–2023 条目），它不是模型能力带来的新事实，**今天不做也照样能跑**。**真正因生成式负载而变的只有一处**：缓存前缀的位置由组装顺序决定（§5.3.4），于是**顺序从可读性问题变成成本问题**。它仍列在本节，是因为这处变化把"组装"从一个工程细节提升成了**同时决定成本与注入防御的架构决策**——§5.4 的两处交接物（与 Ch4 §05 的"分隔与位置"、与 Ch11 §03 的 token 分项上报）都落在这张图上。

- **由此得到的**：**先把"要组装的整体"列全**——系统提示、示例、检索结果、工具描述、历史对话、缓存前缀，**每一段都有位置、长度预算与优先级**；再画一张"各段顺序 + 预算 + 超限裁剪规则"的图，它**今天就能画**，而且同时回答成本问题与注入防御问题。**今天该做的动作**：把上下文组装的顺序画出来——这张图不需要任何采购，且它是 §5.3.4 布局约束与 §4.2（5）第 1 层的共同底稿。

- **由此付出的**：① **组装逻辑会变成一段复杂的代码**（谁在前、超预算时砍谁），**而它的正确性难以测试**；② **装配顺序影响缓存命中**（可读性要为成本让路）；③ **外部内容（检索结果、工具返回）必须与指令有明确边界**——否则它是一条注入通道（§4.2（5））。

- **证据与来源**：【公开】相关能力均为正式条目（§5.2 表第 3 行的①栏成立：供应商侧都把"上下文怎么组织"写进了正式文档）；②**核不到**（第三方非厂商的生产案例）；【经验】"一次看起来很合理的顺序调整可能把命中率打下来"这一现象本节不给数。**注意不要把它当第 1 类前沿**——它的机制创新只有缓存前缀那一处，其余是加固。

- **成熟度**：**L2**。① 成立（能力条目均为正式条目）；② **核不到**；③ 部分成立（"上下文工程"这个说法本身还在演进，没有统一接口）。

- **判定方法**：把你的上下文组装顺序写成一列，逐段问三件事——"**这段是稳定段还是变动段**""**超预算时先砍谁**""**外部内容与指令之间有没有明确边界**"。第一问答不出，缓存无从优化；第三问答不出，存在一条注入通道。

- **什么时候值得做**：上下文里同时有"稳定内容"（系统提示、固定示例）与"每次变的内容"（检索、用户输入），且调用量已经大到 prompt token 进得了账单时。

- **什么时候不值得做**：只有一段固定提示、没有检索与历史时——"组装"这件事尚不存在，先做 §3.2.8 的版本与门禁。

#### 5.3.4 提示缓存：提示布局变成成本结构

- **旧做法与它的卡点**：提示按**可读性**排布——"系统提示 + 示例"这一段在每次调用里重复付费（§4.6 明确 prompt token 随每一次调用重复支付）。卡点是这笔钱**随调用量线性放大**，而团队遇到成本问题时的第一反应通常是**换模型**，不是重排提示（§4.6 的三处间接成本、§7.4 的成本结构表）。

- **AI 改变了什么机制**：生成式推理把一次请求拆成 **prefill 与 decode 两段**，两段的成本结构不同——**prefill 可被共享前缀整段消掉**（这正是前缀缓存生效的原因），decode 与输出长度成正比、几乎无法复用；这是几条推理成本杠杆里**唯一一条生效方式被生成式负载改写过的**（本主题 §5.4 把 token 成本口径交给 [Ch11 §03 成本](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops-section-5-ai.md)，其 §5.2.2 给出的顺序判据是"先测成本项占比 → 再测缓存命中率 → 然后批处理 → 最后量化与蒸馏"；"前缀占比高 → 先做前缀缓存"这条则写在 [Ch12 §05 性能工程](../../12-architecture/05-performance-engineering/05-performance-engineering-section-5-ai.md)）。**它改变的是成本函数，而这足以影响架构决策**。

- **由此得到的**：节省比例约等于共享前缀在输入中的占比【推算：省下的 = 命中前缀 token 数 ÷ 总输入 token 数】；因此"**稳定段（系统提示 + 固定示例）在前、变动段（检索结果 + 用户输入）在后**"从一条建议变成**布局约束**。**今天该做的动作**：看一次你的上下文顺序——不是这个次序的话，**先调顺序再谈优化**（调顺序不花钱，换模型要重跑门禁）。

- **由此付出的**：① **顺序被成本约束**（可读性要为缓存让路，稳定段必须在前）；② **缓存命中率需要监控**（一次"看起来很合理"的顺序调整可能把命中率打下来）；③ **它对"按输入动态注入示例"是负面耦合**——检索式示例插在前缀里会破坏缓存，**因此示例应放在稳定段之后**（这条直接约束了 §3.2.4 检索式示例的落点）。

- **证据与来源**：【公开】主流厂商在 2024 年前后陆续公布缓存计费档位（命中的输入 token 按折扣计费；具名落点见 [Ch15 §10 海外案例](../../15-case-studies/10-overseas-cases/10-overseas-cases-section-5-ai-native---2024-2025.md)，其中记有 "Anthropic 于 2024 年推出 prompt caching 并公开其定价结构"），推理引擎侧同期提供自动前缀缓存；【公开】KV 缓存与请求调度有可复现的系统设计论文（PagedAttention, SOSP 2023，与 [Ch11 §03 §5.2](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops-section-5-ai.md) 引用同一事件）；**具体折扣幅度、最小可缓存长度与计费口径以各厂商定价页与引擎文档当前版本为准**——本节不给折扣数字。【经验】"命中率被一次顺序调整打下来"这一现象本书不给数；②**核不到**。

- **成熟度**：**L2**。① 成立（供应商正式能力条目可核）；② **核不到**（公开材料只给提供方自己的场景）；③ 成立（缓存接口稳定）。

- **判定方法**：做一次**成本对账**——把"占输入多数的前缀段"圈出来，看它在账单上的输入费用占多少；再查缓存命中率**有没有被上报**（拿不到这个数时，布局优化无从验证，§5.4 那句"最容易漏的是 token 构成分项上报"说的就是这类缺口）。

- **什么时候值得做**：输入以"长而稳定"的主干为主（系统提示 + 固定示例占多数），且调用量大到输入费用看得见时【经验：占比与调用量两个量级自己代入，本节不给阈值】。

- **什么时候不值得做**：缓冲命中率拿不到数、或输入本来就短（变动段占绝对多数）时——顺序调整的收益验证不了，也就无法知道有没有做对。

#### 5.3.5 按评测自动搜索提示（DSPy 一类）：为什么停在 L3

- **旧做法与它的卡点**：人写提示、人挑示例；而**改动没有准入条件**——"改完看着更好"是唯一验收方式，于是**改得越多越说不清哪一步是改进**（§6.3 的失败教训与 §4.1 顺序的两个反面）。

- **AI 改变了什么机制**：把"写提示"变成一个**搜索问题**——给定评测指标，系统搜索提示模板与示例组合，而不是靠人写（§5.2 表第 5 行）。**这条与 AI 直接相关**，因为它把提示的产出主体**从人换成了优化器**。

- **由此得到的**：**在你已有扎实评测集的前提下**，"候选生成"这一步可以自动化；**最小可用版本是"系统生成候选 + 人挑选"**（人是判据），而不是让系统直接替换线上提示。**今天该做的动作**：先把评测集做扎实，再谈自动搜索——评测集分辨不出一次人为改动是改进还是退化时，让优化器接手只会更快地放大偏差。

- **由此付出的**：① **过拟合风险**（对门禁样本过拟合，边界样本上更差）；② **可解释性下降**（搜索出来的提示往往不像人写的，没人能解释某段为何存在）；③ **它优化的是你给的指标，而你给的指标未必是你要的东西**——这条性质与 [Ch9 §06 §3.2.7 的 Uplift 定向](../../09-data-intelligence-product/06-precision-operation/06-precision-operation-section-3-sec3.md) 同构：**任何"按指标自动优化"的方法，都会在指标与目标存在偏差时把偏差放大**；**没有分组评测与边界样本时，自动搜索只会把偏差固化**。

- **证据与来源**：【公开】只有框架与论文——全书他处把 **DSPy** 并列在"LLM 编排框架"与"混合检索框架"两处工具链表里，定位正是"想自动搜 prompt / 权重"或"要把 prompt 与管线交给自动优化"的那一格（`04-data-assetization/04-hybrid-search` 与 `04-data-assetization/05-rag-architecture` 的工具链表）；②**核不到**——它真正需要的是"搜索出来的提示在他人数据上也更好"，而这恰是没人公开的部分；【经验】搜索带来的提升幅度本节不给数，因为**这个数只对"你自己的门禁样本 + 你自己的指标"成立**。**提醒：§5.6 的五条预测全部是【经验】档且无具名出处，不要拿它当这里的证据。**

- **成熟度**：**L3**。① 不成立（只有框架与论文，无正式发布条目）；② **核不到**；③ 不成立（目标函数与搜索空间各家不同）。

- **判定方法**：问两个问题——"**我的评测集能不能分辨一次人为改动是改进还是退化**"（答不出，就不具备让优化器接手的前提）；"**门禁样本里有几组是边界样本**"（只有典型样例时，搜索会过拟合到那批样例上，§5.3.5 的代价①）。

- **什么时候值得做**：有分组评测集、有边界样本、且**候选已久但人挑不过来**时——此时自动化的是"生成"，判断仍留给人。

- **什么时候不值得做**：评测集还没建、或评测结果还不分组时——**自动优化在指标与目标有偏差时是放大偏差的机器**，先修尺子再谈自动化。

#### 5.3.6 跨供应商可移植与技能包：为什么停在 L3

- **旧做法与它的卡点**：两种旧做法，卡点各不相同。**其一**：一份提示针对一个模型调好，换供应商就整份重写一遍——**换模型时没有可迁移资产**（§7.7 的两条硬结论之一就是"平台锁定的历史评测结果不可迁移"）。**其二**：把提示打包分发给别人用——**分发的价值全在判据上，而判据是业务规则**。

- **AI 改变了什么机制**：**这一条的机制与 AI 的能力演进无关**——它是结构性的：**提示与档位耦合**（主文件 §2.1 的 `(prompt_version, model_tier)` 与 §2.2 的版本标识），而"换供应商"同时换掉了档位，所以**"一个在 A 上调好的提示在 B 上是否等效，只能实测"**。它仍列在本节，是因为它决定了"**提示资产里哪一部分可以带走**"——这是资产化决策的直接输入。

- **由此得到的**：**可移植的是判据段与示例段**（它们表达业务规则、与模型无关），**要按模型替换的是推理引导段**；技能包一侧的结论是"**可分发的是形式，不是内容**"。**今天的最小版本**：把判据段与示例段做成可移植的，把推理引导段做成按模型可替换的——**这个动作与 §5.3.1 的分段是同一件事**，做一次两处受益。

- **由此付出的**：① 必须接受"**整份提示不可移植**"这一现实（两处档位耦合是结构性的，不是某家产品的问题）；② **跨供应商对照实测的成本每家都要付一次**（同一批门禁样本在 B 上重跑一遍，短不了）；③ **打包分发无法把私有判据一起带出去**——分发出去的是空壳。

- **证据与来源**：【公开】只有局部实践与产品形态（§5.2 表第 6、7 行的①栏分别写"只有局部实践""只有产品形态"）；② **核不到**（跨供应商等效性的第三方对照数据）；③ 不成立（提示与档位耦合是结构性的）。**提示可移植性没有具名产品可引——凡是声称"一次编写、跨模型通用"的，请回到 §5.2 的判别句："换一家厂商，这条结论还成立吗？"**

- **成熟度**：**L3**。① 不成立（无正式发布条目，只有局部实践与产品形态）；② **核不到**；③ 不成立（提示与档位耦合是结构性的，不存在可预期的稳定接口）。

- **判定方法**：把你的提示按四段拆一遍，**逐段问"这一段换模型后还成立吗"**——判据段与示例段通常答"成立"，推理引导段通常答"不成立"。**答不出这条分界的团队，换供应商时只能整份重写。** 一条通用判断：凡是"提示的资产化"方向，先问"其中哪一部分与模型无关"。

- **什么时候值得做**：已经在两个以上供应商之间跑、或已经把"换模型"列入年度计划时——分段的成本很低（半天量级【经验】），而它决定了换代时动多少。

- **什么时候不值得做**：只用一个端点、且判据还在频繁变时——此时"可移植"的收益兑现不了，先做 §3.2.8 的门禁与版本标识。

#### 5.3.7 提示与评测的自动化闭环：为什么它是 L2 而不是 L3

- **旧做法与它的卡点**：评测与提示是两件分开做的事——评测跑在发布前（§2.3 ④ 的离线门禁），失败样本被记录下来，然后由人读着改提示；**改动与"哪些样本错了"之间没有机械联系**。卡点是这一步的人力**是常备投入且不可自动化**（§4.6 的人力三项：标注维护、迭代评审、多档位版本），而"**改哪一段**"这个判断从来没有被样本驱动过。

- **AI 改变了什么机制**：**先明说：闭环的前半段机制与 AI 无关**——"哪一类样本在退化"这件事变成一次可查询的分组结果，靠的是评测工程（§2.2 的分组判据与 §4.2（2）的分组报告），不是模型能力；**真正因生成式负载而新的只有"候选可由模型生成"这一侧**（§5.3.5）。它仍列在本节，是因为这一行是 §5.2 表里**唯一同时依赖"评测有分组结果"与"提示有版本标识"两件本主题基础设施**的方向——它的成熟度因此由这两件的基础设施决定，而不是由模型决定。

- **由此得到的**：闭环的**最小可用版本不需要买任何东西**——分组报告（§4.2（2）的形态：资金 40/40、查询 29/30、边界 9/12）+ 门禁（§4.5 模板 2 的放行条件"无任何分组的违例数上升"）+ 提示资产卡的变更记录（§4.5 模板 1），三者串起来就已经是"样本 → 判断 → 改动 → 复跑"的闭环，只是**中间的"判断"由人做**。**今天该做的动作**：问一句"**最近一次改动，是哪个分组的失败样本驱动的**"——答得出，闭环已经存在；答不出，缺的是分组报告，不是工具。

- **由此付出的**：① 闭环会**放大指标与目标的偏差**（与 §5.3.5 同一机制：闭环越自动，偏差被固化得越快）；② **分组报告本身有维护成本**（§4.6 的标注维护人力，唯一无法自动化的一项）；③ **自动化后"谁决定放行"的责任边界要重新写一遍**——门禁可以自动跑，**放行仍应是一次有记录的决策**（§3.2.8 的代价②：紧急通道也要留痕）。

- **证据与来源**：【公开】评测与提示管理产品都已有正式条目（§5.2 表第 8 行的①栏）。可核验的具名落点在全书他处：`07-agent-evolution/02-feedback-loop` 的 §4 把 **Langfuse、Helicone、Arize Phoenix** 列在"Eval / 监控"一行，判据正是"**能不能按模型 / prompt 版本分桶看指标**"与"**能不能接 CI**"；`07-agent-evolution/03-asset-management` 的 §3 真实使用行记了 **Dust.tt（2023）/ PromptLayer（2024）** 的提示版本与调用监控形态；评测框架一侧见 `02-data-science/07-eval` 的"LLM 评估框架"行（**HELM / OpenAI Evals / Anthropic Evals / lm-evaluation-harness** 等）。②**核不到**——"自动回流的效果"没有第三方公开案例；【经验】闭环带来的收敛速度提升本节不给数。

- **成熟度**：**L2**。① 成立（评测与提示管理产品均有正式条目）；② **核不到**（"自动回流"的效果无第三方生产案例）；③ 部分成立（"回流"的接口形态各家不同，没有可预期的统一接口——这与 §5.3.5 的 L3 的区别正在于①：这里**有正式条目**，那里只有框架与论文）。

- **判定方法**：从最近一次提示改动往回查三样东西——**驱动它的失败样本（落在哪一组）、放行依据（哪一次门禁结果）、改动记录（资产卡的变更记录栏）**。三样里缺哪一样，闭环就断在哪一环。不需要采购。

- **什么时候值得做**：门禁样本已经分组、提示已有版本标识时——此时闭环的增量动作只有"把三样东西串起来"，成本近乎为零。

- **什么时候不值得做**：样本还没有分组、或提示还没有版本号时——此时"闭环"会把未分组的结论与不可归因的改动连起来，等于给偏差装了一条加速通道。

#### 5.3.8 公开进展与文献（按方向聚合的具名清单）

§5.3.8 **不是第九个方向**，而是把 §5.2 那张表的①栏摊开——**八个方向里，哪几条能给出「具名文档 / 论文 + 年份」的可核验出处，哪几条核不到**。下面分三类列，与三个组头一一对应：**论文**与**官方 release note / 文档（判定入口）**两类只收能给出标题（或文档名）+ 年份的条目，**宁少勿假**；官方文档组里若某一条本身即核验入口、而发布年份核不到，写明「年份核不到」并置于该组末尾，不计入上面这条收录条件（**具体版本与日期一律以页面上的条目为准**）；**第三方生产案例**一类按本主题的口径留白并说明原因。**本清单里出现的年份与年月一律属【公开：具名文档 / 发布物 + 年份（或年月）】一档，登记落点随条目给出；比年月更细的时间，以及通过率 / 成本 / 命中率一类数字，本节一律不给。**

- Yao et al., *ReAct: Synergizing Reasoning and Acting in Language Models*, ICLR 2023——「推理与工具交替」的机制来源，全书他处已登记同一出处（本主题 [§3](04-prompt-engineering-section-3-sec3.md) 的真实使用行、`05-agent-platform/01-data-agent` 的 §3.2.1、[Ch15 §10 海外案例](../../15-case-studies/10-overseas-cases/10-overseas-cases-section-5-ai-native---2024-2025.md) §5 的文献行）。它支撑的是**「推理与工具交替」这一机制**，**不是**「提示该怎么写」，也**不是**「工具调用变成模型能力」那条边界（后者属下一条）。
- Schick et al., *Toolformer: Language Models Can Teach Themselves to Use Tools*, NeurIPS 2023——**工具调用从「提示工程」变成「模型能力」的公开依据**（Ch15 §10 §5 的文献行与本主题 [§3](04-prompt-engineering-section-3-sec3.md) §3.2.6 的真实使用行均这样记，即上一条三个落点中的这两处；`05-agent-platform/01-data-agent` 的 §3.2.1 与 §5 文献行只登记 ReAct，不含本条目）：工具描述与调用原先写在提示里，此后成为模型侧能力。
- **PagedAttention, SOSP 2023**——**§5.3.4 的机制来源**：KV 缓存可被共享前缀整段复用，这是「提示布局变成成本结构」的技术依据，本文件 §5.3.4 的证据行与 `11-cross-cutting/03-data-cost-finops` 的 §5.2 引用同一事件（本节按全书的写法只给论文名与会议，不补作者）。
- Es et al., *RAGAS: Automated Evaluation of Retrieval Augmented Generation*, arXiv 2023 起——**§5.3.7 的评测侧公开方法**（同一处 Ch15 §10 的证据行登记该出处）。它解决的是「自动评测怎么算」，**不解决「闭环该不该自动替换线上提示」**——后半句才是 §5.3.7 的判定方法。

- Tunstall et al., *"Efficient Few-Shot Learning Without Prompts"*, 2022（即 SetFit）——「免提示词的少样本」这条对照路线（`02-data-science/02-classification` 的 §5 证据行与主文件的术语表均登记，那一侧把它列在「免微调与轻量适配」一族）。列它的用处是一条提醒：**「必须写提示」本身也只是当时的技术条件**——本主题 [§8](04-prompt-engineering-section-8-sec8.md) 的口径提醒段把这一条写得更硬：这类外部条目**只用于核「能力形态与命名年份」，不用于引「效果数字」**。

**第三方生产案例**

- **本节未能给出**可核验的第三方（非厂商）公开生产案例。公开材料里能核到的是三类：① 厂商用法文档与官方发布物（能支撑判据①）；② 建设方工程自述（本主题 [§6](04-prompt-engineering-section-6-sec6.md) 的四例，按判据正是这一类）；③ 论文与工具（证明机制与形态存在）。**这个空白本身是结论**：它正是 §5.2 那句「本节没有一行达到 L1」的直接原因，也解释了 §5.6 的五条预测为何全部只能标【经验】。
- 要自己补这一类材料，可核的入口只有两个方向：**你自己的门禁样本**（分组通过率 + 不稳定样本数；§5.3.7 的三样串起来就是最小闭环）与**第三方工程博客 / 会议议程里的换代前后对照**（要按 §2.2 的分组口径读，且需「查询集来源 / 指标口径 / 对照条件」三者齐全才可复核）。

**怎么用这份清单**：要核「能力存不存在」，看官方文档与定价页（最快，也是唯一能核①栏的地方）；要核「机制是不是真的」，看论文（最慢但最稳）；要核「在我这里值不值得做」，看 §5.3 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。**这份清单最诚实的部分是它缺的那一半**：八个方向里，**推理型模型的提示形态（§5.3.1）、上下文工程（§5.3.3）、跨供应商可移植（§5.3.6 前半）、Agent 技能包（§5.3.6 后半）这四条，全书核不到任何「具名文档 + 年份」的条目**——凡有人拿一份「公开材料」来支撑这几条中的任何一条，按这里的口径，先问它给不给得出标题与年份。

**引用纪律**：本主题最容易被误引的三类数字是「通过率提升了多少」「成本下降了多少百分比」「缓存命中率是多少」。可复核的做法是回到来源找三样东西——**样本集怎么来的、指标是分组口径还是总体口径、对照的是哪两版（提示版本与模型档位各是什么）**；缺一样就不要引用这个数（这与 §5.2 判据②的空缺、以及本主题 §2.2 的分组判据是同一件事）。

### 5.5 被过度宣传的部分

1. **"用新模型就不用写提示了"**：换模型改的是**推理主体**，不是取消判据——**判据仍要你写**，而且换代时**要重写推理引导段并重跑门禁**。
2. **"提示可以跨模型通用"**：提示与档位耦合是结构性的（§5.3.6）。**可移植的是判据与示例，不是整份提示。**
3. **"自动优化提示省人力"**：它优化的是你给的指标，而**指标与目标的偏差会被放大**（§5.3.5 的过拟合风险）。
4. **"提示越长效果越好"**：prompt token 是**每次调用重复支付**的成本（§4.6），且长上下文本身会稀释关键指令；**"更长"与"更准"不是同向的**。
5. **"提示写好了就不需要评测"**：**改动会持续发生**（业务变、模型换代、示例老化），没有评测就等于每次改动都在赌。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 被证伪的信号 |
| --- | --- |
| "按模型档位分提示版本"会成为标准做法（而不是可选优化） | 三年后主流实践仍用一份提示跨档位，且降级后不做任何调整 |
| 评测的**分组通过率**会取代总体通过率成为标准口径 | 主流实践仍只报一个总的"准确率" |
| 提示缓存会让"稳定段在前"成为硬性布局约束（可读性让路） | 主流实践仍按可读性排布上下文，且不监控缓存命中率 |
| 自动优化提示会长期停在"生成候选 + 人确认"，不直接替换线上 | 主流实践允许系统按指标直接替换线上提示 |
| "提示里的推理引导段"会作为独立可替换的一层被显式管理 | 提示仍是一整段文本，换代时整份重写 |

**这五条全部是【经验】档**：它们是对机制与工程行为的判断，无具名出处、无推导链——**请按"可被证伪"使用，而不是当结论**。

**怎么用这份预测表**：不要用它做技术选型，用它做**反向检查**——每隔半年回来看一次"被证伪的信号"有没有出现。**第五条尤其值得盯**：如果"推理引导段"真的成为独立一层，那么**今天把提示按四段分开**就是提前布局（成本很低，且分段本身对可维护性有利）；如果它没成，分段也不是浪费——**它让"改一处、坏几类"这件事至少可被看见。**

### 5.7 给架构师的行动建议

1. **今年就该做**：20 条门禁样本 + 提示四段化 + 版本与 Owner + 分组评测。**这四件不依赖任何前沿判断**，且是其余一切的前提。
2. **可以试点（每条自带退出条件）**：按档位分版本（退出条件：版本数乘起来之后没有工具支持，靠人记必然出错）；结构化输出走解码层（退出条件：端点不支持，或 Schema 挤压了必要表达）；提示缓存布局优化（退出条件：缓存命中率拿不到数）。
3. **先别投**：自动搜索提示（没有扎实评测集时它会固化偏差）、跨供应商可移植（结构性不成立）、技能包分发（可分发的是形式不是判据）。
4. **无论哪条**：把"**分组通过率 + 不稳定样本数**"作为这一块的第一条 KPI——它同时是提示质量、评测质量与档位适配度的共同语言。
5. **一条反直觉的**：**先删提示，再写提示**——长期迭代的提示里通常有一批**没人能说出依据的段落**（§4.8 的"先坏的是没人知道某段为何存在"）。删掉它们并重跑门禁，**通过率通常会升而不是降**（因为关键指令被稀释了）。这条动作的成本是半天，收益是"提示变短、成本下降、且剩下的每一段都有依据"。

### 5.8 小结

> 本节小结：AI 时代对提示工程的改变**只有一条是机制性的——推理的主体从"提示引导"移到"模型内化"**（§5.3.1），它把"按档位分提示版本"从可选变成必需；其余方向（结构化输出、上下文工程、提示缓存、自动优化、跨供应商移植）都是加固或接口变化。本节没有一行达到 L1，卡点在 ② 上有一条具体解释——**提示是业务判据的载体，公开它等于公开业务规则**；因此成熟度判断必须回到内部判据：**你自己的门禁样本上，分组通过率与不稳定样本数是多少**。**给读者的动作**：先补 20 条门禁样本、把提示四段化（**分段本身就是换代的前置准备**）；再谈结构化输出、缓存布局与自动优化。

> 💡 **思考锚点**：把你的主提示**按四段切开**（判据 / 推理引导 / 示例 / 输出契约），然后对每一段问一句"**如果换一个档位的模型，这一段还要不要**"——判据段与示例段要留，推理引导段很可能要重写或删掉。**这个切分今天就能做**，而它决定你换代时要动多少：**切开了只改一段，没切开就整份重写。**
