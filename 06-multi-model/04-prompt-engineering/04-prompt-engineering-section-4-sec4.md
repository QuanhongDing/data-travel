## 4. 工程实现

### 4.1 落地步骤

这一块有一条与其它主题不同的性质：**它的第一个可交付物是"一组门禁样本"，而不是一个提示**——因为**没有评测样本，提示的每一次改动都无法被判断**。

**Step 1：抽 20 条真实请求，人工标注期望输出（先做这个）**
从线上日志抽 20 条**真实输入**，逐条写下"期望输出"或"期望判据"。**判据**：两个人独立标注同一条，结论是否一致——不一致的那些，正是判据需要写清的地方。**为什么第一步是它**：半小时的事，而它**立刻让后续所有改动可被验证**。

**Step 2：把提示拆成四段，并划清系统 / 任务边界**
**角色与边界 / 任务与判据 / 示例 / 输出约束**。**系统提示只放跨任务共有的部分**（判据跨任务共用才放它），单任务特有的放任务提示。**判据**：改一句系统提示，需要重测的任务类型有几种——**答案就是它的影响面**。

**Step 3：模板 + 变量，且变量有"必填 / 缺省"声明**
提示与代码分离，由配置提供。**判据**：每个变量的缺省值写在**使用方文档**里，而不是只在模板实现里（否则会出现"看起来正常的错答案"）。

**Step 4：补示例（若判据不可文字化）**
固定示例覆盖核心判据、**必须含反例**；长尾用检索式示例，但**必须绑快照**。**判据**：示例集有版本，与提示版本一同发布。

**Step 5：定义输出契约，并写出失败路径**
字段 + 枚举 + 版本；解析失败时是**重试**（有上界）还是**报错**（关键链路宁失败不猜）。**判据**：解析失败率有数。

**Step 6：建评测门禁（按任务分区 + 按输入类型分组）**
每个任务分区一组固定样本；报**分组通过率**而不是总体通过率（§2.2）。**判据**：改动必跑，结果留痕，能回滚。

**Step 7：按模型档位分版本**
`(prompt_version, model_tier)` 是完整标识；降级链的每一跳有自己的提示版本。**判据**：换一次档位，有一套对应的评测结果。

**Step 8：把版本与评测接进发布流程**
发布与回滚都是改指针；**紧急通道存在但使用有记录，且事后必须补评测**。**判据**：能回答"上一版是什么、为什么换掉"。

**顺序的反面（最常见的错误）**：**先优化提示、后建评测**——优化会变成"凭感觉改"，而且**改得越多、越说不清哪一步是改进**；一旦团队形成了"改完看几个例子就上"的习惯，**评测集会被当成额外负担**而不是必需品。**第二条反面**：**先按档位分版本、后建评测**——多份版本没有各自的评测结果，等于把不确定性乘上档位数。

### 4.2 关键技术点

**（1）四段结构的一个实例（口径来自业务，不来自模型）**

```yaml
prompt_id: ticket_escalation
prompt_version: 7
owner: support-platform@
applies_to_tasks: [escalation_judgement]     # 它服务几类任务 —— 影响面的分母
model_tiers: [flagship, mid]                 # 每个档位一份渲染配置

system: |                                    # 跨任务共有的判据放这里
  你是一名客服工单分级助手。你只做判断，不执行动作。
  判定必须依据下列口径，不得自行发明口径：
    · 涉及资金安全（退款/扣款/账户异常） ⇒ 必须升级
    · 涉及人身安全 ⇒ 必须升级
    · 仅咨询类且无资金动作 ⇒ 不升级
  不确定时输出 need_more_info，而不是猜一个结论。

task: |
  依据上述口径判断工单 {{ticket_text}} 是否升级，并给出依据条目编号。

examples:                                    # 固定示例：覆盖核心判据 + 反例
  - input:  "我买的券怎么还没到账"
    output: {escalate: true, reason_codes: ["funds"], note: "涉及资金到账"}
  - input:  "问一下会员权益有哪些"
    output: {escalate: false, reason_codes: [], note: "纯咨询，无资金动作"}
  - input:  "帮我查一下上月账单明细"        # ← 反例：看着像资金，其实只是查询
    output: {escalate: false, reason_codes: [], note: "查询类，无资金动作"}

output_contract:
  schema: {escalate: bool, reason_codes: [enum], note: string, need_more_info: bool}
  on_parse_failure: retry_once_then_error   # 关键链路：宁可失败不可猜
```

**判据**：上面三个部分**各自有一个可核查的问题**——系统提示的判据是否可判定（"涉及资金安全"要看得到实例才能判，因此示例里给了反例）；任务的依据是否可引用（`reason_codes`）；输出是否有枚举与失败路径。

**（2）门禁样本的组织（按任务分区 + 按输入类型分组）**

```text
evals/
  escalation_judgement/            ← 任务分区
    gate.jsonl                     ← 门禁样本（每次改动必跑）
    edge_cases.jsonl               ← 边界与反例（新增时必须回归）
    报告格式：
      | 输入类型 | 样本数 | 通过 | 违例 | 备注 |
      | 资金类   | 40     | 40   | 0    |      |
      | 查询类   | 30     | 29   | 1    | ← 违例集中在这里，总体通过率看不出来 |
      | 边界类   | 12     | 9    | 3    | ← 边界是业务追问的地方 |
判据：报告必须按类型分组；只报总通过率会把"某类全错"平均掉
```

**（3）稳定性测量（同一输入重复调用）**

```text
void: 取 20 条门禁样本，每条重复调用 n=5 次（temperature 按线上配置）
  稳定   = 5 次输出一致（或落在同一可接受集合内）
  不稳定 = 出现两种以上结论
判据：不稳定样本的分布比"总体通过率"更有信息量 ——
      如果高危及边界样本恰好是那些不稳定的，说明提示在这些区域没有定义清楚
```

**（4）版本标识的落地（缺一项就无法归因）**

```python
call_meta = {
  "prompt_id": "ticket_escalation", "prompt_version": 7,
  "model_name": "…", "model_version": "…",          # 厂商侧也会更新，必须记
  "decode_params": {"temperature": 0.2, "max_tokens": 512},
  "tool_schema_version": None,                       # 无工具时为 None，不要省这个字段
  "retrieval_snapshot": "2024-07-01T00:00Z",         # 检索式示例 / 上下文绑定的快照
}
# 判据：拿这条记录能复现当时的输入吗？不能，说明还有变量没被版本化
```

**（5）提示注入的三层防御（落点都不在提示词里）**

| 层 | 做法 | 强度 | 失效条件 |
| --- | --- | --- | --- |
| 输入分隔与降权 | 外部内容用明确边界包裹 + 声明"以下是指令" | 概率性（**不是保证**） | 模型被说服时失效 |
| **权限前置** | 在检索与工具出口裁剪"这次能触达什么" | **硬约束** | 出口可被绕过时失效（同 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的旁路） |
| 输出校验 | 出向敏感实体检测 + 动作白名单 | 硬约束 | 检测点漏掉缓存 / 日志时失效（同 [Ch8 §02 §3.2.7](../../08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance-section-3-sec3.md) 的双端要求） |

**判据**：**三层里必须有一层是硬的（② 或 ③）**——只靠 ① 是把安全押在模型的服从性上。

### 4.3 工具链与平台

| 能力 | 自建 / 开源 | 产品化 | 选型要点 |
| --- | --- | --- | --- |
| 提示存储与版本 | 自建（配置中心 + 版本表） | 提示管理平台 | **看能不能导出**（锁在产品里就换不掉） |
| 模板渲染 | 自建 / 轻量模板 | 平台自带 | 看变量契约与缺省值是否显式 |
| 评测 | 自建（jsonl + 脚本） | 评测平台 | 看**是否支持按类型分组报**与固定门禁样本 |
| 示例检索 | 复用检索层（[Ch4 §04](../../04-data-assetization/04-hybrid-search/04-hybrid-search.md)） | 平台自带 | 看**是否支持绑定快照**与记录示例 id |
| 输出契约 | 供应商的结构化输出 / 自建校验 | 平台自带 | 看是否支持**解码层约束**（最可靠那条路线） |
| A/B 与灰度 | 复用实验平台（[Ch9 §06](../../09-data-intelligence-product/06-precision-operation/06-precision-operation.md)） | 平台自带 | 看**回滚是不是改指针** |
| 注入防御 | 自建（分隔 + 出口裁剪 + 出向校验） | 安全产品 | 看**权限前置**这一层在不在它的能力里 |

**一条选型原则**：**评测的归属比提示编辑的便利性重要**。一个"改提示很方便"但**不产出分组评测结果**的平台，会让你在改得快的同时失去判断力；而**评测能力**决定了这套东西是"资产"还是"一堆文本"。

### 4.4 存量迁移

**（1）存量的提示散在各处怎么办**

| 对象 | 处理 | 注意 |
| --- | --- | --- |
| 硬编码在业务代码里的提示 | 抽出来 → 建版本 → 与代码解耦 | **先抽高频、高影响的**，不要一次全抽 |
| 同一判据的多份副本 | 合并到一处（或抽进系统提示） | 合并时会出现"两份不一样"——**此时要问业务哪份为准**，不自行合并 |
| 没有评测的提示 | 补门禁样本（抽真实请求 + 人工标注） | **这一步的产出比调整提示本身更值钱** |
| 检索式示例（若有） | 加快照绑定 + 示例 id 记录 | 不绑快照时，历史评测结果不可比 |
| 多档位共用一份提示 | 按档位分版本 + 各自评测 | 先看降级链上有几个档位（版本数 = 档位 × 任务） |

**（2）迁移的三条验收判据**

- **同一判据只出现一处**（不再有分叉副本）。
- **每个提示有门禁样本，且改动必跑**（结果留痕）。
- **换一次模型档位能拿到对应的评测结果**（不是"先上看看"）。

### 4.5 模板 / 示例

**模板 1：提示资产卡（每个提示一张）**

```text
| 项 | 内容 |
| --- | --- |
| prompt_id / 版本 | ticket_escalation / v7 |
| Owner | support-platform@ |
| 服务任务 | escalation_judgement（1 类） |
| 适用档位 | flagship(v7-b)、mid(v7-c) —— 每档一份渲染配置 |
| 四段 | 系统（跨任务判据）/ 任务 / 示例（3 条，含 1 条反例）/ 输出契约 |
| 变量 | ticket_text（必填）；tenant_id（必填）——**无缺省** |
| 示例集版本 | examples-v3（与提示版本一同发布） |
| 评测 | gate.jsonl 82 条，按 3 类分组；最近一次结果：资金 40/40、查询 29/30、边界 9/12 |
| 变更记录 | v6→v7：把"涉及资金"细化为三条列举；原因：边界类违例 3 条集中在"查询 vs 资金"的混淆 |
| 回滚 | 改指针即可；上一版 v6 |
判据：这张卡能回答"改动为什么改、怎么验证的、怎么退回"三问
```

**模板 2：一次提示改动的门禁流程**

```text
1. 改动前：跑一次门禁（拿基线）—— 记录 v6 的通过率与违例分布
2. 改：只改一处（一次改动一个变量，否则无法归因）
3. 跑门禁：分组对比 v6 / v7
   放行条件：① 无任何分组的违例数上升；② 目标分组的违例数下降
   —— 注意是"无任何一组上升"，不是"总体不下降"
4. 线上灰度：按流量分流，观测业务指标（同 §03 网关的租户标签）
5. 回滚条件：业务指标变差即回滚（改指针）
判据：第 3 步的"无任何一组上升"是这条流程的核心 —— 总体不降可能掩盖某一组的退化
```

**模板 3：注入防御的三层检查（可演练）**

```text
① 分隔是否生效：构造一条把"忽略以上指令"藏在检索文档里的输入，
   看模型是否照做 —— 它**大概率仍会**，所以这一层只算降低概率
② 权限是否前置：用无权账号触发同一条链路，去查**上下文构建日志与缓存**
   里有没有出现无权内容（不是查返回值）—— 这是硬约束的关键证据
③ 出向是否拦住：构造一条会输出敏感实体的输入，看是否被拦或要求确认
判据：三层里 ② 必须过 —— 它决定"注入成功后能造成多大后果"
```

### 4.6 成本：这套东西的账单

**硬件**：本主题**无专属硬件成本**——提示的存储与渲染都是配置级负载。三处间接相关：① **评测跑批**（每次改动要跑门禁样本 × 可能的多次重复），成本 = `样本数 × 重复次数 × 单次调用成本`；② **检索式示例的索引**（复用检索层，量小）；③ **灰度期的双版本并行**（同一批流量有两套提示在跑，成本略升）。

**prompt token 是本主题的成本主项**，且它有一个与其它主题不同的性质：**它随每一次调用重复支付**：

```
单次成本 = (系统提示 + 示例 + 检索上下文 + 用户输入) × 单价_in
         + completion_tokens × 单价_out

示例的边际成本 = 示例 token × 调用量        ← 示例是"每次都要付一次"的
判据：当"系统提示 + 示例"占 prompt 的多数时【经验】，
      先做三件事：① 去掉与判据无关的示例；② 把长示例压缩成"输入摘要 + 结论 + 依据码"；
      ③ 长尾示例改检索式（按需注入） —— 这三件的收益按调用量线性放大
```

**人力（主项）**：这一块的人力集中在三项：

1. **评测样本的标注与维护**：抽真实请求、人工标注、随业务演进更新。**这是本主题唯一无法自动化的投入**，且它是其它一切的依据。
2. **提示的迭代与评审**：改动、跑门禁、解读分组结果。**成本随提示数与任务类型数增长**（`提示数 × 任务分区数`）。
3. **多档位版本的维护**：每次模型换代，`档位数 × 提示数` 份版本都要重跑评测。**这项成本随"厂商发版频率"而不是随你的规模增长**——是它最容易被漏算的原因。

**一条推论**：**本主题的成本是"prompt token 随调用量线性 + 人力随提示数与档位数增长"**。因此**它的规模化压力来自"提示与任务的组合数"**——这也解释了为什么"合并相似提示"在这里是实打实的成本优化（与 [Ch9 §04 标签退役](../04-smart-tag-platform/04-smart-tag-platform-section-3-sec3.md) 是同一逻辑）。

### 4.7 容灾与故障演练

**本主题的"灾"分两类**：① **提示服务不可用**（拿不到提示，调用发不出去）；② **提示静默失效**（输出照常返回，但行为已经不对——**更危险**）。

| 失效形态 | 影响面 | 降级策略 | 演练动作 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 配置中心不可用 | 全部调用 | **失败关闭**：不发出"没有系统提示"的请求（**裸调用会放大注入风险**） | 关一次配置中心，验证调用被拒而不是裸发 | 分钟级 |
| 模型版本被厂商更新 | 行为静默变化 | 无自动降级；**告警 + 重跑门禁** | 用同一份门禁样本定期复跑（模型没换也算） | 天级（发现依赖定期跑） |
| 检索式示例索引故障 | 示例注入失败 | 降级到**固定示例子集**（保核心判据） | 关索引，验证是否退到固定示例而不是"无示例" | 分钟级 |
| 输出契约变更 | 下游解析失败 | 契约变更走版本 + 双版本并行期 | 发一版新契约，验证旧版下游仍可用 | 一次发布周期 |
| 提示被误改 | 行为大面积变化 | **回滚指针**；对受影响调用标 `prompt_version` 便于筛样本 | 故意改错一处，验证能回滚并筛出受影响的调用 | 分钟级 |
| 注入攻击成功 | 数据越权 / 错误动作 | 由 ② 权限前置兜底（**这是设计意图**） | 构造注入样本，看它是否只能拿到已授权的内容 | 单请求级 |
| 示例集与提示版本不一致 | 行为时对时错 | 发布流程强制两者同版本 | 人为制造不一致，看门禁能否发现 | 分钟级 |

**这套演练的三条纪律**：

1. **凡是"判定类"机制不可用，必须失败关闭**——配置中心挂了**不许裸发**（没有系统提示的调用同时失去边界与注入防御）。
2. **"提示静默失效"要靠定期复跑门禁发现**——它是本主题唯一会"不报错但变坏"的失效形态，**而模型版本更新是它最常见的成因**。
3. **每次演练留"演练前 / 演练后"两组数字**——特别是分组通过率与不稳定样本数。

### 4.8 演进路线：0 → 1 → 100

**0 → 1：一个提示有版本、有 20 条样本**
- **这一步做什么**：抽 20 条真实请求人工标注；把提示拆四段；给提示建版本。
- **变贵的是什么**：**人力（标注与判据梳理）**——判据要业务确认，而"什么算升级"这类问题不是技术能拍板的。
- **先坏的是什么**：**先坏的是边界输入**——20 条样本里总会漏掉几类，而它们恰恰是业务最先质疑的。**这一阶段的判据不是"通过率多高"，而是"能不能说出这次改动是改进还是退化"。**

**1 → 10：门禁、分区、按档位分版本**
- **这一步做什么**：评测集按任务分区 + 按输入类型分组；改动必跑门禁；模板化；输出契约 + 失败路径；按档位分版本。
- **变贵的是什么**：**评测维护**（样本要随业务演进更新）与**多档位的版本数**（`档位 × 提示`）。**它变贵的不是算力，而是"每次厂商发版都要重跑一遍"这件事。**
- **先坏的是什么**：**先坏的是示例集与提示的同步**——两者分开发布时，行为会变得忽好忽坏，而排查时最先被怀疑的是"模型不稳定"。

**10 → 100：资产化与治理**
- **这一步做什么**：提示接入发布流程（改指针、可回滚、紧急通道有记录）；注入防御三层齐备；示例检索绑快照；合并相似提示；把提示作为对外接口的一部分（供 Agent / 产品消费）。
- **变贵的是什么**：**治理与合并的协调成本**——合并相似提示要先说服两个团队接受同一套判据。
- **先坏的是什么**：**先坏的是"没人知道某段提示为何存在"**——长期迭代后，提示里会积累无依据的段落，而**没人敢删**。因此这一阶段的重点是**给每段标注依据**（哪条判据、哪个案例要求它存在）。

**贯穿三阶段的一件事**：**保留"改动的可验证性"**。它是这一块唯一的健康基础——**提示工程的腐化不会报错，只会表现为"提示越来越长、越来越没人敢改、而效果说不清是变好还是变坏"。**

### 4.10 小结

> 本节小结：提示工程的落地顺序**以"20 条门禁样本"为先**——半小时的事，却让后续每一次改动都可被验证；然后拆四段划边界、模板化并声明变量缺省、补示例（含反例）、定输出契约与失败路径、建按任务分区的评测门禁、按档位分版本、最后接进发布流程。**变贵的是 prompt token（随调用量线性重复支付）与人力（随提示数与档位数增长，且随厂商发版频率被动增长）**（§4.6）——因此**"合并相似提示"在这里是实打实的成本优化**。**容灾有一条本主题特有的纪律**：**配置中心不可用时必须失败关闭**——**没有系统提示的调用同时失去边界与注入防御**；而**"提示静默失效"要靠定期复跑门禁发现**（模型版本更新是它最常见的成因，§4.7）。**三阶段的同一件事**：保留"改动的可验证性"——**这一块的腐化不会报错，只会让提示越来越长、越来越没人敢改，而效果说不清是变好还是变坏。**

> 💡 **思考锚点**：做一件今天就能做的事——**从线上抽 20 条真实请求，人工写下期望输出**，然后拿它们跑一遍当前提示，**按输入类型分组看结果**。你会看到一个此前不知道的数：**某一类输入的违例率**（而总体通过率把它平均掉了）。这一类的违例就是你提示里"没有定义清楚"的那部分——**你打算先补判据，还是先补示例？**
