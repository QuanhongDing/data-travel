## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

接入层形态由**五条约束**决定，顺序不能颠倒：

1. **厂商数量与变更频率**：只用一家，还是三家以上？一年换几次档位？**只用一家且半年不动**时，独立的接入层收益有限（模式 3.2.1 / 3.2.2 够用）。
2. **数据能否出域**：哪些租户 / 哪类数据可以发往外部端点？不能，则必须存在**自托管端点**，且路由的硬约束里要带出网判定。
3. **是否需要按租户计费**：要按租户 / 应用结算，则**记账点必须在网关**（应用侧的统计无法作为结算依据）。
4. **可用性目标**：模型端点不可用时，业务能接受"等待"还是必须"降级出结果"？后者要求降级链与质量损失估计。
5. **团队承接能力**：有没有人能维护归一化层与能力矩阵？（能力矩阵是**长期维护项**，不是一次配置。）

> **判据的用法**：先用 1 判断"要不要独立一层"；用 2、3 决定"这一层必须有哪几个部件"；最后用 4、5 决定"这一层做到多深"。**跳过第 5 条最常见的后果**：网关建起来了，但能力矩阵三个月没更新，路由把"其实不支持工具调用"的模型分配给了工具型任务。

**每条约束的"过关"是可核查的，不是判断题**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 厂商与变更频率 | 能列出近 12 个月的档位变更次数，以及每次变更动了几处代码 |
| 2 数据能否出域 | 有一张"租户 → 可去端点"的表，且它能被机器读取（不是文档） |
| 3 按租户计费 | 能当场按租户拆出一份账单，且与厂商账单对得上 |
| 4 可用性目标 | 端点故障时业务的行为是**写下来的**（等待 / 降级 / 报错），不是临场决定 |
| 5 团队承接 | 能力矩阵有明确的更新触发条件（例如"厂商发布条目变更即更新"）与最近一次更新时间 |

上表五条都是**半天内可以做完的验证**。注意第 5 条的判据刻意写成"触发条件"而不是"有人负责"——**能力矩阵的失效从来不是没人管，而是没有人知道什么时候该管**：厂商发布一条新能力不会主动通知你，所以必须把"更新触发条件"落到一个可执行的动作上（例如每月核对一次各厂商的发布条目）。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 直连厂商 SDK

**被什么约束逼出来**：只有一个厂商、一个应用、且对计量与降级没有要求（多见于原型或内部工具）。

**结构**：应用直接调用厂商 SDK；密钥在应用配置里。

**为什么这样设计有效**：因为**调用链上只有一次网络往返，且没有任何中间状态需要一致**——请求构造、重试策略、错误映射全部在同一个进程里，因此"看到什么就是什么"，调试时不需要跨系统拼时间线。**这条有效性来自"消除了中间层"，所以它在引入任何一个中间件后立刻消失**；这也是它不能作为长期形态的原因：它唯一的那点优势，恰好是后续所有治理要消除的东西。

**代价**：换模型要改代码；密钥散落；计量只能看总额；限流与超时由应用各自处理。

**失效点**：一旦出现第二个厂商或第二个应用——**这个模式不是演进到网关，而是必须被替换**；它的危险在于"看起来能撑很久"。**替换的代价集中在两处**：散落在各应用的密钥（需要一次集中轮换）与各自实现的重试/超时（需要一次行为对齐），两者都比"改一行 endpoint 地址"贵得多。

**判定方法**：把最近一次"换档或者新增一家厂商"改动的文件列出来——若改动落在三个以上应用各自的调用代码里、而不是落在一处配置里，就还停在直连形态；再把这几处引用的密钥来源列一遍，看轮换一次要动几个应用。

**真实使用**：本主题 §1.4 把 2022–2023 定为"直连 SDK 阶段"，其特征正是每个应用各自 `import` 厂商 SDK、换模型即改代码、密钥散落；Ch6 章首把这一层要统一接入的对象列为 OpenAI / Anthropic Claude / 国内大模型，直连阶段的输入就是这些厂商的官方 SDK。§7.2 的候选全景里**没有"直连"这一行**——它不是一个可选方案，而是这条演进线的**起点**（这也解释了为什么 §7.6 的选型矩阵从"单团队单厂商"起步，而不是从"直连"起步）。各厂商 SDK 的调用形态本节不引文档条目，请以各厂商官方 SDK 文档当前版本为准。【公开】（来源：本主题主文件 §1.4 演进历程 2022–2023 年条目；本主题 §7.2 候选全景、§7.6 选型矩阵；Ch6 章首 `06-multi-model/README.md`）

#### 3.2.2 应用内封装（SDK 包装函数）

**被什么约束逼出来**：同一团队内多个应用都要调模型，想少写重复代码。

**结构**：抽出一个内部工具函数库，统一请求构造与重试；各应用依赖这个库。

**为什么这样设计有效**：因为**重复代码被消掉了，而引入的成本只是一个依赖**——没有新进程、没有新部署单元、没有新的网络跳数，所以它是在"直连"之上几乎无代价的一步改进。**但它的有效性边界很明确：库是"代码"而不是"服务"**——凡是需要**跨进程共享状态**的能力（全局计数、统一降级、集中吊销），库都实现不了（除非引入外部存储，那实际上就是在偷偷建一个服务）。**所以它解决的是"写法不统一"，不解决"口径不统一"。**

**代价**：**库是代码，不是服务**——每个应用锁定的库版本不同，行为随之分叉；密钥仍在应用侧；计量与降级无法统一实现（库无法持有全局状态，除非引入外部存储）。

**失效点**：当出现"同一个问题在两个应用里得到不同结果"时，通常是库版本分叉——此时要么统一升级（发版风暴），要么改成服务（网关）。**判据可以量化**：把各应用锁定的库版本列出来，若存在两个以上版本且其中一个已超过一个季度未升级，分叉只是尚未被发现。

**判定方法**：任取一个"同一个问题在两个应用里得到不同结果"的工单，把它追到库版本；再实际问一次"换成服务形态之后，计量与降级能不能统一实现"——凡是需要跨进程共享状态的能力（全局计数、统一降级、集中吊销），库形态都答不了。这一问不需要采购，也不需要改造。

**真实使用**：这一模式在公开材料里**没有可指名的实现**——它是各组织内部的私有库，且各家的形态差异很大（有的只包装请求构造，有的连重试与超时都包）。本主题只按形态描述它：§1.4 的 2023 年阶段，与 §7.2 的候选之一"应用内封装（库）"；§7.3.1 给出了它的机制结论——**库形态的一层在原理上无法承担计量与降级**，因为两者都要跨进程的全局状态（§7.3.1 把"归一化的位置"这一组差异逐条列出）。因此可核验的不是它的产品名，而是它的失效形态：本节失效点给出的判据是"各应用锁定的库版本出现两版以上、且其中一版超过一个季度未升级"。**本节不给具名实现，也不建议据此选型**；§7.3.4 另给出它的迁移口径——依赖他人（或自己）的归一化，都必须自建回归测试集，这条对库形态同样成立。【经验】（来源：本主题主文件 §1.4 2023 年条目；本主题 §7.2 候选表、§7.3.1 与 §7.3.4 的机制差异）

#### 3.2.3 自研统一网关

**被什么约束逼出来**：多厂商 + 需要按租户计量 + 需要降级（约束 2、3、4 同时成立）。

**结构**：独立服务承接全部模型调用；内部分五块（归一化、路由、凭证、计量、韧性）；配置驱动。

**为什么这样设计有效**：因为它让**四件本来分散的事收敛到了同一个位置**——归一化只有一份（跟厂商变化只改一处）、计量只有一个记账点（账能对上）、降级链只有一处实现（行为全局一致）、密钥只有一处托管（能轮换能吊销）。**收敛的有效性来自"唯一性"本身**：任何一件存在两处实现，它就会出现两个版本，而两个版本迟早会不一致；**收敛不是为了让代码好看，而是为了消除"不一致"这个失效形态的产生条件**。

**代价**：① 归一化层要长期跟厂商变化（**这是持续成本，不是一次性成本**）；② 网关自身成为关键路径上的单点（必须多副本 + 熔断 + 容量规划）；③ 多一跳的延迟开销（通常 `1–10 ms` 量级【经验】，不含端点耗时）。

**代价里最容易被低估的一项**：**归一化层的持续成本随"厂商数 × 能力面"增长**。设 `k` 家厂商、每家平均 `m` 个差异点（流式格式、工具调用格式、用量字段、错误码、参数命名），需要维护的映射是 `O(k × m)`；而每新增一家厂商都会**同时引入它与既有厂商之间的差异**（因为你要在同一套内部模型上表达它）。因此"支持第 4 家厂商"的成本通常高于"支持第 2 家"——**这条增长曲线是选型时要提前算的，而不是等它变成排期积压才发现**。

**失效点**：把网关写成"转发器"——只做鉴权与转发，不做归一化与计量；这时它只是多了一跳，没有换来任何收敛。

**判定方法**：换一次模型档位，看要改几处——如果仍然要改应用代码，说明归一化没有真的发生。第二个动作更便宜：问"这一层上有没有哪一件事是**别人绕不过去**的"（记账点、出网判定、吊销），答不出任何一件，就说明它目前只是一个转发器。

**真实使用**：本书他处有一个可指名的同族案例——Ch8 §01 的阿里一例（2020–2024）把"AI 调用收口到统一网关"列为核心机制，并把"AI 调用路径"从"各业务自行调用"改成"统一网关收口"、表中写作"覆盖 100%"（`08-ai-governance/01-ai-data-governance/01-ai-data-governance-section-6-sec6.md` §6.1）。**但该记录在 Ch8 §6.1 里只有一个无标题、无链接的标记**（`[阿里公开材料 2020-2024]`），Ch8 已自行把它按【经验】而非【公开】记——这一降级在 Ch8 §3 的 §3.2.3（AI 资产 registry）与 §3.2.8（嵌入式治理）两处都复述过（`08-ai-governance/01-ai-data-governance/01-ai-data-governance-section-3-sec3.md`），本节同样按【经验】记，引用前请自行核验。接入层侧的形态与机制见 §7.2 的"自研统一网关"一行，与 §7.3.1–§7.3.6 的六组机制差异（归一化的位置、记账点、出网判定、升级面、差异归因、凭证的位置）；成本形状是 §7.4 的**台阶形**（第一份投入付了才能开始用）。【经验】（来源：Ch8 §01 §6.1 阿里案例；本主题 §7.2、§7.3.1–§7.3.6、§7.4）

#### 3.2.4 开源网关 + 自建治理面

**被什么约束逼出来**：想省掉归一化层的长期维护（约束 5 人手不足），但计费与合规口径必须自己掌握（约束 2、3）。

**结构**：归一化与路由用开源网关（以配置为中心的接入层，LiteLLM / One-API 一类），**计量、配额、审计、出网策略**由自建侧接管（网关前置或旁挂一个治理代理）。

**为什么这样设计有效**：因为它按**"变化的来源"**切了一刀——**归一化跟随的是厂商接口的变化**（变化频繁、有社区共同承担、可回归测试），**计量与合规跟随的是你自己的口径变化**（变化低频但不可外包、一旦出错直接影响账单与合规结论）。**把两件不同来源的变化放在不同的人手里，是这个模式真正的机制**：它不是"省人力"，而是"把跟不动的部分交出去，把不能交的部分留下"。**如果切错了边（把配额交给社区默认实现），它省下的每一点人力都会在第一次对账时还回去。**

**代价**：① 升级开源版本会改变归一化行为（要有回归测试集，否则升级即行为变更）；② 治理代理与网关两跳，链路更长；③ 某些厂商的私有能力可能需要自己补适配。

**代价的量化口径**：① 的代价可以估成"每次升级 × 回归测试集规模"【经验：取决于你覆盖了多少厂商 × 多少能力组合】；**没有回归测试集时，这个代价不是变小而是变成未知**——升级后第一次发现行为变化是在生产里。因此这个模式的**准入条件**不是"有开源网关"，而是"有回归测试集"。

**失效点**：把配额与审计也交给开源网关的默认实现——开源网关的默认语义通常是"限流"，**不是"按租户预扣并结算"**；语义不对，账就永远对不上。

**判定方法**：拿开源网关的配额配置按"调用前预扣、调用后结算"跑一遍——如果它只能限流、不能事前扣减，就说明治理面必须自建；再确认一件事：**你的回归测试集存不存在**（这是本模式的准入条件，不是加分项）。

**真实使用**：这一族的具名形态是"以配置为中心的接入层"，本主题在 §3.2.4（LiteLLM / One-API 一类）、§4.3 工具链、§6.2、§7.2 四处按同一口径点名。本书他处对同族给出了可核验的具名清单：Ch10 §01 §4 把多模态的统一路由与配额落在 LiteLLM / OpenRouter / Portkey 上，并给出这条路特有的失效条件——"**网关只做路由、不做输入规范化时，同一张图在不同模型下的差异会在网关之后才暴露**"，表现是排障只能一个个模型试（`10-industry-agent/01-multimodal-ai/01-multimodal-ai-section-4-sec4.md` §4 第 6 条）；Ch4 §07 §7 的候选表把同族记为"AI Gateway（Kong AI 插件 / Portkey / Cloudflare AI Gateway）"，机制写作"在网关层做多模型路由、Token 计量、凭证托管与回退"（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-7-sec7.md` §7 候选表）。**"治理面必须自建"这条结论的落点是本主题 §6.2 的失败教训**（把配额交给社区默认实现 → 限流一直在生效、账单照样穿透预算）。各产品的功能、许可与版本请以各自官方文档当前版本为准。【公开】（来源：本主题 §3.2.4 / §4.3 / §6.2 / §7.2；Ch10 §01 §4 第 6 条；Ch4 §07 §7 候选表）

#### 3.2.5 凭证托管（与网关共生，但可独立先做）

**被什么约束逼出来**：密钥散落在应用配置里，无法轮换与吊销（约束 3 的合规侧）。

**结构**：密钥只存在网关（或专用密钥服务）中；应用只带**租户身份**，不带厂商密钥；出网策略在网关侧判定。

**为什么这样设计有效**：因为**"密钥在哪里"决定了"吊销要多久"**——密钥在应用侧时，吊销是一次**发布**（要等所有实例重启，时间以小时到天计）；密钥在服务侧时，吊销是一次**改配置**（秒级生效）。**这是一个纯粹的结构性差异，与你的运维水平无关**。另外它还顺带消掉一个高频故障：应用侧持有密钥时，"谁能用哪个端点"散在配置文件里，无法回答"哪个租户在用什么端点"；密钥上收之后这个问题变成一次查询。

**代价**：应用与网关之间需要一次可信身份传递（服务身份 / 短期令牌）——这要求你的内部认证已经统一；否则要先把服务身份做起来。**这一步是许多团队卡住的地方**：它不是"网关的问题"，而是"你的服务身份体系成熟度"的问题；如果内部还在用静态 token 互调，先解决那个，再谈凭证托管。

**失效点**：网关内部把密钥写进日志或错误信息（**最常见的泄漏路径**）；判据是"用一次故意失败的请求，检查日志里有没有密钥片段"。

**判定方法**：先做上面这一次故意失败的请求，在日志里全文检索密钥片段与请求内容片段（命中即托管未生效）；再做第二个动作——拿一次真实轮换，记录从"决定轮换"到"所有调用都用上新密钥"的时长。**顺序不能反**：吊销速度再快，只要密钥还在日志里，它就已经泄漏过一次了。

**真实使用**：托管落点在本书他处出现过两类具名形态。① **以密钥管理服务为落点**——Ch4 §06 的多份材料把密钥管理写成 `AES + KMS`，并把它列为统一数据服务架构里的固定部件，同时把"一把密钥管所有数据"列为一条已知风险（`04-data-assetization/06-one-service/06-one-service-section-8-17-1-基础概念与架构理解.md` §8.17.1）；Ch4 §07 §4 的示例同样要求"密钥要来自配置或密钥管理服务"（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-4-sec4.md` §4）。② **以网关侧凭证托管为落点**——Ch4 §07 §5 把"凭证托管"列为边缘 AI 网关可承担的**四件不需要数据语义的判断**之一（缓存 / 回退 / 重试 / 凭证托管），并给出"缓存键必须含身份维度"这类的边界（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-5-ai.md` §5）。本主题 §4.2（4）给的是这套能力在接入层里的配置形态（含 `log_scrub` 与出网默认 deny）。各密钥管理产品的具体接口本节不给文档条目，请以各自官方文档当前版本为准。【公开】（来源：本主题 §4.2（4）；Ch4 §06 §8.17.1；Ch4 §07 §4、§5）

#### 3.2.6 工具调用标准化

**被什么约束逼出来**：工具由不同团队实现，格式与语义不统一（"可写"没有声明、参数没有 Schema、错误没有分类）。

**结构**：工具以**声明式条目**注册（名称、输入 Schema、是否可写、Owner、权限范围、超时）；调用统一经工具出口（与 [Ch5 §02 §4.2（2）](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-4-sec4.md) 同一套出口）；**模型侧的工具描述由注册表生成**，不允许各应用手写。**协议化的形态**（工具 / 资源 / 提示的标准化接入，MCP 一类）由 Anthropic 于 2024 年公开，规范与实现可按规范当前版本核验【公开】；它解决的是"怎么调"，**不解决"谁能调、调了记什么、超了怎么办"**——后者仍由出口承担。

**为什么这样设计有效**：因为**模型看到的工具清单与治理口径来自同一个来源**——注册表。**这一条同时消掉两类错配**：① **能力错配**（模型以为能调、出口却拒绝，因为模型拿到的手写描述与出口的白名单不同步）；② **参数错配**（同一个工具在不同应用里参数格式不同，因为每个应用各写各的描述）。**有效性来自"单一事实源"，不来自"Schema 写得全"**——即使 Schema 不完备，只要它唯一，错配就会在注册那一刻暴露而不是在调用那一刻。

**代价**：Schema 的维护（尤其当工具返回结构化结果时）；以及**工具版本管理**（改名 / 改参数就是不兼容变更，需要版本号）。

**失效点**：工具 Schema 与实现不同步——模型按 Schema 构造参数，实现却按旧格式解析；**判据**是在 CI 里用 Schema 生成示例参数并真实调用一次（冒烟），成本约每次数秒。

**判定方法**：先跑那次 CI 冒烟（用 Schema 生成示例参数真调一次）；再取一个已注册的工具问三句——**模型看到的描述是谁生成的**、它声明的"可写"与出口的白名单是否同源、它改参数时谁会收到通知。三句里有一句答不出来，就说明存在第二份"事实源"。

**真实使用**：这一模式的具名形态是"工具 / 资源 / 提示的标准化接入"（MCP 一类），由 Anthropic 于 2024 年公开——本主题在 §3.2.6（结构一栏）、§4.5 模板 3、§5.2 分级表、§6.3 案例四处按同一口径记它。本书他处给了同一规范的可核验入口与同族的另一行选型记录：Ch4 §07 §5 记"Model Context Protocol 由 Anthropic 于 2024 年公开并开源，其规范以带日期的修订版本发布"（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-5-ai.md` §5）；Ch4 §07 §7 的候选表在协议族里另立"**MCP 网关**"一行，机制写作"以「能力名 + 参数 schema + 权限范围」注册工具，统一鉴权与计量"（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-7-sec7.md` §7 候选表）——**注意这一行的机制描述与本主题"注册表 + 出口"是同一件事的两种落点**：一个落在网关，一个落在平台出口。注册表这一侧的实现骨架见 Ch5 §02 §4 的"工具出口"（§4.2（2）与 §4.2（4）），该节并给出判据"**接入协议不等于接入治理**"——协议解决"怎么调"，平台还要解决"谁能调、调了记什么、超了怎么办"（`05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-4-sec4.md` §4）。规范版本与功能清单以官方规范页当前版本为准。【公开】（来源：本主题 §3.2.6 / §4.5 / §5.2 / §6.3；Ch4 §07 §5、§7；Ch5 §02 §4）

#### 3.2.7 多级降级链

**被什么约束逼出来**：模型端点不可用或质量不达标，而业务要求"出结果"（约束 4）。

**结构**：`大模型 → 中模型 → 小模型 → 规则 / 缓存 / 人工`；每一跳都带**触发条件**与**质量损失估计**；降级要记事件（谁在什么时候被降级）。

**为什么这样设计有效**：因为**它把"可用性"从二值变成了有损的连续值**——不做降级时，端点不可用等于业务中断（可用性只有 0 和 1）；做了降级后，业务在端点故障期间仍能产出**质量较低但可用**的结果。**这个转换之所以成立，前提是"每一跳的质量损失是量过的"**：没量过质量损失的降级链，等价于"用一次不可知的降级换取一次确定的故障"——**它不一定更糟，但它让你无法在事后解释"当时的结论打了多少折"**（这也是 §3.2.7 失效点①要求降级必须标注的原因）。降级链是**一处实现**，因此全局一致。

**代价**：① 需要为每一跳准备评测证据（否则不知道降级后能不能用）；② 中小模型可能需要不同的提示（**同一提示在不同档位上的表现不可假定相同**）；③ 降级期间的结论必须可标注（否则事后无法区分"正常结论"与"降级结论"）。

**代价②的机制**：**提示与模型档位是耦合的**——按大模型写的详细指令，在小模型上可能因为遵循能力不足而变成噪声；按小模型写的精简指令，在大模型上可能浪费了它的能力。因此降级链的每一跳**应当有自己的提示版本**，而这意味着提示版本数从 1 变成 `跳数`；这正是 §3.2.3 的版本四元组在接入层上的体现。

**失效点**：① 降级链**静默**执行（业务看不到自己用的是降级结果）；② 链条过长（大→中→小→规则）导致质量断崖；③ 没有恢复条件（只降不升）——**只降不升会让系统在端点恢复后长期停留在降级状态**，而这段时间的成本与质量损失都是无声的。

**判定方法**：对链上的每一跳问三件事——**它退到哪一档、质量损失多少、什么条件下升回来**。三问缺任一项，这条链就只是一次静默换模型，而不是降级链；再补一个更便宜的动作：造一次端点不可用（把某个端点的配置指向一个必然失败的地址），看事件流里有没有留下 `degraded` 标注。

**真实使用**：本主题与全书都**没有可指名的降级链实现**——它在这本书里始终以**配置形态**出现：§4.2（7）的路由配置用 `fallback: [mid, economy]` 把"顺序即降级链"写成配置，并配 `quality_floor` 这一质量下限；§6.2 记录这一类开源接入层把"路由与回退"做成配置项（模型别名、优先级、重试链），**因此降级链的具体条目因各家配置格式而异，本节不给具名产品**。本书他处对同一机制给出了成熟度交叉结论：Ch12 §03 §5.2.2 把"降级链路与 Prompt 缓存"并列判为 **L2**，且两行都是①满足、②缺、③缺——**降级链路缺③的理由是"分级口径与开关契约是各企业自建，没有跨厂商标准"**（`12-architecture/03-large-event-readiness/03-large-event-readiness-section-5-ai.md` §5.2.2）；本主题 §5.2 分级表在 **L2 与 ②** 两项上与它一致（本主题也把"模型降级链"记为 L2、②核不到），但 **③ 的判据不同粒度**——Ch12 要求的是"分级口径与开关契约跨厂商统一"（故缺③），本主题要求的是你自建的那份回退配置接口稳定（故记成立，见 §4.2（7）的 `fallback` + `quality_floor`）。请按"口径自建"使用本节这一模式。【经验】（来源：本主题 §4.2（7）路由配置、§6.2 开源族的回退配置形态、§5.2 分级表；Ch12 §03 §5.2.2）

#### 3.2.8 缓存（精确缓存 / 语义缓存）

**被什么约束逼出来**：重复请求占比高（如标准问题、固定报表解释），需要降成本。

**结构**：精确缓存（请求 + 参数哈希，命中即返回）与语义缓存（相近问题复用，需带条件）；缓存键要包含**模型版本与提示版本**。

**为什么这样设计有效**：因为**它把成本函数里的"请求数"这一项直接乘以了命中率**——单次成本不变，但计费次数下降，所以节省量 ≈ `命中数 × 单请求成本`【推算：假设命中请求完全不产生端点调用；实际需扣除缓存查询与比对成本】。**有效性完全由两个数决定：重复率有多高、正确的复用能占多少**。而这两条对"精确缓存"与"语义缓存"是不同的：精确缓存只吃"完全相同的请求"，判定是确定性的（没有误判）；语义缓存吃"相近的请求"，判定是概率性的（有误判）。**因此它们的有效性来源不同——精确缓存来自确定性，语义缓存来自覆盖面；而语义缓存的覆盖面越大，误判面越大。**

**代价**：① 缓存必须有**失效条件**（模型换了、语料换了、时间条件变了都要失效）；② 语义缓存的错误复用会**静默传播**（用户看不出答案来自另一个问题）；③ 缓存存储与一致性检查是额外运维。

**失效点**：把语义缓存用在**带数值或时间条件**的问题上（"上月 GMV 多少"被复用给"本月 GMV"）——**这是本层最危险的一类错误**，必须按任务类型禁用。**可执行的禁用清单口径**：凡是答案里含"随时间变化的量"（金额、计数、排名、库存、状态）或"依赖调用方身份"（我的、我们的、我的部门）的任务类型，一律禁用语义缓存；只对"解释型、定义型、流程型"问题开放。

**判定方法**：抽一周的缓存命中记录逐条判"这条命中的答案是否同义"——给不出这个抽检动作，语义缓存就不该开；再确认缓存键是否同时含**模型版本、提示版本、身份维度**三项（本章 §MG.6 就是这三问的可自答版本）。两步都不需要采购。

**真实使用**：与本模式相邻的具名机制是**上下文前缀缓存**、**不是语义缓存**——这个区别必须点明，否则是一次错误具名。Anthropic 于 2024 年推出的 prompt caching 被 Ch7 §01 §8 记为"让重复出现的 system prompt 命中缓存"，并明确它与记忆机制是两件事（前者是 KV cache 复用、无 LLM 决策；后者才是记忆）；自托管侧的对应能力是 vLLM 的 prefix caching 与 SGLang 的 radix attention 一类（`07-agent-evolution/01-long-term-memory/01-long-term-memory-section-8-sec8.md` §8）。Ch12 §05 把"前缀缓存"判为 **L2**，并给出两个可测的数——**共享前缀的 token 占比**与**重复提问的比例**，同时点出它的失效是静默的（前缀里混进时间戳或未排序的 JSON，命中率归零而系统照常工作，只是账单变高）（`12-architecture/05-performance-engineering/05-performance-engineering-section-5-ai.md` §5）。**语义缓存本主题不给具名产品**：它的收益与误命中代价都取决于你自己的重复率与抽检动作，公开的命中率与省钱比例几乎都来自建设方（本主题 §2.2 的盈亏平衡式子、§3.2.8 的禁用清单、§4.6 的命中率区间【经验】）。【公开】（来源：本主题 §2.2 / §3.2.8 / §4.6；Ch7 §01 §8；Ch12 §05 §5）

#### 3.2.9 对外契约形态：自定义契约 / 兼容面 / 两者并存

**被什么约束逼出来**：**约束 5 的另一半**——§3.1 问的是"你这边有没有人能维护归一化层"，本格问的是同一件事的对外侧：**调用方那边有多少人愿意跟着你改客户端**。前八格解决的都是"这一层怎么建"，但建好之后它必然要对调用方**承诺点什么**：调用方拿到的那套请求 / 响应 / 错误结构，就是这一层的**对外契约**——本主题 §6.2 记这一族现状的那一行正是它（"对外暴露一套内部模型（统一的请求 / 响应 / 错误结构），把厂商差异收在适配层"）。**契约只要变过一次，它就从"接口"变成了"承诺"**；而承诺的维护成本不由你的技术方案决定，由**调用方的发版节奏**决定。

**结构**：三种对外形态，分界只有一句话——**调用方愿不愿意改一行客户端代码**。

| 形态 | 做法 | 调用方付什么 | 你的代价 | 失效条件 |
| --- | --- | --- | --- | --- |
| ① 只给自定义内部契约 | 只有一套你定义的请求 / 响应 / 错误结构，调用方按它改客户端 | 一次改造（改代码 → 回归 → 联调 → 发版） | 每新增一个调用方再付一次接入成本 | **出现一个你无权要求它改版的调用方**（外部方、发版周期以季度计的团队）时立刻失效 |
| ② 只给兼容面（OpenAI 一类） | 对外暴露与某套既有契约同形的接口，存量 SDK 只改指向与模型别名 | 近乎为零 | **被那个契约的形状绑住**：它的字段、错误语义与限制成为你的对表面上限 | 你要表达的东西在那个形状里**没有位置**时（工具调用增量、多模态部件顺序、用量分项）——只能塞进私有扩展字段，"兼容面"退化成"兼容面 + 一堆私有字段"，统一语义反而没了 |
| ③ 两者并存 | 兼容面接存量与第三方，原生面表达完整语义 | 存量近零；新调用方按原生面写 | **两套语义要长期对齐**：每个新能力要在两个契约上各定义一次，默认值、错误映射、用量口径会随时间漂移 | **原生面没有真实用户**时——没人迁过来，兼容面事实上是主契约，而那份对齐成本照付 |

**判据（§7.3.4 的同一逻辑换到对外方向）**：§7.3.4 判定升级面用的是"行为变更是否出现在变更评审的议题里"；换到对外方向就是**"契约变更是否出现在调用方的发版计划里"**。所以选择依据是**调用方里"愿意改客户端代码"的占比**，而不是偏好：调用方只有内部一两个应用、与这一层在同一次发版里发布，①就够（**§7.3.6 的失效条件用的是同一条推理——看的不是应用数，而是发布节奏最慢的那个应用**）；有多个团队各按自己的节奏发版、还有第三方，②是唯一低成本的形态。**③ 只在"两者都有、且你能指认哪个是主契约"时成立**：指认不出主契约的"并存"，结果是两个契约都只被维护一半。

**为什么这样设计有效**：因为**兼容面把最贵的那一项接入成本转给了"既有约定的形状"**——调用方不改调用代码，省下的是回归与联调。这一条在本书他处有实证：换成兼容 OpenAI 接口的别家客户端时"只需改 model 名"（`01-modeling/07-graph-reasoning/07-graph-reasoning-section-4-sec4.md` §4 例 4 的代码注释）；推理引擎侧的对外服务接口被记为"按 OpenAI 兼容形态提供"，并且这直接构成为那一行"接口稳定性"判据的满足依据（`12-architecture/03-large-event-readiness/03-large-event-readiness-section-5-ai.md` §5 的"证据与来源"块）；同族口径另见 Ch9 §01 的 §5（把"OpenAI 兼容的服务接口"记为事实标准）与 §4（把模型市场的对外暴露写成"统一推理 API（OpenAI 兼容 / 自定义）"）（`09-data-intelligence-product/01-ai-compute/01-ai-compute-section-5-ai.md`、`09-data-intelligence-product/01-ai-compute/01-ai-compute-section-4-sec4.md`）。**因此选 ② 的真实理由不是"省自己的事"，而是把"每个调用方一次改造"降成"一次配置"。**

**代价**：① **兼容面是一份你不拥有的契约**——它的形状由别人演进，你只能跟（与 §7.3.4 是同一机制：**行为变更的时点被别人决定**）；② **兼容面几乎不覆盖你的治理字段**——配额、租户、出网判定、降级标注在那套形状里都没有位置（§3.2.6 的同类结论"协议解决'怎么调'，不解决'谁能调、调了记什么、超了怎么办'"在对外契约上同样成立），所以②必须配一条**私有参数通道**，而这条通道默认应当是**窄且可枚举的白名单**，不能变成"什么都能传"的口子；③ **形态"两者并存"的两套语义对齐是长期人力**，不是一次性工作量。

**什么算"不兼容变更"**（把 §3.2.6 已写成一条代价的"工具改名 / 改参数就是不兼容变更"扩到对外契约）：七条里**只有第一条看得见，其余六条都是"字段没动、行为变了"**——这正是 §7.3.4"归一化的行为变化难以从表面看出"的对外版本。① 字段改名 / 删除 / 类型变化（调用方按旧名解析，直接失败）；② **必填性变化**（把可选改必填，平时不传该字段的调用方全部被拒——最隐蔽）；③ **默认值变化**（字段一个没动，没显式传参的调用方行为变了）；④ **错误码语义重映射**（同一个码换了含义，按错误码做重试与降级的调用方会做错决定）；⑤ 枚举值新增（对"未知值即报错"的调用方是不兼容——**因此"未知值报错还是忽略"必须写进契约**，否则它算不算不兼容变更由调用方各自解释）；⑥ **流式事件序列变化**（事件类型、顺序、结束帧、用量收尾；调用方的解析器按它写死，本主题 §4.2（1）的"流式"一类必归字段就是它）；⑦ **用量 / 计费口径变化**（调用方拿这些字段对账，口径改一次它的成本看板全失真）。**这七条与本书他处同类清单的分界**：①–⑤ 是任何一份"对外接口承诺"都会写的字段级演进纪律（Ch4 §07 §8 的版本纪律即同族，故不构成本主题的专属内容）；**⑥⑦ 别处承接不了**——它们锚在本主题 §4.2（1）的"流式"与"用量"两类必归字段上，只在模型调用这一侧成立。

**废弃窗口怎么写进契约**（三条，缺一条等于没有承诺）：① **版本标识要出现在请求与响应里**——调用方要能在**运行期**知道自己在用哪一版（只写在 URL 或只写在交付文档里都不够）；② **弃用标记要机器可读**——响应头或响应字段里带"已弃用 + 日落条件"，而不是发一封通知邮件；③ **弃用期内行为冻结**——旧版本只修缺陷、不加能力，否则"兼容"是随缘的。**窗口长度怎么定**：判据不是拍一个天数，而是**调用方里发版周期最长的那个的周期**（同 §7.3.6 的推理）。书内他处有一份可参照的口径：Ch4 §06 把统一数据服务的版本策略写成"变更必破坏模型一致性时强制新版本，老版本进入弃用周期"【经验：书内记为"一般 3~6 个月"】，配套动作是"只加字段不删字段、删除走废弃期（带警告）、强制新版本走评审与灰度"（`04-data-assetization/06-one-service/06-one-service-section-8-8-4-统一数据服务实现.md` §8.4.2「八个核心设计原则」第 1 条"版本化"；该文件标题写作"8.3 §8.4 统一数据服务实现"、内只有 §8.4.1–§8.4.5，引其版本策略请按 §8.4.2 定位）；Ch4 §07 §8 的版本纪律写作"字段只增不删，废弃字段先标 `deprecated` 并保留两个版本周期，再移除"（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-8-sec8.md` §8）。**两条反例**：只做"加新版本"、忘了废弃旧版本（Ch4 §06 已把它写成反模式）；以及"改了 schema 直接报错、没有兼容期与弃用流程"——后者的后果在 Agent 场景被放大：**字段缺失会让模型反复重试**（`04-data-assetization/06-one-service/06-one-service-section-3-sec3.md` §3.5 反模式表）。

**对内归一化 ≠ 对外契约**（本格与本主题 §4.2（1）那条清单的分界，必须写清）：§4.2（1）的六类必归字段（消息 / 工具 / 流式 / 用量 / 错误 / 控制）是**对内**的——它约束的是你跟厂商的关系，判据是往返测试在必归字段上逐项相等、且能跑在 CI 里（§4.2（3）），**改起来只需要你自己同意**；对外契约约束的是你跟调用方的关系，**改一次要付一次调用方的改造成本**（上面那七条就是这份成本的清单）。两者的关系是：**内部模型是你"表达的"，对外契约是你"承诺的"**——所以对外面通常只暴露内部模型的**一个子集 + 冻结的取值域**：六类里"错误"与"用量"几乎必然进契约（调用方用它们做重试与对账），"控制"类进契约时必须**把取值范围定死**（各家的参数名与上下界不同，是 §4.2（1）已举过的差异点），否则调用方按自己的假设传参，正好落在 §3.2.6 的"参数错配"上；而 §4.1 第 3 步与主文件 §2.3 第 8 条给出的**透传白名单，在对外侧要窄得多**——内部透传是"你自己的应用绕过归一化"，对外透传是"你开放给调用方绕过契约"，后者默认应当禁止。

**失效点**：① **兼容面当原生面用**——对外只有兼容面，调用方已经在往里塞厂商私有参数与私有扩展，统一语义名存实亡（**判据**：数一数请求里有多少个字段是你自己在契约之外加的）；② **两套契约的默认值漂移**——"两者并存"形态下同一个请求在两面得到不同结果（**判据**：同一批请求分别走两面，逐字段比对）；③ **弃用只发通知不改机制**——旧版本没有运行期弃用标记，调用方直到被下线那天才知道。

**判定方法**：三个动作，都不需要采购。**动作一（选形态）**：把调用方按发版周期排一列，加一栏"愿不愿意改客户端代码"——这一栏就是形态选择的依据，而不是偏好。**动作二（存量接入的验收）**：拿一个存量应用，**不改一行 SDK 调用代码**，只改指向（`base_url` 与模型别名，即 §4.4 的第 1 步），跑它的回归集或当日真实流量，要求四条同时成立——响应结构逐项相同、错误码映射相同、流式事件序列相同、用量字段与厂商账单口径可比（§4.2（1）的对账口径）——**并且这一步做完，账能按租户拆开**（§4.4 第 1 步的判据）。**若为了跑通必须改 SDK 代码，那说明"兼容"只是名字像**：要么补适配层，要么承认这是形态 ①。**动作三（废弃窗口）**：抽一个已标弃用的版本，问三句——调用方能不能在**运行期**知道自己在用它、能不能在**机器可读的地方**看到日落条件、弃用期内它有没有被加过能力。三句里有一句答不出来，那个窗口就只存在于文档里。

**真实使用**：兼容面这一形态的可核验锚点都在**"这个形态存在"**这一层，不在契约条目本身——vLLM 的对外服务接口按 OpenAI 兼容形态提供（`12-architecture/03-large-event-readiness/03-large-event-readiness-section-5-ai.md` §5 的"证据与来源"块，原文按【公开】记 release notes）；把"OpenAI 兼容的服务接口"记为事实标准、并据此判接口稳定性成立的，是 Ch9 §01 §5（`09-data-intelligence-product/01-ai-compute/01-ai-compute-section-5-ai.md`）。**"某家接入层的对外契约长什么样"在本主题与全书都核不到可引记录**，因此本节**不给任何厂商的 SDK 细节与版本事实**（那是本主题自定的易腐项，也是本节只写判据不写版本的原因），只给上面的形态与判据；选型面上的入口是本主题 §5.4.1 三条判定点里的第一条"对外是否暴露一套统一的请求 / 响应 / 错误结构"。**废弃流程的具名参照在 Ch7 §03 §8**：资产退役被写成四步（提前通知 → 替代推荐 → 灰度切换 → 观察期归档），并记为 LangChain Hub 的 deprecation flow 与 Stripe API 的版本退役规范（`07-agent-evolution/03-asset-management/03-asset-management-section-8-sec8.md` §8）——**那四步是"退役动作"的清单，本节给的是"写进契约的三条"，两者互补而非替代**。各产品的对外接口与弃用公告，按各自官方文档当前版本核验。【经验：兼容面的收益与两套语义的对齐成本取决于你自己的调用方构成与发版节奏，公开材料给不出"你这里"的占比与周期】（来源：本主题 §3.2.6、§4.2（1）（3）、§4.4、§5.4.1、§6.2、§7.3.4、§7.3.6；`01-modeling/07-graph-reasoning/07-graph-reasoning-section-4-sec4.md`、`12-architecture/03-large-event-readiness/03-large-event-readiness-section-5-ai.md`、`09-data-intelligence-product/01-ai-compute/01-ai-compute-section-4-sec4.md`、`09-data-intelligence-product/01-ai-compute/01-ai-compute-section-5-ai.md`、`04-data-assetization/06-one-service/06-one-service-section-8-8-4-统一数据服务实现.md`、`04-data-assetization/06-one-service/06-one-service-section-3-sec3.md`、`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-8-sec8.md`、`07-agent-evolution/03-asset-management/03-asset-management-section-8-sec8.md`）

### 3.3 模式选择决策表

| 约束组合 | 推荐形态 | 必须同时上的部件 | 不选它的原因（反面） | 关键判据（可核查） |
| --- | --- | --- | --- | --- |
| 单厂商、单应用 | 3.2.1 直连 SDK | 无 | 上网关会引入不必要的一跳 | 半年内是否会换模型（否） |
| 单团队、多应用、同厂商 | 3.2.2 应用内封装 | 统一库 + 版本约束 | 库版本分叉会让行为不一致 | 多应用是否出现过"结果不一致"（是→改服务） |
| 多厂商 + 按租户计费 | 3.2.3 自研网关 | 归一化、能力矩阵、计量、凭证托管、熔断 | 应用内封装无法提供统一记账点 | 账单能否按租户拆开（不能→需要网关） |
| 人手不足但要计费与合规 | 3.2.4 开源网关 + 自建治理面 | 治理代理、回归测试集、升级流程 | 默认限流语义不等于预扣结算 | 配额是否需要"调用前拦截"（是）；回归测试集存不存在（否→先补） |
| 密钥散落、需要轮换 | 3.2.5 凭证托管 | 服务身份 + 出网策略 | 密钥在应用侧无法即时吊销 | 吊销一次密钥需要多久（> 小时→需要托管） |
| 工具由多团队提供 | 3.2.6 工具标准化 | 注册表、Schema、出口、版本号 | 手写工具描述会与治理口径错配 | 模型看到的工具清单是否由注册表生成（否） |
| 端点不可用要求出结果 | 3.2.7 降级链 | 每跳触发条件 + 质量损失估计 + 降级标注 + 恢复条件 | 无降级=一次端点故障就是一次事故 | 端点故障时业务是否可接受"等待"（否） |
| 重复请求占比高 | 3.2.8 缓存（精确优先） | 缓存键含模型与提示版本 + 失效条件 + 禁用清单 | 语义缓存的静默错误复用 | 重复请求占比是否 > 20%【经验】 |
| 调用方多、发版节奏不一致 | 3.2.9 兼容面（②，必要时③兼容面 + 原生面） | 版本标识进响应 + 运行期弃用标记 + 私有参数通道白名单 | 只给自定义契约 = 每个调用方一次改造；两套契约长期对齐 | 调用方里"愿意改客户端代码"的占比（低 → 兼容面） |

### 3.4 组合模式：真实系统不会只用一种

1. **底座组合**：3.2.3（统一网关）+ 3.2.5（凭证托管）——**凭证托管是网关的第一个可交付价值**，也是投入最小的一步（可以先做它，再做归一化）。
2. **分工组合**：3.2.4（开源网关）+ 3.2.3 的治理面——把"跟厂商变化"外包给社区，"钱与合规"留在手里。
3. **韧性组合**：3.2.7（降级链）+ 3.2.8（缓存）——降级的最后一跳常是"返回缓存结果"，两者要有统一的口径（**降级到缓存时也要标注**）。
4. **治理组合**：3.2.6（工具标准化）+ 平台侧的出口（3.2.3 的计量）——工具调用与模型调用共享一套配额与留痕。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 上了降级链但没上质量损失估计 | 降级后不知能不能用，事故期间无法解释结论打了多少折 |
| 上了语义缓存但没做任务类型禁用 | 数值题被错误复用，旧答案静默传播 |
| 上了网关但应用仍持密钥 | 归一化做了、凭证没收，吊销仍要等发布 |
| 上了开源网关但没建回归测试集 | 升级即行为变更，第一次发现是在生产 |
| 降级链只降不升 | 端点恢复后长期停留在降级状态，成本与质量损失无声 |
| 计量只在网关做而工具侧直连 | 模型调用可归因、工具调用不可归因，账只对一半 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **网关只做转发** | 换模型仍要改代码 | 多一跳却没换来收敛 | 先把"能通"当成了目标 |
| **能力矩阵不维护** | 路由把不支持工具的模型分给工具任务 | 运行期报错，且难归因 | 矩阵是文档，容易过期 |
| **密钥进日志** | 故意失败一次，日志里能搜到密钥片段 | 凭证泄漏且无感知 | 日志只考虑排查方便 |
| **按请求数限流而不按 token** | 一个大请求打满配额 | 配额口径与实际消耗不成比例 | 复用了 API 网关的实现，没改计量单位 |
| **跨端点自动重试** | 同一逻辑请求在两家端点都执行 | 成本翻倍，结果不可比 | 把"重试"当成通用容错 |
| **降级不标注** | 复盘时无法区分正常与降级结论 | 决策依据不可追溯 | 降级被当成内部实现细节 |
| **语义缓存无禁用清单** | 数值/时间类问题出现旧答案 | 静默错误传播 | 缓存命中率好看，没人查正确性 |
| **计量事后统计** | 超发在观测之后被发现 | 配额无约束力 | 事前预扣要写流水，工作量大 |
| **工具 Schema 与实现不同步** | 模型按 Schema 传参被实现拒绝 | 工具调用成功率下降，且原因难定位 | 缺少 CI 冒烟 |
| **库版本分叉** | 同一个问题在不同应用得到不同结果 | 行为不一致，且归因到"模型不稳定" | 库是代码不是服务，版本约束无人守 |
| **提示不跟档位版本化** | 降级后质量断崖，或大模型上表现平庸 | 提示与材质的耦合被忽略 | 一套提示走天下看起来更省事 |
| **能力矩阵无更新触发条件** | 厂商发了新条目而矩阵半年未动 | 路由决策基于过期信息 | 只指定了负责人，没指定"什么时候动" |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 直连 SDK → 应用内封装 | 同一段调用代码被抄第三遍 | 3.2.2 | 一次统一改造，风险低 |
| 应用内封装 → 统一网关 | 多应用行为不一致；账单拆不开【经验：三个以上应用或两个以上厂商是常见触发点】 | 3.2.3 / 3.2.4 | 各应用改指向网关；密钥上收；补计量流水 |
| 无降级 → 有降级链 | 一次端点限流就影响业务【经验：端点可用性波动在月度尺度上几乎必然发生】 | 3.2.7 | 每跳准备评测证据；降级标注进留痕；每跳的提示版本化 |
| 无缓存 → 精确缓存 → 语义缓存 | 成本随重复请求线性上涨 | 3.2.8 | 缓存键设计与失效条件；语义缓存要建禁用清单 |
| 单租户 → 多租户计费 | 账单只有一个总额 | 3.2.3 的计量 + 平台配额 | 记账字段补齐；历史数据无法追溯（**只能从上线日起算**） |
| 自研网关 → 开源网关 + 治理面 | 归一化层的排期积压持续增长 | 3.2.4 | **先建回归测试集**，再迁移路由；治理面旁挂或前置 |
| 请求数限流 → token 计量 | 大请求打满配额而小请求额度闲置 | 3.2.3 的计量口径 | 需要"预估 token 上限"的能力（与预扣同一套机制） |

**一条通用判据**：**跃迁的触发点不是"厂商数变多"，而是"某个失效形态第一次出现"**——第一次出现"两个应用结果不一致"就该统一口径；第一次出现"账单拆不开"就该上计量；第一次出现"端点故障影响业务"就该上降级。**按厂商数量预设跃迁点，几乎一定过早或过晚**（两家厂商但零计费要求时，网关的收益可能不抵它的运维面）。

### 3.7 自检清单

- [ ] 换一个模型档位，需要改代码吗？改几处？（目标：0 处，只改配置）
- [ ] 归一化覆盖了哪些字段？**流式增量、工具调用增量、用量字段**是否都在内？
- [ ] 归一化层的维护成本量过吗（厂商数 × 差异点）？支持第 N 家厂商的成本是否高于第 N−1 家？
- [ ] 能力矩阵存在吗？每条能力能否指向可核验的文档条目？**更新触发条件写下来了吗**？最近一次更新是什么时候？
- [ ] 密钥存在几个地方？能否在一处轮换并即时吊销？日志里会不会出现密钥片段？
- [ ] 计量记在调用**前**还是调用后？是否有预扣与结算两笔流水？
- [ ] 记账字段是否包含 `tenant / app / session / endpoint / model_version / cache_hit`？缺哪一项？
- [ ] 重试是否区分了可重试与不可重试？是否允许跨端点重试（默认应禁止）？
- [ ] 降级链有几跳？每跳的质量损失量过没有？降级事件是否标注进留痕？**有没有恢复条件**？
- [ ] 降级链的每一跳有自己的提示版本吗？还是全套共用一份提示？
- [ ] 缓存键包含模型版本与提示版本吗？失效条件写下来了吗？语义缓存有禁用清单吗（数值 / 时间 / 身份相关是否在内）？
- [ ] 工具描述是由注册表生成的吗？Schema 与实现有 CI 冒烟吗？
- [ ] 出网策略与租户分级对齐了吗？哪些租户的数据不允许发往外部端点？
- [ ] 网关自身是多副本吗？它的容量（QPS 与连接数）量过没有？
- [ ] 各应用锁定的接入库版本有几个？是否存在超过一个季度未升级的分叉？
- [ ] 用开源网关的话，回归测试集覆盖了多少厂商 × 能力组合？
- [ ] 对外契约是自定义契约、兼容面，还是两者并存？依据是调用方里"愿意改客户端代码"的占比，还是偏好？**并存的话，哪个是主契约？**
- [ ] 契约变更怎么被调用方发现？响应里有版本标识、有**运行期**的弃用标记吗？废弃窗口的长度是按"最慢调用方的发版周期"定的，还是拍了一个天数？
- [ ] 反向验一次：抽一个存量应用**不改一行 SDK 调用代码**、只改指向，能不能跑通？**若必须改，那是"兼容"还是"名字像"？**

### 3.8 小结

> 本节小结：接入层形态由五条约束按序决定——**厂商数量与变更频率 → 数据能否出域 → 是否按租户计费 → 可用性目标 → 团队承接能力**；九种模式里，**凭证托管（3.2.5）是投入最小、收益最先显现的一步**，**统一网关（3.2.3 / 3.2.4）是收敛四件事的唯一位置**，而**降级链与缓存（3.2.7 / 3.2.8）是两件"收益明显但必须带失效条件"的加法**；**对外契约形态（3.2.9）是唯一一格"往外看"的**——前八格回答"这一层怎么建"，它回答"建好之后对调用方承诺什么"，选哪种形态不取决于技术偏好，而取决于**调用方里"愿意改客户端代码"的占比**（同一个占比也决定了你的契约变更会不会出现在调用方的发版计划里）。判断这一层有没有真正建起来，只看两条：**换模型是否不改代码**；**账单是否能按租户拆开**。至于"要不要独立一层"，判据不在厂商数量，而在**"不一致"这个失效形态有没有出现过**。

> 💡 **思考锚点**：拿你最近一个月的一个高频请求类型，回答三个数：它的重复率有多高、它是否带数值或时间条件、它的单次成本量级是多少。第一个数决定该不该上缓存，第二个数决定**能不能**上语义缓存，第三个数决定这件事的收益上限——三个数里若有一个你答不上来，那正是你下一步该补的计量字段。
