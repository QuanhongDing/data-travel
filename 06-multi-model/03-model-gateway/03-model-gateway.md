## 1. 概念与定位

### 1.1 是什么

**学术 / 工业定义**：多模型统一网关（Model Gateway）是**在应用与模型端点之间插入的一层**，把"多厂商、多协议、多计费口径"的差异收敛成**一套接口**。它通常提供五类能力：**归一化**（请求 / 响应 / 流式 / 错误码 / 能力字段）、**路由**（按成本、质量、合规、可用性选端点）、**凭证与出网**（密钥托管、出网策略）、**计量与配额**（token 与调用记账、预扣）、**韧性**（超时、重试、熔断、降级链）。

**工程定义**：在数据架构师手里，多模型网关是**一次把"换模型不改代码"变成工程事实**的工作——**判据是**：把一个应用从 A 模型切到 B 模型，需要改的代码行数是不是 0（或只改配置）。

**统一网关 vs API 网关 vs 应用内封装**（这是最常被混的三件事）：

| 维度 | API 网关 | 应用内封装（SDK / 工具函数） | 多模型统一网关 |
| --- | --- | --- | --- |
| 面向 | 南北向流量（外部→内部） | 单个应用自己的调用 | 内部应用→模型端点 |
| 治理对象 | 路由、鉴权、限流、审计 | 无（每个应用各写一遍） | 归一化、路由、计量、降级 |
| 计量单位 | 请求数 / 流量 | 无法归因 | **token × 单价，可归因到租户 / 应用** |
| 换了模型要做什么 | 无关 | 改每个应用的代码 | 改路由配置 |
| 典型失效 | 配错路由 | 各应用行为不一致 | 单点：网关自身不可用 |

**一句话判断**：**「不能在不改代码的前提下换模型」= 还没有统一接入层。**

### 1.2 为什么需要

统一接入层是被**五件事**逼出来的，每一件都无法靠"应用里写得好一点"解决：

1. **厂商差异**：请求字段、流式协议、工具调用格式、错误码、用量字段、能力支持（多模态 / 工具 / 长上下文）**各家不同**，且随时间变化。应用直连意味着每个应用都维护一套适配代码。
2. **凭证**：密钥放应用里是**问不出"谁在用"**的；托管在网关才能做轮换、吊销与审计。
3. **计量**：没有统一记账点，账单只能看总额——这与 [Ch11 §03 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md) 的"成本必须归属"直接冲突。
4. **韧性**：模型端点会限流、会超时、会不可用。降级链（大模型 → 中模型 → 小模型 → 规则）只能在一层里实现，写在每个应用里就等于没有降级。
5. **变更**：模型档位与版本迭代很快；没有网关，"换一档试试"这件事要发一次版。

### 1.3 在 AI 时代数据架构中的位置

```
   [Agent 平台 / 数据应用 / 报表助手]      ← Ch5、Ch9
                ↓ 一套接口（归一化后）
   [多模型统一网关 · 本文]
        ↓            ↓             ↓
   [自托管推理]   [厂商端点 A]   [厂商端点 B]
    (vLLM 类)      (合规出域?)     (按量计费)
                ↓
   [工具协议层：工具 / 资源 / 提示]  ← 由平台侧统一出口治理
```

- **上游**：Ch5 Agent 平台（网关是平台的依赖：平台传租户与版本标签，网关负责归一化与计量）。
- **下游**：Ch4 数据资产化（RAG 的生成侧也走这一层）、Ch9 数据智能产品（产品里的模型调用同理）。
- **横向**：Ch8 AI 治理（出域合规与审计）、Ch11 成本与可观测、Ch12 高可用（多活与容量）。

### 1.4 演进历程

- **直连 SDK 阶段（2022–2023）**：每个应用各自 `import` 厂商 SDK；换模型 = 改代码；密钥散落。
- **应用内封装阶段（2023）**：抽出内部工具函数统一下调用；**解决了"少写重复代码"，没解决"行为一致、计量、降级"**——因为封装在每个应用里各存一份。
- **独立网关阶段（2023–2024）**：出现以配置为中心的接入层（开源网关一类），把多厂商端点、路由与重试做成配置项；这一阶段的主要成果是**"换模型不改代码"**。
- **平台化阶段（2024–2025）**：网关与 Agent 平台 / 治理面接起来——配额从出口扣、成本按租户归、灰度按会话分流；工具调用也从"各家自有格式"转向**协议化接入**（工具 / 资源 / 提示的标准化，规范与实现可按规范当前版本核验【公开】）。

> 主线：**能力从"应用里的函数"上收到"一层"，再从"一层"上收到"一套协议"。**

## 2. 核心原理

### 2.1 关键概念定义

- **归一化层（Normalization）**：把各厂商的请求 / 响应结构映射到统一模型的动作。**归一化的边界要写清楚**：哪些字段是"必归"（消息、工具、流式增量、用量），哪些是"透传"（厂商私有参数）。
- **能力矩阵（Capability Matrix）**：模型 × 能力（流式 / 工具调用 / 并行工具 / 多模态 / 结构化输出 / 长上下文 / 缓存）的表格。它是**路由的前置数据**，也必须随厂商更新维护。
- **凭证托管（Credential Vault）**：密钥不落在应用代码与配置里，由网关持有并支持轮换与吊销。
- **路由策略（Routing Policy）**：决定"这次请求发给谁"的规则，输入可以是任务类型、租户、档位、成本预算、可用性。
- **降级链（Fallback Chain）**：端点不可用或质量不达标时按顺序退到下一档；**每条链都要带"质量损失"的估计**（否则降级后没人知道结果能不能用）。
- **计量（Metering）**：按 `input/output tokens × 单价` 记账，并打上租户 / 应用 / 会话标签；**预扣后结算**是唯一能防超发的形态。
- **流式归一（Stream Normalization）**：把各家的流式分片（增量文本、工具调用增量、结束原因）映射成统一事件序列——**这是归一化里最容易漏的一块**。
- **影子对比（Shadow / A-B）**：同一请求并行发给两个端点，比较质量与成本；用于换档前的证据收集。
- **出网策略（Egress Policy）**：哪些租户 / 哪类数据可以发往外部端点（与 [Ch8 治理](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md) 的分级保密对接）。

### 2.2 数学 / 形式化基础

**归一化是一个映射**：设厂商 v 的请求空间为 `R_v`、统一请求空间为 `R`，归一化就是 `f_v: R → R_v` 与逆映射 `g_v: R_v → R`。**归一化的正确性判据**（可写成测试）：对任一统一请求 `r`，`g_v(f_v(r))` 与 `r` 在"必归字段"上必须逐项相等——**这一条可以在 CI 里自动跑**，且它比"人工看一遍"可靠得多。

**路由决策**：把路由写成一个函数

```
endpoint* = argmax_{e ∈ E} [ w_q · Q(e, task) − w_c · C(e, tokens) − w_r · Risk(e, tenant) ]
约束：Cap(e) ⊇ Need(task)   且   Egress(e, tenant) = allow
```

- `Q` 是质量估计（可用离线评测集给出，**没有评测集时只能给档位排序，不能给分**）；
- `C` 是成本（tokens × 单价）；
- `Risk` 是合规风险（出域、跨境、租户策略）；
- 约束是**硬条件**：能力不满足或出网不允许的端点直接出局——**不要把它变成权重**（这与 §7.1 的"门槛不是权重"同一条理）。

**成本模型（网关本身也在成本函数里）**：

```
月成本 = Σ_端点 (tokens × 单价) + 缓存带来的节省 − 网关自身成本
网关自身成本 = 实例数 × 单实例月成本 + 日志/计量存储 + 运维人力
节省项 = 命中缓存的请求数 × 平均单请求成本 × 缓存命中质量折损系数
```

**一条可自测的判据**：**缓存命中率如果长期低于 20%【经验，随任务形态浮动】，语义缓存带来的质量折损与复杂度不划算**——此时先做"精确缓存"（同请求同参数）而不是语义缓存。

**降级链的质量损失**：设 `q_0` 是主端点在你的评测集上的得分、`q_i` 是第 i 档的得分，则降级后的损失是 `Δq_i = q_0 − q_i`。**必须事先量出来**，否则降级发生时没人能判断"要不要人工兜底"。

**代入一组数看两个关键判据怎么用**：

```text
【预扣倍率】记 prompt = 1k tokens，max_output_tokens 配 2k，实测 completion P99 = 200
  预扣 = 1k + 2k = 3k      实际 = 1k + 0.2k = 1.2k
  → 预扣倍率 = 3 / 1.2 = 2.5 倍【推算：口径为"预扣上限 ÷ 实际均值"】
  → 推论：同一份预算能支撑的在途并发请求数，被这个倍率直接腰斩
  → 动作：把 max_output_tokens 收到实测 P99 的 1.2–1.5 倍（仍是保守的）

【缓存盈亏平衡】设重复请求占比 p、命中率 h、质量折损系数 k_loss
  收益 = p × h × 单请求成本 − 缓存查询成本
  若精确缓存 h ≈ p（键相同才命中），语义缓存 h 更高但 k_loss > 0
  → 判据：当 p < 20%【经验】时，语义缓存的复杂度与折损不划算，先做精确缓存
  → 另一条硬约束：缓存键必须含身份维度（租户 / 权限），否则跨租户复用 = 数据泄漏
```

**这两条式子的共同点**：它们都把"感觉该做"变成"算得出来"——**预扣倍率决定预算能不能用满，缓存盈亏平衡决定缓存值不值得做**。两者都不依赖对模型能力的任何判断，因此可以先于选型完成。

### 2.3 关键算法 / 方法

1. **能力探测与维护**：以厂商文档的"功能条目"为唯一依据建立能力矩阵（**不靠试**）；矩阵变更走一次评审（因为路由依赖它）。**判据**：任一模型的能力行，都能指向一条可核验的文档条目。
2. **路由**：规则优先（任务类型 → 档位 → 端点），成本与质量作为同档内的排序依据；**实时按请求特征判定**属于进阶形态，先有规则再谈。判据：路由配置改动是否需要发版（不需要才算配置化）。
3. **缓存**：① **精确缓存**（请求原文 + 参数哈希）——安全但命中低；② **语义缓存**（相近问题复用答案）——命中高但有**错误复用风险**（相似≠相同，尤其涉及数值与时间条件）。语义缓存必须"带条件"（例如只对"解释性问答"启用，对"取数类"禁用）。
4. **超时与重试语义**：区分**可重试**（限流、连接失败、5xx）与**不可重试**（内容策略拒绝、参数非法）；重试必须带**幂等键**（网关层的重试会让同一逻辑请求到达两次）。**默认不要跨端点自动重试**（换端点的结果不可比），除非业务显式允许。
5. **熔断与半开**：连续失败率越线即熔断该端点，**定期半开探测**恢复；熔断粒度按端点而不是按厂商（同厂商不同区域/配额域的表现不同）。
6. **灰度与影子**：按租户 / 会话比例分流；换档前先影子对比（同请求双发），收集质量与成本的差值证据。
7. **成本归因**：记账字段至少 `tenant / app / session / endpoint / model_version / tokens_in / tokens_out / cache_hit`；**缺任一项，事后都无法回答"钱花在哪"**。
8. **归一化字段映射的生成与校验**：映射不是手写文档，而是**可执行的往返测试**。设厂商 v 的请求空间为 `R_v`、统一空间为 `R`，归一化是 `f_v: R → R_v`（出向）、逆映射是 `g_v: R_v → R`（入向）；**必归字段上的恒等性 `g_v(f_v(r)) ≡ r` 就是它的正确性判据**，可以在 CI 里按字段逐项比较。**两条构造要求**：① 必归字段清单要**先定后写实现**（清单是判据，实现是细节，顺序反了就会出现"实现到哪算哪"的字段集）；② 未进清单的字段必须有**透传白名单**通道，否则某个应用会用"绕过归一化"的方式传私有参数，而那条通路不受任何校验。**判据**：给一次厂商接口变更，能否在 CI 里一次跑出"哪些字段受影响"。

### 2.4 与相邻概念的关系

- **多模型网关 vs API 网关**：API 网关治理南北向流量（鉴权 / 限流 / 路由到服务）；多模型网关治理**到模型端点的调用**（归一化 / 计量 / 降级）。两者可复用同一套限流实现，但**治理对象的单位不同**（前者是请求，后者是 token）。
- **多模型网关 vs Agent 平台**：平台管"谁在跑、状态在哪、谁批准、额度多少"；网关管"这次请求怎么发出去、算多少钱、坏了怎么办"（详见 [Ch5 §02 平台架构](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture.md) 的接口表）。**网关是平台的依赖，不是平台的替代。**
- **多模型网关 vs 自托管推理服务**：自托管推理（vLLM 一类）解决"模型跑在你自己的 GPU 上"；网关解决"在多个可选项之间怎么选、怎么记账"。自托管端点在网关眼里**就是一个端点**。
- **多模型网关 vs 编排框架**：编排框架决定"多步怎么走、什么时候调模型"；网关决定"这一步的模型调用发给谁"。**把路由写在编排里（例如按节点硬编码模型名）是常见的耦合**——换档要改编排。
- **多模型网关 vs 检索层**：检索（[Ch4](../../04-data-assetization/README.md)）决定"给模型什么上下文"；网关决定"这些上下文交给哪个模型、花多少钱"。语义缓存与检索缓存的**失效条件不同**（前者随模型版本、后者随语料版本）。

> 💡 **思考锚点**：把你最近一次"换模型"的操作回想一遍——改了多少个文件、发了多少次版、回滚用了多久？再回答一个问题：你的密钥现在存在几个地方？这两个答案决定你该先做归一化，还是先做凭证托管——你打算先动哪一个？
