## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研 / 开源 / 云厂商"打分有三个结构性问题：① 同一列在不同处境下方向相反（"可控性"对合规团队是必需、对两个人的团队是负担）；② 打分表隐含"这些选项互斥"，而真实形态常是组合（开源网关 + 自建治理面）；③ 最关键的判据（能否出域、是否需要按租户计费）**不是可打分的维度，而是门槛**——不满足直接出局。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 数据能否出域 | 哪些租户 / 哪类数据可发往外部端点？ | 不能出域 → 必须存在自托管端点，且出网判定要进路由硬约束（**门槛不是权重**） |
| 计量归属 | 记账点由谁实现、在调用前还是调用后？ | 要按租户结算 → 记账点必须自己掌握且在调用前 |
| 归一化维护 | 谁跟厂商接口变化？ | 这是**持续成本**，交给社区还是自己扛，决定长期人力 |
| 凭证与出网 | 密钥归谁、能否强制白名单？ | 合规与审计的落点；密钥散落则轮换与吊销永远做不干净 |
| 韧性与降级 | 端点故障时能否出结果、降级能否被标注？ | 决定业务 SLA 与复盘能力 |
| 团队承接能力 | 有没有人能长期维护归一化、能力矩阵与计量？ | 这一层的真实成本是长期人力，不是首版实现 |

> **读法**：先用第 1 条筛掉不可行；再用第 2、4 条筛掉"钱与合规不在自己手里"的方案；最后用第 3、5、6 条在剩下的里选——**第 6 条最容易被跳过，也最容易在第二年变成技术债**。

**还有一条隐藏得更深的缺陷：这六行问的不都是候选方案**——第 1 行（数据能不能出域）与第 6 行（有没有人能长期维护）问的就是你自己，第 2、4 行的答案也由你的要求定（要不要按租户结算、密钥能不能强制托管），真正要拿到候选之间去比的是第 3、5 行。约束决定候选的上界，属性只在候选之间分配名次——"可控性"对合规团队是必需、对两个人的团队是负担，同一列在不同处境下方向相反（这正是开头第 ① 条结构性问题的机制成因）。所以本节的第一张表不是方案评分表，而是一组**能淘汰候选**的判据。

**六条的答案形态也是两类，不能混在一张表里**：第 1、2、4 条的答案是"是 / 否"（能否出域、是否要按租户结算、密钥能否强制托管），它们是门槛；第 3、5、6 条的答案是"多贵 / 多久"（归一化维护要多少人、降级链要多少评测工作、有没有人能长期接手），它们是成本。**把两类答案压进同一张打分表，等于用"分数低"掩盖了"不满足"**——而"不满足"的那一条，正是 §7.7 里迁移代价最贵、甚至不可逆的那一格。

**关于排序**：本节照样给顺序，但每一行的先后都要落在一个**可判定的位置**上——§7.6 的"不选它的原因"列几乎每行都写的是机制（记账在调用前还是调用后、出网粒度到不到租户级、计量单位是请求还是 token），只有"上网关是治理过剩"那一行是权衡；§7.8 的"关键理由（机制层面）"列同理。本主题对这一条要卡得比别处更死：机制理由最终都得回答同一个问题——**判定点是不是在你唯一的出口上**；出网判定、记账点、归一化这三件里只要有一件的判定点落在你的链路之外，那一行剩下的唯一理由就是"它做不到"，先后也就排不动了（§7.8 第 3、4 行的理由正是前两件）。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 应用内封装（库） | 少写重复代码 | 抽出内部工具函数库，各应用依赖 | 单团队、单厂商 | 库版本分叉；无统一计量；密钥仍在应用侧 |
| 自研统一网关 | 一层收口 | 归一化、路由、凭证、计量、韧性五块自研 | 有平台团队、合规要求强 | 长期人力；归一化要持续跟厂商变化 |
| 开源网关直用 | 配置化接入 | 以配置为中心的接入层（LiteLLM / One-API 一类） | 想快速拿到归一化与路由 | 计量与配额语义按社区默认；升级改变行为 |
| 开源网关 + 自建治理面 | 分工 | 归一化用开源，计量 / 配额 / 审计 / 出网自建 | 人手有限但钱与合规要自己掌握 | 两跳链路；升级需回归测试集 |
| 云厂商模型接入层 | 托管接入 | 厂商提供端点接入与用量统计 | 数据可出域、追求最快上线 | 口径与出网策略按厂商；跨厂商能力受产品限制 |
| 通用 API 网关改造 | 复用既有设施 | 在 API 网关上补模型调用与计量插件 | 已有成熟 API 网关的团队 | **限流单位与计量对象不同**（请求 vs token） |
| 平台内置接入层 | 平台自带 | Agent 平台自带的模型接入与用量统计 | 已选平台且不想多一层 | 与平台绑定；跨平台复用性差 |

**这七个候选其实分三族**：**自建族**（应用内封装、自研统一网关）——归一化与计量都在自己手里，代价是长期人力；**开源族**（开源网关直用、开源网关 + 自建治理面）——把"跟厂商变化"外包给社区，代价是升级管理与回归成本；**平台 / 云族**（云厂商接入层、通用 API 网关改造、平台内置接入层）——拿到成品能力，代价是口径与边界由别人定。

**族内可替换，跨族不可换**：自建族与开源族之间换，动的是归一化的实现位置；从这两族换到平台 / 云族，等于**把计量与出网口径交给别人**——那不是技术迁移，是治理决策。

**"跨族不可换"要拆成三个决定才用得上**：① 记账点的位置（谁能在调用前扣减），② 出网判定的位置（谁能在唯一出口上拒绝），③ 归一化的归属（谁跟厂商接口变化）。三件事里**只有第 ③ 件能靠迁移解决**——前两件一旦交出去，收回时要重建口径，而重建口径时历史用量只以对方的报表粒度存在（§7.7 的硬结论）。所以"族内可换"的准确含义是：换的是实现，不换的是这三件的归属；"跨族不可换"的准确含义是：换族必然要动前两件的归属，而其中一件（记账点）动了就丢历史。

**表里"典型使用者"一栏不点名，是因为多数候选在本主题与全书里都没有可指名的实现**——可具名的位置集中在接口侧与规范侧的几处：开源族在 §4.3 的工具链表里写作"以配置为中心的接入层（LiteLLM / One-API 一类）"，这条口径在本主题 §3.2.4、§4.3、§6.2 与本节四处一致；工具侧由标准化接入规范承载（由 Anthropic 于 2024 年公开，规范与实现可按规范当前版本核验【公开】；§3.2.6 / §4.5 / §5.2 / §6.3 四处同一口径）；观测侧由 OpenTelemetry 语义约定承载（§4.3）。**其余五行——应用内封装、自研统一网关、云厂商模型接入层、通用 API 网关改造、平台内置接入层——本节不给具名产品**，理由见 §5.2 的结论：接入层的生产细节（归一化边界、缓存正确性、路由质量）本来就是内部信息，公开材料几乎全是建设方自述。要核验一个候选"有没有人在生产里用"，可核验的入口不是产品名，而是**它的接口或规范是否公开、是否有版本化的文档条目**——这正是 §5.2 三条判据里的第 ① 条。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 归一化的位置：应用内、一层里，还是别人的产品里

**机制是什么**：归一化只有三个位置——应用内（每应用一份）、独立一层（一份）、厂商产品内（不在你手里）。

**它在各候选中的实现差异**：自建族的两者都在"你的一层里"（库是代码形态的一层，网关是服务形态的一层），区别是**能否持有全局状态**（计量与降级需要全局状态，库做不到）；开源族在"你的一层里"，但实现来自社区；平台 / 云族在"别人的一层里"。

**实现差异（定性）**：

| 候选族 | 归一化落在哪 | 谁决定字段语义 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建族（应用内封装） | 各应用各一份（库形态的一层） | 每个应用的开发者 | 同一字段在两个应用上的默认值不同，行为分叉且无人能归因 |
| 自建族（自研统一网关） | 你自己的一层（服务形态的一层） | 你的平台团队 | 归一化成为排障必经之地；厂商新增字段无人补，边界被逐次侵蚀 |
| 开源族 | 你的一层里，但实现来自社区 | 项目维护者与你的配置 | 实现随版本演进改了行为，而你的应用先在线上发现 |
| 通用 API 网关改造 | 复用既有网关上补的一层 | 你的网关团队 | 补的是转发与限流，字段语义仍留在各应用里 |
| 平台 / 云族 | 别人的产品里 | 厂商 | 厂商不支持的能力只能等；粒度与必归清单不匹配时没有接口可改 |

**由此必然导出的性质**：因为**计量与降级需要全局状态**，所以"库形态的一层"**原理上无法承担这两件事**——这解释了为什么应用内封装永远停在"少写重复代码"，而不会自然长成网关。

**公开证据**：这一层的实现形态在本主题有可核验的书面口径——§4.1 步 3 把"必归字段清单 + 透传字段清单"并列为一次交付、主文件 §2.3 第 8 条给出"清单先定后写实现"与透传白名单的构造要求，§4.2（1）给出前一份里的六类字段，§4.2（3）给出可进 CI 的往返测试代码，§4.5 模板 1 给出统一请求的字段集；开源侧的载体在 §4.3 写作"以配置为中心的接入层（LiteLLM / One-API 一类）"（同一口径见 §3.2.4 与 §6.2 的案例标题）【公开】（来源：本主题主文件 §2.3、§4.1、§4.2、§4.3、§4.5）。**"库形态的一层在生产里长不成网关"这一条，本主题与全书都核不到第三方生产案例**——§5.2 把归一化判为 L2，理由是判据①③成立、②不成立（第三方非厂商生产案例核不到）【经验】（来源：本主题 §5.2 判据表与 §5.3.1）。要自己判一次，可执行的动作是：数一次换档或加厂商改动了哪些文件——改动落在三个以上应用的调用代码里，就还停在库形态。

**失效条件**：当合规或结算要求出现时，"库形态"必须被替换（不是升级）——这是它与其它候选的关键差别。

#### 7.3.2 记账点：调用前、调用后，还是别人的报表里

**机制是什么**：记账点决定配额是"约束"还是"报表"。

**它在各候选中的实现差异**：自建族可在调用前预扣；开源族要看网关是否暴露调用前钩子（多数只给限流，不给预扣结算语义）；平台 / 云族的记账点在你的链路之外，你只能读它的报表（**口径与粒度由它定**）。

**实现差异（定性）**：

| 候选族 | 记账点在哪 | 配额是约束还是报表 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建族（自研统一网关） | 你的出口上，调用前可预扣 | 约束 | 记账点被做了两处，两个口径对不上；晚做会丢历史 |
| 开源族（直用） | 网关的用量记录里，多在调用之后 | 报表 | 限流一直在生效，账单照样穿透预算 |
| 开源族（+ 自建治理面） | 你的治理面里，可加调用前钩子 | 约束 | 治理面旁挂在链路上，绕过它的调用不被记账 |
| 平台 / 云族 | 在你的链路之外 | 报表 | 粒度与租户 / 会话不匹配，拆不到责任主体 |

**由此必然导出的性质**：因为**观测点晚于超发点**，所以任何"读别人报表"的方案都不能防止超发——它的语义是"事后知道"，不是"事前约束"。

**这条性质还有一个工程上的推论：记账点只能有一个**。两个记账点（例如"平台侧配额"与"网关侧流水"各记一份）在数字不一致时，**没有任何一方能自称权威**——它们各自都是按自己的口径算的，而差异本身又归因不到某一笔调用上。§4.1 把"建计量记账点"排在第 4 步、把判据写成"任意一天的账单能否按租户拆开"，实质是在要求**唯一性**：不是"有记账"，而是"只有一处记账"。这个判据可以当场执行：任取一天的用量，让两套系统各算一次，看差异能不能逐笔对上。

**公开证据**：这一条在本主题有可核验的判据形态而不是产品形态——主文件 §2.1 的计量条把"预扣后结算"写成唯一能防超发的形态，§4.2（6）给出可照抄的两笔流水（`reserve` / `settle` 按 `request_id` 配对），§4.6 的成本表把"网关自身成本"与"归一化维护"分开记【公开】（来源：本主题主文件 §2.1、§4.2（6）、§4.6）。**"某家开源接入层的默认配额语义是限流而不是预扣"这一条，本节给不出具名文档条目**，只给可自测的判定：拿它的配额配置按"调用前预扣、调用后结算"跑一遍，跑不通就说明治理面必须自建【经验】（来源：本主题 §3.2.4 的准入条件与 §6.2 的失败教训——"配额交给社区默认实现"是那一节的教训句）。

**失效条件**：当业务方要求"额度用完即拒绝"时，只有调用前记账的方案能满足；否则需求本身要改。

#### 7.3.3 出网判定：路由的硬约束，还是应用的自觉

**机制是什么**：合规要求能否被**强制执行**，取决于判定点是否在你唯一的出口上。

**它在各候选中的实现差异**：自建族与开源族（+ 自建治理面）可在出口判定；开源网关直用要看它是否支持按租户的出网策略；平台 / 云族的出网由厂商定义（可能只有"是否允许使用外部端点"这一粒度）。

**实现差异（定性）**：

| 候选族 | 判定点在哪 | 能否强制执行 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建族 / 开源族（+ 治理面） | 唯一出口上，进路由的硬约束 | 能（失败必须失败） | 存在"应用可直连外部端点"的旁路，策略退化成自觉 |
| 开源族（直用） | 网关的出网策略配置里 | 取决于它支持的粒度 | 粒度只到"是否允许外部端点"，到不了租户与地域 |
| 通用 API 网关改造 | 既有网关的策略里 | 能，但端点分类要重做 | 复用了请求数口径，端点分类里没有地域与托管形态维度 |
| 平台 / 云族 | 厂商的产品里 | 由厂商定义 | 只有"允许 / 不允许"一档，举证材料只能是它的报表 |

**由此必然导出的性质**：因为**策略没有强制执行点就只能是自觉**，所以"应用侧不传敏感内容"这种实现不能算合规控制项——审计时也无法举证。

**为什么"演练"是这一条唯一的硬证据**：策略配得对不对，读配置看不出来——出网规则里的租户分类、端点分类、默认拒绝这三件事任何一处写错，都会让策略"看起来生效"而实际放行。而**一次成功被拒的演练同时证明三件事**：判定点在链路上（请求真的经过了它）、策略在生效（它真的拒绝了）、拒绝是可复现的（别人再跑一次还是拒绝）。这也是 §4.7 把"出网策略误配"列为六类故障演练之一的原因——它的失效形态是**放行**，而放行不产生任何告警。

**公开证据**：这一条在本主题有可核验的配置形态：§4.2（4）的 `egress: {default: deny, rules: [...]}` 与 `log_scrub` 给出白名单制与脱敏前置的写法，"出网策略失败必须失败"这条纪律写在 §4.7 演练表之后（与"计量失败不得导致业务失败"方向相反，两者要分开设计）；平台侧的同一接口在 Ch5 §02 §4.2 写作 `egress: gateway`（唯一出口的标识，缺这一项的工具不允许注册）【公开】（来源：本主题 §4.2（4）、§4.7；Ch5 §02 §4.2）。**分区合规的那组出网证据（拒绝日志 + 端点分布 + 一次演练）本主题给不出第三方生产案例**——§6.4 的案例是匿名的，只作机制示例、不作举证，且它给出的"受监管租户端点分布应落在自托管"是目标值而不是实测值【经验】（来源：本主题 §6.4 的材料纪律与 §5.2 分级表首行（"统一接入层的归一化"，L2）判据②核不到）。

**失效条件**：当审计方要求"证明受监管数据未出域"时，只有"出口强制 + 拒绝日志 + 演练记录"这一组动作能作为证据。

#### 7.3.4 升级面：谁能改变你的行为

**机制是什么**：这一层的软件升级会不会改变行为。**更准确的说法是**：行为变更的时点，与你自己发版的时点，是不是同一个时点——对齐，变更就在你的节奏里；解耦，变更就在别人的节奏里。

**它在各候选中的实现差异**：自建族的行为由你控制（但厂商接口变化会间接改变行为）；开源族**升级即潜在行为变更**（归一化实现随版本演进）；平台 / 云族的行为变更由厂商发布节奏决定（**你可能没有选择权**）。

**实现差异（定性）**：

| 候选族 | 行为由谁改 | 变化什么时候可见 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建族 | 你的团队（厂商侧变化会间接改变行为） | 你发版时 | 厂商改了默认值或新增字段，你的回归测试没覆盖到那一格 |
| 开源族 | 项目维护者 + 你的配置 | 你执行升级的那一刻 | "升级"的理由通常与行为无关（修缺陷、跟新端点），行为变更是附带后果，不进变更评审 |
| 通用 API 网关改造 | 网关插件的版本 | 插件升级时 | 策略语义随插件版本变化，而你的应用不知道 |
| 平台 / 云族 | 厂商的发布节奏 | 厂商通知你时（也可能不通知） | 行为变更没有选择权，只能被动适配 |

**由此必然导出的性质**：因为**归一化的行为变化难以从表面看出**，所以任何依赖他人归一化的方案都必须自建**回归测试集**——没有它，"升级"就是一次不可控上线。

这条性质还有一层更适合拿去做判断的表述：**升级面的实质是"行为变更是否出现在变更评审的议题里"**。自建族里它会（你改代码时躲不掉），开源族里它常常不会（升级的动机是修缺陷），平台 / 云族里它根本不经过你。**一条不需要外部材料的观测量**：把"最近一年这一层的行为发生变化的次数"与"你自己主动发版的次数"比一比——比值接近 1，说明你控制着升级节奏；明显大于 1，说明大部分行为变更不是你发起的，而你的回归测试集大概率没有覆盖它们。

**公开证据**：本主题把这一条的落地动作写成了可核验的准入条件与夹具——§3.2.4 把"有回归测试集"定为采用开源网关的前置条件，§4.3 的夹具一行直接写"没有回归测试集，则升级开源版本即行为变更"，§4.2（3）给出往返测试进 CI 的写法，§6.2 把升级影响面的量级写成"厂商数 × 被改动的能力组合数"【推算】（来源：本主题 §3.2.4、§4.2（3）、§4.3、§6.2）。**"某家开源接入层的某次升级改变了归一化行为"这一条，本节与全书都核不到可引用的记录**——所以这里的证据只能到"准入条件 + 自测动作"这一步【经验】。自测动作是：数回归测试集覆盖的"厂商 × 能力"组合数，与实际用到的组合数之差，就是升级风险的不可见部分。

**失效条件**：当这一层的实现完全由你自己维护、且厂商接口在观察期内没有变化时，升级面的差别会消失（自建族的两个变数同时归零）。但这个前提很难长期成立：§4.6 把"厂商接口演进"写成在季度尺度上可预期发生的事——**所以升级面的差别只在"观察期足够短"时消失，它不是可以被选型消除的差别**。

#### 7.3.5 差异归因：计量单位能不能对上厂商账单

**机制是什么**：接入层记的账与厂商账单之间必然存在差异，**差异能不能被逐条解释**，取决于记账时存了什么。

**它在各候选中的实现差异**：自建族的记账字段由你定义，可以存分项（prompt / completion / 缓存命中 / 思考 token）；开源族通常提供用量记录，但**分项粒度取决于实现**（只存总量的开源网关无法归因差异）；平台 / 云族的记账点在你之外，你拿到的是它给的粒度。

**实现差异（定性）**：

| 候选族 | 记账粒度 | 差异能否逐条解释 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建族 | 你定义，可到分项 | 能 | 字段定义了但没人按月对账，差异分析退化成"承认差异存在" |
| 开源族 | 用量记录，分项粒度取决于实现 | 只存总量的实现不能 | 对账只能给出一个差额，归因不到"是哪一类 token 差出来的" |
| 通用 API 网关改造 | 请求级计数（计量对象还是请求） | 不能 | 单位与成本不成比例，差异解释不了也修不动 |
| 平台 / 云族 | 对方给的报表维度 | 取决于它的维度 | 粒度不够时只能回填总量，历史差异永久不可归因 |

**由此必然导出的性质**：因为**"同一个总 token"在不同厂商账单里含义不同**（系统提示是否计入、缓存命中是否打折、推理型模型的内部思考 token 是否单计），所以**只存总量的记账在原理上无法解释差异**——它只能给出一个差额，而差额无法归因到"是哪一类 token 差出来的"。**这条性质决定了一个具体的字段清单**（§4.2（6）的流水表），也决定了"每月差异分析"这项工作能不能落地：字段不够时，差异分析会退化成"承认差异存在"。

**公开证据**：这一条的判据在本主题被拆成了可执行的三件事——§4.2（1）给出"差异 > 5% 就要查口径"的对账判据（对的是"你账上的 tokens 与厂商账单"，按月比一次），并把常见来源列全（系统提示是否计入、思考 token 是否计入、缓存命中是否按不同单价计）；§4.2（6）给出可照抄的字段清单；§4.6 把"归一化维护成本"单列为持续成本（§7.4 的表另把"口径不一致导致的对账成本"记为平台 / 云族的隐性成本）【公开】（来源：本主题 §4.2（1）、§4.2（6）、§4.6、§7.4）。**这里的容差不要与 §4.1 步 4 括号里的"差异 < 1%"混起来**：那一处量的是同一个记账点内部"按租户拆开后的分账一致性"，本处量的是你的账与厂商账单之间的口径差，两者比较的对象不同；本节引对账判据时一律取 §4.2（1）的 5% 这一档（§8 的三处引用也是这一档）。**各厂商账单口径差异的权威对照表，本节核不到**——它属于商业条款与产品文档层面的信息，随合同与版本变化，**本节不给具体差异项与比例**。可核验的入口是你自己的月度对账记录，判据是"每一笔差额能否指到一项口径差别上"，而不是"差额有多小"【经验】（来源：本主题 §5.2 分级表（七行的判据②一栏都是"核不到"）与 §6.1 的失败教训）。

**失效条件**：当结算金额出现争议（业务方质疑"为什么这个月这么贵"）时，只有分项记账能回答；总量记账只能给出"系统就是这么算的"——这在内部结算里不构成解释。

#### 7.3.6 凭证的位置：应用进程里、你的出口上，还是平台里

**机制是什么**：密钥所在的**进程边界**，决定"轮换与吊销"是一次配置变更还是一次发版。凭证只有三个位置——应用进程内（每个应用各自持有）、你的出口上（一层持有，应用只带服务身份）、平台 / 厂商的产品里（你拿到的是一个签发与吊销的管理动作）。

**它在各候选中的实现差异**：自建族里，应用内封装必然把密钥留在应用侧（库没有地方放密钥，只能从配置读）；自研统一网关可以把密钥收到出口；开源族同样能在网关侧托管，但要看它的密钥存储形态是否支持"应用不可见"；平台 / 云族的凭证由平台签发，你拿到的是管理面，代价是吊销与轮换的时点由它定义。§7.6 的三条次序原则把这一条排在第一位（"先把凭证与记账点立起来，再谈归一化"），理由正是它不依赖厂商接口的稳定性。

**实现差异（定性）**：

| 候选族 | 密钥在哪 | 谁执行吊销 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建族（应用内封装） | 各应用的配置与代码里 | 每个应用的维护者（各做一遍） | 密钥散落在若干处仓库与配置中，轮换要逐个应用发版 |
| 自建族（自研统一网关） | 你的出口上（或专用密钥服务） | 你的平台团队（改一次配置） | 出口成了凭证的唯一持有者，也成了必须做高可用的单点 |
| 开源族 | 网关侧，形态取决于实现 | 你（但要先确认它不把密钥回显进日志与管理接口） | 调试接口或管理面回显密钥，密钥进了日志与工单 |
| 平台 / 云族 | 平台 / 厂商侧 | 厂商（你发起、它执行） | 吊销的生效时点不由你定；跨平台的凭证要各管一套 |

**由此必然导出的性质**：因为**吊销动作的执行者等于密钥的持有者**，所以"密钥在应用里"这一形态下，**吊销耗时的下界是发布节奏最慢的那个应用的发布周期**，且它与应用数量同向增长；密钥收到出口之后，吊销从"发版 × 应用数"变成"一次配置变更"。这条性质还解释了一个常见现象：**密钥轮换的频率往往由组织的发布节奏决定，而不是由安全要求决定**——不是因为不知道怎么轮换，而是因为轮换的代价被应用数量放大了。**推论**：凭证托管是接入层里唯一一件"越早做收益越大"的事——它不让任何已有功能变强，但它让所有后续动作的代价下降。这正是 §4.1 把它排成八步的第 2 步、§3.4 把它称作"网关的第一个可交付价值"的机制原因。

**公开证据**：托管侧的落点在本书他处有具名形态——Ch4 §06 的多份材料把密钥管理写成"加密 + 密钥管理服务"并列为数据服务架构的固定部件，Ch4 §07 §4 的示例要求密钥来自配置或密钥管理服务；出口侧的同一接口在 Ch5 §02 §4.2 写作 `egress: gateway`【公开】（来源：Ch4 §06 §8.17.1、Ch4 §07 §4、Ch5 §02 §4.2）。本主题给的是配置形态：§4.2（4）的 `credentials: {mode: gateway_only, rotation: {…, revoke_path: immediate}}` 与 `log_scrub`【公开】（来源：本主题 §4.2（4））。**"应用侧不得持有密钥"要可验证**这一条，判据是扫代码与配置中的密钥指纹、而不是靠规范；§4.9 自检清单把这条与"故意失败一次、看日志里能不能搜到密钥片段"并列【经验】（来源：本主题 §3.2.5 的失效点与 §4.9 自检清单）。各云厂商密钥管理服务的轮换与吊销接口，请以其官方文档当前版本为准，本节不给产品名与接口名。

**失效条件**：当所有应用同仓发布、发布周期与安全要求同频（一次发布覆盖全部调用方）时，"密钥在应用里"与"密钥在出口上"的吊销耗时差消失——此时凭证托管的收益只剩"谁在用"这一条可观测性。反过来，**只要出现一个发布节奏慢于安全要求的应用，这个差别立刻回来**；所以判断该不该收凭证，看的不是当前的应用数，而是**发布节奏最慢的那个应用**。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| 自建族 | 人力（首版 + 跟厂商变化的长期维护） | 归一化的持续适配、能力矩阵维护、网关自身高可用 | 随厂商数与接口变化频率增长 |
| 开源族 | 人力（集成 + 回归）与社区风险 | 升级回归测试集的维护、社区默认语义与你的结算口径的偏差修补 | 随升级频率与定制深度增长 |
| 平台 / 云族 | 按量计费（token / 调用） | 口径不一致导致的对账成本、出网粒度不足带来的合规改造 | 随调用量线性增长 |

**成本函数的三条判据**：① **自建族是"台阶形"**（人力按人年跳，不随调用量变），调用量小时极贵、大时最省；② **平台 / 云族是"线性"**，量小最省、量大最贵；③ **开源族是"台阶 + 线性"**（集成是台阶，回归与定制是线性）。**选型的实质是：先量调用量级与合规边界，再看落在哪条曲线的哪一段。**

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：V = 年调用量（次/年）    H = 常备人力（人年）    c = 单次调用托管成本（元/次）
    F = 开源集成的首版人力（人年）   r = 每次升级的回归成本（人年/次）   n_up = 年升级次数

自建族：  Cost_self(V) = H_self × 人均年成本                    ← 与 V 无关（台阶形）
开源族：  Cost_oss(V)  = (F + n_up × r) × 人均年成本 + 治理面人力  ← 台阶 + 按升级次数线性
平台族：  Cost_cloud(V) = V × c                                ← 与 V 线性（斜率 c）

令 Cost_self = Cost_cloud，解出「自建开始划算」的年调用量：
    V* = (H_self × 人均年成本) / c      【推算】
```

**单位说明（两条式子共用一个刻度）**：`V`、`V*`、`V**` 一律以**次/年**计，`c` 以元/次计——这样 `V × c` 与 `人力 × 人均年成本` 两侧同为"元/年"，解出来的 `V*`、`V**` 也才能与 `V` 直接比较。若把 `V` 改按"万次"记（同一量级里更顺手的写法），两条式子的右侧都要先折成次再比，否则 `V*` 与 `V` 会差四个数量级，"代入看落在哪一侧"这一步就整错。§7.5 第 3 问里的"月请求数在万级"是该问自己的档位刻度，与这里的计量单位无关。

**这个式子的用法**：代入你自己的 `H` 与 `c`，`V*` 就是你该不该自建的量化分界。**两个容易算错的输入**：

- **`H_self` 是常备人力而不是首版人力**——首版算一次，常备是每年。且它的主导项不是"写代码"，而是 §7.3.4 说的"跟厂商变化"：厂商数越多、接口变更越频繁，`H_self` 越高。
- **`r`（每次升级的回归成本）在开源族里是真实支出**——它随"厂商数 × 能力组合数"增长。**团队若没有把回归测试集计入排期，`r` 会被算成 0，估值必然偏低**；而它不会因为没排期就不发生。

**再写一条式子，用来回答"要不要自己集成"**：

```text
令本节上文的 Cost_oss(V) 与 Cost_cloud(V) 相等，解出「开源开始比托管划算」的年调用量：
    V** = [(F + n_up × r) × 人均年成本 + 治理面人力] ÷ c      【推算】（单位同上：次/年）

自建族与平台族的分界仍是上式的 V*，两者的差别只在分子：
    V*  的分子 = H_self × 人均年成本                     ← 只有常备人力
    V** 的分子 = (F + n_up × r) × 人均年成本 + 治理面人力 ← 首版人力 + 年升级次数 × 单次回归成本 + 治理面人力
```

**`V*` 与 `V**` 的大小关系不是先验的**：`H_self` 是常备人力、不含首版；`F + n_up × r` 含首版且随升级次数累加（`V**` 的分子另加一笔治理面人力）。**升级频繁的团队，开源族的分子会超过自建族的分子**——这是"用开源省人力"这个直觉失效的地方：开源省掉的是"跟厂商变化的实现工作"（归一化本身），**没有省掉"验证变化没有改行为"的工作**（回归测试集），而后者的量级同样随厂商数增长。

**隐性成本怎么量，而不是怎么估**：三族各有一笔"上线时不计入、第二年计入"的账，它们的共同点是**不产生账单**，因此不会被任何财务动作提醒。可核验的量法只有一条——**数动作次数**：① 自建族数"最近一年因为厂商接口变化改动的适配处数"（这就是 `H_self` 的实际增量）；② 开源族数"最近一年的升级次数 × 每次升级要重跑的回归用例数"（这就是 `n_up × r`）；③ 平台 / 云族数"最近一个季度因为口径不一致而人工解释的差额条数"（这就是对账成本）。三个数都从自己的记录里数得出来，不需要任何外部材料。

**一条经验判据**：调用量还小、团队里也还没有平台角色时，"自建"与"开源 + 自建治理面"的总成本差别不大（两者都是台阶形，差别在台阶高度）；**成本函数的台阶项随厂商数增长**（§3.2.3 的 O(k×m)：归一化的维护量与升级回归量都同向增长），而加第二家厂商这一步往往发生在业务已经把接入层当成既有设施之后。但**触发点不看厂商数**——§3.6 的通用判据是"某个失效形态第一次出现"，并明说"按厂商数量预设跃迁点，几乎一定过早或过晚"（它给这一档的【经验】信号是"多应用行为不一致、账单拆不开"，把"两个以上厂商"只当常见触发场景之一）。所以"加第二家厂商"应当被当成一次**重估成本函数的时点**，而不是"该建 / 不该建"的反转点【经验】（来源：本主题 §3.2.3 的 O(k×m) 与 §3.6 的跃迁判据）。判断方法：在加第二家厂商之前，先估一次"归一化改动处数"与"回归用例数"会各涨多少。

**成本之外还有一项不进入任何曲线的东西**：**历史用量的可追溯性**。它在跨族迁移时是最不可恢复的资产（§7.7 的硬结论）：从平台 / 云族收回时，历史用量只以对方的报表粒度存在，**粒度不够就无法补齐**。因此在接近 `V*` 的区间里，"已经开始积累的计量流水有多细"应当作为一个偏向"不迁"的权重。

### 7.5 决策树（每个分支都要有阈值依据）

1. **是否有租户的数据不能出域？**
   - 是 → 必须存在自托管端点，且出网判定必须在你的出口上 → **平台 / 云族的"直用"出局**；进入第 2 问。
   - 否 → 进入第 3 问。
2. **是否要按租户结算？**
   - 是 → 需要调用前记账 → **自建族或开源族 + 自建治理面**；再按第 4 问细分。
   - 否 → 进入第 3 问。
3. **调用量级与会话形态？（按"每月 token 量与请求数"量两个数）**
   - 量小（例如月请求数在**万级**【经验：以"是否需要专门一层"为分界，请用你自己的量级校准】）且数据可出域 → **平台 / 云族的托管接入**最省。
   - 量大或已有多厂商 → 进入第 4 问。
4. **有没有人能长期维护归一化与能力矩阵（按 0.3–1 人年的常备投入量级估算【经验】）？**
   - 有 → **自研统一网关**（控制力最强）。
   - 没有 → **开源网关 + 自建治理面**（把归一化交给社区，钱与合规留在手里）。

**阈值的诚实说明**：上表的"万级请求"与"0.3–1 人年"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的量级与排期校准，**不要当门槛用**。

**每个分支的阈值依据**（阈值从哪来、能不能自己算）：

- **第 1 问的"不能出域"**：依据是 §7.3.3 的位置机制——判定点必须在你唯一的出口上，所以这一问是门槛，答案形态是"是 / 否"，**不存在阈值**。
- **第 2 问的"要按租户结算"**：依据是 §7.3.2——只有调用前的记账点能给出"额度用完即拒绝"的语义。同样没有阈值，只有"要不要"。
- **第 3 问的"调用量级"**：依据是 §7.4 的两条式子——`V*`（自建 vs 托管）与 `V**`（开源 vs 托管）都由你自己的 `H`、`F`、`c` 决定，**所以这一问的阈值只能你自己算**，本节给的"万级"只用来区分档位【经验】。可执行的动作：把上一季度的请求量折成"次/年"（与 §7.4 的 `V` 同一刻度），连同托管单价 `c` 代入两条式子看落在哪一侧。
- **第 4 问的"有没有人能长期维护"**：依据是 §7.3.4——行为变更是否出现在变更评审的议题里，取决于谁执行升级。因此这一问的判据不是编制数，而是**这个角色在最近一个季度里是否真的做过一次归一化维护或能力矩阵更新**；没做过，就等于没有这个人【经验】。
- **矩阵里不引入新阈值的那些行**：§7.6 的"数据可出域、追求最快上线"与"已选定 Agent 平台"两行，同样由第 1、2 问筛出（前者不满足第 1、2 问所以可出域，后者从平台侧自带的出口走），它们不引入新阈值——**矩阵里凡是靠新增阈值才能成立的行，都是没有机制依据的行**。

**树里没有"预算"节点，这一点需要单独说明**：把"预算够不够"当作分叉，最常见的后果是**为省下托管费而选了一个机制上要持续投入人力的方案，第二年发现人力成本反而更高**——托管费是按量滚的账、人力是按时段跳的台阶，两者形状不同，而立项时只看得到前者【经验】。预算不是筛选条件，它是 §7.4 三条曲线在你自己的参数下的投影：你的调用量决定线性项，你的厂商数与升级频率决定台阶项。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单团队、单厂商、无结算要求 | 应用内封装 | 开源网关直用 | 上网关是"治理过剩"，但若半年内会加第二家厂商则直接用网关 |
| 多厂商、要按租户结算 | 自研统一网关 | 开源网关 + 自建治理面 | 直用开源的默认限流语义不等于预扣结算 |
| 人手有限、合规要求强 | 开源网关 + 自建治理面 | 自研统一网关 | 自研的归一化维护会长期占用人力 |
| 数据可出域、追求最快上线 | 平台 / 云族托管接入 | 开源网关直用 | 托管的出网粒度可能不足，合规改造要另想办法 |
| 已有成熟 API 网关 | 通用 API 网关改造 | 开源网关 + 自建治理面 | **限流单位与计量对象不同**（请求 vs token），改造量大且容易漏 |
| 已选定 Agent 平台 | 平台内置接入层 | 开源网关 + 自建治理面 | 平台内置的计量粒度可能只到平台级，达不到租户级 |

**组合的两条次序原则**：① **先把凭证与记账点立起来，再谈归一化**——它们不依赖厂商变化，可先落地；② **先把出网判定收到唯一出口，再做降级与缓存**——合规是硬约束，韧性与效率是可选项。

**还有第三条，方向相反但同样重要**：③ **归一化的"边界"可以先划、实现可以后补**——即先把"必归字段清单 + 透传白名单"两份文档写出来（半天的事），再决定这些字段由谁实现。**这条的价值在于它把一件看起来必须"选完型才能开始"的事，变成了一件可以立刻开始的事**；而且这两份文档在任何族里都用得上（自建族用它约束实现，开源族用它写回归测试集，平台 / 云族用它核对对方的粒度够不够）。

**三个常见组合**（各说明职责边界与运维代价）：

1. **通用 API 网关（前置鉴权与限流）+ 自建或开源的模型接入层（归一化与记账）**。API 网关管南北向的鉴权、限流与审计，模型接入层管到端点的调用与计量。**职责边界**：资质的判断在前者（谁可以调），额度的扣减在后者（花了多少）。**运维代价**：两层的限流单位不同——前者按请求、后者按 token，必须明确"以哪一层的数为准"；否则会出现"入口放行了、出口又拒绝"这种没人认得下来的报错。
2. **开源网关 + 自建治理面 + 平台侧出口标识**。归一化与路由用开源，计量 / 配额 / 审计 / 出网自建，平台侧把网关标成唯一出口（Ch5 §02 §4.2 的 `egress: gateway`）。**职责边界**：跟厂商变化的部分外包，钱与合规的部分自建。**运维代价**：治理面是**前置还是旁挂**必须写清——旁挂的治理面拦不住绕过它的调用（§6.2 的失败教训正是"限流一直在生效、账单照样穿透预算"）；前置则要求治理面自己也能扛住流量与自身的高可用。
3. **自研统一网关 + 云厂商接入层（影子期双跑）**。主力走自研，云厂商接入层只在新档位影子对比期间承接抽样请求。**职责边界**：生产路径只有一条，云侧只作对照。**运维代价**：双跑期间同一逻辑请求会被两家各执行一次，**成本按份数上涨**，因此必须带 §4.2（8）的停止条件与最小样本量；影子结束即下线，不下线就变成两套并存的长期成本。

三个组合的共同点是**入口复用既有设施、出口只留一个**：能复用的复用（鉴权、限流、追踪），必须唯一的唯一（记账点、出网判定、归一化）。反过来设计——两个记账点、若干条可直连的出路——是本主题最常见的形态错误。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 应用内封装 → 网关 | 行为分叉、账单拆不开 | 各应用改指向网关、密钥上收、补计量流水 | 以月计【经验】 |
| 开源直用 → 开源 + 自建治理面 | 配额只能限流、无法预扣结算 | 加治理代理、补记账与出网判定 | 以月计【经验】 |
| 平台 / 云族 → 自建 / 开源 | 出网粒度不足、口径不可控 | 重建归一化与记账点、历史用量无法补齐 | **以季度计**【经验】，且历史数据不可追溯 |
| API 网关改造 → 专用接入层 | 限流单位错位（请求 vs token） | 把计量对象从请求改为 token，调账口径 | 以月计【经验】 |
| 无能力矩阵 → 有能力矩阵 | 路由把任务分给不支持的模型 | 按文档建矩阵 + 抽检验证 | 以周计【经验】 |
| 总 token 记账 → 分项记账 | 与厂商账单有差异但无法归因 | 补字段并回填（**历史只能按总量保留**） | 以周计改字段，**历史差异永久不可归因** |
| 全局语义缓存 → 按任务类型开关 | 数值 / 时间类问题出现旧答案 | 建禁用清单 + 抽检流程 + 回滚已污染答案 | 以周计，且**已传播的错误答案无法回收** |
| 静态路由 → 成本感知路由 | （若反向：先做了动态路由） | 先补评测集，再谈动态 | **无评测集时不可迁**（迁了也只是按单价排序） |

**一条硬结论**：八条路里最贵的是**"把计量与出网交给别人"之后的收回**——它不只是技术搬迁，还包括口径重建与**无法追溯的历史**。**所以第 1、2 条判据（能否出域、是否要结算）必须在第一版就判对。**

**第二条硬结论**：**上表里有两项的代价是不可逆的**——"历史差异永久不可归因"与"已传播的错误答案无法回收"。其余六项都是"要花时间"，这两项是"花了时间也拿不回来"。**这条区分决定优先级**：如果只能做一件事，做那两件不可逆的（分项记账字段、语义缓存禁用清单），而不是先做那些"早做晚做都来得及"的（能力矩阵、降级链）。

**四条常见反模式**（症状 → 机制上错在哪 → 正确做法）：

- **把接入层做成转发器**：症状是应用已经不走厂商 SDK 了，但换一个档位仍要改应用代码。机制上**归一化没有真的发生**——转发的判定点是"出口"，而归一化的判定点是"字段"，两者不是同一件事。正确做法：用 §3.2.3 的判据，换一次档位，看要改几处。
- **先做路由，后补能力矩阵与记账点**：症状是路由上线很快、也确实省了钱，但账上看不出来。机制上路由的**前置数据是能力矩阵**（没有它，路由会把任务分给不支持的端点），而路由的**收益只有记账点能确认**（§4.1"顺序的反面"写的就是这一条）。正确做法：按八步顺序，矩阵与记账点在前。
- **把语义缓存当省钱开关**：症状是命中率上去了、成本下来了，随后出现"用上个月的数据回答本月的问题"。机制上语义缓存的命中判据是相似而不是相同，**错误会静默传播**（精确缓存的误判率为零，它只在键完全一致时命中）。正确做法：§3.2.8 的禁用清单 + 抽检动作，给不出抽检动作就不开；这条的代价形态就是上表里的"已传播的错误答案无法回收"。
- **把请求数当配额单位**：症状是复用了现有 API 网关的限流，看起来"已经有配额了"。机制上**观测点晚于超发点**，且单位与成本不成比例——同样数量的请求可以产生相差几个数量级的账单【经验】（§6.1 的失败教训给出的就是这个形态）。正确做法：按 §7.3.2 换单位，且预扣、结算、对账、差异解释四件配套一起换。

四条反模式的共同点是**它们都在机制层面改变了"判定点在哪"**：归一化退到转发、路由退到拍脑袋、缓存退到命中率、配额退到请求数。判断一次接入层建设有没有走偏，看的不是它上线了多少能力，而是**它的判定点有没有落在"钱与合规"那一侧**。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 一个团队、一家厂商、无结算要求 | 应用内封装，但先把必归字段清单写下来 | 上网关是治理过剩，而清单在任何族里都用得上 |
| 半年内会加第二家厂商 | 直接从网关起手 | 库形态的一层原理上做不了计量与降级 |
| 有租户的数据不能出域 | 自托管端点 + 出网判定进路由硬约束 | 判定点不在唯一出口上，合规只能是自觉 |
| 要按租户 / 应用出账 | 调用前预扣、调用后结算 | 观测点晚于超发点的方案永远防不住超发 |
| 多人多应用、密钥散落 | 先收凭证，再谈归一化 | 吊销的执行者等于密钥的持有者；这一步不依赖厂商接口变化 |
| 人手少，但钱与合规要自己掌握 | 开源网关 + 自建治理面 | 把"跟厂商变化"外包，把记账点与出网判定留在手里 |
| 已经有成熟的 API 网关 | 可以复用，但必须换计量单位 | 请求数与 token 不是同一个计量对象，差几个数量级【经验】 |
| 已选定 Agent 平台 | 平台内置接入层，先确认粒度到不到租户级 | 计量粒度只到平台级时，内部结算没有靶点 |
| 追厂商新能力要快 | 留透传白名单并写下来 | 归一化边界会被"绕过传私有参数"逐次侵蚀 |
| 调用量很小、便宜优先 | 托管接入 | 台阶形的成本在量小时最贵 |
| 被要求"证明没出域" | 拒绝日志 + 端点分布报表 + 一次演练 | 只有能被演练复现的拦截才算控制项 |
| 有人提议开语义缓存省钱 | 先给出禁用清单与抽检动作 | 语义缓存的错误不产生错误日志 |

> 本节小结：七个候选之间的差异，最终都能归到三问——**归一化落在谁手里**（应用内 / 你的一层 / 别人的产品里）、**记账点在调用前还是调用后**、**出网判定有没有强制执行点**。三问决定了它们的成本曲线形状（自建台阶、开源阶梯 + 线性、平台按量线性）与迁移代价（跨族迁移以季度计，同族以月计）。**选型顺序不可颠倒**：先用"能否出域"与"是否要结算"筛掉不可行，再用"归一化维护成本"与"团队承接能力"在剩下的里选——把后者当权重而不是门槛，是第二年最常见的预算超支原因。

**凭证位置与出网判定是同一问的两半**：第三问（出网判定有没有强制执行点）决定"请求能不能出去"，§7.3.6 的凭证位置决定"应用有没有能力自己出去"。两者合起来，才是 §7.1 判据 4 的完整含义——**少了任何一半，另一半都只是纸面制度**：有强制出口但密钥还在应用侧，出口可以被绕过；密钥收干净了但没有强制出口，请求只是"不知道能不能出去"。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的接入方式做一次"门槛检查"（不是打分）：数据能否出域、计量归属、归一化维护、凭证与出网、韧性与降级、团队承接——哪一条是"不满足"而不是"分数低"？那一条就是你明年最可能被迫迁移的方向；而你今天的补救，是否还落在"同族迁移（以月计）"这一格里？
