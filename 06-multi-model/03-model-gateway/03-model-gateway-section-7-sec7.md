## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研 / 开源 / 云厂商"打分有三个结构性问题：① 同一列在不同处境下方向相反（"可控性"对合规团队是必需、对两个人的团队是负担）；② 打分表隐含"这些选项互斥"，而真实形态常是组合（开源网关 + 自建治理面）；③ 最关键的判据（能否出域、是否需要按租户计费）**不是可打分的维度，而是门槛**——不满足直接出局。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 数据能否出域 | 哪些租户 / 哪类数据可发往外部端点？ | 不能出域 → 必须存在自托管端点，且出网判定要进路由硬约束（**门槛不是权重**） |
| 计量归属 | 记账点由谁实现、在调用前还是调用后？ | 要按租户结算 → 记账点必须自己掌握且在调用前 |
| 归一化维护 | 谁跟厂商接口变化？ | 这是**持续成本**，交给社区还是自己扛，决定长期人力 |
| 凭证与出网 | 密钥归谁、能否强制白名单？ | 合规与审计的落点；密钥散落则轮换与吊销永远做不干净 |
| 韧性与降级 | 端点故障时能否出结果、降级能否被标注？ | 决定业务 SLA 与复盘能力 |
| 团队承接能力 | 有没有人能长期维护归一化、能力矩阵与计量？ | 这一层的真实成本是长期人力，不是首版实现 |

> **读法**：先用第 1 条筛掉不可行；再用第 2、4 条筛掉"钱与合规不在自己手里"的方案；最后用第 3、5、6 条在剩下的里选——**第 6 条最容易被跳过，也最容易在第二年变成技术债**。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 应用内封装（库） | 少写重复代码 | 抽出内部工具函数库，各应用依赖 | 单团队、单厂商 | 库版本分叉；无统一计量；密钥仍在应用侧 |
| 自研统一网关 | 一层收口 | 归一化、路由、凭证、计量、韧性五块自研 | 有平台团队、合规要求强 | 长期人力；归一化要持续跟厂商变化 |
| 开源网关直用 | 配置化接入 | 以配置为中心的接入层（LiteLLM / One-API 一类） | 想快速拿到归一化与路由 | 计量与配额语义按社区默认；升级改变行为 |
| 开源网关 + 自建治理面 | 分工 | 归一化用开源，计量 / 配额 / 审计 / 出网自建 | 人手有限但钱与合规要自己掌握 | 两跳链路；升级需回归测试集 |
| 云厂商模型接入层 | 托管接入 | 厂商提供端点接入与用量统计 | 数据可出域、追求最快上线 | 口径与出网策略按厂商；跨厂商能力受产品限制 |
| 通用 API 网关改造 | 复用既有设施 | 在 API 网关上补模型调用与计量插件 | 已有成熟 API 网关的团队 | **限流单位与计量对象不同**（请求 vs token） |
| 平台内置接入层 | 平台自带 | Agent 平台自带的模型接入与用量统计 | 已选平台且不想多一层 | 与平台绑定；跨平台复用性差 |

**这七个候选其实分三族**：**自建族**（应用内封装、自研统一网关）——归一化与计量都在自己手里，代价是长期人力；**开源族**（开源网关直用、开源网关 + 自建治理面）——把"跟厂商变化"外包给社区，代价是升级管理与回归成本；**平台 / 云族**（云厂商接入层、通用 API 网关改造、平台内置接入层）——拿到成品能力，代价是口径与边界由别人定。

**族内可替换，跨族不可换**：自建族与开源族之间换，动的是归一化的实现位置；从这两族换到平台 / 云族，等于**把计量与出网口径交给别人**——那不是技术迁移，是治理决策。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 归一化的位置：应用内、一层里，还是别人的产品里

**机制是什么**：归一化只有三个位置——应用内（每应用一份）、独立一层（一份）、厂商产品内（不在你手里）。

**它在各候选中的实现差异**：自建族的两者都在"你的一层里"（库是代码形态的一层，网关是服务形态的一层），区别是**能否持有全局状态**（计量与降级需要全局状态，库做不到）；开源族在"你的一层里"，但实现来自社区；平台 / 云族在"别人的一层里"。

**由此必然导出的性质**：因为**计量与降级需要全局状态**，所以"库形态的一层"**原理上无法承担这两件事**——这解释了为什么应用内封装永远停在"少写重复代码"，而不会自然长成网关。

**失效条件**：当合规或结算要求出现时，"库形态"必须被替换（不是升级）——这是它与其它候选的关键差别。

#### 7.3.2 记账点：调用前、调用后，还是别人的报表里

**机制是什么**：记账点决定配额是"约束"还是"报表"。

**它在各候选中的实现差异**：自建族可在调用前预扣；开源族要看网关是否暴露调用前钩子（多数只给限流，不给预扣结算语义）；平台 / 云族的记账点在你的链路之外，你只能读它的报表（**口径与粒度由它定**）。

**由此必然导出的性质**：因为**观测点晚于超发点**，所以任何"读别人报表"的方案都不能防止超发——它的语义是"事后知道"，不是"事前约束"。

**失效条件**：当业务方要求"额度用完即拒绝"时，只有调用前记账的方案能满足；否则需求本身要改。

#### 7.3.3 出网判定：路由的硬约束，还是应用的自觉

**机制是什么**：合规要求能否被**强制执行**，取决于判定点是否在你唯一的出口上。

**它在各候选中的实现差异**：自建族与开源族（+ 自建治理面）可在出口判定；开源网关直用要看它是否支持按租户的出网策略；平台 / 云族的出网由厂商定义（可能只有"是否允许使用外部端点"这一粒度）。

**由此必然导出的性质**：因为**策略没有强制执行点就只能是自觉**，所以"应用侧不传敏感内容"这种实现不能算合规控制项——审计时也无法举证。

**失效条件**：当审计方要求"证明受监管数据未出域"时，只有"出口强制 + 拒绝日志 + 演练记录"这一组动作能作为证据。

#### 7.3.4 升级面：谁能改变你的行为

**机制是什么**：这一层的软件升级会不会改变行为。

**它在各候选中的实现差异**：自建族的行为由你控制（但厂商接口变化会间接改变行为）；开源族**升级即潜在行为变更**（归一化实现随版本演进）；平台 / 云族的行为变更由厂商发布节奏决定（**你可能没有选择权**）。

**由此必然导出的性质**：因为**归一化的行为变化难以从表面看出**，所以任何依赖他人归一化的方案都必须自建**回归测试集**——没有它，"升级"就是一次不可控上线。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| 自建族 | 人力（首版 + 跟厂商变化的长期维护） | 归一化的持续适配、能力矩阵维护、网关自身高可用 | 随厂商数与接口变化频率增长 |
| 开源族 | 人力（集成 + 回归）与社区风险 | 升级回归测试集的维护、社区默认语义与你的结算口径的偏差修补 | 随升级频率与定制深度增长 |
| 平台 / 云族 | 按量计费（token / 调用） | 口径不一致导致的对账成本、出网粒度不足带来的合规改造 | 随调用量线性增长 |

**成本函数的三条判据**：① **自建族是"台阶形"**（人力按人年跳，不随调用量变），调用量小时极贵、大时最省；② **平台 / 云族是"线性"**，量小最省、量大最贵；③ **开源族是"台阶 + 线性"**（集成是台阶，回归与定制是线性）。**选型的实质是：先量调用量级与合规边界，再看落在哪条曲线的哪一段。**

### 7.5 决策树（每个分支都要有阈值依据）

1. **是否有租户的数据不能出域？**
   - 是 → 必须存在自托管端点，且出网判定必须在你的出口上 → **平台 / 云族的"直用"出局**；进入第 2 问。
   - 否 → 进入第 3 问。
2. **是否要按租户结算？**
   - 是 → 需要调用前记账 → **自建族或开源族 + 自建治理面**；再按第 4 问细分。
   - 否 → 进入第 3 问。
3. **调用量级与会话形态？（按"每月 token 量与请求数"量两个数）**
   - 量小（例如月请求数在**万级**【经验：以"是否需要专门一层"为分界，请用你自己的量级校准】）且数据可出域 → **平台 / 云族的托管接入**最省。
   - 量大或已有多厂商 → 进入第 4 问。
4. **有没有人能长期维护归一化与能力矩阵（按 0.3–1 人年的常备投入量级估算【经验】）？**
   - 有 → **自研统一网关**（控制力最强）。
   - 没有 → **开源网关 + 自建治理面**（把归一化交给社区，钱与合规留在手里）。

**阈值的诚实说明**：上表的"万级请求"与"0.3–1 人年"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的量级与排期校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单团队、单厂商、无结算要求 | 应用内封装 | 开源网关直用 | 上网关是"治理过剩"，但若半年内会加第二家厂商则直接用网关 |
| 多厂商、要按租户结算 | 自研统一网关 | 开源网关 + 自建治理面 | 直用开源的默认限流语义不等于预扣结算 |
| 人手有限、合规要求强 | 开源网关 + 自建治理面 | 自研统一网关 | 自研的归一化维护会长期占用人力 |
| 数据可出域、追求最快上线 | 平台 / 云族托管接入 | 开源网关直用 | 托管的出网粒度可能不足，合规改造要另想办法 |
| 已有成熟 API 网关 | 通用 API 网关改造 | 开源网关 + 自建治理面 | **限流单位与计量对象不同**（请求 vs token），改造量大且容易漏 |
| 已选定 Agent 平台 | 平台内置接入层 | 开源网关 + 自建治理面 | 平台内置的计量粒度可能只到平台级，达不到租户级 |

**组合的两条次序原则**：① **先把凭证与记账点立起来，再谈归一化**——它们不依赖厂商变化，可先落地；② **先把出网判定收到唯一出口，再做降级与缓存**——合规是硬约束，韧性与效率是可选项。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 应用内封装 → 网关 | 行为分叉、账单拆不开 | 各应用改指向网关、密钥上收、补计量流水 | 以月计【经验】 |
| 开源直用 → 开源 + 自建治理面 | 配额只能限流、无法预扣结算 | 加治理代理、补记账与出网判定 | 以月计【经验】 |
| 平台 / 云族 → 自建 / 开源 | 出网粒度不足、口径不可控 | 重建归一化与记账点、历史用量无法补齐 | **以季度计**【经验】，且历史数据不可追溯 |
| API 网关改造 → 专用接入层 | 限流单位错位（请求 vs token） | 把计量对象从请求改为 token，调账口径 | 以月计【经验】 |
| 无能力矩阵 → 有能力矩阵 | 路由把任务分给不支持的模型 | 按文档建矩阵 + 抽检验证 | 以周计【经验】 |

**一条硬结论**：七条路里最贵的是**"把计量与出网交给别人"之后的收回**——它不只是技术搬迁，还包括口径重建与**无法追溯的历史**。**所以第 1、2 条判据（能否出域、是否要结算）必须在第一版就判对。**

### 7.8 小结

> 本节小结：七个候选之间的差异，最终都能归到三问——**归一化落在谁手里**（应用内 / 你的一层 / 别人的产品里）、**记账点在调用前还是调用后**、**出网判定有没有强制执行点**。三问决定了它们的成本曲线形状（自建台阶、开源阶梯 + 线性、平台按量线性）与迁移代价（跨族迁移以季度计，同族以月计）。**选型顺序不可颠倒**：先用"能否出域"与"是否要结算"筛掉不可行，再用"归一化维护成本"与"团队承接能力"在剩下的里选——把后者当权重而不是门槛，是第二年最常见的预算超支原因。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的接入方式做一次"门槛检查"（不是打分）：数据能否出域、计量归属、归一化维护、凭证与出网、韧性与降级、团队承接——哪一条是"不满足"而不是"分数低"？那一条就是你明年最可能被迫迁移的方向；而你今天的补救，是否还落在"同族迁移（以月计）"这一格里？
