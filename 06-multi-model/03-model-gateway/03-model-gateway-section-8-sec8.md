### 8.2 统一接入层的边界与选型

#### §MG.1 团队同时用着两家厂商的模型，三个应用各自直连。请说明：（1）"统一接入层"与"API 网关""应用内封装的函数库"分别解决什么问题，为什么后者不能自然长成前者；（2）如果现在要建这一层，第一件该做的事是什么、为什么不是归一化；（3）如何用一条可验证的判据说明这一层"建成了"？

**1. 考察点**

- 能否把三种东西的**治理对象**分清楚（南北向流量 / 代码复用 / 到模型端点的调用）。
- 是否理解"库形态的一层"为什么在原理上做不了计量与降级（**缺全局状态**）。
- 能否给出**可验证的建成判据**，而不是"我们做了统一接入"。

**2. 参考答案框架**

**第一层：三者解决什么（回答第 1 问）**。API 网关治理**南北向流量**（鉴权、限流、路由到服务），计量单位是**请求**；应用内封装的库解决**代码复用**，不持有全局状态；统一接入层治理**到模型端点的调用**，计量单位是 **token**，并负责归一化、路由、凭证、降级。**库不能长成网关的原因**：计量需要"调用前的预扣 + 调用后的结算"两笔流水，降级需要"跨应用的端点健康状态"，两者都要求**全局状态**——函数库没有地方放这些状态（除非引入外部存储，那就已经是在做服务了）。

**第二层：第一件该做的事（回答第 2 问）**。**先收凭证**，不是先做归一化。理由：① 凭证托管的收益立即可见（轮换一次只改一处、吊销即时生效），且**不依赖厂商接口的稳定性**；② 归一化是长期维护项（厂商接口会变），先做它会把团队拖进持续适配，而治理收益（谁在用、能不能吊销）却还没拿到；③ 凭证托管是归一化的前提——密钥不落应用，应用才可能改成"只带租户身份"的统一请求。

**第三层：建成判据（回答第 3 问）**。两条，都可当场验证：**① 换一个模型档位，改动的代码行数为 0（只改配置）**；**② 任意一天的用量能按租户 / 应用拆开，且与厂商账单的差异可解释（量级控制在 5% 以内【经验：常见差异来自系统提示与思考 tokens 是否计入】）**。两条中缺任何一条，都说明这一层还没建成——第 1 条证明"归一化成立"，第 2 条证明"记账点成立"。

**第四层：为什么"先收凭证"的收益最先显现，而"先做归一化"不是**。把两个动作的收益形态并排看：收凭证的收益是**一次性台阶**——吊销从"逐个应用发版"变成"一次配置变更"，做完就不再重复投入；归一化的收益是**每多一家厂商才兑现一次**，而它的成本是随厂商接口变化持续发生的。更关键的是两者的**前置关系**：密钥留在应用侧时，应用的请求里必然带着厂商身份，此时要把它改成"只带租户身份"的统一请求，等于同时改密钥与请求形态两件事；先收凭证之后，归一化要落的只剩"字段映射"一件。§3.4 把这一步写成"网关的第一个可交付价值"、§4.1 把它排在八步的第 2 步，理由都在这里（机制上的完整解释见 §7.3.6：吊销的执行者等于密钥的持有者）。

**第五层：为什么建成判据必须是"行为"而不是"架构声明"**。第 3 问要的两条判据，共同点是**都能当场执行并给出是 / 否**：换档改动行数为 0 是一个可以被别人复现的动作（让他来改一次试试），账能拆开是一个可以在任意一天执行的动作（挑一天来拆）。对照三类常见的"声明式判据"——"所有应用都走网关"（无法验证有没有旁路）、"我们做了统一封装"（无法区分库与网关）、"我们有配额体系"（无法区分报表与约束）。**能被别人复现的才是判据，能被自己陈述的只是立场。**

**第六层：把三种东西放回候选全景里**。本题开头的处境（两家厂商、三个应用各自直连）落在 §7.2 的**候选表之外**——那张表从"应用内封装（库）"起算，因为直连不是一条可选方案，而是"接入层还不存在"的状态（这就是七行里没有它的原因）。要从这个状态往前走，第一刀是**选族**：自建族（应用内封装 → 自研统一网关）把归一化与计量都留在自己手里，代价是长期人力；开源族（开源网关直用 → 开源网关 + 自建治理面）把"跟厂商变化"外包，代价是升级管理与回归测试集；平台 / 云族拿到成品能力，代价是口径与边界由别人定。**族内换的是实现，跨族换的是记账点与出网判定的归属**——后者不是技术迁移，是治理决策（§7.6 的矩阵每行都带"不选它的原因"，就是给这一刀用的）。

**3. 常见陷阱**

- 把"统一接入"讲成"统一 SDK"——库没有全局状态，做不了计量与降级。
- 只讲归一化的收益，不讲它的**持续成本**（厂商接口变化在季度尺度上可预期发生）。
- 用"我们所有应用都走网关"当作建成判据——**判据必须是可当场验证的行为**（换档改动数、账单可拆分），不是架构声明。
- 用"统一接入"覆盖"统一出口"——网关上了，但应用仍有直连外部端点的路径。此时**计量与出网都不是"部分成立"**：绕过通路的调用不进任何账、也不受任何策略约束（§7.3.3）。

**4. 追问预测**

- 「网关会不会成为单点？」——会：它是关键路径，所以必须多副本 + 熔断 + 容量规划；数据面上的其他部件可以无状态随便扩。
- 「统一了以后，厂商的新能力怎么用？」——留**透传白名单**：约定俗成的字段走归一化，厂商私有参数走透传；两者都要有文档，否则接入层会变成瓶颈。
- 「我们只有一家厂商，需要这一层吗？」——按量级判断：若半年内会加第二家、或要按租户结算，就直接建；否则先用应用内封装（但要知道它的上限）。
- 「两家厂商的能力差异很大（一家没有工具调用），归一化怎么做？」——**能力差异不进归一化，进路由的硬约束**（§2.2 把能力与出网写成约束，§MG.4 第 1 问同一口径）。归一化只管字段形态；把能力差异塞进归一化，会得到一个"看起来统一、实际每次都要按厂商写分支"的接口——那种接口换档仍然要改代码，第 1 条判据没达标。

**5. 参考资料**

- 三种"一层"的定位差异，可对照本书 [Ch4 §07 数据 API 网关](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway.md)（南北向）与 [Ch5 §02 平台架构](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture.md)（平台侧出口）。
- 成本必须归属到 Owner 的口径见 [Ch11 §03 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)。
- 候选方案的分族、筛选次序与"跨族不可换"所指的三个决定，见本主题 [§7.1–§7.2](03-model-gateway-section-7-sec7.md)；"凭证先于归一化"的机制解释见同文件 §7.3.6。
- 平台侧把网关标成唯一出口的接口形态见 [Ch5 §02 §4.2](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-4-sec4.md)（`egress: gateway`）。

### 8.3 归一化：字段、流式与用量口径

#### §MG.2 你要把两家的模型调用归一到一套接口。请说明：（1）哪些字段是"必归"的，为什么流式与工具调用最容易漏；（2）用量口径在各家不一样，你如何对齐，容差定多少；（3）怎么保证归一化在厂商升级或换档后不悄悄失效？

**1. 考察点**

- 能否把归一化**落到字段级**，而不是"统一成一个接口"。
- 是否知道用量口径的差异点（系统提示、思考 tokens、缓存命中）。
- 能否给出**可自动跑的验证**（往返测试），而不是人工检查。

**2. 参考答案框架**

**第一层：必归字段（回答第 1 问）**。六类：**消息**（角色、内容、多模态部件及其顺序）、**工具**（清单、调用参数、结果回传）、**流式**（文本增量、工具调用增量、结束原因、用量收尾）、**用量**（input / output tokens、缓存命中标记）、**错误**（可重试 / 不可重试、限流、内容策略拒绝、参数非法）、**控制**（温度、最大输出、停止词、结构化输出开关）。**流式最容易漏**的原因：各家的分片语义不同——有的**只在最后一帧给用量**，中间帧不带；工具调用的参数是**分片拼接**的（需要缓冲与拼装），不是一次给全。**工具调用最容易漏**的原因：参数类型不一致（有的厂商把 JSON 变成字符串传），以及"工具结果回传"的格式各家不同。

**第二层：用量口径（回答第 2 问）**。差异集中在三处：系统提示是否计入 input、思考 tokens 是否单列、**缓存命中是否按不同单价计**。对齐动作：**按月与厂商账单对账，差异逐条解释**；容差定在 **5% 以内**【经验，口径差异超过这个量级通常意味着有一类 tokens 没被统计】。**不做对账的后果**：你以为在按 token 计费，实际上账目基准是错的，所有成本优化都建在错误基线上。

**第三层：不悄悄失效（回答第 3 问）**。**把归一化写成往返测试并进 CI**：对每个厂商、每种请求形态（普通 / 流式 / 带工具 / 多模态），断言 `g_v(f_v(r))` 与 `r` 在必归字段上逐项相等。这样厂商升级或换档时，**行为变化先在 CI 暴露**，而不是在生产上暴露。配套动作：能力矩阵的每格可核验（随机抽三格能在 10 分钟内核验），矩阵变更走评审。

**第四层：两份文档的先后次序**。"必归字段清单"与"透传字段清单"必须先写下来、再写实现。理由不是流程洁癖：**清单是判据，实现是细节**，顺序反过来，字段集就会变成"实现到哪算哪"——每加一家厂商，字段集随实现漂移一次，而没有任何时刻能把"应该归到什么程度"回答清楚。两份文档的分工也要写清：必归清单约束"统一接口里必须有的字段"，透传白名单约束"统一接口之外允许存在的通路"——**没有白名单，某个应用会用绕过归一化的方式传私有参数，而那条通路不受任何校验**（§2.3 第 8 条）。

**第五层：归一化的边界由谁改、按什么改**。清单不是一次写死的：厂商新增能力（新的多模态部件形态、新的工具调用形态）时，先决定它进必归清单还是走透传，再决定实现。判断方法只需问一句——**"这个字段会不会影响路由或计量？"**：会影响（例如"是否支持并行工具""缓存命中标记"）就必须进必归，因为它要被路由与记账点读到；不影响（厂商私有的调优参数）走透传。**判据**：给一次厂商接口变更，能否在 CI 里一次跑出"哪些字段受影响"。

**第六层：归一化是持续成本，不是一次性投入**。它的增长量是"厂商数 × 差异点数"——每加一家厂商，要归的字段集合就按两家的差异逐项扩大，而这项工作不会结束（§3.2.3 把这条增长写成 O(k×m)，§4.6 把"归一化维护成本"单列为持续成本）。**观测量**：数"最近一年因为厂商接口变化改动的适配处数"，这个数就是归一化维护的实际规模，它应当与"厂商数 × 一年内的接口变更次数"同阶——**若它远低于这个乘积，多半不是维护得好，而是有变更没有被发现**（判据回到第一层：往返测试覆盖了哪些组合）。另一条容易忽略的：归一化把排障路径变长了——**统一请求的形态与到达厂商的形态不再一一对应**，所以留痕里要能同时看到两侧（否则现场只能靠猜）。

**本题的判据类型**：三个子问题问的分别是"边界在哪""口径怎么对齐""怎么保证它不悄悄失效"——**三者要的都是可执行动作，而不是状态描述**。凡是答成"我们做了归一化""我们对齐了口径"的，都还停在状态描述；面试官要听的是"用哪个动作能证明它成立"（往返测试跑在 CI 里、差异能指到口径项、清单能先于实现评审）。

**3. 常见陷阱**

- 归一化只覆盖"消息"，漏掉流式与工具，导致换档后前端解析失败。
- 把用量口径"按自己理解"记，不与账单对账——账目基准错误无法通过优化弥补。
- 用人工检查代替测试：**升级/换档是高频事件，人工检查必然漏**。
- 先写实现、后补清单——字段集变成"实现到哪算哪"，每加一家厂商就漂移一次；且两份文档的顺序反了之后，"应包括哪些字段"这个问题永远不会有一个可评审的答案（§4.1 步 3 把清单列为产物、把往返测试列为判据，就是这个次序）。

**4. 追问预测**

- 「透传字段怎么管？」——白名单制：只有明确列出的厂商私有参数可透传，其余一律拒绝（否则归一化的边界会被逐步侵蚀）。
- 「同一个提示在不同档位上能用吗？」——**不能假定相同**：档位越低，指令跟随越弱，往往需要更短、更明确的提示；降级链里要允许"按档位绑提示版本"。
- 「结构化输出怎么归一？」——统一成一个"输出 Schema + 校验失败时的重试策略"；注意各家对"约束强度"的实现不同（有的只是提示，不是硬约束）。
- 「流式归一最难的是什么？」——**结束原因与用量收尾**：有的厂商只在最后一帧给用量、中间帧不带，有的把工具调用参数分片下发（要缓冲与拼装）。所以归一化要在**事件序列**这一层对齐，而不是在"单个 JSON 文档"这一层对齐（§4.5 模板 2 给的就是事件序列的形态）。

**5. 参考资料**

- 多模态 / 工具调用在请求中的表达形态，可按各厂商 API 文档的"消息结构"章节当前版本核验【公开：以官方文档当前版本为准】。
- 工具 / 资源 / 提示的协议化接入由 Anthropic 于 2024 年公开（规范与实现可按规范当前版本核验）【公开】。
- 归一化往返测试的写法见本主题 [§4.2（3）](03-model-gateway-section-4-sec4.md)；必归字段清单（六类）见 §4.2（1）；统一请求与统一流式事件的模板见 §4.5。
- 协议化那一层"解决什么、不解决什么"（权限 / 计量 / 审计 / 幂等仍在治理侧）见本主题 [§6.3](03-model-gateway-section-6-sec6.md) 与 §5.3.2。

### 8.4 凭证托管与出网合规

#### §MG.3 审计方要求"证明受监管数据没有发往外部模型端点"。请说明：（1）从工程上如何做到"技术上不可能"而不是"规范上不允许"；（2）你会拿哪些可核验的证据去举证；（3）日志里最容易泄漏什么，怎么防？

**1. 考察点**

- 能否把合规从"制度约束"变成"**强制执行点**"。
- 能否给出**可举证的证据组**（而不是一句承诺）。
- 是否知道凭证泄漏最常见的路径（日志与错误信息）。

**2. 参考答案框架**

**第一层：做到"技术上不可能"**。三个条件缺一不可：① **凭证托管**——厂商密钥只存在于网关（或专用密钥服务），应用侧不得持有（可用密钥指纹扫描代码与配置来验证，而不是靠规范）；② **出网白名单**——默认拒绝，按租户分级放行，受监管租户只允许命中自托管端点；③ **判定点在唯一出口上**——出网判定进路由的**硬约束**（不满足即出局），而不是应用侧的 if 判断。**关键**：只要存在"应用能直连外部端点"的路径，合规就只是自觉。

**第二层：举证证据组**。四条：① **拒绝日志**（含租户与端点类别、不含内容）：证明越界请求会被拒绝；② **受监管租户的端点分布报表**：应 100% 落在自托管；③ **一次演练记录**——让受监管租户的请求指向外部端点并验证被拒（**"演练过拒绝"比"承诺不发送"有力得多**）；④ **密钥托管证明**——应用侧扫描结果 + 轮换记录。四条合起来构成可审计的闭环。

**第三层：日志泄漏**。最常见的三条路径：① 请求头或错误信息里带上 `Authorization`；② 网关内部异常栈把配置对象打出来；③ 调试日志把完整请求体落盘。防法：**写日志前自动脱敏**（`log_scrub` 在写之前生效，而不是靠人记得删）+ **故意失败一次并搜日志**（用密钥片段做全文检索，命中即为缺陷）。

**第四层：三个条件不是并列，是串联**。① 凭证托管决定"应用有没有能力直连"（没有密钥就没有能力），② 出网白名单决定"即使有路径，能不能过"，③ 判定点在唯一出口决定"这一层是不是必须经过"。三者的关系是**能力 → 策略 → 位置**。任何一条缺失，合规都退回"应用自觉"：有密钥没白名单是"记得别发"，有白名单没有唯一出口是"另有一条路可以发"，有出口但凭证还在应用侧是"出口可以被绕过"。**这就是"技术上不可能"这个词的准确含义**——不是"我们不让"，而是"这条路径不存在"。

**第五层：四条证据各自证明哪个条件**。四条证据不是并列的材料清单，它们一一对应：① 拒绝日志证明"策略在生效"（对应条件②），② 受监管租户的端点分布报表证明"实际走的路符合策略"（对应条件②的结果），③ 一次演练记录证明"拦截是可复现的"（对应条件③——判定点确实在唯一出口上，否则演练会从另一条路漏出去），④ 密钥托管证明"应用没有直连能力"（对应条件①）。**对照着讲的好处是**：审计方问"怎么证明"时，你能直接回答"这一条对应哪个条件、材料在哪"，而不是把四份材料一起端上去。

**第六层：合规结论要能随新应用接入而不重做**。判断一次合规改造是不是"结构性"完成，看的是**新接入的应用需要做什么**：如果它只需要登记租户身份、出网与否由策略自动决定，那么合规是结构性的；如果它需要"知道哪些数据不能发出去"并自己把关，那么合规仍然是自觉的——只是换了个人自觉。这条判据也解释了为什么拒绝日志要记**租户与端点类别**而不记内容：日志本身要能进审计材料，内容进去就等于把泄漏面扩大一次。再补一条工程细节：出网判定要**默认拒绝、按租户分级放行**（§4.2（4）的 `egress` 结构），而不是"默认放行 + 黑名单"——黑名单的失效形态是放行，而放行不产生告警（§7.3.3）。

**本题的判据类型**：合规题的答案必须落在"能不能被演练复现"上——**策略、承诺、规范都是陈述，拒绝日志与演练记录才是证据**。三层答完如果还举不出一次演练，答案就还停在制度层。这也是本题最容易失分的地方：多数候选人能把"我们做了凭证托管与出网白名单"讲得很完整，却答不出"怎么证明它在生效"。

**3. 常见陷阱**

- 把合规做在应用侧（"我们不传敏感数据"）——审计无法举证，且新应用接入即绕过。
- 只有策略没有演练——策略是否生效无从证明。
- 日志脱敏靠规范执行——**脱敏必须是代码路径的一部分**。
- 把"密钥管理服务"与"凭证托管"当成一件事——前者是存放与轮换密钥的部件，后者是"密钥不落在应用侧"这条形态约束。用了密钥管理服务、但应用仍从它读取密钥，等于**条件①没有成立**（判据是扫代码与配置里的密钥指纹，不是"我们用了 KMS"）。

**4. 追问预测**

- 「自托管端点的成本怎么摊？」——自托管是"台阶形"固定成本（无论用多少都要付），外部端点是"线性"；**受监管租户的单位成本通常更高，这个差值应体现在内部结算里**，而不是被平均掉。
- 「跨境与出域是一回事吗？」——不是：跨境是地域维度的合规，出域是"是否离开你的边界"；判定粒度要能同时表达这两者（端点分类标签里要带地域）。
- 「密钥轮换会影响正在跑的请求吗？」——设计上要支持"新密钥生效、旧密钥在短窗口内仍可用"，否则轮换就是一次短暂不可用。
- 「业务方一定要用某家只有公开端点的模型，但该租户不能出域，怎么办？」——按"能力与出网是硬约束"处理（§2.2）：该租户拿不到这个能力，而不是给它开一个例外。**例外一旦开了，拒绝日志就不再是证据**——它证明的是"该租户通常被拒"，而不是"该租户一定被拒"。
- 「端点分类怎么做才不会越用越乱？」——分类维度要少而稳定：**托管形态**（自托管 / 公开端点）、**地域**（境内 / 境外）、**能承载的数据级别**。三个维度任一缺项，策略就会退化成"逐租户写例外"；而例外一多，拒绝日志就不再能作为证据（它只能证明"通常被拒"）。

**5. 参考资料**

- 分级保密与出网策略的治理口径见 [Ch8 治理](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md)；合规控制项与举证方式见 [Ch11 §07 审计与合规](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md) 与 [Ch11 §02 数据安全](../../11-cross-cutting/02-data-security/02-data-security.md)。

### 8.5 路由策略与降级链

#### §MG.4 模型端点会限流、会超时。请说明：（1）路由该由什么决定，哪些条件必须是硬约束而不是权重；（2）降级链怎么设计，降级的"质量损失"如何事先量出来；（3）降级发生时，系统里必须留下什么痕迹？

**1. 考察点**

- 能否区分**门槛条件**（能力、出网、合规）与**排序条件**（成本、质量）。
- 是否理解"降级要带质量损失估计与标注"，而不是静默退让。
- 能否把重试语义与降级区分开（**跨端点重试 ≠ 降级**）。

**2. 参考答案框架**

**第一层：路由的输入（回答第 1 问）**。硬约束（不满足即出局）：**能力满足**（工具调用、并行工具、结构化输出、多模态、上下文长度）、**出网允许**（租户分级）、**数据边界**。排序条件（同档内比较）：质量估计（来自你自己的评测集）、成本（tokens × 单价）、延迟与可用性。**关键判断**：把能力与合规当权重，会在运行期产生"看起来选了最省的端点、但它不支持工具调用"这类错误——**这类错误的根因是判据类型错了，不是参数调错了**。

**第二层：降级链与质量损失（回答第 2 问）**。链条形态：`旗舰 → 中档 → 经济档 → 规则 / 缓存 / 人工`；每跳要有**触发条件**（限流、超时、不可用、质量不达标）与**质量损失估计** `Δq = q_0 − q_i`（用你已有的评测集量）。三点要求：① 中小档**通常需要不同的提示**（同提示跨档表现不可假定一致）；② 每跳要有**恢复条件**（半开探测自动回切，避免只降不升）；③ 降级到"缓存 / 规则"时也要按"有损"处理（结果不能与正常结论混用）。

**第三层：痕迹（回答第 3 问）**。三条：① 事件流里带 `degraded: true` 与**实际端点**（业务侧必须能看见）；② 留痕里记录**触发原因**（限流 / 超时 / 质量不达标）与**持续时长**；③ 成本流水里标注该次调用**用的是哪一档**（否则事后无法解释成本结构变化）。**判据**：任意一次降级，能否从留痕里回答"什么时候、因为什么、退到哪一档、持续多久"。

**第四层：三类故障的处置不一样，混用就会出事**。① **限流**：可重试，但要在同端点退避，降级是备选而不是默认——限流是"等一等就好"，降级是"换一个档"；② **超时**：可重试，**禁止换端点**（换端点等于用不同模型回答同一个问题，结果不可比）；③ **不可用**：进降级链（§4.7 演练表的"主端点不可用"一行给的就是这一跳的判据）。三类的共同边界是**幂等性**：带副作用的工具调用一律不重试（§4.2（5）的重试语义表就是按这四列排的）。"排队还是降级"的判断也在这一层：交互式会话里排队破坏体验（降级更合适），批量任务里排队更省（但要给队列积压一个可观测信号）。

**第五层：恢复条件与"只降不升"**。降级链只写"退到哪一档"是不完整的，每一跳还必须写"什么时候升回来"——形态是**半开探测自动回切**。只降不升是成本与质量的双输：端点恢复后仍在用低档，质量没拿回来，而低档省下的那点钱不会出现在任何账上（业务在低质量结果上做的返工也不进这个账）。判据就是 §4.7 演练表里的那一行——主动切断主端点，看恢复后有没有自动回切。

**第六层：把"重试""降级""排队"三个动作分开**。三者的目标不同：重试是"同一个端点再来一次"（成功则业务无感），降级是"换一个端点把结果交出去"（有损），排队是"等额度恢复"（不损但延迟）。**混用会同时丢掉两样东西**：把重试写成跨端点，等于把降级伪装成重试（成本翻倍、结果不可比，事件流里还没有 `degraded` 标注）；把降级写成重试，等于让业务等在一条已经不可用的端点上。§4.2（5）的重试语义表就是按这条边界排的——**"重试范围"那一列始终是同端点，只有它守住，降级链才有意义**。还有一条与成本有关的观察量：降级次数与降级到的档位应当能在成本流水里按档位切开（第三层的第 ③ 条），否则"这个月成本结构变了"这件事只能靠回忆解释。

**本题的判据类型**：路由题要听出"硬约束"与"排序条件"的分界，降级题要听出"有损可用"与"静默退让"的分界——**两处分界错了，参数调得再对也没用**。这两个分界也正是本题两处最容易被绕过去的地方：把能力与出网写成权重（第一个分界错），把降级写成一次内部重试（第二个分界错）。答完三层后，可以主动补一句"这两处的分界是什么"，往往比继续展开细节更能拿分。

**3. 常见陷阱**

- **跨端点自动重试**当成降级——同一逻辑请求在两家端点各执行一次，成本翻倍且结果不可比。
- 降级静默执行——业务拿到的是低档结果却以为是正常结果。
- 只降不升——端点恢复后仍在用低档（成本与质量双输）。
- 降级链过长（大 → 中 → 小 → 规则）——质量断崖且无人负责：每一跳都带来提示版本分叉，链条越长，"这次结果到底是哪一档产出的"越难回答；而且 §4.7 的演练判据要求**每一跳都能被单独触发与观测**，链条越长越做不到。

**4. 追问预测**

- 「限流时应该排队还是降级？」——看业务：交互式会话排队会破坏体验（降级更合适）；批量任务排队更省（但要给队列积压一个可观测信号）。
- 「质量不达标怎么判定？」——必须有离线评测集；没有评测集就只能用"结构化校验失败 / 工具调用失败"这类**硬信号**代替，这属于降一档判据【经验】。
- 「多租户下怎么按租户选档？」——把档位放进租户策略（合规租户默认锁定自托管档），而不是让业务自己选。
- 「质量损失 Δq 怎么事先量出来？」——只能用你自己的评测集：没有评测集时退到硬信号（见上一问）；**两者都拿不出来时，不要写"降级后质量损失可接受"这句话**，因为它无法复核，而这句话恰恰是降级链能不能在事故里被信任的前提。
- 「熔断按厂商还是按端点？」——**按端点，不按厂商**：同一厂商不同区域 / 不同配额域的表现不同，按厂商熔断会把你本来还能用的端点一起切掉（§2.3 第 5 条）。这也是"降级链的每一跳都应当是可独立观测的端点"的原因——熔断粒度与降级粒度过粗，两者会互相污染。

**5. 参考资料**

- 熔断半开、灰度与回滚的机制见 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)；容量与可用性口径见 [Ch12 §04 容量规划](../../12-architecture/04-capacity-planning/04-capacity-planning.md)。
- 降级链与路由配置的形态见本主题 [§4.2（7）](03-model-gateway-section-4-sec4.md)；重试语义表见 §4.2（5）；六类故障演练见 §4.7。
- 降级链为何被 §5.2 判为 L2（判据②核不到）见本主题 [§5.2](03-model-gateway-section-5-ai.md)；"多模态归一与降级链是加固而不是新机制"见 §5.3.6。

### 8.6 计量、配额与对账

#### §MG.5 业务方要求"额度用完即拒绝"。请说明：（1）记账点放在链路的哪一刻，为什么事后统计不行；（2）预扣与结算怎么配对，漏扣怎么发现；（3）你如何证明这个额度是"真的"在起作用？

**1. 考察点**

- 能否把"配额"从报表语义改成**拦截语义**。
- 是否理解预扣-结算的配对关系与泄漏风险。
- 能否给出**可核验的证明动作**。

**2. 参考答案框架**

**第一层：记账时点（回答第 1 问）**。必须在**调用前**（网关侧预扣）：按请求的上限预估扣减，调用完成后按实际用量结算并退差额。**事后统计不行**的原因很直接：观测点晚于超发点——从报表里看到超发时，钱已经花出去了。**语义判据**：把额度调成一个很小的值，发一次请求，**应当在调用发生前被拒绝**（而不是"调用完成后报表显示超了"）。

**第二层：配对与漏扣（回答第 2 问）**。`reserve` 与 `settle` 按 `request_id` 配对，**未配对的 reserve 就是"泄漏的预扣"**；要有每日对账任务：找出超过 N 分钟未配对的记录并释放，同时输出一个"泄漏率"指标。**泄漏率长期大于千分之一【经验，随超时与异常比例浮动】说明有系统性缺口**（例如超时后没有结算路径）。另外两条：① 计量写入失败**不应导致业务失败**（本地缓冲补写）；② 记账要用整数微单位，避免浮点误差累积。

**第三层：证明额度在起作用（回答第 3 问）**。三个可核验动作：① **演练**：把某租户额度临时调到 0，验证请求被拒且拒绝原因明确；② **对账**：把网关记账与厂商账单按月比对，差异逐条解释（量级控制在 5% 以内【经验：差异常来自系统提示与思考 tokens 计入口径】）；③ **归因**：任取一天，能按租户 / 应用 / 会话把用量拆开且合计等于总额。三条都能执行，配额才不是纸面制度。

**第四层：预扣上限怎么定，以及它自己也是一个可观测量**。预扣按"输入估算 + `max_output_tokens`"估上限，结算按实际用量退回差额。这里的隐患不是"扣不准"，而是**扣得太大**：预扣上限远高于实际输出时，同一份预算能支撑的在途并发请求数被这个倍率直接腰斩——§2.2 给出的就是这条推导的口径（预扣上限 ÷ 实际均值【推算】，读者的参数换成自己的输入长度、`max_output_tokens` 与 completion 分位数即可重算）。配套动作是**把 `max_output_tokens` 收到实测 completion 分位数的一个小倍数上**（§2.2 给的是这个量级）【经验】。**这个倍率本身应当被监控**：它长期偏大，说明额度被"在途占位"吃掉了，而不是被真实用量吃掉——两种吃法的处置完全不同（前者调参，后者扩容或限流）。

**第五层：并发下"先查后扣"为什么会失效**。预扣必须是**原子操作**（数据库行锁或原子计数器）：先读余额、再判断、再扣减的三步实现，在并发下会让多个请求同时通过"判断"这一步，于是额度被超发——而且超发发生在配额生效的那一刻，事后对账只能看到账目不平，看不到是谁超的。另一条与并发相关的是**结算路径必须存在**：漏扣的典型来源不是"没记账"，而是"记了账却没有结算路径"（超时、连接中断、进程被杀）。所以 §4.2（6）把"未配对的预扣"定成一个要由对账任务每天清理的对象，并按"泄漏率"监控【经验：量级随超时与异常比例浮动】。

**第六层：把配额做成"能被业务看见"的东西**。业务方要的不是"有配额"，而是"我知道还剩多少、什么时候会被拒"。因此三件东西要同时存在：**余额可见**（调用方能在调用前查到剩余额度）、**拒绝原因明确**（额度不足 / 权限不足 / 端点不可用三者必须在错误码与日志里可区分）、**回退路径明确**（额度用尽后是降档还是报错，由租户策略定，而不是由调用方临时决定）。这三件里最常缺的是第二件：把"额度不足"和"端点不可用"混成同一个 5xx，会让业务方在额度充足时以为被限流、在额度用尽时以为对端故障。另有一条纪律要写进设计：**计量写入失败不得导致业务失败**，但**出网策略失败必须失败**（§4.7 的末行）——两者方向相反，落在同一段代码里时最容易被写成同一种处理。

**本题的判据类型**：计量题的答案必须能落在"调用前"这一侧——**任何落在调用后的方案，无论统计得多准，都只能回答"花了多少"，回答不了"还能不能花"**。这个分界一旦说清，"预扣 / 结算 / 对账 / 泄漏率"这一串机制就是它的自然推论；说不清，它们就只是四个孤立的名词。本题最后那问（"怎么证明额度是真的"）考的正是这一点：三条动作全部是"事前语义"的验证动作，而不是报表口径的讨论。

**3. 常见陷阱**

- 配额按"请求数"而不是"token"——一个大请求打满额度，口径与实际成本不成比例（**复用了 API 网关的实现，没改计量单位**）。
- 只做事后统计——无法防止超发，也无法向业务方交代。
- 缺少未配对预扣的释放——额度被"泄漏"的预扣占着，业务方看到"我有额度却调不动"。
- 记账字段缺 `session` 或 `model_version`——成本能拆到租户但拆不到会话，优化没有靶点。
- 把额度实现成一个可以并发放过的计数器（先查后扣的三步写法）——**配额在第一次并发峰值的第一秒就失效**，而且失效形态是"账目对不上"而不是"拒绝变多"，最难归因。

**4. 追问预测**

- 「预扣按什么估上限？」——按 `max_output_tokens + 估算输入` 预扣，结算按实际；预扣过大会挤占额度，过小会失去约束意义（**按任务的输出上限分布定**）。
- 「并发下预扣怎么保证不超发？」——预扣必须是**原子操作**（数据库行锁或原子计数器），先检查后扣减的两步实现会在并发下失效。
- 「客户要求看自己的用量明细怎么办？」——记账流水按租户导出（注意脱敏：内容不能导出，只能导用量与元数据）。
- 「厂商账单比你的账多，和比你的账少，哪个更危险？」——**多（你少记了）更危险**：少记意味着有调用没有落在任何租户的账上，内部结算多收或少收都无处可追；少（你多记了）通常是预扣没有结算，属于可修复的账目问题。方向可以这样判断，量级只能用自己的月度对账记录说话。

### 8.7 缓存与影子对比

#### §MG.6 有人提议"加一层语义缓存把成本砍一半"。请说明：（1）什么情况下语义缓存是错的，为什么它比精确缓存危险；（2）缓存键要包含什么、失效条件怎么定；（3）换档前如何用影子对比拿证据，影子本身怎么避免烧钱？

**1. 考察点**

- 能否指出语义缓存的**错误复用**风险，并给出禁用清单的做法。
- 是否理解缓存键与**版本**的绑定关系。
- 能否给影子对比加上**停止条件**。

**2. 参考答案框架**

**第一层：什么时候不能用（回答第 1 问）**。**带数值或时间条件的任务必须禁用**（"上月 GMV"被复用给"本月 GMV"），以及**权限相关**（不同租户的相同问题答案不同）、**实时性相关**（行情、库存、告警）的任务。**比精确缓存危险的原因**：精确缓存只在"请求完全一致"时命中，错误概率低且可解释；语义缓存的命中判据是"相似"，相似≠相同，而错误会**静默传播**——用户看到的是格式正确、来源错误的答案。**判据**：如果某个任务类型你**说不出**"如何发现错误复用"的抽检动作，就不该给它开语义缓存。

**第二层：缓存键与失效（回答第 2 问）**。键必须包含：**归一化后的请求 + 关键参数 + 模型版本 + 提示版本 + 租户 / 权限域**（权限域不进键会造成越权命中）。失效条件：模型或提示版本变更即整体失效；语料 / 数据源变更按 TTL 失效（TTL 取决于数据刷新周期）；**用户显式"重新生成"必须绕过缓存**。运维动作：每日抽检命中记录（人工核对是否同义），抽检发现错误即**收窄启用范围**。

**第三层：影子对比与停止条件（回答第 3 问）**。做法：按会话哈希抽样（例如 5%），同请求双发到"现档"与"新档"，收集**质量分（用评测集）、单请求成本、P95 延迟**；达到最小样本量（例如每任务类型 200 条【经验，以能看出差异为原则】）后评估。**停止条件必须写死**：成本增幅或延迟增幅超过设定阈值即停止影子——**否则影子会长期运行并把成本翻倍**，这是"优化变事故"的最常见形态。

**第四层：缓存的失效条件，与检索缓存不是一回事**。缓存键里必须带**模型版本与提示版本**，这是"换档或改提示即整体失效"的机制决定；而检索缓存的失效条件是**语料版本**（§2.4 把这条差别单独写成一句：前者随模型版本、后者随语料版本）。两者混用会得到一个"看起来省了钱、实际拿旧上下文回答了新问题"的链路——它的症状与语义缓存错误复用一样是静默的，但根因在检索侧而不在缓存侧。**判断顺序**：先确认失效条件写的是哪一类版本，再谈命中率；**版本维度缺失时，命中率越高越危险**。

**第五层：影子的结论必须落进配置，否则它只是一次实验**。影子对比产出的是三个数（质量分、单请求成本、P95 延迟）在一组样本上的对照；这三个数的用途不是选出一个"更好的档位"，而是改写 §4.2（7）的路由配置（哪类任务走哪档、`quality_floor` 定在哪）。**判据**：一次影子对比结束后，必须能指出路由配置里被改动的行；指不出来，说明结论没有落地——下次换档要重做一次同样的实验，而这次实验的成本已经花掉了。

**3. 常见陷阱**

- 权限域不进缓存键 → 跨租户命中（**安全事故**）。
- 语义缓存全局开启、无禁用清单 → 数值题错误复用。
- 影子没有停止条件与样本量 → 成本翻倍、结论不可用（样本太少看不出差异）。
- 缓存命中率作为唯一指标 → 命中率高但错误复用的方案会被选出来（**指标错位**）。
- 用"相似度阈值"代替禁用清单——阈值是全局的一个数，而禁用是按任务类型的判断：数值类、含时间条件、依赖调用方身份的任务，**在任何阈值下都不该开**（§3.2.8 的禁用清单口径）。阈值调低只会让它错得更少，不会让它不错。

**4. 追问预测**

- 「精确缓存的命中率通常多高？」——个位数到两成【经验，随请求重复率浮动】；低于这个量级时，先确认"请求是否真的重复"（很多"重复"其实是参数不同）。
- 「缓存和降级链怎么配合？」——降级的最后一跳常是"返回缓存结果"，此时**也要标注 `degraded`**（不能与正常缓存命中混淆）。
- 「影子对比发现新档更贵但更好，怎么决策？」——看任务的失败代价：取数类任务优先成本，决策类任务优先质量；把结论写进路由策略而不是一次性判断。
- 「怎么判断一次缓存命中是错的？」——抽检动作要能写出"这条命中是否同义"的判断依据。**写不出依据，说明这条任务的答案到底是"同义即可复用"还是"必须逐次重算"本身就还没想清楚**——那就不该给它开语义缓存，而不是先开了再靠抽检兜。

### 8.8 本章小结

本节收录 6 道题，覆盖**多模型统一网关与工具协议**的六个核心考点：**边界 → 归一化 → 凭证与出网 → 路由与降级 → 计量与配额 → 缓存与影子**。六道题构成一条完整的建设链路：

- **§MG.1 边界**：三种"一层"的治理对象不同；建成判据是"换档不改代码 + 账能拆开"。
- **§MG.2 归一化**：六类必归字段；重量要口径与账单对齐；靠往返测试进 CI 防悄悄失效。
- **§MG.3 合规**：凭证托管 + 出网白名单 + 唯一出口；举证靠拒绝日志、分布报表、演练记录、托管证明。
- **§MG.4 路由与降级**：能力与合规是硬约束；降级要带质量损失与 `degraded` 标注；禁止跨端点自动重试。
- **§MG.5 计量**：调用前预扣、调用后结算、每日对账未配对项；用演练、对账、归因三件事证明额度是真的。
- **§MG.6 缓存**：语义缓存必须带禁用清单与抽检动作；影子对比必须带停止条件与样本量。

> 六道题与本节 §7 的机制单元对应：§MG.1 → §7.3.1（归一化的位置）与 §7.3.6（凭证的位置）；§MG.2 → §7.3.1 与 §7.3.5（差异归因）；§MG.3 → §7.3.3（出网判定）与 §7.3.6；§MG.4 → §7.3.3（出网判定，取其中"进路由的硬约束"那一面：能力与出网都是门槛不是权重）与 §7.7 的迁移代价表（静态路由 → 成本感知路由一行）；§MG.5 → §7.3.2（记账点）与 §7.3.5；§MG.6 → §4.2（7）（8）的配置形态与 §7.6 的三条次序原则。

**答题心法**：先说清约束（能否出域、是否要结算、团队承接能力），再说清选项（七条路的三族），最后说清取舍与代价。这一层的问题，面试官真正想听的是 **"你的判据类型对不对"**——把"能力与合规"当权重、把"事后统计"当配额、把"跨端点重试"当降级，都是判据类型错误，比参数调错更难发现。
