## 4. 工程实现

### 4.1 落地步骤

**八步，顺序不能颠倒**：

| 步 | 动作 | 产物 | 判据（先写下，再动手） | 为什么必须在这一步 |
| --- | --- | --- | --- | --- |
| 1 | **建能力矩阵** | 模型 × 能力表，每行指向可核验的文档条目 | 任一行能否独立核验（能/不能） | 路由依赖它；没有它，路由就是拍脑袋 |
| 2 | **收凭证** | 密钥上收 + 应用只带服务身份 | 吊销一次密钥的耗时（目标：分钟级） | 投入最小、收益最先显现 |
| 3 | **定归一化边界** | 必归字段清单（消息 / 工具 / 流式 / 用量）+ 透传字段清单 | 归一化往返测试能否在 CI 跑过 | 边界不清，后面每次加厂商都要重谈 |
| 4 | **建计量记账点** | 记账流水表 + 预扣 / 结算两笔 | 任意一天的账单能否按租户拆开（差异 < 1%） | 记账点只能有一个；晚做会丢历史 |
| 5 | **接路由与降级链** | 路由配置 + 降级链（每跳带触发条件与质量损失） | 端点故障时业务是否出结果；降级是否标注 | 路由是配置化的第一体现 |
| 6 | **上韧性** | 超时 / 重试语义表 + 熔断 + 半开探测 | 跨端点重试是否默认禁止 | 重试语义错会让你在事故里付双倍 |
| 7 | **上缓存（精确优先）** | 缓存键（含模型与提示版本）+ 失效条件 + 禁用清单 | 数值 / 时间类问题是否被禁用 | 缓存错用会静默传播错误 |
| 8 | **上灰度与影子** | 按租户 / 会话分流 + 影子对比流水 | 换档是否有质量与成本差值证据 | 换档不能靠感觉 |

**顺序的反面**：最常见的错误是**先做路由（看起来最有产出）**——没有能力矩阵的路由会把任务分配给不支持的模型；没有计量的路由省下的钱无法确认（**省了多少，账上看不出来**）。

### 4.2 关键技术点

**（1）归一化的必归字段清单**（可直接作为评审清单）

| 类别 | 必归字段 | 常见坑 |
| --- | --- | --- |
| 消息 | 角色、内容、多模态部件（图 / 文件引用） | 图与文本的**顺序**在不同厂商语义不同 |
| 工具 | 工具清单、调用参数、调用结果回传 | 参数类型（字符串化 JSON）不一致 |
| 流式 | 文本增量、工具调用增量、结束原因、用量收尾 | 有的厂商**只在最后一帧给用量**，中间帧不带 |
| 用量 | input / output tokens、缓存命中标记 | 各家口径不同（是否含系统提示、是否含思考 tokens） |
| 错误 | 可重试 / 不可重试、限流、内容策略拒绝、参数非法 | 同类错误在不同厂商的 HTTP 码不同 |
| 控制 | 温度、最大输出、停止词、结构化输出开关 | 参数名与取值范围差异（0–1 与 0–2） |

**用量口径的判据**：把"你账上的 tokens"与"厂商账单的 tokens"按月对账，**差异 > 5% 就要查口径**（通常来自系统提示是否计入、思考 tokens 是否计入、缓存命中是否按不同单价计）。

**（2）能力矩阵（示例形态）**

| 模型档位 | 流式 | 工具调用 | 并行工具 | 结构化输出 | 多模态 | 长上下文 | 自托管可选 |
| --- | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 旗舰档 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | 否 |
| 中档 | ✓ | ✓ | ✓ | ✓ | 部分 | ✓ | 视权重许可 |
| 经济档 | ✓ | ✓ | ✗ | 部分 | ✗ | 中 | ✓ |
| 规则 / 缓存档 | ✗ | ✗ | ✗ | — | ✗ | — | ✓ |

**维护纪律**：矩阵变更走一次评审（因为路由依赖它）；每个 ✓ / ✗ 都要能指向一条文档条目——**判据**：随机抽三格，能否在 10 分钟内核验。

**（3）归一化往返测试（可进 CI）**

```python
NORMALIZE_CASES = [                     # 统一请求 → 厂商请求 → 统一响应
    {"msgs": [{"role": "user", "content": "hi"}], "tools": [], "stream": True},
    {"msgs": [{"role": "user", "content": [{"type": "image", "ref": "s3://…"}]}], "stream": False},
    {"msgs": [{"role": "user", "content": "查上月 GMV"}], "tools": [TOOL_SCHEMA], "stream": False},
]

def test_normalization_roundtrip(vendor):
    for case in NORMALIZE_CASES:
        wire = to_vendor(vendor, case)                 # f_v: R → R_v
        back = from_vendor(vendor, fake_response(wire))# g_v: R_v → R
        assert same_on_required_fields(case, back), (vendor, case)
```

**这一条测试的价值**：厂商升级或换档时的行为变化，会先在 CI 里暴露——**而不是在生产上暴露**。

**（4）凭证托管与出网策略**

```yaml
credentials:
  mode: gateway_only          # 应用侧不得持有厂商密钥
  rotation: {interval_days: 90, revoke_path: immediate}
egress:
  default: deny
  rules:
    - {tenant: analytics-team, endpoint_class: public_vendor, allow: true}
    - {tenant: regulated-bu,   endpoint_class: public_vendor, allow: false}   # 只能走自托管
    - {tenant: "*",            endpoint_class: self_hosted,   allow: true}
  log_scrub: [api_key, authorization, secret]
```

**三条硬要求**：① 应用侧"不得持有密钥"要**可验证**（扫代码与配置中的密钥指纹，而不是靠规范）；② 出网默认拒绝（白名单制）；③ 日志脱敏要**自动**（`log_scrub` 在写日志前生效，而不是靠人记得删）。

**（5）超时与重试语义表**（把"能不能重试"写成表，而不是写在每个调用点）

| 情形 | 可重试 | 重试范围 | 说明 |
| --- | :---: | --- | --- |
| 连接失败 / DNS | ✓ | 同端点 | 指数退避，最多 2 次【经验：次数与端点恢复时间分布有关】 |
| 429 限流 | ✓ | 同端点 | 遵守 `Retry-After`；无该头时按退避 |
| 5xx | ✓ | 同端点 | 仅幂等请求；带副作用的工具调用一律不重试 |
| 400 参数非法 | ✗ | — | 重试必然同样失败 |
| 内容策略拒绝 | ✗ | — | 换端点结果不可比，应提示业务 |
| 超时（无响应） | ✓ | 同端点 | **禁止换端点**：换端点等于用不同模型回答同一个问题 |

**（6）计量流水（两笔：预扣与结算）**

```sql
CREATE TABLE gw_meter (
  id            BIGSERIAL PRIMARY KEY,
  request_id    UUID NOT NULL,
  tenant_id     TEXT NOT NULL,
  app_id        TEXT,
  session_id    TEXT,
  endpoint      TEXT NOT NULL,
  model_version TEXT NOT NULL,
  kind          TEXT NOT NULL,          -- reserve | settle
  tokens_in     BIGINT, tokens_out BIGINT,
  cache_hit     BOOLEAN NOT NULL DEFAULT FALSE,
  amount_micros BIGINT NOT NULL,        -- 以微单位记账，避免浮点误差
  created_at    TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON gw_meter (tenant_id, created_at);
```

**判据**：`reserve` 与 `settle` 必须成对（按 `request_id` 可配对）；**未配对的 reserve 就是"泄漏的预扣"**，要有对账任务每天找出并释放。

**（7）路由配置（示例）**

```yaml
routes:
  - match: {task: sql_generation, tenant_class: any}
    primary: flagship
    fallback: [mid, economy]           # 顺序即降级链
    quality_floor: mid                 # 低于此档需人工兜底
  - match: {task: summarize_doc, tenant_class: regulated}
    primary: self_hosted_mid           # 合规租户只走自托管
    fallback: [self_hosted_economy]
  - match: {task: explain_metric, cache: semantic_allowed}   # 语义缓存只开在解释类
    primary: economy
    cache: {type: semantic, ttl_s: 86400, model_version_pinned: true}
```

**（8）影子对比（换档前的证据）**

```yaml
shadow:
  from: mid
  to: flagship
  sample: {percent: 5, by: session_id, min_samples_per_task: 200}   # 达到最小样本量再评估
  collect: [quality_score_from_eval_set, cost_per_request, p95_latency]
  stop_rule: {max_cost_delta_pct: 50, max_latency_delta_pct: 80}    # 越线即停，避免影子本身烧钱
```

**判据**：影子对比必须有**停止条件**——否则影子会长期运行并把成本翻倍（这是最常见的"优化变事故"）。

### 4.3 工具链与平台

| 层 | 可选 | 选型判据 |
| --- | --- | --- |
| 归一化与路由 | 开源网关（以配置为中心的接入层，LiteLLM / One-API 一类）；或自研 | 人手 vs 需要跟厂商变化的频率（变化快、人手少 → 开源 + 自建治理） |
| 自托管推理 | 高吞吐推理服务（vLLM / TGI 一类） | GPU 供给形态与量化需求；权重许可是否允许私有化 |
| 前置限流与鉴权 | 通用 API 网关 | 是否已有统一网关可复用（注意：**限流单位要改成 token**） |
| 计量与配额 | 自建流水表 + 对账任务；或平台侧配额 | 是否要与平台配额统一（应统一，避免两套口径） |
| 观测 | OpenTelemetry 语义约定 + 追踪后端 | 是否需要与平台 Trace 打通（应打通：会话 → 步 → 模型调用） |
| 夹具 | 归一化往返测试 + 能力矩阵核验清单 + 影子对比流水 | 是否有回归测试集（没有，则升级开源版本即行为变更） |

### 4.4 存量迁移

**从直连 SDK 迁到网关，四步**（每步可独立验证）：

1. **只换出口**：应用仍用原 SDK 的调用形态，但把 `base_url` 指向网关（网关做透传 + 计量）。**判据**：账能拆到租户。
2. **收密钥**：应用去掉厂商密钥，改带服务身份。**判据**：吊销一次密钥（应用无感）。
3. **切归一化**：应用改用统一接口（不再用厂商 SDK 的参数名）。**判据**：换一个档位不改代码。
4. **上路由与降级**：把硬编码的模型名换成档位标签。**判据**：端点故障时业务出结果且被标注。

**双跑对拍**：第 3 步期间，同一批真实请求同时走"旧直连"与"新网关"，比较响应结构与用量口径——差异项必须逐条解释（这一动作通常能发现 3–5 处归一化遗漏）。

### 4.5 模板 / 示例

**模板 1：统一请求（应用侧只写这一种）**

```json
{
  "tenant": "analytics-team",
  "app": "metric-copilot",
  "session": "6f1c…",
  "task": "sql_generation",
  "tier": "auto",
  "messages": [{"role": "user", "content": "查上月 GMV 同比"}],
  "tools": ["warehouse.query_readonly"],
  "structured_output": {"schema_ref": "answer_v3"},
  "stream": true,
  "budget": {"max_output_tokens": 2048}
}
```

**模板 2：统一流式事件（把各家分片归一）**

```json
{"type": "text_delta",  "text": "上月 GMV"}
{"type": "tool_delta",  "tool": "warehouse.query_readonly", "args_delta": "{\"sql\":\"SELECT"}
{"type": "usage",       "tokens_in": 1280, "tokens_out": 96, "cache_hit": false}
{"type": "finish",      "reason": "tool_call", "endpoint": "flagship", "degraded": false}
```

**关键在 `degraded`**：降级必须出现在事件流里，**否则业务侧无法区分"正常结论"与"降级结论"**（这是 §3.5 反模式"降级不标注"的技术落点）。

**模板 3：登记一个工具（与平台出口共用）**

```yaml
tool: warehouse.query_readonly
input_schema: {type: object, required: [sql], properties: {sql: {type: string, maxLength: 20000}}}
writable: false
limits: {max_rows: 10000, timeout_ms: 30000}
scope: {tenants: [analytics-team], tables_allow: ["dws_*", "dim_*"], deny: ["pii_*"]}
model_visible: true            # 该工具是否对模型可见（由注册表生成模型侧描述）
```

### 4.6 成本：这一层省下与花掉的钱

**三块收益、两块成本**（【推算：口径固定，单价按你的合同代入】）：

| 项 | 口径 | 量级（【经验】） |
| --- | --- | --- |
| 路由收益 | 经济档承接比例 × 单请求价差 | 高重复、低复杂度任务里，经济档可承接**三成到七成**流量，取决于质量评测集的结论 |
| 缓存收益 | 命中数 × 单请求成本 × （1 − 质量折损） | 精确缓存命中率通常**个位数到两成**；语义缓存可更高，但只在解释类任务上允许 |
| 降级收益 | 由"不可用 → 有损可用"折算，难直接计价 | 与业务 SLA 挂钩，**不按省钱算** |
| 网关自身成本 | 实例数 × 月单价 + 计量存储 + 运维 | 与端点成本相比通常在**百分之几**量级【经验】 |
| 归一化维护成本 | 每次厂商变更的适配工时 | **这是持续成本**：厂商接口演进在季度尺度上可预期发生 |

**一条判据**：**"网关自身成本 ÷ 端点成本"若长期大于 10%，说明接入层过重**——先收敛实例数与日志量，而不是继续加功能。

### 4.7 容灾与故障演练

| 故障 | 演练动作 | 通过判据 | 常见失效点 |
| --- | --- | --- | --- |
| 主端点限流 | 让网关对主端点返回 429 | 降级到备用档且事件里 `degraded=true` | 无降级链 → 业务直接失败 |
| 主端点不可用 | 主动切断主端点 | 降级链条按顺序生效；恢复后半开探测自动回切 | 只降不升 |
| 网关自身故障 | 滚动重启网关实例 | 应用无感（多副本 + 连接池重试） | 单副本网关 |
| 计量写入失败 | 让流水表只读 | 请求仍可完成，**预扣流水进本地缓冲并补写** | 计量失败导致请求全失败（把可观测性当成了强依赖） |
| 出网策略误配 | 让一个合规租户命中外部端点 | 请求被拒绝并给出明确原因 | 出网策略不生效（最严重：合规事故） |
| 缓存污染 | 注入一条错误缓存 | 禁用清单生效、正确性抽检能发现 | 语义缓存无禁用清单 |

**一条纪律**：**计量失败不能导致业务失败**——计量是治理需求，不是业务依赖；预扣可以做"本地先记、异步补写"，但**出网策略失败必须失败**（两者方向相反，务必分开设计）。

### 4.8 演进路线：0 → 1 → 100

- **0 → 1（收口）**：能力矩阵 + 凭证托管 + 计量记账点。判据：换模型不改代码；账能按租户拆。
- **1 → 10（韧性）**：路由 + 降级链 + 超时重试语义表 + 熔断。判据：端点故障时业务出结果且被标注。
- **10 → 100（效率与合规）**：缓存（精确 → 语义，带禁用清单）+ 影子对比 + 多租户出网策略 + 与平台配额统一。判据：一次影子对比出结论；一次合规演练通过。

### 4.9 自检清单

- [ ] 能力矩阵是否每一行都可独立核验？最近一次更新是什么时候？
- [ ] 归一化往返测试进 CI 了吗？覆盖流式与工具调用吗？
- [ ] 用量口径与厂商账单对过账吗？差异是多少（目标 < 5%）？
- [ ] 应用侧真的不持有密钥吗？用密钥指纹扫过代码与配置吗？
- [ ] 出网策略是白名单制吗？合规租户能否被技术上阻止访问外部端点？
- [ ] 日志脱敏是自动的吗？故意失败一次，日志里能搜到密钥片段吗？
- [ ] 预扣与结算成对吗？有没有对账任务在找"泄漏的预扣"？
- [ ] 重试语义表写下来了吗？跨端点重试是否默认禁止？
- [ ] 降级事件是否出现在流式事件与留痕里（`degraded` 字段）？
- [ ] 缓存键包含模型与提示版本吗？语义缓存的禁用清单是谁定的、什么时候复核？
- [ ] 影子对比有停止条件吗？上次影子花了多少钱？
- [ ] 计量写入失败时业务是否会失败（**不应失败**）？出网策略失败时是否会失败（**应失败**）？

### 4.10 小结

> 本节小结：接入层的工程实现可以压缩成一句话——**先把"钱与合规"收进来，再把"差异与韧性"归一化**。八步顺序的实质是：能力矩阵是路由的前置数据（没有它就没有可选性）、凭证托管是投入最小的第一步（先做它）、记账点只能有一个（晚做会丢历史）、韧性语义要写成表（写在调用点就一定会分叉）。两块成本里，**网关自身成本要与端点成本一起看**（比值长期超 10% 就是过重），**归一化维护是持续成本**（不是一次性投入）——把这两点想清楚，才不会在第二年把"统一接入层"做成新的技术债。

> 💡 **思考锚点**：挑一个你现在直连的模型调用，做两件事：给它加一个"档位标签"而不写死模型名（这一步能验证你的接入层是否是配置化的），再去厂商账单里找一次它的实际 token 用量，与你自己的记录比一比。这两个动作加起来不超过半天，却能回答"你的账准不准、你的档位能不能换"——你打算先做哪一个？
