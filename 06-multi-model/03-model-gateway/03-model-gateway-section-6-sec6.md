## 6. 落地实践

> **本节的材料纪律（先说清楚）**：接入层的公开材料以**产品文档与工程博客**为主，生产细节（归一化边界、缓存正确性、路由质量）极少公开。因此本节**不列具名公司的生产案例**，只用**三类形态**的类型归纳来讲机制——每一类都标明对应 §3 的哪个模式，并给出可自测的判据。
>
> **这些形态来自公开材料（产品文档、规范、工程博客）的类型归纳，不是对任何一家公司内部实现的转述**；文中数字一律标档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的数值，请以你自己的实测口径为准。

### 6.1 形态一：单团队多厂商接入（对应 §3.2.4 + §3.2.5）

**背景与挑战**：一个数据平台团队为内部应用提供模型能力，同时用着两家厂商（一家通用旗舰、一家自托管中档）。应用各自直连，密钥散在 5 个仓库里；一次模型档位调整要改 7 处代码。

**触发点**：一次密钥轮换——厂商要求 90 天轮换一次，团队花了两天把 5 个仓库全部改完并各自发版。**轮换本身不是问题，"改 5 处 + 5 次发版"才是**。

**详细做法（按 §4.1 的第 2、3、5 步）**：

- **凭证托管**：密钥上收到接入层；应用改带服务身份。这是**投入最小、见效最快**的一步——不需要动归一化。
- **归一化边界**：先定"必归字段清单"（消息 / 工具 / 流式 / 用量 / 错误 / 控制参数六类），再写往返测试。
- **档位标签**：应用里不再写模型名，只写档位（`flagship` / `mid` / `economy`）；映射在接入层配置里。

**具体数字（档位标注）**：

- 归一化层的延迟开销：`1–10 ms` 量级【经验，不含端点耗时；随是否跨网络与校验深度浮动】。
- 用量口径对账：接入层记账与厂商账单按月比对，**差异控制在 5% 以内视为口径对齐**【经验：常见差异来自系统提示是否计入与思考 tokens 是否计入】。
- 换档成本：从"改 7 处 + 发版"降到"改一行配置"。

**失败教训**：**第一版只做了透传 + 计量，没做归一化**——结果是"账能对上，但换档仍要改代码"。教训：透传只是过渡态（§4.4 的第 1 步），**归一化才算真的建了接入层**。

### 6.2 形态二：多租户计费网关（对应 §3.2.3 的计量 + 平台配额）

**背景与挑战**：接入层要服务多个业务线，且业务线要求"自己的消耗算自己的账"。此前只有一张总账单，分摊靠人肉按会话数估算。

**触发点**：季度结算争议——两个业务线对分摊比例各执一词，**没有任何一方能拿出可信的计量证据**。

**详细做法**：

- **记账字段补齐**：`tenant / app / session / endpoint / model_version / cache_hit` 全部落库（§4.2（6）的流水表）。
- **预扣后结算**：调用前按上限预扣、调用后按实际结算并退差额；每天跑一次"未配对预扣"的对账任务并释放泄漏项。
- **与平台配额统一**：模型侧与工具侧共用同一套租户配额（避免两套口径）。
- **口径对齐**：每月把接入层记账与厂商账单做一次差异分析，差异项**逐条解释**（不是记个数字了事）。

**具体数字（档位标注）**：以"每请求平均 `1k` input + `200` output tokens"【经验，随任务复杂度浮动】估算，记账流水行数是请求数的 **2 倍**（预扣 + 结算）——**存储量级按"请求数 × 2 × 单行字节数"估**，保留期建议热 90 天、温 1 年，超过后只留聚合结果【推算：口径同上；具体字节数取决于你的字段宽度】。

**失败教训**：**先做事后统计、后补预扣**——补上预扣之后才发现历史三个月的数据无法追溯（只有统计口径，没有流水）。教训：**记账点只能有一个，而且它必须在调用前就存在**；没有流水的历史，永远补不回来。

### 6.3 形态三：合规出域网关（对应 §3.2.5 的出网策略）

**背景与挑战**：部分租户（受监管业务）的数据不允许发往外部端点；平台需要**在技术上保证**这一点，而不是靠"应用自觉"。

**触发点**：一次审计——审计方问"你怎么证明受监管数据没有发往外部模型"，团队只能回答"我们的代码里没这么写"。

**详细做法**：

- **出网白名单**：默认拒绝，按租户分级放行；受监管租户只允许命中自托管端点。
- **端点分类**：把端点分成 `self_hosted` / `public_vendor` 两类，路由的硬约束里带出网判定（**不满足即出局，不是权重**）。
- **可核验的审计动作**：① 网关拒绝日志（含租户与端点类别，不含内容）；② 受监管租户的端点分布报表（应 100% 落在自托管）；③ 一次演练：让受监管租户的请求指向外部端点，验证被拒绝——**"演练过拒绝"比"承诺不发送"有力得多**。
- **日志脱敏**：密钥与内容在写日志前自动剥离（§4.2（4）的 `log_scrub`）。

**具体数字（档位标注）**：合规端点的成本差是决定性的——自托管端点的固定成本（GPU 或预留实例）与按量计费的外部端点**不在同一成本函数上**：前者是台阶（无论用多少都要付），后者是线性【经验】。因此**受监管租户的单位成本通常高于公开端点租户**，这个差值应在报价与内部结算里体现，而不是被平均掉。

**失败教训**：**把"合规"实现成配置开关而不是路由硬约束**——第一版把出网判定写在了应用侧（"应用不传敏感内容就行"），结果一次新应用上线后直接调了外部端点。教训：**合规判定必须在唯一出口上强制执行**（与 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的"出口收口"同一条理）。

### 6.4 真实落地路径（基于上述三种形态提炼）

三种形态拼起来是一条顺序固定的路径，与 §4.8 对应：

1. **先收凭证、再定归一化边界**（形态一）——投入最小、见效最快；归一化做完，"换模型不改代码"才成立。
2. **再建记账点与配额统一**（形态二）——记账点必须在调用前存在；与平台配额共用一套口径。
3. **最后做出网分级与审计动作**（形态三）——它是前两步的**合规封装**：只有在唯一出口上，出网判定才可强制执行。

**顺序的反面**：先做合规策略、后建唯一出口——策略会因为没有强制执行点而形同虚设。

### 6.5 踩坑与经验（三种形态提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 只透传不归一化 | 换档仍要改代码 | 接入层只剩一跳 | 补必归字段与往返测试 |
| 记账点在应用侧 | 账单拆不开、口径不一 | 无法结算 | 记账点上收到网关（调用前） |
| 预扣不带对账 | 额度"被占着"但没人用 | 配额被泄漏的预扣挤占 | 每天对账未配对预扣并释放 |
| 出网判定写在应用侧 | 新应用绕过 | 合规事故 | 出网判定进路由硬约束 |
| 语义缓存无禁用清单 | 数值题出现旧答案 | 静默错误传播 | 按任务类型禁用 + 每周抽检 |
| 影子对比无停止条件 | 成本翻倍 | 优化变事故 | 影子带停止阈值与样本量 |
| 跨端点自动重试 | 同一请求两家都执行 | 成本翻倍、结果不可比 | 重试默认限定同端点 |
| 降级不标注 | 复盘无法区分结论来源 | 决策依据不可追溯 | 事件流与留痕加 `degraded` |

### 6.6 ROI 评估（三个形态的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 换档效率 | 一次档位调整的端到端时长与改动文件数 | 从"改多处 + 发版（天级）"降到"改配置（分钟级）" | 统计最近 5 次档位调整的改动文件数 |
| 凭证轮换 | 轮换一次的耗时与需发版的应用数 | 从"改多处 + 多次发版（天级）"降到"一处轮换（分钟级）" | 记录上次轮换的实际耗时 |
| 路由收益 | 经济档承接比例 × 单请求价差 | 高重复低复杂度任务可承接**三成到七成**流量（取决于评测集结论） | 用评测集量一次"经济档能否达标" |
| 缓存收益 | 命中数 × 单请求成本 ×（1 − 质量折损） | 精确缓存命中率**个位数到两成**；语义缓存更高但只在解释类允许 | 统计一周的重复请求占比 |
| 接入层自身成本 | 实例 + 计量存储 + 运维 | 相对端点成本通常在**百分之几**量级 | 按月核算两者之比（> 10% 即过重） |

**读法**：前三项（换档、轮换、路由）是**效率与治理收益**，第四项是**成本收益**，第五项是**代价**。接入层最容易在"第五项"上翻车——它一旦过重，所有收益都被吃掉。

> 本节小结：三种形态的先后顺序不是偏好而是依赖——**凭证托管是第一步**（投入最小），**归一化边界是接入层成立的前提**（没有它，换模型仍要改代码），**记账点必须在调用前**（否则历史补不回来），**出网判定必须落在唯一出口上**（否则策略形同虚设）。三次失败教训指向同一件事：**接入层的价值不在"多了一层"，而在"这一层上有什么是不可绕过的"**。

> 💡 **思考锚点**：从 §6.1–§6.3 里挑一个与你当前处境最像的形态，只做一件最小的事——按它列出的"判据"跑一次自测（换一次档位看改动几处 / 拆一次账单看能不能对上 / 演练一次出网拒绝）。哪一件你**今天就能做**，就先做它：能被立刻验证的缺口，优先级永远高于推断出来的缺口。
