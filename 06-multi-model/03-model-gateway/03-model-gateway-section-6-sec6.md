## 6. 落地实践

> - **§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证。
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 微软"**把限流单位从"请求数"改成"token 数"：计量单位的改变带来一整套配套机制 2+ 年**"（2023-2024）

**背景（Why）**

用 API 网关给大模型做限流时，最自然的选择是复用既有的**请求数限流**——但它在模型场景下几乎立刻失效：

- **请求之间的成本差异是数量级的**——一次 200 token 的问答和一次塞进 3 万 token 上下文的长任务，在请求数口径下各计一次，而实际消耗相差百倍以上；
- **配额失去约束力**——按请求数限流的租户可以把每个请求都开到最大上下文，账单照样穿透预算；
- **容量无法预估**——端点侧的瓶颈是算力（与 token 数相关），不是连接数（与请求数相关），因此请求数限流保护不了端点。

**触发点（What）**

微软在其 API 网关产品里为 AI 类接口提供了**按 token 计的限流能力**（[微软公开材料 2023-2024]，核验入口是该产品的官方策略文档，**按当前版本核**）：配额可以在"每分钟 token 数"这个单位上定义，并按订阅 / 产品维度作用与作用域。它对接入层的启示不在"多了个策略"，而在**计量单位一旦换成 token，一整套配套机制就必须跟着换**：

- **限流发生在哪一刻**——token 数只有等响应结束才知道，因此需要**预估**（prompt token 精确可算、completion 需按上限预估）；
- **超限怎么处理**——是拒绝（429）还是截断上下文；
- **计量与限流是不是同一套数**——如果限流按预估、账单按实际，两者必然有差异，差异要有解释。

**详细做法（How）**

**① 预扣与结算分离（核心，也是本主题 §4.2（6）的通用形态）**

- **关键设计**：把"消耗"拆成**两笔流水**——调用前按估算上限**预扣**，调用后按实际用量**结算**并退还差额。
- **关键性质**：**只有在调用前拦截，配额才构成约束**；只做事后统计的配额，在超发那一刻已经来不及（§3.5 的「计量事后统计」反模式）。
- **关键示意**：

  ```text
  为什么 token 计量必须拆成两笔流水
    请求 → ① 数 prompt tokens（可精确计算）
          ② 估 completion 上限 = max_output_tokens（配置值）
          ③ 预扣 = f(prompt) + max_output_tokens
          ④ 调用端点
          ⑤ 结算 = f(prompt) + f(实际 completion)
          ⑥ 退还 = 预扣 − 结算
    ────────────────────────────────────────────────
   若只做 ⑤：超发发生在观测之前 → 配额无约束力
   若只做 ③：额度被"占着"，需每天对账未配对预扣并释放
   判据：配额是否在"调用发生前"就已扣减
  ```

**② 计量字段必须能支撑"单位换算"**

- **关键设计**：流水里要同时存 **prompt / completion / 缓存命中 / 思考 token** 各自的量，而不是只存一个"总 token"。
- **为什么**：**同一个"总 token"在不同厂商的账单里含义不同**（系统提示是否计入、缓存命中是否按折扣计、推理型模型的内部思考 token 是否单独计费）——这正是 §6.1 的"差异控制在 5% 以内视为口径对齐"里那 5% 的来源。**只存总量，差异就无法归因到具体是哪一类 token。**

**具体数字（档位标注）**

- 预扣倍率与预算的关系：设单请求 prompt `1k`、`max_output_tokens` 设 `2k`，则每次调用的预扣是 `3k`，而实际平均 completion 可能只有 `200`——**预扣是实际消耗的十几倍**【推算：3k ÷ 0.2k = 15；这个倍率直接决定"同一份预算能支撑多少并发在途请求"】。**因此 `max_output_tokens` 不是越大越好**：它每加一倍，等效可用预算就减半。
- 记账存储量级：流水行数是请求数的 **2 倍**（预扣 + 结算），保留期建议热 90 天、温 1 年，之后只留聚合【推算：存储量 = 请求数 × 2 × 单行字节数；单行字节数取决于你的字段宽度】。
- 用量对账差异：与厂商账单按月比对，**差异控制在 5% 以内视为口径对齐**【经验：常见差异来自系统提示是否计入与思考 token 是否计入】。
- **自测动作**：把你的 `max_output_tokens` 配置值与实测 completion 的 P99 比一下。**若前者超过后者 5 倍以上，你的配额里有一大块是被预扣占着、永远用不到的。**

**失败教训**

**第一版沿用了 API 网关的请求数限流**——理由是"网关本来就有这个能力"。结果是两个租户用同样多的请求数产生了相差两个数量级的账单，配额完全没有约束力。教训：**计量单位不是实现细节，它是配额的语义**——换计量单位等于换了一整套配额机制，配套的预扣、结算、对账、差异解释都必须跟着换。

### 6.2 开源网关族（LiteLLM / One-API 一类）"**把归一化做成配置，把治理留给使用方 3+ 年**"（2021-2024）

**背景（Why）**

多厂商接入里最不值得自研的是**归一化**：它随厂商接口变化，变化频繁、模式重复、可由社区共同承担。但最不能外包的是**计量与合规**：它们跟随你自己租户与合规口径的变化，一旦出错直接影响账单与审计结论。

- **归一化的变化来源在外部**——厂商改流式格式、加用量字段、调错误码，你只能跟；
- **治理的变化来源在内部**——租户划分、配额策略、出网分级，由你的组织决定，且没有"行业通用答案"。

**触发点（What）**

一组开源接入层项目把"多厂商归一化"做成了**配置 + 适配层**（[开源项目公开材料 2021-2024]，核验入口是各项目的仓库与文档，**按当前版本核**；本主题只描述这一类项目的**机制形状**，不比较具体项目）。它们的共同形状是：

- **对外暴露一套内部模型**（统一的请求 / 响应 / 错误结构），把厂商差异收在适配层；
- **路由与回退以配置表达**（模型别名、优先级、重试链）；
- **计量与配额通常提供"用量记录"这一层，但不提供"按租户预扣并结算"的完整语义**。

**详细做法（How）**

**① 切分的判据是"变化的来源"，不是"实现的难易"**

- **关键设计**：**跟随外部变化的（归一化、路由适配）交给社区；跟随内部口径的（计量、配额、审计、出网）自己拿**。
- **为什么这样切**：**外部变化有"可回归测试"的性质**——你可以在固定测试集上验证升级前后行为一致；而内部口径的变化没有客观基准（"该给这个租户多少额度"没有标准答案），因此**它的判断权必须留在组织内部**。
- **一个可核查的准入条件**：**上这个模式之前，先看你的回归测试集存不存在**。没有测试集时，开源网关的每一次升级都是一次行为变更，而你不会在升级时发现它（§3.2.4 的失效点）。

**② 治理代理的前置与旁挂**

- **关键设计**：自建治理面有两种落点——**前置**（治理代理在网关之前，网关只知道"这是一个已授权的请求"）与**旁挂**（网关先走，治理面旁路观察与记账）。
- **两者的差别**：前置能**拦截**（配额不足直接拒绝），旁挂只能**记录**（事后发现）。**若你的目标里有"配额必须有约束力"，就必须前置**；旁挂适合"先观测后治理"的过渡期。

**具体数字（档位标注）**

- 两跳的延迟叠加：治理代理 + 网关两跳均为 `1–10 ms` 量级【经验，不含端点耗时】，合计进入个位到十位毫秒区间——**相对端点耗时（通常数百毫秒到秒级）可忽略，但在流式首字节场景下它直接进 TTFT**。
- 升级风险的量化：每次升级的影响面 ≈ `厂商数 × 被改动的能力组合数`【推算：回归测试集若按"厂商 × 能力"笛卡尔积覆盖，则测试规模与该乘积同阶；这是"要不要自建归一化"时最容易被低估的一项成本】。
- **自测动作**：数一下你的回归测试集覆盖了多少个"厂商 × 能力"组合；再数一下你实际用到的组合数。**两个数差得越多，升级风险越不可见。**

**失败教训**

**第一版把配额也交给开源网关的默认实现**——默认语义是"限流"（单位时间的请求频率），而业务要的是"按租户预扣并结算"。结果：**限流一直在生效，但账单照样穿透预算**，而团队因为"配额已经配了"而迟迟没有发现语义不对。教训：**看一个组件能不能承担某件事，要看它的语义，不是看它的功能列表**——"有 quota 字段"和"是预扣结算语义"是两件事。

### 6.3 Anthropic"**把工具 / 资源 / 提示的接入协议化：集成成本从平台转移到协议层 1+ 年**"（2024-2024）

**背景（Why）**

在工具接入协议化之前，**每一个平台都要自己定义一遍工具描述格式**：名称怎么写、参数 Schema 用哪个方言、错误怎么分类、权限怎么声明。这带来两个后果：

- **同一个工具要接 N 遍**——N 个平台各写一份适配，工具的维护者对每一种平台都要跟；
- **生态无法复用**——一个工具的实现只对定义它的那个平台有意义。

**触发点（What）**

Anthropic 于 2024 年公开了工具 / 资源 / 提示的标准化接入规范（MCP 一类；见 §3.2.6，**规范与实现可按规范当前版本核**【公开】）。它的机制是**把"工具怎么被描述与调用"从平台私有实现提升为跨平台协议**：第三方工具按协议实现一次，多个平台可发现与调用。

**详细做法（How）**

**① 明确协议解决什么、不解决什么（本条最有价值）**

- **协议解决**：工具的描述与调用形态（名称、输入 Schema、能力语义）、发现方式；**因此它把"接入 N 次"降为"实现一次"。**
- **协议不解决**：**谁能调**（权限）、**调了多少**（计量）、**调了什么**（审计）、**重调一次会不会重复**（幂等）。这四件恰好是治理面的全部内容——**它们不是协议遗漏，而是协议不该管**：权限与配额是组织内部的口径，不可能有跨组织的标准答案。
- **因此结论是一条选型结论**：**协议化之后，平台的差异化从"接入多少工具"转向"治理做得多严"**（§5.3.2）。**如果你的平台价值主张是"接入的工具多"，协议普及之后这个主张会消失。**

**② 接入前先落治理（顺序不能反）**

- **关键设计**：先把治理四项（权限 / 计量 / 审计 / 幂等）落在唯一出口上，再接入协议工具；反过来则会出现"什么都能调、什么都不知道"的平台。
- **判据**：随机挑一个已接入的工具，回答"哪个租户在什么时候调过它、调了多少次、超配额时会发生什么"——**三问答不全，说明协议接入跑在了治理前面。**

**具体数字（档位标注）**

- 集成成本形状的变化：接入 `N` 个平台 × `M` 个工具的适配工作量，从 `O(N × M)` 降到 `O(M + N)`【推算：协议化前每个平台各写一份 M 个工具的适配；协议化后 M 个工具按协议实现一次、N 个平台各实现一次协议客户端，故为 M + N】。**这是协议化唯一可量化的收益形状**，也是判断"值不值得迁"的依据。
- **自测动作**：数一下你现在维护着几份"同一个工具的适配"（同一工具在不同平台 / 不同应用各写一遍）。**数量大于 1 的部分，就是协议化能省掉的部分。**

**失败教训**

**第一版把协议接入当成了"生态建设"的终点**——工具接进来了，权限与计量还没做，于是"能调"变成了"敢不敢让人调"的问题；真正上线时不得不把大部分工具又关掉。教训：**协议降低的是"接入"的成本，不是"放行"的成本**；后者由治理面决定，与协议无关。

### 6.4 某股份制银行"**把出网判定做成路由硬约束：合规从"应用自觉"变成"不可绕过" 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

部分租户（受监管业务）的数据不允许发往外部端点。团队此前的做法是"在开发规范里写明"，并靠代码评审把关。

**触发点（What）**

一次审计——审计方问"你怎么**证明**受监管数据没有发往外部模型"，团队的回答是"我们的代码里没这么写"。**这句话在审计里不成立**：它证明的是意图，不是事实。

**详细做法（How）**

**① 出网判定进路由硬约束（核心修正）**

- **关键设计**：把端点分成 `self_hosted` / `public_vendor` 两类，**租户 → 可去端点**写成机器可读的表；路由时先做这一步判定，**不满足即出局，不是权重**。
- **为什么必须是硬约束**：**权重可以被"综合打分"绕过**（某个实现只要在打分时给一点灵活性，合规就成了可调项）；门槛不能。这与本主题 §7.1 第 1 条判据（部署边界是门槛不是权重）是同一条理。

**② 三个可核验的审计动作**

| 动作 | 产出 | 为什么它比"承诺"有力 |
| --- | --- | --- |
| 拒绝日志 | 含租户与端点类别（**不含内容**）的拒绝记录 | 证明"系统在拦"，且拦的动作可数 |
| 端点分布报表 | 受监管租户的端点分布（应 **100%** 落在自托管） | 把"没有违规"变成"分布符合预期"这个可观测量 |
| 一次演练 | 让受监管租户的请求指向外部端点，验证被拒绝 | **"演练过拒绝"是唯一能证明拦截存在的证据** |

**③ 日志脱敏前置**

- **关键设计**：密钥与内容在写日志前自动剥离（§4.2（4）的 `log_scrub`）。
- **为什么放在这条案例里**：合规的举证材料是**拒绝日志**，而拒绝日志里如果夹带了被拒绝请求的内容，**举证材料本身就成了泄漏面**——这正是本主题 §3.2.5 失效点"密钥进日志"的同族。

**具体数字（档位标注）**

- 合规端点的成本差是决定性的：自托管端点的固定成本（GPU 或预留实例）与按量计费的外部端点**不在同一成本函数上**——前者是台阶（无论用多少都要付），后者是线性【经验】。因此**受监管租户的单位成本通常高于公开端点租户**，这个差值应在报价与内部结算里体现，而不是被平均掉。
- 审计举证的时间量级：把"能不能举证"变成一个可执行的检查（跑一次演练 + 导一次报表）后，**单次举证的耗时从"跟审计方来回解释"降到"导两张表"**【经验：随你的留痕字段完整度浮动】。
- **自测动作**：现在就能做的唯一验证——**让一个受监管租户的请求指向外部端点，看它会不会被拒**。若不会被拒（或需要改配置才能拒），说明出网判定还没有落在唯一出口上。

**失败教训**

**把"合规"实现成配置开关而不是路由硬约束**——第一版把出网判定写在了应用侧（"应用不传敏感内容就行"），结果一次新应用上线后直接调了外部端点。教训：**合规判定必须在唯一出口上强制执行**（与 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的"出口收口"同一条理）；而"配置开关"与"路由硬约束"的差别正是**可不可以被绕过**。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条顺序固定的路径，与 §4.8 对应：

1. **先收凭证、再定归一化边界**（§6.2 的起点）——投入最小、见效最快；归一化做完，"换模型不改代码"才成立。
2. **再建记账点与配额统一**（§6.1）——记账点必须在调用前存在；与平台配额共用一套口径；计量单位（token 而非请求数）决定了配额的语义。
3. **出网判定进路由硬约束并配备审计动作**（§6.4）——它是前两步的**合规封装**：只有在唯一出口上，出网判定才可强制执行。
4. **最后消费协议化带来的接入红利**（§6.3）——但要**先落治理再接协议**，否则得到的是"什么都能调、什么都不知道"。

**顺序的反面**：先做协议接入 / 先做合规策略、后建唯一出口——两者都会因为没有强制执行点而形同虚设。**这条反面在两处出现，说明它不是偏好问题：凡是"策略"，都必须先有一个"不可绕过的执行点"。**

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 只透传不归一化 | 换档仍要改代码 | 接入层只剩一跳 | 补必归字段与往返测试 |
| 按请求数限流 | 大请求打满配额、小请求额度闲置 | 配额口径与实际消耗不成比例 | 换 token 计量 + 预扣结算（§6.1） |
| `max_output_tokens` 设得过大 | 预算被预扣占满，实际用量很低 | 等效可用预算被腰斩 | 按实测 completion P99 收紧预扣上限 |
| 记账点在应用侧 | 账单拆不开、口径不一 | 无法结算 | 记账点上收到网关（调用前） |
| 预扣不带对账 | 额度"被占着"但没人用 | 配额被泄漏的预扣挤占 | 每天对账未配对预扣并释放 |
| 只存"总 token" | 与账单有差异但无法归因 | 差异无法解释 | 分存 prompt / completion / 缓存 / 思考 token |
| 出网判定写在应用侧 | 新应用绕过 | 合规事故 | 出网判定进路由硬约束 |
| 把配额交给开源网关默认实现 | 限流生效但账单穿预算 | 语义不对，配额无约束力 | 治理面前置，语义自查 |
| 开源网关升级无回归测试集 | 升级即行为变更，生产才发现 | 行为变化不可归因 | 先建"厂商 × 能力"测试矩阵再上 |
| 先接协议后落治理 | 工具能调但不敢放行 | 接入完成、上线卡住 | 先落治理四项再接协议（§6.3） |
| 拒绝日志带内容 | 举证材料本身成为泄漏面 | 合规材料的二次泄漏 | 日志脱敏前置（`log_scrub`） |
| 语义缓存无禁用清单 | 数值题出现旧答案 | 静默错误传播 | 按任务类型禁用 + 每周抽检 |
| 跨端点自动重试 | 同一请求两家都执行 | 成本翻倍、结果不可比 | 重试默认限定同端点 |
| 降级不标注 | 复盘无法区分结论来源 | 决策依据不可追溯 | 事件流与留痕加 `degraded` |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——接入层的收益形态是"时长与口径"，不是"百分比"。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 换档效率 | 一次档位调整的端到端时长与改动文件数 | 从"改多处 + 发版（天级）"降到"改配置（分钟级）" | 统计最近 5 次档位调整的改动文件数 |
| 凭证轮换 | 轮换一次的耗时与需发版的应用数 | 从"改多处 + 多次发版（天级）"降到"一处轮换（分钟级）" | 记录上次轮换的实际耗时 |
| 路由收益 | 经济档承接比例 × 单请求价差 | 高重复低复杂度任务可承接**三成到七成**流量（取决于评测集结论） | 用评测集量一次"经济档能否达标" |
| 缓存收益 | 命中数 × 单请求成本 ×（1 − 质量折损） | 精确缓存命中率**个位数到两成**；语义缓存更高但只在解释类允许 | 统计一周的重复请求占比 |
| 计费可结性 | 能否按租户拆出账单并与厂商账单对上 | 从"人肉分摊"到"可举证" | 当场按租户拆一次账单，比一次差异 |
| 合规可举证性 | 单次举证所需时间与材料数 | 从"来回解释"到"两张表 + 一次演练" | 跑一次演练并导一次端点分布报表 |
| 接入层自身成本 | 实例 + 计量存储 + 运维 | 相对端点成本通常在**百分之几**量级 | 按月核算两者之比（> 10% 即过重） |

**读法**：前四项是效率与成本收益，第五、六项是**治理收益**（能不能结账、能不能举证），最后一项是**代价**。接入层最容易在最后一项上翻车——它一旦过重，所有收益都被吃掉。**另一条读法**：第五、六项的收益是"从不能到能"，没有百分比可比——**这类收益通常比前四项的百分比收益更重要**，因为它们决定的是"这件事能不能做"，而不是"做得多快"。

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**凭证托管是第一步**（投入最小），**归一化边界是接入层成立的前提**（没有它，换模型仍要改代码），**记账点必须在调用前**（否则历史补不回来），**出网判定必须落在唯一出口上**（否则策略形同虚设），**协议化只降低接入成本、不降低放行成本**。四次失败教训指向同一件事：**接入层的价值不在"多了一层"，而在"这一层上有什么是不可绕过的"**——凡是策略，都必须先有一个不可绕过的执行点。

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你当前处境最像的案例，只做一件最小的事——按它列出的"判据"跑一次自测（换一次档位看改动几处 / 拆一次账单看能不能对上 / 数一次同一个工具的适配份数 / 演练一次出网拒绝）。哪一件你**今天就能做**，就先做它：能被立刻验证的缺口，优先级永远高于推断出来的缺口。
