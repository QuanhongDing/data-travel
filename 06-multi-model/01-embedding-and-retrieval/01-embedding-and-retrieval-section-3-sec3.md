## 3. 设计模式与范式

> 原 § 3 共 169 行：8 个模式各配一块流程示意（共 8 块、16 个围栏），每个模式只有「优点 / 缺点 / 适用」三行结论，索引与存储结构只以标签形式出现在图里（如「ANN 索引（HNSW）」），无失效条件、无真实使用；另有 10 行决策表与 10 条反模式。重写为 ~300 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

把「Bi-Encoder + ANN」「Hybrid」「Late Interaction」并列成一张表，会让人以为它们是同一道题的不同解法。它们不是同一道题。**每个模式都是某一条约束被顶到极限之后剩下的那个解**：文档量到亿级、语义匹配在标识符上必然出错、长文档分块必然丢信息、索引内存放不下——每一条都单独否掉一批方案，活下来的那个才成为「模式」。

所以正确的顺序不是「先选模式、再检查适不适合」，而是「先量约束、再看哪几个模式还没被否掉」。同是「企业知识库检索」，语料是十万份 PDF 还是十亿条行为日志，正确答案完全不同：前者的问题是「一块 chunk 切多长」，后者的问题是「索引放内存还是放磁盘」。

下面六条约束，任一条不同，结论就不同。第三列是它最容易推翻的那个直觉。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态与写入模式 | 向量是一次写入还是持续增量（决定索引能否增量维护，还是必须定期重建） | 「先选模型再搭索引」——写入模式先否掉了不能增量维护的索引 |
| 访问模式（点查 / 扫描 / 聚合） | 元数据过滤发生在向量检索之前还是之后（pre-filter 与 post-filter 的召回率并不相同） | 「ANN 是纯向量近似」——真实查询几乎总带过滤条件，过滤方式会改变召回 |
| 变更频率与历史要求 | 语料更新频率、历史版本是否仍需可检索（决定 chunk 失效策略与重编码范围） | 「换模型只是改一行配置」——向量空间不兼容，换模型 = 全量重编码 |
| 一致性要求 | 从「文档写入」到「可被检索到」的可接受延迟 | 「写入即能搜到」——ANN 索引有构建与刷新窗口 |
| 规模与成本约束 | 是否压缩向量（量化 / 低维截断）、索引驻内存还是驻磁盘 | 「精度只取决于模型」——同一模型下，索引参数与压缩率对召回的影响同样大 |
| 团队技能与运维能力 | 两段式、多级重排是否值得维护（每加一级就多一个模型、一段延迟、一套评估） | 「加重排总是更好」——重排把评估面从一个变成两个 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 Bi-Encoder + ANN 检索（标准召回模式）

- **被什么约束逼出来**：文档量到百万级以上时，query 与每篇文档逐一交互的算力不可接受。
- **结构**：

```sql
-- 约束落到表结构上：向量是列，相似度是索引
CREATE TABLE doc_chunk (
  chunk_id   BIGINT PRIMARY KEY,
  doc_id     BIGINT NOT NULL,
  chunk_no   INT    NOT NULL,
  content    TEXT   NOT NULL,
  embedding  VECTOR(1024) NOT NULL,   -- 维度由模型固定；换模型 = 全表重编码
  updated_at TIMESTAMPTZ NOT NULL
);
CREATE INDEX idx_chunk_hnsw ON doc_chunk USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);   -- 示例参数，以 pgvector 官方文档当前版本为准
```

- **为什么这样设计有效**：因为 query 与文档各自独立编码，文档向量能在离线一次算好、只存一份，在线只剩「编码 query 一次 + 图索引上一次近似遍历」，所以单次检索的在线算力与语料总量解耦。
- **代价**：① 编码时 query 与文档互不可见，交互信息在编码阶段就丢了；② 索引通常常驻内存（【推算】推导链：1 亿 × 1024 维 × 4 字节 ≈ 410 GB，尚未计入图边与副本，故亿级 1024 维全精度常驻内存不现实）；③ 换编码模型必须全量重编码并重建索引。
- **失效点**：当查询含标识符、订单号、罕见专名时，「语义最相近」会反转成「答非所问」，因为双编码器把只差一两个字符的字面串压进了同一片邻域——`A12345` 与 `A12346` 几乎重合。
- **真实使用**：HNSW 由 Malkov 与 Yashunin 提出（arXiv:1603.09320, 2016），此后成为 Milvus / Qdrant / Weaviate / pgvector 的默认或首选索引之一（【公开：各项目官方文档，可按项目名检索核验，以当前版本为准】）。

#### 3.2.2 Bi-Encoder + Cross-Encoder 重排（召回 + 精排模式）

- **被什么约束逼出来**：双编码器丢掉的交互信息，无法靠调大候选数补回来——把 K 从 10 提到 1000，只会把噪声一起提上来。
- **结构**：

```text
两级检索的分数不同量纲，不可直接比 —— 这是工程上最常见的坑
  第一级 Bi-Encoder    ：余弦相似度，全局可比，但只回答"方向像不像"
  第二级 Cross-Encoder ：对 (q, doc) 联合编码后输出相关性分数
────────────────────────────────
q → Bi-Encoder → Top-K 候选（K 常取几十到几百【经验】）
                     │
                     └→ 每个 (q, doc_i) 独立打分 → 按第二级分数重排 → Top-N → LLM
────────────────────────────────
关键：第一级的分数只用来"取候选"，绝不能用来定阈值
      阈值必须标定在第二级分数上，因为只有第二级回答"到底相不相关"
```

- **为什么这样设计有效**：因为第二级把 query 与每篇候选放进同一个注意力上下文里联合编码，token 级交互得以保留，所以「语义接近但其实无关」的候选会被真正压下去——而这份算力只按候选数计费，不按语料规模计费。
- **代价**：延迟随 K 线性增长（每个候选都要过一次完整前向）；并引入第二套评估口径——召回指标与最终排序指标必须分开测，否则无法判断错在召回还是错在重排。
- **失效点**：当第一级没把正确文档放进 Top-K 时，重排再强也救不回来——精排的收益上限由召回率封顶，K 只抬高上限、不提高精度；此时继续加重重排预算，是把钱花在一个已经封死的天花板上。
- **真实使用**：两段式「先召回再精排」在 MS MARCO 上被系统验证（Nogueira & Cho, arXiv:1901.04085, 2019）；可比较的双编码器句向量由 Sentence-BERT 确立（Reimers & Gurevych, arXiv:1908.10084, 2019）【公开：论文可按编号检索核验】。

#### 3.2.3 Late Interaction（ColBERT 系）模式

- **被什么约束逼出来**：长文档切成 chunk 之后，跨 chunk 才能拼出的答案，无法被任何单 chunk 的向量召回。
- **结构**：

```text
文档侧（离线）：每个 token 一个向量，一个文档 = n 个向量
   doc「押金退还周期为 7 个工作日」 → [v1 v2 … vn]
查询侧（在线）：每个 token 一个向量
   query「押金多久退」 → [q1 q2 … qm]
相似度 = Σ_j max_i (q_j · v_i)      ← MaxSim：每个查询词找文档里最像的那个词
────────────────────────────────
存储放大的推导链：
  同一篇文档，从"1 个向量"变成"n 个向量"，n = 文档 token 数
  → 未压缩时，索引存储相对单向量方案放大 ≈ n 倍（n 由截断长度封顶）
  → ColBERTv2 的残差压缩把每个 token 向量压到远小于全精度
  → 实际放大 ≈ n ÷ 压缩率，随截断长度与压缩率共同变化【推算】
```

- **为什么这样设计有效**：因为相似度计算被推迟到检索时、并按 token 取 max，所以「哪个词对上哪个词」这个信息被保留下来——数字、条款号、专名的精确命中不会像双编码器那样被语义近似抹平。
- **代价**：每文档 n 个向量，索引规模与构建时间随 token 数线性上升；检索时每个查询 token 都要与文档向量做一次比较，在线算力高于单向量检索。
- **失效点**：当文档本来就被切得很短（几十个 token）时，「token 级精确匹配」反转成纯粹的存储与算力负担，因为短文档的交互信息本来就少，MaxSim 相对单向量的召回增益补偿不了索引膨胀。
- **真实使用**：ColBERT（Khattab & Zaharia, arXiv:2004.12832, 2020）、ColBERTv2 的残差压缩（Santhanam et al., arXiv:2112.01488, 2022）、基于它的检索引擎 PLAID（arXiv:2205.09707, 2022）、面向文档图像的 ColPali（arXiv:2407.01449, 2024）【公开：论文可按编号检索核验】。

#### 3.2.4 Hybrid Retrieval（混合检索）模式

- **被什么约束逼出来**：语义匹配在字面匹配上必然出错（标识符、数字、专名），而任何单一表示都无法在这两类匹配上同时最优。
- **结构**：

```text
两路召回 + 融合 —— 融合函数决定混合检索的成败
  ① 稠密路：embedding → ANN 索引 → 按距离排序
  ② 稀疏路：BM25 倒排，或学习型稀疏表示 → 按权重排序
────────────────────────────────
两路分数不同量纲，不能直接相加：
  RRF：score(d) = Σ_r 1 / (k + rank_r(d))   ← 只用排名，不用原始分数，无需归一化
  加权：必须先各自归一化，而归一化方式本身会改变最终结果
  → 先用 RRF 拿到可复现的基线，再决定是否值得引入权重
────────────────────────────────
融合之后的候选集，再接第二级 Cross-Encoder 精排（见 3.2.2）
```

- **为什么这样设计有效**：因为两路召回的失败模式不重叠——稠密路漏字面精确匹配，稀疏路漏同义改写——所以取并集（而非交集）后，被任一单路漏掉的正确答案仍留在候选里，融合函数只需负责把它们排上去。
- **代价**：维护两套索引、两条写入链路、两套分词与语料处理；两套索引之间的一致性（同一文档在两边都存在且都是最新版本）成为新的运维面。
- **失效点**：当语料以短文本与专名为主（商品编码、工单号）时，稀疏路几乎总能赢，「混合」反转成拖慢检索、抬高维护成本的冗余——因为此时语义路带来的增量召回接近于零。
- **真实使用**：RRF 由 Cormack 等人提出（SIGIR 2009），是多路结果融合的经典做法；BGE-M3 在同一个模型里同时输出稠密、稀疏与多向量三路表示（Chen et al., arXiv:2402.03216, 2024）【公开：论文可按编号检索核验】。

#### 3.2.5 Multi-Stage Reranking（多级重排）模式

- **被什么约束逼出来**：单级重排的精度上限被上一级的候选集封住，而高价值场景（法律、医疗、金融）愿意为最后几个百分点的精度付费。
- **结构**：

```text
级联：每一级只对上一级的输出做更贵的计算
   全量语料 ──[廉价、可并行]──► Top-1000
                              ──[中等成本]──► Top-100
                                             ──[最贵、最准]──► Top-10
────────────────────────────────
成本模型（决定级联是否划算）：
   总成本 ≈ N1×c1 + N2×c2 + N3×c3，且 N1 ≫ N2 ≫ N3、c1 ≪ c2 ≪ c3
   → 只要级数之间的量级差足够大，总成本就由最廉价的一级主导
────────────────────────────────
级联成立的唯一前提：每一级必须"高召回、低精度"
   廉价级一旦变成"高精度、低召回"，后面所有级都在错误的候选集里精挑
```

- **为什么这样设计有效**：因为候选量按数量级递减、而单次打分成本按数量级递增，两者相乘后总成本由最廉价的一级主导，所以能用接近粗排的预算，买到接近「全量语料都过最贵模型」的精度。
- **代价**：延迟是各级之和（无法并行）；暴露面按级数翻倍——任何一级的模型版本、资源配额、超时都会改变最终结果，排障必须按级定位。
- **失效点**：当廉价级被调成「高精度、低召回」（例如把 Top-K 压得很小）时，级联反转成昂贵的精度陷阱——指标看起来更好，但正确答案早已在第一级被丢掉，后面几级只是在错误的候选集里反复挑选。
- **真实使用**：级联式排序是工业检索系统的通用结构，多数团队的做法是「召回模型 + 一个可替换的重排模型」，再按线上指标决定是否加级【经验：本节不逐一断言某公司用了哪几级，可按各团队公开的工程材料自行核验】。

#### 3.2.6 Instruction-Tuned Embedding（指令嵌入）模式

- **被什么约束逼出来**：一个组织里同时存在检索、分类、聚类、去重等任务，为每个任务单独训练并维护一个编码器，成本与维护面都不可持续。
- **结构**：

```text
同一模型 + 不同任务前缀 → 不同语义空间
   "为这个查询找相关文档：<q>"        → 检索空间
   "把这个文本分到最接近的类别：<x>"  → 分类空间
   "把这个文本聚到最相似的簇：<x>"    → 聚类空间
────────────────────────────────
工程约束（比模型选择更容易出错）：
   · 写入侧与查询侧的前缀必须成对出现，且必须与训练时一致
   · 改前缀 = 改变向量空间 → 必须全量重编码
   · 前缀属于"模型行为的一部分"，必须进版本管理与回归评估
```

- **为什么这样设计有效**：因为前缀在训练时就与任务一同参与对比学习，模型学到的是「按前缀切分语义空间」，所以推理时切换任务只需换前缀、不必换模型，一个服务实例能同时服务多种任务。
- **代价**：前缀成了隐式接口——任何调用方漏写或写错前缀都会**静默退化**（不报错，只是结果变差），因此前缀必须封装在服务端，不能交给调用方传参。
- **失效点**：当任务种类很少且集中（例如只做检索一件事）时，「多任务统一」反转成纯粹的额外风险面——可切换的任务空间从未被用到，而前缀不一致导致的静默退化却始终存在。
- **真实使用**：BGE-M3 用一个模型同时支持稠密、稀疏、多向量三种输出（arXiv:2402.03216, 2024）；Nomic Embed v1.5 与 Jina Embeddings v3 都把任务前缀或任务特定适配器作为对外接口的一部分【公开：模型卡与官方文档可按名称检索核验，以当前版本为准】。

#### 3.2.7 Multimodal Embedding（多模态嵌入）模式

- **被什么约束逼出来**：检索对象同时包含文本、图像、页面截图，而各模态之间没有天然可比的中间表示。
- **结构**：

```text
统一向量空间：对齐靠"配对数据"或"锚模态"，不靠架构
   文本 ─┐
   图像 ─┼→ 各自编码器 → 投影到同一 d 维空间 → 跨模态近邻检索
   视频 ─┤                    ↑
   音频 ─┘   两两对比（CLIP 类）：对齐只在"训练数据里成对出现过"的模态之间成立
────────────────────────────────
推论（限两两对比）：文本↔图像对齐好，不代表图像↔音频也对齐。
      没在训练中成对出现过的模态组合，在两两对比下空间对不上。
      例外：以某个模态为锚做绑定（ImageBind 类做法）——只用 (image, X) 配对训练，
      可让从未成对出现过的模态组合（音频↔深度）产生涌现式对齐。
────────────────────────────────
文档场景的替代路径：把页面渲染成图像后直接编码（ColPali 类做法）
   → 绕开"版面结构在文本抽取阶段被破坏"这个前置问题
```

- **为什么这样设计有效**：因为对比学习把成对出现的两种模态映射到同一空间的邻近位置，所以任一模态的向量都能直接检索到另一模态的条目——跨模态检索不必先做模态转换（例如先生成图片描述再检索）。
- **代价**：编码器与预处理链路变成两套甚至多套，同一份内容的向量来自不同编码器、彼此不可直接比较；且哪些模态组合能被对齐，由配对策略决定而不是由模型参数量决定——两两对比只保证成对出现过的组合，每多覆盖一个组合就要补一批配对数据，或改用以某个模态为锚的绑定（ImageBind 类做法），前者是数据与标注成本，后者是训练与评测成本。
- **失效点**：当查询需要对图像内部的细粒度文字做精确匹配（票据号、合同条款）时，「跨模态语义相近」反转成「把识别错误当成检索结果」，因为统一空间对齐的是整体语义，不是字符级内容。
- **真实使用**：CLIP 用图文对比学习建立共享空间（Radford et al., ICML 2021, arXiv:2103.00020）；ImageBind 以图像为锚把对齐扩展到六种模态（Girdhar et al., arXiv:2305.05665, 2023）；ColPali 把文档页面图像直接编码用于检索（arXiv:2407.01449, 2024）【公开：论文可按编号检索核验】。

#### 3.2.8 Matryoshka Embedding（俄罗斯套娃）模式

- **被什么约束逼出来**：检索的不同阶段对精度要求不同，而全维度向量在粗排阶段的代价（内存、带宽、距离计算）被候选数量成百上千倍地放大。
- **结构**：

```sql
-- 存全维度，用低维度建索引：截断发生在索引与查询侧，不在存储侧
CREATE TABLE doc_chunk (
  chunk_id  BIGINT PRIMARY KEY,
  embedding VECTOR(1024) NOT NULL,
  payload   JSONB
);
CREATE INDEX idx_coarse ON doc_chunk
  USING hnsw ((subvector(embedding, 1, 128)::vector(128)) vector_cosine_ops);
-- 粗排走 128 维索引 → 精排回到 1024 维全向量
-- 关键前提：训练阶段必须让前 128 维"单独也有意义"，否则截断即失真
```

- **为什么这样设计有效**：因为训练损失同时施加在多个前缀长度上（前 64、128、256…维各自都被要求能完成检索），低维前缀不是「高维的残缺版」，而是各自成立的近似表示，所以可以按阶段选维度。
- **代价**：训练目标比单维度多一层约束，同等参数量下全维度指标通常略低于为固定维度专门训练的模型；且截断长度必须与训练时的嵌套长度对齐，随手取一个中间值（如 300 维）并不保证有效。
- **失效点**：当业务只有一个检索阶段、且向量总量不大时，「按需选维度」反转成一次纯损失——省下的内存不足以抵消全维度的轻微精度下降，因为低维截断的收益只有在维度真正成为瓶颈时才兑现。
- **真实使用**：Matryoshka Representation Learning 由 Kusupati 等人提出（NeurIPS 2022, arXiv:2205.13147）；OpenAI 在 text-embedding-3 系列上公开了可缩短输出维度的参数（2024）【公开：可按 OpenAI 官方文档当前版本核验】。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 百万级语料、延迟敏感、无标注 | 3.2.1 Bi-Encoder + ANN | 不上重排：没有标注就没有可验证的增益，加了只是变慢 | 能否在自有评测集上量出重排的净收益 |
| 百万级语料、准确率优先 | 3.2.2 召回 + 精排 | 不上多级：两级已吃掉大部分收益，第三级的边际收益要先测出来 | 召回率和最终精度是否分开测 |
| 语料以标识符 / 数字 / 专名检索为主 | 3.2.4 Hybrid | 不上纯向量：语义路在这类查询上增量召回接近于零 | 抽样看漏召回样本的字面特征 |
| 长文档、跨段落的答案 | 3.2.3 Late Interaction | 不上单纯分块：分块会把跨段落的答案切散，任何单 chunk 向量都召回不到 | 平均答案跨度是否超过一个 chunk |
| 高价值、可接受秒级延迟 | 3.2.5 多级重排 | 不上单级：单级重排的上限被上一级候选集封住 | 每级是否都保持高召回 |
| 多任务共用一套向量资产 | 3.2.6 指令嵌入 | 不上多模型：多模型 = 多份全量向量 + 多套重编码流程 | 前缀是否已封装在服务端 |
| 检索对象含图像 / 页面 | 3.2.7 多模态 | 不上纯文本抽取：版面结构在抽取阶段就会丢 | 目标模态组合是否已被对齐覆盖（两两对比的配对数据，或锚模态绑定） |
| 亿级向量、内存受限 | 3.2.8 Matryoshka | 不上全维度：全维度常驻内存不现实（见 3.2.1 的推算） | 维度是否已是瓶颈，而非模型能力 |
| 多语言 / 跨境 | 多语言双编码器 + Hybrid | 不上单语言模型：跨语言检索直接失效 | 评测集是否含跨语言 query |
| 端侧 / 边缘部署 | 小模型双编码器 | 不上重排与多级：端侧没有算力预留 | 端侧内存与延迟预算 |

本主题下最常被误选的一对，是 **3.2.2（召回 + 精排）与 3.2.5（多级重排）**。误选的后果不是变慢一点，而是**评估被混淆**：多级重排有三段分数，团队却往往只用最终 Top-N 的单一指标看效果；一旦指标下降，无法判断是召回级漏了、还是中间级把正确答案压下去了，于是只能靠加机器和调 K 试错。选 3.2.5 的前提是**每一级都有独立可测的召回率**——测不出，就不该加这一级。

### 3.4 组合模式：真实系统不会只用一种

**组合 1：Hybrid 召回 + Cross-Encoder 精排。** 稠密路负责语义改写，稀疏路负责字面精确，两者取并集后交 Cross-Encoder 精排。职责边界是：融合只负责「不漏」，精排负责「排对」——把精度要求压在精排上，融合函数就应尽量简单（RRF）。运维代价是两套索引 + 一个重排服务，三者版本必须一起回归。适合百万到千万级语料、查询形态混合（既有自然语言又有编码）的场景【经验：规模档为经验区间，非测量值】。

**组合 2：Bi-Encoder 粗排 + Late Interaction 中排 + Cross-Encoder 终排。** 粗排从全量降到千级，中排用 token 级 MaxSim 处理长文档与精确命中，终排做联合编码打分。职责边界按「成本 × 精度」逐级收紧，每一级都必须保持高召回。运维代价是三套索引或三套模型服务，延迟是三级之和，排障必须按级定位。适合长文档为主、对精度有硬要求且能接受秒级延迟的场景。

**组合 3：Matryoshka 粗排 + 全维精排 + 可替换重排。** 用低维前缀建索引承担粗排，精排阶段回到全维度向量，最后接一个可独立替换的重排模型。职责边界是：低维只负责「把候选缩到可控规模」，任何精度判断都不得基于低维分数。运维代价是要维护「训练时嵌套长度 ↔ 索引维度」的一致性约定，一旦改训练就得重建索引。适合亿级向量、成本敏感、又要保留精度上限的场景。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因 | 修法 |
| --- | --- | --- | --- | --- |
| 直接用默认 Embedding | 检索结果「看着还行」，但业务方举例时经常答非所问 | 模型与语料分布不匹配，召回率从一开始就被封在一个低水平 | 起步时没有评测集，模型选择无法被质疑 | 先建评测集，再用 MTEB 与自有集交叉选型 |
| 忽略 Rerank | 召回 Top-K 直接塞给 LLM，答案里常混入无关段落 | 双编码器丢掉的交互信息没有被任何环节补回 | 粗排分数看起来「已经很像」 | 加精排，并把召回指标与排序指标分开测 |
| 维度浪费 | 索引内存与距离计算成为瓶颈，但召回并未明显领先 | 高出训练目标所需的维度，只抬成本不抬精度 | 认为「维度高 = 效果好」 | 用可截断维度的模型，按阶段选维度 |
| 硬负样本缺失 | 离线指标高，上线后对近似改写样本失灵 | 缺少近似负例时，模型学不到决策边界，相邻语义被压在一起 | 只用了随机负例（in-batch 默认） | 用两路召回的边界样本做难负例挖掘 |
| 长文档直接截断 | 关键信息在文档中后段时整篇召回失败 | 截断是硬信息损失，后面的所有排序都无从恢复 | 模型上下文有限，先截了再说 | 分块 + 重排，或改用 token 级交互 |
| 冷启动数据不足 | 领域评测集上明显低于通用榜表现 | 领域词表在通用语料中几乎没出现过，向量空间没有为它留位置 | 领域无标注数据，且不愿自建 | 合成查询-文档对做微调，并保留评测集 |
| 忽视多语言 | 跨语言 query 完全检索不到 | 单语言模型的向量空间没有跨语言对齐 | 初期只有单语言用户 | 换多语言模型，评测集加入跨语言 query |
| 召回 + 生成脱节 | 召回还不错，但答案是错的 | 召回没有考虑生成端的上下文预算，塞进去的相关内容挤掉了真正需要的 | 检索与生成由不同团队负责 | 让 K 与 chunk 长度对齐生成端预算，端到端评测 |
| 无评估体系 | 每次「优化」都无法证明变好了 | 没有基线就没有回归，任何改动都无法归因 | 评测集建设被视为「不产出业务价值」 | 建评测集 + 固定基线 + 每次改动出对照 |
| 盲目追求 SOTA | 换了榜单第一，线上指标没动 | 榜单语料与自有语料不同分布，收益不迁移 | 用榜单替代了自有评测 | 按自有评测集的净收益选型 |

其中三个最容易在生产里爆掉：

**「无评估体系」是最危险的一个**，因为它让其余九个反模式全都不可观测。没有基线时，任何「换模型 / 调 K / 加级」都无法被证伪，团队只能靠主观印象迭代；而检索类系统的退化通常是**静默的**——线上不会报错，只是答案质量缓慢下滑。表征是：问「这次改动提升了多少」时，回答是一个例子而不是一个数字。

**「忽略 Rerank」的暴露方式是端到端的**：检索团队交出的 Top-K 里确实有正确文档（召回率没问题），但 LLM 只读前几段就下结论，于是错误答案被归因到「模型不行」，真正的原因是非相关段落被排在了前面。修它不需要换模型，只需要在召回与生成之间加一级排序。

**「召回 + 生成脱节」常与「长文档直接截断」同时出现**：为了塞进上下文预算，chunk 被切得很碎，跨段落信息被切散；召回按 chunk 打分，生成按 token 预算拼接，两个环节各自最优，拼起来却是「关键条件所在的 chunk 没进预算」。判据是：能否回答「最终答案所依据的那段文字，在召回的候选里排第几」。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：**规模或访问模式跨过某个阈值后，原来正确的模式会变成错误的**。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 十万 → 百万向量 | 暴力 / 低精度索引 | 查询延迟随向量数线性上升，延迟预算被撑爆 | 图索引或聚类索引 | 索引构建时间与内存上升；召回率需重新标定 |
| 百万 → 亿级向量 | 全维度常驻内存索引 | 内存成本主导（见 3.2.1 的推算），单机放不下 | 量化 / 低维截断 / 磁盘索引 | 精度下降需用评测集量化；索引重建周期变长 |
| 单语言 → 多语言 | 单语言编码器 | 跨语言 query 召回接近于零 | 多语言编码器 | 全量重编码；原有阈值与 K 全部失效 |
| 纯文本 → 多模态 | 纯文本抽取 + 文本向量 | 版面结构在抽取阶段丢失 | 多模态统一空间或页面图像编码 | 需为每种模态维护编码与预处理链路 |
| 只做检索 → 进 LLM 上下文 | 以召回率为唯一目标 | 生成端有 token 预算，召回率不再是唯一指标 | 端到端评测 + 精排 + 上下文预算对齐 | 需重建评测口径（从召回率改为端到端答案质量） |

最后一行是最容易被低估的：**从「检索系统」变成「RAG 的召回层」之后，优化目标从召回率换成了端到端答案质量**，而这两者的最优 K、最优 chunk 长度、最优重排策略常常不同——很多团队在这一步继续沿用检索时代的调参结论，于是出现「召回指标一直在涨、用户满意度不再涨」的局面。表中的量级是经验台阶【经验】，不是测量值，具体阈值必须用自有评测集重新标定。

### 3.7 自检清单

1. 是否有**固定的评测集与基线**？每次改动能否报出一组对照数字，而不是一个例子。
2. 召回指标与最终排序指标是否**分开测量**？出错时能否判断是召回漏了还是重排压错了。
3. 语料里是否存在**标识符、数字、专名**这类查询？若有，混合检索是否已经在跑。
4. 平均答案跨度是否**超过一个 chunk**？若超过，是否有跨 chunk 的召回手段。
5. chunk 切分策略是否**记录在案并与评测挂钩**？（改了切分就必须重跑评测）
6. 编码模型的**前缀 / 指令**是否封装在服务端，而不是由调用方传入。
7. 写入侧与查询侧是否用了**同一版本、同一前缀**的编码器？有无版本漂移的检测。
8. 向量维度是否已经是**实际瓶颈**？若不是，是否还在为「更高维度」付出成本。
9. 换编码模型的**全量重编码与索引重建**流程是否演练过？在多少时间内能完成。
10. 索引参数（如图索引的构建与查询参数）是否**与召回率一起标定**过，而不是沿用默认值。
11. 召回的 K 是否与**生成端的上下文预算**对齐？K 增大后答案质量是否真的变好。
12. 是否有机制发现**静默退化**（向量分布漂移、语料分布变化）？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 语料大、延迟敏感、无标注 | 3.2.1 Bi-Encoder + ANN | 在线算力与语料总量解耦，是唯一能扩展到亿级的形态 |
| 有标注、精度优先 | 3.2.2 召回 + 精排 | 交互信息只能靠联合编码补回，且只按候选数计费 |
| 长文档、精确命中 | 3.2.3 Late Interaction | token 级 max 保留了「哪个词对上哪个词」 |
| 查询含编码 / 专名 | 3.2.4 Hybrid | 两路失败模式不重叠，并集之后不漏 |
| 多任务共用向量资产 | 3.2.6 指令嵌入 | 一个空间按前缀分片，省掉多份全量向量 |
| 亿级 + 内存受限 | 3.2.8 Matryoshka | 让低维前缀成为独立成立的表示，而非残缺版 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**「正确答案能不能被一次独立的向量比较找出来」**。能，就用双编码器 + ANN，把其余预算全部投在索引与召回率上；不能（因为要精确命中、因为答案跨段落、因为对象不是文本），就必须引入某种形式的**交互**（token 级 max、联合编码、稀疏路），并为这份交互付出延迟、存储或维护面的代价。所有模式的分歧，最终都落在这条线上。
