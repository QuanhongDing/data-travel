## 5. 前沿演进（AI 时代）

> 原 § 5 共 150 行、为方向清单（7 个演进方向、3 组 RAG 组合、13 条学术条目、12 条工业条目、一张 10 行榜单快照、10 条趋势），条目指向工具而不指向机制。本节按「能力 → 机制 → 证据 → 成熟度 → 现在该做什么」重写，每条原条目的去向在 §5.1 末的对照段里逐条交代。

### 5.1 先分清三类「前沿」

本章的机制链在 [§ 7](01-embedding-and-retrieval-section-7-sec7.md) §7.3 里被拆成四段：编码时 query 与文档互相看不见（§3.2.1）、ANN 用召回率换延迟、重排用算力换精度（§3.2.2）、结构信息只能存在向量或图或提示词三者之一里（§7.3.4）。这四段在 LLM 出现之前就已定型。所以本节要判的不是「LLM 能不能接进检索」，而是 **LLM 有没有改动这四段里任何一段的性质**。

按这条标准筛一遍，原清单里真的落在机制上的只有两处：**第一处是训练信号的产生方式**——从「人写查询-文档对」变成「模型生成 + 人抽检」，它改变的是领域适配的**成本函数**；**第二处是检索的发起权**——从固定流水线挪进模型，它改变的是**接口边界**，而不是可达性。这两处落到 §5.2.1 与 §5.2.2。

其余十二行（长上下文、Late Interaction、多模态、Matryoshka、重排、GPU 索引、端侧、评测标准化、Hybrid 默认、GraphRAG 结合，以及 LLM 作为重排器与 Embedding 作为 Agent 工具）**改的是表示形态、训练目标或硬件，不是 LLM 的能力**。它们即使没有 LLM 也会发生，其中几项（Hybrid、重排、量化）在 LLM 兴起之前就是检索工程的常规做法。把它们与上面两处并列写成「AI 时代的演进」，会让真正要做的三件事——**建自有评测集、给候选数与阈值定标、算清索引内存账**——一件都排不进排期。

本节用 L1 / L2 / L3 三级区分。判据必须可核验，而不是「感觉成熟」：

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口 / 生态未稳，或**仅有厂商与建设方自有案例**，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

**本节不对 L1 判据做任何修正，也不缩小它的适用范围。** 本主题最诱人放宽的正是第②条：embedding 与检索领域有大量公开论文、可下载的开源权重、可复现的榜单，很容易把「有公开的机制性材料」读成「有第三方生产案例」。但按判据读，**论文证明的是方法可行，榜单证明的是在别人的语料上表现好，产品文档证明的是厂商声称它能做**——三者都不是「某非厂商组织公开过它在生产里的语料规模、召回目标与实测结果」这类带参数的材料。另有一条纪律：**已经在生产里跑了多年的既有能力**（Hybrid 融合、Cross-Encoder 重排、量化压缩、向量库本体）不是 AI 方向——但这不等于本节不评它们：重排与 Hybrid 就是表里的第 9、13 行，量化并入第 10 行，三者都另有 §5.2.4 的逐条拆解，向量库本体则归 §4.3 的既有栈。它们照样标级别，但级别评的是「公开证据够不够 L1」，而不是「LLM 有没有带来它」——读表时不要把这几行读成 AI 方向。

还有三件容易混的事，先在这里分开：

- **产品名 vs 能力名**：「长上下文 embedding」「可截断维度」「多向量检索」都是**能力名**，不是某个产品的专属功能；同一能力在不同模型卡里挂在不同的名字下（[§ 4](01-embedding-and-retrieval-section-4-sec4.md) §4.3 把它们一并列在工具链里）。判定方法：按**模型全名 + 该能力的输入与输出形态**核对，而不是按能力名归类。
- **榜单名次 vs 模型能力**：原 §5.3 给过一张 MTEB 头部快照。榜单的名次与分数随提交时间变化，任何写进书里的快照都会在几个月内失真，**因此本节不给分数、不给名次**；判定入口是榜单本身（HuggingFace 上的 MTEB 与 C-MTEB 页面），且必须与自有评测集双向核对。
- **论文原型 vs 产品实现**：论文演示的是方法可行性，产品实现要受编码长度、索引格式、显存与召回口径的约束。判定方法：看它的实现有没有把「截断 / 压缩带来的召回损失」显式暴露成一个可调的参数。

> 表里**没有任何一行达到 L1**，原因不在技术，而在本主题公开材料的构成：可核验的只有**论文、模型卡与厂商/项目文档**三类，加上本书 [§ 6](01-embedding-and-retrieval-section-6-sec6.md) 整理的四个案例（智源 / OpenAI / Cohere / Voyage）——而后者是**建设方自述**，按判据读正是 L2 的定义。**L2 不等于「不能用」**：表里多行在真实系统里天天在跑；L2 只表示**公开证据到不了 L1**。要警惕的是把 L2 当 L1 用，写成「所以可以按榜单第一名的模型定架构」。

**这三级的排法直接决定路线图的顺序**：

- **先做的三件事不在表里**，因为它们是 AI 之前的既有能力，却是后面每一行的评估前提：建自有评测集（§3.7 第 1 条）→ 把召回指标与排序指标分开测（§7.3.3 的指标 A / B）→ 算清索引内存账（§7.4 的推算）。没有这三件事，「换了模型有没有变好」无从判断。
- **L2 做 PoC，并先测两个数**：正确片段进 Top-k 的比例（指标 A）与自有评测集上的端到端答案质量（指标 B）。这两个数拿不出来，L2 就停在原地，与选哪家模型无关。
- **L3 不排进排期**：多轮自主检索、GraphRAG 结合、动态选模型都属于「等信号」。它们有一个共同前提——**先能度量"一次检索够不够"**，而这个度量比多轮检索本身重要得多。
- **回填机制**：每次检索系统复盘时回填一次级别；某个 L2 若一年内仍拿不到自己语料上的实测收益，降为 L3 并停止投入。

**原条目去向对照**（下文行号均指 §5.1 的演进方向表）：原 7 个方向全部保留——方向 1 拆成三行（Embeddings as Tools → 第 16 行，LLM-generated Embeddings → 第 2 行，Self-RAG → 第 3 行）；方向 2、3、5、6、7 分别落在第 5、7、6、1、10 行；方向 4 落在第 8 行。表里另有第 15 行（LLM 作为重排器）是按主文件 §2.3 已有的条目补的，不在原清单内。原 §5.2 的三组结合保留：RAG 标准架构的两级拆到第 9 行（精排）与第 13 行（召回段），GraphRAG 融合落在第 14 行，Agentic RAG 一组落在第 3、4 行。原 §5.3 的 13 条学术条目是**模型名而非机制**：BGE-M3 / Nomic Embed v1.5 / Jina Embeddings v3 / LongEmbed 归第 5 行，ColBERT v2 / ColPali 归第 6 行，LLM2Vec 归第 2 行与 §5.2.1，VLM2Vec 归第 7 行，Snowflake Arctic Embed / GTE-Qwen2 / mxbai-embed-large / mixedbread Rerank / Cohere Embed v3 属选型问题，归 §4.3 的工具链与 §5.4 的判定入口。原 §5.3 的 12 条工业条目：5 条向量库版本（Milvus / Qdrant / Weaviate / Pinecone Serverless / pgvector）属于**既有栈的版本能力**，归 §4.3，其与本主题演进相关的增量只有三条——内置 Hybrid（第 13 行）、GPU 与量化（第 10 行）、成本结构变化（§7.4）；其余 7 条是模型发布（OpenAI text-embedding-3 / Cohere Embed v3 与 Rerank 3 / Snowflake Arctic Embed / BGE-M3 GA / Voyage AI / Nomic Embed v1.5 / Jina v3），落在第 1、2、5、8、9 行与 §5.4。原 §5.4 的 10 条趋势一条不丢：第 1–4 条落在第 5–8 行，第 5 条落在第 9 行，第 6 条落在第 10 行，第 7 条落在第 3 行，第 8–10 条落在第 11–13 行。

### 5.2 演进方向逐条拆解（核心节）

下面把方向分成四组，**四组都按同一套结构逐条写**（旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度）；第四组也逐条写，因为那一族的共同点恰恰是「机制没变」，只有逐条摆出来才看得出每一行改的到底是哪一层。四组的差别在于**改动落在哪一层**：

| 方向 | 改变了什么机制 | 落在哪一层 |
| --- | --- | --- |
| §5.2.1 训练信号合成 | 造训练样本的边际成本从人的注意力挪到算力 | **成本函数**（领域适配从"标注预算"变成"算力 + 抽检"） |
| §5.2.2 检索发起权交给模型 | 控制流的决策点从工程代码挪进模型 | **接口边界**（多一层模型调用与终止条件） |
| §5.2.3 表示形态的扩展 | 一次向量比较 → 多次或多种比较 | **表示与存储**（本主题里唯一随语料线性放大的成本） |
| §5.2.4 机制没变的那一族 | 大多没有改变机制 | **训练目标、硬件与既有能力的延伸**（换参数 / 换硬件 / 与 LLM 无因果关系） |

读法建议：如果时间只够读一节，读 §5.2.1——它是本主题里唯一**改变了成本函数**的变化，也是唯一一个「不做评测集就无法判断有没有收益」的方向。只写收益不写代价的方向，在评审时应被直接打回：本主题里每一次「检索更准了」，都对应一处新的判断成本——**合成数据要人去抽检，多轮检索要人去设上界，多向量索引要人去算内存**。

#### 5.2.1 训练信号合成：领域适配的成本函数被改写（原方向 6；原 5.3 学术条目 LLM2Vec）

- **旧做法与它的卡点**：通用编码器在垂直领域失灵（医疗、法律、内部代号），解法是微调；而微调要的是成对的「查询-文档」，这批数据恰恰是组织里没有的——业务不写查询日志、工单不成对、标注要懂业务的人逐条写。卡点不在算力，在**正样本的边际成本不随规模摊薄**（§3.5「冷启动数据不足」）。
- **AI 改变了什么机制**：**训练信号的产生从「人写」挪到「模型生成 + 人抽检」**——LLM 读一遍文档就能合成出像真的查询。这是本主题里唯一一条真正落在**成本函数**上的机制变化：它把「造一条正样本」从人的注意力换成算力。
- **由此得到的**：**因为造正样本的成本从人的注意力挪到了算力，所以没有标注预算的团队第一次能做领域适配**——过去只有攒得起标注人力的大厂能做的微调，现在两三个人的团队也能起步。得到的是**信号**，不是精度：合成分布与真实查询分布之间的差，由评测集负责发现。
- **由此付出的**：**其一，合成数据会把自己的偏见写成训练目标**——模型合成的查询只覆盖模型想得到的问法，而真实用户的口语、错别字、指代恰在分布外；这类偏差不会让离线指标变差，只会让长尾更差（§3.5 的失效形态）。**其二，评测样本成了更稀缺的东西**：合成能造出无限训练样本，却造不出可信的评测样本，一旦训练与评测都由同一个模型合成，离线指标会失真。**其三，基线换一次、索引重建一次**：编码模型是基础设施决定而不是超参（§3.1 的变更频率约束、§7.4 的全量重建成本）。

```text
   合成数据能补什么、不能补什么（这决定它值不值得做）
   ────────────────────────────────────────────────
   能补：领域术语与文档风格上的分布差
         → 症状：行业词在通用语料里稀疏，向量空间没为它留位置
   补不了：真实用户的问法分布
         → 口语、错别字、多轮指代、内部黑话，模型自己想不到
   ────────────────────────────────────────────────
   判定方法：从真实查询日志里抽 200 条自建评测集，先量基线；
             再用合成数据微调，在同一批 200 条上重测。
             只在合成集上测，等于用模型给自己打分。
   ────────────────────────────────────────────────
   附带账：换基线 = 全量重编码 + 重建索引（§7.4），
           这笔钱要在立项时就写进预算
```

- **证据与来源**：【公开】Sentence-Transformers 是成熟的句向量微调框架，BGE-M3 一类模型公开了训练脚本（可按各项目官方文档当前版本核验）；LLM2Vec 一类方法把 LLM 直接改造成编码器（2024，可按论文题名核验）。**本节未能核到可点名的第三方（非厂商）公开生产案例**——即「某非厂商组织公开过它合成数据的规模、抽检口径与微调后的净收益」这类带参数的材料。
- **成熟度**：**L2**。判据：① 满足（框架与脚本有版本化发布物）；**②核不到**；③ 合成数据的格式与验收口径各家不同 → 做 PoC，不要把它当核心依赖。本节标题括注的另一个子项**「LLM 直接产出向量」**（§5.1 表第 2 行，即 LLM2Vec 一支）单独看也是 **L2**，但判据不同：① 满足（论文与开源实现可按题名核验，2024）；**②核不到**；③ 输出维度与编码成本未与现有 ANN 生态对齐——两行的 ③ 不是同一条，级别只能按各自那一行的判据读。
- **判定方法**：先建 200 条真实查询的评测集并量出基线，再把微调前后的同一批查询结果对照；同时抽 50 条合成样本请懂业务的人判真假。**前者决定值不值得做，后者决定合成器能不能用。**
- **什么时候不值得做**：评测集还没有时——没有基线，微调带来的变化无法归因；或基线已经接近业务可接受水平时——此时瓶颈通常在排序而不在编码（§7.3.3）。

#### 5.2.2 检索发起权交给模型：接口边界变了，可达性没变（原方向 1 的 Self-RAG；原 5.2 的 Agentic RAG 一组；原趋势 7）

- **旧做法与它的卡点**：标准架构把检索写死成流水线的一环——来了查询就检索、固定取 K 条、直接拼进提示词（原 §5.2 给出的两段式流程图）。卡点在两处，且都不是编码器能修的：**不该检索的问题也检索**（打招呼也要过一次向量库），以及**一次召回不足时没有第二次机会**。
- **AI 改变了什么机制**：**控制流的决策点从工程代码挪进模型**——由模型判断要不要检索、检索几轮、要不要先改写查询。这条改变落在**接口边界**上（多一层模型调用、多一个终止条件），而**不落在可达性上**：它不改变「一次独立的向量比较能找出的东西」（§7.3.1、§3.8 的同一条结论）。
- **由此得到的**：**因为终止条件由模型按问题难度决定，所以简单问题可以不走检索、难问题可以走多轮，平均成本第一次能随问题难度伸缩**——固定流水线下这两类问题付一样的钱，因为轮数是写死的。
- **由此付出的**：**其一，成本与延迟随轮数线性增长且上界不明**——调用次数是运行期决定的，所以步数上限必须显式设（§7.6 组合 6 把「不设上界的长尾账单不可控」列为该组合的运维代价）。**其二，评估面翻倍**——固定流水线只要测「检索质量」，自主决策还要测「决策质量」（该检索的没检索、不该检索的检索了），而后者没有现成指标。**其三，不可复现**——同一个问题两次走不同轮数、给不同答案，而日志里通常没有「当时为什么决定再检索一轮」的依据，排障时无从复盘。
- **证据与来源**：【公开】Self-RAG（2023）、CRAG（2024）、Adaptive-RAG（2024）一类论文按题名可检索核验，均把「是否检索、检索几轮」作为模型决策；查询侧的其他手段（HyDE、Query Rewrite）见 [04 混合检索](../../04-data-assetization/04-hybrid-search/04-hybrid-search.md) §2.1。**本节未能核到**可点名的第三方（非厂商）公开生产案例，也未核到带参数的「轮数—收益」曲线。原 §5.2 把 Agentic RAG 与 RAG 标准架构并列在同一层，本节按机制把它们分开：标准架构是**固定流水线**，Agentic RAG 是把**决策权交出去**，两者的成本结构不同。
- **成熟度**：**L3**（Agent 自主决定检索这一形态：① 无正式条目、② 不适用、③ 终止条件与成本上界无约定）；同一族的**查询侧改造**单独看是 **L2**（① 形态在书内与公开材料里可核验；**②核不到**；③ 改写增益与成本口径无共识）——两者不是同一个子项，级别只能各自判。
- **判定方法**：把「检索」这一步换成固定一轮，再换成自主多轮，同一批问题跑两遍，比较指标 B（端到端答案质量）与每问的检索次数、token 成本。**只报质量提升、不报成本变化的多轮检索，不可作为架构变更的依据。**

#### 5.2.3 表示形态的扩展与它带来的存储账（原方向 2、3、5；原趋势 1、2、3）

- **旧做法与它的卡点**：一段文本、一个向量。三处卡点都不能靠调参解决：长文档必须切块，而切块会把跨段落的证据切散（§3.2.3）；精确命中（型号、条款号、错误码）会被整体语义平均掉（§7.3.1 的失效条件）；图像与扫描件里的信息在文本抽取阶段就已经丢了（§3.2.7）。三条卡点分别对应原方向 2、5、3。
- **AI 改变了什么机制**：**把「一次向量比较」换成「多次比较或多种比较」**——长上下文提高单次编码的容量，多向量保留 token 级证据，多模态把对齐扩到别的模态。**要老实说清：这三条不是 LLM 带来的**，它们来自编码器容量、训练目标与配对数据，即使没有 LLM 也会发生。它们是**表示形态的扩展**，不是架构变化。
- **由此得到的**：**因为表示不再被压成一个向量，「精确命中」与「语义改写」第一次可以被同时要求**（对照 §7.3.1 的失败方式表：词项族兜逐字、单向量族兜换词、多向量族两边都要）；长文档也不再依赖「切得够巧」。
- **由此付出的**：**其一，存储与算力按倍数放大，且这是本节唯一随语料线性放大的成本**：【推算】同一篇 512 token 的文档，单向量方案是 768 个数值，ColBERT 类方案是 512 个约 128 维向量即 65,536 个数值，约 85 倍；若单向量取 3,072 维则约 21 倍（推导链见 §7.3.1，量级相差一到两个数量级）。**其二，模态越多对齐越难**：文本↔图像对齐好不代表图像↔音频对齐好，没在训练中成对出现过的组合空间是对不上的（§3.2.7 的推论）。**其三，每条链路各带一个模型版本**，版本矩阵随之膨胀（§7.6 组合 7 的运维代价）。

| 表示形态 | 它买到什么 | 成本由谁主导 | 判定方法 |
| --- | --- | --- | --- |
| 长上下文编码 | 少切一块，跨段落证据还在 | 编码算力随长度上升 | 长文直编 vs 分块 + 重排，用同一批查询对比 |
| 多向量（Late Interaction） | token 级精确命中，同时容忍改写 | 索引体积（21–85 倍量级【推算，§7.3.1】） | 先估索引体积，再问内存预算 |
| 多模态统一空间 | 图里的信息不必先转成文字 | 配对数据的覆盖度（不是参数量） | 找一条「答案只在像素里」的查询试 |

- **证据与来源**：【公开】ColBERT（2020）、ColBERTv2（2022）、PLAID（2022）、ColPali（2024）、CLIP（2021）、ImageBind（2023）、BGE-M3（2024）均可按论文编号或题名核验；各模型的可编码长度以模型卡当前版本为准。**本节未能核到**可点名的第三方（非厂商）公开生产案例，也未核到「多向量索引在生产规模下的实测成本」这类带参数的材料。
- **成熟度**：三条都判 **L2**，理由见 §5.1 表第 5–7 行（① 可核验、**②核不到**、③ 各自的口径无约定）→ 做 PoC，不要做核心依赖。
- **什么时候不值得做**：语料以短文本为主时——短文档本身的交互信息就少，MaxSim 相对单向量的召回增益补偿不了索引膨胀（§3.2.3 的失效点）；答案所在位置明确且单跳时——多模态与多向量都换不来收益。

#### 5.2.4 被写进「AI 时代」但机制没变的那一族

这一族有十行，其中九行来自原清单、一行（LLM 作为重排器）是按主文件 §2.3 已有的条目补的；下面按同一套六行结构逐行写全（旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度）。共同点是：**收益真实存在，但没有一条的收益来自 LLM 的能力**。它们要么只是换了训练目标（Matryoshka），要么换的是执行硬件与索引参数（GPU 索引、量化、端侧），要么是**把既有做法接进新链路**（GraphRAG 结合、Embedding 作为工具），要么与 LLM 没有因果关系（Hybrid 默认、重排、评测标准化）。**读下面这十行的方式是看「改变了什么机制」这一条**：没有一行改成「LLM 让检索更强」，改的都是训练目标、硬件、评测口径或结构存放位置——这解释了它们为什么全部停在 L2 / L3：判据②核不到只是表层，更深的原因是**它们的好处不来自 LLM，也就不会因为 LLM 变强而变得可核验**。另有一件常被省略的事：**Hybrid、重排、量化、评测集**这四条不是「以后要做」，而是「现在就该做」——它们与 LLM 无关，却是 §5.1 表里所有 L2 方向变得可评估的前提；把它们写成「AI 时代的检索演进」，或者与「换更长的上下文模型」放在同一张排期表里竞逐资源，会让 §5.1 表里那三件真正要做的准备——**建评测集、分开测召回与排序、算内存账**——一件都排不进排期，这是本主题最常见的一次排序错误。

- **Matryoshka 维度截断（原方向 4）｜旧做法与它的卡点**：全维度向量在粗排阶段的代价被候选数成百上千倍放大——同一份索引，每次比较都要读完整个向量（§7.4 的内存账）。
- **AI 改变了什么机制**：**训练目标变了，与 LLM 无关**：损失同时施加在多个前缀长度上，一个向量因此同时满足多种维度预算。
- **由此得到的**：低维前缀独立成立，可按阶段选维度（§3.2.8）——粗排用截断维度、精排用全维度，不必为粗排另建一套索引。
- **由此付出的**：同等参数量下全维度指标通常略低；截断长度必须与训练嵌套长度对齐，随手取中间值不保证有效。
- **证据与来源**：① 满足（MRL, 2022；可截断维度的对外接口见 OpenAI 官方文档, 2024）；**②核不到**；③ 截断长度与训练嵌套长度的对齐约定无通行做法。
- **成熟度**：**L2** → 只在维度已是实际瓶颈时启用，做 PoC，不做核心依赖。

- **重排成为标配（原趋势 5；原 5.2 RAG 标准架构的 Cross-Encoder 一级；原 5.3 的 mixedbread Rerank）｜旧做法与它的卡点**：双编码器丢掉的交互信息无法靠调大 K 补回——候选集再大，正确片段没进 Top-k 也救不回来（§7.3.3 的指标 A）。
- **AI 改变了什么机制**：**与 LLM 无关**：Cross-Encoder 用算力换精度，机制在 §3.2.2 已定型。
- **由此得到的**：把「语义接近但无关」的候选压下去，且只按候选数计费——精度按候选量购买。
- **由此付出的**：延迟随 K 线性增长；引入第二套评估口径；K 成为必须持续调参的业务参数。
- **证据与来源**：① 满足（Cohere Rerank / BGE Reranker 一类有产品与模型卡发布物，2024）；**②核不到**；③ 阈值必须标定在第二级分数上，这一点无强制约定。
- **成熟度**：**L2** → 上重排前先量 §7.3.3 的指标 A：A 低时重排救不回来。

- **LLM 作为重排器（补增：主文件 §2.3 已列的 LLM-as-Reranker）｜旧做法与它的卡点**：Cross-Encoder 的精度上限受候选集与模型容量限制，换更大的 Cross-Encoder 也换不来「读懂候选再打分」的能力。
- **AI 改变了什么机制**：**换了打分器，没换机制**：仍是「对候选逐个打分」，变的是打分器从专用小模型换成通用 LLM。
- **由此得到的**：候选集很小、且能接受离线或低 QPS 时，用它换取更高的排序上限（上限有多高必须自己量）。
- **由此付出的**：**算力账很硬**：【推算】k = 100、每对约 600 token ⇒ 一次查询约 6 万 token；每天 10 万次 ⇒ 6×10⁹ token/天（§7.4），只适合低 QPS 或离线。
- **证据与来源**：① 核不到（无独立发布物，属既有能力的一种用法）；**②核不到**；③ 无接口约定。
- **成熟度**：**L3** → 只在低 QPS 或离线场景试，先按 §7.4 的算力账估「每问多少 token」。

- **GPU 与专用硬件加速 ANN（原方向 7；原趋势 6）｜旧做法与它的卡点**：距离计算与内存带宽成为亿级语料的主导成本（§7.4）。
- **AI 改变了什么机制**：**换了执行硬件，没换近似搜索的性质**：召回损失依然不可见（§7.3.2）。
- **由此得到的**：单位距离计算成本下降，同预算下可换更大的召回。
- **由此付出的**：收益上限由「数据能否驻显存」决定，显存通常小于内存；驱动与库版本成为新的运维面。
- **证据与来源**：① 满足（RAPIDS 生态的 RAFT / cuVS 一类有项目官方文档，可按项目名核验）；**②核不到**；③ 显存规格与召回口径没有统一报告要求。
- **成熟度**：**L2** → 先算显存账，再决定要不要上。

- **量化与压缩（原方向 7 的「内存优化」；原 5.3 工业条目的 pgvector 量化能力）｜旧做法与它的卡点**：全精度向量常驻内存不现实（§7.4 的 307 GB 推算）。
- **AI 改变了什么机制**：**与 LLM 无关**：PQ / 二值量化是既有的向量压缩手段。
- **由此得到的**：索引体积按档位下降，亿级检索变得可能。
- **由此付出的**：分辨力下降，必须靠重排补精度；压缩档位要用自有评测集标定。
- **证据与来源**：① 满足（PQ 有公开论文，2011）；**②核不到**；③ 无统一召回口径。
- **成熟度**：**L2** → 压缩档位的召回损失要用自有评测集量出来再定档。

- **端侧 Embedding（原趋势 8）｜旧做法与它的卡点**：查询数据不能出端时，云端编码不可用——这一支的驱动力是合规，不是效果。
- **AI 改变了什么机制**：**与 LLM 无关**：靠蒸馏（主文件 §2.3）与维度截断（§3.2.8）把模型做小。
- **由此得到的**：数据不出端也能检索。
- **由此付出的**：对齐质量下降；模型版本升级要跟着终端版本走。
- **证据与来源**：① 核不到（无独立发布物）；**②核不到**；③ 内存与延迟预算无标准。
- **成熟度**：**L2** → 只有当查询必须不出端时才做；否则端侧省下的是带宽，付出的是对齐质量。

- **评测与选型的标准化（原趋势 9；原 5.3 榜单快照）｜旧做法与它的卡点**：选型靠模型卡自述与榜单名次，无法回答「在我这里行不行」。
- **AI 改变了什么机制**：**与 LLM 无关**：它是评测口径问题，不是模型能力问题。
- **由此得到的**：横向可比，能快速缩小候选。
- **由此付出的**：榜单语料与自有语料不同分布，收益不迁移（§3.5「盲目追求 SOTA」）。
- **证据与来源**：① 满足（BEIR 2021 / MTEB 2022 / C-MTEB 2023，以榜单当前版本为准）；**②核不到**；③ 口径修正方法无通行做法。
- **成熟度**：**L2** → 用「自有评测集 + 榜单」双向核对，榜单只用来缩小候选，不用来做结论。

- **Hybrid 检索成为默认（原趋势 10；原 5.2 RAG 标准架构的召回段）｜旧做法与它的卡点**：语义匹配在字面匹配上必然出错——编号、型号、条款号会被整体语义平均掉（§3.2.4）。
- **AI 改变了什么机制**：**与 LLM 无关**：两路失败模式不重叠来自 BM25 与双编码器的机制差异（§7.3.1）。
- **由此得到的**：取并集后不漏，融合函数只需负责排序。
- **由此付出的**：两套索引、两条写入链路，一致性成为新的运维面。
- **证据与来源**：① 满足（词项检索有长期公开文献与实践，Robertson & Zaragoza, 2009）；**②核不到**；③ 融合函数（RRF / 加权）无强制约定。
- **成熟度**：**L2** → 先数语料里「必须逐字命中」的 token 有多少（§7.5 的第一个节点）。

- **GraphRAG 与向量检索结合（原 5.2 的 GraphRAG 融合一组）｜旧做法与它的卡点**：多跳问题在单段式 RAG 上凑不齐事实——答案所需的两个事实分散在两篇互不引用的文档里（§7.3.4）。
- **AI 改变了什么机制**：**换了结构存放的位置，没换检索机制**：结构从「上下文里」挪到「图的边上」（§7.3.4）。
- **由此得到的**：没有任何单篇文档包含完整答案时也能答。
- **由此付出的**：抽取质量决定上限且难自动度量；建图成本入库时一次付清、随语料更新迭付。
- **证据与来源**：① 核不到（Microsoft GraphRAG 是开源项目，2024，可按项目名核验，但「它与向量检索的标准接法」无正式条目）；② 不适用；③ 图与向量两条链路的边界无约定。
- **成熟度**：**L3** → 先判断问题是否需要多跳（§7.3.4 的失效条件：单跳事实问题建图换不来收益）。

- **Embedding 作为 Agent 工具（原方向 1 的 Embeddings as Tools）｜旧做法与它的卡点**：Agent 需要多种检索能力（语义、逐字、多模态），单一编码器给不全。
- **AI 改变了什么机制**：**没有改变机制，只扩大了可选择面**。
- **由此得到的**：能力扩展不必改流程：按任务、语言、模态路由到不同编码器（§7.6 组合 7 的形态）。
- **由此付出的**：选择面扩大后选错率上升，而选错不报错；且**跨模型路由在多向量空间下不可行**（§3.1），每多一个模型就多一条"要不要重建索引"的决策。
- **证据与来源**：① 无正式条目；② 不适用；③ 各家向量空间互不兼容（换模型 = 全量重编码，§3.1）。
- **成熟度**：**L3** → **不要把「按 query 动态选编码模型」写进架构**——向量空间不可比，路由到第二个模型等于建第二套索引。

### 5.3 与本主题既有栈的接口在哪

检索与上下游之间不是「结合」关系，而是**交接物**关系：谁把什么交给谁、数据以什么形态穿过边界、失败时谁负责。这张表的「现状」一列用同一套 L1 / L2 判据，但评的是**这个接口**，不是 §5.1 表里的演进方向——两者不要互相引用，否则同一个 L1 会在两处指两件事。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 检索 ↔ 混合检索（[../../04-data-assetization/04](../../04-data-assetization/04-hybrid-search/04-hybrid-search.md)） | 交接物 = 稠密路候选的**名次**（不是原分数）；融合用 RRF 只吃名次，避免跨量纲比较 | 融合层；名次丢失「差距有多大」的信息，一路遥遥领先与勉强命中被同等对待 | L2（① RRF 有公开文献 2009；**②核不到**；③ 加权融合的归一化方式无约定） |
| 检索 ↔ RAG 架构（[../../04-data-assetization/05](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md)） | 交接物 = Top-K 候选 + 出处；K 必须与生成端上下文预算对齐 | 检索侧；K 调大而答案质量不动，说明瓶颈在别处（§3.5「召回 + 生成脱节」） | L2（集成面成熟，但「K 与预算对齐」无通行做法） |
| 检索 ↔ Data Agent（[../../05-agent-platform/01](../../05-agent-platform/01-data-agent/01-data-agent.md)） | 交接物 = 检索工具的结构化返回（片段 + 出处 + 分数）；Agent 侧负责步数与成本上界 | 双方共用；不设步数上限时，长尾查询的账单不可控（§7.6 组合 6） | L2（工具形态可核验，成本上界无约定） |
| 检索 ↔ LLM in SQL（[../02-llm-in-sql](../../06-multi-model/02-llm-in-sql/02-llm-in-sql.md)） | 交接物 = Schema / 指标的检索结果（Schema RAG 的候选集） | 检索侧；候选集漏表会表现为「系统说没有这张表」 | L2（① 形态在各框架文档可核验；**②核不到**；③ 候选集的召回口径无标准） |
| 检索 ↔ 知识图谱（[../../01-modeling/06](../../01-modeling/06-knowledge-graph/06-knowledge-graph.md)） | 交接物 = 实体标识；向量召回出的实体必须能被图谱解析成同一个节点 | 图谱侧；同名实体被合并成一个时，多跳链路会接错 | L2（跨系统标识对齐无通行做法） |
| 检索 ↔ 推荐 / 特征平台（[../../02-data-science/05](../../02-data-science/05-recommendation/05-recommendation.md)） | 交接物 = 用户与物品向量作为特征；漂移意味着向量分布变化 | 双方共用；向量漂移不报错，只表现为效果缓慢下滑（§3.7 第 12 条「静默退化」） | L2（漂移检测口径各家不同） |
| 检索 ↔ 数据安全（[../../11-cross-cutting/02](../../11-cross-cutting/02-data-security/02-data-security.md)） | 交接物 = 行 / 列级权限上下文；**权限必须在检索之前生效**——如果在召回之后才过滤，越权内容已经进过上下文 | 安全侧；过滤时机错位时，越权发生在权限判断之前 | L2（① 字段级策略是两侧共用元数据，无独立发布物；**②核不到**；③ 过滤时机无强制约定） |
| 检索 ↔ 可观测（[../../11-cross-cutting/04](../../11-cross-cutting/04-observability/04-observability.md)） | 交接物 = 指标 A / B（§7.3.3）与逐级延迟；两个指标必须分开上报 | 可观测侧；只报最终答案质量时，无法判断错在召回还是排序 | L2（指标可定义，分段上报无通行做法） |

一句话概括：**LLM 没有给这条链路加新的一级，它改的是「谁来产生训练信号」与「谁来决定要不要检索」两个位置**。由此得到三条约定。

**第一条约定：召回指标与排序指标必须分开测。**（§7.3.3 的指标 A / B）这条约定今天是可选的，当 §5.2.2 的多轮检索进入链路后会变成必需的——因为轮数一多，「答案不对」的归因对象从一个变成三个：召回漏了、排序压错了、还是模型决定不再检索了。

**第二条约定：向量空间是版本化的资产。** 换编码模型 = 全量重编码 + 重建索引（§3.1、§7.4），所以模型版本必须与切块策略一样进版本管理，而不是当超参。

**第三条约定：先算内存账，再谈模型选型。**【推算，推导链见 §7.4】1 亿条 768 维 float32 ≈ 307 GB；截到 256 维 ≈ 102 GB；改用 PQ 压到约 96 字节/向量 ≈ 9.6 GB（约 1/32）。**能不能上稠密检索往往不是模型问题，而是内存预算问题**——这个判断比换哪个模型更早发生。

```text
   LLM 改的两个位置，落在不同的边界上，谁也不能替谁兜底
   ────────────────────────────────────────────────
   训练信号（5.2.1） ──► 落在「编码器质量」这条边界上
       必须回答：合成数据的偏差谁去发现？答：自建评测集
   检索决策（5.2.2） ──► 落在「控制流与成本上界」这条边界上
       必须回答：轮数上界谁定？答：设计期定，不是运行期省
   ────────────────────────────────────────────────
   两者都没有改变：编码时 query 与文档互相看不见（§3.2.1），
                   所以「一次独立的向量比较能找出的东西」仍是上限（§7.3.1）
   判定方法：任一「检索更准了」的说法，先问它改的是训练数据、
             控制流，还是只是换了硬件与参数
```

- **MTEB 与 C-MTEB 榜单页面**（[§ 4](01-embedding-and-retrieval-section-4-sec4.md) §4.3 已列）——核验「哪些模型在哪些任务上靠前」。**名次会变，不要把它当结论**；判定方法是用榜单缩小候选、用自有评测集做结论。
- **向量库的官方文档**（Milvus / Qdrant / Weaviate / pgvector / Pinecone 一类，见 §4.3）——核验内置 Hybrid、量化档位与 GPU 索引这些能力**是不是该版本的正式条目**，而不是预览或路线图。

**第三方生产案例**

- **本节未能给出**可核验的第三方（非厂商）公开生产案例。公开材料里能核到的是三类：① 论文与模型卡（属方法与模型一侧）；② 厂商与项目文档；③ 建设方的工程自述——[§ 6](01-embedding-and-retrieval-section-6-sec6.md) 整理的智源 / OpenAI / Cohere / Voyage 四个案例，出处标注为「机构名 + 年份区间」，按判据属**建设方自述**，不构成第②条。**这个空白本身是结论**：它正是 §5.1 表里没有任何一行到 L1 的直接原因。
- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——200 条真实查询的评测集、指标 A 与指标 B 两组数、一次换模型的全量重编码耗时实测。这三组数在评审里的分量超过任何榜单名次。
- 三类证据里**最容易造假的是「召回率」**：只报一个召回数字而不说查询集怎么来的、判定的正确片段由谁标注、Top-k 的 k 取多少，无法复核。**判定方法**：只接受同时给出「查询集来源 / 标注方式 / k 与召回目标」三者的召回率。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **长上下文**：拿 20 篇超出旧模型长度的文档，比较直编与分块 + 重排在自有查询上的命中差异。
2. **多向量**：先按 §7.3.1 的推算估索引体积，再问内存预算是否放得下。
3. **多模态**：找一条「答案只在像素里」的查询，看纯文本链路是否结构性地答不了。
4. **Matryoshka**：把索引维度改成训练嵌套长度之外的任意值，看召回是否掉——掉了说明对齐前提被破坏。
5. **多轮检索**：同一批问题跑固定一轮与自主多轮两遍，比较指标 B 与每问 token 成本。
6. **GPU 索引**：算一次「数据总量 × 维度 × 每维字节数」与显存的比值。

**怎么用这份清单**：要核「能力存不存在」看官方文档与模型卡（最快）；要核「机制是不是真的」看论文（最慢但最稳）；要核「在我这里值不值得做」看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。三类之外还有一种最没用、却最常见的形式：把「某库支持亿级毫秒检索」写进方案而不写条件——它既不能被复核，也不能被证伪。

### 5.5 被过度宣传的部分

本节列四条（常规为三条）：本主题的过度宣称集中在两类——**给一个没有条件的性能数字**，以及**以为换掉链路里某一个部件，整条链路就会变好**。

**「亿级向量毫秒级检索」**——实际是：延迟与召回是一对可调参数，不是两个可以同时达到的指标（§7.3.2）。同一个索引，把查询参数调小就更快更不准，调大就更准更慢；HNSW 的召回损失还**不会报错**，只表现为「答案偶尔找不到」。**为什么会这样**：ANN 的定义就是用召回率换延迟，任何单点延迟声称都能被另一个召回目标推翻。**它什么时候才会成真**：当声称同时给出**数据量、维度、召回目标（recall@k）、硬件与是否含过滤条件**——缺一项，这个数字就不可比。**判定方法**：拿自己的语料与查询集，在固定召回目标下测延迟，而不是在固定延迟下看召回。

**「换更强的 embedding 模型就能提升 RAG」**——实际是：检索链路的瓶颈常常不在编码器，而在排序或切块（§7.3.3）。**为什么会这样**：重排的输入是候选集，它不能创造候选；而编码器只负责把候选捞进 K 条以内，如果正确片段已经在 Top-k 里但排名靠后，换编码器不解决任何问题。**它什么时候才会成真**：当指标 A 已经足够高、而指标 B 明显低——那时瓶颈才真的在排序；反过来 A 低才轮到扩召回（可能是编码器，也可能是缺字面路）。**判定方法**：先量 A 与 B 两个指标，再决定花钱的方向。

**「长上下文让分块策略成为过去」**——实际是：长上下文解决的是「编码时看不全」，解决不了「生成端 token 预算有限」。**为什么会这样**：召回与生成是两个各自最优的环节，把整篇长文档召回回来，它会挤掉真正需要的那几段（§3.5「召回 + 生成脱节」的判据：最终答案所依据的那段文字在候选里排第几）。**它什么时候才会成真**：当生成端的上下文预算与检索端的返回粒度能够对齐（例如返回精定位的片段而不是整篇）。**判定方法**：问一句「最终答案依据的那段文字，在召回候选里排第几」。

**「Agent 自主检索让检索更聪明」**——实际是：多轮检索把延迟与调用成本乘上轮数，而它不改变可达性（§5.2.2）。**为什么会这样**：它的收益来自「按问题难度伸缩」，而伸缩的前提是先能度量「一轮够不够」——这个度量今天没有现成指标。**它什么时候才会成真**：框架把「是否检索」做成可评估的默认组件，并同时上报决策质量与每问成本。**判定方法**：同一批问题跑固定一轮与自主多轮，两个数一起报。

这四条的共性：**它们都把「能力更强」当成了「结果更好」**——更强的编码器、更长的上下文、更多的检索轮次都是能力；而检索系统真正的稀缺资源是**「正确片段有没有进候选，以及它在候选里排第几」**这个判断。判断被跳过时，能力越强，账单越大。

### 5.6 未来 3–5 年：可证伪的预测

这一节写了**五条**，比常规的三到四条多一条，理由是 §5.1 表里有五组方向只有「评级」没有「信号」就会无法回填级别：长上下文（第 1 条）、Matryoshka 默认化（第 2 条）、端侧（第 3 条）、评测标准化（第 4 条）对应原趋势 1、4、8、9；第 5 条对应 §5.2.2 的本节新判断（检索决策权归属）。信号必须是外部可观察的（正式功能条目、模型卡字段、榜单规则），而不是「我觉得会」。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 长上下文的默认档位会继续上行，但**分块不会消失** | 主流模型卡把默认可编码长度推高一个档位，同时官方文档仍给出「超长时如何截断」的说明 | 出现「长文直编在所有公开评测上稳定超过分块 + 重排」的一致结果，且给出评测条件 |
| 可截断维度会成为新模型卡的**常规字段**，而不是少数模型的卖点 | 新发布的模型卡把「支持截断的嵌套长度」写进接口说明，并给出各长度的指标 | 新模型仍只公布单一维度，且明确说明截断损失不可接受 |
| 端侧检索会先落在**隐私受限**场景，而不是通用场景 | 出现给出「端侧内存预算 + 延迟 + 评测集」三者的非厂商公开报告 | 端侧方案只出现在演示里，且不给内存与延迟数字 |
| 榜单会继续被用来**缩小候选**，而选型结论会转向自有评测集 | 采购或评审材料里出现「自有查询集 + 指标 A / B」这一栏，且与榜单名次并列 | 选型讨论仍以榜单名次或性能页作为唯一依据 |
| 「是否检索」会变成一个**可评测的组件**，单轮与多轮并存而不是替代 | 框架把检索决策做成默认组件，并同时暴露决策质量指标与每问成本 | 检索决策仍写死在流程里，多轮只出现在演示中 |

写这五条时的共同约定：**信号必须是外部可观察的**（模型卡字段、官方文档条目、带条件的公开评测），而不是「我觉得会」。**被检验得最快的是第五条**——主流框架的下一个版本里有没有那个组件，一年内就能看到；**最慢的是第三条**——端侧报告的规范（内存、延迟、评测集三者齐全）形成周期通常以年计。**回填规则**：每年评审时把 §5.1 表里对应的行重判一次；若信号指向证伪那一列，级别下调而不是维持。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 还没有评测集 | 抽 200 条真实查询、人工标注正确片段，量出指标 A 与 B（§7.3.3） | 观察这两个指标能否在换模型 / 调 K / 加级时各自解释变化 | 不要在评测集之前换编码模型——换了也说不清有没有变好 |
| 检索答不对，想换模型 | 先量 A：A 低才扩召回，A 高而 B 低就上重排 | 观察漏召回样本的字面特征（编号、专名多不多） | 不要用「更强的模型」去解决排序问题 |
| 语料以编号 / 型号 / 条款为主 | 补字面路，做多路召回 + RRF（§3.2.4） | 观察混合检索与纯稠密在编号类查询上的命中差异 | 不要为这类语料上多向量——存储账先摆不平 |
| 长文档、答案跨段落 | 用自有查询比较「长文直编」与「分块 + 重排」 | 观察生成端上下文预算与返回粒度是否已对齐 | 不要在没量过指标 A 的情况下直接上多向量索引 |
| 想用 LLM 合成数据做领域适配 | 先建评测集与基线，再合成；抽 50 条合成样本人工判真假 | 观察合成偏差是否在长尾查询上暴露 | 不要让训练与评测由同一个模型合成 |
| 想上多轮自主检索 | 先量「一轮够不够」（指标 A），再设步数上限与终止条件 | 观察框架有没有把检索决策做成可评估的默认组件 | 不要把没有成本上界的多轮检索写进架构 |
| 亿级向量、内存吃紧 | 先算内存账：截断维度或量化，再用重排补精度（§7.4） | 观察压缩档位下的召回损失是否被自有评测集量出来 | 不要先买 GPU——数据驻不进显存时，收益拿不到 |
| 语料含图像 / 扫描件 | 确认「答案是否只在像素里」，是则走页面图像编码 | 观察跨模态评测集的构造方式有没有出现通行做法 | 不要用「先 OCR 再纯文本检索」硬做版面敏感的场景 |
| 有人提议接 GraphRAG | 先用 §7.3.4 的判据判断问题是否需要多跳 | 观察图与向量两条链路的边界有没有形成约定 | 不要为多跳问题之外的需求建图 |
| 预算有限，只能做一件事 | 建评测集 + 分开上报指标 A / B | 观察对不上的部分落在哪一类（召回 / 排序 / 切块 / 预算） | 不要一上来先换模型——瓶颈在哪都还不知道 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（全量重编码、索引膨胀、每问成本上升），**而收益依赖一个尚未成立的假设**（瓶颈在编码 / 长文能替代分块 / 多轮一定更好）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 LLM 真正改变的是**两个原本由工程流水线固定的位置**——**训练信号的产生**（从人写标注到模型合成 + 人抽检，落在成本函数上）与**检索的发起**（从流程写死到模型决策，落在接口边界上）。前者让没有标注预算的团队第一次能做领域适配，代价是把「合成数据的偏差」这件事交给了评测集；后者让成本随问题难度伸缩，代价是上界不明、评估面翻倍。**它没有改变的是**：编码时 query 与文档仍然互相看不见，所以「正确答案能不能被一次独立的向量比较找出来」仍是这条链路的上限（§7.3.1、§3.8）；找不到时唯一的路仍然是引入某种形式的交互——token 级 max、联合编码或稀疏路——并按 §7.3.1 的推算为它付存储。
>
> 判断本主题下任何新提法的快捷方式：**它改的是训练数据、控制流，还是只是硬件与参数？** 改训练数据的，要立刻回答「偏差谁来发现」（答案只能是自建评测集）；改控制流的，要立刻回答「轮数上界谁定」（答案只能是设计期）；只换硬件与参数的，要立刻回答「内存账算过没有」。第二个判断同样快：**这个问题需要一次向量比较，还是需要精确命中或跨段落证据？** 需要后者的，别交给更长的上下文去赌。
>
> 如果只能带走一句话：**先把评测集、指标 A / B 的分开上报、索引内存账这三件事做完，再谈换不换模型**——这三件事做完，本节表里所有 L2 都变得可评估；这三件事没做完，L2 与 L3 的差别只体现在演示里。
