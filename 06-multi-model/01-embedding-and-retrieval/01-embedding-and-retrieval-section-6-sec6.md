## 6. 落地实践

### 6.1 智源研究院"**BGE-M3：一次编码同时产出稠密、稀疏与多向量三路表示 3+ 年**"（2021-2024）

**背景（Why）**

智源研究院 2021 年面临**检索质量受限的几个具体瓶颈**：
- **中文与多语言效果不稳**——**当时主流 embedding 模型英文表现好，中文短查询与专有名词场景明显偏弱**
- **单一稠密向量覆盖不了两类查询**——**语义泛化靠稠密向量，但具体型号、编号、术语这类查询靠稠密向量常常排不准**
- **长文档被截断**——**上下文只有几百 token，长文档必须切块，切块本身就会切断语义**
- **多语言与多粒度需要多套模型**——**不同语言、不同长度的用例各自要一个模型，工程上难以统一**

**触发点（What）**

2021 年起智源研究院推进 **BGE 系列（含 BGE-M3）**（[BGE 技术报告 2021-2024]），目标：
- **一次编码产出多种检索表示**——稠密、稀疏、多向量同时得到
- **中文与多语言效果领先**——覆盖中英双语及更广语种
- **支持长输入**——减少切块对语义的破坏

**详细做法（How）**

BGE-M3 的**5 大核心组件**：

1. **"一次编码、三路输出"（核心创新）**
   - 关键设计：**同一次前向计算同时产出稠密向量（语义）、稀疏权重（词项级重要性）与多向量表示（token 级匹配）**；检索时可按场景组合这三路，而不必部署三套模型
   - 关键能力：**稠密与稀疏的互补性在一套模型内获得**——型号、编号类查询靠稀疏命中，语义泛化靠稠密覆盖，token 级匹配补足细粒度
   - 关键数字：**三路表示同源，多语言覆盖 100+ 语种**（[BGE 技术报告 2021-2024]，【公开】）
   - 关键示意：
     ```text
     文档 ─▶ chunk（500~1000 token，重叠约 15%）─▶ BGE-M3 一次编码
                                                       │
        三路输出（同一模型、同一次前向）：
          · dense   ：1024 维向量        → 语义泛化
          · sparse  ：词项权重           → 型号 / 编号 / 专有名词精确命中
          · colbert ：token 级多向量      → 细粒度交互匹配
                                                       ▼
                                    向量库（稠密）+ 倒排（稀疏）
                                                       │
     查询 q ─▶ BGE-M3 编码 ─▶ 多路混合检索（加权融合）
                                                       │
                              top-k=100 → 重排序 → top-10 → 生成
     -- 关键：三路来自同一次编码，检索侧可以按场景选路，
     --       而不需要为"稀疏"和"稠密"分别维护一套模型与一套向量化流程
     ```

2. **稀疏表示复用同一套词表思想（核心）**
   - 关键设计：**稀疏输出给出的是"词项权重"，可与关键词倒排索引体系对接**
   - 关键能力：**混合检索不必依赖传统的 BM25 配置**，语言相关的分词、停用词问题一并被模型吸收
   - 关键性质：**稀疏与稠密同源——两路出自同一次编码，稀疏侧不必再另配一套词表与调参**

3. **长输入支持（核心）**
   - 关键设计：**支持较长的输入长度**，减少"必须切得很碎才能编码"的压力
   - 关键能力：**段落级语义不容易在切块处被切断**，减少因切块策略导致的检索失败

4. **多语言统一（核心）**
   - 关键设计：**同一模型覆盖多语种**，跨语言检索不额外搭链路
   - 关键能力：**"中文查英文文档"这类跨语言检索开箱可用**
   - 关键数字：**100+ 语种、跨语言检索开箱可用**

5. **开源与可自托管（核心创新）**
   - 关键设计：**模型权重开源，可在自有环境部署**
   - 关键能力：**数据不出内网即可完成向量化**——这在金融、政企等对数据出域敏感的场景是硬门槛，也是它被广泛采用的重要原因
   - 关键性质：**"权重可下载"与"企业可落地"是两件事——自托管换到的是数据不出域与版本可控，付出的是运维与容量由使用方自己承担**

**BGE-M3 关键数字**（[BGE 技术报告 2021-2024]）：

| 指标 | 改前（主流方案） | 改后 | 提升 |
| --- | --- | --- | --- |
| **检索表示来源** | 稠密一套 + BM25 一套 | 一次编码产出三路 | **模型与流程各减一套** |
| **多语言覆盖** | 英文强、中文偏弱 | 100+ 语种 | **跨语言可用** |
| **专有名词 / 编号查询** | 稠密向量常排不准 | 稀疏路精确命中 | **盲区消除** |
| **输入长度** | 数百 token | 支持长输入 | **切块压力下降** |
| **跨语言检索** | 需额外链路 | 同模型直接可用 | **∞** |
| **部署方式** | 多为 API 调用 | 可私有化自托管 | **数据不出域** |
| **混合检索依赖** | 需配置 BM25 分词 / 停用词 | 模型内吸收 | **配置负担下降** |
| **多路融合** | 需多模型对齐 | 同源输出，易融合 | **工程成本下降** |

**具体数字（How much）**

- 团队规模：智源研究院 BGE 团队数十人，社区贡献者众多
- 关键数字：**一次编码三路输出**；**100+ 语种**；**可自托管**；**开源生态广泛采用**
- 业务影响：成为中文与多语言检索广泛采用的开源 embedding 方案，支撑大量 RAG 与检索系统

**失败教训**

- 早期「**只用稠密向量**」——型号、编号、专有名词类查询排不准，倒逼**「同模型产出稀疏路，与稠密路互补」**
- 「**稀疏依赖 BM25 配置**」——分词与停用词调优成为长期负担且与模型不匹配，倒逼**「稀疏权重由模型产出，减少人工配置」**
- 「**长文档切得很碎**」——语义在切块处被切断导致检索失败，倒逼**「支持更长输入，降低对切块策略的过度依赖」**
- 「**多语言各用一套模型**」——工程与效果双重割裂，倒逼**「单模型多语种，跨语言检索直接可用」**

### 6.2 OpenAI"**text-embedding-3：把向量维度做成可压缩的参数 3+ 年**"（2021-2024）

**背景（Why）**

OpenAI 2021 年面临**"检索质量与存储成本难以同时优化"**：
- **向量维度固定**——**模型输出多少维就存多少维，存储与检索成本无法按业务精度需求调节**
- **精度需求差异极大**——**有些场景（法律检索）要极致精度，有些场景（粗筛、去重）几百维就够**
- **换模型成本高**——**模型一换，全部向量要重算，历史数据的检索一致性被打破**
- **调用侧工程简单化诉求**——**希望"同一套接口"覆盖编码、批处理与降维**

**触发点（What）**

2021 年起 OpenAI 推进 **text-embedding 系列（含维度压缩能力）**（[OpenAI 公开材料 2021-2024]），目标：
- **维度可按需指定**——同一模型支持不同输出维度
- **精度与成本可权衡**——业务按场景选择维度
- **接口统一**——编码、批处理、降维在同一接口族内完成

**详细做法（How）**

OpenAI embedding 方案的**5 大核心组件**：

1. **"维度可指定"的压缩机制（核心创新）**
   - 关键设计：**同一模型可按请求指定输出维度**（如全套维度或截断到更小的维度），且**降维后的向量仍保持可用的语义质量**，而不是简单粗暴截断
   - 关键能力：**"精度 vs 存储"从"换模型"降级为"改一个参数"**——这让不同业务能在同一套基础设施上按自己的成本预算运行
   - 关键示意：
     ```text
     对照"换模型"与"改参数"两种降本路径
       ✗ 换更小的模型
         全部向量需重算 → 历史数据与新数据分布不一致
         → 检索一致性被打破，还要维护两套向量
       ✓ 同模型指定更小维度（本方案）
         同一模型、同一接口，仅输出维度不同
         → 精度可权衡，且不需要换掉整套向量化流程
     ────────────────────────────────────────────────
     场景化选择示例：
       精排前的粗召回 / 去重      → 较小维度，省存储与算力
       法律 / 医疗等高精度检索     → 完整维度
       跨场景同步的向量           → 统一维度，保证可比
     -- 关键：把"维度"暴露成一个显式参数，
     --       相当于把成本决策权交给业务，而不是由模型固定
     ```

2. **统一的编码 / 批处理接口（核心）**
   - 关键设计：**编码、批量编码与降维在同一接口族内**，工程侧不需要拼装多套调用
   - 关键能力：**批量入库与在线查询走同一套语义**，避免"离线用 A、在线用 B"导致的分布不一致

3. **模型版本与语义稳定性（核心）**
   - 关键设计：**版本迭代时保持接口稳定**，并明确"换版本需重算向量"的边界
   - 关键能力：**工程侧能清楚判断"什么时候必须重嵌入"**，避免新旧向量混用导致的检索质量静默下降

4. **与检索 / 向量库生态的对接（核心）**
   - 关键设计：**输出向量可直接写入主流向量库与检索系统**，不绑定特定存储
   - 关键能力：**选型自由**——模型与向量库可分别替换

5. **按场景选维度的实践约定（核心创新）**
   - 关键设计：**沉淀"什么场景用什么维度"的经验规则**，避免团队各自试错
   - 关键能力：**降本决策有参照**，而不是凭感觉砍维度导致检索质量塌陷

**OpenAI embedding 方案关键数字**（[OpenAI 公开材料 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **向量维度** | 模型固定 | 可按请求指定 | **成本可按场景调** |
| **降本方式** | 换更小模型（需重算全部向量） | 改一个参数 | **不必换流程** |
| **历史向量一致性** | 换模型即打破 | 同模型内保持可比 | **一致性可控** |
| **接口数量** | 编码 / 批处理 / 降维分散 | 统一接口族 | **工程简单** |
| **离线在线一致性** | 常因方案不同而分叉 | 同一套接口 | **同源** |
| **模型与存储绑定** | 部分方案强绑定 | 输出可写主流向量库 | **选型自由** |
| **版本切换边界** | 不清晰 | 明确"需重算"的边界 | **避免静默质量下降** |
| **维度选择依据** | 凭感觉 | 按场景约定 | **有据可依** |

**具体数字（How much）**

- 团队规模：OpenAI 团队数千人，embedding 由其平台团队维护
- 关键性质：**维度可配**；**接口统一**；**离线在线同源**；**生态兼容**
- 业务影响：让使用方在同一套基础设施上按场景权衡精度与成本，被大量 RAG 系统采用

**失败教训**

- 早期「**向量维度由模型固定**」——精度需求低的场景也要付出完整维度的存储成本，倒逼**「把维度做成可指定参数，降维后仍保持语义质量」**
- 「**用换小模型的方式降本**」——全部向量需重算，历史与新数据分布不一致，倒逼**「同模型内调整维度，避免打破一致性」**
- 「**离线与在线用不同方案编码**」——同一文本两处向量不一致，检索结果不可复现，倒逼**「统一接口族，离线在线同源」**
- 「**版本切换边界不明**」——新旧向量混用导致检索质量静默下降，倒逼**「明确"必须重算"的版本边界」**

### 6.3 Cohere"**用 input_type 区分查询与文档：把"非对称检索"做成接口的一部分 3+ 年**"（2021-2024）

**背景（Why）**

Cohere 2021 年面临**"查询与文档不对称"被普遍忽视**：
- **查询短、文档长**——**用同一个向量空间、同一种编码方式处理两者，效果并非最优**
- **使用者常犯的错误**——**把文档向量和查询向量用完全相同的处理方式生成，甚至复用同一批缓存的向量**
- **多语言与多场景**——**检索、分类、聚类对向量的期望不同**
- **企业场景的部署约束**——**部分客户要求私有化部署**

**触发点（What）**

2021 年起 Cohere 推进 **Embed 系列（区分输入类型与用途）**（[Cohere 公开材料 2021-2024]），目标：
- **显式区分查询与文档编码**——把非对称性做进接口
- **多场景适配**——检索 / 分类 / 聚类各有对应处理
- **企业可部署**——支持私有化

**详细做法（How）**

Cohere Embed 方案的**5 大核心组件**：

1. **input_type：把"这段文本是查询还是文档"变成必填参数（核心创新）**
   - 关键设计：**调用时必须声明输入类型（查询 / 文档）**，模型据此采用不同的编码路径；这使"查询短、文档长"的不对称性在接口层被显式表达
   - 关键能力：**避免使用者把查询当文档编码**——这是检索效果最容易出问题、也最难自查的一个点
   - 关键性质：**非对称性从使用者的经验问题变成接口的必填参数——漏填或填错在调用层立刻暴露**
   - 关键示意：
     ```text
     对称 vs 非对称：为什么"用同一种方式编码两侧"会损失效果
       对称做法（常见但次优）
         query  ─编码─▶ v_q ┐
                            ├─ 同一空间、同一路径
         doc    ─编码─▶ v_d ┘
         → 查询通常只有几个词、文档有几百字，二者分布本就不对称
       ────────────────────────────────────────────────
       非对称做法（本方案）
         embed(texts=[...], input_type="search_document")  → v_d
         embed(texts=[...], input_type="search_query")     → v_q
         → 模型为两类输入采用不同编码路径，检索时再比对
     -- 关键：把"非对称"从使用者的经验问题，变成接口的必填参数
     --       漏填或填错会在调用层立刻暴露，而不是半年后在效果指标上才发现
     ```

2. **按用途区分的任务类型（核心）**
   - 关键设计：**检索、分类、聚类等用途各有对应的输入类型**
   - 关键能力：**同一模型服务多类下游任务**，不必为每类任务各选一个模型

3. **多语言支持（核心）**
   - 关键设计：**同一模型覆盖多语种**，跨语言检索无需额外链路
   - 关键能力：**多语言知识库开箱可用**

4. **私有化与部署灵活性（核心）**
   - 关键设计：**除 API 外支持在客户环境部署**
   - 关键能力：**数据不出域即可完成向量化**——对金融、政企客户是硬性要求

5. **批量与在线一致（核心创新）**
   - 关键设计：**批量入库与在线查询使用同一套模型与同一套输入类型约定**
   - 关键能力：**避免"离线用文档类型、在线忘了用查询类型"这类不一致**

**Cohere Embed 方案关键数字**（[Cohere 公开材料 2021-2024]）：

| 指标 | 改前（常见做法） | 改后 | 提升 |
| --- | --- | --- | --- |
| **查询 / 文档编码方式** | 同一路径处理 | input_type 区分 | **非对称性显式化** |
| **参数漏填风险** | 无提示，效果静默下降 | 必填，调用即暴露 | **问题前置** |
| **多任务模型数量** | 各任务各选模型 | 同一模型多任务 | **模型数下降** |
| **多语言** | 需额外链路 | 同模型覆盖 | **∞** |
| **部署方式** | 多为 API | 可私有化 | **数据不出域** |
| **离线在线一致性** | 常因类型不符而不一致 | 同一套约定 | **一致** |
| **检索效果自查** | 依赖效果指标才发现 | 接口层即可检查 | **可自查** |
| **企业合规场景** | 常因不可私有化被排除 | 可部署到客户环境 | **∞** |

**具体数字（How much）**

- 团队规模：Cohere 团队数百人
- 关键性质：**input_type 显式区分**；**多任务共用模型**；**可私有化**；**离线在线一致**
- 业务影响：把非对称检索这一"经验性最佳实践"固化成接口约定，降低使用者的隐性踩坑率

**失败教训**

- 早期「**查询与文档用同一路径编码**」——检索效果长期偏低但难以定位原因，倒逼**「把输入类型做成必填参数，非对称显式化」**
- 「**把非对称性写进文档当"最佳实践"**」——文档没人看，实际使用中大量漏用，倒逼**「做成接口必填参数，漏填即暴露」**
- 「**每类任务各选一个模型**」——模型数量与运维成本膨胀，倒逼**「同一模型按用途区分输入类型」**
- 「**只提供 API**」——有数据出域要求的客户无法使用，倒逼**「支持私有化部署」**

### 6.4 Voyage"**为长文档与领域检索做专用 embedding 3+ 年**"（2022-2024）

**背景（Why）**

Voyage 2022 年面临**通用 embedding 在专业与长文档场景的明显短板**：
- **长文档必须切块**——**一份几十页的合同被切成几十块，单块语义碎片化，检索时难以判断"整份文档是否相关"**
- **领域术语效果差**——**法律、金融、代码等领域的专有表达，通用模型区分度不足**
- **检索精度的商业价值**——**在这些场景里，检索错一条的代价远高于普通搜索**
- **成本与精度的取舍**——**客户既想用大模型级别的效果，又受限于向量存储与检索成本**

**触发点（What）**

2022 年起 Voyage 推进**面向长文档与领域的 embedding 模型**（[Voyage 公开材料 2022-2024]），目标：
- **长文档可整篇表示**——减少切块带来的语义碎片化
- **领域效果优先**——按行业提供更合适的模型
- **与检索栈可分离**——模型与向量库可独立替换

**详细做法（How）**

Voyage embedding 方案的**5 大核心组件**：

1. **长上下文：让"整篇文档一个向量"成为可能（核心创新）**
   - 关键设计：**支持长的输入长度，使整篇文档（而非切块）可被编码为单个向量**；对于"判断整份文档是否相关"的场景，避免切块造成的语义碎片
   - 关键能力：**"文档级"检索与"片段级"检索可以并存**——整篇向量用于召回文档，片段向量用于定位内容
   - 关键示意：
     ```text
     切块检索 vs 文档级单向量：适用场景不同
       切块检索（片段级）
         长文档 ─切块─▶ [块1][块2]…[块N] ─编码─▶ 多向量
         适合：回答"文档里哪一段提到了 X"
         风险：单块语义碎片化 → 判断"整份文档是否相关"容易出错
       ────────────────────────────────────────────────
       文档级单向量（长上下文）
         长文档 ─整篇编码─▶ 单向量
         适合：召回"相关文档"、判定文档整体主题
         收益：不做切块决策，避免切块策略本身成为效果瓶颈
       ────────────────────────────────────────────────
       实践：两级并存
         文档级向量做粗召回 → 命中后再用片段级向量定位具体位置
     -- 关键：长上下文不是"更长的切块"，而是提供了"不切块"这个选项
     ```

2. **领域化模型（核心）**
   - 关键设计：**按领域（法律 / 金融 / 代码等）提供更适配的模型**
   - 关键能力：**领域术语区分度更高**，检索精度在专业场景明显改善
   - 关键性质：**领域精度是"用通用性换"来的——选型与评测要按领域分别做，"一个模型覆盖全部场景"的省事不再成立**

3. **量化与维度权衡（核心）**
   - 关键设计：**支持向量量化与维度选择**，在保持精度的前提下降低存储与检索成本
   - 关键能力：**"精度不塌陷的降本"**——量化与降维在合适的范围内对检索质量影响可控
   - 关键性质：**量化与降维换成本，代价是精度存在边界——"不塌陷"是前提条件，不是无条件的保证**

4. **模型与检索栈解耦（核心）**
   - 关键设计：**输出向量可写入任意主流向量库**，模型与存储分别演进
   - 关键能力：**换模型不必换存储，换存储不必换模型**

5. **批处理与在线查询同源的工程约定（核心创新）**
   - 关键设计：**入库与查询使用同一模型版本与同一套输入类型约定**，并把"何时必须重嵌入"写清楚
   - 关键能力：**避免新旧向量混用导致的检索质量静默下降**

**Voyage embedding 方案关键数字**（[Voyage 公开材料 2022-2024]）：

| 指标 | 改前（切块 + 通用模型） | 改后 | 提升 |
| --- | --- | --- | --- |
| **长文档处理** | 必须切块，语义碎片化 | 长上下文，可整篇单向量 | **切块不再是必然** |
| **文档级相关性判断** | 依赖块级拼凑 | 文档级向量直接判断 | **准确率提升** |
| **领域术语区分度** | 通用模型偏低 | 领域模型 | **专业场景改善** |
| **存储与检索成本** | 全精度存储 | 量化 / 维度权衡 | **成本可降** |
| **提升方式** | 换模型需换全部链路 | 支持维度与量化参数 | **温和调优** |
| **模型与存储** | 常强绑定 | 解耦，可独立替换 | **选型自由** |
| **版本切换** | 边界不清 | 明确"需重嵌入"条件 | **避免静默下降** |
| **两级检索** | 不支持文档级 | 文档级粗召 + 片段级定位 | **∞** |

**具体数字（How much）**

- 团队规模：Voyage 团队数十人
- 关键性质：**长上下文整篇编码**；**领域模型**；**量化与维度权衡**；**模型与存储解耦**
- 业务影响：为法律、金融、代码等专业检索场景提供更合适的 embedding，并支持两级检索结构

**失败教训**

- 早期「**长文档一律切块**」——单块语义碎片化，判断"整份文档是否相关"频繁出错，倒逼**「提供长上下文，允许整篇编码为单向量」**
- 「**用通用模型做专业检索**」——领域术语区分度不足导致检索精度不够，倒逼**「按领域提供适配模型」**
- 「**只靠降维来省成本**」——精度塌陷且不可逆，倒逼**「量化与维度权衡，在可控范围内优化」**
- 「**模型与向量库强绑定**」——换任一侧都要重构整条链路，倒逼**「输出向量与检索栈解耦」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**一个开源 embedding（可自托管）+ 一种向量库 + 固定切块策略**」（**最简单**）——**1 个场景、十万级片段**
- 产出：**切块策略文档 + 检索评测集（含"检索不到"的负样本）+ 向量入库与查询同源的约定**
- 团队：**2-3 人**
- 验证标准：**入库与查询使用同一模型版本与同一输入约定**、**评测集上有召回基线**、**能区分"召回漏了"与"排序错了"**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 场景 / 百万级片段 / 多语言**」
- 引入「**非对称处理（查询与文档编码区分）**」——把非对称性做成显式约定
- 引入「**稠密 + 稀疏混合检索**」——覆盖专有名词与编号类查询
- 团队：5-10 人
- 验证标准：**专有名词查询命中改善**、**非对称约定被强制执行（漏用即暴露）**、**多语言可检索**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 场景 / 亿级 / 长文档**」
- 引入「**长上下文支持与文档级单向量**」——两级检索：文档级粗召 + 片段级定位
- 引入「**维度 / 量化权衡**」——在精度可控前提下降低存储与检索成本
- 团队：10-30 人
- 验证标准：**文档级相关性判断改善**、**存储成本下降且检索质量不塌陷**、**模型与向量库可独立替换**

**100 → 1000 阶段：12-24 个月**

- 引入「**领域化模型选择**」——按业务领域选适配模型
- 引入「**版本边界与重嵌入流程**」——明确"何时必须重算"并支持灰度切换
- 团队：30-100 人
- 验证标准：**换模型有明确边界与灰度路径**、**专业场景检索精度达标**、**新旧向量不混用（无静默质量下降）**

### 6.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**检索表示来源**」 | 稠密一套 + 关键词一套 | 一次编码产出多路 | **模型与流程各减一套** |
| 「**专有名词 / 编号查询命中**」 | 稠密向量常排不准 | 稀疏路精确命中 | **盲区消除** |
| 「**查询 / 文档处理**」 | 同一路径（次优） | 非对称显式区分 | **效果提升且问题前置** |
| 「**长文档处理**」 | 必须切块，碎片化 | 长上下文，可整篇单向量 | **切块不再是必然** |
| 「**文档级相关性判断**」 | 依赖块级拼凑 | 文档级向量判断 | **准确率提升** |
| 「**存储 / 检索成本**」 | 固定全维度高精度 | 维度 / 量化可权衡 | **成本可按场景下调** |
| 「**降本代价**」 | 换模型需重算全部向量 | 同模型内调参 | **一致性不被打破** |
| 「**离线在线一致性**」 | 常因方案不同而不一致 | 同模型同约定 | **可复现** |
| 「**多语言 / 跨语言**」 | 额外链路 | 单模型覆盖 | **∞** |
| 「**部署约束（数据出域）**」 | 仅 API | 可自托管 / 私有化 | **∞** |

**关键投资回报**：
- **直接节省**：「**模型与流程各减一套 + 维度可权衡 + 存储成本可下调**」——**embedding 方案的成本不只是模型调用费，还包括"多套模型、多套流程、额外链路"带来的工程与运维开销**；把多路表示合并到一次编码、把维度暴露成参数，省下的是长期的基础设施与人力
- **业务价值**：「**专有名词盲区消除 + 文档级检索可行 + 离线在线可复现**」——**检索质量的上限由 embedding 方案决定**：稠密单路必然在型号编号类查询上失分，切块必然在文档级判断上失分；这两类问题的改善往往直接对应检索可感知的效果提升
- **AI 时代关键**：「**非对称检索显式化 + 长上下文（不切块）选项 + 版本边界清晰**」——**这是 RAG 与 Agent 检索的地基**：把"查询与文档不对称""何时必须重嵌入"这类隐性经验做成显式约定与参数，才能让检索质量不随团队更替而漂移；而"不切块"这个选项则让文档级语义第一次可以被直接检索

---

> **本节小结**：
> - 4 个真实案例（智源 BGE-M3 / OpenAI / Cohere / Voyage）印证：**Embedding 不是「选个模型调 API」，是「多路表示同源 + 非对称检索显式化 + 长上下文选项 + 维度与量化可权衡 + 版本边界清晰」5 件套**。
> - 关键时间线：BGE-M3 3+ 年 / OpenAI 3+ 年 / Cohere 3+ 年 / Voyage 2+ 年 —— **embedding 方案是持续演进的基础设施**，且**决定检索上限的往往是"表示形态与约定"，而不是模型排行榜上的分数**。
> - 选型第一原则：「**开源可自托管 + 单向量库 + 固定切块 + 评测集**」（**最简单**）——**1 个场景** → 「**非对称约定 + 稠密稀疏混合**」（**必须**）→ 「**长上下文与文档级向量 + 维度量化权衡**」（**生产**）→ 「**领域模型 + 版本边界与灰度重嵌入**」（**AI 时代**）。
> - 99% 的失败来自「**只用稠密单路 + 查询文档同路编码 + 一律切块 + 离线在线不一致**」——必须有 **混合多路 + 非对称显式 + 长上下文选项 + 同源约定**。
> - 真正的 ROI 来自「**盲区消除 + 文档级检索可行 + 成本可权衡 + 结果可复现**」——是**搜索、RAG 与 Agent 检索质量能否真正上台阶的分水岭**。

> 💡 **思考锚点**：把你现在的规模（场景数 / 片段量级 / 团队人数）对到 6.5 的四档里，只检查这一档的验证标准——「入库与查询同模型版本同输入约定」和「能区分召回漏了还是排序错了」这两条，你现在能当场跑出来吗？答否，说明你已在用下一档的功能（混合检索 / 文档级单向量）补当前档没打好的地基。
