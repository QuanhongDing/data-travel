### 2.1 Snowflake"**把 LLM 调用做成 SQL 函数：成本与治理同时收进数仓 3+ 年**"（2021-2024）

**背景（Why）**

Snowflake 2021 年面临**"LLM 能力在数仓之外"带来的三类问题**：
- **数据要出仓**——**客户数据已在数仓里，做摘要、分类却要把数据导出到应用侧**
- **成本两套账**——**LLM 调用成本与数仓用量分属两套账单，无法归因到具体业务**
- **结果脱离治理**——**LLM 产出的标签落在数仓外，权限与血缘断链**

**触发点（What）**

2021 年起 Snowflake 推进 **Cortex AI Functions**（[Snowflake 公开材料 2021-2024]），目标：
- **LLM 调用 SQL 化**——像内置函数一样使用
- **数据不出仓**——推理在数仓内完成
- **成本与治理统一**——沿用既有账务与权限体系

**详细做法（How）**

Snowflake Cortex 在 SQL 层的**5 大核心组件**：

1. **LLM 调用与内置函数同语法（核心创新）**
   - 关键设计：**摘要、分类、情感、翻译、补全等以 SQL 函数暴露**，与 `SUM` / `SUBSTR` 在语法层面无差别；调用参数（模型档位、温度等）作为函数参数表达
   - 关键能力：**"要不要用 LLM"从架构决策降级为一次函数选择**——这是 LLM 在数据分析工作流里能普及的前提
   - 关键性质：**函数化调用、免自建推理服务**
   - 关键示意：
     ```sql
     -- LLM 调用与内置函数同语法，结果直接落表
     CREATE OR REPLACE TABLE review_enriched AS
     SELECT review_id,
            review_text,
            ai_classify(review_text, ARRAY('好评','差评','中性')) AS sentiment,
            ai_summarize(review_text)                             AS summary,
            ai_complete('按要点给出建议', review_text)             AS suggestion
     FROM   reviews
     WHERE  ds = CURRENT_DATE;

     -- 产出的表沿用原有权限与血缘，成本计入同一套用量口径
     ────────────────────────────────────────────────
     对照"导出到应用侧的 LLM 服务"：
       导出数据 → 调用外部服务 → 结果写回 → 权限与血缘要重建一遍
       且此时"这批标签是谁授权生成的"已无法从数仓侧回答
     -- 关键：把 LLM 当作数仓内置能力，而不是一个外部系统
     ```

2. **SQL 层的 token 与成本控制（核心）**
   - 关键设计：**按行调用的成本可预估**（输入长度 × 行数），客户可在 SQL 里先做过滤与采样再调用；批量作业与交互查询的成本口径统一
   - 关键能力：**"这条 SQL 大概要花多少钱"在提交前可估算**——LLM 进入分析流程后，成本控制必须前移
   - 关键性质：**成本可预估、可按业务归因**

3. **提示词模板随 SQL 版本化（核心）**
   - 关键设计：**提示词写在 SQL / 视图定义中，与 SQL 一起进入版本管理**，而不是散落在应用代码里
   - 关键能力：**"这份标签是用哪版提示词生成的"可查**——提示词变了效果就变，不版本化就无法归因
   - 关键性质：**提示词随 SQL 版本化**

4. **结构化输出的强约束（核心）**
   - 关键设计：**分类、抽取类调用要求按固定枚举或结构返回**，返回不符合约束的行被识别并按策略处理（重试 / 置空 / 拒绝）
   - 关键能力：**避免把自由文本塞进结构化列**——"模型偶尔返回一句解释"这类问题会让下游全部出错
   - 关键性质：**结构化输出校验、非法值可识别**

5. **结果落表与治理延续（核心创新）**
   - 关键设计：**LLM 产出直接写为普通表**，权限、血缘、质量规则照常生效
   - 关键能力：**AI 产出的数据不是治理盲区**——这是企业级 LLM 分析能过合规评审的关键
   - 关键数字：**治理延续 100%**

**Snowflake Cortex SQL 层关键数字**（[Snowflake 公开材料 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **LLM 调用方式** | 导出数据 + 外部服务 | SQL 函数调用 | **免自建服务** |
| **数据出仓** | 需导出 | 不外流 | **-100%** |
| **成本口径** | 两套账单，难归因 | 与数仓用量统一 | **可归因** |
| **提示词管理** | 散落在应用代码 | 随 SQL 版本化 | **可追溯** |
| **结构化输出** | 自由文本，下游易错 | 枚举 / 结构强约束 + 校验 | **非法值可识别** |
| **结果治理** | 落在仓外，断链 | 落表，权限血缘延续 | **100%** |
| **成本可预估** | 提交后才知道 | 按输入长度与行数预估 | **可前移控制** |
| **客户规模** | 0 | 10000+ | **∞** |

**具体数字（How much）**

- 团队规模：Snowflake 工程团队数千人
- 关键数字：**10000+ 客户**
- 业务影响：让不具备 AI 工程能力的数据团队直接在数仓内做文本理解类分析

**失败教训**

- 早期「**导出数据到应用侧调 LLM**」——合规与治理双失守，倒逼**「推理下推到数仓内，调用函数化」**
- 「**LLM 成本与数仓用量分账**」——无法归因、预算失控，倒逼**「统一用量口径 + 提交前成本预估」**
- 「**提示词写在应用代码里**」——换提示词后效果变化无法追溯，倒逼**「提示词随 SQL 一起版本化」**
- 「**让模型自由输出文本**」——结构化列里混入解释性文字导致下游解析失败，倒逼**「枚举 / 结构强约束 + 非法值校验」**

### 2.2 Databricks"**ai_query 与推理结果入表：让模型版本成为血缘的一部分 3+ 年**"（2021-2024）

**背景（Why）**

Databricks 2021 年面临**"模型推理不入治理"**：
- **数据加工在 SQL / DataFrame，模型调用在 Python**——**两种表达来回切，中间多一次数据落地**
- **推理结果落在临时位置**——**不纳入血缘，下游不知道这张表是怎么来的**
- **换模型是"隐形变更"**——**下游表的语义其实变了，但血缘里看不出来，没有人为下游受影响负责**
- **成本混杂**——**模型调用与数据计算混在一起，无法按业务拆分**

**触发点（What）**

2021 年起 Databricks 推进**模型调用接入 SQL 层（推理结果入表、模型入血缘）**（[Databricks 公开材料 2021-2024]），目标：
- **调用成为 SQL 表达式**——同一执行计划内完成
- **结果即表**——与普通表同等治理
- **模型版本可追**——换模型前列出受影响下游

**详细做法（How）**

Databricks SQL 层 LLM 能力的**5 大核心组件**：

1. **模型调用作为 SQL 表达式（核心创新）**
   - 关键设计：**推理以 SQL 函数 / 表达式调用**，输入是列、输出是新列，整条加工链路仍是一句 SQL
   - 关键能力：**"数据处理 + 模型推理"在同一执行计划内**，不再需要"出表 → Python → 调模型 → 写回"的往返
   - 关键数字：**推理 100% 在 SQL 内完成、无中间落地**
   - 关键示意：
     ```sql
     -- 推理结果直接落为普通表，与常规 ETL 无异
     CREATE OR REPLACE TABLE doc_insights AS
     SELECT doc_id,
            doc_text,
            ai_classify(doc_text, ARRAY('合同','发票','报告','其他')) AS doc_type,
            ai_extract(doc_text, '{"amount":"decimal","date":"date","party":"string"}')
                                                                   AS extracted,
            ai_query('llm-endpoint', CONCAT('用一句话概括：', doc_text)) AS summary
     FROM   raw_docs
     WHERE  ds = CURRENT_DATE;

     -- 血缘中记录：该表由哪个 endpoint / 模型生成
     -- 换模型前可据此列出受影响的下游表与作业
     ────────────────────────────────────────────────
     关键：让"调模型"看起来像"加一列"，
           治理（血缘 / 权限 / 质量）才能自动跟上
     ```

2. **模型 / endpoint 作为血缘节点（核心）**
   - 关键设计：**模型或 endpoint 是血缘图中的一类节点**，与表、作业并列
   - 关键能力：**"换这个模型会影响哪些表"可查询**——这让模型迭代从"高风险变更"变成"可评估变更"
   - 关键性质：**模型影响力可查**

3. **结构化抽取的 schema 化（核心）**
   - 关键设计：**抽取类调用以 schema 描述输出结构**，输出与 schema 不符的行被识别处理
   - 关键能力：**LLM 抽取结果能安全进入结构化表**，而不是留成一坨文本
   - 关键性质：**抽取输出可校验**

4. **按业务归因的用量统计（核心）**
   - 关键设计：**模型调用量与数据计算量按作业 / 业务维度统计**
   - 关键能力：**"这个业务在 LLM 上花了多少"可回答**——成本归因是 LLM 铺开的前置条件
   - 关键性质：**用量可按业务归因**

5. **影子执行与灰度（核心创新）**
   - 关键设计：**换模型时先对同一批数据跑"影子表"**，对比新旧输出差异，达标后再切换主表
   - 关键能力：**模型切换有可量化的验证过程**，而不是"换了以后看业务反馈"
   - 关键性质：**切换前有对比验证**

**Databricks SQL 层 LLM 关键数字**（[Databricks 公开材料 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **推理调用位置** | Python 作业 | SQL 表达式 | **同一执行计划** |
| **中间数据落地** | 出表 → Python → 写回 | 无往返 | **-100%** |
| **推理结果治理** | 落临时位置，血缘不全 | 落普通表，完整血缘 | **∞** |
| **模型版本可见性** | 只在代码里 | 血缘中的节点 | **影响面可查** |
| **换模型的风险评估** | 凭经验 | 按血缘列下游 + 影子对比 | **可量化** |
| **结构化抽取** | 自由文本 | schema 约束 + 校验 | **可入结构化表** |
| **成本归因** | 与数据计算混合 | 按作业 / 业务统计 | **可归因** |
| **企业客户** | 0 | 10000+ | **∞** |

**具体数字（How much）**

- 团队规模：Databricks 团队 5000+ 人
- 关键数字：**10000+ 客户**
- 业务影响：让数据工程与模型推理共用一套表达与治理体系，服务全球 10000+ 企业

**失败教训**

- 早期「**SQL 加工 + Python 调模型**」——来回切且多一次落地，倒逼**「模型调用作为 SQL 表达式，同一执行计划内完成」**
- 「**推理结果落临时位置**」——脱离血缘与权限，倒逼**「结果落为普通表，纳入统一治理」**
- 「**换模型血缘无感知**」——下游语义已变却无人知道，倒逼**「模型 / endpoint 作为血缘节点，换版前列下游」**
- 「**抽取输出直接当文本用**」——下游无法解析且无法校验，倒逼**「按 schema 约束输出并校验非法行」**

### 2.3 阿里"**MaxCompute PAI UDF：把批处理 LLM 的成本与数据边界一起管住 5+ 年**"（2019-2024）

**背景（Why）**

阿里 2019 年面临**"EB 级数据上做 LLM 批处理"的硬约束**：
- **数据量决定成本**——**LLM 按 token 计费，在 EB 级数据上"全量调一遍"成本不可承受**
- **数据不能出域**——**导出到外部服务既不经济也不合规**
- **批处理与在线推理要求不同**——**离线打标可以慢、但要便宜；在线查询要快、量小**
- **特征与推理不同源**——**离线特征用 SQL 算、推理侧又算一遍**

**触发点（What）**

2019 年起阿里推进 **MaxCompute + PAI 的 AI UDF 与一体化链路**（[阿里 MaxCompute / PAI 公开材料 2019-2024]），目标：
- **推理在仓内执行**——数据不出仓
- **批处理成本可控**——先筛选再调用
- **特征与推理同源**

**详细做法（How）**

阿里仓内 LLM 批处理的**5 大核心组件**：

1. **"先筛选、再调用"的成本前置（核心创新）**
   - 关键设计：**在 SQL 里先用条件与去重把候选集缩到必要规模，再对候选集调用 LLM**；对已处理过的数据用增量键跳过
   - 关键能力：**LLM 成本与"实际需要处理的数据量"挂钩，而不是与全表行数挂钩**——这是 EB 级数据上做 LLM 批处理能负担得起的关键
   - 关键性质：**成本随必要数据量而非表规模增长**
   - 关键示意：
     ```sql
     -- 成本控制的关键不在模型档位，而在"让多少行进入调用"
     INSERT INTO doc_labels
     SELECT d.doc_id,
            ai_classify(d.doc_text, ARRAY('投诉','咨询','建议')) AS label
     FROM   raw_docs d
     LEFT JOIN doc_labels_existing e ON d.doc_id = e.doc_id
     WHERE  d.ds = CURRENT_DATE
       AND  d.text_len BETWEEN 20 AND 2000   -- ① 排除过短/过长（无信息或超长贵）
       AND  e.doc_id IS NULL                 -- ② 增量：已标注的不再调用
       AND  d.source IN ('app','web');       -- ③ 只处理需要的来源
     ────────────────────────────────────────────────
     对比："全量调一遍"
       全表 10 亿行 × 每行 500 token → 成本量级完全不同
     而实际真正需要新增标注的可能只有几百万行
     -- 关键：LLM 批处理的成本杠杆在 SQL 的过滤与增量逻辑里，不在模型选择上
     ```

2. **数据不出仓的 UDF 形态（核心）**
   - 关键设计：**LLM 能力以 UDF 形式在仓库内可用**，输入是列、输出是新列
   - 关键能力：**合规与成本同时改善**——省掉导出，也省掉出域风险
   - 关键数字：**导出 0**

3. **批处理与在线用不同档位（核心）**
   - 关键设计：**离线批处理用更经济的模型档位，在线交互用更强的档位**；两者按场景分流
   - 关键能力：**成本与质量的权衡落在"任务分档"上**，而不是一个档位打天下
   - 关键性质：**任务分档、成本与质量各取所需**

4. **失败行与重试策略（核心）**
   - 关键设计：**调用失败或输出不合规的行单独落表**，可单独重跑而不必整批重来
   - 关键能力：**批处理的可恢复性**——EB 级作业不可能因少量失败行整体重跑
   - 关键性质：**失败行可单独重跑**

5. **提示词与模型版本随作业记录（核心创新）**
   - 关键设计：**作业产出记录"用了哪版提示词、哪个模型"**
   - 关键能力：**标签口径变化可归因**，而不是"这批标签和上批不一样但不知道为什么"
   - 关键性质：**版本可追溯**

**阿里仓内 LLM 批处理关键数字**（[阿里 MaxCompute / PAI 公开材料 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **LLM 调用位置** | 导出到外部服务 | 仓内 UDF | **数据不出仓** |
| **成本与数据量的关系** | 与全表行数挂钩 | 与必要候选集规模挂钩 | **显著下降** |
| **重复标注** | 每次全量重跑 | 增量键跳过已处理 | **成本按增量增长** |
| **数据导出流量** | 全量导出 | 0 | **-100%** |
| **任务分档** | 单一档位 | 离线 / 在线分档 | **成本与质量各取所需** |
| **失败处理** | 整批重跑 | 失败行单独重跑 | **可恢复** |
| **提示词 / 模型版本** | 无记录 | 随作业记录 | **可追溯** |
| **数据规模** | PB | EB | **1000x** |

**具体数字（How much）**

- 团队规模：阿里 MaxCompute + PAI 团队 500+ 人
- 关键数字：**导出 0**；**数据规模 PB → EB（1000x）**
- 业务影响：支撑阿里集团内在 EB 级数据上的文本理解批处理，并向云上客户输出

**失败教训**

- 早期「**把全表数据都调一遍 LLM**」——成本随表规模上升且大量重复处理，倒逼**「先筛选 + 增量跳过，让成本与必要数据量挂钩」**
- 「**导出到外部服务调用**」——成本与合规双输，倒逼**「仓内 UDF，数据不出仓」**
- 「**离线与在线用同一档位**」——离线批处理成本过高或在线体验不足，倒逼**「按任务分档」**
- 「**少量失败行导致整批重跑**」——EB 级作业无法承受，倒逼**「失败行单独落表并单独重跑」**

### 2.4 MotherDuck"**本地与云端混合执行：把 LLM 查询放在数据所在的位置 2+ 年**"（2022-2024）

**背景（Why）**

MotherDuck 2022 年面临**"分析数据天然分散"的现实**：
- **数据体量的极端分化**——**核心事实表很大（云端），但很大一部分分析用的数据其实很小（本地文件、CSV、小表）**
- **全部上传云端成本高**——**为了分析一个本地小文件把数据传上去，传输成本与等待时间都不划算**
- **本地有算力闲置**——**客户端机器有计算能力，却只用来发请求**
- **LLM 查询的额外约束**——**LLM 调用按 token 计费且需要联网，处理"只需要本地数据"的任务时不必要地产生了上传与调用成本**

**触发点（What）**

2022 年起 MotherDuck 推进**本地与云端混合执行的查询引擎**（[MotherDuck 公开材料 2022-2024]），目标：
- **按数据位置选择执行位置**——本地数据本地算，云上数据云上算
- **减少不必要的上传与传输**
- **LLM 调用按必要性触发**

**详细做法（How）**

MotherDuck 混合执行的**5 大核心组件**：

1. **"数据在哪，算在哪"的执行计划切分（核心创新）**
   - 关键设计：**查询被拆成可在本地与云端分别执行的部分**——本地表在本地处理、云端表在云端处理，中间只交换必要的中间结果
   - 关键能力：**避免"为了 JOIN 一个本地小表把大数据搬来搬去"**——传输量与执行位置都由优化器决定
   - 关键性质：**不必要传输大幅减少**
   - 关键示意：
     ```text
     混合执行：按数据位置切分计划，只交换必要中间结果
       查询：本地 CSV（小） ⋈ 云端事实表（大）
       ✗ 全部上传模式
         本地 CSV ─上传─▶ 云端 ─▶ 云端执行 JOIN ─▶ 返回结果
         问题：小文件上传尚可接受，但若本地数据稍大就变成传输瓶颈
       ✓ 混合执行模式
         本地：扫描 CSV + 过滤 / 聚合 → 中间结果（小）
         云端：扫描事实表 + 与中间结果 JOIN
         结果：回传客户端
     ────────────────────────────────────────────────
     对 LLM 查询的延伸：
       若某个 LLM 调用只依赖本地数据 → 在本地执行，数据不出机器
       若依赖云端大表 → 在云端执行，只回传结果
     -- 关键：把"执行位置"当作优化器的一个决策，
     --       而不是让使用者按数据位置手工拆分查询
     ```

2. **本地算力参与执行（核心）**
   - 关键设计：**客户端承担本地数据的处理**，云端负责大表与全局聚合
   - 关键能力：**本地闲置算力被用起来**，同时减少云端计算量
   - 关键性质：**云端计算量下降**

3. **LLM 调用的必要性判定（核心）**
   - 关键设计：**先判断某个 LLM 调用是否必要**（如本地规则或已有标签能否满足），必要时才调用；对可本地完成的任务不上云
   - 关键能力：**LLM 成本与"是否真的需要模型"挂钩**，而不是"每条数据都调一次"
   - 关键性质：**调用量按必要性收敛**

4. **提示词与结果在本地可控（核心）**
   - 关键设计：**本地处理的提示词与结果可留在本地**，不必上传
   - 关键能力：**对数据敏感的场景可在本地完成一部分 LLM 相关工作**，减少数据外流
   - 关键性质：**本地可闭环的场景数据不外流**

5. **开发体验一致（核心创新）**
   - 关键设计：**同一套 SQL / API 覆盖本地与云端**，使用者不必学两套
   - 关键能力：**"混合执行"对使用者是透明的**——否则为了省传输而要手工拆分查询，反而增加复杂度
   - 关键性质：**同一套接口、对使用透明**

**MotherDuck 混合执行关键数字**（[MotherDuck 公开材料 2022-2024]）：

| 指标 | 改前（全上传模式） | 改后 | 提升 |
| --- | --- | --- | --- |
| **执行位置** | 全部云端 | 按数据位置切分 | **不必要传输减少** |
| **本地算力** | 闲置 | 参与执行 | **云端计算量下降** |
| **本地小数据参与 JOIN** | 需上传 | 本地处理后只传中间结果 | **传输量显著下降** |
| **LLM 调用** | 每条数据都调 | 先判必要性 | **调用量收敛** |
| **敏感数据场景** | 必须上传 | 本地可闭环 | **数据不外流** |
| **接口** | 上传 / 云端两套 | 同一套 SQL | **开发体验一致** |
| **对使用者的透明度** | — | 混合执行透明 | **无额外复杂度** |
| **成本结构** | 传输 + 云端算力 | 传输下降、本地分担 | **总成本下降** |

**具体数字与关键性质（How much）**

- 团队规模：MotherDuck 团队数十人
- 关键性质：**按数据位置切分计划**；**本地算力参与**；**LLM 按必要性调用**；**透明混合执行**
- 业务影响：让以本地文件为主的分析场景无需全量上传即可结合云端数据，并减少不必要的 LLM 调用

**失败教训**

- 早期「**所有数据都上传云端再算**」——小数据也要传，传输与等待成本不划算，倒逼**「按数据位置切分执行计划」**
- 「**让使用者手工拆分查询**」——为省传输增加了使用复杂度，倒逼**「优化器决策执行位置，对使用者透明」**
- 「**每条数据都调一次 LLM**」——大量本可用规则或已有标签覆盖的数据也被调用，倒逼**「先判必要性，必要时才调用」**
- 「**敏感数据必须上传才能处理**」——限制了一部分场景，倒逼**「本地可闭环的任务完全在本地完成」**

### 2.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**一个 LLM 分类 / 摘要函数 + 一张小表试点**」（**最简单**）——**1 个场景、十万级行**
- 产出：**调用前过滤逻辑 + 提示词随 SQL 版本化 + 失败行单独落表**
- 团队：**2-3 人**
- 验证标准：**实际调用行数远小于表行数**、**提示词版本可追溯**、**失败行可单独重跑**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 场景 / 百万级行**」
- 引入「**结构化输出的强约束与校验**」——分类 / 抽取类输出按枚举或 schema 约束
- 引入「**任务分档（离线经济档 / 在线强档）**」+「**增量跳过已处理行**」
- 团队：5-10 人
- 验证标准：**结构化列不混入自由文本**、**增量运行成本按新增数据增长**、**离线 / 在线分档生效**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 场景 / 亿级行**」
- 引入「**推理结果落表并纳入血缘**」+「**模型 / 提示词版本进血缘**」
- 引入「**按业务归因的用量统计**」
- 团队：10-30 人
- 验证标准：**推理结果 100% 入血缘**、**换模型前列出受影响下游**、**成本可按业务归因**

**100 → 1000 阶段：12-24 个月**

- 引入「**影子执行对比 + 灰度切换**」——模型切换有量化验证过程
- 引入「**按数据位置选择执行位置（混合执行）**」——减少不必要传输与调用
- 团队：30-100 人
- 验证标准：**模型切换有对比数据支撑**、**不必要传输显著下降**、**敏感数据场景本地可闭环**

### 2.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**LLM 调用成本与数据量的关系**」 | 与全表行数挂钩 | 与必要候选集规模挂钩 | **显著下降** |
| 「**重复处理（已标注数据再调一次）**」 | 每次全量重跑 | 增量键跳过 | **成本按增量增长** |
| 「**数据导出流量**」 | 全量导出到外部 | 0 | **-100%** |
| 「**提示词可追溯性**」 | 散落在应用代码 | 随 SQL 版本化 + 进血缘 | **100%** |
| 「**结构化输出可用性**」 | 自由文本，下游易错 | 枚举 / schema 约束 + 校验 | **可入结构化列** |
| 「**模型切换的验证方式**」 | 上线后看反馈 | 影子对比 + 灰度 | **可量化** |
| 「**成本归因**」 | 与数据计算混合 | 按业务 / 作业统计 | **可归因** |
| 「**推理结果治理**」 | 落在平台外 | 落表，权限血缘延续 | **100%** |
| 「**不必要传输（混合执行场景）**」 | 全部上传云端 | 本地处理只传中间结果 | **显著下降** |
| 「**企业客户 / 覆盖**」 | 0 | 10000+ 企业 | **∞** |

**关键投资回报**：
- **直接节省**：「**LLM 成本与必要数据量挂钩（而非表规模）+ 增量跳过 + 导出为 0**」——**EB 级数据上做 LLM 批处理，成本杠杆在 SQL 的过滤与增量逻辑里，不在模型档位**；先筛选再调用这一条，往往比换更便宜的模型省得更多
- **业务价值**：「**结构化输出可入列 + 结果入表可治理 + 换模型可评估**」——**LLM 进入数据流程后，最大的风险是"产出不可控且变更不可见"**：输出不合结构、换模型无人知情、成本无法归因，这三条都会让 LLM 分析止步于试点
- **AI 时代关键**：「**提示词与模型版本随 SQL 版本化 + 结果入血缘 + 影子对比切换**」——**这是把 LLM 从"试验"纳入"生产数据流程"的必要条件**：提示词即逻辑、模型即依赖，两者都必须可追溯、可对比、可回滚；否则数据团队无法为带 LLM 的数据产物负责

---

> **本节小结**：
> - 4 个真实案例（Snowflake / Databricks / 阿里 / MotherDuck）印证：**LLM in SQL 不是「**在查询里调个模型**」，是「**调用函数化 + 成本前移（先筛再调 + 增量）+ 结构化输出约束 + 提示词与模型版本化 + 结果入血缘**」**5 件套**。
> - 关键时间线：Snowflake 3+ 年 / Databricks 3+ 年 / 阿里 5+ 年 / MotherDuck 2+ 年 —— **LLM 与数据栈融合是 2+ 年持续工程**，且**成本杠杆在 SQL 的过滤与增量逻辑，不在模型档位**。
> - 选型第一原则：「**一个 LLM 函数 + 一张小表 + 提示词版本化**」（**最简单**）——**十万级行** → 「**结构化输出约束 + 任务分档 + 增量跳过**」（**必须**）→ 「**结果入表入血缘 + 成本按业务归因**」（**生产**）→ 「**影子对比切换 + 按数据位置选择执行位置**」（**AI 时代**）。
> - 99% 的失败来自「**导出到外部调模型 + 全表都调一遍 + 提示词散在应用代码 + 输出不约束**」——必须有 **推理下推 + 先筛再调 + 提示词版本化 + 结构化约束**。
> - 真正的 ROI 来自「**成本随必要数据量增长 + 导出 0 + 输出可入结构化列 + 换模型可评估**」——是**LLM 能否从试点纳入生产数据流程的分水岭**。
