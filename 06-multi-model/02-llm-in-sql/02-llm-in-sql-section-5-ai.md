## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单在本主题上的第一个问题是没有时间维度。读者按它排路线图，会先去做那个写不出验收标准的，而不是先做明天就能上线的。

第二个问题是机制差异被抹平。本主题的「演进」实际横跨三层，改动它们的东西完全不同：

1. **算子在哪儿执行**（SQL 表达式位置 / 批处理作业 / 内网推理端点）——决定账单形状与合规边界。
2. **问题由谁提出**（人写 SQL / 自然语言 / 智能体编排）——决定入口，不决定算子。
3. **谁来选模型、怎么记账**（模型路由与 token 归因）——决定成本能不能归到团队。

[§3 §3.1](02-llm-in-sql-section-3-sec3.md) 已经把三条硬约束写在前面：**数据能不能离开引擎**、**进入模型调用的行数占表行数的比例**、**产出的结果要不要进正式数据链路**。这三条里没有一条会被更强的模型改掉——模型变强不改变「数据能不能出仓」是一次合规判定，也不改变「进入调用的行数 × 单价 = 账单形状」这个乘法。AI 真正改变的只有第一层里的一个点：**调用点从应用进程移进了 SQL 执行器**。这一点足够重要，因为它让「百万行的批量标注」从一项 ETL 工程变成一条 `INSERT ... SELECT`；但它不改变另一件事——**模型服务仍然是数据库之外的一个依赖**，把调用点搬进执行器，不会把它搬进同一个故障域。

本节用 L1 / L2 / L3 三级划分，三条判据必须可核验（本节不修正判据，全节按这三条判）：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期。
- **L2 可试点**：① 满足（能力已可用），而 ② 不满足（拿不出第三方（非厂商）公开的生产案例）——「已可用但接口 / 生态未稳」与「仅有厂商自有案例」都落这一档。③ 此时可以是满足、大体满足或不满足，**但每一行必须写明是哪一种**：③ 的成色不改变级别，却决定这条方向离 L1 还差多远。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性；或者 ① 与 ③ 两条都拿不出可核验的依据（能力可能确实已经发布，但读者按判据复核不了它，也就不能拿它排期）。记录即可，不要在架构里为它预留假设。

判据 ② 在本主题格外难过，原因值得先说清：**这门技术的公开材料天然是发布方自述**。库内 AI 是各家数仓的核心卖点，GA 公告、函数参考、样板客户故事都由厂商自己提供；而「多大数据量上跑、失败时怎么办、一年内接口改过几次」这类要用来判断代价的材料，通常不在里面。因此本节表里五行停在 L2、五行停在 L3。**② 只有「满足」与「降为 L2」两种命运**：它不能被改写成「有公开的 GA 公告」（那是 ①），也不能靠「本节只评估某一层」把适用范围缩小来绕过去。

还要说清 L2 在本节的含义：它标的是**证据缺口**，不是「不能用」。一行落在 L2，缺的首先是「别人用过、并且公开说了代价」这类材料，不是能力本身；③ 是好是坏都可能落 L2（见表，每一行都写明是哪一种），采不采用由读者按自己的风险偏好决定，判据不因这句说明而放宽。另有一条评级规则全节通用：**合并方向取最弱子项**——「跨库统一 AI 算子接口」是多条能力的方向句之和，本节把它当叙事处理，不当作一个能单独定级的能力。

**本节没有一行达到 L1。** 离得最近的是五行——AI Function 写进表达式位置、文档与多模态 AI Function、自然语言查询、Self-Hosted LLM 接入、模型路由。这五行的 **① 都满足**（各自有可核验的正式条目），**共同缺的只有 ②**（第三方非厂商公开生产案例）——这是它们停在 L2 的原因。但 **③ 上五行并不齐，必须分行看**：自然语言查询与 Self-Hosted LLM 接入的 ③ 只算大体满足（前者依赖每个组织自己的语义层完备度，后者的服务端接口趋同但没有可移植的判定依据）；而 AI Function 写进表达式位置、文档与多模态 AI Function、模型路由三行的 ③ **不满足**（前两者换一家产品就要重写 SQL，后者的分档依据无标准形态）。所以「五行都只缺 ②」说的是**证据缺口**，不等于「五行只差点材料」——③ 的成色决定它离 L1 还差多远，逐行判据以表与 5.2.x 为准，两处必须一致。判断某条方向是不是 L1，不要看有多少厂商在同一年发布了它，看第 ② 条的材料是不是**发布方之外的机构**给出的：单靠 GA 公告与样板客户故事，无论多少条，都还是 L2。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式发布载体能不能找到——在 SQL 函数参考或版本化文档里有没有条目，带不带版本号？找不到 → L3。
2. 发布方之外的证据能不能找到——有没有人公开讲过它在多大数据量上跑、失败时怎么办？找不到 → L2。
3. 这条接口明年会不会变——**换一家产品，同一件事要不要重写 SQL？** 要重写 → 至多 L2。

第 3 句在本主题特有的失手方式，是把**能力名**当成**产品名**：同一个能力在不同平台的函数名与签名各不相同——`ai_classify` / `ai_summarize` / `ai_extract` / `ai_embed` / `ai_generate` 在 Snowflake Cortex、Databricks AI Functions、DuckDB `ai_functions` 下各有各的写法，而 `ai_query` 是 Databricks 一侧的名字（见同目录 [§4 §4.3](02-llm-in-sql-section-4-sec4.md)），**不要互相套用**。判定方法是去该平台的 SQL 函数参考里找「调用模型 / 生成向量」的正式条目，找得到再谈支持；只看首页文案，会把「加了一个函数」读成「换了一代架构」。

### 5.2 演进方向逐条拆解（核心节）

下面四个小节按同一套结构写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**。只写收益不写代价的方向，评审时应直接打回——本主题里每一次能力提升，都对应一项成本结构的变化。

读这套结构时有两个约定。**第一，「机制」那一行必须落到一个可以被改动的对象上**——调用点的位置、接口的边界、谁决定路由。写成「更智能了」「门槛更低了」的，都不算机制。**第二，「代价」那一行必须是真实存在的新成本项或新故障模式**，而不是「需要学习」这类永远成立的代价。

#### 5.2.1 AI Function 写进 SQL 表达式位置：换的是调用点，不是模型

- **旧做法与它的卡点**：旧做法是把文本导出到应用侧调模型、再把结果写回库。卡点有两处：**其一，数据必须离开引擎**——受监管数据发给企业之外的端点本身不可接受，而绕开它建起来的通道至少四步（ETL → Python → 调 LLM → 回库，主文件 §1.2 痛点 1、2）；**其二，产出物没有落点**——它在应用侧的生命周期里，不在数据库的治理域里，所以「这批标签谁生成的」答不出来。而「AI Functions 标准化」这一提法，要补上的正是「标准化的是哪一层」这一层。
- **AI 改变了什么机制**：**改变了调用点的位置**——模型调用从「应用层的一段代码」变成「SQL 里的一个函数」，于是它被纳入同一个执行计划：谓词下推、列裁剪、并行度都由引擎决定（[§3 §3.2.1](02-llm-in-sql-section-3-sec3.md)）。注意这不是成本结构的变化（token 照付、网络往返照付），而是**接口边界的变化**：调用从进程边界移到了表达式边界。
- **由此得到的**：**因为算子写在 SQL 的表达式位置，所以「先过滤再调用」由优化器而不是由代码顺序决定**——进入算子的行数可以被谓词下推压到必要规模，而账单形状正比于这个行数；**又因为产出物落成普通列或普通表，所以它一次获得三样东西**：可被下游 JOIN 的稳定产物、可被 WHERE 跳过的增量键、可被限定范围重跑的失败行（[§3 §3.2.2](02-llm-in-sql-section-3-sec3.md)）。这两条合起来，是多模态能力真正的价值所在——**把 PDF、图片、表格变成可 JOIN 的列**，与把文本变成一列情感标签，用的是同一条机制。
- **由此付出的**：**其一，失败粒度被放大**——每次调用都带一次端点往返，行数即往返次数，而 SQL 的失败粒度通常是整条查询，一次模型抖动会放大成一次作业失败（[§3 §3.2.1](02-llm-in-sql-section-3-sec3.md)）。**其二，共享资源被外部依赖挤占**——向量列让行宽显著增加，不相干的扫描跟着变慢，列裁剪与分区隔离从优化项变成必须项。**其三，可移植性为零**：函数名、计价口径、权限模型、失败语义四件事各家不同，换一家产品就要重写 SQL——这正是「统一接口」这条叙事今天不成立的原因。**其四，多模态那条路最贵**：解析一件 PDF 的单次调用成本与延迟高于一次文本分类【经验】，把它放进交互路径前必须先用自有样本量测。
- **证据与来源**：【公开】各平台的 SQL 函数参考是唯一可靠入口——Snowflake 的 Cortex 函数族、Databricks 的 `ai_query` 一类函数、BigQuery 的 ML 函数族、阿里 MaxCompute 的 AI UDF、PostgreSQL 的 pgai、ClickHouse 与 DuckDB 的 AI 函数扩展都有正式文档条目（【公开：主文件 §1.4 记录 Snowflake Cortex 于 2023-11 GA；**命名各不相同，不要互相套用**】）。**② 不满足**：本节给不出「发布方之外的机构公开的、含数据量与代价的库内调用生产案例」这一材料。
- **成熟度**：**L2**（与 5.1 表前两行一致），判据：① 满足、③ 不满足（无跨平台接口）、**② 不满足**。

| 判断项 | 应用侧调模型 | 库内 AI Function |
| --- | --- | --- |
| 调用点在 | 应用进程内 | SQL 执行器内 |
| 谁决定进入调用的行数 | 代码里的循环与过滤顺序 | 优化器的谓词下推 |
| 产出物落在 | 应用侧的生命周期里 | 普通列 / 普通表，可 JOIN、可增量跳过 |
| 失败粒度 | 可只重跑失败的那一批 | 通常是整条查询 |
| 换平台代价 | 改配置与端点 | 重写 SQL |

```text
同一件事的三种执行位置（决定账单形状与失败粒度）
  A. 应用侧逐行调用
     读表 ──► Python 循环 ──► 逐次 HTTP ──► 写回     ← 往返次数 = 行数
  B. 库内表达式位置（本方向）
     INSERT INTO t SELECT id, ai_classify(x) FROM src WHERE dt = :d
                          └─ 谓词先下推，进入算子的行数由引擎决定
  C. 批处理作业（[§3 §3.2.2]）
     先压候选集 ──► 增量键 LEFT JOIN 跳过已处理行 ──► 结果落表
  ────────────────────────────────────────────────
  关键：B 与 C 改的都是「调用点在哪儿」，都不改「模型服务是外部依赖」
        因此失败语义必须先在最小 SQL 上测出来（模型不可用时报错、返回 NULL
        还是静默写入空值），再决定它能不能进关键路径
```

**怎么判断这条方向在你这里值不值**（三项都不需要新采购）：把「进入算子的行数 ÷ 扫描行数」这个比值量一次——它是账单形状的分母；查函数签名里模型标识是不是必填——它决定「这一列由哪个模型生成」能不能被记录；在压测里人为让模型端点返回限流响应，看连接池是否被打满——它决定这条依赖要不要画进架构图。

#### 5.2.2 自然语言查询内嵌：主件是语义层，模型只是接口

- **旧做法与它的卡点**：旧做法是业务方提需求、分析师写 SQL。卡点不在 SQL 的语法，而在**口径**：同一句「上周 GMV」，两个分析师能写出两种 SQL，而两种都语法正确（[§3 §3.2.4](02-llm-in-sql-section-3-sec3.md)）。
- **AI 改变了什么机制**：**把「从需求到查询」的翻译环节从人换成了统计模型**——只换了翻译环节，没有换口径的来源。口径仍然来自指标定义与语义层（[Ch4-10 指标平台](../../04-data-assetization/10-metric-platform/10-metric-platform.md)、[Ch1-10 指标体系](../../01-modeling/10-metric-system/10-metric-system.md)）。
- **由此得到的**：**因为口径来源没有变，所以自然语言查询的准确率上限由语义层的完备度决定，而不是由模型能力决定**——这解释了一个反复出现的现象：同一款产品在演示里表现很好、在自有 schema 上明显变差，因为演示用的是厂商准备好的语义模型。**又因为翻译的落点是定义层里的指标而不是表上的列**，所以同一个问题在任何时间、任何工具里问，都落到同一段口径上（[§3 §3.2.4](02-llm-in-sql-section-3-sec3.md)）。
- **由此付出的**：**其一，新增一层需要长期维护的资产**（语义模型、指标定义、列的业务含义），它的维护成本不会因为有了 LLM 而消失，反而因为入口变多而变大；**其二，错误形态变了**——从「SQL 报错」变成「SQL 跑通了但口径是错的」，后者不会被任何监控发现，只在业务复盘时暴露，因此拒答策略与人工抽检是组件的一部分而不是兜底；**其三，权限面扩大**——自然语言入口让不懂 schema 的人也能发起查询，行级与列级权限必须在这条新入口上重新验证一遍。
- **证据与来源**：【公开】跨域 Text2SQL 的公开基准（BIRD，Li 等，NeurIPS 2023 Datasets and Benchmarks Track）给出的是通用 schema 上的执行准确率，**它测的不是你的口径**；产品侧 Cortex Analyst、Databricks Genie、PolarDB 自然语言查询都有官方文档可核验其前置条件（多数要求先定义语义模型）。**② 不满足**。
- **成熟度**：**L2**（与 5.1 表「自然语言查询内嵌」行一致），判据：① 满足、③ 大体满足、**② 不满足**。

**判定方法（自己怎么核验）**：从生产查询日志里抽一百条真实问题，覆盖三档——单表聚合、多表 JOIN、含口径歧义的指标；让产品生成查询、人工只判「结果对不对」。**如果第二档与第三档的正确率明显低于第一档，说明瓶颈在语义层与 schema 表达而不在模型**，此时换产品不会改善；反过来，如果三档都接近，说明语义层已经足够好，可以扩大入口范围。

#### 5.2.3 请求发往谁的机器：Self-Hosted 与模型路由

- **旧做法与它的卡点**：旧做法只有一条通路——调外部 API。卡点不在模型质量，而在**请求的边界**：受监管数据上，把内容发给企业之外的端点本身就不可接受（主文件 §1.2 痛点 1），而且每个业务方各自调 API 时，token 花在哪、该由谁付，答不出来（主文件 §1.2 痛点 6）。
- **AI 改变了什么机制**：**改变了请求的落点与决策位置**——推理从「外部端点」扩成「外部端点 + 内网推理服务」两条通路，而「这条请求走哪条」从各业务自己写死变成调用侧的一段路由逻辑。这是**决策位置的迁移**，不是模型能力的提升。
- **由此得到的**：**因为内网推理服务把「模型」和「数据」放进了同一个可审计的边界内，所以「请求不能出边界」这一类要求第一次可以被架构满足，而不是靠逐个人负责**；**又因为路由与 token 账务落在同一处，所以「按任务分档、按团队归因」有了落点**——这是唯一真正可交付的部分。它同时解释了为什么自托管的价值与「模型强不强」关系不大：**它买的是边界，不是分数**。
- **由此付出的**：**其一，运维单元多了一个**——内网推理服务是新的值班对象、容量对象与升级对象，而它的故障会直接表现为数据库侧的排队；**其二，合规风险被位移而不是消除**——若端点实际在公网、或请求里带了不该出的字段，风险照旧，把模型换成开源权重不改变这一点；**其三，路由的可解释性成本**——一旦请求分流由逻辑决定，线上结果不一致时就要先回答「这条走的是哪条通路」，路由规则必须能落进变更记录，否则排障第一步就卡住。
- **证据与来源**：【公开】自建推理框架这一侧有可点名的公开载体——vLLM 的 PagedAttention（Kwon 等，"Efficient Memory Management for Large Language Model Serving with PagedAttention"，SOSP 2023）以及 vLLM / Ollama / SGLang 各自的版本化发布记录；托管推理那一侧（阿里云 PAI、腾讯 TI、火山方舟）有产品文档，按产品名即可检索其部署形态。判定入口是「该端点是否支持在自有网络内部署、是否给出并发与显存的容量口径」，而不是「模型是不是开源」。模型路由这一侧同样有可点名的载体——开源与托管两类的模型网关都在正式文档里给出路由规则与按 key / 团队归因的用量字段，并有版本化发布记录；但它没有行业标准。**① 判的是有没有可点名的正式载体，③ 判的是接口形态稳不稳**：载体有、形态没有，这是这一行 ① 成立而 ③ 不成立的原因。**② 不满足**。
- **成熟度**：**L2**（与 5.1 表「Self-Hosted LLM 接入」与「模型路由」两行一致），判据逐行对该表：**Self-Hosted LLM 接入**——① 满足、③ 大体满足（服务端接口趋同）、**② 不满足**；**模型路由**——① 满足、③ **不满足**（分档依据无标准形态）、**② 不满足**。两行的 ③ 不同，是因为「请求发往谁的机器」这一层已有趋同的接口，而「按什么分档」这一层还没有。

#### 5.2.4 其余方向为什么停在这里

下面五条同样按六行结构写：它们停在低处不是因为看不到收益，而是因为判据过不去；逐条写全六行，是为了让「停在这里」这个判断能被复核，而不是留一句印象。

- **库内微调 · 旧做法与它的卡点**：行业适配的旧做法是在外部 ML 平台上训、再想办法把权重接回来；卡点是权重与评测散在两个系统里，谁改了什么说不清。
- **库内微调 · AI 改变了什么机制**：把「训练入口」搬进数据库控制台——换的是操作入口的位置，不是权重与评测的归属。
- **库内微调 · 由此得到的**：如果训练数据本来就在库里，那么「取数 → 训练」之间的距离确实被缩短，数据搬运这一段可以省掉。
- **库内微调 · 由此付出的**：**产出物的治理成本被留在原地**——权重版本、评测集、回滚路径都不随着入口一起进来；而一次微调的效果必须靠自有评测集验收，拿不出评测集，投入会变成一次无法验收的作业。
- **库内微调 · 证据与来源**：**① 本节不判满足**——主文件 §1.4 的演进时间线没有收录 Cortex Fine-Tuning / Mosaic AI Fine-Tuning 的发布条目，本节因此给不出「文档名 + 年份」这一档的正式 release note；可核验的入口是按这两个产品名在两家官方文档的当前版本里检索其微调条目，看它是否标 GA、训练数据是否需要出域。这两项在 [§4 §4.3](02-llm-in-sql-section-4-sec4.md) 的工具链清单里以**能力名**出现，那不是带年份的发布条目——本节 ① 判的是有没有可点名的正式载体，不是这家厂商有没有提过这项能力。**③ 不满足**（权重与评测不在治理域内）、**② 无**。
- **库内微调 · 成熟度**：**L3**（与 5.1 表「库内微调」行一致）：① 不满足、③ 不满足、② 无。

- **多智能体 + AI Function / Data Agent 调度 · 旧做法与它的卡点**：跨系统的取数动作靠人按工单编排，「要不要调、调哪个」由人判断；既不能规模化，出错了也没有可归属的对象。
- **多智能体 + AI Function / Data Agent 调度 · AI 改变了什么机制**：把「动作选择」表述成一次编排——算子成为被调度的对象。**换的是被编排对象的聚合方式，不是 SQL 算子本身**。
- **多智能体 + AI Function / Data Agent 调度 · 由此得到的**：如果算子已经能写成 SQL 函数，那么「取数 → 生成 → 回写」三段在同一个工具面里串起来是自然的，不需要为每一段单独造一个系统。
- **多智能体 + AI Function / Data Agent 调度 · 由此付出的**：**失败无法归属**——在工具目录、调用预算与权限模型成立之前，让智能体去调库内算子，调错的后果没人接得住；且动作比查询更不可逆，一次越权取数不是一次「结果不对」，而是一次数据事故。
- **多智能体 + AI Function / Data Agent 调度 · 证据与来源**：没有面向「在数据库内编排多智能体」这一能力项的正式发布；**① 不满足、③ 不满足**（工具入参——返回行数上限、超时、token 预算——没有稳定形态，各平台的可介入点不同）、**② 无**。
- **多智能体 + AI Function / Data Agent 调度 · 成熟度**：**L3**（与 5.1 表「多智能体 + AI Function」行一致）：① 不满足、③ 不满足、② 无。

- **库内推理硬件加速 · 旧做法与它的卡点**：旧做法是靠增加推理副本或换更小的模型来压延迟，卡点是这两条路都会先撞到「数据要搬过去」这一步。
- **库内推理硬件加速 · AI 改变了什么机制**：把推理搬到数据旁、并配加速硬件——换的是**数据搬运量**，不是模型算力本身；省下的是搬运，不是计算。
- **库内推理硬件加速 · 由此得到的**：在数据搬运占大头的工作负载上（大表批量打标），它的收益与需要搬运的数据量成正比，这是它唯一站得住的机制性收益。
- **库内推理硬件加速 · 由此付出的**：**加速器是新的容量与成本对象**——显存决定并发上限、型号决定可部署的模型大小、稀缺性决定排队策略，这些都进入运维；而收益面在搬运量小的负载上接近于零，此时它只是把同一份算力换了个位置。
- **库内推理硬件加速 · 证据与来源**：**①③ 不满足**——本节给不出「官方文档名 + 年份」这一档的条目，而且加速形态与具体硬件型号绑定（Snowflake Cortex 的 NVIDIA A100 侧、Databricks GPU 集群、ClickHouse GPU、阿里含光 800 各自成一套），性能声称普遍缺条件限定语；判定入口是各平台官方文档里有没有「GPU / 加速器」这一节，以及其中的数字是否同时给出数据量、批大小、硬件型号与目标（延迟还是吞吐）。**② 无**。「性能 10x–100x」既无来源也无条件限定语，本节不转载。
- **库内推理硬件加速 · 成熟度**：**L3**（与 5.1 表「库内推理硬件加速」行一致）：①③ 不满足、② 无。

- **与 GraphRAG 的结合 · 旧做法与它的卡点**：多跳事实的「为什么」靠人写规则链或展示层模板，属性关系一变就要改代码；图侧实体与库侧主键之间没有既定的交接方式。
- **与 GraphRAG 的结合 · AI 改变了什么机制**：把「多跳关系推理」从手写规则链换成在图与检索上生成的推理路径——换的是**关系与解释的产生方式**，不是取数算子的执行位置。
- **与 GraphRAG 的结合 · 由此得到的**：如果实体到主键的映射成立，同一张图可以分别充当召回通道、过滤条件或解释层，一份数据准备支持三种用法。
- **与 GraphRAG 的结合 · 由此付出的**：**三种角色对数据与延迟的要求不同**（召回要可检索、过滤要低延迟、解释要可回溯），接口未定意味着无论选哪一种都要重做一次数据准备；检索侧一旦返回没有主键的实体，等于把幻觉直接送进结果。
- **与 GraphRAG 的结合 · 证据与来源**：这条路线的公开代表是可点名的——Microsoft Research 的 GraphRAG（Edge 等，"From Local to Global: A Graph RAG Approach to Query-Focused Summarization"，arXiv 2024）及其开源实现，是「图 + 检索」的可检索入口；但它是**检索侧**的工作，没有定义「图侧实体与库侧主键如何交接」这一条。**①③ 不满足**——本条的关键环节（图与检索的交接形态）没有公开定义；**② 无**。
- **与 GraphRAG 的结合 · 成熟度**：**L3**（与 5.1 表「与 GraphRAG 的结合」行一致）：①③ 不满足、② 无。

- **「跨库统一 AI 算子接口」 · 旧做法与它的卡点**：无旧做法可谈——这是目标句，不是一件已在做的事；卡点在于它缺一个可验收的形态。
- **「跨库统一 AI 算子接口」 · AI 改变了什么机制**：**没有改变任何机制**。函数名相似不等于接口统一；统一接口要先统一失败语义与计价模型，而这两件是各产品的商业边界。
- **「跨库统一 AI 算子接口」 · 由此得到的**：在单平台内，它带来的是一致性（同一套语法覆盖分类、摘要、抽取、向量）。
- **「跨库统一 AI 算子接口」 · 由此付出的**：把「名字相似」当作「接口统一」，会让选型阶段低估迁移成本——而迁移成本主要落在 SQL 重写上，不在数据搬运上。
- **「跨库统一 AI 算子接口」 · 证据与来源**：**①③ 不满足**：没有出现被两家以上主要平台按同一语义实现的正式标准条目；**② 无**。
- **「跨库统一 AI 算子接口」 · 成熟度**：**L3**（与 5.1 表合并叙事行一致，按合并规则取最弱子项）：①③ 不满足、② 无。

把上面五条并排看，会发现它们停在低处的理由只有两类：**一类是接口还不成立**（图与检索的交接形态、智能体的工具目录与权限模型、跨平台的函数语义），**一类是产出物的治理没有跟上**（微调的权重版本与评测集、加速器的容量对象）——这两类都落在判据 ③；而 ① 在这五条里全不满足，记录的正是「连一条可点名的正式条目都还拿不出」。判据 ② 问的是另一件事：**能拿出「别人在生产里用过」的材料，本身就是前提条件成立的证据**。这也解释了为什么 ② 在本主题如此难过：它要求的不是更多厂商支持，而是有人愿意把代价讲出来。

### 5.3 与本主题既有栈的接口在哪

LLM in SQL 不是独立系统：它的输入来自业务表与非结构化件，输出交给下游的目录、指标与智能体。写清接口边界（谁调用谁、以什么形态穿过边界、失败时谁负责）比写「与 X 结合」有用。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| SQL 算子 ↔ 模型服务 | 交接物 = 一次函数调用（提示 + 行内容 → 文本或向量）；**模型标识必须作为入参出现** | 数据库侧；它是把外部服务的可用性引进 SLA 的那一侧 | 各平台接口已发布，命名与计价不同（L2） |
| 算子产出 ↔ 元数据 / 数据目录 | 表定义与产出物登记「这一列由哪个模型、哪个版本生成」 | 目录侧：缺项即拒绝发布 | 需新增元数据字段 |
| 提示词 ↔ 治理域 | 交接物 = 提示版本；产出进报表时它必须可审计 | 数据团队（产出进正式链路后，「这批标签谁生成的」要答得出） | 多数实现里提示词留在应用侧，未进登记 |
| 自然语言入口 ↔ 语义层 / 指标平台 | 交接物 = 指标定义（口径），不是模型的猜测 | 语义层侧；口径错的查询不会报错 | 边界要先划清（L2） |
| 批量产出 ↔ 增量键 | 交接物 = 可被 WHERE 跳过的增量键与可限定范围的重跑边界 | 作业侧：增量键漏写等于重复付费 | 既有工程做法 |
| 算子 ↔ 向量索引 | 交接物 = 距离分数 + 编码器版本；过滤与向量扫描的先后由优化器决定 | 检索侧：分数不带口径则两次检索的结果不可合并 | 仓内建索引与独立服务两条路，见 [§7 §7.3.4](02-llm-in-sql-section-7-sec7.md) |
| 智能体 ↔ SQL 算子 | 交接物 = 工具入参（返回行数上限 + 超时 + token 预算） | 智能体平台侧（预算与权限）；数据库侧负责资源隔离 | 未定型（L3） |
| 自托管推理 ↔ 内网 | 交接物 = 一个只在内网可达的推理端点 | 运维侧：它同时是新故障域与新的运维单元 | 可做，但要把它算进值班与容量 |
| token 用量 ↔ 查询与团队 | 交接物 = 按查询或按团队可归因的用量记录 | 平台侧：不单列就混进数据库账单，无法归因 | 各平台计价与用量视图能力不同 |

这张表的九行里，只有两行属于既有能力（批量产出与增量键、算子与向量索引的先后判断），其余都要新建登记或新建责任归属。**失败归属必须在设计阶段写清**，否则会退化成扯皮：一次批量打标的结果不对，是模型换了版本、提示改了措辞、还是增量键漏写导致重跑了旧数据？三件事都能解释同一个现象，而它们分属三个团队。唯一能让争论停下的是把「模型版本 + 提示版本 + 增量键」登记成资产——也就是 5.7 里那条最不性感、却最省事的要求。

**两步式检索这条既有做法**就落在表的第 6 行：召回段用距离算子先取候选（`ORDER BY embedding <=> ai_embed(:query, ...)` 加 `LIMIT k`），生成段用 `ai_generate_text(...)` 把候选内容拼进提示词产出答案，两段写在同一条 SQL 里。它成立的前提正是那一行的交接物——**距离分数必须与编码器版本一起带出来**，否则「换了 embedding 模型之后两次召回的结果不再可比」这件事不会被任何报错发现。两段的完整结构见 [§3 §3.2.3 融合模式](02-llm-in-sql-section-3-sec3.md)（召回与结构化过滤联立）与 [§3 §3.2.5 智能体模式](02-llm-in-sql-section-3-sec3.md)（召回给依据、SQL 聚合给事实）；本节不为它单独定级，它是已有做法，不是前沿。

其中有一处最容易漏：**「模型版本」与「提示版本」不是同一件事**。模型版本决定向量与分数的可比性（换了模型，旧向量与新向量不再可比，需按模型版本重建索引），提示版本决定标签的口径（改了措辞，同一批文本的分档会漂移）。两者都要登记，登记时把它们写成两个字段，比合成一个「AI 版本」要好：事后靠日志把同一条产出回推到模型与提示版本，返工量通常比事前登记高一个数量级【经验：随产出量与日志留存期变，留存期覆盖不了回推窗口时这条路径可能走不通】。

**判定这张表有没有被用起来**：每个季度核对两个数——本季有多少条 AI 产出能追到模型版本，有多少条能追到提示版本。两个数都是零，说明表还停在文档层面。

### 5.4 公开进展与文献

分三类列，只列能给出会议 / 文档名 + 年份的条目；**宁少勿假**。判定 ① 时按同一判据：**有同行评审论文或版本化公开实现的可判 ①，只有会议名的不判**。

**论文**

- Li 等，"Can LLM Already Serve as A Database Interface? A Big Bench for Large-Scale Database Grounded Text-to-SQLs"（BIRD），NeurIPS 2023（Datasets and Benchmarks Track）——跨域 Text2SQL 的公开基准，用来说明「基准准确率 ≠ 你的口径准确率」，是 5.2.2 判据 ② 之外给读者的替代核验入口。
- Yu 等，Spider，EMNLP 2018——Text2SQL 基准的前身，多表 JOIN 与跨库 schema 的评测形态自此定型。
- Reimers & Gurevych，EMNLP 2019（Sentence-BERT）——把语义相似度变成可计算距离，是「在库里生成向量」这条能力的方法来源。
- Malkov & Yashunin，"Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs"，arXiv 2016 / IEEE TPAMI 2020——近邻索引的原始工作，理解「索引是有状态的数据结构」的起点。

**官方 release note / 文档（判定入口）**

- pgvector CHANGELOG（0.5 于 2023 引入 HNSW、0.7 于 2024 引入 halfvec / bit、0.8 于 2024 引入迭代索引扫描）——核验「向量索引建在仓内」这一侧是否已 GA、接口是否跨多个主版本未变。
- 各平台 SQL 函数参考（Snowflake 的 Cortex 函数族 / Databricks 的 `ai_query` 一类函数 / BigQuery 的 ML 函数族 / 阿里 MaxCompute 的 AI UDF / PostgreSQL 的 pgai / ClickHouse 与 DuckDB 的 AI 函数扩展）——核验「在库内调用模型」这一能力的唯一可靠入口。**函数名各不相同，不要互相套用**；判定方法是在函数参考里找三样东西：是否要求显式传入模型标识、计费是否按 token 单列、**模型不可用时返回什么**（第三样最容易在文档里缺失，缺失就按「会静默写入坏数据」来设计）。
- 自建推理框架与托管推理服务的版本化文档——核验「请求发往谁的机器」这一侧；判定入口是「该端点是否支持在自有网络内部署」，而不是「模型是不是开源」。

**第三方生产案例**

本节**不给出**可核验的第三方生产案例。「60%+ 企业将部署自托管」与「性能 10x–100x」既无来源也无条件限定语，本节不转载。**这个空白本身是结论**：它直接决定了本节没有一行达到 L1。要补这一类材料，可按关键词（库内调用模型的生产实践、prompt 版本治理、token 归因）在第三方工程博客与会议议程里自行检索核验。

**引用纪律**：本主题最容易被误引的三类数字是「加速倍数」「识别准确率」「成本下降百分比」。可核验的做法是回到来源找三样东西——数据量、模型与批大小、硬件条件；缺一个就不要引用这个数。

### 5.5 被过度宣传的部分

**「AI 算子会像 SQL 一样跨数据库统一」** —— 实际是：函数名、计价口径、权限模型、失败语义四件事各家不同，换一家产品就要重写 SQL。原因：统一接口的前提是先统一失败语义与计价模型，而这两件事分属各产品的商业边界，不是技术难点，因此不会因为「大家名字取得像」而收敛。**它什么时候才会成真**：出现被两家以上主要平台按同一语义实现的正式标准条目——判定时看标准文档里有没有出现「调用模型」的语法条目，而不是看一批函数名是否相似。

**「Self-Hosted LLM 让数据不出仓，合规问题就解决了」** —— 实际是：把「数据被传出去」的风险换成了「新的运维对象与新的故障域」的风险，而且端点若实际暴露在公网，请求照样出了边界。原因：合规判的是**请求发往谁的机器**，不是模型是否开源；把权重换成开源版本，不改变链路拓扑。**它什么时候才会成真**：模型服务与数据库处在同一故障域、同一审计域内，且「模型不可用时这次写入是回滚、留空还是写占位值」被写进产品文档——这条语义写进一致性说明之前，「数据不出仓」只是一个部署形态。

**「库内推理硬件加速让推理快 10–100 倍」** —— 实际是：它省掉的是**数据搬运**，不是模型算力；收益与需要搬运的数据量成正比，在搬运量小的负载上接近于零。原因：这类说法普遍不带条件限定语，而性能同时取决于数据量、批大小、模型与硬件，跨环境不可比。**它什么时候才会成真**：看到与「只换模型端点」这一对照组并排给出的数字，且带上数据量、批大小、硬件型号与目标（延迟还是吞吐）——四项缺一，这个倍数就不能进选型结论。

三条合起来看，被过度宣传的部分有同一个形状：**它们都把「接口变好了」或「位置变了」讲成了「架构变好了」**。统一接口改的是命名（失败语义仍各管各的）、自托管改的是请求落点（依赖仍在自己手上，只是换了个地方）、硬件加速改的是搬运路径（算力上限一点没动）。识别方法因此很简单——**把宣传句里的动词换成「接口」「位置」「搬运」，看它还成不成立**：换成这三者仍成立的是工程改良，只有换成「存储」或「所有权」才成立的是架构变化。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 「跨平台统一 AI 函数接口」不会出现，跨平台迁移仍以重写 SQL 为主 | 各平台继续保留自己的函数名与计价模型；跨平台迁移的公开材料里出现「等价写法对照表」这类文档 | 出现被两家以上主要平台按同一语义实现的正式标准条目，且至少两个平台按它提供函数 |
| 库内调用模型会成为数仓标准能力，但默认只走离线与批量路径；在线写路径仍以应用侧调用为主 | 产品文档把「是否允许在写事务内调用」单独列成一节；公开实践里写路径调用仍少见 | 主流产品把「写入自动调用模型」做成默认行为，并明确写出模型不可用时的降级语义 |
| 模型版本与提示版本会像表结构一样进入变更登记 | 平台的变更记录与目录字段里出现「模型版本 + 提示版本」；发布流程把它们列为必填 | 三年后仍只登记表结构变更，模型与提示靠口头同步；换模型后旧产出无法判断可比性 |
| 自然语言入口会以「语义层 + 检索 + 生成」三段式落地，而不是把问题直接丢给模型 | 产品文档把语义模型定义列为前置条件；第三方实践里语义层建设的篇幅明显大于模型选型的篇幅 | 出现无需任何语义定义、直接对原始 schema 稳定达到可上线准确率的公开评测 |

四条都能被**公开文档与实际变更记录**证实或证伪，不需要内部数据：

- 第 1 条看标准文档与各平台函数参考，一到三年见分晓。
- 第 2 条看产品文档里有没有「写事务内调用」这一节，一到两年。
- 第 3 条看发布流程的必填字段，一到两年。
- 第 4 条看产品前置条件与第三方实践分享的结构，两到三年。

最值得先盯第 3 条：它是唯一一条**不依赖任何新产品发布**就能观察到的信号，而且它一旦做不到，其余三条的结论都失去可比性——模型换了而没人知道，任何跨期对比都不成立。

提醒一句：这四条问的都不是「哪个模型会更强」，而是「**判断依据会不会出现在公开文档里**」。前者无法证伪，后者可以逐条核对。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有大批文本 / 工单要打标，结果要进报表 | 走批处理：先压候选集、增量键跳过已处理行，结果落普通表（[§3 §3.2.2](02-llm-in-sql-section-3-sec3.md)） | 进入算子的行数 ÷ 扫描行数这个比值是否在下降 | 不要在增量键没写进 WHERE 之前开跑；不要把模型调用放进在线写事务 |
| 业务方提出「自然语言取数」 | 先建语义层与自建评测集，模型只当翻译层（5.2.2） | 自建评测集上三档问题的正确率差距，而不是产品演示 | 不要在语义层建好之前对业务开放入口；不要跳过行级权限在新入口上的重新验证 |
| 数据不能出企业网络 | 用内网推理端点作为一条并列通路，并把它算进值班与容量（5.2.3） | 该端点是否成为数据库侧排队的来源；它有没有进容量盘点 | 不要以为换了开源权重就等于合规；不要省掉「模型不可用时怎么办」这一条语义 |
| 想统一 token 成本口径 | 把路由与 token 账务放在同一处，让用量能归到查询与团队（本节 §5.3） | 用量能不能按团队拆分，而不是一笔混在数据库账单里 | 不要在没有归因的情况下做成本优化；不要按单价档位选型而忽略进入调用的行数 |
| 想上智能体编排取数 | 先补前置：工具目录 + 权限范围 + 调用预算 | 平台是否把这三样做成一等能力 | 不要在没有权限与审计的前提下让智能体调用库内算子 |
| 刚开始引入库内 AI 能力 | 先把三样登记成资产：模型版本、提示版本、增量键（本节 §5.3） | 有多少条 AI 产出能追到模型与提示版本 | 不要把厂商 GA 公告与样板客户故事写进选型结论 |

「明确不要做」这一列的共用逻辑只有一句：**本节真正变了的只有「调用点在哪儿」，数据边界与账单形状一寸没动**。所以预算应当投在模型版本登记、提示版本治理与增量键这三件确定性工程上；这三样没定下来之前，任何「AI 原生数仓」的采购都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先定边界**：数据能不能离开引擎，答案决定候选集是「一条通路」还是「两条通路」。
2. **再压行数**：谓词下推与增量键先做到位，这一步决定账单形状，且不需要任何新采购。
3. **然后登记版本**：模型版本与提示版本进变更记录。这一步决定跨期对比有没有意义。
4. **最后才谈智能体与统一接口**：这两类都会改变责任归属且接口未定，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新模型——边界划分、增量键、版本登记、用量归因，全是流程与工程。这也解释了本节为什么没有 L1：真正成熟的那部分（把函数写在 SQL 里、把产出落成表）不需要被宣传，而需要被宣传的那部分，还没有成熟到能被发布方之外的人核验。

### 5.8 小结

> 本节小结：AI 在本主题上**只改了一条机制**——**调用点从应用进程移进了 SQL 执行器**，于是「百万行的批量标注」从一项 ETL 工程变成一条 `INSERT ... SELECT`，算子被纳入同一个执行计划，产出物落成可 JOIN、可增量跳过、可限定范围重跑的普通列与普通表。它**没有改变**的是三件事：数据边界仍是合规判定（换开源权重不改变请求发往谁的机器）、账单形状仍正比于「进入调用的行数 × 单价」、模型服务仍是数据库之外的一个依赖（失败粒度因此是整条查询）。本节没有一行达到 L1，离得最近的五行——AI Function 写进表达式位置、文档与多模态 AI Function、自然语言查询、Self-Hosted LLM 接入、模型路由——① 都成立，**共同缺的只有「第三方（非厂商）公开生产案例」这一条**（③ 的成色五行不同，逐行见表与 5.2.x）；所以现在该投的是模型版本与提示版本的登记、增量键与用量归因，而不是「跨库统一 AI 算子接口」。
