## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

把 8 个模式排成一张「按场景选一个」的表，读起来像是同一个问题的 8 种做法。实际上它们要被拆成三层：**算子在哪儿执行**（函数化 / 批处理 / 自托管 / BYO-LLM / 边缘是第一层，差别在数据动不动、模型来自谁）、**怎么召回非结构化内容**（融合 / 智能体是第二层）、**问题由谁提出来**（NL2SQL 是第三层）。同一个团队通常三层各选一个，而不是八选一。

第一层之所以会分叉，只因三条硬约束：**数据能不能离开引擎**、**进入模型调用的行数占表行数的比例**、**产出的结果要不要进正式数据链路**。前两条与实现技巧无关，第三条决定「这份标签谁负责」。忽略它们去比较「哪个更快」，等于在比 8 个模式里最不重要的一项。

第二层的分叉点是**向量列与结构化过滤是否总在同一句查询里出现**。带高选择性过滤的检索，召回与过滤联立会把候选集压掉几个数量级；纯向量的点查、高并发、无过滤，则反过来适合专职的索引服务。这是「索引建在哪个域」的问题，不是「谁更先进」。

第三层的分叉点是**提问的人写不写 SQL**。这一层只有 NL2SQL 一个入口：它消费算子的产出、不改变算子任何一项机制——把这一层与执行层放进同一张表比较，是本节最容易被误读的地方。智能体虽然也落在消费路径上，但它的分叉点是召回方式，按 3.1 归第二层（见 3.2.5）。

换个角度看同一件事：**每个模式都是某条约束在当时的最优解，约束一挪，最优解就变了**。函数化是"结果必须立刻返回"逼出来的，批处理是"行数远超交互能承受的量"逼出来的，私有化是"连请求都不能出边界"逼出来的，BYO-LLM 是"任务难度分层而预算有限"逼出来的。读下面的模式时，先记住它对付的是哪条约束，比记住它的写法更有用——写法可以换，约束不会。**判断自己该用哪一个，不是去比较它们的能力清单，而是先把自己的约束写成一句话，再看哪一个模式是这句话的直接产物。**

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据边界（数据能不能离开引擎） | 候选集合的大小。一旦出仓就多一份长期存活的副本，权限、生命周期与账单都要在第二处重建 | 「LLM in SQL 只是比外部 API 快一点」——在受监管数据上这不是快慢之差，是行与不行之差 |
| 调用粒度与成本杠杆位（进入调用的行数 ÷ 扫描行数） | 账单的形状：随业务量增长，还是随表规模线性上涨 | 「成本高就换个便宜档位」——档位单价差数倍，进入调用的行数可差两个数量级 |
| 访问模式（集合批处理 / 单次交互 / 语义检索） | 算子放哪、批合并有没有意义、向量索引建在哪一侧 | 「批处理对什么都更快」——单次交互下批合并没有可合并的空间，只增加排队延迟 |
| 延迟要求（交互 SLA vs 离线窗口） | 走同步算子还是异步作业；决定超时降级与失败重跑粒度 | 「延迟高就上小模型」——单次交互的延迟由模型决定，合并与并行帮不上忙 |
| 一致性要求（产出是否进正式链路） | 提示词与模型版本要不要落进治理域 | 「提示词写在应用里更灵活」——产出要进报表时，「这批标签谁生成的」必须先答得出 |
| 模型来源与合规等级 | 请求发往谁的机器：托管端点 / 自建端点 / 内网推理 | 「BYO-LLM 就安全了」——端点若在公网，请求照样出了边界 |
| 团队技能（会 SQL 的人 vs 会 Python 工程栈的人） | 落地速度，以及错选之后的纠正成本 | 「AI 能力要先建在应用侧」——把能力推进到会 SQL 的人能自己用，是这门技术最直接的组织收益 |

表里最后一行最常被当成"软因素"漏算，但它解释的是最硬的一种差距：**同一套技术，在会 SQL 的人占多数的组织里落地快，在只有应用团队能维护它的组织里落地慢**。因为执行层算子把 AI 能力从"需要 Python 工程栈"降到"会写 SQL 即可"，所以它改变的不只是技术选型，还有"谁能提出问题"这件事本身——代价是数据团队从此要为带 LLM 的产出负责，那份责任要求提示词与模型版本必须落在他们能审计的地方。

### 3.2 模式逐个拆解（核心节）

八个模式按**怎么调 → 怎么召回与提问 → 请求与推理放在谁的机器上**分三组依次讲：3.2.1–3.2.2（函数化 / 批处理）、3.2.3–3.2.5（融合 / NL2SQL / 智能体）、3.2.6–3.2.8（私有化 / BYO-LLM / 边缘）。**这是讲解顺序，不是 3.1 的三层**——两套分组并不相同：3.1 的第一层（算子在哪儿执行）是 3.2.1、3.2.2 与 3.2.6–3.2.8，第二层（怎么召回非结构化内容）是 3.2.3 与 3.2.5，第三层（问题由谁提出来）是 3.2.4；也就是说 3.2.6 私有化并不属于「执行层之外」的第三层，它正是第一层在「请求发往谁的机器」上的分叉。每个模式都按「约束 → 结构 → 机制 → 代价 → 失效点 → 真实使用」六件事拆解，其中**失效点一律反转本模式自己的优点**——不是"稍微复杂"，而是"在什么条件下它原本的优点会变成缺点"。

#### 3.2.1 函数化模式（AI Function 直接调用）

- **被什么约束逼出来**：结果要在一次交互里返回，而补一次 ETL 加一轮回写的时间与副本成本都付不起。
- **结构**：

```sql
-- 算子在 SELECT 列表里，与 SUM / SUBSTR 在语法位置上一视同仁
SELECT review_id,
       ai_classify(review_text, ['positive','negative','neutral']) AS sentiment,
       ai_summarize(review_text, max_words => 50)                   AS summary
FROM   reviews
WHERE  product_id = 'P001'     -- 谓词先下推：它决定有多少行进入算子
  AND  dt = CURRENT_DATE;
```

- **为什么这样设计有效**：因为算子写进了 SQL 的表达式位置，所以它被纳入同一个执行计划——谓词下推、列裁剪、并行度都由引擎决定，调用发生在数据已被存储层扫描出来的那一刻，不需要另起一段搬数据的工序。
- **代价**：每次调用都带一次模型端点的网络往返，行数即往返次数；尾延迟由模型抖动决定而不是由引擎决定，而 SQL 的失败粒度通常是整条查询——一次抖动放大成一次作业失败。
- **失效点**：当进入算子的行数从几十行涨到百万行时，「简单、即写即用」反转成「账单随表规模线性上涨」，因为每行的固定开销不再能被"只调一次"摊薄，而过滤条件没有跟着行数一起收紧。
- **真实使用**：Snowflake Cortex 把摘要、分类、情感、翻译、补全以 SQL 函数暴露，与 `SUM` / `SUBSTR` 在语法层面无差别（【公开：主文件 §1.4 记录 Snowflake Cortex 于 2023-11 GA，含 `ai_classify` / `ai_summarize` / `ai_extract`】；版本与能力边界以 Snowflake 官方文档当前版本为准）。

#### 3.2.2 批处理模式（批量 AI 处理）

- **被什么约束逼出来**：候选集在百万行以上、延迟允许按调度周期计，而逐行调用按 token 付不起。
- **结构**：

```sql
-- 先压候选集，再用增量键跳过已处理行，最后才调用
INSERT INTO review_ai_daily
SELECT r.review_id,
       ai_classify(r.review_text, ['positive','negative','neutral']) AS sentiment,
       ai_embed(r.review_text, model => 'bge-m3')                    AS embedding
FROM   reviews r
LEFT   JOIN review_ai_daily p ON r.review_id = p.review_id
WHERE  r.dt = :biz_date       -- 分区裁剪：只扫当天
  AND  p.review_id IS NULL;   -- 增量键：已标注过的行不进算子
```

- **为什么这样设计有效**：因为结果落成普通表，它一次获得三样东西——可被下游 JOIN 的稳定产物、可被 WHERE 跳过的增量键、可被限定范围重跑的失败行；批处理便宜的根本原因不是"一次调很多"，而是"只调需要调的那些行"。
- **代价**：新鲜度被调度周期封顶（T+1 或小时级）；向量列让行宽显著增加，不相干的扫描会跟着变慢，列裁剪与分区隔离是配套的必须项而不是优化项。
- **失效点**：当上游是持续到达的数据、而作业又被写成"每天全量重算"时，「结果可持久化」反转成「重复付费」——每轮重跑都把已处理过的行再调一次，账单随执行次数而非数据增量增长，因为增量键没被写进 WHERE。
- **真实使用**：阿里 MaxCompute + PAI UDF 的批处理案例把「**成本前置**」列为第 1 条核心组件：在 SQL 里先用条件与去重把候选集缩到必要规模再调用，对已处理过的数据用增量键跳过（【公开：本书 §6 阿里案例组件清单，转引阿里公开材料 2019–2024】；UDF 能力以阿里云官方文档当前版本为准）。

#### 3.2.3 融合模式（向量 + SQL 混合）

- **被什么约束逼出来**：一次检索既要按语义召回、又要按结构化条件过滤，两者必须在同一句查询里联立——否则要把候选 ID 集合搬回原库再过滤。
- **结构**：

```sql
-- 向量列与结构化列在同一张表上，召回与过滤进入同一个执行计划
SELECT d.doc_id, d.title, u.department,
       1 - (d.embedding <=> ai_embed(:query, model => 'bge-m3')) AS similarity
FROM   documents d
JOIN   users u ON d.author_id = u.id
WHERE  u.department = 'Sales'          -- 高选择性谓词先把候选集缩小
  AND  d.dt >= CURRENT_DATE - 30
ORDER  BY d.embedding <=> ai_embed(:query, model => 'bge-m3')
LIMIT  10;
```

- **为什么这样设计有效**：因为向量列与结构化列同处一行、同一个存储域，"先按部门过滤再算距离"与"先算距离再回表过滤"可以在同一个优化器里比较代价；跨系统召回则只能先把 ID 集合搬过去——过滤越严、命中集合越小，这笔搬运的相对开销越大。
- **代价**：向量列让行宽显著增加，无关查询的全表扫描变慢。按每条 1024 维、FP16（2 字节）折算，每条向量约 2 KB；1 亿条约 **200 GB** 常驻【推算：1024 × 2 B = 2 KB/条 × 1 亿条；维度与精度按你的模型实际取值重算】。索引算法（HNSW / IVF / PQ）见主文件 §2.2。
- **失效点**：当查询是纯向量点查、不带任何结构化条件且并发很高时，「召回与过滤联立」这个优点不再存在，而把点查放进通用分析引擎要为它常驻一整套引擎资源——优点反转成资源错配。
- **真实使用**：主文件 §2.4 把「LLM in SQL vs 专用向量数据库（Pinecone / Milvus）」列为相邻概念对照，只给"一体化 vs 专注向量"的定性定位、不含年份（【经验】：两类路线各自的成熟度差异，请按各厂商官方文档与 release note 的当前版本自行核验）。判定方法：拿最近一个月最频繁的那条检索请求，数它带几个高选择性结构化过滤条件。

#### 3.2.4 NL2SQL 模式（自然语言查询）

- **被什么约束逼出来**：提问的人不写 SQL，而正确答案又依赖口径（哪张表、哪个状态、哪个时间窗）——翻译必须落在定义层上，否则每次提问都是一次重新解释。
- **结构**：

```text
"上周 GMV 是多少？"
      │
      ├─ ① Schema Linking：从元数据 / 语义层召回候选表与指标（主文件 §2.3）
      ├─ ② 口径解析：命中语义层里的指标定义，而不是裸表直译
      │      SELECT SUM(payment_amount) FROM dwd_trade_order
      │      WHERE order_status = 'PAID' AND dt BETWEEN :start AND :end
      ├─ ③ 执行与自校正：失败或结果异常则回退重写
      └─ ④ 答不出就拒答——不允许"用相近口径凑一个"
```

- **为什么这样设计有效**：因为翻译的落点是**定义层里的指标**而不是表上的列，同一个问题在任何时间、任何工具里问，都落到同一段口径上——这套东西的价值不在"能翻"，而在"翻到的总是同一个口径"。
- **代价**：多了一层可能翻错的环节，而它的错误形态不是报错，而是"跑得通、语义不是提问者的本意"；因此拒答策略与人工抽检是组件的一部分，不是兜底。
- **失效点**：当提问者本来就会写 SQL 时，「零门槛」反转成「多一层翻译」——门槛收益对这部分人根本不存在，而翻错的风险照样存在。
- **真实使用**：Snowflake Cortex Analyst 与 Databricks Genie 都属这类（【公开：主文件 §1.4 记录 Cortex Analyst 于 2024-05 GA、Genie 于 2025-03】；以两家官方文档当前版本为准）。判定方法：看过去一个月里，用户自己改写 AI 生成 SQL 的比例。

#### 3.2.5 智能体模式（AI Function + RAG）

- **被什么约束逼出来**：答案既要"有依据"（来自文档）又要"算得准"（来自表），两种数据形态互不替代。
- **结构**：

```sql
-- 向量召回给依据，SQL 聚合给事实，两者在同一个查询里组装
WITH retrieved AS (
  SELECT chunk, 1 - (embedding <=> ai_embed(:q, model => 'bge-m3')) AS sim
  FROM   docs WHERE tenant_id = :tenant ORDER BY sim DESC LIMIT 5
), fact AS (
  SELECT COUNT(*) FILTER (WHERE status = 'PAID') AS paid_cnt
  FROM   orders WHERE dt = :d
)
SELECT ai_generate_text(
         '依据：' || STRING_AGG(chunk, E'\n')
       || E'\n事实：' || (SELECT paid_cnt FROM fact)
       || E'\n问题：' || :q, model => :strong_tier) AS answer
FROM retrieved;
```

- **为什么这样设计有效**：因为"事实"这一段走的是 SQL 聚合而不是模型记忆，数值不可能被幻觉出来；模型只负责把检索到的依据与算准的事实组织成话，责任边界可查。
- **代价**：一次问答串两段链路（召回 + 生成），端到端延迟是两段之和；两套存储意味着两条新鲜度链路——业务表口径改了，向量侧的元数据也要跟着刷新，而"索引里的元数据比业务表旧"不会报错，只会让效果悄悄变差。
- **失效点**：当问题本身只是"查一个数"时，「有依据 + 自然语言表达」反转成「绕远路」——两段链路里没有一段是为查数设计的，延迟翻倍而准确性不变。
- **真实使用**：多数团队的形态是"向量召回给上下文、SQL 聚合给事实"（【经验】：切分长度、召回条数这类参数差别很大，不在本节给统一值；可按「hybrid RAG + SQL」检索公开工程实践，按自己的评测集复测）。

#### 3.2.6 私有化模式（自托管 LLM）

- **被什么约束逼出来**：连"请求"都不能出边界——不是数据不出仓，而是数据不出内网。
- **结构**：

```sql
-- 端点指向内网推理服务；函数签名不变，变的是请求发往谁的机器
ALTER DATABASE app SET ai_model_endpoint = 'http://vllm.internal:8000/v1';
SELECT ai_generate_text('总结以下评论文本：' || review_text, max_tokens => 256)
FROM   reviews WHERE dt = CURRENT_DATE;
```

```text
数据平面：表 ──扫描──► 引擎内算子 ──HTTP──► vLLM / Ollama（内网）──► 权重在本机
控制平面：模型版本、提示词、用量配额 全部落在企业边界之内
```

- **为什么这样设计有效**：因为权重与推理都在内网，"请求出边界"这条风险项被彻底移除——合规上这是"行与不行"的差别，不是分数高低；同时端点、模型版本与配额全在同一治理域内，用量可以按业务归因。
- **代价**：自建推理要自己承担容量规划、限流与版本管理，算力的固定成本与运维人力不随业务量下降；端点抖动会直接表现为查询失败，重试粒度是整条查询，因此幂等要按"整条查询"设计。
- **失效点**：当任务复杂度上升、内网模型答不好时，「数据不出内网」这条优点不反转，但「自主可控」会反转成「能力上限自己扛」——使用者会绕开内网通道去用外部工具，合规控制随之失效。
- **真实使用**：金融、医疗、政务等强合规场景的常见选择（【经验】）。判定方法：看数据出网策略里有没有一条针对模型端点域名的放行规则——有放行规则，说明请求确实出了边界。

#### 3.2.7 混合云模式（BYO-LLM）

- **被什么约束逼出来**：任务难度分层明显、成本敏感，但合规等级又不允许全部调用走同一个来源——需要"签名不变、来源可换"。
- **结构**：

```sql
-- 签名不变，端点按任务分档：枚举型输出走经济档，开放式生成走强档
SELECT ai_classify(review_text, ['positive','negative'], model => 'economy_tier') AS sentiment,
       ai_generate_text('解释这条差评的可能原因：' || review_text,
                        model => 'strong_tier', max_tokens => 256)               AS reason
FROM   reviews WHERE dt = CURRENT_DATE;
```

- **为什么这样设计有效**：因为"从固定枚举里选一个"与"开放式写一段"的失败代价完全不同，所以按任务分档能在保持产出结构稳定的同时，把大部分调用放到便宜档位上——开销由调用分布决定，而不是由最贵的那个任务决定。
- **代价**：同一批数据用两个档位会得到两批口径不一致的标签；分档引入效果差异，必须配影子表对比与回滚路径；缓存又引入新的失效语义（TTL、"输入相同但期望不同"的边界要写清楚）。
- **失效点**：当任务分布以开放式生成为主时，「分层路由省钱」反转成「分档基本没省」——便宜档承接的调用量本就很小，而双档位带来的版本管理与效果对齐成本照付。
- **真实使用**：主文件 §2.3 的「模型路由」把基于任务 / 成本 / 合规 / 延迟四类路由列为独立做法；本书 §6 的 Databricks 案例把「换模型时先对同一批数据跑影子表、对比新旧输出差异，达标后再切换主表」列为组件（【公开：见主文件 §2.3 与本书 §6 Databricks 案例组件清单】；口径名与档位名以各供应商当前价目与文档为准）。

#### 3.2.8 边缘模式（Edge AI）

- **被什么约束逼出来**：数据产生在边缘（门店设备、工控机、车载），上行带宽与出网成本不允许把原始数据传回中心，而判断又要在本地毫秒级完成。
- **结构**：

```text
边缘节点（门店 / 设备 / 工控机）                中心
  原始数据（图像 / 文本 / 传感器）
        │  本地预处理：规则先过滤，只有命中才进模型
        ▼
  本地小模型（SQL 调用本地推理进程）──只上行结构化结果（标签 / 计数）──►  汇总表
        │
  结果落本地表 ── 断网可继续工作；网络恢复后补传（带本地时间戳与幂等键）
```

- **为什么这样设计有效**：因为只有结构化结果上行、原始数据不出节点，带宽占用与合规暴露面同时被压小；判断在本地完成，端到端延迟不再受回传链路影响。
- **代价**：模型要能在受限算力上跑起来（量化 / 蒸馏），每个节点的模型版本都要能远程升级与校验；节点数量一多，"版本 × 配置"的组合本身就是一套需要常驻维护的系统工程。
- **失效点**：当任务需要跨节点的全局上下文（同一用户在多家门店的行为）时，「本地闭环」反转成「看不到全貌」——单点判断都对、整体判断错，而修正只能靠中心侧规则补偿，且补偿规则往往滞后于数据。
- **真实使用**：IoT、零售门店、工业设备是典型场景（【经验】：开源小模型的参数规模与量化版本可由其官方模型卡核验；"某公司在某门店部署了某模型"这类断言不在本节给出）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 数据不出仓 + 单次交互 + 几十行 | 函数化 | 批处理为吞吐设计，交互场景下只增加排队延迟 | 进入算子的行数是否在百行量级 |
| 数据不出仓 + 百万行以上 + 离线窗口 | 批处理 | 函数化每行一次往返，账单随表规模线性上涨 | 「调用行数 ÷ 扫描行数」 |
| 语义召回总带高选择性过滤与 JOIN | 融合（仓内向量） | 专用向量库要把召回集合搬回来，过滤越严越不划算 | 最频繁检索请求的结构化过滤条件个数 |
| 纯向量点查 + 高并发 + 无结构化条件 | 专用向量数据库 | 仓内向量要为点查常驻一整套分析引擎资源 | 过滤条件数是否为零 |
| 提问的人不写 SQL | NL2SQL + 执行层算子 | 只给算子，门槛没有下降 | 用户自己改写 AI 生成 SQL 的比例 |
| 答案要有依据 + 要有算准的数值 | 智能体（召回 + SQL 事实） | 纯 RAG 让数值依赖模型记忆 | 问题里是否含聚合或数值 |
| 请求也不能出边界 | 私有化（内网推理） | BYO-LLM 若指向公网端点，合规断在最后一跳 | 出网策略里有几条端点域名放行规则 |
| 任务难度分层 + 成本敏感 | 混合云（BYO-LLM + 分档 + 缓存） | 单一档位把简单任务付成复杂任务的价 | 经济档能承接的调用量占比 |
| 数据产生在边缘 + 上行带宽受限 | 边缘小模型 + 只回传结构化结果 | 中心批处理要求把原始数据传回来 | 单节点上行带宽 vs 原始数据日增体积 |
| 需要跨节点的全局上下文 + 原始数据不能上行 | 边缘本地判断 + 中心规则补偿 | 纯本地闭环会"单点判断对、整体判断错" | 判断需要的历史窗口是否跨越多个节点 |

本主题下**最常被误选的一对是「函数化」与「批处理」**。误选的方向几乎总是把大表交给函数化写法：理由是"先跑通再说"，而它跑得通——只是账单随表规模走、重跑时把已处理过的行再调一次。等到账单被发现时，要重写的是作业结构（补谓词下推、增量键、失败行落表），不是函数参数；这也是本书 §6 的阿里与 Snowflake 两个案例把成本控制写进 SQL 的过滤逻辑、而不是写进模型选择章节的原因。

第二常被误选的是**把 NL2SQL 当成批处理的替代品**。这两者根本不在同一层：一个决定问题怎么被提出来，一个决定计算在哪一侧发生。误选的表现是——先上了 NL2SQL，发现业务方问出来的数依旧口径不一，因为底层仍没有一处唯一的定义；正确的顺序是先把口径落到定义层（主文件 §2.3 的「指标语义层集成」），再叠翻译层，**否则翻译层只是把口径混乱提前暴露给更多不会分辨的人**。

判断自己属于哪种误选，有一个共同的动作：**把最近一次处理的「扫描行数」与「调用行数」写下来**。两个数接近，说明杠杆没用上（对应第一种误选）；两个数差得远但业务方仍在质疑数字，说明问题不在算子层（对应第二种误选），要去定义层找。

### 3.4 组合模式：真实系统不会只用一种

三层模式各选一个是常态，三条常见组合的差别只在"多叠了哪一层"：

**组合一：执行层算子 + 消费层入口（函数化 / 批处理 + NL2SQL 或 Agent）**。职责边界——算子只负责在数据所在处执行语义计算，Agent 只负责理解意图与编排，**Agent 不搬运数据**。运维代价——消费层新增一条失败路径（意图理解错），因此每个结论都要能指回它调用的那次查询。适合规模：有业务方直接取数诉求、且已有稳定指标口径与元数据的组织。

**组合二：算子 + 向量 + 检索组织（融合 / 智能体）**。职责边界——向量层负责"找到相关的"，SQL 负责"算准的"，模型只负责把两者组织成话；三层各自可替换。运维代价——两套存储、两条新鲜度链路，业务表结构变更时向量侧的元数据要同步刷新，而这类不一致只在效果上暴露、不在监控里暴露。适合规模：知识问答与检索型应用，且检索请求普遍带结构化过滤。

**组合三：算子 + 控制平面（私有化或 BYO-LLM 分档 + 提示词版本化 + 缓存）**。职责边界——引擎提供算力与批处理，SQL 提供数据与治理，提示词随 SQL 进版本管理与血缘，模型档位决定质量与成本的取舍。运维代价——提示词迭代要走 SQL 变更流程，比改一行应用常量重得多；缓存与分档各自引入新的语义（失效、口径不一致）。适合规模：产出要进正式报表或特征链路、需要回答"这批标签是谁用哪个模型生成的"。

三条组合有一条共同的排布原则：**让每一件做它机制上最擅长的事**——算子在数据在的地方执行，检索在索引在的地方发生，翻译层只服务不会写 SQL 的人。第二原则是**组合数不超过团队的运维带宽**：每多一件，就多一处新鲜度告警、多一个"两套系统对同一个问题给出不同答案"的战场；组合的价值来自职责边界清楚，而不是来自组件数量多。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 每行一次 LLM 调用 | 作业里把整表直接丢进 AI 函数，调用行数 ≈ 扫描行数 | 固定开销无法摊薄，账单随行数线性上涨 | "反正是批处理"——把批处理理解成"一次处理很多"，而不是"只处理该处理的" | 谓词下推压候选集 + 增量键跳过已处理行 + 批合并 |
| 忽视 Token 成本 | 上线后账单随表规模走，预算按业务量做的 | 成本函数形状与预期不符，扩表即扩账 | 成本被记在"模型选择"这一栏，而杠杆在"进入调用的行数" | 成本监控按作业归因 + 配额 + 按任务分档 |
| 数据出仓违规 | 数据先导出再调外部 API，产出回写进仓 | 多一份长期副本，权限、生命周期、账单要在第二处重建 | 抄的是应用侧范式，而数据平台侧没有可下推的执行者时，导出是最省事的一步 | 判据是"数据能不能动"：不能动就只能走库内算子，而不是导出后再调外部端点 |
| Prompt 注入攻击 | 被处理的文本里出现"忽略以上指令"类内容 | 文本被当指令执行，越权或破坏性动作在数据侧生效 | 把模型当函数用，却忘了它的输入里有不受控的文本 | AI 函数只读、只分类或只从固定枚举取值，不暴露执行能力；加注入检测与沙箱 |
| 忽视缓存 | 同一批文本反复调用，结果表里同一 review_id 有多次调用记录 | 为相同输入重复付费，重跑成本与首跑相同 | 缓存被认为是引擎的优化项，而不是作业设计的一部分 | 输入 hash 精确缓存 + 语义缓存 + TTL，把命中率纳入作业指标 |
| 向量检索索引未优化 | 检索延迟随表增长，执行计划里出现对全表的距离计算 | 从"近似最近邻"退化成"精确全表距离"，延迟不可用 | 先跑通功能，索引与压缩被排在性能优化里 | 建 ANN 索引（HNSW / IVF / PQ）+ 向量压缩 + 分片；量化前先定召回率底线 |
| AI Function 滥用 | 简单聚合、字符串截断也走 AI 函数 | 为确定性计算付不确定的价格与延迟 | SQL 里能调 AI，就用 AI 代替 SQL 原生能力 | 原生聚合与字符串函数优先，AI 只做语义理解、生成与分类 |
| 结果不可解释 | 同一输入多次调用输出不同，业务方拒绝采信 | 产出无法进正式链路，只能算"某个应用的中间结果" | 把 LLM 的产出当普通列，而它的口径由提示词与模型共同决定 | 固定枚举 / 结构化输出约束 + 多次采样投票 + 规则校验 + 人工抽检 |
| 模型版本管理混乱 | 不同批次标签由不同模型生成，产出表里查不到用的是哪版 | 产出无法归因，"为什么这批标签和上批不一样"答不出 | 模型与提示词被当作配置而非口径的一部分 | 提示词随 SQL 版本化，模型 / endpoint 进入血缘，换模型先跑影子表 |
| 忽视延迟 SLA | 单次交互查询端到端延迟远超预算 | 交互场景不可用，用户绕开平台自行取数 | 用离线批处理的指标衡量交互链路 | 交互走小档位或缓存；批量走异步作业；设超时降级 |

三个最危险的，在生产里是这样暴露的（末尾另附一组常被一起踩的）：

**「每行一次调用」通常不是一次事故，而是一次预算超支。** 它在试点期完全正常——数据量小，两种写法的账单看起来一样；进入生产、表规模上去之后，成本随时间线性上涨，根因藏在"每一行都发一次请求"这个写法里，不在预算科目里。修它的动作是把过滤与增量补上，而不是换模型：档位单价差数倍，进入调用的行数差两个数量级。

**「数据出仓违规」暴露在审计而不是在监控。** 它不会让任何一条查询变慢或变红，只是在第二个系统里凭空多出一份副本，而"谁能读、留多久、算谁的预算"这三个问题在出仓那一刻没有答案。补上的规则往往与仓内那份不一致，于是同一份数据在两处有两套权限——这件事的代价不在账单上，在审计结论上。

**「Prompt 注入」暴露在数据侧。** 被处理的文本来自外部，而模型分不清"这段文本是数据"还是"这段文本是指令"。修法不是加一句提示词让模型更听话，而是**不让 AI 函数具备执行能力**：它只从固定枚举里取值、只输出受约束的结构，破坏性动作永远不经过模型。

**「忽视缓存」与「结果不可解释」常常一起出现。** 这两条看起来无关，其实同源：它们都说明团队把 LLM 调用当成了"一次不可控的远程调用"，而不是"一个有输入、有输出、可复算的算子"。一旦按算子来对待，缓存就在设计的自然位置上（输入相同即命中），可解释性也有了抓手（固定枚举、结构化输出、多次采样投票）；反之，两件事都会变成事后补丁——缓存靠加一层中间件，可解释性靠人工抽检。**判定方法很简单：问"同一行数据重跑一次，产出会不会变"——答案不确定，说明它现在还不是一个算子。**

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 候选集从千行到亿行 | 函数化直调 | 每行一次往返，账单随表规模线性上涨 | 批处理 + 谓词下推 + 增量键 | 新鲜度从秒级降到调度周期；首轮仍需一次全量 |
| 从离线窗口到交互查询 | 批处理 | 为吞吐设计，交互下只增加排队延迟 | 函数化 + 小档位 + 缓存 | 交互不能复用批处理的结果表，要重新定义口径 |
| 检索从无过滤到强过滤 | 专用向量数据库 | 召回集合搬运的相对开销随过滤选择性上升 | 仓内向量（同表联立） | 向量列让行宽增加，需配套列裁剪与分区隔离 |
| 从单档位到多档位 / 多模型 | 单档位直调 | 无法回答"这批产出用的是哪个模型" | 分档 + 提示词版本化 + 影子表 | 提示词迭代要走 SQL 变更流程，试错变慢 |
| 从中心处理到边缘处理 | 中心批处理 | 上行带宽与合规暴露面同时放大 | 边缘小模型 + 只回传结构化结果 | 节点模型版本管理成为独立工程 |
| 从单团队内网到多团队 / 多租户 | 各自自建端点 | 配额与用量无法按团队归因，限流互相干扰 | 统一模型网关 + 按业务归因 | 网关自身成为关键路径，要按"整条查询重试"设计幂等 |

跃迁的共同点是**模式本身没有变坏，是约束换了**：候选集涨了一个量级，函数化的"简单"就变成了"贵"；检索多了高选择性过滤，独立索引就变成了"绕路"。所以换模式的信号不是"出现了更好的工具"，而是**某个约束跨过了阈值**——这类阈值是可以事先量出来的（调用行数占比、过滤条件选择性、上行带宽与数据日增量的比值），不是要等到出事才知道。**把这三个比值设成监控项，比记住这张表的任何一行都更有用。**

### 3.7 自检清单

- [ ] 最近一次 AI 作业里，「调用行数 ÷ 扫描行数」是多少？比值超过一成【经验：自检判据用的经验阈值，不是对现实效果的测量】，说明谓词下推与增量跳过没做。
- [ ] 产出表里是否记录了「哪版提示词、哪个模型档位」？提示词是写在 SQL / 视图里，还是拼在应用代码里？两问合起来决定口径能否从数据侧归因。
- [ ] 数据出仓之后产生了哪些长期存活的副本？每一份的权限、生命周期与预算各归谁？
- [ ] 同一份文本重复出现时是否命中缓存？抽 100 行重复文本，数实际产生了多少次调用。
- [ ] 向量列所在表的查询是否带上了列裁剪与分区条件、是否已建 ANN 索引（HNSW / IVF / PQ 一类）？执行计划里若仍在算全表距离，这一层还没落。
- [ ] AI 算子的输出是否有固定枚举或结构化约束？同一行数据重跑一次产出会不会变？两问任一答不上，说明它还不是一个可复算的算子。
- [ ] 失败行是否单独落表、可单独重跑？若一次失败要整批重来，重试成本等于一次全量。
- [ ] NL2SQL 场景是否配了"答不出就拒答"？没有拒答的翻译层，会用相近口径凑出答案。
- [ ] AI 函数是否用在了 `SUM` / `COUNT` 就能解决的地方？出现即违反"原生能力优先"。
- [ ] 单次交互查询的端到端延迟预算里，模型调用占几成？没有这个数，超时降级无从设计。
- [ ] 有没有一条"这个模式什么时候该换"的阈值监控？三个可量的比值：调用行数 ÷ 扫描行数、过滤条件选择性、上行带宽 ÷ 数据日增量。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 数据不能出仓，提问者会写 SQL | 函数化 / 批处理（按行数分流） | 数据不跨存储边界，副本数为零；代价是把端点抖动搬进了查询的关键路径 |
| 数据不能出仓，提问者不写 SQL | 上述算子 + NL2SQL（附拒答） | 翻译落在定义层上，口径唯一；代价是多一层可能翻错的环节 |
| 数据不能出仓，请求也不能出内网 | 私有化（内网推理） | 请求与权重都在边界内；代价是算力固定成本与能力上限自担 |
| 检索总带结构化过滤 | 融合（仓内向量） | 召回与过滤在同一执行计划里联立；代价是行宽增加与 ANN 调优的边界 |
| 纯向量点查、高并发 | 专用向量数据库 | 专职服务为 ANN 优化；代价是第二份副本与两条新鲜度链路 |
| 产出要进正式链路 | 任一算子 + 提示词版本化 + 模型进血缘 | 口径可归因，产出才可能被数据团队负责；代价是提示词迭代变慢 |

> 本节小结：本主题下决定模式选择的唯一那条约束是**数据边界**——它先筛掉一半候选，剩下的再按「进入调用的行数」分流。其余所有维度（延迟、成本、新鲜度、团队技能）都只是在这一层筛选之后做微调；反过来，把边界问题当成权重去打分，就会得出一个既跑得通、账单又不受控的方案。
>
> 💡 **思考锚点**：把你最近一条 AI 取数链路的两个属性写出来——数据能不能出仓（边界），以及每次调用要代入多少行（行数）。按 3.1 的筛选顺序它该落在哪个模式？如果第二步的行数把你推向批处理，而第一步的边界你其实判错了（数据本可出仓），你会白付哪一份代价：仓内算力，还是那一层的副本与新鲜度链路？
