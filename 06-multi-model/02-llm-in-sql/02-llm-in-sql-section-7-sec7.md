## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

第一，打分把**硬约束**压扁成了**权重**。「数据不出仓」一列给外部 LLM API 打 1 分、给 LLM in SQL 打 5 分，读起来像是「弱 4 分」，好像可以靠其他维度的高分补回来；但在受监管的数据上，这不是 4 分的差距，而是**候选集合直接少一个**——合规是「行与不行」，不是「好与不好」。把一票否决项写成扣分项，是把最贵的一次决策伪装成一次权衡。

第二，同一维度在不同负载下权重相反。并行性能在**百万行离线批处理**上是决定性的，因为成本按调用的行数线性累加，MPP 内并行与批合并能把它整体摊薄一个量级；而在**一次交互查询**上它几乎无差别——那只是一两次往返，谁多一层调度都看不出来。分数是同一个数，含义随负载反转，而表里没有「负载形态」这一维。

第三，把**互补关系**当成了**竞争关系**。NL2SQL / Data Agent、RAG / 向量库、GraphRAG 与 LLM in SQL 不在同一层：前者是**消费层入口**（人怎么把问题提出来），后者是**执行层算子**（计算在哪一侧做）。把它们并排放进同一张表，读者会得出「要选一个」的结论；正确动作是把消费层叠在执行层之上（7.6）。

第四，「工具成熟度」这一维在这里最容易被读错。给 LLM in SQL 打 4 分、低于外部 LLM API 与专用向量数据库的 5 分——这个分差反映的是「谁先出现、受众有多广」，不是「谁能力弱」。而「先出现」这条差异会自行消失：**【公开】** 主文件 §1.4 记录自 2023 年起 Snowflake Cortex、Databricks AI Functions、阿里 PolarDB AI、PostgreSQL pgai 依次把函数化调用做进 SQL 层（各条目的版本与年份见该节；逐条请以各厂商官方文档当前版本为准）。**用一条正在消失的差异去做两三年周期的选型，是本末倒置。**

第五，真正决定这类系统成败的约束，几乎都不在打分表的维度里：**进入模型调用的行数占扫描行数的比例**（决定账单）、**提示词与模型版本放在谁的代码库里**（决定可追溯）、**产出结果落在哪个治理域**（决定血缘是否延续）。三条在表里一行都没有。

第六，决策树把**三个不同层次**的东西塞进了同一个叶子节点：「企业级 AI 数据平台」一档写的是「LLM in SQL + Data Agent + RAG」——这三件分别是执行层、消费层与检索层的东西，它们之间不存在取舍，只有装配顺序。决策树的作用是在**互斥**的分支之间做选择；把互补项并列成一条分支，读者会以为存在一条「不用组合就能全都要」的捷径。这也是本章把候选分成四族、并把其中一族标为「与其余正交」的原因（7.2）。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 数据边界 | 数据能不能离开当前引擎、要离开几次 | 这是一条**筛选用**的硬约束，不是权重：跨一次边界就多一份副本，而副本本身就是受监管数据上的风险项，也是「两套账、两套权限」的起点 |
| 成本杠杆位 | 账单随「进入调用的行数」增长，还是随「表规模」增长 | LLM 按 token 计费，而 SQL 的输入是集合——杠杆在「让多少行进入调用」（谓词下推 + 增量跳过），不在模型档位；两者相差的量级不同（见 7.4 的推算） |
| 调用粒度 | 能不能把多行合并成一次调用、相同输入能不能复用结果 | 决定每行的固定开销（网络往返）能否被摊薄。这是集合语义天然占优、逐行脚本天然吃亏的一处，与引擎强弱无关 |
| 治理延续 | 提示词、模型版本、产出结果分别落在哪 | 三者不落在同一个治理域内，「这份标签是谁用哪个模型生成的」就答不出来，血缘在下游断链，而带 LLM 的产出无法被数据团队负责 |
| 检索耦合 | 向量召回是否总与结构化过滤 / JOIN 同时发生 | 决定向量索引建在仓内还是独立服务。跨系统召回要把 ID 集合搬来搬去，这笔开销随过滤条件的选择性上升——过滤越严，来回搬运越不划算 |
| 团队技能 | 会 SQL 的人多，还是会 Python 工程栈的人多 | 决定落地速度与错选后的纠正成本；把 AI 能力推进到「会 SQL 的人能自己用」，是这门技术最直接的组织收益（主文件 §1.1 列为解决的核心问题之二） |

> 这 6 条的权重随处境移动：**数据边界**是唯一一票否决的判据（受监管数据上它先筛掉一半候选）；**成本杠杆位**在批处理场景升为第一；**治理延续**在产出要进入正式报表、指标或特征链路后才成为硬要求；**检索耦合**只在你要做语义检索时才出现。**团队技能**自始至终都在，只是常被当成「软因素」而漏算——它是解释「同一个技术在两家公司落地速度差一年」的主因。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 外部 LLM API（Python 直调） | 应用侧调用通用模型 | 数据导出到应用进程，逐条或分批发往模型端点，结果再写回 | 应用开发 | 按 token 计费，各模型厂商商业服务 |
| Python + LangChain 等应用侧编排 | 应用侧把检索、调用、组装串成链 | 编排逻辑与提示词都在应用代码里，与数据平台零耦合 | AI 应用团队 | 开源框架 + 自备模型端点 |
| ETL + LLM 批处理 | 离线作业内做批量调用 | 先把数据落到作业可读的位置，再批量调用、结果写回 | 数据工程团队 | 自建，成本 = ETL 引擎 + token |
| 专用向量数据库（Pinecone / Milvus） | 以 ANN（近似最近邻）索引为核心的服务 | 向量与原文或元数据写入独立索引，召回返回 ID 集合 | 检索型应用、RAG 团队 | Pinecone 为商业托管；Milvus 为开源项目 |
| LLM in SQL（Snowflake Cortex / Databricks AI Functions / 阿里 PolarDB AI / PostgreSQL pgai） | 把 AI 算子做成 SQL 函数 | 算子在引擎内，数据不跨存储边界；调用由引擎批合并与并行调度 | 分析师、数据工程 | 随数仓 / 数据库提供，按用量计费 |
| In-Database ML（BigQuery ML / Apache MADlib） | 库内传统机器学习 | 训练与预测在库内，输入是表、输出是列——LLM in SQL 的直接前身 | 数据团队 | 随引擎提供 / 开源 |
| BYO-LLM（库内函数 + 自备模型端点） | 库内算子 + 可替换的模型来源 | 函数签名不变，端点可指向供应商托管或自建服务，按任务分档 | 成本敏感且合规要求混合 | 按端点计费 / 自建 |
| Self-Hosted LLM（vLLM / Ollama 于内网） | 库内算子 + 内网推理 | 权重与推理都在内网，请求与数据都不出企业边界 | 金融 / 医疗 / 政务 | 开源推理引擎 + 自备算力 |
| NL2SQL / Data Agent（Snowflake Cortex Analyst / Databricks Genie） | 消费层入口 | 把人话翻成 SQL，再交给执行层跑——它消费算子，不替代算子 | 业务方、BI 使用者 | 随平台提供 |
| RAG / GraphRAG | 消费层检索增强 | 向量召回 + 图遍历 + SQL 查事实，拼成答案 | 智能问答、知识应用 | 自建或随平台提供 |

这 10 个候选分**四族**，分族依据是「算子和数据各在哪一侧」，而不是品牌或开源闭源：

- **族一 · 算子外置、数据去找模型**（外部 LLM API、Python + LangChain、ETL + LLM 批处理）。内部差异只是「怎么搬、批量多大」，共同点是有**一份出仓的副本**。
- **族二 · 算子外置、索引专用**（专用向量数据库）。数据同样要出来，换回来的是一套为 ANN 优化的索引结构与调优手段。
- **族三 · 算子下推**（LLM in SQL、In-Database ML、BYO-LLM、Self-Hosted LLM）。数据不动、算子进引擎；四者差别在「模型来源可不可换」与「是否生成式」。
- **族四 · 消费层入口**（NL2SQL / Data Agent、RAG / GraphRAG）。与前三族**正交**：它不决定算子在不在仓内，只决定问题怎么提出来。

**先分族再选，能省掉一半比较**：族一的三个候选之间差异通常小于族一与族三之间的差异；族四根本不该进同一张选型表，它是叠加项。族与族之间的边界也正在互相侵入——专用向量库开始补结构化过滤与元数据，仓内引擎开始补向量索引与自然语言入口——**所以真正需要先定下来的不是「谁的功能更全」，而是「权威源放在哪一侧」**：向量与元数据在哪一侧是权威的，召回与过滤就应当在那一侧完成，另一侧只做转发。

分族还直接给出各族**特有的失败方式**，这比典型优势更有用：**族一死于出仓副本**——数据导出去以后权限、生命周期、两套账单都要重建一遍；**族二死于第二份副本的新鲜度**——业务表改了字段，向量库里那份元数据还是旧口径；**族三死于把外部依赖搬进关键路径**——模型端点的限流与抖动会成为查询失败的原因，而 SQL 的重试粒度通常是整条查询；**族四死于把「翻译」当成「理解」**——NL2SQL 可以生成一条跑得通、但语义不是用户本意的 SQL。

### 7.3 机制差异：为什么它们表现不同（核心节）

候选之间的差异看似十几种，但都能归到四条机制上。下表先给出全貌，四条随后逐个展开：

| 机制 | 一句话 | 它主要把哪两族分开 |
| --- | --- | --- |
| 算子的位置 | 数据跨不跨存储边界、跨几次 | 族一 / 族二与族三 |
| 调用粒度 | 账单随行数跑还是随表规模跑 | 族一（行级）与族三（集合语义） |
| 控制平面 | 提示词、模型版本与用量归谁记 | 族一（应用侧）与族三（治理域内） |
| 检索落点 | 向量索引与结构化数据是否同域 | 族二与族三的向量能力 |

#### 7.3.1 算子的位置：数据去找模型，还是模型来找数据

**机制是什么**：一次 AI 计算有两个可放置的部分——**数据**和**算子**。凡是引擎内执行的查询，数据天然在存储侧；算子放在哪，决定了要不要把数据搬过一次边界，搬几次，以及在搬过去的那一侧谁来重建设权限与治理。

**它在各候选中的实现差异**：

| 候选 | 数据移动方向 | 是否产生第二份长期副本 | 谁承担吞吐 |
| --- | --- | --- | --- |
| 外部 LLM API（Python / LangChain） | 仓内导出到应用进程 | 是（导出文件、中间表、日志） | 应用侧并发度 |
| ETL + LLM 批处理 | 仓内落到作业可读位置 | 是（中间落点） | ETL 引擎 |
| 专用向量数据库 | 转成向量后写入独立索引 | 是（向量 + 元数据副本） | 向量库服务 |
| LLM in SQL | 数据不动，调用从引擎发往端点 | 否 | MPP 引擎 |
| In-Database ML | 数据不动，模型进库内 | 否 | MPP 引擎 |

**由此必然导出的性质（因果句）**：因为**算子在引擎内、数据不跨存储边界**，所以成本函数里的「搬运」项直接消失，同时也不存在第二份副本——**这件事在合规上的意义大于在成本上的意义**：受监管数据上，副本本身就是问题，而不是它值多少钱。代价是**把外部依赖搬进了查询的关键路径**：模型端点的限流、超时与抖动成为执行计划的一部分，而 SQL 的失败粒度通常是**整条查询**（不像逐行脚本可以只重跑失败的那几行），所以一次端点抖动会放大成一次作业失败。族一没有这个失败模式——它的失败是应用级的，重试的也是应用级的那一段。

**公开证据**【公开】：主文件 §1.2 把「数据不出仓」列为第一驱动力，§1.4 记录 2023 年起 Cortex / AI Functions / PolarDB AI / pgai 依次把函数化调用做进 SQL 层（年份与版本条目见该节，逐条请以各厂商官方文档当前版本为准）。判定方法：数一次「数据从进仓到离开仓」的边界跨越次数——LLM in SQL 为 0，其余候选为 1 或更多；再数「有多少份长期存活的副本」——这一项决定你要维护几套权限。

**为什么这条机制决定的是「能不能用」而不是「快不快」**：副本这件事没有中间状态。数据出仓之后，你要在第二个系统里重新回答「谁能读、留多久、算谁的预算」三个问题，而这三个问题的答案在出仓的那一刻是缺失的，只能事后补——补上的规则往往与仓内那份不一致。**所以「数据边界」是一条前置判据：它决定候选集合，而不是给候选打分。**

**失效条件**：当数据本来就不在仓内（本地文件、外部 SaaS、另一个云的数据），或处理逻辑无法用 SQL 表达（多轮对话、需要自定义控制流的 Agent 循环）时，下推这一侧已经没有可下推的执行者，族一反而更直接。

#### 7.3.2 调用粒度：行级调用、批合并与缓存——token 成本曲线的形状

**机制是什么**：LLM 按 token 计费，而 SQL 是集合语义：一条查询天然面对 N 行。行级调用与批调用的差别不是实现细节，而是**成本函数的形式**——它决定账单是随表规模跑，还是随「真正需要处理的那部分」跑。

**它在各候选中的实现差异**：

| 候选 | 默认调用粒度 | 单位成本随什么变化 | 相同输入能否复用 |
| --- | --- | --- | --- |
| 外部 LLM API（循环调用） | 行级，一行一次往返 | 行数 × 每行 token + 每行固定开销 | 需自己实现，多数没有 |
| ETL + LLM 批处理 | 可手工分批，取决于作业实现 | 行数 / 批大小 + 落点出入 | 作业级缓存，粒度粗 |
| LLM in SQL | 引擎可对算子做批合并与并行调度 | 进入算子的行数 × 每行 token | 可按输入 hash 做精确缓存，被 §2.3 列为独立优化项 |
| 专用向量数据库 | 批量写入 + ANN 查询 | 索引中的向量数 + 查询次数 | 向量本身可复用，无需重算 |

**由此必然导出的性质（因果句）**：因为**SQL 的输入是集合而不是单条**，引擎可以在算子层面把多行合并成一次调用（主文件 §2.3 的 Batching），于是每行的网络往返被消除、固定开销被摊薄——**由这一条带来的量级差远大于换一个更便宜的模型档位**：档位之间的单价差异通常是数倍（【经验】：同一代模型的不同档位常见个位数倍到十倍区间，实际以供应商当前价目为准），而「让多少行进入调用」相差两个数量级（7.4 的推算）。反过来说，**因为批处理的收益来自「合并」，它对逐行交互的查询无效**——那种场景下单次延迟由模型决定，合并帮不上忙，此时"更快"只能靠更小的模型或缓存命中。

**公开证据**【公开】：主文件 §2.2 把 Batching、Caching、Push-Down、Cost-Based Optimization、Predicate Push-Down 列为 AI 算子的关键优化问题，并给出算子的代价模型 $\text{Cost}(f, n) = n \times \text{TokenCost}(f) + \text{NetworkCost}(f) + \text{CacheHit}(f)$；§2.3 明确列出「行内批处理把多行合并为一次调用（batch=32）」与「基于输入 hash 的精确缓存、基于相似度的语义缓存」两条做法。**案例侧只是部分印证**：§ 6 的四个案例中，只有阿里仓内批处理案例把「先筛选、再调用 + 增量键跳过已处理行」写成第 1 条核心组件（「成本前置（核心创新）」，成本随必要数据量而非表规模增长）；Snowflake 案例把成本控制列为第 2 条组件，其做法是「在 SQL 里先做过滤与采样再调用」；MotherDuck 案例有一条形近而意不同的组件——「LLM 调用的必要性判定」（先判该不该调，不是先缩小候选集）；Databricks 案例的 5 条组件里没有任何一条讲调用行数的收敛，只在组件 1 的 SQL 示意中带了 `WHERE ds = CURRENT_DATE` 这类日期过滤（逐条见 [§ 6 落地实践](02-llm-in-sql-section-6-sec6.md) 各案例的组件清单）。判定方法：把最近一次批处理作业的两个值取出来对比——**扫描行数**与**实际调用行数**；这两个数的比值就是你的成本杠杆还有多少没用到。

**为什么这条机制决定了试点能不能活到生产**：试点期数据量小，两种调用粒度的账单差距看不出来；一旦进入生产、表规模上去，行级调用的成本随时间线性上涨，而它的根因藏在「每一行都发一次请求」这个写法里，不在预算科目里——**等到账单被发现时，重写的是作业，不是参数**。这也解释了 § 6 的案例为什么这样写：阿里案例把「先筛选、再调用」放在第一条核心组件，Snowflake 案例把成本控制单独列成一条组件——**把成本杠杆写在作业的第一屏，它才会在评审时被看见；只写在模型选择的章节里，它就会留到账单出现时才被发现。**

**失效条件**：当每行输入很短、总行数很少，或结果必须在一次交互内返回时，没有可合并的空间；此时行级调用就是最优解，硬加批处理只会把延迟拉长（§3.5 陷阱 10 的「忽视延迟 SLA」是同一件事的另一面）。

#### 7.3.3 控制平面：调用、版本与账务归谁

**机制是什么**：模型调用有三样东西必须有人管——**账务**（用了多少 token、算谁的）、**版本**（哪个模型、哪版提示词）、**限流**（谁先被挡住）。这三件事放在引擎侧还是业务侧，决定了它们能不能被回答。

**它在各候选中的实现差异**：

| 候选 | 提示词放在哪 | 模型版本记录在哪 | 用量按什么归因 |
| --- | --- | --- | --- |
| 外部 LLM API（Python / LangChain） | 应用代码或配置中心 | 代码仓库，或没有记录 | 应用侧埋点（多数没有） |
| ETL + LLM 批处理 | 作业脚本内 | 作业配置 | 作业维度（较粗） |
| LLM in SQL | SQL / 视图定义内，随 SQL 版本化 | 与 SQL 同处一个版本管理体系，模型可作血缘节点 | 与数据用量同一套口径，可按业务归因 |
| 专用向量数据库 | 不涉及（只做检索） | 不涉及 | 索引与查询分开计 |

**由此必然导出的性质（因果句）**：因为**提示词写在 SQL 里，它就和 SQL 一起进入了版本管理与血缘**，所以「这批标签是哪个模型、哪版提示词生成的」从一次翻代码的动作变成一次查询；而如果提示词留在应用代码里，数据平台与应用侧各记录一半，排查要跨仓库拼凑——**这不是工具能力强弱的问题，是「逻辑写在谁的仓库里」的问题**。代价是**提示词的迭代要走 SQL 变更流程**，比改一行 Python 常量重得多；在提示词高频试错的阶段，这份摩擦是真实存在的，不能假装它不存在。

**公开证据**【公开】：§ 6 中 Snowflake Cortex 案例把「提示词随 SQL 版本化」列为独立组件，Databricks 案例把「模型 / endpoint 作为血缘节点」列为独立组件，阿里仓内批处理案例把「提示词与模型版本随作业记录」列为独立组件（三条见 [§ 6 落地实践](02-llm-in-sql-section-6-sec6.md) 各案例的组件清单）。判定方法：问一个可验证的问题——「上周产出那张标签表，用的是哪个模型版本」；一分钟内答得出，说明控制平面在治理域内；要翻代码仓库才答得出，说明它在外。

**为什么这条机制决定了产出能不能被负责**：带 LLM 的产出与普通 ETL 产出的差别，在于它的「口径」由提示词与模型版本共同决定，而这两样都不在数据表里。数据团队能为一列 `SUM(amount)` 负责，是因为这个口径写在 SQL 里、可被审计；同理，只有当提示词与模型版本也写在同一个可审计的地方，团队才可能为 `ai_classify(...)` 的产出负责。**控制平面不在治理域内，带 LLM 的产出就只能算「某个应用的中间结果」，不能进正式链路。**

**失效条件**：当团队只有一两个 LLM 场景、模型与提示词以月计不变时，这套版本化投入收不回来——没有人会同时维护两个版本，也就没有可追溯的必要。**这条机制的收益与「变更频率」成正比，而不是与「技术先进性」成正比。**

#### 7.3.4 语义检索的落点：向量索引建在仓内，还是独立服务

**机制是什么**：向量检索是近似最近邻问题，靠索引把「对全表算距离」换成「在索引结构里搜索」。索引建在哪，决定了召回结果要不要跨系统回传。

**它在各候选中的实现差异**：

| 候选 | 索引在哪 | 召回后怎么连明细 | 副本情况 |
| --- | --- | --- | --- |
| 专用向量数据库 | 独立服务 | 召回返回 ID 集合，回原库查明细；或在向量库里再存一份元数据 | 产生第二份副本（向量 + 至少一部分元数据） |
| 仓内向量（LLM in SQL） | 与业务表同库 | 向量列与结构化列在同一行，同一次查询内 JOIN 与过滤 | 无第二份 |
| 混合（向量库 + 仓） | 索引在向量库，过滤在仓 | 两段式：先召回、再回仓过滤（或先过滤再召回，取决于选择性） | 元数据两份 |

**由此必然导出的性质（因果句）**：因为**仓内向量把「向量列」与「结构化列」放在同一张表上**，召回与过滤可以在同一个查询计划里联立，先用谓词缩小候选集再算距离；而独立向量库的召回必须把候选集合带回来（或者在库里也维护一份元数据，形成第二份副本）——**这道边界的代价随「过滤条件的选择性」上升**：过滤越严、命中集合越小，跨系统来回搬运的相对开销越大。反过来说，**因为专用向量库是专为 ANN 索引而生的服务**，它在索引调优、量化压缩、分片与高并发查询上的成熟度高于后出现的仓内向量能力（HNSW、IVF、PQ 三类索引算法见主文件 §2.2；HNSW 的原始论文可按「HNSW + Malkov」自行检索核验）。**这不是谁更先进，是「检索是否需要与结构化条件联立」这一个问题。**

**公开证据**【经验】：「哪一类在索引调优上更成熟」没有单一权威来源，因此改用范围与条件表述，并给出可核验的路径。主文件 §2.2 给出向量检索的形式化定义（TopK 最近邻）与 HNSW / IVF / PQ 三类索引算法，§2.3 的「向量 + SQL 融合」列出向量索引、混合查询、向量化 JOIN 与向量聚合四种做法，§2.1 给出仓内向量函数的定义（`ai_embed` / `ai_search`），§2.4 把「LLM in SQL vs 专用向量数据库（Pinecone / Milvus）」列为相邻概念对照——但该处只给「一体化 vs 专注向量」这一定位，不含年份与版本。需要说清的是：**主文件 §1.4 的演进时间线并未覆盖本节这条对比**——全节只收录了「2024-06 阿里云 PolarDB AI Function 发布，含 `ai_generate` / `ai_embed`」这一条仓内向量条目，专用向量库（Pinecone / Milvus）在整份主文件里都只出现在 §2.4 的定性对照中，没有年份。所以两类路线「谁先出现、各自成熟到哪一步」，请按各厂商官方文档与 release note 的当前版本自行核验。判定方法：把最近一个月最频繁的那条检索请求拿出来，数一下它带几个结构化过滤条件——一个都不带，专用向量库是更直接的工具；带两三个且选择性很高，仓内联立的收益就出来了。

**为什么这条机制决定了「检索」是不是一笔额外的账**：检索一旦跨系统，就要维护两条新鲜度链路（业务表一条、索引一条），而「索引里的元数据比业务表旧」这类问题不会报错，只会让召回结果悄悄变差——**它属于那类「只在效果上暴露、不在监控里暴露」的故障**（与 §3.5 陷阱 8「结果不可解释」同源）。仓内向量把两条链路合成一条，代价是接受通用引擎在 ANN 调优上的边界。

**失效条件**：当检索完全是向量驱动、没有结构化条件、并发很高时，仓内一体化的优势消失——把一个点查场景放进通用分析引擎，等于要为它养一整套分析引擎的资源；此时独立向量库的索引与水平扩展更合适。

### 7.4 成本结构对比（不是价格表，是成本函数）

各族的成本函数**形状不同**，这才是选型的核心。写成统一形式：

```
月成本 ≈ 搬运(处理次数 × 数据体积 × 出网单价)
        + 模型调用(进入调用的行数 × 每行 token × 档位单价)
        + 引擎(扫描行数 + 调用行数 × 每行算子开销)
        + 治理重建(产出落点数 × 每处重复建设的成本)
        + 人力(常驻组件数 × 技能稀缺度 + 提示词与模型的维护)
```

**先看哪一项是主导项**：

| 族 | 主导项 | 隐性项 | 处理规模翻 10 倍时 |
| --- | --- | --- | --- |
| 族一（外部 API / 应用编排 / ETL + LLM） | 模型调用 + 搬运 | **治理重建**（权限、血缘、账单各来一遍） | 近似线性，且副本数不变（副本更大而已） |
| 族二（专用向量库） | 索引常驻内存 | **第二份副本的新鲜度维护** | 内存近似线性增长，需要量化或分片 |
| 族三（算子下推） | 模型调用（进算子行数） | **端点限流与失败重试** | 若过滤与增量做到位，**账单不随表规模走** |
| 族四（消费层入口） | 每次提问的翻译与调用 | **翻译错误的排查成本** | 随提问次数走，与数据规模无关 |

**算一笔能复算的账**【推算】。设定：一张 1 亿行的评论表，每行文本约 200 token（按中英混排约 2.5 字节/token 折算 ≈ 500 B/行，故全表体积 ≈ 1 亿 × 500 B = **50 GB**）；本次真正需要新增标注的候选集只占 2%，且其中 90% 已在历史结果表里、可由增量键跳过。

- 全表调用一次：1 亿行 × 200 token = **2×10¹⁰ token**。
- 先筛再调 + 增量跳过：1 亿 × 2% = 200 万行，再乘 10%（增量未命中的部分）= **20 万行**；20 万 × 200 token = **4×10⁷ token**。
- 两者之比：2×10¹⁰ ÷ 4×10⁷ = **500 倍**。

推导链两端都来自上面写明的三个前提（1 亿行、200 token/行、2% × 10%），可以按你自己的数据替换后重算。对照一下：同一代模型换一个便宜档位，单价差异通常在**个位数倍到十倍**区间【经验】。**所以「先筛再调 + 增量」这一个动作的杠杆，比选模型档位大两个数量级**——这也解释了为什么 § 6 的阿里与 Snowflake 两个案例把成本控制写进 SQL 的过滤逻辑，而不是写在模型选择的章节里。

**搬运这一项的量级**：同一条流水线，全量导出一次就是 50 GB 出网；按出网流量计费（**单价请以你所用云厂商当前价目为准**，多数公有云的对象存储出网单价高于同体积的月存储单价【经验】），且每处理一次就要搬一次，重复次数不受控制。LLM in SQL 把这一项变成 0——**不是因为单价便宜，是因为次数为 0。**

**索引常驻是族二最容易被低估的一项**【推算】：1 亿条文本按 1024 维向量、FP16 存储计算，每条 1024 × 2 B = 2 KB，合计 **≈ 200 GB**；这笔内存要常驻、要能支撑查询延迟，其单价远高于对象存储。用乘积量化等手段压缩能把体积降下来，压缩比通常在数倍量级【经验】——但压缩会带来召回率的取舍，这份取舍要在选型时就承认。

**族三有一项特性容易被忽略**：把向量列放进同一张表会让**行宽增加**，不相干的全表扫描会跟着变慢。所以「向量放仓内」不是无代价的，代价是**必须配套列裁剪与分区隔离**（主文件 §2.2 的谓词下推与算子下推）。这一条不改变结论，只改变施工顺序。

**唯一不随规模下降的一项是人力与治理重建**：调用成本、存储、搬运都能靠技术手段压下去（过滤、压缩、下推），但「提示词与模型的维护」「常驻组件数 × 技能稀缺度」只随场景数与组件数增长。这也解释了为什么同一门技术在小团队是「省了事」，在大团队可能变成「多养了一个平台」——**判断方法很简单：把候选方案各自需要常驻维护的组件数列出来，乘以你现有团队里能维护它的人数，看这个乘积是否超过了你雇他们的理由。**

### 7.5 决策树（每个分支都要有阈值依据）

下面的树按**约束**而不是按**产品**分叉：先问「数据能不能动」（硬约束），再问「成本杠杆用上了没有」（可测量），最后才问「要不要叠消费层」。**读法**：树上的每个判断节点，在树后的「阈值依据」里都有一条对应解释，逐条一一对应；任何一条答不上来，就先去做「上树之前的三项验证」，不要靠猜往下一层走。

```
[数据能不能离开当前引擎？]
   │
   ├── 不能（受监管 / 数据主权要求）→ 族三（LLM in SQL）
   │        │
   │        └── [模型能不能用供应商托管的档位？]
   │              ├── 能  → 托管档位 + 按任务分档（离线经济档 / 在线强档）
   │              └── 不能 → BYO-LLM（自建端点）或 Self-Hosted LLM（内网推理）
   │
   └── 能 → [把「进入调用的行数 ÷ 扫描行数」估出来]
            │
            ├── 比值偏高（调用行数没比扫描行数低多少）→ 先做「谓词下推 + 增量键 + 缓存」，再谈选型
            │            （行级调用会随表规模线性上涨）
            ├── 比值已压得很低 → [这批处理是否需要进入正式的数据链路？]
            │            ├── 需要 → 族三：结果落表、纳入血缘与权限
            │            └── 不需要（一次性探索）→ 族一或族二，够用即止
            └── 无论落在哪一边 → [这次处理要不要做语义检索？]
                     ├── 需要，且检索总带结构化过滤 → 仓内向量
                     ├── 需要，且是纯向量点查、高并发 → 专用向量数据库
                     └── 不需要 → 不引入向量层

（以下两问对上述所有分支共用）

[消费方会不会自己写 SQL？]
   ├── 会   → 直接用算子，不叠加翻译层
   └── 不会 → 在算子之上叠 NL2SQL / Data Agent，并硬性附上「答不出就拒答」

[本次处理的总 token 量级是否已进入你的月度预算前几位？]
   ├── 是 → 先把「进入调用的行数」压下来，再考虑换档位
   └── 否 → 不要为成本做架构改动，此时优化的是无足轻重的一项
```

**阈值依据**（树上每个判断节点在此各有一条，逐条对应）：

- **「数据能不能离开当前引擎？」**：依据是 7.3.1 的副本机制。这不是成本问题而是候选集合问题：一旦数据出仓，就多出一份长期存活的副本，权限、生命周期与账单都要在第二个系统里重建。判定方法：问「这份数据出仓后，谁能读、多久销毁、按哪个部门的预算算」——答不上来，就按「不能」处理。
- **「模型能不能用供应商托管的档位？」**：依据是合规边界与模型来源的耦合。BYO-LLM 与 Self-Hosted 的差别不在函数签名（两者在 SQL 层看起来一样），而在**推理发生在谁的机器上**：前者只是把端点换成自建服务，后者才把请求也关在内网。判定方法：看数据出网策略里有没有一条针对模型端点域名的放行规则——有规则，说明请求确实出了边界。
- **「进入调用的行数 ÷ 扫描行数」这条线**：依据是 7.4 的成本函数形状，不取某个绝对规模、也不写死一个百分比。口径是方向的：【经验】判断——比值越接近 1（调用行数没比扫描行数低多少），模型调用项越容易挤进月度预算的前几位，账单开始随表规模而不是随业务量变化，这时正确动作是把过滤与增量逻辑补上，**而不是换一个更便宜的模型**；比值压得越低，函数化直调的简单性越值钱。判定方法：取最近一次作业的「调用行数」与「扫描行数」两个值相除，这两个值在现有监控里就有。
- **「这批处理是否需要进入正式的数据链路？」**：依据是治理延续这条判据。一次性探索的产出没有下游，落点在哪儿都无所谓；一旦要进报表、指标或特征链路，产出就必须落成表并继承权限与血缘，否则「这份标签谁生成的」在下游变成不可答的问题（7.3.3）。判定方法：问「这张表会不会被别的作业 JOIN」——会，就走族三。
- **「这次处理要不要做语义检索？」**：这一问对应三条分支，判据是 7.3.4 的边界代价。这条线的形式是**过滤条件的选择性**，不是数据量：带两三个高选择性条件时，先过滤再算距离能把候选集压掉几个数量级，而跨系统召回会把这个收益在搬运上还回去；纯向量点查、无结构化条件且并发高时，方向相反。**「不需要」也是一条分支**——不引入向量层，本身就是最常见也最容易被越过的正确结论。判定方法：拿最频繁的那条检索请求，数它的结构化过滤条件个数。
- **「消费方会不会自己写 SQL？」**：依据是消费层与执行层的正交关系（7.2 的族四）。NL2SQL 的价值在于把「提问」这一侧的门槛降到零，它**不改善执行侧的任何一项机制**；给会写 SQL 的人叠翻译层，等于凭空多一层可能翻错的环节。判定方法：看过去一个月的查询里，用户自己改写 AI 生成 SQL 的比例——比例高，说明翻译层没解决问题，只是把问题挪了一层。
- **「本次处理的总 token 量级是否进入预算前几位？」**：这一条是**给优化排序**，不是给选型分叉。依据是 7.4 的杠杆排序：单价档位与「进入调用的行数」不在同一个量级上（500 倍 vs 数倍），先在哪个上面用力，结论是确定的。

**上树之前先做的三项验证**（都比选型更重要）：

1. **量一次「调用行数 ÷ 扫描行数」**：这个比值决定你有没有把成本杠杆用上（对应 7.3.2）。
2. **数一次数据出仓后产生的长期副本数**：副本数决定你要维护几套权限与账单（对应 7.3.1）。
3. **问一次「上周那批标签用的是哪个模型版本」**：答不出，说明控制平面在治理域之外（对应 7.3.3）。

这三项里任意一项不满足要求，无论落在树的哪一档，都应该先补齐它，而不是先换工具。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 受监管数据上做文本分类 / 摘要 | LLM in SQL + 托管档位 | Self-Hosted LLM（库内调用） | 外置路线的第一道门就过不去：数据出仓即产生不可控副本 |
| 百万行以上离线批量打标 | LLM in SQL 批处理模式 | ETL + LLM 批处理 | 后者的成本随表规模走，且结果落在仓外，治理要重建 |
| 单条交互式语义处理（低延迟） | 外部 LLM API 或库内小模型档位 | 库内批处理模式 | 批处理是为吞吐设计的，交互场景下只增加排队延迟 |
| 纯向量点查、高并发、无结构化条件 | 专用向量数据库（Pinecone / Milvus） | 仓内向量 | 把点查放进通用分析引擎，要为它养一整套引擎资源 |
| 语义检索总带结构化过滤与 JOIN | 仓内向量（LLM in SQL） | 向量库 + 仓内两段式 | 两段式要把召回集合搬回来，过滤越严越不划算 |
| 业务方自助提问、不写 SQL | LLM in SQL + NL2SQL / Data Agent | 纯 BI 语义层 | 没有执行层算子时，翻译出来的 SQL 仍要人手工落地执行 |
| 内网 / 无外网 / 模型需自主可控 | Self-Hosted LLM（库内调用） | BYO-LLM 指向内网端点 | 端点若在公网，请求仍出了边界，合规链条断在最后一跳 |
| 成本敏感、任务难度分层明显 | BYO-LLM + 按任务分档 + 缓存 | 单一档位 | 单一档位会把简单任务也付成复杂任务的价 |

**常见组合**（共 6 条）：

1. **LLM in SQL + Data Agent**：构成——Data Agent 负责理解意图与编排，LLM in SQL 负责在数据所在处执行语义算子，BI 工具负责展现。职责边界——Agent 只决定「做什么」，不搬运数据；算子只执行，不负责意图理解。运维代价——Agent 侧新增一条失败路径（意图理解错），因此每个结论都要能指回它调用的那次查询。**成熟度限定**：多智能体 / Agent 编排在 §5.1 判为 L3（观望），先建工具目录与权限模型，不要把编排放进取数关键路径。【经验】
2. **LLM in SQL + RAG / 向量库**：构成——向量召回给上下文，SQL 聚合与过滤给事实。职责边界——向量层负责「找到相关的」，SQL 负责「算准的」；两层各自可替换。运维代价——两套存储、两条新鲜度链路，业务表结构变更时向量侧的元数据要同步刷新。【经验】
3. **LLM in SQL + GraphRAG**：构成——图找实体与关系，SQL 查事实与聚合，LLM 负责组织答案。职责边界——图只回答「谁和谁有关系」，不承担数值计算；数值一律回 SQL。运维代价——图与表之间的实体标识必须对齐，否则同一个实体在两处是两个对象。**成熟度限定**：「与 GraphRAG 的结合」在 §5.1 判为 L3（观望），不要把图查询放进取数关键路径。【经验】
4. **LLM in SQL + Self-Hosted LLM**：构成——内网推理引擎提供端点，SQL 层调用；模型权重与请求都不出内网。职责边界——引擎提供算力与批处理，SQL 提供数据与治理。运维代价——自建推理要自己负责容量、限流与版本，端点抖动会直接表现为查询失败，需要按「整条查询重试」设计幂等。【经验】
5. **LLM in SQL + BI 工具**：构成——AI 函数处理文本列，产出的表由 BI 工具直接消费。职责边界——算子产出的是**普通表**，可视化层不需要知道它由 LLM 生成（否则 BI 侧要维护第二套口径）。运维代价——产出口径变化时，看板侧的语义要跟着复核。【经验】
6. **LLM in SQL + 按任务分档 + 缓存**（成本敏感 + 批量处理）：构成——离线用经济档、在线用强档；提示词与输入 hash 做精确缓存，相似输入做语义缓存。职责边界——分档决定质量与成本的取舍，缓存决定重复输入不再付费。运维代价——缓存引入新的失效语义（TTL 与「输入相同但期望不同」的边界要写清楚），分档引入效果差异（同一批数据用两个档位会得到两批口径不一致的标签）。【经验】

> 组合的第一原则是**让每一件做它机制上最擅长的事**：算子在数据在的地方执行，检索在索引在的地方发生，翻译层只服务不会写 SQL 的人。第二原则是**组合数不超过团队的运维带宽**——每多一件，就多一处新鲜度告警、多一个「两套系统对同一个问题给出不同答案」的战场。

### 7.7 选错的代价与迁移成本

**反模式：把「全表调一遍」当成批处理的正常成本** —— 症状：作业直接把整张表丢进 AI 函数，理由是「反正是批处理」。后果：账单随表规模线性上涨，且每轮重跑都把已处理过的行再调一次；当表增长到十倍时，成本也跟着十倍，而此时想去掉的是「重复调用」这件事，而不是换模型（§3.5 陷阱 1 与陷阱 2 是同一根因）。正确的做法：**谓词下推把候选集先压小，再用增量键跳过已处理行**，让成本随「真正需要处理的数据量」增长——这是 § 6 阿里案例里被写成核心组件的做法。

**反模式：提示词留在应用代码里，SQL 只传句子** —— 症状：为了「灵活」，SQL 里只写 `ai_generate_text(:prompt, text)`，prompt 在应用侧拼装。后果：同一批数据在不同时间由不同版本提示词生成，口径变化无法归因，而产出已经进了报表（§3.5 陷阱 9）。正确的做法：**提示词随 SQL 版本化，并让模型版本进入产出表的元数据**——变更频率低时这套投入不明显，但一旦要回答「为什么这批标签和上批不一样」，它是唯一的依据。

**反模式：把 LLM 产出的标签落在仓外** —— 症状：结果先写到应用侧数据库或对象存储，「以后再回灌」。后果：产出脱离血缘与权限体系，下游无法判断这张标签表能不能用、由谁负责；等到要回灌时，两边的口径已经分叉，还多出一份要清理的副本。正确的做法：**结果直接落成普通表**，让既有权限、血缘与质量规则自动生效（§ 6 Snowflake 案例把「结果落表与治理延续」列为第 5 条核心组件；Databricks 案例并未把它单列为组件，落表只写在组件 1 的 SQL 示意与「失败教训」段落里——落表这件事在案例中的**排序位置**，本身就说明它是不是被当成一等设计）。

**反模式：为压延迟把逐行调用拆成大量并发小查询** —— 症状：一次查询里对每行发起独立调用，靠并发数硬顶。后果：每行都要付一次固定开销，成本高于批处理而不自知；同时把引擎的并发额度占满，影响同库的其他查询（§3.5 陷阱 5「忽视缓存」与陷阱 10「忽视延迟 SLA」的叠加）。正确的做法：先合并成批、再靠缓存吃重复输入；如果延迟仍不达标，换更小的档位或把结果预物化，而不是继续加并发。

| 迁移方向 | 数据处理侧改动 | 查询与接口改写 | 治理重建 | 团队再学习 | 量级（【经验】） |
| --- | --- | --- | --- | --- | --- |
| 外部 API / ETL + LLM → LLM in SQL | 调用从应用侧挪进 SQL，过滤与增量逻辑补上 | 作业改写成 SQL，提示词随 SQL 版本化 | 产出从仓外搬回仓内，权限与血缘重新挂上 | 中（要懂算子代价与批处理） | 月级 |
| 外部 API → Self-Hosted / BYO-LLM | 端点替换，函数签名不变 | 基本不改 | 需为自建端点补容量、限流与审计 | 中到高（要运维推理服务） | 月级 |
| 专用向量库 → 仓内向量 | 向量列写入业务表，索引重建 | 召回与过滤合并成一条 SQL | 消除第二份副本，元数据新鲜度问题消失 | 中（要懂向量索引在引擎侧的调优边界） | 月级 |
| 仓内向量 → 专用向量库 | 向量与元数据导出到独立服务 | 召回从一条 SQL 拆成两段式 | 新增一份副本及其刷新链路 | 中 | 月级 |
| 仓外产出 → 仓内产出 | 落点改为仓内表 | 下游改为直连该表 | 权限、血缘、质量规则重新生效 | 低到中 | 周级 |
| 单一档位 → 按任务分档 + 缓存 | 增加分档判断与缓存键设计 | 调用参数按任务类型区分 | 需记录每次产出用的档位，否则口径不可比 | 中 | 周级到月级 |

> 注意「专用向量库 → 仓内向量」这一行与直觉相反：它看起来是「往分析引擎里塞一个新负载」，实际的迁移动作是**消掉一份副本与一条刷新链路**，代价是接受通用引擎在 ANN 调优上的边界。**这类迁移的主要工作量从来不在搬数据，而在重新划定「谁是权威源」与「哪一层负责新鲜度」。**

### 7.8 小结

LLM in SQL 的选型特殊性在于：**它选的是「算子放在哪一侧」，而不是「哪个产品更好用」**。所有候选的差异都可以收到一条上——算子和数据在不在同一个执行域里。算子外置（族一、族二）换来最丰富的模型与生态，代价是一份出仓副本、两套账与两条需要同步的新鲜度链路；算子下推（族三）换来零搬运与治理延续，代价是把外部依赖搬进了查询的关键路径；消费层（族四）与前两者正交，它只决定问题怎么提出来。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 受监管 / 数据不许出仓 | LLM in SQL（+ 托管档位或 Self-Hosted） | 算子在引擎内，数据不跨边界，副本数保持为 0 |
| 百万行以上离线批处理 | LLM in SQL 批处理模式 + 谓词下推 + 增量键 | 成本随「进入调用的行数」而非表规模增长，杠杆差可达两个数量级 |
| 单条交互式处理、延迟敏感 | 外部 API 或库内小档位 | 批处理的收益来自合并，交互场景里没有可合并的空间 |
| 纯向量点查、高并发 | 专用向量数据库 | 为 ANN 而生，索引调优与水平扩展更直接 |
| 语义检索总带结构化过滤 | 仓内向量 | 召回与过滤同计划联立，不必把 ID 集合搬回来 |
| 业务方自助提问 | LLM in SQL + NL2SQL / Data Agent | 翻译层服务不写 SQL 的人，不改善执行侧机制 |
| 模型必须内网自持 | Self-Hosted LLM（库内调用） | 请求与数据都不出边界；BYO-LLM 若端点在外，合规链断在最后一跳 |
| 成本敏感、任务难度分层 | BYO-LLM + 按任务分档 + 缓存 | 档位差异是数倍量级，先筛再调是百倍量级，优化顺序由此确定 |

> 本节小结：本章所有候选之间，**唯一真正起决定作用的差异是「算子被放在数据所在的执行域内，还是数据被搬到算子所在的那一侧」**——它同时决定了一票否决的合规边界、成本函数里有没有「搬运」与「第二份副本」两项、以及产出能不能自动继承血缘与权限。其余维度（模型丰富度、索引调优手段、工具成熟度）都是在确定了这件事之后才需要精算的第二层问题；先定算子位置，再谈其他。
>
> 💡 **思考锚点**：拿你最大的一张 AI 处理表算一次——谓词下推能把候选集压到原表的几分之几？按 §7.4 的成本函数，账单随「进入调用的行数」而非表规模走，下推与增量键的杠杆按 §7.8 可达两个数量级；你的表若在百万行以上，你此刻是按「进入调用的行数」付费，还是仍在按表规模付费？
