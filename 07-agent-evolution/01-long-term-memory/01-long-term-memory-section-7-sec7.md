## 7. 与其他方法对比

> 本节把主文件 §0 速读地图里「我的业务该选哪种记忆方案」那一行兑现成一条可执行的路径。长期记忆的候选之间没有绝对优劣，它们的差异集中在四条机制上：**冲突在哪条路径上收敛**、**上下文预算怎么分配**、**记忆落成什么物理形态**、**隔离与删除落在哪一层**。本节对每条机制都写成「因为 A，所以在 B 条件下必然优于 C，代价是 D」，并逐条标出证据档位。

### 7.1 先立判据：为什么打分表会误导

打分表最危险的地方不是分数不准，而是它把**场景相关的结论伪装成绝对结论**。假设给「记忆质量」这一维打分：提取式记忆（§3.2.4）与纯追加的向量检索（§3.2.2）谁该得高分？在「用户偏好会变、且要回答当前值」的场景里，写路径做比对与更新的提取式必然赢；在「只求原话、不要抽取失真」的场景里，排序完全反过来——抽取每多一步，就多一次把假设写成事实的机会（§3.2.4 的失效点）。分数的差别不来自实现质量，来自你的约束。同样，同一维度在不同规模下**权重相反**：写入成本在每天几百轮对话的量级下可以忽略，在亿级条目 + 十万级用户的量级下是主导项；而「可复盘性」在小团队里是奢侈品，在受监管行业里是准入门槛（§6 的四个案例把这一条演示了四遍）。

第二条更隐蔽：**候选根本不在同一层**。本章实际出现过三类东西——**形态**（Session Memory、提取式、分页式、知识图谱记忆、情景记忆、混合模式）、**框架**（Mem0、Letta、Zep、MemoryBank、Cognee 与各家 Agent 框架的 Memory 模块）、**底座**（向量库、图库、关系库与事件表、缓存）。把它们放进一张表，读者会误以为它们在同一维度上可比，而真实关系是依赖顺序：**形态决定要不要写路径，框架是形态的一种实现，底座是框架的落点**。换底座救不回选错的形态，换框架也救不回选错的形态——这是本章最省时间的一条判断。

第三条是**阈值没有来处**。读者真正要回答的是「我什么时候该从向量追加换成提取式」「什么时候该上独立向量库」，而这类问题在打分表里被压成一个名次，既看不到交点在哪，也看不到交点凭什么这么定。本节的决策树（7.5）里每个判断节点都在树后给出依据与**在你自己的环境里重算这个阈值的方法**。

所以本节的比较方式是：先固定几条与场景无关的判据，再让每个候选在判据上给出机制层面的解释，最后把选择落到可观测的信号上。判据本身不排序——排序由你的约束决定。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 写入通道由谁决定 | 什么被写进去：用户显式声明 / 模型抽取 / 行为推断 | 它决定记忆准确率的**上限**：抽取式记忆的错误率就是抽取器的错误率，这条上限无法靠读路径优化补回来（§5.2.1） |
| 事实的时效性 | 有没有「当前值」这个概念，同一主谓能否并存多条有效记录 | 决定冲突是在写路径收敛还是留给读路径猜，进而决定「同一个问题今天答 A、明天答 B」会不会发生（§3.5「记忆冲突」） |
| 记忆跨越的边界 | 会话内 / 会话之间 / 事件之间 | 边界一确定，存储形态基本被锁死：会话内只需要 KV + TTL，跨会话必须做抽取或建关系，跨事件必须留过程（§3.8 的同一条） |
| 上下文预算与召回形态 | 记忆怎么进上下文：固定截断 / 顶 k 相似度 / 模型自主换页 | 上下文预算是零和的——调进来的每一条都在挤掉别的；分配方式决定「记得多」能不能变成「表现好」（§5.2.2） |
| 成本随什么增长 | 条目数 × 用户数 / 原文体积 / 每轮一次抽取调用 / 常驻组件 | 唯一能提前算清的判据：它决定哪个候选在哪个规模上净胜，也决定「加钱能不能解决」（7.4） |
| 隔离与删除的落点 | 作用域是否写进分片键；删一个用户要动几处存储 | 唯一会造成**不可逆后果**的判据：其余问题都能靠治理慢慢修，而跨租户泄露一旦发生就已经发生（§3.5） |

这六条不并列：**写入通道与时效性**是硬边界（错了加钱解决不了），**边界与预算**决定形态与召回方式，**成本**决定规模切换点，**隔离与删除**排在最后不是因为最不重要，而是因为它必须在建之前定——它要写进存储布局，事后补要重做分片键与索引（§3.6「单用户单 Agent → 多租户多 Agent」一行给的就是这笔账）。

用这张表的正确方式不是逐条打分求和，而是：**先用「记忆跨越的边界」砍掉一半**（只活过一次会话的根本进不了后面几条），**再用「写入通道 + 时效性」二分**（要不要写路径、要不要当前值），剩下的候选才轮到成本与隔离来排序。框架与底座放到最后选，因为它们的可替换性高于形态。

### 7.2 候选方案全景

第一层是**形态级候选**——它决定记忆落在哪、能不能回答某类问题：

| 形态 | 定位 | 核心机制（一句话） | 典型使用者 | 代表实现 |
| --- | --- | --- | --- | --- |
| Session Memory | 会话内的一致性 | 键为 `session_id` 的消息序列 + TTL，读写退化为点查与追加 | 所有 Agent 产品的默认层 | Redis 一类缓存 / sessions 表 |
| Vector RAG 记忆 | 用原文承载跨会话记忆 | 对话切块 → 向量检索顶 k → 注入；写入是纯追加 | 演示期与轻量场景 | pgvector / Milvus / Qdrant |
| 提取式记忆 | 跨会话的稳定事实 | 抽取事实 → 与已有记忆比对 → ADD / UPDATE / DELETE，写路径收敛当前值 | 个性化、客服 | Mem0、Zep |
| 分页式记忆 | 上下文装不下时的调度 | 把窗口当物理内存、外部存储当虚拟内存，由模型用函数调用换页 | 长任务、长对话 | Letta（前身 MemGPT） |
| 压缩式记忆 | 成本敏感的长历史 | 以遗忘曲线为蓝本做衰减与摘要压缩，换取体积与 token | 成本敏感、不要求精确回忆 | MemoryBank 路线 |
| 知识图谱记忆 | 多跳关系 | 实体 + 关系 + 时间显式建模，可沿边遍历 | 推荐、风控、多 Agent 协作 | Cognee、Neo4j 一类 |
| 情景记忆（Episodic） | 复盘与举证 | 事件级落库，保留当时的召回候选与工具参数 | 受监管行业、有事故复盘要求 | Langfuse / Helicone 一类 |
| 混合模式 | 四项都要 | 同一批输入在写路径分发到多形态，读路径按作用域路由并融合打分 | 生产态平台 | 阿里三层、字节三形态（§6） |

第二层是**框架级候选**——同一个形态下，换框架换的是「哪条约束被做成一等公民」：

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Mem0 | 提取式记忆的开源实现 | 把写路径定义为抽取 + 比对 + ADD / UPDATE / DELETE | 个性化类应用 | 开源项目 + 托管服务 |
| Letta（前身 MemGPT） | 分页式记忆的工程化平台 | Core / Archival 分层 + 模型自主换页 | 长任务 Agent | 开源项目 + 商业平台（2024 年公司化【公开】，可按「Letta MemGPT」检索核验） |
| Zep | 时序事实 | 把时间做成事实的一等属性并叠加衰减 | 跨会话连续性要求高的产品 | 开源 + 商业服务 |
| MemoryBank | 压缩式记忆的研究路线 | 用遗忘曲线控制保留与压缩 | 研究与实践参照 | 论文路线，非采购项 |
| Cognee | 图谱 + 向量混合 | 事实抽取与关系推理做在同一条读路径上 | 需要多跳的场景 | 开源项目 |
| LangChain Memory / LangGraph Checkpoint | Agent 框架自带的记忆模块 | 状态快照与流程状态可恢复、可重放 | 流程编排为主的团队 | 开源框架 |
| AutoGen Memory | 多 Agent 框架的记忆模块 | 会话与群组状态在 Agent 间的传递 | 多 Agent 实验与原型 | 开源框架 |
| Self-Edit Memory（A-Mem 一路） | 写路径的第二段 | 让模型回过头复检并修正已写入的条目 | 长期自进化研究 | 论文路线（A-Mem，2025），非采购项 |
| 平台内建记忆 | 产品自带能力 | 跨会话记忆 + 用户可查看 / 编辑 / 删除 | 直接使用平台的团队 | 随产品提供（OpenAI 与 Anthropic 均于 2025 年公开此类能力【公开】；核验看有没有可编程写入与按条目删除接口） |
| 自研记忆层 | 记忆成为独立服务 | Memory API（读 / 写 / 检索 / 遗忘）+ 多形态存储 | 平台团队 | 自建（§4.3） |

第三层是**底座与周边件**——它们决定容量、延迟、召回质量与可观测性：

| 组件位 | 候选 | 它决定什么 | 许可 / 商业模式 |
| --- | --- | --- | --- |
| 向量检索 | pgvector / Milvus / Qdrant / Weaviate / Pinecone | 相似度召回的规模上限与索引内存 | pgvector 随 PostgreSQL；其余开源或托管 |
| 关系与事件存储 | PostgreSQL / ClickHouse | 「当前值」的唯一约束、事件表的体积与扫描 | 开源，自运维或托管 |
| 图存储 | Neo4j / NebulaGraph / Apache Jena / Oxigraph | 多跳遍历的代价与 schema 演进 | 商业 + 开源并存 |
| 缓存 / 会话 | Redis / DragonflyDB / Memcached | TTL 语义与热路径延迟 | 开源，自运维或托管 |
| 嵌入 / 重排 | BGE-M3 / text-embedding-3-large / Cohere embed-v3；重排 Cohere Rerank / BGE Reranker | 召回质量，以及「换模型要重算全量向量」这一次性成本 | API 或开源权重 |
| 评估与可观测 | Langfuse / Helicone / Arize Phoenix / Mem0 Evals | 能否把「召回对不对」变成可回归的指标（评估集 + 分数 + 版本对比） | 开源 + 托管 |
| 冷数据 | 对象存储 + 离线索引 | 归档事件与历史对话的成本 | 按量计费 |

这三层的关系是**依赖顺序而不是并列清单**：形态选错，换框架救不回来（同一个提取式形态下，Mem0 换 Zep 的差别主要在时间维度这一项）；框架选错，换底座更救不回来。再往上归一次「族」，同族内部差异小、跨族差异大：**会话族**（Session Memory）只解决一次会话；**追加族**（Vector RAG 记忆、压缩式记忆）写入廉价、不做冲突解决；**收敛族**（提取式、知识图谱记忆）在写路径上建当前值与实体同一性；**过程族**（情景记忆）只追加、不修改。跨族比较要问的是「我能不能换族」，族内比较才轮到「选哪一个」——绝大多数选型事故不是选错了族内的那一个，而是选了不属于自己约束的族（7.7 的第一条反模式）。

### 7.3 机制差异：为什么它们表现不同（核心节）

这四个机制有依赖顺序：**7.3.1 决定一致性**，是最上游的一条；**7.3.2 决定「记得多」能不能变成「表现好」**；**7.3.3 决定哪些问题根本问不出来**；**7.3.4 决定这套系统能不能被合规地运营下去**。前两条在「花多少、准不准」，第三条在「能不能」，第四条在「敢不敢上线」。

#### 7.3.1 冲突在哪条路径上收敛

**机制是什么**：同一件事出现两个说法时，**在哪一刻、由谁**决定以哪个为准——是写入时收敛，还是留给检索时去猜。

| 收敛位置 | 代表 | 同一主谓能并存几条 | 读路径要做什么 |
| --- | --- | --- | --- |
| 不收敛（纯追加） | Vector RAG 记忆、压缩式记忆 | 多条 | 由模型临场分辨新旧；而更旧的那条并不因为更旧就排在后面 |
| 写路径收敛 | 提取式（带有效时间）、Zep 时序事实 | 一条当前值 | 直接取当前值，不需要判断 |
| 写路径收敛 + 实体同一性 | 知识图谱记忆 | 同一实体只保留一个节点（实体消解），关系显式建模 | 先解析实体，再沿边遍历 |
| 不对冲突负责 | 情景记忆 | 不适用（事件只追加） | 需要另一个形态回答「当前值」 |

**由此必然导出的性质**：因为冲突在写路径收敛，所以读路径拿到的是唯一当前值、同一个问题在不同轮次会得到同一个答案；**代价是准确性被整体压在抽取器身上**——错的事实一旦落库，就获得与用户亲述同等的权重，而读路径不区分二者（§5.2.1 把这句话浓缩为「写路径是故障发生地，读路径是故障暴露地」）。反过来，因为纯追加路线不设收敛点，所以它的写入永不失败、也永不阻塞，**代价是新旧值会被同时召回**，表现为「短期内体感记得挺多，几周后开始自相矛盾，而排查时每条记录单看都是对的」（§3.3 的同一段判断）。

**公开证据**：【公开】写路径的收敛动作有公开定义——Mem0 把写操作定义为抽取 + 比对 + ADD / UPDATE / DELETE（开源项目与其论文，arXiv 2504.19413，2025 年 4 月提交；项目本身 2024 年即开源，两者时间口径不同）；Zep 走「时序事实 + 时间衰减」路线，把时间做成事实的一等属性（Zep 团队的时序知识图谱论文与官方文档，2025）。这两条均可按题名与 arXiv 编号（前四位即提交年月）自行检索核验。「同一主谓是否只保留一条当前值」的判定方法不看功能页，而是看 schema 里有没有那条唯一约束——本章 §3.2.4 给的示例正是这样一个带 `WHERE valid_to IS NULL` 的唯一索引。

**失效条件**：当被记住的事实**本身不随时间变化**（合同条款、产品目录、术语表），或写入量极大而读取只按时间倒序时，写路径的比对是纯成本——此时纯追加路线更快、更便宜，且没有抽取失真这一层风险。另一个失效条件在抽取器身上：当用户的语言习惯里充满反事实与假设（「如果我下周出差，帮我订靠窗的座位」），抽取器会把假设写成事实，而写路径没有任何机制能识别——此时要补的不是更聪明的抽取，而是把 `source` 分成 `user_msg` / `inferred` / `external` 并让读路径按来源降权（§5.2.1）。

#### 7.3.2 上下文预算怎么分配

**机制是什么**：记忆总量几乎总是大于上下文窗口，所以每条记忆进入提示词的方式必须被决定——按位置截断、按相似度取顶 k、还是由模型自主调度。

| 分配方式 | 代表 | 依据 | 漏召时的表现 |
| --- | --- | --- | --- |
| 固定截断 | Session Memory、摘要压缩 | 最近 N 轮 / 保留摘要 | 确定性地丢掉早期信息（摘要不可逆） |
| 顶 k 相似度 | Vector RAG 记忆、提取式记忆 | 向量相似度（+ 时间 / 重要性 / 置信度加权） | 关键记忆被相似但不相关的内容挤出 |
| 多路召回 + 重排 | 混合模式 | 相似度 + 时间 + 重要性 + 置信度 + 访问频次 | 融合权重失配，噪声与漏召同向恶化 |
| 模型自主换页 | MemGPT 分页 / Letta | 模型按当前任务判断换入换出 | **表现与「没有记忆」完全一样，且不可观测** |

**由此必然导出的性质**：因为进入上下文的内容从「按位置截断」变成「按需调度」，所以同一个窗口预算能覆盖更长的历史；**代价是每一轮都要多一次判断的 token 与延迟，而调度错误比检索错误更贵**——该调进来的没调进来时，日志里看不出是一次漏召还是一条本就不该存在的记忆，用户只会觉得 Agent 又忘了（§5.2.2）。第二条推论与规模无关：因为上下文预算是零和的，所以把顶 k 调大能改善漏召、同时恶化噪声，**只测一头的调参会把问题推到另一边**——这就是「必须同时测漏召与噪声」的机制原因，也是 §5.2.2 给出那条自验方法（一个「必须用到三个月前某条记忆」的问题 + 一个「与历史无关」的问题）的理由。

**公开证据**：【公开】把上下文窗口类比操作系统物理内存、由模型通过函数调用换页的公开方法（MemGPT，arXiv 2312.08194；arXiv 编号前四位即提交年月，本节的月口径取该编号对应的 2023-12，请以 arXiv 页面上当前显示的提交与修订年月为准；该路线的工程化平台 Letta 于 2024 年公司化）；【公开】向量检索在按相似度取顶 k 时的行为由各向量库的索引文档定义（pgvector 2021 年开源、其 0.5.0 版本于 2023 年引入 HNSW 索引，Milvus 2019 年开源，Qdrant 2021 年开源）。检索路由与「记忆增强生成」的生产效果没有可核验的公开来源，本条只主张机制、不主张效果。

**失效条件**：当上下文窗口本身大到能容纳全部记忆时，调度的收益下降而成本照付——每轮多一次判断、多一轮延迟。此时正确的做法是退回「全量注入 + 去重排序」，把预算花在提高召回精度上。判据是你的记忆总量是否真的超过了窗口能容纳的量，而不是模型宣传的窗口有多大。另有一条容易混淆的边界：**上下文缓存（prompt cache）优化的是同一段前缀的重复计算成本，不承担业务连续性**——把记忆做成缓存命中率优化，会在缓存失效时表现为整体失忆（§2.4 与 §5.2.2 同此口径）。

#### 7.3.3 记忆的物理形态决定它能回答哪类问题

**机制是什么**：记忆条目被存成什么形状，直接决定了哪些问题可以被检索回答、哪些问题在物理上无从回答。

| 物理形态 | 能回答的问题 | 回答不了的问题 | 代表 |
| --- | --- | --- | --- |
| 原文块（不加结构） | 「上次关于 X 说了什么」 | 「这个偏好的当前值是什么、什么时候改的」 | Vector RAG 记忆 |
| 结构化事实条目 | 「当前值是什么、来自哪次对话、置信度多少」 | 「上一次为什么答错」——过程不在条目里 | 提取式记忆 |
| 事件（含中间状态） | 「当时系统看到了什么、在哪一步分叉」 | 「这条偏好的当前值」——需要另做聚合 | 情景记忆 |
| 实体 + 边 | 「和谁有关、几跳之内」 | 「原话怎么说的」——边上只有属性 | 知识图谱记忆 |

**由此必然导出的性质**：因为关系被显式建模，所以「和我同项目的人最近在问什么」可以沿边遍历得到，而相似度只能给出「意思相近」而不是「有关系」；**代价是每条记忆落库前先要做实体链接**，而这一步做不好时，图会「看起来连通、实际断裂」——同一实体被拆成多个节点，多跳查询根本走不通，且这种错误不报错，只让召回结果变少，团队往往误以为是「数据不够」（§3.2.5）。同理，因为事实条目丢掉了过程，所以**一旦需要复盘，就必须另建事件表**；而事件表按发生顺序完整落库的代价是它通常成为记忆体系里最大的一张表，PII 密度也最高（§3.2.6）。

**公开证据**：【公开】属性图与其查询语言的公开实现与文档（Neo4j 1.0 于 2010 年发布，NebulaGraph 2019 年开源，TigerGraph 平台 2017 年发布）；【公开】图谱 + 向量混合检索的公开项目（Cognee 官方文档与论文，2024–2025）；【公开】事件级追踪作为可观测载体（Langfuse 与 Helicone 均于 2023 年开源）。以上三条均可按「产品名 + 发布年份」或题名检索核验，具体能力与版本以各项目官方文档当前版本为准。

**失效条件**：当查询里从来没有出现两跳以上的关系时，图谱部分是额外的工程与写入成本——「用不上多跳时，图谱只是更贵的表」（§4.3 的同一条判据）。当保留期被压缩、或事件的 `context` 字段被省略时，情景记忆退化成「只留下结果、无法定位分叉」，而输入输出相同的事件可能对应完全不同的中间状态，事后无法区分「检索召回了错的证据」与「生成时忽略了对的证据」。

#### 7.3.4 隔离与删除落在哪一层

**机制是什么**：记忆通常同时落在缓存、向量库、关系库、图库与日志里，于是「写」是一次异步、可重试、可补写的动作，而「删」必须一次性覆盖全部副本。隔离与删除的落点决定了它们能不能被事后补上。

| 落点 | 由什么决定 | 事后能不能补 |
| --- | --- | --- |
| 隔离：存储分片键 | 建库时的分区键（user / org / agent） | 不能优雅补：要重做分片键与索引，历史数据重分布（§3.6） |
| 隔离：查询改写器 | 检索入口是否统一 | 能补，但每漏一处就跨租户一次，且不会有异常 |
| 删除：主表条目 | 一张表 | 能补 |
| 删除：向量索引与倒排索引 | 写入时是否登记了条目与索引的对应关系 | 能补，前提是能枚举出「这条记忆被索引在哪几处」 |
| 删除：派生摘要 / 图谱边 | 抽取与实体链接是否留了来源 | 最难：派生件没留来源时，只能按用户整体重建 |

**由此必然导出的性质**：因为删除必须一次覆盖全部副本，**所以记忆系统的删除成本 ≈ 需要覆盖的存储处数 × 一次编排**，它不随规模增长、只随架构复杂度增长——这是本节唯一一条「与数据量无关、只与件数有关」的成本项，也是混合模式最容易被低估的代价（§3.2.7）。第二条推论：因为隔离写在存储布局里才能不依赖每个查询的自觉，**所以「先做单用户、隔离以后再加」是一条做不到的路线**——隔离的落点是分片键 + 查询改写器，而不是「每个查询记得加 WHERE」（§3.5「记忆泄露」）。第三条：**自动遗忘不能替代删除接口**。自动遗忘由重要性 × 衰减低于阈值触发，判据是模型判断、允许出错；合规删除由用户或监管触发，判据不依赖任何模型判断。两者合并的后果是：阈值一旦调错，会连带删掉本应受合规保护的记忆，而这笔删除无法举证「是模型判的」——举证责任在你（§5.2.3）。

**公开证据**：【公开】缓存与会话键的过期语义有公开文档（Redis 于 2009 年首次发布，自早期版本即提供键过期语义与 TTL 相关命令，可按「Redis EXPIRE」检索核验）；【公开】各向量库与图库的过滤 / 分区能力写在其官方文档里——但它们提供的是**容器**，不提供「哪些实体是同一个」「跨存储怎么删干净」这两条规则（§5.5「记忆即服务即插即用」的同一条）。跨存储删除编排没有标准件，判定方法是把自己的存储清单列一遍，问「删一个用户要动几处」——答不出来的那几处，就是将来合规审计会问到的地方。

**失效条件**：当记忆只存在一处（单表单库的 Session Memory）、且没有合规删除义务时，本节列出的全部代价都不存在——这也是为什么最小起步形态应该尽量让记忆只落一处。反过来，一旦为了能力先把四种形态都建起来、再补隔离与删除，返工的不是应用层代码，而是存储布局本身（§3.4 末段的同一条结论）。

### 7.4 成本结构对比（不是价格表，是成本函数）

把上面四条机制写成式子，记忆系统的成本函数大致是：

```
成本 ≈ 抽取调用成本   （随“轮数 × 用户数”增长，与条目数无关）
     + 存储成本       （随“条目数 × 用户数”增长；原文路线另有“轮数 × 用户数 × 保留期”一项）
     + 检索成本       （随“条目数 × 召回路数 × 查询次数 × 重排是否开启”增长）
     + 常驻组件与人力 （向量库 / 图库 / 抽取管道 / 评估与监控的固定项）
     + 删除与导出编排 （随“该用户记忆散布的存储处数”增长，低频但不可省）
```

各候选的**主导项**与**隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| Session Memory | 缓存内存与 TTL 期内的键数 | 缓存与持久化的一致性约定；会话内是 PII 高密度区，保留期必须显式 |
| Vector RAG 记忆 | 原文体积 + 向量索引内存（随条目数） | 冲突让检索精度随使用时长下降；按条目删除要重建集合 |
| 提取式记忆 | 每轮一次抽取调用（随轮数 × 用户数） | 抽取质量监控与冲突规则的长期调参；原文若另存，体积回到原文路线 |
| 分页式记忆 | 每轮多一次换页判断的 token 与延迟 | 调度错误不可观测，表现与「没有记忆」相同 |
| 知识图谱记忆 | 每条记忆落库前的实体链接 | 实体消解质量与 schema 迁移；多跳路径数膨胀需要限跳与剪枝 |
| 情景记忆 | 事件表体积（随事件量线性） | 通常是记忆体系里最大的表，且 PII 密度最高 |
| 混合模式 | 上述各项之和 | 一致性没有单一真值（事实条目与事件表可能给出两个口径）；写放大；删除要跨存储编排 |
| 平台内建记忆 | 平台侧固定成本 | 可编程性受限：只有「开启 / 关闭」「清除全部」的产品，不构成可依赖的存储接口 |

【推算：存储成本的量级，口径与 §5.2.3 一致】前提【经验】：一个用户每天产生 20 条候选事实、每条事实文本约 100 token；中文 UTF-8 下一个 token 约 2–3 字节，本账按下限 2 字节。事实条目路线：文本 20 × 100 × 2 B = 4 KB/天；向量按 1024 维 float32 计，每条 1024 × 4 B = 4 KB，20 条 = 80 KB/天；合计 ≈ 84 KB/天 ≈ **30 MB/用户/年**（84 KB × 365 ≈ 30,660 KB，与 §5.2.3 只算向量得出的 29 MB 同量级，差额即上面那 4 KB/天的文本）。原文路线（同一批人）：按每天 40 轮、每轮用户 + 助手合计 800 token 计 = 32,000 token/天，文本 ≈ 64 KB/天；若再按 300 token/块切块并逐块建向量，则约 107 块/天 × 4 KB ≈ 428 KB/天；合计 ≈ 492 KB/天 ≈ **180 MB/用户/年**。**10 万活跃用户 ⇒ 事实条目约 3 TB、原文 + 分块向量约 18 TB**。这条推算的结论有三层：① 记忆存储不是零成本项，它随用户数线性增长，这才是保留策略存在的理由；② 两条路线的比值约 **6 倍**，且**比值由向量化的粒度决定**——切得越细、向量份数越多，比值越大，§6 案例里「体积低 1~2 个数量级」取的正是更细的切块口径，与本节的差别是口径而不是矛盾；③ 真正把量级拉开的不是形态，而是**保留期**，因为原文项随保留期线性增长，而事实项基本不随。

【推算：抽取调用的量级，与存储成本是两条独立曲线】前提：一轮对话（用户 + 助手）按 800 token【经验】；一次抽取调用的输入 = 本轮对话 800 token + 提示模板与已有相关记忆约 1,200 token = 2,000 token，输出约 300 token，单次合计 **2,300 token**【经验】。相对本轮对话本身（800 token）放大约 **2.9 倍**。按 10 万用户、每人每天 40 轮计 = 400 万轮/天 ⇒ 400 万 × 2,300 = **92 亿 token/天**；折算成「每百万 token 单价 P」的形式即 **约 9,200 × P/天**（本节不写具体单价，因为报价按月变化，请以所用模型厂商定价页当前版本为准）。纯追加路线在同一批对话上只需要每轮一次向量化，没有第二次模型调用。这条推算的结论是**反直觉的那一条**：「记忆条目少所以成本低」不成立——抽取成本由**会话量**决定，与条目数无关；因此一个把抽取粒度做得很细（一问答一事实）的系统，存储成本下降而抽取成本不变。

**这张成本函数里最容易算错的一项是混合模式：它的成本是各项之和，不是各项的最大值。** 会话、事实、图谱、情景四套存储各自有保留期、隔离与删除义务，于是同一个用户的一次删除请求要动四处；读路径的四路召回还要各自归一化打分并融合，重排一旦开启就再多一跳延迟。所以「多加一种形态」的边际成本不是那一套存储的单价，而是**删除项与人力项各加一份**——这两项都不随数据量增长、只随件数增长，加预算买不回来。

**在哪一项花力气：读三个数就够了**。① **每用户每年的条目数**与**原文保留期**（决定存储项，见上面第一条推算）；② **每轮是否发生抽取调用、以及抽取调用的输入长度**（决定包含记忆上下文的提示模板是否在无谓地放大输入——这是最容易改的一项，因为它不改变准确性只改变成本）；③ **一个删除请求覆盖到的存储处数**（决定编排项，也决定合规风险）。这三项都不需要新埋点：条目数从记忆表就能数出来，抽取调用量从模型用量账单就能读出来，存储处数自己列一遍就有了。

**这份成本函数还有一个用法：判断「加钱能不能解决问题」**。五项里，存储项与检索项是可以用钱买到的（换更大的向量库、加索引内存、加副本）；而抽取项、人力项与编排项买不到——抽取项随**会话量**增长，人力项随**常驻组件数**增长，编排项随**存储处数**增长。所以当账单里抽取项或编排项开始占主导时，正确的动作是改架构或改写入策略，而不是加预算。

### 7.5 决策树（每个分支都要有阈值依据）

用这棵树的方式是**从上往下依次问，第一个命中你的分支就是你的位置**。T1、T2 是形态的分水岭（要不要长期记忆、要不要写路径），答完基本锁定族；**T3–T8 与 T1、T2 的答案正交**——关系、复盘、预算、合规、共享、规模都不由「事实会不会变」决定，所以两支在 T2 之后合流，逐项独立作答，任一项的结论不阻断后两项。树上每个带编号的节点，都在树后的「阈值依据」里有且仅有一条对应解释，并给出**在你自己的环境里重算这个阈值的方法**。

```
T1 这份记忆需要在会话结束后被复用吗？
├── 不需要 → Session Memory（键为 session_id 的 KV + TTL）；不要再往上加任何长期件
└── 需要 → 继续 T2

    T2 被记住的事实会变，且需要回答「现在的值是什么」吗？
    ├── 会   → 提取式：冲突在写路径收敛，条目带 valid_from / valid_to
    └── 不会 → 原文追加即可（Vector RAG 记忆），但必须监控「新旧值并存」这一症状（7.3.1）
        ※ 两支在此合流。T3–T8 与 T1 / T2 的答案正交，逐项独立作答。

        T3 查询里是否真的出现两跳以上的关系？
        ├── 是 → 在提取式之上补知识图谱记忆；实体链接必须先于事实写入
        └── 否 → 不补图谱：用不上多跳时，图谱只是更贵的表

        T4 有没有「复盘失败决策 / 对外举证」的要求？
        ├── 有 → 追加情景记忆表，且必须保留当时的中间状态（召回候选、工具参数、模型版本）
        └── 没有 → 不建事件表：它通常是记忆体系里最大的一张表，PII 密度也最高

        T5 不加调度时的记忆注入量，是否已超过窗口可用预算的一半？
        ├── 是 → 引入分页或分层（Core / Archived）与召回预算（顶 k + token 上限）
        └── 否 → 全量注入 + 去重排序即可；不要为长窗口付调度成本

        T6 是否存在删除 / 导出义务（法规、未成年人、医疗金融）？
        ├── 有 → 先建删除编排（条目 + 向量 + 倒排 + 派生摘要），再谈自动遗忘
        └── 没有 → 仍要建按条目删除接口，只是可以先不做跨存储编排

        T7 同一个用户的记忆会不会被多个端或多个 Agent 读到？
        ├── 会 → 记忆抽成独立服务，作用域进分片键 + 查询改写器（跨 Agent 共享按 §5 属 L3：先做作用域与写权限，不假设跨 Agent 记忆一致）
        └── 不会 → 单库单租户模型足够，但不要把隔离写在应用层条件里

        T8 单租户的记忆条目量级是多少？
        ├── 十万级以下 → 用与业务库同栈的向量能力（pgvector 一类）
        └── 亿级 / 需要独立扩缩容 → 独立向量库 + 按作用域分区 + 重排
```

**阈值依据**（与树上每个带编号的判断节点 T1–T8 一一对应）：

- **T1「会话结束后是否复用」**：依据是**键的粒度与任务的粒度是否一致**（§3.1）。判定方法不是问产品经理「要不要个性化」，而是取一条真实任务看它的生命周期是否长于会话的生命周期：长于就会在会话结束时丢掉未完成的状态（§3.2.1 的失效点）。
- **T2「事实会不会变」**：依据是 7.3.1 的机制——**只要同一主谓可能出现第二个值，就必须在写路径上有一个收敛点**，否则读路径只能靠模型临场分辨。判定方法是查一条真实记忆的业务语义：「用户改地址后旧地址还有意义吗」。有意义（如历史账单地址）说明需要的是带有效区间的事实表；无意义则说明纯追加就够。
- **T3「是否真的出现两跳以上关系」**：依据是 7.3.3 的机制——**相似度无法表达「有关系」**。判定方法是从现有查询日志里找「必须先按某实体筛出一批人、再按这些人取他们的行为」这类问题；这类问题存在才值得建图，只是偶尔出现可以用关系表多跳 SQL 兜住（§4.3 同此判据）。
- **T4「是否有复盘与举证要求」**：依据是**外部要求而不是技术偏好**：受监管行业的事故复盘、未成年人场景的家长可查、争议留证，都要求能回答「当时系统看到了什么」。判定方法是问「如果昨天那条回答被投诉，你能拿出当时进模型的召回候选集吗」——拿不出，说明需要情景记忆，而不是需要更好的模型。
- **T5「注入量是否超过窗口可用预算的一半」**：依据是上下文预算是零和的（§5.2.2）——窗口要同时容纳系统提示、本轮输入与工具结果，记忆只是其中一路；当记忆要占掉一半以上时，剩下的空间不足以容纳任务本身，此时引入调度换来的收益才大于它每轮多花的 token 与延迟。用「预算的比例」而不是一个绝对 token 数，是为了让它随你实际使用的模型窗口一起移动。判定方法是把最近一次请求的注入内容按来源拆一遍，看记忆占了多大比例。
- **T6「是否存在删除 / 导出义务」**：依据是**法规义务，不是技术阈值**：GDPR 与个保法下的删除请求是义务，用户要求就必须删，不能由重要性分数决定。判定方法是问「用户行使删除权时，你们能不能枚举出他的记忆散布在哪些存储」，并把「自动遗忘不能替代删除接口」写成硬约束（§5.2.3）。
- **T7「是否多端 / 多 Agent 共读」**：依据是**用户身份能否跨端对齐成同一个 `user_id`**（§3.3 最后一行的判据）。若身份对齐不了，先解决标识问题，再建统一记忆——否则会把同一用户拆成两份互不可见的画像，任何一端都拼不出完整画像。
- **T8「条目量级十万级 / 亿级」**：依据是**向量索引的构建内存与扩缩容需求**：与业务库同栈的向量能力在向量量级与索引构建内存上会成为瓶颈，而独立向量库多一套备份、权限与一致性协调成本（§4.3 的同一条判据，该处的量级口径是【经验】）。判定方法看两个数：单租户的向量条目数与「是否需要对向量库单独扩缩容」——两者都超出同栈能力时才独立部署。换底座要重算全量向量，所以这一步的判断要尽量晚做、一次做对。

这八个节点里，**答错了回不来的是两条：T2，以及 7.1 判据表里那条「唯一会造成不可逆后果」的判据——隔离与删除的落点（落在 T6 / T7 上）**。T2 决定形态（要不要写路径、要不要当前值），而形态一旦被写进实现，换掉它意味着重新抽取全部存量；隔离与删除的落点在 7.3.4 已经拆开过：作用域要写进存储分片键（事后补要重做分片键与索引、重分布历史数据，是该表唯一一格「不能优雅补」），派生摘要与图谱边要在写入时就留下来源（不留来源时只能按用户整体重建，§3.6）。其余节点都依附在形态之上、可以逐个补：图谱加在提取式之上，事件表加在事实表旁边，向量能力换底座——它们的失败形态是「贵的、慢的」，而不是「回不去的」。所以排优先级时，**T2 与 T6 / T7 的答案要在动手写第一行代码之前定下来**（T6 的「有义务」分支本来就是「先建删除编排、再谈自动遗忘」，T7 的底线是把作用域写进分片键、查询改写器可以后补），T3、T4、T5、T8 的答案可以随规模逐个回答，回答顺序按 7.4 里哪一项先成为主导项来定。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 只要跨会话连续性，不要求精确当前值 | Session Memory + Vector RAG 记忆 | Session + 提取式（若偏好会变） | 直接上图谱：多跳用不上，只多一套实体链接的写入成本 |
| 偏好会变、要回答「当前值」 | 提取式（带有效时间与冲突解决） | 提取式 + 知识图谱 | 纯向量追加：新旧值并存且都会被召回（7.3.1） |
| 长任务、上下文装不下全部过程 | 分页式（MemGPT / Letta 路线） | 摘要压缩 | 纯摘要不可逆：被压掉的信息换不回来 |
| 查询有多跳关系 | 提取式 + 知识图谱记忆 | 关系表里多跳 SQL | 只靠相似度：回答不了「和谁有关」 |
| 要复盘失败决策、要能举证 | 情景记忆（含中间状态） | 事实条目 + 原始日志另存 | 只留事实条目：条目丢掉了过程，定位不到分叉点 |
| 受监管 / 未成年人场景 | 提取式 + 情景记忆 + 删除编排 | 单库 + 应用层删除 | 只删主表：向量与倒排索引里仍留有可被检索到的残片 |
| 多端 / 多 Agent 共享同一份记忆 | 记忆做成独立服务 + 作用域进分片键 | 各端各建一库后做离线合并 | 应用层 WHERE 过滤：漏一处即跨租户，且不会有异常 |
| 平台化、要给很多 Agent 复用 | 平台内建的三形态（变量 / 数据库 / 记忆库） | 自研记忆层（Memory API 四动作） | 每个 Agent 自研：同一份用户事实被重复抽取，口径不一致 |
| 成本敏感、不要求精确回忆 | 压缩式记忆 + 保留期上限 | 提取式 + 更短的保留期 | 全量原文保留：成本随轮数 × 保留期线性增长（7.4） |

**这张矩阵里最容易被误选的一对，是「记忆做成独立服务」与「每个 Agent 各建一库」**。两者读起来都是「每个 Agent 都有记忆」，差别只在所有权放在哪一级：前者把记忆的所有权放在用户 / 组织一级，后者放在 Agent 实例一级。误选的实际后果不是「重复建设」——重复建设的真正代价是**同一份用户事实有两份互不可见的版本**，当两个 Agent 给出不同答案时，没有任何机制能判断谁对；而会话缓存与记忆混用还会造成另一种症状：**有时记得、有时不记得**，取决于命中哪个实例（§4.3 缓存一行的同一条判据）。所以这一对的选择不该由性能决定，而应由「同一用户会不会被多个 Agent 读到」决定。

**四条常见组合及其职责边界**（组合的价值在于**边界清楚**，不在于件数多）：

- **组合一：Session Memory + 提取式记忆（最小跨会话闭环）**。Session 承载一次会话内的上下文，会话结束时抽取事实写入长期记忆，下次会话开始时按用户召回。边界：Session 只管「这次」、不做抽取；抽取器只管「记什么」、不决定「下次给不给」。运维代价：抽取质量要持续监控（幻觉率、重复率），TTL 与长期保留期是两套策略而 PII 口径必须统一，且上线当天删除义务就同时落在两套存储上。适合规模：任何有跨会话需求的产品的最小起步形态，1–2 人可维护【经验】。
- **组合二：Session + 提取式 + 知识图谱（需要关系推理）**。事实条目回答「是什么」，图谱回答「和谁有关」，Session 回答「现在在做什么」。边界：图谱只承载稳定的实体与关系（用户、订单、项目），不承载临时状态；写入有先后（先实体链接，再写事实）。运维代价：多一套实体消解与 schema 迁移的长期工作，两条召回路径要融合排序且权重需要按业务调，图的数据质量没有监控就会静默退化。
- **组合三：提取式 + 情景记忆（需要合规与复盘）**。事实条目是「用户画像」，情景事件是「行为台账」：前者追求少而准，后者追求全而可溯。边界：事实条目可以被更新与失效，情景事件不可修改（只能追加，或按合规要求删除整条）。运维代价：情景表体积最大，保留期与归档策略必须显式；删除请求要同时覆盖事实条目与其来源事件；导出要能给出可读的原始记录。
- **组合四：平台化记忆服务（多 Agent / 多业务复用）**。把记忆做成独立服务，运行时通过 Memory API 的读 / 写 / 检索 / 遗忘四个动作访问（这四个动作画在 §4.3 的架构图上；写入、检索、遗忘与合规导出各自的入参与必须带回项，见 §4.5 模板 1 的契约表），按 `user` / `agent` 双维度分区。边界：服务负责隔离、删除与召回，业务方负责定义「什么算事实」与「谁的两次说法谁优先」。运维代价：多一套服务的可用性与版本管理；跨作用域的授权模型要先定，否则「都放在一个库里、谁都能查」。

这四条组合共享同一条纪律：**每引入一件，就要能回答「它的写入由谁触发、它坏了由谁发现」**（§5.7 把这条写成「预算该投在写路径的可回滚、删除路径的可验证、读路径的可观测三件确定性工程上」）。答不上来的一律先不加——多一件带来的不是能力，而是多一条会静默失效的链路。另有一条共同的顺序：**先定义记忆的作用域与删除路径，再定义记忆的形态**；反过来做（先把形态都建起来、再补隔离与删除）是本章最常见的返工来源（§3.4）。

### 7.7 选错的代价与迁移成本

**反模式：把向量数据库当记忆系统整体购入** —— 症状是把对话塞进向量库、按相似度召回，演示期效果立竿见影，于是它被当成记忆系统整体引入；后果是延迟暴露且难以回退：向量库不提供三样东西——**当前值的概念**（同一事实的旧值与新值在向量空间里几乎不可区分）、**写入通道的治理**（它不判断什么该记）、**删除编排**（删主表不等于删索引），等到缺口显形时记忆已经写进主链路，换掉它的成本是把已沉淀的对话重新抽取一遍；正确做法是先按 7.1 的「候选不在同一层」承认这是**形态层**的选择，再按 T2 决定要不要在写路径上加收敛点——判断方法只有一句：问它能不能回答「这个偏好的当前值是什么、什么时候改的、改之前是什么」（§4.3 的同一条判据）。

**反模式：先回灌历史，再补删除编排** —— 症状是项目立项时最有说服力的动作是「把历史对话全量抽取进记忆」（它最容易立项、看起来最像进展）；后果是它同时做两件不可逆的事：把未经复核的错误事实赋予与用户亲述同等的权重，以及让删除义务从回灌完成那一刻起立即生效——回灌 3 个月还是 3 年，最终差别体现在一次删除请求要覆盖多少条、多少存储；正确做法是按 §4.4 的顺序走：**先跑通会话内记忆与删除编排，再决定回灌的范围与深度**，并且回灌必须与记忆清单页（逐条查看 / 编辑 / 删除 + 来源标注）一起上线，否则会把「系统背着我记东西」的信任问题放大。同族的另一个错误是把自动遗忘当删除接口——评分不能替代义务（§5.2.3）。

**反模式：把上下文缓存当记忆** —— 症状是「我们的模型有 prompt cache，命中率很高，所以长期记忆已经有了」；后果是缓存的键是前缀、记忆的键是用户，前者失效只影响成本、后者失效影响业务连续性——缓存一旦失效或版本升级，表现为**整体失忆**，而这类失忆与「记忆没写进去」在监控上无法区分；正确做法是按 §2.4 与 §5.2.2 的边界把两者分开：缓存优化的是同一段前缀的重复计算成本，记忆承担的是业务连续性，判断方法是问「清空缓存之后，用户昨天交代的约束还在不在」。

**换成另一个要动什么**：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 纯向量追加 → 提取式 | 存量原文要重新抽取一遍；抽取质量不可判的部分建议只留档不回灌【经验：量级为月】 | 检索入口从「按相似度取顶 k」改为「按作用域取当前值 + 加权召回」【经验：量级为周】 | 新增抽取管道、冲突规则与质量监控【经验：量级为月】 | 从「调相似度阈值」转为「调抽取与冲突规则」，监控项完全不同【经验：量级为月】 |
| 提取式 → 提取式 + 知识图谱 | 不搬数据，但存量事实要回跑一次实体链接【经验：量级为月】 | 多一条并行召回路径，需重排融合与权重调参【经验：量级为月】 | 新增图库、schema 版本管理与实体消解质量校验【经验：量级为季】 | 图查询与向量检索是两套技能【经验：量级为月】 |
| 应用层隔离 → 存储分片键隔离 | 历史数据要按作用域重分布【经验：量级为月】 | 过滤条件从每个查询里的 WHERE 收到查询改写器【经验：量级为周】 | 重做分片键与索引【经验：量级为季】 | 从「记得加条件」变成「入口统一负责」【经验：量级为周】 |
| 无跨存储删除 → 删除编排 | 不搬数据，但要先梳理「记忆散布在哪些存储」【经验：量级为周】 | 查询侧不改，接口侧新增按条目删除与导出【经验：量级为周】 | 给删除做幂等与补偿，并保留台账【经验：量级为月】 | 删除从「删一行」变成「一次编排 + 一次验证」【经验：量级为月】 |
| 平台内建记忆 → 自研记忆服务 | 存量记忆导出后按新 schema 重建（须先确认导出接口存在）【经验：量级为月】 | 调用方从平台接口改为 Memory API 四动作【经验：量级为月】 | 新增抽取 / 存储 / 检索 / 遗忘 / 审计六个模块的运维【经验：量级为季】 | 记忆从「产品功能」变成「需要人认领的系统」【经验：量级为季】 |

这张表里最难的一列不是「数据迁移」，而是**「团队再学习」**：搬数据有工程手段（限批回灌、双读校验），可以按周排期；而从「调相似度阈值」转到「调抽取与冲突规则」意味着**监控项与排障路径整体换掉**——漏召不再表现为检索分数低，而表现为用户重复交代同一件事的次数上升（§5.2.2 给的那个可观测信号）。所以这一列的成本应当提前算进去，而不是在迁移启动之后才补。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 记忆只需活过一次会话 | Session Memory（KV + TTL） | 键与会话同粒度，读写退化为点查与追加，运维面近零 |
| 只要「上几轮聊过什么」、不要求精确 | Vector RAG 记忆 | 存原文不引入抽取失真；代价是无结构、无时间，冲突不被收敛 |
| 事实会变、要回答「当前值」 | 提取式（有效时间 + 冲突解决） | 更新发生在写路径，读路径才不需要自己分辨新旧 |
| 上下文装不下、任务又很长 | 分页式（MemGPT / Letta 路线） | 换页由模型按当前任务决定，不必预先知道哪些记忆将来有用 |
| 查询需要多跳关系 | 知识图谱记忆（实体 + 关系 + 时间） | 关系被显式建模才能遍历，相似度无法表达「和谁有关」 |
| 要复盘与举证 | 情景记忆（含当时的中间状态） | 只有留下当时的系统状态，才能定位决策的分叉点 |
| 合规要求可删除 / 可导出 | 删除编排（全副本 + 全索引 + 台账） | 记忆散布多处，删除必须一次覆盖全部副本；评分不能替代义务 |
| 多端 / 多 Agent 共享 | 记忆独立服务 + 作用域进分片键 | 隔离只有写进物理布局，才不依赖每个查询的自觉 |
| 平台化复用 | 平台三形态（变量 / 数据库 / 记忆库）或自研记忆层 | 形态由「记什么」决定，平台保证底线质量，业务定义语义 |

上面九行可以压缩成一句判断：**先确认你的记忆跨越哪几条边界，再在剩下的候选里按「冲突有没有收敛点」二分**。落到具体动作上，第一次选型时最值得做的三件准备是：① 数出你的「每用户每年条目数 / 原文保留期 / 每轮是否发生抽取调用」三个数（它们决定 7.4 里哪一项是主导项）；② 列出「删一个用户要动几处存储」（它决定你在 T6 上能不能通过合规审计）；③ 问清楚「同一个用户会不会被多个 Agent 读到」（它决定 T7，而 T7 是唯一一条与规模无关、却最容易出事故的判据）。

三个容易被忽略、但会在半年量级后显形的检查项【经验：量级为季到半年】：

- **你有没有一条「用户重复交代同一件事的次数」的指标？** 没有它，读路径的漏召是不可观测的——它只会表现为用户觉得「这系统不太可靠」。
- **记忆清单页上线了吗？** 没有它，回灌会让「系统背着我记东西」的信任问题放大，而逐条可控是消费级记忆的隐私基线（§6 的第一个案例把它作为失败教训记下）。
- **删除演练做过吗？** 校验必须覆盖向量索引与倒排索引中的残片，而不是只删主表——这项演练放在切换前做，成本最低（§4.4）。

> 本节小结：这一组候选之间，在边界确定之后，**唯一真正起决定作用的差异是「写路径上有没有一个收敛点」**——即新旧冲突是在写入这一刻收敛（提取式、知识图谱），还是留给读取去猜（原文追加、压缩式）。它决定了同一个问题会不会两次得到不同答案，而这条差异**补不上只能换形态**；其余差异（上下文怎么分配、事件留不留、底座用哪个）都是在形态选定之后逐步补齐的工程问题；**只有隔离与删除的落点不能留到那时**——它要写进存储布局，必须与形态在同一步定下来（7.3.4）。（§3.8 立的是更上游的那条约束——记忆要跨越的边界；边界决定你要不要写路径，本节这条决定写路径长什么样。）
>
> 💡 **思考锚点**：拿一件会变的事实（比如用户当前的某项偏好）在两个会话里各问一次——会不会拿到两个不同答案？如果会，你的写路径上有没有一个收敛点，还是 §7.8 表里再多的「迁移前准备」也补不上、只能换形态？
