## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表读起来像一道选择题：单次会话选 Session Memory，个性化选 Mem0，长任务选 MemGPT，复杂推理选知识图谱。但只要把两个"个性化"放一起看，它立刻失效：一个是把用户偏好当作**长期不变的事实**（住址、语言偏好），另一个是偏好**按月甚至按天变化**（最近失眠、正在选装修风格）。前者可以用一张事实表加拉链解决，后者必须有时间维度与冲突解决——同一个"场景"，正确模式完全不同。

真正做决定的是约束。长期记忆里有六条反复出现：**记忆要跨越的边界**（会话内 / 会话之间 / 事件之间）、**写入通道由谁决定**（用户显式声明 / 模型抽取 / 行为推断）、**事实的时效性**（新值是否取代旧值）、**检索预算**（延迟与注入 prompt 的 token 上限）、**作用域与隔离**（个人 / 团队 / Agent / 项目）、**删除与导出义务**（合规要求）。任一条不同，模式选择就会翻转。

所以本节先立约束、再谈模式。下表不是选型表，而是"最容易被约束推翻的直觉"清单——当你觉得某个模式"显然更好"时，先回去看是哪条约束在替你说话。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 记忆要跨越的边界（会话内 / 跨会话 / 跨事件） | 落在哪一类存储 | 「用一个向量库解决所有记忆」——会话内的记忆用 KV + TTL 就够，上向量库只增加链路与成本 |
| 写入通道（显式声明 / 模型抽取 / 行为推断） | 记忆准确率的上限 | 「提取越自动越好」——抽取由模型决定"记什么"，准确率上限就是抽取器的准确率 |
| 事实的时效性（旧值是否被新值取代） | 要不要时间维度与冲突解决 | 「存下来就行」——住址这类事实会变，没有当前值概念的记忆系统必然给出过期答案 |
| 检索预算（延迟 + token） | 记忆的存储形态（原文 / 事实 / 图） | 「记得越全越好」——注入 prompt 的记忆有硬上限，超出的部分不是被记住而是被挤掉 |
| 作用域与隔离（个人 / 团队 / Agent） | 隔离模型与共享模型 | 「先做单用户，隔离以后再加」——隔离要写在存储布局里，事后补要重建分片键 |
| 删除与导出义务（合规） | 物理布局能否真正删干净 | 「删主表就够了」——向量索引与倒排索引里仍留有可被检索到的残片 |

还有一条不写在表里、却决定所有模式能否落地的约束：**记忆存在多处时，"写"是一件容易的事，"删"是一件难的事**。记忆通常同时落在缓存、向量库、关系库、图库与日志里，写入可以异步、可以失败重试，而删除必须一次性覆盖全部副本。凡是把删除当作"以后再做"的系统，最终都要为补一次删除而做跨存储的编排工作。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 Session Memory（会话记忆）

- **被什么约束逼出来**：多轮对话与多次工具调用之间必须共享同一份上下文，而这份上下文只在一个会话内有意义——为它建长期检索链路，收益远小于成本。
- **结构**：以会话为键的消息序列，配 TTL；热路径放缓存，落地盘做持久化。

```sql
CREATE TABLE session_message (
  session_id  VARCHAR(64) NOT NULL,
  turn_no     INT         NOT NULL,
  role        VARCHAR(16) NOT NULL,   -- system / user / assistant / tool
  content     TEXT,
  token_count INT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (session_id, turn_no)
);
-- 热路径：Redis key = sess:{session_id}，value = 消息列表，TTL 到期即"失忆"
-- 关键取舍：TTL 不是清理策略，是产品行为——到期后用户就"重开一世"
-- 工作记忆（WM）= 系统提示 + 本轮输入 + 检索召回 + 最近若干轮，由本表供料
```

- **为什么这样设计有效**：因为键是会话而不是用户，所以读永远是点查、写永远是追加到尾、过期与清理由一次 TTL 完成，整个模式的运维面几乎为零；代价是它的能力边界恰好在会话边界上——跨会话的一切都必须由别的模式承担。
- **代价**：上下文窗口是硬上限，会话越长，每轮携带的历史越多，越到后面单轮成本越高；进程重启、扩容与内存驱逐都要保证消息不丢（缓存与持久化要有一致性约定）；会话内是高密度 PII 区，保留期必须显式。
- **失效点**：当任务的生命周期长于会话的生命周期（用户第二天回来继续、或一次任务跨多次会话）时，Session Memory 从"简单够用"反转成"用户体感失忆"，因为 TTL 与上下文窗口两个机制都不表达"这件事还没做完"——它的本质是键的粒度与任务的粒度不一致。
- **真实使用**：用 Redis 的键过期语义承载会话缓冲是多数团队的做法【经验】；Redis 于 2009 年首次发布并自早期版本即提供键过期语义，其 EXPIRE / TTL 的语义与边界可按官方文档核验（版本与语义以官方文档当前版本为准，亦可按「Redis EXPIRE」检索）【公开】。会话 TTL 常见落在 24 小时到 30 天区间，具体取值应按业务会话跨度定【经验】。

#### 3.2.2 Vector RAG 记忆（原对话切块检索）

- **被什么约束逼出来**：不想为"记得"付出结构化建模的代价，且需要被记住的内容形态不规则、事先无法枚举。
- **结构**：把对话或文档切块 → 向量化 → 按相似度取 top-k → 注入 prompt。写入是纯追加，没有更新与冲突处理。

```sql
CREATE TABLE memory_chunk (
  chunk_id    BIGSERIAL PRIMARY KEY,
  user_id     VARCHAR(64) NOT NULL,
  source_type VARCHAR(16) NOT NULL,   -- conversation / doc / note
  text        TEXT        NOT NULL,
  embedding   VECTOR(1024) NOT NULL,  -- 维度取决于所选嵌入模型
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON memory_chunk USING hnsw (embedding vector_cosine_ops);
-- 检索：ORDER BY embedding <=> $q LIMIT k
-- 注意这里没有的列：没有 valid_to、没有重要性、没有置信度、没有来源模型
```

- **为什么这样设计有效**：因为库里存的是原文而不是抽取结果，所以召回内容不会引入抽取环节的失真（信息无损），且新增数据只需插入一行、不用做实体消解或冲突解决；代价是它没有结构——同一事实的旧值与新值在向量空间里几乎不可区分，"取到哪一条"由相似度而非由时间决定。
- **代价**：存储体积等于原文，远大于事实条目；检索噪声随条目数增长（top-k 永远会返回 k 条，哪怕只有一条相关）；无法回答"这个偏好的当前值是什么"这类需要聚合或时序的问题。
- **失效点**：当同一事实被反复写入且互相矛盾时，Vector RAG 记忆从"覆盖面广"反转成"越用越错"，因为冲突解决机制缺位，top-k 会把两条矛盾的旧记录同时召回交给模型自己挑——而更旧的那条并不因为更旧就排在后面。这正是"无结构"在时间维度上的具体后果。
- **真实使用**：向量检索与 HNSW 索引有公开实现与文档【公开】（来源：pgvector 2021 年开源、其 0.5.0 版本于 2023 年引入 HNSW 索引，Milvus 2019 年开源，Qdrant 2021 年开源——三条均可由各产品官方文档与 release note 核验，可按「pgvector HNSW」检索）；把历史对话按相似度召回并注入上下文是 [§4 工程实现](01-long-term-memory-section-4-sec4.md) 里的基础做法。

#### 3.2.3 MemGPT 分页（层次化记忆 + 自我换页）

- **被什么约束逼出来**：上下文窗口是硬上限，而任务需要的记忆是无界的；由人工事先决定"哪些内容该常驻"在通用场景下不可行。
- **结构**：把上下文窗口当作物理内存、外部存储当作虚拟内存，由模型通过函数调用完成换入换出。

```text
┌─ 上下文窗口（"物理内存"的类比） ─────────────────┐
│  System       人格与指令，常驻                     │
│  Core Memory  用户档案 + 当前任务状态，可读写      │
│  Recall Area  本轮从 Archival 换入的内容           │
└──────────────────────────────────────────────────┘
        │  function call：search / insert / replace / evict
        ▼
  Archival Memory（外部存储：向量库 / 关系库 / 文件）

关键：换页的决策者是模型自己（它持有一个记忆工具集）
      而不是外部的固定窗口策略（"保留最近 N 轮"）
```

- **为什么这样设计有效**：因为换入换出由模型按当前任务的需要决定，所以上下文里放的是"此刻最相关的那部分"，而不需要预先知道哪些记忆将来会有用；代价是每一轮都要额外消耗 token 去维护记忆结构并做换页决策，而模型可能判断错。
- **代价**：每轮多出一次或多次工具调用的延迟与 token；Core Memory 的分区与字段要预先设计好（否则模型不知道该往哪写）；换页出错时是"静默地丢掉了关键上下文"，不会抛异常。
- **失效点**：当某条信息被反复判为"不重要"而挤不回上下文时，分页记忆从"能处理超长任务"反转成"确定性地失忆"，因为换页判断的依据来自当前上下文，而当前上下文里已经没有那条信息了——模型无法为它看不见的东西打高分，这是自我换页机制的内在盲区。
- **真实使用**：把 LLM 上下文类比操作系统内存、由模型用函数调用换页的公开方法【公开】（MemGPT: Towards LLMs as Operating Systems，主文件 [§1.4 演进历程](01-long-term-memory.md) 把该论文记为 2024 年的突破阶段；版本与日期以论文页面当前内容为准）；该路线的工程化平台为 Letta【公开】（来源：Letta 官方文档，2024 年公司化，前身为 MemGPT 项目，可按「Letta MemGPT」检索核验）。

#### 3.2.4 Mem0 式提取记忆（事实抽取 + ADD / UPDATE / DELETE）

- **被什么约束逼出来**：记忆要跨会话长期保留，就不能存原文（体积、噪声、无法定位删除）；而"什么值得记"又写不成规则。
- **结构**：对话 → LLM 抽取事实 → 与已有记忆比对 → 执行 ADD / UPDATE / DELETE（无需变更时为 NOOP）→ 落库为带时间与置信度的条目。这是 Mem0 与 Zep 的共同骨架，Zep 的差异在于把时间维度做成第一等公民并配时间衰减。

```sql
CREATE TABLE memory_fact (
  id          UUID PRIMARY KEY,
  user_id     VARCHAR(64) NOT NULL,
  subject     VARCHAR(128),
  predicate   VARCHAR(64),
  object      TEXT,
  fact_text   TEXT NOT NULL,
  embedding   VECTOR(1024),
  importance  REAL CHECK (importance BETWEEN 0 AND 1),
  confidence  REAL CHECK (confidence BETWEEN 0 AND 1),
  valid_from  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  valid_to    TIMESTAMPTZ,            -- NULL 表示当前有效
  source      VARCHAR(16)             -- user_msg / inferred / external
);
-- 同一主谓只保留一条"当前值"：冲突解决落在写路径上，而不是留给读路径去猜
CREATE UNIQUE INDEX ON memory_fact (user_id, subject, predicate)
  WHERE valid_to IS NULL;
```

- **为什么这样设计有效**：因为写路径做的是"抽取 + 比对 + 更新"而不是纯追加，所以任一时刻每个主谓只有一条当前值，读的时候不需要模型自己分辨新旧；代价是准确性被压在抽取器身上，而"新值是否真的取代旧值"也需要有人（或模型）来判。
- **代价**：抽取会引入幻觉，错的事实一旦落库就获得与用户亲口陈述同等的权重；需要去重与冲突解决策略并长期调参；原始对话要么丢弃（损失可复盘性），要么另存（回到体积问题）。
- **失效点**：当抽取器开始把假设、玩笑、假设性提问写成事实时，提取式记忆从"自动、智能化"反转成"自动化地产生并长期保留错误"，因为记忆的写入通道无人复核，而读路径默认它是真的——风险之所以难以消除，是因为它发生在写路径、暴露在读路径。
- **真实使用**：Mem0 开源并把写操作定义为 ADD / UPDATE / DELETE 一类动作【公开】（Mem0 开源项目与其论文，arXiv 2504.19413，2024–2025；可按「Mem0 additive memory」检索核验）；Zep 走"时序事实 + 时间衰减"路线，把事实与时间绑定【公开】（Zep 的时序知识图谱论文与官方文档，2025；可按「Zep temporal knowledge graph memory」检索核验）。多数个性化场景落在这条路线上【经验】。

#### 3.2.5 知识图谱记忆（实体 + 关系 + 时间）

- **被什么约束逼出来**：有些问题需要多跳推理（"与我同一个项目的同事最近在问什么"），向量相似度给不出这类答案；而实体与关系需要稳定标识，才能被反复引用与更新。
- **结构**：节点、边、以及边上的时间与来源；写入前先做实体链接（消解同名与别名）。

```text
(:User {id}) -[:PURCHASED {ts, qty}]-> (:Product {sku})
(:User {id}) -[:WORKS_ON  {ts, role}]-> (:Project {id})
(:User {id}) -[:ASKED     {ts, intent}]-> (:Topic {name})

多跳查询（向量检索表达不了的那一类）：
  MATCH (me:User {id:$u})-[:WORKS_ON]->(p:Project)<-[:WORKS_ON]-(peer:User),
        (peer)-[a:ASKED]->(t:Topic)
  WHERE a.ts > now() - interval '30 days'
  RETURN t.name, count(*) AS cnt ORDER BY cnt DESC

写入前的关键一步：实体链接
  "我司" / "我们公司" / 公司全称 → 同一个 (:Org) 节点
  这一步错了，图看起来是通的，实际是断的
```

- **为什么这样设计有效**：因为关系被显式建模，所以"谁和谁有关"可以沿边遍历得到，而不是靠向量相似度猜测；代价是写入要先做实体链接与 schema 约束，图查询与向量检索成为两条并行召回路径，融合排序需要额外加权。
- **代价**：工程复杂度与写入成本（每条记忆落库前先做实体链接）；schema 演进要迁移存量节点与边；图的规模增长会让多跳查询的路径数迅速膨胀，需要限制跳数与剪枝。
- **失效点**：当实体链接做得不好时，图谱记忆从"可推理"反转成"看起来连通、实际断裂"，因为同一实体被拆成多个节点，多跳查询的路径根本走不通——而这种错误不报错，只让召回结果变少，团队往往误以为是"数据不够"而不是"图错了"。
- **真实使用**：属性图数据库与其查询语言有公开文档【公开】（来源：Neo4j 1.0 于 2010 年发布，NebulaGraph 2019 年开源，TigerGraph 平台 2017 年发布——三条均可由各产品官方文档与发布记录核验，可按「产品名 + 发布年份」检索）；把知识图谱与向量检索混合的做法见 Cognee 一类项目【公开】（Cognee 官方文档与论文，2024–2025，见 [§5 前沿演进](01-long-term-memory-section-5-ai.md)）。

#### 3.2.6 Episodic（情景）记忆

- **被什么约束逼出来**：要复盘"上次为什么答错"，就必须保留事件本身——抽取后的事实条目恰好把过程丢掉了；反事实推理需要知道"当时的系统看到了什么"。
- **结构**：事件表，粒度是"一次发生"；除输入输出外，必须留下当时的中间状态。

```sql
CREATE TABLE episodic_event (
  id         BIGSERIAL PRIMARY KEY,
  user_id    VARCHAR(64) NOT NULL,
  session_id VARCHAR(64),
  ts         TIMESTAMPTZ NOT NULL,
  event_type VARCHAR(32) NOT NULL,  -- user_query / agent_action / tool_call / feedback
  actor      VARCHAR(16) NOT NULL,  -- user / agent / tool
  payload    JSONB NOT NULL,        -- 完整输入输出
  context    JSONB,                 -- 召回候选集 / 工具参数 / 模型与 prompt 版本
  outcome    VARCHAR(16),           -- success / fail / neutral
  feedback   JSONB
);
-- 关键：context 里必须留下"当时的中间状态"
--       否则复盘只能看到输入与输出，看不到分叉点
```

- **为什么这样设计有效**：因为事件按发生顺序完整落库，所以可以重建"决策发生时系统看到了什么"，失败归因与反事实推理才有材料；代价是体积随事件量线性增长，且它按时间与条件筛选的检索方式，比按相似度召回慢得多。
- **代价**：这通常是记忆体系里最大的一张表，存储与治理成本最高；PII 密度最大（payload 是原始内容），保留期必须显式管理；写入与在线链路的耦合要处理好（落库不能拖慢推理，通常只能异步）。
- **失效点**：当保留期被压缩、或 context 字段被省略时，情景记忆从"可复盘"反转成"只留下结果、无法定位分叉"，因为输入输出相同的事件可能对应完全不同的中间状态——事后无法区分"检索召回了错的证据"与"生成时忽略了对的证据"。
- **真实使用**：可观测平台以事件级追踪为载体，记录每次调用与工具参数的完整链路【公开】（来源：Langfuse（2023 年开源）、Helicone（2023 年开源）一类产品的官方文档，可按「产品名 + 开源年份」检索核验）；把"事件 + 时间 + 上下文"作为记忆粒度的工程含义，见主文件 [§2.1 关键概念](01-long-term-memory.md)。

#### 3.2.7 混合模式（多形态分层组合）

- **被什么约束逼出来**：没有任何一种记忆形态能同时满足四件事——会话内要廉价、跨会话要稳定、关系要能推理、过程要能复盘；而真实产品往往四项都需要。
- **结构**：写路径把同一批输入分发到多种形态，读路径按作用域路由并融合打分。

```text
写路径（对话结束时异步执行）
  会话消息 ─┬─▶ 事实抽取 ──▶ memory_fact（去重 / 冲突解决 / 置信度）
            ├─▶ 原文与中间状态 ──▶ episodic_event
            └─▶ 实体链接 ──▶ 图谱边
读路径（每次请求）
  ① 按作用域路由：当前会话 → Session
                  用户画像 → memory_fact
                  关系推理 → 图谱
                  过程复盘 → episodic_event
                  外部知识 → 文档 RAG
  ② 各路召回 → 归一化打分（相似度 + 时间衰减 + 重要性 + 置信度）→ top-k
  ③ 注入 prompt（每路都要带来源与作用域标签）
关键：少一路的作用域过滤，整体隔离就失效
```

- **为什么这样设计有效**：因为不同形态的记忆可以由同一批输入在写路径上一次产出，所以组合的边际成本主要落在读路径的路由与融合上；代价是四套记忆存储（会话、事实、图谱、情景）各自要有治理（保留期、隔离、删除、导出）——外部知识 RAG 只读、不进这套治理，但它是读路径上的第五路，删除一个用户要四处同步。
- **代价**：架构复杂度与运维面成倍；一致性没有单一真值（事实条目说 A、事件表说 B，用户该看到哪个需要定义）；写放大（一次对话产生多份副本）；删除与导出要跨存储编排。
- **失效点**：当作用域过滤只在其中某几路生效时，混合记忆从"能力互补"反转成"由最小的那个漏洞决定整体"，因为跨作用域污染只要一条路径漏了就发生，其余路径的正确性不能补偿它——"记忆泄露"在混合架构里最容易发生，也正是这个原因。
- **真实使用**：四路组合落到具体业务上是客服 Agent 这一类——Session 存当前工单、事实条目存用户偏好、图谱存「用户-订单-商品」关系、RAG 查产品手册（该例出自「混合模式」；它比 §3.2.7 的五路少一路，缺的那一路是过程复盘 episodic_event）。把它落到存储上，用的就是主文件 [§2.5 记忆的数据建模](01-long-term-memory.md) 给出的三类模型（2.5.1 事实三元组、2.5.2 情景事件、2.5.3 图谱实体）与 2.5.4 的物理存储选择；把多层记忆做成一等能力的平台实践（阿里个人 / 团队 / 组织三层、字节的变量 / 数据库 / 记忆库三形态）见 [§6 落地实践](01-long-term-memory-section-6-sec6.md)。

把这 7 个模式放在一起看，会发现它们并不是竞争关系：其中四种是**同一份记忆落在不同位置上的形态**——会话内（Session）、跨会话的稳定事实（提取式）、跨会话的关系（图谱）、跨事件的过程（情景）。这四种形态落在 §3.1 那三条边界上，"跨会话"这一条上落了稳定事实与关系两种，所以"四"数的是落点，不是边界。剩下三个模式回答的不是"落在哪里"：Vector RAG 用原文承载跨会话记忆，是最省事也最没有结构的一种；MemGPT 分页解决的是"上下文装不下"；混合模式把这几种形态各取一份组合起来。选型的第一步不是比优劣，而是判断你的记忆实际跨越哪几条边界。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 记忆只需活过一次会话（单次客服、临时任务） | Session Memory（KV + TTL） | 不用向量库：跨会话能力用不上，多一条链路就是纯成本 | 会话结束后是否真的不需要复用 |
| 只要"上几轮聊过什么"，不要求精确 | Vector RAG 记忆 | 不用提取式：抽取会引入失真，而这里对精确性要求低 | 召回错一条的代价能否接受 |
| 偏好会随时间变化、要能回答"当前值是什么" | 提取式（带 valid_from；时间衰减按 §5.1 属 L3——只做保留期上界、不假设衰减能自动分出好坏） | 不用 Vector RAG：原文块之间无法区分新旧值 | 是否有时间列或衰减因子 |
| 长任务、上下文装不下全部过程 | MemGPT 分页 | 不用纯摘要：摘要不可逆，被压掉的信息换不回来 | 记忆能否被模型主动检索回上下文 |
| 知识密集型 Agent、且查询含两跳以上关系 | 知识图谱记忆 | 不用向量检索：相似度回答不了"和谁有关" | 查询是否真的需要遍历关系 |
| 要复盘失败决策、要能举证 | Episodic 记忆（+ 中间状态） | 不用事实条目：条目丢掉了过程，定位不到分叉点 | 事件是否带召回候选与工具参数 |
| 合规要求可删除、可导出 | 混合模式 + 删除编排 | 不用单库：记忆散布在缓存 / 向量 / 关系 / 图多处 | 能否枚举出所有存有该用户记忆的存储 |
| 多 Agent 协作、要共享部分记忆 | 共享图谱 + 显式作用域（跨 Agent 共享按 §5 属 L3：只记录，不假设跨 Agent 记忆一致；可先落地的只有作用域与写权限的显式化） | 不用共享向量库：相似度召回无法表达"谁有权看" | 作用域标签是否写进存储分片键 |
| 用户跨设备 / 跨平台，同一人的记忆要合成一份画像 | 提取式记忆 + 中央化存储（统一画像） | 不用按端各建一库：同一用户的事实会分裂成互不可见的两份，任何一端都拼不出完整画像 | 用户身份能否跨端对齐成同一个 user_id |

本节最常被误选的一对，是**把 Vector RAG 记忆当成通用长期记忆**。二者的机制差别不在检索质量，而在**写路径**：RAG 式记忆只追加、不更新，因此库里可以同时存在"住在北京"和"搬到上海了"两条记录，且它们向量相近、都会被召回；提取式记忆在写路径就完成比对与更新，读路径拿到的是唯一当前值。误用的典型后果是：短期内体感"记得挺多"，几周后开始出现自相矛盾的回答，而排查时每条记录单看都是对的。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Session Memory + 提取式记忆（最小跨会话闭环）**

- 构成：Session 承载一次会话内的上下文，会话结束时抽取事实写入长期记忆，下次会话开始时按用户召回。
- 职责边界：Session 只管"这次"，不做抽取；抽取器只管"记什么"，不决定"下次给不给"；召回侧按作用域过滤。
- 运维代价：抽取质量要持续监控（幻觉率、重复率）；TTL 与长期保留期是两套策略，PII 处理口径要统一；这一层一旦上线，删除义务就同时落在两套存储上。
- 适合规模：任何有跨会话需求的产品的最小起步形态，团队 1–2 人即可维护【经验】。

**组合二：Session + 提取式 + 知识图谱（需要关系推理）**

- 构成：事实条目回答"是什么"，图谱回答"和谁有关"，Session 回答"现在在做什么"。
- 职责边界：图谱只承载稳定的实体与关系（用户、订单、项目），不承载临时状态；事实条目承载属性与偏好；两者的写入要有先后（先实体链接，再写事实）。
- 运维代价：多一套实体消解与 schema 迁移的长期工作；两条召回路径要融合排序，权重需要按业务调；图的数据质量没有监控就会静默退化。
- 适合规模：推荐、风控、多 Agent 协作类场景，通常从"查询里真的出现多跳需求"那一刻起才值得上。

**组合三：提取式 + Episodic（需要合规与复盘）**

- 构成：事实条目是"用户画像"，情景事件是"行为台账"；前者追求少而准，后者追求全而可溯。
- 职责边界：事实条目可以被更新与失效（用户改地址），情景事件不可修改（只能追加，或按合规要求删除整条）；两者共同支撑"为什么给出这个答案"的举证。
- 运维代价：情景表体积最大，保留期与归档策略必须显式；删除请求要同时覆盖事实条目与其来源事件；导出要能给出可读的原始记录。
- 适合规模：受监管行业、或有明确事故复盘要求的场景。

三条组合共享一个前提：**先定义记忆的作用域与删除路径，再定义记忆的形态**。反过来做（先把四种记忆都建起来，再补隔离与删除）是本节最常见的返工来源——因为隔离要写进分片键、删除要跨存储编排，这两件事都无法在事后用应用层代码优雅地补上。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 记忆爆炸 | 记忆条目数持续上升且无人清理；检索结果里无关项变多 | top-k 永远返回 k 条，噪声与条目数同向增长，关键记忆被挤出上下文 | 写入不设门槛（"先记下来总没错"），删除没有负责人 | 写入按重要性阈值筛选 + 时间衰减 + 定期合并 |
| 记忆幻觉 | 用户说"我没说过这个"，但记忆里有 | 错事实获得与用户亲述同等权重，后续所有回答都以它为真 | 抽取只做一次、没有置信度与来源标注 | 写入标 confidence 与 source，低置信需二次确认 |
| 记忆过期 | 推荐仍基于半年前的偏好；用户已改住址而系统还在用旧值 | 记忆是无时间结构的，旧值不因更旧而降权 | 表结构里没有 valid_to / 有效时间 | 加有效时间与衰减；冲突时以新值覆盖并留旧值 |
| 记忆冲突 | 同一问题两次回答不一致；两条矛盾记忆同时被召回 | 读路径面对矛盾证据，只能靠模型临场选择，结果不稳定 | 写入路径没有比对步骤，只追加不更新 | 唯一索引约束"当前值" + 冲突解决策略 |
| 记忆泄露 | 用户 A 看到用户 B 的信息 | 隔离缺失时，一次召回即可跨租户取数，且不会有异常 | 隔离写在应用层 SQL 里，而不是存储分片键上 | 按 user / agent 维度分区，过滤进查询改写器 |
| 强制记忆 | 用户要求删除却被"记住"；删除接口不存在或无效 | 合规义务无法履行，且残片仍在向量与倒排索引里可被检索 | 删除没有跨存储编排，只删了主表 | 提供主动遗忘 API，覆盖全部副本与索引 |
| 记忆污染 | 同一条错误信息被反复写入、反复生效 | 恶意的错误信息进入长期记忆后，被当成用户事实长期复用 | 写入不做来源校验与频次限制 | 写入校验 + 来源审计 + 异常频次拦截 |
| 全量塞 Context | 单次请求 token 消耗异常高；延迟上升 | 上下文窗口被挤满，真正关键的信息被截断，成本同步上涨 | 认为"记得越多越好"，没有召回预算概念 | top-k + 重排 + 摘要，给召回设 token 预算 |
| 无时间维度 | 无法回答"这是什么时候的事" | 旧事实与新事实等权，时序问题无法正确回答 | 建模时把记忆当作静态事实表 | 加时间戳与有效区间，检索时带时间衰减 |
| 无重要性 | 噪声淹没关键记忆；重要与琐碎记忆同权 | 检索排序没有可用的区分度，只能靠相似度 | 一视同仁地写入，重要性函数未定义 | 用 LLM 评分给出重要性（f: E → [0, 1]）并参与排序 |

**记忆泄露是唯一会造成不可逆后果的一条**：其他反模式都能靠治理慢慢修，而跨租户泄露一旦发生，用户已经看到了不该看的内容。它在混合架构里最容易被引入——§3.2.7 读路径上的五条召回路径（当前会话、用户画像、关系推理、过程复盘、外部知识）各写各的 WHERE 条件，只要有一条漏了作用域过滤，整体隔离就失效。所以隔离的落点是"存储分片键 + 查询改写器"，而不是"每个查询记得加条件"。

**记忆冲突的隐蔽性在于它不产生错误、只产生不一致**。同一个问题今天答 A、明天答 B，用户会觉得"这系统不太可靠"，但日志里每条记录都合法。机制上它是写路径缺了比对步骤：只要允许同一主谓有多条并存，"取哪条"就变成了读路径的随机性。

**记忆污染与记忆幻觉的区别在于来源**：幻觉是模型自己产生的错误，污染是外部注入的错误进入长期记忆后被反复使用。后者的危险在于它会自我强化——错误记忆影响回答，回答又被当作新证据写回记忆，形成一个不需要外部输入的循环。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单轮问答 → 跨会话连续性 | 无记忆 / 只带最近若干轮 | 每轮都要用户重述背景，任务无法跨天续接 | Session + 提取式记忆 | 要建抽取链路与抽取质量监控 |
| 事实从"不变"到"会变" | 纯追加的 RAG 式记忆 | 新旧值并存且都会被召回，回答开始自相矛盾 | 带有效时间的提取式记忆 | 表结构要改、存量记忆要做时间回填与去重 |
| 单用户单 Agent → 多租户多 Agent | 应用层 WHERE 过滤 | 漏一处条件即跨租户泄露，且无法审计 | 存储分片键隔离 + 查询改写器 | 要重做分片键与索引，历史数据要重分布 |
| 从"记了就用" → 合规可删可导出 | 主表删除 | 向量与倒排索引里仍可检索到，删除不算完成 | 删除编排（全副本 + 全索引 + 台账） | 要梳理"记忆散布在哪些存储"，并给删除做幂等与补偿 |
| 单模态 → 多模态 | 纯文本记忆 | 图片、语音里的信息无法进入记忆 | 多模态嵌入 + 统一条目模型 | 嵌入模型、存储、检索都要换，且跨模态相似度需要校准 |
| 固定 top-k → 需要精确回忆 | 单路相似度召回 | 关键记忆常被相似但不相关的内容挤出 | 多路召回 + 重排（相似度 + 时间 + 重要性 + 置信度） | 要引入重排模型与离线评估集，延迟预算会变紧 |
| 单一 Agent 自用 → 团队共享记忆 | 每 Agent 各自建库 | 同一份用户事实被重复抽取，口径不一致 | 记忆做成平台化服务 + 显式作用域共享（跨 Agent 共享按 §5 属 L3：只记录，不假设跨 Agent 记忆一致；可先落地的只有作用域与写权限的显式化） | 要定义共享边界与写权限，接入方要改接口 |

一条经验判据：**当"用户说过的"与"系统记住的"开始反复不一致时，就该换模式了**——它说明记忆的写路径已经跟不上事实的变化速度，而不是检索或模型的问题。

### 3.7 自检清单

1. 记忆表里有没有"当前值"这个概念？同一主谓能否并存多条有效记录？能，就存在记忆冲突的结构基础。
2. 每条记忆是否带来源与置信度？用户说"我没说过这个"时，能否定位它是哪次抽取、由哪个模型产生的？
3. 记忆是否带时间戳或有效区间？能否回答"这条是多久以前的"？
4. 删除一个用户的全部记忆，需要操作几个存储？能否枚举完整？（枚举不出，说明删除不可能做完）
5. 删除请求是否会同步清理向量索引与倒排索引中的残片？只删主表即违反「强制记忆」的修法（主动遗忘 API 必须覆盖全部副本与索引）。
6. 检索的 top-k 是否会跨租户召回？作用域过滤写在应用层条件里，还是写在存储分片键与查询改写器里？
7. 注入 prompt 的记忆是否设了 token 预算？超预算时的裁剪规则是什么（按分数、按时间，还是按作用域）？
8. 记忆条目数的增长曲线是什么形状？有没有清理、合并与衰减在跑？
9. 是否存在"同一事实被写成多个实体节点"的情况？图谱的实体消解准确率是多少？
10. 情景记忆里是否保留了当时的中间状态（召回候选、工具参数、模型与 prompt 版本）？只留输入输出则无法复盘。
11. 低置信度的推断类记忆，是否被标注为"推断"而不是与用户亲述同权？读路径会不会区分二者？
12. 有没有一个用户可见的记忆入口（查看 / 编辑 / 删除 / 关闭）？没有，则合规与信任都无从谈起。

这份清单里，2、4、5、6 属于"结构性问题"：答错了不是优化不够，而是存储布局需要改；其余属于治理问题，可以靠流程与监控逐步补齐。**先修结构，再补治理**——反过来做，治理动作会在一个不支持隔离与删除的结构上反复失败。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 记忆只需活过一次会话 | Session Memory（KV + TTL） | 键与会话同粒度，读写退化为点查与追加，运维面近零 |
| 事实会变、且要回答"当前值" | 提取式（有效时间 + 冲突解决） | 更新发生在写路径，读路径才不需要自己判断新旧 |
| 上下文装不下、任务又很长 | MemGPT 分页 | 换页由模型按当前任务决定，不必预先知道哪些记忆将来有用 |
| 查询需要多跳关系 | 知识图谱记忆 | 关系被显式建模才能遍历，相似度无法表达"和谁有关" |
| 要复盘与举证 | Episodic（含中间状态） | 只有保留下当时的系统状态，才能定位决策的分叉点 |
| 覆盖广、不要求精确 | Vector RAG 记忆 | 存原文不引入抽取失真，代价是无结构、无时间 |
| 合规要求可删除 / 可导出 | 混合模式 + 删除编排 | 记忆散布多处，删除必须一次覆盖全部副本 |
| 多租户与多 Agent 协作 | 存储分片键隔离 + 显式作用域 | 隔离只有写进物理布局，才不依赖每个查询的自觉 |

> 本节小结：本主题下决定模式选择的**唯一那条最前置的约束，是记忆要跨越的边界**——会话内、会话之间、还是事件之间。它一确定，存储形态就基本被锁死：会话内只需 KV 加 TTL，跨会话必须做抽取或建关系，跨事件必须留过程；其余约束（时效性、写入通道、检索预算、隔离与删除义务）都是在选定边界之后做的二次筛选。也因此，选型的第一问不是"哪个记忆框架更好"，而是"我的记忆真正需要跨越哪几条边界"。
>
> 💡 **思考锚点**：数一下你自己那条记忆链路：同一主谓能不能并存多条有效记录、删除一个用户要操作几个存储（§3.7 第 1、4 条）？这两问答不上来时，你缺的是治理流程还是存储布局——本节说结构性问题要先修结构再补治理，你打算从哪一类动手？
