## 4. 工程实现

[§ 3](01-long-term-memory-section-3-sec3.md) 回答的是「记忆要跨越哪几条边界、每种形态被什么约束逼出来、在什么条件下反转」。本节接着往下走一步：**在形态已经选定之后，把它装进一个正在跑的生产系统要按什么顺序做、每一步怎么在线上确认做对了、什么信号说明这套记忆其实已经坏了。**

两类读者起点不同，读法也不同：**4.1–4.3 与 4.5 对两类读者同时有效**（顺序与判据相同，只有规模阈值不同）；**4.4 专给存量系统**——已经在跑的 Agent 没有记忆层，或者只有一个被当成记忆用的文档向量库。从零搭建的读者可以从 4.1 的顺序做下来；存量系统的读者应当先读 4.4 的第 ① 步（只加会话缓存，一次上线即可见效，且可原样回退），再回到 4.1 补齐写路径与删除编排。

### 4.1 落地步骤

五个步骤的依赖是单向的：**边界与删除义务 → 形态与写入通道 → 存储与检索 → 接上运行时 → 遗忘、审计与监控**。顺序不能换，原因集中在一点：**删除义务必须在第一次写入之前定义**，否则第一次写入之后，你要先补一套跨存储的删除编排，才能让已经存在的记忆符合要求。

**Step 1：定边界、作用域与删除义务（1–2 周，随合规要求变【经验】）**

1. **写清记忆要跨越的边界**：会话内 / 会话之间 / 事件之间——[§ 3.1](01-long-term-memory-section-3-sec3.md) 定义的那三条边界，也正是决定存储形态的那条约束。跨设备、跨用户复用同一份记忆不属于边界，它落在第 2 项的作用域上（[§ 3.3](01-long-term-memory-section-3-sec3.md) 的「跨设备 / 跨平台」一行），两者不要混在一张清单里数。
2. **写清作用域**：个人 / 团队 / 项目 / Agent，并明确作用域标签要落进**存储的分片键**，而不是只写在应用层的查询条件里。
3. **写清删除与导出义务**：用户能否查看、编辑、删除、导出；删除请求要覆盖哪几处存储（缓存 / 向量索引 / 关系库 / 图库 / 归档）；一次删除的完成标准是什么。
4. **列出所有会持有记忆的存储**，包括日志与备份。这一步的产物是后续删除编排的输入——枚举不出的地方，就是将来删不干净的地方。

- **产物**：边界与作用域定义（一页）、删除义务清单（存储 → 副本 → 清理方式 → 校验方法）、作用域分片键设计。
- **判据**：拿一个真实用户，问「删掉他的全部记忆要操作几个存储、由谁执行、怎么验证删干净了」。答不出完整清单，说明第 ④ 项没做完；答出但清单里没有向量索引与倒排索引，说明只想到了主表。
- **为什么必须这一步、为什么在最前**：删除与隔离是**布局问题**，不是流程问题。它们要写进分片键与索引结构，事后用应用层代码补，代价是重建索引与重分布历史数据（[§ 3.6](01-long-term-memory-section-3-sec3.md) 的跃迁代价就是这么来的）。先写后补，补的是整个存储。

**Step 2：选形态、定写入通道（1–2 周，与 Step 1 可部分并行【经验】）**

1. **按边界选形态**，不按「哪个框架更火」选：会话内 → Session Memory（KV + TTL）；跨会话的稳定事实 → 提取式；跨会话的关系 → 图谱；跨事件的过程 → 情景记忆（对照表见 [§ 3.3](01-long-term-memory-section-3-sec3.md)）。
2. **定写入通道由谁决定**：用户显式声明 / 模型抽取 / 行为推断。这一条决定记忆准确率的**上限**——抽取由模型决定「记什么」，上限就是抽取器的准确率。
3. **定冲突解决策略**：同一主谓能否并存多条？以「最近更新优先」还是「来源优先级优先」？用户亲述与模型推断谁覆盖谁。
4. **定重要性函数与阈值**：哪些记忆值得长期保留（`f: E → [0, 1]`），低于阈值的入 ttl 队列而不是长期库。

- **产物**：形态选择说明（约束 → 形态 → 为什么不选另一个）、写入通道定义、冲突解决规则、重要性阈值。
- **判据**：把一个真实业务问题走一遍——「用户改过地址之后，系统会不会用旧地址回答」。走得通，说明冲突解决落在写路径；走不通（要靠读路径判断新旧），说明第 3 项还停留在口头。
- **为什么必须这一步**：写入通道决定了整套系统的上限，而它是三件事里唯一**无法在运行时观察出来**的——检索慢可以优化、成本高可以降级，但「抽取器把玩笑写成了事实」在线上表现为「答得挺对，偶尔不对」，没有可观测的信号（[§ 3.2.4](01-long-term-memory-section-3-sec3.md) 的失效点）。

**Step 3：落存储与检索 API（2–4 周，随需接入的存储种类数与检索 API 调用方数量变【经验】）**

1. **按数据形态分居存储**：向量 → 向量库；事实与关系 → 关系库 / 图库；原始事件 → 列存或对象存储；热会话 → 缓存（物理选择参照主文件 §2.5.4）。
2. **检索 API 固定为 `search(query, scope, budget) → top-k`**：入参必须带作用域与 token 预算，不能只有 query。
3. **检索必须可解释**：返回结果里带相似度、时间、重要性、置信度、访问频次五个分量（与主文件 §2.2 的 `w1–w5` 一一对应），否则线上无法判断「这条为什么被召回」。
4. **建立离线评估集**：准备一批「该召回哪条」的问题，作为后续调权重的回归基线。

- **产物**：存储选型与分片方案、检索 API 契约（见 4.5 模板 1）、打分函数配置（见 4.5 模板 4）、离线评估集与基线分数。
- **判据**：跑一次评估集，检查 (a) 关键记忆是否出现在 top-k 内；(b) 把 top-k 从 5 调到 20，结果里是否出现跨作用域的条目（出现即隔离有漏洞）；(c) 单次检索的分量是否能逐项打印出来。
- **为什么必须这一步、为什么排在接框架之前**：检索 API 的入参决定了上层的写法。如果先接框架、再补作用域参数，框架内已经写死的调用点要逐个改；而带预算与作用域的签名一旦固定，接入方只能在合法范围内使用记忆，越界在接口层就被挡住。

**Step 4：接上 Agent 运行时（1–2 周，随框架既有 Memory / Checkpoint 抽象与写路径挂载点的匹配度变【经验】）**

1. **接入框架的 Memory / Checkpoint 模块**（LangChain Memory、LangGraph Checkpoint、AutoGen Memory 一类），先跑通「一个会话内不丢上下文」。
2. **把写路径挂在会话结束或消息落库之后**，不阻塞推理路径——写可以异步、可以重试，读不能。
3. **给读路径设 token 预算**：注入 prompt 的记忆不能无限增长，超预算时按打分量截断，而不是按时间截断。
4. **把来源与作用域标签注入 prompt**：每一条被注入的记忆都要带「来自哪里、属于谁」，这既是模型判断的依据，也是线上排障的抓手。

- **产物**：接入层代码与配置、写路径的异步任务定义、注入 prompt 的拼装函数、读路径的预算与截断规则。
- **判据**：(a) 关掉记忆读取后，Agent 的行为差异是否可复现（能复现说明记忆真的在起作用，而不是模型自己在猜）；(b) 打印一次完整 prompt，检查注入的记忆总量是否在预算内、是否条条带来源。
- **为什么必须这一步**：它是唯一能验证前两步是否成立的环节——存储再漂亮，如果注入 prompt 的路径没接上，用户侧行为不会有任何变化；反过来，它也最容易把问题暴露出来：一旦注入量不受控，token 成本与延迟会先于效果亮红灯。

**Step 5：遗忘、审计与监控（持续，首版 2–3 周，随合规范围与审计留存要求变【经验】）**

1. **加入遗忘机制**：主动删除（消失）与保留期上界是必做项；时间衰减（降权）按 §5.1 属 L3——只做上界，不假设衰减能自动分出好坏、不做核心依赖（见 [§5 前沿演进](01-long-term-memory-section-5-ai.md)）。二者不可互替。
2. **写入 / 读取审计**：每一笔记忆的写入时间、来源会话、提取模型版本、被读取次数都要可查。
3. **监控三项指标**：记忆准确率（抽样确认）、检索命中率（评估集回归）、成本（条目数 × 平均注入 token）。
4. **提供用户可见的记忆入口**：查看 / 编辑 / 删除 / 关闭四项能力齐备，且逐条显示「这条是什么时候记住的」。

- **产物**：衰减与删除任务、审计日志表、监控看板、用户侧记忆管理页。
- **判据**：(a) 发起一次真实删除请求，端到端走完并**在检索侧验证召回不到**；(b) 抽 20 条记忆核对真伪，记录确认为真的比例；(c) 打开记忆管理页，看能否删掉一条而只删它一条。
- **为什么必须放在最后但必须做**：前四步都在让记忆「变得有用」，这一步在让记忆「变得可信」。缺了它，系统仍能跑，但一旦用户发现删不掉、或者发现系统记错了东西，前面所有投入的信任额度会被一次性收回。

**分阶段对照**（同一套动作在不同规模下的重点不同）：

| 阶段 | 目标 | 关键产出 | 典型周期 |
| --- | --- | --- | --- |
| 0→1 | 跑通最小记忆闭环 | Session Memory（KV + TTL）+ 抽取 prompt | 1–2 周【经验】，随现有缓存设施的可复用度变 |
| 1→10 | 接入结构化记忆 | 提取式事实条目 + 向量库（Mem0 / Zep / 向量库一类） | 1–2 个月【经验】，随要接入的记忆形态数与历史回灌范围变 |
| 10→100 | 自研 + 合规 + 监控 | 自研记忆层 + 图谱 + 遗忘 + 审计 | 半年以上【经验】，随合规范围变 |

**最常被跳过的是 Step 1 的第 ④ 项与 Step 2 的第 2 项**——「列全存储」和「写清写入通道」，两者都不产出用户可见的功能。跳过后第一个出问题的时点通常落在**第一次真实删除请求**（受监管业务里快的话首个季度内【经验，随删除请求的到达频率变】）：这时才发现记忆同时落在缓存、向量库、关系库和归档里，而删除脚本只覆盖了主表，检索侧仍能召回残片；紧接着第二个问题是「这条错误记忆到底是谁写进去的」——因为没有记录写入通道与提取模型版本，追不到源头。

### 4.2 关键技术点

**1. 记忆提取**

- **做法**：LLM 从对话中抽取实体、关系、属性、事件，输出受 schema 强约束的条目（`subject / predicate / object / fact_text / confidence / source`）；prompt 里显式禁止把假设、玩笑、假设性提问写成事实。
- **机制**：读路径默认记忆为真，所以**整套系统的准确率上限就是抽取器的准确率**——抽取环节的失真会在下游被放大，而不是被平均掉。
- **失效条件**：当抽取器开始把条件句与假设句写成既定事实时，提取式记忆从「自动、智能」反转成「自动化地产生并长期保留错误」。**症状**：用户说「我没说过这个」；观测信号是低置信度条目占比与用户否认率同步上升。
- **档位**：【经验】。

**2. 记忆存储（向量 + 关系 + 时间戳）**

- **做法**：同一批输入按形态分居写入；写入路径异步、可重试；每条记忆带 `created_at / updated_at / valid_from / valid_to / source`。
- **机制**：一份记忆写进多处时，**「写」是容易的，「删」是难的**——写可以异步、可以失败重试，删必须一次覆盖全部副本。因此存储布局的第一约束不是吞吐，而是「删除能否被枚举」。
- **失效条件**：当新增第四处存储（例如为混合检索加一套倒排索引）而删除任务清单没有同步更新时，删除从「完成」变成「看起来完成」。**症状**：删除接口返回成功，但用该用户的关键词检索仍能召回内容。
- **档位**：【经验】。

**3. 记忆检索（相似度 + 时间衰减 + 重要性 + 置信度 + 访问频次，加权后重排）**

- **做法**：按主文件 §2.2 的评分函数取分量（相似度 + 时间衰减 + 重要性 + 置信度 + 访问频次），归一化后取 top-k 并做重排；权重按离线评估集调，不按手感调。
- **机制**：**top-k 永远返回 k 条**，哪怕只有一条相关——所以噪声会与条目数同向增长，必须靠加分项与重排制造区分度，否则「记得越多、召回越差」。
- **失效条件**：当条目数增长而权重长期不动时，关键记忆被相似但不相关的内容挤出。**症状**：用户需要的记忆确实在库里，但不在召回集里——这类故障在线上看不出来，只能靠离线评估集检出。
- **档位**：【经验】（分值权重与 k 的取值区间，按语料规模与评估集定）。

**4. 记忆压缩**

- **做法**：对长历史定期做摘要压缩，把「过去 N 条对话」压成「若干条要点」，压缩比由注入 prompt 的 token 预算倒推。
- **机制**：摘要**不可逆**——被压掉的信息不是被「记住得少一点」，而是消失了。因此压缩只能用在「未来仍需知道、但不需要逐字复现」的内容上。
- **失效条件**：当压缩任务积压或失败重试无告警时，压缩比失控，被压掉的可能恰好是唯一证据。**症状**：能回答「用户大致关心什么」，但回答不了「上次具体是哪个订单出的问题」。
- **档位**：【经验】。

**5. 记忆遗忘（时间衰减 + 用户主动删除）**

- **做法**：时间衰减做降权，主动删除做消失；删除走编排（全副本 + 全索引 + 台账），并支持导出。
- **机制**：时间衰减解决的是「旧的不该和新的一样重」，删除解决的是「它不该再存在」——**两者是不同性质的动作，不可互替**。只做衰减，合规义务不满足；只做删除，成本与噪声持续上涨。
- **失效条件**：当删除只覆盖主表、或删除任务不是幂等时，重试会造成部分副本已删、部分未删。**症状**：同一用户在不同入口看到不同的检索结果。
- **档位**：【经验】（保留期取值区间，按合规与业务定）。

**6. 记忆冲突解决（版本号 / 有效时间 / 来源优先级）**

- **做法**：用唯一索引约束「当前值」（如 `WHERE valid_to IS NULL`），把冲突解决放在写路径；来源优先级显式定义（用户亲述 > 用户确认过的推断 > 模型推断）；旧值失效而非删除，保留可追溯性。
- **机制**：只要允许同一主谓并存多条，「取哪条」就变成读路径的随机性——而**读路径不具备裁判所需的上下文**，它看到的只是若干条都像真的记录。
- **失效条件**：当「最近更新优先」被无条件执行时，模型推断会覆盖用户亲述（推断的发生频率天然更高）。**症状**：用户明确改过的偏好被「推断值」顶掉；这类问题不会报错，只会让用户觉得系统「自作主张」。
- **档位**：【经验】。

**7. 记忆隔离（作用域标签 + 存储分片键）**

- **做法**：作用域写进分片键与索引结构；查询经改写器强制注入作用域过滤；缺失作用域条件的查询在接口层直接拒绝。
- **机制**：应用层 `WHERE` 过滤的错误概率随查询点数线性增长，而**一次漏写就是一次跨租户泄露**——其余查询的正确性无法补偿它（[§ 3.5](01-long-term-memory-section-3-sec3.md) 把这一条列为唯一会造成不可逆后果的反模式）。
- **失效条件**：在混合形态下，读路径上的每一路召回（当前会话 / 用户画像 / 关系推理 / 过程复盘 / 外部知识）各写各的过滤条件，只要一条漏了就整体失效。**症状**：没有任何异常日志，只有越权召回。
- **档位**：【经验】。

**8. 记忆去重**

- **做法**：写入前按相似度阈值合并重复事实；阈值按业务调，并保留「合并来源」以便回溯。
- **机制**：合并是**有损**的——两条独立事实被误并之后，原始的两条不再存在，纠正需要人工。因此阈值宁可偏高（漏并后再补），不要偏低头。
- **失效条件**：当业务引入新实体类型（人名、产品名、缩写）而阈值沿用旧值时，误并率上升。**症状**：用户抱怨「系统把两件事混成一件」。
- **档位**：【经验】（相似度阈值的量级，随实体类型的混淆程度与写入量变）。

**9. 记忆血缘**

- **做法**：每条记忆记录来源会话、写入时间、提取模型与 prompt 版本、以及它由哪一条用户消息产生。
- **机制**：读路径默认记忆为真，所以**可追溯性是唯一的纠错入口**——用户否认时，能定位到具体抽取、才能判断是抽取错了还是用户记错了，也才能回滚同一批错误。
- **失效条件**：当提取模型换版本而未回填版本字段时，新旧两批记忆无法区分，回滚不能按批次执行。**症状**：明知某批记忆有问题，却只能逐条人工核对。
- **档位**：【经验】。

**10. 记忆冷热分层**

- **做法**：热数据（当前会话、活跃用户画像）放缓存、向量库与关系库；冷数据（历史事件、归档对话）放对象存储 + 离线索引；迁移与回捞策略显式定义。
- **机制**：命中分布决定成本，**所以冷热的分界应该按访问频次划，而不是按时间划**——按时间迁移会把「很久没访问但下次一定要用」的记忆（合规相关、事故复盘相关）移出在线路径。
- **失效条件**：当分层按日期批量执行时，在线路径的召回集出现空洞，回捞又来不及。**症状**：检索延迟长尾变长，且长尾集中在特定时间段的用户上。
- **档位**：【经验】。

### 4.3 工具链与平台

工具按「要解决哪一环」选，每一环都要能回答「在什么约束下选它、不选它要付什么代价」：

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 专用记忆框架 | Mem0、Letta（前身 MemGPT）、Zep、MemoryBank、Cognee | 看它把哪条约束做成一等公民：写入通道（提取式）、上下文预算（分页式）、时间维度（时序事实）、存储成本（压缩式）、关系推理（图谱混合）。记忆边界一变，首选框架随之变 | 框架的默认抽象与业务边界不一致时，要么绕开框架自己实现，要么把业务削足适履；后者的症状是「记忆总是差一点」 |
| 向量数据库 | Milvus、Qdrant、Weaviate、Pinecone、pgvector | 已有 PostgreSQL 且向量规模不大（十万级以下【经验】）优先 pgvector，少一套运维与一致性；需要独立扩缩容、多路过滤或亿级规模再上独立库 | 独立库多一套备份、权限与一致性协调成本；反过来，pgvector 在向量量级与索引构建内存上会成为瓶颈，迁移要重算全量向量 |
| 知识图谱 | Neo4j、NebulaGraph、Apache Jena、Oxigraph | 查询是否**真的**需要多跳（「和我同项目的人最近在问什么」）。属性图实现偏工程、RDF 系实现偏标准与推理；嵌库形态适合单机小规模 | 用不上多跳时，图谱只是更贵的表；而实体链接不做好，图会「看起来连通、实际断裂」（[§ 3.2.5](01-long-term-memory-section-3-sec3.md)） |
| Agent 框架 Memory 模块 | LangChain Memory、LangGraph Checkpoint、AutoGen Memory | 记忆是否需要跨进程、跨框架、跨版本复用。流程编排为主、需要状态快照时用 Checkpoint；记忆需要独立演进时不要让框架持有存储 | 记忆与框架生命周期绑定，换框架或升级版本时要迁移历史状态；隔离与删除也只能在框架能表达的范围里做 |
| 缓存 / Session | Redis、DragonflyDB、Memcached | 需要 TTL 语义、数据结构与持久化可选时用 Redis 系；纯字符串缓存、无过期语义需求时 Memcached 更省 | 缓存没有 TTL 语义时，「失忆」要靠应用层实现；而有 TTL 的缓存不能当长期存储用，两者混用会造成「有时记得、有时不记得」 |
| 评估工具 | Langfuse、Helicone、Arize Phoenix、Mem0 Evals（Mem0 开源项目随论文发布的评测框架，论文 arXiv 2504.19413，2025-04 提交，见 [§ 8](01-long-term-memory-section-8-sec8.md)） | 判据只有一个：能否把「召回对不对」变成可回归的指标（评估集 + 分数 + 版本对比） | 没有评估集就无法判断一次权重调整或换模型是变好还是变坏，所有优化都变成手感 |
| Embedding 模型 | OpenAI text-embedding-3-large、BGE-M3、Cohere embed-v3 | 按语言覆盖、维度预算、是否需要自托管（数据不出域）选；**换模型要重算全量向量**，所以先定「能不能接受一次全量重算」 | 中途换模型而不重算，新旧向量不可比，召回质量静默下降；需自托管却选了纯 API 方案，会在合规评审时被整体推翻 |
| 重排模型 | Cohere Rerank、BGE Reranker | 判据是有没有延迟预算余量：重排能显著提升 top-k 精度，但会给每次检索加一跳 | 不做重排时，只能靠调相似度阈值硬扛噪声，而阈值调高会漏召回 |

六条专用框架路线把不同的约束做成了第一等公民，选型时对着看：

| 路线 | 记忆形态 | 它把哪条约束做成一等公民 | 什么条件下不要选它 |
| --- | --- | --- | --- |
| Mem0 | 提取式记忆（自动 ADD / UPDATE / DELETE） | 写入通道：由模型决定记什么 | 需要逐字复现历史过程时——事实条目丢掉了过程 |
| Letta（前身 MemGPT） | 分页式记忆（Core / Archival 换页） | 上下文预算：把上下文当物理内存 | 需要确定性召回时——换页由模型判断，会静默丢掉它看不见的东西 |
| Zep | 时序事实 | 时间维度：事实带有效时间与衰减 | 事实本身不随时间变化、且写入量极大时，时序开销是纯成本 |
| MemoryBank | 压缩式记忆（以遗忘曲线为蓝本做衰减） | 存储与 token 成本 | 需要精确回忆某次事件时——压缩不可逆 |
| Cognee | 图谱 + 向量混合 | 关系推理与事实抽取的融合 | 查询里没有多跳需求时，图谱部分是额外的工程与写入成本 |
| LangGraph Checkpoint | Agent 状态快照 | 工程化编排：状态可恢复、可重放 | 需要跨框架、跨业务共享同一份用户记忆时——它管的是流程状态，不是用户画像 |

**什么时候自研记忆层（10→100 阶段）**：当通用框架在四件事上同时不够用时——**合规要求在指定区域内存储与删除、记忆需要跨多个 Agent 与框架共享、写入通道需要业务自定义的冲突规则、以及需要把记忆作为独立服务对外提供**。自研的形态是把记忆做成一个独立服务，运行时通过 Memory API 读写：

```text
┌────────────────────────────────────────────────────┐
│                  Agent Runtime                      │
│   (LangGraph / AutoGen / 自研)                       │
└─────────────────────┬───────────────────────────────┘
                      │ Memory API (read / write / search / forget)
┌─────────────────────▼───────────────────────────────┐
│              Memory Layer (自研)                      │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  │
│  │  Extraction │  │   Storage   │  │  Retrieval  │  │
│  │  Pipeline   │  │   Layer     │  │   Engine    │  │
│  └─────────────┘  └─────────────┘  └─────────────┘  │
└─────────────────────┬───────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────┐
│         Vector DB + KG + KV + Cold Storage           │
│  Milvus / Neo4j / Postgres / S3                      │
└─────────────────────────────────────────────────────┘
```

自研记忆层的六个模块与职责：

| 模块 | 职责 | 关键技术点 |
| --- | --- | --- |
| Extraction | 从对话提取事实 | LLM + schema 强约束（含 `confidence` / `source`） |
| Storage | 多形态存储 | 向量 + 关系 + 时序；分片键带作用域 |
| Retrieval | 混合检索 | 向量 + 关键词 + 图谱多路召回 + 重排 |
| Importance | 重要性评分 | LLM 评分 + 行为反馈（访问频次） |
| Forgetting | 主动遗忘 | 时间衰减 + 删除编排（全副本 + 全索引 + 台账） |
| Audit | 审计日志 | 写入与读取全量留痕，可按用户与批次回查 |

**这一列里最容易被误选的是「向量数据库」。** 它最容易被当成「记忆系统」整体购入，因为从演示上看，把对话塞进向量库、按相似度召回，效果立竿见影。误选的根本原因不是检索质量，而是**向量库不提供三样东西**：当前值的概念（同一事实的旧值与新值在向量空间里几乎不可区分）、写入通道的治理（它不判断什么该记）、删除编排（删主表不等于删索引）。误选的典型后果是**延迟暴露且难以回退**：这套选型在演示期的表现掩盖了写路径的缺口，等到缺口显形时记忆已经写进主链路，换掉它的成本是把已沉淀的对话重新抽取一遍（症状与反转条件见 [§ 3.3](01-long-term-memory-section-3-sec3.md)）。判断方法只有一句：问它能不能回答「这个偏好的当前值是什么、什么时候改的、改之前是什么」。

### 4.4 存量迁移

已经在跑的 Agent 系统，起点通常有三类：**①无状态 Agent**（只有上下文窗口）；**②有会话缓存但无跨会话记忆**；**③有向量库做文档 RAG，并被当成记忆用**。三类的迁移路径不同，但第一步相同。

**① 先做一件立刻见效且可回退的事：把会话记忆补上**

加一层 Session Memory（`session_id` / `thread_id` 为键的 KV + TTL），不做抽取、不改 schema、不回灌历史。

- **为什么先做它**：零 schema 变更、零回灌、零新增向量成本；一次上线即可让同一会话跨工具调用不丢上下文，收益当天可感。
- **可回退性**：摘掉缓存读取路径，业务回到原状——数据在 TTL 内自然过期，不留下需要清理的半成品。
- **判据**：同一会话进行到第 10 轮时，模型仍能答出第 1 轮给出的硬约束（例如「只统计已支付订单」）；关掉缓存后该能力消失。两次对比即完成验证，不需要评估集。

**② 历史资产分三类处理，不返工**

判断依据不是「有多少数据」，而是三件事：**删除义务是否覆盖得住、抽取成本是否可接受、历史语料质量是否可判**。

| 类别 | 判定 | 处理 | 理由 |
| --- | --- | --- | --- |
| 回灌抽取 | 有明确的授权 / 合规依据，语料质量可判，且用户可见与可删的能力已上线 | 全量抽取入长期记忆 | 历史偏好是最有价值的冷启动数据 |
| 只回灌近窗口 | 活跃用户、近若干个月【经验】的对话 | 分批抽取，其余留档 | 更早的偏好多数已失效，抽取成本换不回收益 |
| 打标不回灌 | 其余历史对话（含测试、无效轮次、来源不明的导入） | 归档并登记存在性与访问路径，**不进检索索引** | 归档的意义是让「不处理」变成决定；不回灌则不进删除义务范围 |

**原则：先算删除成本，再算回灌成本。** 回灌进去的每一条都进入删除义务范围——回灌 3 个月还是 3 年，最终差别体现在一次删除请求要覆盖多少条、多少存储。同时，回灌必须与**记忆清单页**一起上线（逐条查看、编辑、删除，并标注来源），否则回灌会把「系统背着我记东西」的信任问题放大。

**③ 双轨怎么维持**

无记忆路径与记忆路径并行，对照口径固定为三项：**同一批问题的答案一致性、用户否认率、检索延迟与注入 token**。三项都要在切换前有基线，否则切换后无法归因。

- **维持时长**：至少覆盖一个完整业务周期（含低峰与高峰各一次），通常在一个季度以上【经验】。
- **双轨期最容易出事的是删除请求**：用户在记忆路径上删掉一条之后，旧路径仍可能从历史对话里带出同一条信息。所以双轨的**第一天**就要把删除请求同时打到两条路径，并做一次端到端演练——这项演练放在切换前做，成本最低。

**④ 什么信号说明可以退出双轨**

三条同时满足才切断旧路径：

1. 抽 20 条记忆核对真伪，确认为真的比例稳定在一个可接受区间【经验】——低于区间就先修抽取，不要先切路径；
2. 删除请求端到端演练成功至少一次，且校验覆盖了向量索引与倒排索引中的残片（不是只删主表）；
3. 注入 prompt 的记忆 token 不超预算，且检索 P99 在延迟预算内。

三条缺一时强行切换的后果是**用户体感「记忆时好时坏」，且无法归因**——因为两条路径的差异没有被对照口径固定下来，最后只能全量回滚。

**存量改造里最容易犯的错，是先回灌再说。** 回灌最容易立项、看起来最像进展，但它同时做两件不可逆的事：把未经复核的错误事实赋予与用户亲述同等的权重，以及让删除义务从回灌完成那一刻起立即生效。正确顺序是：**先跑通会话内记忆与删除编排，再决定回灌的范围与深度**。

### 4.5 模板 / 示例

**模板 1：记忆 API 契约（四个动作）**

| 动作 | 入参（必带项） | 必须带回 | 为什么 |
| --- | --- | --- | --- |
| `write` | 作用域、来源会话、抽取模型版本、`confidence`、`source` | 写入结果 + 冲突处置（新增 / 更新 / 合并 / 忽略） | 冲突处置要可见，否则「为什么这条没记上」无法回答 |
| `search` | query、作用域、召回预算（top-k + token 上限） | 条目 + 五分量分数（相似度 / 时间 / 重要性 / 置信度 / 访问频次） | 分数是线上排障与调权的唯一抓手 |
| `forget` | 作用域、时间范围或条目 id、幂等键 | 覆盖到的存储清单 + 各处结果 | 没有清单就无法判断「删干净了没有」 |
| `export` | 作用域、格式 | 可读的条目与来源 | 可携权与事故复盘都依赖它 |

**怎么用**：作用域是必填项，不要设计成可选——可选参数最终会被漏传，而漏传的后果是跨作用域召回。`search` 的预算是给调用方设的上限，不是建议值，超预算时由服务端截断而不是由调用方自觉。

**模板 2：记忆抽取 Prompt（schema 强约束）**

```text
你是记忆抽取器。从下面这段对话中抽取值得长期保留的事实，只输出 JSON 数组。

规则：
1. 只抽取用户明确陈述或明确确认过的内容；推断出来的内容 source 标 "inferred"。
2. 不要抽取：假设性提问、玩笑、助手自己说的话、一次性的操作指令。
3. 每条包含：subject / predicate / object / fact_text / confidence(0-1) / source(user_msg|inferred) /
   valid_from（若对话里给了时间）
4. 找不出可长期保留的事实时返回空数组。宁少勿错。

对话：
{conversation}
```

**怎么用**：第 4 条「宁少勿错」是这段 prompt 里最不能删的一句——它把阈值从「能抽就抽」移到「不确定就不抽」。`source` 与 `confidence` 两项必须落库（对照 4.2 第 1 条），否则抽取质量无法度量。规则里的「助手自己说的话」要显式排除，否则模型会把上一轮的答复当成用户事实重新写回。

**模板 3：删除编排清单（每新增一处存储就加一行）**

| 存储 | 副本 / 索引 | 清理方式 | 幂等键 | 校验方法 |
| --- | --- | --- | --- | --- |
| 会话缓存 | 主从 + 持久化 | 按 key 精确删 | `user_id + request_id` | 读一次该 key，应为空 |
| 向量库 | 主索引 + 倒排索引 | 按 id 删 + 重建受影响分片 | 同上 | 用该用户关键词检索，应召回 0 条 |
| 关系库 | 主表 + 索引 | 事务内删除 | 同上 | 计数查询应为 0 |
| 归档 / 冷存 | 对象存储 + 离线索引 | 删除对象 + 重建离线索引 | 同上 | 离线检索应为空 |

**怎么用**：这张表的价值在于**它是会过期的**——每次给系统加一处存储或索引，就要加一行，否则删除会静默地只做一部分。校验方法一栏只接受「能自动执行的查询」，写「人工确认」的行视为未完成。幂等键每一项都必须相同，否则重试会产生重复任务，而重复任务在多副本场景下会造成部分删除、部分未删。

**模板 4：检索打分配置片段**

```yaml
retrieval:
  top_k: 8                  # 召回条数，按注入预算定，不按"记得越多越好"
  weights:
    similarity: 0.5
    recency: 0.2            # 时间衰减，半衰期按业务定
    importance: 0.2         # LLM 评出的重要性
    confidence: 0.05        # 提取置信度
    access: 0.05            # 访问频次（隐式反馈），历史被检索次数归一化后的值
  token_budget: 800         # 注入 prompt 的记忆上限
  truncation: by_score      # 超预算时按分数截断，不按时间
  scope_filter: enforced    # 作用域过滤由改写器强制注入，不可关闭
```

**怎么用**：五项权重之和要为 1，且不要照抄这五个数——先跑离线评估集拿到基线分，再逐项调。`top_k` 与 `token_budget` 要一起改：只调召回条数而不设 token 上限，长条目会把预算吃光。`scope_filter` 一栏在任何环境都不应改成 `optional`，它是隔离的唯一强制点。

**模板 5：四类框架的接入形态**

| 路线 | 接入形态 | 迁出时的注意事项 |
| --- | --- | --- |
| Mem0（提取式） | 在会话结束时调用写入，按 `user_id` 检索；抽取与冲突解决由框架完成 | 迁出时要带走事实条目与来源，不要只带走向量 |
| LangGraph Checkpoint（状态快照） | 编译图时挂 checkpointer，按 `thread_id` 持久化状态，多轮对话自动续接 | 它是流程状态，不是用户画像；迁出时不要把 checkpoint 当记忆库导出 |
| Letta（分页式） | Agent 持有记忆工具集，由模型在 Core 与 Archival 之间换入换出 | 迁出时要确认哪些内容曾长期停留在 Archival 而从未被换入，这些内容对模型是「不存在的」 |
| Zep（时序事实） | 会话消息写入后按 `session_id` 检索，返回事实并带时间戳与重要性 | 迁出时保留时间戳与有效区间，否则新旧值会重新变成并列关系 |

**怎么用**：这张表只描述接入形态，具体的客户端方法与参数名以各项目官方文档的当前版本为准——这类 SDK 迭代较快，按「项目名 + memory」检索官方文档核对即可。选型时先看「接入形态」这一列与你的会话结束时机是否对得上；对不上时通常需要自己包一层，而这一层要写进 4.3 的选型记录里。

### 4.6 成本：这套东西的账单

三项里真正相关的是**人力**与**云账单**；硬件可以忽略——记忆库的量级远小于数仓。它的成本结构由一条性质决定：**记忆是「越用越贵」的**，每写一条就永久增加检索与注入的负担。

- **注入 token（主成本）**：每次检索都把 top-k 条记忆拼进 prompt，成本 ≈ `每请求注入 token × 请求量 × 模型单价`【推算】。§4.1 Step 5 第 3 条已把它列为三项监控之一（条目数 × 平均注入 token），这一项随记忆条数单调上涨，所以「记得越多」不是免费的。
- **提取成本**：每次会话结束做一次 LLM 抽取，单次便宜，但按会话量线性放大【经验】；离线回灌是一次性的大头（全量对话 × 抽取 token）。
- **存储**：向量库 / 对象存储的账单在本主题里占比很小【经验】——记忆条数通常远小于文档 RAG 的语料。**这个主题不贵在存储，贵在每次检索的注入与每次写入的抽取**，即贵在「动作」而非「资产」。
- **人力**：集中在 Step 1 的删除义务与 Step 2 的写入通道（以「周–月」计，见 §4.1 各步【经验】），因为这两件是布局问题，事后返工要重建索引与重分布历史。

通用的 FinOps 方法见 [11-cross-cutting/03 数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)；本节要说的是它在本主题里落成「按次」而非「按量」。

### 4.7 容灾与故障演练

本主题的失效形态与存储类主题不同：**坏掉的往往不是「读不到」，而是「读到错的」或「删不掉」**——这是三个不同的方向。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 抽取器把玩笑 / 条件句写成事实 | 长期且静默：读路径默认记忆为真（§4.2 第 1 条） | 按来源与批次回滚错误条目 | 抽 20 条核对真伪（§4.1 Step 5 判据 (b)；§4.9 第 9 条） | 越晚发现越贵；回滚依赖血缘（§4.2 第 9 条） |
| 检索侧不可用 | 所有跨会话记忆注入失效 | 退回无记忆路径（模型只能靠上下文猜） | 关掉记忆读取路径，看行为差异能否复现（§4.1 Step 4 判据） | 秒–分钟级【经验】 |
| 删除删不干净（漏一处索引 / 副本） | 合规风险，且不可逆 | 无有效降级——只能事前把清单列全 | 发起真实删除，用关键词在向量索引与倒排索引两侧验零（§4.5 模板 3） | 删除只有「完成 / 未完成」，没有部分恢复 |
| 写入通道中断（抽取不可用） | 新记忆丢失 | 排队重试，原始会话先存档待补抽取 | 停掉抽取服务，看写入是否阻塞推理路径 | RPO 取决于会话原文是否留档【经验】 |

**两个不能照搬通用容灾的地方**：其一，**跨地域多活在这里不是主要问题**——记忆不是可重建的派生数据（§3.4 与 §4.2 第 1 条都强调写错了没有第二道防线），丢掉一段用户亲述无法从别处重算，所以 RPO 不能像派生数据那样放松，这一点要多机房副本之外的「原文留存」来兜；其二，**删除演练本身就是容灾演练**——一次删除请求要覆盖缓存 / 向量 / 关系 / 归档，任一存储来不及恢复，删除就算不上「完成」（§4.5 模板 3）。通用容灾编排见 [Ch12 §07 容灾](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)，注入式故障演练见 [Ch12 §06 混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)。

### 4.8 演进路线：0 → 1 → 100

§4.1 的「分阶段对照」已给出三个阶段的目标与产出，本节只补它没说的一句——**每个阶段变贵的是什么、先坏的是什么**。

| 阶段 | 先坏的是什么 | 变贵的是什么 |
| --- | --- | --- |
| 0 → 1 | 会话一长就丢上下文（无跨会话记忆） | 便宜：一层 KV + TTL，复用既有缓存设施，不给 token 账单加项 |
| 1 → 100 | **准确率上限**：抽取器把玩笑 / 条件句写成事实，且在运行时观察不到（§4.2 第 1 条） | **注入 token 与噪声**：top-k 永远返回 k 条，条目越多噪声越多（§4.2 第 3 条） |
| 100 → | **删除与隔离的覆盖面**：每加一处存储 / 索引，删除清单就多一个漏点（§4.2 第 2、7 条）；一次漏写就是不可逆泄露 | **治理人力**：合规要求的区域性存储与删除、跨 Agent 共享、自定义冲突规则——这才逼出自研记忆层（§4.3；其中**跨 Agent 共享按 §5 属 L3：只记录，不假设跨 Agent 记忆一致**） |

**这个主题的演进是反直觉的**：前两个阶段在让记忆「变得有用」（记得更多、召回更准），第三个阶段全在让记忆「变得可控」（删得掉、隔离得住、可追溯）。成本重心也随之下移——从「推模型 / 写抽取」（0→1）挪到「每次检索的注入 token」（1→100），最后挪到「治理与合规」（100→）。若按「先把记忆做厚」的直觉推进，会在 1→100 就撞上噪声与成本，而 100→ 的删除义务早在那之前就已经生效了。

### 4.9 自检清单

**结构层面的判定**——记忆表里有没有「当前值」概念、作用域过滤写在存储分片键还是写在每个查询的 `WHERE` 里、条目数的增长曲线是什么形状——在 [§ 3.7](01-long-term-memory-section-3-sec3.md) 的自检清单里，本节不重复：那几条答错，意味着存储布局要改，而不是优化不够。本节列的是**装进存量系统之后**的检查动作，每一条都能用一次操作当场验证：

1. **回灌与清单页同批**：抽 3 个刚回灌的活跃用户，打开记忆清单页逐条核对其「来源会话」与原始对话是否对得上；有对不上的，说明回灌批次与用户可见入口不是同批上线。
2. **删除演练**：对一个测试用户发起删除，然后 (a) 用他的关键词检索应召回 0 条；(b) 向量索引与倒排索引两侧分别验一次，只查主表等于没验；(c) 原样重放同一请求，结果与第一次一致（幂等）。
3. **双轨基线**：切换前把三项对照口径各记一次基线——同一批问题的答案一致性、用户否认率、检索 P99 与单次注入 token；没有基线，切换后任何波动都无法归因。
4. **记忆真的在起作用**：临时关掉记忆读取路径，再问同一个问题，行为差异能否稳定复现？不能复现，说明记忆没有真正进入 prompt，或者进去的是模型本来就知道的内容。
5. **注入量受控**：打印一次完整 prompt，检查注入的记忆是否在 token 预算内、是否条条带来源与作用域标签、超预算时是按分数截断而不是按时间截断。
6. **接口不放开默认值**：检索入参缺作用域或缺预算时，接口层是否直接拒绝？如果它默认放开，隔离与成本控制就都只剩口头约定。
7. **删除覆盖清单能否自动生成**：抽取一次真实删除请求的覆盖清单，看它是系统算出来的还是人回忆出来的；清单里少一处存储，删除就是「看起来完成」。
8. **换模型的代价可知**：换 Embedding 模型时，能否报出需要重算的向量条数与重算窗口？新旧向量混在同一索引里被检索，召回质量下降不会有任何报错。
9. **真伪抽样**：抽 20 条记忆核对真伪，记录确认为真的比例【经验】；低于可接受区间时先修抽取，不要先去调检索权重。
10. **过程留痕**：情景类记忆里是否保留了当时的中间状态（召回候选、工具参数、模型与 prompt 版本）？只留输入输出，复盘时看不出决策分叉点。
11. **用户侧入口**：记忆管理页的查看 / 编辑 / 删除 / 关闭四项是否齐备，且每条显示「什么时候记住的」？删一条是否只删掉那一条？

第 2、3、7 条最常被跳过，而它们恰好是唯一能在事故前发现「删除没删干净」与「切了之后归因不了」的检查。**先修结构，再补治理**——反过来做，治理动作会在一个不支持隔离与删除的结构上反复失败，而且每次失败都要消耗一次团队的信任额度。

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节，是**把写入通道当成受控入口**——抽取带 schema 与来源、冲突解决落在写路径、旧值失效而非覆盖。理由是一条单向依赖：读路径默认记忆为真，写错了就没有第二道防线，而检索、压缩、分层、监控这些都是可以事后优化的工程；写路径的错误无法靠「把检索做得更准」来修复，只会被更准地检索出来。删除与隔离是紧随其后的第二件——它们是布局问题，只能在第一次写入之前定义。
>
> 💡 **思考锚点**：给你现在的记忆写入通道做一次 §4.10 的验收：抽取出的条目是否条条带 schema 与来源、冲突解决是不是落在写路径（而不是读时才合并）、旧值是被标记失效还是被直接覆盖？三样缺一样，读路径就越过你直接默认记忆为真——检索做得再准也只是更准地召回错误。再按 §4.9 第 5 条打印一次完整 prompt：注入的记忆超出 token 预算时，是按分数截断还是按时间截断？你打算先补写入端哪一样？
