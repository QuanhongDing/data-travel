## 6. 落地实践

### 6.1 Cursor"**Composer：把改动范围从"一个文件"扩到"一次任务涉及的所有文件" 1+ 年**"（2023-2024）

**背景（Why）**

Cursor 2023 年面临**"补全式助手解决不了真实开发任务"**：
- **真实改动跨多个文件**——**加一个字段往往要同时改模型、接口、校验、测试、调用方，只补一个文件等于没做完**
- **依赖关系不可见**——**模型不知道"改这个函数会影响哪些调用点"**
- **改动范围失控**——**一次性改太多文件会带来不可审阅的 diff，开发者不敢接受**
- **上下文取舍难**——**整个仓库放不进上下文，必须选"相关的那些文件"，选错就改错**

**触发点（What）**

2023 年起 Cursor 推进 **Composer（多文件编辑）**（[Cursor 公开材料 2023-2024]），目标：
- **按任务圈定改动范围**——涉及的所有文件一起改
- **依赖关系参与决策**——改动的波及面可见
- **diff 可审阅**——改动范围可控、可逐项接受

**详细做法（How）**

Cursor Composer 的**5 大核心组件**：

1. **以任务为单位圈定文件集合（核心创新）**
   - 关键设计：**先从需求推导出"需要动哪些文件"，再逐个生成改动**；文件集合的推导依赖代码库索引（符号、引用、导入关系），而不是靠模型凭语义猜
   - 关键能力：**改动范围有依据、可解释**——这是多文件编辑能被信任的前提：开发者能看懂"为什么动了这几个文件"
   - 关键性质：**跨文件改动可完成、范围可解释**
   - 关键示意：
     ```text
     多文件改动的推导链（不是"凭语义猜要改哪些文件"）
       需求："给订单加一个渠道字段"
            │
       ① 代码库索引（符号 / 引用 / 导入 / 测试关联）
            │
       ② 推导需要改动的文件集合：
            · schema / 模型定义
            · 接口层出入参
            · 校验与默认值
            · 调用点（由索引导出的引用位置）
            · 相关测试
            │
       ③ 逐个生成 diff → 开发者逐项接受 / 拒绝 / 编辑
     ────────────────────────────────────────────────
     关键：先用索引把"波及面"算出来，再让模型写代码
           如果顺序反了（先让模型写、再看用到哪里），必然漏改调用点
     ```

2. **diff 分块与逐项接受（核心）**
   - 关键设计：**改动以可逐块接受 / 拒绝的形式呈现**，而不是"全部接受或全部丢弃"
   - 关键能力：**开发者可以保留对的部分、改掉错的部分**——这把"敢不敢用"的门槛显著降低
   - 关键性质：**逐块可控**

3. **上下文检索与相关性排序（核心）**
   - 关键设计：**按任务检索相关文件与片段**（符号引用、近期改动、测试文件），而不是把整个仓库塞进去
   - 关键能力：**在上下文有限的前提下尽量取到"真正相关"的内容**，这是多文件任务能做对的基础
   - 关键性质：**上下文按相关性取用**

4. **多轮编辑与状态保持（核心）**
   - 关键设计：**多轮对话中保持"已改了哪些文件、当前处于什么状态"**，避免第二轮把第一轮的改动改回去
   - 关键能力：**多轮协作可行**——真实开发本来就是来回调整的过程
   - 关键性质：**多轮编辑状态可控**

5. **技能沉淀：把常用改动模式抽成可复用能力（核心创新）**
   - 关键设计：**高频的改动模式（如"新增字段的完整改动链"）被沉淀为可复用的操作模式**，减少每次都从零推导
   - 关键能力：**经验被复用而非重复推导**——这既是 Skill 提取的雏形，也是效果的持续来源
   - 关键性质：**常用模式可复用**

**Cursor Composer 关键数字**（[Cursor 公开材料 2023-2024]）：

| 指标 | 改前（单文件补全） | 改后 | 提升 |
| --- | --- | --- | --- |
| **改动范围** | 单个文件 | 一次任务涉及的全部文件 | **任务可完成** |
| **改动范围依据** | 无（模型猜） | 代码库索引推导 | **可解释** |
| **漏改调用点** | 常见 | 由引用索引覆盖 | **显著减少** |
| **审查方式** | 全接受 / 全丢弃 | 逐块接受 / 拒绝 / 编辑 | **可控** |
| **上下文使用** | 当前文件为主 | 按相关性检索多文件 | **相关性提升** |
| **多轮协作** | 状态易丢失 | 保持已改文件状态 | **可控** |
| **常用模式** | 每次重新推导 | 沉淀为可复用模式 | **效率提升** |
| **任务完成度** | 部分（需人工补） | 端到端可完成 | **显著提升** |

**具体数字（How much）**

- 团队规模：Cursor 团队数十至上百人
- 关键性质：**跨文件任务可完成**、**改动范围可解释**、**diff 逐块可控**
- 业务影响：把 AI 助手从"补全单行"推进到"完成一次开发任务"，直接改变开发者与工具的协作方式

**失败教训**

- 早期「**只做单文件编辑**」——真实任务跨多个文件，补完一个还得手改其余，倒逼**「以任务为单位圈定文件集合并一起改」**
- 「**让模型凭语义猜要改哪些文件**」——调用点频繁漏改，倒逼**「先用代码库索引算波及面，再生成改动」**
- 「**一次性给出全部改动**」——diff 过大且无法分批处理，倒逼**「改动分块，逐项接受 / 拒绝」**
- 「**把整个仓库塞进上下文**」——既不现实也不相关，倒逼**「按任务检索相关文件与片段」**

### 6.2 Cognition Devin"**自主循环 + 沙箱：让 Agent 能自己做完整任务 1+ 年**"（2024）

**背景（Why）**

Cognition 2024 年面临**"助手模式的天花板"**：
- **助手需要人盯着**——**每一步都要人确认，无法真正减少人力，只是把打字换成了看屏**
- **任务中途失败就断**——**没有自主纠错能力，报错就要人接手**
- **危险操作无隔离**——**让模型直接操作真实环境，一次误删就是事故**
- **长任务无法持续**——**一个任务动辄几十步，超出单次交互的承受范围**

**触发点（What）**

2024 年 Cognition 推出 **Devin（自主软件工程 Agent）**（[Cognition 公开材料 2024]），目标：
- **自主循环**——自行规划、执行、观察、修正
- **沙箱隔离**——危险操作在隔离环境中发生
- **长任务可完成**——几十步的任务能持续跑下去

**详细做法（How）**

Devin 自主循环的**5 大核心组件**：

1. **"计划—执行—观察—修正"自主循环（核心创新）**
   - 关键设计：**Agent 先产出任务计划，逐步执行并用真实反馈（编译错误、测试结果、命令输出）判断是否达成，未达成则修正计划或实现**；循环持续到任务完成或明确放弃
   - 关键能力：**从"一次性生成"变成"持续逼近"**——真实工程任务的完成本质上是反复试错，而不是一次成型
   - 关键性质：**多步任务可自主完成、中途错误可自纠**
   - 关键示意：
     ```text
     自主循环：用真实反馈驱动，而不是靠模型自认为对
       任务 ─▶ ① 计划（拆解为可执行步骤）
                │
                ▼
              ② 执行（编辑文件 / 运行命令 / 查资料）
                │
                ▼
              ③ 观察（用真实信号判定）
                 · 编译 / 类型检查是否通过
                 · 测试是否通过
                 · 命令退出码与输出
                │
         成功 ──┴──▶ 完成
                │
         失败 ──▶ ④ 修正（改实现 / 改计划 / 换路径）──▶ 回到 ②
     ────────────────────────────────────────────────
     关键：判定标准来自环境（编译 / 测试 / 退出码），不来自模型自评
           → 这是"自主"与"幻觉式自信"的分界线
           → 也决定了循环能否收敛：有真实反馈才能纠错
     ```

2. **Docker 沙箱与能力边界（核心）**
   - 关键设计：**Agent 的编辑与命令执行在隔离沙箱内进行**，可挂载代码库、限制网络与危险操作
   - 关键能力：**"让 AI 自主操作"与"别搞坏生产环境"可以同时成立**——这是自主 Agent 能被企业允许运行的前提
   - 关键性质：**沙箱隔离、危险操作受限**

3. **多任务并行与资源调度（核心）**
   - 关键设计：**多个任务可并行推进**，各自独立环境；资源按需分配
   - 关键能力：**并行度提升单位时间的产出**，也把"排队等一个任务结束"的等待消除
   - 关键性质：**多任务并行**

4. **工具与技能的按需加载（核心）**
   - 关键设计：**能力以工具 / 技能形式组织，按任务需要加载**（浏览器、终端、代码搜索、依赖管理等）
   - 关键能力：**不必把所有能力一次性塞进上下文**，同时便于新增能力
   - 关键性质：**能力按需加载、可持续扩展**

5. **人在关键节点的介入（核心创新）**
   - 关键设计：**自主运行，但在高风险动作或方向性决策上设置人工确认点**
   - 关键能力：**"自主"不等于"无人监督"**——把人工介入放在真正需要判断的节点，而不是每一步
   - 关键性质：**高风险节点有人工确认**

**Devin 自主 Agent 关键数字**（[Cognition 公开材料 2024]）：

| 指标 | 改前（助手模式） | 改后 | 提升 |
| --- | --- | --- | --- |
| **执行方式** | 每步人工确认 | 计划—执行—观察—修正自主循环 | **人力介入大幅减少** |
| **判定依据** | 人判断对错 | 编译 / 测试 / 退出码等环境信号 | **不依赖模型自评** |
| **中途错误** | 需人接手 | 自主修正重试 | **可自纠** |
| **运行环境** | 真实环境 | Docker 沙箱隔离 | **风险受控** |
| **任务时长** | 单次交互内 | 数十步长任务 | **可完成复杂任务** |
| **并行度** | 串行等待 | 多任务并行 | **吞吐提升** |
| **能力组织** | 全量塞入上下文 | 工具 / 技能按需加载 | **可持续扩展** |
| **人工介入** | 每一步 | 仅高风险 / 方向性节点 | **介入点更精准** |

**具体数字（How much）**

- 团队规模：Cognition 团队 50+ 人
- 关键性质：**自主循环**、**沙箱隔离**、**多任务并行**、**环境信号驱动纠错**
- 业务影响：把 AI 从"需要人盯着的助手"推进到"能独立完成任务的执行者"，服务大量企业工程团队

**失败教训**

- 早期「**每步都要人确认**」——人力没省下，只是把打字换成看屏，倒逼**「引入自主循环，只在关键节点介入」**
- 「**用模型自评判断是否完成**」——自我判断不可靠导致"看起来做完了其实没做完"，倒逼**「用编译 / 测试 / 退出码等环境信号判定」**
- 「**让 Agent 直接在真实环境操作**」——一次误操作就是事故，倒逼**「Docker 沙箱隔离 + 危险操作限制」**
- 「**把所有能力一次性塞进上下文**」——上下文被占满且不便扩展，倒逼**「工具 / 技能按需加载」**

### 6.3 Cognition"**单线程长上下文的取舍：为什么不做"多 Agent 并行" 1+ 年**"（2024）

**背景（Why）**

Cognition 2024 年面临**"要不要上多 Agent 架构"的架构抉择**：
- **任务天然可拆**——**看起来"调研 + 写代码 + 测试"可以分给不同 Agent 并行做**
- **但拆分会丢上下文**——**各子 Agent 只知道自己那部分，无法共享决策背后的完整推理**
- **并行带来冲突**——**多个 Agent 同时改同一批文件，冲突远比并行带来的收益棘手**
- **长上下文能力在提升**——**单线程能承载的上下文越来越大，多 Agent 的必要性被削弱**

**触发点（What）**

2024 年 Cognition 在 Devin 架构上做出**"单线程长上下文优先、谨慎引入多 Agent"的判断**（[Cognition 公开材料 2024]），目标：
- **不为了并行而拆分上下文**——保持决策信息的完整
- **用长上下文替代多角色协作**——同一个推理链自己完成多步
- **仅在真正可隔离时才并行**——如独立环境的多个任务

**详细做法（How）**

Cognition 架构取舍的**5 大核心组件**：

1. **"上下文完整性优先于并行度"的判断准则（核心创新）**
   - 关键设计：**把"是否需要共享决策上下文"作为能否拆分的判据**——需要共享则单线程长上下文，能完全隔离（如独立沙箱里的不同任务）才并行
   - 关键能力：**避免"为了并行牺牲正确性"**——这是一个反直觉但关键的架构判断：并行的收益是速度，代价往往是上下文碎片化导致的决策质量下降
   - 关键性质：**决策上下文不碎片化**
   - 关键示意：
     ```text
     拆分的判据：子任务之间是否需要共享决策上下文
       ✗ 看似可拆、实则不该拆（常见误判）
         "调研 → 写代码 → 测试"分给 3 个 Agent 并行
         问题：
           · 写代码的 Agent 不知道调研时为什么排除了方案 B
           · 测试的 Agent 不知道实现里刻意的取舍
           → 每个 Agent 都在信息缺失下做局部最优决策
       ✓ 能完全隔离时才并行
         任务 A（仓库 X，沙箱 1）  ┐
         任务 B（仓库 Y，沙箱 2）  ├─ 彼此无共享上下文需求 → 可并行
         任务 C（仓库 Z，沙箱 3）  ┘
     ────────────────────────────────────────────────
     关键：把"并行"的适用范围限定在"可完全隔离"的任务之间，
           而不是把"一个任务内部的步骤"拆成多个角色
     ```

2. **长上下文承载多步推理（核心）**
   - 关键设计：**依赖不断增长的有效上下文长度，让同一个 Agent 在一次推理链里完成探查、决策、实现、验证**
   - 关键能力：**决策理由与实现细节始终在同一上下文里**，减少"信息在交接中丢失"
   - 关键性质：**单链可承载多步推理**

3. **避免多 Agent 的文件冲突（核心）**
   - 关键设计：**同一代码库的并行改动被克制**——多个 Agent 同时改同一批文件，冲突处理成本往往超过并行收益
   - 关键能力：**"看起来快"与"实际更快"之间的差距被识别出来**
   - 关键性质：**同一仓库内避免无节制并行**

4. **真实反馈取代 Agent 间互评（核心）**
   - 关键设计：**不用"一个 Agent 评判另一个 Agent"来提升质量**，而是用编译、测试、运行结果这类环境信号
   - 关键能力：**避免"互相确认错误"**——多个模型互相认可同一个错误答案是常见的失败模式
   - 关键性质：**判定依据来自环境而非 Agent 互评**

5. **可完全隔离时才并行（核心创新）**
   - 关键设计：**并行用在"独立仓库 / 独立沙箱 / 独立任务"之间**，而不是"同一任务的不同步骤"
   - 关键能力：**并行的收益（吞吐）被拿到，而并行的代价（上下文碎片、文件冲突）被避开**
   - 关键性质：**多任务并行、单任务内不拆**

**Cognition 架构取舍关键数字**（[Cognition 公开材料 2024]）：

| 指标 | 改前（多 Agent 拆分） | 改后 | 提升 |
| --- | --- | --- | --- |
| **拆分判据** | 任务"看起来可拆" | 子任务是否需共享决策上下文 | **避免误拆** |
| **决策上下文** | 分散在各子 Agent，易丢失 | 单链完整保留 | **决策质量提升** |
| **文件冲突** | 多 Agent 同时改同一仓库 | 同一仓库内克制并行 | **冲突大幅减少** |
| **质量判定方式** | Agent 互评 | 编译 / 测试 / 运行结果 | **避免互相确认错误** |
| **并行的适用范围** | 任务内部步骤 | 可完全隔离的任务之间 | **收益留、代价避** |
| **多步推理** | 拆到多个角色 | 单线程长上下文承载 | **信息不碎片化** |
| **实现复杂度** | 编排多个 Agent 的通信与共识 | 单链 + 少量并行任务 | **显著降低** |
| **调试难度** | 跨 Agent 追踪 | 单链可完整回放 | **显著降低** |

**具体数字（How much）**

- 团队规模：Cognition 团队 50+ 人
- 关键性质：**上下文完整性优先**、**同一仓库克制并行**、**环境信号取代互评**、**可隔离才并行**
- 业务影响：为自主 Agent 的架构选择提供了一条"反热门"的判断路径，减少了为并行付出的正确性代价

**失败教训**

- 早期「**按"看起来能不能拆"把任务分给多个 Agent**」——子 Agent 在信息缺失下做局部决策，倒逼**「以"是否需共享决策上下文"为拆分判据」**
- 「**让多个 Agent 同时改同一仓库**」——冲突处理成本超过并行收益，倒逼**「同一仓库内克制并行」**
- 「**用 Agent 互评提升质量**」——出现多个 Agent 互相认可同一错误，倒逼**「用编译 / 测试 / 运行结果等环境信号判定」**
- 「**为了并行而把推理链切断**」——决策理由在交接中丢失，倒逼**「长上下文承载完整推理链」**

### 6.4 Anthropic"**Auto-Skill：从执行轨迹中提取可复用技能 1+ 年**"（2023-2024）

**背景（Why）**

Anthropic 2023 年面临**"Agent 每次都在重新发明同一件事"**：
- **重复推理同样的问题**——**同类任务（如"排查一个失败的 CI"）的解题路径高度相似，却每次从零思考**
- **经验不沉淀**——**成功完成任务的过程没有被记录下来，下一次无法复用**
- **技能手工编写不可扩展**——**靠人写技能库，覆盖面永远落后于实际任务分布**
- **技能质量难保证**——**手写的技能可能过时、可能与当前工具不匹配**

**触发点（What）**

2023 年起 Anthropic 推进**从执行轨迹中自动提取可复用技能**（[Anthropic 公开材料 2023-2024]），目标：
- **从成功轨迹中提取技能**——把"怎么做成的"沉淀下来
- **可验证**——技能必须能在类似任务上复现效果
- **可维护**——过时技能能被识别与淘汰

**详细做法（How）**

Auto-Skill 提取的**5 大核心组件**：

1. **"轨迹 → 技能"的提取链路（核心创新）**
   - 关键设计：**从成功完成任务的完整轨迹中，抽取"在什么条件下、按什么步骤、用什么工具、如何判断成功"的结构化技能**；不是把整段轨迹存下来当模板
   - 关键能力：**经验从"不可检索的过程记录"变成"可被检索与复用的能力单元"**——这是重复任务能被加速的根本
   - 关键性质：**技能自动提取、可检索复用**
   - 关键示意：
     ```text
     从轨迹中提取"技能"而不是"模板"
       原始轨迹（一次成功任务）
         步骤 1 读错误日志 → 步骤 2 定位失败用例 → 步骤 3 复现 → 步骤 4 修复 → 步骤 5 验证
       ────────────────────────────────────────────────
       提取出的技能（结构化，而非整段模板）
         适用条件：CI 失败且报错指向某个测试用例
         前置检查：该用例能否在本地稳定复现
         步骤：读日志 → 定位用例 → 本地复现 → 最小化改动 → 跑该用例 → 跑相关用例
         成功判据：目标用例通过 且 相关用例未回归
         反例提示：不要在无法复现时直接改代码（曾导致误改）
       ────────────────────────────────────────────────
     关键区别：
       存模板 → 换个报错就套不上，且模板里含有大量与本次无关的具体信息
       存技能 → 描述"条件—步骤—判据—反例"，可在同类任务上复用
     ```

2. **成功判据的可验证性（核心）**
   - 关键设计：**技能必须带明确的成功判据**（测试通过、命令退出码、指标达标），且该判据可被自动检验
   - 关键能力：**技能是否真的有效可验证**，而不是"看起来写得很对"
   - 关键性质：**技能带可检验判据**

3. **技能在相似任务上的回归验证（核心）**
   - 关键设计：**提取出的技能要在同类的历史任务上回放**，确认能达成同样结果后才纳入技能库
   - 关键能力：**过滤掉"偶然成功"的轨迹**——一次成功可能靠运气，回放才能证明可复用
   - 关键性质：**入库前需回归验证**

4. **工具与环境的版本绑定（核心）**
   - 关键设计：**技能记录其所依赖的工具与接口版本**；工具变更时相关技能被标记需复核
   - 关键能力：**避免"技能过时后仍在被使用"**——这是自动沉淀机制最容易出的问题
   - 关键性质：**版本绑定、过时技能可识别**

5. **技能库的检索与淘汰（核心创新）**
   - 关键设计：**技能按适用条件检索复用**；长期未被使用或被证明失效的技能被标记淘汰
   - 关键能力：**技能库与资产目录一样需要"下线通道"**——否则技能越积越多却越来越不敢用
   - 关键性质：**可检索、可淘汰**

**Auto-Skill 关键数字**（[Anthropic 公开材料 2023-2024]）：

| 指标 | 改前（手工技能库） | 改后 | 提升 |
| --- | --- | --- | --- |
| **技能来源** | 人工编写 | 从成功轨迹自动提取 | **覆盖面跟随任务分布** |
| **沉淀粒度** | 整段模板 | 条件—步骤—判据—反例 | **可泛化复用** |
| **有效性验证** | 难以验证 | 带可自动检验的成功判据 | **可验证** |
| **入库条件** | 写完即入库 | 在历史同类任务上回放通过 | **过滤偶然成功** |
| **工具变更影响** | 技能静默失效 | 版本绑定，变更即标记复核 | **过时可识别** |
| **技能检索** | 靠人工记忆 | 按适用条件检索 | **复用率提升** |
| **技能淘汰** | 只增不减 | 长期未用 / 失效可淘汰 | **库可维护** |
| **重复任务耗时** | 每次从零推理 | 复用已验证路径 | **显著下降** |

**具体数字（How much）**

- 团队规模：Anthropic 研究与工程团队数百人
- 关键性质：**轨迹自动提取**、**带可检验判据**、**入库前回归**、**可检索可淘汰**
- 业务影响：让 Agent 在高频重复任务上复用已验证的解决路径，同时保持技能库的可信与可维护

**失败教训**

- 早期「**手工编写技能库**」——覆盖面落后于实际任务分布且更新滞后，倒逼**「从成功轨迹中自动提取技能」**
- 「**把整段轨迹当模板存下来**」——含有大量本次特有信息，换任务就套不上，倒逼**「提取为条件—步骤—判据—反例的结构化技能」**
- 「**不看判据就入库**」——"偶然成功"的路径被当成通用技能，倒逼**「技能必须带可自动检验的成功判据」**
- 「**技能只增不减**」——过时技能仍被使用且越积越多，倒逼**「工具版本绑定 + 失效标记 + 淘汰通道」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**手工整理的少量技能 + 明确成功判据**」（**最简单**）——**1 个团队、10+ 技能**
- 产出：**技能模板（适用条件 / 步骤 / 成功判据 / 反例）+ 每次使用可回溯到技能版本**
- 团队：**2-3 人**
- 验证标准：**每个技能有可自动检验的成功判据**、**技能有版本**、**使用效果可归因到技能**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 团队 / 100+ 技能 / 环境信号判定**」
- 引入「**用环境信号（编译 / 测试 / 退出码）判定完成**」——取代模型自评与 Agent 互评
- 引入「**执行环境隔离（沙箱）**」+「**危险操作受限**」
- 团队：5-10 人
- 验证标准：**完成判定不依赖模型自评**、**误操作不触及真实环境**、**技能复用率可统计**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 团队 / 千级技能 / 长任务自主循环**」
- 引入「**"轨迹 → 技能"的提取链路**」+「**入库前在历史同类任务上回放验证**」
- 引入「**技能与工具版本绑定，变更即标记复核**」
- 团队：10-30 人
- 验证标准：**技能自动提取且过滤偶然成功**、**工具变更后受影响技能被标记**、**长任务可自主完成并自纠**

**100 → 1000 阶段：12-24 个月**

- 引入「**上下文完整性优先的并行判据**」——只在可完全隔离的任务间并行
- 引入「**技能库检索与淘汰机制**」+「**高风险节点人工确认**」
- 团队：30-100 人
- 验证标准：**同一任务内不因并行而碎片化上下文**、**过时技能能淘汰**、**高风险动作有人工确认点**、**多任务吞吐提升且无冲突事故**

### 6.6 踩坑与经验（4 个真实案例提炼）

| 「**每步都要人确认，人力没省下」 | 1 次 | 1 次 | 1 次 | 1 次 | 「**自主循环 + 仅关键节点人工确认」 |

| 「**手工编写技能库，覆盖落后**」 | 1 次 | 1 次 | 1 次 | 1 次 | 「**从成功轨迹自动提取技能**」 |

### 6.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**任务完成度**」 | 单文件 / 部分完成 | 跨文件端到端完成 | **显著提升** |
| 「**漏改调用点**」 | 常见 | 由引用索引覆盖 | **显著减少** |
| 「**人力介入频率**」 | 每步确认 | 仅关键 / 高风险节点 | **大幅减少** |
| 「**完成判定可靠性**」 | 模型自评 | 编译 / 测试 / 退出码 | **不依赖自评** |
| 「**误操作风险**」 | 直接在真实环境操作 | 沙箱隔离 + 操作受限 | **事故显著减少** |
| 「**重复任务耗时**」 | 每次从零推理 | 复用已验证技能 | **显著下降** |
| 「**技能有效性**」 | 难以验证 | 带可检验判据且入库前回放 | **可验证** |
| 「**过时技能**」 | 静默失效仍被使用 | 版本绑定 + 标记复核 + 淘汰 | **可维护** |
| 「**多任务吞吐**」 | 串行等待 | 可隔离任务并行 | **吞吐提升** |
| 「**架构复杂度与调试难度**」 | 多 Agent 编排、跨 Agent 追踪 | 单链 + 少量并行 | **显著降低** |

**关键投资回报**：
- **直接节省**：「**重复任务耗时显著下降 + 人力介入大幅减少 + 调试复杂度降低**」——**Agent 的成本大头不是模型调用，而是"人盯着它做"和"每次重新思考同一件事"**；技能沉淀与自主循环同时压缩这两项
- **业务价值**：「**跨文件端到端完成任务 + 环境信号驱动自纠 + 沙箱可控**」——**Agent 能不能被真正用起来，取决于三件事**：任务能否做完、做错了能否自己发现、出错会不会搞坏环境。这三条都成立，Agent 才从演示走进日常工程
- **AI 时代关键**：「**技能提取（条件—步骤—判据—反例）+ 环境信号判定 + 上下文完整性优先**」——**这是 Agent 从"每次从零开始"走向"组织能力可积累"的机制**：技能要能被提取、验证、淘汰；完成判定要不依赖模型自评；架构选择要不为并行牺牲决策质量——这三点决定了 Agent 的能力是否随时间复利增长

---

> **本节小结**：
> - 4 个真实案例（Cursor / Devin / Cognition / Anthropic）印证：**Agent Skill 提取不是「写技能库」，是「任务级范围推导 + 环境信号判定 + 沙箱隔离 + 从轨迹提取结构化技能 + 上下文完整性优先」5 件套**。
> - 关键时间线：Cursor 1+ 年 / Devin 1+ 年 / Cognition 1+ 年 / Anthropic 1+ 年 —— **Agent 能力建设是快速演进中的工程**，且**最能决定上限的两件事是"完成判定用什么信号"与"技能是否被结构化沉淀"**。
> - 选型第一原则：「**少量手工技能 + 明确成功判据**」（**最简单**）——**1 个团队** → 「**环境信号判定 + 沙箱隔离 + 技能复用统计**」（**必须**）→ 「**轨迹自动提取 + 入库前回放 + 版本绑定**」（**生产**）→ 「**上下文完整性优先的并行 + 技能淘汰机制**」（**AI 时代**）。
> - 99% 的失败来自「**只改单文件 + 模型自评判定 + 真实环境裸跑 + 轨迹当模板存**」——必须有 **任务级范围推导 + 环境信号 + 沙箱 + 结构化技能提取**。
> - 真正的 ROI 来自「**端到端完成 + 人力介入大幅减少 + 重复任务复用 + 调试复杂度降低**」——是**Agent 能否从演示环境走进日常工程的分水岭**。
