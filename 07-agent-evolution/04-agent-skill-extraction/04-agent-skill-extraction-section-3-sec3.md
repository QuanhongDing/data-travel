## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

真实的模式选择长在六条约束上，而同一个客服团队同时满足两组互相矛盾的约束：处理**退款式高频意图**（同一意图每天被调用上百次）与处理**长尾投诉**（同一意图一个月碰两次），正确模式已经不同——前者适合在线固化，后者只可能靠离线挖掘覆盖。

第一条约束是**写入时机与写入依据**：Skill 是从真实轨迹里归纳的，还是从自造任务里生成的？写入是周期性批处理，还是每条轨迹结束时判断一次？入库闸门是自动化阈值，还是人工签字？这三问一答完，模式基本就定了——因为它们在结构上决定了 Skill Library 的写入路径有几条、每条多贵。

第二条约束更隐蔽，也更致命：**行为日志的完整度**——**成功不等于正确**。Trajectory 只记动作与结果状态，不含因果说明——这一点主文件 §2.1 的定义（「单次任务执行轨迹」）本身没有展开，是本节的推论。于是所有从成功轨迹归纳 Skill 的模式，都在做同一件事——**从结果反推必要步骤**，而误差来源必然包含「把成功那一次的补偿动作当成必要步骤」。这个误差不会在验证集上暴露（补偿动作在同分布任务上照样有效），只会在环境变化后暴露（见 §3.2.1 失效点与 §3.2.2 失效点）。

第三条约束是**结果的机器可判定性**。它决定验证环节能不能自动化，进而决定闸门放在阈值侧还是人工侧。第四条是**变更频率**，它决定 Skill 的半衰期，因而决定"离线周期"的上限——周期取得比业务变更还长，挖出来的是历史。第五条是**错误成本与可回滚性**，它决定闸门能不能只放在阈值侧。第六条是**团队规模与 Skill 归属**，它决定库是一个人的抽屉还是组织的资产。

把这六条约束合起来看，会发现一个反直觉的结论：**这五个模式不是五个难度档位，而是四条写入路径**。离线、在线、Self-Play 分别回答"样本从哪来"，HITL 回答"谁批准"，混合模式回答"它们如何在同一个库里共存"。把它们按"先进程度"排序（很多选型讨论实际就是这么做的：Self-Play 看起来最自动，所以最先进）会直接导致误选——Self-Play 的先决条件是环境可判定，这个条件在绝大多数数据岗位上不成立，它的"先进"建立在别人付不起的前提上。约束表里每一行的作用，就是先把这个前提翻出来，再谈模式。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 写入时机与写入依据（触发方式由任务频次分布决定） | 写入路径有几条、每条多贵；触发是"阈值触发"还是"周期触发"——高频意图几次执行就有统计显著性，长尾意图永远凑不够样本 | 「自动提取对所有任务都适用」被推翻：阈值型模式对长尾 key 永远不写，库看着在长，覆盖率原地不动 |
| 行为日志的完整度 | 抽象出来的是"必要步骤"还是"成功时的伴随动作" | 「成功轨迹 = 正确做法」被推翻：日志只有结果状态，没有因果关系 |
| 结果的机器可判定性 | 验证能否自动化，进而决定闸门在阈值侧还是人工侧 | 「让 LLM 当裁判就能自动验」被推翻：判定器与被判定对象同源时，两侧的错误是相关的，验证会一致地漏掉同一类错 |
| 变更频率（业务口径 / 工具 API / 模型版本） | Skill 的半衰期，以及离线挖掘周期的上限 | 「周期越短越新鲜」被推翻：周期短于聚类收敛所需样本量时，挖出来的簇是噪声而不是模式 |
| 错误成本与可回滚性 | 闸门放在自动侧还是人工侧 | 「人工审核越多越安全」被推翻：审核容量是硬约束，超过容量后的人工闸门退化成盖章 |
| 团队规模与 Skill 归属 | Skill Library 是"个人抽屉"还是"组织资产" | 「先让每个人攒自己的 Skill 更快」被推翻：私有 Skill 的跨人复用率为零，且离职即丢失（§3.5 的 Skill 私藏） |

用这张表的方式不是逐行打勾，而是**找出你自己满足的那一行的否定面**：如果任务频次分布是长尾主导，那么"在线固化"这一列的所有优点都与你无关，而它的阈值触发机制会成为你的主要故障来源。约束表的价值在于**提前告诉你哪一列不该看**。

### 3.2 模式逐个拆解（核心节）

下面 5 个模式：离线 Skill Mining、在线 Procedural Memory、Self-Play RL、Human-in-the-Loop 校验、混合模式。前四个各覆盖一个写入路径，第五个回答「它们如何在同一个库里共存」。

**五个模式共用一个分母**：它们都在做「轨迹 → Skill Template → 验证 → 入库」这条链，区别只在这条链上**哪一步被提前或延后**。离线把"聚类 + 抽象"延后到一个周期，在线把"抽象"延后到阈值之后，Self-Play 把"轨迹来源"提前到执行之前，HITL 在"入库"这一步插入人工，混合模式把三者并联。看每个模式时，先定位它在链上动的是哪一步——这比记它的适用场景更能预测它会怎么坏。

#### 3.2.1 离线 Skill Mining

**被什么约束逼出来**：任务分布长尾、单 key 样本稀疏，但**全量日志的绝对量足够大**——只能用"先聚类、再抽象"的批处理路径，因为稀疏 key 单独看永远不够样本。

**结构**：

```text
离线 Skill Mining（周期批处理管道）
  行为日志（Trajectory 全集，一个周期窗口）
        │  ① 归一化：把动作名 / 参数 / 结果状态对齐到同一 schema
        ▼
  轨迹向量化（LLM Encoder）──► 轨迹聚类（HDBSCAN，自动选 ε，可识别噪声簇）
        │  ② 聚类对象是"整条轨迹"，不是单次调用
        ▼
  簇内抽样 ──► LLM 抽象（主文件 §2.3.2 的"总结 + 模板提取"）
        │  ③ 产出 Skill Template：参数化步骤 + 触发条件 + 成功判据
        ▼
  Skill Verification（主文件 §2.3.3）：在未参与抽象的新任务上回放
        │  ④ hit_rate 达标才进入候选池
        ▼
  Skill Library（写入是"整批追加 + 人工复核"，不是逐条覆盖）
```

**图里有三处不能省（对应图中的 ① ② ④）**：① 归一化（把动作名与结果状态对齐到同一 schema）——省掉它，聚类会把"调用了同一个工具但参数语义不同"的轨迹混在一簇；② 聚类对象是**整条轨迹**而不是单次调用——按单次调用聚类得到的是"常用动作统计"，不是"任务做法"；④ 在**未参与抽象**的新任务上回放验证——用参与抽象的那批轨迹验证，等于用训练集考试（§3.5 Skill 过拟合）。图中的 ③ 是抽象环节的产出物（Skill Template），不是"可省的一步"的候选。

**为什么这样设计有效**：因为聚类是在**整条轨迹**的向量上做的，所以"同类任务的不同做法"会自然落进同一个簇，簇内的差异正好暴露出哪些步骤是共有的、哪些是可替换的——LLM 抽象的任务因此从"发明一个步骤序列"降级为"在若干真实序列里找公共骨架"。这是批处理路径不可替代的地方：**只有在簇的层面，"必要"与"偶然"才可比较**，单条轨迹内部无从比较。

**代价**：① 新鲜度滞后一个完整周期——离线周期 T 越长，Skill 的平均年龄越接近 T/2（【推算】：抽取时刻均匀分布在周期内，故平均滞后为半个周期）；② 抽象阶段的 token 成本集中在一次批处理里，成本形态是"脉冲"而不是"平滑"，需要为它单独做配额的规划；③ 聚类结果对内不可解释——HDBSCAN 的簇是密度定义的，没有自然语言标签，簇的语义要靠 LLM 事后命名，命名错了整簇的抽象都会被带偏。

**失效点**：当业务口径或工具 API 在**一个周期内**发生变更时，「批处理能比较出公共骨架」这个优点会反转成**成批固化过时做法**，因为簇里混着变更前后的两类轨迹，LLM 抽象会把两代步骤的并集写成一份"通用模板"，而这份模板在变更后的环境里每一段都只有一半可用。判别信号：模板里出现两个互斥的步骤（如"用旧接口取状态"与"用新接口取状态"并列）。

**真实使用**：这一族的工程形态是「从执行轨迹中提取结构化技能，而不是把整段轨迹存成模板」，本章 §6.4 记录了这个方向的完整做法（技能必须带可检验的成功判据、必须能在同类历史任务上回放），具体材料可按机构名与关键词自行核验。更普遍的情况是自建：多数做了自动提取的团队走的是"周期批处理 + 人工复核"这条最保守的路（【经验】）。

#### 3.2.2 在线 Procedural Memory

**被什么约束逼出来**：少数意图占据绝大多数调用量，且**每次从头推理都在重复付费**——约束是"高频 + 同构"，所以要在轨迹结束的那一刻就判断能不能固化。

**结构**：

```python
# 在线固化：写入条件是"阈值触发"，不是"周期触发"
def on_trajectory_end(traj):
    key = intent_key(traj)                 # ① 归并键：意图 + 关键实体
    stat = stats.incr(key, traj)           # ② 只更新计数与成功率，不调 LLM
    if stat.success_rate <= 0.9: return    # ③ 成功率未过阈值：不写（0.9 为示例取值）
    if stat.count <= 100: return           # ④ 样本量未过阈值：不写（100 为示例取值）
    skill = abstract_skill(key, stat)      # ⑤ 过阈值才调 LLM 抽象（昂贵步骤被推迟）
    registry.upsert(skill, evidence=stat)  # ⑥ 写入是"按键覆盖"，不是追加
```

**结构里有三处是它的全部要害**：归并键（决定库里有没有重复槽位）、两个阈值（决定谁来承担抽象成本）、覆盖写（决定历史能否回滚）。这三处任意一处定错，模式就会以"看起来在正常工作"的方式失效——归并键太粗会造成混槽（见失效点），阈值定太高会让库长期为空，覆盖写会让版本无从追溯。

**为什么这样设计有效**：因为贵的步骤（LLM 抽象）被放在两个阈值之后，所以绝大多数轨迹只付出一次计数器自增的成本，只有已经反复成功的 key 才付抽象成本——**写入成本随"重复程度"而不是随"流量"增长**。同时因为写入是按键覆盖，同一个意图在库里只有一个槽位，Agent 检索时不存在两个候选互相竞争。

**代价**：① 归并键成了全局单点——`intent_key` 的粒度决定了库的粒度，键太粗会把两类任务混进同一槽位，键太细会退化成长尾（每个键都过不了阈值）；② 覆盖写使历史版本默认丢失，没有版本化就没有回滚，一次错误的抽象会直接顶掉正在用的那份；③ 阈值把"慢热但正确"的模式永久排除——一个成功率 0.85、但每次都能完成任务的做法永远进不了库。

**失效点**：当**意图识别在变更期出现系统性偏移**时，「同一意图只有一个槽位、检索时不存在两个候选竞争」这个优点会反转成**把两类不同任务固化到同一键上**，因为归并键只提供唯一槽位、写入又是覆盖写，两类任务没有并存的余地：一旦线上流量短暂地偏向了另一类任务并越过了阈值，旧的正确 Skill 就被覆盖，而这类覆盖在监控上不表现为失败（成功率计数本身是键级的，键内部换了任务它照样算"成功"）。判别信号：同一 Skill 的步骤里出现条件分支，而分支条件对应的是**任务类型**而不是参数取值。

**真实使用**："从执行轨迹中提取程序性记忆"这一思路的学术源头之一是 Reflexion（Shinn 等，《Reflexion: Language Agents with Verbal Reinforcement Learning》）——它把自我反思沉淀为可重读的 verbal reinforcement，即把成功经验变成可复用的文本记忆；该论文的 arXiv 记录与 NeurIPS 会议版年份在不同材料中记法不一，引用年份之前请以 arXiv 条目与 NeurIPS 官方论文页为准。需要区分的是：Reflexion 的沉淀对象是**反思文本**，不是参数化步骤序列；把前者当作后者的公开实现来引用会夸大其覆盖范围。

#### 3.2.3 Self-Play RL

**被什么约束逼出来**：冷启动时**没有历史日志**（离线与在线两条路都拿不到输入），但**环境能对成功给出机器可判定的信号**——约束是"无样本 + 可判定"，所以只能让 Agent 自己造任务。

**结构**：

```text
Self-Play RL（样本自造 → 强化 → 固化）
初始化：种子 Skill Library（少量人工技能）
   │
   ├─► ① 自造任务：课程式加难度（环境生成 / 任务改写 / 组合已有 Skill）
   │      │
   │      ▼
   │   ② 用当前 Skill 执行 ──► 环境返回可判定的成功信号
   │      │
   │   ┌──┴──────────────────┐
   │  成功                   失败
   │   │                      │
   │  ③ 强化该 Skill 的权重    ④ 探索新步骤（Compositional Skill 组合）
   │   │                      │
   │   └────────┬─────────────┘
   │            ▼
   └──── ⑤ 回到 ①，循环 N 轮
   停止条件：环境还能不能给出"判定"——不是轮数到了没有
```

**结构里最关键的一处分离**：① 任务生成器（课程）与 ② 判据（环境反馈）是两个独立部件。如果两者由同一个模型提供（让模型既出题又判分），这一模式就失去了它唯一的立身之本——样本可以自造，但裁判必须独立于被训练者；③ 强化步与探索步必须都能写回库，只强化不探索会锁死在最早的种子技能上。

**为什么这样设计有效**：因为成功信号来自**环境**而不是来自模型自评，所以"强化"这一步有独立于模型的判据——这正是它能靠自造样本工作的原因：样本是我造的，但裁判不是我。由此，"难度可以自动上调"成立：任务难度的调节旋钮（课程设计）与成功判据（环境反馈）是两个独立部件，可以一个动一个不动。

**代价**：① 只适用于可判定环境——一旦成功判据需要人来判断，"自造 + 自评"就退化成自我确认；② 奖励信号会被钻空子（reward hacking）：环境给的判据越单一，Agent 越容易找到"判据通过但任务没完成"的路径，库里积累的 Skill 数量在涨而实际能力没涨；③ 训练循环本身没有终点，需要人为设定"什么时候停"，而停早了库不成熟、停晚了成本不可控。

**失效点**：当**判据与真实目标之间出现可被利用的缝隙**时，「样本自造 + 环境判定」这个优点会反转成**批量固化投机策略**，因为自造循环是一个优化器：它会在判据的边界上做梯度上升，而判据是环境的近似——被优化得越久，Skill 越贴着判据边界而不是贴着目标。判别信号：Skill 在自造任务上的通过率持续上升，但在真实任务抽样上的通过率不动。

**真实使用**：Voyager（Wang 等，《Voyager: An Open-Ended Embodied Agent with Large Language Models》）在 Minecraft 中把这一族做到了系统级：自动课程生成任务、用不断增长的 Skill Library 做终身学习；该论文的 arXiv 版本号与首发月份请以 arXiv 条目页为准。需要注意的是它并非纯 Self-Play——判据里有 LLM 作为语义裁判的成分，且 Skill Library 以向量近邻检索支撑复用；把 Voyager 当作"纯 RL"引用会误导读者对判据来源的判断，引用时请对照论文原文（本章 §5、§8 中对它的口径也以此为准）。

#### 3.2.4 Human-in-the-Loop 校验

**被什么约束逼出来**：Skill 会进入**不可回滚的链路**（涉资金、涉合规、涉人身），而自动判据的置信度不足——约束是"错误成本高于审核成本"，所以闸门必须在人这一侧。

**结构**：

```text
Human-in-the-Loop 校验（置信度分流闸门）
LLM 抽象产出候选 Skill
   │
   ├─ 可自动判定的部分：在留出验证集上回放 → hit_rate（主文件 §2.3.3）
   │
   ▼
置信度打分 = f(样本量, hit_rate 下界, 触发条件是否唯一, 步骤是否含未命名参数)
   │
   ├─ 高分 ──► 自动入库（前置条件：不进关键链路 / 可回滚 / 有版本）
   │
   └─ 低分 ──► 人工审核队列
                 审核项：触发条件 / 步骤必要性 / 成功判据 / 反例提示
                  │
                  ├─ 通过 → 入库（记录 reviewer 与审核时间）
                  └─ 驳回 → 退回候选池，并记录驳回理由（供下一次抽象参考）
```

**结构里最容易被做错的一处**：打分函数的位置。它必须在**抽象之后、入库之前**，且它的输出只决定"谁来判断"，不决定"能不能入库"——一旦让打分直接决定入库，人工队列就只是摆设（高分自动入库那条边会吞掉本该进队列的候选）。审核项的四个字段（触发条件 / 步骤必要性 / 成功判据 / 反例提示）是固定的，不能按候选自由裁剪，否则审核深度会随审核员的忙碌程度浮动。

**为什么这样设计有效**：因为人工不是审核**全部**候选，而是只审核**低分**候选，所以人工成本与"模型的不确定性"成正比，而不是与"Skill 总量"成正比——库越大，人工绝对量由低分比例决定，而不是由库规模决定。这让"人工闸门"在规模上可持续：把人工放在分流器的低分侧，等于让模型把人的注意力花在它自己最没把握的地方。

**代价**：① 打分函数本身是个模型，它有假阴性（把该审的判成高分）和假阳性（把能自动入库的拉去排队），两个方向都会持续消耗人力与时效；② 审核队列是排队系统，流量高峰时候选积压，积压期间"已成功执行但未入职"的经验不在库里，Agent 继续重复推理；③ 审核留下的"通过"记录本身成为事实上的标准——审核员的口味会被抽象进 Skill，而这份口味不会写在文档里。

**失效点**：当**候选产出速度超过审核容量**时，「人工把关」这个优点会反转成**盖章**，因为队列压力会把审核动作从"逐条判断"压缩成"批量通过"，而打分函数的分流阈值在压力下通常会被下调而不是上移（下调更省事）——于是高风险候选也可能从自动侧通过。判别信号：审核队列的**平均停留时间**（不是队列长度）持续上升，同时单条审核耗时持续下降。

**真实使用**：这一模式在公开材料里极少被单独宣传，因为它不像自动提取那样"看起来先进"；它更多以组织约束的形式存在——高合规场景要求 AI 产出的可执行步骤在入库前有人签字（【经验】）。做选型判断时，可核验的问题是：你的 Skill 库里，有多少条能指出**最后一个看过它的人**是谁（见 §3.7 自检清单）。

#### 3.2.5 混合模式（离线 + 在线 + 人工）

**被什么约束逼出来**：同一套 Agent 能力必须同时覆盖高频意图、长尾意图与高风险链路——**任何单一写入路径都有它覆盖不到的区域**，所以约束是"任务分布本身是多峰的"。

**结构**：

```text
混合模式：三条写入路径，一个出口
  离线层（周期）             在线层（每条轨迹）        人工层（异常时）
  ─────────────────         ──────────────────        ─────────────────
  全量轨迹聚类                只更新命中统计            低置信候选
  LLM 抽象（可批、可等）       过阈值才调抽象            审核触发条件与判据
  产出：候选 Skill 池         产出：已固化 Skill        产出：放行 / 驳回
        │                          │                        │
        └────────────┬─────────────┴────────────────────────┘
                     ▼
        Skill Library（唯一写入出口，带版本与来源证据）
                     │
        检索（触发词预筛 → 向量精排 → 图谱组合）
                     ▼
                 Agent Runtime
  关键：不是"三选一"，是"三条写入路径共用一个带版本的库"
        任何路径都不得绕过版本化直接改库，否则回滚无从下手
```

**结构里的关键约定**：三条路径都**不直接写库**，而是把候选交给版本层；版本层是唯一出口。这条约定决定了混合模式能不能成立——如果在线路径为了降延迟直接改库，那么离线的候选、人工的驳回记录与线上的实际状态三者会立刻失去一致性，回滚也就没有基准点。

**为什么这样设计有效**：因为三条路径的**成本形态互补**——离线的成本是脉冲式（周期一次，可预算），在线的成本是连续小额（计数器自增），人工的成本是按件计（与低分比例成正比）。共用一个带版本的出口后，覆盖长尾靠离线、降重复推理靠在线、挡高风险靠人工，**每一层只承担它最便宜的那部分工作量**。这是"混合模式"在决策表里被推荐给"任务分布多峰、多团队共享"场景的真正理由：不是因为混合更全面，而是因为这类任务的分布本身就是多峰的。

**代价**：① 三条路径写同一个库 ⇒ 必须引入版本、来源与冲突解决，库里每一个 Skill 都要能回答"谁写的、依据是什么、什么时候写的"，否则三方互相覆盖；② 运维面从"一条管道"变成"三条管道 + 一个一致性层"，需要有人对库的整体质量负责；③ 在线与离线可能对同一个意图给出不同 Skill，必须定义优先级的判定规则（通常以证据量而不是以新鲜度为准），否则行为在同一周内会不一致。

**失效点**：当**没有人为库的整体质量负责**时，「三条路径各司其职」这个优点会反转成**三条路径各自积累、互相覆盖**，因为每一层都只看自己的指标：离线看候选池大小、在线看覆盖率、人工看队列清空速度——三者都可以在局部达标的同时让库整体退化（大量语义重复的低质 Skill 堆积）。判别信号：库的 Skill 总数在涨，但**去重后的有效 Skill 数**不动，且同一意图的检索结果在不同时间返回不同 Skill。

**真实使用**：多数把 Skill 提取做成生产系统的团队最终落到这一形态（【经验】），因为它不是设计出来的，而是被三类问题依次逼出来的：先离线解决"手工编写覆盖不足"，再加在线解决"周期内重复推理"，再加人工闸门解决"高风险链路不敢自动上"。本章 §6 记录的 4 个落地案例可以按此三层去读，看每一家在哪个阶段补了哪一层。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 高频意图（同 key 日调用两位数以上）+ 结果可自动判定 | 在线 Procedural Memory | 离线要等一个完整周期才产出，期间的重复推理成本已经付掉；高频场景不需要聚类收敛就已具备统计显著性 | 同一意图键的日执行次数是否已进入两位数【经验】 |
| 长尾主导（长尾 key 的绝对调用量超过头部）+ 日志量充足 | 离线 Skill Mining | 在线模式对每个 key 都要样本量过阈值，长尾 key 永远不达标，等于永远不写 | 单 key 样本量的分布：头部占比是否已低于长尾总量 |
| 无历史日志（冷启动）+ 环境可给出机器可判定的成功信号 | Self-Play RL | 离线与在线都依赖真实轨迹，冷启动时输入为空；人工编写覆盖不了任务组合 | 环境的成功判据能否在无人参与时返回（能否被自动化检验） |
| 高风险链路（资金 / 合规 / 人身）+ 错误不可回滚 | HITL 校验，叠加在上述任一模式之上 | 纯阈值入库把"统计上够好"当成"可以上"，风险外溢给用户 | 该 Skill 进入的链路能否在一次回滚操作内撤销 |
| 多 Agent / 多团队共享能力 | 混合模式 + 组织级 Skill Library | 单一模式在多团队下会产生私有 Skill，跨 Agent 复用无从谈起 | 是否存在"某人的 Agent 会做而另一个人的不会"的现象 |
| 业务口径 / 工具 API 高频变更 | 在线固化 + 离线定期重聚（混合模式的变体） | 纯离线跟不上变更，纯在线会被变更期的噪声轨迹污染 | 口径变更频率是否高于离线挖掘周期 |

**本主题下最常被误选的一对，是在线 Procedural Memory 与离线 Skill Mining。** 误选的典型形态是「用在线模式去做长尾」：团队看到在线模式"实时、自动、无需批处理"就选它，但长尾 key 永远到不了阈值，库长期接近空，于是团队得出结论"自动提取不管用"，退回人工编写——**失败原因被记成了"方法不行"，实际是"阈值触发机制与长尾分布不匹配"**。反向误选是「用离线模式去做高频」：每周重跑全量聚类，产出的是"一周前的主流做法"，在变更期尤为致命，因为那一周的轨迹恰好横跨两代做法，抽象出的模板是两代的并集（§3.2.1 失效点）。两个方向的后果都不表现为报错，而表现为"库看着在长、能力不动"。

**误选之后的诊断动作也不同，这一点比结论更重要。** 在线模式误用在长尾上，正确的诊断不是调低阈值（调低会让长尾 key 在样本不足时被抽象，产出的是过拟合 Skill），而是**扩容到能覆盖长尾的那条路径**：要么把相似 key 归并成更粗的意图（用离线重聚产出归并建议），要么切到离线挖掘。离线模式误用在高频上，正确的动作不是缩短周期（周期短于"变更窗口"时挖到的就是噪声），而是**为头部意图单独开一条在线通道**——即演化成 §3.2.5 的混合模式。换句话说，两种误选的修法都不是调参，而是换路径，这也解释了为什么调参往往只是把问题推迟一个周期。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：离线挖掘主管道 + HITL 闸门 + 版本化入库。** 离线负责从全量日志里挖候选（覆盖长尾是它唯一能做到的事），人工闸门只拦低分候选（承担"不可回滚链路"的判断成本），版本化保证任何一条都能回滚。**职责边界**：离线只产候选、不直接改线上；人工只判低分、不重写候选；版本层只做记录、不做质量判断。**运维代价**：一条批处理调度 + 一支审核队列 + 一套版本表，最重的是审核队列的人力预算——它是唯一无法靠调参压下去的项。**适合规模**：意图种类在十到百量级、日志量还不需要采样、错误成本中等偏高的团队（【经验】）。

**组合 B：在线固化主管道 + 离线定期重聚。** 在线把高频意图的重复推理成本压掉，离线每周期把在线固化过的 key 重新聚类一次，用于发现"两个键其实是同一个意图"（键太细导致的人为长尾）与"一个键里混了两类任务"（键太粗）。**职责边界**：在线只管写与覆盖，离线只管**键的归并建议**，不能直接改线上的键——键一改，历史统计全部失配。**运维代价**：两套成本形态（连续小额 + 周期脉冲）要分别做预算；键归并需要人工确认，因为归并是破坏性操作。**适合规模**：意图高度集中、日调用量大、业务变更中等的场景（【经验】）。

**组合 C：Self-Play RL + LLM-as-Judge（语义裁判）+ 人工抽检。** 在可判定环境里自造任务，用环境信号做硬判定，用 LLM 作为语义裁判补足"过程质量"这一维，人工只做抽检（不逐条审）。**职责边界**：环境信号管"成不成"，语义裁判管"好不好"，人工管"判据本身对不对"。**运维代价**：需要维护判据本身（判据也会过时），且要持续监控 reward hacking 信号（自造任务通过率与真实任务抽样通过率的差距）。**适合规模**：任务可自动验证、且环境可控（游戏 / 代码 / 数学类）的场景；把这一组合搬到无判定环境会退化成自我确认。**公开参照**：Voyager 的判据里有 LLM 语义裁判成分（Wang 等；该论文的版本与年份以 arXiv 条目页为准），它属于这一组合而不是纯 Self-Play。

**选择组合时唯一需要先回答的问题，是"库里谁说了算"。** 组合 A 把决定权交给人工，组合 B 交给统计（`intent_key` 的粒度就是它的全部权力），组合 C 交给环境判据。三者可以叠加，但**优先级必须显式**：当人工的判断与统计的结果相反时听谁的？多数团队的回答是"听人工"，这会让审核队列成为唯一的质量瓶颈；更稳的回答是"人工只能收紧、不能放宽"——即人工可以驳回自动入库，但不能把被统计拒绝的候选直接放行，因为那样等于绕过了所有阈值。这条规则写下来只要一行，但它决定了三种组合叠加后是否仍然可解释。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **Skill 爆炸** | 库中 Skill 总数持续增长，但去重后的有效数不动；同一意图检索会返回不同 Skill | 检索候选间的区分度被稀释，排序误差放大，误触发率上升——它不是"变慢"，是"选错" | 每个写入路径都只看自己的指标（候选数 / 覆盖率），没有人为库的整体唯一性负责 | 写入前做语义去重 + 重要性阈值 + 定期合并同类；把"有效 Skill 数"而不是"Skill 总数"作为库的健康指标 |
| **Skill 幻觉** | Skill 的步骤在验证集上通过，但在真实任务上出现"从未发生过的步骤" | 抽象层把不存在的因果写进步骤序列，Agent 会照着执行，错误直接落到用户侧 | LLM 抽象被要求"总结出通用模板"，而模板这一输出形态天然倾向于补齐缺失的环节 | 验证集必须来自未参与抽象的任务；步骤必须带证据（来自哪条轨迹）；人工只审低分但不省掉这一步 |
| **Skill 过拟合** | Skill 在历史同分布任务上命中率高，在新任务上命中率骤降 | Skill 编码的是那批任务的具体特征而不是可迁移的骨架，跨任务复用率接近零 | 验证集与训练集同源（同一批轨迹切分），验证只证明了"记得住" | 验证集按时间或按来源切分（用之后的轨迹验之前的 Skill）；多样性要求写进抽象 prompt |
| **Skill 冲突** | 同一意图存在多条可用 Skill，且建议相反 | Agent 行为在同一周内不一致，用户侧表现为"偶发的不讲理" | 三条写入路径共用一个库但没有优先级规则，覆盖写与追加写混用 | 版本管理 + 显式优先级规则（通常以证据量排序，不以新鲜度）；冲突进入人工队列而不是自动裁决 |
| **Skill 退化** | Skill 的最后更新时间很早，但仍在被检索命中 | 过期 Skill 仍在被调用，且失败不报错（步骤语法有效、语义已过时），静默算错的概率上升 | 没有把"新鲜度"作为一等指标；提取有管道而退役没有管道 | 持续评估 + 老化检测 + 定时重放；给每个 Skill 记录最后验证时间，超期自动降级为候选 |
| **Skill 私藏** | 能力只存在于个人 Agent 的工作目录或私有 prompt 里 | 能力无法跨人复用，人员流动即能力归零；同时库的覆盖率被高估 | 个人侧先攒自己的更快见效，组织侧的制度滞后于个人实践 | 组织级 Skill Library 作为唯一写入口；把"私有 Skill 是否入库"纳入交付定义 |
| **Skill 不可解释** | Skill 是黑盒：能执行但说不清为什么是这几步 | 无法审计、无法在出错时定位是判据错还是步骤错，回滚决策没有依据 | 抽象只输出步骤，不输出依据；结构化描述被视为额外工作 | 强制结构化描述（触发条件 / 步骤 / 成功判据 / 反例）；入库时记录来源轨迹与证据量 |
| **Skill 难复用** | 同一类任务有多条高度雷同的 Skill，参数各不相同 | 抽象度太低导致复用率低，库规模虚高（与 Skill 爆炸互为表里） | 归并键取得过细（按具体参数而非按意图），写入时天然分裂 | 抽象度适中：参数化到"用户可填具体值"这一层；用离线重聚检测可归并的键 |

**Skill 爆炸在生产中的典型暴露方式**：它不是以"性能问题"暴露的，而是以**误触发**暴露的——某一天某个高频意图开始偶发地走了错误分支，排查发现库里存在一条语义高度相似的 Skill 抢到了 top-1。此时团队的第一反应通常是加大 top-k 让 LLM 重排，但候选池变大只会让区分度更差；正确的动作是回到写入侧做去重（【推算】：设库中 Skill 数为 N、每次检索取 top-5，候选池相对大小从 N=10³ 时的 0.5% 降到 N=10⁴ 时的 0.05%，推导链为——候选池占比下降意味着候选之间的相似度差距被压缩，而排序误差的绝对容差不变，于是同样的 embedding 噪声会造成更多错排；结论是"检索选错"而不是"检索变慢"）。

**Skill 幻觉在生产中的典型暴露方式**：它往往在某一类边界任务上集中爆发——Skill 里多了一步"检查 X"，而这一步在历史轨迹中从未出现，是抽象阶段为了"模板完整性"补上去的。它之所以危险，是因为这一步看起来总是合理的（谁会反对多一次检查），只有在 X 检查本身有副作用或耗时显著时才被发现。

**Skill 退化在生产中的典型暴露方式**：它完全不暴露。上游 API 改了字段名而 Skill 里仍是旧字段，Agent 执行后拿到空值并继续走完流程，成功判据照样通过。发现它的唯一途径是有人主动重放验证——这也是为什么「最后验证时间」必须和「最后更新时间」分开记录：被检索命中的 Skill 不等于被验证过的 Skill。

**它的机制是"成功判据比步骤活得久"。** 步骤依赖的是工具、接口、字段名这些会变的东西，判据依赖的是"任务达成"这一层语义，后者几乎不变；于是接口改名时步骤已经失效、判据却照样通过——判据太粗（"接口返回 200"）就无法察觉返回值是空的。这解释了为什么给每条 Skill 的成功判据加严，比提高提取频率更能降低退化风险：提取频率只影响新 Skill 的质量，判据精度才决定旧 Skill 失效时会不会被发现。

上面三种暴露方式有一个共同的观察位置：**它们都发生在检索命中之后、执行结果之前**——Skill 被选中了，执行也"完成"了，问题只出在中间那一段。因此把监控放在事后成功率上是看不见它们的；唯一有效的观察点是**执行轨迹与 Skill 步骤的比对**（§3.7 自检清单第 9 条）。

**Skill 冲突值得单独说一句，因为它的诱因是"成功"而不是"失败"。** 冲突通常在库扩容期出现：同一个意图先由离线挖出一条，后来流量涨上去、在线模式又固化出一条，两条都有正面的验证记录，谁也没有错。此时如果没有"证据量优先"这类显式规则，检索侧就会按相似度随手选一条，于是同一种任务在不同时间被不同方式处理——用户侧的感受是"这个 Agent 有时讲理有时不讲理"，而排查看不出任何一条 Skill 有问题。**冲突的修法不是删掉一条，而是写下判定规则**：删任何一条都在丢失证据，只有规则能让库在多写入路径下保持一致。

**三个反模式有一条共同的根**：它们都来自"提取有管道、退役没管道"。Skill 爆炸是只加不去重（同一做法被反复写进库），Skill 退化是只加不退役（过期的条目留在库里继续被命中），Skill 私藏是只加不收敛（能力停在个人侧，进不了组织库）——三者的修法也都不是更聪明的提取算法，而是三个缺失的运维动作：去重、退役、收敛到组织库。把这句记住，比记住八条反模式的名字有用。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：**跨过某个阈值后，原来正确的模式会变成错的**，而它不会报错——它只是开始以"偶发误触发""库在长但不复用""静默算错"这类形式表现为质量问题。下表五条跃迁里，三条关于库本身（规模、组织边界、共享范围），两条关于数据量与变更速度；共同点是每一条的触发信号都不是性能曲线，而是**质量指标的漂移**。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| Skill 数 10² → 10³【经验，量级阈值】 | 全量语义检索（embedding 相似度直接取 top-k） | 候选之间的相似度差距被压缩，排序噪声开始造成误触发（§3.5 Skill 爆炸） | 分层检索：触发词预筛 → 向量精排 → 图谱组合匹配 | 要补一套触发条件抽取（历史 Skill 大多没写触发条件），冷启动期误触发率会先上升 |
| 库维护者 1 人 → 多团队共建【经验，组织规模阈值】 | 单写入路径 + 人工全审 | 人工容量跟不上多团队的候选产出，闸门退化成盖章（§3.2.4 失效点） | 置信度分流 + 分层审核（低分进队列，高分自动入库但仅限可回滚链路） | 需要先建立"哪些链路可回滚"的清单，否则分流规则没有依据 |
| 单 Agent → 多 Agent 共享能力 | 各 Agent 各自建库 | 能力重复建设且口径分叉，跨 Agent 迁移只能靠人工搬运 | 组织级 Skill Library + Cross-Agent Transfer（Transfer 本身按 §5 属 L3：跨 Agent 的 schema 与版本协议尚未标准化，此档可先落地的只有 schema 与版本协议的统一，不要把它当作设计前提） | 需要统一 Skill 的描述 schema（本章 §4 子文件的 §4.5 给出的 `apiVersion: ai-skill/v1` 一类 schema）与版本协议，存量 Skill 要重写描述 |
| 日轨迹量 10⁴ → 10⁷【经验，量级阈值】 | 全量轨迹向量化 + 全量聚类 | 聚类的时间与成本随轨迹量线性甚至超线性增长，周期内跑不完 | 采样聚类（按意图分层抽样）+ 增量聚类 | 采样会漏掉低占比但高风险的任务族，需要单独为高风险族保留全量通道 |
| 业务口径低频 → 高频变更 | 离线周更（或月更） | 周期内的轨迹横跨两代做法，抽象出的是并集模板（§3.2.1 失效点） | 在线固化为主 + 离线定期重聚 + 键归并建议 | 在线固化的阈值需要按新业务重新标定，旧阈值在新分布下可能永不触发 |

**判断"是不是该换了"的信号不在性能指标上。** 库规模、检索延迟、抽象成本这三项都可以在模式已经过时的情况下继续好看，因为它们衡量的是"管道通不通"，而模式过时的表现是"管道通、出口不对"。可观察的置换信号是四个质量指标的趋势：误触发率、去重后的有效 Skill 数、空跑率、同意图检索结果的一致性。前三个上升（或停滞）加上最后一个下降，就该考虑换模式了；四个指标里没有一个在监控上，才是"库在长、能力不动"这类问题的真正成因。

**这五条跃迁里最难被承认的是第一条。** 从全量语义检索换到分层检索，表面上只是"加一层过滤"，实际上要补的是历史 Skill 里普遍缺失的**触发条件**字段——它意味着对存量做一次批量重写，而重写期间的误触发率会先上升。团队通常在误触发已经影响到业务之后才愿意付这笔迁移成本，而这时库里的 Skill 数量决定了重写的工作量：迁移成本与库规模同向增长，越晚做越贵（【经验】）。第二条跃迁（单写入路径 → 分流闸门）的成本形态完全不同：它是**制度成本**，需要先产出一份"哪些链路可回滚"的清单，这份清单不可能由平台团队单方面给出，必须由每条链路的负责方确认。

### 3.7 自检清单

以下 12 条按"能不能当场查"排序：前 5 条查库里的记录字段，后 7 条查管道与闸门本身。每条都要能回答"是 / 否 / 查不到"，答"查不到"的条目本身就是不合格项——因为它意味着这个属性没有被记录。

- [ ] 库里的每一件 Skill，能否回答「最后看过它的**人**是谁、什么时候」？答不出的条目是否已标记为待审？
- [ ] 「最后更新时间」与「最后**验证**时间」是否是两个字段？如果只有一个，说明被命中的 Skill 可能从未被验证。
- [ ] 抽出任意一条 Skill 的步骤，能否指出每一步来自**哪几条轨迹**？不能溯源的步骤即为幻觉候选。
- [ ] 验证集是否与抽象用的轨迹**按时间或来源切分**？同批切分的命中率只证明"记得住"。
- [ ] 每个 Skill 是否带**成功判据**和至少一条**反例提示**？只有步骤没有判据的 Skill，失败时无法归因。
- [ ] 是否存在一个**为库整体质量负责**的角色或门禁？如果三条写入路径各自看自己的指标，Skill 爆炸只是时间问题。
- [ ] Skill 的触发条件是否**可判定**（描述的是任务特征而不是"当合适时"）？不可判定的触发条件是误触发的根源。
- [ ] 是否记录了**空跑率**（被检索命中但未被采用的比例）？只记录采用次数会系统性高估 Skill 的价值。
- [ ] 抽一条 Skill 的步骤与它最近一次被调用的轨迹比对：Agent 是否**真的按它执行**？仍然自由发挥说明这条 Skill 只是参考文本。
- [ ] 涌现出的新做法是否会被**收敛回库**、且所有 Skill 都落在**组织级库**（而不是个人工作目录）？后者是 Skill 私藏的判据。
- [ ] 是否有**退役管道**？只提取不退役的库，规模只会单调上升（与 Skill 爆炸、Skill 退化同源）。
- [ ] 高风险链路上的 Skill 是否由**人的签字**放行、且人工**不能放行被阈值拒绝的候选**？否则闸门同时是旁路，高风险链路事实上没有闸门。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 高频同构任务、结果可自动判定 | 在线 Procedural Memory | 昂贵步骤（LLM 抽象）被两个阈值挡住，写入成本随重复程度而非随流量增长 |
| 长尾主导、日志量充足、允许一个周期的滞后 | 离线 Skill Mining | 只有在簇的层面，"必要"与"偶然"才可比较，单条轨迹内部无从比较 |
| 冷启动、环境可给出机器可判定的成功信号 | Self-Play RL | 判据来自环境而非模型自评，样本可以自造而裁判必须独立 |
| 高风险、不可回滚链路 | HITL 校验（叠加层） | 人工成本与模型的不确定性成正比，而不是与库规模成正比 |
| 任务分布多峰、多团队共享 | 混合模式 + 版本化出口 | 三条路径成本形态互补，但必须共用一个带版本的库，否则互相覆盖 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**「样本从哪来、什么时候写、谁批准」这三件事实在同一条写入路径上的组合**——行业、任务类型、模型能力都不决定它。任务频次决定写入是阈值触发还是周期触发，结果可判定性决定闸门在阈值侧还是人工侧，而"成功轨迹不等于正确做法"这一条贯穿所有模式：它决定了每个模式都必须有一个能反转自己优点的失效条件，也决定了**验证集必须与人审闸门同时存在**——前者挡住"看起来对"，后者挡住"看起来安全"。
>
> 还有一条推论值得单独记住：**库的价值不在"有多少条 Skill"，而在"有多少条能被验证、能被回滚、能被别人用"**。三个指标分别对应验证集的存在、版本层的存在、组织级库的存在——它们都是运维动作，不是模型能力。这也是为什么本节的 5 个模式里，有 3 个的失效点与"写入太快、退役太慢"有关：提取能力容易买到，治理节奏买不到。
>
> 💡 **思考锚点**：把你库里当前的 Skill 总数除以「去重后的有效数」——这个比值若持续变大，按 §3.5 你已在「Skill 爆炸」区间；而 §3.6 列出的四个换模式信号（误触发率、去重后有效 Skill 数、空跑率、同意图检索结果一致性）里，你现在真正在监控的有几个？一个都没监控，你凭什么判断库是在长能力还是在长噪声？
