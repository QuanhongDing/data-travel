## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是**没有时间维度**。「从执行轨迹里提取结构化技能」已经有工程形态（本章 [§6 落地实践](04-agent-skill-extraction-section-6-sec6.md) 里「Auto-Skill」一节记录的案例：技能必须带可检验的成功判据、必须能在同类历史任务上回放），而「自动合成完整 Workflow」只有路线图与技术演示。两者被并列成七个方向，读者据此排路线图就会踩空——前者的失败方式是接口还会变，后者的失败方式是它可能根本不落地。

第二个问题是「Skill」这个词在三个层次上被混用：**产品功能**（Agent 平台或 IDE 里的技能与编排能力）、**工程机制**（技能 schema、归并键、入库闸门、退役管道）、**算法研究**（Self-Play、组合、程序性记忆建模）。三者的可规划性差一个量级：产品功能写在平台发布说明里；工程机制写在模板 schema 与管道代码里（本章 §4.5 的 `apiVersion: ai-skill/v1`）；算法研究写在论文里，而论文里的原型与产品里的实现经常不是一回事——§3.2.3 已经把 Voyager 归到「判据里含 LLM 语义裁判」这一类，按纯 RL 引用会误导读者对判据来源的判断。

第三个问题是没有反方观点。清单不会写出「这条方向今天不值得投」，于是「Self-Play RL」（先决条件是环境能无人判定成功，§3.2.3）与「在线阈值固化」（有调用日志的团队现在就能做）被排进同一列。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（或版本化发布的 schema 与产品文档）；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期（技能的定义字段与版本语义不随版本翻烧饼）。
- **L2 可试点**：①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

**判据声明（只对 ① 生效）**：本主题对 L1 的判据做如下修正——**① 的核验入口放宽为「正式 release note，或版本化发布的 schema 与产品文档（技能模板 schema、平台的技能能力文档）」**；理由是技能这一族还没有跨厂商的标准，能被读者直接定位的版本化材料主要就是这两类，而本节要评估的归并键与入库判据本来也不写在功能发布说明里（那些只覆盖「有没有技能库」这个开关）。修正只改 ① 的入口、不改它的强度，② 与 ③ 一字未动。下文四行的评级与 5.2 的逐条成熟度都按修正后的 ① 判。

判据 ② 在本主题尤其难过：**技能提取的公开材料几乎全部是建设方自述**。平台文档由厂商写，本章 §6 的案例由建设方发布，开源项目的能力说明由项目自己维护。「第三方（非厂商）公开生产案例」要求的是一个既不卖这套东西、也不靠它立论的团队，公开描述了自己在生产里的用法与失败。本节口径：**② 只有「满足」与「降为 L2」两种命运**——不能改成「有公开生产记录」，不能靠「本节只评估写入侧」缩小适用范围来绕过，也不存在「准 L1」「L1 的边界案例」这类说法。

另有一条评级规则，全节通用：**按机制分族，一族一行；族的级别取族内最弱子项**。这不是放宽判据，而是读者做规划时的实际含义——族里只要有一个子项不能依赖，这一族的架构就不能整体依赖。族内每个子方向的名字都列在「方向」列里，5.2 逐族拆解，两处的级别与判据必须一致。

| 演进方向（族内子方向） | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **提取链路**：Auto-Skill（LLM 生成技能）/ 离线 Skill Mining / 在线 Procedural Memory（阈值固化）/ Procedural Memory Modeling / LLM 总结 + 人工校验 | L2 | ① 满足：技能模板 schema（本章 §4.5）与平台技能文档可核验；② 不满足：公开案例皆建设方自述；③ 不满足：归并键与入库判据字段各家不一 | 只对高频同构意图开写入；每条带触发条件与成功判据，缺判据的不入库 |
| **样本自造**：Self-Play RL / Workflow Discovery / Auto-Workflow Discovery / Auto-Workflow Synthesis | L3 | ① 不满足：只有论文与技术演示，无跨版本稳定语义；② 不满足；③ 不满足：任务生成器与判据的边界无公开契约 | 记录；只在环境能无人判定成功的领域（编译 / 测试 / 命令退出码）做实验 |
| **组合与跨域**：Compositional Skill / Cross-Agent Skill Transfer | L3 | ① 不满足：跨 Agent 共享只有研究性描述与路线图；② 不满足；③ 不满足：跨 Agent 的 schema 与版本协议未标准化 | 先把自家库的 schema 与版本定下来；不要把跨域共享当作设计前提 |
| **库的出口**：Skill Library 基础设施化 / Procedural Memory 与 Semantic Memory 融合 / Skill 入库为资产 / Skill 建模为图谱节点（GraphRAG）/ Skill 命中率评估 | L2 | ① 满足：资产登记与版本化有公开产品文档（LangChain Hub 2023、PromptLayer 2024，见 [Ch7 §3 §7.3.1](../03-asset-management/03-asset-management-section-7-sec7.md)）；② 不满足；③ 不满足：退役与命中率没有可比口径 | 把 Skill 当资产登记（不可变版本 + Owner + 退役通道）；评估只做观测，不做门禁 |

**本节没有一行达到 L1。** 四行里最高的两行（提取链路、库的出口）都卡在判据 ② 上：拿不出第三方（非厂商）的生产案例。两者也都还缺 ③——提取链路的归并键与入库判据没有统一约定，库的出口缺退役与命中率的可比口径。真正的缺口是「谁在生产里用了、错了多少、怎么回滚」这类材料，而**技能提取还有一个比检索更难的地方：它的效果没有公开可比的度量口径**。检索有命中率，技能库的命中率不算数——一条技能被检索到不等于被采纳，被采纳也不等于结果正确（§3.5 的判据是「成功判据比步骤活得久」，步骤失效时判据照样通过）。没有度量，第三方无法证明自己的用法可复制，采购方也无法判断它值不值得排进路线图。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的技能模板 schema 或平台技能文档能不能找到，字段有没有版本？找不到 → L3。
2. 建设方之外的证据能不能找到？找不到 → L2。
3. 技能的定义字段与归并键明年会不会变？会变 → 至多 L2。

三个常见误判，排路线图时最容易踩：

- **把「有技能库」误当成「有可编程的技能存储」**：能不能按条件检索、能不能按条目退役、能不能回滚到上一版，是三个不同的问题；只提供「保存 / 删除」的产品不构成可依赖的库。
- **把「提取出的条数多」误当成「库好用」**：库的健康指标是去重后的有效数，不是总数（§3.5 Skill 爆炸）。
- **把「一次成功」误当成「可复用」**：验证集必须来自未参与抽象的任务，否则验证只证明了「记得住」（§3.5 Skill 过拟合）。

清单里具名条目 / 产品的落点如下（**只给归属与核验方式，不对其能力下断言**）：

| --- | --- | --- |

这张表的用法是**反向核验**：先看某个产品在功能页上宣称的能力，再回表里找它落在哪一行，然后按该行的判据去看它。同一件产品可能同时落在两行（例如既做提取又在平台内提供技能库），此时要分别评级——**一个产品在两个方向上成熟度不同是常态，整体评成一个级别才是误判**。

### 5.2 演进方向逐条拆解（核心节）

四族按「技能库的哪一段被自动化」排序：提取链路决定技能怎么进库，样本自造决定没有历史日志时样本从哪来，组合与跨域决定技能能走多远，库的出口决定技能被谁消费。四族的级别不同，但失效模式是同一个：**入库这一段有管道，退役这一段没有管道**——§3.5 把 Skill 爆炸、Skill 退化、Skill 私藏三条反模式归到同一个根，说的正是这件事。

还要把「机制改变」与「接口改良」分开，因为只有前者值得排进路线图：

- **接口改良**（写入时机）：离线与在线的差别是「什么时候写、谁来付抽象成本」，抽象产出的形态没变，换一条路径不改变技能是什么。
- **机制改变**（判据来源）：把「看起来对」换成「在未参与抽象的任务上可回放」，这是新增了一道以前不存在的判定——它才是技能能自动入库的原因。
- **接口改良**（schema 统一）：统一描述 schema 让技能能被别的 Agent 读，但技能本身的定义没变，所以它解决的是分发问题，不是能力问题。
- **机制改变**（库的出口多元化）：一旦「去重后的有效数」成为要看的指标，去重与退役就从「可以不做」变成「必须有人做」。

判断只需一句话：如果这条方向只是让同一件事更容易被调用，它是接口改良；如果它让某件以前做不到的事第一次有了判定依据，它才是机制改变。本节四族里属于后者的只有两条，而它们恰好也是评级最高的两行（提取链路与库的出口，均为 L2）。

#### 5.2.1 提取链路：Auto-Skill、离线挖掘、在线固化与人工校验

- **旧做法与它的卡点**：技能要么靠人手写，要么把成功轨迹整段存成模板。手写写不全——技能库的覆盖面永远落后于实际任务分布；存整段模板则换个报错就套不上，因为模板里混着大量与本次任务无关的具体信息。真正难的不是「记下来」，而是「这一条凭什么算技能」——这个判断不落在存储上，落在判据上。
- **AI 改变了什么机制**：把「哪些步骤是必要的」从人的归纳换成一次 LLM 抽象（主文件 [§2.3.2](04-agent-skill-extraction.md) 的「总结 + 模板提取」），并把入库判据从「看起来对」换成一次可回放的验证（主文件 [§2.3.3](04-agent-skill-extraction.md) 的命中率）。写入时机同时被拆成两条可选路径：周期触发（离线）与阈值触发（在线）。
- **由此得到的**：因为抽象被降级成「在若干真实序列里找公共骨架」，所以**只有在簇的层面，「必要」与「偶然」才可比较**，单条轨迹内部无从比较（§3.2.1）——这是批处理路径不可替代的地方；因为每条技能带可回放的判据，所以「偶然成功」能在入库前被过滤，而不是等它在生产里暴露；因为阈值触发的抽象成本挂在「重复程度」而不是「流量」上，所以高频意图常常只付一次抽象成本（§7.3.1）。
- **由此付出的**：抽象出来的可能是「成功那一次的补偿动作」而不是必要步骤——Trajectory 只记动作与结果状态，不含因果说明（§3.1 第二条约束），这个误差在同分布任务上不暴露；归并键成了全局单点，键太粗混槽、太细退化成长尾（§3.2.2 与 §7.3.3）；成功判据比步骤活得久，于是接口改名后表现为静默算错而不是报错（§3.5 Skill 退化）；人工闸门有容量上限，超过容量后退化成盖章（§3.2.4 失效点）。
- **证据与来源**：【公开】技能描述的结构化字段口径写在本章 [§4.5 模板 1](04-agent-skill-extraction-section-4-sec4.md)（`trigger` / `steps` / `success_criteria` / `counter_examples`，可按字段名检索核验当前版本）；【公开】把反思沉淀为可重读文本的公开论文是 Reflexion（Shinn 等，《Reflexion: Language Agents with Verbal Reinforcement Learning》，NeurIPS 2023 会议版；arXiv 条目同样落在 2023 年，引用前请以 arXiv 条目页与会议论文集核验），需注意它的沉淀对象是反思文本而非参数化步骤序列；抽取式技能写入的公开失败率与回滚机制：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「提取链路」行一致：① 满足、② 不满足、③ 不满足）。本条覆盖三个方向：Auto-Skill、Procedural Memory Modeling、LLM 总结 + 人工校验；另按本章的机制口径补入两条细分路径——离线 Skill Mining 与在线 Procedural Memory，二者的定义与代价在 [§3.2.1 / §3.2.2](04-agent-skill-extraction-section-3-sec3.md) 展开。

写入闸门只有三种形态，而它们决定库里最终有什么：

```text
写入闸门（三条路，选错不会报错，只会表现为「库在长、能力不动」）
  ① 周期触发（离线）
     每周期对全量轨迹重跑：归一化 → 聚类 → 抽象 → 留出验证集回放
     闸门位置：命中率过阈值才进候选池，人工复核整批
     代价：新鲜度滞后半个周期
           【推算】抽取时刻在周期 T 内均匀分布，故平均滞后 ≈ T/2
  ② 阈值触发（在线）
     每条轨迹结束时只更新计数；成功率与样本量双阈值都过，才调 LLM 抽象
     闸门位置：两个阈值（示例取值 0.9 与 100【经验：须按业务分布重新标定】）
     代价：长尾键永远过不了阈值，库里没有它们的位置
  ③ 人工闸门（HITL）
     按置信度分流：高分自动入库（仅限可回滚链路），低分进人工队列
     闸门位置：审核容量。超过容量后，闸门退化成盖章
  ────────────────────────────────────────────────
  判定方法：抽最近一个月入库的 10 条技能【经验：随库规模与检索量变，
  库越大抽得越多】，逐条回答「它由哪几条轨迹产生、谁批准的、上一次
  被验证是什么时候」——三问缺一，你手上的是候选池，不是技能库
```

**【推算】阈值触发覆盖的是调用量，不是覆盖率**：设日轨迹 10⁴ 条、意图键 10³ 个，其中 50 个头部键覆盖约 80% 的调用量【经验：随业务分布变，头部越集中该比例越高】。阈值触发只对越过阈值的键付抽象成本，抽象次数 ≈ 50，占全部键的 50 ÷ 10³ = 5%。推导链到此为止是纯除法，读者可复算：**剩下约 950 个键在库里没有位置**，它们对应的调用量只能靠周期触发覆盖，而周期路径的成本形态是「一次全量聚类」的脉冲。这也解释了为什么「用在线固化做长尾」这类误选不报错——它只表现为库看着在长、覆盖率原地不动（§7.4）。

- **失效条件**：当业务口径或工具 API 在**一个周期内**变更时，离线路径会把变更前后两代做法抽象成一份「并集模板」，判别信号是模板里出现两个互斥的步骤（§3.2.1）。在线路径的对应失效发生在意图识别偏移期：两类不同任务被固化到同一个键上，而监控上看不出异常，因为成功率计数是键级的（§3.2.2）。
- **自验方法**：任取一条正在被检索命中的技能，试着回答三件事——它由哪几条轨迹抽象而来、入库时是谁批准的、上一次被回放验证是什么时候（§7.8 小结末段的三问与此同口径）。三件都答得出，提取链路才算建起来了；答不出其中任何一件，你手上的是候选池，不是一条可运维的写入路径。

#### 5.2.2 样本自造：Self-Play RL 与自动流程发现

- **旧做法与它的卡点**：冷启动时没有历史日志，离线与在线两条提取路径都拿不到输入；靠人设计练习任务又受人的想象力限制，覆盖不到 Agent 在实际环境里会碰到的角落。Self-Play 要解决的是「样本从哪来」，不是「怎么抽象」——这个问题在两条既有路径上都无解。
- **AI 改变了什么机制**：把样本来源从人的设计换成一次课程式生成（§3.2.3 的「① 任务生成器」），并让成功判据来自**环境**而不是来自模型自评（编译是否通过、测试是否通过、命令退出码）。Workflow Discovery 与 Auto-Workflow Synthesis 是同一机制在「多步流程」这一粒度上的延伸：前者发现重复出现的流程模式，后者试图直接合成完整流程。
- **由此得到的**：因为样本可以自造、而裁判独立于被训练者，所以这一类路径**不依赖历史日志也能起步**；因为难度旋钮（课程设计）与成功判据（环境反馈）是两个独立部件，所以难度可以自动上调而判据不动——这正是它能把「冷启动」这一条堵上的原因。
- **由此付出的**：只在环境能无人判定成功时成立——一旦成功需要人判断，「自造 + 自评」就退化成自我确认（§3.2.3）；奖励信号会被钻空子（reward hacking），因为判据是真实目标的近似，优化得越久，技能越贴着判据边界而不是贴着目标；训练循环没有自然终点，停早了库不成熟、停晚了成本不可控；Auto-Workflow Synthesis 还多一层代价——流程级的「成功」比单步更难机器判定，因为流程的中间状态通常没有可回放的锚点。
- **证据与来源**：【公开】Voyager（Wang 等，2023；在环境中把自动课程与不断增长的技能库做到系统级，其 arXiv 版本号与首发月份请以 arXiv 条目页为准；判据里含 LLM 作为语义裁判的成分、技能库以向量近邻检索支撑复用，按纯 RL 引用会误导判据来源，§3.2.3）；自动流程合成目前可核到的公开材料是技术演示与产品路线图；第三方（非厂商）生产案例：无公开可核验来源。
- **成熟度**：**L3**（与 5.1 表「样本自造」行一致：① 不满足、② 不满足、③ 不满足）。本条覆盖四个方向：Self-Play RL、Workflow Discovery、Auto-Workflow Discovery、Auto-Workflow Synthesis。

自造样本是否可行，取决于成功能不能被无人判定——这是选型时唯一需要先查的一条：

| 环境类型 | 成功能否无人判定 | 自造样本是否可行 | 可核验的公开形态 |
| --- | --- | --- | --- |
| 代码（编译 / 测试 / 命令退出码） | 能 | 可行 | 公开材料以厂商技术演示为主 |
| 数学与形式化问题 | 能（有形式化判据） | 可行 | 公开论文为主 |
| 游戏（内置胜利条件） | 能 | 可行 | Voyager（2023，§3.2.3） |
| 数据与业务流程 | 通常不能 | 退化为自我确认 | 无公开可核验来源 |

- **失效条件**：当判据与真实目标之间出现可被利用的缝隙时，自造循环会沿判据边界做梯度上升（§3.2.3）。判别信号就是两条曲线的分叉：技能在自造任务上的通过率持续上升，在真实任务抽样上的通过率不动。**这条失效不是调参能修的**——它要求判据与目标重新对齐，而目标通常写不成机器可判定的形式。
- **自验方法**：问自己两个问题就能定位这条路径能不能上——「出题的那个组件，和判分的那个组件，是不是同一个」，以及「如果不看任务结果、只看这条判据，它会不会通过」。第二个问题答「会」时，说明判据是过程的近似而不是目标的度量；此时正确的动作是先补判据，而不是先扩训练轮数。

#### 5.2.3 组合与跨域：Compositional Skill 与 Cross-Agent Skill Transfer

- **旧做法与它的卡点**：技能库按「一次任务一条技能」组织，长任务要么靠人预先编排 Workflow，要么让 Agent 每一步都从库里检索。跨 Agent 时更糟：能力停在各个 Agent 自己的工作目录里，同一个做法被并行造 N 份、口径还各有微差（§3.6 第三条跃迁），迁移只能靠人工搬运。
- **AI 改变了什么机制**：把「技能」从一个整块换成可组合的单元——组合出的复合技能仍带触发条件与成功判据，长任务的自动分解因此第一次有了可验证的终点；同时把共享边界从「Agent 实例」提到「组织级 Skill Library」，用统一的描述 schema 与版本协议连接。这是接口边界的改变，不是换了个前端。
- **由此得到的**：因为能力入库而不入 Agent 实例，所以换框架不必重建库，多个 Agent 能按同一个版本协议取同一份技能；因为复合技能仍带判据，所以「长任务做完了没有」不再靠人看结果，而是靠判据判定。
- **由此付出的**：组合的候选池按平方增长——n 条技能两两组合是 O(n²) 量级的候选，而库的「有效数 / 总数」比值会继续下滑（§3.5 的 Skill 爆炸与 Skill 难复用互为表里）；跨 Agent 必须先统一 schema 并重写存量技能的描述，这笔迁移成本与库规模同向增长，越晚做越贵（§3.6 第三条跃迁）；复合技能失败时，定位到是哪个子技能出错需要额外的证据链（每一步的来源轨迹），单步技能不需要。
- **证据与来源**：跨 Agent 共享与自动组合目前可核到的公开材料是研究性描述与产品路线图；组织级技能库的 schema 与版本协议口径写在本章 [§4.5](04-agent-skill-extraction-section-4-sec4.md)（`apiVersion: ai-skill/v1` 一类）与 [§3.6 第三条跃迁](04-agent-skill-extraction-section-3-sec3.md)；三者的公开生产记录：无公开可核验来源。
- **成熟度**：**L3**（与 5.1 表「组合与跨域」行一致：① 不满足、② 不满足、③ 不满足）。本条覆盖两个方向：Compositional Skill、Cross-Agent Skill Transfer。

组合的候选池增长是这件事最容易被低估的代价：

| 库里的技能数 N | 两两组合的候选数 ≈ N²/2【推算：纯组合计数，N 取该档下限】 | 可核验的收敛手段 |
| --- | --- | --- |
| 10²【经验，量级阈值】 | ~5×10³ | 全量试跑仍可行，靠留出验证集筛 |
| 10³【经验，量级阈值】 | ~5×10⁵ | 必须先用触发条件预筛，再对候选做验证回放 |
| 10⁴【经验，量级阈值】 | ~5×10⁷ | 无标准件；候选远多于验证容量，组合退化成抽奖 |

- **失效条件**：当触发条件写得不够细时，组合会把两条本不该叠加的技能接在一起，而**复合技能的成功判据可能仍然通过**——判据测的是任务达成，不是路径正确。判别信号：复合技能的步骤里出现条件分支，而分支条件对应的是任务**类型**而不是参数取值（与 §3.2.2 在线路径的失效信号同形）。
- **自验方法**：抄出库里触发条件最接近的 10 条技能【经验：随库规模与检索量变，库越大抽得越多】，逐条问「这条能不能由另外两条组合出来」。能组合出来的那些，说明抽象粒度还停在单步层、组合机制根本没被用上；反过来，如果一条复合技能失败后查不出是哪个子步骤错，说明每一步的来源轨迹没有落库。

#### 5.2.4 库的出口：技能库基础设施化、记忆分层与资产化

- **旧做法与它的卡点**：技能库的下游只有一个消费方——本 Agent 运行时的检索接口。于是同一个能力在资产登记表、长期记忆、图谱里各有一份描述，没有一处是「当前值」；退役没有通道，被命中一次就永远留在库里（§3.5 Skill 退化：过期技能仍在被检索命中，且失败不报错）。
- **AI 改变了什么机制**：把库的出口从「一个检索接口」扩成多条消费通道——资产登记（不可变版本 + 别名 + Owner + 退役）、反馈闭环（被选中 / 执行成功 / 用户采纳三段）、长期记忆（程序性记忆与语义记忆分集合、共检索入口）、图谱（技能作为节点参与多跳查询）。机制上的关键变化是：**库第一次有了「整体质量」这个必须有人负责的对象**。
- **由此得到的**：因为技能只采集一次而被多处消费，所以「去重后的有效技能数」可以成为库的健康指标，退役与去重这两件运维动作第一次有了依据（§3.5 三条反模式共同的根就是「提取有管道、退役没管道」）；因为程序性记忆与语义记忆按同一套键做隔离，所以「怎么做」与「是什么」能在同一检索入口里按用途分流，而不是互相挤占排序（§7.2「与相邻方法的边界」）。
- **由此付出的**：出口一多，「谁为库的整体唯一性负责」就成了必须回答的问题；答不出就会退化成多条路径各自在自己的指标上达标而库整体退化（§7.3.4 的失效条件）。命中率不是效用：被检索到不等于被采纳，执行成功也不等于结果正确——§3.5 的判断是「成功判据比步骤活得久」。图谱那一层还有一个自己的代价：节点是「技能」还是「工具调用」决定了多跳查询能否回溯到来源轨迹，混排会让结果不可解释。
- **证据与来源**：【公开】资产登记与版本化的产品文档（LangChain Hub 的公开文档 2023、PromptLayer 的公开文档 2024，见 [Ch7 §3 §7.3.1](../03-asset-management/03-asset-management-section-7-sec7.md)）；【公开】企业级 Agent 平台的动作级留痕与角色绑定（Salesforce 官方文档，2024–2025，可按「Agentforce agent actions」检索核验）；技能级命中率与采纳率的公开可比口径：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「库的出口」行一致：① 满足、② 不满足、③ 不满足）。本条覆盖五个方向：Skill Library 基础设施化、Procedural Memory 与 Semantic Memory 融合、Skill 入库为资产、Skill 建模为图谱节点（GraphRAG）、Skill 命中率评估。

- **失效条件**：当没有人为库的整体质量负责时，「多条出口各司其职」会反转成各出口各自记账——资产表看登记数、记忆层看检索量、图谱看节点数、评估看成功率，四项都在涨，而库里可复用的技能数不动（§7.3.4）。判别信号是把「技能总数」与「去重后的有效数」两条曲线画在一起：前者单调上升而后者走平，即为此症。
- **自验方法**：在同一张图上叠三条曲线——技能总数、去重后的有效数、最近 90 天内被采纳过的技能数【经验：观察窗口随调用频次变，低频业务的窗口应拉长到一年】。第一条涨而第二条平，是库在增长、能力没增长；第三条不动，说明库的出口还没有接到真实消费方，此时补出口比补提取更值。

### 5.3 与本主题既有栈的接口在哪

技能库不是新的一层存储，它是**挂在既有资产、记忆与评估体系之上的一个写入与消费协议**。下表写清谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 提取链路 ↔ [§2.3.3 Skill 验证算法](04-agent-skill-extraction.md) | 轨迹 → 抽象 → 带判据的技能；在未参与抽象的任务集上回放得命中率，过闸门才入库 | 提取侧负责入库精度；运行时不做二次校验 | L2（5.2.1）；验证算法在主文件有定义，闸门阈值与留出切分须自建 |
| 技能存储 ↔ [§4.5 模板 / 示例](04-agent-skill-extraction-section-4-sec4.md) | `apiVersion: ai-skill/v1` 一类 schema：`trigger` / `steps` / `success_criteria` / `counter_examples` 四段 | 库维护者；缺触发条件的库，误触发只是时间问题（§7.3.3） | 字段口径在本章内可核；跨组织无标准 |
| 技能库 ↔ [Ch7 §3 资产管理](../03-asset-management/03-asset-management.md) | Skill 作为一类资产登记：不可变版本 + 别名 + Owner + 退役通道 | 资产侧负责版本与退役；提取侧只产出候选 | L2（5.2.4）；登记语义成熟，技能级语义未稳 |
| 技能库 ↔ [Ch7 §2 反馈闭环](../02-feedback-loop/02-feedback-loop.md) | 调用埋点三段：被选中 / 执行成功 / 用户采纳 | 反馈侧；只测成功率看不见误触发与静默算错 | 能力可用、口径须自建 |
| 技能库 ↔ [Ch7 §1 长期记忆](../01-long-term-memory/01-long-term-memory.md) | 程序性记忆（步骤）与语义记忆（事实）分集合存储，共用检索入口 | 记忆侧负责隔离；混集合会让「怎么做」与「是什么」互相挤占排序 | 存储可复用，边界规则须自建 |
| 技能 ↔ 模型与工具快照 | schema 里记录所依赖的工具 / 接口 / 模型版本，变更时标记需复核 | 库维护者；未记录时表现为「技能过时后仍在被使用」（本章 §6 落地实践「Auto-Skill」一节的组件四「工具与环境的版本绑定」） | 版本绑定已被列为组件之一，无标准件 |

这张表里只有一行是「有现成件可用」：技能按 schema 落库。其余五行**都要自建或自测**，而且失败几乎都落在库维护者之外——提取精度归业务方（他们定义什么算完成），采纳率归产品侧，模型快照归平台侧。把它写进接口表的用处不是分工好看，而是**事故发生时不必现场决定谁负责**；如果这张表在你们那里画不出来，说明技能库还没有人认领。

**判定这张表有没有被用起来**：每个季度核两个数【经验：核对频率随库规模与写入速度变，库越大、写入越快，核得越勤】——去重后的有效技能数（写入侧），以及被检索命中但从未被采纳的技能占比（消费侧）。两个数一个都不看，技能库就还停留在提取管道层。

另有一处边界要单独说清：**技能库与长期记忆不是同一层**。主文件 §2.4 已把「Skill Extraction vs RAG」的差别写成「怎么做 vs 是什么」；落到接口上，程序性记忆的键是任务类型，语义记忆的键是实体，两者可以共用一套检索基础设施，但不能共用一套归并键——用实体键去归并技能，会把「同一个人」的两类任务混进同一个槽位，这正是 §3.2.2 描述的混槽（两类不同任务被固化到同一键上）的变体：集合分开了，归并键没分开。

### 5.4 公开进展与文献

- **论文**【公开】：Voyager（Wang 等，《Voyager: An Open-Ended Embodied Agent with Large Language Models》，2023）把自动课程与不断增长的技能库做到系统级，是样本自造这一族的公开源头之一，但其判据含 LLM 语义裁判、技能库以向量近邻检索支撑复用，引用时请对照论文原文，其 arXiv 版本号与首发月份以 arXiv 条目页为准；Reflexion（Shinn 等，《Reflexion: Language Agents with Verbal Reinforcement Learning》，NeurIPS 2023 会议版）把自我反思沉淀为可重读的文本，是程序性记忆的邻近工作，但**沉淀对象是反思文本而非参数化步骤序列**，把它当作参数化技能的公开实现会夸大其覆盖范围（引用年份之前请以 arXiv 条目与 NeurIPS 官方论文页核验，本章 [§3.2.2](04-agent-skill-extraction-section-3-sec3.md) 同此核验口径）；程序性记忆建模的公开论文：主文件 §1.3 的时间线把它记在 2025-06，本节不转述其结论，定位该文献请按「procedural memory / LLM agent / 程序性记忆建模」一类关键词检索论文库，并以条目页给出的题名、作者与收录信息为准。**引用纪律**：论文里的原型与产品里的实现是两件事，不要把论文结论当作产品能力。
- **官方 release note / 产品文档（判据 ① 的核验入口）**【公开】：技能描述的结构化字段口径写在本章 [§4.5 模板 1](04-agent-skill-extraction-section-4-sec4.md)；平台的技能与编排能力的版本化说明（本章 [§6 落地实践](04-agent-skill-extraction-section-6-sec6.md) 里「Cursor Composer」与「Devin」两节记录的是产品形态，不是技能库能力，核这类能力时看的是有没有可编程的写入、按条目退役与版本化行为说明，而不是有没有「技能」这个词）。
- **第三方（非厂商）公开生产案例**：无公开可核验来源。这是本节没有任何方向被评为 L1 的直接原因（判据 ②）。
- **值得注意的空白**：公开材料里能查到「用了哪条提取链路」，查不到「用了多久、库里有多少条、错了几条、怎么回滚」。这不是因为它们不重要，而是因为技能库的失败通常是静默的（运行了、但采用了过时的步骤），不容易被写成一份可引用的报告。它同时意味着：**这类判断只能自己测**。

还有一处口径必须写清：本节把「产品形态」与「能力评级」分开。本章 §6 的四个案例（Cursor Composer、Devin、单线程长上下文的取舍、从执行轨迹提取技能）记录的是产品与工程形态，它们证明的是「这件事有人在做」，不构成判据 ② 意义上的「第三方（非厂商）生产案例」——建设方自述在本节口径下，正是 L2 的定义所指的那一类。

本节涉及的项目与论文迭代快，最容易出错的三类引用是：

| 引用类型 | 常见错误 | 核验方式 |
| --- | --- | --- |
| 「某项目在某年发表论文」 | 把开源时间当论文时间，或用二手解读代替原文 | 查 arXiv 编号前四位（即提交年月）或对应会议论文集 |
| 「某产品支持技能自动提取」 | 把演示里出现过的能力当成已发布能力 | 查官方文档里该能力的标记（GA / 预览）与适用版本 |
| 「某方案让命中率提升 X%」 | 把建设方自述数字当作可比较结论 | 看验证集怎么切（是否留出）、指标定义，以及有没有建设方之外的复现 |

### 5.5 被过度宣传的部分

**「Agent 会自己总结经验，越用越聪明」**

- *实际是什么*：把「有一条提取管道」当成「有一个能用的库」。决定体感的是检索命中的那几条是否恰好适用，而写入量上升会同时抬高检索空间里的噪声。
- *为什么会这样*：入库这一段有管道、退役这一段没有（§3.5 三条反模式的共同根），而命中率不是效用——被选中不等于被采纳，执行成功也不等于结果正确。
- *什么时候它才会成真*：库的健康指标从「技能总数」换成「去重后的有效数」被普遍采用，且退役有自动通道（最后验证时间、老化检测、定时重放）时。

**「Skill 库跨 Agent 共享，一次沉淀处处可用」**

- *实际是什么*：跨 Agent 共享先是描述 schema 与版本协议的问题，再是权限问题。缺 schema 时，共享出去的是描述不一致的条目，接进来还要人工重写。
- *为什么会这样*：归并键与抽象粒度决定「哪些任务算同一件事」（§7.3.3），而它们在各 Agent 之间没有共同定义；跨 Agent 的冲突仲裁（同一意图有两条相反技能）也还没有规则可依。
- *什么时候它才会成真*：出现被多方采纳的技能描述标准与版本协议，且存量技能完成一次描述重写。与此同时，跨 Agent 的记忆一致性与跨域冲突仲裁仍是开放问题。

**「Self-Play 让 Agent 不依赖历史数据即可自我进化」**

- *实际是什么*：它把「样本从哪来」这一条堵上了，但没有堵上「成功由谁判定」。只在环境能无人判定成功的领域（编译、测试、命令退出码）成立。
- *为什么会这样*：自造循环是一个优化器，它会在判据的边界上做梯度上升（§3.2.3）；判据是真实目标的近似，被优化得越久，技能越贴着判据边界而不是贴着目标。
- *什么时候它才会成真*：出现与目标强相关、又完全机器可判定的判据（这在数据与业务流程里目前写不出来），或出现判据与目标偏差的公开度量口径。

这三条有一个共同结构：它们都把「管道已经就位」说成「能力已经就位」。提取链路的管道确实已经就位（这也是它和库的出口能评 L2 的原因），但「就位」指的是**实现存在**，不是**效果可证**。所以判断它们何时成真的办法是同一个——看公开材料里有没有出现可核验的判断依据（schema 字段、验证集切法、采纳率口径），而不是看产品页上有没有多一个带「Skill」的名字。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 技能条目会把「触发条件 + 成功判据 + 反例」做成入库硬字段（本章 §4.5 的 schema 形态） | 主流平台的技能定义里出现这三个字段的 schema 与校验规则；缺字段不能发布 | 三年后平台的技能定义仍只有名称 + 描述 + 参数 |
| 技能库的运维重点从「提取」转到「去重与退役」 | 出现以「去重后有效技能数」为口径的公开指标或产品功能 | 公开材料仍只报「技能总数」，且没有老化检测这类功能的影子 |
| 跨 Agent 共享长期停在「同一组织、同一 schema」，不进入跨组织流通 | 跨组织共享仍需要人工搬运与描述重写；公开案例都发生在单一组织内 | 出现被多方采纳的跨厂商技能描述标准与目录，且能直接互认 |
| Self-Play 长期只在可判定环境（代码、数学、游戏）成立，不进入数据与业务流程 | 公开材料里 Self-Play 的案例持续集中在可自动判定的环境 | 出现需要人判定成功的数据或业务流程上的公开自造样本案例 |

四条预测都能靠**公开文档与论文**证实或证伪，不需要内部数据：

- 第 1 条看平台的技能 schema 文档，一到两年见分晓。
- 第 2 条看有没有出现「有效数」这类口径的公开指标，两到三年。
- 第 3 条看跨组织案例的形态与描述标准的采纳范围，两到三年。
- 第 4 条看自造样本案例落在哪类环境上，三到五年。

最值得先盯的是第 1 条：它是四条里最先能见分晓的一条（一到两年的窗口，见上列；其余三条是两到三年与三到五年），且它的信号**不依赖任何新模型发布**——schema 由接口设计决定，不由模型能力决定；它也是把技能从「候选池」变成「可依赖资产」的那一步。

第 2 条的影响面最大：一旦「去重后有效数」成为公认口径，本节四行里最高两行的评级就可能同时改变（判据 ③ 会第一次有材料可用）。反过来说，如果你在三年内都没看到这样的口径出现，那么「技能库已经成熟」这个判断就始终缺少公开依据，架构上应当继续按「可以有、不能依赖」来对待。

还有一条不放进表里的观察：本节四行的评级里，唯一可能被**单点事件**改变的是判据 ②。它不需要新技术，只需要一个建设方之外的团队愿意公开写「我们用了、错在哪、怎么回滚」。在这件事发生之前，技能提取的评级上限就是 L2，与实现做得多么完整无关——这也是本节把「本节没有一行达到 L1」写成结论、而不是写成缺口的原因：它是一条可核验的判断，不是一个待补的作业。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 客服 / 助手类 Agent，任务集中在少数高频意图 | 只对高频同构意图开阈值触发的写入（§3.2.2），每条带触发条件与成功判据 | 平台技能定义是否出现 schema 化的判据字段 | 不要让自动提取的技能进入不可回滚链路（涉资金、赔付、资格判定） |
| Coding Agent，任务分布长尾 | 走周期触发（§3.2.1），并把「归一化」这一步补上，否则聚类会混簇 | 离线周期是否短于业务与工具链的变更周期 | 不要用在线固化覆盖长尾——长尾键永远过不了阈值（5.2.1 的推算） |
| 想把技能库做成组织资产 | 先把 schema（`trigger` / `steps` / `success_criteria` / `counter_examples`）与版本协议定下来，再谈共享 | 是否出现跨 Agent 的描述标准 | 不要在架构里假设技能天然跨 Agent 一致（跨域是 L3） |
| 库已有一定规模（【经验】千条以上） | 把「去重后有效数」而非「总数」作为健康指标，补退役通道（最后验证时间 / 老化检测 / 定时重放） | 是否出现公开的去重与退役口径 | 不要靠加大检索 top-k 救误触发——候选池变大会让区分度更差（§3.5） |
| 想做 Self-Play / 自动流程合成 | 只在你确知环境能无人判定成功的领域做实验，并保证任务生成器与判据互相独立 | 是否出现数据 / 业务流程上的公开自造样本案例 | 不要在数据与业务流程里上自造循环——成功需要人判断时它会退化成自我确认（5.2.2） |

「明确不要做」那一列的共用逻辑只有一句：**本节真正变了的是「哪些步骤算技能、凭什么算」的判断方式，没变的是「判断错了谁来发现、谁来回滚」**。所以预算该投在入库判据的可回放、退役通道的可验证、检索命中的可观测三件确定性工程上；在这三件之前，任何「组合技能」「跨 Agent 共享」的规划都不会带来可度量的收益。

最容易被误当成进展的第一步是「先把提取管道跑起来」——它最容易立项、看起来最像进展，产出的却是候选池而不是库。判据很直接：跑完第一个周期后，能不能说出「这个月进了几条、其中几条通过了留出验证、上一次被验证是什么时候」；三个都答不出，管道跑得再顺也只是在堆候选。

如果只能排一个顺序，按这条走：

1. **先定入库判据**：每条技能的触发条件与成功判据必须可回放，验证集按时间或按来源切分，与抽象用的轨迹分开（§3.7 自检清单第 4、5 条）。这一步不需要新采购。
2. **再把退役通道打通**：记录最后验证时间（与最后更新时间分开记），超期自动降级为候选。它是「库不退化」的唯一闸门。
3. **然后给检索加一个可观测信号**：命中但未被采纳的占比，用来发现误触发与静默失效。
4. **最后才谈组合与跨域**：它们会改变 schema 与版本协议，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新的模型能力——schema、留出验证集、退役通道、命中观测，全是工程与流程。这也解释了本节为什么没有 L1：真正已经就位的那部分（存储与检索）不需要被宣传，而需要被宣传的那部分（自造样本、组合、跨 Agent 共享），还没有成熟到能被建设方之外的第三方核验。两者之间的落差，就是本节四行评级全部停在 L2 与 L3 的原因。

### 5.8 小结

> 本节小结：技能提取里 AI 真正改变的只有一条机制——**把「哪些步骤是必要的」从人的归纳换成一次模型抽象，并把入库判据从「看起来对」换成一次可回放的验证**，因此技能库第一次可以不靠人手写而持续增长；它没有改变的是**「判断错了谁来发现」**：入库有管道、退役没有管道，成功判据比步骤活得久，所以过时技能是静默失效的。本节没有 L1 方向：能排进路线图的是入库判据可回放、退役通道可验证、检索命中可观测这三件工程，而不是「组合技能」或「跨 Agent 共享」。
