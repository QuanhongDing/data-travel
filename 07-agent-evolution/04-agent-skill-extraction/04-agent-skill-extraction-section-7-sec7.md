## 7. 与其他方法对比

>
> **证据档位**：【公开】给出来源与年份；【推算】写出推导链；【经验】只给量级与条件，不给精确值。

### 7.1 先立判据：为什么打分表会误导

打分表把一个场景相关的结论写成了绝对结论。「质量：人工编写 5 分、Skill Mining 3 分」——这个 3 分指的是"抽象出的 Skill 不够准"，还是"覆盖面不够"？两者对应的修法完全相反：前者要加验证集，后者要换写入路径。同一维度在不同规模下权重甚至会相反：库里只有几十条 Skill 时，"可解释"几乎不重要；到了 10³ 量级【经验】、多个团队共用时，它变成决定库能不能被信任的那一项（同一阈值在 7.5 节点⑥与 7.8 表里按同一档位使用）。

更根本的问题是：**候选之间不是难度档位，而是四条写入路径**（§3.1）。离线挖掘、在线固化、Self-Play 回答"样本从哪来"；人工编写回答"没有样本时谁写"；HITL 回答"谁批准"；混合模式回答"它们如何在同一个库里共存"。按"先进程度"排序会直接导致误选：Self-Play 看起来最自动，但它的先决条件是环境能给出机器可判定的成功信号，这个条件在多数数据与业务流程里并不成立——它的"先进"建立在别人付不起的前提上。

同理，"效率：Self-Play 5 分、人工编写 1 分"是一条没有信息量的结论：Self-Play 的效率取决于环境判据的质量与训练循环有没有终点，人工编写的效率取决于任务分布的稳定性。同一个分数在两种约束下指向相反的动作。

所以本节用的判据不是七维打分，而是六条约束。它们各自会推翻一条常见直觉：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 样本来源与写入时机 | 样本来自真实轨迹、自造任务，还是人工编写？写入是周期触发还是阈值触发？ | 触发方式由任务频次分布决定：高频意图几次执行就有统计显著性，长尾意图永远凑不够样本 |
| 判据的独立性 | 成功由谁判定——环境信号、LLM 裁判，还是人？ | 判定器与被判定对象同源时，两侧错误相关，验证会一致地漏掉同一类错 |
| 抽象粒度与归并键 | 归并键按意图还是按参数？抽象到什么程度？ | 键太细库里全是重复槽位（难复用），键太粗会把两类任务混进同一槽位（误触发） |
| 变更频率与半衰期 | 业务口径与工具 API 多久变一次？ | 决定 Skill 的半衰期，因而决定离线周期上限与是否必须版本绑定 |
| 错误成本与可回滚性 | 该链路的错误能否在一次回滚内撤销？ | 决定闸门放在阈值侧还是人工侧 |
| 归属与共享范围 | 库是个人的抽屉，还是组织资产？ | 私有 Skill 的跨人复用率为零，且人员流动即归零（§3.5 Skill 私藏） |

判据的用法不是逐条打勾，而是**找出你满足的那一行的否定面**：如果任务频次分布是长尾主导，那么"在线固化"这一列的所有优点都与你无关，而它的阈值触发机制会成为你的主要故障来源。

打分表最容易掩盖的三条机制差异，每一条都独立于行业：

- **写入成本随什么增长**：在线随"重复程度"增长、离线随"轨迹总量"增长、人工随"Skill 条数"增长。三十条 Skill 的团队和三千条的团队，成本曲线形状不同，用同一个 1–5 分描述它们没有信息量。
- **失效发生时能不能被发现**：在线模式的失效（键混槽）在监控上表现为成功；离线模式的失效（并集模板）要到下一个周期才暴露；Self-Play 的失效（reward hacking）只有在自造任务与真实任务的通过率曲线放在一起看时才看得见。
- **谁能叫停它**：阈值可以调、周期可以改、人工可以驳回，但"自造循环什么时候停"必须由人设定——没有停止条件的模式，不该按"自动化程度"拿高分。

还有一条打分表带来的惯性要打破：**不要把"自动化程度"当成选型目标**。自动化是手段，它买到的是"减少人参与"，付的代价是"判据必须能被机器判定"。当你提供不了这样的判据时，提高自动化程度不会减少工作，只会把错误从人看得见的地方搬到看不见的地方——这也是 §3.2.3 失效点（自造循环贴着判据边界跑）在选型阶段的形态。

判据之间还有一个优先级：**判据的独立性 > 样本来源 > 其余四项**。因为它决定闸门能不能自动化，而闸门自动化与否，决定了你后面每一步能省下多少人——反过来，样本来源不理想（例如只有长尾日志）仍然可以用离线挖掘补，判据不独立则没有任何写入路径能救。

### 7.2 候选方案全景

下表「公开参照 / 典型形态」这一列给出的是各候选的**参照物或典型形态**，不构成【公开】证据：全表只有 Voyager 一行带年份（2023，其【公开】出处见 7.3.2），其余各行要么是可自行检索核验的形态描述，要么直接标注了【经验】。表中所有机制描述都是本文按机制推断的，不构成来源。

| 方案 | 定位 | 核心机制（一句话） | 公开参照 / 典型形态 | 归属与许可 |
| --- | --- | --- | --- | --- |
| 人工编写（含 Prompt / 工具定义） | 无样本时的兜底路径 | 人把步骤写死，质量由写的人负责 | 通用 Agent 框架的工具与指令定义 | 自有，可直接编辑 |
| 离线 Skill Mining | 周期批处理的写入路径 | 全量轨迹聚类 → LLM 抽象 → 回放验证 → 入库 | HDBSCAN 一类密度聚类 + LLM 抽象（§3.2.1） | 自建为主 |
| 在线 Procedural Memory | 每条轨迹结束时的写入路径 | 按键计数 → 过阈值才抽象 → 覆盖写 | Reflexion 一类"反思文本沉淀"（§3.2.2） | 自建为主 |
| Self-Play RL | 冷启动的样本自造路径 | 自造任务 → 环境判定 → 强化 / 探索 | Voyager（2023，Minecraft 中的技能库发现） | 研究原型居多 |
| HITL 校验 | 叠加在任一写入路径上的闸门 | 置信度分流：低分候选进人工队列 | 多以组织约束形式存在，少见单独宣传 | 内部流程 |
| 混合模式 | 三条写入路径共用一个带版本的出口 | 离线管长尾、在线管高频、人工管低分 | 多数生产系统最终落到这一形态（【经验】） | 自建为主 |
| Cross-Agent Transfer | 库的分发形态 | 共享库 / 领域隔离 / 联邦 / Skill 市场 | 见下方四条分发路径 | 视形态而定 |

**Cross-Agent Transfer 的四条分发路径**：

- **共享 Skill Library**：所有 Agent 读同一个组织级库，一致性好，但库成为单点，写入权限必须收口。
- **领域隔离**：按金融 / 医疗 / 客服分配库，隔离清晰，但跨域复用率低，同一个做法会被各域各写一遍。
- **Skill 联邦**：跨组织共享，需要"不暴露明细也能校验"的机制——同态加密属于其中一种实现方向。
- **Skill 市场**：Skill 作为可交换资产，需要计量、计费与仲裁，因此它对 Skill 的可验证性要求最高——没有成功判据的 Skill 在市场上无法定价。

这几个系统按机制归位，它们不是同一层的候选：**Voyager**（自造课程 + 技能库检索复用）、**Reflexion**（把反思沉淀为可重读的文本记忆）、**Auto-Skill 与 Compositional Skills**（LLM 生成技能、以及由已有技能组合出新技能）属于写入路径族；**Cursor Composer**（IDE 内的多文件编排，把高频改动模式沉淀为可复用模式）与 **Devin**（端到端自主循环）属于使用侧与执行侧。它们并不在同一层：写入路径族回答「技能从哪来」，使用侧与执行侧回答「谁来用、在哪用」——把它们并列在一起，容易让读者以为两者可以横向比较。

**与相邻方法的边界**：Skill Extraction 与 **RAG** 的区别是"怎么做"与"是什么"——RAG 检索的是事实与文档，Skill 检索的是步骤序列；两者都要检索，但前者的失败表现为"答错事实"，后者的失败表现为"做错流程"，因此后者的验证必须回放到任务上而不能只比相似度（§2.4）。Procedural Memory 与 **Semantic Memory** 的边界同理：程序性记忆存的是"怎么做"且必须可执行，语义记忆存的是"是什么"且只需可读——把反思文本当成可执行步骤入库，是这条边界被跨过时最常见的错误（§3.2.2 对 Reflexion 的口径提醒）。

这七个候选其实分两族：**写入路径族**（人工编写、离线、在线、Self-Play）与**治理分发族**（HITL、混合、Cross-Agent Transfer）。同族内部的差异远小于跨族差异——先确定写入路径，再选治理与分发形态，能省掉一半比较。

九个平台模块，按机制归属只有三处，外加一处三侧共用的落点——缺任何一处都会以特定方式坏掉：

- **写入侧**：轨迹存储（列存或对象存储 + 表格式）、聚类引擎、抽象服务——缺它则没有候选产出，而这一侧最容易买到现成组件，也最容易被误当成全部工作。
- **治理侧**：验证器、HITL 界面、退役器——缺它则"库在长、能力不动"，且过时技能不会被发现；这一侧没有现成组件可买，因为它对应的是流程而不是能力。
- **使用侧**：检索器、评估器——缺评估器则空跑率不可见，而只统计采用次数会系统性高估库的价值。
- **三侧共用的落点**：Skill 存储（Skill Store）——它不属于任何一侧，却是三侧读写权限与版本协议汇合的地方；把它当成"反正已经有一个库了"而略过，等价于略过 7.3.4 的唯一出口。

把九个模块当成平级清单来盘点，最常见的后果是预算与人力几乎全落在写入侧：写入侧有现成工具、有清晰的产出物（候选条数），而治理侧与使用侧的产出物是"没有发生的故障"，很难写进汇报。

**这里需要澄清一个常见误解**：Skill Mining 不是"更高级的日志分析"。日志分析回答"发生了什么"，Skill 提取要回答"以后该怎么做"，因此它的产物必须能被检索、能被回放、能被退役——三个要求分别对应 7.3.3、7.3.2 与 7.7 反模式三。只在"能产出候选"这一点上闭环的管道，不是本节的候选之一，而是一个日志分析工具。

最后补一句关于"归属与许可"这一列的读法：它在这张表里不是法律问题，而是**演进速度问题**。自建路径的每一步（聚类、抽象、验证、退役）都由你自己决定什么时候改；用现成编排框架起步的团队则要接受框架的抽象与节奏。前者慢但可控，后者快但要跟着别人的版本走——这与 7.1 的第六条判据（归属与共享范围）是同一件事的两面：库最终属于谁，决定了谁能改它。

### 7.3 机制差异：为什么它们表现不同（核心节）

**四个模式共用一个分母**：它们都在做「轨迹 → Skill Template → 验证 → 入库」这条链，区别只在这条链上**哪一步被提前或延后**。离线把"聚类 + 抽象"延后到一个周期，在线把"抽象"延后到阈值之后，Self-Play 把"轨迹来源"提前到执行之前，HITL 在"入库"这一步插入人工，混合模式把三者并联。看每个候选时，先定位它在链上动的是哪一步——这比记它的适用场景更能预测它会怎么坏。

下面四节各拆一个机制维度：写入时机、判据来源、抽象粒度、库的出口。它们之间有包含关系——**写入时机决定攻击面，判据来源决定闸门能否自动化，抽象粒度决定复用率，库的出口决定前三者能否共存**。按这个顺序读，比按"哪个方法更强"读更容易定位自己的问题。

#### 7.3.1 写入时机：阈值触发与周期触发

**机制是什么**：写入是"每条轨迹结束时判断一次"（阈值触发），还是"每个周期对全量轨迹重跑一次"（周期触发）。

| 候选 | 触发方式 | 谁承担抽象成本 | 覆盖哪部分任务 |
| --- | --- | --- | --- |
| 在线 Procedural Memory | 阈值触发（成功率 + 样本量双阈值） | 只有过阈值的键付 LLM 抽象成本 | 高频同构意图 |
| 离线 Skill Mining | 周期触发 | 每个簇都要付 | 只要全量日志足够大，长尾也在内 |
| Self-Play RL | 训练循环内批量触发 | 每个训练轮次 | 环境能生成的任务分布 |
| 人工编写 | 人决定 | 人 | 取决于人的覆盖意愿 |

**由此必然导出的性质**：因为在线路径把昂贵步骤（LLM 抽象）放在两个阈值之后，所以写入成本随"重复程度"而不是随"流量"增长——绝大多数轨迹只付一次计数器自增。这条机制反过来推出它的盲区：**长尾 key 永远到不了阈值**，库里长期没有它们的位置。离线路径正相反：因为聚类在**整条轨迹**的向量上做，所以同类任务的不同做法会落进同一个簇，簇内差异正好暴露出哪些步骤共有、哪些可替换——**只有在簇的层面，"必要"与"偶然"才可比较**，单条轨迹内部无从比较（§3.2.1）；代价是新鲜度滞后半个周期（【推算】：抽取时刻在周期内均匀分布，故平均滞后约为 T/2），且抽象成本集中在一次批处理里呈脉冲形态，需要单独做配额规划。

离线路径里有一处不能省的工程前提：**归一化**——把动作名、参数与结果状态对齐到同一 schema。省掉它，聚类会把"调用了同一个工具但参数语义不同"的轨迹混进同一簇，而混簇的后果会一路传导到抽象阶段（产出的模板对任何一类任务都只对一半）。这一点决定了离线挖掘的成败在很大程度上是数据工程问题，而不是聚类算法问题（§3.2.1 图注）。

**公开证据**："从执行轨迹中提取结构化技能"这一方向的工程形态记录在本章 § 6 的 Auto-Skill 案例小节（技能必须带可检验的成功判据、必须能在同类历史任务上回放），具体材料可按机构名与关键词自行核验；阈值型在线固化在公开材料中多以产品能力的形式出现，可按产品的记忆 / 技能功能文档核验（请以官方文档当前版本为准）。

**失效条件**：业务口径或工具 API 在一个周期内变更时，离线会把变更前后两代做法抽象成一份"并集模板"——判别信号是模板里出现两个互斥的步骤（如"用旧接口取状态"与"用新接口取状态"并列，§3.2.1）。在线路径的对应失效发生在意图识别偏移期：两类不同任务被固化到同一键上，而监控上看不出异常（成功率是键级的，键内部换了任务它照样算成功）。

**对选型的含义**：这两条失效方向相反，所以它们**不能靠调参互相弥补**。用在线模式做长尾时的正确动作是换路径（归并键或离线），用离线模式做高频时的正确动作是给头部单独开一条在线通道——两个方向的修法都不是改阈值或改周期，而是改写入路径（§3.3）。

#### 7.3.2 判据的来源：环境、LLM 还是人

**机制是什么**：Skill 是否"有效"由谁判定——环境返回的成功信号、LLM 裁判，还是人工签字。

**实现差异**：Self-Play 用环境信号做硬判定（编译是否通过、测试是否通过、命令退出码）；离线与在线用留出验证集上的命中率（hit_rate），必要时叠加 LLM-as-Judge 补足"过程质量"这一维；HITL 只在低置信候选上请人判定触发条件与步骤必要性。

**因果句**：因为"样本可以自造、但裁判必须独立于被训练者"是自造循环唯一的立身之本，所以 Self-Play 里任务生成器与判据必须是两个独立部件——两者由同一个模型提供时，这个模式就退化成自我确认。同理，因为判定器与被判定对象同源时错误是相关的，所以"让 LLM 当裁判就能自动验"只在判定维度与被判定维度不同的时候成立（环境信号管"成不成"、语义裁判管"好不好"），否则验证会一致地漏掉同一类错（§3.1）。**判据的独立性还决定了一个模式的迁移边界**：Self-Play 在可判定环境（代码、数学、游戏）里成立，搬到需要人来判断成功的数据或业务流程里，就只剩自我确认这一种可能。

**公开证据**：Voyager（2023 年）【公开】是这一族做到系统级的公开案例，但需要注意它的判据里含 LLM 作为语义裁判的成分，技能库以向量近邻检索支撑复用——**把 Voyager 当作"纯 RL"引用会误导读者对判据来源的判断**（§3.2.3，引用时请对照论文原文，其 arXiv 版本号与首发月份以条目页为准）。Reflexion 这一条**不标【公开】**：本节只能给出论文名称与判定方法，给不出可统一的年份（它的 arXiv 记录与会议版年份在不同材料中记法不一），若要引用请按论文标题（Shinn 等，《Reflexion: Language Agents with Verbal Reinforcement Learning》）在 arXiv 条目页与 NeurIPS 官方论文页自行核验年份。判据来源上更需要注意的是：Reflexion 的沉淀对象是**反思文本**而不是参数化步骤序列，把前者当作后者的公开实现会夸大其覆盖范围（§3.2.2）。

**失效条件**：当判据与真实目标之间出现可被利用的缝隙时，自造循环会沿判据边界做梯度上升——Skill 在自造任务上的通过率持续上升，而真实任务抽样上的通过率不动（reward hacking）。判别信号就是这两条曲线的分叉。

**对选型的含义**：判据的独立性可以直接查——问"如果我不看任务结果，只看这条判据，它会不会通过"，以及"出这个判据的组件，和被它判定的那个组件是不是同一个"。HITL 之所以要在闸门上再叠一层人，正是因为前两个问题在任何自动判据上都存在答不好的情况（§3.2.4）。

#### 7.3.3 抽象粒度与归并键：决定库的复用率

**机制是什么**：归并键决定"哪些任务算同一件事"，抽象粒度决定"一条 Skill 能覆盖多少种任务"。

**实现差异**：`apiVersion: ai-skill/v1` 一类 schema 用 `trigger` / `steps` / `success_criteria` / `counter_examples` 四个字段分别承接触发条件、步骤、成功判据与反例（§4.5 模板 1 的完整 YAML）；归并键取"意图 + 关键实体"而不是具体参数取值；抽象度定在"参数化到用户可填具体值"这一层（§3.5 的修法）。

**因果句**：因为在线路径的归并键提供唯一槽位、写入又是覆盖写，所以键太细会让每个键都过不了阈值、库长期为空，键太粗会把两类不同任务固化到同一键上——**两类任务没有并存的余地**，一旦流量短暂偏向另一类并越过阈值，旧的正确 Skill 就被覆盖，而这种覆盖在监控上不表现为失败。离线路径的对应失效是抽象度过低：同一类任务产出多条雷同 Skill、参数各不相同，库规模虚高而复用率不变（§3.5 的"Skill 爆炸"与"Skill 难复用"互为表里）。这也解释了"抽象度的最优边界"这类开放问题的机制形态：**它不是一个可调参数，而是归并键粒度与检索分层共同决定的结果**。

**公开证据**：这一维度没有单一外部基准可引，可核的是本章自带的字段口径：§4.5 模板 1 的 schema 把四件写成 `trigger` / `steps` / `success_criteria` / `counter_examples`；四件齐不齐的逐条判定项另见 §3.5 的修法列（"强制结构化描述"一行）与 §3.7 自检清单第 5 条（"是否带成功判据和至少一条反例提示"），照这两处核验自家库，比对照任何外部榜单都直接。缺触发条件的库，误触发只是时间问题（§3.6 第一条跃迁）。

**失效条件**：检索侧靠加大 top-k 来救误触发，会加速暴露区分度不足——候选池相对大小随库规模下降（【推算】：设库中 Skill 数为 N、每次取 top-5，候选池占比自 N=10³ 的 0.5% 降到 N=10⁴ 的 0.05%；占比下降意味着候选之间的相似度差距被压缩，而排序误差的绝对容差不变，于是同样的 embedding 噪声会造成更多错排——结论是"检索选错"而不是"检索变慢"，§3.5）。

**对选型的含义**：抽象粒度与归并键是**写入侧唯一能事后补救的维度**——检索分层可以救候选过多，但救不了"两条语义相同的 Skill 同时存在"；因此去重与键归并要放在写入侧，而不是等检索侧排序去兜。

归并键定得对不对，有一个可以当场执行的判定方法：**把最近一个月检索命中率最高的 10 条 Skill 的触发条件抄出来，看它们之间有没有两条会在同一个任务上同时命中**。有，说明键太粗；如果另一个极端——同一个业务意图在库里能找到 5 条以上参数各异的条目——说明键太细。这个检查不需要任何工具，只需要库里有触发条件这一字段。

#### 7.3.4 库的出口与版本：决定能不能回滚与一致

**机制是什么**：所有写入路径是直接改库，还是把候选交给一个带版本的**唯一出口**。

**因果句**：因为混合模式下三条路径的成本形态互补（离线是周期脉冲、在线是连续小额、人工是按件计），所以它能让"覆盖长尾、压重复推理、挡高风险"各由最便宜的一层承担；但正因为三条路径写同一个库，所以必须有一个带版本的唯一出口与显式优先级规则——否则离线的候选、人工的驳回记录与线上实际状态会立刻失去一致性，回滚也没有基准点。优先级规则通常**以证据量而非新鲜度**为准：冲突的诱因是"成功"而不是"失败"，同一个意图先由离线挖出一条、后来流量涨上去在线又固化一条，两条都有正面验证记录，删任何一条都在丢证据（§3.5"Skill 冲突"）。

**实现差异**：单一写入出口 + 版本表 + 来源证据（来自哪几条轨迹、样本量、最后验证时间）；Cross-Agent Transfer 之上还要统一描述 schema 与版本协议，存量 Skill 需要重写描述。检索侧的四条匹配方式（关键词 / 语义 / 任务相似度 / 图谱）与三种调用方式（显式工具调用 / 隐式自动选择 / 先检索再显式调用）属于这一层的使用侧实现——它们不改变写入机制，但决定误触发率：关键词匹配召回低，语义匹配的精度依赖分层，而隐式调用把选错直接暴露给用户。技术选型同理：轨迹存储用列存或对象存储加表格式（ClickHouse、对象存储 + Iceberg 一类），Skill 存储用关系库或向量库，检索用 Embedding + BM25 混合，人工审核用标注工具——这些组件可按各自官方文档核验，它们都不是选型维度。

**失效条件**：当没有人为库的整体质量负责时，"三条路径各司其职"会反转成三条路径各自积累、互相覆盖——每一层都在自己的指标上达标（离线看候选池大小、在线看覆盖率、人工看队列清空速度），而库整体退化（Skill 总数在涨、去重后的有效数不动）。

**公开证据**：这一维度没有可以一并引用的统一材料，能核的是各框架官方文档对自身能力边界的描述——RAG 与工具编排框架（LangChain / LangGraph、LlamaIndex 一类）提供的是调用侧编排能力，不是技能提取与治理能力；把编排框架当作提取平台是常见错配。判定方法很直接：打开你所选框架的官方文档，按"是否包含轨迹聚类、验证与退役"三项逐一核对（各框架的模块划分与命名随版本变动，请以官方文档当前版本为准）。

**对选型的含义**：唯一出口是**四个维度里唯一不能省掉的一项**。写入时机与判据来源都可以随场景替换（今天用离线、明天加在线），但一旦有两条路径同时写库而没有版本与优先级，回滚与一致性就无从谈起——所以选型的最后一步不是选模式，而是约定"谁能在库里改什么"。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
总成本 ≈ 采集与存储（随轨迹量线性）
       + f(抽象)：离线为周期脉冲；在线为「过阈值次数 × 单次抽象成本」
       + 验证回放（随验证集规模与 Skill 数）
       + 人工审核（按件，与低置信候选比例成正比）
       + 检索与维护（随有效 Skill 数增长，去重与退役是隐性项）
       + Self-Play 的环境与训练算力（无自然终点，需人为设定停止条件）
```

每个候选的主导项与隐性成本：

| 候选 | 主导成本项 | 隐性成本 | 成本形态 |
| --- | --- | --- | --- |
| 人工编写 | 人的时间 | 覆盖面落后于任务分布、更新滞后 | 线性于 Skill 数 |
| 离线 Skill Mining | 全量轨迹向量化 + 聚类（随轨迹量线性至超线性） | 周期配额的脉冲占用；簇命名错误会带偏整簇抽象 | 周期脉冲 |
| 在线 Procedural Memory | 单次抽象成本 × 过阈值键数 | 归并键维护；覆盖写导致历史版本默认丢失 | 连续小额 |
| Self-Play RL | 环境与训练算力 | 无自然终点；reward hacking 之后"库在长、能力不涨" | 无界循环 |
| HITL | 审核人力 | 队列积压期间，已成功执行但未入职的经验不在库里 | 按件计 |
| Cross-Agent Transfer | 一次建设的 schema 与版本协议 | 存量 Skill 描述重写；跨域冲突仲裁 | 一次性 + 接入成本 |
| 混合（组合 A~E 的形态） | 各层成本之和 | 一致性层与库 owner 的人力 | 三种形态叠加 |

把上表前六行横着读一遍会看到一个结构性事实：**它们的主导成本几乎不在同一项上**——人工的时间、离线的算力、在线的抽象调用、Self-Play 的环境、HITL 的人力、跨 Agent 的协议建设；第七行（混合）不新增主导项，它是这六层成本形态的叠加。所以"哪个便宜"没有统一答案；但它也意味着**混合模式的总成本不是各项之和**：高频由在线承担、长尾由离线承担、低分由人工承担之后，每一层只承担它最便宜的那部分工作量（§3.2.5）。

**【推算】头部 / 长尾两种分布下的写入成本**：设某团队日轨迹 10⁴ 条、意图键 10³ 个，其中 50 个头部键覆盖约 80% 的调用量【经验】。

- 在线路径：只有过阈值的键才付抽象成本，抽象次数 ≈ 头部键数 ≈ 50 次/周期；其余轨迹每条只付一次计数。这 50 条 Skill 覆盖了约 80% 的调用量，而剩下的长尾（约 20% 调用、约 950 个键 = 10³ − 50）在线路径**一条也覆盖不到**，只能交给离线。
- 离线路径：抽象次数 ≈ 簇数，簇数与"意图种类"同阶；若簇数为 10²–10³，则在线路径的抽象次数约为离线的 1/2 到 1/20，且离线每次聚类还要处理整窗轨迹，其采集与聚类成本随轨迹量增长。
- 结论：在头部集中的分布下，在线路径用几十次抽象覆盖了约 80% 的**调用量**——但覆盖面并非"几乎不损失"：它只覆盖了 5% 的**意图键**（10³ 中的 50 个），剩下约 950 个键在库里没有位置，20% 的调用量也就落在库外。**在长尾主导的分布下结论反转**——长尾键永远过不了阈值，在线路径的抽象次数趋近 0，覆盖率也趋近 0（无论按键数算还是按调用量算）。这正是"用在线模式做长尾"这类误选不报错、只表现为"库看着在长、能力不动"的原因（§3.3）。

另一条可复用的量级：离线路径的新鲜度滞后为半个周期【推算】（抽取时刻在周期内均匀分布，故平均滞后 ≈ T/2）。它把"离线周期能取多长"变成一个可算的问题：周期长于业务变更窗口时，挖到的是历史。

还有一项容易被算漏的成本：**判据本身要维护**。环境信号来自编译、测试与退出码，而这些判据会随工具链升级而变化；语义裁判的 prompt 与模型版本同样会变。因此"验证成本"不是一次性的——它是随工具链变更频率增长的经常项，也是 Self-Play 与组合 C 的成本曲线里唯一无自然终点的那一段。判断方法很直接：把你的工具链版本号写下来，问"上一次升级后，有多少条 Skill 被重新验证过"；答不出，说明这条成本还没有被计入。

### 7.5 决策树（我该选哪一条）

```
① 有历史轨迹吗？
   ├─ 没有 → 冷启动：少量人工 Skill 打底 + 明确成功判据
   │        且问：环境能否在无人参与下判定成功？
   │        ├─ 能 → Self-Play RL 可行
   │        └─ 不能 → 先补埋点与判据，不要上自造循环
   └─ 有 ↓
② 单键日执行次数是否已达两位数【经验】？
   ├─ 是（头部集中）→ 在线 Procedural Memory
   └─ 否（长尾主导、但全量日志量充足）→ 离线 Skill Mining
③ 业务口径 / 工具 API 的变更周期是否短于离线挖掘周期？
   ├─ 是 → 在线为主 + 离线定期重聚（混合模式的变体）
   └─ 否 → 保持单一写入路径即可
④ 该 Skill 进入的链路能否在一次回滚操作内撤销？
   ├─ 不能 → 必须叠加 HITL 闸门（低分候选进队列）
   └─ 能 → 可按阈值自动入库
⑤ 库是否被两个以上团队或 Agent 消费？
   ├─ 是 → 组织级库 + 版本化唯一出口 + Cross-Agent Transfer
   └─ 否 → 单团队库 + 显式 owner
⑥ 有效 Skill 数是否已进入 10³ 量级【经验】？
   ├─ 是 → 检索从全量语义检索换成分层检索（触发词预筛 → 向量精排 → 图谱组合）
   └─ 否 → 全量语义检索够用
```

**阈值依据**（与树上节点一一对应）：

- 节点①「有没有历史轨迹 / 环境能否无人判定」：离线与在线两条路径都依赖真实轨迹，冷启动时输入为空；Self-Play 的先决条件是判据来自环境而不是模型自评（§3.2.3）。
- 节点②「单键日执行次数达两位数」：这条阈值卡的是**分布的形状**，不是"几次执行就够算显著"——头部键与长尾键的日执行次数通常相差几个数量级，取值只要落在两者之间，就能把头部与长尾分开，两位数【经验】只是这一档的量级写法（§3.3 用的是同一个阈值）。它和 §3.2.2 的**样本量阈值不是同一件事**：那里的 `stat.count <= 100` 是示例取值，若照它标定，日执行次数刚够两位数的键仍可能过不了样本量这一关。所以两个阈值要一起看——分布决定写不写得到，样本量决定写出来的能不能信。长尾 key 在两条上都过不去，在线路径对它们永不写入（§3.3；两个阈值都请按自己任务的执行频次分布重新标定）。
- 节点③「变更周期短于离线挖掘周期」：周期内的轨迹若横跨两代做法，抽象出的是两代步骤的并集模板（§3.2.1 失效点）。
- 节点④「能否在一次回滚内撤销」：错误成本与可回滚性决定闸门放在阈值侧还是人工侧；纯阈值入库把"统计上够好"当成"可以上"（§3.3）。
- 节点⑤「是否被两个以上团队或 Agent 消费」：私有 Skill 的跨人复用率为零，且人员流动即归零（§3.5"Skill 私藏"）。
- 节点⑥「有效 Skill 数进入 10³ 量级」：库规模上去后候选之间的相似度差距被压缩，排序噪声开始造成误触发——表现是"检索选错"而不是"检索变慢"（§3.6 第一条跃迁，量级阈值为经验值）。

树上六个判断里，②③是关于"分布"的，①④是关于"判据与风险"的，⑤⑥是关于"组织与规模"的。它们之间有一个顺序：**分布判据决定写入路径，风险判据决定闸门，规模判据决定检索与共用形态**——顺序颠倒时最常见的后果是"先建了组织级库，却没有一条能被验证的 Skill"。

本主题下最常被误选的一对，是**在线 Procedural Memory 与离线 Skill Mining**，而且两个方向都会发生。「用在线做长尾」的典型形态是：团队看到在线模式"实时、自动、无需批处理"就选它，但长尾 key 永远到不了阈值，库长期接近空，于是团队得出结论"自动提取不管用"，退回人工编写——**失败原因被记成了"方法不行"，实际是"阈值触发机制与长尾分布不匹配"**。「用离线做高频」的典型形态是：每周重跑全量聚类，产出的是"一周前的主流做法"，在变更期尤为致命，因为那一周的轨迹恰好横跨两代做法，抽象出的模板是两代的并集（§3.2.1 失效点）。两个方向的后果都不表现为报错，而表现为"库看着在长、能力不动"。

误选之后的诊断动作也不同，这一点比结论更重要：在线误用在长尾上，正确动作不是调低阈值（会让长尾 key 在样本不足时被抽象，产出过拟合 Skill），而是**扩容到能覆盖长尾的那条路径**；离线误用在高频上，正确动作不是缩短周期（周期短于变更窗口时挖到的是噪声），而是**为头部意图单独开一条在线通道**。两种修法都是换路径，这也解释了为什么调参往往只是把问题推迟一个周期（§3.3）。

**什么时候该换模式**（这是一条不写在树里、但必须挂在看板上的动作）：模式过时的表现不是性能下降，而是质量指标漂移——误触发率上升、去重后的有效 Skill 数停滞、空跑率上升、同一意图的检索结果在不同时间返回不同 Skill。这四个指标有一个共同点：**它们都不在常规监控上**（§3.6）。因此选型之后要补的第一件事不是加管道，而是把"有效 Skill 数"（而不是总数）与"同意图检索结果的一致性"做成可观测项——否则下一次该换模式时，你看到的仍然只是一条好看的检索延迟曲线。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 冷启动、无日志、环境可判定 | Self-Play RL | 少量人工 Skill 打底 | 人工编写覆盖面落后于任务分布 |
| 冷启动、无日志、环境不可判定 | 人工编写（带显式成功判据） | 先补埋点与判据再提 | Self-Play 在无判定环境退化成自我确认 |
| 高频同构任务（退款 / 工单分类） | 在线 Procedural Memory | 离线挖掘 | 离线要等一个完整周期，期间的重复推理成本已经付掉 |
| 长尾主导、日志量充足 | 离线 Skill Mining | 在线固化 + 离线重聚 | 在线对长尾 key 永不写入 |
| 数学 / 代码等可自动验证的环境 | Self-Play RL | 环境信号 + 语义裁判组合 | 无判定环境的同类做法不可搬 |
| 高合规、不可回滚链路 | 人工编写 + HITL 校验 | 任一自动路径叠加 HITL | 纯阈值入库把"统计上够好"当成"可以上" |
| 多 Agent / 多团队共享能力 | 混合模式 + 组织级库 + Cross-Agent Transfer | 领域隔离 | 领域隔离的跨域复用率低，能力仍在重复建设 |
| 日轨迹量到 10⁴–10⁷【经验】、且要在一个周期内跑完 | 采样聚类（按意图分层抽样）+ 增量聚类 | 每周期全量重聚类 | 聚类的时间与成本随**轨迹量**线性甚至超线性增长，周期内跑不完（§3.6 第四条跃迁）；采样会漏掉低占比但高风险的任务族，需为高风险族保留全量通道 |

> 上表最后一行的判据是**日轨迹量**，不是 Skill 条数——库规模 10² → 10³【经验】触发的是另一条跃迁（全量语义检索 → 分层检索，见决策树节点⑥）。这两个变量经常被并成一格用：库变大并不等于周期跑不完，"跑不完"只跟轨迹量有关；而"检索选错"只跟库规模有关（§3.6）。

五个常见组合，每条给出职责边界与运维代价，以及它们各自成立的前提：

- **组合 A：离线挖掘主管道 + HITL 闸门 + 版本化入库**。职责边界：候选的产出、放行与留痕分属三个部件——挖矿只出候选，闸门只在低分候选上做取舍，版本层只回答"现在生效的是哪一版"。运维代价：它的成本几乎全落在两条与算法无关的线上——审核队列的人力（按件计，随低置信候选比例浮动）与版本表的日常维护；与组合 B 相比它多付一个周期的写入延迟，因此它成立的条件是**这条链路的错误成本高于一个周期的滞后成本**。适合的画像：意图种类在十到百量级、日志量尚未需要采样、链路错误成本中等偏高（【经验】）。
- **组合 B：在线固化主管道 + 离线定期重聚**。职责边界：在线负责把重复推理成本压掉，离线只产出"哪些键该合并、哪个键里混了两类任务"的诊断，改键这个动作必须在别处显式执行。运维代价：在线那一半是连续小额、离线那一半是周期脉冲，两种形态叠在一起，总成本更可预测但更难归因到单一预算科目；键归并是破坏性操作，一旦省掉人工确认，历史统计与库内槽位会一起失配。适合的画像：头部集中、日调用量大、业务口径变化中等（【经验】）。
- **组合 C：Self-Play + 语义裁判 + 人工抽检**。职责边界：环境信号、语义裁判与人各自回答不同的问题——"成不成""好不好""判据本身对不对"，三者不能互相顶替。运维代价：判据自身会随工具链与模型版本过时，需要长期比对自造任务通过率与真实任务抽样通过率的差距；这一项是本表所有组合里唯一没有天然终点的人力 / 算力开销。适合任务可自动验证且环境可控的场景；搬去无判定环境会退化成自我确认。
- **组合 D：组织级库 + 版本协议 + Cross-Agent Transfer**。边界：所有 Agent 通过统一 schema 读写同一份库，"领域隔离"只体现在可见范围，而不是各自建库。运维代价：存量 Skill 要重写描述、冲突要显式仲裁，且必须有人对库的整体质量负责——没有这个角色，三条路径会各自积累、互相覆盖（§3.2.5 失效点）。
- **组合 E：人工编写打底 + 少量自动候选 + 版本化入库**。边界：人负责触发条件与成功判据（这两项最难自动生成），自动侧只负责从轨迹里提出候选与统计数据。运维代价：最小，但覆盖面由人的投入决定；适合刚起步、任务种类在个位数的团队（【经验】）。它常被当成"不够先进"，但它是唯一在没有任何历史轨迹、也没有环境判据时仍然成立的一条。

五条组合各自的前提不同：A、B 需要"真实轨迹"，C 需要"环境可判定"，D 需要"多个消费者"，E 什么前提都不需要——这也是为什么它经常是唯一能立刻开始的一条。

选择组合时唯一需要先回答的问题是"**库里谁说了算**"。组合 A 把决定权交给人工，组合 B 交给统计（归并键的粒度就是它的全部权力），组合 C 交给环境判据。三者可以叠加，但优先级必须显式：多数团队的回答是"听人工"，这会让审核队列成为唯一的质量瓶颈；更稳的回答是"**人工只能收紧、不能放宽**"——人工可以驳回自动入库的候选，但不能把被阈值拒绝的候选直接放行。

**Skill Library 是组织能力的一面镜子，这句话有可操作的版本**：一个部门的 Skill 库能回答"这个部门到底会不会做某类事"，而它的五个可观测指标分别是**库的规模、跨团队复用率、检索命中率、老化周期、演进频率**——前两个看广度，第三个看命中得准不准，第四个看它有没有在腐烂，最后一个看它还在不在长。这五个指标并不落在同一个机制上：规模与命中率对应 7.3.3 的归并键与触发条件（键太细则规模虚高、缺触发条件则误触发），复用率对应 7.3.4 的库出口与共享形态，演进频率对应 7.3.1 的写入时机（提取管道是否还在跑），老化周期对应治理侧的退役动作（7.7 反模式三）。任何一个指标缺失，都会让另外四个变得可以刷。

还有一条判据决定你该选哪几个组合，而不是哪一个：**组合之间不是替代关系，而是覆盖关系**。组合 E 覆盖"没有轨迹也没有判据"的阶段，组合 A、B 覆盖"有轨迹、任务分布单峰"的阶段，组合 C 覆盖"环境可判定"的阶段，组合 D 覆盖"多个 Agent 共享"的阶段。真实系统的迁移不是按时间表发生的，而是按条件逐个触发的：有了真实轨迹才轮到 A 或 B，环境变得可判定才轮到 C，出现第二个消费者才需要 D——而每一次迁移的成本都不在提取管道上，而在描述 schema、版本协议与 owner 的建立上（见 7.7 的迁移表）。

### 7.7 选错的代价与迁移成本

**反模式一：用在线模式做长尾** —— 症状：看到在线"实时、自动、无需批处理"就选它，库长期接近空。机制：阈值触发与长尾分布不匹配，长尾 key 永远到不了阈值。错误的修法是调低阈值——那会让长尾 key 在样本不足时被抽象，产出过拟合 Skill；正确做法是换路径：把相似键归并成更粗的意图（由离线重聚产出归并建议），或整体切到离线挖掘（§3.3）。

**反模式二：把成功轨迹当模板存** —— 症状：换个报错就套不上，模板里含大量与本次无关的具体信息。机制：轨迹只记动作与结果状态、不含因果说明，从结果反推必要步骤时，会把"成功那一次的补偿动作"当成必要步骤；这个误差不会在同分布验证集上暴露，只会在环境变化后暴露。正确做法是提取为「适用条件—步骤—成功判据—反例提示」的结构化技能，并让每一步能追溯到来源轨迹（本章 § 6 的 Auto-Skill 案例、§3.5"Skill 幻觉"）。

**反模式三：只提取不退役** —— 症状：库单调增长，老 Skill 仍在被命中，而失败不报错。机制：成功判据比步骤活得久——步骤依赖工具、接口、字段名这些会变的东西，判据依赖"任务达成"这一层语义，于是接口改名时步骤已经失效而判据照样通过。正确做法是把"最后更新时间"与"最后验证时间"分成两个字段，超期自动降级为候选，并让工具版本变更触发技能复核（§3.5"Skill 退化"）。

**反模式四：把库当成无权限的共享目录** —— 症状：任何自动流程都能往库里写，没人审过的新条目立刻对所有 Agent 生效。机制：库是所有 Agent 的共同执行路径，一条投机或恶意的 Skill 一旦入库，就会以"被检索命中"的方式被反复执行——写入权限与审计要求不应低于代码仓库（【经验】）。可核验的判定方法：库里是否每一条都能回答"最后看过它的人是谁、什么时候"（§3.7 自检清单）。

**反模式五：把提取当成一次性项目** —— 症状：立项时做一轮全量挖掘、上线一批 Skill，之后管道没人维护；半年后库里既有失效条目、也有没人补的长尾。机制：提取是一次性动作，而**去重、退役与重验证是持续动作**——前者有明确产出物可被验收，后者没有，于是在项目制里必然先被砍。正确做法是把"本期退役多少条、重验证多少条"写进运维指标，而不是只统计"新增多少条"：新增量是唯一不需要维护也会自然增长的指标。

| 换过去要动什么 | 离线 → 在线 | 在线 → 离线 | 单一 → 混合 | 单团队 → 组织级 |
| --- | --- | --- | --- | --- |
| 轨迹侧 | 加实时归并键与计数（不必重跑全量） | 建立全量归一化与聚类管道 | 两条管道并存 | 统一埋点 schema |
| Skill 侧重写 | 覆盖写替代追加，需补版本 | 候选池替代线上条目 | 统一描述 schema 与优先级规则 | 存量 Skill 重写描述与可见范围 |
| 闸门与规则 | 双阈值需按新分布重新标定 | 审核队列可保留 | 需显式优先级（通常按证据量） | 需冲突仲裁与库 owner |
| 团队再学习 | 阈值调参与归并键设计（【经验】：周级） | 聚类与抽象 prompt 工程（【经验】：周级） | 一致性层与版本协议（【经验】：月级） | 治理流程与评审（【经验】：月级） |
| 存量候选 | 需把已有 Skill 补上归并键与触发条件 | 需把线上条目降级为候选重跑 | 需为历史条目补来源证据 | 需重新划定可见范围 |

本节的反模式二至五与 §3.5 的反模式共享一个根：**提取有管道、退役没管道**。按缺失的运维动作归类，它们分别是——去重（Skill 爆炸：同一做法被反复写进库）、退役（Skill 退化：过期条目留在库里继续被命中）、收敛（Skill 私藏：能力停在个人侧）、抽象（把轨迹当模板：复用率趋零）、设闸（库无写入门禁：任何流程都能写）、常设（一次性上线：加完就停）。六者的修法都不是更聪明的提取算法，而是那六个缺失的运维动作。

**反模式一不在这六类里，也不共享这个根**：它的成因是**写入路径与任务分布的形状不匹配**，缺失的不是某个运维动作，而是一次路径选择，所以它的修法是换路径（改归并键或换写入路径），调参救不回来（§3.3）。把五条反模式一并塞进"提取有管道、退役没管道"这个根，会让最容易被误选的那一条反而看不出自己的病因。

**跨语种 Skill**（中文与英文 Skill 是否等价）取决于检索侧 embedding 空间的对齐程度，相似度阈值需要按语言重新标定，`hit_rate` 不能跨语言直接比较；**基于 Skill 做反事实推理**（"不用这条 Skill 会怎样"）要求库保留版本与来源证据——没有版本，反事实没有比较基准，这也再次指向 7.3.4 的唯一出口。

迁移的次序也有讲究：**先补描述，再换管道**。存量 Skill 的触发条件、成功判据与来源证据补齐之后，换写入路径只是换一条产候选的管道；反过来做，则会在换管道的同时失去对旧条目的可比性，最终只能推倒重来。这条次序在四列迁移里都成立，也是"迁移成本与库规模同向增长、越晚做越贵"这句话的具体含义（§3.6）。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 高频同构、结果可自动判定 | 在线 Procedural Memory | 昂贵步骤被两个阈值挡住，写入成本随重复程度而非流量增长 |
| 长尾主导、日志量充足、能容忍一个周期滞后 | 离线 Skill Mining | 只有在簇的层面，"必要"与"偶然"才可比较 |
| 冷启动、环境能给出机器可判定的成功信号 | Self-Play RL | 判据来自环境而非模型自评，样本可自造但裁判必须独立 |
| 高风险、不可回滚链路 | HITL 校验（叠加层） | 人工成本与模型的不确定性成正比，而非与库规模成正比 |
| 任务分布多峰、多团队共享 | 混合模式 + 组织级库 + Cross-Agent Transfer | 三条路径成本形态互补，但必须共用一个带版本的出口 |
| 库已到 10³ 量级【经验】 | 分层检索 + 去重 + 退役管道 | 候选池越大区分度越差，误触发先从检索侧暴露 |
| 还没有任何埋点 | 人工编写 + 显式成功判据 | 没有轨迹就没有聚类对象，自动提取无从启动 |
| 工具链与业务口径高频变更 | 在线固化 + 离线重聚 + 版本绑定 | 半衰期短于离线周期时，挖到的是历史 |

> 本节小结：这几个候选之间真正起决定作用的差异只有一条——**"样本从哪来、什么时候写、谁批准"这三件事在同一条写入路径上的组合**。行业、任务类型与模型能力都不决定它；判据的独立性决定闸门能不能自动化，而"成功轨迹不等于正确做法"这一条，决定了每种方法都必须有一个能反转自己优点的失效条件。
>
> 还有一条推论值得单独记住：**库的价值不在"有多少条 Skill"，而在"有多少条能被验证、能被回滚、能被别人用"**。三个指标分别对应验证集的存在、版本层的存在、组织级库的存在——它们都是运维动作，不是模型能力。这也是为什么选型时真正要问的不是"用哪种提取方法"，而是"**退役管道、验证集与人审闸门，你准备先建哪一个**"。
>
> 如果只允许在本节留下一个问题，那应该是：**你的库能不能回答"这条 Skill 谁批准过、依据是哪几条轨迹、上一次被验证是什么时候"**。三个问题里答不出任何一个，说明当前瓶颈不在提取方法上——换方法不会改善它。
>
> 💡 **思考锚点**：把库里两个字段拉出来对一下——「最后更新时间」与「最后验证时间」相差超过你一个治理周期的条目占多少比例？这个比例就是「老化」在你这里的读数。再看运维报表统计的是「新增多少条」还是「退役 / 重验证多少条」——只统计前者，你正踩在反模式五上，而新增量是唯一不维护也会自己涨的指标。
