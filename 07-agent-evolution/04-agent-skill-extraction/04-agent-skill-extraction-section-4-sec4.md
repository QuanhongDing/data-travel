## 4. 工程实现

§3 说明了几条写入路径（离线挖掘 / 在线固化 / Self-Play / 人工闸门）各自被什么约束逼出来，代价与失效点在哪。§4 回答下一个问题：**管道接上之后，第一步产出什么、做到什么程度算过关、已经存在的手写 Skill 怎么办。**

术语沿用主文件与 §3，不另立口径：**轨迹（Trajectory）**、**轨迹簇**、**Skill Template**、**Skill Library**、**归并键**、**验证集与 hit_rate**，以及 Skill 的四个字段——**触发条件 / 步骤 / 成功判据 / 反例**。本节按「落地步骤 → 关键技术点 → 工具链 → 存量迁移 → 模板 → 自检」组织。

读者分两类。**从零搭建**的团队按 4.1 的七步顺序走，4.4 可以略读——管道还没有，也就没有存量。**已经有手写 Skill 库、或已经有人往库里塞过东西**的团队建议先读 4.4：你们最贵的成本不是把管道接起来，而是决定哪些旧条目直接进库、哪些补字段、哪些打标挂账，这件事的顺序与从零搭建完全不同。

### 4.1 落地步骤

七步里有硬顺序，也有可并行的部分（候选池与验证工具可以同时准备）。每一步的三件事都要在当步做完，不能留到下一周补。

**Step 1：收集 Agent 行为日志（1–2 周【经验】，随接入的 Agent 数量与埋点密度变）**

1. 定埋点范围：工具调用序列、每次调用的入参与返回状态、任务终态、失败原因、耗时与 token 数。
2. 按 task 而不是按 request 建主键——一次任务可能包含几十次模型调用，按 request 记会把一条轨迹切碎成几十条。
3. 先只采不洗：这一阶段不判断轨迹好坏，只保证「发生过的事都被记下来」。

- **产物**：轨迹表（task_id / 步骤序列 / 每步入参出参摘要 / 终态）+ 一份埋点字段清单。
- **判据**：抽 3 条最近发生的真实任务，看能否用轨迹表把它们从头到尾还原——缺哪一步的入参摘要，就回到埋点里补哪一列。还原不出来，说明采到的是调用日志而不是轨迹。
- **为什么必须第一步**：后面六步全部以轨迹表为唯一输入，清洗、聚类、抽象、验证都只是它的不同用法。埋点缺一列，补它要重跑整条链；而这一步成本最低、可回退性最好（补埋点不影响线上行为）。

**Step 2：轨迹清洗与归一化（2–4 周【经验】，随接入工具数与命名混乱程度变——工具越多、别名与包装层越杂，归一化的面越大）**

1. 归一化动作名与参数名：把同一个工具的不同写法（大小写、别名、包装层）收敛到同一命名空间。
2. 去噪与去重：剔除被中断的轨迹、调试痕迹，以及同一任务的重复重试（保留最后一次成功的）。
3. 把「策略」与「环境噪声」分开：与任务无关的系统提示、时间戳、随机 ID 从轨迹里剥离。

- **产物**：归一化 schema（动作名词典 + 参数类型）+ 清洗后的轨迹集，并记下丢弃的比例与原因。
- **判据**：抽 20 条清洗后的轨迹，看「调用了同一个工具但参数语义不同」的两类调用是否已能被区分开——它们混在一起时，聚出来的簇会在同一个模板里出现两个互斥分支。
- **为什么必须排在聚类之前**：聚类比较的是动作序列，命名不一致会让同一种做法分裂成多个簇，命名过度合并又会把两种做法捏成一簇。两种错误都不报错，只在抽象出的模板里表现为「有一条永远走不到的分支」。

**Step 3：轨迹向量化与聚类（2–4 周【经验】，随轨迹量与意图数变——轨迹量决定编码成本，意图数决定调参与人工核簇的轮数）**

1. 向量化对象是**整条轨迹**，不是单次调用。
2. 聚类用 HDBSCAN 一类密度聚类（不需要预设簇数、能把噪声单独成簇）；长轨迹可用 Transformer 序列编码加相似度聚类。
3. 每个簇记三件事：簇大小、簇内成功率、簇内轨迹的时间分布。

- **产物**：轨迹簇清单（簇大小 / 簇内成功率 / 时间分布 / 代表轨迹 3 条）。
- **判据**：看噪声簇占比与簇的时间分布——一个簇的轨迹若横跨一次工具改版，簇里就混着两代做法，抽象出来的会是两代的并集。
- **为什么必须这一步**：只有在簇的层面，「必要步骤」与「偶然步骤」才可比较（§3.2.1）。单条轨迹内部无从比较，直接从单条轨迹抽象，产出的是那一次的流水账。

**Step 4：LLM 抽象成 Skill Template（1–2 周【经验】，随待抽象的簇数与返工轮数变——簇数决定要跑多少个抽象批次，四字段缺项、或步骤回溯不到轨迹 ID 时需要整簇重抽，轮数就上去了）**

1. 按簇抽样（不要全量塞进 prompt），把代表轨迹连同簇内差异一起交给模型。
2. 要求输出四个字段：触发条件 / 步骤 / 成功判据 / 反例提示（模板见 4.5）。缺字段的候选不进候选池。
3. 强制每一步标注它来自哪几条轨迹。

- **产物**：候选 Skill 清单，每条带四个字段与逐步的来源轨迹 ID。
- **判据**：抽 3 条候选，逐步骤追问「这一步出现在哪几条轨迹里」——答不出具体轨迹 ID 的步骤就是幻觉候选（§3.5 的 Skill 幻觉），退回重抽。
- **为什么排在聚类之后、验证之前**：抽象是唯一把成本集中起来的步骤（一次 LLM 批处理），它必须吃进已经聚好的簇；放在验证之前，是因为验证集要按簇留出，先验证后抽象等于用同一批数据自证。

**Step 5：Skill 验证（2–4 周【经验】，随验证集规模变）**

1. 留出验证集：用时间更晚、或来自另一批来源的任务，不能与抽象用的轨迹同批切分。
2. 回放并统计 hit_rate（成功次数 ÷ 尝试次数）；可自动判定的部分自动判，其余走人工。
3. 失败案例单独归档，标明失败形态（触发条件不成立 / 步骤缺失 / 判据太宽）。

- **产物**：每个候选的 hit_rate + 一份失败案例表。
- **判据**：抽 3 条被判定为「成功」的记录，人工复核执行结果是否真的达成任务——判据写成「接口返回 200」这类粗口径时，返回空值也会被判成成功。
- **为什么必须有这一步**：一次成功可能靠运气，回放才证明可复用；没有验证集，库里增长的只是条目数而不是能力。

**Step 6：Skill 入库与版本化（1–2 周【经验】，随待入库条目数与资产登记的评审层级变——走组织级资产登记时要多等审批）**

1. 入库字段沿用 4.5 的 schema：触发条件 / 步骤 / 成功判据 / 反例，加来源证据（轨迹条数、成功率、最后验证时间）。
2. 版本化与组织级资产登记联动：Skill 是一种 AI 资产，资产登记与版本协议的约定见 [§ 3 资产管理](../03-asset-management/03-asset-management.md)。
3. 多条写入路径（离线候选池 / 在线固化 / 人工审核）共用一个带版本的出口，任何一条路径都不直接改线上。

- **产物**：Skill Library 条目 + 版本记录 + 每条 Skill 的来源证据。
- **判据**：抽 3 条 Skill，能否回答「最后看过它的人是谁、什么时候」，以及「它的判据上次被验证是哪天」。答不出的条目标记为待审。
- **为什么排在验证之后**：库是所有人检索的输入，未验证的条目一旦入库，误触发的事故会被记在「自动提取」这个方法论上（§3.3 说的误选诊断）。

**Step 7：持续更新与退役（持续）**

1. 重跑节奏与业务变更窗口对齐：口径或工具 API 的变更频率高于重跑周期时，簇里会混进两代轨迹。
2. 记录两个时间：最后更新时间与最后验证时间——被检索命中不等于被验证过。
3. 建退役管道：长期未命中、或回放失败率上升的条目降级为候选。

- **产物**：重跑周期表 + 退役记录 + 每条 Skill 的两个时间字段。
- **判据**：抽查库里的条目，最后验证时间超过一个重跑周期的有多少条——这个数字只增不减，说明退役管道没接上。
- **为什么放在最后但不省略**：提取有管道、退役没管道，库的规模只会单调上升，这是 §3.5 三条反模式共同的根。

**最常被跳过的是 Step 2 的归一化。** 它不产出任何能被上级看见的东西，而轨迹表在 Step 1 之后已经「看起来能用了」。跳过后第一个出问题的时点通常在 Step 4：抽象出的模板里出现两个互斥的步骤（例如「用旧接口取状态」与「用新接口取状态」并列），此时排查会先指向模型「胡说」，实际是聚类把两代做法混进了一个簇。

### 4.2 关键技术点

**1. 行为日志采集（agent run trace）**

- **做法**：按 task 建主键，记录工具调用序列、每步入参出参摘要、终态与失败原因；先只采不洗。
- **机制**：因为 Skill 提取的全部误差都来自「从结果反推必要步骤」（§3 的第二条约束），所以轨迹必须带上每步的入参与返回状态——只记「调用了什么工具」时，抽象只能靠猜来判断哪一步是必要的。
- **失效条件**：**当归档策略按固定窗口截断轨迹、或对长轨迹只保留首尾时**，这条会坏在「补偿动作被当成必要步骤」上，因为失败重试与恢复动作恰好集中在被截掉的中段。症状是抽出的模板里多了一步「重试」，而这一步在成功路径上从未出现过。
- **档位**：埋点字段与 task 主键口径为【经验】。

**2. 轨迹向量化**

- **做法**：把整条轨迹（动作序列 + 关键参数摘要）编成一个向量；长轨迹用序列编码，不要只对首尾或对单次调用编码。
- **机制**：因为聚类要回答的是「两次任务是不是同一种做法」，所以编码对象必须是整条轨迹；按单次调用编码得到的只是「常用动作统计」，那是另一个问题。
- **失效条件**：**当轨迹长度分布很宽（同一意图既有 3 步也有 30 步）时**，定长摘要会把长轨迹压成与短轨迹看不出差别的一段。症状是簇内轨迹的步数方差极大，且抽象出的模板步骤数接近簇内最长的那条。
- **档位**：为【经验】。

**3. 聚类（HDBSCAN / Transformer 序列聚类）**

- **做法**：HDBSCAN（自动选 ε、噪声单独成簇）用于中等规模；长轨迹用 Transformer 序列编码加相似度聚类。
- **机制**：因为密度聚类不需要预设簇数，簇的形状由轨迹本身的密度决定，所以「同一意图的不同做法」会自然落进同一个簇——簇内差异正好暴露出哪些步骤是共有的、哪些是可替换的。
- **失效条件**：**当日轨迹量从万级升到千万级（10⁴ → 10⁷）时**，全量聚类在周期内跑不完（§3.6 的第四条跃迁）；此时应改为按意图分层抽样加增量聚类，但要为低占比高风险的任务族保留全量通道，因为抽样会系统性地漏掉它们。症状是某个低频但关键的任务族长期没有对应的 Skill。
- **档位**：量级阈值为【经验】。

**4. LLM 抽象（输出四个字段，不是输出一段说明）**

- **做法**：prompt 里给出簇内代表轨迹与簇内差异，要求输出触发条件 / 步骤 / 成功判据 / 反例提示，且每一步带来源轨迹 ID。
- **机制**：因为「总结出通用模板」这个指令天然倾向于补齐缺失环节，所以输出必须被四个字段约束住、且每一步可回溯到轨迹——这才让幻觉步骤从「看不出来」变成可检测（§3.5 Skill 幻觉的修法）。
- **失效条件**：**当验证样本来自参与抽象的那批轨迹时**，模板会编码那批任务的具体特征，跨任务命中率骤降。症状是同一批任务的命中率很高、换一批任务就掉到接近零（§3.5 Skill 过拟合）。
- **档位**：为【经验】；prompt 模板见 4.5。

**5. Skill 验证（自动 + 人工）**

- **做法**：自动部分用可机器判定的成功判据（测试通过、退出码、指标达标）；人工部分只审低置信候选，审核项固定为触发条件 / 步骤必要性 / 成功判据 / 反例。
- **机制**：因为人工成本与模型的不确定性成正比、而不是与库规模成正比（§3.2.4），所以把闸门放在「低分侧」的库才能持续变大。
- **失效条件**：**当候选产出速度超过审核容量时**，闸门退化成盖章——症状是审核队列的平均停留时间上升，同时单条审核耗时下降。另一条失效来自判据本身：判据比步骤活得久，接口改名后步骤已失效、判据照样通过（§3.5 Skill 退化）。
- **档位**：审核项与分流口径为【经验】。

**6. Skill 版本化（与资产登记联动）**

- **做法**：Skill 带 SemVer 版本与不可变历史，写入走单一出口；变更记录（谁、何时、依据哪些轨迹）随条目保存。
- **机制**：因为多条写入路径共用一个库时，覆盖写会让历史版本默认丢失（§3.2.2 的代价），所以版本层是回滚的唯一基准点；版本化同时让「评估记录挂到版本上」成立。
- **失效条件**：**当在线路径为了降延迟直接改库时**，离线候选、人工驳回记录与线上实际状态三者立刻失去一致性。症状是同一个意图的检索结果在不同时间返回不同 Skill，而每一次改动都查不到是谁改的。
- **档位**：与 [§ 3 资产管理](../03-asset-management/03-asset-management.md) 的版本协议一致，字段定义以该节为准。

**7. Skill 检索（基于任务匹配 Skill）**

- **做法**：分层检索——触发词预筛 → 向量精排 → 组合匹配；排序里带质量维度（hit_rate、最近验证时间、被采用次数）。
- **机制**：因为库规模上去以后候选之间的相似度差距被压缩，单靠向量相似度会在噪声下错排（§3.5 的推算），所以需要一层可判定的触发条件先做粗筛。
- **失效条件**：**当库里 Skill 数进入千级时**，纯语义检索的误触发率上升，表现为某个高频意图偶发走了错误分支。此时正确的动作是回到写入侧做去重，而不是加大 top-k——候选池变大只会让区分度更差。
- **档位**：库规模量级阈值为【经验】。

### 4.3 工具链与平台

表里给的是类别与判据，不是推荐组合。产品与能力以厂商官方文档当前版本为准；拿不准某工具是否支持某项能力时，用「选型判据」一栏的核验动作确认，不要按宣传材料推断。

| 类别 | 候选 | 选型判据 | 不选它的代价 |
| --- | --- | --- | --- |
| Coding Agent（轨迹的来源） | Cursor Composer、Devin（Cognition） | 它的运行过程能否导出结构化轨迹（步骤、参数、终态），而不只是对话记录 | 只能拿到文本对话时，Step 2 要额外做一遍动作抽取，且抽不准的那部分永久进不了库 |
| 自研 Agent 平台 | Cognition Labs 一类自研平台（Devin 背后的公司） | 平台是否把「任务终态」定义清楚——没有终态的轨迹无法做验证 | 终态模糊时 hit_rate 无从计算，验证环节退化成人工目测，闸门随之失守 |
| 技能库的研究参照 | Voyager、Reflexion | 把它们当**思路来源**而不是现成实现：Voyager 的判据里有 LLM 语义裁判成分（不是纯 Self-Play），Reflexion 沉淀的是反思文本而不是参数化步骤；两篇论文的题名与版本口径见 §3.2.3、§3.2.2 | 把研究原型当生产组件接进来，会一并继承它的判据口径；判据来源不清时，库里积累的是贴着判据边界的投机做法 |
| Agent 编排框架 | LangChain / LangGraph、LlamaIndex | 它负责「把流程跑起来」，不负责「从轨迹里挖技能」：选它的判据是能否把每次调用的入参出参落到自己的存储里 | 把编排框架当成提取平台，最终得到一条 prompt 链加一个向量库——没有验证、没有退役，接着出现的就是 Skill 爆炸与 Skill 退化 |
| 向量化与聚类 | 通用句子编码器类模型、HDBSCAN 一类密度聚类库 | 编码器能否对整条轨迹取向量；聚类能否把噪声单独成簇 | 用需要预设簇数的聚类，噪声会被强行塞进某个簇，抽象出来的模板来自「本来就不像」的轨迹 |
| 轨迹与 Skill 存储 | 关系库 / 对象存储 + 元数据表；已有资产登记平台时接它 | 存储能否回答「这条 Skill 来自哪几条轨迹、最后验证时间是哪天」 | 只存 Skill 正文、不存来源与时间：出现 §3.5 的 Skill 冲突时无法按证据量排序，过期条目也无从暴露——§3.5 说 Skill 退化「完全不暴露」，它唯一的发现途径是主动重放，前提是每条记录都带「最后验证时间」 |
| Self-Play RL 框架 | 类别：任务生成器 + 环境判据 + 强化循环（多为自研） | 判据必须来自环境而不是模型自评——让模型既出题又判分，这一族就没有立身之本（§3.2.3） | 判据与生成器同源时，「自造任务通过率上升、真实任务不动」这类钻空子无法被发现 |
| 人工审核界面（HITL UI） | 通用工单 / 审核队列，或自研队列 | 审核项能否固定为四项（触发条件 / 步骤必要性 / 成功判据 / 反例），而不是按候选自由裁剪 | 审核深度随审核员的忙碌程度浮动，队列压力大时闸门退化成盖章 |

平台形态先用一张模块图对齐即可，不必一次建齐：

│  │  Trajectory  │  │   Cluster    │  │   Abstract  ││

**这一类里最容易被误选的是 Agent 编排框架。** 它离「提取」最近、装起来最快，于是很多团队的第一版方案是「把轨迹塞进 prompt，让模型输出一段步骤，存进向量库」。这条路径缺的正是三个运维动作：验证集、版本层、退役管道——结果不是提取不出东西，而是提取出来的东西慢慢与线上做法脱节，并且没人能发现（§3.5 里三种反模式共同的根）。

### 4.4 存量迁移

已经有 Skill 库的团队，迁移目标不是「换成自动提取」，而是**让旧条目在新管道下有据可查，并且不因为迁移本身把线上行为改坏**。四步按「只读盘点 → 分类处置 → 双轨 → 收口」排。

**① 先做一次只读盘点（1–2 周【经验】，随库条目数与存放分散度变——条目越多、越分散在个人目录与私有 prompt 里，导出与逐条对字段越慢；这一步不改任何线上条目，可回退）**

导出库里全部条目，每条只补五个字段：谁写的、最后更新时间、最后**验证**时间、最后被检索命中的时间、有没有触发条件。这一步不调整任何 Skill 的内容，只产出一次事实基线。它的价值是让后面每一步都能对回这份基线；它可回退，是因为结论不进任何线上路径。

**判据**：数两件事——「最后验证时间」为空的条目有多少，触发条件为空的条目有多少。前者是幻觉与退化的候选池，后者是误触发的候选池。两个数都能数出来，说明基线可用；数不出来，说明库缺字段，先补字段再谈迁移。

**② 历史条目分类处置（不要全部返工）**

| 存量形态 | 处置 | 理由 |
| --- | --- | --- |
| 有触发条件 + 有成功判据 + 有 Owner | 直接进新库，保留原版本号 | 触发条件与成功判据都已具备，返工是净损失 |
| 只有步骤、没有判据（手写 Skill 的多数） | **打标挂账**：标注「判据待补」，仍可被检索 | 一次性补齐会把所有人拖去写文档；挂账期间先靠人工审核兜底 |
| 只有一段提示词文本、没有步骤 | 降级为候选池条目，不占检索位 | 提示词回答的是「说什么」，不是「怎么做」，两者在同一库里会互相污染检索 |
| 停在个人工作目录 / 私有 prompt 里的 Skill | 只做归集与登记，不改写法 | 私有 Skill 的跨人复用率为零，且人员流动即归零（§3.5 Skill 私藏） |
| 已被证明失效、但仍在库里的条目 | 不删，标记为退役并保留历史 | 删除会丢失「它当初为什么进来」的证据，下一次抽象很可能再产出同一条 |

**判据**：抽 3 条被标为「判据待补」的条目，人工执行一次，看能否当场写出一条可判定的成功判据——写不出来的条目说明它本身不可验证，应转入候选池，而不是继续留在检索位。

**③ 双轨怎么维持、维持多久**

双轨的形态是：**手写 Skill 继续对线上生效，自动提取的结果只写候选池**；候选池与线上库分开存储，进库必须经一次人工审核。维持 **1–2 个月**【经验，随意图数与审核容量变——意图数多、审核人手少时会更长】。

双轨期三条纪律：① 不把候选池条目的 hit_rate 与手写 Skill 的成功率直接比较，两者的验证集不同源；② 同一条 Skill 在库与候选池里只有一份正文，避免两处修改；③ 候选池里被驳回的条目保留驳回理由，它是下一轮抽象 prompt 的输入。

**④ 什么信号说明可以退出双轨**

三个可观测信号，同时出现两个即可收口：① 抽 3 个高频意图，自动提取产出的 Skill 在回放中的 hit_rate 不低于手写版本；② 误触发率没有上升——这是 Skill 爆炸最早暴露的地方；③ 同一个意图不再有人手工新增 Skill。

若经过两个完整重跑周期，三个信号全不成立，正确的动作是**把阈值重新标定或退回纯离线**，而不是继续双轨：双轨的隐性成本是同一个意图长期存在两种做法，用户侧看到的是「有时讲理有时不讲理」（§3.5 Skill 冲突）。

**迁移期最常见的三个错误**：① **先跑一遍批处理、再把旧库删掉**——旧条目里含有人工审核留下的判断，删了就没有回滚基准；② **把重跑周期设得比业务变更窗口还短**——周期内凑不够聚类收敛所需的样本量，挖出来的是噪声（§3.1 约束表第四行、§3.3 的误选诊断段；注意这与 Step 7 第 1 条的「变更频率高于重跑周期」是两条不同的约束，后者才对应 §3.6 的第五条跃迁）；③ **只迁移条目、不迁移字段**——触发条件与最后验证时间要么补上、要么显式标为空，沉默缺失会让半年后「库里有多少条其实是死的」这个问题无法回答。

### 4.5 模板 / 示例

**模板 1：Skill 描述 schema（`apiVersion: ai-skill/v1`）**

```yaml
apiVersion: ai-skill/v1
kind: Skill
metadata:
  name: refund-order
  owner: alice@company.com        # 具体到人，不是团队
  version: 1.2.0                  # SemVer：行为变化才动主版本
  tags: [客服, 退款]
  createdAt: 2025-01-15
  source:
    trajectory_count: 1247        # 来源证据：来自多少条轨迹（示例值）
    success_rate: 0.92            # 抽象时该簇的成功率（示例值）
    last_updated: 2025-09-20
    last_verified: 2025-09-20     # 与 last_updated 分开记
spec:
  description: 处理用户退款请求
  trigger:                        # 字段一：触发条件，必须可判定
    intent: "refund_request"
    keywords: ["退款", "退钱"]
    exclude: ["退款政策咨询"]
  steps:                          # 字段二：步骤，每步可回指来源轨迹
    - {step: "验证订单状态", action: "call_api:order_api.get_status",
       params: [order_id], evidence: [traj-8812, traj-9103]}
    - {step: "计算退款金额", action: "compute:refund_amount",
       params: [order_id, reason], evidence: [traj-8812]}
    - {step: "提交退款申请", action: "call_api:payment_api.refund",
       params: [order_id, amount], evidence: [traj-8812, traj-9155]}
    - {step: "通知用户", action: "send_notification",
       params: [user_id, message], evidence: [traj-9103]}
  success_criteria:               # 字段三：成功判据，可机器检验
    - refund_status == "approved"
    - user_acknowledged == true
  counter_examples:               # 字段四：反例提示
    - "订单状态不可退时不要提交退款，先转人工"
    - "金额与订单实付不一致时不要直接提交"
  eval:
    hit_rate: 0.92
    avg_quality: 0.87
```

**怎么用**：填 `trigger` / `steps` / `success_criteria` / `counter_examples` 四段，缺一不可——但四段齐备只说明这条 Skill 能被检索、能被验证。§7.8 小结末段的三问（谁批准过、依据是哪几条轨迹、上一次被验证是什么时候）落在另外三格上：`owner`、每一步的 `evidence`、`source.last_verified`，逐条判定项见 §3.5 的修法列与 §3.7 自检第 1–3 条。`owner` 必须是人；`source` 与 `eval` 两段由管道回填，不要手写；`last_updated` 与 `last_verified` 是两个字段，只有一个时，被命中的 Skill 可能从未被验证过。示例里的条数与比率是占位示例，不要照抄。另有一项当场可做的检查：抄出库里命中率最高的 10 条触发条件，看有没有两条会在同一个任务上同时命中（§7.3.3 末段）。

**模板 2：从轨迹簇抽象 Skill 的 Prompt 与调用**

```python
import openai

SKILL_ABSTRACTION_PROMPT = """
以下是若干次同类任务的成功执行轨迹（同一簇内，含簇内差异）：

{trajectories}     # 每条带 trajectory_id
请总结出可复用的执行技能，并把簇内差异写进反例：

1. trigger —— 什么条件下适用（描述任务特征，不要写"当合适时"）
2. steps —— 参数化步骤，每步标注它来自哪些 trajectory_id
3. success_criteria —— 可被机器检验的完成判据
4. counter_examples —— 该做法在什么情况下不适用

约束：
- 不得引入轨迹里没有出现过的步骤；不确定的步骤宁可不写
- 参数用 {{变量}} 占位，抽象到"用户可填具体值"这一层
- 输出 JSON，字段名固定为 skill_name / trigger / steps / success_criteria / counter_examples
"""

batch_text = "\n\n".join(cluster_trajectories)       # 一个簇的代表轨迹 + 簇内差异，拼成文本
prompt = SKILL_ABSTRACTION_PROMPT.replace("{trajectories}", batch_text)
resp = openai.OpenAI().chat.completions.create(
    model="gpt-4o",                                  # 示例模型：换成你实际使用的模型即可
    messages=[{"role": "user", "content": prompt}],
)
skill_json = resp.choices[0].message.content         # 落库前按 4.5 模板 1 校验四段是否齐备
```

**怎么用**：`{trajectories}` 里必须同时给代表轨迹与簇内差异，只给「最好的那几条」得到的是过拟合模板；「不得引入轨迹里没有出现过的步骤」这一条不能删——它是抑制幻觉步骤的唯一约束，删掉后模型会为模板完整性自动补步骤。调用部分写的是 `openai` SDK 的 `chat.completions` 形状与 `gpt-4o` 这一例，换成别家模型或别的版本时只改这一处，prompt 本身不用动，具体写法以所用 SDK 官方文档的当前版本为准。

**模板 3：轨迹向量化与聚类**

```python
import hdbscan
from sentence_transformers import SentenceTransformer

encoder = SentenceTransformer("all-MiniLM-L6-v2")   # 示例编码器；长轨迹按 4.2 第 2 条换成序列编码
trajectories = [...]                       # 归一化后的整条轨迹文本
embeddings = encoder.encode(trajectories)
clusterer = hdbscan.HDBSCAN(min_cluster_size=10)   # 示例取值，按样本量调
labels = clusterer.fit_predict(embeddings)

clusters = {}
for traj, label in zip(trajectories, labels):
    clusters.setdefault(label, []).append(traj)
# label == -1 是噪声簇：不要丢，它往往对应长尾任务
```

**怎么用**：编码对象必须是整条轨迹，不是单次调用；`min_cluster_size` 是示例取值，取到比「一个意图的日均调用次数」还大时，长尾意图会全部落进噪声簇；噪声簇不要直接丢掉，先看里面有没有低占比但高风险的任务族。

**模板 4：Skill 验证（按时间切分验证集）**

```python
def verify_skill(skill, validation_tasks, checkpoint):   # 验证集须来自抽象之后的任务
    rows = []
    for task in validation_tasks:
        result = apply_skill(skill, task)
        rows.append({
            "task_id": task.id,
            "success": check_success(result, task.expected),
            "failure_mode": classify_failure(result),  # 触发条件/步骤缺失/判据太宽
        })
    hit_rate = sum(r["success"] for r in rows) / len(rows)
    return {"hit_rate": hit_rate, "rows": rows, "validation_window": checkpoint}
```

**怎么用**：`validation_tasks` 必须与抽象用的轨迹按时间或来源切分，同批切分得到的 hit_rate 只证明「记得住」；`failure_mode` 一列不要省——失败形态决定下一轮是改触发条件还是补步骤，只有成功率的报告无法定位。

**模板 5：Self-Play 循环（仅限环境可判定的场景）**

```python
def self_play_loop(agent, library, rounds):
    for _ in range(rounds):
        task = agent.generate_task()                  # 任务生成器
        result = agent.execute(task, library)
        if evaluate(task, result):                    # 判据来自环境，不是模型自评
            library.reinforce(result.used_skills)
        else:
            library.add(extract_skill(result.trajectory))   # 探索分支，不能省
    # 停止条件：环境还能不能给出判定，而不是轮数到了没有
```

**怎么用**：`evaluate` 必须来自环境（测试、退出码、可判定的指标）；让模型既出题又判分时，这个循环退化成自我确认。同时要监控「自造任务通过率」与「真实任务抽样通过率」的差距——差距拉大就是钻判据空子的信号（§3.2.3 的失效点）。任务判据需要人来判断的场景不要用这条模板。

### 4.6 成本：这套东西的账单

三项里两条相关、一条可以忽略，先说结构再说量级。

**云账单**集中在两种形态：一次性的是 Step 3 全量轨迹向量化与 Step 4 每簇一次 LLM 抽象，持续的是 Step 5 回放。抽象账单可用一个算式估：`≈ 簇数 × (单簇 prompt token + 输出 token) × 模型单价`。单簇 prompt 取约 20 条轨迹（4.1 Step 3 定的 3 条代表轨迹，再加若干条簇内差异轨迹）、每条摘要约 1k token【经验，随摘要粒度变】，合计约 2–3 万 token【推算，上式的直接代入】；单价以所选模型官方定价页当前版本为准【经验，随模型厂商与版本变】。关键结论：抽象成本由**簇数（意图数）**决定，与轨迹总量无关——同一意图多采一万条轨迹，抽象的账单不涨，涨的是向量化与存储。

**人力**是这个主题真正的大头，而且它的计价方式与库规模无关、与**模型的不确定性**同向（§3.2.4）。归一化（Step 2）是纯粹的人力投入，工具越多、别名与包装层越杂，面越大；审核（Step 5）是持续投入，候选产出速度一旦超过审核容量，闸门就退化成盖章。§4.1 说最常被跳过的是 Step 2——从账上看正因为它是三处成本里唯一「花在人身上、当期看不见产出」的一处。

**硬件**这一项可以基本忽略：按 task 建主键的轨迹表是输入侧最大的一份存储，但它便宜。这个主题贵的地方不在算力，而在**记录纪律**：触发条件、最后验证时间这些字段，缺一列，半年后「库里有多少条其实是死的」就答不出来，补它的代价是重跑整条链——这正是 §4.4 ② 选择「打标挂账」而不是一次性返工的原因。

这道账的特殊性在于：输入可以很便宜地堆，输出却按**人工判断的次数**计价，而判断次数由聚类分不分得开决定——Step 2 省下的钱，会在 Step 4 的整簇返工上还回来。通用的成本归因方法见 [11-cross-cutting/03-data-cost-finops](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)、容量规划方法见 [12-architecture/04-capacity-planning](../../12-architecture/04-capacity-planning/04-capacity-planning.md)，本节只给本主题特有的结构。

### 4.7 容灾与故障演练

先说清为什么这里不谈跨地域容灾：管道本身无状态，轨迹表在，就能从 Step 1 重跑重建成库；**唯一不可重建的资产是 Skill Library 连同它的来源证据（每条 Skill 来自哪几条轨迹、最后验证时间）**。所以本主题的「容灾」是保护这份带证据的版本历史（§4.2 第 6 条的单一出口 + SemVer 不可变历史），而不是多机房切换——把库迁到异地而不迁证据，等于迁了一个无法验证的副本。跨地域多活与备份的通用做法见 [12-architecture/07-disaster-recovery](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)，本节只列本主题特有的失效形态。

| 失效模式 | 影响面 | 降级策略 | 恢复目标 |
| --- | --- | --- | --- |
| 埋点按固定窗口截断轨迹（§4.2 第 1 条） | 补偿/重试动作被当成必要步骤，抽出的模板带幻觉步骤 | 回退到未截断的埋点口径，重跑 Step 2–4 | 丢的是轨迹完整度而非库；恢复点取「上一次口径变更」【经验】 |
| 聚类把两代做法混进一簇（跳过 Step 2 的典型后果） | 模板出现互斥分支，误触发打到线上 | 冻结该簇入库，退回 Step 2 重做归一化 | 单簇级，不动已入库条目；小时级【经验】 |
| 验证集与抽象集同批切分（§4.2 第 4 条） | 命中率虚高，过拟合条目入库 | 作废该验证记录，按时间重切后复验 | 恢复点取「上一个可信验证窗口」【经验】 |
| 在线路径直改库（§4.2 第 6 条） | 离线候选 / 人工驳回 / 线上状态三方不一致，且查不到改动人 | 关掉在线写入，回滚到上一版库，恢复单一出口 | RTO 小时级【经验】，取决于版本历史是否完整 |
| 判据比步骤活得久（§3.5 Skill 退化） | 接口改名后步骤已失效、判据照样通过，**不暴露** | 主动重放（唯一发现途径），命中率骤降即降级为候选 | 无自动恢复，靠重放周期兜底 |

演练方案不是切机房，而是**把故障注入到管道的数据侧**：注入「工具改名」「归档截断」「验证集同批切分」三类扰动，看四个质量指标（误触发率、空跑率、去重有效数、同意图一致性）是否暴露——指标不暴露，说明监控缺的是质量维度而不是性能维度（§3.6 末段）。混沌方法论见 [12-architecture/06-chaos-engineering](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)。

### 4.8 演进路线：0 → 1 → 100

**0 → 1（最小可用）**：单 Agent、两三个高频同构意图，离线挖掘跑通一次全链——一条轨迹表 → 一个验证集 → 一条入库带四字段的 Skill。这一阶段变贵的是**埋点与归一化的人力**（Step 1–2）；先坏的是**验证集**：没有它，唯一能证明「可复用」的证据就缺了，第一次跨任务命中率骤降会被归到模型头上，实际是拿同一批数据自证（§3.5 Skill 过拟合）。此刻按 4.3 模块图注，没有数据的模块先不要建。

**1 → 100（规模化）**：意图数上升、Agent 变多、日轨迹量上量级。触发 §3.6 的前两条跃迁——库从 10² 升到 10³【经验，量级阈值】时全量语义检索开始误触发，要换分层检索；维护者从 1 人变多团队时人工全审退化成盖章，要上置信度分流。这一阶段变贵的是**审核容量与归一化面**；先坏的是**闸门**：队列停留时间上升、单条审核耗时下降，就是闸门开始盖章的信号。轨迹量再上 10⁴ → 10⁷【经验，量级阈值】时，全量聚类周期内跑不完，换成采样 + 增量，代价是低占比高风险的任务族被系统性漏掉，需为它们单独留全量通道。

**100 →（下一道坎）**：库进组织级、跨 Agent 共享能力（注意：Cross-Agent Transfer 本身按 §5 属 L3——跨 Agent 的 schema 与版本协议尚未标准化，这一档可先落地的只有 schema 与版本协议的统一，不要把共享当作设计前提）。变贵的是 **schema 统一与存量重写**——分层检索要补历史 Skill 普遍缺失的触发条件，这是一次批量重写，重写期误触发率先上升（§3.6 第一条跃迁的迁移代价）；先坏的是**口径**：各 Agent 各自建库导致能力重复建设、跨 Agent 迁移只能靠人工搬运。收敛到组织级库之前要先定描述 schema（4.5 模板 1）与版本协议，否则跨 Agent 迁移没有共同格式可搬。更远的方向（程序性记忆建模、组合技能、库基础设施化）见 [§ 5 前沿演进](04-agent-skill-extraction-section-5-sec5.md)。

### 4.9 自检清单

1. 抽 3 条最近的真实任务，看能否还原出完整的工具调用序列与每步入参——缺哪一列就说明埋点缺哪一列。
2. 抽 20 条清洗后的轨迹，看「同一工具、不同参数语义」的调用是否已能被区分开。
3. 看聚类结果的噪声簇占比与簇的时间分布：有没有哪一个簇横跨了一次工具改版。
4. 抽 3 条候选 Skill，逐步骤问「它来自哪几条 trajectory_id」，答不出的步骤即为幻觉候选。
5. 验证集与抽象集是否按时间（或来源）切分？同批切分得到的命中率不算证据。
6. 每条 Skill 是否同时具备触发条件、步骤、成功判据、反例四个字段？
7. 「最后更新时间」与「最后验证时间」是不是两个字段？
8. 抽 3 条 Skill，能否回答「最后看过它的人是谁、什么时候」。
9. 有没有一个为库整体质量负责的角色或门禁？三条写入路径各自看自己的指标时，Skill 爆炸只是时间问题。
10. 库里 Skill 总数与去重后的有效数，最近一个周期各涨了多少？只有前者涨，说明缺去重。
11. 上一季度退役了几条？一条都没有，通常不是因为没有过期条目。
12. 抽一条 Skill 与它最近一次被调用的轨迹比对：Agent 是否真的按它执行？

### 4.10 小结

> 本节小结：七步里唯一不可替代的是 **Step 2 归一化与 Step 5 验证集** 这一对——归一化决定聚类比较的是不是同一种做法，验证集决定入库的是不是真的可复用。两者都产不出当期可见的成果，因此最容易被推迟；而跳过它们的代价不在当季爆发，而是在第一次遇到「库里条数在涨、能力不动」时一次性还清——那时你已经无法区分哪些条目是幻觉、哪些是过拟合、哪些只是过期。
>
> 还有一条推论值得单独记住：**这套管道的产出不是一个「方法」，而是一组运维动作**——去重、退役、收敛到组织级库。提取算法可以换，这三个动作换不掉；§3 的八条反模式里有三条同源于此。
>
> 💡 **思考锚点**：翻你现在的 Skill / Prompt 库：有多少条答得上「最后验证时间」和「触发条件」这两个字段（答不出的就是幻觉与误触发的候选池）？你打算按本节的双轨给它留 1–2 个月、用验证集现算一次 hit_rate，还是直接全量切到新管道？
