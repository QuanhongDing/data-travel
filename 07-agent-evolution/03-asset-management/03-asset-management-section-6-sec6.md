## 6. 落地实践

### 6.1 字节"**扣子 Coze：给 Agent 资产装上五阶段生命周期 4+ 年**"（2020-2024）

**背景（Why）**

字节 2020 年面临**"Agent 越建越多，却没人管得住"**：
- **4 业务各自建 Agent**——**同一能力的 Prompt、插件、工作流被重复实现，质量参差**
- **没有生命周期概念**——**建了就一直挂着，没人知道哪些还在用、哪些该下线**
- **改了就回不去**——**Prompt 改坏之后无法定位"上一版是什么"，只能凭记忆重写**
- **责任不清**——**某个 Agent 出问题，找不到负责人**

**触发点（What）**

2020 年字节推进**扣子 Coze 的 Agent 资产管理（含生命周期与版本）**（[字节扣子 Coze 公开材料 2020-2024]），目标：
- **资产有生命周期**——创建 / 评审 / 上线 / 迭代 / 下线
- **版本可追溯可回滚**——Prompt、工作流、插件都版本化
- **责任到人**——每个资产有 Owner

**详细做法（How）**

扣子 Coze 资产管理的**5 大核心组件**：

1. **五阶段生命周期状态机（核心创新）**
   - 关键设计：**每个 Agent 资产必须按"草稿 → 评审 → 上线 → 迭代 → 下线"流转**，状态变更需要相应权限；**下线的资产仍保留历史版本**，可随时恢复
   - 关键能力：**"资产数量只增不减"这一必然趋势被机制化解决**——没有下线通道的资产目录，三年后一定无法维护
   - 关键数字：**生命周期覆盖率 100%、僵尸资产可识别**
   - 关键示意：
     ```text
     资产生命周期状态机（每次流转都需要权限与记录）
       草稿 ──提交──▶ 评审中 ──通过──▶ 已上线 ──┬──▶ 迭代中 ──▶ 已上线
         │              │                      │
         │           驳回│                      │ 长期无调用 / Owner 确认
         ▼              ▼                      ▼
       已废弃 ◀────── 已废弃 ◀────────────── 待下线 ──确认无调用──▶ 已下线
                                                              │
                                                      保留历史版本，可恢复
     ────────────────────────────────────────────────
     关键点：
       · 上线不是终点，而是"迭代"的起点（大部分时间资产处于"迭代中"）
       · 下线必须有"调用方清单 + Owner 确认"，而不是按时间硬删
       · 下线 ≠ 删除：历史版本保留，避免"删了发现有人在用"
     -- 关键：把"管得住"表达成一个显式状态机，而不是靠人记
     ```

2. **Prompt / 工作流 / 插件的独立版本化（核心）**
   - 关键设计：**三类资产各自版本化**；Agent 引用的是"某个具体版本"，而不是"最新版"
   - 关键能力：**改 Prompt 不再影响已在线的 Agent**——这是"能安全迭代"与"不敢动"的分水岭
   - 关键性质：**版本可回滚、引用可固定**

3. **依赖关系与影响面（核心）**
   - 关键设计：**记录 Agent 引用了哪些 Prompt / 插件 / 工作流**；变更前列出受影响资产
   - 关键能力：**"改这个插件会影响哪些 Agent"可查**，而不是上线后由业务反馈
   - 关键性质：**依赖可追、影响面可列**

4. **Owner 与调用统计（核心）**
   - 关键设计：**每个资产有具体 Owner**；统计调用量与最后调用时间
   - 关键能力：**"这个 Agent 还有没有人用"可回答**——下线决策有依据，问题也有明确联系人
   - 关键数字：**Owner 覆盖 100%、调用可统计**

5. **评审清单化（核心创新）**
   - 关键设计：**上线评审按清单执行**（能力边界、数据来源、权限、成本预期、失败兜底），而不是凭感觉放行
   - 关键能力：**评审从"看一遍"变成"逐项确认"**——这是质量下限能被守住的原因
   - 关键数字：**评审清单 100% 执行**

**字节扣子 Coze 资产管理关键数字**（[字节扣子 Coze 公开材料 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **资产生命周期** | 无（建了就挂着） | 五阶段状态机 | **可管可控** |
| **版本管理** | 无（改了就回不去） | Prompt / 工作流 / 插件独立版本化 | **可回滚** |
| **引用方式** | 引用"最新版" | 引用固定版本 | **改动不影响在线** |
| **依赖可见性** | 不清楚谁在用 | 依赖关系 + 影响面可列 | **∞** |
| **Owner 覆盖** | 无 | 100%（具体到人） | **责任明确** |
| **调用统计** | 无 | 调用量与最后调用时间 | **下线有据** |
| **评审方式** | 凭感觉 | 清单化逐项确认 | **质量下限可守** |
| **下线机制** | 只增不减 | 待下线 → 确认无调用 → 已下线（保留历史） | **目录可维护** |

**具体数字（How much）**

- 团队规模：字节扣子 / 平台团队数百人
- 关键数字：**五阶段生命周期**；**独立版本化**；**Owner 100%**；**下线有据**
- 业务影响：支撑平台上大量 Agent 的可管理演进，覆盖字节内部多业务与对外开发者

**失败教训**

- 早期「**建了 Agent 就一直挂着**」——目录随时间失控、无人知道哪些还在用，倒逼**「引入五阶段生命周期与调用统计」**
- 「**Prompt 改了无法回退**」——改坏之后只能凭记忆重写，倒逼**「Prompt / 工作流 / 插件独立版本化」**
- 「**Agent 引用"最新版"**」——某次改 Prompt 意外影响多个在线 Agent，倒逼**「引用固定版本，升级需显式操作」**
- 「**下线按时间硬删**」——删了之后发现有业务在用，倒逼**「下线前确认无调用 + 保留下线资产的历史版本」**

### 6.2 阿里"**通义 25 BU 的 AI 资产登记与复用：把 Prompt 与工具当成公司资产 4+ 年**"（2020-2024）

**背景（Why）**

阿里 2020 年面临**25 BU 重复造同一类 AI 能力**：
- **同类能力被反复实现**——**"文本摘要""意图识别""商品打标"这类能力在多个 BU 各写一套 Prompt**
- **找不到已有资产**——**不知道公司里已经有人做过，于是从零开始**
- **质量无法横向比较**——**同一个能力有 5 个版本，但不知道哪个效果好**
- **合规与成本**——**不同 BU 各自调用模型，成本与数据使用边界都难以统一**

**触发点（What）**

2020 年阿里推进**通义 AI 资产登记与复用体系**（[阿里通义公开材料 2020-2024]），目标：
- **能力可发现**——先搜已有资产，避免重复建设
- **质量可比较**——同一能力多版本之间有统一评测
- **成本与边界统一**——模型调用与数据使用走统一通道

**详细做法（How）**

阿里 AI 资产体系的**5 大核心组件**：

1. **"能力"作为登记单位，而非"实现"（核心创新）**
   - 关键设计：**登记的是"能力"（如"商品标题质量评估"），其下可以挂多个实现版本**；业务方按能力搜索，再选实现
   - 关键能力：**避免"同一能力 5 个实现却互不知晓"**——搜索粒度从"某个 Prompt"上升到"某类能力"
   - 关键性质：**能力级登记、跨 BU 可搜可复用**
   - 关键示意：
     ```text
     登记粒度：以"能力"为单位组织，实现版本挂在能力下
       能力：商品标题质量评估
         ├─ 实现 v1  来源：天猫搜索团队  评测：F1 = 0.82  成本：低
         ├─ 实现 v2  来源：淘宝内容团队  评测：F1 = 0.87  成本：中
         └─ 实现 v3  来源：通义实验室    评测：F1 = 0.91  成本：高
                      ▲
       业务方视角：
         ① 搜能力（"标题质量评估"）→ 直接看到三个实现
         ② 按"效果 / 成本 / SLA"筛选，而不必自己从零写
       ────────────────────────────────────────────────
     对照"以 Prompt 为单位登记"：
       搜到 50 个 Prompt 片段，但看不出哪个解决的是同一问题
       → 无法比较、无法复用，登记价值大打折扣
     -- 关键：登记的粒度决定了"复用是否真的会发生"
     ```

2. **统一评测与横向比较（核心）**
   - 关键设计：**同一能力下的实现用同一套评测集打分**，结果公开可见
   - 关键能力：**"用哪个实现"有客观依据**，而不是谁的名气大用谁的
   - 关键性质：**同能力评测口径统一**

3. **统一调用通道（核心）**
   - 关键设计：**模型调用走统一网关**，成本按 BU 归因；数据使用边界由平台统一约束
   - 关键能力：**成本可见、边界统一**——避免各 BU 各自接模型导致预算与合规双失控
   - 关键性质：**调用统一、成本可归因**

4. **Owner 与版本演进（核心）**
   - 关键设计：**每个实现有 Owner 与版本历史**；能力下的实现可新增、可标记推荐版本
   - 关键能力：**资产随使用自然演进**，推荐版本由评测与使用量共同决定
   - 关键性质：**Owner 覆盖、推荐版本机制**

5. **复用度作为资产指标（核心创新）**
   - 关键设计：**统计每个实现被多少业务引用**，复用度高的在搜索结果中优先
   - 关键能力：**"好资产"自动浮现**——这比行政要求"要复用"有效得多
   - 关键性质：**复用度可统计、排序可优化**

**阿里 AI 资产体系关键数字**（[阿里通义公开材料 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **登记粒度** | 无统一登记 | 能力级登记 + 实现版本 | **可搜可比较** |
| **重复建设** | 同类能力多 BU 各写一套 | 复用已有实现 | **显著下降** |
| **质量可比性** | 无法横向比较 | 同能力统一评测集 | **有客观依据** |
| **BU 覆盖** | 各自为战 | 25 BU 统一体系 | **∞** |
| **调用成本** | 各自接模型，无法归因 | 统一网关按 BU 归因 | **可归因** |
| **数据使用边界** | 各自约束 | 平台统一约束 | **一致** |
| **资产演进** | 无版本无 Owner | Owner + 版本历史 + 推荐版本 | **可维护** |
| **复用引导** | 靠行政要求 | 复用度可统计并影响排序 | **有效** |

**具体数字（How much）**

- 团队规模：阿里通义 / 数据中台团队数百人
- 关键数字：**能力级登记**；**25 BU 统一**；**同能力统一评测**；**成本可归因**
- 业务影响：覆盖阿里集团内 25 BU 的 Prompt / 工具类 AI 资产登记与复用

**失败教训**

- 早期「**以 Prompt 为单位登记**」——搜出一堆片段却看不出哪些解决同一问题，倒逼**「以"能力"为登记单位，实现版本挂其下」**
- 「**同一能力多个实现却无法比较**」——选型凭名气，倒逼**「同能力用统一评测集打分并公开」**
- 「**各 BU 各自接模型**」——成本无法归因、数据边界不一致，倒逼**「统一调用网关 + 按 BU 归因」**
- 「**靠行政要求推动复用**」——推不动，倒逼**「统计复用度并影响搜索结果排序，让好资产自然浮现」**

### 6.3 OpenAI"**GPT Store：用"上架 + 版本 + 分发"管理第三方资产 3+ 年**"（2021-2024）

**背景（Why）**

OpenAI 2021 年面临**"平台上的资产由第三方创建"带来的治理难题**：
- **构建者众多且水平不一**——**官方无法逐一定制，但也不能放任质量**
- **资产会持续迭代**——**上架后还会改配置，用户看到的版本必须明确**
- **责任边界**——**某个应用出问题，需要能定位到构建者与当时的配置版本**
- **分发现状差**——**好资产难以被发现，重复建设普遍**

**触发点（What）**

2021 年起 OpenAI 推进 **GPT Store 的资产上架与分发机制**（[OpenAI 公开材料 2021-2024]），目标：
- **资产可上架可发现**——构建者自助发布
- **版本与责任明确**——配置版本可追溯
- **质量下限可控**——上架与运营有约束

**详细做法（How）**

GPT Store 资产治理的**5 大核心组件**：

1. **上架即登记完整元数据（核心创新）**
   - 关键设计：**上架时必须提交能力说明、知识来源、可用动作、适用边界与失败表现**；这些元数据既是"给人看的介绍"，也是"给平台治理用的清单"
   - 关键能力：**"这个应用能做什么、依赖什么"在平台上可被系统化读取**——这决定了后续的分发、治理与责任定位是否可能
   - 关键性质：**元数据完整方可上架**
   - 关键示意：
     ```text
     上架元数据：同时服务三类使用方
       上架时提交：
         · 说明（Instructions）    —— 能力边界与适用场景
         · 知识（Knowledge）       —— 依赖哪些文件 / 检索源
         · 动作（Actions）         —— 会调用哪些外部 API
         · 观感 / 分类 / 示例      —— 便于被检索与理解
       ────────────────────────────────────────────────
       给用户：知道它能做什么、不能做什么
       给平台：知道它依赖什么（外部 API 出问题时可定位）
       给治理：出问题时能定位到构建者与当时的配置版本
     -- 关键：把"介绍"和"治理所需信息"合成一份元数据，
     --       避免"宣传归宣传、治理归治理"两套信息
     ```

2. **版本化与责任绑定（核心）**
   - 关键设计：**每次配置变更产生新版本**；线上运行记录使用的配置版本与构建者
   - 关键能力：**"当时那个版本是什么样的"可复现**——这是出问题时能定位、能回滚的基础
   - 关键性质：**配置版本可追溯**

3. **知识通道与动作通道分离（核心）**
   - 关键设计：**知识类依赖走文件检索，能力类依赖走动作调用**，两类在元数据中分开声明
   - 关键能力：**"它为什么会这样回答"可分别归因**（是检索到的内容，还是调用了外部服务）
   - 关键性质：**依赖类型可区分**

4. **分发与发现机制（核心）**
   - 关键设计：**分类、检索、推荐与榜单**，让好资产被找到
   - 关键能力：**发现机制替代了"官方逐个推荐"**——分发的规模化靠机制而非人力
   - 关键性质：**资产可发现、重复建设下降**

5. **质量下限与运营约束（核心创新）**
   - 关键设计：**上架有基本约束与运营审核**；对滥用、误导性描述、违规动作做下架处理
   - 关键能力：**平台不必保证每个资产都好，但必须保证下限与可追责**——这是开放生态能持续的前提
   - 关键性质：**下限可控、可下架**

**GPT Store 资产治理关键数字**（[OpenAI 公开材料 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **上架方式** | 官方逐个定制 | 构建者自助上架 | **规模化** |
| **元数据完整性** | 仅有介绍文字 | 能力 / 知识 / 动作 / 边界清单 | **可被系统读取** |
| **版本管理** | 配置改了不可追 | 变更即新版本 | **可复现可回滚** |
| **责任定位** | 无法定位 | 版本 + 构建者绑定 | **可追责** |
| **依赖归因** | 无法区分 | 知识通道 / 动作通道分离 | **可分别归因** |
| **发现机制** | 依赖人工推荐 | 分类 / 检索 / 榜单 | **规模化分发** |
| **质量下限** | 无明确约束 | 上架约束 + 可下架 | **可控** |
| **生态规模** | 少量官方应用 | 大量第三方资产 | **∞** |

**具体数字（How much）**

- 团队规模：OpenAI 平台 / 应用团队 1000+ 人
- 关键性质：**自助上架**；**元数据完整方可上线**；**配置版本可追溯**；**可下架**
- 业务影响：让第三方以自助方式发布 AI 应用，并把分发从"官方定制"转为"机制化发现"

**失败教训**

- 早期「**上架只填一段介绍文字**」——平台无法据此做治理与归因，倒逼**「元数据清单化：能力 / 知识 / 动作 / 边界」**
- 「**配置变更不留版本**」——出问题时无法复现当时行为，倒逼**「变更即新版本，线上记录所用版本」**
- 「**知识依赖与动作依赖混在一起描述**」——回答出错时无法判断是检索内容问题还是外部调用问题，倒逼**「两类通道在元数据中分开声明」**
- 「**依赖人工推荐发现资产**」——分发无法规模化，倒逼**「分类 / 检索 / 榜单的机制化发现」**

### 6.4 Salesforce"**Agentforce：在企业元数据体系上管理 Agent 资产 3+ 年**"（2021-2024）

**背景（Why）**

Salesforce 2021 年面临**"Agent 进入企业后与既有系统脱节"**：
- **企业已有成熟的对象、字段、权限模型**——**Agent 若自建一套元数据，就会与 CRM 事实脱节**
- **Agent 会读写业务数据**——**它必须遵守与人工用户相同的权限与审计要求**
- **资产需要与业务对象绑定**——**"这个 Agent 服务于哪些客户、哪些工单"必须可追**
- **合规与审计**——**企业客户要求"AI 做了什么"可被逐条回溯**

**触发点（What）**

2021 年起 Salesforce 推进 **Agentforce（在企业元数据之上构建与管理 Agent）**（[Salesforce 公开材料 2021-2024]），目标：
- **复用企业既有元数据**——Agent 定义绑定到对象与权限模型
- **行为可审计**——每次动作可回溯
- **资产生命周期可管**

**详细做法（How）**

Agentforce 资产管理的**5 大核心组件**：

1. **Agent 定义建立在企业既有元数据之上（核心创新）**
   - 关键设计：**Agent 的能力、动作、数据范围引用企业的对象 / 字段 / 权限模型**，而不是另建一套 AI 专用元数据
   - 关键能力：**Agent 与业务事实天然一致**——"客户等级"这类概念不必在 Agent 侧重新定义一遍，也不会与 CRM 漂移
   - 关键性质：**元数据复用、概念不漂移**
   - 关键示意：
     ```text
     对照：AI 专用元数据 vs 复用企业元数据
       ✗ 为 Agent 另建一套元数据
         Agent 侧定义"客户等级""工单状态" → 与 CRM 定义各说各话
         权限也要再实现一遍 → 与人工用户的权限边界不一致
       ✓ 建立在企业既有元数据之上（本方案）
         Agent 动作 = 引用「对象 + 字段 + 动作」
         数据范围 = 复用「角色 / 权限 / 共享规则」
         审计     = 走企业既有的留痕体系
       ────────────────────────────────────────────────
       收益：
         · 概念一致：Agent 说的"客户等级"就是 CRM 里的定义
         · 权限一致：Agent 不会看到人工用户看不到的数据
         · 审计一致：不需要为 AI 再搭一套审计
     -- 关键：企业场景下，AI 资产最贵的不是模型，而是"与既有系统保持一致"
     ```

2. **动作与权限绑定（核心）**
   - 关键设计：**Agent 可执行的动作与数据范围受角色与共享规则约束**
   - 关键能力：**"AI 越权操作"在权限模型层就被限制**，而不是靠提示词约束
   - 关键性质：**权限一致、越权在模型层受限**

3. **行为留痕与可回溯（核心）**
   - 关键设计：**每次 Agent 动作记录：谁触发、执行了什么动作、访问了哪些记录、结果如何**
   - 关键能力：**"这个 Agent 上周对哪些工单做了什么"可逐条回放**——企业合规与故障复盘的硬要求
   - 关键性质：**动作可逐条回溯**

4. **资产生命周期与所有权（核心）**
   - 关键设计：**Agent 资产有所有者、版本、适用范围与启用状态**
   - 关键能力：**资产随业务变化可停用可迭代**，而不是建完就留在生产环境里
   - 关键性质：**生命周期可管、所有权明确**

5. **与业务流程绑定（核心创新）**
   - 关键设计：**Agent 挂在具体业务场景下**（某类工单、某个销售流程），而非独立存在
   - 关键能力：**效果好坏的判断有业务上下文**——"这个 Agent 在客服工单场景下表现如何"比"这个 Agent 综合得分多少"更有决策价值
   - 关键性质：**场景化绑定、评估有业务上下文**

**Salesforce Agentforce 关键数字**（[Salesforce 公开材料 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **元数据来源** | 为 AI 另建一套 | 复用企业对象 / 字段 / 权限 | **概念不漂移** |
| **权限控制** | 提示词约束为主 | 复用角色 / 共享规则 | **越权在模型层受限** |
| **审计** | 需另建 AI 审计 | 走既有留痕体系 | **一致可回溯** |
| **动作可回溯** | 部分 | 谁 / 什么动作 / 哪些记录 / 结果 | **逐条可回放** |
| **资产生命周期** | 建后长期挂着 | 所有权 + 版本 + 启停 | **可控** |
| **业务绑定** | 独立存在 | 挂具体业务场景 | **评估有上下文** |
| **企业客户** | 0 | 10000+ | **∞** |
| **合规场景可用性** | 审计不足难通过 | 可逐条举证 | **∞** |

**具体数字（How much）**

- 团队规模：Salesforce 平台团队数千人
- 关键数字：**复用企业元数据**；**权限一致**；**动作可逐条回溯**；**10000+ 企业客户**
- 业务影响：让企业在既有 CRM 元数据与权限体系之上构建与管理 Agent，满足合规可审计要求

**失败教训**

- 早期「**为 Agent 另建一套元数据**」——概念与 CRM 各说各话、权限要再实现一遍，倒逼**「Agent 定义建立在企业既有元数据之上」**
- 「**靠提示词约束 Agent 不要越权**」——约束不可靠且不可举证，倒逼**「动作与数据范围绑定角色与共享规则」**
- 「**审计只记录对话文本**」——无法回答"对哪些记录做了什么操作"，倒逼**「记录谁 / 什么动作 / 哪些记录 / 结果」**
- 「**Agent 建完就一直挂在生产环境**」——随业务变化无人维护，倒逼**「所有权 + 版本 + 启停状态」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**资产登记表 + Owner + 版本化 Prompt**」（**最简单**）——**1 个团队、10+ 资产**
- 产出：**资产登记模板（能力 / 依赖 / Owner / 版本）+ 简单评审清单 + 版本可回滚**
- 团队：**2-3 人**
- 验证标准：**每个资产有 Owner 与版本历史**、**改 Prompt 可回滚**、**上架前过评审清单**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 团队 / 100+ 资产**」
- 引入「**以"能力"为登记单位，实现版本挂其下**」——搜到能力而非片段
- 引入「**依赖关系与影响面**」+「**调用统计与最后调用时间**」
- 团队：5-10 人
- 验证标准：**同能力多实现可比较**、**变更前可列出受影响资产**、**僵尸资产可识别**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 团队 / 千级资产 / 多业务**」
- 引入「**统一评测与横向比较**」+「**统一调用通道与成本归因**」
- 引入「**完整生命周期状态机（含下线前确认无调用）**」
- 团队：10-30 人
- 验证标准：**同能力评测口径统一**、**成本可按业务归因**、**下线过程无业务中断**

**100 → 1000 阶段：12-24 个月**

- 引入「**复用度作为资产指标并影响排序**」——好资产自然浮现
- 引入「**动作与数据范围绑定既有权限模型 + 动作级留痕可回溯**」
- 引入「**资产与业务场景绑定，评估带业务上下文**」
- 团队：30-100 人
- 验证标准：**复用度提升且重复建设下降**、**越权在权限模型层受限**、**动作可逐条回溯**、**评估有业务上下文**

### 6.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**资产可管理性**」 | 建了就挂着 | 五阶段生命周期 | **目录可长期维护** |
| 「**变更可回滚性**」 | 改了就回不去 | 版本化 + 固定引用 | **可回滚** |
| 「**重复建设**」 | 同类能力各写一套 | 能力级登记 + 复用 | **显著下降** |
| 「**选型依据**」 | 凭名气 / 感觉 | 同能力统一评测 | **有客观依据** |
| 「**依赖可见性**」 | 不清楚谁在用 | 依赖关系 + 影响面 | **变更风险前置** |
| 「**成本归因**」 | 各自接模型 | 统一通道按业务归因 | **可归因** |
| 「**权限一致性**」 | 提示词约束为主 | 复用既有权限模型 | **越权在模型层受限** |
| 「**审计可回溯性**」 | 仅记录对话 | 动作级留痕（人 / 动作 / 记录 / 结果） | **逐条可举证** |
| 「**下线风险**」 | 按时间硬删 | 确认无调用 + 保留历史 | **无业务中断** |
| 「**资产规模 / 企业客户**」 | 少量手工维护 | 大量资产 / 10000+ 企业 | **∞** |

**关键投资回报**：
- **直接节省**：「**重复建设显著下降 + 目录可长期维护 + 成本可归因**」——**AI 资产管理的成本不在登记本身，而在"重复造同一类能力"与"资产只增不减导致无人敢动"**；把登记粒度定在"能力"、把下线做成常规流程，省下的是长期的人力与治理负担
- **业务价值**：「**同能力可比较 + 变更可回滚 + 复用度自然浮现**」——**资产管理的价值在于让 AI 能力从"个人产物"变成"组织资产"**：能被找到、能被比较、能被安全改动，团队才敢复用别人的能力而不是各自重写
- **AI 时代关键**：「**建立在既有元数据与权限之上 + 动作级留痕 + 能力级登记**」——**这是 AI 资产能否进入企业生产系统的门槛**：AI 若在既有治理体系之外自成一套，权限与审计必然双失守；而"能力级登记"则让 AI 资产第一次有了可被组织和复用的基本单位

---

> **本节小结**：
> - 4 个真实案例（字节 / 阿里 / OpenAI / Salesforce）印证：**AI 资产管理不是「建个资产列表」，是「能力级登记 + 版本化与固定引用 + 生命周期与下线通道 + 统一评测与复用度 + 建立在既有权限与审计之上」5 件套**。
> - 关键时间线：字节 4+ 年 / 阿里 4+ 年 / OpenAI 3+ 年 / Salesforce 3+ 年 —— **AI 资产管理是 3+ 年长期工程**，且**成败取决于"登记粒度"与"下线通道"这两件看似不起眼的事**。
> - 选型第一原则：「**登记表 + Owner + 版本化**」（**最简单**）——**1 个团队** → 「**能力级登记 + 依赖可见 + 调用统计**」（**必须**）→ 「**统一评测 + 统一调用通道 + 完整生命周期**」（**生产**）→ 「**复用度驱动排序 + 绑定既有权限与动作留痕**」（**AI 时代**）。
> - 99% 的失败来自「**只增不减 + 改了回不去 + 登记粒度太细 + 与业务系统脱节**」——必须有 **生命周期与下线 + 版本化固定引用 + 能力级登记 + 复用既有元数据**。
> - 真正的 ROI 来自「**重复建设下降 + 变更可回滚 + 成本可归因 + 审计可逐条举证**」——是**AI 能力能否从个人产物变成组织资产的分水岭**。

> 💡 **思考锚点**：把你的 Agent / Prompt / 工具清单过一遍 § 3.7 的两条判据：登记粒度是不是停在「能力」这一层（还是细到每个 Prompt 一份）、有没有哪条资产从建到现在「只增不减」、既没有 Owner 也没有下线通道——按本节 99% 的失败模式，后者是不是就是你下一次「改了就回不去」的候选？
