## 3. 设计模式与范式

> 原 § 3 共 73 行、为模式表格（6 个模式 + 9 条反模式 + 5 行生命周期选择表），缺少结构示意、机制解释与失效分析，重写为 ~325 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把资产分发的设计讲成了一道选择题：研发选 Git、运营选 Prompt Library、C 端选 Store、企业内部选私有 Marketplace、模型消费选 MaaS。但同一个「运营团队」在两家公司会得到完全相反的答案：一家只有 3 个业务同学、每周改两次 Prompt（该留在 Git 里），另一家有 200 个业务同学、每天改几十次、谁都能上线（必须要有平台与 alias）。同一个场景，正确模式不同。

真正推着决策走的是六条约束：**消费方是谁**（决定分发通道与门槛）、**资产形态**（纯文本还是有副作用的可执行体，决定门禁做到哪一层）、**变更对调用方的影响强度**（决定版本号语义与兼容承诺）、**与模型版本的绑定强度**（决定契约怎么写）、**治理与合规要求**（决定是否需要强制准入与计量）、**存量规模**（决定要不要质量分与自动退役）。这六条里任一条不同，模式选择就会翻转。

所以本节先立约束、再谈模式。下表不是选型表，而是「本主题下最容易被约束推翻的直觉」清单——当你觉得某个模式「显然更好」时，先回去看是哪条约束在替你说话。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 消费方是谁（作者本人 / 研发同事 / 全企业任意角色 / 企业外部） | 分发通道与治理强度 | 「先建平台再谈治理」——消费方全是研发时，Git 已经提供了版本、评审、权限、回滚四件事，自建平台先增加的是摩擦 |
| 资产形态（纯文本 Prompt / 可执行 Skill / 有副作用 Workflow） | 门禁做到哪一层 | 「Prompt 与 Skill 用同一套流程」——Skill 有接口契约与副作用，必须测；Prompt 没有接口，只能靠评估断言 |
| 变更对调用方的影响强度 | SemVer 的分界怎么划 | 「版本号只是编号」——AI 资产的行为改变常常不出现在接口签名上，主版本号的判据只能是评估基线的变化 |
| 与模型版本的绑定强度 | 契约里必须写死什么 | 「资产是自包含的」——多数 AI 资产绑定某个模型快照，模型一升级，可用资产就变成失效资产（主文件 §1.5） |
| 治理与合规要求（数据边界 / 审计 / 计费） | 是否需要强制准入 | 「治理是平台的事」——没有准入与计量，平台只能记录被自愿登记的资产，真实调用照样在别处发生 |
| 存量规模与质量 | 要不要质量分与自动退役 | 「资产越多越好」——登记数增长后检索噪声上升，复用率会反向走低（见 §3.5「无退役」） |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 Git 化 Prompt

- **被什么约束逼出来**：Prompt 是纯文本、改动频繁、改错直接影响线上回复，而团队的工具链已经在 Git 上——在没有平台的阶段，Git 是唯一现成的「版本 + 评审 + 权限 + 回滚」四件套。
- **结构**：资产就是仓库里的文件树，契约写在元数据文件里，门禁写在 CI 里。

```yaml
# ai-assets/prompts/customer-service-refund/metadata.yaml
apiVersion: ai-asset/v1
kind: Prompt
metadata:
  name: customer-service-refund
  owner: alice@company.com      # 具体到人，不是团队
  version: 1.2.0                # SemVer：行为变化才动主版本
  tags: [客服, 退款]
spec:
  template_file: template.md    # 正文可 diff、可评审
  variables:
    - {name: order_id, type: string, required: true}
    - {name: tone, type: string, default: 友好}
  model: {provider: openai, name: "<带日期的模型快照>", temperature: 0.2}
  eval: {dataset: eval/cases.jsonl, metrics: [accuracy, safety]}
```

- **为什么这样设计有效**：因为资产就是版本库里的文件，diff、评审、回滚、权限四件事直接复用 Git 既有机制，新增的只有 CI 里的 schema 校验与评估门禁，所以从零到可治理的成本接近「加一条流水线」；代价是「消费」这件事本身被要求具备 Git 能力。
- **代价**：消费方必须会 Git，非研发被挡在门外；模板变量契约要在 CI 里校验，否则遗漏变量只在运行时才暴露；运行时取值要么加一次发布（有延迟），要么让进程直接读仓库（把版本库变成生产依赖，一次网络抖动就是一次故障）。
- **失效点**：当消费方从研发扩展到运营 / 客服时，「版本可控」从优势反转成门槛，因为他们不会用 PR 消费资产，最后把模板复制进自己的文档，资产回到孤岛状态，而且线上真正跑的那一份在版本库之外。
- **真实使用**：LangChain Hub 以中心化仓库方式托管与分享 Prompt 模板 【公开】（LangChain 公开文档，2023）；把 Prompt 与调用它的代码同仓、走 code review，是研发团队最普遍的做法 【经验】。

#### 3.2.2 Prompt Library

- **被什么约束逼出来**：改 Prompt 的人与写代码的人不是同一批（运营 / 业务），迭代节奏是「天」而不是「发版周期」，同时上线前还要能做 A/B 与评估——这三件事 Git 都给不了。
- **结构**：内容是数据、运行时按别名取版本；版本不可变，别名可移动。

```text
作者（Web 编辑器）
   │ 保存 → 新版本（不可变快照）
   ▼
资产库：asset（稳定 ID）
        ├── version（不可变：模板 + 参数 + 评估记录）
        └── alias（dev / staging / prod）── 可移动，指向某个 version
   │
   ├─▶ 运行时 SDK：按 alias 取版本（本地缓存 + 取不到时降级到上一可用版本）
   ├─▶ 实验：按流量比例把不同 version 指向不同会话
   └─▶ 评估：每次保存触发离线评估，结果挂在 version 上
关键：「线上在跑哪一版」必须是一个能查到、能审批、能回滚的名字
```

上图的三个概念落到表上就是三张表：资产、版本、别名。这张 DDL 是 Prompt Library 与「真·配置表」的分界线——没有不可变版本与别名，它只是一张能改内容的表。

```sql
CREATE TABLE prompt_asset (          -- 稳定身份：调用方引用的永远是它
  asset_id    VARCHAR(64) PRIMARY KEY,
  owner       VARCHAR(128) NOT NULL, -- 具体到人
  tags        TEXT[],
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE prompt_version (        -- 不可变快照：只插入，不更新
  asset_id    VARCHAR(64) NOT NULL REFERENCES prompt_asset(asset_id),
  version     VARCHAR(32) NOT NULL,  -- SemVer
  template    TEXT        NOT NULL,
  model_snapshot VARCHAR(64) NOT NULL,   -- 写死快照，不写滚动别名
  params      JSONB       NOT NULL,
  eval_run_id BIGINT,                -- 该版本的评估记录，发布门禁的凭据
  created_by  VARCHAR(128) NOT NULL,
  PRIMARY KEY (asset_id, version)
);

CREATE TABLE prompt_alias (          -- 可移动指针：prod 指针的每次移动都要留痕
  asset_id    VARCHAR(64) NOT NULL,
  alias       VARCHAR(16) NOT NULL,  -- dev / staging / prod
  version     VARCHAR(32) NOT NULL,
  moved_by    VARCHAR(128) NOT NULL,
  moved_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (asset_id, alias)
);
```

- **为什么这样设计有效**：因为内容与代码部署解耦，改 Prompt 不需要发版，所以迭代周期从「发版节奏」缩到分钟级、且业务方自助；代价是 Prompt 不再经过代码评审，质量门禁必须由资产库自己补回来（评估 + alias 移动审批）。
- **代价**：这是一套要长期运营的内部产品（登录、权限、审计、实验、评估），运维面不比一个业务系统小；调用方多了一层运行时依赖，取版本失败必须有降级路径；版本不可变意味着存储只增不减，历史版本需要保留与清理策略。
- **失效点**：当「免发版」被当成「免评审」时，可迭代从优势反转成不可追溯，因为线上跑的是 alias 指向的版本，而 alias 何时被谁移动、移动前后评估分是多少若无记录，出事时既回不到「上一个好版本」，也说不清改动是谁做的。
- **真实使用**：Dust.tt 面向团队提供 Prompt 协作与版本管理 【公开】（Dust 公开产品材料，2023）；PromptLayer 提供 Prompt 版本管理与调用监控 【公开】（PromptLayer 公开产品材料，2024）。两者在本章 [§4.3 工具链](03-asset-management-section-4-sec4.md) 中同样列出。

#### 3.2.3 Agent Store

- **被什么约束逼出来**：分发对象是企业外部的陌生人，平台没有强制力要求他们遵守流程；平台能提供的只有流量、分发与支付，供给量必须靠外部开发者的自身动机长出来。
- **结构**：平台定上架契约（身份 + 能力声明 + 数据处理声明 + 审核），生态方按契约提交，运行在平台沙箱里。

```json
{
  "name": "invoice-helper",
  "version": "1.0.0",
  "capabilities": ["code_interpreter", "http_action"],
  "actions": { "openapi": "openapi.yaml", "auth": "oauth2" },
  "data_handling": { "stores_user_data": true, "retention_days": 30 },
  "review": { "status": "listed", "policy_version": "2024-01" }
}
```

- **为什么这样设计有效**：因为平台把上架、分发、计费收成一套契约，单个开发者拿到的是渠道而不是客户，所以供给可以随外部动机自我扩张，平台不必自己生产资产；代价是质量与安全的闸门只剩审核与运行沙箱，你必须接受别人替你判断质量。
- **代价**：能力边界（能否读用户数据、能否发网络请求）必须在上架时就声明并覆盖审核，审核能力随供给量线性上涨；对企业消费方来说，这些是边界之外的资产，数据出界风险由使用方承担，无法靠平台条款转移；排序规则不透明时，资产的成功与否取决于平台而非资产本身。
- **失效点**：当供给量增长超过审核与排序能力时，商店从「发现可用资产」反转成「检索噪声源」，因为排序若被调用量、曝光量这类流量指标驱动，先来的资产会持续自我强化，新资产只能靠标题与包装争取曝光——§3.5 的「无退役 / 资产私用」在公域里会放大成僵尸上架。
- **真实使用**：OpenAI 在 2023-11 宣布、2024 年初上线 GPT Store，向 ChatGPT 用户提供第三方 GPT 的分发 【公开】（OpenAI 公开公告，2023-2024）；字节扣子 Coze 是面向 B 端的 Agent 开发与分发平台 【公开】（字节公开材料，2024），其生命周期治理见 [§3.1 扣子 Coze 案例](03-asset-management-section-6-sec6.md)。

#### 3.2.4 私有 Marketplace

- **被什么约束逼出来**：企业内资产的消费方是任意角色的同事，而且资产会碰内部数据，所以必须能回答三个问题：谁能用、用了算谁的成本、出了问题找谁。Git 与外部 Store 都回答不了。
- **结构**：准入、授权、计量、生命周期四件套，任何一件缺失都会退化成「贴满链接的文档页」。

```text
企业资产市场（关键在「必须经过」）
  作者 ──▶ ① 准入：登记（Owner / 版本 / 文档 / 评估分）+ 安全评审
              └─ 未登记不可被调用（是门禁，不是建议）
  消费方 ──▶ ② 授权：以调用方身份取用（数据边界、字段级权限、配额）
              ▼
            ③ 计量：调用量 / token / 成本 → 归属到调用方部门
              ▼
            ④ 生命周期：发布 / 灰度 / 退役通知 / 替代资产推荐
  平台内部：Registry（资产库）+ Eval Hub（评估）+ 血缘（依赖与影响面）
```

三张表把「准入 / 授权 / 计量」立起来：登记表决定什么能存在，授权表决定谁能调，计量表决定算谁的钱。缺了第三张，前两张就只是文档。

```sql
CREATE TABLE asset_registry (        -- 准入：未登记则运行时拒绝加载
  asset_id     VARCHAR(64) PRIMARY KEY,
  kind         VARCHAR(16) NOT NULL, -- Prompt / Skill / Workflow / Agent
  owner        VARCHAR(128) NOT NULL,
  docs_url     TEXT        NOT NULL, -- 缺文档不放行
  eval_score   NUMERIC(5,2) NOT NULL, -- 发布时的评估分，后续用于排序与退役
  phase        VARCHAR(16) NOT NULL, -- draft / published / deprecated / retired
  checksum     VARCHAR(64) NOT NULL  -- 制品 ↔ commit 一致性校验的锚点
);

CREATE TABLE asset_entitlement (     -- 授权：调用方身份决定可用范围
  subject_id   VARCHAR(128) NOT NULL,   -- 人 / 服务账号 / 部门
  asset_id     VARCHAR(64)  NOT NULL,
  data_scope   TEXT[] NOT NULL,         -- 允许触达的数据域（字段级权限的粗粒度）
  quota_per_day BIGINT,
  granted_by   VARCHAR(128) NOT NULL,
  PRIMARY KEY (subject_id, asset_id)
);

CREATE TABLE asset_usage (           -- 计量：成本归属的唯一依据
  asset_id     VARCHAR(64)  NOT NULL,
  version      VARCHAR(32)  NOT NULL,
  caller       VARCHAR(128) NOT NULL,   -- 归属到调用方，而不是归属到资产作者
  tokens       BIGINT,
  calls        INT          NOT NULL,
  event_time   TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
```

- **为什么这样设计有效**：因为调用必须穿过市场，成本可归属、责任可定位、退役能通知到具体调用方——这三件事是「贴文档」永远做不到的；代价是市场成为所有调用的关键路径，它的可用性与延迟必须按生产系统标准运维。
- **代价**：建设成本相当于做一个内部产品（门户 + Registry + 权限 + 计量 + 评估）；强制准入必然带来摩擦，团队有动力绕过；计量口径一旦与实际调用不符，成本归属就失去公信力，进而失去约束力。
- **失效点**：当准入与评估的摩擦高于绕过的收益时，私有市场从「治理入口」反转成影子资产的温床——市场里的资产漂亮、看板指标漂亮，真实调用却发生在绕过市场的代码里，因为绕过是零边际成本，而登记要付评审与文档成本。
- **真实使用**：Salesforce Agentforce 与微软 Copilot Studio 这类企业平台把 Agent 纳入既有元数据、权限与审计体系 【公开】（厂商公开材料，2024-2025），本章 [§3.4 Salesforce Agentforce 案例](03-asset-management-section-6-sec6.md) 有展开；阿里通义 / 星图的资产市场形态见主文件 §1.3、§2.6。

#### 3.2.5 MaaS（模型即服务）

- **被什么约束逼出来**：模型能力不是每个团队的差异化优势，而自建推理意味着 GPU 采购、集群运维与模型迭代三份长期投入；业务对按需弹性的需求远强于对完全可控的需求。
- **结构**：把模型能力压成一个 HTTP 契约，契约里唯一不能省的是「带日期的模型快照」。

```text
你的服务 / Agent ──▶ 外部模型服务
                        · 模型标识：必须是带日期的快照，不是滚动别名
                        · 参数：温度 / 最大输出 / 结构化输出 schema
                        · 凭证与配额
        ▲                       │
        └── 计量（token / 调用）+ 弃用时间表（服务商版本公告）
约束：契约若写的是滚动别名，服务商升级就是一次没有经过评审的 breaking change
```

- **为什么这样设计有效**：因为能力被封装成一次网络调用，你承担的成本从「拥有一套推理基础设施」变成「一个客户端 + 一份调用预算」，模型能力升级会自动落到调用上而不需要你迁移；代价是数据必须离开你的边界，且可用性与行为的上限被服务商绑定。
- **代价**：数据出域合规（敏感数据需要脱敏、私有化部署或改自建）；单位成本随调用量近似线性上涨，而能力提升带来的收益未必同比例；版本被弃用时要跟着迁移，而 Prompt 常常是在旧模型上调优的（主文件 §1.5），迁移必须重跑评估集。
- **失效点**：当服务商滚动更新快照或改变默认行为（默认输出格式、拒答策略）时，「免运维」从优势反转成不可控变更，因为你的评估基线测的是旧快照、线上跑的是新快照；这类失效在传统软件资产里没有对应物，它是 AI 资产独有的失败模式。
- **真实使用**：Replicate 以按调用计费方式对外提供模型推理 API 【公开】（Replicate 公开产品材料，可自行核验）；阿里云百炼等云厂商的模型服务是主文件 §1.3、§2.6 列出的 MaaS 形态 【公开】（厂商公开材料，2024-2025）。多数团队的做法是把模型快照写死、评估集跑通后再切换 【经验】。

#### 3.2.6 混合模式

- **被什么约束逼出来**：同一批资产在生命周期不同阶段、面对不同消费方时，最优通道不同——作者要 Git 的评审与 diff，消费者要门户的检索与授权，模型能力来自外部。任何单一模式想覆盖全链路，必然在一端受损。
- **结构**：源码与制品分离，「作者态」与「消费态」各用各的通道，中间靠一致性校验连接。

```text
作者态（Git）                        消费态（平台）
 prompts/**.md ──▶ CI 构建 ──▶ Registry 制品（不可变版本 + 评估分）
      │                                    │
      │                                    ├─▶ 门户：检索 / 授权 / 计量 / 退役
      └──────── 一致性校验（制品 ↔ commit）◀┘
模型能力：MaaS（外部合约）    运行支撑：Agent Runtime（取制品 + 调模型）
```

- **为什么这样设计有效**：因为「怎么写」与「怎么被消费」被拆成两条通道，作者继续用熟悉工具、消费者只面对稳定制品，两类需求互不牺牲；代价是同一份资产有了两种表示，必须有回溯校验（制品能定位到某个 commit），否则会分裂成两套真相。
- **代价**：发布链路变长，改一行也要走流水线，构建、缓存、失效策略都要投入；制品与源码的一致性检查要进流水线，否则审计链在「制品 → commit」这一步就断了。
- **失效点**：当平台允许在生产版本上直接热改时，混合模式从两全反转成两套真相，因为下一次从 Git 构建会把热改覆盖或产生分叉，而线上到底跑的是哪一份谁也说不清。
- **真实使用**：Prompt 放 Git 做源码管理、再发布到 Registry / 门户供消费，是有平台团队时的常见形态 【经验】；扣子 Coze 的资产生命周期与通义的企业级登记属于「平台侧制品 + 企业治理」的混合形态，见 [§6 落地实践](03-asset-management-section-6-sec6.md)。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 消费方全是研发、资产是纯文本 Prompt | Git 化 Prompt | 不选 Prompt Library：无非研发消费方时，平台先带来的是摩擦而非复用 | 消费方会不会写 PR |
| 消费方含运营 / 业务、改 Prompt 是周级或更快 | Prompt Library + 评估门禁 | 不选纯 Git：非研发被 PR 挡住后必然复制粘贴，资产随即失联 | 是否有非研发人员每周都要改一次 |
| 同一资产被多个服务共享、需要灰度与回滚 | 混合模式（Git 源码 + Registry 制品） | 不选纯 Git：运行时直连仓库会把版本库变成生产依赖 | 是否存在多个独立上线节奏的调用方 |
| 企业内、资产会碰内部数据、要成本归属 | 私有 Marketplace | 不选外部 Store：外部平台无法承担内部数据边界与成本归属 | 是否必须回答「谁在用、算谁的钱」 |
| 面向企业外部分发、供给要靠外部开发者 | Agent Store | 不选私有 Marketplace：公域没有强制准入力，只能靠契约与审核 | 供给是否必须来自外部 |
| 模型能力非差异化、要求按需弹性 | MaaS | 不选自建推理：GPU 与模型迭代的运维面自建不起 | 数据是否允许出域 |
| 数据分类里有「不得出域」的类别 | 私有化 / 自建模型 + 私有 Marketplace | 不用公有 MaaS：数据出域不可接受，责任也无法靠条款转移 | 数据分类清单里有无出域禁止项 |
| 资产数已超过人工盘点能力 | 混合模式 + 质量分 + 自动退役 | 不选「继续加登记」：登记数上涨而检索质量下降，复用率反向走低 | 检索前 10 条里有几条是能用的 |

本节最常被误选的一对，是**把 Git 化 Prompt 与 Prompt Library 当成「二选一」来投票**。它们的差别不是好不好用，而是**谁被授权改**：Git 授权给有仓库权限的人，Library 授权给有平台账号的人。误选的后果相当具体——选了 Git 而消费方含运营，模板会以复制的形式散出去，线上跑的那一份不在版本库里；选了 Library 而消费方全是研发，则把 Git 已经提供的版本、评审、权限重建了一遍，多出登录、权限、审计的长期运营成本，而研发依旧在自己的仓库里维护另一份。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Git 源码 + Registry 制品 + 私有门户（企业内标准形态）**

- 构成：Git 承担作者的撰写、评审与 diff；Registry 承担不可变版本、评估分与检索；门户承担授权、计量与退役通知。
- 职责边界：Git 只管「怎么被写出来」，不负责运行时取数；门户只管「谁能用、用了多少」，不改内容。
- 运维代价：一条构建发布流水线 + 一套 Registry + 一套权限计量，三处都要 Owner；一致性校验进流水线后，任何热改都会破坏这条链。
- 适合规模：多团队共用资产、调用方数量超过十个、需要成本归属的团队。

**组合二：Prompt Library + Eval Hub + 灰度（业务主导迭代）**

- 构成：Library 提供分钟级改 Prompt 与 alias；Eval Hub 提供每次保存触发的离线评估；灰度按流量切换版本。
- 职责边界：Library 负责迭代速度，Eval 负责守住下限（回退用例数为零才允许继续），灰度负责上线后的真实读数。
- 运维代价：评估集要持续换血，否则一年后它描述的是过去；alias 移动要有审批记录，否则回滚失去锚点。
- 适合规模：业务方自助改 Prompt、日改动量已超过研发排期能力的组织。

**组合三：私有 Marketplace + MaaS（自建能力 + 外部模型）**

- 构成：内部 Skill / Workflow 走私有市场登记与授权；模型能力通过 MaaS 合约引入（快照写死）。
- 职责边界：市场管「资产边界内的一切」（数据、权限、成本），MaaS 管「模型能力」，两边靠数据分类清单划界。
- 运维代价：数据分类必须落到字段级并持续维护；模型弃用时间表要纳入资产台账，否则「可用资产」会因外部升级突然失效。
- 适合规模：有明确数据分级、且有合规审计要求的组织。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 资产孤岛 | 同一个 Prompt 在多个服务里各有一份近似副本 | 改进无法扩散，同一缺陷在 N 处独立存在，修复成本随副本数放大 | 资产化被当成额外流程，直接写进代码最快 | 建登记入口并让「调用已登记资产」比复制更省事 |
| 无 Owner | 资产出问题只能找到「某团队」；Owner 离职后无人接手 | 失效资产无人维护也无人敢退役，质量单向衰减 | Owner 字段被当成元数据填项而非责任 | Owner 具体到人 + 离职自动触发资产移交 |
| 无版本 | 线上跑的那一版无法用名字指认，回滚时不知回到哪 | 评估读数无法与版本对应，改进与回退都不可判定 | 早期用「改文件 + 重部署」代替版本管理 | 版本不可变 + 别名可移动 + 版本与评估记录绑定 |
| 无评估 | 上线靠「试了感觉不错」；换模型后无人知道有没有变差 | 质量变化没有观测通道，模型升级这类外部变更会静默破坏资产 | 评估集建设成本高、且要先有真实用例 | 发布前跑评估集，回退用例为 0 才放行 |
| 无血缘 | 改底层资产时列不出下游；升级后才发现某个 Agent 被破坏 | 影响面不可枚举，变更只能靠事后修复 | 资产以文件形式散落，依赖关系没有落库 | 把「资产 → 资产」依赖登记入库，变更前查下游 |
| 无文档 | 有资产但没人知道输入输出与适用场景，拿起来用不了 | 可发现却不可用，检索命中后仍需问作者，复用率上不去 | 文档被认为可以「后面补」 | 文档是发布门禁的一部分，缺文档不能发布 |
| 过度资产化 | 每个一次性脚本都要求登记、评审、写文档 | 管理成本随资产数线性上涨，团队把资产化当成负担而整体抵触 | 把「都管起来」等同于治理能力 | 分级资产化：区分个人草稿 / 团队资产 / 企业资产，只有后两级强制治理 |
| 无退役 | 仓库里存在大量无人调用的资产，检索前列全是旧的 | 检索信噪比下降，优质资产被淹没，复用率反向走低 | 退役要通知调用方，比新建麻烦 | 按调用量 + 最后调用时间自动标记，走通知与替代推荐后归档 |
| 资产私用 | 关键 Prompt 只存在某人本地；离职后能力随人走失 | 组织能力无法沉淀，同一能力反复重建 | 个人效率优先，平台流程被视为阻碍 | 企业级 Owner + 关键资产调用必须经过平台 |

**资产孤岛是最危险的一条，因为它是其他八条的共同成因。** 它在生产里的暴露方式很隐蔽：没有报错、没有告警，只是在一次事故复盘时被发现「同一个 Prompt 在四个服务里有四个版本，只有一个改过」。机制上，只要「复制」比「登记 + 取用」更省事，资产就会持续向外扩散，而每一次扩散都让后续的口径统一难上一档。

**过度资产化的暴露方式是团队集体抵触。** 它不会立刻出问题，而是让治理动作本身失去支持：当一次性脚本也被要求走完登记、评审、评估全流程时，团队会选择把东西放到平台之外——治理指标在涨，治理覆盖面在缩。

**无退役的暴露方式是「检索越用越不可信」。** 机制上，资产只增不减，排序又没有质量维度，于是旧资产靠历史调用量长期占据前排；一旦有人因为前排资产不可用而改用私下渠道，平台的可信度就进入单向下降。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单团队 → 多团队共用 | 各自仓库自管理 | 同一能力被并行造 N 份，且互不可见 | 统一 Registry + Owner + 检索 | 要迁移存量资产、补 Owner 与文档，且要接受登记带来的产出变慢 |
| 消费方从研发扩到运营 | Git 化 Prompt | 非研发发不出 PR，改用复制粘贴 | Prompt Library（或门户 + 制品） | 要建平台并运营它；研发侧仍需保留源码态与制品同步 |
| 资产数超过人工盘点能力（【经验】千级以内还能人工看，万级必须靠指标） | 人工目录与人工排序 | 排序与退役全凭印象，噪声上升 | 质量分（新鲜度 / 调用量 / 评估分）+ 自动退役 | 要有调用埋点与评估记录，否则质量分算不出来 |
| 从内部自用扩到对外分发 | 私有 Marketplace | 内部准入对外部开发者没有强制力 | Agent Store（契约 + 审核 + 沙箱） | 要建审核能力、运行沙箱与政策版本管理，成本远高于内部门户 |
| 单个模型 → 多模型 / 多版本 | 资产绑定「某个模型」 | 换模型即换行为，资产批量失效 | 资产绑定「评估基线 + 模型能力声明」 | 每类资产都要有一份与模型解耦的评估集，并重跑基线 |
| 自建模型 → 外部模型 | 自建推理 | GPU 与模型迭代的运维面跟不上业务节奏 | MaaS（快照写死 + 弃用时间表纳入台账） | 数据出域合规评审、Prompt 在新快照上重调评估 |

补一句判据：**当「登记与治理的边际成本」开始高于「复用带来的收益」时，就该换模式，而不是继续加流程**。资产系统失控的常见方式不是管不住，而是管得太细，最后没人用。

### 3.7 自检清单

1. 随机抽一个线上 Agent，能否说出它今天用的 Prompt 是哪一版（名字可查，不是「最新版」）？答不出，即「无版本」。
2. 每个资产的 Owner 是否具体到人？填团队名即不算。
3. 关键资产（被多个服务引用的那些）的清单能否自动生成？靠人工整理说明血缘未落库。
4. 最近一次模型升级时，有多少资产重跑过评估集？答不出，说明资产与模型快照的绑定关系没登记。
5. 发布门禁里是否有「缺 Owner / 缺文档 / 缺评估不放行」这三条硬规则？
6. 有没有一条路径能让非研发同事在不复制粘贴的前提下改 Prompt 并上线？
7. 检索结果的排序是否含质量维度（调用量、新鲜度、评估分）？若只有相关性，退役机制迟早失效。
8. 最近一个季度内退役过几个资产？一个都没有，通常不是因为没有僵尸资产。
9. 敏感数据类资产是否全部落在「不得出域」的调用路径上？是否存在对公有 MaaS 的直接调用而未过数据分类评审？
10. 制品与源码能否互相定位（制品 → commit；commit → 制品）？做不到，审计链已断。
11. 是否存在「热改线上版本」的操作入口？存在即等于承认有两套真相。
12. 成本归属是否与实际调用一致（抽查账单与调用日志能否对上）？对不上，计量就形同虚设。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 消费方全是研发，资产是纯文本 | Git 化 Prompt | 复用 Git 已有的版本、评审、权限三件事，新增成本只有一条流水线 |
| 消费方含非研发，迭代是分钟级 | Prompt Library + 评估门禁 | 内容与部署解耦才可能免发版迭代；免发版就必须自建门禁 |
| 多个服务共享同一资产 | 混合模式（源码 + 制品） | 作者态与消费态分开，才既能 diff 又能稳定引用 |
| 企业内、碰内部数据、要成本归属 | 私有 Marketplace | 调用穿过市场，成本归属与责任定位才成立 |
| 对外分发、供给来自外部 | Agent Store | 公域只能靠契约与审核，强准入在外部没有执行力 |
| 模型能力非差异化 | MaaS（快照写死） | 运维面缩到一个客户端，能力升级自动落袋 |
| 数据不得出域 | 私有化模型 + 私有 Marketplace | 数据边界不因外部条款而改变 |
| 资产数已超人工盘点 | 质量分 + 自动退役 | 只增不减的登记表，检索质量必然单向下降 |

> 本节小结：本主题下决定模式选择的**唯一那条最前置的约束，是「谁在消费这个资产」**——它一确定，分发通道与治理强度就被卡死：作者自用时不需要平台；同团队研发用 Git 就够；全企业任意角色必须有 Registry + 授权 + 计量（私有 Marketplace）；企业外部则只剩契约与审核（Agent Store / MaaS）。其余约束（资产形态、变更影响强度、模型绑定）都是在通道选定之后，决定契约怎么写、门禁设在哪一层。
