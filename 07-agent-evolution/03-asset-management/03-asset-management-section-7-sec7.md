## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表的形态是给 Git / Library / Store / Marketplace 四列逐行打 1–5 分（复用、治理、流通、可发现性、协作、变现、合规共七行）。这类表的问题不在数字不准，而在**它把会随场景翻转的结论固定成了绝对排序**。同一个「治理」维度：如果资产是纯文本 Prompt、消费方全是研发，Git 已经把版本、评审、权限、回滚四件事全部提供，它在该维度上应当最高；如果资产会碰内部数据、需要成本归属，Git 直接不及格，因为「谁在用、算谁的钱」它根本回答不了。分数把这两种场景压成一个数字，于是读者拿到的排序在任何具体场景里都可能反掉。

第二层问题是权重。同一维度在不同规模下权重相反：资产数十个时「运维复杂度」权重大——多一个常驻组件就是实打实的负担；资产数上千时「发现与退役」权重大——排序里没有质量维度，检索前列会被旧资产长期占据（§3.5「无退役」）。打分表给每个维度同等权重，等价于默认「你不关心规模」。

第三层问题是分数掩盖了唯一的真问题：**这些模式回答的不是同一道题**。Git 回答「怎么写、怎么回滚」，Store 回答「怎么把外部供给分发出去」，MaaS 回答「模型能力从哪来」。把它们放进同一张表逐行比较，等于把三张不同考卷的分数并列排名。

第四层问题最隐蔽：打分表把**能力**与**约束**混在了一起。「Marketplace 变现 5 分」说的是它能做什么，「Git 合规 4 分」说的是它不需要额外做什么——一个能力的分数和一个约束的分数并列，读者无法判断哪一列的变化会推翻自己的结论。而真实选型里，推翻结论的从来不是能力不足，而是约束不匹配：数据不得出域、非研发发不出评审、没有埋点就算不出成本归属。

四个层次的问题指向同一个结论：**分数是结论，判据才是信息**。所以本章改为「判据 → 机制 → 证据 → 决策」，把「谁更好」全部改写成条件句。判断任何一条对比结论是否可信，先问它有没有说清「在什么前提下」；说不清前提的排序，只能当作候选清单使用。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 授权锚点 | 授权落在什么上（仓库权限 / 平台账号 / 准入清单 / API key） | 锚点决定「谁能改、谁能用」，也决定消费方一扩大时模式会不会失效——它是唯一会随组织扩张而反噬的判据 |
| 调用是否穿过平台 | 调用路径上有没有必经节点 | 有必经节点，成本归属与退役通知才有执行手段；没有节点，治理只能事后统计（§7.3.2） |
| 成本结构 | 成本挂在哪个自变量上（资产数 / 消费方人数 / 调用量） | 三种自变量随规模增长的速度完全不同，选错等于把成本押在增长最快的那一项上（§7.4） |
| 版本与模型的耦合方式 | 契约里写的是带日期快照还是滚动别名 | 写滚动别名意味着外部一次更新就等于一次未经评审的行为变更，资产静默失效（§7.3.3） |
| 发现与退役机制 | 排序里有没有质量维度、有没有下线通道 | 只增不减的登记表，检索信噪比必然单向下降，复用率反向走低（§7.3.4） |
| 治理可举证性 | 出事后能否逐条回溯、能否自证权限范围 | 决定资产能否进入受监管场景；证据链断裂时，平台再好也过不了合规评估 |

> 这 6 条里，**授权锚点是前置判据**：它一确定，分发通道与治理强度基本被卡死；其余五条是在通道选定之后，决定契约怎么写、门禁设在哪一层。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| **Git 化 Prompt**（含 LangChain Hub） | 作者态源管理 | 资产就是版本库里的文件，diff / 评审 / 回滚 / 权限全部复用 Git 既有机制 | 研发团队 | 开源工具 + 自建仓库；LangChain Hub 为中心化模板仓库 【公开】（LangChain 官方文档，2023；在官方文档站检索 "LangChain Hub"） |
| **Prompt Library**（Dust.tt、PromptLayer） | 免发版迭代通道 | 内容与部署解耦：版本不可变、alias 可移动，运行时按 alias 取版本 | 运营 / 业务主导迭代的团队 | 商业 SaaS 【公开】（Dust 官方文档，2023；PromptLayer 官方文档，2024；分别检索 "Dust prompt versioning"、"PromptLayer prompt registry"） |
| **Agent Store（公域）**（GPT Store、扣子 Coze、通义 / 星图） | 面向外部供给的分发 | 平台定上架契约 + 审核 + 沙箱，供给由外部开发者的自身动机扩张 | C 端构建者、B 端开发者 | 平台制 【公开】（OpenAI 官方公告，2023-2024；字节 Coze 官方公告，2024；分别检索 "GPT Store"、"扣子 Coze 上架"） |
| **私有 Marketplace**（自研 / Agentforce / Copilot Studio） | 企业内治理入口 | 准入 + 授权 + 计量 + 生命周期四件套，调用必须穿过市场 | 大型企业、受监管行业 | 商业平台或自研 【公开】（Salesforce 官方文档，2025；微软官方文档，2024；分别检索 "Agentforce agent actions"、"Copilot Studio 发布渠道"） |
| **MaaS**（Replicate、阿里云百炼、Bedrock、Vertex AI） | 模型能力供给 | 把模型能力压成一个 HTTP 契约，按调用计量 | 不愿自建推理的团队 | 按调用付费 【公开】（Replicate 官方文档，2023-2025；阿里云官方文档，2024-2025；分别检索 "Replicate API"、"阿里云百炼模型服务"） |
| **混合模式**（Git 源码 + Registry 制品 + 门户） | 作者态与消费态分离 | 源码走 Git、制品走 Registry，中间靠「制品 ↔ commit」一致性校验连接 | 多团队共用资产的组织 | 自建（平台团队） |
| **传统 ITAM**（软硬件台账体系） | 参照系：资产治理的既有范式 | 以台账条目为单位登记、盘点、许可与回收 | 企业 IT 部门 | 既有企业流程与工具 |
| **Model Registry**（模型管理） | 参照系 / 联动方 | 以模型权重与版本为单位登记，血缘绑定训练数据与代码 | ML 平台团队 | 自建（MLflow 等开源实现）或云厂商托管服务 |

这 8 行里只有 6 个是候选，另外 2 个是参照系；6 个候选又只分**三族**，先分族再选能省掉一半比较：**自管族**（Git 化 Prompt）——平台成本≈0，能力上限取决于使用者自己的工具链；**平台族**（Prompt Library、私有 Marketplace、混合模式）——有常驻平台与运营团队，治理能力来自平台，代价是平台必须被运维；**市场族**（Agent Store、MaaS）——平台不生产资产、只提供契约与分发，能力与质量的上限由外部供给方决定。

**传统 ITAM 与 Model Registry 都是参照系，不是候选**，两把尺子的量程不同：ITAM 量的是「哪些治理动作不必重新发明」——凡是它已经解决的（台账、许可、盘点、回收），照搬即可；凡是它回答不了的（输出不确定、行为评估、模型耦合），才是 AI 资产管理真正的难点（主文件 §1.5）。Model Registry 量的是「模型侧那一半」——它解决「权重从哪来、哪一版」，不解决「谁在调用、算谁的钱」，两者的关系是联动而非替代（§7.3.3）。

读这张表有一个实用次序：先定位自己在**哪一族**，族内候选的差异通常只有一两条判据，族间的差异才是结构性的。跨族比较时尤其要小心——把「自管族的零成本」与「平台族的可计量」放进同一张表逐项对比，得到的结论一定是「两者都好」，这是没有信息量的。

> 表中与下文的所有公开来源标注，统一写成「机构 + 材料类型 + 年份 + 检索关键词」而不是固定链接——这类产品文档与公告随版本更迭、深链容易失效。核验方式是到该机构的官方文档站或公告区，用括注里的产品名 + 功能关键词检索；引用时请以官方当前版本为准。

### 7.3 机制差异：为什么它们表现不同（核心节）

四个维度是自上而下选的：**授权锚点**决定谁能参与，**必经节点**决定治理动作有没有执行手段，**模型快照绑定**决定资产有没有保质期，**排序与退役**决定资产库能不能长期维持在可用状态。前两条决定「能不能管」，后两条决定「管了以后能不能长期有效」。每个小节都按「机制 → 各候选实现 → 必然导出的性质 → 公开证据 → 失效条件」写；性质一律写成因果句，因为选型要用的是因果，不是形容词。

#### 7.3.1 授权锚点：授权落在仓库权限、平台账号还是准入清单上

- **机制是什么**：每个模式都有一个决定「谁能改、谁能用」的锚点。锚点决定了模式的准入成本，也决定了消费方扩大时它会往哪个方向失效。
- **它在各候选中的实现差异**：

| 候选 | 授权锚点 | 谁能改 | 谁能用 | 由此划定的边界 |
| --- | --- | --- | --- | --- |
| Git 化 Prompt | 仓库权限（分支保护 + 评审） | 有仓库写权限的人 | 能读仓库的人 | 非研发被评审流程挡在门外 |
| Prompt Library | 平台账号 + 角色 | 有平台账号的作者 | 拿到 alias 的调用方 | 改的人与写代码的人解耦 |
| Agent Store | 上架契约 + 平台审核 | 构建者（仅自己的资产） | 平台全部用户 | 公域没有强制准入，只有审核与沙箱 |
| 私有 Marketplace | entitlement（主体 × 资产 × 数据域 × 配额） | 已登记的作者 | 被明确授权的主体 | 未登记则运行时拒绝加载 |
| MaaS | 服务商侧 API key + 配额 | 服务商（你改不了） | 持 key 的服务 | 你能控制的只有调用参数与 Prompt |
| 混合模式 | 双锚点：Git 管写、门户管用 | 作者（Git）+ 发布流水线 | 门户授权的主体 | 需要一致性校验，否则两套真相 |

```text
同一次「改 Prompt」，在两个锚点下的路径差异
  Git 锚点（仓库权限）
    作者改文件 → 提交评审 → 合并 → 部署 / 发布
      失效方式：非研发发起不了评审（准入卡住）；没人评审就合并（质量失守）
  Library 锚点（平台账号）
    作者改 Web 编辑器 → 保存即生成新版本 → 跑离线评估 → 移动 alias（需审批）
      失效方式：账号体系成为新的准入门槛；alias 移动不留痕则不可回滚
  ────────────────────────────────────────────────
  共同点：两者都把「批准」这件事显式化了
  差别只在「谁能排到队」——Git 排给有仓库权限的人，Library 排给有账号的人
```

- **由此必然导出的性质**：因为 **Git 把授权锚在仓库权限上**，所以版本、评审、权限、回滚四件事是零成本继承的（都是 Git 既有机制），代价是**消费方必须具备仓库操作能力**——一旦消费方扩到运营 / 客服，模板会以复制粘贴的形式散到版本库之外，线上实际运行的那一份不再可指认。反过来，因为 **MaaS 的授权锚在服务商手上**，你买到的是一份可被单方面变更的能力合约：能控制的只有调用参数与 Prompt，模型标识若写成滚动别名，服务商的更新就是一次没经过你评审的行为变更。
- **判定方法（可自行核验）**：问三个问题就能确定一个模式的授权锚点——① 一个新同事想改这份资产，需要谁批准？② 一个新消费方想用它，需要谁批准？③ 批准是显式发生（有记录）还是默认成立？第 ③ 问最关键：锚点不留记录时，「谁能改」只存在于人的记忆里，人员一变即失效。
- **公开证据**：LangChain Hub 以中心化仓库托管与分享 Prompt 模板 【公开】（LangChain 官方文档，2023；检索 "LangChain Hub"）；Dust.tt 提供团队级 Prompt 协作与版本管理 【公开】（Dust 官方文档，2023；检索 "Dust prompt versioning"）；PromptLayer 提供 Prompt 版本管理与调用监控 【公开】（PromptLayer 官方文档，2024；检索 "PromptLayer prompt registry"）。「把 Prompt 与调用它的代码同仓、走 code review」是研发团队最普遍的做法 【经验】。
- **失效条件**：Git 的失效点是消费方越过评审门槛时；私有 Marketplace 的失效点是准入摩擦高于绕过收益时；Agent Store 的失效点是供给量增长超过审核能力时。三者的共同规律是——**锚点的摩擦一旦高于绕过的收益，资产就会迁移到锚点之外**。

#### 7.3.2 调用是否穿过平台：准入、授权、计量三张表决定成本能否归属

- **机制是什么**：调用路径上是否存在一个必经节点。有节点，准入（什么能存在）、授权（谁能调）、计量（算谁的钱）三件事才有落库的位置；没有节点，这三件事只能事后统计，治理动作全部失去执行手段（§3.2.4）。
- **它在各候选中的实现差异**：

| 候选 | 调用路径上有无必经节点 | 成本能否归属到调用方 | 退役能否通知到具体调用方 |
| --- | --- | --- | --- |
| Git 化 Prompt | 无（进程直接读文件 / 仓库） | 不能 | 不能（只能发公告） |
| Prompt Library | 有软节点（运行时按 alias 取版本） | 能（按调用方记账） | 能（新版本上线后监控旧版本调用量） |
| Agent Store | 有（运行在平台沙箱内） | 平台侧可计 | 平台可下架，构建者不能定向通知 |
| 私有 Marketplace | 有硬节点（未登记 / 未授权即拒绝加载） | 能（调用方身份即归属维度） | 能（调用方清单直接可得） |
| MaaS | 有（服务商网关计量） | 平台侧原生计量，可按 key 再归因 | 服务商弃用通知 + 自建台账 |
| 混合模式 | 有（门户取制品） | 能 | 能 |

```text
没有必经节点时的「治理」，退化成事后统计
  研发本地改 Prompt ──▶ 直接上线 ──▶ 调用模型 ──▶ 账单落在公司
        │                                            │
        └─ 资产台账里没有这一版                      └─ 拆不到团队
  插入必经节点之后
  调用方 ──▶ 门户（校验登记状态 + entitlement）──▶ 制品 ──▶ 模型
                    │
                    └─ 计量落库：谁 / 哪一版 / 多少 token
  ────────────────────────────────────────────────
  关键：节点不是「多加一层」，而是让「谁在用、算谁的钱」第一次有答案
```

- **由此必然导出的性质**：因为**调用被强制穿过市场**，所以「谁在用、算谁的钱、退役通知发给谁」三问第一次有了确定性答案；代价是市场成为所有调用的关键路径，必须按生产系统标准运维（可用性、延迟、降级），而且**当准入摩擦高于绕过收益时，市场会从治理入口反转成影子资产的温床**——绕过是零边际成本，登记要付评审与文档成本。这条机制推翻了「先建平台再谈治理」的直觉：平台若不能降低调用成本，就只会抬高登记成本。
- **为什么这条在 AI 资产上比在数据资产上更紧要**：数据资产的成本形态是「存储 + 计算」，多数是一次性建设加稳态运行；AI 资产的成本形态是「每次调用都在流钱」——模型 token 是持续消耗项。因此「算谁的钱」不是财务口径问题，而是预算能不能活下去的问题：一个没有计量的平台，会在某个月份发现自己替全公司付了模型账单，而账单上没有任何一个维度能拆分到团队。
- **公开证据**：Salesforce Agentforce 把 Agent 的动作与数据范围绑定在既有角色与共享规则上，动作级留痕可逐条回溯 【公开】（Salesforce 官方文档，2025；检索 "Agentforce agent actions / sharing rules"），本章 [§ 3.4 Agentforce 案例](03-asset-management-section-6-sec6.md) 有展开；阿里通义以统一调用网关按 BU 归因成本并统一约束数据边界 【公开】（阿里云官方文档，2020-2024；检索 "通义调用网关计量"）。
- **失效条件**：当资产不碰内部数据、也不需要成本归属时（例如消费方全是研发、资产是纯文本），必经节点带来的只有摩擦。

#### 7.3.3 版本与模型快照的绑定方式：资产有没有保质期

- **机制是什么**：AI 资产的行为由两个变量共同决定——资产自身的版本，以及它引用的模型快照。契约里写「带日期的快照」还是「滚动别名」，决定了外部更新会不会绕过你的评审。
- **它在各候选中的实现差异**：

| 候选 | 版本化对象 | 模型绑定写在哪 | 外部更新的影响 |
| --- | --- | --- | --- |
| Git 化 Prompt | 模板文件 + metadata（SemVer） | metadata 的 model 字段 | 快照未写死时，升级即重新调参 |
| Prompt Library | 不可变版本 + alias | version 记录里的快照字段 | 新快照 = 新版本，可先跑评估再移 alias |
| Agent Store | 配置版本 | 平台侧的模型选项 | 平台升级模型，构建者的行为随之改变 |
| 私有 Marketplace | 登记项 + 制品版本 | 登记表要登记「依赖哪个模型」 | 模型弃用要纳入资产台账，否则一批「可用资产」突然失效 |
| MaaS | 不版本化（它是供给方） | 你的契约里 | 服务商滚动更新即未经评审的行为变更 |
| 混合模式 | 制品版本 + commit 锚点 | 制品的依赖声明 | 要能「制品 → commit」回溯，才说得清上线跑的是哪一份 |
| Model Registry（参照 / 联动） | 模型权重版本 | 血缘绑训练数据与代码 | 模型侧变更可反向查出哪些资产依赖它 |

```text
契约里的两种写法及其后果
  ✗ model: <厂商>-latest                ← 滚动别名
      今天解析到快照 A，明天可能解析到快照 B
      评估基线测的是 A，线上行为却是 B
      → 失效表现：「没人改过任何东西，效果却变差了」
  ✓ model: <厂商>-<带日期的快照>
      升级变成显式动作：先在新快照上重跑评估集，再发布新版本
      → 「模型升级」被还原成一次可评审、可回滚的变更
```

- **由此必然导出的性质**：因为**行为由「资产版本 × 模型快照」两个变量决定**，所以只版本化资产本身并不能让行为可复现——评估基线测的是旧快照、线上可能跑在新快照上，这类失效在传统软件资产里没有对应物（它的依赖被 lock 在本地，而模型服务的滚动更新不在你的锁文件里）。这也是 AI 资产必须与 Model Registry 联动的原因：模型侧的版本变更，要能反向查出「哪些资产依赖它」。
- **判定方法（可自行核验）**：把资产台账里的模型标识字段逐条看一遍——凡是形如「最新版 / 默认 / 不带日期的别名」的条目，都是潜在静默失效点。再查一件事：上一次模型侧变更时，有多少资产重跑了评估集？答不出，说明「资产 × 模型」的依赖关系没有落库，失效只能等业务反馈。
- **公开证据**：主文件 §1.5 已把「强依赖模型（模型升级 → Prompt 失效）」列为 AI 资产比传统软件资产更难治理的原因之一；§3.2.5 把「契约写滚动别名」列为 MaaS 的失效点。
- **失效条件**：当资产不绑定外部模型（纯检索、纯规则、或自建推理且权重固定）时，这条差异消失，资产回到传统软件资产的行为模型。

#### 7.3.4 发现与退役：排序里有没有质量维度

- **机制是什么**：检索排序的输入变量决定了资产库的长期信噪比。只有相关性 → 旧资产靠历史调用量自我强化；含质量维度（新鲜度 / 调用量 / 评估分 / 复用度）→ 劣质与僵尸资产自然下沉。
- **它在各候选中的实现差异**：

| 候选 | 发现方式 | 排序输入 | 退役通道 |
| --- | --- | --- | --- |
| Git 化 Prompt | grep + 找人问 | 无排序（靠目录结构） | 删文件（无通知） |
| Prompt Library | 名称 / tag 检索 | 可挂评估分与调用量 | 停用 alias + 通知调用方 |
| Agent Store | 分类 / 榜单 / 推荐 | 公域榜单偏曝光与调用量 | 平台下架 |
| 私有 Marketplace | 检索 + 推荐 + 分类导航 | 质量分 + 复用度（可驱动排序） | 待下线 → 确认无调用 → 归档（保留历史版本） |
| MaaS | 按模型能力描述检索 | 平台侧 | 服务商弃用时间表 |
| Model Registry（参照） | 按模型名 / 版本 | 模型指标 | 模型下线 |

```text
排序输入决定资产库的长期形态
  只按相关性排序
      ──▶ 标题好、创建早的资产长期占前排 ──▶ 信噪比单向下降
  加质量分（新鲜度 / 调用量 / 评估分）
      ──▶ 僵尸资产下沉；但前提是有调用埋点与评估记录
  再加复用度
      ──▶ 排序开始逼近「组织真实认可的价值」
  ────────────────────────────────────────────────
  但没有下线通道时，上面三档都只是「排得好看」：
      库里仍塞满零调用资产，检索成本持续上升，最终没人再信排序
```

- **由此必然导出的性质**：因为**登记表只增不减、且排序只看相关性**，所以旧资产会靠历史调用量长期占据检索前列，信噪比单向下降、复用率反向走低——这是整个主题里唯一一条「投入越多、体验越差」的机制；代价是质量分需要有调用埋点与评估记录才成立，而这两样在「只做登记」的系统里通常都不存在，所以质量分往往最后才补上，也直接决定了僵尸资产能存活多久。
- **三类排序输入的差别值得单独说清**：相关性解决「能不能搜到」，质量分解决「搜到的是不是好的」，复用度解决「别人是不是真的在用」。只做相关性时，标题写得好的资产永远排在前面；只有质量分时，评估分高但无人使用的资产仍占据前排；加上复用度之后，排序才开始逼近组织真实认可的价值。
- **公开证据**：§3.5 已把「无退役」列为反模式，并给出「按调用量 + 最后调用时间自动标记，走通知与替代推荐后归档」的修法；§6.2 阿里通义的实践把「复用度可统计并影响搜索结果排序」列为让好资产自然浮现的机制 【公开】（阿里云官方文档，2020-2024；检索 "通义资产复用度排序"）。资产搜索的常见工程形态是全文检索 + 向量检索的混合检索 【经验】。
- **失效条件**：资产数在【经验】千级以内时人工盘点尚能兜住，质量分的边际收益不明显；超过之后没有质量维度就一定失控（§3.6 同一量级判据）。

### 7.4 成本结构对比（不是价格表，是成本函数）

这些模式的成本差异不是「谁贵谁便宜」，而是**成本挂在不同的自变量上**。可以统一写成：

```
总成本 ≈ 固定平台成本                    # 门户 / Registry / 权限 / 计量 / 评估
        + f(资产数, 消费方人数)          # 治理与运营摩擦，近似线性
        + g(调用量, 单次 token 数)        # 能力消耗，近似线性
        + h(影子资产)                    # 绕过治理产生的隐性成本，不体现在任何看板上
```

| 模式 | 主导项 | 隐性成本（h） | 规模上去后谁更贵 |
| --- | --- | --- | --- |
| Git 化 Prompt | f 中的「消费方人数」 | 线上实际运行的那一份不在版本库里 | 消费方一扩张就贵——每个非研发角色都会复制出一份副本 |
| Prompt Library | 固定平台成本 + f(资产数) | alias 移动不留痕 → 回滚失去锚点 | 资产数过千时贵（历史版本只增不减） |
| Agent Store（公域） | 固定成本（审核 + 沙箱 + 政策版本管理） | 排序规则不透明时，流量指标自我强化 | 供给量超过审核能力时贵 |
| 私有 Marketplace | 固定平台成本（四件套） | 准入摩擦高于绕过收益 → 影子资产 | 固定成本先到、收益后到，最考验组织耐心 |
| MaaS | g(调用量)，对资产数与人数零阶 | 数据出域合规 + 模型弃用迁移（Prompt 常在旧快照上调优） | 调用量大时线性变贵，但不因组织扩张跳变 |
| 混合模式 | 固定成本 + f(资产数)（一致性校验） | 存在热改入口 → 两套真相 | 资产数与调用方同时增长时，三套件运维同到顶 |
| 传统 ITAM（参照） | f(台账条目数)，以人力盘点为主 | 无「行为评估」维度，AI 资产的行为变化不是版本号能表达的 | 条目数增长时线性变贵，且不吃规模效应 |
| Model Registry（参照） | f(模型数) | 不覆盖 Prompt / Skill 的调用点 | 模型数不多时不构成主要成本 |

表里最容易被忽略的是第四项 **h(影子资产)，而它往往是四项中最大的一项** 【经验】。原因在机制层面：绕过治理是零边际成本，登记要付评审与文档成本，于是治理越严、影子资产越多，而影子资产既不在资产台账里，也不在你为治理付的那份预算里——它只在两种时刻显形：一次事故复盘（发现线上跑的版本不在库里），或一次合规检查（发现某个团队直连了公有模型）。所以判断一个资产平台是否健康，不看登记数，看**登记数与真实调用数的差额**。

三项关键的【推算】：

- **治理开销随资产数的增长【推算】**：以「登记 + 评审 + 文档」合计 40 分钟/次变更为例 【经验】。资产数 1 000、平均每月每资产发生 1 次变更 ⇒ 1 000 × 40 分钟 = 40 000 分钟 ≈ 667 人时/月，按 160 人时/人月折算 ≈ **4.2 人月/月**；把资产数推到 10 000、频次不变 ⇒ ≈ **42 人月/月**。推导出的结论是：治理成本对资产数近似线性，而「重复建设省下的量」不随资产数线性增长，因此**资产数每上一个量级，登记粒度必须变粗一档**（Prompt 级 → 能力级）、门禁必须从「人工评审每一项」换成「按影响面自动分流」。
- **MaaS 的成本形状【推算】**：单次成本 = 输入 token 数 × 输入单价 + 输出 token 数 × 输出单价（单价请以服务商当期价目为准）。以单次输入 2 000 token、输出 500 token 计，10 万次/日的日成本 = 10⁵ × 单次成本。可靠的结论是**函数形状**：它对调用量一阶线性、对资产数与消费方人数零阶——一个团队用和十个团队用，平台侧的固定成本不变。这与私有 Marketplace 恰好相反。
- **自建推理与 MaaS 的盈亏平衡【推算】**：自建成本 ≈ 一次性容量投入 + 长期运维人力（与调用量弱相关，近似一个常数抬升）；MaaS 成本 ≈ 调用量 × 单次成本（过原点、一阶线性）。两条曲线必然相交，交点位置取决于把当期硬件与模型价目代入后的具体数值（请按当期价目自行计算）。本节能给出的可靠结论只有形状：**调用量不成规模时自建永远算不过 MaaS**——而多数组织的多数 AI 资产，调用量都不成规模。

### 7.5 决策树（每个分支都要有阈值依据）

```
开始
  │
  ├─ Q1 消费方里有非研发角色吗？
  │      否 ─▶ Git 化 Prompt（+ CI 校验）                    〔依据 1〕
  │      是 ▼
  ├─ Q2 资产触达的数据里有「不得出域」类别吗？
  │      是 ─▶ 私有化模型 + 私有 Marketplace                  〔依据 2〕
  │      否 ▼
  ├─ Q3 必须能回答「谁在用 / 算谁的钱 / 退役通知发给谁」吗？
  │      否 ─▶ Prompt Library + 评估门禁                      〔依据 3〕
  │      是 ▼
  │      ├─ Q4 供给是否必须来自企业外部开发者？
  │      │      是 ─▶ Agent Store（契约 + 审核 + 沙箱）         〔依据 4〕
  │      │      否 ▼
  │      ├─ Q5 存在多个独立上线节奏的调用方吗？
  │      │      否 ─▶ 私有 Marketplace（准入 / 授权 / 计量 / 退役）〔依据 5〕
  │      │      是 ─▶ 混合模式（Git 源码 + Registry 制品）      〔依据 5〕
  │      ▼
  ├─ Q6 资产数是否已达万级（人工盘点失效）？
  │      是 ─▶ 在所选模式上叠加「能力级登记 + 质量分 + 自动退役」〔依据 6〕
  │      否 ─▶ 维持所选模式，先不做质量分
  │
  └─ 横切：模型能力从哪来？
         数据不得出域或自用规模足够 ─▶ 自建推理（权重固定）
         否则                        ─▶ MaaS（快照写死 + 弃用时间表纳入台账）〔依据 7〕
```

用法：从 Q1 往下走到底得到一个模式；再回头把 Q6 与横切问一遍——它们与前面的分支是**叠加关系而非互斥关系**（Q6 决定要不要加质量分，横切决定模型能力从哪来），漏掉这两个叠加项是决策树最常见的误用。

**阈值依据**：

- **依据 1（Q1）**：Git 的授权锚是仓库权限（§7.3.1）。【经验】当非研发消费方超过 1 人、且每月需要改 1 次以上时，让他们走评审的成本高于复制粘贴的成本，副本就会出现。
- **依据 2（Q2）**：「不得出域」由数据分类清单判定，与规模、与工具成熟度都无关；数据一旦出域，责任无法靠服务条款转移（§3.2.3 Agent Store 代价段、§3.3 决策表）。
- **依据 3（Q3）**：判据是能否回答「谁在用、算谁的钱、退役通知发给谁」——这三问答不出，说明调用路径上还没有必经节点（§7.3.2），模式只能停在 Library 这一层。
- **依据 4（Q4）**：公域没有强制准入力，平台对陌生供给方只有审核与沙箱两种手段（§3.2.3）；供给若不必来自外部，用外部市场的合规成本远高于收益。
- **依据 5（Q5）**：只要存在两个独立上线节奏的调用方（一方要求固定版本、一方要求快速迭代），单一通道必然牺牲一端，此时需要源码 / 制品分离（§3.2.6）；只有一个节奏时，加这一层只是多一次构建。
- **依据 6（Q6）**：【经验】资产数在千级以内人工盘点还能兜住，万级必须靠指标——与 §3.6「资产数超过人工盘点能力」的跃迁判据同源，理由是治理成本对资产数线性增长（§7.4 第一项推算）。
- **依据 7（横切）**：判据是数据是否允许出域 + 自用规模是否足以摊平自建推理的长期投入；MaaS 的成本对调用量一阶线性（§7.4 第三项推算），规模小时自建算不过。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 研发团队、纯文本 Prompt | Git 化 Prompt | LangChain Hub + 自建仓库 | 不选 Prompt Library：无非研发消费方时，平台先带来的是登录、权限、审计的长期运营成本 |
| 运营 / 业务自助改 Prompt、天级迭代 | Prompt Library + 评估门禁 | 混合模式 | 不选纯 Git：非研发被评审挡住后必然复制粘贴，资产随即失联 |
| C 端流量 / 创作者经济 | GPT Store、扣子 Coze 等公域 Store | 自建对外门户 | 不选私有 Marketplace：公域供给靠外部动机，自建门户拿不到外部开发者 |
| 企业内部、碰内部数据、要成本归属 | 私有 Marketplace（自研 / Agentforce / Copilot Studio） | 内部门户 + 制品库 | 不选公域 Store：外部平台无法承担内部数据边界与成本归属 |
| 模型能力非差异化 | MaaS（Replicate / 阿里云百炼 / Bedrock / Vertex AI） | 自建推理 | 不选自建：容量投入、集群运维、模型迭代三份长期投入，多数团队摊不平 |
| 数据分类含「不得出域」项 | 私有化模型 + 私有 Marketplace | 自建模型 + 内网推理 | 不用公有 MaaS：数据边界不因服务条款而改变 |
| 多调用方、上线节奏不一致 | 混合模式（Git 源码 + Registry 制品） | 制品库 + 双通道发布 | 不选纯 Git：运行时直连仓库会把版本库变成生产依赖 |
| 资产数已达万级 | 能力级登记 + 质量分 + 自动退役 | 混合模式 + 复用度排序 | 不选「继续加登记」：登记数上涨而检索质量下降，复用率反向走低 |
| 受监管行业、审计要逐条举证 | 私有 Marketplace + 动作级留痕 | 混合模式 + 审计留痕 | 不选仅记录对话的 Store 类形态：答不出「对哪些记录做了什么」 |

「不选它的原因」一列比「首选」一列更重要：选型的失败多数不是选错了首选项，而是没意识到备选项在什么条件下会反超。

矩阵之外还有三类议题，落到机制上都是同一条判据的延伸，不构成独立选型逻辑。**计费模型**（完全免费 / 成本中心 / 按调用付费 / 价值分成 / 订阅制）本质是「计量表按什么口径算钱」，只有在调用穿过必经节点（§7.3.2）之后才是个可选择的问题——没有节点时，五种口径一种也实施不了。**资产联邦**（跨组织共享）本质是把授权锚点从企业内 entitlement 换成跨组织合约，因此除授权与计费分账外，还要额外解决合规审查与隐私计算（脱敏 / 联邦学习）：锚点换了，另外五条判据的算法不变。**行业差异**落到的是「治理可举证性」这一条判据的强度差别，而不是另一套选型逻辑：金融要合规与可解释、医疗要可追溯、教育要适龄性与安全、零售要在体验与成本之间取舍、制造要准确性与实时性、法律要准确性与可追溯、政企要国产化与等保——七类行业的资产形态相似，分野在举证强度与数据边界。同理，AI 素养、资产贡献文化、复用优先、Owner 文化、评估文化、文档文化这六项组织能力，是「显式校验」能否落地的人事基础——缺了它们，门禁只会在第一次赶工时被绕过。

**4 个常见组合**（真实系统不会只用一种）：

1. **Git 源码 + Registry 制品 + 私有门户（企业内标准形态）**。职责边界：Git 只管「怎么被写出来」，Registry 管不可变版本与检索，门户管「谁能用、用了多少」。运维代价：三处都要 Owner；一致性校验一旦进流水线，任何热改都会破坏制品 ↔ commit 这条链。
2. **Prompt Library + Eval Hub + 灰度（业务主导迭代）**。职责边界：Library 负责迭代速度，Eval 守住下限（回退用例为零才允许继续），灰度提供真实读数。运维代价：评估集要持续换血，alias 移动必须有审批记录，否则回滚失去锚点。
3. **私有 Marketplace + MaaS（自建能力 + 外部模型）**。职责边界：市场管「资产边界内的一切」（数据、权限、成本），MaaS 管「模型能力」，两边靠数据分类清单划界。运维代价：数据分类要落到字段级并持续维护；模型弃用时间表要纳入资产台账，否则一批可用资产会因外部升级突然失效。
4. **Agent Store + 私有 Marketplace 双通道（对外分发 + 对内治理）**。职责边界：公域通道负责供给与流量，内域通道负责数据边界与计费；同一份能力以两个制品形态存在。运维代价：审核能力与内域准入能力是两套人，且必须防住「用公域通道绕开内域数据边界」这条路径。

四条组合的共同特征是**没有一条能单独覆盖全链路**——作者要 diff、消费者要授权与计量、模型能力来自外部，三者落在三套机制上。判断组合是否成立只有一条标准：各件之间的边界是不是靠**显式校验**连接的（制品 ↔ commit、调用方 ↔ entitlement、模型依赖 ↔ 台账）；边界靠约定连接时，组合会在第一次人员变动后失效。

### 7.7 选错的代价与迁移成本

**反模式：把 Git 化 Prompt 当成选型终点** —— 症状：消费方里已经有运营 / 客服，他们改 Prompt 的方式是从版本库复制一份到自己的文档里 → 后果：资产孤岛，同一缺陷在 N 份副本里各自独立存在，且线上运行的那一份无法用名字指认（§7.3.1）→ 正确的做法：把「非研发能否在不复制粘贴的前提下改 Prompt 并上线」当作硬判据，答不出就必须引入 Library 或「门户 + 制品」。

**反模式：资产数还没过百就先建私有 Marketplace** —— 症状：消费方全是研发、资产数十个，却先建门户 + 权限 + 计量 + 评估 → 后果：登记摩擦高于绕过收益，团队把资产放到平台之外，治理指标在涨、真实覆盖面在缩（§7.3.2）→ 正确的做法：先用 Git + 一条 CI 流水线；等到必须回答「谁在用、算谁的钱」时再建，届时那三个问题本身就是需求。

**反模式：把资产绑定到滚动模型别名** —— 症状：契约里写的是不带日期的滚动别名，评估基线在旧快照上跑 → 后果：服务商一次滚动更新就是一次未经评审的行为变更，资产静默失效——传统软件资产没有这类失效，因为它的依赖被锁在本地（§7.3.3）→ 正确的做法：模型标识写带日期的快照，弃用时间表纳入资产台账，并保留一份与模型解耦的评估集用于迁移后重跑基线。

三个反模式有一个共同点：它们都不是技术选错，而是**把模式当成了目标**。Git 化 Prompt 是「低成本获得版本 / 评审 / 权限 / 回滚」的手段，私有 Marketplace 是「让调用穿过治理」的手段——手段一旦变成目标，判断标准就从「它解决了哪个约束」切换成「它够不够正规」，而正规程度是可以无限追加的。

**换成另一个要动什么**（工作量量级均为【经验】）：

| 迁移路径 | 数据迁移 | 查询 / 调用改写 | 运维重建 | 团队再学习 | 总体量级 |
| --- | --- | --- | --- | --- | --- |
| Git 化 Prompt → Prompt Library | 小：模板文件导入即可 | 小：调用点从读文件改为按 alias 取版本 | 中：多一套要长期运营的平台 | 中：非研发学新入口，研发学制品同步 | 数周—数月 |
| Prompt Library → 私有 Marketplace | 中：版本历史与 alias 要转成登记项 | 中：调用改走市场，鉴权与配额重写 | 大：四件套全建并配值班 | 大：准入 / 评审 / 计量流程要全员接受 | 数月—一年 |
| 私有 Marketplace → 混合模式 | 中：制品与源码双向对齐 | 小：调用点基本不变 | 中：多一条构建发布流水线与一致性校验 | 中：作者回到 Git，消费方仍面对门户 | 数月 |
| 公有 MaaS → 自建 / 私有化模型 | 小：无存量数据要迁 | 大：Prompt 要在新模型上重调并重跑评估集 | 大：推理集群与容量规划 | 大：从「调 API」变成「管模型」 | 数月—一年 |
| Agent Store → 私有 Marketplace | 大：外部资产通常无法迁入 | 大：动作与鉴权模型不同 | 大：审核能力换成准入 / 授权 / 计量能力 | 大：分发逻辑从「流量」换成「权限」 | 一年量级 |

方向反过来（Marketplace → Library、自建 → MaaS）通常是**减负担**；真正难迁的是「治理承诺」——上层已经把「谁在用、算谁的钱」写进流程，降级意味着放弃这些能力，因此多数团队宁可继续背固定成本也不降级。这也解释了为什么模式一旦选定，实际更换率远低于预期：**迁移成本的大头从来不在技术侧，而在已经建立起来的流程与责任分配**。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 消费方全是研发、资产是纯文本 | Git 化 Prompt + CI 校验 | 授权锚在仓库权限上，版本 / 评审 / 权限 / 回滚零成本继承，新增成本只有一条流水线 |
| 消费方含非研发、迭代是分钟级 | Prompt Library + 评估门禁 | 内容与部署解耦才可能免发版迭代；免发版就必须把门禁补在评估与 alias 审批上 |
| 企业内、碰内部数据、要成本归属 | 私有 Marketplace | 调用穿过必经节点，成本归属与退役通知才有执行手段，靠文档页永远做不到 |
| 面向企业外部分发 | Agent Store（契约 + 审核 + 沙箱） | 公域没有强制准入力，能用的只有契约、审核与运行隔离 |
| 模型能力非差异化 | MaaS（快照写死） | 成本对调用量一阶线性、对组织规模零阶，运维面缩到一个客户端 |
| 数据不得出域 | 私有化模型 + 私有 Marketplace | 数据边界不因外部条款而改变，责任也无法靠条款转移 |
| 多调用方、节奏不一致 | 混合模式（源码 + 制品） | 作者态与消费态分离，才能既 diff 又稳定引用 |
| 资产数已达万级 | 能力级登记 + 质量分 + 自动退役 | 治理成本对资产数线性增长，登记粒度必须随之变粗，否则治理先于收益触顶 |
| 受监管行业、要逐条举证 | 私有 Marketplace + 动作级留痕 | 可举证性决定资产能否进入生产，证据链断裂时其余能力都没有意义 |

> 本节小结：这些模式之间**唯一真正起决定作用的差异，是「授权与调用的落点」**——授权锚在仓库权限、平台账号、准入清单还是 API key 上，以及调用是否必须穿过那个锚点。锚点决定了消费方能扩到多远、成本能否归属、退役能否通知到人；其余差异（版本语义、门禁层级、评估方式、检索排序）都是在锚点确定之后才需要回答的问题。把这一条想清楚，打分表里那七行的排序就不再需要了。
>
> 💡 **思考锚点**：数一下你平台上「登记数」与「真实调用数」的差额——那就是 7.4 成本函数里最容易被漏算的 h 项；再确认你的授权锚点落在哪：仓库权限、平台账号、准入清单还是 API key？这个差额越大，说明锚点越容易被绕过，你先收紧哪一处？
