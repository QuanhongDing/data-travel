## 4. 工程实现

§3 说明了 Git 化 Prompt、Prompt Library、Agent Store、私有 Marketplace、MaaS 与混合模式各自被什么约束逼出来，并给了选择判据。§4 回答下一个问题：**选定之后第一步做什么、做到什么程度算过关、存量资产怎么办。**

本节 4.1–4.3 给的是步骤、技术点与工具链本身，从零起步与存量改造两类读者共用；4.4 存量迁移则只面向「资产已经散落在代码库、文档和各个平台账号里，想把它收敛成可治理资产」的团队——AI 资产的起点几乎不可能干净，所以对多数团队来说 4.4 不是补充章节而是主路径的一部分。从零起步、手上还没有存量资产可言的新团队，可以整节跳过 4.4，直接按 4.1 的顺序走。

### 4.1 落地步骤

**Step 1：资产盘点与分级（1–2 个月【经验】；随代码库数量与资产数量变化）**

1. 盘点范围为 Prompt、Skill、Workflow 三类（Agent 模板、知识库、评估集在后续步骤纳入），来源包括代码库、Prompt 平台账号、文档与知识库页面。
2. 先做「引用计数」而不是「重要性投票」：用代码检索数出每个资产被多少个调用点引用，作为分级输入。
3. 分三级——个人草稿 / 团队资产 / 企业资产，只有后两级强制治理。

- **产物**：资产清单（名称 / 类型 / 位置 / 引用点数 / 疑似 Owner / 分级）；一份「暂不治理」名单（分级为个人草稿的）。
- **判据**：抽查 10 个调用点，清单里都能找到它引用的资产；再抽 10 条清单条目，都能指出它在磁盘上的位置。任一侧对不上，说明清单是印象汇总而不是检索结果。
- **为什么必须这一步 / 为什么在这个位置**：盘点决定治理的**分母**。分母不清就上流程，流程立刻面对「到底有多少东西要登记」这个答不出的问题，通常的结局是只登记了主动来登记的那部分，其余成为影子资产。分级决定分母里哪些是「必须做」——不分级而强制全面治理，团队会把东西放到平台之外去（这正是 §3.5「过度资产化」的触发条件）。

**Step 2：版本管理（Git 化）（2–4 周【经验】；随资产数量与改动频率变化）**

1. 模板正文单独成文件（可 diff、可评审），元数据写进 manifest：Owner 具体到人、version、tags、带日期的模型快照、评估数据集路径。
2. 版本号沿用 SemVer，判据是**行为变化**：改错别字动补丁号，新增变量或能力动次版本号，输出行为或模型快照变更动主版本号。
3. CI 里加一条校验：manifest 字段齐全，且模板里的占位符集合 == variables 声明集合。

- **产物**：仓库里的资产目录结构（`ai-assets/<kind>/<name>/`）；manifest schema 与 CI 校验规则；版本号判据的一页说明。
- **判据**：故意在模板里加一个未声明的占位符再提 PR，CI 必须拦住；把 Owner 改成团队名再提 PR，CI 也必须拦住。拦不住，说明校验只写在文档里。
- **为什么必须这一步 / 为什么在这个位置**：Git 已经提供了版本、评审、权限、回滚四件事，这一步的增量成本接近「加一条流水线」，而它产出的 manifest 是 Step 3 评审与 Step 4 发布平台的输入——没有 manifest，评审没有可评的对象，平台没有可登记的字段。版本判据必须在这里定死，否则 Step 5 把评估记录挂到版本上时，会发现「版本号变了但行为没变」，评估历史不可比。

**Step 3：评审流程（与 Step 2 并行，2–4 周【经验】；随资产数量与需要分流的资产类型数变化）**

1. 按类型分流：Skill / Workflow 走 Code Review（代码、依赖、副作用、错误处理）；Prompt 走 Prompt Review（指令、few-shot、变量语义、注入风险面）。
2. 安全审查：能触达哪些数据域、是否会把内部数据交给外部模型服务、是否存在 Prompt 注入面。
3. 性能与成本：跑一次离线评估集，记录通过率与单次调用成本。

- **产物**：按类型各一份的评审 checklist；评审记录（谁评、评了什么、结论）；挂在版本上的离线评估报告。
- **判据**：从最近 10 个合并的 PR 里抽 3 个，每个都能追到一份评审记录与一份评估报告；再抽 1 个 Prompt 类 PR，确认记录里回答了「这段改动会不会让模型把内部数据带进输出」。
- **为什么必须这一步 / 为什么在这个位置**：改 Prompt 的门槛低到不需要发版，评审因此是它唯一的质量门禁。放在 Step 2 之后，是因为评审对象必须是「可 diff 的正文 + 结构化 manifest」；放在 Step 4 之前，是因为平台门禁要引用评估报告作为放行凭据。

**Step 4：发布平台（Registry）（1–2 个季度【经验】；本清单里最重的一步，随资产数量与需要接入的调用方数量变化）**

1. 建 Registry 三件套：资产（稳定 ID）+ 不可变版本（正文 + 参数 + 评估记录）+ 可移动别名（dev / staging / prod）。
2. 别名移动要有审批与留痕；运行时按别名取版本，并保留「取不到时降级到上一可用版本」的路径。
3. 制品与源码做一致性校验（制品能定位到某个 commit），校验步骤进流水线。

- **产物**：资产 / 版本 / 别名三张表与取版本 SDK；别名移动的审批流；制品 ↔ commit 校验的流水线步骤。
- **判据**：做一次回滚演练——把 prod 别名指回上一个版本，确认线上行为跟着变，且记录里能查到「谁在什么时候移动的、移动前后评估分是多少」。做不到，说明别名可移动但没有锚点。
- **为什么必须这一步 / 为什么在这个位置**：它是「线上跑的是哪一版」这个问题的唯一答案。有了它，Step 5 的埋点才能把调用归属到具体版本，Step 3 的评估报告才能挂到具体版本；没有它，评估记录与线上行为对不上，回滚无从下手。也是因为它最重，所以不能一上来就做——先做会得到一个空平台，而空平台消耗的是团队对整套治理的信任。

**Step 5：使用统计与评估反馈（1–3 个月【经验】，与 Step 4 并行铺开；随调用方数量与需要埋点的运行时入口数变化）**

1. 调用埋点：记录调用方身份、资产版本、耗时、token 与成本；成本归属到调用方，而不是归属到资产作者。
2. 评估 Hub：离线评估集（用例 + 断言）与在线读数（任务完成率、采纳率、成本/次、违规率）分开存放，两者都挂版本。
3. 反馈回流：把线上失败样例补进评估集，至少每月一轮——不换血的评估集描述的是过去的业务。

- **产物**：调用日志表；评估集仓库与评估报告归档；一张按「资产 × 调用方」的用量与成本表。
- **判据**：随机挑一个资产，回答三个问题——今天被哪几个调用方用了、用了多少次、成本多少；再抽样对一次账单，数字要能对上。对不上，计量就失去了公信力。
- **为什么必须这一步 / 为什么在这个位置**：没有埋点，Step 6 的市场排序与 Step 7 的退役都失去依据——退役要通知调用方，前提是知道调用方是谁；没有评估集，Step 3 的门禁会退化成「看着还行」。放在 Step 4 之后，是因为埋点必须记版本号，否则数据无法归因。

**Step 6：资产市场（Marketplace）（2–3 个月【经验】；随调用方数量与授权粒度变化）**

1. 准入：未登记不可被调用（是门禁，不是建议）；登记项含 Owner、文档、评估分。
2. 授权：以调用方身份取用（数据域 + 配额），而不是「知道资产 ID 就能取用」。
3. 计量与生命周期：用量归属到调用方部门；退役要走通知与替代资产推荐。

- **产物**：市场门户（检索 / 详情 / 申请授权 / 用量页）；授权与配额表；退役流程与通知模板。
- **判据**：抽 3 个正在被调用的资产，确认每一个都有授权记录；再构造一个「绕过市场直接调用」的场景，确认它在技术上被拒绝，而不是事后被追责。
- **为什么必须这一步 / 为什么在这个位置**：它是「谁能用、用了算谁的钱、出事找谁」这三个问题的答案载体。放在 Step 4、5 之后，是因为市场需要 Registry 提供可发布的资产、需要计量提供排序与成本数据；先建门户后建计量，门户会退化成贴满链接的文档页。

**Step 7：治理（血缘 / 权限 / 退役）（持续）**

1. 血缘：登记三类依赖——资产 → 资产、资产 → 模型快照、资产 → 知识库 / 数据集；变更前查下游清单，含下游 Agent 与调用方。
2. 权限：Owner 具体到人、离职自动触发移交；调用权限以主体（人 / 服务账号 / 部门）为单位授予。
3. 退役：按调用量与最后调用时间标出候选，走「通知 → 替代推荐 → 归档 → 观察期后删除」。

- **产物**：依赖登记表与下游影响面查询；Owner 台账与离职移交流程；退役候选清单与季度退役记录。
- **判据**：改一个被多处引用的底层资产（如知识库版本），确认系统能列出下游资产与调用方；再查看最近一个季度的退役记录，若为零，抽 10 个零调用资产逐个确认它们是否真的还有用。
- **为什么必须这一步 / 为什么在这个位置**：资产只增不减时，检索质量会单向下降，最后没人再用平台。它排在最后启动，但「退役通知要发给谁」这个问题必须在 Step 6 之前就想清楚——退役通知依赖 Step 5 的调用方数据。

**最常被跳过的是 Step 1 的分级。** 症状要到 Step 6 才显形：团队被要求把所有 Prompt 都登记、都评审、都写文档，于是登记量在涨、平台外的调用也在涨——因为绕过是零边际成本，而登记要付评审与文档成本。等到有人开始问「为什么市场里资产这么少、实际调用这么多」，【经验】典型已经过去了 1–2 个季度，快慢取决于资产数与调用方数量。

### 4.2 关键技术点

**Prompt 版本化与变量化**

- **做法**：模板正文单独成文件（可 diff），变量在 manifest 里声明 name / type / required / default；CI 比对「模板占位符集合 == 声明集合」；运行时按别名取版本，而不是引用某个文件的路径。
- **机制**：因为正文与声明分离且占位符集合被机器比对，所以「漏传变量」这类错误在合并前暴露，而不是等到线上某条分支才抛出；代价是每次改 Prompt 都要过一次流水线，作者拿不到「保存即生效」的手感。
- **失效条件**：**当变量被当成「内容容器」时**（调用方把拼好的整段上下文塞进一个变量），这条会失效——模板退化成字符串拼接，CI 只能校验占位符存在、无法校验内容形态，口径漂移重新回到调用方手里。症状是同一个资产在不同调用方那里输出风格差异明显，而模板 diff 几乎没变。
- **档位**：【经验】。

**Skill 的抽象、测试与文档**

- **做法**：Skill = 名称 + 语义描述 + 输入输出 schema + 错误语义 + Owner；测试分两层——契约测试（必填项、类型、错误码）与选择测试（把描述放进候选集，让模型做一次工具选择，看它是否选对）。
- **机制**：因为 Skill 是被模型「按描述」选择的，描述就是它的接口，所以描述不准确表现为选错工具而不是报错；把描述纳入测试集，这个失败模式才能在发布前暴露。代价是要额外维护一份「工具选择」评估集，且每次改描述都要重跑。
- **失效条件**：**当 Skill 数量增长到描述开始互相重叠时**（例如三个描述里都出现「查询订单」），选择准确率会下降，因为模型在语义相近的候选之间没有可依赖的判据。症状是线上出现「参数正确但答非所问」的调用，日志里的工具名是相邻的另一个。
- **档位**：【经验】（数量级分界按团队自身的描述区分度实测，不给精确阈值）。

**Workflow 可视化编排**

- **做法**：用图结构定义流程（节点 = Skill / Agent，边 = 数据依赖与控制流），节点输入输出显式声明；图定义进版本库，与制品一起发布。
- **机制**：因为流程成了数据而不是散落在代码里的分支语句，「谁调用了谁、失败走哪条边」可以静态读出，进而能自动生成影响面与回放路径；代价是图需要运行时引擎，对两三个节点的串行流程引入图的抽象收益为负。
- **失效条件**：**当节点内塞进一大段自由代码时**，可视化会失效——图上只看到一个节点，节点内的分支与副作用不可见。症状是图看起来很干净，排障时仍然要去翻节点代码，图与实际流程成了两张皮。
- **档位**：【经验】。

**资产血缘与影响分析**

- **做法**：把三类依赖登记入库（资产 → 资产、资产 → 模型快照、资产 → 知识库 / 数据集）；变更前查下游清单，清单要含下游 Agent 与调用方，而不只是下游资产。
- **机制**：因为 AI 资产的行为变化常常不出现在接口签名上（改一段 Prompt 就改变了输出），影响面必须由依赖登记提供，类型系统与编译报错都帮不上忙；代价是依赖要真实维护，漏登记的依赖等于不存在。
- **失效条件**：**当依赖是运行时动态产生的时**（Agent 按任务选工具、按用户身份选知识库），静态血缘会漏掉这一类——它们只在运行时存在。症状是改了一个知识库版本，查询到的下游清单是空的，但第二天有 Agent 的输出变了；修法是补一层运行时采集。
- **档位**：【经验】。

**资产权限与 Owner 制度**

- **做法**：Owner 具体到人（不是团队）；权限以调用方身份授予（数据域 + 配额）；Owner 离职自动触发资产移交。
- **机制**：因为资产会触达数据，权限只有以调用方为单位授予，成本与责任才落到具体主体上；代价是每新增一个调用方都要走一次授权，横向铺开的速度变慢。
- **失效条件**：**当授权粒度粗到「一个部门一个账号」时**，这一层失效——计量无法归属到具体消费方，事故也无法定位。症状是账单上成本集中在少数几个账号，问「谁在用」答不出，于是配额与退役都没有抓手。
- **档位**：【经验】。

**资产价值评估与 ROI 计算**

- **做法**：成本侧记 token / 调用次数 / 推理时长；收益侧记「原本需要多少人时」或「任务完成率 × 单次人工成本」；两侧按同一口径落在同一张表上，口径在资产上线前写死。
- **机制**：因为 AI 资产的收益常体现为省下的人时而不是直接收入，只有事先固定「替代了哪件事、这件事原来要多久」这个基线，跨资产比较才成立；代价是要在需求侧做一次基线测算，这项工作事后补不出来。
- **失效条件**：**当基线是事后回忆时**，ROI 会失效——对比基准可以被随意调整。症状是同一个资产在两个季度的 ROI 相差数倍，而调用量与使用场景都没变。
- **档位**：【推算】示例：若某资产日均调用 N 次、每次替代人工 X 分钟，则月度替代人时 ≈ N × X × 30 ÷ 60；N 取自 Step 5 的埋点，X 取自上线前的基线测量，两者都用本团队自己的数据，不引用外部数字。

**资产搜索与推荐**

- **做法**：索引覆盖名称 / 描述 / tag / 示例输入输出；排序显式包含质量维度（评估分、调用量、最近调用时间），并给新资产留探索位。
- **机制**：因为检索按文本相似度排序，历史调用量高的资产会自我强化，所以质量与新鲜度必须作为显式维度进入排序，否则旧资产长期占据前排；代价是质量分的计算口径一旦变更，历史排序不可比，得接受一次「排序跳变」。
- **失效条件**：**当资产数超过人工盘点能力、而排序仍只有相关性时**，检索前排会被旧资产占满，团队转而使用私下渠道，平台可信度进入单向下降（机制见 [§3.5 无退役](03-asset-management-section-3-sec3.md)）。症状是检索请求量平稳，但平台内资产的调用占比在降。
- **档位**：【经验】。

**资产评估与 A/B 测试**

- **做法**：离线评估集（用例 + 断言）作为发布门禁，门禁规则是「回退用例数为 0 才放行」；在线 A/B 按流量切版本，读业务指标（任务完成率、采纳率、成本/次）与安全指标（违规率）。
- **机制**：因为同一 Prompt 不同次输出不同、换模型快照也会改变行为，质量变化必须由一个稳定参照物来测量，而不是靠上线后的体感；代价是评估集自身要维护，它会随业务漂移而过期。
- **失效条件**：**当评估集长期不换血时**，门禁失效——通过门槛只覆盖历史用例，新场景的退化它测不到。症状是评估全绿而线上投诉增加，且投诉集中在最近新增的场景；修法是从线上失败样例定期回补用例。
- **档位**：【经验】起步几十条用例即可跑通门禁，覆盖主要业务分支通常要到百条量级，随场景数增长（区间为实践归纳，不是统计结果）。

### 4.3 工具链与平台

选型的第一判据不是「哪个平台功能多」，而是 [§3.1](03-asset-management-section-3-sec3.md) 里那条最前置的约束——**谁在消费这个资产**。消费方一确定，通道与治理强度就被卡死。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| Prompt 源码管理（消费方是研发） | Git + PR、LangChain Hub（LangChain 公开文档，2023） | 消费方全是研发、资产与代码同仓、需要 diff 与评审 → 直接用 Git；只需要一个可分享的模板仓库 → LangChain Hub | 消费方全是研发却先上平台，等于把 Git 已有的版本、评审、权限、回滚重建一遍，多出登录与审计的长期运营成本，而研发仍在自己的仓库里维护另一份 |
| Prompt 协作与版本（消费方含非研发） | Dust.tt（团队 Prompt 协作与版本管理，公开产品材料 2023）、PromptLayer（版本管理与调用监控，公开产品材料 2024） | 存在非研发同事每周都要改 Prompt，或需要在保存时触发离线评估 → 选带「不可变版本 + 别名 + 评估」的平台形态 | 没有别名与不可变版本，「线上跑的是哪一版」只能靠人记，回滚没有锚点 |
| 企业内资产市场 | 自建 Registry + 门户；厂商企业平台（Salesforce Agentforce、微软 Copilot Studio 等，厂商公开材料 2024–2025） | 必须回答「谁能用、算谁的钱、出事找谁」，或数据不允许出域 → 私有形态；已有成熟元数据、权限、审计体系且希望复用 → 厂商企业平台 | 用外部 Store 承担内部分发，准入没有强制力，关键资产照样散落在平台之外；数据边界也无法靠平台条款转移 |
| 对外分发市场 | OpenAI GPT Store（OpenAI 公开公告 2023–2024）、字节扣子 Coze（字节公开材料 2024）、阿里通义 / 星图（厂商公开材料 2024–2025） | 分发对象是企业外部的陌生人、供给必须来自外部开发者 → 公域 Store 的契约 + 审核 + 沙箱 | 用公域 Store 做内部分发，等于把质量与安全的判断权交给外部审核规则 |
| 模型能力（MaaS） | Replicate（按调用计费的模型推理 API，公开产品材料，可按官方文档核验）、各云厂商模型服务 | 数据分类清单里有无「不得出域」的类别；契约里能否写死**带日期的模型快照**而不是滚动别名 | 契约写滚动别名时，服务商升级就是一次没经过评审的行为变更，而你的评估基线测的还是旧快照 |

表内产品与厂商的年份按「来源类型 + 年份」标注，可按产品名与年份在对应官方文档 / 官方发布记录中自行检索核验；年份口径以官方发布记录为准。

表里**最容易被误选的是 Marketplace 作为起点**：先做市场门户，再考虑登记与计量。典型后果是目录是空的、排序没有质量维度、也没有调用埋点，门户最终退化成「贴满链接的文档页」；正确的顺序是先有 Registry（什么能存在）与计量（谁在用），市场才有内容可分发。

### 4.4 存量迁移

存量团队的现状通常是：Prompt 在代码里、在平台账号里、在某个人的文档里各有一份；Skill 就是几个函数；Workflow 是几段脚本；没有人能说清一共有多少。这套存量的处理原则是**改动即改造**，不是一次性返工。

**① 立刻见效且可回退的第一步。** 先做只读盘点（Step 1 的清单），不动任何代码。第二步选一个被引用最多的 Prompt，把它变成「仓库里的文件 + manifest」，但**不改调用方式**——代码里那份原样保留。这一步随时可回退（manifest 不生效时，原来的路径照跑），产出却直接可检查：这个 Prompt 从此可 diff、可评审。

**② 历史资产按三类处理，不要一次性返工。**

| 类别 | 判定方式 | 处理方式 |
| --- | --- | --- |
| 高引用、场景稳定、有明确 Owner | 引用计数靠前，且近一个季度有人在用 | 补 manifest 与评估集，进 Registry，走新流程 |
| 低引用或场景已变 | 引用计数靠后，或最后调用时间很久 | 打标挂账（标「未登记 / 未评估」），不动它；等它被再次修改时改造 |
| 个人私有（只存在某人本地） | 清单里 Owner 是人且不在任何仓库 | 只做登记与 Owner 确认，不强制评审——避免把作者推向平台之外 |

判据：抽查 5 个资产，能指出每个属于哪一类；指不出的，说明分类只做了命名。三类里**第三类要格外克制**：对只在一人手里、且没有跨团队调用的资产，强制评审的收益小于把作者推走的损失。

**③ 双轨怎么维持、维持多久。** 双轨 = 存量资产继续按旧方式被引用，新资产与「被改动的存量资产」走新流程。边界必须写死一条：**同一个资产不允许两处可改**——改造后的资产要在原位置留一行指向 Registry 的引用，否则立刻出现两套真相。维持时长不用日历定，用收敛条件定（见 ④）；【经验】典型是 1–2 个季度，快慢取决于资产数与调用方数量。

**④ 什么信号说明可以退出双轨。** 三个信号同时成立才算：抽查 10 个近期新增的调用点，全部引用 Registry 中的资产而不是复制模板；存在一个非研发同事在未复制粘贴的前提下改并上线了 Prompt；最近一次模型快照切换时，能列出受影响资产并重跑了评估集。反向信号同样明确：只要「直接改线上版本」的入口还开着，双轨就不会自然退出，它会长成两套真相。

### 4.5 模板 / 示例

**模板 A：资产 manifest（`ai-asset/v1`）**

```yaml
apiVersion: ai-asset/v1
kind: Prompt
metadata:
  name: customer-service-refund
  owner: alice@company.com          # 具体到人，不是团队
  version: 1.2.0                    # SemVer：行为变化才动主版本
  tags: [客服, 退款]
  createdAt: 2025-01-15
  updatedAt: 2025-09-20
spec:
  template_file: template.md        # 正文单独成文件，可 diff、可评审
  variables:
    - {name: agent_name, type: string, required: true}
    - {name: tone, type: string, default: 友好}
    - {name: question, type: string, required: true}
  model:
    provider: <your-provider>
    name: "<带日期的模型快照>"        # 不要写滚动别名
    temperature: 0.7
  eval:
    dataset: eval/customer-service-v1.jsonl
    metrics: [accuracy, safety, style]
status:                             # 平台回填字段，作者不要手填
  phase: published
  usageCount: 0
  satisfaction: 0.0
```

**怎么用**：`name` / `owner` / `version` 三项必填且 Owner 必须是人；`model.name` 填带日期的快照；`status` 整段由平台回填——手填的那一刻它就不再可信。`metrics` 里写自己团队真实会算的那几项，不要照抄示例的三项。

**模板 B：Prompt 资产化（正文与元数据分离）**

```python
from langchain.prompts import PromptTemplate

# 正文来自 template.md，变量声明来自 manifest；二者由 CI 比对
prompt_asset = PromptTemplate(
    template=open("ai-assets/prompt/customer-service-refund/template.md").read(),
    input_variables=["agent_name", "tone", "question"],
)

formatted = prompt_asset.format(
    agent_name="退款客服", tone="友好", question="如何申请退款？"
)
```

**怎么用**：`input_variables` 必须与 manifest 的 `variables` 逐项一致（不一致时 CI 应拦截）；模板文本不要写进 Python 字符串，否则 diff 与评审的对象就不是正文了。

**模板 C：Skill 资产化（描述即接口）**

```python
from langchain_core.tools import Tool

refund_skill = Tool(
    name="refund_api",
    description="查询某笔订单的退款状态。当用户问「退款到哪一步了」「钱什么时候到账」时使用。",
    func=refund_api_call,
    args_schema=RefundInput,      # {order_id: string}，字段名必须与实现一致
)
```

**怎么用**：`description` 是给模型看的接口文档，写「什么时候用」而不是「这个函数做了什么」；`args_schema` 的字段名必须与实现签名一致，否则参数正确性无从保证。示例里的一句话说清适用场景即可，不要堆形容词。

**模板 D：Workflow 资产化（图定义与元数据分家）**

```python
from langgraph.graph import StateGraph

workflow = StateGraph(MyState)
workflow.add_node("query_data", query_data_skill)   # 节点名是影响面分析的锚点
workflow.add_node("analyze", analyze_skill)
workflow.add_node("report", report_skill)
graph = workflow.compile()
```

**怎么用**：节点名会成为血缘与影响面的键，不要用 `node1` / `node2`；资产元数据（Owner / version / tags）写进模板 A 的 manifest，不要在代码里再写一份——两处都写就等于两套真相。图的编译与运行时配置按所用框架官方文档当前版本填。

**模板 E：资产评估记录（挂在版本上）**

```json
{
  "asset_id": "prompt-refund",
  "version": "1.2.0",
  "metrics": {
    "task_completion": "<数值>",
    "csat": "<数值>",
    "cost_per_call": "<数值>",
    "violation_rate": "<数值>"
  },
  "ab_test": { "vs_version": "<对照版本>", "delta": "<指标变化>", "p_value": "<数值>" },
  "evaluator": "auto+human",
  "evaluated_at": "<日期>"
}
```

**怎么用**：`metrics` 的键要绑定到本团队的口径与数据来源（每个键都能答出「从哪张表算的」），键名之外的数值都必须来自真实评估结果；`ab_test` 必须来自真实实验，没做过就留空，不要填一个看起来合理的数；记录与 `version` 绑定，回滚演练时才能回答「移动前后评估分是多少」。

**模板 F：平台架构（模块职责）**

```text
作者态（Git / 平台编辑器） ──▶ 制品（不可变版本 + 评估分）
                                   │
        ┌──────────────────────────┬──────────────────────────┐
        │              AI Asset Management Platform            │
        │  Asset Registry   Version Control   Marketplace      │
        │  Eval Hub         Lineage Tracker   Access Control   │
        │  Search/Recom     Usage Stats       Retirement       │
        └──────────────────────────┬──────────────────────────┘
                                   ▼
                             Agent Runtime
```

| 模块 | 职责 | 对应本节的哪一步 |
| --- | --- | --- |
| Asset Registry | 资产注册、查询、检索 | Step 1、Step 4 |
| Version Control | SemVer 版本管理、别名 | Step 2、Step 4 |
| Marketplace | 资产市场、准入 / 授权 / 计量 | Step 6 |
| Eval Hub | 离线 / 在线评估 | Step 3、Step 5 |
| Lineage Tracker | 血缘、影响分析 | Step 7 |
| Access Control | 权限、配额 | Step 7 |
| Search / Recom | 资产搜索、推荐 | Step 6、§4.2 搜索与推荐 |
| Usage Stats | 调用统计、成本 | Step 5 |
| Retirement | 自动 / 手动退役 | Step 7 |

**怎么用**：这张表是用来对进度的，不是用来排期的——九个模块不必同时开工，按最后一列的顺序做；如果某个模块对应的步骤还没做，先不要建那个模块，否则会得到一个没有数据的空模块，而空模块比没模块更容易让人误以为治理已完成。

### 4.6 成本：这套东西的账单

AI 资产管理的账单不在推理算力上——推理是消费方 Agent 运行时的账（单次调用成本口径已在 4.2、4.5 的评估记录模板里给过）。资产管理自己贵在两件事：**每个版本各跑一次的评估**与**不可变制品的长期留存**。两者都按「资产数 × 版本数」增长，不按调用量增长。这是它最反直觉的地方——用的人越少、迭代越勤，账单反而涨。

- **云账单：评估重跑是主项。【推算】** 月评估成本 ≈ 受管资产数 N × 月均新版本数 V × 单版本评估集条数 M × 单次评估调用单价 P。N、V、M 取自你自己 4.5 的调用埋点与评估集规模，P 取自所用模型服务官方定价页的当期价格（按官方文档核验）。这里不代入数值——N/V/M 的量级差异足以让结论反转。**为什么贵在这里**：评估对象是随机输出，同一版本必须跑完整评估集才敢下结论，抽样会漏掉长尾失败；这一条直接来自 §1.5「输出不确定」。
- **存储：不可变版本是刻意的，别省。【经验】** 单资产单版本的正文 + manifest 在几十 KB 量级，真正占空间的是评估报告与历史评估集；总量随「资产数 × 保留版本数」线性涨，通常落在 GB 量级，一般不构成主要成本。删旧版本等于删掉回滚锚点（见 4.9 第 6 问）。
- **人力：评审与文档是最大项，且随资产类型数放大。【推算】** 评审工时 ≈ 每版本 checklist 项数 × 单条核实耗时；Skill/Workflow 走 Code Review、Prompt 走 Prompt Review（4.1 Step 3），分流类型越多，要维护的 checklist 越多。**为什么贵在这里**：成本结构与微服务的 Code Review 相同，但触发频率高一个量级——改 Prompt 不需要发版（§1.5），评审次数远多于代码评审。
- **模型快照换代是一笔隐性账单。【经验】** 每次绑定快照切换，血缘图里指向它的全部资产都要重跑评估集（§2.5）；不跑，评估基线就与线上行为脱钩，回滚时无法回答「移动前后评估分是多少」。
- 跨主题的成本方法论（分账、单位成本）不复述，指向 [§11 数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)。本节只给本主题特有的部分：治理的固定账单与调用量无关，只与版本数有关。

### 4.7 容灾与故障演练

Registry 不是在线服务，它挂了不直接打崩线上 Agent——这是它和数据库类主题最大的不同，也决定了容灾的靶心不是「保可用」，而是保住两个可回答性：**线上跑的是哪一版**、**切换后哪些资产受影响**。

| 失效模式 | 影响面 | 降级策略 | 演练 | 恢复目标 |
| --- | --- | --- | --- | --- |
| Registry 不可写（发布/回滚通道断） | 新版本发不出、回滚做不了；已上线版本照跑 | 只读降级：资产正文本就存在 Git，以 Git 仓库为 source of truth 手工发版（Git 是天然灾备） | 关掉发布接口，用 Git 走完一次发版 + 回滚 | 【经验】RTO 分钟级到小时级，随手工步骤数变化 |
| 血缘索引损坏或未登记 | 模型快照切换时漏掉受影响资产 → 静默行为漂移 | 用 manifest 里登记过的 eval.dataset 路径反查受影响面 | 随机切一个模型快照，看能否列出受影响资产并重跑评估 | 【经验】RPO 近零到小时级（manifest 在 Git，损失限于未推送的改动），暴露靠演练频率 |
| 评估集 / 评估服务不可用 | 新版本过不了门禁，发布阻塞；不阻塞线上 | 允许带「待评估」标记灰度，生产继续跑旧版本 | 停评估服务，走一次降级灰度 | 【经验】小时级 |
| 模型滚动别名漂移（服务商升级） | 「同一版本」行为变了，评估基线失效 | manifest 写死带日期的快照（4.5 模板 A），漂移即报错 | 把 provider 改成滚动别名，看 CI 是否拦下 | 预防型，无 RTO |

**这项演练与混沌工程的位置不同**：混沌工程测运行时在故障下能不能降级，这里测**治理链在故障下还能不能回答「跑的是哪一版」**——它是一条恢复路径，不是一次攻击注入（通用方法论见 [§12 混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)）。

**为什么不适用跨地域容灾**：制品是 Git 仓库 + 元数据，天然多地冗余；把 Registry 做成跨地域双活，保的是一个原本分钟级可手工恢复的通道，投入产出比不成立。本主题真正的容灾对象是**结论的可复现性**（评估能否重跑出同一结论），不是节点存活。跨地域形态见 [§12 灾备](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)，本主题只指过去。

### 4.8 演进路线：0 → 1 → 100

- **0 → 1（最小可用）：把一个被引用最多的 Prompt Git 化。** 做 4.4 ①那样的最小动作——正文成文件 + manifest + 一条 CI 校验占位符一致，调用方式不变、随时可回退。此阶段**变贵的是**评审人力（第一次要建立 checklist 与 Owner 习惯）；**先坏的是**「线上跑的是哪一版」——只要还有第二个入口能改线上版本，两套真相就开始长。
- **1 → 100（规模化）：Registry + 不可变版本 + 别名 + 埋点。** 触发信号是 §3.6 的规模跃迁：资产数与调用方数量让「人记版本」失效。此阶段**变贵的是**评估重跑（版本数 × 评估集，见 4.6）与 Registry 运维；**先坏的是血缘与检索**——资产只增不减、检索排序没有质量维度（评估分 / 调用量 / 最近调用），平台会先退化成「贴满链接的文档页」（4.3、§3.5 反模式）。
- **100 →（观望项，不进路线图）：资产联邦。** 这是唯一一个把资产推出组织边界的方向，本主题 [§5.1](03-asset-management-section-5-sec5.md)、[§5.2.1](03-asset-management-section-5-sec5.md) 把它判为 **L3（观望）**——公开材料只有概念表述、没有可核验的产品形态，授权模型与存储地约定属合同与合规议题，不是技术选型。所以它不构成 0→1→100 里的一站：路线到 100 为止，之后是把登记必填项、计量归属、退役通道三件工程做扎实（[§5.8](03-asset-management-section-5-sec5.md)）；联邦只记录、观察「不穿过平台就调不到资产」这类信号（§5.6 第 1 条），不为它预留架构假设。真要走到那一步，**变贵的是**准入与合规审查——分发对象变成外部陌生人，契约、沙箱、许可从「组织内约定」升级为「对外承诺」；**先坏的是退役与许可**——跨组织后「通知调用方退役」失去强制力，一个被外部依赖的资产可能永远退不掉，许可条款也不在原组织的改写范围内。

### 4.9 自检清单

1. 随机抽一个线上 Agent，能否说出它今天用的 Prompt 是哪一版（名字可查，不是「最新版」）？
2. manifest 里的 Owner 是否具体到人？填团队名即不算。
3. CI 是否校验「模板占位符集合 == variables 声明集合」？没有，则漏变量只在运行时暴露。
4. 发布门禁里有没有「缺 Owner / 缺文档 / 回退用例数 > 0 不放行」这三条硬规则？
5. 调用埋点能否回答「这个资产今天被哪几个调用方用了多少」，而不只是总调用量？
6. 最近一次模型快照切换时，有多少资产重跑了评估集？答不出，说明模型绑定关系没登记。
7. 检索排序是否含质量维度（评估分 / 调用量 / 最近调用时间）？只有相关性，退役机制迟早失效。
8. 抽查 10 个近期新增的调用点，有几个是引用 Registry 资产的？全是复制粘贴，说明双轨没在收敛。
9. 是否存在「直接改线上版本」的操作入口？存在即等于承认有两套真相。
10. 最近一个季度退役过几个资产？一个都没有，通常不是因为没有僵尸资产。
11. 成本归属能否与实际调用对上（抽样账单 vs 调用日志）？对不上，计量形同虚设。
12. 敏感数据类资产的调用路径，是否全部不经过外部模型服务？有一条直接调用而没过数据分类评审，边界就已经破了。

### 4.10 小结

> 本节小结：整条落地路径里唯一决定成败的环节，是 **Step 4 的 Registry——不可变版本 + 可移动别名 + 制品与源码的一致性校验**。它贵、它慢、它看起来只是个内部系统，但「线上跑的是哪一版」这个问题只有它能回答：没有它，Step 5 的埋点归不到版本、Step 3 的评估分挂不到版本、Step 4 的回滚演练没有锚点，整套治理会退化成一堆互相不引用的记录。也正因为贵，它不能是第一步——先做 Registry 会得到一个空平台，而空平台消耗的是团队对治理这件事的信任，这比晚做半年到一年更难挽回【经验，区间随团队规模与既有信任存量变化】。
>
> 💡 **思考锚点**：对照本节 4.5 的模块—步骤对应表，数一下你现在建了几个模块、各自对应的步骤是否真做了？尤其那个「先建 Registry」的一步——你的埋点能不能把一次线上调用归到具体资产版本、回滚演练有没有版本锚点？这些还答不上来时，你建的是 Registry，还是那个「消耗团队信任的空平台」？
