## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是**没有时间维度**。同一个清单里，「厂商已发布、有对外文档与版本化行为」的能力（GPT Store 与扣子这类分发通道），和「只有路线图里一行字」的条目（资产联邦、Marketplace 标准化）被并列在一起——这份清单共 10 个方向；本节五个族逐条覆盖的就是这 10 个。读者据此排路线图会踩空：前者的失败方式是接口与准入规则会变，后者的失败方式是它可能根本没有产品形态。

第二个问题是「AI 资产」在三个层次上被混用：**分发通道**（Store / Marketplace / MaaS）、**资产自身的形态与写入方式**（自描述字段、自动生成）、**资产的判定与治理**（评估、价值度量、推荐、合规审计）。三者的可规划性差一个量级：分发通道写在平台发布说明里；资产形态写在登记表 schema 与生命周期流程里（主文件 [§2.3 资产生命周期管理](03-asset-management.md)）；判定与治理写在产品功能页与厂商路线图里，而功能页上的描述与版本化能力经常不是一回事。

第三个问题是没有反方观点。「AI 资产市场将成为 App Store」这类句子永远正确，因而没有信息量；清单也不会出现「这条方向今天不值得投」。本节把这类断言改写成可证伪的信号，放在 5.6。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（本节对「release note」的取材口径见下方的判据修正声明）；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期（准入、授权、计量的语义不随版本翻烧饼）。
- **L2 可试点**：①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

**本节对本书的 L1 判据做了如下修正**：判据 ① 中的「正式 release note」，在本主题按「有对外发布、且行为可按版本对照的文档」取——含 release notes / what's new 页与版本化的产品文档、规范。理由是 AI 资产平台的能力通常不随某个产品版本号集中发布，若只认「某个产品 edition 的 release note」，会把已 GA、文档齐备的能力一律记成 ① 不满足，评级反而失真。修正只作用于 ① 的证据形态，②③ 的主体不变（第三方非厂商案例 / 接口稳定）。下表五行都按修正后的 ① 逐行判；本节无一行达 L1 与这条修正无关——第一行卡在 ② 与 ③，其余四行连 ① 都不满足。

判据 ② 在本主题尤其难过：**AI 资产分发的公开材料几乎全部是建设方自述**。平台文档由厂商写，本章 §6 的四个案例（字节扣子、阿里通义、OpenAI GPT Store、Salesforce Agentforce）也都是建设方视角。「第三方（非厂商）公开生产案例」要求的是一个既不卖这套东西、也不靠它立论的团队，公开描述了自己在生产里的用法与失败——在资产市场这件事上，这类材料目前拿不出来。本节口径：**② 只有「满足」与「降为 L2」两种命运**——不能改成「有公开生产记录」，不能靠「本节只评估资产登记层」缩小适用范围来绕过，也不存在「准 L1」「L1 的边界案例」这类说法。

另有一条评级规则，全节通用：**按机制分族，一族一行；族的级别取族内最弱子项**。这不是放宽判据，而是读者做规划时的实际含义——族里只要有一个子项不能依赖，这一族的架构就不能整体依赖。族内每个子方向的名字都列在「方向」列里，**逐子项的级别与判据写在「判据」列里（写成「逐子项定级」，读者可据此复算族级别）**；5.2 逐族拆解，两处的级别与判据必须一致。因此当族内出现级别差一个量级的子项时（已发布的能力 vs 只有路线图的条目），正确做法是**拆族**，而不是把整族按最强者评。

| 演进方向（族内子方向） | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **分发通道**：AI 资产市场（MaaS）/ AI Asset Store 与企业知识管理融合 / 具名平台（GPT Store、Coze、通义星图、Agentforce、Copilot Studio、AgentKit、Vertex AI Agent Builder、Bedrock Agents） | L2 | 族内逐子项定级：MaaS、八个具名平台、AI Asset Store 与企业知识管理融合三类子项 ① 均满足（平台侧有官方公告与产品文档，2023–2025，见 [§4.3 工具链与平台](03-asset-management-section-4-sec4.md)；企业检索与知识库侧有版本化产品文档），② ③ 均不满足（公开案例皆建设方自述；准入、授权、计量的语义各家不同，跨平台无标准，§7.3.2）；族级别取最弱子项 = L2 | 先做对内分发（登记 + 计量 + 退役）；对外分发放到有审核与沙箱能力之后 |

| **检索与治理侧**：资产智能推荐 / 资产合规审计 | L3 | ① 不满足：可核到的是平台功能页描述，缺可对照的版本化规范；② 不满足；③ 不满足 | 推荐先用质量分排序兜底（§7.3.4）；合规审计先用规则清单，不依赖模型判断 |

**本节没有一行达到 L1。** 五行里最高的只有第一行（分发通道），它卡在判据 ② 与 ③ 上：拿不出第三方（非厂商）的生产案例，准入与计量的语义也没有跨平台标准——能力可用而判定标准尚未形成共识，这正是 L2 的定义覆盖的情况。第二行（市场化与联邦）是按上述族规则拆族的结果：它和分发通道同属「把资产推到组织边界之外」这个思路，但族内两个子项都只有路线图表述——**把它们排进 PoC 正是本节开头说要避免的踩空**。市场化与联邦这一行、以及后面三行，都连 ① 都不满足：它们目前的公开形态是功能页描述与路线图，没有可以对照版本的规范。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的官方文档里有没有这个能力的版本化说明（GA / 预览、适用版本、行为变更记录）？找不到 → L3。
2. 建设方之外的证据能不能找到（不是厂商案例、不是本章自带的案例）？找不到 → L2。
3. 准入、授权、计量的语义明年会不会变？会变 → 至多 L2。

三个常见误判，排路线图时最容易踩：

- **把「有市场」误当成「有分发通道」**：市场上架不等于调用被强制穿过平台。没有必经节点时，准入、计量、退役通知三件事只能事后统计（§7.3.2）。
- **把「上架数量多」误当成「生态成立」**：上架数是供给侧的计数，判断生态要看有没有「调用量集中在少数资产上」这类分布证据，而不是总数。
- **把「厂商的合规功能」误当成「合规审计」**：平台的审计能力解决的是平台内的动作留痕，跨平台、跨组织的数据边界仍要由你侧的分类与授权清单回答。

### 5.2 演进方向逐条拆解（核心节）

五个族按「资产在生命周期上被自动化的那一段」排序：分发通道与市场化 / 联邦决定资产怎么被消费（这两个族机制同源、级别不同，合在 5.2.1 里对照拆解），写入侧决定资产怎么被造出来，判定侧决定资产好不好是否有依据，检索与治理侧决定好资产能不能浮上来、坏资产能不能被拦住。五族的级别不同，但失效模式是同一个：**治理动作都要求调用穿过某个节点，而"绕过"这件事的边际成本是零**（§7.3.2）。

还要把「机制改变」与「接口改良」分开：能作为长期方向排进路线图的只有前者，接口改良是近期的工程实施（5.7 那一列「现在就该做」）——它值得做，但不构成别人绕不过的门槛。

- **机制改变**（分发通道的必经节点）：一旦调用必须穿过平台，准入、计量、退役通知第一次有了落库的位置——「谁在用、算谁的钱、坏了谁负责」这三问第一次有了答案。这是本族能评 L2 的原因，也是它同时最容易被绕过的原因。
- **接口改良**（资产自描述）：多几个字段让资产更容易被人读懂，但资产的版本语义没变——它解决的是可读性，不是可治理性。
- **接口改良**（把评估分绑进排序，以及 5.2.4 的智能推荐）：这两项改的是同一处——资产「被找到」的路径。排序输入里多一个质量维度、推荐换掉找资产的入口（§7.3.4），僵尸与劣质资产会因此下沉，但三问仍然没有答案；按下面那句判据，它们归接口改良，不归机制改变，也不该记在判定侧名下——判定侧交出去的是评估分，排序是检索侧的动作（5.2.3 与 5.2.4 各执一半）。

判断只需一句话：如果这条方向只是让资产更容易被找到或被读懂，它是接口改良；如果它让「谁在用、算谁的钱、坏了谁负责」第一次有了答案，它才是机制改变。

#### 5.2.1 分发通道（L2）与市场化 / 联邦（L3）：Store、Marketplace、MaaS 与资产联邦

- **旧做法与它的卡点**：Prompt 与 Skill 散在各自的仓库里，用完即弃；想让别的服务复用，要么复制粘贴，要么靠口头约定。资产没有版本，改动无法回滚；调用不穿过任何节点，于是**「谁在用、算谁的钱、退役通知发给谁」三问都没有答案**（§7.3.2）。这不是工具问题——是调用路径上缺一个必经节点。
- **AI 改变了什么机制**：把资产的分发从「文件复制」变成「按契约取制品」，并在调用路径上插入一个必经节点（市场 / 门户 / 网关）。机制上的关键是：**节点让准入、授权、计量三件事第一次有落库的位置**，成本归属与退役通知也第一次可定向。
- **由此得到的**：因为调用被强制穿过节点，所以「谁在用、算谁的钱、退役通知发给谁」从估算变成查询结果；因为账号或登记项成了授权锚点，改资产的人与写代码的人可以解耦（§7.3.1）——改的人不必懂代码，用的人不必认识作者。
- **由此付出的**：节点成为所有调用的关键路径，必须按生产系统标准运维（可用性、延迟、降级），而这层运维在「没有市场」的形态里根本不存在；**当准入摩擦高于绕过收益时，市场会从治理入口反转成影子资产的温床**——绕过是零边际成本，登记要付评审与文档成本；资产语义还多了一层外部依赖：多数资产绑定某个模型快照，服务商升级就是一次未经你评审的行为变更（主文件 [§1.5](03-asset-management.md) 与 §7.3.3）。
- **证据与来源**：【公开】平台侧的公开公告与产品文档（OpenAI 在 2023 年 11 月的开发者日上宣布 GPT Store、2024 年 1 月起面向付费用户开放；Salesforce 官方文档 2024–2025 记录 Agentforce 的动作级留痕与角色 / 共享规则绑定；字节、阿里的公开材料 2024–2025，见本章 [§6 的四个案例](03-asset-management-section-6-sec6.md)）；MaaS 的公开产品形态（Replicate 等按调用计费的模型推理 API，可按官方文档核验）；第三方（非厂商）生产案例与跨平台流通标准：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「分发通道」行一致：① 满足、② 不满足、③ 不满足）。本条覆盖：AI 资产市场（MaaS）、AI Asset Store 与企业知识管理融合，以及八个具名平台；另两个方向（资产 Marketplace 标准化、资产联邦）机制不同、级别也不同，见本节末的「市场化与联邦」。

三种分发形态的差别不在「哪里功能多」，而在调用路径上有没有节点：

```text
三种分发形态的接口边界（谁调用谁 / 失败谁负责）
  ① Git 化（无节点）
     调用方 ── 直接读文件 / 仓库 ──► 模型
     准入：无   计量：无   退役通知：只能发公告
     失败归谁：调用方自己（他不知道有谁在用同一份资产）
  ② 门户 / 市场（软节点，按别名取制品）
     调用方 ──► 门户（校验登记状态 + 授权）──► 制品 ──► 模型
     准入：有（未登记不能发布）  计量：有（按调用方记账）
     退役通知：有（能列出旧版本的调用方）
     失败归谁：门户（可用性、延迟、降级）
  ③ 私有 Marketplace（硬节点，未授权即拒绝加载）
     调用方 ──► entitlement（主体 × 资产 × 数据域 × 配额）──► 制品
     准入：强制   计量：按主体归属   退役：调用方清单直接可得
     失败归谁：市场侧；摩擦高于绕过收益时，调用会迁到节点之外
  ────────────────────────────────────────────────
  判定方法：问「一个新消费方想用这份资产，需要谁批准、这次批准
  留没留记录」。批准是默认成立时，你只有登记表，没有分发通道
```

- **失效条件**：当资产不碰内部数据、也不需要成本归属时（消费方全是研发、资产是纯文本 Prompt），必经节点带来的只有摩擦，此时正确做法是退回 Git 形态（§3.2.1、§7.3.2）。反过来，当准入摩擦高于绕过收益时，节点会从治理入口反转成影子资产的温床——判别信号是登记表里的资产数与实际调用日志里的资产数出现系统性差额。
- **自验方法**：抽三项正在被调用的资产，回答「它的调用方有谁、上一次调用发生在什么时候、如果明天要下线它，通知发给谁」。三问都答得出，说明调用确实穿过了节点；答不出，说明你手上有一张登记表，但没有分发通道。

**同一个「市场」思路下的第二族：市场化与联邦（L3）**。它和分发通道的差别不在功能多少，而在它连产品形态都还没有：

- **旧做法与它的卡点**：跨组织共享资产时，授权模型、数据能落到哪、按什么口径计量、退役通知发给谁，全靠合同逐条谈；每换一个合作方就重谈一遍。没有可复用的机器可读约定，谈成之后也没有地方落库，于是**每次共享都是一次例外**，同一件资产在两家合作方处的语义可以完全不同。
- **AI 改变了什么机制**：**没有改变机制**。这一族要解决的是「资产能不能跨过组织边界流通」，而机制上的前提（谁能授权、数据落在哪、失效通知发给谁）今天在单一组织内已被 §7.3.2 的三张表回答；跨组织时这三张表要换成合同、数据出境判断与审计义务。**要越过的是治理边界，不是技术缺口**，所以 AI 在这里没有新增杠杆——它能让契约文本草拟得更快，但草拟不产生强制力。
- **由此得到的**：现在能得到的只有设计上的收益——把资产登记项、版本号与调用方清单按将来可交换的形态定义（外部主体有独立标识、存储地是登记字段而不是注释），真要联邦时不必重建。这是**为将来省掉一次重构**，不是今天多出一项能力。
- **由此付出的**：把 L3 的方向写进架构假设的代价是预算与排期被占住，而交付物可能只是路线图上的一个名字——5.1 说的「只有路线图里一行字」的两条就是它们。反向的代价同样存在：为了「以后能联邦」而过早引入跨组织的授权模型与存储地约定，会立刻抬高对内的准入摩擦，把调用赶到节点之外（见本节的失效条件）。
- **证据与来源**：跨平台资产描述与流通标准、以及「资产联邦」的产品形态：无公开可核验来源（见 5.4）；本章 [§4.5 模板 / 示例](03-asset-management-section-4-sec4.md) 的 `apiVersion: ai-asset/v1` 一类 schema 是本章自带的字段口径，属自建规范，不是行业标准。可按「跨组织数据共享授权模型」「AI 资产流通标准」自行检索核验有无多方采纳的规范出现。
- **成熟度**：**L3**（与 5.1 表「市场化与联邦」行一致：① 不满足、② 不满足、③ 不满足）。这条方向现在的正确用法是**记录**：把它写进观察清单并定义「什么信号出现才算成真」（见 5.6 第 1 条），而不是排资源。

#### 5.2.2 写入侧：资产自描述与自动生成

- **旧做法与它的卡点**：资产的可发现性与可用性靠作者自觉写文档。写的人少、写得不全、写完不更新——结果是「检索命中后仍需问作者」，复用率上不去（§3.5 无文档）。作者侧还有一层困难：Prompt 类资产没有接口签名，运行时才能发现问题，而文档正是唯一的事前描述。
- **AI 改变了什么机制**：把「补文档」和「造资产」从纯人力换成一次模型生成——自描述是让 LLM 从资产本体（模板、示例、调用记录）反推出 README / Eval / Few-shot；自动生成是让 LLM 直接从需求或历史轨迹产出资产草稿。**它改变的是资产的写入成本，不是资产的判定成本。**
- **由此得到的**：因为文档与示例的补全成本下降，所以历史上因「没人写文档」而失联的存量资产第一次有机会被补齐描述；因为草稿生成成本下降，所以资产数量可以更快扩张——但这条推论同时是它的代价来源。
- **由此付出的**：生成物默认不进评审流程时，自动生成等于把治理整体绕过——资产数量上涨而有效数不动（§3.5 资产孤岛与过度资产化会同时出现）；**自描述的质量上限就是它读到的材料**，材料里没有成功判据时，生成出来的 Eval 只是形式的；模型还会补齐并不存在的适用场景（与技能侧的「抽象出从未发生的步骤」同族），而被补上的描述比缺失的描述更难被发现，因为它看起来完整。
- **证据与来源**：自描述字段与自动生成目前可核到的公开材料是平台功能页描述与厂商演示；「文档是发布门禁的一部分」这一条在本章 [§3.5 反模式](03-asset-management-section-3-sec3.md) 的修法列里有明确口径（文档缺项不能发布）；第三方生产案例与版本化规范：无公开可核验来源。
- **成熟度**：**L3**（与 5.1 表「写入侧自动化」行一致：① 不满足、② 不满足、③ 不满足）。本条覆盖两个方向：资产自描述（自带 README / Eval / Few-shot）、资产自动生成（LLM 生成资产）。

要走自动化，先把「哪些字段是硬门禁」定下来——自动化只能填这些字段，不能替它们定标准：

| 字段 | 谁来填 | 缺了会怎样 | 可否自动生成 |
| --- | --- | --- | --- |
| 适用场景 | 作者 | 检索命中后仍需问作者，复用率上不去 | 可生成草稿，必须人确认 |
| Eval 集与通过线 | 作者 / 业务方 | 模型升级后无声变差，没有观测通道（§3.5 无评估） | **不能**：可自动扩样，不可自动定通过线 |
| Few-shot 示例 | 作者 | 新调用方要试错，首用成本高 | 可自动生成，须抽检 |
| Owner（具体到人） | 作者所在团队 | 出事只找得到「某团队」；离职即失联 | **不能** |
| 依赖的模型快照 | 发布流水线 | 服务商滚动更新即未经评审的行为变更 | 可自动回填，不可自动升级 |

- **失效条件**：当资产的输出不确定、评估维度又多时，自动生成的 Eval 会给出一份**看起来完整、实际测不出问题**的评估集——判别信号是「评估集全过、业务侧仍抱怨」。此时要补的不是更大的模型，而是把通过线的定义权收回到业务方。
- **自验方法**：随机抽 5 件自动生成描述或自动生成草稿的资产【经验：随资产数变，资产越多抽得越多】，回答「它的通过线是谁定的、负责人是谁」。两问都答「是生成的」，说明这条链路上没有任何人做过判断。

#### 5.2.3 判定侧：资产自动化评估与价值度量

- **旧做法与它的卡点**：资产好不好靠「试了感觉不错」。上线没有评估集，模型升级后无人知道有没有变差；成本也算不出来——同一件资产被多少服务调用、每次多少 token，在「不穿过节点」的形态里没有地方落库（§7.3.2）。质量与成本两条反馈都没有，迭代就只能靠换 Prompt 试。
- **AI 改变了什么机制**：把「好不好」从人的主观判断换成一次可复现的评分（LLM-as-Judge + 人工抽样），把「值不值」从感觉换成一个可算的比值（ROAS）。机制上它做的是同一件事：**把质量与成本变成可记录、可比较的量**——而比较要求口径固定。
- **由此得到的**：因为有了可复现的评分，模型快照升级这类外部变更第一次能被观测到（评估基线变了没有）；评估分同时也是检索侧可用的排序输入，挂上去后僵尸与劣质资产会自然下沉（§7.3.4）——但排序是检索侧的动作，判定侧交出去的是分数（5.2.4）。
- **由此付出的**：判定器与被判定对象同源时，两侧的错误是相关的，验证会一致地漏掉同一类错（同机制见 [Ch7 §4 §3.1 的约束表](../04-agent-skill-extraction/04-agent-skill-extraction-section-3-sec3.md)）；成本归属做不到时价值度量的分母不可信，而分母不统一时横向比较没有任何意义；更现实的一层代价是**评估集本身要维护**——工具链与模型快照一变，基线就得重跑，这笔成本随变更频率增长，是一次性的建设费之外的另一项经常支出。
- **证据与来源**：【公开】「发布前跑评估集、回退用例为 0 才放行」这一条写在本章 [§3.5 反模式](03-asset-management-section-3-sec3.md) 的修法列；资产复用度可统计并影响搜索结果排序，是本章 [§6 的阿里通义案例](03-asset-management-section-6-sec6.md) 记录的机制（阿里云官方文档，2020–2024，可按「通义资产复用度排序」检索核验）；LLM-as-Judge 与 ROAS 的公开可比口径：无公开可核验来源。
- **成熟度**：**L3**（与 5.1 表「判定侧：评估与价值度量」行一致：① 不满足、② 不满足、③ 不满足）。本条覆盖两个方向：资产自动化评估（LLM-as-Judge + 人工抽样）、资产 ROAS。

评估与价值度量要分开算，因为它们的分母性质不同：

```text
两类度量，两种用途（混用会让两个结论都不可信）
  评估分（相对量，与基线比）
     输入：评估集 + 通过线 + 当次模型快照
     用途：发布门禁、版本回归、A/B
     可比范围：同一资产的不同版本——跨资产比较要先统一评估集
     失效信号：集全过而业务侧仍抱怨 → 通过线宽了，不是模型变强了
  价值度量（比值，与投入比）
     分子：业务侧可归因的收益（减少的工时 / 提升的接受率 / 降低的单价）
     分母：模型调用 + 平台运维 + 人力
     用途：单资产趋势、预算取舍
     可比范围：分母口径一致的资产；口径不一致时横向排名无意义
     失效信号：分子改口径就能翻倍 → 说明归因方式没有固定
  ────────────────────────────────────────────────
  共同前提：两者都要求调用穿过节点（§7.3.2）。
  没有计量时，两个数都只能靠人估，而估出来的数不能用来做取舍
```

- **失效条件**：当资产的收益无法归因（一件 Prompt 被三个服务共用，收益落在哪个业务指标上说不清）时，价值度量的分子就是主观的，此时该做的是退回**相对比较**（同一资产的两个版本比）而不是绝对收益。判别信号：换个归因口径，排名就变。
- **自验方法**：拿一件线上资产，问「上一次模型快照变更时，它重跑评估集了吗」以及「它的调用成本能拆到哪个团队」。前一问答不出，说明评估没进流程；后一问答不出，说明计量没落库——两问答不出时，别谈 ROAS。

#### 5.2.4 检索与治理侧：资产智能推荐与合规审计

- **旧做法与它的卡点**：资产检索靠名称与标签，排序只看相关性——于是标题好、创建早的资产长期占前排（§7.3.4 的三类排序输入里只做了一类）。合规审查靠人工整理清单：哪些资产含个人信息、谁被授权访问，每次审计都要重新盘点一遍，而资产还在持续新增。
- **AI 改变了什么机制**：推荐把「适配判断」从人读描述换成一次模型匹配（按任务描述选资产）；合规审计把「逐条核对」换成规则 + 模型抽取。要区分的是两处改动的性质：**推荐这一侧改的是排序输入**——候选里多了一个质量维度（§7.3.4），它决定的是资产「被找到」的概率、与判定侧交出的评估分是同一件事的两端，按 5.2 开头的判据属**接口改良**，不构成机制改变；**合规审计这一侧改的是举证落点**——审计结论从「有没有」变成「谁能证明」，这一处才回答「坏了谁负责」，而它的成立前提是合规属性进入登记必填项（5.3 表与 5.5 第三条），今天还不成立。
- **由此得到的**：因为排序输入里出现了质量维度，劣质与僵尸资产会自然下沉，检索信噪比不再单向下降（§7.3.4）；因为合规属性可以挂到资产登记项上，**「哪些资产含个人信息、谁能访问」这类问题第一次可以变成一次查询**，而不是一次盘点。
- **由此付出的**：推荐会放大已有的偏差——排序里没有质量维度时，模型只会把「曝光高的」推得更高，形成自我强化（§7.3.4 的机制句）；合规审计的结论若由模型给出，**举证责任仍在人**，而「这是模型判的」不能作为合规答复（同族讨论见 [Ch7 §1 §5.2.3](../01-long-term-memory/01-long-term-memory-section-5-ai.md)）；推荐与审计都要读资产元数据，元数据不全时两者都会给出「看似有结论、其实缺输入」的输出。
- **证据与来源**：【公开】排序输入分三类、以及「按调用量 + 最后调用时间自动标记，走通知与替代推荐后归档」的修法，写在本章 [§7.3.4](03-asset-management-section-7-sec7.md) 与 [§3.5 无退役](03-asset-management-section-3-sec3.md)；【公开】企业级平台把 Agent 动作与数据范围绑定在既有角色与共享规则上、动作级留痕可逐条回溯（Salesforce 官方文档，2024–2025，可按「Agentforce agent actions / sharing rules」检索核验）；智能推荐与自动合规审计的公开生产案例：无公开可核验来源。
- **成熟度**：**L3**（与 5.1 表「检索与治理侧」行一致：① 不满足、② 不满足、③ 不满足）。本条覆盖两个方向：资产智能推荐、资产合规审计。

- **失效条件**：当资产元数据不全时（没有 Owner、没有评估分、没有调用埋点），推荐与审计会同时退化成「有结论、无依据」——判别信号是推荐结果无法解释「为什么推它」，而审计结论无法给出「依据是哪一条记录」。此时要补的是元数据，不是更聪明的模型。
- **自验方法**：从检索前列里取 10 条【经验：随资产数与检索量变，库越大抽得越多】，问「为什么它排在前面」；再从审计报告里取 3 条结论【经验：随审计频次变，首次可多抽】，问「依据是哪一条落库的记录」。两处都答得出，说明这两项已经接在元数据上；答不出，说明它们接在模型上。

### 5.3 与本主题既有栈的接口在哪

AI 资产不是新的一层数据，它是**挂在既有账号、权限、计量与元数据体系之上的一套登记与分发协议**。下表写清谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 资产登记 ↔ [§2.4 资产版本管理（SemVer）](03-asset-management.md) | 不可变版本 + 可移动别名；版本号与评估记录绑定 | 资产侧；别名被移动而不留痕时，回滚没有锚点（§3.5 无版本） | 机制成熟，可直接用；判据是别名移动有没有审批记录 |
| 分发通道 ↔ [§7.3.2 准入 / 授权 / 计量三张表](03-asset-management-section-7-sec7.md) | 调用方 → 节点（校验登记状态与 entitlement）→ 制品 → 模型 | 市场侧；节点成为关键路径，须按生产系统运维 | L2（5.2.1）；节点可建，绕过不可禁 |
| 资产 ↔ 模型快照 | 契约里写死带日期的快照；模型侧变更能反查依赖它的资产 | 平台侧；未登记依赖时表现为「没人改过任何东西，效果却变差了」 | 须自建依赖回查（§7.3.3） |
| 资产 ↔ [§2.3.7 退役](03-asset-management.md) | 待下线 → 确认无调用 → 归档（保留历史版本）+ 替代资产推荐 | 资产 Owner；缺退役通道时库只增不减，检索信噪比单向下降 | 机制明确，落点是有没有调用埋点 |
| 资产 ↔ [Ch7 §2 反馈闭环](../02-feedback-loop/02-feedback-loop.md) | 评估资产（Eval 集）既是资产的输入，也是反馈闭环的产物 | 业务方定通过线，平台侧只跑基线 | 接口清楚；通过线的定义权常被平台顺手拿走 |
| 资产 ↔ [Ch7 §1 长期记忆](../01-long-term-memory/01-long-term-memory.md) | 记忆资产按用户 / 团队隔离，与 Prompt 类资产的授权模型不同 | 记忆侧负责隔离与删除义务；资产侧不管删除 | 授权模型不通用，须分别设计 |
| 资产 ↔ [Ch7 §4 技能提取](../04-agent-skill-extraction/04-agent-skill-extraction.md) | Skill 作为一类资产登记：提取侧只产出候选，资产侧管版本与退役 | 提取侧负责入库精度，资产侧负责可回滚 | L2（与技能侧 §5.1「库的出口」行同口径） |

这张表里只有两行是「有现成件可用」：一是 SemVer 版本机制，二是退役流程的形态。其余各行**都要自建或自测**，而且失败几乎都落在平台团队之外——通过线归业务方，删除义务归合规方，模型快照归平台侧，审批记录归资产的 Owner。把它写进接口表的用处不是分工好看，而是**事故发生时不必现场决定谁负责**；如果这张表在你们那里画不出来，说明资产还没有人认领。

**判定这张表有没有被用起来**：每个季度核两个数——检索前 10 条【经验：随资产数与检索量变，库越大抽得越多】里有几条是能用的（信噪比），以及退役时能不能列出全部调用方（分发通道是否真的穿过节点）。两个数一个都不看，资产管理就还停留在登记表层。

### 5.4 公开进展与文献

- **论文**【公开】：本主题可引的是**方法**类文献，不是「资产市场」这一形态本身——后者今天的公开材料是产品文档与合同，没有可引的论文。三篇与本节方向直接对应、可按题名检索核验：Zheng 等《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》（NeurIPS 2023）对应 5.2.3 的评估器：该文既给出模型裁判与人类偏好一致程度的大致水平，也记录了三类系统性偏差（位置偏好、冗长偏好、自我增强偏好）——其中的「自我增强偏好」正是 5.2.3 那条「判定器与被判定对象同源」的代价在文献侧的依据；Mitchell 等《Model Cards for Model Reporting》（FAT\* 2019）与 Gebru 等《Datasheets for Datasets》（2018）对应 5.2.2 的自描述字段——两者的共同做法是把「该记录哪些字段」定成固定字段表，而不是让生成器自由发挥，这正是 5.2.2 把「哪些字段是硬门禁」单列一表的原因。**注意**：这些文献给出的是方法与它的局限，不构成本主题的公开可比口径；判据 ② 要的第三方生产案例仍无公开来源（见下一类）。
- **厂商公开公告与产品文档（判据 ① 的核验入口）**【公开】：OpenAI 在 2023 年 11 月的开发者日上宣布 GPT Store，2024 年 1 月起面向付费用户开放（可按「GPT Store」检索官方公告与帮助文档，开放范围以公告为准；上架数量一类计数在公告与媒体中口径不一，不要作为架构判断依据）；Salesforce 官方文档（2024–2025）记录 Agentforce 的动作级留痕与角色 / 共享规则绑定，可按「Agentforce agent actions」检索核验；字节扣子、阿里通义与百炼、Microsoft Copilot Studio、Google Vertex AI Agent Builder、AWS Bedrock Agents 的公开产品材料（2023–2025，名称与当前形态请以各厂商官方文档当前版本为准）；Replicate 等按调用计费的模型推理 API（可按官方文档核验）。本章 [§4.3 工具链与平台](03-asset-management-section-4-sec4.md) 给出的是选型判据，不是能力背书。
- **标准与规范**：跨平台资产描述与流通目前**没有**可核验的公开标准；本章 [§4.5](03-asset-management-section-4-sec4.md) 的 `apiVersion: ai-asset/v1` 一类 schema 是本章自带的字段口径，属于自建规范，不是行业标准——引用它时请按「本章口径」而非「业界标准」表述。
- **第三方（非厂商）公开生产案例**：无公开可核验来源。这是本节没有任何方向被评为 L1 的直接原因（判据 ②）。
- **值得注意的空白**：公开材料里能查到「平台提供哪些功能」，查不到「谁用了、用了多久、哪些资产实际在产生收益、怎么回滚」。这不是因为它们不重要，而是因为资产的失败通常是静默的（调用成功了、但资产本身已经过时），不容易被写成可引用的报告。它同时意味着：**这类判断只能自己测**。

本节涉及的产品迭代快，最容易出错的三类引用是：

| 引用类型 | 常见错误 | 核验方式 |
| --- | --- | --- |
| 「某平台在某年推出某能力」 | 把宣布时间当发布 / GA 时间，或把路线图当既成事实 | 查官方公告与产品文档里的 GA / 预览标记与适用版本 |
| 「某平台有数百万资产」 | 把供给侧计数当生态成立的证据 | 看有没有调用分布这类需求侧证据；无则只记为计数 |
| 「某方案让复用率提升 X%」 | 把建设方自述数字当作可比较结论 | 看复用率怎么定义（调用数 / 去重调用方数），以及有没有建设方之外的复现 |

### 5.5 被过度宣传的部分

**「AI 资产市场将成为 AI 时代的 App Store」**

- *实际是什么*：移动应用商店的成立前提是「分发是唯一合法路径」——开发者绕不开它。AI 资产没有这个前提：Prompt 是一段文本，Skill 是一段配置，复制粘贴的边际成本是零。
- *为什么会这样*：市场能强制的是它自己的沙箱，管不到别处；而准入摩擦高于绕过收益时，资产会迁到市场之外（§7.3.2）。判据 ② 拿不出第三方生产案例，也是同一条机制在证据层面的表现。
- *什么时候它才会成真*：出现「不穿过市场就调不到模型或数据」的强制条件（例如资产必须绑定平台侧的统一网关与数据权限），且调用日志与登记表的资产集合一致。

**「资产可以自己描述自己，写上 README 与 Eval 就够用」**

- *实际是什么*：自描述解决的是可读性，不解决可治理性。资产的版本语义、依赖的模型快照、退役通道，都不因为多了一个 README 字段而存在。
- *为什么会这样*：评估集的通过线只能由业务方定，模型可以扩样但不能定线（5.2.2 的字段表）；而生成出来的描述看起来完整，因此比缺失的描述更难被发现。
- *什么时候它才会成真*：自描述字段进入发布门禁（缺项不能发布），且 Eval 的通过线由业务方签字而不是由生成器给出。

**「资产合规审计可以自动化，交给模型审就行」**

- *实际是什么*：自动审计能做的是从元数据里抽取与比对；它回答不了「这次审计的结论由谁签字」。合规举证的落点是可核验的记录，不是模型的判断。
- *为什么会这样*：审计要求可举证，而模型输出不可举证（同族的边界讨论见 [Ch7 §1 §5.2.3](../01-long-term-memory/01-long-term-memory-section-5-ai.md) 关于自动遗忘与合规删除的分野）；元数据不全时，自动审计给出的是「有结论、无依据」。
- *什么时候它才会成真*：合规属性（数据分类、授权主体、存储地）成为资产登记的必填项，且审计结论能逐条回溯到落库记录。

这三条有一个共同结构：它们都把「接口已经就位」说成「机制已经就位」。分发通道、自描述字段、审计抽取确实已经就位（这也是分发通道能评 L2 的原因），但「就位」指的是**实现存在**，不是**约束存在**。判断它们何时成真的办法是同一个——看公开材料里有没有出现可核验的约束（强制经过的节点、进入门禁的字段、可举证的记录），而不是看功能页上有没有多一个带「Marketplace」或「Compliance」的名字。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 资产分发长期是「对内强制、对外自愿」：企业内市场管得住，公域市场管不住 | 企业内部市场普遍接在统一网关与数据权限上；跨平台流通仍靠人工搬运 | 出现让资产「不穿过某平台就调不到模型或数据」的公域强制条件 |
| 资产评估的公共口径先出现在**平台侧**（同一平台内可比），不出现跨平台排名 | 平台文档给出评估集构造与通过线的规范；跨平台对比仍无公开榜单 | 出现被多方采纳的跨平台资产评测集与公开排名 |
| 资产数量会继续增长，而「去重后的有效资产数」成为主要健康指标 | 平台侧出现「活跃资产 / 僵尸资产」这类内建统计与自动退役 | 公开材料仍只报登记总数，且没有按调用情况分类的统计 |
| 模型快照绑定会成为资产登记的必填项（资产有保质期成为共识） | 资产登记 schema 里出现「依赖哪个模型快照」字段，且弃用时要触发资产复核 | 三年后主流登记表里仍只有资产自身版本，没有模型依赖字段 |

四条预测都能靠**公开文档与登记 schema**证实或证伪，不需要内部数据：

- 第 1 条看内外分发的强制力差异，一到两年见分晓。
- 第 2 条看评估规范出现在平台文档还是行业标准里，两到三年。
- 第 3 条看平台统计口径是「总数」还是「活跃数」，两到三年。
- 第 4 条看登记 schema 的必填字段，三到五年。

最值得先盯的是第 4 条：它是本节唯一一条**不依赖任何新模型发布**就能观察到的信号——模型依赖是否落库由登记 schema 决定，不由模型能力决定；它也是把资产从「登记项」变成「有保质期的制品」的那一步（主文件 [§1.5](03-asset-management.md) 已把强依赖模型列为 AI 资产比传统软件资产更难治理的原因之一）。

第 2 条的影响面最大：一旦评估口径出现在平台侧并趋同，本节判定侧那一行的评级就可能改变（判据 ③ 会第一次有材料可用）。反过来说，如果你在三年内都没看到评估集构造与通过线的公开规范，那么「资产评估已经成熟」这个判断就始终缺少公开依据，架构上应当继续按「可以有、不能依赖」来对待。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 消费方全是研发，资产是纯文本 Prompt | 留在 Git：版本、评审、权限、回滚四件事已由 Git 提供（§3.2.1） | 消费方是否出现非研发角色 | 不要先建平台——它先把 Git 已有的四件事重建一遍，还多出长期运营成本 |
| 消费方含运营 / 业务，改 Prompt 是周级或更快 | 上带「不可变版本 + 别名 + 离线评估」的平台形态，并把 alias 移动做成需审批的动作 | 平台文档是否给出评估集的构造规范 | 不要让别名移动不留痕——回滚没有锚点 |
| 需要回答「谁在用、算谁的钱」 | 先建计量与 entitlement（§7.3.2），再谈门户与推荐 | 调用日志与登记表的资产集合是否一致 | 不要在调用不穿过节点时承诺成本归属——那时三张表都没有落库位置 |
| 资产数已过人工盘点能力（【经验】千级以内勉强人工，万级必须靠指标） | 排序输入加质量维度（新鲜度 / 调用量 / 评估分 / 复用度）并建退役通道（§7.3.4） | 是否出现「活跃 / 僵尸」这类内建统计 | 不要靠继续加登记解决——登记数上涨而检索质量下降（§3.5 无退役） |
| 想采购或对接外部资产市场 | 先定义验收口径：准入规则、计量归属、退役通知能不能定向 | 是否出现第三方（非厂商）生产案例 | 不要用外部市场承担内部分发——公域准入对内部没有强制力，数据边界也无法靠平台条款转移 |
| 想做合规审计自动化 | 先把数据分类、授权主体、存储地做成资产登记的必填项 | 审计结论能否逐条回溯到落库记录 | 不要让模型给出审计结论——举证责任在人，不在模型 |

「明确不要做」那一列的共用逻辑只有一句：**本节真正变了的是「资产有没有一个必经节点」，没变的是「谁为资产的长期质量负责」**。所以预算该投在计量归属的可核验、版本与别名可回滚、退役可定向通知三件确定性工程上；在这三件之前，任何「资产联邦」「智能推荐」的规划都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先定登记 schema 与必填项**：Owner 具体到人、依赖的模型快照、数据分类、评估集指针（§3.7 自检清单第 1–5 条与第 9 条）。这一步不需要新采购。
2. **再把计量与准入打通**：让调用穿过一个节点，准入、归属、退役通知才有落点（§7.3.2）。
3. **然后给排序加质量维度**：质量分需要调用埋点与评估记录，所以它必须排在第二步之后。
4. **最后才谈市场与联邦**：它们会改变所有权与授权边界，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新的模型能力——登记必填项、计量归属、排序维度、退役通道，全是工程与流程。这也解释了本节为什么没有 L1：真正已经就位的那部分（版本、登记、平台内分发）不需要被宣传，而需要被宣传的那部分（自动生成、智能推荐、自动合规审计、市场标准化），还没有成熟到能被建设方之外的第三方核验。两者之间的落差，就是本节五行评级全部停在 L2 与 L3 的原因。

### 5.8 小结

> 本节小结：AI 资产管理里 AI 真正改变的只有一条机制——**把分发从「复制文件」换成「调用穿过一个必经节点」**，因此准入、授权、计量、退役通知第一次有了落库的位置，资产也第一次可以按版本与调用方被管理；它没有改变的是**「谁为资产的长期质量负责」**：资产数量会自己增长，而版本、评估、退役都不会自己发生。本节没有 L1 方向：能排进路线图的是登记必填项、计量归属、退役通道这三件工程，而不是「资产联邦」或「智能推荐」。
>
> 💡 **思考锚点**：数一下你手上纳管的资产落在哪一档——千级以内勉强还能人工盘点，到了万级就必须给排序加质量维度（新鲜度 / 调用量 / 评估分 / 复用度）并建退役通道，否则只是「登记数上涨、检索质量下降」。再查一件事：如果你的平台允许移动别名，这次移动留痕了吗？没有锚点，回滚就无从谈起。
>
