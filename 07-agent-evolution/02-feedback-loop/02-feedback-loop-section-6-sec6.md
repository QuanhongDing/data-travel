### 2.1 DeepSeek"**GRPO：用"组内相对优势"替代 critic 网络 1+ 年**"（2024-2025）

**背景（Why）**

DeepSeek 2024 年面临**推理能力强化学习的成本瓶颈**：
- **PPO 需要 critic 网络**——**critic 与策略模型同量级，等于显存与算力投入翻倍**
- **推理任务的奖励稀疏**——**答案对错只在末尾给一次信号，中间过程的奖励极难评估，critic 训练尤其困难**
- **训练稳定性差**——**策略与 critic 互相追跑，超参敏感、复现成本高**
- **长链推理对显存要求高**——**长思维链本身已占用大量显存，再放一个 critic 直接放不下**

**触发点（What）**

2024 年 DeepSeek 推进 **GRPO（组相对策略优化）**（[DeepSeek 公开材料 2024-2025]），目标：
- **去掉 critic 网络**——显存与算力占用显著下降
- **适配稀疏奖励**——用同一问题的多个采样结果互相比对
- **长链推理训练可行**

**详细做法（How）**

GRPO 的**5 大核心组件**：

1. **组内相对优势：用"同一问题的多次采样"替代"学出来的价值函数"（核心创新）**
   - 关键设计：**对同一个问题采样一组回答，用组内奖励的均值与离散程度计算每个回答的相对优势**，不再训练独立的 critic 网络估计基线
   - 关键能力：**基线由"同组样本"直接给出，不需要另一个网络去学**——这同时解决了显存占用与稀疏奖励下的基线估计难题
   - 关键数字：**显存与算力占用显著下降、长链推理训练可行**
   - 关键示意：
     ```text
     PPO vs GRPO：基线从哪里来，决定了资源占用

       PPO（需要 critic）
         问题 q ─▶ 采样回答 ─▶ 奖励 r
                              │
              critic 网络 v(s) 预测基线 ──▶ 优势 = r − v(s)
         成本：critic 与策略同量级 → 显存/算力 ≈ 翻倍
         难点：推理任务奖励稀疏，critic 很难学准

       GRPO（组内相对）
         问题 q ─▶ 采样 G 个回答 ─▶ 各自奖励 r₁…r_G
                              │
              基线 = mean(r₁…r_G)   （不需要任何网络）
              优势_i = (r_i − mean) / std
         成本：无 critic → 省下与策略同量级的显存
         收益：稀疏奖励下更稳，因为基线来自同题样本的直接比较
     ────────────────────────────────────────────────
     关键：把"估计基线"从"训练一个网络"换成"多采样几次"
           用采样成本置换训练成本，在长链推理场景下这笔账更划算
     ```

2. **多采样与显存权衡（核心）**
   - 关键设计：**组内采样数（G）是可调参数**，与去 critic 省下的显存做权衡
   - 关键能力：**资源分配从"固定双份模型"变成"可控的采样次数"**，可按硬件条件与任务难度调节
   - 关键数字：**采样数可调、显存占用可控**

3. **稀疏奖励下的稳定性（核心）**
   - 关键设计：**优势基于组内归一化**，同一问题内的相对好坏比绝对分数更稳定
   - 关键能力：**对奖励尺度不敏感**——不必精调奖励的数值范围就能训练
   - 关键数字：**对奖励尺度不敏感、训练更稳**

4. **无需价值网络的推理链训练（核心）**
   - 关键设计：**奖励只施加在最终答案上**（对错 / 可验证结果），中间推理步骤不需要逐步标注
   - 关键能力：**可利用"结果可自动验证"的任务（数学、代码）大规模构造训练信号**，不依赖人工逐步标注
   - 关键数字：**依赖可验证奖励，不依赖过程标注**

5. **可复现与超参简化（核心创新）**
   - 关键设计：**去掉 critic 后需要协调的超参减少**（不再有策略与 critic 的学习率配比问题）
   - 关键能力：**训练配置更容易复现与迁移到新任务**——这是方法能否被广泛采用的实际因素
   - 关键数字：**超参数量减少、复现成本下降**

**GRPO 关键数字**（[DeepSeek 公开材料 2024-2025]）：

| 指标 | 改前（PPO 类方案） | 改后 | 提升 |
| --- | --- | --- | --- |
| **基线估计方式** | 训练 critic 网络 | 组内采样相对比较 | **去掉一个网络** |
| **显存占用** | 策略 + critic 两份 | 仅策略 + 采样 | **显著下降** |
| **算力投入** | 双模型训练 | 单模型 + 多采样 | **成本下降** |
| **稀疏奖励适配** | critic 难学准 | 组内归一化，对尺度不敏感 | **更稳定** |
| **长期推理链训练** | 显存常放不下 | 可行 | **∞** |
| **奖励来源** | 常需过程标注 | 可用可验证的最终结果 | **可大规模构造** |
| **需协调的超参** | 策略 / critic 学习率配比等 | 明显减少 | **复现成本下降** |
| **超参敏感度** | 高 | 低 | **更易迁移** |

**具体数字（How much）**

- 团队规模：DeepSeek 研究与工程团队数百人
- 关键数字：**无 critic**；**长链推理可训练**；**可用可验证奖励**；**复现成本下降**
- 业务影响：为推理型模型提供了一条资源占用更低、可用自动可验证奖励的强化学习路径，并被广泛复现

**失败教训**

- 早期「**照搬 PPO 做推理任务**」——critic 与长思维链同时占显存，训练常跑不起来，倒逼**「去掉 critic，用组内相对优势估计基线」**
- 「**在稀疏奖励下强行训练 critic**」——价值函数学不准导致训练不稳，倒逼**「基线改由同题多采样直接给出」**
- 「**依赖人工标注推理过程**」——过程标注成本高且难以规模化，倒逼**「用最终结果可自动验证的奖励」**
- 「**沿用双模型超参配比**」——调参空间大且难复现，倒逼**「简化超参，提升可复现性」**

### 2.2 OpenAI"**RLHF：把"人类偏好"做成可规模化的三段式管线 5+ 年**"（2019-2024）

**背景（Why）**

OpenAI 2019 年面临**"模型能力在涨、但输出不可用"**：
- **模型只是"续写"**——**擅长补全，但不擅长"按要求回答问题"**
- **对齐目标无法用规则写清**——**"什么是有帮助的回答"这类判断无法用硬编码规则表达**
- **纯人工标注不可持续**——**标注成本随规模线性上涨，且标注质量不一致**
- **反馈没形成闭环**——**模型上线后用户的点赞、重生成、举报等信号没被系统利用**

**触发点（What）**

2019 年起 OpenAI 推进 **RLHF（人类反馈强化学习）三段式管线**（[OpenAI 公开材料 2019-2024]），目标：
- **把人类偏好变成训练信号**——用比较而非绝对打分
- **可规模化**——标注与训练解耦
- **形成持续闭环**——线上反馈能回流

**详细做法（How）**

RLHF 管线的**5 大核心组件**：

1. **"比较优于打分"的偏好采集（核心创新）**
   - 关键设计：**标注者面对同一输入的两个候选输出，判断哪个更好**，而不是给每个输出一个绝对分数
   - 关键能力：**标注一致性与可靠性显著提升**——人对相对比较的判断远比绝对打分稳定，这让偏好数据真正可用
   - 关键数字：**偏好数据可用、标注一致性提升**
   - 关键示意：
     ```text
     RLHF 三段式：把"人的偏好"变成可训练、可规模化的信号

       ① 监督微调（SFT）
          人类示范回答 ─▶ 微调基座模型
          → 得到一个"会按指令回答"的起点模型

       ② 奖励建模（RM）
          对同一 prompt 采样多个输出 ─▶ 标注者两两比较 ─▶ 训练奖励模型
          → 得到"能预测人类偏好"的打分器
          → 关键：比较优于打分；标注与训练在此解耦，可并行扩量

       ③ 强化学习（RL）
          策略模型生成 ─▶ 奖励模型打分 ─▶ 更新策略
          → 用 RM 作为可规模化的"代理人类"
          → 再加 KL 约束：不许偏离 SFT 模型太远（防跑偏、防刷分）
     ────────────────────────────────────────────────
     关键：把"无法规模化的直接人工反馈"，转化为"可规模化的奖励模型"
           于是"提升质量"从"多加标注"变成"多跑训练"
     ```

2. **奖励模型作为"代理人类"（核心）**
   - 关键设计：**奖励模型替代人类在线打分**，使强化学习这一步可以大规模运行
   - 关键能力：**质量迭代的边际成本从"人力标注"转为"算力"**——这是质量能持续爬升的根本原因
   - 关键数字：**打分可规模化**

3. **KL 约束防止"刷分"（核心）**
   - 关键设计：**在策略优化目标中加入与起点模型（SFT 模型）的 KL 惩罚**，限制分布偏离
   - 关键能力：**避免策略"钻奖励模型漏洞"**——奖励模型只是近似，无约束优化会跑向"高分但不可读"的输出
   - 关键数字：**跑偏被约束、输出保持可读**

4. **AI 反馈补充人工（核心）**
   - 关键设计：**用可验证任务（代码、数学）的自动判定，或有明确规范约束的场景，由模型 / 规则给出反馈**，与人工反馈混合
   - 关键能力：**反馈量不再完全受人力限制**，同时人工聚焦在"自动难判定"的偏好上
   - 关键数字：**反馈来源多元化**

5. **线上反馈闭环（核心创新）**
   - 关键设计：**上线后的点赞、重生成、举报等行为被收集并分类**，其中一部分流转为偏好数据
   - 关键能力：**反馈不只来自标注团队，也来自真实使用**——反馈分布与实际使用场景一致，避免"标注偏好"与"真实偏好"脱节
   - 关键数字：**线上信号进入反馈循环**

**RLHF 管线关键数字**（[OpenAI 公开材料 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **对齐信号来源** | 规则 / 提示词约束 | 人类偏好数据 | **可覆盖难写规则的目标** |
| **反馈采集方式** | 绝对打分（一致性差） | 两两比较 | **标注一致性提升** |
| **质量迭代的边际成本** | 人力标注（线性） | 奖励模型打分（算力） | **可规模化** |
| **打分可扩展性** | 受标注人力限制 | 奖励模型替代在线打分 | **不受人力限制** |
| **跑偏控制** | 无 | KL 约束限制分布偏离 | **输出可读稳定** |
| **反馈来源** | 仅人工 | 人工 + 自动可验证 + 线上信号 | **多元化** |
| **反馈与真实场景一致性** | 标注偏好与使用脱节 | 线上信号回流 | **一致** |
| **迭代周期** | 慢（标注瓶颈） | 快（训练瓶颈） | **显著缩短** |

**具体数字（How much）**

- 团队规模：OpenAI 团队 1000+ 人，含专门的对齐研究与数据标注运营
- 关键数字：**三段式管线**；**比较优于打分**；**奖励模型规模化**；**线上反馈回流**
- 业务影响：为对话模型提供了可规模化的对齐路径，并成为行业的通用范式

**失败教训**

- 早期「**只做监督微调**」——模型能模仿示范但不擅长权衡偏好，倒逼**「引入偏好比较并训练奖励模型」**
- 「**用绝对打分采集偏好**」——标注一致性差、噪声大，倒逼**「改为两两比较」**
- 「**无约束地最大化奖励模型分数**」——策略学会钻漏洞，输出变得机械且难读，倒逼**「加入 KL 约束限制偏离起点模型」**
- 「**只看标注团队的偏好**」——与真实用户偏好脱节，倒逼**「把线上采纳 / 重生成 / 举报等信号回流进反馈循环」**

### 2.3 字节"**豆包：多业务统一偏好闭环与"AI 反馈"扩量 4+ 年**"（2021-2024）

**背景（Why）**

字节 2021 年面临**多业务各自做对齐的重复与割裂**：
- **4 业务（抖音 / TikTok / 西瓜 / 今日头条）各有 AI 场景**——**对齐标准、标注口径、评估集各建一套**
- **人工反馈成本高**——**反馈量跟不上模型迭代速度**
- **多模态对齐缺失**——**图像、视频相关的偏好判断缺乏统一标准**
- **反馈无法跨业务复用**——**同类问题在一个业务被标注过，另一个业务又标一遍**

**触发点（What）**

2021 年字节启动**豆包统一偏好闭环（含 AI 反馈扩量）**（[字节公开材料 2021-2024]），目标：
- **统一偏好标准与标注口径**——跨业务可复用
- **AI 反馈扩量**——用模型替代部分人工判断
- **多模态对齐**

**详细做法（How）**

字节豆包反馈闭环的**5 大核心组件**：

1. **统一偏好标准与评估集（核心创新）**
   - 关键设计：**把"什么算好回答"写成跨业务通用的判定准则**，并配套统一评估集；各业务在此之上叠加自己的场景规则
   - 关键能力：**反馈数据跨业务可复用**——同一批偏好数据能同时服务多个业务的模型
   - 关键数字：**4 业务统一标准、反馈数据可复用**
   - 关键示意：
     ```text
     统一标准 + 场景叠加（避免 4 套标准各标各的）
       通用判定准则（跨业务共用）
         · 事实性 / 有害性 / 指令遵循 / 表述清晰度 …
         · 配套统一评估集（回归基线）
                 │
       业务场景叠加（各业务自己的补充规则）
         抖音：内容创作辅助相关偏好
         西瓜：长文本摘要与改写偏好
         头条：信息类问答的事实性权重更高
     ────────────────────────────────────────────────
     反馈数据流向：
       人工偏好 ─┐
                 ├─▶ 统一偏好库（跨业务可复用）
       AI 反馈  ─┘         │
                           ▼
                  奖励建模 / 策略优化 ──▶ 4 业务模型共同受益
     -- 关键：统一的是"判定准则与数据格式"，差异化的是"场景权重"
     --       若完全统一会丢场景特性；完全分散则数据互不复用
     ```

2. **AI 反馈扩量（核心）**
   - 关键设计：**由模型按统一准则对输出做判断**，人工聚焦在"模型判不准"的样本上抽检与修正
   - 关键能力：**反馈量不再受人工规模线性限制**，人工从"全量标注"转为"抽检 + 疑难裁决"
   - 关键数字：**反馈吞吐显著提升、人工聚焦疑难样本**

3. **多模态偏好统一（核心）**
   - 关键设计：**图像 / 视频相关偏好（相关性、合规性、画面质量）纳入同一套判定框架**
   - 关键能力：**多模态场景不必另建一套标注与评估体系**
   - 关键数字：**多模态统一框架**

4. **反馈数据质量校验（核心）**
   - 关键设计：**对反馈数据本身做一致性检查**（同一批样本重复标注的一致率、AI 反馈与人工反馈的偏离度）
   - 关键能力：**发现"判定准则本身有歧义"或"AI 反馈系统性偏移"**——否则错误反馈会把训练带向错误方向
   - 关键数字：**反馈质量可监控**

5. **与训练流程的解耦（核心创新）**
   - 关键设计：**反馈生产与模型训练分离**，反馈以数据形式沉淀，训练侧按需取用
   - 关键能力：**反馈资产可跨模型版本、跨业务复用**，而不是"标完就训、训完就丢"
   - 关键数字：**反馈资产可积累**

**字节豆包反馈闭环关键数字**（[字节公开材料 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **偏好标准** | 4 业务各一套 | 统一准则 + 场景叠加 | **数据可复用** |
| **反馈来源** | 以人工为主 | 人工 + AI 反馈 | **吞吐显著提升** |
| **人工角色** | 全量标注 | 抽检 + 疑难裁决 | **人力聚焦高价值判断** |
| **反馈数据复用** | 各业务各自标注 | 统一偏好库跨业务复用 | **重复标注下降** |
| **模态覆盖** | 文本为主 | 文本 / 图像 / 视频统一框架 | **多模态** |
| **反馈质量监控** | 无 | 一致率 + 偏离度 | **可发现系统性偏移** |
| **反馈资产形态** | 标完即用于训练 | 沉淀为可复用数据资产 | **可积累** |
| **业务覆盖** | 各自为战 | 4 业务 + 6 亿+ 用户场景 | **∞** |

**具体数字（How much）**

- 团队规模：字节豆包 / 对齐团队 200+ 人
- 关键数字：**4 业务统一准则**；**AI 反馈扩量**；**多模态统一框架**；**反馈资产可复用**
- 业务影响：支撑抖音 / TikTok / 西瓜 / 今日头条多场景模型的统一对齐与持续迭代

**失败教训**

- 早期「**各业务各自定义好回答**」——标准不一导致反馈数据无法复用、重复标注，倒逼**「统一准则 + 场景权重叠加」**
- 「**全部依赖人工反馈**」——反馈量跟不上模型迭代，倒逼**「AI 反馈扩量，人工转向抽检与疑难裁决」**
- 「**反馈数据不做质量校验**」——AI 反馈的系统性偏移把训练带偏且难以察觉，倒逼**「一致率与偏离度监控」**
- 「**反馈标完即训、训完即弃**」——同一批判断被反复重做，倒逼**「反馈沉淀为可复用数据资产，与训练解耦」**

### 2.4 Cursor"**Composer：把 IDE 里的"采纳与回退"变成在线反馈信号 1+ 年**"（2023-2024）

**背景（Why）**

Cursor 2023 年面临**"代码助手的效果反馈最密集也最被浪费"**：
- **反馈天然存在**——**开发者接受或拒绝一次补全、保留或撤销一段修改，本身就是最真实的判断**
- **但通常没被系统利用**——**这些信号散落在编辑器行为里，没有进入模型改进循环**
- **离线偏好与真实体验有差距**——**在标注环境里"看起来更好"的代码，在真实工程里可能不合规范、不符合项目习惯**
- **多语言多框架**——**不同语言、框架、代码库风格的偏好差异极大，难以统一标注**

**触发点（What）**

2023 年起 Cursor 推进**基于编辑器内采纳行为的在线反馈闭环**（[Cursor 公开材料 2023-2024]），目标：
- **把采纳 / 回退作为反馈信号**——来自真实使用而非标注环境
- **按项目与场景区分偏好**——而非一刀切
- **闭环速度加快**——从"收集—标注—训练"压缩到"收集—训练"

**详细做法（How）**

Cursor 反馈闭环的**5 大核心组件**：

1. **"采纳 / 拒绝 / 撤销"作为一级反馈信号（核心创新）**
   - 关键设计：**编辑器中的接受、拒绝、部分编辑、撤销等行为被记录为反馈**；这些信号反映的是"在真实工程上下文里是否有用"
   - 关键能力：**反馈来自真实工作流，规模与真实性都远高于人工标注**——这消除了"标注偏好与真实偏好脱节"的问题
   - 关键数字：**反馈来自真实使用、规模远超标注**
   - 关键示意：
     ```text
     编辑器行为 → 反馈信号 → 训练闭环（无需额外标注环节）

       IDE 内行为                     解释为的反馈
       ─────────────────────────────  ──────────────────────────────
       接受补全                       正反馈（在当前上下文中可用）
       按下继续 / 编辑后接受           部分正反馈（方向对，细节需改）
       撤销刚接受的补全                强负反馈（当时看起来对，实际错）
       忽略建议继续手写                弱负反馈（未采纳）
       在 diff 中只保留一部分           细粒度反馈（哪几行有价值）
     ────────────────────────────────────────────────
     关键点：撤销是最有价值的信号之一
       接受是"当时觉得对"，撤销是"用起来发现不对"
       后者反映的是真实可用性，标注环境里很难复现
     -- 关键：把"已经被记录但被浪费的行为数据"接进训练闭环
     ```

2. **按项目上下文区分偏好（核心）**
   - 关键设计：**反馈与触发时的上下文一起记录**（语言、框架、项目风格），使训练能学到条件化的偏好
   - 关键能力：**"这个项目习惯的写法"可以被学到**，而不是把各项目偏好平均掉
   - 关键数字：**上下文条件化、项目风格可学**

3. **长会话与多轮编辑的反馈（核心）**
   - 关键设计：**不只记录单次补全，也记录"多轮修改后最终保留了什么"**
   - 关键能力：**能区分"一次生成就好"与"来回改了几轮才好"**——后者说明模型的初稿质量仍有差距
   - 关键数字：**多轮编辑可评估**

4. **反馈的偏差校正（核心）**
   - 关键设计：**识别系统性偏差**——如某类项目大量使用某框架导致反馈分布倾斜；对低覆盖场景做重加权或补采
   - 关键能力：**避免模型退化为"只服务主流项目"**
   - 关键数字：**分布偏差可发现**

5. **闭环速度优先（核心创新）**
   - 关键设计：**反馈收集、清洗、训练、上线链路尽量短**，以"周"而非"季"为单位迭代
   - 关键能力：**反馈的价值随时间衰减**——用户与生态变化很快，收集半年后才用上的反馈，可能已不对应当下需求
   - 关键数字：**迭代周期以周计**

**Cursor 反馈闭环关键数字**（[Cursor 公开材料 2023-2024]）：

| 指标 | 改前（纯离线偏好） | 改后 | 提升 |
| --- | --- | --- | --- |
| **反馈来源** | 人工标注环境 | IDE 内真实行为 | **真实性与规模兼得** |
| **反馈规模** | 受标注人力限制 | 随使用量增长 | **不受人力限制** |
| **最有价值的信号** | 未采集 | 撤销 / 部分保留 | **补捉真实可用性** |
| **偏好条件化** | 全局一刀切 | 按语言 / 框架 / 项目风格 | **可学到项目习惯** |
| **多轮编辑评估** | 只看单次生成 | 记录最终保留结果 | **区分初稿质量** |
| **分布偏差** | 不易察觉 | 可识别并重加权 | **避免只服务主流场景** |
| **迭代周期** | 季级 | 周级 | **显著缩短** |
| **标注偏好脱节** | 常见 | 反馈即真实使用 | **基本消除** |

**具体数字（How much）**

- 团队规模：Cursor 团队数十至上百人
- 关键数字：**采纳 / 撤销作为反馈信号**；**上下文条件化**；**周级迭代**；**偏差可校正**
- 业务影响：把编辑器里本就存在的使用行为转化为持续的模型改进信号，缩短"发现不好用"到"改好"的距离

**失败教训**

- 早期「**只用离线偏好数据**」——标注环境里"更好"的代码在真实工程里常不合项目习惯，倒逼**「把 IDE 内采纳 / 撤销行为接入反馈」**
- 「**只记录接受与拒绝**」——漏掉了信息量最大的"接受后又撤销"，倒逼**「把撤销与部分保留作为一等反馈信号」**
- 「**把不同项目的偏好混在一起学**」——各项目风格被平均掉，倒逼**「反馈与上下文同记录，学习条件化偏好」**
- 「**反馈收集周期过长**」——反馈到达训练时场景已变，倒逼**「压缩闭环链路，以周为单位迭代」**

### 2.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**两两比较采集偏好 + 一个奖励模型 + 小规模 RL**」（**最简单**）——**1 个场景、单模态**
- 产出：**判定准则文档 + 两两比较标注流程 + 奖励模型 + KL 约束配置**
- 团队：**3-5 人（含标注运营）**
- 验证标准：**标注一致率达标**、**奖励模型在留出集上与人类偏好排序一致**、**策略输出不因优化而变得不可读**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 场景 / 多模态**」
- 引入「**线上行为信号回流**」（采纳 / 撤销 / 举报等）——反馈分布与真实使用一致
- 引入「**反馈数据质量校验**」（重复标注一致率、自动反馈与人工反馈偏离度）
- 团队：10-20 人
- 验证标准：**线上信号进入反馈循环**、**反馈质量可监控**、**自动反馈无明显系统性偏移**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 场景 / 多业务统一**」
- 引入「**统一判定准则 + 场景权重叠加**」——反馈数据跨业务复用
- 引入「**反馈资产与训练解耦**」——反馈沉淀为可复用数据资产
- 团队：20-50 人
- 验证标准：**跨业务反馈可复用**、**重复标注显著下降**、**反馈资产跨模型版本可用**

**100 → 1000 阶段：12-24 个月**

- 引入「**反馈条件化（按上下文 / 项目 / 用户群区分偏好）**」+「**分布偏差识别与重加权**」
- 引入「**闭环速度优先：周级迭代链路**」
- 团队：50-100 人
- 验证标准：**条件化偏好可被学到**、**低覆盖场景不退化为服务主流**、**闭环周期 ≤ 2 周**

### 2.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**反馈采集方式**」 | 绝对打分（一致性差） | 两两比较 | **标注一致性提升** |
| 「**训练显存占用**」 | 策略 + critic 两份 | 仅策略 + 采样 | **显著下降** |
| 「**质量迭代的边际成本**」 | 人力标注（线性） | 奖励模型 / 自动反馈 | **可规模化** |
| 「**反馈规模来源**」 | 受标注人力限制 | 随使用量增长 | **不受人力限制** |
| 「**反馈与真实使用的一致性**」 | 标注偏好常脱节 | 线上行为回流 | **基本消除脱节** |
| 「**多业务 / 多场景复用**」 | 各自标注 | 统一准则 + 场景叠加 | **重复标注下降** |
| 「**反馈资产形态**」 | 标完即弃 | 沉淀为可复用资产 | **可积累** |
| 「**闭环迭代周期**」 | 季级 | 周级 | **-80%+** |
| 「**分布偏差**」 | 不易察觉 | 可识别并重加权 | **避免退化为服务主流** |
| 「**输出稳定性**」 | 易被奖励漏洞带偏 | KL 约束 + 校验 | **可读稳定** |

**关键投资回报**：
- **直接节省**：「**边际成本从人力标注转为算力 + AI 反馈扩量**」——**反馈循环的成本瓶颈在"获取反馈"这一环**；把它从"人工逐条标注"改为"奖励模型 + 自动可验证反馈 + 线上行为信号"，质量迭代才可能持续而不是被标注预算卡住
- **业务价值**：「**反馈来自真实使用 + 闭环周级 + 多业务复用**」——**对齐的价值在于"模型变好用"这件事能被持续、快速、低成本地推动**；来自真实工作流的反馈（采纳 / 撤销）比标注环境里的判断更接近可用性本身
- **AI 时代关键**：「**可验证奖励 + 条件化偏好 + 反馈资产化**」——**这是 Agent 与模型能持续进化的机制基础**：可验证奖励让训练信号可大规模构造；条件化偏好避免把不同场景的需求平均掉；反馈资产化则让"改进"成为可积累的组织能力，而不是每次从零开始

---

> **本节小结**：
> - 4 个真实案例（DeepSeek / OpenAI / 字节 / Cursor）印证：**反馈循环不是「**收一批标注训一版模型**」，是「**比较优于打分 + 去掉昂贵基线 + 自动与线上反馈扩量 + 统一准则与条件化偏好 + 闭环速度优先**」**5 件套**。
> - 关键时间线：DeepSeek 1+ 年 / OpenAI 5+ 年 / 字节 4+ 年 / Cursor 1+ 年 —— **反馈循环是持续工程**，且**真正的瓶颈始终是"反馈的获取成本与真实性"，而不是训练方法本身**。
> - 选型第一原则：「**两两比较 + 一个奖励模型 + KL 约束**」（**最简单**）——**1 个场景** → 「**线上信号回流 + 反馈质量校验**」（**必须**）→ 「**统一准则 + 场景叠加 + 反馈资产化**」（**生产**）→ 「**可验证奖励 + 条件化偏好 + 周级闭环**」（**AI 时代**）。
> - 99% 的失败来自「**绝对打分 + 只做 SFT + 无约束刷分 + 只用离线偏好**」——必须有 **两两比较 + 偏好优化 + KL 约束 + 线上信号**。
> - 真正的 ROI 来自「**边际成本转为算力 + 反馈来自真实使用 + 周级闭环 + 跨业务复用**」——是**模型与 Agent 能否持续变好而不是停在某一版的分水岭**。
