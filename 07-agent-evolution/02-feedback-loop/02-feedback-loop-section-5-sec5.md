## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是**没有时间维度**。同一张清单里，「算法定义已经固定、有版本化发布的开源实现、数据格式基本统一」的条目，和「只有一篇论文提过、产品里还没有对应开关」的条目被并列成七行方向。读者据此排路线图时，两者的失败方式完全不同：前者最多是接口改名，后者可能根本不存在。

第二个问题是「反馈」这个词在同一份清单里横跨三层。它可以是**测量方法**（你怎么知道新版更好：A/B、Interleaving、Eval），**训练算法**（一批反馈怎么变成权重：RLHF / DPO / GRPO / KTO / IPO / Online DPO），或**运行时机制**（模型在推理时拿反馈做什么：自评、自修、检索纠错）。三层可规划性差一个量级：测量方法写在实验平台的发布说明与统计教材里；训练算法写在论文与开源实现里；运行时机制既没有接口契约也没有评测口径，只能看产品文档当前写了什么。

第三个问题是没有反方观点。清单里不会出现「这一条今天不值得投」，于是「跨 Agent 反馈共享（联邦学习）」这类还停在研究阶段的条目，会和「用偏好数据做一次离线微调」这类早就有成熟工程做法的条目排在同一个列表里。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（或版本化发布的规范与文档）；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期（数据格式与语义不随版本翻烧饼）。
- **L2 可试点**：①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

**判据 ② 在本主题尤其难过**，原因值得先说清：反馈闭环的公开材料几乎全部是**建设方自述**。产品文档由厂商写，落地案例由建设方发布，开源项目的能力说明由项目自己维护，「第三方（非厂商）公开生产案例」要求的是一个既不卖这套东西、也不靠它立论的团队，公开写出自己的用法与失败。本节的口径是：**② 只有「满足」与「降为 L2」两种命运**——不改成「有公开生产记录」，不靠「本节只评估离线训练」缩小适用范围来绕过，也不存在「准 L1」「L1 的边界案例」这类说法。

另有一条评级规则，全节通用：**按机制分族，一族一行；族的级别取族内最弱子项**。这不是放宽判据，而是读者做规划时的实际含义——族里只要有一个子项不能依赖，这一族的架构就不能整体依赖。族内每个子方向的名字都列在「演进方向」列里，5.2 逐族拆解，两处级别与判据必须一致。

| 演进方向（族内子方向） | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **测量与评估**：A/B 测试 / Interleaving / Eval-Driven Development / LLM-as-Judge 评估 | L2 | ① 满足：实验与评估平台有版本化发布与公开文档；② 不满足：公开案例或是平台供应商的客户故事、或是自建方的自述，两者都不构成第三方；③ 大体满足：分流与显著性检验的语义早已固定，评估口径各家自定 | 测量先于训练：把评估集与分流标识建起来，它们决定后面所有算法能不能被验证 |
| **把反馈变成参数**：RLHF / DPO / KTO / IPO / GRPO / Online DPO / 在线学习（FTRL）/ Contextual Bandit | L2 | ① 满足：算法有公开论文，实现有版本化发布的开源库；② 不满足：落地描述皆建设方自述；③ 大体满足：偏好对的形状 `(prompt, chosen, rejected)` 稳定，但超参与数据配比口径各家不一 | 先在可自动判分的任务上试；主观任务上先解决反馈去偏，再谈训练 |
| **自反馈与自我改进**：Constitutional AI / Self-Play / Self-Refine / Agent Self-Critique | L2 | ① 满足：方法论文与框架内的实现说明可核验；② 不满足；③ 不满足：原则内容、自评提示、迭代轮数由实现方自定义，无跨实现契约 | 只在能自动判分的任务上开自反馈；主观任务上把它当草稿生成器，不当验收器 |
| **反馈的消费与管理**：Feedback-Driven RAG / GraphRAG 反馈 / 反馈驱动的记忆 / 反馈驱动的资产 / 多模态反馈 / 反馈数据治理 / 跨 Agent 反馈共享（联邦） | L3 | ① 不满足：族内七个子项里只有检索回填有正式文档级的公开实现，其余六项只有实现说明、论文、演示、路线图或法规义务；② 不满足；③ 不满足：反馈如何回填到检索、评分如何换算成资产价值，均无契约 | 只做「反馈可查、可回溯到原始事件」这一层；不要在架构里假设反馈能自动定价或跨组织流通 |

**本节没有一行达到 L1。** 四行里最高的三行都卡在同一条上：拿不出第三方（非厂商）的生产案例。三者的差别在 ③——**测量与评估**的 ③ 最干净（分流、假设检验、显著性这些语义几十年没变），它的缺口在「评估口径谁定」；**把反馈变成参数**的 ③ 大体满足（偏好对的形状稳定），缺口在超参与数据配比无法复算；**自反馈**的 ③ 最弱，原则与提示由实现方自定义，换一个团队就是另一套判据。真正的缺料是「谁在生产里用了、错了多少、怎么回滚」——而这一族还有一个别的主题没有的困难：**反馈闭环的效果没有公开可比的度量口径**。同一个反馈信号喂进不同算法得到更好的模型，好不好取决于评估集与指标定义，而这两样各家自定；没有公共口径，第三方就无法证明自己的用法可复制，采购方也无法判断它值不值得排进路线图。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式 release note、版本化文档或公开论文能不能找到？找不到 → L3。
2. 建设方之外的证据能不能找到？找不到 → L2。
3. 它的数据格式与语义明年会不会变？会变 → 至多 L2。

第 3 句在本主题特别容易失手：**同一个词在不同实现里指的不是同一件事**。「在线学习」在推荐语境里指更新排序或路由决策（回滚成本低），在 LLM 语境里被用来指更新模型权重（回滚成本高一个量级）；「自我改进」有的指推理时的多轮修订（不改权重），有的指用自产数据继续训练（改权重）。判定方法是查该实现的接口与数据流，看它改的是**权重、上下文，还是决策**，而不是看功能名。

三个常见误判，排路线图时最容易踩：

- **把「有反馈入口」误当成「有反馈数据」**：点赞按钮是产品功能，可编程读取的反馈事件流才是接口。两者之间差着一份数据导出协议与一套口径。
- **把「能采到反馈」误当成「反馈能直接当标签」**：线上反馈有偏——只有极端体验才会被点，且同一次点击在不同曝光位下的含义不同；不经校正的反馈进训练，等于把曝光策略的偏差固化进模型。
- **把「模型变好」误当成「闭环保通了」**：一次微调让离线指标变好，与「线上持续变好」之间隔着评估口径、分流标识与回滚路径三件工程。

这张表的用法是**反向核验**：先看某个产品在功能页上宣称的能力，再回到表里找它落在哪一行，然后按该行的判据去看它。同一件产品可能同时出现在两行上（例如既提供反馈入口又提供评估能力），此时要分别评级——**一个产品在两个方向上成熟度不同是常态，把它整体评为一个级别才是误判**。

### 5.2 演进方向逐条拆解（核心节）

四族按「反馈走到哪一步」排序：测量决定你知道什么，训练决定参数怎么变，自反馈决定模型能不能自己给自己信号，消费与管理决定反馈流到哪里、被谁管。四族的级别不同，失效模式却是同一个：**反馈一旦离开它原来的上下文，就再也回不到「这条信号是在什么条件下产生的」**。

#### 5.2.1 测量与评估：A/B 测试、Interleaving 与 Eval 驱动开发

- **旧做法与它的卡点**：靠人工抽检质量，或靠上线后看业务指标。人工抽检的样本量上不去——抽几百条看不出小改动，抽几万条没有人时；A/B 测试要跑够样本量，周期以周计，而一个版本往往同时改了多个变量，测出的差异归不到具体改动上；离线评估集由人维护，一冻结就与线上分布脱节，改版越快脱节越严重。
- **AI 改变了什么机制**：把「判断这条输出好不好」从人换成一次模型调用（LLM-as-Judge），使评估的**边际成本从人时变成 token**。变化的是成本函数，不是测量的统计原理——分流、对照、显著性这一套没变。
- **由此得到的**：因为评估的边际成本从「一个人时」降到「一次调用」，**所以**每次改动都能过一遍全量评估，而不是抽样；**又因为**评估可以放进 CI，**所以**「改动必须过评估门禁」这套 Eval-Driven Development 才在成本上成立——这是反馈闭环里少见的、收益能直接算出来的机制变化。【推算】一轮全量评估按 2,000 条用例【经验：随用例集条数变，条数越多越能覆盖长尾】、每条样本的提示与回答合计约 1,500 token【经验：随回答长度变】计：2,000 × 1,500 = 3,000,000 token ≈ 3 百万 token；同一轮若改人工评审、按每条 3 分钟计：2,000 × 3 ÷ 60 = 100 人时【经验：按每条 3 分钟估】。差别不在总量，而在**每加一次改动时的边际成本**。
- **由此付出的**：判官本身是概率模型——它给出的分数没有置信区间，换一个判官模型分数就变，而**判官模型的版本往往没有和评估结果一起被登记**，于是两次评估之间的差异说不清是产品变好了还是判官变了；它有系统性偏好（偏长回答、偏好与自己同源模型的输出）；用模型取代人之后，「谁对分数负责」这个问题没有人接——**测量层的错误不会当场上报，它会以「我们一直在优化一个测不准的指标」的形式静默存在几个月**。

三种测量形态不是替代关系，它们测的东西、贵的地方与偏的东西都不同：

| 测量形态 | 它测什么 | 贵在哪 | 主要偏置 |
| --- | --- | --- | --- |
| A/B 测试 | 真实业务指标上的差异 | 样本量与周期：指标越小越难动 | 分流口径与指标定义；同时改多个变量时归因不到具体改动 |
| Interleaving | 排序偏好（更省流量） | 实现复杂度：要能把两路结果混排 | 只适用于有列表形态的场景，对生成式输出不适用 |
| Eval 驱动（含模型判官） | 输出质量，每次改动都能跑 | 判官调用与用例集维护 | 判官的系统性偏好与版本漂移；用例集与线上分布脱节 |

- **证据与来源**：【公开】在线受控实验的方法论有系统整理（Kohavi 等《Trustworthy Online Controlled Experiments》，2020，可按书名检索核验）；【公开】模型作为评估者的偏差有公开讨论（《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》，2023）；第三方（非厂商）生产案例：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「测量与评估」行一致：① 满足、② 不满足、③ 大体满足）。本条覆盖：A/B 测试、Interleaving、Eval-Driven Development，以及作为评估实现手段的 LLM-as-Judge。

- **失效条件**：当业务指标本身无法在短周期内移动（低频、高价值、长决策链的场景）时，A/B 测试的样本量要求使周期长到不可用，此时评估集的质量成为唯一抓手——判据是「你的评估集能不能覆盖线上长尾」，而不是你有多大的流量。
- **自验方法**：把同一批输出同时交给两个判官（如两个不同版本的评估模型或模型 + 人工各 100 条【经验：随用例集规模变，规模越大越准】），看两次排序是否一致。排序一致，分数可以当趋势看；排序翻转，说明你现在测的是判官，不是产品。

#### 5.2.2 把反馈变成参数：RLHF / DPO / GRPO 与在线反馈更新

- **旧做法与它的卡点**：想改变模型行为只能改规则或重训。主观质量类的需求（答得更合口味）写不成规则；RLHF 的三段式又太贵——它需要一个与策略同量级的奖励模型或 critic，而推理任务的奖励稀疏（只有答案末尾给一次信号），critic 学不准，超参敏感（本章 §6 案例 6.1 的起点就是这条卡点）。
- **AI 改变了什么机制**：把「什么算好」从人写的规则换成了一批偏好样本上的一个损失函数。三条路线的区别可以归到一句话：**基线从哪来**。RLHF 让一个学出来的奖励模型给分；DPO 把奖励隐式表示为与参考模型的对数比，省掉奖励模型与 PPO 阶段；GRPO 用同一个问题多次采样的组内均值当基线，省掉 critic 网络。
- **由此得到的**：因为基线由同组样本直接给出，**所以**稀疏奖励下训练更稳、显存与算力占用显著下降，长链推理的训练变得可行；因为 DPO 把奖励隐式化，**所以**偏好数据一采到就能训，从「反馈」到「参数」的链路由三段压成一阶段——**这是反馈闭环第一次可以按周迭代而不是按季度迭代**。
- **由此付出的**：三层代价，逐层放大。① **数据形态反过来选算法**：只有点赞点踩的产品用不了成对偏好方法，得退到单点形式的损失（KTO 一类），而单点标签的信息量低于成对比较——你能采到什么，决定了你能用什么。② **目标是「更像被选中的那条」，不是「更正确」**：奖励被利用是结构性的，需要 KL 约束或护栏指标兜底，而护栏指标本身又要人来定。③ **在线更新把线上模型变成可被实时输入影响的系统**：一旦反馈流被污染（刷量、某个用户群分布偏移），污染会直接进权重，回滚窗口内业务不可用；而主观任务上「污染进没进模型」在离线指标上看不出来。
- **证据与来源**：【公开】RLHF 三段式（InstructGPT，2022）、直接偏好优化（DPO，2023）、组内相对优化（DeepSeek 的公开技术报告，可按题名核验；注意它的公开提出时间早于 2025 年的推理模型报告，两份报告的提交时间可各自核对）；【公开】单点偏好（KTO）与防过拟合（IPO）各有公开论文；第三方（非厂商）生产案例：无公开可核验来源（公开的落地描述几乎全是建设方自述，含本章 §6 案例）。
- **成熟度**：**L2**（与 5.1 表「把反馈变成参数」行一致：① 满足、② 不满足、③ 大体满足）。本条覆盖：RLHF、DPO、KTO、IPO、GRPO、Online DPO、在线学习（FTRL）、Contextual Bandit。

```text
选哪条路线，先问两个问题（答案决定算法，而不是反过来）
   ① 奖励能不能由一个不依赖模型的函数算出来？
        能  → 走可验证奖励（组内相对优化一类），生成与判分都免费
        不能 → 必须有人或模型判分，此时先算标注预算，再选损失函数
   ② 你采到的标签是成对的还是单点的？
        成对 → DPO 一类可直接用
        单点 → 需要单点形式的目标，信息量更低，样本需求更高
   ────────────────────────────────────────────
   两个问题都答不上来 ⇒ 现在不缺算法，缺的是反馈采集与去偏
   判据：你的线上日志能不能直接变成训练样本？不能，就先修采集
```

- **失效条件**：当任务没有可自动判定的答案，且用户反馈稀疏（大多数会话没有任何显式反馈）时，偏好学习这条链路的输入端就是空的——此时把预算加在算法侧不会改善任何指标。另一个失效条件是分布漂移快于训练周期：在线更新追不上，离线批训又永远滞后。
- **自验方法**：取一批被标注为「更好」的输出，人工复核其中 20 条【经验：随标注成本与风险等级变】。若复核通过率明显低于你的接受线，说明你优化的是标注者的偏好，而不是用户的偏好。

#### 5.2.3 自反馈与自我改进：Constitutional AI、Self-Play、Self-Refine 与 Agent Self-Critique

- **旧做法与它的卡点**：评判者只能是人——要么人工标注偏好，要么人工写规则。人工标注贵且慢，而且人对自己偏好的表述本身不稳定；写规则更写不全，越细的规则越容易互相冲突。自反馈想解决的就是「请不起人当裁判」这件事。
- **AI 改变了什么机制**：把「评判者」从人换成一个按**书面原则**打分的模型（Constitutional AI），或按**可验证结果**打分的环境（Self-Play 在数学、代码这类任务上）；Self-Refine 则把修正动作放在推理时——生成、自我批评、重写，迭代若干轮而不改权重。判定标准从「专家共识」变成了「一份厂商自定义的原则文档」。
- **由此得到的**：因为评判不再需要人来标，**所以**在答案能被自动判分的那一类任务上，训练信号近乎无限——模型可以自己出题自己解，规模不再受标注预算约束；因为修正在推理时完成，**所以**不改权重就能改善单次输出，这使得自反馈成为唯一一种不需要训练基础设施的改进手段。
- **由此付出的**：代价集中在**循环性**上。① 同一个模型既产生错误又判定错误——判官与被判者同分布，它无法提供生成时没有的信息，因此自反馈在同类任务上更容易收敛到「更像自己」，而不是「更正确」。② 自我精修在不能自我判定的任务上会让答案**更自信但没有更对**（多轮重写只是把表述打磨得更像那么回事），而迭代几轮有收益这件事在论文里成立、在产品里不必然——**论文里的原型与产品里的实现是两件事**。③ 原则自评把判据写进一份自定义文档：换一个组织就是另一套判据，没有跨实现契约，也就无法做第三方复核。④ 自反馈会放大原有的分布偏差：模型偏好的风格被反复强化，而这条偏差在日志里表现为「模型越来越一致」，不容易被当成问题。
- **证据与来源**：【公开】书面原则自评的方法论文（Constitutional AI，2022 年公开，可按题名检索核验）；【公开】Self-Refine（2023）与自我博弈路线（现代形态见 AlphaZero 一路，2017）各有公开论文；第三方（非厂商）生产案例：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「自反馈与自我改进」行一致：① 满足、② 不满足、③ 不满足——能力可用而判定标准尚未形成共识）。本条覆盖：Constitutional AI、Self-Play、Self-Refine、Agent Self-Critique。

自反馈能工作，只取决于三个前提；缺任何一个，加自评轮数都只是加成本：

```text
自反馈的三个前提（缺一个，收益就退化成「更像自己」）
   ① 可判分   奖励能由一个不依赖模型的函数算出来
              能  → 自出题自解成立，信号近乎无限
              不能 → 判官只能是模型或人，此时先算标注预算
   ② 判官不同源  判官与生成者来自同一分布时，它提供不了新信息
              检查方法：换一个不同来源的判官，看排序是否翻转
   ③ 修正可回滚  这轮修正改的是上下文（可丢弃）还是权重（要能回退）
              改权重 → 必须有回滚件，否则一次判错会被固化
   ────────────────────────────────────────────
   判据：把「零轮自评」与「N 轮自评」两版混起来盲评
        偏好与轮数不相关 ⇒ 自反馈在当前任务上只有成本，没有收益
```

- **失效条件**：当任务的主观成分高（文案风格、共情表达、设计取舍）时，自评的判据只能由实现方自己写，此时自反馈的收益无法与「换了个人写的提示词」区分开；正确做法是把它降级为草稿生成器，验收仍然交给人，而不是继续加自评轮数。
- **自验方法**：把同一批输出的「零轮自评」与「N 轮自评」两版混在一起让人盲评，若盲评偏好与轮数不相关，说明自反馈在这里只增加了 token 成本。

#### 5.2.4 反馈的消费与管理：从检索回填到跨 Agent 共享

- **旧做法与它的卡点**：反馈采到之后只有一条去处——攒够一批做训练。于是三类需求全都无处安放：想立刻修正一次检索结果（等不到下一轮训练）；想知道哪个资产、哪条记忆更值钱（评分无依据）；想让多个 Agent 共享同一批反馈（没有通道，只有各自的日志）。同时反馈数据本身在治理上处于盲区：它是用户数据、也可能是训练数据，但两类台账里都找不到它。
- **AI 改变了什么机制**：把反馈的消费点从「训练」扩到**运行时**——反馈可以直接改检索排序（把被采纳的结果往上提）、改图谱关系（用户纠正一条边）、改记忆的保留决策（反馈评分即记忆重要性评分）、改资产的质量分。机制上的共同点是把反馈当作**运行时的一个输入**，而不是一批待训练的样本。
- **由此得到的**：因为反馈不必等到下一轮训练才生效，**所以**闭环的响应时间从「周」压到「分钟」；因为同一批反馈可以被多处消费，**所以**「只采一次、多处复用」在结构上成立——这也是把反馈当成一类独立资产管理的理由。
- **由此付出的**：① **回填路径越多，责任越糊**：反馈改了排序 → 谁负责这条排序信号是对的？反馈改了记忆保留 → 与合规删除义务的边界在哪（答不出来时，删除请求会连带删掉本应留证的记录）？② **反馈的可信度问题被放大**：训练侧可以用一批数据摊平噪声，运行时侧一条被污染的反馈就直接改变这一次的结果，且没有回滚记录。③ **评分不可比**：反馈评分换算成「记忆重要性」「资产价值」的规则由实现方自定义，没有公开可比的评估口径——**用一个没有口径的分数去决定删除与定价，是这一族最大的风险**。④ 跨 Agent 共享的第一道门槛不是密码学而是**授权**：加密保护的是传输与存储的内容，不保护「谁有权让对方的 Agent 用我的用户反馈去训练」。
- **证据与来源**：检索侧反馈回填有公开实现与文档（可按「learning to rank」「点击反馈重排」检索核验）；族内其余六项的情况是——GraphRAG 关系纠错、反馈驱动的资产价值评分、多模态反馈、跨 Agent 反馈共享目前可核到的公开材料是论文、演示与路线图；反馈驱动的记忆只有实现说明（与 [长期记忆 §5.2.3](../01-long-term-memory/01-long-term-memory-section-5-ai.md) 的保留策略行同判据）；反馈数据治理目前只有法规义务、没有实现口径。第三方（非厂商）生产案例：无公开可核验来源。
- **成熟度**：**L3**（与 5.1 表「反馈的消费与管理」行一致：① 不满足——族内七个子项里只有检索回填有正式文档级的公开实现，其余六项只有实现说明、论文、演示、路线图或法规义务；② 不满足；③ 不满足）。本条覆盖：Feedback-Driven RAG、GraphRAG 反馈、反馈驱动的记忆、反馈驱动的资产、多模态反馈、反馈数据治理、跨 Agent 反馈共享（联邦）。

| 反馈的消费点 | 生效时机 | 回滚对象 | 可核验的现有件 |
| --- | --- | --- | --- |
| 检索排序（重排、加权） | 下一次检索 | 排序模型与权重 | 排序框架与特征存储，接口成熟 |
| 图谱关系（纠正一条边） | 下一次查询 | 关系版本 | 图库提供版本化写入，但纠错规则要自建 |
| 记忆保留（重要性评分） | 下一次衰减计算 | 条目与其索引 | 无标准件；与删除义务的边界须写死 |
| 资产定价（质量分） | 下一次盘点 | 分数与口径 | 无标准件，无公开口径 |
| 跨 Agent / 跨组织共享 | 对方下次使用 | 授权与存储位置 | 无标准件；先是合同问题，再是技术问题 |

- **失效条件**：当反馈的采集量本身不足（绝大多数会话没有任何显式信号）时，任何消费点都建不起来——此时该做的是补采集与去偏，而不是增加消费点。另一个失效条件是消费点跨越了组织边界：跨组织的反馈共享在没有责任划分文本之前，技术上做得通也不该做。

### 5.3 与本主题既有栈的接口在哪

本节不写「与 AI 结合」这类空话，只写三件事：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 反馈采集 ↔ 应用埋点（主文件 §1.4 的采集层） | 事件表 + `feedback_type` 区分显式 / 隐式 / 派生；隐式信号必须连带存曝光上下文 | 应用侧；采集漏了无法事后补 | L2：字段设计可自建，无标准件 |
| 反馈清洗 ↔ 数据质量（Ch11 · 01） | 交接物 = 干净反馈 + 去噪标记；每条都要能指回原始事件 | 数据侧；清洗规则改了要能重跑并比对 | L2 |
| 反馈 → 训练数据（主文件 §2.1 的偏好对 Preference Pair） | `(prompt, chosen, rejected)` 或单点标签 + 采集条件 | 训练侧；去偏失败会在离线指标上表现为「训了没变好」 | L2（5.2.2） |
| 反馈 → 检索（5.2.4） | 反馈加权后的排序信号；必须带「这条信号来自哪次曝光」 | 检索侧；污染信号无回滚记录时归因不回 | L3 |
| 反馈 → 记忆（[长期记忆 §5.2.3](../01-long-term-memory/01-long-term-memory-section-5-ai.md)） | 反馈评分即记忆重要性评分，进保留策略 | 记忆侧；合规删除不由评分决定 | L3，与 Ch7 §1 同判据 |
| 反馈 → 资产（Ch7 §3 资产管理） | 交接物 = 资产质量分与使用次数 | 资产侧；分数口径要写下来才可比 | L3 |
| 反馈 → 治理（[Ch8 · AI 数据治理](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md)） | 反馈数据作为独立资产类型登记；含来源、留存期、二次使用授权 | 合规侧；登记缺失时「这条反馈用于训练过谁」答不出 | 义务性接口，需自建 |

一句话概括：**AI 没有让「采反馈」变容易，它让「反馈的消费点」从一个（训练）变成了五个（检索、图谱、记忆、资产、跨组织）**。消费点每多一个，就多一条需要回滚路径的链路，而回滚路径在绝大多数团队里是后补的。

两条最容易出错的约定，单独写清：

**第一，反馈必须在采到的那一刻带上产生条件。** 缺了曝光位、缺了当时展示的候选集，事后就无法把一次点击还原成「偏好」。判定方法很具体：随机抽 10 条隐式反馈【经验：随采样成本变】，看能不能复原「当时它和谁比、排在第几」；答不出的比例，就是你这一批反馈不可用的比例。

**第二，训练用与运时用要分开两条通路。** 训练侧的反馈可以容忍噪声并批量摊平，运行时侧的反馈必须逐条可回滚——把两者合成一条，结果是「一次被刷量的反馈同时污染了排序和下一轮训练」。判定方法是问：这条反馈被消费了几次、分别在哪，答不出来就说明你只有一条通路。

再补一条失败责任的划法，因为它决定事故电话打给谁：**「反馈没采到」与「反馈采错了」是两件性质不同的事，不能混在一个告警里。** 没采到是覆盖问题，可以靠补埋点解决；采错了是语义问题——比如一次「复制」被记成满意，而用户其实是在把错误答案复制去求助——它会静默地污染下游所有消费点，而且只有人工复核能发现。所以采集侧要能给反馈打上「来源类型」与「是否已复核」，让下游按来源降权；把两类缺口合成一个采集率指标，等于把这些污染永久隐藏起来。

- WebGPT（2021）与 HH-RLHF（2022）——人类反馈驱动的检索与有害性偏好数据，属于 RLHF 之前的早期形态；引它们是为了区分**论文里的原型**与**产品里的实现**。
- 模型作为评估者的偏差（《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》，2023）——位置偏置、长度偏置、自我偏好的公开讨论出处。

**官方文档 / release note（判据 ① 的核验入口）**

本节列不出符合「文档名 + 年份」条件的 release note 条目：判据 ① 要读的是版本发布说明与产品文档页，而这类页面持续更新，同一个页面在不同版本下的内容并不相同，标一个固定年份反而不可复现。按上文的规则，它们不作文献条目，与产品文档合并到下面的检索入口里单列，只给检索点与判定标准。

**检索入口（产品文档页与 release 页持续更新，本节不代写文档名与年份，只给检索点与判定标准）**

- TRL（开源训练库的偏好优化实现，Apache-2.0；归属见 [§7 与其他方法对比](02-feedback-loop-section-7-sec7.md) 的候选表）——检索点：仓库的版本发布说明与偏好优化相关文档；判定标准是「偏好数据格式与超参口径有没有跨版本变化」，不是「支持多少种损失函数」。
- Statsig / GrowthBook（实验与评估平台；归属见 §7 候选表）——检索点：官方发布说明与指标定义文档；判定标准是分流标识与指标口径怎么定义、怎么随版本变化。
- Langfuse（LLM 观测与评估平台；归属见 §7 候选表）——检索点：官方文档里的 trace 数据结构条目；判定标准是「一次调用能否被还原成可标注的样本」，这是把线上流量变成训练数据的前提。
- ChatGPT / Claude / Cursor / Devin / 豆包 / 通义千问 / DeepSeek——检索点：官方文档里「反馈」「评估」「微调数据」的正式条目；判定标准是「有没有可编程的反馈读写接口与版本化行为说明」，**不是有没有点赞按钮，更不是案例页上的效果数字**。产品内可见点赞入口与「训练侧用了哪种算法」是两件事：后者属于厂商未公开的实现细节，本节不作断言。
- OpenAI o1 / o3 的公开介绍——厂商自述其推理能力由强化学习训练（2024-2025，按官方页面当前版本核验）；本节只把它作为「可验证奖励在推理任务上有效」的一条线索，不当作第三方结论。

**第三方（非厂商）公开生产案例**

- 无公开可核验来源。这是本节没有任何方向被评为 L1 的直接原因（判据 ②）。

**值得注意的空白**：公开材料里能查到「用了哪种算法」与「架构长什么样」，查不到「反馈怎么去偏、训了几轮、错了怎么回滚」。这不是因为它们不重要，而是因为反馈闭环的失败通常是静默的（指标缓降、模型越来越像自己），不容易被写成一份可引用的报告。它同时意味着：**这类判断只能自己测**。§5.2.1 与 §5.2.3 给出的两条自验方法（双判官排序比对、盲评偏好与轮数的相关性）就是这个原因。

### 5.5 被过度宣传的部分

**「Self-Improvement：Agent 会自己越用越聪明」**

- *实际是什么*：能自我改进的只有「答案能被一个不依赖模型的函数判对错」的那类任务——代码能不能跑、题能不能对、SQL 结果对不对。在主观质量类任务上，自反馈只是把模型的偏好写得更像它自己。
- *为什么会这样*：判官与被判者同分布，自反馈提供不了生成时没有的信息；原则自评的判据由实现方自定义，没有跨实现契约（5.2.3 的 ③）。
- *什么时候它才会成真*：出现与生成模型不同源、且可被第三方复核的判官，或任务本身变得可验证。

**「在线 DPO：实时反馈驱动实时训练」**

- *实际是什么*：把「采到反馈」与「反馈可用」混为一谈。线上反馈先要过两道关——曝光位偏差与样本自选择（只有极端体验才被点），过不了这两关的反馈进训练，等于把曝光策略的偏差固化进模型。
- *为什么会这样*：反馈的采集条件是界面的副产物，不是设计出来的；而运行时侧的一条污染信号没有回滚记录（5.2.4 的代价 ②）。
- *什么时候它才会成真*：出现可核验的反馈去偏口径，以及「在线更新 + 可回滚」的标准件；在那之前，在线更新应停留在检索、排序、路由这类可回滚的决策点上。

**「多模态反馈与跨 Agent 反馈共享已经可以规划」**

- *实际是什么*：多模态反馈（语音、表情、行为）目前可核到的是演示与预览；跨 Agent 反馈共享先是授权问题，再是密码学问题——加密保证「算的时候看不见明文」，不保证「谁有权让对方的 Agent 用我的用户反馈」。
- *为什么会这样*：各模态的标签如何归并到同一套偏好口径没有共识；存储地、跨境传输、用户向谁主张删除权属于法律与合同层面，不能用密码学消除。
- *什么时候它才会成真*：多模态需要出现跨模态的统一偏好口径；跨组织共享需要出现明确的反馈委托标准与责任划分。

这三条有一个共同结构：它们都把「机制已经就位」说成「能力已经就位」。偏好学习的机制确实已经就位（这也是它能评 L2 的原因），但「就位」指的是**实现存在**，不是**效果可证**。所以判断它们何时成真的办法是同一个——看公开材料里有没有出现可核验的判断依据（去偏口径、判官版本登记、授权模型），而不是看功能页上有没有多一个带「Feedback」的名字。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 反馈的**去偏与归因**会成为闭环里被单独建设的环节，与训练算法分开 | 公开材料开始区分「原始反馈」与「校正后反馈」两层，并给出曝光位校正的口径；工具链出现独立的归因组件 | 三年后主流做法仍把点击 / 点赞直接当标签，且没有公开的校正口径 |
| 自反馈与自我博弈继续收敛在**可验证任务**上，主观任务上不取代人工偏好 | 公开的强化学习训练报告越来越集中在可自动判分的任务；主观任务上的验收仍以人工评估为主 | 出现被多方复用的、主观任务上的可验证奖励构造，并有人复现出同样的效果 |
| 在线更新长期停在「离线批训 + 短周期在线探索」的分层，不直接更新生成模型权重 | 平台把在线更新限制在检索、排序、路由这类可回滚的决策点上，并把它与生成模型的发布流程分开 | 出现把线上反馈直连生成模型权重、且带标准回滚件的主流方案 |
| 反馈数据的治理要求落进法规 / 标准的**实施细则**，而不停留在原则表述 | 监管或标准组织的公开文件里出现对反馈数据采集、留存、二次使用的具体条款 | 相关义务仍只落在「训练数据」的总括表述上，没有单独条款 |

四条预测都能靠**公开文档**证实或证伪，不需要内部数据：第 1、3 条看工具与平台的接口形态，一到三年见分晓【经验：随工具链换代速度变，产品更新越慢窗口越长】；第 2 条看公开训练报告的任务分布，两到三年【经验：随公开报告的发布节奏变】；第 4 条看监管与标准文本的更新，三到五年【经验：随法规修订周期变，不同法域差别大】。

最值得先盯的是第 1 条：它是本节唯一一条**不依赖任何新模型发布**就能观察到的信号——去偏与归因是接口与流程设计，不是模型能力；它也是把反馈从「采到就用」变成「可依赖资产」的那一步。

另有六条趋势，其中三条已被上表覆盖——「在线学习 + Agent 平台融合」落在第 3 条预测，「反馈数据治理成为 AI 治理核心议题」落在第 4 条，「跨 Agent 反馈共享（联邦学习）」落在 5.5。剩下三条——「反馈闭环自动化（Self-Improvement）」「RL 与 Self-Play 结合」「多模态反馈（语音 / 表情 / 行为）」——本节不写进预测表，因为它们各自的成真信号无法在不预先假设产品形态的前提下写出来（多模态反馈的成真信号取决于下一个主流交互界面是什么，而那正是待预测的变量本身）；前两条已在 5.2.3 逐条评估。**写不出信号的预测不要写**：把它们记录在 5.2.3 与 5.5 里，比给一个永远正确的句子更有用。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 客服 / 助手类产品，正在纠结选哪种算法 | 先把反馈采集与评估集建起来（带曝光上下文、带判官版本）；算法先用现成开源实现跑通一个基线 | 是否出现可核验的反馈去偏口径 | 不要在反馈采集还没带上下文时就开始训模型——你训的是界面，不是偏好 |
| 有可验证答案的任务（取数、SQL、代码） | 走可验证奖励路线（5.2.2 的第一个问题答「能」）；先建自动判分器 | 公开训练报告在可验证任务上的推进速度 | 不要把可验证任务的经验直接搬到主观任务上 |
| 推荐 / 搜索类产品 | 把在线更新的范围钉在排序与路由上，并给它独立回滚开关 | 是否出现「在线更新 + 标准回滚」的现成件 | 不要让线上反馈直连生成模型的权重 |
| 受监管行业（金融 / 医疗 / 教育） | 先补 HITL 痕迹与反馈数据的台账（来源、留存期、二次使用授权） | 反馈数据是否出现单独的监管条款 | 不要在缺审计痕迹时上自动更新——事后举证责任在你 |
| 想采购实验 / 评估 / 观测平台 | 先定义验收口径：能否导出原始事件、能否记录判官版本、能否按条目回滚 | 是否出现第三方维护的公共评估口径 | 不要按「支持多少种反馈类型」选型——类型多不等于口径对 |

「明确不要做」那一列的共用逻辑只有一句：**本节真正变了的是「反馈能被用在哪里」，没变的是「这条反馈是在什么条件下产生的、错了谁负责」**。所以预算该投在采集带上下文、去偏有口径、消费点有回滚三件确定性工程上；在这三件之前，任何「跨 Agent 反馈共享」「多模态反馈」的规划都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先让反馈带上产生条件**：曝光上下文、采集入口、判官与模型版本（5.2.1 与 5.3 的第一条约定）。这一步不需要新采购。
2. **再建评估集与判官版本登记**：没有它，后面所有算法的效果都无法被验证。
3. **然后才动参数**：在可自动判分的任务上跑通一条偏好学习链路，其余任务先停在提示工程。
4. **最后才谈消费点与共享**：它们会改变授权边界与回滚范围，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新的模型能力——事件表字段、评估集、判官版本登记、回滚开关，全是工程与流程。这也解释了本节为什么没有 L1：真正已经就位的那部分（测量与离线偏好学习）不需要被宣传，而需要被宣传的那部分（自反馈、在线训练、跨组织共享），还没有成熟到能被第三方核验。两者之间的落差，就是本节四行评级全部停在 L2 与 L3 的原因。

### 5.8 小结

> 本节小结：反馈闭环里 AI 真正改变的只有一条机制——**把「什么算好」从人写的规则换成了一次模型或可验证函数的判断**，因此反馈第一次可以在没有等量人工标注的前提下规模化进入训练与运行时；它没有改变的是**这条判断的成立条件**：反馈离开它的产生上下文就不可用，判官与被判者同分布就提供不了新信息，而反馈的价值至今没有公开可比的度量口径。所以本节没有 L1 方向：能排进路线图的是采集带上下文、去偏有口径、消费点有回滚这三件工程，而不是「越用越聪明的 Agent」或「实时反馈实时训练」。
>
> 💡 **思考锚点**：拿你现有的一条反馈链路自查两点：它采到的反馈带没带曝光上下文与判官版本？它对应的奖励能不能被一个可验证函数算出来？按 5.7 的四步顺序，你现在卡在第几步——是判官与被判者同分布给不出新信息，还是采集阶段就没带上产生条件？
