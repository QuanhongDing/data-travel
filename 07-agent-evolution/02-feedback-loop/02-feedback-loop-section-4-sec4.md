## 4. 工程实现

本节按「**一条反馈从产生到改变权重**」的顺序组织：§4.1 把它拆成 8 步并给每步的产物与判据，§4.2 给 9 个关键技术点的机制与失效条件，§4.3 按约束给工具选型判据，§4.4 讲已经上线、日志早在跑但反馈没被当成反馈的系统怎么补，§4.5 给可直接套用的模板与代码，§4.6、§4.7 收口。

两类读者入口不同。**从零建闭环的人**按 §4.1 顺序走，前 4 步（采集 → 存储 → 清洗归因 → 训练数据生成）走完再谈训练——跳过前 4 步直接训练，等于没有任何判据可用（依赖顺序见 [§ 7.5](02-feedback-loop-section-7-sec7.md) 第 2 层）。**已有线上系统的人**先看 §4.4：这类系统的真实处境往往是「反馈早就在日志里，只是没有按事件的粒度存下来」，第一步不是新建设施，而是把已有日志按反馈事件的口径离线重解析一遍。

### 4.1 落地步骤

**Step 1：反馈采集设计（显式 + 隐式）（2–4 周）**【经验，随已有埋点体系的成熟度变】

1. 显式通道（评分 / 点踩 / 纠错）与隐式通道（采纳 / 复制 / 撤销 / 重生成 / 放弃）写进同一张事件表，用 `feedback_type` 区分；隐式信号必须连带存曝光位次。
2. 每条事件必须带 `session_id`、`turn_id`、`model`、`prompt_version`、`position`、`experiment_id`——身份维度只有写入时能定死，事后补不回来。
3. 埋点与 SDK 同版本发布；写入异步、不阻塞用户请求。

- **产物**：一张 `feedback_event` 事件表（DDL 见 §4.5 模板四）+ 一份埋点字段字典（字段名 / 含义 / 谁维护）+ 一条「从线上某个动作到表里某一行」的端到端验证记录。
- **判据**：抽 3 个真实会话，看能否在表里追到每个动作对应的行，并回答「这条信号属于哪个模型版本、哪个 prompt 版本」；再确认隐式事件是否带了 `position`（缺它，位置偏置无法校正）。
- **为什么必须这一步 / 为什么在这个位置**：清洗、归因、训练、实验全部以这份事件表为输入。先上训练再补埋点的人，会在拿到第一批偏好对时发现它们无法按模型版本分桶，于是第一批数据只能整体作废；而 `position` 与 `prompt_version` 这两个字段一旦漏采，历史数据无法回填。

**Step 2：反馈存储（Feedback Lake）（2–6 周）**【经验，随事件量级与合规要求变】

1. 与业务主库隔离的独立存储，避免分析型写入影响在线库。
2. 原始层 append-only（只追加、不原地覆盖），派生层（标签、归因结果）可重算、可整层重建。
3. 定义保留策略与 PII 处理（脱敏字段清单、同意状态随事件记录）。

- **产物**：Feedback Lake 的原始事件层 + 派生层 + 保留策略文档 + PII 字段清单。
- **判据**：任取一条半年前的事件，能否在不修改原始层的前提下用新口径重算一次归因标签；再抽样确认 PII 字段已按清单处理（写入示例见 §4.5 模板二）。
- **为什么必须这一步 / 为什么在这个位置**：判定准则、场景权重、模型版本都会变。只有原始层不可变时，口径变更才是一次重算而不是一次数据损失。它必须排在清洗之前——清洗逻辑本身就要反复改，若把清洗结果直接覆盖原始事件，这层保障会提前毁掉。

**Step 3：反馈清洗、归因（3–6 周）**【经验，随事件量与需要归因的环节种类数（检索 / 工具调用 / 生成）变】

1. 清洗：去重、反作弊、剔除机器流量、按来源加权。
2. 归因：把反馈落到**可修改的动作**上——检索候选集与引用、工具调用轨迹、prompt 版本，而不是停在「这次体验差」。
3. 漂移检测：比对分布（反馈构成、场景占比、模型版本占比），而不只看聚合指标。

- **产物**：清洗规则清单 + 归因结果表（事件 → 具体环节）+ 漂移看板。
- **判据**：抽 10 条负向反馈，看能否各自定位到「是检索错了还是生成错了」；定位不到的条数比例即归因覆盖率，把它当成一级指标看。
- **为什么必须这一步 / 为什么在这个位置**：没有归因的反馈只能驱动「全量重训加猜测」——闭环看起来在转，学习没有发生（[§ 3.5](02-feedback-loop-section-3-sec3.md)「反馈未归因」）。它必须排在训练数据生成之前，因为不同的归因结果对应不同的样本构造方式：检索类问题进重排训练，生成类问题进偏好训练。

**Step 4：训练数据生成（2–4 周）**【经验，随每类样本的构造难度与标注强度变】

1. 按归因结果分三类构造样本：偏好对（chosen / rejected）、演示样本、纠错样本。
2. 标注走流水线：问题池 → 任务分片 → 多人重复标注 → 黄金集校验 + 一致率 → 仲裁 → 偏好库；指南本身版本化。
3. 偏好库与训练解耦：先沉淀、按需取用，同一批数据可以在换算法后继续用。

- **产物**：偏好库（带 prompt 版本与来源标注）+ 可 diff 的标注指南 + 一致率报表。
- **判据**：抽 20 条偏好对让两人重标，看是否会判「打平」（判不出的比例即标签的可分辨程度）；再取 200 条真实样本人工评一遍，拿到自己任务上的真实单价与一致率——这两个数决定后面标注预算能不能覆盖所需样本。
- **为什么必须这一步 / 为什么在这个位置**：样本形态由算法分支决定（成对走 DPO / RLHF，单点走 KTO，可验证走 GRPO），先建偏好库再选算法，可以在同一批数据上换算法而不必重采；反过来先定算法再采数据，每换一次算法就要重标一轮。

**Step 5：模型迭代（DPO / GRPO / Online）（按迭代周期）**【经验：离线批训以周计，在线更新以天计】

1. 按 [§ 3.3 模式选择决策表](02-feedback-loop-section-3-sec3.md) 选分支，不在一个场景上同时上两条训练路线。
2. 离线分支配评估集门禁与 KL 约束；在线分支（Online DPO）必须先有分钟级回滚能力再开。
3. 每次训练留下完整配置：基座版本、数据版本、参考模型冻结点、组大小或 KL 系数。

- **产物**：一份可复现的训练配置 + 训练前后在同一评估集上的读数 + 一个明确的回滚点。
- **判据**：训练前后的读数必须在同一份**从未参与调参的留出集**上取；若只有训练集指标上升而留出集不动，本次不得上线。
- **为什么必须这一步 / 为什么在这个位置**：它必须排在评估集之后。没有评估集就上 RLHF，等于把「训一版废一版」变成常态——每一版都要付出完整训练成本，却没有任何判据能告诉你这一版比上一版好（[§ 7.4](02-feedback-loop-section-7-sec7.md)）。

**Step 6：A/B 测试、灰度（2–6 周 / 次实验）**【经验，随想检测的提升幅度变】

1. 先算最小样本量：给定基线指标、想检测的最小提升、显著性水平 α（常取 0.05）与统计功效 1 − β（常取 0.8）（方法与系统论述见【公开】Kohavi 等, 2020）。
2. 方差大或流量小的场景，用实验前同一用户的历史指标做协变量调整降方差（CUPED，【公开】Deng 等, WSDM 2013），必要时改用交叉展示（Interleaving，【公开】Radlinski 等, CIKM 2008）。
3. 灰度分层放量（小流量 → 分群 → 全量），每层设明确的通过条件。

- **产物**：实验设计一页纸（假设、指标、最小样本量、计划时长）+ 分层放量计划 + 停止规则。
- **判据**：把最小样本量除以日流量算出天数，再与「这个结论最晚什么时候要被用上」对比；超期即判跑不动，换方案而不是先开实验再看。
- **为什么必须这一步 / 为什么在这个位置**：它是唯一能把离线读数与线上效果对齐的一步；排在训练之后，是因为用一个无结论的实验占着流量的代价，大于暂时不上线（判定方法见 [§ 7.5](02-feedback-loop-section-7-sec7.md)）。

**Step 7：监控、回滚（上线即开始）**

1. 三层监控：业务指标、模型行为指标（拒答率 / 输出长度 / 工具调用成功率）、反馈信号分布。
2. 明确回滚触发条件与执行人；版本与配置都能一键切回。
3. 在平静期做一次回滚演练，记录从决定到切回的耗时。

- **产物**：回滚预案（触发条件、执行人、演练记录）+ 一次真实演练的耗时读数。
- **判据**：演练耗时是否短于你能接受的最大用户影响窗口；长于它，就不要开在线更新。
- **为什么必须这一步 / 为什么在这个位置**：在线更新的出错是在生产上出错，回滚能力是它的前提而不是补救。离线批训的场景下它是第二前提，第一前提仍是评估集。

**Step 8：反馈本身的质量治理（长期）**

1. 给反馈数据定 Owner、保留策略与 PII 处理。
2. 质量校验：重复标注一致率、自动反馈与人工反馈的偏离度、覆盖率。
3. 分布偏差识别与重加权（低覆盖场景不退化为只服务主流）。

- **产物**：反馈数据的 Owner 名单 + 质量指标（一致率 / 偏离度 / 覆盖率）+ 保留与 PII 策略文档。
- **判据**：问「这批数据的 Owner 是谁、保留多久、含 PII 的字段怎么处理」，三个问题都要能在文档里找到答案；再抽一次自动反馈与人工反馈的一致率。
- **为什么必须这一步**：反馈数据本身会漂移与污染（运营激励、界面改版、刷分），没有质量治理时噪声会被当成信号学进模型（[§ 3.5](02-feedback-loop-section-3-sec3.md)「反馈噪声」）。

8 步里最容易在排期上被挤掉的是 **Step 3 的归因**与 **Step 8 的质量治理**——它们的产物不是可见的新功能，看起来像「后续优化项」。跳过后第一个出问题的时点通常在第二次上线之后：模型确实更新了，却说不清改掉的是哪一类错误；症状是同一批错误反复出现，而每一轮都只能靠全量重训加猜测来应对。

### 4.2 关键技术点

**1. 反馈 API 设计**

- **做法**：一个写入接口吃两类事件（显式 / 隐式），服务端补全 `model`、`prompt_version`、`position`、`experiment_id`；`event_id` 幂等；写入异步，不进入用户请求的关键路径。
- **机制**：因为反馈的用途是「按版本分桶比较」，身份维度必须在写入时定死，事后无法回填；异步写入让采集不增加用户可见延迟，这正是采集可以做稠密的前提。
- **失效条件**：**当推理侧还没有统一的 prompt 版本标识、只能靠上线时间人工登记时**，这条失效——跨版本指标不可比，症状是所有对比都退回到「上线前 vs 上线后」这种混杂了其他变更的比较。
- **档位**：写入延迟预算【经验】（判定方法是在网关侧取 P99，与业务接口的延迟预算同量级）。

**2. Feedback Lake（专用存储）**

- **做法**：原始层 append-only + 派生层可重算；按事件量分区、冷热分层；反馈表不进业务主库。写入示例见 §4.5 模板二。
- **机制**：因为判定准则与归因逻辑会变，原始事件必须保持不可变，才能在同一条数据上用新口径重算——这与数仓里「原始层 → 明细层」的分层是同一个机制；隔离存储则避免分析型写入影响在线库。
- **失效条件**：**当团队为了省事直接在业务库里 UPDATE 反馈标签时**，这条失效：一次口径变更会把历史样本原地改写，再也无法回答「按新口径这批数据长什么样」；症状是每改一次准则就要重新采集一轮。
- **档位**：【经验】。

**3. 标注平台（Label Studio、Scale AI、Argilla 等）**

- **做法**：标注做成流水线——问题池 → 任务分片 → 多人重复标注 → 黄金集校验 + 一致率 → 仲裁 → 偏好库；指南版本化，疑难样本升级给资深标注。
- **机制**：因为「什么是有帮助的回答」写不成规则，人的判断是唯一能覆盖长尾语义的通道；冗余标注 + 黄金集则把「谁的判断」变成可度量的量，否则标注质量无法审计。
- **失效条件**：**当指南留下歧义而没有仲裁机制时**，这条失效：同一个歧义在各标注员身上朝不同方向独立地错，「多标几遍」从提高覆盖变成放大噪声；症状是一致率下降而教学质量不变。
- **档位**：把复核设计成按批放行（先全量复核 200 条建立基准，之后按 10% 抽样，抽到判错就回到全量）为【经验】（推导见 [§ 7.5](02-feedback-loop-section-7-sec7.md)）。

**4. A/B 测试平台（火山引擎、Optimizely、Statsig、GrowthBook 等）**

- **做法**：开实验前先算最小样本量；用实验前协变量做降方差（CUPED）；小改进改用 Interleaving；分层灰度并设停止规则。
- **机制**：因为最小样本量随「想检测的提升幅度」平方反比增长，「小改动测不出来」是数学结果而不是执行力问题；CUPED 的收益不是提高精度，而是把所需样本量降下来，在小流量场景里直接决定实验能不能做成。
- **失效条件**：**当由最小样本量折算出的实验时长超过业务决策周期时**，这条失效：实验会跑成一个无结论的结论并一直占着流量，症状是每次结论都说「观测到正向但不显著」。
- **档位**：α = 0.05、1 − β = 0.8 为【公开】通行取值（Kohavi 等, 2020）；具体实验的样本量必须按自己的基线与最小提升重算，不要沿用别处的数字。

**5. Eval 平台（Langfuse、Helicone、Arize Phoenix 等）**

- **做法**：离线评估集版本化并挂到 CI 门禁（回退数为 0 才允许进灰度）；LLM 评委 + 抽样复核；另留一份从未参与调参的留出集；评估集本身定期换血。
- **机制**：因为评价标准被外化成可执行断言，每次改动都能得到同一把尺子的读数，回退在合并前就被发现；LLM 评委的作用是把人工比例压下来，让评估能跟得上改动频率。
- **失效条件**：**当评估集既用于调参又用于验收、且没有留出集时**，它从「衡量泛化的尺子」变成「被优化掉的目标」；症状是离线分数持续上升而线上投诉不变。第二个方向是把人工比例压得太低：先在你自己的任务上测一致率，不达标时正确的动作是加人工，不是换评委。
- **档位**：强模型评委与人类偏好的一致率有公开报告给出 80% 量级（【公开】Zheng 等, 2023, MT-Bench）；「取 200 条真实样本自测一致率」为【经验】判定方法（[§ 7.5](02-feedback-loop-section-7-sec7.md)）。

**6. Reward Model 训练**

- **做法**：用偏好对（prompt, chosen, rejected）训练一个打分器（Bradley-Terry 损失）；记录偏好对的来源与生成它的模型版本；每轮训练前先校验偏好对是否过时。
- **机制**：因为偏好被压成一个可复用的标量函数，人就被从每一轮训练里拿掉了，边际成本从人力变成算力；代价是它给出的是代理目标——代理与真实目标一旦脱钩，优化压力会把这个差距放大。
- **失效条件**：**当策略被允许朝奖励高的方向大幅移动、且奖励模型与策略同分布时**，这条失效（奖励被钻空子）：奖励分数上升而人工抽查质量下降，症状是输出开始出现可识别的格式讨好或谄媚特征。兜底手段是 KL 约束 + 人工抽查，两者缺一不可。
- **档位**：偏好对「是否过时」的判定不用天数——用旧偏好对重跑一次 DPO，看它还能不能把 chosen 排前，排不动即判过时【经验】（[§ 7.5](02-feedback-loop-section-7-sec7.md)）。

**7. PPO / DPO / GRPO 训练框架（TRL、OpenRLHF、LLaMA-Factory 等）**

- **做法**：按模式决策表选分支；DPO 需冻结参考模型；GRPO 需 group size N 与奖励函数（规则或可验证器）；RLHF 三段式只在确需在线 RL 时使用。
- **机制**：因为 DPO 的目标只依赖成对偏好与参考模型，不需要奖励模型也不需要在线采样循环，「每天一批偏好数据直接更新策略」在工程上可行；GRPO 则把基线从「训练一个 critic 网络」换成「同一问题多采样几次」，用采样成本置换训练成本。
- **失效条件**：**当同一 prompt 的多次采样奖励方差很小时**，组内相对优势接近噪声，这条失效：训练几乎不更新或不稳定，症状是组内均值随 N 增大而不收敛。判定方法是画「N 对组内均值标准差」的曲线，取走平处，不设固定值。
- **档位**：GRPO 训练期生成本数约为 DPO 的 4 倍（N = 8 对 2 条回答，【推算】，[§ 7.4](02-feedback-loop-section-7-sec7.md)）；显存上 DPO 约需两套权重、RLHF 约四套，故 DPO 的显存需求约为 RLHF 的一半量级（【推算】，不含优化器状态与激活等常数项）。

**8. 在线学习框架（FTRL、Contextual Bandit 等）**

- **做法**：把决策与更新放在同一条链路上——打分 → 选动作 → 观测奖励 → 在线更新；奖励定义与长期指标绑定并定期校验；FTRL 用于稀疏大规模特征的流式更新，Bandit 用于决策点即反馈的场景。
- **机制**：因为探索被写进决策式（置信上界或后验采样），系统不需要离线标注就能持续获得信息并自我修正；代价是它必须拿一部分真实流量换信息。
- **失效条件**：**当奖励函数与业务目标错位时**（用点击率当奖励而目标是留存），这条失效——它只会忠实、且越来越熟练地优化你给它的那一个数；症状是代理指标持续上升而长期指标下滑，且只有月度复盘才看得出来。第二个方向是**反馈频率不够**（分钟级反馈数只有个位数量级时，在线更新的方差会吞掉信号，【经验】[§ 7.5](02-feedback-loop-section-7-sec7.md)），此时应攒成批走离线。
- **档位**：【经验】，判定起点是把最近一周的反馈按分钟聚合，看每分钟平均条数。

**9. 反馈数据治理（去噪、归因、漂移检测）**

- **做法**：去重 + 反作弊 + 按来源加权；归因记录检索候选、工具调用与 prompt 版本；漂移检测比对分布（反馈构成、场景占比、模型版本），而不是只看聚合指标。
- **机制**：因为反馈是有偏样本（愿意打分的人不代表全体，曝光位的改变会让同一次点击的含义不同），不做校正的反馈会把系统既有偏好当成用户偏好再喂回去；而漂移只在分布层面可见——聚合指标是分布变化的滞后读数。
- **失效条件**：**当噪声治理只做「剔除异常值」而不看来源结构时**，这条失效：被剔除的往往是长尾人群而不是噪声，症状是模型在小众场景上的表现持续退化，最终只服务主流场景。
- **档位**：【经验】。

### 4.3 工具链与平台

按「要解决的问题」选，并把「不选它的代价」一起算进去：

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 标注平台 | Label Studio、Scale AI、Snorkel、Argilla | 看两件事：能不能自建（数据不出域）、能不能做冗余标注 + 黄金集。有合规约束时自建优先 | 数据不能出域却选了纯 SaaS 的团队，最后会退回手工表格，一致率与黄金集全部消失 |
| Eval / 监控 | Langfuse、Helicone、Arize Phoenix | 判据是「能不能按模型 / prompt 版本分桶看指标」与「能不能接 CI」 | 只能看总览的监控台，答不出「从哪一版开始坏的」，回退只能靠用户发现 |
| A/B 平台 | 火山引擎、Optimizely、Statsig、GrowthBook | 判据是分流一致性、指标口径可自定义、是否支持 CUPED 类降方差 | 用业务表自己算分流，样本比例失衡会先污染实验结论 |
| 偏好数据 | Argilla、Hugging Face H4 | 判据是界面能不能把「打平」与「弃答」记为合法选项 | 只允许二选一的界面会制造假偏好，训练学到的是一条并不存在的分界线 |
| 训练框架 | TRL、OpenRLHF、LLaMA-Factory | 判据是「训练时同时驻留几套权重」与是否支持你要用的算法分支 | 显存不够时只能改小基座，而基座规模对最终效果的贡献通常大于对齐算法之间的差异 |
| 在线学习 | FTRL、BanditLib、Vowpal Wabbit | 判据是反馈频率与延迟预算是否够（分钟级反馈数为个位数量级时不要上） | 频率不够仍上在线更新，方差吞掉信号，等于白跑一轮并留下一个不可复现的版本 |
| Self-Improvement | Self-Play 框架、Constitutional AI 库 | 判据是「谁来判断这一轮比上一轮好」——答案必须是一个独立于模型的判定器 | 判定器若就是模型自己，得到的是同源偏差而不是进化，错误会被一致地放大 |

这张表里最容易被误选的是「Eval / 监控」这一行：团队常常先买了可观测台，然后把它当评估体系用。后果是能看到每次调用的成本与延迟，却没有一份可版本化、可挂门禁的评估集，于是任何回退都只能等用户发现。判据只有一句：**这套工具能不能回答「把 prompt A 换成 B，哪些用例变坏了」**；答不出，它就是监控，不是评估。

各产品对上述能力的支持与配额会随版本变化，采购前**请以官方文档当前版本为准**，不要按本表的类别名推断某个工具一定具备某项特性。

### 4.4 存量迁移

这一节写给「系统已经上线、日志已经在写，但反馈没有被当成反馈处理」的人。

**① 先做什么可以立刻见效且可回退（1–2 周）**【经验，随已有日志的完整度与需要映射的动作种类数变】

- 把已有会话日志按反馈事件的口径离线重解析一遍：日志里通常已经有复制、重生成、撤销、放弃、会话时长这些动作，把它们映射到 `signal` 字段；用批处理作业跑，不动线上代码。
- **产物**：一份「已有日志字段 → `feedback_event` 字段」的映射表 + 一批解析出的历史事件（按周分区）。
- **判据**：抽一天日志，看解析出的事件数与会话数是否在同一量级，且能否还原出「哪些会话给了负向信号」；解析不出的动作先记进映射表的待办列。
- **可回退**：整段是离线作业，产物不影响线上服务，无效即停。

**② 存量数据怎么分类处理（三类，不要统一返工）**

- **有版本标识的历史日志**（已带模型 / prompt 版本）：可直接进 Feedback Lake 的原始层，用于回溯分析。
- **只有动作、没有版本标识的日志**：作为弱标签使用——可用于行为分布与漂移基线，不要用于按版本归因。
- **无法还原上下文的日志**（无 `turn_id`、无曝光位次）：打标挂账，只用于粗粒度趋势，不进训练样本。
- **判据**：抽 3 天日志，各自能否归入三类；出现「以为能用于训练、实际缺版本标识」的，先挂账。

**③ 双轨怎么维持、维持多久**

- 旧路径不动（现有报表与线上策略照旧），新路径并行：埋点从新版本开始生效，反馈事件双写（业务库 + Feedback Lake）；训练侧初期只消费新路径数据，历史数据先用于评估集与漂移基线。
- **时长【经验】：2–3 个迭代周期**（若迭代周期为周级，约 1–2 个月）——足够积累一批覆盖主要场景的反馈事件，也足够暴露埋点字段的缺口。
- **判据**：新路径的事件量能否支撑「按模型版本分桶后每组样本数仍然够看」；不够就继续采，不要提前切换。

**④ 什么信号说明可以退出双轨**

- 新路径的事件覆盖了主要场景（按场景占比看，而不是按总量看）；
- 用历史数据建的评估集能在 CI 里跑完，并给出与基线可比的读数；
- 一次口径变更能在不重新采集的前提下对历史事件重算——这说明「原始层不可变」这条设计成立。
- **退出动作**：把历史数据区从「评估用」扩到「训练可用」（仅限第①类），同时关掉旧路径的解析作业，避免两套口径长期并存。

存量迁移里唯一不可逆的动作是「为了补字段而回填历史数据」——历史日志里没有的维度补不回来，硬填等于把猜测写进训练样本。正确做法是把缺口记进字段字典，让新版本从今天开始采全；已有的空缺用「覆盖了哪个时间段、缺哪些字段」显式记录下来，作为后续所有分析的口径说明。

### 4.5 模板 / 示例

**模板一：偏好训练（DPO / GRPO）**

```python
from trl import DPOTrainer, DPOConfig

# DPO 训练
trainer = DPOTrainer(
    model=model,
    ref_model=ref_model,
    args=DPOConfig(output_dir="./dpo-output"),
    train_dataset=preference_dataset,  # {"prompt": ..., "chosen": ..., "rejected": ...}
)
trainer.train()
```

GRPO 训练（示意）：

```python
from trl import GRPOTrainer, GRPOConfig

trainer = GRPOTrainer(
    model=model,
    reward_funcs=[accuracy_reward, format_reward],
    args=GRPOConfig(
        output_dir="./grpo-output",
        num_generations=8,        # 组大小
        beta=0.04,                # KL 系数
    ),
    train_dataset=math_dataset,
)
trainer.train()
```

**怎么用**：`model` / `ref_model` / 数据集三格按你的场景填；`num_generations` 与 `beta` 是示例值，不要照抄——N 由「同一 prompt 多次采样的奖励方差」决定（画 N 对组内均值标准差的曲线取走平处），`beta` 是 KL 系数，取值要用评估集扫一遍，并确认输出没有因为优化而变得不可读。

**模板二：Feedback Lake 写入（显式 / 隐式）**

```python
# 显式反馈
feedback_lake.write(
    user_id="alice",
    event_id="ev-8f2a",  # 写入侧生成，重试时保持同值（唯一约束去重）
    session_id="s-123",
    turn_id=3,
    feedback_type="explicit",
    signal="rating",  # 字段名与取值都按模板四 DDL：评分 = signal + value
    value=5,
    prompt=prompt,
    response=response,
)

# 隐式反馈
feedback_lake.write(
    user_id="alice",
    event_id="ev-8f2b",
    session_id="s-123",
    turn_id=3,
    feedback_type="implicit",
    signal="copy",  # 用户复制了回答
    prompt=prompt,
    response=response,
)
```

**怎么用**：所有字段名与取值都以模板四的 DDL 为准——显式评分没有独立的 `rating` 列，写成 `signal='rating'` + `value`；隐式动作只记 `signal`（如 `copy`），不带 `value`。示例省略了上下文参数——实际写入时不要省 `position`（缺位次无法做偏差校正；模板四的 DDL 未列此列，要自行补上）、`prompt_version` 与 `model`（缺版本无法归因）、`experiment_id` / `group`（缺它无法把反馈回溯到实验）；`event_id` 要由写入侧生成、重试时保持同值（幂等全靠它，换成库返回的 `id` 就失效了），`user_id` 应写脱敏后的稳定标识，而不是登录名。若要连「评语」这类自由文本一起存，DDL 里没有对应列：另建一列 `comment TEXT` 并纳入 PII 脱敏清单，不要把它塞进 `signal`。

**模板三：A/B 分流（稳定哈希）**

```python
import hashlib

def assign_group(user_id, experiment_name):
    h = hashlib.md5(f"{user_id}-{experiment_name}".encode()).hexdigest()
    return "treatment" if int(h, 16) % 100 < 50 else "control"
```

**怎么用**：加实验名进哈希，保证同一用户在同一实验内分组稳定、跨实验互不干扰。上线前先排除内部账号与爬虫，否则分流比例会被污染；`50` 是示例比例，实际按影响面定（破坏性越大的改动，初始放量越小）。这段只解决「怎么分」，不解决「要不要开」——开不开按 §4.1 Step 6 的最小样本量判据算。

**模板四：反馈事件 schema（DDL）**

```sql
CREATE TABLE feedback_event (
    id            BIGSERIAL PRIMARY KEY,        -- 库生成的代理键
    event_id      VARCHAR(64) NOT NULL UNIQUE,  -- 写入侧生成的幂等键，重试以它去重
    user_id       VARCHAR(64) NOT NULL,
    session_id    VARCHAR(64),
    turn_id       INT,
    timestamp     TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- 反馈内容
    feedback_type VARCHAR(32) NOT NULL,  -- explicit / implicit / derived
    signal        VARCHAR(64) NOT NULL,  -- rating / copy / accept / reject / ...
    value         FLOAT,                  -- 数值（评分 / 概率）

    -- 上下文
    prompt        TEXT,
    response      TEXT,
    model         VARCHAR(64),
    prompt_version VARCHAR(32),

    -- 归因
    experiment_id VARCHAR(64),
    group         VARCHAR(32),

    -- 治理
    pii_masked    BOOLEAN DEFAULT FALSE,
    consent       BOOLEAN DEFAULT TRUE
);

CREATE INDEX idx_user_ts ON feedback_event(user_id, timestamp DESC);
CREATE INDEX idx_experiment ON feedback_event(experiment_id, group);
```

**怎么用**：这张表可以整体照用，但有三处不要省——`turn_id`（否则反馈对不到具体一轮）、`position`（本模板未列，隐式信号必须补上，否则位置偏置无法校正）、`experiment_id` / `group`（否则反馈无法回溯到实验）。表里有两个标识列，别当成一个：`id` 是库生成的代理键，`event_id` 是写入侧生成的幂等键，重复提交靠它的唯一约束落成一行——§4.2 第 1 条说的「写入幂等」指的就是它，所以它必须由写入方在请求前生成并随重试保持同值，不能等库返回 `id`（§ 3.2.1 的示意 DDL 只按一列展示标识列且由库生成，生产表以本模板为准）。索引按查询模式建：按用户取时间序、按实验取分组；若你还做检索类归因，另建一张候选集与引用的明细表（见 [§ 3.2.7](02-feedback-loop-section-3-sec3.md)）。

### 4.6 自检清单

1. 抽 3 个真实会话，能否在反馈事件表里追到每个动作对应的行，并回答它属于哪个模型版本、哪个 prompt 版本？
2. 隐式信号事件是否带了曝光位次与曝光次数？缺任一项，位置偏置无法校正。
3. 原始反馈层是否 append-only？一次口径变更时，能否在不重新采集的前提下对历史事件重算标签？
4. 是否存在不止一条负反馈通道（点踩 / 撤销 / 放弃 / 纠错）？只有正向信号即违反「反馈单一」。
5. 抽 10 条负向反馈，能否各自定位到「检索错」还是「生成错」？这个比例（归因覆盖率）有没有被当成一级指标在看？
6. 最近一次口径变更（判定准则 / 场景权重）是什么时候？变更后历史事件重算了没有？
7. 评估集最近一次换血是什么时候？它是否同时用于调参和验收（是，则必须另留一份未参与调参的留出集）？
8. 用最小样本量除以日流量算出的实验天数，与这个结论的最晚使用时间相比是否超期？超期后换了什么方案？
9. 在线更新能否分钟级回滚到上一稳定版本？做过一次真实演练并记下耗时了吗？
10. 标注指南最近一次修订记录在哪？各标注员的一致率与黄金集通过率是多少？
11. 反馈数据的 Owner、保留策略、PII 处理在哪里能找到？LLM 评委的一致率在你自己的任务上测过吗（先取 200 条真实样本）？
12. 训练用的 chosen / rejected 是否全部出自当前策略、且没有随机化探索？是，则存在自我强化风险。

如果这 12 条只能先做一条，选第 5 条。它同时暴露采集与归因两个环节：定位得到，说明反馈能变成「改哪个动作」的指令；定位不到，反馈量再大也只能驱动全量重训加猜测，其余各条多半只是在把系统做得更贵。

### 4.7 小结

> 本节小结：整条落地链里唯一决定成败的环节，是 **Step 3 的归因**——它决定反馈能不能被翻译成一条可执行的修改指令。其余步骤的成本大多可以用工程手段压低（存储分层、分层采样、批处理、LLM 评委 + 抽样复核），只有归因做不到时，闭环会停在「看起来在转」的状态：反馈量不小、模型也在更新，但每次更新都改对改错无从判断。判断它有没有做到，只需抽 10 条负向反馈，看能否各自指到具体的检索、生成或工具调用环节。
>
> 💡 **思考锚点**：抽一批你线上最近的负向反馈事件，`model` 与 `prompt_version` 两列都非空的比例是多少？这个数如果偏低，「这一版比上一版好」就只能退化成比哪两段时间——那还算得上闭环吗？
