## 7. 与其他方法对比

> 原文件共 198 行：其中 §7 部分 130 行（至第 131 行的分隔线结束），为两张无依据打分表 + 选型表 + Checklist，缺少机制解释与可溯源证据；其后 67 行（第 132–198 行）误串入了 §8 面试真题集的内容（全景视图表、分主题展开、真题清单），本次一并清除。本节重写为 ~330 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

**第一个错位是把不同层的东西放进同一张表打分。** 原表是 6 行维度（适用 / 实时 / 成本 / 数据需求 / 稳定性 / 推理能力）× 5 个候选列（A/B 测试、RLHF、DPO、GRPO、Online Bandit），逐格填的还不是同一套词：只有「实时 / 成本 / 数据需求 / 稳定性」四行是「高 / 中 / 低」，「适用」行是「通用 / 训练 / 推理」，「推理能力」行是「不直接提升 / 中 / 高」。但这五个候选根本不在同一层：A/B 测试是**测量方法**（不改模型，只改你「知道什么」），RLHF / DPO / GRPO 是**离线训练算法**（把一批数据变成权重），Online Bandit 是**在线决策**（每个决策点选动作），Constitutional AI 是**自反馈机制**（把人类换成书面原则）。给它们打分，等于把体温计、退烧药、体温调节中枢和免疫系统放在一张表上评「好不好用」。方法论上正确的做法是：先按层分族，只在同族内部比较。

**第二个错位是维度随场景反转。** 取「数据需求」这一行：在「答案能自动判对错」的任务上（代码、数学、SQL 生成），数据需求反而**越高越好**——因为生成和判分都免费，你可以静默地造出百万级带标签的样本，此时「数据需求低」不是优点，是能力上限低。反过来，在「主观质量」类任务上（文案、共情、风格），每一条偏好都要人工比较，数据需求直接等于预算，此时「数据需求低」是决定性优势。同一维度在两个场景里排序相反，打分表只能给一个。

**第三个错位是维度不可加。** 把「稳定性」与「推理能力」放进同一个加权和，等于默许「用可控性换分数」。稳定性不达标是**工程正确性问题**（一次训练把线上模型训废，回滚窗口内业务不可用），推理能力不达标只是**效果问题**（答得不够好）。前者必须先作为硬约束筛掉——一个会周期性训崩的流水线，无论它的效果上限多高，都不该接在用户面前。

**第四个错位是阈值凭空来。** 原表写「推理 / 数学 → 高（GRPO）」，但没有回答「为什么是 GRPO」以及「什么时候不成立」。真实原因是：GRPO 用可验证奖励替代了学出来的奖励模型，而**凡是答案能被一个不依赖模型的函数判对错的任务，用人工偏好都是浪费**——这不是能力高低，是信号可得性。判据要写清这条边界，否则读者会在没有可验证答案的任务上照搬 GRPO，然后发现自己其实只是用一个模型去给另一个模型打分，绕回了奖励模型的所有问题。

**本章采用的 7 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 信号可得性 | 奖励能不能由一个不依赖模型的函数算出来 | 决定奖励的噪声底噪与采样的边际成本，是 GRPO 与 RLHF 分野的第一因 |
| 是否需驻留第二个模型 | 要不要单独训一个奖励模型 / critic | 决定显存、工程复杂度，以及失败模式（reward hacking 从哪来） |
| 反馈到参数的时延 | 从用户动作到权重变化需要多久 | 决定它能修今天的漂移，还是只能修长期能力 |
| 数据形态假设 | 要成对偏好、单点标签，还是可验证奖励 | 决定你已有的线上日志能不能直接用，采集成本差一个量级 |
| 探索与护栏 | 优化它会压垮哪个别的指标 | 决定要不要加 KL 约束、探索机制与护栏指标 |
| 可复现与可审计 | 同一批数据能否复现同一个模型、决策能否溯源 | 决定它在受监管场景能不能上线，也决定事故能否复盘 |
| 生态与锁定 | 换掉它要重建什么（数据格式、指标口径、平台） | 这一族的锁定点不在算法里，而在观测 / 实验 / 标注平台上：偏好样本的 trace 结构、分流标识与指标口径一旦按某个平台沉淀，换算法的成本远低于换平台 |

### 7.2 候选方案全景

「核心机制」一列填的是**信号如何变成参数或决策**，不是它「强不强」；「许可 / 商业模式」一列填的是**离开它的代价**——方法类候选没有可谈的许可，锁定发生在工具类候选上。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| A/B 测试 | 测量（不动模型） | 随机分流 + 假设检验，用最小样本量判定差异 | 任何线上改动的验证 | 方法，无许可约束；自研或买实验平台 |
| Interleaving | 测量（更省流量） | 把两路结果交叉混排成一条列表，按点击偏好判定 | 排序 / 推荐 / 检索 | 方法，无许可约束（公开论文与实现） |
| CUPED | 测量（降方差） | 用实验前同一用户的历史指标做协变量调整 | 需要缩短实验周期的团队 | 方法，无许可约束；主流实验平台多已内置 |
| Eval-Driven Development | 工程流程 | 测试集进 CI，模型 / Prompt 改动必须过评估门禁 | 迭代频率高的 LLM 应用 | 工程实践，无许可约束 |
| RLHF | 离线训练（三段式） | SFT → 训奖励模型 → PPO 最大化奖励，配 KL 惩罚 | 通用对齐、行为塑形 | 算法公开（论文），实现以开源库为主（如 TRL，Apache-2.0） |
| DPO | 离线训练（一阶段） | 直接在偏好对上优化策略，奖励被隐式表示为与参考模型的对数比 | 有偏好数据、算力有限 | 同上 |
| IPO | 离线训练（加约束） | 在偏好对上加恒等映射约束，抑制 DPO 把 chosen / rejected 差距拉满 | 偏好数据有噪声、易过拟合 | 同上 |
| KTO | 离线训练（单点） | 用前景理论把「好 / 不好」的单点标签映射成效用 | 只有点赞点踩的产品 | 同上 |
| GRPO | 离线训练（组内相对） | 同一 prompt 采样一组回答，用组内相对优势替代 critic 与绝对奖励 | 数学、代码、可验证任务 | 同上 |
| Online DPO | 训练（在线） | 用当前策略生成回答、当场拿反馈，滚动做 DPO | 需要持续改进且分布会变的场景 | 同上 |
| Contextual Bandit | 在线决策 | 按上下文选动作（选排序 / 选 prompt / 选模型），用即时奖励更新 | 推荐、排序、路由 | 算法公开；开源实现见 Vowpal Wabbit，云厂商的推荐 / 实验服务多为商业托管形态 |
| FTRL | 在线学习 | 跟随正则化领导者 + 稀疏特征在线更新 | 广告 CTR、风控 | 算法公开；开源实现见 Vowpal Wabbit |
| Constitutional AI | 自反馈 | 模型按一组书面原则自评并修订，再用 AI 反馈做 RL | 安全与价值观对齐 | 方法公开（论文），无产品许可 |
| Self-Refine | 自反馈（推理时） | 生成 → 自我批评 → 重写，迭代若干轮，不改权重 | 生成质量兜底 | 方法公开（论文） |
| Self-Play | 自反馈（训练时） | 自己出题自己解，用可验证结果作奖励 | 可验证环境（代码、数学、博弈） | 方法公开（论文） |
| LLM-as-Judge | 评估器 | 用强模型按 rubric 打分，替代大部分人工评估 | 评估预算受限的团队 | 方法公开；可自建，也可买评估服务 |
| HITL / Active Learning 平台 | 数据生产 | 任务队列 + 标注 UI + QA 审核 + 主动挑高价值样本 | 关键决策点必须有人 | 开源自托管与商业 SaaS 并存（开源代表见下方 Label Studio 一行） |
| Statsig / GrowthBook | 实验与分流平台 | 把分流、假设检验、指标口径产品化，实验从「自研统计」变成「配置」 | 需要常态化跑实验的团队 | Statsig：商业 SaaS（有免费档）；GrowthBook：开源自托管 + 商业云 |
| Langfuse | LLM 观测与评估平台 | 把每次调用的输入输出、成本、评分沉淀成可查询的 trace | LLM 应用团队 | 开源核心 + 商业云 / 企业版 |
| Arize | 模型与 LLM 漂移监控 | 用参照分布比对线上特征与输出的漂移，越界即告警 | 有稳定在线流量的团队 | 商业平台（SaaS / 企业版） |
| Prometheus + Grafana | 基础设施指标与告警 | 周期拉取（pull）时序指标，按规则触发告警与看板 | 任何有服务在跑的系统 | Prometheus（Apache-2.0）+ Grafana（AGPLv3），均有商业托管版 |
| Label Studio | 反馈标注与审计 | 任务队列 + 可定制标注 UI + 质检规则，把人工反馈变成结构化样本 | 需要人工标注 / 复核的团队 | 开源（Apache-2.0），另有企业版 |

这些候选分五**族**。族的切分标准是**闭环的形状**（反馈从哪来、经过什么、多久回到系统），而族 2 内部还留着一条按**奖励来源**切的分界——奖励来源正是 §7.3.1 的第一条机制，所以这一族要再分两支：

- **族 1 测量型**（A/B 测试、Interleaving、CUPED、Eval-Driven Development）——不改变模型，只改变「你知道什么」；它的工具实现就是实验平台（Statsig / GrowthBook）、LLM 观测与评估平台（Langfuse / Arize）与基础设施指标层（Prometheus + Grafana）。这一族的**许可与商业模式差异最大、锁定也最深**：换训练算法改的是训练代码，换实验平台要重导分流标识与历史指标口径。
- **族 2 离线训练型**（RLHF、DPO、IPO、KTO、GRPO）——把反馈变成权重，一轮闭环以**天–周**计，反馈的**延迟在这一族是设计特征而不是缺陷**。族内按输入形态分两支：

  - **族 2a 偏好驱动**（RLHF、DPO、IPO、KTO）——输入是**已经收集好的偏好标签**，成本付在采集期；
  - **族 2b 可验证奖励驱动**（GRPO）——输入是一段不依赖模型的**判定函数**，样本必须在**训练时用当前策略现采**（§7.3.1 与 §7.4），成本因此压在训练期而不是采集期；
- **族 3 在线型**（Contextual Bandit、FTRL、Online DPO）——反馈直接进入策略或参数，动作与学到的结论在同一时间尺度上；
- **族 4 自反馈型**（Constitutional AI、Self-Refine、Self-Play）——把「人」替换成书面原则、自我批评或可验证环境；
- **族 5 供料与验收型**（HITL 平台、LLM-as-Judge、Active Learning）——为前四族生产数据、评估结果；这一族的平台实现以 Label Studio（开源自托管）为典型。

同族内部可以逐项替换（把 DPO 换成 IPO，改的是一个损失函数项；把 KTO 换成 DPO，改的是数据采集方式）；族 2 的**跨支替换**（2a ↔ 2b）比这重一档——它要重建的是采集能力，从「组织人写偏好」换成「写判定函数 + 训练期采样」；跨族替换要动的是**闭环的形状**——离线族换成在线族，要新建一条从决策日志到参数更新的实时通路；换成自反馈族，要把「谁来定义好」从标注规范改写成可执行的判定函数。**先分族再选，能省掉一半比较。**

### 7.3 机制差异：为什么它们表现不同

#### 7.3.1 奖励信号从哪来：可验证性决定噪声底噪与能力上限

**机制是什么**：训练类方案的全部行为由「奖励从哪里来」决定。奖励可以是人写的偏好、一个学出来的模型、一段可执行的判定函数，或者模型自己按书面原则的评判——四者的噪声结构、造假空间与采样成本完全不同。

**实现差异**：

| 奖励来源 | 代表 | 噪声来源 | 可否被优化目标「钻空子」 | 采样边际成本 |
| --- | --- | --- | --- | --- |
| 人类偏好 | RLHF / DPO | 标注者分歧、疲劳、位置偏差 | 少见（人不易被系统性欺骗） | 高（每条都要人） |
| 学出来的奖励模型 | RLHF 第二阶段 | 奖励模型自身的泛化误差 | **是**（reward hacking） | 低（推理即可） |
| 可验证函数 | GRPO / Self-Play | 判定规则的漏洞、覆盖不全 | 是，但空子会以「测试通过、场景不对」的形式暴露 | 极低 |
| 书面原则 + 模型自评 | Constitutional AI | 原则的表述歧义、自评模型与被评模型同源 | 是（模型学会了顺着原则的表面措辞写） | 低 |

**由此必然导出的性质**：因为 RLHF 的奖励来自一个**学出来的**模型，所以它优化的对象是「奖励模型认为好」，而不是「人认为好」——这两个目标只在奖励模型的泛化误差范围内重合。于是必然导出两件事：一是策略会主动寻找奖励模型打分高但人并不喜欢的输出（reward hacking），二是**奖励模型的质量上限就是策略的质量上限**，再多算力也跨不过去。也正因为如此，RLHF 必须外挂 KL 惩罚把策略拴在参考模型附近——KL 的作用不是「防止过拟合」，而是**限制策略能走多远，从而限制它能找到多少奖励模型的漏洞**。

反过来，因为 GRPO 在可验证任务上用一段不依赖模型的函数给奖励，奖励里没有人偏好带来的噪声，也不存在「奖励模型被欺骗」这一层，所以它不需要**用 KL 项去兜奖励模型的漏洞**——KL 在 RLHF 里防的是策略钻奖励模型的空子，没有奖励模型就没有这个空子。但这不等于 GRPO 没有 KL：GRPO 的原始目标里仍带 β·D_KL(π_θ‖π_ref) 一项（【公开】DeepSeekMath, arXiv 2402.03300, 2024），参考模型也仍在训练时驻留（见下表），KL 在这里的作用退化为「限制策略偏离基座过远」。把 KL 项整个去掉的是 DeepSeek-R1 在 RL 阶段的设定（【公开】DeepSeek-R1 技术报告, 2025，可自行核验其报告），属于「奖励完全来自规则判定」之后才成立的一步选择，不是 GRPO 这个算法本身的定义。同一个机制立刻给出它的边界：**判定函数写得出来的任务，它才能用**；答案无法自动判对错的任务（写作、共情、风格）上，规则给不出奖励，只能退回用另一个模型打分——此时它退化成 RLHF 的一个变体，reward hacking 的风险原样回来。

**公开证据**：从人类偏好学奖励的原始工作见 Christiano 等（【公开】NeurIPS 2017）；三段式 SFT → 奖励模型 → PPO 的规模化验证见 InstructGPT（【公开】Ouyang 等, 2022），该论文同时报告标注员与研究人员之间的偏好一致率只有七成量级——这正是「人类偏好本身有噪声」的直接证据。Constitutional AI 用书面原则替代人类标注见 Bai 等（【公开】arXiv 2212.08073, 2022）；GRPO 由 DeepSeekMath 提出（【公开】arXiv 2402.03300, 2024），并在 DeepSeek-R1 上用于推理任务（【公开】DeepSeek-R1 技术报告, 2025）。可自验的判定方法：把你的奖励来源换成一段最朴素的规则（如「必须能通过编译」），看训练曲线是否还能收敛——收敛得越顺，说明此前的人工偏好大半在替这条规则打工。

**失效条件**：当任务没有可自动判定的正确答案、且业务又对风格高度敏感时，可验证奖励退场；此时不应勉强造规则，而应改用成对偏好并把注意力放在标注一致性（双标 Kappa）上。

#### 7.3.2 中间模型：显式奖励模型与隐式奖励的必然代价

**机制是什么**：偏好数据要变成参数更新，中间要不要经过一个独立的「打分模型」，决定了工程形态与失败模式。

**实现差异**：

| 方案 | 训练时驻留哪些模型 | 是否需要在线采样 | 奖励在哪 | 主要失败模式 |
| --- | --- | --- | --- | --- |
| RLHF | 策略 + 参考 + 奖励模型 + critic | 需要（on-policy） | 奖励模型里（显式） | 奖励模型被钻空子 |
| GRPO | 策略 + 参考（无 critic、常无奖励模型） | 需要，且每条 prompt 多采样 | 规则或组内相对（显式但廉价） | 组内基线不稳、规则有漏洞 |
| DPO | 策略 + 参考 | **不需要** | 策略与参考的对数比里（隐式） | 偏好数据分布过时 |
| KTO | 策略 + 参考 | 不需要 | 同上，但标签是单点 | 缺少「相对谁」的信息 |
| IPO | 策略 + 参考 | 不需要 | 同上，加恒等约束 | 约束过强导致学不动 |

**由此必然导出的性质**：因为 DPO 把奖励隐式地表示成「策略相对参考模型的对数比」，所以它不需要单独训奖励模型，也不需要在线采样——整个训练从「四个模型 + 一个 RL 循环」塌缩成「一个监督式损失」。这直接导出一个可推算的结论：**在同等算力下 DPO 能训更大的基座模型**，因为它的显存占用大致是 RLHF 的一半量级（【推算】，按训练时驻留模型数 4 → 2 线性推算，未计入优化器状态等常数项）。代价是这个隐式奖励只在**你收集偏好的那个分布上**有效：一旦策略偏离该分布，对数比的估计不再可靠，这就是 DPO 对偏好数据质量与覆盖度格外敏感的原因——它不是训练不稳，是**它信任你的数据**。

反过来，因为 RLHF 有一个显式的奖励模型，它可以在训练中持续从当前策略采样的新分布上打分（on-policy），所以它在探索新行为上更强——代价是要维护四个模型与一个 RL 循环的稳定性。这两条是一对：**RLHF 用工程复杂度换分布适应性，DPO 用分布适应性换工程简洁**。

再推一步：因为 KTO 的标签是单点（好 / 不好）而不是成对，它丢失了「相对于谁」的信息，所以它必然在「全部回答都还不错」的分布上区分度低；但同一个原因让它可以**直接消费产品里已经存在的点赞点踩日志**，采集成本从「专门组织标注」降到「顺手记录」。这不是精度换成本的折中，而是**数据可得性换区分度**——很多时候后者才是项目能不能启动的分界线。

**公开证据**：DPO 见 Rafailov 等（【公开】NeurIPS 2023）；IPO 指出 DPO 在偏好数据可分时倾向于把 chosen 与 rejected 的差距拉到最大（过拟合），并提出恒等映射的修正见 Azar 等（【公开】arXiv 2310.12036, 2023）；KTO 用前景理论把单点标签映射为效用见 Ethayarajh 等（【公开】arXiv 2402.01306, 2024）；Online DPO 用当前策略在线生成回答并获取反馈见 Guo 等（【公开】arXiv 2402.04792, 2024）。可自验的判定方法：用一批**旧模型**的偏好对重跑 DPO，看它在**新模型**的输出上是否仍能把 chosen 排在前面——排不动就说明分布已经过时。

**失效条件**：当偏好数据由当前策略之外的模型生成、且其间已经过至少一次基座换代时，DPO 的推理性假设不成立，应改走 Online DPO 或 RLHF 重新采样。反之，当任务根本不需要「新行为」、只需要「更稳定地做对已知的事」时，RLHF 的分布适应性是纯成本。

#### 7.3.3 反馈到参数的时延：能修漂移，还是只能修能力

**机制是什么**：从「用户产生一个反馈」到「系统行为因此改变」，中间的时延决定了这条闭环能修复哪一类问题。这是一个纯粹的时延问题，不是精度问题。

**实现差异**：

| 方案 | 反馈到行为的时延 | 改变了什么 | 能修的 | 修不了的 |
| --- | --- | --- | --- | --- |
| FTRL / Contextual Bandit | 秒–分钟（一个决策周期） | 决策策略（选哪个动作） | 分布突变、长尾 query 增多、某数据源当天失败 | 写作质量、推理深度 |
| Online DPO | 小时–天 | 模型权重 | 最近一周内新增的错误模式 | 当次会话里的错误 |
| 离线训练（RLHF / DPO / GRPO） | 天–周 | 模型权重 | 长期能力：理解、风格、工具使用 | 今天出现的漂移 |
| A/B 测试 | 天–周（受最小样本量约束） | 不改变系统，只改变认知 | 「哪个版本更好」这个问题 | 任何系统行为 |
| Self-Refine | 秒（推理时） | 这一次的输出 | 本条回答的明显缺陷 | 模型下一次还会犯同一个错 |

**由此必然导出的性质**：因为离线的偏好训练必须等「一批数据攒够 → 一轮训练 → 一次评估 → 灰度」，端到端时延以天计，所以它**在结构上无法修复今天出现的坏结果**。把漂移类问题（某类 query 突然激增、某个上游数据源今天返回空、某个客户的语料分布异常）交给离线闭环，结果一定是「模型整体变得更好用，但今天的坏结果要等到明天才有人修」。反过来，因为 bandit 在每一个决策点都更新，它能在分钟级吸收分布变化，但它只能学「选哪个」（排序、选 prompt、选模型、要不要检索），**学不会「怎么写」**——这是两种闭环必须并存而不是互相替代的根本原因。

再推一步：因为反馈信号本身可能带滞后（留存、续费、退款、人工质检结果要等到次日或月末），所以凡是目标指标带滞后的场景，在线闭环拿不到即时奖励，bandit 会退化成「用近似的即时信号（点击、采纳）去代理长期指标」，而这个代理本身可能把系统引偏（点了不等于满意）。此时正确做法是把在线闭环限制在**与长期指标方向一致**的代理信号上，并单独用离线评估监控长期指标——两套信号不能互相替代，只能互相校验。

**公开证据**：FTRL-Proximal 的稀疏特征在线学习实现见 McMahan 等（【公开】KDD 2013，广告点击率预测）；LinUCB 的上下文老虎机形式化见 Li 等（【公开】WWW 2010，个性化新闻推荐）；交叉展示（Interleaving）比 A/B 测试同灵敏度下更省流量，见 Radlinski 等（【公开】CIKM 2008 及同系列工作）。实验设计与最小样本量的系统论述见 Kohavi 等（【公开】《Trustworthy Online Controlled Experiments》, Cambridge, 2020）。可自验的判定方法：统计「从用户点踩到线上行为改变」这件事在你的系统里实际花了多久——如果团队答不出这个数，说明这条闭环没有被度量过。

**失效条件**：当你的流量规模小到分钟级只有个位数反馈时，在线闭环的方差会吞掉信号，此时应当把反馈攒成批，走离线路线——**在线学习的收益随反馈频率增长，频率不够时它只是噪声放大器**。

#### 7.3.4 反馈的分配方式：成对、单点、组内相对、绝对

**机制是什么**：一条反馈是一份信息。「成对比较」「单点好坏」「组内相对」「绝对打分」四种标签形态，决定了标注的难度、噪声水平、以及一次标注能带来多少信息量。

**实现差异**：

| 标签形态 | 代表 | 标注者要做的事 | 一次标注的信息量 | 主要偏差 |
| --- | --- | --- | --- | --- |
| 绝对打分 | 早期 RLHF 打分、主观评测 | 给单条回答标一个分数 | 低（要跨人校准刻度） | 标注者各自的尺度不同 |
| 成对偏好 | RLHF / DPO / IPO | 从两条里选一条更好 | 中 | 长度偏差、位置偏差 |
| 组内相对 | GRPO | 对一组回答分别判对错，由组内均值做基线 | 高（一次判 N 条） | 组太小则基线不稳 |
| 单点好坏 | KTO | 只判「这条行不行」 | 低（无参照） | 缺相对信息，区分度弱 |

**由此必然导出的性质**：因为绝对打分要求标注者在心里维持一把跨人一致的尺子（什么是 7 分、什么是 8 分），而人对绝对刻度的校准远不如对相对比较的校准稳定，所以实践中偏好对的一致率高于绝对打分——这是 RLHF 与 DPO 都建立在偏好对上、而不是绝对分数上的直接原因。Bradley-Terry 模型正是为「把成对比较转成可用的分数」而存在的（【公开】Bradley & Terry, Biometrika, 1952）。代价是成对数据要求同一个 prompt 下有两个回答，**采集成本相对单点直接翻倍**，而且在两个回答质量接近时标注噪声会急剧上升（此时「谁更好」几乎是抛硬币）。

因为 GRPO 用**同一 prompt 下的组内均值**作为基线，所以它不需要跨 prompt 校准奖励尺度——这正是它能够使用规则奖励（不同题目的难度天然不同，分数不可比）而 RLHF 不能的直接原因：规则给的原始分跨题目不可比，但组内相对可比。反过来这也解释了 group size 为什么重要：基线只有在组内样本足够多时才稳定，N 太小时均值本身带噪声，优势估计就不可信。

因为 KTO 用前景理论里的「损失厌恶」给单点标签定权（坏结果比好结果带来更大的效用落差），所以它对「负面反馈稀少但重要」的产品很合适——用户更愿意点踩而不愿意点赞，这种分布下 KTO 的设定比 DPO 更贴合真实日志。代价是它的信号量天然少于成对偏好。

**公开证据**：成对比较的统计基础见 Bradley & Terry（【公开】Biometrika, 1952）；损失厌恶见 Kahneman & Tversky 的前景理论（【公开】Econometrica, 1979），KTO 直接借用该框架；LLM 评委与人类偏好的一致率在 MT-Bench 系列工作中报告为超过 80%（【公开】Zheng 等, 2023），与人与人之间的一致率接近——这个数字是「用模型替代大部分人工评估」的可行性依据，但它只在 rubric 明确、且任务不需要细粒度区分时成立。可自验的判定方法：把你手上两个回答都换成同一份（复制成两条），看标注者能否一致地判出「打平」——判不出来的那一档，就是标注噪声的下限。

**失效条件**：当两个被比较的回答来自不同模型、不同长度或不同格式时，成对偏好会带上长度与呈现偏差。此时必须做长度控制与位置交换，否则模型学到的是「长 / 格式漂亮 = 更好」，而不是「更有用」。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
总成本 ≈ 采集成本   f(反馈条数 × 每条成本)
        + 评估成本   g(人工比例, LLM 评估比例, 抽样复核率)
        + 训练成本   h(基座规模, 训练时驻留模型数, group size N, 采样次数)
        + 在线探索成本 i(被分流去尝试的流量占比 × 实验时长)
        + 护栏与回滚成本 j(灰度层数, 回滚窗口, 值班能力)
```

**各族的主导项与隐性成本**（族 2 按 2a / 2b 两支分列）：

- **族 1 测量型**：主导项是**流量成本**（被分流去实验的那部分用户，拿到的是你预期更差或不确定的版本）；隐性成本是实验平台本身（分流一致性、指标口径、幂等分析）。
- **族 2a 偏好驱动离线训练**：主导项是**采集与标注**（每条偏好都要人），训练算力是第二项；隐性成本是**奖励模型被钻空子后的返工**——它不在预算表里，但一次严重的 reward hacking 会让整轮训练作废。
- **族 2b 可验证奖励驱动离线训练（GRPO）**：采集期成本接近零（奖励由判定函数现算，不需要人），主导项因此**反转到训练期**——每条 prompt 要用当前策略先采一组回答再逐条判分，生成本数按本节末的【推算】约为 DPO 的数倍；隐性成本是**判定函数的维护与覆盖**——函数写得越窄，模型越会去轰它没盖到的地方，这是 2b 版的「返工」。
- **族 3 在线型**：主导项是**探索成本**（持续留出一部分流量做探索，不按当前最优决策）；隐性成本是**长期指标的滞后**——短期代理指标好转而长期指标恶化的情形，只有在月度复盘时才看得出来。
- **族 4 自反馈型**：采集成本接近零，主导项变成**推理算力**（Self-Refine 每次多若干轮生成）或**训练算力**（Self-Play 需要环境与大量采样）；隐性成本是**同源偏差**——用同一个模型评判自己，偏差不会被发现，只会被放大。
- **族 5 供料与验收型**：主导项是人工预算与 LLM 评估账单；隐性成本是 rubric 的维护——rubric 一旦与实际业务目标脱节，评估会稳定地给出「通过」，而线上指标在下滑。

注意两类成本的增长方式**根本不同**：主导项随样本量增长（可以按条计价、可以预算），隐性成本随**轮次与迭代频率**增长（每一轮训练都可能触发一次返工）。所以真正要比的不是「哪个更贵」，而是「哪一个的隐性成本落在我的团队能力范围内」——一个没有评估集、没有回归门禁的团队上 RLHF，等于把「训练一版废一版」变成常态。

**【推算】同等算力下能训多大的基座**：RLHF 训练时需要同时驻留策略、参考、奖励模型与 critic 四套权重，DPO 只需策略与参考两套（GRPO 通常也是两套，但无 critic）。按驻留模型数线性推算，DPO 的显存需求约为 RLHF 的一半量级（【推算】，不含优化器状态与激活等常数项）。这条推算的含义是：在固定算力预算下，**选 DPO 往往意味着能训更大的基座，而基座规模对最终效果的贡献通常大于对齐算法之间的差异**——这是「先用 DPO 上线，再看要不要上 RLHF」这条常见路径的数学理由，而不是流行度理由。

**【推算】GRPO 的采样量**：GRPO 对每个 prompt 采样一个 group（设 group size N = 8）并逐条打分，而 DPO 的一条偏好对包含 2 个回答。按回答数之比推算，GRPO 在训练期的**生成本数约为 DPO 的 4 倍**（【推算】，8 / 2）。但两者的算力位置不同：DPO 的偏好对可以离线、用更便宜的模型批量生成后长期复用，GRPO 的采样必须在训练时用当前策略完成——**一个把成本压在采集期，一个压在训练期**，选型时要看的是哪一期的算力更富裕。

**【推算】A/B 的流量成本**：若一次实验分走 10% 的流量、持续两周，则这两周内这 10% 的用户拿到的是不确定版本；如果实验目标是检测一个较小的提升，最小样本量随「想检测的提升幅度」的平方反比增长（【公开】方法见本节 §7.5「阈值依据」中的 A/B 最小样本量一条；系统论述见 Kohavi 等, 2020），小改动要测出来需要成倍的样本与时间。CUPED 用实验前同一用户的历史指标做协变量调整来降低方差（【公开】Deng 等, WSDM 2013），从而减少所需样本量——**它的收益不是提高精度，是把样本量需求降下来**，在小流量场景里这直接决定实验能不能做成。

**【经验】LLM 评估与人工的相对成本**：行业普遍实践给出的量级是「用 LLM 做评估的成本比人工低一到两个数量级」（【经验】）。这个量级高度依赖两家供应商的定价、你的任务长度与抽样复核比例，不要当常数用。可操作的判定方法是先跑一个小样本：取 200 条真实样本，人工与 LLM 各评一遍，既得到一致率，也得到真实单价——一致率低于你的任务可接受水平时，唯一的替代方案是提高人工抽样比例，而不是换一个判分模型。

### 7.5 决策树（每个分支都要有阈值依据）

```
第 0 层（硬约束，先问）：同一个错误会不会重复发生、且代价不可接受？
├─ 会 → 必须有一条能改权重的闭环（族 2 或族 3），只做测量不够
└─ 不会 → 族 1（测量 + 评估集）即可，先别动权重
第 1 层：这个任务的答案能不能由一段不依赖模型的函数判对错？
├─ 能 → 用可验证奖励 + 组内相对（GRPO 类）；人工偏好在这里是浪费
│        └─ 并定下 group size N（依据见下）
└─ 不能 ↓
第 2 层：你手上现成的反馈是什么形态？
├─ 只有点赞 / 点踩（单点） → KTO（直接消费已有日志）
├─ 有成对偏好 → 进入第 3 层
└─ 什么都没有 → 回到族 1 与族 5：先建采集与评估集，不要跳到训练
第 3 层：偏好数据是不是由**当前这一代**模型生成的？
├─ 是（on-policy） → DPO
├─ 不是（旧模型 / 别家模型） → Online DPO 或 RLHF（重新采样）
└─ 是但噪声大 / DPO 已过拟合 → IPO
第 4 层：你要修的是「今天的坏结果」还是「长期能力」？
├─ 今天的（分布突变、上游故障、长尾激增） → 族 3：在线决策，不动权重
└─ 长期能力 → 族 2，配 A/B 灰度与回滚
     └─ 若是用 A/B 来验收：先算 A/B 最小样本量（依据见下）；算出来的量级跑不动 → 换 CUPED / Interleaving，或改用离线评估集做门禁
第 5 层：人工标注预算能覆盖全部需要的样本吗？
├─ 覆盖不了 → LLM-as-Judge + 抽样复核 + Active Learning 挑高价值样本
└─ 覆盖得了 → 人工标注 + 双标一致性（Kappa）管控
```

**阈值依据**：

- **「同一错误会不会重复、代价可不可接受」（第 0 层）**：无阈值，硬约束。判定方法：把最近 30 天的事故与投诉按「同类错误」归并，看 Top 3 是否重复出现。重复出现的错误不会因为测量做得更细而消失，只会被更精确地记录——**测量与修复是两件事，不能互相替代**。
- **「答案能否由不依赖模型的函数判定」（第 1 层）**：二值判断，做法是**试着把判定函数写出来**——单元测试、数值比对、编译通过、schema 校验、SQL 能否执行。写得出来就走可验证奖励路线。写不出来就不要造规则，因为一条覆盖不全的规则会训练出「专轰漏洞」的模型。
- **「group size N」（第 1 层走 GRPO 类分支后的训练参数）**：不设固定值，因为它由「同一 prompt 多次采样的奖励方差」决定（奖励方差大就需要更大的 N 才能把组内均值变成稳定基线）。可操作的判定方法是画一张「N 对组内均值标准差」的曲线，取曲线走平处；主文件 §2.2.3 说的「组内相对」正是这层机制，没有普适最优值。
- **「单点还是成对」（第 2 层）**：由你已有的日志形态决定，不是自由选择——成对偏好要求同一个 prompt 下存在两个可比较的回答，单点只要一个动作。两者的采集成本差一个量级，这是它成为第 2 层判据的原因。
- **「什么都没有 → 先建采集与评估集」（第 2 层的第三分支）**：这一支没有可算的阈值，依据是**依赖顺序**而非数字——族 1 与族 5 的产物（评估集、标注流水线、日志埋点）正是族 2 / 族 3 / 族 4 的输入，跳过它们直接训练等于没有任何判据可用（这也是 §7.7「跳过评估集直接上 RLHF」这条反模式的来源）。可操作的判定方法是问「我本周能不能拿出一份 200 条、带标签、与训练数据不同源的评估集」；答不出就先落族 1。
- **「是不是当前这一代模型生成的」（第 3 层）**：**刻意不用天数**。判定方法是用旧偏好对重跑一次 DPO，看它在新模型输出上还能不能把 chosen 排前；排不动即判定为分布过时。用「两周」这类天数做阈值是伪精确——同一个基座相隔两周的数据通常仍可用，换基座或经过一轮大版本对齐后，隔三天的数据也可能失效。
- **「噪声大 / 已过拟合 → IPO」（第 3 层的第三分支）**：阈值是**偏好对的可分离程度**，不是某个误差数字。IPO 的提出动机正是 DPO 在偏好对可分时把 chosen 与 rejected 的对数比差距一路拉满、从而过拟合（【公开】Azar 等, arXiv 2310.12036, 2023），所以判定方法是看训练集上两类样本的得分分布是否几乎不重叠、且验证集指标不再上升——两项同时成立就属于这一支。若噪声来自标注者本身（连复制成两条的同一份回答都判不出「打平」，见 §7.3.4 的自验方法），则先修数据质量，换算法解决不了。
- **「今天的坏结果 vs 长期能力」（第 4 层）**：不是数字阈值，是**时间尺度是否匹配**。判定方法是问「这个错误的成因是不是今天才出现的」（上游数据源变了、流量分布突变、某客户语料异常）——这类成因在离线训练完成后往往又变了，所以即使训练再充分也不会被自动修掉；模型一直不会做的事才适合进训练队列。这条依据的量化形式是 7.3.3 给的时延对比：离线闭环端到端以**天–周**计，而漂移的产生频率在**天以内**，两个量级不匹配时只能换闭环形状，调参弥补不了。
- **「A/B 最小样本量」（第 4 层「长期能力 → 配 A/B 灰度」分支的验收参数）**：不是经验常数，由 power analysis 计算——给定 baseline 指标、想检测的最小提升、显著性水平 α（通常取 0.05）与统计功效 1 − β（通常取 0.8）可算出最小样本量（【公开】方法与系统论述见 Kohavi 等, 2020）。它随「想检测的提升幅度」平方反比增长，这就是「小改动测不出来」的数学原因，也是判断一次实验是否值得做的依据。
- **「跑不动 → 换 CUPED / Interleaving 或退回离线评估集」（第 4 层的退路分支）**：「跑不动」不是一个样本量数字，而是**算出来的实验时长超过了业务决策周期**——把最小样本量除以日流量得到需要跑的天数，再与「这个结论最晚什么时候要被用上」比，超期即判跑不动（这与 §7.3.3 的时延对比是同一条判据：闭环修不了某个问题，通常不是精度不够，而是它的时延量级赶不上问题出现的频率）。退路按代价排序：先用 CUPED 做实验前协变量降方差（【公开】Deng 等, WSDM 2013），再用 Interleaving 换更省流量的灵敏度（【公开】Radlinski 等, CIKM 2008）；两者都还不够时，就把这次改动交给离线评估集做门禁，放弃线上实验——**放弃一次实验的代价，小于用一个无结论的实验去占着流量**。
- **「LLM 评委可信度」（第 5 层）**：用一致率自验而非采信宣传数字。MT-Bench 报告强模型评委与人类偏好一致率超过 80%（【公开】Zheng 等, 2023）；在你的任务上跑 200 条自测，若一致率显著低于这个水平，就不能把人工比例压到 10% 以下。
- **「抽样复核率」（第 5 层）**：由「一致率 × 单条后果」共同决定，没有统一数字。可操作的起点是把复核设计成**按批放行**：先全量人工复核 200 条建立基准，之后按 10% 抽样，一旦抽到判错就回到全量——这条规则的价值是把复核成本从常数变成「只在出问题时变贵」。
- **「人工标注预算能否覆盖所需样本」（第 5 层）**：这一层的阈值不是拍出来的比例，而是**成本函数算出来的比值**：把「需要标注的样本条数 × 单条人工成本」与预算相除，比值大于 1 就是覆盖不了，落到 LLM-as-Judge + 抽样复核那一支。单条成本的量级见 §7.4 的【经验】（LLM 评估比人工低一到两个数量级），可操作的起点是先取 200 条真实样本人工评一遍，拿到自己任务上的真实单价再乘总条数——这也正是 §7.4 那条【经验】在这里的落点。反过来，覆盖得了的那一支的前提是标注团队自己的双标一致率达标：先做 200 条双标测量，一致率低于模型评委的水平（80% 量级，【公开】Zheng 等, 2023）时，加人不提高数据质量，只会把噪声买得更贵。

**这棵树刻意不覆盖的分支**（以及为什么）：

- **「要不要上 Constitutional AI」**：它替换的是**标注环节**，不是训练环节（用 AI 反馈做 RL 时仍走 RLHF 的那套流程）。判定方法：问「我有没有一份可执行、可争论的书面原则」——没有这份原则就上 Constitutional AI，等于让模型自己决定什么是对的，偏差会被系统性地放大而不是被发现。
- **「要不要做自我进化（Self-Improvement）」**：只有当环境能给出**独立于模型**的判定（编译器、测试、对局胜负）时，自我进化才有明确信号。判定方法：问「谁来判断这一轮比上一轮好」，答案若是「模型自己」，那就是同源偏差而非进化。
- **「要不要做在线学习」**：由反馈频率决定，而不是由技术偏好决定（【经验】：分钟级反馈数是个位数量级时，在线更新的方差会吞掉信号）。频率不够时把反馈攒成批走离线，成本更低且更可复现。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 数学 / 代码 / SQL 等可验证任务 | GRPO 类（可验证奖励 + 组内相对） | RLHF | 人工偏好在此是浪费：噪声大、单条贵，而正确答案本来就能免费判定 |
| 通用对话质量、风格、安全 | 偏好对训练（DPO 起步） | RLHF（要探索新行为时） | 无成对标签的 KTO 在「都不错」的分布上区分度低 |
| 只有点赞点踩的产品日志 | KTO | 先补采集成对偏好 | DPO 需要成对数据，而你没有；为了拿成对数据而新造标注流程，成本往往不划算 |
| 分布快速漂移（时效性问答、新闻、热点） | Contextual Bandit / FTRL（不动权重） | Online DPO | 离线训练的时延以天计，注定修不了今天的坏结果 |
| 偏好数据来自旧模型 | Online DPO | RLHF 重新采样 | 直接上 DPO 会学到已过时的排序偏好 |
| 偏好数据噪声大、DPO 过拟合 | IPO | 先修数据质量 | KTO 不用成对但不解决噪声 |
| 安全 / 价值观对齐 | Constitutional AI（原则 + AI 反馈） | 人工红队 + 偏好训练 | 纯人工标注在此扩不起规模，且原则一旦书面化就可复用 |
| 可自动判分的环境（代码、博弈） | Self-Play | 人工偏好 | 自我博弈的样本由环境免费判分，人工标注是纯成本 |
| 单次回答质量兜底（不改权重） | Self-Refine | 更好的基座模型 | 它只改这一次输出，模型下次还会犯同样的错 |
| 评估预算有限 | LLM-as-Judge + 抽样复核 | 全人工 | 全人工的一致性并没有显著更高，但成本高一个量级 |
| 受监管 / 需审计的场景 | Eval-Driven Development + 全链路留痕 | 无 | 无留痕的闭环无法在事后回答「这版模型为什么上线」 |
| 小流量、想缩短实验周期 | CUPED + Interleaving | 常规 A/B | 流量不够时常规 A/B 跑不出显著结果，实验永远「无结论」 |

**常见组合**（每条注明职责边界与运维代价）：

- **族 1 + 族 2（测量 + 离线训练）**：评估集与 A/B 负责判定「新版是否更好」，离线训练负责产生新版。边界是：**测量不改权重，训练不改判据**——判据归业务，一旦训练槽位有权改判据，指标就会被优化到好看而不是有用。运维代价是两套体系都要维护：评估集的持续更新（否则它会被模型逐渐过拟合）与训练流水线的回归门禁。
- **族 3 + 族 1（在线决策 + 测量）**：bandit 负责分钟级吸收分布变化，A/B 负责在长周期上回答「这条策略是否真的更好」。边界是：在线部分只允许动**可逆、可回退的决策**（选哪个检索源、选哪个 prompt 模板），一旦它开始改权重，回滚就不再是秒级。运维代价是护栏指标与自动回滚必须真的接通——没有自动回滚的在线优化，等于把一次配置错误放大成全量故障。
- **族 5 + 族 2（供料 + 训练）**：LLM-as-Judge 做初筛、人工做抽样复核、Active Learning 挑高价值样本。边界是：**只有人能定义 rubric，模型只能执行 rubric**。运维代价是 rubric 要版本化——业务目标变了而 rubric 没改，模型会稳定地在优化一件已经不重要的事。
- **族 4 + 族 2a（自反馈 + 偏好训练）**：Constitutional AI 生成初版对齐数据，人工偏好做最终校准。边界是：自反馈负责扩量，人工负责定标；两者不能互相替代。运维代价是要维护那份书面原则，并定期检查模型是否学会了「顺着原则的表面措辞写」而不是遵守原则的实质。
- **全族 + 反馈湖（数据基础）**：所有族的输入都来自同一份 Feedback Lake。边界是：湖负责**采集、清洗、脱敏、归因**，各族只消费加工后的样本。运维代价是 schema 治理与漂移检测——反馈字段一旦变更而没有版本管理，下游所有训练流水线会同时静默失效。

组合的原则只有一条：**每加一件，都要说清它负责哪一段，以及它挂掉时谁来兜底**。bandit 挂了，兜底是回退到固定策略（此时只是失去适应性，不影响正确性）；LLM-as-Judge 挂了，兜底是提高人工抽样比例（此时成本上升但结论仍可信）；离线训练流水线挂了，兜底是**保持当前版本不动**——最坏的做法是让一条未经评估的版本顶上去。

上面 7 条判据里的「**生态与锁定**」在这一层最容易踩空。锁定点几乎全在工具类候选上：反馈湖的 schema、实验平台的分流标识、标注平台的任务格式，三者都会变成事实上的接口标准——Langfuse / Arize 上的 trace 结构、Statsig / GrowthBook 上的实验与指标口径、Label Studio 上的任务模板，一旦沉淀了百万级历史样本，**换训练算法只需改训练代码，换平台要重导数据并重建口径**。所以「先建反馈湖 + 实验平台、再选算法」这个顺序是有代价的：它把不可逆的那一半先做掉了。可操作的缓解办法是只把**平台无关的中间层**（样本 ID、时间戳、反馈类型、归因目标）定为强制 schema，把平台特有的字段放在旁路（【经验】：锁定成本随已沉淀的样本量与口径数量增长，而不随订阅费增长）。

### 7.7 选错的代价与迁移成本

**反模式：用不可验证的规则去训可验证任务之外的东西** —— 症状：为了拿到「免费奖励」，给主观任务硬写一段判分规则或 prompt，让另一个模型按它打分 → 后果：模型学会的是「怎么在这段规则下拿高分」，而规则本身覆盖不全，于是质量在规则覆盖的方向上提升、在规则之外的方向上退化，且退化不会报警 → 正确的做法：规则只用在能自动判对错的任务上；主观任务老老实实用成对偏好，并把预算花在标注一致性上。

**反模式：把测量当成修复** —— 症状：建了完善的埋点、看板、LLM 评估与漂移监控，然后认为已经很成熟 → 后果：每一个错误都被记录得更精确，但没有一条通路能改变模型行为，同一类投诉在半年后仍然是 Top 1 → 正确的做法：先问第 0 层判据「同一错误会不会重复出现」，会重复的必须有一条能改权重或改决策的闭环，测量是它前面的必要条件，不是替代品。

**反模式：跳过评估集直接上 RLHF** —— 症状：偏好数据还没攒够、评估集还没有，就先把 RLHF 流水线搭起来 → 后果：一旦出现 reward hacking，你既没有评估集判断「模型是不是变差了」，也没有回滚判据，只能靠用户投诉来发现问题，而那时损失已经发生 → 正确的做法：评估集先行，且它必须**独立于训练数据**；训练数据与评估集同源，等于用自己出的卷子给自己打分。

**反模式：在线闭环动权重** —— 症状：把用户点踩直接接进在线训练，分钟级更新权重 → 后果：单条噪声直接进参数，模型在一天之内漂到某个角落，而且**基线已经变了**——你无法判断当前的差结果是最新版造成的还是前一版造成的，回滚也失去参照 → 正确的做法：在线闭环只动可逆的决策（选检索源、选模板），要动权重走批量 + 评估 + 灰度。

**反模式：用同一个模型评估自己的输出** —— 症状：让模型按 rubric 自评，并把自评分作为训练奖励 → 后果：同源偏差被系统性放大——模型很快学会写出「让自评环节满意」的输出，而这些输出与真实用户偏好的差距不会被任何环节发现 → 正确的做法：评估器与被评模型不同源（不同模型、或不同模型 + 人工抽样），并且始终保留一条人工一致率的测量。

| 从 → 到 | 数据 / 资产迁移 | 流水线改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| RLHF → DPO | 已有的偏好对可直接复用（同格式） | 训练代码从多模型 RL 循环改为单损失 | 显存与并行策略重配（模型数约减半） | 从「调 RL 稳定性」到「调数据质量」 | 中 |
| DPO → GRPO | 偏好对形态不适用，需准备可验证奖励与采样环境 | 加采样与组内优势计算 | 训练期算力上移（生成量增大） | 从「比好坏」到「判对错」 | 中–高 |
| DPO → KTO | 成对偏好可退化为两条单点标签 | 损失函数替换 | 基本不变 | 从「构造对比」到「标注 desirability」 | 低 |
| 离线 → 在线（DPO → Online DPO / Bandit） | 需新建「决策 → 反馈」的实时通路 | 训练 / 决策服务从批改为流 | 加实时特征、护栏与自动回滚 | 从「离线评估」到「在线实验与事故应对」 | 高 |
| 人工标注 → LLM-as-Judge | 历史标注转为基准集（**最大项**：需要人工逐条建立基准） | 评估流水线接入模型评委 + 抽样复核 | 评估成本从人力转为推理资源 | 从「写标注规范」到「写 rubric 并验证一致率」 | 中–高 |
| 无反馈闭环 → 有闭环 | 历史日志需清洗、脱敏、归因为可用样本 | 埋点、清洗、训练、灰度四段全新建 | 全套（湖、流水线、A/B 平台、监控） | 跨度最大：工程 + 算法 + 产品 | 极高 |

关于迁移时机有一条容易被忽略的约束：**闭环算法的迁移几乎不能在模型已经全量在线的状态下做**，因为迁移期间新旧两套必须在同一份流量上共存（影子评估或双跑），而双跑会带来指标口径的混乱。可操作的做法是拆成三段：**先在离线评估集上比对新旧两套**（无线上影响）→ **再在小流量上灰度并行**（以护栏指标为准，不以效果指标为准）→ **最后切换并保留回滚窗口**。愿意接受这个节奏，迁移才是可控的。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 答案能自动判对错 | GRPO 类（可验证奖励 + 组内相对） | 奖励免费且无人工噪声，人工偏好是纯浪费 |
| 只有点赞点踩 | KTO | 单点标签可直接消费已有日志，采集成本降一个量级 |
| 有成对偏好、算力有限 | DPO | 无奖励模型、无在线采样，显存约为 RLHF 的一半量级 |
| 需要探索新行为、分布会变 | RLHF 或 Online DPO | 显式奖励模型支持 on-policy 采样 |
| 偏好数据来自旧模型 | Online DPO / RLHF 重新采样 | DPO 的隐式奖励只在收集偏好的分布上成立 |
| 今天的坏结果必须今天修 | Contextual Bandit / FTRL | 离线闭环的时延以天计，结构上修不了漂移 |
| 安全与价值观对齐 | Constitutional AI + 人工定标 | 原则可书面化、可复用，能扩量；但定标必须留给人 |
| 环境能自动判分 | Self-Play | 样本由环境免费判分，无需人工 |
| 评估预算受限 | LLM-as-Judge + 抽样复核 + Active Learning | 一致率超过 80% 量级时可替代大部分人工，但必须自测 |
| 受监管、需审计 | Eval-Driven Development + 全链路留痕 | 无留痕的闭环答不出「这版模型为什么上线」 |
| 小流量、要缩短实验周期 | CUPED + Interleaving | 降方差与交叉展示直接减少所需样本量 |

回到本章 7 条判据里权重最高的两条：**信号可得性**决定候选集合（能自动判对错的任务不应使用人工偏好），**反馈到参数的时延**决定闭环形状（修漂移必须走在线、修能力才走离线）。这两条回答完，成本、稳定性、生态才有讨论价值——顺序反了，讨论就永远停在「哪个算法更先进」这个跟你的场景无关的问题上。

与原文件最大的方法论差别是：原文件给的是**结论**（两张打分表 + 一张选型表），本章给的是**推导**（为什么 RLHF 必须外挂 KL 惩罚、为什么 DPO 的隐式奖励只在收集偏好的分布上成立、为什么 bandit 学不会「怎么写」）。结论会随版本与基座换代过时，推导不会——这也是 §2 核心原理与 §6 落地实践值得与本节对照阅读的原因。

> 本节小结：这些方法之间唯一真正起决定作用的差异是**「奖励从哪里来，以及它到你手里的时延有多长」**——奖励来源决定噪声底噪与能力上限（人 / 学出来的模型 / 可验证函数 / 模型自评各自带一种偏差），时延决定这条闭环能修今天的漂移还是只能修长期能力。其余维度（数据需求、稳定性、显存、成本）都是这两条的下游结果。
