## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表读起来像一道选择题：客服选显式评分、推荐选 Bandit、LLM 应用选 Eval——仿佛场景一确定，模式就唯一确定。但只要把两个"客服 Agent"放在一起看，这个表立刻失效：一个是每天几百次对话、每条都能人工看的高价值场景（该走 HITL），另一个是每天百万级对话、只有极小比例有显式打分的场景（必须走隐式信号 + 自动去噪）。同一个"场景"，正确模式完全不同。

真正做决定的是约束。反馈闭环里有六条约束反复出现，任一条不同，模式选择就会翻转：反馈**能不能自动验证**（决定你能不能绕开人）、**延迟预算是多少**（决定离线批训还是在线上更新）、**信号是否可归因**（决定反馈能否定位到具体动作）、**单位采集成本**（决定你能采多密）、**分布是否有偏**（决定要不要校正）、**团队有没有标注 / RL / 实验基础设施**（决定方案能不能落地）。

所以本节先立约束、再谈模式。下表不是选型表，而是"最容易被约束推翻的直觉"清单——当你觉得某个模式"显然更好"时，先回去看是哪条约束在替你说话。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 信号可自动验证性 | 能不能不依赖人 | 「要提升就得有人来标」——结果可自动判对错的任务（数学 / 代码）可用可验证奖励替代人工判断 【公开】（DeepSeek 用组内相对优化 + 可验证奖励训练推理模型，2024-2025） |
| 反馈延迟预算 | 离线批训还是在线上更新 | 「模型要变聪明就得分季度重训」——延迟预算压到天级时，重训周期本身就成了瓶颈 |
| 信号可归因性 | 反馈能否定位到具体动作 | 「反馈回来了就能改」——回答级的好恶定位不到"是检索错了还是生成错了" |
| 单位采集成本 | 采样密度 | 「多采一点总没坏处」——存储与治理成本随事件量上涨，采不到的信号不是免费的 |
| 分布偏差 | 要不要校正、怎么校正 | 「隐式行为是客观的」——曝光位与界面改动会让同一次点击的含义完全不同 |
| 团队与合规能力 | 方案能否落地、能否自证 | 「有反馈就该训模型」——缺 HITL 痕迹与审计记录的方案，在受监管行业不能上线 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 显式 + 隐式双通道

- **被什么约束逼出来**：愿意主动打分的用户永远是极少数，而打分最多的那批又最不代表全体；只用显式样本量上不去，只用隐式意图全靠推测。
- **结构**：两类信号进同一张事件表，用 `feedback_type` 区分；隐式信号必须连带存曝光上下文，否则事后无法做位置校正。

```sql
CREATE TABLE feedback_event (
  event_id       BIGSERIAL PRIMARY KEY,
  user_id        VARCHAR(64) NOT NULL,
  session_id     VARCHAR(64),
  turn_id        INT,
  timestamp      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  feedback_type  VARCHAR(16) NOT NULL,  -- explicit / implicit / derived
  signal         VARCHAR(32) NOT NULL,  -- rating / copy / undo / retry ...
  value          DOUBLE PRECISION,
  position       INT,                   -- 隐式信号缺它就无法做偏差校正
  model          VARCHAR(64),
  prompt_version VARCHAR(32)
);
```

- **为什么这样设计有效**：因为显式信号"稀疏但意图明确"、隐式信号"稠密但意图模糊"，两类互补，所以能用显式校准"哪些行为真的对应满意"，再用隐式覆盖显式采不到的人群；代价是两者的换算系数必须持续重估，不能一次定死。
- **代价**：两条采集链路 + 两套质量监控；每个隐式事件都要带位置与曝光上下文；同一张表混存两类信号，消费侧必须明确"哪类是标签、哪类只是特征"。
- **失效点**：当显式反馈被运营激励污染、或一次界面改版让同一行为的含义漂移时，双通道从互补反转成互斥，因为同一条事件在两种语义下给出相反标签，而校准系数还停在旧分布上。
- **真实使用**：ChatGPT 同时提供点赞 / 点踩与"重新生成 / 复制"这类行为信号 【公开】（OpenAI 产品界面，2022 起）；用点击类隐式信号做大规模在线学习有公开工程记录 【公开】（McMahan 等，KDD 2013）。

#### 3.2.2 HITL 标注平台

- **被什么约束逼出来**："什么是有帮助的回答"这类判断写不成规则，只能由人给；且金融、医疗等场景要求"人在回路"本身可举证。
- **结构**：标注是一条异步批处理流水线，"任务 → 标注 → 审核 → 一致率校验 → 偏好库"，而不是"谁有空谁标一下"。

```text
问题池 ──▶ 任务分片 ──▶ 多人重复标注（交叉 / 冗余）
                            │
            黄金集校验 ◀────┤  一致率 + 与黄金集的偏离度
                            ▼
                       仲裁（疑难样本升级给资深标注）
                            │
                            ▼
                 偏好库（preference pair / 演示 / 纠错）
                            │
                    训练侧按需取用（与训练解耦）
```

- **为什么这样设计有效**：因为人的判断能覆盖规则写不出的长尾语义，所以标注是唯一能为"价值观类目标"产出标签的通道；代价是吞吐与人力线性绑定，且质量标准完全由指南的清晰度决定。
- **代价**：吞吐上限 = 标注人力，无法靠加机器解决；需要黄金集与一致率监控这一整套"标注的质检"；指南越含糊，返工与仲裁成本越高。
- **失效点**：当指南留下歧义又没有仲裁机制时，"多标几遍"从提高覆盖反转成放大噪声，因为同一个歧义会在各标注员身上以不同方向独立地错，而一致率指标只报警、不告诉你错在哪。
- **真实使用**：通用标注平台有公开产品资料（Label Studio、Scale AI、Argilla，见 [§4.3 工具链](02-feedback-loop-section-4-sec4.md)）；把人类偏好做成可规模化三段式管线的公开方法是 RLHF 【公开】（OpenAI，2022）。

#### 3.2.3 Online Bandit（上下文老虎机）

- **被什么约束逼出来**：反馈的延迟预算极短——必须在用户等待的那几百毫秒内给出决策，无法等离线批处理；同时每个决策的收益依赖当时的上下文，没法预先算好。
- **结构**：把"探索"写进决策规则本身，用置信区间或后验采样在"当下最优"与"还没试够"之间分配流量。

```text
对每个请求（上下文 x）：
  对候选动作 a 估计收益  μ̂(a|x) 与不确定性 σ̂(a|x)
  选择  argmax [ μ̂(a|x) + α · σ̂(a|x) ]      ← 探索项随尝试次数衰减
  观测奖励 r
  在线更新 μ̂, σ̂（无需重训整个模型）
      │
      └─▶ 冷启动期必然表现差；随样本积累收敛
```

- **为什么这样设计有效**：因为探索与利用被写进同一个决策式，所以系统不需要任何离线标注就能持续获得反馈并自我修正；代价是它必须拿一部分真实流量去换信息。
- **代价**：regret（探索期少赚的那部分就是学费）；需要实时特征与低延迟打分链路；冷启动阶段的表现一定低于最优策略，业务方要能接受这段时间的指标下滑。
- **失效点**：当奖励函数与业务目标错位（用点击率当奖励，而目标是留存）时，Bandit 从"自动优化"反转成"高效地把系统推向错误目标"，因为它只会忠实、且越来越熟练地优化你给它的那一个数。
- **真实使用**：新闻推荐用上下文老虎机做在线选择的公开方法是 LinUCB 【公开】（Li 等，WWW 2010，Yahoo 新闻场景）；广告点击率预估的大规模在线学习有公开工程记录 【公开】（McMahan 等，KDD 2013）。

#### 3.2.4 Eval-Driven（评估驱动开发）

- **被什么约束逼出来**：LLM 输出没有唯一正确答案，"看起来更好了"不可复现；改动（换模型、改 prompt、调检索）随时可能让已经好了的用例回退。
- **结构**：把质量标准从人的感觉搬到一组可执行断言上，并把它挂在合并流程上——评估集是 CI 的一部分，不是上线前的临时检查。

```text
每次改动（模型 / prompt / 检索 / 工具）：
  ① 跑离线评估集  →  逐用例断言：通过 / 失败 / 未覆盖
        · 断言：包含必需要点 / 不得包含禁项 / 结构化字段合法 / 引用可追溯
  ② 与基线对比     →  改进数、回退数（回退为 0 才允许继续）
  ③ 通过 → 小流量在线实验（A/B）→ 看在线指标
    失败 → 直接拦住，不进灰度
      │
      └─▶ 评估集本身需要版本化与定期换血，否则会被优化掉
```

- **为什么这样设计有效**：因为评价标准被外化成可执行断言，所以每次改动都能得到"同一把尺子"的读数，回退在合并前就被发现；代价是这把尺子覆盖不到的地方仍然会漏，而且尺子本身会过时。
- **代价**：每个用例都要写、要裁、要做泄漏检查；评估集的维护是长期成本（用例会烂、会与线上分布脱节）；断言只能覆盖可表达的那部分质量。
- **失效点**：当评估集被反复用于调参时，它从"衡量泛化的尺子"反转成"被优化掉的目标"，因为人和模型都会朝已见过的用例过拟合，而线上分布的用例并不在这把尺子上。
- **真实使用**：把评估框架开源、鼓励用公开评估集做回归是已被公开的做法 【公开】（OpenAI Evals，2023）；LLM 评估与可观测产品（Langfuse、Helicone、Arize Phoenix）见 [§4.3 工具链](02-feedback-loop-section-4-sec4.md)。

#### 3.2.5 Self-Improvement（Self-Play / Self-Refine）

- **被什么约束逼出来**：有些任务没有人给逐步标注（推理链），或者人类反馈的成本高到不可承受；但这些任务的结果常常可以自动判对错。
- **结构**：把"评判"从人手里搬到模型或验证器手里——自批评自修正，或自己出题自己对局。

```text
Self-Refine：生成 ─▶ 自我批评（按明确标准找问题）─▶ 修正 ─▶ 再批评 …
                 （循环 N 轮，N 越大成本越高、收益递减）
Self-Play：  自己生成任务 ─▶ 自己求解 ─▶ 可验证器 / 对手判胜负 ─▶ 更新

共同点：反馈的产出者与消费者是同一个系统或用同一套规则
        └─▶ 单位反馈成本从"人时"变成"推理算力"
```

- **为什么这样设计有效**：因为评判被内化或用可验证规则替代，所以反馈的单位成本从人时降到算力，反馈量不再受人力线性限制；代价是评判者与生成者同源时，错误会共振而不是被纠正。
- **代价**：多轮迭代的 token 成本（收益随轮数递减）；无外部锚点时，质量上限就是模型自身的判断力；自生成任务的分布会向模型自己的舒适区收缩。
- **失效点**：当评判与生成同源、又没有外部可验证信号时，"自我改进"从提升反转成退化（多样性塌缩 / 偏见自我固化），因为评判标准就是模型自己的分布，缺少把错误拉回来的外力。
- **真实使用**：Self-Refine 有公开方法与评测 【公开】（Madaan 等，2023）；自我对局在棋类上被验证有效 【公开】（AlphaGo Zero，Nature 2017；AlphaZero，Science 2018）；用可验证奖励做规模化自我改进的推理模型 【公开】（DeepSeek-R1，2025）。

#### 3.2.6 Online DPO（实时反馈驱动的在线偏好训练）

- **被什么约束逼出来**：反馈延迟预算被压到"天"甚至"小时"级，季度重训赶不上场景变化；而 RLHF 需要单独训奖励模型再跑 PPO，一轮周期太长、成本太高。
- **结构**：偏好对从真实流量里现采现用，闭环压到"收集 → 直接更新策略 → 灰度上线"，中间不经过奖励模型这一层。

```text
在线服务 ──▶ 采集偏好对（采纳 / 撤销、重生成前后、人工裁决）
                    │
      ┌─────────────┴──────────────┐
      │ 参考模型 π_ref（冻结）       │  在线策略 π_θ（每日 / 每小时增量更新）
      └─────────────┬──────────────┘
                    ▼
        DPO 目标：直接抬高 chosen、压低 rejected（对 π_ref 归一化）
                    ▼
        灰度 / 小流量 → 监控 → 可回滚
```

- **为什么这样设计有效**：因为 DPO 的目标只依赖"成对偏好 + 参考模型"，不需要奖励模型也不需要在线 RL 采样循环，所以"每天一批偏好数据直接更新策略"在工程上可行；代价是每一批数据只反映当天的分布与当时的策略偏好。
- **代价**：参考模型与在线策略要在显存与版本上共存；训练版本与服务版本的一致性要严格管理；必须有分钟级回滚能力——在线更新出错是在生产上出错的。
- **失效点**：当 chosen / rejected 全部由当前策略自己采样产生、且没有随机化探索时，在线 DPO 从"持续对齐"反转成"自我强化"，因为"哪个更好"的分布由被训练者自己决定，几轮之后模型只是在确认自己的口味。
- **真实使用**：DPO 的公开方法在不需要奖励模型的偏好学习上成立 【公开】（Rafailov 等，2023），开源模型用它做偏好对齐 【公开】（Zephyr-7B，Hugging Face H4，2023）；"在线 DPO"的工业节奏各家差异大，多数团队的做法是按批次增量更新 + 灰度，而不是逐条实时更新 【经验】。

#### 3.2.7 Feedback-Driven RAG

- **被什么约束逼出来**：RAG 的错误多数发生在检索而不是生成，而"这段证据是否相关"没有标准答案，只能从引用、采纳、纠错这些下游结果反推。
- **结构**：反馈必须落在 chunk / 文档级而不是回答级，否则无法定位到具体证据；因此要连检索候选集与最终引用一起落库。

```sql
CREATE TABLE retrieval_feedback (
  query_id     VARCHAR(64) NOT NULL,
  doc_id       VARCHAR(64) NOT NULL,
  rank         INT,                    -- 召回位次，用于做位置偏置校正
  retrieved    BOOLEAN,                -- 是否被召回
  cited        BOOLEAN,                -- 是否出现在最终答案的引用里
  user_marked  VARCHAR(16),            -- 有用 / 没用 / 纠错为哪一条
  answer_rating SMALLINT,              -- 回答级评分，仅作弱信号
  event_time   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

- **为什么这样设计有效**：因为反馈落在候选证据这一层，所以它能直接训练或校准重排器与切分策略，而回答级的好恶只能告诉你"这次不好"、告诉不了"哪里不好"；代价是每次查询都要存下完整候选集与引用关系。
- **代价**：检索日志体量远大于反馈事件本身（每次查询 × top-k）；归因仍然不精确（回答好不代表每个被引用的 chunk 都相关）；删改文档会污染历史反馈样本。
- **失效点**：当"被引用"被当成"相关"的唯一真值标签时，反馈闭环从改善检索反转成自我窄化，因为生成模型倾向于引用它已经倾向召回的文档，回路把召回器原有的偏好当成相关性标准再喂回去。
- **真实使用**：用点击 / 采纳类数据训练排序器有公开的方法基础 【公开】（Joachims，KDD 2002）；检索增强生成的公开框架 【公开】（Lewis 等，2020）。具体产品的 RAG 反馈闭环细节公开有限，多数团队的做法是"候选集 + 引用 + 纠错"三件一起采 【经验】。

#### 3.2.8 Constitutional AI

- **被什么约束逼出来**：价值观与有害性判断既贵又难一致，而且准则本身会频繁修订——每改一次准则就重训一遍标注团队是不可接受的。
- **结构**：把评判标准外化成一份可读、可版本化的准则文本，让模型按它自我批评、自我修订，再用这些自我判定去扩量构造偏好数据。

```text
宪法（一份自然语言准则，可版本化、可 diff）
  · 条目形如："若回答涉及 X，应当先说明 Y，而不是直接给结论"
        │
        ▼
① 生成初稿 ─▶ 模型按准则自我批评 ─▶ 修订稿
② 用"初稿 vs 修订稿"造出偏好对 ─▶ 偏好训练（把准则压进权重）
        │
        ▼
审计留痕：准则版本号 + 每次判定的依据条目
```

- **为什么这样设计有效**：因为评判标准被外化成一份可 diff 的文档，"改标准"从一项人力组织工作变成一次代码评审；代价是准则的任何歧义都会被一致地、无差别地放大到全部样本上。
- **代价**：准则编写与维护要覆盖长尾危害，本身就是高技能工作；模型自我评判会带来与准则未言明部分不一致的系统性偏差；要保留准则版本与判定记录，否则无法审计。
- **失效点**：当准则本身含糊或过宽时，它从"可扩展的一致标注"反转成"大规模的一致错误"，因为同一个歧义被应用到全部样本上，而且没有人工抽样去发现它——人工通道被绕开得越彻底，这个盲区越晚被发现。
- **真实使用**：用一组书面准则让模型自我评判、替代部分人工标注的公开方法 【公开】（Anthropic，Constitutional AI，2022）；用模型反馈扩量、人工转向抽检与疑难裁决的做法见 [§6 字节豆包案例](02-feedback-loop-section-6-sec6.md)。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 高价值、低频、要人参与（客服 Agent） | 显式评分 + 隐式会话 | 不用纯 Bandit：样本太少，探索成本换不回信息 | 每条会话的人工审核成本是否可承受 |
| 高频、即时决策、奖励可即时观测（推荐系统） | 隐式反馈 + Online Bandit | 不用 Eval-Driven：等离线评估出来，流量已经过去了 | 奖励偏差与延迟是否可接受 |
| 用户行为本身就是判断（代码 Copilot） | 显式 Accept / Reject（+ 撤销作为强负反馈） | 不用打分制：打分打断工作流，采纳行为零成本可得 | 能否把撤销 / 部分保留也采到 |
| 产出是多轮修改的结果（创作助手） | 显式评分 + 修改轨迹 | 不用单点评分：终稿评分掩盖了模型初稿的真实差距 | 是否记录"改了几轮才可用" |
| 通用对话（通用 LLM Chat） | 点赞 / 点踩 + 复制等隐式信号 | 不用 HITL：对话量远超人能审核的规模 | 显式反馈占比是否低到必须靠隐式补 |
| 任务可自动判定成败（Coding Agent） | 接受率 + 测试通过率 | 不用人工评分：测试通过与否是更硬、更便宜的信号 | 是否存在可自动验证的失败条件 |
| 改的是 prompt / 模型 / 检索链路（LLM 应用开发） | Eval-Driven | 不用在线实验做唯一判据：没有离线门禁，回退要等用户发现 | 评估集能否在合并前跑完 |
| 要输出价值判断（安全 / 价值观对齐） | Constitutional AI（+ 人工抽检） | 不用纯 HITL：准则总在改，重训标注团队不可持续 | 准则能否写到可 diff、可判定的粒度 |
| 结果可自动验证的推理任务（数学 / 代码） | Self-Improvement + 可验证奖励 | 不用过程标注：逐步标注推理链成本高且不可规模化 | 是否有可靠的自动验证器 |
| 问答质量取决于证据质量（RAG 问答） | Feedback-Driven RAG | 不用回答级反馈：定位不到是哪条证据的问题 | 能否采到候选集与引用关系 |

本节最常被误选的一对，是**把 Online Bandit 与 Eval-Driven 当成同一类"用反馈改进"**。二者的机制完全不同：Bandit 优化的是你喂给它的即时奖励，Eval 守的是离线下限。误把 Bandit 当 Eval 用（没有门禁就在线更新、且奖励是代理指标），典型后果是指标持续涨、真实质量持续降，而且因为每次更新都是小步的、无法复现的，出问题时连"从哪一版开始坏的"都说不清。

### 3.4 组合模式：真实系统不会只用一种

**组合一：双通道采集 + Eval 门禁 + 灰度（通用 LLM 应用的最小闭环）**

- 构成：显式 / 隐式双通道负责"采到什么"，Eval 负责"什么不许上线"，灰度与 A/B 负责"上了之后怎么看"。
- 职责边界：采集层只负责把事件原样落库并标注信号类型，不做质量判断；Eval 只守已知的坏，不负责发现新的好。
- 运维代价：三套系统（埋点、评估、实验）都要有 Owner；评估集的换血要排进例行工作，否则一年后就是一座废墟。
- 适合规模：从有第一个真实用户起就该有，小团队即可起步。

**组合二：HITL 标注 + Constitutional AI 扩量（人工转抽检）**

- 构成：模型按准则做全量判断，人工只处理"模型判不准"与抽检样本；判定结果沉淀为可复用偏好数据，与训练解耦。
- 职责边界：AI 反馈负责覆盖度，人工负责校准与裁定歧义；准则本身由人维护。
- 运维代价：要监控一致率与"AI 与人工的偏离度"，否则系统性偏移无人发现；标注团队技能要求从"能标"转为"能判难例、能改准则"。
- 适合规模：多业务、多模态、反馈量已超出人工全量标注能力的组织。

**组合三：隐式采纳信号 + 增量偏好训练 + 上下文条件化（代码助手 / 工具型 Agent）**

- 构成：采纳 / 撤销提供密集信号，增量偏好训练提供短周期更新，上下文条件化避免把不同项目的风格平均掉。
- 职责边界：采集层记录触发时的上下文（语言 / 框架 / 项目），训练层按上下文分桶学习条件化偏好。
- 运维代价：参考模型与在线策略并存；必须能分钟级回滚；低覆盖场景要做重加权或补采，否则模型会退化成只服务主流项目。
- 适合规模：有稳定真实流量、且工程团队能承担在线更新的团队。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 反馈缺失 | 上线后只能靠"感觉变差"发现问题；没有反馈事件表 | 分布漂移无观测通道，质量随时间单向下降 | 采集被当成后续优化项，先上功能再说 | 先建事件表与埋点，再谈训练 |
| 反馈错配 | 指标在涨，用户投诉也在涨 | 优化目标与业务目标不是同一个量，系统高效地向错误方向收敛 | 用最容易采到的代理指标（点击 / 采纳率）代替真实目标 | 找真实目标的代理，并用长期指标校验 |
| 反馈延迟 | 反馈到训练间隔以季度计；上线后场景已变 | 训练数据描述的是过去的需求，更新永远差一个周期 | 采集、清洗、训练、上线各自独立排期 | 压缩链路，把闭环周期当成一级指标 |
| 反馈噪声 | 同一问题标签互相矛盾；个别用户在刷分 | 噪声在训练中被当成信号学习，模型学会讨好噪声源 | 没有去噪与异常检测，所有事件等权 | 去重、反作弊、按来源加权 |
| 反馈单一 | 只有正向信号；没有负反馈通道 | 缺少负例，偏好学习退化为"全面抬高"，偏置无法纠正 | 正反馈好采、负反馈难采（用户通常直接走掉） | 主动设计负反馈通道（点踩 / 撤销 / 离开） |
| 反馈过载 | 事件表巨大，但没人说得清哪些进了训练 | 存储与治理成本上涨，有效信号被淹没在噪声里 | 把所有行为默认都当反馈，无采样策略 | 定义"什么才算反馈"，分层采样 |
| 反馈未归因 | 知道这次体验差，不知道是检索错还是生成错 | 反馈无法定位到可修改的动作，闭环空转 | 采集只有回答级结果，没有中间环节的轨迹 | 记录检索候选、工具调用、prompt 版本 |
| 反馈冷启动 | 新功能 / 新模型没有反馈，永远排不上迭代 | 无样本 → 无优化 → 无用户 → 无样本，自我锁死 | 依赖自然反馈积累，没有冷启动方案 | 冷启动期用人工 / 合成偏好 / 模板引导采信号 |

**反馈错配是最危险的一条**，因为它不在数据层面暴露。它暴露的方式是指标仪表盘一片绿、用户群里开始出现"最近是不是变傻了"的抱怨。机制上，只要奖励是代理指标，优化压力一定会把它压到与真实目标脱钩的位置——这也是 Bandit 类模式最容易翻车的点。

**反馈延迟的隐蔽性在于它从不报错**。它只是让团队一直用上个季度的世界解释这个季度的问题，而且延迟越大、单次更新的动作就越大，出错的代价也越高。

**反馈未归因则让闭环"看起来在转"**：反馈量不小、模型也在更新，但每次更新都是全量重训加猜测，改对改错无从判断——工具有了，学习没发生。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 反馈量超过人能逐条看的阈值（约千条 / 天量级，【经验】） | 人工逐条审核 | 审核工时随事件量线性上涨，审不过来就变成只看前几页 | 抽检 + 一致率监控 + 自动去噪 | 要建黄金集与抽检管道，且要接受"不再逐条看" |
| 闭环周期从季度压到周 | 离线批训练（RLHF 三段式） | 标注与奖励模型训练周期长于场景变化周期 | 增量偏好训练 / 在线 DPO | 参考模型与策略并存、版本一致性、分钟级回滚 |
| 单业务扩到多业务 | 各业务自建偏好标准 | 同一判断被重复标注，数据互不复用 | 统一判定准则 + 场景权重叠加 | 准则编写与场景权重调参，需要跨团队评审 |
| 文本扩到多模态 | 文本标注指南 | 指南表达不了图像 / 视频的判断标准 | 统一判定框架 + 多模态评估集 | 标注工具、质检流程、评估集都要改造 |
| 从"只能靠人判"到"有可验证器" | 纯 HITL | 标注吞吐成了训练信号的上限 | 可验证奖励 + 自采样（组内相对） | 要为每类任务写验证器，并防验证器被钻空子 |
| 单模型扩到多模型 / 多 prompt 版本 | 混合口径的反馈池 | 反馈归因不到具体版本，改进无法定位 | 反馈按模型与 prompt 版本分桶 | 埋点口径、统计口径、实验平台一起改 |

补一句判据：**当"采集"的成本开始高于"消费"的成本时，就该换模式了**。反馈系统最容易失控的方式不是采不到，而是采了一堆没人用、还要一直维护和治理的信号。

### 3.7 自检清单

1. 反馈事件表里，能否回答"这条信号属于哪个模型版本、哪个 prompt 版本"？答不出即无法归因。
2. 隐式信号事件是否带了曝光位次与曝光次数？缺任一项，位置偏置就无法校正。
3. 是否存在不止一条负反馈通道（点踩 / 撤销 / 放弃 / 纠错）？只有正向信号即违反"反馈单一"。
4. 评估集最近一次换血与新增用例是在什么时候？超过一个季度未动，它已在描述过去。
5. 评估集是否同时用于调参和验收？是，则它已被优化掉，需另留一份从未参与调参的留出集。
6. 反馈从产生到可用于更新的中位延迟是多少？这个数是否被当成一级指标在看？
7. 有一条真实反馈回来时，能否追到"哪一次检索 / 哪一次工具调用"？不能，即"反馈未归因"。
8. 在线更新（若有）能否在分钟级回滚到上一稳定版本？不能，就不要开在线更新。
9. 训练用的 chosen / rejected 是否全部出自当前策略？是，且无随机化探索，则存在自我强化风险。
10. 标注指令最近一次修订的记录在哪？各标注员的一致率与黄金集通过率是多少？
11. 反馈数据本身有没有 Owner、保留策略与 PII 处理？答不上来，说明反馈还没被当成资产治理。
12. 换成新模型版本后，是否保证评估集能跑完全量用例并给出与基线可比的读数？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 反馈稀疏但意图明确、人的判断不可替代 | 显式 + 隐式双通道、HITL 标注 | 人对长尾语义的判断无法被规则替代，双通道解决覆盖度 |
| 反馈延迟必须压到秒级、决策即反馈 | Online Bandit | 探索写在决策式里，不需要离线标注就能持续获得信息 |
| 反馈量超出人工规模、判断标准还会变 | Constitutional AI + HITL 抽检 | 标准外化成可 diff 的准则，改标准不用重训标注团队 |
| 反馈延迟被压到天 / 小时级 | Online DPO | 不需要奖励模型的偏好目标让每批数据都能直接进训练 |
| 无人类标注但结果可自动验证 | Self-Improvement + 可验证奖励 | 反馈单位成本从人时变为算力，可规模化构造 |
| 错误主要发生在检索环节 | Feedback-Driven RAG | 反馈落在候选证据层，才能训练重排而不是只评价回答 |
| 改动频繁、怕回退 | Eval-Driven | 质量标准外化成可执行断言，才能在同一把尺子上比较版本 |

> 本节小结：本主题下决定模式选择的**唯一那条最前置的约束，是反馈信号的延迟预算**——它一确定，可选模式集合就被卡死：秒级只可能是 Bandit 或在线规则，天级是增量偏好训练，季级才是 RLHF 三段式这类重管线；其余约束（可验证性、归因性、分布偏差）都是在预算允许的集合里做二次筛选。
>
> 💡 **思考锚点**：先量你们反馈「从产生到可用于更新」的中位延迟（3.7 第 6 条）落在哪个量级——秒、天、还是季？它一旦定档，3.8 表里的可选模式就只剩对应那几行。再量第二个数：当前链路里「采集」的单位成本是否已高于「消费」（3.6 的换挡判据）——若是，你该先停掉的不是模型，是一部分没人消费的信号。
