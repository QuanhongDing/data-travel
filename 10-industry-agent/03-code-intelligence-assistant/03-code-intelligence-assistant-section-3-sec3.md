## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

代码智能助手的形态由**五条约束**决定，顺序不能颠倒：

1. **源码能否出域**：私有代码是否允许发往外部端点？**这一条直接筛掉一半形态**（不能出域 → 必须自托管推理 + 本地索引，SaaS 方案出局）。
2. **交互延迟要求**：补全要落在编辑节奏内（百毫秒到秒级区间），还是可以接受"提交后异步返回"（审查 / 问答）？
3. **动作可逆性**：只读（问答 / 审查建议）还是可写（生成代码 / 修改文件）？**可写必须有人审与回滚路径**。
4. **有没有评测集**：没有私有评测集时，"效果"只能主观判断，因此**建评测集必须与助手同期上线**（这是本主题的前置条件，不是后续优化）。
5. **责任归属**：审查意见造成的返工与事故由谁负责？（决定审查是否阻断、是否留痕、是否要求可解释）

> **判据的用法**：先用 1 决定"能选哪一族"；用 2 决定"哪些能力可做同步、哪些必须异步"；用 3 决定"要不要人审与沙箱"；用 4 **决定先做哪一块**（没有评测集时，先做评测集比先做能力更划算）；用 5 决定审查的强度。

**每条约束的"过关"是可核查的**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 源码能否出域 | 出网白名单覆盖**全部组件**（模型 / 索引 / 遥测 / 日志），并通过一次**真实连接审计** |
| 2 交互延迟 | 补全链路的 P95 与**启用率**同时有数（只看延迟看不出"用户还在不在用"） |
| 3 动作可逆性 | 每一个可写动作都有对应的人审入口与回滚路径 |
| 4 有没有评测集 | 私有评测集的样本来自**你自己的仓库历史**，且有版本（否则改一次丢失一次可比性） |
| 5 责任归属 | "谁负责"落到一个具体角色（例如当值评审人），而不是"团队共同负责" |

第 4 条是本主题最反常的一条：**它把一件通常是"后续优化"的事（建评测集）变成了前置条件**。原因是本主题的失败形态几乎都是**静默的**——补全的接受率下降没有错误日志、审查的意见被批量忽略没有告警、生成的测试断言空洞仍然"通过"。**没有评测集，这些失败都没有观测面**；因此"先做能力、后建评测"在本主题里等于"先做一件看不见结果的事"。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 IDE 内补全（FIM，延迟优先）

**被什么约束逼出来**：约束 2 最紧的一支——补全必须跟得上打字节奏。

**结构**：编辑器前缀 + 后缀 → 上下文检索（限时预算）→ 模型生成 → 呈现候选；整个链路有**硬超时**（超时即不呈现，而不是"慢慢等到出结果"）。

**为什么这样设计有效**：因为**延迟不是一个可以事后优化的指标，而是一个会决定功能生死的门槛**——用户对补全的容忍度由打字节奏给定（几百毫秒内），超过之后他不是"等得久一点"，而是**关掉这个功能**；因此唯一有效的设计是**把整个链路的每一步都压在预算内，并在超预算时降级呈现（少给候选）而不是延时**。**这条机制解释了一个反直觉的选择**：为什么宁可降低质量也不超时——因为在补全这个场景里，"慢"的代价（功能被关）远高于"少"的代价（用户自己写）。

**代价**：为了延迟，上下文预算与模型档位都被压小 → 质量上限降低；因此需要**用更好的检索与重排**（而不是更大的模型）来补。**这里的机制是**：模型档位每升一档，延迟与成本都上台阶，而可用的上下文预算反而被压缩；**唯有检索与重排是"在相同延迟预算内提高信息密度"**，所以它是这一支唯一有效的质量杠杆。

**失效点**：把补全做成同步等待长上下文——**用户会直接关掉这个功能**（这类失败的信号是"启用率骤降"，而不是任何错误日志）。**因此埋点必须包含启用率与接受率**：它们是这个模式唯一的观测面（§3.1 约束 4 的直接后果）。

#### 3.2.2 仓库级问答（检索 + 重排 + 引用）

**被什么约束逼出来**：问题多为"谁调用它 / 为什么这么设计 / 这段逻辑在哪"，**纯向量检索答不了结构性问题**（约束：需要符号与引用）。

**结构**：问题解析（抽符号 / 路径 / 关键词）→ 三路召回（符号、引用、向量）→ 重排 → 生成并**附代码位置引用**（文件 + 行号）。

**为什么这样设计有效**：因为**代码里的"相关性"有一半是结构性的，不是语义性的**——"谁调用这个函数"在语义上没有任何线索（调用方的代码可能与函数体毫无文字相似度），但在**引用图**上是直接可查的一条边。**三路召回的有效性来自各自覆盖一类问题**：符号索引覆盖"按名字找"，引用图覆盖"按关系找"，向量覆盖"按意图找"——**只做向量时，"谁调用它"这类问题会在原理上答不出来**，而它恰好是最高频的一类。

**代价**：索引新鲜度成为答案正确性的前提（索引滞后 → 答旧行为）；跨语言、宏与生成代码的解析差异要单独处理。**"索引滞后"为什么是正确性问题而不是体验问题**：滞后的索引会**给出看起来完全合理但已经过时的答案**（例如指出一个上周已删除的调用方），而用户没有任何信号能察觉——**因此滞后量必须作为日常指标**，而不是等用户发现。

**判据**：**每个答案都能指到文件与行号**；索引滞后量有指标（例如"滞后 ≤ N 个提交"）。

#### 3.2.3 变更审查（非阻断建议 / 门禁）

**被什么约束逼出来**：约束 3、5——审查意见会被人消费，误报的代价是"没人再看"。

**结构**：变更（diff）+ 仓库上下文 → 规则（约定与易错模式）与模型（语义问题）双路 → 意见分级（**建议 / 提醒 / 阻断**）→ 留痕（谁提的、是否被采纳）。**默认不阻断**；只有"确定性规则命中"（格式、禁止 API、缺失测试）才进阻断级。

**为什么这样设计有效**：因为**审查意见的权威来自"它错了怎么办"**——确定性规则错了，你可以复现并改规则；模型意见错了，你只能调阈值，而阈值调整会连带影响所有类别。**把两类意见放在同一个强度上，会让"门禁的可靠性"取决于一个概率系统的表现**；而门禁一旦出现一次明显误报，"批量忽略"就会成为团队的默认动作，此后**真实问题也会被一起忽略**（§3.5 反模式的机制）。因此**分级不是"温和一点"，而是保住门禁权威的唯一做法**。

**代价**：意见要及时（提交时给出，而不是第二天）；误报要能归因（哪条规则过宽 / 模型哪个标签阈值过低）。**"及时"的机制**：审查意见的价值随"代码上下文在开发者脑中的新鲜度"衰减——提交后第二天给出，开发者已经进入下一件事，采纳成本上升到一个不合理的高度。

**判据**：**审查采纳率**与**误报归因率**（误报中能归因的比例）；前者低于阈值就该收窄规则或提高模型阈值。

#### 3.2.4 测试生成（沙箱验证 + 有效性抽检）

**被什么约束逼出来**：约束 4——"生成的测试通过了"不等于"测试有用"。

**结构**：基于被测函数 + 相邻测试风格生成 → **在沙箱里跑**（必须编译、必须通过）→ **有效性抽检**（人为注入小缺陷，看生成的测试是否失败）。

**为什么这样设计有效**：因为它把**两个容易混淆的指标分开了**——"通过"衡量的是语法与运行正确性，"有效"衡量的是**它能不能发现缺陷**；而**只有后者才是测试的价值**。变异式抽检（人为注入缺陷看测试是否失败）之所以是关键设计，是因为它把"有效性"变成了**一个可以自动化的实验**：注入一个 `>=` 改 `>` 的缺陷，测试若仍然通过，就说明它没有断言到边界。

**代价**：沙箱的冷启动与依赖安装成本（这与 [Ch5 §02 §3.2.8](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的沙箱是同一类设施）；生成测试的风格要与仓库既有测试一致（否则会引入两套风格）。**"两套风格"的代价常被低估**：它不只是美观问题——后续维护者要同时理解两种写法，且生成风格的测试**会在重构时被优先删除**。

**失效点**：把"测试通过率"当作唯一指标——会生成大量**断言空洞**的测试（跑通但不验证行为）。**判据**：抽检时注入的缺陷是否被捕获；**这个数（缺陷捕获率）才是测试生成的真实质量指标**。

#### 3.2.5 缺陷定位与修复（候选 + 沙箱 + 人审）

**被什么约束逼出来**：约束 3——修改是**可写动作**，必须可验证、可回滚。

**结构**：从失败测试 / 报错栈 / 变更集定位 → 生成候选修复 → **沙箱验证（编译 + 相关测试）** → 呈现为**待审的变更**（不直接合并）。

**为什么这样设计有效**：因为它把**"可能性"与"已验证"分成了两种不同的交付物**——未经沙箱验证的候选只是**线索**（告诉人"往这边看"），通过验证的候选才是**修复**（可以进入评审）。**这条区分直接决定信任**：一旦有一次"未验证的候选被当成修复呈现"，用户此后会怀疑所有候选；而**验证是可以自动化的**，因此这条质量线不需要增加人力就能守住。

**代价**：定位依赖测试与日志的质量（测试缺失时定位退化为"猜"）；验证成本随仓库规模上升（跑哪些测试是策略问题）。**"跑哪些测试"的判据**：优先跑**受影响范围**（被修改函数的调用方与相关测试），超时后再缩小；**不做范围收敛的沙箱会慢到没人用**。

**判据**：**修复候选的"验证通过率"**（通过沙箱验证的候选占比）与**最终被合并的比例**。两个数要一起看：通过率高但合并率低，说明候选解决的**不是人关心的问题**；通过率低说明生成质量不足。

#### 3.2.6 私有化全栈（自托管模型 + 本地索引）

**被什么约束逼出来**：约束 1 最硬的一支——源码不出域。

**结构**：自托管推理服务（按需 GPU）+ 本地索引与向量库 + 本地评测集；**全链路的出网出口只有"模型端点"这一个内部地址**（与 [Ch6 §03 模型网关](../../06-multi-model/03-model-gateway/03-model-gateway.md) 的出网白名单对齐）。

**为什么这样设计有效**：因为**"不出域"只有做成架构事实才可举证**——制度要求（"大家不要发出去"）在审计里不成立，而**"全链路只有一个内部地址"可以被连接审计验证**（§3.2.8 的越权演练同理）。**它的有效性不来自更强的保密能力，而来自更少的出网点**：出网点越少，可验证性越高。

**代价**：模型档位受自托管能力限制（通常弱于最前沿的托管模型）；GPU 固定成本是**台阶形**（无论用多少都要付，见 [Ch6 §03 §7.4](../../06-multi-model/03-model-gateway/03-model-gateway-section-7-sec7.md) 的成本曲线）；索引与推理的运维面自持。**这里有一条直接的推论**：**因为模型档位受限，私有化形态下"用检索与重排补质量"不再是可选优化，而是必需项**（§3.2.1 的同一逻辑）。

**失效点**：只在"模型"这一层做私有化，而**索引或遥测走了外部服务**——这是最常见的"假私有化"；判据是**出网白名单 + 实际连接审计**，不是架构图。**"假"之所以常见**：模型层最容易看见（它是主链路），索引与遥测是旁路组件，容易在建架构图时被忽略。

#### 3.2.7 混合（补全本地 / 审查与问答走受控端点）

**被什么约束逼出来**：约束 1 与 2 的组合——补全对延迟极敏感（本地小模型），而审查 / 问答对质量更敏感且可异步（可用更强模型）；但"能不能出域"随仓库分级不同。

**结构**：按**仓库分级**路由——公开 / 开源仓库可用外部端点；私有仓库强制走自托管。**同一套能力，两条端点路径**（这正是模型网关存在的意义：路由由配置决定，不由代码决定）。

**为什么这样设计有效**：因为**"延迟敏感"与"质量敏感"这两类需求的最优点在不同端点上**——补全的最优是"本地小模型 + 强检索"，审查与问答的最优是"强模型 + 可等待"。用一个端点同时满足两者，必然在某一侧妥协；**分路之后，两侧各自取最优，且分界由"仓库分级"这个合规事实决定**（而不是由工程偏好决定）。**这也是它比"全私有化"更现实的理由**：不是所有仓库都需要最强隔离。

**代价**：两条路径的**评测要分开做**（否则无法比较）；且必须保证"私有仓库的请求永远不会命中外部端点"（这一点必须**演练**，不能靠配置审阅）。**"必须演练"的机制**：分级路由的正确性依赖"仓库标签"这个输入，而标签会错（新仓库未打标、迁移后未更新）——**配置审阅只能验证逻辑，演练才能验证输入**。

**失效点**：分级信息缺失或过粗（例如只按"组织"分级，而仓库级敏感度不同）——一旦判错，就是一次泄漏。

#### 3.2.8 权限域与审计（先裁剪，再检索）

**被什么约束逼出来**：约束 1 与 5——私有代码的可见范围与操作留痕。

**结构**：请求进入时先确定**可见域**（仓库 / 分支 / 目录 / 时间范围）→ **在可见集合内**做检索 → 生成 → 留痕（谁、何时、对哪个仓库、做了什么动作、是否采纳）。

**为什么这样设计有效**：因为**"先检索后过滤"与"先裁剪后检索"不是性能差异，而是"内容有没有被读出来"的差异**——后者的召回阶段已经把无权内容读进了内存、日志与模型上下文，即使最终不呈现给用户，**暴露面已经存在**。前置裁剪把权限判定变成一个**不可绕过的输入条件**，而不是一个后置的展示逻辑。

**代价**：可见域判定要接企业的权限系统（与 [Ch11 §02 数据安全](../../11-cross-cutting/02-data-security/02-data-security.md) 的做法一致）；跨仓库引用的边界要定义清楚（依赖库的源码算不算可见）。**后者的机制**：代码的可见性天然带有"传染性"——一段代码的可见范围会牵出它引用的类型定义、接口、配置；**不定义这条边界，就会出现"能看到 A 仓库所以也能看到 A 依赖的 B 仓库"这类越权路径**。

**判据**：**用一次越权尝试做演练**（用无权账号请求私有仓库，验证被拒且拒绝原因可查）。

| --- | --- | --- | --- | --- |
| 源码可出域、只做补全 | 3.2.1 补全（可走端点） | 硬超时、**启用率 + 接受率**埋点 | 上审查 / 问答会分散首版 | 启用率与接受率是否可测（否→先补埋点） |
| 源码不可出域 | 3.2.6 私有化全栈 | 自托管推理、本地索引、出网白名单（覆盖遥测） | SaaS 方案直接违反边界 | 出网白名单 + 连接审计是否覆盖全部组件 |
| 需要"谁调用它"类问答 | 3.2.2 仓库级问答 | 符号 / 引用 / 向量三路索引、引用回指、滞后指标 | 纯向量检索答不了结构性问题 | 抽三个函数，能否答出调用方（能） |
| 变更质量参差 | 3.2.3 审查（非阻断） | 规则与模型双路、意见分级、归因字段、提交时给出 | 让模型意见进阻断级 → 门禁不可预测 | 采纳率与误报归因率 |

| 有明确的缺陷定位需求 | 3.2.5 修复候选 + 人审 | 沙箱验证（受影响范围优先）、待审变更、回滚路径 | 直接合并未验证候选 | 候选验证通过率**与**合并率 |
| 仓库分级不同（公开 + 私有） | 3.2.7 混合 | 仓库级分级、两条端点路径、分别评测 | 一刀切会让私有仓库违规或让公开仓库效果受损 | 私有仓库请求是否 100% 命中自托管（演练） |
| 多团队共用、要审计 | 3.2.8 权限域 + 审计 | 可见域前置、留痕、越权演练、跨仓库边界定义 | 先检索后过滤 = 泄漏 | 越权尝试是否被拒且可查原因 |

### 3.4 组合模式：真实系统不会只用一种

1. **底座组合**：3.2.8（权限域前置）+ 3.2.6 或 3.2.7（端点选择）——**这两件是所有能力的前置**，先做它们再做能力。
2. **能力组合**：3.2.1（补全，同步、延迟优先）+ 3.2.2（问答，异步可接受）+ 3.2.3（审查，提交时触发）——三种节奏不同，**评测也要分三套**。
3. **可信组合**：3.2.4（测试）+ 3.2.5（修复候选）+ **沙箱**——"先验证再呈现"是这一支可信度的来源；没有沙箱，生成物只能当线索。
4. **评测组合**：离线基准 + 私有评测集 + 线上接受率/采纳后留存（三层，与 [Ch2 §07](../../02-data-science/07-eval/07-eval.md) 一致）。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 上了补全但没埋接受率 | 无法证明价值，也无法判断"延迟降到多少才够" |
| 上了审查但意见不分级 | 把建议做成阻断，团队批量绕过 |
| 上了测试生成但没有有效性抽检 | 断言空洞的测试增加维护成本 |
| 私有化只做了模型层 | 索引或遥测出域，审计不通过 |
| 混合路由只审配置不演练 | 仓库标签错误导致私有仓库命中外部端点 |
| 修复候选先呈现后验证 | 一次编译不过就摧毁全部信任 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **补全等待长上下文** | 启用率骤降、延迟 P95 失控 | 功能被关掉，投入白费 | "上下文越多越好"的直觉 |
| **审查意见进阻断级** | 开发者绕过门禁 / 批量忽略 | 门禁不可预测，失去权威 | 把模型判断当确定性规则 |
| **测试只看通过率** | 覆盖率上升但缺陷照旧漏 | 断言空洞，维护成本上升 | 通过率是最容易测的指标 |
| **无接受率埋点** | 无法回答"助手有没有用" | 无法优化也无法争取预算 | 埋点被当作后续工作 |
| **假私有化** | 索引或遥测走外部服务 | 合规事故 | 只在模型层考虑边界 |
| **先检索后过滤权限** | 日志里出现不该出现的仓库名 | 泄漏 + 浪费 | 权限判定放在链路的后面 |
| **未经沙箱验证就呈现修复** | 候选代码编译不过 / 测试失败 | 信任崩塌 | 沙箱建设成本高 |
| **索引长期滞后** | 答的是旧行为 | 结论错误且难发现 | 重建代价大，没有滞后指标 |
| **评测集用公开基准代替私有集** | 榜单很好、业务无感 | 优化方向错位 | 公共基准更容易获得 |
| **仓库标签缺失或过期** | 混合路由下私有仓库命中外部端点 | 一次泄漏 | 分级靠人工打标，没有复核 |
| **上下文预算按"能塞多少"分配** | 预算涨了但质量不涨 | 边际收益为零仍继续加 | 缺少"再增加预算边际收益 < 1 个百分点"的判据 |
| **意见在次日给出** | 采纳率低，开发者说"已经在做别的了" | 审查价值随上下文新鲜度衰减 | 审查挂在每日批处理上而不是提交钩子 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 无助手 → 补全 | 团队开始自建脚本 / 用外部工具 | 3.2.1 | 埋点与评测集从零建 |
| 补全 → 仓库级问答 | "这段逻辑在哪、谁调用的"问题反复出现 | 3.2.2 | 符号 / 引用索引与引用回指 |
| 问答 → 审查 | 变更质量参差、评审成为瓶颈【经验：评审时长与变更量同时上升是常见触发点】 | 3.2.3 | 规则体系与归因字段；意见分级 |
| 单仓库 → 多仓库 / 多团队 | 权限与审计要求出现 | 3.2.8 + 3.2.7 | 可见域接入权限系统；分级与两条端点路径 |
| 端点 → 私有化 | 合规要求收紧【经验：受监管行业几乎必然走到这一步】 | 3.2.6 | 自托管推理与本地索引的运维面；评测需重做 |
| 建议 → 可写动作 | 开始有人要求"让它直接改" | 3.2.5 + 人审 + 沙箱 | 回滚路径与验证流水线 |
| 全私有化 → 混合 | 私有化的模型档位成为质量瓶颈，而部分仓库其实可出域 | 3.2.7 | 需要仓库级分级 + 两条路径分别评测（**先演练再上线**） |

### 3.7 自检清单

- [ ] 补全的延迟 P95 是多少？超过编辑节奏时，功能是否会自动"少呈现而不是慢呈现"？
- [ ] 接受率与**采纳后留存**都埋点了吗？两个数分别是多少？**启用率**有吗？
- [ ] 仓库索引覆盖符号、引用、向量三类吗？**索引滞后量**有指标吗？
- [ ] 上下文预算按来源切分了吗？有没有"再增加预算边际收益 < 1 个百分点"的判据？
- [ ] 问答的答案能指到文件 + 行号吗？跨语言 / 生成代码的处理定义了吗？
- [ ] 审查意见分级了吗？**确定性规则与模型建议分开**了吗？误报能归因吗？意见是提交时给出还是次日？
- [ ] 生成的测试在沙箱里跑过吗？**有没有变异式有效性抽检**？生成风格与既有测试一致吗？
- [ ] 修复候选是否"验证通过才呈现"？合并是否仍走人审？沙箱是否按受影响范围收敛？
- [ ] 可见域是**在检索之前**判定的吗？跨仓库依赖的可见性定义了吗？
- [ ] 私有仓库的请求是否 100% 命中自托管端点（**演练验证**）？
- [ ] 仓库分级标签是谁打的？有没有复核机制（新仓库、迁移后）？
- [ ] 评测三层（离线基准 / 私有集 / 线上指标）都有吗？私有集有多少样本、有版本吗？
- [ ] 留痕记录了什么（谁、何时、哪个仓库、什么动作、是否采纳）？能否支撑审计？

### 3.8 小结

> 本节小结：代码智能助手的形态由五条约束按序决定——**源码能否出域 → 交互延迟 → 动作可逆性 → 有没有评测集 → 责任归属**；八种模式里，**权限域前置（3.2.8）与端点选择（3.2.6 / 3.2.7）是所有能力的前置**，**补全（3.2.1）是延迟最紧的一支**，**沙箱验证（3.2.4 / 3.2.5）是可信度的来源**。判断这一支有没有建成，只看两条：**它的建议能不能在你的仓库里编译并通过测试**；**你能不能说出它的接受率与采纳后留存**——说不出，就还停在"看起来聪明"。**本主题还有一条特有的判断**：它的失败几乎全是静默的（启用率下降、意见被忽略、测试断言空洞都不会报错），因此**评测集不是后续优化，而是前置条件**。

> 💡 **思考锚点**：拿最近一次你（或同事）采纳的助手建议，追问两个问题：它在 N 天后还在代码里吗？它的改动有没有对应的测试？如果第一问答"没了"、第二问答"没有"，说明这一支缺的是**验证与评测**，不是模型能力——你打算先补沙箱，还是先建私有评测集？
