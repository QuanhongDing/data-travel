## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

1. **机制变了**：上下文从"单文件"变成"仓库级检索 + 重排"；补全从"只看前缀"变成 FIM（前后缀同时给定）；动作从"写"扩到"审查与验证"。**这类变化影响架构决策。**
2. **接口与规范变了**：编辑器与代码托管平台的扩展接口、语言服务器协议、沙箱运行时的接口在演进【公开：以各自规范与文档当前版本为准】。**这类变化影响集成方式。**
3. **只多了产品**：同一套能力换包装。**只在选型表里体现。**

判别方法仍是那一句：**"换一家厂商，这条结论还成立吗？"**

### 5.2 判据与分级

沿用三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定、可预期**。

| 演进方向 | 级别 | 机制变了什么 | 判据落点（可否自行核验） |
| --- | --- | --- | --- |
| 仓库级检索增强（补全 / 问答） | **L2** | 上下文从"单文件"扩到"检索 + 重排后的仓库片段" | ① 成立（检索与向量能力是成熟文档条目）；② **核不到**（公开的采纳数据几乎都来自建设方）；③ 成立 |
| FIM 补全（前后缀同时给定） | **L2** | 生成条件从"只看前缀"变成"前后缀 + 上下文" | ① 成立（多家实现与文档条目可核）；② 核不到；③ 成立 |
| 变更审查（概率性意见） | **L2** | 审查从"确定性规则"扩到"语义判断" | ① 成立（产品功能条目可核）；② **核不到采纳率与误报率的独立数据**；③ 部分成立（意见格式与阈值各家不同） |
| 沙箱内验证后呈现 | **L2** | 生成物先编译 / 先跑测试再给人看 | ① 成立（沙箱运行时是成熟条目）；② 核不到；③ 成立 |
| 测试生成（含有效性抽检） | **L2** | 从"补覆盖"变成"生成 + 用变异抽检验证有效性" | ① 成立；② 核不到；③ 部分成立（有效性口径各家不同） |
| 缺陷定位与自动修复 | **L3** | 从"提示问题"到"给出补丁" | ① 只有演示与自研；② 核不到；③ 不成立（补丁正确性口径未统一） |
| 自主完成多文件任务（自主 PR） | **L3** | 从"单点建议"到"端到端改动 + 提交" | ① 只有演示；② 核不到；③ 不成立（**责任无法归属**） |

**本节没有一行达到 L1**——卡点同样在 ②：**代码助手的效果数据（接受率、采纳后留存、审查采纳率）几乎都来自建设方**，且公共基准与私有仓库的表现差异很大。因此这一支的成熟度应按"**机制可验证、效果必须自测**"理解。

### 5.3 演进方向逐条拆解（核心节）

下面五个方向（§5.3.1–§5.3.5）按**同一套结构**写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**（判定方法与适用条件另列）。它们各自的级别见 §5.2 的那张表——**表给结论，本节给机制**；只写收益不写代价的方向，在评审时应被直接打回。§5.3.6 把同一套结构反过来用：遇到本节没列到的新名词，用那三步自己判。

#### 5.3.1 仓库级上下文：换的是"看什么"，不是"模型多大"

- **旧做法与它的卡点**：上下文是"光标前后若干行"。卡点有两处：**其一，"与仓库约定一致"这类要求无法满足**——模型看不到这个仓库既有的命名、错误处理与目录约定，生成片段语法正确、风格陌生；**其二，"谁调用它 / 这段在哪"在原理上答不出来**——答案不在任何一个文件里，而在文件之间的引用关系里（§2.3 第 1 条的判据就是拿"抽一个函数能否答出调用方"来验的）。

- **AI 改变了什么机制**：上下文来源从"光标附近"换成"**符号定义 + 引用点 + 测试 + 文档**，经检索与重排后注入"。这是**输入构成的改变，不是模型规模的改变**——模型还是那个模型，它看到的东西变了；因此它不要求更大的显存或更长的窗口，只要求一套索引。

- **由此得到的**：因为检索可以按符号与引用召回，**结构性问题第一次可答**（§3.2.2 的三路召回各覆盖一类问题：符号覆盖"按名字找"、引用图覆盖"按关系找"、向量覆盖"按意图找"）；又因为检索把预算花在最相关的片段上，**相同 token 预算内的信息密度上升**——这正是 §3.2.1 代价一栏说的"唯一有效的质量杠杆"。

- **由此付出的**：**索引成为一级基础设施**（符号 / 引用 / 向量三类），随之新增两个运维项——**新鲜度**（滞后量指标）与**预算切分**（各来源配额，见 §4.2（2）的粗排 → 重排 → 预算切分三步）；此外**判错的方式变了**：检索不到时系统不报错，只给一个"看起来合理的旧答案"（§3.2.2 的失效点），所以**索引滞后必须是日常指标，不能等用户发现**。

- **证据与来源**：【经验】代码助手的真实效果数据（接受率、采纳后留存、评审采纳率）几乎全部由建设方自述，构不成 §5 判据②要求的第三方非厂商生产案例，本主题 §6 收录的四例同属建设方材料。【公开】"按语义边界切块而不是按固定行数"这一做法在书内他处已有可核验落点：`04-data-assetization/05-rag-architecture` 的 §8 记了用 tree-sitter 按函数 / 类 / 方法边界做 AST 切分（可在该节自行核验），与本节 §4.2（1）的判据③是同一机制。

- **成熟度**：**L2**。① 成立（语言服务器协议、AST 解析器、向量与图索引都是成熟且有正式文档条目的能力）；**② 核不到**（无第三方非厂商的效果数据）；③ 部分成立（索引与检索接口稳定，但"上下文怎么选"各家不同，没有统一接口）。

- **判定方法**：抽三个已知答案的函数，问"谁调用它 / 改了会影响谁"，看它能否给出调用点（文件 + 行号）；再看"索引滞后多少提交"是否在日常看板上。

- **什么时候值得做**：仓库大、约定多，且"这段逻辑在哪 / 谁调用它"这类问题反复出现时——它是补全之外最高频的一类需求。

- **什么时候不值得做**：只想要补全、仓库又小或约定松散时——先把 §3.2.1 的埋点做起来，索引的收益要等"结构性问题"成为瓶颈才兑现。


#### 5.3.2 FIM：一行改动的收益，来自"与后文一致"

- **旧做法与它的卡点**：生成条件只有**前缀**（光标之前的文本）。卡点在**局部一致性**：一行改动常常要"与后文衔接"——改函数签名要让下面的调用点仍成立，补一段分支要知道后面已经有什么。只看前缀时，模型对"后面是什么"完全无知，于是**生成片段经常与紧随其后的代码重复或冲突**，用户要删掉一半才能用。

- **AI 改变了什么机制**：生成条件从"只看前缀"变成"**前缀 + 后缀同时给定**"。这是**条件信息的改变，不引入新的模型能力**：同一模型、同样的延迟预算，多了一个输入。

- **由此得到的**：因为后缀参与了条件，**"与后文衔接"由模型而不是由用户来保证**；§2.3 第 3 条把它的判据写成可实测的对照——**与只给前缀相比，私有评测集的通过率有提升**。也就是说这条方向不需要靠"感觉更顺"来论证，它可以被量出来。

- **由此付出的**：**对渲染与合并逻辑有要求**——生成片段与前缀 / 后缀在界面上有重叠区，编辑器要处理"重叠部分怎么显示、怎么一次性接受"，这是产品侧的实现成本而不是模型侧的成本；此外**评测必须能区分两种条件**，否则无法证明这个改动有效——等于投入了训练与推理改造成本却拿不出证据。§4.2（2）的批注也提醒：FIM 让上下文更贴题，但**上下文预算的分配规则要跟着改**。

- **证据与来源**：【经验】各编辑器与补全产品对 FIM 的界面处理方式不同，公开材料里没有可对照的跨产品效果数据，本节因此不给文档名与年份，请以各自官方文档当前版本为准。【公开】"前后缀同时作为生成条件"这一机制的一般描述见 §2.3 第 3 条，其判据（A/B 对照的通过率差）可以按 §4.2（7）的评测三层在你自己的私有评测集上复现。

- **成熟度**：**L2**。① 成立（多家实现与文档条目可核）；**② 核不到**（效果数据来自建设方）；③ 部分成立（FIM 本身是训练与推理侧的形态，编辑器侧的合并与呈现接口各家不同）。

- **判定方法**：在私有评测集上做一次对照——**同一批样本，"只给前缀"与"前缀 + 后缀"两种条件的通过率差多少**；差值读不出来时，先扩样本（§4.2（7）：样本量要能分辨 1 个百分点的差异）。

- **什么时候值得做**：改动集中在"需要与后文一致"的场景（改签名、补分支、写测试）时——这时收益最直接。

- **什么时候不值得做**：评测集还分辨不出 1 个百分点的差异时——先扩样本、先把埋点补齐，再谈这一条。


#### 5.3.3 审查：从规则到概率判断的分工

- **旧做法与它的卡点**：审查靠**确定性规则**（格式、禁止 API、缺失测试）加**人读 diff**。卡点不是"规则不准"，而是**规则的供给跟不上问题的种类**——语义类问题（这段改动在什么条件下会空指针、这个重试会不会放大下游压力）写不成规则；而人读 diff 的产能有限，评审一旦成为瓶颈，团队会先牺牲深度，再牺牲覆盖面。

- **AI 改变了什么机制**：审查从"**确定性判断**"扩到"**概率判断**"，并按判断来源分级——**确定性规则命中进阻断级，模型意见一律进建议级**（§4.2（4）的字段划分：`rules` 与 `model_checks`）。**这不是"多一类意见"，而是给两类意见划了不同的权力**。

- **由此得到的**：因为语义类问题第一次有了"值得看一眼"的供给，**覆盖面扩了**；又因为只有确定性规则能阻断，**门禁的可预测性没有被牺牲**——§3.2.3 的机制说得很直接：审查意见的权威来自"它错了怎么办"，确定性规则错了可以复现并改规则，模型意见错了只能调阈值，而调阈值会连带影响所有类别。

- **由此付出的**：**新增两类固定成本**——误报归因（每条误报要能落到某条规则或某个阈值，否则改不动）与阈值治理；**新增一类风险**：一旦有模型意见进了阻断级，一次明显误报就会让"批量忽略"成为团队默认动作，此后真实问题一起被忽略（§3.5 反模式表）。**还有一条时效要求**：意见必须在提交时给出——§3.2.3 的机制是它的价值随"代码上下文在开发者脑中的新鲜度"衰减，次日给出时采纳成本高到没人看。§7.3.5 另有一条与采购相关的推论：**计价基准（按席位还是按调用）会决定你把哪个指标当 KPI**，从而反过来塑造审查意见的产出方式。

- **证据与来源**：【公开】"确定性规则"这一侧在书内已有具名工具可对照：`13-decision/06-tech-debt` 的 §4.3 工具链表把 SonarQube / SonarCloud 列在"代码质量度量"一行、把 Snyk Code / Semgrep / GitHub CodeQL 列在"静态分析与安全"一行——它们正是可复现、可归因的那一类，可在该表自行核验。【经验】模型意见的采纳率与误报率没有第三方给出的跨产品数据，本节不点名任何产品。

- **成熟度**：**L2**。① 成立（产品功能条目可核）；**② 核不到**（公开材料里没有第三方给出的采纳率与误报率）；③ 部分成立（意见格式与阈值各家不同，没有统一接口）。

- **判定方法**：抽一周的意见，逐条问"这是规则命中还是模型判定""误报能不能归因到具体规则或某个阈值"；答不出来的那部分，就是还没有归因字段。

- **什么时候值得做**：变更量大、评审成为瓶颈，且已经有一套确定性门禁时——没有后者，模型意见只是"另一个提示器"，形不成门禁。

- **什么时候不值得做**：团队还没有人处理误报时——增加一类意见只会增加忽略，先把归因字段与采纳率统计做起来。

#### 5.3.4 沙箱与有效性：把"看起来对"变成"验证过"

- **旧做法与它的卡点**：生成物直接呈现给人。卡点是**验证责任被推给了消费者**——开发者要自己判断"这段改得对不对、编译过不过、既有测试还成不成立"；而**判断成本随生成量上升**：生成得越多，人花在判断上的时间越多，净收益被吃掉。这是生成式能力在工程场景里最常撞到的一堵墙：**供给增加了，验收费没有降**。

- **AI 改变了什么机制**：生成物在呈现之前**先经过一次可自动化的验证**——跑编译与相关测试；测试生成再加一层**变异式抽检**（人为注入一个小缺陷，看生成的测试能否发现，§4.2（5））。**它把"验证"这个动作从人前移到了流水线**，这一点与 §5.3.3 的"把判断分级"是同一类动作：**改变的不是能力，而是判断发生的时机与主体**。

- **由此得到的**：因为它把**"通过"与"有效"两个指标分开了**（"通过"衡量语法与运行正确性，"有效"衡量能不能发现缺陷），而**只有后者才是测试的价值**——变异式抽检把"有效性"变成一个可以自动化的实验，于是**质量线可以在不增加人力的情况下守住**（§3.2.4 的机制）；同时**呈现物的可信度被分级**：已验证的是"修复"，未验证的只是"线索"（§3.2.5）。

- **由此付出的**：**沙箱成为前置依赖而不是可选件**——没有它，可写动作不该开（§3.2.4 的"对架构决策的影响"）；**新增一块执行算力**——冷启动、依赖安装与测试时长都要付，§4.6 把它列进成本项；**验证范围要收敛**——优先跑受影响范围（被修改函数的调用方与相关测试），不做范围收敛的沙箱会慢到没人用（§3.2.5 代价一栏）。还有一条必须写下来的**边界**：沙箱只保证"可编译 / 相关测试通过"，**不保证语义正确**——跨模块改动仍需要人审。

- **证据与来源**：【经验】沙箱与验证流水线在公开材料里多以"平台能力"的形式出现，没有第三方给出的"呈现物可信度提升"的量化对照，本节不点名产品；判定入口是 §4.2（5）的抽检发现率与 §4.2（6）的两个数（验证通过率、合并率）。【公开】"变异测试用于检验测试有效性"是通用方法，不属于任何厂商专有技术，也不对应某个年份或版本。

- **成熟度**：**L2**。① 成立（沙箱运行时与容器 / 微虚拟机是成熟且有文档条目的能力）；**② 核不到**；③ 成立（沙箱是通用设施，接口稳定）。

- **判定方法**：对上周新增的生成测试做一次抽样，注入一个边界缺陷（把 `>=` 改成 `>`），看抽到的测试里有多少会失败——这个比例就是 §4.2（5）的抽检发现率。

- **什么时候值得做**：要开"可写动作"（测试生成 / 修复候选）时——沙箱是它的前置条件，不是配套项。

- **什么时候不值得做**：只做只读三件（补全 / 问答 / 审查建议）时——没有写动作就没有需要验证的呈现物，先把 §3.2.1 的埋点与私有评测集做起来。

#### 5.3.5 自动修复与自主任务：为什么停在 L3

- **旧做法与它的卡点**：从"指出问题"（审查意见、报错、失败测试）到"改掉问题"之间**全靠人**。卡点是**人力带宽**：定位、修改、验证三段都要人做，而前两段在多数情况下是模式化的（失败测试 → 定位 → 小改重试），**人的时间没有被用在判断上**。

- **AI 改变了什么机制**：机制从"生成文本"扩到"**生成可执行改动 + 在沙箱里验证 + 呈现为待审变更**"（§4.2（6））。**关键在多出来的那一环**：验证是可自动化的，因此"候选"与"已验证候选"第一次成为两种不同强度的交付物（§3.2.5）。**如果没有那一环，这一条不是演进，只是把风险提前**。

- **由此得到的**：因为定位与首轮修改被自动化，**人的注意力从"找"转到"判"**；又因为沙箱能自动否掉编译不过的候选，**呈现给人的候选质量下限被抬高了**——这是这一支唯一真实的新增能力，也是它值得做的最小版本。

- **由此付出的**：**三条卡点都还没解**。① **正确性口径不统一**——能跑通不代表符合意图，而"符合意图"没有自动化判据；② **责任无法归属**——多文件改写带来副作用时，追责链条断在"模型给的建议"上；③ **评审成本可能高于自己写**——改动越大，人越要重建一遍上下文才能判断。因此 §4.8 把它排在 0→1→100 的最后一步，且**即便上，也只上"候选 + 沙箱 + 人审"，不交出合并权**（合并的可逆性来自版本控制，见 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)）；§7.3.3 把这一条写成"可写动作的护栏"。

- **证据与来源**：【经验】这一方向的公开材料以演示与自研为主，**没有第三方非厂商的补丁正确性数据**；§5.2 的表把它列为 L3，卡点正是判据②（核不到），本节因此不点名产品。【公开】§6.4 的案例给出一条可直接借用的做法——**阻断只由确定性规则产生**——同一条纪律适用于修复候选的呈现：先沙箱验证，再给人看。

- **成熟度**：**L3**。① 只有演示与自研（没有正式发布条目支撑"可依赖"的定位）；**② 核不到**；③ 不成立（补丁正确性的口径未统一，没有稳定接口可言）。**L3 的动作是"只做最小版本"**：最小版本 = 候选生成 + 沙箱验证 + 人审，不做自动合并。

- **判定方法**：把最近一批候选修复拿出来数两个数——验证通过率与最终合并率；两个数一起看，通过率高而合并率低，说明候选解决的**不是人关心的问题**（§3.2.5 的判据）。

- **什么时候值得做**：测试覆盖与日志质量都够（定位不退化）、且沙箱与回滚路径已经就位时——这时它能把"定位 + 首轮修改"这段模式化劳动接过去。

- **什么时候不值得做**：测试缺失（定位退化为猜）或评审带宽本来就紧时——你会用更多的候选换掉更少的人工判断，净收益为负。

#### 5.3.6 一条可复用的操作：怎么判断某条演进方向该不该跟

上面的分级是结论，下面把它变成三步操作——**以后遇到本节没列到的新名词，用这三步自己判**：

**第一步：定位它替换掉了哪个部件。** 写不出"它替换的是谁"，就说明它没有机制内容。**本主题合法的三种答案**：替换了一个**部件的实现**（如检索从单一向量换成三路 + 重排）、替换了一个**字段的归属**（如审查意见从"一条文本"变成"带等级与归因的结构"）、替换了一个**动作的落点**（如验证从"人看"前移到"沙箱跑"）。判不出来 → 归第 3 类，只改选型表。

**第二步：查三条判据的落点，尤其是②。** ① 与 ③ 通常容易满足，**真正的分水岭是 ②——第三方非厂商的生产案例**。本主题的卡点比多数主题更硬：**代码助手的真实效果数据（采纳率、留存、缺陷率）几乎全部由建设方自述**，而公共基准（补全 / 修复类基准）与**私有仓库的分布差异很大**——同一个模型在榜单上领先，在某个具体仓库上可能毫无优势。**因此本主题里"榜单好"离"已验证"最远**。

**第三步：按级别决定动作，且动作要带退出条件。**

| 级别 | 动作 | 必须同时写下的东西 |
| --- | --- | --- |
| L1 | 可以直接进架构约束 | ——（本主题暂无） |
| L2 | 排进试点，**但不进架构约束** | **退出条件**（什么观测结果出现就停）；本主题还要加一条：**它是否让"可验证性"下降** |
| L3 | 只做最小版本，不做技术选型 | 最小版本是什么（如自动修复只做"生成候选 + 沙箱验证 + 人审"，不做自动合并） |

**本主题特有的准入条件有两条**：① **任何提升自动化程度的方向，都要先回答"出问题时谁能看出它错了"**——本主题的失败几乎全是静默的（启用率下降、意见被忽略、测试断言空洞都不报错），**没有观测面的能力不该上线**；② **任何依赖"更大的模型"来提升质量的方向，都要先证明"检索已经到位"**——因为在延迟与固定成本的双重约束下，检索与重排是唯一能在同一预算内提高信息密度的杠杆（§5.3.1）。

### 5.5 被过度宣传的部分

1. **"AI 写代码占比 X%"**：这个数字通常按"被采纳的字符数"统计，**不等价于"生产力"**；可核验的替代指标是**采纳后留存 + 缺陷率**。
2. **"自主完成整个需求"**：端到端多文件任务目前停在演示；真正的门槛是**评审成本**与**责任归属**，不是模型能力。
3. **"公共基准第一就等于好用"**：公共基准与私有仓库的分布差异很大（约定、框架、领域语言），**私有评测集才是决策依据**。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 被证伪的信号 |
| --- | --- |
| "先沙箱验证再呈现"会成为可写动作的默认要求 | 两年后主流工具仍直接呈现未验证改动且无沙箱 |
| 代码助手的验收指标会从"接受率"转向"采纳后留存 + 缺陷率" | 采购与验收仍只看接受率或"生成占比" |
| 私有化部署会成为受监管行业的默认形态（自托管模型 + 本地索引） | 两年后受监管行业仍普遍依赖外部端点 |
| 符号 / 引用索引会成为代码助手的基础设施（纯向量检索不足以支撑"谁调用它"） | 主流实现仍只做向量检索且对结构性问题无解 |

**这四条全部是【经验】档**：它们是对机制与采购行为的判断，无具名出处、无推导链——**请按"可被证伪"使用，而不是当结论**。

### 5.7 给架构师的行动建议

1. **今年就该做**：可见域前置 + 私有评测集 + 补全（含接受率埋点）。三件事不依赖任何前沿判断。
2. **可以试点**：仓库级问答（符号 + 引用 + 向量三路召回）；审查（非阻断、带归因字段）；测试生成（沙箱 + 变异抽检）。
3. **先别投**：自动修复的"直接合并"与自主多文件任务——责任与评审成本还没有通行做法。
4. **无论哪条**：把**"每次补全的平均成本"**与**"采纳后留存"**作为两条日常指标——前者说明工程效率，后者说明真实价值。

### 5.8 小结

> 本节小结：AI 时代对代码助手的改变**有两条是机制性的**——**上下文从"单文件"变成"仓库级检索 + 重排"**（于是索引与预算成为基础设施）、**生成物从"直接呈现"变成"沙箱验证后呈现"**（于是沙箱成为可写动作的前置依赖）；其余方向（FIM、审查概率化、测试有效性抽检）都是在这两条之上的接口与判据加固。这一支没有一行达到 L1，卡点全在"第三方非厂商生产案例"；因此请按"**机制可验证、效果必须自测**"理解它——效果只能靠你的私有评测集与线上指标去量。

> 💡 **思考锚点**：如果明天你的模型端点不可用，四类能力的降级行为分别是什么？"补全安静地不出现"是合格的，"呈现未经验证的改动"是不合格的——这一条你能立刻回答，说明 §4.7 的纪律已经落地；如果答不上来，你打算先把哪一类能力的降级策略写下来？
