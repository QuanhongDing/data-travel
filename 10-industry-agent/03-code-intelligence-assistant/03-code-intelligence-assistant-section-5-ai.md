## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

1. **机制变了**：上下文从"单文件"变成"仓库级检索 + 重排"；补全从"只看前缀"变成 FIM（前后缀同时给定）；动作从"写"扩到"审查与验证"。**这类变化影响架构决策。**
2. **接口与规范变了**：编辑器与代码托管平台的扩展接口、语言服务器协议、沙箱运行时的接口在演进【公开：以各自规范与文档当前版本为准】。**这类变化影响集成方式。**
3. **只多了产品**：同一套能力换包装。**只在选型表里体现。**

判别方法仍是那一句：**"换一家厂商，这条结论还成立吗？"**

### 5.2 判据与分级

沿用三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定、可预期**。

| 演进方向 | 级别 | 机制变了什么 | 判据落点（可否自行核验） |
| --- | --- | --- | --- |
| 仓库级检索增强（补全 / 问答） | **L2** | 上下文从"单文件"扩到"检索 + 重排后的仓库片段" | ① 成立（检索与向量能力是成熟文档条目）；② **核不到**（公开的采纳数据几乎都来自建设方）；③ 成立 |
| FIM 补全（前后缀同时给定） | **L2** | 生成条件从"只看前缀"变成"前后缀 + 上下文" | ① 成立（多家实现与文档条目可核）；② 核不到；③ 成立 |
| 变更审查（概率性意见） | **L2** | 审查从"确定性规则"扩到"语义判断" | ① 成立（产品功能条目可核）；② **核不到采纳率与误报率的独立数据**；③ 部分成立（意见格式与阈值各家不同） |
| 沙箱内验证后呈现 | **L2** | 生成物先编译 / 先跑测试再给人看 | ① 成立（沙箱运行时是成熟条目）；② 核不到；③ 成立 |
| 测试生成（含有效性抽检） | **L2** | 从"补覆盖"变成"生成 + 用变异抽检验证有效性" | ① 成立；② 核不到；③ 部分成立（有效性口径各家不同） |
| 缺陷定位与自动修复 | **L3** | 从"提示问题"到"给出补丁" | ① 只有演示与自研；② 核不到；③ 不成立（补丁正确性口径未统一） |
| 自主完成多文件任务（自主 PR） | **L3** | 从"单点建议"到"端到端改动 + 提交" | ① 只有演示；② 核不到；③ 不成立（**责任无法归属**） |

**本节没有一行达到 L1**——卡点同样在 ②：**代码助手的效果数据（接受率、采纳后留存、审查采纳率）几乎都来自建设方**，且公共基准与私有仓库的表现差异很大。因此这一支的成熟度应按"**机制可验证、效果必须自测**"理解。

### 5.3 演进方向逐条拆解（核心节）

#### 5.3.1 仓库级上下文：换的是"看什么"，不是"模型多大"

**机制**：上下文来源从"当前文件"扩到"符号定义 + 引用点 + 测试 + 文档"，并经过检索与重排。

**对架构决策的影响**：**索引成为一级基础设施**（符号 / 引用 / 向量三类），并且带来两个新运维项：**新鲜度**（滞后量指标）与**预算切分**（各来源的 token 配额）。这两件事在"单文件补全"时代不存在。

**边界**：上下文更多**不等于**效果更好——边际收益会先陡后平（§2.2）；**判据**是"增加预算的边际收益 < 1 个百分点时，把预算让给延迟"。

#### 5.3.2 FIM：一行改动的收益，来自"与后文一致"

**机制**：生成条件加入后缀，模型能生成"与后文衔接"的片段。

**对架构决策的影响**：**对渲染与合并逻辑有要求**（要处理"前后缀与生成结果的重叠"），并在评测上要能**区分"只给前缀"与 FIM 的差异**——否则无法证明这个改动有效。**可执行动作**：在私有评测集上做 A/B 对照（同一批样本两种条件）。

#### 5.3.3 审查：从规则到概率判断的分工

**机制**：确定性规则负责"必须拦"，模型负责"值得看一眼"。

**对架构决策的影响**：**门禁只能由确定性规则构成**（否则门禁不可预测）；模型意见必须有**置信度与归因字段**，并统计**采纳率 / 忽略率**。**判据**：模型意见造成的返工必须能归因到"哪条提示 / 哪个阈值"。

**边界**：审查意见**不阻断**是可用性的前提；一旦阻断，团队会绕过门禁，反而失去治理点。

#### 5.3.4 沙箱与有效性：把"看起来对"变成"验证过"

**机制**：生成物先在隔离环境编译并跑相关测试；测试生成再用变异式抽检验证有效性。

**对架构决策的影响**：沙箱从"平台的一个部件"变成**代码助手的前置依赖**（没有它，可写动作不该开）；成本上增加一块**执行算力**（沙箱冷启动与测试时长）。

**边界**：沙箱验证只保证"可编译 / 相关测试通过"，**不保证语义正确**——因此仍需要人审（尤其是跨模块改动）。

#### 5.3.5 自动修复与自主任务：为什么停在 L3

**机制**：从"指出问题"到"给出补丁 / 直接完成多文件任务"。**卡点**：① 补丁正确性的口径不统一（能跑通 ≠ 符合意图）；② **责任无法归属**（把副作用交给模型）；③ 多文件改动的评审成本可能高于自己写。**给读者的动作**：把"自主"限定在**候选生成 + 沙箱验证 + 人审**，而不是把合并权交出去。

#### 5.3.6 一条可复用的操作：怎么判断某条演进方向该不该跟

上面的分级是结论，下面把它变成三步操作——**以后遇到本节没列到的新名词，用这三步自己判**：

**第一步：定位它替换掉了哪个部件。** 写不出"它替换的是谁"，就说明它没有机制内容。**本主题合法的三种答案**：替换了一个**部件的实现**（如检索从单一向量换成三路 + 重排）、替换了一个**字段的归属**（如审查意见从"一条文本"变成"带等级与归因的结构"）、替换了一个**动作的落点**（如验证从"人看"前移到"沙箱跑"）。判不出来 → 归第 3 类，只改选型表。

**第二步：查三条判据的落点，尤其是②。** ① 与 ③ 通常容易满足，**真正的分水岭是 ②——第三方非厂商的生产案例**。本主题的卡点比多数主题更硬：**代码助手的真实效果数据（采纳率、留存、缺陷率）几乎全部由建设方自述**，而公共基准（补全 / 修复类基准）与**私有仓库的分布差异很大**——同一个模型在榜单上领先，在某个具体仓库上可能毫无优势。**因此本主题里"榜单好"离"已验证"最远**。

**第三步：按级别决定动作，且动作要带退出条件。**

| 级别 | 动作 | 必须同时写下的东西 |
| --- | --- | --- |
| L1 | 可以直接进架构约束 | ——（本主题暂无） |
| L2 | 排进试点，**但不进架构约束** | **退出条件**（什么观测结果出现就停）；本主题还要加一条：**它是否让"可验证性"下降** |
| L3 | 只做最小版本，不做技术选型 | 最小版本是什么（如自动修复只做"生成候选 + 沙箱验证 + 人审"，不做自动合并） |

**本主题特有的准入条件有两条**：① **任何提升自动化程度的方向，都要先回答"出问题时谁能看出它错了"**——本主题的失败几乎全是静默的（启用率下降、意见被忽略、测试断言空洞都不报错），**没有观测面的能力不该上线**；② **任何依赖"更大的模型"来提升质量的方向，都要先证明"检索已经到位"**——因为在延迟与固定成本的双重约束下，检索与重排是唯一能在同一预算内提高信息密度的杠杆（§5.3.1）。

### 5.5 被过度宣传的部分

1. **"AI 写代码占比 X%"**：这个数字通常按"被采纳的字符数"统计，**不等价于"生产力"**；可核验的替代指标是**采纳后留存 + 缺陷率**。
2. **"自主完成整个需求"**：端到端多文件任务目前停在演示；真正的门槛是**评审成本**与**责任归属**，不是模型能力。
3. **"公共基准第一就等于好用"**：公共基准与私有仓库的分布差异很大（约定、框架、领域语言），**私有评测集才是决策依据**。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 被证伪的信号 |
| --- | --- |
| "先沙箱验证再呈现"会成为可写动作的默认要求 | 两年后主流工具仍直接呈现未验证改动且无沙箱 |
| 代码助手的验收指标会从"接受率"转向"采纳后留存 + 缺陷率" | 采购与验收仍只看接受率或"生成占比" |
| 私有化部署会成为受监管行业的默认形态（自托管模型 + 本地索引） | 两年后受监管行业仍普遍依赖外部端点 |
| 符号 / 引用索引会成为代码助手的基础设施（纯向量检索不足以支撑"谁调用它"） | 主流实现仍只做向量检索且对结构性问题无解 |

**这四条全部是【经验】档**：它们是对机制与采购行为的判断，无具名出处、无推导链——**请按"可被证伪"使用，而不是当结论**。

### 5.7 给架构师的行动建议

1. **今年就该做**：可见域前置 + 私有评测集 + 补全（含接受率埋点）。三件事不依赖任何前沿判断。
2. **可以试点**：仓库级问答（符号 + 引用 + 向量三路召回）；审查（非阻断、带归因字段）；测试生成（沙箱 + 变异抽检）。
3. **先别投**：自动修复的"直接合并"与自主多文件任务——责任与评审成本还没有通行做法。
4. **无论哪条**：把**"每次补全的平均成本"**与**"采纳后留存"**作为两条日常指标——前者说明工程效率，后者说明真实价值。

### 5.8 小结

> 本节小结：AI 时代对代码助手的改变**有两条是机制性的**——**上下文从"单文件"变成"仓库级检索 + 重排"**（于是索引与预算成为基础设施）、**生成物从"直接呈现"变成"沙箱验证后呈现"**（于是沙箱成为可写动作的前置依赖）；其余方向（FIM、审查概率化、测试有效性抽检）都是在这两条之上的接口与判据加固。这一支没有一行达到 L1，卡点全在"第三方非厂商生产案例"；因此请按"**机制可验证、效果必须自测**"理解它——效果只能靠你的私有评测集与线上指标去量。

> 💡 **思考锚点**：如果明天你的模型端点不可用，四类能力的降级行为分别是什么？"补全安静地不出现"是合格的，"呈现未经验证的改动"是不合格的——这一条你能立刻回答，说明 §4.7 的纪律已经落地；如果答不上来，你打算先把哪一类能力的降级策略写下来？
