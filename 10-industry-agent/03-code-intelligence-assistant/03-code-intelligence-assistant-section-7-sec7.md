## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自建 / 买 SaaS / 买私有化交付"打分有三个结构性问题：① 同一列在不同处境下方向相反（"上下文可定制"对自建团队是必需、对三个人的团队是负担）；② 打分表隐含"这些选项互斥"，而真实形态常是组合（自托管模型 + 现成插件 + 自建索引）；③ 最关键的判据（源码能否出域、有没有评测集、责任归属）**不是可打分的维度，而是门槛**——不满足直接出局。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 源码能否出域 | 私有仓库是否允许发往外部端点？ | 不能出域 → SaaS 出局，且必须自托管推理 + 本地索引（**门槛不是权重**） |
| 索引归属 | 符号 / 引用 / 向量索引由谁建、在哪运行？ | 结构性问题（谁调用它）的能力取决于它；也决定合规边界 |
| 评测归属 | 私有评测集由谁建、能否在 CI 里跑？ | 没有它 → 效果只能主观判断，优化不可验证 |
| 动作权限 | 只读建议，还是允许生成并修改代码？ | 可写必须有人审 + 沙箱 + 回滚路径 |
| 责任归属 | 审查意见的返工与事故由谁负责？ | 决定意见是否阻断、是否要求可解释与归因 |
| 承接能力 | 谁维护索引、提示与评测集（按 0.5–1 人年的常备投入量级估算【经验】）？ | 这一支的成本是**长期人力**，不是首版实现 |

> **读法**：先用第 1 条筛掉不可行；再用第 2、3 条筛掉"无法自证效果"的方案；最后用第 4、5、6 条在剩下的里选——**第 3 条最容易被跳过，也是"用了半年说不清有没有用"的根因**。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 自建全栈 | 端到端自持 | 自托管模型 + 自建索引 + 自建交互入口 | 源码不许出域、有平台团队 | 长期人力；模型档位受自托管能力限制 |
| 自托管模型 + 现成插件 | 复用交互与索引 | 用现成的编辑器 / 平台插件，模型指向自托管端点 | 想快速拿到补全体验 | 索引与上下文策略受插件限制（面板效应） |
| 自建检索 + 受控端点的混合 | 分工 | 索引与检索自建，生成走合规端点（按仓库分级） | 公开仓库多、私有仓库少 | 两条路径分别评测；分级判错即泄漏 |
| 商业产品 SaaS | 最快上线 | 端点、索引、交互都由产品提供 | 源码可出域、追求最快 | 私有仓库不可用；成本随席位线性增长 |
| 商业产品私有化交付 | 买成品装进机房 | 产品自带索引与端点，交付含离线包 | 受监管行业、不愿自建 | 定制受产品边界限制；升级依赖厂商 |
| 通用助手改造 | 复用已有工具 | 把通用助手接上代码检索 | 已有助手、诉求很轻 | **缺符号 / 引用索引与沙箱**，结构性问题答不了 |

**这六个候选其实分三族**：**自建族**（自建全栈、自托管模型 + 现成插件、自建检索 + 受控端点）——上下文与索引在自己手里，代价是长期人力；**产品族**（商业产品 SaaS、商业产品私有化交付）——拿到成品能力，代价是边界与形态受产品定；**通用助手改造族**（通用助手改造）——最省事，代价是**缺少代码特有的基础设施**（符号图、沙箱、评测口径）。

**族内可替换，跨族不可换**：自建族内部换的是"交互与索引的实现位置"；从自建族换到产品族，等于**把索引与评测口径一起交出去**——那不是技术迁移，是能力转移。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 索引归属：结构性问题能不能答

**机制是什么**：代码这一支的"结构性问题"（谁调用它、改了会影响谁）只能由**符号与引用索引**回答，向量检索答不了。

**它在各候选中的实现差异**：自建族可自建三类索引；产品族的能力取决于产品是否暴露索引与引用能力（**面板效应**：面板不给你就做不到）；通用助手改造族通常只有向量检索。

| 候选 | 索引由谁建、在哪运行 | 谁决定能力上限 | 静默失效的形态 |
| --- | --- | --- | --- |
| 自建全栈 | 符号 / 引用 / 向量三类都在自己的基础设施里建 | 你自己的解析器覆盖度与刷新节奏 | 解析器覆盖不到的语言、宏与生成代码被"跳过"——答案看起来合理，只是缺项 |
| 自托管模型 + 现成插件 | 索引由插件侧建（可能在客户端，也可能在插件厂商的服务里） | 插件暴露给你的面板 | 面板不给你引用能力 → "谁调用它"被降级成"你可以用编辑器的查找引用" |
| 自建检索 + 受控端点 | 检索自建、生成走受控端点 | 你自己（含"哪些仓库进索引"的分级是否判错） | 分级判错：索引里纳入了本不该出现在这条路径上的仓库 |
| 商业产品（SaaS / 私有化交付） | 产品自带、形态不透明 | 产品边界 | 答不上时**无法区分"索引里没有"与"检索没召回"**——这两类问题的处置完全不同 |
| 通用助手改造 | 通常只有向量检索 | 通用助手 | "谁调用它"永远答不全，且用户不再提问——**日志里没有任何一条错误** |

**由此必然导出的性质**：因为**结构性问题占了开发者日常问题的很大一部分**，所以索引归属决定了这一支的能力上限——**"能不能回答谁调用它"是一个可以在采购阶段直接验证的判据**（拿三个函数去问）。这条性质还有三层常被跳过的推论。

第一层：索引归属决定的不是"效果好一点"，而是**某一类问题能不能答**。这类能力没有中间态——一个只有向量检索的方案，在"这段逻辑在哪"上不是退化而是归零，而它在"这段代码是干什么的"上可以表现得很正常，于是**方案评审时看起来样样都行，上线后只有一类问题没人问**。

第二层：**失败形态是静默的**。这正是 §3.1 把"有没有私有评测集"列为前置约束的同一理由（§3.1 约束四：这类能力的失败不报错、只表现为"没人再用"）。所以索引的验收不能靠"用一阵看效果"，只能靠**当场可执行的动作**——抽函数问调用方，答案要能指到文件加行号。

第三层：索引归属同时决定了**新鲜度归谁管**。索引一旦滞后，答案会指向已经改过的旧行为，而这类错误与"模型答错"在表现上完全一样（§3.2.2 的失效点）：于是滞后从一个体验问题变成**正确性问题**，必须把它做成可见指标（`lag_metric: commits_behind`，模板给的示例阈值取 10 量级【经验：N 由团队按合并频率自定】）而不是靠用户发现。

**公开证据**：本主题已具名的一侧是 **Cursor**（§6.2，2022–2024）——它把仓库级索引作为一等能力，做法一是**按问题类型分派检索通道**（符号 / 引用类走定义与引用、意图类走向量），失败教训是"第一版只做向量检索"（§6.2 做法①与失败教训）【公开】（来源：本主题 §6.2；建设方自述，不构成 §5.2 判据② 要求的第三方案例）。本主题把这条机制落成可执行的配置：§4.2（1）的三类索引（`symbols` / `refs` / `vectors`，配 `lag_metric: commits_behind`）与 §4.2（2）的三步上下文选取；主文件 §2.1 把仓库索引记为"符号表 / 引用图 / 文本向量"三件、§2.3 把索引构建记为"AST / LSP，不靠正则"。同一产品的另一个可交叉核到的痕迹在 **Ch7 §02 §6.4**（`07-agent-evolution/02-feedback-loop/02-feedback-loop-section-6-sec6.md`:286，记 2023–2024 把编辑器内的采纳与回退做成在线反馈信号）——它证明的是"编辑器行为可以当反馈信号"，**不是**"某产品的索引能力如何"，引用时不要把两件事混成一件。索引的获取方式落在语言服务器协议与各语言 AST 解析器上（§4.3 工具链表只以协议 / 类别名出现，本节不补产品名）；某一款解析器对某语言、某版本、某代码形态的支持范围，**请以其官方文档当前版本为准**。

**失效条件**：当团队只要求"补全"而不要求"问答与审查"时，索引的收益下降；但只要出现"这段逻辑在哪"的诉求，就必须有索引。**另一条边界在代码形态上**：仓库里若存在大量宏、模板元编程或编译期生成代码，"符号与引用"这套结构本身就不完整——此时不是索引没建好，而是这类关系在原理上表达不了。可行做法是把这部分**显式标注为"未索引"**，并在回答里说明局限（§8 §CI.2 把它写成一句"宁可说明，不要假装完整"），而不是让答案看起来完整。

#### 7.3.2 上下文策略的可控性：面板效应

**机制是什么**：上下文预算与重排策略是效果的**主要杠杆**（§2.2 的边际收益），可控性决定优化的上限。

**它在各候选中的实现差异**：自建族可完全控制（能按仓库调整预算切分）；产品族通常只能调少量参数；通用助手改造族基本不可控。

| 候选 | 上下文预算与重排由谁定 | 你手里可调的旋钮 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建全栈 | 自己定切分比例与重排策略 | 预算比例、粗排 / 重排、按语法边界切块 | **没有私有评测集就调参**：几个改动方向互相抵消，越调越乱 |
| 自托管模型 + 现成插件 | 插件定 | 少量参数（开关、档位） | 效果到顶后只剩"换模型"这一条路——用稀缺资源（延迟）去换不稀缺的东西（档位） |
| 自建检索 + 受控端点 | 检索侧你定、生成侧受端点限制 | 检索与切块（生成侧不可调） | 把"上下文可控"误读为"端点可控"，于是以为问题已经解决 |
| 商业产品 | 产品定 | 面板上的开关与档位 | **面板效应**：面板上没有的旋钮等于不存在，优化意图不可执行 |
| 通用助手改造 | 基本不可控 | 把文件手工贴进对话 | 补上下文的成本落在每个提问的人身上，且无法复用 |

**由此必然导出的性质**：因为**效果的边际提升主要来自上下文而不是模型**，所以"上下文是否可控"比"模型有多强"更影响长期效果（也和 §4.6 的成本结构一致：上下文 token 通常大于生成 token）。这条性质还带出两层推论。

第一层：**可控性同时是账单的可控性**。既然上下文 token 通常大于生成 token（§4.6 把这条记为"上下文页均 2–6k tokens"量级的【经验】结论，§6.3 也记同一条【经验】），那么"能控制上下文"就等于"能控制成本的主要项"，而"只能换模型"的方案恰好把杠杆放在次要项上——**这不是效果问题，是同一个动作在质量表与账单上同时算错**。

第二层：**可控性只有在有评测集时才可兑现**。没有同一批样本的前后对照，任何预算调整都无法证明有效（主文件 §2.2 要求指标必须能在 CI 里自动跑）。所以"面板给了我几个旋钮"不等于"我能优化"，它只等于"我有了几个能动而不知方向的参数"。

**公开证据**：本主题已具名的证据是配置与曲线两条。配置侧：§4.2（2）的上下文预算切分表（按来源四分，比例写法均为【经验】）连同它的两条判据——**生成结果引用了多少上下文里的符号**（比例过低说明重排没起作用）、以及"增加预算的边际收益低于 1 个百分点时把预算让给延迟"。曲线侧：主文件 §2.2 把质量与上下文的关系记为**先陡后平**，并给出可执行的判据——**边际收益低于 1 个百分点就不再堆预算**【经验】（该判据的校准依据是自有评测集的分辨率，不是行业值）。私有化一侧的机制复述见 §6.3 通义灵码企业版（2023–2024，建设方自述）：它用检索与重排补模型档位的劣势，做法②即"用检索与重排补质量"；做法②之所以成立，前提正是**检索与重排在你的可控范围内**，而模型档位不在（受自托管能力限制）。**一处必须写明核不到**：各家产品的上下文窗口如何切分、重排用什么信号，本主题与全书他处都没有给出可核验的产品文档出处，因此本节不给产品名与年份——判定入口是问一句"这个预算比例我能不能自己改，改完能不能在同一批样本上比较"，答不上后一问，说明可控性不在你手里【经验：以各产品官方文档当前版本为准】。

**失效条件**：当你自建了检索层（把上下文掌握在自己手里）时，产品只提供生成端点是可以接受的——**这正是"自建检索 + 受控端点"这一候选存在的理由**。**另一条边界是评测集**：连私有评测集都没有的团队，"上下文可控"只是一句愿望——此时更该先做的是把评测集立起来（§4.1 把它排在第二步、补全之前），而不是先讨论预算比例。

#### 7.3.3 可写动作的护栏：沙箱与回滚

**机制是什么**：允许"改代码"的那一刻起，就必须有验证（沙箱）与可逆（版本控制 + 人审）。

**它在各候选中的实现差异**：自建族可控（沙箱与验证流水线自建）；产品族看它是否提供沙箱与"验证后呈现"（有的只给建议文本）；通用助手改造族通常没有。

| 候选 | 验证发生在哪 | 回滚靠什么 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建全栈 | 自建沙箱（容器 / 微虚拟机）里编译并跑受影响测试 | 版本控制 + 人审 + 改动范围可枚举 | 沙箱只证明"编译过、相关测试通过"，语义错误照样进主干——**沙箱不是正确性证明** |
| 产品族 | 取决于它是否提供"验证后呈现" | 平台侧变更流程与提交历史 | 只给建议文本 → 验证回到人身上，而"省掉这一环"正是引入它的理由 |
| 通用助手改造 | 通常没有 | 无 | 改动直接贴进编辑器，回滚靠事后发现 |

**由此必然导出的性质**：因为**未验证的改动进入主干后，代价由整个团队承担**，所以"有没有沙箱"直接决定"能不能开可写动作"——**没有沙箱的方案，可写动作应当推迟到沙箱就位之后**。这条性质的重心常被读错：它约束的不是"可写动作好不好用"，而是**"可写动作该不该开"**。同一个机制还给出另一条工程判据：**呈现必须区分"已验证 / 未验证"**（§4.2（6）把这条写成硬判据——呈现记录里必须有"跑过 / 没跑过"的标记），因为一次未验证候选被当成修复呈现，损失的不是那一条建议的可信度，而是整条链路之后所有建议的可信度——§3.2.5 的失效点与 §3.5 的反模式把这条同一个现象从两个角度写了两遍。

还有一层与"回滚"有关的推论：可写动作的**回滚路径必须天然存在**，而不是事后补。改动走版本控制、范围可枚举，回滚就是一个动作；改动若发生在版本控制之外（直接写文件、跨多个仓库同时改），回滚就变成一次考古。所以"有没有沙箱"与"改动是否走版本控制"是同一道门的两个把手，缺一个都不能开。

**公开证据**：隔离执行环境在本书他处是成熟条目——**Ch5 §02 §3.2.8 沙箱执行**（`05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md`:165 起的准入四件套；:179 给三条失效点：共享宿主内核未限制系统调用导致逃逸、沙箱内挂长期凭证、为省冷启动而复用实例导致上一个会话的残留数据成为下一个会话的输入；:181 给判定方法：把挂载面清单与镜像依赖清单对一次账，再做一次滚动重启看实例是否被复用）。回滚侧落在**版本四元组与发布指针**（Ch5 §02 §4 第 7–8 步，`05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-4-sec4.md`:17、:18，判据是"回滚是否只需改一个指针、是否演练过"）。本主题把这些落成 §4.2（6）的修复验证流水线（先跑受影响测试、超时再缩小范围）与 §4.3 的沙箱行（"容器 / 微虚拟机"，选型判据是"是否需要跑编译与测试"）。**范围邻接要写明**：Ch5 那两条证明的是"隔离执行这一层有成熟工程条目"，不是"某助手产品会验证自己的补丁"；本主题 §6 的四个案例里没有任何一例给出"验证通过率"这类可核验数字，因此**本节不给该数字**，只给可自行采集的口径（见 §8 §CI.6 第二层的四条前置条件）。

**失效条件**：只读场景（问答 / 审查建议）不需要沙箱；这也是"先做只读、后做可写"的原因。**另一条边界在沙箱的验证范围上**：它验证的是"能不能跑通"，不是"改动是否符合意图"。当失败模式是"跑得通但语义错"（典型是边界条件、并发与权限判断）时，沙箱给出的绿灯反而是最危险的那类信号——它把人审的注意力从"这里可能错"改成了"这里已经验过"。因此 §5.3.4 把沙箱的结论限定为"把看起来对变成验证过"，而不是"把验证过当成对"。

#### 7.3.4 评测口径与成本曲线

**机制是什么**：三层评测（离线基准 / 私有集 / 线上指标）与成本曲线形状共同决定长期可行性。

**它在各候选中的实现差异**：自建族可自建私有集与线上埋点；产品族通常提供"接受率"这类线上指标，但**私有评测集仍需自己建**（否则无法比较路径）；成本上自建是台阶（GPU 固定成本），产品是线性（席位 / 调用量）。

| 候选 | 私有评测集由谁建 | 线上指标由谁埋 | 成本曲线形状 | 典型失败形态 |
| --- | --- | --- | --- | --- |
| 自建族 | 你自己（从历史提交构造三套样本） | 你自己（留痕必须含"是否采纳"与滞后量） | 台阶形（GPU + 人力，与用量无关） | 建了评测集却没有 CI 回归 → 指标不可比，"优化"退化为手测 |
| 产品族 | **仍需你自己建** | 产品提供接受率一类 | 线性（席位 / 调用量） | 只读产品报表 → 拿一个可被抬高的指标当结论 |
| 通用助手改造 | 无 | 无 | 前期最省 | 回答不了"用了半年有没有用"，只能靠感觉 |

**由此必然导出的性质**：因为**接受率是可被"看起来合理"的建议抬高的**（用户懒得改），所以只有"采纳后留存"能防止指标虚高——**这一项必须在你的埋点里，而不是依赖产品报表**。这条性质还带出两层推论。

第一层：**"谁建评测集"与"谁付成本曲线"是两件事**。产品族可以把模型、索引、交互一并给你，把成本曲线变成一条漂亮的线性，但**评测口径不会随产品一起交付**——因为评测集要的是"你的仓库的历史提交"，这件事在任何商业模式下都只能由你完成。这也是 §7.1 把"评测归属"单列成一条判据、而不是并进"能不能采购"里的原因。

第二层：**三层评测的分工不能互相替代**。离线公共基准回答"横向对标"，局限是它的分布与你的仓库差得远；私有集回答"业务拟合"，局限是样本要持续扩充、且可能过拟合历史行为；线上指标回答"真实价值"，局限是受使用习惯影响、需要样本量。三层缺一层的后果各不相同：缺第一层不知道自己在什么位置，缺第二层不知道改动是否真的有效，缺第三层不知道值不值。

**公开证据**：本主题给出的可核材料是**口径**而不是数值——主文件 §2.1 定义接受率与审查采纳率、§2.2 定义采纳后留存并给出"两个指标一起看"的判据（接受率高、留存低＝补的内容与仓库约定不一致）、§2.2 还给评测样本的形态（仓库状态、光标位置、预算、期望片段）；§4.2（8）把三套样本表列全，其判据是"样本量要能分辨 1 个百分点"【经验：以自有评测集的分辨率为准】；§4.2（3）把补全链路的硬超时做成可验证的实现（超时返回空），对应 §3.2.1 失效点（"这类失败的信号是'启用率骤降'，而不是任何错误日志"）与 §4.1 第 4 步的判据。跨主题一侧，**Ch2 §07 登记的 SWE-bench 一类代码修复基准**是本节唯一可核验的公共基准（`02-data-science/07-eval/07-eval-section-3-sec3.md`:142 与 :207 把它记为公开 Agent 基准；"任务形态与你的产品是否同族"这条判据在 `02-data-science/07-eval/07-eval-section-4-sec4.md`:160），同一章还明记一条限定：**同一基准换 harness 后成功率不可比，只能用来比较方案、不能当上线判据**（`02-data-science/07-eval/07-eval-section-5-ai.md`:38）——**它证明的是"公共基准存在"，不是"某产品效果如何"**。本主题 §6 的四个案例全部来自建设方自述（§6.1–§6.3）或匿名案例（§6.4），§6.7 的 ROI 表也明令不得出现无出处的提升百分比——因此**本节不给任何采纳率、留存率或提升幅度**，只给可自行采集的口径与可自行执行的动作。

**失效条件**：当团队只做只读补全、且人数很少时，私有评测集的建立成本可能高于它换来的收益——此时退一步的做法是把"离线公共基准 + 线上留存"两件留下、把私有集推迟；但推迟的前提是**埋点先补齐**（§4.5 模板 2 的留痕必须有 `accepted` 与 `index_lag_commits` 两个字段），否则推迟的不是评测集，而是判断能力本身。**另一条边界在归因上**：补全的线上指标与"交付质量变化"之间只能建立相关、不能建立因果——同一时期往往还有别的变更在发生，所以把留存直接写进汇报标题是一种越界，可以说的是"这一批采纳的片段在若干周后仍在代码中的比例"这个可采集的事实。

#### 7.3.5 计价基准：按席位还是按调用，决定了你把哪个指标当 KPI

**机制是什么**：候选方案的计价基准不同——**席位制**按"多少个开发者开了这个功能"计费；**按量制**按 token / 调用计费；**自建**的实际支出是 GPU 固定成本 + 人力（与用量无关）。

| 计价基准 | 边际成本 | 优化目标被引向哪里 | 典型失败形态 |
| --- | --- | --- | --- |
| 席位制 | 近零（多一人用不额外花钱） | "让更多人装上" | 装了不用的人在口径下与重度用户等价——**高估价值直到续费时才发现** |
| 按量制 | 随调用线性 | "每次调用更省" | 为压单价而砍上下文 → 质量下滑，而下滑是静默的（没有报错，只有留存变低） |
| 自建 | 近零（GPU 与人力是固定项） | "把固定成本摊薄"（提高使用密度） | 提高使用密度的手段若只剩"催人用"，指标会先涨后落 |

**为什么这是机制差异而不是商务差异**：因为**计价基准会决定优化目标被引向哪里**。

- **按席位**时，边际成本为零（多一个人用不额外花钱），于是**"让更多人装上"成为自然的 KPI**——而"装上"与"用起来"是两件事：一个装了但不用的人，在席位口径下与一个重度的用户等价。**这会系统性高估价值**，直到续费时才发现。
- **按量**时，账单随调用线性增长，于是靶点落到**"每次调用更省"**（更小的上下文、更准的检索、更低的档位）——这正是 §3.2.1 与 §6.3 说的"检索优于换模型"会成为主动行为的原因。
- **自建**时支出是台阶（GPU 与人力），于是靶点变成**"把固定成本摊薄"**（提高使用密度），这与按席位制的方向一致但动机不同。

**它对架构决策的影响**：**不要把"单价便宜"当成选型依据，要问"计价基准会把优化目标引向哪里"**。一个可核查的做法是把两者换算到共同口径——**"每次补全的等效成本"**：席位制 = 年席位费 ÷ 年补全次数；按量制 = 账单 ÷ 补全次数；自建 = 固定成本 ÷ 补全次数。**这一步会把"感觉贵"变成"在哪一段贵"，也会暴露席位制下真实使用密度。** 而真实使用密度（活跃使用人数 ÷ 开通人数）恰恰是席位制选型里最该提前量、最容易漏量的一个数。

**边界**：等效单价只用于同一量级内的比较；它不能解释合规不可迁（那是 §7.1 第 1 条的门槛），也不能替代"采纳后留存"这个价值指标——**成本口径回答"贵不贵"，留存回答"值不值"。**

**公开证据**：本主题给出的是**成本块与推导链**，没有价格——§4.6 把这一支的账单拆成四块（推理、索引与检索、沙箱执行、自托管固定成本），并把它标为【推算：口径固定，单价按你的采购口径代入】，算例的前提是"300 名开发者 × 每人每日 600 次补全"（【经验】，得十万级次/日 的量级）；§4.6 的判据是"把每次补全的平均成本作为日常指标"。台阶形的写法在**模型网关侧**可交叉核到同一条曲线（`06-multi-model/03-model-gateway/03-model-gateway-section-7-sec7.md`:199 把自建族记成 `Cost_self(V) = H_self × 人均年成本`，与调用量 V 无关；:191 记"自建族是台阶形、平台 / 云族是线性"这条判据）；同一主题的 §6.3 记自托管固定成本是台阶形，并给出可换参数重算的推导链——**单位成本 = 固定成本 ÷ 请求量**，固定成本与请求量无关则两者成反比（§6.3 具体数字行）。**一处必须写明**：本节与全书他处都**没有可核验的单价**，所以任何"每席位多少、每千 token 多少"的写法都不在本节的证据范围内；判定入口是把你手里的报价单代入上面那条式子，换算成"每次补全的等效成本"再比。

**失效条件**：当计价基准与用量脱钩（例如按仓库数、按年打包、按账号数封顶）时，"计价基准会把优化引向哪里"这条推论不成立——此时要换一个判据：**计价维度与你的增长方式是否同向**。若计价按资产或用量走而你的仓库数与人数在涨，成本随规模同向上升；若按端点或席位打包而人数不涨，则几乎不额外计费。**另一条边界在自建一侧**：自建的"边际成本近零"只在容量装得下时成立——GPU 容量是按并发上限而不是按峰值买的（§4.6 的优化动作把这条写成"别按峰值买"），一旦请求量越过容量，排队与降级出现，边际成本就从"近零"跳成"一次扩容"，台阶的下一级台阶本身就比线性贵。

#### 7.3.6 责任归属与承接能力：谁承担返工，谁长期养这套东西

**机制是什么**：§7.1 的第 5、6 条判据（责任归属、承接能力）不是软性考量，它们各自对应一组**可观察的机制差别**。**责任归属**决定"意见能不能阻断"——阻断意味着有人要为"拦错了"负责，建议意味着没有人为"漏掉了"负责；**承接能力**决定"这套东西在第三年还在不在"——索引要跟着解析器升级、提示要跟着仓库约定变、评测集要跟着语言与框架扩，这三件事都是按年发生的，不是一次性的。

**它在各候选中的实现差异**：

| 候选 | 返工与事故归谁 | 意见能不能阻断 | 长期维护落在谁身上 | 典型失败形态 |
| --- | --- | --- | --- | --- |
| 自建全栈 | 组织自己（要指定到角色，不是"团队"） | 可以，前提是把确定性规则与模型意见分开 | 自己的平台团队（索引 / 提示 / 评测集三项常备） | **无人明确承接** → 索引滞后、提示过期，能力静默退化，而报表上一切正常 |
| 自托管模型 + 现成插件 | 组织对结果负责、插件对交互负责 | 通常只能做建议 | 组织（提示与评测集）+ 插件方（交互） | 责任被切成三块（模型 / 插件 / 我们），出事时三块互相指认，最后没人改 |
| 自建检索 + 受控端点 | 组织自己 | 可以 | 组织（两条路径要分别有人看） | 两条路径不分开评测与归因 → 效果掉了分不清是检索还是端点 |
| 商业产品（SaaS / 私有化交付） | 厂商对产品负责，**不对你的采纳负责** | 取决于产品是否支持分级 | 厂商（索引与升级） | 把阻断交给概率系统 → 团队整体绕过门禁，真实问题被一起忽略 |
| 通用助手改造 | 无明确归属 | 没有阻断通道 | 无人 | 诉求一升级就得重做，而上一版投入无处回收 |

**由此必然导出的性质**：

第一层：**责任归属决定的不是"意见准不准"，而是"门还可不可预测"**。模型判断是概率性的，一旦它进阻断级，同一个改动今天过、明天不过，团队学到的不是"这里有问题"，而是"门是随机的"——随后发生的不是"更谨慎"，而是**整体绕过**（§3.5 把这条列为反模式，§6.4 的匿名案例把它记成第一版的失败教训）。所以"阻断只由确定性规则产生"不是保守，而是让阻断这个动作**有承接方**：规则的写、改、误报处置都能落到一个具体的人。

第二层：**承接能力是长期年金的形状，不是首版成本**。§7.1 把它估成 0.5–1 人年的常备投入量级【经验】——这里的"常备"是关键：它不是"上线时投 0.5 人年"，而是"此后每年都要有人在这三件事上花时间"。这条推论解释了 §7.7 里那句硬结论为什么成立：跨族迁移最贵的一格是"把索引与评测交出去之后的收回"，因为收回的不只是技术，还有**没人承接的那段时间里已经不成立的评测口径**。

第三层：**责任越模糊，方案越只能停在只读**。只读三件（补全 / 问答 / 审查建议）的失败代价是"这条建议没用"，可写动作的失败代价是"主干里多了一个错的改动"。前者不需要人担责，后者必须有人担责——所以一个责任归属谈不清的组织，**技术上开了可写动作也只是把风险前移**，而不会真的获得那段效率。

**公开证据**：本主题的审查形态只有一份材料，且**它是匿名案例、只作机制示例、不作举证**——§6.4（某大型互联网公司，2021–2024）给的是分工而不是产品：确定性规则进 CI 门禁、模型意见只做建议并带归因字段；"阻断级规则十几条以内"是【经验】档；"采纳率与忽略率一起看"与"意见在提交时给出（改的是采纳成本，不是延迟）"是它的两条做法。本主题把这条分工落成可执行的配置与判据：§4.2（4）的三段结构与它的判据（**阻断级只能由 `rules` 产生**）、§4.5 模板 3 的归因输出（`check` / `level` / `score` / `evidence.similar_incidents`）。与静态分析的边界见主文件 §2.4：**用助手替换 Lint 会让门禁不可预测**。承接能力一侧的证据是运维项而非数值：§4.7 把"依赖服务变更（解析器升级）"单列为一项演练，§4.7 的纪律是"补充是可缺失能力、审查与问答可等待"——这条纪律之所以成立，前提正是**有人知道它坏了**。跨主题可核的同款设施是 **Ch5 §02 的版本四元组与回滚**（`05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-4-sec4.md`:17、:18）——它证明的是"回滚这件事有成熟做法"，不是"某助手产品会把责任分清"。**一处必须写明核不到**：各家产品在"模型意见能不能阻断"上的默认行为与可配置范围，本主题与全书他处都没有可核验的产品文档出处，本节不给产品名与年份；判定入口是问一句"这条意见不通过，能不能拦住合并；如果拦错了，谁来关掉它"——**后一问答不上，说明阻断没有承接方**。

**失效条件**：当组织愿意为返工承担全部责任（例如只有一个团队自产自用、审查意见的误报由写代码的人自己消化）时，"责任归属"不再是分族依据，此时按 §7.3.1–§7.3.5 的其余机制选即可。**另一条边界在承接能力的计量上**：如果团队把索引与评测的维护挂在一个"顺带做"的人身上，账面投入会远低于 0.5 人年【经验】，但这不是承接能力够用，而是**这份投入被隐藏在了别人的加班里**——它的可观察信号是索引滞后量（`commits_behind`）在需求高峰期持续上升，以及评测集规模半年没有增长；两者都不需要访谈即可采集。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 推理（补全 / 问答请求数 × 单次上下文与生成量 × 单价）
      + 索引与检索（索引构建与刷新 + 向量存储 + 检索算力）
      + 沙箱执行（编译与测试的算力 × 开了可写动作的比例）
      + 长期人力（索引 / 提示 / 评测集的常备维护，按人年计）
      + 自托管固定成本（GPU 与预留实例，与调用量无关）
      + 迁移与重建（口径重建 + 历史指标不可延续）
```

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| 自建族 | 人力（索引 / 提示 / 评测的长期维护）+ GPU 固定成本 | 索引重建与解析器升级的适配、提示与评测集维护、沙箱算力 | 随语言数与仓库数增长 |
| 产品族 | 席位 / 调用量计费 | 私有评测集仍需自建、上下文不可控导致的额外优化成本、升级行为变更 | 随开发者数与调用量线性增长 |
| 通用助手改造族 | 最省的前期投入 | 结构性问题答不了 → 团队另建搜索工具（重复投入） | 随诉求升级而被迫重做 |

**成本函数的三条判据**：① **自建族是"台阶形"**（GPU + 人力，不随调用量变），人数多时最省；② **产品族是"线性"**（席位与调用量），人数少时最省；③ **通用助手改造族前期最省但天花板最低**——它省下的钱通常会以"另建搜索工具"的形式花回来。

**三条量级推导**（都可换参数重算）：

1. **自建族的台阶与摊薄**（【推算】）。**等效单价 = 年固定成本 ÷ 年请求量**。推导链：固定成本（GPU 与人力）与请求量无关，而年请求量 = 开发者数 × 人均日请求数 × 年工作日；以 §4.6 算例的参数（300 人 × 每人每日 600 次，【经验】；得十万级次/日）代入，年请求量落在 10⁷ 量级（工作日按每年两百多天计，同属【经验】）。所以**只要人数翻倍而固定成本不变，等效单价就减半**——这就是"自建台阶"在账面上的准确含义。反过来读这条式子更关键：人数少时台阶的"高度"无法被摊薄，此时线性方案在结构上就是更优的，**而不是"更贵但更省事"**。

2. **上下文是账单的主项，不是生成**（【推算】）。单次请求成本 ≈（上下文 token 数 + 生成 token 数）× 单价。推导链：两者共用同一条 token 计价线，因此成本占比等于 token 数占比；而 §4.6 与 §6.3 都把两者的关系记成"上下文 token 大于生成 token"，量级是数倍（【经验】）。结论直接落到动作上：**单次成本对上下文长度的弹性大于对模型档位的弹性**——这正是 §4.6 把优化动作排成"先重排与预算、再模型档位"的原因，也是 §7.3.2 把"上下文可控性"称作主要杠杆的账面依据。

3. **真实使用密度是席位制的隐藏分母**（【推算】）。**席位制等效单价 = 年席位费 ÷ 实际调用次数**，而实际调用次数 = 开通人数 × 真实使用密度 × 人均日调用次数 × 年工作日。推导链：若真实使用密度从"人人日用"降到"约一半人日用"（假设属【经验】），分母减半、等效单价翻倍——**账单没变，单价翻了一倍**。所以席位制选型里最该提前量、最容易漏量的不是单价，是真实使用密度；它也是唯一能在采购谈判之前用一次试点量出来的数（试点期间统计"活跃使用人数 ÷ 开通人数"）。

**一条经验判据**（【经验】）：多数团队在**数十到一两百名开发者**的规模上，产品族的线性账单低于自建族的台阶，因为台阶还没被摊薄；进入**数百人以上**之后，台阶的那一级开始被摊平，而产品族的账单仍按人头涨，此时结构上应该重算一次上面第 1 条的式子，而不是沿用两年前的结论。这条线是经验线而非定律——它随"人均日请求数"与"自建固定成本"两个参数漂移；可自行核验的做法是把这两个参数各取高低两档，重算四次。

**还有一项常被忽略的成本：过期资产**（【经验】）。提示、评测样本与审查规则都会随仓库演进而过期——函数改名了、口径改了、某种写法在仓库里已经绝迹。它们不会自动消失：要么开始失效（评测样本永远跑不过，于是整批被忽略），要么静默地对着一个不再出现的场景求值（于是覆盖率数字看起来比实际更高）。**资产库越大，这类"僵尸资产"的绝对数量越多**。判断方法很直接：随机抽 20 条规则或评测样本，逐条问"它上次命中是因为真问题，还是因为被评测的对象已经变了"——这个动作与 §6.4 给审查案例的那套自测动作是同一个形状，也是 §7.3.6 说的"承接能力"在账面上的可见形式。

### 7.5 决策树（每个分支都要有阈值依据）

1. **私有仓库的源码能否出域？**
   - 不能 → **SaaS 出局**；进入第 2 问。
   - 能 → 进入第 3 问。
2. **有没有人能长期维护索引与评测（按 0.5–1 人年的常备投入量级估算【经验】）？**
   - 有 → **自建全栈**或**自建检索 + 受控端点的混合**（后者适合公开仓库多、私有仓库少的组织）。
   - 没有 → **商业产品私有化交付**（把索引与端点维护转移给厂商）。
3. **是否要求"结构性问题可答"（谁调用它 / 这段在哪）？**
   - 要求 → 必须有符号与引用索引 → **自建族或支持索引的产品族**；进入第 4 问。
   - 不要求（只要补全） → **商业产品 SaaS** 或**自托管模型 + 现成插件**最省。
4. **是否要开放"可写动作"（生成测试 / 修复）？**
   - 要 → 必须有沙箱 + 人审 + 回滚路径（自建族可控；产品族要看是否提供沙箱）。
   - 不要 → 只做只读三件（补全 / 问答 / 审查建议），成本与风险都低。
5. **审查意见的误报与漏报，能落到一个具体角色吗（责任归属）？**
   - 能（有 Owner、误报要有人关掉、规则改动有评审） → 可以把**确定性规则**放进阻断级，模型意见仍只做建议。
   - 不能 → **模型意见永不阻断**（责任无法归属时，阻断只会训练团队绕过门禁）；此时问题的答案不在候选表里，而在"阻断这件事有没有承接方"上（§7.3.6）。

**阈值依据**（逐条给来源）：

- **①「能否出域」**：判据是**可判定的事实**而不是态度——私有仓库的源码是否允许发往组织之外的端点。来源是 §3.1 第 1 条约束与 §7.1 把"门槛"与"权重"分开的那句话。这一条没有金额阈值，也没有"部分出域"的中间态：允许出域与不允许出域的组织，候选集合是不相交的。
- **②「有人长期维护」**：依据是 §4.7 的运维项清单与 §7.3.6 的承接能力——索引要跟解析器升级、提示要跟仓库约定、评测集要跟语言与框架扩，这三件事按年发生。用 0.5–1 人年【经验】只用来区分"有专人做 / 顺带做"，**不要当门槛用**；更可靠的判据是"这三件事各自有没有一个能被叫到名字的人"。
- **③「结构性问题可答」**：依据是 §7.3.1 的机制——符号与引用关系只能由结构化索引回答，向量检索在这类问题上不是退化而是归零。判定不问需求方想不想要，而看**日常问题里有没有"谁调用它 / 这段在哪"**：有，就必须进"索引在自己手里"那一族。
- **④「要不要开可写动作」**：依据是 §7.3.3 的机制——沙箱证明的是"跑得通"，版本控制提供的是"可回滚"，两者缺一个，可写动作的失败代价就由整个团队承担。这条分支的判据不是"我们想不想让 AI 改代码"，而是"沙箱与回滚是否都已就位"。
- **⑤「责任能不能落到角色」**：依据是 §7.3.6 与 §6.4 的分工——阻断级只能由确定性规则产生，而规则的写、改、误报处置要落到具体的人。举不出这个人，就说明"阻断"没有承接方。这条分支**不给数字**：判定入口是一句可以直接问出口的话——"这条意见拦错了，谁去关掉它"。

**树里没有"预算"节点**，这一点需要单独说明：把"预算是否超过某个数"作为分叉，等于**用一个尚未被推导出来的结果当输入**。预算是 §7.4 三条推导的结果——开发者数与人均请求数决定台阶能不能摊薄，真实使用密度决定席位单价的分母，语言数与仓库数决定长期人力。把预算当分叉节点最常见的后果是：**为省许可费选了台阶形方案，而人数不够、台阶摊不薄，两年后发现人力账单反而更高**——许可费是一次的账，人力是按年滚的账，两者形状不同，而立项时只看得到前者【经验】。

**阈值的诚实说明**：上表的"0.5–1 人年"与"三个函数"（索引验证）都是【经验】档——用来区分"这一档"与"那一档"，请用你自己的排期校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 源码不出域、团队有平台能力 | 自建全栈 | 商业产品私有化交付 | 全自建首版慢，可先只做补全 |
| 源码不出域、团队小 | 商业产品私有化交付 | 自托管模型 + 现成插件 | 插件方案对索引与上下文不可控 |
| 公开仓库多、私有仓库少 | 自建检索 + 受控端点（按仓库分级） | 商业产品 SaaS | 分级判错即泄漏，需要演练保障 |
| 只想要补全、源码可出域 | 商业产品 SaaS | 自托管模型 + 现成插件 | 席位线性成本在人数多时不划算 |
| 要求"谁调用它"等结构性问题 | 自建族（索引自建） | 支持符号索引的产品族 | 纯向量检索答不了结构性问题 |
| 已有通用助手 | 自建检索层 + 通用助手做生成 | 商业产品 SaaS | 缺符号图与沙箱，可写动作做不了 |
| 审查意见要能阻断、且责任可落到 Owner | 自建族（规则与模型分开，**阻断只由确定性规则产生**） | 支持分级阻断的产品族 | 把阻断交给概率系统后，门变成随机的，团队会整体绕过（§7.3.6） |

**四个常见组合**（各说明职责边界与运维代价）：

1. **自托管模型 + 现成插件 + 自建私有评测集**：插件管交互与补全，自建索引层管结构性问题，私有集管口径。运维代价：**插件的上下文策略不可控**，所以第 7.3.2 条的面板效应仍在，结构性问题只能靠自建索引那一层补；私有集要随语言与框架持续增补，而这份工作没有任何供应商能替你做（§7.3.4）。
2. **自建索引 + 受控端点 + 模型网关分级**：索引自建，生成按仓库分级路由（§3.2.7 的形态，落地物是 §4.5 模板 1 的 `repo_classes` 与 `policy`）。运维代价：**两条路径要分别评测与归因**，否则效果掉了分不清是检索还是端点；仓库标签的复核机制必须覆盖新仓库与迁移后的仓库，否则分级会随时间静默失效（§3.2.7 的判定方法就是一次演练）。
3. **商业产品 SaaS + 自建私有评测集 + 只读三件**：产品提供补全、问答与审查建议，私有集自建，可写动作不开。运维代价：**接受率与采纳后留存必须自埋**（§7.3.4）；席位口径下要按月统计真实使用密度（§7.3.5），否则续费前算不出等效单价。
4. **私有化交付 + 沙箱 + 留痕**：适合受监管、且确实要开可写动作的组织。运维代价：升级依赖厂商的发布节奏，行为变更要在你的私有集上重新过一遍；阻断级规则要收敛到十几条以内【经验】（§6.4），否则门会从"拦住问题"变成"制造摩擦"。

四个组合的共同点是**入口低门槛、关键动作强约束**：面向所有人的补全走成本最低的那条路，面向"要拦 / 要改"的动作走可举证、可回滚的那条路。反过来设计——全量强约束（门变成摩擦）或全量弱约束（关键动作没有承接方）——是这一支最常见的形态错误。

**组合的两条次序原则**：① **先把索引与评测集立起来，再选生成端点**——生成端点是可替换的，索引与评测是资产；② **先把可见域与出网白名单收口，再谈效果**——合规是门槛。

### 7.7 选错的代价与迁移成本

**反模式：把"开通人数"当价值** —— 症状是汇报里的成绩是"已开通多少人" → 后果是装了不用的人在席位口径下与重度用户等价，价值被系统性高估，直到续费时才被发现；机制上这是 §7.3.5 说的"计价基准把优化目标引向了装上" → 正确做法：汇报同时给两个数——**活跃使用人数 ÷ 开通人数**（真实使用密度）与采纳后留存，前者是可当场采集的，后者是唯一抗操纵的价值指标。

**反模式：把助手当 Lint 用** —— 症状是用模型意见替换了原来的确定性门禁（"让 AI 来判断该不该拦"） → 后果是门变成随机的：同一个问题今天过、明天不过，团队学到的不是"这里有问题"，而是"绕过去"；机制上这是 §7.3.6 说的"阻断必须有承接方"，概率系统无法承接"拦错了谁负责" → 正确做法：**阻断级只由确定性规则产生**（§4.2（4）的判据），模型意见永远是建议，靠归因字段与阈值迭代。

**反模式：先开可写动作、后补沙箱** —— 症状是"先让它直接改代码，验证以后再加" → 后果是一次未验证候选被当成修复呈现，损失的不是那一条建议的可信度，而是此后所有建议的可信度；机制上这是 §7.3.3 说的"沙箱决定的是可写动作该不该开"，而不是好不好用 → 正确做法：呈现必须区分"已验证 / 未验证"（§4.2（6）的判据），未验证的只作为线索呈现，合并仍走人审。

**反模式：拿接受率当唯一 KPI** —— 症状是报表只报接受率，优化动作围绕它转 → 后果是长建议更容易被接受，于是上下文越堆越长、延迟上升、留存没涨，**指标变好而价值没变**；机制上这是 §7.3.4 说的"接受率可被看起来合理的建议抬高"，它计量的是"用户懒不懒改"，不是"内容对不对" → 正确做法：以采纳后留存为主指标，把延迟与成本当护栏指标一起看——**没有护栏的结果指标会导致以延迟与成本为代价的假优化**。

这四个反模式的共同点是**它们都把"可度量的量"当成了"要度量的量"**：开通人数、意见条数、接受率、可写动作的次数。可度量的量恰好是最容易变好的那一段，而它们与"这一支有没有用"之间隔着一层机制。

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| SaaS → 私有化 | 合规审查不通过 | 重建自托管端点与本地索引；**历史使用数据无法延续** | 以月计【经验】 |
| 通用助手 → 专用助手 | 结构性问题答不了 | 补符号 / 引用索引、沙箱与评测集 | 以月计【经验】 |
| 无评测集 → 有评测集 | 无法判断优化是否有效 | 从历史提交构造三套样本 | 以周计【经验】 |
| 只读 → 可写 | 需要"让它直接改" | 补沙箱、验证流水线、人审与回滚路径 | 以月计【经验】 |
| 产品族 → 自建族 | 上下文不可控、效果到顶 | 自建索引与检索、迁移评测口径 | **以季度计**【经验】，且提示与规则需重建 |

这张表最容易被低估的是**"迁移动作"里的第二项**：迁移从来不只是搬组件，而是**口径重建**。换索引要重建评测样本（新索引能召回什么、切块边界变了没有），换端点要在同一批样本上重跑一遍基线，开可写动作要先有沙箱上的通过率基线——每一项都不是"配置一下"。表里还有两条可自行核验的规律：① **评测集是唯一可跨族带走的资产**，所以"先把评测集立起来"这件事在任何迁移方向上都是降低代价的动作；② **工作量量级与"动作权限"同向**——只读之间的迁移以周与月计，一旦牵动可写动作，最小单位就变成月。

再算一次摊销（【推算】）：一次跨族迁移按一个季度的人力计，若把它摊到此后三年的使用期上，等效于每年约占该团队人力的一小段（推导链：一次性投入 ÷ 使用年数）；**但真正不可逆的那一项不进入这道算式**——迁移前积累的线上指标（接受率、留存、采纳率的时序）在新口径下不能延续，而"有没有一年以上的趋势"恰恰是判断这一支值不值的唯一材料。所以硬结论里说的"最贵"不是人力贵，是**这段时序买不回来**。

**一条硬结论**：六条路里最贵的是**"把索引与评测交出去之后的收回"**——它不只是技术搬迁，还包括口径重建与**无法延续的历史指标**。**所以第 1、2、3 条判据（能否出域、索引归属、评测归属）必须在第一版就判对。**

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 源码不能出域、有平台团队 | 自建全栈，或自建检索 + 受控端点 | 索引与评测是自己能长期维护的资产；出域是门槛，不是权重 |
| 源码不能出域、团队小 | 商业产品私有化交付 | 把索引与端点的维护转移给厂商；代价是定制受升级节奏限制 |
| 源码可出域、只要补全 | 商业产品 SaaS | 补全不需要符号索引，此时线性账单最省（人数少时线性最便宜） |
| 要求"谁调用它"能答 | 索引自建的那一族（或支持符号索引的产品族） | 结构关系只能由符号与引用索引回答，向量检索在这类问题上归零 |
| 上下文策略要能自己调 | 自建检索 + 受控端点 | 效果的边际来自上下文而不是模型档位，且上下文是账单主项 |
| 要开可写动作 | 先补沙箱 + 人审 + 回滚，再开 | 沙箱决定的是"该不该开"，不是"好不好用"；失败代价由整个团队承担 |
| 要做阻断级审查 | 确定性规则与模型意见分开 | 概率系统进阻断级会让门变成随机的，团队会整体绕过 |
| 已有通用助手 | 自建检索层做检索、通用助手做生成 | 缺符号图与沙箱，只能停在只读；要接受"结构性问题答不了" |
| 公开仓库多、私有仓库少 | 自建检索 + 受控端点（按仓库分级） | 一条路径一个端点；分级判错即泄漏，靠一次演练保障 |
| 答不出"用了半年有没有用" | 先把评测集与埋点立起来 | 三层评测缺一层，结论就带一种偏：公共基准不拟合、线上指标可被抬高 |
| 没人承接索引与评测 | 把维护转移给厂商（私有化交付） | 承接能力是长期年金；没人承接时，索引滞后与提示过期会静默发生 |
| 已经选了产品族、效果到顶 | 先量真实使用密度与留存，再决定是否跨族 | 跨族迁移以季度计，且历史指标不能延续——**先量，再迁** |

> 本节小结：六个候选之间的差异，最终都能归到三问——**索引归谁建**（决定结构性问题能不能答）、**上下文可控吗**（决定效果优化的上限）、**有没有沙箱**（决定能不能开可写动作）。三问决定了它们的成本曲线形状（自建台阶、产品线性、通用改造前期最省但天花板最低）与迁移代价（跨族迁移以季度计，同族以月计）。**选型顺序不可颠倒**：先用"能否出域"筛掉不可行，再用"索引与评测归属"筛掉无法自证效果的，最后用"责任与承接能力"在剩下的里选——**把"谁维护评测集"当权重而不是门槛，就是"用了半年说不清有没有用"的根因**。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案（或你打算选的方案）做一次"门槛检查"：源码能否出域、索引归属、评测归属、动作权限、责任归属、承接能力——哪一条是"不满足"而不是"分数低"？那一条就是你明年最可能被迫迁移的方向；而你今天的补救，是否还落在"同族迁移（以月计）"这一格里？
