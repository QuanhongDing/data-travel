## 1. 概念与定位

### 1.1 是什么

**学术 / 工业定义**：代码智能助手是**以代码仓库为语料与操作对象**的智能体家族，典型能力有五类：**补全**（在编辑位置续写）、**仓库级问答**（"这个函数被谁调用、为什么这么写"）、**审查**（在变更进入主干前给出问题）、**测试生成**（补覆盖并识别边界）、**修复**（定位缺陷并提议改动）。

**工程定义**：在数据架构师手里，代码智能助手是**一件"上下文工程 + 权限工程 + 评测工程"三合一的产品**：

- **上下文工程**：决定"给模型看什么"（符号定义、引用、测试用例、提交历史、文档），并按**预算**分配。
- **权限工程**：决定"谁能看哪些仓库"（私有代码的可见域），以及"能改什么、要不要人审"。
- **评测工程**：决定"怎么知道它真的有用"（离线基准 + 私有评测集 + 线上接受率）。

**「代码智能助手」与「通用聊天助手」的差别**：

| 维度 | 通用聊天助手 | 代码智能助手 |
| --- | --- | --- |
| 语料 | 通用知识 | **你的仓库 + 依赖 + 构建与测试配置** |
| 正确性口径 | 说得对 | **能不能编译 / 测试能不能过 / 是否与仓库既有约定一致** |
| 延迟 | 秒级可接受 | 补全要**在编辑节奏内**（人机交互的时间常数很紧） |
| 权限 | 通常无差别 | **按仓库 / 分支 / 目录的可见域** |
| 评测 | 主观 | **有可执行的判据**（测试通过率、接受率、审查采纳率） |
| 失败代价 | 答错 | **把错误代码写进主干**（污染整个团队的资产） |

**一句话判断**：**「它能不能在你仓库里编译通过」是这一支的第一判据**——一个不能跑的补全，无论多"聪明"都是负资产。

### 1.2 为什么需要

这一支是被**五件事**逼出来的：

1. **上下文体量**：仓库动辄几十万行；模型窗口装不下——**必须做"选什么给它看"的工程**（检索 + 重排 + 预算），而不是"把相关文件都塞进去"。
2. **私有代码不许出域**：多数企业对源码有明确边界要求，这决定了架构（自托管推理 + 本地索引），也决定了"能不能用 SaaS 产品"。
3. **编辑节奏的延迟约束**：补全的价值与延迟强相关——**超过编辑节奏的补全会被人主动关掉**。
4. **审查要担责**：审查意见要能被人（以及被审者）接受，**误报会直接导致"没人再看"**；因此误报归因是必需能力。
5. **评测缺失是常态**：多数团队没有代码评测集，于是"效果好不好"只能靠感觉——**建评测集本身就是这一支的交付物之一**。

### 1.3 在 AI 时代数据架构中的位置

```
   [IDE / PR 平台 / CI]  ← 交互入口
            ↓
   [代码智能助手 · 本文]
     ├ 仓库索引（符号 / 引用 / 依赖 / 测试）
     ├ 上下文选取与预算
     ├ 模型（自托管或端点）→ 经 [模型网关](../../06-multi-model/03-model-gateway/03-model-gateway.md)
     ├ 权限域（按仓库 / 分支）
     └ 评测（离线基准 + 私有集 + 线上接受率）→ 经 [实验平台](../../02-data-science/07-eval/07-eval.md)
```

- **上游**：Ch1 图与建模（代码依赖图与知识图谱同源）、Ch4 检索（向量 + 混合检索的工程做法）。
- **下游**：Ch5 §02 平台（助手作为平台上的作业与工具出口）、Ch7 资产沉淀（提示与规则作为可沉淀资产）、Ch11 §01 质量（审查规则与质量门禁同源）。
- **横向**：Ch8 治理（源码分级与审计）、Ch11 §03 成本、Ch12 §09 灰度与回滚（助手改动进主干的回滚路径）。

### 1.4 演进历程

- **编辑器补全阶段（2021 起）**：以"单文件 + 前缀"为上下文做行级 / 块级补全；解决了"打字快"，**没有解决"与仓库约定一致"**。
- **仓库级检索阶段（2023–2024）**：把仓库切块、建向量与符号索引，检索后重排再生成——**"仓库级上下文"第一次成为可工程化的对象**，随之而来的是索引新鲜度与上下文预算两个新问题。
- **审查与测试阶段（2024）**：助手从"写"扩到"看"（变更审查）与"验"（测试生成）；此时**误报率与测试有效性**成为主要质量问题。
- **修复与私有化阶段（2024–2025）**：出现"定位缺陷并提议修复"的形态，以及面向受监管行业的**全私有化部署**（自托管模型 + 本地索引 + 审计留痕）。评价标准从"补得准不准"转向**"接受率、审查采纳率、测试有效率"**。

> 主线：**上下文从"单文件"扩到"整个仓库"，动作从"写"扩到"看与验"，最后落到"能不能在合规边界内全集运行"。**

## 2. 核心原理

### 2.1 关键概念定义

- **仓库索引（Repo Index）**：三类信息的集合——**符号表**（定义位置、签名）、**引用图**（谁调用谁、谁引用谁）、**文本向量**（注释 / 文档 / 片段）。它决定"能不能按语义找上下文"。
- **新鲜度（Freshness）**：索引相对仓库 HEAD 的滞后程度。**判据**：索引滞后的提交数（例如"滞后 ≤ N 个提交"），而不是"多久重建一次"。
- **上下文预算（Context Budget）**：为一次请求分配给上下文的 token 上限，以及**在各来源间的切分**（当前文件 / 相关定义 / 引用点 / 测试 / 文档）。**这是这一支最重要的可调项**。
- **FIM 补全（Fill-in-the-Middle）**：在光标处按"前缀 + 后缀"生成中间片段；**与"只看前缀"相比，它显著提高与后文的一致性**。
- **接受率（Acceptance Rate）**：被采纳的建议占比——**补全的核心线上指标**（比"生成得好不好"更接近价值）。
- **审查采纳率（Review Adoption）**：审查意见被开发者实际修掉的比例；**它是"误报是否可承受"的直接度量**。
- **权限域（Visibility Domain）**：一次请求可见的仓库 / 分支 / 目录范围；**必须在检索前生效**（先裁剪可见集合，再做检索）——顺序反了就会"检索到不该看的、再过滤"，既泄漏又浪费。
- **私有评测集（Private Eval Set）**：用本仓库历史提交构造的"输入 → 期望"样本（补全 / 修复 / 审查各有其形态）；**没有它，一切效果讨论都是主观的**。
- **沙箱执行（Sandboxed Execution）**：让助手生成的代码 / 测试在隔离环境里跑（编译、跑测试）后再呈现——**"先验证再呈现"是这一支可信度的来源**。

### 2.2 数学 / 形式化基础

**补全的延迟预算**（决定"能用还是会被关掉"）：

```
T_total = T_context(检索 + 重排) + T_model(首 token 延迟 + 生成) + T_render

经验区间（量级，随仓库规模与部署形态浮动）【经验】：
  T_context  数十毫秒 ~ 数百毫秒
  T_model    数百毫秒 ~ 秒级（取决于模型档位与部署）
判据：超过编辑节奏的补全，接受率会明显下降 —— 所以「先保延迟、再保质量」
```

**这条判据的用法**：把延迟与质量当成**有序目标**——先让 `T_total` 落在可接受区间，再在同等延迟下换更优的上下文（例如用更好的重排，而不是换更大的模型）。

**接受率与"看起来好"的差别**：

```
接受率 = 被采纳的建议数 / 呈现的建议数
采纳后留存 = 采纳的片段在 N 天后仍存在于代码中的比例   （更接近真实价值）
```

**判据**：**两指标一起看**——接受率高但留存低，说明"补了又被改掉"（多半是与仓库约定不一致，而不是语法错误）。

**上下文预算的边际收益**：

```
质量 ≈ f(有效上下文的 token 数)   ——  先陡后平
判据：当「再增加 X% 上下文预算」带来的私有评测集提升 < 1 个百分点【经验：以自有评测集的分辨率为准】，
      这块预算应该让给延迟（减小 T_context）而不是继续堆上下文
```

**评测集的构成**（补全类的最小形态）：

```
样本 = (仓库状态, 光标位置, 上下文预算, 期望片段)
指标 = exact-match（严格） + 编辑距离内的 match（宽松） + 编译通过率
判据：所有指标必须能在 CI 里自动跑 —— 否则"改了提示 / 换了模型"就没有回归依据
```

### 2.3 关键算法 / 方法

1. **索引构建**：按语言解析符号与引用（AST / 语言服务器协议一类），**不靠正则**；文本向量用于注释与文档检索。**判据**：随机抽一个函数，能在索引里回答"谁在调用它"。
2. **上下文选取**：三步——**粗排**（符号 / 引用 / 向量召回）→ **重排**（按与当前编辑位置的距离、相似度、是否同测试）→ **预算切分**（按来源配额）。**判据**：上下文里"被用到的比例"可测（生成片段中引用了多少上下文里的符号）。
3. **FIM 补全**：以"前缀 + 后缀"为条件生成；**判据**：与只给前缀相比，私有评测集的通过率有提升（这是可以实测的对照）。
4. **审查**：规则（既定的仓库约定、易错模式）与模型（语义问题）混合；**每条意见必须落到一条可解释的判据**（否则无法归因误报）。**判据**：意见能被标注为"规则命中"或"模型判定 + 置信度"。
5. **测试生成**：生成后**先在沙箱里跑**；**"通过但无效"的防法**是变异测试式的抽检（人为在源码里注入一个小缺陷，看生成的测试能否发现）——**能发现缺陷的测试才算有效**。
6. **缺陷定位与修复**：从"失败测试 / 报错栈 / 变更"入手定位，生成候选修复，**先在沙箱验证（编译 + 跑相关测试）再呈现**；不可逆的合并动作仍走人审（与 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md) 一致）。
7. **评测与回归**：离线基准（公共集）用于横向对标，**私有评测集用于业务拟合**，线上接受率 / 采纳后留存用于真实价值；**三者缺一不可**（这就是 [Ch2 §07 效果评估](../../02-data-science/07-eval/07-eval.md) 的"三层评估"用在代码上）。

### 2.4 与相邻概念的关系

- **代码智能助手 vs 通用聊天助手**：语料与判据不同——前者的第一判据是"能不能编译 / 测试能不能过"，后者是"说得对"。
- **代码智能助手 vs 仓库级 RAG（[Ch4 §05](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md)）**：RAG 提供检索与生成的基础做法；代码这一支额外要求**符号与引用结构**（纯向量检索对"谁调用它"这类问题乏力），以及**先编译后呈现**。
- **代码智能助手 vs 静态分析 / Lint**：静态分析是**确定性规则**（零误报或可控误报、可解释）；助手是**概率判断**。**正确分工**：确定性规则进 CI 门禁（拦硬错误），助手给"语义问题"的建议（不阻断），**用助手替换 Lint 会让门禁变得不可预测**。
- **代码智能助手 vs 实验/评测平台（[Ch2 §07](../../02-data-science/07-eval/07-eval.md)）**：评测平台提供"三层评估 + 样本集管理"；助手把它的样本形态具体化为"仓库快照 + 光标位置 + 期望片段"。
- **代码智能助手 vs Agent 平台（[Ch5 §02](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture.md)）**：平台提供会话、工具出口、配额与审计；助手是平台上的**一个高交互频率租户**（它的延迟要求比一般 Agent 更紧）。

> 💡 **思考锚点**：在你的仓库里挑一个函数，回答三个问题：谁在调用它（引用图能不能答）、它有没有测试（有效测试还是只跑通）、它最近一次被改是为什么（提交与讨论能不能检索到）。这三问对应的正是 §2.1 的三类索引；哪一问答不上来，就是你上下文工程当前最短的那块板——你打算先补哪一块？
