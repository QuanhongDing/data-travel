## 4. 工程实现

### 4.1 落地步骤

**八步，顺序不能颠倒**：

| 步 | 动作 | 产物 | 判据（先写下，再动手） | 为什么必须在这一步 |
| --- | --- | --- | --- | --- |
| 1 | **定可见域与端点** | 仓库分级 + 端点选择（自托管 / 受控端点） | 越权尝试是否被拒且可查原因 | 它决定后面所有能力能用哪一族 |
| 2 | **建私有评测集** | 从历史提交构造的样本（补全 / 修复 / 审查三套） | 样本数是否够分辨 1 个百分点的差异 | 没有它，后续所有"优化"都无法验证 |
| 3 | **建仓库索引** | 符号表 + 引用图 + 向量索引；滞后量指标 | 抽一个函数能答出"谁调用它" | 上下文工程的输入；结构性问题全靠它 |
| 4 | **补全（先做最紧的延迟）** | FIM 链路 + 硬超时 + 接受率埋点 | 超时是否"少呈现"而不是"慢呈现" | 补全的失败信号是启用率骤降，必须早测 |
| 5 | **仓库级问答** | 三路召回 + 重排 + 引用回指 | 答案能否指到文件 + 行号 | 复用语料与索引，成本增量小 |
| 6 | **审查（非阻断）** | 规则与模型双路 + 意见分级 + 归因字段 | 误报能否归因到规则或阈值 | 责任最重的一环，必须先有归因能力 |
| 7 | **测试与修复候选** | 沙箱 + 有效性抽检 + 验证后呈现 | 注入小缺陷，生成的测试能否发现 | "先验证再呈现"是可信度的来源 |
| 8 | **线上指标与迭代** | 接受率 / 采纳后留存 / 审查采纳率 / 候选验证通过率 | 最近一次优化依据的是哪个指标 | 把"感觉有效"变成"可证明有效" |

**顺序的反面**：最常见的错误是**先上补全、后建评测集**——于是"效果好不好"只能靠感觉，**每一次提示或模型调整都变成不可验证的赌博**。第 2 步之所以排在能力之前，就是因为它是后续一切的前提。

### 4.2 关键技术点

**（1）仓库索引的构成与刷新**

```yaml
index:
  symbols:  {provider: lsp_or_ast, fields: [name, signature, path, span, kind]}
  refs:     {provider: lsp_or_ast, fields: [from, to, kind: call|import|inherit]}
  vectors:  {chunk: "按函数/类边界切块，不按行数机械切", fields: [path, span, doc, summary]}
refresh:
  trigger: [push_to_main, pr_merge]
  lag_metric: commits_behind            # 判据：滞后 ≤ N 个提交（N 由团队定，可先取 10 量级）
  incremental: true
```

**判据**：① 抽一个函数，能答出"谁调用它"（引用图有效）；② 索引滞后量作为日常指标可见；③ 切块按**语义边界**（函数 / 类）而不是固定行数（否则上下文会带上半个函数）。

**（2）上下文预算的切分（可直接作为配置起点）**

| 来源 | 用途 | 预算占比（例） | 选择依据 |
| --- | --- | --- | --- |
| 当前文件（前后文） | 局部一致性 | 约三分之一【经验】 | 固定 |
| 相关定义（符号所在文件） | 类型与签名正确 | 约四分之一【经验】 | 引用图最近的 N 跳 |
| 引用点与测试 | 用法与约定 | 约四分之一【经验】 | 同类调用与相邻测试 |
| 文档 / 注释 / 提交信息 | 意图与约定 | 余量【经验】 | 向量召回 |

**判据**：生成结果中**引用了多少上下文里的符号**（比例过低说明重排没起作用）；以及"增加预算的边际收益 < 1 个百分点"时把预算让给延迟。

**（3）补全链路的硬超时**

```python
def complete(prefix, suffix, budget_ms):
    ctx = retrieve_context(prefix, budget_ms=budget_ms * 0.3)   # 检索有自己的预算
    if time_left() <= 0: return []                              # 宁可不出，也不慢出
    try:
        out = model.fim(prefix, suffix, ctx, deadline=budget_ms * 0.7)
    except Timeout:
        return []
    return rank_candidates(out, limit=3)
```

**判据**：超时返回空（而不是等待）——**这是"少呈现而不是慢呈现"的实现**，也是补全能否被长期启用的关键。

**（4）审查规则（含归因字段）**

```yaml
rules:                              # 确定性规则：可进 CI 门禁
  - id: r-no-direct-prod-cred
    when: {pattern: "prod_.*secret", in: changed_lines}
    level: block
    why: 生产凭据不得硬编码（见《安全基线》）
  - id: r-require-test
    when: {changed: src/**, missing: tests/**}
    level: remind
model_checks:                       # 概率判断：仅作建议
  - id: m-boundary-check
    prompt_ref: review_boundary_v3
    level: suggest
    threshold: 0.70                  # 按标签分别设阈值
attribution: [rule_hits, model_score_by_check, review_round]   # 误报归因必需字段
```

**判据**：**阻断级只能由 `rules` 产生**（确定性）；`model_checks` 一律 `suggest`。误报必须能落到 `rule_hits` 或 `model_score_by_check`。

**（5）测试生成的有效性抽检（变异式）**

```python
def mutation_probe(src_file, func_name):
    """在源码里注入一个小缺陷，看生成的测试能否发现它"""
    for m in sample_mutations(src_file, func_name, k=5):     # 例如边界条件翻转、off-by-one
        if not run_generated_tests(src_file_with(m)):        # 测试失败 = 发现了缺陷 ✓
            yield "detected", m
        else:
            yield "missed", m
```

**判据**：**抽检发现率**（`detected / (detected + missed)`）——它比"测试通过率"更接近"测试有没有用"；抽检应纳入常态（例如每周对新增测试抽样）。

**（6）修复候选的验证流水线**

```
定位（失败测试 / 报错栈 / 变更集）
   → 生成候选改动
   → 沙箱：编译 + 跑相关测试（策略：先跑受影响的测试，超时再缩小范围）
   → 通过 → 呈现为待审变更（附：改了哪些文件、跑了哪些测试、结果如何）
   → 不通过 → 只作为线索呈现（明确标注"未验证"）
```

**判据**：呈现时**必须区分"已验证"与"未验证"**；合并仍走人审（可逆性来自版本控制，见 [Ch12 §09](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)）。

**（7）权限域前置**

```python
def handle(user, repo, branch, request):
    dom = visibility(user, repo, branch)     # 先确定可见域（接企业权限系统）
    if not dom: raise Denied(reason="no_visibility")
    ctx = retrieve(request, within=dom)      # 只在可见集合内检索
    if not ctx.hits:                         # 空结果要显式：不回退为"不过滤"
        return Answer(text="你的可见域内无匹配内容", citations=[])
    # 上下文预算：按"边际收益 < 阈值"截断，而不是塞到上限为止
    ctx = budget.trim(ctx, until=lambda c: marginal_gain(c) < MIN_GAIN)
    out = model.complete(prompt=build(ctx), max_tokens=request.max_tokens)
    # 审计在调用之后写，但**字段取自调用前冻结的输入**——
    # 否则回溯时拿到的是"事后状态"，无法复现它当时看到了什么
    audit.write(user, repo, branch, request.kind, dom,
                accepted=None,               # 采纳与否由后续反馈回填
                inputs_hash=ctx.hash, model_version=MODEL_VERSION)
    return Answer(text=out, citations=ctx.citations)
```

**判据**：**用一次越权尝试做演练**（无权账号请求私有仓库，验证被拒且原因可查）；依赖库源码是否可见要有明确定义。

**（8）评测集的三套样本（补全 / 审查 / 修复）**

| 集合 | 样本形态 | 指标 | 构造来源 |
| --- | --- | --- | --- |
| 补全 | (仓库快照, 光标, 期望片段) | exact / 宽松匹配、编译通过率 | 历史提交（删除的未来行即期望） |
| 审查 | (变更 diff, 人工标注的意见) | 采纳率、误报率 | 历史 PR 的评审意见 |
| 修复 | (失败测试, 正确补丁) | 通过率、修复正确率 | 历史"测试红 → 变绿"的提交对 |

**判据**：样本量要能分辨 1 个百分点的差异（样本少时先扩样本，再谈优化）；三套都要能在 CI 里跑。

### 4.3 工具链与平台

| 层 | 可选 | 选型判据 |
| --- | --- | --- |
| 解析与索引 | 语言服务器协议 / AST 解析器 / 现成代码索引工具 | 支持的语言是否覆盖你的仓库（多语言时要逐个确认） |

| 沙箱 | 容器 / 微虚拟机（与 [Ch5 §02 §3.2.8](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 同类设施） | 是否需要跑编译与测试 |
| 交互入口 | IDE 插件 / 代码托管平台的应用 / CI 步骤 | 用户在哪里（IDE 内补全、PR 内审查、CI 里门禁） |

### 4.4 存量迁移

**从"没有助手"或"个人用外部工具"迁到企业内助手，四步**（每步可独立验证）：

1. **收口与埋点**：把个人使用的工具替换为受控入口（先只做补全），**同时埋接受率**。判据：能回答"启用了多少人、接受率多少"。
2. **索引与问答**：建仓库索引，上线"谁调用它 / 这段在哪"的问答。判据：抽三问能指到文件与行号。
3. **审查进评审流程**：先只做**非阻断建议**，收集采纳率与误报归因。判据：采纳率与误报归因率可见；误报能定位到规则或阈值。
4. **可写动作（可选）**：测试生成与修复候选，全部经沙箱验证 + 人审。判据：注入缺陷的抽检能发现；候选呈现带"已验证 / 未验证"标记。

**迁移的判据代替"上线"**：这一支的"上线"不是一次发布，而是**接受率与采纳率能持续被观测、并随优化上升**。

### 4.6 成本：这一支的账单

**四块成本**【推算：口径固定，单价按你的采购口径代入】：

| 成本块 | 构成 | 优化动作 |
| --- | --- | --- |
| 推理成本 | 补全请求数 × 单次成本（量最大） | 前缀缓存、小模型 + 重排、合并请求窗口 |
| 索引与检索 | 索引构建 / 刷新 + 向量存储 | **增量刷新**（不要每次全量重建）、按语义边界切块 |
| 沙箱执行 | 编译与测试的算力 | 只跑受影响测试、结果缓存 |
| 自托管固定成本 | GPU / 预留实例（台阶形） | 与补全并发模型匹配（**别按峰值买**，按并发上限与排队策略买） |

**算例（建立量级感）**：设 `300` 名开发者、每人每日 `600` 次补全请求【经验：随编辑器习惯浮动】。

- 日请求量 ≈ `300 × 600 = 18 万次/日`（量级：十万级/日）——**这是全公司请求量最大的一类 AI 调用**，因此"单次成本降 1 分钱"的收益远大于其它场景；
- 上下文页均 `2–6k` tokens【经验】，按 `18 万次/日` 估算，**上下文 token 总量是比生成 token 更大的成本项**——所以**先优化上下文（重排与预算），再优化模型档位**；
- **判据**：把"每次补全的平均成本"作为日常指标；它是这一支最容易通过工程手段下降的数字。

### 4.7 容灾与故障演练

| 故障 | 演练动作 | 通过判据 | 常见失效点 |
| --- | --- | --- | --- |
| 索引滞后 / 构建失败 | 停掉索引刷新一天 | 滞后量指标告警；问答答案明确标注"基于旧索引" | 无滞后指标 → 答旧行为且无人知 |
| 模型端点故障 | 让自托管端点不可用 | 补全静默降级（不呈现）；问答/审查排队或降级到小模型并标注 | 补全卡住导致编辑器卡顿 |
| 沙箱不可用 | 停掉沙箱 | 修复候选与测试生成**暂停呈现**（而不是跳过验证呈现） | 跳过沙箱 → 未验证代码外流 |
| 越权请求 | 用无权账号请求私有仓库 | 被拒、原因可查、留痕 | 权限判定在检索之后 |
| 误报风暴 | 激活一条过宽规则 | 意见被批量忽略前能被检出（用忽略率告警） | 没有忽略率指标 |
| 依赖服务变更 | 升级语言服务器 / 解析器 | 索引重建后符号与引用覆盖率不下降 | 解析器升级后大量文件解析失败无人知 |

**一条纪律**：**补全是"可缺失"能力**——端点故障时它应当安静地不出现（用户不会因此无法工作）；而**审查与问答是"可等待"能力**——它们可以排队，但不应静默降级为未标注的低质量结果。

### 4.8 演进路线：0 → 1 → 100

- **0 → 1（有人在用）**：可见域 + 私有评测集 + 补全（含埋点）。判据：启用率与接受率可见；评测集能在 CI 里跑。
- **1 → 10（用得住）**：索引（符号 / 引用 / 向量）+ 仓库级问答 + 审查（非阻断）+ 沙箱。判据：答案指到行号；审查误报可归因；生成测试经沙箱与抽检。
- **10 → 100（可交付 / 可私有化）**：自托管全栈（或分级混合）+ 修复候选（验证后呈现）+ 三层评测 + 完整审计。判据：私有仓库请求 100% 命中自托管（演练过）；最近一次优化能指出依据的指标。

### 4.10 小结

> 本节小结：这一支的工程实现可以压缩成一句话——**先把边界（可见域与端点）和尺子（评测集）立起来，再让能力一个个接上去**。八步顺序的实质是：可见域与端点决定"能选哪一族"（步骤 1）、私有评测集决定"能不能验证优化"（步骤 2）、索引决定"结构性问题能不能答"（步骤 3）、硬超时决定"补全会不会被关掉"（步骤 4）、归因字段决定"误报能不能降下来"（步骤 6）、沙箱决定"生成物可信不可信"（步骤 7）。四块成本里最有杠杆的是**上下文（而非生成）**：请求量在十万级/日时，**先优化重排与预算，再谈换模型**。

> 💡 **思考锚点**：算一下你（或你想做的）助手的"上下文 token ÷ 生成 token"。如果这个比值大于 3【经验量级】，说明成本主要花在"让模型看"而不是"让模型写"——那么下一步该做的是更好的重排，而不是更大的模型；另外，抽查一次最近的采纳，问"它有没有被测试覆盖"。你打算先补重排，还是先补沙箱？
