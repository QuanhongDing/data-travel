## 8. 面试真题集

### 8.2 补全：延迟、上下文预算与价值度量

#### §CI.1 团队要给 300 名开发者上线代码补全。请说明：（1）延迟与质量的取舍顺序，为什么不能"先把质量做上去再优化延迟"；（2）上下文预算怎么分配，什么情况下应该把预算让给延迟；（3）"补全有没有用"该用什么指标回答，为什么接受率不够？

**1. 考察点**

- 能否指出补全是**延迟敏感**能力，且失败信号是"启用率下降"而不是报错。
- 是否理解上下文预算的**边际收益递减**，并能给出"何时把预算让给延迟"的判据。
- 能否指出接受率的**可被抬高性**，并给出更接近价值的指标。
- 加分项：能把"300 名开发者"换算成请求量与成本量级，并说清这一支的失败为什么**在日志里看不见**；以及能各给出一次演练（端点断开、索引滞后）来证明这两条都不是纸面结论。

**2. 参考答案框架**

**第一层：取舍顺序（回答第 1 问）**。**先保延迟、再保质量**。理由：补全的价值与"是否跟得上编辑节奏"强相关——一旦超过节奏，用户会直接关闭功能（**这类失败的信号是启用率骤降，日志里什么都没有**）。所以工程实现上要**硬超时**：超时返回空（少呈现），而不是等待（慢呈现）。质量提升的正确路径是**在同等延迟下换更好的上下文**（更好的重排），而不是换更大的模型。

**第二层：预算分配与让渡（回答第 2 问）**。按来源切分预算：当前文件前后文（局部一致性）、相关定义（类型与签名正确）、引用点与测试（用法与约定）、文档 / 提交信息（意图）。判据：**当"再增加预算"在私有评测集上的提升低于 1 个百分点**【经验：以自有评测集的分辨率为准】时，把这块预算让给延迟（压缩检索耗时或缩短上下文）。此外，检索本身要有独立预算（例如总预算的 30%）。

**第三层：价值度量（回答第 3 问）**。接受率**不够**，因为它可以被"看起来合理"的建议抬高（用户懒得改就直接接受）。应同时看：**采纳后留存**（采纳片段在 N 天后仍在代码中的比例）与**缺陷率变化**（与补全的相关性需谨慎归因）。判据：**两个指标一起看**——接受率高、留存低，说明补的内容与仓库约定不一致。

**第四层：把"300 人"落到两个数上（回答"这一层怎么验收"）**。规模侧：300 人 × 每人每日 600 次【经验】（这正是 §4.6 算例的取值），得 18 万次/日、十万级/日 的**量级**（【推算】：由上面两个参数相乘）——这是全公司调用量最大的一类 AI 能力，所以**单次成本的边际下降在大基数上等于一笔可观的钱**，这也是"每次补全的平均成本"必须进日常指标的原因。成本结构侧：上下文 token 通常大于生成 token（数倍量级【经验】），于是**成本的杠杆在"检索与重排"，不在"模型档位"**。判据：把一个数报成两个数——**P95 延迟 + 每次补全的等效成本**。只压成本不看延迟会掉启用率，只追延迟不看成本会让方案在第二年无法续命；两个数一起看，才谈得上"可持续"。

**第五层：两次上线前演练（回答"失败长什么样"）**。这一支的失败是**静默的**：没有报错、没有 5xx、没有工单，只有用的人慢慢变少。所以验收不能靠"用一阵看看"，只能靠两次可重复的演练。① **端点断开演练**：把生成端点切断（或强制触发超时），验证链路返回空而不是等待——**少呈现优于慢呈现**（§4.2（3）的硬超时就是为此写的）；② **索引滞后演练**：把一条已重命名的符号留在索引里，验证答案不会以同样自信的语气给出旧行为，而是能带出"这份索引落后于主干"的信息。判据：演练之后你要能回答一句"这次的失败会体现在哪个指标上"——**答不出，说明这一层根本没有观测面**，而不是"这次没出问题"。

**3. 常见陷阱**

- 用"生成质量好"替代"延迟可接受"——功能被关掉，质量再好也没用。
- 无硬超时——编辑器在等待，用户体感是"卡顿"。
- 只看接受率——指标虚高，无法指导优化。
- 上下文"越多越好"——token 成本上升、延迟上升，边际收益递减。
- **把"加预算"当成"加检索结果"**——预算的边际收益先陡后平（§2.2），只加量不换重排，会同时抬高成本与延迟而质量不动；正确动作是换重排信号，不是把窗口塞满。
- **不设检索段的时间上限**——检索与生成共用同一个端到端预算，检索没有上限时，它会先把留给生成的余量吃掉，表现为"我什么都没改，怎么变慢了"。
- **用离线基准的分数判断上线效果**——公共基准与你的仓库在语言、框架、约定上都不同（§7.3.4 第二层），它可以用来横向对标，不能用来验收。

**4. 追问预测**

- 「300 人规模下请求量多大？」——按每人每日 600 次（§4.6 算例的取值）估算，约 **18 万次/日**（十万级）【经验：随编辑器习惯浮动；§6.1 的区间为 500–800 次/人/日，按该区间是 15–24 万次/日】——这是全公司量级最大的 AI 调用，**单次成本降一分钱的年化收益很可观**。
- 「上下文 token 与生成 token 的比例？」——常见量级是上下文大于生成（三倍上下【经验】），所以**先优化重排与预算**。
- 「怎么知道重排起作用了？」——统计"生成结果引用了多少上下文里的符号"；比例过低说明重排无效。
- 「延迟预算怎么在检索与生成两段之间分？」——先给检索一个固定份额的上限，超时即降级为"只带当前文件"；**把检索做成可降级的一段**，而不是不可控的整段，这样端点变慢时你还有一个台阶可下。
- 「'采纳后留存'怎么埋出来？」——留痕里记下采纳片段的位置与内容指纹，若干周后按同一位置回查；留存 = 仍在原位置且内容未被改动的采样比例。注意分母只计"已到观察窗"的样本，否则新采纳会把留存冲高。
- 「如果团队坚持先优化质量怎么办？」——用一个可判定的替代条件交换：在同一批私有样本上把"更大的模型"与"更好的上下文"各跑一遍，若前者的提升小于评测集的分辨率（§7.3.4 的"1 个百分点"判据【经验】），就说明该优化的是上下文，而不是档位。

**5. 参考资料**

- 检索与重排的工程做法见 [Ch4 §04 混合检索](../../04-data-assetization/04-hybrid-search/04-hybrid-search.md) 与 [Ch2 §05 推荐系统](../../02-data-science/05-recommendation/05-recommendation.md) 的排序思路。

- 本主题内部可逐节核的四处：[§2.2](03-code-intelligence-assistant.md) 的延迟经验区间与"先保延迟、再保质量"；[§4.2（3）](03-code-intelligence-assistant-section-4-sec4.md) 的硬超时实现与判据；[§4.6](03-code-intelligence-assistant-section-4-sec4.md) 的四块成本与算例；[§7.3.4](03-code-intelligence-assistant-section-7-sec7.md) 的三层评测与"接受率可被抬高"。

### 8.3 仓库索引与上下文选取（"谁调用它"）

#### §CI.2 开发者常问"这个函数被谁调用、改了会影响谁"。请说明：（1）为什么向量检索答不了这类问题；（2）你会建哪几类索引，各自的字段与刷新方式；（3）如何验证索引是有效的，以及索引滞后会造成什么后果？

**1. 考察点**

- 能否指出**结构性问题需要结构化的索引**（符号 / 引用），而不是语义相似。
- 能否把索引**落到字段与刷新策略**。
- 能否给出**可执行的验证动作**与滞后后果。
- 加分项：能指出索引是**源码的等价副本**（因此它的可见域与审计要跟源码同级），并能说出滞后为什么主要当日常指标看趋势、而只在构建失败与演练时告警。

**2. 参考答案框架**

**第一层：为什么向量检索不行（回答第 1 问）**。向量检索按**语义相似**召回，而"谁调用它"是**精确的结构关系**：调用点可能在语义上与函数名毫不相似（`f()` 被 `g()` 调用，两者文本不同但结构相连）。此外，向量召回返回的是"相似文本块"，无法给出**完整的调用集合**——而"影响面"要求的正是完整性。**判据**：随机抽一个函数，把"调用它的地方"全部找出来——这是一次可以直接验证的动作。

**第二层：索引的构成与刷新（回答第 2 问）**。三类：① **符号表**（名称、签名、路径、区间、种类）；② **引用图**（调用 / 导入 / 继承的边）；③ **文本向量**（注释、文档、片段，按语义边界切块而不是固定行数）。刷新：**在推送到主干或合并时增量刷新**，并把**滞后量**（落后多少个提交）作为指标。**判据**：三类索引都有；滞后量可见；切块按函数 / 类边界。

**第三层：验证与后果（回答第 3 问）**。验证动作：① 抽十个函数问"谁调用它"，与 IDE 的引用查找对照（这是**自带的对照工具**，成本极低）；② 抽一个近期改动，检查"影响面"是否包含实际受影响的文件。**滞后后果**：答案指向旧行为（例如函数已被重命名或删除），而这类错误**看起来完全合理**——所以必须有滞后指标，而不是靠用户发现。

**第四层：新鲜度怎么做成工程（把"后果"接到动作上）**。三层结构里最容易漏的是**刷新策略**：全量重建的窗口与仓库规模同阶，所以它的频率必然低，滞后反而更大；可行形态是**增量刷新 + 定期全量**（§4.2（1）的配置把刷新与 `lag_metric: commits_behind` 写在一起，示例阈值取 10 量级【经验：N 由团队按合并频率自定】）。判据有两条：① **新提交合并后，索引可见的滞后量能被报出来**；② 任何一个答案都能附带"这份索引落后主干多少"的信息。**滞后的处置方式也要选对，而且要分两层**：**稳态**把它当日常指标看趋势——告警会被静音一次，趋势不会被静默一年；**构建失败或演练时**仍然要告警——§4.7 的"索引滞后 / 构建失败"演练，通过判据就是"滞后量指标告警"、以及答案明确标注"基于旧索引"。至于"滞后阈值取多少才算可接受"，取决于你的合并频率与检索对象：改得越频繁的模块，同样的滞后量越危险，所以阈值应当能按仓库或目录调，而不是全局一个数（以你自己的合并频率校准，不引行业值）。

**第五层：索引与可见域的交界（先裁剪，再检索）**。索引本身天然是"全局"的（一份符号表覆盖所有已索引仓库），而检索必须是"局部"的：请求进来先定可见域（仓库 / 分支 / 目录），**只在可见集合内检索**（§3.2.8 与 §4.2（7）把这条做成前置的 `visibility()`）。反过来做（先检索后过滤）有两个后果，且都不是"体验问题"：① 不可见内容已经被读进内存与日志——**泄漏面在那一步就扩大了**；② 检索与排序算到的候选里有一半用不上，算力与 token 白花。判据是一条可直接执行的演练：用无权账号请求私有仓库，验证被拒、且拒绝原因可查。索引层还有一条常被忽略的边界：**跨仓库依赖（内部包、vendor 目录）的可见性必须显式定义**——不定义就等于默认可见，于是"从依赖库里读到不该读的内容"成为一条没有规则可依的路径。

**3. 常见陷阱**

- 只用向量检索——"谁调用它"永远答不全。
- 索引全量重建——成本高、频率低、滞后大；应增量刷新。
- 无滞后指标——答旧行为而无人知。
- 按固定行数切块——上下文里出现半个函数，模型容易误解。
- **把"未索引"当成"不存在"**——解析器覆盖不到的语言、宏与生成代码会被静默跳过，答案缺一块而看不出缺；正确做法是在回答里显式标注这部分未索引（宁可说明，不要假装完整）。
- **把索引当派生数据放在不受管的存储上**——索引是源码的等价副本，它的存放位置与访问控制必须与源码同级；"它只是索引"这句话是很多私有化方案的破口。
- **用一个"整体覆盖率"数字掩掉某种语言为零**——多语言仓库要按语言逐个确认解析器覆盖度，否则最常见的失败恰好是"某个次要语言的文件全部检索不到"。

**4. 追问预测**

- 「跨语言 / 生成代码怎么办？」——解析器覆盖不到的部分要显式标注为"未索引"，并在回答里说明局限（**宁可说明，不要假装完整**）。
- 「索引要不要包含测试与文档？」——要：测试是"用法约定"的最好来源，文档 / 提交信息提供"意图"。
- 「索引与知识图谱的关系？」——引用图是代码领域的关系图，可并入企业图谱（见 [Ch1 §06 知识图谱](../../01-modeling/06-knowledge-graph/06-knowledge-graph.md)）；但**先保证单仓库的引用完整性**，再谈全局图谱。
- 「索引存在哪、谁能读？」——这是私有化方案里最容易被跳过的一问：索引要有与源码相同的可见域控制，**并且"谁在什么时候查了哪个仓库"要进审计日志**（§4.3 的审计行就是为这一问准备的）。
- 「滞后量为什么不能只靠告警？」——因为告警针对的是"要不要现在起床"，而滞后在稳态下是持续存在的状态，只靠告警的结果是每周收到一批、然后被规则静音；它的主位子是日常指标与趋势图。但**构建失败与演练这两个时点仍要告警**——§4.7 的"索引滞后 / 构建失败"演练，通过判据就是"滞后量指标告警"。
- 「引用图要不要做到跨仓库？」——先单仓库、后跨仓库：跨仓库的边一旦引入，§4.2（7）的可见性问题会同时被引入，而这一层比引用完整性难处理得多。

### 8.4 代码审查：规则与模型的分工、误报归因

#### §CI.3 你要为多个团队上线"AI 代码审查"。请说明：（1）为什么确定性规则与模型意见必须分级，各自放在什么位置；（2）误报怎么归因，归因之后怎么改；（3）如何知道审查真的有用，而不是"提了很多意见"？

**1. 考察点**

- 能否坚持"**门禁只由确定性规则构成**"这一原则，并解释原因。
- 能否把误报**归因到可修改的对象**（规则、阈值、提示）。
- 能否用**采纳率 / 忽略率**回答"有没有用"。
- 加分项：能指出"意见从隔日移到提交时"改的是**采纳成本**而不是延迟；并能说清组织级规则与团队级规则的分界（只能加严，不能放松）。

**2. 参考答案框架**

**第一层：分级与位置（回答第 1 问）**。**确定性规则**（格式、禁止 API、凭据模式、缺失测试）进 CI 门禁，可阻断（可解释、可复现、可审计）；**模型意见**（边界条件、并发隐患、命名与约定）只作为**建议**呈现，**永不阻断**。原因：模型判断是概率性的，一旦进阻断级，门禁就变成"不可预测的门"，团队会整体绕过（**失去治理点**比"少拦几条"代价更大）。

**第二层：误报归因（回答第 2 问）**。每条意见必须带：**规则命中（哪条规则）**或**模型标签 + 置信度（哪个检查、多少分）**，以及被采纳与否。归因后按两条路改：规则过宽 → 收窄规则或加白名单；模型阈值过低 → 调阈值或收窄适用文件范围。**判据**：每次调整记录依据与前后指标（与 [Ch13 §01 ADR](../../13-decision/01-adr/01-adr.md) 的留痕一致）。

**第三层：有用性度量（回答第 3 问）**。三个数：**审查采纳率**（意见被实际修掉的比例）、**忽略率**（被忽略的比例，是"误报是否可承受"的直接信号）、**门禁拦截数**（确定性规则命中数，是"下限保障"）。**判据**：忽略率上升时应先收窄规则 / 阈值，而不是加大意见量——**意见越多而采纳率越低，等于在训练团队忽略它**。

**第四层：意见的到达时机（采纳成本的真实来源）**。两层机制要分开看。**确定性规则**在提交 / 推送时同步执行：快、可复现、失败原因就是规则本身，因此它可以阻断；**模型意见**异步给出、不阻塞合并，所以它的采纳率主要由"到达时作者还在不在这个变更上"决定。这里的经验是反直觉的：**把意见从次日移到提交时，改的不是延迟，是采纳成本**（§6.4 的匿名案例把这一条列为它的做法之一）。判据有两条且都可采集：① 一次提交的耗时里审查占了多少（同步部分必须占比很小）；② 意见到达时距最后一次编辑的时间（越短越好）。**顺序也要显式设计**：先确定性规则（可能阻断）、后模型意见（只能建议），两者的结果不能混在同一个"审查通过 / 不通过"里。

**第五层：多团队的口径治理（组织级门槛不可放松）**。规则库与阈值按组织级维护，团队可以在其上"加严"，**不能放松组织级门槛**（与 [Ch11 §02 数据安全](../../11-cross-cutting/02-data-security/02-data-security.md) 的分级治理同源）。这一层的失效形态是**规则分叉**：每个团队各维护一份，半年后同一类问题在不同团队被不同对待，而组织级报表上完全看不出来——因为每个团队自己的采纳率都"正常"。判据：抽查两个团队对同一类文件的规则集，看组织级那几条是否都在；再看新增规则是否走过评审、是否带改动前后的指标记录。另外，**阻断级规则的条数要收敛**（§6.4 记的是十几条以内【经验】），数量的上限由"被绕过一次的成本"决定，而不是由你能写多少条决定。

**3. 常见陷阱**

- 模型意见进阻断级——团队绕过门禁（且真实问题被一起忽略）。
- 无归因字段——误报只能靠感觉调，永远降不下来。
- 用"提出意见数"当作价值——这与"有用"无关，甚至负相关。
- 意见延迟给出（隔日）——开发者已进入下一件事，采纳成本上升。
- **把"意见越来越严"当成进步**——意见量上升而采纳率下降，等于在训练团队忽略它；正确看的是"忽略率的趋势"而不是"意见数的增长"。
- **不给适用范围**——对生成代码、第三方 vendor 目录提风格意见，是误报最常见的来源；范围过宽时，正确做法是收窄路径，而不是降低阈值。
- **归因只记"模型给了多少分"**——分数不可修改，规则与阈值可以；归因字段要能指到**可修改的对象**（哪条规则、哪个检查、哪个阈值），否则误报永远降不下来。
- **用审查替代测试**——审查是概率建议，测试是确定性门；两者不是同一层保障，用前者替换后者会让门禁退化为不可预测。

**4. 追问预测**

- 「审查意见会不会拖慢合并？」——确定性规则在提交时执行（快）；模型意见异步给出（不阻塞）。**顺序与阻塞性必须显式设计**。
- 「多团队怎么避免意见口径不一？」——规则库与阈值按组织级维护，团队可在其上加"更严"的规则，但不能放松组织级门槛（与治理分级的做法一致，见 [Ch11 §02 数据安全](../../11-cross-cutting/02-data-security/02-data-security.md)）。
- 「要不要屏蔽某类文件的审查？」——要，按路径做范围控制；**范围过宽是误报的常见来源**（例如对生成代码提风格意见）。
- 「误报率多少算可接受？」——不给行业数（本主题与全书他处都没有可核验的独立数据）：可接受线由**忽略率**决定——忽略率一旦上升，说明误报已经在训练团队忽略，这条线比任何百分比都可靠。
- 「怎么证明审查真的避免了事故？」——很难归因，且做不出可信的反事实；可做的是分开报两个数：**确定性规则的拦截数**（下限保障）与"被拦截后是否补了对应测试"（是否真的修好了）。把两者加在一起当"避免了 N 次事故"是越界。
- 「模型意见的阈值谁定、多久调一次？」——组织级给默认值与适用文件范围，团队只能收紧；每次调整要记录依据与前后指标（与 ADR 的留痕一致），否则半年后没人能解释这个阈值为什么是这个数。

**5. 参考资料**

- 门禁与质量规则的工程做法见 [Ch11 §01 数据质量](../../11-cross-cutting/01-data-quality/01-data-quality.md)（断言与门禁同源）与 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)（可逆性）。
- 模型意见的置信度与阈值管理可对照 [Ch6 §03 §4.2（5）](../../06-multi-model/03-model-gateway/03-model-gateway-section-4-sec4.md) 的分类阈值与归因字段。
- 本主题内部可逐节核：审查规则的三段结构（`rules` / `model_checks` / `attribution`）与"阻断级只能由 `rules` 产生"的判据见 [§4.2（4）](03-code-intelligence-assistant-section-4-sec4.md)；可归因输出（`check` / `level` / `score` / `evidence`）见 [§4.5 模板 3](03-code-intelligence-assistant-section-4-sec4.md)；与静态分析 / Lint 的边界见 [主文件 §2.4](03-code-intelligence-assistant.md)；机制差异见 [§7.3.6](03-code-intelligence-assistant-section-7-sec7.md)。

- 核验入口：取最近 50 条变更统计采纳率与忽略率，再**抽查 20 条被忽略的意见**人工判误报【经验：两处样本量按团队提交频次与意见量自定】——两个数对不上，说明归因字段没有真正生效（这是 §6.4 给的自测动作，成本只有一次人工抽检）。

### 8.5 测试生成的有效性与沙箱验证

#### §CI.4 有人说"用 AI 补测试能把覆盖率提上去"。请说明：（1）覆盖率高为什么不等于测试有用，你会用什么动作检验；（2）生成的测试必须经过什么流程才能进入仓库；（3）如何避免生成测试引入"flaky"与维护负担？

**1. 考察点**

- 能否指出"通过但无效"的测试形态（断言空洞、重复实现逻辑）。
- 能否给出**可执行的检验动作**（变异式抽检）。
- 是否理解"沙箱先跑"与"风格一致"是进入仓库的前置条件。
- 加分项：能说清抽检要被当成实验来设计（抽样、缺陷要有语义、记录未捕获的类型），并指出判定器不能与被判对象同源。

**2. 参考答案框架**

**第一层：覆盖率不等于有效（回答第 1 问）**。覆盖率只说明"代码被执行过"，不说明"行为被验证过"——**断言空洞**（例如只断言不抛异常）的测试能把覆盖率抬上去而毫无价值。检验动作：**变异式抽检**——在被测函数里人为注入小缺陷（边界翻转、off-by-one、早返回），看生成的测试是否失败；**发现率**（detected / total）才是有效性的直接度量。抽检应常态化（例如每周对新增测试抽样）。

**第二层：进入仓库的流程（回答第 2 问）**。① **沙箱执行**：必须编译、必须在沙箱里跑过并通过；② **风格一致**：与仓库既有测试框架、命名与组织方式对齐（否则引入两套风格）；③ **人审**：评审者检查"是否真的在验证行为"（尤其断言质量）；④ **可回滚**：作为普通变更走版本控制（回滚路径天然存在）。**判据**：呈现时必须区分"已验证（跑过）"与"未验证"。

**第三层：flaky 与维护负担（回答第 3 问）**。防法：① **禁用**依赖时间、随机、外部网络的生成模式（或强制注入可控的时钟 / 随机源）；② **重复运行**抽检（同一测试跑 N 次是否稳定）【经验：以检出偶发失败为目标，具体次数按测试耗时定】；③ **隔离**：不共享可变状态；④ **维护归属**：生成的测试进入仓库即由该模块 Owner 维护（**不能"生成了就没人管"**）。

**第四层：把"有效性"做成一个可重复的实验（回答"抽检怎么做才不是走过场"）**。变异式抽检的三件工程化要求，缺一件结论就不可信。① **抽样而不是全量**：全量的代价随测试数线性上升，而判据只需要一个比例，所以按周对新生成的测试抽样即可；② **注入要有语义意义**：边界翻转、off-by-one、提前返回这类"改了行为"的缺陷才有判据价值，注入无意义改动（改注释、改空白）会人为抬高发现率；③ **记录未发现的缺陷类型**——发现率是一个数，但"哪一类缺陷没被抓到"才是下一轮提示与规则改进的输入。判据：`detected / (detected + missed)`，并且**发现率为零的批次可直接判为无效测试**（本判据由 §3.2.4 的失效点与 §4.2（5）的 `detected/(detected+missed)` 推出；§3.2.4 原文只写"缺陷捕获率才是真实质量指标"，未给"为零即无效"这条阈值）。再加一条验证纪律：**判定器不能与被判对象同源**——用同一个模型判断"这些测试好不好"，偏差不会出现在结果里，只会出现在结论里。

**第五层：维护归属与生命周期（回答"谁来养"）**。生成的测试进入仓库即由该模块 Owner 维护，**不能"生成了就没人管"**。生命周期要提前定义，否则会出现一种隐蔽的浪费：与实现强耦合的测试（断言内部调用顺序、断言私有函数被调用了几次）在重构时会被成批删除，而它们**从未验证过任何行为**——只是把实现照抄了一遍。所以进入仓库前要加一问：**"实现改写后，这条断言还应不应该成立？"**答案是"不该"的，说明它测的是实现而不是行为。判据：统计新增测试在若干周后的存活率与失败归因（因实现变更失败 vs 因真实缺陷失败）——存活率低且失败集中在"实现变更"，说明这一批是维护负担而不是资产。

**3. 常见陷阱**

- 用覆盖率作为验收指标——会优化出断言空洞的测试。
- 生成后不在沙箱跑就提交——编译不过或直接红。
- 允许生成依赖时间 / 网络的测试——flaky 立刻出现（且最难排查）。
- 只生成不维护——测试随代码演进而失效，成为噪声。
- **把"失败"当成"检测到"**——测试失败也可能是编译错误、超时或环境缺失；抽检要先确认失败的原因是被注入的缺陷，否则发现率是假的。
- **只抽检新增、从不体检存量**——存量测试的有效性基线长期未知，于是"覆盖率涨了"与"测试能抓住缺陷"这两件事永远分不清。
- **让模型自己评判自己生成的测试**——同源判定会系统性高估；判定器要么是变异抽检这类可执行的机制，要么由人来定。
- **忘了生成的测试也是一种代码资产**——它进入仓库后要过同样的评审、同样的风格约束、同样的维护归属，否则仓库里会出现第二套风格不同的测试。

**4. 追问预测**

- 「测试生成的收益怎么量化？」——用"新增测试的变异发现率"与"这些测试捕获的真实缺陷数"；**不要用覆盖率增量**。
- 「能不能让模型自动修 flaky 测试？」——暂不建议：flaky 的根因常在并发或时间依赖，需要结构性理解；可由模型给线索、人定位。
- 「生成的测试要不要算入覆盖率目标？」——应当**不计入或另计**，否则会激励"刷覆盖"。
- 「测试生成与修复候选能不能共用一套验证？」——能共用**基础设施**（沙箱、编译、跑相关测试），但不能共用**判定**：测试看"自身是否有效 + 仓库是否变绿"，修复看"受影响测试是否从红转绿"，两者是两种判定（§4.2（6）的流水线只覆盖后者）。
- 「沙箱里跑不过的测试怎么呈现？」——只作为线索，不呈现为"已生成"；这与修复候选"已验证 / 未验证"的区分是同一条纪律（§4.2（6）的判据），混合呈现会让"跑过"这个标记失去意义。
- 「存量仓库的测试要不要补一轮抽检？」——建议做一次性的体检，用它估计"已有测试的有效性基线"；这个基线决定你之后新增测试的预期值，也决定"补测试"这件事还值不值得投人。

**5. 参考资料**

- 核验入口：每周对新增测试抽样做一次变异抽检，报出缺陷捕获率与未捕获的缺陷类型；再把上一批生成测试的存活率与失败归因取一次。

### 8.6 私有化部署与权限域（源码不出域）

#### §CI.5 客户要求"源码不允许离开内网"。请说明：（1）从工程上如何做到可信，而不是承诺；（2）你会拿什么证据证明"没有出域"；（3）权限域（谁能看哪些仓库）应该在链路的哪一步生效，为什么？

**1. 考察点**

- 能否把"不出域"落到**架构与可核验动作**（而不只是部署说明）。
- 能否给出**证据组**（白名单、连接审计、演练记录）。
- 能否指出权限判定**必须在检索之前**。
- 加分项：能说出"按仓库切分"与"按能力切分"的差别，并指出分级那一层只能靠一次演练加一次事件驱动的标签复核来维护。

**2. 参考答案框架**

**第一层：做到可信（回答第 1 问）**。三件事缺一不可：① **自托管推理**（模型端点在内网，含权重与推理服务）；② **本地索引与向量库**（索引不出域，否则"检索即泄漏"）；③ **出网默认拒绝 + 白名单**（只放行内部端点），并且**覆盖全部组件**（含遥测、日志上报、依赖更新）。**最常见的"假私有化"是只把模型换到内网而索引或遥测仍连外部**。

**第二层：证据组（回答第 2 问）**。① **出网连接审计**（在一段时间内，除白名单外没有任何外部连接）；② **一次演练**：故意配置一个外部端点并验证请求被拒绝（**"演练过拒绝"比"承诺不发送"有力**）；③ **权重与依赖的来源校验**（哈希 / 签名）；④ **审计日志可导出**（客户可自行核验）。四条构成可交付的"合规包"。

**第三层：权限域的生效位置（回答第 3 问）**。**必须在检索之前**：请求进入时先确定可见域（仓库 / 分支 / 目录），**只在可见集合内检索**。若"先检索再过滤"，会有两个后果：① 检索本身已经把不可见内容读进内存与日志（**泄漏**）；② 浪费算力与 token（**成本**）。**判据**：用无权账号做一次越权请求，验证被拒且拒绝原因可查。

**第四层：容量与成本（私有化不是"搬进内网"，而是换了一条成本曲线）**。自托管的固定成本是**台阶形**：单位成本 = 固定成本 ÷ 请求量，与调用量成反比（§6.3 把这个推导链写得很直白，§7.3.5 也同一条）。由这条式子直接得到两个动作。① **容量按并发上限买，不按峰值买**：按峰值买会把台阶抬到下一级，而那一级在非峰值时段全程闲置；配的办法是给补全设排队与降级——**少呈现而不是让请求无限等待**（这与 §4.2（3）硬超时是同一条纪律）。② **账单不止 GPU**：§4.6 的四块成本里，索引与检索、沙箱执行、自托管固定成本各占一块，私有化方案常只算了第一块。判据：报出**并发上限、排队丢弃比例、P95** 三个数——丢弃比例不为零而用户无感，说明降级策略生效；用户感到卡顿，说明降级没生效（那时"丢弃"发生在用户侧，不在你手里）。另一条判据是**等效单价**：把年固定成本除以年请求量，与"如果走外部端点"的账单比一次——**这一步是私有化立项时唯一能算清的经济账**。

**第五层：分级路由的判错面（混合形态唯一的失效点）**。按仓库分级的混合形态（公开仓库走外部端点、私有仓库走自托管）在架构上没有难点，它的风险全在"分级判错"上，而判错有三类具体形态：① **新仓库没有标签**——默认落哪边决定风险方向，必须**默认最严**（默认走自托管），否则新建的私有仓库第一次提问就走错了路；② **仓库迁移或改名后标签没跟着走**——标签的键要选择不会随迁移变化的标识，并且要有定期复核；③ **路径规则匹配到了 vendor、生成目录或镜像出来的代码**——它们可能来自不该出域的上游。判据就是 §4.5 模板 1 里 `verify` 段写的那一条演练：**用 private 仓库请求外部端点，验证被拒且留痕**；再加一条定期复核——把"新增仓库清单"与"已有标签的仓库清单"做差集，差集不为空就说明分级在漂移。这一层的纪律要说全：**正确性无法靠配置审阅证明，只能靠一次演练加一次定期复核**。

**3. 常见陷阱**

- 只私有化模型，索引 / 遥测出域（**假私有化**，合规审查必不通过）。
- 权限判定放在检索之后（泄漏 + 浪费）。
- 靠"配置审阅"证明没出域（应由**连接审计**证明）。
- 权重来源不明（无法回答"装的是哪版模型"）。
- **把"索引是派生数据"当成可以不设防的理由**——索引与源码内容等价，它的存储、访问与审计必须与源码同级。
- **只审计模型端点**——遥测、日志上报、依赖更新同样是出网点，而它们**最容易漏**（§6.3 的第一版失败正是"只在模型层切换端点"）。
- **按能力切分而不按仓库切分**（补全走内网、问答走外部）——同一份源码会同时出现在两条路径上，等于把最严的那条路径作废。
- **忘了"私有化之后模型档位会降一级"这件事的成本**——档位劣势要靠检索与重排补，这就把 §7.3.2 的上下文可控性从"优化项"变成了"必需项"。

**4. 追问预测**

- 「内网 GPU 不够怎么办？」——按**并发上限**而非峰值买容量（台阶形成本），并对补全设置排队与降级（少呈现），而不是让请求无限等待。
- 「跨仓库依赖的源码可见吗？」——需要显式定义（按"依赖的许可证与敏感度"分级），否则会出现"从依赖里读到不该读的内容"。
- 「客户要自证怎么办？」——提供审计日志导出 + 演练记录 + 白名单配置；这三件是**客户可以自己复现的**。
- 「私有化之后模型档位不够怎么办？」——先补检索与重排（§6.3 的做法②），而不是先换更大的模型：换模型会把固定成本再抬一级台阶，同时让延迟变差，等于用两笔代价换一个次要杠杆。
- 「能不能只私有化补全、把问答留在外部？」——不能按能力切，只能按仓库切；按能力切会让同一份源码出现在两条路径上（见上一条陷阱）。
- 「标签复核多久做一次？」——不给固定周期【经验】：正确的判据是把它挂在"新仓库创建"与"仓库迁移"这两个事件上，做事件驱动复核，再配一次定期巡检兜住漏事件的场景。

### 8.7 评测体系与可写动作的边界

#### §CI.6 领导问"我们的代码助手效果如何"。请说明：（1）你会拿哪三层数据回答，各自的局限是什么；（2）什么条件下才允许"让助手直接改代码"；（3）如果只能上一项指标，你选哪个？

**1. 考察点**

- 能否给出**三层评估**并指出各自局限（公共基准 ≠ 你的仓库）。
- 能否明确**可写动作的前置条件**（沙箱、人审、回滚、评测）。
- 能否选出**抗操纵**的单一指标。
- 加分项：能说清三层数据各自的时间常数与样本量要求，并能**当场写出一条退出条件**——回答"什么情况下我们会关掉它"比回答"现在效果多好"更能说明指标是被使用的。

**2. 参考答案框架**

**第一层：三层数据（回答第 1 问）**。① **离线公共基准**：用于**横向对标**，局限是分布与你的仓库差异大（语言、框架、约定、领域词）；② **私有评测集**（补全 / 审查 / 修复三套，来自历史提交）：用于**业务拟合**，局限是样本需要持续扩充、且可能过拟合历史行为；③ **线上指标**（接受率、**采纳后留存**、审查采纳率、候选验证通过率）：用于**真实价值**，局限是受使用习惯影响、且需要足够样本。**判据**：三层缺一不可——只有公共基准会优化错方向，只有线上指标会被操纵。

**第二层：可写动作的前置条件（回答第 2 问）**。四条同时满足才可以开放：① **沙箱**（编译 + 跑相关测试）；② **人审**（合并权在人）；③ **可回滚**（走版本控制，且改动范围可枚举）；④ **评测可比较**（私有集能在 CI 跑，改动前后可比）。**判据**：呈现必须区分"已验证 / 未验证"；未验证的只能作为线索。

**第三层：单一指标（回答第 3 问）**。选**采纳后留存**（配合延迟与成本作为护栏）。理由：它抗操纵（"看起来合理但改掉了"会立刻反映出来）、与价值最接近、且能跨能力复用（补全 / 修复都适用）。**注意**：它是**结果指标**，需要埋点与足够样本，且必须与"延迟 / 成本"这两个护栏指标一起看——**没有护栏的结果指标会导致以延迟与成本为代价的假优化**。

**第四层：采集频率、样本量与护栏（回答"这些数怎么看"）**。三层数据不是并列的三张报表，它们的时间常数不同：**延迟与成本按日看**（它们是运维护栏，坏了当天就要处理）、**留存与采纳率按周看**（信噪比需要样本量）、**公共基准按版本看**（换题目集或裁判版本后分数不可比，引用要连版本一起给）。样本量的判据只有一条，却常被跳过：**样本量要能分辨你想分辨的差异**——§4.2（8）把它写成"样本量要能分辨 1 个百分点"这个形式【经验：分辨率随样本量与业务波动而定，此处只给形式】，含义是**分辨率由样本量决定，不由指标定义决定**。护栏的设计理由也要说清：结果指标单独看会诱导"用延迟与成本换数字"——把上下文塞满能抬高接受率、把审查阈值调低能抬高通过率，两者都会在护栏指标上现形；所以**护栏越线时，结果指标的好看不算数**。

**第五层：从指标到决策（什么情况下该停）**。一套指标若只用于汇报，很快会变成"解释为什么数字不好"的材料；要让它有约束力，必须在事前写下**退出条件**。三个可判定的信号：① **接受率上升而留存下降**——内容被"懒得改"地接受了，说明建议与仓库约定不符；② **忽略率上升**——审查在训练团队忽略它，此时正确动作是收窄规则或阈值，而不是加意见；③ **每次补全的等效成本上升而使用密度没变**——优化方向错了（§7.3.5 的等效单价口径）。任一条成立，动作都不是"再调一版"，而是回到 §7.3 的机制层找原因。判据：**能拿出一份写下来的退出条件**——写不出"什么情况下我们会关掉它"的方案，等于没有验收标准；这也是 §5.3.6 把"退出条件"列为评估任何新方向必填项的原因。

**3. 常见陷阱**

- 只报公共基准——与业务无关。
- 只报接受率——可被抬高。
- 在沙箱与人审缺位时开放可写动作——一次事故就全面叫停。
- 单一结果指标不做护栏——会用延迟与成本换数字。
- **口径在月度汇报里反复变**（分母变、观察窗变）——趋势消失在口径变化里，而每个月的数字看起来都"正常"。
- **只看平均值不看分位**——体验由 P95 决定，平均值会被大量命中简单场景的样本掩盖（"平均很快、体感很慢"就是这样产生的）。
- **把"没有报错"当成"没问题"**——这一支的失败基本不报错，只有启用率与留存的变化（§3.1 把"有没有评测集"列为前置约束，理由正是失败是静默的）。
- **用公共基准的涨幅回应"有没有用"**——基准确认的是能力位置，不确认价值；拿它当回答，等于用别人的仓库替你验收。

**4. 追问预测**

- 「私有评测集会不会过拟合历史？」——会：应**按时间切分**（用较早提交建样本、较晚提交做验证），这与 [Ch2 §01 特征平台](../../02-data-science/01-feature-store/01-feature-store.md) 的 point-in-time 思路一致。
- 「怎么衡量审查的价值？」——用采纳率 + 忽略率 + 确定性规则拦截数三者组合；**单看意见数没有意义**。
- 「指标多久看一次？」——延迟与成本按日（运维护栏），留存与采纳率按周（信噪比需要样本量）。
- 「留存怎么算才不被稀释？」——固定"采纳时点 + 固定观察窗"，只对已到观察窗的样本计留存；**不要用"全部历史采纳"做分母**，否则最近大量新采纳会把留存冲高。
- 「停用之后这些数据还有用吗？」——有用，而且是最有价值的那部分：留存与采纳的时序是判断"这一支值不值"的唯一材料；§7.7 的硬结论说的就是"这段时序买不回来"，所以停用时应当保留而不是清空。
- 「三个指标冲突时听谁的？」——按**不可逆性**排序：延迟导致功能被关掉是不可逆的（用户走了不会回来），成本上升是可逆的（可以换计价方式）；护栏冲突时先修不可逆的那一条。

### 8.8 本章小结

本节收录 6 道题，覆盖**代码智能助手**的六个核心考点：**补全的延迟与度量 → 索引与上下文 → 审查分工 → 测试有效性 → 私有化与权限 → 评测与可写边界**。六道题构成一条完整的建设链路：

- **§CI.1 补全**：先保延迟（硬超时、少呈现不慢呈现），上下文预算有边际判据，价值看"采纳后留存"而不是接受率。
- **§CI.2 索引**：结构性问题必须由符号 / 引用索引回答；三类索引 + 滞后量指标；抽函数问"谁调用它"即可验证。
- **§CI.3 审查**：门禁只由确定性规则构成；误报必须可归因；忽略率是先行信号。
- **§CI.4 测试**：覆盖率不等于有效；变异式抽检给有效性度量；沙箱 + 风格一致 + 人审才进仓库。
- **§CI.5 私有化**：模型、索引、遥测全线不出域；证据靠连接审计与演练；权限域在检索之前生效。
- **§CI.6 评测**：三层评估缺一不可；可写动作需沙箱 + 人审 + 可回滚 + 可比评测；单一指标选"采纳后留存"并配延迟与成本护栏。

**答题心法**：先说清约束（能否出域、延迟要求、动作可逆性、有没有评测集、责任归属），再说清选项（六条路的三族），最后说清取舍与代价。这一支的面试官真正想听的是 **"你的验证与度量在哪里"**——把答案落到"某个判据 + 一个可当场执行的动作"（抽函数问调用方、查一次连接审计、统计两周留存），远比讲模型能力有说服力。
