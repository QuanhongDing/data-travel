## 6. 落地实践

> **本节的材料纪律（先说清楚）**：代码助手的公开材料以**产品文档与基准榜单**为主，而**采纳率、误报率、缺陷率这类效果数据几乎都来自建设方**，且公共基准与私有仓库的分布差异很大。因此本节**不列具名公司的生产案例**，只用**三类形态**的类型归纳来讲机制——每一类都标明对应 §3 的哪个模式，并给出可自测的判据。
>
> **这些形态来自公开材料（产品文档、基准、工程博客）的类型归纳，不是对任何一家公司内部实现的转述**；文中数字一律标档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的数值，请以你自己的实测口径为准。

### 6.1 形态一：团队内私有化补全（对应 §3.2.1 + §3.2.6）

**背景与挑战**：一个 20–50 人的研发团队，源码不允许发往外部服务；团队此前有人在个人层面用外部工具，但**公司层面无法回答"代码有没有出去"**。

**触发点**：一次安全审查——审计方要求说明"个人使用的补全工具会把什么内容发出去"。团队答不上来，于是决定自建并且**只允许一个出网出口**。

**详细做法（按 §4.1 的第 1、2、4 步 + §4.4 的第 1 步）**：

- **可见域与端点**：仓库分级；私有仓库强制走自托管端点；出网白名单只放行内部端点（**用连接审计验证，不看架构图**）。
- **私有评测集**：从历史提交里构造补全样本（删除的未来行即期望），先在 CI 里跑通。
- **补全 + 埋点**：FIM 链路带硬超时（超时返回空，不等待），同时埋接受率与延迟分段。
- **收口**：把个人工具替换为受控入口（这是"能回答审计"的关键动作）。

**具体数字（档位标注）**：

- 请求量级：`30` 人 × 每人每日 `500–800` 次补全 ≈ **1.5–2.4 万次/日**【经验：随编辑器习惯与"是否开启自动补全"浮动】——量级是"万级/日"。
- 延迟目标：整链路 `T_context + T_model + T_render` 要落在**编辑节奏内**；自托管中小模型下常见量级是**数百毫秒到秒级**【经验，随模型档位与部署形态浮动】；**超过这个区间，接受率会明显下降**。
- 成本结构：上下文 token 通常**大于**生成 token（比例常在三倍上下【经验】）——所以**先优化重排与预算，再谈换模型**。

**失败教训**：**第一版没埋接受率**——上线两个月后无法回答"有没有用"，也无法判断"延迟降到多少合适"。教训：**埋点不是后续工作**；对补全而言，埋点与功能同期上线，否则整件事无法被评估。

### 6.2 形态二：企业级审查门禁（对应 §3.2.3 + §3.2.8）

**背景与挑战**：多个产品线共用一套仓库群，评审质量参差：有的团队靠资深同事人工看，有的团队基本没人看。管理层希望"用工具兜住底线"。

**触发点**：一次线上事故——一个硬编码的生产凭据被合并进主干。复盘发现：评审时没人注意到，而这类问题**本来可以用确定性规则拦住**。

**详细做法**：

- **确定性规则进阻断级**：格式、禁止 API、凭据模式、缺失测试——这些进 CI 门禁（可解释、可复现）。
- **模型意见只做建议**：语义问题（边界条件、并发隐患、命名与约定）作为 `suggest` 呈现，**带置信度与归因字段**。
- **采纳率与忽略率**：统计意见被采纳与被忽略的比例（**忽略率是"误报是否可承受"的直接信号**）。
- **权限域与留痕**：按仓库裁剪可见域；留存"谁、何时、对哪个仓库、提了什么意见、是否被采纳"。

**具体数字（档位标注）**：

- 阻断级规则的数量：**应当很少**（把"必须拦"的收敛到十几条以内【经验：规则越多，边界越模糊】），其余全部为建议。
- 误报治理的循环：按"规则命中 / 模型标签 + 阈值"归因，**每次调整记录依据与前后指标**（与 [Ch13 §01 ADR](../../13-decision/01-adr/01-adr.md) 的留痕思路一致）。
- 意见时效：审查意见应在**提交时**给出（而不是次日），否则开发者已经进入下一件事，采纳成本上升【经验】。

**失败教训**：**第一版把模型意见也做成阻断**——结果是开发者批量忽略，门禁形同虚设，而且真实问题也被一起忽略。教训：**门禁只能由确定性规则构成**；概率性判断只能做建议，并且必须带可归因的字段，否则无法迭代。

### 6.3 形态三：面向产品的代码助手（对外交付）（对应 §3.2.5 + §3.2.7）

**背景与挑战**：把代码能力做成对外产品或内部平台服务，面对多个客户 / 多个团队，**必须同时满足合规（分级端点）与效果（接受率）**。

**触发点**：一个客户提出"我们的私有仓库也要用"，但产品此前只有外部端点路径——**这要求把"按仓库分级路由"补上**，否则要么违规、要么丢掉这个客户。

**详细做法**：

- **仓库分级与两条端点路径**：公开仓库走外部端点、私有仓库走自托管；**判定在网关侧按仓库标签执行**（与 [Ch6 §03 §4.2（4）](../../06-multi-model/03-model-gateway/03-model-gateway-section-4-sec4.md) 的出网策略同源）。
- **分别评测**：两条路径的效果分开测（否则无法回答"客户用哪条更划算"）。
- **可写动作的护栏**：修复候选**经验证才呈现**，且呈现时明确区分"已验证 / 未验证"；合并权始终在人。
- **产品化指标**：按客户统计接受率、采纳后留存、意见采纳率——**这三个指标构成"效果证明"的最小集合**。

**具体数字（档位标注）**：

- 两条路径的成本差是**结构性的**：自托管是台阶形固定成本（无论用多少都要付），外部端点是线性按量【经验】——**因此私有仓库路径的单位成本通常更高**，这个差值应体现在报价里，而不是被平均掉。
- 沙箱验证的成本：它随"要跑多少测试"变化；可执行策略是**先跑受影响测试**、超时后再缩小范围【经验：以能在可接受时间内给出结论为准】。

**失败教训**：**把"私有化"当成部署变体而不是架构约束**——第一版只在模型层切换端点，索引与遥测仍走外部服务，客户的合规审查直接不通过。教训：**"不出域"必须覆盖全链路组件**（模型、索引、遥测、日志），并用出网白名单与连接审计举证。

### 6.4 真实落地路径（基于上述三种形态提炼）

三种形态拼起来是一条顺序固定的路径，与 §4.8 对应：

1. **先定边界（可见域与端点）+ 先建尺子（私有评测集）**——这两件是所有能力的前置。
2. **再做补全与埋点**（形态一）——它是请求量最大的一支，也是最快能证明"有没有用"的一支。
3. **然后做索引与问答**——结构性问题（谁调用它 / 这段在哪）的价值随时间累积。
4. **最后做审查与可写动作**（形态二、三）——它们涉及责任与合规，必须在归因、沙箱、人审都到位之后。

**顺序的反面**：先做可写动作（最吸引人），后补沙箱与评测——**未经验证的改动会直接进入主干**，一次事故就会让整个项目被叫停。

### 6.5 踩坑与经验（三种形态提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 无接受率埋点 | 无法回答"有没有用" | 无法优化、无法争取预算 | 埋点与功能同期上线 |
| 补全等待长上下文 | 启用率骤降 | 功能被关掉 | 硬超时 + 少呈现不慢呈现 |
| 模型意见进阻断级 | 开发者批量忽略 | 门禁失去权威 | 阻断只由确定性规则产生 |
| 权限判定在检索之后 | 日志里出现不该出现的仓库 | 泄漏 | 可见域前置 |
| 假私有化（索引/遥测出域） | 合规审查不通过 | 项目被叫停 | 全链路出网白名单 + 连接审计 |
| 测试只看通过率 | 覆盖上升、缺陷照旧 | 断言空洞 | 变异式有效性抽检 |
| 未验证候选直接呈现 | 编译不过 / 测试红 | 信任崩塌 | 沙箱验证后再呈现 |
| 索引无滞后指标 | 答的是旧行为 | 结论错误且难发现 | 滞后量作为日常指标 |
| 用公共基准代替私有集 | 榜单好、业务无感 | 优化方向错位 | 建私有评测集（三套样本） |

### 6.6 ROI 评估（三种形态的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 补全效率 | 接受率 × 采纳后留存 | 接受率可测；**留存才是价值**（不设通用值，必须自测） | 埋点后取两周数据 |
| 上下文成本 | 每次补全的平均成本（上下文 + 生成） | 量级以"十 万次/日"计，**单次成本降一分钱的年化收益可观** | 统计成本与 token 构成 |
| 审查有效性 | 采纳率、**忽略率**、被拦的确定性问题数 | 确定性规则命中是"下限"，模型意见是"增量" | 取最近 50 条变更统计 |
| 合规收益 | 能否回答"代码有没有出去" | 从"答不上来"到"有白名单 + 连接审计 + 演练记录" | 做一次出网演练并留痕 |
| 排障时间 | "这段逻辑在哪 / 谁调用它"的耗时 | 从**分钟级人工搜索**到**秒级带引用回答**【经验】 | 抽 10 个真实问题计时 |
| 代价 | 自托管固定成本 + 沙箱算力 + 索引运维 | 台阶形（按 GPU 与并发买，不按峰值买） | 按月核算固定成本 ÷ 调用量 |

**读法**：前三项是**效率与质量收益**，第四项是**合规收益**（无法折算金额，但它是"项目能否存在"的前提），第五项是**工程收益**，最后一项是**代价**。这一支最容易出现的错位是**只算"生成了多少代码"，不算"留存了多少、缺陷率变化"**。

> 本节小结：三种形态的先后顺序不是偏好而是依赖——**边界与尺子先行**（可见域、端点、私有评测集），**补全带埋点**（请求量最大、最快可证伪），**索引与问答**（结构性问题），**审查与可写动作最后**（责任最重）。三次失败教训指向同一件事：**代码助手的失败几乎都不是"模型不够强"，而是"缺了验证与度量"**——缺埋点就说不清价值、缺归因就降不下误报、缺沙箱就不敢让它动代码。

> 💡 **思考锚点**：从 §6.1–§6.3 里挑一个与你最像的形态，只做一件最小的事——按它的"判据"跑一次自测（查一次出网连接审计 / 统计两周接受率 / 抽查 20 条审查意见的误报归因）。哪一件**今天就能做**就先做它：能被立刻验证的缺口，优先级永远高于推断出来的缺口。
