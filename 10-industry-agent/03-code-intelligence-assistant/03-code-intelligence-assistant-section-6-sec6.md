## 6. 落地实践

> **本节的材料纪律（先说清楚）**：代码助手的公开材料以**产品文档与基准榜单**为主，而**采纳率、误报率、缺陷率这类效果数据几乎都来自建设方**，且公共基准与私有仓库的分布差异很大。因此本节 4 例的构成是：
>
> - **§6.1–§6.3** 是**产品文档层面的机制复述**（边界策略放在哪一层、仓库级索引解决哪类问题、私有化后拿什么补质量），**不是对任何一家公司内部实现的转述**；方括号内是**来源类型 + 年份**，属**建设方自述**，不构成本书 §5 判据里要求的「第三方（非厂商）公开生产案例」，读者需按其官方材料自行核验。
> - **§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证。
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 GitHub Copilot"**把「内容排除」做成一等策略：边界由策略层承担，不由每个应用各自遵守 3+ 年**"（2021-2024）

**背景（Why）**

企业引入代码助手时，最先撞上的不是效果问题，而是**"代码有没有出去"**：

- **个人层面的使用先于公司层面**——研发人员会先自己装上工具，公司后知后觉；
- **"不发送敏感内容"无法靠纪律执行**——它要求每个使用者在每次补全时做一次判断，而补全的触发是**无意识的**（边打字边触发）；
- **审计要的是证据**——"我们规定了不许用"在审计里不成立（同 [Ch6 §03 §6.4](../../06-multi-model/03-model-gateway/03-model-gateway-section-6-sec6.md) 的"承诺不是证明"）。

**触发点（What）**

GitHub Copilot 面向企业提供了**内容排除**能力（[GitHub 公开材料 2021-2024]，核验入口是其官方文档，**按当前版本核**）：可以在**平台策略层**声明哪些路径 / 仓库的内容不应被用于该服务的上下文。它对接入设计的启示是一条**落点判断**：

- **边界不能放在"每个使用者的行为"上**——那是不可执行的；
- **也不能放在"每个应用的代码"里**——那要求 N 个应用各实现一遍同样的判定（§3.2.8 的"先裁剪再检索"在组织层面的版本）；
- **只能放在平台策略层**——一处声明、全局生效，且可被审计。

**详细做法（How）**

**① 把边界声明成策略，而不是文档**

- **关键设计**：一条"哪些内容不可用于该服务"的**机器可读声明**，由平台在执行时读取；**使用者不需要知道这条策略存在**。
- **关键性质**：**可执行性来自"使用者无感"**——凡是要求使用者每次做判断的策略，实际执行率都趋近于"记得的时候"。
- **关键示意**：

  ```text
  三种边界落点，只有一种可审计
    ── 落点 A：使用规范（文档）──────────────────────────
       "禁止将敏感仓库内容发送至外部服务"
       → 执行率 = 记得的时候；审计时无法举证
    ── 落点 B：每个应用的代码 ────────────────────────────
       应用1 实现一遍过滤；应用2 实现一遍；应用3 忘了
       → N 份实现 → 迟早有一份漏；审计要查 N 个地方
    ── 落点 C：平台策略层（可执行）────────────────────
       一处声明：{ excluded: ["/secrets/**", "*/internal-*"] }
       执行体在上下文组装前读取它
       → 使用者无感；审计只需查一处策略 + 一次演练
    ────────────────────────────────────────────────
   判据：这条边界"下一次被违反"需要谁记得什么？
        A 需要每个人每次记得；B 需要每个应用作者记得；
        C 不需要任何人记得 → 只有 C 可审计
  ```

**② 用一次演练证明边界存在**

- **关键设计**：构造一次**本应被排除**的请求（把一个被排除路径下的片段放进上下文触发条件），验证它确实没有进入外发内容。
- **为什么**：策略的**声明**与策略的**生效**是两件事——排除规则依赖路径匹配，而路径匹配的边界（软链接、大小写、子模块）经常与直觉不同。**演练是唯一能证明"生效"的动作**（§3.2.7 的同一逻辑）。

**具体数字（档位标注）**

- 请求量级：`30` 人 × 每人每日 `500–800` 次补全 ≈ **1.5–2.4 万次/日**【经验：随编辑器习惯与"是否开启自动补全"浮动】——量级是"万级/日"。**这个量级决定了两件事**：埋点必须覆盖全量（否则样本偏差），以及任何在链路上新增的一次判定都必须极轻（`万级/日` × 每次几毫秒就是可观的 CPU 时间）。
- 延迟预算：整链路 `T_context + T_model + T_render` 要落在编辑节奏内；**自托管中小模型下常见量级是数百毫秒到秒级**【经验，随模型档位与部署形态浮动】；**超过这个区间，接受率会明显下降**（§3.2.1 的失效点）。
- 成本结构：**上下文 token 通常大于生成 token**（比例常在数倍量级【经验】）——所以**先优化检索与预算，再谈换模型**（§3.2.1 的代价部分给了同一条推论）。
- **自测动作**：做一次内容排除演练（构造一条本应被排除的请求，看它是否真的没有外发）；再统计一次"上下文 token ÷ 生成 token"这个比值。

**失败教训**

**第一版把边界写进了《使用规范》**——上线两个月后，安全审查问"你怎么证明敏感仓库的内容没有发出去"，团队只能回答"我们规定过"。教训：**边界必须落在策略层并可演练**——**规范约束的是人的记忆，策略约束的是系统的行为**；只有后者能举证。

### 6.2 Cursor"**仓库级索引：让「谁调用它」这类结构性问题可答 2+ 年**"（2022-2024）

**背景（Why）**

代码问答的真实问题分布与"通用问答"差别很大：

- **"谁调用它""这个配置从哪来""这段逻辑在哪"** 是最高频的一类；
- **这些问题在语义上几乎没有线索**——调用方的代码可能与被调用函数毫无文字相似度，**向量检索在原理上答不出来**；
- **答错的代价高**——用户会照着答案去改代码，而一个"看起来合理但已经过时"的答案（指向已删除的调用方）不会被察觉。

**触发点（What）**

Cursor 一类工具把**仓库级索引**作为一等能力（[Cursor 公开材料 2022-2024]，核验入口是其官方文档，**按当前版本核**）：对代码库建立索引以支持跨文件的上下文与问答。它对链路的启示是**问题类型与检索通道的对应关系**：

- **符号 / 引用类问题要靠图结构**（定义与引用是一条可查的边）；
- **意图类问题要靠向量**（"怎么做重试"没有固定的符号名）；
- **两者不可互相替代**——这是 §3.2.2 三路召回的由来。

**详细做法（How）**

**① 按问题类型分派检索通道**

- **关键设计**：解析问题里的**符号 / 路径 / 关键词**，据此选择主通道；三路召回的**权重可调**，但每类问题至少有一路能覆盖。
- **为什么不能只做一路**：**结构性问题与语义问题的最优检索方式不同**——只做向量时"谁调用它"答不出；只做符号时"怎么做重试"答不出（没有符号可匹配）。**三路的价值不在"更多"，而在"覆盖不同的问题类型"。**

**② 索引滞后量作为日常指标**

- **关键设计**：把"索引比仓库 HEAD 落后多少个提交 / 多久"作为**日常指标**（不是故障指标）。
- **为什么它是正确性问题**：滞后的索引会给出**看起来完全合理但已经过时**的答案（例如指出一个上周已删除的调用方），**而用户没有任何信号能察觉**——这与"报错"完全不同：报错会被修，静默的过时答案会被当成事实使用。

**具体数字（档位标注）**

- 请求量级：问答的请求量通常**比补低一到两个数量级**（补全是每次按键触发，问答是主动提问）【经验】——因此**问答侧的延迟预算宽松得多**，可以把预算花在检索与重排上；**这条差异是"共用一个端点"最常见的错误来源**（用补全的预算做问答，答案必然浅）。
- 索引规模与重建窗口：索引规模与仓库代码量同阶；**全量重建的时间与仓库规模成正比**，因此常见的做法是"增量索引 + 定期全量"，并**把滞后量作为重建策略的输入**【推算：重建窗口 ≈ 代码量 ÷ 索引吞吐，吞吐取决于解析器与并发度，请按你自己的仓库代入】。
- **自测动作**：抽三个函数，问助手"谁调用它"——**能不能答出调用方、并给出文件与行号**；再查一次当前的索引滞后量（多少个提交 / 多久）。

**失败教训**

**第一版只做了向量检索**——理由是"向量检索更通用"。结果是最高频的那类问题（谁调用它、这段在哪）答得很差，用户不再提问；**而这条失败没有任何错误日志**（它是一个"看起来能用但用户不用了"的功能）。教训：**代码里的相关性有一半是结构性的**；把通用方案套到代码上，会恰好漏掉最高频的一类问题——**而静默的功能死亡不会有人来报修**。

### 6.3 阿里"通义灵码：企业版把补全放进内网，并用检索补回模型档位的劣势 2+ 年**"（2023-2024）

**背景（Why）**

私有化形态的**代价与补偿是同一件事的两面**：

- **不能出域 → 只能用自托管模型**，而自托管模型的档位通常弱于最前沿的托管模型；
- **质量上限因此被压低**，但需求没有变（用户仍然要"补得准、答得对"）；
- **唯一能在同一延迟预算内提升信息密度的杠杆是检索与重排**（不是更大的模型——那会同时抬高延迟与固定成本）。

**触发点（What）**

通义灵码的企业版面向私有化场景提供部署形态（[阿里公开材料 2023-2024]，核验入口是其官方文档，**按当前版本核**）。它引出的是一条**关于补偿路径的判断**：

- **私有化不是"把同一套能力搬进内网"**——栅栏外的模型档位拿不到了，必须换一种方式把质量补回来；
- **而补的方式只有一种**：**在相同的延迟与算力预算内，把更相关的上下文送进模型**（检索、重排、符号索引）。

**详细做法（How）**

**① 先建"尺子"，再谈调优（顺序不能反）**

- **关键设计**：**私有评测集必须在能力上线之前建**（§3.1 约束 4）——样本来自**你自己的仓库历史**（例如"删除的未来行即期望"这类可自动构造的样本）。
- **为什么顺序不能反**：私有化的效果差异**无法用公共基准观察到**（公共基准与私有仓库的分布差得很远，§3.5 的反模式）。没有私有集时，"优化"只能靠感觉，而**私有化场景下每一次错误决策都贵**（GPU 是台阶成本，"再试一版"的代价是排期不是账单）。

**② 用检索与重排补质量，而不是换更大的模型**

- **关键设计**：把差额预算投在**上下文相关性**上（更好的检索、更准的重排、更聪明的预算分配），而不是投在模型档位上。
- **机制**：模型档位每升一档，**延迟与固定成本同时上台阶**，而可用的上下文预算被压缩；检索与重排是**唯一在相同预算内提高信息密度的杠杆**（§3.2.1 的代价部分）。

**③ 全链路不出域：把遥测也计入**

- **关键设计**：出网白名单要覆盖**模型 / 索引 / 遥测 / 日志**四类组件，并用**连接审计**验证。
- **为什么遥测最容易被漏**：它是旁路组件（不在主链路上），建架构图时容易不画；而它恰好**会携带代码片段与用户行为**——"假私有化"最常见的形态就是在这一层漏出去（§3.2.6 的失效点）。

**具体数字（档位标注）**

- 自托管固定成本是**台阶形**：GPU 按"买多少算力"而非"用多少次"计费，因此**请求量低时单位成本极高、量上来后摊薄**【推算：单位成本 = 固定成本 ÷ 请求量，固定成本与请求量无关 ⇒ 反比关系】——这是 §3.2.6 与 [Ch6 §03 §7.4](../../06-multi-model/03-model-gateway/03-model-gateway-section-7-sec7.md) 的同一条成本曲线。
- 上下文 token 与生成 token 的比值常在**数倍量级**【经验】——**这条推论是私有化场景的核心**：因为上下文占大头，所以**优化上下文（检索、重排、去重）的杠杆高于优化生成（换模型）**。
- **自测动作**：统计"上下文 token ÷ 生成 token"；再查一次出网白名单是否包含遥测组件，并做一次连接审计（不是看架构图）。

**失败教训**

**把"私有化"当成部署变体而不是架构约束**——第一版只在模型层切换端点，索引与遥测仍走外部服务，客户的合规审查直接不通过。教训：**"不出域"必须覆盖全链路组件**（模型、索引、遥测、日志），并用出网白名单与连接审计举证。

### 6.4 某大型互联网公司"**审查门禁：模型意见只做建议，阻断只由确定性规则产生 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

多个产品线共用一套仓库群，评审质量参差：有的团队靠资深同事人工看，有的团队基本没人看。管理层的诉求是"用工具兜住底线"。

**触发点（What）**

一次线上事故——一个硬编码的生产凭据被合并进主干。复盘发现：评审时没人注意到，而这类问题**本来可以用确定性规则拦住**（正则匹配凭据模式即可）。

**详细做法（How）**

**① 确定性规则进阻断级，模型意见只做建议（核心修正）**

- **关键设计**：格式、禁止 API、凭据模式、缺失测试——这些进 CI 门禁（可解释、可复现）；语义问题（边界条件、并发隐患、命名与约定）作为**建议**呈现，**带置信度与归因字段**。
- **为什么门禁只能由确定性规则构成**：**门禁的权威来自"它错了怎么办"**——确定性规则错了可以复现并改规则；模型意见错了只能调阈值，而阈值调整会连带影响所有类别。**一次明显误报就会让"批量忽略"成为默认动作，此后真实问题也被一起忽略**（§3.2.3 的机制）。
- **关键性质**：**阻断级的规则数量应当很少**——把"必须拦"收敛到十几条以内【经验：规则越多，边界越模糊】；其余全部为建议。

**② 采纳率与忽略率两个数一起看**

- **关键设计**：统计意见被采纳与被忽略的比例；**忽略率是"误报是否可承受"的直接信号**。
- **为什么忽略率比误报率更有效**：误报率需要人工判定"这条到底算不算误报"（成本高、口径不一）；**忽略率是行为数据**（开发者用脚投票），可直接采集、无法辩解。

**③ 意见时效：提交时给出**

- **关键设计**：审查意见在**提交时**给出（而不是次日批处理）。
- **机制**：审查意见的价值随"代码上下文在开发者脑中的新鲜度"衰减；次日给出时，开发者已进入下一件事，**采纳成本上升到不合理的高度**（§3.2.3 的代价）。

**具体数字（档位标注）**

- 阻断级规则的数量：**应当很少**（十几条以内【经验】）。
- 意见时效的代价：把意见从"次日"移到"提交时"，**改动的不是延迟数字，而是采纳成本**——同一个意见在提交时是"顺手改一下"，在次日是"重新载入上下文再改"【经验：两种情形的采纳率差异显著，请用你自己的采纳率数据校准】。
- **自测动作**：取最近 50 条变更，统计意见的**采纳率与忽略率**；再抽查 20 条被忽略的意见，人工判其中有多少是误报——**这一步把"忽略率"与"误报率"对上，是校验门禁健康度的最小动作**。

**失败教训**

**第一版把模型意见也做成阻断**——结果是开发者批量忽略，门禁形同虚设，而且真实问题也被一起忽略。教训：**门禁只能由确定性规则构成**；概率性判断只能做建议，并且必须带可归因的字段，否则无法迭代（这条与 §3.2.3 的机制部分同源）。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条**顺序固定**的路径，与 §4.8 对应：

1. **先定边界与端点，再建尺子**（§6.1、§6.3）——可见域、端点选择、私有评测集是所有能力的前置；**评测集不是后续优化**（§3.1 约束 4）。
2. **再做补全与埋点**（§6.1）——它是请求量最大的一支（万级/日），也是最快能证明"有没有用"的一支。
3. **然后做索引与问答**（§6.2）——结构性问题（谁调用它 / 这段在哪）的价值随时间累积，且它的请求量小、延迟预算宽，可以做得更深。
4. **最后做审查与可写动作**（§6.4）——它们涉及责任与合规，必须在归因、沙箱、人审都到位之后。

**顺序的反面**：先做可写动作（最吸引人），后补沙箱与评测——**未经验证的改动会直接进入主干**，一次事故就会让整个项目被叫停。**另一条反面**：先做审查门禁、后做意见归因——没有归因字段时，误报无法定位到具体规则或阈值，门禁会在"越收越紧"与"被完全忽略"之间反复。

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 无接受率埋点 | 无法回答"有没有用" | 无法优化、无法争取预算 | 埋点与功能同期上线 |
| 边界写在《使用规范》里 | 审计时无法举证 | 边界不可执行 | 边界进平台策略层 + 演练（§6.1） |
| 补全等待长上下文 | 启用率骤降 | 功能被关掉 | 硬超时 + 少呈现不慢呈现 |
| 只做向量检索 | "谁调用它"答不出 | 最高频的一类问题失效，且静默 | 符号 / 引用 / 向量三路（§6.2） |
| 索引滞后无指标 | 答的是旧行为 | 结论错误且难发现 | 滞后量作日常指标 |
| 模型意见进阻断级 | 开发者批量忽略 | 门禁失去权威 | 阻断只由确定性规则产生（§6.4） |
| 意见在次日给出 | 采纳率低 | 审查价值随新鲜度衰减 | 意见挂在提交钩子 |
| 权限判定在检索之后 | 日志里出现不该出现的仓库 | 泄漏 | 可见域前置 |
| 假私有化（索引/遥测出域） | 合规审查不通过 | 项目被叫停 | 全链路出网白名单 + 连接审计（§6.3） |
| 只有内容排除声明、没有演练 | 排除规则的边界（软链/大小写）不符预期 | 策略"声明了但不生效" | 一次本应被排除的请求做演练 |
| 测试只看通过率 | 覆盖上升、缺陷照旧 | 断言空洞 | 变异式有效性抽检 |
| 未验证候选直接呈现 | 编译不过 / 测试红 | 信任崩塌 | 沙箱验证后再呈现 |
| 用公共基准代替私有集 | 榜单好、业务无感 | 优化方向错位 | 建私有评测集 |
| 仓库标签缺失或过期 | 混合路由下私有仓库命中外部端点 | 一次泄漏 | 标签复核机制 + 禁出域演练 |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——代码助手的收益形态是"留存、缺陷与举证能力"，不是"生成了多少代码"。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 补全效率 | 接受率 × **采纳后留存** | 接受率可测；**留存才是价值**（不设通用值，必须自测） | 埋点后取两周数据 |
| 结构性问题可答性 | "谁调用它 / 这段在哪"的答出率与引用准确率 | 从**答不出**到**带文件行号答出** | 抽三个函数问调用方 |
| 审查有效性 | 采纳率、**忽略率**、被拦的确定性问题数 | 确定性规则命中是"下限"，模型意见是"增量" | 取最近 50 条变更统计，并抽查 20 条忽略项 |
| 合规可举证性 | 能否回答"代码有没有出去" | 从"答不上来"到"有策略 + 连接审计 + 演练记录" | 做一次出网/内容排除演练并留痕 |
| 排障时间 | "这段逻辑在哪 / 谁调用它"的耗时 | 从**分钟级人工搜索**到**秒级带引用回答**【经验】 | 抽 10 个真实问题计时 |
| 上下文成本 | 每次补全的平均成本（上下文 + 生成） | 量级以"万次/日"计；**上下文常大于生成**，故优先优化检索 | 统计成本与 token 构成 |
| 代价 | 自托管固定成本 + 沙箱算力 + 索引运维 | 台阶形（按 GPU 与并发买，不按峰值买） | 按月核算固定成本 ÷ 调用量 |

**读法**：前五项是**效率、质量与合规收益**，第六项是**成本收益**（且它的杠杆在检索不在模型），最后一项是**代价**。这一支最容易出现的错位是**只算"生成了多少代码"，不算"留存了多少、缺陷率变化"**——前者是产出量，后者才是价值。

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**边界与尺子先行**（可见域、端点、私有评测集），**补全带埋点**（请求量最大、最快可证伪），**索引与问答**（结构性问题、延迟预算宽，可以做得更深），**审查与可写动作最后**（责任最重）。四次失败教训指向同一件事：**代码智能助手的失败几乎都不是"模型不够强"，而是"缺了验证与度量"**——缺埋点就说不清价值、缺归因就降不下误报、缺沙箱就不敢让它动代码、缺演练就证明不了边界。

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你最像的案例，只做一件最小的事——按它的"判据"跑一次自测（做一次内容排除演练 / 抽三个函数问调用方 / 统计上下文与生成的 token 比 / 抽查 20 条被忽略的审查意见）。哪一件**今天就能做**就先做它：能被立刻验证的缺口，优先级永远高于推断出来的缺口。
