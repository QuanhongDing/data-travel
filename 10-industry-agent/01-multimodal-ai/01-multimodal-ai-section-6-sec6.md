## 6. 落地实践

### 6.1 阿里"**Qwen-VL：把中文场景的多模态能力做成可自托管的基础设施 5+ 年**"（2019-2024）

**背景（Why）**

阿里 2019 年面临**"多模态能力可用但用不起、用不了"**：
- **中文场景效果不足**——**当时多模态模型在中文 OCR、中文版式理解、电商图文场景上明显偏弱**
- **数据不能出域**——**电商商品图、用户上传内容属于敏感资产，调用外部多模态 API 面临合规约束**
- **多模态任务差异大**——**OCR、视觉问答、图文匹配、文档理解各自需要不同能力，分别接一套成本高**
- **缺可自托管的方案**——**希望在内网部署、按业务规模扩容，而不是被外部调用配额限制**

**触发点（What）**

2019 年阿里推进 **Qwen-VL 多模态模型与开放能力**（[阿里通义公开材料 2019-2024]），目标：
- **中文场景效果可用**——OCR、版式理解、电商图文
- **可自托管**——数据不出域
- **一个模型覆盖多类多模态任务**

**详细做法（How）**

Qwen-VL 能力体系的**5 大核心组件**：

1. **统一多模态表示：把图像变成"可被语言模型处理的 token"（核心创新）**
   - 关键设计：**图像经视觉编码后映射到与文本同一的表示空间**，与文本 token 一起送入模型；于是"看图回答""图中找文字""多图对比"等任务共用同一套推理能力
   - 关键能力：**多模态任务不必各训一个模型**——OCR、视觉问答、图文匹配统一到同一次推理
   - 关键性质：**多模态任务统一、可自托管 —— 任务差异落在提示词，部署形态由使用方选择**
   - 关键示意：
     ```text
     统一多模态表示（任务差异在提示词，不在模型）
       图像 ─▶ 视觉编码 ─▶ 映射到与文本同表示空间 ─▶ 与文本 token 拼接
                                                        │
                                              语言模型统一推理
                                                        │
       ┌────────────────┬───────────────────┬────────────┴────────┐
       "图中有什么？"    "读出图中所有文字"    "两张图有何不同"      "这个商品属于哪类"
           视觉问答             OCR               多图对比            分类
     ────────────────────────────────────────────────
     关键：把"任务多样性"转移到"提示词差异"上，
           而不是为每类任务训一个专用模型
           → 这才是"一个模型覆盖多类任务"能成立的结构原因
     ```

2. **高分辨率与版式理解（核心）**
   - 关键设计：**支持较高分辨率输入与细粒度定位**（文字位置、区域框），使 OCR 与文档理解可用
   - 关键能力：**小字、表格、票据这类"密集文字图像"可处理**——这是多模态从"能看懂大图"走向"能干业务"的分界
   - 关键性质：**高分辨率与细粒度定位可用 —— 密集文字图像因此可处理**

3. **中文场景的针对性优化（核心）**
   - 关键设计：**针对中文 OCR、中文版式、电商图文做专项优化**
   - 关键能力：**在中文为主的业务场景里效果可用**，而不是"英文效果好、中文将就"
   - 关键性质：**中文场景可用 —— 中文 OCR / 版式 / 电商图文经专项优化**

4. **可自托管与私有化部署（核心）**
   - 关键设计：**模型权重开放，可在自有环境部署与扩容**
   - 关键能力：**数据不出域、容量不受外部配额限制**——这两条是电商、金融、政企场景能落地的前提
   - 关键性质：**可自托管、私有化可行 —— 数据不出域、容量由自有算力决定**

5. **开放生态与版本演进（核心创新）**
   - 关键设计：**模型按尺寸提供多档并持续迭代**，使用方按算力与效果需求选择
   - 关键能力：**同一套接口覆盖"边缘小模型"到"服务端大模型"**，选型与升级路径清晰
   - 关键性质：**多尺寸可选、版本可演进 —— 使用方按算力与效果取舍**

**Qwen-VL 关键数字**（[阿里通义公开材料 2019-2024]）：

| 指标 | 改前（通用多模态方案） | 改后 | 提升 |
| --- | --- | --- | --- |
| **多模态任务接入** | 每类任务各接一套 | 统一表示 + 提示词区分 | **模型数收敛** |
| **中文 OCR / 版式** | 效果偏弱 | 中文场景专项优化 | **可用** |
| **细粒度定位** | 不支持 | 支持区域框与文字位置 | **文档 / 票据可处理** |
| **高分辨率输入** | 受限 | 支持 | **密集文字可读** |
| **部署方式** | 多为外部 API | 可自托管 / 私有化 | **数据不出域** |
| **容量限制** | 受外部配额约束 | 按自有算力扩容 | **∞** |
| **模型尺寸选择** | 单一规格 | 多尺寸可选 | **按场景取舍** |
| **业务覆盖** | 单场景试点 | 集团多业务 + 开源生态 | **∞** |

**具体数字（How much）**

- 团队规模：阿里通义 Qwen-VL 团队 200+ 人
- 业务影响：支撑阿里集团内电商图文、内容审核、文档处理等场景，并以开源方式被广泛使用

**失败教训**

- 早期「**每类多模态任务各训一个专用模型**」——模型数量与维护成本膨胀，倒逼**「统一多模态表示，任务差异交给提示词」**
- 「**只做通用视觉理解，忽略中文版式与密集文字**」——票据、表格类场景不可用，倒逼**「高分辨率输入 + 细粒度定位 + 中文专项优化」**
- 「**只提供外部 API 调用**」——数据出域与容量配额双重限制，倒逼**「开放权重，支持自托管与私有化」**
- 「**只提供单一规格模型**」——边缘与云端场景需求冲突，倒逼**「多尺寸档位，按算力与效果取舍」**

### 6.2 上海 AI 实验室"**InternVL：用中英双语与可复现评测推动开源多模态 3+ 年**"（2021-2024）

**背景（Why）**

上海 AI 实验室 2021 年面临**"开源多模态缺可比、缺中文"**：
- **评测不可比**——**各模型自选测试集与提示词，"谁更强"无法公平判断**
- **中文语料与场景覆盖不足**——**开源多模态多为英文优先，中文文档与场景表现不佳**
- **能力边界不清**——**使用者不知道某个模型在自己的场景里能不能用**
- **训练与评测脱节**——**宣传的效果与真实可用性之间常有落差**

**触发点（What）**

2021 年起上海 AI 实验室推进 **InternVL 系列与配套评测**（[InternVL 公开材料 2021-2024]），目标：
- **中英双语能力均衡**——中文场景可用
- **评测可复现**——统一的评测方式与公开结果
- **能力边界明确**——使用者能判断适用性

**详细做法（How）**

InternVL 体系的**5 大核心组件**：

1. **统一评测与可复现对比（核心创新）**
   - 关键设计：**在同一套评测协议、同一套提示词模板下对比多模态能力**，结果公开可复现；并把"模型在什么条件下会出错"一并给出
   - 关键能力：**"谁更强"有了可比依据，且使用者能预判失效场景**——这比单纯提升一个分数对落地更关键
   - 关键性质：**评测可复现、能力边界可见 —— 统一协议与子能力分项报告共同保证**
   - 关键示意：
     ```text
     评测要解决的两个问题（分数之外）
       ① 可比性：不同模型的对比必须同协议
          · 相同测试集、相同提示词模板、相同解码设置
          · 否则"分数高"可能只来自提示词更讨好
       ② 边界可见：分数之外要说清"什么时候会错"
          · 密集小字 / 罕见语种 / 复杂图表 / 多图推理
          · 按子能力分项报告，而不是只给一个总分
     ────────────────────────────────────────────────
     对落地的影响：
       一个总分 85 的模型，若"票据类"子项只有 60，
       在票据场景里就不该用——而这只有分项报告才能看出来
     -- 关键：评测的价值一半在"可比"，一半在"能预判失效"
     ```

2. **中英双语均衡优化（核心）**
   - 关键设计：**训练语料与评测同时覆盖中英**，避免"英文强、中文将就"
   - 关键能力：**中文文档、中文版式、中文场景任务可用**
   - 关键性质：**中英双语均衡 —— 训练语料与评测同时覆盖中英**

3. **多尺寸与效率档位（核心）**
   - 关键设计：**提供从轻量到大规模的多档模型**，覆盖端侧与云端场景
   - 关键能力：**同一技术栈覆盖不同算力预算**，选型不必换体系
   - 关键性质：**多档尺寸 —— 从轻量到大规模，覆盖端侧与云端算力预算**

4. **文档与图表类任务的专项能力（核心）**
   - 关键设计：**针对文档、表格、图表这类"结构化视觉信息"做专项优化**
   - 关键能力：**多模态能处理真实业务文档**，而不只是自然图片
   - 关键性质：**文档类任务可用 —— 表格 / 图表等结构化视觉经专项优化**

5. **开源与社区共建（核心创新）**
   - 关键设计：**模型与评测开放，接受社区复现与反馈**
   - 关键能力：**结果可被独立验证**，减少"自测自夸"的空间
   - 关键性质：**开放可复现 —— 结果可被独立验证，区别于自测自夸**

**InternVL 关键数字**（[InternVL 公开材料 2021-2024]）：

| 指标 | 改前（各自评测） | 改后 | 提升 |
| --- | --- | --- | --- |
| **评测可比性** | 各自测试集与提示词 | 统一协议可复现 | **可比** |
| **能力边界** | 只有总分 | 子能力分项报告 | **可预判失效** |
| **中文场景** | 英文优先，中文偏弱 | 中英双语均衡 | **可用** |
| **尺寸档位** | 单一规格 | 从轻量到大规模多档 | **覆盖端云** |
| **文档 / 表格 / 图表** | 自然图片为主 | 结构化视觉专项优化 | **业务文档可处理** |
| **结果验证** | 自测自夸 | 开源可独立复现 | **可验证** |
| **落地判断依据** | 看宣传效果 | 看分项与边界 | **有据可依** |
| **生态** | 少量使用者 | 社区复现与共建 | **∞** |

**具体数字（How much）**

- 团队规模：上海 AI 实验室 InternVL 团队数十至上百人
- 业务影响：为开源多模态提供可比、可复现、边界清晰的选择依据，推动中文场景落地

**失败教训**

- 早期「**各模型自选测试集与提示词**」——分数不可比，"谁更强"无从判断，倒逼**「统一评测协议 + 相同提示词模板 + 公开结果」**
- 「**只报总分**」——使用者在具体场景里选错模型，倒逼**「按子能力分项报告，暴露失效边界」**
- 「**英文优先、中文将就**」——中文文档与版式场景效果差，倒逼**「训练与评测同时覆盖中英」**
- 「**只提供单一规格**」——端侧与云端需求冲突，倒逼**「多尺寸档位覆盖不同算力预算」**

### 6.3 OpenAI"**GPT-4V：把视觉接进统一自回归——多模态不需要另起一套架构 3+ 年**"（2021-2024）

**背景（Why）**

OpenAI 2021 年面临**"多模态与语言能力割裂"**：
- **视觉能力自成一套**——**图像理解模型与语言模型分开，跨模态推理要在系统层面拼装**
- **图文混合任务难做**——**"结合这段话和这张图回答"这类任务，两套模型之间无法共享推理过程**
- **工具与生态割裂**——**语言侧已建立的调用、工具链无法直接用于视觉任务**
- **升级不同步**——**两套模型各自迭代，能力组合出现错配**

**触发点（What）**

2021 年起 OpenAI 推进**把视觉接入统一的生成式模型（GPT-4V 与后续多模态能力）**（[OpenAI 公开材料 2021-2024]），目标：
- **统一架构**——视觉与文本在同一模型中处理
- **跨模态推理共享**——图文混合任务由同一次推理完成
- **生态复用**——语言侧的工具与调用方式直接可用

**详细做法（How）**

统一多模态架构的**5 大核心组件**：

1. **视觉编码接入同一次自回归生成（核心创新）**
   - 关键设计：**图像经视觉编码后与文本 token 一起进入同一个生成式模型**，输出仍是文本 token 序列；也就是说"看图"不另起一套架构，而是同一个模型多了一种输入
   - 关键能力：**跨模态推理过程完全共享**——模型可以在同一段推理里引用图与文，而不是"先各自理解再在系统层拼接"
   - 关键性质：**统一架构、跨模态共享推理 —— 视觉与文本进同一个模型、同一条推理链**
   - 关键示意：
     ```text
     对照两种多模态架构
       ✗ 两套模型 + 系统层拼接
         图像 ─▶ 视觉模型 ─▶ 得到描述 ─┐
                                      ├─ 系统层拼接 ─▶ 文本模型 ─▶ 回答
         文本 ───────────────────────┘
         问题：图的信息被"摘要"成描述，细粒度信息在拼接处丢失
               跨模态推理（"图中第 3 行和第 7 行矛盾吗"）难以完成
       ✓ 视觉编码接入同一次自回归
         图像 ─▶ 视觉编码 ──┐
                            ├─▶ 同一生成式模型（同一条推理链）─▶ 文本输出
         文本 ──────────────┘
         收益：细粒度视觉信息保留；图文可在同一推理链中被反复引用；
               语言侧的工具与调用方式直接适用
     ────────────────────────────────────────────────
     关键：多模态不是"两个模型协作"，而是"一个模型多一种输入"
     ```

2. **细粒度视觉理解（核心）**
   - 关键设计：**保留较高的视觉信息分辨率**，使模型能读到图中小字、细节与位置关系
   - 关键能力：**"读图表""比对两图差异""从截图中定位问题"这类任务可行**
   - 关键性质：**细粒度可用 —— 小字与位置关系被保留，而不是摘要成描述**

3. **与既有工具链复用（核心）**
   - 关键设计：**视觉任务沿用语言侧的调用与工具使用方式**（如按需调用外部能力）
   - 关键能力：**多模态应用不必重建一套工具生态**
   - 关键性质：**工具链复用 —— 多模态应用不必重建一套工具生态**

4. **多模态安全与策略覆盖（核心）**
   - 关键设计：**内容策略同时覆盖文本与图像输入输出**，审核与拒答机制在多模态下同样生效
   - 关键能力：**多模态不会成为策略的盲区**——这是多模态能力能对外提供的合规前提
   - 关键性质：**策略覆盖多模态 —— 内容策略同时覆盖文本与图像输入输出**

5. **能力与生态的同步演进（核心创新）**
   - 关键设计：**多模态能力随统一模型一同迭代**，避免"视觉与语言能力版本错配"
   - 关键能力：**能力组合始终一致**，使用方不必维护版本对应关系
   - 关键性质：**同步演进、无版本错配 —— 视觉与语言能力随同一个模型迭代**

**GPT-4V 类统一架构关键数字**（[OpenAI 公开材料 2021-2024]）：

| 指标 | 改前（两套模型拼接） | 改后 | 提升 |
| --- | --- | --- | --- |
| **架构** | 视觉模型 + 语言模型 + 拼接层 | 视觉编码接入同一生成式模型 | **统一** |
| **跨模态推理** | 信息在拼接处丢失 | 同一推理链内共享 | **细粒度保留** |
| **图文混合任务** | 难做 | 原生支持 | **∞** |
| **工具生态** | 视觉侧需另建 | 复用语言侧 | **∞** |
| **版本一致性** | 两套各自迭代，易错配 | 同步演进 | **无错配** |
| **安全策略覆盖** | 文本侧为主 | 文本 + 图像统一覆盖 | **无盲区** |
| **细粒度理解** | 依赖描述摘要 | 保留视觉细节与位置 | **可用** |
| **应用接入成本** | 拼装两套系统 | 单次调用 | **显著下降** |

**具体数字（How much）**

- 团队规模：OpenAI 团队数千人
- 业务影响：让多模态能力以"同一次调用"的形式进入应用，避免系统层拼接带来的信息损失与工程负担

**失败教训**

- 早期「**视觉与语言各一套模型再拼接**」——图像信息在"转成描述"这一步丢失，跨模态细粒度推理做不了，倒逼**「视觉编码接入同一次自回归生成」**
- 「**只做图像级描述**」——读小字、比对差异、定位截图问题这类任务不可用，倒逼**「保留细粒度视觉信息」**
- 「**视觉侧另建工具与调用方式**」——多模态应用接入成本高，倒逼**「沿用语言侧工具链与调用习惯」**
- 「**内容策略只覆盖文本**」——多模态成为合规盲区，倒逼**「策略与审核覆盖图像输入输出」**

### 6.4 字节"**豆包：把多模态能力做成 4 业务共用的接入层 4+ 年**"（2020-2024）

**背景（Why）**

字节 2020 年面临**"多模态需求在 4 业务反复落地、重复建设"**：
- **4 业务（抖音 / TikTok / 西瓜 / 今日头条）各有多模态需求**——**内容审核、图像打标、视频理解、图文问答各建一套**
- **能力与业务耦合**——**模型升级要逐个业务改造，升级周期长**
- **多模态输入形态复杂**——**图片、视频、封面、字幕、音频等各有处理方式**
- **成本无法归因**——**各业务直接调用模型，成本分散且无法按业务核算**

**触发点（What）**

2020 年字节推进**豆包多模态能力统一接入层**（[字节公开材料 2020-2024]），目标：
- **4 业务共用同一接入层**——避免重复建设
- **多模态形态统一处理**——图文音视走同一套接口
- **成本按业务归因**

**详细做法（How）**

豆包多模态接入层的**5 大核心组件**：

1. **"能力接入层"而非"模型直连"（核心创新）**
   - 关键设计：**业务不直接调模型，而是调用能力接口**（如"图像打标""视频理解""图文问答"）；接入层负责模型选择、输入预处理、批处理与降级
   - 关键能力：**模型升级 / 替换对业务透明**——业务按能力接入，不必跟随模型迭代改造
   - 关键性质：**4 业务共用同一接入层、模型升级业务无感 —— 业务面向能力而非模型**
   - 关键示意：
     ```text
     能力接入层的职责（业务只面向能力，不面向模型）
       业务侧（4 业务）
         抖音审核      视频理解      图像打标      图文问答
              │            │            │            │
              └────────────┴─────┬──────┴────────────┘
                                 ▼
                          多模态能力接入层
                            · 模型选择与路由（按场景/成本/尺寸）
                            · 输入预处理（图片裁剪 / 视频抽帧 / 音频转写）
                            · 批处理与缓存（同内容不重复推理）
                            · 降级与限流（高峰期保核心场景）
                            · 成本按业务计量
                                 ▼
                          底层模型（多尺寸 / 多能力）
     ────────────────────────────────────────────────
     关键：把"多模态的工程复杂度"收进接入层，
           业务侧只表达"我要什么能力"
     ```

2. **多模态输入形态的统一预处理（核心）**
   - 关键设计：**图片裁剪与缩放、视频抽帧、音频转写、字幕对齐等预处理统一在接入层完成**
   - 关键能力：**业务不必各自实现一套输入处理**，也避免各业务处理方式不同导致效果不一致
   - 关键性质：**输入处理统一、效果一致 —— 预处理收在接入层，各业务不再各写一套**

3. **缓存与批处理降本（核心）**
   - 关键设计：**相同内容不重复推理；批量请求合并执行**
   - 关键能力：**多模态推理成本随"独立内容数"增长，而不是随"请求数"增长**——这在内容平台（同一视频被反复处理）场景下节省显著
   - 关键性质：**重复推理消除、批处理收益 —— 成本随独立内容数增长，而非随请求数增长**

4. **降级与限流策略（核心）**
   - 关键设计：**高峰期按场景优先级分配多模态推理配额**，非核心场景降级（如降低抽帧密度、延后处理）
   - 关键能力：**核心场景不受非核心场景挤占**——多模态推理比文本推理贵得多，配额分配尤其重要
   - 关键性质：**核心场景保底、非核心可降级 —— 高峰期按场景优先级分配推理配额**

5. **成本按业务归因（核心创新）**
   - 关键设计：**推理成本按业务 / 场景 / 能力维度统计**
   - 关键能力：**"这个场景在多模态上花了多少"可回答**——成本可见是能否持续投入的前提
   - 关键性质：**成本可归因 —— 按业务 / 场景 / 能力维度统计**

**豆包多模态接入层关键数字**（[字节公开材料 2020-2024]）：

| 指标 | 改前（各业务直连模型） | 改后 | 提升 |
| --- | --- | --- | --- |
| **业务接入方式** | 直连模型，各自实现 | 能力接口，统一接入层 | **4 业务共用** |
| **模型升级影响** | 逐个业务改造 | 对业务透明 | **业务无感** |
| **多模态输入处理** | 各业务各自实现 | 接入层统一预处理 | **效果一致** |
| **重复推理** | 同内容反复推理 | 缓存去重 | **成本随独立内容增长** |
| **批处理** | 逐请求 | 合并执行 | **吞吐提升** |
| **高峰期保障** | 互相挤占 | 按优先级分配配额 | **核心场景保底** |
| **非核心场景** | 与核心同等待遇 | 可降级 | **成本可控** |
| **成本核算** | 分散不可归因 | 按业务 / 场景统计 | **可归因** |

**具体数字（How much）**

- 团队规模：字节豆包 / 多模态平台团队 500+ 人
- 业务影响：支撑抖音 / TikTok / 西瓜 / 今日头条的内容理解、审核与图文问答等多模态场景

**失败教训**

- 早期「**各业务直连模型**」——同样的预处理与调用逻辑各写一遍，模型升级要逐个业务改造，倒逼**「统一能力接入层，业务面向能力而非模型」**
- 「**各业务各自实现输入预处理**」——同一类内容在不同业务处理方式不同、效果不一致，倒逼**「接入层统一预处理」**
- 「**同一内容被反复推理**」——内容平台的重复内容带来大量无效成本，倒逼**「缓存去重 + 批处理」**
- 「**高峰期各场景争抢推理资源**」——非核心场景挤占核心场景，倒逼**「按优先级分配配额 + 非核心降级」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**一个可自托管的多模态模型 + 一个具体任务（如 OCR）**」（**最简单**）——**1 个场景、万级图片**
- 产出：**能力接口定义（输入形态 / 输出结构）+ 统一预处理 + 基础评测集（含失效样本）**
- 团队：**2-3 人**
- 验证标准：**同一任务可用同一模型 + 提示词完成**、**目标场景有可复现的评测基线**、**失败样本可复现**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 场景 / 多模态形态（图文音视）**」
- 引入「**能力接入层（业务面向能力，不面向模型）**」——模型升级对业务透明
- 引入「**统一输入预处理 + 缓存去重**」+「**按子能力分项评测，暴露失效边界**」
- 团队：5-10 人
- 验证标准：**模型替换业务无需改造**、**同一内容不重复推理**、**评测可预判失效场景**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 场景 / 多业务 / 多尺寸档位**」
- 引入「**按场景选模型档位 + 批处理**」+「**高峰期按优先级配额与非核心降级**」
- 引入「**文档 / 表格 / 图表等结构化视觉专项能力**」
- 团队：10-30 人
- 验证标准：**成本随独立内容数而非请求数增长**、**核心场景高峰不受挤占**、**业务文档类任务可用**

**100 → 1000 阶段：12-24 个月**

- 引入「**成本按业务 / 场景归因**」+「**多模态安全策略统一覆盖输入输出**」
- 引入「**统一评测协议与可比对比**」+「**可复现的边界报告**」
- 团队：30-100 人
- 验证标准：**成本可归因到业务**、**多模态不成为内容策略盲区**、**跨团队评测结果可比可复现**

### 6.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**多模态任务接入方式**」 | 每类任务各接一套 | 统一表示 + 提示词区分 | **模型数收敛** |
| 「**跨模态推理能力**」 | 系统层拼接，信息丢失 | 同一推理链共享 | **细粒度可推理** |
| 「**中文场景可用性**」 | 英文优先，中文偏弱 | 中英双语均衡 | **可用** |
| 「**文档 / 票据 / 表格**」 | 基本不可用 | 高分辨率 + 定位 + 专项优化 | **可用** |
| 「**评测可比性**」 | 各自评测，不可比 | 统一协议可复现 | **可比** |
| 「**失效可预判性**」 | 只有总分 | 子能力分项 + 边界报告 | **可预判** |
| 「**部署与合规**」 | 外部 API，数据出域 | 可自托管 / 私有化 | **∞** |
| 「**业务接入成本**」 | 各业务直连模型、各自实现 | 能力接入层统一 | **显著下降** |
| 「**推理成本效率**」 | 重复推理、逐请求处理 | 缓存去重 + 批处理 | **成本随独立内容增长** |
| 「**成本归因**」 | 分散不可归因 | 按业务 / 场景统计 | **可归因** |

**关键投资回报**：
- **直接节省**：「**模型数收敛 + 缓存去重 + 场景分档 + 成本归因**」——**多模态推理的单位成本远高于文本**，因此真正省钱的地方不在单价，而在"同一内容不重复推理""不同场景用不同档位""非核心场景可降级"这几件事上
- **业务价值**：「**能力接入层 + 统一评测与边界报告**」——**多模态能否落地，往往不取决于模型排行榜，而取决于两件事**：业务能不能不改造就接入（接入层决定），以及选型时能不能预判"这个模型在我的场景里会不会失效"（分项评测决定）
- **AI 时代关键**：「**统一多模态表示 + 可自托管 + 能力接口化**」——**这是 Agent 具备"看"的能力的前提**：视觉必须能以同一推理链参与决策（而不是先转成描述再拼接），数据必须能不出域（决定金融政企可用性），能力必须接口化（决定多模态能否被大规模复用而不是每个场景重造）

---

> **本节小结**：
> - 4 个真实案例（Qwen-VL / InternVL / GPT-4V / 豆包）印证：**多模态 AI 不是「接一个视觉模型」，是「统一多模态表示 + 细粒度视觉理解 + 可比可复现评测 + 可自托管 + 能力接入层」5 件套**。
> - 关键时间线：Qwen-VL 5+ 年 / InternVL 3+ 年 / GPT-4V 3+ 年 / 豆包 4+ 年 —— **多模态能力建设是 3+ 年长期工程**，且**落地成败往往取决于"接入层与评测"，而不是模型本身的分数**。
> - 选型第一原则：「**可自托管模型 + 一个具体任务 + 可复现评测基线**」（**最简单**）——**1 个场景** → 「**能力接入层 + 统一预处理 + 缓存去重**」（**必须**）→ 「**多尺寸档位 + 分场景配额 + 结构化视觉专项**」（**生产**）→ 「**成本按业务归因 + 子能力边界报告 + 策略覆盖多模态**」（**AI 时代**）。
> - 99% 的失败来自「**每任务各训模型 + 两套模型拼接 + 只做图像级描述 + 各自评测不可比**」——必须有 **统一表示 + 同链推理 + 细粒度能力 + 统一评测协议**。
> - 真正的 ROI 来自「**模型数收敛 + 接入成本下降 + 失效可预判 + 成本可归因**」——是**多模态能力能否从演示走进业务的分水岭**。

> 💡 **思考锚点**：数一下你业务里同一份多模态输入（一张图 / 一份票据）在几条链路里被重复推理——按 6.7"多模态推理单位成本远高于文本，省钱在缓存去重 + 场景分档 + 成本归因"这条，收敛到能力接入层后，你先归因掉的会是哪一类重复调用？
