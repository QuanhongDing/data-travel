## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自建 / 买平台 / 用 RAG 改造"打分有三个结构性问题：① 同一列在不同处境下方向相反（"可定制标签体系"对垂直行业是必需、对通用场景是负担）；② 打分表隐含"这些选项互斥"，而真实形态常是组合（买采集 + 自建判断 + 自建分发）；③ 最关键的判据（授权边界、误报代价、有没有人做抽检）**不是可打分的维度，而是门槛**——不满足直接出局。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 授权边界 | 信源是否允许摘要 / 对外分发？ | 不允许对外分发的信源决定渠道形态（**门槛不是权重**） |
| 时效预算 | 从发布到可见允许多久？ | 分钟级 → 必须流式 + 兜底；天级 → 批处理足够 |
| 误报与漏报代价 | 报错了会怎样？漏报了会怎样？ | 决定闸门密度（是否要人审）与阈值取向 |
| 判断口径归属 | 标签体系、主体白名单、阈值由谁维护？ | 口径不放自己手里 → 垂直行业的判断力无法积累 |
| 抽检人力 | 谁每周做抽检？ | **没有这个人，链路三个月内退化成噪声源** |
| 受众结构 | 一个人、多角色，还是多客户？ | 决定分发形态（一份简报 vs 扇出 + 频控） |

> **读法**：先用第 1 条筛掉不可行（授权不允许对外分发 → 面向客户的产品形态出局）；再用第 3、5 条筛掉"无人维护的高风险形态"；最后用第 2、4、6 条在剩下的里选——**第 5 条最容易被跳过，也是这条链路最常见的死因**。顺序反过来最常见的结果是：先按"时效"选了流式链路，再回头发现手上没有能做抽检的人——第 1 条答错时，后面几条的结论会一起作废。

**这六条判据不在同一个量纲上，而且六条全是"我的约束"、没有一条是"方案的属性"**：只有第 1 条（授权边界）是**否决性的**——它不参与比较，只决定候选集合。它的落点是 §4.2（1）里的 `entitlement.redistribute_external` 一行；这一行写错的后果不是"效果差"，而是把只允许内部转发的信源配进了对外渠道，一次越界分发就足以让整条链路停下，收益无法补偿。其余五条（时效预算、误报与漏报代价、口径归属、抽检人力、受众结构）都可以"部分满足"，作用是在剩下的候选里**分配名次**——但"抽检人力"这一条在打分表上会被写成"运维友好 +1 分"这类措辞，而在本主题的处境里它是门槛：没有人做抽检的链路，三个月内退化成噪声源（§3.1 约束 5），这与"某列分数低一点"不是同一件事。**因此本节的第一张表不是评分表，而是一组能淘汰候选的判据**；候选自身的能力（能不能自检断供、能不能把分发单位立成事件簇、能不能做片段级回指）留到 §7.2 与 §7.3 的机制表里去讲——它们决定名次，决定不了上界。

**同一条判据在不同链路里的分量也不同**：同一条"时效预算"，在"监管突发必须分钟级可见"的链路上是硬约束，在"周报型行业综述"的链路上几乎不构成约束——§3.1 的约束 2 与 §3.2.1 的判定方法把这件事写成一句可判定的话：把信源的 `interval_min` 与那一段的 P95 目标并排，**若 P95 目标小于一个抓取间隔，这个模式在原理上就不达标**。所以固定权重的打分表在这里失效：它给"实时支持"这一列打出的高分，既不能证明该方案适合突发型链路，也不能证明它不适合周报型链路；能替代它的只有对每个信源逐个算一遍 `interval_min` 与 P95 的差。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 自建端到端链路 | 全链路自持 | 采集、去重、分类、摘要、分发、反馈全部自建 | 垂直行业、有数据工程能力 | 长期人力；信源与规则要持续维护 |
| 通用抓取 + 自建摘要 | 只自建判断层 | 采集用通用抓取或商业数据源，判断与分发自建 | 想控制判断口径的团队 | 采集侧的授权与稳定性依赖第三方 |
| 商业情报平台（买） | 产品化 | 平台自带信源、分类与分发，按席位或数据量计费 | 时效与定制要求不高 | 标签体系与阈值由产品定；垂直判断力难积累 |
| 通用 RAG / 检索平台改造 | 复用检索能力 | 把情报当"持续流入的语料"，用检索平台做摘要与查询 | 已有成熟检索平台的团队 | **情报不是问答**：缺断供、去重、频控、时效四件 |
| Agent 平台上的情报作业 | 平台 + 作业 | 情报作为平台上的常驻作业，复用平台的配额、审计、工具出口 | 已建 Agent 平台的团队 | 平台解决治理，**不解决情报语义**（去重、回指、频控要自己写） |
| 人工简报 + 自动化辅助 | 人机分工 | 人定信源与口径，自动化做采集、去重与初稿 | 团队小、判断风险高 | 时效受人力限制（人休假即断） |

**这六个候选其实分三族**：**自建族**（自建端到端链路、通用抓取 + 自建摘要）——判断口径完全自持，代价是长期人力；**产品族**（商业情报平台、通用 RAG / 检索平台改造）——拿到现成能力，代价是口径与形态受制于产品；**人机族**（Agent 平台上的情报作业、人工简报 + 自动化辅助）——把"判断"与"自动化"分开，代价是时效与规模受人力约束。

**族内可替换，跨族不可换**：自建族内部换的是采集与判断的实现位置；从自建族换到产品族，等于**把标签体系与阈值交给别人维护**——那不是技术迁移，是判断力的转移。

**"通用抓取 + 自建摘要"这一行在采集侧还有另一种现实形态：不自己抓，而是从数据提供方按数据集订阅。** 书内已具名的形态是数据市场里的数据提供方（`15-case-studies/10-overseas-cases/10-overseas-cases-section-8-sec8.md` §8 把 Snowflake Marketplace 的数据提供方记为 Bloomberg / Reuters / Weather Company 一类）。它与"通用抓取"的机制差别只有一处，但这一处直接决定 §7.3.2 的答案：**素材的授权边界写在数据集的订阅条款里，而不在你的抓取配置里**——于是"能不能对外分发"这个问题从"我判"变成了"我查"，而且条款变更不一定主动通知你。把这一形态放进候选表时不要新开一行：它在机制上属于自建族的采集侧，**换掉的只是"素材从哪来"，判断层与分发层一件都没有换**。

**候选表还有一条它没写、但决定成败的维度：分发单位与去重单位是不是同一个。** 六行候选里，"自建端到端链路"与"Agent 平台上的情报作业"都必须由自己把这个单位立起来（§7.3.2 给出三处必须共用的标识）；产品族的默认单位常是"文章 / 条目"；人机族的单位由人临时决定。**这条维度不写进候选表的后果是**：选型时看起来六个候选都在比"能力"，落地后才发现真正的差别在"同一件事会被推几次"。

**表里"主要代价"一列是机制在账面上的投影，不是采购条款。** 自建族那一行写的是"长期人力"，而它的形状是**台阶形**（按人年跳）；产品族写的是"口径受制"，而它的形状是**线性**（席位 × 数据量）；人机族写的是"时效受人力限制"，形状是**人的时间线性**。三种形状在 §7.4 展开——**选型时如果只读这一列的措辞、不读它的形状，就会出现"为省许可费选了台阶形方案、两年后发现人力账单更高"这一类判断失误**。

**本节不具名的一处**（按证据纪律显式声明）：商业情报平台与生成式摘要类产品的**引用回指粒度**（回指到篇还是到片段）与**标签体系口径**（类别集合能否由客户改），这两件事本主题与全书他处都核不到可引用的产品文档，所以本节不点产品名、也不写年份；要自己判，就用两个动作去试：取一条该产品输出的摘要，看它的出处能不能点开到一个**片段**而不是整篇；再取一个你想加而它没有的标签，问一句"我能不能自己加"。答不上后一问，说明口径不在你手里（§7.3.4）【经验：以各产品官方文档当前版本为准】。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 触发方式：信源变化驱动，还是人驱动

**机制是什么**：链路的驱动源只有两种——**外部变化**（情报）或**人的提问**（问答）。

**它在各候选中的实现差异**：自建族与人机族都是"变化驱动"（有调度、有断供判据）；**产品族的"RAG 检索平台改造"是"人驱动"**——它没有"没人问也要跑"的机制，因此需要额外补上调度、断供与推送。

| 候选 | 驱动源 | 谁决定"什么时候跑" | 静默失效的形态 | 兜底由谁承担 |
| --- | --- | --- | --- | --- |
| 自建端到端链路 | 外部变化 | 你自己的调度与信源分级 | 调度停了：没有推送，也没有报错 | 你自己（调度 + 断供判据 `no_data_alert_after`） |
| 通用抓取 + 自建摘要 | 外部变化（在别人手上） | 数据提供方的发布节奏 + 你的拉取 | 提供方改了字段或延迟了发布 | 提供方的条款，与你自己的兜底轮询 |
| 商业情报平台（买） | 外部变化（平台侧） | 平台的信源清单与刷新节奏 | 平台少覆盖了某个信源，你不知道 | 平台；你只能通过"漏报"发现 |
| 通用 RAG / 检索平台改造 | 人的提问 | 提问者 | 没人问时什么都没发生，且看不出异常 | **无**（要自己补） |
| Agent 平台上的情报作业 | 平台调度 + 作业配置 | 平台的调度器与配额 | 作业被配额挡住或被降级，异常在平台侧 | 平台提供观测面，**情报语义要自己补** |
| 人工简报 + 自动化辅助 | 人的工作节奏 | 人 | 人休假：整条链断 | 人（靠交接） |

**由此必然导出的性质**：因为**"变化驱动"要求持续运行且可被发现失效**，所以任何从问答形态改造来的方案，都必须补"断供检测"这一件；否则它会**静默失效**——系统仍在响应提问，但外部变化已经不再进来。**这条性质还有一层常被忽略的推论**：一个"什么都没来"的状态，在链路上与你自己坏掉的状态**长得完全一样**，因此断供检测必须是**由你发起的独立探测**（心跳或低频轮询），而不能是"等待对方报错"——这也是 §3.2.2 把兜底轮询列为该模式**组成部分**而不是附加项的原因。

**触发方式还决定了一件成本结构上的事：失败的可补偿性**。变化驱动下，"这一轮没抓全"是一个可以被重放的单位（§4.2（2）的游标"处理失败不推进"与 `replay()`）；而人驱动下没有"轮"这个概念，漏掉就是漏掉了。**因此从人驱动改成变化驱动时，真正要新建的不是调度本身，而是"可重放的窗口"**——存量迁移（§4.4）的影子对比之所以要跑 2–4 周【经验：周期随信源发布频率浮动】，就是为了让"人工报了而系统没报"这份清单先出现。

**公开证据**：本主题自己的证据是配置级的——§4.2（1）把断供判据写成信源登记里的一个必填字段（`health: {no_data_alert_after: 12h}` 是模板给的配置值），§4.5 模板 2 给出它的实现（按 `(source_id, max(ingested_at))` 与阈值比对），§4.7 演练表把通过判据写成"`no_data_alert_after` 内告警并通知到 Owner"【公开】（来源：本主题 §4.2（1）（2）、§4.5 模板 2、§4.7）。**这一步的调度实现落在全书他处已具名的编排产品上，但要写明这是范围邻接、不是举证**：Ch3 §12 的选型表把 Apache Airflow（2.9+）记为"代码定义的通用编排"、把 Apache DolphinScheduler（3.1+）与阿里云 DataWorks 记为"可视化 / 声明式编排"，并给出"团队以 Python 为主 → Airflow；维护者以数仓 / SQL 开发为主 → DolphinScheduler"这条判据；Ch3 章 README 把消息队列记为 Kafka / Pulsar / RocketMQ 一类。**这些条目证明的是"调度与队列这一层有成熟产品"，不是"某产品在做行业情报"**——本主题 §4.3 的采集行只写到"官方 API / RSS / SDK / 合规的页面采集"，没有产品名【公开】（来源：`03-data-stack/12-scheduler/12-scheduler-section-4-sec4.md` §4.3 工具链与平台、`03-data-stack/README.md` 的组件行）。

**失效条件**：当业务只要求"我提问时能查到最新"时，问答形态够用；一旦要求"没人问也要报"，就必须改造（成本主要在调度与去重）。**另一条边界在信源侧**：当所有信源都不提供可拉取的接口、只提供推送时，"独立探测"这一件在物理上做不成，此时唯一可行的兜底是"要求对方向你发心跳"，而这需要写进合同——做不到的话，这条链路就只剩"静默失效"一种失败形态。至于某一款信源的接口语义、配额与心跳约定，请以该信源方官方文档的当前版本为准，本节不给站点名。

#### 7.3.2 分发单位：素材、事件簇，还是"人订阅的流"

**机制是什么**：分发单位的粒度决定了重复与骚扰的形态。

**它在各候选中的实现差异**：自建族多数能做到事件簇（因为它掌握去重）；产品族的默认单位常是"文章 / 条目"（去重可能有，但**跨源归并**未必开放配置）；人机族由人做归并（质量高、规模小）。

| 分发单位 | 重复是靠什么消除的 | 授权边界的落点 | 频控的作用点 | 改成簇时要动几处 |
| --- | --- | --- | --- | --- |
| 素材（文章 / 条目） | **判断型**：每次再判一次是否重复，判一次错就重复一次 | 逐条素材判 | 只能按条数压 | 初始态 |
| 事件簇 | **结构型**：只要归簇正确，重复在机制上不可能发生 | 簇内按**来源级**标记裁剪（簇里含不可分发来源时，须剔除该来源而保留簇） | 按 簇 × 人 × 群组 三个维度 | **三处**：分发键、频控维度、留痕主键 |
| 人订阅的流 | 取决于上游是否已归并；上游不归并就等于素材单位 | 由订阅规则决定（边界通常不进配置） | 按人 | 改口径与订阅两层，最大 |

**由此必然导出的性质**：因为**重复推送是用户流失的第一驱动**，所以分发单位的选择不是"优化项"而是"生存项"——**产品族若不能把分发单位设成簇，就必须自己加一层归并**（成本：一遍额外的去重与推送改写）。**判断型与结构型的差别值得单独说清**：判断型的去重每次都要重新决定，所以它的正确率与素材量同阶衰减；结构型的去重只要归簇正确，重复就在机制上不可能发生——**这是本主题里少见的"用结构而不是用判断消除一类缺陷"的做法**（§3.2.4）。

**由此还有一条代价不对称的推论，它决定了阈值该往哪边偏**：重复的代价是"用户烦"，误合并的代价是**漏报**（两条不同事件被合成一条，表现为"少报了一件事"且看起来正常）。**两个方向的代价不同阶**，因此阈值应当偏向"宁可不合"，评估时**同簇准确率与拆分准确率两个数都要看**——只报前者会系统性高估质量（§3.2.4 的判据与 §4.2（3）的抽检口径）。

**还有一条"单位"这个决定为什么来得特别早的理由**：簇标识会被**三处外部引用**——分发键（§4.2（8）的 `cluster_id`）、频控维度（§4.2（7）的 `event_cluster 24h/1`）、留痕主键（§4.5 模板 3 的分发记录）。三处一旦有了历史数据，**改单位就等于同时改三处并作废历史**；三处各用各的标识时，会出现"频控认为推过了 / 留痕里查不到 / 用户又收到一次"这种自相矛盾的状态，且没有任何单一视角能看出它是矛盾的——§3.2.7 的判定方法（实收 + 被挡 ≠ 候选池）存在的意义就是把这种矛盾逼出来。

**公开证据**：本主题的机制证据在 §6.1——Palantir 一类分析平台把数据组织成"对象 + 关系"而不是以文档为原子单位，"同一件事"因此有一个**天然的同一性判据**（对象标识 + 关系），分发单位与去重单位自动统一（`…-section-6-sec6.md` §6.1 的两种单位对照图）；配置级证据是 §4.2（7）的三维频控与 §4.2（8）含 `cluster_id` 列的 `intel_sla` 表（该表主键是 `item_id`，簇标识在这里是分发与对账用的键）；案例级证据是 §6.4 的簇生长规则（不重推、只更新）【公开】（来源：本主题 §6.1、§6.4、§4.2（7）（8）、§4.5 模板 3）。同一族问题（把多份观察归到同一实体）在全书他处已具名，**但引用时必须说明它讲的是别的东西**：Ch1 §09 把托管实体解析服务写成一行（AWS Entity Resolution / Salesforce Data Cloud / Palantir Foundry / 阿里云实体解析），机制是"候选生成 + 匹配规则 / 模型 + 人工复核工作台，客户只做字段映射"——**那里归的是主数据身份，这里归的是外部事件，两者不可互相替代**（来源：`01-modeling/09-one-id/09-one-id-section-7-sec7.md` §7.2、`01-modeling/09-one-id/09-one-id-section-4-sec4.md` §4）。

**失效条件**：当同一事件的来源数长期为 1（独家信源）时，归并的收益有限；但只要来源数 ≥ 2 且高频，归并就是必需。**另两条失效条件更硬**：① **授权边界可能让簇级裁剪退化为整簇不可分发**——如果唯一来源不可对外分发，剔除之后这个簇对外就是空的，此时正确动作是"这一簇只进内部渠道"，而不是"把来源去掉再发"；② **簇会生长**——如果没定义簇生长规则（新增来源默认不重推、只在依据实质变化时标"更新"补推一次），那么"分发单位是簇"这件事只完成了前半，重复会从"每篇素材推一次"变成"每次来源新增推一次"（§6.4 的触发点正是这一形态：同一并购事件被推了三遍，因为簇在生长）。

#### 7.3.3 摘要的可验证性：片段回指，还是"通顺即可"

**机制是什么**：摘要是否要求**每个事实点指回片段**，决定它能否被审计与纠错。

**它在各候选中的实现差异**：自建族可实现片段级回指（需要自己存片段映射）；产品族通常只给"原文链接"（**回指粒度到篇，不到段**）；人机族由人保证（但不可扩展）。

| | 无回指（自由生成） | 回指到篇 | 回指到片段 + 数值回查 |
| --- | --- | --- | --- |
| 读者的验证成本 | 只能选择信，或自己去搜原文 | 要在长文里自己找 | 一次点击 |
| 能否被审计 | 不能 | 部分（能定位到文档） | 能（能定位到事实点） |
| 数字幻觉能否被拦 | 不能 | 取决于人愿不愿意去核 | 回查不通过即剔除，不写进摘要 |
| 生成侧要多做什么 | 什么都不用 | 存文档标识 | 存片段映射；回查前做单位 / 口径规范化 |
| 故障期降级成什么 | —— | —— | 抽取结果 + 原文链接（**降功能不降可信**） |

**由此必然导出的性质**：因为**决策场景需要可点开验证**，所以"回指到篇"在情报场景属于**半成品**——用户仍要自己找；判据是"摘要里的每个数字能否在一次点击内被验证"（§3.2.6 的「点开一个位置」）。**这条性质的机制来源不是"模型更准"，而是验证成本的量级差**：没有回指时，验证一条情报要么信、要么自己去搜原文（成本高到没人做）；有片段回指之后，验证变成一次点击。§3.2.6 把这条差别写成一句——**"引用回指只指到整篇等于没有回指"**。

**第二条性质是"数字为什么必须机械化回查，而不是靠人读"**：文字表述的偏差读者能察觉，**数字的偏差读者察觉不到**，而且数字会被直接拿去用（复制进汇报材料时，"这个数未经验证"这个标注会丢失）。因此回查只有两种可选设计——"不通过就标注置信度"或"不通过就不写"；**选前者的做法在流转中会失效**，因为置信度不会跟着数字走（§6.2 的机制解释把这条写成了"不写是不可绕过的，标注是可以丢的"）。

**第三条性质容易被低估：回查必须先规范化再比对**。情报里的数值经常经过**单位换算**（亿元 → 万元）、**口径改写**（同比 → 环比）与**指代替换**（"该公司" → 具体名称），所以"原文里有没有这个字符串"这种弱回查会把大量正确的数值判成"原文没有"，最终表现为**回查通过率低到没人看**。代价因此不是存储，而是**维护一套按领域的规范化规则**。

**公开证据**：本主题两个案例都是这一形态的直接出处——§6.2 把通讯社的生产方式写成"一条新闻从产生起就带着来源与时间"，并落成"摘要按事实点 + 出处片段生成"与"回查前先做规范化"；§6.3 补上两件本主题独有的要求：引用要带**抓取时间**（否则材料被改后无法回答"我看的是哪一版"），以及权限要在召回前裁剪【公开】（来源：`…-section-6-sec6.md` §6.2、§6.3）。自己的模板在 §4.2（6）（事实点 + 出处片段 + 数字校验 + 多来源）与 §4.5 模板 1（`value_appears_in_span` 不通过即 `drop`）。若要把"事实性"做成可跑的指标，全书他处给出的是 RAG 侧的评估框架【公开】：RAGAS 于 2023.10 发布、2025 年形成 RAGAS / TruLens / ARES / DeepEval 的评估体系，指标含 `faithfulness` / `groundedness`，同一章明确提醒"忠实性在各框架里的定义不同、跨框架分数不可比"（来源：`04-data-assetization/05-rag-architecture/05-rag-architecture.md` §1.4 记 RAGAS 于 2023.10 发布、并把 2025 年记为"评估体系成熟（RAGAS、TruLens、ARES、DeepEval）"；这条提醒见同章 §4.2 的评估做法与 §3 的评估反模式表）。**生成内容标识侧另有一条合规锚点**：Ch8 §01 把《人工智能生成合成内容标识办法》（2025）映射成"输出侧标识注入 + 输出留档中的标识字段"，与《生成式人工智能服务管理暂行办法》（2023）同列【公开，监管公示】（来源：`08-ai-governance/01-ai-data-governance/01-ai-data-governance-section-7-sec7.md` §7 与同章 §4、`99-outro/03-trends/03-trends-section-5-ai.md` §5）。

**失效条件**：当摘要只用于"扫一眼知道发生了什么"（不作决策依据）时，回指到篇可以接受。**另有两条边界**：① **多模态输入下"片段"的定义要重做**——音视频的片段位置是时间戳与转写片段，沿用文本侧的"段号"会让回指直接失效（§5.3.5）；② **回指的粒度要与摘要的粒度匹配**——即时渠道的一句话摘要只需带关键数字的出处，日报的完整摘要要带每个事实点的出处，两者的字段可以不同，但**都不能没有出处**。

#### 7.3.4 判断口径的归属：自己的标签体系，还是产品的分类

**机制是什么**：标签体系与阈值决定了"什么算重要"，这是垂直行业判断力的载体。

**它在各候选中的实现差异**：自建族自持（可积累）；产品族用产品分类（**跨客户的通用口径**，未必贴合你的行业）；人机族由专家自持。

| 口径由谁维护 | 误报的下降路径 | 积累在哪里 | 换供应商 / 换人时 | 撞天花板的方式 |
| --- | --- | --- | --- | --- |
| 自己（自建 / 半自建） | 归因到规则或阈值 → 改 → 复测 | 自己的标签体系与阈值库 | 资产留在自己手里 | 抽检人力跟不上，阈值长期不动 |
| 产品方 | 提交反馈 → 进厂商迭代队列 | 厂商的样本分布上 | 历史判断记录不可迁移 | 你的行业与产品目标客群分布不同 → 误报降不下来 |
| 专家（人机族） | 人的经验直接改 | 个人身上（不在系统里） | 人一走就归零 | 时效与规模 |

**由此必然导出的性质**：因为**误报只能通过"归因到规则 / 阈值并修改"来下降**，所以口径不在自己手里的方案，**误报是只能忍受的常数**——这也解释了为什么"买平台"在垂直行业往往会在第二年遇到天花板。**第二层性质是关于遗漏的**：一条误报要能被改掉，前提是它**能被落到一个可改的对象上**（哪条规则过宽、哪个标签的阈值过低）；因此"归因字段"不是可选的日志，而是**调优能力的物理前提**——§4.2（5）把它写成 `attribution: [rule_hits, model_score_by_label, classified_at]` 三个必落字段，§3.2.5 的判定方法是"抽 20 条被判为误报的情报，逐条填'命中了哪条规则'或'哪个标签的多少分'——有任何一条填不出，说明归因字段没进库"。

**第三层性质是口径会自己膨胀**：标签体系一旦没有 Owner 与增删流程，新增标签的速度会持续高于归档的速度；此时同一个误报可以落到多个标签上，**无法定位到阈值**——也就是说，口径名义上还在你手里，实际上已经失去可调性。这是"自持口径"最容易发生的退化，它的可测信号是**两个增速的对比**，而不是标签总数。

**公开证据**：本主题的落地配置在 §4.2（5）——规则用 `priority: hard` 表达"必须命中且可解释"，模型侧阈值按标签分别设，并强制落归因三字段；§3.2.5 把"两类判断各用它自己需要的可解释性标准"写成机制段【公开】（来源：本主题 §4.2（5）、§3.2.5）。全书他处有两条同构的具名做法，**可作旁证但对象不同**：Ch11 §01 把"AI 辅助能力（非独立品类）"单列一行（Mona AI Quality Copilot / Anomalo Autonomous / Monte Carlo + LLM 一类），用法写的是"生成规则草稿与异常归因"，并明确"**生成的规则必须经复核才能进 P0**"；Ch1 §09 把托管实体解析服务描述为"候选生成 + 匹配规则 / 模型 + 人工复核工作台"。两者支持的都是同一条分工线——**机器给候选，规则与阈值由人定**（来源：`11-cross-cutting/01-data-quality/01-data-quality-section-4-sec4.md` §4.3 工具链表、`01-modeling/09-one-id/09-one-id-section-7-sec7.md` §7.2）。至于某个产品的标签类别集合能否由客户增改，本章核不到可引用的产品文档，判定入口见 §7.2 末尾那条【经验】。

**失效条件**：口径归属的价值**依赖于一个前提——有人真的在用这个权限**。当团队没有抽检与阈值维护的排期时，自持口径只是"名义上在你手里"：阈值不会自己变准，标签体系不会自己收敛，此时它的表现与产品族的默认口径没有区别（§3.1 约束 5 把这条写成"没有这个人，情报系统会在三个月内退化成噪声源"）。**另一条边界**：当你的行业与产品的目标客群分布恰好一致时，"通用口径"并不构成损失——判断这件事的依据是"你的误报能不能归因到某个可改对象"，而不是"口径是不是你写的"。

#### 7.3.5 反馈闭环的归属：你的系统能不能被"改对"

**机制是什么**：情报系统的质量不是一次调出来的，而是**一轮一轮改出来的**；而"能不能改对"取决于反馈闭环落在谁手里。

**它在各候选中的实现差异**：自建与半自建的方案里，反馈（打开 / 采纳 / 纠错 / 屏蔽 / 补报漏报）**回流到你自己能改的参数上**（规则、阈值、提示、信源等级）；买成品的方案里，反馈通常回流到**厂商的迭代队列**——你能提交，但不能直接改，改动节奏与方向由对方定。

| | 反馈回流到哪 | 谁能改阈值 | 一次改进的周期 | 失效信号 |
| --- | --- | --- | --- | --- |
| 自建 / 半自建 | 自己的规则、阈值、提示、信源等级 | 你 | 一个抽检周期 | 反馈只进报表，不进参数 |
| 产品族 | 厂商的迭代队列 | 厂商 | 厂商的版本周期 | 你的反应是"提工单给厂商" |
| 人机族 | 专家本人 | 人 | 即时，但不可留存 | 专家休假即停 |

**由此必然导出的性质**：因为**情报质量的两侧（误报与漏报）不对称**（§3.1 约束 3），所以"能改"这件事的价值不是效率，而是**能不能把阈值调到适合你自己的误报—漏报偏好**。成品方案的默认阈值是**厂商在它的样本分布上调出来的**，与你的信源集合、受众容忍度都不同；**如果你的业务对漏报更敏感（多数情报场景如此），一个无法调整的默认阈值就是一个长期失配。**

**第二层性质：反馈的价值取决于"它接到了哪几个参数上"**。同一份反馈数据（打开 / 采纳 / 纠错 / 屏蔽 / 补报）可以接到三种不同的地方——接到看板上（只看得见）、接到人的判断上（改了但没留痕）、接到规则与阈值上（可复现、可回看）。**只有第三种会让系统一轮一轮变准**，而它的成本是一个常备动作："最近一次阈值调整依据的是哪组数据"。§4.2（9）把回流指标按 `信源 × 标签 × 渠道` 三个维度分组，为的正是让反馈能指到**具体那个可改对象**上——拆不开的反馈（只有一个总分）无法回答"这是频控的问题还是标签的问题"（§6.4 的判据）。

**第三层性质：反馈天然只覆盖误报，不覆盖漏报**。用户会报"这条推错了"，但不会报"这么重要的事你没报"——除非你**给了一个入口**。因此"漏报可测量"这件事在机制上不是统计问题，而是**产品设计问题**：漏报样本必须靠人工标注集或用户补报入口产生，**这是本主题唯一无法自动化的测量**（§4.2（9）把"漏报反馈"单列成一行，并写明"没有它，漏报率永远无法测量"）。

**公开证据**：本主题的配置与指标证据在 §4.2（9）（打开 / 采纳 / 纠错 / 屏蔽 / 漏报反馈五行的口径与用途）与 §4.5 模板 3（分发留痕 SQL，含 `suppressed_reason`）；案例证据在 §6.4（匿名某券商研究所）——三维频控、被挡条数上看板、屏蔽率作先行指标，以及那条方向性错误的失败教训（把"被挡下的条数"当成"漏推"去修）【公开】（来源：本主题 §4.2（9）、§4.5 模板 3、§6.4）。全书他处对"护栏有没有在起作用"有更细的具名讨论，**注意节归属**：Ch9 §06 精准运营把"频控能不能按用户统一裁决"列为**门槛而非权重**，并写下"**没有这个人，运营系统会稳定地滑向过度触达**"（该句在 `09-data-intelligence-product/06-precision-operation/06-precision-operation-section-3-sec3.md` §3，不在该节 §7）；同一章 §7.1 的判据表与候选表给出"按活动算频控 → 总量随活动数线性上升"这条失效模式，§4 给出护栏值守的常备投入形态。**两者是同一条机制的两种场景**（对外情报分发 / 对内运营触达），可以互为旁证，不要互相替代——前者的约束来自"同一事件簇重复推送"，后者的约束来自"多活动叠加"（来源：`09-data-intelligence-product/06-precision-operation/06-precision-operation-section-7-sec7.md` §7.1、`…-section-3-sec3.md` §3、`…-section-4-sec4.md` §4）。

**失效条件**：当用户开始报"这条推错了"或"这么重要的事居然没报"时，如果你的反应是"提工单给厂商"，说明反馈闭环不在你手里——**此时要么补一层自己的过滤与排序（把厂商输出当输入），要么接受一个不由你调的质量曲线**。**另两条边界**：① **反馈量太小时统计不显著**——受众只有十几个人的链路，打开率的波动无法区分"内容变差"与"那天没人看"，此时应当用**可数的事件**（纠错次数、补报次数）而不是比率；② **反馈回流若不覆盖"被挡下的条数"，频控会退化成单向放大器**——因为被挡条数在直觉上长得像"漏推"，它天然会被归进"待修的缺陷"，而不是"在正常工作的护栏"（§6.4 的机制解释）。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
情报链路的账单 ≈ 采集（抓取请求数 × 单价，或自建爬虫的机器与运维）
              + 处理（去重 / 抽取 / 分类的算力，按素材量还是按簇量计，差一个量级）
              + 摘要（摘要调用次数 × 单次成本；只对进入分发候选的簇做）
              + 分发（推送条数 × 渠道单价；短信类远高于邮件 / IM）
              + 人力（信源维护 + 阈值维护 + 抽检：这是唯一不随技术栈变化的一块）
              + 误报处置（误报量 × 单条处置与信任损耗）
```

**这张账单里最容易被写错的一项是"处理"那一行按什么计**：按素材量计与按簇量计，差了归簇收敛的那一档（下面是推导）。**因此架构上"先归簇再摘要"这一步同时是质量决策与成本决策**——它把成本从"转载越多越贵"改成"事件越多越贵"，后者才是与业务量同步的那个量。

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| 自建族 | 人力（信源维护 + 规则与阈值 + 抽检） | 信源结构变化的适配、抽检的长期投入、归簇阈值的重标定 | 随信源数与行业变化频率增长 |
| 产品族 | 许可 / 席位 / 数据量计费 | 口径不贴合导致的额外人工筛选、归并层与回指层的自建 | 随席位数与数据量线性增长 |
| 人机族 | 人的时间（判断与撰写） | 时效瓶颈（人休假即断）、规模上限 | 随覆盖要求与受众数增长 |

**成本函数的三条判据**：① **自建族是"台阶形"**（人力按人年跳），覆盖面广时最省；② **产品族是"线性"**（席位 × 数据量），受众少时最省；③ **人机族是"人的时间线性"**，判断质量最高但**规模不可扩展**。**选型的实质是：先量"信源数 × 受众数 × 误报代价"，再看落在哪条曲线的哪一段。**

**曲线的形状决定什么时候两条线交叉**，这一点比单价重要得多。台阶形方案的成本在一次人年投入的时点上跳一次，随后在一段覆盖区间内几乎水平；线性方案的成本随席位与数据量连续上升。因此**在覆盖面窄、受众少的一端，线性方案的总成本往往低于台阶形；而在覆盖面广、信源多的一端，台阶形方案的总成本低于线性**——两者的交叉点不是一个固定规模，而由"你的信源数与受众数落在哪一档"决定。**这里有一条常被漏算的项**：台阶形方案的"台阶"不只在建设期出现，**它在每次信源结构变化时会出现一次小的台阶**（抓取方式变了、抽取规则要重写、阈值要重标定）；线性方案的隐性成本则出现在"口径不贴合"这一侧（要自己补归并层与回指层）。**两条曲线的隐性成本形状不同，因此"哪家便宜"这个问题在不给定规模区间时无法回答。**

**三条量级推导**（都可以用你自己的参数重算）：

1. **归簇带来的摘要与处理成本收敛**（【推算】）。设日均新增素材 N 条、经三级去重后成簇 M 个、其中进入摘要的 S 个。本主题 §4.6 的算例取 N ≈ 2,000、M ≈ 600、S ≈ 300【经验：取值随行业事件集中度浮动】，得 **摘要量 ÷ 素材量 ≈ 300 ÷ 2,000 = 15%**（推导链：素材量 → 成簇量 → 进入分发候选量；两个折算比例都可替换）。**这个比例决定了什么**：摘要与分类的成本从此按"簇"计而不按"素材"计，**转载越多，这个比例越低、优势越大**——反过来说，如果这个比例接近 1，说明链路里还没有筛选层，涨的是账单而不是覆盖。

2. **扇出与频控挡下的量**（【推算】）。设日成簇 M ≈ 600、每簇平均命中 k ≈ 5 个订阅者，则日投放 ≈ **600 × 5 = 3,000 条**；本主题 §4.6 与 §6.4 给出的档位是"被频控挡下的通常占**两到四成**"【经验：随事件集中度与订阅密度浮动】。**推导链**：日投放量 × 挡下比例 = 省下的推送量，即 3,000 × 0.2 到 3,000 × 0.4 ≈ **600–1,200 条/日**；按天数外推得到年量级的同一比例（推导式为 日投放 × 挡下比例 × 365）。**这个量级决定了什么**：扇出倍数 k 把"簇数"放大成"投放数"，而挡下的那两到四成正是放大后的部分——**所以频控的收益随订阅密度上升而上升，人越多它越值钱**，这与"多推没坏处"的直觉正好相反；同时，**渠道选择本身就是成本决策**（即时渠道与汇总渠道的单位成本不同档）。

3. **抽检人力的下限**（【推算】）。两项常备抽检：同簇质量抽 100 组（§4.2（3）与 §3.2.4 的抽样口径，§6.1 记为单组约 1–2 分钟【经验】）⇒ 约 **1.7–3.3 小时/周**（推导链：100 × 1–2 分钟 ÷ 60；§6.1 按 1.5 分钟中值记为 2–3 小时/周，两者是同一次推算的两种写法）；摘要事实性抽 20 条（§3.2.6 的判据与 §4.1 第 6 步的验收口径，§6.2 记为单条约 5 分钟【经验】）⇒ 约 **1.7 小时/周**（推导链：20 × 5 分钟 ÷ 60）。两项合计约 **每周 3.4–5 小时**（半天到一天的四分之一量级）。**这个量级决定了什么**：链路可以从小规模起步——**真正的门槛不是钱，而是"有没有人在期"**（§3.1 约束 5）。**同时要诚实标注推导的边界**：由条数能推出来的只有这两项，**§7.5 里 0.1–0.5 人年那一档【经验】的上限不来自抽检**，而来自信源复核与阈值维护这两件无法按条数折算的工作；把上限归给抽检会低估它。

**一条经验判据**（【经验】）：多数团队在**信源数十个、受众十几人**这一档上，线性方案（买）与台阶形方案（自建）的总成本差距不大，此时应当按判据选而不是按价格选；进入**信源上百、受众上百**之后，采集与分发的单位成本开始由规模决定，而**抽检与阈值维护这两项人力不随规模摊薄**——于是"自建还是买"的答案会反过来，决定因素是**你有没有把抽检排进常备投入**。这条线是经验线而非定律，能自测的只有一件事：**把信源清单里"上次复核时间"这一列拉出来，数一下最近一个季度新增了几个信源、又复核过几个**——复核数远小于新增数，说明信源维护已经欠账，此时无论选哪一族，成本都会在下一轮信源变化里以"适配返工"的形式补回来（见本节最后一段）。

**还有一项成本落在"信源变了"这一侧：抽取规则的失效**。信源改版、换接口、换栏目之后，挂在旧结构上的抽取规则不会自动失效——它要么开始抽不到内容（覆盖悄悄变小，而信源清单上仍写着"已接入"），要么静默地对着一个不再更新的字段抽取（错误率上升但不报警）。**前者尤其危险，因为它不会触发断供告警**：断供判据只比对每个信源的 `max(ingested_at)`，只要还有零星条目进库就不会告警（§4.2（1）的模板），于是覆盖的缺口要靠"每个信源每周入库条数与它自己的历史基线比"才看得见；后者属于**结构漂移**（正文抽取长度异常下降）【经验：判据要比的是同信源每周入库条数与正文长度跟它自己的历史基线，基线随该信源的发布频率与栏目体量浮动】。**规则库越大，这类欠账越多，而且一次信源改版通常只打掉其中几条**——所以它表现为一次次局部返工，而不是一次可规划的重构。判断方法是随机抽一批抽取规则，逐条问"它上次失效是因为信源变了，还是因为它已经不再被写入了"。

### 7.5 决策树（每个分支都要有阈值依据）

1. **信源是否允许摘要与对外分发？**
   - 不允许对外分发 → 面向客户的产品形态出局；进入第 2 问。
   - 允许 → 进入第 2 问（但分发侧仍需按信源分级做渠道隔离）。
2. **时效要求是天级还是小时 / 分钟级？**
   - 天级 → **人工简报 + 自动化辅助**或**产品族**最省；进入第 4 问。
   - 分钟 / 小时级 → 必须流式 + 兜底轮询 → **自建族或人机族**；进入第 3 问。
3. **误报代价高吗（是否会进入对外决策）？**
   - 高 → 必须有人审闸门 → **自建族（自持口径）或人机族**；且抽检人力按"高风险条数 × 单条时长"预算【经验：高风险量级百条以上应改抽审】。
   - 不高 → **Agent 平台上的情报作业**（复用平台治理，情报语义自建）。
4. **有没有人能每周做抽检与阈值维护（按 0.1–0.5 人年的常备投入量级估算【经验】）？**
   - 有 → **自建族**（判断力可积累）。
   - 没有 → **产品族**，并明确接受"口径由产品定、误报是常数"。

**阈值的诚实说明**：上表的"0.1–0.5 人年"与"百条"都是【经验】档——用来区分"这一档"与"那一档"，请用你自己的量级与排期校准，**不要当门槛用**。

**这棵树分两段：第 1 问定的是"能不能做"，第 2–4 问定的是"在能做的里面怎么选"**。第 1 问是**门槛**（它筛掉的是不可行，不是不划算）；第 2–4 问是**在可行集合里选族与形态**。两段不能互相替代——一个授权只允许内部转发的信源集合，无论第 2–4 问答得多好，都进不了对外渠道；反过来，一个授权完全放开的链路，也不会因为"授权不是问题"就自动变得更便宜。**因此顺序不能颠倒**：先答第 1 问，再答其余。

**每个分支的阈值依据**：

- **第 1 问「授权边界」**：依据是§3.1 约束 1 与它的"过关标志"——**每个信源都能回答"能不能摘要、能不能对外分发"，且这个答案以机器可读的形式存在（不是文档）**。这一条之所以是门槛而不是权重，是因为它的违约形式不是"效果差"而是"不可用"：一次越界分发会让整条链路停下，而收益无法补偿。落到配置上就是 §4.2（1）的 `entitlement.redistribute_*` 三个字段，落到判定上就是"任取一条对外推送，能否回答它包含哪些来源、每个来源的授权是什么"（§6.3 的判据）。
- **第 2 问「时效」**：依据是"从发布到可见允许多久"这个**业务问题**，而不是数据量或技术栈。它的可核查形式是本主题反复用的那一条：把信源的抓取间隔（§4.2（1）的 `interval_min`）与该段的 P95 目标并排——**若 P95 目标小于一个抓取间隔，批处理在原理上就不达标**（§3.2.1 的判定方法）。因此"天级 / 小时级"这条分界不是刻度，而是**"你的节拍器能不能覆盖你的 SLA"**这个可判定问题。
- **第 3 问「误报代价」**：依据是 §3.1 约束 3 与它强调的不对称——**误报的代价是"用户不再看"（随误报率累积），漏报的代价是"错过一次判断"（集中爆发）**。判据不是"误报多不多"，而是"这条情报会不会进入对外决策 / 涉及监管口径 / 涉及重大利益"——即"报错了会不会产生实际损失"。达到这一档才需要闸门，而闸门一旦上，它的适用范围必须收窄到高风险标签与主体名单，否则人力立刻成为瓶颈（第 4 问）。
- **第 4 问「抽检人力」**：依据是 §3.1 约束 5 与它的过关标志——**抽检与阈值维护在排期里"有名字"，不是"谁有空谁看"**。这里给"0.1–0.5 人年"这一档【经验】是为了让"有没有人"这个判断落到可比较的量上；但**可被条数推导出来的只有抽检那部分**（§7.4 第 3 条推导给出每周 3.4–5 小时的量级），**区间上限来自信源复核与阈值维护**这两件无法按条数折算的工作。判断方法是查排期表里有没有这个名字，而不是估算人年。

**为什么这棵树里不设"预算"节点**："预算是否超过某个数"看起来是最务实的一条分叉，但它是一个**结果**，不是**输入**——预算是 §7.4 三条推导的输出（信源数决定采集与维护，归簇收敛率决定处理与摘要，订阅密度决定分发与频控），把它当分叉等于把答案写进了问题里。更实际的后果是：比预算时只看得到许可费（一次性、写在合同上的那个数），看不到信源结构变化时反复发生的适配返工与那两项常备抽检——前者有发票，后者只出现在排期表上。**因此"贵不贵"的正确问法是先估信源数与受众数，再回到 §7.4 的两条曲线上去定位，而不是先问预算多少**【经验】。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 垂直行业、信源多、要自持口径 | 自建端到端链路 | 通用抓取 + 自建摘要 | 全自建首版慢，采集侧可先借外部数据源 |
| 已有成熟检索平台 | Agent 平台上的情报作业（+ 自建去重与回指） | 通用 RAG / 检索平台改造 | **RAG 是问答形态**：缺断供、去重、频控、时效四件，改造量大 |
| 误报代价高、团队小 | 人工简报 + 自动化辅助 | 自建端到端链路 | 人机族的时效受人力限制，但判断质量最高 |
| 时效与定制要求不高 | 商业情报平台 | 产品族 + 自建分发层 | 产品口径通用，垂直判断力难积累 |
| 多客户交付、要求不重复推送 | 自建端到端链路 + 三维频控 | 产品族 + 自建归并与频控层 | 产品的分发单位常是条目，归并需自建 |
| 只要求"我提问时能查到" | 通用 RAG / 检索平台改造 | 商业情报平台 | 无触发式分发时，RAG 形态够用且最省 |

**组合的两条次序原则**：① **先把信源清单与去重立起来，再谈摘要与分发**——前言决定后者的上限；② **先把断供判据写死，再谈个性化**——一个静默失效的链路，个性化只会加速它的死亡。

**矩阵的读法是：先按"授权边界"定可行集合，再按"误报代价 + 抽检人力"定族，最后按"时效 + 受众结构"定形态。** 每行的"不选它的原因"都不是能力不足，而是**机制不落在收益点上**；要看这张矩阵用得对不对，只需认出你的痛点是哪一类——痛在"同一件事被推了三遍"，该补的是 §7.3.2 的分发单位；痛在"信源停了三天没人知道"，该补的是 §7.3.1 的断供判据与 §4.2（1）的 `no_data_alert_after`；痛在"用户开始静音"，该补的是 §7.3.5 的反馈闭环。**这三处不会随同一个产品一起买到**，选型时要把它们当成三件独立的工程，而不是一份功能清单上的三行。

**四个常见组合**（各说明职责边界与运维代价）：

1. **自建采集 + 事件簇去重 + 外部摘要能力**：采集与去重自建（这两件决定覆盖与"用户还愿不愿意看"），摘要调用外部生成能力（这一件可以替换）。职责边界是"归簇之前自持、归簇之后可外采"——因为**分发单位与去重单位必须是同一个**（§7.3.2），把这两件分给两家会立刻产生"谁负责不重复"的悬空。运维代价：归簇阈值与窗口要自己标定与重标定（§4.2（3）），抽检动作不能外包（§7.4 第 3 条推导给出的那两项人力）。
2. **买信源 + 自建判断与分发**：素材从数据提供方按数据集订阅（§7.2 末尾那种形态），去重、分类、摘要、频控、反馈全自建。职责边界是"素材的授权边界由订阅条款决定、判断口径由你决定"。运维代价：**授权边界不在你的配置里**，条款变更不主动通知，因此要把它当成一条外部依赖来观测（订阅清单与条款版本要有人维护）；覆盖面上限由提供方的数据集清单决定，你只能通过漏报样本发现缺口。
3. **Agent 平台上的情报作业 + 自建情报语义**：复用平台的调度、配额、审计与工具出口，自己补去重、回指、频控三件。职责边界是"平台管治理，你管语义"。运维代价：**平台的观测面看不到情报语义的失败**——作业"成功"不等于"没漏报"，因此断供与时效四段的指标仍要在你自己这一侧建（§4.2（8））；另外平台的配额会成为一个新的静默失效点（作业被降级时，错误在平台侧）。
4. **人机分工 + 自动化前置**：人定信源与口径、审高风险，自动化做采集、去重与初稿。职责边界是"判断留给人、机械劳动交出去"。运维代价：**时效的上限由人的在场时间决定**（人休假即断），因此这套组合必须与"高风险闸门的超时默认动作"配套——超时默认不推还是默认推送，取决于误报与漏报哪个更贵，且必须写下来而不是留给实现（§3.2.8）。

四个组合的共同点是**判断与机械劳动分开、门槛与权重分开**：面向所有信源的覆盖走自动化路径（便宜、可扩展），面向高风险事件的判定走人审与可举证的阈值（贵、不可扩展）。反过来设计只有两种下场：**全量人审**把"高风险标签 + 主体名单"这道收窄动作取消掉，闸门队列积压、时效先垮（积压条件 `n > λ/μ`）；**全量自动分发高风险**把监管口径与重大利益的判断交给模型，第一次报错就触发前述那种"链路必须停下"的后果。**这两条路都是把"门槛"降级成了"权重"**，也正是这条链路最常见的两种形态错误。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 问答形态 → 情报形态 | "没人问就不动"；无断供判据 | 补调度、去重、时效监控、分发与频控 | 以月计【经验】 |
| 条目分发 → 事件簇分发 | 同一事件推三遍 | 建归并层、改推送改写与频控口径 | 以月计【经验】 |
| 产品族 → 自建族 | 口径不贴合、误报降不下来 | 重建标签体系、阈值与归并层；**历史判断记录无法迁移** | **以季度计**【经验】，且历史经验不可追溯 |
| 无回指 → 有回指 | 用户反复问"哪来的" | 补片段映射（需回填历史素材的处理） | 以月计【经验】，**历史摘要不可回补** |
| 人机族 → 自建族 | 时效不达标、人一休假就断 | 把人的判断规则化（标签、白名单、阈值） | 以季度计【经验】，规则化本身是最难的部分 |

**一条硬结论**：六条路里最贵的是**"把判断口径交给别人之后的收回"**——它不只是技术搬迁，还包括口径重建与**不可追溯的历史判断**。**所以第 1、3、4 条判据（授权边界、误报代价、口径归属）必须在第一版就判对。**

**四个反模式：它们都在机制层面改变了"成本随什么增长"**

**反模式：把"推送条数 / 覆盖信源数"当成果** —— 症状是这两个数被写进汇报，而"同一事件被推了几次""多少条摘要能被点开验证"没人统计 → 后果是链路稳定地朝"多推"优化，因为那是唯一有数、有反馈的方向；机制上，**在素材分发单位下，推送条数会随转载量自然上升，而不随判断增量上升**——也就是说，这个指标衡量的恰好是最不该被最大化的那个量（§7.3.2 的两种单位差别就落在这里） → 正确做法是把分母换成事件簇：统计"同一事件簇的推送次数"与摘要的"可验证率"（§6.7 把它单列为**准入性**收益项），并保留"被频控挡下的条数"这一条正面指标。

**反模式：先做漂亮的摘要，后补去重与回指** —— 症状是首版把力气全押在摘要模板与提示上 → 后果是摘要质量的提升被重复推送与不可验证**同时抵消**（§6.5 与 §4.1 的顺序反面）；机制上，去重与回指是摘要的**前置条件而不是并列项**：没有归簇，同一件事会被摘要多次且口径不一致；没有片段映射，摘要里的数字无处回查。而这两件恰好**收益不可见、成本立刻发生**，因此在排期机制下必然被排到最后——这不是判断失误，是排期结构的自然结果 → 正确做法是把"同一事件簇的推送次数"做成一个天天有人在看的数，让"没有发生的重复"第一次有观测面（§6.1 的机制解释）。

**反模式：把"被频控挡下的条数"当漏推去修** —— 症状是看板上出现一个下降的数字，团队的第一反应是"我们漏推了" → 后果是频控被逐步放宽，链路退回骚扰形态，而退订是**不可逆**的损失；机制上，这个指标在直觉上长得像坏消息，于是天然被归进"待修的缺陷"而不是"在正常工作的护栏"——**一个从没挡下过任何东西的护栏，和没有护栏是一回事**（§6.4 的机制解释，其出处见 `09-data-intelligence-product/06-precision-operation/06-precision-operation-section-3-sec3.md` §3） → 正确做法是把它归进正面指标，并要求挡下的条目能回答"被哪条规则、在哪个时间窗上挡住"（§4.5 模板 3 的 `suppressed_reason`）。

**反模式：把"能抓到"当成"能分发"** —— 症状是授权边界写在文档或制度里、不在配置里 → 后果是这条边界在下一次新应用接入时被绕过，而这类越界的代价不是效果变差，是**链路必须停下**；机制上，**只写在文档里的约束没有执行点**——它依赖每个接入方都记得，而"记得"不是机制 → 正确做法是把它做成分发侧的强制判定：对外渠道只允许 `redistribute_external: true` 的信源，簇里若含不可对外分发的来源则剔除该来源而保留其余来源（§4.2（1）与 §6.3 的判据）。

把这四个反模式并排看，会发现它们各自替换掉了一个量：推送条数替换了"同一事件簇的推送次数"，摘要观感替换了可验证率，被挡条数替换了护栏有效性，文档替换了配置里的 `entitlement.*`。**替换的共同后果，是 §7.4 表里"成本随什么增长"那一列没有换项**——账单依然随素材数与信源数走，而不是随事件数走。所以评估一份情报链路建设方案时，不看它列了多少能力，而是回到 §7.4 的表里指一行：你新增的机制，把哪一行的"成本随什么增长"改掉了。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 信源不能对外分发 | 只进内部渠道；产品形态出局 | 授权边界是否决项，不是权重——它筛的是可行集合（§7.3.2 失效条件①） |
| 没人问也要报 | 必须补调度 + 断供检测 + 去重 + 频控四件 | 人驱动的形态没有"持续运行且可被发现失效"的机制，会静默失效 |
| 同一事件多来源、且高频 | 分发单位改成事件簇 | 判断型去重每次都要重新决定，结构型去重让重复在机制上不可能发生 |
| 归簇阈值拿不准 | 偏向"宁可不合"，同时看两个方向 | 误合并的代价是漏报、重复的代价是用户烦——两者不同阶 |
| 摘要要进入决策 | 片段级回指 + 数值机械化回查 | 验证成本从"读者搜原文"降到"点开一次"；数字偏差读者察觉不到 |
| 摘要只用于扫一眼 | 回指到篇可以接受 | 没有决策依赖时，可验证性不构成准入条件 |
| 摘要模型端点会故障 | 预写降级目标：抽取结果 + 原文链接 | 故障期人更依赖系统结论，无出处的摘要杀伤力更大（降功能不降可信） |
| 误报会进入对外决策 | 人审闸门 + 超时默认动作写死 | 高风险全自动 = 把责任交给模型；超时不定义则取舍变成偶然 |
| 用户开始退订 / 静音 | 先查频控与误报，不要先加内容 | 屏蔽是不可逆的先行信号，用户先于系统指标发现超量 |
| 被挡条数上看板后被质疑 | 说明它是护栏在工作，不是漏推 | 一个从没挡下过任何东西的护栏与没有护栏等价 |
| 抽检没人做 | 要么把名字排进期，要么接受默认口径 | 口径留在手里但无人调，与口径在厂商手里没有区别 |
| 只能买平台 | 补一层自己的过滤与排序，并明确接受默认阈值 | 反馈闭环不在你手里时，阈值无法调到你的误报—漏报偏好 |
| 存量是人工简报 | 影子对比 2–4 周【经验】，产出"人工报了而系统没报"清单 | 这份清单是后续调优唯一的靶子，也是迁移最有价值的产物 |
| 想要一个"行业情报"的现成产品名 | 本节不给 | 全书与本主题都没有可核验的产品文档出处；判定入口见 §7.2 末尾 |

> 本节小结：六个候选之间的差异，最终都能归到三问——**触发方式是"外部变化"还是"人的提问"**、**分发单位是素材 / 事件簇 / 人订阅的流**、**判断口径（标签与阈值）在谁手里**。三问决定了它们的成本曲线形状（自建台阶、产品线性、人机按人的时间线性）与迁移代价（跨族迁移以季度计，同族以月计）。**选型顺序不可颠倒**：先用授权边界与误报代价筛掉不可行，再用口径归属与抽检人力在剩下的里选——**把"有没有人做抽检"当权重而不是门槛，是这条链路最常见的死因**。
>
> 还有一条把这六个候选串起来的暗线：**它们对"单位"的处理方式不同**。自建族可以自己把单位定成事件簇，产品族的单位通常由对方定成条目，人机族的单位由人临时决定。**而"单位"这个选择同时决定了三件事——重复能不能被结构性消除、成本随什么增长、迁移时要不要重建历史**；正因为它是同一个决定的三个面，本节把它拆成 §7.3.2 的机制、§7.4 的账单、§7.7 的迁移代价三处来讲，而不是三个可以自由组合的选择。**其余维度（模型能力、功能清单、评分高低）都是这一条选择的下游后果。**

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次"门槛检查"（不是打分）：授权边界、时效预算、误报与漏报代价、判断口径归属、抽检人力、受众结构——哪一条是"不满足"而不是"分数低"？那一条就是你明年最可能被迫迁移的方向；而你今天的补救，是否还落在"同族迁移（以月计）"这一格里？
