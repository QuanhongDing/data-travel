## 6. 落地实践

> **本节的材料纪律（先说清楚）**：情报链路的公开材料以**产品介绍、工程博客与行业实践综述**为主，来源清单、误报率、摘要正确性这类数据极少公开。因此本节 4 例的构成是：
>
> - **§6.1–§6.3** 是**产品文档层面的机制复述**（分发单位怎么定义、可信度由什么承担、权限在链路的哪一步裁剪），**不是对任何一家公司内部实现的转述**；方括号内是**来源类型 + 年份**，属**建设方自述**，不构成本书 §5 判据里要求的「第三方（非厂商）公开生产案例」，读者需按其官方材料自行核验。
> - **§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证。
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 Palantir"**把情报装进「对象 + 关系」而不是「文档流」：去重与分发共用同一个单位 5+ 年**"（2019-2024）

**背景（Why）**

情报链路最容易被低估的一步不是抓取，也不是摘要，而是**"一条情报"到底以什么为单位存在**：

- **素材不是情报**——同一件事有多篇报道、多个角度、多次更新，把素材当成分发单位，就必然重复；
- **重复会摧毁信任**——用户对"同一件事推三遍"的容忍度极低，而这类重复在转载普遍的行业里是常态；
- **去重与分发如果不是同一个单位，就会打架**——去重按文本相似度做，分发按素材做，那么"相似但不同"的素材仍会被各推一次。

**触发点（What）**

Palantir 一类分析平台的做法是把数据组织成**对象与关系**（实体、属性、关系类型），而不是以文档为原子单位（[Palantir 公开材料 2019-2024]，核验入口是其官方产品文档，**按当前版本核**）。它对情报链路的启示不在"分析能力"，而在**单位的选择**：

- **对象是"世界里的东西"**（一家公司、一次处罚、一笔交易），**文档是"关于它的观察"**；
- **当单位是对象时，"同一件事"有一个天然的同一性判据**（对象标识 + 关系），而不是靠"文本像不像"；
- **分发单位与去重单位因此自动统一**——这正是 §3.2.4 想解决的问题。

**详细做法（How）**

**① 分发单位从"素材"改成"事件簇"，且簇有身份**

- **关键设计**：一个**事件簇** = 一个主体 + 一个动作 + 一个时间窗；同簇的每篇报道是**关于这个簇的观察**，而不是独立的条目。
- **关键性质**：**"同一件事推几遍"这个问题在结构上消失了**——不是靠每次都判重，而是靠"簇只有一个分发入口"。这正是 §3.2.4 说的"用结构而不是用判断消除一类缺陷"。
- **关键示意**：

  ```text
  两种单位带来的两种世界（决定重复能不能被结构性消除）
    ── 单位 = 文档（素材流）────────────────────────────
       文档A → 推
       文档B → 推      ← 同一件事的第二篇报道
       文档C → 推      ← 转载改写
       结果：靠"每次判重"去拦，判一次错就重复一次
    ── 单位 = 事件簇（对象 + 观察集）──────────────────
       簇X = (主体=某公司, 动作=被监管处罚, 时间窗=2024-06-01..05)
             ├─ 观察1（官方公告）  ← 来源等级 A
             ├─ 观察2（媒体转载）  ← 来源等级 C
             └─ 观察3（行业评论）  ← 来源等级 C
       分发的是"簇X"一次；多观察作为可信度信号呈现
       结果：重复在结构上不可能发生
    ────────────────────────────────────────────────
   判据：分发的键是"簇标识"还是"素材标识"？
        答"素材"就意味着重复只能靠每次判断去拦
  ```

**② 同簇多来源是可信度信号，不是冗余**

- **关键设计**：不要把同簇的多篇合并成一条（那会丢掉"几家都在报道"这个信号），而是**保留观察集并标注来源等级**。
- **为什么**：**去重的目标是"少推"，不是"少存"**——把多来源压成一句摘要，会让用户失去"这件事被几家独立确认"的判断依据；而这恰好是情报里最重要的一个信号。

**具体数字（档位标注）**

- 归簇带来的分发收敛：设日新增素材数百条，经三级去重后成簇百余个，**进入摘要与分发的通常是素材量的百分之十几到三成**【经验：随事件的集中度浮动】——**这就是"先归簇再处理"的直接收益**，且它同时降低了摘要成本（对簇摘要一次，而不是对每篇素材摘要一次）。
- 误合并的代价不对称：误合并的代价是**漏报**（两条不同事件被合成一条），重复的代价是**用户烦**。因此阈值应偏向"宁可不合"，并用 **"拆分准确率"** 与 "同簇准确率" 一起评估【经验：只报同簇准确率会系统性高估质量】。
- **自测动作**：找一次同一事件的多篇报道，看它被分发了几次；再抽样 100 组被判为同簇的素材，人工核对**两个方向**的准确率。

**失败教训**

**第一版把去重当成"优化项"**——先上线全量推送，再补去重。结果是"补完之前，用户已经不看"。教训：**去重不是优化，是分发的前提**；同一件事推第二遍，是在消耗这条链路唯一的资产（用户的注意力）。

### 6.2 路透社"**新闻作为带来源与时间戳的事件流：可信度由「来源链」承担，不由「文风」承担 10+ 年**"（2014-2024）

**背景（Why）**

情报摘要最容易走错的方向是**把"好读"当成质量目标**：

- **"好读"与"可信"是两个方向的优化**——流畅的改写会抹掉限定词（"据称""尚未确认"），而限定词恰恰是可信度的载体；
- **读者无法自行验证**——一条没有出处的摘要，用户要么信、要么自己去搜原文，后者的成本高到没人做；
- **在决策场景里，不可验证的摘要是负资产**——它比"没有摘要"更危险，因为它看起来像结论。

**触发点（What）**

新闻通讯社的生产方式提供了一个成熟的参照：**一条新闻从产生起就带着来源与时间**（发布机构、发布时间、地点、以及"这一条是对哪一条的更新/更正"），下游可以据此判断"它是原始报道还是转述、是否被更正过"（[路透社公开材料 2014-2024]，核验入口是其新闻产品与供稿规范文档，**按当前版本核**）。这个形态的启示是：

- **provenance（来源链）是产品的组成部分，不是元数据**——它决定了这条信息能被怎么用；
- **更正与更新是显式事件**——不是"悄悄改掉"，而是"发布一条更正"。

**详细做法（How）**

**① 摘要按"事实点 + 出处片段"生成（不是按段落）**

- **关键设计**：摘要里的每个**事实点**（数值、日期、主体、动作）都要指回原文的**片段**，而不是"整篇原文"。
- **为什么必须到片段**：指向整篇时，用户的验证成本仍然很高（要在长文里找）；**只有指到片段，验证才是一次点击**——§3.2.6 说"引用回指只指到整篇等于没有回指"，说的就是这件事。
- **关键性质**：**它把"信不信"从一个主观判断变成一次可点开的动作**。这条转换的价值与模型质量无关——**即使模型完全准确，没有回指的摘要也无法被组织采用**，因为它无法被审计。

**② 数值 / 日期 / 主体做机械化回查，且回查前先规范化**

- **关键设计**：回查不通过的数字**不写进摘要**（不是"标个置信度"）。
- **为什么是"不写"而不是"标注"**：数字是会被直接拿去用的，**标注的置信度在流转中会丢失**（被复制进 PPT 时没人带上"这个数未经验证"）；而"不写"是不可绕过的。
- **规范化的必要性**：情报里的数值经常经过**单位换算**（亿元 → 万元）、**口径改写**（同比 → 环比）与**指代替换**（"该公司" → 具体名称），因此回查必须先在规范化后的文本上比对，否则只能做"原文里有没有这个字符串"的弱回查。

**③ 更正与更新显式化**

- **关键设计**：一条已经分发的信息被更正时，**发一条"更正"而不是静默修改**；簇新增重要来源时，**标"更新"再推一次**（§6.4 的簇生长规则）。
- **为什么**：静默修改会让"已经据此做过判断的人"无法察觉自己用的是旧版；这在决策场景里等同于制造了一个不可见的错误。

**具体数字（档位标注）**

- 抽检负荷（必须投入的那一项）：**每周抽 20 条摘要，逐条核对数值 / 日期 / 主体**，单条约 5 分钟 ⇒ 约 **1.7 小时/周**【推算：20 × 5 分钟 ÷ 60】。**这个数字的意义是：可信度有一个人力下限，低于它就只能靠运气。**
- 时效分解：`采集 ≤ 5 分钟 + 处理 ≤ 5 分钟 + 摘要 ≤ 3 分钟 + 分发 ≤ 2 分钟 ≈ 15 分钟`量级【经验：各段目标随信源接口与模型档位浮动】，**四段分开测**才能定位"为什么晚了"——把四段合成一个"端到端 15 分钟"，出问题时无法归因。
- **自测动作**：抽 20 条摘要，逐条核对数值 / 日期 / 主体；再问一个问题——**"最近一次更正，用户是怎么知道的？"** 答不出，说明更正还没有显式化。

**失败教训**

**把摘要做成"通顺优先"**——第一版提示只要求"简洁流畅"，没有要求引用。一次误报（模型把"某公司的关联公司被处罚"写成"该公司被处罚"）被市场部直接用于对外口径修改，事后追查发现摘要根本没有出处。教训：**情报摘要的第一要求是"可验证"，不是"好读"**；好读但不指出处的摘要，在决策场景里是负资产。

### 6.3 Glean"**权限前置 + 片段级引用：把验证成本从「读者搜原文」降到「点开看」3+ 年**"（2021-2024）

**背景（Why）**

企业里的"情报"大量藏在内部系统（文档、工单、代码、邮件），而这带来一个合成场景特有的约束：

- **同一份索引服务所有人**——但每个人的可见范围不同；如果检索在权限之前发生，**召回结果的条数本身就会泄漏"存在哪些你看不到的东西"**；
- **内部材料不可外发**——授权边界（§3.1 约束 1）决定它能进哪个渠道；
- **答案必须能回指**——企业用户对"助手说的"信任度低，需要能点开看原文。

**触发点（What）**

Glean 一类企业检索 / 助手产品把**权限判定放在检索之前**（可见域在召回阶段就被裁剪，而不是在返回之后过滤），并提供到来源的引用（[Glean 公开材料 2021-2024]，核验入口是其官方产品文档，**按当前版本核**）。它的启示有两层：

- **"先召回再过滤"与"先裁剪再召回"不是性能差异，是安全差异**——后者才保证"不可见的东西不进入你的上下文"；
- **引用回指的粒度是产品级要求**，不是附加功能。

**详细做法（How）**

**① 权限前置：可见域在召回前裁剪**

- **关键设计**：把"谁能看什么"作为**检索的输入条件**（过滤下推到索引 / 向量检索阶段），而不是返回后筛。
- **为什么必须前置**：因为**返回后过滤已经把内容读出来了**——它进了进程内存、可能进了日志、可能进了模型上下文。**在"数据出域"这类合规判定上，'读出来再删掉'与'不读出来'不是同一件事**（同 [Ch4 §05 RAG](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md) 与 [Ch8](../../08-ai-governance/README.md) 的要求）。另一层收益是**条数不泄漏**：后过滤会让"召回 50 条、返回 3 条"这个差异暴露"存在 47 条你看不到的东西"。

**② 引用回指指到片段，且带抓取时间**

- **关键设计**：引用不只是"哪篇文档"，而是"哪个片段 + 什么时候抓的"。
- **为什么需要抓取时间**：内部材料会变；**没有抓取时间的引用，在材料被修改后就无法回答"我当时看到的是哪一版"**——这让引用在争议场景里失效。这一点与 §6.2 的"更正显式化"是同一条理的两面。

**③ 授权边界决定渠道（不是决定要不要抓）**

- **关键设计**：把"能不能对外分发"写成信源的属性，分发时按渠道类型过滤——**不能对外分发的信源只能进内部参考渠道**。
- **为什么**：授权边界是**采集前就该知道的**（它决定你能拿它做什么），而不是分发时才判的；把它写成信源属性，可以让"某个渠道里不该出现的来源"在配置层面就不可能发生。

**具体数字（档位标注）**

- 前置与后过滤的差异量级：后过滤的"白召回"比例取决于权限分布，**在权限差异大的组织里可以到多数**（召回 50 条、可见 10 条）【经验：随组织的信息隔离强度浮动】——**这个比例就是"读出来又删掉"的那部分开销与暴露面**。
- 抽检口径同 §6.2：**每周 20 条**逐条核对引用可点开、且指向的片段确实支持该事实点【经验】。
- **自测动作**：取一条摘要的引用，点开看它落在哪——**是整篇文档、还是具体片段**？再问"这份材料上周改过吗，引用能说明我看到的是哪一版吗"。

**失败教训**

**第一版把权限做在返回之后**——技术上"拿到了正确的结果"（用户看到的确实是他有权看的），但**召回阶段已经把无权内容读进了内存与模型上下文**，一次日志打印就会把它带出去；同时"召回 50 条返回 3 条"的差异还向用户暗示了看不见的内容的存在。教训：**权限的落点决定它是"安全"还是"看起来安全"**——前置是安全，后置是看起来安全。

### 6.4 某券商研究所"**频控与渠道编排：把推送预算当稀缺资源管理 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

研究所同时服务内部（投研、销售）与外部客户，多角色、多订阅、多渠道。情报系统上线后，团队最初的想法是**"推得越多，用户越觉得值"**。

**触发点（What）**

一次客户投诉——同一并购事件被推了三遍（因为**簇在生长**：每新增一个来源就推一次），客户认为"系统不专业"，并要求给出频控说明。同期内部出现另一种反馈：分析师把该渠道静音了。

**详细做法（How）**

**① 簇生长规则：不重推，只更新**

- **关键设计**：簇新增来源时**默认不重推**，只更新"多来源列表"；只有满足"重要度显著上升"（例如新增来源是官方口径）才补推一次，且**标题标明"更新"**。
- **为什么这样切**：它区分了两种"新"——**信息量的新**（多了一个转载）与**判断依据的新**（官方口径出现、金额量级变化）。前者不该触发推送，后者该。**判据可写死**：来源等级提升、或某个事实点发生了实质改变。

**② 三维频控 + 被挡留痕**

- **关键设计**：`事件簇 × 人 × 时间窗` 三个维度分别设限，外加"每人每日上限"与"群组上限"；**被挡下的条数留痕并上看板**。
- **为什么三个维度都要**：按人限防个体过载、按群组限防一个团队被同一件事刷屏、按事件簇限防多来源重复——**三者缺一，另外两个都会被绕过**（只按人限，则同一件事仍会通过不同的人扩散成团队噪声）。
- **"被挡留痕"的机制价值**：**被挡下的数量是系统在自我约束的证据**——它同时是给客户的说明材料（"本周系统挡下了 N 条"）与内部调参的依据。**把它当成"漏推"去修，是本主题最常见的方向性错误。**

**③ 渠道分级与反馈回流**

- **关键设计**：即时渠道只推 P0，其余进日报 / 周报；反馈按 `客户 × 标签 × 渠道` 统计打开 / 采纳 / 纠错 / 屏蔽；**屏蔽率上升即视为先行告警**（通常先查频控）。
- **为什么把屏蔽率当先行指标**：屏蔽是**用户在系统出问题之前给的信号**，而打开率是滞后指标——**只看打开率的系统会优化成"推用户爱看的"**（§3.5 的反模式），偏离情报目标。

**具体数字（档位标注）**

- 分发量级：设 `600` 簇/日、平均命中 `5` 个订阅者 → `3,000` 条投放；被频控挡下的通常占**两到四成**【经验：随事件集中度与订阅密度浮动】。
- 成本结构：采集是"请求数 × 单价"（数千次/日量级）、摘要只对进入分发的簇（**素材量的百分之十几**）、分发按渠道计费（短信类成本远高于邮件 / IM）——**渠道选择本身就是成本决策**。**一条容易被漏算的**：**第三方渠道的投递失败是静默的**（邮件进垃圾箱、IM 被折叠），因此"推送成功"与"送达"必须分开统计，否则频控的输入数据是错的。
- **自测动作**：把某人一天的实收条数数列出来；再问"我们的频控规则写在哪、被挡了多少条、这些数字每周有人看吗"。

**失败教训**

**认为"多推没坏处"**——产品侧最初的想法是"推得越多，客户越觉得值"。事实相反：**重复与噪声会直接侵蚀续费**。教训：**推送预算是稀缺资源**；"被频控挡下的条数"应当出现在运营看板上，而不是被当成"漏推"去修。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条顺序固定的路径，与 §4.8 对应：

1. **先清单化信源 + 定时效预算**（§6.1 的前半）——没有这两个，后面所有优化都无靶点；信源清单里必须写清授权边界与断供判据。
2. **再做事件簇去重**（§6.1）——它是"用户还愿意看"的前提，必须在分发之前；**分发单位与去重单位必须是同一个**。
3. **然后上引用回指与事实性回查**（§6.2、§6.3）——把摘要从"好读"变成"可验证"；引用要到片段，权限要到召回之前。
4. **最后做频控、渠道分级与反馈回流**（§6.4）——让系统在规模化后仍不变成骚扰源，并把"被挡下的条数"做成正面指标。

**顺序的反面**：先做"更漂亮的摘要"、后补去重与回指——摘要质量的提升会被重复推送与不可验证**同时抵消**。**另一条反面**：先做分发渠道的扩张（"全渠道触达"）、后做频控——渠道越多，叠加起来的超量越难察觉（§3.4 的误配"频控只做在渠道侧"）。

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 去重当优化项 | 同一事件推三遍 | 用户不再看 | 事件簇前置于分发 |
| 分发单位是素材而非簇 | 转载各推一次 | 重复只能靠每次判断去拦 | 分发键改成簇标识（§6.1） |
| 把同簇多来源合并成一条 | 失去"几家独立确认"的信号 | 可信度判断依据丢失 | 保留观察集并标来源等级 |
| 阈值偏向"合" | 两条不同事件被合成一条 | 漏报（比重复更危险） | 偏向"宁可不合" + 双方向抽检 |
| 无断供判据 | 某信源静默失效半年 | 覆盖悄悄变小 | 每信源写死 `no_data_alert_after` |
| 只依赖推送 | 通道中断时系统"正常" | 静默断供 | 兜底轮询 + 心跳（§3.2.2） |
| 摘要无回指 | 无法回答"哪来的" | 信任崩塌、决策失真 | 引用指到片段 + 数值回查 |
| 回查不做规范化 | 单位 / 口径改写被误判为"原文没有" | 弱回查形同虚设 | 回查前先规范化（§6.2） |
| 不通过的数字"标注置信度" | 流转中置信度丢失 | 未验证数字被直接使用 | 不通过就不写（§6.2） |
| 更正静默 | 已据此决策的人无从得知 | 制造不可见的错误 | 更正与更新显式化 |
| 权限做在返回之后 | 无权内容已进内存与上下文 | "看起来安全" | 权限前置于召回（§6.3） |
| 引用无抓取时间 | 材料改了之后无法回答"我看的是哪版" | 引用在争议场景失效 | 引用带抓取时间 |
| 关键词规则过宽 | 同名不同公司误报 | 模型也拦不住 | 主体白名单 + 规则归因 |
| 无频控 / 只看打开率 | 用户退订、系统推"爱看的" | 渠道失效、偏离目标 | 三维频控 + 屏蔽率作先行指标 |
| 把"被挡条数"当漏推修 | 频控被逐步放宽 | 退回到骚扰 | 被挡条数上看板，作为正面指标 |
| 只统计推送成功 | 频控的输入数据是错的 | 以为推了 10 条实际送达 3 条 | 送达率与推送成功率分开 |
| 降级成"无出处摘要" | 故障期间错误率飙升 | 最危险的一类降级 | 降功能不降可信 |
| 按任务记采集结果 | 任务成功但某信源整月无数据 | 部分失败被成功状态掩盖 | 采集结果按信源记录 |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——情报链路的收益里有一项是"没有发生的坏事"，它无法折算成百分比。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 人工覆盖 | 分析师每天手工看信源的时间 | 从**小时级/人日**降到**分钟级的抽检**【经验】 | 记录一周内"手工翻信源"的实际耗时 |
| 时效 | 从发布到可见的 P95（四段分开） | 人工简报是**小时到一天级**；自动化链路按 SLA 设计（四段之和） | 抽 20 条测四段延迟 |
| 重复推送 | 同一事件簇的推送次数 | 从**多次**降到**1 次（+ 更新）** | 找一次多来源事件，数推送条数 |
| 误报下降 | 误报数 / 推送数（按标签分组） | 靠主体白名单 + 规则归因**从机制上**下降（幅度取决于原规则的宽度） | 取最近 50 条推送，人工判误报并归因 |
| 分发成本 | 推送条数 × 渠道单价 | 频控挡下的条数（**两到四成**）即省下的量 | 统计被挡条数与渠道分布 |
| 可验证率 | 摘要里能点开验证到片段的事实点占比 | 从"无法验证"到"可点开"——**这项决定摘要能否进入决策流程** | 抽 20 条摘要，数可点开的事实点比例 |
| 抽检人力 | 每周抽检条数 × 单条核对时长 | 20 条/周 × 约 5 分钟 ≈ **1.7 小时/周**【推算：20 × 5 分钟】 | 实际做一次并记录耗时 |

**读法**：前三项是**效率与时效收益**，第四、五项是**质量与成本收益**，第六项是**准入性收益**（可验证率不合格时，摘要根本无法进入决策流程），最后一项是**必须投入的代价**。情报链路与其它系统最大的不同是：**它的收益里有一项是"没有发生的坏事"（漏报被拦住）**——这项无法直接折算成金额，但它是这条链路存在的全部理由。**另一条读法**：最后一项（抽检人力）不该被优化掉——它是这条链路可信度的下限，**砍掉它省下的是 1.7 小时/周，付出的是一条不可信的链路**。

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**信源清单与时效预算决定有没有靶点**，**事件簇决定用户是否还愿意看**，**引用回指与权限前置决定摘要能不能被信任与使用**，**频控与反馈决定规模化后是否还成立**。四次失败教训指向同一件事：**情报系统的失败几乎都不是"模型不够好"，而是"链路里少了一道闸门"**——少去重就重复、少回指就不可信、少频控就变骚扰、少断供判据就静默死亡、少权限前置就"看起来安全"。

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你最像的案例，只做一件最小的事——按它列出的"判据"跑一次自测（关一个信源看多久被发现 / 数一次重复推送 / 抽查一条摘要能否点开到片段 / 数一次某人一天的实收条数）。哪一件**今天就能做**就先做它：能被立刻验证的缺口，优先级永远高于推断出来的缺口。
