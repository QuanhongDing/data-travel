## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

情报链路的形态由**五条约束**决定，顺序不能颠倒：

1. **信源的可获取性与授权边界**：能抓还是只能买？抓到之后**能不能摘要、能不能对外分发**？（授权边界直接决定分发形态——不能分发的信源只能进"内部参考"渠道。）
2. **时效要求**：从发布到可见允许多久？分钟级（行情、监管突发）还是天级（研报、周报）？**这一条决定采集是流式还是批处理**。
3. **判断风险**：误报的代价有多大？漏报的代价有多大？（决定分类阈值、是否需要人审、是否需要"高风险必须引用回指"。）
4. **受众结构**：给一个人看，还是给多个角色 / 客户看？（决定分发是"集中一份简报"还是"按订阅扇出"。）
5. **人力**：有没有人能每天做抽检与阈值维护？（**没有这个人，情报系统会在三个月内退化成"噪声源"**——这是本主题最现实的约束。）

> **判据的用法**：先用 1 决定"哪些信源进哪个渠道"；用 2 决定采集架构；用 3 决定闸门密度；用 4 决定分发架构；用 5 决定**自动化到什么程度**。跳过第 5 条最常见的后果：全自动上线、无人抽检，三个月后用户把它屏蔽。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 定时批处理（拉模式）

**被什么约束逼出来**：信源只提供页面 / 文件（无推送接口），且时效要求是天级。

**结构**：按调度周期抓取 → 落原始素材 → 增量处理 → 生成简报（例如每日一次）。

**为什么有效**：实现最简单、对信源压力最小、成本可预测（每天一轮）。

**代价**：时效上限 = 抓取间隔（**判据**：如果 SLA 要求 30 分钟内可见，而抓取间隔是小时级，这个模式在原理上达不到目标）。另：**单点失败会整轮缺失**（这一轮全没抓到），需要"失败重跑这一段窗口"的能力。

**失效点**：突发事件的时效要求超出批处理能力时，用户会转向其他渠道——**此时不是优化批处理，而是给高价值信源加一条流式通道（模式 3.2.3）**。

#### 3.2.2 事件驱动流式（推模式 / Webhook / 订阅接口）

**被什么约束逼出来**：信源提供推送或订阅接口，且时效要求在分钟级。

**结构**：信源主动推送 → 入队 → 实时处理（去重 / 抽取 / 分类 / 摘要）→ 分发。

**为什么有效**：时效最短；无需轮询（对信源友好，也不容易触发反爬）。

**代价**：① **必须处理"乱序与重复投递"**（推送通常是"至少一次"）；② 需要队列与背压（突发事件爆发时流量是脉冲，例如某公司一次性发布 20 条公告）；③ 端点自身成为依赖（推送中断就是断供，需要**心跳 / 兜底轮询**）。

**失效点**：只依赖推送而没有兜底轮询——推送通道静默中断时，**系统会安静地什么都不做**（这正是情报系统最危险的失败形态）。

#### 3.2.3 混合：重要信源流式 + 长尾批处理

**被什么约束逼出来**：约束 2 分化明显——少数信源要求分钟级，几十个长尾信源天级即可；同时约束 5（人力）要求成本可控。

**结构**：**分级信源清单**——A 级（少数、高价值、高频）走流式；B 级（多数）走批处理；C 级（试探性信源）低频抓取并观察质量。

**为什么有效**：把抓取预算花在**真正影响判断的信源**上；长尾用低成本覆盖。

**代价**：分级标准必须写下来并可复核（"为什么这个信源是 A 级"）；分级评审要定期做（信源价值会漂移）。

**判据**：**任一信源属于哪一级，能否从配置里读出来，并说明它上一次被复核的时间。**

#### 3.2.4 三级去重 + 事件簇

**被什么约束逼出来**：同一事件有多个来源，且转载 / 改写普遍（约束：重复推送会摧毁信任）。

**结构**：① **同源重复**（指纹完全相同）→ 丢弃；② **跨源相似**（向量相似度 ≥ 阈值且时间窗口内）→ 归入同一**事件簇**；③ **人工确认的相关事件** → 关联（不是重复）。

**为什么有效**：分发的单位从"素材"变成"事件簇"，**从机制上消灭"同一件事推三遍"**。

**代价**：阈值与时间窗口要按事件类型分别标定（并购 vs 行情差异极大）；**误合并**会把两条不同的事件合成一条（这会直接造成漏报，比重复更危险）。

**判据**：抽样 100 组"被判为同簇"的素材人工核对——**同簇准确率与拆分准确率（不该合的别合）两个都要看**。

**失效点**：只按文本相似度去重，忽略"同一事件的不同角度报道"——正确形态是"同簇但呈现多来源"，而不是"合并成一条"（多来源本身就是可信度信号）。

#### 3.2.5 规则 + 模型混合分类

**被什么约束逼出来**：纯规则对同义 / 同词不同义无解；纯模型无法满足"必须命中的硬信号"（如监管文号、公司代码）。

**结构**：**规则层**负责硬信号（文号、代码、关键词组合，必须可解释）；**模型层**负责语义归类（标签体系内的多标签分类）；两者结果合并，冲突时按事先规则处理（例如"硬信号优先"）。

**为什么有效**：硬信号的召回与可解释性由规则保证；语义覆盖由模型补齐。

**代价**：两套逻辑要维护；**标签体系**必须有 Owner 与增删流程（否则标签会膨胀到无法量误报）。

**判据**：任一被推送的情报，能否回答"它命中了哪条规则、模型给了哪一档置信度"；以及**误报能否归因到"规则过宽"或"模型阈值过低"**。

**失效点**：只优化模型阈值而不管规则——规则过宽造成的误报（例如关键词命中了同名不同公司）会一直存在，且模型再准也拦不住。

#### 3.2.6 带引用回指的摘要 + 事实性校验

**被什么约束逼出来**：LLM 摘要会编，而情报里的假事实代价极高（约束 3）。

**结构**：摘要按"事实点 + 出处"生成（每个事实点指回原文句子 / 段落）；**数值、日期、主体做机械化回查**（是否出现在原文、是否被改写）；**回查不通过的数字不写进摘要**。

**为什么有效**：把"信不信"从主观判断变成**可点开验证的动作**；机械化回查能拦住最危险的一类错误（数字幻觉）。

**代价**：生成时要保留片段映射（存储与处理成本上升）；回查规则要按领域维护（单位换算、同比 / 环比表述）。

**判据**：**每周抽 20 条摘要，逐条核对数值 / 日期 / 主体**；抽检发现的错误要能定位到"哪类提示 / 哪类信源"。

**失效点**：引用回指只指到"整篇原文"而不是具体片段——用户仍要自己找，**等于没有回指**。

#### 3.2.7 频控与渠道编排

**被什么约束逼出来**：个性化推送会自然演化为骚扰（约束 4）。

**结构**：三维频控（人 / 群组 / 事件簇 × 时间窗）＋渠道分级（即时渠道只推高优先级；汇总走日报 / 周报渠道）＋**"同一事件簇 24 小时内只推一次"**这类硬规则。

**为什么有效**：把"推送预算"当成稀缺资源管理；即时渠道的每一次推送都必须有理由（优先级来自规则 + 信源等级 + 用户订阅）。

**代价**：优先级定义要写下来并复核；渠道有我方与第三方（邮件 / IM / 短信）的成本与投递质量差异。

**判据**：**一个人一天最多收到多少条**这个数写在哪；以及有多少条是被频控挡下的（**被挡下的数量是系统在自我约束的证据**）。

**失效点**：只按"用户订阅了什么"推送，不按"事件重要度"——结果重要事件被噪声淹没（用户会退订整个渠道）。

#### 3.2.8 人审抽检闸门（高风险情报）

**被什么约束逼出来**：某些事件（监管处罚、并购、财务重大变化）误报代价极高（约束 3）。

**结构**：按标签 / 金额阈值 / 主体名单把情报分为"高风险"与"常规"；高风险走**人审闸门**（有超时，超时默认不推或降级为"参考"），常规直接分发。

**为什么有效**：把人工判断力集中到最少数、最贵的那几条上——**这是本主题里唯一"用人力换质量"的杠杆**。

**代价**：受人的响应时间限制（与 [Ch5 §02 §2.2](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture.md) 的积压条件 `n > λ/μ` 同源）；且要防"橡皮图章"（统计否决率，连续两季度为零说明闸门没起作用）。

**失效点**：闸门适用范围过宽（都走人审）→ 人力瞬间成为瓶颈，且时效必然不达标。

### 3.3 模式选择决策表

| 约束组合 | 推荐形态 | 必须同时上的部件 | 不选它的原因（反面） | 关键判据（可核查） |
| --- | --- | --- | --- | --- |
| 信源只有页面、时效天级 | 3.2.1 定时批处理 | 增量游标、失败重跑、断供检测 | 上流式是过度设计 | SLA 是否 ≥ 抓取间隔（是） |
| 有推送接口、时效分钟级 | 3.2.2 流式 | 队列、去重、背压、**兜底轮询** | 只靠推送会静默断供 | 是否有心跳 / 兜底（无→必须补） |
| 信源数量多、价值差异大 | 3.2.3 混合 | 信源分级清单与复核周期 | 全域高频抓取成本与风险双高 | 每个信源的级别与上次复核时间 |
| 一事件多来源 | 3.2.4 三级去重 + 事件簇 | 指纹 + 向量 + 时间窗；簇内多来源保留 | 直接分发素材 → 重复推送 | 抽检同簇准确率与拆分准确率 |
| 有硬信号（文号 / 代码） | 3.2.5 规则 + 模型混合 | 标签体系与 Owner、误报归因 | 纯模型拦不住硬信号，纯规则覆盖不了语义 | 误报能否归因到规则或模型 |
| 假事实代价高 | 3.2.6 引用回指 + 事实性校验 | 片段映射、数值回查、每周抽检 | 无引用回指的摘要在情报场景不可用 | 每周抽检是否执行、错误能否归因 |
| 多角色 / 多客户 | 3.2.7 频控 + 渠道编排 | 三维频控、优先级规则、被挡统计 | 不频控 → 退订；不分级 → 重要被淹没 | 每日每人上限写在哪；被挡条数 |
| 高风险事件（监管 / 并购） | 3.2.8 人审闸门 | 风险分级规则、闸门超时、否决率统计 | 全自动分发高风险情报 = 把责任交给模型 | 否决率是否长期为零 |

### 3.4 组合模式：真实系统不会只用一种

1. **采集组合**：3.2.3（分级信源）——A 级流式 + B/C 级批处理，**这是绝大多数情报系统的现实形态**。
2. **判断组合**：3.2.5（规则 + 模型）+ 3.2.4（事件簇）——先归簇，再对簇做一次分类（**避免对同一事件的 5 篇报道各分类一次**，既省成本又一致）。
3. **输出组合**：3.2.6（引用回指）+ 3.2.8（高风险人审）——**高风险必须同时具备"可点开验证"与"有人签字"**。
4. **分发组合**：3.2.7（频控与渠道）——即时渠道推"高风险 + 高优先级"，汇总渠道推全量。

**常见误配**：归簇在分类之后（同一事件被分类多次、标签不一致）；引用回指做在分发之后（用户看到的摘要已无出处）；频控只做在渠道侧（不同渠道叠加起来仍然超量）。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **只有推送没有兜底轮询** | 某天一条都没来，但系统"正常" | 静默断供，情报链路实际已死 | 推送接入比轮询简单 |
| **对素材分发而非事件簇** | 同一事件推三遍 | 用户屏蔽渠道 | 去重被当作"画蛇添足" |
| **关键词规则过宽** | 同名不同公司被反复误报 | 误报长期存在且模型拦不住 | 规则只是"先能用"的过渡品，没维护 |
| **摘要无引用回指** | 用户问"这条哪来的" | 无法验证，信任崩塌 | 摘要只按"通顺"优化 |
| **数字不做回查** | 摘要里的金额与原文不符 | 假事实进入决策 | 回查要额外做片段映射 |
| **只看打开率不看漏报** | 打开率高但关键事件漏了 | 系统优化成"推用户爱看的" | 指标只选容易测的 |
| **无频控** | 用户退订 | 分发渠道失效 | 个性化被理解成"全部推" |
| **无人抽检** | 三个月后误报率无人知道 | 系统退化成噪声源 | 抽检是长期人力，预算里没有 |
| **信源清单无 Owner** | 某信源挂了半年无人知 | 覆盖悄悄变小 | 信源被当作"配置"而不是"资产" |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 人工简报 → 抓取 + 规则 | 覆盖不够、人一休假就断 | 3.2.1 | 信源清单与规则体系从零建 |
| 抓取 + 规则 → 规则 + 模型 | 同义漏报、同词误报都压不下去 | 3.2.5 + 3.2.4 | 标签体系与归簇阈值要先立 |
| 批处理 → 混合（加流式） | 突发事件总是慢半拍【经验：时效要求从"天"提到"小时"是常见触发点】 | 3.2.3 | 队列、背压、兜底轮询 |
| 单渠道 → 多渠道 + 个性化 | 有人收到太多、有人收不到 | 3.2.7 | 频控与优先级规则；渠道成本核算 |
| 全自动 → 高风险人审 | 一次误报造成实际损失 | 3.2.8 | 风险分级规则 + 闸门超时 + 否决率统计 |
| 无质量口径 → 有口径 | 无法回答"系统在变好吗" | 漏报 / 误报 / 时效三组指标 | 需要人工标注样本（**这是唯一无法自动化的投入**） |

### 3.7 自检清单

- [ ] 信源清单里每个信源都有 Owner、授权边界与上次复核时间吗？
- [ ] 推送型信源有兜底轮询吗？**断供检测的判据是什么**（多久没数据算断）？
- [ ] 采集延迟、处理延迟、摘要延迟、分发延迟**分开测**了吗？各自的 P95 是多少？
- [ ] 增量游标可回拨重放吗？重放会不会产生重复推送？
- [ ] 去重是按事件簇分发的吗？同簇准确率与拆分准确率各是多少？
- [ ] 标签体系有 Owner 与增删流程吗？误报能归因到"规则过宽"还是"模型阈值过低"吗？
- [ ] 摘要的引用回指指到**片段**了吗？数值 / 日期 / 主体做机械化回查了吗？
- [ ] 每周抽检 20 条摘要这件事，谁在做？最近一次发现的错误定位到了什么？
- [ ] 每人每天的推送上限写在哪？被频控挡下的条数是多少？
- [ ] 高风险情报有人审闸门吗？闸门有超时吗？否决率统计过吗？
- [ ] 反馈回流回流了什么？最近一次阈值调整依据的是哪组数据？
- [ ] 漏报率怎么测（有没有"应该报但没报"的样本集）？

### 3.8 小结

> 本节小结：情报链路的形态由五条约束按序决定——**授权边界 → 时效要求 → 判断风险 → 受众结构 → 人力**；八种模式里，**分级信源（3.2.3）与事件簇去重（3.2.4）是链路的骨架**（前者决定成本与覆盖，后者决定用户是否还愿意看），**引用回指与事实性校验（3.2.6）是可信度的下限**，**频控与人审闸门（3.2.7 / 3.2.8）是把"自动化"约束在可承受范围内的两个阀门**。判断这条链路有没有真正建起来，只看两条：**断供时你多久知道**；**同一件事会不会推第二遍**。

> 💡 **思考锚点**：在你的情报链路上做两个可当场验证的动作：① **把某个信源的抓取关掉，看多久后有人发现**（这测的是断供检测）；② **找一次同一事件的多篇报道，看它推了几次**（这测的是事件簇）。两个动作各花不到半天，却能回答"这条链路到底是活的还是看起来活的"——你打算先测哪一个？
