## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

情报链路的形态由**五条约束**决定，顺序不能颠倒：

1. **信源的可获取性与授权边界**：能抓还是只能买？抓到之后**能不能摘要、能不能对外分发**？（授权边界直接决定分发形态——不能分发的信源只能进"内部参考"渠道。）
2. **时效要求**：从发布到可见允许多久？分钟级（行情、监管突发）还是天级（研报、周报）？**这一条决定采集是流式还是批处理**。
3. **判断风险**：误报的代价有多大？漏报的代价有多大？（决定分类阈值、是否需要人审、是否需要"高风险必须引用回指"。）
4. **受众结构**：给一个人看，还是给多个角色 / 客户看？（决定分发是"集中一份简报"还是"按订阅扇出"。）
5. **人力**：有没有人能每天做抽检与阈值维护？（**没有这个人，情报系统会在三个月内退化成"噪声源"**——这是本主题最现实的约束。）

> **判据的用法**：先用 1 决定"哪些信源进哪个渠道"；用 2 决定采集架构；用 3 决定闸门密度；用 4 决定分发架构；用 5 决定**自动化到什么程度**。跳过第 5 条最常见的后果：全自动上线、无人抽检，三个月后用户把它屏蔽。

**每条约束的"过关"是可核查的**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 授权边界 | 每个信源都能回答"能不能摘要、能不能对外分发"，且这个答案以**机器可读**的形式存在（不是文档） |
| 2 时效要求 | 采集 / 处理 / 摘要 / 分发四段延迟**分开测**过，各自的 P95 是已知数 |
| 3 判断风险 | 误报与漏报的代价是**分开估**的（二者常不对称，用一个数概括会导致阈值拍脑袋） |
| 4 受众结构 | 每个角色的订阅与优先级规则写下来过 |
| 5 人力 | 抽检与阈值维护在排期里**有名字**，不是"谁有空谁看" |

第 3 条的两侧不对称是本主题最容易被压平的一条：**误报的代价是"用户不再看"，漏报的代价是"错过一次判断"**——前者的代价随误报率累积，后者的代价集中爆发。因此阈值不该是一个"平衡点"，而应当**按事件类型分别定**（§3.2.4 的阈值标定与 §3.2.8 的风险分级都是这条约束的直接产物）。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 定时批处理（拉模式）

**被什么约束逼出来**：信源只提供页面 / 文件（无推送接口），且时效要求是天级。

**结构**：按调度周期抓取 → 落原始素材 → 增量处理 → 生成简报（例如每日一次）。

**为什么这样设计有效**：因为**抓取节奏由你单方面决定**——没有对外依赖、没有连接要保持、没有推送端点要暴露。由此推出三条实际收益：对信源压力可控（节流由自己定）、成本可预测（每天一轮，预算等于轮数 × 单轮成本）、失败可重跑（一轮没抓全，重跑的就是那个时间窗）。**它的有效性来自"控制点在采集方"这一点**，而不是来自"实现简单"——实现简单只是它的表象，机制是**你拥有节奏的决定权**。

**代价**：时效上限 = 抓取间隔（**判据**：如果 SLA 要求 30 分钟内可见，而抓取间隔是小时级，这个模式在原理上达不到目标）。另：**单点失败会整轮缺失**（这一轮全没抓到），需要"失败重跑这一段窗口"的能力。**这里有一条容易被忽略的配套要求**：增量游标必须**可回拨重放**——否则"重跑失败窗口"这个能力在实现上不成立，只能等下一轮。

**失效点**：突发事件的时效要求超出批处理能力时，用户会转向其他渠道——**此时不是优化批处理，而是给高价值信源加一条流式通道（模式 3.2.3）**。另一条失效点更隐蔽：**批处理的"成功"会掩盖部分失败**——一轮里 30 个信源成功 29 个，任务状态是"成功"，而缺的那一个可能正是关键信源；因此**必须按信源记录采集结果**，而不是按任务。

**判定方法**：取任一 B 级信源，把它的 `interval_min`（§4.2（1）的信源登记模板里就是这个字段）与 §2.2 里那一段的 P95 目标并排列出——**若 P95 目标小于一个抓取间隔，这个模式在原理上就不达标**：问题出在节拍，不在实现质量，换更好的抓取实现或加机器都不会改善。

**真实使用**：本主题把这一形态的调度实现落在 §4.3 工具链的「调度与编排」一行——「工作流调度器（Airflow / DolphinScheduler 一类）」；它的配置级落点是 §4.2（1）的信源登记模板（`access: {mode: poll, interval_min: 15}` 这一行），它在账上的样子见 §4.6 算例（A 级 20 个 × 96 次 + B 级 180 个 × 24 次 = 6,240 次/日）；主文件 §1.4 把这个形态在本书时间线上的起点记为「抓取 + 规则阶段（2010s）：爬虫 / RSS 聚合 + 关键词规则」。全书他处对这类编排产品的定位更具体：Ch3 §12 把 Apache Airflow（2.9+）归在「代码定义的通用编排」、把 Apache DolphinScheduler（3.1+）与阿里云 DataWorks 归在「可视化 / 声明式编排」，并给出「团队以 Python 为主 → Airflow；维护者以数仓 / SQL 开发为主 → DolphinScheduler」这条判据。**但要说清这是范围邻接，不是举证**：本节引的是「节拍与配额落在哪一类调度器上」，不是「谁用某个产品做情报采集」——本主题 §4.3 的采集行只写到「官方 API / RSS / SDK / 合规的页面采集」，并没有产品名；具体信源方的抓取条款与配额请以其官方文档当前版本为准。【公开】（来源：本主题 §4.2（1）、§4.3、§4.6 与主文件 §1.4；`03-data-stack/12-scheduler/12-scheduler-section-4-sec4.md` §4.2 选型表）

#### 3.2.2 事件驱动流式（推模式 / Webhook / 订阅接口）

**被什么约束逼出来**：信源提供推送或订阅接口，且时效要求在分钟级。

**结构**：信源主动推送 → 入队 → 实时处理（去重 / 抽取 / 分类 / 摘要）→ 分发。

**为什么这样设计有效**：因为**延迟的决定权从"你的轮询间隔"移到了"信源的发布时刻"**——发布即到达，因此时效下限不再是你的调度周期。同时它顺带解决两件事：不再轮询（对信源友好，也降低触发反爬的概率）、不再有"这一轮没抓全"这个类别（改成了"这一条没收到"，粒度更细、更容易补偿）。

**代价**：① **必须处理"乱序与重复投递"**（推送通常是"至少一次"）；② 需要队列与背压（突发事件爆发时流量是脉冲，例如某公司一次性发布 20 条公告）；③ 端点自身成为依赖（推送中断就是断供，需要**心跳 / 兜底轮询**）。**第 ③ 条的机制值得说清**：推送是**信源主动**的行为，因此"没有消息"与"信源没发布"在你的系统里长得一模一样——**只有引入一个独立的、由你发起的探测（心跳或低频轮询），才能把这两种情况区分开**。这就是为什么兜底轮询不是"多此一举"，而是这个模式的**组成部分**。

**失效点**：只依赖推送而没有兜底轮询——推送通道静默中断时，**系统会安静地什么都不做**（这正是情报系统最危险的失败形态）。

**判定方法**：停掉一个推送端点，等过该信源的 `no_data_alert_after`（§4.2（1）里给的默认值是 12 小时），看两件事同时发生没有——**断供告警触发并通知到 Owner**、以及**兜底轮询把这段窗口里漏掉的条目补回来**（§4.7 演练表把通过判据写成后者）。两件都没发生，链路就处在"看起来在跑"的状态（§4.5 模板 2 的断供检测 SQL 就是这条判定的实现）。

**真实使用**：本主题把这一形态的实现写在 §4.3 工具链的同一行——「流式用消息队列」，但没有点名产品；配套判据在 §4.7 的演练表：「推送通道中断 → 停掉推送端点 → 通过判据是兜底轮询或重投生效」。全书他处对消息层与流处理引擎有具名条目：Ch3 数据仓库的选型表把「消息队列」列为 Kafka / Pulsar / RocketMQ（另有 AutoMQ / Confluent Warpstream），给出的代价是「队列只当传输、不留历史 → 实时链路无法重放」；同章把采集侧写成「业务库走 CDC（Debezium / Flink CDC）、第三方 API 走 DataX / Airflow 定时抽取」——后者恰好是 §3.2.3 里 B / C 级信源的对照形态；Ch1 §06 把「批处理（Airflow / DolphinScheduler）还是流处理（Flink / Kafka Streams）」写成一条按「允许多久不同步」来判的选择。至于某一款推送接口的投递语义与配额条款，请以该信源方官方文档的当前版本为准。【公开】（来源：本主题 §4.3、§4.7 与主文件 §1.4；`03-data-stack/01-data-warehouse/01-data-warehouse-section-4-sec4.md` §4.2 选型表；`01-modeling/06-knowledge-graph/06-knowledge-graph-section-4-sec4.md` §4）

#### 3.2.3 混合：重要信源流式 + 长尾批处理

**被什么约束逼出来**：约束 2 分化明显——少数信源要求分钟级，几十个长尾信源天级即可；同时约束 5（人力）要求成本可控。

**结构**：**分级信源清单**——A 级（少数、高价值、高频）走流式；B 级（多数）走批处理；C 级（试探性信源）低频抓取并观察质量。

**为什么这样设计有效**：因为**抓取成本与信源价值不是线性关系**——大量长尾信源对判断的边际贡献很小，而它们的抓取成本（请求量、解析维护、反爬风险）与高频信源同阶。分级把预算从"数量"转到"影响判断的那几个"上，**有效性来自"按价值分配预算"这个结构，而不是来自"混合"这个形式**——如果信源价值分布是均匀的，分级就没有收益。

**代价**：分级标准必须写下来并可复核（"为什么这个信源是 A 级"）；分级评审要定期做（信源价值会漂移）。**这里有一条硬要求**：A 级的判定必须能指向一个可核验的理由（例如"它发布的内容在过去 6 个月里被引用/触发过 N 次"），否则分级会退化成"谁嗓门大谁是 A 级"——而 A 级的成本远高于 B 级，噪音化的分级会直接把预算吃掉。

**判据**：**任一信源属于哪一级，能否从配置里读出来，并说明它上一次被复核的时间。**

**失效点**：当信源价值分布变得均匀、或 A 级名单被"谁嗓门大谁是 A 级"填满时，分级把预算压在了不产生判断增量的信源上——**早期信号是 A 级信源数持续上升，而 A 级的引用 / 触发次数不升**；此时正确的动作是重做一次 A 级复核（回到上面那条可核验理由），而不是继续加 B 级。另一种失效是分级与断供判据脱钩：A 级信源挂着流式通道，却没有 `no_data_alert_after`（§4.2（1）），于是最贵的那条通道反而最不容易被发现已经死了。

**判定方法**：把信源清单按 `tier`（§4.2（1））分组，看每组里有多少条同时写下了**上一次复核时间**——本主题 §4.2（1）的清单模板目前只有 `tier` 而没有这一列，缺它就意味着分级已退化为一次性标签，A 级的成本优势会在下一轮信源漂移里被吃掉。

**真实使用**：这一形态在本主题里有配置级证据——§4.2（1）信源登记模板的 `tier: A` 字段（注释即「A 流式 / B 批处理 / C 试探」），§4.3 工具链把「时效要求与信源是否分级」直接写成调度层的选型判据，§4.6 的算例把它落到账上（200 个信源里 A 级 20 个按 15 分钟一轮、B 级 180 个按 1 小时一轮）；§3.3 决策表把它记成「信源数量多、价值差异大」一行的推荐形态，§7.6 选型矩阵的「垂直行业、信源多、要自持口径」一行首选自建端到端链路，其采集侧的现实形态就是这一条。全书他处可引的是同一族编排产品的分级事实（Ch3 §12：Airflow 属代码定义、DolphinScheduler 与 DataWorks 属可视化托管），但「哪一级配哪一类调度」是本节的分配建议，不是任何产品的公开规格——具体调度语义请以其官方文档的当前版本为准。【公开】（来源：本主题 §4.2（1）、§4.3、§4.6、§3.3 决策表与 §7.6 选型矩阵；`03-data-stack/12-scheduler/12-scheduler-section-4-sec4.md` §4.2 选型表）

#### 3.2.4 三级去重 + 事件簇

**被什么约束逼出来**：同一事件有多个来源，且转载 / 改写普遍（约束：重复推送会摧毁信任）。

**结构**：① **同源重复**（指纹完全相同）→ 丢弃；② **跨源相似**（向量相似度 ≥ 阈值且时间窗口内）→ 归入同一**事件簇**；③ **人工确认的相关事件** → 关联（不是重复）。

**为什么这样设计有效**：因为**分发的单位从"素材"变成了"事件簇"**——重复的消除不靠"再判一次是否重复"，而靠"同一簇只分发一次"这个结构。**这是本主题里少见的"用结构而不是用判断消除一类缺陷"的做法**：判断型的去重每次都要重新决定，结构型的去重只要归簇正确，重复就在机制上不可能发生。

**代价**：阈值与时间窗口要按事件类型分别标定（并购 vs 行情差异极大）；**误合并**会把两条不同的事件合成一条（这会直接造成漏报，比重复更危险）。**两个错误方向的代价不对称**是这里的关键：重复的代价是"用户烦"，误合并的代价是"少报了一件事"——因此阈值应当**偏向"宁可不合"**，并保留"同簇多来源"的呈现（多来源本身是可信度信号）。

**判据**：抽样 100 组"被判为同簇"的素材人工核对——**同簇准确率与拆分准确率（不该合的别合）两个都要看**。只看前者会系统性高估质量。

**失效点**：只按文本相似度去重，忽略"同一事件的不同角度报道"——正确形态是"同簇但呈现多来源"，而不是"合并成一条"。

**判定方法**：抽样 100 组被判为同簇的素材，**同时**算同簇准确率与拆分准确率两个数——只报前者会系统性高估质量，两个数里更该被盯住的是拆分准确率（它对应的是漏报，代价不对称）。

**真实使用**：本主题的机制证据在 §6.1——Palantir 一类分析平台把数据组织成「对象 + 关系」而不是以文档为原子单位，"同一件事"因此有天然的同一性判据（对象标识 + 关系），分发单位与去重单位自动统一；本节借的是这个**单位的选择**，不是它的实现。形态证据在 §4.2（3）的三维表（正文指纹 / 向量相似 / 主体 + 动作 + 时间三元组）与 §2.2 的形式化（`sim ≥ θ_sim` 且 `|t1−t2| ≤ W`，θ 与 W 按事件类型标定）；候选差异见 §7.3.2——「产品族的默认分发单位常是文章 / 条目，跨源归并未必开放配置」。同一族问题（把多份观察归到同一实体）在全书他处以实体解析产品化：Ch1 §09 把 Palantir Foundry Entity Resolution（图原生 + Ontology）、AWS Entity Resolution、Salesforce Data Cloud、阿里云实体解析列为「托管实体解析服务」，机制描述是「服务商提供候选生成、匹配规则 / 模型与人工复核工作台，客户只做字段映射」——这与本节的「归簇 + 抽样人工核对」是同一种分工，**但适用对象不同（那里是主数据身份，这里是外部事件），引用时不可互相替代**。【公开】（来源：本主题 §6.1、§4.2（3）、§2.2 的形式化、§7.3.2；`01-modeling/09-one-id/09-one-id-section-7-sec7.md` §7.2 候选表与 `01-modeling/09-one-id/09-one-id-section-4-sec4.md` §4 产品表）

#### 3.2.5 规则 + 模型混合分类

**被什么约束逼出来**：纯规则对同义 / 同词不同义无解；纯模型无法满足"必须命中的硬信号"（如监管文号、公司代码）。

**结构**：**规则层**负责硬信号（文号、代码、关键词组合，必须可解释）；**模型层**负责语义归类（标签体系内的多标签分类）；两者结果合并，冲突时按事先规则处理（例如"硬信号优先"）。

**为什么这样设计有效**：因为**两类错误的可解释性要求不同**——硬信号（"这只股票代码被处罚了"）一旦判错，用户会问"你凭什么"，因此它的依据必须是**可复述的规则**；语义归类（"这属于哪一类风险"）本身就是模糊判断，用户能接受"模型给了 0.7 的置信度"。**把两类判断放在同一个判别器里，会导致"要么规则被稀释、要么模型被拖累"**——混合的有效性来自**让每类判断用它自己需要的可解释性标准**。

**代价**：两套逻辑要维护；**标签体系**必须有 Owner 与增删流程（否则标签会膨胀到无法量误报）。**"标签膨胀"有一个可测的信号**：新增标签的速度持续高于归档标签的速度——此时误报归因会失效（同一个误报可以落到多个标签上，无法定位到阈值）。

**判据**：任一被推送的情报，能否回答"它命中了哪条规则、模型给了哪一档置信度"；以及**误报能否归因到"规则过宽"或"模型阈值过低"**。

**失效点**：只优化模型阈值而不管规则——规则过宽造成的误报（例如关键词命中了同名不同公司）会一直存在，且模型再准也拦不住。

**判定方法**：抽 20 条被判为误报的情报，逐条填「命中了哪条规则」或「哪个标签的多少分」——**有任何一条填不出，说明归因字段没进库**，阈值调整就只能是拍脑袋。

**真实使用**：本主题的落地配置在 §4.2（5）——规则用 `priority: hard` 表达「必须命中且可解释」，模型侧 `threshold` 按标签分别设，并强制落 `attribution: [rule_hits, model_score_by_label, classified_at]` 三个字段，这正是「误报能否归因」的技术落点；§4.2（4）的抽取 Schema 用「动作」的枚举值把硬信号与语义类目分开。全书他处有两条同构的具名做法：Ch11 §01 §4.3 把「AI 辅助能力（非独立品类）」单列一行（Mona AI Quality Copilot / Anomalo Autonomous / Monte Carlo + LLM 一类），用法写的是「生成规则草稿与异常归因」，并明确「生成的规则必须经复核才能进 P0」——这与本模式「硬信号要可复述、语义判断可带置信度」是同一条分工线的两个场景；Ch1 §09 把托管实体解析服务描述为「候选生成 + 匹配规则 / 模型 + 人工复核工作台」，同样是「机器给候选、规则与阈值由人定」。模型侧的具体阈值取值与标签集合，本节不给文档出处，请以你自己在标注样本上标定出来的版本为准。【公开】（来源：本主题 §4.2（4）（5）与 §7.3.4；`11-cross-cutting/01-data-quality/01-data-quality-section-4-sec4.md` §4.3 工具链表；`01-modeling/09-one-id/09-one-id-section-7-sec7.md` §7.2）

#### 3.2.6 带引用回指的摘要 + 事实性校验

**被什么约束逼出来**：LLM 摘要会编，而情报里的假事实代价极高（约束 3）。

**结构**：摘要按"事实点 + 出处"生成（每个事实点指回原文句子 / 段落）；**数值、日期、主体做机械化回查**（是否出现在原文、是否被改写）；**回查不通过的数字不写进摘要**。

**为什么这样设计有效**：因为它把**信任的验证成本从"读者去读原文"降到了"点开一个位置"**——没有引用回指时，用户验证一条情报要么信、要么自己去搜原文（成本高到没人做）；有回指之后，验证变成一次点击。**这个成本差是本模式的全部价值**：它不是"让模型更准"，而是"让读者能自己判断准不准"。而机械化回查之所以单列，是因为**数值幻觉是最危险的一类错误**——文字表述的偏差读者能察觉，数字的偏差读者察觉不到（而且数字会被直接拿去用）。

**代价**：生成时要保留片段映射（存储与处理成本上升）；回查规则要按领域维护（单位换算、同比 / 环比表述）。**后者的机制**：回查是"字符串层面的比对"，而情报里的数值经常经过**单位换算**（亿元 → 万元）、**口径改写**（同比 → 环比）和**指代替换**（"该公司"→ 具体公司名），因此回查必须先做一次规范化再比对；不做规范化就只能做"原文里有没有这个字符串"这种弱回查。

**判据**：**每周抽 20 条摘要，逐条核对数值 / 日期 / 主体**；抽检发现的错误要能定位到"哪类提示 / 哪类信源"。

**失效点**：引用回指只指到"整篇原文"而不是具体片段——用户仍要自己找，**等于没有回指**。

**判定方法**：抽 20 条摘要，逐条把每个数值 / 日期 / 主体点回片段，**能点开、且片段确实支持该事实点的比例就是可验证率**——这个比例不达标时，摘要根本无法进入决策流程（§6.7 把"可验证率"单列为准入性收益项，就是这条判定的账目化）。

**真实使用**：本主题的两个案例都是这一形态的直接出处——§6.2 把通讯社的生产方式写成「一条新闻从产生起就带着来源与时间」，并把它落成「摘要按事实点 + 出处片段生成」与「回查前先做单位 / 口径规范化」；§6.3 补上两件本主题独有的要求：引用要带抓取时间（否则材料被改后无法回答"我看的是哪一版"），以及权限要在召回前裁剪。自己的模板在 §4.2（6）（事实点 + 出处片段 + 数字校验 + 多来源）与 §4.5 模板 1（`value_appears_in_span`，回查不通过即 `drop`，不写进摘要）。若要把"事实性"做成可跑的指标，全书他处给出的是 RAG 侧的评估框架：RAGAS 于 2023.10 发布、2025 年形成 RAGAS / TruLens / ARES / DeepEval 的评估体系（`04-data-assetization/05-rag-architecture` §1.4），指标含 `faithfulness` / `groundedness` 一类；同一章明确提醒「忠实性在各框架里的定义不同、跨框架分数不可比」，且这一整族在该章 §5 判为 L2（② 第三方非厂商生产案例不满足）。分发侧还有一条合规锚点：Ch8 §01 把《人工智能生成合成内容标识办法》（2025）映射成「输出侧标识注入 + 输出留档中的标识字段」。【公开】（来源：本主题 §6.2、§6.3、§4.2（6）、§4.5 模板 1；`04-data-assetization/05-rag-architecture/05-rag-architecture.md` §1.4 与 §4.3、`04-data-assetization/05-rag-architecture/05-rag-architecture-section-5-ai.md` §5；`08-ai-governance/01-ai-data-governance/01-ai-data-governance-section-4-sec4.md` §4）

#### 3.2.7 频控与渠道编排

**被什么约束逼出来**：个性化推送会自然演化为骚扰（约束 4）。

**结构**：三维频控（人 / 群组 / 事件簇 × 时间窗）＋渠道分级（即时渠道只推高优先级；汇总走日报 / 周报渠道）＋**"同一事件簇 24 小时内只推一次"**这类硬规则。

**为什么这样设计有效**：因为**用户对渠道的容忍度是"配额"而不是"偏好"**——一个人一天能消化的情报条数是有限的，超过这个数之后，第 11 条与第 100 条的效果是同一档（都是不看），但代价不同（后者会导致退订）。三维频控的机制是**把这三个维度的约束分别施加**：按人限总量（防个体过载）、按群组限重叠（防一个团队被同一件事刷屏）、按事件簇限重复（防同一件事多来源重复）。**三者缺一，另外两个都会被绕过。**

**代价**：优先级定义要写下来并复核；渠道有我方与第三方（邮件 / IM / 短信）的成本与投递质量差异。**这条代价里有一条常被忽略的**：**第三方渠道的投递失败是静默的**（邮件进垃圾箱、IM 被折叠）——因此"推送成功"与"送达"必须分开统计，否则频控会以为自己推了 10 条而用户只看到 3 条。

**判据**：**一个人一天最多收到多少条**这个数写在哪；以及有多少条是被频控挡下的（**被挡下的数量是系统在自我约束的证据**）。

**失效点**：只按"用户订阅了什么"推送，不按"事件重要度"——结果重要事件被噪声淹没（用户会退订整个渠道）。

**判定方法**：把某人一天的**实收条数**、`suppression_log` 里的**被挡条数**、以及**候选池条数**三个数并排列出——三者不相容（实收 + 被挡 ≠ 候选）就说明有渠道绕过了频控（§4.2（7）的配置与 §4.5 模板 3 的分发留痕 SQL 就是这三个数的出处）。

**真实使用**：本主题的案例证据在 §6.4（匿名某券商研究所）：三维频控 `事件簇 × 人 × 时间窗`、被挡条数留痕上看板、屏蔽率当先行指标；配置级证据在 §4.2（7）（`event_cluster 24h/1`、`user 24h/8`、`group 24h/20`，`suppression_log: true`），指标口径在 §4.2（9）的反馈回流表。全书他处对同一机制有一条更细的讨论：Ch9 §06 精准运营把「频控能不能按用户统一裁决」列为**门槛而非权重**，并指出「按活动算频控」的失效模式——总量随活动数线性上升而单活动视角看不见；同一节还写下「没有护栏值守的体系会稳定滑向过度触达」。两者是同一条机制的两种场景（对外情报分发 / 对内运营触达），可以互为旁证，**但不要互相替代**：前者的约束来自"同一事件簇重复推送"，后者的约束来自"多活动叠加"。第三方渠道的投递回执与折叠 / 垃圾箱判定字段，本主题与全书都没有给出具名产品规格——请以你所选渠道服务商官方文档的当前版本为准。【公开】（来源：本主题 §6.4、§4.2（7）（9）；`09-data-intelligence-product/06-precision-operation/06-precision-operation-section-7-sec7.md` §7.1 判据表与候选表）

#### 3.2.8 人审抽检闸门（高风险情报）

**被什么约束逼出来**：某些事件（监管处罚、并购、财务重大变化）误报代价极高（约束 3）。

**结构**：按标签 / 金额阈值 / 主体名单把情报分为"高风险"与"常规"；高风险走**人审闸门**（有超时，超时默认不推或降级为"参考"），常规直接分发。

**为什么这样设计有效**：因为**人的判断力是稀缺且不可扩容的资源**——把有限的人力集中到最少数、最贵的那几条上，是唯一能同时保住时效与质量的分配方式（约束 5 的直接产物）。**它的有效性有严格前提：分级规则必须准确**——如果"高风险"的分级把大量常规事件也划进来，闸门立刻变成瓶颈；反过来，分级漏掉真正的高风险事件，闸门等于不存在。**因此闸门模式真正的工程难点不在闸门本身，而在分级规则。**

**代价**：受人的响应时间限制（与 [Ch5 §02 §2.2](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture.md) 的积压条件 `n > λ/μ` 同源）；且要防"橡皮图章"（统计否决率，连续两季度为零说明闸门没起作用）。**超时的默认动作必须明确**：超时"默认不推"保质量，"默认推送"保时效——**选哪一个取决于约束 3 里误报与漏报哪个更贵**，而这是一个必须写下来的决定（不能留给实现）。

**失效点**：闸门适用范围过宽（都走人审）→ 人力瞬间成为瓶颈，且时效必然不达标。

**判定方法**：统计高风险队列的**否决率**与**闸门超时率**两个数——两者同时长期为零，说明闸门要么没接到流量、要么已经变成橡皮图章（"连续两季度为零"这条判据来自下面的机制出处，不需要采购任何东西就能统计）。

**真实使用**：本主题不给具名的闸门产品——**情报场景的人审闸门目前没有可点名的公开实现，本节只给形态**：§7.5 决策树第 3 问把它写成「误报代价高 → 必须有人审闸门」，且"超时默认动作"（默认不推 / 降级为参考）必须写下来；§6.2 的失败教训（一次把"关联公司被处罚"写成"该公司被处罚"的误报被直接用于对外口径修改）是这条闸门存在的全部理由。机制的出处是本书 Ch5 §02：人审闸门的积压条件 `n > λ/μ`（λ/μ 持续大于现有 n 时，应先缩小闸门适用范围而不是加人），以及防"橡皮图章"的可核查动作——抽检批准记录并统计否决率，连续两季度为零说明这个闸门没有在实际起作用。本主题与它的差别只有一处：平台的闸门拦的是写操作与不可逆动作，**情报的闸门拦的是"分发"**，因此后者的超时默认动作是质量与时效的取舍，必须显式写下。【公开】（来源：本主题 §7.5 决策树、§6.2 失败教训、§4.4 存量迁移；`05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture.md` §2.2 与 `05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md` §3）

### 3.4 组合模式：真实系统不会只用一种

1. **采集组合**：3.2.3（分级信源）——A 级流式 + B/C 级批处理，**这是绝大多数情报系统的现实形态**。
2. **判断组合**：3.2.5（规则 + 模型）+ 3.2.4（事件簇）——先归簇，再对簇做一次分类（**避免对同一事件的 5 篇报道各分类一次**，既省成本又一致）。
3. **输出组合**：3.2.6（引用回指）+ 3.2.8（高风险人审）——**高风险必须同时具备"可点开验证"与"有人签字"**。
4. **分发组合**：3.2.7（频控与渠道）——即时渠道推"高风险 + 高优先级"，汇总渠道推全量。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 归簇在分类之后 | 同一事件被分类多次、标签不一致 |
| 引用回指做在分发之后 | 用户看到的摘要已无出处 |
| 频控只做在渠道侧 | 不同渠道叠加起来仍然超量 |
| 逐素材分类而非逐事件簇 | 成本随转载数放大，且同一事件得到不同标签 |
| 闸门超时默认动作未定义 | 实现自选，质量与时效的取舍变成偶然 |
| 兜底轮询的频率高于推送延迟 | 兜底变成主路径，成本优势消失 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **只有推送没有兜底轮询** | 某天一条都没来，但系统"正常" | 静默断供，情报链路实际已死 | 推送接入比轮询简单 |
| **对素材分发而非事件簇** | 同一事件推三遍 | 用户屏蔽渠道 | 去重被当作"画蛇添足" |
| **关键词规则过宽** | 同名不同公司被反复误报 | 误报长期存在且模型拦不住 | 规则只是"先能用"的过渡品，没维护 |
| **摘要无引用回指** | 用户问"这条哪来的" | 无法验证，信任崩塌 | 摘要只按"通顺"优化 |
| **数字不做回查** | 摘要里的金额与原文不符 | 假事实进入决策 | 回查要额外做片段映射与规范化 |
| **只看打开率不看漏报** | 打开率高但关键事件漏了 | 系统优化成"推用户爱看的" | 指标只选容易测的 |
| **无频控** | 用户退订 | 分发渠道失效 | 个性化被理解成"全部推" |
| **无人抽检** | 三个月后误报率无人知道 | 系统退化成噪声源 | 抽检是长期人力，预算里没有 |
| **信源清单无 Owner** | 某信源挂了半年无人知 | 覆盖悄悄变小 | 信源被当作"配置"而不是"资产" |
| **按任务记采集结果** | 任务显示成功，但某个信源整月无数据 | 部分失败被成功状态掩盖 | 成功/失败是任务级概念，信源级失败看不见 |
| **标签只增不归档** | 误报无法归因到具体阈值 | 阈值调整失去依据 | 加标签容易、归档要人决策 |
| **推送成功率当送达率** | 频控以为推了 10 条、用户只看到 3 条 | 频控的输入数据是错的 | 第三方渠道的失败是静默的 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 人工简报 → 抓取 + 规则 | 覆盖不够、人一休假就断 | 3.2.1 | 信源清单与规则体系从零建 |
| 抓取 + 规则 → 规则 + 模型 | 同义漏报、同词误报都压不下去 | 3.2.5 + 3.2.4 | 标签体系与归簇阈值要先立 |
| 批处理 → 混合（加流式） | 突发事件总是慢半拍【经验：时效要求从"天"提到"小时"是常见触发点】 | 3.2.3 | 队列、背压、兜底轮询 |
| 单渠道 → 多渠道 + 个性化 | 有人收到太多、有人收不到 | 3.2.7 | 频控与优先级规则；渠道成本核算；送达率统计 |
| 全自动 → 高风险人审 | 一次误报造成实际损失 | 3.2.8 | 风险分级规则 + 闸门超时（含默认动作）+ 否决率统计 |
| 无质量口径 → 有口径 | 无法回答"系统在变好吗" | 漏报 / 误报 / 时效三组指标 | 需要人工标注样本（**这是唯一无法自动化的投入**） |
| 单一阈值 → 按事件类型的阈值 | 并购与行情用同一套阈值，两侧都不对 | 3.2.4 的分类型标定 | 需要按类型积累标注样本（成本随类型数增长） |

### 3.7 自检清单

- [ ] 信源清单里每个信源都有 Owner、授权边界与上次复核时间吗？
- [ ] 推送型信源有兜底轮询吗？**断供检测的判据是什么**（多久没数据算断）？兜底频率是否低于推送延迟？
- [ ] 采集结果是**按信源**记录还是只按任务？任务成功时如何发现"某个信源整月无数据"？
- [ ] 采集延迟、处理延迟、摘要延迟、分发延迟**分开测**了吗？各自的 P95 是多少？
- [ ] 增量游标可回拨重放吗？重放会不会产生重复推送？
- [ ] 去重是按事件簇分发的吗？同簇准确率**与拆分准确率**各是多少？阈值是否偏向"宁可不合"？
- [ ] 标签体系有 Owner 与增删流程吗？标签增速与归档速度哪个快？误报能归因到"规则过宽"还是"模型阈值过低"吗？
- [ ] 摘要的引用回指指到**片段**了吗？数值 / 日期 / 主体做机械化回查了吗？回查前有没有做单位与口径的规范化？
- [ ] 每周抽检 20 条摘要这件事，谁在做？最近一次发现的错误定位到了什么？
- [ ] 每人每天的推送上限写在哪？被频控挡下的条数是多少？**"推送成功"与"送达"分开统计了吗**？
- [ ] 高风险情报有人审闸门吗？闸门有超时吗？**超时的默认动作（不推 / 降级）写下来了吗**？否决率统计过吗？
- [ ] 反馈回流回流了什么？最近一次阈值调整依据的是哪组数据？
- [ ] 漏报率怎么测（有没有"应该报但没报"的样本集）？

### 3.8 小结

> 本节小结：情报链路的形态由五条约束按序决定——**授权边界 → 时效要求 → 判断风险 → 受众结构 → 人力**；八种模式里，**分级信源（3.2.3）与事件簇去重（3.2.4）是链路的骨架**（前者决定成本与覆盖，后者决定用户是否还愿意看），**引用回指与事实性校验（3.2.6）是可信度的下限**，**频控与人审闸门（3.2.7 / 3.2.8）是把"自动化"约束在可承受范围内的两个阀门**。判断这条链路有没有真正建起来，只看两条：**断供时你多久知道**；**同一件事会不会推第二遍**。

> 💡 **思考锚点**：在你的情报链路上做两个可当场验证的动作：① **把某个信源的抓取关掉，看多久后有人发现**（这测的是断供检测）；② **找一次同一事件的多篇报道，看它推了几次**（这测的是事件簇）。两个动作各花不到半天，却能回答"这条链路到底是活的还是看起来活的"——你打算先测哪一个？
