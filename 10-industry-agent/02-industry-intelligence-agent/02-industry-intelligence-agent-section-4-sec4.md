## 4. 工程实现

### 4.1 落地步骤

**八步，顺序不能颠倒**：

| 步 | 动作 | 产物 | 判据（先写下，再动手） | 为什么必须在这一步 |
| --- | --- | --- | --- | --- |
| 1 | **建信源清单** | 每个信源：归属方、获取方式、**授权边界**、抓取配额、Owner、分级（A/B/C） | 任一信源能否回答"能不能对外分发" | 授权边界决定渠道；没有它，后面所有分发都有合规风险 |
| 2 | **定时效预算** | 采集 / 处理 / 摘要 / 分发四段的 P95 目标 | 四段之和是否 ≤ SLA | 只给总时长的 SLA 在事故里无法定位 |
| 3 | **建增量与去重** | 游标（可回拨）+ 指纹 + 事件簇 | 重放一段窗口会不会产生重复推送 | 去重是"用户还愿意看"的前提 |
| 4 | **建标签体系** | 标签清单 + Owner + 增删流程 + 每条标签的判据 | 误报能否归因到某条规则 / 某档阈值 | 没有标签体系就无法量误报 |
| 5 | **接抽取与分类** | Schema 约束的抽取 + 规则/模型混合分类 | 被推送情报能否追溯到命中的规则与置信度 | 归因能力决定调优能力 |
| 6 | **做摘要与回指** | 摘要模板（事实点 + 出处）+ 数值 / 日期 / 主体回查 | 每周抽检 20 条能否执行 | 不可验证的摘要在情报场景不可用 |
| 7 | **建分发与频控** | 订阅规则 + 三维频控 + 渠道分级 | 每人每日上限写在哪；被挡条数可见 | 频控是把个性化约束在可承受范围内 |
| 8 | **建反馈与告警** | 反馈回流指标 + 断供告警 + 漏报样本集 | 最近一次阈值调整依据哪组数据 | 没有反馈，系统三个月后退化成噪声源 |

**顺序的反面**：最常见的错误是**先把摘要做得很漂亮（看起来最有产出）**——然后发现：不知道哪些信源该抓（步骤 1 缺）、不知道晚了算不算晚（步骤 2 缺）、同一件事推了三遍（步骤 3 缺）、误报无法归因（步骤 4 缺）。**摘要质量的提升会被前四步的缺失全部吃掉。**

### 4.2 关键技术点

**（1）信源登记（可直接作为清单模板）**

```yaml
source: regulator-announcement-a
owner: compliance-team@example.com
access: {mode: poll, endpoint: "https://…", auth: none, interval_min: 15}
entitlement: {summarize: true, redistribute_internal: true, redistribute_external: false}
quota: {max_requests_per_hour: 60, backoff: {on_403: 6h, on_5xx: 30m}}
cursor: {type: last_id, replayable: true}
tier: A                     # A 流式 / B 批处理 / C 试探
health: {no_data_alert_after: 12h}     # 断供判据：12 小时无新数据即告警
fixtures: [company_name_whitelist, doc_id_pattern]
```

**三条硬要求**：① **授权边界必须显式**（`redistribute_external: false` 意味着该信源的情报只能进内部渠道——这一条要在分发侧被强制，而不是靠人记得）；② **断供判据必须写死**（`no_data_alert_after`），否则静默失效无法被发现；③ **游标可回拨**，否则发现漏抓也无法补救。

**（2）增量游标与漏报防护**

```python
def advance(cursor, items):
    # 关键：先处理再推进游标；处理失败不推进（否则永久漏掉这条）
    for it in sorted(items, key=lambda x: x.published_at):
        if not process(it):            # 失败即中断本轮
            return cursor
        cursor = it.published_at       # 逐条推进
    return cursor

def replay(source, since, until):
    # 发现漏抓时的补救：把窗口重放；去重指纹保证不会重复推送
    for it in fetch_range(source, since, until):
        process(it, dedup=True, replay=True)
```

**判据**：① 处理失败不推进游标（避免"跳过即丢失"）；② 重放走同一套去重，**重放不产生重复推送**（这是一次可以用半天验证的动作）。

**（3）事件簇的三个维度**

| 维度 | 作用 | 常见取值方向 |
| --- | --- | --- |
| 正文指纹 | 抓同源重复（转载 / 重复抓取） | 归一化后的正文哈希 |
| 向量相似 | 抓跨源改写 | 相似度阈值 + 时间窗**按事件类型分别标定**（并购类窗口可到数天【经验】；行情类分钟级） |
| 主体 + 动作 + 时间 | 抓"同一事件的不同角度" | 抽取出的 `(主体, 动作, 日期)` 三元组作辅助键 |

**判据**：抽样 100 组同簇素材，人工核对**同簇准确率**与**拆分准确率**（不该合的有没有被合）——**拆分错误比合并错误更危险**（合并错误表现为重复，拆分错误表现为两条都报、看起来正常，但漏掉了"它们其实是同一件事"的判断）。

**（4）抽取的 Schema（示例）**

```json
{
  "主体": {"company": "string", "aliases": ["string"]},
  "动作": {"type": "enum", "values": ["并购","增资","处罚","发布","召回","中标","离职","诉讼"]},
  "金额": {"value": "number?", "currency": "CNY|USD|?", "source_span": "string"},
  "时间": {"event_date": "date", "published_at": "datetime"},
  "引用": {"span_start": "int", "span_end": "int", "source_id": "string"}
}
```

**关键字段是 `source_span` / `引用`**：抽取结果必须带**原文片段位置**——它同时服务于摘要的引用回指与数值回查（`金额.value` 必须能在 `source_span` 里找到）。

**（5）分类与误报归因**

```yaml
rules:                       # 硬信号：必须命中，可解释
  - id: r-reg-doc-id
    when: {doc_id_pattern: "^〔20\\d\\d〕\\d+号$"}
    label: [监管文件]
    priority: hard           # hard = 强制命中；soft = 加权
model:                       # 语义层：标签体系内多标签
  labels_ref: taxonomy_v3
  threshold: {default: 0.62, 监管文件: 0.50, 舆情: 0.70}   # 阈值按标签分别设
attribution:                  # 误报归因所需字段
  - rule_hits
  - model_score_by_label
  - classified_at
```

**判据**：**每一条误报都能落到"规则命中（哪条）"或"模型分数（哪个标签、多少分）"**——没有这两个字段，误报只能靠感觉调。

**（6）摘要模板与事实性回查**

```markdown
【标题】{主体}{动作}：{核心事实一句}
【事实点】
- {事实 1}〔出处：{source_id} 第 {span_start}-{span_end} 段〕
- {事实 2}〔出处：…〕
【数字校验】金额 / 占比 / 日期逐项标注"原文一致 ✓"或"原文未找到 ✗（已剔除）"
【影响范围】{为什么与订阅者相关，一句}
【多来源】{同簇内的其它来源数与列表}
```

**三条硬规则**：① **回查不通过的数字一律剔除**（宁可少一个数字，不可多一个错数字）；② 引用指到**片段**（段落 / 句子级），不是整篇；③ 多来源要**列出来**（同簇来源数本身就是可信度信号）。

**（7）分发与频控**

```yaml
channels:
  - {name: im_urgent, priority_floor: P0, cap_per_user_per_day: 3}
  - {name: email_digest, priority_floor: P2, cap_per_user_per_day: 1, schedule: "09:00"}
frequency_caps:
  - {scope: event_cluster, window_h: 24, max: 1}     # 同一事件簇 24h 只推一次
  - {scope: user,          window_h: 24, max: 8}
  - {scope: group,         window_h: 24, max: 20}
suppression_log: true        # 被挡下的条目要留痕（证明系统在自我约束）
```

**判据**：**被频控挡下的条数**要作为日常指标——它是"系统没有变成骚扰源"的直接证据。

**（8）SLA 监控（四段分位）**

```sql
CREATE TABLE intel_sla (
  item_id      TEXT PRIMARY KEY,
  source_id    TEXT NOT NULL,
  published_at TIMESTAMPTZ NOT NULL,   -- 信源侧时间
  ingested_at  TIMESTAMPTZ NOT NULL,
  enriched_at  TIMESTAMPTZ,
  summarized_at TIMESTAMPTZ,
  delivered_at TIMESTAMPTZ,
  cluster_id   TEXT,
  priority     TEXT
);
-- 四段延迟分别算 P95；断供按 (source_id, max(ingested_at)) 与阈值比对
```

**判据**：**任取一天，能算出每个信源的四段 P95**；断供告警能在 `no_data_alert_after` 内触发（这可以用一次"故意关掉抓取"的演练验证）。

**（9）反馈回流指标（按信源 × 标签 × 渠道分组）**

| 指标 | 口径 | 用途 |
| --- | --- | --- |
| 打开率 | 打开 / 送达 | 渠道与标题质量 |
| 采纳率 | 被引用 / 转发的条数 / 送达 | 真实价值（比打开率可靠） |
| 纠错率 | 用户标注错误 / 送达 | 直接指向误报与事实性 |
| 屏蔽率 | 退订 / 静音 / 屏蔽 | **危险的先行指标**（一旦上升要先查频控） |
| 漏报反馈 | 用户补报"这事你没告我" | 唯一能测漏报的途径 |

**判据**：**漏报反馈渠道存在吗**？没有它，漏报率永远无法测量（这也是本主题最难的一项——**它需要人工标注样本，无法自动化**）。

### 4.3 工具链与平台

| 层 | 可选 | 选型判据 |
| --- | --- | --- |
| 调度与编排 | 工作流调度器（Airflow / DolphinScheduler 一类）；流式用消息队列 | 时效要求与信源是否分级 |
| 采集 | 官方 API / RSS / SDK / 合规的页面采集 | **优先 API 与 RSS**；页面采集要先看授权边界 |
| 存储 | 原始素材区（对象存储）+ 结构化库（事件 / 标签 / 分发记录） | 是否需要按片段回溯（回指需要片段） |
| 去重与检索 | 向量库 + 全文索引 | 事件簇的时间窗与相似度阈值要可配置 |
| 抽取与分类 | Schema 约束抽取（规则 / 模型混合）、标签体系管理 | 是否需要误报归因字段（需要 → 强制） |
| 摘要 | 带片段映射的生成链路 + 数值回查 | 是否要求引用回指（情报场景：必须） |
| 分发 | 邮件 / IM / 短信 / 内部应用；模板引擎 | 渠道成本与投递质量；是否要按角色分版 |
| 观测 | 四段延迟指标 + 断供告警 + 群体指标（打开 / 采纳 / 纠错 / 屏蔽） | 是否有漏报反馈入口 |

### 4.4 存量迁移

**从人工简报 / 规则抓取迁到可运营链路，四步**（每步可独立验证）：

1. **清单化**：把现在"人脑子里"的信源写成清单（含授权边界、Owner、分级）。**判据**：任一信源可回答能否对外分发。
2. **影子对比**：自动化链路与人工简报并行 2–4 周，比较**覆盖（漏了哪几条）**、**时效（早多少）**、**误报（多推了哪几条）**。**判据**：能列出"人工报了而系统没报"的清单——**这份清单是后续调优的靶子**（也是本主题最有价值的迁移产物）。
3. **逐步接管**：先接管"覆盖率"（自动生成候选，人做筛选），再接管"分发"（自动分发常规、人工只审高风险）。**判据**：人工筛选比例逐周下降。
4. **建立质量闭环**：漏报样本集 + 每周抽检 + 阈值调整记录。**判据**：最近一次阈值调整能指出依据。

**迁移的判据代替"上线"这个动作**：情报系统的"上线"不是一次发布，而是**人工介入比例的持续下降 + 质量指标不退化**。

### 4.5 模板 / 示例

**模板 1：摘要生成与回查（伪代码）**

```python
def summarize_with_citation(doc, facts):
    spans = locate_spans(doc, facts)               # 每个事实点在原文中的位置
    summary = llm_summarize(facts, spans)          # 提示要求逐条带出处
    for f in summary.facts:
        if f.kind in ("amount", "date", "entity"):
            ok = value_appears_in_span(doc, f, spans[f.tid])
            if not ok:
                f.drop = True                      # 回查不通过 → 剔除，不写进摘要
    summary.facts = [f for f in summary.facts if not getattr(f, "drop", False)]
    summary.sources = cluster_sources(doc.cluster_id)   # 多来源列表
    return summary
```

**模板 2：断供检测（SQL 判据）**

```sql
-- 任意信源若超过阈值没有新数据，产出告警行
SELECT s.source_id, s.owner, max(i.ingested_at) AS last_seen,
       now() - max(i.ingested_at) AS silent_for
FROM sources s LEFT JOIN intel_items i USING (source_id)
GROUP BY s.source_id, s.owner, s.no_data_alert_after
HAVING now() - max(i.ingested_at) > s.no_data_alert_after;
```

**模板 3：一条分发的完整留痕（复盘入口）**

```sql
SELECT i.item_id, i.source_id, i.cluster_id, i.priority,
       i.published_at, i.ingested_at, i.summarized_at, i.delivered_at,
       d.channel, d.suppressed_reason
FROM intel_items i LEFT JOIN intel_delivery d USING (item_id)
WHERE i.cluster_id = $1 ORDER BY i.published_at;
```

### 4.6 成本：这条链路的账单

**四块成本**【推算：口径固定，单价按你的采购口径代入】：

| 成本块 | 构成 | 优化动作 |
| --- | --- | --- |
| 采集成本 | 抓取请求数 × 单价（或自建爬虫的机器与运维） | 信源分级（A 级高频、C 级低频）、增量抓取 |
| 处理成本 | 去重 / 抽取 / 分类的算力 | **先归簇再分类**（同一事件只分类一次） |
| 摘要成本 | 摘要调用 × token 单价（含重试） | 只对"进入分发候选"的簇摘要（**不要对全量素材摘要**） |
| 分发成本 | 推送条数 × 渠道单价（短信 / IM 配额） | 频控本身就是成本控制（被挡下的条数也是省下的钱） |

**算例（建立量级感）**：设 `200` 个信源、A 级 `20` 个每 `15` 分钟抓一次、B 级 `180` 个每小时一次【经验：分级比例随行业浮动】。

- 日抓取请求数 ≈ `20 × 96 + 180 × 24 = 6,240` 次/日（量级：数千次/日）；
- 若日均新增素材 `2,000` 条、经去重后成簇 `600` 个、进入摘要的 `300` 个【经验】，则**摘要量只有素材量的 15%**——这就是"先归簇再摘要"的价值；
- 分发量按 `600` 簇 × 平均 `5` 个订阅者命中 ≈ `3,000` 条/日，被频控挡下的通常占**两到四成**【经验】。

**一条判据**：**"摘要条数 ÷ 素材条数"的比例越低越好**（说明归簇与筛选在起作用）；如果这个比例接近 1，说明还没有筛选层。

### 4.7 容灾与故障演练

| 故障 | 演练动作 | 通过判据 | 常见失效点 |
| --- | --- | --- | --- |
| 信源断供 | 关掉某信源的抓取 | `no_data_alert_after` 内告警，Owner 被通知 | 无断供判据 → 静默失效 |
| 抓取被限流 / 封禁 | 让信源返回 403 / 429 | 退避策略生效，不触发更大封禁 | 无退避 → 越抓越封 |
| 推送通道中断 | 停掉推送端点 | 兜底轮询或重投生效，条目最终送达 | 只依赖推送 |
| 摘要模型端点故障 | 让模型返回 5xx | 降级为"仅抽取 + 原文链接"（**不降级为无出处的摘要**） | 降级时仍在生成无回指的摘要（最危险的降级） |
| 误报风暴 | 注入一批同一模式素材 | 频控与优先级生效；误报能被归因到规则或阈值 | 无频控 → 用户被淹没 |
| 重复推送 | 重放一段窗口 | 事件簇去重挡住重复 | 去重在分发之后 |

**一条纪律**：**摘要环节的降级必须"降功能不降可信"**——可以退回到"只给原文与抽取结果"，**绝不能退回到"没有出处的自由生成"**。

### 4.8 演进路线：0 → 1 → 100

- **0 → 1（有人用）**：信源清单 + 增量去重 + 规则分类 + 人工筛选后的分发。判据：不再有人手工翻信源。
- **1 → 10（可信）**：事件簇 + 引用回指 + 事实性回查 + 频控 + 四段 SLA 监控。判据：同一事件不再重复推送；每条摘要可点开验证。
- **10 → 100（可运营）**：标签体系与误报归因 + 反馈回流 + 漏报样本集 + 高风险人审闸门 + 渠道分级。判据：**最近一次阈值调整能指出依据**；漏报反馈渠道在运转。

### 4.9 自检清单

- [ ] 信源清单里每个信源都有授权边界、Owner、分级与断供判据吗？
- [ ] 推送型信源有兜底轮询吗？故意关掉一个信源，多久被发现？
- [ ] 游标"失败不推进"吗？重放窗口会不会重复推送？
- [ ] 去重是"分发单位 = 事件簇"吗？同簇准确率与拆分准确率各是多少？
- [ ] 抽取结果带片段位置吗？金额 / 日期能在原文里回查吗？
- [ ] 摘要里回查不通过的数字被剔除了吗？引用指到片段还是整篇？
- [ ] 标签体系有 Owner 与增删流程吗？误报能归因到规则或阈值吗？
- [ ] 每人每日推送上限写在哪？被频控挡下的条数是多少？
- [ ] 高风险情报有人审闸门与超时吗？否决率统计过吗？
- [ ] 四段延迟（采集 / 处理 / 摘要 / 分发）分别有 P95 吗？
- [ ] 摘要降级时会不会产出"无出处的摘要"（**不应**）？
- [ ] 漏报反馈入口存在吗？最近一次人工标注做了多少条？
- [ ] "摘要条数 ÷ 素材条数"是多少？这个比例是否说明筛选层在起作用？

### 4.10 小结

> 本节小结：情报链路的工程实现可以压缩成一句话——**先把信源与时效变成可管理的对象，再让摘要变得可验证**。八步顺序的实质是：授权边界决定渠道（步骤 1）、四段预算决定能不能定位问题（步骤 2）、事件簇决定用户是否还愿意看（步骤 3）、标签体系决定能不能量误报（步骤 4）、片段映射决定摘要能不能被验证（步骤 6）、频控与断供告警决定这条链路是否"活着"（步骤 7、8）。四块成本里最有杠杆的是**"先归簇再摘要"**（摘要量通常只有素材量的百分之十几）与**频控**（被挡下的条数同时是省下的钱与守住的信任）。

> 💡 **思考锚点**：算一下你（或你想做的）链路的"摘要条数 ÷ 素材条数"。如果这个比例大于 0.5，说明筛选层几乎不存在——那么下一步不是换更强的摘要模型，而是补**事件簇与优先级**；此外，挑一条你最近发出的情报，试着只凭摘要本身回答"这条哪来的、数字对不对"，答不上来就说明引用回指还没落地。你打算先补哪一块？
