## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

1. **机制变了**：抽取从"模板 / 序列标注"变成**生成式抽取 + 原文回指 + 字段级置信度**；起草从"套模板"变成"生成 + 人审"；执行从"单个 RPA 脚本"变成"状态机 + 可补偿动作"。**这类变化影响架构决策。**
2. **接口与规范变了**：电子发票与电子凭证的格式规范、办公套件的扩展接口、身份与单点登录协议在演进【公开：以各自规范与文档当前版本为准】。**这类变化影响集成与合规。**
3. **只多了产品**：同一套能力换包装。**只在选型表里体现。**

判别方法仍是那一句：**"换一家厂商，这条结论还成立吗？"**

### 5.2 判据与分级

沿用三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定、可预期**。

| 演进方向 | 级别 | 机制变了什么 | 判据落点（可否自行核验） |
| --- | --- | --- | --- |
| 生成式文档抽取（带原文回指） | **L2** | 从模板 / 标注模型变成"生成 + 位置回指 + 置信度" | ① 成立（文档理解类能力条目可核）；② **核不到**（准确率数据几乎都来自建设方）；③ 部分成立（Schema 表达各家不同） |
| 字段级置信度与低置信转人工 | **L2** | 阈值从"整篇"细化到"字段"，人工只核对不确定的部分 | ① 成立；② 核不到；③ 成立 |
| 流程状态机 + 可补偿动作 | **L2** | 从"脚本串行执行"变成"显式状态与补偿" | ① 成立（持久化工作流引擎的文档条目）；② 核不到（补偿动作表是业务特有的，无通行清单）；③ 成立 |
| 短期凭证与按实例授权 | **L2** | 凭证从"长期服务账号"变成"按流程实例、短期、最小权限" | ① 成立（身份与令牌相关文档条目）；② 核不到；③ 成立 |
| RPA 与模型分工（理解 / 执行分离） | **L2** | 从"模型直接操作界面"变成"模型给判断、RPA 做执行" | ① 成立；② 核不到；③ 部分成立（RPA 工具接口差异大） |
| 受限端到端办公 Agent | **L3** | 从"多步人工点击"到"一句话办完" | ① 只有演示与自研；② 核不到；③ 不成立（**责任无法归属**） |
| 全自主审批决策 | **L3** | 由模型决定"批不批" | ① 只有演示；② 核不到；③ 不成立（**合规与责任均无通行做法**） |

**本节没有一行达到 L1**——卡点同样在 ②：**办公自动化的效果数据（字段准确率、介入率、返工率）几乎都来自建设方**，且**强依赖于各家自己的单据形态与流程**，跨组织不可比。因此这一支应按"**机制可验证、效果必须自测**"理解。

### 5.3 演进方向逐条拆解（核心节）

下面五个单元（§5.3.1–§5.3.5）按**同一套结构**写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**（个别单元另列判定方法与适用条件）。它们各自的级别见 §5.2 的那张表——**表给结论，本节给机制**；只写收益不写代价的方向，在评审时应被直接打回。§5.3.6 把同一套结构反过来用：遇到本节没列到的新名词，用那三步自己判。

#### 5.3.1 生成式抽取：把"模板维护"换成"回指与阈值"

- **旧做法与它的卡点**：抽取靠"为每种版式写模板 / 规则"，或靠序列标注模型（主文件 §1.4 的"OCR + 模板阶段（2018–2022）"与"抽取模型阶段（2022–2024）"）。卡点不在准确率，而在**模板的供给速度**：版式由外部（供应商、税局、客户）决定，模板数随供应商数增长，而**新增一个版式就要一次人工对齐**——于是"抽得准"这件事的维护成本随外部变化线性上升，而外部变化不受你控制。

- **AI 改变了什么机制**：抽取从"按版式匹配"换成"**按文档理解生成结构化字段**"，并把两样东西变成一等产出——**字段级置信度**与**原文位置**（§3.2.2 的结构）。用 §5.3.6 第一步的话说，这是**替换了一个部件的实现**：模板匹配换成"生成 + 回指 + 阈值"。

- **由此得到的**：因为不再需要为每种版式写模板，**版式变化的边际成本从"一次人工对齐"降到"观察曲线是否漂移"**；又因为每个字段带原文位置，**人工核对第一次可以做到"一键跳原文"**——而这是介入率能被压住的前提（§3.2.2 代价一栏：没有原文位置，转人工会退化成橡皮图章）。§4.2（3）把它的操作写成了三条：按置信度分桶统计抽错率、画出「阈值 → 介入率 / 漏出率」两条曲线、取业务可接受错误率对应的最小阈值。

- **由此付出的**：**新增两项基础设施职责**——**原文位置的存储与呈现**（供人工核对）与**阈值曲线的维护**（阈值成为质量与成本的调节旋钮）；此外**判错的方式变了**：生成式抽取的误差不会以"抽不到"的形式出现，而是以"给了一个看起来合理的值"的形式出现，所以**必须靠曲线与抽检去发现，而不是靠报错**。这两项是"换生成式抽取"的真实代价，比换模型重要。**还有一条不能省的边界**：生成式抽取**必然**有误差，因此"低置信转人工"与"高代价字段用更严阈值"**不能省**——省掉它们，等于把错误直接写进业务系统。

- **证据与来源**：【公开】文档理解与 OCR 这一侧在书内他处有具名实现可对照——`04-data-assetization/01-multimodal-db` 的主文件把 Tesseract / PaddleOCR / EasyOCR 列在"OCR"一行、把 LayoutLMv3 列在"文档理解"一行，其 §4 另把 PyMuPDF / Unstructured 记作文档结构化；`10-industry-agent/01-multimodal-ai` 的 §4 给出"版面模型给坐标、模型做理解与组织、关键字段取值取自确定性路径"的组合。【经验】抽取准确率的公开数字几乎都来自建设方，且与单据形态强相关（§5.3.6 第二步），本节不引任何一家的准确率——判定入口是你自己的字段级曲线（§4.2（3））。

- **成熟度**：**L2**。① 成立（文档理解类能力是成熟且有正式文档条目的能力）；**② 核不到**（准确率数据几乎都来自建设方，且跨组织不可比）；③ 部分成立（各家的 Schema 表达不同，没有统一的抽取结果交换格式）。

- **判定方法**：字段一侧的动作同 §3.2.2 与 §6.3 的自测（按字段统计"高置信自动通过 / 低置信转人工"的比例与核对通过率）；本方向另加一条——画一次「阈值 → 介入率」与「阈值 → 漏出率」，**画不出这两条线，说明阈值还是拍脑袋定的**；再随便挑一个低置信字段，看能否一键跳回原文那一块。

#### 5.3.2 状态机与补偿：从"能跑"到"错了能退"

- **旧做法与它的卡点**：流程靠"脚本串行执行"或散落的 `if-else` 推进；跨系统写入的第一版假设是"要么全成功、要么全失败"。卡点有两处：**其一，卡住是看不见的**——单据停在"等审批"这个状态时它只是"没有下一步"，在统计上不显示为失败（§3.2.5 的机制）；**其二，部分成功是常态而不是意外**——把它当异常分支处理，实现里就会留下"假装不会发生"的路径（§3.2.6 的机制）。

- **AI 改变了什么机制**：**机制与 AI 无关**——显式状态机、超时、幂等、补偿这套东西在生成式模型出现之前就是分布式系统与工作流引擎的既有机制（具名落点见下面的"证据与来源"）。**它仍列在本节，是因为办公智能体把这条链路的写入面扩大了**：模型一旦能读材料、填字段、给判断，可以自动推进的步骤就变多，而**每多一个可写动作，就多一格需要写"失败怎么退"的位置**（§5.3.6 末尾的第一条准入条件）。换句话说，AI 不产生这个机制，但 AI 使它的缺失从"少见"变成"常见"——所以在本节里它属"必做项"，而不是"该不该跟的新方向"。

- **由此得到的**：因为流程被显式建模，**"每个状态都有超时"变成一条可检查的约束**，于是"有多少单据卡在哪一步"第一次可查（§3.2.5）；又因为每个可写动作被要求回答"怎么退"，**不可逆动作不能放在链路中间**成了一条设计期约束，而不是运行期的补丁（§4.2（5）的 `no_compensation` 清单就是它的落地物）。

- **由此付出的**：**状态机建模成本**（流程图与实现要对齐，一旦分叉，"卡在哪一步"的统计就不再可信）；**补偿动作表要逐个业务系统定义**——没有通用的"回滚 API"，财务上"退"往往是一条新单据（红字单）而不是撤销，**因此这份表是一份业务文档而不是技术组件**，需要财务与业务共同确认（§3.2.6 代价一栏）。**还有一条边界**：补偿不是"撤销"，它本身也要留痕（用 `inverse_of` 指向被补偿的动作，§4.5 模板 2），否则事后无法证明已退回。

- **证据与来源**：【公开】这一侧的具名落点在书内他处——`03-data-stack/12-scheduler` 的 §7 选型清单把 Camunda、Flowable 一类列为"面向业务流程与人工审批节点"的通用工作流引擎（并说明它们不是数据批次编排），`03-data-stack/07-architecture-decisions` 的 §8 第四层"云原生调度演进"把 Temporal 记为"分布式工作流引擎，高复杂度 + 多步骤场景首选"；`01-modeling/01-business-process-modeling` 的主文件把 BPMN 流程建模定位为"过程执行"，判据是"这张图会不会被下游执行或审计引用"，工具侧给出 BPMN.io / bpmn-js / Camunda Modeler。**这些引擎与建模工具落到本主题的就是 §3.2.5 的骨架与 §4.2（4）的状态配置那一格**——引擎承担状态、超时与转交，BPMN 图供下游执行与审计引用；它们不是 §3 的新模式。**这一行的 ② 核不到——补偿动作表是业务特有的，没有通行清单**（§5.2 表里这一行的 ② 栏即此）。（来源：`03-data-stack/12-scheduler/12-scheduler-section-7-sec7.md` §7；`03-data-stack/07-architecture-decisions/07-architecture-decisions-section-8-sec8.md` §8 第四层；`01-modeling/01-business-process-modeling/01-business-process-modeling.md` BPMN 行；本主题 §4.2（4））

- **成熟度**：**L2**。① 成立（持久化工作流引擎的文档条目可核）；**② 核不到**（无通行的补偿动作清单，也就无第三方可对照的生产案例）；③ 成立（状态机与超时是通用设施，接口稳定）。

- **什么时候值得做**：链路里出现"等待与二次确认"，或第一次出现"部分成功"时——**这两个信号比业务量更早告诉你该上骨架**（§3.6 的通用判据：跃迁的触发点是某个失效形态第一次出现，而不是量变大）。

- **什么时候不值得做**：流程是一次性的、只读的（查一下、写个草稿）时——骨架的收益有限，先按 §3.2.1 的轻形态上线。

#### 5.3.3 短期凭证与按实例授权：把爆炸半径压到一张单据

- **旧做法与它的卡点**：写入业务系统用**长期服务账号**——按服务发放、长期有效、scope 通常给到"能写这个系统的数据"。卡点在于**爆炸半径**：一次凭证泄漏（或一次误操作）的影响面是"所有流程、所有单据"，而不是"某一张单据的一个时间窗"（§7.3.2 把它写成"凭证的粒度决定了爆炸半径"）。

- **AI 改变了什么机制**：**机制与 AI 无关**——按实例签发短期凭证是身份与授权体系的既有做法（具名落点见"证据与来源"）。**它列在本节的理由与 §5.3.2 同源**：办公智能体把"写入"从少数几个后台服务扩到"每个流程实例都在写"，于是凭证的**持有者数量与生命周期**都发生了量级变化——**服务账号时代"服务可信"这个假设不再成立**，因为写入的主体变成了一堆短命的流程实例。

- **由此得到的**：安全模型从"服务可信"变成"实例可信"——**一次凭证泄漏的影响面从"所有单据"缩到"一张单据的窗口期"**；scope 与流程步骤对齐之后，"越权调用"第一次可以被演练验证（用超 scope 的凭证调用，看是否被拒并留痕，§4.7 的越权演练）。

- **由此付出的**：**要内部身份体系支持细粒度签发**（这正是 §7.3.2 说的"自建族可控、产品族取决于它是否支持细粒度授权"那条差异）；凭证的 **scope 必须与流程步骤对齐**（写 ERP 的凭证不该能读人事），于是"流程定义变了、授权也要跟着变"成为一项持续工作；还有一条：凭证短期化之后，**重试与补偿路径需要重新取凭证**，这会与 §3.2.6 的失败分类交互。

- **证据与来源**：【公开】**"服务身份应短期、最小权限、可即时吊销"这一族做法在书内他处有具名落点**：`11-cross-cutting/07-audit-and-compliance` 的 §8 把 SPIFFE / SPIRE 记作"云原生时代的 Kerberos"——基于非对称密钥 + 短期证书、避免 KDC 单点，同节另把 OIDC / SAML 记作跨云身份联邦的做法；`04-data-assetization/07-data-api-gateway` 的 §4 把"集成身份系统（OAuth 2.0 / JWT / SSO）"与"把『你是谁』和『你能看哪些行、哪些列』拆成两件事"写成一条实现原则。**但按"按流程实例签发"这一具体粒度，② 仍核不到**：公开材料里没有第三方给出的、可对照的影响面数据。

- **成熟度**：**L2**。① 成立（身份与令牌相关文档条目可核）；**② 核不到**（无第三方生产案例数据）；③ 成立（令牌与授权是通用设施，接口稳定）。

#### 5.3.4 RPA 与模型分工：把脆弱性收敛到一处

- **旧做法与它的卡点**：两条极端路线各有各的卡点。**纯 RPA**：按录制步骤 / 坐标回放，确定性高但**界面一改就断**，维护成本随流程数线性上升（主文件 §1.4 的"RPA 阶段（2015–2020）"）。**让模型直接操作界面**（识别屏幕 + 自主点击）：对界面变化更耐受，但**脆弱性与不可归因叠加**——失败时无法区分"理解错"与"执行错"，模型的点击也无法用脚本复现，审计与回归都做不了。

- **AI 改变了什么机制**：**按"脆弱性来源"把一件事拆成两件**——模型负责"读与判断"（读界面 / 文档的语义、判断该点哪里、异常时给出解释），RPA / 脚本负责"点与写"（确定性执行），界面变化时**由模型给出变更建议而不是直接改**（§3.2.7 的结构）。用 §5.3.6 第一步的话说，这是**替换了一个动作的落点**：界面变化时的决定权从"模型的执行动作"移到"人确认的变更动作"。

- **由此得到的**：因为两类脆弱来自不同原因——RPA 的脆弱来自**界面变化**（外部原因，可批量修复），模型的脆弱来自**理解偏差**（概率原因，不可批量修复）——**修复成本从"每次都要人看"降到"界面变了批量改选择器"**；而模型的价值变成"提早告诉你界面变了"（它能量出"这里点不到"）；同时**两类错误第一次可以分开观测**，后续优化才有了靶点（§3.2.7 的判据）。

- **由此付出的**：**混合链路的调试更复杂**（要区分"理解错"与"执行错"，也就要求两类失败各自的日志与计数）；**界面变化仍需人工确认修法**——"只给建议"的理由是责任：**模型直接改选择器意味着一次误判会静默地让所有同类操作错位**，而人确认把错误暴露在变更时刻而不是执行时刻（§3.2.7 代价一栏）；此外 RPA 一侧仍需**变更探测**（每天对关键页面做一次元素存在性检查）才能把改版从"运行时故障"变成"提前告警"。**边界**：不要让模型直接操作系统界面（脆弱且难归因）。

- **证据与来源**：【公开】这一分工在书内他处有具名对照——`10-industry-agent/01-multimodal-ai` 的 §8 把 RPA 与 Computer Use Agent 的差别写成"RPA 是**预定义脚本**（按录制步骤执行）、Computer Use Agent 是**自主决策**（按目标动态规划）"，并记下"当前稳定性不如 RPA，生产落地仍以 RPA 为主"；同主题的 §4 把文档链路的同一分工写成"确定性转写 + 模型理解与组织，**关键字段的最终取值取自确定性路径**"；本主题 §4.3 工具链表把"API 直连优先，无 API 时走 RPA"写成选型判据。【经验】RPA 产品的接口差异大、公开材料几乎都是厂商自述，本节不点名任何一家产品；判定入口是"两类错误能否分开计数"这条判据。

- **成熟度**：**L2**。① 成立（RPA 与界面自动化的能力条目可核）；**② 核不到**（无第三方给出的分工效果数据）；③ 部分成立（RPA 工具接口差异大，"读"与"写"之间没有统一接口）。

- **判定方法**：同 §3.2.7 的判定方法（让一个界面元素消失，看失败是否可归因；再确认两类错误能否分开计数）。

#### 5.3.5 受限端到端与全自主审批：为什么停在 L3

- **旧做法与它的卡点**：办公动作原本由人"多步点击"完成——打开系统、找到单据、填字段、提交。卡点不是"慢"，而是**每一步都在人的判断下发生，因此每一步的责任都有人承担**；要提升效率就得减少人，而减少人就直接改动了责任结构。

- **AI 改变了什么机制**：从"多步人工点击"变成"一句话办完"——**动作的发起者从人变成模型**，而**动作集由注册表（白名单）定义、模型只能选择其中一项**（§3.2.8 的结构）。这两个方向共用一条机制：**受限端到端**是把发起者换掉而保留边界，**全自主审批**是进一步把"批不批"也交给模型——后者换掉的不只是发起者，而是**签字这个动作本身**。

- **由此得到的**：因为边界由执行器强制而不是由提示词约束，**受限端到端是可做的**——"不允许做的事"从"可能发生"变成"不可能发生但会明确失败"（§3.2.8 的机制）；而它可做的前提是**四条同时满足**：动作白名单、全链路留痕（输入 / 判断 / 动作三段可回放）、不可逆动作前置审批、幂等与补偿齐备——缺任何一条，它都只能作为演示（§8.7 的答案框架）。

- **由此付出的**：**受限端到端**：白名单之外的请求会失败，因此必须给出"为什么不能做"的清晰反馈——没有它时用户会反复尝试，而"模型做不到"与"系统不允许"在用户看来是同一件事（§3.2.8 代价一栏）；回放与留痕的存储成本上升。**全自主审批**：它卡在"合规与责任归属"——**批与不批是责任行为，不是技术行为**，没有通行的做法可以照抄。

- **证据与来源**：【经验】两个方向都只有演示与自研材料，**核不到第三方非厂商的生产案例**——这正是它们在 §5.2 表里停在 L3 的原因（判据 ② 与 ③ 都不成立）。**给读者的动作**：把"自主"限定在"理解 + 起草 + 建议"，签字权保留给人；要评估某个端到端方案，用"三段留痕可回放 + 动作集来自注册表"这两样东西来判断，而不是看它演示得多流畅。

- **成熟度**：**L3**。① 只有演示与自研（本节不给任何产品名）；**② 核不到**；③ 不成立——**受限端到端卡在"责任无法归属"，全自主审批卡在"合规与责任均无通行做法"**。


#### 5.3.6 一条可复用的操作：怎么判断某条演进方向该不该跟

上面的分级是结论，下面把它变成三步操作——**以后遇到本节没列到的新名词，用这三步自己判**：

**第一步：定位它替换掉了哪个部件。** 写不出"它替换的是谁"，就说明它没有机制内容。**本主题合法的三种答案**：替换了一个**部件的实现**（如抽取从"模板匹配"换成"生成 + 回指 + 阈值"）、替换了一个**字段的归属**（如审批记录从"结果"变成"输入快照 + 依据"）、替换了一个**动作的落点**（如凭证从"按服务发放"变成"按流程实例发放"）。判不出来 → 归第 3 类，只改选型表。

**第二步：查三条判据的落点，尤其是②。** ① 与 ③ 通常容易满足，**真正的分水岭是 ②——第三方非厂商的生产案例**。本主题的卡点有一条特殊的形状：**办公自动化的效果数据（介入率、返工率、错单率）几乎全部由建设方自述，而且它们高度依赖各自的组织流程与单据分布**——同一个模型在 A 公司的报销单上很好，在 B 公司的合同条款上可能毫无优势。**因此本主题里，"别人的数字"最不可移植。**

**第三步：按级别决定动作，且动作要带退出条件。**

| 级别 | 动作 | 必须同时写下的东西 |
| --- | --- | --- |
| L1 | 可以直接进架构约束 | ——（本主题暂无） |
| L2 | 排进试点，**但不进架构约束** | **退出条件**（什么观测结果出现就停）；本主题还要加一条：**它是否让"退回能力"变差** |
| L3 | 只做最小版本，不做技术选型 | 最小版本是什么（如全自主审批只做"生成建议 + 人确认 + 留痕"） |

**本主题特有的准入条件有两条**：① **任何提升自动化程度的方向，先回答"它把哪个动作变成了可写"**——**每多一个可写动作，就多一格需要写"失败怎么退"的位置**（§6.4 的红线检查）；② **任何减少人工环节的方向，先回答"少掉的那个人原本在拦什么"**——办公场景里的人工环节常常是**偶然形成但真实存在的闸门**，把它去掉之前要先确认那个风险已经被系统承担。

### 5.5 被过度宣传的部分

1. **"全自动办公"**：宣称"单据自己流转、审批自己完成"。**可核验的形态**是"理解 + 起草 + 建议自动化，签字保留给人"；全自主审批在合规与责任上无通行做法。
2. **"抽取准确率 99%"**：这个数字通常来自**自家单据分布**，换一个供应商版式就会变；可核验的形态是**你自己的字段级曲线**。
3. **"RPA 已死，全用 Agent"**：确定性操作交给概率模型，**是提高而非降低维护成本**——分工才是正解（§3.2.7）。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 被证伪的信号 |
| --- | --- |
| "字段级置信度 + 低置信转人工"会成为单据类抽取的默认形态 | 两年后主流实现仍用整篇阈值且无转人工规则 |
| "补偿动作表"会成为流程自动化的标准交付物 | 两年后实现仍普遍把不可逆动作放在链路中间 |
| 短期凭证（按流程实例）会成为跨系统写入的默认做法 | 主流实现仍用长期服务账号写入业务系统 |
| 端到端验收指标会从"准确率"转向"介入率 + 返工率" | 采购与验收仍只看抽取准确率 |

**这四条全部是【经验】档**：它们是对机制与采购行为的判断，无具名出处、无推导链——**请按"可被证伪"使用，而不是当结论**。

### 5.7 给架构师的行动建议

1. **今年就该做**：流程与红线清单 + 字段级阈值 + 幂等与补偿动作表。三件事不依赖任何前沿判断。
2. **可以试点**：生成式抽取（先选一类单据，带原文回指与更严阈值）；审批工单的输入快照；短期凭证。
3. **先别投**：全自主审批与"一句话办完且无需确认"的端到端——责任与合规无通行做法。
4. **无论哪条**：把**介入率与返工率**作为两条日常指标——前者说明自动化程度，后者说明自动化质量。

### 5.8 小结

> 本节小结：AI 时代对办公自动化的改变**有两条是机制性的**——**抽取从模板变成"生成 + 回指 + 字段级置信度"**（于是阈值曲线与原文位置成为基础设施）、**流程从脚本变成"状态机 + 可补偿动作"**（于是可补偿性成为设计期约束）；其余方向（短期凭证、RPA 与模型分工）都是在这两条之上的安全与工程加固。这一支没有一行达到 L1，卡点全在"第三方非厂商生产案例"；因此请按"**机制可验证、效果必须自测**"理解它——**效果只能靠你自己的字段曲线与端到端两个指标去量**。

> 💡 **思考锚点**：如果你的抽取模型明天换一代（更强），你的**阈值表**需要重画吗？如果需要，说明你的"质量—成本旋钮"依赖模型；如果不需要，说明阈值是按字段代价定的（正确做法）。再问一个：你现在的**补偿动作表**有几条？答"零条"意味着不可逆动作在链路里没有任何退路——你打算先补哪一张表？
