## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自建 / 买 RPA / 买办公套件能力 / 用通用助手改造"打分有三个结构性问题：① 同一列在不同处境下方向相反（"可定制流程"对多变的组织是必需、对三条固定流程是浪费）；② 打分表隐含"这些选项互斥"，而真实形态常是组合（既有工作流引擎 + 自建理解层）；③ 最关键的判据（动作可逆性、数据敏感级、留痕要求）**不是可打分的维度，而是门槛**——不满足直接出局。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 动作可逆性 | 要写的动作能不能撤？有没有补偿动作？ | 不可逆动作决定闸门位置与"哪些步骤不能自动"（**门槛不是权重**） |
| 数据敏感级 | 涉及人事 / 财务 / 合同吗？能否出域？ | 不能出域 → 托管方案出局，且留痕强度要升 |
| 留痕与责任 | 需要"不可否认"到什么程度？谁签字？ | 决定审批工单是否要带输入快照、是否必须记录理由 |
| 确定性骨架归属 | 状态机、超时、重试、补偿由谁实现？ | 这些**必须零概率**——交给模型就是错的架构 |
| 执行入口 | 有无 API？只能走界面吗？ | 无 API → 必须引入 RPA 或界面自动化，并由它承担确定性执行 |
| 承接能力 | 谁维护 Schema、阈值曲线与补偿动作表（按 0.5–1 人年的常备投入量级估算【经验】）？ | 这一支的成本是**长期人力**，不是首版实现 |

> **读法**：先用第 1 条筛掉"把不可逆动作自动化"的方案；用第 2 条筛掉不可行的部署形态；用第 3、4 条筛掉"骨架不稳"的方案；最后用第 5、6 条在剩下的里选——**第 4 条最容易被跳过，也是"自动化越做越不可控"的根因**。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 自建端到端 | 全链路自持 | 解析 + 抽取 + 状态机 + 执行全部自建 | 流程多、要求高 | 长期人力；首版慢 |
| 自建理解层 + 既有工作流引擎 | 骨架复用 | 引擎做状态 / 超时 / 重试，模型做理解与起草 | 已有引擎的组织（多数企业） | 引擎与模型的接缝要长期维护 |
| 自建 + RPA 混合 | 应对无 API | 模型理解、RPA 执行（理解 / 执行分离） | 遗留系统多 | 两类错误的可观测性要额外建设 |
| 商业 RPA 平台 + 自建 LLM 层 | 买执行、自建理解 | RPA 平台负责界面执行，LLM 层负责读与判断 | 想省执行器维护 | 平台与 LLM 层的集成与升级耦合 |
| 办公套件自带智能能力 | 买成品 | 直接使用办公 / ERP 套件里的智能抽取与流程能力 | 流程标准、不想自建 | 字段与阈值由产品定；定制受边界限制 |
| 通用对话助手改造 | 最轻 | 把通用助手接到文档索引与表单上 | 只想"能查会写" | **缺执行、缺留痕、缺补偿**，做不了流程 |

**这六个候选其实分三族**：**自建族**（自建端到端、自建理解层 + 既有工作流引擎、自建 + RPA 混合）——骨架与理解都在自己手里，代价是长期人力；**产品族**（商业 RPA 平台 + 自建 LLM 层、办公套件自带智能能力）——拿到成品执行器或成品能力，代价是边界与口径受产品定；**改造族**（通用对话助手改造）——最省事，代价是**缺少流程所需的骨架**（状态机、幂等、补偿、留痕）。

**族内可替换，跨族不可换**：自建族内部换的是"执行器与引擎"；从自建族换到产品族，等于**把流程骨架与留痕口径一起交出去**——那不是技术迁移，是责任界面的转移。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 确定性骨架的归属：谁保证"零概率"

**机制是什么**：流程的推进、超时、重试、幂等、补偿这五件事**必须零概率**；它们由代码 / 引擎保证，还是由模型"尽力而为"，决定系统是否可控。

**它在各候选中的实现差异**：自建族可把骨架固化在状态机里；产品族的骨架由产品定义（**面板效应**：产品不给你细粒度超时与补偿，你就做不到）；改造族**没有骨架**（只有对话流）。

**由此必然导出的性质**：因为**概率性判断无法保证"一定不会漏"**，所以任何把骨架交给模型的方案都会出现"偶发跳步 / 偶发重复"——这类问题**难复现、难定位**，且往往在月末对账时才暴露。

**失效条件**：当流程确实是"一次性的、无写操作的"（如查一下、写个草稿）时，骨架的收益有限；一旦出现多步与写操作，骨架就是必需。

#### 7.3.2 执行入口与凭证归属：爆炸半径

**机制是什么**：写入业务系统用**长期服务账号**还是**按流程实例的短期凭证**，决定一次泄漏或一次误操作的影响面。

**它在各候选中的实现差异**：自建族可控（可按实例签发）；产品族取决于它是否支持细粒度授权（有的只支持"一个连接器一个账号"）；改造族通常**根本没有写入能力**（也算一种"安全"）。

**由此必然导出的性质**：因为**凭证的粒度决定了爆炸半径**（长期账号 → 全部单据；实例凭证 → 一张单据的窗口期），所以凭证归属是**安全设计的核心**，而不是集成细节。

**失效条件**：当写入量极小、且目标系统的权限模型本身很粗（例如只分"读写"）时，细粒度凭证的收益有限；但仍应**按最小权限**给账号。

#### 7.3.3 可补偿性：错了能不能退

**机制是什么**：每个可写动作有无**显式逆向动作**，以及不可逆动作是否被前置审批——它决定系统"出错后的代价"。

**它在各候选中的实现差异**：自建族需要**逐个业务系统定义**补偿动作（没有通用回滚接口）；产品族看是否为具体动作提供逆向能力（多数 RPA 平台只提供"重试"，不提供"冲销"）；改造族没有这一层。

**由此必然导出的性质**：因为**补偿动作是业务特有的**（财务冲销、通知更正、归档撤回），所以"可补偿性"无法靠产品解决——**它必须由懂业务的人写下来**，这也是本主题最容易被低估的工作量。

**失效条件**：只读流程不需要补偿；含写操作的流程必须有（或把该动作列入"不可逆、必须前置审批"）。

#### 7.3.4 留痕与责任：能不能认定"谁批的"

**机制是什么**：审批记录是否含**输入快照与理由**，决定事后能否还原决策依据。

**它在各候选中的实现差异**：自建族可设计工单结构（含快照与理由必填）；产品族的工单结构由产品定（**多数只记"通过 / 驳回"**）；改造族的对话记录不是合规留痕（可被编辑、且不含结构化字段）。

**由此必然导出的性质**：因为**责任认定需要"当时基于什么"，而不只是"结果是什么"**，所以留痕结构不达标的方案，会在第一次审计或第一次争议时暴露——而此时已无法回补历史。

#### 7.3.5 人放的位置：闸门（事前）还是例外处理（事后）

**机制是什么**：同一个"人"可以放在链路的两处，而这两处的**成本函数形状完全不同**：**闸门**（每个动作都等人批，成本随动作数线性增长）与**例外处理**（只有低置信 / 命中红线的才转人，成本随异常率增长）。

**它在各候选中的实现差异**：自建与半自建方案能让"人"落在**任意位置**（因为转人工规则由你定义）；**成品平台**通常把人的位置写进了产品形态——要么是"审批节点"（事前闸门），要么是"事后复核"，而**不一定提供"按字段置信度转人工"这种细粒度**；**RPA 类方案**的人往往落在"维护选择器"上（不是业务闸门）。**这三者的成本函数形状因此不同**：闸门随量线性、例外处理随异常率、RPA 随界面变动频率。

**由此必然导出的性质**：因为**办公场景的动作量通常很大而异常率很低**，所以"闸门"模式在量上来之后必然变成瓶颈（人力 `n > λ/μ`，§3.2.5）；**而"例外处理"模式的质量完全取决于"异常判据准不准"**——判据过宽则退化成闸门（全都转人工），过窄则异常静默通过。**因此选型的实质不是"要不要人"，而是"你的异常判据能不能做得准"**——做得准，人就可以事后出现；做不准，就只能事前拦。

**失效条件**：当"介入率"持续上升而"漏出率"没有下降时，说明异常判据失效（它把正常单据也判成异常）；此时**正确的动作不是加人，而是回到字段级阈值去重标**（§6.3 的介入率—漏出率曲线）。**反过来的失效形态更危险**：介入率下降、漏出率也"下降"——后者往往不是真的改好了，而是判据被放宽了，而放宽的后果要等到某一张错单进了不可逆步骤才显现。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| 自建族 | 人力（Schema / 阈值 / 补偿表维护）+ 解析抽取成本 | 补偿动作表的持续补充、单据版式变化的适配、留痕存储 | 随单据类型数与流程数增长 |
| 产品族 | 许可 / 连接器 / 调用计费 | 定制受边界限制导致的额外人工环节、升级行为变更 | 随流程数与连接器数线性增长 |
| 改造族 | 最省的前期投入 | 无法承载写操作 → 团队另建流程（重复投入） | 随诉求升级而被迫重做 |

**成本函数的三条判据**：① **自建族是"台阶形"**（人力 + 固定设施，不随单据量变），单据量大时最省；② **产品族是"线性"**（许可 / 连接器 / 调用量），单据量小时最省；③ **改造族前期最省但天花板最低**——省下的钱通常以"另建流程与人工补录"的形式花回来。

### 7.5 决策树（每个分支都要有阈值依据）

1. **流程里有没有不可逆的写动作（发款 / 对外发送 / 入账）？**
   - 有 → **必须有人审闸门 + 补偿动作表**；并要求方案支持细粒度授权与工单留痕 → **改造族出局**；进入第 2 问。
   - 没有（只读 / 可完全回滚）→ 进入第 3 问。
2. **有无 API 可调？**
   - 有 → **自建理解层 + 既有工作流引擎**（多数企业的现实解）；进入第 4 问。
   - 没有 → **自建 + RPA 混合**（理解 / 执行分离）。
3. **单据量与版式变化频率？（按"每日单据数"与"每月新增版式数"量两个数）**
   - 量大（每日**千级**以上【经验：以"人工录入是否成为瓶颈"为分界】）或版式频繁变化 → 进入第 2 问（倾向自建族）。
   - 量小且版式稳定 → **办公套件自带能力**或**产品族**最省。
4. **有没有人能长期维护 Schema、阈值曲线与补偿动作表（按 0.5–1 人年的常备投入量级估算【经验】）？**
   - 有 → **自建端到端**（控制力最强）。
   - 没有 → **商业 RPA 平台 + 自建 LLM 层**，或**办公套件自带能力**（接受"口径由产品定"）。

**阈值的诚实说明**：上表的"千级/日"与"0.5–1 人年"都是【经验】档——用来区分"这一档"与"那一档"，请用你自己的量级与排期校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 财务 / 合同类（不可逆写动作多） | 自建理解层 + 既有引擎（+ 补偿表） | 自建端到端 | 产品族的工单与授权粒度常不够 |
| 遗留系统多、只能走界面 | 自建 + RPA 混合 | 商业 RPA 平台 + 自建 LLM 层 | 让模型直接操作界面脆弱且难归因 |
| 单据量大、版式频繁变化 | 自建端到端 | 自建理解层 + 引擎 | 产品族的字段与阈值不可控 |
| 单据量小、流程标准 | 办公套件自带能力 | 商业 RPA 平台 | 自建在量小时不划算 |
| 只想"能查会写" | 通用对话助手 + 文档索引 | 办公套件自带能力 | 若上了写操作则骨架缺失（应升级方案） |
| 多部门共用、要求统一留痕 | 自建端到端（统一工单与留痕） | 产品族 + 自建留痕层 | 各部门各自买产品 → 留痕口径分裂 |

**组合的两条次序原则**：① **先把红线、字段代价与补偿表立起来，再选执行器**——执行器可替换，红线与补偿表是资产；② **先把工单留痕结构定下来，再谈自动化程度**——留痕结构不达标，自动化程度越高越危险。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 改造族 → 自建 / 产品族 | 需要写操作与留痕 | 补状态机、幂等、补偿、工单与授权 | 以月计【经验】 |
| 产品族 → 自建族 | 工单 / 授权粒度不足、阈值不可控 | 重建骨架与留痕口径；**历史工单不可迁移** | **以季度计**【经验】 |
| RPA 直接操界面 → 混合 | 界面一变全断 | 拆出理解层与执行层；补两类错误的观测 | 以月计【经验】 |
| 长期账号 → 实例凭证 | 一次泄漏影响面过大 | 接身份体系、按实例签发、补越权演练 | 以月计【经验】 |
| 无补偿表 → 有补偿表 | 部分成功退不回 | 逐个业务系统定义逆向动作并演练 | 以月计【经验】，**业务侧工作量占大头** |

**一条硬结论**：六条路里最贵的是**"把骨架与留痕交出去之后的收回"**——它不只是技术搬迁，还包括口径重建与**无法迁移的历史记录**。**所以第 1、3、4 条判据（可逆性、留痕与责任、骨架归属）必须在第一版就判对。**

### 7.8 小结

> 本节小结：六个候选之间的差异，最终都能归到三问——**确定性骨架由谁实现**（状态机 / 超时 / 幂等 / 补偿）、**凭证的粒度有多大**（决定爆炸半径）、**审批工单留的是什么**（决定责任能否认定）。三问决定了它们的成本曲线形状（自建台阶、产品线性、改造前期最省但天花板最低）与迁移代价（跨族迁移以季度计，同族以月计）。**选型顺序不可颠倒**：先用"有没有不可逆写动作"筛掉不可行，再用"骨架与留痕归属"筛掉不稳的方案，最后用"承接能力"在剩下的里选——**把"谁维护补偿表"当权重而不是门槛，就是"上线三个月后不敢再扩"的根因**。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次"门槛检查"（不是打分）：动作可逆性、数据敏感级、留痕与责任、确定性骨架归属、执行入口、承接能力——哪一条是"不满足"而不是"分数低"？那一条就是你明年最可能被迫迁移的方向；而你今天的补救，是否还落在"同族迁移（以月计）"这一格里？
