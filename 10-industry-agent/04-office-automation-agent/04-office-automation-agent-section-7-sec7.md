## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自建 / 买 RPA / 买办公套件能力 / 用通用助手改造"打分有三个结构性问题：① 同一列在不同处境下方向相反（"可定制流程"对多变的组织是必需、对三条固定流程是浪费）；② 打分表隐含"这些选项互斥"，而真实形态常是组合（既有工作流引擎 + 自建理解层）；③ 最关键的判据（动作可逆性、数据敏感级、承接能力）**不是可打分的维度，而是门槛**——不满足直接出局。

比"列的处境性"更实质的问题在**列的构成**上。给这四个选项打分，可用的列无非"可定制程度""智能程度""留痕完备度""上手速度"，而它们**方向并不一致**——"留痕完备度"这一列其实就是 §7.3.4 表里"工单里记什么"的那组字段：字段越多、审批越慢，在只求快的链路上是负担，在"审计要逐单举证"的链路上却是硬约束（§3.2.1 与 §3.2.5 就是这两种链路的对照）。等权相加时，**"总分高"既可能是留痕做得好，也可能是留痕做得省**，两种相反的处境会落在同一个分数上。更要紧的是，这几列全是"**候选的属性**"，没有一列是"**我的约束**"——约束决定候选的上界（下面六条里的第 1、2、6 条），属性只在候选之间分配名次；而"能不能"是布尔判断，把它折算成 1–5 分，等于**把一个淘汰条件降级成了一个排序因素**。这正是下面这张表不叫"评分表"的原因。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 动作可逆性 | 要写的动作能不能撤？有没有补偿动作？ | 不可逆动作决定闸门位置与"哪些步骤不能自动"（**门槛不是权重**） |
| 数据敏感级 | 涉及人事 / 财务 / 合同吗？能否出域？ | 不能出域 → 托管方案出局，且留痕强度要升 |
| 留痕与责任 | 需要"不可否认"到什么程度？谁签字？ | 决定审批工单是否要带输入快照、是否必须记录理由 |
| 确定性骨架归属 | 状态机、超时、重试、补偿由谁实现？ | 这些**必须零概率**——交给模型就是错的架构 |
| 执行入口 | 有无 API？只能走界面吗？ | 无 API → 必须引入 RPA 或界面自动化，并由它承担确定性执行 |
| 承接能力 | 谁维护 Schema、阈值曲线与补偿动作表（按 0.5–1 人年的常备投入量级估算【经验】）？ | 这一支的成本是**长期人力**，不是首版实现 |

> **读法**：先用第 1 条筛掉"把不可逆动作自动化"的方案；用第 2 条筛掉不可行的部署形态；用第 6 条筛掉"首版做得出来、第二年没人承接"的方案；最后用第 3、4、5 条在剩下的里选——**第 4 条最容易被跳过，也是"自动化越做越不可控"的根因**。

**六条里最容易被跳过的是第 4 条（确定性骨架归属）与第 6 条（承接能力）。** 第 4 条不看，就会出现"让模型负责推进流程"的方案，而它的失效形态是偶发跳步与偶发重复——**难复现、难定位，往往在月末对账时才暴露**（§7.3.1 的表给出三族的差异）。第 6 条不看，则会出现"首版做出来了、第二年没人维护 Schema 与补偿表"的局面：这一支的成本主体是**长期人力，而不是首版实现**（§6.3 把 Schema 维护成本记为随单据类型数线性增长的一项【经验】）。这两条之所以容易被跳过，是因为它们的证据都不在"方案演示"里——演示能证明"这条路走得通"，证明不了"这条路第二年还有人走"。

**使用顺序建议**：先答 1、2（能不能用在这里：不可逆动作与出域约束），再答 5（执行入口：有没有 API），最后答 3、4、6（留痕强度、骨架归属、谁来长期承接）。**第 1、2、6 条是门槛，答错的代价是重做或第二年静默失效；第 3、4、5 条是排序，答错的代价是越运维越贵。**

**关于排序**：本节给出的先后都是**机制上的先后**——办公自动化的选型里排得动的是"换一条路要动哪一格"，排不动的是"哪条路效果更好"。§7.6 那九行的"不选它的原因"列即按此写：除了"自建在量小时不划算"一行是量级权衡，其余八行写的都是机制——工单字段集由谁定（§7.3.4）、凭证粒度只到"一个连接器一个账号"（§7.3.2）、部署形态不会因你的要求而改（§7.3.6）、重建第二个权限源会产生随时间变大的差集（§6.1）。§7.8 的"关键理由（机制层面）"列同理（十二行里只有"自建会把'台阶形'的固定投入摊在太少的量上"一行是量级权衡）。**效果那一档在本主题排不了**：介入率与返工率没有第三方对照（§5.2 的 ② 栏——效果数据几乎都来自建设方，且强依赖各自的单据形态与流程）。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 自建端到端 | 全链路自持 | 解析 + 抽取 + 状态机 + 执行全部自建 | 流程多、要求高 | 长期人力；首版慢 |
| 自建理解层 + 既有工作流引擎 | 骨架复用 | 引擎做状态 / 超时 / 重试，模型做理解与起草 | 已有引擎的组织（多数企业） | 引擎与模型的接缝要长期维护 |
| 自建 + RPA 混合 | 应对无 API | 模型理解、RPA 执行（理解 / 执行分离） | 遗留系统多 | 两类错误的可观测性要额外建设 |
| 商业 RPA 平台 + 自建 LLM 层 | 买执行、自建理解 | RPA 平台负责界面执行，LLM 层负责读与判断 | 想省执行器维护 | 平台与 LLM 层的集成与升级耦合 |
| 办公套件自带智能能力 | 买成品 | 直接使用办公 / ERP 套件里的智能抽取与流程能力 | 流程标准、不想自建 | 字段与阈值由产品定；定制受边界限制 |
| 通用对话助手改造 | 最轻 | 把通用助手接到文档索引与表单上 | 只想"能查会写" | **缺执行、缺留痕、缺补偿**，做不了流程 |

**这六个候选其实分三族**：**自建族**（自建端到端、自建理解层 + 既有工作流引擎、自建 + RPA 混合）——骨架与理解都在自己手里，代价是长期人力；**产品族**（商业 RPA 平台 + 自建 LLM 层、办公套件自带智能能力）——拿到成品执行器或成品能力，代价是边界与口径受产品定；**改造族**（通用对话助手改造）——最省事，代价是**缺少流程所需的骨架**（状态机、幂等、补偿、留痕）。

**族内可替换，跨族不可换**：自建族内部换的是"执行器与引擎"；从自建族换到产品族，等于**把流程骨架与留痕口径一起交出去**——那不是技术迁移，是责任界面的转移。

族之间还有一条比"自建 / 买"更实质的分界：**状态与身份这两个权威源住在谁那里**。自建族把状态机放在自己的引擎里、把可见域接在自己的身份体系上；产品族的状态由产品的流程定义决定、可见域由产品的账号体系决定；改造族**两个都没有**（对话记录既不是状态，也不是身份）。这条分界决定了 §7.4 里哪一项是主导项——**权威源在自己手里时，账单的主导项是人力；交出去之后主导项变成许可与适配，而人力并没有消失，只是从"建骨架"挪到了"绕开骨架的边界"**（§6.2 把这件事写成"多数组织不愿为一条流程去改引擎"这样一条取舍）。

**这六行里，自建族那三行都能在书内他处找到具名的部件级对照，而产品族与改造族那三行一个都没有**——这一点必须先说清楚，否则很容易把"部件层的具名物"误读成"成品层的候选"。可对照的都是**部件**：第二行里的引擎，`03-data-stack/12-scheduler` 的 §7 把 Camunda、Flowable 一类列为"面向业务流程与人工审批节点"的通用工作流引擎（并明确它们不是数据批次编排），`03-data-stack/07-architecture-decisions` 的 §8 把 Temporal 记为分布式工作流引擎、高复杂度多步骤场景首选；建模符号一侧，`01-modeling/01-business-process-modeling` 的主文件给出 BPMN.io / bpmn-js / Camunda Modeler，并交代它们与 OMG 的 BPMN 标准的关系。解析与抽取侧，`04-data-assetization/01-multimodal-db` 把 Tesseract / PaddleOCR / EasyOCR 列在 OCR 一行、把 LayoutLMv3 列在文档理解一行，其 §4 另把 PyMuPDF / Unstructured 记作文档结构化（同一组清单本主题 §3.2.5 与 §5.1 已列过，§7.3.1 不再复述）；判定侧的确定性规则见 `09-data-intelligence-product/02-decision-intelligence` 的 §4.3 工具链与平台（DMN 决策表与 Drools DMN / Camunda DMN / IBM ODM 一类，判据是"规则由谁改、要不要逐条举证"）。**成品层则一律不具名**：商业 RPA 平台、办公套件自带的智能能力、通用对话助手这三行**没有第三方（非建设方）的具名生产案例**；本主题 §6.1–§6.3 的微软 / 钉钉 / 飞书是具名**建设方案例**，按 §6 的声明只作机制示例、不作举证（§5.2 把"RPA 与模型分工"判为 L2、③ 部分成立，理由也是这类工具接口差异大、公开材料几乎都是厂商自述）。**因此本节只说明它们的机制位置，不点产品名；评估它们时请按 §7.3 的表与 §7.5 的判据逐格自问。**【公开】（来源：`03-data-stack/12-scheduler/12-scheduler-section-7-sec7.md` §7；`03-data-stack/07-architecture-decisions/07-architecture-decisions-section-8-sec8.md` §8；`01-modeling/01-business-process-modeling/01-business-process-modeling.md` 的 BPMN 与工具行；`04-data-assetization/01-multimodal-db/01-multimodal-db.md` 工具表与其 §4；`09-data-intelligence-product/02-decision-intelligence/02-decision-intelligence-section-4-sec4.md` §4.3 工具链与平台；本主题 §5.2 与 §6.1–§6.3）

表里最后一列（主要代价）常被当成采购问题，其实它是机制问题：**你问的不是"贵不贵"，而是"代价随什么增长、而增长的那一项你有没有"**。自建族的代价随单据类型数与流程数增长（人力），产品族随流程数与连接器数增长（许可与集成），改造族的代价不随量增长，而是**在诉求升级时一次性重做**。判断方法很直接：把方案方的计价维度与 §7.4 表里"成本随什么增长"那一列并排看——**这两列一旦反向，采购就会变成长期成本陷阱**（例如计价按流程数走，而你正打算把流程数扩大一个量级）。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 确定性骨架的归属：谁保证"零概率"

**机制是什么**：流程的推进、超时、重试、幂等、补偿这五件事**必须零概率**；它们由代码 / 引擎保证，还是由模型"尽力而为"，决定系统是否可控。

**它在各候选中的实现差异**：自建族可把骨架固化在状态机里；产品族的骨架由产品定义（**面板效应**：产品不给你细粒度超时与补偿，你就做不到）；改造族**没有骨架**（只有对话流）。

| 候选族 | 骨架住在哪 | 谁决定"超时与重试"的形态 | 典型失败形态（可观测） |
| --- | --- | --- | --- |
| 自建族 | 自己的状态机 / 引擎 | 你——可细到"每一个节点" | 若把骨架写进提示词：偶发跳步、偶发重复，月末对账才暴露 |
| 产品族 | 产品的流程定义 | 产品（面板给出什么，你只能用什么） | 缺细粒度超时与补偿 → 单据长期停在某个节点，且在统计上不算失败 |
| 改造族 | 没有骨架 | 没有人决定（"下一步"每次都是一次生成） | 卡住的单据只显示为"处理中"，无超时、无告警、无统计口径 |

**由此必然导出的性质**：因为**概率性判断无法保证"一定不会漏"**，所以任何把骨架交给模型的方案都会出现"偶发跳步 / 偶发重复"——这类问题**难复现、难定位**，且往往在月末对账时才暴露。

这条差异之所以是"表现不同"而不只是"实现风格不同"，在于**它决定的是可观测性的存在与否，而不是可观测性的好坏**：状态机给出的是一个**有限、可列举**的状态集合，于是"每个状态的滞留数与耗时"是可以被统计的对象；而模型生成的"下一步"是一个**开放集合**，它没有枚举，因此**无法被统计**——"更灵活"与"看不见"在这里是同一枚硬币的两面（§6.2 把这条写成了失败教训的机制解释）。

**公开证据**：这一格的具名对照是**部件**而不是成品——引擎与建模符号的完整清单见 §7.2 的"部件级对照"（本主题 §3.2.5 与 §5.1 也已列过，本节不复述）；**这一格要说清的是它们与"零概率"的关系**：引擎把状态、超时与转交写成显式定义，BPMN 图供下游执行与审计引用（判据是这张图会不会被下游执行或审计引用），这正是"骨架不该由模型实现"的具名形态。本主题 §6.2 的钉钉一例给出了它在真实系统里的位置：流程推进、节点指派、超时与转交由平台侧流程引擎承担，Agent 只输出某个状态节点上的判断与字段。**各引擎超时与补偿的具体行为本节不引具体文档，请以各自官方文档当前版本为准；这一行的判据 ②（第三方非厂商生产案例）核不到**——办公流程的内部实现几乎不公开（§5.2 那张表的 ② 栏即此）。【公开】（来源：本主题 §7.2 的部件对照、§3.2.5 与 §5.1；`03-data-stack/12-scheduler/12-scheduler-section-7-sec7.md` §7；`03-data-stack/07-architecture-decisions/07-architecture-decisions-section-8-sec8.md` §8 第四层；`01-modeling/01-business-process-modeling/01-business-process-modeling.md` 的 BPMN 与工具行；本主题 §6.2 与 §5.2）

**失效条件**：当流程确实是"一次性的、无写操作的"（如查一下、写个草稿）时，骨架的收益有限；一旦出现多步与写操作，骨架就是必需。

#### 7.3.2 执行入口与凭证归属：爆炸半径

**机制是什么**：写入业务系统用**长期服务账号**还是**按流程实例的短期凭证**，决定一次泄漏或一次误操作的影响面。

**它在各候选中的实现差异**：自建族可控（可按实例签发）；产品族取决于它是否支持细粒度授权（有的只支持"一个连接器一个账号"）；改造族通常**根本没有写入能力**（也算一种"安全"）。

| 候选族 | 写入入口 | 凭证的持有者与生命周期 | 典型失败形态（可观测） |
| --- | --- | --- | --- |
| 自建族 | API 直连优先 | 流程实例 / 短期 / 最小 scope | 迁移期仍用长期服务账号 → 爆炸半径是"全部单据"而不是"一张单据一个窗口" |
| 产品族 | 产品提供的连接器 | 平台侧配置，粒度取决于产品是否支持按实例授权 | 粒度只到"一个连接器一个账号" → "越权被拒并留痕"这条演练做不了 |
| 改造族 | 通常没有写入能力 | 无 | 真的需要写入时被迫整体升级（同族内以月计，跨族以季度计【经验：同 §7.7】） |

**由此必然导出的性质**：因为**凭证的粒度决定了爆炸半径**（长期账号 → 全部单据；实例凭证 → 一张单据的窗口期），所以凭证归属是**安全设计的核心**，而不是集成细节。

这里还有一条常被忽略的方向性差别：**读的一侧与写的一侧走的是同一条入口，却有两套不同的约束**。写的一侧关心的是"能不能被拒、被拒之后有没有痕迹"；读的一侧关心的是"内容有没有离开边界"。产品族的连接器经常只把写的一侧说得清楚（能不能写、写多少），而把读的一侧含糊过去——**于是"能否出域"这个问题会在第一份敏感文档进链路时才被提出，而那时链路已经建好了**（§7.5 把这一条单列成一问）。

**公开证据**：**"应用侧不持有长期密钥、出网默认拒绝"这一族做法在书内他处有具名落点**——`06-multi-model/03-model-gateway` 的 §4.2（4）给出凭证托管与出网策略，并把它收成三条硬要求：**应用侧不得持有密钥且要可验证、出网默认拒绝、日志脱敏自动**。身份一侧，`11-cross-cutting/07-audit-and-compliance` 的 §8 题集里（§5.5.6 与 §5.5.7 两题）把 SPIFFE / SPIRE 记作"云原生时代的 Kerberos"（基于非对称密钥 + 短期证书、避免单点），同处另把 OIDC / SAML 记作跨云身份联邦的做法；`04-data-assetization/07-data-api-gateway` 的 §4 把"集成身份系统（OAuth 2.0 / JWT / SSO）"与"把『你是谁』和『你能看哪些行、哪些列』拆成两件事"写成一条实现原则。**但落到"按流程实例签发"这个具体粒度上，② 核不到**：公开材料里没有第三方给出的、可对照的影响面数据。**各身份体系的签发粒度与令牌有效期本节不具名，以各自官方文档当前版本为准。**【公开】（来源：`06-multi-model/03-model-gateway/03-model-gateway-section-4-sec4.md` §4.2（4）；`11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-8-5-5-大规模集群安全架构设计与优化.md` §5.5.6 与 §5.5.7；`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-4-sec4.md` §4；本主题 §4.2（7）与 §4.7）

**失效条件**：当写入量极小、且目标系统的权限模型本身很粗（例如只分"读写"）时，细粒度凭证的收益有限；但仍应**按最小权限**给账号。

#### 7.3.3 可补偿性：错了能不能退

**机制是什么**：每个可写动作有无**显式逆向动作**，以及不可逆动作是否被前置审批——它决定系统"出错后的代价"。

**它在各候选中的实现差异**：自建族需要**逐个业务系统定义**补偿动作（没有通用回滚接口）；产品族看是否为具体动作提供逆向能力（多数 RPA 平台只提供"重试"，不提供"冲销"）；改造族没有这一层。

| 候选族 | 逆向动作从哪来 | 谁定义"退"的语义 | 典型失败形态（可观测） |
| --- | --- | --- | --- |
| 自建族 | 逐个业务系统写下来（一份业务文档） | 业务 / 财务——技术只能实现它 | 技术单方定义 → 冲销与财务口径不符，账上留一笔谁也说不清来路的尾差 |
| 产品族 | 平台是否为该动作提供逆向能力 | 产品（多数只给"重试"这一种） | 把重试当补偿 → 重复入账，且月末对账才暴露 |
| 改造族 | 无 | 无人定义 | 没有写操作，所以也没有"退"；一旦开始写，"退"要在升级时一次性补（跨族以季度计【经验：同 §7.7】） |

**由此必然导出的性质**：因为**补偿动作是业务特有的**（财务冲销、通知更正、归档撤回），所以"可补偿性"无法靠产品解决——**它必须由懂业务的人写下来**，这也是本主题最容易被低估的工作量。

还有一条与"重试"有关的机制差别必须点出来：**重试改变的是"成功的概率"，补偿改变的是"已经发生的事"**——两者不是强弱关系，而是两条不同的路径。因此"多数产品只提供重试"这件事的后果不是"补偿弱一点"，而是**在部分成功之后系统根本没有收敛点**：它只能停在中间状态等人工临场判断（§6.4 的失败教训把这条写成"重试永远替代不了补偿"）。同理，补偿的代价结构也不一样：它的大头是**决策成本**（"该怎么退"）而不是执行成本——§6.4 的匿名案例里，事故处理的时间被"确认该怎么退"占去大半，**这部分时间不因为产品更好而消失，只因为这张表预先写好了才消失**。

**公开证据**：**"补偿式一致性没有通用回滚接口"这一条在书内他处有具名落点**——`00-introduction/04-glossary` 的术语表把 Saga / 2PC / TCC 收作"分布式事务模式"，同族的讨论见 `12-architecture/08-data-consistency`；纪律一侧，`12-architecture/09-gray-and-rollback` 的 §4 把"把不可逆动作压到流程的最后一步"与"**单程票清单**（已不可逆的变更及其日期）"写成同一套要求，并指出单向门必须写明"不可逆动作在第几步"——这正是 §7.3.3 这条差异在回滚语境里的同义表述。**本节不给任何一家的补偿成功率或冲销窗口长度**：补偿动作表是业务特有的、没有通行清单（§5.2 表里"流程状态机 + 可补偿动作"一行的 ② 栏写的就是这句）；本主题 §6.4 的匿名案例只作机制示例、不作举证。【公开】（来源：`00-introduction/04-glossary/04-glossary.md` 术语表；`12-architecture/08-data-consistency`；`12-architecture/09-gray-and-rollback/09-gray-and-rollback-section-4-sec4.md` §4；本主题 §4.2（5）、§4.5 模板 2、§5.2 与 §6.4）

**失效条件**：只读流程不需要补偿；含写操作的流程必须有（或把该动作列入"不可逆、必须前置审批"）。

#### 7.3.4 留痕与责任：能不能认定"谁批的"

**机制是什么**：审批记录是否含**输入快照与理由**，决定事后能否还原决策依据。

**它在各候选中的实现差异**：自建族可设计工单结构（含快照与理由必填）；产品族的工单结构由产品定（**多数只记"通过 / 驳回"**）；改造族的对话记录不是合规留痕（可被编辑、且不含结构化字段）。

| 候选族 | 工单里记什么 | 谁决定字段集 | 典型失败形态（可观测） |
| --- | --- | --- | --- |
| 自建族 | 输入快照（原文哈希 + 抽取结果）+ 校验结果 + 决定 + 理由 + 后续动作 | 你——`reason` 可以设为必填 | 只记"已批准" → 事后无法还原"当时基于什么批的" |
| 产品族 | 产品工单的结构（多为通过 / 驳回 + 时间 + 人） | 产品 | 审计时**记录在、但举不了证**：既有材料回答不了"基于什么" |
| 改造族 | 对话记录 | 没有人 | 可被编辑、无结构化字段 → 既不是权威源，也接不进既有保留策略 |

**由此必然导出的性质**：因为**责任认定需要"当时基于什么"，而不只是"结果是什么"**，所以留痕结构不达标的方案，会在第一次审计或第一次争议时暴露——而此时已无法回补历史。

这里还有一条只有办公场景才成立的机制：**留痕的完备度是被"外部事件"检验的，而不是被日常运行检验的**。日常运行时，只记结果与记全套看不出任何差别——两者都不影响流程跑通；差别只在一次审计、一次争议或一次组织调整时才显形，而那时**补录是不可能的**（当时那份材料与当时那个人的判断都已不可重建）。§6.1 的失败教训把同一条机制写在权限上：两份表之间没有同步机制，差异只会被外部事件制造、不会被内部流程消除——**留痕口径也一样：它是拿到工单结构的那一刻定下来的，之后每一次事故只是在结算当初那个决定。**

**公开证据**：留痕的字段形态在本主题内部有可照抄的落点——§4.2（6）的审批工单给出 `input_snapshot`（含原文哈希与抽取结果）、`checks`、`decision`（含 `reason`）、`deadline_at` 四段结构（`reason` 必填），§4.5 模板 2 则要求补偿动作本身也留一条流水（`inverse_of` 指回被补偿的动作）。**书内他处的同源口径**：`11-cross-cutting/07-audit-and-compliance` 的 §3 把"模型版本与评估报告 → 工具调用留痕（读了哪些库表 / 接口）→ 输出合规检查"写成一条可举证的链路，并给出留痕体量的推算口径；`11-cross-cutting/06-data-assetization` 的 §8 把电子签名、时间戳与不可篡改存证列作"不可否认"的技术手段（**该处是存证语境，本节只借它作旁证，不把它写成办公审批留痕的实现**）。**各产品工单里究竟有哪些字段，本节不引任何一家文档，请以各自官方文档当前版本为准。**【公开】（来源：本主题 §4.2（6）与 §4.5 模板 2；`11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-3-sec3.md` §3；`11-cross-cutting/06-data-assetization/06-data-assetization-section-8-sec8.md` §8）

**失效条件**：当链路里没有任何"对外产生后果"的动作（纯内部查询、草稿不对外）时，留痕强度可以降；只要有对外发送、入账或发布，工单就必须能回答"谁、何时、依据什么、批准了什么"——**这条判断不随组织大小变化，只随动作的对外性变化。**

#### 7.3.5 人放的位置：闸门（事前）还是例外处理（事后）

**机制是什么**：同一个"人"可以放在链路的两处，而这两处的**成本函数形状完全不同**：**闸门**（每个动作都等人批，成本随动作数线性增长）与**例外处理**（只有低置信 / 命中红线的才转人，成本随异常率增长）。

**它在各候选中的实现差异**：自建与半自建方案能让"人"落在**任意位置**（因为转人工规则由你定义）；**成品平台**通常把人的位置写进了产品形态——要么是"审批节点"（事前闸门），要么是"事后复核"，而**不一定提供"按字段置信度转人工"这种细粒度**；**RPA 类方案**的人往往落在"维护选择器"上（不是业务闸门）。**这三者的成本函数形状因此不同**：闸门随量线性、例外处理随异常率、RPA 随界面变动频率。

| 候选族 | 人落在哪 | 成本随什么增长 | 典型失败形态（可观测） |
| --- | --- | --- | --- |
| 自建 / 半自建 | 任意位置（转人工规则由你定义） | 例外处理 → 随异常率 | 异常判据过宽 → 退化成闸门（正常单据也被判成异常） |
| 产品族 | 产品写死的形态：审批节点或事后复核 | 闸门 → 随动作数线性 | 不提供"按字段置信度转人工"这种细粒度 → 要么介入率失控，要么异常静默通过 |
| RPA 类 | 维护选择器上（不是业务闸门） | 随界面变动频率 | 人不在业务闸门上，而在"修脚本"；异常单据的减速没人管 |

**由此必然导出的性质**：因为**办公场景的动作量通常很大而异常率很低**，所以"闸门"模式在量上来之后必然变成瓶颈（人力 `n > λ/μ`，§3.2.5）；**而"例外处理"模式的质量完全取决于"异常判据准不准"**——判据过宽则退化成闸门（全都转人工），过窄则异常静默通过。**因此选型的实质不是"要不要人"，而是"你的异常判据能不能做得准"**——做得准，人就可以事后出现；做不准，就只能事前拦。

**公开证据**：这条差异的两个量在书内都有可核验的写法。**闸门的宽度**用到达率与人均处理率表达——本主题 §6.2 给出 `n > λ/μ`【推算：与 Ch5 §02 平台架构的积压条件同源】，并明确它**用来判断"闸门是不是过宽"，而不是用来申请加人**：它把"人能承受多少量"写成两个可观测的数，加人不改变这个比值的形状，只有收窄转人工范围才改变它。**例外处理的质量**用两条曲线表达——本主题 §4.2（3）与 §6.3 把"阈值 → 介入率 / 漏出率"写成一条业务能讨论的曲线，判据是"业务能在曲线上指出它选的那个点"。部件一侧，`05-agent-platform/02-agent-platform-architecture` 的 §3.2.7 把"人审闸门"实现为同步审批与异步工单两种形态——**这正是"人落在哪"在平台侧的具名落点**；同节 §3.2.4 的"工具出口收口"保证人审这一环不能被绕过。**各产品把人放在哪一格，请以其官方文档当前版本为准；本节不点名任何产品**（§5.2 把"RPA 与模型分工"一行判为 L2、③ 部分成立）。【公开】（来源：本主题 §4.2（3）、§6.2 与 §6.3；`05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md` §3.2.4 与 §3.2.7；Ch5 §02 的积压条件）

**失效条件**：当"介入率"持续上升而"漏出率"没有下降时，说明异常判据失效（它把正常单据也判成异常）；此时**正确的动作不是加人，而是回到字段级阈值去重标**（§6.3 的介入率—漏出率曲线）。**反过来的失效形态更危险**：介入率下降、漏出率也"下降"——后者往往不是真的改好了，而是判据被放宽了，而放宽的后果要等到某一张错单进了不可逆步骤才显现。

#### 7.3.6 数据敏感级与出域路径：读的一侧的爆炸半径

**机制是什么**：§7.3.2 讲的是**写**的一侧（凭证粒度决定一次误操作能改坏多少），这一条讲的是**读**的一侧——**文档在哪里被解析、索引建在哪里、模型端点部署在谁的边界内、日志与遥测去了哪里**。这**四处**任意一处把内容送出去，链路就已经出域，而这件事**与写入权限完全无关**：一条只读的问答链路同样可以出域（§3.2.1 把"责任面为零"与"错误代价为零"分开讲，同一条区分在这里变成"责任面为零不等于出域风险为零"）。

**它在各候选中的实现差异**：自建族可以把解析、索引、模型端点与遥测都放在自己的边界内（代价是自担算力与运维）；产品族的出域路径由产品的部署形态决定——**买到的"智能"往往意味着"文档要送到厂商端点"**；改造族通常**默认走外部端点**（因为它本身就是通用助手的接线）。**这一格的差异不是"谁更安全"，而是"你还能不能选"**。

| 候选族 | 文档在哪被解析 | 模型端点在哪 | 典型失败形态（可观测） |
| --- | --- | --- | --- |
| 自建族 | 自己边界内（可自托管） | 可自托管，可按文档分级路由 | 以为整体自托管，但**解析 / 索引 / 遥测三处仍出去了**（"假私有化"） |
| 产品族 | 由产品部署形态决定 | 由产品决定（多为厂商端点） | 到第一份人事 / 财务文档进链路时才发现走不通，而链路已经建好 |
| 改造族 | 通常在自己的客户端 | 默认外部端点 | 文档分级这件事根本没做——一份链路处理所有文档，无法证明敏感文档没出域 |

**由此必然导出的性质**：因为**"不能出域"是一个布尔约束，而不是一个评分维度**（§7.1 第 2 条把它列为门槛），所以它一旦不满足，**该候选无论其余维度多好都直接出局**——这正是数据敏感级被放在"门槛"而不是"权重"里的原因。反过来，因为出域是**读**的一侧的事，**它的失效不会被写操作暴露**：没有一笔错误入账、没有一次重复提交、流程成功率也照常——**它只是把不该出去的东西送出去了**，而在被发现之前没有任何一个业务指标会变差。这条性质解释了为什么它必须在第一版就判对：**它没有任何"运行期信号"能把人叫醒，唯一的信号是审计或一次泄漏。**

**公开证据**：出网与凭证托管这一族做法在书内他处有具名落点——`06-multi-model/03-model-gateway` 的 §4.2（4）给出凭证托管与出网策略，其三条硬要求见 §7.3.2 的公开证据，其中**出网默认拒绝**正是这一格的具名判据；本主题 §4.3 那条总判据（每一层都要能写出"不选它的原因"，与 `06-multi-model/03-model-gateway` 的 §7 同一把尺子）在这里同样适用。分级与权限域一侧见 `08-ai-governance/01-ai-data-governance`（分级保密与权限）与 `08-ai-governance/02-data-security-and-compliance`（数据安全与合规）。**但"哪一家的智能抽取是否必须把文档送到厂商端点"这类问题，本节不引任何一家文档**——部署形态与数据流向随产品版本变化，**请以各自官方文档当前版本为准**；本主题 §5.1 已把"办公套件扩展接口在演进"归入第二类前沿（接口与规范变了），其档位就是【公开：以各自规范与文档当前版本为准】。判定入口是四件可自测的东西：连接审计（一段时间的出网记录）、一次拒绝演练、文档分级与路由配置、留痕可导出——**四件合起来才是证据，架构图不是**（§8.6 的答案框架给出同一组）。【公开】（来源：`06-multi-model/03-model-gateway/03-model-gateway-section-4-sec4.md` §4.2（4）；`08-ai-governance/01-ai-data-governance` 与 `08-ai-governance/02-data-security-and-compliance` 的分级与合规口径；本主题 §5.1、§4.3 与 §7.3.2）

**失效条件**：当文档本身不含敏感信息、或已做**可核验的**字段级脱敏之后再外发时，出域路径的差别会消失——但"可核验"是这条失效条件的全部内容：**给不出脱敏规则与抽检结果，就等于没有脱敏**。另一条：当组织已经把解析与端点放在云上、且该云在合规口径上算"域内"时，这一格也不再构成差异——**"域"是按合规边界定义的，不是按机房位置定义的**。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| 自建族 | 人力（Schema / 阈值 / 补偿表维护）+ 解析抽取成本 | 补偿动作表的持续补充、单据版式变化的适配、留痕存储 | 随单据类型数与流程数增长 |
| 产品族 | 许可 / 连接器 / 调用计费 | 定制受边界限制导致的额外人工环节、升级行为变更 | 随流程数与连接器数线性增长 |
| 改造族 | 最省的前期投入 | 无法承载写操作 → 团队另建流程（重复投入） | 随诉求升级而被迫重做 |

**成本函数的三条判据**：① **自建族是"台阶形"**（人力 + 固定设施，不随单据量变），单据量大时最省；② **产品族是"线性"**（许可 / 连接器 / 调用量），单据量小时最省；③ **改造族前期最省但天花板最低**——省下的钱通常以"另建流程与人工补录"的形式花回来。

**把它写成成本函数**（不是价格表）：

```
成本 ≈ 解析与抽取的调用（单据数 × 页数 / 字段数 × 单次成本）
      + 人工核对（单据数 × 介入率 × 单张核对时长）
      + 阈值与补偿表的维护（单据类型数 × 每类的常备工时）
      + 许可与集成（流程数 / 连接器数 / 调用量）
      + 未收敛的部分成功（事故次数 × 单次处理时长）
```

三族里哪一项是主导项，直接决定"单据量变大时谁更省"：

- **自建族**：主导项是**第一、二、三项**。其中第三项不随单据量变化（这就是"台阶"），第一、二项随单据量增长但单价由你自己的设施与阈值决定——**所以量大时它摊得最薄**。
- **产品族**：主导项是**第四项**，并随流程数与连接器数增长。它的第一至三项被产品的口径替代，**但第二项不会归零**——转人工这件事产品不能替你做（§7.3.5 表里"产品族"一行的失败形态即此）。
- **改造族**：主导项是**第五项**（缺骨架导致的重复投入与人工补录）。它不在采购合同里，因此最容易被漏掉。

**三条量级推导**：

1. **人工核对这块有多大**（【推算】）。本主题 §4.6 给了一条可换参数的算例链：日单据 `1,200` 张、单张核对 `3` 分钟【经验：参数随业务形态浮动】。取介入率 `40%`，则人工量 ≈ `1,200 × 40% × 3 分钟 = 1,440 分钟 ≈ 24 人时/日`（口径＝单据数 × 介入率 × 单张核对时长，三个参数都可按你自己的数替换）。**同一条链的微分结论更用得上**：介入率每降 5 个百分点 ≈ `1,200 × 5% × 3 分钟 = 180 分钟 ≈ 3 人时/日`（【推算】，同一口径）——**这就是"阈值标定"为什么比"换一代抽取模型"更直接**：前者是给乘数降系数，后者只是给第一项降单价，而第一项的单价通常不是主项。

2. **它折算成几个人**（【推算】）。把上面那 24 人时/日按每年约 `250` 个工作日【经验】折算：`24 × 250 = 6,000 人时/年`；再按每人年 `1,700–2,000` 工时【经验】折算 ≈ **3 人年**（推导链：人时/日 × 工作日数 ÷ 每人年工时；6,000 ÷ 2,000 = 3.0，6,000 ÷ 1,700 ≈ 3.5）。**这条推导解释了 §7.1 第 6 条判据为什么把"0.5–1 人年"写成门槛而不是权重**：那 0.5–1 人年量的是**常备维护**（Schema 与归一规则、阈值曲线、补偿动作表这三件的持续投入），而这里的 3 人年是**运营口径的人工核对量**——两者不是一回事，却是同一个乘数在不同项上的投影。**一个答不出"谁来承接"的方案，省下的通常正好是前者的实现，留下的是后者。**

3. **缺补偿动作表的代价形状**（【推算】）。§6.4 的匿名案例给出唯一可以直接用的量：一次"部分成功"事故的处理时间为三天，其中两天花在**确认"该怎么退"**上。写成年化口径：设此类事故年发生 `k` 次、单次处理 `3` 人日，则年化 ≈ `3k` 人日（口径＝事故次数 × 单次处理人日，`k` 按你自己的历史替换）；而**补偿动作表缺失的边际代价 ≈ 单次处理时间的 2/3**（口径＝"确认退法"2 天 ÷ 总 3 天）——因为**预先写好这张表，省掉的正是那两天**，不是执行退的那不到一天【推算；来源案例本身为匿名材料，只作机制示例，不作举证】。

**一条经验判据**（【经验】）：**当"单据数 × 介入率 × 单张核对时长"这一项已经大于你打算付的许可与集成费用时，自建族的台阶形就开始占优了**——但注意这不是"量够大就选自建"，而是**量够大、且你有能力把介入率压下来**才选自建：一个压不下介入率的自建系统，只是把线性成本换成了一座更高的人工台阶。可自行核验的判据是统计最近一个季度"介入率有没有下降、补偿动作表有没有新增条目"——**两者都停在原地时，换族不会改善账单**。

### 7.5 决策树（每个分支都要有阈值依据）

1. **流程里有没有不可逆的写动作（发款 / 对外发送 / 入账）？**
   - 有 → **必须有人审闸门 + 补偿动作表**；并要求方案支持细粒度授权与工单留痕 → **改造族出局**；进入第 2 问。
   - 没有（只读 / 可完全回滚）→ 进入第 3 问。
2. **有无 API 可调？**
   - 有 → **自建理解层 + 既有工作流引擎**（多数企业的现实解）；进入第 4 问。
   - 没有 → **自建 + RPA 混合**（理解 / 执行分离）。
3. **单据量与版式变化频率？（按"每日单据数"与"每月新增版式数"量两个数）**
   - 量大（每日**千级**以上【经验：以"人工录入是否成为瓶颈"为分界】）或版式频繁变化 → 进入第 2 问（倾向自建族）。
   - 量小且版式稳定 → **办公套件自带能力**或**产品族**最省。
4. **有没有人能长期维护 Schema、阈值曲线与补偿动作表（按 0.5–1 人年的常备投入量级估算【经验】）？**
   - 有 → **自建端到端**（控制力最强）。
   - 没有 → **商业 RPA 平台 + 自建 LLM 层**，或**办公套件自带能力**（接受"口径由产品定"）。
5. **文档能不能出域？（按敏感级判，不按文档量判）**
   - 不能出域 → **自建族**，且**解析 / 索引 / 模型端点 / 遥测四处都要在自己边界内**；产品族与改造族出局（§7.3.6）。
   - 能出域，或敏感文档占比极低且可分链路 → 产品族可用；**但仍要给敏感文档留一条本地链路**（一份链路处理所有文档时，你无法证明敏感文档没出域）。
6. **这些流程的骨架与身份，现在是不是已经有一套在跑？**
   - 有（既有工作流引擎 / 统一身份）→ **不要重建**，走"自建理解层 + 既有引擎"这一行；只有当引擎给不出你需要的粒度（细粒度超时、能不能加留痕字段）时，才评估换引擎（§6.2 把"愿不愿意为一条流程去改引擎"写成一条取舍）。
   - 没有 → 回到第 2 问按 API 有无继续；同时把"要不要引入工作流引擎"当成一个独立决策，而不是顺手选一个。

**阈值的诚实说明**：上表的"千级/日"与"0.5–1 人年"都是【经验】档——用来区分"这一档"与"那一档"，请用你自己的量级与排期校准：**门槛是"有没有人长期承接"这个是非题，不是"够不够 0.5 人年"这个数**。

**每条分支的阈值依据**（把"凭什么这么分"逐条写出来）：

- **①「不可逆写动作」**：判据不是金额，而是两个可逐条判定的问题——"这个动作有没有语义正确的逆向动作"与"逆向窗口有多长"（§7.3.3 的表）；有逆向动作的动作属于"可补偿"，**没有逆向动作或窗口已过的动作必须前置审批，且不得置于链路中间**，这一条与 `12-architecture/09-gray-and-rollback` 的"把不可逆动作压到最后一步""单程票清单"同源。
- **②「有无 API」**：判据是"这一步能不能被脚本复现"——能复现的走 API / RPA，只有需要理解页面语义的那部分才归模型（§3.2.7 的分工）；这里的分界是**可复现性**，不是"哪个更先进"。
- **③「千级/日」与「版式变化频率」**：依据是 §7.4 的推导 1、2——**分界不在绝对量，而在"人工录入是否已经成为瓶颈"**【经验】；版式一侧用的是"每月新增版式数"，因为模板 / Schema 的维护成本随它增长（§6.3 记为随单据类型数线性增长【经验】）。
- **④「0.5–1 人年」**【经验：按常备维护的三件产物量级估算】：依据是常备维护的三件产物——Schema 与归一规则、阈值曲线、补偿动作表（§4.2（2）（3）（5）各给出它们的形态）；**它量的是持续投入而不是首版实现**，所以答"没有"时应当选口径受产品定的方案，而不是选一个没人维护的自建系统。
- **⑤「能否出域」**：依据是 §7.3.6 与 `06-multi-model/03-model-gateway` §4.2（4）的"出网默认拒绝"；**这条是布尔约束，不给阈值**——判据是"受敏感级约束的文档是否全部命中本地端点"，报不出这个比例就说明文档分级没做（§8.6 的答案框架给出同一组证据）。
- **⑥「既有权威源」**：依据是 §6.1 与 §6.2 的两条归属判断——权限的权威源必须唯一、状态机不是要重写的而是要去用的；**这条不涉及阈值，涉及的是重建的代价**（重建一个权限源会产生一个随时间变大的差集；重建一个状态机会失去"卡在哪一步"的统计口径）。

树里没有"预算"节点，这一点需要单独说明：**预算不是筛选条件，而是规模效应在账面上的投影**——它由 §7.4 的三条推导决定（你的介入率决定人工量、你的承接方式决定常备投入、你的补偿表完整度决定事故成本）。把"预算是否超过某个数"当分叉，最常见的后果是**为省下许可费而选了一个机制上要持续投入人力的方案，第二年发现人力成本反而更高**——许可费是一次性的账，常备维护是按年滚的账，**两者的形状不同，而立项时只看得到前者**【经验】。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 财务 / 合同类（不可逆写动作多） | 自建理解层 + 既有引擎（+ 补偿表） | 自建端到端 | 产品族的工单与授权粒度常不够 |
| 遗留系统多、只能走界面 | 自建 + RPA 混合 | 商业 RPA 平台 + 自建 LLM 层 | 让模型直接操作界面脆弱且难归因 |
| 单据量大、版式频繁变化 | 自建端到端 | 自建理解层 + 引擎 | 产品族的字段与阈值不可控 |
| 单据量小、流程标准 | 办公套件自带能力 | 商业 RPA 平台 | 自建在量小时不划算 |
| 只想"能查会写" | 通用对话助手 + 文档索引 | 办公套件自带能力 | 若上了写操作则骨架缺失（应升级方案） |
| 多部门共用、要求统一留痕 | 自建端到端（统一工单与留痕） | 产品族 + 自建留痕层 | 各部门各自买产品 → 留痕口径分裂 |
| 文档含人事 / 财务 / 合同，不能出域 | 自建族（本地解析 + 本地端点 + 出网白名单） | 产品族 + 敏感文档分链路走本地 | **出域是布尔约束，不满足即出局**；产品族的部署形态不会因你的要求而改（§7.3.6） |
| 已有统一身份与工作流引擎在跑这些流程 | 自建理解层 + 既有引擎（不重建骨架） | 自建端到端 | 重建第二个权限源会产生随时间变大的差集；重建状态机会丢掉"卡在哪一步"的统计（§6.1、§6.2） |
| 已有 RPA 在跑、界面会改版 | 保留 RPA 执行 + 加模型理解层与变更探测 | 全部改成模型直接操作界面 | 把确定性执行交给概率系统，脆弱性与不可归因会同时上升（§3.2.7） |

**矩阵的读法是：先按"后果是否可逆 + 能不能出域"定可行性，再按"量与技术栈"定族。** 表格右边那列"不选它的原因"不是能力排序——要"事后能逐单举证"，工单字段集由产品定的那一格就选不了（§7.3.4）；要"一次误操作只坏一张单据"，凭证粒度只到"一个连接器一个账号"的那一格就选不了（§7.3.2）。用法只有一句：**你要的收益得落在你引入的那一格机制所作用的位置上**——位置对不上时，换一件更好的产品不会让这一行变得可选，它换掉的是产品的强弱，换不掉机制的作用点。

**组合的两条次序原则**：① **先把红线、字段代价与补偿表立起来，再选执行器**——执行器可替换，红线与补偿表是资产；② **先把工单留痕结构定下来，再谈自动化程度**——留痕结构不达标，自动化程度越高越危险。

**三个常见组合**（各说明职责边界与运维代价）：

1. **既有工作流引擎 + 字段级阈值与转人工 + 补偿动作表**（最常见的真实形态）：引擎管状态、超时、转交与工单；阈值曲线管"哪些字段转人工"；补偿动作表管"失败怎么退"。运维代价：流程定义、阈值表与补偿表是**三份要同步维护的资产**，流程一改三份都要跟着改——**缺少这条同步纪律时，最先失效的一定是补偿表**，因为它只在事故发生时才被读到（§7.4 推导 3 给出的正是它的代价形状）。
2. **RPA / 界面自动化 + 模型理解层 + 变更探测**：模型负责读与判断并给出变更建议，RPA 负责点与写，变更探测每天对关键页面做一次元素存在性检查。运维代价：两类错误要各自有日志与计数（否则优化没有靶点），且**修法仍由人确认**——把"改选择器"交给模型，等于让一次误判静默地影响所有同类操作（§3.2.7）。
3. **端到端 Agent 边界 + 审核三层 + 全链路留痕**：白名单动作集限定"能做什么"，审核三层（规则 / 模型 / 人）限定"该不该批"，留痕保证输入、判断、动作三段可回放。运维代价：白名单要随业务增长持续登记动作，回放与留痕的存储随调用量上升；**这三件里缺任何一件，端到端就只能作为演示**（§3.2.8 与 §8.7 的答案框架给出同一组前置条件）。

三个组合的共同点是**入口低门槛、关键环节强约束**：谁都能查的问题走最低成本的入口；不可逆与对外的那一步走最严的闸门。反过来设计——全链路强约束（介入率失控）或全链路弱约束（不可逆步骤没有闸门）——是本主题最常见的形态错误（前者的由来见 §3.3 决策表"整篇阈值会导致介入率失控"一行，后者见 §3.4 误配表"上了端到端但动作集不是白名单"与 §3.5 反模式表"不可逆步骤放在链路中间"两行）。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 改造族 → 自建 / 产品族 | 需要写操作与留痕 | 补状态机、幂等、补偿、工单与授权 | 以月计【经验】 |
| 产品族 → 自建族 | 工单 / 授权粒度不足、阈值不可控 | 重建骨架与留痕口径；**历史工单不可迁移** | **以季度计**【经验】 |
| RPA 直接操界面 → 混合 | 界面一变全断 | 拆出理解层与执行层；补两类错误的观测 | 以月计【经验】 |
| 长期账号 → 实例凭证 | 一次泄漏影响面过大 | 接身份体系、按实例签发、补越权演练 | 以月计【经验】 |
| 无补偿表 → 有补偿表 | 部分成功退不回 | 逐个业务系统定义逆向动作并演练 | 以月计【经验】，**业务侧工作量占大头** |

**一条硬结论**：六条路里最贵的是**"把骨架与留痕交出去之后的收回"**——它不只是技术搬迁，还包括口径重建与**无法迁移的历史记录**。**所以第 1、3、4 条判据（可逆性、留痕与责任、骨架归属）必须在第一版就判对。**

**四个反模式**（每个都写清"为什么这个错法看起来对"）：

**反模式：把"处理量"当治理成果** —— 症状是汇报里写"本月自动处理多少张单据" → 后果是处理量只说明系统在跑，**既不说明是否替人省了力，也不说明质量**；当介入率下降而返工率上升时，"更自动了"恰恰是风险被搬到事后的信号 → 机制上这是把**吞吐**当成了**价值**，而吞吐恰好是与质量脱钩的那一个数（它对"低置信字段进没进写路径"完全不敏感） → 正确做法：三个数一起看（介入率 / 返工率 / 流程成功率），并把"返工率不得上升"写成扩大自动化面时的硬约束（§4.2（8）、§8.7）。

**反模式：先做端到端、后补红线与补偿** —— 症状是"一句话办完"先上线（因为它看得见、好演示） → 后果是端到端会迅速扩展"模型能调的动作"，而**每扩展一个可写动作就多一格需要写"怎么退"的位置**，补的时候还要回头看已经上线的全部路径 → 机制上这是**顺序反了**：红线与补偿表不依赖任何模型能力，所以它们本该早做（§6.5 把红线与"为每个可写步骤写下'怎么退'"都放在第 1 步），把它们推到后面并不会降低它们的工作量，只会让它们的对照面变大 → 正确做法：按 §6.5 的四步顺序走，端到端放最后——**这是四个案例里唯一一个"越努力越难"的顺序**。

**反模式：把补偿表当技术组件** —— 症状是补偿动作由技术单方定义、写完就算完成 → 后果是冲销与财务口径不符、账上留一笔谁也说不清来路的尾差，而**"退不干净"正是以尾差的形式显形的** → 机制上技术侧只能看见接口，看不见语义：在接口上"撤销 / 冲销 / 反向"都是一次调用，在业务语义上它们分别是抹掉、记一笔反向记录、补一条更正，**因此这件事在原理上无法由技术单方完成** → 正确做法：补偿表由业务 / 财务确认，并做一次人为制造失败的演练——**表写对了却没人按它收敛过，等于把决策成本重新推给下一次事故**（§6.4）。

**反模式：把"能不能"当"好多少"** —— 症状是选型时给"可定制程度""智能程度""留痕完备度"打分后取总分最高者 → 后果是**把一个淘汰条件降级成了一个排序因素**：动作可逆性与数据敏感级这两条不满足时要重做，而不是"少得几分" → 机制上打分表只能表达连续量，表达不了布尔约束与处境权重（§7.1 讲的就是这件事） → 正确做法：先过门槛（不可逆动作、出域约束），再在剩下的候选之间比代价函数（§7.4）。

四个反模式的共同点是**它们都在机制层面把"某个可度量的量"替换成了"要度量的量"**：处理量替换了价值，演示效果替换了顺序，接口调用替换了业务语义，总分替换了门槛。评估一个办公自动化方案时，看的不是它列了多少能力，而是**它有没有让 §7.4 表里"成本随什么增长"那一列换项**。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 链路里有不可逆写动作（发款 / 对外发送 / 入账） | 前置闸门 + 补偿动作表，或把该动作列入不可逆清单 | 没有逆向动作时，"退"只能靠事故现场的临场判断 |
| 只读、只查文档 | 文档问答 + 引用回指，不上写操作 | 责任面为零；一旦用户开始"抄进系统"，真实需求已经是抽取入库 |
| 单据量大、版式频繁变化 | 自建端到端，或自建理解层 + 既有引擎 | 产品族的字段与阈值不可控，维护成本会从你手里转到产品边界上 |
| 单据量小、流程标准 | 办公套件自带能力 / 产品族 | 自建会把"台阶形"的固定投入摊在太少的量上 |
| 无 API、只能走界面 | RPA 执行 + 模型理解（理解 / 执行分离） | 让模型直接操作界面，会把脆弱性与不可归因叠在一起 |
| 已有工作流引擎与统一身份在跑这些流程 | 自建理解层 + 既有引擎（不重建骨架） | 重建第二个权限源会产生随时间变大的差集；重建状态机会丢掉滞留统计 |
| 文档含人事 / 财务 / 合同，不能出域 | 自建族，解析与端点都在自己边界内 | 出域是布尔约束而非权重，不满足即出局 |
| 审计要"谁能还原当时基于什么" | 自建族（工单可设计为含输入快照与理由必填） | 产品族的工单结构由产品定，审计时容易"记录在、但举不了证" |
| 没有团队能常备维护 Schema / 阈值 / 补偿表 | 产品族，接受"口径由产品定" | 这一支的成本主体是长期人力，缺承接能力时自建会静默失效 |
| 介入率与错单率同时难降 | 回到字段级阈值重标，先别加人 | 介入率是阈值这个乘数的系数；加人不改变乘数的形状 |
| 要写多个没有分布式事务的系统 | 幂等键 + 逐系统补偿 + `inverse_of` 留痕 | 部分成功是分布式写入的常态，不是异常分支 |
| 业务要"一句话办完" | 受限端到端（白名单 + 留痕 + 前置审批 + 幂等补偿） | 四件里缺任何一件，它就只能作为演示 |

> 本节小结：六个候选之间的差异，最终都能归到三问——**确定性骨架由谁实现**（状态机 / 超时 / 幂等 / 补偿）、**凭证的粒度有多大**（决定爆炸半径）、**审批工单留的是什么**（决定责任能否认定）。三问决定了它们的成本曲线形状（自建台阶、产品线性、改造前期最省但天花板最低）与迁移代价（跨族迁移以季度计，同族以月计）。**选型顺序不可颠倒**：先用"有没有不可逆写动作"与"能不能出域"筛掉不可行，再用"有没有人长期承接"筛掉第二年静默失效的方案，最后用"骨架归属、留痕强度与执行入口"在剩下的里选——**把"谁维护补偿表"当权重而不是门槛，就是"上线三个月后不敢再扩"的根因**。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次检查（不是打分）：先用三道门槛过一遍——动作可逆性、数据敏感级、承接能力——**哪一条是"不满足"而不是"分数低"**？那一条就是你明年最可能被迫迁移的方向。再用留痕与责任、确定性骨架归属、执行入口这三条给剩下的候选排序；而你今天的补救，是否还落在"同族迁移（以月计）"这一格里？
