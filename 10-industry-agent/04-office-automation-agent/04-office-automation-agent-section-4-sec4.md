## 4. 工程实现

### 4.1 落地步骤

**八步，顺序不能颠倒**：

| 步 | 动作 | 产物 | 判据（先写下，再动手） | 为什么必须在这一步 |
| --- | --- | --- | --- | --- |
| 1 | **画流程并标红线** | 状态机草图 + **不可逆步骤清单** | 每个不可逆步骤前有哪些校验与审批 | 红线决定后面所有闸门的位置 |
| 2 | **定字段与代价** | 单据 Schema + 每字段的"可接受错误率" | 错误代价最高的三个字段是哪些 | 它是阈值与转人工规则的依据 |
| 3 | **建解析与抽取** | 解析链路 + 抽取结果（带置信度与原文位置） | 抽出的表格能否还原行列语义 | 解析质量决定抽取上限 |
| 4 | **建字段级阈值与转人工** | 「阈值 → 介入率 / 漏出率」曲线 + 工单入口 | 介入率是否可接受、漏出率是否达标 | 这是"自动化程度"的调节旋钮 |
| 5 | **建幂等与补偿** | 幂等键设计 + **补偿动作表** | 每个可写步骤失败后怎么退 | 部分成功是常态，没有它必然资损 |
| 6 | **建审批与留痕** | 审批工单（含输入快照）+ 留痕表 | 能否还原"当时基于什么批的" | 责任认定与审计的前提 |
| 7 | **接跨系统执行** | 凭证托管（按流程实例）+ 超时与熔断 | 重复执行是否重复入账 | 幂等与凭证是执行的两条腿 |
| 8 | **建端到端指标** | 人工介入率 + 返工率 + 流程成功率 | 最近一次优化的依据是哪个数 | 没有它，"自动化"只是宣称 |

**顺序的反面**：最常见的错误是**先做抽取（最有产出感）、后补幂等与补偿**——结果是"抽得挺准，但错单被写进系统且退不回来"。第 5 步之所以排在执行之前，是因为**错误一旦进入业务系统，修复成本远高于预防**。

### 4.2 关键技术点

**（1）文档解析：先分版面和表格，再抽字段**

```yaml
parse_steps:
  - {step: layout,   aim: 区分正文 / 表格 / 印章 / 页眉页脚}
  - {step: tables,   aim: 还原"行 × 列"语义（含合并单元格）}
  - {step: text,     aim: 抽取文本与位置（页码 + 框坐标）}
  - {step: quality,  aim: 判定可解析性（扫描质量 / 旋转 / 缺页）}
fallback:
  - {when: "quality < 阈值", action: "转人工录入（不要硬抽）"}
```

**判据**：抽出的表格能还原行列语义；**解析质量差的文档直接转人工**，而不是"尽力抽一个错的"。

**（2）抽取 Schema 与原文位置**

```json
{
  "doc_type": "invoice_v2",
  "fields": {
    "invoice_no":  {"type": "string", "required": true,  "normalize": "upper_trim"},
    "issue_date":  {"type": "date",   "required": true,  "normalize": "iso8601"},
    "amount":      {"type": "decimal","required": true,  "normalize": "cny_2dp", "unit": "CNY"},
    "supplier":    {"type": "string", "required": true,  "normalize": "alias_lookup"},
    "purpose":     {"type": "string", "required": false}
  },
  "provenance": {"span": "page+bbox", "keep_text": true}
}
```

> **`provenance` 为什么是必填**：`span` 给出定位方式（页码 + 区域），`keep_text` 决定是否保留原文——**没有它，人工核对要自己回原文里找，核对成本会高到让人凭印象通过**（转人工因此退化成橡皮图章）。

**判据**：每个字段都能定位回原文（页码 + 区域）；**金额 / 日期 / 主体三个字段必须有归一规则**（否则同一事实会有多种写法）。

**（3）字段级阈值与"阈值 → 介入率 / 漏出率"曲线**

```
做法：取一批历史文档（已人工确认字段真值），对每个字段：
  1) 按置信度分桶，统计每桶的"抽错率"
  2) 画出「阈值 → 介入率 λ(θ)」与「阈值 → 错误漏出率 ε(θ)」
  3) 取业务可接受错误率 ε* 对应的最小 θ，作为初始阈值
判据：三个高代价字段（金额 / 日期 / 主体）用更严的阈值；其余字段可放宽
```

**判据**：阈值表**按字段登记**（可审计、可迭代）；曲线的样本量要能分辨差异（样本不足先攒数据，别急着调阈值）。

**（4）流程状态机与超时**

```yaml
process: invoice_reimburse_v3
states:
  - {id: received,        timeout_h: 24, on_timeout: escalate}
  - {id: extracted,       timeout_h: 4}
  - {id: need_manual_fix, timeout_h: 48, on_timeout: escalate, human: true}   # 人工节点必须有超时
  - {id: pending_approval,timeout_h: 72, on_timeout: reject,     human: true}
  - {id: posting,         timeout_h: 0.5, on_fail: compensate}                # 写系统步骤
  - {id: done | rejected | compensated}
transitions:
  - {from: extracted, to: pending_approval, when: "所有高代价字段置信度 ≥ 阈值"}
  - {from: extracted, to: need_manual_fix,  when: "任一高代价字段置信度 < 阈值"}
```

**判据**：**每个状态都有超时**；人工节点的超时动作明确（升级 / 转交 / 拒绝），**不是静默挂起**。

**（5）幂等键与补偿动作表**

```python
def idem_key(doc):                       # 业务要素构成，不用自增 ID
    return hash_norm(f"{doc.type}|{doc.invoice_no}|{doc.issue_date}|{doc.amount}|{doc.supplier}")
```

```yaml
compensations:
  - {action: "erp.post_invoice", inverse: "erp.reverse_invoice", window_h: 72, note: "红字冲销"}
  - {action: "notify.supplier",  inverse: "notify.supplier_correction", window_h: 24, note: "补发更正说明"}
  - {action: "dms.archive",      inverse: "dms.unarchive",  window_h: 168}
no_compensation:                          # 无补偿动作的动作：必须前置校验与审批
  - "payment.execute"                     # 已发款不可撤 → 只能前置
```

**判据**：**每个可写动作要么有逆向动作，要么进 `no_compensation` 清单并要求前置审批**——这份清单就是 §3.1 第 1 条约束的落地物。

**（6）审批工单与不可否认**

```json
{
  "ticket": "ap-2026-1021-0031",
  "process": "invoice_reimburse_v3",
  "input_snapshot": {"doc_id": "invoice/2026/1021/ab12.pdf", "sha256": "…",
                     "extracted": {"amount": 128000, "supplier": "ACME-001", "issue_date": "2026-10-18"}},
  "checks": {"rules": ["r-amount-within-budget"], "model": [{"id": "m-anomaly", "score": 0.31}]},
  "decision": {"by": "u-2210", "at": "2026-10-21T09:41:00Z", "verdict": "approve", "reason": "预算科目匹配，附件齐全"},
  "deadline_at": "2026-10-24T09:41:00Z"
}
```

**判据**：`input_snapshot` 里**有原文哈希与抽取结果**（这样才叫"不可否认"）；`reason` 字段必填（否则闸门会退化成点"同意"）。

**（7）跨系统执行的凭证与失败分类**

```yaml
credentials:
  mode: per_process_instance
  ttl_minutes: 30                        # 短期凭证
  scope: "erp:invoice:write, dms:archive:write"
failure_classes:
  - {class: retryable,    examples: [timeout, 5xx],      action: retry_backoff, idem: true}
  - {class: compensating, examples: [downstream_reject], action: run_inverse}
  - {class: manual,       examples: [authz_denied, schema_mismatch], action: open_ticket}
```

**判据**：重试一律带幂等键；**"下游拒绝"要能触发补偿**（而不是重试到天荒地老）。

**（8）端到端评测（三段指标）**

| 层 | 指标 | 数据来源 | 用途 |
| --- | --- | --- | --- |
| 抽取（离线） | 字段级 precision / recall | 历史文档 + 人工真值 | 阈值标定与回归 |
| 流程（线上） | 流程成功率、各状态耗时 P95 | 状态机日志 | 定位卡点 |
| 端到端（线上） | **人工介入率**、**返工率** | 工单与纠正记录 | 判断是否真在替人干活 |

**判据**：**返工率必须单独统计**（介入率下降而返工率上升 = 风险被搬到了事后）；三段都要能在看板上看到。

### 4.3 工具链与平台

| 层 | 可选 | 选型判据 |
| --- | --- | --- |
| 文档解析 | 版面分析 + 表格还原 + OCR（商用 / 开源） | 是否要处理扫描件与合并单元格 |
| 抽取 | Schema 约束抽取（模型 / 规则混合）+ 归一库 | 是否需要字段级置信度与原文位置（需要 → 强制） |
| 流程编排 | 工作流引擎 / 自研状态机 | 是否有等待、审批与超时（有 → 引擎更省） |
| 人工环节 | 工单系统（含超时与升级） | 是否要"不可否认"的审批记录 |
| 执行 | API 直连优先；无 API 时 RPA | 是否有 API（无 → 走 RPA + 理解分离） |
| 凭证 | 与内部身份体系对接（短期凭证） | 能否按流程实例授权 |
| 观测 | 状态机日志 + 端到端指标看板 | 是否有返工率来源（人工纠正记录） |

**一条总判据**：**每一层都要能写出"不选它的原因"**——写不出，说明还没量过自己的约束（与 [Ch6 §03 §7.1](../../06-multi-model/03-model-gateway/03-model-gateway-section-7-sec7.md) 同一把尺子）。

### 4.4 存量迁移

**从手工流程迁到自动化，四步**（每步可独立验证）：

1. **影子运行**：自动化跑，但**不写业务系统**（只产出"建议结果"），与人工结果对拍 2–4 周。判据：能列出"自动与人工不一致"的清单——**这份清单是后续调阈值与规则的靶子**。
2. **只读切换**：先接管"查与抽取"（用户仍手工录入），把抽取结果作为**提示**呈现。判据：用户是否认为"照着填比原来快"。
3. **低风险写入**：先对**可补偿**的动作开放自动写入（例如归档、通知），不可逆动作仍人审。判据：重复入账为 0；补偿动作演练通过。
4. **扩大写入面**：按字段与金额分段扩大（先小额、先白名单供应商）。判据：**返工率不上升**；介入率下降。

**迁移的判据代替"上线"**：办公自动化的"上线"不是一次发布，而是**介入率下降而返工率不上升**——这两个数是唯一可信的验收口径。

### 4.5 模板 / 示例

**模板 1：一条抽取结果的呈现（给人核对用）**

```text
单据：invoice/2026/1021/ab12.pdf（第 1 页）
┌ 字段 ──────── 抽取值 ────────── 置信度 ─ 原文位置 ─┐
│ 发票号         INV-2026-1021-88   0.98    第1页 右上 │
│ 开票日期       2026-10-18         0.96    第1页 右上 │
│ 金额（CNY）    128,000.00         0.71 ⚠  第1页 表格「合计」行 │
│ 供应商         ACME-001（别名匹配）0.63 ⚠  第1页 抬头 │
└─────────────────────────────────────────────────┘
⚠ 标记字段低于阈值 → 转人工核对（点开即跳到原文区域）
```

**判据**：低置信字段必须**显式标记且可一键跳到原文**（这是"介入率可控"的实现基础）。

**模板 2：补偿动作的执行记录**

```sql
CREATE TABLE process_action (
  action_id     BIGSERIAL PRIMARY KEY,
  process_id    TEXT NOT NULL,
  step          TEXT NOT NULL,
  action        TEXT NOT NULL,
  idem_key      TEXT NOT NULL UNIQUE,       -- 幂等：唯一约束就是并发安全的实现
  status        TEXT NOT NULL,              -- done | failed | compensated
  inverse_of    BIGINT,                     -- 若本条是补偿动作，指向被补偿的动作
  payload_digest TEXT NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL
);
```

**判据**：补偿动作**也要记一条流水**（`inverse_of` 指向原动作），否则事后无法证明"已退回"。

**模板 3：端到端看板（三个数）**

```text
本周 | 单据 1,240 张
  人工介入率  38%   （上周 46%）
  返工率       2.1% （上周 2.0%）
  流程成功率  97.4% （卡点：need_manual_fix 平均停留 6.2h）
```

**判据**：**三个数一起看**——介入率降、返工率稳，才是真进步；介入率降、返工率升，是把风险搬到了事后。

### 4.6 成本：这条链路的账单

**四块成本**【推算：口径固定，单价按你的采购口径代入】：

| 成本块 | 构成 | 优化动作 |
| --- | --- | --- |
| 解析成本 | 页数 × 单位解析成本（含 OCR） | 先判可解析性（质量差的直接转人工，别硬抽） |
| 抽取与生成成本 | 单据数 × 字段数 × 单次调用 | 只对"可解析"的文档抽取；Schema 瘦身（不必要的字段不抽） |
| 人工成本 | **介入率 × 单据数 × 单张核对时长** | 阈值标定是唯一的杠杆（介入率随阈值变化） |
| 执行与留痕 | 调用次数 + 留痕与工单存储 | 留痕分层（热 90 天 / 温 1 年），只存摘要与哈希 |

**算例（建立量级感）**：设日单据 `1,200` 张、平均 `12` 个字段、每张文档 `3` 页【经验：随业务形态浮动】。

- 抽取调用量 ≈ `1,200 × 12 = 1.44 万次/日`（量级：万次/日）；
- 人工成本：介入率 `40%` × `1,200` = `480` 张/日；按单张核对 `3` 分钟 → **约 24 人时/日**（量级：数人日/日）——**这是这条链路最大的一块成本，也是阈值标定价值最高的地方**；
- **判据**：介入率每下降 5 个百分点，约等于省下 `3 人时/日`（`1,200 × 5% × 3 分钟`）【推算：口径为"单据数 × 介入率变化 × 单张时长"】——**这比"抽取模型换一代"的收益更直接、更可测**。

### 4.7 容灾与故障演练

| 故障 | 演练动作 | 通过判据 | 常见失效点 |
| --- | --- | --- | --- |
| 文档解析失败 | 投放一批低质量扫描件 | 判定"不可解析"并转人工，**不硬抽** | 硬抽导致错单 |
| 抽错字段入库 | 人为把金额抽错并放行 | 能被对账 / 抽查发现，并能补偿冲销 | 无补偿动作 → 退不回 |
| 审批积压 | 停掉审批人回应 | 超时后按策略升级 / 转交，单据不永久挂起 | 人工节点无超时 |
| 跨系统超时 | 让 ERP 长时间无响应 | 熔断 → 失败分类 → 走补偿或转人工 | 无限重试导致重复入账 |
| 重复执行 | 用同一幂等键重跑流程 | 不产生第二笔入账 | 幂等键用自增 ID |
| 越权写入 | 用超出 scope 的凭证调用 | 被拒且记录原因 | 凭证 scope 过宽 |

**一条纪律**：**"错单入库"是本主题最严重的失效**——因此演练必须包含"发现 → 定位 → 补偿"完整闭环，而不只是"发现"。

### 4.8 演进路线：0 → 1 → 100

- **0 → 1（有人在用）**：流程与红线清单 + Schema 与字段级阈值 + 抽取（带原文位置）+ 人工核对入口。判据：介入率可测；低置信字段能被快速核对。
- **1 → 10（可信）**：幂等 + 补偿动作表 + 审批工单（含输入快照）+ 流程状态机（含超时）。判据：重复入账 0；补偿演练通过；审批可还原依据。
- **10 → 100（可运营 / 可交付）**：跨系统凭证托管 + 端到端三段指标 + 影子与分段放量 + （可选）受限端到端 Agent。判据：介入率下降而返工率不上升；越权演练通过。

### 4.9 自检清单

- [ ] 不可逆步骤清单有了吗？它们前面的校验与审批是什么？
- [ ] Schema 里每个字段的"可接受错误率"由业务写下来了吗？
- [ ] 「阈值 → 介入率 / 漏出率」曲线画过吗？高代价字段是否用了更严阈值？
- [ ] 抽取结果带原文位置吗？低置信字段能否一键跳转核对？
- [ ] 幂等键由业务要素构成吗？重跑会不会重复入账？
- [ ] 每个可写动作有逆向动作，或在 `no_compensation` 清单里且被前置审批吗？
- [ ] 补偿动作本身有没有留痕（`inverse_of`）？
- [ ] 每个状态（尤其人工节点）都有超时吗？超时动作是什么？
- [ ] 审批记录含输入快照（原文哈希 + 抽取结果）与理由吗？
- [ ] 凭证按流程实例、短期、最小 scope 吗？越权演练做过吗？
- [ ] 解析质量差的文档是转人工还是硬抽？
- [ ] 端到端三个数（介入率 / 返工率 / 成功率）都看得到吗？最近一次优化依据哪个？
- [ ] 影子运行阶段的"不一致清单"还在维护吗？
- [ ] 全链路能回放吗（输入、判断、动作）？

### 4.10 小结

> 本节小结：办公自动化的工程实现可以压缩成一句话——**先把红线画出来、把阈值量出来，再让自动化一步步接管**。八步顺序的实质是：红线决定闸门位置（步骤 1）、字段代价决定阈值（步骤 2）、解析质量决定抽取上限（步骤 3）、阈值曲线决定介入率（步骤 4）、幂等与补偿决定"错了能不能退"（步骤 5）、审批留痕决定责任可否认定（步骤 6）、凭证决定执行是否安全（步骤 7）、端到端指标决定"自动化"是否名副其实（步骤 8）。四块成本里**人工成本通常是最大的一项**，而它的杠杆只有一个：**阈值标定**——介入率每降 5 个百分点，收益比"换一代抽取模型"更直接、更可测。

> 💡 **思考锚点**：算一下你（或你想做的）链路的"介入率 × 单据数 × 单张核对时长"——它是这条链路真正的主成本吗？如果不是，说明人工已经很少（那下一步该看返工率）；如果是，那你今天最该做的是**画一次阈值曲线**，而不是去换模型。你打算先画曲线，还是先补补偿动作？
