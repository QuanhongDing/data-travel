## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

办公自动化的形态由**五条约束**决定，顺序不能颠倒：

1. **动作可逆性**：这一步是只读，还是会写进业务系统？写了之后能不能撤？（**不可逆动作是这条链路上唯一的"红线"**，它决定哪些步骤必须前置校验与审批。）
2. **数据敏感级**：文档里有个人信息 / 财务数据 / 合同条款吗？（决定权限域、留痕强度、能否出域。）
3. **错误代价分布**：哪些字段错了代价最高？（决定字段级阈值与转人工规则——这是本主题最重要的可调项。）
4. **流程的确定性程度**：流程是稳定的（如报销审批），还是经常有例外？（决定用工作流引擎做骨架，还是需要 Agent 处理分支。）
5. **人的位置**：谁是签字人、谁做异常处理？（决定闸门密度与人工介入率上限。）

> **判据的用法**：先用 1 定"红线"（不可逆步骤在哪、前置要什么）；用 2 定权限与留痕；用 3 定阈值；用 4 定架构（引擎 or Agent）；用 5 定闸门。跳过第 3 条最常见的后果：字段级阈值拍脑袋定，**要么介入率高得没人用，要么错单静默入库**。

**每条约束的"过关"是可核查的**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 动作可逆性 | 每一个可写步骤都有对应的**失败怎么退**（补偿动作）写下来 |
| 2 数据敏感级 | 敏感字段的可见域与留痕强度是**机器可读**的（不是文档） |
| 3 错误代价分布 | **每个字段**的"可接受错误率"由业务写下来过（不是整篇一个数） |
| 4 流程确定性 | 例外分支有清单；清单之外的例外有明确处置（拒绝 / 转人工） |
| 5 人的位置 | 每个审批节点有**具名的角色**与超时动作 |

第 3 条是本主题最容易被压平的一条：**把"整篇准确率"当指标时，阈值失去调节能力**——一个总分高但关键字段经常错的系统，会在"整体合格"的评价下持续产生错单；反过来，为压住小概率错误而把整体阈值收紧，会让介入率飙到没人用。**因此阈值必须按字段定，而"每个字段的可接受错误率"是一个业务决定，不是技术决定。**

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 文档问答（只读）

**被什么约束逼出来**：只想"快速查到文档里写了什么"（约束 1 的最轻一档：不写任何系统）。

**结构**：文档解析 → 切块与索引 → 检索 → 生成回答 + **引用回指（页码 / 段落）**。

**为什么这样设计有效**：因为它**完全不引入新的责任面**——不写任何业务系统，因此没有幂等、补偿、审批这一整套要求，上线周期与风险都最低。**它的有效性来自"责任面为零"这件事**，而这也划定了它的能力上限：**凡是需要改变系统状态的需求，它都办不到**（那是 3.2.2 之后的事）。

**代价**：解析质量决定上限（扫描件与复杂表格是短板）；**回答必须带引用**，否则无法核对。**"必须带引用"为什么是硬要求**：只读问答的产出会被人**抄进业务动作**（用文档里的金额去填单子），因此它的错误同样会传导到不可逆步骤上——**责任面为零不等于错误代价为零**。

**失效点**：把它当作"能办业务"的系统——它只是查询入口；**判据**：用户拿到答案后是否还要手工抄进系统（要抄，说明只是查询）。**这条判据同时指出了下一步**：如果用户普遍在抄，那么真正的需求是 3.2.2（抽取入库），而不是"把问答做得更准"。

**判定方法**：抽三条"答案就在某份文档里"的问题，看回答是否带得出**页码 / 段落级引用**，并点开引用看它能不能落到那一段原文；再问一句"用户拿到答案后还要不要手工抄进系统"。两个动作都不需要采购。

**真实使用**：本主题 §6.1 的微软一例给的是这一模式的输出侧——回答带**引用回指**，并记录"谁问的、问的什么、用了哪些材料"（§6.1 详细做法②）。**这一侧"解析与索引"在书内他处有具名工具可对照**：`04-data-assetization/01-multimodal-db` 的主文件把 Tesseract / PaddleOCR / EasyOCR 列在"OCR"一行、把 LayoutLMv3 列在"文档理解"一行，其 §4 另把 PyMuPDF / Unstructured 记作文档结构化——它们正是这一段链路的可核验实现。**但本节不引任何一家的问答准确率或引用命中率**：这两个量随文档版式与扫描质量变化，跨组织不可比——判定入口是上面那两条动作。【公开】（来源：`04-data-assetization/01-multimodal-db/01-multimodal-db.md` 工具表与其 §4；本主题 §6.1 详细做法②）

#### 3.2.2 结构化抽取入库（带字段级置信度与转人工）

**被什么约束逼出来**：需要把文档字段变成结构化数据（约束 3 的核心场景）。

**结构**：文档解析 → Schema 抽取（带置信度与原文位置）→ **字段级阈值分流**（高置信自动入库、低置信转人工核对）→ 入库（带幂等键）。

**为什么这样设计有效**：因为它**把"模型误差"限制在了低置信字段上**——高置信字段自动通过、低置信字段转人工，于是**人工只核对最不确定的部分**，介入率与错误率同时可控。**这里的关键机制是"阈值是一个可调旋钮"**：调高则介入率上升、错误率下降，调低反之；**没有字段级阈值，就没有这个旋钮**（整篇阈值只能全放或全拦）。

**代价**：Schema 与归一规则要按单据类型维护（金额单位、日期格式、主体别名）；**原文位置**要保存（供回指与核对）。**原文位置是"可核对"的前提**：人工核对时若还要自己在原文里找，核对成本会高到让人直接凭印象通过——**于是转人工变成了橡皮图章**（与 [Ch5 §02 §3.2.7](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的机制同源）。

**判据**：**按字段的 precision / recall**（不是整篇准确率）；以及**低置信字段的人工核对通过率**（若通过率极高，说明阈值过严、白花了人力）。两个数一起看才能校准阈值：通过率高 → 阈值可放宽；通过率低 → 说明模型在那些字段上确实不行，该改的是提示或规则，而不是继续加人。

**失效点**：把阈值定在"整篇"这一级——**它会同时决定"所有字段都放"或"一个字段错就全拦"**，于是系统退化成两个极端（介入率爆表，或错单静默入库），而"阈值是一个可调旋钮"这句话随之失效；**另一种失效是保存了置信度却没保存原文位置**——转人工的人仍要自己回原文里找，核对因此退化成橡皮图章（代价一栏的机制）。

**判定方法**：取最近一周的抽取结果，按字段数两个数——**"高置信自动通过"与"低置信转人工"的比例**，以及**转人工字段的核对通过率**；再随便挑一个低置信字段，看它能不能一键定位回原文那一块（页码 + 区域）。三个动作都不需要采购。

**真实使用**：本主题 §6.3 的飞书一例给的是这一模式最完整的形态——抽取产出"带位置的结构化字段"而非一段摘要，让下游可以是流程而不只是人（§6.3 详细做法①②③）；§4.2（2）给出 Schema 与 `provenance` 的字段形态，§4.5 模板 1 给出给人核对时的呈现格式（低置信字段显式标 ⚠ 且可一键跳原文）。**"按 Schema 做约束抽取"这一侧在书内他处也有具名实现可对照**：`04-data-assetization/01-multimodal-db` 把 LayoutLMv3 记为"文档理解"、把 PaddleOCR 记为"OCR"，`10-industry-agent/01-multimodal-ai` 的 §4 另给出"PaddleOCR 做确定性转写、版面模型给坐标、模型做理解与组织，关键字段的最终取值取自确定性路径"的组合——那是同一件事在文档侧的另一种分工写法。【公开】（来源：`04-data-assetization/01-multimodal-db/01-multimodal-db.md` 工具表；`10-industry-agent/01-multimodal-ai/01-multimodal-ai-section-4-sec4.md` §4；本主题 §6.3、§4.2（2）与 §4.5 模板 1）

#### 3.2.3 起草与润色（人审后使用）

**被什么约束逼出来**：邮件、纪要、通知这类文本需要"写"，但对外发送不可逆（约束 1）。

**结构**：给定要点 + 事实材料 → 生成草稿 → **人审确认后才发送 / 归档**；草稿必须保留"依据材料"的引用。

**为什么这样设计有效**：因为**"写"与"负责"可以被分开，而"写"的部分恰好是成本最高的部分**——起草占用的时间远多于审阅，把起草自动化后，人从"创作者"变成"审阅者"，同样的人力可以处理更多份。**但这笔收益完全依赖一个前提：审阅者真的在审**——若草稿好到让人直接点发送，就会退化成"更长的人审链条里的橡皮图章"，此时**人审的成本没降、责任却已经转移**。

**代价**：人审仍占用时间（价值来自"改比写快"）；**风格与既有模板要对齐**（否则每次都要大改）。**"风格不对齐"会直接吃掉收益**：如果每份草稿要改三成以上，审阅时间就接近自己写——**因此"模板对齐"不是美观问题，而是这笔投入能否回本的分界**。

**失效点**：把草稿直接发出去了——**这是本主题最常见的越界**；判据是"发送动作是否有人审闸门"（可查）。

**判定方法**：抽最近一个月已发出的对外草稿，数两个数——**平均改写比例**（改掉几成才能发）与**发送动作是否都经过同一个可查的人审闸门**；若改写比例长期超过三成，这一模式的收益已经被吃掉（代价一栏的机制）。样本量要够到能分辨差异，口径同 §4.2（3）。

**真实使用**：本主题 §6.1 的微软一例给的是这一模式的可核验一侧——**输出带引用回指**并记录"谁问的、问的什么、用了哪些材料"（§6.1 详细做法②），也就是把"写"与"依据"绑在一起；§4.2（6）给出审批工单里 `input_snapshot` 与 `reason` 的字段形态，`reason` 必填正是为了不让闸门退化成点"同意"。**本节不给任何一家起草类产品的"改写比例"或"采纳率"**——办公自动化的效果数据几乎都来自建设方，且强依赖各家自己的模板与文体（§5.3.6 第二步）；判定入口是你自己那批草稿的改写比例与那个人审闸门。【经验：起草类效果数据无第三方可对照，故不具名】

#### 3.2.4 单据审核（规则 + 模型 + 人审三层）

**被什么约束逼出来**：单据要判断"该不该批"（约束 2、3、5）。

**结构**：**规则层**（金额上限、供应商白名单、必填项、预算余额——确定性、可解释）→ **模型层**（异常识别、条款风险、材料一致性——概率性，带置信度）→ **人审层**（规则命中红线或模型低置信时转人工）。

**为什么这样设计有效**：因为**"必须拦"与"值得看"这两件事的证据标准不同**——红线规则（超预算、供应商在黑名单）一旦判错，业务会问"凭什么"，因此它的依据必须是**可复述的规则**；异常识别本身是概率判断，业务能接受"模型觉得可疑"。**三层的有效性来自让每类判断用它自己需要的可解释性标准**；把两者混在一起，结果必然是"要么规则被稀释、要么模型背锅"。

**代价**：三层要有清晰的**转人工规则**（否则要么全转人工、要么放过异常）；误报要能归因到规则或模型阈值。**"转人工规则"的设计难点是它同时受两个约束**：约束 3（错误代价分布）决定哪些字段必须转，约束 5（人的位置）决定能承受多少量——**这两个约束冲突时，唯一的出路是收窄自动化的字段范围，而不是加人**。

**判据**：**红线规则的拦截数**（下限保障）+ **模型意见的采纳率 / 忽略率** + **误判单的归因率**。

**失效点**：把"必须拦"的判断交给模型——红线规则一旦由概率系统给出，业务问"凭什么"时你只能答"模型觉得可疑"，于是**一次误判就让规则层失去权威**（"批量忽略"从此成为默认动作）；另一种失效是把三层混成一层：规则命中与模型低置信走同一个转人工通道，于是**误判无法归因**——事后分不清是规则过宽还是阈值过低，也就无从改。

**判定方法**：取最近一个月的拦截记录，数三件事——**红线规则各自命中了几次**、**模型意见被采纳与被忽略的比例**、**被推翻的误判里有多少能归因到某条规则或某个阈值**。第三个数答不出来的部分，就是还没有归因字段。

**真实使用**：本主题 §6.2 的钉钉一例给的是这一模式在流程里的落点——**Agent 的输出只是某个状态节点上的判断与字段，不承担"下一步是什么"**（§6.2 详细做法①③），判断与动作因此可以分开归因；§4.2（6）给出审批工单里"规则命中 + 模型分数 + 决定 + 理由"的四段结构。**"确定性规则"这一侧在书内他处已有具名工具可对照**：`09-data-intelligence-product/02-decision-intelligence` 的 §4.3 工具链表把 Drools、Easy Rules、Aviator、QLExpress、Camunda、IBM ODM 列在"规则引擎与决策表"一行，并把 OMG DMN 及其实现（Camunda DMN / Drools DMN）单列为决策表标准侧；同一节的判据是"规则由谁改、要不要逐条举证"——它们正是"可复述、可逐条举证"的那一类，与该判据是同一把尺子。**落到本主题的这一格上**：规则引擎对应 §3.2.4 的"红线规则层"（超预算 / 黑名单 / 必填项——由业务改、能逐条举证的那一层），DMN 决策表则对应"可逐条举证的拦截依据"这一要求；它们不是 §3 的新模式，只是这一层在书内的具名实现。【公开】（来源：`09-data-intelligence-product/02-decision-intelligence/02-decision-intelligence-section-4-sec4.md` §4.3 工具链表与其判据；本主题 §6.2 与 §4.2（6））

#### 3.2.5 流程编排（状态机 + 超时 + 审批 + 留痕）

**被什么约束逼出来**：多步流程需要"推进、等待、超时、回退"（约束 4）。

**结构**：**状态机**显式建模（含人工节点、等待节点、失败节点）→ 每步有超时与重试分类 → 审批节点记录"输入快照 + 依据 + 动作 + 人 + 时间"。

**为什么这样设计有效**：因为**状态机的价值不在"跑得顺"，而在"卡住时能被看见"**——散落的 `if-else` 里，一个单据停在"等审批"这个状态是**不可观测的**（它只是没有下一步），而显式状态机让"每个状态都有超时"成为可检查的约束。**同时它把留痕的粒度定在了"节点"上**：因为每个节点的输入与输出都是显式对象，"审批记录含输入快照"才有可能实现。

**代价**：状态机建模成本（流程图与实现要对齐）；异常分支的处置要写清楚（否则实现里会散落 if-else）。**"流程图与实现对齐"的机制**：两者一旦分叉，"有多少单据卡在哪一步"这类统计就不再可信——**而这类统计是本主题唯一能回答"流程是否在运转"的数据**。

**判据**：**每个状态都有超时**（尤其人工节点）；**审批记录含输入快照**（不只记"已批准"）。**输入快照为什么是必需项**：审批的对象是**当时那份材料**，而不是"这类申请"；只记"已批准"时，事后无法回答"当时基于什么批的"——而这正是责任认定（约束 5）的全部内容。

**失效点**：把"等人"当成无状态——人工节点没有超时，单据会永久挂起，而它在统计上只显示为"处理中"，**不显示为失败，因此安静地积累**（§6.2 详细做法②的机制）；另一种失效是流程图与实现分叉：两边一旦不同步，"有多少单据卡在哪一步"就不再可信——**而这是本主题唯一能回答"流程是否在运转"的数据**（代价一栏的机制）。

**判定方法**：把所有状态（含人工节点）连超时值列成一张表，**空着的那几行就是未来的积压点**；再当场查一次"当前有多少单据卡在哪一步、平均卡了多久"——答不出这个数，说明状态机没有真的建立。两个动作都不需要采购。

**真实使用**：本主题 §6.2 的钉钉一例讲的就是"骨架由既有流程引擎承担、Agent 不重建状态机"（§6.2 触发点与详细做法①）；§4.2（4）给出状态机的配置形态（每个状态带超时值与超时动作）。**"持久化状态机 + 超时 + 人工审批节点"这一侧在书内他处已有具名引擎可对照**：`03-data-stack/12-scheduler` 的 §7 选型清单把 Camunda、Flowable 一类列为"面向业务流程与人工审批节点"的通用工作流引擎（并指出它们不是数据批次编排），`03-data-stack/07-architecture-decisions` 的 §8 第四层"云原生调度演进"把 Temporal 记为"分布式工作流引擎，高复杂度 + 多步骤场景首选"，`03-data-stack/12-scheduler/12-scheduler.md` 另把"调度系统 vs 工作流引擎"列成一组对照；`01-modeling/01-business-process-modeling` 的主文件则把 BPMN 流程建模定位为"过程执行"，判据是"这张图会不会被下游执行或审计引用"，工具侧给出 BPMN.io / bpmn-js / Camunda Modeler。**这几处合起来就是"状态机不是要重写的，而是要去用的"这句话在书内的具名落点。**【公开】（来源：`03-data-stack/12-scheduler/12-scheduler-section-7-sec7.md` §7 与 `03-data-stack/12-scheduler/12-scheduler.md` 的"调度系统 vs 工作流引擎"；`03-data-stack/07-architecture-decisions/07-architecture-decisions-section-8-sec8.md` §8；`01-modeling/01-business-process-modeling/01-business-process-modeling.md` 建模工具行与 BPMN 行；本主题 §4.2（4））

#### 3.2.6 跨系统执行（凭证托管 + 幂等 + 补偿）

**被什么约束逼出来**：一张单据要写进多个系统，部分成功是常态（约束 1、2）。

**结构**：**凭证托管**（按流程实例发放最小权限短期凭证）→ 执行（带**幂等键**）→ 失败分类（可重试 / 需补偿）→ **补偿动作**（冲销 / 红字单 / 人工介入）。

**为什么这样设计有效**：因为**"部分成功"不是一个异常分支，而是分布式写入的常态**——把它当成需要特殊处理的意外，就会在实现里留下"假装不会发生"的路径；把它当成显式状态，系统才具备"从任意中间点收敛"的能力。**幂等与补偿是这条路径的两个组成**：幂等负责"重试不重复"，补偿负责"失败能退"；**只有前者时，系统能在失败后安全重试，但仍可能停在一个不可接受的中间状态**。

**代价**：补偿动作要**逐个业务系统定义**（没有通用的"回滚 API"）；凭证托管要求内部身份体系到位。**"没有通用回滚 API"是本主题最现实的一条约束**：财务系统里"退"通常是一条新单据（红字单），而不是撤销——**因此补偿动作表是一份业务文档，不是技术组件**，它需要财务与业务共同确认。

**失效点**：把写操作放在链路中间且没有补偿动作——一旦后续步骤失败，**已执行的步骤退不回来**（与 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md) 的"不可逆动作不可置于中间"同源）。**判据可以写成一条检查**：把链路按顺序画出来，在每个可写步骤后问"如果下一步失败，这一步怎么退"——**答不出的那一格，就是这条链路的红线所在。**

**判定方法**：把链路按顺序画出来，在**每个可写步骤后面写一句"如果下一步失败，这一步怎么退"**——答不出的那一格标红；再做一次演练：用同一个幂等键重跑一次流程，看会不会产生第二笔入账。两个动作都不需要采购。

**真实使用**：本主题 §6.4 的匿名案例给的就是这一模式的完整形态——补偿动作表由业务 / 财务确认、不可逆步骤不放链路中间、幂等键取业务要素（§6.4 详细做法①②③）；§4.2（5）给出幂等键的取法与 `compensations` / `no_compensation` 的清单形态，§4.5 模板 2 给出补偿动作的流水表（含 `inverse_of`）。**"补偿式一致性没有通用回滚接口"这一条在书内他处也有具名落点**：本主题 §8.3 的参考资料已把 Ch12 的"数据一致性"与"灰度与回滚"两节列作同一族做法（Saga / TCC 一类）；`00-introduction/04-glossary` 的术语表把 "Saga / 2PC / TCC" 收作"分布式事务模式"。**本节不给任何一家的补偿成功率**：补偿动作表是业务特有的、没有通行清单（§5.2 表里"流程状态机 + 可补偿动作"一行的 ② 栏写的就是这句）。【公开】（来源：本主题 §4.2（5）、§4.5 模板 2、§8.3 参考资料；`00-introduction/04-glossary/04-glossary.md` 术语表；`12-architecture/08-data-consistency`）

#### 3.2.7 RPA + Agent 混合（确定性走 RPA，理解走模型）

**被什么约束逼出来**：既有系统没有 API，只能走界面；但界面操作的脆弱性又需要"理解"来兜底（约束 4）。

**结构**：**模型负责"读与判断"**（读界面 / 文档、判断该点哪里、异常时给出解释）→ **RPA / 脚本负责"点与写"**（确定性执行）→ 界面变化时由模型给出**变更建议**（而不是让模型直接操作）。

**为什么这样设计有效**：因为它**按"脆弱性来源"做了切分**——RPA 的脆弱来自**界面变化**（外部原因，可批量修复）；模型的脆弱来自**理解偏差**（概率原因，不可批量修复）。把两者分开，**修复成本就从"每次都要人看"降到"界面变了批量改选择器"**；而模型的价值变成"提早告诉你界面变了"（它能量出"这里点不到"），而不是"自己想办法点"。

**代价**：混合链路的调试更复杂（要区分"理解错"与"执行错"）；**界面变化仍需人工确认修法**（模型只给建议）。**"只给建议"的理由是责任**：模型直接改选择器意味着**一次误判会静默地让所有同类操作错位**；而给出建议、由人确认，把错误暴露在变更时刻而不是执行时刻。

**判据**：**"理解错"与"执行错"能否分开观测**（各自的失败率与日志）。**这条判据是一道门槛**：分不开就说明链路里"读"与"写"的边界没有划出来，后续所有优化都会找不到靶点。

**失效点**：让模型直接操作界面——**脆弱与不可归因会同时发生**：界面一改就大面积失败，而失败时又分不清是"理解错"还是"执行错"（§3.5 反模式表的第一条就是这个）；另一种失效是用坐标定位：分辨率与布局一变即失效，而且失效是批量的、同时发生的，不是逐条的。

**判定方法**：**故意让一个界面元素消失**（改个标签或挪个位置），看系统给出的是"这里点不到"的**可归因失败**，还是静默地操作到了别处；再确认"理解错"与"执行错"能不能分别从日志里数出来。两个动作都不需要采购。

**真实使用**：这一模式在书内他处有两条具名对照。`10-industry-agent/01-multimodal-ai` 的 §4 把文档链路的同一分工写成"PaddleOCR 做确定性转写、版面模型给坐标，模型做理解与组织，**关键字段的最终取值取自确定性路径**"——那句话是"确定性执行与概率性理解分家"在文档侧的完全同构形态；同主题的 §8 又把 RPA 与 Computer Use Agent 的差别写成"RPA 是**预定义脚本**（按录制步骤执行）、Computer Use Agent 是**自主决策**（按目标动态规划）"，并记下"当前稳定性不如 RPA，生产落地仍以 RPA 为主"。§4.3 工具链表则把"API 直连优先，无 API 时走 RPA"写成选型判据。**本节不点名任何一家的 RPA 产品**：这类产品的接口差异大、公开材料几乎都是厂商自述（§5.2 表里"RPA 与模型分工"一行的 ③ 栏写的就是"部分成立"）。【公开】（来源：`10-industry-agent/01-multimodal-ai/01-multimodal-ai-section-4-sec4.md` §4 与同主题 `-section-8-sec8.md` §8；本主题 §4.3 工具链表）

#### 3.2.8 受限端到端 Agent（白名单动作 + 全链路留痕）

**被什么约束逼出来**：业务希望"一句话把事办完"（约束 1、5 的最激进形态）。

**结构**：**动作白名单**（只允许已登记的动作，与 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的工具出口同一套治理）+ 每步留痕 + 不可逆动作前置审批 + **全链路可回放**。

**为什么这样设计有效**：因为**边界由系统强制而不是由提示词约束**——"不允许做的事"如果只写在提示里，它约束的是一个概率系统；写成白名单时，**它约束的是执行器**。**这条差别决定了风险的量级**：前者是"可能发生"，后者是"不可能发生但会明确失败"。而**明确失败正是可接受的形态**——用户得到"这个动作不支持"的反馈，比得到一个"看起来做了但做错了"的结果更好。

**代价**：白名单之外的请求会失败（需要清晰的"为什么不能做"反馈）；回放与留痕的存储成本上升。**"清晰的失败反馈"不是体验优化**：没有它时，用户会反复尝试不被支持的动作，而**"模型做不到"与"系统不允许"在用户看来是同一件事**——前者会被投诉，后者会被接受。

**失效点**：把"能做的动作集"交给模型决定——那等于把风险交给概率；判据是**动作集由注册表定义，模型只能选择其中一项**。

**判定方法**：随便提一个**不在注册表里**的动作，看系统给的是"这个动作不支持"的明确反馈，还是一段"我试着做了"的对话；再把最近一次执行的三段留痕（输入、判断、动作）拉出来，看能不能完整回放。两个动作都不需要采购。

**真实使用**：本主题 §6.1 的微软一例给的是这一模式的边界形态——**助手可见域由既有权限决定、先裁剪再检索**（§6.1 详细做法①），也就是"边界由系统强制而不是由提示词约束"在权限面上的落点；§4.2（7）给出跨系统执行的凭证与失败分类形态。**"动作白名单"这一侧在书内他处已有三处具名落点**：`11-cross-cutting/04-observability` 的 §4 把"自动动作白名单"列为 Agent 自动修复的上线前置产物，并要求**每个动作带幂等说明、回滚命令、允许的最大影响面**（其模板 7 就是这份白名单的形态）；`08-ai-governance/01-ai-data-governance` 的 §7 在"Agent 治理"一行把治理要素写成"授权人、被授权动作白名单、动作上限、人在回路的触发条件"；`08-ai-governance/02-data-security-and-compliance` 的 §8 则把"工具出口的鉴权与**人审闸门**"记作"不可绕过的唯一出口"。**这三处合起来就是"动作集由注册表定义、模型只能选择其中一项"这句话在书内的具名落点。**【公开】（来源：`11-cross-cutting/04-observability/04-observability-section-4-sec4.md` §4 与其模板 7；`08-ai-governance/01-ai-data-governance/01-ai-data-governance-section-7-sec7.md` §7 治理要素表；`08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance-section-8-sec8.md` §8；本主题 §6.1 与 §4.2（7））

### 3.3 模式选择决策表

| 约束组合 | 推荐形态 | 必须同时上的部件 | 不选它的原因（反面） | 关键判据（可核查） |
| --- | --- | --- | --- | --- |
| 只读、想快速查文档 | 3.2.1 文档问答 | 解析 + 索引 + 引用回指 | 直接做自动入库风险大 | 用户是否还要手工抄录（是→仍是查询） |
| 需要结构化字段 | 3.2.2 抽取入库 | 字段级置信度、转人工、幂等键、原文位置 | 整篇阈值会导致介入率失控 | 按字段的 precision / recall；转人工通过率 |

| 需要判断该不该批 | 3.2.4 三层审核 | 红线规则、模型阈值、归因字段、转人工规则 | 单靠模型无法审计、单靠规则覆盖不足 | 红线拦截数 + 采纳率 / 忽略率 |
| 多步流程（含等待） | 3.2.5 流程编排 | 状态机、超时、审批留痕（含输入快照） | 用散落 if-else 替代状态机 → 无法审计 | 每个状态是否有超时；能否统计"卡在哪一步" |
| 要写多个系统 | 3.2.6 跨系统执行 | 凭证托管、幂等、**补偿动作表**（业务文档） | 无补偿 → 部分成功退不回 | 每个可写步骤的"失败怎么退" |
| 既有系统无 API | 3.2.7 RPA + Agent 混合 | 理解 / 执行分离、变更建议（不自动改） | 让模型直接点界面 → 脆弱且难查 | 两类错误能否分开观测 |
| 业务要"一句话办完" | 3.2.8 受限端到端 | 动作白名单、全链路留痕、前置审批、失败反馈 | 动作集交给模型 = 风险不可控 | 动作集是否来自注册表 |

### 3.4 组合模式：真实系统不会只用一种

1. **骨架 + 填充**：3.2.5（状态机骨架）+ 3.2.2 / 3.2.4（模型填充理解与判断）——**办公自动化的标准形态**。
2. **执行 + 兜底**：3.2.6（跨系统执行 + 补偿）+ 3.2.7（无 API 时走 RPA）——执行器怎么变，**幂等与补偿的纪律不变**。
3. **文档链路**：3.2.1（问答，给人用）+ 3.2.2（抽取，给系统用）——**同一份解析与索引支撑两种消费**，不要建两套。
4. **边界组合**：3.2.8（端到端）+ 3.2.4（审核三层）——端到端的每一步仍在白名单与规则之下。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 上了抽取但没上幂等 | 重复入账，财务数据失真 |
| 上了状态机但人工节点无超时 | 单据永久挂起，且"卡在哪一步"统计不出来 |
| 上了端到端但动作集不是白名单 | 模型能"发明"动作，风险不可控 |
| 转人工不带原文位置 | 核对成本高 → 转人工退化为橡皮图章 |
| 草稿与既有模板不对齐 | 改写比例过高，收益被吃掉 |
| 审批只记"已批准" | 事后无法还原依据，责任无法认定 |
| 补偿动作表由技术单方定义 | 与财务口径不符，退不干净 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **让模型直接操作界面** | 界面小改后大面积失败 | 脆弱且难归因 | 把"理解"与"执行"混在一起做 |
| **整篇阈值而非字段级** | 介入率极高（或错单静默入库） | 阈值失去调节能力 | 只做了一个总分 |
| **无幂等键** | 同一单据重复入账 | 财务数据失真 | 只考虑"失败要重试" |
| **不可逆步骤放在链路中间** | 后续失败后已付款退不回 | 资损 | 没有补偿动作表 |
| **审批只记"已批准"** | 事后无法还原依据 | 责任无法认定 | 留痕按结果设计 |
| **人工节点无超时** | 单据永久挂起 | 流程停滞、时效不达标 | 把"等人"当无状态 |
| **草稿直接对外发送** | 出现在客户邮箱里 | 不可逆的沟通事故 | 人审闸门缺失 |
| **无端到端指标** | 只报字段准确率 | 不知道自动化是否真在替人干活 | 指标容易选（准确率好测） |
| **凭证长期驻留** | 凭证泄漏面随流程数扩大 | 安全风险 | 按服务发放而非按流程实例 |
| **白名单之外无提示** | 用户反复尝试不被支持的动作 | "模型做不到"与"系统不允许"被混淆 | 只做了拒绝对话，没做能力边界说明 |
| **转人工不带原文位置** | 人工核对靠自己找原文 | 核对退化为橡皮图章 | 保存原文位置当时没做 |
| **补偿动作由技术单方定义** | 冲销与财务口径不符，账留尾差 | 退不干净 | 补偿被当成技术组件而不是业务约定 |
| **草稿与模板不对齐** | 每份草稿要改三成以上 | 审阅时间接近自己写，收益归零 | 模板对齐被当成美观问题 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 手工 → 文档问答 | 查文档占掉大量时间 | 3.2.1 | 解析与索引（成本低，收益快） |
| 问答 → 抽取入库 | 用户还要手工抄录 | 3.2.2 | Schema、字段级阈值、幂等键、原文位置 |
| 单步 → 多步流程 | 需要等待与二次确认【经验：出现"等审批 / 等材料"就会触发】 | 3.2.5 | 状态机建模与留痕改造 |
| 单系统 → 多系统 | 出现部分成功 | 3.2.6 | 补偿动作表（需业务共同定义）+ 凭证托管 |
| 有 API → 无 API 系统 | 必须走界面 | 3.2.7 | 理解 / 执行分离、变更建议链路 |
| 受限 → 端到端 | 用户要求"一句话办完" | 3.2.8 | 动作白名单 + 全链路留痕（**不可跳过**） |
| 全自动 → 按字段分级 | 介入率与错单率同时难降 | 3.2.2 的字段级阈值 | 需要业务逐字段给出"可接受错误率"（人力投入在业务侧） |

**一条通用判据**：**跃迁的触发点不是"量变大"，而是"某个失效形态第一次出现"**——第一次出现"同一单据入账两次"就该上幂等；第一次出现"已付款退不回"就该上补偿；第一次出现"说不清卡在哪一步"就该上状态机。**按业务量预设跃迁点，几乎一定过早或过晚。**

### 3.7 自检清单

- [ ] 链路里哪些步骤**不可逆**？它们是否都放在了校验与审批之后？**在每个可写步骤后问"下一步失败时这一步怎么退"**——答不出的那一格就是红线。
- [ ] 抽取是**字段级阈值**吗？每个字段的"可接受错误率"由业务写下来了吗？
- [ ] 低置信字段转人工的**介入率**是多少？人工核对的通过率是多少（过高说明阈值过严）？
- [ ] 抽取结果带**原文位置**吗？人工能一键核对吗？
- [ ] 写操作有**幂等键**吗？键取的是业务要素还是自增 ID？
- [ ] 每个可写步骤的**失败怎么退**（补偿动作）写下来了吗？这份表是否经业务 / 财务确认过？
- [ ] 人工节点都有**超时**吗？超时后的动作是什么（默认不执行 / 转交）？
- [ ] 审批记录里有没有**输入快照**与依据？能否还原"当时基于什么批的"？
- [ ] 能否统计"当前有多少单据卡在哪一步"？流程图与实现对得上吗？
- [ ] 跨系统凭证是**按流程实例**发放的吗？权限是否最小？
- [ ] 起草类输出**是否必须人审**才对外发送（可查）？草稿的平均改写比例是多少？
- [ ] "理解错"与"执行错"能分开观测吗（RPA 混合场景）？
- [ ] 端到端两个指标（介入率、返工率）都有吗？最近一次优化的依据是哪个？
- [ ] 端到端 Agent 的动作集来自**注册表白名单**吗？不被支持的动作有没有明确的失败反馈？
- [ ] 全链路能回放吗（输入、判断、动作三段留痕）？

### 3.8 小结

> 本节小结：办公自动化的形态由五条约束按序决定——**动作可逆性 → 数据敏感级 → 错误代价分布 → 流程确定性 → 人的位置**；八种模式里，**状态机骨架（3.2.5）与跨系统执行纪律（3.2.6：凭证 + 幂等 + 补偿）是这条链路的承重结构**，**字段级置信度与转人工（3.2.2 / 3.2.4）是把模型误差约束在可承受范围的唯一手段**，而**起草人审（3.2.3）与动作白名单（3.2.8）是不可越过的两条边界**。判断这一支有没有建成，只看两条：**单据能不能在无人盯着时走完**；**走错时能不能被发现并退回**。**本主题还有一条特有的判据**：补偿动作表是一份业务约定而不是技术组件——它由技术单方定义时，退不干净只是时间问题。

> 💡 **思考锚点**：在你的流程里找出**第一个不可逆步骤**（已发款、已对外发送、已入账），然后回答：它前面有哪些校验与审批？如果答案是"没有"或"靠人记得"，那你现在最该做的不是优化抽取准确率，而是**把它前面的闸门补上**——你打算先补哪一道？
