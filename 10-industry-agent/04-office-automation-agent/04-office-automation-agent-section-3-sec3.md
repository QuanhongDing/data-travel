## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

办公自动化的形态由**五条约束**决定，顺序不能颠倒：

1. **动作可逆性**：这一步是只读，还是会写进业务系统？写了之后能不能撤？（**不可逆动作是这条链路上唯一的"红线"**，它决定哪些步骤必须前置校验与审批。）
2. **数据敏感级**：文档里有个人信息 / 财务数据 / 合同条款吗？（决定权限域、留痕强度、能否出域。）
3. **错误代价分布**：哪些字段错了代价最高？（决定字段级阈值与转人工规则——这是本主题最重要的可调项。）
4. **流程的确定性程度**：流程是稳定的（如报销审批），还是经常有例外？（决定用工作流引擎做骨架，还是需要 Agent 处理分支。）
5. **人的位置**：谁是签字人、谁做异常处理？（决定闸门密度与人工介入率上限。）

> **判据的用法**：先用 1 定"红线"（不可逆步骤在哪、前置要什么）；用 2 定权限与留痕；用 3 定阈值；用 4 定架构（引擎 or Agent）；用 5 定闸门。跳过第 3 条最常见的后果：字段级阈值拍脑袋定，**要么介入率高得没人用，要么错单静默入库**。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 文档问答（只读）

**被什么约束逼出来**：只想"快速查到文档里写了什么"（约束 1 的最轻一档：不写任何系统）。

**结构**：文档解析 → 切块与索引 → 检索 → 生成回答 + **引用回指（页码 / 段落）**。

**为什么有效**：零风险（不写系统）、上线快、价值直接（省掉人工翻阅）。

**代价**：解析质量决定上限（扫描件与复杂表格是短板）；**回答必须带引用**，否则无法核对。

**失效点**：把它当作"能办业务"的系统——它只是查询入口；**判据**：用户拿到答案后是否还要手工抄进系统（要抄，说明只是查询）。

#### 3.2.2 结构化抽取入库（带字段级置信度与转人工）

**被什么约束逼出来**：需要把文档字段变成结构化数据（约束 3 的核心场景）。

**结构**：文档解析 → Schema 抽取（带置信度与原文位置）→ **字段级阈值分流**（高置信自动入库、低置信转人工核对）→ 入库（带幂等键）。

**为什么有效**：把"模型误差"限制在**低置信字段**上，人工只核对最不确定的部分——**介入率可控、错误可控**。

**代价**：Schema 与归一规则要按单据类型维护（金额单位、日期格式、主体别名）；**原文位置**要保存（供回指与核对）。

**判据**：**按字段的 precision / recall**（不是整篇准确率）；以及**低置信字段的人工核对通过率**（若通过率极高，说明阈值过严、白花了人力）。

#### 3.2.3 起草与润色（人审后使用）

**被什么约束逼出来**：邮件、纪要、通知这类文本需要"写"，但对外发送不可逆（约束 1）。

**结构**：给定要点 + 事实材料 → 生成草稿 → **人审确认后才发送 / 归档**；草稿必须保留"依据材料"的引用。

**为什么有效**：把"写"的成本降下来，把"负责"仍留给人。

**代价**：人审仍占用时间（价值来自"改比写快"）；**风格与既有模板要对齐**（否则每次都要大改）。

**失效点**：把草稿直接发出去了——**这是本主题最常见的越界**；判据是"发送动作是否有人审闸门"（可查）。

#### 3.2.4 单据审核（规则 + 模型 + 人审三层）

**被什么约束逼出来**：单据要判断"该不该批"（约束 2、3、5）。

**结构**：**规则层**（金额上限、供应商白名单、必填项、预算余额——确定性、可解释）→ **模型层**（异常识别、条款风险、材料一致性——概率性，带置信度）→ **人审层**（规则命中红线或模型低置信时转人工）。

**为什么有效**：把"必须拦"与"值得看"分开；规则保证下限（可审计），模型提升覆盖（发现规则写不出的异常）。

**代价**：三层要有清晰的**转人工规则**（否则要么全转人工、要么放过异常）；误报要能归因到规则或模型阈值。

**判据**：**红线规则的拦截数**（下限保障）+ **模型意见的采纳率 / 忽略率** + **误判单的归因率**。

#### 3.2.5 流程编排（状态机 + 超时 + 审批 + 留痕）

**被什么约束逼出来**：多步流程需要"推进、等待、超时、回退"（约束 4）。

**结构**：**状态机**显式建模（含人工节点、等待节点、失败节点）→ 每步有超时与重试分类 → 审批节点记录"输入快照 + 依据 + 动作 + 人 + 时间"。

**为什么有效**：流程的确定性被固化下来；**留痕使责任可认定**（不可否认）。

**代价**：状态机建模成本（流程图与实现要对齐）；异常分支的处置要写清楚（否则实现里会散落 if-else）。

**判据**：**每个状态都有超时**（尤其人工节点）；**审批记录含输入快照**（不只记"已批准"）。

#### 3.2.6 跨系统执行（凭证托管 + 幂等 + 补偿）

**被什么约束逼出来**：一张单据要写进多个系统，部分成功是常态（约束 1、2）。

**结构**：**凭证托管**（按流程实例发放最小权限短期凭证）→ 执行（带**幂等键**）→ 失败分类（可重试 / 需补偿）→ **补偿动作**（冲销 / 红字单 / 人工介入）。

**为什么有效**：把"部分成功"这一现实变成显式处理路径；幂等保证重试不重复入账。

**代价**：补偿动作要**逐个业务系统定义**（没有通用的"回滚 API"）；凭证托管要求内部身份体系到位。

**失效点**：把写操作放在链路中间且没有补偿动作——一旦后续步骤失败，**已执行的步骤退不回来**（与 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md) 的"不可逆动作不可置于中间"同源）。

#### 3.2.7 RPA + Agent 混合（确定性走 RPA，理解走模型）

**被什么约束逼出来**：既有系统没有 API，只能走界面；但界面操作的脆弱性又需要"理解"来兜底（约束 4）。

**结构**：**模型负责"读与判断"**（读界面 / 文档、判断该点哪里、异常时给出解释）→ **RPA / 脚本负责"点与写"**（确定性执行）→ 界面变化时由模型给出**变更建议**（而不是让模型直接操作）。

**为什么有效**：把脆弱性收敛到"确定性执行器"的维护上，同时用模型降低"维护成本"（它能量出界面变了）。

**代价**：混合链路的调试更复杂（要区分"理解错"与"执行错"）；**界面变化仍需人工确认修法**（模型只给建议）。

**判据**：**"理解错"与"执行错"能否分开观测**（各自的失败率与日志）。

#### 3.2.8 受限端到端 Agent（白名单动作 + 全链路留痕）

**被什么约束逼出来**：业务希望"一句话把事办完"（约束 1、5 的最激进形态）。

**结构**：**动作白名单**（只允许已登记的动作，与 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的工具出口同一套治理）+ 每步留痕 + 不可逆动作前置审批 + **全链路可回放**。

**为什么有效**：在明确边界内获得端到端效率；边界由系统强制（不是靠提示词约束）。

**代价**：白名单之外的请求会失败（需要清晰的"为什么不能做"反馈）；回放与留痕的存储成本上升。

**失效点**：把"能做的动作集"交给模型决定——那等于把风险交给概率；判据是**动作集由注册表定义，模型只能选择其中一项**。

### 3.3 模式选择决策表

| 约束组合 | 推荐形态 | 必须同时上的部件 | 不选它的原因（反面） | 关键判据（可核查） |
| --- | --- | --- | --- | --- |
| 只读、想快速查文档 | 3.2.1 文档问答 | 解析 + 索引 + 引用回指 | 直接做自动入库风险大 | 用户是否还要手工抄录（是→仍是查询） |
| 需要结构化字段 | 3.2.2 抽取入库 | 字段级置信度、转人工、幂等键 | 整篇阈值会导致介入率失控 | 按字段的 precision / recall |
| 需要写对外文本 | 3.2.3 起草 + 人审 | 人审闸门、依据引用、模板对齐 | 直接发送即越界 | 发送动作是否有人审（可查） |
| 需要判断该不该批 | 3.2.4 三层审核 | 红线规则、模型阈值、归因字段 | 单靠模型无法审计、单靠规则覆盖不足 | 红线拦截数 + 采纳率 / 忽略率 |
| 多步流程（含等待） | 3.2.5 流程编排 | 状态机、超时、审批留痕（含输入快照） | 用散落 if-else 替代状态机 → 无法审计 | 每个状态是否有超时 |
| 要写多个系统 | 3.2.6 跨系统执行 | 凭证托管、幂等、补偿动作表 | 无补偿 → 部分成功退不回 | 每个可写步骤的"失败怎么退" |
| 既有系统无 API | 3.2.7 RPA + Agent 混合 | 理解 / 执行分离、变更建议 | 让模型直接点界面 → 脆弱且难查 | 两类错误能否分开观测 |
| 业务要"一句话办完" | 3.2.8 受限端到端 | 动作白名单、全链路留痕、前置审批 | 动作集交给模型 = 风险不可控 | 动作集是否来自注册表 |

### 3.4 组合模式：真实系统不会只用一种

1. **骨架 + 填充**：3.2.5（状态机骨架）+ 3.2.2 / 3.2.4（模型填充理解与判断）——**办公自动化的标准形态**。
2. **执行 + 兜底**：3.2.6（跨系统执行 + 补偿）+ 3.2.7（无 API 时走 RPA）——执行器怎么变，**幂等与补偿的纪律不变**。
3. **文档链路**：3.2.1（问答，给人用）+ 3.2.2（抽取，给系统用）——**同一份解析与索引支撑两种消费**，不要建两套。
4. **边界组合**：3.2.8（端到端）+ 3.2.4（审核三层）——端到端的每一步仍在白名单与规则之下。

**常见误配**：上了抽取但没上幂等（重复入账）；上了状态机但人工节点无超时（单据永久挂起）；上了端到端但动作集不是白名单（模型能"发明"动作）。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **让模型直接操作界面** | 界面小改后大面积失败 | 脆弱且难归因 | 把"理解"与"执行"混在一起做 |
| **整篇阈值而非字段级** | 介入率极高（或错单静默入库） | 阈值失去调节能力 | 只做了一个总分 |
| **无幂等键** | 同一单据重复入账 | 财务数据失真 | 只考虑"失败要重试" |
| **不可逆步骤放在链路中间** | 后续失败后已付款退不回 | 资损 | 没有补偿动作表 |
| **审批只记"已批准"** | 事后无法还原依据 | 责任无法认定 | 留痕按结果设计 |
| **人工节点无超时** | 单据永久挂起 | 流程停滞、时效不达标 | 把"等人"当无状态 |
| **草稿直接对外发送** | 出现在客户邮箱里 | 不可逆的沟通事故 | 人审闸门缺失 |
| **无端到端指标** | 只报字段准确率 | 不知道自动化是否真在替人干活 | 指标容易选（准确率好测） |
| **凭证长期驻留** | 凭证泄漏面随流程数扩大 | 安全风险 | 按服务发放而非按流程实例 |
| **白名单之外无提示** | 用户反复尝试不被支持的动作 | 体验差且无法改进 | 只做了拒绝对话，没做能力边界说明 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 手工 → 文档问答 | 查文档占掉大量时间 | 3.2.1 | 解析与索引（成本低，收益快） |
| 问答 → 抽取入库 | 用户还要手工抄录 | 3.2.2 | Schema、字段级阈值、幂等键 |
| 单步 → 多步流程 | 需要等待与二次确认【经验：出现"等审批 / 等材料"就会触发】 | 3.2.5 | 状态机建模与留痕改造 |
| 单系统 → 多系统 | 出现部分成功 | 3.2.6 | 补偿动作表 + 凭证托管 |
| 有 API → 无 API 系统 | 必须走界面 | 3.2.7 | 理解 / 执行分离、变更建议链路 |
| 受限 → 端到端 | 用户要求"一句话办完" | 3.2.8 | 动作白名单 + 全链路留痕（**不可跳过**） |

### 3.7 自检清单

- [ ] 链路里哪些步骤**不可逆**？它们是否都放在了校验与审批之后？
- [ ] 抽取是**字段级阈值**吗？每个字段的"可接受错误率"由业务写下来了吗？
- [ ] 低置信字段转人工的**介入率**是多少？人工核对的通过率是多少（过高说明阈值过严）？
- [ ] 抽取结果带**原文位置**吗？人工能一键核对吗？
- [ ] 写操作有**幂等键**吗？键取的是业务要素还是自增 ID？
- [ ] 每个可写步骤的**失败怎么退**（补偿动作）写下来了吗？
- [ ] 人工节点都有**超时**吗？超时后的动作是什么（默认不执行 / 转交）？
- [ ] 审批记录里有没有**输入快照**与依据？能否还原"当时基于什么批的"？
- [ ] 跨系统凭证是**按流程实例**发放的吗？权限是否最小？
- [ ] 起草类输出**是否必须人审**才对外发送（可查）？
- [ ] "理解错"与"执行错"能分开观测吗（RPA 混合场景）？
- [ ] 端到端两个指标（介入率、返工率）都有吗？最近一次优化的依据是哪个？
- [ ] 端到端 Agent 的动作集来自**注册表白名单**吗？
- [ ] 全链路能回放吗（输入、判断、动作三段留痕）？

### 3.8 小结

> 本节小结：办公自动化的形态由五条约束按序决定——**动作可逆性 → 数据敏感级 → 错误代价分布 → 流程确定性 → 人的位置**；八种模式里，**状态机骨架（3.2.5）与跨系统执行纪律（3.2.6：凭证 + 幂等 + 补偿）是这条链路的承重结构**，**字段级置信度与转人工（3.2.2 / 3.2.4）是把模型误差约束在可承受范围的唯一手段**，而**起草人审（3.2.3）与动作白名单（3.2.8）是不可越过的两条边界**。判断这一支有没有建成，只看两条：**单据能不能在无人盯着时走完**；**走错时能不能被发现并退回**。

> 💡 **思考锚点**：在你的流程里找出**第一个不可逆步骤**（已发款、已对外发送、已入账），然后回答：它前面有哪些校验与审批？如果答案是"没有"或"靠人记得"，那你现在最该做的不是优化抽取准确率，而是**把它前面的闸门补上**——你打算先补哪一道？
