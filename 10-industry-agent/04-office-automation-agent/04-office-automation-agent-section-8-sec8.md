### 8.2 抽取质量：字段级口径与阈值标定

#### §OA.1 你要把发票、合同、报销单里的字段抽成结构化数据。请说明：（1）为什么"整篇准确率"不能作为质量口径；（2）阈值应该怎么定，依据是什么；（3）低置信度转人工之后，怎么判断这个阈值定得对不对？

**1. 考察点**

- 能否指出整篇准确率会被**大字段稀释**，从而掩盖高代价字段的错误。
- 能否给出**可执行的阈值标定动作**（曲线而非拍脑袋）。
- 能否用**人工核对通过率**反向判断阈值是否过严。

**2. 参考答案框架**

**第一层：为什么必须字段级（回答第 1 问）**。一张单据有十几个字段，其中金额错了、其余都对，整篇准确率看起来仍有九成以上，**而错误代价集中在那一项**。因此正确口径是**按字段算 precision / recall**（recall 要包含漏抽），并按字段的重要性分级（金额 / 日期 / 主体为高代价字段）。

**第二层：阈值怎么定（回答第 2 问）**。① 取历史文档与人工真值；② 按置信度分桶，统计每桶的抽错率；③ 画「阈值 → 介入率 λ(θ)」与「阈值 → 错误漏出率 ε(θ)」两条曲线；④ 取业务可接受错误率 `ε*` 对应的最小阈值作为初始值。**关键**：`ε*` 必须由业务写下（财务入账与内部纪要的容忍度差一个量级【经验】），否则阈值没有依据；高代价字段用更严阈值。

**第三层：阈值是否合适（回答第 3 问）**。看**人工核对通过率**：若被转人工的字段里有很高比例其实是对的，说明阈值过严（白花人力）；若人工核对时频繁发现错误，说明阈值过松。**两个方向都要看**，然后把结论写回阈值表并记录依据（可追溯）。另一个辅助动作：**定期回放**（把历史文档重新抽一遍，看曲线是否漂移——版式变化会让曲线漂）。

**3. 常见陷阱**

- 用整篇准确率（掩盖高代价字段的错误）。
- 阈值拍脑袋定（介入率要么爆表、要么错单静默入库）。
- 低质量扫描件"尽力抽"（应当判定"不可解析"并直接转人工）。
- 阈值永不重标（版式变化后曲线漂移，而阈值还停在去年）。

**4. 追问预测**

- 「字段级置信度怎么来？」——由抽取链路给出（模型自评或多次一致性）；**无论来源如何，都必须可校准**（用分桶准确率检验它是否单调）。
- 「为什么不用一个大模型直接输出 "is_correct"？」——自我判断不可靠，且无法定位；用**分桶统计**校准置信度才是可验证的做法。
- 「摘要 / 备注类字段也要阈值吗？」——要，但可以放宽（它们错误代价低）；**分级阈值是介入率可控的关键**。

**5. 参考资料**

- 字段级准确率与"按代价分级"的思路可对照 [Ch11 §01 数据质量](../../11-cross-cutting/01-data-quality/01-data-quality.md) 的断言与阈值口径。
- 抽取结果带原文位置与回指的做法见本主题 [§4.2（2）](04-office-automation-agent-section-4-sec4.md)。
- 抽取准确率的公开数字几乎都来自建设方，且与单据形态强相关——**必须自测**【经验】。

### 8.3 幂等、补偿与"部分成功"

#### §OA.2 一张单据要写三个系统（ERP 入账、档案归档、供应商通知）。请说明：（1）"部分成功"如何处理，为什么"重跑一次"是错的；（2）幂等键怎么设计；（3）什么情况下不该自动执行，而必须前置审批？

**1. 考察点**

- 能否指出"重跑 ≠ 补偿"，并解释重复入账的机制。
- 能否给出**业务要素构成的幂等键**（而不是自增 ID）。
- 能否列出**不可逆动作清单**并说明前置审批的理由。

**2. 参考答案框架**

**第一层：部分成功的处理（回答第 1 问）**。多系统写入必然出现"第一步成功、第二步失败"。正确做法有三步：**失败分类**（可重试 / 需补偿 / 需人工）→ **对已成功的步骤执行补偿**（或标记为待补偿）→ **重试时依赖幂等键去重**。**"重跑一次"是错的**：如果第一步已经入账成功，重跑会让它再入一次——**财务数据直接失真**，且这种错误在月末对账时才暴露。

**第二层：幂等键（回答第 2 问）**。用**业务要素**构成：`hash(单据类型, 单据号, 日期, 金额, 供应商)`；**不要用自增 ID 或时间戳**（重跑时它们会变）。实现上靠**唯一约束**保证并发安全（不是先查后写）。**判据**：用同一键重跑一次流程，**不产生第二笔入账**（这是一次可以直接演练的验证）。

**第三层：不可逆动作（回答第 3 问）**。三条判据：① **有没有语义正确的逆向动作**（入账有"红字冲销"、通知有"更正说明"、归档有"撤回归档"）；② **逆向窗口有多长**（财务系统的冲销窗口可能只有几天【经验：随系统规则浮动】）；③ **逆向是否产生新的对外影响**（已发给客户的通知，撤回本身也是一次沟通）。**没有逆向动作或窗口已过**的动作必须**前置校验与审批**，且**不得置于链路中间**（与 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md) 的不可逆动作前置条件同源）。

**3. 常见陷阱**

- 把重试当补偿（重复入账）。
- 幂等键用自增 ID（重跑即重复）。
- 补偿动作不留痕（事后无法证明已退回）。
- 不可逆动作放在链路中间（前面成功、后面失败，退不回）。
- 补偿窗口不写清（窗口外还尝试自动冲销，产生更复杂的状态）。

**4. 追问预测**

- 「补偿动作要不要审批？」——要看影响面：冲销一笔小额入账通常可自动；撤回对外通知应人审（因为它本身是对外动作）。
- 「跨系统的分布式事务能不能用？」——两阶段提交在跨组织系统间通常不可用（参与方不配合），所以**补偿是现实解**；这也是"补偿本身要有状态"的原因。
- 「怎么证明补偿生效了？」——对账（入账与冲销成对）与 `inverse_of` 留痕；**两者都要有**。

**5. 参考资料**

- 不可逆动作与可回滚性的讨论见 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md) 与 [Ch12 §08 数据一致性](../../12-architecture/08-data-consistency/08-data-consistency.md)（Saga / TCC 一类补偿式一致性）。
- 幂等键与出口四件事的顺序见 [Ch5 §02 §4.2（2）](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-4-sec4.md)。

### 8.4 流程状态机、超时与审批不可否认

#### §OA.3 报销流程有"录入 → 核对 → 审批 → 入账 → 归档"五个环节，其中两个需要人操作。请说明：（1）状态机该怎么设计，哪些必须有超时；（2）审批留痕要记到什么程度才算"不可否认"；（3）流程卡住了怎么发现？

**1. 考察点**

- 能否指出**人工节点也必须带超时**（这是最常见的漏项）。
- 能否把"不可否认"落到**输入快照 + 理由**这样的字段级要求。
- 能否用**各状态耗时**回答"流程卡在哪"。

**2. 参考答案框架**

**第一层：状态机与超时（回答第 1 问）**。状态显式化（received / extracted / need_manual_fix / pending_approval / posting / done | rejected | compensated），**每个状态都带超时与超时动作**：人工节点超时 → 升级或转交（不是静默挂起）；写入节点超时 → 熔断并根据失败分类走补偿或转人工。**判据**：把所有状态的超时值列成一张表——**空着的状态就是未来的积压点**。

**第二层：不可否认（回答第 2 问）**。至少记录四段：**输入快照**（原文哈希 + 抽取结果）、**校验结果**（规则命中与模型分数）、**决定**（谁、何时、通过/驳回、**理由**）、**后续动作**（入账 / 冲销的引用）。**只有"已批准"三个字不算留痕**：它无法回答"当时基于什么批准"，也就无法在争议中还原事实。理由字段建议**必填**（否则闸门会退化为点"同意"）。

**第三层：卡点发现（回答第 3 问）**。三个可执行动作：① **各状态耗时 P95 看板**（通常人工节点的等待时间远大于处理时间）；② **超期单据清单**（按状态分组，找出"挂最久"的）；③ **积压趋势**（同状态的单据数在增长就是信号）。**判据**：任一时刻能回答"现在有多少单据卡在哪一步、卡了多久"。

**3. 常见陷阱**

- 人工节点无超时（单据永久挂起，且没人发现）。
- 审批只记结果不记依据（责任无法认定）。
- 把"等待"当作无状态（引擎里没有等待节点，超时无处配置）。
- 卡点靠人反馈（而不是指标）。

**4. 追问预测**

- 「超时后默认通过还是默认拒绝？」——**默认拒绝或转交**：不可逆动作的超时默认"不做"（"默认通过"等于把风险交给时间）。
- 「审批人休假怎么办？」——超时升级 / 代理机制要写进状态机（这也是"人的位置"这条约束的落地）。
- 「状态机能改吗？」——能，但**流程定义要版本化**（正在跑的实例钉住其启动版本），否则同一单据前后走两套逻辑，复盘无法解释。

**5. 参考资料**

- 持久化执行与状态机建模的形态见主流工作流引擎文档（按当前版本核验）【公开：以官方文档当前版本为准】。
- 审批与留痕的合规口径见 [Ch11 §07 审计与合规](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)；流程版本与回滚见 [Ch12 §09](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)。

### 8.5 RPA 与 Agent 的分工（理解 / 执行分离）

#### §OA.4 有五个遗留系统没有 API，只能走界面。请说明：（1）为什么"让大模型直接操作界面"是错的；（2）理解层与执行层如何分工，各自负责什么；（3）界面改版时怎么办？

**1. 考察点**

- 能否指出**概率性操作确定性界面**会让脆弱性与不可归因性叠加。
- 能否给出清晰的分工（读与判断 vs 点击与写入）。
- 能否把"界面改版"从事故变成**有信号的维护**。

**2. 参考答案框架**

**第一层：为什么错（回答第 1 问）**。三件事叠在一起：① **脆弱性**（界面一改就断）；② **不可归因**（失败时无法区分"理解错"与"执行错"）；③ **不可见证**（模型的点击无法用脚本复现，审计与回归都做不了）。**确定性的事就该用确定性的方式做**——这是分工的全部理由。

**第二层：分工（回答第 2 问）**。**理解层**（模型）：读界面文本 / 截图的语义、判断该点哪里、在异常时给出解释与建议；**执行层**（脚本 / RPA）：按确定的定位方式点击与写入、处理弹窗与等待、记录每一步的操作日志。**判据**：两类错误**分开计数**（理解错的发生率、执行错的发生率）——能分开，才能分别优化。

**第三层：界面改版（回答第 3 问）**。三个动作：① **定位方式稳健化**（优先用可访问性标签 / 稳定属性，而非坐标）；② **变更探测**（每天对关键页面做一次"元素存在性检查"，缺失即告警——把改版从"运行时故障"变成"提前告警"）；③ **修法由人确认**（模型可给出"哪个元素变了、建议怎么改"，但**改脚本的决定权在人**）。

**3. 常见陷阱**

- 让模型直接操作（脆弱 + 不可归因）。
- 用坐标定位（分辨率与布局一变即失效）。
- 无变更探测（改版后才发现，且是批量失败）。
- 两类错误混在一个成功率里（无法定位优化方向）。

**4. 追问预测**

- 「为什么不让模型生成脚本、然后跑脚本？」——这正是"理解 / 执行分离"的一种实现：模型产出候选定位与步骤，脚本执行。**仍然要人审脚本**（因为脚本会长期运行在业务系统上）。
- 「截图 + 视觉模型定位行不行？」——可作为**辅助**（判断"页面是否到了预期状态"），但**不应作为唯一定位手段**（成本高、稳定性受渲染影响）。
- 「RPA 的重试算不算幂等？」——不算：RPA 的重试会再次点击与提交；**幂等要靠业务键**（例如提交前先查单据是否已存在）。

**5. 参考资料**

- 工具出口与动作白名单的治理见 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md)（出口收口与四件事）。
- 轮询与变更探测的可观测思路见 [Ch11 §04 可观测](../../11-cross-cutting/04-observability/04-observability.md)。

### 8.6 凭证粒度、权限域与出网合规

#### §OA.5 办公自动化要写 ERP、读人事档案、发对外通知。请说明：（1）凭证应该怎么设计，为什么长期服务账号是错的；（2）权限域应该在链路的哪一步生效；（3）文档里有人事与财务信息，如何保证不出域？

**1. 考察点**

- 能否把凭证粒度与**爆炸半径**联系起来。
- 能否指出权限判定要在**动作之前**（与代码助手"检索之前"同构）。
- 能否给出**可举证**的不出域证据组。

**2. 参考答案框架**

**第一层：凭证设计（回答第 1 问）**。三件事：① **按流程实例**发放短期凭证（而不是长期服务账号）——爆炸半径从"所有单据"缩到"一张单据 + 一个时间窗"；② **最小 scope**（写 ERP 的凭证不应能读人事）；③ **可即时吊销**（发现异常时能立刻停）。**判据**：一次凭证泄漏的影响面能否量化到"实例 + 窗口"。

**第二层：权限域生效位置（回答第 2 问）**。**在动作之前**：请求进入时先确定可见域（这个人 / 这个流程能碰哪些系统与数据），**再决定能否读取与执行**。若"先执行再检查"，会产生两个后果：① 已经发生的写操作无法撤销（不可逆）；② 读操作已把不该看的内容读入内存与日志（泄漏）。**判据**：用一次越权请求做演练（超 scope 调用被拒且留痕）。

**第三层：不出域（回答第 3 问）**。三件事 + 三份证据：**自托管模型端点**（不许外部端点处理人事 / 财务文档）、**本地解析与索引**（文档不出域）、**出网白名单**（默认拒绝）；证据是**连接审计**（一段时间的出网记录）、**一次拒绝演练**、**文档分级与路由配置**（按敏感级决定用哪个端点）。**判据**：能拿出"受敏感级约束的文档 100% 命中本地端点"的报表。

**3. 常见陷阱**

- 长期服务账号（一次泄漏影响全部数据）。
- 权限检查放在动作之后（越权已发生）。
- 只私有化模型，解析 / 索引 / 遥测出域（"假私有化"）。
- 文档不分级、一条链路处理所有文档（无法证明"敏感文档没出域"）。

**4. 追问预测**

- 「同一份文档里既有公开信息又有敏感信息怎么办？」——按**最严级别**处理（整篇走本地端点），或先做**字段级脱敏再外发**（脱敏本身要可核验：给出脱敏规则与抽检结果）。
- 「第三方 OCR 服务算不算出域？」——算：文档内容离开你的边界就是出域；要么自托管 OCR，要么把该路径限定在非敏感文档上。
- 「怎么向审计方证明？」——连接审计 + 拒绝演练 + 分级报表 + 留痕可导出；**四件合起来才是证据**，架构图不是。

**5. 参考资料**

- 出网策略与凭证托管的形态见 [Ch6 §03 §4.2（4）](../../06-multi-model/03-model-gateway/03-model-gateway-section-4-sec4.md)；分级保密与权限域见 [Ch8 治理](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md) 与 [Ch11 §02 数据安全](../../11-cross-cutting/02-data-security/02-data-security.md)。
- 审计与举证口径见 [Ch11 §07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)。

### 8.7 端到端指标与端到端 Agent 的边界

#### §OA.6 领导问"办公自动化做到什么程度了"。请说明：（1）你会用哪几个数回答，为什么不能只报"处理量"；（2）什么条件下才允许"一句话办完"的端到端形态；（3）如果只能上一项指标，你选哪个？

**1. 考察点**

- 能否给出**介入率与返工率**这两个互补指标，并解释为什么单看一个会误导。
- 能否明确端到端形态的**前置条件**（动作白名单、留痕、前置审批、可回放）。
- 能否选出**抗操纵**的单一指标。

**2. 参考答案框架**

**第一层：回答哪几个数（回答第 1 问）**。三个：**人工介入率**（需要人处理的单据占比）、**返工率**（自动处理后被人工纠正的比例）、**流程成功率**（含各状态耗时）。**为什么不能只报处理量**：处理量只说明"系统在跑"，既不说明是否替人省了力，也不说明质量；**介入率降而返工率升**是最危险的信号——风险被从"人工处理"搬到了"事后纠正"，表面上更"自动"了。

**第二层：端到端的前置条件（回答第 2 问）**。四条同时满足：① **动作白名单**（可执行动作来自注册表，模型只能选择；不是靠提示词约束）；② **全链路留痕**（输入、判断、动作三段，可回放）；③ **不可逆动作前置审批**（写外部 / 入账类必须人审，且有超时）；④ **幂等与补偿齐备**（重跑不重复、失败可退回）。**判据**：缺任何一条，端到端形态都只能作为**演示**，不能上生产。

**第三层：单一指标（回答第 3 问）**。选**返工率**（并把介入率与流程成功率作为护栏一起看）。理由：它抗操纵（"看起来自动化了但事后都在改"会立刻反映出来）、直接对应质量、且能跨流程复用。**注意**：它是结果指标，需要工单与纠正记录作为数据来源——**如果现在没有"谁纠正了哪张单"的记录，第一步是先把这个记录做出来**。

**3. 常见陷阱**

- 只报处理量与"节省的人时"（未扣返工）。
- 介入率下降就当成功（不看返工率）。
- 端到端形态在缺白名单 / 留痕 / 幂等 / 补偿时上线（一次事故全面叫停）。
- 纠正记录不落库（返工率永远测不出来）。

**4. 追问预测**

- 「介入率应该降到多少？」——没有通用值：它取决于单据形态与可接受错误率【经验】；**关键是把"当前值与趋势"管起来**，而不是追一个绝对数。
- 「返工率的目标定多少？」——同样取决于业务；但可以定**"返工率不得上升"这条硬约束**（在扩大自动化面时），这是最容易执行的一条。
- 「影子运行阶段的价值是什么？」——它产出"自动与人工不一致"的清单——**这份清单是后续调阈值与规则最具体的靶子**（也是本主题最重要的迁移产物）。

**5. 参考资料**

- 三层评估（离线 / 流程 / 端到端）与样本切分见 [Ch2 §07 效果评估](../../02-data-science/07-eval/07-eval.md)；灰度的护栏与止损见 [Ch12 §09](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)。
- 留痕与回放的口径见本主题 [§4.2（6）](04-office-automation-agent-section-4-sec4.md) 与 [Ch11 §07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)。

### 8.8 本章小结

本节收录 6 道题，覆盖**办公自动化智能体**的六个核心考点：**抽取口径 → 幂等与补偿 → 状态机与留痕 → RPA 分工 → 凭证与出域 → 端到端指标与边界**。六道题构成一条完整的建设链路：

- **§OA.1 抽取**：字段级 precision / recall；阈值靠"介入率—漏出率"曲线标定，`ε*` 由业务写下；用人工核对通过率反向校准。
- **§OA.2 幂等与补偿**：失败分类 + 幂等键（业务要素）+ 显式补偿（不是重跑）；不可逆动作前置且不入链路中间。
- **§OA.3 状态机**：每个状态（含人工节点）都要有超时与超时动作；留痕含输入快照与理由；卡点靠各状态耗时发现。
- **§OA.4 RPA 分工**：理解与执行分离；两类错误分开计数；界面改版靠变更探测提前告警。
- **§OA.5 凭证与出域**：按实例短期最小凭证；权限在动作之前生效；不出域靠自托管 + 白名单 + 连接审计 + 演练。
- **§OA.6 指标与边界**：介入率 + 返工率 + 成功率一起看；端到端需白名单 + 留痕 + 前置审批 + 幂等补偿；单一指标选返工率。

**答题心法**：先说清约束（动作可逆性、数据敏感级、留痕要求、骨架归属、执行入口、承接能力），再说清选项（六条路的三族），最后说清取舍与代价。办公自动化主题下，面试官真正想听的是 **"你的闸门与退路在哪里"**——把答案落到"某个判据 + 一个可当场执行的动作"（用同一幂等键重跑、数一次介入率、演练一次越权），远比讲模型能力有说服力。
