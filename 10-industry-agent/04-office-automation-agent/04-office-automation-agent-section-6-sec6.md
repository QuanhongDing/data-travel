## 6. 落地实践

> **本节的材料纪律（先说清楚）**：办公自动化横跨"协作平台的产品能力"与"企业内部流程改造"两块；前者有公开产品文档，后者的细节（介入率、错单率、补偿动作）几乎不公开。因此本节 4 例的构成是：
>
> - **§6.1–§6.3** 是**产品文档层面的机制复述**（权限怎么继承、流程骨架由谁承担、结构化对象怎么被编排），**不是对任何一家公司内部实现的转述**；方括号内是**来源类型 + 年份**，属**建设方自述**，不构成本书 §5 判据里要求的「第三方（非厂商）公开生产案例」，读者需按其官方材料自行核验。
> - **§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证。
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 微软"**把办公助手挂进既有的权限与合规边界，而不是另建一套 2+ 年**"（2022-2024）

**背景（Why）**

企业办公场景里，"文档"不是孤立文件，而是**挂在一整套既有权限体系下的对象**：

- **权限已经在别处定义过**——SharePoint / 网盘 / 协作平台里已经有"谁能看哪份文档"，另建一套必然不一致；
- **不一致的后果不是"多花钱"，而是"泄漏"**——助手凭它自己的索引答出一条用户无权看的文档，这是一次真实的信息泄露；
- **合规边界也已经在别处定义**——保留策略、审计要求、数据分级，都是既有治理体系的一部分。
- **约束在哪**：这不是"要不要做智能助手"的选择题，而是**权限的权威源只能有一个**——一旦有两个，"谁说了算"就没有答案，而在办公场景里这个答案必须由既有治理体系给出（§3.1 约束 2 的落地形态）。
- **代价在哪**：继承既有权限意味着**助手不能自己决定"谁能用"**——它的可见域、它的保留策略、它的审计链路都被既有体系钉住，产品侧想做的"更聪明的可见性"没有空间；反过来说，这也意味着**助手的能力上限由既有权限体系的精细度决定**。

**触发点（What）**

微软把办公助手接进其协作与文档产品时，走的是**继承既有权限模型**的路线（[微软公开材料 2022-2024]，核验入口是其官方文档，**按当前版本核**）：助手能看到的范围受**既有权限**约束，而不是按"谁能用这个助手"来决定。它对办公自动化的启示是一条**归属判断**：

- **权限的权威源必须唯一**——助手不能成为第二个权限源；
- **因此"助手可见域"不是它的功能，而是它的输入**（§3.2.8 的"先裁剪再检索"在办公场景的形态）；
- **保留与审计同理**——留痕要接进既有合规体系，而不是另建一份。
- **这条判断的代价**：助手的可用性上限由既有权限体系的精细度决定——**既有体系分不清的粒度，助手也分不清**；如果企业的权限模型只到"站点级"，那么助手也只能按站点级裁剪，而它不能靠自己的索引把粒度做细（那等于又建了第二个权限源）。

**详细做法（How）**

**① 权限继承而不是权限重建**

- **关键设计**：助手在检索与生成时，**按调用者的既有身份裁剪可见域**，并把这个裁剪放在召回之前。
- **关键性质**：**权限的权威源只有一个**——这一条同时消掉两类问题：与既有体系不一致（用户看到不该看的）、以及审计时无法举证（"助手的权限表"不是权威源，审计方不认）。
- **关键示意**：

  ```text
  两个权限源会带来的三种不一致（都指向泄漏或误拒）
    ── 若助手自建权限表 ────────────────────────────
       ① 用户被授权看了 A 文档，助手表里没有 → 误拒（体验问题）
       ② 用户在助手表里有 A，但已被撤权 → 泄漏（安全问题）
       ③ 组织架构调整后，两表更新节奏不同 → 长期静默不一致
    ── 若助手继承既有身份 ──────────────────────────
       可见域 = 既有系统对该身份的判定结果（单一权威源）
       → 撤权即时生效；审计链路与既有体系一致
    ────────────────────────────────────────────────
   判据：撤掉一个用户的文档权限后，他问助手能不能问出那份文档？
        能问出 → 你的助手有第二个权限源
  ```

- **关键能力**：把"可见域"当作**输入**而不是**功能**——裁剪发生在**召回之前**，而不是在生成之后过滤。这个次序决定了两件事：无权内容不会进上下文与日志（否则它已经泄漏到"看起来安全"的地方），以及**撤权能即时生效**（因为每次都现算，没有缓存下来的可见域）。
- **判据**：撤掉一个用户的文档权限后，他问助手能不能问出那份文档；以及**用超 scope 的凭证调用一次**，看是否被拒并留痕（同 §4.7 的越权演练）。

**② 输出侧仍要留痕与可核对**

- **关键设计**：回答带**引用回指**（哪份文档、哪一段、什么时候读到的），并记录"谁问的、问的什么、用了哪些材料"。
- **为什么在"已经继承权限"之后还要留痕**：权限解决"能不能看"，留痕解决"看了什么、据此说了什么"——**在办公场景里，一段摘要可能被直接抄进对外文件**，因此它的使用必须可回溯（与 §3.2.1 的"责任面为零不等于错误代价为零"同理）。
- **关键能力**：引用要细到**段级**（哪份文档、哪一段、什么时候读到的），并把"用了哪些材料"单独记成一条可核对的清单——**引用让"不可否认"从"用过这份文档"落到"用过这一段"**。
- **判据**：随便抽一条回答，问"这段结论出自哪一份文档的哪一段、问的人当时有没有权看它"——三个都能答，才叫留痕到位。
- **关键示意**（留痕的最小字段形态，与 §4.2（6）的审批工单同一路数）：

  ```json
  {
    "ask":       {"by": "u-…", "at": "…", "q": "ACME 合同的付款条款是什么"},
    "scope":     {"src": "existing_identity", "docs_visible": "…"},
    "materials": [{"doc_id": "contract/…/acme-…pdf", "rev": "sha256:…", "span": "第 4 页 第 2 节"}],
    "answer_id": "ans-…",
    "cites":     "…"
  }
  ```

  **判据**：字段名与取值都是示意（`…` 处按你的实际取值代入）——`scope.src` 必须指向**既有身份源**，不能是助手自己的表；`materials` 里的每一份都要能回答"该用户当时有权看吗"（`rev` 是原文版本，用来回答"当时读到的是哪一版"）。

**③ 保留与审计同样接进既有合规体系，而不是另建一份**

- **关键设计**：助手产生的记录（问答、引用、材料清单）沿用既有治理体系的**对象、分级与保留周期**，而不是在助手侧另定一套保留策略。
- **为什么**：这与 ① 是同一个机制——**权威源只能有一个**。另建一份保留策略会带来两个后果：两套周期在组织变动后静默分叉；以及审计时"助手侧的记录"不被认作权威材料（审计方认的是既有治理体系的口径），于是出事之后**记录在、但举不了证**。
- **判据**：走一次既有的审计导出流程，看**助手产生的记录能不能一并取出来**——需要单独找助手团队导数据，就说明它还在既有体系之外。

**具体数字（档位标注）**

- 抽检负荷：**每周抽 20 条回答**，逐条核对（引用能否点开、指向的片段是否支持结论、该用户是否有权看）【经验：单条约数分钟】。按单条数分钟算，一周 20 条**是一小时上下的量**——**因此抽检可以是一个常设动作而不是专项**；再往上加量，抽检本身会先成为被砍掉的那一项。
- **自测动作（今天就能做的一条）**：撤掉某个测试账号对某份文档的权限，然后**用该账号问助手那份文档里的内容**——问得出来，说明存在第二个权限源。**这个动作花十分钟，但它是本主题唯一能证明"权限真的继承了"的验证。** 它之所以是"唯一"，是因为**它的价值在于可复现**：任何一次组织架构调整之后都可以原样重跑一遍，因而不必等下一次泄漏来提醒你。
- 权限差异的规模：在企业里"助手表与既有权限表的不一致条数"会随组织变动累积，**这个数没有通用量级，但它应当被当作一个可监控的不一致指标**（而不是靠一次性的核对）【经验】——**把它做成指标，是在这件事唯一可控的地方（发现速度）上投入**：两份权限表之间没有同步机制，差异只会被外部事件制造、不会被内部流程消除（失败教训一栏的机制）。

**失败教训**

**第一版给助手建了自己的文档索引权限表**——理由是"索引侧做过滤更方便"。上线三个月后一次组织架构调整，有人的权限已被撤销但助手表仍是旧的，**一段本不该被看到的合同条款出现在回答里**。教训：**权限的权威源必须唯一**；助手可以有自己的索引，但不能有自己的权限。**机制层的解释**：两份权限表之间没有任何同步机制，而它们的差异只会被外部事件（组织调整、项目换人）制造、不会被任何内部流程消除——**因此这不是一次可以靠"更仔细核对"修好的漏，而是一个必然随时间变大的差集**；同理，"权限判定放在检索之后"也不是体验问题：那时无权内容**已经进了上下文与日志**，泄漏面从"用户看到"扩成"系统里存着"。

### 6.2 钉钉"**把审批流与组织身份接进 Agent：流程骨架仍由状态机承担 3+ 年**"（2021-2024）

**背景（Why）**

办公流程的"智能"诉求容易走偏到"让模型推进流程"：

- **流程的价值在可预期**——报销、请假、采购的路径是**约定**，不是待探索的问题；
- **模型擅长的恰恰相反**——它擅长处理分支与例外，而**把确定性流程交给概率系统，只会引入不可预期的失败**；
- **但流程里确实有"看不懂的材料"**——发票字段、合同条款、附件一致性，这些是模型该做的部分。
- **约束在哪**：流程的"约定"属性意味着**它的正确性不取决于执行者的智能程度**——报销该走几级审批、超时该转给谁，是写下来的规则；把这类规则交给概率系统，等于把一个确定性的东西变成"通常对"（§3.1 约束 4）。
- **代价在哪**：用既有流程引擎做骨架，意味着**流程的形态受引擎能力的约束**（能配出哪些状态、超时能否按节点设、留痕字段能不能加）。这不是技术选型问题，而是"愿不愿意为一条流程去改引擎"的取舍——**而多数组织在这件事上的答案是不改**。

**触发点（What）**

钉钉一类协作平台把**审批流与组织身份**做成了 Agent 可以调用的既有能力（[钉钉公开材料 2021-2024]，核验入口是其开放平台文档，**按当前版本核**）：流程的推进、审批节点的指派、超时与转交由平台侧的流程引擎承担，Agent 负责"读材料、填字段、给判断"。它给出的分工判断是：

- **骨架（状态机）由流程引擎承担**——它已经解决了超时、转交、留痕；
- **Agent 负责骨架里"看不懂"的那一格**——它不该重写骨架。
- **这条分工的代价**：Agent 只在一格上工作，于是**它的能力上限由"那一格有多重要"决定**——如果骨架里的判断格很小（例如只是填几个字段），收益也就到此为止；要扩大收益必须去动骨架，而骨架是约定，不是可以自由试的地方。

**详细做法（How）**

**① 状态机不在 Agent 里重建**

- **关键设计**：Agent 的输出只是**某个状态节点上的判断与字段**，不承担"下一步是什么"。
- **为什么这样切**：**状态机的价值是"卡住时能被看见"**（§3.2.5）；如果 Agent 自己在提示词里实现跳转逻辑，**"有多少单据卡在哪一步"就统计不出来**——因为每一步都成了模型的一次生成，没有显式状态。**这条切分把"流程可观测"这件事保住了。**

- **判据**：任何时刻都能回答"现在有多少单据卡在哪一步、卡了多久"（判据见 §3.2.5 与 §4.2（4））。
- **关键示意**（两种做法的差别只在"状态住在哪"）：

  ```text
  两种做法的差别只在"状态住在哪"
    ── 跳转写在提示词里 ─────────────────────────────
      单据 → [模型生成：下一步该做什么] → 下一步 → …
      统计口径：无（每一步都是一次生成，没有显式节点）
      卡住的单据：显示为"处理中"，无超时、无告警、无口径
    ── 跳转由流程引擎承担 ───────────────────────────
      单据 → received → extracted → pending_approval → posting → done
                    ↑超时    ↑超时（人工节点）    ↑超时（写系统步骤）
      统计口径：每个状态的滞留数与耗时（可查、可告警）
    ────────────────────────────────────────────────
   各状态的超时取值按 §4.2（4）的状态机配置登记，本节不另给数值
  ```

**② 全状态超时（含人工节点）**

- **关键设计**：每个状态都有超时；**人工节点超时后的默认动作必须写死**（默认不执行或转交），而不是留给实现。
- **机制**：等待人工的节点若没有超时，会**永久占着一个单据**——而这类单据在统计上不显示为"失败"，只显示为"in progress"，**因此它会安静地积累**。
- **判据**：把所有状态（含人工节点）连超时值列成一张表，**空着的那几行就是未来的积压点**；再确认超时后的动作是**写死的**（默认不执行或转交），而不是留给实现临场决定。

**③ 审批工单含输入快照与理由**

- **关键设计**：审批节点记录的不是"已批准"，而是"**当时那份输入 + 模型判断 + 依据 + 批准动作 + 人 + 时间**"。
- **为什么必需**：审批的对象是**当时那份材料**（§3.2.5）；缺快照时，事后无法还原"当时基于什么批的"，责任认定（约束 5）就落空。
- **判据**：随便挑一张已批单据，问"当时基于什么批的"——**能还原出当时那份材料的快照与理由，才算留痕**；只答得出"已批准"三个字，说明留痕是按结果设计的。

**④ 升级与代理机制要写进状态机**

- **关键设计**：审批人休假、离职、转岗时的处置**写在状态定义里**（超时后升级到上级、或转交代理人），而不是靠人在群里喊一句。
- **为什么**：这是"人的位置"这条约束（§3.1 约束 5）的落地形态——**只要"谁批"这件事还依赖某个具体的人在线，闸门就有一个可预期的失效模式**；把它写进状态机之后，"等待"才真正变成一个有时间上限的状态，而不是一个可以无限延长的状态。
- **判据**：把审批人角色对应的**具名人员与代理人**列出来，逐个问"他休假两周时这张单会怎样"——答不出一个由系统执行的动作，说明这一格还靠人记着。

**具体数字（档位标注）**

- 时效分解（可自测）：把 `采集/上传 → 解析 → 抽取 → 审批 → 执行` 各段的 P95 分开测；**只报端到端时长会导致"为什么慢了"无法归因**【经验】。**分开测对本主题有用，是因为这五段的"慢"形状不同**：人工节点没有超时时，审批段的尾部会被无上限拉长（§6.2 详细做法②）；而抽取段变慢只是把整体匀速抬高。**合在一起报时这两种快慢看起来一样，"审批慢"这个结论就可能指错了段。**
- 人工节点的占用：设到达率 λ、人均处理率 μ，则所需人力 `n > λ/μ`【推算：与 [Ch5 §02 平台架构](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture.md) 的积压条件同源】——**这个式子用来判断"闸门是不是过宽"，而不是用来申请加人**：它把"人能承受多少量"写成两个可观测的数（到达率与人均处理率），因此加人不改变这个比值的形状，只有收窄转人工范围才改变它。
- **自测动作**：查一次"当前有多少单据卡在哪一步、平均卡了多久"。**答不出这个数，就说明状态机没有真的建立**（它是流程可观测的最小证据）。**这个数之所以是"最小证据"**：引擎日志能告诉你"有哪些状态"，只有这个数能告诉你"状态里有没有东西"。

**失败教训**

**第一版把流程跳转写进了 Agent 的提示词**——理由是"这样更灵活"。结果是：一个单据在"等补充材料"这个状态停了很久没人发现，因为在系统看来它只是"正在处理中"；**而"正在处理中"没有超时、没有告警、也没有统计口径**。教训：**状态机不是要重写的东西，而是要去用的东西**；把显式状态换成模型生成，等于把可观测性换成灵活性——而在流程场景里，可观测性的价值高于灵活性。**机制层的解释**：可观测性依赖的是**枚举**（状态是一个有限、可列举的集合），而模型生成的"下一步"是一个开放集合——**它没有枚举，因此无法统计**；这就是"更灵活"与"看不见"在这件事上是同一枚硬币两面的原因。同理，"人工节点无超时"也不是配置遗漏：它把"等人"当成了无状态，而**在统计上"等待"不显示为失败，于是它只会积累、不会报警**。

### 6.3 飞书"**把多维表格与审批做成可编排的结构化对象：抽取的产物直接进流程 3+ 年**"（2021-2024）

**背景（Why）**

办公自动化里最容易被低估的是**"中间产物的形状"**：

- **文档是非结构化的，而流程需要结构化**——在两者之间必须有一次转换；
- **如果这次转换的产物只是"一段文字"**，那么下游的流程节点（金额校验、供应商比对、预算扣减）都无法直接消费它；
- **于是会出现一层"人肉搬运"**——把模型输出的文字手工填进表格，自动化收益被这一层吃掉大半。
- **约束在哪**：这一次转换的产物形状**决定了下游是谁**（人还是流程）——如果产物只是"一段文字"，那么金额校验、供应商比对、预算扣减这些节点就都无法直接消费它（§3.2.2）。
- **代价在哪**：把产物做成结构化字段，意味着**Schema 与归一规则要按单据类型维护**（金额单位、日期格式、主体别名），而这份成本随单据类型数线性增长【经验】——**它是一个持续项，不是一次性的建模工作**。

**触发点（What）**

飞书一类平台把**多维表格与审批流**做成了**可被程序读写的结构化对象**（[飞书公开材料 2021-2024]，核验入口是其开放平台文档，**按当前版本核**）：字段是具名的、类型是有约束的、记录可以被创建与查询。它给出的判断是：

- **抽取的产物应当是"带位置的结构化字段"**，而不是"一段摘要"（这正是 §3.2.2 的 Schema 抽取）；
- **结构化对象的存在，让"抽取 → 校验 → 入库 → 审批"成为一条不经过人的链路**。
- **这条判断的代价**：结构化对象一旦成为流程的入参，**字段口径就成了接口**——改一个字段名或一条归一规则，影响面会顺着流程节点扩散出去，因此 Schema 的变更要走版本与回归，而不能像改一段提示词那样随手改。

**详细做法（How）**

**① 抽取按 Schema 产出，且每个字段带置信度与原文位置**

- **关键设计**：字段级置信度 + 原文位置；**字段级阈值分流**（高置信自动入库、低置信转人工）。
- **为什么必须字段级**：**整篇阈值没有调节能力**（§3.1 约束 3）——它会同时决定"所有字段都放"或"一个字段错就全拦"，而真实的错误代价分布是**按字段**不同的（金额字段错一分的代价，与备注字段漏一句的代价，相差几个数量级）。
- **判据**：每个字段都能定位回原文（页码 + 区域）；**金额 / 日期 / 主体三个字段必须有归一规则**（否则同一事实会有多种写法）；抽出的表格要能还原"行 × 列"语义（§4.2（1））。
- **关键示意**（阈值表按字段登记；具体阈值按 §4.2（3）的曲线取点，本节不给数值）：

  ```text
  字段级阈值表（按字段登记，可审计、可迭代）
    ┌ 字段 ─────── 归一规则 ────── 阈值 ─ 低置信动作 ┐
    │ amount       cny_2dp        严     转人工核对  │
    │ issue_date   iso8601        严     转人工核对  │
    │ supplier     alias_lookup   严     转人工核对  │
    │ purpose      —              宽     直接呈现    │
    └────────────────────────────────────────────┘
  三个高代价字段用更严阈值，其余放宽 —— 介入率因此可控
  ```

**② 让"介入率—漏出率"成为一条可调的曲线**

- **关键设计**：把阈值当旋钮，画出 **介入率（转人工比例）与漏出率（低置信字段直接入库且出错的比例）** 的对应关系；业务按自己对两侧代价的容忍度选点。
- **关键性质**：**这条曲线是本主题最重要的可调项**——它把一个"技术阈值"翻译成业务能讨论的两个代价（多花人力 / 多出错单）。**没有这条曲线时，阈值只能拍脑袋**；而拍脑袋的典型后果是"要么介入率高得没人用，要么错单静默入库"。
- **判据**：画得出这条曲线（阈值 → 介入率 / 漏出率），且**业务能在曲线上指出它选的那个点**——答不出"我们选在哪、为什么"，说明阈值还是技术侧单方定的（口径见主文件 §2.2；符号 `ε*` 的用法见 §4.2（3））。

**③ 未结构化之前的字段不进入写路径**

- **关键设计**：**低置信字段（或 Schema 未覆盖的字段）可以展示给人看，但不能作为写操作的输入**——写路径只接受"已确认"的字段。
- **为什么**：写操作是不可逆的（约束 1）；**把"未确认"的字段放进写路径，等于把模型误差直接接到资损上**。这条边界可以用一句检查来验证：**低置信字段是否出现在任何自动化写操作的入参里。**
- **判据**：上面那一句检查——出现一次，就是一条把模型误差接到资损上的路径；另外写路径的入参应当能追溯到某个"已确认"动作（谁确认的、在什么时候），否则"已确认"只是一个说法。

**④ 字段口径就是接口：Schema 变更要走版本与回归**

- **关键设计**：Schema 与归一规则**版本化**，流程实例钉住它启动时的那一版；规则变更之后对旧单据做一次重放，看结论有没有变。
- **为什么**：结构化对象一旦成为流程入参，字段口径就不再是"抽取侧的实现细节"，而是接口——改名或改归一规则的影响面会顺着流程节点扩散出去，而且**这类改动不会报错**：下游只是算出了另一个数（这正是触发点里"误差不以错误形式出现"的另一种形态）。
- **判据**：问"上一条归一规则是什么时候改的、改完之后旧单据有没有重放过"——答不出来，说明 Schema 还没有版本。

**具体数字（档位标注）**

- Schema 维护成本按单据类型计：金额单位、日期格式、主体别名这些归一规则**每类单据各一套**，且会在业务变化时修订【经验：成本随单据类型数线性增长】——**线性增长意味着它迟早需要一个常设 owner**（§7.1 第 6 条判据把承接能力写成门槛而不是权重），否则它会在某次业务变化后静默失效。
- 介入率的量级：`介入率` 与 `漏出率` 的对应关系随模型与字段而变，**没有通用值**——本主题不给"典型介入率"，因为任何统一数字都会在你自己的单据分布上失效【经验】——**采购与验收时拿到的"某家介入率"因此不能当基线用**（§5.3.6 第二步：本主题里"别人的数字"最不可移植）。
- **自测动作**：取最近一周的抽取结果，按字段统计"高置信自动通过"与"低置信转人工"的比例，以及转人工的**核对通过率**（通过率极高说明阈值过严）。顺带看一件事：**低置信字段有没有出现在任何自动写操作的入参里**——出现一次就是一次不可逆风险。

**失败教训**

**第一版让模型输出"一段整理好的文字"**——下游由人把它填进表格。结果是：**自动化的收益被"人肉搬运"吃掉大半**，而更严重的是**搬运过程引入了新的错误**（人在抄写时会简化、会漏项）。教训：**抽取的产物形状决定了它能被谁消费**——产出"文字"时下游只能是人，产出"结构化字段"时下游可以是流程。**机制层的解释**：这一层"人肉搬运"的成本不是线性的——它同时引入**延迟**（人什么时候有空）与**新的误差源**（抄写会简化、会漏项），因此它的代价随单量放大；而**这些错误在返工率上会以"不是模型错"的形式出现**，从而让排查方向从一开始就偏——这也是"只报字段准确率看不出问题"的原因。

### 6.4 某大型制造企业"**跨系统执行的补偿动作表：把"失败怎么退"变成业务约定 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

一张采购单要写进 ERP、财务、库存三个系统。团队第一版的假设是"三写要么全成功、要么全失败"。

- **约束在哪**：三写之间没有分布式事务可用——跨组织的系统不会配合两阶段提交，因此"要么全成功、要么全失败"这个假设在工程上不成立（§3.2.6 的机制：部分成功是分布式写入的常态）。
- **代价在哪**：承认"部分成功是常态"，意味着**每一个可写步骤都要额外回答一个问题**（失败了怎么退），而这个问题没有技术层面的通用答案——它是业务问题，因此**这份工作量的主体在业务侧**（§7.7 的迁移代价表把这一条写成"业务侧工作量占大头"）。

**触发点（What）**

一次事故——ERP 写入成功、财务入账成功、库存写入失败。**已入账的凭证退不回来**：财务系统里没有"撤销入账"这个动作，只有"红字冲销"；而红字冲销需要财务在月末前处理，否则账上会留一笔尾差。事故的处理花了三天，其中两天用在**确认"该怎么退"**上下。

- **这次事故给出的成本结构**：处理三天，其中两天用在确认"该怎么退"上——**代价的大头落在"不知道该做什么"上，而不是"做"本身**。这一条比任何比率都更能说明补偿动作表的性质：它不是执行成本，而是**决策成本的预先支付**。

**详细做法（How）**

**① 补偿动作表（一份业务文档，不是技术组件）**

- **关键设计**：对**每一个可写步骤**，写清"它失败时怎么退"：冲销、红字单、反向单据、还是只能人工介入；并标明**该动作由谁执行、在多长时间内有效**（有些冲销有账期限制）。
- **为什么它必须由业务 / 财务确认**：**分布式系统里没有通用的"回滚 API"**——"退"在不同系统里的语义不同（撤销 / 冲销 / 反向 / 无法撤回）。**这份表是业务约定，技术只能实现它**；由技术单方定义时，退不干净只是时间问题。
- **判据**：这份表能**逐个可写动作**对上来——每一个可写步骤要么有一个写明"由谁在多长窗口内做什么"的逆向动作，要么被列进"不可逆、必须前置审批"的清单（§4.2（5）的 `no_compensation`）。

**② 不可逆步骤不放链路中间**

- **关键设计**：把链路按顺序画出来，**在每个可写步骤后问"如果下一步失败，这一步怎么退"**——答不出的那一格，就是红线：要么把它挪到链路的最后一步，要么在它前面把校验做足。
- **判据**：**每个可写步骤都能回答它的"退法"**；不能回答的，只能放在"后面没有会失败的步骤"的位置上。
- **关键示意**（本例的链路逐格检查；窗口与动作名按 §4.2（5）的补偿动作表形态登记）：

  ```text
  逐格检查（本例链路：ERP 入账 → 财务入账 → 库存写入）
    步骤               退法                              答得出吗
    erp.post_invoice   erp.reverse_invoice（红字冲销）       ✔
    finance.post       红字冲销，且须在本月结账前完成         ✔（有窗口）
    inventory.add      重试 / 人工补录                       ✔
    ────────────────────────────────────────────────
    事故形态：前两步成功、第三步失败
      → 已入账的一笔退不回来，只能走"红字冲销 + 月末前处理"
      → 可见红线不在"哪一步会失败"，而在"哪一步的退法有窗口"
    判据：每个可写步骤都要回答"退法"，并标明窗口与执行人
  ```

**③ 幂等键取业务要素 + 按实例的短期凭证**

- **关键设计**：幂等键取**业务要素**（单号 + 动作 + 目标系统），而不是自增 ID；凭证**按流程实例发放**、最小权限、短期有效。
- **两条机制**：**幂等键取自增 ID 等于没有幂等**（重试会生成新的 ID）；**凭证按服务发放会让泄漏面随流程数扩大**（一个服务凭证泄漏，影响所有流程）。
- **判据**：用同一个幂等键重跑一次流程，**不产生第二笔入账**（§4.2（5）的判据）；再用超 scope 的凭证调用一次，看是否被拒并留痕。

**④ 补偿动作自身也要留痕（`inverse_of`）**

- **关键设计**：补偿动作作为一条独立流水记录写下来，并用 `inverse_of` 指回被它补偿的那条动作（§4.5 模板 2 的表结构）。
- **为什么**：财务上的"退"通常是**产生一笔反向记录**而不是抹掉原记录，因此"退没退"在数据上表现为**两条记录成对出现**；没有这个指向关系时，对账只能靠金额与时间人工配对——而**"退不干净"正是以这种方式在账上显形的**：留一笔谁也说不清来路的尾差。
- **判据**：抽一笔已冲销的入账，问"它的反向记录是哪一条"——能从 `inverse_of` 直接指出来，才算可证明已退回（§8.3 的口径：对账与留痕两者都要有）。

**具体数字（档位标注）**

- 事故处理的构成（这条比任何比率都更有说服力）：本例中"确认该怎么退"占了两天，**执行退**不到一天——**补偿动作表的缺失，代价主要花在"不知道该怎么退"上，而不是"退"本身**：既然代价在"不知道"，预先写好补偿动作表就是把这份成本从事故现场移到平时，而平时做这件事的边际成本远低于事故时。
- 幂等键的覆盖：**所有写操作**都要有；漏一个就会出现一次重复入账【经验：重复入账通常在"客户端超时后重试"这类边界上发生】——漏一个写操作就等于留了一条重复入账的路径，而这类错误要等到月末对账才暴露，修复要回退已经发生的账务，代价远高于补一个键。
- **自测动作**：把链路按顺序画出来，在**每个可写步骤后**写下"下一步失败时这一步怎么退"；答不出的标红。**再做一次演练**：人为制造某一步失败，看系统是否按表里的动作收敛。**演练比表本身更重要**：表写对了却没人按它收敛过，等于把决策成本重新推迟到下一次事故。

**失败教训**

**把补偿当成"技术兜底"来设计**——第一版只在代码里写了"失败就重试"，没有为每个写步骤定义退法。事故发生后，团队发现**三个系统里的"退"是三种不同的事**（撤销 / 冲销 / 反向），而这些语义只有财务说得清。教训：**补偿动作表要和幂等键一起设计、由业务确认**；它看起来像文档工作，实际是这条链路的可靠性来源——**没有它，多写链路的"部分成功"就只能靠人的临场判断收拾。** **机制层的解释**：技术侧只能看见接口，看不见语义——在接口上"撤销 / 冲销 / 反向"都是一次调用，在业务语义上它们分别是"抹掉"、"记一笔反向记录"和"补一条更正"，**因此这件事在原理上就无法由技术单方完成**；把它当技术兜底来排期，等于把一段必须由业务提供的信息，排进了一个拿不到它的流程里。这也解释了为什么"重试"永远替代不了"补偿"：**重试只改变成功的概率，不改变已经发生的事**。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条**顺序固定**的路径，与 §4.8 对应：

1. **先定红线**（§6.4）——找出不可逆步骤，把它们放到校验与审批之后，并为每个可写步骤写下"怎么退"。**这一步不需要任何模型能力，但它决定后面所有自动化能走多远。**
2. **再接既有权威源**（§6.1、§6.2）——权限继承既有身份（单一权威源）、流程骨架用既有流程引擎（不重建状态机）。**这两件事都是"用已有的东西"，不是"建新的东西"**，因此它们应当早做而不是晚做。
3. **再把抽取做成结构化字段并画出入率曲线**（§6.3）——让下游可以是流程而不只是人；并用介入率—漏出率曲线把阈值变成业务能讨论的东西。
4. **最后做端到端**（§3.2.8）——只有在红线、权威源、结构化字段都就位之后，"一句话办完"才是可交付的能力；否则它只是把一个更快的链路接到同一个不可控的出口上。

**顺序的反面**：先做端到端（因为"看得见、好演示"），后补红线与补偿——**端到端会把"模型能调的动作"迅速扩展，而每扩展一个可写动作就多一格需要写"怎么退"的位置**；补的时候要回头看已经上线的全部路径。**这是四个案例里唯一一个"越努力越难"的顺序。**

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 助手自建权限表 | 撤权后仍能问出内容 | 存在第二个权限源 → 泄漏 | 权限继承既有身份（§6.1） |
| 权限判定在检索之后 | 无权内容已进上下文与日志 | "看起来安全" | 可见域前置 |
| 流程跳转写进提示词 | 卡住的单据不可见 | 状态不可观测 | 状态机交给流程引擎（§6.2） |
| 人工节点无超时 | 单据永久挂起 | 安静地积累 | 全状态超时 + 默认动作写死 |
| 审批只记"已批准" | 事后无法还原依据 | 责任无法认定 | 审批含输入快照 + 理由 |
| 抽取只产出"一段文字" | 下游由人搬运 | 收益被人肉搬运吃掉，且引入抄写错误 | 产出带位置的 Schema 字段（§6.3） |
| 整篇阈值 | 介入率与错单率同时难降 | 阈值失去调节能力 | 字段级阈值 + 介入率/漏出率曲线 |
| 低置信字段进写路径 | 模型误差直接接到资损 | 不可逆错误 | 写路径只接受已确认字段 |
| 无幂等键 / 键取自增 ID | 重复入账 | 财务数据失真 | 键取业务要素（§6.4） |
| 不可逆步骤在链路中间 | 后续失败后已入账退不回 | 资损 | 按"失败怎么退"逐格检查并挪位 |
| 补偿动作由技术单方定义 | 冲销与财务口径不符 | 退不干净、账留尾差 | 补偿动作表由业务/财务确认 |
| 凭证按服务发放 | 泄漏面随流程数扩大 | 安全风险 | 按流程实例 + 最小权限 + 短期 |
| 无端到端指标 | 只报字段准确率 | 不知道是否真在替人干活 | 端到端介入率 + 返工率 |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——办公自动化的收益形态是"人时、返工与资损的避免"，不是"处理量"。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 人时节省 | 单张单据的人工处理时长 × 处理量 | 从**分钟级全程**降到**秒级 + 低置信字段的核对** | 记录一周内单张单据的实际处理时长 |
| 介入率可控性 | 转人工比例 与 低置信字段核对通过率 | 由字段级阈值决定（**可调**）；通过率极高说明阈值过严 | 按字段统计两个比例 |
| 返工率 | 因字段错误导致的退回 / 更正次数 | 靠"低置信不进写路径"**从机制上**下降 | 取最近 50 张单据数退回次数 |
| 时效 | 各段 P95（采集/解析/抽取/审批/执行） | 分开测才能归因；人工节点无超时会让 P95 无意义 | 抽 20 张单据测五段 |
| 资损避免 | "已执行退不回"的事故次数 | 从**偶发**到**按补偿动作表收敛** | 数最近一年此类事故及其处理耗时 |
| 流程可观测性 | 能否统计"多少单据卡在哪一步" | 从**答不出**到**可查** | 当场查一次当前滞留分布 |
| 代价 | 补偿动作表的维护 + 抽检 + 流程引擎适配 | 由业务与财务共同投入（**不是纯技术成本**） | 统计补偿动作表的条目数与最近一次修订时间 |

**读法**：前四项是**效率与质量收益**，第五、六项是**风险与可观测性收益**（避免资损、能看见流程），最后一项是**代价**。办公自动化最容易出现的错位是**只算"处理了多少张单据"，不算返工与事故**——前者是吞吐，后者才是价值。**另一条读法**：最后一项里"补偿动作表的维护"看起来像文档工作，但它对应的是第五项的资损避免——**砍掉它的投入，代价会在某一次多写失败时一次性付清。**

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**红线与补偿先定**（不需要模型能力，但决定自动化能走多远），**权限与流程骨架接既有权威源**（用已有的东西，不是建新的东西），**抽取产出结构化字段并画出介入率曲线**（让下游可以是流程），**端到端最后做**（它只是把更快的链路接到同一个出口上）。四次失败教训指向同一件事：**办公自动化的失败几乎都不是"模型不够好"，而是"某个不可逆的地方没有闸门、某个跨系统的动作没有退法"**——缺红线就把风险交给概率、缺补偿就把收拾交给临场判断。

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你最像的案例，只做一件最小的事——按它的"判据"跑一次自测（撤权后问一次助手 / 查一次单据滞留分布 / 统计一次介入率与核对通过率 / 逐格写下"失败怎么退"）。哪一件**今天就能做**就先做它：能被立刻验证的缺口，优先级永远高于推断出来的缺口。
