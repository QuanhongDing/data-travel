## 4. 工程实现

一致性方案在 §3 与 [§7](08-data-consistency-section-7-sec7.md) 里是候选族与一棵决策树；本节要回答的是另一类问题：**方案定了之后，谁先动手、每一步怎么验收、手上多出什么、存量代码与存量数据怎么办、双轨维持多久。**

本文件面向两类读者——

- **从零搭建**：核心链路是新建的，可以直接按目标形态落。按 Step 1 → Step 5 顺序走，重点是 Step 2（写集与冲突度盘点）与 Step 5（分区与协调者故障演练）。
- **存量改造**：已有分库分表、已有跨服务调用图、已有在跑的补偿逻辑。先读 4.4，再回到 Step 1：存量改造的业务分级不是「按业务贴标签」，而是从既有调用图与写集冲突里读出来。

分岔点在于**不一致发生时能否自我修复**——这是筛硬约束的判据，也是决定你走族 1 / 族 3（协调型事务 / 数据库内核型）还是族 2 / 族 4（日志与事件型 / 无协调型）的分水岭；四族的定义与成员清单见 [§7.2](08-data-consistency-section-7-sec7.md)。

### 4.1 落地步骤

**Step 1：业务分级（阶段 1，约 2–4 周【经验】；取决于业务域数量与评审轮次）**

1. 强一致业务（金融 / 库存 / 订单状态）：不允许读到旧值，且不一致不可自我修复。
2. 最终一致业务（社交 / 评论 / 通知）：不一致可被对账、重算或用户重试吸收。
3. 弱一致业务（日志 / 推荐 / 埋点）：可丢、可重算、可接受冷启动。
4. 每一档写出「不一致发生时由谁发现、由谁修复」——这一列决定后面能选哪些族。

- **产物**：分级清单（每个业务域一行：档位 + 不一致的发现方 + 修复方 + 可容忍的陈旧窗口）。
- **判据**：拿清单里任意一条「强一致」，去代码仓库找它的写路径，看是否存在「写完立即按同条件查询」的读路径；存在则说明这条链路的读己之写没有被显式声明。再拿任意一条「最终一致」，看它有没有登记一个可观测的滞后量（副本落后版本数 / 中继积压）——没有滞后量的「最终一致」在运行期无法证明自己在收敛。
- **为什么必须这一步 / 为什么在这个位置**：分级是**静态决策**，一旦定下就与运行时的真实冲突率脱节；但它必须排在协议选型之前，因为协议的正确性前提由档位决定——把资金链路放进最终一致档，后面选什么协议都是在给一个错误的目标做优化。顺序反过来（先上框架再补分级）的代价是：框架的行级锁、状态表、补偿队列全部白建，清理它们的成本高于当初审一遍。

**Step 2：写集与冲突度盘点（约 2–4 周【经验】；随实体数量增长）**

1. 对每个核心实体回答：**同一实体是否存在多个写入者**（多 Region、多端、离线重放、人工修数）。
2. 对每个高并发实体测一次**热点行的并发请求数 / 该行可用并发度**的比值。
3. 标记**不可补偿的步骤**（已出账到银行、已发出短信、已监管报送、已回调第三方）。
4. 记录两类量：事务参与者数量的分布、整笔事务 P99 由哪个参与者决定。

- **产物**：写集矩阵（实体 × 写入者数量 × 是否要求不丢更新）+ 热点行冲突度清单 + 不可补偿步骤清单 + 参与者规模分布。
- **判据**：拿写集矩阵里「写入者 > 1」的每一行，去代码里确认是否已有版本判定——确认方式是搜该表的更新语句里有没有 `version` / 条件更新，而不是看设计文档。再拿不可补偿步骤清单，逐一确认它们在链路中的位置；只要有一个不在链尾，这一步就没做对。
- **为什么必须这一步 / 为什么在这个位置**：这两条决定候选集合，而不是给候选排序——写集相交时最终一致必然以静默丢更新的形式失效（§3.2.2），这不是配置问题；不可补偿性决定 Saga 能不能用（§3.2.4）。它们必须排在协议选型之前，因为一旦漏掉，选型讨论会在「哪个更快」上打转，而真正的问题在正确性一侧。

**Step 3：协议选型（阶段 2，约 3–6 周【经验】；随待选型链路条数与需并行比对的候选族数增长）**

1. 强一致档：能收进一个库的走分布式数据库（Global DB）；跨异构资源、同城、低冲突的走 2PC / XA；高冲突热点走 TCC。
2. 最终一致档：长链路且每步可补偿的走 Saga；只需「写库与发事件同生共死」的走 Outbox；不侵入业务代码的走 CDC。
3. 跨服务：按可逆性分段（Saga），热点段内再嵌 TCC。
4. 每一族选出具体实现，并写下「不选其余候选的原因」——用于下次评审时重推。

- **产物**：协议选型矩阵（档位 → 协议 → 实现 → 不选其余候选的机制层原因）+ 阈值依据记录。
- **判据**：抽 3 个选项，看它们的选定理由里有没有出现「性能好」「更先进」这类词；出现即视为没推完，因为本主题下真正的判据是**协调点放在哪一层**与**资源持有多久**两条（§3.1、[§7.3](08-data-consistency-section-7-sec7.md)）。第二条判据：每一个选了 TCC 的链路，是否给出过该热点行的预留失败率自测数据——这个量必须自测，不给固定数值。
- **为什么必须这一步 / 为什么在这个位置**：协议选型是决策树的执行，而树上每个分支都挂在一条可观测的量上；在 Step 2 的量拿到手之前选型，等于在没有阈值的情况下走树，走到哪一支都是凭印象。这就是选型必须排在盘点之后的原因。

**Step 4：实现（阶段 3，约 6–12 周【经验】；随参与方数量与分支数增长）**

1. 分布式事务框架（Seata、DTM 一类）：TCC 三接口、Saga 编排或编制、事务状态表。
2. 一致性协议（自研或开源）：Raft / Paxos 组（etcd、ZooKeeper 一类）、Quorum 读写（`R + W > N`）。
3. 幂等性设计：全局唯一业务键 + 去重表；去重窗口必须覆盖乱序窗口。
4. 补偿与对账：补偿链路的幂等与重试、对账任务与差异挂账流程。

- **产物**：可运行的事务链路 + 幂等键与去重表 + 补偿链路 + 对账报告 + 三条必须写在接口上的语义：`Try` 是否预留、`Confirm` / `Cancel` 是否幂等、`Cancel` 是否支持空回滚。
- **判据**：抽 3 条跨服务写操作，重复投递同一条业务请求，看是否产生第二次副作用；抽最近一次补偿失败记录，看它是否进过人工介入队列、且有一条对账差异与之对应。**判据是这两个可重现的动作，不是「幂等性已实现」。**
- **为什么必须这一步 / 为什么在这个位置**：幂等与对账必须与主链路同一次交付，因为至少一次投递是这类架构的常态而不是异常（§3.5 反模式 2）；把幂等当成后续优化项的团队，会在第一次重试或第一次故障切换时拿到重复副作用，那时数据已经写进去了。补偿链路同理——Saga 的正确形态是「正向链路 + 补偿链路 + 对账链路」三段，对账不是补偿的替代品，而是补偿的必要兜底。

**Step 5：演练验证（阶段 4，约 2–4 周/轮，之后常态化【经验】）**

1. 网络分区演练：明确分区发生时是拒绝写还是接受写。
2. 协调器故障演练：2PC 的协调者、Saga 的编排器、Outbox 的中继，逐个停掉。
3. 数据冲突演练：构造同一实体的并发写，验证是否被检测、如何消解。
4. 每一轮把结论写进 Runbook，而不是留在演练报告里。

- **产物**：演练剧本 + 演练报告（分区期间的行为、恢复耗时、丢失或重复的条数）+ 更新后的 Runbook。
- **判据**：停掉协调者后，系统行为与设计里写的一致——设计说「拒绝写」，就必须观察到写请求被确定性拒绝，而不是超时；数据冲突演练的判据是「并发写之后能否回答哪一次被保留、依据是什么」，答不出依据说明冲突是被静默消解的。
- **为什么必须这一步 / 为什么在这个位置**：协调者恢复、悬挂事务清理、补偿失败处置这三类问题的隐性成本随**故障次数**增长，而它们只在出事时暴露（§3.1、§7.4）——演练是唯一能在低代价时刻把它们暴露出来的手段。它排在实现之后是必然的；但排在「上线」之前是必须的，因为分区行为未定义的系统在第一次真分区时，两个分区会各自推进出相反的决定。

**哪一步最常被跳过**：Step 2（写集与冲突度盘点）。它产出的是一张表而不是一段代码，评审时看不出进展。

跳过它的第一个症状出现在**运行一段时间之后**（不是上线时）：写入者数量在业务演进中会变——新加一个 Region、新加一条离线重放、新加一个人工修数入口——一旦同一实体出现并发写，LWW 或「无版本号的 upsert」就会静默丢更新，系统不报错，只在日终对账里表现为「账对不平但说不清哪一笔」。

### 4.2 关键技术点

**Seata TCC 模式（Try / Confirm / Cancel）**

- **做法**：每个参与方从 1 个接口变成 3 个——`Try` 预留资源（冻结额度、占用库存），`Confirm` 幂等确认，`Cancel` 幂等释放；主业务服务侧维护事务状态表，把「走到哪一步」落盘。三接口的形态大致如下：

```java
@LocalTCC
public interface OrderTccService {
    @TwoPhaseBusinessAction(name = "createOrder",
                            commitMethod = "commit",
                            rollbackMethod = "rollback")
    boolean tryCreate(OrderRequest req);          // Try：订单落草稿 + 冻结库存额度
    boolean commit(BusinessActionContext ctx);    // Confirm：幂等确认（草稿转正）
    boolean rollback(BusinessActionContext ctx);  // Cancel：幂等释放（须含空回滚分支）
}
```

- **做法（续）**：三类边界必须显式处理——空回滚（`Try` 未到先收到 `Cancel`）、悬挂（`Cancel` 先到、`Try` 后到）、幂等；三者都靠事务状态表判定，而不是靠调用顺序「应该不会这样」。
- **机制**：因为「锁」被下沉成业务语义上的预留，所以同一记录的争抢表现为**预留失败**而不是**锁等待**——预留失败可以被业务吸收（排队、重试、确定失败），锁等待只能排队。这就是它把冲突从数据库层搬到业务层、并因此抬高并发上限的原因。
- **失效条件**：当**热点行的并发请求数低于该行的可用并发度**时，这条反转成纯成本：预留失败根本不会发生，团队只是多背了两套接口、一张状态表和三类边界 bug（实现成本按「每接口 1–3 人日、n = 6、每方新增 2 个接口时约 12–36 人日」推算【推算】（推导链：6 × 2 × (1–3) = 12–36））。反向失效同样存在：参与者里只要有**不可补偿的外部系统**（已出账、已发短信），`Cancel` 在语义上不存在，方案退化成人造补偿——症状是「`Cancel` 的实现里出现『记录一条不一致 + 通知人工』」，这等于承认补偿写不出来。热点行的预留失败率阈值不给固定数值，必须自测【经验】。
- **档位**：接口数 1 → 3 是定义决定的常量；实现成本为【推算】；预留失败率为【经验】。

**Outbox 模式（本地消息表 + 异步发布）**

- **做法**：业务写入与事件写入放进**同一个本地事务**；独立中继读出未投递记录、投递到消息系统、标记已投递；消费端用幂等键去重；outbox 表按时间分区，消费后即删或定期归档；中继的积压延迟做成可观测指标。

```java
@Transactional   // 业务写入与 outbox 写入共用一个本地事务
public Order createOrder(OrderRequest req) {
    Order order = orderRepository.save(req.toOrder());
    outboxRepository.save(OutboxMessage.of("order.created", order.toJson()));
    return order;
}

// 中继（独立进程，只做「读未投递 → 投递 → 标记已投递」）
@Scheduled(fixedDelay = 1000)
public void publishOutbox() {
    for (OutboxMessage msg : outboxRepository.findUnpublished()) {
        kafkaTemplate.send(msg.getTopic(), msg.getPayload());
        outboxRepository.markPublished(msg.getId());   // 这一步失败 → 下次重投
    }
}
```

- **机制**：因为两条写入共享同一个本地事务，所以「业务数据在、事件不在」在结构上不可能发生——原子性由本地数据库保证，而不是由投递机制的可靠性保证。这是它相对「应用双写」唯一且决定性的差别：双写没有原子边界，失败必丢一边。
- **失效条件**：当**写入速率增长到中继只能批量抽数**时，「本地原子」反转成「投递延迟不可控」：Outbox 只保证事件不丢，不保证何时发出，中继吞吐成为端到端时延的新上限，而这个上限**不体现在业务写入的耗时里**，容易被误读成「系统很健康」。第二个失效条件是表增长：按每秒 200 条、每条约 1 KB 推算，每日新增约 17 GB【推算】（推导链：速率 × 86,400 秒 × 单条大小）；不做按时间分区，清理语句迟早会锁表。症状是「写入 P99 正常、下游可见延迟持续上升」，以及「某个凌晨的清理任务导致写入抖动」。
- **档位**：17 GB/天为【推算】，速率与单条大小按【经验】取值。

**Raft / Paxos 共识（etcd、ZooKeeper 一类）**

- **做法**：每个分片放多个副本，Leader 接收写入、把日志复制到多数派，多数派持久化即提交；任期（term）单调递增，只有包含最新日志的节点能当选；把协调者的恢复责任交给共识层，而不是自研恢复扫描。
- **机制**：因为提交点位于「多数派持久化」这个崩溃后仍然存在的位置，所以读到的值必定是已经定下来的值——「读到旧值」在结构上不可能发生；同时因为决定权被复制到多数派，单副本故障不再需要人工切主。这是强一致这条路的立足点：**决定权必须落在一个崩溃后仍然存在的位置**（§3.2.1）。
- **失效条件**：当**把模型或其它非确定组件放进重放链路**时，这条前提被破坏：共识要求同一份日志在每个副本上重放出同一个状态，而「输入相同则输出不同」的组件会让副本各自算出不同状态。症状是「副本之间数据不一致但没有任何节点报错」（[§5.2.3](08-data-consistency-section-5-ai.md)）。修法是把模型的输出先落为记录再复制——**模型本身不能出现在重放路径里**。另一个失效条件是参与者中出现不可补偿的外部系统：共识只能保证协议内成员的状态一致，协议外的副作用既不能等待也不能撤回。
- **档位**：机制为定义性事实；Raft 的协议定义见 Ongaro & Ousterhout《In Search of an Understandable Consensus Algorithm》（USENIX ATC 2014）【公开】；Spanner 的时间不确定区间与提交等待机制见 Corbett 等《Spanner: Google's Globally-Distributed Database》（OSDI 2012）【公开】。两篇论文均可按标题自行检索核验。

**幂等与去重（贯穿所有模式的底层件）**

- **做法**：为每一次跨服务写构造一个全局唯一的业务幂等键（流水号 / 请求 ID），在消费侧维护去重表；去重记录带「已处理」与「处理中」两态以防并发重复；去重窗口必须覆盖乱序窗口——乱序到达时，只做「键存在即跳过」会把原始请求也丢掉。
- **机制**：因为至少一次投递是这类架构的常态（投递成功但标记失败、消息中间件重投、消费位点回退都会产生重复），所以去重不是防御性编程，而是模式的组成部件；把「副作用执行」与「幂等键落库」放进同一个本地事务，重复投递就只会在去重表上撞一次墙。
- **失效条件**：当**去重表的保留窗口短于乱序窗口**时，重放的老消息会被当成新消息执行第二次——症状是「对账里出现同一笔请求的两条记录，且两条都看起来正常」，而它只在重试、扩缩容、故障切换这些时刻出现，绝大多数时候系统工作正常。另一个失效条件是幂等键由业务方自行生成：部分渠道漏做即产生重复扣款，所以这类键应由平台层强制而不是靠约定（[§6](08-data-consistency-section-6-sec6.md) 的核心账务案例记录了这条教训）。
- **档位**：机制为定义性事实；去重窗口时长由乱序窗口决定，需实测，不给固定值【经验】。

**CDC（变更数据捕获）**

- **做法**：不侵入业务代码，读取数据库日志（binlog / WAL）把变更投递到下游；采集位点可重放；schema 变更前先确认下游兼容策略。
- **机制**：因为读的是数据库日志而不是业务表，所以它既能拿到「业务写入与事件同生共死」的效果，又不需要业务代码显式写事件表——这让它成为「把数仓 / 缓存 / 搜索索引同步出去」这条需求上比 Outbox 更省的路径。
- **失效条件**：当**同一个边界内还有跨系统的事务要求**时，CDC 不成立——它只保证「数据变更后事件会被发出」，不保证「事件与另一套系统的写入原子」（§3.3 把这条写成「把 Outbox 当跨库事务用」的反向误用）。症状是「下游收到了事件，而对应的业务事务实际上回滚了」，或者「采集组件落后导致下游读到的位点与业务库差了几个小时而不自知」。
- **档位**：机制为定义性事实。

**Event Sourcing（+ CQRS）**

- **做法**：只追加事件（`(aggregate_id, version)` 作主键，唯一约束即乐观并发控制），当前状态由重放得出；配套快照——快照不是优化而是必需品；读侧通常分离成读模型并记录同步位点。
- **机制**：因为事实以追加形式被保留，所以任意时刻的状态都能被重算，审计与回溯不需要额外机制；并发控制也直接由主键承担，不必另加锁。
- **失效条件**：当**合规要求「数据主体可删除」**时，「不可删只可追加」反转成「合规义务无法履行」：事件流是事实记录，物理删除会破坏重放一致性，只能用反向事件表达删除——而反向事件是否满足监管口径不由技术决定。第二个失效条件是重放成本：每聚合每天 100 个事件时一年约 3.65 万个事件，单事件重放按 1 ms 计，一年后一次全量重放约 36 秒，超出交互式读取预算【推算】（推导链：事件数 × 单事件重放耗时）——这也是快照必须在选型时就一起设计的原因。症状是「读取接口的 P99 随系统运行时长逐月抬升」。
- **档位**：重放耗时为【推算】；「删除类合规」的技术实现判据是问业务与法务，而不是问文档。

### 4.3 工具链与平台

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| **分布式事务** | Seata、DTM、ByteTCC | 判据是「协调点放在应用的哪一层」：框架持有协调者，你就要自己兜住协调者恢复、悬挂事务清理与状态表运维。参与者同构且只有数据库时，优先看数据库自带的 XA，而不是引入框架 | 多一层框架即多一套状态表与后台恢复任务；事务分组、滑动窗口一类配置成为新的故障面，且排障路径比业务代码长 |
| **一致性协议** | etcd、ZooKeeper、Consul | 判据是「你要的是定序还是选主」：要日志复制与选主用 etcd（Raft）或 ZooKeeper（ZAB）；只要服务发现与 KV 可不启用共识语义。自研协调逻辑只有在有 7×24 值班能力时才成立 | 自研要自己证明脑裂与丢决议不会发生；选重组件则运维面（奇数节点、磁盘 fsync、快照）随集群数放大 |
| **Global DB** | CockroachDB、TiDB、OceanBase | 判据只有一条且是硬边界：**需要一起提交的数据能否全部住进这一个产品**。能收编 → 协调者下沉进内核，恢复责任转移给数据库；不能收编 → 它只覆盖住进去的那部分，外围仍是最终一致 | 收编不成却按「用了 Global DB 就没一致性问题」设计，结果核心圈强一致、外围圈静默不一致，而两圈的边界没写下来 |
| **CDC** | Debezium、Canal、Maxwell | 判据是「下游能否容忍秒级延迟」与「是否需要业务代码不感知」：需要不侵入 → CDC；需要与业务写入同库原子 → 用 Outbox | 用 CDC 承担「本地写入 + 对外通知」的原子性，等于把原子边界交给一个异步采集组件；另加一套集群与 schema 兼容流程 |
| **消息队列** | Kafka、RocketMQ、Pulsar | 判据是「是否需要把发消息与提交消费位点纳入同一原子边界」：需要 → 选支持幂等生产者与事务的消息系统（Kafka 的事务语义随 0.11 引入，设计见 KIP-98《Exactly Once Delivery and Transactional Messaging》，2017，可按该编号在 Kafka 官方 KIP 索引核验【公开】）；只需要发布订阅 → 普通配置即可 | 用不支持事务的消息系统承担「消费—处理—投递」的端到端一次语义，等于把去重与顺序全推给业务代码，而这条约定通常只写在注释里 |

上表最容易被误选的是**分布式事务框架**：多数团队把「选框架」当成第一步，而真正的第一步是问「这条链路上有没有一个必须存在的协调者，它崩了谁恢复」。框架解决的是「怎么协调」，解决不了「协调者恢复」。

第二容易被误选的是**Global DB**：在「能收编」的约束下它是最省的路径，在「不能收编」的约束下它是最贵的错觉——它不改变外围系统的一致性，只是让核心圈不再有那个问题，而两圈之间的边界经常没被写下来。

### 4.4 存量迁移

**① 先做什么可以立刻见效且可回退**：从**幂等键与去重表**开始。它改的是每条写入路径上的一个字段加一张表，不改事务形态、不改数据归属，任何一条链路都可以单独回滚（去掉去重检查即回到原状）；而它立刻消掉的是存量系统里最常见、最难查的一类问题——重试与故障切换导致的重复副作用。第二个可立即做且可回退的动作是**把不可补偿步骤标出来**：它不改代码，只改评审项，却会立刻否掉一部分「用 Saga 包住整条链路」的计划。常见误区是先上事务框架再补幂等：框架会把「已提交」的语义讲得比实际更完整，团队会以为重复投递已经被框架处理了。

**② 历史资产怎么分类处理**：存量数据按「不一致能否自我修复」分三类，分别对应三种处置。

| 分类 | 特征 | 处置 | 为什么 |
| --- | --- | --- | --- |
| 不一致可自我修复 | 账目、计数、状态类，能被对账或重算还原（内容、埋点、通知、推荐） | 增量改造：只把新增写入切到新机制，历史数据不搬迁，靠一轮全量对账确认基线 | 搬历史数据不改变任何一条业务结论，却要付停机与双跑两笔成本；先固定基线，后续差异才有参照 |
| 不一致可检测但不可自动修复 | 资金、库存类，对账能发现、修复需要人工决策 | 只迁移「仍在被写入的部分」：热数据走新机制，冷数据冻结并打标挂账（标注「此段历史不由新机制保证」） | 全量迁移的收益只在真正会再被写的那部分；把不可自动修复的差异混进迁移，会让挂账变成永久负债 |
| 不一致不可检测 | 静默丢更新（LWW 覆盖）、无版本号的 upsert 造成的丢失，冲突不留任何记录 | 先从「能不能检测」开始补：加版本判定或冲突记录，把不可检测变成可检测，再谈修复 | 不可检测的不一致无法度量，也无法判断迁移是否成功——先补检测的性价比远高于先补修复 |

三类都以「影子读 + 对账」推进，而不是以「一次切换」推进：影子读给出差异基线，对账给出收敛判据，两者都不改写入路径，因此都可随时撤掉。

**③ 迁移期的双轨怎么维持、维持多久**：双轨的成本结构是「双份组件 + 全链路对账 + 双份值班」，而且本主题有一条特有约束——**一致性方案的迁移几乎不能在业务高峰期做**，因为迁移期间新旧两套机制必须在同一份数据上共存（双写或影子读），而双写正是「写库与发事件没有原子边界」那条反模式的成因。因此按三段推进：

1. 先只读切换：新读路径与旧读路径并行，差异挂账；旧路径仍是权威。
2. 再只写切换：新写路径成为权威，旧路径降级为校验（两侧写入结果比对）。
3. 最后下线旧路径：关闭双写与比对，保留一段可回退的影子映射。

双轨时长的**下限**由一个完整对账周期决定（要覆盖月末、结算、大促这类周期性场景，通常不少于一个月【经验】），**上限**由「参与方分批数 × 每批观察期」决定。可以分批，不能压缩观察期——压缩观察期等于放弃唯一的判据。

**④ 什么信号说明可以退出双轨**：

- **对账差异收敛且可归因**：连续若干个对账周期的差异条数趋于 0，剩余差异全部能追到具体成因（历史脏数据 / 已知不可检测段），而不是只有「数字在下降」。
- **补偿链路有真实记录**：迁移期内至少发生过一次补偿，且这次补偿失败后被对账接住、进入了人工队列。**没有发生过补偿的双轨期，不能证明补偿链路可用。**
- **故障演练通过**：分区与协调者故障演练的行为与设计一致（设计说拒绝写，就要观察到确定性拒绝），且结论已写进 Runbook。

顺序上有一条硬约束：**先做只读切换、再做只写切换、最后才动数据形态**（从行到事件、从单模型到读写分离这类变化）。数据形态变化与流量切换同时进行时，出问题两侧都不完整，无法回退。

### 4.5 模板 / 示例

**模板 A：Saga 编排式定义（分段按可逆性，不按服务边界）**

```java
// 分段顺序 = 可逆性顺序：不可逆步骤压到最后
SagaDefinition saga = new SagaDefinition("createOrder")
    .step("createOrder")            // 可逆：补偿 = 置为终态「已取消」
        .action(orderService::create)
        .compensation(orderService::cancel)
    .step("reserveInventory")       // 可逆：补偿 = 加回，需幂等 + 并发校验
        .action(() -> inventoryService.reserve(req))
        .compensation(() -> inventoryService.cancelReserve(req))
    .step("chargePayment")          // 部分不可逆：内部记账先行，外部调用压到最后
        .action(() -> paymentService.charge(req))
        .compensation(() -> paymentService.refund(req))
    .step("sendNotification")       // 不可逆：必须排在最后
        .action(() -> notificationService.send(req))
        .compensation(() -> notificationService.cancel(req));  // 语义上不等于「撤回」
sagaEngine.execute(saga, req);
```

**怎么用**：填的是「step 的顺序」与「每个 compensation 的语义」两处；**`sendNotification` 的补偿不可照抄**——发出去的短信撤不回来，它只能排到最后并把残余失败交给对账，写成 `cancel()` 只是把不一致挪了个位置。每个 `compensation` 都要能被独立重试且幂等，这条不满足就不算写完了这一步。

**模板 B：Outbox 表与中继（同事务写库 + 事件）**

```sql
-- DDL：outbox 表必须按时间分区，否则清理语句会锁表
CREATE TABLE outbox (
  id           UUID        NOT NULL DEFAULT gen_random_uuid(),
  aggregate_id TEXT        NOT NULL,          -- 幂等键的一部分
  topic        TEXT        NOT NULL,
  payload      JSONB       NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  published_at TIMESTAMPTZ,                   -- NULL = 未投递
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- 业务写入与事件写入在同一事务（完整写法见 §4.2「Outbox 模式」）
BEGIN;
  INSERT INTO orders(order_id, user_id, status, amount) VALUES (:id, :uid, 'CREATED', :amt);
  INSERT INTO outbox(aggregate_id, topic, payload) VALUES (:id, 'order.created', :json);
COMMIT;
```

**怎么用**：填分区粒度与保留天数两格（保留期决定峰值容量 = 速率 × 保留时长）；中继侧「投递成功但标记失败 → 重投」是必然发生的，所以**消费端幂等键不能省**，这一格不要照抄成「消费端按 id 去重即可」——重复投递的正是同一个 `id`，去重表必须覆盖乱序窗口。

**模板 C：事务边界与幂等检查清单（一页评审用）**

```markdown
# 链路：<链路名>   评审日期：<日期>

| 步骤 | 参与方 | 可逆? | 补偿怎么写 | 幂等键 | 失败后谁兜底 |
| --- | --- | --- | --- | --- | --- |

- 协调者是谁：<组件 / 框架 / 数据库内核>
- 协调者崩溃后由谁恢复：<自动 / 人工 / 待定>
- 本链路的陈旧窗口承诺：<写后多久可见>
- 不可检测的不一致：<有哪些，为什么>
- 对账任务与差异挂账流程：<任务名 / 责任人>
```

**怎么用**：重点填「可逆?」「补偿怎么写」与「不可检测的不一致」三列；前两列填不出来的步骤必须移出链路或压到链尾，第三列填不出来说明这条链路目前无法证明自己在收敛。

**模板 D：Raft 关键状态（评审时用，不是可直接运行的实现）**

```text
  角色：Follower → Candidate → Leader（心跳超时触发竞选）
  选举：term 单调递增；只有含最新日志的节点能当选
  复制：Leader 追加日志 → 多数派持久化 → 提升 commit_index
  安全：只有 Leader 能推进 commit_index；提交点在多数派持久化之后
  ─────────────────────────────────────────────
  评审三问：
    ① 提交点在哪个副本上？        ② 少数派被隔离后能写吗？
    ③ 老 Leader 恢复后会不会覆盖已提交日志？
```

**怎么用**：三个问题答不出来，就不要自研共识，直接用 etcd 一类现成实现——自研的代价不在写对，而在证明脑裂与丢决议不会发生。

### 4.6 成本：这套东西的账单

三项里真正贵的不在硬件——先说结构。

**云账单与硬件由两条协议机制决定，而不是由数据量决定**：一是**持锁时长**，跨地域多活时它由 `2 × RTT` 决定，RTT 抬高一个量级就把锁持有一并抬高（§3.6 第二行），同一套 2PC 从同城可用变成不可用；二是**参与者数量**，尾部概率按参与者数放大，协调者恢复面同步扩大（§3.6 第三行）。共识副本的复制流量可直接估：`出向流量 ≈ 写入速率 × 单条大小 × (副本数 − 1)`。取写入 200 条/秒、单条 1 KB、3 副本【经验，参数随负载变】，约 400 KB/s ≈ 34 GB/天【推算，上式的直接代入】；副本若跨地域，这份流量按跨区出网计价，单价以所选云厂商出网定价页当前版本为准【经验，随云厂商与地域变】。硬件侧另有一项固定开销：共识集群要奇数节点、要 fsync 磁盘，随集群数放大（4.3）。

**人力才是大头，且它是持续值**：补偿链路（每段一个补偿）、对账任务，以及双轨期「双份组件 + 全链路对账 + 双份值班」三笔（4.4 ③）。它贵在这里的机制是——**补偿与对账只在出事时被消费，却要在平时维持可用**：4.4 ④ 说「没有发生过补偿的双轨期不能证明补偿链路可用」，等价地说，这笔人力不能按「是否用到」来摊。

TCC 把冲突从数据库层搬到业务层、并因此抬高并发上限，代价是每个参与方从 1 个接口变 3 个（4.2 已给 12–36 人日的量级）——这正是「一致性成本与参与者数同向、与数据量无关」的一个具体形态。通用的容量与成本方法论见 [11-cross-cutting/03-data-cost-finops](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)。

### 4.7 容灾与故障演练

本主题的容灾与纯算法主题不同：**跨地域容灾在这里成立**——强一致数据必须在一个跨区仍在的提交点上定下来（§3.2.1），最终一致数据要能给出滞后量。通用多活拓扑与备份策略见 [12-architecture/07-disaster-recovery](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)，本节只列本主题特有的失效形态与恢复目标。

| 失效模式 | 影响面 | 降级策略 | 恢复目标 |
| --- | --- | --- | --- |
| 分区发生时两侧各自推进（Step 5 未定义分区行为） | 两个分区做出相反决定，合并时冲突 | 在 Runbook 里把「拒绝写 / 接受写」显式写死，一侧拒绝 | 强一致链路 RPO = 0【经验，提交点在多数派】；最终一致 RPO = 滞后量（副本落后 / 中继积压）【经验】 |
| 2PC 协调者崩溃、悬挂事务 | 资源被长期锁定，事务状态不明 | 由协调者恢复扫描或人工队列清理悬挂事务 | RTO 天级（人工）→ 小时级（自动恢复）【经验】 |
| Saga 编排器 / Outbox 中继停止 | 链路停在中间态，事件积压 | 中继重启重投 + 消费端幂等挡重复；编排器按状态表恢复 | RTO 小时级【经验】，取决于中继积压量 |
| 非确定组件（模型）进重放路径 | 副本算出不同状态却无节点报错 | 把模型输出先落为记录再复制（4.2） | 无自动恢复，需回到「模型不入重放路径」的结构 |

演练只做四件：停协调者（看是否确定性拒绝而非超时）、造分区（看两侧是否各自推进）、造并发写（看冲突是否留痕）、停中继（看积压有无指标）。四件的判据都是「有无记录」，不是「系统没崩」。混沌方法论见 [12-architecture/06-chaos-engineering](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)。

### 4.8 演进路线：0 → 1 → 100

**0 → 1（最小可用）**：单库 ACID 事务，几百 TPS 量级，补上幂等键与去重表（4.4 ① 的可回退起点）。这一阶段变贵的是**从「原子性免费」到「按写入者计费」的转折**：只要同一实体出现第二个写入者（新 Region、离线重放、人工修数），免费就结束；先坏的是**静默丢更新**——LWW 或无版本号 upsert 在冲突时不报错、不留记录（4.4 ② 第三类），只有日终对账才发现「账对不平但说不清哪一笔」。

**1 → 100（规模化）**：分库分表、服务数上升，再到跨地域。触发 §3.6 的前三条跃迁。这一阶段变贵的是**持锁时长与参与者数**（4.6 的两条机制）；先坏的是**协调者恢复面**：3 → 10+ 服务后尾部概率按参与者数放大，协调者崩溃后的悬挂事务清理从「人处理」变成「没人知道该处理什么」。此时应把 Saga 按可逆性分段、不可逆步骤压到链尾（4.5 模板 A）。

**100 →（下一道坎）**：需要审计回溯（Event Sourcing + CQRS）与「人写 → Agent 写」。变贵的是**读侧全部改写**与**事件 schema 成为长期契约**——§3.6 把这条跃迁的迁移成本列为最高档（表级 → 审计与回溯）；先坏的是**状态窗口**：Agent 写把状态窗口从毫秒级拉到秒级，进程崩溃后无从判断某一步是否执行过，非确定组件一旦进了重放路径，副本不一致却无节点报错（4.2 Raft 条目）。此阶段的前置条件是 Agent 状态可序列化、不可序列化部分拆到动作日志（§3.6 末行）。更远方向见 [§5 前沿演进](08-data-consistency-section-5-ai.md)。

### 4.9 自检清单

- [ ] 每一个跨服务写操作，是否都能说清**协调者是谁**，以及它崩溃后由谁恢复（自动还是人工）？
- [ ] 事务参与者的数量分布是多少？整笔事务的 P99 由哪个参与者决定——这个数是算出来的还是估计的？
- [ ] 每个参与方持有的锁（或业务预留）最长持有多久？这个数是从代码里读出来的吗？
- [ ] 搜一遍更新语句里有没有带版本条件：同一实体的并发写靠版本判定还是靠「后写覆盖」？后者在冲突时会不会留下任何记录？
- [ ] 同一条业务请求重复到达时会发生什么？幂等键是什么、去重窗口覆盖多长、是否覆盖乱序窗口？
- [ ] 是否存在**逆操作写不出来**的步骤？它们是否都在链路最末尾（或已被移出链路）？
- [ ] 读侧能否回答「我现在读到的是哪个位点 / 落后多少」？答不出来就无法给出任何新鲜度承诺。
- [ ] 若用了 Outbox：中继的积压延迟有指标吗？表是否按时间分区？清理任务会不会影响在线写入？
- [ ] 若用了 Saga：迁移期内真的发生过一次补偿失败吗？它被对账接住了吗？
- [ ] 若用了 Event Sourcing：事件 schema 的兼容策略是什么？「删除类」合规请求怎么满足？
- [ ] 分区演练与协调者故障演练做过了吗？结论写进 Runbook 了吗？设计说「拒绝写」时，观察到的是确定性拒绝还是超时？
- [ ] AI 链路上有没有非确定组件出现在重放路径上？模型输出是否已落为记录再复制？Agent 状态是否可序列化？

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **Step 2——先数清「同一实体有几个写入者」与「哪些步骤不可补偿」**。这两条不是评价标准，而是候选集合的筛子：写集相交时，最终一致必然以静默丢更新的形式失效；存在不可补偿步骤时，补偿型方案的正确性上限就被写死了。其余步骤（选型、实现、演练）都建立在这两条答案之上。
>
> 按这条约束，本主题下的验收判据只有三个可重现的动作：重复投递看有没有第二次副作用；并发写看冲突有没有留下记录；停掉协调者看行为是否与设计一致。三个动作都做过，才算把一致性装进了存量系统。
>
> 💡 **思考锚点**：挑你们最要紧的一条跨服务写链路，把 4.10 的三个验收动作各做一遍：重复投递一次，有没有第二次副作用（幂等键的去重窗口覆盖乱序窗口了吗）？造一次并发写，冲突有没有留下记录，还是后写静默覆盖？停掉协调者，观察到的是确定性拒绝还是超时？三件里有一件你当场答不出，说明 Step 2 那份「同一实体有几个写入者」的答案还没落到这条链路上。
