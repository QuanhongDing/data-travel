## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

数据一致性的技术底座在 AI 之前就已定型：CAP / PACELC 划定了权衡空间（§2.2），Paxos / Raft 给出了共识的构造方法，2PC / TCC / Saga / Outbox 的代价结构已在 §7.4 逐项摊开。因此本节要问的不是「这些协议过时了吗」，而是一个更窄的问题：

- **AI 让哪个对象需要新的一致性保证**——例如向量索引、Agent 状态，它们在传统系统里不存在对应概念；
- **AI 让哪一侧的负载分布变了**——例如写入方从人换成 Agent、查询从短事务换成秒级长窗口；
- **协议本身的前提有没有被改动**——这一条最容易被跳过，但它的答案直接决定了上面两条的重要性。

趋势清单之所以会误导读者排路线图，是因为它没有时间维度：把「已 GA 且有人在生产用」的东西，和「路线图里的一句话」并列写在同一个 bullet 列表里，读者从中读不出「下周能不能开工」。第二个问题是**同一个方向内部还有成熟度差异**——「向量检索一致性」这一个条目里，「索引最终一致」是可用的工程事实，而「CRDT 向量索引」在公开实践中看不到生产案例，两者被写在一起时，读者多半会按前者去规划、按后者去承诺。

本节用 L1 / L2 / L3 三级区分，判据取可核验的三条：**有正式 release note、有第三方（非厂商）公开生产案例、接口稳定**——三条全中才是 L1；只有厂商自有案例、或只在小规模被验证过是 L2；只有论文 / 路线图 / 演示是 L3。「感觉成熟」不算判据，因为它无法在评审会上被复核。在评审里用这张表的正确方式是：**先看"现在该做什么"那一列，再回头看级别**——级别只是结论的缩写，行动才是可执行的部分。

为什么判据里要专门写上「**第三方（非厂商）**公开生产案例」这一条？因为在一致性这个主题上，厂商自称与可验证能力之间的差距是结构性的：一致性能力没有"看起来能用"这一档——它要么在分区、崩溃、重试这些异常路径上成立，要么就是没成立，而这些路径恰好是 benchmark 与演示不会覆盖的。一个只有厂商自有案例的能力，最常见的真相是"在厂商自己的负载形态下成立"，而负载形态正是决定一致性方案成败的变量（§7.3.2 的"持锁时长由最慢参与者决定"、§7.3.3 的"谁给事件一个全序"都是同一个道理）。所以本节的判据不是在挑刺，而是在承认一件事：**这个主题的证据成本天然比别人高**，因此宁可把级别压低，也不把未经验证的能力写进读者的路线图。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| Agent 状态放进共识存储（状态机复制 / Raft） | L1 | 共识实现已 GA 且接口稳定，第三方生产案例广泛；变的是写入方不是协议 | 可排进路线图：先把状态迁进现成存储，不要自研协议 |
| Prompt 缓存（含以知识库版本号作 key） | L1 | 已在多家推理服务上 GA，接口稳定，有第三方生产用量 | 可排进路线图，但要把它记成成本机制（见下段） |
| Agent Checkpoint（定期快照 + 恢复回放） | L2 | 机制成熟但「Agent 状态」的可序列化边界（工具调用副作用）尚无稳定约定 | 可做 PoC；关键是先拆开「状态」与「副作用」 |
| Actor 模型（单 Actor 串行处理消息） | L2 | 模型成熟，但它只把并发收敛到消息队列，重复投递与乱序仍需幂等键（§2.1） | 作为局部约束使用，不当作一致性方案 |
| RAG 一致性（知识库 → Embedding → 向量索引 → Prompt 缓存失效） | L2 | 版本化 key 是可落地的工程做法，但无标准化、各家向量库语义不一 | PoC：先把版本号打通，再谈保证 |
| 向量索引跨 Region 异步同步 | L2 | 生产者侧能力已有，跨 Region 同步多为厂商自有案例 | 只做 PoC，不要把「可复现」写进对外承诺 |
| 向量索引 CRDT（自动冲突解决） | L3 | 无公开生产案例；且要求索引结构本身支持合并算子 | 记录，不要在架构里预留假设 |
| 推理结果一致性（temperature = 0 → 相同输入 = 相同输出） | L2（语义稳定）/ L3（逐 token 复现） | 贪心解码只消除采样这一个随机源（5.5 第 1 条）；逐 token 复现写不出任何 release note 的承诺（→L3）；语义稳定只能靠自建评测集小规模验证、无第三方公开生产案例（→L2） | 不要把它当成一致性能力来规划 |
| 边缘一致性（边缘与云端协同一致） | L2 | 机制与既有的因果一致 / 读己之写同源（§1.1），用既有手段即可实现 | 用向量时钟 / 幂等键等既有手段处理，不必等新协议 |
| AI 异常检测（检测一致性异常） | L2 | 可与既有可观测指标结合，已有小规模验证 | PoC：只做检测与告警，接人工流程 |
| AI 决策 CAP（按业务自动选择 CAP） | L3 | CAP / PACELC 是理论权衡模型，不是运行时可调旋钮 | 不要在架构里假设它存在 |
| AI 自动修复不一致 | L3 | 无公开生产案例；把写权限交给不确定组件与共识前提冲突 | 明确不做（见 5.7） |
| 跨链一致性（跨区块链的一致） | L3 | 缺全局可信定序者，与分布式数据库的跨源事务不是同一个问题 | 记录；不要在架构里预留 |
| Self-Consistent AI（AI 系统自一致性） | L3 | 无标准定义、无公开评测方法 | 记录；不要写进架构假设 |

表里有两个 L1，但只有一个是**一致性方向**：把 Agent 状态放进共识存储。Prompt 缓存出现在这张表里，但**它其实是一个成本机制，不提供任何一致性语义**：缓存命中与不命中的输出是否一致，取决于缓存实现与 key 的设计，而不取决于一致性模型。把它当一致性能力来规划，是本主题下最常见的误读。而那个真正的 L1，其成熟度也不来自 AI：Raft 一类的状态机复制在 AI 之前就是 GA 的，AI 只是给它换了一个写入方。

| 条目 | 本节落点 | 归级 |
| --- | --- | --- |
| RAG 一致性（链路段与三条策略） | 5.2.1（可见性）、5.2.3（版本与失效）；GraphRAG 在本主题下没有独立的一致性机制，其一致性需求与向量索引同源 | L2 |

### 5.2 演进方向逐条拆解（核心节）

四个方向在 5.1 的级别里重新归类；其中「RAG 一致性」在机制上不是独立方向，而是「向量索引可见性」与「版本化」这两个既有问题的具体形态。每条都写全「旧做法卡点 → 机制改变 → 得到 → 付出 → 证据 → 成熟度」六项，**只要有一项写不出来，就说明这个方向还没有资格被写进路线图**。

这六项里最容易被跳过、也最该被追问的是第四项（付出）。一个演进方向的"得到"通常是显性的（更快、更省、更自动），而"付出"往往是隐性的：确定性下降、可解释性下降、多出一个成本项、多出一类故障模式、被某个实现绑定。本节对四条方向都给了具体的代价项——如果某份材料里只有收益没有代价，那不是这个方向没有代价，而是写材料的人还没踩到。

先给一张对照表，免得四条读完后仍然分不清哪些是"真变化"：

| 方向 | AI 改变的机制类型 | 一句话判断 |
| --- | --- | --- |
| 5.2.1 向量索引一致性 | 改变了写入路径的**成本结构**（多出一个可失败的异步阶段） | 是新对象，但是旧问题（可见性 vs 时间差） |
| 5.2.2 Agent 状态一致性 | 改变了**写入方与写入节奏**，协议前提不变 | 既有载体换新位置，不是新机制 |
| 5.2.3 推理结果一致性 | 引入链路上**唯一一个非确定组件** | 唯一真正新增的技术约束，且它是负面的 |
| 5.2.4 AI 辅助一致性决策 | 只有异常检测是「人工判断换成统计判断」；另两项是**重新包装** | 一个真机制 + 两个口号 |

#### 5.2.1 向量索引的一致性：跨 Region 异步同步与 CRDT 两条路线

```text
知识库写入 → [原文落库] → [Embedding 调用] → [向量索引构建] → 检索可见
                 ↑ 任一环节滞后，读侧看到的都只是「查不到」
读侧能观测到的只有：命中 / 未命中
  → 无法区分「这条数据确实不存在」与「这条数据还没建好索引」
判定方法：写入时生成一个业务可见的版本戳，检索结果把它带回来，
          读侧就能自查「我读到的是不是至少包含我写的那一版」
```

- **旧做法与它的卡点**：向量库在既有架构里被当成「索引」用，一致性需求被默认成「最终一致就行」（§1.1：最终一致保证最终能看到最新写入，但**没有时间保证**）。
  - 卡点一（可观测性）：调用方**无法区分两种"没结果"**——数据确实不存在，还是索引还没建好。这个歧义在 RAG 里会被放大成错误的归因：运维看到"检索不到刚上传的文档"，先查数据、查权限、查分片，而真因常常是索引构建还在队列里。
  - 卡点二（形态）：向量写入不是一个动作，而是一串流水线，其中 Embedding 是一次外部模型调用，可失败、耗时不可控。传统"写一行"的幂等模型在这里不成立。
- **AI 改变了什么机制**：改变了写入路径的**成本结构**——一次逻辑写入从「写一行」变成「写一行 + 调一次模型 + 建一次索引」，多出来的每一段都可能失败、都可能被重试，**于是重试成了常态，幂等性从"锦上添花"变成必要条件**。
- **由此得到的**：因为索引可见性由一个额外的、可失败的异步阶段决定，**所以「读己之写」（§1.1 第五条）在向量检索里必须被显式声明成会话级保证，而不能当作默认行为**。
  - 同一会话写入后立刻检索，要么把请求串行化到索引可见，要么显式等待索引构建完成事件；
  - 跨 Region 异步同步把这件事从"会话内"升级为"Region 间"，读侧要先明确自己读的是哪个 Region 的视图，再谈一致性。
  - 换算成 RAG 链路的措辞：三条策略里，「最终一致」解决的是可见性延迟，「版本标签」解决的是"读到哪一版"，「缓存失效」解决的是"别复用旧结果"——**三条合起来仍然不回答"写完之后多久能读到"**，那个问题只有显式的会话级等待策略（读己之写）能回答。
- **由此付出的**：代价是检索结果**天然不可复现**，而这不是数据出错、是机制使然——同一查询在索引构建前后得到不同结果。
  - 要做 A/B 评测、要对账、要给监管解释"当时为什么没检索到"，就必须把「索引版本」固定下来并让结果带上它。
  - 第二个代价来自 CRDT 这条路线：CRDT 用「无冲突复制数据类型」的合并语义自动收敛冲突（§2.3 的冲突解决），但它要求索引结构本身支持可交换的合并算子——**这正是它停在 L3 的原因：合并语义对倒排索引、HNSW 图这类结构并不自然成立**，"两个索引合并成一个索引"和"两个计数器合并成一个计数器"难度不在一个层面。
  - 第三个代价是**验收方式要改**：既然结果不可复现，"同一查询两次结果一致"就不能当验收标准，取而代之的是"固定版本下同一次构建的两次检索一致"——这要求测试环境能固定索引版本，而很多团队的测试环境恰恰是随写入流动的。
- **证据与来源**：【公开】CRDT 的形式化定义见 Shapiro 等 *Conflict-free Replicated Data Types*（SSS, 2011），其中"合并函数必须可交换、可结合、幂等"是它成立的前提。
  - **判定方法**：向量库是否支持「读取一致性级别」这类参数，去它官方文档里查该参数是**读侧生效**（读时最多等待到什么程度）还是**写侧生效**（写入何时对外可见）——写侧生效的参数无法让读侧知道自己读到的是哪一版，也就无法支撑「读己之写」。
- **成熟度**：L2——能力可用、语义无标准化；跨 Region 与 CRDT 两条路线都缺第三方公开生产案例。

#### 5.2.2 Agent 状态一致性：把不确定的组件放进确定性的协议里

- **旧做法与它的卡点**：没有专用机制时，Agent 状态就是进程内内存（§3.3 反模式 5 的症状）。卡点不是性能而是**恢复**：一次工具调用已经成功、进程随后崩溃，重启后 Agent 无从判断这一步到底做没做，于是重复下单、重复发信。
  - 三个手段——Checkpoint、状态机复制、Actor 模型——看起来是"三个可选方案"，其实是**三个不同卡点各自的对策**，混在一起选就会选错（见下表的第二列）。
  - 一个常被忽略的前提是：卡点之所以叫"恢复"而不是"一致性"，是因为单进程内并不存在多副本不一致问题；一旦 Agent 被部署成多副本（为吞吐、为容灾），"两个副本各自推进到不同步骤"才成为真正的一致性问题——这也解释了为什么它在 Agent 规模化之后才变得突出。
- **AI 改变了什么机制**：把状态的**写入方**从人换成了 Agent，并把「持有状态的时间窗」拉长了。
  - 一次 LLM 调用的耗时在秒级（【经验】），而不是数据库事务的毫秒级；状态在途期间被并发修改、被重试、被另一个 Agent 分支读到的概率随之上升。
  - 请特别注意：被改变的只是**负载分布**，协议的前提（需要定序、需要幂等、需要可重放）一条都没变。这就是为什么本方向能用 AI 之前就 GA 的实现直接落地。
- **由此得到的**：因为状态窗口变长、写入方又不确定，**所以「把状态放进一个有定序能力的共识存储、由它复制到各副本」比自己写协调逻辑更划算**。
  - 定序这件事有现成的、接口稳定的 GA 实现；自研协调的失败模式（脑裂、丢决议、决议不一致）代价极高，且这些失败模式在 AI 之前就已被完整研究过（§2.3 的一致性协议）。
- **由此付出的**：代价很具体：**它逼迫你把状态序列化成可重放的形态，而 Agent 状态里有相当一部分根本不可序列化**（外部系统句柄、已发生但未落库的副作用、只在模型上下文里的中间态）。
  - 唯一的出路是把「动作日志」与「可合并的状态」拆开：日志进共识存储，副作用本身用幂等键（§2.1）吸收重复。
  - 第二个代价是往返次数——若每次状态变更都写共识存储，共识的 RTT 会按 token 流水的节奏被放大，因此实践中必须按「可重放的最小单位」而非「每次变更」做快照。
  - 第三个代价是**恢复语义的新义务**：一旦能恢复，就必须回答"恢复到哪一点、之后已发生的副作用怎么处理"——这是纯内存方案从不需要回答的问题。
  - 还有一个组织层面的代价：状态放进共识存储后，"状态 schema"就变成了一份对外契约，改字段要像改表结构一样走评审与兼容性检查；而 prompt 与状态结构通常改得很频繁，两边的节奏必须对齐，否则会出现"框架升级一次、下游恢复逻辑全部失效"。
- **证据与来源**：【公开】Raft 见 Ongaro & Ousterhout, *In Search of an Understandable Consensus Algorithm*（USENIX ATC, 2014）。
  - **判定方法**：查你所用 Agent 框架的文档里状态后端是否可插拔、checkpoint 的序列化边界有没有写清楚——写不清边界的框架，其恢复只能是"尽力而为"。
- **成熟度**：状态机复制 L1（协议已 GA、第三方生产案例广泛）；Checkpoint 与 Actor 模型 L2（机制成熟，但 Agent 状态 schema 仍在变，恢复语义无统一约定）。

| 手段 | 它真正解决的卡点 | 它**不**解决什么 |
| --- | --- | --- |
| Checkpoint（快照 + 恢复回放） | 恢复点从哪来、恢复到哪一刻 | 副作用是否已发生——回放会把它再执行一次，仍需幂等键 |
| 状态机复制（Raft 一类） | 谁来定序、多个副本怎么看到同一顺序 | 状态本身是否可序列化；不可序列化的部分仍要单独设计 |
| Actor（单 Actor 串行处理消息） | 本地并发（同一时刻只有一个处理者） | 消息重复投递与乱序——它们来自消息系统，不来自 actor 内并发 |

#### 5.2.3 推理结果一致性：确定性是共识的前提，不是模型的属性

```text
一次检索结果由四个版本共同决定（乘法关系，不是加法）：
    知识库版本 × Embedding 模型版本 × 向量索引版本 × Prompt 缓存 key
只有固定其中三个、一次只动一个，A/B 与回归才有可比性
  → 「RAG 一致性」三条策略（最终一致 / 版本标签 / 缓存失效）真正的落点：
     它们管的是「读到哪一版」，都不管「两次调用是否给同一答案」
```

- **旧做法与它的卡点**：确定性假设来自数据库——同样的输入 + 同样的版本 = 同样的输出。RAG 链路把这个假设原封不动地带进了 LLM：知识库更新 → Embedding 重新生成 → 向量索引更新 → Prompt 缓存失效，整条链上每一段都被当作"可重放的函数"来处理。
  - 卡点在于：**这条链上有一段不是函数**。
  - 派生卡点：于是"用缓存以降低成本"和"用缓存以保证一致"被混为一谈——缓存能降低重复计算的成本，但它对"两次调用给出不同答案"这件事完全无能为力。
- **AI 改变了什么机制**：把链路上**唯一一个非确定组件**放了进来。temperature = 0 只是把采样换成贪心解码，它消除的是「采样随机性」这一个随机源，而不是全部（见 5.5 第 1 条）。机制上的改变可以一句话说清：**链路的其他环节都满足"输入相同则输出相同"，只有模型这一段不满足。**
- **由此得到的**：因为共识协议要求状态机确定性——同一份日志在每个副本上必须重放出同一个状态——**所以任何"让每个副本各自再调一次模型"的设计都会破坏协议前提；正确的位置是把模型输出当作外部输入记入日志**。
  - 写进日志的是那一次的输出本身，副本重放的是这条记录，而不是重算。
  - 这与分布式系统里"把非确定的外部调用结果先记录下来再复制"的既有做法是同一件事，只是外部调用从"取当前时间"换成了"调一次模型"。因此这个方向**不需要新协议，只需要正确的落点**。
- **由此付出的**：代价是 token 成本与日志体积——把模型输出当数据存下来，存储与传输成本按输出长度线性增长，日志里也会沉淀大量不可压缩的自然语言（对下游的压缩、归档、审计检索都是新负担）。换来的是可重放、可审计、可对比。
  - 第二个代价是**版本爆炸**：上图四个版本各自独立演进，组合数是乘法关系，因此"我们能复现昨天的结果"这句话必须附带"在哪四个版本上复现"，否则无法验证。
  - 第三个代价是**度量口径随之改变**：把模型输出当数据存下来之后，"这个回答好不好"就变成对历史记录的离线评估，而离线评估与在线效果的差距需要流量来验证——这也是本节对"效果提升多少"一类问题只给信号、不给数字的原因：这里不存在稳定可复现的度量口径。
- **证据与来源**：无公开可核验来源支持「temperature = 0 即逐 token 可复现」，本节的判断按【经验】档给出。
  - 一个可自行核验的旁证：**任何声称能逐 token 复现的系统，都会显式写明它固定了哪些非确定来源**（组批方式、算子实现、随机种子）。只写 temperature = 0、没有这串限定语的说明，通常并没有解决这个问题。
  - **判定方法**：同一 prompt 固定 temperature = 0 连发多次，比对完整 token 序列；再把并发（batch 组成）固定后重复一次，两次结果不同即说明确定性不成立。
  - 至于"把外部调用结果记入日志"这一做法，本身是分布式系统的既有实践，不依赖本节的判断。
- **成熟度**：「模型输出作为外部输入记录」属 L1（既有做法、接口稳定）；「语义稳定」（同一问题给出等价答案）属 L2（只能在自己的评测集上小规模验证，没有第三方公开生产案例）；「相同输入 = 相同输出」作为对外承诺属 L3。

#### 5.2.4 AI 辅助一致性决策：为什么模型只能待在旁路

- **旧做法与它的卡点**：CAP / PACELC 的权衡由人来做，落地形态是 §4.1 阶段 1 的「业务分级」——按业务把数据分成强一致、最终一致几档，再按档选协议（§7.2 的四个族）。
  - 卡点一：分级是**静态**的，一旦定下就与运行时的真实冲突率脱节。
  - 卡点二：分级做错的成本是双向的（选了强一致，代价是可用性与延迟；选了最终一致，代价是正确性，而正确性问题没有折扣，见 §7.1）。
- **AI 改变了什么机制**：只在一支上真正改变了机制——**异常检测**把「人按经验定的阈值告警」换成「从运行数据里学的统计判断」。
  - 至于「AI 决策 CAP」与「AI 自动修复」，机制上并没有新东西：前者把一个理论权衡模型当成了运行时可调旋钮，后者把写权限交给了一个不确定组件。
- **由此得到的**：因为不一致本身是**可观测的**，**所以「检测」可以由统计模型承担，而且它比固定阈值更能容忍负载形态变化**。可用的观测面包括：
  - 副本落后的版本数（复制延迟）；
  - Saga 补偿的失败率（§2.3）；
  - Outbox 中继的积压延迟（§4.2）；
  - 幂等键的命中率（命中率高说明重复投递多，是需要处理的信号而不是故障）；
  - Quorum（NWR 策略，§2.2）的读写失败率。
  - 同一条阈值在峰值流量下与日常流量下的含义完全不同，而统计模型学的是分布，不是那个数。
  - 这些指标都不是新造的：它们直接取自既有组件的运行状态（§4.2 的 Outbox 中继、§2.2 的 Quorum 读写、§2.1 的幂等键），而 §4.1 阶段 4 的演练验证针对的也正是这几类组件的失败；因此"检测"这条路的接入成本主要花在标注与误报调优上，而不是花在建设上。
- **由此付出的**：检测器本身是一个非确定组件，它会**误报**——把正常的最终一致窗口判成不一致。
  - 误报的代价不是"多看一眼"，而是触发一次不必要的修复动作（重投、补偿、强制同步），而修复动作本身有真实的副作用成本。
  - 一旦把修复也交给模型，就等于让一个不保证确定性的组件拥有写权限，这与 5.2.3 里那条前提（状态机必须确定）正面冲突。所以这条路线的上限是明确的：**模型出建议，修复动作落回确定性的补偿逻辑（Saga 补偿 / Outbox 重投 / 幂等重试）**。
  - 第三个代价是**归因**：告警由模型给出时，"为什么它认为这里不一致"常常无法还原成一条可复核的规则；而一致性事故的复盘恰恰要求可复核。这是检测类能力必须配套"可解释输出"的原因，否则它在事故流程里走不完第一步。
- **证据与来源**：无公开可核验来源支持「AI 自动决策 CAP」或「AI 自动修复不一致」已在生产落地，两条按 L3 处理。
  - 异常检测有同类做法（以既有可观测指标为输入的异常检测）可参考，属 L2；但本节找不到该主题下的第三方公开生产案例，故不升为 L1。
- **成熟度**：异常检测 L2；自动决策 CAP 与自动修复 L3。

### 5.3 与本主题既有栈的接口在哪

不要写「与 AI 结合」这类句子，要写清**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。下表的"现状"一列指的是该接口形态在公开实践中的成熟度，不是某一家厂商的能力。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Agent 状态 ↔ 共识存储 | 状态与动作日志写入同一份复制的 KV / 日志；副本只重放日志，不重算 | 共识层负责定序与持久化；应用负责幂等键 | 生产（Raft 类存储已 GA） |
| 模型输出 ↔ 状态机 | 模型输出作为**外部输入记录**写入日志（副本不重新调用模型） | 记录方；副本不承担重算义务 | 生产做法（确定性重放） |
| 向量检索 ↔ 知识库写入 | 写路径与读路径分离，中间是「索引构建完成」事件 | 应用负责等待或幂等重试；索引层不承诺可见时间 | 试点 |
| Prompt 缓存 ↔ 知识库版本 | 缓存 key 内嵌知识库 / Embedding / 索引版本号 | 应用负责失效；缓存层只保证"相同 key 相同值" | 生产（缓存本身 GA） |
| Outbox / CDC ↔ 下游消费（§4.2） | 本地事务写业务表与事件表，中继读出投递 | 消费端用幂等键去重 | 生产 |

读这张表的方法：**第一行与第二行才是"新"的**——它们把 Agent 状态搬到了一个本就存在的一致性载体上，并把模型输出降级成一条普通日志。其余三行都是既有机制换了个写入方或读方。

边界上要问清的三件事，缺任何一件，这个接口就不能算定义完了：

- **谁调用谁**：是应用直接写共识存储，还是经过一层状态服务？决定了将来换存储的迁移成本。
- **数据以什么形态穿过边界**：是结构化状态，还是"日志条目 + 序列化 blob"？决定了副本能不能只重放、不重算。
- **失败时谁负责**：写入失败时，是应用重试、还是存储层保证？决定了幂等键必须落在哪一侧。

一个实用的判断标准是——如果一处改动让「副本之间需要重新协商谁来决定顺序」，那是架构变化；如果只是让既有机制多了一个调用方，那只是接口变化。本节里的五个结合点，**没有任何一个属于前者**。

把边界上的失败按类型拆开，就能看清责任落在哪一侧：

| 失败类型 | 落在哪一侧 | 对架构的直接影响 |
| --- | --- | --- |
| 写入失败（共识存储不可用） | 存储层返回确定性错误，应用重试 | 幂等键必须存在，否则重试本身会造成重复副作用 |
| 可见性失败（索引尚未构建） | 应用侧（等待，或降级返回"未就绪"） | 接口必须能表达"未就绪"这个状态，否则调用方只能靠猜 |
| 语义失败（模型输出不可重放） | 记录方（日志里没记就等于永远丢失） | 记录必须落在写入路径上，不能事后补录 |

这三行对应三种不同的返工成本：第一行是补一个键，第二行是改一次接口契约，第三行往往意味着一次链路重构——**这也是为什么"把模型输出记入日志"应当尽早做，而不是等到需要审计时再补**。

2024 年的厂商进展有 5 条（Google 2024：Spanner 跨大洲强一致升级、CockroachDB 2024：跨 Region 事务优化、TiDB 2024：HTAP + 多 Region 强一致、阿里 OceanBase 2024：AI 时代一致性增强、字节跳动 2024：自研一致性协议）。这些是**产品能力名而不是可引用的公开技术结论**，本节不替它们背书，只给判定方法：**去对应产品的 release note 或官方文档里查三件事——该能力在哪个版本进入 GA、它对外暴露的一致性语义写在哪一节、有没有第三方（非厂商）的生产案例**。三者缺一，按 L2 处理；只出现在发布会页面或路线图里的，按 L3 处理。这样做不是保守，而是因为一致性能力的"支持"与"保证"差着一条明确的线：前者意味着文档里有一个开关，后者意味着有可验证的语义定义。

### 5.5 被过度宣传的部分

**说法 1：「temperature = 0 就等于确定性输出」**

- **实际是什么**：它只把采样换成贪心解码，消除的是采样这一个随机源。推理侧还有别的非确定来源：请求被怎么组批、attention 与归约核的累加顺序、MoE 的路由选择、浮点加法不满足结合律——任何一处不同，贪心路径都可能在某个 token 上分叉，而后续 token 会把这个分叉放大成完全不同的句子。
- **为什么会这样**：这是**实现层的性质，不是模型层的保证**，因此它会随推理栈、算子实现、硬件版本而变——换个部署形态就可能复现不出昨天的输出。
- **什么时候它才会成真**：主流推理栈把"确定性模式"（固定组批、可复现的归约顺序）写进 release note 并说明开启后的吞吐代价。在那之前，正确的表述是"语义稳定"（同一问题给出等价答案），而不是"输出一致"。

**说法 2：「Agent 状态一致性可以用 CRDT / 向量时钟解决」**

- **实际是什么**：CRDT 提供的是**合并函数**，不是**执行顺序**。计数、集合、文本序列这类结构有良定义的合并；而 Agent 状态里真正会出事的部分是"有副作用的动作序列"——两次「下单」不是可以合并成一次的量。向量时钟同理，它能**检测**冲突（§2.3），但检测出来之后"该保留哪一个"仍然要人来定。
- **为什么会这样**：CRDT 与向量时钟的数学保证建立在"操作之间的序关系可判定"上，而副作用的交换性根本不成立——合并的前提在这里就断了。
- **什么时候它才会成真**：当 Agent 状态被显式拆成「可合并的状态字段」与「必须定序的动作日志」两部分，CRDT 才有位置——此时它管的是前者，后者仍然要共识存储。判定方法：看你的状态字段里有没有任何一个字段的"合并"在业务上需要解释——需要解释的，就不该交给 CRDT。

**说法 3：「AI 自动决策 CAP、自动修复不一致」**

- **实际是什么**：CAP / PACELC 是对权衡空间的描述，不是一组可以运行时切换的开关；而"自动修复"在一致性系统里等价于**给一个不保证确定性的组件以写权限**，这与共识协议要求确定性状态机（5.2.3）直接冲突。
- **为什么会这样**：一致性协议的每一处写法都在为"同一份输入必须导出同一个结果"服务；把统计模型放进这条路径，等于主动引入一个无法用日志重放的决策源——一旦出问题，复盘连"当时模型为什么这样决定"都重现不了。
- **什么时候它才会成真**：当模型的输出被固定记录成日志条目、修复动作落回确定性的补偿逻辑（Saga 补偿、Outbox 重投、幂等重试）。此时"AI 参与修复"成立——但它参与的是**提议**，不是**决定**。判定方法也很直白：问"这次的修复决定写进日志了吗、能不能重放"，答案是否定的就说明它还在 L3。

### 5.6 未来 3–5 年：可证伪的预测

预测必须写成「预测 + 会成真的信号 + 会证伪的信号」；写不出信号的预测不要写，因为它无法被检验，也就不带信息量。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 1. 到 2028 年，主流向量库都会像关系库一样提供**显式的读取一致性级别参数**，而不再只讲"最终一致" | 其官方文档出现"一致性级别"一节，并明确每个级别在读侧等待什么 | 三年内仍只有"最终一致"一种描述，可见性只能靠业务侧 sleep 或重试 |
| 2. Agent 状态会从「框架内置 checkpoint」演进为「可插拔的外部状态后端」，出现与 Agent 框架解耦的状态存储 | 某主流 Agent 框架宣布状态后端可插拔并对接外部 KV / 共识存储 | 状态长期锁死在框架自己的存储里，跨框架迁移只能靠导出文件 |
| 3. 推理服务会出现「确定性模式」（固定组批、可复现 token 序列）作为**受限特性**，但不会成为默认 | release note 里出现 batch invariance / deterministic inference 一类措辞，并附吞吐代价说明 | 两年内无任何主流推理栈提供该开关，或提供了但给不出可复现的验证方法 |
| 4. LLM 不会被放进一致性协议的决策路径（提交 / 中止 / 定序） | 落地的都是"模型出建议、确定性逻辑执行"的形态，审计记录里决策者是确定性组件 | 出现被生产采用、由模型决定提交或中止的共识协议，并给出确定性论证 |

读这四条的方法：**它们的证伪信号都比成真信号更容易观测**。这不是巧合——一致性这个主题的特点是，正确的判断几乎总是"某个新能力没有改变协议前提"，因此预测的默认值是"不变"，只有当证据明确指向改变时才需要修订。第 4 条尤其如此：它不只是预测，也是 5.2.3 那条机制的推论。

每条预测背后的依据分别是：第 1 条依据的是"可见性歧义必须有接口来表达"（5.2.1 的卡点一），只要向量检索继续被用在生产检索链路上，这个歧义就会被要求解决；第 2 条依据的是既有经验——状态一旦需要跨进程存活，它就会脱离框架（这与缓存、会话、任务队列的演化路径一致）；第 3 条依据的是"确定性有吞吐代价"（5.5 第 1 条），有代价的能力不会成为默认；第 4 条依据的是共识协议的前提（5.2.3），它是本节唯一一条**由机制推出、而不依赖趋势判断**的预测。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 单库事务尚能支撑，刚开始接 Agent | 把幂等键补到所有可重试入口（§2.1） | Agent 框架的状态后端是否可插拔 | 不要为了"AI 一致性"把 CRDT / 向量时钟引入写入路径 |
| 已有 Raft 类存储（etcd 一类） | 把 Agent 状态与 checkpoint 迁进去，先拆"状态"与"副作用" | Agent 状态 schema 是否趋稳 | 不要自研共识协议；不要指望模型替你在副本间定序 |
| RAG 已上生产 | 给知识库 / Embedding / 索引打版本号，缓存 key 带上它 | 向量库是否给出读取一致性级别 | 不要把「向量检索结果可复现」写进对外承诺 |
| 正规划跨 Region 的向量检索 | 先问是否真需要跨 Region 强一致——多数场景只需会话级「读己之写」 | 厂商跨 Region 同步能力与文档 | 不要在架构里假设"向量库天然多 Region 强一致" |
| 想上 AI 自动修复 | 先只做不一致检测与告警，结果进人工流程，统计误报率 | 误报率能否降到可接受 | 不要给模型提交 / 中止 / 补数据的权限 |

「明确不要做」这一列是本节的重点：上表五条里要避免的动作有一个共同点——**它们都试图用 AI 去替代一致性协议本身已经解决好的那一部分**，而那一部分恰恰是"必须确定"的地方。省掉这些动作，比多做几个 PoC 更能降低架构风险。

按投入排序，本主题的行动顺序是三件：**先补幂等键**（不需要任何 AI 组件，却是后面一切的前提）→ **再把状态放进有定序能力的存储**（有现成实现，收益立刻可见）→ **最后才谈版本化与缓存**（收益是成本与可复现性，不是正确性）。反过来做，就会先付出复杂度、后付不出收益。

判断某件事该不该现在做，通用口径有两条，它可以覆盖上表全部五个处境：

- 它是否依赖一个**尚未稳定的接口**？是，就等到接口稳定再做——本节里 CRDT 索引、AI 决策 CAP 都属于此类，做了也要重做。
- 它是否在修一个**现在并不存在的问题**？Agent 状态不一致在单副本、无重试、无并发的阶段根本不存在，此时引入共识存储，只会先付出一整套序列化与恢复语义的复杂度。

### 5.8 小结

> 本节小结：AI 在本主题下真正改变的**唯一那条机制**是「谁在写状态、以什么节奏写」——写入方从人换成了 Agent，状态窗口从毫秒级拉长到秒级，于是既有的一致性载体（共识存储、Outbox / CDC、幂等键）被搬到了新的位置上使用。它**没有改变**的是协议的前提：需要定序、需要幂等、需要可重放，**而可重放要求确定性——这正是 LLM 不能进入一致性决策路径的原因**。因此本主题下现在就能排进路线图的，是把 Agent 状态迁进既有的共识存储；其余（CRDT 索引、跨 Region 同步、AI 决策 CAP、自动修复）都还在观望区。
