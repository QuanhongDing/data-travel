## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表的问题不在于分数不准，而在于**它把与场景强相关的结论写成了绝对结论**。同一维度在不同规模下权重相反：当一笔事务只有 2 个参与者、都在同城同一可用区、写 TPS 只有几百时，2PC 的锁持有时间约等于 2 个 RTT（亚毫秒到 1 ms 量级，【经验】），吞吐与 Saga 没有可测差别——此时「强一致」几乎是免费的，选最终一致反而要多写一套补偿逻辑与对账。反过来，当一笔事务跨 5 个服务、其中一个参与者是第三方支付网关（P99 秒级），2PC 的锁持有时间被**最慢的那个参与者**主导，热点行上的锁等待随并发线性放大——此时「强一致」的代价是吞吐坍塌。同一张表在两个场景里应给出相反结论，打分表却只能给一个。

第二个问题是**维度不可加**。打分表把「强一致 5 分」和「性能 2 分」相加，但这两项不是可以相互折价的商品：一致性不满足是**正确性问题**（资金扣错、库存超卖），性能不满足是**体验问题**。正确性问题没有折扣，只能作为硬约束先行——先筛掉不满足正确性的候选，再在剩下的里面比成本。把两者放进同一个加权和，等于默许「用一致性换一点性能」。

第三个问题是**候选不同质**。2PC / TCC / Saga 解决的是「跨服务写入的原子性」；Outbox / CDC 解决的是「本地事务与消息发布的原子性」；Event Sourcing 解决的是「状态的可重建性」；Global DB 解决的是「把分布式问题收进单库语义」。把四类东西塞进一张表逐格打分，等于把「锤子、螺丝刀、电动螺丝刀、以及干脆用胶水」放在一起评分——它们的适用情形本就不重叠。

第四个问题是**阈值凭空来**。常见的决策树写「性能要求：高 → TCC / Saga，中 → Outbox，低 → 2PC」，但「高」是什么量？高并发？低延迟？还是高吞吐？三者对一致性的压力完全不同：低延迟要求惩罚跨 RTT 的往返（利于族 2），高吞吐要求惩罚长持锁（利于族 2 与族 3），而高并发冲突率恰好是 TCC 唯一真正回本的场景。一个没有度量的「高」，等于把决策权还给了直觉。本章的做法是：决策树的每个节点只问**可观测的事实**（参与者有几个、在不在同一个可用区、需要一起改的数据在不在同一个库、这一步可不可逆），阈值一律在树下给出推导链。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 正确性硬约束 | 不一致时业务能否自我修复（对账、退款、人工） | 不能修复＝该候选直接出局，不进入成本比较 |
| 协调点位置 | 提交决定权在应用 / 中间件 / 数据库内核哪一层 | 决定故障模型（谁负责崩溃恢复）与迁移成本上限 |
| 资源持有时长 | 从「开始改」到「确定提交」之间锁了多久 | 由 Little 定律直接决定并发上限，是性能差异的第一因 |
| 定序机制 | 谁给事件一个顺序（单点时钟 / TrueTime / HLC / 向量时钟） | 决定冲突是「可检测」还是「被静默丢弃」 |
| 可补偿性 | 每个正向步骤是否存在语义正确的逆操作 | Saga / TCC 的正确性上限，而非协议实现质量 |
| 运维与恢复能力 | 需要几个常驻组件、故障时谁能恢复决议 | 一致性方案的隐性成本几乎全部在这里 |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者（【经验】） | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 2PC / XA | 跨资源原子提交 | 协调者两阶段投票，参与者持锁直到决议落盘 | 同构数据库集群、传统中间件（JTA/XA） | 协议开放，实现绑定数据库与中间件 |
| 3PC | 2PC 的非阻塞改良 | 在 Prepare 与 Commit 之间插入 PreCommit，靠超时自动推进 | 教材与少数数据库内部实现 | 协议开放 |
| TCC | 应用层补偿事务 | 把「预留—确认—取消」三个业务操作显式写出来，资源锁由业务自己持有 | 支付、交易、账务类系统 | 实现开源（Apache Seata 等），业务代码自研 |
| Saga | 长事务拆分 | 一长串本地事务 + 失败时逆序补偿 | 电商下单、出行预订 | 开源编排引擎（Temporal、Cadence、Seata Saga） |
| Outbox | 本地事务与消息的原子性 | 业务写入与事件写入同一个本地事务，再由中继读出投递 | 事件驱动微服务 | 多数消息中间件与 ORM 生态有实现 |
| CDC | 变更捕获 | 读数据库日志（binlog / WAL）转成变更流 | 数仓实时同步、缓存刷新 | 开源（Debezium、Flink CDC），云上有托管 |
| Event Sourcing（+CQRS） | 状态即事件序列 | 只存事件不存当前状态，状态由重放得出 | 账务、审计留痕类场景 | 模式开放，无单一厂商 |
| Global DB | 把分布式收进单库 | 跨 Region 复制 + 全局时钟 + 内部共识，对应用暴露单库事务语义 | Spanner、CockroachDB、TiDB、OceanBase | 商用与开源混合 |
| 异步消息 + 幂等消费 | 最弱承诺兜底 | 只保证送达，重复与乱序由消费端幂等键吸收 | 通知、计数、日志类链路 | 通用 |

这些候选其实分四**族**：**族 1 协调型事务**（2PC / 3PC / TCC / Saga）——都需要一个「谁来决定提交」的角色；**族 2 日志与事件型**（Outbox / CDC / Event Sourcing）——不引入新协调者，靠本地事务 + 日志顺序传递事实；**族 3 数据库内核型**（Global DB）——把协调者下沉进数据库；**族 4 无协调型**（异步消息 + 幂等、以及 LWW / 向量时钟 / CRDT 这类冲突消解机制）。同族内部可以逐项替换（Outbox 换 CDC 只改中继），跨族替换要动的是业务代码与数据形态。**先分族再选，能省掉一半比较**。

### 7.3 机制差异：为什么它们表现不同

#### 7.3.1 协调点在哪一层：故障恢复的责任归谁

**机制是什么**：一致性协议总需要一个地方决定「提交还是回滚」，并保证这个决定在崩溃后不丢。这个决定权放在哪一层，决定故障模型、性能上限与迁移成本。

**实现差异**：

| 候选 | 协调者 | 决议落盘在哪 | 应用需要承担什么 |
| --- | --- | --- | --- |
| 2PC / XA | 应用侧或中间件事务管理器 | 协调者的 XA 事务日志 | 协调者高可用、恢复扫描、悬挂事务清理 |
| TCC | 业务代码（或一个状态机服务） | 业务自己的「事务状态表」 | 空回滚、悬挂、幂等三类边界 |
| Saga | 编排器（或一组事件订阅者） | 编排器的持久化状态机 | 补偿设计与重试策略 |
| Outbox | 无（本地事务即协调者） | 业务库的 outbox 表 | 中继进程与表清理 |
| Global DB | 数据库内核 | 数据库自己的日志与副本共识 | 几乎为零（写本地事务语法） |

**由此必然导出的性质**：因为 2PC 的协调者是**应用侧进程**，所以「协调者崩溃后如何恢复」这件事必须由使用者自己兜住——XA 日志要么落本地文件要么落数据库，恢复扫描要么定时任务要么启动时全扫；这套东西一旦缺失或写错，症状不是报错而是**部分参与者已提交、部分未提交**的静默不一致。反过来，因为 Global DB 把协调者放进了**数据库内核**，应用写的是本地事务语法，崩溃恢复由数据库负责——你换来的是「不用写任何分布式逻辑」，付出的是「需要一起提交的数据必须全部住在这一个数据库产品里」。

**公开证据【公开】**：Spanner 论文（OSDI 2012）把事务管理、两阶段提交与副本共识全部放进 Spanner 内部，并用 TrueTime 提供有界时钟不确定度（论文报告 ε 典型在毫秒量级、最坏约 7 ms），使外部用户看到的是单库事务；OceanBase 于 2020 年在 TPC-C 榜单登顶（TPC-C 官方结果，2020），说明单库语义可以在分布式存储上做到极致性能——但那条路径要求同一套内核；CockroachDB 1.0 于 2017 年发布（官方 Release，2017），同样把事务协调内置于存储层。你可以自行核验这条判据：打开你用的 Global DB 文档，搜索它是否把「跨节点事务」写成默认语义。

**失效条件**：Global DB 的优势在「需要一起改的数据都能放进它」时才成立。当数据散落在既有 MySQL 分片、MongoDB、对象存储上时，Global DB 只能覆盖新增写入，存量数据仍需 Outbox / CDC 缝合——此时它退化为族 2 的一个成员，而不是替代品。

**为什么 3PC 在工程里很少落地**：3PC 用「让参与者也具备超时推进能力」来消除 2PC 的阻塞，但代价是它必须额外假设**网络延迟有上界**（否则超时判定不可靠）且**不发生分区**（否则两个分区可能各自推进出相反决定）。这两个假设在真实数据中心都不成立，所以 3PC 更像教学中的过渡形态——它说明「阻塞性」的根因不是阶段数不够，而是「决定权集中在一个会崩的进程上」。

#### 7.3.2 资源持有时长：并发上限由「最慢参与者 × 参与者数」决定

**机制是什么**：协调型候选的并发上限由「事务持有资源的时间」决定。按 Little 定律，系统中平均并发持锁事务数 = 事务到达率 × 持锁时长；这个数一旦逼近热点资源的可用并发度，就开始排队。

**实现差异**：

| 候选 | 持有的是什么 | 持有时长 | 谁决定时长 |
| --- | --- | --- | --- |
| 2PC | 数据库行锁 / 表锁 | 2 × RTT + 参与者本地提交时间 | 最慢的参与者 |
| TCC | 业务资源（冻结额度、预留库存） | Try 到 Confirm/Cancel，可能跨用户操作 | 业务流程本身 |
| Saga | 不持有，但中间态对外可见 | — | 业务是否允许中间态 |
| Outbox | 仅本地事务锁 | 毫秒级 | 本地库 |
| Global DB | 数据库内部锁 | 一次 2PC + commit-wait（若有时钟不确定度） | 内核 + 时钟 |

**由此必然导出的性质**：因为 2PC 的锁一直持有到**所有**参与者回报之后才释放，所以它的 P99 由最慢的那个参与者决定，而不是由平均决定——一个参与者偶发 500 ms 的 GC 停顿会把所有并发事务一起拖慢，**这是长尾放大而不是平均值退化**。因为 TCC 把锁下沉成业务语义上的「预留」（冻结额度、占用库存），同一条记录的争抢表现为「预留失败」而不是「锁等待」，所以它能被业务降级策略吸收（排队、重试、部分成功、给用户一个确定失败）；代价是这份降级逻辑要每个参与方都写一遍。

**公开证据【公开】**：Garcia-Molina 与 Salem 的 Saga 论文（SIGMOD 1987）明确用「把长事务拆成可补偿子事务」来规避长锁，这是该模式被提出的原始动机；Google Percolator 论文（OSDI 2010）在 Bigtable 之上用 2PC + 快照隔离实现跨行事务并给出了吞吐数据，可用来核验「2PC 的成本结构」；Kafka 0.11（2017，KIP-98）引入幂等生产者与事务，把「发消息」与「提交消费位点」纳入同一原子边界——这条路线属于族 2 的思路（不引入跨系统锁，只保证边界原子性）。

**失效条件**：TCC 的预留是有成本的——如果预留后必定确认（没有取消分支），TCC 等价于多一次远程调用加一张状态表，纯亏；另外当参与者中存在**不可补偿的外部系统**（已出账到银行、已发出短信）时，Cancel 在语义上不存在，方案退化。

**长尾放大的一个直观量化**（【推算】）：设 5 个参与者，每个参与者本地处理时间的 P50 = 5 ms、单步 P99.9 = 500 ms（即单步超过 500 ms 的概率 p = 0.1%），同城 RTT = 1 ms。2PC 的完成时间 ≈ max(所有参与者)，因此整笔事务超过 500 ms 的概率 = 1 − (1 − p)^5 = 1 − 0.999^5 ≈ 0.5%。推导链是「单步尾部率 → 事务尾部率」：单步 P99.9 在 5 个参与者下被放大成**事务层面约 P99.5 的尾部事件**（尾部率 0.1% → 0.5%，放大 5 倍），而不是「单步 P99.9 变成整笔事务 P50 就带长尾的常见情形」——后者比这个推导能支撑的结论强了两个数量级。放大关系是 1 − (1 − p)^n：n 越大，事务踩到长尾的概率越高，这是「2PC 要限制参与者数量」的定量理由，不只是经验之谈。

上面这条推导有一个必须写明的前提：**各参与者的长尾相互独立**。若长尾强相关（共享 GC、共享存储、同一可用区抖动、同一批发布），事务踩到长尾的**概率**反而降到接近单步的 p——5 次独立机会塌缩成 1 次同时命中的机会；真正变强的是**严重程度**：抖动期间所有在途事务同时持锁，抖动结束后锁队列还要再排一轮，恢复时间长于抖动本身。所以两类长尾的处理方式不同：独立长尾靠「减少参与者数 + 给每个参与者设单步超时上限」压低事务尾部率，相关长尾只能靠「热点资源隔离 + 抖动预算（GC 停顿目标、存储尾延迟 SLO）」从根上掐掉——把独立长尾的概率公式套到相关长尾上，会低估影响面。

2PC 与 Saga 的差别不在尾部概率本身，而在**爆炸半径**：Saga 的慢步骤只拖慢它自己那一条链路，2PC 的慢参与者通过锁把落在同一热点行上的**全部**并发事务一起拖慢。同一份尾部概率，落在 2PC 上是一个同步出现的延迟尖峰（P99 由最慢参与者决定），落在 Saga 上只是一条链路慢——这才是「2PC 的 P99 不等于参与者 P99 的平均」的真正来源，也是它必须限制参与者数量的原因。

#### 7.3.3 定序：谁给事件一个全序

**机制是什么**：最终一致方案里，冲突消解需要一个顺序依据，顺序依据来自「谁的时间戳」。这是族 2 / 族 4 与 Global DB 差异的真正来源。

**实现差异**：

| 定序机制 | 代表 | 性质 | 代价 |
| --- | --- | --- | --- |
| 单库自增 / binlog offset | MySQL → CDC | 单库内天然全序，跨库不可比 | 只能定序到库边界 |
| 集中式 TSO | TiDB（PD 分配时间戳） | 全局可比、可线性一致 | TSO 成为关键路径与单点 |
| 有界不确定度时钟 + commit-wait | Spanner TrueTime | 全局可比且无需协调者排序 | 写延迟下限被抬到 2ε |
| 混合逻辑时钟 HLC | CockroachDB 等 | 物理时钟 + 逻辑计数，避免 commit-wait | 需处理时钟回拨与同毫秒定序 |
| 向量时钟 / 版本向量 | Amazon Dynamo（SOSP 2007） | 检测并发写而非强行定序 | 元数据大小随参与节点数增长 |
| LWW（Last-Write-Wins） | Dynamo 默认策略之一 | 实现最简单 | 静默丢更新，只在「后写必对」时成立 |
| CRDT | Shapiro 等（SSS 2011） | 数学上保证收敛，无需协调 | 只有部分数据结构可表达为 CRDT |

**由此必然导出的性质**：因为 TrueTime 给出的是**有界不确定度**而不是精确时刻，所以 Spanner 必须在提交后等到「当前时刻确实已经超过所有副本的提交时间戳」才对外可见（commit-wait），这直接把写延迟下限抬到约 2ε；反过来，因为 HLC 不承诺不确定度上界，采用它的系统不需要 commit-wait，但必须处理「同一墙钟毫秒内的两个事件如何定序」——**定序责任从时钟下推到了存储层**。因为 LWW 用一个时间戳做最终裁决，所以它在你「能保证后写必对」的场景（用户改自己的资料）之外都会静默丢数据，且丢的时候没有任何报错——这是最危险的一类不一致。

**公开证据【公开】**：TrueTime 与 commit-wait 的机制与 ε 量级见 Spanner 论文（OSDI 2012）；向量时钟与 LWW 的冲突消解见 Amazon Dynamo 论文（SOSP 2007）；CRDT 的收敛性证明见 Shapiro 等人的 Conflict-free Replicated Data Types（SSS 2011）。你也可自行核验：在你的向量库或搜索索引副本上并发写入同一文档，观察哪一版最终保留、是否有冲突记录。

**失效条件**：当写集互不相交（不同用户、不同分片、不同实体）时，定序机制的差异几乎不可观测——为一个不相交写集的系统上 TSO 或 TrueTime 是纯成本。只有当**同一逻辑实体的并发写**变多时，LWW 丢更新、向量时钟膨胀才成为真问题。

另外要注意定序与幂等的关系：**幂等键的有效性依赖一个稳定的顺序**。如果同一条业务请求在乱序下到达两次（先到的是重试、后到的是原始），单纯用「幂等键存在即跳过」会把原始请求也丢掉。所以幂等实现要么带上「请求生成时间 + 单调计数器」，要么把去重窗口设得足够长，用一个更大的时间窗换取「乱序窗口内不出现冲突」——这是族 4 方案里最常见的隐性缺陷，也是它与族 2（靠日志顺序免费获得全序）的实质差距。

#### 7.3.4 可补偿性：补偿能不能写出来

**机制是什么**：Saga / TCC 的正确性不取决于协议实现，取决于「每个正向操作是否存在一个语义正确的逆操作」。

**实现差异**：

| 正向操作 | 可逆性 | 常见做法 |
| --- | --- | --- |
| 创建订单 | 可逆 | 补偿改为终态（已取消） |
| 扣减库存 | 可逆 | 补偿加回，需幂等 + 并发校验 |
| 发放优惠券 | 可逆 | 补偿作废，需要有作废链路 |
| 发送短信 / 推送 | 不可逆 | 只能前置校验 + 事后不能再承诺 |
| 调用外部支付网关 | 部分不可逆 | 内部记账先行，外部调用压到最后 |
| 出账到银行 / 监管报送 | 不可逆 | 不能出现在可回滚链路中间 |

**由此必然导出的性质**：因为补偿操作本身也可能失败（下游宕机、补偿接口有 bug），所以 Saga 无法只靠「补偿重试」达到一致，必须再叠一层「人工介入队列 + 日终对账」，否则一次补偿失败就变成静默不一致——**对账不是补偿的替代品，而是补偿的必要兜底**。因为不可逆操作一旦执行就无法回退，所以正确的顺序约束是**把所有不可逆步骤压到事务链的最后**；这条规则决定了 Saga 的分段边界应当按「可逆性」切，而不是按服务边界切——这与「谁拥有这张表」无关。

**公开证据【公开】**：Saga 论文（SIGMOD 1987）把「补偿事务」作为设计的一等公民；TCC 的三个方法（Try/Confirm/Cancel）同样是为「显式可逆」而设计，Apache Seata 文档中的 TCC 模式即按此定义。可自行核验：拿你的下单链路，逐步骤标注「逆操作是什么、逆操作失败怎么办」，标不出来的步骤就是不可逆步骤。

**失效条件**：如果业务里大量步骤不可逆且不可压后（例如监管要求实时报送），Saga 不适合，此时应回到「单库 + Global DB」把链路收进一个事务，或把报送改成由事件异步派生的旁路。

**四条机制维度的对照速查**（每行给出机制依据，而不是打分）：

| 候选 | 协调点位置 | 资源持有时长 | 定序依据 | 可补偿性要求 | 由机制导出的最短结论 |
| --- | --- | --- | --- | --- | --- |
| 2PC / XA | 应用或中间件 | 2 × RTT（P99 由最慢参与者决定，不随参与者数求和） | 不需要（同步等待） | 无需补偿，但需协调者恢复 | 同城、低冲突时最简单；跨地域热点写必然排队 |
| 3PC | 应用或中间件 | 3 段，超时可推进 | 不需要 | 无需补偿 | 减少阻塞但增加消息轮次，落地少 |
| TCC | 业务代码 / 状态机 | 业务决定（可跨用户操作） | 不需要（同步确认） | 强制三接口 | 只有高冲突热点才回本 |
| Saga | 编排器 | 不持锁，中间态可见 | 依赖事件顺序 | 每步都要能补偿 | 分段必须按可逆性切，不按服务边界切 |
| Outbox | 本地数据库 | 毫秒级（本地事务） | 本地事务提交序 | 中继需幂等 | 解决「写库与发事件」的原子性，不解决跨库 |
| CDC | 无 | 无（只读日志） | 日志位点 | 下游需幂等 | 最好的同步通道，最差的一致性兜底 |
| Event Sourcing | 无 | 无 | 事件追加序 | 需要反向事件 | 换来可重建与审计，付出读模型全改 |
| Global DB | 数据库内核 | 内核内两阶段 + commit-wait | TSO / TrueTime / HLC | 无需补偿 | 只要数据能收进一个库，它就是最省事的选择 |
| 异步消息 + 幂等 | 无 | 无 | 不保证 | 幂等键强制 | 只在「重复可被吸收」的链路成立 |

### 7.4 成本结构对比（不是价格表，是成本函数）

一致性方案没有「单价」可比：同一个产品在自建机房与托管服务上、在 3 副本与 5 副本下、在开启与不开启跨 Region 复制时，成本差一个量级。可比较的是**成本函数的形式**——即成本随哪个变量增长、增长得多快、以及哪一部分不随业务量增长却随故障次数增长。

```
总成本 ≈ 固定组件成本（常驻进程 / 集群 / 副本数）
        + 延迟成本 f(事务到达率 λ, RTT, 参与者数 n)
        + 补偿与状态机维护成本 g(分支数 × 变更频率)
        + 对账与人工介入成本 h(不一致检出率)
        + 恢复能力成本（演练、Runbook、值班技能）
```

**各候选的主导项与隐性成本**：

- **2PC**：主导项是延迟成本；隐性成本是协调者高可用与悬挂事务清理。
- **TCC**：主导项是补偿与状态机维护（每个参与方从 1 个接口变成 3 个，见 §7.5 阈值依据）；隐性成本是空回滚 / 悬挂 / 幂等这三类边界 bug。
- **Saga**：主导项是状态机与编排引擎运维；隐性成本是「中间态被外部消费」时要额外解释。
- **Outbox**：主导项是投递延迟与 outbox 表清理（表增长随业务量线性）；隐性成本是中继进程的重复投递处理。
- **CDC**：主导项是日志采集吞吐与下游反压；隐性成本是 schema 变更时的下游兼容。
- **Global DB**：主导项是副本数带来的存储与写放大（跨 3 Region 复制近似 3 倍存储，【推算】按副本数线性）；优点是这项**可算、可预算**。
- **Event Sourcing**：主导项是事件存储增长与快照重建时间；隐性成本是事件 schema 演进，以及「删除类合规请求」与「事件不可删」的冲突。
- **异步消息 + 幂等**：主导项是幂等键 / 去重表的存储与清理。

注意两类成本的增长方式**根本不同**：主导项随业务量增长（可以用容量规划预算），隐性成本随**故障次数与故障复杂度**增长（不可预测，且只在出事时暴露）。所以选型时真正要比的不是「哪个更快」，而是「哪一个的隐性成本落在我的团队能力范围内」——一个没有 7×24 值班的团队选 2PC，等于把协调者恢复的定时炸弹埋在自己家里。

**【推算】Global DB 的副本成本**：设需要跨 3 个 Region 各留一份全量副本，则存储与写放大约为单副本的 3 倍（【推算】，按副本数线性）。若数据量为 2 TB，等效存储需求约 6 TB 而非 2 TB；同时每次写入要跨 Region 复制，写延迟下限由一个 RTT 决定（同城 ≈ 1 ms，跨地域 ≈ 30 ms，【经验】）。这笔成本是**显性且可算**的，这也是它相对「自研分布式事务」的核心优势。

**【推算】Outbox 表增长**：设一张核心表每秒产生 200 条事件、每条事件序列化后约 1 KB（【经验】，含 JSON 与索引开销），则每日新增约 200 × 86,400 × 1 KB ≈ 17 GB/天。若中继消费后立即删除，稳态容量约等于「消费延迟 × 速率」；若选择保留 7 天用于排障，则峰值约 120 GB。**这个数字决定了你是否必须给 outbox 表做按时间分区**——不做分区，两周后清理语句会开始锁表。

**【推算】2PC 的并发上限（含推导链）**：取同城双可用区 RTT ≈ 1 ms、跨地域（如北京—上海）RTT ≈ 30 ms（【经验】，同城亚毫秒到 1 ms、跨地域 20–40 ms 是业界常见区间）。2PC 一笔事务的持锁时长 ≈ 2 × RTT，即同城 ≈ 2 ms、跨地域 ≈ 60 ms。按 Little 定律，事务到达率 1,000 TPS 时，平均并发持锁事务数 = 1,000 × 0.06 = 60（跨地域）对比 1,000 × 0.002 = 2（同城）。60 个并发持锁落在少数热点行上必然排队，这就是「2PC 不要跨地域用在热点写」的定量依据，而不是一句「2PC 慢」。【推算】结论只在上述 RTT 与 TPS 假设下成立，换成同城、低 TPS 场景，结论反转。

**【推算】一份补偿逻辑的边际成本**：设一条链路上有 n 个参与方，从 Saga 迁移到 TCC 需要每个参与方多实现 2 个接口（Confirm / Cancel），并配套状态表与幂等键。若每个接口按 1–3 人日（【经验】，含测试与边界用例），n = 6 时约增加 12–36 人日；这笔投入换来的收益是「资源预留在业务层可见、可排队」。若你的热点行并发请求数始终低于该行的可用并发度（同一条库存记录几乎不并发扣减，锁等待不构成端到端延迟的主导项），这笔投入不会带来可观测收益——**TCC 只在高冲突场景才回本**，判定方法见 §7.5 阈值依据。

### 7.5 决策树（每个分支都要有阈值依据）

```
第 1 层（硬约束，对全体候选生效，先问）：是否要求「同一实体的并发写不丢更新」？
│   （写集互不相交、或每个实体只有一个写入者时，答案为「否」）
├─ 是 → 定序必须上 TSO / TrueTime / HLC 类方案并配版本判定或冲突检测，禁用一切 LWW 与「无版本号的 upsert」
│        ├─ 跨 Region 且要求线性一致 → TSO / TrueTime（接受 commit-wait 抬高的写延迟下限）
│        └─ 只需单调可比、不愿付 commit-wait → HLC + 显式冲突检测，冲突交业务消解
└─ 否 → 库内自增 / binlog offset 定序即可；LWW 也只在你确认「后写必对」时可接受
     ↓（无论第 1 层怎么答，都继续走第 2 层）
第 2 层（选族）：你的写入是否要求「一起成功或一起失败」？
├─ 不要求（可容忍中间态，且有对账/退款兜底）
│    └─ 族 2 / 族 4：Outbox（写库即发事件） / CDC（不侵入业务读日志） / 异步消息 + 幂等
└─ 要求
    ├─ 需要一起改的数据能否全部放进同一个数据库产品？
    │    ├─ 能 → Global DB（Spanner / OceanBase / TiDB / CockroachDB）
    │    └─ 不能
    │        ├─ 参与者 ≤ 2 且同城同可用区、热点写 < 数千 TPS ？
    │        │    ├─ 是 → 2PC / XA（此时强一致近似免费）
    │        │    └─ 否 ↓
    │        ├─ 参与者里是否存在「不可逆」步骤？
    │        │    ├─ 有但可整体压到链尾 → Saga + Outbox
    │        │    └─ 不可逆且不可压后 → 改造业务流程，或把该段收进 Global DB
    │        └─ 同一热点行的预留失败率是否显著高于 0（并发请求数已超过该行可用并发度）？
    │             ├─ 是 → TCC（预留语义吸收冲突）
    │             └─ 否 → Saga（少写两个接口）
```

**阈值依据**：

- **「是否要求同一实体的并发写不丢更新」**（第 1 层，无阈值）：这是正确性硬约束，不是性能权衡，所以它排在所有阈值之前，也对族 2 / 族 4 的读者同样生效——走最终一致路线的人并不会因此豁免定序问题。判定方法是问两个可观测的事实：**写集会不会相交**（同一用户、同一订单、同一库存行的并发写）与**写入者是几个**（多 Region、多端、离线重放）。两者同时为「是」时，LWW 必然静默丢更新且不留痕迹，与数据规模无关。
- **「参与者 ≤ 2」**：来自能力边界判据。绝大多数数据库厂商的 XA 实现对**同构资源**（同一产品族）支持最完整，协调器恢复由产品自带；一旦参与者变成异构中间件（消息队列 + 缓存 + 外部 HTTP），协调器恢复逻辑就得自研，正确性责任转移到你的团队。参与者从 2 增到 n 时，原子性收益不再增加，而「需要自己兜住的故障面」约按 n 增长。
- **「同城 RTT ≈ 1 ms / 跨地域 ≈ 30 ms」**：【经验】档区间。它决定了 2PC 的持锁时长（2 × RTT），进而决定了并发上限（见 §7.4 的 Little 定律推算）。
- **「热点写 < 数千 TPS」**：由 §7.4 推算反推：同城 2 ms 持锁下 1,000 TPS 仅 2 个并发持锁事务，可忽略；跨地域 60 ms 持锁下同样 TPS 产生 60 个并发持锁，已接近热点行的等待临界。因此这条阈值的作用是把「跨地域 + 热点写」划出 2PC 的适用区，而不是给一个精确的性能数字。
- **「同一热点行的预留失败率显著高于 0」**：这条**刻意不给固定数值**，因为它不是场景常量，而是你自测出来的量——预留失败率由「该行的并发请求数 / 该行可用并发度」决定，而「可用并发度」又由 Try 操作的持有时长与单节点容量共同决定，换个实现就变。可判定的做法是压测比对两条曲线：按 Saga 实现一版，测「热点行上的锁等待占端到端延迟的比例」（若这是主导项，说明冲突确实在吞噬吞吐）；再按 TCC 实现一版，测「预留失败带来的重试与部分成功比例及业务可否吸收」。只有当**锁等待已成为端到端延迟的主导项、且预留失败能被业务降级策略吸收**时，TCC 的两倍接口成本才开始回本。经验上的触发区间是「热点行并发请求数 / 该行可用并发度 > 1 且峰值持续超过一个业务周期」（【经验】）；低于这个量级，冲突被排队自然吸收，TCC 只是多写两个接口。
- **「每个参与方接口从 1 变 3」**：TCC 的定义决定的常量（Try / Confirm / Cancel），不是经验估计。
- **「Global DB 需能装下一起改的数据」**：来自 §7.3.1 的机制约束——协调者在数据库内核里，内核之外的数据它管不到。这是硬边界，无阈值。

**这棵树刻意不覆盖的分支**（以及为什么）：

- **「要不要上 CRDT」**：CRDT 的适用性取决于数据结构能否被表达成可交换 / 可合并的形式（计数器、集合、序列），这不是「一致性要求强弱」能决定的，而是数据模型的数学性质决定的。判断方法：问「两个副本的并发更新能否用一个可交换的合并函数消解」，不能就不能用 CRDT。
- **「要不要上分布式锁」**：分布式锁提供的是**互斥**而不是**事务**。用它来模拟事务的原子性（先锁 A 再锁 B）会引入锁租约过期、时钟依赖与死锁检测，正确性论证比 2PC 更难。判定方法：如果你的需求里有「一起成功或一起失败」，那它是事务问题，不是锁问题。
- **「要不要上拜占庭容错（PBFT 类）」**：只有参与方可能**作恶**（而非只是宕机）时才需要。企业内部系统里参与方作恶的概率远低于其宕机概率，上 BFT 是数量级的成本换一个不存在的威胁。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 账户扣款 / 账务记账 | Global DB 或 TCC + 日终对账 | 2PC（同构库） | 纯 Saga 无法表达「不可逆出账」的补偿 |
| 库存扣减（高并发热点） | TCC（预留语义） | Global DB | 2PC 在热点行上锁等待随并发线性放大 |
| 跨 5+ 服务下单 | Saga + Outbox | 编排引擎工作流 | 2PC 的 P99 由最慢参与者决定，长尾被放大 |
| 写库同时要发事件 | Outbox 或 CDC | 应用双写（禁止） | 双写没有原子边界，失败必丢一边 |
| 数仓 / 缓存实时同步 | CDC | Outbox | 多一套中继与表清理，纯为同步不值 |
| 审计留痕 / 可重建状态 | Event Sourcing + CQRS | 版本化表 + 审计表 | 读路径要全部改写，成本只在强需求时回本 |
| 多 Region 写入 | Global DB，或单元化收窄到单单元 | LWW 冲突消解 | LWW 静默丢更新，冲突无记录 |
| 通知 / 计数 / 日志链路 | 异步消息 + 幂等消费 | — | 为其上事务协调是纯成本 |
| 报表 / 指标口径一致（T+1） | CDC 入仓 + 单一事实来源 | 定时全量比对数 | 实时协调对 T+1 场景无收益，只增加复杂度 |
| Agent 工具调用副作用 | Outbox + 幂等键 | 人工确认闸门 | LLM 重试是常态，无幂等键必然重复执行 |
| 需要一起改的数据跨 3+ 业务域 | 事件驱动 + 对账，放弃强一致 | Global DB（若能收编） | 跨域强一致要求所有域让出写入权，组织成本高于技术成本 |

**常见组合**（每条注明职责边界与运维代价）：

- **Outbox + CDC**：Outbox 负责「业务写入与事件生成同生共死」（同一本地事务），CDC 负责「不侵入业务代码地把 outbox 读出来」。边界是：业务代码不知道下游是谁，中继不解释业务语义。运维代价是多一套 CDC 集群，以及 outbox 表的定期清理与分区。
- **Saga（编排）+ Outbox**：每个本地事务通过 Outbox 发出「这一步已完成」，由编排器决定下一步。边界是编排器**只做决策不做数据搬运**，业务数据永远由各自的服务写自己的库。运维代价是编排器的持久化状态机成为新的关键组件，需要它自己的高可用与重放能力。
- **Global DB + Outbox / CDC**：核心账务进 Global DB 拿到真正的单库事务，向外围系统（搜索、缓存、数仓、Agent 记忆库）的同步走 Outbox 或 CDC。边界是「强一致只保留在最需要的那一小圈」。运维代价是两套一致性体系并存，需要一条明确的「哪些数据在哪一圈」的规则并定期核对。
- **TCC + 日终对账**：TCC 覆盖实时链路，对账覆盖「补偿失败」的长尾。边界是：对账只负责**发现并挂账**，不做自动改写；自动改写会掩盖上游 bug。运维代价是每天必须真的看一次对账差异。
- **一致性 + 单元化**（见 Ch12 §01）：把跨 Region 写入收敛为「尽量同单元内完成」，从根上减少需要跨 Region 协调的事务数量——机制上等价于把 2PC 的参与者从跨地域变成同单元，RTT 从 30 ms 量级降到 1 ms 量级。
- **一致性 + AI 链路**（见 §5 前沿演进）：Agent 的「调用工具」与「写状态」之间也需要原子边界，做法是把副作用收进 Outbox 与幂等键，使重试不会产生重复动作——LLM 的不确定性让「重试」成为常态，幂等从优化项变成前置条件。

组合的原则只有一条：**每加一件，都要说清它负责哪一段边界，以及当它挂掉时谁来兜底**。Outbox + CDC 里 CDC 挂了，业务写入照常（只是事件延迟），这时兜底是「延迟告警 + 位点重放」；Saga + Outbox 里编排器挂了，各服务本地事务已提交，兜底是「编排器状态重放 + 人工核查在途实例」。

### 7.7 选错的代价与迁移成本

**反模式：用打分表选一致性方案** —— 症状：把「强一致 / 性能 / 复杂度」逐格打分再加权，得出一个综合排序 → 后果：在真实负载下要么把正确性交给了只能兜底的工具（资金链路用 CDC 最终一致，靠对账追回），要么吞吐被打死（跨地域热点写选了 2PC，超时率随并发上升）→ 正确的做法：先用「不一致时能否自我修复」筛硬约束，再在合规候选里比 §7.4 的成本函数。

**反模式：用 TCC 解决不可逆问题** —— 症状：为「已出账」「已发短信」硬写一个 Cancel，实现成「记录一条不一致 + 通知人工」 → 后果：Cancel 变成不一致的搬运工，最终仍然要靠对账，而团队多背了三倍接口 → 正确的做法：把不可逆步骤压到链尾 + 前置校验，并用对账覆盖残余长尾。

**反模式：把最终一致当强一致用** —— 症状：写完立即按同样条件查询（假设 read-your-writes）、用刚写入的值做后续决策 → 后果：用户看到「已支付但订单不存在」，或按旧余额二次扣减 → 正确的做法：读己之写（写后短时读主库或会话粘滞），或把读路径也纳入同一事件流并携带版本号。

| 从 → 到 | 数据迁移 | 查询 / 接口改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 2PC → Saga | 补中间态并做存量校验 | 读路径要能解释中间态 | 引入编排器与状态机监控 | 补偿设计与重试策略 | 高（主要落在业务代码） |
| Saga → TCC | 无搬运，需加预留字段与状态表 | 每个参与方接口 1 → 3 | 需支持空回滚 / 悬挂检测 | Try-Confirm-Cancel 语义 | 高 |
| Outbox → CDC | outbox 历史需回填或截断 | 无 | 加 CDC 集群与 schema 演进流程 | 日志解析与反压处理 | 中 |
| CDC → Outbox | 无 | 无 | 去掉 CDC，加 outbox 表维护 | 低 | 低 |
| 自研分库 → Global DB | 存量分库迁移（**最大项**） | SQL 方言兼容性差异需改写 | 全新部署 / 备份 / 扩缩容体系 | 新产品的调优与限流模型 | 极高 |
| 任意 → Event Sourcing | 需要「重建事件」而非搬行 | 读模型全部重写（CQRS） | 事件存储 + 快照 + 重放工具 | 事件版本迁移 | 极高 |

关于迁移时机有一条容易被忽略的约束：**一致性方案的迁移几乎不能在业务高峰期做**，因为迁移期间新旧两套机制必须在同一份数据上共存（双写或影子读），而双写正是 §7.7 第一条反模式的成因。可操作的做法是把迁移拆成「先只读切换（新读路径与旧读路径比对，差异挂账）→ 再只写切换（新写路径，旧路径降级为校验）→ 最后下线旧路径」三段，每段之间留一次完整的对账周期。愿意接受这个节奏，迁移才是可控的；不愿意，迁移就会变成一次事故。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 同构数据库、低热点冲突 | 2PC / XA，或直接用 Global DB | 持锁时长 ≈ 2 × RTT（同城毫秒级），强一致近似免费 |
| 跨地域 + 热点写 | TCC（预留）或 Saga + Outbox | 2PC 的 P99 由最慢参与者决定，长尾被放大 |
| 需要一起改的数据能收进一个库 | Global DB | 协调者在内核里，恢复责任转移给数据库 |
| 数据散落在多套存量系统 | Outbox 或 CDC | 只保证「本地事务与事件」的原子性，不引入跨系统锁 |
| 存在不可逆外部步骤 | 压到链尾 + 对账 | 可补偿性决定正确性上限，补偿失败必须有兜底 |
| 同实体高频并发写 | 禁用 LWW，上 TSO / TrueTime 类定序 | LWW 静默丢更新，冲突无任何记录 |
| 通知 / 计数 / 日志 | 异步消息 + 幂等键 | 为这类链路上协调协议是纯成本 |
| 团队没有 7×24 值班 | 避免 2PC，优先族 2 / 族 3 | 协调者恢复与悬挂事务清理是值班型工作 |

回到本章 6 条判据里权重最高的两条：**正确性硬约束**决定了候选集合（不能自我修复的不一致场景不允许上最终一致），**资源持有时长**决定了同一族内部的选择（同城低冲突用 2PC，跨地域或高冲突用 TCC / Saga）。这两条判据回答完，剩下的生态、许可、学习曲线才有讨论价值——顺序反了，讨论就永远停在偏好层面。

再强调一次本章给的是**推导**（为什么 Outbox 在「写库同时要发事件」这个具体问题上不可替代，以及它在「跨服务原子性」这个它解决不了的问题上会怎样失效）。结论会随版本与本组织的技术栈过时，推导不会——这也是 §4 与 §6 值得与本节对照阅读的原因。

> 本节小结：这些候选之间唯一真正起决定作用的差异是**「提交决定放在哪一层，以及资源被锁多久」**——它同时决定故障恢复责任归谁、并发上限在哪、以及迁移时要动业务代码还是动基础设施。其余维度（复杂度、生态、学习曲线）都是这条差异的下游结果。
