## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

一致性模式的对照表读起来像一道按场景的选择题：金融选强一致、库存选 TCC、订单选 TCC + Outbox、社交选最终一致、日志选 Event Sourcing。但把两个「电商库存」放在一起看，这张表立刻失效：一个是核心 SKU 的库存行每秒接受几百次并发扣减（必须走预留式，否则行锁排队直接把 P99 拉爆），另一个是长尾商品的库存几乎不并发（一个本地事务加行锁就够，上 TCC 纯属多写两套接口）。同一个「电商库存」，正确模式相反。

差异的根子在四条机制维度上，本章 §7.3 把它们逐条拆开过：**协调点在哪一层**（谁决定提交、这个决定在崩溃后还在不在）、**资源持有多久**（持有什么、持多久、由谁决定）、**谁给事件定序**（时间戳从哪来）、**补偿写不写得出来**（每个正向操作有没有语义正确的逆操作）。这四条不是评价标准，是**取值**——任何一个具体模式，都是这四条取值的一个组合。选模式之前先给这四条赋值，比背对照表有用得多。

第一条当即决定故障模型：把协调者放在应用侧，就意味着「协调者崩溃后如何恢复」要由使用者自己兜住（XA 日志落哪、恢复扫描谁跑、悬挂事务谁清）；把协调者放进数据库内核，应用写的就是本地事务语法，恢复由内核负责。**同一套业务语义，这两种选择换来的运维义务完全不同**——§7.3.1 的结论是：Global DB 的代价不是性能，是「需要一起提交的数据必须全部住在这一个数据库产品里」。

第二条决定性能上限。持锁型方案的并发上限由 Little 定律给出：平均并发持锁事务数 = 到达率 × 持锁时长，而 2PC 的持锁时长约等于 2 × RTT（同城约 2 ms、跨地域约 60 ms，【经验】量级见 §7.4）。这意味着 1,000 TPS 下跨地域平均有 60 个事务在持锁——**这不是「2PC 慢」，是「2PC 在跨地域热点写上必然排队」**。而预留型方案（TCC）把冲突从「锁等待」变成「预留失败」，冲突仍在，但可以被业务降级吸收。

第三条决定最终一致方案成不成立：写集互不相交时（每个实体只有一个写入者），LWW 与向量时钟的差别几乎不可观测；一旦同一实体出现并发写，LWW 就会静默丢更新且不报错（§7.3.3），所以「用不用版本判定」不是优化项，而是被写入模式直接决定的是非项。第四条决定长事务能不能拆：补偿写不出来（已出账到银行、已发出短信、已监管报送）的步骤，不能出现在可回滚链路的中间，只能压到最后或移出链路（§7.3.4）。此外还有一条组织层面的约束：一致性方案的**隐性成本随故障次数增长**而不是随业务量增长（协调者恢复、悬挂事务清理、补偿失败处置），一个没有 7×24 值班的团队选 2PC，等于把协调者恢复的定时炸弹埋在自己家里（§7.4 的成本函数）。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 写集是否相交（同一实体是否多写者） | 必须上版本判定 / 冲突检测，还是可以用 LWW | 「最终一致就行」——并发写下的 LWW 是静默丢数据，不是延迟 |
| 协调点放在哪一层 | 故障恢复的责任归谁、应用要写多少分布式逻辑 | 「上了分布式数据库就不用管一致性」——它只覆盖住进去的数据 |
| 热点行的并发度 | 持锁式还是预留式 | 「TCC 性能好所以更优」——低冲突下 TCC 只增加调用次数 |
| 数据能否收进一个库 | Global DB 是替代品还是只覆盖增量 | 「强一致必须用 2PC」——把协调者下沉进内核是更省的路径 |
| 可补偿性 | 长事务能否用 Saga 拆 | 「所有步骤都能回滚」——发出去的短信、出账的资金回不来 |
| 规模与故障频度 | 隐性成本可控还是不可控 | 「选更快的那个」——协调者恢复成本只在出事时暴露 |
| 团队技能与值班能力 | 自研协调还是用现成实现 | 「自己写协调逻辑更灵活」——脑裂与丢决议的代价极高（§7.3.1） |

把这八个模式放回这四条主线上，它们的关系就清楚了：**强一致（3.2.1）** 是把决策权收到一处；**最终一致（3.2.2）** 是放弃这个决策点、靠幂等与定序收敛；**TCC（3.2.3）** 是把锁下沉成业务预留；**Saga（3.2.4）** 是把长事务按可逆性切段；**Outbox（3.2.5）** 是不引入协调者，只保证「写库 + 发事件」这一个局部边界原子；**Event Sourcing（3.2.6）** 与 **CQRS（3.2.7）** 改的是数据形态本身，与传统事务正交；**AI 时代的一致性（3.2.8）** 不发明新机制，只是给既有协议换落点。**把正交的问题当成同一个单选题，是一致性选型出错的最常见形式。**

### 3.2 模式逐个拆解（核心节）

本节沿用 §7.2 的四族分类给模式标注族归属，但展开顺序仍按八个模式逐一拆解，没有按族顺序重排：**族 1 协调型事务**（2PC / 3PC / TCC / Saga，需要「谁来决定提交」这个角色）、**族 2 日志与事件型**（Outbox / CDC / Event Sourcing，不引入协调者，靠本地事务 + 日志顺序传递事实）、**族 3 数据库内核型**（Global DB，把协调者下沉）、**族 4 无协调型**（异步消息 + 幂等，以及 LWW / 向量时钟 / CRDT 这类冲突消解机制）；CQRS（3.2.7）与 AI 时代的一致性（3.2.8）不在这四族之内，它们改的是数据形态与机制的落点。同族内部可逐项替换，跨族替换要动的是业务代码与数据形态。

每个模式给六件事：被什么约束逼出来、结构、为什么有效、代价、失效点、真实使用。**失效点是最该读的一项**——它回答的是「在什么冲突率、什么参与者规模下，这个模式会从对的变成错的」。

#### 3.2.1 强一致模式（CP）

- **被什么约束逼出来**：业务不允许读到旧值（资金、库存、订单状态），而数据已经分布在多个节点上——「决定权必须落在一个崩溃后仍然存在的位置」是它唯一的立足点。
- **结构**：写入必须在多数派或协调者持久化之后才对读可见；协作者的恢复责任由结构决定。

```text
强一致（CP）：决定权落在一处，且这个决定在崩溃后仍然存在

  2PC（协调者在应用侧，族 1）        Paxos / Raft（决定权在多数派）
  ───────────────────────────      ─────────────────────────────────
  Coordinator  ──Prepare──► P1..Pn   Leader ──append──► Follower × N
    │           ◄──Yes/No──┘           │ 多数派持久化即提交
    │ Commit / Rollback ──►            │ term 递增；只有含最新日志者能当选
    ▼                                  ▼
  提交点 = 协调者的日志              提交点 = 多数派持久化

  共同点：写在"协调者 / 多数派"落盘之后才对读可见 → 结构上读不到旧值
  差异：2PC 的决议稳定性取决于协调者自身可恢复；Raft 把决定权复制到多数派
        2PC 失效 → 参与者持锁等待（阻塞）；Raft 失效 → 拒写（不持锁、不可用）

  族 3（Global DB）把这一层搬进数据库内核：Spanner 用 TrueTime 给出有界不确定
    度 ε，提交后 commit-wait 到 2ε 才对读可见；代价是数据要全部住进这一个产品
```

- **为什么这样设计有效**：因为提交点位于一个「崩溃后仍然存在」的位置，所以读到的值必定是已经定下来的值——「读到旧值」在结构上不可能发生，而不是靠读端去检查。
- **代价**：① 写延迟由协调路径决定：2PC 约 2 × RTT，带时钟的 Global DB 还要加上 commit-wait 的等待；② 可用性与协调者（或多数派）绑定，它不可达时就只能拒绝写入；③ 迁移成本最高档：一旦选它，参与同一事务的数据通常要收进同一个引擎，存量数据无法被覆盖。
- **失效点**：当参与者中出现**不可补偿的外部系统**（已出账到银行、已发出短信）时，「绝不出错」反转成「阻塞且无法回退」：因为同步提交要求所有参与者在协议内可回退，而外部系统不在协议内——它只能被等待，不能被撤回。这类步骤必须被移出强一致链路，改成由事件异步派生。
- **真实使用**：Google Spanner 把跨洲强一致做成对外单库事务语义，机制与 TrueTime 的 ε 量级见 Spanner 论文（OSDI 2012，§7.3.1 公开证据段）；CockroachDB 1.0 于 2017 年发布、OceanBase 于 2020 年在 TPC-C 登顶（各自官方发布，§7.3.1）——§7.2 把这一族的代表列为 Spanner、CockroachDB、TiDB、OceanBase，都是「把协调者放进内核」的路线。Raft 的协议定义见 Ongaro & Ousterhout（USENIX ATC 2014）；**3PC** 是 2PC 的非阻塞改良，它用「让参与者也具备超时推进能力」消除阻塞，但额外假设网络延迟有上界且不发生分区——这两个假设在真实数据中心都不成立，所以它在工程里少见落地，只是说明「阻塞的根因不是阶段数不够，而是决定权集中在一个会崩的进程上」（§7.3.1）。【公开】（来源：§7.3.1 公开证据段；§5.2.2 的 Raft 引用；§7.2 候选表；§6 案例 8.1、8.2 的 Google / 阿里两条落地）

#### 3.2.2 最终一致模式（AP）

- **被什么约束逼出来**：可用性与延迟优先，业务能接受「过一会儿才一致」——但要求系统在没有新写入的前提下确实会收敛。
- **结构**：本地先提交并立即返回，变更通过 Outbox / CDC / 事件异步传播到其他副本；收敛靠三个条件同时成立。

```text
最终一致（AP）：放弃"此刻一致"，换"最终收敛"（§7.2 族 2 / 族 4）

  写入 ──► 本地提交（立即返回）──► 变更流（Outbox / CDC / 事件）
                                        │ 异步、可乱序、可重复
                                        ▼
                                   远端副本收敛

  收敛的三个必要条件，缺一不可：
    ① 幂等：重复投递不产生第二次副作用
    ② 定序依据：谁的时间戳说了算 —— LWW / 向量时钟 / CRDT（§7.3.3）
    ③ 冲突可消解：要么被检测出来交给业务，要么被数学上保证可合并

  ─────────────────────────────────────────────────────────
  读侧能观测到的只有"值"，观测不到"这个值是不是最新的"
    → 所以最终一致必须配一个可观测的滞后量（副本落后版本数、中继积压）
    → 并且"最终"没有时间承诺：它是"无新写入时最终一致"，不是"1 秒内一致"
```

- **为什么这样设计有效**：因为写入在没有跨节点协调的情况下就返回了，所以本端可用性不再受对端影响；一致性代价被转移到读侧——读端要么接受旧值，要么显式等待追上某个版本。
- **代价**：① 收敛依赖幂等与定序，这两个前提缺任何一个都会退化成静默不一致（重放产生第二次副作用、LWW 丢更新）；② 每个读端都必须知道「自己可能读到多旧的数据」，这要求把滞后量做成可观测指标；③ 一致性级别从强到弱是一条连续谱（读己之写、单调读、因果一致，见主文件 §1.1 第 5 条与 §2.3 的「一致性级别」清单），选定之后读接口的语义都要跟着写明。
- **失效点**：当同一实体出现并发写时，「高可用」反转成「静默丢更新」：因为 LWW 用一个时间戳做最终裁决，冲突时后到的写覆盖先到的，而系统不会报错（§7.3.3）。这不是配置问题，是模式选择的后果——实体一旦进入多写场景，就必须引入版本判定或 CRDT，否则丢失是不可观测的。
- **真实使用**：Amazon Dynamo 用向量时钟检测并发写并给出 LWW 等消解策略（SOSP 2007，§7.3.3）；CRDT 的收敛性有形式化证明，前提是合并函数可交换、可结合、幂等（Shapiro 等，SSS 2011，§7.3.3、§5.2.1）；「异步消息 + 幂等消费」这一族最弱的承诺在通知、计数、日志类链路里被普遍使用（§7.2 族 4）。【公开】（来源：§7.3.3 公开证据段；§5.2.1 对 CRDT 前提的引用；§7.2 候选表）

#### 3.2.3 TCC 模式

- **被什么约束逼出来**：业务既要「不超卖、不双扣」这种强语义，又不能接受 2PC 那样把数据库行锁一直持有到全局决议落定。
- **结构**：Try / Confirm / Cancel 三层接口，加上业务侧的事务状态表；「锁」被下沉成业务语义上的预留。

```text
TCC：把"锁"下沉成业务语义上的预留（§7.3.2）

  主业务服务                参与方 A              参与方 B
  ─────────                ─────────             ─────────
  Try     ───────────────► 预留（冻结额度）       预留（占用库存）
          ◄─────────────── 成功 / 失败           成功 / 失败
    │ 全部成功 → Confirm（幂等，可重试）
    │ 任一失败 → Cancel（幂等，须支持空回滚）
    ▼
  事务状态表：决策必须落盘，否则重启后不知道自己走到哪一步

  与 2PC 的结构差别：持有的是业务资源，不是数据库行锁
    → 同一记录的争抢表现为"预留失败"，可被业务吸收（排队 / 重试 / 确定失败）
    → 而不是"锁等待"，只能排队
  三个必须写对的边界：空回滚（Try 未到先收到 Cancel）、悬挂（Cancel 先到、Try 后到）、幂等
```

- **为什么这样设计有效**：因为资源在 Try 阶段就以业务语义被冻结，冲突发生在业务能理解、能降级的层面；2PC 的冲突是锁等待，业务层看不到也没法处理。
- **代价**：① 每个参与方从 1 个接口变成 3 个，并各自维护状态表与幂等键——§7.4 按「每接口 1–3 人日」推算，n = 6 时约增加 12–36 人日的实现成本；② 空回滚 / 悬挂 / 幂等这三类边界 bug 是这类方案的主要事故来源，且在单测里很难暴露；③ 它只在「高冲突热点」才回本。
- **失效点**：当热点行的并发请求数低于该行的可用并发度时，「用预留换并发」反转成「纯成本」：因为 TCC 相比本地事务多一次远程调用与一张状态表，而它要解决的锁等待问题根本没出现（§7.4 的推算把这条写成「TCC 只在高冲突场景才回本」）。反向失效同样存在：参与者里只要有不可补偿的外部系统，Cancel 在语义上就不存在，方案退化。
- **真实使用**：Apache Seata 提供 TCC 模式实现，§4.3 把 Seata / DTM / ByteTCC 列在「分布式事务」一栏；§4.2 给出 Try / Confirm / Cancel 三方法的工程示例；§7.5 的决策树把 TCC 限定在「高冲突热点」分支。【公开】（来源：§4.2 TCC 示例；§4.3 工具链表；§7.4 的推算与 §7.5 决策树）

#### 3.2.4 Saga 模式

- **被什么约束逼出来**：一笔业务要跨越多个服务、耗时远超单个数据库事务允许的范围，而业务本身不能不做——只能把它拆成一串可补偿的本地事务。
- **结构**：正向操作链 + 逆序补偿链 + 对账兜底；分段按「可逆性」切，不按服务边界切。

```text
Saga：一串本地事务 + 逆序补偿（§7.2 族 1）

  正向：T1 ──► T2 ──► T3 ──► T4
  失败：T1 ◄── C2 ◄── C3        （逆序补偿；C 自己也可能失败）
            └──► 人工介入队列 + 日终对账（§7.3.4：对账是补偿的必要兜底）

  分段规则：按"可逆性"切，不按服务边界切
    T1 创建订单   可逆   → 补偿改为终态（已取消）
    T2 扣减库存   可逆   → 补偿加回，需幂等 + 并发校验
    T3 发送短信   不可逆 → 必须排在最后
    T4 外部支付   部分不可逆 → 内部记账先行，外部调用压到最后

  两种协调方式，差别在"决定权在哪、故障时谁负责恢复"：
    编排（choreography）：各服务订阅事件自行推进，无中心 → 决定权分散
    编制（orchestration）：中心编排器持有持久化状态机 → 决定权集中
```

- **为什么这样设计有效**：因为每一段都是本地事务，长链路不需要跨服务持锁；把不可逆步骤压到末尾之后，失败时前面的分段都能被语义正确地补偿——**Saga 的正确性不由协议实现决定，由「每个正向操作是否存在语义正确的逆操作」决定**（§7.3.4）。
- **代价**：① 中间态对外可见，任何假设「中间态不会出现」的下游都会被打破；② 补偿逻辑要与正向逻辑同等维护，还要处理「补偿本身失败」；③ 编排器是有状态组件，持久化、重试、幂等都要自己运维；④ 分段边界变成一份需要长期维护的清单。
- **失效点**：当补偿操作本身开始失败时，「拆开长事务」反转成「长尾的静默不一致」：因为 Saga 只保证补偿会被尝试，不保证补偿会成功；一旦补偿失败又没有对账兜底，不一致会留在系统里且没有任何信号（§7.3.4）。所以 Saga 的正确形态一定是三段：正向链路、补偿链路、对账链路——**对账不是补偿的替代品，而是补偿的必要兜底**。
- **真实使用**：Saga 由 Garcia-Molina 与 Salem 在 SIGMOD 1987 提出，原始动机正是「用可补偿子事务规避长锁」（§7.3.2、§7.3.4）；§7.2 候选表把 Temporal、Cadence、Seata Saga 列为开源编排引擎；§4.5 给出编排式 Saga 的工程写法。【公开】（来源：§7.3.2 / §7.3.4 公开证据段（SIGMOD 1987）；§7.2 候选表；§4.5 示例）

#### 3.2.5 Outbox 模式

- **被什么约束逼出来**：业务数据写进了本地库，事件也必须发出去，而跨库事务又不便宜——「写库」与「发事件」需要一个原子边界，且这个边界必须便宜。
- **结构**：业务写入与事件写入放进同一个本地事务；独立中继负责读出并投递。

```sql
-- Outbox：把"写库"与"发事件"放进同一个本地事务（§7.2 族 2）
BEGIN;
  INSERT INTO orders(order_id, status, amount) VALUES (:id, 'CREATED', :amt);  -- 业务写入
  INSERT INTO outbox(id, topic, payload, created_at)
    VALUES (gen_random_uuid(), 'order.created', :json, now());               -- 同一事务
COMMIT;   -- 原子边界到这里为止：要么两者都在，要么都不在

-- 中继（独立进程，轮询或读日志）：
--   读未投递 → 投递到消息系统 → 标记已投递
--   若"投递成功但标记失败" → 会重投 → 消费端必须用幂等键吸收
-- 容量：消费后即删，则稳态容量 ≈ 消费延迟 × 速率；
--       若保留 7 天用于排障，则必须按时间分区，否则清理语句会锁表（§7.4 推算）
```

- **为什么这样设计有效**：因为两条写入共享同一个本地事务，所以「业务数据在、事件不在」这种情况在结构上不可能发生——原子性由本地数据库保证，而不是由投递机制的可靠性保证。
- **代价**：① 中继是单点转发器，它的滞后直接成为下游可见延迟；② outbox 表随业务量线性增长（§7.4 按每秒 200 条、每条约 1 KB 推算约 17 GB/天），分区与清理是长期运维项；③ 重复投递是常态，「消费端幂等」从可选变成必须——这个前提不写在代码注释里，就一定会被某个新消费方漏掉。
- **失效点**：当写入速率增长到中继只能批量抽数时，「本地原子」反转成「投递延迟不可控」：因为 Outbox 只保证事件不丢，不保证何时发出；中继吞吐成为端到端时延的新上限，而这个上限不体现在业务写入的耗时里，很容易被误读成「系统很健康」。
- **真实使用**：Outbox 不引入新协调者，是事件驱动微服务的常见落地形态，多数消息中间件与 ORM 生态都有实现（§7.2 候选表）；Kafka 0.11（2017，KIP-98）引入幂等生产者与事务，把「发消息」与「提交消费位点」纳入同一原子边界（§7.3.2）——这是族 2 的另一条路：不引入跨系统锁，只保证边界原子性。§4.2 给出 Outbox 的工程写法。【公开】（来源：§7.2 候选表；§7.3.2 公开证据段（Kafka 0.11 / KIP-98）；§4.2 Outbox 示例）

#### 3.2.6 Event Sourcing

- **被什么约束逼出来**：业务要求任何时刻的状态都能被解释、被回溯——只存当前状态会丢掉过程，而过程恰恰是审计与复盘要的东西。
- **结构**：只追加事件，当前状态由重放得出；快照不是优化项而是必需品。

```sql
-- Event Sourcing：状态不是被存储的，是被重放出来的（§7.2 族 2）
CREATE TABLE event_store (
  aggregate_id UUID        NOT NULL,
  version      BIGINT      NOT NULL,   -- 每聚合单调递增
  event_type   TEXT        NOT NULL,
  payload      JSONB       NOT NULL,
  occurred_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (aggregate_id, version)  -- 唯一约束即乐观并发控制
);                                     -- 并发写第 N 版只能有一个成功

-- 当前状态 = 从最近一个快照开始，按 version 顺序重放事件
-- 快照不是优化，是必需品：重放成本随事件数线性增长
--   【推算】每聚合每天 100 个事件 → 一年约 3.65 万个事件；单事件重放按 1 ms
--   计【经验】→ 一年后一次全量重放约 36 秒，超出交互式读取预算 → 必须打快照
--   （推导链：事件数 × 单事件重放耗时）
-- 与"删除类合规请求"冲突：事件只可追加，删除只能靠反向事件表达
```

- **为什么这样设计有效**：因为事实以追加形式被保留，所以任意时刻的状态都能被重算，审计与回溯不需要额外机制；并发控制也可以直接由 `(aggregate_id, version)` 这个主键承担，不需要另加锁。
- **代价**：① 事件存储的增长没有上限，快照与归档是长期工程；② 事件 schema 成为对外契约，改一次要兼容全部历史事件；③ 读侧必须重建（通常配合 CQRS，见 3.2.7），所有按当前状态写的查询都要改写——这也是它在 §7.7 的迁移成本分档里位于最高档的原因。
- **失效点**：当合规要求「数据主体可删除」时，「不可删只可追加」反转成「合规义务无法履行」：因为事件流是事实记录，物理删除会破坏重放一致性，只能用反向事件表达删除——而反向事件是否满足监管口径，不由技术决定。这个问题必须在选型时先回答，而不是在上线后补。
- **真实使用**：§7.2 候选表把它归为族 2，典型场景是账务与审计留痕，并指出它与 CQRS 通常捆绑使用；§7.7 把它的迁移成本列为最高一档。【公开】（来源：§7.2 候选表与 §7.7 迁移成本分档）【推算】（重放耗时推导见上文代码块）

#### 3.2.7 CQRS

- **被什么约束逼出来**：读写两侧的形态要求根本不同——写要规范化 schema 与不变式校验，读要宽表与预聚合，用一套模型同时满足两边会让两边都别扭。
- **结构**：写模型与读模型分离，读模型是派生副本，并带有同步位点。

```text
CQRS：把写模型与读模型拆开，各自按自己的形态组织

  命令侧（写）                            查询侧（读）
  规范化 schema / 单事务 / 校验不变式  ──►  宽表 / 物化视图 / 倒排 / 图
  只接受命令，不直接服务查询                只读、可重建、可存在多份
        │ 变更事件（与 Outbox / CDC / Event Sourcing 同一条通道）
        └──────────────────────────────►
  ─────────────────────────────────────────────────────────
  读模型是派生的 → 必须可重建，并记录"同步到哪个位点"
  由此导出：CQRS 的读侧自带一致性问题（可能读到旧版本），
            它不是"读写分离完之后就没事了"

  判定方法：读侧能否回答"我现在读到的是哪个位点"；
            答不出来，就无法对外给出任何新鲜度承诺
```

- **为什么这样设计有效**：因为读侧不承担写入约束，所以它可以按查询形态任意冗余与预聚合，写侧不必为了查询性能做妥协——**两侧的优化目标不再互相牵制**，这是它唯一的、也是决定性的收益。
- **代价**：① 同一份数据有两份表示，必须有一条可靠的变更通道与位点管理；② 读侧一致性成为新的显式问题，所有读接口都要说明「可能读到多旧」；③ 重建读模型（口径变更、索引结构调整）成为常规运维动作，耗时随数据量增长。
- **失效点**：当读侧被下游当成「实时真相」使用（写回、对账、二次加工）时，「读写分离」反转成「两套真相打架」：因为读模型有天然滞后，下游把读到的旧值再写回写模型，等于用旧数据覆盖新数据。正确的边界是：读侧只读，写回路径只允许走命令侧，并且读结果要带上位点或版本。
- **真实使用**：§7.2 把 Event Sourcing 与 CQRS 绑在同一条目（「状态即事件序列」），本章把它视为 Event Sourcing 的常规配套，而不是独立的数据库选型。【公开】（来源：§7.2 候选表）

#### 3.2.8 AI 时代的一致性

- **被什么约束逼出来**：AI 链路改掉了「写入方」与「状态持有窗口」，但没有改掉一致性协议的任何前提——需要定序、需要幂等、需要可重放，这三条一条都没变（§5.2.2）。
- **结构**：三个彼此不同的问题、三个落点，全部落在既有机制上，而不是新协议。

```text
AI 链路把"一致性"拆成三个不同的问题（对齐 §5.2 的编号）

  ① 向量索引一致性（§5.2.1）：一次逻辑写入 = 落库 + 调 Embedding + 建索引
       → 多出一个可失败的异步阶段；读侧只观测到"命中 / 未命中"
       → 「读己之写」必须显式声明成会话级保证，不能当默认行为
  ② Agent 状态一致性（§5.2.2）：状态窗口从毫秒级拉长到秒级（一次 LLM 调用）
       → 前提不变，变的是写入方与窗口长度；状态进有定序能力的共识存储，或
         收敛到单一写入点（单 Actor 串行处理），不可序列化的副作用靠幂等键吸收
  ③ 推理结果一致性（§5.2.3）：链路上唯一一个非确定组件
       → 共识要求状态机确定 → 模型输出必须作为外部输入记入日志，不能重算
  ─────────────────────────────────────────────────────────
  共同点：没有新模式被发明，三条都是"既有协议 + 新落点"
```

- **为什么这样设计有效**：因为三个问题都落在既有机制的边界之内，所以不需要新协议——向量索引的可见性靠会话级等待（读己之写），Agent 状态靠共识存储定序，推理结果靠「把非确定的外部调用结果先记录再复制」这一分布式系统既有做法（原来记的是「取当前时间」，现在换成「调一次模型」）。
- **代价**：① 向量写入变成多段失败点，重试成为常态，幂等从可选变必需；② Agent 状态必须可序列化，而外部句柄、已发生但未落库的副作用不可序列化，迫使把「动作日志」与「可合并的状态」拆开；③ 把模型输出当数据存下来后，存储与日志体积按输出长度线性增长，可以复现的组合数按版本数呈乘法增长（§5.2.3）。
- **失效点**：当把模型放进重放链路、当作「可重放的函数」时，「能恢复」反转成「恢复出不同的结果」：因为共识协议要求同一份日志在每个副本上重放出同一个状态，而模型这一段不满足「输入相同则输出相同」，副本各自算出不同状态，协议前提被破坏。所以模型输出必须先落为记录再复制，**模型本身不能出现在重放路径里**。
- **真实使用**：§5.2 逐条给了成熟度评级：状态机复制 L1（协议 GA、第三方生产案例广泛），向量索引一致性与 Agent Checkpoint / Actor 类手段 L2（机制成熟、语义无标准化）；「相同输入 = 相同输出」作为对外承诺、以及向量索引的 CRDT 合并路线仍在 L3。本节沿用该评级，不额外断言任何公司已全面落地。【公开】（来源：§5.2.1–§5.2.3 的成熟度判定与证据段；§7.3.3 的定序机制对照表）

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 资金 / 库存不允许读到旧值，且数据能收进一个引擎 | 强一致（Global DB） | 2PC 要求自己兜住协调者恢复与悬挂事务清理 | 参与同一事务的数据**能否全部住进同一产品** |
| 跨异构资源（既有分库 + 外部系统）、同城、低冲突 | 2PC / XA | TCC 在低冲突下只是多一次调用与一张状态表 | 参与者数量与**热点行的峰值并发度** |
| 高冲突热点（同一行高频并发扣减） | TCC | 2PC 的持锁时长 2 × RTT 会让 P99 由最慢参与者决定 | 热点行的**并发度是否接近可用并发度** |
| 长链路、跨服务、每步都能写出补偿 | Saga | 2PC 的尾部概率随参与者数放大（1−(1−p)^n） | 每个正向操作**能否写出语义正确的逆操作** |
| 写库与发事件必须原子，下游可容忍秒级延迟 | Outbox | CDC 直读日志解决不了「业务写入与事件同库原子」 | 事件与业务写入**是否落在同一个库** |
| 需要审计、回溯、状态重算 | Event Sourcing（+CQRS） | 只存当前状态，过程信息无法事后补 | 是否存在**「删除类」合规要求** |
| 读写形态差异大、读侧要预聚合 | CQRS | 单模型会让两侧优化目标互相牵制 | 读侧**能否给出位点与新鲜度承诺** |
| 社交 / 评论 / 日志类，可用性优先 | 最终一致（AP） | 强一致在这个场景换不到业务价值，只换来延迟 | 同一实体**是否会出现并发写** |
| 多 Region 写入、每个 Region 独立可写 | AP + 版本判定（向量时钟 / CRDT） | 只用 LWW 会在并发写时静默丢更新 | 是否接受**「丢更新且不报错」** |
| AI 推理 / 智能体 | 既有协议 + 新落点：推理走「链路内一致 + 链路外最终一致」，智能体走「状态机 + Checkpoint」 | 不存在「AI 专用一致性协议」可选 | 非确定组件**是否出现在重放路径上** |

表里最常被误选的一对是 **TCC 与 Saga**。团队读到「电商库存要强一致」这句话，往往直接落到 TCC，理由是「它比 Saga 更接近强一致」。但机制上，TCC 的回本条件是「高冲突热点」——它把锁下沉成业务预留，收益来自把锁等待转成可降级的预留失败；如果这条库存行几乎没有并发，预留失败不会发生，TCC 就只剩两套接口、一张状态表和三类别扭的边界 bug（空回滚 / 悬挂 / 幂等）。反过来，把无补偿能力的链路（发短信、外部支付）塞进 Saga，会在补偿阶段暴露出一堆写不出来的逆操作。**判据是「热点行并发度」与「可补偿性」，不是「想要多强的一致性」**——想要更强的一致性，正确动作通常是回到 3.2.1 的 Global DB，而不是把 Saga 换成 TCC。

第二容易被误选的是 **2PC 与 Outbox**：两者都在解决「多个写入要么都成、要么都不成」，但作用的边界完全不同——2PC 管跨资源事务，需要协调者与参与者共同持锁；Outbox 只管「本地写入 + 对外发事件」这一个边界，不引入任何跨系统锁。把 Outbox 当跨库事务用（以为写了 outbox 就等于分布式事务），得到的是「本地原子、全局不一致」的系统：下游收到了事件，而上游那笔业务实际上回滚了；反过来把 2PC 用在「写库 + 发消息」上，等于为一条消息引入一个协调者与一个持锁窗口。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Outbox + CDC + 幂等消费（原子边界 + 传播通道 + 去重）**

- 构成：业务写入与事件写入同库同事务（Outbox）；中继改为直接读取数据库日志（CDC）而不是轮询表；消费端按幂等键去重。
- 职责边界：Outbox 保证原子边界，CDC 保证低延迟与低开销传播，幂等消费负责把重复抹掉——三者各管一段，任一段缺失都会退化成静默不一致。
- 运维代价：多一个 CDC 采集组件（位点、反压、schema 变更兼容），且下游必须统一约定幂等键的生成规则。
- 适合规模：事件驱动微服务、下游消费者多且异构。【经验】

**组合二：Saga + TCC（长链路用前者分段，热点段内用后者预留）**

- 构成：整条业务链路由 Saga 拆成可补偿的段；其中涉及高冲突资源的段内部改用 TCC 的 Try / Confirm / Cancel。
- 职责边界：Saga 负责链路级的分段与补偿编排，TCC 只负责单段内热点资源的争抢吸收。
- 运维代价：两套错误处理（补偿失败、预留失败）要在同一条链路上叠加，排障路径变长；状态表的数量也随之增加。
- 适合规模：链路长、且链路中只有少数几处是热点。【经验】

**组合三：Event Sourcing + CQRS + Outbox（事实源 + 读模型 + 对外发布）**

- 构成：事件存储是写侧唯一事实源；读模型由事件派生（CQRS）；对外发布也走 Outbox 同一条原子边界。
- 职责边界：Event Sourcing 保证事实可重放与可审计，CQRS 保证读侧可查询，Outbox 保证对外通知与内部状态同步一致。
- 运维代价：三套组件的版本（事件 schema、读模型结构、对外事件契约）都要独立演进且互相兼容，迁移成本是本章最高的一档（§7.7）。
- 适合规模：账务、审计留痕、对账要求强的系统。【经验】

三条组合的共同点是**把「原子性」压缩到尽可能小的范围内**：本地事务能解决的就不要跨库，边界上的问题用 Outbox 或日志顺序解决，跨服务的问题用补偿解决。反过来，凡是把原子边界往外扩的设计（跨库大事务、跨服务长事务），一定会在持锁时长与尾部概率上付代价。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 反模式 1：滥用 2PC | 所有分布式事务都走 2PC，参与者数量持续增加 | 持锁时长 2 × RTT 且 P99 由最慢参与者决定 → 热点行排队、协调者故障即阻塞 | 「强一致就上 2PC」是最容易讲对的一步，且中间件默认就是它 | 按冲突率与可补偿性分流：热点走 TCC、长链路走 Saga、单库范围收进 Global DB |
| 反模式 2：忽视幂等性 | 重复消息导致重复扣款 / 重复发信 | 至少一次投递是常态，去重缺失把「重试」变成「第二次副作用」，且不报错 | 幂等键要在业务层设计，被当成「基础设施会自动处理」 | 所有消息与跨服务调用都带业务幂等键；去重窗口要覆盖乱序窗口（§7.3.3） |
| 反模式 3：跨服务大事务 | 一个事务涉及 10+ 服务、跨多个库 | 协调面与失败面同时扩大：任一参与者的长尾都会放大成整笔事务的尾部（1−(1−p)^n） | 业务初始就是单体，拆分后沿用原来的调用图 | 按可逆性切成 Saga 分段；把不可逆步骤压到最后（§7.3.4） |
| 反模式 4：忽视网络分区 | 假设网络永远可用；没有 P 发生时的明确策略 | 分区发生时系统行为未定义 → 两个分区各自推进出相反决定 | 开发与测试环境很少真的分区，验证靠不上 | 明确 P 发生时的策略（拒绝写还是接受写）；把分区演练放进常规验证（§4.1 阶段 4） |
| 反模式 5：AI 链路的一致性失控 | Agent 状态不一致导致决策错误；重复工具调用 | 状态窗口长且写入方不确定 → 进程崩溃后无从判断某一步是否已执行 | Agent 状态默认放在进程内存里，恢复语义从不被讨论 | 状态进有定序能力的共识存储 + Checkpoint；副作用用幂等键吸收（§5.2.2） |

**「滥用 2PC」**。它的暴露方式是**延迟的形状**：整笔事务的 P99 由最慢的参与者决定，而不是由平均值决定——某个参与者偶发的一次停顿会把落在同一热点行上的全部并发事务一起拖慢（§7.3.2）。团队通常先把它当成「偶发抖动」排查，直到发现抖动总是跟着参与者数量走。机制上的成因很直接：2PC 的锁一直被持有到所有参与者回报之后才释放，参与者的长尾是相与关系而不是相加关系。修法不是调超时，而是把并发模型换掉：热点资源用预留式（TCC）或把数据收进单库（Global DB）。

**「忽视幂等性」**。它的暴露方式是**对账差异**：业务表里出现了同一笔请求的两条记录，而两条记录都「看起来正常」。机制上，至少一次投递是这类架构的常态而不是异常（Outbox 的投递成功但标记失败、消息中间件的重投、消费位点回退都会产生重复），因此去重不是防御性编程，而是模式的组成部件。它容易被忽略的原因是代价是隐性的：没有幂等键时，系统在绝大多数情况下工作正常，问题只在重试、扩缩容、故障切换这些时刻出现。另一个常被漏掉的细节是，幂等键的有效性依赖一个稳定的顺序——乱序到达时，只看「键存在即跳过」会把原始请求也丢掉（§7.3.3）。

**「跨服务大事务」**。它的暴露方式是**事务边缘的膨胀**：为了「保证一致」，越来越多的步骤被拉进同一个事务，参与者从 3 个涨到 10 个以上。机制上这会让尾部概率按 1−(1−p)^n 放大——单个参与者的长尾概率不变，但整笔事务踩到长尾的机会随参与者数增加（§7.3.2 的推算），同时补偿与回滚的复杂度也同步上升。修法是按可逆性重新切段，而不是继续加参与者；切段的边界应与业务语义对齐，而不是与现有的服务边界对齐。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单库 → 分库分表 | 本地 ACID 事务 | 同一事务的写入落到多个库，原子性不再免费 | 按业务边界切分，跨库部分改 Outbox / Saga | 业务代码与数据模型同时改；跨库的查询路径要重写 |
| 同城 → 跨地域多活 | 2PC / 单点协调 | 持锁时长由 2 × RTT 决定，跨地域 RTT 抬高一个量级 | Global DB（或 AP + 版本判定） | 数据要收进同一产品，或接受最终一致并补齐冲突检测 |
| 3 个服务 → 10+ 个服务 | 跨服务事务 | 尾部概率按参与者数放大，协调者恢复面同步扩大 | Saga 分段 + 每段本地事务 | 补偿逻辑要逐个补齐；不可逆步骤必须重排位置 |
| 表级 → 需要审计与回溯 | 只存当前状态 | 过程信息没有落点，事后无法解释「当时为什么是这个值」 | Event Sourcing（+CQRS） | 读侧全部改写；事件 schema 成为长期契约（迁移成本最高档） |
| 读多写少 → 读写形态冲突 | 单模型 | 写侧的规范化与读侧的预聚合互相牵制，两边都不够好 | CQRS | 需要一条可靠变更通道与位点管理，读侧一致性问题要显式化 |
| 人写 → Agent 写 | 进程内内存状态 | 状态窗口从毫秒级变为秒级，进程崩溃后无从判断某一步是否执行 | 共识存储 + Checkpoint + 幂等键 | 状态必须可序列化；不可序列化部分要拆出到动作日志 |

这些跃迁有一个共同点：**触发换模式的不是「数据量」，而是某个具体的结构性矛盾**。上表前三行的成因是「原子边界被跨库写入打破」「持锁时长被 RTT 抬高」「尾部概率被参与者数放大」，后三行是「过程信息没有落点」「读写目标互相牵制」「状态窗口变长且写入方不确定」。数据量大本身不会让模式失效，它一定通过上面某一条起作用。所以判断该不该换，看的不是 QPS 或数据量，而是几个可以直接观测的量：热点行的并发请求数与该行可用并发度的比值（接近 1 说明持锁式必须换）、事务参与者数量的分布（长尾集中在哪一段）、副本落后版本数与中继积压（最终一致的滞后量）、补偿失败的次数与对账差异条数（Saga 兜底是否在起作用），以及幂等键的命中率（命中率高说明重复投递多，是需要处理的信号而不是故障）。§5.2.4 把这几个量直接当作异常检测的输入，原因也在这里：它们取自既有组件的运行状态，不需要新建观测体系。

### 3.7 自检清单

- [ ] 每一个跨服务写操作，是否都能说清**协调者是谁**，以及它崩溃后由谁恢复？
- [ ] 两类直接可算的量是否有数：事务参与者的数量分布、整笔事务的 P99 由哪个参与者决定？
- [ ] 每个参与方持有的锁（或业务预留）**最长持有多久**？这个数是从代码里读出来的，还是估计的？
- [ ] 同一条业务请求重复到达时会发生什么？幂等键是什么、去重窗口覆盖多长？
- [ ] 是否存在**逆操作写不出来**的步骤？它们是否都在链路最末尾（或已被移出链路）？
- [ ] 同一实体是否存在多个写入者？若是，是否上了版本判定或冲突检测，而不是 LWW？
- [ ] 读侧能否回答「我现在读到的是哪个位点 / 落后多少」？没有这个数就无法给出新鲜度承诺。
- [ ] 若用了 Outbox，中继的滞后有多少？表是否按时间分区？清理是否会影响在线写入？
- [ ] 若用了 Event Sourcing，事件 schema 的兼容策略是什么？「删除类」合规请求怎么满足？
- [ ] 是否做过分区演练与协调者故障演练？结论是否写进了 Runbook？
- [ ] AI 链路上有没有非确定组件出现在重放路径上？模型输出是否已落为记录再复制？
- [ ] Agent 的状态是否可序列化？不可序列化的那部分（外部句柄、已发生的副作用）是否已拆到动作日志？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 不能读到旧值，数据能收进一个引擎 | 强一致（Global DB） | 协调者下沉进内核，崩溃恢复由内核负责；代价是覆盖范围限于该产品 |
| 跨异构资源、同城、低冲突 | 2PC / XA | 同步提交最简单；代价是锁持有到全局决议，且协调者恢复要自己兜 |
| 高冲突热点 | TCC | 锁下沉成业务预留，冲突转为可降级的预留失败；代价是三接口与三类边界 |
| 长链路、每步可补偿 | Saga | 分段本地事务不跨服务持锁；代价是补偿与对账两条链路必须长期维护 |
| 本地写入与对外事件要原子 | Outbox | 同一本地事务给出原子边界；代价是中继滞后与表增长成为新上限 |
| 需要审计与状态重算 | Event Sourcing（+CQRS） | 事实以追加保留，状态可重放；代价是读侧重写与事件 schema 长期兼容 |
| 可用性优先、无并发写 | 最终一致（AP） | 本地提交即返回；代价是读侧滞后不可观测，且「最终」没有时间承诺 |

> 本节小结：一致性模式的选择，最终由**「决定权放在哪一层、以及同一实体是否会出现并发写」**这两条约束决定。前者决定了故障恢复归谁、持锁多久、能用哪种算法；后者决定了「最终一致」是否可以不带版本判定。可补偿性、参与者规模与团队值班能力是在这两条确定之后才展开的次级约束——先定这两条，再谈 TCC 还是 Saga。
>
> 💡 **思考锚点**：拿你系统里冲突最贵的那条跨服务写路径，按 §3.6 报两个可观测量——热点行的并发请求数 ÷ 该行可用并发度、事务参与者数量的长尾落在哪一段？前者接近 1 说明持锁式必须换，后者若集中在长尾会把你推向 Saga；这两个数你现在读得出来吗，还是得先补观测？
