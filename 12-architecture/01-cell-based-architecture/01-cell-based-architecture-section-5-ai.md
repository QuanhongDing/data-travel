## 5. 前沿演进（AI 时代）

> 原 § 5 共 70 行、为方向清单（GPU 单元化 / 模型单元化 / Agent 单元化 / 向量检索单元化 / AI 辅助单元化决策，外加 RAG 单元化、2024 厂商进展与五条趋势），缺少机制与成熟度判断，重写为 ~285 行前沿评估。

### 5.1 先分清三类「前沿」

「AI 单元化」这个说法把**三件不同的事**捆在了一起，它们的问题类型完全不同：**其一，把推理服务按既有 Cell 部署**——这是部署问题，答案由主文件 §1.1 的四要素和 §7.3.1 的故障域直接给出；**其二，把 GPU 资源切成每 Cell 一份**——这是容量问题，答案是成本，因为算力不能像数据那样廉价地复制后静置；**其三，让有状态的 AI 组件（向量索引、Agent 状态）跟着 Cell 走**——这是数据归属问题，答案由 §7.3.2 的「全局写数据清单有多长」给出。原文件把三者写成同一张清单，读者很容易把「部署」读成「要买更多卡」，而这两件事的成本相差数倍（见 5.2.2 的推算：示例假设下是 6 倍，倍数随 Cell 数与真实峰值分布变化）。

本主题的机制判据在 §7.5 与 §7.6 里已经写定，本节不新造判据：**「推理要不要单元化」的判据是「推理是否依赖用户级状态」，不是「有没有 GPU」**——有状态的（用户上下文、个性化记忆、随用户切分的向量索引）跟着 Cell 走；无状态的推理副本按共享 GPU 池部署更划算，因为每 Cell 常备算力会让利用率下降（§7.6 的组合段）。本节 5.2 的四条全部按这条判据展开，凡是与它冲突的写法（例如「AI 推理必须单元化」），本节都会指出冲突在哪里。

第二个坑是**能力名、产品名与模式名的混淆**，这在 AI 硬件这一层尤其密集：`MIG` 是 NVIDIA 的 GPU 切分能力（随 A100 引入，官方文档给出实例数与显存切分方式），`cGPU`、`vGPU` 是容器 / 虚拟化层的另一类切分实现（书内 §4.3 记录的工具清单里把三者并列，但它们**不是同一层的东西，也不能互相替代**）；同理，「Cell」这个词在不同体系里指不同层次——AWS 白皮书里的 cell、Azure 的 Deployment Stamp、以及某些数据库中内部存储组织同名，**同名不等于同义**。遇到这类名词，本节只写能力与判定入口，不断言某产品支持某形态。

第三点要说在前面：原 §5.3 的厂商进展里有几条**缺少可核验出处**（阿里「三地五中心 + AI 推理单元化」、字节「GPU 池化利用率提升至 70%」、eBay「单元化支持 AI 搜索」、Google「Spanner Cell 模式」），本节对它们做降档处理——**不是因为它们不成立，而是因为原文件没有给出可核验的公告出处**。在拿不出出处的情况下，正确写法是给判定方法（去哪一份官方文档 / 哪一节里核），而不是断言结论。其中「AWS 2024 Cell-Based Architecture Reference」一条可核验入口明确：AWS Well-Architected 关于限制影响范围的白皮书（2023；书内 §7.3.1 已按此口径引用）。

第四点关于读表：**「级别」说的是能不能现在就规划，不是这件事重不重要**。GPU 池化与向量索引单元化都值得投入，但它们的顺序排在「把无状态推理挂进既有 Cell」之后——因为前者花的是钱（常备算力），后者花的是配置。

级别怎么定，本节用的判据与全书一致，三条全中才是 L1：**有正式 release note 或公开规范；有第三方（非厂商）公开生产案例；接口稳定**。只有厂商自有案例、或只在小规模被验证过是 L2；只有路线图、论文、演示是 L3。这三条要在本主题上落地有一个额外要求：**判据必须落到 Cell 这个单位上**——例如判断「GPU 切分能力是否可用于每 Cell 隔离」，看的不是「云上有没有切分产品」（有），而是「该切分能力的官方文档里有没有写清实例间的故障域与干扰」；判断「AI 调度是否可接管路由」，看的不是「有没有预测模型」（有），而是「有没有第三方公开的误切率」。**判据可核验，是本节与趋势清单的唯一区别。**

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按「无状态 / 算力 / 状态 / 决策」排列：原方向 2 的无状态部分独立成 5.2.1，原方向 1 的算力部分成 5.2.2，原方向 3 与 4 合并为 5.2.3（它们共用同一条判据——状态归属），原方向 5 与自平衡、AI 主导调度合并为 5.2.4。每条都写全「旧做法卡点 → 机制改变 → 得到 → 付出 → 证据 → 成熟度」六项，**只写收益不写代价的方向，在评审时应直接打回**——单元化领域里没有免费的隔离。

#### 5.2.1 无状态推理按既有 Cell 部署：它落在 L1，因为它根本不是新问题

- **旧做法与它的卡点**：原清单列出「每 Cell 独立模型副本 / 模型版本管理（按 Cell A/B）/ 模型降级链路」，把它们当作 AI 带来的新能力。真正的卡点在部署习惯上：**很多团队把推理服务当数据库一样供着**——单集群、大规格实例、人工扩缩，于是把一个无状态服务做成了有状态服务。后果是单元化的隔离被一个共享组件吃掉：所有 Cell 的请求都打到中心的推理集群，**Cell 边界只存在于部署图上，不存在于调用链路上**——这正是 §7.3.1 那条机制的实例：「给现有架构加副本不会改变爆炸半径，只改变同一半径内的存活概率」。
- **AI 改变了什么机制**：**只改变了被部署的对象，没有改变部署与路由机制**。健康探测、Cell 内自包含、按键路由、全链路染色、按 Cell 灰度与切流，这些从 2008 年以来的 Cell 实践里就有（主文件 §1.4 的时间线）。AI 带来的唯一新事实是：被部署的进程由制品（权重 + 配置）重建，**不持有请求级别的状态**——这一点恰好是「适合按 Cell 部署」的条件，而不是阻碍。
- **由此得到的**：**因为推理副本可由制品重建、且不依赖用户级状态，所以它天然适合挂进既有的 Cell 与路由，不必为 AI 单独设计一套单元化**。而且因为它无状态，同一个用户命中哪个 Cell 只影响延迟与就近性，不影响正确性——这让「按 Cell 灰度模型版本」成为可能：**因为路由是「一次决定、全链路遵守」（§7.3.3），所以按 Cell 切分的灰度可以把同一个用户固定在同一版本上，A/B 期间的答案口径不会在同一个人身上跳变**。降级链路同理，它落到既有部件上就是端点池 + 显式档位，而不是散在业务代码里的 `try/except`。
- **由此付出的**：四条真实代价：**其一，每 Cell 一份副本意味着同一份权重在 N 个 Cell 各占一份显存**，模型越大这笔占用越不可忽略（它是「按 Cell 部署」与「共享推理集群」之间唯一真正的取舍）；**其二，版本一致性成为新问题**——若 N 个 Cell 上的模型版本不同步，同一个用户在灰度期间会跨越版本，表现为「答案口径不一致」；**其三，染色泄漏会被 AI 放大**：不由用户请求发起但会写数据或产生副作用的入口（定时任务、消息消费、离线回灌、运维脚本，以及 **Agent 的工具调用**，§7.3.3 已把这一类列为重点检查对象）如果拿不到归属键，就会写到不属于它的 Cell 且不报错；**其四，降级后的答案不可比**——不同模型对同一提问的输出不具有可比性，降级必须按请求类型分档，而不是按「哪个模型还活着」选。
- **证据与来源**：机制侧【公开】：AWS Well-Architected 关于限制影响范围的白皮书（2023，书内 §7.3.1 引用）把 cell 定义为可独立失效的部署单元；AWS Builders' Library 的 *Static stability*（2021）要求故障切换依赖预置路由与容量。生产案例：【公开】主文件 §1.4 记录的时间线（eBay 2008 提出概念、阿里 2012 年起探索、2015 双 11 大规模应用、2018 三地五中心）与 [§6](01-cell-based-architecture-section-6-sec6.md) 的 1.1–1.4（阿里 / 美团 / 字节 / Netflix）。**可自行核验的判定方法**：列出所有「不由用户请求发起但会写数据」的入口，逐个检查它能否拿到归属键；再检查推理服务的调用链是否跨 Cell——**只要有一条链路跨 Cell，单元化对这条链路就是不生效的**。
- **成熟度**：**L1**。判据三条逐条可核验：① 机制有可点名的公开文档——AWS Well-Architected 白皮书 *Reducing Scope of Impact with Cell-Based Architecture*（2023）与 AWS Builders' Library 的 *Static stability using Availability Zones*（2021）；② 第三方生产案例见 § 6 的 1.1–1.4；③ 路由 / 染色 / 探切均为既有部件、接口稳定。机制本身 = 既有单元化机制的直接套用（主文件 §1.1、§7.3.1、§7.3.3），AI 带来的变化只是「多了一类无状态负载」。

同一个 Cell 里，不同请求的归属键并不相同，这张表决定了「谁落在哪」：

| 请求 / 入口 | 归属键 | 落在哪 | 拿不到归属键的后果 |
| --- | --- | --- | --- |
| 用户请求（账户 / 订单 / 推荐） | userId / orderId | 该用户的 Cell | —（有键，正常路由） |
| 推理请求（无状态） | 可无键，按就近与容量路由 | 任一可用 Cell 的副本 | 跨 Cell 调用增加，隔离折损 |
| 有状态推理（用户上下文 / 个性化） | userId | 该用户的 Cell | 状态与服务分处两地，延迟与一致性双输 |
| 定时任务 / 离线回灌 | 必须显式携带业务键 | 键所属 Cell | **静默错域**：写进了别人的 Cell，不报错 |
| Agent 的工具调用（§7.3.3） | 继承发起会话的归属键 | 会话所属 Cell | 静默错域，且比定时任务更难排查 |

这张表里最值得停一下的是最后两行：**它们的共同点是「不由用户请求发起」**，因此没有天然的归属键可带。传统单元化里这两行还比较少见，AI 让它们变多——Agent 会自主发起工具调用，而且可能一次会话里连发多次。**判据很简单：凡是不能回答「这条写入属于哪个键」的入口，都应视为染色泄漏点并补上键**，而不是先上线再看会不会出问题；静默错域的特点是**不报错、只在跨 Cell 一致性校验或对账时暴露**。

#### 5.2.2 GPU：容量不能复制，切分还会改变故障域

- **旧做法与它的卡点**：原清单写「GPU 池化（每 Cell 独立 GPU 池）」「MIG（A100 切分，每 Cell 独立 MIG 实例）」「GPU 弹性（基于推理流量的弹性调度）」。卡点是**成本函数的形态**：数据容灾的增量成本是存储与带宽，近似线性、可预算、可以长期静置；GPU 容灾与单元化的增量成本是**常驻闲置算力**——为了每个 Cell 都能独立承接，你必须在每个 Cell 常备产能，而它们平时不产生收益。§7.3.4 已经指出 Cell 数 N 同时决定爆炸半径与冗余成本，在 GPU 这一行**「冗余」的单价与「算力」的稀缺性叠加**，代价比数据层陡得多。
- **AI 改变了什么机制**：**把「复制」换成了「预留」**。数据可以廉价地异步复制一份放着；GPU 不行，别的 Cell 的卡不能在一秒内搬过来。于是「AI 单元化」的实质从「部署拓扑设计」变成了**容量经济学**：每 Cell 常备多少算力、切分到什么粒度、闲置的那部分谁来买单。MIG 这类切分能力改变的是**切分的粒度**（把一张卡切成多个隔离实例，官方文档给出实例数与显存切分方式），而不是这笔钱的总量。

```text
为什么"每 Cell 一套 GPU"要先算一遍（示例推算，假设可替换）
  假设：12 个 Cell（主文件 §1.1 的对比表把 Cell 数记在 12–100 区间，
        下沿 12 与 §1.4 记的「2015 双 11 首次大规模应用（12 个 Cell）」一致）
        每个 Cell 常备 1 台 8 卡推理机
  → 常备算力 = 12 × 8 = 96 张卡                【推算：Cell 数 × 每 Cell 卡数】
  再假设：按真实流量统计，只有 2 个 Cell 的负载
        需要这个规模（其余 Cell 的峰值远低于常备）
  → 有效利用 = 2 × 8 = 16 张卡，其余 80 张常年闲置
  → 常备成本约为共享池方案的 96 ÷ 16 = 6 倍    【推算：常备卡数 ÷ 有效卡数】
  ────────────────────────────────────────────────
  用法：把上面三个假设换成你自己的数（Cell 数、每 Cell 卡数、
        真实峰值分布），得到的倍数就是"每 Cell 常备"的价钱；
        它与"单元化能不能做到"无关，只与"值不值得"有关
```

- **由此得到的**：**因为算力不可复制、且切分只能改变粒度不能增加总量，所以 AI 单元化的正确形态是「有状态推理按 Cell 预留、无状态推理共享池」**——这与 §7.5 给出的判据（看是否依赖用户级状态）完全一致，也与 §7.6 的选型矩阵与组合结论一致（每 Cell 预留 GPU 会让利用率下降，**所以 AI 单元化只在延迟与合规要求足够强时才做**）。由此还导出一个容易被忽略的收益：**MIG 一类切分能力让「常备」这件事变小**——不必每 Cell 一台整机，可以按实例粒度预留，代价见下一项。
- **由此付出的**：**其一，切分改变故障域，而不是只改变粒度**：一张卡被切成多个隔离实例后，**卡级的物理故障会同时打掉这张卡上的所有实例**——如果这些实例分属不同 Cell，一次卡故障就会同时命中多个 Cell，爆炸半径从 1/N 变成「同一张卡上的 Cell 数 / N」，**隔离看起来更细了，实际共享的故障源反而变多了**；**其二，切分带来性能隔离的不确定性**：共享显存带宽与功耗预算的实例之间存在相互影响，公开材料给的是隔离等级，不是「互不影响」的保证，必须用压测确认；**其三，每 Cell 常备的钱**（上方推算）与「多活本来就要常备一份」的代价会重复计算——若已经为多活备了容量，再按单元化备一次就是双份；**其四，GPU 弹性调度的新失败模式**：调度器本身成为全局共享组件（§7.3.1），配额与库存是外部状态，「以为能拉起」与「真的拉起了」之间隔着一次配额校验，而它在故障当天最容易失败。
- **证据与来源**：MIG 是 NVIDIA 官方文档记录的 GPU 切分能力（随 A100 引入，官方用户指南给出实例数与显存切分方式）【公开】；容器级 GPU 切分（`cGPU` / `vGPU` 一类）见书内 §4.3 的工具清单，属厂商能力，**本节不对其隔离语义做断言**——判定方法是查该能力的官方文档里「故障域」「实例数」「显存与算力切分比例」三节是否齐备。显存与并发的关系有公开论文可核验【公开】：Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention", SOSP 2023——它解释了为什么「少一张卡」不是「慢一点」而是「请求排队甚至 OOM」。**「每 Cell 独立 GPU 池 + 跨 Cell 弹性」没有第三方公开的实测数据**，故本方向判 L2。
- **成熟度**：**L2**。判据：MIG 等切分能力是 GA 的产品能力、机制可核验（NVIDIA 官方文档，A100 起），但「每 Cell 独立池 + 跨 Cell 弹性调度」缺第三方实测，且切分带来的故障域重叠需要自己测；判定方法是**在你的环境里做两件事**——把常备成本按上方推算算一遍，再对切分实例做一次相互干扰的压测（一个实例打满时，同卡其他实例的 P99 变化多少）。

「共享池」与「每 Cell 独立池」的差别不在性能，而在四个不同维度上各让一步：

| 维度 | 共享 GPU 池（无状态推理） | 每 Cell 独立池（有状态推理 / 合规要求） |
| --- | --- | --- |
| 爆炸半径 | 池子整体成为一个共享故障域（§7.3.1 意义上的共同组件） | 单 Cell 故障不扩散，隔离等级提升 |
| 成本形态 | 按峰值预留一份，利用率相对高 | 按 Cell 数预留 N 份，常备闲置（上方推算给出倍数） |
| 弹性 | 池内调度、扩容空间大 | 单 Cell 内弹性受限，跨 Cell 调动要动路由与数据 |
| 隔离确定性 | 依赖调度与限流（软件层保证） | 由部署边界保证（结构层保证），不依赖调度正确性 |

这张表解释了为什么「AI 单元化」不能一句话回答：**它换掉的是「依赖软件层保证隔离」与「依赖结构保证隔离」之间的选择，而这两者的成本相差数倍**（按 5.2.2 的示例假设是 6 倍，不是「差一个量级」这种笼统说法）。有状态推理、合规要求（数据不得离开某地域 / 某单元）应当选右边；纯推理算力最大化利用应当选左边。**同一套系统里两种都会存在**，这也是 §7.6 的组合条目存在的理由。

#### 5.2.3 有状态 AI：向量索引跟着 Cell 走，Agent 状态先别跨 Cell

- **旧做法与它的卡点**：原清单列了「向量索引分片（每 Cell 一份）」「跨 Cell 向量检索容灾」「本地优先」，以及「每 Cell 独立 Agent 集群 / 工具独立 / 状态独立」。卡点在于**这两种状态的「可重建性」完全不同，却被写成同一种处置方式**：向量索引是**可从原件 + 固定模型版本重建的制品**，丢了可以重算；Agent 的状态（会话上下文、已执行动作、待办计划）**不是制品，是一次运行的过程**，丢了只能重放，重放还可能产生副作用（重复下单、重复发通知）。把它们都写成「每 Cell 一份」，等于给可重算的东西付数据的钱，同时给不可重算的东西留下没有恢复方案的风险。
- **AI 改变了什么机制**：**它让「状态」这件事多了一种形态——由模型版本决定的派生数据**。传统单元化里，状态要么是可切的业务数据（订单、账户），要么是无状态的计算；向量索引介于两者之间：**它同时是数据（要版本化、要能追溯用哪个模型版本生成）与计算产物（可重建，但重建要花时间和算力）**。而 Agent 状态是第三种：**有副作用的过程状态**，它的恢复语义与传统状态机一致（幂等 + 去重），而这一点与 AI 无关，是既有工程问题。
- **由此得到的**：**因为向量索引可由原件 + 固定模型版本重建，所以它的单元化形态应当是「本地优先 + 可重建 + 版本可追溯」，而不是「跨 Cell 强同步」**——这与 §7.3.2 的处置逻辑一致：先问「它能否被一个业务键定位、是否只读」，落在「全局且可写」象限的越少越好。落到具体设计上：**查询优先命中本地 Cell 的索引（省跨域延迟），本地缺片或故障时降级为「回源重算」或「跨 Cell 读副本」，而不是要求所有 Cell 的索引实时一致**。Agent 状态则按既有做法处置：**归属键跟着会话走、写入必须幂等、跨 Cell 只做异步补偿**。
- **由此付出的**：**其一，重建时间随语料规模增长并占用算力**，而故障当天你可能既缺检索又缺算力（算力恰是 5.2.2 里最贵的那一项，两笔代价会叠加）；**其二，重建的确定性依赖模型版本不漂移**——如果 Embedding 服务用「最新版本」这种浮动引用，重建出的索引与旧查询不可比，表现为「恢复之后检索质量莫名下降」，而没有任何指标会报错；**其三，本地优先改变了召回分布**：同一个问题在不同 Cell 可能命中不同结果（因为各 Cell 索引的版本或覆盖范围不同），这件事必须写进 SLA 而不是藏在实现里；**其四，Agent 状态跨 Cell 迁移会引入重复副作用**，且它的排查成本高于传统状态机——因为「为什么重复执行」要区分是重放、是模型重试，还是工具调用被染色泄漏到了另一个 Cell（§7.3.3 的静默错域在 Agent 场景里的表现形式）。
- **证据与来源**：「向量索引可重建、原件与索引分离」是主流检索工程的通行做法，可自行核验：查你所用的向量库 release note 里「快照 / 备份 / 恢复」与「跨集群复制」分别是不是正式条目、一致性口径是同步还是异步。幂等与去重是分布式系统的既有要求（与主文件 §2.3 的数据同步方法一致）。**「每 Cell 独立 Agent 集群 + 状态独立」没有可核验的第三方公开生产案例**，故该子项判 L3——**缺失也是一种证据**。
- **成熟度**：向量索引单元化 **L2**（机制可立即实施，但「跨 Cell 强同步」必须逐产品核验，且没有第三方公开的全链路实测）；Agent 集群与状态单元化 **L3**（缺生产案例，且它把一个新的状态迁移问题引入到已有的故障面上）。

演练里必须真的量出下面三个数，否则「索引可重建」只是一句设计意图：**全量重建耗时**（重建要多久、占多少算力）、**重建后的召回一致性**（同一组固定查询下，重建前后 Top-K 的重叠程度）、**跨 Cell 读取的比例与延迟**（本地优先到底省下了什么）。这三个数同时也是「要不要付跨 Cell 复制的钱」的判据——重建只要几分钟就把复制省下，要几小时就重新评估，**按实测数决定，而不是按「高可用听起来更稳」决定**。

三类「状态」在单元化里的处置完全不同，混为一谈就会出现「付了数据的钱、留下没有恢复方案的风险」：

| 状态类型 | 是否可重建 | 是否有副作用 | 处置方式 | 恢复语义 |
| --- | --- | --- | --- | --- |
| 业务数据（订单 / 账户） | 否（唯一） | 有 | 按业务键切分到 Cell，每键单写入者（§7.3.2） | 备份 / 多副本恢复 |
| 向量索引、GraphRAG 索引（派生数据） | **是**（原件 + 固定模型版本） | 无 | 本地优先 + 快照版本化 + 可重建；跨 Cell 只读复制按需 | 重建（耗时随语料规模增长） |
| Agent 状态（会话 / 计划 / 已执行动作） | 否（过程状态） | **有**（工具调用会产生现实影响） | 归属键跟会话走 + 幂等键 + 去重；跨 Cell 只做异步补偿 | 重放（必须幂等，否则重复副作用） |

这张表里最容易看错的是第二行与第三行：**向量索引可以「不怕丢」，Agent 状态不能「随便重放」**。前者的正确性是「重建后与旧查询可比」，后者的正确性是「重放不产生第二次副作用」——两个完全不同的验收标准，而它们在原清单里被写成了同一句「每 Cell 一份、状态独立」。

#### 5.2.4 AI 辅助单元化决策：它要的不是算力，是权限

- **旧做法与它的卡点**：原方向 5 列了「AI Cell 调度（预测流量、自动调度资源）」「AI 故障预测」「AI 容量优化」，原 §5.4 又补了「Self-Balancing Cell」与「AI 主导的 Cell 调度」。卡点不在算法，而在**这三件事各自都要动一个全局的东西**：调度要改路由表、容量优化要改配额、故障预测要先说服人切流。而 §7.3.1 的机制说得很清楚——**管控面（路由、配置下发、发布系统）本身就是全局共享组件，故障时会带着所有 Cell 一起故障**。把决策权交给一个自动系统，等于往共同故障源里再放一个决策者。
- **AI 改变了什么机制**：**它试图把「决策」段从人换成统计判断**，这是本方向唯一真实的机制变化，也是它与「换前端」的区别。但它同时引入了两个固有权衡：**误报与漏报的代价不对称**（容灾里误报 = 自伤，把健康 Cell 的流量切走；漏报 = 延长故障时长），以及**决策宽度的不可分割性**（切流这个动作本身无法只做一半）。
- **由此得到的**：**因为决策段的瓶颈是「谁负责」而不是「准不准」，所以 AI 在当前阶段最可能落地的位置是「建议与验证」而不是「决定」**：预测容量需求、给出扩缩建议、在演练中自动核对是否真的达成了爆炸半径与切换时长目标——这些动作误判代价低（错了只需人复核）、不触碰路由表；而「AI 自动切流」要成真，先要解决的是误切之后谁签字。
- **由此付出的**：**其一，预测性能力制造新的告警面**，而单元化最依赖的恰恰是「告警响了就有人动」，误报会稀释这份信任；**其二，模型给出的调度建议本身依赖流量预测，而流量预测在故障当天的准确率最低**（这正是需要它的时刻）；**其三，自动化把责任链拉长**——「是模型建议切的」不能成为免责理由，因此它与审计要求天然冲突；**其四，Self-Balancing 的收益容易被高估**：Cell 之间的负载再平衡要付出路由表变更与可能的数据迁移（§7.3.3 已指出切分键变更的代价），而「不平衡」很多时候不是调度问题，是分片键选错了。
- **证据与来源**：**本方向没有公开可核验的第三方生产案例，也没有误切率 / 预测准确率的公开评测**。可核验的只有机制侧的既有事实：共享组件清单决定真实爆炸半径（§7.3.1）；动态扩缩与故障切流的既有做法见主文件 §2.3；演练作为验证手段的公开实践见 Netflix 开源 Chaos Monkey（Netflix 技术博客，2011）【公开】；故障切换应依赖预置路由与容量而不是运行时推导（AWS Builders' Library, *Static stability*, 2021）【公开】——后者正是「自动调度」与「静态稳定」冲突的公开依据。
- **成熟度**：**L3**。判据：公开材料以厂商博客与产品公告为主，缺第三方生产案例与量化指标；判定方法是去找**厂商之外**的、含误切次数或预测误报率的公开数据——只看演示视频不算证据。有一个只靠读文档得不到的判定动作：**在下一次演练复盘里问一句「如果这次交给模型决定，它会在哪一步切错、切错之后谁先发现」**；答不上来说明连评估数据都不存在，此时任何投入都是无的放矢。

「建议与验证」具体指哪三件事，值得写清楚——它们的共同点是**都不直接作用于生产流量**：

- **容量建议**：把流量预测转成「下个周期每个 Cell 需要多少资源」，交给容量评审会确认；产出是建议书，不是配额变更。
- **演练核对**：自动比对演练结果与目标（实际爆炸半径、切换时长、错误预算消耗），把差异列出来；产出是复盘材料。
- **缺口发现**：从历史故障与变更记录里找出「共享组件清单中长期没被检查的项」（§7.3.1 的判定方法需要持续维护）；产出是待办清单。

三件事的产出都是文档与报告，**错了只需人复核一次**；而它们一旦被允许直接写路由表或改配额，误判的代价就变成了一次自伤——这就是本节把「建议与验证」与「自动决策」分开的理由，而不是「模型还不够强」。

### 5.3 与本主题既有栈的接口在哪

「AI 时代的单元化」与既有单元化不是「结合」关系，而是**挂载**关系：推理副本、向量索引、Agent 状态三类对象各自挂到既有的哪一个部件上、交出去什么形态、失败时谁负责。「结合」式写法会省掉三件必须回答的事，而这三件事恰好是评审时最容易出问题的地方。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 推理副本 ↔ Cell 自包含部署（主文件 §1.1、[§3](01-cell-based-architecture-section-3-sec3.md) 模式 6） | 无状态进程按 Cell 部署，权重从制品加载；请求按路由层结果落在某个 Cell | 服务方保证副本可重建；SRE 负责探切与切流决策 | 既有机制的直接套用（L1） |
| 模型版本 ↔ 按 Cell 灰度（主文件 §1.3、§7.3.3） | 版本以「Cell 集合」为单位推进；同一归属键在灰度期内固定在同一版本 | 发布方；回滚的优先级高于灰度完成度 | 既有机制（L1） |
| 有状态推理 / 向量索引 ↔ 数据切分键（§7.3.2） | 随用户切分的索引跟着 Cell；全局只读索引按副本复制；写路径只走归属 Cell | 数据归属方；跨 Cell 只读失败时降级为本地重建或返回空 | 需逐产品核验「跨集群复制」是否正式条目（L2） |
| 向量索引 ↔ 制品与版本（与 Ch12 §07 容灾同源） | 交出去的三件套：原件、Embedding 模型版本号、索引快照；三者版本必须同时可查 | 索引侧负责「可重建 + 版本可追溯」；恢复方承担重建耗时 | 「可重建」现在就能做；「跨 Cell 强同步」须逐产品核验（L2） |
| Agent 工具调用 ↔ 全链路染色（§7.3.3） | 会话归属键必须显式透传到每一次工具调用；工具侧写入必须带键 | 会话归属方；工具侧不得自行选择 Cell | 需要新增透传约定，不是既有染色的复用（L3） |
| GPU 容量 ↔ 容量模型（§7.3.4、§7.6） | 不是数据复制而是容量预留：接口是配额与实例库存；共享池按可用量排队 | 平台方保证预留有效；业务方给出降级承诺（排队 / 降档） | 云上是 GA 能力；「每 Cell 独立池」缺第三方实测（L2） |
| AI 调度 / 自平衡 ↔ 管控面（§7.3.1） | **只读**指标与演练数据、**只写**建议与报告，不直连路由表 | 人工确认者；模型不承担切流责任 | 概念与产品公告期，不要在架构里预留假设（L3） |
| 单元化 ↔ 混沌演练与可观测（Ch12 §06 混沌工程；可观测侧的接口要求见主文件 §1.3） | 实验要能按 Cell 注入，把爆炸半径限制在 1/N；监控要能按 Cell 维度切分——**后者是对可观测体系提出的要求，不是现成能力**（可观测章讲的是采集 / 分级 / 归因机制，尚未按 Cell 维度组织）；GPU 指标走既有采集通道（NVIDIA DCGM 一类） | 平台方；单 Cell 故障的发现与定位由值班承担 | 混沌侧是既有技术的复用（L1）；可观测侧是把 Cell 作为既有指标 / 日志 / Trace 的一个维度，属配置与规范，不需要新建系统 |

```text
请求穿过边界的形态（谁把什么交给谁）

  客户端 ──► 路由层（按归属键决定 Cell，一次决定全程遵守）
                │  交接物：请求 + 染色（键）
                ▼
            Cell 内应用 ──► 推理副本（本 Cell，无状态）
                │             └─ 交接物：prompt + 模型版本标识
                │                失败：本 Cell 内换副本 / 降档，不跨 Cell
                ▼
            本地向量索引（本 Cell）
                └─ 交接物：Top-K + 索引版本号 + Embedding 模型版本
                   失败：本地缺片 → 回源重算，或返回空（不返回过期结果）
            Agent 会话 ──► 工具调用（必须携带会话归属键）
                └─ 交接物：会话键 + 幂等键
                   失败：无键则拒绝执行，不允许"就近挑一个 Cell"
  ────────────────────────────────────────────────
  注：三条边界的共同点——把「失败时的处置形态」写进接口契约，
      留给实现去猜的部分，在故障当天一定猜错
```

一句话概括这三条边界：**AI 没有新增调用关系，只新增了三种需要显式携带的东西**——模型版本标识（决定答案口径）、索引与 Embedding 的版本号（决定重建可比性）、会话归属键（决定 Agent 的写入落在哪个 Cell）。单元化做得好不好，看这三样东西在故障当天是否齐全，而不看有没有 AI 组件。

这三条边界还有一个共同的现状：**其中两条不需要新建系统（推理挂进既有 Cell、版本按 Cell 灰度），只有第三条（Agent 工具调用的归属键透传）需要新增一个约定**。这也解释了本主题的分级结果——唯一落在 L1 的方向是「复用既有部件」的那一条，而需要新增约定的那一条停在 L3，因为它必须先回答「会话与工具之间的键由谁生成、超时重试时如何保持一致」，这不是配置问题而是协议问题。

### 5.4 公开进展与文献

分三类列，每条给出可核验的出处；**宁少勿假**，核不到的不列。

**标准、白皮书与官方文档（可核验的判定入口）**

- AWS Well-Architected 白皮书 *Reducing Scope of Impact with Cell-Based Architecture*（2023；书内 §7.3.1 已按此口径引用）——把 cell 定义为可独立失效的部署单元，并把目标写成「限制影响范围」。它同时是本节判 L1 的机制来源。
- Azure Architecture Center 的 *Deployment Stamps pattern*（公开文档；该页由微软持续更新、不绑定单一年份，核验时请以 Azure 架构中心当前版本为准）——同一思路的另一套命名；读它有助于区分「模式名」与「实现」。
- AWS Builders' Library：*Shuffle Sharding*（2019）与 *Static stability using Availability Zones*（2021）——前者说明「防叠加故障」靠子集化而不是更多副本，后者说明故障切换应依赖**预置**的路由与容量而不是运行时扩容，是判断「AI 弹性调度」是否可靠时的公开依据。
- eBay 工程团队关于 Cell-Based Architecture 的公开文章（2008 年前后提出；书内 [§8](01-cell-based-architecture-section-8-sec8.md) 的来源清单收录）——该模式的原始工程定义。
- NVIDIA 的 MIG 用户指南（随 A100 于 2020 年引入）与 NVIDIA DCGM（数据中心 GPU 管理，书内 [§8](01-cell-based-architecture-section-8-sec8.md) 亦把 DCGM 列为 GPU 指标采集入口；它按版本持续发布，具体版本号与发布日期请在 NVIDIA 官方文档库按该名称核验）——GPU 切分能力与 GPU 指标采集的官方入口；**判断某个切分能力是否真的做到隔离，看它文档里的「实例数 / 显存与算力切分比例 / 故障域」三节，而不是看宣传页**。

**论文**

- Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention", SOSP 2023——显存与并发的关系，是「少一张卡不是慢一点，而是请求排队甚至 OOM」这一判断的公开依据。
- Beyer et al., *Site Reliability Engineering*（O'Reilly, 2016，Google 官方出版并公开在线；书内 [§7](01-cell-based-architecture-section-7-sec7.md) 引用其中的错误预算一章）——「用可承受的不可用时间反推容量与切换速度」的方法论，也是本节区分「自动化」与「可归责的自动化」的依据。

**第三方生产案例**

- 主文件 §1.4 记录的演进时间线与 [§6](01-cell-based-architecture-section-6-sec6.md) 的 1.1–1.4：阿里双 11、美团外卖、字节抖音、Netflix 多 Region——四者都是长期运行的单元化生产系统，是本节 L1 判据的第②条。**本节不转述其中的运行指标**（峰值 QPS、成功率、爆炸半径百分比属于一手材料的口径，转述会丢失前提，[§7.3.4](01-cell-based-architecture-section-7-sec7.md) 已按此处理）；**Cell 数是个例外**：它只在 5.2.2 的推算里作为可替换的假设量出现（取值为主文件 §1.1 所记区间 12–100 的下沿 12），换成你自己的数才成立。
- 说明：本主题下**未找到**「AI 主导 Cell 调度」「跨云 Cell」「每 Cell 独立 Agent 集群」的第三方公开生产案例。这一栏的空白，正是 5.2.4 与 5.2.3 判 L3 的依据。

**怎么用这份清单**：它不是「读白皮书就能上生产」的路径，而是一组**判定入口**。遇到任何「某产品支持 AI 推理单元化 / GPU 弹性隔离」的说法，先按上面三类判断它的出处类型——是标准与白皮书（说明机制有共识）、是官方文档里的正式条目（说明能力存在）、还是产品页与演示（说明有人做出来了）——三者的证据强度差一个量级，而这正是 5.1 表里 L3 / L2 / L1 的分界。**清单短不是资料少，是合格证据少。**

最后补一句这份清单**刻意不列**的东西：本节没有收录任何「GPU 利用率提升到 X%」「切换时间缩短到 X 秒」这类数字，也没有收录任何「某产品支持 AI 推理单元化」的能力断言。原因相同——**这类说法缺的是条件限定**：利用率的分母是什么、切换时间的起点与终点分别在哪、隔离是结构保证还是软件保证，三项没写清的指标，读起来像事实，实际不可复现。本节的做法是把它们换成判定入口（查哪一节文档、量哪两个数），读者自己去核——**核得出来的才算证据，核不出来的只是宣传。**

### 5.5 被过度宣传的部分

下面三条不是「唱反调」，而是把**被宣传的能力**与**公开证据支持的能力**分开写。判断标准固定：宣传句里有没有可核验的条件（故障域、利用率口径、误切率）——没有的，就归入下面三条。

**「AI 推理负载必须单元化」**——单元化的判据是**状态归属**，不是负载类型：依赖用户级状态的推理（个性化上下文、随用户切分的向量索引）跟着 Cell 走；不依赖的应当按 §7.6 的组合结论走共享 GPU 池，并在 Cell 内只保留无状态副本。**为什么会这样**：这句话把两件事混成了一件——「隔离是好的」与「隔离是免费的」。每 Cell 常备算力的代价是常驻闲置产能（5.2.2 的推算给出的是倍数级差异），而它的收益只有在延迟或合规确实要求「推理不出 Cell」时才成立。**它什么时候才会成真**：出现含「每 Cell 常备算力的成本与利用率」的第三方公开数据，并且业务侧的延迟或合规约束被写成了可验收的指标（例如「推理不得跨地域」）——两条都有，才值得按 Cell 常备。

**「GPU 池化能把利用率提到 X%」**——利用率没有统一定义：按**卡时**（有多少卡在跑）、按 **SM 占用**、还是按**显存占用**，同一套系统能算出三个很不一样的数；而池化收益与「故障时能不能切」是一对张力——**池子越大，池子本身作为共享组件的爆炸半径越大**（§7.3.1）。**为什么会这样**：池化的分子是"实际用掉的算力"，分母是"为峰值预留的算力"，而峰值分布与业务形态强相关；换一套业务，同一个百分比就不成立。**它什么时候才会成真**：出现带口径（按卡时还是按 SM）、带负载类型（离线批 / 在线推理）、带峰值分布的第三方公开数据；在此之前，正确做法是**自己量三个数**——卡时利用率、显存占用率、以及池子故障时的可切容量。

**「AI 能自动调度 Cell / 自动切流」**——自动化真正能拿走的是「探测」与「执行」两段，而「决策」段的障碍是权限与责任，不是算法。**为什么会这样**：切流这个动作没有中间态（切了一半更糟），而它作用在**全局的**管控面上（§7.3.1：管控面故障时所有 Cell 一起故障）——把决策权交给模型，等于往共同故障源里放一个新的决策者；此外，调度最需要的流量预测，恰恰在故障当天准确率最低。**它什么时候才会成真**：出现可归责的自动切流机制（误切可被追溯与归责）与公开的误切次数 / 误切率，并被审计体系接受；在此之前，AI 在单元化里的合理位置是**建议与演练验证**（自动核对是否真的达成了爆炸半径与切换时长目标），而不是握住路由表。

这三条的共同结构是：**被宣传的能力都指向「自动与全局」，而公开证据支持的都停在「局部与建议」**。所以在评审任何 AI 单元化方案时先问一句「它写的是哪张表」——写建议与报告表可以接，写路由表的现在不要接。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 「AI-Native Cell」这个提法会被拆掉，回归为两件既有事的组合：无状态推理挂进既有 Cell，有状态 AI 按状态归属切分 | 行业不再单独讨论该提法，而是把它并入标准架构白皮书的 workload 章节（推理服务 = 无状态服务的一个 workload 类型）；「按 Cell 单元化 AI」的说法从架构图与产品页上消失 | 出现独立的「AI 原生单元化」标准或产品品类，并被广泛采用（含第三方生产案例） |
| AI 在单元化里的落点会先在「建议与演练验证」，而不是接管路由表（Self-Balancing 亦然） | 出现自动比对演练结果与爆炸半径 / 切换时长目标的产品或内部工具，并有厂商之外的公开实践；出现「调度建议采纳率」这类指标 | 出现自动改路由表的商用能力并公开误切率，且审计体系接受由它触发切流 |
| 边缘 Cell 会以「下沉的缓存 + 轻量推理」形态出现，而不是完整单元化 Cell | 边缘节点上出现可独立失效的推理与缓存子集，并公开其故障隔离与配置下发方案 | 边缘侧长期只做 CDN 与静态缓存（书内 §6 案例 1.4 的 Open Connect 就属此类），推理始终留在中心 |
| 跨云 Cell 在受监管行业之外难以成为主流 | 多年后跨云单元化的公开案例仍集中在金融 / 政企（由双供应商合规要求驱动） | 出现大量互联网公司跨云单元化的公开架构，且披露了管控面、网络与一致性的口径 |

写这四条时的共同约定：**信号必须是外部可观察的**（出现在白皮书 / 官方文档 / release note / 公开案例里），而不是「我觉得会」。凡写不出证伪信号的判断，本节不写——它没有信息量（「未来 AI 原生」这类句子永远正确，因而无法在评审会上当判据用）。另外注意这四条里没有「Cell 会被 AI 取代」这一条：**Cell 解决的故障域问题（共享组件宽度决定爆炸半径）与 AI 无关，AI 只是给它增加了一类负载和一类状态**。

### 5.7 给架构师的行动建议

下表按「你的处境」分行而不是按技术分行：同一项技术在不同处境下的正确动作完全不同——已有单元化体系的团队要做的是「把推理挂上去、把染色补全」，还在单体阶段的团队要做的是「先别谈 AI 单元化」。

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有单元化体系 | 把推理副本挂进已有 Cell 与路由；用 §7.3.3 的判定方法列出染色泄漏点（定时任务、消息消费、离线回灌、运维脚本、Agent 工具调用）并逐个补归属键 | 观察跨 Cell 调用的比例与尾延迟——比例上升说明推理在往中心退 | **不要为 AI 单独设计一套单元化**；不要让推理集群成为所有 Cell 的共同依赖 |
| 刚开始做单元化 | 先按主文件 §1.1 定切分键与 Cell 数，再问「AI 部分的增量是什么」 | 观察共享组件清单是否在收敛（§7.3.1 的判定方法） | 不要在切分键未定之前讨论「AI Cell」；不要承诺推理不跨 Cell 而架构上做不到的事 |
| 有 GPU 集群、正在做多 Cell | 先算一遍「每 Cell 常备 vs 共享池」的倍数（5.2.2 的推算模板），再决定是否切分；对切分实例做相互干扰压测 | 观察卡时利用率与显存占用率，以及池子自身故障时的可切容量 | 不要在没有口径的情况下引用任何 GPU 利用率数字；不要把在线关键推理压在共享池的单一故障域上 |
| 自建 RAG / 向量检索 | 原件 + Embedding 模型版本 + 索引快照三者一起版本化；演练里真的重建一次并记耗时 | 观察所用向量库 release note 里「跨集群复制」是否为正式条目及其一致性口径 | 不要为「索引跨 Cell 强同步」提前买单；不要让 Embedding 服务用浮动版本引用 |
| 已在做 Agent | 把会话归属键透传到每一次工具调用，并给工具写入加幂等键 | 观察是否出现「同一动作被执行两次」或「写到非归属 Cell」的记录 | 不要为 Agent 单独建 Cell；不要让工具调用自行选择 Cell（就近挑一个是静默错域的常见起点） |
| 受监管行业（金融 / 政企） | 把演练做成可举证的记录：谁在何时切了哪些 Cell、达成了什么指标 | 观察监管或行业规范是否开始要求「自动化切换的可追溯性」 | 不要用 AI 生成的 Runbook 直接进应急流程而不经演练验证；不要把跨云当作合规到位的证明 |
| 想上 AI 容量预测 / 自平衡 | 先把它限定在「只读指标 + 只写建议」，并定义建议采纳的判定人 | 观察建议采纳率与预测误报率；两者都没有记录说明还不到引入价值 | **不要给模型任何写路由表或改配额的权限**；不要把调度当作分片键选错的解药 |
| 正在做多 Region 与异地多活 | 先按 §7.3.2 把「全局且可写」的表数清楚，再谈 AI 负载放在哪一层 | 观察全局写数据是否在减少；它每多一项，能达到的隔离等级就矮一级 | 不要把 AI 推理放进「多地可写」的路径；不要用跨云掩盖一致性口径没定清的问题 |

「明确不要做」这一列的共同逻辑是：**这些动作的代价是确定的（常备算力、新组件、可回滚性），而它们的收益依赖一个尚未成立的假设**（AI 负载必须独立单元化 / 容量随时能拉起 / 模型能比人更快决定切流）。等到假设被 5.6 里的信号证实再投入，损失的只是时间，不是钱。

**如果你只能做一件事**：把 §7.3.3 的染色泄漏点清单在本季度跑一遍，并把推理服务与向量索引按状态归属重新分类一次（依赖用户级状态 → 跟 Cell 走；不依赖 → 共享池）。这一件事同时决定三件事：爆炸半径是否真的缩小、GPU 的钱是否花在必要处（5.2.2）、以及 Agent 的写入会不会静默落到别的 Cell（5.2.3）。**它不依赖任何 AI 组件，所以什么时候做都不亏。**

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**单元化的对象与状态形态**——它给单元化增加了两类新东西：**由制品重建、占用稀缺算力的无状态推理副本**，以及**由模型版本决定、可重建但重建要花算力与时间的派生数据（向量索引）**；再加上一类有副作用的过程状态（Agent 状态）。**它没有改变**的是单元化的原理：故障域由**共享组件宽度**决定（§7.3.1）、切分的前提是**每个键只有一个写入者**（§7.3.2）、路由是**一次决定全链路遵守**（§7.3.3）、Cell 数 N 同时决定爆炸半径与冗余成本（§7.3.4）——这四条在 AI 面前一字未改。
>
> 因此本主题的分级结果几乎全由「成本与证据」决定，而不是由机制决定：**把无状态推理挂进既有 Cell 直接落到 L1（机制是既有的）；所有与「每 Cell 常备算力」相关的停在 L2（花的是钱，缺的是实测）；所有与「决策权与责任归属」相关的停在 L3（要的是权限，不是模型）。**
>
> 判断本主题下任何新提法的快捷方式：**它花的是配置、是钱，还是权限？** 花配置的（推理挂进 Cell、补染色、按 Cell 灰度）现在就能做；花钱的（每 Cell GPU、索引复制）要先算账；要权限的（自动切流、自动调度）现在还不成立。
>
