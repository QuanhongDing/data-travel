## 7. 与其他方法对比

单体 / 微服务 / 异地多活 / 单元化并不是同一条轴上的四个档位：**微服务是应用切分粒度**，**异地多活是部署拓扑**，**单元化是「数据归属 + 路由 + 自包含部署」的复合体**，**单体是它们的共同基线**。本章按四个机制维度展开——**故障域边界**、**数据归属与切分键**、**路由与染色**、**容量模型**——而不是按「可用性 / 扩展性 / 复杂度 / 资源成本」逐列打分。

### 7.1 先立判据：为什么打分表会误导

第一个问题是**把不同层的对象塞进同一张表**：微服务回答的是「应用按什么切」，异地多活回答的是「部署在几个地理域、是否同时写」，单元化回答的是「请求与数据按哪个键归属、每份数据有几个写入者」，单体是不做任何切分的基线。把它们逐格打分，等于把「要不要拆服务」「要不要多地域」「数据按谁切」三个独立问题压成一个「推荐度」，读者的下一步动作仍然无从下手。

第二个问题是**同一维度在不同场景下的权重方向相反**。对内部管理系统，年停机预算可能是数小时，此时微服务 + 同城双活已经足够，单元化带来的运维对象膨胀是纯负担；对支付与账务链路，**一次数据错乱（重复扣款、账目不平）的代价远高于一小时的不可用**——正确性权重压倒可用性，此时正确的选择恰恰是「把该链路收进单个故障域」，与「可用性更高」的方向相反（见 §7.3.2）。

第三个问题是**把「可用性 5 分」当成可以直取的收益**。可用性目标对应的是停机预算，而预算是**量级跳变**的：99.9% ≈ 8.8 小时/年，99.99% ≈ 53 分钟/年，99.999% ≈ 5.3 分钟/年（【推算】，按 365 天 = 525,600 分钟换算的算术值）。每多一个 9，预算降一个数量级，而实现它通常要求「把故障域切小」外加「无跨域同步依赖」——这两件事都是结构性的，不是调优出来的。

第四个问题是**能力边界没说清**。单元化不是「更高级的多活」，它有一个硬前提：**请求在入口处能被一个稳定的业务键判定归属**（主文件 §2.2 的 CellID = Hash(UID) mod N_Cells）。当大量请求需要跨键联合查询、或键本身不稳定时，单元化不成立。同时，单元化也不解决全局唯一性（全局序列、全局库存池、全局额度）与跨域强一致——这些必须由额外机制承担。打分表里没有一列记录这些「做不到什么」。

第五个问题是**阈值凭空来**。本章的做法是：决策树的每个节点只问**可观测的事实**（能否判定归属、共享组件清单有多长、全局写数据有几张表、切流是否需要人工），阈值在 §7.5 逐条给出推导。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 故障域边界 | 一个组件挂掉，还有多少请求连带失败 | 可用性上限由「共享组件集合的宽度」决定，不由副本数决定 |
| 数据归属 | 每份数据有几个写入者、能否按一个键切 | 决定跨域一致性要求的强弱，是单元化可行性的第一前提 |
| 路由可判定性 | 请求能否在入口被一个稳定键分类，且全链路遵守 | 不能判定归属就无法隔离；染色泄漏会静默写错域 |
| 容量模型 | 冗余按「分片 1/N + 副本」还是「每域全量」算 | 决定成本随 Cell 数是温和增长还是成倍增长 |
| 变更与灰度单位 | 发布、回滚、实验能否按域切分 | 变更窗口是故障最集中的时段，爆炸半径在这里最贵 |
| 迁移路径 | 从现状到目标要动数据还是只动流量 | 决定迁移成本量级与可逆性（能不能回退） |

> 六条判据都不问「哪种架构更先进」，只问「在你的键、你的数据形态、你的可用性预算下，哪一种隔离是买得到的」。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 公开材料 |
| --- | --- | --- | --- | --- |
| **单体** | 不做切分的基线 | 一套应用 + 一个库，靠主备与备份保命 | 早期系统、内部系统 | 通用形态 |
| **同城双活 / 两地三中心** | 机房级冗余 | 同城两份副本 + 异地一份，切换以机房为单位 | 银行核心、传统企业 | 通用实践 |
| **微服务** | 应用按能力切分 | 服务级独立部署与扩容，但数据与注册中心往往仍共享 | 大多数互联网系统 | 通用形态 |
| **分库分表（Sharding）** | 数据按键切分 | 数据切了，**部署与中间件不切**，一个代理层仍是全局节点 | 高并发交易系统 | 通用形态 |
| **异地多活（Active-Active）** | 部署拓扑多地域 | 多个地域同时承载写入，冲突消解必需（LWW / 版本向量 / CRDT） | Netflix、全球性服务 | Netflix Tech Blog（2013） |
| **单元化（Cell-Based）** | 数据 + 部署 + 路由一起切 | 每个 Cell 自包含（DB + Cache + MQ），请求按键路由到固定 Cell（主文件 §1.1） | 阿里双 11、字节春晚红包（主文件 §1.4） | AWS Well-Architected 白皮书（2023）；主文件 §1.4 |
| **Set（分组）** | Cell 的逻辑分组 | 多个 Cell 组成的逻辑组（主文件 §2.1），用于按组调度与灰度 | 阿里体系内的术语 | 主文件 §2.1 |
| **Deployment Stamps** | 同族模式的另一种命名 | 每个 stamp 是一套独立副本（含数据），由单一服务单元路由 | Azure 架构中心推荐的模式 | Microsoft Azure Architecture Center, Deployment Stamps pattern |
| **Shuffle Sharding** | 限制「叠加故障」的子集化 | 给每个客户分配一个子集（Cell 组合），使两次独立故障撞上同一子集的概率显著下降 | AWS 内部服务 | AWS Builders' Library: Shuffle Sharding（2019） |
| **多集群 + 流量调度** | 切部署不切数据 | 多集群部署 + 全局流量调度（DNS/GSLB/网关），数据仍是共享层 | Kubernetes 多集群体系 | Kubernetes 与多集群项目的公开文档 |
| **AI 单元化** | 算力资源的域化 | 每 Cell 独立 GPU 池、模型副本、Agent 集群、向量索引（主文件 §2.3） | 推理密集型系统 | 主文件 §2.3 |

> 表后一句话：这些候选只分 **5 族**——**族 1 不切分 + 多份冗余**（单体、同城双活 / 两地三中心：成本最低，爆炸半径最大，但每份数据只有一个写入者）、**族 2 切应用不切数据**（微服务、多集群流量调度：隔离到服务级，但数据层仍是共同故障源）、**族 3 切数据但部署不切**（分库分表：数据被切开了，可一个中间件仍是全局）、**族 4 切数据 + 自包含部署**（单元化 / Set / Deployment Stamps：隔离到域级，代价是运维对象乘 N）、**族 5 多地域全量 + 多地可写**（异地多活：每个地域持有全量、多个地域同时可写，隔离到地域级，代价是每次写入都要为冲突消解付账——它不是族 1 的多写变体，也不是族 4 的一种，因为它不按业务键切数据、也不要求部署自包含）、以及一个**横切的补充机制**——**Shuffle Sharding**（用子集化削弱族 2/族 4 中残余共享组件的叠加故障）。同族内部可以逐项替换（单元化 ⇄ Deployment Stamps 只换命名与工具链），跨族替换要动的是**数据的归属方式**与迁移路径。**先分族再选，能省掉一半比较**。

还有两个容易漏掉的判断：**单体**有一项常被低估的真实优势——它**不存在共享组件的增量问题**（只有一个域）；**分库分表**则是**最容易被误认为「已经单元化了」**的形态——它切了数据，部署与中间件仍不切（§7.3.1）。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 故障域边界：隔离等级由「共享组件集合的宽度」决定

**机制是什么**：系统的可用性上限由**共享组件集合**决定——凡是被「所有请求都要经过」的组件，都是不可分割的故障域。副本只解决「同一域内的物理故障」，不解决「共享逻辑组件的故障与变更」。缩小爆炸半径只有两条路：**切分域**，或者**消灭共享**。

**各候选的实现差异**：

| 候选 | 故障域粒度 | 残余的共享组件（真实爆炸半径） | 缩小半径的手段 |
| --- | --- | --- | --- |
| 单体 | 1 个（全局） | 应用、DB、网关、配置 | 主备（不缩半径，只缩故障时长） |
| 同城双活 | 机房级 | DB 主、全局配置、全局序列 | 机房切换（分钟级，常需人工） |
| 微服务 | 服务级 | 共享 DB、注册中心、网关、鉴权 | 服务熔断降级（把故障挡在调用链上） |
| 多集群 + 调度 | 集群级 | 数据层、全局调度面 | 流量切集群（依赖调度面本身可用） |
| 分库分表 | 分片级（数据） | 数据代理、路由表、部署单元 | 分片隔离（但代理挂掉则全挂） |
| 单元化 | Cell 级 | 路由、配置下发、发布系统、全局数据（商品字典 / 全局 ID / 风控） | 按 Cell 隔离 + 管控面分级降级 |
| Shuffle Sharding | 子集级 | 同上，但每次故障影响的子集更小 | 用子集分配削弱叠加故障 |

**由此必然导出的性质**：因为爆炸半径由共享组件的宽度决定，所以**给现有架构加副本不会改变半径，只会改变同一半径内的存活概率**——这就是为什么「多买几台机器」无法把可用性从 99.9% 推到 99.99%。反过来，因为管控面（路由规则、配置下发、发布系统、鉴权）天然是全局的，所以单元化的隔离效果会被管控面反向吃掉：**管控面故障时所有 Cell 一起故障**，这正是「单元化必须做管控面分级降级（配置本地缓存、路由表预置、发布可停）」的机制原因，而不是运维细节。

**公开证据【公开】**：AWS 的 *Reducing Scope of Impact with Cell-Based Architecture*（AWS Well-Architected 白皮书，2023）把「细胞化」的目标直接定义为**限制影响范围（scope of impact）**，并把 cell 定义为可独立失效的部署单元；Microsoft Azure Architecture Center 的 *Deployment Stamps pattern* 给出同一思路的另一套命名；AWS Builders' Library 的 *Shuffle Sharding*（2019）说明「防叠加故障」需要的是**子集化**而不是更多副本；*Static stability using Availability Zones*（AWS Builders' Library，2021）说明故障切换应当依赖**预置的路由与容量**而不是运行时扩容——因为运行时扩容在故障时最不可靠。**读者可自行核验的判定方法**：列出架构里所有「所有请求都要经过」的组件（网关、注册中心、配置中心、鉴权、计费、限流、全局序列、时钟服务），这份清单就是真实爆炸半径边界——它通常比部署图上的 Cell 边界大得多。

**失效条件**：当共享组件清单无法收敛到零（鉴权、风控、计费通常只能部分下沉）时，单元化提供的是**部分隔离**；此时可用性目标应按「最宽的共享面」计算，而不是按 Cell 数计算。把 1/N 的爆炸半径直接当作可用性承诺，是把两种不同的量混为一谈。

#### 7.3.2 数据归属与切分键：每 Cell 一份 DB 与「全局数据清单」的长度

**机制是什么**：单元化的前提是「数据能被一个业务键切开，且**每个键只有一个写入者**」。一旦成立，跨域并发写消失，一致性问题从「跨域事务」降级为「域内事务 + 域间异步」；一旦不成立（多写入者），就必须引入冲突消解，而任何冲突消解都会丢信息或加延迟。

**各候选的实现差异**：

| 候选 | 数据切分 | 每个键的写入者 | 一致性机制 | 代价落在哪 |
| --- | --- | --- | --- | --- |
| 微服务（共享库） | 不切 | 多 | 数据库事务 | 库是全局单点 |
| 分库分表 | 按键切 | 单（同分片内） | 分片内事务 | 跨分片事务/查询要额外机制 |
| 异地多活（Active-Active） | 按地域切且**多地可写** | 多 | 冲突消解（LWW / 版本向量 / CRDT） | 静默丢更新或元数据膨胀 |
| 单元化 | 按键切 + 每 Cell 自包含 | 单 | 域内事务 + 跨域异步 | 全局写数据必须单独处理 |
| 单元化 + 全局数据收编 | 同上，全局数据集中 | 单（集中在中心域） | 中心域内事务 | 中心域成为共同故障源 |

**由此必然导出的性质**：因为「每个键只有一个写入者」时不存在并发写冲突，所以单元化能把跨地域一致性问题降级为域内事务——**这是它相对异地多活的本质优势，而不是「单元比地域小」**（切得再细，只要多地可写就仍需冲突消解）。反过来，因为总有一部分数据天然是全局的（全局唯一 ID、库存池、额度池、风控名单、汇率与商品字典），所以**真正决定单元化成败的不是 Cell 数，而是「全局写数据清单有多长、其中多少可以本地只读复制」——全局可写数据每多一项，能达到的隔离等级就矮一级**。

**公开证据【公开】**：CAP 的原始表述与证明（Brewer 的 PODC 2012 主题演讲；Gilbert & Lynch, *SIGACT News*, 2002）说明网络分区发生时必须在一致性与可用性之间选择；PACELC（Abadi, *IEEE Computer*, 2012）把「无分区时的延迟与一致性权衡」也纳入，这解释了为什么异地多活即使不分区也要付出跨地域写延迟；Dynamo（SOSP 2007）给出多写副本下的冲突消解手段（向量时钟与 LWW）及其代价；Spanner（OSDI 2012）给出另一端的做法（全局时钟 + commit-wait，把写延迟下限抬高到时钟不确定度）。**读者可自行核验的判定方法**：把表按「能否被一个业务键定位」与「是否只读」两维分类，落在**「全局且可写」**象限的表数量，就决定了你能达到的隔离等级。

**失效条件**：当业务本身要求跨用户 / 跨域的强一致（全局库存、资金池、全局额度）时，单元化无法提供；此时只有两条路——把这类数据收进一个专门的中心域（并因此接受它成为共同故障源），或改成「预分配 + 日终对账」的业务方案（用对账吸收暂时的超发/少发）。

#### 7.3.3 路由与染色：一次决定，全链路遵守

**机制是什么**：单元化路由 = 在入口处用一个稳定键决定「这个请求属于哪个 Cell」，并且这个决定在整条链路上被**一致地传递**（流量染色，主文件 §2.1）。路由是「一次决定、全程遵守」，而不是每一跳各自判断。

**各候选的实现差异**：

| 路由机制 | 粒度 | 扩容时的行为 | 灰度能力 |
| --- | --- | --- | --- |
| DNS / GSLB | 地域级 | 粗粒度调整 | 按地域灰度 |
| 服务发现 | 服务级 | 自动注册即可 | 按实例灰度 |
| 取模路由 `Hash(UID) mod N_Cells`（主文件 §2.2） | 键级，同一用户固定命中同一 Cell | N 变化即近乎全量重映射（需重分布与数据迁移） | 按 Cell 灰度 |
| Range 分片 | 键区间级 | 分裂区间 | 按区间灰度 |
| 染色路由（入口打标 + 透传） | 键级且可跨系统传递 | 路由表变更加数据迁移 | 按染色标签灰度（可精确到用户组） |
| 双写 / 多写路由（异地多活） | 多地并写 | 无重分布 | 按地域灰度，需处理冲突 |

> **术语辨析（机制层面）**：主文件 §2.2 把 `CellID = Hash(UID) mod N_Cells` 记作「一致性 Hash」，但按机制它是**取模分片**，两者的扩容行为相反——哈希环上增删节点只重映射约 1/N 的键，而 `mod N` 一旦改 N 就近乎全量重映射。本节按机制称之为**取模路由**，并据此把它归入「增删 Cell 要付重分布与迁移成本」那一类；若某系统真的用一致性 Hash（哈希环），它的扩容迁移量要按该项重估，不能沿用本节按取模分片推出的结论。

**由此必然导出的性质**：因为路由是「一次决定、全链路遵守」，所以**任何一环丢失染色（消息消费、定时任务、异步回填、运维脚本、第三方回调、AI Agent 的工具调用）都会把数据写到不属于它的 Cell，而且不报错**——这是单元化最难发现、也最难回滚的失效模式（静默错域）。反过来，因为染色是显式的，所以它也把「灰度」与「故障切流」变成了路由表的一次变更（主文件 §1.3 提到单元化让灰度可按 Cell 切分、让混沌实验的爆炸半径可控）——**这是单元化在变更窗口里的额外收益，它的价值往往被低估：变更窗口是全年故障最集中的时段**。

**公开证据【公开】**：主文件 §2.2 给出的取模路由形式（CellID = Hash(UID) mod N_Cells）与 [§3.3 反模式 3「跨 Cell 调用频繁」](01-cell-based-architecture-section-3-sec3.md)，共同说明路由命中与否直接决定了跨域调用比例；AWS 白皮书（2023）要求单元化路由层本身**无状态且不成为新的共享故障源**；*Static stability*（AWS Builders' Library，2021）要求故障切换依赖预置路由表而非运行时推导。**读者可自行核验的判定方法**：列出所有「不由用户请求发起但会写数据」的入口（定时任务、消息消费、离线回灌、运维脚本、数据修复工具、Agent 工具调用），逐个检查它能否拿到归属键；拿不到的入口就是染色泄漏点。

**失效条件**：当业务键不稳定（用户换绑手机号、订单跨店、机构用户迁移）或存在必须跨键的联合查询与报表时，路由与查询模式冲突，必须在「重分布（迁移成本）」与「跨 Cell 查询（延迟与可用性成本）」之间取舍——两者都不会免费。判定方法：统计跨 Cell 查询占全部查询的比例，以及每次键变更需要迁移的数据量。

#### 7.3.4 容量模型：Cell 数 N 同时决定爆炸半径与冗余成本

**机制是什么**：Cell 数 N 决定两个方向相反的量——单点故障的影响面约 1/N，以及「每个 Cell 需要独立承载多少」。前者随 N 改善，后者的成本形态取决于数据是**分片式**还是**每 Cell 全量**。

**各候选的实现差异**：

| 候选 | 容量模型 | 单点故障影响面 | 相对单份的成本 |
| --- | --- | --- | --- |
| 单体 + 主备 | 一份容量 + 备用机房 | 100% | 约 2 倍（备用） |
| 双活（两地） | 每地各扛全量峰值 | 50% | 约 2 倍（两地均需全量） |
| 分库分表 | 数据分片到多个库 | 1/分片数（但代理仍是全局） | 约 1 倍数据 + 代理冗余 |
| 单元化（分片式） | 每 Cell 存 1/N 数据，按键路由 | 约 1/N | 数据约 1 倍 + 副本；计算需 N/(N−1) × 峰值 |
| 单元化（每 Cell 全量） | 每 Cell 都持有全量（读本地化） | 约 1/N | 数据约 ×N |
| Shuffle Sharding | 客户分配到子集 | 依子集大小 | 与副本数同阶，但防叠加故障 |

> 上表的比例为**结构比例（【推算】）**，来自副本份数与数据份数的定义推导（例如「两地各扛全量峰值」即 2 份全量），不是任何系统的实测值；实际成本还要乘上单份的实际单价，而单价随机型、地域、采购方式变化，因此本节只比较函数形式。

**由此必然导出的性质**：因为「一个 Cell 故障后它的流量必须去别处」，所以若要求**零容量损失地扛住单 Cell 故障**，集群总容量需达到 N/(N−1) × 峰值——N = 12 时约 109%（+9%），而 N = 2 的双活需要约 200%（+100%）（【推算】，按副本数线性）。**这就是「单元化比双活更省容量」的定量来源：冗余随 N 增大趋近于零**。反向的代价是运维对象数随 N 线性增长（Cell 数 × 组件数），以及每次全量变更要走 N 次——**这两个量的方向相反，所以 N 的最优值来自「可用性预算 / 运维产能」的平衡，而不是「越多越好」**（[§3.3 反模式 1「Cell 数量过多」](01-cell-based-architecture-section-3-sec3.md) 把「100 个 Cell」列为反模式，给出的经验区间是 12–24）。

**公开证据【公开】**：主文件 §1.4 记录的演进时间线（eBay 2008 年提出 Cell-Based 概念、阿里 2012 年起「五彩石」探索、2015 双 11 首次大规模应用、2018 三地五中心；年份与事实以主文件引用的一手公开材料为准）说明这条路线在超大规模场景被长期验证——本节因此**不重复引用其中的规模数字**（Cell 数量、QPS 等属于该一手材料的口径，转述会丢失前提）；AWS 白皮书（2023）把 cell 的容量设计写成「每个 cell 必须能承载被路由到它的全部流量」；Google SRE Book（2016，错误预算见 Ch.3 *Embracing Risk*）公开的错误预算机制给出了「用可承受的不可用时间反推容量与切换速度」的方法论。**读者可自行核验的判定方法**：把「故障 Cell 的流量」与「剩余 Cell 的剩余容量」对一下——如果剩余容量接不住，那么实际可用性由**容量重分配速度**决定，而不是由 Cell 数决定。

**失效条件**：热点用户 / 热点数据会破坏 1/N 的均匀性（[§3.3 反模式 2「热点用户」](01-cell-based-architecture-section-3-sec3.md)）：某大 V 或某个爆款商品把单个 Cell 打满时，爆炸半径不再由 1/N 决定，而由该热点所在 Cell 决定。判定方法：统计各 Cell 的流量分布与 Top-N 用户的分布，比较 P99 与 P50 的 Cell 负载差异；差异显著时，需要缓存、专属 Cell 或按热点二次路由。

**四条机制维度的对照速查**（每行给出机制依据，而不是打分）：

| 候选 | 故障域粒度 | 数据归属 | 路由粒度 | 容量模型 | 由机制导出的最短结论 |
| --- | --- | --- | --- | --- | --- |
| 单体 | 1 个（全局） | 不切 | 无 | 主备 | 小规模最省；DB 是唯一且全局的爆炸点 |
| 同城双活 / 两地三中心 | 机房级 | 不切（或主从） | DNS / GSLB | 双份机房 | 预算在小时级时够用；切换决策是组织成本 |
| 微服务 | 服务级 | 不切 | 服务发现 | 副本 | 服务切了但数据没切，隔离收益被共享层限制 |
| 多集群 + 流量调度 | 集群级 | 不切 | 全局调度面 | 多副本 | 切部署不切数据，调度面是新的全局节点 |
| 分库分表 | 分片级 | 按键切 | 代理 / 中间件 | 分片 + 副本 | 数据切开了，代理仍是全局单点 |
| 异地多活 | 地域级 | 按地域切、多地可写 | 地域路由 | 每地域全量 | 无需重分布，但必须有冲突消解（会丢信息） |
| 单元化 | Cell 级 | 按键切、单写入者 | 取模路由 + 染色透传 | 1/N + 副本；冗余 N/(N−1) | 键定得住时最省的隔离手段 |
| 单元化（每 Cell 全量） | Cell 级 | 按键切、每 Cell 全量只读 | 同上 | ×N | 读本地化换来成本 ×N |
| Shuffle Sharding | 子集级 | 按子集分配 | 子集表 | 与副本同阶 | 防叠加故障，不防单点容量不足 |

### 7.4 成本结构对比（不是价格表，是成本函数）

单元化没有可比单价：同一个架构在自建机房与云上、在分片式与全量式、在人工切流与自动切流下，成本差一个量级。可比较的是**成本函数的形式**：

```
总成本 ≈ 冗余容量成本（分片式 ≈ N/(N−1) × 峰值；全量式 ≈ N × 单份）
        + 运维对象成本（Cell 数 × 组件数 × 单组件运维人时）
        + 跨域协调成本（跨 Cell 调用比例 × 单次跨域代价）
        + 管控面成本（路由 / 配置 / 发布 / 全局数据：不随 Cell 数增长，但必须高可用）
        + 迁移与双跑成本（新旧并存期 = 双份资源 + 对账 + 双份值班）
```

**四个可算的量级（【推算】，推导链见下）**：

1. **爆炸半径** ≈ 1/N：N = 4 → 25%，N = 12 → 8.3%，N = 48 → 2.1%。推导前提是「流量按 Cell 均匀分布」且「故障 Cell 的流量无法由其他 Cell 立即吸收」；两个前提任一不成立，实际影响面都会更大（见 §7.3.4 失效条件）。
2. **切换速度决定可承受事件数**：若一次 Cell 级故障切换需要 T 秒，则一年内能承受的这类事件次数约 = 停机预算 / T。以 99.99%（年预算约 52.6 分钟，【推算】，按 365 天换算）为例：T = 60 秒时约 52 次/年，T = 10 分钟时约 5 次/年。→ **这条推算是「把切换自动化做完比把 Cell 数堆多更值」的定量依据**：人工切流（分钟级，【经验】）会让可用性预算被少数几次事件吃完。
3. **运维对象数** = Cell 数 × 组件数。12 个 Cell × 6 个组件（应用、库、缓存、MQ、网关、可观测）= 72 个部署单元，对比单体的 6 个（【推算】，按上述假设）。→ 这是「Cell 数过多」反模式的实际含义：它不是审美问题，而是变更窗口、值班面与故障排查面的线性膨胀。
4. **跨域调用代价**：同城跨 Cell 约 1 个 RTT（亚毫秒到 1 ms），跨地域约 20–40 ms（【经验】，业界常见区间）。若一条链路上有 3 次跨域调用，端到端延迟约增加 3 × 1 ms ≈ 3 ms（同城）或 3 × 30 ms ≈ 90 ms（跨地域）。→ **这就是「数据按业务键集中、把跨 Cell 调用压到 0」的真正价值所在**，而不是「架构更整洁」；1000 QPS 的链路上，每请求一次跨域即 1000 次额外跨域调用/秒。

**主导项与隐性成本**：

| 候选 | 成本主导项 | 隐性成本（容易漏算） |
| --- | --- | --- |
| 单体 + 主备 | 备用容量 | 切换演练成本；主备切换期的数据丢失窗口 |
| 同城双活 / 两地三中心 | 双份机房容量 | 切换决策的组织成本（谁有权限切、多久能决定） |
| 微服务 | 服务数与部署成本 | 共享数据层把隔离收益吃掉；分布式排查成本 |
| 分库分表 | 数据代理与扩容（重分片） | 代理是新的全局单点；跨分片查询与事务的补丁代码 |
| 异地多活 | 跨地域带宽与写延迟 | 冲突消解带来的静默丢更新；一致性验证成本 |
| 单元化（分片式） | 运维对象数（N × 组件） | 管控面成为新的共同故障源；染色泄漏的排查 |
| 单元化（全量式） | 存储 ×N | 数据一致性同步的复杂度；扩容成本随 N 放大 |
| Shuffle Sharding | 子集分配的复杂性 | 故障后子集重组；对不均匀流量的敏感性 |

**关键判断**：因为**冗余容量成本随 N 递减（N/(N−1)）**，而**运维对象成本随 N 线性递增**，所以存在一个明确的平衡点；又因为**管控面成本与 N 无关但决定上限**（§7.3.1），所以在预算有限时，**先做管控面降级与切流自动化、再增加 Cell 数**是成本顺序上更稳的路径。此外要区分两类成本的增长方式：主导项随业务量增长（可用容量规划预算），隐性成本随**故障次数与变更次数**增长（不可预测，只在出事时暴露）——所以选型时真正要比的是「哪一种的隐性成本落在我的团队能力范围内」。

### 7.5 决策树（每个分支都要有阈值依据）

```
第 1 层（硬约束，先问）：
  (a) 能否为每个请求在入口处确定一个稳定的业务键？
      ├─ 不能（键不稳定 / 大量跨键联合查询 / 报表要全局 JOIN）
      │     → 单元化不成立；走微服务 + 多副本 + 同城双活，把可用性目标控制在可达范围
      └─ 能 → (b)
  (b) 「全局且可写」的数据有几张表（全局 ID / 库存池 / 额度池 / 风控名单 / 商品字典）？
      ├─ 清单长且无法收编 → 隔离等级封顶在「这些数据所在的那一层」，按该层设可用性目标，
      │     不要按 Cell 数承诺（每多一张全局写表，「单写入者」前提就弱一分）
      └─ 短、或能收编到中心域 → 第 2 层

第 2 层（可用性预算 → 实现形态）：你的年停机预算？
├─ 数小时级（99.9% 及以下）→ 微服务 + 同城双活 / 两地三中心
│     （单元化的运维对象膨胀在这个预算下买不到可观测收益）
├─ 半小时级（99.99%）→ 单元化（或 Deployment Stamps）+ 管控面分级降级 + 切流自动化
└─ 分钟级（99.999%）→ 单元化 + 全链路染色 + 自动切流 + 全局写数据清单压到最短

第 3 层（正确性 vs 可用性）：是否存在「数据错乱比短暂不可用更贵」的链路？
├─ 有（资金、账务、库存、计费）→ 该链路数据收进单个域/单库，接受它成为共同故障源；
│     不要为它上跨地域多写（冲突消解会带来静默错更新）
└─ 无 → 可按可用性优先设计（异地多活 + 冲突消解）

第 4 层（成本模型）：数据是「分片式」还是「每 Cell 全量」？
├─ 可分片（按键归属）→ 冗余 ≈ N/(N−1)，成本温和，N 可到 12–24
└─ 必须全量（否则读本地化做不到）→ 成本约 ×N；先问「能否改成缓存或异步只读副本」

第 5 层（变更隔离）：发布能否按 Cell 切分？
├─ 能 → 单元化额外提供「按 Cell 灰度」的变更隔离，收益加权
└─ 不能 → 单元化只剩隔离收益，需要重新评估是否值得（见 §7.3.3）

第 6 层（叠加故障）：你的主要风险是「单台机器挂」，还是「一类依赖同时变慢 /
同一批发布同时出错」？
├─ 单点为主 → 隔离粒度（Cell 数）就是有效手段；加副本只提高同半径内的存活率
└─ 叠加为主 → 在现有隔离之上叠加 Shuffle Sharding（给每个客户分配 Cell 子集），
      并同步维护共享组件清单；此时加副本不改变「两次故障撞上同一子集」的概率
```

**阈值依据**（每条回指树上节点，双向一一对应）：

- **第 1 层 (a)「能否判定归属」**：硬约束，无阈值（§7.3.3）。判定方法：列出所有会写数据但不由用户请求发起的入口（消息消费、定时任务、离线回填、运维脚本、数据修复工具、Agent 工具调用），逐个检查它能否拿到归属键；拿不到就不成立。
- **第 1 层 (b)「全局且可写数据的清单长度」**：硬边界，无阈值（§7.3.2）。依据：清单越长，能写同一份数据的域越多，「每个键只有一个写入者」越不成立，可达到的隔离等级越低——这条不能用「加一个中心域」绕过去，因为中心域本身就是共同故障源。
- **第 2 层「停机预算」三档**：来自可用性的算术换算（【推算】，365 天 = 525,600 分钟）：99.9% ≈ 8.8 小时/年，99.99% ≈ 52.6 分钟/年，99.999% ≈ 5.3 分钟/年。**注意这是预算上限，不是上线后的实际值**；实际值还要减去每次故障的切换时间与修复时间。
- **第 2 层「切换时间 T 决定可承受事件数」**：见 §7.4 推算 2（事件数 ≈ 预算 / T）。这条阈值把「自动化切流」从优化项变成前提条件——人工切流（分钟级，【经验】）在 99.99% 的预算下只允许个位数次事件/年。
- **第 3 层「正确性是否优先于可用性」**：判据是**错误能否被事后还原**，不是数额大小。冲突消解（LWW）造成的丢更新一旦写入就无从从日志还原（Dynamo, SOSP 2007【公开】，§7.3.2），所以资金 / 账务 / 库存 / 计费链路的正确性权重压过可用性，方向与「可用性越高越好」相反；错更新能被对账或回溯修复的链路（内容、推荐、埋点日志）则不必付这个代价。无阈值。
- **第 4 层「分片式 vs 每 Cell 全量」**：硬选择，无阈值（§7.3.4、§7.4）。两者成本函数不同（分片式 ≈ N/(N−1) × 峰值 + 1 份数据；全量式 ≈ ×N 份数据），判定方法是「读本地化是否必须持有全量数据」；若可退化为缓存或异步只读副本，就回到分片式的成本形态。
- **第 4 层「N = 12–24」**：来自 [§3.3 反模式 1](01-cell-based-architecture-section-3-sec3.md) 的经验区间，依据有两项可算——（a）冗余惩罚 N/(N−1)：N = 12 时约 9%，已接近「加容量买隔离」的合理区间，N 再增大收益递减；（b）运维对象数 = N × 组件数，数十个部署单元仍可被一个平台团队覆盖，上百个则超出。这是【经验】档阈值，不是硬边界；关键是 N 的取值应当由「运维产能」反推，而不是由「爆炸半径越小人越好」推。
- **第 5 层「发布能否按 Cell 切分」**：这条决定单元化**是否还有额外收益**，判据来自「变更窗口是全年故障最集中的时段」（【经验】：行业普遍观察，无单一权威来源）与 §7.3.3 的染色机制——只有发布单位能被染色识别，回滚与灰度才能按域生效；发布若是全局的（一套配置、一次全量变更），单元化在运行期之外的收益归零，此时按「只剩隔离收益」重估。无阈值。
- **第 6 层「单点故障 vs 叠加故障」**：分层依据是故障形态而不是规模。当故障是「一台机器挂」，加副本有效；当故障是「一类依赖同时变慢 / 同一批发布同时出错」，同一批客户会被两次独立故障同时击中，副本数再多也不改变子集重叠概率，此时子集化（Shuffle Sharding）有用（AWS Builders' Library, 2019【公开】）。判据：统计近一年故障事件里「单实例」与「同类依赖 / 同批变更」两类成因的占比。

**这棵树刻意不覆盖的分支**（以及为什么）：**「Cell 数具体取几」**（由运维产能与冗余惩罚的平衡决定，不能给一个通用数字）；**「要不要多云」**（多云把管控面与网络复杂度再上一阶，属于供应商风险问题，不是隔离粒度问题）；**「AI 推理要不要单元化」**——判据是「推理是否依赖用户级状态」：依赖（用户记忆、个性化上下文）则跟着 Cell 走，不依赖则应按 GPU 池化（主文件 §2.3），**「有没有 GPU」不构成单元化的理由**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 内部系统 / 中低并发 | 微服务 + 同城双活 | 单元化 | 运维对象膨胀买不到可观测收益 |
| 交易链路（订单、库存） | 单元化（分片式，按用户键） | 分库分表 + 多活 | 分库分表只切了数据，代理层仍是全局单点 |
| 资金 / 账务 | 单域收编 + 日终对账 | 跨域多写 | 冲突消解会静默丢更新，账目不平的代价高于短暂不可用 |
| 全球服务、多地域写入 | 异地多活 + 冲突消解 | 单元化（把写入收敛到单元内） | 单元化要求键稳定；若用户会跨地域迁移，路由与迁移成本上升 |
| 内容 / 推荐 / 读多写少 | 单元化（每 Cell 全量只读副本）| 仅缓存 | 每 Cell 全量成本 ×N，只读副本可用异步复制压低该成本 |
| 单点热点（大 V、爆款） | 专属 Cell + 缓存 + 二次路由 | 靠 Hash 均匀性 | 均匀性假设被破坏时，爆炸半径由热点所在 Cell 决定 |
| 高并发 + 叠加故障敏感 | 单元化 + Shuffle Sharding | 单纯加副本 | 副本不改变子集重叠概率 |
| AI 推理密集型 | AI 单元化（若依赖用户级状态）| GPU 池化 | 无状态推理按池化更省，域化只增运维面 |

**常见组合**（每条注明职责边界与运维代价）：

- **单元化 + 异地多活**：单元化负责「键级归属 + 自包含部署」，异地多活负责「地域级存活」。边界是：**跨地域只同步、不并写关键业务键**（并写会让 §7.3.2 的单写入者前提失效）。运维代价是管控面必须支持「按 Cell + 按地域」两级路由表，且两级都要能独立降级。
- **单元化 + 大促保障**：单元化负责「容量按 Cell 独立规划 + 限流按 Cell 生效 + 单 Cell 过载不扩散」，大促保障负责「压测、预案、值班升级」。边界是：**全局写数据（库存池、券池、名额池）与秒杀热点不随 Cell 缩放**，必须先按 Cell 预分配名额或收编到中心域，否则大促当天被击穿的正是这一层（§7.3.4 失效条件）；容量口径也要从「总量」改为「单 Cell 峰值 × N」。运维代价是压测要做 N 次（每 Cell 一次）、预案要按 Cell 粒度演练，值班面与临时扩容流程都比单体复杂。
- **单元化 + 按 Cell 灰度**：把发布、回滚与实验的单位从「全站」缩到「若干 Cell」。边界是：路由表变更与数据迁移必须分离（先切流量、后迁数据，或反之），两者同时进行会丧失回退能力。运维代价是发布系统要理解 Cell 拓扑（主文件 §1.3 指出单元化让灰度可按 Cell 切分）。
- **单元化 + 混沌工程**：混沌实验按 Cell 注入，把爆炸半径限制在 1/N。边界是：实验必须显式声明「是否允许影响跨 Cell 共享组件」，否则会意外验证成全局故障。运维代价是共享组件清单必须持续维护（§7.3.1 的判定方法）。
- **Deployment Stamps + 无状态路由**：用 stamp 承载一组客户的全栈副本，路由层无状态且不可成为共享故障源。边界与单元化相同，差别在命名与工具链（Azure 架构中心，公开文档）。
- **单元化 + AI 单元化**：有状态推理（用户上下文、向量索引）随 Cell 走，无状态推理走共享 GPU 池。边界是「状态归属」而不是「算力类型」。运维代价是 GPU 产能必须按 Cell 预留，利用率下降——这也是「AI 单元化只在延迟与合规要求足够强时才做」的原因。

组合的原则只有一条：**每加一层（Cell、地域、stamp、子集），都要说清它缩小的到底是哪一种故障域，以及它自己会不会成为新的共同故障源**。答不出来，说明这一层只是在增加运维面，没有缩小爆炸半径（§7.3.1）。

**组合的运维代价集中在哪里**：在「层与层的交界处」，常见三处失血点——（1）路由表在 Cell 层与地域层各有一份，两份不一致时表现为「少数请求反复跨域」（表现为尾延迟异常，而不是报错）；（2）Cell 拓扑变了但共享组件清单没更新，表现为「某次故障的影响面远超预期」；（3）数据迁移与流量切换同时进行，表现为「出问题时无法回退到任一侧」（因为两侧数据都已不完整）。**判定方法**：抽查最近一次 Cell 级变更，看它是否同时改了流量与数据；如果是，它就是一次不可回退的操作。

### 7.7 选错的代价与迁移成本

**反模式：Cell 数量过多** —— 症状：按「爆炸半径越小越好」一路切到 100 个 Cell → 后果：运维对象数 = Cell 数 × 组件数线性膨胀（§7.4 推算 3），变更窗口与值班面同步膨胀；更关键的是，管控面（同一套路由、配置、发布系统）没有随之增强，隔离收益被管控面吃掉（[§3.3 反模式 1](01-cell-based-architecture-section-3-sec3.md)）→ 正确的做法：N 由运维产能反推，先做管控面降级与自动切流，再考虑加 Cell。

**反模式：只做了部署切分，共享组件留在 Cell 外** —— 症状：应用与数据库分了 Cell，但注册中心、配置中心、数据代理、鉴权全部共享 → 后果：共享组件故障时所有 Cell 一起故障，**爆炸半径没有变小，只是部署图变复杂了**（分库分表最常落入这一形态）→ 正确的做法：按 §7.3.1 的判定方法先列共享组件清单，逐个决定「下沉到 Cell 内 / 本地缓存降级 / 接受它成为共同故障源」。

**反模式：用单元化解决一致性** —— 症状：为了「多活」把关键业务键做成多地可写，再用 LWW 做冲突消解 → 后果：LWW 在「后写必对」不成立时静默丢更新（Dynamo 论文中即以此为主要代价，SOSP 2007），账务与库存类数据会出现无报错的数据错误，且事后无法从日志还原 → 正确的做法：**可写键必须单写入者**（§7.3.2），跨域只做异步同步；确需跨域强一致的少量数据收进中心域并接受它成为共同故障源。

**反模式：染色泄漏** —— 症状：只在用户请求入口做路由染色，消息消费、定时任务、离线回填、数据修复脚本没有归属键 → 后果：数据被写入错误 Cell，表面正常、查询时偶发不一致，排查成本极高（因为不报错）→ 正确的做法：把「所有会写数据的入口」列成清单（§7.3.3 的判定方法），逐个补齐归属键或改为由 Cell 内作业执行。

**换成另一种形态要动什么**：

| 从 → 到 | 数据迁移 | 查询 / 接口改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 单体 → 微服务 | 不动（先拆应用） | 拆接口、去跨库 JOIN | 服务编排与观测 | 分布式思维 | 半年到年级 |
| 微服务 → 分库分表 | **大**（重分片、双跑对账） | SQL 要避免跨分片 | 引入数据代理 | 分片键设计 | 季度到半年 |
| 分库分表 → 单元化 | 中（数据可复用，需按 Cell 重规划） | 加染色透传 | **重建**（Cell 拓扑、路由、发布、值班） | 路由与降级语义 | 半年到年级 |
| 同城双活 → 异地多活 | 大（多地域复制 + 冲突消解） | 处理多写与冲突 | 跨地域管控面 | 一致性验证方法 | 年级 |
| 任意 → 单元化 | 大（按 Cell 重新规划归属） | 全链路染色 | 全套重建 | 归属键与降级 | 年级，且难回退 |

> 规律：**迁移成本最高的是「数据归属方式」的变化**（分库分表 ⇄ 单元化 ⇄ 异地多活），因为它要动数据本身与全链路的键传递；而应用侧拆分（单体 → 微服务）是可增量执行的。可操作的做法是把迁移拆成「先只读切换（新路径与旧路径比对，差异挂账）→ 再只写切换（旧路径降级为校验）→ 最后下线旧路径」三段，每段之间留一次完整的对账周期——**愿意接受这个节奏，迁移才是可控的**。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 请求无法在入口判定归属 | 不上单元化，走微服务 + 同城双活 | 路由可判定性是前提，不是优化项 |
| 年停机预算数小时级 | 同城双活 / 两地三中心 | 单元化的运维对象成本在这个预算下买不到收益 |
| 年停机预算半小时级 | 单元化（分片式）+ 自动切流 | 冗余 N/(N−1) 温和；切换速度决定实际可用性 |
| 共享组件清单很长 | 先做降级与本地缓存，再谈 Cell 数 | 爆炸半径由共享面宽度决定（§7.3.1） |
| 存在全局可写数据 | 收进中心域并接受其为共同故障源 | 单写入者前提不成立时冲突消解会静默丢更新 |
| 单点热点业务 | 专属 Cell + 缓存 + 二次路由 | 均匀性假设被破坏时 1/N 不再成立 |
| 叠加故障（一类依赖同时变慢） | Shuffle Sharding | 副本不改变子集重叠概率 |
| 只要一个动作 | 先把「会写数据的入口」逐个补上归属键 | 染色泄漏不报错，是最贵的隐性故障（§7.3.3） |

> 本节小结：这些架构之间，**唯一真正起决定作用的差异是「数据按什么键归属、每个键有几个写入者」**——它决定了能不能切、切完能不能隔离、以及隔离之后还需不需要冲突消解。故障域切分、路由染色、Cell 数、冗余成本，全部都是这条差异的下游结果：键定得住，单元化能把跨地域一致性问题降级为域内事务；键定不住，任何切分都只是把共享单点换个位置摆放。
