## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

六种单元化模式（用户 / 地域 / 业务 / 复合 / 分层 / AI）常被讲成「按场景挑一个」。真实的模式选择是被约束推着走的，其中三条最先起作用：**请求能不能在入口处被一个稳定的键判定归属**（主文件 §2.2 的取模路由 `CellID = Hash(UID) mod N_Cells` 成立的前提）、**每份数据有几个写入者**、**共享组件清单有多长**。第一条决定「能不能切」，第二条决定「切完要不要付冲突消解的成本」，第三条决定「切完到底有没有隔离」。

把这三条代入就发现，模式表里的排序经常是反的：「业务单元化」看起来边界最清晰，但一次下单天然要读用户 + 商品 + 库存，归属键（业务类型）与请求的访问集合不重合，于是**每一个请求都跨 Cell**；而它本来要解决的正是跨 Cell 调用。「地域单元化」看起来天然就近，但归属键是「用户此刻在哪」，人会移动，于是重归属（把用户数据跨地域迁移）变成常态化流程，而不是异常处理。

所以本节的组织方式是：**先立约束，再谈模式**。每个模式都先回答「它被什么约束逼出来」，再给结构示意；结构决定机制，机制决定代价，代价决定它在哪里失效。约束表如下——右列是这条约束最经常被推翻的那句直觉。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式 | 归属键是谁、每份数据有几个写入者 | 「切了 Cell 就有隔离」——若还有共享库或全局表，故障域只是换了个位置摆放 |
| 访问模式（点查 / 扫描 / 聚合） | 单元内闭环能否成立、跨 Cell 调用比例 | 「跨 Cell 只是慢一点」——同步跨 Cell 会把刚切开的故障域重新连起来 |
| 变更频率与历史要求 | 路由表与归属关系的稳定性 | 「路由表随时可改」——改归属要迁数据并双写一段时间，不是改配置 |
| 一致性要求 | 哪些链路必须单写入者 + 同步提交 | 「单元化顺手解决一致性问题」——它只把一致性问题收敛到 Cell 内，不消灭它 |
| 规模与成本约束 | Cell 数、容量预留比例、运维对象数 | 「Cell 越多隔离越好」——运维对象与容量冗余随 N 增长，收益递减 |
| 团队技能与运维能力 | 能否长期维护 N 份一致的部署、路由与降级预案 | 「单元化是一次性项目」——它是长期工程，改归属方式以年计 |

把约束落到操作层面，只需要在动手前问三件事，它们的答案基本决定了该选哪个模式。**这三件事的先后与 3.8 给出的落地次序一致**（3.8 的最后一步「选模式」，正是这三问的落点）：先列清单（决定切完有没有隔离），再数入口（决定能不能切），最后判键（决定这是不是一条能长期用住的归属键，否则切分会从一次切分变成持续迁移）。

1. **列共享组件清单**：全局配置、全局序列、全局库存池、全局额度、维表、搜索索引，逐项判断「它挂掉影响全站还是单 Cell」。清单越长，故障域切分越接近形式主义。
2. **数「会写数据的入口」**：用户请求只是其中之一，消息消费、定时任务、离线回填、数据修复、运维脚本、Agent 工具调用都是写入入口。这些入口里有多少能拿到同一个键？拿不到的比例越高，越不能按业务键切。
3. **判断键的稳定性**：注册即固定的 userId 是稳定键；「当前所在地」「所属机构」「当前活动的商品」都不是——不稳定键会把「切分」变成「持续迁移」。

一句话：**模式的差异不是风格的差异，是「归属键」与「写入者数量」的差异**，其余（Cell 数、冗余比例、路由实现）都是这两条的下游结果。

还有一层约束经常被漏掉：**路由与归属的可判定性是单向的**——一旦按某个键切了数据，后续所有新写入都必须在入口拿到这个键，而这个要求会向后传播到消息格式、调度配置、运维脚本、Agent 工具定义上。因此「先定键、再定模式、最后才写代码」不是流程洁癖，而是因为键的选择一旦落地，就变成了一组跨系统的接口契约，改它等于改所有写入方的签名。本节后面每个模式的「失效点」几乎都能追溯到这条约束被违反的那一刻。

最后要提醒的是：**约束本身会变**。业务从单产品扩到多产品线、从单地域扩到多地域、从只读推荐扩到有状态推理，都会改变上面这张表里某一行的取值，从而把「当前正确」的模式变成「上一代的正确模式」。因此模式选择不是一次性决策，而应该在每次容量评审、每次故障复盘时重答一遍 3.7 的清单——3.6 讲的正是「跨过什么阈值就该换」。

### 3.2 模式逐个拆解（核心节）

六个模式在下面逐个拆解：用户单元化（3.2.1）、地域单元化（3.2.2）、业务单元化（3.2.3）、复合单元化（3.2.4）、分层单元化（3.2.5）、AI 单元化（3.2.6）。它们的区别可以用两个问题一次问清：**归属键取谁**、**每份数据有几个写入者**。这张速览表先给出结论，后面每个模式再展开结构与失效点。

| 模式 | 归属键 | 每份数据的写入者 | 隔离粒度 | 主要代价 |
| --- | --- | --- | --- | --- |
| 用户单元化 | userId | 1（Cell 内） | 用户级 | 路由层成共享组件、跨用户聚合另建链路 |
| 地域单元化 | 地理位置 | 1（域内） | 地域级 | 重归属常态化、每域近乎全量 |
| 业务单元化 | 业务域 | 1（域内），但请求跨域 | 业务级 | 跨 Cell 同步调用进主路径、每域按全站峰值预留 |
| 复合单元化 | userId + 地域 | 1（单元内） | 用户级 + 地域级 | 两级路由表的一致性、二维容量规划 |
| 分层单元化 | 按数据分档（不改键） | 强一致档 = 1 / 弱一致档可多 | 按一致性档位 | 分档需人工裁决并长期维护、三套水位与预案 |
| AI 单元化 | Cell（状态归属） | 状态 1（Cell 内）/ 无状态不限 | 算力 + 状态 | GPU 静态切分、利用率下降、副本数乘 N |

#### 3.2.1 用户单元化

- **被什么约束逼出来**：绝大多数业务请求天然带一个稳定且唯一的用户键，而这个键在入口就能算出来——这是最省额外映射的切法。
- **结构**：

  ```text
  请求 ──▶ 接入层：CellID = Hash(userId) mod N（取模路由）   （染色：请求头带 cellId）
              │
        ┌─────┴──────┬────────────┬─────────────┐
      Cell 0       Cell 1   …   Cell N-1
        └─ 应用（账户 / 订单 / 推荐 全在单元内）
           DB 分片(0)   Cache 分片(0)   MQ 分片(0)
  约束：同一 userId 的所有写入者都在同一 Cell 内（单元内闭环）
  ```

- **为什么这样设计有效**：因为归属是一个在入口可计算的确定性函数、且 cellId 能沿调用链一路传递，所以同一用户的所有读写都落在一个 Cell 内完成，正常路径下跨 Cell 调用为零；「用户数据集中」这条优点由此成立。
- **代价**：三层必然成本——① 路由层成为全局共享组件，必须无状态、可热更新、可预置降级路由表，否则它就是新的单点；② 数据被切了 N 份，跨用户聚合（全站 UV、全局 GMV）必须另建汇总链路；③ 每个 Cell 的容量要按「失效后由剩余 Cell 承接」预留，容量系数约 N/(N−1)【推算：12 个 Cell 时 12/11 ≈ 1.09，即约 9% 额外容量；4 个 Cell 时 4/3 ≈ 1.33，即约 33%】。
- **失效点**：当流量集中到少数键上（大 V、头部商家、秒杀单商品）时，「同一键必然落同一 Cell」这个优点会反转成「热点必然压垮某个 Cell」——因为路由函数对该键是确定性映射，命中同一个 Cell，加机器无法把该键摊开；只能在 Cell 内对该键单独再分片、加副本，或把该键整段迁到专用 Cell。
- **真实使用**：阿里 2015 年双 11 首次大规模应用单元化部署，此后演进到「三地五中心」（该演进年份本书内两处口径不一——[主文件 §1.4 演进历程](01-cell-based-architecture.md) 记 2018、§07 容灾主文件记 2019，本节不锁定具体年份；该时间线为本书整理、未逐条附外部出处，以阿里公开材料为准；可按「阿里五彩石单元化」「阿里三地五中心」检索官方公告与技术文章核验）【经验】。多数电商交易系统的做法是「userId 哈希桶 + 网关路由 + 单元内闭环」三件套【经验】。
- **与相邻模式的边界**：判断它是否被正确使用，只看一个问题——**除用户请求之外，还有哪些写入入口拿不到 userId？** 这些入口是必须补键，还是必须改为由 Cell 内作业执行？两个都做不到时，应该换模式，而不是加更多 Cell。

#### 3.2.2 地域单元化

- **被什么约束逼出来**：数据本地化合规（数据不得出境 / 出省）与跨地域物理延迟——当这两条之一成为硬约束时，切分键只能取「地理位置」，取 userId 反而会把数据搬到违规或超预算的地方。
- **结构**：

  ```text
  地域键（由 GSLB / 客户端上报 / 账号注册地判定）
        │
   ┌────┴─────┬──────────┬──────────┐
  华东域 Cell   华南域 Cell   华北域 Cell
   └─ 应用 + DB + Cache + MQ（域内自包含）
  → 归属键 = 「这份数据允许落在哪个地理域」，与用户量分布无关
  ```

- **为什么这样设计有效**：因为 Cell 与地理域绑定，请求可以在离用户最近的一层终止、数据也落在合规允许的边界内，「就近接入」与「合规边界」这两个目标同时满足；这一条是 hash 切分无论怎么调都拿不到的。
- **代价**：① 路由无法在服务端做纯函数判定，必须依赖 DNS / GSLB / 注册地这类外部信息，缓存过期会打错域；② 每个地理域要持有能被路由到它的全部数据，存储成本按域数放大；③ 跨域写入要么直接禁止（把写收敛回单一主域），要么付冲突消解的成本——这与 hash 切分不同，后者天然是单写入者。
- **失效点**：当用户跨地域移动（出差、搬迁、跨境）时，「就近接入」这个优点会反转成「重归属成本」——因为归属键由「当前所在地」决定，用户一移动，其数据就必须跨域迁移；迁移期间要么双写、要么冻结写入，且迁移本身受合规检查约束（可能根本不允许跨域）。
- **真实使用**：这一类切分主要出现在两个场景——合规要求数据本地化、以及物理延迟压不到预算内的全球服务【经验】。需要区分：Netflix 的多地域主动-主动常被举作地域切分的例子，但按本章 [§ 6 落地实践](01-cell-based-architecture-section-6-sec6.md) 的记录，其账号是**按 account_id 哈希归属主区**、邻区只做只读副本，这属于本节的「复合单元化」，不是纯地域切分。判断方法是问一句：**用户换了所在地之后，数据要不要跟着搬？** 要搬 = 地域单元化，不搬 = 复合 / 用户单元化。
- **与相邻模式的边界**：地域单元化的成本高峰不在稳态，而在**迁移期**——重归属期间要双写或冻结写入，且受合规检查约束。因此它的可行性判据不是「有地域」，而是「有没有一套可执行、可回滚的重归属流程」；没有这个流程时，应该改成「地域只读副本 + 主域写」。

#### 3.2.3 业务单元化

- **被什么约束逼出来**：业务键比用户键更稳定、且各业务域之间没有共享事务——例如以机构、渠道、产品线为主体的系统，用户键根本不唯一。
- **结构**：

  ```text
  接入层 ──▶ 「这是哪个业务域的请求」──▶ 业务 Cell
     ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
     │ 用户 Cell     │ │ 商品 Cell     │ │ 订单 Cell     │
     │ 应用+DB+Cache│ │ 应用+DB+Cache│ │ 应用+DB+Cache│
     └──────┬───────┘ └──────┬───────┘ └──────┬───────┘
            └──── 同步跨 Cell 调用（下单要查用户 + 商品 + 库存）────┘
  → 归属键是「业务类型」；一次下单天然跨 3 个 Cell
  ```

- **为什么这样设计有效**：因为每个 Cell 只承载一个业务域的读写，单业务域的抖动不会污染其他业务域，且各域可独立扩缩容、独立发布；「业务边界清晰」在**变更维度**上确实成立——改订单逻辑不必动商品 Cell。
- **代价**：① 跨 Cell 同步调用进入请求主路径，延迟随所跨 Cell 数累加；② 事务边界被切开，跨域的数据一致性要靠分布式事务或补偿，而协调者本身就是新的共享组件；③ 每个业务域都要按全量峰值预留容量（因为它承接的是全站该业务域流量），冗余比 hash 切分更贵。
- **失效点**：当一次业务请求需要多个业务域的数据时，「业务边界清晰」这个优点会反转成「每个请求都跨 Cell」——因为归属键（业务类型）与请求实际访问的集合（多个业务域）不重合，跨 Cell 同步调用成为常态，任一 Cell 抖动都会顺着调用链传导；单元化本应收敛故障域，结果把故障域从「1 个机房」变成「N 个互相依赖的机房」。
- **真实使用**：金融与核心交易系统按业务域切分是常见做法【经验】，其前提是域间以异步消息为主、同步调用极少。阿里三层拆分中的「业务单元（BU）」是业务维度上的一层，但它的写入归属最终落在**逻辑单元（user_id 哈希桶）**上（见同章 [§ 6 落地实践](01-cell-based-architecture-section-6-sec6.md)），也就是业务维度叠在用户键之上，而不是单独使用——这一点值得照抄：**业务切分负责『谁的地盘』，用户键负责『写入归属』**。
- **与相邻模式的边界**：业务单元化只有在「域间同步调用比例足够低」时才成立，因此落地顺序应该是**先把域间同步调用改成异步消息，再切业务 Cell**；反过来做的团队几乎都会退回共享库。

#### 3.2.4 复合单元化

- **被什么约束逼出来**：单一键不够用——既要「数据集中」（要用户键），又要「就近与合规」（要地域），两者不能互相替代。
- **结构**：

  ```text
  两级归属：先按用户键收敛写入，再按地域决定部署位置
    userId ──hash──▶ 逻辑单元 L（0..N-1）
                        │
                 归属表：L → 地理域（华东 / 华南 / 华北）
                        │
                  域内把 L 映射到具体 Cell
  → 两条腿：用户键管「几个写入者」，地域管「数据落在哪」
  → 代价转移：重归属从「用户移动时发生」变成「容量失衡时发生」
  ```

- **为什么这样设计有效**：因为写入者数量由用户键决定（单写入者、域内事务可解），数据落点由归属表决定（就近与合规可满足），所以它同时拿到了用户单元化的写入收敛与地域单元化的位置控制；这解释了为什么大厂落地时几乎都是复合形态。
- **代价**：① 两级路由表都要能独立热更新与降级，路由正确性从「一个函数对不对」变成「两张表一致不一致」；② 容量规划变成二维问题，任何一个域的用户量增长都要判断是「加 Cell」还是「搬单元」；③ 归属表本身成为强管控对象，改动要走变更流程。
- **失效点**：当两级键的分布不均匀时（例如某地域用户量远大于其他地域），「就近 + 数据集中」这个优点会反转成「地域间容量不均」——因为两级切分把用户量与地理域绑死了，冷域的 Cell 空转、热域的 Cell 打满，而重平衡要跨域迁移数据，可能恰好被合规挡住（最需要搬的时候搬不动）。
- **真实使用**：美团外卖的多 Region 单元化采用「3 Region 按 user_id 哈希归属 + 单元内闭环 + 邻区可接管」的形态（本章 [§ 6 落地实践](01-cell-based-architecture-section-6-sec6.md) 的案例记录把出处记为「美团技术博客 2019」，未给文章标题与链接；可按「美团外卖多 Region 单元化」检索其技术博客原文核验）【经验】；Netflix 的账号按 account_id 哈希归属主区、邻区只读副本，是同一族形态。
- **与相邻模式的边界**：复合单元化的判据是**归属表会不会频繁改**。如果归属表一年改不了几次，两级成本换来的隔离是划算的；如果归属表每周都要动（用户量波动、机构重组），说明第二级键不稳定，应该改成「用户键 + 容量调度」而不是「用户键 + 固定地域」。

#### 3.2.5 分层单元化

- **被什么约束逼出来**：不同数据的**一致性预算**差一个数量级以上【经验】——订单与支付必须单写入者 + 同步提交，评论与推荐可以丢、可以重算，用一套一致性去覆盖两者必然要么过度、要么不足。
- **结构**：

  ```text
  按一致性分档（同一套 Cell 内分三档，档位决定写入路径）
  ┌──────────────────────────────────────────────────────────┐
  │ 核心 Cell（订单 / 支付）   强一致    单写入者 + 同步提交      │
  │ 重要 Cell（商品 / 库存）   最终一致   异步同步 + 可重放        │
  │ 普通 Cell（评论 / 推荐）   弱一致     可丢可重算 + 冷启动容忍   │
  └──────────────────────────────────────────────────────────┘
  纪律：一份数据只属于一个档位；跨档流量走异步，不进入任何提交路径
  ```

- **为什么这样设计有效**：因为一致性预算被显式分档、且分档结果直接决定写入路径（同步提交 / 异步 / 可丢），所以强一致只花在必须的链路上，其余链路可以在峰值下自由降级；「无跨 Cell 调用」在核心档内仍然保持。
- **代价**：① 「这份数据属于哪一档」必须由人裁决并长期维护，分档错了会直接体现在提交路径的延迟与可用性上，而且错误通常在上线后才暴露；② 跨档读取（核心档读弱一致档的画像）要接受陈旧数据，业务方需要显式知道这一点；③ 三档意味着三套容量水位与三套降级预案。
- **失效点**：当强一致档的数据量或访问量增长时，「把强一致限制在少数链路」这个优点会反转成「强一致档成为全站瓶颈」——因为强一致要求单写入者 + 同步提交，其吞吐无法通过加只读副本摊开，只能按写入者所在 Cell 的规格上限走；这时必须把该档再拆档（例如把「支付」从「订单」里再分出来），而不是加机器。
- **真实使用**：交易类系统把「资金 / 库存」放强一致档、「行为 / 画像」放弱一致档是通行做法【经验】。阿里案例中记录的「单元内强一致本地库 + 跨单元异步同步」是两档形态（见同章 [§ 6 落地实践](01-cell-based-architecture-section-6-sec6.md)）。
- **与相邻模式的边界**：分层单元化最容易和「微服务按能力拆分」混同——后者切的是应用，前者切的是**写入路径与降级顺序**。判据是：如果某份数据被移出强一致档之后，业务方无法接受「读到几秒前的值」，那它就不该被分档，而应该单独成一个强一致域。

#### 3.2.6 AI 单元化

> **读法说明**：这个模式的判据是**状态归属**（有状态跟 Cell 走），不是「用不用 GPU」；「每 Cell 常备 GPU 产能」与「Agent Cell」的级别分别是 L2 与 L3、**不要预设**（见 [§5](01-cell-based-architecture-section-5-ai.md) §5.1 与 §5.7：GPU 池化「不要为每个 Cell 常备产能」、Agent「不要为 Agent 单独建 Cell」）。下表因此把它按「状态归属」定义，GPU 预留只是代价项、不是默认结论。

- **被什么约束逼出来**：有状态推理（会话上下文、向量索引）不允许跨 Cell 取用——跨 Cell 取状态会同时引入冷启动延迟与合规风险，而 GPU 产能的分配又要可控。
- **结构**：

  ```text
  Cell k（每 Cell 一套算力与状态）
   ├─ GPU 池（仅当推理依赖 Cell 内状态时才按 Cell 预留，属 L2；不跨 Cell 调度）
   ├─ 模型副本（同一版本，随 Cell 一起发布）
   ├─ Agent 集群（会话上下文写在本 Cell 的存储里）
   └─ 向量索引（本 Cell 用户的向量，避免跨 Cell 检索）
  无状态推理请求 → 共享 GPU 池（可跨 Cell 调度）
  → 边界由「有没有状态」划定，不由「用不用 GPU」划定
  ```

- **为什么这样设计有效**：因为会话上下文与向量索引这类状态被放在 Cell 内，推理请求不需要跨 Cell 取状态，端到端延迟由本 Cell 资源决定、可预测且可隔离；同时模型副本与 Cell 对齐，发布与回滚可以按 Cell 灰度。
- **代价**：① GPU 产能必须按 Cell 预留，不能把闲置 Cell 的卡借给忙 Cell，利用率必然下降；② 模型副本数乘 Cell 数，显存与版本管理成本线性放大；③ 发布必须保证 N 份副本一致，否则同一用户换 Cell 会得到不同模型行为。
- **失效点**：当推理负载在 Cell 间分布不均时（少数 Cell 用户活跃、多数沉寂），「延迟可预测」这个优点会反转成「利用率与延迟二选一」——因为 GPU 预留是配置项而不是弹性资源，想跨 Cell 调度有状态请求就必须把上下文搬过去，而搬上下文恰好是本模式要避免的那件事。缓解手段只有两条：把有状态推理的比例降下来（会话外置成无状态），或者接受「产能按 Cell 静态切分、利用率换确定性」。
- **真实使用**：这一类形态目前主要出现在对延迟与合规有硬要求、且推理依赖用户级状态的场景【经验】。**可自行核验的判断方法**：问它的推理平台「这个 Cell 的卡能不能借给别的 Cell」——能借就说明只是共享池 + 分区部署，不是 AI 单元化；再问「会话上下文存在哪」，存在 Cell 内才符合本模式。
- **与相邻模式的边界**：AI 单元化是唯一一个**边界由状态而不是由数据归属划定**的模式。因此它可以与前面任何一个模式叠加（在用户单元内再按状态切算力），但单独使用时，它不提供任何「用户数据隔离」的保证——这两件事经常被混为一谈。

六个模式共享同一条前提与同一组代价，值得单独写出来：

- **共享前提**：归属键必须在**所有写入入口**都拿得到，且全链路染色一致。任一个入口漏了染色，模式名再正确也不产生隔离——这正是 3.5 把「染色泄漏」单列一行的原因。
- **共享代价**：运维对象乘 N（N 份配置、N 份发布、N 套水位）、容量按 N−1 预留、跨 Cell 对账链路必须存在。这几项与选了哪个模式无关，只与 Cell 数有关。
- **共享失效前提**：共享组件清单没有收敛时，所有模式都会退化成「把共享单点换个位置摆放」。因此正确的落地顺序是**先收敛全局数据，再谈 Cell 切分**，而不是先切 Cell 再补全局表。

把「共享代价」按 Cell 数展开，就能看出为什么大厂最后都把 Cell 数收在两位数【经验】——发布份数与演练组合数是线性以上增长，而容量项与影响面按 1/N 递减。

| Cell 数 N | 单 Cell 故障的影响面 | N−1 接管所需额外容量 | 发布 / 配置份数 | 演练组合数 |
| --- | --- | --- | --- | --- |
| 4 | 25% | 约 33% | 4 | 4（单个失效）/ 6（两个同时失效） |
| 12 | 8.3% | 约 9% | 12 | 12 / 66 |
| 24 | 4.2% | 约 4% | 24 | 24 / 276 |
| 100 | 1% | 约 1% | 100 | 100 / 4950 |

【推算】影响面 = 1/N；额外容量 = N/(N−1) − 1；组合数 = C(N, k)。表里可以看出两件事：**隔离收益按 1/N 递减**（4 → 100 时影响面只从 25% 降到 1%），而**单点与双点演练的组合数按 N² 增长**（12 → 100 时从 66 涨到 4950）。这就是「Cell 越多越好」的反例。

这张表也解释了 12~24 这个常见区间是怎么来的【经验】：12 以后影响面的改善已经很有限（8.3% → 4.2%），而演练组合数从 66 涨到 276；继续加 Cell 得到的是「更小的爆炸半径」和「更少的演练覆盖」，后者恰好会让前者的收益无法被验证。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 写多、请求都带稳定用户键、要求爆炸半径收敛（电商交易） | 用户单元化 | 业务单元化会让一次下单跨多个 Cell | 所有会写数据的入口能否拿到 userId |
| 用户键稳定 + 有数据本地化或就近约束（内容平台） | 复合单元化（用户键 + 地域） | 纯地域切分无法收敛写入者；纯 hash 切分满足不了本地化 | 两级键的分布是否大体均匀 |
| 业务键稳定、域间以异步为主、用户键不唯一（金融交易 / 核心系统） | 业务单元化 | 强行按用户切会切碎强一致的业务事务 | 是否存在稳定业务键、跨域同步调用比例 |
| 无稳定用户键、负载天然按地域分布（全球化服务） | 地域单元化 | 按用户 hash 切会让重归属成为常态 | 用户移动频率、合规是否允许数据跨域 |
| 延迟与一致性要求差异大（交易与推荐并存） | 分层单元化（按一致性分档） | 全站一套一致性要么过度、要么不足 | 数据能否被明确分档，且分档不频繁变 |
| 有状态推理为主、延迟与合规有硬约束（AI 推理） | AI 单元化（状态归属在 Cell 内） | 共享 GPU 池无法保证跨 Cell 取状态的延迟 | 推理是否依赖 Cell 内状态 |
| 规模小、共享组件清单短（内部系统） | 不做单元化 | 单元化让运维对象乘 N，收益为负 | 共享组件清单长度、可接受的故障时长 |
| 大促 / 脉冲峰值、日常水位很低 | 用户单元化 + 分层一致性 | 纯单元化只切了流量，峰值下核心档仍受单写入者上限约束 | 峰值是否来自少数键（若是，先解热点） |
| 多业务共用一个交易库、故障串联 | 先按业务拆单元，再按用户键收敛写入 | 只按业务拆会让跨域调用进主路径 | 各业务域之间的同步调用比例 |
| 有数据本地化 / 出境合规要求 | 地域单元化，或复合单元化（合规域内再哈希） | 纯 hash 切分无法保证数据落点 | 合规是否允许数据跨域迁移 |
| 已有异地多活但未做键级归属 | 先补用户单元化，再谈 Cell 数 | 多地域全量与键级归属解决的是不同问题（前者要付冲突消解） | 每个业务键当前有几个可写地域 |
| 有状态推理上量、延迟需可预测 | AI 单元化（状态归属在 Cell 内；GPU 池与模型副本是否按 Cell 预留属 L2，见 [§5](01-cell-based-architecture-section-5-ai.md)） | 共享池无法保证跨 Cell 取状态的尾延迟 | 推理是否依赖用户级状态 |

表后要点：**最常被误选的一对是「用户单元化」与「业务单元化」**。误选的实际后果有两种，且都不报错。其一，在只有用户键稳定、业务域互相调用的系统里选了业务单元化——每次请求跨 2~3 个 Cell 的同步 RPC，延迟随跨 Cell 数累加，单元化本应收敛故障域，实际把故障域扩成了 N 个互相依赖的 Cell。其二，在以机构 / 渠道为主体、用户键不稳定的系统里选了用户单元化——大量写入入口（消息消费、定时任务、运维脚本）拿不到归属键，数据被写进错误 Cell，表现为「表面正常、查询偶发不一致」，排查成本极高。判据只有一句：**先数「会写数据的入口」，再看它们能不能都拿到同一个键。**

再补一条常被忽略的判据：**「共享组件清单长度」比「业务规模」更能决定要不要做单元化**。一个规模不大、但把配置、字典、序列、额度都收敛成可独立降级的系统，做用户单元化的收益是真实的；而一个规模很大、但全局表与全局序列散落在各处的系统，切完 Cell 之后故障域几乎没变——下面的清单应该在做决策之前就列出来，而不是做完之后才补。

第二常被误选的一对是**「地域单元化」与「复合单元化」**：看到「业务跑了多个地域」就直接按地域切数据，结果用户一跨地域就触发重归属；正确的问法是「跨地域的是**部署**还是**数据**」——只有数据也要按地域停住（合规）时才取地域做归属键，否则应该用用户键归属、地域只作部署位置。

表中「不做单元化」这一行（内部系统）不是保守选项，而是有硬依据的：单元化的固定成本是运维对象乘 N 与 N−1 容量预留，如果共享组件清单本来就短、故障容忍度也高，这些成本换不回任何可用性——规模小不是「暂时不做」的理由，而是「这条路的成本结构不划算」的理由。

### 3.4 组合模式：真实系统不会只用一种

- **单元化 + 异地多活**：单元化负责「键级归属 + 自包含部署」，异地多活负责「地域级存活」。边界是**跨地域只同步、不并写关键业务键**——并写会让单写入者前提失效。运维代价是管控面必须同时支持「按 Cell」与「按地域」两级路由表，且两级都要能独立降级。适合规模：单地域容量已经吃紧、且业务能接受跨域只读副本带来的秒级陈旧【经验】。
- **单元化 + 分层一致性**：单元化给边界，分层给每档数据各自的写路径与降级预案。边界是**一份数据只属于一个档位**，跨档只走异步。运维代价是三套容量水位与三套降级演练。适合规模：核心链路（资金、库存）与推荐 / 画像共存、且大促期间需要「非核心先降级」的系统。
- **单元化 + 混沌工程 / 按 Cell 灰度**：单元化让故障注入与灰度发布的爆炸半径都可按 Cell 计量（主文件 §1.3 把它们列为相邻章节的直接关系）。边界是**注入与灰度都必须在生产真实流量下做**，否则验证不到路由与容量重分配。运维代价是每次演练要做数据护栏（避免污染真实用户资产）。适合规模：Cell 数已达到两位数、切流已自动化到无需人工决策的系统。

这三组组合有一个共同点：**单元化只负责「切」，不负责「切完之后的事」**。存活靠异地多活，降级靠分层一致性，可信度靠混沌与灰度。因此组合的引入顺序也基本固定——先做单元内闭环，再做按 Cell 的灰度，最后做异地多活；顺序颠倒会让每一次演进都要回头补前一步的前提。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| Cell 数量过多 | Cell 数远超两位数，每次发布要改 N 份配置、演练排期排不完 | 运维对象与容量冗余随 N 线性增长，单个 Cell 变小后反而更难定位故障 | 把「隔离更细」当成目标，而不是把「故障域可管理」当成目标 | 回到 12~24 这个量级【经验】，隔离不足的部分用分层档位解决 |
| 热点用户 | 单个 Cell 的 CPU / 连接数周期性尖峰，且尖峰总是同一个 userId | 路由是确定性映射，热点键无法摊开；一个键能打挂一个 Cell，等于把爆炸半径还给了那部分用户 | 容量按均值规划，没做键级分布分析 | 热点识别 + 单键再分片 / 专用 Cell；把「单元内副本」做成可开关的能力 |
| 跨 Cell 调用频繁 | 链路追踪里同步跨 Cell span 占比高，P99 随跨 Cell 数阶梯式上升 | 切开的故障域被同步调用重新连起来：任一 Cell 抖动都传导到全链路 | 归属键选错（用业务键切、按用户访问），或单元内闭环没做完就先接了跨域需求 | 把跨 Cell 调用改成异步消息；数据按归属键收敛；确需实时读就做 Cell 内只读副本 |
| 资源浪费 | 各 Cell 利用率长期低于一半，扩容时按「每 Cell 都能扛全站峰值」算 | 容量系数从 N/(N−1) 变成 N，等于为不存在的故障付 N 倍成本【推算：N=12 时两种口径相差约 11 倍】 | 用「安全第一」替代容量模型，没定义故障接管的目标范围（N−1 还是 N−2），于是扩容评审时算不出「为什么加了 Cell 单位成本反而更高」 | 明确接管目标（通常 N−1），按此预留；把容量系数写进决策记录，并让每个 Cell 的水位单独可见 |
| 忽视全局数据 | 配置表、商品字典、全局序列放在某个 Cell，其他 Cell 访问它变慢或写错（健康时没有任何征兆） | 全局表成为新的共享单点，故障域切分被绕过；典型暴露是「这个 Cell 挂了，别的 Cell 连配置都读不到」 | 全局数据「量小、改得少」，被当作可以随手放进去的东西 | 把全局数据列成清单，放中心化存储（配置中心 / 全局服务），指定降级读路径，并规定它不得成为写路径的强依赖 |
| 染色泄漏（本文件新增） | 消息消费、定时任务、离线回填、数据修复脚本写的记录出现在错误 Cell，且不报错 | 归属键在这些入口缺失，写入落到默认 Cell；问题只在查询时以「偶发不一致」的形式暴露 | 只在用户请求入口做了路由染色，把「所有会写数据的入口」当成了「所有请求」 | 把会写数据的入口列成清单逐个检查归属键；拿不到键的改由 Cell 内作业执行 |
| 把 Cell 当部署分区（本文件新增） | Cell 之间仍有共享库或共享缓存，只是把应用分了几组部署 | 共享存储是共同故障源，故障域实际没变；隔离承诺是纸面上的 | 把「按机房分组部署」等同于「自包含」 | 逐项验证每个 Cell 的 DB / Cache / MQ 是否独立；共享项必须列清单并给出降级路径 |

展开三个最危险的：

**跨 Cell 调用频繁**最危险的地方在于它不是故障，而是「一直有点慢」。单元化的全部收益都建立在「故障不传导」上，而同步跨 Cell 调用恰好是把传导路径重新接回来：延迟上，一次请求跨 3 个 Cell 就意味着端到端 P99 由这三个 Cell 的尾延迟共同决定；可用性上，任一 Cell 的抖动都会变成全链路的抖动。它在生产中的典型暴露方式是**大促期间某个非核心 Cell 的慢查询把核心链路拖垮**，而监控上看到的是核心链路超时——排查方向会先指向核心 Cell。

**热点用户**的暴露方式更有欺骗性：因为路由是确定性映射，热点键永远命中同一个 Cell，所以现象是「某一个 Cell 的指标异常、其他 Cell 正常」，看起来像「这一个 Cell 部署有问题」。它的机制后果是**隔离承诺在那一部分用户身上失效**——12 个 Cell 中 1 个被打挂，全局影响约 1/12 ≈ 8.3%【推算：故障 Cell 占比 = 1/N_Cells】，但如果被打挂的是头部商家所在的 Cell，业务口径的影响远大于这个比例。

**染色泄漏**的暴露方式是「不报错」。写入落到错误 Cell 后，单条记录本身是合法的，只有在跨 Cell 对账或全量查询时才表现为缺失或重复；因此它的平均发现时间最长，而修复要回填数据 + 补全入口 + 校验历史，成本远高于在入口补一个归属键。这也是 [§ 7 与其他方法对比](01-cell-based-architecture-section-7-sec7.md) 把它列为最贵隐性故障的原因。

这三条的共同点是**都不通过「服务挂了」这种形式暴露**：跨 Cell 调用频繁表现为「一直有点慢」，热点用户表现为「某个 Cell 指标异常」，染色泄漏表现为「偶发不一致」。因此它们不会触发常规的可用性告警，只能靠 3.7 自检清单里的那几项指标（跨 Cell 占比、键级热点分布、跨 Cell 对账差异）提前发现。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：**规模或访问模式跨过某个阈值时，原来正确的模式会变成错的**。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单机房容量到顶、但仍在单地域 | 不做单元化（单库分表） | 单机房故障仍是 100% 影响；分表只切了数据，没切部署与故障域 | 用户单元化（先做单元内闭环 + 网关路由） | 中：动应用与数据路由，不动业务语义 |
| Cell 数从个位数涨到两位数 | 用户单元化（手工维护路由） | 路由表与发布份数手工维护会出错，切流靠人判断 | 复合单元化（归属表 + 自动化切流 + 预置降级路由） | 中偏大：要建归属表与两级路由的管控面 |
| 业务跑到多地域 | 用户单元化（单地域全量） | 跨地域延迟进入主路径，且合规开始提要求 | 复合单元化，或对合规场景转纯地域单元化 | 大：要动数据归属与迁移路径，且难回退 |
| 强一致档数据量增长到单 Cell 上限 | 分层单元化（三档） | 强一致档受单写入者 + 同步提交的吞吐上限约束，加副本无效 | 在强一致档内再拆档（支付 / 订单 / 库存各自成档） | 中：动事务边界，要重做补偿与对账 |
| 有状态推理上量、延迟成为硬指标 | 共享 GPU 池 + 分区部署 | 跨 Cell 取会话上下文与向量索引带来尾延迟与合规问题 | AI 单元化（状态归属在 Cell 内；GPU 池按 Cell 预留属 L2，见 [§5](01-cell-based-architecture-section-5-ai.md)） | 大：产能规划方式改变，利用率下降需业务认可 |
| 共享组件清单变长（全局表、全局序列、全局额度） | 任意单元化模式 | 共享组件成为新的单点，故障域切分被绕过 | 先把共享组件收敛成可降级服务，再谈 Cell 切分 | 视清单长度而定，通常先做这一项再谈其他 |
| 业务从单产品扩到多产品线 | 用户单元化（业务维度不下沉到 Cell 层） | 按产品线切 Cell 会让跨产品请求（用户中心、支付）跨 Cell | 保持 Cell 按用户键切，产品维度用应用侧隔离 | 小：不动数据归属，只动应用边界 |

一条规律：**迁移成本最高的是「数据归属方式」的变化**（分表 ⇄ 单元化 ⇄ 异地多活），因为它要动数据本身与全链路的键传递；而路由实现、Cell 数、容量水位的调整是可增量执行的。可操作的做法是把迁移拆成「先只读切换（新旧路径比对，差异挂账）→ 再只写切换（旧路径降级为校验）→ 最后下线旧路径」三段，每段之间留一次完整对账周期。

补充两点判据。其一，**跃迁的触发条件应该是可观测的**：不是「感觉该升级了」，而是「单 Cell 容量水位连续多个大促周期超过某条线」「跨 Cell 同步调用占比超过某条线」「重归属工单数量超过某条线」这类可以由监控直接给出的信号——把触发条件写成指标，跃迁才不会变成一次拍脑袋的大重构。其二，**每一次跃迁都必须留下可回退路径**：归属方式改变是不可逆的（数据已经按新键分布），所以回退路径通常表现为「旧键的映射表仍然保留一段时间 + 双写校验」，而不是「把新架构删掉」。这两点决定了一个团队能不能安全地走完 3.6 表里的任意一行。

### 3.7 自检清单

- [ ] 所有「会写数据的入口」（用户请求 / 消息消费 / 定时任务 / 离线回填 / 运维脚本 / 数据修复 / Agent 工具调用）是否都能拿到同一个归属键？拿不到的是不是已经列进清单？
- [ ] 归属键是否是**稳定键**（用户注册即确定），而不是会随状态变化的键（所在地、所属机构）？
- [ ] 共享组件清单是否列全了？清单上任何一项挂掉，影响面是全站还是单 Cell？
- [ ] 正常路径下的同步跨 Cell 调用占比是多少？有没有任何一个接口的跨 Cell 数超过 1？
- [ ] 容量是按「任意 1 个 Cell 失效后由剩余 Cell 承接」（N−1）预留的，还是按「所有 Cell 同时扛全站峰值」（N）预留的？两者的成本差是多少？
- [ ] 路由表能否热更新、能否预置降级路由？切流是否需要人工决策？
- [ ] 每个 Cell 的容量水位是否单独可见？有没有做键级热点分布分析（而不是只看均值）？
- [ ] 强一致档的数据是否被显式列成清单，且这份清单最近一次更新是什么时候、谁审过？
- [ ] 跨档读取是否会读到陈旧数据，业务方是否知道并接受？
- [ ] 全局唯一性（全局序列、全局库存池、全局额度）由谁承担？是否被误认为单元化顺带解决了？
- [ ] 跨 Cell 对账链路是否存在？染色泄漏若发生，多久能被发现？
- [ ] 混沌演练是否在真实流量下按 Cell 做过，且验证过容量重分配而不只是验证实例重启？

自检的用法：**上面 12 项里只要有 3 项以上答不上来，就不该开始切 Cell**，因为答不上来的项几乎都是后面会以事故形式暴露的项（归属键覆盖、共享组件清单、容量系数、对账链路）。反过来说，能答完这 12 项的系统，即使暂时不做单元化，也已经具备了把故障域讲清楚的能力——这本身是大促与容灾评审里最有价值的一份材料。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 用户键稳定、单地域、要收敛爆炸半径 | 用户单元化 | 归属在入口可算、cellId 可全链路传递 → 单元内闭环 |
| 用户键稳定 + 数据本地化 / 就近要求 | 复合单元化 | 用户键定写入者数量，归属表定数据落点，两个问题分开解 |
| 业务键稳定、域间异步为主 | 业务单元化 | 单域故障不污染他域；但必须先把跨域同步调用改成异步 |
| 无稳定用户键、负载按地域分布 | 地域单元化 | 合规与延迟同时满足；代价是重归属成为常态流程 |
| 一致性预算差异大 | 分层单元化 | 分档直接决定写入路径，强一致只花在必须的链路上 |
| 有状态推理、延迟与合规硬约束 | AI 单元化（状态归属在 Cell 内） | 状态留在 Cell 内，延迟可预测；代价是 GPU 利用率下降（每 Cell 常备 GPU 属 L2，见 [§5](01-cell-based-architecture-section-5-ai.md)） |
| 规模小、共享组件清单短 | 不做单元化 | 运维对象乘 N 的代价大于收益，先做同城双活即可 |
| 合规要求数据落点可控 | 地域单元化（域内可再哈希） | 合规是位置约束，hash 切分不改变数据位置 |

> 本节小结：本主题下**决定模式选择的唯一那条约束，是「请求能不能在入口被一个稳定键判定归属、且所有写入者都拿得到这个键」**。它决定了能不能切；而「每份数据有几个写入者」决定了切完要不要付冲突消解的成本。Cell 数、冗余比例、路由实现、发布方式全部是这两条的下游结果——键定得住，单元化能把跨地域一致性问题降级为域内事务；键定不住，任何切分都只是把共享单点换个位置摆放。
>
> 判断顺序也由此确定：**先列共享组件清单，再数写入入口，最后才选模式**。共享组件清单决定了切完有没有隔离，写入入口决定了能不能切，模式只是对这两条答案的命名。三个反模式（跨 Cell 调用频繁、染色泄漏、把 Cell 当部署分区）都是在这两步没做完时选择模式的直接后果。
>
> 💡 **思考锚点**：拿本节 12 项自检对着你的系统量一遍——归属键是否覆盖了全部「会写数据的入口」、共享组件清单列全了没有、容量是按 N−1 还是按 N 预留的；再问一句：你的跃迁触发条件是监控能直接给出的信号，还是一句「感觉该升级了」？
>
