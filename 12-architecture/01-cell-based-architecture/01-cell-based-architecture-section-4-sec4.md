## 4. 工程实现

单元化在 §3 里是一张模式对照表；本节要回答的是另一类问题：**模式选定之后，先做什么、怎么知道做对了、做完手上多出什么、存量系统怎么办、多久能退出双轨。** 本文件同时面向两类读者——

- **从零搭建**：新系统，还没有按业务键切过数据。Step 1 → Step 4 按顺序走完即可，重点是 Step 2（把归属键做成全链路契约）与 Step 4（在真实流量下验证容量重分配）。
- **存量改造**：已经分库分表、或已在多机房部署但键级归属没做。先读 4.4，再回到 Step 2 与 Step 3；对这类读者，Step 1 的前半程是**盘点**而不是设计——共享组件清单与写入入口清单都要从既有系统里查出来（次序与 §3.1 的三件事一致），这两份清单决定了 Cell 数能取多少、键的改造量有多大。

两条路线的分岔点是**归属键在现有入口上能不能拿全**，而不是 Cell 数。这一条也决定了本节其余部分对你有多少约束力：拿不全的入口清单本身就是待办清单。

### 4.1 落地步骤

**Step 1：业务域切分与共享组件盘点（约 2–6 周【经验】；取决于共享组件清单长度，而不是 Cell 数）**

1. 列共享组件清单：全局配置、全局序列、全局库存池、全局额度、维表、搜索索引、注册中心、鉴权，逐项判「挂掉影响全站还是单 Cell」——这份清单的长度是估算 Cell 数（第 4 条）的输入之一。
2. 列出全部「会写数据的入口」——用户请求、消息消费、定时任务、离线回填、运维脚本、数据修复工具、Agent 工具调用——逐条标注它能否拿到归属键。
3. 识别业务键候选（userId / orderId / region），按 §3.1 的三条约束逐项判定：请求能否在入口被一个**稳定的**键判定归属（注册即固定的 userId 是稳定键，「当前所在地」「所属机构」不是）、每份数据有几个写入者、共享组件清单有多长（第 1 条已列出）。
4. 估算 Cell 数量：由第 1 条的清单与运维产能反推（§3.5 的反模式「Cell 数量过多」与 [§7.5 决策树](01-cell-based-architecture-section-7-sec7.md) 都指向 12–24【经验】），而不是先做 4 个再逐步加——重分配比初次分配贵。
5. 设计路由规则：Hash 算法（如 [§6](01-cell-based-architecture-section-6-sec6.md) 案例中记录的 `murmur3` 形态）、容灾策略（邻 Cell 接管）、路由表的存储位置与热更新通道。
6. 定容量的两个口径：接管目标取 N−1 还是 N−2；每 Cell 水位是否单独可见。

- **产物**：① 归属键决策记录（一个键 + 它拿不到的入口清单 + 每个入口的处置方式：补键 / 改由 Cell 内作业执行 / 明确接受写默认 Cell）；② 共享组件清单（每项标注「下沉到 Cell 内 / 本地缓存降级 / 接受它成为共同故障源」）；③ Cell 数初值 + 路由方案 + 单元内闭环边界（哪些调用允许跨域）。
- **判据**：拿第 2 条的入口清单去**代码仓库**抽 3 条非用户入口（一条定时任务、一条消息消费、一条运维脚本），看它们的写入路径上是否真的带着归属键——不是看设计文档上写了没有。再拿第 1 条的清单去线上拓扑里核对每个组件的真实形态与清单上标注的处置是否一致——判据不是「有没有全局唯一实例」，而是「每一项的处置标注是否与线上真实形态相符」（处置只有三种：下沉到 Cell 内 / 本地缓存降级 / 接受它成为共同故障源）。
- **为什么必须这一步 / 为什么在这个位置**：归属键一旦落地就变成跨系统的接口契约（消息格式、调度配置、运维脚本、Agent 工具定义都要带着它），改它等于改所有写入方的签名——所以它必须排在数据切分与路由实现**之前**。共享组件清单则必须排在 Cell 数之前，因为它决定「切完之后到底有没有隔离」；两件事顺序反过来做，会出现「Cell 数已经定为 24，才发现全局库存池还没收编」，那时 N 的取值要重算、容量要重估、部分切分规则要重做。

**Step 2：键与染色的全链路贯通（约 6–12 周【经验】；随入口数量与调用深度增长）**

1. 从入口把归属键与染色标记（cellId / 逻辑单元 ID）透传到全部下游，包括消息头、RPC 上下文、异步任务参数。
2. 对拿不到键的非用户入口做改造，二选一：补键（消息带不上键就改消息格式），或改为由 Cell 内作业执行（定时任务按 Cell 分片跑）。
3. 建立跨 Cell 对账链路（T+1 或小时级），输出「归属算出的 Cell 与记录实际所在 Cell 不一致」的差异条数。
4. 把「跨 Cell 同步调用」做成可观测指标：链路追踪里同步跨 Cell 的 span 占比、每个接口的跨 Cell 数。

- **产物**：全链路染色透传的实现 + 非用户入口的处置记录 + 一份跑得起来的跨 Cell 对账报告 + 跨 Cell 调用占比的监控面板。
- **判据**：抽 3 天的对账报告，看差异条数是否趋向 0 且能逐条归因（属于已知的历史脏数据，还是新增泄漏）；抽 3 个接口的链路追踪，看同步跨 Cell span 数是否 ≤ 1。**判据必须是这两个数，不能是「染色改造完成了」。**
- **为什么必须这一步 / 为什么在这个位置**：染色是「一次决定、全链路遵守」的机制（判定方法见 §3.3 与 [§7.3.3](01-cell-based-architecture-section-7-sec7.md)）——任何一段丢了标记，该段之后的写入就落不到该落的 Cell，而且**不报错**，只在查询时表现为偶发不一致。它必须排在数据切分之前，因为切分一旦开始，「写错 Cell」就从配置问题变成数据搬迁问题；对账链路也必须在这里就位，否则你无法度量改造是否真的在收敛。

**Step 3：数据切分与路由上线（约 8–16 周【经验】；随数据量与双跑时长增长）**

1. DB 水平切分：按归属键水平切到 N 个库（ShardingSphere / Vitess 一类代理分片）。
2. Cache 切分：Redis Cluster 按归属键分片，避免跨 Cell 缓存读取。
3. MQ 切分：Kafka Topic 按归属键分区，保证同一键的事件落在同一分区。
4. 路由层：先只读切换（新旧路由同时算，差异挂账），再只写切换（旧路径降级为校验）。
5. 每个 Cell 的容量水位独立可见。

- **产物**：分片规则与路由表 + 双跑期的差异挂账报告 + 各 Cell 独立水位看板 + 一份「切流与数据迁移分离」的操作规程。
- **判据**：抽 3 张核心表，各取 3 个归属键，看同一键的记录是否只出现在一个 Cell；再演练一次路由表热更新，确认切过去能切回来。数据迁移与流量切换**不得在同一次变更里发生**——判据是「最近一次 Cell 级变更记录里，是否同时改了流量与数据」；答「是」，它就是一次不可回退的操作。
- **为什么必须这一步 / 为什么在这个位置**：数据切分排在染色之后，因为切分的正确性完全依赖「键已在入口被判定」；排在路由之前，因为路由表只是把「归属」这件事对外表达出来，它本身不产生归属。只读切换先于只写切换，是因为只读阶段可以用旧路径做比对（差异挂账），而只写阶段只能靠对账兜底——顺序倒过来，你会失去唯一的参照物。

**Step 4：故障隔离与演练验证（约 4–8 周/轮，之后常态化【经验】）**

1. 单 Cell 故障演练：停一个 Cell，观察流量改派、容量重分配、邻 Cell 水位。
2. 数据一致性验证：跨 Cell 对账，检查消息丢失或重复。
3. 流量调度演练：动态调整 Cell 流量，含热点键的单 Cell 压测。
4. 发布、按 Cell 灰度与混沌注入都必须声明「是否允许影响跨 Cell 共享组件」。
5. 演练必须在生产真实流量下做，每次开数据护栏。

- **产物**：演练剧本 + 演练报告（爆炸半径、切换耗时、邻 Cell 峰值水位）+ 更新后的 Runbook + 共享组件清单的最新版本。
- **判据**：停掉一个 Cell 后，剩余 Cell 的峰值水位 < 100%——只统计「服务没挂」不算通过。每次演练后必须能报出三个数：受影响 Cell 占比、切换耗时（秒）、邻 Cell 峰值水位。
- **为什么必须这一步 / 为什么在这个位置**：容量重分配只有真实流量能验证——测试流量压不出「邻 Cell 接管后叠加自身流量」的水位，而这正是 N−1 预留是否够用的唯一检验。它必须排在切分之后，因为演练对象是 Cell 拓扑本身；也必须排在宣布完成之前，因为演练暴露的问题绝大多数要回到 Step 1 改共享组件清单或改 N，而不是改代码。

**哪一步最常被跳过**：Step 2（键与染色的全链路贯通）。它没有可视化的产出（没有新面板、没有新架构图），验收时也不像 Step 3 那样有「切完了」这个明确节点，于是常被压缩成「入口网关加个 header」。

跳过后第一个出问题的时点**不在投产当天，而在投产后的第一个大促或第一次批量运维**：定时任务与数据修复脚本写进默认 Cell，单条记录合法、查询偶发缺失或重复。它的排查成本远高于在入口补一个归属键，因为它既不报错，也没有稳定的复现路径。

### 4.2 关键技术点

**单元化路由（网关侧）**

- **做法**：网关从请求上下文取归属键，算出逻辑单元 ID，把 cellId 写进请求头并沿调用链透传；路由表由配置中心下发、支持热更新与预置降级路由；网关本地缓存一份路由规则，在配置中心不可达时用本地版本决策；无状态，可水平扩展。
- **机制**：因为归属是一个在入口可计算的确定性函数、且结果能沿链一路传下去，所以同一键的所有读写都在一个 Cell 内完成，正常路径下跨 Cell 调用为零——「单元内闭环」由此成立，而它同时是延迟（少一次跨域 RTT）与隔离（少一条故障传导路径）两个收益的共同来源。
- **失效条件**：当**路由表退化成一个唯一副本的全局服务**（配置中心只有一套、网关又无本地缓存）时，这条会从隔离手段变成新的共同故障源：配置中心不可达时全部 Cell 一起失去路由能力。症状不是某个 Cell 报警，而是**所有 Cell 在同一时刻同时开始报错，且报错内容与业务无关**。第二个失效条件出现在**键不可在入口判定**时（跨键的全局报表 JOIN、会变化的所在地），此时路由函数存在，但结果长期不稳定。
- **档位**：机制部分为定义性事实；本条无数字主张——「正常路径下跨 Cell 调用为零」是机制的定义性结论，不是阈值（Cell 数区间的档位见 4.1 第 4 条）。

**一致性 Hash 路由**

- **做法**：用虚拟节点把每个 Cell 映射到哈希环上的多段区间，键哈希后取环上顺时针第一个节点；需要两级归属时，再叠一张归属表（逻辑单元 → 地域）。
- **机制**：因为虚拟节点让每个 Cell 在环上占多段，所以 Cell 增减时受影响的键比例约为 1/N 而不是全量重分布——「扩一个 Cell」由此从一次全量搬迁变成一次局部搬迁；同时「同一键必落同一 Cell」的确定性仍然成立。
- **失效条件**：当**键分布本身不均匀**（大 V、头部商家、秒杀单商品）时，均匀性假设被破坏：路由是确定性映射，热点键永远命中同一个 Cell，加机器无法把该键摊开。症状是「某一个 Cell 的 CPU / 连接数周期性尖峰，且尖峰总是同一个键，其余 Cell 正常」——看起来像这个 Cell 部署有问题，实际是键的问题。缓解手段只有键内再分片、单键专用 Cell、或把该键整段迁走三种。
- **档位**：机制为定义性事实；热点识别依赖键级分布分析，不能只看均值。

**流量染色（生产 / 压测 / 灰度）**

- **做法**：在请求上下文（HTTP 头 / RPC 上下文）里带三类标记——归属标记（cellId）、环境标记（压测流量）、发布标记（灰度批次）；异步链路（消息头、调度参数）必须同样携带；下游按标记决定读哪个 Cell、写哪个 Cell、是否短路外部副作用。
- **机制**：因为标记是全链路唯一的路由依据，所以「读本地化」与「跨域隔离」在结构上可表达；也正因为它唯一，任何一段丢失标记就等价于该段放弃归属——染色泄漏的代价不在于那一次写错，而在于**它不报错**。
- **失效条件**：当**新增一个写入入口而没有同步加染色**时（新上线的定时任务、新的数据修复脚本、新的 Agent 工具调用），写入落到默认 Cell：单条记录合法，只在跨 Cell 对账或全量查询时表现为缺失或重复。症状是「对账差异每天几十条、逐条看都合法、数量随新功能上线台阶式上升」。判据是把「会写数据的入口」做成清单并纳入上线检查，而不是靠代码审查发现。
- **档位**：机制为定义性事实；差异条数的量级随入口数量与业务量变化，不给固定值【经验】。

**数据库水平切分（ShardingSphere / Vitess 一类）**

- **做法**：按归属键做库级分片（如 `ds_${0..11}.orders_${0..1}` 这类实际节点表达），分片算法用 MOD 或一致性 Hash；表级再按另一个键（orderId）二次分片时，必须先确认库级键与表级键的对应关系不会产生跨库 JOIN。
- **机制**：因为分片键与归属键一致，SQL 路由与流量路由用的是同一个函数，二者不会漂移——这是「数据在哪个 Cell」与「请求去哪个 Cell」始终对得上的唯一保证。代理层还带来一个附加收益：应用不必知道分片拓扑。
- **失效条件**：当**分片键选得比归属键更细**（按 orderId 分表而按 userId 归属）时，会在一个 Cell 内出现跨多个分片的事务与排序，性能随分片数下降；当**查询不带分片键**时，代理要广播到全部分片，长尾由最慢分片决定。症状是「绝大多数查询正常、少数查询偶发慢一个数量级，且这些查询的过滤条件里都缺分片键」。代理层本身也是共享组件，它挂掉时全部 Cell 一起受影响——这一条要写进共享组件清单。
- **档位**：机制为定义性事实；分片数与节点表达的写法随实现而异。

**消息与配置的跨 Cell 协同**

- **做法**：同一归属键的事件进入同一分区（分区键 = 归属键）；跨 Cell 的业务动作走异步消息而非同步 RPC，落库用幂等键去重；全局配置、全局序列、全局额度这类「全局且可写」的数据，要么收编到中心域 + 本地只读缓存 + 降级路径，要么明确接受它成为共同故障源并写进清单。
- **机制**：因为分区键与归属键一致，事件在 Cell 内被顺序消费，同一键的状态变更天然有序；跨 Cell 走异步则意味着调用方不持有对端的执行结果，对端抖动只表现为延迟而不是失败传导。配置类全局数据走「中心写 + 本地读」也是同一逻辑：写路径单点，读路径分散，读可用性因此不依赖中心。
- **失效条件**：当**全局且可写的数据被留在某个 Cell 里**时，其他 Cell 访问它会跨域，且它成为新的共同故障源——症状是「这个 Cell 挂了，别的 Cell 连配置都读不到」；健康时没有任何征兆，所以这条只能靠清单发现（见 [§3.5 反模式表](01-cell-based-architecture-section-3-sec3.md) 中「忽视全局数据」一行）。当全局数据的写路径不单一时，还会叠加冲突消解问题，即退回 §3.1 的「每份数据几个写入者」这条约束。
- **档位**：机制为定义性事实。

### 4.3 工具链与平台

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| **路由层** | Spring Cloud Gateway、Kong、Envoy | 网关要能改请求头、能读本地路由缓存、在配置中心不可达时仍能决策；已有服务网格则把路由下沉到 Sidecar，避免两处各有一套规则 | 路由规则散在应用代码里，改一次归属要发 N 个服务的版；两套规则不一致时表现为少数请求反复跨域（尾延迟异常、不报错） |
| **DB 分片** | ShardingSphere、Vitess、MyCat | 按「是否需要应用无感」选：应用无感选代理式（Vitess 一类）；要对 SQL 路由做精细控制选 JDBC 增强式（ShardingSphere 一类）；已有自研数据访问层时改动量是主因 | 分片键只能由应用自己保证，跨库 JOIN 与不带分片键的查询会在规模化后集中暴露；代理层作为共享组件没被列入清单 |
| **配置中心** | Apollo、Nacos、Consul | 判据是「网关能否在它不可达时用本地缓存继续决策」+「配置变更是否有版本与回滚」；不接受「配置中心挂了全站失去路由」 | 配置中心成为共同故障源，隔离承诺在它故障那一刻归零 |
| **服务发现** | Eureka、Consul、Nacos | 判据是「注册信息里是否携带 Cell 归属」——不带归属的服务发现会让路由层拿不到拓扑，只能用静态规则 | 拓扑变更后路由表与实例列表不一致，跨 Cell 调用突然上升 |
| **流量调度** | Istio、Linkerd、阿里云 AHAS | 判据是「限流与重试的单位是不是 Cell」：限流是全局的，单 Cell 过载仍会扩散；选型前先确认该产品能按 Cell 维度配置与观测 | 单 Cell 过载无法就地降级，限流在某处生效却保护不了真正的瓶颈 |
| **AI 单元化（GPU 切分）** | NVIDIA MIG（硬分区）；阿里云 cGPU、vGPU（容器 / 虚拟化层切分） | 两者不在同一层、不能互相替代（见 [§5.2.2](01-cell-based-architecture-section-5-ai.md)）：要硬件级故障域隔离看硬分区，要多租户共享与弹性看容器层切分 | 把容器层切分当故障域隔离用，隔离语义与预期不符；判定方法是查该能力的官方文档里「故障域 / 实例数 / 显存与算力切分比例」三节是否齐备 |

上表最容易被误选的是**路由层**：多数团队的第一反应是「网关我们本来就有，加个过滤器就行」，于是路由规则落在某个服务的代码里，与配置中心、服务注册中心各有一套拓扑认知。后果不在上线时出现，而在两种时刻出现——**扩容时**（路由表与实例列表不一致，部分请求跨域，尾延迟上升但错误率为 0，没人会当故障处理）与**配置中心故障时**（所有 Cell 同时失去路由能力）。正确的选型动作不是「选哪个网关」，而是先回答：路由表放在哪、谁是它的唯一可信来源、它不可达时谁兜底。

GPU 那一行要注意产品层级：硬分区与容器层切分解决的不是同一个问题，把两者并列成「可替换候选」是本主题下最常见的名词混淆。

### 4.4 存量迁移

**① 先做什么可以立刻见效且可回退**：从「跨 Cell 对账」开始，而不是从切分开始。对账是只读的、可随时关掉、不改变任何写入路径，但它会在一到两个对账周期内（天级～两周【经验】；取决于数据量、库表数与对账链路是否已经存在）给出两份你此前没有的数据：哪些归属键的写入分散在多个地方（对账差异），以及哪些表根本没有归属键（无法判断落点）。这两份数据正是 Step 1 的入口清单与共享组件清单的来源。第二个可立即做且可回退的动作是**把「全局且可写」的数据列成清单**——它不改代码，只改评审项，却能立刻否掉一部分「先切了再说」的计划。常见误区是先做流量染色再选键：染色是手段，键没定之前透传目标是不确定的，改一次键就要重新贯通一遍全链路。

**② 历史资产怎么分类处理**：存量数据按「有没有归属键」分三类，分别对应三种处置，不要混用。

| 分类 | 特征 | 处置 | 为什么 |
| --- | --- | --- | --- |
| 有稳定键 | 每行都能算出归属键，且键不会再变 | 全部迁移：离线按键重分布 + 迁移后按 Cell 全量对账 | 键稳定意味着这是一次性成本；分两次迁移只会付两次停机与两次对账 |
| 有键但会变 | 键存在，但业务上会变（所在地、所属机构） | 只迁移「仍在被访问的部分」：热数据按当前键迁，冷数据打标挂账、访问时按新键懒迁移 | 全量迁移的成果会被下一次键变更作废，等于给不稳定的东西付稳定的成本 |
| 无键 | 历史日志、外部导入、无主键的宽表 | 打标挂账：标注「无归属、不可路由、落在默认 Cell」，并在资产目录里对使用者可见 | 强行补键会引入错误的归属——伪造的键比没有键更危险，因为它能通过校验；挂账至少让盲区是已知的 |

三类都以「双写 + 对账」推进，而不是以「停机搬迁」推进：停机窗口在大体量数据上通常凑不出来，而双写期正好是建立对账链路的时机。

**③ 迁移期的双轨怎么维持、维持多久**：双轨的成本结构是「双份资源 + 全链路对账 + 双份值班」，因此应当**按 Cell 分批收敛**，而不是一次全量并行：

1. 先只读切换：新路由与旧路由同时计算，比对结果差异挂账；此阶段旧路径仍是权威。
2. 再只写切换：新路径成为权威，旧路径降级为校验（两侧写入结果比对）。
3. 最后下线旧路径：关掉双写与比对，保留一段时间的可回退映射表。

双轨时长的**下限**由一个完整业务周期决定（对账要覆盖月末、大促、结算这类周期性场景，通常不少于一个月【经验】），**上限**由「批次数 × 每批观察期」决定（每批之间留一次完整对账周期）。批次可以多，每批的观察期不能再压缩——压缩观察期等于放弃对账这条判据。

**④ 什么信号说明可以退出双轨**：满足前两条即可退出单批双轨、进入下一批；三条都满足才可以整体下线旧路径。

- **对账差异收敛且可归因**：连续若干个对账周期的差异条数趋于 0，且剩余差异全部能追到具体成因（已知历史脏数据），而不是只有「数字在下降」。
- **跨 Cell 调用占比稳定**：正常路径的同步跨 Cell 调用占比不随批次上升——它若上升，说明新批次的键在部分入口拿不到。
- **故障演练通过**：按 Cell 停服演练中，剩余 Cell 的峰值水位在预留范围内。这条不通过就退出双轨，等于把风险留给下一次故障。

顺序上有一条硬约束：**切流与数据迁移永远不在同一次变更里发生**。两者同时进行时两侧数据都不完整，出问题无法回退到任一侧——这是本主题下最常见的不可回退操作。

### 4.5 模板 / 示例

**模板 A：归属键决策记录**

```markdown
# 归属键：<键名>（<业务域>）

- 键的稳定性：注册即固定 / 会随业务变化（写出变化频率）
- 所有会写数据的入口及其取值方式：
  | 入口 | 类型 | 能否拿到键 | 处置（补键 / 改 Cell 内作业 / 挂账） |
  | --- | --- | --- | --- |
- 共享组件清单（每项：下沉 / 本地缓存降级 / 接受为共同故障源）
- 接管目标：N−1 还是 N−2；据此的容量系数
- 已知盲区：<无键的资产清单 + 为什么不上键>
```

**怎么用**：填的是「入口表」与「盲区」两格，其余格是判断结果的记录；「处置」一列不允许留空——留空的那一行就是这次切分最可能出问题的位置。这张表在每次架构评审时重答，不要求一次写全。

**模板 B：跨 Cell 对账 SQL（核对归属与落库位置）**

```sql
-- 目标：找出「归属键算出的 Cell」与「记录实际所在 Cell」不一致的行
-- 在每个 Cell 的分片上执行，筛出不属于本 Cell 的行
SELECT :cell_id                        AS found_in_cell,
       user_id,
       MOD(ABS(hashtext(user_id)), :n_cells) AS expected_cell,
       COUNT(*)                        AS rows_wrong_place
FROM   orders
WHERE  MOD(ABS(hashtext(user_id)), :n_cells) <> :cell_id
GROUP  BY user_id
HAVING COUNT(*) > 0
ORDER  BY rows_wrong_place DESC
LIMIT  100;
```

**怎么用**：`hashtext()` 只是占位——换成你实际的路由函数（murmur3 / 一致性 Hash 取环），**这是整段里唯一不能照抄的一格**：两者不一致会把正确数据报成差异。`LIMIT` 保留以控制单次扫描成本；「查不到差异」不等于没有差异，只等于在这个函数下查不到。

**模板 C：单 Cell 停服演练剧本**

```markdown
# 演练：停服 Cell <k>

前置：数据护栏已开启；邻 Cell 水位看板可见；切流开关可回滚
步骤：
1. 记录 t0 时全部 Cell 的 QPS / 水位 / 跨 Cell 调用占比（基线）
2. 停服 Cell <k>，记录流量改派完成时刻 t1：切换耗时 = t1 − t0【经验：自动切流秒级～分钟级】
3. 记录 t1 之后 30 分钟内邻 Cell 峰值水位 —— 必须 < 100%
4. 做一次跨 Cell 对账，记录差异条数
5. 恢复 Cell <k>，记录回切耗时与回切期间的错误率
通过判据：邻 Cell 峰值水位 < 100%，且切换耗时在切换预算内
未通过时的回退动作：<明确写出改哪一个值：N / 接管目标 / 键内再分片>
```

**怎么用**：填「停服 Cell k」与「回退动作」两处；第 3 步是唯一真正的判据——只验证「服务没挂」不算通过，因为可能失败的是容量重分配那部分。

**模板 D：分片规则（ShardingSphere 形态，库级键与表级键分开声明）**

```yaml
rules:
- !SHARDING
  tables:
    orders:
      actualDataNodes: ds_${0..11}.orders_${0..1}
      databaseStrategy:            # 库级键 = 归属键，必须与流量路由用同一个函数
        standard:
          shardingColumn: user_id
          shardingAlgorithmName: cell_mod
      tableStrategy:               # 表级键可以更细，但不得让库级键的查询变成广播
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: order_hash
  shardingAlgorithms:
    cell_mod:
      type: MOD
      props:
        sharding-count: 12
```

**怎么用**：填「库级分片数与算法」和「表级键」两格。**唯一不能照抄的是两个键的选择**：库级键必须与流量路由的归属键一致（不一致时对账模板 B 会给出大量假差异）；表级键换成谁都行，只要「带归属键的查询不会因此广播到全部分片」，这一条要拿最常用的 3 条查询去验证。

**模板 E：单元化写入闭环骨架（写入必须落在本 Cell）**

```java
// 入口算一次归属，之后全链路只读上下文，不再重算
int cellId = CellRouter.cellOf(userId);
RequestContext.setCellId(cellId);          // cellId 进上下文，随 RPC / 消息头透传
RequestContext.setUserId(userId);

// 单元内闭环：读写都走当前 Cell 的数据源，跨 Cell 只允许异步
orderService.create(req);                  // 数据源由 cellId 决定，不由应用参数决定

// 防线：任何一次写入前核对「算出的 Cell」与「当前所在 Cell」
if (cellId != CellContext.current()) {
    throw new CellMismatchException(userId);   // 宁可拒写，也不要静默写错 Cell
}
```

**怎么用**：填「归属计算函数」与「当前 Cell 的判定来源」两处；最后那段校验是这套骨架里最值钱的一行——它把染色泄漏从「偶发不一致」变成「一条可统计的异常指标」，**这一段不要为了减少报错而删掉**，删掉它以后，写错 Cell 的记录会静默留在库里，只能靠对账事后发现。

### 4.6 成本：这套东西的账单

单元化的账单不在算力总量上，而在**两处结构性乘法**：中间件实例数，与接管冗余。

- **硬件 / 容量**：贵在冗余口径取的是**接管目标**而不是均值。若设计为单 Cell 故障由其余 Cell 承接，每 Cell 需按 `N/(N−1)` 的系数备容量（【推算】：N 个 Cell、接管目标 N−1 → 系数 = N/(N−1)；N=12 时为 12/11 ≈ 1.09，即 +9%；接管目标 N−2 时为 12/10 = 1.20，即 +20%）。这条算式就是 §2.2「每 Cell 资源 = 总资源 / Cell 数 + 冗余」里「冗余」那一项的取值依据——由接管目标定，不由经验拍板。
- **云账单**：贵在**每 Cell 一套 DB + Cache + MQ**。Cell 自包含（§2.1）意味着中间件实例数随 N 线性增长，哪怕每个 Cell 的实例都很小；这笔「重复的中间件」正是单元化区别于单纯分库分表的地方。
- **人力**：贵在**拓扑只有一个可信来源**这件事要持续维护。路由表、配置中心、服务发现、网关四处的 Cell 认知必须一致（§4.3 路由层一行），任何一处漂移都表现为跨 Cell 调用无声上升——这是常态人力而非一次性投入；归属键治理与对账链路（§4.4）同样按 Cell 数摊开。

一句话：单元化把成本从「一次性切分工程」换成「随 N 线性增长的中间件与处置人力」，所以 N 越大越贵，换回来的是爆炸半径 1/N（§2.2）。通用的成本归集与 FinOps 口径见 [03-data-cost-finops](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节只算单元化特有的那部分。

### 4.7 容灾与故障演练

单元化的容灾不是「有没有多机房」——它本身就是多机房形态——而是**隔离承诺在共同故障源上是否还成立**。

- **失效模式 → 影响面**：(1) 配置中心 / 服务发现不可达 → 所有 Cell 同时失去路由能力，隔离归零，这是单元化最危险的单点（§4.3）；(2) 单 Cell 的 DB / MQ 故障 → 影响面 = 1/N，但若该 Cell 被同步跨 Cell 调用，故障沿调用链扩散；(3) 归属键变更（用户所在地变了）→ 数据留在旧 Cell、与新算出的 Cell 不一致，表现为对账差异而非报错。
- **降级策略**：网关本地缓存路由表，配置中心不可达时按缓存决策；单 Cell 过载时按 Cell 维度限流、就地降级，而不是全局限流（§4.3 流量调度一行）。
- **演练方案**：单 Cell 停服演练剧本已在 §4.5 模板 C 给出，此处不重复，只强调其第 3 步「邻 Cell 峰值水位 < 100%」是唯一真判据；再补一项**键变更演练**——人为改一批用户的归属键，观察对账差异是否出现、懒迁移是否触发。通用混沌方法论见 [06-chaos-engineering](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)，容灾分层见 [07-disaster-recovery](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)。
- **恢复目标**：自动切流 RTO【经验：秒级～分钟级】，跨 Cell 异步同步 RPO【经验：秒级～分钟级，取决于 MQ 同步延迟】，非零。**跨地域灾备不作为独立目标**——单元化的灾备指标应由 Cell 数 N 与接管目标表达（见 §4.6），另立一套只会与容量口径打架。

### 4.8 演进路线：0 → 1 → 100

- **0 → 1（最小可用）**：不切物理 Cell，只把**归属键算出来并统一写入路径**——入口算一次、全链路透传（§4.5 模板 E 骨架），数据仍在单库。此时变贵的是给无键历史资产挂账的治理成本；先坏的是**归属键盲区**：定时任务、消息消费、运维脚本这些非用户入口会在你不知道的地方写错落点。
- **1 → 100（规模化）**：按 N 切出物理 Cell，配齐路由层、配置中心、服务发现与对账链路，双轨按 Cell 分批收敛（§4.4）。此时变贵的是中间件实例数与接管冗余（§4.6）；先坏的是**共同故障源**——配置中心或某条跨 Cell 同步链路一挂，隔离承诺同时失效。
- **100 →（下一道坎）**：把无状态推理副本挂进既有 Cell（L2）——「每 Cell 独立 GPU 池 / Agent 集群」属 L2 / L3、是方向而非必经阶段（主文件 §2.3、[§5](01-cell-based-architecture-section-5-ai.md)：GPU 池化「不要为每个 Cell 常备产能」、Agent「不要为 Agent 单独建 Cell」）。此时变贵的是 GPU 的故障域切分（硬分区 vs 容器层，见 §4.3）；先坏的是**有状态推理的会话归属**：「这个 Cell 的 GPU 能不能借给别的 Cell、会话状态存在哪」两个答案若与单元化语义不一致，跨 Cell 推理会绕过隔离。
- **贯穿三阶段的一件事**：归属键的稳定性。三个阶段变贵的东西与先坏的东西都围绕它——键越稳定，切分越接近一次性工程；键会变，每一阶段都要为「懒迁移」留一条路径（§4.4 第二类资产），否则上一阶段的迁移成果会被下一次键变更作废。

- [ ] 共享组件清单上的每一项，去线上拓扑里核对是否为每个 Cell 各有一份？若只有一份，它是否被明确接受为共同故障源？

- [ ] 若涉及有状态推理：这个 Cell 的 GPU 能不能借给别的 Cell？会话状态存在哪？两个答案是否与「AI 单元化」的语义一致？

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **Step 2——把归属键做成全链路契约**。它没有可视化产物、也没有明确的完工节点，所以最常被跳过；但它决定了 Step 3 的数据切分是不是在做无用工，也决定了 Step 4 的演练能不能得出可用的水位结论。判据只有两条：非用户入口的写入路径上是否真的带着键，以及跨 Cell 对账的差异条数是否收敛到可归因。
>
> 与之等价的另一条约束是顺序：**先列共享组件清单，再定 Cell 数，最后才写路由代码**。共享组件清单决定切完有没有隔离，Cell 数只是这份清单与运维产能的下游结果。存量改造的读者请把 4.4 的「先对账、再列清单」放在 Step 1 之前执行。
>
> 💡 **思考锚点**：从你的代码仓库抽 3 条非用户入口（一条定时任务、一条消息消费、一条运维脚本），看它们的写入路径上是否真的带着归属键——§4.1 说这才是 Step 2 的判据，而不是「染色改造完成了」。再看 §4.4：你的存量里有多少是「有键但键会变」（所在地、所属机构）——这部分你打算全量迁，还是只迁热数据、冷数据打标挂账？
