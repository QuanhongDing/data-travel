### 6.1 阿里双 11 单元化 10+ 年演进（2013-2024）

**背景（Why）**

阿里 2013 年面临**双 11 容量爆炸**：
- **2013 双 11**——**1.7 亿订单**——**单库撑不住**（**MySQL 极限 5 万 QPS**）
- **单机**——**故障域大**——**一台挂全挂**
- **水平扩展难**——**MySQL 分库分表**——**业务侵入大**

**触发点（What）**

2013 年**阿里启动单元化项目**（[ArchSummit 2014 演讲]），目标：
- **支撑双 11 万亿级交易**——**水平扩展**
- **故障域隔离**——**单 Cell 挂不影响其他 Cell**
- **业务侵入小**——**SDK 自动路由**

**详细做法（How）**

阿里单元化的**6 大核心创新**（来自 [阿里单元化白皮书 2016]）：

1. **业务域切分（核心创新）**
   - 关键设计：按 **userId Hash**——**拆成 N 个 Cell**
   - 关键代码：
     ```java
     // 阿里单元化路由
     public class CellRouter {
         public int getCellId(long userId) {
             return (int) (Math.abs(userId) % TOTAL_CELLS);
         }
     }
     // 12 个 Cell 起步，2023 扩到 30+ Cell
     public static final int TOTAL_CELLS = 30;
     ```
   - 关键能力：**业务无感知**——**通过 SDK 自动路由**

2. **三地五中心（同城双活 + 异地灾备）**
   - 关键设计：**杭州 2 + 上海 1 + 深圳 1 + 异地灾备 1**——**3 个数据中心**
   - 关键能力：**同城双活**——**A 中心挂 B 中心接管**
   - 关键代码：
     ```yaml
     # 阿里单元化三地五中心
     regions:
       - name: hangzhou-1
         cells: [1, 2, 3, 4]    # 主
       - name: hangzhou-2
         cells: [5, 6, 7, 8]    # 备
       - name: shanghai-1
         cells: [9, 10, 11, 12] # 同城灾备
       - name: shenzhen-1
         cells: [13, 14, 15, 16] # 异地灾备
     ```

3. **数据库分片（核心创新）**
   - 关键设计：**每 Cell 独立数据库**——**避免单库热点**
   - 关键能力：**PB 级数据**——**水平扩展**
   - 关键代码：
     ```sql
     -- 每 Cell 独立数据库
     CREATE DATABASE cell_01_orders;
     CREATE DATABASE cell_02_orders;
     ...
     CREATE DATABASE cell_30_orders;
     -- 业务方访问时自动路由
     ```

4. **跨 Cell 调用（消息中心）**
   - 关键设计：**跨 Cell 调用**——**通过消息中心（Notify / RocketMQ）**
   - 关键能力：**异步**——**不阻塞**

5. **流量调度（GSLB）**
   - 关键设计：**阿里自研 GSLB（Global Server Load Balancer）**——**按地理位置**
   - 关键能力：**北京用户**——**路由到北京 Cell**——**降低延迟**

6. **故障域隔离（核心目标）**
   - 关键设计：**单 Cell 挂**——**只影响 1/30 用户**——**不影响全局**
   - 关键能力：**P0 故障**——**30% 流量降级**——**可降级**

**阿里双 11 单元化关键数字**（[公开演讲 双 11 2023]）：

| 年份 | Cells 数 | 订单数 | GMV | 0 严重故障 |
| --- | --- | --- | --- | --- |
| 2013 | 12 | 1.7 亿 | 350 亿 | ✅ |
| 2016 | 16 | 6.5 亿 | 1207 亿 | ✅ |
| 2019 | 24 | 2684 亿 GMV | 2684 亿 | ✅ |
| 2020 | 24 | 4982 亿 GMV | 4982 亿 | ✅ |
| 2022 | 30 | 万亿级 | 1 万亿 | ✅ |
| 2023 | 30+ | 1.5 万亿级 | 1.5 万亿 | ✅ |

**具体数字（How much）**

- 团队规模：阿里单元化团队 100+ 人
- 关键数字（[双 11 2023 复盘]）：
  - **30+ Cell**
  - **三地五中心**
  - **万亿级 GMV**
  - **10 年 0 严重故障**
- 业务覆盖：淘宝 / 天猫 / 支付宝 / 闲鱼 / 钉钉 / 菜鸟 / 饿了么

**失败教训**

- 第 1 阶段**Cell 数量太少（4 个）**——**热点**——倒逼**「**12-30 个**」**
- **跨 Cell 同步**——倒逼**「**最终一致**」**而非强一致
- **数据库分片**——倒逼**「**自动分片**」**机制
- **流量调度**——倒逼**「**GSLB 自研**」**

### 6.2 字节春晚红包 8 年演进（2017-2024）

**背景（Why）**

字节 2017 年面临**春晚红包**极端压力：
- **春晚 5 分钟**——**20 亿 QPS**——**抖音 / 支付宝 / 微信 抢红包**
- **2016 支付宝春晚**——**宕机 90 分钟**（**系统过载**）
- **字节 2017 首次**——**必须扛住**

**触发点（What）**

2017 年字节**启动单元化项目**（[ArchSummit 2018 演讲]），目标：
- **20 亿 QPS**——**水平扩展**
- **0 严重故障**——**春晚级容灾**

**详细做法（How）**

字节春晚红包的**5 大核心创新**：

1. **超大规模单元化（30+ Cells）**
   - 关键设计：**30+ Cells**——**按 userId Hash**
   - 关键能力：**20 亿 QPS**——**水平扩展**

2. **流量调度（自研 GSLB）**
   - 关键设计：**字节自研 GSLB**——**按地理位置**
   - 关键代码：
     ```go
     // 字节 GSLB 路由
     func Route(userId int64, geo string) int {
         cellId := userId % 30
         // 按地理位置优先
         if geo == "BJ" {
             return cellId % 6  // 北京 6 个 Cell
         }
         if geo == "SH" {
             return 6 + cellId % 6  // 上海 6 个 Cell
         }
         return cellId
     }
     ```

3. **数据库分库分表（每 Cell 独立）**
   - 关键设计：**每 Cell 独立 MySQL**——**避免热点**
   - 关键能力：**20 亿 QPS**——**分散到 30 个 MySQL**

4. **资金链路专属（核心创新）**
   - 关键设计：**红包资金**——**独立 Cell**——**异步处理**
   - 关键能力：**资金链**——**不能垮**——**100% SLA**

5. **春晚级容灾（0 故障要求）**
   - 关键设计：**同城双活 + 异地灾备**——**故障自动切换**
   - 关键能力：**0 切换延迟**——**春晚期不出问题**

**字节春晚红包关键数字**（[ArchSummit 2018]）：

| 年份 | Cells | QPS 峰值 | 0 故障 | 关键事件 |
| --- | --- | --- | --- | --- |
| 2017 | 30+ | 20 亿 | ✅ | 首次春晚红包 |
| 2018 | 30+ | 25 亿 | ✅ | 改进版 |
| 2019 | 30+ | 30 亿 | ✅ | 抖音爆发 |
| 2021 | 30+ | 40 亿 | ✅ | 抖音春晚 |
| 2023 | 30+ | 50 亿 | ✅ | 1.5 万亿 GMV |

**具体数字（How much）**

- 团队规模：字节春晚团队 200+ 人
- 关键数字：
  - **20-50 亿 QPS 峰值**
  - **30+ Cells**
  - **8 年 0 严重故障**
- 业务影响：支撑**字节全部业务**（抖音 / TikTok / 西瓜 / 今日头条 / 电商）

**失败教训**

- 早期**Cell 数量不够**——倒逼**30+**
- **GSLB 误判**——倒逼**「**健康检查**」**
- **数据库热点**——倒逼**「**自动重分片**」**
- **资金链**——倒逼**「**独立 Cell**」**

### 6.3 美团单元化 5 年（2018-2022）

**背景（Why）**

美团 2018 年面临**多业务线**挑战：
- **外卖 / 到店 / 酒旅 / 电影 / 出行**——**5+ 业务线**
- **日订单 1000 万+**——**MySQL 单库撑不住**
- **业务方独立**——**每业务线独立数仓**——**重复建设**

**触发点（What）**

2018 年美团启动**统一单元化**——**目标：5 套数仓 → 1 套**。

**详细做法（How）**

美团单元化**5 大组件**：

1. **业务域切分（按业务线）**
   - 关键设计：5 个 Cell（**5 业务线**）——**按业务线**
   - 关键能力：**业务独立**——**故障隔离**

2. **数据分库分表（按 userId）**
   - 关键设计：每 Cell 独立数据库——**按 userId 分片**

3. **跨 Cell 调用（消息中心）**
   - 关键设计：跨 Cell 调用——**消息中心异步**
   - 关键工具：美团自研 **Mafka**（**基于 Kafka**）

4. **流量调度（自研 GSLB）**
   - 关键设计：**美团自研 GSLB**——**按地理位置**

5. **故障域隔离（核心目标）**
   - 关键设计：单 Cell 挂——**只影响 1/5 业务**

**具体数字（How much）**

- 团队规模：美团单元化团队 50+ 人
- 关键数字：
  - **5 Cells**（5 业务线）
  - **日订单 1000 万+**
  - **5 套数仓 → 1 套**
  - **3 年 0 严重故障**
- 业务覆盖：外卖 / 到店 / 酒旅 / 电影 / 出行

**失败教训**

- 早期**Cell 数量不够**——倒逼**按业务线**5 个
- **数据分片**——倒逼**「**userId Hash**」**
- **跨 Cell 同步**——倒逼**「**消息中心**」**

### 6.4 Netflix 多区域单元化 5+ 年（2018-2024）

**背景（Why）**

Netflix 2018 年面临**全球多区域**挑战：
- **190+ 国家**——**2 亿+ 付费用户**
- **AWS 多 region**——**数据主从复制**
- **跨 region 单元化**

**触发点**

2018 年 Netflix 启动**多 region 单元化**——**目标：全球可用性 99.99%**。

**详细做法（How）**

Netflix 单元化**4 大组件**：

1. **全球 Cell 划分（按地理）**
   - 关键设计：每个 region 独立 Cell
   - 关键能力：**local 优先**——**降低延迟**

2. **Cell 内独立数据库（Cassandra）**
   - 关键设计：每 Cell **Cassandra 集群**——**多 region 复制**
   - 关键能力：**最终一致**——**99.99% 可用性**

3. **流量调度（自研 Zuul）**
   - 关键设计：Netflix 自研 **Zuul**（**API Gateway**）——**按地理位置**
   - 关键能力：**EU 用户**——**EU Cell**——**降低 50ms 延迟**

4. **故障域隔离（核心）**
   - 关键设计：单 region 挂——**只影响 1/3 用户**
   - 关键能力：**自动切换**——**2 分钟内恢复**

**具体数字（How much）**

- 团队规模：Netflix 单元化团队 30+ 人
- 关键数字：
  - **3+ regions**
  - **99.99% 可用性**
  - **2 亿+ 用户**
- 业务覆盖：Netflix 全球

**失败教训**

- 早期**Cassandra 一致性问题**——倒逼**「**最终一致**」**
- **跨 region 复制**——倒逼**「**异步 + 监控**」**
- **Zuul 误判**——倒逼**「**健康检查**」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选**MySQL 分库分表 + GSLB**（最简单）
- 接入**核心 1-2 个业务**（订单 / 支付）
- 部署**4-8 个 Cell**——**同城双活**
- 团队：3-5 人

**1 → 10 阶段：6-12 个月**

- 扩展到**10+ Cell**——**按业务线**
- 引入**消息中心**——**跨 Cell 异步**
- 引入**同城双活**——**自动切换**
- 团队：10-20 人

**10 → 100 阶段：12-24 个月**

- 扩展到**30+ Cell**——**多 region**
- 引入**异地灾备**——**分钟级切换**
- 引入**单元化监控**——**GSLB + 健康检查**
- 团队：20-50 人

**100 → 1000 阶段：12-24 个月**

- 引入**Serverless 单元化**——**按需启停**
- 引入**Cell 内资源隔离**（**cgroups / namespace**）
- 团队：50-100 人

---

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 美团 / Netflix）印证：**单元化不是「**分库分表**」，是「**Cell 划分 + 同城双活 + 跨 region 联邦**」**组合。
> - 关键时间线：阿里 10+ 年 / 字节 8 年 / 美团 5 年 / Netflix 5+ 年 —— **单元化是 10+ 年长期工程**。
> - 选型第一原则：**MySQL 分库分表**（最简单）→ **同城双活**（必须）→ **异地灾备 + 多 region**（全球化）。
> - 99% 的失败来自「**Cell 数量不够 + 跨 Cell 同步 + 故障切换**」——必须有**充足 Cell + 消息中心 + 自动切换**。
> - 真正的 ROI 来自「**春晚级 0 故障 + 万亿级 GMV**」——是**大厂核心业务的基础设施**。
