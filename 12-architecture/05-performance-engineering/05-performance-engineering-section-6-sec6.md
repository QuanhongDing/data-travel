## 6. 落地实践

### 6.1 阿里"**双 11 性能 7x 10+ 年**"（2013-2024）

**背景（Why）**

阿里 2013 年面临**双 11 性能 7x**：
- **7x 流量**——**传统架构撑不住**
- **60 万笔/秒**——**峰值压力**
- **JVM + 数据库**——**核心优化**

**触发点（What）**

2013 年阿里启动**双 11 性能 7x**（[阿里 2013]），目标：
- **7x 平滑**
- **0 性能事故**
- **JVM + 数据库优化**

**详细做法（How）**

阿里双 11 性能 7x 的**5 大核心组件**：

1. **JVM 调优（核心创新）**
   - 关键设计：**G1 GC + MaxGCPauseMillis=200**
   - 关键能力：**停顿不再与业务高峰叠加**
   - 关键数字：**暂停 < 200ms**
   - 关键示意：
     ```text
     关键 JVM 参数（G1 GC，暂停目标 200ms）
     -XX:+UseG1GC
     -XX:MaxGCPauseMillis=200        # 目标：单次暂停 < 200ms
     -XX:InitiatingHeapOccupancyPercent=45
     -Xms8g -Xmx8g                   # 堆固定，避免动态扩缩抖动
     调优前后：Full GC 频发 / STW 2s+ → Young GC < 200ms、无 Full GC
     # 大促前关掉"自动调参"，堆固定 + 暂停目标写死
     ```

2. **数据库优化（核心）**
   - 关键设计：**读写分离 + 分库分表 + 索引优化**
   - 关键能力：**单库写入瓶颈被拆到多个库与分片，吞吐随分片数扩展，不再靠单机升配**
   - 关键数字：**10x 提升**

3. **多级缓存（核心）**
   - 关键设计：**本地 + Redis + CDN**
   - 关键能力：**绝大多数请求被挡在数据库之前**
   - 关键数字：**P99 < 50ms**

4. **限流 + 削峰（核心）**
   - 关键设计：**Sentinel 限流 + 消息队列削峰**
   - 关键能力：**洪峰被挡住与削平，下游按自己的节奏消费**
   - 关键数字：**7x 平滑**

5. **全链路压测（核心创新）**
   - 关键设计：**生产环境真实流量**
   - 关键能力：**容量是否真够在事前就有答案，而不是大促当天才知道**
   - 关键数字：**7x 流量**

**阿里双 11 性能 7x 关键数字**（[阿里 2013-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**峰值吞吐**」** | 单机房 5 万笔/秒 | 60 万笔/秒 | **+1100%** |
| **「**GC 暂停**」** | 秒级（Full GC） | < 200ms | **-90%** |
| **「**P99 延迟**」** | 秒级 | < 50ms | **-95%** |
| **「**DB 吞吐**」** | 单库基线 | 10x（分库分表） | **+900%** |
| **「**缓存命中**」** | 60% | 95%+ | **+58%** |
| **「**大促承载**」** | 1x | 7x | **+600%** |
| **「**性能事故**」** | 每年数次 | 0 | **-100%** |
| **「**机器成本**」** | 7x 硬扛 | 按需扩容 | **-35%** |

**具体数字（How much）**

- 团队规模：阿里双 11 性能团队 200+ 人
- 关键数字：**7x 平滑**、**0 事故**、**P99 < 50ms**
- 业务影响：覆盖**双 11 全场景**

**失败教训**

- 早期「**Full GC 停顿叠加在峰值上**」——停顿与业务高峰撞在一起、P99 直接破线，倒逼**「换低停顿 GC（G1/ZGC）并把 GC 指标纳入 P99 归因」**
- 「**数据库单库扛峰值**」——连接与写入都到上限，倒逼**「分库分表 + 读写分离」**
- 「**缓存只做一层**」——命中率上不去、回源压力大，倒逼**「本地 + Redis + CDN 多级缓存」**
- 「**没有全链路压测**」——容量到底够不够只能等大促当天才知道，倒逼**「用真实流量做生产级压测」**

### 6.2 字节"**抖音春晚 5 亿+ 互动 5+ 年**"（2019-2024）

**背景（Why）**

字节 2019 年面临**抖音春晚 5 亿+ 互动**：
- **5 亿+ 互动**——**春晚峰值**
- **红包 24 小时**——**特殊业务**
- **6 亿+ 用户**

**触发点（What）**

2019 年字节启动**抖音春晚 5 亿+ 互动**（[字节 2019]），目标：
- **5 亿+ 互动**
- **春晚 0 事故**
- **P99 < 100ms**

**详细做法（How）**

字节抖音春晚 5 亿+ 互动的**5 大核心组件**：

1. **JVM 调优（核心创新）**
   - 关键设计：**G1 GC + ZGC**
   - 关键能力：**停顿不再与业务高峰叠加**
   - 关键数字：**暂停 < 10ms**
   - 关键示意：
     ```text
     关键 JVM 参数（ZGC，暂停目标 < 10ms）
     -XX:+UseZGC
     -XX:ZCollectionInterval=120     # 周期触发，摊平停顿
     -XX:+UnlockExperimentalVMOptions
     -Xms16g -Xmx16g                 # 大堆 + ZGC 支撑低停顿
     调优前后：G1 大堆停顿 100ms+ → ZGC 停顿 < 10ms
     # 红包峰值对停顿极敏感：ZGC 用染色指针 + 并发整理换低停顿
     ```

2. **多级缓存（核心）**
   - 关键设计：**本地 + Redis + CDN**
   - 关键能力：**绝大多数请求被挡在数据库之前**
   - 关键数字：**P99 < 50ms**

3. **消息队列（核心）**
   - 关键设计：**Kafka 削峰 + 异步**
   - 关键能力：**洪峰被挡住与削平，下游按自己的节奏消费**
   - 关键数字：**5 亿+ 互动**

4. **限流 + 削峰（核心）**
   - 关键设计：**Sentinel 限流 + 异步**
   - 关键能力：**洪峰被挡住与削平，下游按自己的节奏消费**
   - 关键数字：**5 亿+ 互动**

5. **灰度发布（核心创新）**
   - 关键设计：**小流量灰度 → 放量**
   - 关键能力：**新版本一旦有问题，影响面只限灰度内那部分流量，不会一次扩散到全量用户**
   - 关键数字：**0 事故**

**字节抖音春晚关键数字**（[字节 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**互动峰值**」** | 不可用 | 5 亿+ | **∞** |
| **「**GC 暂停**」** | 100ms+（G1 大堆） | < 10ms（ZGC） | **-90%** |
| **「**P99 延迟**」** | 秒级 | < 100ms | **-95%** |
| **「**MQ 削峰**」** | 不可用 | 5 亿+ 互动 | **∞** |
| **「**缓存命中**」** | 60% | 95%+ | **+58%** |
| **「**用户覆盖**」** | 不可用 | 6 亿+ | **∞** |
| **「**春晚事故**」** | 曾崩 | 0 | **-100%** |
| **「**灰度步长**」** | 激进全量 | 小流量→放量 | **收敛** |

**具体数字（How much）**

- 团队规模：字节春晚红包团队 500+ 人
- 关键数字：**5 亿+ 互动**、**0 事故**、**P99 < 100ms**
- 业务影响：覆盖**抖音 6 亿+ 用户**

**失败教训**

- 早期「**Full GC 在春晚峰值上叠加**」——停顿被流量放大、服务直接不可用，倒逼**「换 G1 GC 并做堆与分配速率调优」**
- 「**缓存只有一层**」——热点请求全部回源、数据库被打穿，倒逼**「做多级缓存」**
- 「**没有限流和削峰**」——瞬时洪峰直接压垮下游，倒逼**「限流 + 消息队列削峰」**
- 「**灰度一步到位**」——新版本一旦有问题就是全量事故，倒逼**「小流量起步、逐步放量」**

**触发点（What）**

2019 年美团启动**外卖 100 万单/小时**（[美团 2019]），目标：

- **中午高峰 0 事故**

- 「**只在低峰做压测**」——压不出真实高峰的问题，倒逼**「全链路真实流量压测」**

### 6.4 Netflix"**2 亿+ 用户 P99 < 200ms 6+ 年**"（2018-2024）

**背景（Why）**

Netflix 2018 年面临**2 亿+ 用户 P99 < 200ms**：
- **2 亿+ 用户**——**全球**
- **视频流**——**实时**
- **P99 < 200ms**

**触发点（What）**

2018 年 Netflix 启动**2 亿+ 用户 P99 < 200ms**（[Netflix 2018]），目标：
- **2 亿+ 用户**
- **P99 < 200ms**
- **全球**

**详细做法（How）**

Netflix 2 亿+ 用户 P99 < 200ms 的**5 大核心组件**：

1. **JVM 调优（核心创新）**
   - 关键设计：**G1 GC + ZGC**
   - 关键能力：**停顿不再与业务高峰叠加**
   - 关键数字：**暂停 < 10ms**
   - 关键示意：
     ```text
     关键 JVM 参数（服务分级 GC 策略）
     流媒体控制面（低延迟）：-XX:+UseZGC -Xmx16g
     批量编码 / ETL（高吞吐）：-XX:+UseG1GC -XX:MaxGCPauseMillis=200
     调优前后：统一默认 GC 卡顿 → 低延迟服务暂停 < 10ms、P99<100ms
     监控：GC 暂停 / 堆占用 / 分配速率纳入全链路监控告警
     # 2 亿+ 用户下：GC 停顿是全链路 P99 的关键放大器
     ```

2. **多级缓存（核心）**
   - 关键设计：**本地 + Redis + CDN**
   - 关键能力：**绝大多数请求被挡在数据库之前**
   - 关键数字：**P99 < 100ms**

3. **CDN（核心）**
   - 关键设计：**Open Connect CDN**
   - 关键能力：**用户就近获取内容，不必跨越长路径**
   - 关键数字：**100+ Region**

4. **自适应码率（核心）**
   - 关键设计：**根据带宽自适应**
   - 关键能力：**弱网能起播、好网不浪费带宽**
   - 关键数字：**60fps**

5. **压测 + 监控（核心创新）**
   - 关键设计：**压测 + 全链路监控**
   - 关键能力：**端到端结果被实测，而不是靠配置推断**
   - 关键数字：**P99 < 200ms**

| **「**首屏时间**」** | 数秒 | < 1s（CDN） | **-80%** |
| **「**CDN 节点**」** | 少 | 100+ Region | **∞** |
| **「**自适应码率**」** | 固定 | 60fps 自适应 | **∞** |
| **「**暂停（GC）**」** | 100ms+ | < 10ms（ZGC） | **-90%** |
| **「**卡顿率**」** | 高 | 低（自适应） | **-90%** |
| **「**带宽成本**」** | 高 | CDN 就近 + 压缩 | **-30%** |

**具体数字（How much）**

- 团队规模：Netflix 性能团队 200+ 人
- 关键数字：**2 亿+ 用户**、**P99 < 200ms**、**100+ Region**
- 业务影响：覆盖**Netflix 全球 2 亿+ 用户**

**失败教训**

- 早期「**首屏卡顿**」——内容从中心回源、路径长，倒逼**「把内容预置到用户所在网络的边缘」**
- 「**固定码率**」——弱网起播失败、好网浪费带宽，倒逼**「自适应码率」**
- 「**带宽成本随用户增长线性上升**」——跨网传输量大，倒逼**「就近服务 + 压缩」**
- 「**只看服务端指标**」——「返回成功」并不等于「用户看着流畅」，倒逼**「端到端采集起播时间与卡顿率」**

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 美团 / Netflix）印证：**性能工程不是「默认配置」，是「JVM 调优 + 多级缓存 + 数据库优化 + 限流 + 全链路压测」5 件套**。

> - 选型第一原则：「**JVM 调优 + 多级缓存起步**」（**最简单**）——**1 个业务** → 「**数据库优化 + 限流 + 削峰**」（**必须**）→ 「**多级缓存 + 消息队列**」（**生产**）→ 「**2 亿+ 用户 + 100+ Region CDN**」（**AI 时代**）。
> - 99% 的失败来自「**JVM 慢 + DB 慢 + 缓存弱 + 大促雪崩**」——必须有 **G1 GC + 读写分离 + 多级缓存 + Sentinel**。
