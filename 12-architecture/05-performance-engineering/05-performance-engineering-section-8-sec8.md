### 8.2 分主题展开

#### §8.2.1 美团 ClickHouse 在实时分析场景下出现慢查询，请你设计一套端到端的慢查询治理体系。

**1. 考察点**

- 是否理解**慢查询治理不是"调一条语句"**，而是「**事前预防 → 事中发现 → 事后治理**」全链路工程。
- 能否说清 ClickHouse（OLAP）与 MySQL（OLTP）在慢查询根因上的**结构性差异**——OLAP 慢往往不是单条 SQL 写错，而是**分区裁剪失效、Join 顺序错、聚合下推没做**。
- 是否知道**分布式场景下"慢"的定义要分层**：节点内慢（单 shard 慢）、节点间慢（数据倾斜）、查询计划慢（plan time 占比高）。
- 加分项：能结合美团公开的 ClickHouse 治理经验（如查询超时管控、慢查询日志、SQL 拦截器）谈落地。

**2. 参考答案框架**

**第一层：先定义"慢"——SLO 必须先行。** 慢查询治理的前提是定义**分位数 SLO**：

- OLTP 场景（MySQL）：P99 < 100ms 是基线，慢查询阈值通常取 P95 > 200ms 或 P99 > 500ms。
- OLAP 场景（ClickHouse）：由于涉及大表扫描，P99 可放宽到 5s–30s，但**必须按业务分级**——大促实时看板 P99 < 1s、BI 报表 P99 < 10s、离线探索 P99 < 60s。
- SLO 不是装饰：所有 SQL 在提交时就必须打标（业务域 + 优先级 + 预期 P99），无标查询直接拒绝或走低优先级队列。

**第二层：事前预防——把慢查询挡在上线前。**

- **SQL Review 准入**：所有上线 SQL 必须经过 EXPLAIN 检查，重点看 `type`（ALL/FULL SCAN 直接拒绝）、`rows` 扫描行数（> 千万级需业务侧确认）、`Extra`（Using filesort / temporary 需改造）。
- **查询超时与资源配额**：ClickHouse 配置 `max_execution_time`、`max_memory_usage`、`max_rows_to_read`；超过阈值直接 kill，避免一条慢查询拖垮整个集群。
- **强制索引 / 分区键**：核心表的 WHERE 条件必须命中分区键（通常是 `dt` / `event_date`），否则走全表扫描是性能灾难。**美团实践**的核心之一就是「强制 WHERE 带 dt 分区」作为上线门槛。
- **物化视图预聚合**：高频聚合查询（按城市 + 品类 + 天的 GMV）通过 AggregatingMergeTree 或物化视图预先算好，查询时只读汇总结果。
- **读写隔离**：大查询走专用集群（读副本），不与高 QPS 小查询抢资源——这是 ClickHouse 比 MySQL 更敏感的一点。

**第三层：事中发现——监控与拦截。**

- **慢查询日志**：开启 ClickHouse 的 `query_log` 系统表，按 `query_duration_ms`、`read_rows`、`memory_usage` 排序，每周 review TOP 100。
- **实时拦截器**：对运行中的长查询做"渐进式降级"——前 30 秒正常返回，超过后切换到采样、超过 5 分钟直接 kill 并告警 owner。
- **Profile 采样**：开启 ClickTrace / `query_profiler_real_time_period_ms`，记录每个查询的 CPU、内存、IO、网络消耗，定位瓶颈在哪个算子。
- **业务指标关联**：把慢查询日志与业务指标（订单量、广告曝光）绑定，**自动定位"是数据量增长导致还是某条烂 SQL 导致"**——美团内部称之为"SQL 与业务量的相关性分析"。

**第四层：事后治理——TOP SQL 治理 SOP。**

对每条慢 SQL 走"**五步定位法**"：

1. **看 EXPLAIN**：确认执行计划是否符合预期（分区裁剪、索引命中、Join 顺序）。
2. **看 Profile**：定位耗时算子（Filter / Join / Aggregate / Merge 哪个占比最高）。
3. **看数据分布**：用 `SAMPLE` 抽样确认数据倾斜——某个 shard 特别慢通常是数据倾斜。
4. **看 IO 与网络**：磁盘读放大？Shuffle 过大？节点间数据倾斜？
5. **重写或改表**：根据根因选择手段——加索引、改 Join 顺序、预聚合、冷热分层、换存储格式（MergeTree → ReplacingMergeTree）。

**第五层：组织与机制。** 单靠技术治不了慢查询，必须配套机制：

- **Owner 制度**：每条慢 SQL 必须找到业务 Owner + 数据 Owner，限期治理（通常 P0 问题 1 周、P1 问题 1 月）。
- **周会 Review TOP 慢查询**：美团 / 阿里都有专门的 SQL Review 周会，对 TOP 100 慢查询逐条过。
- **平台化**：把"EXPLAIN 检查 / 超时管控 / 慢查询 Top 榜"封装成平台能力，避免每个团队各做一套。
- **灰度上线**：新 SQL 先在影子库或小流量跑，验证 P99 达标后再全量。

**3. 常见陷阱**

- **只讲 EXPLAIN 不讲 SLO。** 面试官问"如何治理"，上来就讲 EXPLAIN 是把工程当函数，说明没在生产干过。
- **把 OLTP 经验套到 OLAP 上。** MySQL 的"加索引就快了"在 ClickHouse 上不成立——OLAP 慢往往要靠预聚合 / 改表结构 / 换存储引擎。
- **只看均值不看长尾。** 平均查询 200ms，但 P99 是 30 秒——只看均值是慢查询治理最大的盲区。
- **忽略分布式倾斜。** 单 shard 慢是单机问题；节点间数据倾斜是 Sharding 策略问题；查询计划慢是优化器问题。答不出这三层就太浅。
- **没有 Owner 制度。** 没有责任人的慢查询治理最终会变成"治不完的烂 SQL"——这是组织问题，不是技术问题。

**4. 追问预测**

- **「ClickHouse 单条查询很快，但并发上来就慢，怎么办？」** 答：这是 ClickHouse 的典型瓶颈——单查询快靠向量化执行 + 列存，但**并发能力弱**（MergeTree 不擅长高频小查询）。治理手段：① 合并小查询为批量；② 加读写分离把大查询隔离；③ 改用 Doris / StarRocks 等 MPP 引擎替代高频小查询；④ 用 ClickHouse 做离线 + Druid 做实时。
- **「EXPLAIN 显示走了索引，但还是很慢，可能是什么原因？」** 答：三个常见原因——① 索引统计信息过期（`ANALYZE TABLE` 没跑）；② 回表代价高（覆盖索引缺失，需要回聚簇索引）；③ 数据倾斜（同一个索引下某些 value 占比过高，导致 IO 不均）。
- **「ClickHouse 和 Doris / StarRocks 在慢查询治理上的本质差异？」** 答：ClickHouse 是"单机性能极致 + 并发弱"，慢查询治理侧重**资源隔离与查询合并**；Doris / StarRocks 是"MPP 分布式 + 并发强"，慢查询治理侧重**数据倾斜与 Join 顺序**。选择哪个引擎取决于查询模式，而不是性能高低。
- **「你们怎么量化慢查询治理的 ROI？」** 答：算"**慢查询占比 × 查询频次 × 单条耗时**"——把 TOP 100 慢查询的总耗时从集群总耗时的 30% 降到 5%，相当于释放 25% 的集群资源，可量化到节省 X 万元/年。

**5. 参考资料**

#### §8.2.2 在 Redis Cluster 中，大 Key（BigKey）与热 Key（HotKey）是稳定性的最大威胁。请你设计一套发现、治理与防护体系。

**1. 考察点**

- 是否理解**大 Key 与热 Key 是两个不同问题**：大 Key 是"单 Key 体积大"（如 Hash 存 1000 万元素），热 Key 是"单 Key 访问频次高"（如秒杀商品缓存）。二者都会拖垮 Redis，但治理手段完全不同。
- 能否说清大 Key 的**三类危害**：① 删除时阻塞（DEL 一个 1GB 的 Key 会阻塞 Redis 主线程数十毫秒）；② 迁移卡顿（Cluster 迁移 slot 时卡顿）；③ 内存倾斜（单节点内存爆掉）。
- 是否知道热 Key 的**三类危害**：① 单节点 QPS 瓶颈（无法水平扩展）；② 缓存击穿（Key 过期瞬间回源雪崩）；③ 带宽打满（单 Key 大 value + 高并发）。
- 加分项：能结合 Redis 6.0+ 的 `MULTI-EXEC`、Lazy Free、Client-side Caching 等特性谈新解法。

**2. 参考答案框架**

**第一层：先定义"大"与"热"——阈值因业务而异。**

- **大 Key 的阈值**（业内通行参考）：
  - String：value > 10 KB。
  - Hash / List / Set / Stream：元素数量 > 10000 或整体 > 10 MB。
  - 但**业务敏感度不同阈值也不同**——支付链路核心 Key 1MB 就算大；推荐候选集 50MB 也合理。**阈值必须按业务分级**。
- **热 Key 的阈值**：通常以 QPS 衡量——单 Key QPS > 10000（占总集群 5% 以上）就算热。但同样要看**业务重要程度**——大促爆款商品的 5 万 QPS 是热 Key，某个长尾标签的 5 千 QPS 也要治理。

**第三层：发现——离线扫描 + 实时探测双管齐下。**

- **离线扫描**：
  - **redis-cli `--bigkeys`**：遍历整个 DB 找出每种类型的 Top 1 大 Key，**采样统计**而非全量（避免阻塞生产）。
  - **RDB 离线分析**：用 `redis-rdb-tools` 解析 RDB 文件，按 Key 体积 / 类型分布排序，找出大 Key 列表。这是头部互联网的标准做法——**美团 / 阿里都用 RDB 离线分析做大 Key 巡检**。
  - **定期任务**：每天 / 每周跑一次扫描，结果入库到审计表，按业务 Owner 推送给负责人。
- **实时探测**：
  - **Proxy 层埋点**（如 Codis / Twemproxy 自带）：在代理层统计每个 Key 的 QPS 与带宽，热 Key 自然浮现。
  - **Redis `MONITOR` + 采样**（慎用）：高开销，仅用于短时诊断。
  - **客户端上报**：在业务代码里对高频 Key 主动埋点上报，是补充手段。
  - **`redis-cli --hotkeys`**（Redis 7.0+）：基于 LFU 访问频次输出热 Key，是新工具。

**第四层：治理——拆分、复制、迁移三板斧。**

针对**大 Key**：

- **拆分——从源头治理**：把大 Hash / List 拆成多个小 Key（如按 user_id 取模拆 100 个 Key），从根本上消除大 Key。
- **Lazy Free 异步删除**：Redis 4.0+ 提供 `UNLINK` 命令替代 `DEL`，大 Key 删除放进后台线程，不阻塞主线程。Redis 6.0+ 进一步把所有"可能慢"的删除（过期 Key、FLUSHDB）都默认走 Lazy Free。
- **迁移工具**：用 `redis-migrate-tool` 或自研工具做平滑迁移，避免 Cluster 重分片时卡顿。

针对**热 Key**：

- **多副本复制**：把热 Key 复制 N 份（如 `product:hot:001` ~ `product:hot:005`），业务侧按 user_id 取模读不同副本，把单 Key QPS 降到 1/N。
- **本地缓存兜底**：在客户端进程内做一层 Caffeine 本地缓存，热 Key 在 JVM 内直接返回，**不再走 Redis**——这是**美团 / Netflix 公开方案**的核心做法。Netflix EVCache 甚至把热 Key 缓存在 JVM 直接跳过 Redis。
- **Key 散列**：把热 Key 按业务维度拆分（如把"爆款商品详情"按用户地域拆成 N 个 Key），让热点天然分散。
- **读写分离 + 水平扩容**：热 Key 走读副本，主从分担 QPS；如果是 Key 体积大的"伪热 Key"，先解决大 Key 再看热度。

**第五层：防护——把治理做成平台能力。**

- **上线准入**：CI 流水线自动检测新 Key 的预估体积 / QPS，超阈值拒绝上线。
- **运行期告警**：单 Key 内存 > 阈值、单 Key QPS > 阈值、单节点带宽 > 阈值都触发告警。
- **熔断与降级**：热 Key 引发的雪崩可触发"本地缓存模式"——Redis 不可用时自动降级到本地缓存。
- **混沌演练**：定期对热 Key 做强制过期 / 节点宕机演练，验证治理方案的有效性。

**3. 常见陷阱**

- **把大 Key 与热 Key 混淆。** 二者治理手段完全不同，混在一起答必然答不全。
- **只讲发现不讲治理。** 扫描出大 Key 列表很容易，治理才是真正的工程难题——拆分、迁移、复制都有代价。
- **不知道 `UNLINK` 与 Lazy Free。** 直接用 `DEL` 删大 Key 会阻塞 Redis 主线程数毫秒，这是经典的生产事故源头。
- **忽略热 Key 的"伪热"。** 业务以为是热 Key 实际上是**大 Key**——一个 5MB 的 String 即使只 1000 QPS，单节点带宽也会被打满。区分"真热"与"伪热"是必备能力。
- **没有业务分级阈值。** 所有 Key 用同一阈值会"误报"或"漏报"，必须按业务重要程度分级。

**4. 追问预测**

- **「Redis Cluster 节点内存倾斜严重，单节点 OOM，怎么排查？」** 答：先看大 Key 分布——大概率是某个业务域的 Key 整体偏大且未做拆分；次看热 Key 分布——某个爆款 Key 集中到单 slot 导致该节点 QPS / 内存双高。治理手段是**重新规划 slot 与 Key 散列策略**。
- **「热 Key 引发雪崩，怎么设计降级方案？」** 答：三层降级——① 客户端本地缓存兜底（Caffeine，秒级 TTL）；② Proxy 层熔断（丢弃非核心读）；③ 回源限流（对 DB 加令牌桶，挡住回源雪崩）。Netflix EVCache 是把本地缓存做到极致的代表。
- **「大 Key 怎么平滑迁移？」** 答：用 `redis-migrate-tool` 或自研工具做"分批搬迁"——每次迁移 10% 数据，每批间留间隔观察 cluster 状态；迁移完后再切换业务路由；最后清理旧 Key。
- **「Redis 7.0 的 `FUNCTION` 与 `CLUSTER SLOTS` 改进对治理有什么帮助？」** 答：`FUNCTION` 支持把治理逻辑下推到 Redis 服务端（如自定义大 Key 检测函数），减少业务侧维护成本；`CLUSTER SLOTS` 改进让 slot 迁移更平滑，缓解大 Key 迁移卡顿。

#### §8.2.3 在一个高并发 Web 服务中，数据库连接池（Druid / HikariCP）与业务线程池（Tomcat / 自定义线程池）经常成为瓶颈。请你说明如何合理配置连接池与线程池参数。

**1. 考察点**

- 是否理解**连接池与线程池是两个不同维度的资源**：连接池约束"对外部 IO 的并发"，线程池约束"对 CPU 的并发"，二者通过 Little's Law 关联。
- 能否基于 Little's Law（`并发 = QPS × 平均响应时间`）从业务目标反推资源数量，而不是拍脑袋设值。
- 是否知道**经典的反模式**：连接池配 1000、线程池配 800、然后服务一启动就 OOM。背后的物理约束是 FD 上限与内存上限。
- 加分项：能区分"**同步阻塞线程池**"与"**异步事件循环**"两种并发模型的资源计算差异。

**2. 参考答案框架**

**第一层：先算约束——Little's Law 是起手式。**

Little's Law：`并发数 = QPS × 平均响应时间`。

举例：一个 10000 QPS、平均 RT 50ms 的接口：

- 稳态并发 = 10000 × 0.05 = **500 个并发**。
- 这 500 并发需要的**线程数**取决于线程模型：
  - **同步阻塞**（Java Thread per Request）：线程数 ≈ 并发数 ≈ **500 个**（Tomcat 默认 200 显然不够）。
  - **异步事件循环**（Netty / Vert.x）：线程数 ≈ 少量（一般 = CPU 核数 + 1），所有连接共享一个事件循环。
- 这 500 并发对外部 IO 的需求：
  - 平均 50ms 中有 30ms 是等 DB 连接池 → DB 连接池至少要能"同时支持 500 并发等连接"——但同时要避免每个连接平均等待 30ms，所以连接数应**大于**并发数 / 单连接吞吐。

**第二层：连接池配置——HikariCP 的核心参数。**

HikariCP 是 Spring Boot 默认连接池，配置围绕三个核心参数：

- **`maximumPoolSize`（最大连接数）**：经验公式——
  - **CPU 密集型**：`连接数 = CPU 核数 + 1`（此时 DB 是 CPU 密集）。
  - **IO 密集型**：连接数受 DB 服务端 `max_connections` 限制。通常是 `(DB 服务端 max_connections × 0.8) / 应用实例数`。例如 DB 总连接上限 1000、20 个应用实例 → 每实例 40 个连接。
  - **混合型**：起步按 `(并发数 × DB 等待占比)` 估算，再压测调优。
- **`minimumIdle`（最小空闲连接）**：建议 = `maximumPoolSize`，避免运行时频繁建连。HikariCP 默认是 `maximumPoolSize`（固定大小连接池），这是它比 Druid 默认行为快的原因之一。
- **`connectionTimeout`（获取连接超时）**：默认 30s 过长，生产建议 3-5s——拿不到连接立刻失败，让上游限流/熔断，不要无限制等。
- **`idleTimeout` / `maxLifetime`**：`maxLifetime` 必须小于 DB / 网络设备的 idle timeout（通常 MySQL `wait_timeout` 默认 8h，负载均衡器可能 30min）。建议 `maxLifetime = 30min`。
- **Druid 的额外能力**：监控（SQL 执行时长分布、慢查询统计）、连接泄漏检测（`removeAbandoned`）、自定义 Filter（SQL 改写、敏感字段脱敏）。如果团队需要这些，选 Druid；如果追求极致性能，选 HikariCP。

**第三层：线程池配置——区分业务线程池与 Tomcat 容器线程池。**

**Tomcat 容器线程池**（处理 HTTP 请求的入口）：

- **`server.tomcat.threads.max`**：默认 200，IO 密集型按 `(峰值 QPS × P99 RT)` 估算。上例需要 500+。
- **`server.tomcat.threads.min-spare`**：默认 10，预热连接避免冷启动延迟。
- **`accept-count`**：当线程数满时，accept 队列的长度。默认 100，建议适当调大（如 500），但配合 `max-connections` 防止 OS 层 FD 耗尽。
- **`max-connections`**：Tomcat 能接受的总连接数，默认 8192，需要与 OS `ulimit -n` 对齐。

**业务自定义线程池**（如异步任务、批处理）：

- **`corePoolSize`**：常驻线程数。IO 密集型 `2 × CPU 核数`，CPU 密集型 `CPU 核数 + 1`。
- **`maximumPoolSize`**：最大线程数。建议 ≤ 50 或按压测峰值，**避免无界线程池导致 OOM**。
- **`workQueue`**：**慎用无界队列**（`LinkedBlockingQueue` 默认 `Integer.MAX_VALUE`）——任务堆积是 OOM 与延迟爆炸的根源。推荐用**有界队列 + 拒绝策略**（`CallerRunsPolicy` 或自定义）。
- **`keepAliveTime`**：空闲线程存活时间。IO 密集型可设 60s，CPU 密集型可设 30s。
- **任务隔离**：核心链路（支付）走独立线程池，与非核心（日志、监控）隔离，避免非核心任务占满线程拖垮核心。
- **Netflix Hystrix 的舱壁模式**：每个远程依赖一个线程池，单个依赖慢不会拖垮全部——是熔断思想在线程池维度的落地。

**第四层：异步化——跳出"线程数 = 并发"的陷阱。**

同步阻塞模型下，线程数 ≈ 并发数，500 并发就要 500 线程——这在 Java 里是灾难（默认 1MB 栈 × 500 = 500MB 栈内存）。**异步化的核心是用少量线程处理高并发**：

- **Servlet 3.0 异步**：`request.startAsync()` 释放容器线程，等回调完成再写回响应。Tomcat 默认支持。
- **Spring WebFlux / Reactor**：基于 Netty 的响应式编程，事件循环模型，单机可支撑 1 万+ 并发。
- **Kotlin 协程 / Go goroutine**：轻量级线程（M:N 调度），百万级并发可行。
- **CompletableFuture + 自定义线程池**：把阻塞 IO 异步化，等所有 Future 完成再组合结果。

异步化后**线程池大小可以大幅缩小**（一般 8-32 个），但需要重写代码并接受编程模型的复杂度。

**第五层：监控与调优闭环。**

- **连接池监控**：活跃连接数、空闲连接数、获取连接的等待时长分布。HikariCP 的 `HikariPoolMXBean` + Micrometer，Druid 的 StatViewServlet。
- **线程池监控**：活跃线程数、队列深度、拒绝次数、任务执行时长。Micrometer 的 `ExecutorServiceMetrics`。
- **告警阈值**：连接池等待 > 100ms 持续 5 分钟告警；线程池队列深度 > 80% 容量告警；拒绝次数 > 0 立即告警。
- **压测验证**：用 JMeter / k6 / Gatling 模拟峰值 QPS，观察连接池与线程池的实时指标，找到"在 P99 不劣化前提下的最大承载 QPS"。

**3. 常见陷阱**

- **拍脑袋设值。** 连接池 1000、线程池 800 是常见的"大就完事"反模式，没有物理意义。
- **忽略 DB 服务端上限。** 应用连接池 1000 但 DB `max_connections=500`，连接会被服务端拒绝。
- **同步阻塞模型下线程数 ≈ 并发数。** 不理解这个等式就会以为"线程池越大越好"，结果 OOM。
- **无界任务队列。** `new LinkedBlockingQueue<>()` 默认容量无限，任务堆积是延迟与 OOM 的根源。
- **混淆连接池与线程池的资源约束。** 连接池约束 IO、线程池约束 CPU，二者通过 Little's Law 关联，但不是同一个数。

**4. 追问预测**

- **「连接池满了，DB 慢查询导致连接长期被占，怎么治理？」** 答：① 上游加超时（`connectionTimeout=3s`、`socketTimeout=10s`），让慢连接快速失败；② DB 侧加慢查询治理（§8.2.1）；③ 应用侧加熔断（Hystrix / Sentinel），DB 错误率超阈值直接降级。
- **「线程池队列深度报警，怎么决策是该扩容还是该优化下游？」** 答：先看下游——如果 RT 在涨，扩容线程池只是延缓问题；正确做法是定位下游慢根因（DB 慢？远程调用慢？）。如果 RT 稳定但瞬时 QPS 高，可临时扩容 + 加限流。
- **「同步改异步的具体收益怎么算？」** 答：原 500 并发 × 1MB 栈 = 500MB 栈内存；改异步后 32 线程 × 1MB = 32MB，节省 468MB。同时单机并发从 500 提升到 1 万+。代价是编程模型复杂度上升，需要全链路响应式改造。
- **「Tokio / Netty 的事件循环线程数怎么配？」** 一般 = CPU 核数（或 2 × CPU 核数，看是否 IO 密集）。**不要超过 64**，太多反而降低调度效率。

#### §8.2.4 请你系统阐述多级缓存架构的设计，并说明如何治理缓存穿透、缓存击穿、缓存雪崩三大经典问题。

**1. 考察点**

- 是否理解**多级缓存不是为了"快"，而是为了"在不同成本下满足不同一致性要求"**——客户端缓存零延迟但难一致，CDN 缓存低延迟但只读，Redis 集群均衡但有上限，本地缓存快但容量小。
- 能否说清缓存三大问题的**根因与对应解法**——穿透是"查不存在的数据"、击穿是"热点 Key 过期瞬间"、雪崩是"大量 Key 同时过期"。
- 是否知道**缓存与一致性、可用性的三角取舍**（CAP）——缓存是 AP 系统，DB 是 CP 系统，二者组合需要明确的"缓存策略"。
- 加分项：能结合**Netflix EVCache**、**阿里 Tair**、**字节 Aimer** 等工业级缓存中间件谈落地。

**2. 参考答案框架**

**第一层：先立框架——多级缓存金字塔。**

```
        [客户端 / 浏览器缓存]   ← 零延迟、零带宽，但难一致
       [CDN 缓存]              ← 边缘节点、低延迟，但只读
    [应用本地缓存]              ← Caffeine、Guava，毫秒级，但容量小
   [分布式缓存]                 ← Redis Cluster / Tair，毫秒级，容量大
  [数据库查询缓存]              ← MySQL Query Cache / Result Cache
 [数据库]                       ← 持久层，最终一致
```

每一级的取舍：

| 层级 | 延迟 | 容量 | 一致性 | 典型场景 |
| --- | --- | --- | --- | --- |
| 客户端 | 0ms | KB-MB | 最弱 | 用户偏好、首屏数据 |
| CDN | 1-10ms | TB+ | 弱 | 静态资源、热门接口 |
| 本地 | 1ms | GB | 中 | 热点字典、配置 |
| 分布式 | 5-10ms | TB | 中强 | 通用业务数据 |
| 数据库 | 10-100ms | PB | 强 | 全部数据 |

**第二层：缓存策略——三种基础模式。**

- **Cache-Aside（旁路缓存，最常用）**：读时先查缓存，miss 则读 DB 并回填；写时更新 DB 后**失效缓存**（不是更新缓存）。**Netflix EVCache** 是这个模式的工业实现。
- **Read-Through / Write-Through**：缓存作为读写入口，DB 在背后同步——实现复杂，但保证一致性。
- **Write-Behind（异步写回）**：写只更新缓存，异步批量回 DB——性能极高，但有数据丢失风险（如 Redis 宕机丢失更新）。**Redis Stream + Kafka** 是常见组合。

国内大厂的实践：**阿里 Tair** 用 Read-Through 模式做强一致场景；**字节 Aimer** 用 Cache-Aside + 多级本地缓存做超高性能场景。

**第三层：缓存穿透——查不存在的数据。**

- **症状**：每次都查 DB，缓存形同虚设。
- **根因**：恶意攻击或业务设计问题（如用负 ID 查询）。
- **解法**：
  - **空值缓存**：DB 返回空也缓存（如 `null` 或空字符串），TTL 设短（如 5 分钟）。
  - **Bloom Filter**：在缓存前用布隆过滤器判断 Key 是否存在，不存在直接返回——**美团 / 字节都用 Bloom Filter 兜底缓存穿透**。
  - **参数校验**：在 API 层拒绝明显非法的参数（如负数 ID、超长字符串）。

**第四层：缓存击穿——热点 Key 过期瞬间。**

- **症状**：某个超热 Key 过期，瞬时大量请求打到 DB，DB 被打挂。
- **根因**：热点 Key 的并发回源，单 Key 击穿。
- **解法**：
  - **互斥锁 / Single Flight**：Key 过期时，只让一个线程去 DB 加载，其他线程等待或返回旧值。Go `singleflight` 库、Java `Redisson` 的 `RLock` 是工业实现。
  - **逻辑过期**：Key 不过物理 TTL，而是在数据里带 `expire_at`，发现过期时异步刷新——避免"过期瞬间"的存在。
  - **永不过期**：对核心热点 Key（如秒杀商品）设"逻辑永不过期"，后台异步刷新——**阿里双 11 用这个方案兜底秒杀缓存**。

**第五层：缓存雪崩——大量 Key 同时过期。**

- **症状**：某时刻大量缓存同时过期，DB 被瞬时洪峰打挂。
- **根因**：缓存失效时间集中 + 重建耗时 + DB 容量不足。
- **解法**：
  - **过期时间打散**：TTL 加随机抖动（`baseTTL + random(0, 60s)`）——最简单有效。
  - **多级缓存**：即使分布式缓存全部过期，本地缓存仍能兜底（毫秒级返回）。
  - **熔断降级**：DB 错误率超阈值触发熔断，缓存未命中时返回兜底数据（如上次 last值）。
  - **预热**：大促前主动加载热点 Key 到缓存，避免运行时冷启动。
  - **Redis Cluster 高可用**：主从切换 + Sentinel / Cluster，避免缓存层自身故障导致雪崩。

**第六层：一致性——缓存与 DB 的"最终一致性"。**

Cache-Aside 模式下的**经典不一致场景**：

- **写 DB 后删缓存失败**：DB 已更新但缓存还是旧值，下次读到旧数据。
- **并发读写**：线程 A 写 DB，线程 B 读 cache miss 去 DB 读旧值并回填，缓存又是旧值。
- **延迟双删**：写 DB → 删缓存 → 延迟 N ms 再删一次（应对并发回填）。代价是 N ms 内仍可能读到旧数据。
- **基于 binlog 的异步同步**：监听 DB binlog（如 Canal），通过 MQ 异步删除/更新缓存——保证最终一致，**美团 / 阿里都用这个方案做跨级缓存一致性**。
- **版本号 / CAS**：在缓存 value 里带版本，写时用 `SETNX` 带版本号——避免乱序更新。

**3. 常见陷阱**

- **混淆穿透、击穿、雪崩。** 三者根因完全不同：穿透是"查不存在"、击穿是"查过期热点"、雪崩是"查过期大量"。混在一起答说明没真懂。
- **只讲技术不讲取舍。** 缓存是 AP 系统的代表——你接受"最终一致性"才用缓存，期望强一致就用 DB。任何"既要缓存又要强一致"的方案都是反模式。
- **永不过期方案无脑套用。** 数据真的变更了却没人刷新，会导致永久旧值——必须有配套的异步刷新机制。
- **延迟双删的延迟时间拍脑袋。** 必须基于"DB 写入耗时 + 缓存回填耗时"估算，盲目设 500ms 可能不够也可能浪费。
- **Bloom Filter 误判导致业务漏数据。** 布隆过滤器有误判率，必须设置合理 + 兜底（如误判走 DB 加载）。

**4. 追问预测**

- **「多级缓存如何保证一致性？特别是 CDN 缓存失效怎么主动刷新？」** 答：分层治理——本地缓存用 TTL + 主动失效，Redis 用 Canal 订阅 binlog 异步失效，CDN 用 purge API 主动刷新（CDN 没有"被动失效"机制）。**阿里云的 CDN 刷新 API + 业务主动触发**是国内大厂的标准做法。
- **「缓存与 DB 一致性方案中，延迟双删 vs binlog 异步同步哪个更好？」** 答：延迟双删实现简单但仍有窗口；binlog 异步同步保证最终一致但引入 MQ 依赖。**金融级一致**用同步双写 + 分布式事务；**普通业务**用 binlog 异步同步；**非关键业务**用延迟双删。
- **「如果 Redis 整个集群挂了，怎么降级？」** 答：三级降级——① 本地缓存兜底（Caffeine，几秒 TTL）；② 限流（拒绝非核心读）；③ 直连 DB（牺牲性能保可用）。Netflix 在 Redis 不可用时自动切到本地缓存 + DB 直连是工业标杆。
- **「秒杀场景下缓存如何设计才能扛住百万 QPS？」** 答：① 库存预热到 Redis；② Lua 脚本原子扣减（避免超卖）；③ 本地缓存兜底；④ 限流 + 队列削峰；⑤ DB 只做最终一致性兜底。**阿里双 11 秒杀**是工业标杆。

#### §8.2.5 在 OLTP 场景下，一条慢 SQL 拖垮整个库是经典故事。请你系统阐述 SQL 调优的完整方法论，并结合执行计划分析说明常见误区。

**1. 考察点**

- 是否理解**SQL 调优不是"加索引就完了"**，而是「**执行计划 → 索引设计 → 写法重写 → 表结构 → 架构**」五层下钻。
- 能否熟练使用 EXPLAIN / EXPLAIN FORMAT=JSON / OPTIMIZER TRACE 分析执行计划——这是与"背优化技巧"的本质区别。
- 是否知道**常见的反模式**：`SELECT *`、隐式类型转换、函数包裹列、JOIN 顺序错误、深度分页、未命中索引的 ORDER BY 等。
- 加分项：能结合**MySQL 8.0 的 Hash Join、新增索引跳跃扫描、CBO 优化器**等新特性谈演进。

**2. 参考答案框架**

**第一层：先看执行计划——EXPLAIN 是 SQL 调优的"X 光"。**

标准 EXPLAIN 输出字段的含义（必须背熟）：

| 字段 | 关键含义 | 调优信号 |
| --- | --- | --- |
| `type` | 访问类型：ALL（全表扫描）< index < range < ref < eq_ref < const < system | **ALL 是性能灾难**，必须改 |
| `rows` | 优化器预估扫描行数 | 与实际偏差大说明统计信息过期 |
| `key` | 实际使用的索引 | NULL 是没走索引，必须改 |
| `Extra` | 附加信息：Using filesort / temporary / where | 文件排序和临时表是性能杀手 |

进阶工具：

- **EXPLAIN FORMAT=JSON**：看更细的成本估算（如 `cost_info`、`buffer_used`）。
- **OPTIMIZER TRACE**（MySQL 5.6+）：优化器的完整决策过程，能看到为什么选错索引。
- **EXPLAIN ANALYZE**（PostgreSQL）：不仅看计划，还实际执行，返回真实耗时——比 MySQL 更直观。

**第二层：索引设计——覆盖查询的 80% 场景。**

- **最左前缀原则**：联合索引 `(a, b, c)` 能命中 `WHERE a=?`、`WHERE a=? AND b=?`，但不能命中 `WHERE b=?`。
- **覆盖索引**：SELECT 的列都在索引里，无需回表——`Extra: Using index` 是最优解。
- **索引选择性**：高选择性列（值分布均匀，如 user_id）适合建索引；低选择性列（is_deleted、gender）建索引收益小。
- **避免函数包裹列**：`WHERE DATE(create_time) = '2025-01-01'` 会让索引失效——改为 `WHERE create_time >= '2025-01-01' AND create_time < '2025-01-02'`。
- **避免隐式类型转换**：`WHERE phone = 13800000000`（phone 是 varchar）会导致 phone 转数字、索引失效。

**第三层：常见 SQL 反模式与改写。**

1. **`SELECT *`**：查不需要的列浪费 IO + 内存，且无法走覆盖索引。**必改**：SELECT 具体列。
2. **深度分页**：`LIMIT 1000000, 20` 会扫描 10000 020 行——改为游标分页（`WHERE id > X LIMIT 20`）或延迟关联（先查 ID 再 JOIN）。
3. **大 IN 列表**：`WHERE id IN (1,2,3,...,10000)` 会让优化器放弃索引——拆成多次查询或用临时表。
4. **JOIN 顺序错误**：A JOIN B WHERE B.x = ?，如果 A 很大而 B.x 索引缺失，应该先过滤 B 再 JOIN。**用 `STRAIGHT_JOIN` 强制顺序**是 MySQL 专属解法。
5. **未命中的 ORDER BY**：`ORDER BY create_time DESC` 不带 WHERE 条件——必须建 `(create_time DESC)` 索引，否则走 filesort。
6. **OR 条件**：`WHERE a=? OR b=?` 经常让索引失效——改为 UNION ALL。
7. **子查询 vs JOIN**：MySQL 5.6 之前相关子查询执行慢，应改写为 JOIN；5.6+ 优化器已自动优化，但仍需警惕。

**第四层：表结构与数据组织——根治性优化。**

- **冷热分离**：热数据（近 3 个月订单）放主库，冷数据（历史订单）走归档库或 ClickHouse。
- **读写分离**：所有写走主库，所有读走从库；用 Sharding-JDBC / MyCat 等中间件透明路由。
- **分库分表**：单表 > 5000 万行考虑分表，按 user_id 哈希；分库分表后 JOIN 跨库要尽量避免，必要时走宽表或数据冗余。
- **大字段分离**：`content TEXT`、`log JSON` 等大字段单独建表，避免主表行过大。
- **数据类型选择**：能用 INT 不用 BIGINT、能用 VARCHAR(50) 不用 TEXT、能用 DATE 不用 DATETIME——直接降低单行 IO。

**第五层：架构与硬件——最后一道防线。**

- **连接池调优**：DB 连接数受 `max_connections` 限制，应用侧连接池不能盲目调大（§8.2.3）。
- **读写分离代理**：ProxySQL / MyCat / ShardingSphere-Proxy，把读流量透明路由到从库。
- **查询缓存**：MySQL 8.0 之前有 Query Cache，但高并发下反而是累赘——一般禁用。改用 Redis 做应用层缓存。
- **硬件**：SSD（IOPS 提升 10 倍+）、更大的 Buffer Pool（`innodb_buffer_pool_size = 物理内存的 70-80%`）、NUMA 亲和性配置。
- **审计与限流**：所有 SQL 走 Proxy 限流，超阈值告警或 kill——避免单条烂 SQL 拖垮整个库。

**3. 常见陷阱**

- **只加索引不看执行计划。** 索引加错、用不上索引的情况很多，必须 EXPLAIN 验证。
- **忽略统计信息过期。** MySQL 优化器依赖统计信息（`ANALYZE TABLE`），数据大幅变化后必须重收集。
- **过度依赖索引。** 表设计不合理（如单表 5 亿行），加索引也救不了——必须分库分表或冷热分离。
- **混淆"加索引"与"索引生效"。** 加索引不等于用了索引——`WHERE` 写法不对、函数包裹列、类型转换都让索引失效。
- **忽视 ORDER BY / GROUP BY 的索引需求。** 排序与分组也要走索引，否则 filesort 是性能杀手。
- **把 OLTP 调优经验套到 OLAP。** 大表 JOIN、宽表聚合在 ClickHouse / Doris / StarRocks 上才是解法，MySQL 上是死路。

**4. 追问预测**

- **「EXPLAIN 显示走了索引，但实际很慢，可能是什么原因？」** 答：① 索引统计信息过期（`ANALYZE TABLE` 没跑）；② 回表代价高（覆盖索引缺失）；③ 索引选择性差（如性别索引）；④ 数据倾斜（同一索引下某些 value 占比过高）；⑤ IO 瓶颈（磁盘慢、buffer pool miss）。
- **「深度分页怎么优化？给你一个 1 亿行的表。」** 答：① 游标分页（`WHERE id > last_id LIMIT 20`），适合无限滚动；② 延迟关联（`SELECT * FROM t JOIN (SELECT id FROM t LIMIT 1000000, 20) tmp`），先 ID 再回表；③ Elasticsearch 接管分页（基于倒排索引的 search_after）；④ 业务上禁止跳页（如订单列表只能顺序翻）。
- **「JOIN 怎么优化？」** 答：① 小表驱动大表（MySQL 优化器不一定对，可用 `STRAIGHT_JOIN`）；② 关联字段建索引；③ 大 JOIN 走宽表预聚合；④ 跨库 JOIN 避免，改宽表或数据冗余。
- **「MySQL 8.0 的 Hash Join 解决了什么问题？」** 答：MySQL 之前没有原生 Hash Join，大表 JOIN 走 Nested Loop Join（NLJ）是 O(M×N) 复杂度。Hash Join 是 O(M+N)，对大表 JOIN 提升 5-10 倍。**MySQL 8.0.18+ 默认开启**，但仅在等值 JOIN + 无索引场景下生效。
- **「你们怎么量化 SQL 调优的 ROI？」** 答：算「**慢 SQL 数量 × 平均耗时 × QPS**」——把 TOP 100 慢 SQL 的总耗时从集群总耗时的 40% 降到 5%，相当于每天省 100 万+ 次慢查询 IO。

#### §8.2.6 请你系统阐述 JVM GC 调优的方法论，并对比 G1、ZGC、Shenandoah 三大现代 GC 的适用场景。

**1. 考察点**

- 是否理解**GC 调优不是"调参数"，而是"先理解应用内存特征，再选 GC，再调参数"**。
- 能否说清 G1 / ZGC / Shenandoah 的**核心差异**——G1 是"分区 + 增量回收"、ZGC / Shenandoah 是"并发 + 着色指针 / 转发指针"。
- 是否知道**GC 调优的常见目标**：降低 STW 时长、控制 Young / Old GC 频率、避免 Full GC、降低内存占用。
- 加分项：能结合**Java 21 的分代 ZGC**、**GraalVM Native Image**（无 GC）等新方向谈演进。

**2. 参考答案框架**

**第一层：先理解 JVM 内存布局——GC 调优的地图。**

JVM 堆分代（HotSpot 默认）：

- **Young 区**：Eden + 2 Survivor。新对象在 Eden，Minor GC 后存活对象进 Survivor，多次存活后晋升 Old。
- **Old 区**：长生命周期对象。Major GC（Full GC）回收，STW 较长。
- **Metaspace**（JDK 8+）：替代 PermGen，存类元数据，受系统内存限制而非 JVM 堆。
- **Code Cache**：JIT 编译产物，受 `-XX:ReservedCodeCacheSize` 控制。

GC 类型：

- **Minor GC**：Young 区回收，STW 短（一般 < 10ms），高频。
- **Major GC / Full GC**：Old 区 + Young + Metaspace 整体回收，STW 长（百毫秒~数十秒），低频但致命。

调优的本质**是减少 Full GC 的频率与单次 STW 时长**。

**第二层：GC 调优的"四步法"。**

**第一步：识别应用内存特征。**

- **Young 区使用多、Old 区使用少**：短生命周期对象为主（如 API 服务、订单处理），适合高 Young GC 频率 + 低 Old GC 频率。
- **Old 区使用多、Young 区使用少**：长生命周期对象为主（如缓存服务、内存数据库），需要小心内存泄漏。
- **分配速率高（每秒分配 GB 级）**：Young 区容易快速填满，Minor GC 频繁——需要更大 Young 区或减少短生命周期对象。

**第二步：选 GC。**

- **应用延迟敏感（P99 < 100ms）、堆 < 16GB** → **G1 GC**（默认 JDK 9+）。
- **应用延迟极敏感（P99 < 10ms）、堆 > 16GB** → **ZGC**（JDK 11 实验版、JDK 15 生产可用，JDK 21 分代）。
- **需要 OpenJDK 兼容 / 红帽生态** → **Shenandoah**（Red Hat 主推）。

**第三步：调参数。**

**G1 调优核心参数**：

- `-Xms / -Xmx`：堆大小。建议**设相等**（避免运行时扩容带来的 STW），如 `-Xms8g -Xmx8g`。
- `-XX:MaxGCPauseMillis=200`：目标最大暂停时间，默认 200ms。**G1 会尽量满足，但代价是吞吐降低**——不要无脑设 50ms。
- `-XX:G1HeapRegionSize`：Region 大小，1-32 MB，建议 16 MB（堆 < 16GB）。
- `-XX:InitiatingHeapOccupancyPercent=45`：触发并发标记的堆占用阈值，默认 45%。
- `-XX:+G1UseAdaptiveIHOP`：自适应 IHOP，建议开启。
- `-XX:+UseStringDeduplication`：字符串去重，降低 Old 区占用。

**ZGC 调优核心参数**：

- `-XX:+UseZGC`：启用 ZGC。
- `-XX:SoftMaxHeapSize`：软上限，ZGC 会在不超过软上限时尽量回收。
- 其他参数 ZGC 会自适应，**调优空间比 G1 小**——这是 ZGC 的设计目标（"让 GC 自动调优"）。

**第四步：监控与验证。**

- **GC 日志**：`-Xlog:gc*`：详细的 GC 时间、停顿、回收量。
- **JFR（Java Flight Recorder）**：JDK 自带低开销 Profiling 工具，记录 GC、线程、IO 等事件。
- **async-profiler**：开源工具，可视化 GC、CPU、内存分配。
- **Grafana + Prometheus + Micrometer**：把 GC 指标接入监控大盘。

**第三层：常见 GC 问题与排查。**

1. **频繁 Young GC**：
   - 现象：每秒数十次 Minor GC，每次回收少量对象。
   - 原因：Young 区太小 / 短生命周期对象太多 / 内存泄漏（如 ThreadLocal 未清理）。
   - 解决：增大 Young 区比例（`-XX:NewRatio=1`），或减少短生命周期对象（对象池、复用对象）。

2. **频繁 Full GC**：
   - 现象：每小时数次 Full GC，每次 STW 数百毫秒。
   - 原因：内存泄漏 / Old 区太小 / Metaspace 不足 / 显式 `System.gc()` 调用。
   - 解决：用 MAT / jmap 分析堆转储，定位泄漏；调大 Old 区；禁用 `System.gc()`（`-XX:+DisableExplicitGC`）。

3. **单次 GC STW 过长**：
   - 现象：Full GC 一次停 10 秒。
   - 原因：堆过大（> 32GB）+ 大量对象 + 单线程 GC。
   - 解决：换 ZGC（并发收集）；减少堆大小；减少对象数量（用 Off-Heap / 列存）。

4. **内存泄漏**：
   - 现象：Old 区稳定增长，每次 GC 后可用空间越来越少，最终 OOM。
   - 排查：jmap dump → MAT 分析保留树 → 找到持有大对象的根。
   - 解决：清理 ThreadLocal、关闭连接、清理静态集合。

**第四层：未来方向——GraalVM Native Image 与分代 ZGC。**

- **GraalVM Native Image**：把 Java 代码 AOT 编译为本地二进制，**无 JVM、无 GC**——启动时间 < 100ms，内存占用 < 50MB。代价是不支持反射（需配置）、运行期无法生成类。Serverless 场景（AWS Lambda、阿里云函数计算）首选。
- **分代 ZGC（Java 21+）**：在并发 ZGC 基础上引入分代假设（多数对象朝生夕死），降低 GC 频率 50%+，延迟保持 < 1ms。**JDK 21 LTS 已默认推荐**。
- **Lilliput（OpenJDK 实验）**：把对象头压缩到 64 bit 以下，减少 GC 扫描开销。

**3. 常见陷阱**

- **盲目追求低 STW 而忽略吞吐。** 把 `MaxGCPauseMillis` 设到 50ms 会让 G1 频繁触发，部分回收 + 整体吞吐降低 20%——得不偿失。
- **堆大小拍脑袋。** `-Xmx32g` 看似"大就是好"，实际会导致单次 GC 时间极长（数十秒）。建议按"业务峰值 × 1.5"估算。
- **`-Xms != -Xmx`**。两者不等会让运行时扩容触发 Full GC，是常见的 GC 抖动源头。
- **忽视 Metaspace。** Metaspace 溢出（类加载过多，如动态代理、CGLIB）会导致 Full GC，需要监控 Metaspace 使用率。
- **把 GC 问题当 JVM 问题。** 80% 的 GC 问题根因是**应用代码**（内存泄漏、对象池不当）——单纯调 JVM 参数治标不治本。
- **不区分延迟与吞吐场景。** 金融交易要求 P99 < 10ms（选 ZGC），离线报表允许 STW 数秒（G1 默认即可）。

**4. 追问预测**

- **「你们的应用堆 32GB、延迟要求 P99 < 50ms，怎么选 GC？」** 答：**ZGC**——G1 在 32GB 堆上单次 Mixed GC 可能 STW 数百毫秒，无法满足 50ms SLO；ZGC 并发收集可控制在 1ms 以内。Java 21 推荐**分代 ZGC**。
- **「Full GC 怎么定位和止血？」** 答：先看 GC 日志确认是内存泄漏还是分配过快——若是分配过快，调大堆或减少对象；若是泄漏，jmap dump + MAT 分析保留树，找到泄漏点修复；**线上止血**可启动前加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp`，OOM 自动转储。
- **「G1 的 Region 大小怎么选？」** 答：默认按堆大小自动估算（堆 8GB 时 Region=4MB，堆 64GB 时 Region=32MB）。手动设的指导原则——Region 数在 2048-4096 之间最佳，过小 GC 开销大，过大并发标记粒度粗。
- **「ZGC 这么强，为什么不直接用 ZGC？」** 答：① JDK 版本要求（JDK 15+ 才生产可用）；② 操作系统要求（Linux / x86-64）；③ 部分场景吞吐比 G1 低 5-10%（并发收集的写屏障开销）；④ **Java 21 之前 ZGC 不分代**，对分配速率高的场景可能不如 G1。**分代 ZGC** 解决了这个问题。
- **「怎么判断应用应该用 GraalVM Native Image？」** 答：典型场景——Serverless / 短生命周期服务（Lambda、Knative）、CLI 工具、微服务的 sidecar。**不适用**场景——长生命周期大量反射、动态类加载的应用（如 OSGi、Scala）。

#### §8.2.7 请你系统阐述 CPU 火焰图（Flame Graph）的原理、生成方法，并说明如何基于火焰图进行全链路 Profiling 与性能瓶颈定位。

**1. 考察点**

- 是否理解**火焰图不是工具，而是"可视化的调用栈采样数据"**——它的价值在于让复杂的调用关系变成"看一眼就知道哪里最忙"。
- 能否说清**火焰图的生成原理**——基于 perf / bpf / async-profiler 的栈采样，频率（如 99Hz）越高样本越多、但开销越大。
- 是否知道**火焰图的局限**：它展示的是"CPU 占用"，但**不展示** IO 等待、锁竞争、GC 时间——这些需要其他 Profiling 工具（VTune、JFR、async-profiler 的不同事件）。
- 加分项：能结合**Netflix / Uber / Meta** 的 Profiling 实践，以及 **eBPF / Continuous Profiling（Datadog / Polar Signals）**等新方向谈演进。

**2. 参考答案框架**

**第一层：先理解 Profiling 的基本原理——采样的力量。**

火焰图基于**栈采样（Stack Sampling）**：

- Profiling 工具（如 `perf record`）以固定频率（如 99Hz）触发中断，每次中断时记录**当前所有线程的调用栈**。
- 高频采样意味着"几乎所有耗时操作都会被捕捉"——但频率过高会增加开销（一般 99Hz 开销 < 1%）。
- 采样结束后，把栈合并、统计，按"在栈顶的次数"聚合，生成火焰图。

火焰图的**三层含义**：

- **X 轴**：样本总数（不是时间），宽度越大代表占用越久。
- **Y 轴**：调用栈深度，每一层是一个函数。
- **颜色**：通常无意义（仅区分模块），但有些工具会用颜色标识"类型"（on-CPU / off-CPU）。

**第二层：火焰图的类型与适用场景。**

按 Profiling 类型分（Brendan Gregg 分类）：

| 类型 | 火焰图变种 | 适用场景 |
| --- | --- | --- |
| **on-CPU** | CPU 火焰图 | CPU 密集型瓶颈（如序列化、加密） |
| **off-CPU** | Off-CPU 火焰图 | IO / 锁 / Sleep 瓶颈（如线程阻塞） |
| **Memory** | 内存火焰图 | 内存分配热点（如 JSON 序列化） |
| **Page Fault** | Page Fault 火焰图 | 内存换页瓶颈 |
| **Differential** | 差分火焰图 | 优化前后对比 |

**最常用的两类**：

- **CPU 火焰图（on-CPU）**：定位 CPU 消耗最大的函数。`perf record -F 99 -p <pid> -g -- sleep 30` + `perf script | FlameGraph/stackcollapse-perf.pl | FlameGraph/flamegraph.pl > out.svg`。
- **Off-CPU 火焰图**：定位线程等待时间消耗在哪儿（IO、锁、网络）。`perf record -e sched:sched_switch -g -- sleep 30` 生成 off-CPU。

**第三层：生成工具链——从单机到分布式。**

**单机工具**：

- **perf + FlameGraph（Brendan Gregg 开源）**：Linux 内核级 Profiler，几乎零开销采样。最经典方案。
- **async-profiler**（JDK 11+ 友好）：基于 perf 的 JVM Profiler，能采样 Java 方法（而 perf 看的是 native 栈）。**Netflix / Uber 内部生产广泛使用**。
- **JFR（Java Flight Recorder）+ JDK Mission Control**：JDK 自带，开销 < 1%，可视化火焰图。
- **VTune（Intel）**：硬件级 Profiler，看 CPU 流水线、缓存命中率等微架构数据。

**分布式 / 持续 Profiling（2020+ 趋势）**：

- **Google Cloud Profiler**：持续 Profiling，低开销，能跨服务聚合。
- **Datadog Continuous Profiler**：商业 SaaS，支持 JVM / Python / Go / Node / .NET。
- **Polar Signals Cloud**：开源 + 商业，基于 eBPF + Parca 格式。
- **Pyroscope（开源）**：自托管持续 Profiling。
- **Uber's Arize / JVM Profiler**：Uber 内部基于 async-profiler 的持续 Profiling 系统，覆盖全公司 Java 服务。

**第四层：基于火焰图的瓶颈定位 SOP。**

**第一步：选对 Profiling 类型**。

- CPU 100% → CPU 火焰图。
- CPU 不高但 RT 高 → Off-CPU 火焰图（IO / 锁等待）。
- 内存增长快 → 内存火焰图（分配热点）。
- GC 频繁 → JFR + GC 日志。

**第二步：解读火焰图——三步找瓶颈**。

- **看"平顶"**：最宽的平顶函数就是 CPU 消耗最多的——这是直接优化目标。
- **看"长链"**：很深的调用栈意味着层级过多（如反射、动态代理、AOP）——考虑扁平化。
- **看"奇怪函数"**：出现 `park` / `wait` / `lock` / `read` / `write` 等 IO / 锁函数，就是 Off-CPU 瓶颈。
- **看"用户态 vs 内核态"**：用户态占比高 → 应用层逻辑瓶颈；内核态占比高 → 系统调用或网络 IO 瓶颈。

**第三步：定位 → 优化 → 量化**。

举例：某服务 P99 突然从 100ms 涨到 2s。

1. **生成 CPU 火焰图**：发现 JSON 序列化（`Jackson.writeValueAsString`）占比 70%。
2. **根因定位**：某次配置变更把序列化对象从 100 个字段扩到 5000 个字段。
3. **优化**：用 ProtoBuf 替代 JSON + 分页序列化。
4. **验证**：再次生成火焰图，序列化占比从 70% 降到 10%；P99 回到 120ms。

**第五层：生产实践的注意事项。**

- **采样频率**：99Hz 是甜蜜点（< 1% 开销）。生产可开到 999Hz 但要评估开销。
- **持续时长**：30 秒到 5 分钟，足够覆盖至少一个完整的业务周期。
- **进程选择**：高峰期采样才有意义；冷启动期采样看到的可能是预热开销。
- **安全考虑**：火焰图可能暴露内部函数名，符号需要脱敏（生产环境开启符号映射但限制访问）。
- **与 Trace 配合**：火焰图定位"哪个函数慢"，分布式 Trace 定位"哪一跳慢"——两者互补。

**3. 常见陷阱**

- **把火焰图当作万能工具。** 火焰图只能看 CPU / 部分 IO，**不能看 DB 慢查询、网络丢包、业务逻辑错误**——定位"系统慢"要先用 Trace + 日志 + 监控缩小范围，再用火焰图深挖。
- **忽略 Off-CPU。** CPU 火焰图看到 CPU 利用率不高但 RT 高，**一定是 Off-CPU 等待**——必须用 Off-CPU 火焰图。
- **生产环境不敢用 Profiling。** 担心开销可以理解，但**99Hz 的 perf 开销 < 1%**，完全可以生产开启。Uber 在生产环境默认开启持续 Profiling，是工业标杆。
- **生成火焰图不看上下文。** 只看火焰图不知道是哪个时间点、哪个业务场景——必须结合**时间窗 + 业务指标**一起分析。
- **优化后不复测。** 优化后必须再次生成火焰图验证——"看起来快了"不可信。

**4. 追问预测**

- **「火焰图显示某个函数 CPU 占用高，但代码里没有显式调用它——可能是什么？」** 答：常见原因——① 反射调用（`Method.invoke`）；② 字节码生成（CGLIB / Lambda）；③ GC 线程（`G1 Young GC`）；④ JIT 编译开销；⑤ 框架隐式调用（AOP / 拦截器）。需要展开火焰图的下层调用栈才能定位。
- **「Off-CPU 火焰图显示大量 `epoll_wait`，但 P99 很高，可能的原因？」** 答：可能是**线程池满了**——所有线程都在等任务（P99 高是因为任务排队）。需要看线程池队列深度 + 任务执行时长分布。
- **「JVM 应用的火焰图怎么生成才能看 Java 方法（而不是 native）？」** 答：用 `async-profiler`（而非纯 perf），例如 `./profiler.sh -e cpu -d 30 -f /tmp/flamegraph.html <pid>`，能正确显示 Java 栈帧。生产环境 async-profiler 开销 < 2%。
- **「如何做持续 Profiling（Continuous Profiling）？」** 答：用 Uber JVM Profiler、Pyroscope、Datadog Continuous Profiler 等工具，自动定期采样所有实例，火焰图聚合展示，能对比"昨天 vs 今天"——发现性能回归比手动快 100 倍。

### 8.4 通用答题心法

性能工程面试的**三层递进**：

1. **第一层（基础）**：能识别常见瓶颈类型——CPU / 内存 / IO / 数据库。
2. **第二层（中级）**：能针对瓶颈选择合适的工具与方法——火焰图 vs Trace、Redis vs JVM、G1 vs ZGC。
3. **第三层（高级）**：能基于业务 SLO 做**工程权衡**——吞吐 vs 延迟、一致性 vs 可用性、成本 vs 性能。

面试官真正想听的永远是**「你为什么这么选」**——而不是"调大堆、调小 GC、调高并发"。所有性能优化都是在**确定的 SLO 下做资源-体验-成本的平衡**，这是性能工程的核心哲学。
