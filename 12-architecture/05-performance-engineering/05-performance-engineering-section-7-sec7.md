## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把「性能测试 / 容量规划 / 性能工程 / AI 优化」放在同一张 1–5 分的表里比较。这个做法有两个结构性错误。

**错误一：这四件不是同一层的东西。** 性能测试是**测量**（不改变系统），容量规划是**配置供给**（不改代码，改机器数与规格），性能工程是**改机制**（改单请求的资源消耗），AI 优化是**针对特定工作负载的改机制**。给它们打分，等价于给「体温计 / 空调 / 手术 / 健身」打分——它们不是备选项，是可以同时使用、且必须按顺序使用的动作。

**错误二：同一维度的权重在不同规模下会反转。** 「成本降低」在 3 台机器的系统里权重接近 0（省下的钱少于优化的人力），在 1000 台机器或 100 张 GPU 的系统里权重接近全部。在只有 3 台机器时，正确答案是「什么都别做，先加 2 台」。

打分表输出的是**排名**，而选型需要的是「**在我的约束下，下一步做哪一件事，为什么不是另一件**」。更具体地说，本章要回答的是三个可被验证的问题：**(1) 这一步动作改的是成本函数里的哪一项？(2) 它在这个规模下值不值？(3) 它失效的条件是什么？** 一个不能回答「什么时候不适用」的选型建议，本质上还是打分表。

**本章采用的 6 条判据**（每条针对性能主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 改变的是哪一项 | 它改的是成本函数里的**乘法项**（单请求消耗），还是**加法项 / 系数**（机器数、冗余系数） | 乘法项的收益随规模放大，加法项的收益线性——这直接决定「先做哪个」 |
| 负载形态 | 峰值/均值比多大？是稳态还是脉冲？ | 资源成本按**峰值**配置、按**均值**使用；峰值/均值越高，买机器越亏 |
| 瓶颈位置 | 瓶颈在单请求固定开销（O(N) 扫描、N+1、无索引），在扇出尾延迟，还是在供给不足 | 位置决定手段：前两者只能用性能工程，第三才是容量规划的地盘 |
| 时间窗 | 是 3 天后大促，还是 6 个月后架构改造 | 时间窗决定**可用手段集合**——架构改动在短时间窗里是负收益 |
| 单位经济 | 每 QPS / 每 token / 每 GB 的资源成本是多少 | 这是唯一能和「优化的人力投入」放在同一张账上比较的量 |
| 尾延迟与 SLO | P99 / P999 是否写进了 SLO | 有强尾约束时，按平均容量做规划会**系统性不足** |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 性能测试（压测） | 测量：验证承载力 | 拉模型负载发生器打流 + 断言 SLO | JMeter、wrk、k6、Locust；大厂自研全链路压测 | 开源 / 商业（LoadRunner、阿里 PTS） |
| 可观测性 / APM | 测量：定位瓶颈 | 埋点 + 采样 + 聚合，把「慢在哪」变成可查 | OpenTelemetry、Jaeger、SkyWalking、Datadog | 开源规范 + 商业后端 |
| 容量规划 | 供给：配置资源 | 单机容量 × 副本数 × 冗余系数（Little's Law 反推） | 全部云上团队；Google SRE 的容量规划流程 | 方法论，无许可 |
| 弹性伸缩 / 大促保障 | 供给：按需供给 | 指标驱动的扩缩容 + 排队降级预案 | K8s HPA/KEDA、云弹性组；大促保障体系 | 云服务 / 自建 |
| 性能工程 · 应用层 | 改造：改单请求消耗 | Profiling 找热点 → 改算法 / 并发 / 缓存 | JVM 生态（G1/ZGC/Shenandoah）、协程 | 开源 |
| 性能工程 · 数据库层 | 改造：改访问路径 | 索引把 O(N) 变成 O(log N)；分片改变扩展维度 | PostgreSQL/MySQL 索引、ShardingSphere、Vitess | 开源 |
| 性能工程 · 网络/前端层 | 改造：改传输与距离 | 多路复用、0-RTT、边缘缓存、零拷贝 | CDN、HTTP/2-3、TLS 1.3、gRPC、sendfile/io_uring | 开源 + 云服务 |
| AI 优化 | 改造：改 GPU 单位产出 | 批处理 / 分页显存 / 量化，把显存带宽变成吞吐 | vLLM、TensorRT-LLM、ONNX Runtime、TensorRT | 开源 / 商业 |

这 8 项其实分**四族**：**测量族**（压测、可观测性）、**供给族**（容量规划、弹性/大促）、**改造族**（应用/DB/网络三线）、**AI 改造族**。同族内部差异小（都是「测」或都是「配」），跨族差异大（可测 vs 可改）。**先分族再选，能省掉一半比较**：你首先要在「测」「配」「改」里挑一个动作，而不是在 8 个工具里挑一个。

| 候选条目 | 归入本章哪一行 | 它在成本函数里动的是哪一项 |
| --- | --- | --- |
| 前端 → CDN + 资源优化 | 网络/前端层 | 单请求的网络传输量（乘法项） |
| 网络 → HTTP/2 + gRPC + TLS 1.3 | 网络/前端层 | 单请求的连接与握手开销（乘法项） |
| 应用 → JVM + 缓存 + 异步 | 应用层 | 单请求的 CPU 与等待时间（乘法项） |
| 数据库 → 索引 + SQL + 分库分表 | 数据库层 | 访问路径复杂度，或在超阈值后转为加法项（分片=加机器） |
| AI 推理 → 量化 + vLLM + KV Cache | AI 改造族 | 每 token 的 GPU 秒（乘法项） |
| 性能测试、性能工程、容量规划 | 测量 / 改造 / 供给族 | 分别对应「信息」「乘法项」「加法项」 |

一张对照表可以看出关键点：**原来那份清单里，只有「分库分表」是加法项（靠增加机器/分片换性能），其余全部是乘法项**。这不是偶然——分库分表之所以被放在最后、且门槛最高（见 7.7 迁移成本表），正是因为它是这张清单里唯一「不改善单位经济、只增加分布式复杂度」的手段。

**上表只列机制，不列「某产品是否支持某特性」**：性能工具与云服务的特性边界变化快，写死会产生过期断言。凡涉及具体能力，请用下面三种**判定方法**自行核验，而不是相信任何静态清单：

- **是否支持某项优化**：查该项目的 release note 与版本号（不写版本的特性描述一律视为不确定），例如能否在内核态做无侵入采样，取决于内核版本与 `perf` / eBPF 的可用性。
- **成本是否能被压到目标**：用自己的数据做 A/B（同一压测场景、同一数据规模，只改一个变量），而不是引用别人的倍数；别人报告的倍数（如论文里的吞吐倍数）只用来判断「值不值得试」。
- **是否会被自身成本反噬**：任何测量与缓存都会引入新的资源消耗（Trace 存储、缓存内存、批处理排队），必须为它设上限（采样率、保留期、最大批窗口），否则它从手段变成成本项。

### 7.3 机制差异：为什么它们表现不同（核心节）

四族之间的表现差异，可以完整归因到下面四个机制维度。选这四个而不是别的，是因为它们分别对应选型时必然要回答的四个问题：**改的是什么（7.3.1）· 在什么负载下成立（7.3.2）· 收益随规模怎么变（7.3.3）· 瓶颈的物理下限在哪（7.3.4）**。每个维度下面都给出「机制 → 因果 → 公开证据 → 失效条件 → 自验方法」，其中**自验方法**是可以立刻在你自己的系统上执行的判定动作。

#### 7.3.1 测 vs 改：你动的是「已知」还是「主导项」

**机制是什么**：测量不改变系统的任何一个系数，它只把「未知的瓶颈分布」变成「已知的瓶颈分布」；改造则是直接改变成本函数里的主导项。

**各候选的实现差异**：

| 候选 | 是否改变系统 | 改变的对象 | 收益的上限 |
| --- | --- | --- | --- |
| 压测 / APM | 否 | 只改变「你掌握的信息」 | 上限 = 你已知瓶颈的优化空间；未知的仍是未知 |
| 容量规划 | 否（改供给） | 机器数 / 规格 / 冗余系数 | 上限 = 单机效率不变时的线性扩张 |
| 性能工程 | 是 | 单请求资源消耗（乘法项） | 上限 = 算法与 IO 路径的物理下限 |
| AI 优化 | 是 | 每 token 的 GPU 秒（乘法项） | 上限 = 显存带宽与算力的物理下限 |

**由此必然导出的性质**：**因为**测量不改变任何系数，**所以**它单独使用时收益为 0——「测完了还是慢」是逻辑必然，不是执行不力；**又因为**瓶颈位置在优化前不可知，**所以**跳过测量的改造是**随机投资**：期望收益 = 改造收益 × 猜中概率，而绝大多数系统的主导项只有一个，猜错时收益接近 0。正确的顺序不是「哪个更好」，而是「**先测、再改、改不动才配**」。

**公开证据**：Linux 内核的 `perf` 与 eBPF/bpftrace——eBPF 自 Linux 3.18 引入、4.x 起在主流发行版可用于生产诊断，bpftrace 是其上的追踪前端——把「看不到的内核态开销」变成可归因数据【公开，Linux 内核版本历史与 bpftrace 项目文档，2014–2019】；JDK 侧的 JFR（JDK Flight Recorder，JDK 11 起随 OpenJDK 开源，JEP 328【公开，JEP 328，2018】）做了同样的事。这两个工具的公开定位一致：**先让开销可见，再谈优化**。

**失效条件**：当被测系统与生产系统的流量形态、数据分布、依赖延迟不一致时，测量结果会**给错方向**——压测环境里「数据库不是瓶颈」可能只是因为压测数据量小。此时测量的价值反转为负（优化了错误的目标）。

**自验方法**：在生产采样（带采样的 Trace / 连续 Profiler）与压测环境各取一份火焰图，比较**前三大热点的排序是否一致**。排序不一致，说明压测环境不可信，此时任何压测结论都不应直接转成采购单。

#### 7.3.2 稳态假设：Little's Law 什么时候失效

**机制是什么**：`并发数 = QPS × 平均响应时间`（Little's Law，J.D.C. Little，1961【公开】）是容量规划的全部数学基础——它把「需要多少机器」换算成「并发 × 单请求耗时」。但它成立的前提是**稳态**：到达过程平稳、系统不积压。

**各候选的实现差异**：

| 候选 | 假设的负载形态 | 对突发的处理 |
| --- | --- | --- |
| 容量规划 | 稳态 + 峰值可预测（大促有排期） | 按峰值配置，成本按峰值支付 |
| 弹性伸缩 | 负载变化的时间常数 > 扩容时间常数 | 扩容有分钟级延迟，秒级脉冲无效 |
| 性能工程 | 无假设（改的是单请求成本） | 对突发**自动生效**：单请求更便宜 ⇒ 同样资源扛更多突发 |
| AI 优化 | 假设请求可排队成批 | 批处理**放大吞吐但增加排队延迟** |

**由此必然导出的性质**：**因为** Little's Law 的输入是「平均响应时间」，**所以**在负载突变时它会低估需求——系统进入排队后，响应时间上升会**反过来推高所需并发**，形成正反馈（排队崩溃）；**因为**性能工程压缩的是单个请求的耗时，**所以**它同时降低 Little's Law 公式里的两个量（更少的并发 × 更短的时间），在突发下**无需预测就自动生效**。这就是「脉冲负载优先做性能工程、稳态负载优先做容量规划」的机制来源。

**公开证据**：[Netflix Tech Blog, *Performance Under Load*, 2018【公开】] 公开介绍过基于 Little's Law 推导的**自适应并发限制**——用「延迟随并发上升的拐点」动态求最大并发（而不是配置固定线程数）。可自行核验：该文给出的是**判据**（用梯度法在延迟曲线上找拐点）而非某个具体并发值，所以任何「Netflix 的并发数是 N」的说法都不来自它；它印证的是同一条机制：**并发上限不是配置项，是延迟曲线上算出来的量**。

**失效条件**：当并发上限由**下游**决定（如第三方 API 有独立限流）时，本侧的自适应并发只能保护自己，不能保护链路；此时必须改判据为「链路最长板」。

**自验方法**：画一张「并发数 → 吞吐 / 延迟」的曲线，看是否出现延迟上升但吞吐不再增长的拐点。有拐点说明存在排队，容量规划应补到拐点处而不是补到「CPU 看着快满」处；没有拐点说明瓶颈在别处，加机器无效。

#### 7.3.3 成本函数的形状：乘法项 vs 加法项

**机制是什么**：年资源成本可写成

```
资源成本 ≈ 峰值负载 × 单请求资源消耗 × 冗余系数 × 单位资源单价 × 8760h
```

**各候选的实现差异**（同一张成本函数上，各自动的是哪一项）：

| 候选 | 动的是哪一项 | 该项在公式里的位置 | 收益随规模的变化 | 是否改善单位经济 |
| --- | --- | --- | --- | --- |
| 性能测试 / 可观测性 | 不动任何一项，只把「未知的瓶颈」变成「已知」 | — | 无直接收益；它决定其余四项的**命中率** | 否 |
| 容量规划 | 机器数 / 冗余系数 | 加法项 / 系数 | 线性：机器翻倍，账单翻倍 | 否 |
| 弹性伸缩 | 计费时长的分布（常备 → 按需） | 时间权重（8760h 那一项） | 只削掉闲置时段的付费，峰值时段照旧 | 部分（不改变峰值下的单位成本） |
| 大促保障（排队 / 降级 / 异步化） | 峰值负载本身 | **乘数** | 削峰比例直接乘进全年账单 | 是 |
| 性能工程 | 单请求资源消耗（CPU、IO、访问路径） | **乘法项** | 与系统规模成正比 | 是 |
| AI 优化 | 每 token 的 GPU 秒（权重读取次数） | **乘法项** | 与卡数、请求量成正比 | 是 |

这张表可以一句话读完：**能改善单位经济的，只有动「乘法项 / 乘数」的手段**（性能工程、AI 优化、削峰）；测量只改变信息，容量规划只改变线性项的系数，弹性伸缩只改变**计费时长的分布**——它能削掉闲置时段的账单，削不掉峰值时段里「单请求消耗高」这个事实。而「冗余系数」虽然也在乘号后面，它换来的只是**可用性裕度**，不是单位经济的改善（见 7.4）。

**由此必然导出的性质**：**因为**「单请求资源消耗」是**乘数**，**所以**优化它的收益与系统规模成正比——同样一处 10% 的压缩，在 10 台机器上一年省下的钱不足以支付优化人力，在 1000 台机器上则是可观预算；**反过来**，**因为**容量规划动的是加法项，**所以**它的收益永远线性且**不能改善单位经济**：机器翻倍，单位 QPS 成本不变。这解释了一个常见现场现象：**一个只靠扩容活着的系统，其单位成本会随规模固化为常数，永远等不到「规模效应」**。

**公开证据**：Amdahl 定律（Amdahl, 1967【公开】）在串行部分上给出了同一形状的结论——总加速比被**未被优化的固定部分**封顶。可对照的工业信号是 JVM 生态的 GC 演进：G1 自 JDK 9 起成为默认收集器（JEP 248, 2017【公开】），ZGC 与 Shenandoah 于 JDK 15 转为生产可用（JEP 377 / JEP 379, 2020【公开】）。这两代收集器服务的是同一个目标——**降低「停顿」这个与堆大小同向增长的加法项的斜率**，而不是去减少应用本身的分配量（那属于应用层的乘法项）。

**失效条件**：当优化空间已被榨干（算法已是 O(1)、IO 已批量、缓存命中率高），乘法项的边际收益趋零，此时唯一剩下的手段就是供给——**不是性能工程不好，是它已经被用完了**。判断方法：火焰图里再也找不出**非必要热点**，且剩余热点都是个位数百分比（多数团队把「值得动手」的门槛定在 **5%–10% 量级**【经验】），就是榨干的信号。这条门槛是经验值而非物理下限：它随「你的人力单价 / 机器单价」变化——优化人力越贵，值得动手的占比门槛越高。

**自验方法**：把「火焰图里前三大热点的占比之和」写成周报指标。该值长期落在 **20% 量级或更低**（经验阈值，常见取值区间 **15%–30%**【经验】），说明乘法项已无肉可割，继续投入性能工程的人力应该转向供给与稳定性；若长期在 **50% 量级之上**（常见取值区间 **40%–60%**【经验】），说明还有一处主导项没被处理。用区间而非精确值是刻意的：这条线的位置取决于火焰图的采样深度（是否含内核态、是否有未打点的第三方调用），同一系统换采样配置就会挪动几个百分点。

#### 7.3.4 算术强度：为什么 AI 推理不能照搬 JVM 调优

**机制是什么**：一个负载是**算力受限**还是**显存带宽受限**，由它的**算术强度**（每读 1 字节数据能做多少次运算）决定。CPU 上的 Web 服务通常 IO/锁受限（等 DB、等下游）；LLM 的**解码阶段**每生成一个 token 都要把全部权重读一遍，运算量却很小——是典型的**显存带宽受限**。

**各候选的实现差异**：

| 负载 | 主导资源 | 有效手段 | 无效手段 |
| --- | --- | --- | --- |
| Web / 在线事务 | DB IO、锁、连接池 | 索引、连接池、异步化、本地缓存 | 加 CPU 线程（IO 等待时无用） |
| JVM 高吞吐服务 | CPU、GC 停顿 | G1/ZGC、对象分配率、逃逸分析 | 加大堆（可能延长 GC 停顿） |
| LLM 解码 | 显存带宽 | 连续批处理、PagedAttention、量化 | 加推理线程（权重读取量不变） |
| LLM 预填充 / 宽 batch | 算力 | 算子融合、并行、编译优化 | 只做量化（可能反而损失精度与吞吐） |

**由此必然导出的性质**：**因为**解码阶段受限的是「权重读取次数」而不是「运算次数」，**所以**把多个请求拼进一个 batch（连续批处理）能让同一份权重服务于更多 token，吞吐必然上升——这与「多开线程」完全不是一回事，后者不减少权重读取；**因为** KV Cache 占用显存且大小极不规整，**所以**不解决显存碎片就抬不高 batch 上限，吞吐提升会被显存卡住（这正是 PagedAttention 的动机）。

**公开证据**：vLLM 论文（*Efficient Memory Management for Large Language Model Serving with PagedAttention*，SOSP 2023）报告在相同硬件下吞吐相对当时 SOTA 系统的公开结果约 **2–4 倍**【公开，论文摘要，2023】。注意这是**论文在其测试条件（模型、序列长度分布、硬件）下的结果**，不是可无条件移植的系数；可自行核验的方法是：在你的模型与序列长度分布下测「不同 batch 上限的 token/s 曲线」。

**失效条件**：当序列非常长、显存被 KV Cache 占满时，batch 上限降到 1，「批处理红利」消失，此时必须先做显存优化（PagedAttention、量化、前缀缓存）才能再谈吞吐；当负载是**延迟敏感的单用户对话**且 batch 上不去时，连续批处理基本无效。

**自验方法**：固定模型与输入长度分布，测「batch 上限 → token/s → 显存占用」三条曲线。若 token/s 随 batch 上升、显存同时逼近上限，瓶颈是显存管理；若显存有余量而 token/s 平了，瓶颈已转到算力或调度，此时该动的是算子与并行，不是继续加 batch。

### 7.4 成本结构对比（不是价格表，是成本函数）

四个候选的成本**随什么变量增长**：

```
性能测试   ≈ 压测环境成本(固定) + f(压测频次 × 流量规模) + 人力(固定)
容量规划   ≈ 峰值负载 × 单请求消耗 × 冗余系数 × 单价 × 8760h   ← 线性、加法项
性能工程   ≈ 人力(一次性) + 长期维护复杂度(隐性)
AI 优化    ≈ GPU 数 × 卡时单价 × 8760h / 吞吐提升倍数
```

**主导项与隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| 性能测试 | 压测环境的**真实度**（数据量、依赖延迟） | 环境维护 + 每次变更都要重跑；环境失真会导致优化错方向 |
| 容量规划 | 峰值 × 冗余系数 | **过度配置**：冗余是为了兜底，但会固化成常态账单 |
| 性能工程 | 人力 + 对可读性的侵蚀 | 优化引入的复杂度（缓存一致性、手写并发、零拷贝接口）需要**长期**维护 |
| AI 优化 | GPU 小时数 | 批处理引入的**排队延迟**与显存管理复杂度；量化带来的精度回归风险 |

**为什么把「隐性成本」单列**：显性成本（机器、卡时）在账单上可见，于是被高估；隐性成本（维护复杂度、压测环境维护、精度回归、排队延迟）不出现在账单上，于是被系统性低估。两者的相对量级随规模反转——**因为**显性成本随规模线性增长，**而**复杂度成本大致与规模无关（它是「多了一条需要人理解的通路」这种常数级负担），**所以**小系统上复杂度成本占主导、大系统上显性成本占主导。这正是 7.5 里「小系统先测与配、大系统才值得改」的量化来源。

**冗余系数这一项还能和优化「等价兑换」**：把冗余系数从 2.0 降到 1.5，在成本公式里等同于把单请求消耗压掉 25%（两者都是乘数）。但两者的性质完全相反——降冗余**不改善单位经济，且直接消耗可用性裕度**；降单请求消耗是**净收益**。所以当有人提出「我们冗余配太多了，砍一半就能省一大笔」时，正确的对照不是「能省多少」，而是「这 50% 的裕度和一次 10% 的性能优化，哪个该先做」——答案通常在乘法项那边。

**【推算】数量级示例**（推导链完整给出，便于读者换参数重算）：

- 100 台 8C16G 常驻：按公开的通用型实例按需价 **$0.3–0.5/h 量级**（AWS / GCP 公开定价页，2024）【公开】→ 年资源支出 ≈ 100 × $0.4 × 8760 ≈ **$350k/年**【推算】。
- 若性能工程把单请求消耗压 10% → 年省 = $350k × 10% ≈ **$35k**【推算】；优化投入 2 人月（内部全成本按 $15k/人月量级【经验】）≈ **$30k** → 回本期 = 投入 ÷ 年省 = $30k ÷ $35k/年 ≈ 0.86 年 ≈ **约 10 个月**【推算】。
- 因此得到一条可用的门槛：**当年资源账单在 $300k 量级（约 100 台 8C16G）以下时，10% 级别的优化很难在一年内回本**——这条门槛由同一推导给出：账单降到 $300k 时年省 = $300k × 10% = $30k，恰好等于 $30k 投入，回本期正好 12 个月；账单继续下降则回本期线性拉长。此时优先做的是「定位 + 便宜的旋钮」，而不是系统改造【推算】。
- 存储侧的对照（**前提：对象平均大小远大于 128 KB**，Glacier Instant Retrieval 有 **128 KB 最小计费对象尺寸**，若冷数据由大量小日志/小分片构成，实际费用会高于下式，差额量级另算【公开，AWS S3 定价页 2024】）：10 TB 冷数据放 S3 标准层（$0.023/GB-月，AWS 公开定价页 2024【公开】）→ 10 240 GB × $0.023 × 12 ≈ **$2.8k/年**；换 Glacier Instant Retrieval（$0.004/GB-月）→ 10 240 GB × $0.004 × 12 ≈ **$0.5k/年**，即一年省下约 **$2.3k**【推算】，与上面 100 台机器的 $350k 账单相差两个数量级。**说明本地磁盘/冷热分层这类改动的钱在存储上是零头，真正的账单在计算**——这决定了性能工程的优先舞台是 CPU/GPU，不是存储。
- GPU 侧：单张 A100 级加速卡按需 $3–5/h 量级（云厂商公开定价页，2024）【公开】→ 1 张卡常驻约 **$26k–44k/年**【推算】。LLM 服务的账单几乎全是「卡数 × 卡时」，因此**吞吐提升 N 倍 ≈ 单位 token 成本降 N 倍**——这是整章里「性能直接等于钱」最干净的一处换算，也是 AI 优化值得单独成族的原因。

**主导项随场景切换，所以优先级不是固定的**：

| 你的场景 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| 100 台以下、无强 SLO | 人力（优化投入 > 省下的机器钱） | 测量 + 便宜的旋钮（超时、连接池、索引） |
| 千台以上、稳态流量 | 峰值 × 单请求消耗 | 性能工程（改乘法项），之后才补容量 |
| LLM 在线服务 | GPU 卡时（几乎占满账单） | AI 优化（吞吐倍数直接换成钱） |
| 大促型业务 | 峰值 × 冗余系数（按峰值付费） | 排队 / 降级 / 弹性（削峰），而不是扩容 |
| 固定时间窗的批处理 | 作业时限 × 机器数 | 并行度与 shuffle / IO 路径（时限不可延长） |

### 7.5 决策树（每个分支都要有阈值依据）

```
你现在的处境？
├─ 还不知道慢在哪
│    → 测量（可观测性 + 火焰图 + 链路追踪）。任何改造之前先做这件事
│      （瓶颈未知时，改造的期望收益 = 收益 × 猜中概率）
├─ 瓶颈已定位，且是「单请求固定开销」（O(N) 扫描 / N+1 查询 / 无索引 / 重复序列化）
│    → 性能工程（改机制）。乘法项，规模越大越值
├─ 瓶颈是「资源不够」，且负载稳态、峰值/均值 < 2
│    → 容量规划（加机器 / 提规格）。加法项，最快见效，但不改善单位成本
├─ 峰值/均值落在 2–3（大量在线业务的常见区间，判据不明确的地带）
│    → 先做便宜的旋钮 + 一次削峰试验（队列 / 限流 / 异步化 / 排期错峰）
│      用试验后的新峰值与均值重新判一次：新比值 < 2 才扩容
├─ 峰值/均值 > 3（大促、脉冲、批量重跑窗口）
│    → 不买机器：成本按峰值付、按均值用 → 先做排队 / 降级 / 异步化 + 弹性
├─ 有强尾延迟约束（P99/P999 进 SLO）
│    → 性能工程优先于容量规划（按 P99 配置会按最坏情况付费）
├─ AI 推理链路
│    ├─ 解码阶段、显存带宽打满 → 批处理 / PagedAttention / 量化
│    └─ 预填充或宽 batch、算力打满 → 算子融合 / 并行 / 编译优化
└─ 只有 3 天时间窗
     → 只动「可回滚的旋钮」：连接池上限、超时、缓存 TTL、实例规格、索引
       （不做架构改动：无验证的架构改动回归风险高于收益）
```

**阈值依据**：

- **峰值/均值 = 2 与 3，以及两者之间怎么判**：由成本函数推出。资源按峰值配置、按均值使用，闲置率 = 1 − 均值/峰值 = 1 − 1/(峰值/均值)；峰值/均值 = 2 时有一半的钱闲置，= 3 时有 2/3 闲置。**2 与 3 不是两条判据，是同一条判据的两个刻度**：闲置率随峰值/均值单调上升（每 +0.5 约 +8 个百分点），因此区间内**按线性外推比较边际成本**——削峰的边际成本是几天人力加可控的排队延迟（一次性、可回滚），扩容的边际成本是整年按峰值付费（固化进账单）。两者等值时落在中间地带，而「削峰试验」的信息价值（做完后你会知道真实的稳态底座是多少）使它在 2–3 内仍然优先；只有在削峰后新比值仍 < 2、且底座本身已经贴着容量上限时，扩容才是净收益【推算】。
- **$300k/年、100 台 8C16G**：由 7.4 的回本推算给出，不是行业常数；换成你自己的单价与人力成本重算即可，公式已给出【推算】。
- **P99 优先于均值**：扇出场景下，若每个并行子请求有概率 p 变慢，则一个请求遇到至少一个慢分支的概率是 `1-(1-p)^n`。取 p = 1%、n = 100（常见的一次查询扇出上百个分片）→ 约 **63%** 的用户请求会撞上慢分支【推算，模型出自 Dean & Barroso, *The Tail at Scale*, CACM 2013【公开】】。结论：**尾延迟不是长尾，在扇出下它就是常态**，所以不能按平均值做容量规划。
- **3 天时间窗**：短窗内可安全执行的只有配置级、可回滚的旋钮；架构改造需要重新压测与灰度，缺少这两者时引入的回归风险通常大于收益【经验】。

**把决策树展开成执行顺序**（同一棵树，按时间轴读）：

1. **第 1 周 · 只做测量**：接链路追踪 + 连续 Profiler，产出「前三大热点占比」与「P99 的分布形状」（是长尾还是整体右移）。此周**不许改代码**——避免用一次碰巧的改动覆盖掉诊断信息。
2. **第 2 周 · 只动旋钮**：连接池上限、超时、重试退避、缓存 TTL、慢查询索引。这些是**可回滚且互相独立**的，能在一周内排除掉大量「配置型慢」。
3. **第 3–6 周 · 改乘法项**：针对剩下的主导项做改造（算法、IO 批量、批处理、显存管理），每改一项都在压测环境复现「改前 / 改后 / 回退」三组数据。
4. **之后 · 补供给**：乘法项榨干后才配容量，并**重算容量模型**（因为单请求消耗已经变了，旧模型作废）。
5. **持续 · 设回归门禁**：把 P99 与单位成本写进 CI 断言，否则以上四步会在三个月内被下一次功能发版悄悄抹平。

> 这条顺序的机制依据是：**测量 → 配置 → 改造 → 供给** 的每一步都建立在前一步的输出上；跳过第一步的改造是随机投资，跳过第三步的供给是线性烧钱。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单库查询慢且已定位到无索引 | 性能工程（索引 + SQL 改写） | 读写分离 | 直接分库分表：把 O(log N) 的问题升级成分布式事务问题 |
| 稳态流量、资源确实不够 | 容量规划 | 提高单机效率 | 只扩容：成本按峰值付，且会掩盖 O(N) 热点，越扩越贵 |
| 大促 / 脉冲流量 | 异步化 + 排队 + 降级 + 弹性（大促保障） | 容量规划 | 按峰值常备机器：成本 = 峰值 × 全年 |
| LLM 在线服务吞吐不足 | AI 优化（批处理 + 分页显存 + 量化） | 加卡 | 只加卡：单位 token 成本不变，账单与吞吐同比例涨 |
| 线上「莫名其妙变慢」 | 可观测性 / APM（测量） | 临时加机器止血 | 靠猜加机器：钱花了，且不知道是否真的解决 |

**常见组合与其运维代价**：

1. **可观测性（眼睛）+ 性能工程（手）**：可观测性负责给出主导项，性能工程负责改主导项。边界是**可观测性不做决策、性能工程不做埋点**。运维代价：Trace 存储成本随采样率与保留期线性增长，必须显式设上限（采样率 + 保留天数），否则监控自己会变成成本项。
2. **性能工程 + 容量规划**：先改乘法项，再按新的单位消耗配机器；顺序颠倒会导致容量模型被优化结果作废、二次采购。代价：每次优化后**必须重算容量模型**，否则出现过度配置。
3. **性能工程 + 大促保障**：大促前只执行「已在压测环境演练过」的优化，新架构改动冻结。代价：需要能复现生产流量形态的压测环境（这是压测环境真实度的直接成本）。
4. **AI 优化 + 容量规划**：批处理把吞吐抬上去后，容量规划的对象从「卡数」变成「批窗口下的卡数」。代价：批处理**必然引入排队延迟**，与尾延迟 SLO 冲突——组合使用时必须**同时定义最大排队等待**，否则 P99 会被批窗口吞掉。
5. **可观测性 + 弹性伸缩**：用 SLO 指标（而不是 CPU 利用率）驱动扩缩容，才能避免「CPU 不高但请求已经排队」的漏扩容。代价：SLO 指标的计算链路本身必须高可用——扩缩容依赖的指标做得不好，会变成新的单点。

**组合的共同原则**：先做测量族（拿到主导项）→ 在改造族里改乘法项 → 最后用供给族补齐剩下的裕度，并**在每一层都设一条「如果它失效，谁接住」的回退**（性能优化的回退是新旧路线的灰度开关，扩容的回退是缩容，降级的回退是恢复）。没有回退设计的组合，在第一次异常时会同时失去效能与可用性。

### 7.7 选错的代价与迁移成本

**反模式：用压测代替性能工程** —— 每次大促前的压测结论都是「再扩两台就够」，连续三年如此 → 单位 QPS 成本固化不变，规模越大账单越线性上涨，且没有一次真正的能力提升 → **正确做法**：压测只负责给出「瓶颈在谁身上」，把结论接到性能工程（改主导项）而不是采购单上。

**反模式：只优化平均值** —— 监控大盘上 P50 与均值都很漂亮，用户投诉「偶尔很慢」；一次查询扇出上百个分片，1% 的慢分片让约 63% 的请求**至少撞上一个慢分片**【推算，见 7.5】→ 平均值掩盖了尾部的结构性放大 → **正确做法**：把 P99/P999 写进 SLO，按尾延迟而非均值做优化目标与容量规划。

**反模式：先加缓存再找瓶颈** —— 上线本地缓存后 QPS 上升、延迟下降，半年后一致性问题与「改了数据不生效」的工单持续出现；而根因其实是一次 O(N) 的全量扫描 → 缓存掩盖了算法问题，并**把成本从延迟转移到了正确性** → **正确做法**：先用火焰图证明瓶颈是「重复计算 / 重复 IO」，再加缓存，并为每个缓存显式定义失效策略与 TTL。

**反模式：AI 推理照搬 Web 调优** —— 看到 GPU 利用率低就加并发线程/进程，token/s 几乎不变，显存反而先爆掉 → 因为解码阶段是**显存带宽受限**，加并发不减少权重读取量 → **正确做法**：先判断算术强度，带宽受限走批处理与显存管理，算力受限才走算子与并行。

**反模式：把优化做成一次性项目（没有回归门禁）** —— 一次成功的优化上线后没人量，三周后某次例行发版把批处理改成了逐条处理、或把缓存 TTL 改回默认值，延迟悄悄退化回原样 → 因为性能是**无主指标**，没有门禁就必然被下一次功能变更顺手破坏 → **正确做法**：把关键路径的 P99 与单位成本写进 CI 的性能回归断言（同一压测场景、同一数据规模，超过基线一定比例即失败），并指定该指标的责任人。

**反模式的代价量级**（沿用 7.4 的公式估，不引入外部系数）：

| 反模式 | 代价的量级 | 推导依据 |
| --- | --- | --- |
| 用压测代替性能工程 | 单位资源成本三年不变；规模翻倍则账单翻倍 | 成本公式里被改动的只有加法项，乘法项未动【推算】 |
| 只优化平均值 | 「1% 的慢」在 100 路扇出下影响约 **63%** 的请求 | `1-(1-p)^n`，p=1%、n=100【推算】 |
| 先加缓存再找瓶颈 | 延迟改善换来的是**一致性成本**（工单与数据订正） | 成本从延迟项转移到正确性项，且后者更难度量【经验】 |
| AI 推理照搬 Web 调优 | 显存先打满、token/s 几乎不变 | 解码阶段受限的是权重读取次数，加并发不改变它【公开：算术强度（operational intensity）出自 Roofline 模型（Williams, Waterman & Patterson, CACM 2009）；解码阶段的显存带宽受限见 vLLM 论文（SOSP 2023）】 |
| 优化无回归门禁 | 一次顺手的功能发版即可清零 3–6 周的人力投入 | 性能不是功能验收项，默认无人守【经验】 |

**换成另一条路线要动什么**：

| 迁移方向 | 数据迁移 | 代码 / 查询改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 从「只扩容」转向「性能工程」 | 无 | 少量（优化点本身） | 无 | 火焰图、perf/eBPF、JFR、SLO 方法 | 1–2 人月 |
| 从单库转向分库分表 | 大（需双写与对账校验） | 大（分片键设计 + SQL 改写 + 事务模型） | 中间件运维 | 分布式事务、分片规则 | 6–18 人月 |
| 从自建推理服务转向 vLLM 类引擎 | 无（权重可复用） | 中（接口适配 + 采样参数对齐） | GPU 资源调度与显存监控 | PagedAttention、批处理调度、前缀缓存 | 1–3 人月 |
| 从「无监控」转向性能工程体系 | 无 | 中（埋点改造） | Trace 采集与存储 | 火焰图、采样策略、SLO 定义 | 3–6 人月 |
| 从「平均值 SLO」转向「尾延迟 SLO」 | 无 | 少量（断言口径改写） | 需要能保留分位数的指标后端 | 分位数聚合的正确性（跨实例合并） | 1–2 人月 |

> 量级按「一个熟悉本系统的 3–5 人小组」估算【经验】；分库分表之所以是量级最高的迁移，是因为它动的是**数据布局**这种最难回滚的东西。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 不知道慢在哪 | 先测量，别优化 | 瓶颈未知时改造的期望收益 = 收益 × 猜中概率 |
| 稳态、资源不足、无技术债 | 容量规划 | 加法项，最快见效，且无需改代码 |
| 脉冲流量 / 大促 | 排队 + 降级 + 异步化，之后才是扩容 | 成本按峰值付、按均值用，扩机器最不划算 |
| 热点是 O(N) / N+1 / 重复 IO | 性能工程（改乘法项） | 乘法项收益随规模放大，改一次永久生效 |
| 有强 P99 SLO | 性能工程优先，容量规划按尾延迟配 | 扇出下 `1-(1-p)^n` 让慢分支成为常态 |
| LLM 服务吞吐不足 | AI 优化（批处理 / 分页显存 / 量化） | 解码阶段带宽受限，批处理减少权重读取次数 |
| 3 天内要见效 | 只动可回滚的配置旋钮 | 无验证的架构改动，回归风险大于收益 |
| 峰值/均值 > 3 且 SLO 已定 | 削峰（排队 + 降级）优先于扩容 | 冗余与峰值按同一乘数进入账单，削峰直接削减乘数 |
| 优化空间看起来已榨干 | 转供给与稳定性，别再投性能人力 | 火焰图里只剩 5%–10% 量级的非必要热点时，乘法项边际收益趋零【经验】 |
| 任何一条路线落地后 | 立刻补回归门禁与指标责任人 | 性能是无主指标，无人守就必被下一次发版抹平 |

> 本节小结：本章四类手段之间**唯一真正起决定作用的差异**是——**你动的是成本函数里的乘法项，还是加法项**。测量只改变信息，容量规划只改变系数，两者都不改善单位经济；性能工程与 AI 优化改变的是「每请求 / 每 token 的资源消耗」，它是**乘数**，所以它的收益随规模放大、且对突发自动生效。选型顺序因此不是「哪个分数高」，而是：**先测（把未知变已知）→ 再改（把乘法项压小）→ 改不动才配（把加法项补齐）**；跳过中间一步的系统，会在账单上以线性速度付出代价。
>
> 💡 **思考锚点**：把你链路的扇出数 n 与单分支慢比例 p 带进 7.7 的 `1-(1-p)^n`——若 p = 1%、n = 50，有多少比例的请求至少撞上一个慢分片？这个数远大于 1% 时，你现在的 SLO 是写在平均值上，还是写在这种尾部放大后的 P99 上？
