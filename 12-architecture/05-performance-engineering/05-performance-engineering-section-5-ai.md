## 5. 前沿演进（AI 时代）

> 原 § 5 共 85 行、为方向清单（5 个演进方向共 18 条条目 + 1 张 RAG 组件优化表 + 8 条学术/工业进展 + 5 条趋势），缺少机制与成熟度判断，重写为 ~300 行前沿评估。

### 5.1 先分清三类「前沿」

性能工程是本主题里唯一一个「AI 既是手段又是对象」的地方：既有「用 AI 优化性能」（AI 读 trace 找瓶颈、自动调参），也有「优化 AI 的性能」（推理吞吐、RAG 链路、向量检索）。这两件事在趋势清单里被并列成同一种东西，后果是读者把「已 GA 且有人在生产用」与「厂商演示里跑过一次」排进同一条路线图。**本节要解的第一个问题不是「AI 能带来哪些优化」，而是时间刻度**：同一条条目，今天能进方案还是只能记录，差别比它看起来有多大重要得多。

本主题还有两处独有的困难，直接决定判据怎么用。**第一，性能是本主题里唯一「数字可以自己造」的领域**——硬件、模型、数据都在你手里，同一份压测脚本改一个变量就能跑 A/B；这让性能证据比别处便宜，但也意味着**公开的性能数字与你的环境之间没有可移植性**（见 §5.4）。**第二，性能的收益以「单位成本」显形**（本章 [§7.3.3](05-performance-engineering-section-7-sec7.md) 把单请求资源消耗写成成本函数里的乘法项），所以「某方向值不值得做」最终要落到「它动的是不是乘法项」，而不是「它听起来先不先进」。主文件 [§1.2](05-performance-engineering.md) 已把 AI 时代的痛点写成「GPU 显存带宽、模型并行、推理引擎」——注意这三项全是**资源与硬件层**的词，而不是「模型更聪明」，这条线索贯穿本节。

本节用 L1 / L2 / L3 三级区分，判据必须是可核验的三条：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条各挡住一类误判：①挡住"把路线图与预览特性当既成事实"，②挡住"把引擎作者或采购方自己的数字当行业现状"，③挡住"把一次演示当工程"。**三条全中才算 L1**，可以排进路线图；只满足一部分、或只有厂商自有案例的算 **L2**，可做 PoC、不要作为核心依赖；只有路线图 / 论文 / 演示的算 **L3**，记录即可、不要在架构里预留假设。"感觉成熟"不算判据——它在评审会上无法被复核。

**判据声明（本节不对 L1 判据做任何修正）**：上文那三级与三条判据沿用到底，不替换、不放宽。本主题有一处特别诱人放宽的地方，先把话说死：性能领域的公开材料绝大多数**出自引擎作者或提供方自己**，而它们的形态恰恰是「在某个模型、某种序列长度分布、某种硬件上的一个倍数」。规范明确禁止把这类无条件的性能声称当作技术事实（§2.2），所以它们**不构成第②条**。于是**下表没有任何一行达到 L1**——包括那几行「非 AI 的既有能力」；它们满足 ① 与 ③，卡住的都是 ②。这是本表最重要的一句话：**它说明的不是"这些方向不好"，而是"公开证据到不了 L1"**。第②条在本主题有一个特殊之处：**它的缺口可以被部分回填**（自己造一份带条件的对照证据，见 §5.4），但**回填不等于满足第②条**——自造的记录既不是第三方、也不是公开生产案例，因此不参与本节评级。

写这一节时最容易混的四件事，先在这里分开：

- **产品名 vs 能力名**：原清单里的「vLLM / TensorRT-LLM / ONNX Runtime / SGLang」是**引擎产品名**，对应的能力名是「连续批处理」「分页 KV 管理」「前缀缓存」。凡看到"某引擎更快"，先问它在能力名上多提供了什么：多一个调度策略？还是多一层显存管理？两者调优方式完全不同。
- **已发布版本 vs 路线图**：判断某能力是否可用只看一处——**该版本的 release note 或官方文档里有没有对应条目，且标的是正式功能而不是预览**；项目官网的路线图页、benchmark 博客、生态伙伴的转述都不算（§5.4 给了本主题的核验入口）。
- **单机 / 多机**：模型并行、张量并行、流水并行是**多卡**话题，与"单个实例内的批处理"不是一回事；判断某个特性是否真的支持多机，看它的官方文档里有没有独立的多机执行组件与配置项，而不是看博客里的吞吐曲线。
- **论文里的原型 vs 产品里的实现**：本方向大量提法（自动调参、自动 SQL 重写、AI 定位瓶颈）在论文与开源原型里都能找到，但**开箱可用是另一回事**。判定方法：看官方文档里该能力有没有"配置项 / 配额 / 计费"三项中的至少两项——只有一段演示的还不是产品化条目。

**还有一处归类错误要先堵住**：本主题的"AI"同时是手段和对象，很容易把「优化 AI 的性能」（§5.2.1、§5.2.2）与「用 AI 优化性能」（§5.2.3、§5.2.4）混成一类。两者的证据结构完全不同：前者的收益**可以脱离模型能力来论证**（它动的是显存与搬运量，用公式就能推出拐点），后者的收益**完全依赖"模型能读到你打点出来的东西"**。归类一混，就会出现"我们上了 AI 优化，为什么没变快"——上的那个 AI 属于后者，而瓶颈在前者。本节因此把四个核心方向按机制分成"改成本函数形状"、"改负载形态与关键路径"、"改判断依据"三类（§5.2 开头的分类表），而不是按"是否用到 AI"分。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次"单位成本下降"，都对应一处新的失效形态。

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 推理服务 | 成本函数的主导项从算力换成显存带宽与显存容量 | **成本函数的形状**（不是多了几个旋钮） |
| §5.2.2 缓存与并行 | 缓存键从"整条请求"缩到"token 前缀"；链路优化从"单点提速"换成"改依赖结构" | **负载形态与关键路径** |
| §5.2.3 AI 辅助性能分析 | 瓶颈定位从人工读图换成模型读数据排序 | **判断依据**（结论性质没变） |
| §5.2.4 Self-Tuning | 参数调整从人定阈值换成按统计信息的确定性动作 | **判断依据 + 责任位置**（AI 只贡献建议） |

读法建议（四条，按可执行性排序）：

- 只读一节的话读 **§5.2.1**——它是唯一一条**成本函数形状发生变化**的方向，也是唯一能从机制直接推出"容量单位该换成什么"的方向；它的收益不依赖任何模型能力。
- **§5.2.2** 排第二，因为它的收益要等你量清负载性质（共享前缀占比、重复提问比例）之后才兑现；没量之前，缓存与并行都只是"看起来该做"。
- **§5.2.4** 排第三：它的前半（确定性自动化）今天可做，但必须同时定下"上限"与"关掉窗口"，否则它会吸收掉性能回归的信号。
- **§5.2.3** 放最后：它的产出是假设而不是结论，且天花板由埋点字段决定——埋点没补之前做它，成本与收益不成比例。

每条末尾的「证据与来源」采用同一套档位：【公开】指有可核验的出处（论文 / 官方文档 / 公开材料），【推算】指能写出推导链的换算，【经验】指区间估计。**本节不给版本号**：凡涉及"某引擎支持某特性"的地方，一律改写成判定入口（查哪一版 release note 或哪份官方文档）。

#### 5.2.1 推理服务：变化的是成本函数的主导项，不是「多了几个旋钮」

- **旧做法与它的卡点**：既有的性能工程抓手是为 CPU / IO 受限的负载设计的——火焰图、连接池、索引、JIT（主文件 [§2.3](05-performance-engineering.md) 第 1-6 条）。照搬到推理服务会得到两个错误结论：其一，**看到 GPU 利用率高就以为没有瓶颈**（本章 [§7.3.4](05-performance-engineering-section-7-sec7.md) 已写明解码阶段是显存带宽受限，高利用率可能正是在等显存）；其二，**用固定输入长度压测出一个与实际无关的吞吐**（真实负载的输入输出长度是分布，不是常量）。卡点不在手段不够强，而在**压测口径与瓶颈判定口径对不上**：你测的数不是决定成本的那个数。
- **AI 改变了什么机制**：**成本函数的主导项换了**。解码一步要搬的字节数 ≈ 权重字节数（与 batch 无关）+ KV 字节数（与 batch × 上下文长度成正比）。所以吞吐的杠杆是**让同一份权重服务更多 token**（连续批处理），而 batch 能开多大由**显存碎片**决定（分页 KV 管理）。这是"每 token 成本的构成变了"——而不是"可调参数变多了"；判据很清楚：**加线程不改变权重搬运量，加 batch 才改变每 token 的权重搬运量**（[§7.3.4](05-performance-engineering-section-7-sec7.md) 的同一结论）。

```text
一次解码步要搬的字节数（决定每 token 成本的那一项）
  权重读取        ≈ 参数字节数                        ← 与 batch 无关
  KV 读取/写入    ≈ 2 × 层数 × KV头数 × 头维度
                    × 上下文长度 × batch × 每元素字节数  ← 与 batch 成正比
  ────────────────────────────────────────────────────────────
  拐点：KV 字节数 ≈ 权重字节数 的那一档 batch
  → 在此之下，加大 batch 近似"免费"（同一份权重服务更多 token）
  → 在此之上，收益被 KV 搬运与显存容量吃掉
  注：KV 头数由 GQA / MQA 决定，可远小于注意力头数；
      本节不给具体量级——它随层数、KV 头数、精度而变，请按你的模型代入。
```

- **由此得到的**：因为**权重搬运量可被 batch 摊薄、KV 搬运量不可**，所以"加大 batch 提高吞吐"这件事有一个**可以用公式先估出来的拐点**，而这个拐点由上下文长度分布决定——这解释了为什么**长上下文服务与短问答服务的最优配置完全不同**：前者先撞 KV 与显存容量，后者先撞权重带宽。同一句因果换到容量侧：因为每实例能承载的并发由显存预算与上下文长度分布共同决定，所以**推导容量时用 QPS 会把资源买错**——该被容量规划当作单位的，是显存预算与序列长度分布（见 §5.3 第 2 行）。
- **把拐点写成一条可操作的推论**（不需要任何具体数字）：设权重为 W 字节、每 token 的 KV 为 k 字节，则 batch B、上下文长度 L 时 KV 总量 = B × L × k；拐点满足 W ≈ B × L × k，即 **B\* ≈ W / (L × k)**。**由此得到一条与硬件无关的结论：上下文长度翻倍，最优 batch 上限减半**；同理，把 KV 头数减少（GQA / MQA 这类结构改动）会等比例抬高点，而加长上下文会等比例压低它【推算，推导链即上式】。这条推论的价值在于：**它让你在买卡之前就知道该往哪个方向调**，而不是先买卡再撞墙。
- **与主文件的口径对齐**：主文件 [§2.3](05-performance-engineering.md) 第 7 条把"量化 / 剪枝 / 蒸馏 / 连续批处理 / PagedAttention / KV Cache / 模型并行 / 推理引擎"并列成一组"AI 推理优化"条目。本节按机制把它们分到两处——前几项动的是显存与搬运量（本方向），"推理引擎"是承载它们的运行时（§5.1 表第 4 行）；它们在清单里是并列的，在**实施顺序上却是有先后的**（[§3.2.4](05-performance-engineering-section-3-sec3.md) 的叠加顺序：服务侧 → 显存侧 → 模型侧）。
- **反方向的一面**：本方向的所有手段都**不改变模型输出**，因此它们不解决"回答质量不够"这类问题；把推理优化当成模型能力问题的解，得到的只是"更快地给出同一个错答案"（§5.2.2 的降级路径同理）。
- **由此付出的**：**其一，显存成为新的容量单位，而它不可弹性购买**——加实例不等于加显存，一段长上下文请求会挤掉同实例上其他请求的空间，于是"扩容"在推理服务里经常买不到线性收益。**其二，批处理把不同请求绑在一起**：一个请求的异常会影响同批其他请求的尾延迟，而 TTFT 与吞吐互为代价（[§3.2.4](05-performance-engineering-section-3-sec3.md) 已把它写成"任何一方的好看数字都可以用调另一个换来"）——所以**只看吞吐的优化结论不可用于在线服务**。**其三，模型侧压缩的代价是静默的**：量化与蒸馏改变输出分布且通常不报错（同节失效点），意味着**延迟指标全绿而业务指标下滑**；这类"优化成功、质量回退"的账，只有质量基线能发现。
- **证据与来源**：【公开】连续批处理的出处是 Orca（OSDI 2022）、分页 KV 管理的出处是 vLLM 论文（SOSP 2023）；vLLM 论文在其测试条件（模型、序列长度、硬件）下报告约 2-4 倍吞吐，本章 [§7.3.4](05-performance-engineering-section-7-sec7.md) 已引用同一来源并标明条件。**本节不重复任何厂商自述的加速倍数**——性能数字若无"硬件 + 输入输出长度分布 + 批大小 + SLO"四项条件，一律只当方向记录（§5.4）。
- **成熟度**：**L2**——①③成立（连续批处理与分页 KV 在多个彼此独立的推理引擎中都是正式功能，判定入口见 §5.4）；**②核不到**：公开的推理性能材料绝大多数出自引擎作者或采购方自身（§5.4）。
- **判定方法**：固定模型与输入长度分布，测"batch 上限 → token/s → 显存占用"三条曲线（[§7.3.4](05-performance-engineering-section-7-sec7.md) 的自验方法）。token/s 随 batch 上升且显存逼近上限 → 瓶颈在显存管理；显存有余量而 token/s 已平 → 瓶颈已转到算力或调度，此时继续加 batch 是白费。
- **什么时候值得做**：在线推理服务且卡时在账单上可见时——它是本主题里回报最直接的一处（[§7.3.3](05-performance-engineering-section-7-sec7.md) 把"每 token 的 GPU 秒"列为乘法项）。**什么时候不值得做**：如果你的负载是低 QPS、单用户长对话（batch 上不去），批处理红利接近零，此时该先做的是前缀缓存与显存优化，不是调 batch。

#### 5.2.2 缓存与并行：它改的是负载形态与关键路径，不是算力

- **旧做法与它的卡点**：多级缓存（主文件 [§2.3](05-performance-engineering.md) 第 4 条）的隐含假设是"同一份结果会被重复请求"。在 LLM 与 RAG 链路上，这个假设的成立程度分成两半：**前缀**（系统提示词、检索到的长文档、工具定义）确实在多轮会话里反复出现；**用户提问**很少原样重复。卡点是**命中率是负载性质的函数，不是工程能力的函数**——而团队通常拿不到"我的负载里有多少共享前缀"这个数，于是把"加缓存"当成通用优化。
- **AI 改变了什么机制**：**缓存键的粒度与判定性质变了**。前缀缓存把键从"整条请求"缩到"token 前缀"（仍是精确匹配，但匹配面变窄）；语义缓存把键换成"向量相似"（**命中判定从精确匹配变成统计判断**，这是性质变化，不是粒度变化）。并行化那一半改的则是**关键路径**：RAG 的端到端是串行链路的加和，只有当两个组件真的互不依赖时并行才缩短端到端。
- **由此得到的**：因为**前缀在多轮会话中被反复使用**，所以"每轮都重新预填充一遍"这笔成本可以被削掉，且削掉的量与**前缀占比**成正比（不是与请求数成正比）——这解释了为什么同一种缓存技术在客服问答场景效果好、在开放式写作场景几乎无效：**收益由负载里共享前缀的比例决定**。并行那一半同理：因为端到端受**不可并行的固定部分**封顶（Amdahl，主文件 §2.2），所以【推算】若不可并行的部分占 40%，把其余部分压到零，端到端最多降到 40%，加速比上限 = 1 / ((1-P) + P/S)，P = 0.6、S → ∞ ⇒ 1 / 0.4 = **2.5 倍**——**先画关键路径再动手，收益上限是算得出来的**。
- **由此付出的**：**其一，前缀缓存的失效是静默的**——前缀里出现一个时间戳、一个未排序的序列化 JSON、或一个每次不同的工具清单，命中率归零，而系统照常工作，**只是账单变高**；判定方法：看缓存读取的 token 数是否长期为零，为零就是有静默失效源。**其二，缓存写入本身有计价档**——主流 API 把缓存写入与缓存读取分成两个单价（写入更贵、读取显著更便宜），并设最小可缓存长度与 TTL；**倍率、最小长度与 TTL 具体数值请以你所用的那家 API 官方价格页与缓存文档当前版本为准**——命中次数不足时，缓存比不缓存更贵。**其三，语义缓存引入一种新的错误形态**：它可能返回"相似但不等价"的答案，而这类错误不报错、不告警、不可检测（§5.5 第 3 条）。**其四，Agent 侧的三条优化各有独立代价**：工具结果缓存缓存的是**世界状态的快照**，陈旧值会被当成当前值（必须自己定 TTL 与失效条件）；工具并行调用的失败处理从"全有全无"变成"部分成功"（返回什么、谁负责没有通用答案）；链路剪枝直接**改变答案所依据的步数**，质量代价在离线评测里看得到、在线上不报警。

| 原 §5.2 的组件 | 优化手段 | 真正动的量 | 代价落在哪 |
| --- | --- | --- | --- |
| Embedding | 批量推理、量化、缓存 | 重复文本的计算量 | 以文本为键 ⇒ 长尾查询命中率低；量化档位改变 ⇒ 召回分布变化 |
| 向量检索 | 索引调参、量化、GPU 加速 | 召回/延迟的交换点 | 召回目标变了 ⇒ 答案依据变了 |
| Rerank | 批量、缓存 | 重复查询的计算量 | 同 Embedding；且它常在关键路径末段，并行收益有限 |
| LLM 推理 | 连续批处理、分页 KV、前缀缓存 | 每 token 的权重与 KV 搬运 | TTFT↑、静默失效、缓存计价 |
| 全链路 | 并行调用、缓存复用 | 关键路径长度 | 部分成功状态；降级改变质量分布 |

- **证据与来源**：【公开】前缀 / 上下文缓存在主流推理引擎与 API 中是正式功能条目，缓存计价口径（写入与读取两个单价、最小可缓存长度、TTL）在各家官方价格页与缓存文档中可核验；HNSW 是有原始论文与多份彼此独立实现的既有算法（§5.4）。**本节未能核到**"缓存把端到端成本降低多少"的第三方（非厂商）公开对照材料——公开材料只给提供方自己的场景。
- **成熟度**：**L2**——①③成立；**②核不到**；且收益依赖负载性质，无法从他人场景借用。**同一方向下的「链路剪枝」是 L3**（①不成立、②核不到：剪枝等于让模型少看一步，其质量代价没有可复核的公开口径），与 §5.1 表第 8 行、去向对照表里的"L2（前两条）/ L3（剪枝）"逐项一致。
- **判定方法**：抽一周的真实请求，统计**共享前缀的 token 占比**与**重复提问的比例**这两个数。前缀占比高 → 先做前缀缓存；重复提问比例低 → 语义缓存的收益预期要下调，而它的误命中风险不变。
- **判定方法的第二问**：把前缀里"每次都会变"的部分找出来（时间戳、请求 ID、未排序的序列化结果、变化的工具清单）。**找得出一个，就说明当前命中率不是负载的上限，而是实现的上限**——这类问题的修复收益通常比调参大，且不需要改架构。
- **什么时候值得做**：前缀占比天然高的负载——多轮会话、固定系统提示词、固定检索文档集、工具定义很长的 Agent。**什么时候不值得做**：单轮、每次输入都不同、且没有质量度量时；以及**在没有失效规则时开语义缓存**——那是用一个不可检测的错误换一点延迟。

#### 5.2.3 AI 辅助性能分析：换的是「谁来排序」，不是「结论从哪来」

- **旧做法与它的卡点**：瓶颈定位依赖人对火焰图与链路图的解释能力——知道该看哪一层、该怀疑哪一跳。卡点是**初筛成本随规模上升**：链路一长、span 一多，人先要花时间把可疑的挑出来，才能开始判断（主文件 [§1.2](05-performance-engineering.md) 痛点第 1 条"不知道慢在哪里"）。
- **AI 改变了什么机制**：**把"人工排序"换成"统计排序"**——模型从海量 trace / 日志 / 执行计划里挑出可疑项并排序。注意它改变的是**候选的产出方式**，不是**结论的性质**：性能结论必须是因果的（改一处、同一压测、同一指标、方向确定），而模型给的是相关性排序。
- **由此得到的**：因为**初筛从人工换成统计**，所以"每天扫一遍全量 trace 找异常"这件事第一次变得便宜，**盲区从"没看过的链路"缩小到"没打点的链路"**——也就是说，这条方向真正的天花板不在模型能力，而在**埋点字段**：trace 里若没有 token 数、批大小、显存占用、队列长度这几个字段，模型只能看见"这一段慢"，看不见"为什么慢"。**先补字段，再谈模型**。
- **由此付出的**：**其一，相关性在性能数据里遍地都是**——同期增长的两个指标、共享同一条链路的两个组件，都长得像因果；把相关性当因果，会稳定地产出"优化了某个指标、体验没变"的结论（这也是本方向最贵的失败形态）。**其二，它产出的是假设而不是结论**，所以要额外承担一层验证成本：每条假设都必须落成"改一处 + 同一压测 + 同一指标"的对照实验，没落实验的假设不算结论。**其三，它会带来新的混淆**：模型描述的是它读到的数据，而不是系统行为；当埋点自身有偏（采样率、缺失字段）时，模型的排序会**忠实地放大埋点的偏差**。

```text
把"模型给的假设"翻译成"可证伪的形式"（不翻译的假设不算结论）
  模型输出                             必须被追问成
  ─────────────────────────────────   ────────────────────────────────────
  "数据库是瓶颈"                       改哪个参数 / 查哪条计划 → 哪个指标应变化
  "缓存命中率低"                       哪条前缀每次都变 → 命中率应回升多少
  "这段链路慢"                         去掉 / 并行哪一跳 → 端到端应降多少
  ────────────────────────────────────────────────────────────────
  通过标准（三条全中）：① 只改一处；② 跑同一份压测、同一批请求；
                        ③ 看同一个指标（含质量基线），方向可预测
  不通过时：把它记成"待验证线索"，不要记成"已定位瓶颈"
```
- **证据与来源**：【本节未能核到】"模型的瓶颈定位结论在生产中被采纳并验证"的第三方（非厂商）可核验材料；公开可见的是工具演示与自研实践。原清单里"AI 推荐优化 / AI 自动调参"两条同此。
- **成熟度**：**L3**——只有演示与自研，①不成立、②核不到；同组的"把 trace 结构化并按异常排序"属既有规则化能力（**L2，非 AI**），但它不是 AI 带来的，本节不为它另立级别。
- **判定方法**：让工具对同一段故障窗口输出 Top-5 假设，然后逐条问"要证伪它需要改哪一处、看哪个指标"。**答不出可证伪形式的假设，不计入产出**。第二问：随机取三条已知的、历史上真实发生过的性能问题，看模型能否命中——命中率低于随机猜测水平的，不要上生产。
- **什么时候值得做**：trace 字段齐全（含 token 数、批大小、队列、显存）且量已经大到人扫不过来时。**什么时候不值得做**：埋点里没有决定成本的那几个字段时——此时上模型只是把"看不见"包装成"有结论"。

#### 5.2.4 Self-Tuning：确定性那半是既有能力（L2），「由模型决定改什么」是 L3

- **旧做法与它的卡点**：参数靠人调（GC、连接池、并发度、副本数、batch），而**调优的速度赶不上负载形态变化的速度**——调完的第二天流量形状就换了（本章 [§3.2.5](05-performance-engineering-section-3-sec3.md) 把这一点写成"一次性调参给出的是一张过期快照"）。
- **AI 改变了什么机制**：**必须把"自动"与"智能"分开算**。按规则与统计信息施加的确定性动作（阈值触发的扩容、按执行计划的 SQL 重写、JDK 自适应堆与 GC 参数）**不需要模型**——本章 [§3.2.5](05-performance-engineering-section-3-sec3.md) 已给出这条闭环的结构（观测 → 决策 → 施加 → 再测量，并显式规定上下限、变更幅度、冷却时间、可回滚）。模型真正能增益的是**预测与建议**：下一季容量、哪个参数该动、哪条 SQL 该重写；而"由模型决定改表结构 / 改分区 / 换引擎"属于另一类动作。
- **由此得到的**：因为**动作由统计信息与规则驱动**，所以"参数跟上负载变化"这件事今天就能排进路线图，且出问题时**原因可复现、可回放、可在测试环境重现**——这是它相对 AI 决策最大的优势。但这类动作的收益要按落点分两半读。前半是**弹性伸缩**：本章 [§7.3.3](05-performance-engineering-section-7-sec7.md) 的成本函数表把它归在"**计费时长的分布**"这一项上——**它削掉的是闲置时段的付费，峰值时段照旧，不改变峰值下的单位成本**——所以**弹性伸缩这一类动作的收益不随机器规模自动放大，而随你负载的峰谷差放大**：峰谷差小、常年跑在高水位的负载，它的产出不足以覆盖维护成本。后半是**按执行计划的 SQL 重写这类访问路径改动**：同表把"单请求资源消耗"列为**乘法项**、收益判为"**与系统规模成正比**"，它属于性能工程那一类改造——**"收益不随机器规模放大"只对弹性伸缩那一半成立，不能读成对整类自动化动作的结论**。

| 自动动作 | 驱动信息 | 可回滚吗 | 能否进自动通道 |
| --- | --- | --- | --- |
| 扩容 / 缩容 | 延迟与饱和指标 | 可（缩回去） | 可以，但要防振荡 |
| 连接池 / 线程池 / 批大小调整 | 队列长度与饱和 | 可（参数级） | 可以 |
| 按执行计划的 SQL 重写 | 统计信息与执行计划 | 可（计划级，回退即还原） | 可以，但需计划回归门禁 |
| 索引增删 | 查询模式与计划变化 | **中**（新增容易，删除要等观察窗口） | 只进建议通道 |
| 分区结构变更 / 表重构 | 增长与访问趋势预测 | **难**（下游依赖要同步改） | 只进建议通道 |
| 模型量化档位切换 | 成本与质量基线 | **难**（输出分布变了，回退要重评质量） | 只进人工评审 |

这张表的读法是**自下而上找边界**：前三行能自动，是因为它们的产物还能被下一次动作覆盖；后三行不能自动，不是因为技术不可行，而是因为**一次错误决策的后果不能用一次操作撤回**——索引删了要在观察窗口之后才知道有没有打穿，量化切了要重跑质量基线。所以"自动化到什么程度"，在本主题里等价于"**你愿意为哪几类动作准备回滚方案**"。
- **由此付出的**：**其一，可解释性下降**——出问题时没人知道当前参数是从哪个历史状态漂移来的（[§3.2.5](05-performance-engineering-section-3-sec3.md) 的代价清单已列）。**其二，反馈滞后会振荡**——扩容触发得比流量上升晚、流量回落时又在扩，表现是资源用量反复波动，比手动固定参数更差（同节失效点）。**其三，本节要单独指出的一条：自动动作会吸收性能回归的信号**——自动扩容把"变慢了"修复成"资源变多了"，于是**性能劣化不再以告警形式出现，而是变成一条缓慢上升的成本曲线**；这与"自愈降低故障可见性"是同一类教训。**其四，自动 SQL 重写会改变执行计划**，若没有计划级回归门禁，一次重写可能把线上计划换成一个在统计信息过期时更差的计划。
- **证据与来源**：【公开】确定性自动化的取证方式是**判定入口而不是集合断言**——在所用引擎 / 运行时 / 云平台的官方文档与 release note 里逐项核验"自动扩缩容、按执行计划的 SQL 重写、自适应 GC 参数"是否为**正式功能**、能否设上限与关闭。JDK 侧的自适应行为有官方文档与 JEP 可核（[§3.2.5](05-performance-engineering-section-3-sec3.md) 已列 JEP 248 / 333 / 439，并注明参数与默认值随版本变化，以所用 JDK 版本的命令文档为准）。**【本节未能核到】"由模型决定参数上限 / 表结构变更"进入生产的第三方材料**。
- **成熟度**：**L3（"由模型决定改什么"那一半）**——只有演示与自研，①不成立；"确定性自动化"那一半不是本方向新增的东西，就是 §5.1 表第 11 行的 **L2（非 AI）**，级别与判据随该行。
- **判定方法**：周期性给自动动作设一个"**关掉窗口**"，在关掉的那段时间看延迟与错误率是否变化。**变化明显说明自动动作在掩盖问题；毫无变化说明它在做无用功**——两种结果都需要动作，只是方向相反。
- **什么时候值得做**：参数已经多到人跟不过来、且负载有明确日 / 周周期时。**什么时候不值得做**：表结构与访问模式本身还在频繁变（模型天天换、分区策略未定）时——自动优化会一直追一个移动的目标，稳定的产出是账单上的额外计算量，不是性能。

### 5.3 与本主题既有栈的接口在哪

性能工程与 AI 之间不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比"AI 能做什么"更能决定它能不能落地。**「现状」列只写接口契约本身的状态（既有机制 / 未定），不写 L1 / L2 / L3**——它描述接口，不是演进方向；表里出现的接口大多不在 §5.1 的表里，本节不给它们另立级别。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 性能 ↔ 可观测（[11-cross-cutting/04](../../11-cross-cutting/04-observability/04-observability.md)） | 交接物 = trace / 指标里的字段：**token 数、批大小、队列长度、显存占用** | 埋点那一侧；缺这几个字段时 AI 分析只能看见"哪一段慢"，看不见"为什么慢"（§5.2.3） | 既有机制 / 字段未定 |
| 性能 ↔ 容量规划（[§04 容量规划](../04-capacity-planning/04-capacity-planning.md)） | 交接物 = **容量单位**：从"实例数 / QPS"换成"显存预算 + 序列长度分布" | 容量侧；单位选错时"扩容"稳定地买不到线性收益（§5.2.1） | 单位未定 |
| 性能 ↔ 混沌工程（[§06 混沌工程](../06-chaos-engineering/06-chaos-engineering.md)） | 交接物 = **稳态与 SLO 的定义**（TTFT / TPOT 分位，而不是只有 P99 与错误率） | 性能侧定义 SLO；SLO 里缺 TTFT 时，推理链路的混沌实验会给出假的"通过" | 既有机制 / 分位口径未定 |
| 性能 ↔ 成本（[11-cross-cutting/03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)） | 交接物 = 每千 token 成本、缓存命中率、自动动作的计费归属 | 平台与财务的接缝处；**没有归属约定时，自动优化变成"没人认领的计算"** | 归属约定未定 |
| 性能 ↔ 数据目录与语义层（[04-data-assetization/08](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 交接物 = 语义缓存的**判定标准**：相似度阈值与"不等价即拒绝"的规则 | 语义缓存的使用方；误命中不可检测，代价由业务承担（§5.5 第 3 条） | 判定标准未定（无通行做法） |
| 性能 ↔ CI / 发布门禁（[§7 与其他方法对比](05-performance-engineering-section-7-sec7.md)：§7.5 第 5 步与 §7.7 的回归门禁） | 交接物 = **计划级与性能级回归门禁**（自动 SQL 重写、量化上线前跑同一套基线） | 提交与评审的人；缺门禁时自动动作与质量回退都不会被发现 | 既有机制（门禁）/ 自动动作的接入未定 |

一句话概括：**AI 没有给性能工程新增任何层级，只改变了"主导资源"与"谁来排序"**。由此得到五条约定。

**第一条约定：容量与 SLO 的单位必须先换。** 用 QPS 规划推理容量、用 P99 定义推理稳态，都会得到与实际无关的结论。可执行的做法：容量单位写成"显存预算 + 输入输出长度分位"，稳态写成"TTFT / TPOT 分位 + 错误率"两项。

**第二条约定：凡"模型建议 → 改配置"的链路，动作必须可回滚且有对照。** 可回滚的含义很具体：变更落在声明文件里、能重放、有一键回退；有对照的含义是：**改前改后跑同一份压测、看同一个指标**。做不到这两条的输出只能进"建议"通道。

**第三条约定：把"命中率"与"质量"一起进看板。** 缓存与量化的收益全靠某率，而这两个率都可能在延迟指标全绿时恶化（缓存静默失效、量化静默回退）。**只监控延迟与吞吐的性能看板，看不见这两类最贵的失败。**

**第四条约定：给自动动作指定"关掉窗口"与计费归属。** 关掉窗口是检验自动动作是否在掩盖问题的唯一办法（§5.2.4 的判定方法）；计费归属是让它的成本可见——**看不见的成本会在下一次预算评审时以"说不清"的形式回来**。

**第五条约定：凡"让某个率上升"的优化，上线时必须带质量基线。** 量化、蒸馏、语义缓存、链路剪枝、降级返回——这五类动作的失败**全部不体现在延迟、吞吐与错误率上**，而体现在输出分布或答案依据上。它们的共同前置条件因此是同一条：一份改前改后可比的质量基线（数据集、问题分布、评分规则三者固定）。**没有这份基线时，这类优化在指标上永远成功**。

分三类列，**其中论文与生产案例两类只列能给出标题 / 出处 + 年份的条目**；release note / 官方文档一类是判定入口，给核验标准而不给年份，理由见该类开头。**宁少勿假**。

- Amdahl，*Validity of the single processor approach to achieving large scale computing capabilities*（**AFIPS 1967**）——§5.2.2 里那条"并行收益上限"的推导依据；主文件 [§2.2](05-performance-engineering.md) 已把它列为本章的数学基础。

**官方 release note / 文档（判定入口）**

**这一类不给年份，只给核验标准**：release note 与官方文档是持续更新的，某条能力对应哪一年取决于你查的那一版，写死一个年份反而会先于能力本身过期。本类的核验标准只有一句——**以官方文档当前版本为准**，在对应条目里看到该能力被标为"正式功能"（而不是预览 / 路线图），即算核验通过。

- 各推理引擎（vLLM / TensorRT-LLM / ONNX Runtime / SGLang 等）的官方文档与 release note——核验"连续批处理、分页 KV 管理、前缀缓存"是否为正式功能、有哪些调度参数、前缀缓存能否按请求开关；**判定方法：看 release note 里有没有独立条目，而不是看项目官网的路线图或 benchmark 博客**。
- 各 API 提供方的官方价格页与缓存文档——核验"缓存写入 / 缓存读取各自的单价、最小可缓存长度、TTL"三项。**这是本主题唯一必须查价格页才能算清的账**：命中次数不足时缓存比不缓存更贵。
- 各向量库的官方文档——核验 HNSW 的构建与查询参数如何暴露、能否按集合配置；召回目标与延迟的对照要自己测（§5.1 表第 5 行）。
- 各云平台的官方文档——核验"自动扩缩容 / 托管推理"的正式功能条目与配额；**本节不对"某平台支持某型号"作断言**。
- 各 JDK 发行版的官方命令文档——核验自适应堆与 GC 参数在当前版本的实际默认值（[§3.2.5](05-performance-engineering-section-3-sec3.md) 已注明这些值随版本变化）。
- 各推理框架与运行时关于并行策略的官方文档——核验张量并行 / 流水并行 / 多机执行是否是正式能力、需要哪些拓扑配置；**判定方法：看文档里有没有独立的多机执行组件与配置项，而不是看博客里的吞吐曲线**。
- 各可观测方案的语义约定文档——核验 trace / 指标里是否有"token 数、批大小、队列长度、显存占用"这类字段的标准命名。**这是 §5.2.3 那条方向真正的天花板**：字段不存在时，任何模型都看不见"为什么慢"。

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含口径与基线的第三方"AI 性能优化"生产案例。公开材料能核到的是引擎作者与提供方自己的性能报告，以及本书 [§6](05-performance-engineering-section-6-sec6.md) 整理的四个案例（阿里双 11、字节春晚、美团外卖、Netflix 流媒体）——**那是本书自撰的汇总估计，口径与样本由本书给出，不构成第②条要求的第三方（非厂商）公开生产案例**。**这个空白本身是结论**：它正是本节把整张表压在 L2 / L3 的直接原因。
- **本主题的第②条缺口可以自己回填，而且比别处便宜**——这是性能工程相对其他主题的唯一优势。但**回填物不是第②条**：第②条的定义是"有第三方（非厂商）公开生产案例"，自造记录既不第三方、也不公开，所以它**不改变本节的定级**，它改变的是"这个方向在我这里值不值得做"的可复核程度。判定一份自造证据合不合格，只看它有没有写全四项：**硬件（型号与卡数）、输入输出长度分布（不是平均值）、批大小与并发、SLO（延迟目标与质量基线）**。缺一项就只是"跑过一次"。
- **五步自造证据法**（一周内可完成，不需要采购）：① 固定一份与生产同分布的请求集（长度分布必须同分布，不能只用短请求）；② 固定硬件与并发，记录基线四项指标（TTFT / TPOT 分位、吞吐、显存峰值、单位成本）；③ 只改一个变量（batch 上限，或缓存开关，或量化档位）；④ 复跑同一份请求集与同一份压测脚本；⑤ 把"改前 / 改后"与四项条件一起留存。**这份记录就是你在评审会上能拿出的、带条件的自证材料——它补充第②条，但不替代第②条。**

**怎么用这份清单**：要核"能力存不存在"看官方文档与 release note（最快）；要核"机制成不成立"看论文（最慢但最稳）；要核"在我这里值不值得做"只能自己跑（§5.2 每条的判定方法都是为这件事写的）——**第三类问题没有任何公开材料能替你回答，本主题尤其如此，因为性能结论不可移植**。

### 5.5 被过度宣传的部分

**「推理吞吐提升 N 倍」**——实际是：连续批处理与分页 KV 管理提升的是**单位显存能装下的并发请求数**，所以它给的是**批量场景**的收益；在低 QPS、单请求长上下文、或延迟敏感的单用户对话里收益接近零，而且会以 TTFT 上升的形式付出代价。**为什么会这样**：因为它们是显存管理机制而不是算力机制（§5.2.1），可摊薄的只有"权重搬运"这一项，摊到 KV 那一项就开始衰减。**它什么时候才会成真**：出现同时给出"TTFT / TPOT 两个分位 + 批大小 + 硬件 + 输入输出长度分布"的对照材料——只报一个吞吐倍数的，无论来自哪里都只当方向记录。**判定方法**：在你的长度分布下测"batch 上限 → token/s → 显存占用"三条曲线，看拐点在哪。

**「AI 自动定位性能瓶颈」**——实际是：它把"人工读火焰图"换成"模型读 trace 排序"，产出是**可疑清单**；而瓶颈判定需要的是因果（改一处、同一压测、同一指标），模型给的是相关性。**为什么会这样**：性能数据里相关性遍地都是（同期增长的两个指标、共享一条链路的两个组件），而模型读到的只是数据，不是系统；埋点有偏时它会忠实地放大这个偏差。**它什么时候才会成真**：模型输出的假设能自动落成"可执行 + 可回滚 + 带对照"的实验，且实验成功率被公开。**判定方法**：拿三条已知的、历史上真实发生过的性能问题去试，看它能不能命中——命中率是唯一有用的评估方式。

**「语义缓存（Semantic Cache）」**——实际是：它把缓存键从"精确匹配"换成"向量相似"，于是**缓存可能返回一个"相似但不等价"的答案**（例如把"退货要几天"命中成"换货要几天"），而这类错误不报错、不告警、不可检测。**为什么会这样**：相似度阈值本质上是**质量与成本之间的交换旋钮**，没有跨工作负载通用的取值；阈值放宽一点，命中率上升、误命中同步上升，而误命中不出现在任何延迟指标里（本主题里"静默失败"最典型的一处）。**它什么时候才会成真**：出现"**误命中率**"这个指标的公开口径与度量方法，且能被你的负载复现。**判定方法**：从缓存命中里抽样人工复核 100 条，数其中有多少条是"不等价"的——这个数不为零时，先定失效规则，再谈命中率。

这三条的共性：**它们都把"某个率的上升"当成了"性能变好"**——吞吐率、命中率、可疑项命中率。而本主题的判据只有三条：**动的是不是乘法项、代价落在谁身上、失败时看不看得见**。这三条一条也没有因为 AI 而改变。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 推理侧的度量语言会整体换代：性能侧从"吞吐倍数"换成"两个分位 + 单位成本"（TTFT / TPOT 分位、每千 token 成本），容量侧从 QPS 换成"显存预算 + 长度分布"，并在容量评审里被当成硬性输入 | 采购与评审材料里出现这两项分位与成本口径，引擎文档把分位作为一等指标；容量评审模板里出现显存预算与长度分位两栏，扩容决策开始引用它 | 讨论仍停在"哪个引擎更快"，且给出的数字没有硬件与长度分布条件；容量评审仍以 QPS 与实例数为主，且反复出现"扩了但还是慢" |
| 缓存类优化会被当作**负载性质**来评估，而不是当作通用开关 | 平台文档开始要求填写"共享前缀占比"这类前置条件与命中率口径 | 继续以"支持缓存"为卖点，且拿不出命中率与误命中率口径 |
| 自动动作（扩容 / 合并 / 重写 / 调参）会与性能回归检测**分开度量** | 出现"关掉自动动作的对照窗口"这类例行做法 | 回归检测继续被自动动作吸收，SLO 缓慢劣化且不告警 |
| AI 辅助性能分析会先以"提假设 + 生成对照实验"落地，而不是直接给根因 | 工具产物是实验设计与对照方案，并要求回填结果 | 工具产物是"根因：数据库慢"这类结论，且被直接采用、不回填验证 |
写这四条时的共同约定：**信号必须是外部可观察的**（文档条目、验收口径、公开案例、评审模板里的栏目），而不是"我觉得会"。**第一条要按两半分别判**——在自家容量评审模板里加"显存预算 + 长度分位"两栏今天就做得到（快），而"哪个引擎吞吐倍数更高"这类说法从行业话语里退场要等一轮采购周期（慢），不要因为后半没发生就否掉前半；**第二条最可能出现"半对半错"**：命中率口径会出现在平台文档里（对），但"加缓存就更快"的说法不会消失（错），所以这一条要按**文档里有没有前置条件栏**来判，而不是按话语是否消失来判；**第三条只需一次季度复盘**：把自己团队"关掉自动动作的那几天"的延迟与错误率记录留下，就能看出它是否真的与回归检测分开度量；**第四条取决于工具侧愿不愿意给实验设计而不是给根因**，它的信号出现在工具的产物形态里，不出现在你们的看板上。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 推理卡时是账单大头 | 先测"batch 上限 → token/s → 显存"三条曲线，再定配置 | 观察单位 token 成本与显存峰值是否同向变化 | 不要在没测长度分布前照搬公开的批处理配置 |
| 容量规划仍以 QPS 为单位 | 把容量单位改成"显存预算 + 输入输出长度分位" | 观察扩容后单位 token 成本是否线性下降（不降说明单位选错） | 不要用 QPS 推算推理实例数——它会把资源买错 |
| 准备上量化 / 蒸馏 | 先建质量基线，再改模型 | 观察质量指标与延迟是否同时被记录 | 不要在质量基线缺失时先上量化——回退是静默的 |
| 想加语义缓存 | 先定"不等价即拒绝"的规则与阈值来源 | 观察误命中率（抽样复核） | 不要只看命中率；不要在没有失效规则时开语义缓存 |
| SLO 里只有 P99 与错误率 | 补 TTFT / TPOT 两个分位 | 观察推理链路的混沌实验是否还给出"通过" | 不要用端到端 P99 判断推理服务的稳态——它看不见排队 |
| 运维想上 Self-Tuning | 打开确定性自动化，给它设上限与"关掉窗口" | 观察关掉窗口那几天延迟与错误率的变化 | 不要让不可回滚的动作（改分区结构 / 换引擎）进自动通道 |
| 老板要求"用 AI 自动调优" | 把目标拆成"确定性闭环 + 容量预测 + 建议通道"三段，各给验收口径 | 观察三段的负责人是否明确 | 不要签"模型自动决定参数上限"式的目标——它没有可验收的失败定义 |
| 团队想用 LLM 找瓶颈 | 先把 trace 里的 token 数、批大小、队列、显存补上 | 观察模型假设被证实的比例 | 不要用相关性排序替代对照实验；不要在没有可证伪形式的假设上下结论 |
| 有人提议用"更便宜的模型档位"降本 | 先建质量基线，再按档位做 A/B，且固定同一套评测集 | 观察质量分与单位成本是否同时被记录 | 不要在没有质量基线时用降档位数换成本——它不报错，只变差 |
| 想给索引 / 分区做自动决策 | 先用建议模式跑一个观察周期，看建议被采纳后的实际效果 | 观察"自动建议 → 人工采纳 → 指标变化"这条链的命中率 | 不要在没有观察窗口时自动删索引、改分区——这两类动作不能一键撤回 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改模型、动缓存、扩自动化半径、换度量语言），**而收益依赖一个尚未成立的假设**（数字可移植 / 命中即等价 / 模型分析得对）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**成本函数的主导项**——推理链路上决定单位成本的那个量，从"算力 / 调用次数"换成了"显存带宽与显存容量决定的每 token 搬运量"。因此所有真实收益都落在同一处：**让同一份权重服务更多 token、让同一份前缀不被重复搬运**；而所有真实代价也来自同一处：**这些东西都不改变模型输出，所以它们的失败（命中率归零、量化回退、自动动作掩盖回归）全部是静默的**。
>
> 判断本主题下任何新提法的快捷方式：**它动的是乘法项（单请求资源消耗），还是只改了测量方式（[§7.3.3](05-performance-engineering-section-7-sec7.md)）？** 动乘法项的今天就有用（本节判 L2 的那几行），只改测量方式的要先证明它的输出可被证伪。第二条同样快的判断：**它靠的率是哪几个、失败时看不看得见、代价落在谁账上**——三条答不上来的方向，只能停在"建议"通道。
>
> 如果只能带走一句话：**先把单位成本与 SLO 的口径定清楚，再让 AI 去优化**；顺序反过来，就是让一个只会排序相关性的分析层，去优化一套连瓶颈口径都没统一的系统。
>
