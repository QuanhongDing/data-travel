## 4. 工程实现

本节按「落地步骤 → 关键技术点 → 工具链 → 存量迁移 → 模板 → 自检」组织，术语与主文件 §2.1 及 [§ 3](05-performance-engineering-section-3-sec3.md) 保持一致：**基线**、**瓶颈资源类型**、**延迟预算**、**P99 / P999**、**端到端**、**TTFT / TPOT**、**延迟与吞吐可调换**。§3 讲每个模式被什么约束逼出来、机制、代价与失效点；本节只讲**怎么按顺序把它装进组织**，不重复模式的论述。

读者分两类，本节两栏都覆盖。**从零搭建**的团队直接按 4.1 的五步走：基线可以在压测环境里先建立，SLO 与埋点清单在设计期就能定。**存量改造**的团队（系统已在线、多半也已经有若干看板与压测脚本）建议先读 4.4 再回到 4.1——存量的第一步不是建基线，而是**用已有数据拼一份事后基线并把口径统一**，这件事的顺序和从零搭完全不同。

先定一条纪律：**没有基线不做优化，每次改动都要有端到端前后对比**。这是 §3.5 三条最危险的反模式（只看均值、缓存滥用、忽视数据库）共用的判据——它们的共同点是出问题时没有任何一个性能指标报警，而这条纪律是唯一能让那种情况提前暴露的手段。

### 4.1 落地步骤（五步，顺序不能换）

**Step 1：建立性能基线并定义 SLO（【经验】2–4 周，随服务数量与埋点改造面变化）**

1. 采集 QPS / TPS、P50 / P95 / P99 / P999、CPU / 内存 / IO / 网络利用率，形成一份**端到端基线**——同一压测场景、同一数据规模、同一 P99 口径，三者缺一，后面的对比都不成立。
2. 接上三件套：APM（应用性能监控）、Trace（链路追踪）、Metrics（指标）。埋点先接最外层（入口与出口），再按需下沉到具体跳；一次性把每一跳都接齐是常见的第一年项目，不建议作为起点。
3. 定义 SLO：可用性与延迟各一条，并写明统计窗口与分位数口径。示例口径为可用性 99.95%、P99 < 500ms【经验，随业务对延迟的容忍度与成本预算变化，不是普适值】。
4. 把基线与 SLO 存成一份带更新日期的文档，而不是留在某个人的仪表盘里。

- **产物**：一份带更新日期的基线 + SLO 文档（含统计口径）+ 埋点清单（哪个接口埋了哪几个指标）。
- **判据**：抽 3 个核心接口，能否给出同一口径的 P99 与它的瓶颈资源类型；再问「这份基线最近一次更新是什么时候」。答不出，说明只有监控没有基线——**仪表盘上的曲线不是基线**。
- **为什么必须第一步**：后面四步全靠它验收。没有基线，瓶颈定位无法证伪（不知道现状是快是慢）、优化效果无法归因、压测结论无法比较、回归告警无处可依；缺了它，四步的产出都只能靠感觉判断。

**Step 2：瓶颈识别，落到「哪一类资源」（【经验】1–2 个月，随服务数与调用链长度变化）**

1. **关键路径分析**：用链路追踪把一次请求的延迟按跳拆开（客户端 → CDN → 网关 → 应用 → 缓存 → 数据库），画出关键路径并标出每跳的耗时与队列等待，目的是区分「某一跳耗时涨了」与「某一跳前面的队列变长了」（§3.2.1）。
2. 火焰图识别 CPU 热点（perf、async-profiler、eBPF 一类）。
3. 慢查询分析：`EXPLAIN` 看扫描行数与返回行数之比，配慢查询日志与 pt-query-digest 一类工具做聚类。
4. 资源分析：CPU / 内存 / IO / 网络逐项看饱和度，并标注每项是「本层到顶」还是「被上游带上来」。

- **产物**：瓶颈清单，每一条带**资源类型 + 测量证据**（哪个接口、哪个时间窗、哪一个指标）。
- **判据**：清单里每条能否指到一次测量而不是一次讨论；再看有没有出现过「两个团队同时报了两个不同的瓶颈」——出现说明测量口径不同（窗口或分位数不一致），先统一口径再继续。
- **为什么必须第二步**：它决定第三步的作用点。Amdahl 定律给了量化理由（主文件 §2.2 的算例：可并行部分 0.8、并行加速 10 倍时加速比约 3.57 倍而非 10 倍）：优化非瓶颈部分的上限极低，而定位错误的代价要到第三步末期才暴露——那时已经投入了两三个月。

**Step 3：分层优化，只动定位到的那一层（【经验】2–3 个月，随改动面与回归成本变化）**

1. 按 §3.2.2 的四层推进，**一次只动一层**：前端 / 边缘（CDN、资源合并压缩、懒加载）、网络 / 协议（HTTP/2 多路复用、HTTP/3 + QUIC、TLS 1.3、gRPC）、应用（JVM / GC 调优、缓存、异步化、批处理）、数据（索引、SQL、读写分离、分库分表、冷热分层）。
2. AI 推理链路当作独立的一类处理（量化、连续批处理、显存管理），不要套用 CPU 时代的调参思路（§3.5 的第五条反模式）。
3. 每次改动先归类：它属于「减少工作量 / 避免重复工作 / 增加并行」中的哪一类（§3.2 的三类动作表）。归不进任何一类的改动默认回滚。
4. 改完**重新测一次端到端**再决定下一层——瓶颈会随优化移动，凭印象继续优化同一层是最常见的浪费。

- **产物**：每次改动一份记录：改了什么、针对哪条瓶颈证据、属于哪一类动作、端到端前后对比、回滚点。
- **判据**：端到端 P99 动了没有；若有两次连续改动都在同一层而端到端没动，停止在该层加码，回到 Step 2 重新定位（这是 §3.2.2 失效点的直接信号）。
- **为什么必须第三步**：优化必须在瓶颈被测量出来之后做，且必须一层一层地做。把顺序反过来（先加缓存、先扩容）就落入 §3.5 的两条反模式，症状是「局部更快、整体没变」，而此时改动已经进入代码、回滚面随每一轮扩大。

**Step 4：压测验证（【经验】每个版本一轮，单链路半天到一天，全链路按场景数累加）**

1. 单链路压测（k6、JMeter、Locust、Gatling 一类）：找单个服务的承载力上限与延迟拐点。
2. 全链路压测：用生产的流量模型与同量级数据，端到端验证；压测流量要打标记，避免污染生产指标与下游数据。生产环境发压通常需要平台侧能力（流量染色、影子表 / 影子链路），候选如阿里云 **PTS**（性能测试服务）、**AHAS**（应用高可用服务）这一类全链路压测平台，选型判据见 4.3 的「压测」行。
3. 优化前后对比：同一场景、同一数据规模、同一分位数口径。
4. 把压测结论回写进基线（Step 1 的文档），让基线跟着版本走。

- **产物**：压测报告（含场景、数据规模、流量模型、结论）+ 与基线同口径的前后对比。
- **判据**：压测的数据规模与分布是否与生产同量级——不同量级的压测只能证明「没坏」，不能证明「够用」；再核一遍：单链路的结论有没有被写成全链路的承诺。
- **为什么必须排在优化之后**：压测是对改动结果的验收；在优化之前压测，结论会被后续改动作废。它同时是基线的更新入口——没有这一步，基线会长期停在第一次采集的状态，回归告警也就失去了参照。

**Step 5：持续监控与回归告警（持续）**

1. 性能 Dashboard：P99 / QPS / 资源利用率，口径与 Step 1 的基线、SLO 一致。
2. 性能回归自动告警：触发条件用「**相对基线的退化**」而不是绝对阈值。
3. 月度性能 Review：过一遍回归记录、未归因的波动、下一层的容量余量。

- **产物**：看板 + 告警规则（每条注明阈值来源）+ 月度 Review 记录。
- **判据**：上一次性能回归是被告警发现的，还是被用户投诉发现的；告警触发后能不能定位到某次发布或某次数据增长。答不出，说明告警还停在「指标超阈值」，没有做到「回归可归因」。
- **为什么必须最后且不能省**：它是唯一能守住前四步成果的环节。§3.5 对三条危险反模式的判据是「出问题时没有任何一个性能指标报警」——回归告警就是让那种情况不再发生的唯一手段。

**最常被跳过的是 Step 1 的基线与 Step 5 的回归告警。** 两者都不产出功能，进不了需求排期。跳过基线的症状不会在优化当天出现，而是在三个月后：曲线涨了跌了都说不清原因，团队只能再优化一轮，而这一轮动的很可能又不是瓶颈层。跳过回归告警的症状是：优化成果被后续发布一点点吃掉，直到下一次大促或下一次超时才被发现，而那时已经无法回溯是哪一次改动引入的。

**两类读者的起手式不同：**

| 你的处境 | 第一步具体做什么 | 最该避免的起手式 |
| --- | --- | --- |
| 从零搭建（还在设计期） | 从 Step 1 起走；基线可以在压测环境里先建立，SLO 与埋点清单在设计期就能定 | 先把架构做成「理论上很快」的样子，上线才开始测量 |
| 存量改造（已在线运行） | 先做 Step 1 的变体：不加代码，用现有日志与 APM 数据拼一份事后基线，同时把各系统的 P99 口径统一 | 直接开始优化（加索引、加缓存），拿不出优化前的数字 |

### 4.2 关键技术点

**链路追踪（OpenTelemetry 一类标准）**

- **做法**：统一上下文传播规范，用同一条 trace 串起所有跳；采样按「长尾是否被采到」设计——**慢请求必留、快请求抽样**（按延迟触发补充采样）。
- **机制**：因为延迟是各跳耗时之和加排队时间，把每一跳的耗时与队列长度记为独立指标后，「慢」就被分解成「某一跳的耗时涨了」或「某一跳前面的队列变长了」两类可证伪的判断——前者改代码，后者改容量（§3.2.1）。
- **失效条件**：当 QPS 很高而 trace 全量同步上报时失效——埋点与上报本身在关键路径上消耗 CPU 与网络。**症状是开了追踪之后整体 P99 上升**，团队于是把采样率一降再降，最后长尾请求根本采不到，而那正是最需要它的时候。**观测信号**：追踪开销占用的 CPU 比例、慢请求的采样覆盖率。
- **档位**：【公开】OpenTelemetry 的 Trace 规范 1.0 发布于 2021 年（CNCF 项目；语义约定另有独立版本号并持续演进，请以 opentelemetry.io 当前文档为准）。

**JVM / GC 调优（G1 一类现代收集器）**

- **做法**：固定堆（-Xms 与 -Xmx 取同一值，避免运行期扩容）、设定暂停目标（MaxGCPauseMillis 一类）、按**停顿分布**而不是按吞吐调参；先测再调。
- **机制**：因为 GC 停顿直接进入长尾，P99 常常由停顿而不是平均处理时间决定；固定堆让停顿分布稳定，暂停目标把「允许的停顿」变成一条可验收的约束。
- **失效条件**：当堆被设得过大、或暂停目标定得过小时失效——收集器会更频繁地启动以达成目标。**症状是 P99 上升而 CPU 利用率不高**；堆过大还会抬高单次停顿与晋升失败的风险。**观测信号**：GC 日志里的停顿分布（看 P99 停顿而不是平均停顿）、老年代晋升速率、Full GC 次数。
- **档位**：【公开】JEP 248（JDK 9，2017）使 G1 成为默认 GC；JEP 333（JDK 11，2018）引入实验性 ZGC；JEP 439（JDK 21，2023）引入分代 ZGC；参数默认值随版本变化，以所用 JDK 版本的文档为准。

**SQL 与执行计划**

- **做法**：先看 `EXPLAIN` 的**扫描行数与返回行数之比**，再决定是否加索引；避免 `SELECT *`；连接池（HikariCP、Druid 一类）的最大连接数与数据库侧连接上限一起定；读写分离与分库分表只在单库确已到顶后再引入。
- **机制**：因为 B-Tree 索引把查询从全表扫描的 O(N) 降到 O(log N)（算例见主文件 §2.2：100 万行时约 20 次 IO 对 100 万次），所以「先看扫描行数」能在不试错的前提下判断索引是否有用；反过来，扫描行数本就接近返回行数的查询慢在「本就要读这么多」，加索引没有用。
- **失效条件**：当索引建在选择性低的列上、或写入远多于读取时失效——索引维护成本超过查询收益。**症状是写入变慢而查询没有变快**。另一种失效来自分片：分片键决定只有一种访问路径快，跨片聚合把「一台机器慢」换成「每次查询扇出到全部分片」。**观测信号**：每张表的索引数、索引命中率、写入吞吐与索引数是否同向变化。
- **档位**：索引数量、连接池大小的具体取值随表结构与并发模型变化，不给通用数【经验】。

**缓存与失效口径**

- **做法**：每处缓存都要写明「谁失效、何时失效、失效失败怎么办」；给不出失效通道就用短 TTL 换正确性；多级缓存（本地 + 分布式 + CDN）逐层写各自的失效口径（结构与三类结构性风险见 §3.2.3，本节只讲工程要求）。
- **机制**：因为命中率对后端负载是**乘性**影响（§3.2.3 的推算：命中率从 90% 提到 99%，到达后端的请求量降到十分之一），所以多一层缓存带来的是数量级收益；代价是失效面随层数线性增长——一份数据要在 N 层上失效，任何一层漏掉就产生不一致。
- **失效条件**：当出现「写后立即读」的业务、或写频率升高时失效。**症状是写后读不一致的工单反复出现**，而命中率这类指标全程正常。**观测信号**：写后立即读的业务占比、失效通知的传播路径条数、不一致工单的收敛时间。
- **档位**：TTL 按业务能容忍的陈旧时长定，不给通用值【经验】；命中率与后端负载的关系为【推算，推导见 §3.2.3】。

**AI 推理优化（vLLM 一类推理引擎）**

- **做法**：按**服务侧 → 显存侧 → 模型侧**的顺序做：先连续批处理与请求调度，配图级优化（CUDA Graph 一类：把解码循环里形状固定的算子序列捕获成图后回放，省掉逐步重复的内核启动开销，对应推理引擎的 `enforce_eager=False` 一档开关）；再显存管理（KV Cache 与 PagedAttention 一类），最后才量化（FP32 → INT8 / INT4）、剪枝、蒸馏；量化前先建**质量基线**（顺序理由见 §3.2.4）。
- **机制**：因为自回归解码的瓶颈是显存带宽而不是算力，每一步都要读一遍权重与 KV Cache，所以让显存在请求之间被更充分复用，等价于摊薄每 token 成本——这是吞吐提升的主要来源，而不是更快的算子。
- **失效条件**：当任务对精度损失敏感时，量化会**静默回退**：不报错、不超时，只在输出分布上体现。**症状是延迟指标全绿而业务指标下滑**。另一条失效来自批处理：不同请求绑在一起后，任何一个请求的异常都会影响同批其他请求的尾延迟；而且 TTFT 与吞吐互为代价，任何一方的好看数字都可以靠调另一方换来。第三条来自图捕获（CUDA Graph 一类）：它只在计算图形状固定时才省得下启动开销，当请求长度与并发分布变化剧烈、捕获的图覆盖不到实际形状时，只能退回逐步执行——**症状是打开图捕获前后 TTFT 几乎没有变化，且在扩容或批大小改变后出现一段延迟尖刺**（重新捕获的代价）。**观测信号**：TTFT、TPOT、单位 token 成本、显存利用率，以及质量评测的回归曲线。
- **档位**：【公开】连续批处理由 Orca 提出（OSDI 2022），vLLM 的 PagedAttention 是其中被引用最广的显存管理方案（SOSP 2023）；量化带来的体积缩小倍数与质量损失随模型与任务变化，以所用推理引擎与官方评测为准。

**网络与协议（HTTP/2、HTTP/3 + QUIC、TLS 1.3、gRPC）**

- **做法**：先量「单请求的往返次数」与「连接复用率」，再决定升级哪一层；HTTP/3 + QUIC 与 TLS 1.3 的 0-RTT 在边缘终结；服务间调用用 gRPC 一类基于 HTTP/2 的 RPC。
- **机制**：因为握手与往返是**每个请求都要付的固定成本**，加机器摊不掉它，只能在协议层减少往返次数；TLS 1.3 把完整握手压到一次往返，会话恢复可用 0-RTT。
- **失效条件**：当网络路径上有中间盒限制 UDP 时，QUIC 会退化为 TCP 或不可用——**症状是部分客户端（多见于企业网、特定运营商）的 P99 反而比升级前更差**。0-RTT 的失效点在重放防护：它只应承载幂等请求。**观测信号**：按网络类型分组的协议协商成功率、TLS 握手耗时在 P99 中的占比。
- **档位**：【公开】HTTP/2 见 RFC 9113，HTTP/3 见 RFC 9114（2022），TLS 1.3 见 RFC 8446（2018）。

**压测口径**

- **做法**：单链路压测找上限，全链路压测验端到端；压测的数据规模与分布与生产同量级；压测流量打标记。
- **机制**：因为容量问题的本质是排队，而排队只在接近处理能力时才非线性增长，所以压测必须**压到拐点**（延迟开始随并发上升的那个点）；只压「没坏」的区间得不到容量结论。
- **失效条件**：当压测数据规模远小于生产、或流量模型与真实分布不同时失效。**症状是压测全绿而上线后超时**，回查时才发现压测当天数据库只有生产很小一部分数据。**观测信号**：压测数据集与生产数据集的行数与分布差异、压测时的资源利用率峰值是否接近生产峰值。
- **档位**：压测流量规模按「生产峰值的多少倍、用什么模型生成」定，具体倍数随业务峰谷比变化【经验】。

### 4.3 工具链与平台

选型判据写成「在什么约束下选它」。工具是否仍以表中的能力在售、参数与计费口径为何，以厂商官方文档当前版本为准。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| **APM** | Datadog、New Relic、阿里云 ARMS、腾讯 CAT | 它能否给出**与你自己口径一致的 P99**（窗口、分组维度可配），以及能否把 trace id 与指标关联起来 | 多个系统各算一套 P99 时，同名指标无法横向比较，讨论退化成「你那个数怎么来的」 |
| **Trace** | Jaeger、Zipkin、SkyWalking、OpenTelemetry | **上下文传播能否覆盖你全部的语言与中间件**，采样策略能否按延迟触发 | 任何一跳没接上，trace 就断在那里，排查手段退回猜 |
| **Profile** | perf、async-profiler、FlameGraph、eBPF 一类 | CPU 密集选采样型剖析器（低开销、可常开）；要看内核态与 IO 时选 eBPF | 高开销的剖析方式只能短时开，而偶发长尾恰好在那几分钟之外 |
| **压测** | 施压工具 k6、JMeter、Locust、Gatling；全链路压测平台 PTS（阿里云性能测试服务）、AHAS（阿里云应用高可用服务） | 单链路选脚本化程度高的（k6、Locust）；协议覆盖要求广（HTTP / JDBC 等多协议）选 JMeter；全链路优先用平台内置能力——判据是「能不能在生产环境发压并把流量隔离」，需要流量染色与影子表 / 影子链路时选 PTS / AHAS 这一族（能力边界与计费口径以厂商官方文档当前版本为准） | 用单链路工具拼全链路：流量模型、数据构造与标记都要自己实现，通常做不完整；只买施压能力而自建隔离，压测流量会落到生产表或生产指标上，结论随之作废，只能退回测试环境——而测试环境与生产的差异恰是压测要压掉的东西 |
| **JVM 工具** | async-profiler、JFR、VisualVM | 生产常开选 JFR（低开销、有事件流）；定位具体热点用 async-profiler | 只用可视化工具（VisualVM 一类）盯在线服务：开销与安全边界都不适合生产常开 |
| **数据库** | `EXPLAIN`、pt-query-digest、慢查询日志 | 先开慢查询日志（成本最低），再用 pt-query-digest 聚类，最后逐条读 `EXPLAIN` | 不开慢日志时，「哪条 SQL 最贵」只能靠猜，而猜通常落在最新的那条而不是最贵的那条 |
| **AI 推理** | vLLM、TensorRT-LLM、ONNX Runtime 一类推理引擎 | 要连续批处理与高并发 → 面向服务吞吐的引擎；要极致单请求延迟或模型固定 → 编译型运行时 | 用面向吞吐的配置做低延迟场景：TTFT 变长；用编译型运行时做多模型多版本：每次换模型都要重编译 |
| **协议** | HTTP/2、HTTP/3 + QUIC、gRPC | 往返次数多、连接复用率低 → 升级协议；客户端网络环境不可控（企业网限 UDP）→ 先保留 HTTP/2 并灰度 | 一次性全量切到 QUIC：部分客户端 P99 反而变差，而回滚要同时动客户端与边缘两层 |

**这一类里最容易被误选的是「压测」**：把单链路压测的结果当成全链路承诺。误选后果不在压测当天——单链路压测确实能证明服务本身没坏，于是结论被写进容量规划，直到大促时全链路在某个共享依赖（数据库、缓存、下游服务）上排队，才发现链路里的约束根本不是被测的那个服务。**替代判据是一条**：压测报告里有没有写明「这份结论覆盖到哪一跳、不覆盖哪一跳」。

第二容易被误选的是 **APM** 这一行，常被当成「有了工具就有基线」：APM 给的是曲线，基线要的是**同一口径、同一次测量、带更新日期**的一组数。判定方法很具体——打开 APM，问「三个月前这个接口的 P99 是多少、当时的采样与统计口径是什么」；答得出才叫有基线。

表中没有列出的类别不等于不存在，而是**没有稳定的判据可写**：这类工具应当进试点清单，而不是进选型表。

### 4.4 存量迁移

存量系统做性能工程的难点不在技术，而在**你无法选择起点**：系统已经在线、口径已经分散、瓶颈可能来自三年前的一次决策。因此下面的顺序是「先补事实 → 再分类 → 再优化 → 最后收口」。

**① 先补事后基线，不写代码（【经验】1–3 周，完全可回退）。** 用现有日志、APM 数据与数据库慢查询日志拼一份基线（同一统计窗口、同一分位数口径），并把各系统的口径对齐。这一步不改生产，产出是后面每一步的对照物。

- **判据**：让两个团队各自报同一个接口的 P99，差值能否用统计口径解释（窗口、采样、是否含排队、是否含下游超时）——解释不通就先统一口径，别急着优化。

**② 存量接口分类处理，禁止全量改造埋点。**

- **A 类｜有 SLO 的核心接口**：补全埋点（入口 / 出口 / 依赖调用），纳入回归告警。
- **B 类｜在线但无 SLO 的老服务**：只加最外层埋点（入口耗时与错误率），不做内部改造；出问题时再下沉。
- **C 类｜无人使用**：不补埋点，登记退役——它们的曲线进不到任何决策。
- **判据**：每个接口都落在三类之一，分类依据（最近调用时间、调用方数量）可查。

**③ 优化动作按可回退性排序，先做能退回来的。**

- 先做可回退的：加索引、调连接池参数、开慢查询日志、调 JVM 参数——每一项都有明确的回滚点。
- 再做中等代价的：加缓存、异步化、协议升级——可灰度，但会引入新的故障模式与一致性窗口。
- 最后才做不可回退的：分库分表与分片键。§3.6 的判据在这里生效——分片键一旦定错，再平衡要停机或双写，所以**迁移不是重选分片键的时机**。
- **判据**：每个动作能否回答「如果明天不要了，怎么退、退多久、影响谁」；答不出的动作不许进优化清单。

**④ 双轨怎么维持、维持多久。**

- 形态是**优化只落新版本**（灰度发布），旧版本保留基线能力；同一指标的新旧口径并行采集一段时间，直到两条曲线可解释地重合。
- 三级对账：单链路压测结果、端到端 P99、资源用量。**三者不一起改善时，说明改动只挪动了瓶颈**（§3.2.2 的失效点），此时继续加码同一层是浪费。
- 双轨长度由「新旧口径的差异是否已被解释」决定，不由版本计划决定【经验：常见 1–2 个发布周期；新版本改动面越大、涉及存储或协议层时越长】。
- 双轨期的冗余成本可先估【推算：新旧版本同时在线 → 计算资源约多一份，按灰度比例折算；50% 灰度时约多 50% 的实例；若只在边缘层灰度，增量低于此】。
- 双轨期必须有一条「改哪边」的规则：发现性能问题时默认只改新版本，并通过端到端对比确认旧版本是否也需要修；万一必须改旧版本，记录原因与改动人。

**⑤ 什么信号说明可以退出双轨。** 四条同时满足：① 端到端 P99 与资源用量在新版本上稳定不劣于旧版本，且已过一个完整流量周期（含一个高峰）；② 回归告警已在新版本上接管，并触发过一次且有归因记录；③ 压测场景能在新版本上复现同一结论；④ 旧版本的「已知问题清单」已逐条处理或明确接受。

**⑥ 迁移里最常见的三个错误。**

1. **把「加缓存」当第一步。** 它见效最快，也最容易把慢查询掩盖到最不方便的时刻（§3.5 的缓存滥用与忽视数据库两条反模式）。
2. **把单链路压测结论写成全链路承诺。** 判定方法：压测报告里能不能指出「不覆盖哪一跳」。
3. **只改代码，不改容量模型与告警口径。** 换版本后新基线没有被记录，此后所有人都在拿旧基线看新系统，告警要么沉默、要么长期误报。

**最典型的失败是按日历收口**：计划写着「灰度两周后全量」，到点就切。此时旧版本的容量模型、告警阈值、压测场景都还停在旧版本上，它们不会立刻报错，而是在下一次流量高峰时以「所有指标同时偏离」的形式出现。**判据**：退双轨由端到端对比与告警接管状态决定，不由日历决定。

### 4.5 模板 / 示例

**模板一：端到端指标埋点（应用侧）**

```java
// Micrometer：把耗时与计数作为一等指标暴露，维度与看板口径一致
@RestController
public class OrderController {
    private final Counter orderCounter;
    private final Timer orderTimer;

    public OrderController(MeterRegistry registry) {
        this.orderCounter = registry.counter("orders.created");
        this.orderTimer = registry.timer("orders.latency");
    }

    @PostMapping("/orders")
    public Order createOrder(@RequestBody OrderRequest req) {
        return orderTimer.record(() -> {
            Order order = orderService.create(req);
            orderCounter.increment();
            return order;
        });
    }
}
```

**怎么用**：把 `orders.latency` 的**分位数口径**（哪个窗口、是否含排队、是否含下游超时）写进 SLO 文档，否则同一指标会在两个看板上给出两个值；`Timer` 只应包住真正的处理段，把排队时间包进去会让 P99 失去定位价值。

**模板二：链路追踪接入与采样（慢请求必留）**

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(endpoint="collector:4317")))
trace.set_tracer_provider(provider)
tracer = trace.get_tracer(__name__)

@tracer.start_as_current_span("process_order")
def process_order(order_id):
    order = db.query(order_id)          # 依赖调用自动成为子 span
    payment = payment_api.charge(order)
    return {"order": order, "payment": payment}
```

**怎么用**：`endpoint` 指向本地的收集器而不是直连后端，上报失败时才不会阻塞业务；采样策略在收集器侧配成「按延迟触发补充采样」（慢的必留），只按比例采样会让长尾永远采不到。这段代码只解决接入，不解决口径——跨语言服务要统一上下文传播规范，否则 trace 会断在没接入的那一跳。

**模板三：性能改动记录（一次改动一条）**

```markdown
# 改动：{一句话}  日期：{YYYY-MM-DD}  负责人：{到人}  回滚点：{commit / 配置项}

- 瓶颈证据：{哪一类资源 / 哪一次测量 / 查询或截图}
- 动作类型：减少工作量 / 避免重复工作 / 增加并行（三选一，取 §3.2 的三类动作表）
- 端到端前后对比：P99 {改动前} → {改动后}（同一场景、同一数据规模、同一分位数口径）
- 副作用：{资源用量的变化 / 新增的故障模式 / 一致性或陈旧窗口的变化}
- 压测验证：{场景与数据规模}，结论 {通过 / 未通过 / 未跑及原因}
```

**怎么用**：三行是硬要求——瓶颈证据、端到端前后对比、动作类型；「副作用」一列最容易空着，而它恰恰是后面事故的入口（缓存带来陈旧窗口、并行带来下游压力）。本次改动只针对哪一层、覆盖到哪一跳也要写清楚，因为它决定了下次谁来读这份记录。回滚点写在标题行，不要写在正文里——需要回滚时没人会读完一篇记录。

**模板四：SLO 与回归告警口径定义**

```markdown
| 服务 / 接口 | 延迟口径（分位数 + 窗口 + 是否含排队） | SLO 目标 | 基线值（最近更新日期） | 回归告警触发条件 |
| --- | --- | --- | --- | --- |
| {接口} | P99 / 5 分钟滚动 / 不含排队 | {x ms} | {y ms}（{日期}） | 相对基线退化超过 {z%}，持续 {n} 分钟 |
```

**怎么用**：最后一列用**相对基线的退化**而不是绝对阈值——绝对阈值会随业务增长被静默抬高，而相对基线能抓住「悄悄慢下来」。第二列必须写全三项（分位数、窗口、是否含排队），缺一项这份 SLO 就无法与别人的数对齐；「基线值」必须带更新日期，没有日期的基线在两个月后就没有参照价值。

**模板五：AI 推理服务的量化与批处理（先服务侧、再显存侧、最后模型侧）**

```python
# ① 量化：模型侧的最后一步，动手前必须先有质量基线（顺序理由见 §3.2.4）
from awq import AutoAWQForCausalLM
from transformers import AutoTokenizer

model = AutoAWQForCausalLM.from_pretrained(model_path)
tokenizer = AutoTokenizer.from_pretrained(model_path)
model.quantize(tokenizer, quant_config={"zero_point": True, "q_group_size": 128})
model.save_quantized(quant_path)

# ② 推理：交给推理引擎做连续批处理，而不是自己把整批凑齐再解码
from vllm import LLM, SamplingParams

llm = LLM(
    model=quant_path,
    tensor_parallel_size=4,
    gpu_memory_utilization=0.9,
    enforce_eager=False,   # 关闭逐步执行，启用 CUDA Graph 降低内核启动开销
)
outputs = llm.generate(prompts, SamplingParams(temperature=0.7, max_tokens=100))
```

**怎么用**：`tensor_parallel_size` 与 `gpu_memory_utilization` 两格必须按你自己的卡数与显存实测填——照抄会 OOM 或留下大量闲置显存；`gpu_memory_utilization` 留出的余量是给 KV Cache 的，调满会让并发一上来就出现拒绝或抢占。量化那一段只在质量基线已建立、且评测能定期回归时跑：量化误差不体现在报错、超时或延迟上，只体现在输出分布上（4.2 的失效条件）。`enforce_eager=False` 一格对应 4.2 的图捕获：它要求计算图形状稳定，请求长度分布很散时应先在小流量上对比打开前后的 TTFT 再决定是否保留。参数名与默认值以所用库与推理引擎的官方文档当前版本为准。

**模板六：边缘终结 HTTP/3 与 0-RTT（反向代理片段）**

```nginx
# 边缘终结 HTTP/3 + TLS 1.3；0-RTT 只对幂等请求放开
server {
    listen 443 quic reuseport;
    listen 443 ssl http2;
    add_header Alt-Svc 'h3=":443"; ma=86400';
    ssl_protocols TLSv1.3;
    ssl_early_data on;
}
```

**怎么用**：`ssl_early_data on` 只应对幂等请求放开，且必须在上游做重放防护——0-RTT 的请求可被重放，这是它唯一的代价。`listen ... quic` 需要边缘的 UDP 端口在安全组与会话保持上放通，否则客户端协商失败后会悄悄退回 HTTP/2，而总体指标上看不出区别；上线前后要**按网络类型分组**比对协商成功率（4.2 的观测信号）。`Alt-Svc` 的 `ma` 是缓存时长，填得过长会让回滚变慢。

### 4.6 自检清单

- [ ] 有没有一份端到端基线（同场景、同数据规模、P99 口径一致）？它最近一次更新是哪天？
- [ ] 当前瓶颈是**哪一类资源**（CPU / 内存 / IO / 网络 / 显存）？依据的是哪一次测量？
- [ ] 验收口径是 P99 还是均值？报表里只出现均值时，长尾是谁在看？
- [ ] 最近一条慢 SQL 的**扫描行数与返回行数之比**是多少？治理了吗？
- [ ] 每一处缓存能否回答「谁失效、何时失效、失效失败怎么办」？答不出的有几处？
- [ ] 有没有「写后立即读」读到旧值的工单？是修了，还是用「刷新一下」应付过去了？
- [ ] 链路上是否存在跨层失效（本地缓存 + 分布式缓存 + CDN）？失效通知路径写在哪份文档里？
- [ ] 每一次性能改动都有端到端前后对比吗？没有对比的改动还有几处留在代码里？
- [ ] 压测的数据规模与分布与生产同量级吗？压测有没有压到延迟拐点？
- [ ] 如果用了量化 / 蒸馏：质量基线是什么、由谁在看、多久回归一次？
- [ ] 自动扩缩容 / Self-Tuning 有没有上下限、冷却时间与**一键停用**？上次停用演练是什么时候？
- [ ] 上一次性能回归是告警先发现的，还是用户投诉先发现的？告警触发后能否定位到某次发布？

### 4.7 小结

> 本节小结：五步里唯一不能省的是 **Step 1「建基线并定义 SLO」**——它不产出任何功能，却决定了后面四步能否被验收：没有基线，瓶颈定位无法证伪、优化效果无法归因、压测结论无法比较、回归告警无处可依。它比其余环节更值得投入，是因为**它把「快不快」从感受变成了同一口径下的两个数字**：口径一旦固定，争论的对象就从「优化有没有用」移到了「改的是不是瓶颈」上，后面所有环节的返工量才会下降。
>
> 💡 **思考锚点**：§4.6 第一问——「有没有一份端到端基线，最近一次更新是哪天」——你现在答得上来吗？若答不上，先做 §4.1 的 Step 1：把当前瓶颈归到 §4.2 的资源类（CPU / 内存 / IO / 网络 / 显存）里的哪一类，依据的是哪一次测量？再挑一条你正准备做的优化（如缓存或量化），对着 §4.2 的失效条件读一遍：它的失效是报错，还是静默地落在输出分布与长尾上？
