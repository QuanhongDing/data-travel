## 3. 设计模式与范式

> 本主题更早的一版内容共 93 行：列出 5 个模式（全链路分析 / 分层优化 / 缓存金字塔 / AI 推理优化 / Self-Tuning）、1 张 7 行适用场景表与 5 条反模式。其中模式 1（客户端到 DB 的逐跳链路图）与模式 3（缓存金字塔的堆叠图）各配有一段 ASCII 结构示意，模式 2、4、5 则只有要点罗列；整体缺的是机制解释与失效分析。本节按「约束 → 结构 → 机制 → 代价 → 失效点」逐条展开。

### 3.1 先看约束：模式不是选择题，是约束的产物

性能优化最常见的失败不是「选错了手段」，而是**在一个不该优化的地方用了正确的手段**。因为性能有两个底层定律在同时约束所有手段：**Amdahl 定律**决定「优化非瓶颈部分的收益上限」，**Little 定律**决定「延迟与并发之间的换算关系」（两条定律的形式与本章主文件 §2.2 给出的公式一致）。任何模式只有在它作用的那个环节真的是瓶颈时才有收益，这一点由约束决定，不由模式本身决定。

约束的第一条是**延迟预算**。一次请求能容忍的端到端时间有限，而这个预算要在所有同步跳之间瓜分：跳数越多，每一跳分到的预算越少，任何一跳的抖动都会吃掉别人的余量。所以「加一个中间层」这类在功能上毫无代价的动作，在性能上永远是先借后还——借的是延迟预算，还的是长尾。

约束的第二条是**瓶颈资源类型**。CPU、内存带宽、磁盘 IO、网络 RTT、GPU 显存带宽，五者对应的优化手段几乎不重合：CPU 密集靠算法与 JIT，IO 密集靠批处理与索引，GPU 密集靠批与显存管理。**判断错了瓶颈类型，再好的手段也只是把资源花在了不是瓶颈的地方**——这正是阿姆达尔定律在工程上的形态。

约束的第三条是**负载形态**。稳态流量可以用均值做容量决策，突发流量必须看排队论下的瞬时并发，而长尾请求（慢查询、冷缓存、GC 停顿）则完全由 P99/P999 决定。同一套系统在三类负载下的正确模式不同：稳态靠调优，突发靠弹性与限流，长尾靠隔离与降级。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 延迟预算与同步跳数 | 系统能承载多少跳、每跳能分多少时间 | 「多加一层缓存/网关没坏处」——每一跳都要从预算里扣时间，并叠加自己的长尾 |
| 瓶颈资源类型（CPU / 内存 / IO / 网络 / GPU） | 该用哪一类优化手段 | 「加机器就能解决」——若瓶颈是单点串行或锁，扩容只增加排队 |
| 负载形态（稳态 / 突发 / 长尾） | 容量、弹性与降级策略 | 「看平均值做容量规划」——均值达标而 P99 爆掉是常态 |
| 一致性与正确性容忍度 | 缓存与异步化能走多远 | 「缓存能提速就上」——收益是延迟，代价是读到的可能不是最新值 |
| 成本约束（单位请求成本） | 优化的目标函数是延迟还是单位成本 | 「越快越好」——把 P99 从 50ms 压到 20ms 的边际成本常远高于它带来的收益 |
| 可观测能力（能否定位到跳） | 优化能否闭环 | 「先优化再监控」——没有基线，改动后的涨跌无法归因，只能靠感觉 |

**读这张表的方式是找当前真正收紧的那一条**：早期系统通常只被「延迟预算」和「瓶颈类型」约束住；一旦有了成本和合规压力，「一致性容忍度」和「单位成本」会同时收紧，而这两条恰好是缓存与异步化最敏感的地方。

还有一条容易被漏掉的约束：**延迟与吞吐在这条链路上是可调换的**。批处理、合并请求、加大缓冲区都能提高吞吐，代价是单个请求排得更久；反过来说，把批大小调小、把缓冲区调浅，延迟会好看，但单位成本上升。**任何优化方案如果不说明它站在延迟一侧还是吞吐一侧，就无法被验收**——因为两侧的指标永远一涨一落。

### 3.2 模式逐个拆解

先横向看三类优化动作的取舍——下面五个模式都是这张表的某一种配比：

| 优化动作 | 它改变的是什么 | 见效速度 | 天花板 | 主要风险 |
| --- | --- | --- | --- | --- |
| 减少工作量（算法、索引、批处理） | 每请求消耗的资源量 | 中：需要先定位 | 高 | 需要理解业务与数据分布 |
| 避免重复工作（缓存、预计算） | 实际到达后端的请求数 | 快 | 受命中率上限约束 | 一致性与失效面 |
| 增加并行（扩容、并发、异步） | 单位时间的处理能力 | 快 | 受串行部分限制（Amdahl） | 掩盖瓶颈、放大下游压力 |

**这三类动作的作用点不同，不能互相替代**：减少工作量把成本从系统里拿掉，避免重复工作把请求从系统里摘掉，增加并行把压力摊到更多资源上。前两类的收益是**结构性**的（做一次长期有效），第三类的收益是**租来的**（资源涨价即失效）；**先做结构性优化、再做租用式扩容**，是成本效率上唯一稳定的顺序。

#### 3.2.1 全链路性能分析

- **被什么约束逼出来**：系统由多跳组成（客户端 → CDN → 网关 → 应用 → 缓存 → DB），单看任何一跳都「正常」，但端到端就是慢——必须把延迟按跳拆开。
- **结构**：每一跳各自记录耗时与饱和度，而不是只记录一个端到端数字。

```text
客户端 ──► CDN ──► API 网关 ──► 应用层 ──► 缓存 ──► 数据库
   │         │          │           │          │         │
  RTT     缓存命中率    网关耗时    CPU / 内存  缓存命中率  SQL 耗时 /
  DNS      回源率       排队时长    GC 停顿     QPS       行数 / 索引命中
   │         │          │           │          │         │
   └─────────┴──────────┴─────┬─────┴──────────┴─────────┘
                             ▼
                    端到端 trace（同一 trace id 串起所有跳）
                             ▼
        定位结论：时间花在哪一跳？是耗时增加，还是排队增加？
```

- **为什么这样设计有效**：因为延迟是**各跳之和加排队时间**，把每一跳的耗时与队列长度都记为独立指标后，「慢」这个模糊感受就被分解成「某一跳的耗时涨了」或「某一跳前面的队列变长了」这两类可证伪的判断——前者改代码，后者改容量，两者是完全不同的动作。
- **代价**：每一跳都要有埋点，埋点本身消耗 CPU 与网络；跨团队链路要求所有服务采用同一套上下文传播规范，任何一跳没接上，trace 就断在那里，而断了以后排查手段会退回到猜。**这是一条需要长期投入的基建，不是一次接入。**
- **失效点**：当 QPS 很高、而 trace 数据是全量同步上报时，全链路分析的**「看得清」会反转成「新的瓶颈」**，因为埋点与上报本身就在关键路径上消耗 CPU 与网络；典型症状是开了追踪之后整体 P99 上升，团队于是把采样率一降再降，最后采样率低到长尾请求根本采不到——而长尾恰恰是最需要它的时候。
- **真实使用**：链路追踪（Jaeger / Zipkin / SkyWalking）、火焰图（perf、eBPF）、APM（本章主文件 §2.3 列出的工具链）都是这一模式的不同形态；OpenTelemetry 把上下文传播与指标语义标准化，使跨组件对齐成为可能（【公开】CNCF OpenTelemetry 项目，Trace 规范 1.0 发布于 2021 年；语义约定另有独立版本号并持续演进，请以 opentelemetry.io 的当前文档为准）。
- **落地提示**：采样策略要按「长尾是否被采到」来设计，而不是按「总量是否够小」——对慢请求做**按延迟触发的补充采样**（慢的必留、快的抽样），才能在控制开销的同时保住长尾的可见性【经验】。

#### 3.2.2 分层优化

- **被什么约束逼出来**：同一份延迟预算分布在若干层上，而每一层的天花板由不同资源决定——不知道当前哪一层先到顶，优化就没有方向。
- **结构**：把系统切成层，逐层列出「可做的手段」与「该层受什么资源限制」。

```text
层              可做的手段                        本层受限于
──────────────  ────────────────────────────────  ──────────────────────
前端 / 边缘     CDN 缓存、资源合并压缩、懒加载      带宽与 RTT
网络 / 协议     HTTP/2 多路复用、HTTP/3+QUIC、     往返次数与队头阻塞
                gRPC、TLS 1.3 握手、连接复用
应用            JVM / GC 调优、算法与数据结构优化、   CPU、GC 停顿、锁竞争
                异步化、批处理、线程/协程模型
数据            索引、执行计划、读写分离、分区分片、  IOPS、单机数据量、锁
                冷热分层、列存与向量化执行
────────────────────────────────────────────────────────────────────
规则：先测量，确定哪一层先到顶，只优化那一层；
      其余层的优化即使做对了，也只是把天花板挪给下一层。
```

- **为什么这样设计有效**：因为各层的约束资源不重合，**先定位层、再选手段**可以避免在非瓶颈层做无用功；而 Amdahl 定律给出了量化理由——若可优化部分只占整体时间的一小部分，即使把它优化到零，端到端加速比也有上限（本章主文件 §2.2 给出的算例：可并行部分 0.8、并行加速 10 倍时，加速比约 3.57 倍，而不是 10 倍）。
- **代价**：分层后天然出现**局部最优与端到端无改善并存**的场面；同时每层都要独立的监控与容量模型，运维面随层数增长；分层还容易掩盖跨层问题（例如应用层批处理把压力集中到数据库的瞬时峰）。
- **失效点**：当被优化的层不是当前瓶颈层时，分层优化的**「方向清晰」会反转成「投入越大、端到端越没变化」**，因为整个链路的加速上限由**未被优化的那一层**决定——工程上常见的形态是花几个月把应用层 RT 压掉一半，端到端 P99 却几乎不动，因为时间其实花在数据库的锁等待上。
- **真实使用**：这一模式在工程上几乎是默认做法——本章 §6 的四个案例都按「背景 → 触发点 → 详细做法 → 具体数字 → 失败教训」组织，其「详细做法」下的 5 大核心组件里，JVM / GC 调优与多级缓存两项四个案例都有；其余三项组成为：阿里与美团这一组相同（数据库读写分离 / 分库分表、限流 + 削峰、全链路压测），字节是消息队列削峰、限流 + 削峰与灰度发布，Netflix 是 CDN、自适应码率与压测 + 监控。可见本节这张表的四层（前端 / 边缘、网络 / 协议、应用、数据）只覆盖了其中一部分手段——限流削峰、压测监控、灰度发布这类横切件，以及自适应码率这类业务侧手段，都不落在任何一层，网络 / 协议层在四个案例里也没有独立代表；**真实案例的做法是把分层手段与横切保护叠在一起用，而不是只优化一层**。具体的分层手段（HTTP/2、HTTP/3、TLS 1.3、零拷贝、连接池）各自有公开规范可查（【公开】HTTP/2 见 RFC 7540 / 9113，HTTP/3 见 RFC 9114（2022），TLS 1.3 见 RFC 8446（2018））。
- **落地提示**：每完成一层优化，都要**重新测一次端到端**再决定下一层——因为瓶颈会随优化移动，上一轮测出的瓶颈在下一轮多半已经不是瓶颈，凭印象继续优化同一层是最常见的浪费【经验】。

#### 3.2.3 缓存金字塔

- **被什么约束逼出来**：后端的处理能力远低于、而延迟远高于内存读取，而请求中相当大的比例在短时间内是重复的——重复的部分不需要重新计算。
- **结构**：按「离用户越近越快、但越难失效」的顺序叠多层，每层只解决自己那一层的重复。

```text
        浏览器 / 客户端缓存      ← 最快，失效最不可控
      CDN / 边缘缓存             ← 就近命中，按路径与 TTL 失效
    应用进程内缓存（Caffeine 等）← 纳秒级，进程重启即失效，多实例不一致
  分布式缓存（Redis 等）         ← 毫秒级，多实例共享，需要失效通道
 数据库自身的缓存 / 物化视图      ← 与数据同源，失效最可靠
数据源（DB / 对象存储 / 湖）      ← 真相所在
```

```text
读路径（Cache-Aside，最常用的形态）：
  读 → 命中本层？→ 是：返回（注意：返回的可能是旧值）
                → 否：向下一层读 → 回填本层 → 返回
写路径：先写数据源，再失效缓存（先失效、后写，或先写、后失效，
        两种顺序在并发下各有窗口，必须按业务选择并写进文档）
```

- **为什么这样设计有效**：因为每一层的读延迟相差数量级，把请求尽可能拦在离用户最近的层，等价于把绝大部分请求从最慢的一层上摘下来；而命中率对后端负载的影响是**乘性**的——命中率从 90% 提到 99%，到达后端的请求量降到原来的十分之一（【推算】命中率 h 时后端负载 = 总请求 ×(1−h)）。这就是它在高 QPS 场景里收益最高的原因。
- **代价**：**失效面随层数线性增长**——一份数据要在 N 层上失效，任何一层漏掉就产生不一致；多实例本地缓存无法互相通知，只能靠短 TTL 或广播通道；此外必须处理穿透（查不存在的数据）、击穿（热点 key 过期瞬间）、雪崩（大批 key 同时过期）三类问题，这三类都是命中率被推到很高之后才会暴露的**结构化风险**。
- **失效点**：当**写频率升高**或**一致性要求变严**（例如刚写入就必须可读）时，缓存的**「降低后端负载」会反转成「读到旧值」**，因为缓存的失效是**跨层异步**的、每一层各自有自己的 TTL 与通知路径，中间必然存在不一致窗口；窗口的宽度不取决于单层实现好不好，而取决于层数与通知链路长度。
- **真实使用**：浏览器与 CDN 缓存的语义由 HTTP 缓存规范定义（【公开】RFC 9111 的 HTTP Caching，2022 年版）；进程内缓存多用 Caffeine（采用 W-TinyLFU 淘汰策略；该策略源自 TinyLFU 论文，【公开】Einziger、Friedman、Manes 等《TinyLFU: A Highly Efficient Cache Admission Policy》，2014，可按论文标题检索核对，实现细节以项目仓库当前版本为准）；分布式缓存多为 Redis。本章 §6 的四个案例里，缓存都不单独承担峰值：阿里「双 11 性能 7x」、字节「抖音春晚 5 亿+ 互动」与美团「外卖 100 万单/小时」三个案例把它与「限流 + 削峰」并列在 5 大核心组件里，Netflix「2 亿+ 用户 P99 < 200ms」案例则把它与 JVM 调优、CDN、自适应码率、压测 + 监控并列——**缓存前面总要有挡住洪峰的那一层，它只负责减少重复读，不负责吸收突发**。
- **选型提示**：TTL 是最粗但最可靠的失效手段。**给不出失效通道时，就用短 TTL 换正确性**——代价是命中率下降，收益是不需要跨层通知（【经验】）。
- **本地缓存与分布式缓存的分界**：进程内缓存的读延迟最低，但**无法被其他实例失效**，所以只适合「能容忍陈旧、且过期后重建代价低」的数据（字典、配置、维度表）；一旦数据是「刚被某个实例写过、另一个实例必须立刻看到」，就必须落到有失效通道的分布式缓存，或干脆不缓存（【经验】）。
- **最下面那一层（数据库自身的缓存）的现状**：MySQL Query Cache 在 MySQL 8.0 中已被移除（【公开】MySQL 8.0 发行说明的「已移除特性」，可按关键词自行检索核对）——因为它的失效粒度是**整表**，任何一次写入都会清掉该表全部缓存项，写频率一上去就退化成纯开销。如今这一层通常由物化视图或应用侧结果缓存承担，它们保住的是「与数据同源、失效最可靠」这个性质，代价是刷新存在延迟。

#### 3.2.4 AI 推理优化

- **被什么约束逼出来**：推理成本由 GPU 显存与显存带宽主导，而传统性能工程的手段（加索引、减 IO 次数）在这里基本失效；同时又必须在不重训的前提下降低单位 token 的成本。
- **结构**：三层手段叠加——模型侧压缩、服务侧批处理、显存侧管理。

```text
模型侧（改变模型本身）        服务侧（改变请求调度）      显存侧（改变内存布局）
──────────────────────────  ────────────────────────  ─────────────────────────
量化 FP32 → FP16 / INT8 / INT4  连续批处理（请求不等      KV Cache：缓存注意力中间量
剪枝 去掉低贡献参数              整批凑齐，边解码边补位）   PagedAttention：把 KV Cache
蒸馏 大模型 → 小模型            请求排队 + 抢占 + 调度      分页管理，减少碎片
──────────────────────────────────────────────────────────────────────────────
度量口径：TTFT（首 token 延迟）、TPOT（每 token 时间）、
          吞吐（tokens/s）、显存占用、单位请求成本
关键：延迟与吞吐在这条链路上是**可调换**的——
     加大批处理提高吞吐，但会抬高单请求的 TTFT。
```

- **为什么这样设计有效**：因为自回归解码的瓶颈是**显存带宽而不是算力**，每一步都要读一遍权重与 KV Cache；连续批处理与分页显存管理让显存在请求之间被更充分地复用，等价于在同样的硬件上把「每 token 的成本」摊薄——这是吞吐提升的主要来源，而不是靠更快的算子。
- **代价**：量化与蒸馏都会**改变输出分布**，而且回退通常是静默的（不报错、只是变差）；连续批处理把不同请求绑在一起，任何一个请求的异常都会影响同批其他请求的尾延迟；TTFT 与吞吐互为代价，任何一方的好看数字都可以用调另一个换来。
- **失效点**：当任务对精度损失敏感（细粒度分类、长尾语言、需要精确数字或格式的生成）时，量化的**「单位成本下降」会反转成「质量回退且无告警」**，因为量化误差不体现在报错或超时上，而体现在输出分布上——延迟指标全部正常，业务指标悄悄下滑。**所以量化的正确前置条件是先建立质量评测基线，而不是先建吞吐基线。**
- **真实使用**：连续批处理由 Orca 提出并被主流推理引擎采用，vLLM 的 PagedAttention 是其中被引用最广的显存管理方案（【公开】Kwon 等《Efficient Memory Management for Large Language Model Serving with PagedAttention》，SOSP 2023；《Orca: A Distributed Serving System for Transformer-Based Generative Models》，OSDI 2022）；TensorRT-LLM、ONNX Runtime 是常见的推理运行时；vLLM 的调用示例见本章 [§ 4 工程实现](05-performance-engineering-section-4-sec4.md) 的 §4.2「AI 推理优化（vLLM）」，而主文件 §2.3 只是把 vLLM 连同连续批处理、PagedAttention 一起列为「AI 推理优化」的条目之一。
- **手段的叠加顺序**：先做**服务侧**（连续批处理、调度），再做**显存侧**（KV Cache 分页管理），最后才做**模型侧**（量化、蒸馏）。理由是前两者不改变模型输出，风险最低且收益立即可测；模型侧的改动必须伴随质量基线，成本最高。顺序反过来做，就会在没有质量基线的前提下先承担了最大的回退风险【经验】。

#### 3.2.5 Self-Tuning

- **被什么约束逼出来**：参数空间大（GC、连接池、并发度、副本数、批大小），而人工调参的速度赶不上流量形态的变化——调完的第二天负载就换了。
- **结构**：把「测量 → 决策 → 施加 → 再测量」做成闭环，并显式规定边界与人工兜底。

```text
   ┌─────────────┐   指标（P99 / 饱和 / 队列长度）
   │  观测        │◄──────────────────────────────┐
   └──────┬──────┘                               │
          ▼                                      │
   ┌─────────────┐   规则 / 模型给出的    ┌──────┴──────┐
   │ 决策         │──► 候选参数变更 ──────►│  施加        │
   └─────────────┘                         └──────┬──────┘
          ▲                                       │
          │  边界：上下限、变更幅度、冷却时间、      │
          └── 变更窗口、可回滚、超范围需人工确认 ◄──┘
   ────────────────────────────────────────────────────
   自动化程度越高的环节，越需要一个「停止自动」的开关。
```

- **为什么这样设计有效**：因为性能参数与负载之间是**时变关系**，一次性调参给出的是一张过期快照；闭环把「参数是否仍然合适」变成持续被回答的问题，尤其适合有明显日周期与周周期的业务。
- **代价**：自动决策需要可信的指标——指标抖动会直接变成参数抖动；变更本身有风险，因此必须带上下限、冷却时间与回滚；此外它**降低了系统的可解释性**：出问题时没人知道当前参数是从哪个历史状态漂移来的，需要额外的变更审计。
- **失效点**：当系统进入**训练/规则里没出现过的工作负载**（大促、突发事件、灰度新功能）时，Self-Tuning 的**「省人且反应快」会反转成「参数与负载错配且无人能解释」**，因为反馈环依赖历史指标，而反馈本身有滞后——滞后的调节会振荡：扩容触发得比流量上升晚，流量回落时又在扩，最终表现是资源用量反复波动、P99 比手动固定参数时更差。
- **真实使用**：JDK 自身的自适应行为（自适应堆、GC 自适应参数）是「内置自调优」的长期形态（【公开】OpenJDK 官方文档与 JEP：JEP 248 使 G1 成为默认 GC（JDK 9），JEP 333 引入实验性 ZGC（JDK 11），JEP 439 引入分代 ZGC（JDK 21）；参数与默认值随版本变化，请以所用 JDK 版本的 `java` 命令文档为准）；云上的自动扩缩容是工程上使用最广的自调优形态；数据库侧的自动 SQL 优化（按执行计划自动重写、索引推荐）同属这一族的「内置自调优」，只是它的施加环节通常还留着一道人工评审（【经验】）；AI 辅助调优（用模型分析瓶颈并给出候选方案）目前多数停留在**建议**而不是**自动施加**【经验】。
- **自动化的分界线**：把「参数调整」自动化，但把「参数上限」保留给人——因为自动化的收益是响应速度，风险是无人理解的漂移；上限是人能兜住风险的那一层。**没有上限的自调优，本质上是把一次事故的概率换成了一类事故的概率**【经验】。

**五个模式的「代价 → 失效点」对照**（选型速查，不是结论）：

| 模式 | 它买到的东西 | 它必然付出的代价 | 代价开始反噬的信号 |
| --- | --- | --- | --- |
| 全链路分析 | 能定位到跳，而不是靠猜 | 埋点开销 + 全链路规范化改造 | 开了追踪之后 P99 上升，采样率被迫一降再降 |
| 分层优化 | 方向清晰、各层各管一段 | 局部最优，运维面随层数增长 | 某一层投入很大，端到端曲线几乎不动 |
| 缓存金字塔 | 后端负载成倍下降 | 跨层失效面 + 三类结构性风险 | 写后读不一致的工单开始出现 |
| AI 推理优化 | 单位 token 成本下降 | 输出分布改变且静默 + TTFT 换吞吐 | 延迟指标全绿而业务指标下滑 |
| Self-Tuning | 参数跟上负载变化 | 可解释性下降 + 反馈滞后 | 资源用量反复波动，比固定参数更差 |

注意最后一列全部是**信号**而不是**故障**：代价反噬时系统仍在正常运行，只是开始悄悄产生错误结论——延迟达标但读到旧值、吞吐上升但质量下滑、参数还在自动调但已经调错了方向。这也解释了为什么本节把「失效点」单独列一栏：它描述的不是崩溃，而是**优点在某个条件下变成缺点的那一刻**。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 端到端慢，但单跳指标都「正常」 | 全链路分析（3.2.1） | 不要先动缓存：不知道时间花在哪一跳，任何改动都无法归因 | 是否有同一 trace id 串起来的跨跳耗时 |
| 明确知道瓶颈是某一条慢 SQL | 数据层优化 + 索引/执行计划（3.2.2 的数据层） | 不要先加缓存：缓存会把问题掩盖到某个不可预期的时刻集中爆发 | `EXPLAIN` 后的扫描行数与返回行数之比 |
| 读多写少、能容忍短暂旧值 | 缓存金字塔（3.2.3） | 不要上多级：层数越多失效面越大，先证明单层不够用 | 读写比，以及「写后立即读」的业务占比 |
| 写多、且刚写入必须可读 | 数据层优化 + 减少写放大（3.2.2） | 不要指望缓存：一致性要求把缓存收益压到负值 | 写后立即读的比例与容忍延迟 |
| 数据量极大、查询以扫描 + 聚合为主（数据分析类负载） | 列存 + 向量化执行 + 索引（3.2.2 的数据层） | 不要先加缓存：扫描型负载每次都要读全量列，缓存只挡得住重复的那部分，而这类负载的重复率本来就低 | 点查与扫描的比例；`EXPLAIN` 中的扫描行数是否本就接近返回行数（接近则说明慢在「本就要读这么多」，不是缺索引） |
| 数据持续流入、要求秒级到分钟级可见（实时流处理） | Flink + 状态后端优化（3.2.2 的数据层，按流式负载改造） | 不要套用批处理的调参思路：批的瓶颈是吞吐，流的瓶颈是状态大小与 checkpoint 时长 | 状态后端大小 / checkpoint 时长 / 反压指标 |
| GPU 推理成本是主要支出 | AI 推理优化（3.2.4） | 不要先做服务侧扩容：先证明单位成本能降，再谈买卡 | 单位 token 成本 / 显存利用率 / TTFT 与吞吐的取舍点 |
| 大促 / 秒杀类瞬时高压 | 缓存金字塔（3.2.3）+ 限流 / 降级作为前置保护 | 不要只靠扩容：弹性有启动延迟，瞬时峰值永远快过扩缩容 | 从触发扩容到实例可用的时间 vs 峰值的上升时间 |
| 高 QPS Web 服务（流量大、每毫秒都影响转化） | 全链路分析（3.2.1）+ 多级缓存（3.2.3） | 不要只加缓存：不知道时间集中花在哪一跳，层数再加上去也只是把时间花在本就不是瓶颈的层 | 端到端 P99 与各跳耗时占比 |
| API 服务、调用方并发高、单次响应小 | 协议层优化（HTTP/2 多路复用、连接复用、TLS 1.3）+ 异步化 + 单层缓存（3.2.2 的网络 / 协议与应用层） | 不要只靠扩容：握手与往返是每个请求都要付的固定成本，加机器摊不掉它 | 单请求的往返次数与连接复用率 |
| 负载有明显周期、参数频繁失配 | Self-Tuning（3.2.5），且必须带边界与开关 | 不要全自动无上限：反馈滞后会导致振荡 | 指标的采集周期是否明显短于负载变化周期 |

**最常被误选的一对是「缓存金字塔」与「数据层优化（索引 / SQL）」**，误选方向几乎总是**先加缓存**。原因不是不懂缓存有代价，而是缓存的收益当天就能在曲线里看到，而修一条 SQL 要先承认「数据库存在慢查询」这一事实。后果是慢查询被缓存挡住，直到缓存穿透、缓存重建或数据量跨过某个阈值时集中爆发——**缓存不是消除了慢，而是把慢推迟到了它最不方便出现的时刻**。判据只有一条：**先看 `EXPLAIN`，再看命中率**；扫描行数远大于返回行数的查询，缓存只会延长它的寿命。

**第二常被误选的一对是「分层优化」与「增加并行（扩容）」**（后者即 3.2 开头表里的第三类动作），方向通常是**用加机器替代定位**。扩容见效最快、风险最低，因此最容易成为默认动作；但它的收益受阿姆达尔定律约束——若瓶颈是一段串行逻辑、一把锁或一个单点，加机器只会让更多请求排在同一处，平均延迟不变而排队时间上升。判据是：**扩容后的曲线有没有改善**。若扩了两轮而端到端没动，瓶颈一定不在并行度上。

**第三类误选发生在 AI 推理上：用「更多副本」替代「更省显存」**。加副本能提高吞吐，但每个副本都要独占一份权重与 KV Cache，单位成本不降反升；而连续批处理与显存分页管理恰恰是在**同样的卡上**提高单位产出的手段。判据是单位 token 成本，而不是每秒请求数。

### 3.4 组合模式：真实系统不会只用一种

**组合 1：全链路分析 + 分层优化 + 持续监控（APM / OpenTelemetry）**

- **职责边界**：分析负责「问题在哪一跳」，分层优化负责「那一跳该动什么」，监控负责「改完有没有回归」——三者构成一个闭环，缺任何一个都会退化成拍脑袋。
- **运维代价**：埋点与采样策略要长期维护；跨团队的上下文传播规范一旦不统一，链路就会断在最需要它的地方；监控指标本身要控制基数，否则指标系统会先于业务系统撑不住。
- **适合规模**：服务数超过十几个、调用链跨团队、已经有明确 P99 目标的系统。

**组合 2：缓存金字塔 + 数据层容量（读写分离 / 分区分片 / 冷热分层）**

- **职责边界**：缓存解决「重复读」，数据层容量解决「不重复的量也扛不住」——两者解决的是不同问题，不能互相替代。缓存把请求摘掉一部分，但剩下的那部分（穿透、写入、失效后的重建）必须由数据层自己扛住。
- **运维代价**：缓存层要有失效通道与熔断；数据层要有分片键与再平衡方案；两者叠加后**故障模式变多**——缓存挂了会打穿数据库，数据库慢了会让缓存重建变慢，联动故障比单点故障更难排查。
- **适合规模**：读远大于写、且单库已经接近容量或 IOPS 上限的系统。

**组合 3：AI 推理优化 + 缓存（Prompt / KV）+ Self-Tuning（弹性扩缩容）**

- **职责边界**：推理优化降低单位成本，缓存减少重复计算（相同前缀、相同 Prompt），自调优按流量调整实例数——一个管单位成本，一个管重复，一个管总量。
- **运维代价**：三者叠加后**延迟与吞吐的取舍点会随流量漂移**，必须持续校准；同时质量评测基线要作为一等公民维护，否则量化的静默回退会在业务指标上先被发现，而不是在性能指标上。
- **适合规模**：推理成本已经进入单位经济模型的团队（即：单位 token 成本直接影响毛利）。

**三个组合共享同一个前提**：**先有基线，再谈优化**。没有基线，组合里的任何一环出问题时都无法判断是「优化失效」还是「流量变了」；这也是 3.7 自检清单第一条必须是「有没有基线」的原因。

另一个共同前提是**故障域的隔离**：三个组合里每一个都把「快」建立在一个额外的组件上（追踪、缓存、自适应扩缩容），而额外组件本身就是新的故障源。组合越多，越需要回答同一个问题——**这个新组件挂掉之后，系统是变慢还是不可用**；只能变慢的可以进关键路径，会导致不可用的必须放在旁路。

### 3.5 反模式与失效分析

五条反模式里，**过早优化**与**只看均值**是方法错误，**忽视数据库**与**缓存滥用**是判断错误，**忽视 AI 推理特殊性**是经验迁移错误——三类成因不同，修法也不同。**尤其要注意最后一条**：它不是「AI 系统独有的坑」，而是**任何一次技术栈更换都会重演的坑**——上一代最有效的手段会被不加检验地带到新形态上，而新形态的瓶颈资源早已换了类型。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **过早优化** | 优化做在非瓶颈处；改动前后端到端曲线几乎重合；代码为性能变得难懂却说不清收益 | 按 Amdahl 定律，非瓶颈部分的收益上限极低，投入换不来端到端改善，却永久增加了维护成本 | 性能问题带着情绪（用户投诉、领导关注），优化动作是最容易展示的回应 | 先 profile 找瓶颈，再用**端到端指标**验证收益；无验证的优化一律回滚 |
| **只看均值** | 平均延迟达标、P99 是均值的几十倍；容量按均值规划却频繁超时 | 排队系统的尾部由并发与队列决定，均值达标时尾部的用户已经在超时；按均值定容量会系统性低估所需资源 | 均值是最容易拿到的数字，也是报表里默认展示的数字 | 以 P95/P99/P999 为验收口径，并对长尾单独定位（慢查询、GC 停顿、冷启动） |
| **忽视数据库** | 应用层缓存层层加码，但数据库侧仍存在扫描行数远超返回行数的查询 | 数据库是链路上的串行资源，其尾部延迟会直接进入端到端；缓存只是把它挡住，挡不住的那部分照旧 | 应用层改动自主可控，数据库改动要过 DBA、要评估影响面，于是被推迟 | 把慢查询治理当成常规工作：`EXPLAIN`、索引、执行计划回归；数据库是必须优先处理的瓶颈点 |
| **缓存滥用** | 为「提速」加的缓存说不清失效时机；写后读不一致的工单反复出现 | 一致性问题被延迟暴露：平时读到的都是旧值但没人发现，一旦有人据此做决策就变成正确性问题 | 缓存的收益立刻可见，一致性代价延迟且分散 | 缓存必须写清「谁失效、何时失效、失效失败怎么办」；给不出失效通道就用短 TTL |
| **忽视 AI 推理特殊性** | 用 CPU 时代的思路（更快算子、更多副本）优化 GPU 推理；只报吞吐不报质量 | GPU 推理受显存带宽约束，加副本与换算子都无法改变单位成本的结构；量化带来的质量回退不体现在延迟指标上 | 传统性能工程的经验很成功，直接迁移到新形态上 | 用 GPU 侧口径度量（显存、TTFT、TPOT、tokens/s），并把质量评测作为量化的前置条件 |

**最危险的三条**：

**「只看均值」**在生产中的典型暴露方式是**容量规划失准**。按平均 QPS 与平均响应时间做容量（Little 定律下的稳定态估算），看起来余量充足；但真实流量是尖峰的，而排队是非线性的——并发接近处理能力时，队列长度与等待时间的增长远快于流量增长，于是 P99 断崖式上升，而均值指标全程平稳。它的危险在于**报表全绿**。

**「缓存滥用」**的暴露方式是**静默错误**。不一致窗口内读到的旧值不会报错、不会超时、不会进告警；它只会在某次对账或某个用户投诉里被发现，而那时已经无法回溯影响范围。它的危险在于**正确性问题被记在性能账上**。

**「忽视数据库」**的暴露方式是**优化收益不断被吃掉**。应用层每优化一次，曲线好一阵，然后数据库的负载又涨回来；团队反复在应用层加码，直到某天缓存重建把数据库打穿，才第一次认真看那条慢查询——它可能已经存在很久，只是从未被当成瓶颈处理。

**三条的共同点是：出问题时没有任何一个性能指标报警。**判断自己是否已经踩上，只需要做一个动作——**任选一次「优化完成」的改动，问它三个问题**：优化的是不是当时测出来的瓶颈？改完有没有端到端前后对比？这条改动的收益能用一个资源量（CPU / IO / 请求数 / 显存）说清楚吗？三个问题里有任何一个答不上来，那次改动就更接近反模式而不是优化。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单机 → 多实例 | JVM 调优 + 单机优化 | 单机参数不再决定整体容量，实例间不一致成为新问题 | 无状态化 + 负载均衡 + 统一的实例级指标 | 需要把本地状态外移，改造成本与回归面都很大 |
| 单库 → 分片 / 读写分离 | 索引 + SQL 优化 | 单机数据量与 IOPS 触及上限，优化空间被硬件封顶 | 分片键设计 + 路由 + 跨片聚合 | 分片键一旦定错，再平衡要停机或双写 |
| 单层缓存 → 多层缓存 | 分布式缓存 | 单层缓存的网络往返成为新的延迟下限 | 进程内缓存 + 分布式缓存分层 | 失效面从 1 层变 N 层，必须建失效通道与广播机制 |
| 单体 → 微服务 | 火焰图 + 单进程分析 | 调用跨进程，火焰图看不到别的服务 | 分布式追踪 + 每跳独立指标 | 全链路埋点规范化，跨团队推进 |
| CPU 推理 → GPU 推理 | 算子与算法优化 | 瓶颈从算力变成显存带宽，原手段收益趋零 | 批处理调度 + 显存管理 + 量化 | 需要建立质量基线与 GPU 侧度量口径 |
| 手动调参 → Self-Tuning | 人工定期调参 | 流量形态变化快于人工调参周期 | 闭环调优 + 边界与回滚 | 可解释性下降，需要变更审计与停用开关 |
| 单区域 → 多区域 | 就近接入 + 单套缓存 | 缓存副本跨区域，失效通知的传播时间成为不一致窗口 | 分区缓存 + 按数据分级决定是否允许跨区陈旧 | 需要为每类数据明确「可陈旧多久」，并落成配置 |

**判据不是「规模多大」，而是「瓶颈换了资源类型」**：从 CPU 到 IO、从单机内存到网络带宽、从算力到显存带宽——每一次更换都会让上一阶段最有效的手段失效。**优化手段不会过时，它只是被搬到了不再是瓶颈的地方。**

跃迁里最容易被低估的是「单库 → 分片」：它表面上是一次扩容，实际上是**一次数据模型的重新设计**。分片键决定了后续所有查询的可路由性，选错以后，跨片聚合会取代原来的单机 JOIN，性能问题从「一台机器慢」变成「每次查询都要扇出到所有分片再归并」——**规模上去了，单次查询的可预测性反而下降**，而这一步在多数系统里是不可逆的。

还有一类跃迁不在表里但同样常见：**从「有人专职做性能」到「没人专职做性能」**。团队扩张、业务优先级变化后，性能工作会从「项目」变成「日常」。此时唯一能保住成果的不是某个模式，而是**把基线与验收口径固化进流程**（发布前跑什么、看哪个分位数、超了就拦）；没有这一层，规模跃迁时的正确模式也守不住。

### 3.7 自检清单

下面每一条都设计成**可以用一次测量直接回答**的问题，而不是「有没有做性能优化」这类口号式提问。答不出具体数字或近期样本的，就当作「否」。

- [ ] 有没有一份**端到端基线**（同一压测场景、同一数据规模、P99 口径一致），并且能说出它最近一次更新是什么时候？
- [ ] 当前瓶颈是**哪一类资源**（CPU / 内存 / IO / 网络 / 显存），这个判断依据的是哪一次测量而不是哪一次讨论？
- [ ] 验收口径是 P99 还是均值？如果报表里只出现均值，长尾是谁在看？
- [ ] 近三个月最长的一条慢查询，其**扫描行数与返回行数之比**是多少？治理了吗？
- [ ] 每一处缓存能否回答：**谁失效、何时失效、失效失败怎么办**？答不出的缓存有几处？
- [ ] 是否出现过「写后立即读」读到旧值的工单？如果有，是修复了还是用「刷新一下」应付过去了？
- [ ] 链路上是否存在**跨层失效**（本地缓存 + 分布式缓存 + CDN），失效通知的路径写在哪里？
- [ ] 每一次性能改动，是否都有**端到端指标的前后对比**？没有对比的改动有几处还留在代码里？
- [ ] 压测的数据规模与分布，与生产是否同量级？（不同量级的压测只能证明「没坏」，不能证明「够用」）
- [ ] 如果使用了量化 / 蒸馏，**质量基线**是什么、由谁在看、多久回归一次？
- [ ] 自动扩缩容 / Self-Tuning 是否有上下限、冷却时间与**一键停用**？上次停用演练是什么时候？
- [ ] 成本口径里，单位请求（或单位 token）的资源成本是否可算？算不出来的部分是被谁吃掉的？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 端到端慢、不知卡在哪 | 全链路性能分析 | 延迟是各跳之和加排队时间，只有按跳拆开才能把「慢」变成可证伪的判断 |
| 已知瓶颈在某一层 | 分层优化（只优化那一层） | Amdahl 定律决定加速上限由未优化部分给出，非瓶颈层的投入收益趋零 |
| 读多写少、可容忍短暂旧值 | 缓存金字塔 | 命中率对后端负载是乘性影响；代价是跨层异步失效带来的不一致窗口 |
| 写多 / 刚写入必须可读 | 数据层优化 + 减少写放大 | 一致性要求会让缓存收益转为负值，此时唯一有效的方向是减少工作量 |
| GPU 单位成本是主要支出 | AI 推理优化（量化 + 连续批处理 + 显存管理） | 自回归解码受显存带宽约束，摊薄单位 token 成本只能从显存复用入手 |
| 负载有明显周期、参数频繁失配 | Self-Tuning（带边界与开关） | 参数与负载是时变关系；代价是可解释性下降与反馈滞后引起的振荡 |
| 端到端达标但单位成本超标 | 先做结构性优化（减少工作量 + 避免重复），再做并行 | 并行是租来的收益，资源涨价即失效；结构性优化的收益不随价格变化 |

表里多数行的「关键理由」可以还原成一句话：**这个模式改变了哪一类资源的用量**——减少工作量改变的是「每请求消耗」，缓存改变的是「到达后端的请求数」，并行改变的是「单位时间的处理能力」，推理优化改变的是「每 token 的显存成本」，Self-Tuning 改变的是「参数与负载的匹配度」。**前两行是例外**：全链路性能分析不改变任何资源用量，它的价值是把「慢」变成可证伪的判断；分层优化的依据是 Amdahl 定律——加速上限由未优化的那部分给出。**优化不是让代码更快，而是让某种资源不再被浪费。**

选型的提问顺序建议固定为三步：**先问瓶颈是哪一类资源（测量而非讨论），再问这类资源当前被浪费在哪里（重复计算、排队、扫描、碎片），最后才挑一个能减少这种浪费的手段。**

> 本节小结：本主题下决定模式选择的**唯一那条约束是「瓶颈当前落在哪一类资源上」**——CPU、IO、网络、显存、还是一段串行的锁；它一变，上一阶段最有效的手段立刻失效。所以先测量、再选模式、最后用端到端指标验证；顺序颠倒，就会得到一堆「局部更快、整体没变」的改动，以及一条被推迟到最不方便时刻才爆发的慢查询。
