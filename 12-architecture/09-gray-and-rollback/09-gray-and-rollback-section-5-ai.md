## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本章的既有卡点写在主文件 [§1.2](09-gray-and-rollback.md) 的痛点清单里，一共 6 条：全量发布的"赌博式"上线、回滚慢、"数据 / 模型变更难回滚"、Feature Flag 滥用、灰度指标不准，以及 AI 时代新增的那条（模型效果看不见、Agent 配置变更带安全风险）。**前沿之所以是前沿，是因为既有方案在这 6 处卡住了——而 AI 对它们的处理方式完全不同，这是本节要分开的第一件事。** 回滚速度由"数据与模型是否可逆"决定，AI 一个字都没改（§5.2.3）；"模型灰度 / Prompt 灰度 / 工具灰度"改变的是**被灰度的对象**（从代码扩展到非确定产物），流量切分与观察窗口这套机制原样搬用；只有一处真的换了**接口边界**：Agent 被调用时，授权判定发生在哪一侧（§5.2.2）。把这三类混在同一张"演进方向"清单里，读者会误以为"给 Agent 工具做灰度"和"做金丝雀发布"是同一量级的事。

本节用 L1 / L2 / L3 三级区分，判据必须是可核验的三条：

- **L1 生产可用**：① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定。**三条全中才算 L1**，可以排进路线图。
- **L2 可试点**：已可用但接口 / 生态未稳，或仅有厂商自有案例，或只在小规模被验证。可以做 PoC，**不要作为核心依赖**。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。记录，**不要在架构里预留假设**。

三条判据各挡住一类误判：①挡住"把路线图当既成事实"，②挡住"把工具厂商整理的案例页当行业现状"，③挡住"把演示当工程"。"感觉上大家都在用"不算判据——它在变更评审会上无法被复核。

**判据声明（本节不对 L1 判据做任何修正）**：上面三级与三条判据沿用到底，不替换、不放宽。本主题有一处特别诱人放宽的地方，先把话说死：**变更管理的成效指标（回滚耗时、变更失败率、事故数）几乎不以第三方口径公开**，公开材料里能查到的只有三种形态——工具厂商的产品文档与发布说明、采纳方在工具厂商站点上的署名案例、研究机构对大量组织的问卷统计（如 Accelerate / DORA 系列，见 §5.4）。前两种分别对应"厂商自有案例"与"经厂商整理的材料"，都不是第②条要的形态；第三种统计的是**相关性**，不是某个具体生产案例。本节的做法是：**够不到第②条的行一律降到 L2，并在判据格里写明它卡在哪一条**，而不是为它重新定义"什么叫合格的第三方案例"。结果是**下表没有任何一行达到 L1**——包括那几条非 AI 的既有能力行。L2 不等于"不好"，也不等于"不能现在做"，只等于"公开证据到不了 L1"；真正需要警惕的是把 L2 当 L1 排进核心路线图。

写这一节时最容易混的五件事，先在这里分开：

- **产品名 vs 能力名**："AI Native Progressive Delivery"是**产品组合说法**，不是可判定的能力；对应的能力名是"**把非代码产物（Prompt / 模型 / 工具描述）纳入与代码同一套发布对象与回滚路径**"。
- **已发布版本 vs 路线图**：判断某个平台是否真的支持"模型灰度"，只看一处——**该版本的 release note 或官方文档里有没有对应条目**；产品官网的路线图页、大会演示、生态伙伴转述都不算（§5.4 给了判定入口）。
- **自动 vs 智能**：阈值触发回滚、按比例切流、一致性哈希命中判定，都是**确定性动作**，不需要模型；把它们算进"AI 辅助灰度决策"是本主题最普遍的一处混淆（§5.2.4）。
- **单段能力 vs 全链路**：RAG 链路上"每一段都能独立切版本"是既有能力；"同一次请求五段必须同代"是发布编排问题，不是模型问题（§5.2.4）。
- **论文原型 vs 产品实现**：本方向大量提法（自动回滚、智能灰度、仿真环境）在论文与开源原型里都能找到，但**能否在生产里开箱使用是另一回事**。判定方法：看该能力的官方文档里有没有"配额 / 超时 / 计量"三项——有这三项的才是产品化条目，只有一段演示的还不是。

本节**不**再评估的三件事，都在其他章节里：标准发布形态本身（蓝绿 / 滚动 / 金丝雀的机制差异见 [§3](09-gray-and-rollback-section-3-sec3.md) 与 [§7](09-gray-and-rollback-section-7-sec7.md)）、工程实现（配置中心、流量调度、双写与影子表的落地代码见 [§4](09-gray-and-rollback-section-4-sec4.md)）、真实案例（阿里 / 字节 / 美团 / Netflix 见 [§6](09-gray-and-rollback-section-6-sec6.md)）。本节只回答一个问题：**在这些既有能力之上，AI 又改了哪一处机制，改了以后值不值得现在就投。**

**这三级的排法直接决定路线图的顺序**：

- **先做的两条（§5.1 表第 1、2 行）**：编排与分流。它们排在所有 AI 方向之前，因为后面每一个方向的验证都要靠这两样把流量切开——没有它们，"模型灰度""Prompt 灰度"都无从谈起。注意它们的级别**仍是 L2**：动作今天就能开始，但不要在评审材料里把它们写成"行业已普遍验证"的前提。
- **AI 方向里先做 PoC 的两条（§5.1 表第 3、4 行：模型灰度与 Prompt 灰度），并先测三个数**：影子流量与在线灰度得出的结论是否一致；同一用户在观察窗口内跨版本命中的次数；质量指标的方差是否小到能在窗口内判定差异（§5.2.1 的样本量换算）。这三个数拿不出来，这两条就停在原地——它们与"先做的两条"的区别正是：那两条可以直接进方案，这两条必须先有可观测的数字。
- **L3 不排进排期**：Agent 工具与授权（第 5 行）、"AI 自己选路"（第 6 行）、标签灰度（第 8 行）、"AI 决策型"灰度（第 9 行）、灰度 + 仿真与跨云灰度（第 11 行），都属于"等信号"。它们的共同前提（动作可回滚、判定可解释、权限在被调用方）比选哪家工具重要得多。
- **级别复查（只降不升）**：每次发布流程复查时核一遍级别；某个 L2 若一年内仍拿不出自己组织里的实测记录（谁在用、用了多久、失败过几次），降 L3 并停止投入。

**产业侧的案例**：阿里 A/B 平台"实验即代码"（2024）、Netflix AI 辅助金丝雀（2024）、OpenAI 渐进式模型发布（5% → 50% → 100%，该比例出自厂商自述，不构成第②条要求的案例）一类；本节只作方向指认，不逐条断言其能力。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次"灰度更容易了"，都对应一处新的判定责任。

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 模型灰度与 Prompt 灰度 | 被灰度的对象多了一类**非确定产物** | **对象的性质**（"版本"赖以成立的三条性质无法整套保留，逐类对照见 §5.2.1） |
| §5.2.2 Agent 工具与权限灰度 | 被灰度的对象从"版本"变成"能力"，授权判定随灰度状态而变 | **接口边界**（判定位置必须换到被调用方） |
| §5.2.3 数据 / 特征 / 标签灰度 | 消费方数量与速度变化，可逆窗口变短 | **成本函数**（回滚成本由"谁消费过"决定） |
| §5.2.4 推理路由与其余同组方向 | 收益全部来自既有机制，没有一条来自模型 | **多数与 AI 无因果关系** |

读法建议：时间只够读一节就读 §5.2.2——它是本主题里唯一一条"换了接口边界"的方向，也是唯一一条能直接推导出"下一步该补什么"的方向。

每一节末尾的「证据与来源」沿用同一套档位：【公开】指有可核验的出处（官方文档 / 论文 / 公开材料），【推算】指能写出推导链的换算，【经验】指区间估计。**本节不给版本号**：凡涉及"某产品支持某特性"的地方，一律改写成判定入口（查哪一版 release note 或哪份官方文档），因为本主题的产品名与能力名错配率最高——同一个"模型灰度"在三家平台上有三种不同的接法，把它们写成一句"平台支持模型灰度"没有信息量。

#### 5.2.1 模型灰度与 Prompt 灰度：被灰度的对象从"代码版本"变成"非确定产物"

- **旧做法与它的卡点**：灰度系统只处理一类对象——**代码版本**。它有性质：同一版本在同一输入下可复现、产物有内容寻址（镜像 / 制品有 digest）、回滚 = 切回旧版本（[§3](09-gray-and-rollback-section-3-sec3.md) 的版本回滚）。主文件 [§1.2](09-gray-and-rollback.md) 第 3 条痛点"数据 / 模型变更难回滚"，说的就是这套机制在模型与 Prompt 上失效。
- **AI 改变了什么机制**：被灰度的对象多了一类**非确定产物**（模型权重、Prompt、工具描述）。**"版本"这个概念原本靠三条性质成立，而它们在这类对象上都无法整套保留，失效程度还因对象而异**：**"版本"缺少内容寻址**（v2 是什么，取决于某次保存时的内容而非哈希）；**回滚不等于恢复原状**（旧的 Prompt 切回来，用户已看到的历史输出不会消失；已发生的工具调用也撤不回）；**同一版本不保证同一输出**（Prompt 受采样与非确定性内核影响而完全不成立，模型权重只有在固定随机性与算子实现之后才"多数情况可"，工具描述 / 参数这一行则仍是确定性的——见下表）。**所以机制的变化不在"多了一个灰度对象"，而在"版本这个概念赖以成立的三条性质，没有一条能对整类非确定产物照搬"。**
- **由此得到的**：**因为流量切分与观察窗口这套机制与对象类型无关，所以模型 / Prompt 灰度可以复用既有灰度平台**——同样的按用户一致性哈希、同样的观察窗口、同样的回滚触发条件（主文件 [§2.2](09-gray-and-rollback.md) 已给出四类阈值）。这也是它们被放在 L2 而不是 L3 的原因：**没被换掉的机制占了大部分工作量**。把这三条性质逐类对照，能看清哪些工作是"补前提"、哪些是"真新增"：

| 被灰度对象 | 同输入可复现 | 内容寻址（版本 = 内容的指纹） | 回滚 = 恢复原状 |
| --- | :---: | :---: | :---: |
| 代码版本 | 是 | 是（制品摘要） | 是（外部副作用需另处理） |
| 模型权重 | 多数情况可（固定随机性与算子实现后） | 通常有版本号，未必按内容 | 否（已产生的输出不消失） |
| Prompt | 否（采样 + 模型侧漂移） | 通常无 | 否 |
| 工具描述 / 参数 | 是 | 通常无 | 部分（已发生的调用无法撤销） |

- **由此付出的**：**其一，判据从"可用性"变成"质量"，而质量指标没有天生阈值**——错误率与 P99 有明确的坏方向，"回答质量下降 5%"没有，这使自动回滚从"配一条规则"变成"先定义什么叫变差"（§5.5）。**其二，回滚不彻底带来的新故障形态是"混版"**：同一用户在会话中途被切到另一版本，或同一次请求里 Prompt 是 v2、检索索引还是 v1（§5.2.4），产生既不复现于旧版也不复现于新版的第三类行为。**其三，观察窗口与流量比例的乘积决定证据量**：主文件 §2.2 的样本量公式 n = (Z_{α/2} + Z_β)² × 2σ² / δ² 就是这条约束的量化形式。【推算】取 α = 0.05、功效 80%（Z_{α/2}=1.96、Z_β=0.84，前项 = (1.96+0.84)² = 7.84），则 n = 7.84 × 2σ² / δ²；当最小可检测差异 δ 取标准差的 10%（δ = 0.1σ、δ² = 0.01σ²）时，n ≈ 7.84 × 2 ÷ 0.01 ≈ 1568，即**每个实验组约需 1568 个观测**——换算成"能不能在一刻钟的观察窗口里攒够样本"，才是灰度比例该定的地方。
影子流量之所以应该排在在线灰度之前，原因是它与本节的判定链无关：影子流量的结果不返回用户，因此它不需要质量判据、不需要回滚预案、也不需要在观察窗口里攒够样本——它把"新版本会不会崩"和"新版本好不好"两件事拆开了。主文件 [§2.1](09-gray-and-rollback.md) 把影子流量定义为"复制生产流量但不返回给用户"，正是这个定义让它成为唯一一类**失败代价近似为零**的灰度形态。

- **证据与来源**：【公开】模型与 Prompt 的版本化、按比例切流、自动回滚在主流模型平台与渐进式交付工具的官方文档中是正式功能条目（可按产品名 + 「prompt version / canary」检索核验）。本章 [§6](09-gray-and-rollback-section-6-sec6.md) 的四个案例（阿里 / 字节 / 美团 / Netflix）讨论的是按指标决定是否回滚的工程做法，**其中的数字由本书汇总，不构成第②条要求的第三方（非厂商）公开生产案例**（§5.4）。**②核不到**。
- **成熟度**：**L2**（§5.1 表第 3、4 行）：①成立、③未统一（模型侧接口不一 / Prompt 侧版本载体未统一）、②核不到。模型灰度比 Prompt 灰度更靠得住的地方是**影子流量**可以完全不影响用户（主文件 §2.1 的影子流量定义），建议从影子开始，而不是从 1% 在线开始。
- **判定方法**：抽查最近一条 Prompt 变更记录，问三件事——v2 的内容能不能按哈希定位到唯一一份文本？同一会话是否可能跨版本？回滚后已产生的输出怎么处理？三问有一问答不上，就说明现在还不该开自动回滚。
- **什么时候值得做**：模型或 Prompt 的结果直接对用户可见，且你能为"变差"给出一个可统计的口径时。
- **什么时候不值得做**：变更只影响内部工具或离线任务时——用离线回放比对就够了，不必占用在线灰度通道，也不必为它定义质量判据。
- **失效的早期信号**：灰度期间只看错误率不看质量指标；回滚只切流量、不追已产生的输出；同一会话跨版本命中没人统计。

#### 5.2.2 Agent 工具与权限灰度：被灰度的对象从"版本"变成"能力"

- **旧做法与它的卡点**：Feature Flag 的语义是"这个功能对这批用户开 / 关"，开关的两种状态背后是**同一套权限**——用户能调用哪些接口、能读哪些数据，不因他命中哪个版本而变。所以 [§4.2](09-gray-and-rollback-section-4-sec4.md) 的 Flag 评估只需要回答"命中不命中"，不需要回答"他能不能"。
- **AI 改变了什么机制**：Agent 灰度引入的对象是**能力本身**（一个能删数据、能发起支付的工具）。把新工具"只对 1% 用户开放"，在这 1% 用户身上**权限是扩大而不是缩小的**——灰度比例是流量分配参数，权限是布尔判定，两者不在同一维度。**真正的机制变化是：授权判定从"与版本无关"变成"随灰度状态而变"，于是判定必须落在被调用方（工具侧），不能留在调用方**（[04-data-assetization/07 §5.2.1](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-5-ai.md) 把这个前置问题写成"工具清单与权限条目能不能对齐"）。
- **由此得到的**：**因为授权判定必须与流量分配解耦，所以"工具灰度"的正确形态是：工具照常具备完整权限校验，灰度只决定"这个工具是否进入该会话的候选集"**——分开之后才有两层控制：可见性按比例、授权按身份。

| 要做灰度的东西 | 该用什么机制 | 用灰度比例实现的后果 |
| --- | --- | --- |
| 新工具的**可见性**（是否进入候选集） | 按会话 / 用户一致性哈希 | 可行，与权限无关 |
| 工具的 **timeout / retry 参数** | 配置下发（既有能力） | 可行，影响面是超时与重试次数 |
| 工具的**授权与数据范围** | 按身份的布尔判定 + 独立审批 | **不可行**：等于给灰度组扩权，且没有审批路径 |
| 工具的**副作用范围**（写库 / 支付） | 幂等键 + 限额 + 演练环境 | 不可行：1% 的写错产生 100% 的真实副作用 |

两层控制的具体形态可以写成一句判定：**候选集里有没有 = 灰度说了算；调用能不能成功 = 权限说了算。** 前者可回滚（把工具从候选集里去掉即可），后者不可（一次放行就是一次放行）。这条区分也让两类症状有了各自的处理路径：误拒改候选集或改权限配置；越权被拒是工具侧正常工作的证据，不该被当成故障处理。

这一节的判定顺序可以直接抄成检查清单：先查"这次调用代表谁"（没有主体就没有授权），再查"工具能不能被安全重试"（没有幂等键就没有回滚），最后才谈"给多少比例的用户看到"。顺序反了的话，灰度比例这个参数会把两个都没解决的问题伪装成"已经在控制了"。

- **由此付出的**：**其一，判定位置一变，故障归属就变**——越权尝试被拒是工具侧的正常工作，误拒则表现为"Agent 突然不会用了"，两类症状在监控上都表现为错误率上升，必须分开统计。**其二，工具灰度的观察窗口要比代码灰度长**，因为工具失败常不体现在错误率上，而体现在"Agent 换了一条更绕的路径完成任务"，这类退化只能从任务成功率与步数上看到。**其三，能被灰度的前提是工具有幂等键**——没有幂等键的写操作，连"重试"这个最基本的回滚手段都不成立。
- **证据与来源**：【公开】工具调用协议与工具描述格式有公开规范可核验（可按协议名检索；[04-data-assetization/07 §5.2.1](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-5-ai.md) 记录了这类规范的版本化发布方式）。**②核不到**——"谁能调用哪个工具、调用后如何审计"在本节举不出第三方（非厂商）公开生产案例（§5.4）；本章 §6 的四个案例都不涉及 Agent 工具灰度。
- **成熟度**：**L3**（工具与授权）/ **L2**（工具的 timeout / retry 参数配置）（§5.1 表第 5 行）——工具与授权这一半：①只有厂商演示与预览特性，②无，③工具协议与权限模型仍在快速变化；参数配置这一半：①③成立（配置下发是既有能力、接口多年未变）、②核不到，故按 L2 处理。**可以在 PoC 里做"可见性灰度"，但不要在架构里假设"权限可以按比例开放"。**
- **判定方法**：问一句"这次 Agent 工具调用代表的是谁"——答不出，说明授权的第一步还没做完，谈灰度是空转（该问题与 [04-data-assetization/07 §5.2.2](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-5-ai.md) 的"鉴权主体从一个换成两个"是同一件事）。
- **什么时候值得做**：工具带副作用（写库、发起支付、删数据），或工具描述会进入模型上下文时。
- **什么时候不值得做**：工具是纯读、且数据范围与现有权限完全重合时——按普通配置发布处理即可，"灰度"只会多出一层没人维护的开关。
- **失效的早期信号**：工具可见性与权限边界写在同一个配置里；审计里查不出"这次调用代表谁"；越权被拒与误拒混在同一个错误率指标里。

#### 5.2.3 数据 / 特征 / 标签灰度：可逆性的边界不在发布工具

- **旧做法与它的卡点**：数据侧灰度靠影子表与双写（主文件 §2.3 第 6 条；写路径与读切流见 [§4.2](09-gray-and-rollback-section-4-sec4.md) 的数据灰度小节）。卡点不在切流，而在**一旦下游消费了新表，回滚就不再是把读路径切回去**——已基于新数据产生的结论、模型、报表不会随切流消失。主文件 §1.2 第 2、3 条痛点与 §2.2 的 RTO 分级（30 秒 / 5 分钟 / 30 分钟）说的正是这件事：**RTO 的分级不是按工具分的，是按"要不要数据修复"分的**。
- **AI 改变了什么机制**：AI 在这里没有改变机制，改变的是**消费方的数量与速度**——特征与标签的消费者从"几个下游任务"变成"可能同时包括训练、在线推理与 Agent 检索"。于是同一份数据"被消费掉"的路径变多，**可逆窗口变短**：原来是 T+1 的任务才会消费，现在在线推理可能在写入后秒级就消费。
- **由此得到的**：**因为可逆性的边界由"谁消费过"决定，所以数据灰度必须先划出"可以回滚的路径"和"只能向前修"的路径**：

```text
数据灰度的三类路径（判断标准：回滚要不要修复已发生的消费）
  ① 只读影子路径 ：新表只被读、不被消费 → 回滚 = 切回读路径（秒级～分钟级）
  ② 幂等写入路径 ：新表被写且可重放   → 回滚 = 用幂等键重放旧路径（分钟级）
  ③ 已消费路径   ：新标签已进训练 / 在线推理 / 检索
                     → 回滚 = 修复已产生的结论（小时～天级）
  ────────────────────────────────────────────────
  灰度比例能控制的是"有多少请求走新路径"，
  控制不了的是"已经走过去的那些请求的后果"。
```

顺带一个常被忽略的口径问题：**"灰度期间有多少流量走新路径"这个数字容易拿到，"新路径的产物被消费了多少次"这个数字往往拿不到**——因为消费发生在下游、跨团队、跨系统。没有第二个数字，三类路径的划分就只能靠开会拍；这也是本节把"对账"排在"灰度"之前的理由。对账的最小形态是：新旧两张表的行数、主键集合与关键聚合值三个口径按日比对，差异率超过阈值就停灰度——它不依赖任何 AI 能力，却决定了灰度能不能回滚。

- **由此付出的**：**其一，"标签灰度"这个提法本身要打问号**——标签一旦被训练使用就无法按比例撤回，它更接近"带版本的发布 + 事后纠偏"，而不是灰度。**其二，双写的正确性由对账保证，不由灰度比例保证**（主文件 §2.3 把双写的关键写成"一致性靠对账"，这是必须单独投入的部分）。**其三，影子路径的成本常被低估**——影子表要额外存储与写入吞吐，而它带来的是"零用户价值"的验证期开销，容量要按峰值留（[§4.1](09-gray-and-rollback-section-4-sec4.md) Step 5 把它列入数据迁移工具；容量口径见 [§4.4](09-gray-and-rollback-section-4-sec4.md)，按峰值留、不按均值留）。
- **证据与来源**：【公开】双写、影子表、Online Schema Migration（gh-ost / pt-online-schema-change / pg_repack 一类）与 Binlog 反向应用是既有工具的正式能力，工具表见 [§4.3](09-gray-and-rollback-section-4-sec4.md)，接口多年未变。**②核不到**——本节举不出第三方（非厂商）公开生产案例。本章 §6 的"阿里把回滚做成发布的前提条件"是本书汇总的工程做法，不构成②。
- **成熟度**：**L2**（数据 / 特征，§5.1 表第 7 行）：①③成立、②核不到。**标签这一子项按同一判据只能算 L3**（§5.1 表第 8 行）——它缺"可撤回"这个前提。两处级别一致，不在别处另判。
- **判定方法**：拿最近一次数据变更，逐条问"这次变更的产物被谁消费过、消费方能不能重算"；答"不能重算"的路径，就不该用灰度比例去控，而该走变更评审。
- **什么时候值得做**：变更会改变下游可观测的数值（口径、分区、标签语义），或消费方超过一个团队时。
- **什么时候不值得做**：改动只在影子表内、没有任何下游消费时——按普通数据回填处理，不必套一层灰度外壳。
- **失效的早期信号**：双写没有配套对账任务；灰度期间没人统计"新表的下游消费方有几个"；回滚预案里没有"已消费数据的修复"这一节。

#### 5.2.4 推理路由与其余同组方向：收益来自既有机制，不来自模型

- **旧做法与它的卡点**：这一组（推理路由与降级链路、RAG 分段灰度、多维度灰度、可观测性反哺发布决策、灰度 + 仿真、跨云灰度、AI 推荐灰度比例、AI 异常检测、AI 自动回滚）多以"AI 让 X 更好"的形式出现。真正的卡点在别处：**观察窗口内的信号够不够判定**（§5.2.1 的样本量约束）与**判定发生在哪个环节**。推理路由的卡点尤其典型——多模型路由与超时降级都是网关的既有配置项，缺的不是模型，是"哪类请求该落哪一级"的书面规则。
- **AI 改变了什么机制**：**只改了提问方式，没改判定链**。异常检测、日志聚类、变更风险打分，输入仍是同一批指标；它们降低的是"人从告警里找故事的阅读成本"。RAG 五段灰度真正的难点是**链路版本一致性**（同一次请求里五段必须同代），这是发布编排问题。推理路由同理：真正起作用的是网关的多后端权重与超时规则（既有能力），"AI 自己学会选模型"那半缺的是"哪个模型适合哪类请求"的判定依据，而这类依据今天仍由规则与人给出。
- **由此得到的**：**因为判定链没变，这一组里能用的一半今天就能做**——下表的第三列逐条给出本节级别，"真正起作用的是哪一层"那一列用来看每个条目实际靠的是什么（下表九行给出的都是既有能力）：

| 条目 | 真正起作用的是哪一层 | 本节级别 |
| --- | --- | --- |
| 多后端推理路由与超时降级 | 网关的多后端配置 + 超时规则（既有能力） | L2（路由与降级）/ L3（"AI 自己选路"） |
| AI 推荐灰度比例 | 历史变更的失败记录 + 规则 | L3（只有演示） |
| AI 异常检测 | 指标基线与阈值（既有可观测性能力） | L2（能力本身非 AI） |
| AI 自动回滚 | 阈值触发的自动回滚（主文件 §2.2 的四类条件） | L2（阈值型）/ L3（AI 决策） |
| RAG 五段灰度 | 发布编排 + 链路版本一致性 | L2 |
| 可观测性反哺发布决策 | 指标口径与采样密度 | L2（观测侧既有能力） |
| 多维度灰度 | 分流键的设计（按用户 / 租户 / 场景） | L2 |
| 灰度 + 仿真 | 流量录制与回放 | L3 |
| 跨云灰度 | 多云控制面 | L3 |

这张表的读法是从左往右看两遍：第一遍看"真正起作用的是哪一层"，会发现九条的中列写的全是既有能力——网关的多后端配置与超时规则、历史变更的失败记录、指标基线与阈值、阈值触发的自动回滚、发布编排、指标口径与采样密度、分流键的设计、流量录制与回放、多云控制面，**没有一条的收益来自模型**；要求"由模型来决策"的三处（"AI 自己选路""AI 推荐比例""AI 判断回滚"）在中列写的同样是既有能力，它们在最后一列也落在 L3 那半（表里另一处带"AI"字样的"AI 异常检测"，中列写的是"指标基线与阈值"，落在 L2 而不是 L3）。第二遍看最后一列，会发现整条标 L3 的是"AI 推荐比例""灰度 + 仿真""跨云灰度"三条，另有"AI 判断回滚"与"AI 自己选路"两处是半条 L3——它们各自在同一条里还有一半（阈值型自动回滚、多后端路由与超时降级）按 L2 处理。换句话说，**这一组里"AI 让灰度更好"的具体含义是"观测与编排更细"，不是"决策更聪明"**。

- **由此付出的**：**其一，把"能算的"和"要学的"混在一起会推迟该做的事**——阈值型自动回滚今天就能上，等"AI 判断"会让最基础的一条防线缺席。**其二，观测面越宽，判定越慢**：多维度灰度会稀释每个维度的样本量，与 §5.2.1 的样本量约束直接冲突。**其三，仿真环境与生产不同分布**（流量录制能复放请求，不能复放依赖的时变状态），把它当"减少真实环境风险"的手段可以，当"替代真实灰度"不行。
- **证据与来源**：这一组整体**无公开可核验的第三方（非厂商）生产案例**，§5.4 第（3）类不为其列条目；是否值得做，用 §5.7 表"现在就该做"那一列的动作来判。其中"AI 异常检测"与"可观测性反哺判定"要分开看：前者是既有观测能力（阈值、基线、聚类），后者要求指标能按分流维度拆分——两者都不需要模型，把它们记成 AI 方向会让真正缺的那一环（指标口径）继续缺着。
- **成熟度**：见上表逐条；作为一组，**AI 决策型部分整体 L3，确定性部分 L2**（与 §5.1 表第 2、6、9、10、11 行逐条一致）。
- **什么时候值得做**：你已经能按灰度组拆分指标，且观察窗口内的样本量够判定（§5.2.1 的换算）时。
- **什么时候不值得做**：分流维度一多就会稀释样本时——多维度灰度的收益是"更细的观测"，代价是"更慢的判定"，两者不能同时要。
- **失效的早期信号**：把"能算的动作"包装成 AI 能力写进方案；把仿真环境的结果当成上线依据；跨云灰度只做了控制面、没做数据面。

### 5.3 与本主题既有栈的接口在哪

接口的共同形状是"**信号进来、判定出去、动作回去**"。下面每一行都不是"与 X 结合"，而是"数据以什么形态穿过边界、失败时谁负责"：

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 灰度平台 ↔ 监控告警（[11-cross-cutting/04](../../11-cross-cutting/04-observability/04-observability.md)） | 指标以时间序列穿过，灰度侧只读 | **观测侧**：没有按灰度组拆分的指标口径，灰度就无法判定 | 既有能力；缺的是分流维度的指标设计 |
| 灰度平台 ↔ Feature Flag 配置中心（[§4.2](09-gray-and-rollback-section-4-sec4.md)） | "布尔 + 分桶键"穿过，返回命中 / 不命中 | **Flag 侧**：命中判定不确定（同一用户短时间命中不同版本） | 既有能力；一致性哈希是实现细节也是故障点 |
| 灰度平台 ↔ 模型服务 / ML 平台（[§4.3](09-gray-and-rollback-section-4-sec4.md)） | 模型版本 + 流量权重 | **模型平台**：版本与权重不一致，或影子流量与在线流量读的不是同一份权重 | L2 |
| 灰度平台 ↔ 数据侧（[Ch12 §04 容量规划](../04-capacity-planning/04-capacity-planning.md)） | 双写的写入路径 + 读切流比例 | **数据侧**：回滚要修复数据，灰度平台承担不了 | L2；对账是独立工程 |
| 发布流程 ↔ 影响面查询（[11-cross-cutting/05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)） | 变更单携带"受影响的表 / 字段 / 下游"清单进入评审 | **流程侧**：审批通过但影响面没人核，灰度就只是形式 | 既有能力；血缘章节给查询，本章给门禁位置 |
| 灰度平台 ↔ 工具 / Agent 侧（[04-data-assetization/07 §5.2.2](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-5-ai.md)） | 授权判定以"允许 / 拒绝"穿过 | **被调用方**：越权被拒是正常，误拒才是故障 | L3 |
| 灰度平台 ↔ 混沌工程（[Ch12 §06](../06-chaos-engineering/06-chaos-engineering.md)） | 故障注入 + 观察回滚是否真的生效 | **发布流程**：回滚预案没被演练过就等于没有 | 既有能力；两者常各自运行、从不联动 |

三处边界最容易漏：

1. **监控侧的拆分口径**（第 1 行）。灰度要判定，就必须能按"命中 / 未命中"这一维把指标拆开；很多团队有灰度平台、也有监控，但指标上没有这一维，于是观察窗口里只能看到全量指标的平均值——**用均值掩盖长尾**正是主文件 §1.2 第 5 条痛点所指。补这个比补任何 AI 能力都优先。
2. **Flag 侧的一致性哈希**（第 2 行）。命中判定必须对同一用户稳定；一旦实现里混入了"每次请求重新取时间片"这类因素，同一个用户会在观察窗口里反复横跳，结论直接作废。
3. **工具侧的授权**（第 6 行）。这一行的责任归属与前几行相反——**它是唯一一处"拒绝是正常工作、放行才是风险"的边界**，因此它的监控语义（越权被拒 / 误拒）与其他行不同，不能共用同一个错误率面板。

### 5.4 公开进展与文献

分三类列出，每条都给出可核验的入口（拿不准的只写判定方法，不写结论）：

**（1）论文与专著**

- 【公开】《Trustworthy Online Controlled Experiments》（Kohavi / Tang / Xu，剑桥大学出版社，2020）——在线实验与 A/B 统计的方法学，是主文件 §2.2 那套 α / 功效 / 样本量约定的标准出处。
- 【公开】《Accelerate》（Forsgren / Humble / Kim，2018）及其后续 DORA 年度报告——变更管理实践的问卷统计。**注意它的性质**：统计的是相关性，不是某个具体生产案例，因此不能充当 §5.1 的第②条。
- 三条文献（Progressive Delivery for ML / Safe Deployment for LLM / Causal A/B Testing）：按题名在对应会议论文集页面核验会议与年份后再引用，本节不复述其结论。

**（2）官方 release note 与文档（判定入口）**

- 滚动更新与流量权重要分开查：滚动更新查 Kubernetes 官方 API 参考里 Deployment 的 `strategy` 字段（它只定义滚动方式与 `maxSurge` / `maxUnavailable`，**不含按权重切流量**）；按权重切流量查 Service / Ingress / Gateway API 的官方文档或渐进式交付控制器的 release notes，以当前版本为准。
- 渐进式交付控制器（Argo Rollouts / Flagger 一类）——查项目 release notes；其在 CNCF 的成熟级别以 CNCF 官网项目页为准。
- 开关评估规范——以规范站点当前版本为准；"同一个用户稳定命中"这条要求是否被规范约束，看规范原文而不是博客。
- 各模型平台的"版本 / 灰度 / 评测"能力——以产品官方文档为准，**不要以大会演示为准**。
- 各平台"是否支持模型灰度"的判断只用一条：该版本的官方文档里有没有"按比例切流量"与"回滚到指定版本"两个条目；只有"支持多模型"不算。
- 可观测性侧"能否按灰度组拆分指标"——查指标口径文档里有没有"分流维度"这一项；没有这一项，灰度平台再先进也无法判定（§5.3 第 1 行）。
- LLM 可观测性产品（Arize Phoenix / LangSmith / Helicone 一类）——查其官方文档里有没有"分流维度"与"会话级版本标记"这两项；本节不复述产品能力，只把这两项当作判定入口。
- 数据侧"能否回滚"——查变更工具文档里有没有"回滚"与"对账"两个条目同时存在；只有"支持双写"不足以说明可回滚（§5.2.3）。

**（3）第三方（非厂商）公开生产案例**

本节不列（理由见 §5.1 判据声明）。可自行核验的替代路径：检索**采纳方自己发布**的工程文章，优先采信写清了"指标口径 + 观察窗口 + 判定阈值"的材料；只有结论没有方法的材料，按厂商自述对待。任何一条能同时给出这三样的材料，都可以拿去回填 §5.1 表里的级别。

**怎么用这三类材料**：要判断"某个能力现在能不能上"，查第（2）类——官方文档与 release note 是唯一能回答"这个版本有没有这个功能"的材料；要判断"这个能力在真实组织里跑得怎么样"，找第（3）类，找不到就把结论写成"可试点"；第（1）类用来说明"为什么这么做"，不用来说明"现在做到了什么"。三类混用的典型症状是：拿一篇论文证明产品可用，或拿一份产品文档证明实践成熟——两者都会被变更评审会上的一句"谁在用、用了多久"问倒。

### 5.5 被过度宣传的部分

这一节只列三条，入选标准是：如果某个说法在方案评审里被用来**跳过一步验证**，它就值得被拆开。每条按"被过度宣传的说法 → 实际是什么 → 为什么会这样 → 什么时候才会成真"写。

**"AI 自动回滚"** —— 实际是阈值规则加自动执行（主文件 [§2.2](09-gray-and-rollback.md) 给出四类触发条件：错误率、P99、业务指标、投诉量）→ 为什么会这样：回滚判定必须**先于事故定义**，否则事故期间无法解释"为什么回滚了"，也无法复盘；模型给出的判定在事故期间不可申诉。→ 什么时候才会成真：当"哪个指标向坏、坏到多少必须回滚"能从历史事故里被稳定复现，且决策过程可被审计复盘、带申诉路径时。

**"给高权限工具做灰度就能控制风险"** —— 实际是这 1% 用户**获得了**这个权限，不是风险降到了 1% → 为什么会这样：灰度比例作用于流量分配，权限是布尔判定，两者维度不同（§5.2.2）。→ 什么时候才会成真：授权判定在被调用方、扩权走独立审批，灰度只控制可见性。

**"灰度能覆盖数据与模型变更"** —— 实际是灰度只改变**影响范围**，不改变**可逆性** → 为什么会这样：回滚成本由"谁消费过"决定（§5.2.3 的三类路径），而灰度平台看不到消费方 → 什么时候才会成真：消费路径可被枚举、可逆窗口被写进变更规范，且变更评审会逐条核对时。

三条有一个共同点：它们都是**用"更大的范围"替换了"更明确的判据"**——把"哪些指标坏到什么程度要回滚"换成"AI 会判断"，把"哪些身份能用哪个工具"换成"1% 用户先试"。识别这类说法的办法是问一句：**这套机制在出错时，能不能指出具体是哪一条判据被违反了？** 指不出来，就说明它还不是一个可运维的机制。

### 5.6 未来 3-5 年：可证伪的预测

四条预测都写成"预测 + 会成真的信号 + 会证伪的信号"。信号只写**外部可观察的事实**（某个字段出现在配置模型里、某类材料公开出版），不写"体验会变好"这类无法观察的判断。写不出信号的预测，本节不列。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 非代码产物（Prompt / 模型 / 工具描述）被纳入与代码同一套"发布对象 + 版本 + 回滚"模型 | 主流渐进式交付工具的配置模型里出现非代码产物的版本字段，且回滚语义与代码一致 | 两年后各平台仍各自维护一套 Prompt / 模型版本体系，与代码发布互不相识 |
| AI 辅助灰度决策长期停在"建议"通道，不进入自动通道 | 公开事故复盘里出现"自动决策无复核路径"的案例，随后自动通道被收回人工确认 | 出现可审计、带申诉路径的自动回滚生产实践，并公开了方法与阈值口径 |
| RAG 链路灰度收敛为"整体版本为主 + 少数段可独立回滚" | 观测产品提供"链路版本"这一概念，能把一次请求的五段归属到同一代 | 五段仍各管各的，且没有链路级一致性校验 |
| 跨云灰度不会成为主流 | 多云发布仍停在"各云各自发布"，跨云一致性交给数据侧而非发布侧 | 出现跨云统一灰度控制面的公开生产实践，并给出成本口径 |

这四条里，前两条关于**非确定产物怎么管**，后两条关于**混合系统怎么分层**——它们不预测某个产品会不会赢，只预测"某类能力会不会被纳入既有工程体系"。几年后回头核：若配置模型里确实出现了非代码产物的版本字段、且发布复盘里确实出现了自动决策的申诉记录，说明本节的机制判断成立；若只有产品宣传而没有这两类痕迹，说明"AI 原生发布"仍停在演示层。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 还没有稳定的灰度发布 | 应用层最小闭环：滚动 / 蓝绿 + 一条阈值型自动回滚 + 指标按灰度组拆分 | 变更失败率与回滚耗时（对齐主文件 §2.2 的 RTO 分级） | 不要先做"AI 推荐灰度比例"——它排在最后而不是最前 |
| 有灰度平台、Flag 散落 | Flag 治理（Owner + 过期清理 + 归档），统一命中判定的实现 | Flag 总数是否收敛、同一用户跨版本命中的次数是否归零 | 不要用 Flag 承载权限判定 |
| 已上模型与 Prompt | 先做影子流量，再谈比例；给 Prompt 加内容寻址，解会话粘性 | "混版"类投诉、同会话跨版本比例、质量指标的口径是否稳定 | 不要在质量判据没有定义时开自动回滚 |
| 正在做 Agent / 工具 | 把授权判定放到被调用方；工具先补幂等键与限额 | 越权被拒与误拒是否分开统计；任务步数是否在灰度组里异常上升 | 不要把高权限工具的开放做成"灰度比例" |
| 在做数据 / 特征灰度 | 先做对账与可逆窗口分级（§5.2.3 三类路径） | "回滚需要数据修复"的次数、影子路径的容量开销 | 不要把标签变更叫灰度，也不要靠灰度比例回滚已消费的数据 |
| 在评估采购"带 AI 灰度"的平台 | 先问三件事：它按什么维度判定好坏、回滚后已消费的产物怎么处理、授权判定在调用方还是被调用方 | 该平台是否公开了"配额 / 超时 / 计量"三项；供应商是否能给出你的场景下的判定阈值 | 不要为"AI 灰度"这个标签付费——上表前三行的动作与它无关，且必须先做完 |

读这张表的方法是**从"明确不要做"那一列往回读**：本主题里最贵的浪费不是做错方向，而是**把顺序做反**——先买一个带"AI 灰度"标签的组件，再回头补指标拆分与 Flag 治理。上表每一行的"现在就该做"都是可以在一个迭代内完成的、可复现的工程动作；而"一年内观察"那一列若一年后仍是空的，说明这条路本身没被真正走通，应当停下来而不是加大投入。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一一条机制**是"被灰度的对象多了一类非确定产物"（模型权重、Prompt、工具描述），它使"版本"这个概念赖以成立的三条性质（可复现、内容寻址、回滚即恢复）在这类对象上都无法整套保留——**代价是判定判据从可用性变成质量，以及新的"混版"故障形态**。它**没有**改变的是：流量切分、观察窗口、按指标回滚这套骨架（所以模型 / Prompt 灰度今天就能复用既有灰度平台），以及**回滚速度的物理下限**——那个下限仍由"数据与模型被谁消费过"决定，与有没有 AI 无关。
>
> 本节的三级与三条判据未做任何修正（§5.1），因此表里没有 L1 行；这不代表本主题不成熟，只代表**公开材料到不了 L1**。规划时按"表里的 L2 先做、L3 只记录"推进。**升级只认公开材料**：出现第三方（非厂商）公开发布、且写清了指标口径与观察窗口的生产案例后，才回到 §5.1 表改判 L1；本组织内的采纳记录（谁在用、用了多久、失败过几次）能用来判断"要不要继续投入"，但它不是第②条要求的形态。
>
