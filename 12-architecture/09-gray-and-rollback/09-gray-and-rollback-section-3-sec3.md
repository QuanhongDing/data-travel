## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

**模式表把发布讲成了「按场景选一个」，但真实的模式选择是被约束推着走的。** 同一条「上线新版本」，在无状态 Web 服务上和在数据库 Schema 上，正确模式完全不同 —— 不是团队偏好不同，而是**可用的控制量不同**：前者能切流量，后者连「新旧两版数据同时存在」都做不到。所以先立约束，再谈模式。

**最反直觉的一条约束是「可逆性」。** 本章 §2.1 把可逆发布列为独立概念，原因正在于此：回滚不是一个附加能力，而是**发布设计的产物**。「加一列」可逆（回滚 = 不读新列），「删一列」不可逆（旧数据已丢），「数据迁移」介于两者之间（回滚 = 反向重放）。把不可逆变更当可逆变更做规划，是本章所有反模式里后果最重的一类 —— 它的表现形式不是发布失败，而是**发布成功且再也退不回来**。

**第二条是兼容性。** 金丝雀与滚动发布都默认「新旧版本可同时服务同一份数据」。一旦新版本改了协议或 Schema 且不向后兼容，切流这个动作本身就不成立了 —— 此时唯一可用的手段是先把系统改成兼容态（扩展-收缩两阶段），再谈灰度。灰度模式解决不了兼容性问题，它只是兼容性成立之后的加速器。

**第三条是「观察窗口能不能等到信号」。** 灰度的价值来自「小流量先暴露问题」，但长尾故障（P99、特定分群、低频路径）在 1% 流量下可能根本不复现，放大到 50% 才暴露 —— 而此时影响面已经很大。**灰度比例不是越小越安全**：它和故障的统计特性、以及你能容忍的观察时长共同决定。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 变更形态（代码 / 配置 / 数据 / 模型 / Agent 配置） | 决定可用的灰度手段与回滚路径 | 「每种变更都能套同一套灰度」——配置与模型变更没有「实例」可换，只能靠开关与影子 |
| 新旧版本能否并存（兼容性） | 决定切流类模式是否可行 | 「金丝雀是万金油」——协议或 Schema 不兼容时，新老流量根本没法混跑 |
| 变更是否可逆（单向门） | 决定回滚是「切一次流量」还是「跑一次数据修复」 | 「有回滚预案就等于可回滚」——预案不是路径，删掉的列回不来 |
| 副作用是否可隔离 | 决定影子流量能否用于该变更 | 「影子流量就是复制一份请求」——带写副作用的复制会污染真实业务数据 |
| 指标可测量性与观察窗口 | 决定自动回滚的阈值能不能写出来 | 「技术指标全绿就没问题」——业务效果下跌根本不在这套指标里 |
| 发布频率与运维人力 | 决定灰度由人工驱动还是控制器驱动 | 「每次发布人工盯 30 分钟」——每天上千次发布时这条根本不成立 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 金丝雀发布（Canary Release）

- **被什么约束逼出来**：新版本在真实流量下的行为无法事先证明，全量上线等于拿全部用户做实验。
- **结构**：新旧两个版本同时在线，路由层按权重分配流量，**权重是唯一的控制量**。

  ```text
  金丝雀：权重是唯一的控制量
            ┌──────────────────────────┐
  用户 ────►│ 路由层（网关 / 服务网格）  │
            └───────────┬──────────────┘
              weight=99 │ weight=1
                  ┌─────┴─────┐
                  ▼           ▼
             [ v1 旧版 ]   [ v2 新版 ]
                  │           │
                  └─────┬─────┘
                        ▼
              同一套存储 / 同一份 Schema
  回滚 = 把 v2 的 weight 设回 0（不重新部署、不搬数据）
  前提 = 两版能同时读写同一份存储
  ```

- **为什么这样设计有效**：因为控制量只有一个（权重），所以「放大」与「回滚」是同一个动作的正反方向 —— 回滚不需要重新部署、不需要搬数据、不需要等缓存失效，它是**一次配置变更**，而不是一次发布。
- **代价**：新旧两版代码必须同时可运行，等于每次变更都要多维护一个「兼容态」，直到旧版彻底下线；路由层必须支持按权重切分并保证分群稳定（同一用户反复命中同一版本，否则用户体验会来回横跳）。
- **失效点**：当变更涉及新旧不可并存的改动（协议变更、Schema 不向后兼容、单例资源争抢）时，「小流量先试」的收益直接反转为负 —— 因为此时新老流量无法混跑，1% 的灰度流量也会踩到不兼容的数据，**优点（影响面小）变成缺点（问题被稀释到 1%，反而更难定位）**，正确做法是先做扩展-收缩造出兼容态。
- **真实使用**：把权重路由下沉到服务网格（Istio `VirtualService` 的 `weight` 字段）是云原生生态的主流做法（【公开：Istio 官方文档 VirtualService 流量切分章节，以官方文档当前版本为准】）；阶梯普遍取 1% → 10% → 50% → 100%，观察窗口按风险定在 5–30 分钟（【经验】）。

#### 3.2.2 蓝绿发布（Blue-Green Deployment）

- **被什么约束逼出来**：回滚必须在秒级完成，而「重新部署旧版本」本身就要几分钟 —— 回滚动作不能依赖部署系统。
- **结构**：两套完整环境同时常驻，负载均衡器指向其中一套；数据层必须外置，否则切流切不动。

  ```text
  蓝绿：整环境切流，回滚 = 切回去
        ┌────────────────┐
        │   负载均衡器    │
        └───┬────────┬───┘
     100%   │        │   0%
            ▼        ▼
      [ Blue 旧 ]  [ Green 新 ]   ← 两套环境同时常驻，机器成本约 ×2
            └────────┴────────┘
              共用外部化数据（DB / 缓存 / 对象存储）
  切流是一次原子变更；回滚是同一个动作的逆操作
  失效条件：数据层被这次发布一起改掉了 → 切回去也读不了
  ```

- **为什么这样设计有效**：因为切流与部署是两个独立事件，所以「回滚」退化成一次负载均衡指向变更 —— 它不需要构建、不需要调度、不需要冷启动，耗时从分钟级变成秒级（【经验】量级）。这也是「谁能承诺秒级回滚」这个问题的标准答案。
- **代价**：环境成本约翻倍（第二套机器、第二套配置、两套都要跟着安全补丁走）；数据层必须外置且**必须保持两版兼容** —— 蓝绿没有解决数据问题，它只是把数据问题推到了「发布前必须先解决」的位置。
- **失效点**：当发布包含数据层变更（Schema、迁移、索引重建）时，秒级回滚的优势会反转成最大的风险 —— 因为切回旧环境后，旧代码读到的是已被新代码改写过的数据，**系统能启动但结果是错的**，这种故障比直接报错更难发现。蓝绿对「带数据变更的发布」几乎无效，反而会给人一种「我能秒回滚」的错觉。
- **真实使用**：这一模式的经典描述来自 Martin Fowler 的 Blue-Green Deployment 条目（【公开：martinfowler.com, BlueGreenDeployment, 2010】）；实践中它最常用于「应用可切换、数据不改动」的关键服务发布（【经验】）。

#### 3.2.3 滚动发布（Rolling Update）

- **被什么约束逼出来**：实例数量多、镜像包大、且服务无状态 —— 为一次发布常驻两套环境的成本不可接受，只能用同一批机器原地换。
- **结构**：按副本批次替换，批大小由 `maxUnavailable` / `maxSurge` 控制，就绪判据决定实例是否收流量。

  ```text
  滚动发布：实例级原地替换（Kubernetes Deployment 默认策略）
  期望副本 4；maxUnavailable / maxSurge 默认均为 25%
  （【公开：Kubernetes 官方文档 Deployment 滚动更新参数，以官方文档当前版本为准】）
    初始    [v1][v1][v1][v1]
    第 1 步 [v2][v1][v1][v1]   ← 先起新的，就绪后再退旧的
    第 2 步 [v2][v2][v1][v1]
    第 4 步 [v2][v2][v2][v2]
  关键：readiness probe 未通过的实例不接收流量（官方文档，同上）
  回滚 = 把镜像 tag 指回旧版本，整批反向滚一遍
  ```

- **为什么这样设计有效**：因为替换是分批且以「就绪」为前置条件的，所以任意时刻都有一批健康实例在服务 —— 发布过程中不存在「全员不可用」的窗口，且整个过程不需要额外机器。
- **代价**：发布期间新旧版本**长时间混跑**，意味着所有写入路径都必须双版本兼容；且回滚同样要滚一遍全批实例，回滚耗时与实例数成正比，无法做到蓝绿那样的秒级。
- **失效点**：当服务实际是有状态的（本地缓存、本地文件、粘性会话）时，「实例无差异」这个前提被打破，滚动的好处反转为数据不一致 —— 因为流量会被调度到任意实例，而每个实例的本地状态不一致，**用户看到的结果取决于被路由到哪个实例**。
- **真实使用**：Kubernetes Deployment 的默认策略即滚动更新（【公开：Kubernetes 官方文档，以官方文档当前版本为准】）；它也是绝大多数无状态微服务的第一选择（【经验】）。

#### 3.2.4 Feature Flag（功能开关）

- **被什么约束逼出来**：部署（deploy）与发布（release）被耦合在一起 —— 代码上线即功能上线。要解耦两者，就必须存在「代码已部署但功能未开启」的中间态。
- **结构**：开关是数据（配置表 / 配置中心条目），不是代码分支；评估逻辑在请求路径上，按稳定分桶决定是否命中。

  ```sql
  -- Feature Flag 的最小结构：开关是配置，不是「另一份部署」
  CREATE TABLE feature_flag (
    flag_key    VARCHAR(128) PRIMARY KEY,
    enabled     BOOLEAN   NOT NULL DEFAULT FALSE,
    rollout_pct SMALLINT  NOT NULL DEFAULT 0,   -- 0..100，按稳定分桶命中
    bucket_key  VARCHAR(64) NOT NULL,           -- 分桶依据，如 user_id / tenant_id
    owner       VARCHAR(64) NOT NULL,           -- 必须具体到人，不是团队
    expires_at  TIMESTAMP NOT NULL,             -- 到期未清理即产生告警
    payload     JSONB,                          -- 开关携带的参数（阈值、灰度名单）
    updated_at  TIMESTAMP NOT NULL
  );
  -- 评估：bucket = hash(bucket_key) % 100；命中 = enabled AND bucket < rollout_pct
  -- 回滚：UPDATE feature_flag SET enabled = FALSE WHERE flag_key = ?（不重新部署）
  ```

- **为什么这样设计有效**：因为开与关是同一行数据的两个取值，所以「关闭」不需要走发布流程 —— 回滚时间从「一次部署」压缩到「一次配置读取生效」（秒级，【经验】量级），而且开关可以按租户、按分群精确到单个客户，粒度比切流量更细。
- **代价**：代码里长期存在两条分支，测试面翻倍（每个组合理论上都是一条路径，实际只能覆盖其中少数）；开关本身成为需要治理的资产 —— `owner` 与 `expires_at` 是这张表能长期活下去的最小代价，缺了这两列，开关数量会随发布次数单调增长。
- **失效点**：当开关数量增长到无人能列出全量组合时，这个模式的优点（灵活）反转为最大的运维风险 —— 因为**「代码能跑」与「这套开关组合能跑」是两件事**，而组合数随开关数指数增长，最终出故障的不是某个功能，而是某个从未被测试过的开关组合。此时必须靠 `expires_at` + 定期清理把组合数压回来（【经验】：一个季度内无人认领的开关应当视为可删除）。
- **真实使用**：商业与开源方案并存 —— LaunchDarkly（2014 年成立，见本章 §1.4）、Unleash、Flagsmith，以及基于配置中心（Apollo / Nacos）自建（本章 §2.3）。多数团队的做法是自建配置中心承载开关、只用商业方案承载实验类开关（【经验】）。

#### 3.2.5 A/B 测试（A/B Testing）

- **被什么约束逼出来**：灰度只能回答「新版本稳不稳」（技术指标），回答不了「新版本值不值得」（业务指标）；而这个问题的答案只能来自对照实验。
- **结构**：同一时间、两组用户、同一套指标，差异归因于版本；分群键必须稳定，样本量必须在实验前算好。

  ```text
  A/B：分群 + 指标 + 显著性
    流量 ──┬─► 对照组 A（旧策略）──► 指标
           └─► 实验组 B（新策略）──► 指标
  分群键必须稳定（user_id / device_id），否则用户在两组间漂移 → 效应被稀释
  判据不是「B 比 A 高」，而是「在 α 与统计功效约束下差异显著」
  样本量公式见本章 §2.2：n = (Z_{α/2} + Z_β)² · 2σ² / δ²
  → 观察窗口由样本量决定，不能由排期决定
  ```

- **为什么这样设计有效**：因为两组同时经历相同的外部环境（大促、天气、竞品动作），所以任何组间差异都只能归因于版本 —— 这是**同期对照**相对「上线前 vs 上线后」的根本优势，后者无法把版本效应与时间效应分开。
- **代价**：需要可测量的、短周期就能反映的业务指标，且样本量与指标方差强相关 —— 长周期指标（留存、生命周期价值）在小流量下几乎无法在可接受的窗口内得到显著结论；同时实验组要承担「跑一个更差的版本」的业务损失，这是实打实的成本。
- **失效点**：当指标方差大或效应量小而流量不足时，「用真实流量验证效果」的优点反转为缺点 —— 因为**实验会在窗口结束时给出一个「看起来显著但不为真」的结论**（α 就是为此设的误判率），而团队往往在窗口结束时把不显著当作「没有差别」、把显著当作「可以全量」，两种误读都会产生错误决策。此时正确做法是事先算样本量、事后不延长窗口。
- **真实使用**：「营销 / 转化 / UI 改版」的标准手段；开源与商业方案并存（GrowthBook、Optimizely），大型互联网公司多为自研实验平台（本章 §2.3）。**A/B 与灰度的分工是：灰度管稳定性，A/B 管业务效果**（【经验】）。

#### 3.2.6 影子流量（Shadow Traffic）

- **被什么约束逼出来**：新逻辑带写副作用，不能拿真实用户去试；同时又不能等「全量之后再发现问题」—— 需要一种「跑了但不算数」的验证方式。
- **结构**：请求复制一份走新链路，结果丢弃；**副作用隔离点是这个模式的全部要害**。

  ```text
  影子流量：复制请求，丢弃响应
                                 ┌────────────────┐
    真实请求 ──► 主链路 ──► 响应 ──► 用户
         │
         └─(异步复制)─► 影子链路 ──► 结果丢弃
                            │
                     副作用隔离点（要害）：
                       写操作 → 影子库 / 只读副本 / 直接屏蔽
                       外部调用（支付 / 短信）→ 必须屏蔽
  回滚 = 停掉复制（主链路自始未变，因此没有回滚动作）
  ```

- **为什么这样设计有效**：因为影子链路的输出不参与用户可见的结果，所以**它不可能造成用户可见的故障** —— 这让「用生产流量验证」这件事第一次变得无条件安全，也让它成为重构与性能基线验证的首选（重构验证、性能基准测试、新模型预热）。
- **代价**：资源成本约翻倍（同一份流量被处理两次，且常常是高峰时段）；需要维护请求复制与隔离机制，且复制必须异步、不能拖慢主链路 —— 这要求复制侧有独立的超时与熔断。
- **失效点**：当影子链路的写副作用没有被隔离时，「不影响用户」这个优点直接反转为数据污染 —— 因为影子链路写的是同一套下游（真实库、真实队列、真实第三方接口），**影子流量会以 100% 的真实数据量写入影子系统之外的系统**，轻则重复扣款/重复发券，重则污染训练数据（「新模型预热」场景恰好最容易踩这条）。
- **真实使用**：本章 §1.4 记载 Facebook 于 2005 年提出 Dark Launch（在生产跑新代码但不让用户看到结果），可视为该模式的早期形态；读路径复制的典型工程实现是 GitHub 开源的 Scientist（【公开：GitHub Scientist 官方仓库，2016 年开源，以仓库当前版本为准】）。判断某系统是否真的做了影子隔离，看它的写操作去向了哪个库（【经验】核验方法）。

#### 3.2.7 可逆发布（Reversible Release）

- **被什么约束逼出来**：存在一类变更是「单向门」—— Schema 删列、字段语义变更、数据迁移、模型换底座；它们的**回滚成本高于上线成本**，因此不能用「先上线、不行再退」的方式规划。
- **结构**：它不是一种发布方式，而是一组流程约束：把不可逆动作压到流程最后一步，前面每一步都可逆。

  ```sql
  -- 可逆发布的核心是「扩展-收缩」四阶段，不是某个工具
  -- 阶段 1 扩展（新旧代码都能读写，不删不改任何旧结构）
  ALTER TABLE orders ADD COLUMN channel_code VARCHAR(16);   -- 只加
  -- 阶段 2 双写 + 回填 + 对账（差异率收敛到阈值以下才进入下一阶段）
  -- 阶段 3 切读（先读新列，旧列继续保留并继续写）
  -- 阶段 4 收缩（确认不再需要回滚后，才 DROP 旧列）
  -- 单向门动作集中在阶段 4；阶段 1–3 每一步都可逆
  -- 工具示例：pt-online-schema-change / gh-ost 解决的是「阶段 1 不锁表」，
  --           不解决「阶段 4 能不能反悔」——这仍要靠流程约束
  ```

- **为什么这样设计有效**：因为每个阶段都保留上一阶段的完整信息（旧列还在、旧代码还能跑），所以任意时刻的回滚都退化为「改回上一步的状态」，而不是「重建已丢失的数据」—— 它把一次性的大赌注拆成了若干次小赌注。
- **代价**：一次 Schema 变更要跨多个发布周期才能走完（阶段 2 的对账期通常以天计，【经验】），期间代码必须同时处理新旧两种形态，写入放大（双写）与对账作业的持续算力是必然支出；且需要有人真的在阶段 4 之后回来清理，否则「临时保留」会永久保留。
- **失效点**：当团队把「加列」当成完整的可逆发布、却跳过了对账时，这个模式的可靠性反转为虚假安全 —— 因为没有对账的双写只是把不一致藏起来，**回滚回旧列时会读到一份从未被写满的数据**，此时系统不报错但结果错误。判断方法很直接：阶段 2 有没有一个可度量的差异率指标。
- **真实使用**：MySQL 生态普遍使用 Percona Toolkit 的 pt-online-schema-change，或 GitHub 开源的 gh-ost 完成不锁表的在线变更（【公开：Percona Toolkit 与 gh-ost 官方文档 / 仓库，以当前版本为准】）。需要强调：这些工具解决的是「变更期间不锁表」，**不解决「变更能不能反悔」**（【经验】）。

#### 3.2.8 渐进式交付（Progressive Delivery）

- **被什么约束逼出来**：人工盯盘不可持续 —— 发布次数、观察窗口长度、值班人力三者相乘超过了团队可承受的工时；同时阈值必须能被**写成配置**，写不出阈值的变更无法交给控制器。
- **结构**：把金丝雀、蓝绿、Feature Flag、A/B 编排进 CI/CD，由控制器按预定义 step 推进并按指标自动回滚。

  ```text
  渐进式交付：把「人看指标决定」换成「控制器按指标决定」
    提交 ──► CI ──► 滚动/灰度控制器（Argo Rollouts、Flagger、Spinnaker 类）
                       │  ① 按 step 切权重（如 5% → 20% → 50% → 100%）
                       │  ② 每个 step 结束后自动跑指标分析
                       │  ③ 超阈值 → 自动回滚；达标 → 推进 next step
                       ▼
                指标平台（错误率 / P95 / 自定义业务指标）
  人的角色：发布前定义 step 与阈值；而不是发布中盯着屏幕
  ```

- **为什么这样设计有效**：因为决策规则在发布前就以代码形式固化，所以每一次推进都不依赖「当时谁在值班」——**决策与执行被解耦，回滚不再受人的响应速度限制**。
- **代价**：阈值与 step 成为必须维护的配置资产，指标口径不一致时控制器会做出错误动作（把一次正常变更自动回滚掉，或该回滚时判为通过）；引入控制器本身就是新增一个故障面，控制器不可用时发布通道整体不可用。
- **失效点**：当指标口径本身不稳定（上游统计任务延迟、埋点变更、采样率调整）时，「自动决策」的优点反转为「自动犯错」—— 因为控制器无法区分「业务真的变差了」与「指标数据本身出了问题」，它会在数据管道抖动时触发回滚，**把发布系统变成指标管道的下游受害者**。因此自动化之前必须先保证指标的口径稳定性与新鲜度可查。
- **真实使用**：Argo Rollouts（2020 年进入 CNCF 项目体系）与 Flagger（2021 年，见本章 §1.4）是该模式在 Kubernetes 生态的代表实现；Spinnaker（2014 年开源，见本章 §1.4）是更早的统一发布平台（【公开：见本章 §1.4 演进历程所列时间线】）。

#### 3.2.9 AI 时代的智能灰度（AI-Driven Gray Release）

- **被什么约束逼出来**：信号维度爆炸 —— 模型效果、Agent 行为、Prompt 变更的影响无法用几条阈值规则穷举，人工写不全判据。
- **结构**：把「阈值规则」换成「模型判断」，但**执行权必须留在可审计的控制器手里**。

  ```text
  智能灰度：模型只做判断，不做执行
    输入信号：技术指标 + 业务指标 + 用户反馈 + 模型自评 / 影子对比
         │
    ┌────┴────────────────────────────────┐
    │ ① 灰度比例推荐（先 1% 还是先 5%）      │
    │ ② 异常识别（阈值规则覆盖不到的长尾模式）│
    │ ③ 回滚触发建议（含「人未及时响应」兜底）│
    └────┬────────────────────────────────┘
         ▼
    控制器执行：继续 / 暂停 / 扩大 / 回滚   ← 可审计、可复盘
    Agent 类变更额外前置：沙箱测试 + 安全审计（见 §3.5 反模式 8）
  ```

- **为什么这样设计有效**：因为模型的输入可以包含**规则表达不了的高维信号**（多次会话的语义漂移、工具调用成功率、用户追问率），所以在规则写不全的场景里，它能比固定阈值更早注意到异常；同时因为执行权仍在控制器手里，判断错误的上限被限制在「多回滚一次」。
- **代价**：引入一个本身需要灰度、需要评估、需要监控的组件（判断器自己也会退化）；且判断结果的可解释性下降 —— 当模型说「建议回滚」而指标全绿时，团队需要额外机制来建立信任，否则会变成「没人敢用」或「盲目照做」两个极端。
- **失效点**：当模型判断被直接接到执行动作上（取消人工确认与审计）时，「更早发现异常」的优点反转为**不可复盘的自动事故** —— 因为判断器出错时没有任何一层能拦住它，而事后无法解释「当时为什么回滚」，也就无法修正判断逻辑。这类模式的失效点不在准确率，而在**权力边界**：判断与执行必须分离。
- **真实使用**：模型侧灰度（影子模型 → 金丝雀 → A/B）已是 MLflow / KServe 一类模型服务平台的常见能力（见本章 §1.4 时间线中 2023 年一栏）；Agent 侧（Prompt 灰度、工具灰度）尚属前沿实践，多数团队仍在「Feature Flag + 安全审计」阶段（【经验】）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 无状态 Web 服务、流量大、新旧可并存 | 金丝雀 + 自动回滚 | 不用滚动发布：滚动按实例切分，无法保证同一用户命中同一版本 | 路由层能否按权重切流 |
| 实例多、无状态、要快速全量 | 滚动发布 | 不用蓝绿：两套环境常驻的机器成本不可接受 | 实例是否真的无状态、就绪判据是否可靠 |
| 回滚必须秒级、环境成本可承受 | 蓝绿发布 | 不用金丝雀：回滚要重新部署，达不到秒级 | 数据层是否已外置、切流是否原子 |
| 数据库 Schema 变更 | 扩展-收缩 + 双写 + 影子表 | 不用单纯金丝雀：Schema 不是流量能切的维度 | 变更向后兼容（加列）还是不兼容（删列/改语义） |
| 数据迁移 | 双写 + 对账 + 灰度读 | 不用一次性割接：割接失败时没有可退的中间态 | 对账差异率能否收敛到阈值以下 |
| 新模型上线 | 影子模型 → 金丝雀 → A/B | 不跳过影子：模型带写副作用时会污染线上特征/样本 | 模型是否只读、离线指标是否可信 |
| Agent 配置变更（Prompt / 工具） | Feature Flag + 安全审计 | 不用单纯灰度：灰度看不出提示词注入与工具滥用 | 是否有沙箱与可回退的审计开关 |
| 营销活动 / 转化实验 | A/B 测试 | 不用金丝雀：技术指标答不了「哪个转化更好」 | 样本量能否在窗口内凑够 |
| 大促前的变更 | 分群灰度 + 演练 | 不用全量灰度：大促期不允许把风险摊到全量 | 回滚路径是否被实际演练过一次 |
| 跨 Region 发布 | 地域灰度（Region A → Region B） | 不用全局金丝雀：Region 间故障域与用户分布不同 | 故障域是否按 Region 隔离 |
| 内部工具发布 | 轻量灰度（白名单先开） | 不用完整流水线：影响面小，收益低于建设成本 | 使用者是否可枚举 |

**本主题下最常被误选的一对，是「金丝雀」与「可逆发布」。** 两者都会被说成「渐进式、可回滚」，但机制完全不同：金丝雀是**把流量从 100% 收到 1% 再放回去**，它要求新旧版本能共存；可逆发布是**把不可逆动作推迟到流程最后一步**，它恰恰是在新旧不能共存时（Schema 语义变更）唯一可用的方法。误选的后果很具体：团队对一次「字段语义变更」上了金丝雀，发现 1% 流量也在写新语义的数据 —— 此时**数据已经被新语义污染，回滚流量解决不了数据问题**，只能靠人工修数据，事故规模远大于不灰度。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：金丝雀 + Feature Flag（切流量 × 切功能）。** 金丝雀负责「哪份代码在跑」，Flag 负责「哪些功能开着」，二者正交：代码可以先全量，功能仍锁在 1% 租户上。职责边界在于 —— 兼容性问题由金丝雀暴露，功能开关负责即时止血。运维代价是两套控制面（发布系统 + 配置中心）与开关生命周期治理（`owner` + `expires_at`）。适合每天多次发布、且功能需要按租户开关的中大型产品。

**组合 B：影子流量 + 双写对账 + 扩展-收缩（数据变更专用）。** 影子链路用真实流量验证新逻辑但不参与结果；双写 + 对账保证两份数据收敛；扩展-收缩把 Schema 变更拆成四阶段并让前三阶段可逆。职责边界在于 —— 影子负责「逻辑对不对」，对账负责「数据一致不一致」，扩展-收缩负责「能不能反悔」。代价是写入放大（一份数据写两处）加上对账作业的持续算力，且全流程要跨多个发布周期。适合体量大到拿不到停机窗口的在线库。

**组合 C：渐进式交付控制器 + 指标平台 + 自动回滚。** 控制器负责按 step 推进与自动回滚，指标平台提供判据。职责边界是：控制器只管流程，判据的口径归指标平台，谁都不越界。代价是必须先统一指标口径 —— 否则控制器会拿一份不稳定的数据做决策，把发布通道变成指标管道的下游受害者。适合发布频率高、值班人力不足的团队。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 1. Feature Flag 滥用 | 开关数量持续增长，存在「无人能说出全量组合」的状态 | 代码路径组合数随开关数指数增长，故障来自从未被测试的组合而非某个功能 | 新增开关不需要任何审批，删除开关却要评估风险 —— 成本不对称 | 表结构强制 `owner` + `expires_at`；到期未清理告警；按季度清理 |
| 2. 灰度只看均值 | 看板上只有平均 QPS / 平均延迟 | 长尾恶化被均值稀释，P99 与特定分群的问题在灰度期不可见 | 均值是默认指标，分位数与分群需要额外建设 | 看 P50/P95/P99/P999 + 按分群切指标；阈值挂在分位数上 |
| 3. 灰度无明确成功标准 | 灰度已放到 30%，但没人能回答「什么条件下回滚」 | 判据缺失时，回滚决策依赖当时值班人的情绪，故障会被放大到 100% | 阈值需要在发布前定义，而发布前最没人愿意停下来算阈值 | 发布前写死继续/暂停/回滚三组阈值，并落进流水线配置 |
| 4. 回滚「以为能回滚」 | 上线后才发现数据已被写入且不可逆 | 系统能切回旧版本，但旧版本读到的是新版本写的数据，**不报错但算错** | 回滚路径从未被演练，团队只验证了「部署系统支持回滚」这个能力 | 把回滚路径写进发布清单并实际演练；单向门变更走扩展-收缩 |
| 5. 灰度过快 / 过慢 | 1% → 100% 十分钟走完；或 1% → 10% 拖三天 | 过快等于没观察（信号还没出来就已全量）；过慢则回滚窗口被人为拉长，业务损失持续累积 | 节奏没有与风险等级绑定，只有默认值 | 按风险分档设定节奏：低风险小时级全量、中风险天级、高风险周级（【经验】） |
| 6. 忽视「数据灰度」 | 代码走了完整灰度，Schema 与迁移却是全量执行 | 数据层一旦全量执行，上层再精细的灰度也失去回滚能力 | 数据变更由 DBA 或单独流程处理，不在发布流水线上 | 数据变更同流水线：Online Schema Migration + 双写 + 影子表 + 对账 |
| 7. AI 模型灰度只看技术指标 | 模型上线后只监控 QPS、延迟、错误率 | 技术全绿但业务效果下跌，模型会带着「健康」的指标长期留在线上 | 监控体系先于业务指标建设，且业务指标归因周期长 | 模型灰度与 A/B 绑定，看 CTR / 转化率 / 用户满意度等业务指标 |
| 8. Agent 灰度忽视安全审计 | Agent 的 Prompt / 工具配置直接上线，只做技术灰度 | 提示词注入、工具越权、数据外泄这类问题**在技术指标上完全没有信号** | 配置变更被视为低风险（「只是改个文案」），安全评审不在发布流程内 | Agent 配置变更走灰度 + 沙箱测试 + 安全审计，且审计开关可回退 |

**反模式 4（回滚「以为能回滚」）是后果最重的一条，因为它是静默的。** 它在生产中的典型暴露方式是：发布本身成功、监控全绿、回滚也「成功」了 —— 直到某个下游报表在几天后出现对不上的数字。此时已经无法判断哪些数据是新版本写的、哪些是旧版本写的，只能靠人工全量重算。它的根因不是工具不行，而是**「部署系统支持回滚」与「这次变更可逆」被混为一谈**：前者是能力，后者是设计约束。

**反模式 2（只看均值）在灰度场景下格外危险。** 灰度期流量只占 `p`，长尾样本量按 `p` 同比缩减 —— 一个只影响 1% 用户的缺陷，在 1% 灰度流量下只有万分之一的样本（【推算】：1% × 1% = 0.01%），几乎不可能在 5–30 分钟的窗口里被均值指标发现；而放到 50% 时它已经影响了 0.5% 的真实用户（同一条乘法）。**恒等地说：灰度比例越小，长尾问题越容易被「稀释成不存在」**（【经验】）。

**反模式 8（Agent 灰度忽视安全审计）是 AI 时代新增的一条。** 它与前七条的区别在于**故障形态不同**：前七条的失效表现为「系统坏了」，这条表现为「系统按预期工作，但被诱导做了不该做的事」。这类问题没有延迟、没有错误率、没有超时 —— 技术灰度看板上一切正常，因此必须把安全检查前移到发布流程（沙箱测试 + 提示词注入用例集 + 工具权限最小化），而不是指望灰度期的指标发现它。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的。**规模或发布频率跨过某个阈值时，原来正确的模式会变成错的** —— 而且通常不是「变差」，是「变成事故源」。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 实例数 10 → 1000 | 手工分批滚动 | 人手替换跟不上副本数与发布频率 | 控制器驱动的滚动 / 渐进式交付 | 必须先把健康检查与就绪判据做可靠，否则控制器会带着坏实例推进 |
| 发布频率每周 → 每天多次 | 人工灰度 + 人工盯盘 | 观察窗口 × 发布次数的盯盘工时超过人力 | Feature Flag 解耦部署与发布 + 自动回滚 | 开关数量增长，必须同时建立 `owner` 与过期机制，否则换来反模式 1 |
| 单 Region → 多 Region | 全局金丝雀 | Region 间故障域与用户分布不同，全局灰度把风险同步扩散 | 地域级灰度（Region A 先全量） | 数据同步链路要支持「部分 Region 跑新版本」，一致性模型更复杂 |
| 应用内路由 → 服务网格 | 各服务自写权重逻辑 | 每套实现口径不一，回滚行为不可预测 | 权重路由下沉到网格 | 网格本身成为新故障面，且需要统一的指标出口 |
| 模型按季度上线 → 按周上线 | 人工 A/B | 每轮实验的样本量与排期冲突，结论被排期逼出来 | 影子 + 自动实验流水线 | 需要特征回放能力与实验平台，否则实验不可复现 |
| 无安全评审 → 有 Agent 线上变更 | 技术指标灰度 | 安全类故障在指标上无信号 | 沙箱 + 审计门禁 + 可回退开关 | 审计用例集与权限模型成为必须维护的资产 |

### 3.7 自检清单

1. 这条变更**删掉了**任何东西吗（列、字段语义、接口、索引）？删了就是单向门，必须先做扩展-收缩，再谈灰度。
2. 灰度阶梯的**每一级**，观察窗口是否长到覆盖最慢的指标（T+1 报表、按小时聚合）？覆盖不到的那一级等于没有。
3. 回滚动作是否**被真的执行过一次**（演练或上一次真实发布）？没演练过的回滚路径不算路径。
4. 自动回滚的阈值写下来了吗 —— 错误率、延迟、业务指标各自的倍数与观察窗口是否明确？
5. 判据用的是均值还是**分位数 + 分群**？P99/P999 有没有被单独看？
6. 每个 Feature Flag 是否有具体 `owner` 与 `expires_at`？是否存在「开启超过一个季度且无人认领」的开关？
7. 灰度期间新旧版本是否共享同一份存储？如果是，写入冲突与读偏斜（同一用户读到不同状态）由谁负责？
8. 影子链路的**写操作**是否被隔离（影子库 / 只读副本 / 直接屏蔽）？外部调用（支付、短信）是否被屏蔽？
9. 模型或 Agent 配置变更是否走了安全审计与沙箱，而不只是技术指标灰度？
10. 这次变更的回滚时间目标是多少秒？它由哪个动作决定 —— 切流量、换镜像、还是反向重放数据？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 新旧可并存、要缩小影响面 | 金丝雀发布 | 控制量只有权重一个，回滚 = 把权重设回 0 |
| 要秒级回滚、环境成本可承受 | 蓝绿发布 | 回滚是原子切流，不依赖重新部署 |
| 实例多、无状态、要快速全量 | 滚动发布 | 用同一批机器原地替换，不需要第二套环境 |
| 部署与发布要解耦 | Feature Flag | 开关是配置，关闭不需要走发布流程 |
| 要判断「值不值得」 | A/B 测试 | 只有同期对照与显著性检验能回答因果问题 |
| 有写副作用、不能拿真实用户试 | 影子流量 | 复制请求、丢弃响应，故障上限是「无用功」 |
| 存在单向门变更 | 可逆发布（扩展-收缩） | 把不可逆动作压到流程最后一步 |
| 发布频繁、人力不足 | 渐进式交付 | 把人从盯盘挪到「发布前定义 step 与阈值」 |
| 信号维度多、阈值写不全 | AI 智能灰度 | 模型识别长尾异常，执行权仍留在可审计的控制器 |

> 本节小结：本主题下**决定模式选择的唯一那条约束是「变更的可逆性」**。可逆的变更，力气花在「切流量与观察」上；不可逆的变更，力气必须花在「造出兼容态、把单向门动作推到最后一刻」上。所有关于灰度比例、阶梯、观察窗口的争论，都只在可逆性给定的前提下才成立 —— 顺序颠倒了，工具越好，事故越大。
>
> 💡 **思考锚点**：拿你下一次要上的变更先判它落在哪一档可逆性：如果不能靠「权重设回 0」或「关掉 Feature Flag」回滚，你会先在流程里造出哪个兼容态、把那个单向门动作推到第几步——而你现有的观察窗口和阶梯，是按可逆那一档定的还是按不可逆那一档定的？
