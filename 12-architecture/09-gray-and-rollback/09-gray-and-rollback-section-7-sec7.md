## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

**第一，打分把「一体两面」拆成了两个独立维度。** 打分给蓝绿的资源成本 2 分、给滚动发布 5 分，又给蓝绿的回滚速度 5 分、给滚动 3 分。这两组分数不是两条可以分别优化的性质，而是**同一条机制的两面**：蓝绿用「常驻两套完整环境」换来「一次指针操作即可回滚」，滚动用「不占额外资源」换来「回滚要重新拉起旧版本」。读者看到的是「各有优劣」，而真实情况是你**只能选其中一面**——分数把这条约束藏了起来。

**第二，打分表里缺了本主题最关键的一列：你改的是什么对象。** 蓝绿、金丝雀、Feature Flag 切分的是**请求或配置**，回滚是把一个指针或一个布尔值切回去；双写、影子表、Online Schema Migration 切分的是**已经落库的数据**，回滚是反向写回。前者的回滚代价与你改了多少数据无关，后者成正比——这一条差异比所有维度加起来更能决定选型（见 7.3.1）。

**第三，决策树里把可测量的量换成了形容词。** 决策树第二问是「你的回滚难度如何」，分简单 / 中等 / 复杂三档。回滚难度在本主题里是可算的（切的是请求还是数据、要不要反写、产物被消费过没有），把它写成形容词之后，阈值就只能靠感觉给。

**第四，「AI 友好度」这一列的真实含义是「判定与生效是否解耦」。** 打分给 Feature Flag 与 A/B 各 5 分、给蓝绿 3 分。Feature Flag 在 AI 场景里得分高的原因不是它本身是 AI 工具，而是模型权重、Prompt、工具描述这类对象的版本缺少内容寻址（[§ 5 前沿演进](09-gray-and-rollback-section-5-ai.md) §5.2.1 的三个前提），**只有把「生效」从「部署」里拆出来，才谈得上按比例切换与快速切回**。打分把这条因果关系盖住了。

**第五，决策树的两棵子树其实是同一个问题。** 决策树的第一棵按「变更类型」选机制（应用代码 / Schema / 数据迁移 / AI 模型 / Agent 配置 / 产品功能），第二棵按「回滚难度」选兜底（简单 / 中等 / 复杂）。但回滚难度并不是第二个独立维度——**它正是由变更的切分单元决定的**（7.3.1）：切请求与切配置的一律落在「简单」，切已落库数据的一律滑向「复杂」。按变更类型选完机制之后，第二棵树给出的答案通常是重复的；而重复的两棵树会掩盖真正需要单独判断的那件事：**这次变更里有哪些部分一旦发生就撤不回**。

因此本章不排序，只做三件事：**按「切的是哪一类对象」分族**（同族内部差异远小于跨族差异），**给每条机制写清它在什么条件下优势成立、什么条件下消失**，最后把决策落到几个能从现有监控与发布系统里直接取到的量上。

**本章所有数字按三档标注**：【公开】（有可定位的出处，正文给出处，出处为本书其它小节时给出小节号与核验入口；**凡条目本身不含年份主张的——规范、产品的长期能力、通用统计方法——正文会说明这一点，并请以官方文档当前版本为准**）、【推算】（由公开前提推导，正文写出推导链，区间两端都必须能从链上得到）、【经验】（行业普遍实践，只给区间与条件，不给精确值）。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 切分单元 | 变更被按什么切开：请求 / 实例 / 环境指针 / 数据行 / 配置判定 | 它决定回滚是 O(1) 还是 O(n)，也决定灰度比例的最小粒度（不能按请求切分时，粒度被副本数钉死） |
| 检出能力 | 在可接受的观察窗口内，这套机制能看见多小概率的故障 | 灰度比例与观察窗口不是「小心程度」的旋钮，而是检出概率的两个因子（7.3.2 有换算） |
| 共存窗口与兼容性 | 新旧版本共存多久，期间旧版本的读路径还读不读得懂新版本写的数据 | 共存窗口把「向后兼容」从建议变成准入条件：不兼容的变更在滚动下必然故障，在蓝绿下只是切换顺序问题 |
| 判定与生效是否解耦 | 关掉一个功能要不要重新部署 | 决定回滚落在秒级还是分钟级，也决定代码里长期驻留几条分支 |
| 不可逆面 | 这次变更里有哪些东西一旦发生就撤不回（已写的数据、已消费的特征、已产生的模型输出） | 决定这次变更适不适合用「灰度比例」去控，还是必须走变更评审与可回滚设计 |
| 人的响应时间 | 从指标异常到有人做出决定要多久 | 自动回滚的阈值必须设在「比人快」的位置，否则触发条件只是纸面配置 |

> 这 6 条的权重随处境移动：单服务、几百 QPS 时，「判定与生效是否解耦」最先起作用（它决定你能不能在不发版的情况下止血）；跨团队、多消费方之后，「共存窗口与不可逆面」成为硬约束；引入模型与 Agent 之后，「错误可观测性」（§5.2.1 的判据从可用性变成质量）才进入前三。**切分单元**是个例外——它在任何规模下都要先确认，因为它直接决定回滚代价的量级。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 蓝绿发布 | 两套完整环境 + 一次指针切换 | 变更与回滚都作用在**环境指针**上，是 0/100 的原子操作 | 需要秒级回滚、且能常驻双份资源的大型应用 | 平台能力（Spinnaker 一类） |
| 滚动发布 | 逐实例替换 | 切分单元是**实例副本**，编排器控制替换节奏与共存窗口 | K8s 上的无状态服务（默认策略） | 编排器自带 |
| 金丝雀发布 | 按比例放量 | 切分单元是**请求**，比例由流量入口（网关 / 服务网格 / LB 权重）决定 | 流量大的在线服务、模型服务 | Argo Rollouts / Flagger 一类（CNCF 项目） |
| Feature Flag | 配置态开关 | 把「部署」与「生效」解耦，切分单元是**判定表达式**（一致性哈希） | 需要定向开关、暗启动、快速止血的团队 | LaunchDarkly（商业）/ Unleash、Flagsmith、Split.io（商业或开源）/ GrowthBook（开源）/ Apollo、Nacos、Spring Cloud Config（配置中心）|
| A/B 测试 | 实验分组 | 分组为**统计功效**服务，不为风险控制服务 | 产品、推荐、增长实验 | GrowthBook（开源）/ Optimizely（商业）/ 自研 |
| 影子流量 / 影子模型 | 复制流量但不返回用户 | 变更在**用户之外**验证，失败不触达用户 | 重构验证、模型预热、性能基准 | 流量录制与回放能力，多为自建 |
| 数据灰度（双写 + 影子表 + Online Schema Migration） | 数据与结构的分步切换 | **写与读是两个独立开关**：先双写、再切读、最后停旧写 | 表结构变更、数据迁移、口径切换 | gh-ost / pt-online-schema-change / pg_repack（见 §4.3 工具表）|
| 模型 / Agent 灰度（模型、Prompt、工具、配置） | 非确定产物的按比例切换 | 复用流量切分，但**回滚不等于恢复原状**（已产生的输出不消失） | AI 服务、Agent 平台 | MLflow / KServe / Seldon 一类（见 §4.3）|
| 灰度回滚（本章形态） | 渐进式发布 + 自动回滚 + 发布门禁 | 把上面几件组装成一条带判据与止血动作的流水线 | 需要同时满足「敢高频」与「能快速止损」的组织 | 平台自建，能力组合 |

> 表中产品的年份与沿革见主文件 §1.4 与 [§ 4 工程实现](09-gray-and-rollback-section-4-sec4.md) §4.3 的工具表；本条只取「这些工具长期存在、其能力以各自官方文档当前版本为准」这一判断，不在此处断言具体版本号与发布日期。

这 9 个候选分成**四族**。分族的依据不是品牌、也不是开源或闭源，而是**变更被切开的那一类对象**：

- **族一 · 切请求 / 实例 / 指针（代码与配置层）**：蓝绿、滚动、金丝雀、影子流量。它们的回滚都是「把一个动作切回去」——指针、副本、路由权重、流量副本，**代价与已处理的数据量无关**。
- **族二 · 切配置判定（生效层）**：Feature Flag、模型 / Prompt / 工具灰度。它们把「生效」从「部署」里拆出来，于是回滚不必经过发布流水线。
- **族三 · 切实验分组（判据层）**：A/B 测试。它与其他族不是竞争关系——它不降低风险，只回答「新版本是不是更好」，因此常常**叠在族一之上**而不是替代族一。
- **族四 · 切数据（不可逆层）**：数据灰度、双写、影子表、Online Schema Migration，以及特征 / 标签一类产物。**这一族的回滚代价随「已经写进去多少、被谁消费过」增长**，与其他三族的形状根本不同。

**先分族再选，能省掉一半比较**：族一内部比的是资源与粒度（要不要双份、粒度能不能到请求级），族二内部比的是治理（flag 谁来清理、有没有 owner），族四内部比的是可逆路径的划分。跨族之间才出现真正的机制差异（7.3.1）。**每族的典型失败方式也不同，这比典型优势更有用**：族一死于「把兼容性当成建议」——共存窗口内旧版本读到新结构的数据；族二死于「只开不关」——flag 数增长而清理责任消失（§3.3 反模式 1）；族三死于「样本量不足」——用 1% 流量去验证小数点后的提升，然后在噪声上下结论；族四死于「以为能回滚」——上线后才发现数据已经被消费（§3.3 反模式 4）。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 切分单元决定回滚代价的形状：O(1) 还是 O(n)

**机制是什么**：任何灰度机制都在做同一件事——把变更切开，让一部分命中新版本、一部分命中旧版本。**切分单元**就是「按什么切」：请求、实例、环境指针、配置判定，还是已经落库的数据行。回滚的代价由这个单元上的操作代价决定，而不是由工具决定。

**它在各候选中的实现差异**：

| 候选 | 切分单元 | 回滚动作 | 回滚代价与什么成正比 | 回滚速度量级 |
| --- | --- | --- | --- | --- |
| 蓝绿发布 | 环境指针（0/100） | 把负载均衡指向旧环境 | 与数据量无关（O(1)） | 秒级 |
| 滚动发布 | 实例副本 | 用旧版本镜像重新替换回来 | 实例数（O(实例数)） | 分钟级 |
| 金丝雀发布 | 请求 | 把路由权重切回旧版本 | 与已处理请求量无关（O(1)） | 秒级 |
| Feature Flag | 判定表达式 | 改一个配置位 | 与部署无关（O(1)），但只覆盖开关内的分支 | 秒级 |
| 影子流量 | 流量副本 | 停掉复制与对比，不影响用户 | O(1) | 秒级，且本来就不需要 |
| 双写 / 影子表 | 数据的写路径 | 把读切回旧表；已写入的新数据要单独处理 | **已写入行数 + 已消费方数（O(n)）** | 读切回分钟级；数据修复小时到天级 |
| Online Schema Migration | 表的存储形式 | 反向改表或回退到旧表 | 表体积（O(表大小)） | 小时级 |
| 模型 / Prompt 灰度 | 请求（一致性哈希） | 切回旧版本 | 与请求量无关，但**已产生的输出与已发生的调用撤不回** | 秒级（流量）+ 不可逆（产物） |

**由此必然导出的性质（因果句）**：因为**蓝绿把变更作用在环境指针上**，所以回滚是一次原子操作、与数据量无关，代价是它要求「切换瞬间两套环境都完整可用」——这既是它常驻双份资源的原因，也是它在共享数据库上会失效的原因：**一旦新版本已经改过 schema，把指针切回旧环境得到的只是一台读不懂新数据的旧版本**。反过来，因为**数据灰度的切分单元是行而不是请求**，所以把流量切回去不会撤回已经写进新表、新字段的数据：回滚从一次指针操作变成一个**反写作业**，代价随「写了多少行、被多少下游消费过」增长。**这一条差异解释了本主题最重要的一句工程结论：数据与 Schema 变更不能靠「发现不对再回滚」，只能靠事前把不可逆变拆成多步可逆变**（[§ 6 落地实践](09-gray-and-rollback-section-6-sec6.md) 的阿里案例把它总结为「可回滚前置」，并给出更直白的一句：「秒级回滚」不是靠回滚工具做出来的，而是靠变更设计保证的——代码回退了但数据已按新格式写入，回滚根本不可能快）。

**这条机制也解释了 RTO 分级**：主文件 §2.2 把回滚 RTO 分成 30 秒（应用层）、5 分钟（Schema 兼容条件下）、30 分钟（需要数据修复）三档。**这三档不是按工具分的，是按「要不要数据修复」分的**——[§ 5 前沿演进](09-gray-and-rollback-section-5-ai.md) §5.2.3 把数据灰度拆成只读影子 / 幂等写入 / 已消费三类路径，划的正是同一条线。

**公开证据**【公开】：Kubernetes 的 Deployment 默认采用滚动更新并暴露 `maxUnavailable` / `maxSurge` 两个参数来控制替换节奏与共存窗口，判定入口是官方文档 Deployment 的 `strategy` 字段说明（本条描述的是长期存在的官方能力，不含年份主张）；本书 §4.2 的 Argo Rollouts 与 §4.2 的 Istio VirtualService 示例分别给出「按实例替换」与「按权重切流」两种实现；在线改表工具 gh-ost、pt-online-schema-change、pg_repack 的能力见 §4.3 工具表，具体版本与限制以各自官方文档当前版本为准。**其余年份与产品沿革沿用主文件 §1.4 的记述，不在本节重复断言。**

**失效条件**：当你的流量入口根本不支持按请求切分（例如只有 DNS 轮询或多副本直连）时，「金丝雀」实际得到的是实例级粒度，**你能设的最小比例是 1/副本数**——三副本环境下最小就是 33%。此时再讨论「1% 灰度」没有意义，要先补一个能按请求切分的入口，而不是把比例写在配置里自我安慰。

**失效的早期信号**：团队在讨论「灰度比例设多少」，却没人能回答「这个环境能切到的最小粒度是多少」；或者中途发现问题时的第一反应是「把比例调回去」，而对已经写进去的数据没有任何安排。

#### 7.3.2 检出能力：灰度比例 × 观察窗口 × 故障率

**机制是什么**：灰度能不能发现问题，取决于这三件事的乘积——**新版本承担了多少流量、你愿意等多久、故障本身多罕见**。它是一条可以算出来的约束，而不是「小心一点」。

**它在各类故障上的实现差异**：

| 你担心的故障 | 它的可观测形式 | 检出能力由什么决定 | 典型盲区 |
| --- | --- | --- | --- |
| 高概率故障（崩溃、启动失败、依赖不兼容） | 错误率、拒绝率、实例存活 | 极小的比例即可（第一次请求就可能暴露） | 几乎没有 |
| 中概率故障（部分请求超时、偶发 5xx） | 错误率、P99 延迟 | 比例 × 窗口 × 故障率 | 只看均值时被掩盖（§3.3 反模式 2） |
| 低概率但严重的故障（特定用户、特定数据触发的错误） | 业务指标、抽样日志、对账差异 | 需要足够大的样本量，或换一种不依赖流量的手段 | 流量比例小 + 窗口短 = 结构上看不见 |
| 「没坏但变差」（效果下降、回答质量下降） | 业务指标、质量指标 | 统计功效（样本量公式），不是风险判断 | 阈值没有天生数值（§5.2.1） |
| 副作用类（写错数据、发错消息） | 对账、幂等键冲突 | 与比例无关，**1% 的写错也是 100% 的真实副作用** | 灰度比例会给出虚假的安全感 |

**由此必然导出的性质（因果句）**：因为**新版本在单位时间内收到的故障样本数 = 总流量 × 灰度比例 × 故障率**，所以灰度比例与观察窗口是这个乘积里可以互易的两个因子——**比例降 10 倍，就需要把窗口拉长 10 倍才能看到同样多的证据**。【推算】以总流量 1 万 QPS 计（【经验】：中大型在线服务的常见量级，请代入自己的值），1% 金丝雀即新版本承担 100 QPS；若故障率是百万分之一量级（10⁻⁶），则期望的故障出现速率 = 10⁴ × 10⁻² × 10⁻⁶ = 10⁻⁴ 次/秒，**平均约 2.8 小时才出现一次**（1 ÷ 10⁻⁴ = 10⁴ 秒 ≈ 2.8 小时）——而多数团队的观察窗口是分钟到半小时量级【经验】，也就是说这套机制对这类故障**结构上看不见**。要在 30 分钟内攒到 3 次期望故障，需要把比例提到约 17%（3 ÷ (10⁴ × 1800 × 10⁻⁶) = 3 ÷ 18 ≈ 17%），那已经接近全量。**代价是：提高比例会把暴露面同比放大，两个方向不能同时要。**

**这条约束的正确解法不是调比例，而是换机制**：影子流量把「检出」与「暴露」解耦——它复制生产流量给新版本，但不把结果返回用户，因此它的样本量不受灰度比例限制（可以做到 100% 复制），失败代价近似为零；故障注入与回放同理，用主动制造稀缺样本替代被动等待。这也是 §5.2.1 建议「模型上线从影子开始、而不是从 1% 在线开始」的机制来源。

**公开证据**【公开】：样本量公式 n = (Z_{α/2} + Z_β)² × 2σ² / δ² 出自**主文件 §2.2「数学 / 形式化基础」**，[§ 5 前沿演进](09-gray-and-rollback-section-5-ai.md) §5.2.1 引用同一公式作为「证据量」的量化形式；A/B 测试的显著性水平与功效口径（α、1-β）是实验设计中的通用方法（本身不含年份主张），判定入口是任意统计学教科书或实验平台的官方文档，平台侧可另见 [§ 4 工程实现](09-gray-and-rollback-section-4-sec4.md) §4.3 的 A/B 测试平台工具表（该表列工具，不含公式）。**本节只把公式当作推导前提，具体样本量按你自己的方差与最小可检测差异代入计算。**

**失效条件**：当总流量本身很小（例如日均几千次调用）时，无论怎么调比例都不可能攒够统计意义上的样本，此时唯一可行的判据是**离线回放与影子对比**——把过去一段时间的真实输入重放给新版本，用输入输出差异代替在线比例。

**失效的早期信号**：观察窗口还没攒够样本就放量；或者把「窗口内没发现问题」直接写成「没有问题」，而没人算过这套比例 × 窗口能检出多小概率的故障。

#### 7.3.3 共存窗口：向后兼容从建议变成准入条件

**机制是什么**：任何渐进式发布都有一段**新旧版本同时在生产运行**的时间。这段窗口的长度由机制决定：滚动与金丝雀的窗口是「替换节奏 × 实例数」，双写的窗口是「双写持续到对账通过」，蓝绿的窗口在切换瞬间接近于零，Feature Flag 的窗口则可能长达数年。

**它在各候选中的实现差异**：

| 候选 | 共存窗口的形态 | 窗口由什么决定 | 窗口内必须成立的条件 |
| --- | --- | --- | --- |
| 蓝绿 | 切换瞬间（近似为零） | 切换动作本身 | 两套环境读同一份数据时，数据格式对两边都可用 |
| 滚动 | 逐实例替换期间，旧新实例同时服务 | 替换节奏 × 实例数 | 旧版本的读路径能读懂新版本写的数据 |
| 金丝雀 | 按比例并存，直到放量完成 | 放量节奏 | 同上，且同一用户不能因命中版本不同而看到不一致的状态 |
| Feature Flag | 两条分支并存，可能长期 | flag 的清理计划 | 两种开关状态下，数据语义都成立 |
| 双写 / 影子表 | 双写期 + 灰度读期 | 对账通过为止 | 两个写路径的一致性由对账保证（主文件 §2.3） |
| Online Schema Migration | 改表全过程 | 表体积与改表工具 | 改表期间旧代码与新结构兼容 |
| 模型 / Prompt 灰度 | 请求级并存 | 放量节奏 | 同一会话不能跨版本（否则产生「混版」形态的第三类行为，§5.2.4） |

**由此必然导出的性质（因果句）**：因为**滚动发布的新旧共存窗口由逐实例替换决定、且不需要额外资源**，所以它以最低的资源成本分散了风险，代价是这个窗口内**同一份数据会被两个版本读写**——于是「向后兼容」不再是建议而是准入条件：不兼容的读路径在滚动下**必然**故障，而在蓝绿下只是切换顺序问题（先停旧、后起新，代价是一段短暂不可用）。这就是「三种机制的兼容性要求不同」的源头，也解释了为什么「能不能滚动发布」本质上是一个数据格式问题，而不是部署工具问题。

**共存窗口还有一个常被忽略的代价：旧版本必须留得住**。回滚的前提是旧版本仍然可以被启动——镜像还在、依赖库还在、配置还在、对应的数据格式还在。**保留期短于最长观察窗口时，回滚能力会先于故障到来而消失**：上线一周后发现问题、却发现旧镜像已被清理，是这类事故最常见的形态之一。

**公开证据**【公开】：Kubernetes 的滚动更新语义与 `maxUnavailable` / `maxSurge` 的关系见官方文档 Deployment 章节（判定入口：该字段说明与 PodDisruptionBudget 的关系）；expand-migrate-contract 这一类「先加、再迁、最后收」的改表顺序是 Online Schema Migration 的通用做法，工具侧可见 §4.3 的 gh-ost / pt-online-schema-change / pg_repack 条目及其官方文档（本条描述的是长期存在的官方能力与通用做法，均不含年份主张）。**主文件 §2.1 与 §2.3 已给出影子表、双写与变更日志的机制描述，本节不重复。**其余年份与版本以官方文档当前版本为准。

**失效条件**：当变更的性质是「不可向后兼容」且不可拆分时（原地修改字段语义、破坏性删除），共存窗口无法成立，此时只能选蓝绿式的**短暂停写 + 原子切换**，并把停机窗口写进变更计划——把它伪装成「灰度」只会把一次可计划的停机变成一次不可计划的故障。

**失效的早期信号**：兼容性靠评审表态而不是靠一次回放验证；旧版本镜像与配置的保留期没人说得清；发布记录里没有「回滚需要哪些前置条件」这一栏。

#### 7.3.4 判定与生效的耦合度：解耦买到秒级回滚，付出分支债

**机制是什么**：**部署**是「让新代码跑在机器上」，**生效**是「让新行为被用户看到」。传统发布把两者绑在一起，Feature Flag 把它们拆开。拆开之后，「关掉一个功能」不再需要一次发布流水线，而只需要改一个配置位。

**它在各候选中的实现差异**：

| 候选 | 部署与生效 | 回滚要经过什么 | 回滚时间由什么决定 | 长期代价 |
| --- | --- | --- | --- | --- |
| 蓝绿 | 绑定 | 切指针 | 一次负载均衡操作 | 常驻双份资源 |
| 滚动 | 绑定 | 重新拉起旧版本 | 实例重启与就绪时间 | 需要保留旧镜像与配置 |
| 金丝雀 | 绑定 | 切路由权重 | 一次流量规则的生效时间 | 需要保留旧版本可用 |
| Feature Flag | **解耦** | 改一个配置位 | 配置中心的推送时延 | **两条代码分支长期并存**，测试矩阵按 flag 组合增长 |
| 模型 / Prompt 灰度 | 部分解耦（配置与权重可独立切） | 切回旧版本号 | 切换时延 | 历史输出不可撤回、版本缺少内容寻址 |

**由此必然导出的性质（因果句）**：因为 **Feature Flag 把「生效」从「部署」里拆了出来**，所以关掉一个功能不需要一次发布，回滚时间从「重新部署」（分钟级）压到「改一个配置位」（秒级）；代价是**两条代码路径长期同时存在于生产分支里**——每一个 flag 都是一次分支，任何一次改动都要在「开」与「关」两种状态下分别验证，而 flag 一旦没有 owner 与过期时间，分支数只增不减（§3.3 反模式 1 描述的正是这个终局）。**换句话说，秒级回滚不是免费的，它的账记在代码复杂度上，而不是记在基础设施上。**

**这条机制在 AI 场景里被放大**：模型权重与 Prompt 缺少代码那样的内容寻址，回滚切回去的是「一个版本号」而不是「一份确定的内容」（§5.2.1 的三个前提表），因此解耦带来的收益更高、同时「混版」的风险也更高——同一会话跨版本、同一次请求里 Prompt 与检索索引不同代，都会产生既不复现于旧版也不复现于新版的第三类行为。

**公开证据**【公开】：Feature Flag 服务的两条实现路线在本书 §4.3 工具表中给出——商业平台（LaunchDarkly）与开源 / 配置中心路线（Unleash、GrowthBook、Apollo、Nacos），按旗标评估的形态见主文件 §2.2 的一致性哈希示例（`hash(user_id) % 100 < rollout_percentage`）；判定入口是各产品官方文档中「flag 生命周期 / 归档」与「按用户哈希分桶」的说明（本条描述的是长期存在的产品能力，不含年份主张，具体能力以当前版本文档为准）。**本节不引用任何发布次数或回滚耗时的第三方数字**——本书 §6 的四个案例是工程做法综述，其中的数字由本书汇总，不构成可独立复核的第三方测量。

**失效条件**：当 flag 数量增长到无人能列出「现在有哪些开关会影响这个请求」时，解耦收益被分支债吃光——此时正确的动作不是上更快的配置中心，而是把 flag 纳入有 owner、有过期时间的生命周期管理（§3.3 反模式 1 的正解）。

**失效的早期信号**：没人能列出「现在有哪些开关会影响这个请求」；或回滚演练时发现「关掉开关」与「切回旧版本」得到的结果不一致——那说明有一部分行为已经不在开关的控制范围内了。

### 7.4 成本结构对比（不是价格表，是成本函数）

各候选的成本函数**形状不同**。写成统一形式：

```
年成本 ≈ 常驻副本成本(1 + 额外资源比例) × 单位副本成本
        + 流量与配置面(入口网关 / 服务网格 / 配置中心的常驻与运维)
        + 人力(发布平台维护 + flag 治理 + 值班与演练)
        + 回滚成本(切指针 = O(1) ／ 重新部署 = O(实例数)
                   ／ 反写数据 = O(已写行数) ／ 修复已消费产物 = O(下游消费方数))
        + 共存期成本(旧版本镜像 / 配置 / 数据格式的保留，以及双写期的双份存储与吞吐)
```

**第一项：常驻资源。** 【推算】以稳态副本成本为 1 计，蓝绿 ≈ **2**（切换瞬间两套环境都必须完整可用）；滚动 ≈ 1 + `maxSurge` 比例（默认策略下通常为小比例【经验：以你所用的编排器默认值为准】）；金丝雀 ≈ 1 + p（p 常取 1%–10%【经验】，且当副本数很少时 p 被 1/副本数托底）；Feature Flag ≈ **1**（资源不涨，复杂度移到代码里）；影子流量 ≈ 1 + 复制一份的容量与吞吐（§4.1 Step 5「数据灰度 / 模型灰度」把「影子表工具」列入数据迁移工具，但容量口径要按峰值留【经验】）。**这条推算的意义在于：蓝绿贵不是因为它的软件贵，而是因为它的机制要求「切换瞬间两份都在」，所以它的成本是随副本数（而不是随变更次数）增长的固定项。**

**第二项：流量与配置面**，这是最容易被漏掉的一项。金丝雀的能力上限由流量入口决定——没有能按请求切分的入口，你在配置里写的比例不会生效（7.3.1 失效条件）；Feature Flag 需要配置中心的一致性保证；模型灰度需要模型服务平台。**这项成本的形状是「常驻一个高可用组件 + 一支能维护它的队伍」，与变更次数无关。**

**第三项：人力**，它包含两条独立的线：发布平台的维护，以及 **flag 治理**（谁清理、什么时候清理、清理时怎么确认没有依赖）。后者常被当成零成本，直到 flag 数量进入三位数。

**第四项：回滚成本**，这是本章唯一一个**随「已发生的事」而不是随「配置」变化的项**，也是数据变更与代码变更分家的地方：切指针是 O(1)，重新部署是 O(实例数)（分钟级），反写数据是 O(已写行数)（小时到天级【经验】），修复已消费的产物（训练用过的标签、在线推理用过的特征）是 O(下游消费方数)，且往往**没有可逆路径**。**【推算】把这一项换算成人时更直观：一次需要反写的数据变更，其代价 ≈ 涉及行数 × 每行修复成本 + 每个下游消费方的重算成本；当消费方超过一个团队时，"能回滚"基本等于"能重算"，而后者依赖对账与幂等键是否事先建好**（§5.2.3 把对账排在灰度之前的理由）。

**第五项：共存期成本**，包含旧版本镜像 / 配置 / 数据格式的保留（保留期必须覆盖决策窗口，否则回滚能力先于故障消失，7.3.3）与双写期的双份存储与写入吞吐。

**一句话对比**：**蓝绿的成本是「固定双份副本」，滚动的成本是「兼容性约束与实例重启」，金丝雀的成本是「一个能按请求切分的入口」，Feature Flag 的成本是「代码分支债」，数据灰度的成本是「对账与反写作业」。** 这几项不在同一张账单上，把它们的金额相加去比较方案，是最容易做错的比较。

**哪一项是主导项，取决于你的变更频率**：

| 候选族 | 主导项 | 隐性项（最容易漏算） | 变更频率翻 10 倍时的行为 |
| --- | --- | --- | --- |
| 蓝绿 | 常驻双份副本 | 切换链路的演练与容量 | 不变（固定成本，与变更次数无关） |
| 滚动 | 兼容性改造的人力 | 旧版本镜像与配置的保留 | 近似不变，但每次变更的兼容性验证成本线性叠加 |
| 金丝雀 | 流量入口的常驻与运维 | 按分流维度拆分指标的成本 | 不变；但自动回滚的阈值需随业务节律重校 |
| Feature Flag | flag 治理的人力 | 测试矩阵按开关组合增长 | **超线性**：组合数增长快于开关数 |
| A/B 测试 | 样本量所需的时间与流量 | 实验平台与指标口径的维护 | 线性；但所有实验共用同一批流量，实验数受流量上限约束 |
| 数据灰度 | 对账任务与反写作业 | 双写期的双份存储与吞吐 | 线性，且每次变更都要重新划定可逆路径 |

> 这张表的读法是**先看第三列**：它列出的是「不上这套机制也照样会发生、但会被算在别处」的成本。灰度与回滚的多数超支不在工具账单上，而在对账任务、保留策略、指标拆分与 flag 治理这四处。

### 7.5 决策树（每个分支都要有阈值依据）

```
[这次变更改的是哪一类对象？]
   │
   ├─ 代码 / 配置（不改数据结构、不改数据内容）
   │   │
   │   ├─ [流量入口能按"请求"切分吗？（网关 / 服务网格 / LB 权重）]
   │   │     ├─ 能 → 金丝雀 + 自动回滚（默认路线）
   │   │     │        └─ [共存窗口内，旧版本的读路径还读得懂新版本写的数据吗？]
   │   │     │              ├─ 能 → 按比例放大
   │   │     │              └─ 不能 → 先改成兼容（先加、再迁、最后收旧），再灰
   │   │     └─ 不能 → [能常驻两套完整环境吗？]
   │   │           ├─ 能 → 蓝绿（回滚 = 切指针）
   │   │           └─ 不能 → 滚动发布（调小替换幅度）+ 补一个能按请求切分的入口
   │   │
   │   ├─ [关掉这个功能要不要重新部署？] 不想 → 加一层 Feature Flag（并登记 owner 与过期时间）
   │   └─ [要判的是"坏没坏"还是"好不好"？] 后者 → A/B 测试（样本量由最小可检测差异决定）
   │
   └─ 数据 / Schema / 特征 / 模型产物
       ├─ [产物会被下游消费吗？]
       │     ├─ 不会（只读影子路径）→ 影子表 + 灰度读，回滚 = 切读路径
       │     ├─ 会被幂等消费 → 双写 + 对账，回滚 = 用幂等键重放旧路径
       │     └─ 已被消费（训练 / 在线推理 / 检索）→ 不做"灰度"，做变更评审 + 事前兼容
       └─ [需要反写已落库的数据吗？]
            需要 → 决策窗口内必须保留反向日志（变更日志 / Binlog），
                   且保留期要覆盖"从灰度开始到决定不回滚"的整段时间
```

**阈值依据**（树上每个判断节点在此各有一条，逐条对应）：

- **「这次变更改的是哪一类对象？」**：依据 7.3.1 的切分单元机制。它决定后面所有分支的性质——族四（数据）的回滚是 O(n)，族一至族三（请求 / 配置 / 实验分组）是 O(1)。**这一问的判定方法：这次变更有没有让「已经落库的数据」或「已经产生并被消费的产物」变得与新版本绑定。**
- **「流量入口能按请求切分吗？」**：依据 7.3.1 失效条件。这不是规模阈值而是能力阈值：不能按请求切分时，最小粒度被副本数钉死（三副本即 33%），「1% 灰度」只存在于配置里。判定方法：取一台实例，看能不能只对它的部分请求切流。
- **「共存窗口内旧版本的读路径还读得懂新版本写的数据吗？」**：依据 7.3.3。判定方法不是评审表态，而是**把新版本写出的样本数据喂给旧版本的读路径跑一次**——能跑通才叫兼容。
- **「能常驻两套完整环境吗？」**：依据 7.4 的第一项【推算】：蓝绿的常驻成本约为稳态的 2 倍（副本数 × 2，按你自己的单位副本成本代入）。**这条阈值的形式是比值而不是金额**，因为不同环境的单位副本成本相差几个数量级，写死一个金额在不同组织里含义完全不同。
- **「关掉这个功能要不要重新部署？」**：依据 7.3.4 与主文件 §2.2 的 RTO 分级（30 秒 / 5 分钟 / 30 分钟）。要落在第一档就必须让「生效」独立于「部署」。判定方法：假设此刻要关掉它，从决策到生效需要走几步、有没有人有权直接改。
- **「要判的是坏没坏还是好不好？」**：依据主文件 §2.2 的样本量公式 n = (Z_{α/2} + Z_β)² × 2σ² / δ²。【推算】取 α = 0.05、功效 80%（Z_{α/2} = 1.96、Z_β = 0.84，前项 = (1.96 + 0.84)² = 7.84），得 n ≈ 15.7 σ²/δ²；**δ 每缩小 10 倍，样本量涨 100 倍**（n ∝ 1/δ²），所以在指标方差不变的前提下，「验证 1% 的提升」所需样本量是「验证 10% 的提升」的 100 倍。这条依据的用途是：先算样本量，再决定灰度比例与窗口，而不是反过来。
- **「产物会被下游消费吗？」**：依据 7.3.1 的 O(n) 回滚与 [§ 5 前沿演进](09-gray-and-rollback-section-5-ai.md) §5.2.3 的三类路径划分（只读影子 / 幂等写入 / 已消费）。**判定方法是去数「这个产物的消费方有几个、跨几个团队」，而不是问「要不要灰度」**——消费方数目本身决定可逆窗口的长度。
- **「需要反写已落库的数据吗？」**：依据反向日志的存在性与保留期。主文件 §2.3 记变更日志（Binlog 一类）的常见保留窗口为 7–30 天【经验：沿用主文件 §2.3 的区间，具体保留期以你所用的数据库或 CDC 组件文档当前版本为准】；**决策窗口必须完整落在保留期之内，否则「能回滚」只是纸面能力**。

> 上树之前先做三项验证（都比选机制更重要）：① **量一次「从指标异常到有人做出决定」的时间**——自动回滚的阈值必须比它快，否则触发条件只是纸面配置；② **取一台实例，确认能不能只对它的部分请求切流**——不能按请求切分时，7.3.1 的失效条件已经成立，写 1% 也不会生效；③ **拿最近一次变更，数一遍「产物被几个下游消费过」**——消费方数目决定可逆窗口的长度，也就决定它该走灰度还是走变更评审。三项里任意一项不满足，无论落在树的哪一档，都应该先补这一项，而不是先换工具。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 无状态服务、流量大、变更多 | 金丝雀 + 自动回滚 | 滚动发布 | 蓝绿为「原子回滚」常驻 2 倍资源，在这个场景里买不到额外的东西（回滚本来就快） |
| 有状态服务、共享数据库 | 蓝绿（应用层）+ 数据层走「先加、再迁、最后收」 | 滚动 + 兼容性改造 | 纯滚动时共存窗口内旧版本可能读到新结构，故障是必然而不是概率 |
| 需要「某个租户现在就要关掉」 | Feature Flag | 金丝雀 | 按比例切流做不了定向动作；反过来 flag 也做不了「1% 随机用户体验新版」这类统计需求 |
| Schema 变更 / 数据迁移 | 双写 + 影子表 + 对账（先双写、再切读、最后停旧写） | 停机变更（写进计划） | 用灰度比例去控数据变更是把切分单元搞错了：比例控制的是请求，不是行 |
| 新模型上线 | 影子模型 → 金丝雀 → A/B | 直接 A/B | 一步 A/B 把「会不会崩」与「好不好」混进同一个窗口，两个结论都不可靠 |
| Prompt / 工具 / Agent 配置变更 | 可见性按比例（一致性哈希）+ 授权按身份（两层控制）+ 沙箱验证 | 纯 Feature Flag | 按比例开放权限等于给灰度组扩权，且没有审批路径（§5.2.2）；配置类变更不先过沙箱，等于把提示词注入与工具误用的风险直接放大到灰度组 |
| 大促 / 高敏感窗口前的关键变更 | 灰度 + GameDay 演练 + 冻结窗口 | 提前全量并加强监控 | 没有判据与演练的「全量」不是更稳，只是更快 |
| 内部工具、影响面小 | 直接发布 + 冒烟验证 | 金丝雀 | 为影响面不足百人的工具搭灰度流水线，成本收不回来 |

**常见组合**：

1. **灰度 + 监控告警**：构成——灰度提供按比例放量，监控提供判据（错误率、P99、业务核心指标，阈值见主文件 §2.2 的四类条件）。职责边界——灰度只负责「把变更放出去多少」，告警只负责「要不要停」；**没有判据的灰度只是一次延迟的全量发布**。运维代价——需要按灰度组拆分指标（同一份指标要能按分流维度切片），否则你看到的是新旧混合后的平均值（§3.3 反模式 2）。
2. **灰度 + 混沌工程 / GameDay**：构成——混沌工程在生产或类生产环境注入故障，GameDay 用真实节奏演练一次完整回滚。职责边界——混沌工程验证「故障能不能被发现」，GameDay 验证「发现之后能不能在承诺时间内止血」。运维代价——需要一个可复现的环境与一支不被打断的时间窗；**演练必须计时，不计时的演练只证明流程存在，不证明流程有效**。
3. **灰度 + 单元化**：构成——单元化把流量按地理 / 业务单元切开，灰度按单元推进（先在单元 A 放量，再推单元 B）。职责边界——单元化提供故障隔离的物理边界，灰度提供推进顺序。运维代价——**跨单元的共享数据是这条组合的软肋**：如果多个单元共享一份写入，单元化提供的隔离在数据层就不成立。
4. **灰度 + 大促保障**：构成——大促前后设冻结窗口，关键变更必须提前灰度并通过演练，且回滚预案要在冻结前验证过一次。职责边界——灰度负责验证变更，冻结窗口负责防止「验证期」与「峰值期」重叠。运维代价——冻结窗口会推迟其它变更，需要一个有权批准例外的角色，否则冻结会被日常例外侵蚀掉。
5. **灰度 + AI（模型 / Prompt / Agent）**：构成——复用族二的配置判定按比例切分，影子流量先行做「不触达用户」的验证。职责边界——流量切分与观察窗口可直接复用既有平台；**新增的责任是先定义「什么叫变差」并让它可以被统计**（§5.2.1）。运维代价——质量指标没有天生阈值，需要有人长期维护这条判据；且已产生的输出与已发生的工具调用不可撤回。

> 这些机制的**先后顺序本身也有机制依据**：先降低部署风险，再让止血不必经过流水线，再控制暴露面，最后才轮到判「好不好」，无人值守时段再靠自动回滚兜住，最后用演练检验前几步在压力下是否还成立。**顺序倒过来（先做 A/B 再做灰度）会让实验暴露在全量用户面前。**

> 组合的第一原则是**让每一件做它机制上最擅长的事**：流量切分归流量入口，判据归监控，止血归配置位，不可逆的部分归变更评审。第二原则是**组合数不超过团队的运维带宽**——上面 5 条里每多一件，就多一处「同一份指标在两张面板上给出不同结论」的战场、多一个需要长期维护的阈值。**凡是「两个系统都要能回答同一个问题」的组合，最终都会变成口径不一致的战场。**

### 7.7 选错的代价与迁移成本

**反模式：把「流量灰」当成「数据灰」** —— 症状：Schema 或数据迁移用金丝雀比例来放量，1% → 10% → 100% 走得很顺。后果：比例控制的是**请求**，不是**已经写进去的行**；某次变更在 10% 阶段写坏了数据，你把路由权重切回旧版本，坏数据仍在库里，而下游可能已经消费过它——回滚从「一次操作」变成「一次反写加一次重算」（7.3.1）。正确的做法：数据变更走双写 + 影子表 + 对账，先切读、后停旧写，并在事前列出「一旦发生就撤不回」的那部分（§5.2.3 的三类路径）。

**反模式：默认回滚能力与故障同时到达** —— 症状：回滚预案写在文档里，但从没演练过；旧版本镜像与配置的保留期短于最长观察窗口。后果：真出问题时发现旧镜像已被清理、或需要的数据没有备份，「30 秒回滚」变成一次临时的故障排查加一次重新发版。正确的做法：**把回滚当成发布的前置条件**（§6 阿里案例的「可回滚前置」），在发布单上写明回滚路径，并把它计时演练一次；保留期必须覆盖决策窗口。

**反模式：Feature Flag 只开不关** —— 症状：flag 数量进入三位数，没有 owner、没有过期时间，新人无法判断「这个请求现在会走哪条分支」。后果：每次改动都要在多种开关状态组合下验证，测试矩阵按组合增长；特定组合下的缺陷只在生产出现（§3.3 反模式 1）。正确的做法：创建时绑定 owner 与清理期限，把「已全量且稳定 N 天」的 flag 强制归档，让 flag 数量成为一个被度量、被压降的指标。

**反模式：用均值判断灰度结果** —— 症状：灰度期间只看平均延迟与平均 QPS，数字平稳就放量。后果：P99 与长尾用户的问题被平均掉，等业务方反馈时故障已经全量（§3.3 反模式 2）。正确的做法：按分流维度（新旧组）分别看 P50 / P95 / P99 / P999 与关键业务指标，并把「同一指标在新旧组上的差异」作为放量的准入条件。

| 迁移方向 | 配置与数据迁移 | 查询与接口改写 | 运维重建 | 团队再学习 | 量级（【经验】） |
| --- | --- | --- | --- | --- | --- |
| 无灰度 → 金丝雀 + 自动回滚 | 无需迁移 | 需按分流维度拆分指标 | 需引入流量切分入口与自动回滚 | 中 | 周到月级 |
| 滚动 → 蓝绿 | 无需迁移，但需常驻双份环境 | 接口不变 | 需双份容量与一次切换链路 | 低 | 周到月级 |
| 自研发布脚本 → Argo Rollouts / Flagger 一类 | 无需迁移 | 需把发布流程写成声明式资源 | 需接入编排器与指标源 | 中 | 月级 |
| 配置中心 flag → 商业 flag 平台 | flag 定义需迁移 | 需统一评估入口（去掉散落的自研判断） | 需引入配置下发与审计链路 | 低到中 | 周到月级 |
| 停机变更 → Online Schema Migration | 表结构需按「先加、再迁、最后收」重排 | SQL 基本不变 | 需引入改表工具与对账任务 | 高（顺序错了会丢数据） | 月级到季级 |
| 无 flag → 有 flag | 无需迁移 | 需在代码中引入判定入口与两条分支 | 需配置中心与 flag 生命周期管理 | 中 | 周到月级 |

> 注意「停机变更 → Online Schema Migration」这一行的量级最高，与直觉相反——它不是装一个工具，而是**把一次变更拆成一串可逆的小变更，并为每一步准备对账**。**本主题迁移的主要工作量从来不在切换动作上，而在「谁来定义兼容性与回滚路径」，以及这条路径有没有被演练过。**

### 7.8 小结

灰度与回滚选型的特殊性在于：**它选的不是「哪个发布工具更好」，而是「你的变更被切开之后还能不能拼回去」**。所有候选的差异都可以收到一条上——**切分单元是什么，以及在该单元上把操作倒回去的代价是 O(1) 还是 O(n)**。切请求 / 实例 / 指针的（蓝绿、滚动、金丝雀、影子流量）回滚是一次动作，代价与数据量无关，因此它们可以「先上线、出问题再回滚」；切配置判定的（Feature Flag、模型与 Prompt 灰度）把回滚从流水线里拿出来，代价记在代码分支债上；切实验分组的（A/B）不降低风险，只回答「好不好」，所以它叠加而不替代；**切数据的（双写、影子表、Online Schema Migration、特征与标签）回滚是一次反写作业，代价随已写的行与被消费的产物增长——这一族不能靠回滚兜底，只能靠把不可逆变拆成多步可逆变。**

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 无状态服务、有能按请求切分的入口 | 金丝雀 + 自动回滚 | 切分单元是请求，回滚 = 切权重（O(1)），代价与流量无关 |
| 有状态服务、共享数据库、要原子回滚 | 蓝绿（应用层）+ 数据层 expand-contract | 指针切换是 O(1)，前提是两套环境读同一份数据时格式对两边都可用 |
| 没有能按请求切分的入口 | 先滚动发布止血，再补流量入口 | 不能按请求切分时最小粒度被副本数钉死，写 1% 也不会生效 |
| 需要定向开关、暗启动、秒级止血 | Feature Flag（配 owner 与过期时间） | 部署与生效解耦，回滚不必经过流水线；代价是两条分支长期并存 |
| 要回答「新版本是不是更好」 | A/B 测试（先算样本量） | 分组为统计功效服务，样本量 ∝ 1/δ²，比例不能凭感觉定 |
| 低概率但后果严重的故障 | 影子流量 + 故障注入（不要指望提高灰度比例） | 单位时间故障样本数 = 流量 × 比例 × 故障率，比例一提暴露面同比放大 |
| Schema / 数据迁移 / 口径切换 | 双写 + 影子表 + 对账 | 切分单元是行不是请求，回滚是反写作业（O(n)），必须先建对账与幂等键 |
| 变更的产物会被训练 / 在线推理 / 检索消费 | 不做灰度，做变更评审 + 事前兼容 | 已消费的产物没有可逆路径，「能回滚」在这里等于「能重算」 |
| 模型 / Prompt / Agent 工具上线 | 影子先行 → 按比例切可见性 → 授权按身份 | 版本缺少内容寻址、回滚不等于恢复原状；权限是布尔判定，不能按比例开放 |

> 本节小结：本章所有候选之间，**唯一真正起决定作用的差异是「切分单元是什么、把该单元上的操作倒回去要付 O(1) 还是 O(n)」**——它同时决定了回滚能不能被当作兜底手段、灰度比例的最小粒度、共存窗口里兼容性是不是硬约束，以及那一族变更的失败模式（族一死于兼容性、族二死于分支债、族三死于样本量、族四死于「以为能回滚」）。其余维度（工具成熟度、自动化程度、图表好看与否）都是在确定了切分单元与不可逆面之后才需要精算的第二层问题；先算这份账，再谈工具。
