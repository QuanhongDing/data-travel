## 3. 设计模式与范式

### 3.1 主要模式

#### 模式 1：分层防御（Defense in Depth）

```
[客户端] → [CDN] → [WAF] → [API 网关] → [应用层] → [缓存] → [DB]
   ↓         ↓        ↓          ↓             ↓        ↓       ↓
  限流     限流    防DDoS    限流/降级     熔断/降级  击穿防护 主从切换
```

**核心思想**：每一层都做防御，单层失效不至于全栈崩溃。

#### 模式 2：单元化（Cell-Based）

把系统按业务域（用户、订单、商品）切分为 N 个 Cell，每个 Cell 自包含（DB + Cache + MQ），单 Cell 故障不影响其他 Cell。详见 [Ch12 §01 单元化架构](../01-cell-based-architecture/01-cell-based-architecture.md)。

#### 模式 3：熔断降级（Circuit Breaker + Degradation）

- **熔断**：当下游故障率 > 阈值，主动断开调用。
- **降级**：主动关闭非核心功能，释放资源给核心功能。

#### 模式 4：流量调度（Traffic Scheduling）

- **DNS 调度**：粗粒度（机房级）。
- **GSLB**：中粒度（地域级）。
- **服务网格**：细粒度（服务级 / 用户级）。

#### 模式 5：弹性扩容（Elastic Scaling）

- **预测式扩容**：基于预测提前扩容（如大促前 1 小时）。
- **响应式扩容**：基于指标自动扩容（CPU > 70%）。
- **混合扩容**：预测 + 响应双保险。

#### 模式 6：分级保障（Tiered SLA）

- **核心链路**：下单、支付 → 100% 可用，3 个 9 响应时间 < 200ms。
- **重要链路**：商品详情、库存 → 99.9% 可用。
- **非核心链路**：评论、推荐 → 99% 可用，可降级。

#### 模式 7：AI 时代的智能弹性（AI-Driven Auto-Scaling）

- 用 AI 预测流量，提前扩容。
- 用 AI 识别异常流量，自动触发限流。
- 用 AI 做根因分析，加速故障恢复。

### 3.2 适用场景决策表

| 场景 | 推荐模式 | 理由 |
| --- | --- | --- |
| 已知峰值大促（双11、618） | 预测式扩容 + 全链路压测 + 分级保障 | 时间已知，可提前备战 |
| 突发流量（明星直播、爆款） | 响应式扩容 + 限流降级 + 流量调度 | 无法提前预知，需快速响应 |
| 全球化业务（黑五、春节） | 单元化 + 异地多活 + GSLB | 跨地域，分摊压力 |
| AI 推理服务（大模型 API） | 弹性 GPU + Prompt 缓存 + 模型降级 | GPU 资源稀缺，需弹性调度 |
| 智能体链路 | 工具级限流 + 链路降级 + 单工具熔断 | 链路长，单点故障放大 |
| 内部系统（ERP、CRM） | 限流 + 降级（不扩容） | 流量有限，成本敏感 |

### 3.3 反模式与陷阱

#### 反模式 1："靠加机器"硬扛

**症状**：平时不优化，临时堆资源。

**风险**：资源成本高 + 上限有限（机房容量 / 带宽瓶颈）+ 无可扩展性。

**正解**：日常持续优化性能 + 弹性扩容 + 限流降级。

#### 反模式 2：全链路压测缺失

**症状**：只做单链路压测，大促时上下游联动失效。

**风险**：缓存击穿、DB 连接打满、MQ 堆积等"链式故障"无法提前发现。

**正解**：每年大促前 1-2 个月做全链路压测，覆盖真实业务路径。

#### 反模式 3：限流策略一刀切

**症状**：全站统一阈值（如 1000 QPS），不区分核心 / 非核心。

**风险**：核心链路被打挂，非核心链路还活着。

**正解**：按链路分级（核心 5000 QPS，非核心 1000 QPS）。

#### 反模式 4：降级开关混乱

**症状**：100+ 开关没有 owner / 文档 / 演练。

**风险**：关键时刻没人敢按，按错开关导致更大故障。

**正解**：开关 owner 制度、定期演练、文档化、自动化（A/B + 监控触发）。

#### 反模式 5：弹性扩容慢

**症状**：启动 1000 台机器要 10-30 分钟。

**风险**：等扩容完流量高峰已过，或系统已崩。

**正解**：镜像预热（提前制作好镜像）、Spot Instance、Serverless（秒级）、预留 buffer。

#### 反模式 6：值班流于形式

**症状**：值班人员不清楚"出问题找谁、怎么回滚"。

**风险**：错过黄金 5 分钟，故障扩大。

**正解**：On-call 培训、Runbook、定期演练、GameDay。

#### 反模式 7：忽视 AI 链路

**症状**：只保障传统链路，AI 链路成为新的脆弱点。

**风险**：智能体某个工具调用慢/挂，拖垮整链路；GPU 资源耗尽，推理服务雪崩。

**正解**：工具级限流、推理服务弹性、模型降级链路、向量检索容灾。
