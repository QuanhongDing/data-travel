## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式清单最容易被读成一张「按场景挑一个」的菜单：大促用预测式扩容、突发用响应式扩容、全球化用单元化。但同样是「已知峰值的大促」，在两套系统里该用的模式可以完全相反——差别不在场景标签，而在约束：**峰值的时点能不能提前锁定、上升时间与扩容生效时间谁更长、单池有没有承载上限**。约束不同，同一个场景的正确答案就反过来。

大促保障的模式选择之所以特别容易选错，是因为它的候选不是同一类东西（[§ 7.1](03-large-event-readiness-section-7-sec7.md) 把这一点写成了分族）：容量规划是学科，单元化与异地多活是架构形态，限流降级与压测是手段。它们之间大多不是取舍关系，而是配套关系——「要不要全链路压测」与「要不要单元化」之间没有取舍，前者是后者的验证手段。所以下面先立约束表，再谈模式。

举一个具体的差：同样是「已知时点的年度峰值」，如果峰值倍数是日常的 3 倍、持续两小时，正确解是弹性扩容加分级限流降级——按峰值常备两小时的容量，全年绝大部分时间都在浪费；如果倍数到了 10 倍并持续数小时，正确的第一步反而是改架构形态，因为单池已经扩不到那个量级，加钱也加不出来。**同一个场景标签，约束一变，答案就变**。这也是为什么下面每个模式都先写「被什么约束逼出来」，而不是先写它适合什么场景。

上面这些对比的共同点是：**先有用量级的约束，才有模式可选**。所以判定的顺序应当是「先问单体上限、再问上升时间、最后问成本结构」，而不是「先看别人用了什么」。顺序反了，就会在大促前两个月才发现瓶颈不在自己以为的那一层。

还有一条更要紧的：这三条约束都可以被**实测**，而不是被讨论。单体上限能从压测与容量台账里读出来，上升时间能从历史流量曲线上量出来，成本结构能从计费单里算出来——这份约束表是可以被填满数字的，不是一张立场表。

表里最后一列不是「这条直觉错」，而是「它在哪条约束下会反过来」。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 峰值的时点能否提前锁定 | 买「更准的预测」还是「更快的切换」 | 「把流量预测准一点就能扛住」——脉冲型峰值下，预测精度不是瓶颈，切换到备用容量的速度才是 |
| 峰值的上升时间 vs 扩容生效时间 | 弹性扩容来不来得及 | 「弹性扩容能解决峰值」——上升时间短于扩容生效时间时，扩容永远慢一个周期 |
| 单池承载上限与爆炸半径 | 要不要改变架构形态（单元化 / 异地多活） | 「加钱就能加容量」——单池上限被硬件与拓扑封死，加钱也加不出容量 |
| 流量的可分摊维度（用户 / 地域 / 时间） | 能按什么维度分摊 | 「分摊总是有收益」——全局聚合型业务（跨用户排行榜、全局库存）的分摊收益会被跨池调用的成本吃掉 |
| 超载时允许丢什么（链路分级） | 限流与降级的阈值怎么分布 | 「统一阈值最省事」——统一阈值下核心与非核心同时被限，核心先死 |
| 成本结构（常备 vs 弹性） | 容量按峰值常备还是按需购买 | 「常备更稳」——按峰值常备的容量在一年中的绝大部分时间是闲置的（浪费比例见 [§ 7.4](03-large-event-readiness-section-7-sec7.md) 的推算） |

### 3.2 模式逐个拆解（核心节）

下面 7 个模式覆盖主文件 §1.4 与 §2.3 的技术栈，顺序是从「离流量最近的防御」走到「承载流量的形态」：3.2.1–3.2.4 解决「超载时怎么少进来、怎么少坏一点」，3.2.5–3.2.7 解决「容量从哪来、给谁用」。每个模式给同一套六件事：约束、结构、机制、代价、失效点、真实使用。

#### 3.2.1 分层防御（Defense in Depth）

- **被什么约束逼出来**：任何一层防御都会有失效的那一天，约束是**单层失效不能直接击穿最底层**。
- **结构**：

```text
[客户端] → [CDN] → [WAF] → [API 网关] → [应用层] → [缓存] → [DB]
   ↓         ↓        ↓          ↓             ↓         ↓       ↓
 限流      边缘缓存  防 DDoS   限流/降级     熔断/降级  击穿防护 主从切换
────────────────────────────────────────────────────────────────────
每一层的失效形态不同（这才是分层的目的）：
  边缘层失效 → 打进来，但内部还有配额
  网关层失效 → 配额失控，但应用层还能熔断下游
  应用层失效 → 功能降级，但缓存与 DB 仍受保护
  缓存层失效 → 穿透到 DB，靠 DB 侧限流兜住最后一层
关键：每一层防的是「上一层漏过来的量」，不是「把所有量挡在外面」
```

- **为什么这样设计有效**：因为每一层只承担上一层漏过来的量，所以单层失效不会直接到达最底层，而是被下一层的配额接管——防御能力是叠加的，而不是取最大。
- **代价**：每层判定都会叠加延迟；配置面随层数增长；而且超载时的表现是**静默丢弃**（限流不返回错误），定位「到底哪一层在丢」的成本远高于定位一个报错。这也是分层防御必须配一份「每层生效量」的指标，否则你只知道自己被保护了，不知道正在被哪一层丢。
- **失效点**：当多层共用同一份阈值来源（同一份配置、同一个人手工下发、同一个配置中心）时，「单层失效不至于全崩」的优点反转成**同源失效**——一次配错会同时播到所有层，因为分层的防护力来自阈值来源互相独立，而不是来自组件数量多。
- **真实使用**：限流 / 熔断 / 降级作为独立机制的口径见主文件 §2.1 与 §2.3（Sentinel、Hystrix、Resilience4j 等实现的具体能力与维护状态，以各自官方文档当前版本为准）【公开】；把限流布在 CDN 与网关两个位置是多数对外服务的默认做法【经验】。

#### 3.2.2 单元化（Cell-Based）

- **被什么约束逼出来**：峰值规模超过单池能扩到的上限，且机房级故障的爆炸半径是全站——约束是**必须把"全站"这个单位变小**。
- **结构**：

```text
单元化：按用户切，每个单元自包含
  CellID = Hash(userId) mod N_Cells      ← 同一用户永远落在同一个单元
  ┌──────── Cell 1 ────────┐   ┌──────── Cell 2 ────────┐
  │ DB（分片）+ Cache + MQ │   │ DB（分片）+ Cache + MQ │
  └───────────┬────────────┘   └───────────┬────────────┘
              └──────── 跨单元聚合层 ────────┘
                 （只服务全局查询：跨用户排行榜、全局库存）
  ────────────────────────────────────────────────────────────────
  单单元故障影响 = 1 / N_Cells
  关键：分片键与 N 是长期承诺——数据已按新维度重分片后很难收回
```

- **为什么这样设计有效**：因为路由把同一用户固定到同一单元，所以单单元故障的爆炸半径是 `1 / N` 而不是全站（N 越大，单点影响越小，但跨单元的聚合路径越多）；代价是「我的全部订单」这类跨用户聚合必须走额外路径。
- **代价**：每个单元一套常驻组件（DB + Cache + MQ），运维面随 N 增长——每多一个单元，监控、发布、值班、容量标定各多一份；跨单元调用还会引入一致性与延迟成本。
- **失效点**：当业务以全局聚合为主（跨用户排行榜、全局库存、跨单元事务）时，「分摊峰值、缩小爆炸半径」的优点反转成**跨单元调用成为新的瓶颈与新的单点**——聚合层要合并 N 个单元的响应，它的容量不会因为你增加单元数而改善。
- **真实使用**：【公开】路由与资源切分的口径（`CellID = Hash(UID) mod N_Cells`、`每单元容量 = 总容量 / 单元数`、`故障单元占比 = 1 / N_Cells`）见 [Ch12 §01 单元化架构](../01-cell-based-architecture/01-cell-based-architecture.md) §2.2；它与异地多活、削平三者的分工见 [§ 7.3.2](03-large-event-readiness-section-7-sec7.md)。

#### 3.2.3 熔断与降级（Circuit Breaker + Degradation）

- **被什么约束逼出来**：下游变慢或挂掉时，调用方若不主动断开，线程与连接池会被耗光，故障于是从「一个下游」升级成「全站」——约束是**必须在调用链上有一处主动放弃**。
- **结构**：

```text
熔断作用在「调用」上，降级作用在「功能」上——两者对象不同
  ── 熔断：按指标自动断开 ──
    CLOSED（正常）──错误率 > 阈值──► OPEN（断开）
       ▲                                │ 超时（如 30s）
       │                                ▼
       └── 探测成功 ── HALF_OPEN（半开探测）
                          └── 探测失败 ──► OPEN
  ── 降级：按预案逐级收缩功能面 ──
    一级：非核心功能（评论、推荐、积分）
    二级：非核心营销活动与个性化
    三级：读走缓存兜底、写转异步队列
    四级：AI 链路降档（大模型 → 小模型 → 规则兜底，见 [§ 5.2.2](03-large-event-readiness-section-5-ai.md)）
  ────────────────────────────────────────────────────────────────
  关键区别：熔断是自动的（按指标触发）
            降级需要事前定义「关什么、谁有权关、关了以后话术是什么」
```

- **为什么这样设计有效**：因为熔断在下游故障时主动断开调用，故障不会沿调用链向上传染——这是它能替代「无限重试」的原因；代价是阈值标定错误会误杀，断开的可能是正常调用而不是故障调用。
- **代价**：阈值必须在压测中标定，没有通用最优值；半开探测本身会周期性给已经故障的下游再压一次；降级开关需要 owner、文档与演练，否则当晚既不敢按也不敢不按。
- **失效点**：当降级开关没有 owner、没有演练时，「主动收缩功能面以保住核心」的优点反转成**开关债务**——开关在关键时刻退化成一份文档，因为降级的效果只有在被按下的那一刻才能被验证，而平时的验证成本没有人愿意付。
- **真实使用**：【公开】熔断状态机的原始出处见主文件 §2.1（Michael Nygard 的 Circuit Breaker 模式，*Release It!*）；Sentinel 提供流量控制 + 熔断降级 + 系统自适应保护，Resilience4j 是 Hystrix（已停止维护）之后的常见替代【公开】（各项目具体能力以官方文档当前版本为准）。配置形态见 [§ 4.2](03-large-event-readiness-section-4-sec4.md)。

#### 3.2.4 流量调度（Traffic Scheduling）

- **被什么约束逼出来**：容量分散在多个机房与地域，而流量的到达位置与容量的分布位置不一致——约束是**必须有一种手段把请求挪到还有容量的地方**。
- **结构**：

```text
三种调度粒度：代价与生效速度完全不同
  粒度      手段        决定的单位       生效时间      主要限制
  ────────  ──────────  ──────────────  ───────────  ──────────────────
  机房级     DNS         解析结果        受 TTL 约束   客户端缓存不受控
  地域级     GSLB        地理 / 网络质量  分钟级        依赖探测质量
  服务级     服务网格     请求 Header/URI  秒级          需应用全量接入
  用户级     单元化路由   userId Hash      秒级（预置）   改分片键 = 改数据
  ────────────────────────────────────────────────────────────────
  关键：调度只能把流量挪到「已经有容量的地方」
        它不生产容量——总量不够时，调度只是把故障换个地方发生
```

- **为什么这样设计有效**：因为调度的粒度决定「多久能把流量挪走」，所以它能救的是局部容量不足（某个机房、某个地域），救不了总量不足；代价是三种粒度并存时要维护三套口径，且客户端 DNS 缓存会让「已经改好的解析」迟迟不生效。
- **代价**：探测与路由配置的长期维护；跨单元 / 跨地域调度会把延迟与一致性成本一并引入（按地域分摊尤其如此）。
- **失效点**：当容量总量不足，或流量是全局同时到达（上升时间为秒级）时，「把流量挪到有容量的地方」的优点反转成**把同一时刻的压力在多个区域同时复制一遍**——因为调度不改变总到达量；此时有效的是削平（异步受理 + 幂等），而不是分摊（[§ 7.3.2](03-large-event-readiness-section-7-sec7.md)）。
- **真实使用**：【经验】DNS 与 GSLB 是所有对外服务的常规形态；服务网格按 Header / URI 的细粒度路由需要应用全量接入才生效（Istio / Envoy 形态，具体能力以官方文档当前版本为准）【公开】。按 userId 的路由是调度的最高粒度，也是唯一改动了数据分布的粒度。

#### 3.2.5 弹性扩容（Elastic Scaling）

- **被什么约束逼出来**：峰值的持续时长远短于资源的计费周期——按峰值常备意味着绝大部分时间为闲置付费——约束是**容量必须按需买入**。
- **结构**：

```text
三种触发方式，对应三种峰值形态
  预测式：时点可提前锁定  ──► 提前扩容（大促前 1 小时）
            代价：预测偏差直接变成过配或欠配
  响应式：形态不可预知    ──► 按指标扩（如 CPU > 70%）
            代价：永远滞后一个「采集 + 调度 + 启动」周期
  混合式：两者叠加        ──► 预测打底、响应补差
  ────────────────────────────────────────────────────────────────
  HPA 形态：期望副本数 = ceil[ 当前副本数 × (当前指标 / 目标指标) ]
  两个硬约束：
    ① 扩容生效时间 > 峰值上升时间 → 扩容永远慢一步
    ② 有状态服务与推理服务受冷启动 / 供给约束
       ——扩的是「实例」，不是「就绪」
```

- **为什么这样设计有效**：因为触发信号来自已经发生的指标、而扩容动作需要时间才生效，所以弹性扩容天然滞后一个「采集 + 调度 + 启动」周期；反过来，这也正是它的价值所在——它给的是「峰值持续几分钟以上」这类场景的经济解。
- **代价**：预热成本（镜像、连接池、JIT、GPU 显存）不能省；缩容需要防抖动，否则会在阈值附近振荡；用可中断容量时，回收时点由供应商决定，需要中断通知加幂等与重排队兜底。
- **失效点**：当峰值上升时间短于扩容生效时间时，「按需付费、不为峰值常备」的优点反转成**扩容还没到位高峰已过**（或系统已经崩）——因为弹性扩容买来的是「时间」，不是「现成的容量」；此时要换成提前预热 + 预留 buffer + 削平。
- **真实使用**：【公开】Kubernetes HPA 的 autoscaling/v2 自 1.23 起为稳定 API 版本（可按 Kubernetes CHANGELOG 核验）；KEDA 提供按外部指标（如消息积压）的扩缩，是 CNCF 项目（版本与毕业状态以其官方页面为准）。【经验】扩容生效时间必须在压测中实测，不要用文档承诺值——它随镜像大小、调度器负载与节点供给而变。

#### 3.2.6 分级保障（Tiered SLA）

- **被什么约束逼出来**：资源不足时必须有取舍，而「不预先指定谁可以被牺牲」等于把取舍留给故障现场——约束是**牺牲顺序必须在事前写下来**。
- **结构**：

```text
分级保障：先定谁可以被牺牲，再定牺牲的先后
  ┌─ 核心链路 ── 下单、支付
  │    可用性目标最高、响应时间预算最紧；超载时最后才降级
  ├─ 重要链路 ── 商品详情、库存
  │    可短暂降级，但不能长时间不可用
  └─ 非核心链路 ── 评论、推荐、积分
       最先降级，可长时间关闭
  ────────────────────────────────────────────────────────────────
  每一级的阈值必须分开标定：
    全站统一阈值 → 核心与非核心同时被限，核心先死（见反模式 3）
    分级阈值     → 超载时先丢非核心，核心的配额被保住
  关键：分级是「事前写下来的牺牲顺序」，不是当晚的临场判断
```

- **为什么这样设计有效**：因为牺牲顺序是事先写好的，超载时的资源分配不再依赖当晚的判断力与勇气；代价是分级表必须与实际依赖一致。
- **代价**：维护分级表与逐级阈值；每次新增功能都要回答「它属于哪一级」；分级本身会诱发一种错觉——以为标了级就等于依赖已经梳理清楚。
- **失效点**：当核心链路依赖了被判为非核心的下游（例如下单流程里调用了推荐或积分服务）时，「保住核心」的优点反转成**核心被非核心拖死**——因为降级只关掉了非核心的入口，没有切断核心对它的调用；这只能靠在压测中验证依赖，而不是靠分级表本身。
- **真实使用**：【经验】分级保障是电商大促的通行做法，等级划分与具体阈值没有通用值，须结合自身链路在压测中标定；按阶段消除不确定性的备战形态见 [§ 3.1](03-large-event-readiness-section-6-sec6.md)。

#### 3.2.7 AI 时代的智能弹性（AI-Driven Auto-Scaling）

- **被什么约束逼出来**：AI 服务的容量分母不是常数——它随批大小、序列长度、量化位宽与引擎版本变；而实例分配是秒级、模型就绪是分钟级——约束是**同一句「扩容」盖住了两个时间尺度**。
- **结构**：

```text
把「容量不够」拆成三个不同的问题（解法完全不同）
  问题一：实例不够          → 加实例（秒级可解）
  问题二：模型没就绪        → 预热池 / 权重分层缓存（分钟级，必须提前）
  问题三：显存放不下更多并发 → 并发上限 ≈ 可用显存 ÷ 单序列 KV 占用
  ────────────────────────────────────────────────────────────────
  AI 辅助作用在这两个位置：
    ① 预测：用模型预测峰值时点，把「响应式」往前挪成「预测式」
    ② 识别：识别异常流量形态，自动触发限流 / 降档
  它**不**作用在止血上：当晚止血仍靠限流、降级与切换
  ────────────────────────────────────────────────────────────────
  判断瓶颈在哪：扩容后 P99 不随实例数上升而下降
                → 瓶颈在预热或显存，不在实例数
```

- **为什么这样设计有效**：因为容量单位从「实例数」变成「token 吞吐 × 上下文长度分布」，所以「扩容」与「可用」必须拆成两件事，预热于是成为独立的一层；代价是多了一层必须提前标定的常驻成本。
- **代价**：预热池是常备支出，其规模由最坏情况的加载时间（而不是平均负载）决定；GPU 弹性上限受供给与冷启动约束；共享之后利用率不再对应延迟——同一张卡上多租户互相干扰，扩缩信号变成噪声。
- **失效点**：当把「模型没就绪」误判成「实例不够」时，智能弹性的优点反转成**一直扩容、一直没就绪**——监控上实例数达标而业务持续超时，因为瓶颈在权重加载与显存预热，加实例不改变这两个时间尺度（判据见 [§ 5.2.1](03-large-event-readiness-section-5-ai.md)）。
- **真实使用**：【公开】vLLM 自 2023 年起的公开 release notes 记录了连续批处理与分页 KV 缓存（这是「吞吐分母」变化的机制来源）；【公开】AWS EC2 Spot 官方文档给出中断通知机制、容量池模型与「相对按需价最高可低约 90%」的表述——「最高」不等于典型值，规划必须用自己观察到的折扣与中断率【经验】。多模型降级链路的档位见 [§ 5.2.2](03-large-event-readiness-section-5-ai.md)。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 峰值时点可提前锁定、峰值未超单池上限 | 容量规划 + 弹性扩容 + 分级保障 + 全链路压测 | 不选单元化：峰值驱动的弹性增量机时低于改架构形态的固定常驻机时（[§ 7.4](03-large-event-readiness-section-7-sec7.md) 的 `M*`） | 峰值倍数 M 是否越过平衡点 |
| 峰值不可预知、上升时间为秒级 | 响应式扩容 + 流量调度 + 限流降级 + 削平（异步受理 + 幂等） | 不选预测式扩容：预测精度对脉冲型峰值不是瓶颈，切换速度才是 | 峰值是局部不均还是总量不足（总量不足时只有削平有效） |
| 全球化 / 跨地域业务 | 单元化 + 异地多活 + GSLB | 不选单地域多可用区：一次地域故障即全站不可用 | 是否跨法域（跨境副本受合规约束，GDPR 第 44–46 条【公开】） |
| AI 推理服务（大模型 API） | GPU 弹性 + 预热池 + Prompt 缓存 + 模型降档链 | 不选「只加实例」：实例就绪不等于模型就绪 | 扩容后 P99 是否随实例数下降 |
| 智能体链路 | 工具级限流 + 单工具熔断 + 链路降级 | 不选端到端统一阈值：链路可用性是乘法关系，一个工具能拖垮整链 | 每个工具是否各有超时与配额 |
| 内部系统（ERP、CRM） | 限流 + 降级（不扩容） | 不选弹性扩容：流量有限且可协商，扩容的常备成本不划算 | 峰值是否可控且可协商 |
| 总量不足、全局同时到达 | 削平（异步受理 + 排队反馈 + 幂等） | 不选流量调度：调度不生产容量，只会把同一时刻的压力复制到所有区域 | 有没有幂等键与去重（没有则削平会变成重复发放） |

这张表里**最常被误选的一对是「流量调度」与「容量建设」**：当总量不足时，调度只是把故障换个地方发生——它买到的从来不是容量。第二常见的一对是预测式与响应式扩容：脉冲型峰值（明星直播、爆款）里，把预算投在提高预测精度上几乎不影响结果，而把预算投在缩短「扩容生效时间」与削平上才有用。误选的后果不是「效果差一点」，而是**备战期的预算与人力投在了不改变瓶颈的地方**，当晚仍然要靠临时限流兜底。

要注意这张表里没有「全链路压测」这一行：它不是一个可以被选中的模式，而是对已选模式的**验证手段**——你在哪一格，压测的对象就不同（选了单元化就要验证跨单元聚合路径，选了削平就要验证幂等与去重，选了降档链就要逐档验证质量）。把它当成候选去和别的模式比较，就会得出「选了压测就不用单元化」这类错误结论（[§ 7.1](03-large-event-readiness-section-7-sec7.md) 把这一误读单独列为原打分表的第一个问题）。

第三常见的误选是「用流量调度替代容量建设」的变体：把调度层级做得很细（服务网格按 Header 路由），却没有对应的备用容量池。细粒度调度只有在**目的地有容量**时才有意义，否则它只是让请求更快地到达同一个失败的终点。

### 3.4 组合模式：真实系统不会只用一种

1. **容量规划 + 全链路压测 + 分级限流降级**：容量规划负责「按多少资源准备」，全链路压测负责「验证这个准备对不对」（生产环境 + 真实链路 + 流量染色 + 影子隔离），分级限流降级负责「超载时先丢什么」。边界是「算容量 / 验容量 / 超载怎么丢」。运维代价：压测需要长期维护隔离链路与压测数据，这一项的成本不随大促结束而归零。适合规模：单机房、峰值倍数在平衡点 `M*` 以内的场景【经验】。退出条件：一旦峰值超出单池上限，这套组合仍然要继续保留——它是新形态的验证手段，不是被替换掉的那一层。
2. **单元化 + 跨单元聚合层 + 按单元灰度**：单元负责本单元内的读写与一致性，聚合层负责跨用户查询，单元灰度负责发布与止血。边界是「单用户内的一致归单元、跨用户聚合归聚合层、变更暴露面归灰度」。运维代价：聚合层是新的单点与瓶颈，必须能降级为「只查本单元、结果不完整但可用」，且每增加一个单元都要同步容量与路由。适合规模：峰值规模已超过单池可扩上限的场景。退出条件：不适用——分片键与单元数一旦确定就构成长期承诺，这套组合只能扩，不能撤。
3. **弹性扩容 + 预热 + 削平（异步受理）**：弹性扩容承接秒级可扩的部分，预热把不可秒扩的部分（模型权重、连接池、JIT）提前移出关键路径，削平把无法即时处理的量转成「已受理」。边界是「能扩的归弹性、不能扩的归预热、接不住的归异步」。运维代价：幂等与去重必须同时到位，否则压力会从入口搬到后台，并可能造成重复发放。适合规模：峰值时长在分钟级以内、且业务能接受「已受理」语义的场景。

组合不是越全越好，它有确定的引入顺序：**先补验证手段（压测与可观测性），再补超载时的取舍（限流与分级降级），最后才动架构形态**。顺序反过来的代价很具体——先上了单元化却没有压测，你无法回答「跨单元聚合层会不会成为新瓶颈」；先上了降级却没有分级，按下开关时你不知道自己牺牲了谁。

组合的运维代价可以归成一句：**每增加一种形态，就多一份「同一件事在两处是否还对得上」的校验**（阈值是否一致、路由是否覆盖、单元与地域的容量台账是否同步），对不上之处就是当晚最难定位的故障源头。

判断一个组合是否已经过度，有一个可核验的问题：**如果今晚只有一个小时做处置，你按的顺序是什么？** 如果这个问题答不出来，说明形态已经有了，但优先级没有——多出来的那一层在故障现场只会增加犹豫，而不是增加能力。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「靠加机器」硬扛 | 平时不做性能与容量优化，临到大促才提资源工单 | 成本按峰值买、上限由机房容量与带宽封死，且不可扩展 | 加机器是最快能买到的东西，而优化要动代码与链路 | 日常持续优化 + 弹性扩容 + 分级限流降级 |
| 全链路压测缺失 | 只压单条链路，上下游联动从未在压力下跑过 | 缓存击穿、DB 连接打满、MQ 堆积这类链式故障只能等真流量来发现 | 全链路压测需要长期的隔离链路与数据构造，投入在备战期看不到产出 | 大促前做生产环境全链路压测（流量染色 + 影子隔离），覆盖真实业务路径 |
| 限流策略一刀切 | 全站一个阈值，不区分核心与非核心 | 超载时核心与非核心同时被限，核心链路先死 | 一个阈值最容易配、最容易解释 | 按链路分级标定阈值（示意值 1000 / 5000 QPS 不是标定结果）【经验】 |
| 降级开关混乱 | 上百个开关没有 owner、没有文档、没有演练 | 关键时刻开关退化成文档：没人敢按，按错反而放大故障 | 开关是「上个功能顺手加的」，加的时候没规定归属 | 开关 owner 制度 + 定期演练 + 文档化 + 按指标自动触发 |
| 弹性扩容慢 | 扩容生效时间是几十分钟量级【经验】 | 流量的高峰窗口可能只有几十分钟，扩到位时高峰已过 | 镜像大、启动慢、有状态服务与 GPU 冷启动被忽略 | 镜像预热 + 预热池 + 预留 buffer + 可中断容量（配幂等） |
| 值班流于形式 | 值班人员答不出「出问题找谁、怎么回滚」 | 故障响应被推迟到第一轮人工判断之后，错过最初的几分钟 | 值班排班容易做，升级路径与 Runbook 不容易做，于是只做了容易的 | On-call 培训 + Runbook + 定期演练（GameDay） |
| 忽视 AI 链路 | 只保障传统链路，AI 链路的容量与降级没有预案 | GPU 供给与链式调用把故障域放大：单个工具慢就能拖垮整条链 | AI 链路是后加的，没进备战节奏，也没进容量台账 | 工具级限流 + 单工具熔断 + 推理弹性 + 降档链 + 向量检索容灾 |

**最危险的三条在生产中的暴露方式**：

- **「限流策略一刀切」的暴露是静默的**。它不会在备战期暴露，而是在当晚以「核心链路先挂」的形式出现：因为统一阈值被非核心流量先吃满，核心请求排在被拒绝的那一侧，而监控上只看到「限流生效了」这一条好消息。可核验的信号是**把阈值按链路拆开之后，核心链路的配额是否独立**——只要核心与非核心共享同一个桶，分级保障就还没有生效。
- **「降级开关混乱」的成本集中在按下开关的那几秒**。它真正的风险不是开关本身写错，而是**没有人演练过按下之后会发生什么**：降级会同时改变流量形态（用户重试、入口文案、客服进线量），这些副作用只在真实执行时才出现。所以演练的对象不是开关，而是「按下之后的下游反应」——这也解释了为什么开关往往有 owner、有文档，却仍然没人敢按。
- **「忽视 AI 链路」是一条会自我掩盖的反模式**：AI 链路通常只承接部分流量，故障初期表现为「这部分用户体验变差」，不会触发全站级告警；等它通过客服进线量暴露出规模时，通常已经牵连了大量请求。修法的第一条不是加限流，而是**把推理链路的容量与就绪状态接进同一套容量台账**——不进台账的链路，永远不会出现在备战清单上。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 峰值未超单池上限 → 超出单池上限 | 弹性扩容 + 限流降级 | 加钱也加不出容量（单池上限由硬件与拓扑封死），爆炸半径仍是全站 | 单元化（按用户切） | 按用户重分片，一次且不可逆；每单元一套常驻组件，运维面 ×N |
| 单机房 → 跨地域多活 | 单元化 | 一次地域故障仍是全站不可用 | 异地多活 + GSLB | 强一致降为最终一致；跨区延迟；跨境副本受合规约束 |
| 峰值倍数 M 越过平衡点 `M*`（弹性更贵） | 弹性扩容 + 削平 | 按峰值常备的浪费比例随倍数线性上升 | 改变架构形态（单元化 / 异地多活） | 固定常驻机时 F 与运维面乘 N，异地多活的副本是双份而非分摊 |
| 单链路压测 → 上下游联动 | 单链路压测 | 链式故障（缓存击穿、连接打满、消息堆积）在单链路里看不见 | 生产环境全链路压测 + 流量染色 + 影子隔离 | 需要长期维护隔离链路与压测数据，成本不随大促结束归零 |
| 峰值时长从小时级 → 秒级脉冲 | 预测式扩容 + 预热 | 预测精度对着秒级脉冲不起作用，预热只解决首请求慢 | 响应式扩容 + 削平（异步受理 + 幂等） | 需要先补幂等与去重，否则削平会把重复请求的放大效果从入口搬到后台 |
| 备战期一次性压测 → 常态化演练 | 大促前集中做一轮压测与演练 | 一年一次的演练覆盖不到年内新上线的链路，新链路的脆弱点只能等真流量暴露 | 常态化演练（混沌工程 + GameDay）+ 变更后重跑关键链路压测 | 需要常设的可注入点与强可观测性，且误注入本身是一种风险 |
| 传统链路 → 含推理与智能体链路 | 统一容量分母 | 推理容量分母随批大小与序列长度变；实例就绪不等于模型就绪 | 预热池 + 降档链 + 工具级配额 | 预热池是常备成本；每一档降级都要事先单独验证 |

本主题下的阈值不在机器台数，而在两个量：**峰值倍数 M 是否越过平衡点 `M*`**（越过之后弹性与削平的增量机时已高于改架构形态的固定常驻机时），以及**峰值上升时间与扩容生效时间谁更长**（后者更长时，弹性扩容不可能是主方案）。

判断「该换了吗」还有一个更早的信号，它出现在跃迁之前：**备战清单里开始出现「临时增加的常备资源」**——为了这次峰值专门买下的、平时用不上的容量。它每出现一次，都说明当前模式与峰值形态的差距又大了一点；等到这个差距大到无法用一次专项采购覆盖时，换形态就不再是可选项，而是唯一选项。

需要强调的是：**跃迁是单向的**。从单机房走到单元化、从单地域走到多活，都属于「改数据分布」这一类，回退要重做一次分片与一次数据迁移；与之相对，弹性扩容、限流阈值、降级档位都是可逆的。所以判断「要不要跃迁」时，应当把决策的可逆性一起写进记录（见 [Ch13 §08 决策心理学](../../13-decision/08-decision-psychology/08-decision-psychology.md) 的可逆性分级），而不是只比成本。

### 3.7 自检清单

- [ ] 「扩容生效时间」是实测值还是文档承诺值？它比峰值的上升时间长，还是短？
- [ ] 核心链路与非核心链路是否共享同一个限流桶？共享即分级保障尚未生效。
- [ ] 每一个降级开关是否有具名 owner、文档与最近一次演练记录？
- [ ] 有没有一条核心链路的调用依赖被判为非核心的下游？（在压测中验证，不在分级表上验证。）
- [ ] 全链路压测是否覆盖了真实的上下游联动，还是只压了单条链路？影子隔离与数据构造由谁维护？
- [ ] 若今晚峰值翻倍，答案是「加实例」还是「加容量」？如果是加实例，实测过扩容生效时间吗？
- [ ] 推理链路的「实例就绪」与「模型就绪」是否是两个可分别观测的时间量？只有一个，说明预热层还没建。
- [ ] 容量台账里有没有 AI 链路与智能体链路？不进台账的链路不会进备战清单。
- [ ] 值班表之外，升级路径与 Runbook 是否写过、演练过？值班人员能否当场说出「找谁、怎么回滚」？
- [ ] 流量的可分摊维度是否已确定（用户 / 地域 / 时间）？全局聚合类查询是否已有降级路径？
- [ ] 若跨地域部署，跨境副本在目标法域是否可行（GDPR 第 44–46 条一类限制）？
- [ ] 削平依赖的幂等与去重是否已经到位？没有幂等的异步受理会变成重复发放。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 峰值可提前锁定、M 未越过平衡点 | 容量规划 + 弹性扩容 + 分级限流降级 | 峰值驱动的弹性增量机时低于改架构形态的固定常驻机时 |
| 峰值不可预知、上升时间为秒级 | 削平 + 响应式扩容 + 流量调度（局部不均时） | 削平不改数据形态、只改处理方式，是唯一不需要数据迁移的分摊手段 |
| 峰值超出单池上限、爆炸半径全站 | 单元化（按用户切） | 路由把爆炸半径变成 1/N；代价是跨单元聚合与运维面 ×N |
| 跨地域、跨法域 | 异地多活 + GSLB + 单元化 | 把整区故障降为可用性事件，代价是强一致降为最终一致 |
| 含推理服务与智能体链路 | 预热池 + 降档链 + 工具级配额 | 实例分配（秒级）与模型就绪（分钟级）是两个尺度，混作一件事会一直扩容一直没就绪 |
| 多业务共用同一平台 | 分级保障 + 按租户配额 + 工具级限流 | 单租户的流量形态会干扰他人：共享资源时利用率不再对应延迟，配额是唯一可执行的隔离手段 |
| 内部系统、流量可协商 | 限流 + 降级（不扩容） | 峰值可控时，弹性与形态改造的固定常驻成本买不到对应的收益 |

> 本节小结：这一主题下真正起决定作用的差异只有一条——**峰值相对于你的准备窗口是否可控**（时点能不能提前锁定、上升时间是否长于扩容生效时间）。它决定你买的是「更准的预测」还是「更快的切换」，也决定容量是常备还是弹性；分层防御、分级保障、熔断降级、削平与单元化都在这条差异之下派生。反过来说，凡是无法用这两件事解释备战动作（它缩短了切换时间吗？它把峰值移出准备窗口了吗？），都值得先怀疑它是不是在解决一个并不存在的瓶颈。

> 💡 **思考锚点**：拿你最近一次大促的两个数——峰值上升时间与「实测的」扩容生效时间——比一下谁更长：若峰值上升时间短于扩容生效时间（秒级脉冲），你本节买的「预测式扩容 + 预热」还起作用吗？若不起作用，按峰值倍数 M 是否越过平衡点 M*，你是该走削平，还是直接改架构形态？
