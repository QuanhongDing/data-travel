## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

**第一个问题：趋势清单没有时间维度，而大促保障最怕的就是这个。** 把标着「未来」的东西写进备战必做清单，它占掉的是封板前最贵的那个改造窗口；把已经能用的东西写成「未来再说」，峰值当晚你会少掉唯一那把真正管用的开关。同一张清单里，「已经在生产里跑」与「厂商演示里跑过一次」并列，读者据此排备战排期就会踩空。

本节用三级划分，判据必须可核验，而不是「感觉成熟」：

- **L1 生产可用**：
  - ① 已 GA 且有正式 release note；
  - ② 有第三方（非厂商）公开生产案例；
  - ③ 接口稳定。
  - 三条全中才算。没有「准 L1」「边界案例」这类说法——②核不到就是 L2。
- **L2 可试点**：已可用但接口 / 生态未稳，或仅有厂商自有案例，或只在小规模被验证。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。记录，不要在架构里预留假设。

**第二个问题：本主题的「能力」有一半是流程，但判据不因此放宽。**

- 另一半是产品特性（扩缩组件、缓存、限流与降级开关），有正式 release note，好判；
- 真正决定大促成败的却是流程类对象：压测节奏、降级开关的归属、值班授权、演练次数。它们没有 release note，只有公开复盘与会议分享。
- 这不构成放宽①的理由：流程类对象如果拿不出可核验的公开记录（哪一年、哪家、什么形态），同样只能记 L2。**你自己的演练做得好，不等于别人能复核。**
- 与①同理，**③只指接口 / 契约 / 标准的稳定性**（对外 API、协议、语义约定是否多年不变）。「收益不能线性外推」「效果依赖流量形态」都不是③：前者属于收益泛化性问题，后者属于缺第三方验证——它们该记在②上，或写进 5.2 的「由此付出的」。把这类理由塞进③，会让同一列里③的含义一行一个样，读者无法按 5.1 的定义复现评级。

**第三个问题：先问这个方向改变的是哪一层。** 四类方向的前沿性来源不同，成熟节奏也不同：

| 类别 | 问的问题 | 代表方向 | 判 L1 的难点 |
| --- | --- | --- | --- |
| 容量侧 | 峰值的算力从哪来 | GPU 弹性扩容、可中断容量、量化、预热 | 卡在②：公开记录基本是云厂商与平台方自述 |
| 成本侧 | 峰值时的推理怎么变便宜 | Prompt 缓存、模型降级链路 | 卡在②：折扣幅度与命中率都是自测口径 |
| 链路侧 | 一次请求变成多少次内部调用 | Agent 逐工具限流、超时预算、RAG 逐环节限流、向量检索容灾 | 卡在③：调用链的契约与语义约定仍在演进 |
| 决策侧 | 当晚谁判断、判断得多快 | 流量预测、异常检测、根因分析、Runbook 推荐 | 卡在②；其中预测、根因、Runbook 三类连①也缺：只有异常检测与风控类能具名到正式产品文档 |

**第四个问题：别把「模型降级」和「功能降级」当成同一件事。** 大促保障里的降级原本是二值的（关掉评论、关掉推荐），LLM 让它第一次可以是连续的（同一功能换更小的模型、更短的上下文、更浅的检索）。连续降级是本节最有价值的一条机制，也是最容易失控的一条——它的代价写在 5.2.2。

| 演进方向 | 级别 | 判据（① 正式发布记录 ② 第三方（非厂商）公开生产案例 ③ 接口稳定） | 现在该做什么 |
| --- | :---: | --- | --- |
| 推理服务的弹性扩容（GPU 实例弹性、自动扩缩） | L2 | ①③满足（声明式扩缩对象与云厂商正式服务长期 GA）、**②缺**：公开记录是云厂商与平台方自述 | 先把扩缩信号从资源占用换成排队（5.2.1） |
| 可中断 GPU 容量（抢占式承载可排队的推理与离线作业） | L2 | ①③满足、**②缺**（与 [Ch12 §04 容量规划](../04-capacity-planning/04-capacity-planning-section-5-ai.md) 的同一条方向判定一致） | 先按「中断一次值多少钱」给 AI 负载分类 |
| 模型量化（INT8 / INT4 / FP8） | L2 | ①由引擎与硬件发布记录承担、**②缺**：加速比多为厂商与框架方自测、**③缺**：量化格式与算子支持随引擎与硬件世代变化 | 先自测再优化；位宽不等于收益（5.2.1） |
| 模型预热与冷启动控制 | L2 | ①满足、**②缺**、**③缺**：预热的实现方式是各引擎自定义，无标准接口 | 按 SLO 反推预热池大小（5.2.1） |
| Prompt 缓存 | L2 | ①满足（推理引擎与网关侧的正式能力与文档，以官方文档当前版本为准）、**②缺**、**③缺**：最小可缓存长度、失效与计费口径各家不同 | 先量准命中率，再算省了多少（5.2.2） |
| 模型降级链路（大模型 → 中模型 → 小模型 → 规则） | L2 | ①满足、**②缺**、**③缺**：链路的分级口径与开关契约是各企业自建，没有跨厂商标准 | 把每一级做成可独立验证与可回滚的开关（5.2.2） |
| 智能体链路限流与超时预算 | L2 | ①满足（框架与网关提供限流与超时配置）、**②缺**、**③缺**：Agent 调用的可观测约定仍在演进（OpenTelemetry 的 GenAI 语义约定属哪一个稳定性状态，请以其官方文档当前版本为准） | 逐工具限流 + 每环节单独超时（5.2.3） |
| RAG 链路逐环节限流 | L2 | ①满足（Embedding / 检索 / Rerank / 推理各组件有正式文档）、**②缺**、**③缺**：环节边界随框架变化 | 逐环节算容量，不要给整链路拍一个数 |
| 向量检索容灾（分片副本 + 降级关键词 + 降级缓存） | L2 | ①满足、**②缺**、**③缺**：降级路径的实现因引擎而异，无标准接口 | 先把降级路径演练过，再让它上线 |
| LLM 推理容灾与多模型路由 | L2 | ①满足、**②缺**、**③缺**：路由与配额无标准契约 | PoC，按请求难度分流；成熟度与缺③的原因见 5.2.3 的四行判定 |
| AI 需求预测（流量与 GPU 容量，用 LSTM / Transformer 替代 ARIMA） | L3 | **①缺**：没有可核验的验收标准；**②缺**：「比 ARIMA 更准」「AI 预测 GPU 需求就能提前扩容」都是无来源、无条件的比较声称，本节不采用——判定方法是问材料有没有写清预测窗口、误差口径与预测错了的代价（同类数字的使用规则见 5.4） | 先用主文件 §2.3 的业务叠加法 |
| AI 异常检测（爬虫、羊毛党、异常消耗） | L2 | ①满足（云侧异常检测与风控类能力有正式产品文档：AWS CloudWatch 的 Anomaly Detection、Cloudflare Bot Management、AWS WAF Bot Control，GA 状态与版本可按各自官方文档与 release notes 核验）、**②缺**：公开记录是产品页与客户案例页（属厂商材料）、③满足（对外是规则 + 动作 + 日志字段的稳定契约） | 用来发现「形态变了」，不用来自动封禁（5.2.4） |
| AI 根因分析（LLM 读日志与 Trace） | L3 | **①缺**：公开材料以演示与产品页为主，给不出验收标准；**②缺** | 用在复盘写时间线，不用在当晚止血（5.2.4） |
| AI 自动 Runbook 推荐 | L3 | **①缺**、**②缺**；且它推荐的多数动作不可逆 | 只采纳它「下一步该查什么」的部分 |
| 学术侧：AI 驱动的 Auto-Scaling 与预测式负载均衡 | L3 | **①缺**：仅论文与原型，无可核验的发布记录；**②缺**（5.4） | 记录，不要进备战必做清单 |
| 学术侧：自适应熔断与弹性微服务 | L3 | **①缺**、**②缺**：公开材料是论文与仿真，且既有手段已在主文件 §2.3 覆盖 | 先在 §7.3.3 的既有手段上补超时预算 |
| 自愈（自动重启、自动隔离、自动降级） | L3 | **①缺**、**②缺**：公开记录少，且恢复动作与 §7.3.4 的止血顺序直接冲突 | 只自动化可逆动作（5.2.4） |
| AIOps 与 LLMOps 共享可观测性数据（融合决策） | L3 | **①缺**（没有可核验的对外能力）、**②缺** | 先统一 Trace 口径，再谈融合 |
| 跨云弹性（Multi-Cloud Burst） | L2 | ①满足、**②缺**、**③缺**：跨云接口无标准 | 先做可迁移性准备（镜像、权重、密钥） |
| 边缘 + 云端协同的大促分流 | L2 | ①满足（边缘侧托管服务与推理引擎已 GA 多年：AWS IoT Greengrass、Azure IoT Edge、NVIDIA Triton Inference Server 均有公开的 GA 文档与版本记录，可按其官方文档与 release notes 核验）、**②缺**、**③缺** | 只在延迟或数据出域要求下做 |

**本主题下没有方向同时满足 L1 的三条判据。** 最接近的两行是「推理服务的弹性扩容」与「可中断 GPU 容量」：它们满足①（都是长期 GA 的正式服务，扩缩对象与中断通知有正式文档）与③（声明式扩缩对象、中断通知与容量池模型多年未出现破坏性变更），**卡在②**——能查到的公开记录是云厂商自己的客户案例与平台方自述，按判据不计入第三方生产案例。按规则，②核不到就是 L2。其余方向不够格的原因集中在两处：**容量侧与成本侧普遍缺②**（折扣、命中率、加速比都是自测口径），**链路侧以及量化、预热、缓存、降级链路这些方向另外缺③**（量化格式与算子、预热与降级的实现方式、缓存口径都随引擎与框架变化，没有跨厂商标准）。

### 5.2 演进方向逐条拆解（核心节）

下面四条覆盖 5.1 的四类：5.2.1 容量侧（峰值的算力从哪来），5.2.2 成本侧（怎么让峰值更便宜，也是本节唯一改变了失败语义的一条），5.2.3 链路侧（一次请求变成多少次内部调用），5.2.4 决策侧（当晚谁判断）。每条都按同一结构展开：旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度。

#### 5.2.1 推理容量：把「扩容」与「可用」拆成两件事

- **旧做法与它的卡点**：
  - §2.2 的资源估算公式是「所需 Pod 数 = 峰值 QPS ÷ 单 Pod 承载力 ×（1 + 安全冗余%）」。这个公式对大促里的推理服务不成立：分母不是常数，它随批大小、序列长度、量化位宽与引擎版本变。
  - 更硬的卡点是**两个时间尺度被混成一个**：实例分配 / 调度是秒级，模型加载到显存是分钟级。用同一个「扩容」词描述它们，冷启动预算就会整整差一个量级。
  - 加上 §1.2 痛点里的「弹性扩容慢」，大促里最典型的失败形态不是没有容量，而是**容量到了、模型还没就绪**。
- **AI 改变了什么机制**：容量单位从「实例数」改成「token 吞吐 × 上下文长度分布」，并让**计量与就绪彻底分家**——可扩的是实例与显存块，不可秒扩的是权重加载与显存预热。
- **由此得到的**：
  - 因为实例分配与模型就绪是两个尺度，所以预热池与准入控制成了独立的一层：**把加载延迟移出关键路径**，缩容到零才成立；
  - 因为可中断容量用「随时可能被收回」换低单价，所以峰值可以拆成「必须保住的部分」与「可以迟到的部分」——批推理、离线评分、索引重建、特征回填都能放进后者；
  - 因为量化的收益只对权重近似线性，所以「先测后优」第一次是可执行的流程，而不是经验之谈。
- **由此付出的**：
  - **共享之后「利用率」不再对应延迟**：同一张卡上多租户互相干扰，利用率好看而尾延迟恶化，扩容信号变成噪声。
  - **可中断是外生的**：回收时点与规模由供应商容量池决定，需要中断通知 + 幂等 + 重排队兜底；没有幂等键的作业放上去，是在制造重复计算。
  - **折扣是上限不是承诺**：官方给的是「最高可低多少」，实际折扣取决于容量池与中断率，把上限写进预算表是典型的高估。
  - **分母必须自测**：任何单点吞吐数字（尤其是产品页上的）都不能直接当容量分母。
- **证据与来源**：
  - 【公开】vLLM 自 2023 年起的公开 release notes：连续批处理与分页 KV 缓存是「吞吐分母」变化的机制来源；其对外服务接口按 OpenAI 兼容形态提供，是本行判 ③ 满足的依据。
  - 【公开】Kubernetes 官方文档：autoscaling/v2 自 1.23 起为稳定 API 版本（可按 Kubernetes CHANGELOG 核验）；KEDA 作为 CNCF 项目提供按外部指标的扩缩（版本与毕业状态以其官方页面与 release notes 为准）。
  - 【公开】AWS EC2 Spot 官方文档与 What's New（Spot 实例自 2009 年起提供）：中断通知机制、容量池模型与折扣表述（「相对按需价最高可低约 90%」）——「最高」不等于典型值，规划请用你们自己观察到的折扣与中断率【经验】。
  - **②（第三方非厂商的公开生产记录）本节给不出具名来源**：能查到的是云厂商客户案例页（属厂商材料）与第三方扩缩工具的文档（描述「怎么用」，不是「谁在生产里用了、结果如何」）。这是这两行判 L2 而不是 L1 的直接依据。
- **成熟度**：本小节四个方向均为 L2，但缺的判据不同：**实例弹性扩容与可中断容量**是①③满足、②缺；**量化与预热**是①满足、②缺、③缺（量化格式与算子支持随引擎与硬件世代变化，预热的实现方式是各引擎自定义）。5.1 表里同属容量侧、不在本小节展开的三行也在这里定位：**跨云弹性**与**边缘 + 云端协同的大促分流**为 L2（①满足、②缺、③缺：跨云接口与边缘侧的模型下发链路都没有跨厂商标准）；**学术侧的那一行**（表中行名「学术侧：AI 驱动的 Auto-Scaling 与预测式负载均衡」）为 L3（①缺、②缺：公开材料是论文与仿真，无发布记录，见 5.4）。判定方法：问你们平台「实例就绪」和「模型就绪」是不是两个可分别观测的时间量——只有一个，说明这条机制还没被落地。

```text
把「容量不够」翻译成三个不同的问题（三个的解法完全不同）
  问题一：实例不够        → 加实例（秒级可解，弹性扩容）
  问题二：模型没就绪      → 预热池 / 权重分层缓存（分钟级，必须提前）
  问题三：显存放不下更多并发 → KV 预算：并发上限 ≈ 可用显存 ÷ 单序列 KV
  ────────────────────────────────────────────────
  大促当晚最常见的误判：把问题二当成问题一
      → 一直扩容，一直没就绪，监控上「实例数够了」而业务一直超时
  判断它是不是问题二：看扩容后 P99 是否随实例数上升而下降
      不下降 → 瓶颈在预热或显存，不在实例数
```

#### 5.2.2 降级链路与 Prompt 缓存：把「不可用」变成「质量可调」

- **旧做法与它的卡点**：
  - 传统降级是二值的：关评论、关推荐、关积分。开关只有开与关，用户立刻知道功能没了。
  - 二值降级导致一个组织性问题：**开关不敢按**。§7.3.3 已经指出「没有 owner、没有文档、没有演练的开关，在关键时刻既不敢按也不敢不按」，而二值降级的损失可见，谁按谁担责。
  - 成本侧同理：推理按调用线性计费，峰值倍数直接变成账单倍数（主文件 §1.2 把「AI 算力的非线性增长」列为额外复杂度）。
- **AI 改变了什么机制**：**把降级的粒度从「功能」下沉到「质量」**——同一个能力可以由大模型、小模型、规则兜底分别产出，代价是答案质量不同而不是功能消失；同时，**相同前缀的请求命中缓存后按折扣计费**，让成本不再是纯粹的「随调用量线性」——命中带来的是计费折扣，不是归零。
- **由此得到的**：
  - 因为质量可调，所以降级从「丢功能」变成「降体验」，**开关的决策成本下降**：按下去不再等于让用户看见功能缺失，而是让一部分请求拿到更弱的答案；
  - 因为缓存把成本与命中率绑定，所以峰值期的成本曲线出现一个可测的折点——命中率是可测的量，不是假设；
  - 因为多级链路天然可独立验证，所以降级预案第一次能被演练成「逐级试按」，而不是一整块开关。
- **由此付出的**：
  - **质量下降是不可见的**：用户看不出答案变差了，但投诉与转化率会变；降级期间必须把「模型档位」写进可观测维度，否则复盘无法归因。
  - **每一级都要单独验证**：小模型在你的业务口径上是否还可用，是一件必须事先测过的事；没测过的降级级，等于没有这一级。
  - **缓存的一致性成本**：前缀缓存依赖「前缀完全一致」，模板一动命中率归零；缓存本身还要有失效与穿透保护，否则它变成新的故障点。
  - **命中率不是常数**：它随流量形态变化（FAQ 型流量高、自由对话型流量低），按最好情况估收益是常见的高估。
- **证据与来源**：
  - 【公开】**Prompt 缓存**：Anthropic、OpenAI、Google（Gemini API）与 DeepSeek 等厂商在 2024 年前后陆续公布缓存计费档位（缓存命中的输入 token 按折扣计费），vLLM 等推理引擎同期提供自动前缀缓存；具体折扣幅度、最小可缓存长度与计费口径**以各厂商定价页与引擎文档当前版本为准**，可按「prompt caching pricing + 厂商名」自行核验。
  - 【公开】多模型路由与 LLM 网关类能力的正式文档（路由、配额、限流随产品发布迭代，能力边界请按官方文档当前版本核验）。
  - 本主题公开材料里出现的百分比（如「缓存可降低 50%+ 推理成本」）多为厂商或平台方自测口径：**本节不采用具体百分比**，理由是同一句话里的分子（省了多少）与分母（原本多少钱）都没有条件限定语。要核验，按「prompt caching pricing + 厂商名」检索其官方定价页。
  - **②本节给不出具名来源**：能查到的是厂商的计费页与产品博客，属厂商材料。
- **成熟度**：Prompt 缓存与模型降级链路均为 L2，且两行都是①满足、②缺、③缺——Prompt 缓存缺③是因为最小可缓存长度与计费口径各家不同，降级链路缺③是因为分级口径与开关契约是各企业自建，没有跨厂商标准（与 5.1 表逐行一致）。

| 降级档位 | 动作 | 用户能感知到什么 | 必须在备战期准备什么 |
| --- | --- | --- | --- |
| 档位 0（正常） | 大模型 + 完整检索 + 完整上下文 | 正常 | — |
| 档位 1 降检索深度 | 减少召回条数与 Rerank 用量 | 几乎无感 | 各档位下的质量基线（事先测过） |
| 档位 2 降模型档位 | 换更小的模型 / 更短上下文 | 答案变短、变粗 | 小模型在同口径上的可用性验证 |
| 档位 3 规则兜底 | 模板化回答 + 人工入口 | 功能仍在、答案固定 | 兜底话术与转人工路径 |
| 档位 4 关闭入口 | 直接不提供该能力 | 功能消失 | 入口文案与客服预案 |

（这里的「档位」是降级的**质量档位**，与本节 5.1 / 5.2 用来标注成熟度的 L1 / L2 / L3 是两套编号，不要混读。）

#### 5.2.3 智能体链路：故障域从「服务」变成「调用链」

- **旧做法与它的卡点**：
  - 传统大促里，一次请求基本是一次调用：一个服务慢或挂，影响面就是那个服务。
  - Agent 形态把一次用户请求变成 5–10 次 LLM 调用 + 若干次工具调用【经验，量级见主文件 §1.4 的 2023 年节点】。**可用性是乘法关系**：各环节可用率相乘，环节数一多，链路可用率远低于任一单环节。
  - 更麻烦的是失败形态：RAG 链路里「检索返回空」不是错误，它会让 LLM 拿不到证据却照样生成答案——**这类失败不触发熔断**，因为接口全部返回成功。
- **AI 改变了什么机制**：**一次请求的内部调用次数与串行深度增加一个量级**，于是限流、超时、熔断的作用对象从「服务」变成「调用链的每一环」，而每一环都有各自的容量单位（Embedding 看 QPS × 维度，检索看 QPS × 索引大小，Rerank 看 QPS × 文档数，推理看 token）。
- **由此得到的**：
  - 因为可用性是乘法，所以「零星的 99.9%」不再够用：**十个环节各 99.9%，链路可用率约 99.0%**【推算：0.999¹⁰ = 0.99004，即不可用时长约为单环节的 10 倍量级】——这解释了为什么必须给链路设总预算，而不是逐环节各自达标；
  - 因为每一环的容量单位不同，所以逐环节限流是唯一能回答「卡在哪一环」的办法：整链路一个阈值，只会让你在峰值时看见「被拒了」却不知道谁在拖；
  - 因为「检索为空」这类静默失败不报错，所以**质量降级必须有自己的信号**（召回条数、引用覆盖率），否则它只能通过投诉被看见。
- **由此付出的**：
  - **超时必须分层且总预算有限**：每环节单独超时之和若大于用户可接受的总时长，等于没有超时——预算必须自上而下分配，而不是各环节自定。
  - **限流要区分「拒绝」与「降级」**：峰值时把 Agent 的某个工具限流，正确结果通常是「绕过该工具」而不是「整链路失败」，这需要工具层面有可选的降级路径。
  - **成本随环节数放大**：一个请求的 token 成本是各环节之和，重试与纠错循环会把它再乘一遍。
  - **可观测口径还在演进**：Agent 调用的语义约定（gen_ai 一类属性）仍随标准版本调整，代价是跨版本的历史对比会断档——升级前需要先把口径固定下来。
- **证据与来源**：
  - 【公开】主文件 §2.3 第 8 条已把「推理服务弹性、Prompt 缓存、模型降级链路、向量检索容灾、智能体链路限流」列为本主题的既有机制，本节沿用它的问题分解，把每一环的容量单位写清。
  - 【公开】OpenTelemetry 的 GenAI 语义约定用于标注 LLM 调用（其稳定性状态与属性名以官方文档当前版本为准）——它是③在这一行的直接依据：**标准还在演进，就不算接口稳定**。
  - 【公开】向量检索侧的容灾形态（副本、降级为关键词检索、降级为缓存兜底）在各向量库官方文档中均有对应（能力与配额以官方文档当前版本为准）。
  - **②本节给不出具名来源**：Agent 链路限流的公开材料多为框架方与平台方自述。
- **成熟度**：智能体链路限流、RAG 逐环节限流、向量检索容灾、LLM 推理容灾与多模型路由四行均为 L2，且都是①满足、②缺、③缺（缺③的原因分别写在 5.1 表对应行）；5.1 表里同属链路侧的「学术侧：自适应熔断与弹性微服务」为 L3、①缺、②缺——它要解决的正是本小节的分层超时与熔断，但公开材料是论文与仿真（见 5.4），其可落地部分回到 §7.3.3；其中「整链路只设一个统一阈值」的做法应视为反模式——它无法定位瓶颈。

```text
超时预算要自上而下分，不能自下而上加（否则总和必然超）
  用户可接受总时长 T = 3s
  ├─ 网关与鉴权           0.1s
  ├─ 检索（含 Embedding）  0.5s   ← 超时即降级为无检索回答
  ├─ Rerank               0.3s   ← 超时即跳过 Rerank
  ├─ 工具调用（逐个）      0.8s   ← 超时即绕过该工具
  └─ LLM 推理             1.3s   ← 剩余预算，不足则降模型档位
  ────────────────────────────────────────────────
  每一步超时后的动作必须是「降级」而不是「重试」
      重试会把剩余预算吃光，且把故障放大到下游
```

#### 5.2.4 AI 辅助保障决策：改的是「发现」，不是「止血」

- **旧做法与它的卡点**：
  - §7.3.4 已经把不确定性拆成三件事：发现瓶颈（压测）、验证恢复路径（演练）、缩短暴露时长（回滚）。三者里最贵的是时间错位——**「发现问题的时间点」决定你能做什么**。
  - 传统工具在「发现」这一段卡在信噪比：大促当晚告警量是平时的数倍，值班人员的时间和注意力是真正稀缺的资源，而不是数据。
- **AI 改变了什么机制**：主要改**摘要与检索**（把几百条告警压缩成几句话、把「上次类似现象怎么处理的」检索出来），以及**把人的经验判断换成统计判断**（流量预测、GPU 需求预测、异常检测）。
  - 它**没有**改变的是：因果证据仍然来自变更记录与依赖拓扑（这些不在日志文本里），以及**当晚的止血决定权仍然在人手上**。
  - 结论先说：这类能力是**接口改良 + 发现能力改良**，不是架构变化——可以把它接到**可逆**的自动动作上；「不可逆动作只进提示、不进自动化」这条边界写在 5.1 表「AI 自动 Runbook 推荐」一行的判据与 5.7 的「明确不要做」一列里。
- **由此得到的**：
  - 因为摘要能压缩告警量，所以值班人员的注意力被释放出来处理真正要做判断的事——这是本节成本最低、见效最快的 AI 应用；
  - 因为异常检测盯的是形态而不是阈值，所以「今年峰值形态和去年不一样」可以被提前发现，而不是等 SLO 破了才知道；
  - 因为复盘可以从日志里自动生成时间线，所以复盘会的时间从「对齐事实」转向「讨论原因」。
- **由此付出的**：
  - **相关性不是因果**：LLM 读日志得到的是「当时发生了什么」，不是「为什么会发生」；把它的输出当根因，会把复盘带偏。
  - **摘要会掩盖长尾**：被压缩掉的低量告警里，可能正好是某个新故障的第一条线索——摘要必须能下钻到原文。
  - **指引会被当作授权**：Runbook 推荐一旦被当作「照着做」，就把不可逆动作交给了统计建议；推荐的正确用法是「告诉你下一步去哪看」。
  - **异常检测会被业务变更污染**：每一次成功的营销活动在模型眼里都是异常，价值取决于谁去解释异常。
- **证据与来源**：
  - 【公开】主文件 §2.3 第 1 条已把 ARIMA / Prophet / LSTM 与「业务叠加法」列为峰值预测方法；§7.3.4 给出「发现 / 验证 / 止血」的顺序，阈值依据则在 §7.5 的决策树里按节点 T1–T10 逐条给出（§7.3.4 本身不给阈值）——本节不重复，只补 AI 改变了哪一段。
  - 【公开】告警抑制与分组是成熟机制（各类监控与事件管理产品的正式文档均有对应），AI 摘要是在它之上的增量，而不是替代。
  - 【公开】**异常检测这一类的 ① 可以具名**：云侧异常检测与风控类能力有正式产品文档（AWS CloudWatch 的 Anomaly Detection、Cloudflare Bot Management、AWS WAF Bot Control，GA 状态与版本以其官方文档当前版本为准）——这是 5.1 表「AI 异常检测」判 ① 满足的依据（③ 的理由写在那一行的判据栏）；但它同样只有厂商材料，②仍缺。
  - **流量预测、根因分析与 Runbook 推荐这三条的①②本节都给不出可核验的来源**：公开材料以演示与产品页为主，既无验收标准，也无第三方生产记录，只能记 L3。
- **成熟度**：AI 异常检测 L2（①③满足、②缺，①的依据见上一条来源）；AI 需求预测（流量与 GPU 容量）、根因分析、AI 自动 Runbook 推荐、自愈，以及同属决策侧的「AIOps 与 LLMOps 共享可观测性数据」均为 L3，都是①缺、②缺（缺①的原因分别写在 5.1 表对应行）。判定方法：问「这条建议如果自动执行，最坏结果可不可逆」——可逆的可以自动化，不可逆的只能进提示。

### 5.3 与本主题既有栈的接口在哪

不要写「与 X 结合」这种空话。下面写清**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 容量规划（[Ch12 §04](../04-capacity-planning/04-capacity-planning.md)）↔ 大促容量 | 峰值系数与逐层流失率作为输入（逐层建模的口径见 [§6 阿里的备战节奏案例](03-large-event-readiness-section-6-sec6.md)） | 系数低估由容量规划负责；执行不及由大促保障负责 | 成熟，先做 |
| 单元化（[Ch12 §01](../01-cell-based-architecture/01-cell-based-architecture.md)）/ 异地多活（[Ch12 §02](../02-multi-region/02-multi-region.md)）↔ 峰值分摊 | 路由键（`CellID = Hash(UID) mod N_Cells`）与切流指令 | 切流决策由值班指挥负责；路由规则错误由平台负责 | 成熟（见 §7.3.2） |
| 混沌工程（[Ch12 §06](../06-chaos-engineering/06-chaos-engineering.md)）↔ 降级链路 | 故障注入点覆盖到「检索为空」「模型超时」这类静默失败 | 注入未覆盖的静默失败由混沌演练的发起方负责 | 需制度化，AI 链路是新缺口 |
| 灰度与回滚（[Ch12 §09](../09-gray-and-rollback/09-gray-and-rollback.md)）↔ 模型与 Prompt 上线 | 模型档位 / Prompt 版本作为可回滚对象 | 不可回滚的变更由批准它的人负责 | 成熟；模型侧要补门禁 |
| 可观测性（[Ch11 §04](../../11-cross-cutting/04-observability/04-observability.md)）↔ AI 摘要与根因 | Trace + 指标 + 日志导出；摘要必须可下钻回原文 | 数据缺口由可观测性方负责；误判由使用建议的一方负责 | 前一半成熟，下钻链路常缺 |
| 智能体平台（[Ch5 §01](../../05-agent-platform/01-data-agent/01-data-agent.md)）↔ 大促链路保障 | 超时预算与逐工具配额作为契约参数下发 | 未分配预算的环节由 Agent 平台负责 | L2，要新增契约 |
| 向量库（[Ch4 §02](../../04-data-assetization/02-vector-lake/02-vector-lake.md)）↔ 检索降级 | 降级开关（走关键词检索 / 走缓存）与其响应时间承诺 | 降级路径未演练由检索服务方负责 | L2 |
| 推理平台（[Ch9 §01](../../09-data-intelligence-product/01-ai-compute/01-ai-compute.md)）↔ 大促容量 | token 吞吐、上下文分布、模型清单作为输入 | 把厂商吞吐数字直接当分母的一方负全责 | L2，需自测 |

这张表按「现在能不能动」分三档读：**容量规划、单元化、异地多活、灰度回滚这几行现在就能动**，它们几乎不需要新东西，缺了它们后面所有判断都没有输入；**混沌工程与可观测性要补覆盖**——故障注入要延伸到「检索为空」「模型超时」这类静默失败，Trace 要能下钻回原文，这两条是 AI 链路上最常见的缺口；**Agent 平台与推理平台这两行要新增契约**（超时预算、逐工具配额、token 口径），它们的风险在于契约没有写清时，故障会表现为「说不清是谁慢」。

最容易被忽略的一条接口是**分母由谁负责**：§2.2 公式里的「单 Pod 承载力」、推理公式里的「单卡吞吐」，通常由平台方提供、由业务方使用。分母错了，业务方算出来的每一个数都错，而业务方没有能力发现它错——所以这条接口必须写清：分母由平台方提供、带测试条件与测试日期，每次硬件或引擎升级后重测一次。

这张表里有两行的组合口径在本章 [§7.6 选型矩阵](03-large-event-readiness-section-7-sec7.md) 已经给出：AI 推理服务的首选是「GPU 弹性 + Prompt 缓存 + 模型降级链路」，智能体链路的首选是「工具级限流 + 单工具熔断 + 链路降级」而**不选整链路统一限流**。本节 5.1 表把这组能力逐行标级、5.2 逐条给机制，两处的等级与组合口径一致——若两处对不上，以本节的判据说明为准并回改 §7.6。

### 5.4 公开进展与文献

按「论文与公开基准 / 官方 release note 与文档 / 第三方生产案例」三类列出，每条给可核验的名称与年份；第三类本节给不出条目，原因写在那一栏里。

**论文与公开基准**

- 【公开】Kwon 等人，PagedAttention / vLLM（SOSP 2023）：分页 KV 缓存与连续批处理的机制来源。
- 【公开】Gandiva（OSDI 2018）与 AntMan（OSDI 2020）：生产集群中 GPU 共享与动态伸缩的系统工作——「池化与弹性不是新概念」的证据。
- 【公开】Autopilot（EuroSys 2020）：生产集群上的自动容量建议与伸缩，说明自动伸缩有早于 LLM 的公开路线。
- 【公开】MLPerf Inference（MLCommons，2019 年起发布推理基准结果，按规则版本定期更新）：结果与规则版本化的推理基准，作用是提供**可复现的对照条件**，而不是给你一个可以抄的吞吐数字。
- 由此得出一条对本主题有用的判断：**上述基准都不是为「已知时点的倍数级峰值」设计的**。要评估大促形态，可用的公开材料仍然是两处——平台方公开的备战复盘，以及你们自己的全链路压测；这也是本节把「演练能覆盖多少失效模式」写进 5.3 混沌工程那一行、而不是放进文献的原因。

**官方 release note 与文档（① 侧证据）**

- 【公开】AWS EC2 Spot 官方文档与 What's New（Spot 实例自 2009 年起提供）：中断通知、容量池模型、折扣表述（以官方页面当前版本为准）。
- 【公开】Kubernetes 官方文档：autoscaling/v2 自 1.23 起为稳定 API 版本；KEDA 提供按外部指标的扩缩（版本与毕业状态以 CNCF 官网与项目 release notes 为准）。
- 【公开】AWS Fault Injection Service 的官方文档（该服务于 2021 年前后正式可用；名称与能力边界以其官方文档当前版本为准）：以实验模板定义故障注入——它能承担 5.3 里「把注入点延伸到静默失败」这件事。**该服务是否提供、以什么形态提供 AI 推荐，请以其官方文档当前版本为准。**
- 【公开】Netflix 的 Chaos Monkey 是 2011 年前后开源的故障注入工具（可按 Netflix 技术博客与该项目的公开仓库核验）。
- 【公开】vLLM 与主流推理引擎的公开 release notes（2023 年起）：前缀缓存、连续批处理、量化支持这些改变成本与吞吐的能力，按版本可逐条核对。
- 【公开】OpenTelemetry 的 GenAI 语义约定（2024 年前后进入 OpenTelemetry 的语义约定仓库；当前的稳定性状态以官方文档为准）：它是判断「Agent 链路接口是否稳定」的依据。
- 【公开】Anthropic、OpenAI、Google（Gemini API）与 DeepSeek 的 Prompt 缓存计费档位（2024 年前后陆续公布）：缓存命中的输入 token 按折扣计费，折扣幅度与计费口径以各自定价页当前版本为准，可按「prompt caching pricing + 厂商名」核验。

**第三方生产案例（② 侧证据）**

- **本节给不出具名的第三方（非厂商）生产案例**，这不是排版空缺，而是本主题最重要的一个事实：它是 5.1 表里没有一行判到 L1 的直接原因。能检索到的两类材料都不算②——云厂商与平台的客户案例页属厂商材料；第三方工具与框架的文档描述的是「怎么用」，不是「谁在生产里用了、结果如何」。
- 自己核验一条方向够不够 L1 的方法：找一份**非厂商、具名、带年份**的工程博客或会议分享，读它有没有写清负载形态、峰值倍数、降级动作与其代价；写不出这几项，就仍然只能记 L2。
- 检索入口可用「公司名 + 大促 / peak traffic + 推理服务 / LLM gateway」这类组合（峰值保障的复盘分享里，最常出现的正是限流阈值标定与降级演练），命中的厂商产品博客与客户案例页直接剔除——它们读起来最像生产案例，按判据却不算②。

**字节春晚红包一条**：本节**不引用它的具体数字（「20 亿次/分钟」）**。要引用，请以该事件的官方或技术公开材料为准。

**怎么用这几类文献**

- 官方文档用来看**接口与承诺边界**（哪些行为稳定、哪些随版本变）；
- 论文用来看**机制**（为什么吞吐会变），不要拿论文的倍率数字当你的容量分母——论文的运行条件与你的负载不会一致；
- 基准用来看**量级与可比性**，把候选方案放进同一套条件里比；
- 三条都不满足的数字（产品页上的单点吞吐、营销文案里的折扣幅度）不要进公式，也不要进备战必做清单。

### 5.5 被过度宣传的部分

- **「Prompt 缓存可降低 50%+ 推理成本」**——实际是：节省 = 命中率 × 缓存部分的单价差，两个因子都随流量形态变化（FAQ 型流量命中高，自由对话型命中低），把最优情况当默认值是典型高估。**为什么会这样**：缓存要求前缀完全一致，模板一改命中率归零；而且缓存本身还有存储、失效与穿透保护的成本，它是新的故障点。**什么时候它才会成真**：你们能把命中率当成一个持续观测的指标，并且分母（原本那次调用多少钱）带条件说清——这时候这个百分比才有意义。
- **「AI 根因分析让故障定位提速数倍」**——实际是：LLM 从日志与 Trace 里得到的是「当时发生了什么」，根因需要的是因果证据（哪次变更、哪条依赖）。**为什么会这样**：大促当晚真正稀缺的不是分析速度，而是**决定权与回滚权**——很多事故的止损动作是「切流」或「回滚」，它们要授权、要有人签字，快的是摘要，不是决策。**什么时候它才会成真**：把「可逆动作自动执行、不可逆动作保留审批」写成明文规则，并且日志、变更记录与依赖拓扑在同一个时间轴上可对齐——此时它才从写复盘材料变成当晚可用的工具。
- **「GPU 秒级弹性就能扛住峰值」**——实际是：**「秒级」指的是实例分配与调度，模型加载到显存是分钟级**，把后者当前者，冷启动预算会差一个量级。**为什么会这样**：厂商的「秒级弹性」口径里，弹性到的是算力而不是可服务状态；模型权重加载、显存预热、连接池建立都不在调度器的视野里。**什么时候它才会成真**：你的平台能回答「扩容后多久这个实例能返回第一个正确结果」，并且预热池与准入控制被纳入备战流程——见 5.2.1 的判断方法。

### 5.6 未来 3–5 年：可证伪的预测

趋势清单里的句子大多不可证伪（「AI 将主导大促保障」永远正确）。下面把本节可证伪的判断写出来。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 推理侧的分级降级（模型档位）会成为大促预案的标准组件，与「关功能」并列 | 备战文档里出现「降模型档位」的演练项与验收标准；监控里出现「当前模型档位」维度 | 公开复盘里，降级仍只等于关功能；模型档位从不进预案 |
| 前缀缓存与路由会从应用层下沉到网关与引擎的默认配置 | 推理引擎的默认指标里出现缓存命中率；网关文档把路由与配额作为一等能力 | 三年后仍需应用侧各自实现缓存与路由 |
| AI 摘要会成为当晚值班的标配，但它触发自动止血的比例仍然很低 | 值班手册里出现「先看摘要、再下钻原文」的固定流程 | 公开复盘里出现无人值守的自动切流与自动降级 |
| 「AI 主导扩容」的落地形态是「可逆动作自动化 + 不可逆动作审批」，而不是全自动 | 平台里出现明确的「可逆动作白名单」与预算上限 | 主流做法仍是把切流、采购、降级一起交给自动化 |

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 还没有 AI 负载进大促（仅传统链路） | 把可观测性里补上「模型档位」「检索召回条数」两个维度，为将来留位置 | AI 服务是否进入你的峰值链路 | 不要为「AI 大促」单独立项；不要引入 AI 根因分析 |
| 峰值链路里已有一个 LLM 应用 | 把超时预算自上而下分一次；把每个工具的限流与超时写成契约；按 5.2.1 的判定方法查「问题二」 | 引擎侧前缀缓存与路由能力是否已到可用 | 不要整链路设一个统一限流阈值；不要把厂商吞吐数字当分母 |
| 多个 AI 应用 + 多模型 | 建分级降级表并逐级演练（5.2.2）；把模型档位写进可观测维度 | 降级期间的业务指标能否被单独归因 | 不要让没验证过的小模型档位进预案；不要用缓存节省的乐观值做预算 |
| 有 Agent 链路（工具调用 + 记忆） | 逐工具限流 + 每环节超时 + 静默失败的信号（召回条数、引用覆盖率） | GenAI 语义约定的稳定性状态（决定你能否跨版本对比） | 不要在没有幂等与降级路径时把工具调用放进峰值链路 |
| 值班与复盘团队 | 先把 AI 摘要用在「压缩告警 + 生成复盘时间线」 | 摘要能不能下钻回原文 | 不要让 Runbook 推荐直接执行不可逆动作；不要把它当根因 |

「明确不要做」这一列的判据是：**凡是用不可信的分母算出来的容量、用与 SLO 不同构的信号触发的扩缩、以及把不可逆动作交给统计建议的做法，现在做都是浪费**——它们的成本不会立刻出现，而是在第一次峰值形态变化（新模型、新上下文长度、新的 Agent 链路）时集中兑现。

### 5.8 小结

> 本节小结：AI 在本主题下真正改变的**唯一一条机制**，是**把「容量不够」从一种失败变成了一个可设计的降级等级**——传统降级是二值的（功能开 / 关），LLM 让同一能力可以由大模型、小模型、规则兜底分级产出，于是峰值期的选择从「丢不丢功能」变成「降不降质量」。它**没有**改变的，是 §7.3.4 那条老规律：发现问题的时点决定你能做什么，而当晚的止血决定权仍然在人手上。
>
> 因此本章的前沿判断是「容量侧与成本侧先动、决策侧后动」：预热与逐环节限流现在就能做（它们不需要新工具，只需要把两个时间尺度拆开、把预算自上而下分一次）；分级降级需要先有验证过的小模型档位；决策侧是另一种处理——本节判到 L3 的七行里，决策侧占五行（需求预测、根因分析、Runbook 推荐、自愈、AIOps 与 LLMOps 融合），它们只应该被允许生成假设与摘要，不能被允许生成**不可逆**动作（可逆动作的自动化以 5.2.4 的判定方法为限：可逆的可以自动化、不可逆的只能进提示）；另两行是容量侧与链路侧的学术方向（见 5.1 表）。
>
> 💡 **思考锚点**：用 5.2.1 的判定方法问你自己的链路一次——平台的「实例就绪」和「模型就绪」是不是两个可分别观测的时间量，以及扩容后 P99 是否随实例数上升而下降；如果证明瓶颈其实是「问题二：模型没就绪」，你现在有没有把预热池放进备战期、并把降级写成 5.2.2 那张档位 0–4 里可逐级试按的那几级？
