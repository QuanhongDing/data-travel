## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表在这一章有一个比其他章更明显的失效方式：**候选不是同一类东西**。原表的列里同时放着容量规划（一门学科）、单元化与异地多活（两种架构形态）、混沌工程与灰度回滚（两种工程手段）、以及大促保障（本章主题本身）。前三者可以互相比较代价与适用边界，但把主题放进候选里，它在「含自身」的那几维上拿高分是必然的——原表里「大促保障」在峰值承载、复杂度、故障恢复速度、AI 友好度四行都取到（并列）最高分、综合推荐度五星，而在「成本控制」（4 分，容量规划 5 分）与「可持续运营」（3 分，同一行里最低，括号里还注着「仅大促期间」）两行上是落后的一方。这不是结论，是同义反复：不是「大促保障更好」，而是「大促保障包含了这些手段」。

第二，同一个 1–5 量表里混着收益和代价两种方向。「峰值承载」5 分是好事，「复杂度」5 分是坏事——而原表给单元化、异地多活、大促保障在复杂度上都是 5 分。读者看到两个 5 分，无法判断该向往还是该回避。代价维度的正确读法是「你要为它多付什么」，它应该出现在成本函数里（见 7.4），而不是与收益挤在同一列缩放比例上。

第三，打分表跳过了成本随什么增长。「容量规划」与「单元化」的成本曲线形状完全不同：前者的主导项是人力与提前量（几乎不随规模变），后者的主导项是「每 Cell 一套常驻组件」（随 Cell 数线性）。两条曲线在 3 倍峰值下和在 10 倍峰值下的相对位置是相反的（以 t ≈ 100 小时/月的形状为例：3 倍的弹性增量 200N 机时低于形态的固定机时约 219N，10 倍的 900N 则远高于它【推算】），而打分表给的是一个与倍数、也与峰值时长无关的名次——选型恰恰是两者相关的。

第四，原树的阈值凭空给出（原稿只按「3-10 倍」「10-50 倍」「50 倍以上」分档），没有推导。本章的树为每个节点配一条依据（见 7.5），阈值只来自四个地方：7.4 的成本函数（T2–T5 的平衡倍数 `M*`）、扩容机制的生效时间（T7 / T8）、合规约束（T9）、以及失效代价自身的数量级（T10 的资金链路）；T1 与 T6 是形态判断，不设数值阈值。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 峰值的时点与形状 | 峰值能不能在数小时前锁定？上升时间是秒级还是小时级 | 它决定你买的是「更准的预测」还是「更快的切换」，这是两套互不替代的投入 |
| 峰值相对日常的倍数 | 峰值是常态的几倍，每月共持续多久 | 它决定「继续加资源」是否还在成本函数内，以及何时必须改架构形态 |
| 失效的爆炸半径 | 单点故障影响全部用户，还是 1/N 个单元 / 1 个地域 | 决定要不要为可用性付出一致性代价，以及运维面的乘法系数 |
| 发现问题的时机 | 瓶颈在压测时暴露、演练时暴露，还是当晚才暴露 | 发现时刻决定可修复性：越晚发现，越只能靠加资源与收紧限流硬扛 |
| 止血手段的存在性 | 变更能不能回滚，降级优先级是否事先定义 | 故障暴露时长由止血手段决定，与峰值承载能力同等重要 |
| 组织承接能力 | 有没有值班、作战室、跨部门演练与复盘机制 | 峰值是「集中兵力」的场景，没有组织承接的技术方案当晚执行不了 |

> 这 6 条与 [§ 3 设计模式与范式](03-large-event-readiness-section-3-sec3.md) 的模式清单同源：那里给出模式与反模式，这里给出「在什么约束下该选哪一个」。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 容量规划 | 学科：把峰值算成资源量 | 用历史数据与业务漏斗逐层建模，得到各层所需容量（见 [Ch12 §04](../04-capacity-planning/04-capacity-planning.md)） | 所有做峰值准备的组织 | 预测偏差会同时造成过配与欠配 |
| 弹性扩容 | 手段：按指标自动增减资源 | 期望副本数由当前观测指标与目标值的比例推出（Kubernetes HPA 形态） | 云原生团队 | 响应滞后；有状态服务与 GPU 受冷启动与供给约束 |
| 全链路压测 | 手段：在生产环境验证承载力 | 真实链路 + 真实数据 + 按计划倍数打流量，用影子标识隔离 | 有年度级峰值的组织 | 需长期维护隔离链路与压测数据 |
| 单元化（Cell） | 架构形态：按用户切 | `CellID = Hash(UID) mod N`，每 Cell 自包含 DB + Cache + MQ，爆炸半径 = 1/N | 大促型电商、超大流量业务 | 跨单元聚合查询；运维面与组件数随 N 增长 |
| 异地多活 | 架构形态：按地域切 | 同一份数据在多个 Region 提供服务，故障可整区切换 | 全球化业务 | 一致性降级为最终一致；跨区延迟；跨境合规 |
| 混沌工程 | 手段：主动注入故障 | 在生产可控范围注入故障，验证恢复路径而不是验证正常路径 | SRE 团队 | 需可注入点与强可观测性；误注入本身是风险 |
| 灰度与回滚 | 手段：控制变更暴露面与止血 | 按流量比例逐步放量，出问题按开关回退到上一版本 | 所有持续交付团队 | 开关债务；不可回滚的变更等于把风险全押上去 |
| 大促保障 | 编排：把上面几件按节奏组织起来 | 固定备战节奏 + 通关标准 + 作战室与值班，把不确定性分阶段消除 | 有年度固定峰值的组织 | 组织成本高（集中兵力），只在事件级峰值上摊得平 |
| 限流 / 熔断 | 手段：超载时保护系统 | 限流丢请求、熔断断开调用链（CLOSED→OPEN→HALF_OPEN） | 所有对外服务 | 阈值标定不当会误杀真实用户 |
| 降级 | 手段：峰值时收缩功能面 | 按「影响资金 > 影响体验 > 非核心」分级关闭功能，把资源让给核心 | 有清晰链路分级的组织 | 需要事前定义与反复演练，否则当晚无人敢按 |
| AI 推理服务保障 | AI 时代的扩展 | GPU 弹性 + Prompt 缓存 + 模型降级链路（大模型 → 中模型 → 小模型 → 规则） | 有推理服务的团队 | GPU 供给与冷启动限制弹性上限 |
| 智能体链路保障 | AI 时代的扩展 | 单工具限流 + 单工具熔断 + 链路降级，防一个工具拖垮整链 | Agent 平台团队 | 链路长、失败面宽，端到端 SLO 难定 |

这张表与工具选型不同：**没有「许可 / 商业模式」一列**——这十二项是架构形态与工程手段，不是产品，所以用「主要代价」替代了它。

这些候选其实分五族——**五族覆盖上表的 10 行，余下 2 行（第 11、12 项）单独说明**，先分族再选，能省掉一半比较：

1. **容量与资源族**（表中：容量规划、弹性扩容）：回答「按多少资源准备」，输入是预测或指标，输出是资源量。
2. **架构形态族**（表中：单元化、异地多活）：回答「把峰值摊到几个池子上」，改动的是数据分片与部署形态——这一族的代价是**不可逆的**（分片键与地域数定了就难收回）。
3. **流量与依赖控制族**（表中：限流 / 熔断、降级；7.3.3 另把「流量调度」拆出来单列）：回答「超过承载时丢什么、保什么」，在承载不足时才起作用，因此它们不能替代容量建设。
4. **变更与演练族**（表中：全链路压测、混沌工程、灰度与回滚；7.3.4 另把「值班与作战室」单列）：回答「问题多早被发现、多快被止住」，它们不增加承载力，只缩短暴露时长。
5. **主题本身**（表中：大促保障）：它不是与上面四族并列的候选，而是把四族按固定节奏编排起来的流程——这也是 7.1 第一条的由来。

**第 11、12 项（AI 推理服务保障、智能体链路保障）不构成第六族**，它们是上面两族在 AI 服务上的加强，所以放在同一张表里、但在 7.6 与 7.8 里单独分支：GPU 弹性 + Prompt 缓存属于第 1 族（按指标扩容）在「弹性上限由**供给与冷启动**决定、而不是由配额决定」条件下的变体；工具级限流 / 熔断 / 链路降级属于第 3 族（流量与依赖控制）在「一条链上挂十几个工具、单个工具能把整链拖死」形态下的加强。单列它们的原因是失效模式不同（GPU 供给与链式依赖），不是因为它们构成第六种机制。

分族之后有个立即可用的推论：**同族内部才是互斥选择，跨族之间是配套关系**。你在第 2 族里选单元化还是异地多活，是有取舍的；但「要不要全链路压测」与「要不要单元化」之间没有取舍——前者是后者的验证手段。原打分表把这两类问题混在一起比，读者容易得出「选了 A 就不用 B」的结论。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 峰值是「预测出来的」还是「切换出来的」

**机制是什么**：备战的产出是一个「数」（峰值容量）还是一个「动作」（切换能力），取决于峰值的时点是否可控。

**它在各候选中的实现差异**：

| 路线 | 代表 | 前置投入 | 失效方式 |
| --- | --- | --- | --- |
| 预测式（提前扩容） | 容量规划 + 业务漏斗分层建模 + 时间序列预测 | 历史数据、活动增量系数、提前量预算 | 时点或形状判错 → 资源按错误的曲线到位 |
| 响应式（按指标扩容） | Kubernetes HPA、事件驱动的弹性（KEDA 类） | 指标采集、目标值标定、冷却与稳定窗口 | 上升时间短于生效时间 → 扩容永远慢一步 |
| 切换式（可切换容量池） | 常备弹性池 + 一键扩容 / 一键切流 + 反复演练 | 空转的弹性池成本 + 把操作练到肌肉记忆 | 池子未预热 → 切过去也起不来 |

```text
三种路线各要多久才能把容量加上去
  预测式：提前数小时到数天把资源备好 —— 前提是"你知道几点开始"
  响应式：指标越线 → 决策 → 冷启动（拉镜像 / 加载模型 / 预热连接池）
          → 量级在分钟到十分钟（【经验】）
  切换式：切换动作的时间 = "从判断到完成"的演练结果（可被量化并压缩）
  ────────────────────────────────────────────────
  判据不是"哪种更先进"，而是：
      峰值上升时间  vs  扩容生效时间
  上升时间 < 生效时间 → 预测与响应都不成立，必须削平（7.3.2）或切换
```

**由此必然导出的性质**：因为响应式扩容要经过「指标观测窗口 → 决策 → 冷启动」三段，其量级在分钟到十分钟【经验】，所以当峰值上升时间是秒级时，继续提高预测精度也无效——此时要预测的不是「几点」而是「哪一秒」，而这是不可预测的；正确投入是把切换速度或削平能力做上去。因为提前扩容的代价是长时间空转（见 7.4 的推算），所以可预测峰值的真正成本项是「提前多少分钟拉起」而不是「能不能预测准」：提前越多，确定性越高，空转越长。

**公开证据**：Kubernetes HPA 的期望副本数按 `desiredReplicas = ceil[当前副本数 × (当前指标 / 目标指标)]` 计算，输入是**当前观测值**（公式与稳定窗口的默认值随版本调整，请按 Kubernetes 官方文档「Horizontal Pod Autoscaler」章节的当前版本核验）——这决定了它天然是滞后反馈而不是前馈；HPA 另有稳定窗口以避免抖动，会进一步延后动作【经验】。提前拉起与预热对应 [§ 6](03-large-event-readiness-section-6-sec6.md) 阿里双 11 备战的「系统改造 + 缓存预热」环节【公开】（[阿里双 11 技术公开材料, 2019-2024]，同见该案例）。

**失效条件**：当峰值持续时间与扩容生效时间处于同一量级（峰值只持续几分钟）时，弹性的收益被冷启动开销吃掉，容量必须提前常备或靠削平；反过来，当峰值持续数小时以上时，「切换」的价值下降——你迟早要把容量真正加上去，此时容量规划的预测精度重新变得重要。

#### 7.3.2 把峰值摊到哪个维度：按用户切 / 按地域切 / 按时间削平

**机制是什么**：分摊峰值有三个互不相同的维度（表中第 1–3 行），它们的代价落在完全不同的地方：一致性、合规、用户体验。表里第 4 行「按资源优先级」不与这三者并列——它不改变峰值分摊到哪个池子，只改变峰值时谁先用资源。

**它在各候选中的实现差异**：

| 维度 | 代表 | 分摊机制 | 主要代价 |
| --- | --- | --- | --- |
| 按用户切 | 单元化（Cell） | `CellID = Hash(UID) mod N_Cells`，每 Cell 自包含 DB + Cache + MQ；单 Cell 故障影响 1/N | 跨单元查询要额外聚合路径；组件数与运维面 ×N |
| 按地域切 | 异地多活（多 Region） | 就近接入 + 整区切换，容量按 Region 分摊 | 强一致降为最终一致；跨区延迟；副本即跨境传输 |
| 按时间削平 | 静态化 + 边缘承载 + 异步受理 + 幂等去重 | 把同步处理换成「先受理、后处理」，把页面推到边缘，把重复请求挡在入口 | 需要幂等键与去重机制；用户看到的是「已受理」 |
| 按资源优先级 | 资源池隔离 + 分级降级 | 峰值时把资源集中给核心链路 | 降级清单必须事前定义，否则当晚争论 |

**由此必然导出的性质**：因为单元化用一致性 Hash 把同一用户固定到同一 Cell，所以单 Cell 故障的爆炸半径是 `1/N_Cells` 而不是全站（N 个 Cell 是乘法关系：Cell 越多，单点影响越小，但跨 Cell 的聚合路径越多），代价是「我的全部订单」这类全局查询必须走额外聚合或异步同步——它把可用性买到手，付出的是跨单元一致性，并且**运维面随 N 增长**（每多一个 Cell，监控、发布、值班、容量标定都要多一份）。因为异地多活把同一份数据放在两个地域，所以它能把机房级故障变成可用性事件，代价是把强一致换成最终一致、并引入跨境判断：跨境副本本身构成跨境传输，在某些法域下不可行。因为削平不改数据形态、只改处理方式，所以它是三者里唯一**不需要数据迁移**的分摊手段，代价是把「实时结果」换成「已受理」，并要求幂等与去重同时到位——否则削平会把重复请求的放大效果从入口搬到后台。

**公开证据**：【公开】单元化的路由与资源切分口径（`CellID = Hash(UID) mod N_Cells`、`每 Cell 容量 = 总容量 / Cell 数`、`故障 Cell 占比 = 1 / N_Cells`）见 [Ch12 §01 单元化架构](../01-cell-based-architecture/01-cell-based-architecture.md) §2.2；【公开】GDPR 对向第三国传输设有条件限制（Regulation (EU) 2016/679 第 44–46 条，条号与版本以法规原文为准）——这使异地多活在多法域下不只是技术选择；[§ 6](03-large-event-readiness-section-6-sec6.md) 的字节脉冲型备战给出了「静态化 + 边缘承载 + 异步受理 + 幂等」这组削平手段的落地形态【公开】（[字节技术博客, 2019-2024]）。

**失效条件**：当业务本身以全局聚合为主（跨用户排行榜、全局库存、跨 Cell 事务）时，单元化的分摊收益被跨单元调用的成本抵消；当峰值是全局同时到达且上升时间为秒级时，「按地域分摊」只是把同一时刻的压力在多个区同时复制一遍，此时削平比分摊有效；当没有幂等与去重能力时，「异步受理」会把压力从入口搬到后台并可能造成重复发放——削平的前提是幂等，而不是相反。

#### 7.3.3 超过承载时丢什么：限流、熔断、降级作用在三个不同对象上

**机制是什么**：三者分别作用在请求、调用链、功能面上，因此不可互相替代；保护系统与保护核心业务也不是同一件事。

**它在各候选中的实现差异**：

| 手段 | 作用对象 | 生效条件 | 付出的代价 |
| --- | --- | --- | --- |
| 限流 | 请求（丢弃或排队） | 到达速率超过阈值（令牌桶 / 漏桶 / 滑动窗口） | 被丢弃的是真实用户的请求 |
| 熔断 | 调用链（断开对下游的调用） | 下游错误率或慢调用比例越过阈值；状态机 CLOSED → OPEN → HALF_OPEN | 需要设计半开探测与自动恢复 |
| 降级 | 功能面（关闭非核心功能） | 资源指标越线（CPU、连接池水位）或人工开关 | 用户体验受损；必须可逆且演练过 |
| 流量调度 | 流量去向（路由到其他池 / 单元） | 池子容量不均或局部故障 | 需要路由层与数据就近能力 |

```text
三个手段保护的是三个不同的东西（缺一个就留下缺口）
  限流：减少"进入系统的流量"        → 保护系统本身不被打挂
  降级：减少"系统要做的工作"        → 把资源让给核心链路
  熔断：减少"等待的时间"            → 保护调用方不被慢下游拖死
  ────────────────────────────────────────────────
  只限流不降级 → 核心链路仍与非核心抢同一份资源
  只降级不限流 → 慢请求仍占满连接与线程
  只熔断不降级 → 调用链断了，但被让出的资源没人接
```

**由此必然导出的性质**：因为限流丢的是请求、降级关的是功能、熔断断的是调用，所以三者的组合顺序决定了事故形态：先降级后限流，用户会先看到「功能变少」再看到「请求被拒」；反过来先限流后降级，用户会先看到「请求被拒」而功能其实还能关掉一部分——前者体验更好、后者保护更强，这个选择必须在备战阶段就定下来，而不是当晚。因为降级必须「可逆且演练过」才有效，所以开关的数量本身就是风险：没有 owner、没有文档、没有演练的开关，在关键时刻既不敢按也不敢不按，按错一次造成的损失可能大于峰值本身。

**公开证据**：【公开】限流算法（令牌桶 / 漏桶 / 滑动窗口）与熔断状态机（CLOSED / OPEN / HALF_OPEN 与半开探测）见主文件 [§ 2.2](03-large-event-readiness.md) §2.2；【公开】Sentinel 与 Hystrix 作为限流熔断的代表实现、Resilience4j 作为现代化替代品，见主文件 §2.3（某个具体版本是否提供某项能力，以该项目官方文档的当前版本为准，读者可自行核验）。限流阈值与熔断错误率窗口没有通用最优值，必须在压测中标定【经验】。

**失效条件**：当限流按整站统一阈值设定（不区分核心 / 非核心）时，它可能先杀掉关键链路的流量，而把非核心功能留在系统里——「保护系统」反转为「放大损失」；当降级被用来掩盖容量不足（长期靠在降级状态下跑）时，它从应急手段变成默认形态，团队会失去对真实承载力的判断，下一次峰会直接撞在未经降级的链路上。

#### 7.3.4 不确定性的处置顺序：发现 / 验证 / 止血

**机制是什么**：压测、演练、回滚分别对应「发现瓶颈」「验证恢复路径」「缩短故障暴露时长」三件事，它们的价值取决于发生在哪个时刻。

**它在各候选中的实现差异**：

| 手段 | 解决哪一类不确定性 | 什么时候做 | 前置条件 |
| --- | --- | --- | --- |
| 全链路压测 | 真实链路能扛多少 | 提前 1–2 个月【经验】（要留出改造窗口） | 生产环境 + 影子标识 + 数据隔离 |
| 混沌工程 / GameDay | 失效时的恢复路径是否真的可用 | 大促前，多轮 | 可注入的故障点 + 强可观测性 |
| 灰度与回滚 | 变更有问题时多久能止住 | 每次变更 | 配置开关、流量染色、可回滚的变更设计 |
| 值班与作战室 | 组织能否在几分钟内做出决策 | 常态化，规则事前定义 | 升级路径、不可逆操作的双人确认 |

```text
"发现问题的时间点"决定你能做什么（不是决定你多努力）
  提前 2 个月发现瓶颈 → 还有时间改架构、改代码、改容量模型
  提前 1 周发现      → 只能调阈值、加资源、准备降级
  当晚发现           → 只能按预案止血，且预案没演练过基本不可用
  ────────────────────────────────────────────────
  所以备战流程的设计目标不是"把准备做全"，
  而是"把发现问题的时点尽可能前移"
```

**由此必然导出的性质**：因为压测只有在生产环境用真实数据与真实依赖做，才能让环境差异归零，所以它必须同时解决流量隔离问题（影子标识 + 影子表），代价是压测自身成为一条需要长期维护的工程链路——把它放回测试环境做，等于把「压测通过」变成对另一套系统的结论。因为回滚能力决定的是故障暴露时长而不是故障概率，所以它是变更的**前置条件**而不是应急手段：一个不可回滚的变更，其风险等于它的影响面；把「是否可回滚」写进发布门禁，比事后补一套回滚脚本便宜得多。

**公开证据**：【公开】阿里双 11 备战把全链路压测安排在系统改造之后、大促之前约两个月，使发现的问题仍留有修复窗口（[阿里双 11 技术公开材料, 2019-2024]，见 [§ 6](03-large-event-readiness-section-6-sec6.md) 该案例）；【公开】「压测在生产环境做、用影子标识隔离」这一形态同见该案例与主文件 [§ 2.3](03-large-event-readiness.md) §2.3。

**失效条件**：当发现问题的时点已经晚于可改造窗口时，压测的结论只能用于加资源与收紧限流——它仍有价值，但已不能改变架构；反过来，若压测流量隔离不干净，一次压测就可能污染真实数据或干扰真实流量，此时压测从验证手段变成事故源，这也是「削平与隔离要先于压测落地」的原因。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 常备容量(常备倍数 × 常备时长)
     + 弹性容量(峰值增量 × 生效窗口)
     + 架构形态的常驻组件(每 Cell / 每 Region 一套)
     + 演练与压测的组织投入
     + 协同成本（值班、作战室、跨部门）
```

| 方案家族 | 主导项 | 隐性成本 | 成本随什么增长 |
| --- | --- | --- | --- |
| 容量规划 | 人力 + 提前扩容的机时 | 预测偏差同时造成过配与欠配 | 提前量与规模，弱相关 |
| 弹性扩容 | 峰值窗口内的按量资源 | 冷启动与预热（镜像、模型、连接池） | 峰值窗口时长 |
| 单元化 | 每 Cell 一套常驻（DB + Cache + MQ） | 跨单元聚合查询；运维面 ×N | **Cell 数，线性** |
| 异地多活 | 至少双份资源 | 最终一致性、冲突解决、合规判断 | **Region 数，线性** |
| 削平（静态化 / 边缘 / 异步） | 改造工程量（一次性） | 幂等与去重的维护；用户看到「已受理」 | 弱相关，一次建成后边际成本低 |
| 全链路压测 / 混沌工程 | 工具与人的固定投入 | 隔离链路维护、误注入风险 | **几乎不随业务量增长** |
| 灰度与回滚 | 开关与流量染色的建设成本 | 开关债务（无人清理的开关） | 弱相关 |
| 作战室与值班 | 集中兵力的人力（事件期） | 跨部门协调成本 | 事件次数与规模 |

**一个【推算】示例**（前提写全，读者可换成自己的数）：设日常峰值需要 N 台；大促峰值是日常的 M 倍；峰值每月共持续 t 小时。

- 按峰值常备：机时 = M·N × 730 小时/月（730 小时/月按 24 × 365 ÷ 12 折算）【推算】。
- 常态常备 + 峰值期弹性：机时 = N × 730 + (M−1)·N·t。
- **纯浪费比例 = (M−1)/M × (730−t)/730**，代入几种典型形状【推算】：

| 形状 | M（峰值倍数） | t（每月峰值时长） | 按峰值常备的浪费比例【推算】 |
| --- | :---: | :---: | :---: |
| 年度大促 | 10 | 0.5 小时（30 分钟） | **约 90%**（0.9 × 729.5/730） |
| 日级高峰 | 10 | 100 小时（每天约 3.3 小时） | **约 78%**（0.9 × 630/730） |
| 日级高峰、倍数减半 | 5 | 100 小时 | **约 69%**（0.8 × 630/730） |
| 日级高峰、倍数再降 | 3 | 100 小时 | **约 58%**（0.667 × 630/730） |
| 短促高峰、倍数较低 | 3 | 0.5 小时 | **约 67%**（0.667 × 729.5/730） |
| 峰值占满整月 | 10 | 730 小时 | **0%**（此时常备不再浪费，弹性只剩单价差） |

- 结论：**浪费比例同时取决于 M 与 t**——M 越大、t 越短，按峰值常备越浪费；在 M ∈ [3, 10]、t ≲ 100 小时/月的形状里它落在 **58%–90%**；t 取 200 小时/月时降到 48%（M=3）– 65%（M=10），再往上则随 t 单调继续下降，到 t = 730 小时/月时为 0%【推算】。所以「弹性的收益」不能只看倍数：同为 10 倍峰值，t=0.5 小时与 t=100 小时差 12 个百分点；而当 t 接近 730 时，继续买弹性只是把固定成本换成更高的单价。
- 再看「提前拉起」的代价：若把容量在峰值前 30 分钟拉起（预热），弹性窗口从 0.5 小时变成 1 小时，月机时从 734.5N 变成 739N（`730N + 9N × 1`），**增量不到 1%**【推算】——所以「提前拉起 + 预热」在很多场景比「压着峰值点扩」更划算，因为它用不到 1% 的机时换掉了冷启动风险。
- 若把峰值分摊到 2 个 Region（异地多活），机器总量并不因此下降（仍是按峰值准备，只是分别放在两处），增加的是一份**固定的**常驻组件（数据库集群、缓存、消息、值守）与一致性成本【经验】。

**怎么判断你的主导项**：两边都换算成机时再比——左边是峰值驱动的**弹性增量** `(M−1)·N·t`（按峰值窗口计价的机时/月），右边是改架构形态新增的**固定常驻** `F`（每 Cell / 每 Region 一套常驻组件与跨池聚合路径，折成机时/月）。**前者小于后者时，改架构形态在成本账上是亏的**——它买到的是爆炸半径与合规能力，不是省钱（异地多活尤其如此：副本是双份而不是分摊）。把 F 折成日常基线一月机时的比例 φ（`F = φ·N·730`），平衡条件 `(M−1)·N·t = F` 就给出**平衡倍数 `M* = 1 + 730φ / t`**。这条比较不需要新工具，只需要已有的容量台账与月度峰值记录。

```text
两条曲线什么时候交叉（决定"要不要改架构形态"）
  机时/月
    ▲
    │  架构形态族：每 Cell / 每 Region 一套常驻组件
    │  ─────────────────────────────────────  水平线 F（与峰值倍数无关）
    │                     ●  交叉点 M*
    │                ╱
    │  峰值驱动的弹性增量 ╱  (M−1) · N · t，随峰值倍数 M 线性上行
    │              ╱
    │           ╱
    └──────────────────────────────────────────► 峰值倍数 M
  交叉点左侧（M < M*）：弹性增量机时低于 F
      → 改架构形态在成本账上是纯支出
  交叉点右侧（M ≥ M*）：弹性增量机时超过 F
      → 为形态付固定成本在成本账上开始成立；是否真回本仍要与它买到的
        可用性、合规收益一起看（异地多活的副本是双份，不是分摊）
  ────────────────────────────────────────────────
  两边同为机时，可直接比大小：M* = 1 + 730φ / t（φ = F ÷ 日常基线
  一月机时）。横轴上的 M 是自变量，决定交叉点位置的是 t 与 φ：
  φ 取 0.3 时，t = 100 小时/月 时 M* ≈ 3.2，t = 0.5 小时 时
  M* ≈ 439【推算】 —— 也就是说"为每月一次的 30 分钟峰值
  去改架构形态"在成本账上几乎不可能成立，此时该用的是提前拉起
  与削平（7.3.1）：用不到 1% 的机时增量换掉冷启动风险
```

### 7.5 决策树（每个分支都要有阈值依据）

```
T1  你的峰值时点能否在数小时前锁定？
    ├── 能（双 11 / 618 / 春运 / 黑五）
    │   ├── T2  把峰值驱动的弹性增量折成机时 (M−1)·N·t，与改架构形态的
    │   │       固定增量 F 相比 —— 平衡倍数 M* = 1 + 730φ / t
    │   │       （φ = F ÷ 日常基线一月机时，t = 每月峰值总时长）
    │   │       参考档：φ ≈ 0.3 时，t ≈ 100 小时/月 → M* ≈ 3；
    │   │                t ≈ 25 小时/月 → M* ≈ 10
    │   │   ├── T3  M < M* → 容量规划 + 弹性扩容 + 分级限流降级
    │   │   │                （峰值只持续几十分钟时，用提前拉起代替实时弹性）
    │   │   ├── T4  M* ≤ M < 2M* → 上述 + 全链路压测 + 预案逐条演练 + 灰度回滚
    │   │   └── T5  M ≥ 2M* → 上述 + 单元化（按用户切）和 / 或异地多活（按地域切）
    └── 不能（没有可提前锁定的峰值事件）
        ├── T6  峰值以「持续增长」为主、没有可识别的脉冲
        │       → 容量规划（按趋势外推）+ 灰度发布
        ├── T7  有脉冲，且上升时间 < 弹性生效时间（口播类脉冲 / 爆款 / 明星直播）
        │       → 削平：静态化 + 边缘承载 + 异步受理 + 幂等去重
        └── T8  有脉冲，且上升时间 > 弹性生效时间
                → 可切换容量池 + 一键扩容 / 切流，演练到「几分钟内完成」
T9  是否存在「数据不得出境 / 不得跨区汇聚」的法域约束？
    ├── 有 → 在该法域内做单元化；不跨该法域做异地多活
    └── 无 → 异地多活可作为可用性与峰值分摊手段
T10 是否存在资金 / 账务级不可逆链路？
    ├── 有 → 该链路列入「不降级」清单；变更与不可逆操作双人确认 + 双活账本实时对账
    └── 无 → 按「影响资金 > 影响体验 > 非核心」统一分级降级
```

**阈值依据**（与树上的 T1–T10 一一对应）：

- **T1**：依据 7.3.1——预测式与切换式是两套互不替代的投入（一个买「提前量」、一个买「切换速度」），而它们的前提条件正是「时点是否可锁定」；同一条判据见 [§ 6](03-large-event-readiness-section-6-sec6.md) 字节脉冲型备战案例中「准备可切换的容量池而非预测峰值时点」的做法。
- **T2（平衡倍数 `M* = 1 + 730φ / t`）**：依据 7.4 的成本函数——「要不要改架构形态」的成本账就是「峰值驱动的弹性增量机时 `(M−1)·N·t`」与「形态新增的固定常驻机时 `F`」相比；把 F 折成日常基线一月机时的比例 φ（`F = φ·N·730`），解 `(M−1)·N·t = F` 即得。**t 在分母上**，这就是 7.4 图注那句「决定交叉点位置的是 t 与 φ」的算式化：同样的倍数，峰值持续越短，平衡点越高。φ 的取值取决于拆几个池子、每池常驻组件有多少；只拆 2–4 个池子的方案，φ 通常落在 0.2–0.5 量级【经验】（每池的元组件开销远小于该池承载的业务机时，但要按你自己的容量台账折算）。
- **T3（M < M*）**：依据 T2 的式子——φ ≈ 0.3、t ≈ 100 小时/月时 M* ≈ 3；φ ≈ 0.3、t ≈ 25 小时/月时 M* ≈ 10，所以 3 与 10 不是通用常数，而是同一平衡点在两种峰值形状下的取值。主文件 [§ 2.2](03-large-event-readiness.md) 的资源估算公式（`所需 Pod 数 = 峰值 QPS / 单 Pod 承载力 × (1 + 安全冗余%)`）是把 M 换算成 N 的桥：它本身是线性的、与倍数无关，所以它回答的是「增量有多少台」，而不是「阈值在哪」——阈值只能来自把增量折成机时后与固定成本比。峰值只持续几十分钟时，实时弹性来不及，用提前拉起代替（7.4 的推算显示提前拉起带来的增量不到 1%）。
- **T4（M* ≤ M < 2M*）**：上界的 2 倍来自 7.7 的不可逆性——改架构形态要按用户重分片或跨区双写，是一次性、不可逆的大投入，所以只在峰值驱动的增量机时达到固定成本两倍以上时才值得付，一倍余量是【经验】口径（φ 与 t 两个参数都是估计值）。本档还要看 7.4 的推算表：按峰值常备的浪费比例随 M 与 t 一起变——t ≈ 100 小时/月时 M=3 约 58%、M=5 约 69%、M=10 约 78%，t=0.5 小时时 M=3 约 67%、M=10 约 90%【推算】，所以「增量必须交给弹性与削平承担」在整档成立；把全链路压测放在这一档，是因为它正是把 φ 与 t 这两个估计值测成实测值的手段（7.3.4）——在可能回本也可能不回本的区间里，约两个月的前置改造窗口比不可逆迁移便宜（[§ 6](03-large-event-readiness-section-6-sec6.md) 阿里案例的 6 个月备战节奏【公开】，[阿里双 11 技术公开材料, 2019-2024]）。
- **T5（M ≥ 2M*）**：依据 7.4——倍数越过两倍平衡点后，成本账不再是唯一判据：`(M−1)·N·t` 超过 `F` 只说明「为形态付的固定机时」在数量级上能被峰值增量覆盖，而弹性与削平买不到的恰恰是另外两样——**单池 / 单机房的承载上限**（峰值规模超出单池可扩的上限时，加钱也加不出容量）与**爆炸半径 = 全站**。到这一步才轮到单元化（把峰值落到 1/N 个池子）与异地多活（把整区故障降为可用性事件）；这两种形态的代价是固定机时 F 与运维面乘 N，其中异地多活的副本是双份而非分摊，成本账上通常更贵（7.4 最后一条）【经验】。
- **T6（持续增长、无脉冲）**：依据 7.4 的成本函数——这类业务在式子里没有 `(M−1)·N·t` 这一项（t 是事件峰值的每月时长，稳态增长下无从定义），主导项回到表里「容量规划」的人力与提前量，以及「灰度与回滚」的开关与流量染色建设成本；灰度发布在这里承担的是把变更风险按流量比例摊开，而不是分摊峰值，所以它与 T7 的削平、T8 的切换并不互斥。该分支对应原 § 7.2 决策树里「否（无已知峰值事件）→ 持续增长 → 容量规划 + 灰度发布」这条落点，本章保留它。
- **T7（上升时间 < 生效时间）**：依据 7.3.1 的机制——响应式扩容要经过指标观测窗口、决策与冷启动三段，量级在分钟到十分钟【经验】；与 T6 的区别在于这里确有脉冲，只是它来得比扩容快。[§ 6](03-large-event-readiness-section-6-sec6.md) 的脉冲类案例（由节目口播触发、十秒级到达峰值【公开】，[字节技术博客, 2019-2024]，见 [§ 6](03-large-event-readiness-section-6-sec6.md) 该案例）落在这个范围之外，因此削平与切换比扩容有效。
- **T8（上升时间 > 生效时间）**：依据 7.3.1 与 7.4——上升时间略长于生效时间时，把容量提前常备在预热好的池子里并演练切换动作，比继续提高预测精度更有效；7.4 显示提前 30 分钟拉起带来的成本增量不到 1%【推算】，而它换掉的是「切过去也起不来」这一类失败。
- **T9**：依据 7.3.2——异地多活的副本本身构成跨境传输，GDPR 对向第三国传输设有条件限制【公开】（Regulation (EU) 2016/679 第 44–46 条）；因此这个分支由合规约束决定，而不是由性能决定。
- **T10**：依据 [§ 6](03-large-event-readiness-section-6-sec6.md) 的跨部门作战室案例——资金链路需要比「分级降级」更强的约束（不降级 + 双人确认 + 实时对账），因为一次资金差错的代价与一次慢请求不在同一量级；同理，不可逆操作（批量变更、清理）必须双人确认。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 已知峰值、M < M*（φ=0.3、t ≈ 100 小时/月时约 3 倍）、单机房 | 容量规划 + 弹性扩容 + 分级限流降级 | 单元化 | 不选单元化：峰值驱动的弹性增量机时低于形态的固定机时 F，跨单元一致性与运维面 ×N 是纯支出 |
| 已知峰值、M ≥ 2M*（φ=0.3、t ≈ 100 小时/月时约 6 倍以上） | 单元化（按用户切）+ 生产环境全链路压测 | 异地多活 | 不选先上异地多活：跨区最终一致与合规成本要先付，而单区内分摊还没解决 |
| 时点不可预测、秒级脉冲 | 削平（静态化 + 边缘 + 异步 + 幂等去重） | 可切换容量池 | 不选纯预测：秒级上升时间下，扩容的响应永远慢一步 |
| 突发型流量（爆款、明星直播） | 响应式扩容 + 限流 + 流量调度 | 提前常备 | 不选常备：窗口未知，常备成本按天累计 |
| 无峰值事件、流量持续增长 | 容量规划（按趋势外推）+ 灰度发布 | 弹性扩容 | 不选弹性：没有阶跃要追，主导矛盾是负载曲线逐季上移，而不是某一小时的倍数 |
| 全球化、跨地域业务 | 异地多活 + 全局负载均衡 + 单元化 | 单地域多可用区 | 不选单地域：跨区故障无法隔离，一次地域故障即全站不可用 |
| AI 推理服务 | GPU 弹性 + Prompt 缓存 + 模型降级链路 | 按峰值常备 GPU | 不选常备：GPU 的常备成本与稀缺性都是全栈最高的一类 |
| 智能体链路 | 工具级限流 + 单工具熔断 + 链路降级 | 整链路统一限流 | 不选统一限流：一个慢工具会拖垮整条链，而统一阈值分不清是哪个工具 |
| 内部系统（ERP / CRM） | 限流 + 降级（不扩容） | 弹性扩容 | 不选扩容：流量有限，扩容只增加常驻成本 |

**常见组合（职责边界与运维代价）**：

1. **容量规划 + 弹性扩容 + 限流降级（最小可用组合）**：容量规划给基线水位，弹性扩容负责增量窗口，限流降级负责兜底。职责边界是「预测给数、弹性给量、限流给底线」。运维代价是三处阈值必须标定一致——否则会出现「弹性还没起来、限流先把真实流量杀了」这种最难定位的组合故障；三处阈值应来自同一次压测。
2. **单元化 + 跨单元聚合层**：Cell 自包含处理本单元读写，跨单元查询（如「全部订单」）走一个很薄的聚合层。边界是「单用户内的一致归 Cell、跨用户聚合归聚合层」。代价是聚合层成为新的单点与瓶颈，必须能降级（降级为只查本单元，结果不完整但可用），且每增加一个 Cell 都要同步容量与路由。
3. **全链路压测 + 混沌工程 + 灰度回滚（验证与止血三件套）**：压测证明承载力、演练证明恢复路径、回滚控制暴露时长。三者共享同一套生产环境隔离链路与故障注入点，因此常一起建。代价是必须有人常驻维护演练脚本、开关台账与隔离链路；缺了这三样，工具在第二次使用时就不准了。
4. **作战室 + 值班 + 事前决策规则（组织层组合）**：把协同本身当成被设计的系统——统一指挥席、按指标关注面分工、破线即降级、不可逆操作双人确认。代价是常态化的低效（值班占人）与跨部门协调成本，只有年度级事件才摊得平；对普通业务线不适用。

组合的运维代价可以归到一句：**每增加一种形态，就多一份「同一件事在两处是否还对得上」的校验**（阈值是否一致、路由是否覆盖、Cell 与 Region 的容量台账是否与之同步），对不上之处就是当晚最难定位的故障源头。

### 7.7 选错的代价与迁移成本

**反模式：靠加机器硬扛** —— 症状：峰值前按倍数堆资源，不做削平、不做链路分级降级 → 后果：7.4 的推算显示按峰值常备时浪费的机时可达九成（M=10、峰值只持续 30 分钟的形状；M=3、t ≈ 100 小时/月时也有约 58%）【推算】；更严重的是加资源存在硬上限（机房容量、带宽、GPU 供给），超过后继续加钱的边际收益为零 → 正确做法：先算「只为峰值存在的机时占比」，用弹性与削平承担增量，把常备水位的倍数压到最低。

**反模式：只做单链路压测** —— 症状：压测覆盖每个服务自身，不覆盖「入口 → 缓存 → DB → MQ」的真实依赖链 → 后果：单服务全部达标，真实峰值下缓存击穿、连接池打满、消息堆积这类链式故障照样发生，而它们在单链路压测里根本看不见 → 正确做法：在生产环境做全链路压测并做影子隔离，把「上下游联动」当作验收对象，而不是把「每个服务单独达标」当作达标。

**反模式：把降级开关当应急手段** —— 症状：开关上百个、没有 owner 与文档、降级优先级当晚才讨论 → 后果：关键时刻没人敢按，或按错开关造成比峰值更大的损失；7.3.3 说明降级只有在「可逆且演练过」时才成立 → 正确做法：开关有 owner 与台账、定期演练、按「影响资金 > 影响体验 > 非核心」事前分级，并给不可逆操作加双人确认。

**反模式：把弹性扩容当成万能** —— 症状：认为上了 HPA 就能扛任意峰值，包括有状态服务与 GPU 推理 → 后果：秒级脉冲下扩容慢一步（7.3.1），而有状态服务与推理服务的扩容受数据重平衡与模型冷启动约束，扩容动作本身可能引发新的故障 → 正确做法：把链路分成「可弹性的无状态层」与「不可弹性的有状态 / GPU 层」，后者用缓存、削平、提前预热与模型降级处理，不指望它按指标伸缩。

**换成另一个要动什么**：

| 迁移方向 | 数据与容量 | 路由与改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 加资源硬扛 → 弹性 + 削平 | 无 | 页面静态化、受理改异步、补幂等键 | 弹性策略、预热流程、隔离链路 | 容量与降级阈值标定 | 中 |
| 单机房 → 单元化 | **按用户重分片（一次性、不可逆）** | 引入 `Hash(UID) mod N` 路由；跨单元查询改走聚合层 | 每 Cell 一套 DB / Cache / MQ，运维面 ×N | 单元化发布与按 Cell 灰度 | 大 |
| 单地域 → 异地多活 | 历史数据同步 + 双写 | 就近路由 + 冲突解决策略 | 双 Region 常驻、切换演练与数据校验 | 多活一致性模型 | 很大，且跨境场景可能直接不可行 |
| 无演练 → 演练常态化 | 无 | 补故障注入点与开关台账 | 演练环境与观测能力 | GameDay 组织方式 | 中（需人力常驻） |
| 事后复盘 → 事前决策规则 | 无 | 降级分级表与升级路径 | 作战室与值班机制 | 跨部门协同 | 中，但依赖组织授权 |

- 上表量级为【经验】：迁移成本集中在两处——「数据重分片」（不可逆，需要一次性迁移窗口）与「运维面乘 N」（每多一个 Cell 或 Region，监控、发布、值班、容量标定的复杂度都上一个台阶），后者在立项时最常被低估。
- 一条边界：**单元化与异地多活的迁移不可逆**（数据已按新维度分片、副本已跨区写入），因此分片键与地域数应当在决策记录里当作长期承诺写下来，而不是当作可调的参数。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 峰值可提前锁定、M < M*（t ≈ 100 小时/月时约 3 倍） | 容量规划 + 弹性扩容 + 分级限流降级 | 峰值驱动的弹性增量机时低于形态的固定机时（每 Cell / Region 一套），改形态是纯支出 |
| 峰值可提前锁定、M ≥ 2M*（t ≈ 100 小时/月时约 6 倍以上） | 单元化 + 生产环境压测 + 预案逐条演练 | 按峰值常备的浪费比例可达九成【推算】（7.4 表），且单池承载上限与爆炸半径只能靠分摊解决 |
| 时点不可预测、秒级脉冲 | 削平（静态化 + 边缘 + 异步 + 幂等） | 扩容的响应速度追不上上升时间，预测精度提高也无用 |
| 突发型流量、无提前量 | 响应式扩容 + 限流 + 流量调度 | 没有可预测的时点，能提高的只有响应速度 |
| 跨地域业务 | 异地多活（先过合规判断）+ 全局负载均衡 | 副本即跨境传输；一致性降级是分摊能力的代价 |
| 含资金 / 账务链路 | 该链路不降级 + 双人确认 + 实时对账 | 一次资金差错的代价与一次慢请求不在同一量级 |
| AI 推理 / 智能体服务 | GPU 弹性 + 缓存 + 模型降级 + 工具级限流 | GPU-bound 与链式调用使「按指标扩容」这一套失效 |
| 从没演练过 | 先做演练与事前决策规则 | 峰值是集中兵力的场景；没练过的动作当晚大概率不能用 |

> 本节小结：这一主题下真正起决定作用的差异只有一条——**峰值相对于你的准备窗口是否可控**（时点能不能提前锁定、上升时间是否长于扩容生效时间）。它决定你买的是「更准的预测」还是「更快的切换」，也决定容量是常备还是弹性；单元化、异地多活、削平与限流降级都在这条差异之下派生。
