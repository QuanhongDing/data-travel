## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

混沌工程和别处不一样的地方是：**它的"前沿"里混了两件性质完全不同的事**——「把 AI 链路当成新的故障域」（要注入的对象变了）与「用 AI 来选故障、判异常」（做实验的手段变了）。趋势清单把这两件事并列成"AI 时代的混沌工程"，于是读者分不清"AI 链路的混沌"到底是"我该多注入一类故障"还是"我该换个更聪明的工具来选故障"。前者要动的是**稳态的定义面与判据**（§5.2.1-5.2.3），后者只动**候选产出的方式**（§5.2.4）——两者的投入与产出完全不同。

本主题的时间刻度问题比别处更尖锐。主文件 [§1.2](06-chaos-engineering.md) 的痛点里，第 4 条写的是「**演练成本高：手动故障演练需要协调多个团队，难以持续**」，第 6 条写的是「**AI 链路的新脆弱点：Agent 工具调用失败、LLM API 超时、GPU 资源耗尽**」。注意这两条的差别：前者是**成本问题**（靠自动化解决，与 AI 无关），后者是**覆盖面问题**（AI 链路成了新故障域，需要新的注入类型与新的观察量）。把"用 AI 选故障"当成对这两条的回答，会同时漏掉它们——**成本问题靠声明式实验与门禁解决，覆盖面问题靠稳态定义与判据解决**。

本节还有一处结构性的困难：**混沌工程的产出是"发现的问题数与改进项"，属企业内部数据**，公开材料最多到"我们做了这件事"，很少到"因此某类故障的发现率从多少变到多少、口径是什么"。所以本表的第②条（第三方非厂商公开生产案例）在本主题里是最难凑的一栏，且这一点会**系统性地压低全表的级别**，不因方向本身的优劣而改变。

本节用 L1 / L2 / L3 三级区分，判据必须是可核验的三条：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条各挡住一类误判：①挡住"把路线图当既成事实"，②挡住"把工具作者与采纳方自述当行业现状"，③挡住"把一次演练当工程能力"。**三条全中才算 L1**，可以排进路线图；只满足一部分、或只有厂商自有案例的算 **L2**，可做 PoC、不要作为核心依赖；只有路线图 / 论文 / 演示的算 **L3**，记录即可、不要在架构里预留假设。"感觉成熟"不算判据——它在演练复盘会上无法被复核。

**判据声明（本节不对 L1 判据做任何修正）**：上文那三级与三条判据沿用到底，不替换、不放宽。本主题有一处特别诱人放宽的地方，先把话说死：**"我们自己在生产里跑过"不是第②条**——第②条要的是**别人**能核验的材料。于是**下表没有任何一行达到 L1**——包括那几行"非 AI 的既有故障注入能力"，它们满足 ① 与 ③（有正式产品文档、注入接口多年未变），卡住的都是 ②。这是本表最重要的一句话：**它说明的不是"这些能力不成熟"，而是"公开证据到不了 L1"**；也正因如此，本主题的行动顺序**不能由级别决定，只能由"你能不能自己造证据"决定**（§5.4）。

写这一节时最容易混的五件事，先在这里分开：

- **产品名 vs 能力名**：**ChaosBlade** 与 **AWS Fault Injection Service** 是**工具产品名**（**Chaos Mesh / LitmusChaos / Gremlin** 出现在主文件 [§1.4](06-chaos-engineering.md) 的演进历程与 [§4.3 工具链与平台](06-chaos-engineering-section-4-sec4.md) 的选型里），对应的能力名是主文件 [§2.3](06-chaos-engineering.md) 第 1 条那六类故障（进程级 / 网络级 / 资源级 / 应用级 / 数据级 / AI 特定）。凡看到"某工具支持某类故障"，先问它在官方故障类型清单里是**正式动作**还是社区脚本。
- **已发布版本 vs 路线图**：判断某工具是否真的支持某类注入，只看一处——**项目官方文档里的故障类型清单**；新闻报道、厂商公告、生态伙伴的转述都不算（§5.4 给了核验入口）。
- **有工具 ≠ 有实验**：混沌实验由四要素构成（稳态假设 / 故障注入 / 观察对比 / 学习改进，主文件 [§1.1](06-chaos-engineering.md)）。只写"注入了什么"而没有稳态与中止条件的，是**制造故障**，不是混沌工程——本节给级别的对象是"实验能力"，不是"注入能力"。
- **自动回滚 vs AI 判断回滚**：前者是时间 / 指标触发的**确定性动作**（主文件 [§2.3](06-chaos-engineering.md) 第 6 条），属既有成熟能力；后者是"由模型判断该不该回滚"，属 L3。两者混同会让"自愈"听起来比实际成熟（§5.5 第 2 条）。
- **论文里的原型 vs 产品里的实现**：本方向大量提法（故障推荐、异常检测、自动 RCA）在论文与开源原型里都能找到，但**开箱可用是另一回事**。判定方法：看官方文档里该能力有没有"配置项 / 配额 / 计费"三项中的至少两项。

| --- | :---: | --- | --- |

**这三级怎么用**：本主题的行动顺序**不由级别决定**，而由一条更实用的判据决定——**这次实验的判据（稳态 + 中止 + 结论口径）今天能不能写出来**。写得出来（第 1-4 行、第 12 行），今天就能做；写不出来（第 5-11 行、第 13-14 行），先补判据，否则实验会稳定地给出"通过"这个既正确又无用的结论。**顺序反过来做，就是在一套连"稳态包含哪些指标"都没定义的链路上，先引入一个会给故障排序的分析层**。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，在复盘时应被直接打回——本主题里每一次"注入更聪明的故障"，都对应一处新的判定盲区。

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 推理服务 | 容量单位从"实例数 × QPS"换成"显存预算 ÷ 每请求 KV 占用"，故障因此沿竞争而非沿实例传播 | **故障传播路径**（稳态的定义面被扩宽） |
| §5.2.2 智能体链路 | 失败的位置从"调用边界"移到"控制流"：错误不再是 5xx，而是依据变了 | **失败形态**（可归因性丢失） |
| §5.2.3 向量检索与 RAG | 故障的后果从"可用性下降"移到"正确性下降"，且不报错 | **判据的位置**（从在线指标换到离线评分） |
| §5.2.4 AI 辅助决策与自动化混沌 | 选故障从人工经验排序换成数据排序；中止从人工换成规则 | **判断依据**（实验的执行方式没变） |

读法建议（三条，按可执行性排序）：

- 只读一节的话读 **§5.2.1**——它给出了本主题唯一一条"稳态必须扩到哪些指标"的具体清单（队列、显存、长度分布），也是唯一一条能直接推出"为什么传统实验会假通过"的方向。另外三条的共同前提都是"先把观察面补上"：记不出归因、拿不出评分、看不见中止，实验结论都只能是"没崩"。
- **§5.2.2** 与 **§5.2.3** 排第二、第三：它们各自的核心动作（步级记录、离线评分集）本身就是收益的一半，且这两样东西在没有混沌工程时也是该有的。
- **§5.2.4** 放最后：它的收益是"覆盖变得可度量"，而覆盖度量靠规则报表就能做掉一半，AI 那半到不了 L1。

每条末尾的「证据与来源」采用同一套档位：【公开】指有可核验的出处（论文 / 官方文档 / 公开材料），【推算】指能写出推导链的换算，【经验】指区间估计。**本节不给版本号**：凡涉及"某工具支持某特性"的地方，一律改写成判定入口。

#### 5.2.1 AI 推理服务：稳态里缺了显存与队列，实验就会给出假的「通过」

- **旧做法与它的卡点**：既有故障库是为**无状态服务**设计的——kill 进程、网络延迟、磁盘满、CPU 打满（主文件 [§2.3](06-chaos-engineering.md) 第 1 条前三类）。它们对推理服务**信噪比很差**：kill 掉一个推理 Pod，流量被负载均衡转到其余实例，稳态指标（错误率、P99）几乎不动——实验"通过"了，但它什么都没验证。卡点不在故障类型不够多，而在**故障的传播路径与你的观察量不在同一条线上**：真正脆弱的是显存预算与排队，而你观察的是实例存活与错误率（主文件 [§2.1](06-chaos-engineering.md) 把稳态举例为"错误率、P99 延迟、吞吐量"——**这三项恰好都是可用性指标，覆盖不到队列、显存、步级归因与答案依据**）。
- **AI 改变了什么机制**：**容量的计量单位变了，故障的传播方式随之改变**。推理服务的容量不是"实例数 × 每实例 QPS"，而是"每实例的显存预算 ÷ 每请求的 KV 占用"（同章 [05 性能工程 §5.2.1](../05-performance-engineering/05-performance-engineering-section-5-ai.md) 已把容量单位写成显存预算与序列长度分布）。于是同一个"注入一个副本故障"的动作，在传统服务里是**容量减少 1/N**，在推理服务里可能因为剩余实例装不下被转移过来的长上下文请求而**级联**——事故不是发生在被注入的那个实例上，而是发生在**接收流量的那些实例**上。

| 注入什么 | 传统稳态能否发现 | 必须补的观察量 | 补不上的后果 |
| --- | --- | --- | --- |
| 一个推理实例失效 | 往往不能 | 队列长度、剩余实例的显存占用 | 实验给出假的"通过" |
| 限流 / 超时 | 部分能 | 请求排队时长、被拒请求的业务影响面 | 只看到错误率，看不到长上下文请求被优先牺牲 |
| 模型冷启动 | 能（延迟跳变） | 冷启动窗口内的显存峰值与排队 | 误判为"可接受的延迟尖峰" |
| 显存压力（受控占用） | 不能 | 显存占用曲线与拐点位置 | 无法定位级联从哪一档并发开始 |
| 上下文长度异常（远超分布） | 不能 | 输入长度分位（P99 / P999） | 生产里真实存在的"长尾请求杀死实例"看不见 |

- **由此得到的**：因为**容量以显存为单位、故障沿竞争传播**，所以传统实验必须被扩成"**显存竞争实验**"才有意义：用受控的显存占用、并发限制、或刻意拉长的上下文把剩余实例推到拐点（拐点的推算见 [05 性能工程 §5.2.1](../05-performance-engineering/05-performance-engineering-section-5-ai.md)，那里给出的结构结论是"上下文长度翻倍则最优批上限减半"【推算，推导链即该节的 B\* ≈ W /(L × k)】）。**由此可直接推出两件事**：其一，稳态指标必须从"错误率 + P99"扩成"错误率 + TTFT / TPOT 分位 + 队列长度 + 显存占用"；其二，**"注入后系统通过"这个结论在推理链路上没有信息量**——你必须能区分"扛住了"与"流量被转到别处而你没在看"。
- **由此付出的**：**其一，爆炸半径与硬件预算直接冲突**——"最小化爆炸半径"是主文件 [§1.1](06-chaos-engineering.md) 的第五条原则，而真实 GPU 实验需要独占资源，两者在成本上对立。**其二，显存压力实验会污染同卡租户**，多租户集群上基本不可做，于是这类实验只能落在独占集群或预生产环境，而预生产的请求长度分布与生产不同 → **结论的可移植性再次打折**。**其三，队列与显存是内部指标**，把它们接进稳态与中止条件要先改监控——这笔改造成本落在平台侧，且它比注入动作本身贵。**其四，冷启动与限流的正确行为是业务相关的**（拒绝 / 排队 / 降级到小模型），没有通用稳态；实验只能告诉你"当前策略在这条链路下的表现"，不会告诉你"哪个策略对"。
- **证据与来源**：主文件 [§2.3](06-chaos-engineering.md) 第 1 条已把"AI 特定：LLM API 失败、Agent 工具超时、GPU OOM、向量检索失败"列为故障类型；各工具是否**正式**提供 GPU / 显存类动作，以项目官方故障类型清单为准（§5.4）。**【本节未能核到】"GPU / 显存类故障注入在生产环境常态化运行"的第三方（非厂商）可核验材料**。
- **成熟度**：**L2**，但第 5、6 两行的判据不同，不能合并成一句（§5.1 表第 5、6 行）：**第 5 行（限流 / LLM API 失败 / 超时 / 冷启动）**：①③成立——网关 / 代理层的限流与失败注入、LLM API 提供方文档化的限流与超时错误码都是正式条目（核验入口见 §5.4），**②核不到**；**第 6 行（GPU OOM / 显存压力）**：①待核——需在**工具官方故障类型清单**里逐项核验 GPU / 显存类动作是否为正式功能（同 §5.1 表第 6 行），③不成立——各工具的动作语义不统一，**②核不到**。两行停在 L2 的共同原因是②核不到，且稳态口径无通行做法。
- **判定方法**：为一次显存压力实验写下三样东西——**稳态指标（含队列与显存）、中止条件、结论口径**。三样写不出，这次实验的产出只有"系统没崩"这一句，而它在推理链路上是默认结果。第二问：注入后系统通过了，是因为**扛住了**，还是因为**你没在看接收流量的那些实例**？
- **什么时候值得做**：推理链路已是核心依赖、且常年以高并发批处理形态服务时。**什么时候不值得做**：低 QPS、单请求长对话的服务——批处理几乎不发生，显存竞争不是主要失效形态，先做限流与超时的边界验证更划算。

#### 5.2.2 智能体链路：失败形态是「静默偏离」，不是 5xx

- **旧做法与它的卡点**：传统链路的错误处理是"重试 + 熔断 + 降级"，它有三个隐含假设：**调用幂等、失败显式、重试代价可控**。Agent 链路三条都不成立——工具调用可能有副作用（写操作）、失败可能是"成功但返回了错的东西"、重试会把 token 成本按步数乘上去。于是卡点变成：**注入故障之后，无法判定"系统扛住了"还是"模型绕过去了"**；而 Agent 总会产出点什么，所以"有输出"不是判据。
- **AI 改变了什么机制**：**失败的位置从"调用边界"移到了"控制流"**。一次工具超时之后，模型可能改写问题、换一个工具、或按不完整的信息继续作答——最终给出的答案**看起来正常，但依据不同**。机制上是"**错误的可归因性丢失**"：出错的不是某一次调用，而是"这次回答是基于哪些工具结果得出的"这条链。

```text
同一个"工具超时"，两种完全不同的失败（判据必须区分它们）
  控制流层面（真正要观察的）              调用层面（传统稳态只看得到这一层）
  ───────────────────────────────────   ─────────────────────────────────
  步 1  调用订单工具   → 超时            HTTP 5xx / 超时计数 +1
  步 2  模型改写问题 / 换工具 / 放弃检索   无任何指标变化
  步 3  按残缺依据作答 → 输出流畅、无报错   错误率不变、延迟甚至更短
  ──────────────────────────────────────────────────────────────────
  结论：可用性指标全绿（"通过"），但答案的依据已经换过一次
  判据必须补两样：① 步级记录（可归因）② 答案与依据的一致性校验
  另：死循环的判据是"步数 / 成本上限被触发"，不是"抛异常"
```

- **由此得到的**：因为**故障后果落在归因链上而不是调用返回值上**，所以 Agent 链路做混沌的第一件事不是注入，而是**步级记录**（每一步调用了什么工具、参数是什么、返回什么、模型据此做了什么决定）。没有它，实验结论只能是"没崩"——而"没崩"在 Agent 上是默认结果。**由此还能推出第二条判据**：**"死循环"不是错误状态，而是成本无界状态**——它的判据是"步数或成本上限被触发"，而不是"抛出了异常"；所以把它归进"应用级故障注入"（主文件 §2.3 第 1 条）会让人以为它会以错误的形式出现，它不会。
- **由此付出的**：**其一，步级记录本身有成本**——记录要落存储与链路、有时要额外调用（判定依据一致性的那一层），这笔开销落在每次请求上。**其二，止损手段会误伤正常的长任务**：步数上限与成本上限定得紧，复杂问题被截断；定得松，死循环的损失上限就是那个松值——**上限的位置是业务决策，不是技术参数**。**其三，降级行为没有通用答案**：API Key 失效、限流、工具不可用时，拒答 / 降级到缓存答案 / 转人工三种选择的正确性取决于业务，所以"实验通过"这件事本身要相对某个策略来定义。**其四，注入工具失败会污染同期评测**：被注入故障的会话不能用于质量评估，实验数据与评测数据必须分开留。
- **证据与来源**：主文件 [§2.3](06-chaos-engineering.md) 第 7 条已把"AI 智能体韧性：测试 Agent 在 LLM API 失败时的降级能力"列为一类方向，并在 [§3.5](06-chaos-engineering-section-3-sec3.md) 反模式 6 写"忽视 AI 链路"的风险；**公开可核验的第三方生产案例本节未能给出**。"字节 ChaosAgent"以该项目的公开材料为准，本节不复述其能力与年份。
- **成熟度**：**L2**——注入手段可用（在工具层或网关层制造失败与超时），但**判据（步级归因 + 依据一致性）无通行做法**，且第②条核不到（§5.1 表第 7 行）。
- **判定方法**：随机取三条历史会话，回答"这次回答用了哪些工具结果、哪一步开始偏了"。**答不出来就先补归因，不要做混沌**——在没有归因的链路上注入故障，等于在一场不记分的比赛里练习。
- **什么时候值得做**：Agent 已接到有副作用的工具（下单、退款、改配置）、或单次会话成本已经可观测时。**什么时候不值得做**：工具都是只读且会话很短时——失败会被重试吸收，注入的收益主要是"确认了重试有效"，性价比低。

#### 5.2.3 向量检索与 RAG：降级不报错，判据必须换成离线评分

- **旧做法与它的卡点**：RAG 的降级路径在架构图上看得很清楚（检索失败 → 不带检索直接答、Rerank 失败 → 只用向量相似度、索引不可用 → 回退到关键词检索）。卡点是**降级后的质量损失不可观测**：检索挂了以后系统不报错、延迟甚至更短、答案看起来仍然流畅，错的只是"依据"。于是传统判据（错误率 / 延迟 / 可用性）会给出**完全通过**——这也是本节开头那句"通过没有信息量"在本主题里最典型的形态。
- **AI 改变了什么机制**：**故障的后果从"可用性"移到了"正确性"**。把检索从链路里拿掉，人为观察到的差异不是"系统不可用"，而是"答案的依据从检索到的资料换成了模型参数里的记忆"。这条链路可拆成五段（Embedding / 向量检索 / Rerank / LLM / Prompt），每段的故障类型不同，但**它们的共同点是：故障不可从可用性指标上看出**。机制上这是"**判据的位置从在线指标换到了离线评分**"。

| 组件 | 注入什么 | 传统指标看得出来吗 | 真正要看的量 |
| --- | --- | --- | --- |
| Embedding | 服务失败 / 慢响应 | 慢能看出，失败在有缓存时看不出 | 评分集命中率（检索退化为关键词后的差） |
| 向量检索 | 索引不可用 / 返回空 / 返回错 | 空结果可能被当成"没有相关资料" | 引用是否支撑答案；注入错结果最难发现 |
| Rerank | 失败 / 超时 | 几乎看不出 | 排序变化（Top-K 的相关性） |
| LLM | 失败 / 限流 / 超时 | 能看出 | 降级答案与正常答案的评分差 |
| Prompt | 提示词注入 | 看不出（它不是基础设施故障） | 拒答率 / 越权指令被执行的比例（属安全测试） |

- **由此得到的**：因为**故障不表现为错误码**，所以 RAG 混沌的前提是先有一份**离线评分集**（同一组问题 + 同一套评分规则），注入前后的评分差就是"降级的代价"。**这反过来给出一个有用的结论：RAG 混沌的产物不是"系统更稳了"，而是"你知道降级会掉多少分"**——后者才是能用来做架构决策（该不该保留关键词回退、该不该给检索加冗余）的数。同理，它把"降级路径"从一个写死在代码里的兜底，变成一个有代价标签的策略选择。
- **由此付出的**：**其一，评分集要维护**（文档更新、问题分布漂移都要跟进），且它与线上真实质量有偏差——离线问题通常是"好问题"，线上长尾更脏。**其二，"索引失效"的注入方式本身有语义问题**：删除索引、清空集合、返回空结果、**返回错结果（注入噪声）** 是四种不同的故障，前三种常见、第四种才危险，而它最像"正常"（系统照常给答案，依据是错的）。**其三，Prompt 注入不是基础设施故障，而是输入分布的变化**：把它和故障注入并列，会让人以为它有稳态可定义——它没有通用稳态，只有"拒答 / 降级 / 拦截"这类策略选择（§5.1 表第 9 行判 L3）。**其四，回退路径本身可能引入新的正确性风险**：关键词回退在长文档场景下的召回分布与向量检索不同，用户看到的答案风格变了而系统毫无异常。
- **证据与来源**：**无公开可核验的第三方（非厂商）生产材料**——本节能核到的是 RAG 链路组件本身的正式能力条目（各向量库与推理引擎的官方文档，§5.4），以及数据质量侧关于质量维度的度量与质量规则的既有做法（[11-cross-cutting/01](../../11-cross-cutting/01-data-quality/01-data-quality.md)）。本节那张表是自撰的实验设计，不是外部证据。
- **成熟度**：**L2**（组件的注入手段可用，②核不到、判据无通行做法）；Prompt 注入那一行是 **L3**——两者在本节是**两个子项**，级别与 §5.1 表第 8、9 行一致。
- **判定方法**：先问一句"注入之后我拿什么数判它通过或失败"。**答案里没有离线评分或引用校验的，这次实验的结论只能是"系统没崩"**。第二问：把检索结果整体换成"看起来相关但错误"的内容，你的系统会不会察觉？——**不会察觉的那部分，才是 RAG 真正的盲区**。
- **什么时候值得做**：RAG 已承担对外可感知的问答、且已有可复用的评测问题时。**什么时候不值得做**：还没有评测集时——此时的优先级是先把评测集建起来（它同时是质量工程的必需品），而不是先做混沌。

#### 5.2.4 AI 辅助混沌决策与自动化混沌：排序解决不了覆盖，自愈会吸收故障信号

- **旧做法与它的卡点**：故障库扩张的速度远快于选择能力。随机注入（Chaos Monkey 风格，主文件 [§1.4](06-chaos-engineering.md) 的起点）在故障类型少时有效；类型一多、代价差异一大，随机就是浪费。人工按经验挑则不可复现。卡点还有一层：混沌实验的成本不只是环境，还有**误伤带来的信任成本**——一次伤害到别人的演练，会让下一次演练的审批难上很多。
- **AI 改变了什么机制**：**选故障的依据从人工经验换成历史数据**（故障推荐 / 异常检测 / 自动 RCA）。注意这只是**排序依据**的变化；而"实验声明化、进 CI、自动中止"这一半与 AI 无关——它是**声明式实验 + 门禁 + 确定性回滚**的既有工程实践（主文件 [§2.3](06-chaos-engineering.md) 第 3、6 条）。把两者混成一件事，会让"AI 主导混沌"听起来比实际成熟得多（§5.5 第 1、2 条）。
- **由此得到的**：因为**选故障的依据变成了数据**，所以覆盖第一次变得**可度量**——"哪些故障类型从未注入过""哪些注入过但从未产生过判定（既没发现问题也没证明稳定）"这两个数可以直接算出来，混沌从"定期演练"变成"**可度量的覆盖工程**"。这是真实收益，而且它的一半靠规则化的覆盖报表就能做到，不需要模型：**先有覆盖表，再谈排序**。
- **由此付出的**：**其一，统计排序会自我强化**——总挑历史上"有效果"的故障，会让一次都没触发过的类型永远排不进实验，而那些恰恰是"未知未知"；方向与混沌工程的目的（暴露未知脆弱点）相反。**其二，自动中止 / 自动回滚会吸收故障信号**——系统被救回来了，实验日志里留下的是"通过"（这与性能侧"自动扩容吸收性能回归"是同一类失败）。除非实验产物能区分"扛住"与"被救回"，否则**自愈越强，你能看见的脆弱点越少**。**其三，进 CI 会带来实验疲劳**：每次都跑、每次都没问题，实验退化成打勾（[§3.5](06-chaos-engineering-section-3-sec3.md) 反模式 5「为了混沌而混沌」的自动化版本）。**其四，自动 RCA 的结论是因果断言，而可观测数据里相关性遍地**——它的产物是候选清单，必须能落成可证伪的预测（与性能侧 AI 辅助分析同一条约束）。
- **证据与来源**：【公开】声明式实验、自动中止、故障类型清单都是各工具的正式能力条目（核验入口见 §5.4）。**【本节未能核到】"AI 推荐故障提升了有效发现率或覆盖率"的第三方（非厂商）公开材料**。
- **成熟度**：**自动化那半 L2（非 AI 工程实践）**——①③成立、②核不到；**AI 决策那半 L3**——只有演示与自研（§5.1 表第 3、4、10、11 行）。
- **判定方法**：画一张"故障类型 × 是否注入过 × 是否有结论"的矩阵，数一次**从未注入过的类型有几类**。这个数不降，说明你的瓶颈在覆盖而不在排序——**此时引入 AI 推荐只会让已知故障被选中得更频繁**。第二问：上一次实验"通过"时，中止条件是否被触发过？
- **什么时候值得做**：故障类型清单已经长到人工挑不动、且已有覆盖表时（先做覆盖表，成本极低）。**什么时候不值得做**：故障类型还不到十几种、或稳态与中止条件都没定的时候——此时该做的是把前三条做好，不是换一个更聪明的选故障方式。

### 5.3 与本主题既有栈的接口在哪

混沌工程与 AI 之间不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比"AI 能注入什么"更能决定它能不能落地。**「现状」列只写接口契约本身的状态（既有机制 / 未定），不写 L1 / L2 / L3**——它描述接口，不是演进方向。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 混沌 ↔ 可观测（[11-cross-cutting/04](../../11-cross-cutting/04-observability/04-observability.md)） | 交接物 = 稳态指标集 + **步级归因记录**（Agent 每步工具调用与结果） | 可观测侧；缺归因时实验结论只能是"没崩"（§5.2.2） | 既有机制 / 字段未定 |
| 混沌 ↔ 灰度与回滚（[§09](../09-gray-and-rollback/09-gray-and-rollback.md)） | 交接物 = **中止条件**（时间 / 指标 / 手动）与"是否触发过中止"的记录 | 实验执行方；不记录"被救回"时，自愈会吸收故障信号（§5.2.4） | 既有机制（中止）/ 区分口径未定 |
| 混沌 ↔ 容灾（[§07](../07-disaster-recovery/07-disaster-recovery.md)） | 交接物 = 演练与注入的分工：真切换验证 vs 模拟故障验证 | 容灾侧；用注入替代真切换会低估切换时长与数据丢失 | 既有机制 |
| 混沌 ↔ 单元化（[§01](../01-cell-based-architecture/01-cell-based-architecture.md)） | 交接物 = **爆炸半径的物理边界**：单元化决定 r 的上限，而不是流量比例决定 | 单元化侧；没有单元化时，r 只能靠流量比例硬控（r = 故障实例数 / 总实例数，见主文件 [§2.2](06-chaos-engineering.md)；单元化降低爆炸半径见主文件 [§1.3](06-chaos-engineering.md)） | 既有机制 |
| 混沌 ↔ 数据质量（[11-cross-cutting/01](../../11-cross-cutting/01-data-quality/01-data-quality.md)） | 交接物 = RAG / Agent 的**离线评分集与评分规则** | 质量侧；没有它，RAG 混沌只能判"系统没崩"（§5.2.3） | 未定 |
| 混沌 ↔ 成本（[11-cross-cutting/03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)） | 交接物 = GPU 实验的**成本归属**（独占集群跑实验算谁的账） | 平台与财务的接缝处；没有归属约定时，AI 链路演练永远排在既有演练之后 | 归属约定未定 |
| 混沌 ↔ LLM 网关 / 代理 | 交接物 = **注入点**（网关层注入 vs 应用内注入） | 网关侧；注入点在应用内时每次实验都要改代码，自动化就断了 | 既有机制 / 注入点未定 |

一句话概括：**AI 没有改变混沌工程的方法，只改变了故障域与候选产出方式**。由此得到四条约定。

**第一条约定：稳态指标必须覆盖"新增的失效面"。** AI 链路要给稳态补三样东西——**队列与显存**（推理服务，§5.2.1）、**步级归因**（Agent，§5.2.2）、**离线评分**（RAG，§5.2.3）。只补一样都不够：只用可用性指标，三条链路都会给出"通过"。

**第二条约定：实验产物必须区分三种结果——扛住 / 被救回 / 出问题。** 只写"通过 / 失败"的模板，会让自动中止与自动回滚把脆弱点藏起来（§5.2.4）。可执行的做法：在实验记录里加一列"中止条件是否触发"，并要求结论里写明触发时系统本会怎样。

**第三条约定：把覆盖写进实验记录，而不是只写结果。** 每次实验后更新"故障类型 × 是否注入过 × 是否有结论"的矩阵。**没有这张矩阵，讨论"要不要上 AI 选故障"是无从判断的**——因为瓶颈可能在覆盖，而覆盖与排序无关。

**第四条约定：Prompt 注入归安全测试，不归韧性演练。** 它不是基础设施故障，而是输入分布的变化，没有可定义的稳态（§5.2.3）。混在一起做，会让两边都失去判据：韧性演练拿不到稳态，安全测试拿不到攻击面口径。

**这四条约定与主文件那条约束的关系**：主文件 [§2.1](06-chaos-engineering.md) 只要求"先定义稳态"，没有规定稳态包含哪些指标；AI 链路把这件事变成硬约束——**指标选错，实验结论会从"发现问题"变成"确认无事"**，而这种结论在评审上无法与真正的稳定区分开。

### 5.4 公开进展与文献

分三类列，**其中文献与生产案例两类只列能给出标题 / 出处 + 年份的条目**；release note / 官方文档一类是判定入口，给核验标准而不给年份，理由见该类开头。**宁少勿假**。

**文献（可核验：论文 / 专著 / 官方原则文档）**

- 【公开】Basiri 等，*Chaos Engineering*，IEEE Software（**2016**）——把 Netflix 的实践写成学科文献的一篇；主文件 [§1.1](06-chaos-engineering.md) 的五条原则与之一脉相承。
- 【公开】Gunawi 等，*Fail-Slow at Scale: Evidence of Hardware Performance Faults in Large Production Systems*，FAST（**2018**）——"慢故障"在生产系统中真实存在且比崩溃更难发现；这是"注入慢故障与性能退化"这类实验的可核验经验依据，也是主文件 [§2.3](06-chaos-engineering.md) 第 2 条"渐进式实验"的现实理由。
- 【公开】Rosenthal & Jones，*Chaos Engineering: System Resiliency in Practice*（O'Reilly，**2020**）——稳态假设、爆炸半径、GameDay 这些术语的成书化整理。
- 【公开】Netflix 的 *Chaos Engineering Principles*（**2014 年起公开、持续维护**）——主文件 [§1.1](06-chaos-engineering.md) 已按此列出五条原则；"在生产跑、自动持续、最小化爆炸半径"三条要求的出处。
- **三条学术条目（ML 系统的混沌工程、AI 链路的韧性设计、因果推断在混沌分析中的应用；分别标注 NeurIPS 2024 / USENIX ATC 2024 / KDD 2024）本节均无法核验**；判定方法：按论文标题在对应会议的论文集页面检索。**三条所指的方向都保留**（推理链路混沌 → §5.2.1；AI 链路的判据 → §5.2.3；因果与自动 RCA → §5.2.4），但**不作为证据使用**。
- 面向大模型训练 / 推理集群的故障特征与容错研究，本节无法给出具体条目；可按「大模型训练集群故障特征数据中心」这类关键词自行检索核验——它是 §5.2.1 里"推理链路的失效形态"最可能的公开证据来源。

**官方文档 / release note（判定入口）**

**这一类不给年份，只给核验标准**：故障类型清单与文档是持续更新的，某条能力对应哪一年取决于你查的那一版，写死年份反而会先于能力本身过期。核验标准只有一句——**以官方文档当前版本为准**，在故障类型清单里看到该动作是**正式条目**（而不是路线图 / 社区脚本），即算核验通过。

- 开源注入项目的**官方故障类型清单**——核验"进程 / 网络 / 资源 / 应用 / 数据 / AI 类"动作分别在不在清单里，尤其 GPU / 显存类动作；**判定方法：看项目仓库与官方文档的故障模型清单，而不是看新闻稿与生态伙伴的转述**。
- Chaos Mesh 与 LitmusChaos 的官方文档——核验 K8s 原生注入类型（Pod / 网络 / 压力 / DNS / HTTP）各自是正式能力还是实验特性；两者均由 CNCF 托管，**具体成熟度阶段以 CNCF 官网项目页为准**（本节不对"已毕业 / 已孵化"这类断言作事实使用）。
- 云厂商托管故障注入服务的官方文档——核验可用动作、配额、"实验模板与演练编排"是否为正式功能；**本节不对其动作集合作集合断言**。
- 商业混沌平台的官方文档——同上；判定方法：看该能力有没有"配额 + 计费 + SLA"三项中的至少两项。
- 各 LLM API 提供方的**官方状态页与速率限制文档**——核验限流与超时的错误码与响应头。**这是"注入限流与超时"能做得像真的前提**：不知道对方返回的到底是限流错误还是服务端错误，注入的就不是同一种失败，实验结论也不可移植。
- 各推理引擎 / 向量库的官方文档——核验是否提供运行时可用的开关（关闭索引、限制并发、清空缓存、模拟冷启动）；**判定方法：有运行时开关或配置项，注入就能自动化；没有，就只能退到网关层模拟**。

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含口径的第三方"AI 链路混沌"生产案例。能核到的是：各工具项目的公开材料（工具作者与采纳方自述）、本书 [§6](06-chaos-engineering-section-6-sec6.md) 整理的四个案例（Netflix Chaos Monkey、阿里 ChaosBlade、字节混沌平台化、美团演练矩阵）——**那是本书自撰的汇总估计，口径与样本由本书给出，不构成第②条要求的第三方（非厂商）公开生产案例**。**这个空白本身是结论**：它正是本节把整张表压在 L2 / L3 的直接原因。
- **本主题的"材料"其实很好造，因为实验自己就是证据。** 判定一份自造证据合不合格，看它有没有写全五项：**稳态指标**（含哪个分位，以及 §5.3 要求的队列 / 步级 / 评分中适用的那一样）、**爆炸半径**（比例 + 绝对量）、**持续时间与中止条件**、**注入方式**（工具、命令或配置）、**结论与改进项**（发现了什么、改了什么、覆盖矩阵更新了哪一格）。缺一项就只是"演练过一次"。
- **五步自造证据法**（一次演练内可完成）：① 选一条 AI 链路，**先不要选最核心的那条**；② 写下稳态（必须含队列 / 步级 / 评分中适用的那一样）；③ 选一个最小爆炸半径与明确的中止条件；④ 注入 → 观察 → 按"扛住 / 被救回 / 出问题"三分类记录；⑤ 把结论转成改进项，并回填覆盖矩阵。
- 这一类里**最容易造假的是工具方案例**：它们通常省略口径（稳态是什么、中止条件是什么）与规模（多少条链路、什么流量占比）。判定方法：只接受同时给出"注入方式 + 稳态口径"的案例；缺一项就只当方向记录。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **既有注入能力**：数一次故障类型清单里有多少类**从未注入过**。
2. **推理服务**：翻一次注入记录，问"当时队列与显存有没有被观察"。
3. **Agent 链路**：抽三条历史会话，问"这次回答依据了哪些工具结果"。
4. **RAG**：问"检索整体失效时，你拿什么数判降级可接受"。
5. **自动化**：翻实验模板，看有没有"中止条件是否触发"这一列。
6. **跨域**：问一次"跨 Region 切换的真实耗时是多少"，看这个数是演练得来的还是估算的。

**怎么用这份清单**：要核"能力存不存在"看官方故障类型清单（最快）；要核"机制成不成立"看论文（最慢但最稳）；要核"在我这里值不值得做"只能自己跑一次并留好五项记录——**第三类问题没有任何公开材料能替你回答，本主题尤甚，因为混沌的产出是企业内部数据**。

### 5.5 被过度宣传的部分

**「AI 自动选出最高价值的故障」**——实际是：它把"按人工经验排序"换成"按历史数据排序"，而历史数据只包含**曾经注入过**的故障，于是它系统性地收敛到已知故障。

- **为什么会这样**：排序是在已有集合内做的，覆盖问题不在排序层——你缺的是"从没注入过的那些类型"，而它们恰恰不在数据里。
- **它什么时候才会成真**：工具能同时给出"从未注入过的故障类型清单"（覆盖缺口），而不只是"下次注哪个"。
- **判定方法**：数一次你的覆盖矩阵里从未注入过的类型有几类。**这个数不降，说明排序帮不上忙**——此时上 AI 推荐，只是让已知故障被选中得更频繁。

**「Self-Healing Chaos（自愈演练闭环）」**——实际是：成立的一半是**自动回滚**（时间 / 指标触发的确定性动作），未成立的是"由 AI 判断该不该回滚"；而自动回滚有一个副作用：**它吸收故障信号**。

- **为什么会这样**：自愈把两种性质完全不同的结果（系统扛住了 / 系统被救回来了）映射成同一个观测值"实验通过"。
- **它什么时候才会成真**：实验报告能分别给出"未触发自愈时的表现"与"触发自愈前后的对比"两段。
- **判定方法**：翻最近三次实验记录，看有没有"中止条件是否触发"这一列。**没有这一列时，自愈越强，你能看见的脆弱点越少。**

**「在数字孪生里做混沌，零风险」**——实际是：仿真能覆盖的只有**你建模了的那部分**；而混沌工程的价值恰恰来自真实系统里未建模的耦合（重试风暴、连接池耗尽、跨层背压、批处理内请求之间的相互影响）。

- **为什么会这样**：这是"用已知模型验证未知行为"，孪生的保真度无法自证——它永远不会告诉你它漏了什么。
- **它什么时候才会成真**：出现公开的"孪生预测 vs 真实注入结果"的对照精度指标，并且能按故障类型分解。
- **判定方法**：把上一次真实事故的链路丢进孪生，看它能不能复现。**不能复现的那部分，就是孪生的盲区。**

这三条的共性：**它们都把"实验跑得更顺 / 更安全"当成了"系统更韧"**。而混沌工程的判据只有三条：**稳态是否覆盖了真正的失效面、中止是否被记录、覆盖是否有缺口数据**。三条都没有因为 AI 而改变。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| AI 链路混沌的判据会从"可用性"扩到"质量代理指标（离线评分 + 步级归因）" | 实验模板里出现"评分集"与"步级记录"两个必填项 | 公开材料仍只报错误率与延迟，并把"通过"当作结论 |
| 混沌工具的下一个竞争点会是"覆盖缺口报告"，而不是"支持多少种故障" | 工具产物里出现覆盖矩阵 / 未注入清单 | 仍以"支持 N 种故障类型"为卖点，且没有任何覆盖口径 |
| 显存 / GPU 类故障注入会因成本与租户隔离，长期停在独占集群或预生产环境 | 公开做法集中在独占集群 / 预生产，并说明结构差异 | 出现"多租户生产集群上常规运行显存故障注入"的公开做法与安全设计 |
| 自动化与 AI 辅助会先以"默认配置 + 候选清单"落地，而"被救回 / 扛住"的区分与"可证伪预测"不会随之自动出现 | 出现把中止前后分开度量的实践或工具字段，且工具要求填"若结论成立，哪个指标会变、变多少" | 工具原生标注"是否触发中止"并把它计入实验结论；或工具直接输出根因结论、被直接采用而不回填验证 |

写这四条时的共同约定：**信号必须是外部可观察的**（文档条目、模板字段、公开做法），而不是"我觉得会"。**被检验得最快的是第四条**——它只需要在你的实验模板里加一列；**最慢的是第三条**，它取决于硬件成本与多租户隔离这两件与算法无关的事；**第二条最可能出现"半对半错"**：覆盖产物会出现在工具里（对），但"支持 N 种故障"作为卖点不会消失（错），所以这一条要按**工具产物里有没有覆盖矩阵**来判，而不是按话语是否消失来判。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 想给 AI 链路做第一次混沌 | 挑一条非核心链路，写下稳态（含队列 / 步级 / 评分中适用的一样）与中止条件 | 观察"扛住 / 被救回 / 出问题"三分类是否都在发生 | 不要在稳态只有错误率与 P99 时开始——它会稳定地"通过" |
| 只有传统系统的演练 | 先补 AI 链路的三样稳态指标，再选一条链路演练 | 观察覆盖矩阵里 AI 类故障是否从"从未注入"变成"有结论" | 不要把"注入了 LLM API 失败"当作已覆盖 Agent 链路——注入点不同，失败形态不同 |
| 推理服务按实例数规划容量 | 把容量与爆炸半径的单位换成"显存预算 + 长度分布" | 观察注入一个副本后，是否出现接收方实例的级联 | 不要在预生产用与生产不同的长度分布做显存实验，然后套用结论 |
| Agent 已接有副作用的工具 | 先补步级记录，再做工具失败 / 超时注入 | 观察"依据一致性"校验拦下多少条 | 不要在步级归因缺失时做 Agent 混沌——结论只能是"没崩" |
| RAG 已对外提供问答 | 先建离线评分集，再注入检索与 Rerank 故障 | 观察降级前后的评分差，把它写成策略标签 | 不要用"可用性没降"作为 RAG 降级可接受的证据 |
| 有人提议做 Prompt 注入演练 | 把它放进安全测试的范围，定拒答 / 拦截口径 | 观察拒答率与误拒率 | 不要把它与韧性演练混在一次实验里——它没有稳态 |
| 团队想引入"AI 选故障" | 先做覆盖矩阵：故障类型 × 是否注入过 × 是否有结论 | 观察"从未注入"的类型数是否下降 | 不要在覆盖有缺口时先做排序——它只会让已知故障被选中得更频繁 |
| 实验已自动化并带自动中止 | 在实验记录里加"中止条件是否触发"一列 | 观察"被救回"的比例及其长期趋势 | 不要把自动中止当作实验通过的理由——被救回是一种需要解释的结果 |
| 老板要求"把混沌工程 AI 化" | 把目标拆成"稳态补全 + 覆盖矩阵 + 三分类结论"三件事，分别给验收口径 | 观察三件事各自的负责人是否明确 | 不要签"AI 自动决策爆炸半径"式的目标——它没有可验收的失败定义 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改监控、改模板、动注入点、扩演练范围），**而收益依赖一个尚未成立的假设**（排序能覆盖未知 / 自愈不影响观察 / 仿真保真）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**故障域**——推理服务、Agent 链路、RAG 组件成为新的注入对象，而它们的共同特点是**故障后果落在"可用性之外"**：推理落在队列与显存，Agent 落在控制流与依据，RAG 落在正确性。因此真实收益全部来自同一处：**把稳态与判据扩到这些新面上**，而不是来自"更聪明的选故障方式"。它**没有**改变主文件 [§1.2](06-chaos-engineering.md) 那条更前置的约束：**演练成本高、难以持续**——这条要靠声明式实验与门禁解决，与模型无关。
>
> 判断本主题下任何新提法的快捷方式：**它动的是"稳态的定义面"，还是只改了"候选的产出方式"？** 前者今天就能做（本节判 L2 的那几行），后者要先证明它能给出覆盖缺口。第二条同样快的判断：**这次实验的判据是什么、中止有没有被记录、覆盖缺口有多少**——三条答不上来的方向，只能停在"记录"。
>
> 如果只能带走一句话：**先把稳态补到新失效面上，再让 AI 去挑故障**；顺序反过来，就是让一个只在历史故障里排序的分析层，替一套还没定义"什么叫正常"的系统做韧性判断。

> 💡 **思考锚点**：拿 §5.7「明确不要做」那一列扫一遍你现在的演练清单——你有没有在稳态还只有错误率与 P99 时就开过 AI 链路的混沌？再按覆盖矩阵（故障类型 × 是否注入过 × 是否有结论）填一次你的存量：那一格「从未注入」的类型，占整矩阵的几分之几？
