## 4. 工程实现

§3 把生产环境混沌、预生产环境混沌、GameDay、持续混沌、AI 辅助混沌、分层混沌、实验矩阵讲成了约束的产物，并给每个模式标了入场条件。§4 接着回答另一个问题：**入场条件怎么被造出来，以及造的先后顺序为什么不能换。**

本节 4.1–4.3 面向「护栏还没建、要从零把第一批实验跑起来」的团队；4.4 面向「已经有监控、告警、值班与一堆手工演练文档，要在存量上换轨」的团队——这两类读者的第一步不同，所以单独写。4.5 给可直接套用的模板，4.9 给能自己跑的检查动作。

### 4.1 落地步骤

**Step 1：基础准备（1–2 个月【经验】；随关键链路条数与现有监控完整度变化）**

1. 建可观测性：指标与告警、链路追踪、日志三者到齐，且指标能按「最小可观测单元」（1 个实例 / 1 个可用区 / 1 个分片 / 1 个租户）切分。
2. 定义稳态指标：把每条关键链路的稳态写成**指标 + 阈值 + 持续时间**三元组（错误率、P99 延迟、吞吐量、可用性）。
3. 选择混沌平台：按 §4.3 的判据选，不按知名度选；落选理由也要记下来。
4. 指定一名「实验负责人」，明确他有权在指标越界时中止别人的实验。

- **产物**：一张稳态看板（每条关键链路一行：指标 / 阈值 / 窗口 / 数据来源系统）；一份观测入口清单（谁能查指标、查链路、看日志，入口在哪）；一份平台选型记录（候选 × 判据 × 落选理由）。
- **判据**：随机抽 1 条关键链路，让没参与搭建的同学在 5 分钟内答出「它当前的错误率、P99，以及这两个数的数据源来自哪个系统」。答不出，说明稳态还没落到可查的地方，只是口头共识。
- **为什么必须这一步 / 为什么在这个位置**：稳态是全部实验的裁判，没有事先写死的三元组，实验结束后的结论只能靠争论。而且这一步的产物是后面三步的输入——Step 2 的 Runbook 判定标准、Step 3 的自动 Abort 阈值、Step 4 的 CI 门禁门槛，引用的都是这张看板上的数；先做后面三步，等于三次重新定义「正常」。

**Step 2：预生产环境试点（1–2 个月【经验】）**

1. 第一个实验选最小单元：kill 一个 Pod / 一个进程。注入命令按所选平台官方文档填写，例如 ChaosBlade 的 `blade create k8s pod-pod delete`、`blade create cpu fullload`、`blade create network delay`（动作名与参数以官方文档当前版本为准）。
2. 每个实验写一份 Runbook：步骤、观察点、判定标准、Abort 机制、由谁按下去。
3. 团队培训：让值班同学明确「谁发现、谁判定、谁决策回滚」三件事分别落在谁头上。

- **产物**：第一份实验记录（稳态假设、爆炸半径 = 1 个实例、持续时间、观察指标、结论）；Runbook 模板；培训后能独立跑通实验的名单。
- **判据**：让没参与第一次实验的同学照 Runbook 独立重跑一次，全程不需要口头补充、也不需要作者在旁边指点。做不到，说明 Runbook 依赖了当事人的记忆。
- **为什么必须这一步 / 为什么在这个位置**：预生产是唯一允许实验失败的地方，也是唯一能便宜地回答「那个机制到底存不存在」（超时、降级、主从切换是否真的会触发）的地方。它同时是 Step 3 的排练场：没有在预生产跑通过一份 Runbook 就上生产，abort 的实际响应时间会从设计值变成「发现 + 判定 + 决策」三段延迟之和。

**Step 3：生产环境推广（阶段 3，2–3 个月【经验】）**

1. 从非核心业务开始，再逐步推广到核心；首次生产实验把爆炸半径压到最小可观测单元（探索阶段 r < 5%，【经验】）。
2. 建立审批流程：写清多大范围、多长时间、涉及哪些核心资产时需要谁批。
3. 建立告警联动：**实验与告警联动，异常自动 Abort**——指标触发给尽早量、时间触发给时长上限、手动触发兜底，三类触发同时配置。

- **产物**：生产实验审批单（范围 / 时长 / abort 三触发 / 值班人）；爆炸半径台账（每次实验的 r 与命中实例数）；与告警系统打通的自动中止配置。
- **判据**：做一次「中止演练」——把 abort 阈值压到必然触发，确认系统真的在指标越界后自动停止注入并回滚，且值班在约定时间内收到通知。测不出「真的会停」，说明中止链路是纸面的。
- **为什么必须这一步 / 为什么在这个位置**：生产实验消耗的是真实可用性预算，审批与自动中止是这笔预算的保险，不能后补。顺序也不能倒：先验证「异常会自己停」，再谈从非核心扩到核心；先扩范围再补联动，扩出去的那部分范围没有任何保险。

**Step 4：常态化运营（持续）**

1. 持续集成：把实验集挂进 CI/CD，让实验结果与代码版本一一绑定（持续混沌）。
2. GameDay 演练：按季度到半年一次的节奏跑（§3.2.3 的【经验】区间），大促前追加；剧本、熔断条件、复盘机制三样齐备才算一次演练。
3. AI 辅助：用模型做故障推荐与异常识别——**建议权给模型，执行权留在人与自动 Abort 手里**。
4. 改进闭环：每次实验的发现必须转成可追踪的改进项，回归到 Runbook、容量或架构。

- **产物**：与拓扑版本绑定的实验集；实验记录归档；改进项看板（来源实验 / 负责团队 / 状态 / 回归版本）；覆盖矩阵（故障维度 × 业务域）。
- **判据**：打开上个季度的实验记录随机抽 3 条，每条都要能追到至少一条已关闭或有明确排期的改进项；再抽 1 条上季度发现的脆弱点，指出它在哪个版本被回归验证过。两条都答不出，说明这条流水线在产出记录，不是产出韧性。
- **为什么必须这一步 / 为什么在这个位置**：脆弱点是随代码、配置、依赖变更被重新引入的，一次性演练拦不住回归；而这一步的产物（实验集与覆盖矩阵）又是下一轮选题的输入——没有矩阵，选题只能靠印象，结果是同几条链路被反复演练，缺口长期无人认领。

**最常被跳过的是 Step 1 的三元组。** 多数团队从「先注入看看」开始，症状出现在 Step 3 的第一次生产实验结束之后：结论写不成「通过 / 未通过」，只能写成「抖动了一下，可能是实验引起的，也可能是正常波动」。此时回头补稳态，之前消耗掉的可用性预算换不回任何可行动的结论。

### 4.2 关键技术点

**ChaosBlade：把注入能力铺到多层多语言**

- **做法**：按「要验证哪个机制」选注入层——主机 / 资源层（CPU 满载 `blade create cpu fullload`、磁盘写满 `blade create disk fill`）、网络层（`blade create network delay`）、进程层（`blade create process kill`）、容器与编排层（Pod 终止 / 驱逐）、应用层（方法级延迟、抛异常、篡改返回值）。
- **机制**：因为同一故障场景可以在不同层用不同手段实现，所以「打哪一层」是一个可判定的选择：要让服务发现与自愈链路生效就用编排层，要验证依赖异常处理分支就用应用层方法级注入（「依赖返回了错误值」这类故障无法从外部模拟）。代价是覆盖层数越多，需要长期维护的注入实现越多——多语言、多运行时各一套，这笔投入通常由一个平台团队承担。
- **失效条件**：**当「注入命令跑通了」被当成「能力已覆盖」时，这条会坏**——命令跑通只说明注入器与被注入进程通了，不说明故障真的作用到了目标代码路径（版本不匹配、依赖被替换、进程已重启都会让它静默失效）。症状：实验记录显示注入成功，但同期指标没有可归因的变化。
- **档位**：命令形状与开源时间为【公开】（阿里 ChaosBlade 2019 年起开源，动作与参数以官方文档当前版本为准）；层与手段的取舍为【经验】。

**Chaos Mesh：K8s 上的声明式注入**

- **做法**：把实验写成自定义资源（PodChaos / NetworkChaos / StressChaos / DNSChaos 等）交给控制器收敛；网络分区显式写出方向与对端选择器，而不是只写一侧。
- **机制**：因为实验是声明对象而不是一次性脚本，所以它的期望状态可以被控制器持续维持、并在到期后自动回收；这也让实验能进版本库、进流水线。代价是爆炸半径的表达能力被选择器体系限制——`mode: all` 这类写法会把「最小可观测单元」直接放大成整组。
- **失效条件**：**当集群里没有稳定的标签体系时**（同一业务的实例标签不一致，或运维打的标签与业务口径不同），选择器会命中非预期对象；症状是实验记录里的命中实例数大于设计值，而这一点通常要等到实验后核对 r 时才会被发现。
- **档位**：【公开】（Chaos Mesh 为 CNCF 项目；可用资源类型按其官方文档的故障类型章节核验）；标签体系失配的后果为【经验】。

**LitmusChaos：实验与稳态探针绑定**

- **做法**：用 ChaosEngine 声明实验（目标命名空间 / 标签 / 工作负载类型，以及混沌持续时长、混沌间隔、是否强制等参数），并为实验挂稳态探针，探针失败即中止。
- **机制**：因为「实验是否该继续」由探针判定而不是由人盯屏判定，所以实验可以在无人值守的时段跑。代价是探针指标一旦与业务稳态脱钩（只探容器存活、不探端到端成功率），门禁就退化成形式。
- **失效条件**：**当持续时长与间隔按示例值照抄时**，故障的叠加形态会与设计不符——间隔短于恢复时间会形成连续故障，而不是单次抖动；症状是稳态在整个实验期间从未恢复，事后说不清是「扛不住」还是「根本没给恢复窗口」。
- **档位**：ChaosEngine 字段名与参数为【公开】（按 LitmusChaos 官方文档核验当前 schema）；参数取值为【经验】。

**Abort 三触发的可验证接线**

- **做法**：指标触发接告警规则（越界即停止注入并回滚）、时间触发接实验时长上限、手动触发接值班入口；三类都要在预生产上真实触发过一次。
- **机制**：因为时间触发只保证「不会无限期故障」、指标触发才保证「尽早停」、手动触发是无人值守时的兜底——三者职责不重叠，所以缺一个就有一条路径没有保护。代价是每条实验都要把稳态阈值翻译成一条告警规则，实验设计的固定成本上升。
- **失效条件**：**当只有手动触发时**，实际故障时长等于「异常被看见 + 有人判定 + 有人敢按下去」三段延迟之和（跨团队值班时通常以十分钟计，【经验】）；症状不是「停不下来」，而是「停得太晚」，而复盘时大家还会觉得发现得挺快。
- **档位**：【经验】。

**爆炸半径：按最小可观测单元选目标**

- **做法**：目标选择器写「1 个实例 / 1 个可用区 / 1 个分片 / 1 个租户」，把命中实例数与 r 写进实验记录第一行；放大按 5% → 10% → 20% 逐级走，每级先确认稳态恢复能力再加码（【经验】）。
- **机制**：因为实验的期望代价与 r 近似同阶，所以把 r 显式化等于把「这次实验最多伤到多少用户」变成可审批的量；写不出这个数，说明目标选择器还没有能力表达它。代价是对照组要求监控能按单元切分指标——很多团队的监控维度是在这一步才第一次被真正检验。
- **失效条件**：**当故障的传播路径跨单元时**（共享数据库、共享缓存、共享下游限流），小 r 不再等于小影响：一个分片上的慢查询可以拖垮共享存储，进而打满所有分片的连接池；症状是实验设计 r 很小，观测面上却是全链路告警。
- **档位**：r 的分档（探索 < 5%、验证 5–20%、极限 20–50%）为【经验】。

**注入器自身的故障域隔离**

- **做法**：注入通道与控制通道分开——混沌平台的控制器、节点上的注入进程、abort 依赖的告警链路，都不应与被测业务共用同一组会被注入打掉的路径；在预生产上先注入一次「打掉控制面」的故障，确认 abort 仍然可达。
- **机制**：因为 abort 本身是一次控制面操作，若控制面与被注入的故障域重叠，就会在最需要中止的时刻恰好中止不了；把这个前提显式验证一次，才能把「护栏在故障中仍然可用」从假设变成事实。代价是多出一套（至少逻辑隔离的）控制通道与一份额外的演练剧本。
- **失效条件**：**当注入粒度粗到影响 API Server 或节点网络时**（整节点网络分区、节点驱逐、控制面所在可用区故障），注入与中止会同时失效；症状是实验期间指标全面告警，而 abort 命令长时间无响应，最后靠人工重启告警链路才恢复。
- **档位**：【经验】。

### 4.3 工具链与平台

选型的第一判据不是「哪个工具最强大」，而是**这次要验证的假设落在哪一层**——层选错，工具再强也测不到你想测的东西。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 主机 / 进程层注入（含非 K8s 与多语言混布） | ChaosBlade（阿里开源，2019 年起）、Chaos Monkey（Netflix 开源，2011 年起） | 目标是物理机 / VM，或技术栈跨 Java、Go、Node.js、Python 且需要方法级注入 → ChaosBlade；假设只有「实例随机消失」一条且已有自愈编排 → Chaos Monkey 式的随机终止 | 用只认 K8s 对象的工具去覆盖物理机与中间件，非 K8s 部分长期成为「从未被注入过」的盲区 |
| K8s 声明式注入 | Chaos Mesh（CNCF）、LitmusChaos（CNCF） | 需要更细的网络 / IO / DNS 类故障资源 → Chaos Mesh；需要「实验自带稳态探针、探针失败即停」 → LitmusChaos | 把社区脚本里的动作当成平台的正式能力，实验不可复现，平台升级即断 |
| 托管式注入服务 | Gremlin（商业）、AWS Fault Injection Service、Azure Chaos Studio、GCP 相关注入能力 | 团队没有余力长期维护注入器与护栏，且愿意把爆炸半径的控制权交给托管方；再确认云资源类型覆盖是否落在自己的目标资源上（以云厂商官方文档当前版本为准） | 低估自建的人力——注入只是开始，长期成本在护栏维护与多环境适配，这部分通常要由一个平台团队承担 |
| 网络层故障代理 | Toxiproxy（Shopify 开源） | 只需要在单个连接或单个依赖之间制造延迟与断连，且不想为一次验证引入集群级依赖 | 代理成为新的单点：代理自己挂掉时，告警会把「代理故障」误判成「被测系统故障」 |
| 跨平台实验编排 | Chaostoolkit | 需要在异构环境里用同一份实验描述驱动多种注入手段，且实验要作为可版本化的资产维护 | 编排层统一的是「描述」而不是「能力」——底层覆盖不到的地方它一样注入不了，而统一的外观会给人「已覆盖」的错觉 |

表里**最容易被误选的是「按工具知名度选型」**：先选平台，再决定注入什么。典型后果是——选的工具只覆盖容器与编排层，于是每次实验都在验证同一个假设（实例消失无感），而「依赖返回错误值」这类异常处理分支从未被验证过；实验记录的数量很漂亮，实验矩阵里却始终缺那几格。

有一类候选这里只写类别、不写产品：**注入能力的托管程度**（自建注入器 / 托管服务 / 混合）。判断方法可以自行完成——把要注入的故障类型列出来，逐条去候选平台的官方文档「故障类型 / 动作」章节查有没有正式条目；只有社区脚本能做的，按未覆盖处理。

### 4.4 存量迁移

存量团队的现状通常是：已经有监控与告警（但指标没按可观测单元切分）、有一堆手工演练文档（但没人按它跑过）、有几个能切主从的脚本（但没人验证过它还能跑）。这套东西不需要推倒重来，需要的是排序。

**① 立刻见效且可回退的第一步。** 先不加任何注入：把现有告警规则里已经带阈值的那些抄进稳态看板（只读动作，零风险、随时可回退）。第二步仍然不加注入：在预生产上用现有脚本做一次「主从切换演练」——它验证的是存量预案本身是否还能跑，哪怕失败也只损失一次预生产窗口。这两步产出的看板与「预案可用性结论」，是后面所有实验的地基。

**② 历史资产按三类处理，不要一次性返工。**

| 类别 | 判定方式 | 处理方式 |
| --- | --- | --- |
| 已带阈值且能自动判定的告警规则 | 规则里写明了指标、阈值、窗口 | 登记进稳态看板，作为实验的裁判依据 |
| 手工演练文档与 Runbook | 抽 3 份，让没写过它的人照着做一遍 | 能照做的改写成统一 Runbook 模板；做不到的标「待重写」挂账，不立刻返工 |
| 应急预案与恢复脚本（主从切换、流量收敛、降级开关） | 检查可执行性：脚本在不在、权限在不在、执行入口在不在 | 只修「执行不通」的部分；内容不改，留待相关演练触发时再改 |

判据：抽查 5 份历史文档，能指出每份属于上表哪一类；指不出的，说明分类只做了命名没做判定。

**③ 双轨怎么维持、维持多久。** 双轨 = 新实验走平台与新流程，原有的手工演练继续按旧节奏跑。边界必须写死：**同一条链路在同一时间只允许一个注入源**，否则一旦出事，谁也说不清是实验、演练还是真故障。维持时长不用日历定，用收敛条件定（见 ④）；【经验】多数团队在 1–2 个季度内退出双轨，快慢取决于关键链路条数、值班人力与平台完备度。

**④ 什么信号说明可以退出双轨。** 三个信号同时成立才算：最近若干次实验都由值班同学独立完成，不再需要平台同学陪同；原有手工演练已经没人再跑（说明新流程确实更省事，而不是多了一件事）；abort 至少被真实越界触发过一次（说明中止链路被验证过，而不是从未被触发）。如果一个季度内 abort 从未触发过【经验】，那通常是阈值设得过松，不是系统太稳。

### 4.5 模板 / 示例

**模板 A：实验记录（一次实验一份）**

```yaml
experiment: pod-kill-one-replica
hypothesis: 终止 order 服务的一个实例，端到端成功率与 P99 不越界
steady_state:                        # 三元组，缺一不可
  - {metric: success_rate,   threshold: "<你的阈值>", window: "<窗口>", source: "<看板地址>"}
  - {metric: p99_latency_ms, threshold: "<你的阈值>", window: "<窗口>", source: "<看板地址>"}
target:
  mode: one                          # one / fixed / fixed-percent / all
  selector: {app: order}
  instances: 1                       # 必须写数
  blast_radius_r: "<1%"
fault:
  layer: 编排层                       # 主机 / 网络 / 进程 / 编排 / 应用 / 数据 / AI
  type: pod-kill
  params: {duration: "5m"}           # 参数名以所选平台官方文档为准
abort:
  on_metric: "<指标触发条件>"          # 例：success_rate 低于某个值即停
  on_time: "5m"
  manual_owner: "<值班人>"
observation: {}                      # 实验期间的实际读数，实验后回填
conclusion: ""                       # 通过 / 未通过 / 无效（未打到）
followups: []                        # 每条：问题 -> 动作 -> 负责团队 -> 回归版本
```

**怎么用**：`hypothesis` 与 `steady_state` 两栏在实验开始前填，阈值与窗口从稳态看板抄、不现场估，实验后不得修改（改了就等于改裁判）；`target.instances` 必须是数字，写「一批」「若干」即视为无效实验；`fault.params` 只参照结构，具体取值按平台官方文档，不要照抄这里的示例值；`conclusion` 允许写「无效（未打到）」——把没打到的实验如实记下来，比把它记成「通过」更有价值。

**模板 B：ChaosBlade 命令速查（只看参数形状）**

```bash
# 资源层：CPU 满载
blade create cpu fullload --cpu-percent 80 --timeout 60

# 网络层：网络延迟
blade create network delay --time 3000 --interface eth0 --timeout 60

# 进程层：杀进程
blade create process kill --process mysql --timeout 60

# 资源层：磁盘写满
blade create disk fill --path /tmp --size 100 --timeout 60
```

**怎么用**：每个动作都要带 `--timeout`，它是时间触发的下限保障；`80`、`3000`、`100` 都是占位值，按自己的稳态阈值与容量余量定；动作名与参数以官方文档当前版本为准，不要拿这里的示例直接跑生产。

**模板 C：Chaos Mesh 网络分区（声明式）**

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: network-partition-order-to-payment
spec:
  action: partition
  mode: one                # 不要写 all：它会把爆炸半径直接放大到整组
  selector:
    namespaces: [default]
    labelSelectors: {app: order-service}
  direction: to
  target:
    mode: one
    selector:
      namespaces: [default]
      labelSelectors: {app: payment-service}
  duration: "5m"
```

**怎么用**：`mode` 与 `target.mode` 都要写成 `one` 或 `fixed-percent`，先明确命中几个实例；`duration` 必填，它是时间触发；字段名以 Chaos Mesh 官方文档当前版本为准（版本间字段有差异，落库前先查官方 CRD 参考）。

**模板 D：ChaosBlade Operator 提交与观察**

```bash
# 1. 安装 Operator（chart 名称与命名空间以官方文档为准）
helm install chaosblade-operator <your-chart> --namespace <your-namespace>

# 2. 提交一个 Pod 级实验
kubectl apply -f pod-kill.yaml

# 3. 观察实验状态直到结束（不要提交完就走）
kubectl get chaosblade <experiment-name> -w
```

**怎么用**：第 3 步的 `-w` 是「实验结束时有人在场」的最低保障；第 3 步之后立刻回到模板 A 回填 `observation`，隔天补记的观测值不可信。

**模板 E：编排骨架（创建 → 轮询稳态 → 触发中止 → 保证回收）**

```python
# 骨架：把「实验必须被回收」写成 finally，而不是靠人记得
exp = chaos.create(spec)          # spec 即模板 A 的结构
try:
    while exp.running():
        observe(exp)              # 回填模板 A 的 observation
        if steady_state_broken(exp):
            exp.abort("metric")   # 指标触发
            break
except Exception:
    exp.abort("manual")           # 任何异常都不许把故障留在系统里
finally:
    exp.destroy()                 # 回收是幂等的，重复调用安全
```

**怎么用**：把 `chaos.create` / `abort` / `destroy` 换成所选平台的 SDK 或 CLI 调用（接口名以平台官方文档为准）；骨架里真正要保留的是 `finally` 的回收与「异常也 abort」这两行——它们是「无人值守也不会留下未回收故障」的唯一保证。

### 4.6 成本：这套东西的账单

混沌工程的钱不花在注入器上——注入器本身很便宜（ChaosBlade、Chaos Mesh 都是开源的，见 4.3）。真正相关的两项是**护栏的前置投入**与**每次生产实验消耗的可用性预算**，两者都由爆炸半径 r 支配。

**护栏与平台人力（贵在「与业务无关的固定投入」）**：稳态看板、abort 三触发、逐层可观测、预生产等价环境、值班与剧本库——这些在能跑第一个实验之前就必须存在（4.1 Step 1）。它们不产出任何业务功能，却要一支平台团队长期维护，并随「要注入的层数 × 语言 / 运行时数」增长（4.2、4.3 已有说明）。这是本主题最容易被低估的一项：**贵在它要求的运维形态，不在故障注入的算法**。

**可用性预算（单次实验的边际成本）**：生产实验花的是真实可用性。**推算**：单次实验的期望可用性损失 ≈ 爆炸半径 r × 受影响请求量 × 实验时长；探索档 r < 5%（§2.2 的分档【经验，非测量值】）把这一项压到可审批的量级，而把 r 从 5% 加到 20% 等于把这份成本乘四。托管注入服务（Gremlin / AWS Fault Injection Service / Azure Chaos Studio）把这部分转成订阅账单，省的是平台人力而不是可用性。

**硬件**：注入器进程本身开销可忽略；唯一实质的硬件项是**与生产拓扑等价、却又隔离的预生产环境**——这笔环境维护费在只走预生产的团队里就是主要支出（§3.4 组合四）。

> 通用 FinOps 与云成本分摊见 [11-cross-cutting/03-data-cost-finops](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节只标这个主题把钱花在「护栏」与「可用性预算」两处，而非注入器本身。

### 4.7 容灾与故障演练

混沌工程的「容灾」是元问题：它本身就是验证别人容灾的工具，自己却不承载在线流量，因此**不需要 RTO/RPO，也不适用跨地域容灾切换**——把混沌平台做成多活，是把通用高可用错配到一个非服务型组件上。它真实的失效形态是**「验证工具自己坏了，而结论看不出来」**：

| 失效模式 | 影响面 | 降级策略 | 演练方案 |
| --- | --- | --- | --- |
| 实验中途控制面 / 注入器挂掉，故障未被回收 | 注入进去的故障留在系统里，变成真实事故 | 回收由幂等的 `finally` 保证（4.5 模板 E），不依赖人记得 | 注入一次「打掉控制面」的故障，确认 abort 仍可达 |
| 注入通道与 abort 共用故障域 | 最需要中止时恰好中止不了 | 控制通道与注入通道逻辑隔离 | 同上；这是 4.2「注入器自身的故障域隔离」的验收动作 |
| abort 只有手动触发 | 故障时长 = 发现 + 判定 + 敢按之和（跨团队常以十分钟计【经验】） | 补时间触发（时长上限）与指标触发（尽早停） | 把阈值压到必然越界，确认系统自动停并回滚（4.1 Step 3 的中止演练） |
| 实验「通过」但其实没打到 | 消耗了可用性预算，换来一条不可用的结论 | 无降级——只能靠稳态三元组与对照组判定 | 复跑一次，看对照组与实验组的 Δ 是否可复现 |

**判据**：演示一次 abort 的真实越界触发，比读十遍 Runbook 有用——从未被触发过的 abort 等于没接线（4.4 ④）。跨地域 / 多活的真实容灾方案见 [12-architecture/07-disaster-recovery](../07-disaster-recovery/07-disaster-recovery.md)；多区域剧本演练是混沌工程的**验证目标**（§3.6 最后一行），不是混沌平台自身的容灾需求。

### 4.8 演进路线：0 → 1 → 100

混沌的每一级门槛都踩在**护栏的完备度**上，而护栏越完备，能安全消耗的可用性预算越大。

- **0 → 1（最小可用）**：预生产环境 + 手工注入一个最小单元（kill 一个 Pod）+ 手工回滚（4.1 Step 2）。**便宜在**失败零成本、不碰生产；**先坏的是**没有写死的稳态三元组（4.1 的「最常被跳过的是 Step 1 的三元组」）——实验跑完了，结论只能写成「抖动了一下，可能是……」，可用性没损失，但也没换来任何可行动的结论。
- **1 → 100（规模化）**：生产环境混沌 + 分层注入 + abort 三触发自动化 + 实验进 CI（4.1 Step 3–4）。**变贵的是**护栏与平台团队的固定投入，以及从预生产扩到核心链路后开始消耗的真实可用性预算；**先坏的是**abort 只靠手动兜底时「停得太晚」（跨团队常以十分钟计【经验】），以及实验集不随拓扑更新而退化成例行公事（§3.4 组合一）。
- **100 →（下一道坎）**：AI 辅助挑故障 + Self-Healing（主文件 §1.4 的 2023–2025 阶段）。**这一级目前不是既成能力**——[§5.1](06-chaos-engineering-section-5-ai.md) 把「AI 辅助故障选择」与「由 AI 判断是否回滚」都判为 **L3**（只有演示与自研，①不成立、②核不到），[§5.5](06-chaos-engineering-section-5-ai.md) 逐条拆穿这两项被过度宣传的部分，因此**等 §5.6 的可证伪信号出现再投入，不要在架构里把它当必经台阶**。**变贵的是**结构化历史故障与拓扑数据的积累——前期无收益（§3.6 第三行），且必须先把降级路径补出来才能注入 AI 链路；**先坏的是**把执行权交给模型——**建议权可以外放，执行权留在人与自动 Abort 手里**，否则一次不可逆的自动动作就把工具变成事故源。

### 4.9 自检清单

1. 稳态看板上每一条链路，是否都写成了「指标 + 阈值 + 持续时间 + 数据来源」四项？缺任一项即不合格。
2. 随机抽一条链路，5 分钟内能否答出它当前错误率与 P99 的数据来自哪个系统？
3. 每次实验是否都写了命中实例数与 r？写不出数字，说明爆炸半径不可控。
4. 是否留了对照组（未注入的同类单元）？没有对照组，实验组与稳态的差值无法归因。
5. abort 的三类触发是否齐全？只有手动触发的实验，是否已被禁止在无人值守时段运行？
6. 最近一次「中止演练」是什么时候？从未做过，说明中止链路没有证据支持它可用。
7. 注入通道与 abort 依赖的告警链路，是否与被测业务共用同一组可能被一起打掉的路径？
8. 代码 / 配置 / 依赖变更后，实验集有没有更新过？没更新，它描述的是旧拓扑。
9. 上个季度的实验记录里有多少条结论是「通过」？如果全部是「通过」，先查判定门槛，再谈系统韧性。
10. 每条实验记录能否追到至少一条可追踪的改进项？无结论的实验应计入无效消耗。
11. 上次发现的脆弱点，有没有一条能在下个版本被回归验证？没有则复发不可发现。
12. AI 链路是否存在可测的降级路径，并已被注入验证过？没有降级路径，AI 层实验无从设计。

### 4.10 小结

> 本节小结：整条落地路径里唯一决定成败的环节，是 **Step 1 那张写死了「指标 + 阈值 + 持续时间」的稳态看板**。它看起来最不像混沌工程——没有注入、没有实验、没有故障——但它是后面三步唯一的裁判：Runbook 的判定标准、自动 Abort 的阈值、CI 门禁的门槛，全部引用它。跳过它，实验照样能跑，只是跑完之后没人能说清是「系统扛住了」还是「根本没打到」；而后者会以最贵的方式被结算——一次实验消耗了可用性预算，换来一条不可用的结论。
>
> 💡 **思考锚点**：拿你稳态看板上任意一条链路，按 4.9 第 1 条自检：它是否写全了「指标 + 阈值 + 持续时间 + 数据来源」四项？再抽一条没做过的线路，问 4.1 的 Step 1 能否回答它的命中实例数与 r 是多少——这两个数你现在答不上来的话，是打算先补看板，还是直接开注入（后者消耗的可用性预算，对应的是 4.10 哪一类「不可用的结论」）？
