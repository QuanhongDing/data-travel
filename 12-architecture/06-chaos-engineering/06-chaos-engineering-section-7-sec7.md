## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

把「传统测试 / 压力测试 / 容灾演练 / 手动故障演练 / 混沌工程」放在同一张表里逐维度打 1–5 分，最大的问题不是分数不准，而是**它把「取决于场景的结论」伪装成「绝对结论」**。同一个维度在不同的约束下符号会相反，打分表把符号丢掉了。

举一个本章里最典型的维度：「爆炸半径可控」。传统测试拿 5 分、混沌工程拿 4 分（与压力测试同分），但**分数的方向本身就不是绝对的**：在默认约束（炸了要赔钱、没有隔离手段）下，半径小是优点，环境天然隔离的传统测试拿这一行的满分是顺理成章的。但如果你的系统已经有单元化、灰度、流量调度作为物理隔离，那么**半径大反而是优点**——因为真实事故不会只影响 1 个副本，半径太小意味着你验证的是「一个副本消失」而不是「一次真实故障」。同一个维度，两种约束，两个相反的结论。

打分表还隐藏了**前置条件**。混沌工程的「自动化」被打了高分，但「自动化」只有在已经具备①稳态指标、②自动中止、③按标签选择注入范围这三件事的前提下才是优点；这三件都没有时，自动化程度越高越危险——它只是把「靠人手抖造成事故」变成了「按计划造成事故」。打分表不会告诉你这一点，因为它打的是一把尺子，而前置条件是尺子之外的东西。

打分表配套的决策树受同一问题影响。它把「资源投入」分成「充足 / 一般 / 有限」三档据此分流，但没有说明这三档以什么为界——是几个专职人力、一年有多少演练窗口、还是有没有可观测性基建？分界说不清的档位，落到真实选型里只能凭感觉落档，于是决策树退化成一个流程图：它看起来给了答案，实际上只是把你的判断重新排列了一遍。本章 7.5 的每个判断节点都在树后有一条对应的「阈值依据」，并注明那条依据来自成本函数、来自本章的分档，还是来自组织约束。

本章采用的判据框架因此换成三个问句：**在什么约束下、为了验证什么机制、代价是什么**。下面的六条判据都是这三个问句的展开。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 失败判据 | 失败了怎么算失败（断言具体输出，还是断言一组指标不越界） | 一个手段「能发现什么」由它的失败判据决定，而不是由它的功能清单决定 |
| 故障的真实形状 | 注入的是「模拟异常输入」还是「进程真的消失 / 丢包 / 依赖真的变慢」 | 真实事故的形状决定系统哪一层会被压到；形状不对，压不到你想验证的那层机制 |
| 前置依赖 | 需要先有什么才能安全使用（稳态指标、自动中止、隔离单元、流量调度） | 安全性不是手段自身的属性，而是手段与现有基建的**组合属性** |
| 成本函数形状 | 成本随服务数 / 演练频率 / 爆炸半径怎么增长 | 决定它能覆盖多少服务：固定成本高的手段只能覆盖少数核心服务 |
| 组织耦合 | 它是「一个项目」还是「流程里的一个环节」 | 决定它是一次性产出，还是能长期给出结论的机制 |
| 失效条件 | 什么条件下它的结论不再成立 | 不知道自己失效条件的手段，会在环境变了之后继续供给错误的信心 |

这六条判据之间不是并列关系：**失败判据与故障形状决定手段能不能发现问题，前置依赖与成本函数决定它能不能落到足够多的服务上，组织耦合与失效条件决定它的结论能维持多久**。7.3 的四个机制维度正是按这个优先级排的（判据 → 层次 → 门禁 → 持续性）。

### 7.2 候选方案全景

判据落到本章主题上，**「做不到什么」比「能做什么」更值得先问**：传统测试做不到「发现没人写过的场景」；压力测试做不到「回答故障并发时系统会怎样」；容灾演练做不到「验证不是流程、而是流程所依赖的机制」；手动故障演练做不到「在专家不在场时复现结论」；混沌工程做不到「告诉你哪一行代码错了」——它只保证稳态破了这件事被看见。选型时先接受每个手段的那一条「做不到」，比记它们的优点清单有用得多。

候选分两族。**手段族**回答「用哪种方式去验证」，**工具族**回答「注入怎么落地」。两族都要选，但顺序是先选族、再选件。

**手段族（五个候选）**：

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 传统测试（单元 / 集成 / 回归） | 验证功能正确性 | 给定输入，断言输出等于期望值 | 所有研发团队 | 随语言生态自带 |
| 压力测试 | 找承载力上限 | 逐步加大流量，观察指标劣化的拐点 | 所有团队 | JMeter / k6 / Locust 等开源 + 商业压测平台 |
| 容灾演练 | 验证预案与切换流程 | 按书面预案执行切换与恢复，度量流程与时长 | 金融、云厂商 | 自建 + 云厂商容灾产品 |
| 故障演练（手动） | 靠专家制造故障、观察处置 | 人工执行、人工判断、人工恢复 | 已有 SRE 团队的组织 | 自建 |
| 混沌工程 | 验证故障下的稳态是否成立 | 声明稳态假设 + 受控注入 + 稳态被破坏即中止 | Netflix / 阿里 / 字节 / 美团 | 开源工具 + 商业平台 |

**工具族（本章 §4.3 工具链，全部保留）**：

| 工具 | 出品方 | 核心机制（一句话） | 许可 / 商业模式 |
| --- | --- | --- | --- |
| Chaos Monkey | Netflix | 工作时段随机挑选实例终止，让故障常态化 | 开源 |
| ChaosBlade | 阿里 | 按「层 × 语言」组织注入能力，支持方法级改值 / 抛异常 | 开源（Apache-2.0） |
| Chaos Mesh | PingCAP（CNCF） | 以 K8s CRD 声明式注入，与编排控制面同层 | 开源（Apache-2.0） |
| LitmusChaos | CNCF | ChaosEngine CRD + 实验库，Pod 级实验开箱可用 | 开源（Apache-2.0） |
| Gremlin | Gremlin | 商业 SaaS，把安全护栏与审批做进产品 | 商业订阅 |
| AWS Fault Injection Service / Azure Chaos Studio / GCP 混沌能力 | 各云厂商 | 注入器与云资源 API 同层，免自建执行器 | 随云计费 |
| Chaos Toolkit | Chaos Toolkit 社区 | 用 JSON / YAML 描述实验流程，与执行器解耦 | 开源 |
| Toxiproxy | Shopify | 以 TCP 代理形式注入延迟 / 断连 / 慢响应 | 开源 |

两族内部的差异都不大——工具族的差别基本在「注入点挂在编排控制面还是挂在进程内」，手段族的差别只在失败判据与前置依赖。**跨族的差异才是量级差异**。所以先分族判断（我需要的是「验证机制」还是「执行注入」），再在族内按成本与生态选件，能省掉一半以上无意义的比较。

分族的实操问法是两句：**我缺的是「注入能力」还是「判断结论的方法」？** 缺注入能力（有稳态指标、有中止机制，但注入手段只覆盖杀进程）就选工具族；缺判断结论的方法（工具已能杀实例，但每次都只能得出「服务还活着」）就要先回手段族补判据。绝大多数「混沌工程做了但是没用」的现场，缺的不是工具，是后一句。

工具族内部还有一个常被忽略的差别：**注入点是在编排控制面（Chaos Mesh / LitmusChaos 的 CRD），还是在目标进程内（ChaosBlade 的各语言注入器，或应用自带的方法级注入）**。前者免部署、对应用零侵入，但只能注入「编排层能看到的东西」（Pod、网络、卷）；后者能力更细，代价是要在目标机上部署 agent 并按语言维护。这条差别直接决定了你在 7.3.2 里能压到哪一层。

### 7.3 机制差异：为什么它们表现不同（核心节）

五个候选的差别可以全部归因到四个机制维度：**判据**（什么算失败）、**层次**（压到系统的哪一层）、**门禁**（靠什么保证不出事）、**持续性**（结论的保质期由什么决定）。前两个决定「它能发现什么」，后两个决定「它能持续发现什么」。四个维度是递进的：判据不对，后面的维度都无意义；层次不够，判据再好也只能得出「服务还活着」；门禁缺失，前两项越强越危险；持续性缺失，前两项的成果会随时间失效。

下面每个机制小节都按同一结构展开：机制定义 → 各候选的实现差异 → 由此必然导出的性质（写成因果句）→ 公开证据 → 失效条件。

#### 7.3.1 失败判据：断言输出 vs 断言稳态

**机制是什么**：传统测试的判据是「给定输入 → 输出等于期望值」的确定映射；混沌工程的判据是「一组稳态指标在一个时间窗内不越界」。两者的失败判据不同，能覆盖的失败模式就不同。

| 手段 | 失败判据 | 判据何时成立 | 覆盖的失败模式 |
| --- | --- | --- | --- |
| 传统测试 | 输出 ≠ 期望值 | 在测试环境、用例执行的那一刻 | 测试写作者**已经枚举过**的失败模式 |
| 压力测试 | 指标在加压下越过阈值 | 加压过程中 | 容量不足、排队、超时连锁 |
| 容灾演练 | 预案步骤没走通 / 切换超时 | 演练窗口内 | 流程缺失、依赖不可达、切换时长的估计错误 |
| 手动故障演练 | 专家判断「表现不对」 | 专家在场且能判断时 | 专家想到的那些故障 |
| 混沌工程 | 稳态指标越界（或未越界） | 持续运行 + 自动采样 | **从未被枚举过**的失败模式 |

**由此必然导出的性质**：因为传统测试的判据是「具体输入的具体输出」，所以它的能力上限就是测试用例集——没写过的场景它永远发现不了，而「未知未知」（主文件 §1.2）恰恰不在用例集里；因为混沌工程的判据是「稳态指标不越界」，它不需要预先枚举故障的表现形式，所以它能撞出没人想到的失败模式，**代价是它只能告诉你「稳态破了」，不能告诉你「哪一行代码错了」**——定位仍然要靠可观测性回溯与人工分析。判据越「松」，发现未知的能力越强，定位精度越低。

**公开证据**：混沌工程五原则的第一条即「围绕稳态行为建立假设」（【公开】Netflix《Chaos Engineering Principles》五条原则，2014 年前后公开——本章主文件 §1.1 即以此名列出这五条，§1.4 记为 2014 年公开；原文可在 principlesofchaos.org 按该标题查看，以站点当前版本为准）；本章主文件 **§1.1「是什么」的六维对比表**（目标 / 环境 / 故障 / 关注点 / 失败态度 / 实施周期）已把「关注点」与「失败态度」两项按同一判据区分开——「代码是否符合预期」对应断言具体输出，「系统是否在故障中存活」对应断言稳态不越界。

**失效条件**：稳态指标没有定义、或定义得过宽时，判据会退化成「服务还活着」。此时混沌工程与「看一眼监控」等价，什么也发现不了——本章 §6.1 Netflix 案例的失败教训里，「只看服务是否还活着」正是踩过的坑（§6.6 的踩坑对照表也把这条列为四个案例的共性）。

#### 7.3.2 故障的真实形状与注入层次

**机制是什么**：注入的现实性不由「离生产多近」决定，而由**它压到系统的哪一层**决定。压到业务分支、压到容量、压到流程、压到依赖返回，各自能验证的机制完全不同。

| 手段 | 注入形态 | 压到的层 | 典型盲区 |
| --- | --- | --- | --- |
| 传统测试 | Stub / Mock 制造异常返回 | 业务代码里**已经写了分支**的地方 | 没写分支的场景 |
| 压力测试 | 合成或回放的放量流量 | 容量、排队、连接池 | 故障并发发生时的行为 |
| 容灾演练 | 按预案切换 / 摘除 | 流程、切换工具链、依赖可达性 | 预案没覆盖的中途状态 |
| 手动故障演练 | 专家现场制造故障 | 专家想到的那一层 | 专家没想到的层 |
| 混沌工程 | 按「层 × 手段」矩阵选层注入 | 主机 / 容器与编排 / 应用进程内 / 中间件 | 未纳入矩阵的层 |

**由此必然导出的性质**：因为 Mock 只覆盖「代码里已经写了处理分支」的情况，所以它能验证分支写得对不对、验证不了「依赖返回的报文格式变了」这类没有分支的场景；因为应用层方法级注入（延迟 / 抛异常 / 篡改返回值）直接作用在调用点上，所以它能制造「**依赖成功返回、但值或语义是错的**」这一最难用外部手段模拟的故障，**代价是它需要按语言各实现一套注入器**（Java / Go / Node.js / Python 各不相同），能力维护量随「层数 × 语言数」增长。

**公开证据**：本章 §4.1、§4.2 给出 ChaosBlade 在主机、网络、进程、磁盘各层的注入命令；§6.2 记录阿里把注入能力组织成「层 × 手段」矩阵并覆盖 Java / Go / Node.js / Python 四种语言（【公开】[ChaosBlade 官方文档「混沌实验模型 / 实验场景」章节，chaosblade.io，2020–2024]；各版本具体支持的层与语言以 github.com/chaosblade-io/chaosblade 的 Release Note 为准）。可按「chaosblade 注入模型」检索官方文档核验其当前的层与语言清单。

**失效条件**：只做容器层注入（杀 Pod）时，被验证的只是服务发现与流量摘除，而「依赖抖动」「异常处理分支」完全没被压到——这两者恰恰是更接近真实事故的形状（本章 §6.1 Netflix 案例的失败教训）。反过来的失效条件同样存在：**不是「越底层越真实」**，而是按你要验证的机制选层；用主机层注入去验证异常处理分支，同样验证不到（该取舍见本章 §6.2 的矩阵注释）。

#### 7.3.3 爆炸半径与安全门禁：为什么「敢在生产做」是前置条件问题

**机制是什么**：可安全执行 = 稳态假设（提供判据）+ 自动中止（提供执行器）+ 范围控制（提供选择器），三件套缺一不可。门禁不是「态度」，是配置。

| 手段 | 半径由什么决定 | 中止由什么触发 | 谁来把握安全性 |
| --- | --- | --- | --- |
| 传统测试 | 测试环境本身 | 用例跑完 / 断言失败 | 无需，环境隔离 |
| 压力测试 | 加压曲线 | 指标越过阈值或压测时长到点 | 压测执行者 |
| 容灾演练 | 被切换的流量 / 机房范围 | 预案的回退步骤 | 演练指挥 |
| 手动故障演练 | 现场的人 | 现场的人 | **执行者的经验** |
| 混沌工程 | 选择器（标签 / 比例 / 白名单） | 稳态指标越界即自动停止注入 | **配置本身** |

**由此必然导出的性质**：因为自动中止把「发现稳态被破坏」到「停止注入」的时延压到与监控采样同量级，所以安全不再依赖执行者的经验，注入能力可以开放给普通工程师自助执行——覆盖面因此可以大幅扩张；**代价是这条链路的前置项变成了硬约束**：稳态指标必须在可观测性里先建好，没有指标，自动中止没有输入，门禁是空的，配置里的「自动中止」只是一行没人读的文本。本章 §6.3 字节案例的失败教训正对应这条因果：早期没有护栏，只有专家敢做，覆盖面极小，倒逼把安全条件写进实验配置（默认小比例 + 稳态中止）。

**公开证据**：本章 §2.2 给出爆炸半径的比例分档（探索 r < 5%、验证 r = 5–20%、极限 r = 20–50%，属【经验】档——按实践归纳，不同组织的耐受度不同，可结合自己的容量余量与隔离能力上下调整）；§4.1 阶段 3 写明「实验与告警联动，异常自动 Abort」；§6.3 记录字节把「默认小比例 + 逐步加码 + 稳态中止 + 高危审批」作为平台内置约束（【公开】字节跳动技术团队公开分享，2020–2024；本章 §6.3 的案例即据其技术博客与公开演讲整理，具体平台约束原文可按「字节跳动混沌工程故障演练平台」检索核验）。

**失效条件**：当稳态指标的采样周期长于故障的破坏速度（例如把错误率按小时聚合，而注入造成的连锁失败在分钟级完成），自动中止来不及生效。这种情况下「门禁已建立」反而更危险——它给出的信心比没有门禁时更大。

#### 7.3.4 持续性：为什么「一次演练通过」不等于「现在还能扛」

**机制是什么**：韧性是「当前拓扑 + 当前依赖 + 当前流量」的函数，三者都在变，因此任何一次验证的结论都有保质期。

| 手段 | 触发方式 | 复跑频率 | 结论的保质期由什么决定 |
| --- | --- | --- | --- |
| 传统测试 | 每次提交（CI） | 每次变更 | 与代码同步，几乎不过期 |
| 压力测试 | 大促 / 大版本前 | 按需 | 容量与流量模型变化即失效 |
| 容灾演练 | 按季度 / 半年排期 | 年度到季度 | 拓扑与依赖变化即失效 |
| 手动故障演练 | 按项目 | 一次到几次 | 项目结束后无人复跑 |
| 混沌工程 | 调度器周期触发 / 每次发布 | 周期自动 | **配置化，可版本化、可 diff、可复跑** |

**由此必然导出的性质**：因为混沌实验被写成一份声明式配置（目标范围、故障类型与参数、注入节奏、稳态假设、中止条件、结果归档都在配置里），所以它能被调度器周期触发、能被版本化、能被 diff，于是从「一次性项目」变成「持续机制」；**代价是周期运行需要常态化的资源与组织安排**——演练期间要占用冗余容量，出问题时要有能立刻叫停的人，这两项在一次性演练里都不必常备。反过来说：手工敲命令的实验无法复现、无法纳入流程，只能依赖「有人记得去做」，这是手动演练与容灾演练很难跑密的根本原因。

**公开证据**：本章 §6.2 记录 ChaosBlade 的声明式实验配置（【公开】[ChaosBlade 官方文档「混沌实验模型 / 实验场景」章节，chaosblade.io，2020–2024]）；§6.1 记录 Netflix 把实验编排为周期自动运行并持续多年（【公开】[Netflix Tech Blog, "The Netflix Simian Army", 2011]，该文首次公开 Chaos Monkey 的随机终止做法；其后关于 ChAP（Chaos Automation Platform）的文章给出周期自动编排的做法——前一篇可按标题在该博客检索核验，ChAP 相关文章按「Chaos Automation Platform」这一关键词可检索到其公开分享）；§6.3 记录字节把演练排进备战时间轴，并作为「是否可以上大促」的判断依据之一（【公开】字节跳动技术团队公开分享，2020–2024，可按「字节跳动混沌工程大促备战」检索核验）。

**失效条件**：服务拓扑或依赖发生结构性变化后，旧配置仍在跑，但注入点已不在关键路径上——演练照样周期运行、覆盖率数字照样好看，产生的信息量却降为零。这是「配置化」自身的代价：配置不会自动知道它已经过时。

### 7.4 成本结构对比（不是价格表，是成本函数）

对本章这支手段族，成本函数大致是：

```
成本 ≈ 可观测性基建（固定，前置）
     + 常备冗余容量（随注入半径 × 集群规模）
     + 注入平台与执行器（固定 + 随「层数 × 语言数」增长）
     + 组织协调成本（随参与团队数 × 演练频率增长）
     + 误伤损失（随门禁失效概率 × 爆炸半径）
```

对五个手段分别看，**哪一项是主导项、哪一项是隐性成本**：

| 手段 | 主导项 | 隐性成本 | 成本随什么超线性增长 |
| --- | --- | --- | --- |
| 传统测试 | 用例编写与维护（随代码量与变更率） | 测试执行时间（拖慢 CI） | 用例数 × 环境组合 |
| 压力测试 | 压测环境与流量发生器 | 压测环境与生产规格不一致带来的结论偏差 | 压测规模（要按生产规格搭） |
| 容灾演练 | 组织协调（多团队同时到场） | 停机窗口的业务损失 | 参与团队数 |
| 手动故障演练 | 专家工时 | 专家不在场时能力不可复制 | 场景数 × 每个场景要请的专家 |
| 混沌工程 | 可观测性基建 + 稳态指标定义（一次性，但不可省） | 常备冗余容量 | 注入半径 × 集群规模 |

读这张表的方式是：**先找自己那一列里增长最快的那一项**，那才是真正的约束。传统测试的约束是代码变更率（变更越快，用例维护越贵）；压测的约束是压测环境规格要跟得上生产（跟不上时结论直接无效）；容灾演练与手动故障演练的约束都是人（参与团队数、专家是否在场）；混沌工程的约束是冗余容量与可观测性基建。前四者的约束主要来自「人与环境」（组织侧成本），混沌工程的约束来自冗余容量与可观测性基建（系统侧成本）——**组织侧成本不会因为你少做演练而消失，系统侧风险却会因为不做演练而持续积累**，这就是混沌工程值得单独引入的理由。

三项容易算错的成本值得单独说清。

**冗余容量项**：它随「注入半径 × 集群规模」增长，而**不随演练次数增长**——这是它与其余各项最大的不同。一次 40% 半径的实验和十次 40% 半径的实验，容量代价是同一个数（只要不叠加），因为要预留的是「按半径算出来的那份余量」，不是「每次演练消耗一份」。所以提高演练频率（在门禁可靠的前提下）几乎不额外花钱，而放大半径要真金白银。

**误伤损失项**：它的期望值是 `门禁失效概率 × 爆炸半径 × 单次影响的业务价值`。三项里前两项都是可以压的（门禁靠 7.3.3 的三件套，半径靠选择器），但**它的分布是重尾的**：绝大多数实验不产生损失，少数几次失控会一次性吃掉全年预算，并且顺带把组织对这件事的信任清零。这正是为什么 7.3.3 把「稳态假设 + 自动中止」列为前置而不是可选项——不是因为它省钱，而是因为它是把重尾分布截断的唯一手段。

**组织协调成本项**：它近似随「参与团队数」线性增长。手动故障演练之所以很难跑密，不是技术做不到，而是每跑一次都要把每个相关团队的人在同一时间窗里凑齐、并准备好回滚方案。这条约束与 7.3.4 的「配置化」互为因果：把实验写成配置，才可能不靠凑人也能跑。

**下面三个【推算】分别说明三件事：小半径的实例注入为什么测不出容量、半径的容量代价有多大、执行器的维护量随什么增长。**

【推算】设某服务有 20 个副本、平均 CPU 利用率 60%。注入 1 个副本时，剩余 19 个承担全部负载，利用率变为 `60% × 20/19 ≈ 63%`；要让剩余副本被打满，需 `60% × 20/(20−k) ≥ 100%`，即 `12/(20−k) ≥ 1`，解得 `k ≥ 8`。**结论：在 60% 利用率下，杀实例这一维度要到 8/20 = 40% 的半径才会暴露饱和问题**；一次杀 1 个副本（5% 半径）的演练，验证到的其实只是「服务发现与流量摘除」，不含任何容量信息。

【推算】由上一条直接得到半径的容量代价：常态化跑 40% 半径的实验，等价于长期常备约 40% 的冗余机器（推导：需要 k/N = 8/20 = 40% 的副本可以同时消失而不劣化）。这就是为什么多数实践把大半径实验限制在备战前的一次性窗口，而把周期性实验压在小半径——小半径要拿到信息量，正确做法不是继续放大半径，而是**换层注入**（依赖层 / 应用层），因为依赖层注入不需要冗余容量。

【推算】执行器的维护量随「层数 × 语言数」增长：以本章 §6.2 阿里案例的矩阵为例，**层次口径要先说清**——§6.2 的行文按 4 层组织（主机 / 容器与编排 / 应用 / 中间件），它画出的矩阵把「应用」按运行时再拆成 JVM 与 Go/Node/Py 两行，因此表上是 **5 行**而非 5 层；语言覆盖 Java / Go / Node.js / Python 4 种（清单见 §6.2）。逐格看，真正要按语言各实现一遍的只有应用层（4 格），主机 / 容器与编排 / 中间件三层的注入与语言无关（3 格），当前要维护的实现单元是 `4 + 3 = 7`；而**缺口的上限是 `层数 × 语言数`**（按 5 行表算是 20 格）——每加一种语言，应用层就多一格；每加一层（如 GPU、模型服务），矩阵就多一行。所以它是随两个变量增长的**结构化缺口**，不会随复用次数摊薄。这也解释了为什么「统一交付注入能力」比「各 BU 各自造轮子」更省：自建时每个 BU 都要各自填一遍同一个缺口，成本按 BU 数再乘一档；§6.2 的 25 BU 复用同一套能力，正是把这 25 份缺口压成 1 份。

### 7.5 决策树（每个分支都要有阈值依据）

```
你要验证的是什么？（判据决定手段，7.3.1）
├─ 给定输入 → 期望输出是否正确      → 传统测试
├─ 系统能扛多大流量                 → 压力测试
├─ 预案能否按步骤走通、切换要多久     → 容灾演练
├─ 人的处置熟练度、流程有没有漏洞     → 手动故障演练 / GameDay
└─ 故障下的稳态是否仍然成立          → 混沌工程，继续往下

[前置门禁] 是否已具备 ①稳态指标（可查、采样周期到分钟级）
          ②稳态被破坏即自动中止 ③按标签/比例控制注入范围的选择器？
├─ 缺任一项 → 先补可观测性与选择器，此阶段不做注入
└─ 三件齐备 → 继续往下

[第一个实验放在哪？]
├─ 没有任何生产演练记录 → 预生产，先跑通「注入 → 稳态破坏 → 自动中止」闭环
└─ 闭环时延已实测过     → 生产环境，半径按下一档控制

[半径给多少？]
├─ 首次 / 探索期  → r < 5%（严格小于；边界见阈值依据）
├─ 稳定后验证期   → r = 5% – 20%
└─ 极限测试       → r = 20% – 50%，需专项审批且限定在有人值守的演练窗口

[杀实例没发现问题，往哪走？]
├─ 想验证自愈与流量摘除   → 保持容器层注入，重点测恢复时长
├─ 想验证异常处理分支     → 加应用层方法级注入（延迟 / 抛异常 / 改返回值）
├─ 想验证容量与调度       → 加主机层注入，或按 40% 半径放大（见阈值依据）
└─ 想验证依赖退化         → 加中间件层注入（DB 慢查询 / 缓存失联 / MQ 堆积）

[跑多勤？]
├─ 服务数少（约 10 个以内）且变更频率低（低于每周 1 次）→ 季度 GameDay 即可
└─ 服务多或变更频繁                     → 声明式实验配置 + 周期自动运行

[链路里有 AI 组件吗？]
├─ 无 → 成功率 / 延迟 / 吞吐作为稳态即可
└─ 有 → 稳态必须补一维「输出质量」，否则只能验证「服务没挂」
```

**阈值依据**（树上共 7 个判断节点；下面 9 条逐条对应，其中「半径给多少」按三个档位各一条，其余节点各一条）：

- **目的分流（传统测试 / 压测 / 容灾演练 / 手动演练 / 混沌）**：依据是失败判据不同（7.3.1）。判据决定一个手段能发现什么，不是功能清单——用压测的判据去问混沌工程，永远得不到容量拐点，反之亦然。
- **前置门禁三件套（含「稳态指标采样周期到分钟级」）**：依据是机制而非经验——自动中止的输入是稳态指标，范围控制的执行者是选择器；缺稳态指标则中止条件无从判定，缺选择器则半径不可控（7.3.3）。「分钟级」这一量化限定的来源有两处：主文件 §2.2 把稳态定义为「指标在阈值内且持续时间 > t」，该节示例取 5 分钟窗口，采样周期必须细于这个判定窗口，否则「是否越界」判不出来；以及 7.3.3 的失效条件——注入造成的连锁失败在分钟级完成，按小时聚合的错误率来不及触发中止，门禁等于空置。
- **先预生产**：依据是组织约束——在没有任何生产演练记录时，「注入 → 破坏 → 中止」这条链路的时延未经实测，此时在生产环境验证的其实是这条链路本身，而不是系统韧性。
- **r < 5%（探索期）**：依据是本章 §2.2 的爆炸半径分档，该档写作「探索阶段 r < 5%」——是严格小于而非 ≤，因此树与本小结都写 `<`。换算到实例维度：副本数为 N 时杀 1 个副本的半径是 `1/N`，要满足 `1/N < 5%` 需 `N ≥ 21`；N = 20 时 `1/20` 正好等于 5%，落在验证档的端点上，此时要么多杀一个副本（`2/20 = 10%`）要么改按比例选择器。也就是说「一次杀一个副本」只在副本数 21 以上才自动落在探索档，规模越大越稳。
- **r = 5%–20%（验证期）**：依据同为 §2.2 的爆炸半径分档（验证阶段 r = 5–20%）；与上一档的边界正好接在 5%，无重叠也无缺口。
- **r = 20%–50%（极限档，需专项审批）**：下界与上界都取自 §2.2 的极限测试分档（该档原文即标注「谨慎使用」），树写成闭合区间是为了让端点与依据完全对应。**上界 50% 是判据边界，不是行政规定**：容量消失过半之后，实验观测到的已经不是「系统能否在故障中维持稳态」，而是「系统在过载下多久彻底崩溃」——后者属于压测与容灾演练的判据，不再是混沌实验要回答的问题（7.3.1）。组织侧的对应做法见 §6.3 字节案例的「高危操作需审批」。
- **杀实例无发现 → 换层或放大到 40%**：依据是 7.4 的容量推算——60% 利用率、20 副本下需 `k ≥ 8`（40% 半径）才会打满，说明实例维度的小半径注入本身不含容量信息。
- **服务数约 10 个以内 + 变更频率低于每周 1 次 → 季度 GameDay**：依据是组织约束与【经验】——【经验】多数团队在这个规模与频率下，人工排期的季度 GameDay 已能覆盖主要链路；服务数或变更频率再高，人工排期无法覆盖，必须转为周期自动（对应 7.3.4 的声明式配置机制）。
- **AI 链路补「输出质量」稳态**：依据是机制——成功率与延迟对「返回格式正确但语义错误」不敏感；模型服务可能「响应成功但质量下降」，用传统稳态指标测不到（该失效模式见本章 §6.7 的 AI 时代条目）。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单服务起步、无生产演练经验 | 预生产 + ChaosBlade / LitmusChaos 的声明式实验 + 稳态中止 | 商业平台（Gremlin）小范围试用 | 一上来把预算花在执行器上，稳态指标这一前置仍未建 |
| K8s 原生、希望用 CRD 管理实验 | Chaos Mesh / LitmusChaos | ChaosBlade 的 K8s Operator | 它们与编排控制面同层，注入点天然贴合容器层 |
| 多语言混布（Java / Go / Node.js / Python） | ChaosBlade 的层 × 语言能力矩阵 | 自建注入器 | 自建会按语言各写一套，维护量随语言数增长（7.4 的推算） |
| 主机与中间件层（DB / 缓存 / MQ / 资源） | ChaosBlade 的主机与中间件注入 | 自建脚本 + Toxiproxy | 云厂商托管注入只覆盖自家资源，出不了那朵云 |
| 接受订阅、想少自建执行器 | Gremlin（商业） | 云厂商 Fault Injection Service / Chaos Studio | 商业平台替你解决执行器，但不替你定义稳态指标 |
| 开发期的网络抖动与依赖异常回归 | Toxiproxy（TCP 层代理） | 应用层方法级注入 | Toxiproxy 在 TCP 层，模拟不了「成功返回但值错了」 |
| 跨云 / 混合技术栈的流程编排 | Chaos Toolkit（与执行器解耦） | 各云厂商工具拼接 | 单一云厂商工具无法跨云统一编排 |
| 只在开发期验证依赖异常、不接触生产 | Toxiproxy + 应用层方法级注入 | 手工改 stub / mock | stub 只覆盖代码里已经写过的分支（7.3.2） |

**五个常见组合，以及每个组合的运维代价**：

1. **可观测性 → 混沌工程 → 大促保障 → 容灾设计 → 灰度回滚（能力链，非工具链）**。职责边界：可观测性供判据，混沌工程产出「机制是否真的生效」的结论，大促保障把这些结论放进备战通关条件，容灾设计兜底极端场景，灰度回滚负责把修复安全地放上线。运维代价：这条链要求五项常备——任何一项缺失，结论就停在上一环节无法闭环。
2. **混沌工程 + 单元化**。职责边界：单元化提供物理隔离（把爆炸半径限制在一个单元内），混沌工程在这个半径内做注入。运维代价：单元化本身要求数据与流量可分片，分片不彻底的业务只能退回到小半径注入。
3. **混沌工程 + 容灾演练**。职责边界：容灾演练验证「流程与预案」，混沌工程验证「预案所依赖的机制是否真的生效」（切换真的在分钟级完成、限流真的挡住、降级分支真的走通）。运维代价：一次联合演练要同时占用演练指挥与值守人力，频率因此受限。
4. **混沌工程 + AI 链路（GPU / LLM API / Agent 工具调用）**。职责边界：常规注入覆盖基础设施，AI 特定注入覆盖模型服务不可用、工具调用超时、向量检索失败，并把「输出质量」纳入稳态。运维代价：质量型稳态需要标签数据与评测样本，是一笔持续的标注与评测投入。
5. **混沌工程 + 压力测试（叠加使用）**。职责边界：压测提供「高负载」这一背景条件，混沌注入提供「故障」，两者叠加验证的是「高负载下的故障」——这正是大促事故最常见的形状。运维代价：叠加会把稳态破坏的归因变难（分不清是流量造成的还是故障造成的），因此通常一次只叠加一种故障。

挑选组合的顺序：先看**稳态指标是否可查**（不可查则任何组合都无从判定结论），再看**有没有物理隔离手段**（有单元化就优先用它压半径，没有就只能压比例），最后看**结论要流向哪里**——流向备战通关就看组合 1，流向预案修订就看组合 3，流向 AI 链路韧性就看组合 4，流向架构的隔离边界就看组合 2 与组合 5。组合不是越多越好：每多叠一层，稳态破坏的归因难度就上升一档，而演练的价值恰恰在于「知道是哪个机制没生效」。

### 7.7 选错的代价与迁移成本

**反模式：把混沌工程当压力测试用** —— 症状：用混沌实验去找「系统能扛多少 QPS」。因为混沌的判据是稳态指标、压测的判据是拐点，两者不是同一把尺子，结果是实验既没给出容量拐点，也没给出故障下的稳态结论，还多占了一份常备容量。正确做法：容量问题交给压测，混沌实验只在「容量已定、要验证故障下是否仍达标」时使用。

**反模式：没有稳态指标就上生产注入** —— 症状：先装了注入工具，直接在生产杀 Pod「看有没有事」。因为没有判据也没有自动中止（7.3.3），演练与事故没有区别；一旦出事，第一次实验就成了最后一次，团队从此把混沌工程定性为「危险动作」。正确做法：先建稳态指标与自动中止，再在预生产跑通「注入 → 破坏 → 中止」闭环。

**反模式：只做杀实例，然后把覆盖度当成信心** —— 症状：每周自动杀 Pod，覆盖率高，结论是「我们韧性很好」。因为注入压不到依赖层与应用层（7.3.2），被验证的只是自愈与流量摘除，而依赖变慢、异常分支、数据一致性这些更接近真实事故的形状从未被压到。正确做法：用「故障维度 × 业务范围」矩阵管理覆盖度，并按业务定制稳态假设（本章 §6.4 美团方案）。

三个反模式有一条共同的结构：**都在用其中一个机制维度去替代另一个**——用压测的判据替代混沌的判据，用工具替代门禁，用半径替代层次。识别方法也统一：当你发现「我们做了 X，所以我们可以放心了」这句话里，X 回答不了这句话问的问题时，就是反模式。

**换成另一个要动什么**：

| 迁移方向 | 数据迁移 | 注入定义改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 手动故障演练 → 混沌工程 | 无 | 要把实验沉淀为声明式配置 | 需建选择器、调度与中止链路 | 要学稳态假设与中止语义 | 中（【经验】1–2 个季度） |
| 预生产混沌 → 生产混沌 | 无 | 选择器要从环境标签改为生产标签 | 需接生产告警作为中止输入，并建审批与值守 | 要接受「结论可能以事故形式出现」的风险边界 | 中 |
| 只杀实例 → 多层注入 | 无 | 实验要按层重写（应用层要写注入点） | 需按语言部署注入器，按中间件维护实现 | 要掌握「按要验证的机制选层」 | 中–大（随语言数增长） |
| ChaosBlade → Chaos Mesh（或反向） | 无 | 命令式实验要改写为 CRD（或反之） | 执行器与权限模型重建 | 概念相近，主要是配置语法 | 小–中 |
| 自建注入器 → 开源 / 商业平台 | 无 | 自建脚本要重写为平台配置 | 平台接入、权限与审批对接 | 低 | 小 |
| 一次性演练 → 周期自动 | 无 | 配置已可用，主要是补调度元数据 | 需调度集成，并明确「实验失败是否阻断发布」 | 要定义演练结果与发布门禁的关系 | 中 |

这张表里有一个反直觉的分布：**「数据迁移」与「注入定义改写」两列在所有迁移方向上要么是「无」要么是「小」，成本全部压在「运维重建」与「团队再学习」上**。原因是混沌工程不持有业务数据，它只在系统上施加影响，所以换工具、换环境都不涉及数据搬迁。这也意味着迁移的成本几乎全是组织成本——从「谁会做」变成「流程里有没有」，而组织成本无法靠一次投入买断，只能靠机制固化。如果预算只够做一件事，先做「运维重建」（把选择器与中止链路建起来），因为它是另外三项的前置。

### 7.8 小结

把前面的判据、机制、成本与决策树收成一句话：**先确认你有判据（稳态指标），再确认你有刹车（自动中止），然后才谈半径、层次和频率**。这三件事的顺序不能颠倒，因为后一件的效果全部依赖前一件的存在。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 还没有稳态指标，只有一个「稳定性靠值班顶着」的系统 | 先补可观测性与稳态定义，暂不做注入 | 自动中止的输入是稳态指标；没有它，注入没有判据也没有刹车 |
| 有稳态指标，但只在预生产演练过 | 在生产跑小半径（r < 5%）实验，先测闭环时延 | 先验证「注入 → 破坏 → 中止」这条链路本身，再验证系统 |
| 已经会杀 Pod，但从未验证过依赖异常 | 加应用层与中间件层注入，先补故障维度而非放大半径 | 只压容器层得到的是自愈结论，压不到异常处理分支（7.3.2） |
| 演练是每年一次的项目 | 把实验写成声明式配置并接调度，纳入备战通关条件 | 一次通过的结论有保质期；机制化才能复跑（7.3.4） |
| 链路里有 LLM / Agent / GPU | 稳态补「输出质量」维度，并在依赖与模型层做细粒度注入 | 成功率与延迟测不到「答对了但质量掉了」 |
| 多业务多团队，覆盖度说不清 | 用「故障维度 × 业务范围」矩阵管理覆盖，稳态按业务定制 | 覆盖度可量化才能定位缺口；通用稳态会掩盖业务特有失败模式 |

最后提醒一处容易被忽略的前提：混沌工程验证的是「你赖以自信的机制是否真的生效」，因此**它的结论只在这些机制本身没变的前提下有效**。限流阈值、降级开关、切换脚本、依赖拓扑——任何一项变了，之前那次通过的演练就不再构成证据。这也是 7.5 里把「跑多勤」单列为一个判断节点的原因：频率不是资源投入问题，是结论有效性问题。

> 本节小结：这五个候选之间唯一真正起决定作用的差异，是**失败判据**——断言具体输出，还是断言一组指标不越界。前者决定了一个手段只能发现被枚举过的失败模式，后者决定它能撞出未知未知、但必须靠可观测性才能定位。而混沌工程能否落地，不取决于工具选得多好，取决于稳态假设与自动中止这两个前置是否已经存在。
