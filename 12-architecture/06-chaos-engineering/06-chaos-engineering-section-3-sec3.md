## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把混沌工程讲成了「按场景挑一个」：核心业务选生产环境混沌，初创团队选预生产混沌，大促前选 GameDay。这个讲法漏掉了真正的决策变量——**同一个模式在不同约束下的代价可以差一个数量级**。同样叫「生产环境混沌」，在可观测性齐备、abort 就绪、有值班盯盘的团队里是高保真的廉价实验；在同一套东西都缺的团队里，它是一次没有预告的故障。

混沌实验的本质是一次交换：用**受控的可用性损失**换**未知脆弱点的信息**。汇率由三件事决定——能不能及时发现异常（可观测性与稳态基线）、能不能及时停下（abort 与值班）、停下之前会伤到多少人（爆炸半径）。这三件事任缺其一，原本划算的模式就会变得不划算，而模式的名字不会提醒你这一点。

所以本节的顺序是先立约束、再讲模式。**模式不是被选的，是被约束推着走的**：约束不同，同一场景下的正确模式就不同。若一个模式在你当前约束下不成立，那不是模式错了，是你的前置条件还没到位。

这里有一个容易被忽略的推论：**保真度是模式取舍的主轴，但它不是唯一的轴**。同为「在生产上做实验」，把目标选成一个实例、一个可用区还是整个区域，风险等级完全不同——本章 §2.2 用 r（故障实例数 / 总实例数）把这一轴显式化（探索 r < 5%、验证 5–20%、极限 20–50%，【经验】）。所以下面每个模式的结构示意里，目标选择器都是必填项，它不是配置细节。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 稳态指标与可观测性 | 实验能否被判定成败 | 「注入故障后看有没有报错就行」——没有写成「指标 + 阈值 + 持续时间」的基线，报错与否无从归因 |
| 爆炸半径承受力 | 能在哪个环境、多大范围做实验 | 「生产才是真实的，所以必须在生产做」——承受力不足时，生产实验就是事故 |
| 环境保真度 | 预生产结论能外推到哪一步 | 「预生产复现了就等于生产也会这样」——数据分布、流量规模与资源争抢都被简化过 |
| 组织协调成本 | 单次实验是自动化的还是项目制的 | 「演练越正式越好」——协调成本高就无法高频，不能高频就无法发现回归 |
| 停止与回滚能力 | 实验的默认时长与放大节奏 | 「先设计实验，再补 abort」——没有 abort，实验的期望代价不收敛 |
| AI 链路的额外约束 | 故障类型是否要覆盖非确定性组件 | 「AI 链路不可测所以不测」——不可测的是它的输出，可测的是它的降级行为 |

### 3.2 模式逐个拆解（核心节）

七个模式并排列出：顺序既不代表先进程度，也不是一条保真度单调递增或递减的阶梯。第 1 行「生产环境混沌」的门槛最高（稳态基线 + abort 三触发 + 值班盯盘缺一不可），保真度也最高；往下几行则分别沿不同的轴取舍——保真度、安全性、自动化程度、覆盖面——而不是在同一条轴上排队。把它们并排列出来，是为了避免一种最常见的误判——把模式当成风格偏好，而它们其实各自带着入场门槛。

读这张表的正确方式是**逐行读「前置条件」那一列，而不是按行号读先进程度**：保真度越高、爆炸半径越大，对护栏的要求就越严格——生产环境混沌排在第 1 行，是因为它的门槛最高，而不是因为它是「终极形态」。反过来读也成立——**如果你还回答不了「出问题时谁在第几分钟做什么」，那么你需要的不是换一个更先进的模式，而是先把护栏补齐**。

| 模式 | 前置条件（缺一不可） | 条件缺失时的后果 |
| --- | --- | --- |
| 生产环境混沌 | 稳态基线 + abort 三触发 + 值班盯盘 | 实验变成一次没有预告的真实故障 |
| 预生产环境混沌 | 可复现的依赖拓扑 + 数据脱敏 + 流量回放 | 环境退化为「能跑起来的玩具」，结论无可信度 |
| GameDay | 剧本库 + 明确熔断条件 + 复盘机制 | 退化为表演日，演练收益归零 |
| 持续混沌 | 可自动判定的实验 + 豁免与误报处理机制 | 门禁被绕过，实验集与拓扑脱节 |
| AI 辅助混沌 | 结构化历史故障 + 实时拓扑 + 人工复核 | 推荐退化为随机，或只推荐老问题 |
| 分层混沌 | 逐层可注入 + 各层独立可观测 | 单层结论无法归因，跨层故障成盲区 |
| 实验矩阵 | 故障维度与业务域的统一定义 | 覆盖度仍是印象，空格无人认领 |

下面逐个拆解。每个模式都按同一套结构给出：约束 → 结构 → 机制 → 代价 → 失效点 → 真实使用。

#### 3.2.1 生产环境混沌（Production Chaos）

- **被什么约束逼出来**：预生产环境的保真度不足——只有在真实流量分布、真实依赖拓扑、真实资源竞争下，才会暴露「只在生产出现」的脆弱点。
- **结构**：

```text
生产环境混沌的最小闭环（缺任一环都不该开跑）
  ① 稳态假设：错误率 / P99 / 吞吐 在窗口内达标     ← 没有基线，结论无从谈起
  ② 目标选择：按「最小可观测单元」选，而非随机全局
        单元 = 1 个实例 / 1 个可用区 / 1 个分片 / 1 个租户
  ③ 故障注入：进程 / 网络 / 资源 / 应用 / 数据
  ④ 对照组：保留未注入单元的同类指标
  ⑤ 判定：Δ = 实验组 − 对照组，与稳态阈值比较
  ⑥ 停止：时间触发 / 指标触发 / 手动 —— 任一触发即回滚
  ⑦ 学习：问题 → 改进项 → 回归到 Runbook / 容量 / 架构
```

- **为什么这样设计有效**：因为实验对象就是最终要保护的那套环境，所以「环境差异导致结论失真」这一整类误差被消掉了。
- **代价**：实验期间消耗的是真实可用性预算；而且可观测性、abort、值班这三样是**与注入规模无关的固定成本**——注入一个实例和注入十个实例，都要同样一套护栏，所以单位实验的固定开销高，只能靠「一次实验只验证一个假设」控制总量。另一项隐性成本是**判定成本**：对照组要求监控能按单元切分指标，很多团队的监控维度直到这一步才第一次被真正检验。
- **失效点**：当稳态指标不能反映用户真实体验时（例如只盯后端错误率、没有端到端成功率），「生产环境最真实」的优点会反转成**虚假信心**，因为实验只验证你写下来的那条稳态，没写进稳态的退化它一律看不见。
- **真实使用**：Netflix 从 2011 年起在生产随机终止实例，其深远影响不是「发现几个缺陷」，而是把「实例随时可能消失、服务必须无状态可替换」变成了默认设计假设（【公开：Netflix Tech Blog《The Netflix Simian Army》, 2011】）。多数团队的做法是从单个实例 / 单个可用区起步再放大（【经验】）。

#### 3.2.2 预生产环境混沌（Pre-Production Chaos）

- **被什么约束逼出来**：爆炸半径承受力为零——护栏（可观测性、abort、值班流程）还没建好，此时任何生产实验都不受控。
- **结构**：

```text
预生产能复现什么 / 不能复现什么（决定结论的外推半径）
  能复现（机制类问题）
    依赖缺失：下游挂了，上游有没有超时 + 降级
    单点故障：多副本是否真多活、主从是否真能切
    配置错误：连接池 / 重试 / 超时阈值是否互相打架
    编排逻辑：限流、熔断、队列堆积的连锁反应
  不能复现（规模类问题）
    真实流量分布：长尾请求、热点 key
    真实数据量：大表 JOIN、冷热分层边界
    真实资源争抢：连接数、显存、文件句柄
  结论：预生产能回答「有没有那个机制」，
        不能回答「那个机制在多大规模下够不够」。
```

- **为什么这样设计有效**：因为实验对象与真实用户隔离，任何失败都被限定在环境边界内，结论可以放心采集而不必承担用户损失。
- **代价**：环境必须长期维护——数据脱敏、流量录制回放、外部依赖 mock，维护成本随保真度单调上升，而且**永远追不上生产**；这笔成本与实验次数无关，是持续支出。更麻烦的是**保真度错觉**：环境维护得越好，团队越容易忘记它与生产的差距在哪里，而这个差距本身没有仪表盘。
- **失效点**：当预生产结论被当作「生产也会这样」时，可控爆炸半径带来的安全感会反转成**外推误判**，因为预生产里的流量分布与资源争抢是被人为简化过的，而线上故障恰恰多由规模触发。
- **真实使用**：多数团队的共同做法是把预生产当作「机制检验层」——先在这里证明熔断、降级、主从切换确实被触发过，再把规模验证留给生产上的小半径实验（【经验】）。

#### 3.2.3 GameDay（演练日）

- **被什么约束逼出来**：组织协调成本——「谁发现、谁判定、谁决策回滚」这条人的链路，无法靠单点自动化验证，只能靠一次有人真实参与的演练才能暴露。
- **结构**：

```text
GameDay 的结构：把技术实验扩成组织实验
  T−2 周  选剧本（Region 故障 / 主从切换 / 缓存击穿 / LLM API 不可用）
          写死稳态假设、判定标准、熔断条件（何时无条件中止）
  T−1 周  通知相关团队（不搞突袭）、确认值班链路、确认回滚脚本可执行
  T−0     注入 → 观察 → 记录时间线
          真正要记的是「人的动作时刻」：
            第几分钟发现 → 第几分钟判定 → 第几分钟决定回滚 → 第几分钟恢复
  T+1 周  复盘：把动作时刻转成改进项（告警阈值 / Runbook / 权限 / 剧本库）
  交付物（没有这些就等于没演练）：
     时间线 + 未触发告警清单 + Runbook 缺口 + 必须补的自动化
```

- **为什么这样设计有效**：因为演练把「系统行为」和「人的响应」放进同一条时间线，能暴露单靠监控看不到的缺口——告警没响、没人知道去哪看、权限不够、Runbook 步骤已失效。
- **代价**：从 T−2 周到 T+1 周的组织投入远大于实验本身，且演练规模受「陪跑人力」限制，无法与发布频率同步；一次演练能覆盖的剧本数量永远有限。还有一项容易被忽略的成本：演练会把问题明确落到具体团队头上，若复盘被当成追责，下一轮就没人愿意报真问题。
- **失效点**：当 GameDay 退化成「表演日」（剧本提前泄露、只演练已知会通过的场景）时，组织能力建设的收益会反转成**安全幻觉**，因为演练的全部价值来自「暴露意外」，而排练过的东西不再意外。
- **真实使用**：大促前的典型形态是「GameDay + 全链路混沌」——用一次集中演练覆盖跨团队的关键链路。把 GameDay 常规化的团队通常按季度到半年一次，大促前追加（【经验】；其方法论定位可按「AWS Well-Architected GameDay」自行检索核验）。

#### 3.2.4 持续混沌（Continuous Chaos）

- **被什么约束逼出来**：回归成本——脆弱点是随代码、配置、依赖变更被重新引入的，一次性演练拦不住回归；只有把实验挂进发布流程，才能让上周修好的东西不被本周改回去。
- **结构**：

```yaml
# 持续混沌：实验不是「跑一遍看看」，而是「不过就阻断」
pipeline:
  - unit-test
  - integration-test
  - chaos-gate:
      experiments:
        - name: pod-kill-one-replica
          target:       {selector: "app=order", mode: one}   # 爆炸半径 = 1 个实例
          duration:     "5m"
          steady_state: {error_rate: "<0.1%", window: "5m"}
          abort:        {on_metric: "error_rate > 1%", on_time: "5m", manual: true}
        - name: dependency-latency
          target:       {downstream: "payment", latency: "+200ms"}
          steady_state: {p99: "<500ms", window: "5m"}
  - canary-deploy
```

- **为什么这样设计有效**：因为实验与代码版本一一绑定，「哪次提交引入了脆弱点」可以定位到 commit，而不是笼统归因于「最近改得比较多」。
- **代价**：CI 时间被拉长——实验有最短持续时长，压不下去；门禁一旦误报就会阻塞交付，因此必须维护实验白名单与豁免机制，这本身就是一条持续维护面。此外，实验失败时的**归因成本**转移到了开发同学身上：他要知道这条实验在测什么、为什么通过门槛是 0.1% 而不是 1%。
- **失效点**：当实验集长期不更新时，「自动化高频」的优点会反转成**覆盖率幻觉**，因为回归发生在新增依赖与新链路上，而实验集描述的是过去的拓扑——跑一千次旧实验，也测不到本周刚接入的那个外部依赖。
- **真实使用**：Netflix 的随机终止实例本身就是持续形态——它不是一次演练，而是长期在跑（【公开：Netflix Tech Blog《The Netflix Simian Army》, 2011】）。把混沌做成 CI 门禁在多数团队仍属进阶实践，通常要等实验集与豁免机制稳定后才推进（【经验】）。

#### 3.2.5 AI 辅助混沌（AI-Assisted Chaos）

- **被什么约束逼出来**：故障选择的搜索空间——当系统有数百个依赖、每层又有多种故障可注入时，「注入哪一个最有信息量」已经无法靠人工穷举；观察侧同时出现瓶颈：异常模式超出静态阈值能表达的范围。
- **结构**：

```text
AI 辅助混沌的三个位置 + 一条不可让渡的红线
  ① 故障推荐：输入 服务拓扑 + 依赖强度 + 历史故障 + 变更记录
               输出 候选故障列表（按预期信息量排序）
  ② 异常判定：输入 多指标时序
               输出 偏离稳态的候选区间（比静态阈值更早、更细）
  ③ 恢复决策：输入 实验中指标 + 历史恢复记录
               输出 建议回滚 / 建议继续观察
  ────────────────────────────────────────────────
  红线：AI 可以「建议」，执行权必须留在人 + 自动 abort 上
        理由：推荐错了只浪费一次实验机会；
              执行权错了，实验当场变成事故。
```

- **为什么这样设计有效**：因为推荐把「历史故障与当前拓扑的相似度」变成了排序依据，实验预算能被投向更可能命中的假设，而不是顺序遍历故障类型表。
- **代价**：它要求两样前置数据——历史故障记录与实时拓扑，缺任一样推荐就退化为随机；推荐结果仍需人工复核，于是「想实验」的脑力成本换成了「审推荐」的脑力成本，只有实验频次足够高时净收益才为正。第三项隐性成本是**模型自身需要被验证**：推荐质量下滑不会报错，只会让实验命中率悄悄走低。
- **失效点**：当历史故障数据稀疏或分布已偏移时，「按信息量排序」的优点会反转成**只测老问题**，因为模型学的正是历史，而历史里没出现过的故障类型不会被排到前面——可这恰是混沌工程最想找的「未知未知」。
- **真实使用**：该模式目前主要落在「故障推荐 + 异常检测」两个环节，恢复决策基本仍在人手里；多数团队的做法是先用规则驱动（按拓扑关键度与变更频率挑故障），积累够故障数据后再考虑引入模型（【经验】）。

#### 3.2.6 分层混沌（Layered Chaos）

- **被什么约束逼出来**：故障的层级耦合——一次线上故障很少只发生在一个层，但「同时注入跨层故障」会让根因无法归因；分层把故障按注入点所在层切开，使每次实验的因果可归因。
- **结构**：

```text
分层混沌：按「注入点所在层」切分，每层独立可归因
  层                    注入点（示例）                        被验证的假设
  ────────────────────  ───────────────────────────────────  ─────────────────────────
  基础设施层            终止实例 / 驱逐节点 / 磁盘满          实例消失无感、调度能补齐
  网络层                延迟 / 丢包 / 分区 / DNS 故障         超时与重试不互相放大
  应用层                HTTP 5xx / 慢响应 / 限流 / 抛异常     熔断降级真的会触发
  数据层                主从切换 / 缓存击穿 / 队列堆积        数据不丢、切回不重复消费
  AI 层（AI 特定混沌）  LLM API 失败 / 工具调用超时 / GPU OOM 降级路径存在且可用
  ──────────────────────────────────────────────────────────────────────────────────
  顺序纪律：自下而上。下层假设未验证前，上层结论不可信
           （网络层重试还没收敛时，应用层熔断阈值的「通过」没有意义）
```

- **为什么这样设计有效**：因为每一层的故障类型与该层应具备的保护机制一一对应，所以「实验失败」能直接指向「缺哪个机制」，而不是留下一句「系统扛不住」。
- **代价**：实验矩阵按「层 × 故障类型 × 爆炸半径」展开，跨层组合更是笛卡尔积，组合数增长很快；AI 层还有额外前置条件——必须先存在一条可测的降级路径，否则这一层连注入点都无从设计。层数越清晰，维护每层注入能力（多语言、多运行时）的成本也越高，这部分投入通常需要平台团队长期承担。
- **失效点**：当只做纵向切分、从不做跨层组合时，分层的可归因性会反转成**系统性盲区**，因为真实故障常是「网络抖动 → 重试风暴 → 熔断误触发」的链式反应，而单层实验的隐含前提是「其他层都正常」，这个前提在故障中恰恰不成立。
- **真实使用**：Kubernetes 生态的混沌工具普遍按「故障类型 = 一种资源定义」组织，可视为分层混沌的工程化（Chaos Mesh 提供 PodChaos / NetworkChaos / StressChaos / DNSChaos 等，可按其官方文档的故障类型章节核验）；阿里 ChaosBlade 把「在哪一层注入」与「用什么语言的实现」拆成矩阵（见本章 §6.2）。团队通常自下而上逐层补齐（【经验】）。

#### 3.2.7 实验矩阵与覆盖度管理（Coverage Matrix）

- **被什么约束逼出来**：覆盖度的不可回答性——当「故障维度 × 业务域」的乘积涨到几十上百格之后，「我们演练得够不够」只能靠印象回答，而印象指不出缺口在哪一格。
- **结构**：

```text
实验矩阵：把「演练覆盖」变成可数的格子
  行列定义与勾选照录本章 §6.4 的美团矩阵（实例 / 网络 / 依赖 / 资源 / 数据一致性
  五行）；末行「AI 链路」是本节补上的维度，用 ? 表示「该维度尚未进入矩阵定义」，
  而不是「已演练且未通过」
              外卖   到店   酒店   出行   买菜
  实例故障     ✓     ✓     ✓     ✓     ✓
  网络故障     ✓     ✓     ✓     ✗     ✗
  依赖故障     ✓     ✓     ✓     ✓     ✓
  资源故障     ✓     ✗     ✗     ✓     ✗
  数据一致性   ✓     ✓     ✗     ✗     ✗
  AI 链路      ?     ?     ?     ?     ?
  ────────────────────────────────────────────────
  矩阵的三个用途（缺任一项就退化为一张好看的图）：
    ① 缺口清单：✗ 即已知未覆盖、? 即尚未定义，按业务重要性排序补齐
    ② 优先级依据：核心业务的空格优先于非核心业务的空格
    ③ 节奏绑定：把「本轮填哪几格」挂到备战节奏上
```

- **为什么这样设计有效**：因为覆盖度被外化成可数的格子，缺口不再是某个人的记忆，而是一个能被指出、被排期、被验收的对象。
- **代价**：行与列的定义本身要维护（故障维度怎么切、业务域怎么划），且矩阵只度量「做过没有」，不度量「做得对不对」——每一格是否通过，仍要回到该次实验自己的稳态判定。它还引入一条管理成本：空格容易被当成指标，从而催生「为填格而填格」的实验。
- **失效点**：当矩阵的格子变成目标本身时，「缺口可见」的优点会反转成**形式化演练**，因为填格最省力的做法是挑最容易通过的场景——矩阵度量的是覆盖广度，不度量实验的信息量。
- **真实使用**：美团把「故障维度 × 业务范围」做成可查看的实验矩阵，用于回答覆盖度并排优先级（见本章 §6.4；该案例的故障维度为实例 / 网络 / 依赖 / 资源四类，另含数据一致性一行，勾选与上面的示意一致）。多数团队的做法是先用「核心链路 × 主要故障类型」的小矩阵起步，再逐步扩列（【经验】）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 核心业务、稳态团队 | 生产环境混沌 + 持续混沌 | 预生产的结论外推不到规模问题 | 有稳态基线 + abort + 值班，三者齐备 |
| 初创 / 中小型团队 | 预生产环境混沌 + GameDay | 生产实验的期望代价超过收益 | 护栏未就绪，承受不了真实用户损失 |
| 大促前 | GameDay + 全链路混沌 | 单团队实验覆盖不到跨团队链路 | 参与方跨 2 个以上团队（【经验】） |
| AI 推理服务 | AI 层混沌（即 AI 特定混沌：LLM 超时、GPU OOM） | 传统层混沌碰不到推理链路 | 降级路径已存在且可观测 |
| 智能体平台 | AI 层混沌（工具失败、API 超时） | 同上；且 Agent 链路跨外部依赖 | 每个工具调用都有超时与兜底 |
| 数据库 / 存储 | 数据层混沌（主从切换、磁盘满） | 只在应用层注入验证不了持久性 | 有可执行的切换与恢复预案 |
| 微服务架构 | 网络层混沌（延迟、丢包、分区） | 应用层注入测不出重试放大 | 超时 / 重试 / 熔断阈值已知 |
| 覆盖度说不清 | 实验矩阵（故障维度 × 业务域） | 继续加实验只是扩大分母，缺口依旧不可见 | 故障维度与业务域已有统一定义 |

**最常被误选的一对，是生产环境混沌与预生产环境混沌**：误选不是「选错环境」，而是**把两者当成了同一件事的不同档位**。护栏没就绪就上生产，实验会直接变成事故，用户侧表现为一次没有预告的抖动；护栏早已就绪却永远停在预生产，会得到另一种更隐蔽的后果——每次演练都通过，大促或流量尖峰时仍有链路崩掉，而因为「演练一直很成功」，团队会把原因归到「运气不好」，而不是「我们从未验证过规模」。

第二常见的误选是**把分层混沌当成「更多的实验」**：分层解决的是归因问题，不是覆盖率问题。在没有逐层可观测能力的前提下强行铺开五层注入，得到的是一堆无法判定成败的实验记录，消耗掉的可用性预算换不来任何可行动的结论。

### 3.4 组合模式：真实系统不会只用一种

**组合一：分层混沌 + 生产环境混沌 + 持续混沌**（Netflix 型稳态团队）
- 职责边界：分层决定**注入什么类型**的故障，生产环境提供**保真度**，持续混沌负责**防回归**——三者职责不重叠，因此可以叠用。
- 运维代价：实验集必须随拓扑更新（否则退化为例行公事）；门禁需要维护豁免清单；值班要能区分「实验中的异常」与「真实故障」。
- 适合规模：有专职 SRE、服务数上百、可观测性与 abort 已成平台能力。

**组合二：GameDay + 预生产环境混沌**（组织能力建设期）
- 职责边界：GameDay 验证**人的响应链路**，预生产混沌验证**机制是否存在**——一个测组织，一个测系统。
- 运维代价：T−2 到 T+1 周的协调成本是主要开销，因此只能低频；剧本库需要有人维护，否则每次都要重写。
- 适合规模：团队 10–50 人、关键链路 10 条以内（【经验】：档位由「陪跑人力能否覆盖全部关键链路」定出，不是行业统计）。

**组合三：AI 辅助混沌 + AI 特定混沌**（AI 链路韧性）
- 职责边界：AI 辅助负责**挑故障**（在大量候选里排序），AI 特定混沌负责**提供注入点**（LLM 失败、工具超时、GPU OOM）——前者降低选择成本，后者扩大可选集合。
- 运维代价：需要历史故障数据与降级路径两样前置；降级路径本身要先被设计出来，否则 AI 层无从注入。
- 适合规模：智能体链路有数十个外部依赖、且已有明确降级设计。

**组合四：预生产环境混沌 + 持续混沌**（护栏尚未就绪但想自动化的团队）
- 职责边界：预生产提供安全的执行环境，持续混沌提供节奏——在非生产环境里先把「实验进流水线」的机制跑通。
- 运维代价：需要一套与生产隔离但拓扑等价的实验环境，以及能自动判定成败的指标采集；环境维护成本是这里的主要支出。
- 适合规模：中型团队、实验环境稳定性尚可、暂时拿不到生产实验授权。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因 | 修法 |
| --- | --- | --- | --- | --- |
| 爆炸半径过大 | 单次实验覆盖的用户比例远超预期 | 实验从「测量」变成「制造事故」，且故障太大时真实根因被连锁反应掩埋 | 目标是整组而非最小单元，且没有按比例放大的节奏 | 从小到大逐级放大（如 5% → 10% → 20%），每级先验证稳态再放大 |
| 无稳态假设 | 实验结束问「结果算成功吗」，答不出 | 无法区分「系统扛住了」与「根本没打到」；结论不可复现 | 把混沌当成「注入一下看看」的探索，而非实验 | 开工前先写死「指标 + 阈值 + 持续时间」三元组 |
| 无回滚预案 | 实验期间出了意外，没人知道怎么停 | 故障持续多久由「发现与决策的速度」决定，而不是由设计决定 | 把注入脚本当作实验的全部 | 每个实验配 abort 三触发：时间 + 指标 + 手动 |
| 缺乏可观测性 | 异常出现了，但分不清是实验引起还是叠加故障 | 实验只能说「好像有问题」，无法转化为改进项 | 先上混沌、后补监控 | 混沌开工前先建指标、告警与链路追踪；没有反馈信号就没有实验 |
| 「为了混沌而混沌」 | 实验数量在涨、改进项数量不涨 | 资源被消耗而韧性不变；高频次掩盖了零产出 | 把实验次数当 KPI，与发布节奏脱钩 | 每个实验必须产出结论（通过 / 发现问题），问题必须转成改进项并追踪 |
| 忽视 AI 链路 | 传统层实验全绿，AI 链路从未被注入 | AI 链路成为唯一未验证的路径，而它常在峰值下最先退化 | 沿用传统混沌的故障类型表，未随链路扩展 | 把 AI 特定混沌（LLM API、Agent 工具、GPU）纳入分层矩阵；先确认降级路径存在再注入 |

**爆炸半径过大**在生产中最典型的暴露方式不是「实验把系统打挂」，而是**实验中的真故障被误判为实验噪声**：当注入范围足够大，连锁反应会覆盖整个观测面，值班看到的是全面告警，此时既判断不了系统是否扛住了假设中的那个故障，也判断不了是否触发了假设之外的缺陷——一次实验消耗了配额，却什么也没学到。

**无稳态假设**的暴露方式是**争论取代结论**：实验结束后一方说「错误率只涨了一点，说明扛住了」，另一方说「涨了一点就是没扛住」。没有事先写死的基线，这场争论没有裁判，最后往往以「下次注意」收场，脆弱点原样保留。

**无回滚预案**的暴露方式与直觉相反：它不是「停不下来」，而是**停得太晚**。abort 的三类触发里，时间触发给的是时长上限，指标触发给的是「尽早停」的信号，手动触发只是兜底；只配了手动触发的实验，其实际故障时长等于「异常被看见 + 有人判定 + 有人敢按下去」这三段延迟之和，而这三段在跨团队值班时通常以十分钟计（【经验】）。

**缺乏可观测性**的暴露方式最容易被误读：实验期间的异常没人能定位，于是结论被顺理成章地写成「可能是实验引起的，也可能是正常抖动」——一次无法归因的实验不仅没有产出，还会让团队对后续所有实验的结论都打折接受。

**忽视 AI 链路**的暴露方式最隐蔽：传统层实验一直全绿，团队据此认为韧性已达标，直到峰值流量下 LLM API 限流或 GPU 资源耗尽，才发现降级路径从未被验证过——而这类组件恰好在压力下最先退化。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 服务数 10 → 100+（【经验】的量级分界，非精确阈值） | 预生产环境混沌 | 拓扑已无法整体塞进预生产，mock 的真实性追不上依赖增长 | 分层混沌 + 生产小半径实验 | 需先补可观测性、abort 与值班，护栏建设是对交付期的挤占 |
| 发布频率周 → 日/多次 | GameDay | 脆弱点的回归速度快于演练节奏，演练变成追债 | 持续混沌（进 CI 门禁） | CI 时长上升，需建豁免机制并承担误报阻塞交付 |
| 故障候选几十 → 几百 | 人工挑故障 | 人工排序的成本超过实验本身，挑出的故障越来越偏 | AI 辅助推荐 | 需积累结构化历史故障与拓扑数据，前期无收益 |
| 链路含 LLM / Agent | 应用层混沌 | 非确定性组件的失败形态（超时、限流、工具报错）不在应用层故障类型里 | AI 特定混沌 | 必须先有降级路径，相当于先把功能补上再测 |
| 单团队 → 多团队共担 | 单团队实验 | 响应链跨团队，技术实验证明不了组织能协同 | GameDay 组织演练 | 协调成本上升、节奏变慢，必须配剧本库与复盘机制 |
| 单可用区 → 多区域 | 单点注入 | 跨区流量切换与数据同步路径不在单点实验的覆盖内 | 分层混沌 + 区域级剧本演练 | 需先验证流量收敛与数据同步，区域级演练的爆炸半径最大 |

这张表的共性是：**逼你换模式的从来不是规模本身，而是原模式的关键投入开始触顶**——预生产触顶的是保真度上限，GameDay 触顶的是人力节奏，人工挑故障触顶的是排序算力。判断自己是否到了该换的时点，只需问一句：最近三次实验里，有多少结论是「意料之中」？如果全部是，说明当前模式已经不再提供新信息。

### 3.7 自检清单

- [ ] 本次实验的稳态假设是否写成了「指标 + 阈值 + 持续时间」三元组？只有「系统正常」这类描述即为不合格。
- [ ] 爆炸半径是否写清了目标选择器与命中实例数？写不出实例数，说明半径不可控。
- [ ] 是否留了对照组（未注入的同类单元）？没有对照组，Δ 无法归因。
- [ ] abort 是否同时具备时间触发与指标触发？只有手动触发，等于无人值守时不会停。
- [ ] 实验期间由谁盯盘？无人的生产实验不在受控范围内。
- [ ] 是否列出了本次实验**不**覆盖的层与链路？没有盲区清单，就没有外推边界。
- [ ] 代码 / 配置 / 依赖发生变更后，实验集是否更新过？未更新则它描述的是旧拓扑。
- [ ] AI 链路是否存在可测的降级路径？没有降级路径，AI 层实验无从设计。
- [ ] 每个实验是否产出了至少一条可追踪的改进项？无结论的实验应计入无效消耗。
- [ ] 上次发现的脆弱点，有没有一条能在下个版本被回归验证？没有则复发不可发现。
- [ ] 若实验需要跨团队协调，是否已转为 GameDay 剧本而非临时拉群？
- [ ] 是否存在「只演练一定通过的剧本」？若有，演练收益接近零。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 护栏未就绪（无稳态基线 / 无 abort / 无值班） | 预生产环境混沌 + GameDay | 实验必须在用户之外闭环，先证明机制存在 |
| 护栏齐备且追求最高保真 | 生产环境混沌（小半径起步） | 只有真实环境能消掉「环境差异」这一整类误差 |
| 发布频率高、拓扑变化快 | 持续混沌（进 CI 门禁） | 脆弱点随变更回归，只有与 commit 绑定才拦得住 |
| 链路含 LLM / Agent | 分层混沌（含 AI 特定混沌） | 失败形态按层区分，不切层就无法归因 |
| 候选故障多到人工挑不过来 | AI 辅助混沌（建议而非执行） | 用相似度排序替代穷举，执行权仍留在人 |
| 已具多层能力但覆盖率说不清 | 实验矩阵（故障维度 × 业务域） | 覆盖率由印象变成可数，缺口可定位 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**这次交换的汇率——用可用性损失换信息，而汇率由可观测性、abort 与爆炸半径三者共同决定**。护栏到位，生产环境混沌是最优解；护栏缺位，同一个模式立刻变成事故。模式名从来不告诉你护栏在不在。
>
> 一句实操建议：把「本次实验的爆炸半径是几个实例」写进实验记录的第一行。写不出这个数，说明护栏还没到位，此时讨论选哪个模式是伪问题。
>
> 💡 **思考锚点**：为你的下一次实验先填三个数——目标实例数 ÷ 总实例数（r 落在探索 <5%、验证 5–20% 还是极限 20–50%）、稳态假设的「指标 + 阈值 + 持续时间」三元组、abort 三触发你实际具备几种——三者凑不齐，你挑的那个模式只是名字，换个约束同一个模式立刻变成事故；这三样东西，你现在能填出几个？
