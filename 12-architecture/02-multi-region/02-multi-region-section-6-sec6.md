### 6.1 阿里双 11「**三地五中心异地多活**」10+ 年（2013-2024）

**背景（Why）**

阿里 2013 年面临**双 11 多活**挑战：
- **1.7 亿订单**——**单机房**——**「**故障就垮**」**
- **2013 杭州机房故障**——**30 分钟中断**——**损失千万级**

**触发点（What）**

2013 年**阿里启动异地多活项目**（[阿里双 11 2023 复盘]）——**目标**：「**三地五中心 + 单元化**」。

**详细做法（How）**

阿里三地五中心异地多活的**5 大核心组件**：

1. **三地五中心（同城双活 + 异地灾备，核心）**
   - 关键设计：**杭州 2 + 上海 1 + 深圳 1 + 异地灾备 1**——**3 个数据中心**
   - 关键能力：**同城双活**——**A 中心挂 B 中心接管**

2. **单元化（核心创新）**
   - 关键设计：**按 userId Hash**——**12 个 Cell**——**每个 Cell 独立数据库**
   - 关键能力：**故障域隔离**——**单 Cell 挂只影响 1/12 用户**
   - 关键代码：
     ```java
     // 阿里单元化
     public class CellRouter {
         public int getCellId(long userId) {
             return (int) (Math.abs(userId) % 12);
         }
     }
     ```

3. **数据同步（精卫 CDC，核心）**
   - 关键设计：**精卫**（**阿里自研**）——**CDC + 影子库**——**分钟级同步**
   - 关键能力：**最终一致**——**「**跨 Region 数据流**」**
   - 关键数字：**30+ TB 数据**——**分钟级同步**——**8 年 0 故障**

4. **冲突解决（关键）**
   - 关键设计：**订单**——**「**单元化避免冲突**」**
   - 关键设计：**商品**——**LWW**（**Last Write Wins**）
   - 关键能力：**「**无冲突**」**——**「**正确**」

5. **流量调度（GSLB，核心创新）**
   - 关键设计：**阿里自研 GSLB**——**「**地理位置 + 网络质量**」**——**秒级切换**
   - 关键能力：**杭州挂**——**深圳 / 上海**——**自动承接**

**阿里异地多活关键数字**（[阿里双 11 2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **可用性** | 99.9% | 99.99%+ | **10 倍** |
| **故障恢复** | 30 分钟 | 2 分钟 | **15 倍** |
| **GMV** | 350 亿（2013）| 1.8 万亿（2024）| **50 倍** |
| **峰值订单/秒** | 1.7 万 | 60 万+ | **35 倍** |
| **0 严重故障** | 0 | 10+ 年 | **∞** |

**具体数字（How much）**

- 团队规模：阿里异地多活团队 100+ 人
- 关键数字（[2024 公开数据]）：
  - **1.8 万亿 GMV**
  - **10+ 年 0 严重故障**
  - **30+ TB 数据**同步
- 业务影响：阿里**全部业务**——**淘宝 / 天猫 / 支付宝 / 菜鸟**

**失败教训**

- 第 1 年**「**数据冲突**」**——倒逼**「**单元化**」**
- **「**跨 Region 同步**」**——倒逼**「**精卫**」**
- **「**流量切换**」**——倒逼**「**GSLB**」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选**同城双活**（**最简单**）——**2 个机房**
- 接入**1 个业务**——**主备切换**
- 团队：2-3 人

**1 → 10 阶段：6-12 个月**

- 扩展到**异地灾备**（**2-3 个 Region**）
- 引入**单元化**（**按 userId Hash**）
- 引入**数据同步**
- 团队：5-10 人

**10 → 100 阶段：12-24 个月**

- 扩展到**异地多活**（**3+ Region**）
- 引入**GSLB**（**自研**）
- 引入**冲突解决**
- 团队：10-30 人

**100 → 1000 阶段：12-24 个月**

- 引入**「**三地五中心**」**——**5 Region**
- 引入**「**Serverless**」**——**弹性**
- 团队：30-100 人

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 美团 / Netflix）印证：**异地多活不是「**多机房**」，是「**三地五中心 + 单元化 + 精卫 + GSLB**」**组合。
> - 关键时间线：阿里 10+ 年 / 字节 5+ 年 / 美团 4+ 年 / Netflix 5+ 年 —— **异地多活是 10+ 年长期工程**。
> - 选型第一原则：**同城双活**（**最简单**）——**主备切换** → **异地灾备**（**2-3 Region**）→ **异地多活**（**3+ Region**）→ **三地五中心**（**5 Region**）。
> - 99% 的失败来自「**数据冲突 + 跨 Region 同步 + 流量切换**」——必须有**单元化 + 精卫 + GSLB**。
> - 真正的 ROI 来自「**10 倍可用性 + 6-15 倍故障恢复 + 5-35 倍峰值**」——是**大厂核心业务的命脉**。
