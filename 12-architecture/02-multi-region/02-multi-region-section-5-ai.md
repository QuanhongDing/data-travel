## 5. 前沿演进（AI 时代）

> 原 § 5 共 84 行、为方向清单（AI 推理跨 Region / 向量库跨 Region / 训练数据跨 Region / 智能体跨 Region / AI 辅助决策），缺少机制与成熟度判断，重写为 ~300 行前沿评估。

### 5.1 先分清三类「前沿」

趋势清单最根本的毛病是**没有时间维度**。原文件把「LLM API 多 Region」「就近推理」写在同一处（原 §5.1 的「1. AI 推理服务跨 Region」，与它们并列的还有「成本优化路由」「多模型多 Region」），而把「自动切流」写进原 §5.4 趋势第 2 条（原文为「智能体自动选择 Region、自动切流、自动恢复」）、把「AI-Native Multi-Region」写进趋势第 6 条——中间隔着原 §5.2（RAG / 向量库 / GraphRAG）与原 §5.3（学术与工业进展）两节。同一批条目散落在成熟度迥异的几处、却以同等口气并列，读者据此排路线图就会踩空：**前者**是把既有的多 Region 机制套到一个新的负载类型上，**后者**到今天仍只有产品公告与概念描述。本节的三级判据必须可核验，**判据有三条**：**①** 该能力有**正式 release note 或官方文档条目**（不是发布稿、不是演示视频）；**②** 有**第三方（非厂商）的公开生产案例**（建设方自述、产品页演示都不算）；**③** **接口稳定**（不因版本升级改写调用方）。三条全中才是 L1，缺任一条就往下判。

| 级别 | 判据（三条全中） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 正式 release note / 官方文档条目 ② 第三方（非厂商）公开生产案例 ③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用，但接口或生态未稳，或只有建设方自有案例，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

**本节评估的是「AI 带来的增量」，不是多 Region 本身**。这一点决定了级别的读法：单元化多活、Global Database、主区归属这些形态的成熟度由 [§3 设计模式与范式](02-multi-region-section-3-sec3.md)、[§6 落地实践](02-multi-region-section-6-sec6.md) 与 [§7 与其他方法对比](02-multi-region-section-7-sec7.md) 负责，它们是既有的、有公开生产案例的工程；**§5 只问一个问题——把推理服务、向量索引、会话状态、训练数据这四类新对象放上多 Region 之后，哪些只是既有机制的搬运，哪些是新机制，新机制里哪些有证据。**所以「本节没有 L1」不等于「异地多活不能用」，而是说 **AI 带来的那部分增量目前都还缺第三方可复核的证据**。

第二个要先说清楚的写法差异是**事实校正**。原文件里有两处与主文件口径不一致、且可被公开来源核对的说法，本节按证据改正：其一，「Spanner 的 TrueTime 精度提升到微秒级」——TrueTime 的不确定区间是**毫秒量级**（【公开】Spanner, OSDI 2012；与主文件 §2.2 的 1–7ms 区间同口径），微秒级不是这套机制的公开描述；其二，「2024 新增节点间 zero-RTT 通信」——**本地副本上的 zero-RTT 读是 Spanner 论文里就有的机制**，不是 2024 年的新增条目（【公开】Spanner, OSDI 2012）。**这类校正的意义不在于纠错本身，而在于它示范了怎么读工业进展：一个能力是不是「新增」，只能靠 release note 与论文对照，不能靠文章里的年份。**

第三个差异是**对厂商进展的降档处理**：原文件的「工业进展」一栏共五条（Google Spanner 2024「新增节点间 zero-RTT 通信」、CockroachDB 24.x「Serverless 多 Region、跨 Region 强一致」、阿里 OceanBase 2024「AI 集群自动管理」、字节跳动 2024「春晚红包多 Region 调度」、OpenAI 2024「GPT 全球多 Region 部署」），其中 Spanner 一条已在上段按论文校正，其余四条本节不当作既成事实引用，改写成**判定入口**——查该产品对应版本的 release note 里有没有这条，而不是看科普文章里的年份。这里附带澄清一处归栏：**原稿把「TiDB 8.x：HTAP + 多 Region 增强」列在「学术进展」一栏，不在「工业进展」一栏**，本节对它的处理与上述条目相同。**这不是断言它们不成立，而是本节给不出可供读者复核的正式出处**；给不出出处的正确写法是给核验动作，不是给结论。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。六个字段缺一不可——多 Region 领域里没有不付代价的可用性，只写「得到」不写「付出」的方向应当被打回。

#### 5.2.1 推理服务的跨 Region 部署：路由的键变了，路由机制没变

- **旧做法与它的卡点**：原清单列了「LLM API 多 Region 部署」「就近推理」「成本优化路由」「多模型多 Region」。卡点不在「能不能把服务复制到两个 Region」，而在三处：**其一，路由的粒度变细了**——§7.3.3 的归属规则在这里要对「服务 × 模型版本」而不是「服务」做归属，而模型版本是随时会变的制品；**其二，容量不可复制**（同 [Ch12 §07](../07-disaster-recovery/07-disaster-recovery-section-5-ai.md)），「就近推理」的第一约束是目标 Region 有没有卡，不是网络延迟；**其三，切流路径的约束一条都没少**——DNS 受客户端 TTL 约束、共识组过半数派才能选新主（§7.3.4），这些与推理无关。
- **AI 改变了什么机制**：**只改变了被路由的对象，没有改变路由机制**。健康探测、端点摘除、按失败率熔断、就近路由，都是接入层已有的能力；AI 带来的新事实是「上游存在多个质量档位不等价、且都要占稀缺算力的服务」。因此真正新增的工作是**把「模型版本」纳入路由与灰度**——否则同一次请求在两个 Region 会打到不同版本的模型。
- **由此得到的**：**因为推理服务是无状态的、且模型可由制品重建，所以它天然适合挂到既有的热备 / 多活档位上，不必为它单独设计一套容灾**；**因为一次请求的答案分布由模型版本决定，所以「多 Region 推理」的验收标准不是延迟与可用性，而是同版本、可灰度、可回滚**——把「部署一致性」当成推理多活的第二条主线，是本节与「把服务复制两份」的最大区别。
- **由此付出的**：三条代价：**其一，成本路由与数据主权会互相打架**——最便宜的 Region 往往就是数据不该去的 Region，这条冲突必须在路由规则里显式写死优先级，而不是留给调度器按价格自动决定；**其二，模型版本漂移造成「静默不一致」**，同一 prompt 在不同 Region 给出不同答案，这比服务不可用更难发现，且无法用可用性监控抓到；**其三，跨 Region 转发本身要付流量费与额外的 RTT**，「就近」的收益在一次请求需要跨区取数据时会被抵消——这正是 §7.3.3 讲的跨区依赖问题换了个对象。
- **证据与来源**：机制侧属既有工程（路由与归属见 [§7.3.3](02-multi-region-section-7-sec7.md)，故障判定与切流见 [§7.3.4](02-multi-region-section-7-sec7.md)）；跨 Region 延迟量级为【经验】区间——同城 1–3ms、跨城 10–30ms、跨国 100–200ms（与主文件 §2.1 同口径；行业普遍观测值，随城市对与骨干路径不同而异，无单一权威来源，读者可用自己机房到目标 Region 的探测数据校准）。**「切过去之后质量掉了多少」与「跨 Region 接管耗时」均无公开可核验的第三方数据**，故判 L2。
- **成熟度**：**L2**。判据：① 与 ③ 成立（接入层为 GA 通用能力），② 缺非厂商可复核的生产案例；**判定方法是自己在两个 Region 各起一套同版本推理副本，实测「摘除一个 Region 后端点池的收敛时间」与「切换期间返回内容的分布」**——控制台里有没有多 Region 选项，不算证据。

| 路由依据 | 它优化的是什么 | 必然代价 | 什么时候会失效 |
| --- | --- | --- | --- |
| 就近（地理延迟） | 用户感知延迟 | 各 Region 都要常备容量 | 请求需要跨区取数据时，节省被跨区 RTT 抵消 |
| 成本（单价最低） | 单位请求成本 | 跨区转发流量费；可能与主权边界冲突 | 目标 Region 无卡或配额不足 |
| 合规（数据主权） | 合法性 | 可能牺牲延迟与成本 | 业务切分图与合规切分图不一致时（§7.6 组合 6） |
| 容量（哪还有卡） | 可用性 | 路由变得不稳定、难以预测 | 容量状态本身是外部状态，故障当天最不可靠 |
| 端点健康 | 可用性 | 误判会摘掉健康的端点 | 无仲裁机制时形成脑裂（§7.3.4） |

**这五种依据必须排出优先级，不能并列**：现实中的做法是把「合规」写成硬约束（命中即出局，不参与权衡），把「容量」与「端点健康」写成可用性门禁，最后才在剩下的候选里按延迟与成本排序。**把合规当成一个可以和价格加权求和的因子，是这类系统最常见的设计缺陷。**

**部署矩阵必须显式写出来**，否则「就近推理」会很快退化成「每个 Region 各自部署、各自升级」。一份能用的矩阵至少要有三列：**Region × 模型版本 × 该版本是否在当前 Region 可用**。它的价值在故障当天体现——当某个 Region 只有一个版本的副本时，你就知道「切过去」意味着接受一次版本变更，而这必须由业务决定能不能接受，而不是由路由规则默认。**这张矩阵不是文档装饰，它是演练脚本的输入**：演练里要覆盖的场景之一是「主 Region 换掉之后，备用 Region 的版本是旧的」，而这一条在只有业务代码的团队里几乎从未被演练过。

#### 5.2.2 向量索引与 RAG 检索链路的跨 Region：它是制品，不是数据

- **旧做法与它的卡点**：原清单写「Milvus / Pinecone 原生支持跨 Region 复制」「向量索引分片」「跨 Region 向量检索冗余」，并给出 RAG 的四条策略（Embedding 同步、就近检索、降级检索、LLM 路由）。卡点有两个：**其一，「跨 Region 复制」与「集群内多副本」是两种不同的能力**，科普材料里常被混为一谈，判断只能逐产品、逐版本核；**其二更根本——向量索引是「可重建的制品」而不是「只能复制的数据」**，为它买跨 Region 强同步，买到的是「恢复时不用重算」，不是可用性本身。
- **AI 改变了什么机制**：**它把一个藏在数据库内部的索引，变成了一个跨系统、带版本的外部制品**。传统索引丢了从原数据重建即可；向量索引的重建依赖**另一个外部服务（Embedding 模型版本）与一次全量扫描**，于是它同时具备数据的属性（要版本化）与计算产物的属性（可重建、但重建要花钱花时间）。
- **由此得到的**：**因为索引可由「原件 + 固定模型版本」重建，所以跨 Region 策略的正确形状是「保证三者版本可追溯 + 索引可重建」，而不是「索引跨 Region 强同步」**；**因为四段（原件 / Embedding 服务 / 向量索引 / 生成段，同 §5.2.2 的表）的恢复代价不在同一量级，所以它们必须分别处置**：**原件**不可重算，靠对象存储自身的多副本与版本化；**Embedding 服务**与**生成段**是无状态或纯计算，前者故障时降级为关键词 / 元数据检索（**分钟内完成的配置级切换**）、后者换一个副本即可（**分钟级**，归 5.2.1）；唯独**向量索引**要全量重建，随语料规模落在**小时到天级**——**前后相差两到三个数量级（【经验】：按典型语料规模与算力估计，分钟级对小时级约 2 个数量级、对天级约 3 个数量级；准确值以本团队演练实测的重建耗时为准）**。
- **由此付出的**：**其一，重建时间随语料规模增长，而且故障当下你未必有这份算力**——索引重建与 5.2.1 的容量稀缺是同一笔代价，两者会在故障当天叠加；**其二，重建的确定性依赖模型版本不漂移**，若 Embedding 服务用「最新版本」这类浮动引用，重建出来的索引与旧索引不可比，表现为「恢复之后检索质量莫名下降」；**其三，降级到关键词 / 元数据检索会改变召回分布**，同一个问题在降级期与正常期返回不同结果，这件事必须写进 SLA，而不是藏在实现里。
- **证据与来源**：**「索引可重建」是主流向量库与 RAG 工程的通行做法**，可自行核验的判定入口是：查你所用的向量库 release note 里「快照 / 备份 / 恢复」与「跨集群（跨 Region）复制」分别是哪个能力、一致性口径是同步还是异步。**「某产品原生支持跨 Region 复制」这类断言因产品与版本而异，本节不做**。RAG 各段的可重算性对照见下表；**本方向没有第三方公开的全链路成本与恢复实测**，故判 L2。
- **成熟度**：**L2**。判据：① 与 ③ 成立（三段分别处置是既有技术，可立即实施），② 缺第三方公开实测，且「跨 Region 复制」必须逐版本核验；**演练里必须量出两个数**：全量重建耗时与重建后 Top-K 与旧索引的重叠度——**这两个数是「要不要付跨 Region 复制的钱」的判据，不是设计文档里的一句话**。

| 链路段 | 是否可重算 | 跨 Region 处置 | 恢复代价 |
| --- | --- | --- | --- |
| 原件（对象存储里的图 / 音 / 视频 / 文档） | **否**，唯一不可重算的一段 | 按对象存储自身的多副本与版本化能力处理 | 取决于备份策略 |
| Embedding 服务 | 是（纯计算） | 不必跨 Region 常备；故障时降级为关键词 / 元数据检索 | 召回分布改变 |
| 向量索引 | 是（依赖原件 + 固定模型版本） | 快照版本化 + 可重建；跨 Region 强同步需逐版本核验 | 重建耗时随语料规模增长，且占算力 |
| 生成段（LLM） | —（无状态服务） | 归 5.2.1：多副本 + 端点池 + 显式降级档位 | 降级后输出不可比 |

**这张表最重要的用法是「不要用同一套话术对四段下同一个决定」**。把四段放在一起看，就会得到一个与直觉相反的结论：**整条 RAG 链路里唯一「跨 Region 复制更划算」的候选，其实是原件**（它不可重算、按存储计价、且天然支持异步复制）；**其次划算的是索引快照**（体积小、可增量）；**最不划算的是让索引与源端保持强同步**——那等于为一个可以重算的产物持续支付一份跨区带宽。这条推导解释了为什么 RAG 的跨 Region 方案里，钱应该先花在原件与版本元数据上，而不是花在索引的实时同步上。

**GraphRAG 这类图谱增强检索（原稿 §5.2 的标题提到了这个方向，正文只展开了 RAG 的四条策略）是上表的加强版，不是新的一类问题**：它的索引除向量之外还包括实体-关系图与社区摘要，构建过程要跑一次全量抽取，因此**同样可重建、但更贵、且更依赖抽取与摘要所用模型的版本**（这一机制可按「GraphRAG」这一关键词检索其公开实现与论文自行核验）。结论不变，只是在两处更极端：**图索引比向量索引更不该走跨 Region 强同步**（体积与重建成本都更高），而**「版本可追溯 + 可重建」这条要求对它更硬**——抽取模型换了版本，重建出来的图谱与旧图不可比，表现为「恢复之后多跳问题的答案风格整体变了」。

#### 5.2.3 训练数据、主权分界与联邦学习：把法规划出的边界翻译成数据依赖

- **旧做法与它的卡点**：原清单写「数据主权：用户数据不出境（GDPR、个人信息保护法）」「跨 Region 训练：联邦学习，数据不动模型动」「跨 Region 数据同步 / 联邦特征库」。卡点是：**主权边界是一条否决性约束，不是性能参数**——§7.5 的阈值依据②已经把它排在所有性能判断之前；而清单把「联邦学习」写成应对它的通用办法，这会把一条本来清晰的合规约束变成一条技术选型题。
- **AI 改变了什么机制**：**它把「数据放哪」的问题变成了「模型去哪看见数据」的问题**。传统多 Region 里数据的主权边界只影响存储与复制；训练与微调让「模型要看见数据才能学到东西」成为硬依赖，于是**边界两边必须各自有一套能独立跑通的流水线**，而不是一条流水线跨区取数。
- **由此得到的**：**因为边界由法规划定、而业务切分由用户与租户决定，所以两张切分图可能不一致，必须显式维护并同时满足**（§7.6 组合 6 已给出这条组合的代价：跨边界只允许同步必要字段，通常要求业务侧做字段级裁剪与脱敏改造）；**因为联邦学习用通信换「数据不出境」，所以它省下的不是成本而是合规风险，代价是通信轮次、收敛速度，以及参与方必须在模型结构与训练目标上达成一致**。选它之前先回答一个更便宜的问题：**是不是本地建模 + 只交换聚合结果（甚至只交换非敏感统计量）就能满足要求？**
- **由此付出的**：**其一，按辖区分别建设与分别训练意味着重复的算力、重复的评估与重复的上线流程**，这份冗余不会出现在任何一张架构图的显眼位置上；**其二，跨 Region 特征同步引入「同一特征不同 Region 不同值」的静默不一致**，而它直接污染模型效果——这类问题表现为「效果莫名下降」，排查要从特征开始而不是从模型开始；**其三，双跑期与字段级裁剪改造是长尾成本**（迁移期间两套数据要可比对，见 §7.7）。
- **证据与来源**：边界本身可核验且可查原文——【公开】欧盟 GDPR，2018 年起施行（涉及跨境传输的章节），【公开】《中华人民共和国个人信息保护法》，2021 年起施行（涉及跨境提供的条款）；**具体合规判定请以当前有效的法规原文与本地监管要求为准**。联邦学习的机制有公开论文（【公开】McMahan et al., "Communication-Efficient Learning of Deep Networks from Decentralized Data", AISTATS 2017）；**跨辖区联邦学习的生产案例与收敛代价的可比数据本节未列出**，故判 L3。
- **成熟度**：**主权分界 L2**（判据②核不到：本节未列出第三方生产案例；且本行的①不是产品 release note 而是法规原文，说明它连产品级证据都不具备——**这两条都指向同一结论，不会因为边界可查就抬到 L1**）；**联邦学习 L3**。5.1 表里这两行的判据栏与本处按同一口径书写，评级逐条一致。

```text
主权边界的判定顺序（它是否决性约束，必须先于一切性能判断）
  第 1 步 列清单：逐个数据/字段回答"它能否离开辖区"
        ├─ 不许离开  → 该字段的数据面必须落在辖区内的 Region
        ├─ 允许离开  → 仍需核对：是否属于个人敏感信息、是否需单独同意
        └─ 不确定    → 按"不许离开"处理（默认从严，回头再放开）
  第 2 步 画两张图：
        业务切分图 = hash(user) → 单元          （§7.3.3）
        合规切分图 = 字段 → 允许的辖区
        ────────────────────────────────────────
        两张图不一致是常态，不是错误；错的是只画了一张
  第 3 步 处理不一致：跨边界只放行"必要字段"，
        通常要求业务侧做字段级裁剪与脱敏改造（§7.6 组合 6）
  第 4 步 复核训练与推理的依赖：
        模型要在辖区外"看见"这些数据吗？

        └─ 需要   → 再讨论是迁移模型、迁移计算，还是联邦式的交换

  ────────────────────────────────────────────────
  关键：把"联邦学习"当成第 1 步的答案，会把一条合规约束
```

#### 5.2.4 智能体跨 Region 调度与 AI 辅助决策：一个是有状态，一个是权限问题

- **旧做法与它的卡点**：原清单列了「Agent 跨 Region 部署」「Tool 跨 Region 路由」「状态同步」与三条 AI 辅助决策（流量调度 / 故障预测 / 成本优化）。卡点在于它把两类完全不同的问题写在了一起：**智能体是有状态的**——它跨多步持有会话状态、并且会调用产生副作用的工具（发消息、下单、扣款），而 §7.3.1 的写入拓扑与 §7.3.3 的归属规则决定「这份状态放哪」；**AI 辅助决策则卡在 §7.3.4**——「谁有权说这个 Region 挂了」是权限与责任问题，不是精度问题。
- **AI 改变了什么机制**：**智能体把「请求」变成了「有状态的会话」，于是把无状态服务多活这个容易问题，换成了会话归属（粘住某个 Region）问题**；AI 辅助决策试图把「故障判定与切流」从人换成统计判断——**这是两个机制变化，不是一个**。前者是真实的架构变化，后者目前只是把同一件事换了个前端。
- **由此得到的**：**因为会话有状态、工具调用有副作用，所以 Agent 跨 Region 的正确形状是「会话绑定单一 Region + 跨 Region 只做状态复制或可重放日志」，而不是「每一步都就近调度」**——就近调度会把会话撕成两半，副作用还可能被重复执行；**因为切流决策的瓶颈是责任归属，所以 AI 在当前阶段最现实的落点是「建议与验证」**（核对演练是否真达成 RPO / RTO、比对告警与变更记录），而不是自动切流。
- **由此付出的**：**其一，会话绑定会把「就近」的收益抹掉**——用户漫游到另一个 Region 后仍被粘回原 Region，延迟不降反升；**其二，副作用的不可重放性要求全程幂等键与去重**，而幂等设计是把复杂度从基础设施转移到了业务代码里，这笔账要算清楚再决定做不做；**其三，AI 辅助决策制造新的告警面与责任链**——预测性告警的误报会稀释真实告警的可信度，而「是模型建议切的」不能成为免责理由。
- **证据与来源**：会话状态的跨副本合并有公开论文可核验——Dynamo 用向量时钟处理购物车这类「始终可写」的会话数据，把并发版本一并返回给应用层（【公开】Dynamo, SOSP 2007；机制展开见 [§7.3.2](02-multi-region-section-7-sec7.md)）。**本节未列出智能体跨 Region 的公开生产案例，也未找到自动切流的误判率 / 漏报率公开评测**——这一栏的空白就是本方向判 L3 的依据。**缺失也是一种证据。**
- **成熟度**：**智能体跨 Region L3**；其中「会话绑定 + 幂等 + 可重放日志」这套**机制**属既有工程（L2），但它解决的是「不出错」，不是「就近调度」。**AI 辅助决策 L3**。判据：前者缺②且状态一致性无公开实测；后者缺②与量化指标。

判断「会话该不该跨 Region 调度」，有一个不需要读任何产品文档的检验动作：**问一句「这次工具调用如果被执行两次，业务上会怎样」**。答案是「无害」的（查询、渲染、检索）可以跨区重试；答案是「有影响」的（发通知、扣款、占库存）就必须先有幂等键才能谈跨区，而幂等键一旦引入，**会话归属就必须固定**——否则同一个会话的一次用户动作会在两个 Region 各生成一个幂等键，去重也就无从谈起。**这个检验动作的价值在于：它把「能不能就近调度」这个架构问题，还原成了一个业务语义问题。**

Agent 的两类内部状态必须分开处置，用同一套方案处理是常见的错误来源：

| 状态类型 | 例子 | 能否跨 Region 合并 | 处置方式 |
| --- | --- | --- | --- |
| 可交换、可归并 | 计数器、已读标记、标签集合 | 能（CRDT 形状，§7.3.2） | 允许多写者，合并即可 |
| 需按顺序解释 | 对话历史、任务步骤序列 | **不能**随意合并 | 会话绑定单区 + 复制整条序列 |
| 带外部副作用 | 已发的通知、已下的单、已扣的款 | 不能靠合并，只能靠幂等去重 | 幂等键 + 去重表；跨区重试前先查键 |
| 一次性令牌 / 锁 | 会话票据、分布式锁 | 不能合并 | 绑定单区；跨区重建，不做同步 |

**这张表回答的是「哪些状态可以漂」**：只有第一行可以自由跨 Region 合并，第二到第四行都要求会话有归属。**因此「智能体跨 Region 就近调度」这个提法在当前状态下只有第一行成立**——而对话历史恰恰是智能体最核心的那部分状态。

### 5.3 与本主题既有栈的接口在哪

「AI 时代的多 Region」不是与既有多活体系「结合」，而是**四类新对象各自挂到既有的哪一个环节上**。判断接得对不对，看三件事：**谁调用谁、数据以什么形态穿过边界、失败时谁负责**。下表每行的「现状」与 5.1 的级别逐条对应。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 推理服务 ↔ 多 Region 档位（[§3](02-multi-region-section-3-sec3.md)、[§7.3.3](02-multi-region-section-7-sec7.md)） | 无状态服务挂到既有就近路由之后；**路由的键是「服务 × 模型版本」** | 服务方保证副本可重建；SRE 负责摘除与切流决策 | 机制成熟，可直接排进路线图（L2，缺第三方实测） |
| 模型权重与向量索引 ↔ 制品与存储形态 | 制品以对象存储形态留存：权重 + 索引快照 + **Embedding 模型版本号**，三者必须同时可查 | 制品侧负责可重建与版本可追溯；恢复方承担重建耗时 | 「可重建」现在就能做（L2） |
| 会话状态 ↔ 归属规则与冲突解决（[§7.3.2 / §7.3.3](02-multi-region-section-7-sec7.md)） | 会话绑定单一 Region；跨 Region 只搬「可重放日志」或「可合并状态」（向量时钟 / CRDT 形状） | 会话所属单元的归属方；跨单元请求失败是可接受的 | 机制既有，智能体场景无公开实践（L3） |
| 数据主权 ↔ 合规边界（[§7.5 阈值依据②](02-multi-region-section-7-sec7.md)） | **硬约束，不参与加权**：命中即出局；据此维护「业务切分图」与「合规切分图」两张图 | 合规/法务定边界；业务方做字段级裁剪 | 可立即做，且应排在所有性能判断之前（L2） |
| 向量检索 ↔ 数据一致性（[Ch12 §08](../08-data-consistency/08-data-consistency.md)） | 索引与原件靠**重建**对齐，而非跨 Region 强同步；命中不到时降级为关键词 / 元数据检索 | 检索侧负责降级路径：**返回空优于返回过期结果** | 可立即实施（L2） |
| 特征与训练数据 ↔ 容量与调度（[Ch12 §04](../04-capacity-planning/04-capacity-planning.md)） | 按辖区分别建设流水线；跨区只同步必要字段与聚合结果 | 各辖区归属方；跨区特征不一致由特征 Owner 兜 | 分区建设可立即做，联邦学习待核验（L2 / L3） |
| AI 辅助决策 ↔ 演练与切流（[Ch12 §06](../06-chaos-engineering/06-chaos-engineering.md)、[Ch12 §07](../07-disaster-recovery/07-disaster-recovery-section-5-ai.md)） | **只读**监控与演练数据、**只写**建议与报告，不直连切流开关 | 人工确认者；AI 不承担切换责任 | 概念与产品公告期，不要在架构里预留假设（L3） |
| 边缘多 Region ↔ 流量调度（[§4.3](02-multi-region-section-4-sec4.md)） | 仍是 DNS / GSLB / 服务网格三层的既有形态；边缘只是把「就近」的半径缩小 | 调度层；边缘节点无状态、失败可摘除 | 既有能力的复用，与 AI 无关（L3，与 5.1 表同判） |
| 跨云多 Region ↔ 成本与可迁移性（[Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops-section-5-ai.md)） | 先把容器化与「避开厂商专属 API」做成常态；跨云复制与一致性无产品化公开解 | 尚无清晰责任人 | 只做准备，不作为容灾方案（L3） |

```text
四类新对象穿过边界的形态（谁把什么交给谁）
  推理服务 ──► 就近路由层 ──► 副本（Region A / B）
        └─ 交接物：请求 + 模型版本标记（不是"模型名"）
           失败：摘除端点，按显式降级档位处理
  检索侧 ──► 向量索引 / 原件（对象存储）
        └─ 交接物：Top-K + 元数据 + 原件引用
           失败：降级为关键词检索；返回空好于返回过期
  制品侧 ──► 权重 + 索引快照 + Embedding 模型版本号
        └─ 交接物：可重建的三件套（版本必须同时可查）
           失败：由恢复方承担重建耗时，而不是由查询方承担错误结果
  会话侧 ──► 归属单元（按用户哈希）
        └─ 交接物：会话状态 + 可重放日志 + 幂等键
           失败：跨单元请求失败可接受，重复副作用不可接受
  ────────────────────────────────────────────────
  共同点：把「失败时的降级形态」写进接口契约，
          而不是留给实现去猜——猜出来的降级形态无法演练、也无法审计
```

一句话概括这四条边界：**AI 没有新增调用关系，只新增了四件「必须同时可查」的交接物**——端点池里的模型版本标记、检索结果里的原件引用、制品三件套的版本号、会话侧的可重放日志与幂等键。多活做得好不好，看这四样东西在故障当天是否齐全，而不看有没有 AI 组件。

表里这九行有一个共同的失败形态：**接口接上了，责任人没接上**。跨 Region 的切换会把每一个模糊的责任归属都放大——平时「这个依赖归谁管」可以含糊，切流当天含糊就变成无人处置。因此每加一条边界的正确顺序是：先写明这条边的失败由谁负责，再谈怎么接；把负责方写成团队名而不是具体 Owner 的，等于没写，因为团队不会收到告警。**这也是 §7.6 那句「多数团队能稳定维护的组合不超过 2–3 件」在 AI 场景下的具体含义**——四类新对象会各自带进新的依赖边，而每一条边都要有人。

另一条要写进接口契约的东西是**「降级形态」本身**：检索侧返回空还是返回过期结果、生成侧降档还是明确失败、会话侧排队还是报错。这三处**必须由业务方签字**，因为它们决定「出错时用户看到什么」，而这从来不是基础设施能替业务做的决定——**能返回不等于答案正确**，这条判断在跨 Region 场景下比在单区内更贵，因为跨区链路本身会更早地触发降级。

### 5.4 公开进展与文献

分三类列，每条给出可核验的出处；**宁少勿假**，给不出处的不列。

**论文**

- Corbett et al., "Spanner: Google's Globally-Distributed Database", OSDI 2012——用 GPS + 原子钟把物理时间的不确定区间压到毫秒级，并用提交等待越过该区间；**同文也是「本地副本上 zero-RTT 读」这一机制的出处**。
- DeCandia et al., "Dynamo: Amazon's Highly Available Key-value Store", SOSP 2007——向量时钟与会话级合并（购物车），是「有状态会话跨副本」这条线的公开依据。
- Ongaro & Ousterhout, "In Search of an Understandable Consensus Algorithm (Raft)", USENIX ATC 2014——选主与日志复制，是自动切主可工程化的前提。
- Shapiro et al., "Conflict-free Replicated Data Types", SSS 2011——CRDT 的分类与合并性质（含 OR-Set 一类），是「哪些状态可以跨 Region 合并」的判据来源。
- Moraru et al., "There Is More Consensus in Egalitarian Parliaments (EPaxos)", SOSP 2013——无主共识的一条路线，说明「跨 Region 共识」不只有多数派这一种形状。
- McMahan et al., "Communication-Efficient Learning of Deep Networks from Decentralized Data", AISTATS 2017——联邦平均的原始方法，是「数据不动模型动」这条路的机制依据。

**法规与官方口径（可核验的判定入口）**

- 【公开】欧盟 GDPR，2018 年起施行——跨境传输相关章节；**具体判定以当前有效的法规原文与本地监管要求为准**。
- 【公开】《中华人民共和国个人信息保护法》，2021 年起施行——跨境提供相关条款；同前。
- 各云的区域与数据驻留（data residency）官方文档——**某区域是否满足某辖区的驻留要求，只能按该云当期文档核**，不要按产品页的宣传语推断。

**第三方生产案例**

- 说明：本方向下，本节**未列出**符合 5.1 判据②的公开案例——这与 5.1 表里没有任何一行进入 L1 是同一件事。**原有清单里以工业进展为名出现的条目（CockroachDB 24.x、OceanBase「AI 集群自动管理」、字节春晚红包、OpenAI 多 Region）多为厂商自述或建设方自述，按 5.1 的判据②不属于第三方生产案例**；原稿列在「学术进展」一栏的 TiDB 8.x 同样没有可引用的第三方生产案例。因此它们只作为判定入口出现，不作为成熟度证据。

**这份清单的用法**：它不是「读完就能上生产」的路径，而是一组**判定入口**。遇到任何「某产品支持跨 Region 某特性」的说法，先看它的证据属于上面哪一类——是论文里的机制、是官方文档里的正式条目、是法规原文，还是产品页上的一句能力描述；四者的成熟度差不止一个量级。**清单短不是资料少，是合格证据少。**

### 5.5 被过度宣传的部分

下面三条不是唱反调，而是把**被宣传的能力**与**公开证据支持的能力**分开写。判断标准固定：宣传句里有没有可核验的条件（数据规模、口径定义、是否付 RTT）——没有的，就归入下面三条。

**「Zero-RTT 跨 Region / 跨 Region 调用零延迟」**——实际存在的是**本地副本上的 zero-RTT 读**：Spanner 的只读事务可以在本地副本上完成，不付跨区往返，这是论文里就有的机制（【公开】Spanner, OSDI 2012）。原因：跨 Region 的**写**必须经过共识或复制，至少要付一个 RTT；把「读可以本地、写必须跨区」压缩成「跨 Region 零延迟」，等于把架构的关键约束抹掉了——§7.3.1 的「同城可同步、跨城不能」正是这条 RTT 的推论。**它什么时候才会成真**：物理距离不再决定往返时间，或者业务愿意把写路径也变成可异步归并的形状——后者是业务改造，不是网络升级。

**「联邦学习可以解决数据出境问题」**——实际只在特定条件下成立：参与方必须能就同一模型结构、同一训练目标、同一评测口径达成一致，且能承受通信与收敛代价；而**多数场景下有更简单的合规路径**（本地建模、只交换聚合结果或非敏感统计量、按辖区分别建设流水线）。原因：联邦学习把「数据集中」的代价换成了「通信轮次 + 收敛速度 + 跨参与方对齐」的代价，**它买卖的是合规风险，不是成本**。**它什么时候才会成真**：出现非厂商的、公开披露了通信开销与效果差距的跨辖区生产案例——只有机制论文不算，论文证明的是可行性，不是划算。

**「AI 自动选择 Region / 自动切流 / AI-Native Multi-Region」**——自动化能拿走的是「探测」与「执行」两段，**「决策」段的障碍是权限与责任，不是算法**。原因：一次误切的代价由业务承担，而在没有任何机制能让机器「负责」之前，没有人会把生产流量的切换权交出去；这条结论与 [Ch12 §07](../07-disaster-recovery/07-disaster-recovery-section-5-ai.md) 一致，不是本主题特有的。**它什么时候才会成真**：出现被审计体系接受的「自动切换误判率 / 误切次数」指标（即误切可以被追溯与归责），而不是只有「平均恢复时间缩短」的宣传口径。

这三条的共同结构是：**被宣传的能力都指向「跨 Region 不再是问题」，而公开证据支持的都只是「某些路径可以本地化」**。评审任何多 Region 方案时先问一句：**这条路径上，写要付几跳？** 答不出跳数的「零延迟」都是话术。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 「模型版本」会成为多 Region 路由的一等公民，「同版本部署」变成推理多活的默认验收项 | 主流推理网关 / 服务网格的路由文档里出现按模型版本分流与灰度的条目，并被非厂商的公开实践引用 | 三年后模型版本仍靠发布流程人工对齐，路由层不感知版本 |
| 向量索引的跨 Region 讨论会从「复制」转向「可重建」，判据变成重建耗时而不是同步延迟 | 向量库文档把「快照 / 恢复」与「跨集群复制」明确区分并给出耗时口径；公开工程文章开始用重建耗时做决策 | 行业仍以「支持跨 Region 复制」作为索引高可用的唯一卖点 |
| 智能体的多 Region 形状会收敛到「会话绑定 + 可重放日志 + 幂等」，而「每步就近调度」不会被采用 | 出现公开的会话归属与幂等键设计实践（会议分享或工程文章），且都强调状态粘性 | 出现大量宣称「智能体跨 Region 无状态调度」的架构，且不解释副作用去重 |
| AI 辅助的多 Region 决策会先在「演练验证」落地，而不是「自动切流」 | 出现自动比对演练结果与 RPO / RTO 目标的产品，并有第三方生产案例 | 产品宣传仍集中在自动决策切换，没有任何面向演练验证的模块 |

写这四条时的共同约定：**信号必须是外部可观察的**（出现在文档、release note、公开案例里），而不是「我觉得会」。凡写不出证伪信号的判断，本节不写——它没有信息量。

**这四条的用法是留痕，不是等**：把「会成真的信号」一列抄进架构评审模板，每次评审用一句「本季度是否观察到」过一遍。成本接近零，收益是信号真的出现时你手里已有一条写清了要改哪里的记录。反之，某条预测若连续四个季度只出现证伪信号，就把它从观察清单划掉——**可证伪的预测之所以有信息量，正是因为它允许被删掉。**

### 5.7 给架构师的行动建议

下表按「你的处境」分行，而不是按技术分行：同一项技术在已有单元化多活与刚起步的团队里，正确动作完全相反。

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有单元化多活 / 主区归属 | 把推理服务挂进既有档位：多副本 + 端点池 + **把模型版本纳入路由与灰度** | 观察线上是否出现过同版本不一致导致的答案差异 | **不要为推理服务单独设计一套多活**；不要在没有评估集时宣布「降级可用」 |
| 自建 RAG / 向量检索 | 原件 + Embedding 模型版本 + 索引快照三者一起版本化；演练里真的重建一次索引并记耗时 | 观察所用向量库 release note 是否出现跨集群复制条目及其一致性口径 | 不要为「索引跨 Region 强同步」提前买单；不要让 Embedding 服务用浮动版本引用 |
| 业务涉及跨境数据 | 把「不许跨越某条边界的数据/字段」列成清单，并同时维护业务切分图与合规切分图 | 观察监管要求与云方驻留声明是否变化 | 不要把主权边界当成一个可以和价格加权的因子；不要把联邦学习当默认答案 |
| 在做智能体 / 多步 Agent | 按「会话绑定单区 + 可重放日志 + 幂等键」设计；先确认副作用的可重放性 | 观察跨 Region 漫游用户的会话延迟是否显著变差 | 不要按「每步就近调度」设计；不要让工具调用在没有幂等键的情况下跨区重试 |
| 想上 AI 辅助切流 / 故障预测 | 只让它读监控与演练数据、写建议与报告；先积累「模型的建议对不对」的记录 | 观察是否出现厂商之外的、含误报率的公开数据 | 不要给它直连切流开关；不要让预测性告警稀释既有告警的可信度 |
| 受监管 / 金融类业务 | 把演练做成可举证的记录（谁在何时做了什么、达成什么指标） | 观察监管或行业规范是否开始要求「自动化切换的可追溯性」 | 不要把跨云当作合规到位的证明；不要让未演练的切流路径写进 SLA |

「明确不要做」这一列的共同逻辑是：**这些动作的代价是确定的（钱、复杂度、承诺），而收益依赖一个尚未成立的假设**（版本会自动对齐 / 索引可以秒级同步 / 模型能替你做切换决策）。等到 5.6 的信号出现再投入，损失的只是时间。

**如果你只能做一件事**：把下一次切流演练从「有没有切成功」改成量四个数。这四件事对「AI 多活」与「传统多活」同样成立，所以先量它们永远不亏：

1. **摘除一个 Region 后端点池的收敛时间**——推理多活的 RTO 下限（5.2.1）。
2. **切换期间返回内容的分布**：多少请求落到哪个降级档位、下游有没有把它当正常结果消费（5.2.1）。
3. **全量重建一次向量索引的耗时与占用算力**——决定要不要为跨 Region 复制买单（5.2.2）。
4. **跨区写占比 × 写 QPS**——§7.4 那条延迟税的输入；它决定「就近」能不能成立（5.2.1、§7.3.1）。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**多活的「对象」**——从前是数据与服务，现在多了四类：模型制品（有版本）、向量索引（可重建）、会话状态（有副作用）、训练数据（受主权约束）。它**没有**改变的是多活的全部原理：写入拓扑、冲突判定、归属规则、切流机制与成本函数（§7.3 的四条机制、§7.4 的成本函数）在 AI 负载面前一字未改。因此本节把「推理服务挂进既有档位 + 制品三件套版本化 + 会话绑定」排在所有 AI 特色能力之前，把「AI 自动调度与自动切流」排到最后。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是「有几类对象要跨 Region」，还是「跨 Region 这件事的物理约束」？** 前者是要处理的新工程量（版本、可重建、幂等），后者不存在——**光速没有升级**。
