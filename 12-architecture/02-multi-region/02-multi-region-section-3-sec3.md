## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

本节要讲的五个模式不是五个可以互换的选项。把它们压成一句话，分界线只有一条：**同一份数据在同一时刻允许几个写者。** Active-Passive 是单写者；Active-Active 是多写者；单元化多活是「多写者，但每个写者只写属于自己的那一份」；Global Database 是「多写者，冲突在存储层解决」；分层多活不是第五个答案，它是「上面这些机制按数据重要性分档使用」的组合方式。这条分界线与本章 [§ 7.1](02-multi-region-section-7-sec7.md) 列的第一条判据「写入拓扑」是同一件事，本节不做两套术语。

由这条分界线直接推出两件事：单写者族**根本不需要冲突解决**——冲突在结构上不可能发生，所以它的代价全部落在「谁能写」的切换窗口上；多写者族必须定义归属规则或冲突判定，代价落在数据切分、归并语义与跨区延迟上。于是「双活比主备高级」这个直觉在成本上是反的：你为多活付出的不是一份资源的差价，而是把自己从「不存在冲突」推进到「必须为每一类实体定义冲突规则」。

第二条约束是**数据可切分性**。多写者要成立，要么能用归属键（用户 / 租户 / 商家）把写路径切成互不重叠的片，要么能让冲突可归并（计数、集合、寄存器这类可交换类型）。切不动的那部分写——全局唯一编号、跨用户强事务、全局排行榜——只有两条出路：把整个系统退回单写者，或者交给把共识做进存储层的 Global Database。

第三条是**写延迟预算**：同步复制的每一跳都要多付一个往返，跨城在 10–30ms 量级【经验，行业普遍观测值，随城市对与骨干路径不同而异；主文件 §2.1 为同口径表述】。第四条是 **RTO / RPO 要求**，它决定切换是人工还是自动、备区是闲置还是承流量。第五条是访问模式（读多写少、读写均衡、还是就近读），它决定了只读副本能否解决大部分问题；第六条是团队能不能定期演练——**没演练过的切流路径，在真故障时本身就是二次故障源**。

这六条约束之间有一个容易踩的顺序问题：**先定故障域，再定写入拓扑与 RPO/RTO，最后才选技术档位。** 反过来的团队（先选技术、再倒推承诺）通常得到一份写着「RPO=0、RTO 五分钟」的制度文件，而落地的架构只覆盖了机房级故障——承诺与能力之间的缺口不会在日常暴露，只会在第一次真实故障里暴露。同理，把「多活」当成目标而不是手段，就会跳过「这批用户的数据能不能被切分」这一问，而这一问恰恰决定了多活能不能真的收敛影响面。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 写入拓扑（同一份数据允许几个写者） | 「冲突解决」这件事存不存在 | 「先选一致性模型再选架构」被推翻：单写者不需要一致性模型，多写者才需要 |
| 数据可切分性 | 多活能做到多宽、能不能做单元化 | 「多买一个 Region 就叫多活」被推翻：切不动的全局数据仍是单点，它决定真实的爆炸半径 |
| 写延迟预算 | 跨城同步能否进主链路、共识复制能不能用 | 「强一致只是个配置项」被推翻：它要先付一个跨城 RTT，且这笔账随写 QPS 放大 |
| RTO / RPO 要求 | 切换是人工还是自动、备区是闲置还是承流量 | 「有了自动切换 RTO 就短」被推翻：探测与决策两段不因自动化而变短 |
| 访问模式（读多写少 / 就近读 / 读写均衡） | 只读副本够不够、要不要真的多写 | 「多活一定优于主备」被推翻：读多写少的业务里，跨区只读副本能解决九成问题，成本是多活的零头【经验】 |
| 团队运维与演练能力 | 档位的上限 | 「架构选好了就安全」被推翻：切流路径的可信度来自演练次数，不来自设计文档 |

### 3.2 模式逐个拆解（核心节）

以下 5 个模式：Active-Passive、Active-Active、单元化多活、Global Database、分层多活。顺序按「写者从少到多、再按档位组合」排列——这个顺序本身就是它们的依赖关系：单元化的前提是先接受多写者，分层的每一层又是从上面四个里选一个。

另加 3.2.6 作为**补充分组**：主文件 §2.1 与本章 [§ 7.2](02-multi-region-section-7-sec7.md) 还在使用「同城双活 / 两地三中心 / 三地五中心」这三个名字，它们不是新机制，而是上面机制在不同距离档上的组合产物——但名字相近这件事本身会造成误判，所以单独用一节把「哪个名字属于哪个族」说清。

#### 3.2.1 Active-Passive（主备）

**被什么约束逼出来**：业务能接受分钟级的切换窗口，但**不愿为两地都承流量付冗余产能**；或者数据切不动、团队也没有多活的运维能力——约束是「保住数据」优先于「保住写在故障期间可用」。

**结构**：

```text
        写入                          复制方向单向
用户 ──► [Region A：主]  ──CDC / WAL ──►  [Region B：备]
            应用 + 主库                      应用（镜像或按需）+ 从库
                                                │
故障：  探测 ──► 决策（人工 / 半自动）──► 提升从库 + 切流（GSLB / DNS）
────────────────────────────────────────────────
关键：只有一个写入端点 →「同一份数据的两个版本」这个状态在结构上不存在
      所以冲突解决、向量时钟、CRDT 这些机制可以整个省掉
      代价全部落在「谁能写」的切换窗口上
```

**为什么这样设计有效**：因为写入只在一个端点发生，所以复制方向是单向的、任意两个版本之间永远存在全序——**「冲突」这个状态在结构上不可能出现**，于是多写者族那套归并机制（LWW / 向量时钟 / CRDT / 应用层裁决）在这里没有存在的必要性，维护面只剩复制链路与切换脚本两件东西。这正是它成为绝大多数系统的第一站的原因：不是因为便宜，而是因为它把一整类问题删掉了。

**代价**：① 备区资源闲置但持续计费，数据副本与跨区链路是常驻支出【经验，量级取决于数据量与 Region 数】；② RTO 由「探测 + 决策 + 切换」三段组成，其中决策段若需人工，方差最大且不可压缩；③ 写可用性绑在单一 Region 上，切换窗口内所有写失败；④ 备侧平时不承流量，配置、证书、权限、连接串会静默腐化，只有演练才能暴露。

**失效点**：当「不允许停写」成为硬要求时，「结构简单、不需要冲突解决」会反转成**写可用性是单点**，因为无冲突的前提正是一个写者——加副本提高的是数据的存活率，不是写的可用性；切换窗口内写请求无处可去，冗余再多也无处可去。

**真实使用**：AWS Well-Architected 可靠性支柱把灾难恢复策略分为四类（Backup & Restore / Pilot Light / Warm Standby / Multi-Site Active/Active），前三类都是单写者形态【公开，AWS Well-Architected Framework 可靠性支柱及其配套白皮书《Disaster Recovery of Workloads on AWS》；这是一份版本化的持续更新文档，档位不锁首发年份，四类策略的 RPO/RTO 区间以读者查阅到的当期版本为准，可按文件名在官方文档站自行核对】；业内另有一套按**能力等级**（数据级 / 应用级 / 业务级）而非架构名称划分灾备的说法，它也被用来给主备这一档定名【经验，业内分类口径的对照，不是某一份标准的等级命名；本章 [§ 7.5](02-multi-region-section-7-sec7.md) 的阈值依据② 已就此裁定口径，本节与之一致；主文件 §2.3 第 5 项沿用了这一俗称，宜按同一口径理解】。数据平台与内部系统多数落在这一档【经验】。

**上线前必须验证的一件事**：做一次真实的「停掉主 Region 入口、从备侧接管」演练，并记录三个数：数据缺口（差了多少条 / 多久）、切换耗时、对账发现的不一致条数。三个数缺任何一个，你的 RTO 与 RPO 就还只是文档承诺。

#### 3.2.2 Active-Active（双活）

**被什么约束逼出来**：要求「写不停」＋「用户就近」，且业务数据能按用户/实体切分、或冲突可按某种规则归并——约束是**多写者必须被允许**，而不是被容忍。

**结构**：

```text
        ┌──────────── 双向复制（异步 / 双向 CDC）────────────┐
[Region A] ◄──────────────────────────────────────────► [Region B]
 应用 + 主库                                            应用 + 主库
   两个 Region 都能接受写入（同一实体可能同时被两侧修改）
        │
        ▼
冲突解决（四选一，必须显式选出一种，没有「都不用」这个档）
  LWW（时间戳）    → 实现最省，语义损失最大
  向量时钟         → 能检测冲突；检测出来之后仍要人或应用裁决
  CRDT             → 只覆盖可交换可结合的类型（计数、集合、寄存器）
  应用层           → 冲突时抛错，由业务规则决定（订单状态、库存扣减）
────────────────────────────────────────────────
关键：多写者不是「多部署一个机房」，是「必须从上面四种里选一种」
```

**为什么这样设计有效**：因为两个 Region 都能接受对同一实体的写，所以「就近读」与「写不停」这两件事同时成立——这是它相对单写者唯一的、也是全部的收益。它换来的另一面是：**「同一份数据存在两个版本」从一个异常状态变成了常规状态**，于是归并语义第一次成为设计要求；单写者架构里那些「反正不会冲突」的假设（后写的必是新值、状态只能单向流转）在多写者下全部失效。

**代价**：① 每个可多写的实体都要有一条归并规则，规则数量随实体类型增长，且没有跨实体复用的办法；② 跨区复制链路升级为共享依赖，**复制延迟就是不一致窗口**，应用层必须能接受「刚写完可能读不到」；③ 两侧都要能承全量流量，冗余容量是常驻成本；④ 排障难度上升——同一条记录在两个 Region 的写入历史必须都能查到，否则无法复现冲突。

**失效点**：当同一实体被两个 Region 并发修改时，「就近且不停写」会反转成**静默覆盖或人工裁决**，因为 LWW 的判定依据是时间戳而不是业务语义——时钟漂移或写路径抖动会让「后到的旧版本」覆盖「先到的新版本」，而覆盖过程不产生任何错误日志，只能靠对账发现。

**真实使用**：Dynamo 论文把最终一致与 LWW 引入主流实践（SOSP 2007）【公开，Dynamo, SOSP 2007；主文件 §1.4 同口径】；逻辑时钟与因果关系可追到 Lamport 的经典论文【公开，Lamport, CACM 1978】；CRDT 的形式化定义出自 Shapiro 等【公开，Shapiro et al., SSS 2011】。产品侧：DynamoDB 全局表以多 Region 多写方式提供，同一项的并发写按最后写入者胜出（具体判定与边界请以官方文档当前版本为准）【公开，产品文档持续更新】；Cassandra 的冲突解决是按单元格时间戳取最后写入者（同一口径）【公开，官方文档】。判断一个系统是否真的多写，可自行核验：能否向两个 Region 同时写同一条记录，以及官方文档里有没有写明归并规则——写不出归并规则的产品，实际是单写者加只读副本。

**上线前必须验证的一件事**：在受控条件下**制造一次真实的并发写**——同一实体在两个 Region 几乎同时被改，然后观察最终留下的是哪一个版本、有没有留下任何痕迹（日志 / 冲突计数 / 对账差异）。看不到任何痕迹的，说明冲突是被静默覆盖的，这一类问题只能在生产对账时发现。

#### 3.2.3 单元化多活（Cell-Based）

**被什么约束逼出来**：要求**爆炸半径收敛**（一个 Region 故障不能影响全量用户），且数据能按用户标识水平切分——约束是「故障隔离要精确到一批用户，而不是精确到一个机房」。

**结构**：

```text
                     user_id（归属键）
                          │ 哈希
        ┌─────────────────┼─────────────────┐
     单元 1            单元 2            单元 3 …  ← 单元 = 应用 + 数据 + 配置的完整闭环
        │                 │                 │
    [Region A]        [Region B]        [Region A]  ← 单元分布在不同 Region
────────────────────────────────────────────────
三条纪律（缺一条，单元化就退化成「一个大锅分成几个格子」）
  ① 同一用户的全部请求固定落在同一单元（会话、缓存、定时任务都归本单元）
  ② 单元内不依赖别的单元即可完成一次完整业务
  ③ 不可切分的数据（全局唯一编号 / 跨用户强事务 / 全局榜单）单独列出
     —— 它们不进单元，它们是这套架构里唯一还带全局性的东西
```

**为什么这样设计有效**：因为一个用户的全部请求都由同一个单元处理、且该单元只用本单元资源就能完成业务，所以任意一个单元故障只影响属于它的那部分用户——**爆炸半径从 100% 收敛到约 1/单元数**。这一步是「部署了多个 Region」与「故障真的被隔离」之间必须跨过的门槛：Region 多不多是部署问题，单元闭不闭环是数据归属问题。

**代价**：① 数据归属规则是一份全局约束，上线后改动等于全量数据重分布，迁移成本以季度计【经验】；② 跨单元的那少量依赖（全局编号、跨用户转账）必须逐条单独设计，通常退化成异步补偿或幂等重试；③ 单元化中间件与流量调度多为自研或深度定制，没有开箱产品；④ 每增加一个单元，需要做容量、延迟与故障设计的两两路径数按 N(N-1) 增长——3 个单元与 10 个单元的运维复杂度不是线性关系。

**失效点**：当存在**未登记或无法切分的全局数据**时，「爆炸半径收敛」会反转成**故障重新全局化**——因为一条 T0 链路引用了一张全局单点的表，那张表的写者仍然是单点，它一停，所有单元都无法完成完整业务，单元数再多也救不回来。单元化的隔离上限，由这套架构里剩下的全局组件决定。

**真实使用**：阿里用用户维度的单元化把多机房故障的影响面压到单元级别，这条路线是分步推进的——2013 年先上线「两地三中心」，2015 年「异地多活」在双 11 首次大规模应用，2019 年才演进到「三地五中心」（时间线以主文件 [§ 1.4](02-multi-region.md) 为准；[§ 2.1](02-multi-region-section-6-sec6.md) 的案例把 2013–2024 这整个区间合并叙述，标题里的「三地五中心」是这条路线后期定型的形态，不是 2013 年的部署形态）【公开，转引本目录 [§ 2.1](02-multi-region-section-6-sec6.md) 案例，该案例标注的来源为阿里双 11 / 高可用主题公开材料（2013–2024），可按「阿里异地多活单元化」等关键词检索当期公开材料核验】；本章 [§ 01 单元化](../01-cell-based-architecture/01-cell-based-architecture.md) 讲的是同一机制的「逻辑切分」那一面，本节讲的是它作为多 Region 隔离手段的那一面。

**上线前必须验证的一件事**：把**一个单元**的入口整个摘掉，看属于这个单元的用户是否只受到影响面预期内的比例（而不是全站），以及其余单元有没有出现跨单元调用失败。做不到这一点的单元化，实际只是「按用户分库」，隔离并没有生效。

#### 3.2.4 Global Database 模式

**被什么约束逼出来**：存在**切不动**的写（跨用户强事务、全局唯一约束），业务又要求跨 Region 强一致，同时团队不愿或无力自研分布式事务与补偿逻辑——约束是「归属规则写不出来，但强一致仍然要」。

**结构**：

```sql
-- 「切不动」的那类写：跨用户强事务 + 全局唯一约束
BEGIN;
  INSERT INTO ledger(user_id, amount) VALUES (1001, -100);  -- 用户 1001 属单元 1
  INSERT INTO ledger(user_id, amount) VALUES (2002, +100);  -- 用户 2002 属单元 2
  UPDATE global_seq SET v = v + 1 WHERE name = 'order_no';  -- 全局唯一编号
COMMIT;   -- 三条语句跨了单元边界 → 单元化切不动，只能交给全局事务
```

```text
应用（任意 Region）──写──► 本地副本 ──► 共识复制（Paxos / Raft）
                              │
                     多数派副本确认 ──► 提交（commit-wait：越过时钟不确定区间）
                              │
                       提交结果 ──► 各 Region 副本按同一顺序应用
────────────────────────────────────────────────
关键：应用不感知「数据住在哪个 Region」——归属规则从应用层退到了存储层
      真正付出的代价是：每次跨 Region 写都要多等一轮共识 + 一跳 RTT
```

**为什么这样设计有效**：因为「按什么顺序提交」由存储层的共识与全局时间戳统一裁决，所以应用层不需要知道归属规则、也不需要自己实现补偿与去重——**跨 Region 的强一致从「应用工程」变成「数据库的一个属性」**。它替团队省掉的正是上面三个模式里最贵的那部分工作：归属键的设计、冲突规则的维护、跨单元事务的补偿代码。

**代价**：① 每次写都要付共识延迟，跨城一跳在 10–30ms 量级【经验，同 §3.1 口径】，把跨 Region 强一致的写挂在高频主链路上，会在途请求数与连接占用按写 QPS 线性放大；② 产品绑定——方言、事务边界、跨区读语义各不相同，离开时迁移成本高；③ 不是所有负载都该进去：海量日志与大宽表分析放进来通常不划算，它们是另一套系统的事；④ 运维需要理解共识与时钟基础设施，团队技能门槛高于前三个模式。

**失效点**：当写 QPS 高且写路径不能容忍额外延迟时，「应用无感 + 跨 Region 强一致」会反转成**写吞吐被共识延迟支配**，因为共识要求多数派确认，其延迟随 Region 间距与副本数增长，而同一分片上的写是串行提交的——**加副本提高的是可用性，不是写吞吐**，这个方向上的扩容是无效扩容。

**真实使用**：Google Spanner 用 TrueTime（GPS + 原子钟给出有界的时间不确定区间）配合提交等待实现外部一致性【公开，Spanner, OSDI 2012】；共识算法一侧 Raft 是公开的标准实现路径【公开，Raft, USENIX ATC 2014】；开源产品线 CockroachDB 1.0（2017）、TiDB 2.0（2018）、YugabyteDB 1.0（2018）【公开，主文件 §1.4 同口径】；金融级国产化场景常见 OceanBase（主文件 §2.3）。判断某个系统是否真的用了共识复制，一条可自行核验的办法是看它的写路径是否要求多数派确认、副本提升是否需要重新选举——不需要的，多半是单写者加只读副本。

**上线前必须验证的一件事**：在目标 Region 组合下**实测一次跨区写的延迟分布**（P50 与 P99，而不是平均值），并把它与「这批写最上游的接口超时预算」对照。跨区写延迟是常驻税，它不会随流量下降而消失，只会在流量上升时放大。

#### 3.2.5 分层多活（Tiered Multi-Region）

**被什么约束逼出来**：数据的可用性要求分布极不均匀（少数 T0 不能停，大量 T3 停一天可接受），而预算是一条硬约束——把最高档形态套到全部数据上，成本与写延迟会同时失控。

**结构**：

```text
        数据分级（依据：停多久会伤到业务，而不是数据量大小）
T0 交易主链路   → 单元化多活 / 同城双活        RPO ≈ 0，RTO 秒级
T1 关键业务库   → 同城双活                     RPO ≈ 0，RTO 分钟级
T2 分析 / 明细  → 温备（数据面常驻、应用按需）  RPO 分钟级，RTO 小时级
T3 归档 / 冷数据 → 备份 + 时间点恢复            RPO 小时级，RTO 天级
────────────────────────────────────────────────
关键：分层是一张「数据 → 档位」的登记表，它必须有人维护，并且与真实依赖关系一致
      （档位口径沿用业内常见的灾备能力等级对照，量级以自身 RTO/RPO 目标为准）
      一张 T3 表被 T0 链路引用 → 这条链路的实际 RTO 就是 T3 那一档的
```

**为什么这样设计有效**：因为每一层只承担本层数据声明的可用性目标，预算被花在真正不能停的数据上，而不是平摊到全部数据——**这是 T0 那部分买得起最高档的前提**。反过来看，「所有数据都按 RPO=0」这种要求会同时把成本和写延迟推到不可控的位置【经验，与 [§ 07 容灾 §6](../07-disaster-recovery/07-disaster-recovery-section-6-sec6.md) 案例的结论方向一致】。

**代价**：① 需要维护一张「表 → 层 → Owner」的登记表，它本身会过期，而且过期不报错；② 分层让跨层调用成为最危险的依赖（上层被下层拖累），需要额外的依赖检查；③ 演练也必须分层做，全覆盖演练的成本随层数与层内数据量增长，多数团队做不到每次全跑；④ 分层的依据是「业务影响」而非「数据特征」，这要求数据 Owner 真的理解自己的数据在业务里的位置，成本落在组织协调上而不在技术上。

**失效点**：当存在**未登记的跨层依赖**时，「按重要性分配预算」会反转成**实际容灾等级由最弱的一层决定**，因为 RTO 与 RPO 沿依赖链取的是最差的一环，而分层表只登记了数据自己的档位，没有登记「谁依赖它」——一次跨层引用就会让 T0 的承诺降到 T3 的水平，且这个降低在事故前不可见。

**真实使用**：分级 RPO / RTO 是金融与政企的常规做法，业内通行的灾备能力等级口径（数据级 / 应用级 / 业务级）正是按「每一档对应一组 RPO/RTO 承诺」组织的——它是分类口径的对照，不是某一份标准的等级命名（本章 [§ 7.5](02-multi-region-section-7-sec7.md) 的阈值依据② 已就此裁定口径，本节与之一致）【经验，业内分类口径；具体档位数值请按当前有效的标准原文与本地监管要求核验】；[§ 07 容灾 §6](../07-disaster-recovery/07-disaster-recovery-section-6-sec6.md) 记录的两处落地——「容灾分级、成本与价值匹配」与「把零丢失的成本压在关键数据上」——是同一机制的两个样本【公开，转引 [§ 07 容灾 §6](../07-disaster-recovery/07-disaster-recovery-section-6-sec6.md) 案例】。

**上线前必须验证的一件事**：随便挑一条 T0 链路，顺着依赖往上追到最底一层，看最底那层的数据属于哪一档。**这条链路的实际容灾等级，等于它依赖的最弱一档**——分层表的承诺不会自动传导到链路上。

#### 3.2.6 补充分组：同城双活 / 两地三中心 / 三地五中心（名字相近，分族不同）

**被什么约束逼出来**：主文件 §2.1 与本章 §7.2 都用这三个名字描述架构形态，而它们**在写入拓扑上并不属于同一族**——把它们当成「多活的三个强度档」来做技术选型，会在「多写者」与「单写者」之间静默地跳一次族：名字里的「双活」最容易被读成「必须为每一类实体准备归属键与归并规则」，而同城同步复制/共识一次只有一个提交者，这两样东西它都不需要。

**结构**：

```text
           距离与故障域              写入拓扑                            归入本节的哪个模式
──────────────────────────────────────────────────────────────────────────────────────
同城双活     两机房同城（几十公里）    同城同步复制/共识（单写者语义）       ≈ 3.2.1 主备的同城形态（两机房都承读）
两地三中心   同城两中心 + 异地一中心   单写者（异地只保数据）                ≈ 3.2.1 主备 + 异地副本
三地五中心   三城五中心                多写者 + 单元闭环                     ≈ 3.2.3 单元化，Region 数更多
──────────────────────────────────────────────────────────────────────────────────────
关键：名字里的「几地几中心」描述的是**故障域的形状**，
      不描述**写者拓扑**——后者才是决定代价的那一条
      「同城双活」的双写变体（两机房各自接受对同一份数据的写）才归 3.2.2，那时必须补归并规则
```

**为什么这样设计有效**：分开这两件事之后，「三地五中心」与「两地三中心」的差别就从「档位高低」变成了一条可判定的问题——**异地中心是承写还是只保数据**。承写则要处理多写者那一整套（归属键、归并规则、单元闭环），只保数据则仍是单写者的切换窗口问题。前两行的差别同样不是档位，而是**同城那一跳是同步复制/共识还是异步**：同城同步复制/共识只付一跳同城往返（RTT 1–3ms 量级【经验】），所以写端唯一且 RPO≈0；跨城异步只保数据，切换时按复制延迟丢一个窗口。把名字的复杂度与机制的复杂度分开，选型就不必再靠记忆档位表。

**代价**：① 这套对应关系本身需要解释——同一个机房数量可以被组织成单写者形态，也可以被组织成多写者形态，团队里不同人对同一个名字的理解可能不同；② 名称为沟通服务，改名的成本高于改架构的成本，所以只能靠文档固化口径（本节与 §7.2 在「两地三中心 = 单写者、三地五中心 = 多写者」上口径一致；只有同城双活要先问建的是哪一支，见上表第一行）；③ 单元数、Region 数与「是否真跨城」三个量必须同时说清，否则同一名词在不同规模下不是同一件事。

**失效点**：当团队**按名字而不是按写入拓扑**做评审时，「把名字的复杂度与机制的复杂度分开」这个做法会反转成**同一次评审里两套口径并存**，因为分族只写在文档里，而名字跟着人在流动——新成员按字面把「两地三中心」理解为「两个地方」，就会把异地中心也当成承写的一方去设计，等到要写同步复制时才与约束冲突。判别信号很具体：同一次架构评审里，两个人用同一个名字指代了不同的写入拓扑。

**真实使用**：业内在描述灾备要求时，常按能力等级（数据级 / 应用级 / 业务级）而不是架构名称来分档，这种用法的一个好处是避开「按名字比高低」这类失真；但它只是分类口径的对照，不是某一份标准的等级命名——本章 [§ 7.5](02-multi-region-section-7-sec7.md) 的阈值依据② 已就此裁定口径，本节的用法与之一致，合规场景请按当前有效的标准原文与本地监管要求核验【经验，业内分类口径】；本目录 [§6](02-multi-region-section-6-sec6.md) 的四个案例各自用不同名字描述自己的架构，判断它们真正属于哪一族，可按「异地中心是否承写」这一条自行核对。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 金融核心交易：跨用户强事务、数据不可切分 | 同城双活 + 跨城异步（同城同步复制/共识，写端唯一） | 不把 Global DB 当默认底座：共识延迟随写 QPS 放大，而多数场景只有同一个城市的写需要强一致 | 强一致是否真的必需，还是「没想清楚所以全要」 |
| 电商交易：交易与用户行为可按用户键切分 | 单元化多活 + 少量全局组件 | 不选纯 Active-Active：两个 Region 都能写同一张订单表时，爆炸半径仍是 100% | 能否用归属键把写路径切成互不重叠的片 |
| 社交 / 内容：多写，冲突可归并 | Active-Active + 最终一致 | 不为可归并的计数与关系维护归属规则，收益低于成本 | 冲突能否用计数 / 集合 / 寄存器这类可交换类型表达 |
| 数据分析：读多写少、延迟不敏感 | Active-Passive + 跨 Region 只读副本 | 不选多活：分析链路不需要写可用性，多活只为它增加冲突面与双份运维 | 写路径是否只有一条（加载与调度） |
| AI 推理服务：延迟敏感、状态外置 | 单元化 / 主区归属 + 跨 Region 调度 | 不选 Global DB 作为推理底座：推理的一致性需求在特征与向量副本上，不在事务上 | 推理请求是否无状态、能否按用户键路由 |
| 全球化业务：跨大洲强一致 | Global Database（只放必需的表） | 不选裸 Active-Active：跨大洲的冲突判定与修复成本高于把强一致交给存储层 | 跨大洲的强一致是业务要求还是架构偏好 |
| 内部系统 / 成本敏感 | Active-Passive（或单 Region + 异地备份） | 不选多活：可用性目标本身没到需要多活的量级【经验】 | 目标可用性与一次停机的代价是否被算过 |

这张表的用法与 §7.1 的六条判据一致：**先看可行性，再看档位，最后做减法**。第一列里的「能否切分」「是否可归并」属于可行性——不满足就直接出局，不能用「成本更低」「团队更熟」去抵消；「数据不可切分」这一行之所以推荐单写者而不是 Global DB，是因为多数金融核心链路的强一致写集中在同一个城市，把它们放进跨城共识里是在为一个不存在的需求付延迟（这里的「单写者」指同城双活里的同城同步复制/共识：写端唯一，所以它既不需要归属键，也不需要归并规则——3.1 说的「切不动的写只有两条出路」，它走的是其中的第一条）。反过来，最后一列才是真正要在评审会上被回答的问题：**你的强一致是业务要求，还是「没想清楚所以全要」**。

**本主题下最常被误选的一对，是 Active-Active（双活）与单元化多活。** 两者都叫「多活」，都在两个 Region 放应用与数据，于是最容易被当成同一件事的程度差别——但它们回答的是两个不同的问题：**双活回答「写能不能在两个地方发生」，单元化回答「一个地方出事时影响多少人」**。误选形态一：按双活部署（两个 Region 都能写），却没有定义归属键，跨区调用照样存在、爆炸半径仍是 100%，你付了两份资源的钱，只买到「读就近」；误选形态二：先做了单元化切分，却在单元之外留了一张谁都能写的全局表，切分买到的隔离被这一张表抵消。两种误选的后果不同：前者是成本花了、可靠性没升；后者是隔离做了一半，故障时的表现与没做几乎一样。判断只用问一句：故障发生时，用户会不会被自动路由到他数据所在的那个单元之外？

**偏好无法被复核，机制可以**。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：单元化多活 + Global Database（可切分的进单元，切不动的进全局库）。** 职责边界：单元负责「归属确定」的那部分实体（订单、用户、商家），全局库只负责全局唯一编号与跨用户强事务这两类写；**哪张表放哪边必须有一份登记**，否则第二类会悄悄长回应用层去。运维代价：两套存储、两套一致性语义同时存在，团队要同时理解「单元内可以本地读」与「全局库要付共识延迟」两种心算模型。适合规模：多 Region 多写、但存在少量不可切分全局约束的交易类业务（电商、支付）。

**组合 B：同城双活 + 跨城异步灾备（两地三中心的现代形态）。** 职责边界：同城负责 RPO≈0 与机房级 RTO（写路径上的同步只发生在同城），跨城负责 Region 级的数据保底（异步，不进写路径），切流负责把用户从故障 Region 挪走。运维代价：跨城链路与备中心环境常驻，但平时不承流量——**这份「闲置但必须能起来」的能力只能靠定期演练维护**，它不产生日常收益，因此在预算紧张时最先被砍。适合规模：服务范围集中在一个国家、预算有限但需要跨城数据保底的业务。

**组合 C：Active-Passive + 跨 Region 只读副本 + 定期真实切流演练。** 职责边界：只读副本管读延迟与就近访问，主 Region 管全部写，演练管「切流路径到底能不能用」。运维代价：写仍是单点（这是设计选择，不是缺陷），所以切流路径必须常练，且要处理复制延迟导致的「刚写读不到」；读副本的一致性与会话语义需要显式设计。适合规模：读多写少、延迟不敏感的系统——数据平台、内部系统、内容分发类业务【经验】。

三个组合有一个共同的边界：**它们都不是「模式叠加」，而是「职责划分」**。判断一个组合是否成立，不看它包含几个模式，而看每类写是否只有一处归属、每类数据是否只有一个档位承诺。凡是出现「这条链路到底由谁负责写」「这张表到底算哪一档」说不清的地方，组合就已经失效了——而这类失效在平时不报错，只在切换或对账时才显形。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「多 Region 即可抗灾」 | 部署图上有几个 Region，但说不出共享依赖有哪些；演练记录里找不到一次完整切流 | 共享依赖（控制面、DNS、密钥、专线汇聚点、配置下发）没隔离 ⇒ 两个 Region 属于同一个故障域，副本数增加了而可用性没变 | 部署图上确实多了几个框，而故障域的边界不在部署图上，在依赖清单里 | 先列共享依赖清单、圈出真实故障域，再定档位与 Region 数 |
| 跨 Region 强同步 | 用 2PC 或同步复制让跨城写等远端确认 | 每次写至少多付一跳跨城 RTT（10–30ms 量级【经验】）；写 QPS 高时在途请求与连接占用成倍上涨，任一 Region 抖动直接变成写失败 | 把「RPO=0」当成可以勾选的配置项，而不是一个选址与数据模型问题 | 只有低频且不可丢的写走跨区同步；高频可归并的写走异步与合并 |
| 忽视冲突解决 | 两个 Region 都能写同一实体，但没人能说出归并规则是什么 | 并发写被按时间戳静默覆盖，覆盖不产生错误日志；对账时才发现差异，且无法判断哪边是对的 | 冲突在测试环境里几乎不发生（测试流量不会同时在两地写同一实体），「没遇到」被当成「不存在」 | 为每个可多写实体显式选一种归并策略（LWW / 向量时钟 / CRDT / 应用层）并写进设计文档 |
| DNS 切流忽视 TTL | 故障时才切 DNS，且记录 TTL 是分钟或小时级【经验】 | 切流时间被 TTL 与递归解析器缓存拖长，RTO 承诺失效；已有长连接与连接池不会因 DNS 变化立刻重连 | 切流路径平时不用，参数就没人复核；TTL 只被当性能参数看待 | 核心业务把 TTL 压到秒级并配 GSLB，把「切一次再切回来」纳入常规演练 |
| 单 Region 写多 Region 读 | 全部写走 Region A，B/C 只读，写入侧没有分片 | 写者仍是单点，写压力与写故障域都没有改善；跨区读还要处理复制延迟导致的「刚写读不到」 | 把「部署到多个 Region」直接等同于多活，于是先铺读、写留着以后再说 | 按归属键分片写入；若确实切不动，就承认这是 Active-Passive，按单写者架构设计并演练切换窗口 |
| 忽视跨 Region 带宽成本 | 跨区同步是全量还是增量说不清；账单里跨区流量项逐月上涨且无人负责 | 跨区流量是常驻支出，随数据量与副本数增长；带宽打满会反过来拖慢复制延迟，把不一致窗口拉长 | 带宽被当成「网络部门的事」，不进架构评审与成本模型 | 压缩与增量优先、按需同步、对大表复制做采样与限速，把跨区流量纳入容量规划 |

**「多 Region 即可抗灾」在生产中的典型暴露方式**：它不在日常暴露，而在**第一次真实故障**里一次性暴露——故障发生时，流量确实切到了另一个 Region，但监控、密钥、配置中心、镜像仓库里的某一个还在原 Region，于是备侧起来的服务连不上依赖，RTO 由「云厂商修复共享依赖」的时间决定，而不是由你的切换到备用 Region 的脚本决定。可核验的判别信号：把主 Region 的入口完全摘掉之后，备 Region 能否在没有任何原 Region 依赖的前提下跑完一轮完整业务。

**「跨 Region 强同步」在生产中的典型暴露方式**：它表现为**写延迟的持续抬升，而不是一次性的故障**。跨城往返变成每次写都要付的固定税，写 QPS 上升时在途请求数按同一倍率增长，连接池被占满，尾延迟先恶化、平均值后恶化；团队通常先去查数据库与慢查询，而真正的开销在写路径上的那次跨城确认。判别信号：把跨区同步关掉（改异步）后写 P99 立刻回到本地水平——能这样翻转的，说明延迟的来源就是这个反模式，而不是数据库本身。

**「忽视冲突解决」在生产中的典型暴露方式**：它**只有在对账时才暴露，而且暴露时已经无法判责**。两个 Region 各自认为自己写成功了，覆盖发生在复制层，两边日志里都是成功的写；等到对账发现差异时，最需要的那个信息——「这两个版本哪个的业务时间戳更晚」——通常没有被记录，因为当时的设计假设是不需要它。判别信号：抽一条被两侧都改过的记录，能否还原出两侧的写入顺序；还原不出来的，归并规则实际上不存在。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：**规模或访问模式跨过某个阈值后，原来正确的模式会变成错的**，而它不报错——它表现为成本曲线变陡、尾延迟变差、或者某一次故障的影响面远超预期。下表六条跃迁里，共同点是迁移成本都不在工具上，而在数据归属规则与存量演练上。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单机房 → 两个机房 | 单 Region | 机房级故障即全站不可用，而写延迟预算还够承担同城同步 | 同城双活（同城同步复制） | 应用无状态化改造（会话外置、定时任务去重、本地缓存失效），跨多个团队，以季度计【经验】 |
| 同城双活 → 跨城 | 同城双活 | 城市级事件（断电、城域链路中断）会同时打掉两个机房 | 同城双活 + 跨城异步灾备 | 跨城链路与备中心环境常驻成本；备侧平时不承流量，只能靠演练维持可用性 |
| 主备 → 双活 | Active-Passive | 「不允许停写」变成硬要求，分钟级切换窗口不可接受 | Active-Active（先定义归并规则） | 每个可多写实体都要一条归并规则；应用要能接受「刚写完可能读不到」 |
| 双活 → 单元化 | Active-Active | 两个 Region 都能写之后，爆炸半径仍是 100%，跨区调用随业务增长 | 单元化多活 | 数据归属规则一次定死，改动等于全量数据重分布，以季度计【经验】 |
| 自研归并 → Global Database | 应用层 LWW / 补偿逻辑 | 归并规则越攒越多，每加一类实体就加一条，且无法复用 | 把需要强一致的表收进全局库 | 产品绑定与方言适配；已有表迁移与事务边界重划，还要接受共识延迟 |
| 单档 → 分层 | 全部数据按最高档做 | 预算撑不住；或者反过来，T3 数据被 T0 链路依赖，承诺悄悄降低 | 分层多活 + 依赖登记与检查 | 维护「表 → 层 → Owner」登记表与跨层依赖检查，登记表会过期且过期不报错 |

六条里，四条是随着可用性要求提高而**向上迁移**（单机房 → 两个机房、主备 → 双活、双活 → 单元化、单档 → 分层），另外两条不是升档而是**换实现路径**（同城双活 → 跨城；自研归并 → Global Database）。向上的迁移要付的是应用改造与归并规则的代价，换路径要付的是数据归属与登记表的代价；两者共同的规律是：**先到的那一步决定了后一步有多难**——先在双活里定义归属键，将来做单元化只是把归属键的粒度调细；先做双活而不定义归属键，将来做单元化等于重新分配全部存量数据。

### 3.7 自检清单

以下 12 条按「先定约束、再定机制、最后定验证」排列：第 1–3 条查写入拓扑与切分性（可行性），第 4–6 条查机制选择，第 7–9 条查代价是否被正视，第 10–12 条查切流路径是否真的可用。

- [ ] 能否一句话说清「同一份数据在同一时刻允许几个写者」？说不清的，说明还没定档位。
- [ ] 每个可多写的实体，是否都有一条写明了的归并规则（LWW / 向量时钟 / CRDT / 应用层）？写不出来的即视为「忽视冲突解决」。
- [ ] 不可切分的全局数据（全局唯一编号、跨用户强事务、全局榜单）是否被逐条列出、并指定了归属？没列出的，爆炸半径由它们决定。
- [ ] 写路径上是否存在跨城同步确认？若有，它服务的是不是「低频且不可丢」的那类写？
- [ ] 跨区复制是异步还是同步、方向是单向还是双向？这三个参数有没有写进设计文档并被下游系统知道？
- [ ] 若用了 Global DB：是否算过「跨区写 QPS × 共识延迟」这笔在途开销？有没有把大表分析类负载也塞了进去？
- [ ] 备侧 Region 平时是否闲置？闲置的配置、证书、权限、连接串，最近一次复核是什么时候？
- [ ] 是否存在跨层依赖（T0 链路引用 T2/T3 数据）？查一次全量配置而不是抽查。
- [ ] 跨区流量是否进入了成本模型，还是只出现在账单里？全量与增量是否区分过？
- [ ] 最近一次真实切流演练是什么时候（不是流程演练，是把流量切走再切回来）？实测 RTO 与承诺值差多少？
- [ ] 摘掉主 Region 的入口后，备 Region 能否在完全不依赖原 Region 的前提下跑完一轮完整业务？
- [ ] 共享依赖清单（控制面、DNS、密钥、专线汇聚点、配置下发）是否被逐条核对过隔离状态？

### 3.8 小结

下表把本节五个模式（加一个补充分组）按「你的约束 → 建议模式 → 机制理由」重述一遍，约束取自 3.3 决策表的七类场景、3.4 的三个组合，以及 3.2.5 的分层约束（分层多活本身不在 3.3 与 3.4 里），去重后合并同类项。**表内一行不等于 3.3 的一行**：首行把「数据不可切分」与「能接受分钟级切换窗口」两条一起写进了约束，所以落到 Active-Passive + 跨区只读副本；而 3.3 金融核心交易那一行的约束里没有「能接受分钟级切换窗口」，因此它落在同城双活上——两行的差别只在这半条约束。不在表内的约束组合，回到 3.3 用同样两步筛（先可行性、再档位）。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 数据不可切分、能接受分钟级切换窗口 | Active-Passive + 跨区只读副本 | 单写者让「冲突」这个状态在结构上不存在，等于删掉一整类问题 |
| 读多写少、延迟不敏感 | Active-Passive + 跨 Region 只读副本 + 切流演练 | 只读副本解决读延迟，多活解决的是写可用性——你不需要后者的那份代价【经验】，但切换窗口仍要演练 |
| 要求写不停，且冲突可归并 | Active-Active + 显式归并规则 | 多写者换来就近与不停写，代价是每一类实体都要有归并语义 |
| 要求故障影响面收敛到一批用户 | 单元化多活（+ 全局数据单独登记） | 单元闭环让爆炸半径变成约 1/单元数，这是「部署多个 Region」跨不到的那一步 |
| 存在跨用户强事务、又要跨 Region 强一致 | Global Database（只放必需的表） | 把归属与顺序判定退到存储层，应用无感；代价是每次写付共识延迟 |
| 数据的可用性要求高度不均、预算有限 | 分层多活 + 依赖登记 | 按重要性分配预算，才买得起 T0 那一档；前提是跨层依赖可查 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**「同一份数据在同一时刻允许几个写者」**——它决定冲突解决这件事存不存在，也决定其余所有代价落在哪里（单写者落在切换窗口，多写者落在归并语义与跨区延迟）。第二条是数据可切分性，它决定多活能做到多宽、以及爆炸半径的下限；第三条是团队能不能定期演练，它决定前面两条在真故障时是否成立。三者是串联的：写者拓扑选错，切分再精细也改不了爆炸半径；切分没做，档位再高也只是多买了几份副本。
>
> 💡 **思考锚点**：用 3.7 的自检回算你自己的系统——把流量真实切走再切回来，实测 RTO 与你在 3.3 决策表里承诺的那一档差多少？再把单元数代进「爆炸半径约 1/单元数」，看你这套模式真能把一次故障收敛到那批用户，还是只多买了几份副本。
