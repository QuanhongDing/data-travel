## 7. 与其他方法对比

> 原 § 7 共 42 行、为 6 维打分表 + 两条决策树，缺少机制解释与可溯源证据，重写为 ~300 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

原文件把「单 Region / 同城双活 / 两地三中心 / 异地多活 / Global DB」放在一张表里，对「可用性 / 用户体验 / 数据一致性 / 成本 / 复杂度 / AI 友好度」六个维度逐格打 1–5 分，表末另给一行「综合推荐度」星级。问题不在于分数不准，而在于**打分把随场景翻转的结论写成了绝对结论**：同一个「一致性」维度，在账务场景是加分项、在商品详情页是扣分项；同一个「复杂度」维度，对 3 人团队是致命项、对有 200 人 SRE 的组织几乎不计。

更糟的是，这类表隐含了一个错误因果：它把「可用性 99.99%」写成选两地三中心的**理由**，但真实关系是反的——**可用性目标是对「能接受多长不可用」的业务表达，架构形态是达成它的手段**，两者之间还隔着「爆炸半径、RPO、切流时间、跨区依赖」这些中间变量。跳过中间变量，选型就退化成记忆题。

**另外两个被这张表掩盖的事实**：其一，候选方案不是互斥的，真实系统多是「单元化多活 + 主区归属 + 若干全局强一致组件」的混合；其二，跨 Region 的代价大头不是带宽而是**延迟**与**冗余容量**——多活要求每个 Region 都能接管故障 Region 的流量，这份冗余是必须预留的闲置成本，打分表里那个「成本 2 分」根本没告诉你要为它付多少。

**原打分表的三类具体错误**：

| 原表写法 | 错在哪 | 应该怎么写 |
| --- | --- | --- |
| 「数据一致性：单 Region 5 分 / 异地多活 3 分」 | 没说是哪一种一致性（线性一致 / 会话语义 / 最终一致），也没问「这批数据能否异步」 | 「这批数据的写是否可归并；不可归并的实体必须绑单写者」 |
| 「成本：异地多活 2 分」 | 没给出成本函数，2 分对应多少钱、随什么增长，读者无从判断 | 「常驻资源 × Region 数 + 可接管冗余 + 跨区流量」并给量级 |
| 「综合推荐度：异地多活 ★★★★★」 | 这一行的星级并不由上面各列分数导出（各列求和与这组星级不成同序），读者无从知道它按什么算出；而各维度权重随场景翻转，单一排序无法同时对账务与商品详情页成立 | 「在你的写者拓扑与可切分性约束下，唯一可行的是哪一档」 |

**除此之外，原打分表没有把「迁移」列为维度之一**。选型不是一次性的：单 Region → 单元化多活要改数据归属规则，这是全量数据重分布；异地多活 → Global DB 要改事务边界与方言。把「换成另一个要动什么」放进判据，很多看起来更优的方案会立刻失去吸引力（见 7.7 的迁移成本表）。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 写入拓扑 | 同一份数据能否同时有多个写者 | 多写者必然要解决冲突；单写者必定有切换窗口。这是所有约束的源头 |
| 一致性预算 | 单次写能容忍多少额外延迟 | 同步跨 Region 每跳要付一个 RTT，跨城 10–30ms 量级（【经验】）；写延迟预算直接决定「跨城同步复制」能否进入主链路 |
| 爆炸半径 | 一个 Region 故障影响多少用户/请求 | 只有「数据本地闭环 + 流量可切」才能把影响面从 100% 收敛到 1/单元数 |
| 数据可切分性 | 业务数据能否按用户/租户水平切分 | 能切分 → 单元化多活可行；不能切分（全局唯一编号、跨用户强事务）→ 只能退回单写者或 Global DB |
| 运维与演练能力 | 有没有人能定期演练切流 | 没有演练过的切流路径，在真故障时本身就是二次故障源。这是多活能否落地的组织前提 |
| 演进与锁定 | 离开某方案要付出什么 | 单元边界、数据归属规则一旦上线就极难改动，迁移成本以季度计 |

**判据的使用方式**：这六条不是加权求和，而是**顺序筛选**——先看「写入拓扑」与「可切分性」（这两条是可行性，不满足就直接出局），再看「一致性预算」与「爆炸半径」（这两条决定档位），最后用「运维与演练能力」「演进与锁定」做减法（这两条常常否掉技术上更优的方案）。**把可行性判据放在权重判据之前，是本框架与原打分表最本质的区别**：打分表允许「可用性 2 分 + 成本 5 分」互相抵消（原表里单 Region 正是这一格组合），而现实中复杂度往往是一票否决。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 单 Region + 跨区只读副本 | 最低成本的可用性起步形态 | 唯一写者；跨区仅复制只读副本 | 中小规模内部系统、数据平台 | 基础设施按量计费 |
| 同城双活（Active-Active，同城） | 机房级故障不影响服务 | 同城 RTT 1–3ms 量级（【经验】），可承担同步复制/共识的延迟 | 交易主链路、支付类系统 | 自建为主 |
| 两地三中心 | 传统主备 + 异地灾备 | 主中心写入、备中心待命，切换需人工/半自动 | 金融、政企、监管要求场景 | 自建为主 |
| 异地多活（含三地五中心） | 多 Region 同时读写、按单元切分 | 用户哈希 → 单元；单元内数据闭环；跨单元依赖最小化 | 阿里、美团、字节等 | 自建（单元化中间件多为自研） |
| Global Database（Spanner / CockroachDB / YugabyteDB / TiDB / OceanBase） | 把跨 Region 一致性做进数据库 | 共识复制 + 全局时钟/单调时间戳，把冲突判定收敛到数据库内部 | 全球 SaaS、需要跨区强一致的账务 | 托管服务订阅，或开源 + 商业支持 |
| 主区归属 + 播放面分离（Netflix 式） | 用「把跨洋往返摘出关键路径」换取可用性 | 写路径绑定主区，读/播放路径本地化 | 全球流媒体、内容分发类业务 | 自建 |

**先分族，能省掉一半比较**：这些候选其实分三族——**单写者族**（单 Region、两地三中心）不存在冲突解决，代价全在切换窗口；**多写者 + 应用层切分族**（同城双活、异地多活、三地五中心）把冲突消解在「归属规则 + 单元闭环」里，代价在数据切分与迁移刚性；**多写者 + 数据库内解决族**（Global Database 与主区归属式）把冲突消解在存储层，代价在延迟与产品绑定。同族内部差异是量级问题（单元数、Region 数），跨族差异是性质问题（有没有冲突解决这件事）。

**每个候选真正「做不到」什么（判据一的具体化）**：

- **单 Region + 跨区只读副本**：能做到跨区读，**做不到**「写也本地」——写永远是单点，切换窗口必然存在。
- **同城双活**：能做到 RPO≈0，**做不到**城市级故障容灾——同城两机房仍共享城域链路与同城供电等共因风险。
- **两地三中心**：能做到合规口径上的灾备能力，**做不到**「备中心平时承载业务」——它是为最坏情况买的保险，不是产能。
- **异地多活 / 三地五中心**：能做到多 Region 同时服务，**做不到**「任意数据都允许多写者」——可切分性决定它能覆盖多少业务。
- **Global Database**：能做到应用无感的跨 Region 强一致，**做不到**「零延迟税的跨区写」——同步共识的成本随写 QPS 线性放大。
- **主区归属 + 播放面分离**：能做到把读放大本地化，**做不到**写侧的多点化——它优化的是读路径，不解除写集中。

**同一名词在不同规模下不是同一件事**（这也是横向对比最容易失真的地方）：同样是「同城双活」，在两个机房间跑同步复制与在「一个 Region 内的两个可用区」跑同步复制，可用性含义完全不同——**后者对机房级故障无效，只对单机/单可用区故障有效**。同样叫「异地多活」，3 个 Region 与 10 个 Region 的运维复杂度不是线性关系，因为跨 Region 路径数增长为 `N(N-1)`，其中每一条都要做容量、延迟与故障处理设计。**因此对比的前提是把「Region 数量」「是否真跨城」「单元是否闭环」这三件事说清楚**，否则名字相同、性质不同。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 写入拓扑：谁是「唯一写者」

**机制是什么**：决定同一份数据在同一时刻允许几个 Region 接受写入。单写者 = 冲突不可能发生；多写者 = 必须定义冲突判定与归属规则。

| 候选 | 写入拓扑 | 由此得到的必然性质 |
| --- | --- | --- |
| 单 Region / 两地三中心 | 单写者（主中心） | 无冲突解决；写可用性绑定在该写者上，故障即切换窗口 |
| 同城双活 | 多写者，但同城 RTT 小 | 可在写路径上做同步复制/共识，RPO 近 0 |
| 异地多活 / 三地五中心 | 多写者 + 归属规则 | 写可用性不再依赖跨 Region 链路，但数据必须可切分 |
| Global Database | 多写者，冲突在存储层解决 | 应用无需感知归属，代价是每次写付共识延迟 |

**由此必然导出的性质**：**因为同城 RTT 只有 1–3ms 量级而跨城是 10–30ms 量级（【经验】区间：行业普遍观测值，随城市对与骨干路径不同而异，无单一权威来源；主文件 §2.1 为同口径表述），所以「同城可以同步复制、跨城不能」不是实现差异而是物理约束**——跨城同步复制会把每一次写都抬高一跳 RTT，在写 QPS 高的主链路上，这个延迟会线性放大为在途请求数与资源占用（费效比推导见 7.4）。反过来，**因为是单写者，所以两地三中心不需要冲突解决，但它的 RTO 下限就是「发现故障 + 决策 + 切换」的总时间**，这段时间内写是停的。

**由此必然导出的两条工程规则**：第一条，**因为跨城同步写的成本与写 QPS 成正比，所以「跨城同步」只能用在低频且不可丢的写路径上**（资金扣减、状态机终态），高频可归并的写（计数、日志、行为埋点）一律走异步与合并——把这两类写混在一条同步路径上，是整个写侧延迟被抬高的最常见原因。第二条，**因为单写者架构的可用性由切换时间决定，所以它的改进方向是「缩短切换」而不是「增加副本」**——加只读副本不改变 RTO。

**公开证据**：Google Spanner 论文报告 TrueTime 的不确定区间 ε 为个位数毫秒量级，并用「提交等待（commit-wait）」越过该区间实现外部一致性——**这套机制之所以可行，是因为它把「跨 Region 的物理时间不确定性」用专用时钟基础设施压到了毫秒级**（【公开】Spanner, OSDI 2012）。共识复制（Paxos / Raft）是同类机制的另一条路（【公开】Raft, USENIX ATC 2014）。CAP 的「分区时二选一」由 Brewer 2000 年提出、2002 年被形式化证明；PACELC 补充了「无分区时也要在延迟与一致性之间选」（【公开】Abadi, IEEE Computer 2012）。

**失效条件**：当业务写延迟预算（P99 减去业务处理时间）小于跨 Region RTT 时，任何跨 Region 同步写机制都会失效——此时只能改为单写者 + 异步，或者把该数据的写路径收敛到本地。

#### 7.3.2 冲突判定依据：用什么决定「哪个版本是新的」

**机制是什么**：多写者下，两个 Region 同时写同一条记录，系统必须给出一个判定依据。依据的可信度决定了一致性上限。

| 依据 | 实现 | 代价 | 失效形态 |
| --- | --- | --- | --- |
| LWW（Last-Write-Wins） | 比物理时间戳，取大者 | 实现最简 | 时钟漂移下**静默丢更新**，日志里查不到 |
| 向量时钟 | 记录各 Region 版本号，检测并发 | 元数据随参与方线性增长；冲突需应用层解决 | 冲突率高时变成人工工单 |
| CRDT | 用满足交换/幂等（CmRDT）或单调（CvRDT）的数据类型，合并与顺序无关 | 仅适用于特定数据类型（G-Counter、OR-Set 等）；元数据有固定开销 | 业务语义不是 CRDT 能表达的形状（如「订单状态机」） |
| 全局时钟（TrueTime 类） | 用 GPS + 原子钟把不确定区间压到毫秒级 | 需要专用时钟基础设施 | 自建环境拿不到同等时钟保证 |

**由此必然导出的性质**：**因为 LWW 的判定依据是各机器的本地时钟，而本地时钟之间存在漂移，所以在跨 Region 场景下 LWW 丢失的往往不是「后写的那次」而是「时钟较慢的那次」**——这类丢失不会报错、不进冲突日志，只在业务侧表现为「用户说他明明改过」。**因为 CRDT 的合并函数满足交换律与幂等律，所以在网络乱序、重复投递、延迟到达下合并结果依然收敛**，代价是它只能表达那些「可交换的语义」——把订单状态机硬塞进 CRDT 是典型的误用。

**公开证据**：Amazon Dynamo 论文选择用向量时钟检测冲突并把冲突版本一起返回给应用层解决，而不是直接 LWW；论文明确把「时钟不同步导致的丢失更新」列为需要规避的风险（【公开】Dynamo, SOSP 2007）。Spanner 论文则给出另一条路：用可信时钟把「物理时间」变成可用的判定依据（【公开】Spanner, OSDI 2012）。

**冲突率决定机制选择（【经验】）**：冲突不是理论问题而是比率问题——多写者下真正的冲突只发生在「同一实体在极短时间窗内被两个 Region 写到」的情形。**大部分业务里这个比率极低，但它的分布高度集中在少数几类实体上**（用户资料、购物车、库存扣减、状态机字段）。因此【经验】做法是：先按实体枚举「哪些实体的并发写会导致业务不可接受的语义」，把这几类挑出来单独处理（主区归属或应用层冲突策略），其余交给通用机制——把机制选型问题转化为「实体清单」问题。

**机制可以混用，且通常必须混用**：一个真实系统里，绝大多数实体可以归并（用 CRDT 或幂等合并）、少数实体必须单写者（主区归属）、极少数实体必须跨区强一致（Global DB）。**因为这三类实体的数量比通常呈金字塔分布，所以正确的做法是按实体分层选择机制，而不是给整个系统选一种机制**——「我们用了 CRDT」和「我们用了 Spanner」都只是描述了一层，不描述完整架构。

**失效条件**：当同一实体的并发写来自「不同用户、语义不可合并」时（典型如订单状态、库存扣减），所有自动合并机制都会错——正确做法是**不给它多写者**：把该实体绑定到单一主 Region（主区归属），把冲突从根本上消除。

#### 7.3.3 数据归属与路由：请求必须去哪台机器

**机制是什么**：多 Region 下每个请求都要落到某个 Region 处理，归属规则决定「跨 Region 调用还剩多少」。

| 做法 | 归属规则 | 结果 |
| --- | --- | --- |
| 全局共享（未切分） | 无归属，谁都可以读远程主库 | 跨区依赖遍布调用链，一处抖动全站放大 |
| 单元化 / 按用户哈希（Ch12 §01） | `hash(user_id) → 单元 → Region` | 请求在单元内闭环，跨 Region 调用被消除 |
| 主区归属（Netflix 式） | 写路径绑定主区、读路径本地化 | 把跨洋往返摘出关键路径，代价是写侧仍有集中点 |
| Global Database 透明路由 | 数据库内部按 key range 决定副本位置 | 应用无感，但跨 key range 的分布式事务要付共识成本 |

**由此必然导出的性质**：**因为单元化把「同一用户的所有请求」固定在同一单元、并让该单元的数据与服务在同地闭环，所以单机房故障的影响面从 100% 收敛到约 1/单元数**——这才是多活降低耦合的实质，而不是「多部署几份副本」。**反过来，因为归属规则一旦生效，数据就按它落了盘，所以修改归属规则的代价不是改配置而是搬数据**：一个用户换单元的迁移要处理双写、读校验、历史数据搬迁与一致性回滚路径，工作量以季度计。**另一个必然代价**：跨单元事务要么放弃，要么走补偿/最终一致——这是单元化的边界税。

**公开证据（按可核验性降档说明）**：阿里与 Netflix 这两条路径都来自公开分享，但**本节无法把它们定位到某一篇可引用的具体材料，因此不标【公开】，改标【经验】并给出核验方法**。阿里侧的核验入口是双 11 期间发布的年度高可用/单元化技术分享，其特征词是「单元化」「单元内数据闭环」「按『自身 + 可接管』规划容量」「按数据分类定义一致性边界」——**判定方法**：读到任一篇时，检查它是否同时给出（a）故障域的划分方式，（b）跨区调用被消除或降级到了哪一层；只讲「多部署几份副本」的材料不构成对该机制的证据。Netflix 侧的核验入口是 Netflix Tech Blog 的多区域可用性系列文章，特征词是「播放（playback）面与主区路由分离、跨洋往返不落在关键路径上」——**判定方法**：看它给出的失效场景是「主区整体不可用」还是「某个 Region 的播放请求超时」，前者说明它做的是写路径集中 + 读路径本地化，后者才是真的多点写。两条路都印证同一件事：**多活的收益来自「跨区调用减少」，不来自「副本数量增加」**。

**单元划分的三个实操约束**（决定这条路能不能走通）：

1. **归属键必须稳定**：哈希键选错（例如用会被修改的字段、用会话 ID）会导致同一用户在不同时刻落到不同单元，闭环立刻失效。可用性大于均匀性的归属键优于反之。
2. **跨单元写必须能重述为补偿**：转账、发券、扣库存这类跨用户操作，在单元化下不能靠分布式事务，只能靠「先在本地单元记账 + 异步补偿 + 幂等去重」。**不能重述为补偿的业务，就该拒绝上单元化**，而不是硬上之后再补。
3. **全局资源要做成「只读 + 低频写」**：全局配置、国家/地区维表、费率表可以跨单元同步；全局自增编号应改为号段预取（每个单元预领一段，用完再领）——**把高频全局写改造成「低频领号 + 本地发号」是单元化的常见必要改造**。

**失效条件**：当业务存在大量全局唯一性约束（全局自增 ID、全局库存、跨用户清结算）时，闭环不可能达到 100%——正确做法不是追求闭环，而是**把这部分依赖显式枚举出来，压到最小并单独设计一致性等级**。

#### 7.3.4 故障判定与切流：谁有权说「这个 Region 挂了」

**机制是什么**：从「发现异常」到「流量改道」之间的机制决定 RTO 的真实下限。

| 机制 | 切流路径 | 必然的 RTO 约束 |
| --- | --- | --- |
| DNS 调度 | 改解析 → 客户端按 TTL 缓存到期 | RTO 下限 ≈ 客户端实际遵守的 TTL；TTL 60s 时最坏等待 ≥ 60s（【推算】：TTL 未到期前客户端继续命中旧解析） |
| GSLB 健康探测 | 探测 → 摘除节点 → 按策略重定向 | 取决于探测失败判定次数 × 间隔 |
| Anycast / BGP | 路由收敛，就近节点接管 | 收敛较快，但有状态长连接会断，需重连与补状态 |
| 共识选举（Raft/Paxos） | 副本过半数派自动选新主 | 跨 Region 部署时，多数派意味着写要跨 Region 往返 |
| 人工决策切换 | 值班判断 → 执行切换脚本 | RTO 受人的反应速度约束，通常小时级且高风险（【经验】） |

**由此必然导出的性质**：**因为 DNS 的切换速度受客户端缓存 TTL 约束、而 TTL 无法随意调小（过小会让解析量冲击权威 DNS 并增加解析延迟），所以「依赖 DNS 的架构」无法承诺分钟以内的 RTO**——秒级 RTO 必须绕开解析缓存，改用 VIP/BGP/Anycast、服务网格或客户端路由表。**因为共识组要先过半数派才能选出新主，所以把共识组跨 Region 铺开时，可用性提升的代价是写延迟上升**——两者由同一份派数决定，不可能同时最优。**因为健康探测本质上是一个存在误判率的判断器，所以任何自动切流都必须配一个仲裁机制**（见证副本、第三方仲裁节点），否则误判时两端都认为自己该服务，形成脑裂。

**公开证据**：Raft 把「选主 + 日志复制」写成可工程实现的完整算法，是当代多数分布式数据库与控制面的基础（【公开】Raft, USENIX ATC 2014）；共识的可实现性是「自动切主」这条路成立的前提。跨 Region 延迟量级（同城 1–3ms、跨城 10–30ms、跨国 100–200ms）为【经验】区间——行业普遍观测值，随城市对与骨干路径不同而异，无单一权威来源，主文件 §2.1 为同口径表述；读者可用自己机房到目标 Region 的探测数据自行校准。

**切流的四条必测路径**（没测过就等于没有）：其一是**入口路径**——解析/VIP/BGP/客户端路由，验证旧路径多久彻底失效；其二是**数据路径**——目标 Region 的数据是否已就绪、复制延迟是否收敛、只读副本是否追平；其三是**依赖路径**——下游第三方、消息队列、缓存、注册中心是否都换到了就近实例；其四是**回切路径**——切过去之后能不能切回来，回切往往比切出更危险。**因为故障现场几乎不可能正好只坏一个 Region 而这四条路径全部健康，所以演练的价值在于把「切流」从一次性操作变成一条被反复验证过的例行路径。**

**失效条件**：切流路径从未端到端演练过时，所有上述机制只在纸面上成立——真故障时切流本身会变成二次故障源（见 7.7 反模式三）。

### 7.4 成本结构对比（不是价格表，是成本函数）

**多 Region 的总成本可以写成**：

```
总成本 ≈ Σ_Region ( 常驻资源 × (1 + 可接管冗余系数) )
        + f(跨 Region 流量)
        + g(一致性延迟税)
        + h(运维与演练人力)
```

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| 单 Region + 跨区只读副本 | 常驻资源（1 份）+ 复制流量 | 切换期间的写停写窗口；灾备资源平时不承载业务 |
| 同城双活 | 常驻资源 × 2（同城两地） | 同城带宽与机房间链路的可靠性设计 |
| 两地三中心 | 常驻资源 × 3，其中 1 份基本闲置 | 切换本身的决策成本与演练成本 |
| 异地多活 / 三地五中心 | 常驻资源 × Region 数 + 冗余预留 | 单元边界的迁移刚性；跨单元一致性设计成本；演练人力 |
| Global Database | 托管费（随节点数与跨区流量增长） | 每次写付共识延迟；产品绑定与迁移成本 |

**关键结论：多活成本的主干是「冗余容量」而不是「带宽」。** 因为多活要求剩余 Region 在任一同伴故障时接管其流量，所以每个 Region 的容量必须按「自身单元 + 可接管份额」规划——这份冗余在平时是闲置的，但它不是浪费，而是「多活」这个性质的定义的一部分。

**跨 Region 流量的量级（【推算】）**：按 AWS 公开定价页所列的跨 Region 数据传输 $0.02/GB 与 S3 标准存储 $0.023/GB-月（【公开】AWS S3 与数据传输定价页, 2024；此类单价会随区域与时间调整，引用前应复核当期价目）推导——一次性搬运 10 TB 约 10,240 GB × $0.02 ≈ $200 量级；若每日跨区同步增量 1 TB，则月流量约 30 TB，传输成本约 $600/月量级。**同一份增量若在目标 Region 保留 30 天**，累计约 30 TB ≈ 30,720 GB × $0.023 ≈ $700/月量级——**两项同阶，说明「把数据搬过去」的流量账与「把数据多存一份」的存储账必须一起算**，只盯带宽会低估这项支出。**与同量级的常驻计算冗余相比，这两项通常不是主导项**，但它们是「多写者 + 双活」的固有支出，方案越激进增长越快。

**一致性延迟税（【推算】）**：若跨城一次同步写要付约 20ms 的额外 RTT（取 10–30ms 这一【经验】区间的中值作为假设），则 1 万写 QPS 的主链路在任意时刻约有 1万 × 0.02s ≈ 200 个在途写；作为对照，同一笔写若留在本地、响应时间按 1ms 量级假设，则在途写约 1万 × 0.001s ≈ 10 个——即同样的吞吐下，跨城同步把在途并发抬高约 20 倍（约一个数量级），直接体现为连接/线程/内存占用与秒级超时概率的上升。**这条税不写在账单上，写在容量规划里**——这也是「跨城同步只用于低频关键写、而不是全部写」的量化依据。

**各候选的成本函数展开**：

| 候选 | 成本函数形状 | 主导项 | 什么时候会失控 |
| --- | --- | --- | --- |
| 单 Region + 跨区只读副本 | `C₀ + 复制流量` | 常驻资源（1 份） | Region 内单点成为容量与可用性双重上限 |
| 同城双活 | `2 × C₀ + 同城链路` | 常驻资源（2 份） | 同城链路成为共因故障点；容量按 2 份买但只用 1 份峰值 |
| 两地三中心 | `3 × C₀`，其中第三份基本闲置 | 常驻资源（3 份） | 备中心长期不承载业务，切换能力随人员流动衰减 |
| 异地多活 / 三地五中心 | `Σ_Region C_i × (1 + 冗余系数) + 跨区流量 + 演练人力` | **冗余容量 + 人力** | 单元数增加、跨单元依赖增多时，运维复杂度与冗余系数同步上升 |
| Global Database | `托管费（节点数 + 跨区流量） + 写 QPS × RTT 的容量代价` | **写延迟税转化的资源** | 把高频热点写放上跨区共识 |

**三类不该混进来的成本**（混进来会让对比失真）：一是**已经在付的成本**——监控、工单、变更流程本就存在，不该算成多活的新增项；二是**与方案无关的一次性投入**——比如压测环境；三是**不可量化的组织收益**——「多活让团队更有底气」是真的，但它不是成本函数的一部分，应该写进决策理由而不是算进账。

**成本函数的用途不是算总价，而是找主导项**：把上式里的每一项分别估一个量级，哪一项最大，优化就往哪走。若主导项是「常驻资源 × Region 数」，那么减少 Region 数或用更小的可接管容量规划，比省带宽有效得多；若主导项是「写延迟税转化的资源」，那么把跨区同步写改成可归并的异步写，收益远大于换一个更快的引擎。**这也是为什么本节不给价格表：价格会变，主导项不会。**

**一个判断口径**：把「多活」的成本除以「它实际能减少的不可用分钟数」，会得到每避免一分钟不可用要付多少钱。【推算】以 99.9%（年不可用约 8.8 小时）提升到 99.99%（约 52.6 分钟）为例，需要为「每年多避免约 8 小时」付出一套多 Region 常驻冗余——对交易类业务这笔钱通常值，对内部系统通常不值。**这个除法是把架构选型和业务损失挂钩的最简单方法**，也是替代打分表的最直接工具。

### 7.5 决策树（每个分支都要有阈值依据）

```
Q1. 把可用性目标折算成「一年能承受多少不可用分钟」：能接受一个靠人工决策的切换窗口吗？
├─ 能（99.9% 档，年不可用约 8.8 小时【推算】，切换窗口有预算）
│   ├─ 数据有明确的主权/合规边界（不许出境 / 必须留境）？ → 按边界分区：区内单写者 + 跨区异步备
│   ├─ 需要 RPO≈0，且两个机房落在同城范围？ → 同城双活（同步复制/共识）
│   └─ 否则 → 单 Region + 跨 Region 异步只读副本（成本最低）
└─ 不能（99.99% 档约 52.6 分钟/年、99.999% 档约 5.3 分钟/年【推算】，切流必须自动化到分钟以内）
    ├─ 关键路径上是否存在「跨洋往返」的读放大（一次请求要回主区取 N 次数据，N 随页面/分片数放大）？
    │   ├─ 是 → 主区归属 + 读路径/播放面本地化（Netflix 式）：先把跨洋往返摘出关键路径；数据若同时可切分，再叠加单元化
    │   └─ 否 → 进入下一问
    └─ 数据能否按用户/租户水平切分，且跨切片操作可控？
        ├─ 能 → 单元化 + 异地多活（含三地五中心）：爆炸半径 ≈ 1/单元数
        │   └─ 单元数取几个？（下界由爆炸半径定、上界由「剩余 Region 能否接管一个故障 Region」定，见阈值依据⑥）
        └─ 不能（强全局事务 / 全局唯一性）
            ├─ 跨区写占比低但必须强一致 → Global DB 只覆盖这部分数据
            └─ 跨区写是主路径且高 QPS → 先改业务模型做可切分，不要先上 Global DB

定档之后还要回答两个参数问——答不上来就不该定在这一档：
Q2. 按 N 个等大 Region 规划时，每个 Region 能否预留约 1/(N-1) 的额外容量，并再乘上业务峰谷比？
├─ 能 → 按该冗余系数规划容量与预算（这份冗余是「多活」的定义的一部分，不是浪费）
└─ 不能 → 减少 Region 数或缩小「可接管」范围（放弃全体互备），而不是把这笔冗余省掉
Q3. 四条切流路径（入口 / 数据 / 依赖 / 回切）能否按季度各演练一次？
├─ 能 → 保留该档位
└─ 不能 → 降档到「跨区只读副本 + 明确的人工切换预案」，先积累演练能力再升级
```

**树外的三个常见误判**：

- **误判一：把可用性目标当成起点**。应先问「停 5 分钟损失多少」，再问「一年能花多少换它」。同一个 99.99%，对交易系统是硬约束，对内部报表系统是无意义的要求。
- **误判二：把「能不能买到」当成「能不能运维」**。托管型 Global Database 可以一天开通，但把它用好需要理解分布式事务边界、热点分区与跨区读写路由；**开通成本低不等于掌握成本低**。
- **误判三：忽略组织形态**。多活需要值班体系、演练纪律、跨团队变更协同。【经验】在没有常态化 on-call 与演练机制的组织里强推多活，通常得到一个「架构图很漂亮、故障时仍靠人打电话」的结果。

**阈值依据（与树上的判断节点逐条对应）**：

- **① Q1 主节点「能否接受人工决策的切换窗口」**：先把可用性目标折算成可接受的年不可用时间——0.1% × 365 × 24 × 60 ≈ 8.8 小时/年（99.9%），0.01% ≈ 52.6 分钟/年（99.99%），0.001% ≈ 5.3 分钟/年（99.999%）（【推算】）。99.9% 的预算容得下若干次人工决策的切换；99.99% 及以上则要求切流自动化到分钟以内。**切换窗口有多大由切流机制决定**：DNS 受客户端 TTL 约束（TTL 60s 时最坏等待 ≥ 60s，【推算】），秒级 RTO 必须绕开 DNS 缓存路径（VIP/BGP/服务网格/客户端路由表）。**因此这个节点的阈值来自这张换算表，不来自「哪个方案更先进」**——原文件把 99.99% 直接映射到两地三中心，在因果上是反的。
- **② Q1 节点「数据有明确的主权/合规边界」**：这不是性能阈值而是否决性约束——当监管要求数据留在本司法辖区（或某些数据不许出境）时，Region 边界由法规划定，不由容量或延迟决定，所以它排在所有性能判断之前。**判定方法**：列出一份「不许跨越某条边界的数据/字段」清单，清单非空即命中本节点；此时业务切分图与合规切分图可能不一致，两张图必须同时满足（见 7.6 组合 6）。**另一条合规线索是灾备能力等级口径**：业内常把灾备分为数据级（只保证数据可恢复，重建靠人工）、应用级（应用可在备用场地拉起）、业务级（业务可自动切换、RPO/RTO 到分钟级），另有按「同城双活 / 异地多活 / 全球多活」划分的说法——**这些是分类口径的对照，不是某一份国家标准的等级命名**；本文件不再挂具体标准编号，因为该标准原文的等级名称与上述俗称并不一致（主文件 §2.3 第 5 项的措辞沿袭了这处俗称，宜同样按上述口径理解）。合规场景下应直接查当前有效的标准原文与本地监管要求，再决定按哪一档建设口径留证（对应 7.8 的「强监管」一行）。
- **③ Q1 节点「需要 RPO≈0 且同城范围」**：两条子阈值各自独立。**「同城」来自跨 Region 延迟量级（同城 1–3ms、跨城 10–30ms，【经验】）**：同步复制/共识至少付一个 RTT，所以判据是「写延迟预算是否 ≥ 1 个 RTT」，而不是「距离是否好看」；跨城同步把每次写抬高一跳 RTT，在写 QPS 高的主链路上会线性放大在途请求（推导见 7.4）。**「RPO≈0」是二值阈值**：同城同步复制/共识可做到零丢失窗口，跨区异步备只能做到「RPO = 复制延迟量级」——它不随规模变化，只问你能否接受丢掉一个复制窗口内的写。
- **④ Q1 分支「跨洋往返的读放大」**：判据是「单次用户请求沿关键路径跨洋往返几次」，不是「有没有跨洋流量」。若一次请求要回主区取 N 次数据（N 随页面数、分片数、推荐列表长度放大），跨洋 RTT（【经验】100–200ms 量级）会被乘上 N，此时把读路径本地化的收益随 N 线性增长；N 恒为 1 的低频读不值得为它改造架构。**这个节点放在可切分性之前问，是因为它与可切分性正交**——可切分业务同样可能有跨洋读放大（此时两条解法叠加），不可切分业务也可能完全没有读放大（此时不需要 Netflix 式改造）。
- **⑤ Q1 节点「数据能否按用户/租户水平切分」**：不需要数字阈值，它是可行性闸门。**判定方法**是逐实体列表回答两问：（a）同一实体被两个切片并发写时，业务语义是否仍成立；（b）跨切片操作能否重述为「本地记账 + 异步补偿 + 幂等去重」。两问都能答「是」，才走单元化多活这一支；有一批实体答「否」，就把它们单独枚举出来按 ⑦ 处理，而不是整站退回单写者。
- **⑥ Q1 节点「单元数取几个」**：爆炸半径下界 ≈ 1/单元数（【推算】，按用户哈希均分假设）。但单元数上升会让跨单元依赖数、容量冗余复杂度与运维成本同步上升；【经验】多数实践落在个位数到十位数单元，**决定因素是「单 Region 剩余容量能否接管一个故障 Region」，而不是某个绝对数字**。
- **⑦ Q1 节点「跨区写占比低 vs 高」**：由 7.4 的延迟税推导——每次跨区写付一个 RTT 且随 QPS 线性放大，因此 Global DB 只适合覆盖「低频 + 必须强一致」的那部分数据。**这里没有绝对阈值，判定口径是「跨区同步写占比 × 写 QPS」这个乘积**：先算出它，再看它转化的在途请求与资源占用能否吃得下；吃不下就走右分支，先改业务模型。
- **⑧ Q2 节点「冗余系数」**：由「单 Region 故障时，剩余 Region 需接管多少流量」反推——若按 N 个等大 Region 规划且要求任意单 Region 故障不影响服务，则每个 Region 至少需预留约 1/(N-1) 的额外容量（【推算】，等大均分假设）；实际还要乘上业务峰谷比，因此【经验】预留比例通常显著高于理论值。
- **⑨ Q3 节点「演练频率」**：由「切流路径有多少条」反推——四条必测路径（见 7.3.4）若有任一条一年未测，该路径在真故障时的成功率应视为未知。**因此【经验】底线是每季度至少一次限流或单 Region 摘除演练**，而不是每年一次大演练。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 内部后台 / 数据平台，读多写少 | 单 Region + 跨区只读副本 | 两地三中心（合规要求时） | 上多活是为不存在的写可用性付冗余成本 |
| 交易主链路、机房间同城 | 同城双活 | 单 Region + 同城备 | 同城 RTT 允许同步复制，跨城则写延迟超预算 |
| 面向 C 端、用户可切分 | 单元化异地多活 | 三地五中心（容量要求更高时） | 不做单元化就只有副本没有闭环，跨区依赖反而放大故障 |
| 全球 SaaS，账务/账本类数据 | Global DB 覆盖这一部分 | 主区归属 + 应用层补偿 | 把全部热点写放进 Global DB，延迟税随 QPS 线性放大 |
| 全球流媒体 / 大文件分发 | 主区归属 + 读路径本地化 | CDN 化 + 多 Region 只读 | 把跨洋往返留在关键路径上，用户体验被带宽决定 |
| AI 推理服务（无状态、延迟敏感） | 多 Region 就近推理 + 单区写入 | 单区推理 + 边缘缓存 | 推理无状态易复制，但训练/特征写入仍受一致性约束 |
| 训练与离线大作业 | 跨 Region 对象存储复制 + 按需拉起算力 | 单 Region 集中计算 | 离线作业不要求低延迟，为它做多活纯属浪费 |

**常见组合（每条的职责边界与运维代价）**：

1. **异地多活 + 单元化（Ch12 §01）**：多活提供「多 Region 同时服务」，单元化提供「请求在单元内闭环」。**职责边界**：多活管容量与冗余，单元化管耦合与爆炸半径。**运维代价**：单元边界要维护，跨单元依赖需持续审计。
2. **异地多活 + 大促保障（Ch12 §03）**：多活承担「峰值跨 Region 分摊」。**边界**：容量按「自身 + 可接管」规划，大促要预演跨 Region 切换。**代价**：平时冗余成本更高，容量规划从单机房问题变成多机房联合问题。
3. **异地多活 + 容灾（Ch12 §07）**：多活是容灾的高级形态，容灾责任制保留预案与演练纪律。**边界**：多活管常态可用性，容灾管极端场景（多 Region 同时退化的兜底）。**代价**：必须有定期切流演练，否则预案只是文档。
4. **异地多活 + 数据一致性（Ch12 §08）**：多活管拓扑，一致性边界管「哪些数据可以异步」。**边界**：按数据分类定义一致性等级，而不是一刀切强一致。**代价**：需要维护一份显式的一致性边界清单，它是持续演进的资产。
5. **异地多活 + AI**：多活管推理服务的就近部署与容量，AI 侧管模型路由与特征同步。**边界**：无状态推理易多活，向量索引与特征库要多 Region 同步或按 Region 分片。**代价**：模型版本与索引版本的一致性成为新的跨 Region 依赖。
6. **主动-主动 + 单元化 + 数据主权分界**：多活管容量，单元化管耦合，主权分界管「哪些数据不许出境」。**边界**：当合规要求数据留在本司法辖区时，Region 边界会与单元边界不一致，必须显式维护两张切分图。**代价**：跨边界只允许同步必要字段，这通常要求业务侧做字段级裁剪与脱敏改造。
7. **主区归属 + 只读多 Region + CDN**：主区管写入与权威数据，只读 Region 与边缘缓存管读放大。**边界**：读路径允许多级缓存，写路径必须收敛到主区。**代价**：写侧仍是集中点，需要另外的容灾方案兜底。

**组合的运维总账**：每加一件，运维对象就增加一类常驻组件与一组需要定期演练的路径。【经验】多数团队能稳定维护的组合不超过 2–3 件；把上面 7 种组合里的多件全上而没有对应人力，结果是每一件都处于「配置存在但从未验证」的状态——**这种状态下多活提供的是心理保障，不是可用性**。判断办法很简单：任何一件组合技能否在上个季度被演练过一次；不能，就该先删掉它而不是再加一件。

**矩阵怎么读**：表中「首选」一列是可落地的第一选择，「备选」是当首选受合规或容量约束时退守的路径，「不选它的原因」写的是**机制层面的必然代价**而不是优劣判断。**读法是从「不选它的原因」倒推自己是否处在该机制成立的条件下**——例如「上多活是为不存在的写可用性付冗余成本」这句话只在「我的写路径本来就可以短时停」时成立，如果你的写路径一秒都不能停，这一行就不适用于你。

### 7.7 选错的代价与迁移成本

**反模式一：用「多买几个 Region」代替「解决跨区依赖」**。症状是把应用复制到 N 个 Region，数据仍跨 Region 读同一个主库。后果是**可用性一点没提高而成本翻了数倍**——任何一个 Region 故障，其余 Region 都依赖同一个远端数据源，故障照样全站化。正确做法：先做单元内数据闭环，再谈多活；判断标准不是「有几个 Region 在跑」，而是「某个 Region 掉线时，剩余 Region 的请求路径上还有没有指向它的调用」。

**反模式二：用 LWW 解决「用户可见的并发写」**。症状是两地对同一业务实体（订单状态、地址、余额调整）并发写，靠时间戳定胜负。后果是时钟漂移下的**静默丢更新**：不报错、不进冲突日志，只在业务侧表现为客户投诉「我改过」。正确做法：识别出这类实体，把它们绑定到单一主 Region（主区归属），从机制上消除冲突；确实需要多写者的数据才引入向量时钟/CRDT，并明确谁来兜冲突。

**反模式三：把 RTO 写进 SLA 却从不演练切流**。症状是架构图上有完整的多活与自动切换，但切流脚本两年没跑过。后果是**真故障时切流本身变成二次故障源**（缓存未预热、连接池指向错、依赖未就绪，流量涌向尚未就绪的 Region）。正确做法：把切流演练常态化，纳入混沌工程（Ch12 §06）的常规实验清单，并把「演练中发现的问题」作为多活架构的验收项。

**反模式四：把「单 Region 拆成两个」当作多活**。症状是把一半流量挪到另一个 Region，但两个 Region 共用同一个数据库主库、同一套配置中心、同一个消息集群。后果是**可用性没有提升，反而多了一层网络跳数**——共享组件故障时两个 Region 一起挂，而平时每次请求都多付一次跨 Region 往返。正确做法：**多活的验收标准是「故障域清单」而不是「Region 清单」**——逐个列出共享组件，确认哪些已本地化、哪些必须接受共享，并为后者单独准备容灾。

**选型评审时的 5 个必答问题**（可直接替代打分表）：

1. **同一份数据允许几个写者？** 如果答案是 1，后面所有冲突解决的讨论都不需要发生。
2. **不可切分的数据有哪些？** 逐条列实体，而不是列表——同一张表里可能有可切分与不可切分两类字段。
3. **跨 Region 的同步写占比多少？** 这个比例乘以写 QPS 就是延迟税的量级。
4. **上季度切流演练跑过几次，发现了什么问题？** 0 次意味着多活停留在配置层面。
5. **换成另一个方案要动什么？** 数据是否要重分布、事务边界是否要改写、回退路径是否存在。

**换成另一个方案要动什么**：

| 迁移方向 | 数据迁移 | 查询/业务改写 | 运维重建 | 团队再学习 | 工作量量级说明 |
| --- | --- | --- | --- | --- | --- |
| 单 Region → 同城双活 | 低（同城同步复制） | 低 | 中（同城链路、切换流程） | 中 | 以月为单位（【经验】） |
| 单 Region → 异地多活（单元化） | 高（按用户重分片 + 双写校验） | 高（跨单元 JOIN 必须消除） | 高（多 Region 容量、切流、演练） | 高 | 以季度到年为单位（【经验】） |
| 异地多活 → Global Database | 高（全量导入新引擎） | 中高（SQL 方言、事务边界、分布式事务约束） | 中（托管化后运维变轻） | 中高 | 以季度为单位（【经验】），且回退路径要提前设计 |
| Global Database → 单元化多活 | 高 | 高 | 高 | 高 | 以季度到年为单位（【经验】）；相当于重做数据架构，通常只在成本或锁定压力下发生 |
| 两地三中心 → 异地多活 | 中高（备中心转正需数据与流量同时改造） | 中 | 高（从「切换」转向「共存」） | 高 | 以季度到年为单位（【经验】）；技术与数据改造可与团队转型并行，真正的长尾在值班与演练体系从「按年演练」转为「常态运行」 |

**迁移真正的隐藏成本是「双跑期」**：任何一次归属规则或引擎变更，都要经历一段新旧两套并行、双写校验、按比例放量的时间。**因为双跑期内两套系统的数据必须可比对，所以校验工具与差异归因能力决定了双跑期有多长**——这段期间的资源、人力与复杂度是叠加的（两套都在跑），而业务收益尚未兑现。迁移成本表里所有「高」，本质上都是双跑期长、且期间出错代价高；因此凡是能通过「按业务域逐个迁移」把双跑期切成小段并逐段回退的方案，实际风险都远低于一次性切换。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 团队 < 10 人、无专职 SRE（【经验】） | 单 Region + 跨 Region 异步备 | 多活的收益来自闭环与演练，没有演练能力时它只增加成本 |
| 有合规 RPO 要求、机房间可同城 | 同城双活 | 同城 RTT 允许同步复制，RPO 近 0 而无需跨城延迟税 |
| 面向全国 C 端、用户可切分 | 单元化异地多活 | 归属规则 + 单元内闭环把爆炸半径压到 1/单元数 |
| 业务含强全局事务 | 局部 Global DB + 其余单元化 | 只有「不可切分」的那部分才付共识延迟 |
| 有跨洋读放大（流媒体/内容） | 主区归属 + 读路径本地化 | 把跨洋往返从关键路径上摘掉，比加副本更有效 |
| 强监管、需对外证明能力等级 | 按灾备等级口径建设并留证 | 等级口径用于合规举证，实现路径仍需按上面的判据选 |
| 已有单体主库、想逐步演进 | 先做只读副本 + 按业务域拆出第一块可切分数据 | 一次性全量单元化风险过高；按域切分让收益先兑现、回退有路 |
| 写 QPS 高且跨区写占比大 | 先改业务模型做可归并/可切分 | 任何跨区同步机制的成本都随写 QPS 线性放大，先改模型比先换引擎便宜 |

**一条被反复验证的演进顺序**：**先降跨区读，再降跨区写，最后才谈多点写**。第一步用只读副本与缓存把跨区读压下去（收益立即可见、风险最低）；第二步把可切分的写路径按用户归属收敛到本地（这一步才真正需要单元化）；第三步才为剩余不可切分的数据选择主区归属或 Global DB。**反过来做（先上 Global DB 或先做全量单元化）几乎总是超预算**，因为组织还没积累出维护它的能力。

**表里最后一行值得单独强调**：当写 QPS 高且跨区写占比大时，最便宜的第一步往往不是换架构，而是**改业务模型**——把可归并的写改成幂等的合并写（计数、状态位、幂等号），把不可归并的写收敛到少数实体。这一步没有新增组件、不引入新的故障域，而它削减的正是 7.4 里那笔「跨区同步写的延迟税」——按 7.4 的成本函数，这笔税在 Global Database 一档是主导项（「写延迟税转化的资源」），在异地多活一档的主导项则是「冗余容量 + 人力」，减税并不自动改变后一档的成本主干。

多 Region 的成本除以它避免的不可用时间，得到的「每分钟不可用价格」应当与业务损失可比——不可比时，方案再先进也不该上。

> 本节小结：这一组方案之间**唯一真正起决定作用的差异，是「同一份数据允许几个写者」**——它一旦确定，冲突解决、延迟税、数据能否切分、切流机制全部被推导出来；其余维度（可用性、成本、复杂度）都是这条差异的下游结果。因此选型的正确顺序是：先回答「写者是谁」，再回答「归属规则是什么」，最后才是「部署几个 Region」。
