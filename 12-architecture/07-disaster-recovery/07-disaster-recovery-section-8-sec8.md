#### §DR.1 请解释 RPO（Recovery Point Objective）和 RTO（Recovery Time Objective）的定义，并说明在企业内如何把它们量化与落地。

**1. 考察点**

- 是否**真正理解两个指标的语义边界**——RPO 是"能丢多少数据"（数据维度），RTO 是"能停多久"（时间维度），二者不可互相替代。
- 能否把 RPO / RTO 从技术概念翻译成**业务语言**：每丢失 1 小时订单意味着多少钱、每停机 1 分钟意味着多少 DAU 损失。
- 是否知道**国家标准的灾备等级划分**（GB/T 20988-2007）以及等保 2.0 对 RPO / RTO 的硬性要求（等保 3.0 目前仅启动征求意见，尚无正式发布的标准号与实施日期，对照仍按现行有效的等保 2.0）。
- 加分项：能结合具体业务（金融交易、电商订单、视频流媒体）给出三档不同的 RPO / RTO 设计，并说明取舍依据。

**2. 参考答案框架**

**第一层：定义与数学表达。**

- **RPO（Recovery Point Objective，恢复点目标）**：可容忍的**数据丢失量**，单位通常是"时间"。形式化表达：`RPO = 故障发生时刻 - 最后一次成功备份时刻`。例如 RPO = 5 分钟，意味着系统在故障后最多丢失最近 5 分钟的数据。
- **RTO（Recovery Time Objective，恢复时间目标）**：可容忍的**服务中断时间**，表达：`RTO = 故障发生时刻 - 业务恢复时刻`。例如 RTO = 30 分钟，意味着故障后 30 分钟内业务必须恢复。

注意它们的**不对称性**：RPO 越小，需要的备份 / 同步频率越高（成本近似线性增长）；RTO 越小，需要的备用环境"温度"越高（成本指数级增长——冷备到温备到热备到同城双活到异地多活）。

**第二层：如何量化为业务语言。**

量化的关键是把指标翻译成**老板听得懂的钱**：

- **金融场景**：一笔支付丢失意味着监管处罚 + 用户赔付。RPO = 0 的代价是同步复制 + 强一致，意味着写入延迟 ≤ 1ms。
- **电商交易场景**：双 11 一分钟订单约数百万；RTO = 60s 的代价是异地多活 + 自动切换。
- **视频流媒体场景**：用户点开视频时短暂不可用是可接受的；RPO = 几小时（仅 CDN 回源丢失）、RTO = 几分钟，是典型的成本最优选择。
- **数据分析场景**：凌晨报表晚几小时出无伤大雅；RPO = 天级、RTO = 小时级即可。

量化路径：业务部门 + 技术部门联合评审，按"业务影响 × 发生概率"分级，落地《业务连续性等级表》。

**第三层：国家标准与法规。** GB/T 20988-2007 用**能力等级（Level 1–6）**描述灾难恢复要求，每一级对应一组 RPO / RTO 要求。**注意：国内常说的「数据级 / 应用级 / 业务级、同城双活 / 异地多活 / 全球多活」是业内俗称口径，与标准原文的等级名称并不一致**（主文件 §1.1 的六级表即俗称口径），引用以标准原文为准。等保 2.0 三级要求 RPO / RTO 满足"业务连续性需要"；金融行业的《商业银行数据中心监管指引》对核心系统有明确指标（一般 RPO ≤ 30s、RTO ≤ 30min）。

**第四层：常见组合与选型路径。**

- **Level 1（数据级灾备）**：RPO < 24h。仅定期数据备份，无法应对机房级故障——通常只在合规要求最低的场景出现。
- **Level 4（同城双活）**：RPO = 0、RTO 秒级。同城两个机房同时服务，适合强一致要求高的核心系统。
- **Level 5（异地多活）**：RPO = 0、RTO 秒级。跨城市多机房同时服务，是阿里双 11、AWS 全球多活的形态。

**第五层：行业实践。**

- **阿里双 11**：核心交易 RPO = 0、RTO < 30 秒。背后是"三地五中心 + 单元化 + 数据库跨 Region 强一致"——业务按单元（Cell）切分，每个单元自包含应用 + 数据、落在某个机房内形成完整服务闭环，切换时只切单元不发整体切换。
- **AWS Multi-Region**：默认 Multi-AZ（同城双活），可选 Multi-Region（异地多活）。CloudEndure DR 把 RPO 压到 < 30s、RTO < 5min。
- **Netflix**：全球多活（Level 6），RPO = 0、RTO 秒级。它的特点是**无状态服务全球部署 + 有状态数据最终一致**，Cassandra 多 Region 异步复制 + 业务侧容错。
- **招行核心系统**：核心交易 RPO = 0、RTO ≤ 30 分钟。两地三中心（同城双活 + 异地灾备），故障时由监管侧可见的切换流程控制。
- **Google Spanner**：全球强一致数据库，把 RPO = 0 + RTO 秒级的"看似不可能"通过 TrueTime + Paxos 落地到跨大洲机房。

**3. 常见陷阱**

- **混淆 RPO 与 RTO。** 把 RPO 当成"恢复时间"、RTO 当成"数据丢失量"是新手常见错误，必须先讲清两个维度。
- **不量化。** 回答"我们的 RPO 是分钟级"而不给出具体数值（如 RPO = 30s）、不给出业务换算（如每分钟损失 X 万订单），会显得对业务不熟。
- **忽视法规。** 不提等保 / GB/T 20988 / 金融行业规范，会被认为没做过合规级容灾。
- **只讲技术不讲钱。** 风险评估不是技术问题，是"花多少钱换多少可用性"的决策，必须主动算账。
- **一刀切。** 全公司一套 RPO / RTO 是反模式。核心交易 RPO = 0、内部 OA RPO = 天级才是真实场景。

**4. 追问预测**

- **「如果老板要求所有业务 RPO = 0，你怎么回应？」** 答：先区分业务分级——核心系统 RPO = 0、内部系统 RPO = 小时级是合理分层；强求所有系统 RPO = 0 意味着 5–10 倍资源成本，且大部分收益为零。用 ROI 论述说服老板。
- **「GB/T 20988 的 6 级具体怎么划分？你的业务在第几级？」** 答：6 级是按 RPO / RTO 递增的能力等级（Level 1–6）；**答的时候要说清「数据级 / 应用级 / 业务级、同城双活 / 异地多活 / 全球多活」是业内俗称，与标准原文的等级名称不一致**。回答时要讲清自己业务的等级定位理由。
- **「双 11 凌晨零点 RPO = 0，但 RTO 设计成 30 秒可行吗？」** 答：可行——核心交易走异地多活 + 自动健康检查 + 单元化路由；非核心走异步 / 降级链路。这正是阿里单元化设计的核心收益。
- **「金融核心系统一般 RPO / RTO 怎么定？」** 答：监管要求 RPO ≤ 30s、RTO ≤ 30min 是底线；招行、平安、微众等机构在此基础上进一步把 RPO 压到 0（招行核心交易 RPO = 0、微众账户 + 交易强一致 RPO = 0），代价是重资产投入；RTO 则受各行切换流程约束，招行核心系统为 RTO ≤ 30 分钟。

#### §DR.2 请系统对比全量备份、增量备份、差异备份三种策略，并说明在大型数据系统（PB 级）下应当如何组合设计备份方案。

**1. 考察点**

- 能否说清三种备份**数据组织方式的本质差异**，而不是背概念。
- 是否能从"恢复速度、存储成本、RPO、上游压力"四个维度做结构化对比。
- 是否知道 PB 级场景下的**真实挑战**：存储成本爆炸、上游压力大、恢复链路长、跨 Region 同步延迟。
- 加分项：能结合 HDFS、对象存储、关系型数据库、湖仓表（Iceberg/Hudi）给出不同的备份组合。

**2. 参考答案框架**

**第一层：三种备份的核心定义。**

- **全量备份（Full Backup）**：每次备份整个数据集。优点是恢复最简单（任何时间点都可独立恢复）；缺点是**存储成本高、上游压力大（每周期拷全量）**。
- **增量备份（Incremental Backup）**：只备份**自上次任意备份**以来的变化。优点是体积小、上游压力小；缺点是**恢复链路长**——需要 last full + 之后所有 incremental。
- **差异备份（Differential Backup）**：只备份**自上次全量**以来的变化。介于两者之间——恢复只需 last full + last differential，恢复链路比增量短；代价是体积随时间膨胀。

**第二层：四维结构化对比。**

| 维度 | 全量备份 | 差异备份 | 增量备份 |
| --- | --- | --- | --- |
| 单次备份体积 | 最大（=全量数据） | 中等（=上次全量后变化） | 最小（=上次任意备份后变化） |
| 备份速度 | 最慢 | 中等 | 最快 |
| 恢复速度 | 最快（单点恢复） | 中等（last full + last diff） | 最慢（last full + N 个 increment） |
| 存储成本 | 最高（线性 × 周期数） | 中等（膨胀但有上界） | 最低（接近增长量） |
| RPO | 等于备份周期 | 等于增量周期 | 等于增量周期 |
| 上游压力 | 最大 | 中等 | 最小 |

**第三层：PB 级的真实挑战。**

PB 级数据下，三种备份都不能直接用：

- **全量备份不可行**：每周拷 1 次 PB 数据，3 个月备份窗口内的存储 + 跨 Region 带宽成本就是天文数字。Google / Amazon 内部基本不做"传统全量备份"。
- **增量备份恢复链路爆炸**：每天 1 次增量、保留 30 天，恢复时要拼 last full + 30 个 increment；任何一个 corrupt 就要回退到更早的 full。
- **差异备份体积膨胀**：到 backup 周期末差异可能接近全量。

PB 级的正确组合是**"全量 + 增量 + 日志 + 快照 + 时间旅行"** 五件套：

- **小时级：日志（binlog / WAL / CDC）**：用 CDC（Debezium / Maxwell / 阿里 DTS）做变更流，天然分钟级 RPO。
- **天级：差异 + 快照**：每天差异备份 + 文件系统快照（ZFS / LVM / EBS Snapshot），覆盖人为误删和勒索软件。
- **周级：全量压缩归档**：每周 1 次全量，但落**低成本对象存储 + 列存压缩 + 去重**，控制成本。
- **永远：异地复制 + 时间旅行**：数据本身走异地异步复制 / 多 Region，湖表走 Iceberg / Hudi 的 time-travel 能力，恢复秒级到任意时间点。

**第四层：不同存储的备份侧重。**

- **关系型数据库（MySQL / PostgreSQL）**：binlog 复制（PITR）+ xtrabackup 全量 + binlog 差异。MySQL 的 PITR 可恢复到任意时间点。
- **HDFS / 对象存储**：HDFS Snapshot + DistCp + Erasure Coding。最常用的是 HDFS Snapshot（秒级生成、占用少）。
- **湖仓表（Iceberg / Hudi / Delta Lake）**：snapshot + time-travel + 增量读。天生具备按 snapshot 恢复的能力，不需要传统全量。
- **K8s / 微服务**：Velero / Kasten 做 etcd + PV + 资源对象备份。

**第五层：行业实践。**

- **AWS S3 跨 Region 复制（CRR）**：异步把对象复制到目的 Region，对象级 RPO 接近实时且成本可控，是云时代最常用的"异地备份即服务"。
- **Google Spanner / Bigtable 内置多 Region 复制**：底层是 PAXOS / 多 Region 强一致，对外不暴露"备份"概念，备份通过数据复制 + 快照实现。
- **阿里 OSS 跨 Region 复制 + 数据湖归档**：OSS 跨 Region 异步复制，配合 DataWorks / OSS-HDFS 做归档，对外提供"备份 + 归档"一体化服务。
- **Netflix 多 Region 灾备与快照**：Cassandra 跨 Region 异步复制 + S3 持久化日志，配合业务层 time-travel 恢复会话状态。
- **京东 PB 级数据备份**：通过 HDFS Snapshot + DistCp + 跨 Region 复制三件套支撑电商业务数据，是国内大型电商的标准组合。
- **中国电信 / 中国移动运营商级数据归档**：计费 / 营账等核心数据采用 RPO = 0 强一致 + 异地异步归档双轨制，符合"留存即合规"要求。

**3. 常见陷阱**

- **背三种定义而不讲恢复链路。** 面试官真正想知道的是"哪种最易恢复"，必须主动讲增量恢复的链路爆炸问题。
- **忽视 PB 级下的存储 / 带宽成本。** 一上来就说"每天全量备份"会被立刻判定为没实战过。
- **把"快照"当成备份。** 快照 ≠ 备份。快照依赖源存储副本，若存储本身被勒索软件加密，快照也是受害者。必须异地 + 不可变（WORM）才安全。
- **不做恢复演练。** 备份方案没演练等于没备份——这是真实生产的第一杀手。
- **忘 CDC 与备份的差异。** CDC 是变更流的"流式备份"，适用于分钟级 RPO；批量全量 + 增量适用于小时级 / 天级 RPO。两者正交，组合使用。

**4. 追问预测**

- **「PB 级数据下，最节省成本的备份策略是什么？」** 答：组合拳——CDC（变更流）+ 每周一次列存压缩全量（落低成本对象存储 + 开启去重）+ 每日差异 + 异地异步复制 + Iceberg/Hudi 的 time-travel。没有"标准方案"，取舍依赖业务 RPO / RTO 等级。
- **「全量备份和快照的区别？」** 答：全量是逻辑拷贝（独立可恢复）；快照是物理层引用（源存储不可丢失）。**生产环境的最佳实践是"全量到独立存储 + 快照到同一存储"组合**，避免勒索软件双杀。
- **「勒索软件场景下，如何设计不可篡改的备份？」** 答：异地 + WORM（Write-Once-Read-Many）+ 最小特权 + 定期恢复演练。AWS S3 Object Lock、阿里 OSS 保留策略、Azure Blob Immutable Storage 都是不可变存储的代表能力。
- **「MySQL PITR 是怎么实现的？」** 答：基于 binlog + 全量备份。恢复时先恢复 last full + last diff，再 replay binlog 到指定时间点。RPO 等于 binlog 保留周期。

- 阿里云《企业级数据备份与归档最佳实践》——OSS 跨 Region 复制 + 归档的国内大型电商落地。
- **AWS S3 Cross-Region Replication 的工业实践** —— Netflix、Uber 等公司大量使用 S3 CRR 做跨 Region 数据异步复制，对象级 RPO 接近实时且成本可控，是云时代"备份即服务"的代表。
- **Google Spanner 的多 Region 强一致替代"备份"** —— 通过 PAXOS + TrueTime 把跨 Region 复制做成强一致，对外不暴露"备份"概念，是分布式数据库时代的备份新形态。
- **阿里 OSS 跨 Region 复制 + 湖仓归档** —— 阿里电商数据通过 OSS 跨 Region 复制 + DataWorks 归档一体化，支撑双 11 数据资产灾备，是国内大型电商标准组合。
- **京东 PB 级 HDFS Snapshot + DistCp** —— 京东核心交易 / 仓库数据通过 HDFS Snapshot + 跨集群 DistCp 复制到灾备集群，电商场景下 PB 级 RPO = 小时级、RTO = 小时级。

#### §DR.3 异地多活（Multi-Region Active-Active）与灾备（DR）的核心差异是什么？企业如何根据业务做出选型？

**1. 考察点**

- 是否真正理解二者**架构形态的根本差异**——异地多活是"两个中心同时服务"，灾备是"主备 + 切换"。
- 能否说清异地多活的**关键技术挑战**：数据一致性、流量调度、单元化、跨 Region 写入。
- 是否能从**业务类型、合规要求、预算、可承受的复杂度**四个维度做选型，而不是"异地多活就是好"。
- 加分项：能给出真实的反例——某些业务强行做异地多活反而更危险。

**2. 参考答案框架**

**第一层：定义与架构形态。**

- **灾备（DR）**：主中心承担所有流量，灾备中心待命（冷 / 温 / 热），故障时通过切换（manual / auto）把流量切到灾备。**承诺**：业务最终一致性 + 故障时短暂中断。
- **异地多活（Multi-Region Active-Active）**：多个中心**同时承担生产流量**，故障时不需要整体切换——局部路由调整即可。**承诺**：业务持续服务 + 数据最终一致 / 强一致。

**第二层：差异维度对比。**

| 维度 | 灾备 | 异地多活 |
| --- | --- | --- |
| 常态承载 | 主中心 100% | 各 Region 各承担一部分 |
| 故障时行为 | 切换（停服 → 启动备） | 局部路由调整（基本不停服） |
| 数据一致性 | 最终一致（同步 / 异步复制） | 强一致或最终一致 |
| 实现复杂度 | 中 | 高（流量调度、单元化） |
| 成本 | 中等（备中心资源闲置或半负载） | 高（双倍 / 多倍资源） |
| 适用业务 | 中等可用性需求 | 强连续性需求（金融、电商） |
| 典型 RPO / RTO | RPO 秒/分级、RTO 分钟级 | RPO = 0、RTO 秒级 |

**第三层：异地多活的关键技术挑战。**

异地多活不是"双倍资源就行"，它有四道工程难题：

1. **数据一致性**：跨 Region 强一致（如 OceanBase / Spanner）写入延迟高；异步复制则丢数据风险大。**最常见方案是单元化（Cell）**——按用户 / 业务维度切分，每单元落在固定 Region，单元内强一致、跨单元最终一致。
2. **流量调度**：DNS + Global Load Balancer + 单元化路由，按用户 ID / 业务 ID 把请求路由到对应 Region。**典型架构**：GSLB（Global Server Load Balancer）+ 单元化路由 + 异地专线。
3. **数据同步**：跨 Region 同步链路必须可靠 + 可观测。CDC + 消息队列 + 异地专线 + 同步延迟监控 + 同步断点告警，缺一不可。
4. **冲突解决**：跨 Region 同时写入冲突需要策略——LWW（Last Write Wins）/ CRDT（Conflict-free Replicated Data Types）/ 业务层幂等。**金融场景**通常通过单元化回避冲突，**互联网场景**接受最终一致 + 业务容错。

**第四层：选型决策表。**

不是所有业务都需要异地多活。以下决策表给出可量化的判断：

| 业务特征 | 推荐方案 | 理由 |
| --- | --- | --- |
| 金融核心（账户、支付） | 异地多活（强一致）或两地三中心（同城双活 + 异地灾备） | 监管 + 业务连续性双重要求 |
| 电商交易（订单、商品、库存） | 异地多活 + 单元化 | 双 11 / 黑五峰值流量、跨地域用户体验 |
| 互联网应用（UGC、社交） | 异地多活（最终一致） + 业务容错 | 用户体验优先、丢少量数据可接受 |
| 内部 OA / ERP | 灾备（温备 / 热备） | 内部用户容忍度较高、ROI 不划算 |
| 数据分析 / 报表 | 灾备（冷备 / 定时备份） | 凌晨跑批故障 + 几小时延误可接受 |
| AI 推理服务 | 异地多活 + 模型副本跨 Region | 推理延迟敏感、GPU 资源弹性 |
| 中小公司 / 创业初期 | 云厂商 DRaaS（如 AWS CloudEndure、Azure Site Recovery） | 投入低、上线快 |

**第五层：行业实践。**

- **阿里异地多活**：双 11 场景的标杆。基于单元化（Cell）架构，按用户 ID 切分，每个单元自包含应用 + 数据、落在某个机房内形成完整服务闭环，OceanBase 跨 Region 强一致，单元内 RPO = 0、单元间 RTO 秒级。
- **字节跳动多活**：抖音 / TikTok 全球多活（Level 6）。海外多 Region 部署 + 单元化 + 业务层冲突解决（如评论的 CRDT）。
- **AWS 全球多活**：CloudFront + Route 53 + Lambda@Edge，是 SaaS 公司做全球多活的典型路径。
- **招行异地灾备**：监管级金融场景，做"两地三中心"（同城双活 + 异地灾备）而非异地多活，原因是金融监管对最终一致的容忍度低 + 多活架构复杂度超出 ROI。
- **美团多活**：外卖 / 到店等业务按城市做"区域多活"，城市级故障时切到同城备中心，跨地域按单元隔离——是本地生活场景的多活范本。
- **微众银行金融云异地多活**：基于云原生 + 多 Region 部署 + 单元化，账户核心 RPO = 0、信贷 / 风控异步复制 RPO = 秒级。
- **Google Spanner 全球多活**：通过 TrueTime + Paxos 把跨大洲机房做成强一致，是理论意义上"全球多活 = 强一致"的工程答案。
- **Netflix 全球多活**：Cassandra 多 Region 异步复制 + 业务容错（用户位置 / 推荐用本地缓存），代价是 RPO > 0，但 RTO 秒级且成本可控。

**3. 常见陷阱**

- **把异地多活当成"更高版本的灾备"。** 二者是不同的架构形态，不是简单升级。
- **忽略单元化的复杂度。** 不谈单元化就讲异地多活，会被认为没真正做过——单元化是异地多活的"灵魂"。
- **把成本只算基础设施。** 异地多活的真实成本是基础设施 + 流量调度 + 单元化改造 + 数据同步 + 业务侧容错改造，必须算总账。
- **强推异地多活到所有业务。** 一刀切到所有业务是反模式——内部 OA 完全不需要异地多活。
- **忽视监管约束。** 金融行业跨境数据传输有法规限制，强行做异地多活可能触发监管红线。

**4. 追问预测**

- **「异地多活和单元化的关系是什么？」** 答：单元化是异地多活的"灵魂"。异地多活必须按业务维度（用户 / 业务 ID）把请求路由到固定 Region，避免跨 Region 写入冲突——这就是单元化。阿里"三地五中心"按单元切分是这一思想的最经典实现。
- **「字节抖音怎么做到全球多活的？」** 答：海外多 Region + 单元化（按 user_id 路由）+ 业务容错（如评论用 CRDT 解决冲突）+ 跨 Region 专线，是互联网级多活的代表。
- **「异地多活数据冲突怎么解决？」** 答：避免冲突（单元化路由）+ 检测冲突（数据对账）+ 解决冲突（LWW / CRDT / 业务层幂等）。不同业务用不同策略。
- **「监管要求下金融做不了异地多活吗？」** 答：可以做，但需要满足两个前提——单元化隔离 + 跨 Region 同步在监管可接受范围。微众、平安均有国内合规的异地多活实践。

**5. 参考资料**

#### §DR.4 灾备演练（DR Drill）的工程价值是什么？怎样设计才能让演练真正有效，而不是流于形式？

**1. 考察点**

- 是否理解**灾备演练是容灾体系的最后一公里**——只备份不演练等于没备份。
- 能否区分不同演练类型（桌面演练 / 部分演练 / 全量切换 / 实战演练）。
- 是否能从**业务、技术、组织**三个维度分析演练失败的原因。
- 加分项：能给出"演练发现的真实故障"案例（如切换文档过期的真实事件），以及如何用混沌工程 + 灰度发布做日常验证。

**2. 参考答案框架**

**第一层：为什么要演练。**

灾备只"备"不"练"是行业第一大反模式。数据备份往往存在但**切换流程没人跑过**——故障真发生时才发现：切换文档过期、Runbook 步骤缺失、负责人离职、依赖服务不可用。

- **AWS 2022 us-east-1 outage 复盘**：常规故障但部分客户因 DR 流程未演练导致恢复时间远超设计值。
- **2017 年 S3 outage**：AWS S3 误删导致大量企业服务降级，许多企业的"备份"在恢复时发现 RTO 远超设计——演练缺失是主因。

演练发现的真实问题包括：备份数据 corrupt / 不可读、跨 Region 网络断开、依赖服务未容灾、负责人失联、监控告警未触发、自动化脚本失效。

**第二层：演练类型分级。**

按深度递增：

- **桌面演练（Tabletop Exercise）**：会议室场景推演，"如果 Region A 挂了，我们该怎么做"——只过流程。
- **部分演练（Component Drill）**：演练某个组件（数据库切换、DNS 切换、消息队列切换）。
- **全量演练（Full DR Drill）**：模拟完整故障（机房级 / Region 级），真实执行切换。
- **实战演练（Live Cutover）**：在真实业务时段演练，业务真实受影响——最高风险。

头部企业的频率：

- **桌面演练**：每月 1 次。
- **部分演练**：每季度 1 次。
- **全量演练**：每年 1–2 次。
- **实战演练**：阿里双 11 前 1 次（不影响用户）、Google Chaos GameDay（每周 1 次，参与者用 GameDay 框架主动注入故障）。

**第三层：演练的关键设计要点。**

1. **业务分级 + 风险分层**：核心交易先演练，对业务影响小的做"实战演练"、核心做"演练窗口"演练。
2. **明确 RTO 验收标准**：演练必须有"达成 RTO < X 分钟"的成功标准，**不允许无限时演练**。
3. **发现问题的优先级**：演练不是"必成功"，其核心价值是**发现问题**。演练总结必须输出"问题清单 + 改进项 + 责任人 + 时限"。
4. **跨团队参与**：研发 / SRE / DBA / 安全 / 客服 / 产品 / 业务方必须全员参与。故障切到备中心后谁对客户回话、谁对账、谁开发票——全流程跑通。
5. **混沌工程常态化**：演练不应该只在 DR Drill 时才做。Netflix Chaos Monkey / AWS Fault Injection Simulator / 阿里 ChaosBlade / ByteChaos 等**把混沌工程做成日常**——随机注入故障，每天都在验证容灾能力。

**第四层：演练失败的常见原因。**

| 失败原因 | 后果 |
| --- | --- |
| Runbook 过期 | 切换时发现文档与现实不符 |
| 负责人离职 | 关键角色无备份 |
| 自动化脚本失效 | "自动切换"无人维护 |
| 跨 Region 链路断 | 演练才发现同步通道不通 |
| 业务侧容错缺失 | 切换后业务逻辑正确性无法保证 |
| 数据 corrupt | 演练恢复时发现备份坏 |
| 监控告警缺失 | 切换后没人发现"切完了吗" |

**第五层：行业实践。**

- **Netflix Chaos Monkey + Simian Army**：把"随机杀实例"做成日常，每天都在验证弹性。Netflix 工程文化的核心组成。
- **Google DiRT（Disaster Recovery Testing）**：每年大规模全公司演练 + 每周 GameDay 实战，是业界最成熟的 DR Drill 范式。
- **AWS Fault Injection Simulator + GameDay**：AWS 把混沌工程做成云服务，企业可在云上做灾备演练。
- **阿里 ChaosBlade + 双 11 大促演练**：每年双 11 前 1 个月全公司压测 + 演练，验证容灾链路、限流、降级、应急预案。
- **招行 / 平安季度 DR 演练**：金融行业受监管要求，季度全量演练 + 桌面演练 + 监管侧可见报告。
- **ByteDance ByteChaos**：字节内部混沌工程平台，覆盖微服务 / 数据库 / 中间件 / 跨 Region 全栈注入。

**3. 常见陷阱**

- **把桌面演练当全量演练。** 桌面演练 = 推演，不真正切换。讲不清楚这一点会显得没真正做过。
- **不设成功标准。** 没有 RTO / RPO 验收标准的演练是没有意义的，等于"开了会、发个纪要"——这是行业第一陷阱。
- **不输出改进项。** 演练后发现问题没改进机制，问题会沉淀到下一次故障爆发。
- **不敢做实战演练。** 永远躲在演练窗口里，永远测不到真实业务的影响。
- **忽视业务侧容错。** 演练只测基础设施不测业务，会出现"基础设施切完了，但业务逻辑异常"。

**4. 追问预测**

- **「演练发现的问题怎么跟踪？」** 答：演练总结输出 P0/P1/P2 改进项，每项指定责任人 + 时限；下次演练前回溯"上次改完了吗"。Netflix / Google 都有公开的 Postmortem 文化和跟踪机制。
- **「混沌工程和灾备演练的区别？」** 答：混沌工程是日常的、随机的、小颗粒度的注入；灾备演练是周期性的、计划性的、大颗粒度的全量切换。两者互补——混沌工程做"日检"，灾备演练做"年检"。
- **「核心交易怎么演练不影响用户？」** 答：用影子流量 + 流量复制（TCP Replay / 流量回放）+ 灰度切换。阿里双 11 的全链路压测是把真实流量复制到演练环境，跑完了再切真实流量。
- **「金融行业监管对演练的要求？」** 答：监管要求核心系统年度演练 + 季度桌面演练 + 监管侧可见报告。监管会看演练结果、改进行度，是合规硬指标。

- **阿里双 11 全链路压测 + 大促演练** —— 双 11 前 1 个月的全链路压测 + 演练，把真实流量复制到压测环境，是国内电商大促容灾验证的标准动作。

#### §DR.5 MTTR、MTBF 与可用性（Availability）三个指标如何相互推导？请给出一个企业级 SLA 的真实设计案例。

**1. 考察点**

- 是否理解**可用性公式**：`可用性 = MTBF / (MTBF + MTTR)`。
- 能否根据 SLA 反推 MTTR / MTBF 设计——给定 99.99% 承诺，意味着每年最多停 52.6 分钟。
- 是否知道 SLA 的"层级性"——基础设施 SLA、应用 SLA、业务 SLA 是不同的承诺。
- 加分项：能算出 SLA 化合价（Composite SLA），识别级联故障的根因。

**2. 参考答案框架**

**第一层：基础定义。**

- **MTBF（Mean Time Between Failures）**：平均故障间隔时间，**衡量的是"系统有多频繁出故障"**。
- **MTTR（Mean Time To Repair）**：平均修复时间，**衡量的是"出了故障恢复多快"**。
- **可用性（Availability）**：系统正常服务的时间占比，公式：`A = MTBF / (MTBF + MTTR)`。

**第二层：从 SLA 反推 MTTR。**

常用 SLA 目标对应关系：

| SLA | 年停机时间 | 月停机时间 | 周停机时间 |
| --- | --- | --- | --- |
| 99% | 3.65 天 | 7.31 小时 | 1.68 小时 |
| 99.9% | 8.77 小时 | 43.83 分钟 | 10.08 分钟 |
| 99.99% | 52.60 分钟 | 4.38 分钟 | 1.01 分钟 |
| 99.999% | 5.26 分钟 | 26.30 秒 | 6.05 秒 |

设计 SLA 时反过来用：如果承诺 99.99%，要求年停机 ≤ 52.6 分钟。结合业务 MTBF（假设每天 1 次故障，即年 365 次），反推 MTTR ≤ 8.6 秒（52.6 分钟 ÷ 365 次）。这正是为什么"异地多活 + 自动切换"对核心系统是必须的——MTTR 太长会击穿 SLA。

**第三层：SLA 的层级性。**

一个业务可用性 = 它依赖的每个组件可用性的乘积。这就是 **SLA 化合价（Composite SLA）**。

举例：

- Web 服务 99.95% × App 服务 99.95% × 数据库 99.9% × 存储 99.9% × DNS 99.5% = 总可用性 ≈ 99.2%。

这就是"99.99% 单组件 SLA 看似很高，乘起来只剩 99.2%"的真相。所以：

- **不能用一个组件 SLA 等于业务 SLA**——必须每个组件都做容灾。
- **找出最弱环节**——SLA 化合价是定位级联故障根因的工具。
- **Cloud Provider SLA 是承诺下限**——AWS 单 Region EC2 SLA 是 99.99%，但 CloudFront 是 99.5%。设计业务 SLA 必须用"组件 SLA ≤ 业务 SLA"的反推。

**第四层：故障分级与降级策略。**

真实生产中，MTTR 不可能真的做到秒级。降级路径是常态：

- **降级（Degradation）**：故障期间关闭非关键功能（推荐 / 评论 / 个性化），保留核心（登录 / 下单）。
- **熔断（Circuit Breaking）**：下游不可用时切到默认响应，避免雪崩。
- **限流（Rate Limiting）**：保护系统不被突发流量打垮。
- **隔离（Isolation）**：单元化 / 泳道，让一个用户 / 业务的问题不影响其他。

这些手段让 MTTR 实际"被延长"——业务侧感知到的停机时间可能远低于真实 MTTR。

**第五层：行业实践。**

- **Google SRE 的 Error Budget**：把 SLA 翻转为 Error Budget（每季度允许的失败预算），用预算驱动发布决策——预算耗尽则冻结发布、强制修复。Google 把 SLA 从"约束"变成了"工程工具"。
- **AWS Multi-AZ SLA**：单 AZ 99.95%、Multi-AZ 99.99%、Multi-Region 99.999%——AWS 通过 SLA 引导客户分级投入。
- **阿里 P0/P1/P2 SLA**：核心系统 99.99%、重要系统 99.95%、一般系统 99.9%，按业务等级差异化承诺。
- **Netflix 不承诺 SLA 的服务设计**：Netflix 很多服务做"无 SLA 设计"——通过降级 + 业务容错保证用户体验，而非依靠基础设施 SLA。
- **Microsoft Azure SLA Framework**：每个云服务都公布 SLA 卡片，客户可直接看到承诺。

**3. 常见陷阱**

- **直接背 SLA 数字而不讲反推过程。** 关键能力是"给定业务 SLA 反推每个组件的可用性设计"，不是"99.99% ≈ 52 分钟/年"。
- **忽略 SLA 化合价。** 这是最大陷阱——5 个 99.9% 不是 99.999%，而是 99.5% 左右。
- **把降级不当回事。** 真实生产中降级贡献的可用性比"基础设施切换"更高。只讲切换不讲降级是肤浅回答。
- **不绑定业务影响。** 没有"为什么要这个 SLA"的业务换算（每多停 1 分钟损失多少），等于没做 SLA 设计。

**4. 追问预测**

- **「给定业务 SLA = 99.99%、5 个依赖组件，如何设计各组件 SLA？」** 答：均分到 99.998% 左右，每个组件都要 Multi-AZ / 自动切换，且最弱组件（通常 DNS 或 DB）需要 Multi-Region。
- **「什么是 SLA 化合价？为什么不能简单按 99.99% × n 个组件设计？」** 答：因为可用性是"所有组件都正常"的联合概率，乘以子集组合不是叠加。n 个独立组件每个 99.99%，总可用性是 99.99%^n（不是 n × 99.99%）。
- **「Error Budget 怎么落地？」** 答：每季度按 SLA 计算允许的失败时间，超预算时冻结变更、强制可靠性工作。Google SRE 的标准做法。
- **「SLA、SLO、SLI 三者关系？」** 答：SLI 是指标（请求成功率 / 延迟）、SLO 是 SLI 的目标（如 99.9% 成功）、SLA 是对客户的商业承诺（含未达成时的赔偿）。三者从下到上、约束从轻到重。

**5. 参考资料**

- Google SRE Workbook——SLO / Error Budget / MTTR 的完整方法论。
- AWS Service Level Agreements (SLAs) 官方文档——每个云服务的 SLA 数字与化合价计算。
- The Site Reliability Engineering Book（Beyer, Jones, Petoff, Murphy）——SLI / SLO / Error Budget 的原始定义。
- Microsoft Azure SLA Summary——多云 SLA 对比的参考。
- 阿里集团 SRE 实践——大型互联网公司 SLO 体系的国内落地。
- **Google SRE 的 Error Budget 实践** —— 把 SLA 翻转为 Error Budget 驱动发布决策——预算耗尽则冻结发布，是大型互联网公司 SLA 工程的代表性方法论。
- **AWS 分级 SLA 体系** —— 单 AZ 99.95%、Multi-AZ 99.99%、Multi-Region 99.999% 的分级承诺，让客户按需选择并用 SLA 引导分级投入。
- **Netflix 的"无 SLA 设计"** —— 通过降级 + 业务容错保证用户体验，而非依赖基础设施 SLA，是面向用户体验而非技术指标的可用性工程典范。
- **阿里 P0/P1/P2 SLA 分级承诺** —— 核心系统 99.99%、重要 99.95%、一般 99.9% 的差异化承诺，是大型电商按业务等级差异化 SLA 设计的代表。

#### §DR.6 业务连续性管理（BCM）与合规监管：等保 / GDPR / SOX / 金融监管对容灾有哪些硬性要求？

**1. 考察点**

- 是否理解**BCM 是容灾的上层框架**——不只是技术，还包含组织、流程、人员、文档、审计。
- 能否列出国内外**主要法规对容灾的具体要求**——等保 2.0（等保 3.0 尚未发布）、GB/T 20988、GDPR、SOX、PCI DSS、金融监管指引。
- 是否能把合规要求**翻译为工程指标**——"等保三级要求 RPO / RTO 满足业务连续性需要"对应什么？
- 加分项：能给出真实的合规级容灾设计案例（金融、医疗、运营商）。

**2. 参考答案框架**

**第一层：BCM 的定义与组成。**

**业务连续性管理（Business Continuity Management, BCM）** 是一套**从业务视角出发，覆盖风险评估、业务影响分析、连续性策略、演练验证、危机沟通、恢复重建**的完整管理体系。ISO 22301 是国际通用标准。

容灾（DR）是 BCM 的一部分，但 BCM 远大于 DR：

- **业务连续性策略**：业务分级 / 关键业务识别 / 业务影响分析（BIA）。
- **危机沟通**：故障时客户 / 监管 / 媒体 / 员工的对外通报流程。
- **人员备份**：关键岗位的"双人备份"制度，避免单点。
- **文档管理**：Runbook / 应急流程 / 联系方式 / 知识沉淀。
- **演练 + 审计**：定期演练 + 监管报告。

**第二层：国内外法规对容灾的具体要求。**

| 法规 | 适用范围 | 容灾要求 |
| --- | --- | --- |
| **GB/T 20988-2007** | 中国所有行业 | 6 级灾备等级 + RPO / RTO 区间 |
| **等保 2.0** | 中国信息系统 | 三级"应能支撑业务连续性"、四级"应保证业务连续性" |
| **GDPR** | 欧盟业务 | 数据丢失需 72 小时内通报 + 备份可恢复性 |
| **SOX** | 美国上市公司 | 财务系统可审计性 + 备份可恢复性 |
| **PCI DSS** | 信用卡业务 | 数据加密 + 密钥备份 + 季度 DR 演练 |
| **《商业银行数据中心监管指引》** | 中国银行 | 至少两地三中心 + 核心 RPO / RTO 指标 |
| **HIPAA** | 美国医疗 | 患者数据可恢复性 + 6 年保留 |
| **ISO 22301** | 国际通用 | BCM 完整框架 |

**第三层：等保 2.0 的容灾条款要点（等保 3.0 尚未发布，暂无正式条款；下图所列三级 / 四级要求均出自等保 2.0）。**

- **等保三级**：要求"应能提供业务连续性保障"，具体要求灾备中心、关键数据备份、应急预案、年度演练。商业银行需达到"异地灾备 + 同城双活"。
- **等保四级**：要求"应保证业务连续性"，必须是异地多活 / 全球多活。

第四级对应 GB/T 20988 的高等级（Level 5 以上，业内俗称「异地多活」；俗称与标准原文等级名不一致），是涉密行业（如军工、核工业）或国家级关键基础设施的硬指标。

**第四层：金融行业的硬性监管要求。**

国内金融监管对容灾最严：

- **两地三中心**：同城双活 + 异地灾备是硬性要求。
- **核心系统 RPO / RTO**：商业银行、保险公司、券商的核心业务系统 RPO ≤ 30 秒、RTO ≤ 30 分钟是行业默认门槛。
- **季度 DR 演练**：必须有演练报告，监管可见。
- **灾备切换演练**：监管机构（银保监会、人行）会审核演练记录，未演练或演练失败需要整改。

**第五层：行业实践。**

- **招行核心系统 BCM**：两地三中心（同城双活 + 异地灾备）+ 季度全量演练 + 监管侧可见报告，是国内大型商业银行的标准范本。
- **平安银行金融云 BCM**：监管驱动的容灾 + 业务连续性管理，跨集团子公司协同的灾备演练。
- **微众银行金融云 BCM**：云原生 + 异地多活 + 单元化 + 业务连续性管理，是互联网银行在云时代做 BCM 的代表。
- **中国电信运营商级 BCM**：计费 / 营账核心系统 RPO = 0 + 异地灾备 + 季度演练，是运营商行业的合规范式。
- **LinkedIn 合规级容灾**：遵守 SOX + GDPR 双重合规，MySQL 主备 + Oracle 异地灾备 + 加密备份 + 合规审计日志。
- **Amazon AWS 多 Region SLA + 合规**：SOC2 / ISO 27001 / HIPAA / PCI 多重合规，云服务自身就是合规载体。
- **阿里集团合规级容灾**：等保三级 + 行业合规 + 内部 BCM 完整体系，电商 / 金融 / 云三大业务均建立差异化 BCM 设计。

**3. 常见陷阱**

- **把 BCM 等同于 DR。** BCM 远大于 DR——BCM 是管理体系，DR 只是技术手段。
- **不区分国际 / 国内合规。** GDPR 的 72 小时通报是独立要求，与国内等保 / SOX 完全不同。
- **忽视监管演练。** 金融行业监管要求季度演练，未演练会被处罚。
- **不区分业务等级。** 一套 BCM 设计覆盖所有业务，是反模式。核心 / 重要 / 一般业务应有差异化设计。
- **忽略数据保留周期。** HIPAA / PCI 等对数据保留周期有硬要求（HIPAA 6 年、PCI 1 年），不是 RPO 越小越好。

**4. 追问预测**

- **「GDPR 72 小时通报对应到 RPO 怎么设计？」** 答：RPO < 72 小时是最底线（即可恢复）；但实际业务应做到 RPO < 24 小时（更安全）。GDPR 还要求数据可移植性 + 可删除——备份系统必须支持"指定用户的数据清除"。
- **「金融监管要求异地灾备，是不是所有金融机构都必须做两地三中心？」** 答：是。根据《商业银行数据中心监管指引》以及《银行业信息系统灾难恢复管理规范》，核心业务必须两地三中心；中小机构可选择"同业灾备"或"云灾备"作为合规路径。
- **「BCM 体系怎么落地到工程？」** 答：业务影响分析（BIA）→ 业务分级 → 容灾等级 → 容灾架构 → 演练 → 改进项 → 周期审计。把 BCM 翻译成"业务分级表 + 灾备等级表 + RPO/RTO 表 + Runbook + 演练计划"五份资产。
- **「等保三级和等保四级的容灾差异？」** 答：三级"应能支撑"（被动）、四级"应保证"（主动）。三级可以做异地灾备，四级必须异地多活。

**5. 参考资料**

- ISO 22301:2019《Security and resilience — Business continuity management systems》——BCM 的国际通用标准。
- GB/T 20988-2007《信息安全技术信息系统灾难恢复规范》——中国灾备等级国家标准。
- 等保 2.0 相关规范与解读——国内信息系统等级保护对容灾的要求（等保 3.0 尚未发布，对照仍按 2.0）。
- GDPR Article 33 / 34——欧盟数据保护法对数据丢失通报的 72 小时要求。
- 中国银保监会《商业银行数据中心监管指引》——金融行业容灾监管的具体要求。
- PCI DSS v4.0 Requirement 12.10——支付卡行业数据安全标准对灾备与演练的要求。
- **招行两地三中心 + 季度演练的金融 BCM 范本** —— 大型商业银行的核心系统按两地三中心（同城双活 + 异地灾备）部署 + 季度全量演练 + 监管侧可见报告，是国内金融行业 BCM 的标准答案。
- **微众银行金融云 BCM** —— 云原生 + 异地多活 + 单元化 + BCM 完整体系，是互联网银行在云时代做业务连续性管理的代表。
- **中国电信运营商级 BCM 体系** —— 计费 / 营账核心系统 RPO = 0 + 异地灾备 + 季度演练 + 重大事件 24 小时监管通报，是运营商行业的合规级 BCM 范式。
- **Amazon AWS 的合规驱动容灾设计** —— SOC2 / ISO 27001 / HIPAA / PCI 多重合规，云服务自身是合规载体，客户通过选择合规 Region 完成自己的合规要求。

### 8.4 通用答题心法

针对容灾与灾备主题的所有面试题，通用答题心法：

1. **先说约束再说选项**：业务 SLA / 合规要求 / 预算 → 容灾等级 → 架构形态。先讲清约束再讲清选项，面试官最想听的是"你为什么这么选"。
2. **分层回答**：业务层 / 技术层 / 组织层 / 合规层分别给出，不要把基础设施切换当成答案的全部。
3. **算账**：任何 RPO / RTO / 资源投入都要换算成钱（业务损失 / 资源成本 / 合规罚款），只讲技术不算账是常见低分陷阱。
4. **行业案例对照**：头部企业的公开实践（阿里 / Netflix / AWS / Google / 招行 / 中国电信等）是回答的"加分锚点"。
5. **风险与权衡**：永远不能只讲优点，每个选择都有代价，主动说出代价才显得资深。
