## 1. 概念与定位

### 1.1 是什么

**容灾（Disaster Recovery, DR）**是**在任意机房级 / 城市级 / 国家级故障下，确保业务能持续提供服务**的工程体系。

它由四个要素组成：

1. **风险评估**：识别可能的故障（机房故障、自然灾害、网络中断）。
2. **RPO / RTO 设计**：定义可容忍的数据丢失（RPO）和恢复时间（RTO）。
3. **容灾架构**：根据 RPO / RTO 设计容灾架构（冷备 / 温备 / 热备 / 多活）。
4. **演练验证**：定期演练容灾切换，验证恢复流程。

**核心指标**：

- **RPO（Recovery Point Objective）**：可容忍的数据丢失量。如 RPO = 0 表示不能丢数据。
- **RTO（Recovery Time Objective）**：可容忍的服务中断时间。如 RTO < 30 分钟。

**容灾等级**（国家标准 GB/T 20988-2007）：

| 等级 | 名称 | RPO | RTO | 描述 |
| --- | --- | --- | --- | --- |
| **Level 1** | 数据级灾备 | < 24h | — | 定期备份数据 |
| **Level 2** | 应用级灾备 | < 1h | < 12h | 备用环境 + 数据备份 |
| **Level 3** | 业务级灾备 | 分钟级 | 分钟级 | 业务连续性 |
| **Level 4** | 同城双活 | = 0 | 秒级 | 同城两机房同时服务 |
| **Level 5** | 异地多活 | = 0 | 秒级 | 异地多机房同时服务 |
| **Level 6** | 全球多活 | = 0 | 秒级 | 跨大洲多活 |

### 1.2 为什么需要

**业务驱动力**：

- **业务连续性**：金融、电商、医疗核心业务必须 7×24 不间断。
- **合规要求**：等保 2.0 / 3.0、GDPR、SOX 等合规要求灾备。
- **品牌信誉**：宕机 = 头条新闻 + 用户流失。
- **自然灾害**：地震、火灾、洪水、断电不可预测。
- **AI 时代**：AI 服务对延迟敏感，跨 Region 容灾成为标配。

**痛点**：

1. **RPO / RTO 定义不清**：业务说不清"能丢多少数据"。
2. **灾备中心不演练**：灾备环境只备份不验证。
3. **数据同步延迟**：跨 Region 同步延迟导致 RPO 失控。
4. **切换流程长**：切换要 1 小时以上。
5. **运维复杂**：多机房运维成本高。

**在高可用体系中的位置**：

```
[日常高可用] → [同城双活] → [两地三中心] → [异地多活] → [全球多活]
```

**与其他章的关系**：

- **Ch12 §01 单元化**：单元化让容灾粒度更细。

**传统阶段（2000s-2010s）**：

- 2000s：单机备份（磁带）。

## 2. 核心原理

### 2.1 关键概念定义

- **RPO（Recovery Point Objective）**：可容忍的数据丢失量。
- **RTO（Recovery Time Objective）**：可容忍的服务中断时间。
- **冷备（Cold Standby）**：备用环境不启动，数据备份，需手动启动。
- **温备（Warm Standby）**：备用环境启动但不全量，数据准实时同步。
- **热备（Hot Standby）**：备用环境全量启动，数据实时同步。
- **同城双活（Same-City Active-Active）**：同城两机房同时服务。
- **两地三中心（Two-Site Three-Center）**：同城两机房 + 异地灾备。
- **异地多活（Multi-Region Active-Active）**：异地多机房同时服务。
- **灾备切换（Failover）**：从主环境切到备环境。
- **灾备回切（Failback）**：从备环境切回主环境。
- **DR Drill（灾备演练）**：定期演练容灾切换。
- **Backup（备份）**：数据备份（全量 / 增量 / 差异）。
- **Snapshot（快照）**：数据快照。
- **PITR（Point-In-Time Recovery）**：时间点恢复。
- **Log Shipping（日志传输）**：binlog / WAL 实时传输。
- **CDC（Change Data Capture）**：变更数据捕获。
- **HA（High Availability）**：高可用。
- **DR（Disaster Recovery）**：容灾。

### 2.2 数学 / 形式化基础

**RPO / RTO 的数学定义**：

```
RPO = 故障发生时刻 - 最后一次成功备份时刻
RTO = 故障发生时刻 - 业务恢复时刻

例：
- 故障发生在 14:00
- 最后一次备份在 13:00（每小时备份一次）
- RPO = 1 小时
- 业务在 14:30 恢复
- RTO = 30 分钟
```

**备份策略公式**：

```
全量备份周期：T_full
增量备份周期：T_incremental
平均 RPO ≈ T_incremental / 2

例：
- 全量每天 1 次
- 增量每小时 1 次
- 平均 RPO ≈ 30 分钟
```

**可用性公式**：

```
可用性 = MTBF / (MTBF + MTTR)

其中：
- MTBF（Mean Time Between Failures）：平均故障间隔时间
- MTTR（Mean Time To Recover）：平均恢复时间

例：99.99% = 52.6 分钟/年
```

### 2.3 关键算法 / 方法

1. **备份策略**：
   - **全量备份**：每周 1 次。
   - **增量备份**：每天 1 次。
   - **Binlog 备份**：实时（分钟级 RPO）。
   - **PITR**：可恢复到任意时间点。

2. **同步策略**：
   - **同步复制**：强一致，延迟高（< 1ms）。
   - **异步复制**：最终一致，延迟低（秒级）。
   - **半同步复制**：折中，1 个从库同步 + 其他异步。

3. **切换策略**：
   - **手动切换**：运维手动操作。
   - **自动切换**：基于健康检查的自动切换。
   - **半自动**：自动检测 + 人工确认。

4. **数据一致性验证**：
   - **定期对账**：比对主备数据。
   - **CRC 校验**：文件级 CRC 校验。
   - **业务校验**：业务层验证数据完整性。

5. **AI 时代的容灾**：
   - **GPU 容灾**：跨 Region GPU 资源调度。
   - **模型容灾**：模型副本跨 Region。
   - **Agent 容灾**：Agent 状态跨 Region 同步。

## 3. 设计模式与范式

### 3.1 主要模式

#### 模式 1：冷备（Cold Standby）

- 备用环境不启动，只有数据备份。
- 故障时手动启动。
- RPO：小时级（取决于备份频率）。
- RTO：小时级（启动 + 恢复数据）。
- 成本最低。

#### 模式 2：温备（Warm Standby）

- 备用环境启动，但不全量（可能只有 DB，应用按需启动）。
- 数据准实时同步（分钟级）。
- 故障时手动切换。
- RPO：分钟级。
- RTO：分钟级（应用启动）。
- 成本中等。

#### 模式 3：热备（Hot Standby）

- 备用环境全量启动，数据实时同步。
- 自动切换（基于健康检查）。
- RPO：秒级。
- RTO：秒级。
- 成本高。

#### 模式 4：同城双活（Active-Active）

- 同城两机房同时服务。
- 故障时另一机房承接。
- RPO = 0，RTO < 1 分钟。
- 成本高（同城机房资源）。

#### 模式 5：异地多活

- 异地多机房同时服务（详见 [Ch12 §02](../02-multi-region/02-multi-region.md)）。
- RPO = 0，RTO < 1 分钟。
- 成本最高（跨 Region 带宽）。

### 3.2 适用场景决策表

| 业务类型 | 推荐等级 | RPO | RTO |
| --- | --- | --- | --- |
| 金融核心交易 | Level 5-6 | = 0 | 秒级 |
| 电商交易 | Level 5 | = 0 | 秒级 |
| 互联网应用 | Level 3-4 | 分钟级 | 分钟级 |
| 内部系统 | Level 2 | 小时级 | 小时级 |
| 数据分析 | Level 1 | 天级 | 天级 |

### 3.3 反模式与陷阱

#### 反模式 1：灾备只备份不演练

**现象**：灾备中心一直闲着，故障时无法切换。

**正解**：季度 DR 演练。

#### 反模式 2：RPO / RTO 不量化

**现象**：业务说不清"能丢多少数据"。

**正解**：业务 + 技术联合定义 RPO / RTO。

#### 反模式 3：跨 Region 同步延迟失控

**现象**：RPO 假设秒级，实际分钟级。

**正解**：监控同步延迟，告警异常。

#### 反模式 4：灾备切换流程不清

**现象**：故障时找不到切换文档。

**正解**：Runbook + 演练。

## 4. 工程实现

### 4.1 落地步骤

#### 阶段 1：风险评估（1 个月）

1. 识别关键业务。
2. 定义 RPO / RTO。
3. 评估潜在故障（机房级 / 城市级）。

#### 阶段 2：架构设计（1-2 个月）

1. 选择容灾等级。
2. 设计同步策略。
3. 设计切换流程。

#### 阶段 3：实施部署（2-3 个月）

1. 灾备中心建设。
2. 数据同步链路。
3. 健康检查 + 自动切换。

#### 阶段 4：演练验证（持续）

1. 季度 DR 演练。
2. 故障模拟（混沌工程）。
3. 改进项跟踪。

### 4.2 关键技术点

#### 1. MySQL Binlog 同步

```bash
# 主库配置
[mysqld]
server-id = 1
log_bin = /var/log/mysql/mysql-bin.log
binlog_format = ROW

# 从库配置（异步复制）
CHANGE MASTER TO
  MASTER_HOST='master.db.local',
  MASTER_USER='repl_user',
  MASTER_PASSWORD='${REPL_PASSWORD}',  # env var reference
  MASTER_LOG_FILE='mysql-bin.000001',
  MASTER_LOG_POS=4;

START SLAVE;
```

#### 2. PostgreSQL 流复制

```bash
# 主库
wal_level = replica
max_wal_senders = 3

# 从库（同步复制）
primary_conninfo = 'host=master.db.local port=5432 user=repl password=${REPL_PASSWORD}'
synchronous_commit = on
```

### 4.4 代码 / 示例

#### DR Runbook 示例

```yaml
# DR Runbook：电商核心交易系统
metadata:
  name: ecommerce-core-dr
  version: 1.0
  last_updated: 2025-01-01

rpo_rto:
  RPO: 30 seconds
  RTO: 5 minutes

dr_scenarios:
  - scenario: 主 Region 故障
    trigger: 主 Region 健康检查失败 > 2 分钟
    steps:
      - 1. 确认故障（Pingdom / Datadog）
      - 2. 联系 AWS Support
      - 3. 执行 DNS 切换（TTL 60s）
      - 4. 启动备用 Region 服务
      - 5. 验证业务恢复
    owner: sre-team
  
  - scenario: 数据库主库故障
    trigger: DB 主库健康检查失败
    steps:
      - 1. 自动切换到从库（HAProxy）
      - 2. 验证数据一致性（对账）
      - 3. 通知 DBA
      - 4. 修复主库
    owner: dba-team
```

## 5. 前沿演进（AI 时代）

### 5.1 LLM/Agent 时代的演进方向

#### 1. GPU 容灾

- **GPU 跨 Region 调度**：阿里云 EGS、AWS Inferentia。
- **GPU Spot 容灾**：Spot 故障时切到 On-Demand。
- **模型副本跨 Region**：避免单 Region GPU 故障。

#### 2. AI 推理容灾

- **多模型路由**：GPT-4 故障时切到 Claude / 本地小模型。
- **降级链路**：大模型 → 中模型 → 小模型 → 规则。
- **向量检索容灾**：跨 Region 向量索引冗余。

#### 3. AI 辅助 DR

- **AI 故障预测**：预测故障发生。
- **AI 决策助手**：自动决策切换策略。
- **AI 验证**：自动验证 DR 流程。

### 5.2 与 RAG / 向量库 / GraphRAG 的结合

RAG 容灾需要每个组件独立：

```
[Region A]：[Embedding] → [向量检索] → [LLM]
[Region B]：[Embedding] → [向量检索] → [LLM]   ← 容灾
```

**RAG 容灾策略**：

- **Embedding 容灾**：跨 Region Embedding 服务冗余。
- **向量索引容灾**：向量索引跨 Region 复制。
- **LLM 容灾**：多模型路由。

### 5.3 学术与工业最新进展（2024-2025）

- **AWS 2024**：发布 AI 辅助 DR 决策助手。
- **Azure 2024**：跨 Region DR 服务增强。
- **阿里云 2024**：三地五中心 + AI 推理容灾。
- **Google Spanner 2024**：全球多活 + AI 推理容灾。

### 5.4 未来 3-5 年趋势

1. **AI 主导的 DR**：AI 自动决策、自动切换。
2. **跨云 DR**：跨云厂商的容灾。
3. **Self-Healing DR**：故障自动恢复。
4. **AI 原生容灾**：把 AI 推理容灾作为一等公民。

## 6. 落地实践

### 6.1 真实案例

#### 案例 1：阿里双11 容灾

**背景**：双11 期间业务不可中断。

**关键实践**：

- **三地五中心**：杭州 2 + 上海 1 + 深圳 1 + 异地灾备 1。
- **单元化 + 异地多活**：业务按 Cell 切分，每 Cell 跨 5 中心。
- **DR 演练**：每月 1 次，每年 1 次大促演练。

**结果**：2015-2024 0 严重故障。

#### 案例 2：AWS DR 实践

**场景**：某 SaaS 公司使用 AWS DR。

**关键实践**：

- **Multi-AZ**：同城多 AZ（默认）。
- **Cross-Region Replication**：S3 / RDS 跨 Region 复制。
- **CloudEndure DR**：连续复制，RPO < 30s，RTO < 5min。
- **DR 演练**：季度演练。

**结果**：故障切换时间 < 5 分钟。

### 6.2 踩坑与经验

#### 坑 1：灾备只备份不演练

**解决**：季度 DR 演练，把演练当实战。

#### 坑 2：跨 Region 同步延迟

**解决**：监控同步延迟，告警异常。

#### 坑 3：切换流程不清

**解决**：Runbook + 演练 + 自动化。

### 6.3 落地路径（0→1, 1→10, 10→100）

#### 0→1

1. RPO / RTO 定义。
2. 数据备份。
3. 灾备中心。

#### 1→10

1. 温备 / 热备。
2. 自动切换。

### 7.2 决策树

```
你的业务可用性要求？
├─ 99% → 冷备
├─ 99.9% → 温备
├─ 99.99% → 热备 / 同城双活
└─ 99.999% → 异地多活

你的 RPO 要求？
├─ 天级 → 冷备
├─ 小时级 → 温备
├─ 分钟级 → 热备
└─ 秒级 → 同城双活 / 异地多活
```

### 7.3 组合使用

- **容灾 + 单元化**：单元化让容灾粒度更细。
- **容灾 + 异地多活**：异地多活是容灾的高级形态。
- **容灾 + 混沌工程**：验证容灾流程。
- **容灾 + 大促保障**：大促前的容灾演练。
