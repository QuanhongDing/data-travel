## 4. 工程实现

**先说本节与 §3 的分工**：§3 回答「有哪几档、各被什么约束逼出来、什么条件下会坏」；本节回答「选定之后怎么装上去」。两者的分界线是：**§3 的产物是一份决策，本节的产物是一串可被检查的东西**——签署过的目标登记表、跑得起来的同步链路、装了独立告警的观测、一份有实测值的演练记录。

本文件同时面向两类读者，但主路径是**存量改造**：绝大多数团队手上已经有一套复制链路、一份写着 RPO/RTO 的制度文件和一个从没真切过的备侧环境。从零搭建的读者可以直接从 4.1 顺读；**在存量系统上改造的读者，请把 4.1 当作顺序依据、把 §4.4 当作自己的主路径**——两者的第一步不同：从零搭的人先写目标，存量改造的人先量现状（现在的复制延迟是多少、上一次演练是哪一年）。

### 4.1 落地步骤

**Step 1：风险评估与目标签署（约 1 个月【经验】，随业务线数量与签署轮次变）**

1. 列业务清单，逐项只问两个问题：这份数据最多能丢多少（RPO）、这块服务最多能停多久（RTO）。答案由业务方签署，技术团队负责提供成本曲线供其选择，不代为填写。
2. 写故障域清单：要防的是机房级、城市级还是 Region 级。顺序是**先定故障域 → 再定 RPO/RTO → 最后才定技术档位**（为什么这个顺序不能换，见 §3.1）。
3. 画出共享依赖：控制面、IAM 与密钥、DNS、专线汇聚点、配置中心、发布系统——副本与主站共享的每一样东西，都只是把故障域按原样复制了一份（§3.1 的第四条约束）。
4. 给业务方一张成本曲线而不是一个方案：RPO 从小时级推到秒级、RTO 从小时级推到分钟级，各需要多少持续投入与多少不可逆的改造（数据模型、应用无状态化）。让业务在曲线上选点，而不是在方案上投票——**技术团队能做的是把代价讲清楚，不能替业务决定愿意为可用性付多少**。【经验】

- **产物**：一张「数据类 → RPO/RTO → 适用范围 → 签署人」登记表（形态见 §3.4 的分级登记表），外加一张共享依赖清单。适用范围一列必须写清「哪些数据、哪些路径」，否则 RPO=0 会被读成覆盖全部数据。
- **判据**：抽 3 行登记表，逐行问签署人「这个数字是您签的吗、它覆盖哪些路径、谁能在故障时宣布它不生效」。答不上来的行视为未签署，退回重签。再抽一条共享依赖，问「它挂了会发生什么」——这一条判据能筛掉大多数只在图上分开、实际共享控制面的「双活」。
- **为什么必须第一步**：后面三步全部以这两个数字为输入。同步还是异步由 RPO 决定（Step 2）；备侧常驻到什么程度由 RTO 决定（Step 3）；演练判什么算通过也由它们决定（Step 4）。目标若由技术团队自己拍，得到的一定是一份写着「RPO=0，RTO=5 分钟」的文件，而实际架构只覆盖机房级故障——这个缺口不会在日常暴露，只会在第一次真实故障里结算（§3.1 末尾）。

**Step 2：架构设计（1-2 个月【经验】，随是否需要应用无状态化改造变）**

1. 按 Step 1 的约束组合查 §3.3 的决策表选容灾等级与档位，并且**按数据类分别选**：交易、报表、日志三类不必同档，用一个统一目标覆盖全系统本身就是反模式（§3.5）。等级名称与 RPO/RTO 区间的对照见主文件 §1.1。
2. 定同步策略：哪些路径进同步复制、哪些只走异步，把同步集的成员与数量写下来——**同步集的边界就是 RPO=0 的边界**（机制见 §3.2.3）。
3. 定切换流程：探测信号有哪几类、按「全部满足」还是「多数满足」判定、谁有权说切、谁有权说切回、网络分区时站在哪一侧。这些必须在事前写死，不能留给故障当时讨论。
4. 定回切路径与数据追齐方式：切换方案里若不含回切，第一次真实故障后系统会永久停在备侧。

- **产物**：架构图 + 切换与回切流程 + 一份写清「哪些数据不在覆盖范围内」的目标说明书。
- **判据**：找一个没参与设计的人，让他照着流程文档做一次桌面推演，看能否说出「从探测到决策」这一步由谁在多长时间内完成。推演走不通，说明流程还停在架构图层面。再问一句「备侧的容量上限是多少、怎么测出来的」——答不出说明备侧能力尚未被量化。
- **为什么必须在实施前**：档位一旦进入实施，再改档位就等于换选址与数据模型，返工的不只是代码，还有已经采购的带宽、实例与专线（§3.6 的迁移代价列）。设计阶段改一次的成本，与实施后改一次的成本不在同一个量级。

**Step 3：实施部署（2-3 个月【经验】，随数据量与跨团队审批面变）**

1. 建备侧环境：按选定档位确定备侧常驻程度（冷 / 温 / 热 / 多活），并把「扩容上限」「配额」「出口白名单」这类要审批的事项提前办完——温备的 RTO 承诺就卡在这些审批上（§3.2.2）。
2. 铺数据同步链路：库级用日志复制（binlog / WAL），跨系统用 CDC，跨 Region 的集群资源用备份工具。各链路的配置要点与坑见 §4.2。
3. 装健康检查与自动切换：多信号交叉确认 + 防误切机制（fencing / quorum），并显式配置「分区时取保守侧」。
4. 装观测：把**复制延迟**、**副本存活**、**备份作业结果**拆成三个独立指标与告警。三者合成一个，等于三个都看不见（这是 §3.5 里「跨 Region 同步延迟失控」的直接成因）。

- **产物**：可运行的备侧环境 + 同步链路 + 切换脚本 + 三条独立告警 + 一份备侧启动耗时实测值。
- **判据**：在备侧跑一次不接流量的全链路启动并计时；抽一条复制链路，看它的延迟指标在过去 30 天有没有出现采集空白段——**空白段意味着「没有告警」可能只是「没有数据」**。
- **为什么必须排在演练之前**：演练要验证的是流程与清单，不是「环境能不能建起来」。把建环境的未知留到演练现场，演练就退化成一次排障，而排障耗时不计入任何 RTO 承诺。

**Step 4：演练验证（持续；建议每季度一次【经验】，随业务变更频率与合规要求变）**

1. 真演练而非桌面推演：真切、真恢复、**真回切**。
2. 每次记录三个数：实测 RPO（最后一次成功复制的时点与故障时点之差）、分段实测 RTO（探测 / 决策 / 执行三段分别记）、对账发现的不一致条数。
3. 用混沌工程做常态化的故障注入，补上演练现场造不出来的场景——尤其是**网络分区**（不是节点宕机）这一类只在分区下才暴露的故障（机制见 §3.5 第三条）。
4. 未通过项跟踪到关闭，并把它分成两类：「清单过期」（DNS 解析指向、证书与密钥有效期、IAM 与配额、第三方出口白名单、许可证、写死在连接串里的主站地址）与「逻辑缺陷」。前者的修法是把它纳入演练 checklist，后者的修法才是改代码。

- **产物**：一份带实测值的演练记录 + 未通过项台账 + 一份更新过的 Runbook 版本。
- **判据**：把上一次与这一次的实测 RPO/RTO 并排放，看差异有没有解释；抽一条未通过项，看它是否已关闭或已挂到具体角色与日期。再查一件事：这一次演练有没有动到回切流程。
- **为什么必须持续做**：那串一次性清单只有被读到的时候才会被更新，而它只在切换当天被读到。演练不可替代的作用，就是**让这份清单在故障到来之前保持有效**。同时，RPO/RTO 在演练之外不是属性，只是承诺——没有实测值，你不知道自己的能力在哪。

**最常被跳过的一步是 Step 4 里的「回切」与「实测值记录」，而不是演练本身。** 多数团队会切一次并宣布演练成功，但不会切回来、也不记录分段耗时。跳过的后果不在演练当天出现，而在第一次真实故障之后：系统停在备侧，主站变成一个无人维护的资产，而「双活」退化成「一套在跑、一套在闲置」——此时再想回切，要先重建一个已经停止接收变更的站点。判断有没有跳过，只需查一件事：演练记录里能不能找到一次**回切耗时**。

四步的一页速查（工期均为【经验】，随业务线数量、数据量与改造面变）：

| Step | 典型工期 | 手上应多出来的东西 | 一句话判据 |
| --- | --- | --- | --- |
| 1 风险评估与目标签署 | 约 1 个月 | 目标登记表 + 共享依赖清单 | 抽 3 行问签署人，能否各自复述数字与适用范围 |
| 2 架构设计 | 1-2 个月 | 架构图 + 切换/回切流程 + 覆盖范围说明书 | 没参与设计的人能否照文档走完桌面推演 |
| 3 实施部署 | 2-3 个月 | 备侧环境 + 同步链路 + 切换脚本 + 三条独立告警 | 备侧不接流量启动一次并计时；延迟指标有无采集空白 |
| 4 演练验证 | 持续（建议每季度） | 带实测值的演练记录 + 未通过项台账 | 两次实测值并排能否解释差异；回切耗时在不在 |

### 4.2 关键技术点

**1. 异步复制：用 GTID 定位、把复制延迟做成一等指标（MySQL binlog 链路）**

- **做法**：主库开启 ROW 格式 binlog 并设置唯一的 server-id；从库以 GTID 自动定位（`SOURCE_AUTO_POSITION=1`）而不是写死日志文件名与偏移；复制延迟持续采集并单独告警。注意语法已换代：MySQL 8.0.23 起 `CHANGE MASTER TO` / `START SLAVE` 被 `CHANGE REPLICATION SOURCE TO` / `START REPLICA` 取代，旧语法仍可执行但已弃用【公开，MySQL 8.0 Reference Manual 中「CHANGE REPLICATION SOURCE TO Statement」与「START REPLICA Statement」两节，更名自 8.0.23（2021 年）起；该手册持续更新、不锁定首发年份，读者可按语句名在官方手册中自行检索核对，具体版本号与旧语法当前的弃用/移除状态以当期文档为准】。
- **机制**：因为 RPO 由「复制延迟」而不是由「复制是否开着」决定，所以把这个量做成连续的观测序列，才能回答「此刻故障会丢多少」；因为 GTID 把位点编码进事务本身，所以从库重指到新主库时不需要人去核对 binlog 文件名与偏移——**故障切换的执行段因此变短，而执行段正是 RTO 里最不该出错的段落**。代价是：ROW 格式的 binlog 体积明显大于 STATEMENT 格式，存储与网络开销上升；GTID 还要求主库统一开启，历史实例必须先补开并有停写窗口。
- **失效条件**：**当单笔事务很大（批量导入、一次全表更新）时，延迟不再由网络决定，而由这一个事务的提交粒度决定**——从库必须等它整体重放完才能推进，延迟会突然跳到分钟级再回落。症状是延迟曲线上出现**尖峰而非缓慢抬升**；尖峰宽度与最大单事务的量级成正比，这个量可以直接从 binlog 里量出来。第二个失效面在**并行复制策略**：写入热点集中在一张表时，按库并行的策略无从发挥，需要按事务组并行的策略才能摊开（策略与参数以官方文档当期版本为准）。
- **档位**：语法更名【公开，MySQL 8.0 Reference Manual 中的「CHANGE REPLICATION SOURCE TO Statement」与「START REPLICA Statement」两节，更名自 8.0.23（2021 年）起，读者可按语句名自行检索核对，以当期文档为准】；延迟由最大事务决定的结论属机制推导；量级随事务粒度变，不在这里给精确值【经验】。

**2. 同步复制：开关在主库的成员名单，不在 `synchronous_commit`（PostgreSQL 流复制）**

- **做法**：主库设 `wal_level = replica`、`max_wal_senders > 0`，并在 `synchronous_standby_names` 中显式列出同步集的成员；`synchronous_commit` 控制的是提交时 WAL 的写入/刷盘级别，两者不是同一件事，把「同步复制」当成一个 `on` 是常见误配（各参数语义与可选值以 PostgreSQL 官方文档当期版本为准）【公开，PostgreSQL 官方文档「Replication」配置一节中 `synchronous_commit`、`synchronous_standby_names`、`wal_level`、`max_wal_senders` 的条目；该文档持续更新、不锁定首发年份，读者可按参数名自行检索核对】。同时决定：同步集成员掉线时，主库是停写还是降级为异步。
- **机制**：因为同步复制把「提交返回成功」绑定到「同步集中的远端已收到（或已落盘）WAL」，所以已确认的写不会随主库失效而丢失——**RPO=0 的覆盖范围恰好等于同步集里的成员**，名单之外的一切复制都是异步的。代价是等待进入了每一次提交：同城同步的等待在毫秒级，跨城同步的等待则在数十毫秒量级【推算，推导链见 §3.2.4：往返光缆里程约 2×1,200 km ÷ 2×10⁸ m/s ≈ 12 ms 纯传播，叠加交换设备与路由绕行后工程实测常落在 25–35 ms 量级】，交易链路的 P99 预算会先崩。
- **失效条件**：**当同步集里只剩一个成员、而这个成员不是宕机而是被网络隔离时**，主库侧的等待会表现为大面积写超时。症状是「数据库没有宕、所有写都卡住」。此时最危险的动作是手工清空 `synchronous_standby_names` 来「恢复服务」——那一步会把 RPO=0 静默降级成异步，而降级这件事不会产生任何告警。可观测信号：写超时与副本的 `pg_stat_replication` 状态变化同时出现。
- **档位**：参数语义【公开，PostgreSQL 官方文档「Replication」配置一节，其中列出的参数随版本增删，以当期版本为准，读者可按参数名自行检索核对】；延迟量级【推算】，按自己拨测为准。

**3. 跨 Region 的资源备份：备份对象与卷快照都带区域边界（K8s / Velero 一类工具）**

- **做法**：集群资源用备份工具的 **Schedule 对象**（`spec.schedule` + `spec.template`）做周期备份；`kind: Backup` 是一次性对象，把它当成定时任务是常见的配置错误。命名空间、PV 与所需镜像清单要一起纳入；跨 Region 恢复时，备份与其卷快照必须先复制到目标 Region。
- **机制**：因为这类工具备份的是 K8s API 对象加卷数据，所以它能重建工作负载——但集群控制面自身、负载均衡、IAM、DNS 记录这些云侧资源不在它的备份范围内，**「集群能重建」不等于「依赖能重建」**。又因为对象存储与块存储快照通常是区域级资源、需要显式复制才能跨区可用，所以「备份在那里、随时能恢复」这件事在主 Region 故障当天并不自动成立。代价是备份要跨 Region 存一份，存储与流量成本随副本数上升【推算，副本数 1 → 2】，且首次跨区复制的时间进入 RTO。
- **失效条件**：**当备份只存在主 Region 的对象存储里时，一次 Region 级故障会同时带走生产与备份**。症状很具体：平时的恢复演练（都在主 Region 做）全部通过，真实区域故障时找不到可用的备份副本。第二个失效面是卷快照与集群的耦合——换 Region 恢复时 storageClass、可用区、实例类型往往对不上，流程会卡在挂载这一步。
- **档位**：备份对象类型划分与快照的区域归属【公开，Velero 官方文档中 `Backup` 与 `Schedule` 两个 API 对象的定义，以及云厂商官方文档中块存储快照的区域属性说明；两者持续更新、不锁定首发年份，以当期文档为准，读者可按产品名加对象名自行检索核对】；成本随副本数翻倍属机制推导【推算：副本数 1 → 2】。

**4. 健康检查与自动切换：多个信号交叉确认，并事先回答「分区时站哪一侧」**

- **做法**：至少三类信号——进程/端口存活、应用层探测（能跑通一条真实查询）、复制延迟是否在收敛；判定规则（全部满足 / 多数满足 / 连续 N 次满足）事前写死。外部合成监控（拨测类工具，如 Pingdom / Datadog 的可选功能）与内部健康检查互为参照，避免单一视角——**外部视角能看见「服务已不可达」，内部视角能看见「服务还在但数据不对」，两者缺一就会出现盲区**。切换动作清单化：提升副本 → 对账 → 切流（DNS / VIP / 代理层）→ 放量，每一步带一个可回退点。
- **机制**：因为最危险的故障不是节点宕机而是网络分区，所以判定必须取保守侧——**分区场景下「能继续服务」与「数据不错乱」不可兼得**，而自动切换把「判断错误就执行」这件事也自动化了（§3.5 第三条）。代价是：交叉确认会拉长决策段，RTO 变长；用放宽条件换来的速度，会在分区场景里变成双写的入口。
- **失效条件**：**当切换条件只按「节点宕机」设计、且没有 fencing / quorum 时**，网络分区会让两侧各自认为对方已死并各自提升为主，两个方向同时接受写入，冲突在分区恢复时才暴露，且无法靠重放修复。症状不是切换变慢，而是**短时间内出现两次提升事件**。可观测信号：备侧提升事件计数在窗口内 > 1。
- **档位**：机制推导（依据同 §3.5、§3.2.3）；判定规则的取值属组织自设，标【经验】。

**5. 切换决策与 Runbook：把「谁有权说切」写成角色，而不是人名**

- **做法**：Runbook 每个场景写四段——触发条件、执行步骤（每步带预计耗时）、Owner 角色、回退点；版本化并与演练同步更新。DNS 的 TTL 在事前调到与 RTO 预算匹配（TTL 是切换耗时里少数可以事前压缩的量，但压得越短，解析查询量越高，取值须在解析压力与切换速度之间权衡）。回切路径与切换路径必须写成两份，权限也分开。
- **机制**：因为 RTO = 探测 + 决策 + 执行，而执行段在自动化之后已经被压得很短，所以剩下的方差几乎全落在决策段（§3.1）。**把「该不该切」从讨论变成核对条件，是在压缩 RTO 里唯一还长的那一段。** 代价是 Runbook 成了一份需要持续维护的资产，而维护它不产生当期产出，因此最先腐化——它由一串只在切换当天才会被读到的一次性清单构成（§3.5 第一条已列出这些清单）。
- **失效条件**：**当 Runbook 的版本落后于环境时，它比没有 Runbook 更危险**，因为它会把人引向一个已经失效的动作。症状是演练中「照着文档做」反而制造了新故障。可维护的判据是：每次演练记录里是否出现过「文档与实际不一致」这一项——**这一项长期为空，通常说明演练没有真做，而不是说明文档很准**。
- **档位**：【经验】。

**6. 恢复后的对账：把「切换成功」与「数据正确」分成两件事**

- **做法**：切换完成后跑三类校验——主键/行数抽样比对、业务层校验（例如订单金额汇总与账务系统核对）、关键链路的端到端业务校验；不一致条数按**时间窗口**定位，而不是只报一个总数。
- **机制**：因为异步复制下的丢失是「一段时间窗口内的行」而不是「整条链路」，所以按总量比对通常什么都看不出；只有把口径对到时间窗口上，才能知道该补哪些数据、以及对外承诺的 RPO 是否真的守住了。代价是备侧必须能跑同一套统计逻辑（可比口径），这部分工作量常被低估——它对账的是能力，不只是数据。
- **失效条件**：**当主备两侧的写入时间戳口径不一致（一侧用库时间、一侧用应用时间）时**，对账会产生大量假阳性，团队随后不再读这份报告——**一份总在报错的对账报告，最终的下场是被关掉**。症状是对账告警长期挂在「已知问题」状态、没人处理也没人删除。
- **档位**：【经验】。

**7. 灰度回切：把「切回来」当成一次发布来做**

- **做法**：回切不一次性完成，而是按流量比例分阶段——先把一小部分读流量引回主站，观察一致性延迟与错误率，再逐步放大到写流量；每一阶段设一个可停在原地的时间窗，出问题就停在当前比例而不是整体回落。回切前先确认主站已经追齐变更（追齐判据是「复制延迟归零并稳定一段时间」，阈值由 RPO 承诺反推，不是拍脑袋）。
- **机制**：因为回切方向上「主站的数据比备站旧」是常态，所以在追齐完成之前把写流量引回去，会产生两个方向的写入与两套时间线——**回切的风险不在动作本身，而在数据追齐与流量切换之间的那段重叠期**。把它按比例分阶段，等于把这段重叠期的暴露面从全量压到一小部分。代价是回切时长被拉长，这段时间里两套环境都要被维护、监控与值守；分阶段还要求流量调度层支持按比例而非按全量切换，这个能力要提前确认（不是所有 DNS/GSLB 方案都提供）。
- **失效条件**：**当流量调度层只能做整体切换时**，「灰度回切」会退化成一句口号，实际操作要么全切要么不切——症状是回切方案在纸面上有五个阶段，演练记录里只有一次性的切换。另一个失效面是**追齐判据被设成「延迟为 0」**：在持续写入的系统里，延迟为 0 只是一个瞬时点，判据必须是「归零并稳定一段时长」，否则回切永远达不到开始条件。
- **档位**：分阶段比例与稳定时长属组织自设【经验】；分布比例与阈值不在这里给具体值，须由自家复制延迟分布决定。

**这七条的共同判据**：它们全部指向同一件事——**让切换当天需要现场判断的事情变少**。GTID 让执行段少一次人工核对；同步集名单让 RPO 的边界可以被陈述；跨 Region 的备份副本让恢复不必依赖「主 Region 还能读」；三类信号交叉确认让决策不必在故障当天临时讨论；Runbook 让动作不依赖记忆；按时间窗口对账让丢失可被定位；灰度回切让回退不必整站推翻重来。反过来用同样成立：**任何一条如果增加了切换当天的现场判断量，那它就是装错了，无论它在平时看起来多优雅。**

### 4.3 工具链与平台

选型不看品牌，看约束。下表每行给出「在什么约束下选它」以及「不选它的代价」，产品名只是当前实现。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 逻辑备份 | mysqldump、pg_dump | 库不大、可接受恢复慢、需要跨版本可读的文本格式、或需要按表挑选时选它 | 恢复时长与数据量成正比；TB 级数据一次恢复可能超出停机窗口（对应 §3.6「单库从 TB 到 PB」那一行的跃迁） |
| 物理备份 | xtrabackup（MySQL）、pg_basebackup（PostgreSQL） | 数据量大、只需恢复到最近时点、且版本与平台一致时选它 | 与版本和平台绑定紧，跨大版本恢复能力弱于逻辑备份；换引擎时这份备份用不上 |
| 变更数据捕获（CDC） | Debezium、Maxwell、阿里云 DTS | 需要把变更同时喂给备库、数仓与下游时选它；只做库间复制时优先用引擎自带的日志复制 | 把 CDC 用在一个只求「保数据」的目标上，等于为不需要的语义付一跳中间件的运维成本——多一跳就多一个故障点，而这个故障点在切换当天才显形 |
| 文件系统 / 块存储快照 | ZFS、LVM、云盘快照（如 AWS EBS Snapshot） | 需要秒级、应用相对无感的时点副本时选它；前提是存储层能提供一致性快照 | 多卷不同时的一致性缺口会让恢复出来的是一个「撕裂」的状态，且这个问题只在恢复那一刻才暴露 |
| K8s 资源备份 | Velero、Kasten | 既要重建 API 对象也要重建卷时选它；验收标准是备份清单里是否包含恢复所需的全部云侧依赖 | 把它当成「整站备份」，会在 Region 故障时发现控制面依赖、负载均衡与 IAM 不在备份里 |
| 云厂商托管灾备（DRaaS） | AWS 的托管灾备能力（以 CloudEndure Disaster Recovery 之名进入市场，产品线已并入 AWS 自有服务，当前名称与能力范围以官方文档当期版本为准）、Azure Site Recovery、阿里云灾备 | 目标是异构环境（物理机或他云）、需要 agent 级块复制、且不愿自建复制链路时选它 | 用它去覆盖「逻辑损坏」类故障：块级复制会把误删与加密一并复制过去，时间点副本仍要另备（§3.2.7） |
| 切换编排与流量调度 | DNS / GSLB、VIP 与代理层（如 HAProxy 一类）、云厂商流量管理 | 判据只有两条：解析生效时间是否落在 RTO 预算内、能否按地域精确切流；再加一条「探活从哪里发起」 | 把 DNS 当成秒级开关：TTL 与递归解析缓存决定切换下限，而这个延迟恰好发生在最紧张的几分钟里 |
| 备份的存储介质 | 对象存储（支持保留期与不可改写语义） | 需要「回到某个过去时点」且要防内部人/勒索删除时选它；判据是凭据是否与生产隔离 | 用可被生产凭据删除的介质，等于把「能回到过去」这个能力交到了攻击者手上（§3.2.7） |

**这一类里最容易被误选的是 CDC 工具**：它常被当成「顺便解决容灾」的一站式方案——接了 CDC，下游能读、备库也有数据，看起来一举两得。误选的典型后果是链路多了一跳中间件，而这一跳的延迟、积压与版本升级进入关键路径；真出事时，你要先判断是源库的问题、CDC 的问题还是目标库的问题，而这段时间正好是 RTO 预算里最紧的部分。判断方法很简单：**如果你的目标只是「让另一份副本跟上」，引擎自带的日志复制就够；只有当同一份变更需要被多个下游消费时，CDC 才是对的选择。**

**这一类里的第二个常见错误是「同类叠两套」**：既有引擎自带的日志复制，又接一套 CDC 做同一件事；既买了云厂商托管灾备，又自建一套块复制。两套机制同时搬运同一份变更，出事时第一件要做的事不是修，而是判断**该以哪一套的进度为准**——而这个判断要花的时间通常比修本身更长。可维护的判据只有一句：同一条数据路径上，是否只有一个机制负责把它送到对岸。**加第二套的理由如果只是「冗余」，它带来的是判断成本，不是可用性。**

### 4.4 存量迁移

大多数组织的容灾不是从零建的，而是在一套已经跑了多年的复制链路上补课。下面是一个存量团队的完整路径：①-④ 是主干（先做什么、历史资产怎么分、双轨怎么维持、什么时候可以宣布建成），⑤-⑧ 是排期与口径上最容易翻车的四件事。

**① 先做什么：两件两周内可完成、且完全可回退的事**（约两周【经验】，随监控栈与备份工具的现状变：已有指标平台与现成备份工具时更短，需要新接一条采集链路、或新申请一套隔离的恢复环境时更长）。

第一件是把**复制延迟从「副本存活」里拆出来**，单独做一个指标与告警。这不改架构、不申请窗口、失败可以回退（把告警关掉即可）。第二件是做一次**只读恢复演练**：在隔离环境里恢复一份备份，不动生产、不切流量，记录三个数——取回带宽、恢复耗时、对账不一致条数。它的判据很直接：这次恢复出来的库，能不能独立回答一条业务查询。两件事的价值在于它们**先把「未知」变成「已知」**，而架构改造的排期需要这份已知。

还有一件容易被高估难度的事：**第一次切换演练应当选非核心业务**。选核心业务做首演，会让「演练」在组织里立刻变成一件高危活动，排期要等一个业务低谷、签字要跨两三层，最后往往拖过一年；而选一个内部系统先切一次，得到的是同一套流程与同一批清单，成本却低一个量级。首演的目的不是证明架构，而是**把流程里所有需要别人配合的环节先跑通一遍**。

**② 历史资产怎么分类处理：分三类，不要全部返工。**

- **能重算的资产**（报表、宽表、指标）：不返工，**打标挂账**——在登记表里写明 RPO 小时级、责任人、以及重算路径。判据是「这份数据被错误更新后能不能靠重算修复」，能重算的就不要付 RPO=0 的成本（§3.4 组合 D）。
- **有存量承诺、不能重算的核心链路**：整条改造，顺序按「读路径 → 写路径」推进。先改读路径是因为它可回退：读错了能切回主站，写错了会留下脏数据。
- **无下游、无 Owner 的资产**：先判定再处置。对容灾而言，**下线一个没人用的资产，等于减少了一份需要被覆盖的范围**——这是最容易见效、却最常被忽略的一步。

**③ 双轨怎么维持、维持多久。**

容灾的「双轨」不是新旧系统并存，而是：**生产继续跑，备侧按目标档位常驻，演练按固定节奏真切一次并切回来**。维持时长不按日历定，按证据定——判据是连续 2-3 次【经验】演练同时满足三条：实测 RPO/RTO 落在承诺内、对账不一致条数为 0 或有明确归因、未通过项全部关闭。三条缺一条，就还在双轨期。**双轨期必须把回切练到**，否则第一次真实切换之后，「双轨」会变成「一套在跑、一套在闲置」。

**④ 什么信号说明可以退出双轨。**

出现下面四条，才可以对外宣布容灾建成：切过去与切回来都有可复现的记录；复制延迟、副本存活与备份作业结果三条告警都已上线、且都被真实触发过至少一次；备份凭据与生产凭据分离、且有恢复演练的实测数字；登记表每一行都能指到具体责任人与一个恢复动作。任一条不满足，现在的状态是「图纸已画完」，不是「容灾已建成」。

**⑤ 组织侧的最后一步。** 把演练写进年度节奏并明确「谁有权说切 / 谁有权说切回」。这一步的成本全在组织上而不在技术上：多团队共管时，决策段的耗时随参与方数量增长，而它恰好是 RTO 里方差最大的一段（§3.6 最后一行）。

**⑥ 哪些改造必须占停写窗口，哪些不占。** 存量迁移的排期难点不在动作多，而在**哪几个动作必须停机**。不需要停写的：拆分复制延迟指标、补对账逻辑、把 Runbook 与演练记录模板化、给备份存储换一套独立凭据（前提是新增一套而不是替换）。必须占窗口的：给历史实例补开 GTID、把 binlog 格式从 STATEMENT 切成 ROW、改分片键或数据模型、把备侧从「同 Region」搬到「跨 Region」的首次全量同步。排期时把后者集中到少数几个窗口里一次做完，比分散成十次停机更容易向业务解释，也更容易让业务签字——**每一次停写都是要向业务借时间，而借得越碎，签字的人越多、越难推进**。

**⑦ 一次判断存量迁移是否真的在推进的检查。** 隔一个月看两个数：A＝登记表里「有具体责任人与恢复动作」的行数占比；B＝上一次演练记录里实测 RPO/RTO 是否比上上次更接近承诺。A 只涨不落说明覆盖面在扩大；B 没有改善而 A 在涨，说明**登记的进度快过了能力的进度**——那种状态最危险，因为它会产出一份看起来完整的容灾台账，而真实能力原地未动。

**⑧ 迁移期的对外口径。** 迁移期间最常失控的不是技术进度，而是**对外承诺的口径**：业务方随时会问「现在 RPO 是多少」，若答案仍是制度文件上的旧数字、而实际能力已经变化（例如异地复制被降级为异步），承诺与能力之间就被撕开一个新的缺口——补上它比当初多说一句「当前实测是 X、目标是 Y」贵得多。做法是给登记表加一列「当前实测值」，与「目标值」并列，并按演练节奏更新。**只写目标不写实测的表，会让所有人默认目标已经达成。**

### 4.5 模板 / 示例

**1. DR Runbook 骨架**

```yaml
# DR Runbook（示例骨架；RPO/RTO 为示例值，实际值须由业务签署并写明适用范围）
metadata:
  name: ecommerce-core-dr
  version: 1.0
  last_updated: 2025-01-01
  owner_role: sre-oncall          # 写角色不写人名；人名会过期，角色不会

rpo_rto:
  RPO: 30 seconds                 # 适用范围：哪些数据、哪些路径
  RTO: 5 minutes                  # 分段记录：探测 / 决策 / 执行

dr_scenarios:
  - scenario: 主 Region 故障
    trigger: 多信号同时失败并持续 > 2 分钟【示例值】
    decide_by: sre-oncall         # 谁有权说切
    decide_back_by: sre-lead      # 谁有权说切回——必须单独写
    steps:
      - 1. 交叉确认：进程存活 / 应用层探测 / 复制延迟，三类信号同时异常
           （外部拨测 Pingdom / Datadog 一类 + 内部健康检查，互为参照）
      - 2. 通报云厂商支持通道（如 AWS Support）并同步开始自助处置，不等回复
      - 3. 先判分区还是宕机：分区时取保守侧（停写），不得自动提升
      - 4. 提升备侧 → 按时间窗口对账 → 再切流（DNS / GSLB，TTL 事前对齐 RTO，示例取 60 秒）
      - 5. 放量并验证关键业务链路
      - 6. 记录分段耗时与对账不一致条数
    rollback_point: 第 4 步之前，备侧尚未承接写入
  - scenario: 数据库主库故障（非分区）
    trigger: 主库进程不可用，且同 Region 副本健康、延迟收敛
    decide_by: dba-oncall
    steps:
      - 1. 按预置规则提升副本（自动），记录提升事件计数
      - 2. 对账（按时间窗口比对，而不是只比总量）
      - 3. 通知下游，附受影响的时间窗口
      - 4. 修复主库，并安排一次回切演练
    forbidden: 禁止用清空同步集的方式「恢复服务」——那一步把 RPO=0 静默降级为异步
```

**怎么用**：把 `metadata`、`forbidden` 与第 3 步的「先判分区还是宕机」照抄；`trigger` 的分钟数、`RPO`/`RTO` 与 TTL 的 60 秒都是示例值不要照抄，必须换成 Step 1 签署过的数字与自家 RTO 预算；`owner_role` 填角色，不要填人名。

**2. 演练记录表（每次演练填一行，跨次对比才有意义）**

| 字段 | 本次实测 | 上一次实测 | 差异是否有解释 |
| --- | --- | --- | --- |
| 实测 RPO（最后一次成功复制时点 → 故障时点） | | | |
| 探测段耗时 | | | |
| 决策段耗时 | | | |
| 执行段耗时 | | | |
| 回切耗时 | | | |
| 对账不一致条数（含时间窗口） | | | |
| 未通过项数量 / 其中最老一条的开启时间 | | | |

**怎么用**：只填「本次」没有价值——这张表的作用是让两次之间的差异无处可藏。若某一行长期为空（常见的是「回切耗时」），不要把它解释为「不需要」，把它读成「这一步还没做」。

**3. 三条独立告警的规则骨架（复制延迟 / 副本存活 / 备份结果）**

```text
告警 1  复制延迟（这是 RPO 的直接观测值）
  表达式：取自复制状态中的延迟字段，或用「写入时间戳之差」自算
  阈值：由业务签署的 RPO 反推，不是拍一个"看起来很安全"的数
  持续时间：必须带 for 条件——瞬时的延迟尖峰是正常的
  ★ 指标名与字段名随采集器与引擎版本变化，以你所用的 exporter / 引擎文档为准
告警 2  副本存活（与告警 1 分开，绝不合并）
  表达式：副本进程可达 + 复制线程在运行
  要点：它回答"副本还在不在"，不回答"数据差多少"；合并两条 = 两个问题都看不见
告警 3  备份结果（只在失败时发出，成功不发）
  表达式：备份作业连续失败次数 ≥ 2，或最近一次成功时间超过计划周期的 2 倍
  要点：备份链路的故障模式是静默失败——成功通知不产生信号，连续失败才是
```

**怎么用**：照抄的是「三条分开」这个结构，不是阈值——阈值必须由自家签署的 RPO 反推。落地后的第一条判据是：把三条告警各自人为触发一次，看它们是不是分别到达了不同的人；若三条都落到同一个收件箱且被同一条规则静默，等于没拆。

**4. 故障场景清单（演练覆盖率的分母）**

| 场景 | 触发形态 | 覆盖它的是哪一档 | 最近一次演练 | 未通过项数 |
| --- | --- | --- | --- | --- |
| 单机房 / 单可用区失效 | 节点与网络同时不可达 | | | |
| 城市级事件 | 同城两机房同时不可用，或同城专线中断 | | | |
| Region 级故障 | 整个区域的服务与控制面不可用 | | | |
| 控制面级故障 | 云厂商侧 IAM / 配额 / 控制面异常，工作负载本身正常 | | | |
| 网络分区 | 主备互相不可见但都活着（不是宕机） | | | |
| 逻辑损坏 | 误删、批量错更新、程序缺陷写坏数据 | | | |
| 凭据泄露 / 勒索加密 | 生产与备份的凭据同时落入他人之手 | | | |
| 上游依赖不可用 | DNS、证书、第三方出口白名单、许可证失效 | | | |

**怎么用**：这张表的唯一用途是当分母用——**「覆盖率」写成「已演练场景数 / 总场景数」，而不是「有没有做过演练」**。第 4、5、7 行是绝大多数团队从未演练过的三行，它们也是真实故障里占比不低的三类。第 8 行不是架构问题，它只在切换当天才被读到，所以只能靠演练维持。

### 4.6 成本：这套东西的账单

容灾的账单结构与数据平台其它主题相反：**它不是为「跑得快」付钱，而是为「出事那天还能跑」付钱**，且大部分按**时间**而非按**用量**计价。

- **备侧资源（主导项）**：冷 / 温 / 热 / 多活的差别首先是一张**常驻率**账单——冷备备侧≈0（只付备份存储），热备备侧常年按主站同规格在线，多活两侧常年满配。等级名称与 RPO/RTO 对照见主文件 §1.1。这就是 Step 1 那张「成本曲线」（§4.1）的纵轴。
- **带宽与存储（随数据量线性）**：异步复制的复制流量、跨 Region 的备份副本，都随**数据量 × 副本数**走【推算：备份跨 Region 存一份，存储按副本数 1→2 翻倍，见 §4.2 第 3 条】；同步复制的等待不花存储钱，但会把时延摊进主链路每一次提交（往返时延的量级见 §4.2 第 2 条）。
- **人力（被低估）**：演练节奏（建议每季度一次【经验】，§4.1 Step 4）是常年发生的账单，且跨团队时决策段耗时随参与方数量增长（§4.4 ⑤）。它的特点是**永不产生当期产出**，因此最先被砍——后果不在当月，而在第一次真实故障。
- 通用的预留实例、存储分层 FinOps 见 [11-cross-cutting §03 数据成本](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)；本主题特有的成本是「备侧常驻率」。

### 4.7 容灾与故障演练

本主题**本身就是**容灾方法论——「容灾体系怎么建」是 §3 与 §4.1–4.5 的正文，跨地域切换就是本文，无需在此另写一遍。这一节写的是**容灾体系自己的容灾**：那套流程、目标与台账会以什么方式悄悄失效，以及怎么演练它。通用的故障注入方法（网络分区、常态化混沌）见 [12-architecture §06 混沌工程](../06-chaos-engineering/06-chaos-engineering.md)。

- **失效模式（都是「看着没坏」）**：(a) **目标与实测脱节**——登记表只写目标值不写实测值，所有人默认目标已达成（§4.4 ⑧）；(b) **只切不回切**——演练记录里找不到一次回切耗时，双活退化成「一套在跑、一套闲置」（§4.1 Step 4 末）；(c) **共享控制面**——备侧与主站共用 IAM / 密钥 / DNS / 发布系统，等于把故障域原样复制了一份（§3.1）；(d) **备份只活在一个 Region**——平时的恢复演练全在主 Region 做、全部通过，真实区域故障当天找不到可用副本（§4.2 第 3 条）。
- **影响面**：与机器故障不同，这四类**能力在降、指标不报**——只有把「目标分辨率」与「实测能力」两个数并列才看得见（§4.4 ⑦ 的 A、B 两数）。
- **降级策略**：备侧尚不可信时，明确降级为「只承诺已实测到的档位」——宁可对外说「当前 RPO 小时级、目标秒级」，也不要让制度文件上的旧数字继续充当承诺（§4.4 ⑧）。
- **演练方案**：对容灾体系本身做**元演练**——随机抽一个故障场景、不预先通知、完整走完「探测 → 决策 → 切换 → 对账 → 回切」；网络分区交给混沌工程的常态化注入（分区是演练现场最难造、又最致命的场景，§4.1 Step 3/4）。
- **恢复目标**：没有秒级 RTO；指标是**目标与实测的收敛速度**【经验：以「演练节奏」为刻度，连续 2–3 次演练三项同时达标才算双轨结束，§4.4 ③】。
- **为什么这里不另设「跨地域容灾」**：因为它就是跨地域容灾的实现本身；给「容灾方法」再建一个异地副本，不解决它真正的失效面——**方法失效在组织与实测，不在机房**。

### 4.8 演进路线：0 → 1 → 100

§1.4 给的是这个**领域**的技术史（磁带 → 两地三中心 → 异地多活 → 自愈）；这一节给**一个组织**从「有备份」到「多活」的三段。其中「自愈」按 §5.1 属 **L3**（概念与路线图期），只记录、不写进架构假设，不作为组织路线图的终点。

- **0 → 1（先能恢复）**：逻辑 / 物理备份 + **一次只读恢复演练**（隔离环境恢复一份、记录取回带宽 / 恢复耗时 / 对账条数，§4.4 ①）。变贵的是备份存储与恢复环境；先坏的是——「备份成功」通知掩盖了**备份不可恢复**（备份链路的故障是静默失败，§4.5 模板 3）。
- **1 → 100（能切、能切回来）**：复制链路 + 三条拆开的独立告警（延迟 / 存活 / 备份）+ 目标签署 + 季度真演练 + 回切（§4.1）。变贵的是**备侧常驻率与跨区带宽**（§4.6 的账单），以及常年发生的演练人力；先坏的常是**回切**与**实测值记录**（§4.1 Step 4 末）——跳过它，第一次真实切换后系统会永久停在备侧。
- **100 →（下一道坎）**：从「两地三中心」走向「多活」；「自愈」（§1.4 的 2025+ 条目）按 §5.1 属 **L3**，只记录、不写进架构假设。墙不在复制技术，而在**对等写入下的冲突与对账**：两地三中心还能说「以主侧为准」，多活两侧都是主，冲突要在数据模型层解决（异地多活见 [Ch12 §02 异地多活](../02-multi-region/02-multi-region.md)）。变贵的是应用无状态化与数据模型改造，先坏的是那段「追齐与切流重叠期」（§4.2 第 7 条）。

### 4.9 自检清单

下面每一条都指向一个可以当场翻出来看的对象（配置文件、指标图、演练记录、台账），而不是一个态度。查的时候不要问「做了吗」，去把那个对象打开。

- [ ] 复制链路的配置是声明在版本库（IaC / 配置管理）里，还是只存在于某台机器的命令行历史中？后者能否在故障当天被另一组人重建？
- [ ] 复制延迟是一个独立指标，还是与「副本存活」合成了一条？过去 30 天它有没有采集空白段？
- [ ] 同步集的成员有几个？成员掉线时主库的行为（停写 / 降级）是显式配置的，还是由默认值决定的？
- [ ] K8s 备份对象是 `Backup` 还是 `Schedule`？上一次恢复演练是在目标 Region 做的，还是在同 Region 做的？
- [ ] 演练记录里有没有分段耗时？三段里最长的是哪一段——它是探测、决策还是执行？
- [ ] 最近一次对账的不一致条数是多少？它能不能定位到一个具体时间窗口？
- [ ] 切换脚本能否由没写过它的另一组人执行完，且过程中不需要联系原作者？
- [ ] 备侧与生产之间共享的依赖（IAM、密钥、DNS、配置中心、发布系统、专线汇聚点）是否列成清单，并逐项标注了故障时是否可用？
- [ ] 备份的跨 Region 副本是否可读？读它需要谁的权限、这个权限与生产是否共用一套凭据？
- [ ] 登记表里每一行的恢复动作能不能写在一页纸内？写不满一页说明它还是一个愿望，不是一条路径。
- [ ] 有没有一条告警是专门为「备份作业连续失败」设的？还是只在作业成功时发一条成功通知（成功通知不产生信号）？
- [ ] 上一次演练的未通过项台账里，最老的一条开了多久？它属于「清单过期」还是「逻辑缺陷」？

### 4.10 小结

> 本节小结：容灾的工程实现里唯一决定成败的环节是 **Step 4 的演练，而且是把实测值记下来的那一次**——其余步骤（选档位、铺链路、写 Runbook）都能靠文档与配置完成，只有演练会把「切换当天才会被读到的一串一次性清单」逼到台面上。它比其余环节更值得投入，原因很直接：**RPO/RTO 在没有实测值之前不是属性，只是承诺**；而承诺与能力之间的缺口不会在日常暴露，只会以真实故障的形式一次性结算。
>
> 💡 **思考锚点**：隔一个月看两个数（§4.4 第⑦条）：A＝登记表里「有具体责任人与恢复动作」的行数占比，B＝最近一次演练的实测 RPO/RTO 是否比上上次更接近承诺。如果你这里 A 只涨不落、B 却没改善，你会先补台账里的哪一列，还是先把决策段的耗时压下来？
