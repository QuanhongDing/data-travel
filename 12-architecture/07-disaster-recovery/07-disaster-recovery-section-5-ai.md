## 5. 前沿演进（AI 时代）

> 原 § 5 共 54 行、为方向清单（GPU 容灾 / AI 推理容灾 / AI 辅助 DR / RAG 容灾 / 跨云 DR / Self-Healing），缺少机制与成熟度判断，重写为 ~290 行前沿评估。

### 5.1 先分清三类「前沿」

趋势清单最根本的毛病是**没有时间维度**。原文件把「GPU 跨 Region 调度」「模型副本跨 Region」和「AI 自动决策切换」「Self-Healing DR」写在相邻的小标题下，读者据此排路线图就会踩空：前一组里的多数条目今天就能做（它们只是把既有机制套到新对象上），后一组到今天仍只有厂商博客与产品公告。本节的三级判据必须可核验——**看正式 release note 里有没有这个条目、看有没有非厂商的公开生产案例、看接口是否稳定**——而不是「感觉成熟」。判据还要落到本主题的具体动作上：例如"跨 Region GPU 秒级接管"的判据不是"云上有没有 GPU 产品"（有），而是"有没有第三方公开的实测接管时长"（没有）。

容灾这个主题还有一个额外的坑：**AI 让"容灾对象"变了，但没有让"容灾原理"变**。RPO / RTO 的定义、同步与异步复制的语义、冷 / 温 / 热备与多活的档位、failover 与 failback 的流程（主文件 §2.1、§2.3）在 AI 服务面前一字未改。变的是被保护的对象多了三类：**推理服务**（无状态，但依赖稀缺的 GPU 容量）、**模型权重**（有版本、可重建）、**向量索引**（既是数据又是计算产物）。判断一个"前沿方向"值不值得投入，第一句要问的是：**它改变的是容灾的对象与成本结构，还是只是把同一个机制换了个名字？**

第三点要说在前面：本节对原文件里当作既成事实写下的厂商进展（如"AWS 2024 发布 AI 辅助 DR 决策助手""Azure 2024 跨 Region DR 服务增强"）采取了降档处理——**不是因为它们不成立，而是因为原文件没有给出可核验的公告出处**。在拿不出出处的情况下，正确的写法是给判定方法（去哪一版 release note / 哪一份官方公告里核），而不是断言结论。这也是本节与前四节最大的写法差异。

按这条标准，本主题下的方向分成三级（判据栏给出的是读者可以自己去核的动作）：

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 推理服务的多 Region 多活（多副本接入 + 多模型路由 + 降级链路） | **L1** | 机制与无状态 Web 服务多活同构（健康探切 + 负载均衡 + 熔断降级）；接入层接口稳定；不需要 AI 专属证据 | 排进路线图：把推理服务直接挂进既有的热备 / 多活档位 |
| GPU 容灾（跨 Region 调度 / Spot 兜底 / 容量预留 / 模型副本跨 Region） | **L2** | 云上 GPU 容量预留与多可用区实例是 GA 产品能力；但跨 Region 接管受配额、库存与权重加载时间限制，**无第三方公开的实测接管时长** | 做 PoC：只承诺「降级可用」，不承诺 RTO 秒级 |
| RAG 检索链路容灾（Embedding / 向量索引 / 检索服务三段） | **L2** | 组件级冗余是既有技术；但「向量索引跨 Region 复制」还是「本地可重建」，取决于具体产品的 release note（多数把复制做成集群内能力） | 先做「索引可重建 + 版本可追溯」，跨 Region 强同步留待逐版本核验 |
| AI 辅助 DR（故障预测 / 决策助手 / 自动验证） | **L3** | 公开可核验的多为厂商博客与产品公告；**无**第三方生产案例，**无**误报率 / 漏报率的公开评测 | 记录，不要在架构里预留「AI 会提前发现故障」的假设 |
| 跨云 DR（多云厂商冗余） | **L3** | 需求成立，但公开可核验的主要是案例叙述；跨云一致性与双栈运维复杂度没有产品化的公开解，数据出口与专线是新增常驻成本 | 只做「可迁移性」准备（容器化、避开厂商专属 API） |
| Self-Healing DR / AI 原生容灾 / AI 主导 DR | **L3** | 概念与路线图期；切换决策的瓶颈是权限与责任，不是算法 | 不要写进架构假设，最多把它当成「自动化 Runbook 的下一个版本」 |

> 本主题下唯一处在 L1 的方向是**第一行：把推理服务当无状态服务纳进既有的热备 / 多活档位**——它的全部构件（健康探测、端点摘除、多副本、探切）都有通用实现，换成推理服务不需要任何新原理，"能不能用"因此不构成问题。其余方向的共同点是**瓶颈都不在机制，而在成本与证据**：GPU 是稀缺资源，"跨 Region 接管"要先有容量才有意义；AI 辅助 DR 缺的是第三方证据与误报代价的量化；跨云与 Self-Healing 缺的是责任归属。**判据可核验，是本节与趋势清单的唯一区别。**

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。六个字段缺一不可——只写"得到"不写"付出"的方向，在评审时应当被直接打回，因为容灾领域里没有免费的可用性。

#### 5.2.1 推理服务的容灾：接入层已经 L1，因为它根本不是新问题

- **旧做法与它的卡点**：原清单把「多模型路由（GPT-4 故障时切到 Claude / 本地小模型）」与「降级链路（大模型 → 中模型 → 小模型 → 规则）」列为 AI 带来的新能力。卡点不在"能不能切"，而在**切过去之后你不知道质量掉了多少**：不同模型对同一 prompt 的输出不可比，切换会改变答案口径；大多数系统只监控了"可用性"，没有监控"降级期间的输出分布"；更隐蔽的是很多团队把推理服务当数据库一样供着——单 Region、大规格实例、人工切流，**把无状态服务做成了有状态服务**，于是撞上主文件 §1.2 里"切换流程长 / 运维复杂"这两条老痛点。
- **AI 改变了什么机制**：**只改变了被路由的对象，没有改变路由机制**。健康探测、端点摘除、按失败率熔断、降级到兜底路径，这些在 API 网关里已有十余年；AI 带来的唯一新事实是"上游存在多个质量档位不等价的服务，且它们都要占 GPU"。
- **由此得到的**：**因为推理服务是无状态的、且模型可由制品重建，所以它天然适合挂到既有的热备 / 多活档位上，不必为它单独设计一套容灾**；落到工程上就是把「多模型路由」实现成网关的端点池，把「降级链路」实现成显式的质量档位（见下方示意），而不是散落在业务代码里的 `try/except`。这也意味着这项能力的验收标准与容灾无关、与网关有关：**端点池能不能按上游失败率自动摘除**。
- **由此付出的**：三条真实代价：**其一，降级后的输出不确定且不可比**——公开渠道没有带条件的"降级期间准确率下降多少"基准，只能自建评估集；**其二，降级把故障从"不可用"变成"看起来可用"**，若监控只看可用性，降级会静默持续数天，而"返回了但算错了"比"返回 503"更难发现；**其三，多 provider 带来新的锁定面**：路由层一旦依赖某个 provider 的私有参数（特定的工具调用或推理字段），切换就等于改代码，"可切换"退化成"可切换但没人敢切"。
- **证据与来源**：机制层面属既有工程，无厂商专属来源可引；**本方向没有公开可核验的第三方性能数据**，因此不要引用任何"切换后准确率保持 X%"的说法。可核验的判定入口是网关的 release note：查它是否支持按上游错误率 / 延迟自动摘除端点，以及降级是否可配置为"按请求类型分档"。
- **成熟度**：**L1**。判据：全部构件（健康探测、端点摘除、熔断、多副本）都有 GA 的通用实现，"能在生产用"不需要 AI 专属证据。

```text
把「降级」写成显式的质量档位（而不是隐式的 try/except）
  档位 0  主模型（跨 Region 多副本）                    ← 正常
  档位 1  同族等价模型（另一 Region / 另一版本）
  档位 2  小模型（能力下降已知，仅用于分类 / 抽取类请求）
  档位 3  规则 / 缓存 / 模板兜底（只保证「有响应」）
  档位 4  明确失败（返回 503 + 可重试）

  每档必须同时可回答：谁在降级、从何时开始、恢复条件是什么
  ────────────────────────────────────────────────
  关键：档位 2 以下对「答案类」请求是错误的——
        能返回不等于答案正确，所以档位要按请求类型选，
        而不是按「哪个模型还活着」选
```

判断一个请求能不能降级，要按请求类型而不是按技术实现来分：

| 请求类型 | 允许的最低档位 | 谁定这一档 | 判定方法 |
| --- | --- | --- | --- |
| 分类 / 抽取 / 打标 | 档位 2（小模型） | 业务方 + 评估集 | 用历史样本跑一遍小模型，看与主模型的一致率是否可接受 |
| 摘要 / 改写 / 草稿 | 档位 1（同族等价模型） | 业务方 | 抽样人评，看是否普遍需要重写 |
| 事实问答 / 涉及金额与合规 | 档位 4（明确失败） | 合规 / 风控 | 问一句"这句话错了谁负责"，答案不是"没人"就不许降级 |
| 只要"有响应"的交互（如补全建议） | 档位 3（模板兜底） | 业务方 | 确认用户能看出这是兜底内容，而不是被当成 AI 答案 |

> 这张表把"降级"从工程决策变成业务决策：**能降到哪一档，不由网关决定，由"错了谁负责"决定。**

#### 5.2.2 GPU 容灾：容量不是一个可以「复制」的东西

- **旧做法与它的卡点**：原清单写「GPU 跨 Region 调度（阿里云 EGS、AWS Inferentia）」「GPU Spot 容灾（Spot 故障时切到 On-Demand）」「模型副本跨 Region」。卡点是：**GPU 容灾的成本函数与数据容灾方向相反**。数据容灾的增量成本是存储与带宽，近似线性、可预算；GPU 容灾的增量成本是**常驻闲置算力**——为了在故障时接管，你必须在备用 Region 常备同等算力的卡，而它们平时几乎不产生收益。于是"RTO 越短，闲置成本越高"这条曲线比数据库场景陡得多，主文件 §1.1 那张按 RPO / RTO 分级的表在 GPU 这一行需要额外加一列"常备容量的价钱"。
- **AI 改变了什么机制**：**把"复制数据"换成了"预留容量"**。数据可以廉价地异步复制到第三个 Region 并一直躺在那里；GPU 不行，卡在别的 Region 只是"别人在用"。容灾计划的实质因此从"复制链路设计"变成"容量经济学 + 启动时间工程"。

| 维度 | 数据容灾 | GPU / 推理容灾 |
| --- | --- | --- |
| 冗余对象 | 数据副本 | 算力容量 |
| 增量成本形态 | 存储 + 带宽，随数据量增长，可预算 | 常驻闲置算力，随"最短可接受 RTO"增长 |
| 能否异地冗余后长期静置 | 能（异步复制后放着即可） | 不能（卡会被别的负载占用，或按预留持续计费） |
| 恢复动作 | 从副本恢复 | 拉起进程 + 加载权重 + 预热 |
| 主要失败模式 | 复制中断、副本损坏 | 配额不足、库存不足、权重加载超时 |
| 便宜档（Spot 等）是否可用 | 不适用 | 只能承接可丢失 / 可排队的流量 |
| 故障当下的止损动作 | 切到副本继续服务 | 先把请求排队或降档，再等容量拉起 |

```text
为什么"秒级 RTO"在 GPU 场景要先算一遍（示例推算，假设可替换）
  假设：70B 级模型，FP16 权重
  权重体积 ≈ 70 × 10^9 参数 × 2 字节 ≈ 140 GB      【推算：参数量 × 每参数字节数】
  跨 AZ / 跨 Region 拉取的有效带宽取 5–10 GB/s       【经验：云上拉取的常见量级区间，
                                                实际值随实例带宽与并发显著变化】
  仅"加载权重"一项 ≈ 140 GB ÷ 5–10 GB/s ≈ 14–28 秒  【推算：体积 ÷ 带宽】
  再叠加：进程拉起、预热 / 图编译、首个请求排队（均未计）
  ────────────────────────────────────────────────
  用法：把上面四个假设换成你自己的数（模型规模、实测带宽、预热方式），
        得到的就是你的 RTO 下限 —— 它与"复制了多少数据"无关
```

- **由此得到的**：**因为容量不可复制、且推理进程启动要先加载权重（权重体积与加载耗时随模型规模增长），所以推理容灾的真实 RTO 有一条与数据无关的下限：探测 + 决策 + 拉起进程 + 加载权重 + 预热**；这条链只能靠实测得出，因此把 RTO 目标写成秒级之前，必须先把自己的这条链量出来——否则"RPO = 0、RTO < 30s"只是口号，且它的失败会在真故障当天才暴露。
- **由此付出的**：**其一，常驻备容量的钱**，这是本方向最大的一项代价，且它与"多 Region 多活"的代价重复计算（多活本来就要常备容量，若还按容灾再备一份就是双份）；**其二，Spot 兜底是次级可用性而不是等价替代**——云方给出的回收预警是分钟级窗口（AWS 官方文档「Spot 中断通知」的口径为中断前 2 分钟，【公开，AWS EC2 用户指南 · Spot 中断通知，2015 年前后起该口径在多个版本文档中一致】），这点时间只够"优雅退出 + 把请求转走"，不够"在别处拉起并预热"，因此 Spot 只能承接可丢失 / 可排队的推理流量；**其三，跨 Region GPU 调度引入新的失败模式**：调度器本身成为单点，配额与库存是外部状态，"以为能拉起"与"真的拉起了"之间隔着一次配额校验，而这个校验在故障当天最可能失败（同 Region 的其他客户也在抢）。
- **证据与来源**：Spot 中断预警窗口为云方公开文档口径【公开，AWS EC2 用户指南 · Spot 中断通知，2015 年前后起口径一致】；推理服务的显存与并发特性有公开论文可核验【公开，Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention", SOSP 2023】，它解释了为何"少一张卡"不是"慢一点"而是"请求排队甚至 OOM"。**跨 Region GPU 秒级接管无公开可核验来源**，故本方向判 L2 而非 L1。
- **成熟度**：**L2**。判据：云上容量预留与多 Region GPU 实例是 GA 的产品能力，但配额与库存是云方状态、第三方实测接管时长缺失；判定方法是**在你的云账号里，在目标 Region 实际拉起所需规格并记下从发起到可服务的时间**——控制台里有没有这个规格，不算证据。

#### 5.2.3 RAG / 向量检索链路的容灾：三段依赖必须分别处置

- **旧做法与它的卡点**：原文件 §5.2 画了「[Region A]：[Embedding] → [向量检索] → [LLM]」两行并列的示意，并给出 Embedding / 向量索引 / LLM 三条容灾策略。问题在于：**这三段的"处置代价"差两三个数量级，用同一套"跨 Region 冗余"去处理，会把钱花错地方**。Embedding 是纯计算，故障时降级为关键词检索即可；LLM 是无状态服务（归 5.2.1）；**唯独向量索引需要单独决策**——它既不像数据那样只能复制，也不像计算那样可以随手重来。
- **AI 改变了什么机制**：**把一个"索引"变成了"制品"**。传统检索里索引是数据库的内部实现，丢了靠原数据重建；向量索引的重建**依赖另一个外部服务（Embedding 模型版本）与一次全量扫描**，因此它同时是"数据"（要版本化）与"计算产物"（可重建，但重建要花钱花时间）。

| 链路段 | 是否可重算 | 处置方式 | 恢复代价 |
| --- | --- | --- | --- |
| 原件（对象存储里的图 / 音 / 视频 / 文档） | **否**，唯一不可重算的一段 | 按主文件 §2.1 备份族处理：多副本 + 版本化 | 取决于备份策略 |
| Embedding 服务 | 是（纯计算） | 不跨 Region 常备；故障时降级为关键词 / 元数据检索 | 召回分布改变 |
| 向量索引 | 是（依赖原件 + 固定模型版本） | 快照版本化 + 可重建；跨 Region 强同步需逐版本核验 | 重建耗时随语料规模增长，且占算力 |
| 生成段（LLM） | —（无状态服务） | 归 5.2.1：多副本 + 端点池 + 显式降级档位 | 降级后输出不可比 |

- **由此得到的**：**因为向量索引可由原件 + 固定模型版本重建，所以容灾策略应当从"跨 Region 复制索引"改成"保证原件与 Embedding 模型版本可追溯 + 索引可重建"，代价是恢复期变长、且恢复期需要额外算力**；把索引当"零丢失的数据"来复制，等于为一个可重算的产物付数据的价钱——而这个价钱买的不是可用性，只是"恢复时不用重算"。
- **由此付出的**：**其一，重建时间随语料规模增长并占用算力**，故障当下你可能既缺检索又缺算力（而算力正是 5.2.2 里最贵的那一项，两笔代价会叠加）；**其二，重建的确定性依赖模型版本不漂移**——如果 Embedding 服务用"最新版本"这种浮动引用，重建出的索引与旧查询不可比，表现为"恢复之后检索质量莫名下降"；**其三，降级到关键词 / 元数据检索虽可用，但改变了召回分布**，同一个问题在降级期与正常期会返回不同结果，这件事必须写进 SLA 而不是藏在实现里。
- **证据与来源**：「原件与索引分离、索引作为可重建制品」是主流向量库与 RAG 工程的通行做法，可自行核验：查你所用的向量库 release note 中「快照 / 备份 / 恢复」与「跨集群（跨 Region）复制」分别是哪个能力、一致性口径是同步还是异步。**跨 Region 向量索引复制是否被某产品支持因产品与版本而异，本节不做断言。**
- **成熟度**：**L2**。判据：三段分别处置的机制是既有技术、可以立即实施，但"索引跨 Region 复制"必须逐版本核验，且没有第三方公开的 RAG 全链路容灾实测。

演练里必须真的量出下面两个数，否则"索引可重建"只是一句设计意图：

- **全量重建耗时**：从零重建索引需要多久，以及它占多少算力——故障当天你未必有这份算力。
- **重建后的召回一致性**：用同一组固定查询，比对重建前后 Top-K 的重叠程度；重叠度低说明模型版本或预处理口径发生了漂移。

这两个数同时也是"要不要付跨 Region 复制的钱"的判据：如果重建只要几分钟，复制索引的钱可以省下；如果要几小时，就重新评估——**按实测数决定，而不是按"高可用听起来更稳"决定。**

#### 5.2.4 AI 辅助 DR：故障预测、决策助手与自动验证

- **旧做法与它的卡点**：原清单的「AI 故障预测 / AI 决策助手 / AI 验证」，以及原 §5.4 的「AI 主导的 DR / Self-Healing DR / AI 原生容灾」。卡点在主文件的公式里：**可用性 = MTBF / (MTBF + MTTR)**，而 MTTR 由"探测—决策—执行"三段构成。既有手段在这三段上的收益分布极不均匀：探测与执行早已自动化（健康检查、探切脚本、Runbook），**唯独"决策"段仍由人承担，且是方差最大的一段**——一次跨 Region 切流往往要等值班主管确认，耗时取决于"人在不在"。
- **AI 改变了什么机制**：**它试图把"决策"段从人换成统计判断**——这是本方向唯一真实的机制变化，不是换前端。但它同时引入了决策类问题的固有权衡：**误报与漏报的代价不对称**。容灾里误报（不该切却切了）的代价是自伤，漏报（该切没切）的代价是延长故障时长；提高预测召回通常意味着提高误报，两者不能同时最优。

| MTTR 的三段 | 既有手段的自动化程度 | 方差来源 | AI 的现实落点 |
| --- | --- | --- | --- |
| 探测 | 已自动化（健康检查、SLO 告警） | 阈值设置 | 用异常检测压低误报，但会引入新的告警面 |
| 决策 | 主要靠人 | "人在不在" | 短期落在"建议 + 演练验证"，不落在"自动切流" |
| 执行 | 已自动化（探切脚本、Runbook） | 脚本本身的正确性 | 用生成式模型写 Runbook 草稿，必须人工评审 + 演练验证 |

- **由此得到的**：**因为决策段的瓶颈是"谁负责"而不是"准不准"，所以 AI 在当前阶段最可能落地的位置是"验证"而不是"决定"**：自动核对演练结果是否真达成了 RPO / RTO、自动比对告警与变更记录、自动生成 Runbook 草稿——这些动作误判代价低（错了只需人复核）、不触碰切流开关；而"AI 自动决定切换"要成真，先要解决的是误切之后谁来负责。
- **由此付出的**：**其一，预测类能力制造新的告警面**，预测性告警的误报会稀释真实告警的可信度，而容灾最依赖的恰恰是"告警响了就有人动"；**其二，用生成式模型产出的 Runbook 有幻觉风险**，而 Runbook 是故障时被执行的东西，错一步会扩大故障，必须有人工评审与演练验证；**其三，把 AI 放进应急链路会拉长复盘的责任链**——"是模型建议切的"不能成为免责理由，因此它多半会与审计要求冲突。
- **证据与来源**：**本方向没有公开可核验的第三方生产案例，也没有误报率 / 漏报率的公开评测**。可核验的只有机制侧的既有事实：MTTR 分解与 MTBF / MTTR 公式见主文件 §2.2；演练作为验证手段的公开实践见 Netflix 开源 Chaos Monkey（【公开】Netflix 技术博客，2011 年）与 AWS Fault Injection Simulator（【公开】AWS 官方公告，2021 年前后正式可用）。
- **成熟度**：**L3**。判据：公开材料以厂商博客与产品公告为主，缺第三方案例与量化指标；判定方法是去找**厂商之外**的、含误报率与漏报率的公开数据——只看演示视频不算证据。

这条方向还有一个只靠读文档得不到的判定动作：**在演练复盘里问一句"如果这次交给模型决定，它会在哪一步切错、切错之后谁先发现"**。答不上来说明连评估数据都不存在，此时任何"AI 辅助 DR"的投入都是无的放矢；反过来，如果每次演练都能留下"模型的建议对不对"的记录，这批记录本身就是将来把它升到 L2 所需要的证据。

### 5.3 与本主题既有栈的接口在哪

「AI 时代的容灾」与既有容灾体系不是"结合"关系，而是**挂载**关系：推理服务、模型制品、向量索引三类新对象各自挂到既有的哪一个档位、哪一个环节上，才是本节要说清的事。"结合"式写法省掉了三件必须回答的事——**谁调用谁、数据以什么形态穿过边界、失败时谁负责**。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 推理服务 ↔ 热备 / 多活档位（主文件 §1.1、[§3 设计模式与范式](07-disaster-recovery-section-3-sec3.md)） | 无状态服务挂到既有负载均衡 / DNS 探切之后，多副本跨 Region | 服务方保证副本可重建；SRE 负责探切与切流决策 | 机制成熟，可直接排进路线图（L1） |
| GPU 容量 ↔ 容量规划（Ch12 §04） | **不是数据复制，而是容量预留 + 配额**；接口是云方配额与实例库存 | 平台方保证预留有效；业务方负责降级承诺（排队 / 降档） | 云上是 GA 能力，"跨 Region 秒级接管"无第三方实测（L2） |
| 模型权重 / 向量索引 ↔ 备份与版本化（主文件 §2.1 备份族） | 制品以对象存储形态留存：权重 + 索引快照 + **Embedding 模型版本号** | 制品侧负责"可重建 + 版本可追溯"；恢复方承担重建耗时 | "可重建"现在就能做；"跨 Region 强同步"需逐产品核验（L2） |
| 多模型路由 ↔ 网关（Ch11 横切） | 网关按上游失败率 / 延迟摘除端点，请求在端点池内重试 | 网关团队负责路由策略；各 provider 只负责自身 SLO | 既有技术，不需要 AI 专属设计（L1） |
| 向量检索 ↔ 数据一致性（Ch12 §08） | 索引与原件靠重建对齐，而非跨 Region 强同步；命中不到时降级为关键词 / 元数据检索 | 检索侧负责降级路径：**返回空优于返回过期结果** | 可立即实施（L2） |
| AI 辅助 DR ↔ 演练与可观测（Ch12 §06、Ch11） | **只读**监控与演练数据、**只写**建议与报告，不直连切流开关 | 人工确认者；AI 不承担切换责任 | 概念与产品公告期，不要在架构里预留假设（L3） |
| 容器化 / 单元化 ↔ 故障域划分（Ch12 §01） | 以单元为故障域，推理副本按单元部署，一次请求尽量在单元内完成 | 单元归属方；跨单元请求在故障时失败是可接受的 | 既有技术的复用，与 AI 无关（L1） |
| 切流 ↔ 灰度与回滚（Ch12 §09） | 切流与回滚走同一套灰度通道：先切小比例流量验证，再放大 | 发布方；**回滚的优先级高于切流完成度** | 可立即实施（L1） |
| 推理质量 ↔ 可观测（Ch11） | 新增业务指标穿过边界：降级请求占比、降级答案被下游采信的比例 | 业务方；平台方只提供指标通道 | 需要新建，不是既有指标的复用（L2） |

```text
请求穿过边界的形态（谁把什么交给谁）
  客户端 ──► 网关端点池 ──► 推理副本（Region A / B）
                │              └─ 交接物：请求 + 档位标记（不是「模型名」）
                └─ 失败：摘除端点 + 按档位降级（档位由请求类型决定）
  检索侧 ──► 向量索引 / 原件（对象存储）
                └─ 交接物：Top-K + 元数据 + 原件引用
                   失败：降级为关键词 / 元数据检索，返回空好于返回过期
  制品侧 ──► 权重 + 索引快照 + Embedding 模型版本号
                └─ 交接物：可重建的三件套（三者版本必须同时可查）
                   失败：由恢复方承担重建耗时，而不是由查询方承担错误结果
  ────────────────────────────────────────────────
  注：三条边界的共同点——把「失败时的降级形态」写进接口契约，
      而不是留给实现去猜；猜出来的降级形态无法演练、也无法审计
```

一句话概括这三条边界：**AI 没有新增调用关系，只新增了三种"不会失败的一次"的交接物**——端点池里的档位标记、检索结果里的原件引用、制品三件套的版本号。容灾做得好不好，看这三样东西在故障当天是否齐全，而不看有没有 AI 组件。

### 5.5 被过度宣传的部分

下面三条不是"唱反调"，而是把**被宣传的能力**与**公开证据支持的能力**分开写。判断标准固定：宣传句里有没有可核验的条件（数据规模、误报率、第三方案例）——没有的，就归入下面三条。

**「AI 能预测故障，所以可以提前切流」**——实际能落地的只有"提前准备"而不是"提前切换"。原因：容灾里误报（切走健康主站）与漏报（故障拖长）代价不对称，而预测模型的召回与误报是一对权衡；此外预测结论要变成动作，中间隔着"谁批准"。**它什么时候才会成真**：出现厂商之外的、含误报率与漏报率的公开数据，且产品把预测结论绑定到"预热资源 / 预置容量"这类无副作用的动作上——那才是它第一个合理的落点。

**「Self-Healing DR：故障自动恢复，人不再参与」**——自动化真正能拿走的是"探测"与"执行"两段，而"决策"段的障碍是权限与责任，不是算法。原因：一次误切的代价由业务承担，在没有任何机制能让机器"负责"之前，没有人会把生产流量的切换权交出去。**它什么时候才会成真**：出现公开的"自动切换误判率 / 误切次数"指标并被审计体系接受（即误切可以被追溯与归责），而不是只有"平均恢复时间缩短"的宣传口径。

**「跨云 DR 天然更安全」**——跨云把"单云故障"换成了"两套异构栈的运维与一致性风险"，同时新增数据出口费与专线这两项常驻成本；公开可核验的材料多为案例叙述，缺少含成本与一致性口径的公开数据。原因：容灾的目标是缩短故障时的不可用时长，而跨云把这个目标外包给了一个更难验证的假设（两朵云同时可用、且数据一致）。**它什么时候才会成真**：跨云数据复制与一致性变成产品化能力，并出现在第三方公开案例中（含成本结构）——在此之前，跨云只应作为"可迁移性"准备（容器化、避开厂商专属 API），而不是容灾方案本身。

这三条的共同结构是：**被宣传的能力都指向"决策"，而公开证据都只支持"感知"**。所以在评审任何 AI 容灾方案时先问一句"它输出的是判断还是动作"——输出判断的可以试，输出动作的现在先不要接。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 「推理容灾」的讨论重心会从"多 Region 部署"转到"容量预留"，即把 GPU 预留当成 pilot light 的等价物 | 云厂商 DR 白皮书里出现"GPU 容量预留"作为一个容灾档位；第三方公开案例把它列为标准做法 | 三年后主流做法仍是"接受推理降级 / 排队"，容量预留因价格过高无人采购 |
| AI 辅助 DR 会先在"验证"落地，而不是"决策" | 出现自动比对演练结果与 RPO / RTO 目标的产品，并有第三方生产案例（而非厂商自述） | 产品宣传仍集中在"自动决策切换"，且没有任何面向演练验证的模块 |
| 「AI 原生容灾」这个提法会被拆掉，回归为两件既有事的组合（推理服务多活 + 制品版本化） | 行业不再单独讨论该提法，而是把它并入标准 DR 白皮书的 workload 章节（推理服务 = 无状态服务的一个 workload 类型） | 出现独立的"AI 原生容灾"标准 / 产品品类并被广泛采用 |
| 跨云 DR 在受监管行业之外难以成为主流 | 多年后跨云 DR 的公开案例仍主要集中在金融 / 政企（由双供应商合规要求驱动） | 出现大量互联网公司跨云多活的公开架构，且披露了成本与一致性口径 |

写这四条时的共同约定：**信号必须是外部可观察的**（出现在白皮书 / release note / 公开案例里），而不是"我觉得会"。凡写不出证伪信号的判断，本节不写——它没有信息量。

### 5.7 给架构师的行动建议

下表按"你的处境"分行，而不是按技术分行：同一项技术在不同处境下的正确动作完全不同——已有热备体系的团队要做的是"挂上去"，而刚开始做容灾的团队要做的是"先别谈 AI"。

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有热备 / 多活体系 | 把推理服务挂进既有档位：多副本 + 端点池 + 显式降级档位；为降级期建一个独立评估集 | 观察降级被触发的次数与时长——降级频繁说明容量而非容灾才是问题 | **不要为推理服务单独设计一套容灾**；不要在没有评估集时宣布"降级可用" |
| 刚开始做容灾 | 先按主文件 §1.1 定档位与 RPO / RTO，再问"AI 部分的增量是什么" | 观察 GPU 容量预留的实际价格与可获得性 | 不要在档位未定之前讨论"AI 容灾方案"；不要承诺 GPU 跨 Region 秒级 RTO |
| 自建 RAG | 原件 + Embedding 模型版本 + 索引快照三者一起版本化；演练里真的重建一次索引并记耗时 | 观察所用向量库 release note 是否出现跨集群 / 跨 Region 复制条目及其一致性口径 | 不要为"索引跨 Region 强同步"提前买单；不要让 Embedding 服务用浮动版本引用 |
| 关键链路含推理（在线交易 / 客服） | 按请求类型分级：哪些请求允许降级到小模型，哪些必须明确失败 | 观察线上"降级返回"被下游当正常结果消费的案例数 | 不要把降级返回混进正常结果流；不要让监控只看可用性 |
| 受监管行业（金融 / 政企） | 把演练做成可举证的记录（谁在何时做了什么、达成什么指标） | 观察监管或行业规范是否开始要求"自动化切换的可追溯性" | 不要用 AI 生成的 Runbook 直接进应急流程而不经演练验证；不要把跨云当作合规到位的证明 |
| 以 Spot / 抢占式资源压低推理成本 | 只把可丢失 / 可排队的流量放在 Spot 上；对 Spot 中断做"优雅退出 + 转流量"的自动化 | 观察 Spot 回收真的发生时的转流成功率 | 不要把在线关键链路压在 Spot 上；不要指望 Spot 预警窗口够用来异地重新拉起 |

「明确不要做」这一列的共同逻辑是：**这些动作的代价是确定的（钱、复杂度、承诺），而它们的收益依赖一个尚未成立的假设**（AI 会提前发现故障 / 容量随时能拉起 / 索引可以秒级同步）。等到假设被 5.6 里的信号证实再投入，损失的只是时间，不是钱。

**如果你只能做一件事**：把下一次 DR 演练从"有没有切成功"改成"量四个数"。演练若只验证流程能不能走通，它回答不了本节任何一个问题：

1. 从故障注入到流量切走的**决策段耗时**——这段是 MTTR 方差的主要来源。
2. 在目标 Region 从零拉起推理副本到**可服务**的耗时——5.2.2 的 RTO 下限。
3. 全量**重建一次向量索引**的耗时与占用算力——5.2.3 的处置依据。
4. 降级期间返回内容的分布：多少请求落到哪个档位、下游有没有把它当正常结果消费——5.2.1 的代价。

这四个数不区分"AI 容灾"还是"传统容灾"，**它们对两者都成立**，所以先量它们永远不亏。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**容灾对象的成本函数**——数据可以廉价复制，GPU 容量不能；索引可以从原件重建，模型权重可以从制品加载。因为这一点，"推理服务的接入层容灾"直接落到了 L1（它是既有机制的直接套用），而所有与"容量、制品、索引重建时间"相关的方向都停在 L2，与"决策权与责任归属"相关的方向停在 L3。它**没有**改变的是 RPO / RTO 的定义、复制的语义、档位的划分与 failover 的流程——这些仍然是主文件 §2 的那一套。
>
> 判断本主题下任何新提法的快捷方式：**它要花的是钱、是容量，还是权限？** 花钱与花容量的（GPU 预留、索引复制）现在就能算账；要权限的（自动切换）现在还不成立。
