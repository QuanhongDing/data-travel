## 3. 设计模式与范式

> 原 § 3 共 81 行、为 5 个档位条目 + 1 张业务等级表 + 4 条反模式，缺少结构示意、机制解释与失效分析，重写为 8 小节模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

等级表把容灾讲成「按业务重要性选一档」，但同样是「核心交易系统」，落在三个团队手里的档位常常不同。原因不是预算，而是三条约束：**能容忍丢多少数据（RPO）、能容忍停多久（RTO）、以及写路径上还能加多少延迟（同步复制的代价）**。第三条最容易被忽略，却往往直接推翻前两条的选择。

本主题的全部机制可以压成两句话，后面每个档位都从这两句话推出来：**RPO 由「在哪里等」决定，RTO 由「要不要人来决策」决定。** RPO = 0 的唯一实现方式是「在向客户端返回成功之前，确保远端已持久化」；这个「等」发生在网络协议层、存储引擎层还是应用逻辑层都不改变一件事——它至少要多花一个跨站往返时间，所以**跨站同步有一个由距离决定的物理下限，工程投入无法突破它**。RTO 则由「探测 → 决策 → 执行」三段构成，其中只有决策段的方差最大且最不可压缩（量级推导见 [§ 7 与其他方法对比](07-disaster-recovery-section-7-sec7.md) 的机制一节）。

第四条约束是**故障域的形状**：容灾的有效性等于「副本与主站之间共享的那部分依赖有多少」。物理位置隔开只是必要条件，真正的故障域由共享控制面、共享身份与密钥体系、共享配置下发路径、共享 DNS、共享专线汇聚点这些东西圈出来。所以在读下表时请记住：**档位越高不等于越安全，只等于「交出去的写延迟与运维复杂度越多」。**

这几条约束之间还存在一个容易踩的顺序问题：**先定故障域，再定 RPO/RTO，最后才定技术档位。** 反过来（先选技术、再倒推承诺）的团队，通常会得到一份写着「RPO=0，RTO=5 分钟」的制度文件，而实现它的架构只覆盖了机房级故障——承诺与能力之间的缺口不会在日常暴露，只会在第一次真实故障里暴露。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| RPO 要求（能丢多少数据） | 复制是异步还是同步、重放/追齐链路要不要存在 | 「异地也做同步就有 RPO=0」——写延迟被跨城 RTT 推高，交易 P99 预算先崩 |
| RTO 要求（能停多久） | 切换是自动还是人工、备侧是常驻还是按需拉起 | 「有了自动切换 RTO 就短」——探测与决策不压缩，执行再快也只省几秒 |
| 写延迟预算 | 同步复制能否进写路径、要不要改为单元化 | 「RPO=0 是配置项」——它是选址问题与数据模型问题 |
| 故障域要求（机房 / 城市 / Region / 大洲） | 档位的上限、以及需要隔离哪些共享依赖 | 「跨 AZ 就是容灾」——控制面级故障下两个 AZ 是同一个故障域 |
| 数据形态（能否按用户/订单分区） | 异地多活是否可行、全局热点要不要改模型 | 「多活一定要全局强一致」——分区后只需覆盖跨单元的少量数据 |
| 成本与运维能力 | 备侧是冷备、温备还是多活，以及演练频率 | 「备着就是为了省钱」——冷备闲置的资源成本常高于多活同时承载【经验，量级取决于资源单价与利用率，本目录 §6 案例的结论方向一致】 |

### 3.2 模式逐个拆解（核心节）

以下 6 个档位覆盖原文件列出的全部模式（冷备、温备、热备、同城双活、异地多活），并把速读地图（主文件 §0）中与「同城双活」并列列出的「两地三中心 / 同城多活」一并展开（两地三中心的定义见主文件 §2.1）；最后补上第 7 条——**备份与时间点恢复**，它不是档位，而是所有档位都必须叠加的基础机制。

三句话概括这 7 条的相互关系：**冷备/温备/热备解决「同 Region 内能不能快速起来」，同城双活/两地三中心/异地多活解决「故障域有多宽」，备份与 PITR 解决「能不能回到过去」。** 前两组是「可用性」的不同强度，第三组是「可恢复性」——它不能被前两组替代，因为复制会把逻辑损坏一起复制过去。

#### 3.2.1 冷备（Cold Standby）

- **被什么约束逼出来**：业务能接受**小时级的停机**，但必须防住**数据被写坏**（误删、批量错更新、勒索加密）——约束是「保留时间点」，而不是「保留近实时镜像」。
- **结构**：

```text
生产库 ──► 每日/每周全量 ──┐
         └─ 持续日志归档 ──┴──► 对象存储（Object Lock / WORM 语义，保留 N 天）
                                   │
故障后：建新环境 ──► 恢复基础备份 ──► 重放日志到目标时间点 ──► 校验对账 ──► 接流
                                   └─ 这条链路只提供「回到过去」，不提供「就地接管」
关键隔离：备份存储的写入/删除凭据与生产凭据分离（否则一次误删会同时失去两者）
```

- **为什么这样设计有效**：因为备份保留的是**时间点**而不是镜像，所以它能覆盖镜像类机制覆盖不了的故障——逻辑损坏在同步/异步复制下会传播到所有副本，而「回到污染前的某个时点」只能靠一份没被污染的副本；又因为恢复方向是「新建环境后从零拉起」，所以它对故障类型不做假设，这使它成为唯一能应对「数据被恶意删改」的结构。
- **代价**：RTO 由「建环境 + 恢复 + 校验」的人力主导，且数据量越大、保留期越长，恢复与重放的时间越长；备份保留期的存储成本随保留期线性增长【经验，成本随保留期线性增长，单价按对象存储计】；恢复链路只有在演练时才会被验证，平时是一种「买入期权」式的支出。
- **失效点**：当**「发现损坏的时间」长于「保留期」**时，备份这个优点会反转成缺点——你会拥有一堆完好的备份，却没有任何一份早于污染点，因为保留期覆盖不到发现延迟；保留期该定多长，取决于「你能多快发现一次错误的批量更新」，而不是取决于容量预算。
- **真实使用**：AWS Well-Architected 可靠性支柱把灾难恢复策略分为四类，「备份与恢复（Backup & Restore）」是最低一级，RPO/RTO 为小时级量级【公开，AWS Well-Architected Framework 可靠性支柱及其配套《Disaster Recovery of Workloads on AWS》白皮书；该文档持续更新、不锁定首发年份，四类策略与区间以当期文档为准，读者可按文件名自行核对】；不可变备份的公开机制是对象存储的一次写入多次读取（WORM）语义【公开，Amazon S3 Object Lock 官方公告, 2018】。本目录 [§ 7 与其他方法对比](07-disaster-recovery-section-7-sec7.md) 的 §7.3.4「备份与容灾防的不是同一类故障」把这件事单独列为一节——镜像负责分钟级接管、但会把逻辑损坏同步到所有副本，不可变时间点副本负责「回到某个过去时点」，因此它是与多活并列的独立机制，而不是多活的附属品【转引本仓库 § 7 的机制推导，可按节号复核；本目录 §6 的四个案例讨论的是 RPO/RTO 如何达成与验证，不含不可变备份的内容】。
- **上线前必须验证的一件事**：真正执行一次「恢复到目标时间点」的演练，并记录三个数：取回带宽、恢复耗时、对账发现的不一致条数。三者缺一，你的「可恢复」就还只是文档承诺。

#### 3.2.2 温备（Warm Standby）

- **被什么约束逼出来**：业务要求**分钟级的 RTO**，但不愿为闲置的全量副本长期付费——约束是「备侧必须便宜」，同时「拉起时间必须可预测」。
- **结构**：

```text
主站：应用（多副本）──► 主库
                        │ 异步/半同步复制（日志投递）
                        ▼
备站：数据面常驻（数据库副本、对象存储复制）        ← 只跑数据，不跑全量应用
      应用层：镜像/最小实例（可复核配置，但不承流量）  ← 需要时按预置模板扩容
      ─────────────────────────────────────────────
      拉起 = 扩容 + 预热 + 接流（时间取决于「扩容上限是否被测过」）
```

- **为什么这样设计有效**：因为数据面始终在跑、配置与镜像始终在同步，所以故障后需要做的只是「把计算拉起来」——把不可预测的「环境重建」换成可量化的「扩容与预热」；又因为备侧不承流量，日常成本远低于多活。**代价被换成了一件可测量的事（拉起耗时），而不是一件不可测的事（能不能建起来）。**
- **代价**：备侧资源闲置但并非免费（数据副本与对象存储复制是持续支出）；应用层的镜像与配置必须**定期复核**才不会腐化——「配置腐化」是温备最典型的失血点：半年不拉起，模板里的连接串、证书、IAM 权限就已经全部过时。
- **失效点**：当**拉起所需的容量超过备用区的配额上限**时，优点（RTO 分钟级）反转成缺点（拉起到一半卡在配额上，实际 RTO 以小时计），因为温备的 RTO 承诺建立在「扩容能一次成功」这个未经验证的假设上；同理，当依赖的上游（DNS、证书、第三方接口白名单）需要事前申请时，RTO 由审批时长决定。
- **真实使用**：AWS 的四类灾难恢复策略把这一档拆成相邻两级——「Pilot Light：数十分钟级」与「Warm Standby：分钟级」，Pilot Light 只保留数据面、应用从零按需创建，比 Warm Standby 弱一档【公开，AWS Well-Architected Framework 可靠性支柱及其配套《Disaster Recovery of Workloads on AWS》白皮书；文档持续更新、不锁定首发年份，两级量级以当期文档为准，读者可按文档名自行核对】。本节的温备按「Warm Standby，分钟级」记；若备侧应用完全按需创建、只有数据面常驻，实际落在 Pilot Light 一档，RTO 须按数十分钟量级承诺。判断一家公司的温备是否真实可用，有一条可自行核验的判据：**在备用区做一次不接全量流量的扩容演练，看能不能达到目标实例数**——做不到的温备，实际是冷备。
- **上线前必须验证的一件事**：把「抢占有生产流量的配额」这件事提前做完（配额提升、镜像预热、连接串与密钥复核），并记录一次扩容到目标容量的耗时曲线。

#### 3.2.3 热备（Hot Standby）

- **被什么约束逼出来**：业务要求**秒级 RPO 与分钟级内 RTO**，且允许写路径承担一个**同城（低 RTT）**的同步确认——约束是「不能让任何一次已确认的写丢失」，同时「不能依赖人工决策」。
- **结构**：

```yaml
# 结构要点（以「同步/半同步复制 + 健康检查切换」为例）
主库:  synchronous_commit = on          # 每个事务等待至少一个从库确认
从库:  持续接收 WAL / binlog            # 与主库同 Region，可提升
切换:  多个健康信号（进程、SQL 探测、复制延迟）交叉确认 → 自动提升 + VIP/GSLB 切流
防误切: 脑裂保护（fencing）/ 法定票数（quorum）/ 保守侧停写
```

- **为什么这样设计有效**：因为提交前必须在同 Region 的副本上确认落盘，所以「已确认的写」不会因单机房失效而丢失；又因为切换由多信号交叉确认驱动、不需要人判断，所以 RTO 的方差被压到最小——**这两件事各自都有明确代价：前者是写延迟，后者是误切风险。**
- **代价**：写延迟增加一个同城往返（通常在毫秒级【经验，量级取决于同城专线与机房内网络条件】）；副本侧要一直承担复制开销；自动切换必须配套防误切机制，而这些机制本身也是延迟与复杂度；此外，热备只在本 Region 内构成冗余，跨 Region 的能力要靠 3.2.5/3.2.6 叠加。
- **失效点**：当**故障不是「节点宕机」而是「网络分区」**时，自动切换会把系统推向双写（脑裂），此时「切得快」这个优点反转成数据错乱的来源；正确动作是让自动决策取保守侧（宁可停写也不双写）。另一个失效面是**控制面级故障**：如果备站与主站共享同一 Region 的控制面、IAM 与配额，那么它们不是两个故障域，RTO 由云厂商的修复时间决定，你的自动化在这段时间里完全失效【公开，AWS 官方 us-east-1（北弗吉尼亚）区域事件总结，2020 年 11 月与 2021 年 12 月各发布一篇；读者可按「区域 + 月份」在 AWS 官方事件总结页面定位原文；两次事件的影响范围都超出单可用区、恢复以小时计】。
- **真实使用**：本目录 [§ 6 落地实践](07-disaster-recovery-section-6-sec6.md) 记录的字节「分级 RPO」即把零丢失压在关键数据上，而不是全量拉平【公开，转引本仓库 §6 案例，2019–2024】。这一档的边界可以直接从机制对照表读出：本目录 [§ 7 与其他方法对比](07-disaster-recovery-section-7-sec7.md) 的 §7.3 末尾那张对照速查表把热备（同 Region）的瓶颈段记为「决策段（若需人工确认）」、把它的故障边界记为「抗得住单机房，抗不住控制面级故障」——判断一家公司的热备是否真实，看它的切换在演练里是否真的零人工介入。
- **上线前必须验证的一件事**：在受控环境下制造一次「主库不可达但未宕机」的分区场景，观察系统是进入停写还是双写；演练记录里如果没有这一条，自动切换就是一个未经检验的危险开关。

#### 3.2.4 同城双活 / 同城多活（Same-City Active-Active）

- **被什么约束逼出来**：业务要求 **RPO = 0 且不能接受长时间停机**，同时**写延迟预算不允许跨城往返**——约束把可用的距离锁死在同城（几十公里量级）之内。
- **结构**：

```text
        ┌──────── 同城专线（毫秒级 RTT）────────┐
机房 A                                    机房 B
 应用集群 ◄── 同步 / quorum 复制 ──► 应用集群      ← 两侧同时承流量
 数据库主节点                        数据库备节点（可提升）
        └── 统一调度 / 配置中心 / 服务发现 ──┘
接入层：GSLB / DNS + 就近接入；会话与定时任务须无状态化或有明确归属
```

- **为什么这样设计有效**：因为同城 RTT 在毫秒量级，同步复制的写延迟代价可控；又因为两侧都常驻且同时承流量，所以「备侧闲置」这件事被消除了——**容灾的成本被换成日常产能**。北京—上海这类距离可作为反面对照：京沪大圆（直线）距离约 1,070 km，而容灾口径里常写的「北京—上海 1,200 km」是光缆路由里程量级，两点往返即 2,400 km；光纤中信号传播约 2 × 10⁸ m/s，**只算光学传播**时 1,200 km 的往返约 12 ms，再叠加交换设备与路由绕行后工程实测常在 25–35 ms 量级【推算 + 经验，推导链：2 × 1.2 × 10⁶ m ÷ 2 × 10⁸ m/s = 12 ms；大圆距离由两地坐标按球面距离公式算得 1,067 km；纯传播与实测两个量级及其边界条件同见 [§ 7 与其他方法对比](07-disaster-recovery-section-7-sec7.md) 的 §7.3.1，实际值须以自己拨测为准】——这正是同城与跨城的分界成本。
- **代价**：同城专线与双份资源是持续支出；应用必须无状态化（会话外置、定时任务去重、本地缓存失效策略），这是一次性的、但往往跨多个团队的改造成本；数据一致性判断要设计「谁能写哪一部分」，否则两侧双写会在合并时产生冲突。
- **失效点**：当发生**城市级事件或专线中断**时，优点（RPO=0 且可切换）反转成缺点——两个机房同时不可用或在分区下互相等待，因为同城双活的故障域仍然是「一座城市 + 同一条专线」；同理，**配置中心的全局误改**会同时击穿两侧，因为共享依赖没有隔离。
- **真实使用**：国标 GB/T 20988-2007 用能力等级描述灾难恢复要求，等级越高对「数据零丢失」与远程集群的要求越强【公开，GB/T 20988-2007；各级措辞以标准原文为准】（主文件 §1.1 给出的等级与 RPO/RTO 区间即转引该标准）。本目录 §7 给出的机制对照表也把「同城双活」列为「写延迟代价在毫秒级、性价比最高的一档」。
- **上线前必须验证的一件事**：在只留单侧承载的条件下跑一轮全量业务（不是压测，是真实流量切过去一段时间），记录容量余量、状态依赖（会话、定时任务、文件）与对账差异。

#### 3.2.5 两地三中心（Two-Site Three-Center）

- **被什么约束逼出来**：监管或业务要求「同城高可用 + 异地保数据」，但**不接受把跨城 RTT 加进写路径**——约束把异地中心限定为「保数据的角色」，而不是「同时承写的角色」。
- **结构**：

```text
同城：A 中心（主）◄── 同步复制 ──► B 中心（同城备，可提升）
                     │
                     │ 异步复制 / 日志投递（跨城，不进写路径）
                     ▼
异地：C 中心（保数据 / 可做只读与批量，不承写）
边界：C 中心接管的代价 = 接受「最后一次成功复制的时点」 → RPO > 0
      若把 C 也改成同步 → 写延迟 = 跨城 RTT，交易链路 P99 预算被击穿
```

- **为什么这样设计有效**：因为同城用同步复制拿到 RPO=0，跨城用异步复制拿到「城市级故障下的数据存活」，所以两个不同强度的故障被两套不同代价的机制分别覆盖；又因为异地中心不参与写路径，跨城链路的抖动不会传导为线上交易延迟——**这是一个用「接受 RPO>0」换取「不牺牲写延迟」的显式交易。**
- **代价**：三个中心的资源与跨城带宽是持续成本；跨城异步复制意味着**在整城失效时必然丢一段数据**，这段窗口等于复制延迟（分钟级是常见量级【经验，具体取决于跨城链路质量与复制方式，须实测】）；此外「多久决定把 C 提升为主」是一条只有演练才能回答的流程问题。
- **失效点**：当决策层把「有三个中心」读成「三个中心都能写」时，优点（城市级故障下有数据）反转成缺点（业务连续性承诺落空）——整城失效时切到 C 必须接受 RPO > 0，而对外承诺的 RPO=0 无法兑现；反过来，若为了兑现 RPO=0 把 C 改成同步，跨城 RTT 会直接进入每次提交，写延迟按跨城往返量级抬升。
- **真实使用**：阿里自 2010 年上线「两地三中心」、2017 年大规模应用「异地多活」、2019 年推进「三地五中心」【公开，转引本目录主文件 §1.4 演进历程，具体年份以阿里公开材料为准】。可自行核验的判据：问一句「整城失联后，异地中心接管的 RPO 是多少，谁签的字」——答不出来的组织，实际上没把这条路走通过。
- **上线前必须验证的一件事**：单独演练一次「提升异地中心」，记录实际 RPO（最后一次复制时点与故障时点之差）与业务侧接受程度；这个数字必须写进对外承诺，而不是留在架构图里。

#### 3.2.6 异地多活（Multi-Region Active-Active）

- **被什么约束逼出来**：既要**城市级甚至区域级故障下持续可写**，又要**写延迟不跨城**——两条约束的交集只有一个解法：**让跨城的同步只覆盖必须跨城的那一小部分数据**，即单元化（数据按用户/订单分区，各单元独立承写）。
- **结构**：

```text
路由层：分片键（user_id / order_id / shop_id）→ 归属单元的字典
单元 A（Region 1）              单元 B（Region 2）
 应用 + 数据库（主）             应用 + 数据库（主）
   · 单元内数据：同步复制 → RPO = 0（单元内）
   · 单元间：异步复制 / 变更订阅 → 供跨单元查询与统计
全局：身份、发布、密钥、路由字典（理想状态只剩这些共享）
残留代价：全局唯一热点（全局递增 ID、全局库存池、全站计数）必须改数据模型
         （改为可分段 ID、按单元配额、可合并的近似计数）
```

- **为什么这样设计有效**：因为写只在单元内同步完成，跨城只走异步，所以「RPO=0」与「写延迟不跨城」可以并存——但**RPO=0 的适用范围被缩小到「单元内的数据」**，跨单元的数据仍然有复制窗口；又因为故障被限制在一个单元内，影响面从「全站」变成「一个分片」，可用性预算因此可以装进年度停机时间（例如 99.99% 对应一年约 52.56 分钟【推算，推导链：365 × 24 × 60 = 525,600 分钟；× (1 − 0.9999) = 52.56 分钟】）。
- **代价**：分片键一旦选定，改造成本极高（数据迁移 + 路由字典变更 + 跨单元事务改写）；跨单元查询要么做合并查询、要么走异步数据（接受延迟与不一致）；运维复杂度上升为「多套等价环境」，包括发布、监控、容量与演练。
- **失效点**：当业务存在**无法分区的全局热点**时，优点（RPO=0 且写延迟低）反转成缺点——所有写被逼回跨城同步，前两条约束同时失守；此时正确动作是改数据模型（分段、配额、近似值），而不是加快网络。另一个失效面是**路由/归属数据的变更**：归属迁移期间的跨单元双写或漏写是静默的，对账才发现。
- **真实使用**：本目录 [§ 6 落地实践](07-disaster-recovery-section-6-sec6.md) 记录的美团「3 Region 多活容灾：用单元内副本拿到 RPO 0，用单元间隔离控制影响面」【公开，转引本仓库 §6 案例，2019–2024】；Netflix 的多区域 active-active 与区域疏散演练自 2013 年起公开【公开，Netflix Tech Blog, 2013】。可自行核验的判据：查你的业务里「必须全局唯一」的字段有几个——每个都是一个不会被容灾解决的物理约束。
- **上线前必须验证的一件事**：做一次「归属迁移」演练——把一小批用户的归属从一个单元改到另一个单元，观察跨单元双写与漏写是否发生、对账能否发现。这类错误在生产里是静默的。

#### 3.2.7 备份与时间点恢复（基础机制，不是档位）

- **被什么约束逼出来**：上面 6 个档位解决的都是「站点/城市失效」，但**逻辑损坏**（误删、批量错更新、程序缺陷、勒索加密）会随复制到达每一个副本——约束是「必须能回到某个过去的时间点」，而这件事不能由任何复制机制提供。
- **结构**：

```text
全量（周期 T_full） + 增量/差异（周期 T_incr） + 持续日志归档（binlog / WAL）
        │
        └─► 恢复目标 = 基础备份 + 重放到目标时间点（PITR）
平均 RPO ≈ T_incr / 2   【推算，推导链：损坏发生在两次增量之间的时点服从均匀分布，期望为半个周期】
注意：平均 RPO 是统计期望，单次事故的 RPO 最坏可达一整个 T_incr
```

- **为什么这样设计有效**：因为备份与日志是**两条独立的恢复能力**（一条回得到某个全量点，一条才能精确到秒级时间点），所以「多久做一次全量」与「能恢复到多细」被解耦；又因为时间点副本与生产凭据隔离，它能防住生产侧已经无法自救的场景——这是档位表里任何一档都替代不了的能力。
- **代价**：存储随保留期线性增长；链路自身的故障模式是「静默失败」（备份作业连续失败几天却没人发现），所以必须有独立的备份成功告警与**恢复验证**；跨全量与增量的恢复过程耗时很长，与数据量成正比。
- **失效点**：当备份**可被生产侧凭据删除**时，优点（能回到过去）反转成缺点（攻击者拿到生产凭据即等于拿到备份的删除权），因为隔离性没有做；当只有备份成功告警、没有恢复验证时，备份链路的「成功」与「可恢复」是两件事。
- **真实使用**：对象存储的 WORM 与保留期强制是公开可用的机制【公开，Amazon S3 Object Lock 官方公告, 2018】；PostgreSQL 官方文档描述的 PITR 依赖「基础备份 + WAL 归档 + 恢复目标」三件套【公开，PostgreSQL 官方文档 · 持续归档与时间点恢复；步骤以当期版本文档为准】。
- **上线前必须验证的一件事**：问三个问题——**谁能删它**（是否与生产共用凭据）、**保留多久**（是否覆盖最慢一类损坏的发现延迟）、**恢复一次要多久**（没测过就等于不知道）。

| 约束组合 | 推荐档位 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |

| RPO = 0 + 写延迟预算毫秒级 | 3.2.4 同城双活 | 跨城同步无法在毫秒预算内完成 | 应用是否已无状态化 |
| 城市级故障下「保数据」即可 | 3.2.5 两地三中心 | 异地多活需要单元化改造，成本高一个量级 | 业务能否接受接管时 RPO > 0 |
| 城市级故障下仍须可写 + 低延迟 | 3.2.6 异地多活（单元化） | 两地三中心的异地只保数据，不承写 | 是否存在无法分区的全局热点 |
| 只有备份、没有演练 | 先不改架构，先建演练能力 | 任何档位在没有演练数据时都等于「未知 RTO」 | 最近一次演练的实际 RPO/RTO 实测值 |
| 存在全局唯一热点且必须跨城 | 先改数据模型，再选档位 | 同步确认必然付一个跨站往返，任何档位都绕不开 | 热点字段是否可分段或近似 |
| 合规要能自证恢复能力 | 任意档位 + 审计与演练常态化 | 没有演练与留痕，架构再强也无法向监管举证 | 演练记录与恢复耗时是否可归档调取 |

表中最常被误选的一对是 **3.2.5 两地三中心与 3.2.6 异地多活**：两者都画了三个（或更多）中心，看起来只差规模，实质上差在「异地能不能承写」。误选的后果有两种，都很具体：一是整城失效时被迫把异地中心提升为主，才发现在异步复制下必然丢失一段数据，而对外承诺是 RPO=0；二是为了兑现承诺把异地复制改成同步，写延迟按跨城往返抬升数十毫秒量级【推算，见 3.2.4 的距离折算链】，交易链路的 P99 预算被击穿，团队随后开始加机器——而这是一次选址与数据模型问题，加机器无效。

读这张表的正确顺序是从「关键判据」一列倒着读：先量出自己的复制延迟、能否分区、写延迟预算，再去找匹配行。另外提醒一句：**推荐档位这一列不是排他的**——一家公司可以同时对交易数据用异地多活、对报表数据用冷备、对日志数据只做聚合留存，按数据类分级本身就是正确做法，用一个统一目标覆盖全系统才是反模式（见 3.5）。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：一份数据 + 两份时间预算（防写坏 vs 防站点失效）** = 3.2.1 + 3.2.3/3.2.6。构成：同步/异步复制提供分钟级接管，对象存储上的时间点副本（WORM）提供「回到故障前的某个时点」。两者防的不是同一类故障——镜像会同步传播逻辑损坏，时间点副本不会，但它的恢复方向是「回到过去」而不是「就地接管」。运维代价：两套凭据、两套演练脚本；适合任何已经上了热备以上档位的系统。

**组合 B：同城同步 + 异地异步（3.2.4 + 3.2.5 的组合）**。构成：同城两机房同步复制拿到 RPO=0，异地中心异步接收日志承担城市级故障下的数据存活。职责边界要写清：异地中心的角色是「保数据 + 接管时明确 RPO>0」，不是「日常可写」。运维代价：跨城带宽与三套环境的一致性对账；适合「有监管要求、但写延迟预算不允许跨城同步」的业务。

**组合 C：异地多活 + 单元化 + 分级目标（3.2.6 + 开关）**。构成：按分片键划单元，单元内 RPO=0，单元间异步；同时把「全局唯一热点」单独列出并改造（可分段 ID、配额、近似计数）。运维代价最高：多套等价环境的发布、监控与演练，且路由字典本身成为关键路径；适合用户/订单天然可分区、且承诺「城市级故障持续可写」的业务。

**组合 D：按数据类分级（同一家公司同时用多个档位的做法）**。构成：交易/订单类走 3.2.6（单元化 + 单元内同步），配置与用户资料走 3.2.4（同城双活 + 全局读），报表与日志走 3.2.1（周期性快照 + 聚合留存），全部叠加备份与 PITR。职责边界：分级依据是「这张数据被错误更新后能不能靠重算修复」——**能重算的就不要付 RPO=0 的成本**。运维代价：分级本身要维护一张「数据类 → 目标 → 责任人」的登记表，且新系统上线时必须先归类。适合规模：中大型组织，也是本目录 §6 四个案例共同呈现的形态【公开，转引本仓库 §6 案例，2019–2024】。

四句总纲：**组合 A 决定「能不能回到过去」，组合 B 决定「城市级故障下还剩什么」，组合 C 决定「城市级故障下还能不能写」，组合 D 决定「这些成本花得值不值」。** 组合 A 是任何档位都该叠加的底线，组合 B 是「同城已做到、异地只求保数据」的最优性价比，组合 C 是唯一能同时装下「城市级故障」与「低写延迟」的形态（代价是数据模型先让步）。 四者叠加时，最容易失控的不是技术，而是**分级登记表的维护**——它一旦过期，分级就退化成「按老印象配置」。所以这张表应该长这样（可被审计、可被核对，而不是留在架构文档里的一段话）：

```yaml
# 分级登记表（下列数值均为示例，实际值须由业务签署）
# 每一行 = 一类数据，一个签署过的目标，一个具体责任人
- data_class: 交易与订单
  rpo: 0                      # 适用范围必须写清：单元内数据；跨单元为异步
  rto_minutes: 1
  pattern: 异地多活 + 单元化      # 对应 3.2.6
  failsafe: 不可变备份           # 对应 3.2.7，与镜像路径凭据隔离
  backup_retention_days: 30    # 依据：最慢一类损坏的发现延迟
  drill: 季度，含区域疏散与回切
  owner: <具体角色；写团队名等于无人负责>
- data_class: 报表与埋点
  rpo: 小时级
  rto_minutes: 240
  pattern: 周期快照 + 聚合留存     # 对应 3.2.1
  failsafe: 快照副本（可重算，因此不必付 RPO=0 的成本）
  drill: 半年
  owner: <具体角色>
```

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 灾备只备份不演练 | 演练记录停留在立项那年；切换步骤只存在于文档 | RTO 从「一个可估计的随机变量」变成「未知数」，切换失败点会在真实故障中第一次暴露 | 演练要协调多个团队且占用生产窗口，被当成可推迟的工作 | 固定节奏的真演练（含回切），每次记录实测 RPO/RTO 与未通过项 |
| RPO / RTO 不量化 | 问「能丢多少数据」时得到的答案是「尽量少」 | 无法分级，于是用最贵的手段覆盖全部数据，或最便宜的手段覆盖关键数据 | 指标需要业务签字，而技术团队不愿把承诺写死 | 由业务签署单一数字（含适用范围：哪些数据、哪些路径） |
| 跨 Region 同步延迟失控 | 监控只盯副本存活，不盯复制延迟；RPO 假设秒级、实测分钟级 | 异步复制下的真实 RPO 由复制延迟决定，延迟不监控就无法知道当前能丢多少 | 复制是基础设施行为，应用侧看起来「一直没报错」 | 把复制延迟当一等指标监控与告警，并定期做「停主站测实际丢失量」的验证 |
| 灾备切换流程不清 | 故障时找不到 Runbook，或找到的版本已过期 | 决策段耗时占绝大多数，RTO 呈长尾，SLA 看的是尾部而不是均值 | 流程文档被当成一次性交付物 | Runbook + 演练 + 版本化；明确「谁有权说切 / 说切回」 |
| 自动切换无脑裂保护 | 演练中制造网络分区，系统出现双写 | 自动切换把可用性拉满的同一瞬间，把数据一致性风险也拉满 | 只按「节点宕机」设计故障模型，忽略了分区 | 分区时取保守侧（停写）+ fencing/quorum，并把该行为纳入演练 |
| 备份与生产共用凭据 | 备份存储的删除权或密钥与生产同一套 | 一次误删或勒索加密会同时摧毁生产与备份，时间点副本失去意义 | 凭据复用是省事的默认路径 | 独立凭据 + 不可改写（WORM）+ 独立账号 |
| 用一个统一目标覆盖全系统 | 全公司一张表写着「RPO=0，RTO=5 分钟」 | 目标与成本脱钩：为该目标付了全量成本，却仍有大量系统实际做不到 | 承诺写在一份制度文件里，而不是按数据类与路径分级 | 按数据类与路径分级定目标，各自写下适用范围与责任人 |
| 把演练当成一次性项目 | 演练报告只在立项与验收时存在，之后无人维护 | 恢复流程与真实环境之间的差距随时间扩大，演练结论失效 | 演练没有纳入日常工程节奏，也没有指标跟踪 | 固定节奏 + 未通过项跟踪闭环 + 每次实测值可对比 |

其中三个最危险，值得单独展开：

**灾备只备份不演练。** 它的典型暴露方式不是「切换脚本跑不动」，而是一连串小清单同时过期：DNS 的 TTL 与解析指向、证书与密钥的有效期、IAM 权限与配额、第三方接口出口白名单、许可证、连接串里写死的主站地址、监控与告警通道本身。这些都不属于「切换逻辑」，而是切换时才会被读到的**一次性清单**；只有真演练会把它们暴露出来。所以演练的价值不在于验证架构，而在于让这份清单保持有效。

**跨 Region 同步延迟失控。** 它的危险在于**双向静默**：应用侧只看到「写入正常」，基础设施侧只看到「副本存活」，而真正的 RPO 取决于复制延迟这个没人监控的量。典型暴露方式是主站故障后按秒级 RPO 的设想接管，实际丢失了一段数据，事后复盘才发现复制延迟在过去一段时间已持续增长（跨城链路劣化、大事务阻塞、副本追赶不上）。修法是把「复制延迟」与「副本存活」分成两个指标，并定期做一次「假设现在故障，会丢多少」的推演。

**自动切换无脑裂保护。** 它属于「越自动化越危险」的一类：自动化把 RTO 压到分钟级的同时，也把「判断错误就执行」这件事自动化了。典型暴露方式是网络分区（而不是节点宕机）——两侧都认为对方已死，各自提升为主，随后在两个方向接受写入，等分区恢复时数据冲突已经产生，且冲突无法靠重放修复。机制上的原因很直接：**可用性与一致性在网络分区下不可兼得**，任何自动切换方案都必须事先回答「分区时站在哪一侧」。当团队只按「节点宕机」设计故障模型时，这个问题从来没有被问过。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原档位 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 承诺从「宕机可等」到 99.99% | 单机房 + 备份 | 单机房无法把年度停机压进 52.56 分钟【推算，推导链见 3.2.6：525,600 分钟 × 0.0001】的预算 | 3.2.4 同城双活 | 应用无状态化、会话与定时任务改造、双份资源长期持有 |
| 从「机房级故障」到「城市级故障」 | 3.2.4 同城双活 | 同城双活的故障域本来就是「一座城市 + 一条专线」 | 3.2.5 两地三中心（先保数据） | 跨城带宽 + 数据追齐流程 + 明确接管时的 RPO>0 |
| 从「保数据」到「持续可写」 | 3.2.5 两地三中心 | 异地只保数据，整城失效时无法继续承写 | 3.2.6 异地多活 + 单元化 | 分片键选择与数据迁移、跨单元事务改写、路由层成为关键路径 |
| 写入出现无法分区的全局热点 | 3.2.6 异地多活 | 热点被逼回跨城同步，写延迟与可用性同时失守 | 改数据模型（分段 ID / 配额 / 近似计数）而不是换档位 | 业务语义变更，需与业务共同签字确认可接受的近似 |
| 合规要求从「无」到「需举证」 | 任意档位 | 没有审计与演练记录，无法向监管证明恢复能力 | 演练与审计常态化（含第三方演练） | 组织成本为主：固定演练窗口、记录归档、责任人 |
| 备份威胁从「误删」到「勒索 / 内部人」 | 周期全量 + 日志归档 | 可被删除的备份在凭据泄露后等同于没有备份 | 不可变备份（WORM）+ 独立凭据 | 保留期存储成本上升；恢复演练频率上升 |
| 单库从 TB 到 PB | 逻辑备份 / 定时导出 | 一次全量导出与恢复的时间超出停机窗口，备份窗口与业务窗口互相挤压 | 物理备份 / 存储快照 + 增量 + 日志归档 | 需要存储层配合（快照一致性、跨 Region 复制通道） |
| 组织从 1 个团队到多团队共管 | 口头约定「谁切谁回切」 | 故障时决策段耗时增长，RTO 尾部变长 | 权限与流程显式化（谁有权切 / 切回），并把演练变成例行 | 需要持续的组织投入，而不是一次性交付 |

一句话总结这一节：**档位不是被「用户量」推动升级的，是被承诺（RPO/RTO）、故障域要求与数据形态这三个约束的变化推动的**——其中数据形态这条最容易被忽略，而它恰恰决定「异地多活」这条路走不走得通。

### 3.7 自检清单

- [ ] RPO 与 RTO 是否为**单一数字**、由业务签署，并写明适用范围（哪些数据、哪些路径）？
- [ ] 复制延迟是否作为独立指标被监控与告警（而不是只监控副本存活）？
- [ ] 最近一次演练的时间、参与人、**实测** RPO/RTO 是否有记录，且未通过项有跟踪闭环？
- [ ] 演练是否包含**回切（failback）**，而不只是切过去？
- [ ] 备份存储是否使用与生产**隔离的凭据**，且是否具备不可改写（WORM）语义？
- [ ] 备份保留期是否长于「最慢一类损坏的发现延迟」？给出天数与依据。
- [ ] 「谁有权说切 / 谁有权说切回」是否明确到角色，且不依赖某个人在场？
- [ ] 网络分区（脑裂）场景下，自动切换的行为是保守停写还是双写？是否演练验证过？
- [ ] 是否存在必须全局唯一的数据（全局 ID、库存池、计数）？是否已列出并给出改造计划？
- [ ] 副本与主站共享的依赖清单（控制面、IAM、密钥、DNS、专线汇聚点、配置中心、发布系统）是否画过？
- [ ] 备侧容量是否做过「能否接住 100% 流量」的实测？
- [ ] 是否有一张按数据类分级的登记表，且每行都有具体责任人（不是团队名）？

### 3.8 小结

| 你的约束 | 建议档位 | 关键理由（机制层面） |
| --- | --- | --- |
| 停机可等小时级 + 要能回到过去 | 冷备 + 不可变备份 | 只有时间点副本能对抗逻辑损坏；镜像类机制会传播损坏 |
| RTO 分钟级 + 成本敏感 | 温备 | 数据面常驻、计算按预置模板拉起，代价换成可测量的扩容耗时 |
| RPO 秒级 + 单 Region | 热备 | 同步/半同步复制 + 多信号自动切换，代价是写延迟与防误切机制 |
| RPO = 0 + 毫秒级写延迟预算 | 同城双活 | 同城 RTT 使同步确认的代价可控，双活让备侧不闲置 |
| 城市级故障下保数据 | 两地三中心 | 同城同步 + 异地异步，用接受 RPO>0 换取不牺牲写延迟 |
| 城市级故障下持续可写 | 异地多活 + 单元化 | 把跨城同步压缩到只需覆盖跨单元数据；代价是数据模型让步 |
| 无法分区（全局热点） | 先改数据模型，再谈档位 | 物理下限不会被架构绕开：同步确认必然付一个跨站往返 |
| 仅需合规举证、业务可停数小时 | 冷备 + 备份审计留痕 | 为举证能力付多活的成本没有收益；举证靠的是可调取的演练与恢复记录 |

> 本节小结：本主题下决定档位选择的**唯一那条约束**是——**你能不能在「返回成功之前等待远端确认」**（也就是能不能接受写路径上多一个跨站往返时间）。能等，同城同步就能给你 RPO=0；不能等，就必须把数据分区、让跨城只走异步。其余约束（RTO、成本、团队能力）都在它之下做微调。
