## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表给 `RPO / RTO / 成本 / 复杂度` 逐格打了 1–5 分，再加一行（维度）「综合推荐度 ★」。它的问题不是分数定得不准，而是**四类不同性质的东西被当成了可加总的量**：RPO 与 RTO 是**需求**（由业务与合规给定，是不可退让的边界），成本与复杂度是**代价**（可以比较、可以预算）。把需求与代价同向打分，等于默许「用一点数据丢失换一点成本」——而一致性不满足是**正确性问题**（资金错账、账实不符），没有折扣可打，只能作为硬约束先行筛掉候选，再在剩下的里比代价。

第二个问题是**结论被写成绝对的，而它其实是场景相关的**。「冷备 = 1 分」在移动 App 在线交易场景里成立，但在 T+1 离线分析、内部报表、训练数据管线这类**可以停 4 小时**的场景里，冷备是唯一理性的解——同一维度在两个场景里权重相反。打分表只能给一个数，于是它必然在其中一个场景里给出错误结论。

第三个问题是**候选不同层**。`冷备 / 温备 / 热备` 是「备用环境的就绪程度」，是同一族里的三个**档位**；`同城双活 / 异地多活` 是「谁在承流量」这个正交轴上的取值。打分表把这两层塞进同一张表逐格打分，读者会以为它们互相替代。而一套完整的容灾选型里还有两条**打分表未涵盖、但同属选型开关轴**的维度：**复制方式**（同步 / 半同步 / 异步）与**切换方式**（手动 / 半自动 / 自动，见 §7.2 与主文件 §2.3）。这四层（档位 / 接入形态 / 复制方式 / 切换方式）必须成套选，且各层的取值可以自由组合——「异地多活 + 异步复制 + 自动切流」与「异地多活 + 半同步 + 人工确认」是两种不同的系统。

第四个问题是**阈值凭空来**：「99.9% → 温备、99.99% → 热备」。但 99.9% 对应**每年 8.76 小时**停机预算、99.99% 对应 **52.6 分钟**、【推算，按 365 天 × 24 小时 × 60 分钟 ×（1 − 可用性）计算】——8.76 小时的预算完全可以被一套「冷备 + 自动化恢复脚本」吃掉；而 52.6 分钟里，一次跨 Region 的人工决策加切流就可能占掉大半。所以「可用性目标 → 档位」的映射不能查表，必须先把目标翻译成**停机预算**，再用自己的故障模型算出**主要故障形态的恢复时长**，两者一比才得出档位。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 故障域边界 | 你要防的那类故障，其边界画在哪里（进程 / 机器 / 机房 / 城市 / Region / 云账号） | 副本与主站在同一故障域内等于没放；边界画错时 RPO / RTO 都只是纸面数字（见 §7.3.3） |
| RPO 的达成机制 | 「不丢数据」靠提交前等远端确认，还是靠事后补 | 等待位置决定写延迟下限 = 跨站 RTT，这是物理约束不是调优问题（见 §7.3.1） |
| RTO 的构成 | 探测 / 决策 / 执行三段各占多久 | 三段的方差差异极大，自动化的收益几乎全部来自压掉「决策」段（见 §7.3.2） |
| 数据可分区性 | 一次业务请求能否只在一个单元内完成 | 能分区时跨站同步只覆盖少量跨界数据；不能分区则「RPO=0」与「跨站」在物理上二选一 |
| 时间维度可回滚性 | 你需要的是「回到 5 分钟前」还是「就地接管」 | 备份与容灾防的不是同一类故障，逻辑损坏只能靠时间点副本（见 §7.3.4） |
| 演练与实测能力 | 上次真实切换是什么时候、实测指标是多少 | 未演练的容灾在真故障时按未验证路径执行，「宣称指标」与「实测指标」常差一个数量级 |

> 这 6 条里前四条是技术判据，第五条是**语义判据**（决定要不要两套机制），第六条是**组织判据**（决定承诺能不能兑现）。打分表把第六条完全漏掉了，而它恰恰是「灾备建设完成但故障时用不起来」的最常见原因。

**打分表的四个维度去哪了**（保留读者已知的讨论对象，只是换了问法）：`RPO` 与 `RTO` 从「打分维度」上升为**输入约束**——它们是业务方给定的数，不是候选方案提供的功能，所以在新框架里承担「第一层筛选」的角色（§7.5 第 1、2 层）；`成本` 从「一个分数」拆成**成本函数的形状**（哪一项随数据量增长、哪一项随故障次数增长，§7.4）；`复杂度` 拆成**常驻组件数与值班技能要求**，并归入「运维代价」而不是独立打分维度（§7.6 的每条组合都会点名）。打分表的「综合推荐度 ★」不再保留——它没有可复算的依据，而本章的每个分支都要能回溯到一条机制或一条公开证据。

### 7.2 候选方案全景

> 本节覆盖全部候选（冷备 / 温备 / 热备 / 同城双活 / 异地多活），并按主文件补入备份族（§2.1 的 Backup / Snapshot / PITR）、日志传输（§2.1 的 Log Shipping / CDC）、两地三中心（§2.1）、同步 / 半同步 / 异步复制（§2.3 的同步策略）、手动 / 自动切换（§2.3 的切换策略）、单元化（§1.3、§2.4）、混沌演练（§1.3、§2.4）七项。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 计费方式 |
| --- | --- | --- | --- | --- |
| **备份族**（全量 / 增量 / 快照 / PITR / 不可变备份） | 时间点副本 | 周期性留存历史状态，可回退到过去某一时刻 | 全部系统（法定最低要求） | 按存储容量与取回量计价 |
| **日志传输 / CDC 复制** | 复制通道 | 用 binlog / WAL / 变更流做增量投递，可在任意层重放 | 数据库、数仓、缓存同步 | 开源（Debezium、Flink CDC）+ 云托管 |
| **同步 / 半同步 / 异步复制** | 复制语义（开关轴） | 提交是否等待远端落盘——决定 RPO 与写延迟 | 全部单主数据库 | 数据库内置 |
| **冷备（Backup & Restore）** | 就绪度最低档 | 只留数据副本，故障时从副本重建整套环境 | 内部系统、离线分析、训练管线 | 通用；云上按存储 + 出流量计费 |
| **温备（Pilot Light / Warm Standby）** | 中间档 | 数据层近实时同步、应用层留最小可运行副本，故障时扩容接管 | 一般互联网业务 | 通用 |
| **热备（Hot Standby）** | 高就绪档 | 全量资源常驻 + 实时复制 + 健康探测驱动切换 | 交易类核心系统 | 通用 |
| **同城双活（Active-Active）** | 同城接入形态 | 同城两（三）机房同时承流量，数据同步复制 | 金融核心、电商交易 | 需同城专线与统一接入层 |
| **两地三中心** | 同城双活 + 异地数据中心 | 同城两机房承接业务，异地第三中心承接灾难接管 | 金融、政企（定义见主文件 §2.1） | 自建或专有云，含专线成本 |
| **异地多活（Multi-Region Active-Active）** | 跨城接入形态 | 每个 Region 独立承接（分片后的）流量，数据按归属写入 | 超大规模互联网 | 以自研为主 |
| **单元化** | 收敛故障域 | 把一次请求收敛到单元内完成，使故障域 = 单元 | 阿里等超大规模系统（见 Ch12 §01） | 自研，需改造路由与数据归属 |
| **手动 / 半自动 / 自动切换** | 切换机制（开关轴） | 由人还是由健康探测决定「切」 | 全部 | 平台内置或自研编排 |
| **混沌工程 / 演练** | 验证手段 | 主动注入故障，验证切换链路与 Runbook 是否真的可用 | Netflix 起家，后被广泛采用 | 开源（Chaos Monkey 等）+ 云托管（如 AWS FIS） |

**这些候选只分 3 族**：**族 1 时间点恢复**（备份族）——解决「回到过去」；**族 2 就绪度档位**（冷备 / 温备 / 热备 / 同城双活 / 两地三中心 / 异地多活）——解决「多久能接管」，同族内部是同一根轴上的取值；**族 3 支撑开关**（日志传输、复制语义、切换机制、单元化、演练）——不独立存在，而是串在族 2 每个档位上的可选件。**先选族 2 的档位，再选族 3 的开关**，能省掉一半比较；反过来先纠结「同步还是异步」是没有意义的，因为档位不同，这个开关的代价完全不同（见 §7.3.1）。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 RPO 靠「在哪里等」决定：跨站同步的写延迟有一个物理下限

**机制是什么**：RPO=0 的唯一实现方式是**在向客户端返回成功之前，确保远端已持久化**。这个「等」发生的层次（网络协议 / 存储引擎 / 应用逻辑）不影响一件事：**它至少要多花一个跨站往返时间**。

**各候选的实现差异**：

| 复制语义 | 等待什么 | RPO | 写延迟下限 |
| --- | --- | --- | --- |
| 异步复制 | 不等远端 | > 0（等于复制延迟窗口） | 无额外 |
| 半同步复制 | 等指定从库写入 relay log / WAL | 窗口收窄但不为零 | +1 × 跨站 RTT |
| 同步 / quorum 复制 | 等多数派持久化 | 0（在多数派存活的前提下） | +1 × 跨站 RTT（Raft 单轮）；跨站点部署可能 +2 轮 |
| 对象 / 文件跨 Region 复制 | 由复制服务后台完成 | 分钟级（见下） | 不影响在线写 |

**由此必然导出的性质**：因为 RPO=0 要求远端的确认，所以**跨站同步的写延迟下限由距离决定，而不是由工程投入决定**。光纤中信号传播速度约为 2 × 10⁸ m/s（对应折射率约 1.5），因此北京—上海约 1,200 km 的纯传播往返至少 2 × 1.2 × 10⁶ ÷ 2 × 10⁸ ≈ 12 ms【推算，仅含光学传播，不含交换设备与路由绕行】；工程实测通常在 25–35 ms 量级【经验，公网与专线绕行差异较大】。若你的核心交易路径写 P99 预算是 10 ms，那么「跨 1,200 km 的 RPO=0」在物理上就不可能——这不是选型问题，是选址问题。

**公开证据【公开】**：AWS Well-Architected Framework 可靠性支柱给的四类灾难恢复策略，其 RPO/RTO 量级依次是「备份恢复——小时级」「Pilot Light——数十分钟级」「Warm Standby——分钟级」「多站点主动 / 主动（Multi-Site Active/Active，即多站点同时承流量，不是主备结构）——秒级到接近零」（[AWS Well-Architected Framework 可靠性支柱及配套《Disaster Recovery of Workloads on AWS》白皮书，2018 年首次发布、此后多次更新]；具体区间以当期文档为准）。这条量级阶梯与上面的机制推导一致：**越接近 RPO=0，就越必须把「等待」放进写路径，于是代价从存储费变成延迟**。另一个更强的证据是对象复制通道：Amazon S3 Replication Time Control 的承诺是「99.99% 的对象在 15 分钟内完成复制」【公开，AWS S3 Replication Time Control 功能说明与 SLA；该承诺写在持续更新的官方文档里，来源可核验，但不锁定发布年份，数值以当期文档为准】——**即便由云厂商托管的复制通道，其公开承诺也只是分钟级**。因此「RPO 秒级」不能靠跨 Region 的对象复制达成，只能靠提交前同步（付 RTT）或把写入收敛进单元（见 §7.3.3）。

**失效条件**：当写入可以分区（不同用户、不同订单落在不同单元）时，跨站同步只需要覆盖**跨界的那一小部分数据**，物理下限的代价被摊薄到可以忽略——这就是单元化能让「异地多活 + 强一致」并存的原因。反过来，如果业务存在**全局唯一热点**（全局递增 ID、全局库存池、全站计数），跨站同步的代价必然集中在这一处，此时正确的动作是改数据模型（把全局量改成可分段或可合并的近似量），而不是加快网络。

#### 7.3.2 RTO 由「探测 + 决策 + 执行」三段构成，而方差最大的是决策段

**机制是什么**：从故障发生到业务恢复，时间被消耗在三段上：**探测**（多快判定「该切了」）、**决策**（谁有权说「切」、要不要会签）、**执行**（切流、连接迁移、数据追齐）。把 RTO 当成一个整体去压，最常见的后果是压错了段。

**各候选的实现差异**：

| 切换机制 | 探测 | 决策 | 执行 | 典型的段占比 |
| --- | --- | --- | --- | --- |
| 手动切换 | 靠人发现（监控告警） | 多人会签 + 上报 | 运维按 Runbook 操作 | 决策段占绝对多数【经验】 |
| 半自动 | 健康探测触发 | 一人确认 | 预置脚本执行 | 决策段仍可占一半以上【经验】 |
| 全自动 | 多信号交叉确认 | 无（规则预置） | 预置路径自动执行 | 执行段为主 |
| DNS / GSLB 切流 | 依赖探测 | 依赖配置变更 | 受 TTL 与客户端缓存影响 | 执行段的尾部很长（见下） |

**由此必然导出的性质**：因为**人的判断延迟方差远大于机器执行的方差**，所以只要「决策」还挂在人身上，RTO 就是一个呈现长尾的随机变量（均值常在 30 分钟量级、尾部可达数小时，而不是稳定的 30 分钟）【经验，量级取自行业普遍的故障处理记录，须用自己团队的故障时间戳实测】，而 SLA 承诺看的是尾部而不是均值。**自动化在 RTO 上的收益几乎全部来自压掉决策段**，把执行从 20 分钟压到 2 分钟只值 18 分钟，把决策从 25 分钟压到 0 却值 25 分钟。反过来，**因为自动切换的去风险手段（多信号交叉确认、切回成本评估）本身也是延迟**，所以「防误切」与「压 RTO」是一对直接对抗的目标：误切的代价可能大于不切（在故障其实只影响次要链路时把全量流量切走），所以高可用性目标不能只靠「更快的自动切换」达成，还需要**分级切流**（先切一部分流量做验证，再全量）。

还有一条容易漏掉的执行段下限：**DNS 切流的 RTO 下限是一个 TTL 量级**。因为递归解析器与客户端会按 TTL 缓存记录，且部分客户端与运行时不遵守 TTL，所以「TTL = 60 s」意味着乐观情况 1 分钟量级即可生效、而尾部要按最不听话的那部分客户端算【推算，基于 TTL 的缓存语义；尾部倍数取决于客户端实现，需实测】。可自行核验：把你的域名 TTL 改小一次，观察核心依赖的解析器实际什么时候刷新。

**公开证据【公开】**：Netflix 早在 2013 年就公开描述过其 AWS 上的多区域主主（active-active）架构与区域级故障演练（[Netflix Tech Blog, Active-Active for Multi-Regional Resiliency, 2013]），其公开的做法里「区域疏散」本身是一条被反复演练的常规操作而不是应急预案；AWS 于 2021 年推出 Fault Injection Simulator（[AWS 官方公告, 2021]），把「注入故障验证切换链路」变成可托管的能力。这两条都指向同一件事：**RTO 是被测出来的，不是被设计出来的**——没有演练数据的 RTO 只是一个愿望。

**失效条件**：当失败模式是**脑裂（网络分区）**而不是节点宕机时，「快速自动切换」会把系统推向双写。此时正确的动作是让自动决策**采取保守侧**（宁可停写也不双写），代价是 RTO 变长——这条约束优先于 RTO 目标。

#### 7.3.3 故障域的形状：为什么「跨 AZ」不等于容灾

**机制是什么**：容灾的有效性等于**副本与主站之间共享的那部分依赖有多少**。物理位置隔开只是必要条件；真正的故障域是「共享控制面、共享配置下发路径、共享身份与密钥体系、共享专线汇聚点、共享 DNS」这些东西圈出来的范围。

**各候选的实现差异**：

| 档位 | 副本与主站共享什么 | 能抗住的故障 | 抗不住的故障 |
| --- | --- | --- | --- |
| 同 Region 多 AZ | 同一 Region 的控制面、IAM、配额、部分网络组件 | 单机、单机架、单 AZ 的物理故障 | Region 级控制面故障、配置误下发、配额耗尽 |
| 同城双活（双机房） | 同城专线、同一套调度与配置中心 | 单机房失效 | 城市级事件、专线中断、配置全局误改 |
| 两地三中心 | 同一云账号与主账号体系 | 单机房失效；异地中心保数据 | 主账号 / 配置中心的全局故障 |
| 异地多活 | 少量（理想情况只剩身份与发布系统） | 城市级故障 | 全局发布导致的同版本缺陷、密钥体系故障 |
| 跨云 / 跨账号 | 几乎不共享（代价是运维分裂） | 云厂商级故障 | 自研组件自身缺陷 |

**由此必然导出的性质**：因为**控制面故障的分辨率往往粗于可用区**，所以「主备跨两个 AZ」这类架构在控制面级故障下面不是两个故障域而是一个；此时 RTO 不再由你的切换机制决定，而由**云厂商的修复时间**决定——你的自动化能力在这段时间里完全失效。所以选型时必须先把**共享依赖清单**画出来（控制面、IAM、密钥、DNS、配置中心、专线汇聚点、发布系统），再判断「副本是否躲开了这些依赖」；躲不开的档位，其真实可用性上限由供应商决定，而不是由你的架构决定。

**公开证据【公开】**：AWS 在 2020 年 11 月与 2021 年 12 月各发布过 us-east-1 区域事件的公开总结（[AWS 事件总结, 2020 / 2021]），两次事件的影响范围都超出单个可用区，恢复时间以小时计——它们共同说明**「多 AZ」这一层的冗余不构成对控制面级故障的防护**。国标侧的对应物是 GB/T 20988-2007《信息安全技术信息系统灾难恢复规范》，它用能力等级描述灾难恢复要求，等级越高对「数据零丢失」与「远程集群」的要求越强【公开，GB/T 20988-2007；各级的具体措辞请以标准原文为准】——也就是说，**标准的分级依据是「你做到了什么能力」，而打分表的 ★ 是「别人认为你好不好」，两者不是一回事**。

**失效条件**：把容灾推到跨云或跨账号能扛住供应商级故障，但代价是运维体系分裂（两套 IAM、两套网络、两套发布），需要有人长期维护等价的运行环境。当团队没有这个运维能力时，跨云的「理论容灾能力」会在第一次真实故障中因不熟悉而失效——**容灾能力受限于你最不熟练的那一侧**。

#### 7.3.4 备份与容灾防的不是同一类故障

**机制是什么**：备份保留的是**时间点**（能回到过去），容灾保留的是**近实时的可用镜像**（能就地接管）。这两者在故障模型上互补，在数据形态上互相伤害：镜像会**同步传播逻辑损坏**。

**各候选的实现差异**：

| 机制 | 能恢复的故障 | 恢复方向 | 对逻辑损坏 |
| --- | --- | --- | --- |
| 快照 / 全量备份 | 误删、误改、勒索加密、程序缺陷 | 回到过去某个时间点 | 有效（前提是副本未被污染） |
| PITR（基础备份 + 日志归档） | 同上，且精度到时间点 | 回到任意时间点 | 有效，覆盖到最后一个已归档日志 |
| CDC / 异步复制 | 站点故障 | 就地接管（近似最新） | 无效，损坏会随复制到达远端 |
| 同步复制 / 多活 | 站点故障，且 RPO=0 | 就地接管（最新） | 无效且传播更快 |
| 不可变备份（WORM） | 误删、勒索、内部人删库 | 回到过去 | 有效（因为不可改写） |

**由此必然导出的性质**：因为多活/同步复制把每一次写都投递到远端，所以**一次 `DROP TABLE` 或一次批量错误更新会在毫秒到秒级同时出现在所有副本上**——RPO=0 的架构在「逻辑损坏」这一类故障面前的 RPO 其实是「零防护」，它的可用性越高、传播越快。因此正确的问题不是「备份和容灾二选一」，而是「**把两类机制的恢复窗口分开设计**」：镜像负责分钟级接管，时间点副本负责「回到 1 小时前」，且**时间点副本必须是不可改写且与生产凭据隔离的**，否则勒索软件在拿到生产凭据的同时也拿到了备份的删除权。

**公开证据【公开】**：Amazon S3 于 2018 年推出 Object Lock，提供 WORM（一次写入多次读取）语义与保留期强制（[AWS 官方公告, 2018]）；PostgreSQL 官方文档描述的 PITR 依赖「基础备份 + WAL 归档 + 恢复目标」三件套（[PostgreSQL 官方文档, 持续归档与时间点恢复]；具体操作步骤以当期版本文档为准）。可自行核验这条判据：在你的备份链路上问三个问题——**谁能删它**（是否与生产共用凭据）、**保留多久**（是否覆盖「发现得最慢的那类损坏」）、**恢复一次要多久**（没测过就等于不知道）。

**失效条件**：当数据量达到 PB 级、且要求「回到任意时间点」时，完整的热备 + 长时间点保留的成本会显著高于业务价值；此时可行的折中是**分层**：核心表逐日全量 + 持续日志（保留 7–30 天【经验，量级取自常见实践；保留期应由「你能多快发现一次错误批量更新」决定，成本随保留期线性增长，见 §7.4】）、一般表按周、日志与埋点类只保留聚合结果。分层的依据是**「这张表被错误批量更新的可能性与修复难度」**，而不是它的容量。

**四条机制维度的对照速查**（每行给出机制依据，而不是打分）：

| 档位 / 开关 | 副本与主站共享的依赖 | RPO 达成方式 | RTO 的瓶颈段 | 时间点回滚 | 由机制导出的最短结论 |
| --- | --- | --- | --- | --- | --- |
| 冷备 | 几乎不共享（只有备份介质） | 备份周期（小时–天） | 环境重建（人力主导） | 有（最完整） | 停机预算小时级以上时它是对的，不是「最低档」 |
| 温备 | 备份介质 + 部分云内依赖 | 日志投递 + 周期快照 | 扩容与预热未验证 | 有 | 便宜且够用，前提是扩容上限被测过 |
| 热备（同 Region） | 同一 Region 控制面 / IAM / 配额 | 半同步或同步复制 | 决策段（若需人工确认） | 需另建 | 抗得住单机房，抗不住控制面级故障 |
| 同城双活 | 同城专线、统一调度与配置 | 同步 / quorum 复制（付一个同城 RTT） | 应用无状态化程度 | 需另建 | 写延迟代价在毫秒级，是性价比最高的一档 |
| 两地三中心 | 同一账号体系与配置下发路径 | 同城同步 + 异地异步 | 跨城切换的决策与数据追齐 | 需另建 | 能扛单机房，扛不住「整城失联后继续可写」 |
| 异地多活 | 身份 / 发布 / 密钥（理想状态） | 单元内同步 + 单元间异步 | 路由与数据归属的正确性 | 需另建 | 唯一能装下 5.26 分钟年度预算的常见形态 |
| 单元化（开关） | 路由层与全局字典 | 不改变 RPO，缩小代价范围 | 跨界请求的处理策略 | 无关 | 让「强一致」与「跨城」不再互斥的前提 |
| 不可变备份（开关） | 独立存储与独立凭据 | 不适用（是时间点） | 取回与恢复演练 | 有（且不可删改） | 唯一能对抗「逻辑损坏」的机制 |

> 这张表替代打分表的做法：每一行都能回溯到 §7.3 的某一条机制，而每一格都不给分数——因为分数在跨场景比较时会失效（§7.1 已论证），而机制不会。

### 7.4 成本结构对比（不是价格表，是成本函数）

容灾没有统一单价：同一套架构在自建与托管、3 副本与 5 副本、开与不开跨 Region 复制之间，成本差一个量级。可比较的是**成本函数的形式**：

```
容灾总成本 ≈ 备用资源持有成本（就绪度 × 主集群成本）
           + 复制与流量成本（写入速率 × 跨站单价）
           + 时间点保留成本（数据量 × 副本数 × 保留期）
           + 常态运维成本（组件数、技能、值班）
           + 演练成本（参与人时 × 频次 + 业务影响窗口）
           + 切换期权成本（预留容量 + 未使用的对等环境维护）
```

**各档位的主导项与隐性成本**：

| 档位 | 成本主导项 | 隐性成本（最容易漏算） |
| --- | --- | --- |
| 冷备 | 时间点保留成本（容量 × 保留期） | **恢复时长**：无自动化时，重建环境的人力在故障当下才被计入 |
| 温备 | 数据层全量常驻 + 扩容弹性 | 扩容上限未验证（预留配额、镜像预热、依赖启动顺序） |
| 热备 | 全量资源常驻（接近 100% 主集群） | 双份配置漂移：备用环境半年不被使用后与生产不一致 |
| 同城双活 | 双机房资源 + 同城专线 | 应用必须无状态化 / 会话外置，改造工作量落在业务代码 |
| 两地三中心 | 三中心资源 + 长距专线 | 跨城复制的延迟预算与多数派布局（见 §7.3.1 / §7.3.3） |
| 异地多活 | 2 倍以上资源（但可摊到容量）+ 改造工程量 | 单元化改造与数据归属规则，是**项目级**而不是运维级投入 |
| 单元化 | 路由层 + 数据归属体系 | 一次跨单元请求的处理策略（拒绝、异步、还是走窄链路） |

**注意两类成本的增长方式根本不同**：成本函数的前四项各有自己的驱动变量——备用资源持有成本随**主集群规模**（就绪度只是一个倍数）、复制与流量成本随**写入速率**、时间点保留成本随**数据量 × 保留期**，这三项随业务量增长，可预算、可容量规划；常态运维成本则随**组件数与值班规模**增长，是固定支出、与业务量无关。而演练与切换期权这两项与业务量无关——前者按**参与人时 × 频次**增长，后者按**常驻的预留容量与对等环境维护**计费——且只在出事时才暴露。**因为演练成本随「参与人数 × 频次」线性增长，而它换来的收益（把宣称 RTO 变成实测 RTO）恰恰是不可省略的**，所以容灾预算里必须单列一条演练线，否则它会在第一次业务压力下被砍掉，然后容灾就退化成一份文档。

**【推算】时间点保留成本的量级**：设需保留 10 TB 数据。按对象存储标准层 $0.023/GB-月【公开，AWS S3 定价页，2024 口径；价格会调整，请以当期定价为准】推算，年成本 ≈ 10 × 1,024 GB × $0.023 × 12 ≈ $2.8k；按 Glacier Instant Retrieval 档（$0.004/GB-月）推算约 $0.5k/年。**结论不是「用便宜档位」，而是「保留期的成本决定了你能承诺多长的回溯窗口」**——保留 30 天与保留 1 年之间是 12 倍存储差，而能发现「3 个月前被错误覆盖的口径」这个能力，只有长保留才买得到。

**【推算】跨 Region 复制的带宽成本**：设某 OLTP 集群的日志投递速率约 20 MB/s【经验，中等规模交易库的量级，需按自己的 WAL/binlog 速率实测】，则日流量 ≈ 20 MB/s × 86,400 s ≈ 1.7 TB/天。以云厂商跨区域数据传出常见的 $0.02/GB 量级【经验，单价随区域对与厂商差异较大】推算，年成本约 1.7 × 1,024 × 365 × $0.02 ≈ $1.3 万量级。这笔钱买到的不是「更低的 RPO」，而是「异地那份副本是新的」——**如果你的 RPO 目标本来就允许分钟级，那用低成本的对象复制通道就够，不需要为每一笔事务付跨站带宽**。

**【推算】演练成本的量级**：以 20 人参与、每次 8 小时、单位人时成本 ¥200【经验，一线城市资深工程师全成本 ÷ 年有效工时 2000 小时的量级，与本书 Ch14 口径一致】计，一次真实切换演练的人力成本 ≈ 20 × 8 × 200 = ¥3.2 万/次；按季度一次计约 ¥12.8 万/年。若再把「把生产流量切走再切回」的业务影响计入，这个数字还要乘以业务小时的损失。**这笔钱是容灾里唯一「看得见收益」的支出**（它直接决定实测指标是否存在），也是最容易被砍的——判断方法是问：上一次演练是什么时候，当时的实测 RPO / RTO 是多少。

**钱应该花在哪一段**：把上面的成本函数按「压哪一段」重新分组，会得到一条实用的分配规则——**压 RPO（更小的丢失窗口）的钱主要花在复制通道与写路径延迟上，压 RTO（更快的恢复）的钱主要花在常驻资源、自动化与演练上**。两者的边际成本曲线形状不同：复制通道的成本随**写入速率**增长（可按容量规划预算），自动化与演练的成本随**组件数与参与人数**增长（是固定支出，与业务量无关）。【经验，量级判断】因此当团队说「容灾太贵」时，值得先问一句：贵的是哪一段？如果是复制带宽，那是业务量的问题（可摊薄）；如果是自动化与值班，那是组织能力的问题（要靠减少组件数而不是加钱解决）。最常见的浪费是**为已经达标的 RPO 继续采购通道，却让 RTO 的决策段一直挂在人身上**——前者花钱买不到业务感知的变化，后者不花钱则承诺永远只是愿望。

### 7.5 决策树（每个分支都要有阈值依据）

```
第 0 层（对所有档位都生效，先问）：你要防的故障，最粗的那一类是什么？
│   （把「共享依赖清单」画出来：控制面 / IAM / DNS / 配置中心 / 专线汇聚点 / 发布系统）
└─ 依据清单画故障域边界 → 决定候选集合（§7.3.3）；边界画不对，下面每一步都白做

第 1 层：可用性目标换算成停机预算后，最大可接受停机是多少？
├─ ≥ 8.76 小时/年（99.9% 以下）────► 冷备 / 温备 + 自动化恢复
├─ 52.6 分钟/年 量级（99.99%）─────► 热备（同 Region 内）+ 自动切换
└─ 5.26 分钟/年 量级（99.999%）────► 必须跨 Region 且切换全自动 + 常态化演练
                                   （人工确认与 99.999% 不能同时承诺）

第 2 层：RPO 要求是什么？
├─ 天级 ─────────────────────────► 全量 + 增量备份即可（平均 RPO ≈ 增量周期 / 2）
├─ 小时级 ───────────────────────► 每小时级增量 / 日志归档（Log Shipping）+ 可脚本化的重建
├─ 分钟级 ───────────────────────► 日志连续投递（binlog / WAL）或托管对象复制
└─ 秒级 / = 0
    ├─ 你的写入能否收敛进单元（同一请求只落一个单元）？
    │   ├─ 能 ──► 单元内同步复制 + 单元间异步（异地多活）
    │   └─ 不能 ─► 只能付跨站 RTT：同城（< 数十 km）可行；跨城需先确认
    │               写 P99 预算是否大于一个跨站 RTT（§7.3.1）
    └─ 用的是 quorum 复制（Raft / Paxos 类）吗？
        ├─ 是，且要求「某城市整体失联后仍可写」──► 多数派必须跨越城市边界
        │    （n = 5、每城 ≤ 2 副本，如三地五中心）
        └─ 否 / 只要求扛单机房 ─────────────► 同城多数派 + 异地异步副本（两地三中心）

第 3 层：需要时间点回滚能力吗？
├─ 是 ──► 与上面并行建设时间点副本，且必须不可改写、凭据隔离（§7.3.4）
└─ 否 ──► 仍建议保留最低限度的不可变副本（勒索与误删不看你的业务类型）

第 4 层：谁是切换决策者？
├─ 能做到多信号交叉确认 + 自动执行 ─► 自动切换；用分级切流防误切
└─ 只能人工确认 ────────────────────► RTO 的下限 = 值班响应 + 会签流程
                                     不要对外承诺秒级 RTO
```

**阈值依据**（每条粗体即树上的节点，与树双向一一对应）：

- **第 0 层 · 故障域清单**：不设数值阈值——它是前置筛选而不是判断题，所以这里给的是判定方法而不是数：按 §7.3.3 的机制（容灾有效性 = 副本与主站还剩多少共享依赖），先把共享依赖清单（控制面 / IAM / 密钥 / DNS / 配置中心 / 专线汇聚点 / 发布系统）写出来，再让候选集合由这份清单决定。
- **第 1 层 · 8.76 小时 / 52.6 分钟 / 5.26 分钟**：由可用性定义换算，公式为 `年停机 = 525,600 分钟 × (1 − A)`【推算】。这三个数字是**预算**不是能力：99.99% 的 52.6 分钟要求「探测 + 决策 + 执行」三段合计不超过 52.6 分钟，而其中决策段在人参与的形态下就容易吃掉一半【经验，由 §7.3.2 的段构成推出】。
- **第 1 层 · 99.999% 必须跨 Region**：单个 Region 的可用性上限由供应商与其共享依赖决定（见 §7.3.3 的公开事件证据：区域级事件的恢复时间以小时计）。一年 5.26 分钟的预算装不下任何一次小时级事件，所以档位必须上移到「不依赖单一 Region 控制面」的形态。
- **第 1 层 · 常态化演练**：不设固定频次。判定方法是**把上一次演练的实测 RTO 与承诺值相减**，差值超过一个数量级的档位，说明当前承诺没有证据支撑，应先补演练再谈架构升级。
- **第 2 层 · 天级**：由主文件 §2.2 的公式 `平均 RPO ≈ 增量周期 / 2` 推算：按日计增量时，平均丢失约半天【推算，代入主文件 §2.2 公式】。这一档不需要把等待放进写路径，因为「备份 + 恢复」通道的成本只随容量与保留期增长（§7.4），不引入常驻第二套环境。
- **第 2 层 · 小时级**：同一公式，按小时计增量或日志归档时，平均丢失约半小时【推算，代入主文件 §2.2 公式】。它与分钟级的交界不在「备用集群多大」，而在**通道是否常开**：分钟级要求日志连续投递（通道常开、断流即告警），小时级只要求归档不丢、且能按脚本重建。
- **第 2 层 · 分钟级 / 秒级 = 0（含「写入能否收敛进单元」这一分支）**：来自 §7.3.1 的公开证据——S3 RTC 这类最强承诺的复制通道，公开承诺也只是分钟级，所以分钟级目标不需要把等待放进写路径；而秒级目标在物理上要求等一个跨站 RTT，二者不能用同一套通道实现。至于「能不能收敛进单元」，判据不是阈值而是你的数据模型：一次业务请求若能只落一个单元完成，跨站同步就只覆盖跨界的那一小部分数据（§7.3.1 失效条件）；若存在全局唯一热点（全局递增 ID、全局库存池、全站计数），按定义就收敛不了，此时只能改数据模型。
- **第 2 层 · 「同城（< 数十 km）可行」**：用 §7.3.1 的同一个传播公式换算：50 km 的纯传播往返 ≈ 2 × 5 × 10⁴ m ÷ 2 × 10⁸ m/s ≈ 0.5 ms【推算，仅含光学传播，不含交换设备与路由绕行】——与一次本地 fsync 同量级，因此同城同步的延迟代价会被应用自身的写开销掩盖；而 1,200 km 跨城的纯传播往返约 12 ms、工程实测 25–35 ms 量级【经验，公网与专线绕行差异较大】。所以「数十 km」不是一条地理红线，而是「跨站 RTT 与本地写开销同量级」的边界；界线附近的取值应由你自己的拨测决定。
- **第 2 层 · 「跨城需先确认写 P99 预算 > 一个跨站 RTT」**：取自 §7.3.1 的推算。若你的写 P99 预算小于 25–35 ms 量级，跨城同步在物理上不可行，此时的选择只有「改选址」「改数据模型（去全局热点）」或「把 RPO 目标降到分钟级」。
- **第 2 层 · quorum 布局**：以 quorum 复制（Raft / Paxos 类，多数派 = ⌊n/2⌋ + 1）为例，n = 3 可容忍 1 个副本故障、n = 5 可容忍 2 个【推算，多数派定义】。要让「某个城市整体失联后仍可写」，该城市持有的副本数必须 ≤ n − 多数派阈值（n = 5 时每个城市最多 2 个副本）；这解释了为什么「同城双活 + 异地一中心」能扛单机房故障、却扛不住整城故障后继续可写，而「三地五中心」这类布局正是为了让多数派跨越城市边界。注意：**单主 + 指定从库 ack 的行式复制（如 MySQL 半同步）没有多数派概念**——它保证的是「日志已离开主库」，切换后谁是最新主需要另外的仲裁机制，不能用同一套推导。
- **第 3 层 · 时间点回滚**：依据是 §7.3.4 的失效条件——保留期应由「发现得最慢的那类损坏」决定，而不是由容量决定（容量只影响成本，见 §7.4）。所以这一层即使答「否」，也要保留最低限度的不可变副本：逻辑损坏不区分业务类型。
- **第 4 层 · 「多信号交叉确认 + 自动执行」与「值班响应 + 会签」**：不设固定数值，判定方法是**拆最近一次真实故障（或演练）的时间戳**：告警到达值班手机的时刻 − 故障发生时刻 = 探测延迟；第一个有权限的人按下切换的时刻 − 告警时刻 = 决策延迟。这两个差值的实测值，就是「值班响应 + 会签」这条 RTO 下限【经验，取值随组织形态与值班安排差异极大，只能用自家记录测】。若决策延迟远大于探测延迟，说明瓶颈不在探测，加快探测没有收益（见 §7.3.2）。

**这棵树刻意不覆盖的分支**（以及为什么）：

- **「要不要上跨云」**：跨云不是技术判据而是**组织判据**——它的收益（规避厂商级故障）只有在「两侧运维能力等效」时才可实现，而这要求有同一批人能按同一份 Runbook 操作两套环境。判定方法：看上一次跨云侧的变更是否由常规值班完成，而不是靠少数专家支援。做不到就先把单云内的故障域边界画对，再谈跨云。
- **「RPO 是不是必须精确到 0」**：RPO 的语义是「**可容忍**的丢失量」，不是「必须为零」。把 RPO 写成 0 常常是词汇上的懒惰。判定方法只有一句话：问业务方「如果丢掉最后 30 秒的成单，需要人工补录还是完全不可接受」——答「可以人工补」的场景，为它付跨站同步的延迟代价是买错了东西。
- **「双活里能不能双写」**：双写是**脑裂的成因**，不是高可用的手段（见 §7.3.2 失效条件）。判定方法：问「两个站点同时接受同一实体的写入时，冲突由谁裁决、按什么规则裁决」——答不出这条规则，就不能双写，只能按数据归属分片写入。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 为什么此时不选备选（机制层面） |
| --- | --- | --- | --- |
| T+1 离线分析 / 训练管线（可停数小时） | 冷备 + 对象存储跨区域复制 | 温备 | 常驻资源买不到任何业务价值，停机预算本来就够 |
| 内部系统 / 办公后台（RPO / RTO 均为小时级） | 温备（同 Region）+ 日志归档（Log Shipping） | 冷备（纯周期备份） | 冷备的 RPO = 距上一次备份的时长（平均为增量周期 / 2，主文件 §2.2），RTO 由人力重建环境主导；两项都正好压在小时级的边界上，没留余量给「晚一小时才发现故障」这种常态 |
| 一般在线业务（允许分钟级中断） | 温备（同 Region）+ 自动切换 | 热备（成本更高） | 就绪度换取的是 RTO，RTO 不是瓶颈时是纯支出 |
| 支付 / 交易核心（RPO=0，停机预算分钟级） | 同城双活（quorum 复制）+ 异地数据副本 + 不可变备份 | 三地五中心 | 三地五中心要让多数派跨越城市边界，每次提交都要多等一个跨城 RTT（§7.3.1），而它多买到的只是「整城失联后仍可写」这一类故障；停机预算在分钟级、故障域画到机房与单城时，同城 quorum + 异地副本已经够用，先付这份延迟与三中心固定成本是买错了东西 |
| 全局性秒杀 / 大促（峰值极短且全局） | 提前扩容 + 单元化收敛 + 演练 | 纯跨站同步 | 全局热点下跨站同步的代价集中在少数行上，会形成排队 |
| 超大规模、可分区业务 | 异地多活 + 单元化 | 两地三中心 | 两地三中心是「一个写入点 + 一个备用中心」，异地中心平时不承流量：既摊不掉超大规模的容量与就近接入需求，也拿不回那部分常驻资源的成本；要把它变成产能，做的就已经是异地多活了 |
| 需要「回到 1 小时前」 | PITR / 快照 + 不可变保留 | 延迟副本（滞后镜像） | 延迟副本给的是一个固定滞后、且不断前移的窗口：窗口内的错误写入已被回放进来，也无法选任意时间点；当发现延迟超过滞后量时，它已经被污染（§7.3.4） |
| 有监管留存要求 | 不可变备份 + WORM 保留期 | 普通快照 | 普通快照可被同凭据删除，不构成留存证据 |
| 跨云 / 规避厂商绑定 | 跨账号 + 跨云副本（数据面） | 单云多 Region | 单云多 Region 的各 Region 仍共享同一套控制面、IAM、账号体系与配额（§7.3.3），厂商级或账号级错误会同时命中所有 Region——它买到的是区域内可用性，规避不了厂商绑定 |

**常见组合**（每条注明职责边界与运维代价）：

- **容灾 + 单元化**：单元化让容灾粒度更细——故障域从「Region」缩到「单元」，一次故障只影响一个单元的用户。边界是：**单元化要求业务可分区**（哪些数据必须全局、哪些能本地化），这本账必须先算清。运维代价是路由层成为新的关键路径，且「跨界数据」需要一条明确的窄链路与降级策略（拒绝、异步还是走主单元）。
- **容灾 + 异地多活**：异地多活是容灾的高级形态——它把「备用资源」变成「产能」，所以备用资源不再是纯成本。边界是：多活只在你**能承受跨 Region 的一致性代价**时成立（否则退化成「两个区域互相写同一份数据」，那是脑裂而不是多活）。运维代价是发布、配置、配额、密钥四件事都必须多 Region 一致地做，任何一次全局变更都可能同时打穿两个 Region。
- **容灾 + 混沌工程**：混沌工程验证容灾流程——它是把「宣称 RTO」变成「实测 RTO」的唯一手段。边界是：混沌实验必须**先有稳定的观测与止血能力**，否则注入故障等于制造故障。运维代价是每次实验都要有明确的爆炸半径上限与值班兜底。
- **容灾 + 大促保障**：大促前的容灾演练是「在峰值下验证切换」的场合——峰值下的切换失败率远高于日常（连接数、锁、队列深度都不同）。边界是演练必须包含**回切**（切走再切回），只切不回的演练会掩盖回切路径的问题。运维代价是大促窗口内不能做架构变更，只能做已验证参数的调整。
- **备份 + 容灾（并行而非二选一）**：备份负责「回到过去」（误删、勒索、程序缺陷），容灾负责「就地接管」（站点故障）。边界是两者必须**凭据隔离 + 存储隔离**，否则一次生产凭据泄漏会同时毁掉两者。运维代价是两套恢复流程都要测——只测其中一套，等于没测。

组合的原则只有一条：**每加一件，都要说清它挡的是哪一类故障，以及它挂掉时谁来兜底**。单元化挂了，兜底是「回落到主单元处理跨界请求」；异地多活的复制链路挂了，兜底是「把该 Region 切成只读」；不可变备份挂了，兜底是「承认当前没有逻辑损坏的恢复能力并升级告警」。

**一个可承诺的容灾方案至少要回答五个问题**（无论档位高低，缺一项就会出现一种典型症状）：

| 问题 | 答不出来的症状 | 对应本节 |
| --- | --- | --- |
| 副本与主站之间**还剩哪些共享依赖** | 故障时两侧一起挂，RTO 变成供应商的修复时间 | §7.3.3 |
| 每次写入**在哪里等远端确认** | 宣称 RPO=0 但实测有窗口，或写延迟在多活上线后莫名上升 | §7.3.1 |
| **谁**有权决定切换、需要几次确认 | RTO 呈现长尾（均值 30 分钟量级、尾部数小时）【经验，量级依据同 §7.3.2】，SLO 无法按均值承诺 | §7.3.2 |
| 逻辑损坏（误删 / 勒索）时**回到哪个时间点** | 镜像把损坏复制到所有副本，事后无路可退 | §7.3.4 |
| 上次真实切换的**实测** RPO / RTO 是多少 | 承诺与实测差一个数量级，且故障时才发现依赖缺失 | §7.4 / §7.5 |

这五个问题同时是**评审清单**：评审一套容灾方案时，与其争论「该选几级」，不如逐条要求对方给出答案与证据（监控数据、演练记录、共享依赖清单）。说不出证据的那一条，就是这套方案真实的风险位置。

### 7.7 选错的代价与迁移成本

**反模式：把「跨 AZ」当容灾** —— 症状：主备放在同一 Region 的两个可用区，对外宣称「抗机房故障」→ 后果：控制面级或配额级故障时两侧一起不可用，RTO 从「我的切换速度」退化为「供应商的修复时间」（见 §7.3.3 的公开事件证据）→ 正确的做法：先列共享依赖清单，把副本放到不与主站共享控制面、IAM、DNS 与配置下发的边界之外。

**反模式：灾备只备份不演练** —— 症状：灾备中心长期闲置，Runbook 长期没人打开 → 后果：故障时按未验证的路径操作，实测 RPO / RTO 与承诺差一个数量级，且切换途中才会发现依赖缺失（DNS 记录、证书、镜像、配额）→ 正确的做法：把**真实切换 + 回切**练成常规操作，并记录每次的实测指标作为承诺的证据。

**反模式：把备份当容灾用（或反之）** —— 症状：只有每日全量备份，却承诺「RTO 30 分钟」；或多活建设完备，却没有不可变时间点副本 → 后果：前者的恢复要小时级，后者在一次误删后无路可退（镜像已把损坏复制到所有副本）→ 正确的做法：两类机制并行建设，并分别测恢复时长。

**反模式：宣称 RPO=0 但从不测量复制延迟** —— 症状：架构上是同步复制，但没人监控复制链路是否降级为异步（很多实现会在从库超时后自动降级）→ 后果：切换后方才发现最后一段时间的数据缺失，而且**没有任何监控曾经报过警** → 正确的做法：把复制延迟与「当前生效的复制模式」当作一等 SLO 指标，并在切换流程里加入两端对账（行数 / 校验和 / 关键业务量）这一步。

| 从 → 到 | 数据迁移 | 架构改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 冷备 → 温备 | 无（复制通道升级） | 应用需能「按需启动」 | 引入弹性与预热流程 | 恢复流程从「重建」变「扩容」 | 周–月 |
| 温备 → 热备 | 无 | 备用环境全量常驻，配置需一致 | 双份环境的一致性巡检 | 自动切换的判定与防误切 | 月 |
| 热备 → 同城双活 | 无（复制语义升级为同步 / quorum） | **应用需无状态化 + 会话外置**（最大项） | 双机房统一的发布与拨测 | 写延迟预算的重算（加了一个 RTT） | 月–季 |
| 同城双活 → 异地多活 | 需要「数据归属」重划（最大项） | **单元化改造 + 路由层** | 多 Region 一致的发布 / 配额 / 密钥 | 跨界请求的处理策略 | 季–年 |
| 任意 → 加入不可变备份 | 存量需重新归档 | 无 | 独立的存储与凭据体系 + 保留期策略 | 恢复演练（回到指定时间点） | 周 |
| DNS 切流 → 就近接入 / 单元路由 | 无 | 接入层重写 | GSLB / 路由服务上线 | 路由规则的灰度与验证 | 月 |

**迁移的时机约束**：容灾档位的迁移**不能在业务高峰期做**，因为迁移期间新旧两套机制必须同时在线（双写或影子流量），而双写正是「逻辑损坏同步传播」（§7.3.4）最危险的时刻。可操作的节奏是：先只读切换（新路径与旧路径比对，差异挂账）→ 再写路径切换（旧路径降级为校验）→ 最后下线旧路径，每段之间留一次完整的演练周期。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 停机预算 ≥ 小时级 | 冷备 / 温备 + 自动化恢复 + 不可变备份 | 就绪度买的是 RTO，RTO 不是瓶颈时是纯支出 |
| 停机预算 52.6 分钟量级 | 同 Region 热备 + 自动切换 + 分级切流 | 决策段的方差是 RTO 的主要来源，先把决策自动化 |
| 停机预算 5.26 分钟量级 | 跨 Region 多活 + 单元化 + 常态化演练 | 单 Region 控制面故障的恢复时间以小时计，装不下这个预算 |
| 要求 RPO = 0 且能分区 | 单元内同步 + 单元间异步 | 跨站同步只覆盖跨界数据，物理下限的代价被摊薄 |
| 要求 RPO = 0 且不可分区 | 先改数据模型（去全局热点），再谈架构 | 全局热点下跨站 RTT 必然集中在少数行上 |
| RPO 只要分钟级 | 日志连续投递 / 托管对象复制 | 托管复制通道的公开承诺就是分钟级，不必为每笔事务付跨站延迟 |
| 存在误删 / 勒索风险 | 不可变（WORM）时间点副本 + 凭据隔离 | 镜像会同步传播逻辑损坏，回退能力只能靠时间点副本 |
| 团队没有 7×24 值班 | 不要承诺秒级 RTO；用分级切流 + 降级策略换时间 | 人工决策段的方差决定尾部，承诺无法被组织能力兑现 |

回到本章 6 条判据里权重最高的两条：**故障域边界**决定了候选集合（边界画错的架构，其真实可用性由供应商决定），**RPO 的达成机制**决定了同族内部的选择（要不要把等待放进写路径，代价是一个跨站 RTT 的物理下限）。这两条回答完，剩下的成本、复杂度、生态才有讨论价值——顺序反了，讨论就永远停在「我们该做多活吗」这种没有前提的偏好里。

再强调一次本章与打分表最大的方法论差别：打分表给的是**结论**（「异地多活 ★★★★★」），本章给的是**推导**（异地多活为什么在「可分区 + 停机预算秒级」这两个前提下不可替代，以及它在「不可分区」时为什么会退化成脑裂源）。结论会随产品与年份过时，推导不会。

> 本节小结：这些候选之间唯一真正起决定作用的差异是**「副本与主站之间还剩多少共享依赖，以及为了让远端确认付出了多少延迟」**。前者决定你能挡住哪一类故障（§7.3.3），后者决定你在写路径上要付一个什么量级的物理代价（§7.3.1）——其余维度（成本、复杂度、产品成熟度）都是这两条的下游结果。
