### 7.1 阿里"**RPO 0 RTO 30s 双 11**"6+ 年（2018-2024）

**背景（Why）**

- **RPO 0**——**零数据丢失**
- **RTO < 30s**——**秒级切流**
- **双 11 7x**——**0 容忍**

**触发点（What）**

2018 年阿里启动**RPO 0 RTO 30s 双 11**（[阿里 2018]），目标：
- **RPO 0**
- **RTO < 30s**
- **0 事故**

**详细做法（How）**

阿里 RPO 0 RTO 30s 的**5 大核心组件**：

1. **异地多活（核心创新）**
   - 关键设计：**3 地 5 中心**
   - 关键能力：**异地容灾**
   - 关键数字：**3 地 5 中心**

2. **数据强一致（核心）**
   - 关键设计：**DLedger + Raft + 3 副本**
   - 关键能力：**RPO 0**
   - 关键数字：**RPO 0**

3. **自动切流（核心）**
   - 关键设计：**健康检查 + 自动切流 + 5s 切**
   - 关键能力：**秒级切流**
   - 关键数字：**5s 切**

4. **演练验证（核心）**
   - 关键设计：**真实演练 + Chaos**
   - 关键能力：**演练验证**
   - 关键数字：**100+ 演练**

5. **多活切流（核心创新）**
   - 关键设计：**多活切流 + 灰度**
   - 关键能力：**灰度切流**
   - 关键数字：**灰度 100%**

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / Netflix / 美团）印证：**容灾不是「**主备机房**」，是「**多 Region + DLedger + 自动切流 + Chaos + 演练**」**5 件套**。
> - 关键时间线：阿里 6+ 年 / 字节 5+ 年 / Netflix 5+ 年 / 美团 5+ 年 —— **容灾是 5+ 年长期工程**。
> - 选型第一原则：「**3 Region + DLedger 起步**」（**最简单**）——**1 个业务** → 「**自动切流 + 演练**」（**必须**）→ 「**Chaos 验证**」（**生产**）→ 「**4 Region / AI 化**」（**AI 时代**）。
> - 99% 的失败来自「**单 Region 故障 + 演练不真实 + 切流慢**」——必须有 **多 Region + 真实演练 + 5s 自动切流**。
