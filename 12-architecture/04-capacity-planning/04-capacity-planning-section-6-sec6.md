### 6.1 阿里双 11 容量规划 10+ 年（2013-2024）

**背景（Why）**

阿里 2013 年面临**双 11**容量爆炸：
- **2013 1.7 亿订单**——**MySQL 单库撑不住**
- **峰值是平时 10 倍**——**资源浪费大**
- **2013 双 11 当天 1 次卡顿**——**损失千万级**

**触发点（What）**

2013 年**阿里启动容量规划项目**（[阿里 2023 双 11 复盘]）——**目标**：「**3 个月备战 + 0 故障**」。

**详细做法（How）**

阿里双 11 容量规划的**5 大核心组件**：

1. **3 个月前：业务预测 + 容量模型**
   - 关键设计：**业务方预测**（**GMV / 订单量**） + **Prophet / ARIMA 时序预测**
   - 关键代码：
     ```python
     # 阿里双 11 容量预测
     from prophet import Prophet
     model = Prophet()
     model.fit(historical_data)
     future = model.make_future_dataframe(periods=30)
     forecast = model.predict(future)
     # 预测双 11 峰值
     peak_qps = forecast['yhat'].max() * 1.5  # 安全系数
     ```

2. **资源采购（3 个月前）**
   - 关键设计：**Spot + RI + Savings Plans**——**GPU / 数据库 / 带宽**
   - 关键数字：**预算 3 套**（**保底 / 预期 / 冲刺**）
   - 关键代码：
     ```python
     # 阿里容量采购
     # 3 个月前：
     # 1. 保底容量（去年双 11 + 30%）
     # 2. 预期容量（业务预测 + 50%）
     # 3. 冲刺容量（极端情况 + 100%）
     # 3 套容量 = 100% 覆盖
     ```

3. **弹性扩容（1 个月前）**
   - 关键设计：**阿里云 ESS（弹性伸缩）**——**秒级扩缩容**
   - 关键能力：**3 倍容量预热**——**1 分钟内完成**
   - 关键代码：
     ```yaml
     # 阿里云 ESS 配置
     scaling_rule:
       min_instances: 100
       max_instances: 1000
       scale_up_threshold: 60%  # CPU 60% 触发扩容
       scale_down_threshold: 30%
       cooldown: 60s
     ```

4. **预热（1 周前）**
   - 关键设计：**缓存预热 + 连接池预热 + JIT 预热 + GPU 预热**
   - 关键数字：**命中率 99%+**
   - 关键代码：
     ```java
     // 阿里缓存预热
     @PostConstruct
     public void warmUp() {
         // 1. 热点数据加载到 Redis
         for (Long hotKey : hotKeys) {
             redis.get(hotKey);
         }
         // 2. DB 连接池预热
         for (int i = 0; i < poolSize; i++) {
             connection = pool.borrow();
             pool.return(connection);
         }
         // 3. JIT 预热
         for (int i = 0; i < 1000; i++) {
             hotMethod();
         }
     }
     ```

5. **压测验证（1 周前）**
   - 关键设计：**全链路压测**——**10 万级**——**影子流量**
   - 关键能力：**真实环境**——**不影响生产**
   - 关键数字：**发现 100+ 性能瓶颈**

**阿里双 11 容量规划关键数字**（[阿里 2023 双 11 复盘]）：

| 年份 | GMV | 峰值订单/秒 | 容量采购（亿） | 0 严重故障 |
| --- | --- | --- | --- | --- |
| 2013 | 350 亿 | 1.7 万 | 0.1 | ✅ |
| 2016 | 1207 亿 | 17.5 万 | 1 | ✅ |
| 2019 | 2684 亿 | 50 万 | 5 | ✅ |
| 2022 | 1 万亿 | 60 万 | 10 | ✅ |
| 2023 | 1.5 万亿 | 60 万+ | 15 | ✅ |
| 2024 | 1.8 万亿 | 60 万+ | 20 | ✅ |

**具体数字（How much）**

- 团队规模：阿里双 11 备战总投入 2000+ 人
- 关键数字（[2024 公开数据]）：
  - **1.8 万亿 GMV**
  - **60 万笔/秒峰值**
  - **20 亿+ 容量采购**
  - **3 个月备战**
- 业务影响：阿里**全部业务**

**失败教训**

- 2013 第一次**容量不足**——倒逼**「**3 套预算**」**
- **缓存冷启动**——倒逼**「**预热**」**
- **弹性误判**——倒逼**「**压测**」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选**Prophet / ARIMA**（**最简单**）——**时序预测**
- 接入**1 个业务**——**容量评估**
- 团队：2-3 人

**1 → 10 阶段：6-12 个月**

- 扩展到**10+ 业务**
- 引入**弹性扩容**（**K8s HPA / 阿里云 ESS**）
- 引入**全链路压测**（**10 万级**）
- 团队：5-10 人

**10 → 100 阶段：12-24 个月**

- 扩展到**100+ 业务**
- 引入**GPU 容量规划**（**AI 时代**）
- 引入**大促常态化**（**2 次/年**）
- 团队：10-30 人

**100 → 1000 阶段：12-24 个月**

- 引入**AI 容量预测**——**自动预测**
- 引入**多 region**——**异地灾备**
- 团队：30-100 人

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 美团 / Netflix）印证：**容量规划不是「**拍脑袋**」，是「**业务预测 + 资源采购 + 预热 + 压测 + 现场**」**组合。
> - 关键时间线：阿里 10+ 年 / 字节 5+ 年 / 美团 5+ 年 / Netflix 5+ 年 —— **容量规划是 10+ 年长期工程**。
> - 选型第一原则：**Prophet / ARIMA**（**最简单**）——**时序预测** → **弹性扩容**（**K8s HPA / ESS**）→ **全链路压测**（**必须**）→ **多 region**（**全球化**）。
> - 99% 的失败来自「**容量不足 + 缓存冷启动 + 弹性误判**」——必须有**3 套预算 + 预热 + 压测**。
> - 真正的 ROI 来自「**避免大促故障 + 5-50000 倍峰值支撑**」——是**大厂核心业务的命脉**。
