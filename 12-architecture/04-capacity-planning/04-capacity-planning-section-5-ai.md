## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

**第一个问题：趋势清单没有时间维度。**

同一张清单里，「已经在生产里跑」和「厂商演示里跑过一次」被并列。对容量规划来说，这个错误的代价特别直接：把 L3 的东西写进采购假设，你买回来的是一批用不上的卡；把 L1 的东西当成「未来再说」，你付的是三年按需价与预留价的差价。

本节用三级划分，判据必须可核验，而不是「感觉成熟」：

- **L1 生产可用**：
  - ① 已 GA 且有正式 release note；
  - ② 有第三方（非厂商）公开生产案例；
  - ③ 接口稳定。
  - 三条全中才算，没有「准 L1」「边界案例」这类说法——②核不到就是 L2。
- **L2 可试点**：已可用但接口 / 生态未稳，或仅有厂商自有案例，或只在小规模被验证。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。记录，不要在架构里预留假设。

**第二个问题：本主题的①要换一种找法，但不能放宽。**

- 容量规划的一半「能力」是产品特性（扩缩组件、分区、托管服务），有正式 release note；
- 另一半是**公式与参数**（§2.2 的资源需求公式、GPU 需求公式、Little's Law），它们没有 release note，只有官方文档、论文与公开基准。
- 这不构成放宽判据的理由：公式类对象如果拿不到第三方在公开基准上的复核，同样只能算 L2——**你自己算得通不等于别人能复现**。
- 所以 5.1 表里凡是**公式与参数**的对象（token 计量的口径、推理优化的加速比、显存账本的参数），①列写的是「由官方文档、论文与公开基准承担」，而不是某一份 release note；判级比照的是这些公开材料里有没有可复核的值。
- 与①同理，**③只指接口稳定性**（对外契约、API、标准是否多年不变）。「收益不能线性外推」是收益泛化性问题，「利用率与 SLO 不同构」是度量效度问题，两者都不是③：它们该记在②（缺第三方验证），或写进 5.2 的「由此付出的」。把这类理由塞进③，会让同一列里③的含义一行一个样，读者无法按 5.1 的定义复现评级。

**第三个问题：本主题最典型的事故起点，是把厂商吞吐数字当分母。**

- 「单卡支持 X token/s」这类声称既不是①也不是②，它只是**一个数字**；而 §2.2 的 GPU 需求公式里，分母正是「单 GPU 吞吐 × 利用率」。
- 分母错一倍，卡数就错一倍。所以本主题的读法是：**任何性能声称都必须带条件**（模型规模、量化位宽、批大小、序列长度、并发数、硬件型号），没有条件的数字一律不进公式。
- 判定方法：把候选数字换成「在与你相同的批大小与序列长度下，官方文档或公开基准给出的实测值」，换不出来就说明这个数字不可用。

**第四个问题：先问这个方向改变的是哪一层。**

本节把方向分成四类，它们的前沿性来源不同，成熟节奏也不同：

| 需求侧 | 容量怎么用 | 批处理、量化、路由、前缀缓存 | 收益类能力普遍卡在②：公开记录多是框架方与平台方自述 |

**本主题下没有方向同时满足 L1 的三条判据**；最接近的一行是「可中断容量承载容错负载」（抢占式实例用于批推理、离线评分、索引重建这类可中断、可重排的作业）。

- 它满足①：这是长期 GA 的正式服务，官方文档给出中断通知机制与容量池模型；
- 它满足③：中断通知与容量池这类接口多年未出现破坏性变更。
- **它卡在②**：第三方（非厂商）的公开生产记录，本节给不出具名来源——能查到的是云厂商自己的客户案例页，那属于厂商材料，按判据不计入②。按本节规则，②核不到就是 L2，不写「准 L1」「边界案例」这类说法（详见 5.2.2 与 5.4 的第三方生产案例一栏）。
- 其余方向不够格的原因绝大多数落在②：**公开的生产记录基本来自平台方与厂商自述**——需求侧的量化 / 路由 / 前缀缓存、控制回路的信号与预热、供给侧的集群与训练调度、决策侧的预测 / 推荐 / 异常检测都属于这一条；严格说，全表 20 行没有一行②满足。其中「GPU 池化 / 切分」与「RAG 链路的分组件容量」两条，在②之外还多卡一条③——前者是分区与共享调度没有跨厂商标准，后者是组件边界随框架变化。

### 5.2 演进方向逐条拆解（核心节）

下面四条覆盖 5.1 分类表里的三类：5.2.1 与 5.2.2 都是供给侧（先是「容量以什么为单位度量、池怎么拆」，再是「容量从哪来」，也是本节最接近 L1 的一条），5.2.3 是控制回路（容量什么时候动：信号与启动），5.2.4 是决策侧（容量怎么定）；需求侧那几项（批处理、量化、路由、前缀缓存）机制上是 5.2.1 的推论——把一个分母拆成两个可分别度量的量——判级则在 5.1 表里逐行给出，不单列。每条都按同一结构展开：旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度。

#### 5.2.1 从「卡数」到「Token 吞吐」：显存与算力是两个池子

- **旧做法与它的卡点**：
  - **公式的分母不可信**：§2.2 的 GPU 需求公式是「推理 QPS × 每请求 token 数 ÷（单卡吞吐 × 利用率）」。这个公式没错，但它把请求当成同质的——真实负载里，同一个 QPS 下短问答与长文档的显存占用可以差一个数量级。
  - **整卡独占让两个池子的利用率错位**：一个大模型加载后显存吃满，算力却大量闲置；反过来，小模型把算力用满时显存还有富余。用一个「GPU 利用率」指标同时描述这两件事，必然失真。
  - **模型大小是硬门槛**：7B / 13B / 70B 这类档位【公开，属业界通用规模档位】在权重显存上相差一个数量级，这决定了「这张卡能不能装下」是一个先于性能的问题。
- **AI 改变了什么机制**：容量单位从「卡数 / 实例数」改成「token 吞吐 × 序列长度分布」，并把 GPU 拆成**两个可分别分配的池子**：
  - **显存池** = 权重（常数项）+ KV cache（随并发 × 上下文增长的变量项）；
  - **算力池** = prefill 与 decode 占用的计算时间，由批大小与引擎实现决定。
  - 改变的是**度量结构**：过去「几个卡」是一个数，现在「多少 token 吞吐、多大的 KV 预算」是两个可以分别优化、分别采购的数。
- **由此得到的**：
  - 因为显存与算力可以分开度量，所以优化手段第一次能对应到池子上——量化与蒸馏减的是权重显存，KV 量化与前缀缓存减的是 KV 显存，连续批处理与更大批大小提的是算力利用率；
  - 因为 KV cache 随上下文**线性**增长，所以「上下文长度」是一个可以与 QPS 独立翻倍的容量变量——这是长上下文真正的成本形态，而不是「模型变聪明了」的副产品；
  - 因为单位变成了 token，容量与业务量之间第一次有了直接传导路径（业务量 → token 数 → 吞吐 → 卡数），这正是 §2.2 公式能被当作规划工具的前提。
- **由此付出的**：
  - **分母必须自测**：单卡吞吐高度依赖批大小、序列长度、量化与引擎版本，任何单点数字都不能直接用作容量分母；用营销页数字当分母，是本节最常见的事故起点。
  - **共享之后「利用率」失去与延迟的对应关系**：同一张卡上多租户互相干扰，利用率看着很高、尾延迟却在恶化，扩容信号变成噪声。
  - **计量与计费复杂化**：按 token 归因需要新的记账维度，否则成本会算到「平台」头上而不是业务头上，成本优化就失去了方向。
  - **硬件世代锁定**：切分比例、量化收益、显存带宽的提升幅度都与具体加速器绑定，换一代硬件就要重做一次假设。
- **证据与来源**：
  - 【公开】vLLM 的 PagedAttention 工作（SOSP 2023 论文）与 vLLM 自 2023 年起的公开 release notes：连续批处理与分页 KV 缓存是「吞吐分母」变化的机制来源。
  - 【公开】MLPerf Inference（MLCommons 发布，规则与结果版本化）：给出把「单卡吞吐」放进有条件比较的手段——它是本主题里少数可以替代厂商数字的公开分母来源。
  - 【公开】NVIDIA 的分区能力随 A100（2020）引入并在后续世代延续（以 NVIDIA 官方文档当前版本为准）；集群级 GPU 共享的公开系统工作包括 Gandiva（OSDI 2018）与 AntMan（OSDI 2020）。
- **成熟度**：L2（①满足、②缺、③缺：分区与共享调度接口随硬件世代变化，没有跨厂商标准）。

```text
显存账本【推算，输入参数按公开模型配置核验】
  输入：70B 级、80 层、64 个查询头、head_dim 128（公开配置里的一类，按你要部署的
        模型自己的配置文档核验；此处按 MHA——K/V 头数 = 查询头数——计算）
  权重：700 亿参数 × 2 字节（FP16）        ≈ 140 GB      【推算：7×10^10 × 2B】

  结论二：容量规划要规划的是两项之和，不是「一张卡能跑几个模型」
  结论三：位宽减半只对权重近似成立（140 GB → 70 GB）

          —— 不能按位宽线性外推，必须实测
```

#### 5.2.2 可中断容量：把峰值的最后一段买成「可丢的」

- **旧做法与它的卡点**：
  - **峰值的最后一段最贵**：§4.1 阶段 4 把资源分成「预留实例（基线 70–80%）+ 弹性扩容（峰值 20–30%）+ 可中断」【经验，沿用 §4.1 阶段 4 的分档】。按峰值买意味着平时闲置，按月付账单；按基线买意味着峰值顶不住。
  - **采购周期长于业务变化**：§1.2 指出 GPU / 数据库 / 带宽采购要 1–3 个月【经验】——等你算清楚要多少，窗口已经过去了。
  - **所以瓶颈不是「预测得多准」，而是「预备得多灵活」**：能不能把一段容量买成「随时可以不要」的形态。
- **AI 改变了什么机制**：把资源的**持久性**与**价格**解耦——可中断容量用「随时可能被收回」换低单价，代价由工作负载承担。
  - 只要负载能容忍中断（可重试、可重排、可丢弃），容量不足就表现为「变慢」而不是「失败」；
  - **改变的是失败语义，不是容量大小**：这是本节唯一一条不需要新算法、只需要重新分类工作负载就能拿到的机制红利——也正因为如此，它是 5.1 表里最接近 L1 的一行（差的是②，见下）。
- **由此得到的**：
  - 因为峰值被分成「必须保住的部分」和「可以丢的部分」，所以扩容决策从一个数字变成两个数字（保底容量 + 可中断增量）；
  - 因为失败语义从「报错」变成「降级 / 重排」，所以批推理、离线评分、索引重建、日志与特征回填这类 AI 负载天然适合放在这一段——它们的共同点是**结果可以迟到，不能算错**；
  - 因为这一段的价格显著低于按需价，所以容量规划第一次可以在「保 SLO」和「控成本」之间做连续调节，而不是二选一。
- **由此付出的**：
  - **中断是外生的**：回收的时点与规模由供应商的容量池决定，容量规划的一个输入项从此不可控，必须靠中断通知与重排队设计来兜底。
  - **廉价不等于总成本低**：中断事件的恢复开销、为可中断而增加的重试与幂等设计，都是工程成本；没有幂等键的作业放在可中断容量上，是在制造重复计算。
  - **折扣是区间不是承诺**：官方给出的是**折扣上限**，实际折扣取决于容量池与中断率——把上限写进预算表是典型的高估。
  - **不适用于有状态与长时任务**：训练进程状态大，被回收一次可能损失远超省下的钱——这与 5.1 表里「弹性训练判 L2」是同一个判断。
- **证据与来源**：
  - 【公开】AWS EC2 Spot 是长期 GA 的正式服务，官方文档给出中断通知机制、容量池模型与「相对按需价最高可低约 90%」的表述（以官方页面当前版本为准——「最高」不等于典型值，规划时请用你们自己观察到的实际折扣与中断率【经验】）。
  - 【公开】AWS What's New 与 EC2 用户指南的 Spot 章节：中断通知（两分钟预警）与容量池这类接口的演进可逐年核对——①和③的依据都在这里。
  - **②（第三方非厂商的公开生产记录）本节给不出具名来源**：能检索到的是云厂商自己的客户案例页（属厂商材料，按判据不计入②）与第三方扩缩 / 调度工具的文档（描述的是「怎么用」，不是「谁在生产里用了、结果如何」）。这正是本行判 L2 而不是 L1 的直接依据——它缺的是证据，不是能力；一旦你能指认一份具名带年份的第三方生产记录（工程博客或会议分享，写清跑的是什么负载、可中断占比多少、重跑成本几何），这一行就该改成 L1。
- **成熟度**：**L2**——①③满足（长期 GA 且有正式发布记录、中断通知与容量池接口长期稳定），②缺（第三方非厂商的公开生产记录拿不出具名来源，理由见上）。

把工作负载按「中断一次的实际代价」分类，是这条方向（本节最接近 L1 的一条）唯一需要做的准备工作：

| 工作负载 | 中断一次的实际代价 | 能不能丢 | 该放在哪一档 |
| --- | --- | --- | --- |
| 在线同步推理（用户等结果） | 直接变成用户可见的失败 | 不能 | 保底容量（预留 / 按需） |
| 批推理、离线评分、特征回填 | 重跑一次的时间与算力 | 能（可重排） | 可中断增量 |
| 训练（长时、有大状态） | 从最近检查点恢复，可能损失数小时【经验】 | 谨慎 | 先用按需，观望 |
| 索引重建、离线评测 | 重跑，通常幂等 | 能 | 可中断增量 |
| 数据搬迁与冷数据重压缩 | 重跑，带宽是主要成本 | 能 | 可中断增量 |
- **适用范围**：这条方向（本节最接近 L1 的一行）只覆盖「能容忍中断的负载」。把大模型训练放进抢占式容量，本节的判断是 L2——不是不能跑，而是公开的第三方案例太少，而恢复开销又最容易被低估。

#### 5.2.3 弹性扩缩：把信号从「利用率」换成「排队」

- **旧做法与它的卡点**：
  - §2.2 的 HPA 公式用利用率做信号（当前指标值 ÷ 目标值），这对 CPU 密集的无状态服务成立；
  - 但对 GPU 推理不成立：利用率高不等于该扩容（可能正在高效批处理），利用率低也不等于不用扩（可能在等 KV 显存分配、等上游、或在一个长请求里空转）；
  - 更根本的问题是**度量与 SLO 不同构**：用户等待的是排队时间，而不是任何资源占用率。
- **AI 改变了什么机制**：把扩缩信号从「资源占用」换成「需求堆积」（队列深度、排队时间），并把「预热」单独立出来解决——因为模型加载到显存是分钟级而不是秒级，**「信号正确」与「资源及时可用」必须分开解决**。
  - 注意两处「秒级」不是一回事：5.1 表里 Serverless GPU 一行引的「秒级弹性」指的是**实例分配 / 调度**是秒级（这是厂商发布说明的口径）；**模型加载到显存是分钟级**。把后者当成前者，冷启动预算就会整整差一个量级。
  - 这是把一个控制问题拆成两个：信号（用与 SLO 同构的量触发）与启动（把加载延迟移出关键路径）。
- **由此得到的**：
  - 因为信号与 SLO 同构，所以扩容可以在用户可感知的延迟恶化**之前**触发；
  - 因为预热把启动延迟移出关键路径，所以「缩容到零」成为可能——对低频模型，这是唯一真正的成本手段；
  - 因为排队时间是可观测的业务量，所以容量复盘第一次能回答「这次抖动是容量不够，还是批处理策略变了」。
- **由此付出的**：
  - **批处理层会主动制造排队**：把「批得更好」误判成「容量不足」是这套机制最常见的误判，需要把批处理等待时间与真实排队分开统计。
  - **缩容到零带来冷启动**：低频模型的 P99 由冷启动决定，SLO 与成本在这个点上直接对立，必须显式选择。
  - **过度扩缩带来抖动**：GPU 实例的创建 / 销毁成本与显存碎片，可能让「快速缩容」比多留一台更贵。
  - **预热池本身是闲置成本**：池子大小要由 SLO 反推，而不是由「利用率好看」决定——一旦让它去美化利用率指标，它就会变大。
- **证据与来源**：
  - 【公开】Kubernetes 官方文档：autoscaling/v2 自 Kubernetes 1.23 起为稳定 API 版本（可按 Kubernetes CHANGELOG 核验），是把扩缩策略写成声明式对象的稳定接口。
  - 【公开】KEDA（CNCF 项目）提供按外部指标（队列长度等）的扩缩，具体版本与项目毕业状态以 CNCF 官网与项目 release notes 为准。
  - 【公开】云厂商的推理弹性与 Serverless GPU 有正式发布说明与配额文档（以官方当前版本为准）。
  - ②（非厂商公开生产记录）本节未给出：公开材料基本来自平台方与厂商，这是这几个方向停在 L2 的直接原因。
- **成熟度**：L2（①③满足、②缺）；其中「把 GPU 利用率直接当扩容信号」单列为 L3——它缺的不是③（接口并不新），而是②，外加一条可核验的效度证据：利用率与 SLO 不同构，而这个判断在公开材料里没有被第三方在生产上验证过（见上表与 5.1 表同一行）。

| 扩缩信号 | 与 SLO 的关系 | 在什么情况下会误判 | 可用性 |
| --- | --- | --- | --- |
| CPU 利用率 | 间接 | CPU 密集服务可用；被 I/O 等待放大时误判 | §2.2 公式适用，成熟 |
| GPU 利用率 | 弱 | 批处理中高利用率不代表该扩容，长请求中低利用率也不代表不该扩 | 不要单独使用 |
| 队列深度 | 强 | 批处理等待混入时高估 | 需拆分统计 |
| 排队时间（P95/P99） | 直接 | 归因错误（上游慢被算成自己容量不足） | 首选信号 |
| 显存 / KV 占用 | 强（决定能否接受新请求） | 长上下文请求会突然吃满 | 作为准入控制 |

#### 5.2.4 AI 辅助容量规划：换了预测器，还是换了机制？

- **旧做法与它的卡点**：
  - 容量规划里真正难的不是拟合，而是两个结构性约束：**采购周期长于业务变化周期**（§1.2 的 1–3 个月），以及**决策面对的是尾部**（低估一次是事故，高估是每月账单）；
  - §2.3 的传统方法（ARIMA / Prophet / 业务叠加法）已经能做趋势与节假日，卡点在输入侧：业务计划、营销排期、大模型上线计划这些信息在文档与会议里，不在时间序列里。
- **AI 改变了什么机制**：主要改的是**预测器的输入类别**（从纯数值序列扩到能吃计划文本与多变量），以及**交互形态**（自然语言问「明年要多少 GPU」）。
  - 这两者都不改变上面两个结构性约束：模型再准，采购周期不会缩短；模型再好，低估一次仍然是事故。
  - 所以本节对这条线的定性是：**异常检测与资源推荐是机制改良（把人工判断换成统计判断），自然语言接口只是换前端**（把同样的数字换个方式问出来）。
- **由此得到的**：
  - 因为模型能吃进「计划文本」这类非数值输入，所以业务叠加法（§2.3）可以从人肉对齐变成半自动，业务侧的假设第一次能被显式写进模型输入；
  - 因为交互成本降低，所以容量假设可以被更频繁地质询——在「假设错得离谱」的场景里，这一点比精度提升更值钱；
  - 因为异常检测盯的是指标形态而不是阈值，所以「这次高峰形态和去年不一样」可以被提前发现，而不是等 SLO 破了才知道。
- **由此付出的**：
  - **精度指标与决策目标错位**：MAE / MAPE 降了不代表采购更省——容量决策的成本是**分位数**上的（P95 低估率），而 MAPE 对低估与高估一视同仁。
  - **幻觉进采购单**：把自然语言接口的输出直接变成采购数量，是最危险的用法；自然语言接口只能用来生成假设，不能用来生成订单。
  - **可解释性下降**：ARIMA / Prophet 的趋势 / 季节 / 节假日分解是能在复盘会上被追问的，黑箱模型给出的数字没有这个能力。
  - **异常检测会被业务变更污染**：每一次成功的营销活动在模型眼里都是异常——异常检测的价值取决于谁去解释异常，而不是模型多灵敏。
- **证据与来源**：
  - 【公开】Google 的 Autopilot 工作（EuroSys 2020）描述了生产集群上的自动容量建议与自动伸缩——它说明「用统计方法自动给容量建议」是一条更早的公开路线，这不是从 LLM 开始的，也没有改变它的约束。
  - ②（非厂商公开生产记录）本节未给出：这一类能力的公开材料主要是云厂商的发布说明与产品页。
- **成熟度**：AI 异常检测与 AI 资源推荐为 L2（①③满足、②缺）；AI 流量预测与自然语言接口为 L3（缺独立效度证据与验收标准）——与 5.1 表逐项一致。

### 5.3 与本主题既有栈的接口在哪

不要写「与 X 结合」这种空话。下面写清**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。这张表是本节最可执行的部分。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 监控告警（Ch11）↔ 预测模型 | 固定窗口的指标序列（QPS / CPU / 队列 / GPU 利用率 / 显存）导出 | 数据缺口由监控方负责；模型误差由容量规划方负责 | 成熟，先做 |
| 大促保障（Ch12 §03；本目录 [§3.2.2 分层容量规划](04-capacity-planning-section-3-sec3.md) 与 [§6 落地实践](04-capacity-planning-section-6-sec6.md) 给的是同一套系数）↔ 容量规划 | 峰值系数与逐层放大比作为输入，按层给容量而不是等比例 | 系数低估由容量规划方负责；执行不及由大促保障负责 | 成熟 |
| 弹性扩容（§4.1 阶段 4）↔ 容量规划 | 扩缩的上下界、目标信号、预热时间由容量规划给出 | 信号选错（用 GPU 利用率扩 GPU 负载）由给出信号的一方负责 | L2，先改信号 |
| 混沌工程（Ch12 §06）↔ 容量规划 | 故障注入验证「缩容后还有多少余量」 | 容量假设被证伪后，由容量规划方修订假设并更新采购计划 | 需制度化 |
| 成本优化（Ch11）↔ 容量规划 | 预留 / 按需 / 可中断三档比例与承诺期限 | 承诺型采购的错误由批准采购的人负责（不可逆） | 现在就能落地（判 L2，见 5.2.2） |
| AI 平台（Ch5）↔ 容量规划 | token 吞吐、上下文长度分布、模型清单作为输入 | 把厂商吞吐数字直接当分母的一方负全责 | L2，需自测 |

这张表按「现在能不能动」分三档读：**成本优化这一行现在就能落地**（它是 5.1 表里最接近 L1 的一行，卡在②上，按判据记 L2，见 5.2.2）——它不需要新工具，只需要把工作负载按「能不能丢」重新分类，并给可中断的那部分补上幂等与重排队；**弹性扩容这一行要改流程**（判 L2），要改的是它这一行里的目标信号与预热时间，风险在于改错信号会让扩缩在最需要的时候不动；**监控告警与大促保障这两行是数据接口**，它们几乎不需要新东西，但缺了它们，后面所有判断都没有输入。剩下两行改的是别的东西：混沌工程只改验证方式（把容量假设拿去证伪），AI 平台这一行要求把分母的测试条件一起交接。

接口设计上最容易犯的一个错，是把「承诺型采购」和「自动扩缩」放进同一个自动化决策里：扩缩是可逆的、秒级的，采购是不可逆的、按合同周期的。把两者合并，等于让一个会犯错的程序去签不可撤销的合同。

还有一个更隐蔽的接口问题：**分母由谁负责**。§2.2 里以「单实例承载力 / 单卡吞吐」为分母的是两条公式——资源需求公式除以「单 Pod 承载力」，GPU 需求公式除以「GPU 吞吐 × 利用率」（HPA 公式的标度项是目标利用率，不属于这一类）——而这个分母通常由平台方提供、由业务方使用。分母错了，业务方算出来的每一个数都错，但业务方没有能力发现它错——所以这条接口必须写清：分母由平台方提供、带测试条件与测试日期，并且每次硬件或引擎升级后重新测一次。

**第三方生产案例（② 侧证据）**

- **本节给不出具名的第三方（非厂商）生产案例**，这不是排版上的空缺，而是本主题最重要的一个事实：它正是 5.1 表里没有一行判到 L1 的直接原因（20 行里缺②的占绝大多数）。能检索到的两类材料都不算②——云厂商的客户案例页属厂商材料；第三方扩缩 / 编排工具的文档与教程描述的是「怎么用」，不是「谁在生产里用了、结果如何」。
- 自己核验一条方向够不够 L1 的方法：找一份**非厂商、具名、带年份**的工程博客或会议分享，读它有没有写清负载形态、可中断占比、重跑成本与中断率；写不出这四项，就仍然只能记 L2。
- 检索入口可以用「公司名 + preemptible / Spot instances + 工作负载名」这类组合（可中断的编码转码、批处理与离线评分是这类记录里最常出现的负载），命中的厂商博客与客户案例页直接剔除——它们读起来最像生产案例，按判据却不算②。
- 这也解释了 5.2.2 为什么停在 L2：可中断容量缺的从来不是能力（它是本节最容易落地的一条），而是这一栏里的一条具名记录。

**怎么用这几类文献**

- 官方文档用来看**接口与承诺边界**（哪些行为是稳定的，哪些随版本变）；
- 论文用来看**机制**（为什么吞吐会变），不要用论文的倍率数字当容量分母——论文的运行条件与你的负载不会一致；
- 基准用来看**量级与可比性**，把候选硬件放进同一套条件里比；
- 三条都不满足的数字（营销页上的单点吞吐）不要进公式。

### 5.5 被过度宣传的部分

- **「GPU 池化把利用率从 20% 提到 70%」**——这句话在 GPU 虚拟化 / 池化产品与云厂商产品页的宣传材料里反复出现（各家给出的起点与终点数字并不一致）；本节保留它，只为指出它缺什么。**要核验它出自哪一份材料**，按「GPU pooling utilization」一类关键词检索厂商文档即可；核不出来源，就不要把它写进容量假设。**实际是**：池化提升的是**平均利用率**，而容量规划需要的是**峰值可用容量**；共享与切分会引入互相干扰（尾延迟恶化），把利用率与可用容量脱钩。**为什么会这样**：利用率是时间的平均，SLO 是分布的分位数，两个量在共享场景下不再单调对应。**什么时候它才会成真**：池化层能提供可核验的隔离保证（给出每租户的延迟分布，而不只是一个总利用率数字），那时候利用率才能重新被当作容量信号。
- **「AI 预测流量比 ARIMA 精度高」**——实际是：精度提升通常说的是平均误差（MAE / MAPE），而容量决策关心的是**尾部低估**；而且预测误差在扩缩链路里会被安全冗余系数乘性放大，误差的影响不是线性的。为什么会这样：容量规划里真正贵的从来不是预测不准，而是**采购周期长于决策周期**——预测提前三个月给出、采购要三个月拿到，等于没有提前量。什么时候它才会成真：模型被评估的是分位数指标（如 P95 低估率），并且采购能在预测窗口内完成；两条缺一条，换模型都不会改善结果。
- **「AI Agent 自动决策何时扩容、缩容、采购」**——实际是：扩缩可以自动（可逆、秒级、有上下界），采购与承诺型资源（预留实例、包年、大集群）不该自动（不可逆、按合同周期、金额大）。为什么会这样：把两类动作放进同一个自动化决策，等价于让一个会犯错的程序去签不可撤销的合同，而且它犯错的时候你往往已经在合同期内。什么时候它才会成真：自动化被明确限制在可逆动作（扩缩、路由、批大小、缓存策略），不可逆动作保留人类审批，且自动化带可回滚的预算上限——这才是「AI 主导容量规划」能落地的形态。

### 5.6 未来 3–5 年：可证伪的预测

趋势清单里的句子大多不可证伪（「AI 将主导容量规划」永远正确）。下面把本节可证伪的判断写出来。

本节其余方向在 5.1 表里的归类是：**GPU 即服务与 Serverless GPU**（L2，按需形态会继续扩张，但它的扩缩精度受限于冷启动）；**边缘 + 云端协同**（只在延迟或数据出域约束下成立，L2）；**数字孪生容量规划**（见下表最后一行）。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 推理容量的计量单位会从「卡时」转向「token 服务质量」，成本归因跟着换 | 云账单里出现按 token / 按有效吞吐的计价项；内部成本分摊表按 token 归因；SLO 文档里出现 token 级指标 | 三年后 GPU 账单仍按卡时结算，内部成本仍按实例数分摊 |
| 可中断容量会成为推理备用池的标准配置，但训练侧的抢占式弹性仍是少数派 | 推理服务的部署文档里出现「可中断备用池 + 预热 + 无损摘除」的固定模式；训练侧公开案例仍集中在少数团队 | 大量团队公开报告训练也能用抢占式容量且恢复开销可忽略 |
| 多池调度会因「容量可得性」而不是「避免锁定」普及——同一工作负载同时使用多家算力 | 出现以容量可得性而非单价为主要卖点的调度层；推理框架把多集群路由做成内置能力 | 主流推理框架三年后仍以单集群为默认部署形态 |
| 数字孪生式的容量模拟不会成为主流 | 出现「从生产流量自动回放生成仿真负载」的成熟工具链 | 三年后容量决策仍以「小比例真实流量灰度 + 压测」为主 |

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 单集群、单模型的小团队 | 把 token 数与上下文长度分布记进指标；按 §2.2 公式自测一次单卡吞吐当分母 | 托管推理服务能否给出可核验的延迟分布 | 不要引入 GPU 切分与多租户；不要自建流量预测模型；不要把利用率当扩容信号 |
| 多模型、多租户的推理平台 | 按信号表把扩缩信号从利用率换成排队时间；建预热池；给成本加 token 归因维度 | 池化的隔离保证是否可核验（有没有每租户延迟分布） | 不要把关键推理与小模型共享同一张卡而不做隔离验证；不要只按卡时给内部计费 |
| 有训练需求的团队 | 先解决排队与配额；把检查点策略当成容量假设的一部分 | 抢占式训练的公开生产记录是否变多 | 不要把抢占式当训练默认；不要在没有检查点策略前上弹性训练 |
| 峰谷落差大、成本敏感的业务 | 把工作负载按「能不能丢」重新分类，先上可中断容量（本节最接近 L1 的一条，见 5.2.2） | 实际折扣与中断率（用你们自己的观察值，不用官方上限） | 不要用跨云来省单价——出口流量与运维复杂度通常先吃掉差价 |
| 需要向老板解释「明年要不要买机器」 | 用 §2.2 公式 + 自测分母给出区间，写成三档（保底 / 弹性 / 可中断） | 采购周期是否还能覆盖预测窗口（覆盖不了就必须改预备方式） | 不要把厂商吞吐数字写进采购申请；不要用单一数字回答峰值问题 |

「明确不要做」这一列的判据是：**凡是用不可信的分母算出来的卡数、用与 SLO 不同构的信号触发的扩缩、以及把不可逆采购接进自动化的做法，现在做都是浪费**——它们的成本不会立刻出现，而是在第一次形态变化（新模型、新上下文长度、新峰值形态）时集中兑现。

### 5.8 小结

> 本节小结：AI 在本主题下真正改变的**唯一一条机制**，是把容量单位从「设备」改成「服务量」——GPU 从一张独占的卡变成「显存池 + 算力池」，需求从「QPS」变成「token 吞吐 × 上下文长度分布」。它**没有**改变的是容量规划的两条老约束：采购周期长于业务变化周期，以及决策面对的是尾部而不是均值。
>
> 因此本章的前沿判断是「供给侧先动、决策侧后动」：可中断容量是唯一不需要新工具的方向（把峰值的最后一段买成可丢的），但它卡在②上、按判据记 L2——也就是说它现在就能做，但不该被排进采购计划；需求侧的池化与量化需要先自测分母，而预测与自动化只应该被允许生成假设、不该被允许生成订单。
>
> 💡 **思考锚点**：把明年的采购申请拆成保底 / 弹性 / 可中断三档，其中可中断那一档占多少？它对应的正是你峰值里「能不能丢」的那最后一段——如果这档为零，你把整个峰值都买成了不可中断的常驻容量；如果它很大，你的 SLO 里哪一条允许这段被抢占而降级？
