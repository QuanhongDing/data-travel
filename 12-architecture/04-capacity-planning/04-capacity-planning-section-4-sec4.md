## 4. 工程实现

§ 3 回答的是「容量要分成几块、每块按什么价格买、什么时候发出扩容指令」；本节不重复这些模式论述，只回答落地层面的四件事：**按什么顺序做、每一步怎么知道自己做对了、手上多出什么东西、已经有一堆在跑的资源与旧估算习惯的组织怎么接进来**。

本文件面向两类读者。**从零建立规划能力的组织**（有监控、没有任何容量记录）走完整五阶段；**已有部分能力但从未闭环的组织**（有监控、有历史曲线，但没人记录过单机承载力和扩容耗时）重点在阶段 1 的第 4 条与阶段 5，中间阶段可以快速过。§4.4 写给第二类读者——你们要解决的不是「怎么预测」，而是「旧的拍脑袋估算怎么退役」。

### 4.1 落地步骤

五个阶段，前三个产出「数」，第四个产出「承诺」，第五个产出「校准」。每阶段给三件事：**产物**、**判据**、**为什么必须这一步**。

#### 4.1.1 阶段 1：数据采集（1–2 个月【经验：随指标面已覆盖多少、历史保留期多长而变——要补的指标、要补做压测的服务越多越靠上界】）

1. **采集资源指标**：QPS、CPU、内存、存储、网络、GPU 利用率——按分钟粒度落库并保留原始桶。只留天级均值等于把峰值抹掉，而排队延迟由峰值决定（非线性关系见 §3.1）。
2. **采集业务指标**：DAU、订单量、GMV、模型推理 QPS——与资源指标用同一套时间戳、同一套实体维度（按业务域 / 端 / 租户）。两套数据对不齐时，阶段 2 的因子归因做不了。
3. **采集历史**：至少覆盖一个完整年度周期【经验：只有 3 个月数据时，年度季节性无法与趋势区分；保留期由你的业务周期决定，不是固定值】。
4. **同步采集两项不来自监控的「过程量」**：单实例承载能力（必须实测，不能用规格书）、扩容就绪时间 T_ready（从触发到**首批请求成功返回**，不是 Pod 已 Running）。

- **产物**：指标清单（指标名 / 粒度 / 保留期 / 责任人）+ 一张《单实例承载能力与 T_ready 实测记录》。
- **判据**：随机挑一天，用当天数据重算「当天峰值利用率」，与监控图上当天的值比对；对有 SLO 的服务，能画出「P99 延迟 vs 峰值利用率」的散点。画不出来，说明采集里缺了分位或峰值桶。
- **为什么必须这一步 / 为什么在这个位置**：后面每一个数字都要在这里找到来源。跳过第 4 条的组织，阶段 3 只能用厂商参数换算，得到的实例数是「理论上」——而承载力取决于你的业务代码与单次开销，与核数之间没有固定换算关系；补测要等下一个峰值，所以这一步拖不得。

#### 4.1.2 阶段 2：预测建模（2–3 个月【经验：随需要建模的序列条数、以及业务方给增长系数的速度而变；序列逐条调参与逐条签字会顶到上界】）

1. **基线预测**：对每个有历史序列的服务跑一条时间序列（Prophet / ARIMA 一类），输出**带区间**的预测而不是点值（代码见 §4.2.1）。
2. **业务叠加**：把业务增长、营销活动、版本上线的预期增量叠加到基线上——这几个量由业务方给值并签字，不由模型自己从残差里拟合（做法见 §4.2.3）。
3. **峰值预测**：用历史上真实的峰值事件标定峰值倍率，而不是用日常序列外推。
4. **GPU 预测**：按「推理 QPS × 单请求 Token 数 ÷ 单卡吞吐 ÷ 利用率」换算，而不是按 QPS；显存按「最大并发 × 最长序列」再校验一遍（见 §4.2.4）。

- **产物**：一份带区间的预测表（服务 × 未来各月 × 基线 / 峰值 / 上下界）+ 每个预测值标注的**因子来源**。
- **判据**：只用上一个峰值**之前**的数据回测那一次峰值，看实测值是否落在区间内；落在区间外也必须能指出是哪个因子错了——归不到因子的偏差会在下一次原样重演。
- **为什么必须这一步 / 为什么在这个位置**：阶段 3 的换算需要「未来要承载多少」这个输入。先算资源再想预测，等于先定预算再定需求，之后所有精算都建立在一个没有依据的总量上。

#### 4.1.3 阶段 3：资源评估（3 周–1.5 个月【经验：随要换算的层数、以及阶段 1 的两项过程量是否已实测到位而变——承载力与 T_ready 没拿到时要等下一个峰值补测，直接顶到上界】）

1. **应用层**：Pod 数、实例类型——按阶段 1 实测的单实例承载力换算，不用规格书。
2. **数据层**：存储量、IOPS、带宽——存储按「日增量 × 保留期 × 副本数 × 压缩比」算，并把冷热分层对应的介质分别列价。
3. **基础设施层**：CPU、内存、网络、GPU。
4. **AI 层**：GPU、推理服务、向量库——显存按最坏组合算，均值对它没有意义。

- **产物**：一张分层资源清单（每层：需求值 / 换算依据 / 用到的实测值 / 归属团队）。
- **判据**：挑任意一层，用它的需求值反推回入口流量，看是否与阶段 2 的预测一致。对不上，说明换算链里混用了别人的系数——最常见的错误是应用层用自测承载力、数据层用厂商吞吐。
- **为什么必须这一步 / 为什么在这个位置**：它是「预测」到「采购」之间唯一的换算层，也是唯一能暴露「哪一层会先成为瓶颈」的地方（层的顺序与系数怎么定见 §3.2.2）。

#### 4.1.4 阶段 4：采购与调度（持续）

把评估出的资源按**可中断性**与**使用时长**分成三份，分别买；再定调度方式：

1. **预留实例**：覆盖基线资源，占比 70–80%【经验：该分档随利用率分布形态而变，基线越平稳占比可越高；必须用自己的利用率曲线标定，不要照抄】。
2. **弹性扩容**：覆盖峰值资源，占比 20–30%【经验，与上一条同一分档，判据是峰值持续时间是否长于就绪时间】。
3. **Spot Instance（抢占式）**：只承载可中断任务——批量离线、可检查点的训练、无状态且可重试的任务【经验：折扣随机型 / 区域 / 时段变化很大，请以当前价目页为准】。
4. **跨云调度**：只在「数据搬得动」的那部分负载上做，判据见 §3.2.6。

- **产物**：采购结构表（每类资源：承诺量 / 计价方式 / 覆盖的负载 / 盈亏平衡利用率）+ 一份可中断负载清单。
- **判据**：把「已承诺量 ÷ 实际用量」按周画出来——持续高于 1 说明在为闲置付承诺价，持续低于 1 说明预留不足、正在按高价补；同时逐项确认被放到抢占式上的负载都有检查点，且检查点间隔远小于中断通知到实际回收的时间（这个窗口必须实测，不能按文档假设）。
- **为什么必须这一步 / 为什么在这个位置**：采购结构必须在容量总量定下来之后才定，否则会出现「因为预留便宜所以多买」的倒推（见 §3.4）；而它被放在持续阶段，是因为承诺可以在周期结束后调整，峰值却不能等。

#### 4.1.5 阶段 5：持续优化（持续）

1. **预测准确性评估**：每个周期算出预测值与实测值的偏差，并归因到具体因子。
2. **资源利用率优化**：调高 / 调低资源，用实测值回填容量登记表（单实例承载力、T_ready）。
3. **AI 辅助决策**：让模型给推荐值与区间，但把决策与签署留在流程里（边界见 §3.2.5）。

- **产物**：容量登记表（每个容量数字：值 / 来源 / 上次校准时间 / 上次偏差归因）+ 本周期校准记录。
- **判据**：能回答「上一次预测偏了多少、偏在哪个因子、这个因子有没有被修」。答不上来，即校准回路没有闭合，这一阶段的输出只是一份没人用的报表。
- **为什么必须这一步 / 为什么在这个位置**：容量规划是少数会被真实数据当场检验的工作——峰值当天就知道估准没估准。没有记录就没有收敛，换任何预测算法都会在同一处错第二次。

**最常被跳过的一步**是阶段 1 第 4 条的两项过程量——**单实例承载能力实测值**与**扩容就绪时间 T_ready**。它们不像 CPU 曲线那样自动就有，要专门压测、专门演练，因此最容易被推迟到「下一个峰值之后」。跳过它们的症状不出现在报告里，而出现在峰值当天：阶段 3 的实例数是按规格书换算的（偏乐观），阶段 4 的弹性比例是按「扩容很快」假设定的（也偏乐观），于是副本数在涨、业务指标在恶化，而团队在峰值期间找不到任何一个能立刻回答「到底哪里不够」的数。

### 4.2 关键技术点

四条，每条给 **做法 / 代码或配置 / 机制 / 失效条件 / 档位**。这里的失效条件写的是**装进真实系统之后**才会出现的那一类（配置项、指标选型、预热门控），模式层面的失效点见 §3。

#### 4.2.1 时间序列基线预测（Prophet / ARIMA 一类）

**做法**：以「服务 × 指标」为序列，训练窗口 ≥ 1 个完整年度周期；把已知节假日与活动排期作为**显式回归量**传入，不让模型从残差里猜；输出始终取区间（`yhat_lower` / `yhat_upper`），点值只用于展示。
```python
from prophet import Prophet
model = Prophet(yearly_seasonality=True, weekly_seasonality=True,
                daily_seasonality=True, holidays=holidays_df,   # 双11 / 618 等排期
                changepoint_prior_scale=0.05)                    # 先验，需按序列平滑度调
model.fit(df)                                                # df 列：ds, y
forecast = model.predict(model.make_future_dataframe(periods=365))
predicted = forecast[['ds', 'yhat', 'yhat_lower', 'yhat_upper']]
```
**机制**：因为序列被拆成趋势项 g(t) + 季节项 s(t) + 节假日项 h(t)（分解形式见主文件 §2.2），所以「周期性」与「一次性活动冲击」分开建模——活动排期作为显式输入进 h(t)，就不会被吸收进趋势项，从而不会在活动结束后把趋势永久抬高。这是它相对单纯外推的主要差别。

**失效条件**：**当训练窗口内发生结构性阶跃时**（产品改版、渠道结构变化、单体服务被拆分），模型会把阶跃当成趋势的一部分继续外推——趋势项允许在窗口内改变变化率，于是它忠实地把一次性阶跃延伸到了未来。**症状**是预测持续单向偏高（或偏低），残差在阶跃点前后呈现明显不同的水平。识别信号：把预测值与实测值画在同一时间轴上并标出已知的业务变更时点，变更点之后偏差若长期同号，就是这个问题。修法是在变更时点截断训练窗口，或把变更写成回归量而不是交给趋势项（【公开，Prophet 官方开源仓库与其论文 Taylor & Letham；开源年份见主文件 [§ 1.4](04-capacity-planning.md) 记的 2017，参数含义以当期文档为准】）。

#### 4.2.2 弹性扩容（HPA / VPA / Cluster Autoscaler / KEDA）

**做法**：分三层配置——Pod 数用 HPA、Pod 规格用 VPA、节点数用 Cluster Autoscaler；事件驱动的负载（队列消费、Kafka）用 KEDA 按队列深度 / lag 扩，而不是按 CPU 扩。给 HPA 显式设置 `behavior` 的扩缩稳定窗口，并给所有扩容目标设置非零的 min replicas。
```yaml
apiVersion: autoscaling/v2        # HPA：资源型负载（下列数值与窗口皆为示意，须自行标定）
kind: HorizontalPodAutoscaler
metadata: {name: order-service-hpa}
spec:
  scaleTargetRef:                 # 不能省：HPA 必须指名它扩哪个工作负载，缺这一段 apply 会被拒
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 10                 # 不要设 0：冷启动代价不在指标里
  maxReplicas: 1000
  metrics: [{type: Resource, resource: {name: cpu, target: {type: Utilization, averageUtilization: 70}}}]
  behavior:                       # 稳定窗口：扩得快、缩得慢，抑制「扩完就缩」的抖动
    scaleUp:   {stabilizationWindowSeconds: 0,   policies: [{type: Percent, value: 100, periodSeconds: 15}]}
    scaleDown: {stabilizationWindowSeconds: 300, policies: [{type: Percent, value: 10,  periodSeconds: 60}]}
---
apiVersion: keda.sh/v1alpha1      # KEDA：事件型负载，按积压量扩
kind: ScaledObject
metadata: {name: kafka-consumer-scaler}
spec:
  scaleTargetRef: {name: order-consumer}    # 同样不能省：指名被扩的工作负载
  minReplicaCount: 5
  maxReplicaCount: 500
  triggers:
  - type: kafka
    metadata:
      bootstrapServers: kafka:9092          # 触发器缺这两项连不上 broker / 认不出消费组
      consumerGroup: order-consumer-group
      topic: order-events
      lagThreshold: '100'
```
**机制**：HPA 的副本数按「当前指标值 ÷ 目标指标值」的比值乘当前副本数算出【公开，Kubernetes 官方文档 · Horizontal Pod Autoscaler：`autoscaling/v2` 自 Kubernetes 1.23 起为稳定 API 版本（可按 Kubernetes CHANGELOG 核验）；公式与默认容忍度以当期文档为准】——这意味着扩缩速度由**指标的响应速度**决定，而不是由阈值决定；KEDA 把触发信号换成队列深度这类与积压量直接相关的量，于是扩缩与业务积压同向变化，而不是与 CPU 这种间接量同向。

**失效条件**：**当单次请求的开销可变时**（AI 推理的序列长度、转码的码率、批处理的批次大小），按 CPU 扩容会失效——CPU 不涨而排队时间涨，扩缩器看不到任何需要扩的信号，**症状**是队列积压持续增长、副本数纹丝不动。第二个失效面：**当 min replicas 被设为 0、或进程需要冷启动（加载模型、建立连接池、填充缓存）时**，从扩容到「真的能服务」之间有一段没有指标能反映的空白，**症状**是「Pod 已 Running 但请求仍在超时」——所以要在就绪探针之后另设一道预热门控，把「能服务」而不是「已运行」作为扩容完成的判据（【公开，Kubernetes 官方文档 · HPA 的 `behavior` 字段（`autoscaling/v2`，自 Kubernetes 1.23 起为稳定 API 版本）与 KEDA 触发器文档（KEDA 作为 CNCF 项目提供按外部指标的扩缩）；可用字段与默认值随 Kubernetes / KEDA 版本变化，配置前请以当期文档为准】）。

#### 4.2.3 业务叠加预测（乘积形式与它的校准）

**做法**：容量 = 活跃用户数 × 人均行为次数 × 单次行为开销；三个因子分别实测、分别归因，相乘得到**基线**。业务增长与活动峰值倍率是**另一组量**——它们是叠加在基线之上的显式系数，由业务方给值、由历史回测给区间，不参与三因子的归因。两组量在同一张归因表里分列。
```python
# 以下全部是占位符：必须换成你自己的实测值，不要照抄任何一个系数
# 第 1 段：三个驱动因子相乘 → 基线（各自实测、各自归因，不要只留乘积）
active_users      = <活跃用户数>          # 因子 1，业务方给
actions_per_user  = <人均行为次数>        # 因子 2，实测
baseline_qps      = active_users * actions_per_user / <统计窗口秒数>   # 窗口与阶段 1 的粒度对齐
# 因子 3「单次行为开销」不进 QPS：它以「单实例承载力」的倒数形式出现在下一段
# 第 2 段：两个显式系数叠加 → 峰值（业务方签字，不由模型拟合）
business_growth   = <业务方给的增长率>      # 由业务签字
promotion_boost   = <历史峰值实测倍率>      # 由上一个峰值事件标定
single_pod_capacity = <阶段 1 实测的单实例承载力>   # 不是规格书
safe_margin       = <由 SLO 与事故损失算出的冗余>

predicted_peak_qps = baseline_qps * business_growth * promotion_boost
required_pods      = predicted_peak_qps / single_pod_capacity * safe_margin
```
**机制**：乘积形式在流程里落成一张**归因表**——每个周期把偏差按「用户数 / 人均行为 / 单次开销 / 业务增长系数 / 峰值倍率」分五行记，于是「下一次改哪个数」有依据，而不是把偏差笼统记成「预测不准」。因子行与系数行必须分列：混成一行时，同一个偏差会在相邻两个周期被归到不同的行，归因表就退化了。两个系数也因此不能交给模型去拟合——拟合出来的系数会同时吸收业务增长与结构变化，可归因性随之消失。乘积形式的可归因性与「误差相乘」这两条性质见 [§ 3 设计模式与范式](04-capacity-planning-section-3-sec3.md) 的 3.2.3——三个各自 ±10% 的因子最坏给出 +33% / −27%【推算，推导链（1.1³ 与 0.9³）见该处，本节不重复】；本节只讲怎么把它算进流程，以及为什么两个系数必须与因子分列。

**失效条件**：**当一次变更同时改动两个以上因子时**（上新模型、改推荐策略、换客户端版本），因子之间的独立性被打破，乘积法的归因会给出错误答案——你会把「单次开销上涨」归因到「人均行为下降」，因为两个因子同向变化、互相掩盖。**症状**是校准记录里同一个偏差连续几个周期被归到不同的因子。识别信号：把每次产品 / 模型变更的时点与因子偏差的时点画在一起，若总有两三个因子同时偏，说明乘积结构在这个负载上已经不适用，应改为按变更分组的对照（变更前后各取等长窗口）。

#### 4.2.4 GPU 资源规划

**做法**：按 Token 数而不是请求数建模——所需卡数 = 推理 QPS × 平均单请求 Token 数 ÷（单卡吞吐 × 目标利用率）；再用「最大并发 × 最长序列」单独校验一遍显存。吞吐与利用率都用自己的压测值，不用厂商规格、也不用别处的数字。
```python
def estimate_gpu_count(inference_qps, avg_tokens_per_request,
                       gpu_throughput,            # tokens/s，必须自测：随模型、量化、批大小而变
                       gpu_utilization=0.7, safety_margin=1.3):   # 两个默认值均为示意
    return int(inference_qps * avg_tokens_per_request
               / (gpu_throughput * gpu_utilization) * safety_margin) + 1
```
**机制**：GPU 规划与 CPU 规划的分野在于**显存是一条硬上限**——CPU 超载可以靠排队吸收（延迟变差但请求还在处理），显存不足会直接失败，所以它不能用均值规划，必须按最坏组合留出空间。因为这条硬上限存在，按请求数建模会在序列变长时系统性低估：QPS 不变，显存与算力需求同时上升。

**失效条件**：**当推理服务开启连续批处理、前缀缓存或投机解码时**，单卡吞吐不再是一个常数，而是随并发与请求相似度变化的函数——用固定吞吐换算出的卡数会随负载形态漂移：负载越同质越容易被高估，越异质越容易被低估。**症状**是同一服务的「实测卡数 ÷ 估算卡数」在不同时段相差很大。修法是把吞吐改成按「批大小 × 序列长度」分桶的实测表，而不是一个标量。可自行核验的判据：统计线上实际批大小分布，若绝大多数请求长期是批大小 1，说明连批处理能力都还没用上（同 §3.5 的判据）（【经验】）。

### 4.4 存量迁移

这一节写给**已经在跑一堆资源、但容量决策还停留在口头估算**的组织。要解决的问题不是「怎么预测」，而是「新方法怎么在旧习惯旁边活下来，并且真的替代它」。

#### ① 立刻见效且可回退的第一步

**先做两张表，不改任何架构。** 一是《容量登记表》：把在用的资源逐个登记成行（见 §4.5 示例 3）；二是《T_ready 实测记录》：对每个可扩服务做一次扩容演练，记录从触发到首批请求成功返回的耗时。

- **为什么可回退**：这两件事都是纯记录，不申请采购、不改配置，删掉不影响任何系统。
- **判据**：拿 T_ready 与「历史最快一次流量上升的耗时」比一次。比值 > 1 的服务，其峰值必须按常驻容量准备——这一条会直接改变后面的迁移顺序（先补它的容量，而不是先优化它的预测）。
- **不要在这一步做的事**：不要顺手调整任何 HPA 阈值或采购结构。此时还没有任何实测数字支撑调整，改出来的只是另一组猜值。

#### ② 存量资产怎么分类处理

| 类别 | 适用范围 | 处理方式 | 风险 |
| --- | --- | --- | --- |
| **全部重做** | 新建、体量小、无历史承诺的资源 | 从一开始就接进登记表与新口径 | 几乎无风险，但只适用于新资源 |
| **只改动的部分**（主流） | 绝大多数在跑的资源与监控 | 已签的预留 / 节省计划**不动**（提前退通常更贵），但**新签**的承诺按登记表里的利用率分位签；已有监控不动，但**新增指标**一律按「分钟粒度 + 峰值分位」落库 | 新旧两套口径会并存一段时间，必须有人维护「新指标清单」 |
| **打标挂账** | 无法补齐历史的服务、无实测承载力的服务 | 不返工，明确标注缺口：无历史序列的写「容量按业务驱动换算（§4.2.3）」，无实测承载力的写「当前值来自规格书，待下一次峰值后回填」 | 挂账项需要定期复核，否则等于被遗忘 |

核验方法：随机抽 3 个服务，看它们的容量数字能不能说出「来源 + 上次校准时间」。说不出来源的数字，就是尚未挂账的缺口。

#### ③ 双轨怎么维持、维持多久

- **双轨的形态**：每个容量周期（例如每次大促前）同时给出两套数——新方法给**区间**，旧方法给**点值**；峰值过后把实测值同时回填到两边。差异与归因必须逐次记录。
- **维持时长【经验】**：至少覆盖一次**真实的峰值**。判断依据不是月数而是事件数——平峰期两套数总是很接近，看不出差别，只有峰值能区分两种方法。所以「维持 3 个月」这种说法没有意义，应该是「维持到经历过一次最大活动」。
- **双轨期禁止的两件事**：不记录原始数字只留结论（等于每个周期重新开始）；让两套数中的一套直接进入采购（双轨是参照，不是并行决策，否则采购量会翻倍）。
- **成本主体是回填**，不是多算一次预测：回填如果没人做，双轨就是两份没人看的表。

#### ④ 什么信号说明可以退出双轨

四个条件同时满足才退出：**① 连续两个峰值周期**，新方法的区间都包含了实测值，且偏差能归因到具体因子；**② 登记表里不再有「来源不明」的条目**（每条都能说出实测 / 换算 / 经验）；**③ 每个可扩服务的 T_ready 都在峰值条件下实测过一次**并写进登记表；**④ 峰值结束后有一次正式复盘**，实测值已回填模型参数。任何一条不满足就继续双轨：继续的成本可算（多一次回填与复盘），提前退出的成本不可算（下一年的采购又回到凭印象）。

### 4.5 模板 / 示例

#### 示例 1：时间序列 + 业务叠加 + 资源评估的完整链路

```python
import pandas as pd
from prophet import Prophet

df = pd.read_csv("history.csv")            # 列：ds, y（服务 × 指标）
holidays = pd.DataFrame({                  # 活动排期：日期必须与业务排期一致
    'holiday': ['double11', 'double618', 'double12'],
    'ds': pd.to_datetime(['2022-11-11', '2023-11-11', '2024-11-11',
                          '2022-06-18', '2023-06-18', '2024-06-18',
                          '2022-12-12', '2023-12-12', '2024-12-12']),
    'lower_window': 0, 'upper_window': 1})

model = Prophet(yearly_seasonality=True, weekly_seasonality=True,
                daily_seasonality=False, holidays=holidays,
                changepoint_prior_scale=0.05)     # 先验，按序列平滑度调，不要照抄
model.fit(df)
forecast = model.predict(model.make_future_dataframe(periods=365))

peak_qps = forecast[forecast['ds'].dt.month == 11]['yhat_upper'].max()   # 取上界，不取点值
required_pods = int(peak_qps / SINGLE_POD_CAPACITY * SAFE_MARGIN)          # 两者都是自测值
print(f"预测峰值上界={peak_qps:.0f}  建议 Pod={required_pods}")
print(f"其中预留={int(required_pods*0.7)}（基线）  弹性={int(required_pods*0.3)}（峰值）")
```
**怎么用**：填三格——`history.csv` 的序列、节假日表的排期日期、`SINGLE_POD_CAPACITY` 与 `SAFE_MARGIN`（前者来自 §4.1.1 阶段 1 的实测，后者来自 SLO 与事故损失）。
**不要照抄**：`changepoint_prior_scale` 之类的先验参数要按你的序列调；末尾那个 70 / 30 拆法是 §4.1.4 的【经验】分档，必须用自己的利用率曲线标定，照抄等于把一个别人的经验值当成自己的实测值。

#### 示例 2：GPU 资源池化（多租户共享，MIG 配置）

```yaml
apiVersion: v1
kind: ConfigMap
metadata: {name: mig-config}
data:
  config.yaml: |
    version: v1
    mig-config:
      - device-filter: ["nvidia.com/A100"]
        mig-devices:
          "0": ["1g.5gb", "1g.5gb", "2g.10gb", "3g.20gb"]   # 计算切片合计 = 该卡切片总数
---

kind: Pod
metadata: {name: inference-pod-1}

  containers:

```
**怎么用**：填两格——`device-filter` 换成你的 GPU 型号与资源名；`mig-devices` 里的 profile 组合**各切片相加必须等于该卡的计算切片总数**（示例按 A100 40GB 的 7 个计算切片给出：1g×2 + 2g×1 + 3g×1）。可用 profile 表随 GPU 型号与驱动版本变化，请以当期官方文档为准。
**先逐键核对 schema**：mig-parted / GPU Operator 的 v1 配置里，`mig-config` 是否作为键出现、`mig-devices` 取「设备序号 → profile 数组」还是「profile 名 → 数量」、是否另有 `mig-enabled` / `devices` 一类键，都随版本变化。落地前请按官方文档当前版本的 v1 示例逐键比对（可按「mig-parted config v1 mig-devices」自行检索核验），**以官方示例为准**，本示例只用来表达「一张卡的切片怎么组合」这层意图。
**不要照抄**：不要照抄「一服务一切片」的粒度——切片大小应由**最大请求的显存需求**决定（理由见 §4.2.4 的失效条件）；如果你的调度器已按整卡分配，还要把切片数换算成卡数。

- [ ] 容量报告的主指标是**峰值利用率**还是均值？有没有 P99 延迟与峰值时段的对应曲线？
- [ ] HPA / VPA / Cluster Autoscaler 三层是否都配了？有没有负载出现「Pod 扩了但卡在 Pending」？
- [ ] 事件型负载（队列消费、Kafka）的扩缩信号是积压量还是 CPU？后者的话，最近一次积压有没有触发扩容？
- [ ] 有没有 min replicas = 0、或需要冷启动（加载模型、填缓存）的服务？就绪探针之后还有多少没有指标覆盖的预热时间？
- [ ] 被放到抢占式资源上的负载，逐项确认过可中断吗？检查点间隔是否远小于中断通知到实际回收的时间（并实测过）？
- [ ] GPU 规划是按请求数还是按 Token 数？显存是否按「最大并发 × 最长序列」校验过？线上实际批大小分布是什么？
- [ ] 业务排期、活动、版本上线是否作为容量模型的**显式输入**，而不是等出了偏差再解释？
- [ ] 存储的访问分布、保留期、介质是否在同一张表里列出？冷数据占比与介质单价是否单独成一行？
- [ ] 上一个周期的预测偏差是多少、归因到哪个因子、这个因子被修了吗？校准记录能否被调取？

### 4.7 小结

> 本节小结：整个落地过程里，唯一决定成败的环节是 **阶段 1 里那两项不来自监控的数字——单实例承载能力的实测值，与扩容就绪时间 T_ready**。它们决定了后面每一步能不能算：没有承载力，资源评估只能用规格书换算；没有 T_ready，基线与弹性的比例就是猜的。其余环节（预测算法、工具链、采购结构）都可以边跑边迭代，只有这两个数必须在下一次峰值之前拿到——因为它们只能在峰值条件下测出来。判断一个团队有没有真的在做容量规划，看它有没有这两张表，而不是看它用了哪个预测模型。

> 💡 **思考锚点**：填 §4.5 那张容量登记表的一行——你的单实例承载能力是「实测」还是「规格书换算」？若是实测，4.6 会追它是在什么负载形态下测的（批大小、序列长度），以及 T_ready 是峰值测的还是平峰测的。GPU 那行再问一句：显存是按「最大并发 × 最长序列」校验的，还是按平均？这三个格子只要有一个空着，你下一次峰值是不是就还在拿别人的经验值当自己的实测值？
