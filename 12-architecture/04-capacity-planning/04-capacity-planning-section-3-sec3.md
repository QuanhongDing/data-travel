## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

场景表把容量规划讲成「按业务类型选一种预测方法」。但同一个「周期性业务」，三家团队会给出三套答案：一个用 Prophet 加人工叠加，一个按业务漏斗逐层算，一个干脆只做压测不做预测。差异不在业务类型，在**你手里的时间够不够把资源在生产高峰到来之前准备好**。

这个主题的机制可以压成三句话。第一句：**容量决策的实质是「扩容完成的耗时」与「流量上升的耗时」的比值**。比值小于 1，弹性可以替你接住峰值，你只需要算准总量；比值大于 1，弹性在峰值期间等于不存在，容量必须以常驻资源的形式提前买下来。所有预测方法的价值，都只是把这个比值往小于 1 的方向推——预测式扩容的全部意义是**提前发出扩容指令**，而不是让扩容变快。

第二句：**均值永远推不出够不够用，因为排队是非线性的**。在单队列单服务台模型下，平均等待时间与服务时间之比为 ρ/(1−ρ)（ρ 为利用率）【公开，M/M/1 排队模型，等待时间 W_q = ρ/(1−ρ) × 服务时间】；利用率从 70% 升到 90% 时，这个比值从 2.33 升到 9【推算，推导链：0.7/0.3 = 2.33；0.9/0.1 = 9】。所以「平均 CPU 利用率 30%」与「够不够用」之间没有推导关系——决定 P99 的是峰值那几百毫秒里到底排队排了多久。

第三句话是关于成本的对称性：**多备一个单位是按时间付费的确定性支出，少备一个单位是按概率付费的期望损失**。两者单位不同、方向相反，所以「安全系数给多少」不是一个可以拍的数字，而是一次显式比较——把「多备一份的月成本」与「少一份时的事故损失 × 发生概率」写在同一张纸上。写不出来，说明这个数目前还是经验值；那就至少把它明确标成经验值，并在下一次峰值后用实测回填。

因此本节的组织顺序是：先用 3.1 的约束表确定「弹性能不能用、总量怎么换算」，再看 3.2 里对应模式的结构与失效点，最后到 3.3 选型。反过来（先挑预测算法再找场景）的团队，常会得到一个预测精度很高、但没有任何人用它做决策的模型——因为决策需要的不是更准的均值，而是「最坏情况下够不够」这个问题的答案。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 流量上升的时间尺度（秒级脉冲 / 分钟级爬坡 / 小时级日常峰 / 季节性） | 弹性是否可用，以及基线要覆盖到哪一档 | 「上了自动扩容就不用预留」——就绪时间必须短于上升时间，否则弹性等于不存在 |
| 峰值持续时间与弹性就绪时间 | 双轨容量的分界点、预热策略 | 「峰值越短越该用弹性」——峰值越短，弹性越来不及，反而越是必须常驻 |
| 负载的可中断性（能否检查点恢复、是否无状态） | 抢占式资源能用在哪一部分负载上 | 「便宜就都用抢占式」——不可中断的负载用抢占式，省下的钱会被中断损失吃掉 |
| 单次请求开销是否稳定（请求长度、码率、模型档位是否可变） | 能否用「请求量 × 单次开销」换算容量 | 「QPS 就是容量」——单次开销翻倍时 QPS 不变，容量需求已经翻倍 |
| 资源类型的供给弹性（CPU 秒级 / 存储分钟级 / GPU 与专线按采购周期） | 哪些资源必须提前买，哪些可以按需 | 「所有资源都能弹性」——GPU 与带宽的可得性由采购周期决定，不由 API 决定 |
| 数据保留期与访问分布（热 / 温 / 冷） | 存储容量的分层与单位成本口径 | 「存储便宜不用管」——保留期无限增长时，它是唯一随时间长青的成本项 |

### 3.2 模式逐个拆解（核心节）

以下 6 个模式（基线 + 峰值双轨预测、分层容量规划、业务驱动预测、弹性 + 预留混合、AI 辅助决策、多云容量管理），顺序按「先定容量结构 → 再定分配粒度 → 再定换算方式 → 再定采购结构 → 再看预测工具 → 最后看供给来源」排列。

每个模式请先读「被什么约束逼出来」，再读失效点——**失效点决定它在你这里能不能用**：容量规划里的失效点，几乎全部集中在一个地方，就是「你以为会及时到来的那部分资源，其实没有及时到来」。

六个模式回答的是不同层次的问题，按顺序读就不会混：3.2.1 决定「容量分成几块」，3.2.2 决定「每块怎么分给各层」，3.2.3 决定「每块有多大」，3.2.4 决定「每块以什么价格买下」，3.2.5 决定「什么时候发出扩容指令」，3.2.6 决定「这些资源从哪里来」。前一环没有结论时，后一环的任何优化都只是在错误的总量上做精算。

#### 3.2.1 基线 + 峰值双轨预测

- **被什么约束逼出来**：负载由两段性质不同的成分构成——日常窄幅波动，加上偶发的大幅峰值；一个资源池无法同时做到「按日常规模付费」与「峰值时够用」，两者的价格与时间尺度都不同。
- **结构**：

```text
 双轨容量 = 常驻基线 + 弹性峰值
   基线：按日常峰值（含方差）常驻，以长期承诺价计价
   峰值：按「峰值 − 基线」的差值准备，以按需/抢占价计价，可回收
   ────────────────────────────────────────────────
   双轨划算的机制条件只有一条：
      峰值持续时间 T_peak  >  弹性就绪时间 T_ready
   T_peak ≤ T_ready 时：弹性池在峰值期间等于不存在，
      基线被迫按峰值准备，双轨退化成单轨（为峰值全额付费）
   ────────────────────────────────────────────────
   就绪时间 T_ready 的组成（串行，不能只看其中一段）：
      调度 + 节点创建 + 镜像拉取 + 进程启动
      + 缓存/连接池预热 + 模型加载（AI 服务）
   总成本口径（必须换算到同一单位再比较）：
      基线单价 × 8760 h  +  峰值单价 × T_peak × 峰值天数
      （8760 h = 365 × 24，按整年计；这个乘法本身就是推导，不是估计）
```

- **为什么这样设计有效**：因为两段负载被拆到两种计价方式上，所以总成本变成「基线规模 × 长期单价 + 峰值规模 × 短时单价」这个可算的加法——它把「要不要为峰值全额付费」从一个信念变成一次减法。同时基线承担了「弹性来不及」的那部分风险，双轨才真正成立。
- **代价**：两套容量口径要同时维护（两套监控指标、两套 SLO、两套压测场景），分界线的位置也只能由历史数据标定；基线定高了白付、定低了弹性接不住，两个方向的误差都在花钱，而它们的方向相反、需要的证据也不同。
- **失效点**：当**峰值持续时间短于弹性就绪时间**时，优点（成本与承压兼顾）反转成缺点（弹性来不及，峰值期间实际可用容量等于基线），因为弹性不是开关，它由调度、节点创建、镜像拉取、预热这几步串行组成，任何一步的耗时都会推迟可服务时间。修法不是把弹性调快，而是把触发点提前（预测式扩容，见 3.2.5）或把峰值纳入基线。
- **真实使用**：阿里把双 11 容量拆成「基线常驻 + 弹性承接大促增量」两部分准备【公开，转引本目录 [§ 6 落地实践](04-capacity-planning-section-6-sec6.md) 案例（阿里双 11 技术公开材料 2018–2024）】；云厂商的购买选项本身就是这套结构的成本表达（预留实例/节省计划打底、按需兜峰值、抢占式跑可中断任务）【公开，各云厂商计算实例购买选项与抢占式实例文档，以当期文档为准】。
- **AI 时代新增的约束**：推理服务的峰值形状不再只跟随用户作息，而是跟随批处理与训练任务的启动时刻（同一时刻拉起成百上千张卡），所以「基线 / 峰值」的分界要按任务调度来划，而不能只按用户曲线划。
- **上线前必须验证的一件事**：做一次**峰值条件下**的扩容演练，记录从触发到「真的能服务」（不是 Pod 已 Running，而是首批请求成功返回）的完整耗时，把 T_ready 写进容量登记表。

#### 3.2.2 分层容量规划

- **被什么约束逼出来**：系统是多层的（应用层 / 数据层 / 基础设施层 / AI 层），而各层对同一份入口流量的放大倍率并不相同；只看总入口会漏掉先成为瓶颈的那一层，等比例扩容则会在不重要的层上浪费。
- **结构**：

```text
 按层给容量（各层系数来自历史实测，不等比例扩）
   【下列系数转引本目录 § 6 案例给出的阿里双 11 实测值，
     是示例而非通用常数 —— 自己的系数必须自己实测】
   入口     系数 7.0x  → 最先承压，容量要最先到位
   详情     系数 5.5x  → 可缓存、可降级
   加购     系数 3.2x  → 缓存命中率最高的一层
   下单     系数 2.8x  → 强保障，缓存收益低
   支付     系数 2.5x  → 不可降级，冗余要给足
 ────────────────────────────────────────────────
 四类资源并行评估（按下列四层展开；主文件 §2.3 第 7 条「多维度容量评估」
   给的是 CPU / 内存 / 存储 / 网络 / GPU 五个资源维度，属层内细分，与这四层不同）：
   应用层：QPS / 并发 / 响应时间
   数据层：存储量 / IOPS / 带宽
   基础设施：CPU / 内存 / 网络 / GPU
   AI 层：推理 QPS / Token 吞吐 / 模型显存占用
 关键：层的顺序由系数决定，冗余量由「该层能否降级」决定 ——
       可降级层少备（靠降级兜底），不可降级层足备（靠容量硬扛）
```

- **为什么这样设计有效**：因为每单位入口流量在各层的转化率不同，所以「容量」不是单一标量，而是每层各自的一个标量；把它拆开之后，预算就落在会先成为瓶颈的那一层上，而不是均匀地摊在不会成为瓶颈的层上。系数与「可降级程度」联动，还让「多备多少」有了业务依据，而不是给所有层用同一个安全系数。
- **代价**：层的划分与系数维护是一次持续投入（每层都要有人认领、要定期复测），层数越多校准成本越线性；跨层的隐性耦合（连接池、线程池、数据库最大连接数、节点池）会让单层模型失真；层与层之间的变化有传导延迟，某层系数变了不会立刻在其它层体现。
- **失效点**：当**各层消费的是同一份共享资源**时，优点（按层精确分配）反转成缺点（每层都算够了、合起来不够），因为各层的容量上限并不独立——它们抢的是同一个连接池、同一批节点、同一块网卡。此时正确动作是把共享资源本身单列为一层来规划，或者给它做硬隔离（配额、资源池划分），否则各层的「够」只是一种加法错觉。
- **真实使用**：阿里在大促容量规划中按业务漏斗逐层实测放大比，而不是用全链路统一倍数【公开，转引本目录 [§ 6 落地实践](04-capacity-planning-section-6-sec6.md) 案例（2018–2024）】；Netflix 把带宽按「并发观看流数 × 平均码率」换算，而不是按用户数外推——这是其自建分发（Open Connect）公开材料里的带宽量纲，可按关键词「Netflix Open Connect」检索官方页面核验【公开，Netflix Open Connect 官方页面，量纲细节以当期内容为准】。
- **AI 时代新增的约束**：AI 层多了一条别的层没有的硬上限——显存。CPU 超载可以靠排队吸收，显存不足会直接失败，所以 AI 层的容量必须按「最大并发 × 最长序列」这一档算，均值对它没有意义。
- **上线前必须验证的一件事**：用一段**真实重放的流量**（不是合成流量）跑一次全链路，找出第一个触到资源上限的层，看它与容量模型预测的瓶颈层是不是同一层。

#### 3.2.3 业务驱动预测

- **被什么约束逼出来**：新业务没有历史资源曲线可用，但业务侧有可解释的驱动量（用户数、订单量、观看时长、活动排期）；直接外推资源量在新业务上无数据可依，只能从业务量换算。
- **结构**：

```text
 容量 = 活跃用户数 × 人均行为次数 × 单次行为资源开销
        （三个因子分别实测、分别归因，且分业务/分端/分时段）
 因子链（主文件 §2.3 第 2 条「业务驱动预测」的漏斗模型 + 回归模型）：
   GMV 增长 → 订单量增长 → QPS 增长 → CPU/带宽/GPU 需求增长
 ────────────────────────────────────────────────
 乘积形式的两个后果（必须同时记住）：
   ① 可归因：预测偏差能定位到具体是哪一个因子错了
   ② 误差相乘：三个各自 ±10% 的因子，乘积最坏偏差 +33% / −27%
      【推算，推导链：1.1³ = 1.331；0.9³ = 0.729】
      因子每多一个，最坏偏差的区间就再乘一次
 ────────────────────────────────────────────────
 参考量级（用于校验自己的换算是否离谱）：
   并发数 ≈ QPS × 响应时间【推算 + 公开，推导链：Little's Law（Little, 1961）L = λW；
   1000 QPS × 0.1 s = 100 并发】——响应时间变一倍，并发需求也变一倍
```

- **为什么这样设计有效**：因为资源需求被写成乘积，所以每个因子都能单独实测、单独归因——预测偏了以后，团队能回答「是用户数估错了，还是人均行为估错了，还是单次开销变了」，而这是任何校准机制的前提。
- **代价**：因子链越长，误差按乘法累积（三个 ±10% 的因子最坏给出 +33%/−27%【推算，推导链同结构块】），因此必须给每个因子配一条偏差监控，而不是只监控最终预测值；业务量与资源量之间的关系会随架构变化（一次查询改写、一次缓存改造都会改变单次开销），因子要定期复测。
- **失效点**：当**业务结构发生变化**（新入口、渠道结构变化、产品改版、推荐或分发策略调整）时，优点（可换算、可归因）反转成缺点（算得很细，但基数错了），因为系数是从历史行为拟合出来的，而业务变化不产生告警——它只表现为预测持续偏低或偏高，等到有人注意到时，已经跨过了几个容量周期。
- **真实使用**：字节把容量按「用户规模 × 行为强度 × 单次行为开销」三因子建模，并分业务、分端、分时段分别计量【公开，转引本目录 [§ 6 落地实践](04-capacity-planning-section-6-sec6.md) 案例（字节技术博客 2019–2024）】；Netflix 用观看行为与码率作为带宽的驱动量，而不是用户数——它与本条的三因子形式同构：观看行为对应「人均行为次数」，码率对应「单次行为开销」，所以换成三因子建模时它不需要改结构【公开，Netflix Open Connect 官方页面，核验方式见 3.2.2 真实使用】。
- **AI 时代新增的约束**：模型上线本身就是一次业务动作，而它会同时改动「人均行为次数」与「单次开销」两个因子——三个因子里有两个被同一次变更影响，误差不再独立，乘积法的归因能力随之下降。
- **上线前必须验证的一件事**：挑一个历史时点做回测——只用该时点之前的数据预测其后一个月，与真实值比较，并把偏差归因到具体因子；归不到因子的偏差，会在下一次继续发生。

#### 3.2.4 弹性 + 预留混合（采购结构）

- **被什么约束逼出来**：同一份算力的单价随「承诺时长」与「可中断性」剧烈变化，而不同负载对「能不能被中断」的容忍度完全不同；没有任何一种采购方式对全部负载都最优，于是只能把负载与采购方式配对。
- **结构**：

```yaml
# 采购结构（示意；比例须由自己的利用率曲线标定，不要照抄）
commitment:                # 打底：覆盖基线负载
  type: reserved | savings_plan
  coverage: 日常利用率的长期分位（不是峰值，也不是均值）
  break_even: "利用率 > (1 − 折扣率)"   # 见下方推导
on_demand:                 # 兜底：覆盖峰值与不可预测部分
  coverage: 峰值减基线后的差值
spot:                      # 只用于可中断负载
  workloads: [批量离线, 可检查点的训练, 无状态且可重试的任务]
  interrupt_notice: 云厂商给出的中断通知窗口（可配置，务必实测）
  requirement: 检查点间隔 << 中断通知到实际回收的时间
```

- **为什么这样设计有效**：因为预留把「使用时长的波动」换成了「价格的确定性」，所以它的划算条件是**利用率高于盈亏平衡点**——设按需单价为 1、预留价为期付折扣价 (1−d)，承诺期 H 内实际使用 h 小时，则预留划算当且仅当 (1−d) < h/H，即利用率必须超过 (1−d)：折扣 40% 对应盈亏平衡利用率 60%【推算，推导链：预留按期付固定成本、按需按小时计价，两者相等的点解出 h/H = 1−d】。而抢占式把不确定性从「价格」一侧转移到了「可用性」一侧，因此它只对可中断负载成立。两者是两次方向不同的风险转移，不能互相替代。
- **代价**：三类资源并存使容量口径变复杂——必须同时监控「已承诺量、实际用量、被回收量」三个数，否则既看不出浪费也看不出缺口；买错机型、区域或期限的预留无法追回；抢占式负载要做检查点、重试与幂等改造，这是实打实的开发成本。
- **失效点**：当**负载形态在承诺期内变化**（服务下线、机型换代、区域迁移、模型换代导致原 GPU 型号不再合适）时，优点（锁定低价）反转成缺点（锁定的是用不上的资源），因为「以承诺换价」的另一面就是承诺期内无法随形态调整。对抢占式负载还有第二个失效面：当**回收频率高于检查点间隔**时，净收益可能为负——重算与重启的代价会超过省下的差价。
- **真实使用**：抢占式/Spot 实例在回收前会给出可配置的中断通知窗口，因此「周期性检查点 + 抢占式资源」是公开可行的组合【公开，各云厂商抢占式实例的中断行为与通知窗口文档，以当期文档为准】；集群调度层对可中断负载做资源回收与超卖有公开的工程实践【公开，Google Borg 论文（EuroSys 2015）中关于优先级、抢占与资源回收的描述】。
- **AI 时代新增的约束**：训练任务的检查点变得很大（模型权重加优化器状态），检查点本身的存储与写入带宽成为一项新容量，它既不属于在线流量，也不属于离线流量，最容易被漏计。
- **上线前必须验证的一件事**：在真实峰值时段做一次抢占回收演练，记录从收到中断通知到任务恢复训练的实际损失（时间与算力），再与省下的差价比较——这个比值才是抢占式能不能用的依据。

#### 3.2.5 AI 辅助决策

- **被什么约束逼出来**：可解释的人工建模（趋势 + 季节 + 节假日叠加）与非线性的模型（能捕捉多变量与突变）各有所长；同时模型输出的是「条件下的期望」，而容量决策最终要的是一句能被签署的承诺——这个差距只能由人来补，所以 AI 必须被放在流程中特定的位置上。
- **结构**：

```text
 历史指标 + 业务计划（排期/活动/内容上线）
        │
        ▼
   特征管线 ──► 预测模型（输出带区间）──► 资源组合推荐 ──► 人签署
        │                    │                    │
   漂移监控            区间宽度决定         风险边界（guardrail）：
   重训 / 回滚          该给多少冗余          推荐值被夹在业务可达区间内
        ▲
        │
   异常检测（异常流量 / 异常消耗）──► 触发复核与校准，不直接改容量
 ────────────────────────────────────────────────
 AI 不进入的环节：故障时的取舍、跨团队的成本归属、承诺的对外表述
 预测式扩容的真正作用：把扩容指令提前，让 T_ready 落在 T_peak 之前
 自然语言接口：对容量登记表提问（「下季度 GPU 够不够用」）
      —— 只做查询与解释，读的是既有数字，不产出可签署的承诺
```

本模式由四个子能力组成，它们的边界必须分开，混在一起就会出现「让模型既预测又承诺」的越界：

- **AI 预测**：唯一向前看的一项，输出带区间的需求预测，负责「会涨到多少」。
- **AI 推荐资源**：把预测的区间换算成资源组合（机型、比例、购买方式），受 guardrail 夹取，负责「买什么」。
- **AI 异常检测**：只对**已经发生**的偏离做识别（异常流量、异常消耗），输出的是「这条曲线不像平常」而不是「接下来会怎样」，动作是触发复核与重训，不直接改容量——它与预测的分工是「事后发现」对「事前估计」，两者互为对方的反馈回路。
- **AI 自然语言接口**：对容量登记表做查询与解释（「下季度 GPU 够不够用」「为什么估了这么多」），降低的是读数的门槛；它读的是既有数字，本身不产生判断，因此它把模型的价值放大，也会把错误的口径同样放大。

- **为什么这样设计有效**：因为模型输出的是区间而不是点，所以它改变的是「冗余怎么分配」与「扩容指令什么时候发」，而不是「要不要留冗余」——它把方差从「未知」变成「可估」，但不会把方差变成零。而预测式扩容之所以有效，恰恰是因为它不改变扩容速度，只改变扩容的起点。
- **代价**：特征管线与模型运维（漂移监控、重训、回滚、版本管理）本身就是一条新的生产链路，它自己也要被规划容量；可解释性下降会让决策者在区间变宽时退回经验值（于是模型的边际价值被自己吃掉）；模型的推理与训练开销也要计入成本，形成一个自指的约束。
- **失效点**：当**发生分布外事件**（政策变化、突发事件、渠道改版、产品重构、竞品动作）时，优点（拟合历史、自动捕捉周期性）反转成缺点（在最需要判断的那一刻给出一个自信而错误的数），因为训练分布不覆盖该事件，模型会把异常平滑成「看起来合理」的值。判据很直接：**最近一次需要人工推翻模型输出是什么时候、依据是什么**——从未发生过，说明模型只被用来确认既有判断。
- **真实使用**：Prophet 是公开开源的时间序列工具，设计上把趋势、季节与节假日拆成可解释的项【公开，Prophet 官方开源仓库与其论文（Taylor & Letham）】；KEDA 的 cron 触发器提供按日历时段的扩缩，是「预测式扩缩」最朴素且在生产的形态【公开，KEDA 官方文档 · cron trigger】；Kubernetes 的 HPA 给出副本数的计算公式与默认容忍度【公开，Kubernetes 官方文档 · Horizontal Pod Autoscaler，公式与默认值以当期文档为准】；异常检测一侧的算法族（统计的 Z-Score / IQR / 3σ 原则，机器学习的 Isolation Forest / One-Class SVM，深度学习的 Autoencoder）在主文件 §2.3 第 3 条「异常检测」中列出，均为公开可查的通用方法【公开，主文件 §2.3 第 3 条「异常检测」】；自然语言接口这一层目前只见于各家 AI 助手类产品与内部平台的演示，没有可比口径的规模数据，按【经验】。
- **AI 时代新增的约束**：AI 负载的单次开销会随上下文长度、批大小、量化策略持续变化，模型要预测的分布本身漂移得比传统业务快——这既是 AI 辅助规划最有用的地方，也是它最容易过期的地方。
- **上线前必须验证的一件事**：检查预测的**区间**有没有被用于决策。若所有决策都只看点预测、从不看区间宽度，等于把一个随机变量当成了已知量，冗余就无法随不确定性调整。

#### 3.2.6 多云容量管理

- **被什么约束逼出来**：单一供应商的配额上限、机型可得性与价格成为天花板，同时合规可能要求资源或数据落在特定地域；跨供应商可以缓解供给约束，但会引入新的持续成本。
- **结构**：

```text
 按「可迁移性」给每一层资源定位（不是按价格表定位）
   ┌ 无状态计算 ────────────── 可迁移：容器 / 无服务器 / 批量任务
   │   ↑ 迁移成本一次性、可控
   ├ 有状态数据 ────────────── 迁移成本持续：出网费 + 延迟 + 一致性
   │   ↑ 搬一次很贵，搬来搬去更贵
   └ 托管服务/专有芯片 ─────── 事实不可迁移：改造量 = 重写
 ────────────────────────────────────────────────
 控制面统一：IaC（同一份声明部署到多云）+ 统一配额与监控视图
 数据平面就近：数据落在哪，计算就尽量落在哪 —— 跨区流量是持续支出
 决策顺序：先问「数据能不能动」，再问「哪家便宜」
```

- **机制（为什么这样设计有效）**：因为算力可以搬走而数据的持续迁移要付带宽与延迟，所以多云的可行边界由**数据所在位置**决定，而不是由价格表决定——你能搬走的是无状态计算，搬不走的是有状态数据以及它产生的跨区流量。反过来，把可迁移的部分真搬走，确实能在供给与议价上获得选择权，这是它唯一的正收益来源。
- **代价**：控制面翻倍（两套 IAM、网络、配额、镜像、合规基线、监控与值班），故障定位要跨两个厂商的能力边界；跨云流量费与延迟是持续项；运维技能面变宽，等效于增加了组织的最小规模。
- **失效点**：当**工作负载与某供应商的托管服务深度绑定**（托管数据库、托管消息、专有 API、专用加速芯片）时，优点（可迁移、可议价）反转成缺点（迁移成本远超差价），因为可迁移性在架构选型那一刻就已经被放弃了——后面再做迁移，等于重写而不是搬迁。
- **真实使用**：跨云出网费用是各云厂商价目表中公开的一项，可直接用自己当前的实际流量做乘法估算【公开，各厂商网络出网价目页】；混合云与多云是主流云厂商公开支持的架构方向【公开，各云厂商混合云/多云官方文档】。可自行核验的判据：**列出你的有状态数据总量与月度跨区流量，再乘上双方的出网单价**——这个数若接近甚至超过你预期省下的差价，多云在你的场景里就只剩供给保障这一个理由。
- **AI 时代新增的约束**：加速卡的可得性还受供应链与出口管制这类非技术因素影响，弹性技术对它无效【经验，具体情形随政策与时间变化，请以当期公开信息为准】；这让「可迁移性」的价值上升，同时也让「数据就近」这条约束更硬。
- **上线前必须验证的一件事**：用自己最近一个月的真实跨区/跨云流量乘上双方出网单价，算出多云每年多付的钱，并与预期省下的差价对比；同时列出所有绑定在某家托管服务上的组件，它们是「不可迁移」的那部分。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 稳态业务：波动小、增长慢、内部系统 | 3.2.1 基线 + 峰值双轨（峰值档取小），采购上偏预留 | 上弹性调度与预测模型的运维成本高于收益 | 基线利用率是否长期高于盈亏平衡点 |
| 周期性业务（电商）：有明显季节与节假日效应 | 3.2.3 业务驱动 + 3.2.2 分层（按漏斗逐层算系数） | 只做时间序列会把「活动排期」当成噪声，而它是这类业务最大的自变量 | 排期/活动是否被作为显式输入 |
| 突发流量（直播、热点事件）：上升时间分钟级以内 | 3.2.1 双轨（基线覆盖到能承受的档位）+ 预测式扩缩提前触发 | 纯响应式扩容的就绪时间追不上脉冲，弹性会「一直在扩但一直不够」 | 实测的 T_ready 与历史最快上升时间的对比 |
| AI 推理服务：单次开销可变（请求长度/模型档位） | 3.2.3 换算（请求数 × Token 数 / 单卡吞吐 × 利用率）+ 分层到 AI 层 | 按 QPS 规划 GPU 会系统性低估：QPS 不变而序列变长时显存与算力需求同时上升 | 是否按 Token 而非请求数建模 |
| AI 训练：可中断、可检查点 | 3.2.4 抢占式 + 常量部分用预留 | 全价买训练算力会为大量空闲时间付费；但把不可中断的在线推理放到抢占式上会直接伤可用性 | 检查点间隔是否远小于中断通知到回收的时间 |
| 大数据离线：批处理、有明确窗口 | 3.2.1 双轨 + 3.2.4 抢占式，并把窗口对齐到在线低峰 | 用同一套资源承载在线与离线会把两条互不相关的高峰叠在一起 | 离线窗口是否与在线峰值错开 |
| 内部系统：无明确 SLO、可用性容忍度高 | 简单基线 + 预留，不做弹性 | 弹性与多云的复杂度会超过它节省的成本 | 停机 1 小时的业务损失是否可忽略 |
| 新业务无历史曲线，但有同构的老业务 | 3.2.3 业务驱动，单次开销因子借用老业务 | 纯时间序列在新业务上没有可拟合的序列 | 老业务的单次开销是否真能迁移（架构是否同构） |
| 在线与离线峰值天然错开 | 3.2.1 双轨 + 谷时复用（低峰转给离线与训练） | 不利用错峰等于为同一批资源付两次费用 | 在线与离线的峰值时段重叠度有多大 |

表中最常被误选的一对是 **3.2.1 基线 + 峰值双轨与 3.2.4 弹性 + 预留混合**。两者画出来都是「预留打底 + 弹性兜峰值」，看起来只差一个词，实际回答的是两个不同问题：前者回答**要准备多少容量**，后者回答**这些容量以什么价格买下来**。误选的后果有两种，都很具体：一是用采购结构替代容量模型——买到了一堆折扣份额，但总量本身估错，省下的钱被超卖与临时按需补货吃掉；二是只算总量不看采购结构——业务里大半算力是可中断的批量任务，却全部按预留买下，为「不会被中断」这个用不上的性质付了全额。

读这张表的正确顺序是从「关键判据」一列倒着读：先量出自己的 T_ready、利用率分布、可中断比例，再去找匹配行。另外提醒一句：**推荐模式这一列不是排他的**——同一家公司完全可以对交易链路用双轨加预留、对训练任务用抢占式、对报表用冷热分层，按负载类型分级规划本身就是正确做法；用一套统一策略覆盖全部负载才是反模式（见 3.5 的「忽视冷数据」）。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：容量结构（3.2.1）× 价格结构（3.2.4）**。构成：双轨决定基线池与峰值池的规模，采购结构决定这两池分别用什么承诺与计价方式买下来。职责边界必须写清：**先算量，再算价**——顺序反了就会出现「因为预留便宜所以多买」的倒推。运维代价：两套口径（容量口径与成本口径）要能对上账，否则月度账单与容量报告各说各话；适合任何规模，也是最小可行的起点。

**组合 B：分层（3.2.2）× 业务驱动（3.2.3）**。构成：业务驱动回答「总量会长到多少」（横向），分层回答「哪一层会先成为瓶颈」（纵向），两者相乘才是一份可执行的扩容清单。职责边界：业务驱动给出的总量必须被逐层分解，否则你只知道要加资源、不知道加在哪；分层给出的系数必须以业务量变化重新校准，否则系数会随时间失效。运维代价：系数与因子两套参数都要有人维护与复测；适合多业务共用基础设施的中等以上规模。

**组合 C：预测式扩容（3.2.5）× 压测与事后校准**。构成：模型与排期给出「什么时候开始扩、扩到多少」的假设，全链路压测与事后复盘给出事实；每一次峰值之后用实测值回填模型参数。职责边界：模型只负责提前量与推荐值，压测负责回答「单机到底能扛多少」这个模型推不出来的数。运维代价：压测环境要长期保持与生产同构，否则压测结论不可迁移；适合有明确峰值事件、且愿意为一次压测付出环境的规模。

三条组合之间有一条硬性顺序：**先有量与价（组合 A），再有粒度（组合 B），最后才是预测工具与压测（组合 C）**。反过来从预测模型起步的团队，常在第一次真实峰值后才发现两件事：没有一个地方记录了「单机能扛多少」，也没有一处能说清「多备一份的边际成本是多少」——预测精度再高，也补不上这两个空白。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 拍脑袋扩容 | 扩容方案里的数字来自「上次大概是这么多」；复盘中无法说明估算依据 | 资源量与实际需求双向偏离，且偏差不可解释、不可收敛，每年重复同一个误差 | 历史数据没被留存或没被对齐到业务量上，估算成为唯一可行手段 | 每个数字给出因子与来源，事后用实测值回填（3.2.3 + 3.2.5） |
| 只看均值 | 容量报告的结论是「平均利用率 30%，够用」；P99 延迟却在峰值时段超标 | 均值掩盖峰值分布，容量在尾部失效；而排队延迟恰恰由尾部决定（等待时间 ∝ ρ/(1−ρ)） | 均值是最容易取到的数，而 P99 与长尾需要按时间桶与分位做聚合 | 按峰值分位与时间桶评估，把峰值利用率作为主指标 |
| 忽略业务变化 | 用去年同期的流量曲线外推今年；活动排期与产品改版不在输入里 | 基数或系数已失效，模型给出的仍是历史形状的答案，误差持续单向累积 | 业务动作发生在业务侧，没有被接入容量流程，也没有触发重新校准 | 业务排期/上线/改版进容量输入，并设月度滚动校准（3.2.3 失效点） |
| 弹性扩容慢 | 实测扩容耗时远长于峰值持续时间；峰值期间一直是「正在扩容」 | 弹性在峰值窗口内不可用，容量实际由基线决定，双轨退化成单轨 | 只配置了扩容策略，没有实测 T_ready，也没有把镜像预热与缓存预热算进耗时 | 预测式扩容提前触发 + 预热（镜像/缓存/连接池/模型）+ 压测验证 T_ready（3.2.1 失效点） |
| GPU 资源浪费 | 每个 AI 服务独占 GPU；GPU 利用率长期处于低区间 | 单位推理成本被闲置吃掉；受采购周期约束的稀缺资源被低效占用，无法用弹性补救 | 推理服务按「一服务一卡」部署，缺少池化与并发复用（batching）能力 | GPU 池化 + 推理优化（量化、批处理、显存复用）+ 按 Token 建模 |
| 忽视冷数据 | 所有数据都在高成本介质上；存储成本随保留期单调增长且无人认领 | 存储是唯一随时间长青的成本项，介质单价差会按期数放大；容量报告里它被当作常量忽略 | 冷热迁移需要访问模式数据，而在线链路优先，存储分层被一直推迟 | 按访问分布做冷热分层（热/温/冷对应 SSD/HDD/对象存储），并把保留期与介质绑定 |

其中四个最危险，值得单独展开：

**「弹性扩容慢」是唯一一个「配置存在但能力不存在」的反模式。** 它的典型暴露方式不是扩容报错，而是峰值期间的监控曲线：副本数确实在涨，但业务指标一路恶化到峰值结束——涨得太晚。机制上的原因很直接：就绪时间是**串行**的（调度 → 节点创建 → 镜像拉取 → 启动 → 预热），而其中每一步都可能因为峰值时刻的集群整体繁忙而变慢——峰值不仅让业务变慢，也让扩容变慢。所以 T_ready 必须在峰值条件下实测，而不是在平峰时测一个乐观值。

**「只看均值」的隐蔽性来自它每天都在被复述。** 容量报告、成本报告、资源看板默认都用均值，于是「平均利用率 30%」这类数字会进入所有评审材料，成为事实上的共识。机制上的后果是：团队据此做出「不需要扩容」的判断，而真实约束在尾部——等待时间随利用率非线性上升（ρ 从 0.7 到 0.9，等待时间从约 2.33 倍服务时间升到 9 倍【推算，推导链见 3.1】），所以均值 30% 与峰值 90% 可以同时成立，而后者才是事故的来源。

**「忽视冷数据」是最容易被漏进容量报告的一项。** 别的资源都会在忙时暴露短缺，存储不会——它只会在账单上安静地增长。它的典型暴露方式是年度成本复盘时发现存储占了大头，而其中大部分数据在过去一个季度里没有被读过一次。修法不需要复杂技术，需要的是把「访问分布、保留期、介质」三个字段放到同一张容量登记表里，让分层成为一次有依据的决策而不是一个口号。

**「GPU 资源浪费」的根因通常不是采购，而是部署形态。** 「一服务一卡」时，GPU 的利用率由该服务自己的流量决定，而不是由这张卡的能力决定；机制上，加速卡的效率只在批处理下才体现——单请求推理会把大量时间花在等待与显存搬运上，算力单元大部分时间是空的。所以修法要两个方向同时做：池化（多个服务共享一个池，靠调度错峰）与批处理（把并发请求合并成一次前向）。可自行核验的判据是**批大小分布**：如果绝大多数请求的批大小长期是 1，那么池化与推理优化的空间一点都还没被用上。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 日均模型 → 需要按小时/时段建模 | 单峰或日均容量 | 两个高峰之间的谷被低估、峰被平均掉，容量既不够又浪费 | 分时段建模，识别各峰形状差异（早峰陡、晚峰宽） | 采集粒度从日降到小时并长期留存；运维排班与资源调度要跟着时段走 |
| 全局总量 → 局部（城市/区域/租户）独立规划 | 一套全局容量 | 全局总量够，但局部爆掉；平均掩盖了分布 | 按地理或租户粒度独立规划容量 | 规划对象数量随地理/租户数量增长，报告必须自动化生成 |
| 资源月度购买 → 需要分钟级弹性 | 预留为主 | 峰值上升时间缩短到弹性就绪时间以下 | 增加弹性池 + 预测式扩容 + 预热 | 需要镜像与缓存预热机制、以及集群层面的空闲容量预算 |
| 单一负载 → 在线与离线混跑 | 一套容量承载全部负载 | 两条互不相关的高峰叠加，谷时的资源空转 | 错峰复用：低峰把资源转给离线与训练 | 调度优先级与抢占机制；离线任务的完成时间变得依赖在线负载 |
| 业务量可估 → 出现不可预测的突发 | 历史外推 | 分布外事件发生时，外推给出的仍是历史形状的答案 | 外部因素（天气、活动、内容上线）作为预案触发条件，而不是靠现场判断 | 需要预案库与触发源；每次触发都要复盘是否值得 |
| CPU/存储为主 → GPU 成为主要成本 | 按 QPS 与容量换算 | 单次开销可变（序列长度、模型档位），按请求数建模系统性低估 | 按 Token 吞吐与显存建模，并把训练与推理的资源边界划开 | 需要新的指标采集（Token/秒、显存、批大小）；采购周期长，弹性无法兜底 |
| 自有可控 → 多云/混合云 | 单云采购 | 配额与机型可得性成为天花板，同时数据位置带来合规约束 | 无状态计算跨云 + 有状态数据就近（3.2.6） | 控制面翻倍；跨云流量费与延迟成为常态成本项 |
| 人工决策 → 需要可复盘的决策 | 口头估算 | 误差无法归因，逐年重复同一个错误 | 容量登记表（量与价、因子与来源、校准记录可查） | 记录与校准的持续投入，短期看不到收益 |
| 单次开销稳定 → 单次开销可变 | 按请求数换算容量 | 请求数不再是守恒量，按它建模会系统性低估 | 按真开销量（Token 数 / 字节 / 耗时）建模 | 需要新增指标采集，建模口径与看板要一起改 |
| 按需购买 → 配额成为上限 | 弹性扩容 | 弹性受配额约束，而配额审批有前置时间，峰值当天申请来不及 | 提前申请配额 + 关键容量以常驻方式锁定 | 配额管理成为容量流程的固定一环，需要专人跟进 |
| 单模型档位 → 多档位混跑 | 一套容量池 | 不同档位的资源画像差异大，混跑会互相挤占（大模型的显存挤掉小模型的并发） | 按档位分池或做路由隔离，小模型下沉到更便宜的硬件 | 路由与池化改造；效果与成本的取舍需要与业务共同决定 |

一句话总结这一节：**模式不是被「规模」推动升级的，是被三个约束的变化推动的——流量上升的时间尺度、单次请求开销是否稳定、以及资源的可得性由谁决定。** 其中第二条最容易被忽略，而它恰恰决定「按 QPS 规划」这套最常用方法在 AI 负载上还能不能成立。

### 3.7 自检清单

- [ ] 是否实测过**扩容就绪时间 T_ready**（含节点创建、镜像拉取、缓存与模型预热），且是在峰值条件下测的？
- [ ] 历史最快的一次流量上升用了多久？它与 T_ready 的比值是多少，是否小于 1？
- [ ] 容量报告的主指标是**峰值利用率**还是均值？有没有 P99 延迟与峰值时段的对应关系？
- [ ] 每个容量数字是否都能说出它的**因子与来源**（是实测、是业务换算、还是经验）？
- [ ] 单机/单实例的承载能力（QPS、连接数、Token/秒）是否有实测值，而不是来自规格书？
- [ ] 业务排期、活动、内容上线、产品改版是否作为容量模型的**显式输入**？
- [ ] 基线容量占长期承诺资源的比例是多少？基线利用率是否高于盈亏平衡点（1 − 折扣率）？
- [ ] 可中断负载的比例是否统计过？被放到抢占式资源上的，是否只有可中断负载？
- [ ] 抢占式负载的**检查点间隔**是否远小于中断通知到实际回收的时间？
- [ ] AI 服务是按请求数还是按 **Token 数与显存**建模？同一服务的单次开销波动有多大？
- [ ] 存储的访问分布、保留期与介质是否在同一张表里？冷数据的占比与介质单价是否被单独列出？
- [ ] 上一次预测与实际值的偏差是多少、归因到哪个因子？校准记录能否被调取？

这 12 条里，第 1、2、4 条是「决定其余各条是否还有意义」的三条：T_ready 不知道，弹性与基线怎么分都是猜；比值不知道，双轨结构就没有依据；数字说不出来源，校准就无从下手。其余各条都可以边做边补，这三条拖不得。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 峰值上升慢（小时级）、日常波动小 | 基线 + 峰值双轨，采购偏预留 | 弹性来得及，双轨把「为峰值全额付费」变成可算的减法 |
| 峰值上升快（分钟级以内） | 基线覆盖到可承受档位 + 预测式扩容提前触发 | 就绪时间是串行的，峰值下还会更慢；提前触发比加快扩容更可行 |
| 各层放大比不同、有明确瓶颈层 | 分层容量规划 | 容量是每层各自的标量；按层分配才能把钱花在瓶颈层上 |
| 新业务、无历史曲线 | 业务驱动预测（乘积形式） | 因子可实测、可归因；代价是误差相乘，需给每个因子配偏差监控 |
| 负载可中断、有明确窗口 | 弹性 + 预留混合（含抢占式） | 预留的盈亏平衡由利用率决定；抢占式只对可中断负载成立 |
| 单次开销可变（AI 推理） | 按 Token 与显存建模，而不是按请求数 | 序列长度变化时 QPS 不变而需求翻倍；请求数不是守恒量 |
| 单供应商配额成为天花板 | 先算数据搬不动的代价，再决定是否多云 | 可迁移的是无状态计算，搬不走的是数据与它的跨区流量 |
| 需要可复盘、可归因的决策 | 容量登记表（量、价、因子、校准记录） | 校准的前提是历史值可查；没有记录就没有收敛 |

这张表里最后一行值得单独强调：它既不是模式也不是工具，而是**前面所有模式能不能收敛的前提**。容量规划与其它架构主题最不同的一点是——它的输出会被真实数据检验（峰值当天就知道估准没估准），所以它的进步方式是「记录 → 对比 → 校准」这一循环，而不是「换一个更强的模型」。没有记录的组织，换什么预测算法都会得到同一个结果：每年重新估一次，然后每年错在同一个地方。

> 本节小结：本主题下决定模式选择的**唯一那条约束**是——**你的弹性就绪时间能不能短于流量上升时间**。能，容量可以被拆成「常驻基线 + 弹性峰值」，预测的价值在于把扩容指令提前；不能，峰值就必须以常驻资源的形式提前买下，预测的价值在于决定买多少。其余约束（采购折扣、分层系数、可中断比例、多云与否）都在它之下做微调——而它们全部依赖同一件事：**这些数字有没有被实测过并记录下来**。
