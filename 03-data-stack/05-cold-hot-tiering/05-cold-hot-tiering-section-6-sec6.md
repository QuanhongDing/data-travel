### 5.1 Netflix"**S3 + Glacier 三层分层**"8+ 年（2016-2024）

**背景（Why）**

Netflix 2016 年面临**存储成本爆炸**：
- **EB 级数据**——每月 S3 成本**千万级美元**
- **80% 数据访问少**——但全部放 S3 Standard
- **归档需求**——合规要求**7 年留存**

**触发点（What）**

2016 年 Netflix 推出**三层分层**（S3 Standard + S3 IA + Glacier）（[Netflix 2016]），目标：
- **存储成本 -60%**
- **访问延迟可控**
- **生命周期自动化**

**详细做法（How）**

Netflix 三层分层的**5 大核心组件**：

1. **热层：S3 Standard（核心）**
   - 关键设计：**最近 30 天** + 频繁访问
   - 关键能力：**毫秒级访问**
   - 关键数字：**覆盖 20% 数据**

2. **温层：S3 IA（核心）**
   - 关键设计：**30-90 天** + 偶尔访问
   - 关键能力：**秒级访问** + 成本减半
   - 关键数字：**覆盖 50% 数据**

3. **冷层：Glacier（核心创新）**
   - 关键设计：**90 天+** + 几乎不访问
   - 关键能力：**小时级恢复** + 成本再减 80%
   - 关键数字：**覆盖 30% 数据**

4. **生命周期自动化（核心）**
   - 关键设计：**S3 Lifecycle 规则** + **自动转换层**
   - 关键能力：**零人工**
   - 关键数字：**自动化 100%**

5. **查询兼容（核心创新）**
   - 关键设计：**Athena / Trino 全层查询** + **S3 Select 单层读取**
   - 关键能力：**业务无感**
   - 关键数字：**查询兼容 100%**

**Netflix 三层分层关键数字**（[Netflix 2016-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **存储成本** | 基线 | -60% | **-60%** |
| **热层访问** | 不可用 | 毫秒级 | **∞** |
| **冷层成本** | 基线 | -80% | **-80%** |
| **生命周期** | 不可用 | 100% 自动化 | **∞** |
| **查询兼容** | 不可用 | 100% | **∞** |
| **EB 级** | 不可用 | 100% | **∞** |
| **7 年留存** | 不可用 | 100% | **∞** |
| **归档合规** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：Netflix S3 / 存储团队 50+ 人
- 关键数字：**EB 级**；**存储 -60%**；**全自动化**
- 业务影响：覆盖**Netflix 全球 2 亿+ 用户**

**失败教训**

- 早期「**全部 S3 Standard**」——成本爆炸，倒逼三层
- **冷层恢复太慢**——Glacier 取回小时级，**业务第一次用就崩**；后**预热 + 主动取回**
- **生命周期规则设错**——把热点数据自动归档到冷层，**查询慢 100 倍**；后**按访问频次自动判定**

### 5.3 字节"**湖仓分层 + 列存压缩**"4+ 年（2020-2024）

**背景（Why)**

字节 2020 年面临**湖仓一体后的存储优化**：
- **PB 级数据**——Iceberg + Parquet
- **冷热不分**——全部 Standard

**触发点（What）**

2020 年字节启动**湖仓分层**（[字节 2020]），目标：
- **存储 -40%**
- **冷热自动迁移**

**详细做法（How)**

字节湖仓分层的**5 大核心组件**：

1. **Iceberg 表格式（核心）**
   - 关键设计：**Parquet 列存 + Zstd 压缩**
   - 关键能力：**PB 级 + 高压缩比**
   - 关键数字：**压缩比 5x**

2. **冷热分层（核心创新）**
   - 关键设计：**最近 30 天** → SSD；**30-90 天** → HDD；**90+ 天** → 对象存储
   - 关键能力：**自动迁移**
   - 关键数字：**成本 -40%**

3. **列存压缩（核心）**
   - 关键设计：**Parquet + Zstd + 字典编码**
   - 关键能力：**压缩比 5x**
   - 关键数字：**存储 -60%（同数据）**

4. **生命周期（核心）**
   - 关键设计：**Iceberg expire_snapshots** + **数据自动清理**
   - 关键能力：**零人工**
   - 关键数字：**自动化 100%**

5. **查询兼容（核心创新）**
   - 关键设计：**StarRocks / ClickHouse 全层查**
   - 关键能力：**业务无感**
   - 关键数字：**查询 P99 < 3s**

**字节湖仓分层关键数字**（[字节 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **存储成本** | 基线 | -40% | **-40%** |
| **压缩比** | 1x | 5x | **+5x** |
| **热层** | 不可用 | 毫秒级 | **∞** |
| **冷层** | 不可用 | 100% | **∞** |
| **生命周期** | 不可用 | 100% | **∞** |
| **查询兼容** | 不可用 | 100% | **∞** |
| **PB 级** | 不可用 | 100% | **∞** |
| **Lakehouse 分层** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：字节存储团队 100+ 人
- 关键数字：**PB 级**；**压缩 5x**；**存储 -40%**
- 业务影响：覆盖**字节全部业务**

**失败教训**

- 早期「**冷热不分**」——全部 Standard，成本爆炸，倒逼分层
- **冷层恢复慢**——对象存储秒级，**业务首次用崩**；后**预热 + 主动取回**
- **列存压缩参数错**——压缩比过低，**存储 -20% 不达预期**；后**调参 + Benchmark**

### 5.4 Snowflake"**Time Travel + 自动化分层**"8+ 年（2016-2024）

**背景（Why)**

Snowflake 2016 年面临**云数仓存储成本**：
- **客户存储爆炸**——PB → EB 级
- **冷热不分**——成本高
- **合规要求**——**Time Travel + 不可变存储**

**触发点（What）**

2016 年 Snowflake 推出**自动化分层 + Time Travel**（[Snowflake 2016]），目标：
- **存储成本 -70%**
- **Time Travel 90 天**
- **自动化**

**详细做法（How)**

Snowflake 分层的**5 大核心组件**：

1. **Standard 层（热）**
   - 关键设计：**最近 90 天 + 频繁**
   - 关键能力：**毫秒级**
   - 关键数字：**20% 数据**

2. **Snowpark / Iceberg 外部表（温）**
   - 关键设计：**90-365 天**
   - 关键能力：**秒级 + 成本 -50%**
   - 关键数字：**50% 数据**

3. **Archive（冷层创新）**
   - 关键设计：**365+ 天** + 几乎不访问
   - 关键能力：**分钟级恢复** + 成本 -90%
   - 关键数字：**30% 数据**

4. **Time Travel（核心）**
   - 关键设计：**90 天可回滚 + 不可变存储**
   - 关键能力：**Time Travel + 审计**
   - 关键数字：**10000+ 客户**

5. **自动化（核心创新）**
   - 关键设计：**按访问模式自动判定**
   - 关键能力：**零人工**
   - 关键数字：**自动化 100%**

### 5.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**S3 Standard 或 OSS Standard 起步**」（**最简单**）——**10+ 业务**
- 关键设计：**生命周期规则 + 自动迁移**
- 团队：**2-3 人**
- 验证标准：**成本下降**、**查询延迟可接受**

**1 → 10 阶段：6-12 个月**

- 扩展到「**PB 级 + 三层分层**」
- 引入「**自动判定冷热**」
- 引入「**列存压缩（Parquet + Zstd）**」
- 团队：5-10 人
- 验证标准：**存储 -40%**、**查询兼容**

**10 → 100 阶段：12-24 个月**

- 扩展到「**EB 级**」
- 引入「**Time Travel + 不可变存储**」
- 引入「**Archive 冷层**」
- 团队：10-30 人
- 验证标准：**存储 -70%**、**EB 级**

**100 → 1000 阶段：12-24 个月**

- 引入「**全自动化分层 + 跨云**」
- 团队：30-100 人
- 验证标准：**10000+ 客户**、**IPO**

---

> **本节小结**：
> - 4 个真实案例（Netflix / 阿里云 / 字节 / Snowflake）印证：**冷热分层不是「**全部 Standard**」，是「**Standard + IA + Archive + 列存压缩 + 自动化**」**5 件套**。
> - 关键时间线：Netflix 8+ 年 / 阿里云 6+ 年 / 字节 4+ 年 / Snowflake 8+ 年 —— **冷热分层是 4+ 年长期工程**。
> - 选型第一原则：「**S3 / OSS Standard + 生命周期规则**」（**最简单**）——**10+ 业务** → 「**三层 + 列存压缩**」（**必须**）→ 「**EB 级 + Time Travel**」（**生产**）→ 「**全自动化 + 跨云**」（**AI 时代**）。
> - 99% 的失败来自「**冷热不分 + 冷层恢复慢 + 生命周期规则错**」——必须有 **三层 + 自动判定 + 预热**。
> - 真正的 ROI 来自「**存储 -70% + 压缩 5x + 10000+ 客户**」——是**大厂核心存储分层基础设施的命脉**。
