## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

「业务场景 → 推荐模式 → 典型技术栈」的决策表，读起来像「按场景挑一个」，但分层方案不是被场景挑出来的，是被约束推出来的。同样落在「云原生、要分层」这一格的两家公司，一家有完整的访问日志采集，可以用「多久没被读过」当判据；另一家没有，只能退回「业务标注 + 年龄」（[§7.3.1](05-cold-hot-tiering-section-7-sec7.md)）。两者的实现、运维面、事故形态完全不同，却共用同一个推荐格。

权重最高的一条约束不是数据量，而是**分层引擎能观测到什么信号**。引擎要迁移数据，必须先判断一块数据冷不冷，而可用的信号只有三类：写入时间（元数据里就有，最廉价）、最近访问时间（要持续采集，最贵）、对未来的预测（要有访问序列与回测）。因为写入时间是一个与访问热度无关的量，所以以它为主判据的规则必然误归档——这是本章所有模式分野的起点。

第二条约束是**分层动作由谁执行**：存储服务执行（声明式规则，没有搬运作业）、分布式文件系统执行（块级存储策略）、开放表格式执行（文件与清单）、人执行（脚本或手动搬）。执行位置决定了分层能不能对查询层透明，而不透明是分层被绕过的主因（[§7.3.3](05-cold-hot-tiering-section-7-sec7.md)）。

第三条约束是**取回能等多久**。归档档的取回是异步且按量计费的（[§7.3.2](05-cold-hot-tiering-section-7-sec7.md)），这一条不满足时，省钱的动作会直接变成事故：只要存在「可能被临时调用」的数据，进归档档的第一次调用就是小时级等待。

第四条约束是**团队技能与运维能力**。同一个分层方案，在有专人负责数据平台的团队里能跑十年，在三五人的团队里三个月就无人维护、成本静默反弹（[§7.1](05-cold-hot-tiering-section-7-sec7.md)）。这条约束不会出现在任何技术选型表里，却往往权重最大——它决定的不是「规则设计得对不对」，而是「规则能不能长期活下去」。

把四条约束合起来看，本主题的底层机制只有三个变量：**判据是什么信号**（写入时间 / 访问行为 / 预测）、**执行者是谁**（存储服务 / 文件系统 / 表格式 / 人）、**取回通道要多久**（即时 / 分钟到小时 / 需调度）。7 个模式就是这三个变量在不同取值下的组合；换句话说，模式之间的差别不是「谁更强」，而是「各自把哪一维的代价放在了账面的哪一侧」。

上面四条是判据层面的约束；把同一个问题拆成可逐行核对的清单，是下面六行——前四行决定候选集与可行性，后两行决定这件事值不值得做。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式 | 分层粒度是块、对象、分区还是文件 | 「分层就是换个存储类」——高频更新与追加写的分层动作完全不同 |
| 访问模式（点查 / 扫描 / 聚合） | 跨层查询能不能被业务接受 | 「透明就是好」——点查落到归档档时，透明等于看不见的慢 |
| 变更频率与历史要求 | 分层与版本回收能不能共用流程 | 「省钱顺便清历史」——两者共用同一批文件，耦合后不可逆（[§7.3.4](05-cold-hot-tiering-section-7-sec7.md)） |
| 一致性要求 | 同一份数据能不能存在两套命名空间 | 「双栈只是多一套权限」——跨栈搬运路径一旦缺校验，会出现冷侧缺文件、热侧已删除 |
| 规模与成本约束 | 值不值得分层、能上几档 | 「分层一定省钱」——1 TB 下沉对象存储标准层的年节省约 $24（【推算】1000 GB × ($0.30 − $0.023 × 12) = 1000 × 0.024 ≈ $24，云单价先乘 12 换年化，推导见 [§7.4](05-cold-hot-tiering-section-7-sec7.md)） |
| 团队技能与运维能力 | 规则能不能长期活下去 | 「规则配好就一劳永逸」——人执行的规则必然静默过期 |

读这张表的方法是从上往下：前四行决定**候选集与可行性**，后两行决定**这件事值不值得做**。顺序反过来——先被「我们数据量大」吸引，再回头发现访问日志根本没采集、查询入口还没统一——是本主题最常见的返工来源（[§7.5](05-cold-hot-tiering-section-7-sec7.md)）。

### 3.2 模式逐个拆解（核心节）

先看执行者是谁：**规则由存储层自己执行**的有 3.2.1 HDFS 存储策略与 3.2.2 对象存储生命周期，同一类的 3.2.5 把「判定」也一并交给了存储层；**执行者是一个中间层**的有 3.2.3 统一存储与 3.2.4 表格式分层；3.2.6 与 3.2.7 改变的不是执行者，而是判据与作用范围。前面两类内部换件代价小（改规则、换存储类、换策略），跨类切换要重做数据组织方式（改表格式、搬文件、重建规则体系）——先分清属于哪一类再选，能省掉一半比较。

每个模式按六件事展开：被什么约束逼出来、结构、为什么这样设计有效、代价、失效点、真实使用；六件事之后各附一条**核验方法**，说明读者怎么在自己这份数据上确认它确实在按预想工作。**其中失效点最关键**：它回答的是「这个模式的优点在什么条件下会反转成缺点」，而这一条在模式清单里是完全缺失的。

#### 3.2.1 HDFS Archive Storage（本地数据中心分层）

- **被什么约束逼出来**：数据在自建集群里、介质换不动云，唯一的着力点是「块落在哪种盘上」。
- **结构**：

```text
HDFS 存储策略：目录级声明，块级生效
  /warehouse/hot    → Storage Policy: ALL_SSD   所有副本落在 SSD
  /warehouse/mixed  → Storage Policy: ONE_SSD   一副本 SSD，其余 DISK（HDD）
  /warehouse/warm   → Storage Policy: WARM      DISK 与 ARCHIVE 混用
  /warehouse/cold   → Storage Policy: COLD      全部落在 ARCHIVE（默认策略是 HOT，即全 DISK）
  写入：客户端写块 → NameNode 按目录策略为每个块选存储类型 → DataNode 落盘
  迁移：hdfs mover 按「当前落点 vs 策略要求」的差异在后台搬块
  注意：策略声明的是「用哪种存储类型」，不声明「何时迁」——
        迁移要由 mover 显式触发，这是它与对象存储生命周期的机制差别
  → 应用始终用同一个 HDFS 路径读写，介质差异不出现在访问路径里
```

- **为什么这样设计有效**：因为策略是**目录级声明、块级生效**，副本落在哪种介质由 NameNode 分配时决定，所以「数据在哪一层」不进入应用的访问路径——应用仍按同一个路径读写，介质差异被分布式文件系统吸收。这套机制由 HDFS-8365 在 2015 年引入（[主文件 §1.4](05-cold-hot-tiering.md)）【公开】。
- **代价**：迁移是集群内的后台搬块，消耗的正是你打算拿来跑作业的磁盘与网络带宽；更根本的是**副本因子放大了每层的存储成本**——三副本意味着三个介质层各存三份。另外策略作用在共享命名空间的目录上，改一次目录策略会影响所有写在它下面的作业。
- **失效点**：当**存储类型配额（storage type quota）用尽**时，「一个路径搞定三层、应用无感」的优点反转成写入阻塞——因为策略是声明式的，引擎没有「退一步落到 HDD」的语义，配额不够时写入直接失败而不是自动降级。
- **真实使用**：HDFS 存储策略是 Apache Hadoop 的公开能力（[主文件 §1.4](05-cold-hot-tiering.md) 记为 2015 年 HDFS-8365）【公开】。可自行核验：`hdfs storagepolicies -listPolicies` 列出集群支持的策略集，`hdfs storagepolicies -getStoragePolicy -path <dir>` 查某个目录当前生效的策略。
- **核验方法**：对目录跑 `hdfs fsck <path> -files -blocks -locations`，看副本实际落在哪种存储类型上——策略写对了不等于块已经搬过去，mover 没跑完之前两者会长期不一致。

#### 3.2.2 对象存储分层（S3 / OSS / COS）

- **被什么约束逼出来**：数据已在云上，介质不由你选、只能选存储类；而且你没有搬运作业的算力预算，规则必须由存储服务自己执行。
- **结构**（与 [主文件 §2.3](05-cold-hot-tiering.md) 的生命周期规则同构）：

```yaml
lifecycle_rules:
  - prefix: "logs/"
    status: "Enabled"
    transitions:
      - days: 30
        storage_class: "IA"        # 30 天后转低频
      - days: 90
        storage_class: "Archive"   # 90 天后转归档
    expiration:
      days: 365                    # 365 天后删除
  # 转换（transitions）与过期（expiration）是两条独立规则：
  # 转换只改存储类、不删对象；过期才决定对象生死
```

- **为什么这样设计有效**：因为规则**声明式地挂在存储服务上、以对象年龄为触发条件**，所以分层不产生搬运作业、不需要值班运维——规则一旦写下就由服务持续执行。这也是它成为绝大多数云上组织默认形态的原因（[§7.2](05-cold-hot-tiering-section-7-sec7.md)）。
- **代价**：档位不是免费换的。低频与归档档通常设有**最小存储期**，未满期转档或删除会按剩余天数补收；取回另行按量计费；这些条款按档位分别列明（AWS S3 与阿里云 OSS 自 2016 年起提供分层存储入口，见 [主文件 §1.4](05-cold-hot-tiering.md)；档位名与计费规则请以官方文档当前版本为准）【公开】。也就是说「转档」这个动作有最小成本单位，比它更短的生命周期只会白花钱。
- **失效点**：当**数据形态是大量小对象**时，「零搬运、零运维」的优点反转成「请求与取回费用超过存储费」——因为下沉与取回都按对象为单位计数计费，对象数不随分层减少，存储费降了而请求费不变甚至上升，成本结构从字节尺度换到了对象尺度。
- **真实使用**：Netflix 自 2016 年起用三层（Standard → IA → Glacier）+ 生命周期自动化做合规留存，本章 [§6 的 Netflix 案例](05-cold-hot-tiering-section-6-sec6.md) 记录了它把「访问频次为主判据、年龄为兜底」作为核心设计；阿里云 OSS 侧把同一形态做成开箱即用的四档能力，见 [§6 的阿里云 OSS 案例](05-cold-hot-tiering-section-6-sec6.md)【公开】。
- **核验方法**：抽几个已转换的对象做一次 HEAD / stat，确认它们当前的存储类、最后修改时间与规则一致；再检查规则里的转换天数是否短于目标档位的**最小存储期**——短于它的规则会在每次转换时白付一笔。

#### 3.2.3 统一存储分层（Ceph / JuiceFS / JindoFS）

- **被什么约束逼出来**：组织既有的 HDFS 生态不能丢，又想要对象存储的成本曲线；而两套命名空间并存意味着两套权限、两套目录与一份跨栈一致性成本。
- **结构**：

```text
统一存储：一套介质管理 + 两套协议入口
   HDFS 客户端 ──(HDFS 协议)──┐
                              ├──► 元数据服务（命名空间 / 权限 / 配额）
   S3 客户端 ───(S3 协议)────┘             │
                                           ▼
                                    数据服务（块 / 对象）
                                           │
                           ┌───────────────┼───────────────┐
                       NVMe / SSD         HDD          对象存储后端
  → 元数据与数据分离：元数据服务管「在哪」，数据面管「落在哪层介质」
  → 两个协议入口必须看到同一个命名空间；各持一份元数据的，是网关不是统一存储
```

- **为什么这样设计有效**：因为元数据与数据分离、协议在入口层归一，所以两种生态可以写到**同一份介质管理**上——同一批数据既能被 HDFS 工具链访问，也能被 S3 API 访问。这是它与「HDFS + 对象存储双栈」的机制差异，也是它被混合云场景选中的原因（[§7.2](05-cold-hot-tiering-section-7-sec7.md)）。
- **代价**：多出一个**元数据服务**，它自身成为可用性与性能的收敛点，必须做成高可用；协议转换还会引入语义落差（例如对象侧的覆盖写语义与文件侧的追加语义并不一致），接入的每一条工具链都要单独验证。项目文档（Apache Ozone、Ceph、JuiceFS、JindoFS）可自行核验其协议支持矩阵【公开】。
- **失效点**：当**写入形态以高频小文件随机写为主**时，「两套协议共享一份介质」的优点反转成「元数据服务成为瓶颈」——因为所有协议入口的元数据操作都收敛到同一个服务，加数据节点并不能缓解它，只有对元数据服务分片才行。
- **真实使用**：Ceph、JuiceFS、JindoFS 是这一族里被反复引用的三个项目（[主文件 §1.4](05-cold-hot-tiering.md) 把「JindoFS + JuiceFS + Ceph 统一存储」记为 2022 年的进展）【公开】。判断方法：看它是否同时提供文件协议与对象协议、且两者指向同一个命名空间——只有一个协议入口的是存储网关，不是统一存储。
- **核验方法**：用文件协议写一个文件、用对象协议读同一个路径，确认读到的是同一份字节而不是两套副本；再对同一路径做一次覆盖写，确认两个协议在「覆盖写 / 追加写 / 重命名」上的语义落差已经逐条验证过。

#### 3.2.4 表级分层（Iceberg / Hudi / Paimon）

- **被什么约束逼出来**：分层必须对查询透明，且要按分区 / 文件的热度下沉，粒度比对象级更细（[§7.2](05-cold-hot-tiering-section-7-sec7.md)）；而表这一层同时还背着版本管理这件事。
- **结构**：

```sql
-- 一张表，物理文件按温度分布在不同介质；介质位置不进 SQL 语义
CREATE TABLE dws_trade_1d (
  shop_id   BIGINT,
  gmv       DECIMAL(18,2),
  stat_date DATE
) USING iceberg
PARTITIONED BY (days(stat_date))
TBLPROPERTIES (
  'write.data.path'     = 's3://bucket/warehouse/dws_trade_1d',   -- 新数据（热）
  'write.metadata.path' = 's3://meta/warehouse/dws_trade_1d'      -- 清单独立存放
);
-- 分层动作发生在文件层：把旧分区的数据文件下沉到低频档，
-- 清单（snapshot / manifest）仍引用同一批文件 → 对 SQL 完全透明
-- Hudi 的两条路：COW 每次更新重写数据文件（写放大），MOR 追加日志再异步合并（读放大）；
-- 对分层而言动作相同（都是下沉文件），但代价落在不同阶段
```

- **为什么这样设计有效**：因为表格式把**数据文件与文件清单分成两层元数据**（[§7.3.4](05-cold-hot-tiering-section-7-sec7.md) 引 Iceberg 表规范），所以下沉一批文件只需改「这些文件放在哪个存储类」，清单仍指向同一批文件——查询层按表名查即可，不需要知道介质位置。Iceberg 于 2018 年开源并进入 ASF 孵化，Hudi 2017 年开源、2019 年进入 ASF，Paimon（原名 Flink Table Store）2023 年进入 ASF 孵化、2024 年 1.0 毕业；三者的发布历史与表规范可自行核验（[§7.3.3](05-cold-hot-tiering-section-7-sec7.md)）【公开】。
- **代价**：多出两套元数据的**常驻维护**——快照过期、清单重写、小文件合并；这些作业失效是静默的（查询照样能跑，只是越来越慢）。同时 COW 与 MOR 的取舍本身就是代价：COW 每次更新重写数据文件（写放大），MOR 追加日志再异步合并（读放大），Paimon 用 LSM 把冷数据的合并推到后台——选哪个都在为同一次更新付两种账中的一种。
- **失效点**：当**分区粒径本身不合理**（一个分区占全表绝大多数数据）时，「按分区热度下沉、粒度比对象级细」的优点反转成粒度劣势——因为下沉的最小单位是分区，搬一个分区等于把其中仍在被读的数据一起搬走，误归档的规模由分区设计决定，而不是由分层策略决定。
- **真实使用**：字节把跨介质分层建在 Iceberg 统一表上（一张表三种介质），见 [§6 的字节湖仓分层案例](05-cold-hot-tiering-section-6-sec6.md)；Snowflake 的设计取向是「分层不改变计算层行为」，见 [§6 的 Snowflake 案例](05-cold-hot-tiering-section-6-sec6.md)【公开】。
- **核验方法**：查一次表的分区数与各分区的数据文件数、平均文件大小——**粒径与小文件数决定了分层的实际粒度**，「按分区下沉」在某个分区占全表绝大多数数据时，等于按整表下沉。

#### 3.2.5 智能分层（S3 Intelligent-Tiering / OSS 智能分层）

- **被什么约束逼出来**：组织承认自己不会长期维护规则，而人执行的规则必然静默过期（[§7.2](05-cold-hot-tiering-section-7-sec7.md)）。
- **结构**：

```text
智能分层：访问行为的采集与判定都在存储服务内部闭环
   对象写入 ──► 存储服务内部记录访问行为（客户不配置任何规则）
                     │
        ┌────────────┴─────────────┐
     频繁访问档                长期未访问档
        │                              │
        └──── 访问行为变化 ────────────┘   自动来回迁移
   客户侧只做一件事：把对象放进这个存储类
   → 与生命周期规则的区别：触发信号是「访问行为」，不是「对象年龄」
   → 代价也在这里：判定依据不外露，且监控与自动化费用按「对象数」计，不按字节计
```

- **为什么这样设计有效**：因为触发信号从「对象年龄」换成了「访问行为」，而采集与判定又发生在存储服务内部，所以它同时消掉了两件事——写入很久但天天被读的数据不再被误归档，访问日志的采集链路也不落在客户身上。S3 Intelligent-Tiering 于 2020 年推出、阿里云 OSS 智能分层于 2021 年推出（[主文件 §1.4](05-cold-hot-tiering.md)）【公开】。
- **代价**：判定逻辑由平台定义，**可解释性低**——你问不到「它为什么认为这个对象是冷的」；并且自动化本身有成本，监控与自动化费用通常按**对象数**计收（具体价格以官方定价页当前版本为准）【公开】。
- **失效点**：当**对象数极多而单对象极小**时，「无需人工规则就能自动优化」的优点反转成「自动化费用超过省下的存储费」——因为自动化与请求费用按对象数计，而存储节省按字节数计，两个尺度不同：小对象上后者的节省趋近于零，前者照收。
- **真实使用**：S3 Intelligent-Tiering 与阿里云 OSS 智能分层是这一族的两个代表（[§7.2](05-cold-hot-tiering-section-7-sec7.md)）【公开】。判断方法：看它有没有「按最近访问时间」这一触发条件——有，说明它属于自动分层；只有「距今 N 天」，说明你面对的是生命周期规则。
- **核验方法**：挑一批已知访问规律的对象（例如每天被读一次）观察它是否留在热档；再把账单里的监控与自动化费用单独拎出来看它是否随对象数增长——只看存储费会得出错误结论，因为两项的计量单位不同。

#### 3.2.6 AI 驱动的自动分层（2024+）

- **被什么约束逼出来**：访问模式有规律，但规则与平台内置判定都跟不上业务节奏——尤其回捞是异步动作，等判定成立再迁就已经晚了。
- **结构**：

```text
预测型分层：判据从「过去多冷」换成「未来多冷」（§7.3.1）
   访问序列（对象 / 分区 × 时间）
        │
        ├─► 特征：最近 k 天访问次数、访问间隔、业务日历（月末 / 大促）
        ├─► 模型：预测未来 T 天是否会被访问
        └─► 动作：预测为冷 → 提前下沉；预测为热 → 提前回捞 / 预热
   与智能分层的分工：预测管「提前量」，平台规则管兜底
   回测：在历史访问序列上先重放一遍，看误归档条数是否低于规则式分层
   回滚通道：预测动作必须可撤销（判冷 → 下沉；判错 → 能回到原档位）
```

- **为什么这样设计有效**：因为迁移（尤其是回捞）本身是耗时动作，而预测在数据真正变冷之前就给出动作，所以它多出的那段时间正好覆盖迁移延迟——这是它相对「判定成立后再迁」的唯一但关键的机制优势。
- **代价**：模型要求一条独立的**数据加工流水线**（特征回填、训练、回测、上线），它的运维形态是数据流水线而不是一条配置；并且**没有回测的预测型分层，等于把误归档的风险从规则搬进了模型**（[§7.6](05-cold-hot-tiering-section-7-sec7.md)），还更难解释。
- **失效点**：当业务发生一次**改变访问形态的大事件**（新产品上线、报表口径变更）时，「提前量」这个优点反转成「错误的提前量」——因为模型学到的是旧分布，它会比不做预测更早地把一批即将变热的数据下沉，事故因此提前发生而不是被避免。
- **真实使用**：【经验】这一族目前多见于超大规模、访问模式有规律的组织自研或平台侧尝试；[主文件 §1.4](05-cold-hot-tiering.md) 把「AI 驱动的自动分层（预测访问模式）」记为 2025 年的演进方向【公开】。这一族的两个技术栈是「Iceberg V3 + ML」与「自研 + LLM」——前者把预测挂在表格式的元数据与统计上，后者把预测做成一条独立的模型服务；两条路径的共同点是需要一条预测流水线，而不是一条配置。判断方法：问它的动作有没有回滚通道与回测报告——没有这两件，它就不是预测型分层，而是一次性的批处理搬家。
- **核验方法**：要一份回测报告（用历史访问序列重放，给出误归档条数）并确认动作可回滚；两件都拿不出时，它带来的风险高于它省下的存储费。

#### 3.2.7 多云分层

- **被什么约束逼出来**：数据必须按属地或合规要求落在指定云上，同时业务逻辑不能按云复制三份。
- **结构**：

```text
多云分层：控制面统一，数据面按属地分散
   统一元数据 / 目录（表 → 分区 → 文件位置清单）
        │
   ┌────┼──────────────┬──────────────┐
 AWS S3            阿里云 OSS      Azure Blob
 热 + 低频          热 + 归档        热 + Archive
   └────┴──────────────┴──────────────┘
   统一读入口（查询引擎按清单里的位置读，不按「哪朵云」读）
   → 分层规则按云分别配置；取回时间、最小存储期、保留能力逐云列明
   逐云台账：各云归档档的取回时间、最小存储期、是否支持不可删改留存，各记一行
```

- **为什么这样设计有效**：因为访问入口统一在表与清单这一层、数据位置记在清单里，所以多云的核心工作从「把数据搬到一起」变成「把位置记清楚」——查询引擎读的是位置，不读云名。这决定了多云分层可行性的边界：清单能描述到的，就能跨云。
- **代价**：**合规面按云数成倍增长**——各家的归档取回时间、最小存储期、不可删改留存能力（对象锁一类，AWS S3 自 2018 年起提供，[§7.3.4](05-cold-hot-tiering-section-7-sec7.md)）都不相同，必须逐云验证；此外任何跨云复制都按出网流量计费，这是多云架构里最容易失控的一项。
- **失效点**：当**跨云查询从例外变成常态**时，「数据按属地分散」的优点反转成「每次查询都要跨云取数」——因为出网流量与跨云延迟随查询次数与字节数累积，而合规约束又不允许把数据集中到一处，两个约束此时互相锁死。
- **真实使用**：【经验】受属地合规约束的跨国企业普遍采用这一形态，具体实现多为「统一表格式 + 各云对象存储」的组合。判断方法：看它的查询入口是不是只有一个逻辑入口，以及非属地查询是不是被限制在汇总层——明细跨云即常态，说明这层设计还没做。
- **核验方法**：对每朵云分别打开它的归档档文档，逐项确认取回时间、最小存储期与保留策略支持情况；再统计跨云查询在全部查询里的占比——占比决定出网流量是一项次要费用还是主要费用。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 数据 < 1 TB、延迟敏感 | 单层高性能介质 | 分层的年节省额低于规则维护成本 | 年节省额 vs 规则维护人力（【推算】1 TB 下沉对象存储标准层约 $24/年，推导见 [§7.4](05-cold-hot-tiering-section-7-sec7.md)） |
| 云上、百 TB 级、以分析为主 | 对象存储生命周期分层（两档起步） | 表格式分层要额外引入清单与快照维护 | 执行者是谁：存储服务执行则无搬运作业 |
| 云上、数据可能被临时调用 | 低频档（即时取回） | 归档档取回异步且按量计费 | 取回能等多久 |
| 本地已有 HDFS 生态 | HDFS 分层（存储策略） | 统一存储要重做命名空间与工具链 | 块级策略是否已能满足分层诉求 |
| 本地 + 云混合、既要 HDFS 生态又要对象成本 | 统一存储分层（Ceph / JuiceFS / JindoFS） | HDFS + 对象存储双栈要长期维护两套命名空间、两套权限与一条跨栈搬运路径 | 两套协议是否指向同一个命名空间 |
| 表已由开放表格式管理 | 表格式分层 + 对象存储生命周期 | 只用对象级生命周期，粒度到不了分区 | 分区粒径与更新形态 |
| 不愿长期维护规则 | 智能分层 | 手动分层必然静默过期，且过期不可见 | 谁执行「判定」这件事 |
| 访问模式有规律、规模超 PB | 智能分层 + 预测型分层 | 纯规则跟不上业务节奏，且回捞有延迟 | 有无可回测的访问序列 |
| AI 训练集的读取形态（访问有规律、可回测） | AI 驱动分层 | 智能分层只能按已发生的访问判定，给不出提前量 | 有没有回测通道与动作回滚 |
| 受属地 / 合规约束 | 多云分层 + 各云归档 + 保留策略 | 单云集中违反属地要求 | 跨云查询是不是例外 |
| 本地、PB 级、冷数据以留存为主 | HDFS 分层 + 磁带离线层 | 全量换统一存储要重做命名空间与工具链 | 数据是否需要「偶发但在线可取」 |
| 小文件极多、请求次数高 | 先合并小文件，再配分层规则 | 直接对小文件配生命周期规则 | 请求与取回费用是否已超过存储费 |

本主题下最常被误选的一对是**对象存储生命周期分层与智能分层**。误选的依据通常是「我们有访问日志，所以能用访问行为」——但生命周期规则的触发条件在主流云产品里只有「距今 N 天」一类，没有「最近访问时间」（[§7.3.1](05-cold-hot-tiering-section-7-sec7.md)）【公开】。照着生命周期规则的文档去搭一套「访问频次为主判据」的规则，访问频次只能写进自己的调度脚本，于是「声明式零运维」这个唯一优势被作废，形态退回成手动分层。判断方法：打开目标产品的生命周期规则文档，若触发条件里没有「最近访问时间」，那么「按访问行为」一定落在自动分层能力上，而不是生命周期规则上。

### 3.4 组合模式：真实系统不会只用一种

**组合一：表格式分层 + 对象存储生命周期分层**（Lakehouse 的默认形态）。表格式承担「逻辑与版本」——一张表、文件清单、快照；对象存储承担「介质与成本」——存储类与生命周期规则。运维代价是两件事必须解耦：数据下沉与快照过期各走各的流程、各自独立校验，合进同一个作业就会「省钱顺手删历史」（[§7.3.4](05-cold-hot-tiering-section-7-sec7.md)）。适合百 TB 到 PB 级的湖仓，也是 [§6 的字节湖仓分层案例](05-cold-hot-tiering-section-6-sec6.md) 的形态。

**组合二：HDFS + 对象存储（混合双栈）**。HDFS 承担热数据的低延迟读写与既有生态，对象存储承担冷数据的低成本与容量。运维代价是两套命名空间、两套权限，外加一条跨栈搬运路径——**这条路径必须有校验**，否则会出现「冷侧缺文件、热侧已删除」这类无从发现的缺口。适合本地已有集群、且冷数据主要用于留存与偶尔回捞的组织。

**组合三：智能分层 + 预测型分层（+ 手动例外清单）**。平台内置能力管绝大多数通用数据，预测层管提前量，人的角色收缩为「设计规则与例外清单」。运维代价集中在两点：预测需要回测与验证集；例外必须有台账（哪些数据被手工钉在某个档位、为什么），没有台账的例外会变成没人敢动的黑盒（[§7.6](05-cold-hot-tiering-section-7-sec7.md)）。适合 PB 级以上、且多数数据无需人工干预的组织。

三条组合的责任归属并不相同：组合一里，被下沉的文件仍记录在表格式的清单中，误归档名单可以由「清单里有什么」与「查询实际读到了什么」交叉比对得到；组合二里，两套命名空间之间没有共享的访问视图，名单只能靠在跨栈搬运路径上打点；组合三里，判定由平台给出、依据不外露，人能做的只是维护例外台账并定期复核。三者唯一共通的硬要求是：**必须有一个组件持有「哪些数据被下沉后又被读过」这个数**——没有它，规则会一直按错误的方向执行下去。

上面三条组合的组件数分别是 2、2、3（组合三把例外清单也算一件），对应待校验的一致性问题分别是 1、1、3 对；**每多加一件，待校验的对数按组合数增长——四件之间就是六条潜在的不一致**。所以每加一层介质或一个组件之前，先写下它消掉的是哪一条成本或哪一类事故；写不出来时，它带来的规则与校验成本会超过它省下的存储费。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 全用 SSD | 存储账单里单个介质单价占绝对多数，各层数据量分布只有一个非零项 | 按 [主文件 §1.2](05-cold-hot-tiering.md) 的二八定律（多数查询落在少数数据上），大比例字节为少数访问付最贵单价。但**单价落差值取决于下沉目标档位**（年化口径，【推算】，见 [§7.4](05-cold-hot-tiering-section-7-sec7.md)）：对对象存储标准层只有约 1.1 倍（$0.30 对 $0.276）、对 IA 约 2 倍（$0.15）、对 Glacier 约 6.3 倍（$0.048）、对自建 HDD 约 7.5 倍（$0.04）、对磁带约 300 倍（$0.001） | 早期数据量小，买 SSD 最省事；分层要到量级足够大才显出差额 | 按访问频率分层；**冷数据至少要沉到 IA 以下的档位**——标准层与 NVMe 几乎同价，沉到标准层不产生单价节省 |
| 分层规则不合理（把热数据迁到冷层） | 上线后某张「很久没写」但仍被每天读的表进了冷层，报表从秒级变小时级 | 误归档是静默的：没有访问行为采集时，团队事先不知道哪些数据处在错误层级 | 生命周期规则的原生触发条件是对象年龄，而年龄与热度无关（[§7.3.1](05-cold-hot-tiering-section-7-sec7.md)） | 以访问频次为主判据、年龄为兜底，并补齐访问日志采集 |
| 忽视回迁（Recall） | 冷数据被业务临时调用，第一次调用即产生分钟到小时级等待 | 归档档取回异步且按量计费，一次抽查就可能吃掉一整年的存储节省（[§7.3.2](05-cold-hot-tiering-section-7-sec7.md)） | 选档时只比较了存储单价，没有把「取回能不能等」列为条件 | 对可能被临时调用的数据配预热 / 主动取回，或改用即时取回的低频档 |
| 归档数据未做合规检查 | 数据已过保留期仍在流通，或不可删改的数据被搬到不支持保留策略的档位 | 留存与分层是两件事：分层管「放在哪里」，保留策略管「能不能删」，只做一件不构成合规 | 把「不可删改留存」当成归档档的附带属性 | 明确保留期限 + 自动过期删除，并逐档确认该档位支持保留策略 |
| 未做压缩 | 存储账单里字节数远高于业务数据本身，同一份数据的多个副本都未压缩 | 压缩降体积、分层降单价，两者是相乘的杠杆；只做分层等于放弃其中一半 | 压缩要重新写文件并验证读取路径，分层只改一条规则，先做便宜的那个 | 列存 + ZSTD / Snappy；压缩比须在自己的数据上实测（见 3.6） |
| 跨层访问性能差 | 热冷混查的作业网络带宽打满，端到端延迟由跨层读取决定 | 跨层查询的延迟随介质落差增长，介质落差大到分钟级时业务无法接受（[§7.3.2](05-cold-hot-tiering-section-7-sec7.md)） | 「数据都在同一张表里」被误读成「读取代价也一样」 | 缓存热数据 + 异步预加载；或承认这类数据不该被分层 |

三个最危险的反模式值得单独说。**「分层规则不合理」危险在它的启动延迟**：规则刚上线时看不出问题，因为被误判的那批数据此刻确实很少被写；等到三到六个月后它被天天读，症状才出现，而此时团队已经没有「哪些数据处在错误层级」的名单——[§7.3.1](05-cold-hot-tiering-section-7-sec7.md) 给的修法是先补访问采集再定规则，顺序反过来就永远答不出「这一步做对了没有」。

**「归档数据未做合规检查」危险在它有两个相反的错误方向**：一个方向是保留期没有配置，数据过期不删，留史无限增长，成本被留史吃掉——它的表现是「分层做了但账单不降」，容易被误判成规则没生效而继续加码；另一个方向是不可删改的数据被下沉到一个不支持保留策略的档位，此时「能不能删」由该档位的生命周期规则替你回答，历史会在一次常规的过期删除里消失，且无法从任何备份恢复「当时看到的是什么」。两个方向都不在分层的操作面上暴露，要等到审计或取证时才显形。正确做法是两道确认：**逐档确认该档位支持不可删改留存**，并**显式配置保留期与自动过期删除**——只做后者的，会在不支持保留策略的档位上丢掉历史；只做前者的，会在留史无限里把省下的钱花回去。

**「忽视回迁」危险在它伪装成选型偏好**：选归档档时看到的只是单价下降，代价要等到几个月后的一次抽查才出现。因为取回是异步且按量计费的，一次批量取回的费用与等待可以吃掉一整年的存储节省；而这件事在压测里不会暴露——压测测的是吞吐与 P99，不会去读一个三年没人碰过的对象。所以选档时该把「取回能等多久」写进选型理由，而不是只写「单价更低」。

至于「未做压缩」与「跨层访问性能差」，它们的成因是同一个**排序错误**：压缩要重写文件并验证读取路径，跨层缓存要新增一层，而分层只要改一条规则就能上线；团队于是先做最便宜的那件，随后发现收益被未压缩的体积与跨层读取的延迟各吃掉一部分。修法是把「体积」与「取回路径」列进验收项，而不是列进待办。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| < 1 TB → 百 TB | 单层高性能介质 | 单价差的绝对额开始可观（【推算】1 TB 下沉对象存储标准层约省 $24/年，即 1000 GB × ($0.30 − $0.023 × 12)；这个绝对额尚压制不了维护成本，到百 TB 级才反过来） | 对象存储生命周期分层，两档起步 | 规则设计 + 取回策略 + 成本可视成为常驻工作（[§7.7](05-cold-hot-tiering-section-7-sec7.md)） |
| 百 TB → PB | 手动 / 半自动分层 | 规则条数随业务数增长，人执行的规则静默过期 | 声明式规则或智能分层 | 不改数据，重建规则体系与回归流程 |
| 对象级 → 分区级 | 对象存储生命周期分层 | 对象粒径太粗，热点分区与冷分区被一起下沉 | 表格式分层 + 底层对象存储 | 元数据重构，快照与分区维护转为常驻工作 |
| 单云 → 多云 | 单云分层 | 属地合规与单云风险要求数据按云分布 | 多云分层（统一清单 + 各云归档） | 全量搬迁与双跑验证；出网流量成为新的成本项 |
| 规则 → 预测 | 智能分层 | 回捞是异步动作，判定成立后迁移已经晚了 | 预测型分层 + 智能分层兜底 | 特征回填、回测、验证集与回滚通道 |
| 归档档 → 低频档（回退） | 归档档分层 | 出现「可能被临时调用」的数据，取回代价首次使用即事故 | 低频档（即时取回），或归档档 + 预热 | 冷数据回捞受取回时间约束，回退窗口以天计 |
| 双栈 → 统一存储 | HDFS + 对象存储双栈 | 两套命名空间与权限的维护面随业务数增长 | 统一存储（Ceph / JuiceFS / JindoFS） | 全量搬迁 + 双跑验证；协议映射与权限重建 |

这七行按「要不要动数据」还可以再分一次：百 TB → PB 只重建规则体系、规则 → 预测只换触发方式，这两行不搬数据；对象级 → 分区级动的是元数据组织，数据文件可以留在原处；其余四行（含那条方向相反的回退）都会产生一次真实的数据流动，其中「单云 → 多云」与「双栈 → 统一存储」还各附一次双跑验证。同一张表里工作量能差出一个数量级，先看清这一行属于哪一类，再决定要不要立专项。

表里与小结里出现的年节省额有两个口径，**不能并成一个区间**：$24 对应「1 TB 从高性能层下沉到对象存储标准层」（1000 GB × ($0.30 − $0.023 × 12) = 1000 × 0.024 ≈ $24），$252 对应「同量数据改下沉到归档层」（1000 GB × ($0.30 − $0.004 × 12) = 1000 × 0.252 ≈ $252）——两个数背后是两个不同的动作，相差 10 倍，引用时必须写明是哪一种（推导见 [§7.4](05-cold-hot-tiering-section-7-sec7.md)）。关于压缩的基准也要写清：列存 + Zstd 在日志与分析类数据上常见压缩比是 5~10 倍（相对未压缩原始文本），相对已经列存化的文件再叠加通常只再省 50~80%（[主文件 §2.3](05-cold-hot-tiering.md)、[§7.4](05-cold-hot-tiering-section-7-sec7.md)）【经验】——引任何一个数之前，先写清基准是哪一个。

还有一类跃迁是**不该换**的：当分层已经跑稳、只是成本偶尔反弹时，要换的往往不是模式，而是度量——先补上成本可视与误归档指标，再决定动不动结构；没有度量时，任何自动化都只是把偏差藏得更深。

跃迁的触发信号也不是「数据量涨了」，而是**某条约束的取值变了**：信号由年龄变成可采的访问行为、执行者由人变成服务、取回要求由「可以等」变成「不能等」、范围由单云变成多云的属地要求。约束没变而只换模式，通常只是换了一套需要重新踩一遍的坑。

### 3.7 自检清单

- [ ] 分层规则的触发条件是「距今 N 天」还是「最近访问时间」？若是前者，被它判为冷的对象里，有没有仍在被每天读取的？
- [ ] 访问日志是否可信？（一个周期性全量扫描作业会让所有数据看起来都是热的，此时判据必须退回「业务标注 + 年龄」）
- [ ] 有没有一个组件对「误归档」负责？具体说：有没有采集「被下沉后短期内又被读取」的对象数这个指标？
- [ ] 可能被临时调用的数据，是否落进了取回异步的档位？若是，预热 / 主动取回通道是否已经建立？
- [ ] 业务是否需要知道数据在哪一层？如果查询存在两套入口，说明跨层拼接落在应用层，分层会在几个月内被绕过。
- [ ] 分层动作与版本回收是否写在同一个流程里？两者共用同一批文件，合并即不可逆。
- [ ] 不可删改留存的数据，所在档位是否支持保留策略？保留期是否已配置（未配置时「正交」会退化成「分层打折、留史无限」）？
- [ ] 成本函数里的每一项是否可观测？至少要有各层数据量分布、各层取回量与请求次数、误归档条数这三项。
- [ ] 压缩比是在自己的数据上实测的，还是引用了一个带错基准的倍数？
- [ ] 手动分层的例外有没有台账（哪些数据被钉在哪个档位、为什么）？
- [ ] 下层的档位是否设了最小存储期？生命周期规则里的转换天数是否短于它？
- [ ] 分层生效后，是否做过一次「关掉分层规则，业务还能不能跑」的回退演练？

这 12 条里，第 1–4 条是**门槛项**——判据信号与取回通道做错，分层会直接变成事故来源，任何规模下都成立（[§7.1](05-cold-hot-tiering-section-7-sec7.md) 把「分层触发依据」与「取回代价」列为同一组门槛判据）；第 5–12 条是**权重项**，重要性随规模与业务形态放大，可以先做简单的版本再补。权重项里有一组要先查：第 6–7 条（分层与版本回收、档位保留策略）——它们同属「分层与留史 / 版本正交」这一个维度，按重要性算仍是权重项，但**做错不可逆**（历史被删、档位不支持不可删改留存，都没有回头路），所以检查优先级与门槛项相同。

### 3.8 小结

把本节所有结论压成一句：**先过门槛（判据与取回），再谈权重（透明度、正交、自动化）；门槛不满足时，换任何模式都只是换一种事故形态。**

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 数据 < 1 TB | 单层高性能介质，不分层 | 年节省额低于规则维护成本（【推算】每 TB 下沉对象存储标准层约 $24/年、改下沉归档层约 $252/年，两个动作分列，见 3.6） |
| 云上、百 TB 级、分析为主 | 对象存储生命周期分层，两档起步 | 执行者是存储服务：没有搬运作业，也就没有需要值班与回归的迁移流程 |
| 本地已有 HDFS | HDFS 分层（存储策略） | 策略声明在目录、迁移由集群侧后台完成，应用读写的仍是同一个路径 |
| 本地 + 云混合 | 统一存储（Ceph / JuiceFS / JindoFS） | 两套协议指向同一个命名空间，省掉一条跨栈搬运路径与它的校验 |
| 表已由开放表格式管理 | 表格式分层 + 对象存储生命周期 | 下沉的最小单位是分区 / 文件，清单仍指向同一批文件，查询层看不到介质 |
| 不愿维护规则 | 智能分层 | 触发信号是访问行为而非对象年龄，采集与判定在服务内部闭环 |
| 访问模式有规律、规模超 PB | 预测型分层 + 智能分层兜底 | 迁移是异步动作，预测多出的提前量正好覆盖它 |
| 受属地 / 合规约束 | 多云分层 + 各云归档 + 保留策略 | 入口统一在清单层，位置记在清单里，不必把数据搬到一起 |

> 本节小结：7 个模式不是一个并列的选项清单，而是**判据信号、执行者、取回通道**这三个变量取值的组合——所以「换模式」之前要先问清换的是哪个变量：只换执行者（改规则、换存储类）是一次配置变更，换判据信号要补一条访问采集链路，换取回通道等于重新回答「这批数据能不能等」。三者里最需要先定下来的是判据信号，因为它是唯一一个选错后不会立刻暴露的变量；而全节唯一不可逆的一处，是分层与版本回收必须各自独立——它做错的代价是历史无法恢复。
>
> 💡 **思考锚点**：先量你的一次下沉动作落在 §3.6 的哪个价差档——沉到对象存储标准层只省约 1.1 倍（$0.30→$0.276），沉到归档层才省约 6.3 倍（→$0.048）。用你现有的数据量算这笔年节省额（每 TB 下沉标准层约 $24、下沉归档层约 $252）：它是被一次批量取回就可能吃掉的量级吗？若是，你该先补的是访问采集（先定判据信号），还是先改下沉档位（只换执行者）？
