## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表的第一处误导，是**维度方向没有定义**。原表在「运维复杂度」一列给全 SSD 2 分、给分层存储 4 分，但没有说明高分代表「更简单」还是「更复杂」。事实上分层存储一定比单层难运维——它额外引入了三件事：生命周期规则的设计与回归、取回策略与取回费用、跨层查询的一致性。于是这一列的读法只能二选一：若高分代表「更复杂」，它与事实一致；若代表「更简单」，它恰好写反了。原表没有说明是哪一种，读者也就无从判断自己读到的到底是哪一种。方向不明的一列，等于没有这一列。

第二处误导，是**把「成本」当成一个数**。原表给分层存储的成本打 5 分、全 SSD 打 1 分，读起来像「分层一定更省钱」。但分层能不能省钱，取决于一个非常具体的条件：**你分层的那批数据是不是真的很少被取回**。取回一次的代价（延迟 + 按量费用）有可能吃掉一整年的存储节省——把它当成一个静态分数，就丢掉了这个条件。

第三处误导，是**把不同量级的东西放在同一张表里**。「扩展性」给全对象存储 5 分、分层存储 5 分，看起来并列；但对象存储的扩展性是「加前缀、不搬数据」，分层存储的扩展性是「多加一档介质与一套规则」。同样是 5 分，一件事是免费的，另一件事是常驻工作量。

第四处误导，是**评的是产品能力，而选型考的是你的运维能力**。「扩展性」「运维复杂度」这些列评的都是方案本身的属性，但真正决定成败的是你的团队能不能把规则长期维护下去——同一个分层方案，在有专人负责数据平台的团队里能跑十年，在三五人的小团队里三个月就无人维护，成本悄悄反弹。这张表里没有「你」这一列，而那一列才是权重最大的。

因此本章的判据不是「几分」，而是三句话：**这套方案在机制上做不到什么**、**它的成本随什么变量增长**、**我离开它要付什么**。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 分层触发依据 | 判据是「写入多久」还是「多久没被读」 | 只看年龄会把仍被每天读取的数据推进冷层，查询慢一个量级以上；同一业务里既有高频表也有死表 |
| 取回代价 | 取回要等多久、按什么计费 | 归档层不是「更便宜的硬盘」；取回延迟与费用是「分层省钱」与「分层制造事故」的分界线 |
| 介质落差 | 相邻两层的延迟差几个数量级 | 落差决定跨层查询能不能被业务接受；落差大到分钟以上时，取回策略必须先于分层落地 |
| 对查询层的透明度 | 业务要不要知道数据在哪一层 | 一旦要，复杂度就转嫁给业务，分层会在几个月内被绕过 |
| 与留史 / 版本的关系 | 分层动作会不会动到历史版本 | 两者耦合时，省钱会顺手删掉时间旅行与合规举证的能力 |
| 单价差 × 体积压缩 | 相邻层单价差多少，数据能压多少 | 分层降单价、压缩降体积，是两个相乘的杠杆；只做一个远达不到目标 |

这 6 条分两类：前两条是**门槛项**——不满足时不是「差一点」，而是「这套分层会变成事故来源」；后四条是**权重项**——重要性随规模与业务形态反转。按顺序读：先过门槛，再比权重。另外，权重项必须按**你自己的组织**来读：同一个方案在两个团队里，运维成本可以差出一个数量级，而这恰恰是打分表最无法覆盖的一列。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 全 SSD | 单层高性能介质 | 所有数据同一介质，无迁移、无规则 | 数据量小、延迟敏感 | 硬件采购或云盘 |
| 全 HDD | 单层廉价盘 | 用介质换成本，性能靠并行摊 | 本地大容量、吞吐型批处理 | 硬件采购 |
| 全对象存储 | 单层对象 | HTTP 接口 + 无限扩展，无目录层级 | 云上新建、以分析为主 | 云服务按量 |
| 分层存储 | 多级介质 + 生命周期 | 按热度把数据分布到不同介质，规则自动迁移 | 通用答案形态 | 云服务 / 自建皆可 |
| HDFS 分层 | 本地集群内多介质 | 存储策略（HOT / WARM / COLD / ALL_SSD / ONE_SSD）声明块落哪种盘 | 本地数据中心 | 开源（Apache Hadoop） |
| 对象存储生命周期分层 | 云上多档存储类 | Standard → 低频 → 归档 → 深度归档，规则声明式下沉 | 绝大多数云上组织 | 云服务按量 |
| 统一存储 | 一套系统多协议 | 同时提供 HDFS 与 S3 语义，底层介质可分层 | 本地 + 云混合、既要生态又要成本 | 开源（Ceph / JuiceFS / JindoFS / Ozone） |
| 表格式分层 | 湖仓内按分区 / 文件分层 | 开放表格式管理文件清单与分区元数据，介质差异由存储侧消化 | Lakehouse 项目 | 开源（Iceberg / Hudi / Paimon） |
| 智能分层 | 存储服务自动判定热度 | 平台监控访问行为，无人工规则地自动迁移 | 不愿长期维护规则的组织 | 云服务（S3 Intelligent-Tiering、OSS 智能分层一类） |
| 手动分层 | 人工或定时脚本搬数据 | 由人决定搬什么、何时搬 | 早期或极少数关键数据 | 自建脚本 |
| AI 驱动分层 | 预测访问模式后再分层 | 用访问序列预测未来热度，提前布置数据位置 | 超大规模、访问模式有规律 | 自研或平台能力 |
| 磁带 / 深度归档 | 最冷层 | 离线介质，取回以小时到天计 | 合规长期留存 | 硬件 / 云服务 |

这 12 个候选分三**族**：**单层介质**（全 SSD、全 HDD、全对象、磁带）、**生命周期分层**（分层存储、HDFS 分层、对象存储分层、统一存储、手动分层）、**表级与智能分层**（表格式分层、智能分层、AI 驱动分层）。同族内部换件代价小（改规则、换存储类），跨族切换要重做数据组织方式（改表格式、搬文件、重建规则体系）。**先分族再选，能省掉一半比较。**

族内的差别也必须说清：

- **单层介质族内**：全 SSD 与全 HDD 的差别是单价与 IOPS 的取舍；全对象与磁带差在取回模型——对象存储"取回慢但不离线"，磁带"取回要挂载、可能要人工介入"。原表把「全 SSD」「全 HDD」「全对象」三列并列打分，掩盖了它们并不在同一维度上：**全 SSD 与全 HDD 是介质选择**（同一套文件系统里换盘，访问方式不变），**全对象是架构选择**（换成扁平命名空间 + HTTP 接口，数据组织方式跟着改）。把「换一块盘」与「换一套访问方式」放进同一列比强弱，比出来的是分数，不是可比性。
- **生命周期分层族内**：真正的差别在**规则由谁执行**。对象存储分层与 HDFS 分层都由存储层自己执行规则（声明式）；统一存储把两套协议映射到同一份介质管理上；手动分层由人执行——人执行的规则必然过期，因为没人会长期每周去搬数据。
- **表级与智能分层族内**：表格式分层作用于「文件与分区」，智能分层作用于「对象」，AI 驱动分层作用于「预测」。前两者是执行层的位置差异，后者是判据的来源差异——它把"按访问行为"进一步推成"按预测的访问行为"。

原 § 7 出现过的候选——全 SSD、全 HDD、全对象、分层存储、对象存储分层（Standard + IA + Glacier）、HDFS 分层（SSD / HDD）、统一存储、智能分层、手动分层、Iceberg / Hudi 表级分层、AI 驱动分层 + 多级介质——在上表中逐条保留，并补入磁带 / 深度归档与统一存储的具体项目名，未做删减。

原 § 7 的决策树用「< TB / TB ~ PB / > PB」三档切开规模，方向是对的——规模确实是分层决策的第一变量——但那三档之间的边界没有给出任何依据，另有两处节点（「云上 / 本地」的分叉、以及「> PB → AI 驱动分层」）同样没有依据。本章 7.4 会把边界补上：它来自「分层年节省额」与「规则维护成本」的对比，以及「介质单价差 × 数据量」的绝对差额；7.5 的阈值依据里再对每个节点逐条解释。

### 7.3 机制差异：为什么它们表现不同

以下 4 个机制维度，决定了候选之间的绝大多数可观察差异。前两个决定「分层会不会变成事故」，后两个决定「分层能不能长期存活」。

#### 7.3.1 分层触发依据：写入时间 vs 访问行为

- **机制是什么**：分层引擎需要一个**可观测的触发信号**。最廉价的是「写入距今多久」（元数据里就有），最贵的是「最近多久被读过」（需要持续采集访问日志）。选哪个信号，决定了误归档的规模。
- **在各候选中的实现差异**：

| 方案 | 触发信号 | 后果 |
| --- | --- | --- |
| 手动分层 | 人的主观判断 | 规则必然过期；没人长期每周搬数据 |
| 按年龄的规则（很多早期生命周期规则） | 对象写入时间 | 三年没写但仍被每天读的表被推进冷层 |
| 按访问行为的规则 | 最近访问时间 | 需要采集访问日志；判定更准，代价是采集链路 |
| 智能分层 | 平台自动采集访问行为 | 无需人工规则，但访问模式判定由平台定义，可解释性低 |
| AI 驱动分层 | 访问序列的预测 | 判据从"过去多冷"变成"未来多冷"，收益更高、可解释性更低 |

- **由此必然导出的性质**：因为**写入时间是一个与访问热度无关的量**，所以以年龄为主判据的规则，会把「写入很久但一直在读」的数据当作冷数据——同一个业务里既有每天被查的维表，也有三年没人碰的归档表，按业务或按年龄划分都会错杀。判据必须落在**数据本身**的访问行为上，且必须以**访问行为为主、年龄为兜底**：年龄只用来处理"从未被读过"这一类访问日志里没有记录的数据。
- **公开证据**：对象存储的生命周期规则以「对象年龄（写入或最后修改距今的天数）」为原生转换条件——AWS S3 Standard-IA 与阿里云 OSS 分层存储自 2016 年起提供这一入口（见主文件 [§1.4 演进历程](05-cold-hot-tiering.md)；条件清单与支持的档位请以官方文档当前版本为准）【公开】。而「按访问行为」在这两家产品里**对应的是自动分层能力，而不是生命周期规则**：S3 Intelligent-Tiering 与阿里云 OSS 智能分层由平台采集访问行为后无人工规则地迁移（见主文件 §1.4：前者 2020、后者 2021）【公开】。**可自行核验的判断**：打开目标产品的生命周期规则文档，若触发条件只有「距今 N 天」一类、没有「最近访问时间」，则该产品的「按访问行为」必然落在自动分层能力上——把这两者当成同一条规则的两副面孔，会照着生命周期规则的文档去搭一套它做不到的判据。本章 [§6 的 Netflix 案例](05-cold-hot-tiering-section-6-sec6.md) 记录了把"访问频次为主判据、年龄为兜底"作为核心设计的落地形态。
- **失效条件**：当访问日志本身不可信（大量扫描型查询周期性触碰全部数据）时，「访问行为」这个信号会被噪声淹没——一个每月跑一次全量扫描的作业，会让所有数据看起来都是热的。此时判据要退回到"业务标注 + 年龄"的组合，而不是继续加大访问行为的权重。
- **采集访问行为这件事本身有成本**：精确的"最近被读过"需要保存每个对象或每个分区的访问记录，冷数据规模越大，这份记录的体量也越大。所以工程上的常见做法是**分层采集**：热层记到对象级，冷层只记到分区 / 前缀级。精度下降会直接变成误归档率上升，这二者之间的取舍必须在设计阶段就写下来，而不是等到报表变慢时才发现。

#### 7.3.2 取回代价：写入便宜，读出贵

- **机制是什么**：分层介质的成本不对称——把数据**放进去**几乎不花钱，把数据**取出来**要付出时间与费用。所以分层不是「把硬盘换便宜的」，而是「用取回代价换存储单价」。
- **在各候选中的实现差异**：

| 方案 | 取回形态 | 取回代价落在哪 |
| --- | --- | --- |
| HDFS 分层（本地多介质） | 块已在本地，迁移是后台动作 | 主要是迁移带宽与后台 I/O |
| 对象存储生命周期分层 | 即时（低频档）→ 分钟到小时级（归档档） | 取回时间 + 按量取回费用 |
| 磁带 / 深度归档 | 需挂载，小时到天级 | 人工/调度介入 + 介质调度 |
| 表格式分层 | 文件级，引擎按表名访问 | 跨层查询的延迟，业务可感知 |
| 智能分层（部分档位） | 自动取回，可能异步 | 取回费用 + 短暂延迟 |

- **由此必然导出的性质**：因为归档档的取回是**异步且按量计费**的，所以只要某类数据存在"可能被临时调用"的要求，它就不该直接进归档档——正确做法是先给它配**预热 / 主动取回**机制，让"临时调用"走一条已经预热好的路径。反向的性质同样成立：因为低频档的取回是即时的，所以**低频档与归档档的取舍不应该按"数据重不重要"来分，而应该按"取回能等多久"来分**——这是两个不同的问题。
- **公开证据**：归档档的取回时间与取回计费方式是**按档位分别列明**的——AWS S3 Glacier 与阿里云 OSS 冷归档（见主文件 [§1.4 演进历程](05-cold-hot-tiering.md)：前者 2017、后者 2018）都取「存储单价更低 + 取回另行按量计费」这一形态，档位名、取回时长与计费规则请以官方文档当前版本为准【公开】；本章 [§6 的 Netflix 案例](05-cold-hot-tiering-section-6-sec6.md) 与 [§6 的阿里云 OSS 案例](05-cold-hot-tiering-section-6-sec6.md) 都记录了"取回代价首次使用即事故"这一失败教训。
- **失效条件**：当访问模式是**不可预测的偶发全量读取**（如年度审计要抽查一批随机对象）时，任何按"不再访问"假设建立的分层都会在抽查时暴露——此时应立即启用批量取回模式，并把这批抽查看作一次计划内的成本，而不是故障。
- **取回档位要提前选**：归档档内部通常再分「加急 / 标准 / 批量」这类取回优先级，越快越贵——AWS S3 Glacier 提供加急 / 标准 / 批量三档取回，阿里云 OSS 的归档与冷归档同样按解冻优先级分档；各档的名称、取回时长、上线时间与当前价格请以官方文档与功能发布记录为准（主文件 [§1.4](05-cold-hot-tiering.md) 记录了这两条归档线各自的公开出现年份）【公开】。要回答的问题不是"能不能取回"，而是"哪一档取回能落在业务可接受的等待里"。

#### 7.3.3 对查询层的透明度：统一入口 vs 按层暴露

- **机制是什么**：分层在物理上把数据放到了不同介质，但**逻辑上是否还是同一张表 / 同一个路径**，由架构决定。逻辑统一时，介质差异被存储侧消化；逻辑分裂时，业务必须自己知道数据在哪一层。
- **在各候选中的实现差异**：

| 方案 | 逻辑视图 | 业务的负担 |
| --- | --- | --- |
| 表格式分层（Iceberg / Hudi / Paimon） | 一张表，物理文件分布在不同介质 | 无：按表名查即可 |
| 对象存储生命周期分层 | 同一个对象路径 | 无：按路径取即可（代价是取回延迟） |
| HDFS 分层 | 同一个 HDFS 路径 | 无：存储策略对应用透明 |
| 手动分层（搬到另一套系统） | 两套命名空间 | **需要**：业务要判断查哪一套 |
| 按业务划分存储系统 | 多个入口 | **需要**：跨层查询要在应用层拼装 |

- **由此必然导出的性质**：因为分层一旦对查询层可见，"查哪一层"这个问题就落到业务方头上，所以它会在很短的时间内被绕过——业务为了省事，要么全查热层（成本没降），要么把冷数据再复制一份到热层（成本反而上升）。所以**分层能被大规模采纳的前提，是它对查询层透明**；透明度不是体验优化，是这套机制能否存活的条件。
- **公开证据**：开放表格式以"一张表 + 文件清单 + 分区元数据"的方式管理物理文件，介质位置不在 SQL 语义里——Apache Iceberg（2018 年开源并进入 ASF 孵化）、Apache Hudi（2017 年开源、2019 年进入 ASF）、Apache Paimon（原名 Flink Table Store，2023 年进入 ASF 孵化、2024 年 1.0 毕业）的项目文档与表规范均可自行核验【公开】；本章 [§6 的字节湖仓分层案例](05-cold-hot-tiering-section-6-sec6.md) 把"分层对查询可见"列为首要失败教训；[§6 的 Snowflake 案例](05-cold-hot-tiering-section-6-sec6.md) 记录了「分层不改变计算层行为」的同一设计取向。
- **失效条件**：当跨层查询的延迟本身已经超出业务容忍（例如点查要落到归档档）时，透明反而变成"看不见的慢"。此时正确做法不是把数据搬回热层，而是在**取回策略**上加一层预热，或者干脆承认这类数据不该被分层。

#### 7.3.4 分层与留史正交：介质维度 vs 版本维度

- **机制是什么**：系统里有两件独立的事——数据**存在哪种介质**上（成本维度），以及**保留多少历史版本**（正确性维度）。它们共用同一份物理字节，所以实现上极易被合并成一个动作。
- **在各候选中的实现差异**：

| 方案 | 分层动作作用于 | 版本回收由谁决定 | 耦合风险 |
| --- | --- | --- | --- |
| 表格式分层（Iceberg / Hudi） | 数据文件与清单文件的位置 | 快照过期策略（独立过程） | 把快照过期写进同一个作业，会误清仍在引用的数据 |
| 对象存储生命周期 | 对象本身（含旧版本） | 版本保留策略 | 生命周期规则若不区分版本，会连历史版本一起下沉或删除 |
| 快照 / 时间旅行机制 | 当前版本 | 保留期配置 | 分层"顺手清理"会让时间旅行失效 |
| 手动分层 | 由人搬运 | 由人决定 | 无人对"哪些能删"负责 |

- **由此必然导出的性质**：因为分层动作与版本回收**共用同一批文件、却服务于两个不同的目标**，所以一旦把它们写进同一个流程，省钱的动作就会顺手删掉历史——而历史一旦删掉，时间旅行与合规举证同时失效，且无法从任何备份中恢复"当时看到的是什么"这一事实。正确的做法是让两个维度各自独立：**分层只改介质位置，版本回收只由保留期策略决定**，两者互不触发。
- **公开证据**：表格式把"数据文件 + 快照"作为两类不同的元数据对象管理——Apache Iceberg 表规范（Table Spec）中快照（snapshot）引用一批文件清单、文件清单再引用数据文件（data file），两者是不同层级的概念，该规范随项目 2018 年进入 Apache 孵化后公开、可自行核验【公开】；本章 [§6 的 Snowflake 案例](05-cold-hot-tiering-section-6-sec6.md) 把"分层只管介质、版本回收只由 retention 决定"作为核心设计，并把"分层时误清历史版本"列为失败教训。
- **失效条件**：当保留期本身没有配置（历史无限增长）时，"正交"就退化成"分层打折、留史无限"——成本优化被留史成本吃掉。此时要解决的是保留期配置，而不是把两件事重新耦合起来。
- **顺带划清一个边界**：不可删改留存（对象锁一类能力）与分层也是两件事——前者限制「能不能删」，后者决定「放在哪里」。把两者混为一谈，就会出现为了省钱把不可删的数据搬到不支持保留策略的档位上。二者必须同时成立才叫合规。【公开】（AWS S3 以 Object Lock 提供不可删改留存，2018 年起可用；阿里云 OSS 以「合规保留策略」提供同类能力，其上线时间与各能力支持的存储档位请以官方文档与功能发布记录为准）

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ Σ(数据量_层 i × 单位成本_层 i)      ← 存储成本，分层能压的就是这一项
     + 取回与请求费用(次数 × 单次价)         ← 隐性且随访问模式剧烈变化
     + 迁移 / 后台 I/O 成本                  ← 随数据流动量
     + 运维成本(规则维护、成本可视、回归)      ← 随常驻规则数与业务数
     + 性能损失(跨层查询延迟)                 ← 不直接进账单，但进业务等待
```

**分层只改变第一项的系数，其余四项都可能因为分层而变大。** 这正是「分层一定省钱」这句直觉最容易出错的地方：第一项的下降是确定的，后面四项的上升取决于访问模式。

【推算】先看相邻层之间的**单价落差**（以主文件 [§2.1 介质分级表](05-cold-hot-tiering.md) 的单位成本为起点）。该表里两族介质的计价周期不同——自建介质是年化成本、云对象存储是月单价——所以下面**一律先把月价乘 12 换算到年化口径再比**：

- 高性能层 $0.30/GB·年 ÷ 对象存储标准层 $0.276/GB·年（$0.023 × 12）= **约 1.1 倍**
- 高性能层 $0.30/GB·年 ÷ 归档层 $0.048/GB·年（$0.004 × 12）= **约 6.3 倍**
- HDD 层 $0.04/GB·年 ÷ 归档层 $0.048/GB·年 = **约 0.83 倍**（HDD 反而更低）
- 高性能层 $0.30/GB·年 ÷ 磁带 $0.001/GB·年 = **约 300 倍**

这里有一条必须说清的结论：**换算到同一周期后，HDD 的单位成本低于对象存储标准层**（$0.04 对 $0.276/GB·年；反过来说，S3 Standard 比自建 HDD 贵约 6.9 倍）。两族单价的构成不同——自建 HDD 是"裸盘折旧 + 机架电力 + 运维人力"，云 Standard 是"多副本持久性 + 多可用区 + 免运维 + 按需弹性"的服务价——但即便两边都摊全，**"存到云上就便宜"这个直觉在最常用的标准档上并不成立**。

**两条阶梯换算到同一周期后，数值上几乎是重合的**：NVMe `$0.30` 对 Standard `$0.276`（1.1 倍）、SATA `$0.15` 对 IA `$0.15`（约 1.0 倍）、HDD `$0.04` 对 Glacier `$0.048`（0.83 倍）；只有磁带 `$0.001` 显著低于 Deep Archive `$0.0119`（约 0.08 倍）。**所以"分层"这个动作在两边都能省钱，但"沉到哪一档"不能照抄**：云上的便宜档位买到的是**更弱的取回能力**——$0.048/GB·年的 Glacier 取回要等分钟到小时、还有最小存储期与按量取回费，$0.04/GB·年的自建 HDD 随时在线。在本地，便宜的介质只是慢；在云上，便宜的档位还会"不在线"。这一条决定了同一个分层策略不能在两边逐档平移。

【推算】再看一次完整的分配算例。假设 1 PB 数据、按温度同热度分布为 20% / 30% / 50%（**这个比例是假设，不是结论**，它只用于展示算法；按 1 TB = 1000 GB 计）：

- 高性能层 200 TB × $0.30/GB·年 = 200 000 GB × 0.30 ≈ **$60.0k/年**
- HDD 层 300 TB × $0.04/GB·年 = 300 000 GB × 0.04 ≈ **$12.0k/年**
- 对象存储标准层 500 TB × $0.023/GB·月 × 12 = 500 000 GB × 0.276 ≈ **$138.0k/年**
- 合计 ≈ **$210.0k/年**
- 对照全部放在高性能层：1 000 000 GB × 0.30 = **$300k/年**
- 差距 = 300 ÷ 210 ≈ **1.4 倍**

推导链完整：数据量 × 单价 = 各层成本，求和得到分层方案；同一总量 × 高性能层单价 = 对照方案。**这个 1.4 倍里没有算取回费用与运维成本，而 1.4 倍本身已经很薄**——只要取回量或请求次数稍大，这点差额就会被吃掉。**第一项能压多少，取决于下沉的目标档位离热层有多远，而不是取决于"分了层"这件事本身**：本例省下的 $90k 里，$78k 来自那 300 TB 落到 HDD（300 000 GB × ($0.30 − $0.04)），只有 $12k 来自 500 TB 落到对象存储标准层（500 000 GB × ($0.30 − $0.276)）——**标准层这一档几乎不省单价，靠的是体量大才凑出一笔数**。若把这 500 TB 改放到 IA（年化 $0.15）或 Glacier（年化 $0.048），总成本会降到 $147k 与 $96k，差距随即拉开到 2.0 倍与 3.1 倍。

【推算】再看「小数据不要分层」这条结论的依据。1 TB 数据从高性能层下沉到对象存储层，一年能省多少？（云侧单价先乘 12 换到年化）

- 下沉到标准层：1000 GB × ($0.30 − $0.023 × 12) = 1000 GB × ($0.30 − $0.276) = 1000 × 0.024 ≈ **$24/年**
- 下沉到归档层：1000 GB × ($0.30 − $0.004 × 12) = 1000 GB × ($0.30 − $0.048) = 1000 × 0.252 ≈ **$252/年**

也就是说，**小于 1 TB 的数据集，下沉到标准层一年只省下 $24——连一名工程师十几分钟的工时都不值**；改下沉到归档层也只有 $252，仍低于规则设计、取回策略、成本可视与回归这套常驻工作的人力成本，而分层还要额外承担误归档的风险。**注意这两个数差了 10 倍，它们背后是两个不同的动作**，引用时必须写明是哪一种。【经验】行业普遍在百 TB 量级以下先做压缩与分层规则模板、暂不投入专人维护，到 PB 量级才把它作为专项。

【经验】压缩是分层的乘数而非替代：列存 + Zstd 在日志与分析类数据上常见的压缩比区间是 5~10 倍，具体取决于数据分布与编码参数，必须在自己的数据上 benchmark；**分层降的是单价，压缩降的是体积，两者相乘**，只做其中一个通常达不到目标。**注意倍数要先确认基准**：相对未压缩的原始文本是 5~10 倍；相对已经列存化、尚未压缩的文件，再叠加 Zstd 通常只再省 50~80%（即再压 2~5 倍）——主文件 §2.3 给的是后一种百分比口径，本节给的是前一种倍率口径，两者说的是不同基准，不是两个互相矛盾的数字；引任何一个之前，先写清基准是哪一个。

【经验】还有一条常被漏掉的要求：**成本函数里的每一项都必须能被观测，否则分层等于盲开**。最小可用的指标有三个——各层数据量的分布、各层的取回量与请求次数、以及**误归档条数**（被下沉后短期内又被读取的对象数）。第三个最重要，因为它是唯一能直接回答「我的分层判据选对了没有」的量。多数团队的看板只放了前两个，结果是省了钱，却答不出「有没有伤到业务」。

### 7.5 决策树（每个分支都要有阈值依据）

树的形状由判据的先后顺序决定：**先问值不值得分层**（数据量够不够大），**再问能不能用归档档**（能接受多长的取回），**然后问怎么分**（判据与透明度），**最后才问怎么长期维护**（正交、可视、智能化）。

```
[你的数据总量在哪个量级？]
 ├─ < 1 TB
 │   └─ 全 SSD（不分层）：分层收益 < 规则维护成本
 │
 ├─ 1 TB ~ 100 TB
 │   └─ [数据在云上还是本地？]
 │        ├─ 云上 → 对象存储生命周期分层（先做两档：标准 + 低频）
 │        └─ 本地 → HDFS 分层（存储策略）或统一存储；先只做热 / 冷两档
 │
 └─ > 100 TB
     ├─ [能否接受「取回要等」（分钟到小时级）？]
     │    ├─ 否 → 只用「即时取回」的档位（低频档），不进归档档
     │    └─ 是 → 可启用归档 / 深度归档 / 磁带；同时必须配套「预热 / 主动取回」
     │
     ├─ [分层依据用什么信号？]
     │    ├─ 有可信的访问日志 → 以访问频次为主判据，年龄为兜底
     │    └─ 无（或日志被周期性全量扫描污染）→ 业务标注 + 年龄组合，并先补访问采集
     │
     ├─ [业务是否需要知道数据在哪一层？]
     │    ├─ 是（按层暴露出多套入口）→ 先改造成统一入口（统一表格式 / 统一路径），再分层
     │    └─ 否 → 表格式分层 / 对象存储生命周期分层 / HDFS 存储策略
     │
     ├─ [是否要保留历史版本（时间旅行 / 快照 / 合规留存）？]
     │    ├─ 是 → 分层与版本回收必须解耦：分层只改介质，回收只由保留期决定
     │    └─ 否 → 分层与快照清理可共用同一套运维流程，但仍需独立校验
     │
     └─ [规模到 PB 级以上了吗？]
          ├─ 否 → 手动配置 + 定期回归即可
          └─ 是 → 多级介质 + 成本可视闭环；规则维护作为常驻工作
                  （访问模式有规律时再考虑智能分层 / AI 驱动分层）
```

**阈值依据**（与树上每个判断节点一一对应）：

- **节点「< 1 TB 不分层」**：来自 7.4 的推导——1 TB 从高性能层下沉到对象存储层，下沉到标准层年节省约 $24，下沉到归档层约 $252。这两个数都低于维持一套分层规则、监控与回归所需的人力成本（按小时计即可覆盖）。依据是**节省额与维护成本的对比**，不是习惯。
- **节点「1 TB ~ 100 TB 只做两档」**：档位每加一层，就多一份取回时间与计费规则要解释给业务听、多一条规则回归路径。【经验】不到百 TB 的量级上，第二档带来的额外节省通常小于它增加的运维面，所以先做「标准 + 低频」两档、把规则跑稳，再考虑第三档。
- **节点「数据在云上还是本地」**：机制判据——云上分层的执行者是对象存储服务（声明式规则、没有搬运作业），本地分层的执行者是 HDFS 存储策略或统一存储（需要集群侧配置与后台迁移带宽）。两边不能照抄同一套策略：7.4 已说明自建介质与云档位换算到同一周期后数值几乎重合（NVMe `$0.30` 对 Standard `$0.276`、HDD `$0.04` 对 Glacier `$0.048`），**差的是同一笔钱买到的取回能力**——云上便宜档位还附带"不在线"（异步取回、最小存储期、按量取回费），本地便宜的介质只是慢。
- **节点「> 100 TB 才考虑归档档」**：来自 7.4 的单价落差——归档层单价约为对象存储标准层的 1/6（月价 $0.004 对 $0.023/GB·月，0.004 ÷ 0.023 ≈ 0.17；年化后 $0.048 对 $0.276/GB·年，比值相同），只有当数据量大到绝对差额可观时，这笔下降才值得用取回延迟去换。量级判据来自「单价差 × 数据量」的绝对额，不是拍数。
- **节点「能否接受取回要等」**：机制判据——归档档的取回是异步且按量计费的（云厂商文档按档位列明取回时间与计费方式，具体以官方文档当前版本为准）。只要存在"可能被临时调用"的数据，它进归档档就必然在第一次被调用时暴露。
- **节点「分层依据用什么信号」**：机制判据——判别标准是访问日志是否可信。周期性全量扫描会让"热"这个信号失真，此时应退回"业务标注 + 年龄"组合，并先补访问采集，而不是加大访问行为的权重。
- **节点「业务是否需要知道数据在哪一层」**：机制判据——判别的标准是有几个查询入口。多入口意味着跨层查询要在应用层拼装，分层会在短期内被绕过；所以顺序是**先统一入口，再分层**，不能反过来。
- **节点「是否要保留历史版本」**：机制判据——分层作用于介质位置、回收作用于保留期，两者共用同一批文件。共用一个流程就会出现"省钱顺手删历史"，所以只要需要时间旅行或合规留存，就必须显式解耦。
- **节点「规模到 PB 级以上」**：量级判据——PB 级以上，单层介质无法同时满足成本与性能（7.4 的算例中，1 PB 单层与分层相差约 1.4 倍），且规则数量随业务数增长，必须把成本可视与规则回归做成常驻闭环。【经验】

用法上有两点要强调。其一，这棵树**不是一次走到底的清单，而是四组各自要回答的问题**——值不值得分、能不能用归档、怎么分、怎么长期维护；现实中最常见的错误顺序是先被规模吸引（「我们数据量大」），再回头发现访问日志根本没有采集、查询入口还没有统一。其二，**树上每一层都允许"不做"**——不做归档档、不做智能分层、不做 AI 预测，都是合法答案；分层唯一不能省的是「判据选对」与「与留史解耦」这两条，因为它们做错的代价不可逆。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 数据 < 1 TB | 全 SSD | 单层对象存储 | 分层节省额低于规则维护成本（见 7.4 推导） |
| 云上、以分析为主、百 TB 级 | 对象存储生命周期分层（两档起步） | 全对象存储 + 压缩 | 全对象单层在跨越百 TB 后缺少进一步下压空间 |
| 本地数据中心、已有 HDFS | HDFS 分层（存储策略） | 统一存储 | 直接换统一存储要重做命名空间与工具链 |
| 本地 + 云混合 | 统一存储（Ceph / JuiceFS / JindoFS / Ozone） | HDFS + 对象存储双栈 | 双栈意味着两套权限、两套目录与跨栈一致性 |
| Lakehouse 项目 | 表格式分层 + 底层对象存储 | 仅依赖对象存储生命周期 | 表级分层可按分区热度下沉，粒度比对象级更细 |
| 不愿长期维护规则 | 智能分层 | 手动分层 + 季度回归 | 手动规则必然过期，且过期是静默的 |
| 访问模式有规律、规模超 PB | AI 驱动分层 + 智能分层 | 智能分层 | 预测型分层需要足够的访问序列与验证集，缺了就先别上 |
| 合规长期留存 | 归档层 + 不可删改保留策略 | 磁带 | 磁带取回要挂载与调度，不适合"偶发但需在线可取"的留存 |
| 取回可能被临时调用 | 低频档（即时取回） | 归档档 + 预热机制 | 无预热的归档档第一次被调用就是事故 |
| 小文件极多、请求次数惊人 | 先合并小文件再分层 | 直接对小文件配生命周期规则 | 请求与取回费用可能超过存储费本身 |
| 历史版本必须可查 | 分层只改介质，保留期独立配置 | 把快照过期并入分层作业 | 合并流程会顺手删掉历史，且不可恢复 |

**4 个常见组合**（原组合清单保留并补出职责边界与运维代价）：

1. **HDFS + 对象存储（混合）**：HDFS 承担热数据的低延迟读写与已有生态，对象存储承担冷数据的低成本与无限容量。职责边界是「计算靠近热数据、冷数据只为留存与偶尔回捞」。运维代价是两套命名空间与两套权限，以及一条跨栈的数据搬运路径——**这条路径必须有校验，否则会出现"冷侧缺文件、热侧已删除"**。
2. **Lakehouse + 分层存储**：Iceberg / Hudi / Paimon 负责表与文件清单，底层对象存储负责介质与生命周期。职责边界是「表格式管逻辑与版本，存储管介质与成本」。运维代价是两件事必须解耦：数据下沉与快照过期各走各的流程，且各自独立校验。
3. **智能分层 + 手动分层**：智能分层处理占绝大多数的通用数据（无需人管），手动分层只处理少数关键数据（例如必须留在某个档位的合规数据、或必须预热的高价值数据）。职责边界是「平台管默认、人管例外」。运维代价是要有一份"哪些数据被手工钉在某个档位、为什么"的清单——没有这份清单，例外会变成没人敢动的黑盒。
4. **AI 分层 + 智能分层**：AI 分层用访问序列预测未来热度、提前布置数据位置，智能分层继续兜住预测之外的长尾。职责边界是「预测管提前量、规则管兜底」。运维代价是预测需要验证集与回归——**没有回测的预测型分层，等于把误归档的风险从规则搬到了模型里**，而且更难解释。

组合的运维代价随组件数**超线性**增长：两件之间是一条搬运路径与一组校验，四件之间是六条潜在的不一致。所以每加一层介质或一个组件，都要能说清它消掉的是哪一条成本或哪一类事故；说不清时，它带来的规则与校验成本会超过它省下的存储费。

还有一条容易被忽略的判据：**组合里必须有一个组件对「误归档」负责**。分层一旦上了规模，最贵的错误不是多花了存储费，而是把还在被读的数据推进了冷层——如果没有一个组件持有"哪些数据被下沉后又被读过"这个指标，整套组合就没有反馈回路，规则会一直按错误的方向执行下去。

### 7.7 选错的代价与迁移成本

**选错的代价可以事先归账。** 四类反模式的损失落在不同的账上：反模式一落在**事故账**（冷数据被业务临时调用，第一次就是小时级等待）；反模式二落在**账单单账**（分层省下的单价被取回与请求费用吃掉，账单不降反升）；反模式三落在**不可逆账**（历史版本被顺手清理，时间旅行与合规举证同时失效，且无法从备份恢复）；反模式四落在**维护账**（规则过期后成本静默回升——它不是某一笔费用变贵，而是"该降的没降"，所以账单上看不出异常）。四者的共同点是**都不会在压测里暴露**——压测测的是吞吐与 P99，而这四件事伤的是可预期性、可回溯性与可维护性。

**反模式一：生命周期规则只看年龄，不看访问行为。** 症状是上线三到六个月后，某张"很久没写"但仍被每天查询的表被推进冷层，下游报表从秒级变成小时级。后果是查询慢一个量级以上，且因为没有访问行为的采集，团队无法事先知道哪些数据处于这种状态。正确做法是**以访问频次为主判据、年龄为兜底**，并先补齐访问日志采集。

**反模式二：只看存储单价，不看取回与请求费用。** 症状是大量小文件被下沉、隔月被批量取回，账单里存储费下降而取回费上升。后果是总成本不降反升，团队却因为"单价确实降了"而找不到原因。正确做法是在分层前先算**取回量与请求次数**这两个变量，并把"取回费用"纳入成本可视看板。

**反模式三：分层与版本回收写在同一个流程里。** 症状是分层作业上线后，时间旅行查不到数据、合规审计取不到某个时点的快照。后果是不可逆——被清掉的历史版本无法恢复。正确做法是**分层只改介质位置，版本回收只由保留期策略决定**，两者各自独立校验与告警。

**反模式四：手动分层靠人长期维护。** 症状是上线时规则正确、半年后无人执行，成本回升到分层之前的水平。后果是"做了分层"变成一条已经过期的配置，而没人知道自己已经不达标。正确做法是从一开始就选**声明式规则或智能分层**，把人的角色限定在"设计规则与例外清单"，而不是"执行迁移"。

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 全 SSD → 分层存储 | 按热度下沉，可在线进行 · 中 | 基本不变（保持统一入口） · 低 | 新增规则、取回策略与成本可视 · **高** | 中 |
| 分层存储 → 全 SSD（回退） | 冷数据回捞，受取回延迟约束 · **高** | 基本不变 · 低 | 回退规则、保留期与预热机制 · 中 | 低 |
| 手动分层 → 声明式 / 智能分层 | 不改数据，只改触发方式 · 低 | 不变 · 低 | 重建规则体系与回归流程 · 中 | 中 |
| 单栈 → 统一存储 | 全量搬迁 + 双跑验证 · **高** | 协议层可兼容，工具链需验证 · 中 | 两套协议映射、权限与配额重建 · **高** | **高** |
| 对象级分层 → 表格式分层 | 数据不动，元数据重构 · 中 | SQL 基本不变，表格式迁移需验证 · 中 | 快照与分区维护成为常驻工作 · 中 | 中 |
| 规则式 → AI 驱动分层 | 不改数据 · 低 | 不变 · 低 | 预测管线 + 回测与验证集 · **高** | **高** |

（工作量量级为【经验】档：**高** = 需要专项项目与全量数据动作，**中** = 需要一到两个迭代，**低** = 配置级调整。）

看这张表要抓住一条：**迁移成本的大头几乎总落在「取回侧」与「验证侧」，不在存储侧**。把数据放下去通常很快，把它拿回来往往受取回时间与费用约束；而"分层之后到底省没省、有没有误归档"，只有在有成本可视与误归档指标的前提下才能回答。所以更稳的顺序是：先建成本可视与访问采集 → 再定规则 → 最后才搬数据。顺序反过来，就会在搬完之后无法回答"这一步做对了没有"。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 数据 < 1 TB | 全 SSD，不分层 | 分层年节省（约 $24~252/年/TB）低于规则维护成本 |
| 云上、百 TB 级、以分析为主 | 对象存储生命周期分层，两档起步 | 规则由存储层执行，无需搬运作业；先跑稳再扩档 |
| 本地已有 HDFS | HDFS 分层（存储策略） | 存储策略对应用透明，不必改动业务访问路径 |
| 本地 + 云混合 | 统一存储 | 一套介质管理 + 两套协议，避免两套命名空间与权限 |
| PB 级、Lakehouse | 表格式分层 + 对象存储生命周期 | 表级粒度更细，且介质差异不进 SQL 语义 |
| 取回可能被临时调用 | 低频档，或归档档 + 预热 | 归档取回异步且按量计费，第一次调用就是事故 |
| 需要时间旅行 / 合规留存 | 分层与版本回收解耦 | 两者共用同一批文件，合并流程会顺手删掉历史 |
| 访问模式有规律、规模超 PB | 成本可视闭环 + 智能 / AI 分层 | 预测型分层需要回测，不能替代成本可视与误归档指标 |
| 只有少数关键数据要特殊对待 | 智能分层 + 手动分层（例外清单） | 平台管默认、人管例外，例外必须有台账 |
| 取回时间不可接受又必须降本 | 压缩 + 就地换介质，保留即时取回档 | 分层降本的前提是取回代价可被业务吸收，吸收不了就别降 |
| 规则没人维护、成本已反弹 | 先建成本可视与误归档指标，再谈自动化 | 没有度量时，任何自动化都只是把偏差藏得更深 |
| 有合规留存要求 | 归档层 + 保留策略，并确认该档位支持不可删改 | 留存与分层是两件事，必须同时成立才叫合规 |

> 本节小结：这些方案之间，**唯一真正起决定作用的那一条差异，是「分层触发用的是写入时间还是访问行为」**。用写入时间，分层会在几个月内制造一类静默事故——仍被高频读取的数据被推进冷层，而团队事先无从知道是哪些；用访问行为（并配以年龄兜底），误归档才会被压到可控。判据定对之后，二次筛选由两件事决定：**取回能不能被业务接受**（决定能否用归档档，以及要不要配套预热），以及**分层对查询层是否透明**（不透明就会被绕过，成本优化在几个月内反弹）。而分层与版本回收必须始终正交——这是唯一一条一旦做错就无法回头的地方。
>
> 配合 [§ 2 核心原理](05-cold-hot-tiering.md)、[§ 3 设计模式与范式](05-cold-hot-tiering-section-3-sec3.md) 与 [§ 6 落地实践](05-cold-hot-tiering-section-6-sec6.md) 阅读。

一句话的选型顺序：**先确认数据量够不够大，再确认取回能不能被业务接受，然后才选档位与判据，最后把分层与留史拆开。** 顺序倒过来，就会得到一个省了钱但让业务变慢、或者省了钱但把历史删掉的系统——而这两件事的代价都比多花的存储费高。
