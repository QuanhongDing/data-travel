## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是没有时间维度。在同一份清单里，「已经 GA、有人在生产里跑」和「厂商演示里跑过一次」被写成格式完全相同的两行；读者据此排路线图，就会把一次演示当成一个可以排期的工作项。所以本节不按热度排，而按**可核验的成熟度**排。

判据只有三条：

- **①** 已 GA 且有正式 release note——能按名字与年份被第三方检索到；
- **②** 有第三方（非厂商）公开生产案例——建设方自述不算第三方；
- **③** 接口稳定——不是每次小版本都会改的预览特性。

按这三条，方向只分三级：

| 级别 | 判据（三条全中才算） | 你该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ①②③ 全中 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口或生态未稳；或仅有厂商自有案例；或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

第②条是本节最容易被绕过的一条，所以把规则写在前面：

- **第②条不满足就是 L2**，不写「准 L1」「L1 的边界案例」这类说法；
- **不在单格里放宽判据**——本节没有为离线计算这一主题另立修正条文，上表三条判据在 5.2 的逐项评估里逐字沿用；
- **L1 行里一旦出现「边界」「待核」这类自证不满足的字眼，说明它本来就该是 L2。**

本主题在 AI 时代出现的可辨识方向有四个，按**机制**（而不是按话题）归入下面四行——归类只改变组织方式，不改变任何一条的成熟度。本节遵循一条更严的纪律：**不把「某产品在某版本支持某能力」写成断言**——同一产品在不同版本里的状态不同，写错比省略更贵——只锚定 release note 的名称与年份。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **把模型调用搬进批作业** | L2 | ① 满足：Spark 4.0.0 于 2025 年正式发布，发行说明含 SQL 侧的模型调用函数族；② 不满足：无可指名的第三方（非厂商）公开生产案例；③ 不满足：函数族与模型服务端点在发行版之间不一致 | 用它做「离线生成向量、抽取实体」，但把模型版本与提示词版本写进输出表属性，不让下游依赖不可重放的结果 |
| **自然语言 → SQL 的取数入口** | L2 | ① 满足：厂商产品有正式发布说明（2024）；② 不满足：皆为厂商自有案例；③ 不满足：语义层格式、模型与提示词都在变 | 只做「候选生成 + 人审核」，且入口开放前必须先接上机器可读的密级与口径 |
| **计算去找数据：内嵌 OLAP 与联邦查询** | L2 | ① 满足：内嵌引擎 1.0 于 2024 年正式发布、联邦查询引擎已 GA 多年；② 不满足：新用法（被程序或 Agent 当作内嵌分析组件）无可指名的第三方生产案例；③ 不满足：多机扩展与外部格式、向量扩展的接口仍在变 | 单机场景直接用；跨源查询前先确认每个源能不能给出统计信息 |
| **调优与运维的自治** | L3 | ① 不满足：没有把「自治调优」作为正式 GA 特性的 release note；② 不满足；③ 不满足：建议接口、指标口径与回滚机制都没有稳定形态 | 先补可观测性；不要把任何自动建议直接接到生产队列参数上 |

**本节四行里没有 L1。** 这不是对产品的判断，而是第②条的门槛使然：四行里有三行的 ① 成立且可直接指名——「内嵌 OLAP」有 1.0 的正式发布、「引擎内置模型调用」有 4.0 的正式发行说明、「自然语言 → SQL」有厂商的正式发布说明——但这三行都拿不出**可指名的第三方（非厂商）公开生产案例**。按上面的规则，缺第②条就是 L2，本节不做例外。

由此得到本主题的正确姿态：

- AI 相关的这几项**都可以做 PoC，但不要成为核心依赖**；
- 真正可以排进路线图的离线计算能力——分区并行执行与运行时自适应（机制见本章 §2.2）、shuffle 与 stage 边界、分区级重算（机制见本章 §7.3.1 与 §7.3.2）——**都是既有机制，不属于本节的新前沿**；
- 本节的价值不在于告诉你「未来会怎样」，而在于告诉你**这四条里哪一条会真的改动你的架构**。

还有一件事要先说清楚，否则后面四条会被误读：**AI 对这四条的改动深度完全不同。**

- 方向一（模型调用）改变的是**成本函数**——批作业里第一次出现按 token 计费、且结果不确定的算子；
- 方向二（自然语言）改变的是**接口边界**——SQL 从「人的产出物」变成「机器的候选产出物」；
- 方向三（内嵌与联邦）**没有被 AI 改变**，它只是多了一个新调用方（程序与 Agent）；
- 方向四（自治）改变的是**人机分工**——诊断这一步被外包出去，但决策权没有移交。

把四条放在一个清单里读，会得出「离线计算全面 AI 化」的结论；分开读才会发现：**其中只有第一条是执行模型层面的变化。**

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 把模型调用搬进批作业：从「算得准」到「算得起、且可重放」

- **旧做法与它的卡点**：批处理引擎的代价函数里只有三项——`Cost = α × I/O + β × CPU + γ × Network`（见本章 §2.2），它的隐含承诺是「同样的输入 + 同样的代码 = 同样的输出」。要用模型加工数据，旧做法是把数据搬出引擎：
  - 导出到对象存储 → 用外部脚本或服务逐条调用 → 再导回来；
  - 卡点不在算力，而在**边界**：一旦跨出引擎的调度与故障恢复范围，分区、重试、血缘这三样东西同时失效；
  - 而且逐条调用意味着吞吐由服务端的并发配额决定，**跟你买了多少机器无关**。
- **AI 改变了什么机制**：把「调用模型」从引擎外的独立服务搬成引擎内的一类算子（SQL 侧的模型调用函数族，以及被引擎当作普通 map 算子调度的批量推理）。机制上改变的是：**一个非确定性的外部调用被纳入了引擎的分区、重试与调度体系**——这是执行层面的变化，不是换个前端。
- **由此得到的**：因为调用变成了算子，所以它自动获得了批处理的三个既有性质——按分区并行、随作业重试、被同一个 DAG 调度。于是：
  - 「给十亿行文本生成向量」从「一个要自己写并发控制与断点续跑的离线程序」变成「一个能设资源队列、能看进度、能重跑的标准作业」；
  - 分片之间的一致性不需要自己保证，因为**分片边界由引擎划定**；
  - 代价是它同时继承了引擎的调度语义——也就是说，作业重试会连带重跑模型调用。
- **由此付出的**：四项代价，没有一项是运维细节。
  1. **可重放性被静默破坏**：模型版本、采样参数、服务端实现都会在两次运行之间变化，于是同一个 DAG 跑两次得到不同的落表结果，而血缘仍然指向同一张上游表。**引擎不会报错**——这是本节最危险的一项：不是数据错了，是「数据不再可复现」这件事本身没有告警。
  2. **代价模型里没有「token」这一项**：优化器看到的仍是 I/O、CPU、网络三项，模型调用对它是透明的一行函数；于是它可能把 AI 算子当成便宜的 map 算子来排计划（放到广播侧、被重复求值，或在 AQE 改写后被多次物化）。**预算控制必须由你在引擎之外补一层。**
  3. **数据出域**：行内容要离开你的存储边界送到模型服务提供方，数据密级与合规边界需要重新划一遍，而这件事在引擎里没有任何表达方式。
  4. **新的失败模式**：限流与超时是外部故障，重试会成倍消耗配额；部分成功的作业会产出一张「一半有向量、一半没有」的表，而下游读到的是一张语法完全合法的表。
- **证据与来源**：Spark 4.0.0 于 2025 年正式发布，发行说明把 Spark Connect、半结构化类型与 SQL 侧的模型调用函数族列为主要变化【公开】（Apache Spark 4.0.0 Release Notes, 2025）。**注意命名纪律**：这类函数在不同平台上的名字并不一致，不要把它当成某个产品的专属能力（同一个能力在一家叫 `ai_query`，在另一家叫别的名字，是常见误记）。判定方法是查你所装版本官方文档的「内置函数」清单里有没有该函数族，以及它要求配置哪个模型服务端点。GraphRAG 这条方法的原始出处是微软研究院 2024 年的论文（From Local to Global: A Graph RAG Approach to Query-Focused Summarization, 2024），其公开材料把索引阶段的模型调用成本列为主要代价【公开】。
- **成熟度**：**L2**。① 满足（Spark 4.0.0 于 2025 年正式发布，有正式 release notes）；② 不满足（无可指名的第三方非厂商公开生产案例）；③ 不满足（函数族与模型服务端点在发行版之间不一致）。**可做 PoC，不要做核心依赖。**

「与 RAG / 向量库 / GraphRAG 的结合」常被写成三条并列的工具清单。它们其实是同一机制下的三种接口形态——都是「批作业产出 AI 需要的中间物，再写进一个引擎之外的索引」。区别不在 AI，而在**失败时谁负责**：

| 条目 | 接口形态（谁调用谁） | 谁负责失败 | 现在该怎么摆 |
| --- | --- | --- | --- |
| Spark + RAG（批量 Embedding → 向量库；LangChain Spark Integration 属这一形态） | 作业分区调用模型服务生成向量，再由连接器写入向量库 | 作业侧：向量库只收到已经成功的批次，失败的那部分需要作业重跑 | 把「生成向量」与「写索引」**拆成两步**，第二步可独立重放 |
| Spark + 向量库（写 Milvus / Pinecone / LanceDB 一类；LanceDB Connector 属这一形态） | 连接器把 DataFrame 分区映射成批量写入 | 向量库：冲突与覆盖语义（upsert 还是 append）由它决定，不由你决定 | 写入前先确认它的主键与覆盖语义，否则重跑会产生重复条目 |
| Spark + GraphRAG（抽实体关系 → 图库；Neo4j Spark Connector 属这一形态） | 作业产出（头实体, 关系, 尾实体）三元组，经图库连接器写入 | **无人负责**：图库不校验抽取质量，抽错了它照样写进去 | 抽取质量必须由你自己留样核对——图库不会告诉你它抽错了 |

为什么必须把「生成」与「写索引」拆成两步，可以看这个对比：

```text
不拆（一条绳索上的两次失败域）
  作业 A：读源表 → 调模型生成向量 → 直接写向量库
    失败点 1：模型限流         → 整个 A 失败，下次从头来（重跑 = 重新付费）
    失败点 2：向量库写冲突     → 整个 A 失败，向量已生成的部分白付一次钱
  → 两个失败域共用一次重试，任何一侧抖动都让另一侧的钱白花

拆（两次可独立重放）
  作业 A：读源表 → 调模型生成向量 → 落成「向量表」（带 model_version / prompt_version 列）
  作业 B：读向量表 → 写向量库（幂等 upsert）
    失败点 1 落在 A：重跑 A，成本 = 重新调模型（这是必须付的一次）
    失败点 2 落在 B：重跑 B，成本 = 只重写索引（模型调用不重复付费）
  → 同时得到另一件副产品：向量表里带着模型版本，半年后能回答「这批向量是谁生成的」
```

一个必须自己算的量级，用来说明「为什么这件事要当成本项目而不是技术项目」：

- 全量生成一次向量的成本 ≈ 行数 × 每行平均 token 数 × 单价；
- 以 10 亿行、每行 256 token 为例【推算】（推导链：10^9 行 × 256 token/行 = 2.56 × 10^11 token，除以 10^6 得 2.56 × 10^5 百万 token）；
- 总价 = 2.56 × 10^5 × 单价。单价请按你所用服务当前的公开定价页代入（把它取在 0.1–1 美元/百万 token 的区间内【经验】，总价落在 2.6 万–26 万美元这一量级）；
- **这个量级才是重点**：决定它的三个量（行数、每行 token 数、重跑次数）全部由你的数据与流程决定，只有单价是外部变量——而**重跑次数恰恰就是被上一条「可重放性」破坏的那个量**。

#### 5.2.2 自然语言 → SQL：被改变的不是引擎，是「谁写 SQL」

- **旧做法与它的卡点**：取数的路径是「业务提需求 → 数据同学理解口径 → 写 SQL → 跑 → 对账 → 交付」。卡点是**往返延迟与口径知识的不对称**：
  - 业务方无法自己验证一句话的需求是否被正确翻译；
  - 每一次翻译都要排期，于是探索性取数被排期成本压掉；
  - 要特别指出：卡点**不在引擎**——本章 §2 讲的 Catalyst、CBO、AQE 在处理这类查询上都不缺能力，缺的是「把自然语言需求变成正确 SQL 并确认它正确」这一步的人力。
- **AI 改变了什么机制**：把「自然语言 → 关系代数表达式」这一步由人换成统计模型。它改变的是**接口边界**：SQL 从「人的产出物」变成「机器的候选产出物」，人的角色后移到审核位。
- **由此得到的**：因为翻译成本从「一次排期」降到「一次生成 + 一次审核」，所以**探索性取数的次数可以脱离人力约束上升**——以前不敢问、问了也没人排期的问题，现在可以先问一遍。而且这个收益是可验证的：
  - 生成的 SQL 是确定性执行的，能被 EXPLAIN 拆开、能与旧口径对账；
  - 这与「模型直接给结论」有本质区别——后者的对错无从检验，前者的对错有现成的工具链。
- **由此付出的**：代价集中在错误形态上。
  1. **写错的 SQL 会报错，语义错的 SQL 不会**：语义错的查询会正常返回一个数字，而这个数字会被当成事实进入决策，甚至被写进下游表。这是本方向最贵的一项代价，也是它必须保留人工审核位的根本原因。
  2. **它把目录与语义层从「治理项目」变成了「前置依赖」**：模型要选表、判断字段含义、决定能不能读，全靠机器可读的元数据；没有这层，选表只能退化为「表名相似度」。书内「数据目录」一章（04-data-assetization/08-data-catalog）的落地实践把元数据称作 Text2SQL 与 Agent 取数的成像条件，说的正是这条依赖。
  3. **它绕过了一道旧防线**：以前「这张表能不能读」由人的经验把关，自然语言入口把这一步变成模型判断——所以密级必须是机器可读且强制的，否则这是一次合规事故，而不是一次体验退化。
  4. **口径知识的归属问题**：口径是沉淀在你的语义层里，还是沉淀在厂商的模型里，决定了三年后的迁移成本。
- **证据与来源**：主流湖仓与数仓在 2024 年推出了面向 SQL 的自然语言助手（Databricks Assistant、Snowflake Cortex 系列），各能力的可用状态随版本推进，以官方发布说明的当前状态为准【公开】（Databricks / Snowflake 官方发布说明, 2024）。**判定方法**：不看演示，查三件事——
  - 它是否给出所用表与字段的引用（可追溯）；
  - 它在不确定时是拒答还是猜（**拒答率**是可信度的直接指标）；
  - 生成结果能否回灌到你的语义层做对账。
- **成熟度**：**L2**。① 满足（厂商产品有正式发布说明）；② 不满足（可指名的落地案例都出自厂商自身）；③ 不满足（语义层格式、模型与提示词都在变）。**可做试点，不要做核心依赖。**

#### 5.2.3 内嵌 OLAP 与联邦查询：让计算去找数据

- **旧做法与它的卡点**：批处理的既有答案是「把数据搬进一个湖或仓再查」。它有两个卡点：
  - **搬运本身就是主要成本**——跨系统 ETL 的存储、调度与口径同步都被这笔搬运养着；
  - **搬不完**——数据散在关系库、对象存储、消息系统里，永远有源没进仓。
  本章 §1.1 讲「离线 vs 实时」时按处理范围划分，而这一节的分野不是时间维度，是**计算与数据的相对位置**。
- **AI 改变了什么机制**：**AI 没有改变这两个机制，这一点必须老实说。** 内嵌 OLAP（进程内分析引擎，DuckDB 与 DataFusion 都属这一族——前者是完整的进程内数据库，后者是可嵌进别的系统的执行与优化库）与联邦查询（跨源统一 SQL）都是 AI 之前就成立的架构方向——本章 §1.4 把内嵌 OLAP 与 AI 原生并列写在第四阶段，但两者是同时发生，不是因果。AI 对这个方向的真实影响是**换了一个调用方**：
  - Agent 与代码助手需要在自己的进程里对一个本地数据集跑 SQL——内嵌引擎在这里是**被嵌入方**，调用者是程序而不是人；
  - 取数入口需要一份能覆盖多源的名字空间——联邦引擎在这里是**取数入口**。
  所以准确的说法是：**这是接口层面的新用法，不是执行模型的变化。**
- **由此得到的**：因为内嵌引擎把「启动一个数据库」的成本降到「加载一个库」，所以**分析引擎开始出现在以前不会出现它的地方**——Notebook 单元、CI 作业、应用进程、Agent 的沙箱；这些位置以前要么自己写循环，要么连一个远端数仓（每次查询付一次网络与排队）。而因为联邦查询把多个源收进同一个名字空间，所以「一句话 → 一条 SQL 覆盖多源」在接口上成立，这正是 5.2.2 那条入口的前置条件。
- **由此付出的**：两类代价分别落在两侧。
  - **内嵌侧**：
    - 扩展轴只有纵向一条——换更大的机器，超过单机能力就必须换引擎（本章 §7.3.3 的「扩展轴」一节给出同一结论）；
    - **多机是长期争议点**，判定方法是看该版本的 release note 里有没有**独立的多机执行组件**，而不是看 benchmark 博客——把外部编排层套在一个单机引擎上分片跑，得到的是「多个单机任务」，不是一个分布式计划；
    - 原本由服务端承担的事（并发写限制、备份、权限、多用户共享）全部回到使用者身上。
  - **联邦侧**：
    - 引擎不再拥有数据，只拥有计划：谓词与聚合能不能下推取决于连接器；
    - 拿不到统计信息的源上，代价估算会退化成猜测（邻章「查询优化器」的 §7.3.4 讲的正是这类「接进来不等于能被优化」）；
    - 跨源查询没有统一快照，跨源 JOIN 会把中间结果拉到协调层物化，网络量成为主导项；
    - 故障责任分散——哪个源挂了、算谁的，需要在接口上先说清楚。
- **证据与来源**：内嵌引擎的设计目标出自其公开论文（DuckDB: an Embeddable Analytical Database, SIGMOD 2019）【公开】；其 1.0 版本于 2024 年正式发布【公开】（DuckDB 1.0 Release 说明, 2024）。联邦查询的「协调层规划 + 连接器」形态，以及它的流水线交换与故障恢复语义，已在本章 §7.3.1 与 §7.3.2 展开（Trino 官方文档与发布说明，版本持续修订，按你所装版本核验）。**判定方法**：跨引擎共存出问题，八成出在「引擎支持的表格规范版本」与「表格式元数据里有没有列级统计信息」这个矩阵上——Iceberg 这类表格式的规范按 v1 / v2 / v3 之类版本号迭代，与你的写入引擎是否一致，比 SQL 方言更常出事（本章 §7.3.4 给的核验方式同一套）。向量检索的接口同样按扩展清单核验：**连维护方一起看**——官方维护还是第三方维护，决定这个扩展跟着谁升级。
- **成熟度**：**L2**。① 满足（内嵌引擎 1.0 于 2024 年正式发布、联邦查询引擎已 GA 多年）；② 不满足（「被程序或 Agent 当作内嵌分析组件」这一新用法无可指名的第三方非厂商公开生产案例）；③ 不满足（多机扩展、向量与外部格式扩展的接口仍在变）。

两侧的接口边界可以这样对照：

```text
内嵌：把引擎搬到数据旁边（同机）
  [程序 / Notebook / Agent 沙箱] ──(进程内调用，不经网络栈)──► DuckDB 一类内嵌引擎
       数据形态：本地文件 / 对象存储上的 Parquet / 表格式
       边界上的失败：本机进程崩溃 —— 失败域 = 一台机器
       不需要的部件：协调层、worker 编排、网络交换

联邦：把计划架在多个源上面（数据不动）
  [取数入口 / BI / Agent] ──► 协调层（解析 + 规划）
                                 │  下推到各连接器
      ┌──────────────┬───────────┴──────────┬───────────────┐
   关系库          数据湖（表格式）      消息/对象存储      另一套数仓
       边界上的失败：某个源超时 / 下推失败 → 中间结果被拉到协调层物化
       必须接受的代价：跨源无统一快照；拿不到统计信息的源上估算退化
```

#### 5.2.4 调优与运维的自治：把「读日志的人」换成模型

- **旧做法与它的卡点**：作业调优卡在**信息与判断力不匹配**：
  - Spark UI 与日志里有全部所需信息，但会读的人少，读一次要几十分钟到几天【经验】；
  - 参数（并发度、分区数、资源配比）与数据分布之间没有闭式解，只能靠经验试错；
  - 既有产品里已有的自适应（AQE）能处理的只有内建的那几类调整（关联策略、分区合并），且只在物化点之后生效（本章 §2.2；「决策固定在哪一刻」这一分层视角见邻章「查询优化器」§7.3.3）。
- **AI 改变了什么机制**：把「读日志 → 给假设」这一步换成模型。**它改变的是诊断环节的人力成本，不是优化决策的信息量**——模型读到的日志、计划、指标与一个人读到的是同一批，它没有新的观测通道；而它能做的动作是改配置，不是改本次执行，所以它落在「回路层」而不是决策层。

```text
它落在哪一层（决定它的收益上界）
  编译期：CBO 选关联顺序与策略            ┐
  stage 边界：AQE 用实测统计改写计划        ├─ 这两层 AI 没有拿到决策权
  stage 内部：算子已启动，不可替换         ┘
  ────────────────────────────────────────────────
  回路层：改配置（并发度 / 分区策略 / 资源配比），下一次运行才生效
      └─ 模型今天能做的全部动作都在这条线上
  → 所以它的收益上界 = 一个耐心的专家手动做一遍能得到的东西
  → 也所以它天然安全：改错了只影响下一次运行，且可以退回
```

- **由此得到的**：因为诊断的人力成本下降，所以**「每个作业都被看过一次」从不现实变成现实**：
  - 以前资源只够分析最贵的几条作业；
  - 现在可以对全量作业做一遍初筛，把「值得人看的作业」从几百条压到几条【经验】；
  - 注意这条收益的上界——**恰好等于一个耐心的专家手动做一遍能得到的东西**，因为信息没有增加，只是读它的成本下降了。
- **由此付出的**：四项代价。
  1. **建议不可排序就会失去信任**：一串「建议」如果给不出「先做哪一条」的定量依据，其中混进一条错的就足以让团队整体弃用（邻章「查询优化器」§7.4 把「建议无法排序时的信任流失」列为本方向的隐性成本）。
  2. **验证与回滚的工程量才是主导成本**：每条建议都要有对照、指标口径与回滚开关，否则改坏了无法归因；这笔投入比模型推理本身贵【经验】。
  3. **相关不等于因果**：从历史中学到的是「设了这个参数的作业更快」，而不是这个参数为什么有效；照搬到流量形态不同的时段（例如大促）会失效。
  4. **爆炸半径**：调参是按队列生效的，一次改动影响整条队列；而「本次执行的计划」不接受外部建议覆盖——同一时刻只能由一层做决策（邻章「查询优化器」§7.3.3）。
- **证据与来源**：「有限自适应」的边界是可核验的既有事实——AQE 由 Spark 3.0（2020）引入、自 Spark 3.2.0（2021，SPARK-33679）起默认开启，本章 §7.3.1 已引其 release notes【公开】。作业级分析器（例如 Sparklens 这类通过监听器模拟不同资源规模下作业行为的公开工具）的存在说明「提交前预测性价比」这个需求在 AI 之前就有——判定方法是去开源托管平台检索该项目是否仍在维护，以及它最后一次适配的引擎版本。而「用模型做诊断」目前的产品形态是自然语言诊断入口，**不是引擎核心的决策权移交**——判定方法：查该引擎的 release note 里有没有「由模型决定计划选择」这类条目；只有「建议 / 解释」字样的属于诊断层，不是自治层。
- **成熟度**：**L3**。① 不满足（没有把「自治调优」作为正式 GA 特性的 release note）；② 不满足；③ 不满足（建议接口、指标口径、回滚机制都没有稳定形态）。**记录即可，不要在架构里为它预留假设。**

自治方向包含三个能力——自动监控、自动调优、自动恢复。前两个落在上面这个诊断层；**第三个要单独交代一句，否则会显得本节把它漏掉了**：恢复这件事的既有部分本就属于引擎的故障恢复机制——「重算丢失的分区还是重跑整条查询」由中间结果是否落盘决定（本章 §7.3.2 给出这条分界的机制推导），与模型无关，所以本节不再把它作为前沿单列；本节 5.2.1 里「作业重试会连带重跑模型调用」正是这条既有机制的副作用，而不是一项新能力。仍停在观望的是它的 AI 版本：让模型判断一次失败该重跑、该跳过还是整批回滚。判定方法与上一条同源——release note 里出现「由模型决定恢复动作」才算进了这一层；只写「失败重试策略可配置」的，仍属既有机制的可配置化。

### 5.3 与本主题既有栈的接口在哪

不写「与 X 结合」这种空话。下面每一行给出的都是**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。这张表的用途是划清责任——本节所有「AI 能力」的失败都不会由引擎承担，因为它们的接入点都在引擎的调度边界之外。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 模型调用 ↔ 调度与资源队列 | 作业把模型调用当作算子提交；队列只认 CPU 与内存，看不到 token 配额 | 作业侧：配额耗尽时作业失败，队列完全不感知 | 需要你在引擎之外补一层「token 预算」，引擎不带这个计量维度 |
| 模型产出的中间物 ↔ 目录与血缘 | 作业写出向量列与三元组表；血缘系统看到的是「表读写」，看不到「这条向量由哪个模型版本生成」 | 当前无人负责——这是本节里最真实的空白 | 只能靠约定：把模型版本、提示词版本写进表属性与列注释，机制上不强制 |
| 自然语言入口 ↔ 语义层与密级 | 入口先取 schema 与指标定义，再生成 SQL；密级必须和 schema 同源返回 | 入口侧：不确定时必须拒答，拒答率是它唯一可信的指标 | 入口的可信度上限由你的语义层决定，与模型强弱关系不大 |
| 内嵌引擎 ↔ 对象存储与表格式 | 直读 Parquet 或表格式文件，不经元数据服务；名字空间由文件路径或 attach 定义 | 使用者：权限、快照一致性、备份全部回落到文件系统与表格式 | 多引擎共存靠表格式，不靠引擎；服务端职责需要你自己补回 |
| 联邦查询 ↔ 取数入口 | 入口把一条 SQL 交给协调层，由连接器下推到各源 | 协调层：下推失败时由它承担网络与物化成本，源头不感知 | 能用，但要接受「拿不到统计信息的源上估算退化」这个前提 |
| 诊断建议 ↔ 配置变更流程 | 建议以文本产出，由人翻译成配置改动，走变更流程生效于下一次运行 | 人：建议本身不承担任何责任，采纳即由人承担 | 单向只读，不写回引擎——这正是它安全的原因，也是收益上界的原因 |

### 5.5 被过度宣传的部分

**「引擎原生支持大模型，离线计算进入 AI 原生时代」**

- 实际是什么：把一次外部推理调用包装成一个 SQL 函数。它没有改执行模型（仍是分区并行的 map 形态）、没有改代价模型里的成本项、也没有解决结果不可重放的问题。
- 为什么会这样：函数是接口层最薄的一层抽象，做它不需要动调度、shuffle 或代价模型，所以它先被做出来——**先做出来的往往是最容易做的那一层，而不是最有价值的那一层。**
- 什么时候它才会成真：当优化器能把 token 预算算进代价函数、且引擎能对推理结果做确定性缓存（同输入同模型版本 → 复用结果）时，那才是执行模型的变化。
- 信号：release note 里出现「模型调用参与计划选择」或「推理结果可缓存」这类条目，而不是函数清单又变长了。

**「内嵌引擎是分布式批处理的替代品 / 已经支持多机并行」**

- 实际是什么：单进程内嵌引擎，扩展轴只有纵向；它的便宜来自「没有跨节点边界」这件事本身，加上分布式就等于把便宜的那部分丢掉。
- 为什么会这样：多机并行不是加一个参数，而是要有独立的多机执行组件（负责分片、交换与故障恢复），这与它的设计目标冲突。
- 判定方法：看该版本的 release note 里有没有独立的多机执行组件，而不是看 benchmark 博客；本章 §7.3.3 从「扩展轴」给出了同一结论。
- 什么时候它才会成真：当它自己发布这套组件，并且有人用它在多机规模上替换掉一个分布式作业——那时它改变的才是定位，而不只是措辞。

**「AI 让调优自动化，调优的人可以省了」**

- 实际是什么：压缩了诊断环节的人力，没有改变决策与验证环节。
- 为什么会这样：模型没有新的观测通道，也没有执行通道；它读到的是同一批日志与指标，改的是下一次运行的配置。
- 什么时候它才会成真：建议能被排序（每条带预期收益与置信区间），且验证与回滚被自动化到「改坏可在分钟级退回」。
- 信号：产品文档里出现「建议的预期收益区间」，而不是「一键优化」——前者意味着它知道自己的建议值多少钱，后者通常意味着它不知道。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 「批作业里调用模型」会成为常规形态，但**不会**进入代价模型 | 引擎发布推理结果缓存与 token 预算类配置项，并被写进资源队列文档 | release note 只见函数清单扩张，三年后队列仍只按 CPU / 内存 / 核时计量 |
| 自然语言取数会在「有人审核」的形态下站稳，在「无人审核直连生产」上长期停在试点 | 产品文档把「引用来源、拒答、审计日志」列为核心能力，而不是把准确率当卖点 | 出现多家非厂商的、无人审核、直连核心指标的公开生产案例 |
| 内嵌引擎会成为 Agent 的默认本地分析组件，但**不会**取代分布式批处理 | Agent 框架的官方文档把某个内嵌引擎列为默认数据分析工具 | 内嵌引擎发布独立的多机执行组件，且出现用它替换掉分布式作业的公开案例 |
| 离线计算的成本口径从「核时」扩展为「核时 + token」 | 调度或资源队列产品把模型调用预算作为一等资源计量 | 三年后资源队列的计量维度没有变化 |

四条预测共用一个判据：**看计量与预算，而不是看函数清单。** 一个能力如果真进了执行模型，它一定会以「可被计量、可被预算、可被退回」的形态出现在产品里；只出现在函数列表与博客标题里的，通常停在接口层。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有大量非结构化数据要加工成向量 / 实体 | 把它做成可重放的作业：模型版本、提示词版本、入参摘要写进输出表属性；把「生成」与「写索引」拆成两步 | 引擎侧的推理结果缓存与 token 预算机制 | 不要把模型调用埋进一个不可重放的 UDF，再让下游表直接依赖它的输出 |
| 想让业务方自助取数 | 先补机器可读的元数据（表语义、口径、密级、Owner），入口只做候选生成 + 人审核 | 语义层定义的跨工具可移植性 | 不要在密级标注完成前开放入口；不要让入口直连生产核心指标 |
| 数据散在多源，想少搬一次 | 用联邦查询做取数入口，但把跨源 JOIN 的中间结果落点与超时设计清楚 | 各数据源能否稳定提供统计信息 | 不要在拿不到统计信息的源上做多表跨源 JOIN——估算退化会让计划变得不可解释 |
| 做本地或单机分析（Notebook、CI、Agent 沙箱） | 内嵌引擎可以直接用，它的失败面就是这台机器 | 多机扩展是否出现独立执行组件 | 不要把它当分布式方案的规模替代；不要指望它在多用户共享、权限与备份上替代服务端 |
| 作业调优成本高、专家不够 | 先把可观测性补齐：最终计划、shuffle 字节量、最慢 task 与中位 task 的耗时比 | 诊断类建议是否开始带定量收益 | 不要让自动化建议直接改生产队列参数——在验证与回滚链路建成之前，它只是一份候选清单 |
| 已经在用 AI 生成大批量中间物 | 把「全量重算一次要多少钱」先算出来（行数 × 每行 token 数 × 单价，再乘上你实际的月重跑次数） | 单价与配额策略的变化 | 不要在算清这笔钱之前把全量重算做成日常流程 |

最后一行值得单独说一句：它看起来最不像架构决策，却是本节里唯一一条**会在第一个月就产生账单影响**的建议。前五行都在说「怎么摆才不返工」，这一行说的是「怎么摆才不至于在第一次重跑时被账单叫停」。

### 5.8 小结

> 本节小结：AI 在离线计算里真正改变的**唯一那条机制**，是把外部模型调用纳入了「确定性批作业」的边界内——它给成本函数加了一项按 token 计费、且结果不可重放的算子，改变了接口边界（SQL 由机器起草）与人机分工（诊断外包），但**没有改变**执行模型：分区并行、shuffle 落盘、stage 边界与代价模型里的三项成本都还在原地。
>
> 因此判断这类能力是否值得排期，只看一件事——它有没有变成「可计量、可预算、可退回」的东西；只看函数清单与演示，会把接口改良读成架构变化。
>
