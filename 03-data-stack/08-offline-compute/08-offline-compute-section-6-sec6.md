## 6. 落地实践

### 6.1 字节"**Spark + Iceberg 承载 10 万+ 任务/日 5+ 年**"（2019-2024）

**背景（Why）**

字节 2019 年面临**离线计算在 EB 级数据下的三重失效**：
- **Hive on MR 跑不动**——**一个全表聚合动辄小时级，业务方等不到结果就先拍脑袋决策**
- **小文件爆炸**——**流式写入产生的百万级小文件让每次任务都先花大量时间在"列目录"上**
- **流批双写冗余**——**同一份数据实时一份、离线一份，存储成本翻倍且口径对不上**
- **数万级任务/日已逼近调度承载**——**调度与资源争抢成为稳定性主要来源**（改后为 10 万+/日，见 §6.1 关键数字表）

**触发点（What）**

2019 年字节推进 **Spark + Iceberg 统一离线计算底座**（[字节技术博客 2019-2024]），目标：
- **EB 级可算**——大表聚合从小时级进入十分钟级
- **数据 0 冗余**——流批共享同一份文件
- **10 万+ 任务/日稳定调度**

**详细做法（How）**

字节离线计算架构的**5 大核心组件**：

1. **Spark + Iceberg 的元数据驱动读取（核心创新）**
   - 关键设计：**用 Iceberg 的 manifest 元数据替代 Hive 的目录列举**；Spark 直接读元数据拿到"哪些文件、每列统计是什么"，据此跳过无关文件
   - 关键能力：**扫描量由"文件数"决定而不是"目录规模"决定**——这是 EB 级能跑出十分钟级的根本原因
   - 关键数字：**查询 P99 小时级 → < 10min、扫描量常压到全表 1%**
   - 关键示意：
     ```text
     Spark 离线读取 Iceberg（元数据驱动，不是目录列举）
       Spark SQL ──▶ Iceberg catalog（按名取当前 snapshot-id）
                        │
                        ▼
              snapshot-N / manifest-list（avro）
                 ├─ manifest ─▶ data file-1.parquet（Zstd，含列级 min/max/null_count）
                 └─ manifest ─▶ data file-2.parquet（Zstd，同左）
                        │
        优化器用 manifest 里的列统计做三件事：
          ① 分区裁剪：dt 不在范围内 → 整个 manifest 跳过
          ② 文件裁剪：amount 的 min/max 不满足谓词 → 跳过该文件
          ③ 列裁剪：只读 SELECT 涉及的列（列存 + Zstd，压缩比 5~10x）
     Flink（实时）──后台小文件合并──▶ 写回同一张 Iceberg 表
     -- 关键：EB 级数据只存一份；流与批读的是同一批 parquet 文件，口径不可能不一致
     ```

2. **流批共享同一份存储（核心）**
   - 关键设计：**Flink 实时写入与 Spark 离线重写落在同一张 Iceberg 表**，后台 compaction 负责把流式产生的小文件合并成大文件
   - 关键能力：**存储成本与口径一致性同时改善**——去掉 Lambda 的第二份存储
   - 关键数字：**数据冗余 0、存储成本 -40%**

3. **小文件自动合并（compaction）（核心）**
   - 关键设计：**按分区统计文件大小与数量，超过阈值触发重写**，目标单文件 128MB~512MB；合并过程本身以快照提交，不破坏读一致性
   - 关键能力：**流式写入不再以牺牲读性能为代价**，这是"流批一表"能长期成立的运维前提
   - 关键数字：**小文件百万级 → 万级、读取时"列目录"开销基本消失**

4. **分布式调度与资源隔离（核心）**
   - 关键设计：**按业务优先级分队列**，SLA 任务与临时分析任务物理隔离；大查询限流排队
   - 关键能力：**10 万+ 任务/日下，核心链路不被临时大查询挤占**
   - 关键数字：**10 万+ 任务/日、核心任务 SLA 达标**

5. **4 业务统一底座（核心创新）**
   - 关键设计：**4 业务共用 Spark 引擎版本、Iceberg 表规范与调度平台**，差异只在数据域与业务逻辑
   - 关键能力：**引擎优化一次、全部业务受益**，避免"每个业务一套 Spark 参数调优经验"
   - 关键数字：**4 业务统一、引擎版本唯一**

**字节 Spark + Iceberg 关键数字**（[字节技术博客 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **引擎** | Hive on MR | Spark on Iceberg | **查询 P99 小时级 → < 10min** |
| **单表扫描量** | 全表扫 | 分区 + 文件 + 列三级裁剪 | **常压到全表 1%** |
| **小文件数量** | 百万级（无治理） | 万级（自动 compaction） | **-99%** |
| **数据冗余** | 流批双写两份 | 流批共享一份 | **-50%** |
| **存储成本** | 基线 | -40% | **-40%** |
| **任务量** | 数万/日 | 10 万+ 任务/日 | **+100%+** |
| **业务覆盖** | 各业务各自搭 | 4 业务统一底座 | **∞** |
| **数据规模** | PB | EB | **1000x** |

**具体数字（How much）**

- 团队规模：字节离线计算 / 数据平台 200+ 人
- 关键数字：**查询 P99 < 10min**；**小文件 -99%**；**存储 -40%**；**10 万+ 任务/日**
- 业务影响：覆盖抖音 / TikTok / 西瓜 / 今日头条的全部离线加工与分析

**失败教训**

- 早期「**Hive 目录列举当元数据**」——百万小文件下任务大部分时间花在列目录，倒逼**「Iceberg manifest 元数据 + 三级裁剪」**
- 「**流批各写一份**」——存储翻倍且口径对不上，倒逼**「同一张 Iceberg 表流批共享 + 后台 compaction」**
- 「**临时大查询与 SLA 任务共用队列**」——核心报表因资源被抢而延迟，倒逼**「按优先级分队列 + 物理隔离 + 大查询限流」**
- 「**各业务各调一套 Spark 参数**」——调优经验无法复用，倒逼**「统一引擎版本 + 统一表规范」**

### 6.2 阿里"**MaxCompute 自研引擎在 EB 级单表上的代价优化 10+ 年**"（2014-2024）

**背景（Why）**

阿里 2014 年面临**"EB 级单表 SQL"这个开源方案当时打不下来的场景**：
- **25 BU 数据集中到集团**——**单表 EB 级，开源引擎在规划阶段就撑不住**
- **存储与计算耦合**——**扩容要搬数据，且按峰值预付费，成本随峰值而非用量**
- **SQL 是唯一通用语言**——**几万名分析师与运营，不可能要求他们写 Spark 代码**
- **对外商业化诉求**——**内部能力需要能作为云产品服务 100 万+ 企业**

**触发点（What）**

2014 年阿里推进 **MaxCompute 自研离线引擎 + 100 万+ 企业对外输出**（[阿里 MaxCompute 公开材料 2014-2024]），目标：
- **EB 级单表可 SQL**——靠分区裁剪把扫描量压到可接受范围
- **存算分离**——扩容不搬数据、按用量付费
- **100 万+ 企业可用**

**详细做法（How）**

阿里 MaxCompute 离线引擎的**5 大核心组件**：

1. **存算分离 + 分区/列/谓词三级裁剪（核心创新）**
   - 关键设计：**SQL 先经 CBO 优化器**，用表的统计信息把"先裁分区、再裁列、最后下推谓词"三层过滤做尽；存储层与计算层完全解耦，各自独立扩容
   - 关键能力：**EB 级单表的实际扫描量常被压到原表的极小比例**，让"大表也能交互式跑 SQL"成立
   - 关键数字：**EB 级单表、扫描量常压到全表 1% 量级、SQL 10 万+/天**
   - 关键示意：
     ```text
     ┌── MaxCompute 存算分离 ──────────────────────────┐
     │  SQL ─▶ 优化器(CBO，基于表/列统计)               │
     │            │                                     │
     │            ▼                                     │
     │      分布式执行 DAG（Fuxi 调度）                  │
     │         · 分区裁剪  dt IN (...)  → 跳过无关分区   │
     │         · 列裁剪    只读 SELECT 涉及的列          │
     │         · 谓词下推  WHERE 尽量靠近数据源          │
     │            │                                     │
     │  元数据层：表 / 分区 / 列统计（优化器的输入）      │
     │  计算层  ：Fuxi，10 万+ 并行实例，作业级隔离       │
     │  存储层  ：Pangu，三副本 / 纠删码，按量计费        │
     └──────────────────────────────────────────────────┘
     -- 关键：EB 级单表能跑，靠的不是"算得快"，而是"读得少"
     --        三级裁剪确保实际 IO 只落在真正需要的数据上
     ```

2. **CBO 与统计信息质量（核心）**
   - 关键设计：**优化器的输入是统计信息（行数、列直方图、NDV）**，因此统计信息的采集与新鲜度被当作一等公民运维
   - 关键能力：**"统计信息过期导致选错 JOIN 策略"这类性能事故被系统性消除**
   - 关键数字：**统计信息覆盖核心表 100%**

3. **多租户隔离与配额（核心）**
   - 关键设计：**每个 BU 有资源配额**，跨配额借用需申请；作业级隔离避免互相拖垮
   - 关键能力：**一次误操作的大查询不会波及全集团**——这是集团级平台能同时服务 25 BU 的前提
   - 关键数字：**配额隔离 100%、作业级故障不扩散**

4. **SQL 作为统一入口（核心）**
   - 关键设计：**绝大多数加工与分析的入口就是 SQL**，复杂逻辑用 UDF / 图 / 迭代计算扩展
   - 关键能力：**数十万使用者的学习成本被压到最低**，平台不必为每种角色提供不同工具链
   - 关键数字：**SQL 10 万+ 作业/天、使用门槛低**

5. **对外商业化与能力复用（核心创新）**
   - 关键设计：**内部引擎能力直接封装为公有云产品**，同一套引擎服务内部与外部客户
   - 关键能力：**内部 EB 级场景验证过的能力，天然适合中小企业**；规模化摊薄研发成本
   - 关键数字：**100 万+ 企业客户**

**阿里 MaxCompute 离线引擎关键数字**（[阿里 MaxCompute 公开材料 2014-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **架构** | 存算耦合 | 存算分离，独立扩缩 | **扩容不搬数据** |
| **EB 级单表 SQL** | 规划阶段即不可行 | 三级裁剪，常压到全表 1% | **∞** |
| **作业规模** | 数万/日 | 10 万+ SQL 作业/天 | **+100%+** |
| **扩容代价** | 搬数据 + 按峰值预付费 | 按实际用量付费 | **成本贴合用量** |
| **多租户隔离** | 混部，互相影响 | 配额 + 作业级隔离 | **故障不扩散** |
| **统计信息覆盖** | 部分 | 核心表 100% | **优化器决策可靠** |
| **数据规模** | PB | EB | **1000x** |
| **企业客户（云上）** | 0 | 100 万+ | **∞** |

**具体数字（How much）**

- 团队规模：阿里 MaxCompute 团队千级人员规模
- 关键数字：**EB 级单表可 SQL**；**扫描量常压到全表 1%**；**10 万+ 作业/天**；**100 万+ 企业**
- 业务影响：覆盖阿里全集团 25 BU，并作为公有云产品服务 100 万+ 企业

**失败教训**

- 早期「**存算耦合**」——扩容必须搬数据且按峰值预付费，倒逼**「存算分离 + 按量付费」**
- 「**统计信息过期不管**」——优化器选错 JOIN 策略，单个作业从 10 分钟变 2 小时，倒逼**「统计信息采集与新鲜度纳入运维指标」**
- 「**所有作业共用一个资源池**」——一个 BU 的误操作大查询拖垮全集团，倒逼**「按 BU 配额 + 作业级隔离」**
- 「**只服务内部场景**」——能力与研发成本无法摊薄，倒逼**「同一套引擎对外输出为云产品」**

### 6.3 腾讯"**跨 Region 离线数仓：把明细留在本地、只传聚合 10+ 年**"（2014-2024）

**背景（Why）**

腾讯 2014 年面临**跨地域离线加工的网络成本与延迟**：
- **4 Region + 8+ 业务**——**微信生态的数据天然分散在各区域**
- **跨区搬明细代价极高**——**明细数据体积巨大，跨区带宽成本与传输时延都不可接受**
- **T+1 时效要求**——**小时级的 T+1 已不能满足业务**
- **小文件百万级**——**Hive 表在流式写入下小文件爆炸，合并前查询极慢**

**触发点（What）**

2014 年腾讯推进 **TDW 跨 Region 离线数仓**（[腾讯技术博客 2014-2024]），引擎后继由 Hive 演进为 Spark + Iceberg，目标：
- **跨区只传聚合**——明细不出本地
- **T+1 小时级 → 分钟级**
- **8+ 业务 / 13 亿+ 用户统一**

**详细做法（How）**

腾讯 TDW 跨 Region 离线架构的**5 大核心组件**：

1. **"明细本地、聚合跨区"的数据布局（核心创新）**
   - 关键设计：**每个 Region 完整保存本区域的明细数据并就地完成明细层加工；跨区只传输 DWS/ADS 层的聚合结果**，集团报表由各区域聚合结果合并而成
   - 关键能力：**跨区带宽由"明细体量"降到"聚合体量"**，这直接决定跨地域数仓是否经济可行
   - 关键数字：**跨区带宽 -90%、T+1 时效 -90%**
   - 关键示意：
     ```text
     跨 Region 离线数仓数据流（明细不出本地）
       Region A              Region B              Region C
       ┌──────────┐          ┌──────────┐          ┌──────────┐
       │ ODS 明细 │          │ ODS 明细 │          │ ODS 明细 │   ← 明细仅本地存储
       │ DWD 明细 │          │ DWD 明细 │          │ DWD 明细 │
       │ DWS 区域 │          │ DWS 区域 │          │ DWS 区域 │   ← 就地聚合
       └────┬─────┘          └────┬─────┘          └────┬─────┘
            │   只传聚合结果（DWS/ADS）                 │
            └──────────────┬───────────────────────────┘
                           ▼
                   集团 DWS / ADS（集中合并）
     ────────────────────────────────────────────────
     判断准则：跨区传输的应该是「已经缩小的结果」，而不是「原始明细」
       明细跨区 = 带宽成本随数据量线性上涨，且随时延放大
       聚合跨区 = 传输量常比明细小 2~3 个数量级
     ```

2. **Spark + Iceberg 作为统一引擎（核心）**
   - 关键设计：**各 Region 用同一套 Spark + Iceberg 栈**，表格式统一便于跨区元数据协作
   - 关键能力：**区域间任务可复用同一份作业定义**，运维与调优经验共享
   - 关键数字：**8+ 业务统一引擎**

3. **小文件合并与文件大小治理（核心）**
   - 关键设计：**合并目标单文件 128MB~512MB**；对高频写入分区做更激进的合并策略
   - 关键能力：**流式写入密度越高，合并策略越激进**，避免"写入越快、读得越慢"
   - 关键数字：**小文件百万级 → 万级（-99%）**

4. **跨 Region 元数据与调度协作（核心）**
   - 关键设计：**集团层调度器按 Region 下发区域任务 + 集中的合并任务**；区域任务失败只重跑该区域
   - 关键能力：**故障半径限定在单个 Region**，不会因一个区域的问题阻塞全集团出数
   - 关键性质：**故障半径收敛到单 Region**

5. **13 亿+ 用户规模的容量保障（核心创新）**
   - 关键设计：**按业务与时段错峰调度**；大促 / 春节等峰值前预留容量并做压测
   - 关键能力：**在超大规模下把"出数时间"当作可承诺的 SLA 来运营**
   - 关键数字：**覆盖微信 13 亿+ 用户、核心报表 SLA 达标**

**腾讯 TDW 跨 Region 离线关键数字**（[腾讯技术博客 2014-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **跨区传输内容** | 明细全量搬运 | 只传 DWS/ADS 聚合 | **带宽 -90%** |
| **T+1 时效** | 小时级 | 分钟级 | **-90%** |
| **小文件数量** | 百万级 | 万级 | **-99%** |
| **引擎** | Hive | Spark + Iceberg | **查询显著提速** |
| **业务覆盖** | 各业务各建 | 8+ 业务统一 | **∞** |
| **故障半径** | 全集团出数阻塞 | 单 Region | **收敛** |
| **数据规模** | PB | EB | **1000x** |
| **用户规模** | 亿级 | 13 亿+ | **10x+** |

**具体数字（How much）**

- 团队规模：腾讯 TDW 团队 200+ 人
- 关键数字：**跨区带宽 -90%**；**T+1 -90%**；**小文件 -99%**；**13 亿+ 用户**
- 业务影响：支撑微信生态 8+ 业务的跨区域离线加工与集团报表

**失败教训**

- 早期「**把明细跨区搬到一个中心仓库**」——带宽成本与传输时延都不可接受，倒逼**「明细留在本地、只传聚合」**
- 「**小文件不治理**」——流式写入越频繁查询越慢，倒逼**「按分区密度动态调整合并策略，目标单文件 128~512MB」**
- 「**集团调度一把抓**」——某区域任务失败导致全集团出数延迟，倒逼**「区域任务独立 + 元数据与调度分层协作」**
- 「**不区分峰值与平时容量**」——春节 / 大促前集中出数导致排队数小时，倒逼**「错峰调度 + 峰值前预留与压测」**

### 6.4 Netflix"**Iceberg 列存 + Zstd：让 EB 级扫描落在可承受的 IO 上 5+ 年**"（2019-2024）

**背景（Why）**

Netflix 2019 年面临**EB 级数据下 IO 成本成为主要瓶颈**：
- **2 亿+ 用户的全量播放行为**——**EB 级数据，行存全扫的 IO 成本不可承受**
- **全球 4 Region**——**数据分析需求分散，不能只在一个区域集中处理**
- **ML 特征回填频繁**——**需要反复扫描大范围历史数据，IO 放大问题被反复触发**
- **Schema 演进与时间旅行需求**——**传统 Hive 表既难演进也难回溯**

**触发点（What）**

2019 年 Netflix 在 S3 上推进 **Spark + Iceberg 列存 + Zstd**（[Netflix Tech Blog 2019-2024]），目标：
- **IO 降一个数量级**——列存让"只读需要的列"成立
- **4 Region 就近分析**
- **EB 级低 IO 成本**

**详细做法（How）**

Netflix 离线架构的**5 大核心组件**：

1. **列存 + 高压缩比：把 IO 从"扫全行"变成"只读列"（核心创新）**
   - 关键设计：**Parquet 列存 + Zstd 压缩**，单数据文件控制在 128MB~512MB；查询时只读取 SELECT 涉及的列，其余列完全不产生 IO
   - 关键能力：**"宽表只查 3 列"这类最常见分析的 IO 降为行存全扫的约 1/10**，这是 EB 级能负担得起的前提
   - 关键数字：**IO 降为约 1/10、压缩比 5~10x**
   - 关键示意：
     ```text
     S3 对象存储 ──▶ Iceberg 表（分区 = dt + region）
        ├─ data file：Parquet + Zstd（列存）
        │     单文件 128MB ~ 512MB（避免小文件）
        │     列级统计（min/max/null_count）随 manifest 保存
        └─ snapshot 链：支持 Time Travel / 秒级回滚
     ────────────────────────────────────────────────
     一次「只查 3 列」的查询在两种格式下的 IO 对比
       行存：读完整行 → 不关心的 40 列也全读      100% IO
       列存：只读那 3 列（且相邻行同列连续）        ~10% IO
       + Zstd：压缩比 5~10x，落到磁盘的是压缩后字节
     -- 关键：EB 级上"能不能查"取决于"读多少"，不取决于"算多快"
     --        列存 + 压缩把 IO 基数降下来，压缩再降一次
     ```

2. **文件大小治理（核心）**
   - 关键设计：**目标单文件 128MB~512MB**；过小触发合并，过大影响并行度上限
   - 关键能力：**避免"流式小文件"与"超大文件并行度不足"两种极端**
   - 关键数字：**单文件 128~512MB**

3. **4 Region 就近分析（核心）**
   - 关键设计：**每个 Region 有自己的存储与分析集群**，跨区只做必要的元数据协作与结果汇总
   - 关键能力：**分析延迟不受跨洋网络影响**，同时满足数据驻留的区域要求
   - 关键数字：**4 Region 就近处理**

4. **快照支撑的回填与重现（核心）**
   - 关键设计：**ML 特征回填读取指定快照**，保证"同一份特征用同一份数据重算能得到同样结果"
   - 关键能力：**特征回填不再是"边跑边变"的不确定过程**
   - 关键数字：**回填可重现 100%**

5. **Spark 作为统一离线引擎（核心创新）**
   - 关键设计：**离线 ETL、特征工程、ML 预处理都跑在 Spark 上**，共享 Iceberg 存储契约
   - 关键能力：**数据工程与 ML 工程共享同一份数据视图**，避免"两份特征两份口径"
   - 关键性质：**全站离线作业统一引擎**

**Netflix 离线架构关键数字**（[Netflix Tech Blog 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **存储格式** | 行存（Hive 时代） | Parquet 列存 + Zstd | **压缩比 5~10x** |
| **典型查询 IO** | 全行扫描 100% | 只读相关列 ~10% | **-90%** |
| **单文件大小** | 大小不一（常见小文件） | 128MB~512MB 受控 | **并行度与 IO 均衡** |
| **Region 布局** | 集中分析 | 4 Region 就近 | **跨区 IO 消除** |
| **Schema 演进** | 全表重写 | 仅改元数据 | **与数据量解耦** |
| **时间旅行 / 回滚** | 不支持 | 按快照回溯，秒级 | **∞** |
| **ML 特征回填** | 结果不可重现 | 指定快照，可重现 | **100%** |
| **数据规模** | PB | EB | **1000x** |

**具体数字（How much）**

- 团队规模：Netflix 数据平台工程（数据平台部 DIE 口径约 200+ 人；数据团队合计约 1000+ 人 —— 两个数字的主语不同，见 [Netflix 案例 §1.3](../../15-case-studies/05-netflix-data-stack/05-netflix-data-stack.md)【经验】）
- 关键数字：**IO -90%**；**压缩比 5~10x**；**4 Region**；**EB 级**
- 业务影响：支撑 Netflix 全球 2 亿+ 用户的数据分析、推荐特征工程与 A/B 实验评估

**失败教训**

- 早期「**行存全表扫**」——宽表只查几列也要读全行，EB 级下 IO 成本不可承受，倒逼**「列存 + Zstd，IO 降约一个数量级」**
- 「**文件大小放任不管**」——小文件拉高调度开销，超大文件限死并行度，倒逼**「单文件目标 128~512MB + 自动合并」**
- 「**把分析集中在单一区域**」——跨洋读取延迟与区域数据驻留要求冲突，倒逼**「4 Region 就近分析」**
- 「**ML 特征回填不固定数据版本**」——同一份特征重算结果不同，实验无法复现，倒逼**「回填读取指定快照」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**Spark + Iceberg + 列存 + 压缩**」（**最简单**）——**PB 级以下、1 个业务**
- 产出：**Iceberg 表规范 + 单文件大小目标（128~512MB）+ 分区裁剪验证报告**
- 团队：**2-3 人**
- 验证标准：**典型宽表只查 3 列的 IO 降 ≥ 80%**、**分区裁剪生效（执行计划可见）**、**Schema 演进不停机**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 业务 / 多引擎**」
- 引入「**自动小文件合并（compaction）**」——流式写入不以牺牲读性能为代价
- 引入「**统计信息采集与新鲜度纳入运维指标**」——保证优化器决策可靠
- 团队：5-10 人
- 验证标准：**小文件数 -90%**、**统计信息覆盖核心表 100%**、**查询 P99 较基线 -50%**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务 / EB 级 / 多地域**」
- 引入「**明细本地、聚合跨区**」的数据布局——跨区只传缩小的结果
- 引入「**按优先级分队列 + 配额隔离**」——大查询不挤占 SLA 任务
- 团队：10-30 人
- 验证标准：**跨区带宽 -80% 以上**、**核心任务 SLA 达标率 ≥ 99%**、**故障半径收敛到单域**

**100 → 1000 阶段：12-24 个月**

- 引入「**快照绑定（回填 / 训练产物 → 数据快照 id + 代码版本）**」——结果可重现
- 引入「**错峰调度 + 峰值前容量预留与压测**」+「**多 Region 就近处理**」
- 团队：30-100 人
- 验证标准：**回填 / 训练可重现 100%**、**峰值期出数 SLA 不劣化**、**任意时点回滚秒级**

### 6.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**典型查询 IO**」 | 行存全扫 100% | 只读相关列约 10% | **-90%** |
| 「**压缩比**」 | 1x（行存） | 5~10x（列存 + Zstd） | **5~10x** |
| 「**查询 P99**」 | 小时级 | < 10min | **-95%** |
| 「**小文件数量**」 | 百万级 | 万级 | **-99%** |
| 「**数据冗余 / 存储成本**」 | 流批双写两份 | 流批共享一份，-40% | **-40~50%** |
| 「**跨区带宽**」 | 明细全量搬运 | 只传聚合 | **-90%** |
| 「**T+1 时效**」 | 小时级 | 分钟级 | **-90%** |
| 「**EB 级单表 SQL 可行性**」 | 规划阶段即不可行 | 三级裁剪，常压到全表 1% | **∞** |
| 「**任务规模 / 业务覆盖**」 | 数万/日、各业务各建 | 10 万+/日、4~8 业务统一 | **+100%+ / ∞** |
| 「**结果可重现（回填 / 训练）**」 | 不可重现 | 快照 id 绑定 100% | **∞** |

**关键投资回报**：
- **直接节省**：「**IO -90% + 压缩 5~10x + 存储 -40~50% + 跨区带宽 -90%**」——**离线计算的成本几乎全部由 IO 与存储决定**；列存把"读多少"降到约十分之一，压缩再把落地字节降 5~10 倍，两者相乘就是 EB 级场景下能否负担得起的分界线
- **业务价值**：「**查询 P99 小时级 → 十分钟级 + T+1 分钟级**」——**离线计算的收益不只是省钱，而是把"等数据"从业务流程里删掉**：小时级的 T+1 意味着决策必须按天做，十分钟级则让当天迭代成为可能
- **AI 时代关键**：「**列存 + 快照绑定 + 分区/列裁剪**」——**这是 AI 特征工程与训练的成本地基**：特征回填本质是反复扫描大范围历史数据，没有列存与裁剪，成本会高到无法迭代；而快照绑定则保证"同一个模型可以精确复现同一份训练数据"，这是模型审计与实验可复现的前提

---

> **本节小结**：
> - 4 个真实案例（字节 / 阿里 / 腾讯 / Netflix）印证：**离线计算不是「堆机器」，是「列存 + 三级裁剪 + 小文件 compaction + 统计信息质量 + 分队列隔离」5 件套**。
> - 关键时间线：字节 5+ 年 / 阿里 10+ 年 / 腾讯 10+ 年 / Netflix 5+ 年 —— **离线计算底座是 5+ 年长期工程**，且**核心命题从不是"算得快"，而是"读得少"**。
> - 选型第一原则：「**Spark + Iceberg + 列存 + 压缩**」（**最简单**）——**PB 级以下** → 「**自动 compaction + 统计信息运维**」（**必须**）→ 「**明细本地聚合跨区 + 分队列配额隔离**」（**生产**）→ 「**快照绑定可重现 + 多地域就近 + 峰值容量保障**」（**AI 时代**）。
> - 99% 的失败来自「**目录列举当元数据 + 行存全扫 + 小文件不治理 + 统计信息过期**」——必须有 **manifest 元数据 + 列存压缩 + 自动合并 + 统计信息覆盖**。
> - 真正的 ROI 来自「**IO -90% + 压缩 5~10x + P99 -95% + 跨区带宽 -90%**」——是**大厂离线数据底座能否承载 EB 级与 AI 特征工程的命脉**。

> 💡 **思考锚点**：本节把命题钉在「读得少」而不是「算得快」，并给了 6.5 那条四级阶梯——先拿你自己的离线栈填两个数：你最慢的那条大表查询，扫描量有没有像案例那样被三级裁剪压到全表的 **1%** 量级（0→1 档验收线「典型宽表只查 3 列的 IO 降 ≥ 80%」过没过）？你的存储还是不是「流批各写一份」（冗余没归零，6.7 的「存储 -40~50%」就落不到你头上）？两个数填完才知道自己卡在哪一级——若 IO 已过线、却在 6.6 里先踩了「统计信息过期，优化器选错计划」，你 1→10 档该先补的是自动 compaction，还是把统计信息的采集与新鲜度纳入运维？
