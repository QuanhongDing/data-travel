## 3. 设计模式与范式

> 重写口径：原 § 3 共 97 行、3 个 `###` 小节、0 个代码围栏（没有结构示意），列出 8 个模式与 7 个反模式。本版把 8 个模式与 7 个反模式的名称全部保留，原决策表里的场景组合与候选引擎（Flink、StarRocks、Doris、DataWorks）也一并并进 §3.3，为每个模式补上约束、结构、因果机制、代价与失效点，约 310 行。

### 3.1 先看约束：模式不是选择题，是约束的产物

「T+1 报表用 Spark、即席查询用 Trino、单机分析用 DuckDB」这类模式表，读起来像一份按场景勾选的菜单。但真实的离线架构不是选出来的，是被约束推出来的：同一句「算出昨日的 GMV」，在单机装得下的规模上是 DuckDB 里一条 SQL；在十万级任务/日的规模上必须是 Spark 写进带快照的表格式；在存量表全躺在 Hive Metastore 里的组织里，正确的第一步往往只是换一个执行引擎。三者写的 SQL 几乎一样，差别全在**中间结果的落点、故障后从哪里继续、以及这套东西每天被问多少次**。

所以本节的顺序是先把约束立起来，再看模式。判断一个模式选择是否成立，标准很简单：**你能不能说出它被哪条约束逼出来**。说不出约束的选型理由（最常见的是「统一技术栈」「社区活跃」）不是约束，是偏好——而偏好会把团队推到约束的另一侧，例如为了统一技术栈把多轮 JOIN 的批量作业放到交互式引擎上跑（后果见 [§ 7.7](08-offline-compute-section-7-sec7.md)）。

还有一条约束容易被漏掉：**这份算力每天实际被使用多少小时**。同样 100 vCPU，按需临时集群每天跑 2 小时与常驻集群 720 小时，账单差一个数量级（【推算】——推导链：vCPU 数 × 单价 × 月运行小时数，取 24 ÷ 2 = 12 倍；完整算式与单价来源见 [§ 7.4](08-offline-compute-section-7-sec7.md)），而这个差值与你选哪个引擎无关。它属于**交付形态**约束：不改变正确解，只改变代价，因此它决定的是"该不该常驻"，而不是"该选谁"。把这两类约束混在一起谈，就会出现"因为 Trino 省机器所以选 Trino"这类站不住的结论。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式 | 中间结果能否在算子间不落盘地传下去 | 「都是 SQL，换个引擎结果一样」——宽依赖轮数一多，引擎的恢复粒度就变成决定性问题 |
| 访问模式（点查 / 扫描 / 聚合） | 启动开销与执行开销谁占主导 | 「延迟低的引擎更快」——交互式引擎赢在短查询，重 ETL 上它会整条重跑 |
| 变更频率与历史要求 | 是否需要表格式与快照（Time Travel） | 「表就是一堆文件」——没有表格式，多引擎共存与回溯都不成立 |
| 一致性要求 | 是否允许多个引擎并发写同一张表 | 「读写分离随便谁写」——提交协议只保证单写者语义下的原子性 |
| 规模与成本约束 | 单机、集群还是云托管算力 | 「能装进内存就不用分布」——扫描量超过内存若干倍后，溢出磁盘会吃掉全部收益 |
| 团队技能与运维能力 | 能长期维护几种引擎 | 「多接一个引擎只是多配一次」——每多一种引擎，就多一条排障路径 |

### 3.2 模式逐个拆解（核心节）

原文件列出的 8 个模式全部保留，逐个给出约束、结构、机制、代价与失效点。

每个模式按同一套模板读：**约束**说明它被什么逼出来（说不出约束的模式不必选它）；**结构**用一段示意把关键机制画出来（示意里的"关键"一行才是要记住的东西）；**因果**给一条「因为机制 A，所以性质 B」的句式；**代价**是这套结构必然要付的成本，不是"略显复杂"；**失效点**写清优点在什么条件下反转成缺点。凡是你无法从模板里说出"失效点"的模式，说明还没真正理解它——**一个说不出什么时候会失效的方案，选它靠的是运气**。

#### 3.2.1 Hive on Spark：元数据不动，只换执行引擎

- **被什么约束逼出来**：表定义、分区、权限全在 Hive Metastore 里，动元数据的风险远高于换执行引擎；存量 SQL 也不能重写。
- **结构**：
```text
          Hive Metastore（表定义 / 分区 / 权限，权威且唯一）
                          │ 同一份元数据
   HiveQL 客户端 ────────►│◄──────── Spark / Trino 等引擎的 catalog
                          ▼
                    执行引擎（可替换）
                      ├── MapReduce（历史默认，最慢）
                      ├── Tez（DAG 执行）
                      └── Spark（Hive on Spark）
  ────────────────────────────────────────────────
  关键：引擎只回答"怎么算"，Metastore 回答"表在哪"
        → 迁移 = 换执行引擎，而不是换元数据
```
- **为什么这样设计有效**：因为元数据被放在独立于计算引擎的 Metastore 里、计算被交给可替换的引擎，所以存量迁移中「改动最小」的那条路径存在——表定义、分区、权限一行不动，只换执行路径。
- **代价**：每次执行多一层 HQL 到引擎计划的翻译，参数与方言要维护两套；该引擎的版本兼容矩阵成为长期负担。
- **失效点**：当组织已不再新增 Hive 资产、新作业全部原生写 Spark 时，「元数据不动」会反转成「两套方言与两套调优心智长期并存」的负担，因为同一份业务逻辑要在 HQL 与 Spark SQL 两条路径上分别适配与排错。
- **量化判据**：存量表里有 Metastore 条目的比例；没有条目的表（只有对象存储 URI）在接入前要先补一层表格式与注册流程，工作量从零变成周级到月级【经验】。
- **真实使用**：传统企业存量数仓迁移的过渡形态【经验】。判断方法：把你实际用的 Spark 与 Trino 的 catalog 指向同一个 Metastore 地址，看两边能否列出同一批表——能列出，即这条解耦层在生效。

#### 3.2.2 Spark SQL 直连：跳过翻译层，直接吃表格式与对象存储

- **被什么约束逼出来**：新作业没有存量方言包袱，也不接受"多一层翻译"，希望直接读 Parquet / Iceberg / Hive 表。
- **结构**（谓词下推与列剪裁在计划层完成，而不是在运行期过滤）：
```sql
-- Spark SQL 直连表格式：选择性在计划期就落到扫描上
SELECT dt, region, SUM(amount) AS gmv
FROM   iceberg.silver.orders
WHERE  dt BETWEEN '2025-01-01' AND '2025-01-31'   -- 分区剪裁
  AND  order_status = 'paid'                       -- 谓词下推
GROUP  BY dt, region;
-- 结构要点：表格式同时提供 (1) 表定义 (2) 分区与清单 (3) 快照
--           引擎拿到的不是文件路径，而是一份可下推的计划
```
- **为什么这样设计有效**：因为引擎拿到的是带 schema 的逻辑计划而不是一段 SQL 文本，所以谓词下推、列剪裁与代码生成能在计划期一次做完，扫描量由查询的选择性决定而不是由表大小决定。
- **代价**：方言从此绑定 Spark SQL，换引擎要改 SQL 与函数；表格式与各引擎的版本矩阵成为多引擎共存时的主要故障源。
- **失效点**：当查询变成亚秒级交互需求时，「直接读文件、无服务端」会反转成「每次都要付秒级启动开销」，因为冷启动与作业时长同量级时，省掉的那层翻译相对于启动成本可以忽略。
- **量化判据**：表格式规范版本与所有读写引擎的版本矩阵是否对得上——多引擎共存的故障八成出在这个矩阵上，而不是 SQL 方言上【经验】（该比例的来源是经验判断，不是统计量；判定方法见 [§ 7.3.4](08-offline-compute-section-7-sec7.md) 的版本矩阵一条）。
- **真实使用**：字节的离线任务体系以 Spark + 表格式为底座，规模达十万级任务/日量级【经验】（该量级在公开技术分享里反复出现，可按「字节跳动 离线计算 Spark Iceberg 任务量」一类关键词自行检索核验；完整的工程过程见 [§ 6 案例 8.1](08-offline-compute-section-6-sec6.md)）。

#### 3.2.3 Spark + Iceberg + Trino：写读分离的湖仓

- **被什么约束逼出来**：既要有批量重加工的写入能力，又要有分析师随时可查的读取能力，而且不想把同一份数据存两遍。
- **结构**：
```text
   Spark（唯一写入方）──► Iceberg 表（快照 + 清单文件 = 元数据契约）
                                │
                          ┌─────┴─────┐
                          ▼           ▼
                     Trino（读）   DuckDB（读 / 本地）
   ────────────────────────────────────────────────
   契约在"表格式"上，不在引擎上：
     新增一个读取方 = 让它的 catalog 认识这份快照
     不需要搬数据，也不需要复制一份给分析师
   边界：写入路径集中，读取路径分散
```
- **为什么这样设计有效**：因为表格式把表定义与快照从 Metastore 抽到了数据文件旁边的元数据文件里，所以同一份数据可以被 Spark 写、被 Trino 读、被 DuckDB 直读——多引擎共存才在工程上成立。
- **代价**：三套组件的版本兼容是长期负担；小文件与清单膨胀需要定期合并（compaction）；读取方看到的快照存在可见性延迟【经验】，刚提交的数据未必立刻可见。
- **失效点**：当写入方从一个变成多个时，「一份数据两处用」会反转成「快照互相覆盖、口径对不上」的事故源，因为提交协议只在单写者语义下保证原子性，跨引擎并发写要靠 catalog 的锁与人工约定兜底。
- **量化判据**：写入方数量（必须为 1）+ 每张表的快照保留时长（决定存储放大与回溯能力）+ 单分区文件数（决定是否需要立即合并）。
- **真实使用**：Netflix 以 Iceberg 列存承载 EB 级扫描【经验】（公开的技术分享里长期以此作为列存收益的例证），且 Iceberg 由 Netflix 开发并开源、2018 年捐入 Apache 基金会孵化器、2020 年毕业为顶级项目【公开】（时间线可在 Apache 基金会的项目公告与 Apache Iceberg 官网自行核验）；完整的工程过程见 [§ 6 案例 8.4](08-offline-compute-section-6-sec6.md)。

#### 3.2.4 Trino 联邦查询：原地读多源，不落地

- **被什么约束逼出来**：数据分散在数仓、关系库、消息队列里，而「先抽数落地再查」要多一次落盘与一轮调度，分析师的等待被拉长。
- **结构**：
```sql
-- Trino：一次查询跨三个连接器，数据不落地
SELECT o.order_id, o.amount, c.user_name, k.event_type
FROM   hive.sales.orders        o
JOIN   mysql.crm.customers      c ON o.user_id = c.id
LEFT   JOIN kafka.events.user_events k ON o.user_id = k.user_id
WHERE  o.dt = '2025-01-01';
-- 结构要点：Connector 负责"这个源怎么读"，引擎负责"怎么算"
--           谓词与投影能否下推，取决于对应 Connector 的实现
```
- **为什么这样设计有效**：因为连接器把「读哪个源」变成可插拔接口、执行走 worker 内存中的流水线交换而不设执行屏障，所以端到端延迟比同规模的屏障型引擎低一个量级。
- **代价**：下推能力因连接器而异，下推不到就会把整表拉进计算集群；查询规划发生在 Coordinator 这个单点上，高并发时先撞的是它的 CPU，而不是 worker 的算力。
- **失效点**：当跨源访问从例外变成常态（每天都要 JOIN 三四个源的全量数据）时，「原地读、不落地」会反转成「每次都在源端重复全表扫描」，因为联邦查询不缓存中间结果，重复的部分每次都要重算——此时正确做法是把高频部分物化成表。
- **量化判据**：把跨源查询的过滤条件下推给引擎，看源端实际返回多少行——下推不到的跨源查询会把整表拉进计算集群；同时观察 Coordinator 与 worker 谁先饱和。
- **真实使用**：Trino 是 Presto 社区分叉出的那条主线——分叉发生在 2018 年末，2019 年 1 月发布首个独立 release，2020 年才更名为 Trino【公开】（**分叉与更名不是同一年的事**，两者相隔约两年；时间线可对照 Trino 官方沿革说明，以及其发布记录里版本编号的连续性自行核验）；联邦查询是它被广泛采用的主因。

#### 3.2.5 DuckDB 内嵌分析：把集群省掉

- **被什么约束逼出来**：数据装得进一台机器、分析在 Notebook 或本地完成，为它维护一个集群的固定成本不划算。
- **结构**：
```sql
-- DuckDB：进程内直接读 Parquet，无服务端、无网络往返
SELECT region, SUM(amount) AS gmv, COUNT(DISTINCT user_id) AS users
FROM   read_parquet('s3://lake/orders/dt=2025-01-01/*.parquet')
WHERE  order_status = 'paid'
GROUP  BY region
ORDER  BY gmv DESC;
-- 结构要点：文件即表；没有 Metastore、没有权限体系、没有并发写
--           "表在哪"这个问题被交给文件路径
```
- **为什么这样设计有效**：因为引擎在进程内、按列式批次向量化执行，所以它省掉的是 shuffle 与调度这两项开销，而不是少算了数据——单机能容纳的数据上，这部分开销往往就是大部分耗时。
- **代价**：扩展轴只有纵向一条（超过单机能力就必须换引擎，不是加机器）；没有中心元数据，也就没有多用户隔离、统一权限与血缘可追；单进程语义下并发写不受支持。
- **失效点**：当单次扫描量超过内存约 5 倍（64 GB 内存下约 320 GB）【经验】时，「省掉 shuffle」会反转成「磁盘往返主导」，因为数据放不进内存就得溢出到磁盘，此后每个算子都要读写盘。
- **量化判据**：把同一查询在 1 倍、2 倍、5 倍内存的数据量上各跑一次，看耗时是否呈超线性上升——超线性说明磁盘往返已主导，与硬件具体数字无关。
- **真实使用**：DuckDB 于 2024 年发布 1.0（【公开】[DuckDB 1.0 发布公告, 2024]——可在 DuckDB 官方仓库的发布记录里按版本号 1.0.0 自行核验），被广泛用于本地与 Notebook 场景的 OLAP 分析。

#### 3.2.6 Spark Structured Streaming（离线语义）：一套代码，两种触发

- **被什么约束逼出来**：同一条业务逻辑既要能按批跑全量，又要能按流跑增量，团队不接受维护两套口径。
- **结构**：
```python
# 流式接口 + 离线语义：处理完当前可用数据就停，然后退出
# （PySpark 等价写法）
streaming_df = (spark.readStream.format("kafka")
                     .option("subscribe", "orders").load())
query = (streaming_df.writeStream
                     .trigger(availableNow=True)      # 关键：不是常驻
                     .option("checkpointLocation", "s3://ckpt/orders")
                     .toTable("iceberg.silver.orders"))
# 结构要点：同一份 DataFrame 逻辑，由 trigger 决定"按批跑"还是"一直跑"
#           checkpoint 目录是状态的一部分，丢了就得重来
```
- **为什么这样设计有效**：因为流式执行与批执行共用同一套 DataFrame API 与同一份逻辑计划，所以「一套逻辑、两种触发」在语义上成立，批与流的口径漂移被结构性消除。
- **代价**：checkpoint 成为必须维护的状态（其丢失等价于重跑）；去重与 upsert 语义要由 sink 与主键约定承担；增量进度的可观测性弱于独立调度的批作业。
- **失效点**：当延迟要求压到秒级以内时，「处理完可用数据就停」会反转成延迟瓶颈，因为它按批调度、最小延迟由批间隔决定——此时需要的是常驻流作业，而不是更短的调度间隔。
- **量化判据**：批间隔（`availableNow` 两次触发的实际间隔）与业务可接受的端到端延迟之比；两者接近时，这个折中就不能再用了。
- **真实使用**：这是已有批作业迁移到流批一体时最常见的过渡形态【经验】；`availableNow` 触发与 checkpoint 的语义可由你所用 Spark 版本的官方 Structured Streaming 文档核验。

#### 3.2.7 MaxCompute：把引擎、元数据、调度合成一体

- **被什么约束逼出来**：EB 级单表与海量任务量，且自建机房的容量、外购引擎的可定制程度都不够。
- **结构**：
```text
   统一元数据 ─┐
   统一调度  ──┼──► 自研执行引擎 ──► 作业级资源隔离
   统一权限  ─┘
   ────────────────────────────────────────────────
   关键：三层由同一方掌控，于是可以跨层优化
         例：用单表统计信息重排执行计划、
             调度与算力一起弹性伸缩、
             配额直接挂在作业而不是集群上
   代价：优化的前提是"这一整套同时在场"
```
- **为什么这样设计有效**：因为元数据、调度与执行引擎由同一方掌控，所以能做跨层的联合优化——例如把统计信息直接喂给计划重排、把弹性伸缩做在调度层，而这类优化在多引擎拼接的栈里没有人负责。
- **代价**：方言、函数与 SDK 与平台绑定；作业诊断依赖厂商工具链；优化经验不可移植到其他引擎。
- **失效点**：当业务要求多云或本地化部署时，「跨层优化」会反转成「算力与元数据一起被绑定」的迁移壁垒，因为优化的前提正是那套自研组件同时在场——拆开之后既失去优化，又要重付一遍迁移成本。
- **量化判据**：有多云或本地化部署的硬要求吗？有，就先把"绑定成本"算进立项材料；没有，跨层优化的收益才可能兑现。
- **真实使用**：阿里 MaxCompute 以自研引擎承载 EB 级单表负载【经验】（其产品材料与公开分享长期以此为定位，可按「MaxCompute EB 级单表 自研引擎」一类关键词自行检索核验；完整的工程过程见 [§ 6 案例 8.2](08-offline-compute-section-6-sec6.md)）。

#### 3.2.8 Spark 4.0 + AI Functions：让模型调用成为计划里的一个算子

- **被什么约束逼出来**：AI 特征与 Embedding 要批量生成，而把 PB 级数据搬出集群再算，既慢又把数据搬到了治理边界之外。
- **结构**：
```sql
-- 把模型调用表达成表函数，与普通算子一起进入计划
CREATE TABLE gold.item_embedding AS
SELECT item_id,
       ai_embed(item_title, item_desc) AS emb,   -- 模型调用作为列表达式
       region, dt
FROM   silver.item
WHERE  dt = '2025-01-01' AND region IN ('CN','US');  -- 先过滤，再调用
-- 结构要点：
--   (1) 过滤/剪裁在调用之前生效 → 调用次数由选择性决定
--   (2) 向量与半结构化类型（如 VARIANT）成为一等的列类型
--   (3) 模型版本 + 提示词成为作业依赖的一部分
```
- **为什么这样设计有效**：因为模型调用被表达成计划里的一个算子，所以分区剪裁与谓词下推能在它之前生效，调用次数由数据的选择性决定，而不是由表的大小决定。
- **代价**：外呼有配额与速率限制，必须按批限流与退避重试；模型版本与提示词要跟作业一起版本化，否则结果不可复现；单次调用的成本进入作业成本函数，且通常远高于一次普通算子。
- **失效点**：当模型调用位于计划下游、且上游数据量极大时，「下推省调用」会反转成「重跑即重新付费」，因为任何一次 stage 失败都会让已算过数据上的模型调用重打一遍——修法是先把结果物化到表，再对其加幂等键。
- **量化判据**：单次调用成本 × 调用次数，与"先把结果物化再加幂等键"的方案对比；前者随重跑次数放大，后者把重跑变成纯计算。
- **真实使用**：开源 Spark 4.0 提供了 VARIANT 等半结构化类型与 Spark Connect 等能力；模型调用类表函数主要由托管发行版提供（例如 `ai_query` 一类的接口）。**具体函数与可用性以你所用发行版的官方文档为准**（该接口随版本演进，故不锚定年份）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 存量表在 Metastore 里 + 暂不迁移 | 保留 Metastore，换执行引擎（3.2.1） | 一次性重写 Spark SQL 直连的元数据迁移风险高于收益 | 表有 Metastore 条目，还是只有一个对象存储 URI |
| 新作业 + 固定调度 + 多轮宽依赖 | Spark SQL 直连 + 表格式（3.2.2） | 不选交互式引擎：失败即整条重跑，重跑又更易失败 | shuffle 落盘量 ÷ 输入量（大于 1–3 倍即需按中间结果做容量规划）【经验】 |
| 大数据 ETL（重加工 + 上游已有流式入湖） | Spark + Iceberg + Flink（3.2.2 / 3.2.3） | 不选"重加工也交给流式引擎"：多轮宽依赖与全量回溯在流式路径上代价更高 | 重加工里含不含多轮宽依赖、需不需要全量回溯 |
| 分析师即席 + 多源联邦 | Trino 联邦查询（3.2.4） | 不选 Spark：秒级启动对交互查询不可接受 | 日有效查询小时数 ÷ 24 |
| 报表类高频聚合 + 单源 | StarRocks / Doris（预聚合 + 外表，引擎族见 [§ 7.2](08-offline-compute-section-7-sec7.md)） | 不选 Trino：每次现算的成本随查询频次线性上升 | 同一查询每天被问多少次、预聚合能命中多少 |
| 单机百 GB 到数百 GB + Notebook | DuckDB 内嵌分析（3.2.5） | 不选分布式：这个量级只剩调度开销 | 单次扫描量 ÷ 内存（超过约 5 倍即换族）【经验】 |
| 一套逻辑要同时按批与按流 | Structured Streaming 离线语义（3.2.6） | 不选两套代码：批流两套实现必然口径漂移 | 延迟要求是否已低于批间隔 |
| 实时与离线统一（延迟已压到批间隔以下） | Spark + Flink（3.2.6 的常驻流对偶） | 不选"把批间隔调短"：批间隔是延迟的硬下限，调短只是把批做成不稳定流 | 端到端延迟要求 ÷ 批间隔 |
| 写重加工 + 读随时可查，一份数据 | Spark + Iceberg + Trino（3.2.3；报表侧可再加 StarRocks 走外表预聚合） | 不选"两个引擎都写"：快照会互相覆盖 | 写入方是否唯一 |
| EB 级单表 + 云端算力 + 可接受绑定 | MaxCompute（3.2.7） | 不选自建：容量与跨层定制能力不足 | 是否有多云或本地化硬要求 |
| 阿里系业务 / 调度与元数据想一并托管 | MaxCompute + DataWorks（3.2.7） | 不选自建栈：调度、元数据与权限要重搭一遍 | 组织是否已绑在该生态上、迁移成本算不算得过来 |
| 批量生成 Embedding / AI 特征 | Spark + 表函数（3.2.8） | 不选"把数据搬出去算"：既慢又跨出治理边界 | 单次调用成本 × 调用次数是否进入成本函数 |

**本主题下最常被误选的一对，是 Trino 与 Spark**：把多轮 JOIN 的批量作业放进 Trino（为了"统一技术栈、延迟又低"），把交互查询丢给 Spark（为了"少接一个组件"）。前者的实际后果是夜间批处理窗口被重试吃掉——流水线引擎失败即整条重跑；后者是分析师为一次查询等一个冷启动。**分界线不在数据多大，而在作业含不含多轮宽依赖**：含，就必须落在屏障型引擎上。

反向的误选同样常见：**把 DuckDB 当成"小号的 Spark"来接生产任务**。它的单机优势只在"数据装得下"时成立，而生产任务的扫描量往往随分区数增长——一旦越过内存的数倍，它既没有空间做细粒度恢复（单进程失败即重来），也没有分布式出路。选它的前提是能对扫描量给出上界，给不出上界时应该选分布式方案。

### 3.4 组合模式：真实系统不会只用一种

**组合 1：Spark + 表格式 + Trino（写读分离）**

- **组合构成**：Spark 负责写入与重加工，表格式（Iceberg / Hudi / Paimon）负责快照与元数据契约，Trino 负责交互查询。
- **职责边界**：**写入方唯一**——Spark 是唯一写入者，其他引擎只读；多个引擎同时写同一张表，必须显式约定提交协议与冲突处理。
- **运维代价**：三套组件的版本矩阵（表格式规范版本 × 两个引擎版本）需要长期维护，这是这个组合最真实的成本项。
- **适合规模**：万级表以上、写入负载与读取负载的特征明显分化（前者重吞吐、后者重延迟）的组织。

**组合 2：Spark + DuckDB（算力分层）**

- **组合构成**：Spark 做大规模 ETL 与出表层，DuckDB 在单机或 Notebook 里对结果集做交互分析。
- **职责边界**：**DuckDB 只读、不承担共享写入**，也不承担多用户权限——它处理的是"已经算好的结果"，而不是"共享的资产"。
- **运维代价**：很低（DuckDB 无服务端、无 Metastore），但要守住"结果集"的体量上限：一旦分析师真去 `read_parquet` 整个数据湖，单机会被打爆，而此时故障不在 Spark 侧，排障方向容易跑偏。
- **适合规模**：从中小团队到中大型团队的分析侧，前提是数据准备与交互分析能清楚分层。

**组合 3：Hive Metastore 保持 + 引擎逐个替换**

- **组合构成**：元数据层完全不动，把执行引擎从 MR / Tez 换成 Spark，或让 Trino 直读 Hive 表。
- **职责边界**：**Hive 只负责"表在哪"，不负责"算得多快"**——引擎的选择必须显式化并写进作业模板，否则又会退回"按 Hive 调优"的随机状态。
- **运维代价**：短期内三种引擎并存，排障路径变多；换来的是迁移风险最低、可以按作业逐个推进。
- **适合规模**：存量千级到万级表、且不能停机迁移的传统企业。

组合的第一原则是**让"写"集中、"读"分散**：写入路径越单一，表格式与提交协议越可控；读取方可以有很多个，因为它们只共享同一份元数据契约。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 使用 RDD 编程 | 新作业里出现 `map` / `reduceByKey` 而周围全是 DataFrame | 优化器整段失效：Catalyst 与 Tungsten 的谓词下推、代码生成、向量化都作用不到算子级 API 上 | 早期 Spark 教程与老代码直接沿用 | 优先 DataFrame / Spark SQL；仅有非结构化解析等 SQL 表达不了的场合才落到 RDD 层 |
| 忽视数据倾斜 | stage 内最长 task 与中位 task 耗时差一个量级 | 屏障型引擎在 stage 边界等最慢的 task，倾斜的代价被按"最慢分区"而不是"平均分区"计费 | 开发环境数据均匀，倾斜只在生产规模出现 | AQE 倾斜 Join 处理 + 两阶段聚合（加盐）+ 广播 Join；上线前用全量数据跑一次分布检查 |
| 小文件未治理 | 单个分区下文件数上万，作业启动时间超过计算时间 | 文件级元数据操作与任务调度开销变成主导项——启动开销大于处理时间，加机器也无法改善 | 流式/微批写入与频繁覆写天然产生小文件 | 写入侧定期合并 + 用表格式的合并机制；把"单分区文件数"做成监控指标 |
| 未启用 AQE | 执行详情里出现大量空的分区与固定分区数 | 静态计划按编译期估计的分区数执行，末段大量分区无数据却仍要调度 | 沿用了旧版本的默认配置 | 使用 AQE 默认为 true 的版本（Spark 3.2.0 起 `spark.sql.adaptive.enabled` 默认为 true【公开】[Apache Spark 3.2 Release Notes, 2021]——可在 Spark 官方发布说明中按版本号 3.2.0 与条目 SPARK-33679 自行核验，[§ 7.3.1](08-offline-compute-section-7-sec7.md) 引的是同一条版本事实；**"3.0 引入"与"3.2 起默认"是两件事，不要合并**），旧版本显式开启 |
| Hive 性能问题（默认走 MR） | 同类 SQL 在 Spark 上小时级、在 Hive 上仍是数小时；没人说得清底层是 MR 还是 Tez | 调优方向随机：按"Hive 调优"找的参数其实属于底层引擎，效果不可复现 | Hive 只暴露 SQL 入口，底层引擎是隐式的 | 把"方言"与"引擎"解耦：Hive 保留元数据与方言兼容角色，执行引擎显式选择 |
| Spark 资源调度不合理 | Executor 内存与 core 固定写死，OOM 与"内存闲置"同时出现 | 静态配额与动态负载不匹配：shuffle 峰值时 OOM，其余时段资源空转 | 配置从模板复制而来，缺乏按负载调整的反馈 | 开启动态分配 + 按分区规模规划并行度；把资源请求写进作业模板而不是散落在提交脚本里 |
| 滥用 UDF | 计划里看不到下推，同规模 SQL 比内置函数慢显著 | 自定义 UDF 对优化器是不透明黑盒，谓词与列剪裁都推不进去 | 内置函数找不到就用循环重写一遍 | 优先内置函数；确需自定义时用向量化的 Pandas UDF，并评估其可下推性 |

三个最危险的反模式，在生产中是这样暴露的。

**忽视数据倾斜**很少以"作业慢"这种温和形态出现，它的典型暴露方式是某个 stage 长期停在进度条的 99%（说明性举例：约 200 个 task 里完成了 199 个，最后一个跑了数小时——此处两个数字是举例，不是统计量），然后 executor 因超出内存被杀、stage 重算、重算又撞上同样的倾斜——**受害的不只是耗时，还有作业成功率**。而屏障型引擎的计费口径是"最慢的那个分区"，所以倾斜一旦出现，加机器往往不但没用，还会因为任务数变多而放大调度开销。

**小文件未治理**的暴露方式是"数据没变多、作业却越来越慢"：单分区文件数随每日写入线性增长，文件级元数据操作与任务调度开销随之增长，而加机器对元数据操作几乎没有帮助。它还有一个不易察觉的副作用：同一份数据重新合并之后，谓词下推能裁掉的分区才真正被裁掉，扫描量可能因此下降一个量级。

**滥用 UDF** 的暴露方式最隐蔽：逻辑正确、结果正确、只是永远比隔壁团队的同规模作业慢，且查执行计划看不出原因——**优化器从未看到那段逻辑**，谓词下推、列剪裁与代码生成都在它面前失效。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单机 → 分布式 | DuckDB 内嵌 | 单次扫描量超过内存约 5 倍（64 GB 下约 320 GB）后磁盘往返主导【经验】 | Spark + 表格式（3.2.2） | SQL 重写、补元数据与权限、补调度 |
| 百 GB → PB | Spark SQL 直连 + 本地盘 shuffle | shuffle 落盘量超过本地盘容量，必须改落对象存储；且启动与调度开销随任务数增长 | 分区策略重构 + 表格式 + 容量按中间结果规划 | 分区键与文件布局重做，历史数据需重写 |
| 单写入方 → 多引擎并发写 | Spark + Iceberg + Trino（单写） | 快照互相覆盖、口径对不上 | 冻结写入方（只留 Spark 写，其他只读），或引入提交协调 | 组织约定与工具链改造，比技术改动更难 |
| 小时级 → 分钟级 → 秒级 | Structured Streaming 离线语义 | 批间隔成为最小延迟的硬下限 | 常驻流作业 + 实时链路 | 运维形态从"跑批"变成"值班"，监控与告警体系要重建 |
| 单团队 → 多租户 | Spark 独占集群 | 排队与配额冲突，一个团队的倾斜作业拖慢所有人 | 多租户 SQL 网关（如 Kyuubi）+ 队列配额 | 引入网关层，作业提交入口与鉴权改造 |
| 传统 Hive → 湖仓 | Hive on Spark | 单引擎写入 + 单引擎读取，交互查询无路可走 | 表格式 + 多引擎（3.2.3） | 存量表迁移与双跑校验，周期通常以月计【经验】 |

跃迁的共同规律是：**触发点几乎总是"中间结果放不下"或"被问的次数变了"，而不是"数据量数字变了"**。所以判断该不该换模式，不要看表的总量，要看你最近一次全量作业的 shuffle 放大倍数、以及这套结果每天实际被查询的小时数。

迁移次序也有规律：**先换"每天被问最多次"和"每次出事代价最大"的那部分**，而不是按表数量平均推进。理由与 §7.5 的判定门一致——存量迁移的投入产出比由痛点密度决定。反过来说，如果一次迁移计划里列不出"哪一个作业必须换"，那它大概率不是一次迁移，而是一次重写；重写的窗口期通常以季度计【经验】，在此期间两套链路必须同时跑通。

### 3.7 自检清单

- [ ] 每个作业的 shuffle 放大倍数（shuffle 落盘量 ÷ 输入量）实测过吗？大于 1–3 倍时，容量规划是否以中间结果为准而不是以输入为准【经验】？
- [ ] 有没有把含多轮 JOIN / GROUP BY 的批量作业放在不设执行屏障的交互式引擎上跑？
- [ ] 同一张表是否存在多个写入引擎？若有，提交协议与冲突处理写在哪里？
- [ ] 事实表与中间表里是否出现过大量小于一个数据块的小文件？单分区文件数有没有进监控？
- [ ] 执行计划里还能看到多少 `map` / `reduceByKey` 这类算子级 API（即优化器看不到的逻辑）？
- [ ] 自定义 UDF 是否经过评估，确认内置函数或向量化 UDF 无法替代？
- [ ] 团队是否说得清每个 Hive 作业底层跑的是 MR、Tez 还是 Spark？说不清就说明引擎是隐式的。
- [ ] 交互查询的日有效利用率算过吗？低于 30% 时，是否考虑过"按需跑批 + 结果表"替代常驻集群【经验】？
- [ ] 接入的表有 Metastore 条目，还是只有一个对象存储 URI？后者意味着迁移工作量从零变成周级到月级。
- [ ] 若一个作业在长跑中被 kill，恢复是重算局部还是整条重来？长窗口作业是否用了具备细粒度恢复的引擎？
- [ ] 模型调用类算子（AI 特征、Embedding）是否按选择性下推？重跑一次是否会把已算数据的模型调用重打一遍？
- [ ] 新增一种引擎之前，算过它会新增几条排障路径吗？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 存量表在 Metastore，不能停机迁移 | 保留元数据，换执行引擎（3.2.1） | 元数据与计算解耦，迁移只换执行路径 |
| 多轮宽依赖 + 需要细粒度恢复 | Spark SQL 直连 + 表格式（3.2.2） | 中间结果落盘 + 执行屏障 → 故障退化为局部重算 |
| 多源、交互、延迟敏感 | Trino 联邦查询（3.2.4） | 内存流水线交换不设屏障 → 端到端延迟低一个量级 |
| 单机装得下的分析 | DuckDB 内嵌（3.2.5） | 进程内向量化，省掉 shuffle 与调度 |
| 一份数据、两个消费方 | Spark 写 + 表格式 + Trino 读（3.2.3） | 契约落在表格式上，增读取方不搬数据 |
| 批与流同一套逻辑 | Structured Streaming 离线语义（3.2.6） | 同一份逻辑计划，由触发方式决定按批还是常驻 |

> 本节小结：本主题下决定模式选择的**唯一那条约束，是"中间结果能不能在算子之间不落盘地传下去"**——它同时决定了恢复粒度、尾延迟与容量规划的口径。其余约束（规模、成本、团队技能）只影响代价大小与交付形态，不改变正确解；而一旦你按"数据量数字"而不是按"依赖形态"选型，选出的模式就会在第一次 stage 失败时暴露。
