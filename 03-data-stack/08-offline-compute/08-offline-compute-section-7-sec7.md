## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表给 Spark 的"性能"打 5 分、Hive 打 3 分，给 DuckDB 的"扩展性"打 2 分、AI 友好打 5 分。这些分数的问题在于**它们把不同物种放在同一条跑道上比**：DuckDB 是进程内单机引擎，Spark 是分布式 DAG 调度器，Trino 是交互式 MPP 查询引擎，Hive 是"SQL 翻译层 + 可替换执行引擎"。拿"扩展性"给 DuckDB 打 2 分，等价于拿"载重"给一辆摩托车打分——它不是"不那么能载"，而是**品类不同**。真正需要回答的问题是：**你的作业形态决定了你该选哪个品类**，而不是在这个品类里挑分数高的。

第二个问题是同一维度在不同规模下权重相反。小规模时"易用性"和"启动成本"压倒一切——一条 `SELECT` 从写完到出结果的时间就是全部体验；大规模时"故障恢复粒度"和"shuffle 能落多大盘"成为硬约束，易用性退到很后面。**而这类逐列打分的表隐含地假设各维度权重与规模无关**，因此它给出的排序只在一个规模区间内成立——**规模一变，排序会翻转，而分数不会。**

第三，打分表把**引擎能力**与**交付形态**混在一起。Spark 可以跑在本地的按需集群上，跑在常驻 YARN 集群上，也可以跑在托管的 Serverless 版本上——这三者的成本模型差一个量级，但"Spark"这个名字在打分表里只有一行。同理，Trino 常驻与 Trino 按需是完全不同的账单结构。**本章因此把"运行小时数"当作与引擎选择同等重要的一个维度**（见 7.4），因为它往往才是账单差异的主因。

第四，离线计算领域有一条**被打分表完全遗漏**的事实：这门技术栈的选型，八成不是选出来的，而是**历史形成的**。企业里已有的 Hive Metastore、已有的调度系统、已有的 SQL 方言习惯、已有的运维人员技能，共同构成了一个极强的约束。因此本章的决策树不是"从零选引擎"，而是"**在既有约束下，哪个引擎值得新增**"。

第五，打分表把"AI 友好"当成一个引擎属性，这是个范畴错误。**离线计算在 AI 时代的位置是"批量生成训练与检索用的数据"，而不是"自己变成 AI 系统"**：批量 Embedding、特征回填、训练样本拼接，这些都是标准的宽依赖批处理——它们对引擎的要求与十年前的 ETL 没有本质区别，只是数据形态从结构化变成了文本与向量。所以"AI 友好"真正在问的是"**这个引擎能不能高效地读写列式文件与向量列**"，这是 7.3.4 里表格式耦合的问题，不是一张单独的评分卡。

**本章所有数字按三档标注**：【公开】（有公开来源，正文给出处与年份）、【推算】（由公开前提推导，正文写出推导链）、【经验】（行业普遍实践，只给区间与条件）。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 作业形态 | 是重 ETL（多轮宽依赖）还是即席查询（单轮扫描） | 两者对中间结果落点与故障恢复的要求相反，直接决定品类 |
| 中间结果的落点 | shuffle 落哪、能不能不落 | 决定作业规模上限、尾延迟，以及"失败要不要整条重跑" |
| 成本随什么增长 | vCPU-小时、常驻小时数、还是单机规格 | 决定账单主项是"跑多久"还是"养多久"；这是最容易被忽略的一条 |
| 元数据与表格式耦合 | 换引擎要不要动元数据与文件布局 | 决定迁移成本与"能不能多引擎共存" |
| 存量约束 | 已有 Metastore / 调度 / 权限 / 人员技能是什么 | 决定哪些方案在组织上根本落不了地 |
| 演进风险 | 项目活跃度、是否仍被上游投入 | 决定三年后你会不会被迫再做一次迁移 |

> 判据必须结合本主题具体化：离线计算里**唯一真正不可协商的一条是"作业形态"**——它把候选劈成两半，剩下五条只在你已经进入正确的那一半之后才有意义。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Spark | 通用分布式 DAG 计算引擎 | 把作业切成以 shuffle 为边界的 stage，逐 stage 调度、shuffle 落盘、按 lineage 重算 | 离线 ETL 主力，PB 级批处理 | Apache-2.0；亦有托管版（EMR / Databricks 等） |
| Hive | SQL-on-Hadoop 的 SQL 层与元数据服务 | SQL 方言 + Hive Metastore，执行交给可替换引擎（MR / Tez / Spark） | 传统企业存量数仓 | Apache-2.0 |
| Trino | 分布式交互式 MPP 查询引擎 | Coordinator 规划、Worker 流水线内存交换，无 stage 屏障；Connector 接多源 | 联邦查询、ad-hoc 分析 | Apache-2.0；亦有托管版 |
| Presto（PrestoDB） | Trino 的同源分支 | 同源架构，社区与生态走向不同 | 已完成 Presto 绑定的团队 | Apache-2.0 |
| DuckDB | 进程内单机 OLAP 引擎 | 无服务、向量化 + morsel 驱动执行、可溢出到磁盘、直读 Parquet | 单机分析与 AI 数据准备 | MIT |
| MPP OLAP（Doris / StarRocks） | 面向 OLAP 的实时分析库 | 自有的存储 + 向量化执行 + 物化视图，查询低延迟 | 报表与实时分析 | Apache-2.0 |

这六个候选分成**四族**，跨族差异远大于族内差异。**族一：DAG 调度型批量引擎**（Spark）——以 stage 屏障和 shuffle 落盘换取 PB 级稳定性。**族二：SQL 层 + 可替换执行引擎**（Hive）——它的"能力"其实是它下面那个引擎的能力。**族三：交互式 MPP 查询引擎**（Trino、Presto、Doris/StarRocks）——以内存流水线交换替代 stage 间落盘来换低延迟，代价是故障域大（族内仍有差别：Trino / Presto 基本不设执行屏障，Doris / StarRocks 的部分算子仍有屏障，见 7.3.1 的表）。**族四：进程内单机引擎**（DuckDB）——没有分布式，也没有分布式带来的复杂度。

**先分族再选**能省掉一半比较：如果一个作业是"每天全量重算、多轮 JOIN"，它天然落在族一，把 DuckDB 或 Trino 的分数拿来比毫无意义；如果需求是"分析师点一下就出结果"，它天然落在族三/族四，Spark 的启动延迟就是不可接受的。

还要提醒**同族内部的差异是"运维与生态"，不是"能力"**：Trino 与 Presto 同源，Doris 与 StarRocks 同源，选哪个更多取决于社区活跃度、连接器覆盖与团队已有经验，而不是能否完成任务。

| 同族内的候选对 | 能力上是否等价 | 真正该比什么 | 判定方法 |
| --- | :---: | --- | --- |
| Trino ↔ Presto（PrestoDB） | 基本等价（同源分叉） | 社区活跃度、连接器覆盖、"要不要为了迁移而迁移" | 拿同一批生产 SQL 在两个引擎上跑，看结果与延迟是否同量级；同量级就不迁移 |
| Doris ↔ StarRocks | 基本等价（同源演进） | 物化视图与外部表能力、团队既有经验 | 用你的真实报表压测两者，看"预聚合能命中多少" |
| Hive-on-Tez ↔ Hive-on-Spark | **不等价**：性能由底层引擎决定 | 是"换引擎"还是"换方言"，二者成本完全不同 | 看作业的实际执行引擎（`EXPLAIN` 或作业历史），而不是看 SQL 写在哪 |
| Spark（托管） ↔ Spark（自建） | 能力等价，交付形态不同 | 按需小时数、启动延迟、运维带宽 | 按 7.4 的成本函数分别算一遍账单 |

**而跨族之间真正不能比的，是交付形态**。同一个 Spark，按需起集群与常驻集群的成本差一个量级（7.4 会算这笔账）；同一个 Trino，常驻与按需的体验与账单完全不同。因此本章把每个候选都当作"引擎 + 交付形态"的组合来看——**只写引擎名的对比表，实际上漏掉了决定账单的那一半。**

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 中间结果的落点与执行屏障

**机制是什么**：宽依赖（JOIN、GROUP BY）必须把数据按 key 重新分布。这次分布的结果放在哪里，以及是否要在该处"等齐所有上游任务"，决定了一个引擎的规模上限与尾延迟。

**它在各候选中的实现差异**：

| 候选 | 中间结果落点 | 执行屏障 | 由此产生的典型延迟 |
| --- | --- | --- | --- |
| Spark | Shuffle 文件落本地盘（可配远端） | 有：stage 之间等齐 | 秒级启动 + 分钟级执行 |
| Hive（on Tez） | Tez 的中间结果，可落盘或内存 | 有：DAG 顶点之间 | 依底层引擎 |
| Trino / Presto | Worker 内存中的流水线交换 | 无屏障，边算边传 | 亚秒到秒级 |
| DuckDB | 单进程内流水线，必要时溢出磁盘 | 无跨节点屏障 | 毫秒到秒级 |
| Doris / StarRocks | 内存 + 本地存储的流水线 | 部分算子有 | 亚秒级 |

**由此必然导出的性质（因果句）**：因为 **Spark 把 shuffle 结果落盘并在 stage 边界设置屏障**，所以它能把"故障恢复"退化为**局部重算**（丢失的分区按 lineage 重算，不必重跑整个作业）——这是它能稳定承载 PB 级作业的根本原因；但同一机制也必然带来两个代价：一是**每个 stage 边界都要等最慢的那个 task**，尾延迟被放大；二是**shuffle 落盘量成为容量规划的硬约束**，一个多轮 JOIN 的作业可能把中间结果写得比输入还大。反过来，因为 **Trino 走内存流水线交换、不设屏障**，所以它的端到端延迟通常比同规模 Spark 低一个量级；但也因此**一个 worker 的故障会让整条查询失败**——这正是 Trino 后来引入 fault-tolerant execution、把 exchange 落到对象存储的原因（【公开】[Trino 发布说明, 2022]）。

**怎么量化这条机制**（选型前必做的一次测量）：

| 你要测的量 | 怎么测 | 它决定什么 |
| --- | --- | --- |
| shuffle 放大倍数 = shuffle 落盘量 ÷ 输入量 | 跑一次全量作业，读执行详情里的 shuffle 字节数 | 大于 1–3 倍时（【经验】），容量规划要以中间结果为准，而不是以输入为准 |
| 最长 task 与中位 task 的耗时比 | 看 stage 内 task 耗时的分布 | 比值高说明数据倾斜，屏障的尾延迟代价被放大 |
| 失败后重算的比例 | 主动 kill 一个 executor 后观察恢复范围 | 决定长作业能否接受流水线引擎 |

**公开证据**【公开】：Spark 的 RDD 与 lineage 重算机制出自其原始论文（NSDI 2012 "Resilient Distributed Datasets"）；AQE（运行时按实际 shuffle 统计调整分区与 Join 策略）由 Spark 3.0（2020）引入，但 `spark.sql.adaptive.enabled` 直到 Spark 3.2.0（2021，SPARK-33679）才默认为 true——**"3.0 引入"与"3.2 起默认"是两个版本事实，不能合并**（[Apache Spark 3.0 / 3.2 Release Notes, 2020–2021]）；Trino 的 fault-tolerant execution 把 exchange 落对象存储以支持失败重试（[Trino 发布说明, 2022]）。判定方法：看该引擎的"作业失败后发生了什么"——只重试失败 task 的是屏障型，整条重跑的是流水线型。

**失效条件**：当作业的 shuffle 量很小（例如单轮扫描聚合）时，Spark 的屏障机制只剩开销没有收益，此时单机引擎或流水线引擎更快更省；反过来，当作业的 shuffle 放大倍数极高（多轮 JOIN + 数据倾斜）时，内存流水线引擎会因为中间结果放不下而失败——**"能不能把中间结果放到下一个算子之前不落盘"就是这条分界线**。

#### 7.3.2 故障恢复粒度：重算一个分区，还是重跑整条查询

**机制是什么**：分布式执行必然遇到节点故障、抢占、OOM。故障后"从哪里继续"，直接决定了作业在长窗口内的成功率。

**它在各候选中的实现差异**：

| 候选 | 恢复单位 | 依赖什么 | 长作业的成功率特征 |
| --- | --- | --- | --- |
| Spark | 分区 / stage | RDD lineage + shuffle 文件仍在 | 高：重算局部即可 |
| Hive（MR / Tez） | task / DAG 顶点 | 中间结果落盘 + 引擎重试 | 中到高，依引擎 |
| Trino | 整条查询（默认） | 需启用 fault-tolerant execution 才有更细粒度 | 低：失败即整条重跑 |
| DuckDB | 整个进程 | 无（单机，失败即重来） | 与单机稳定性一致 |
| Doris / StarRocks | 查询级 | 部分算子可重试 | 中 |

**由此必然导出的性质（因果句）**：因为**恢复粒度的前提是"中间结果还在"**，所以凡是把中间结果落盘的引擎（Spark、Hive-on-Tez）天然获得细粒度重算能力；而因为**流水线引擎的中间结果只存在于内存中，一旦节点死亡数据就没了**，所以它只能整条重跑——于是**故障恢复粒度本质上不是"容错做得够不够好"，而是"你愿意为落盘付多少代价"的另一个侧面**。这就是为什么"长跑作业用 Spark、短查询用 Trino"不是偏好，而是机制决定的：**作业时长越长，遇到故障的概率越高，细粒度恢复的价值就越大。**

**这条机制还有一个常被忽略的推论**：恢复粒度决定了**抢占式实例能不能用**。使用价格更低、随时可能被回收的计算资源时，细粒度恢复的引擎（族一）只需重算被回收的部分，而整条重跑的引擎会一次损失整条查询的全部进度——**所以"能不能用抢占资源"不是运维策略问题，而是引擎机制问题**，它反过来影响单位算力的实际价格（抢占资源的折扣幅度不写具体数字，可由云厂商的竞价实例定价页核验，通常显著低于按需价【经验】）。

**公开证据**【公开】：Spark 的 lineage 重算在原始论文中被作为核心设计目标陈述（NSDI 2012 "Resilient Distributed Datasets"）；Trino 默认情况下查询失败不重试、需要显式开启 fault-tolerant execution 才能容忍节点失败（[Trino 发布说明, 2022]）；Hadoop 与 Tez 的 task / container 重试语义属机制描述，各自文档的版本线分散、无单一可锚定的年份，故不标【公开】，可由你所用版本的官方文档自行核验。判定方法：在测试集群上主动 kill 一个 worker，观察作业是"重算几分钟"还是"从头开始"——这是最快区分两族的方法。

**失效条件**：当作业足够短（秒级到分钟级）时，整条重跑的成本低于细粒度恢复的架构开销，细粒度容错反而是过度设计——**这也是很多团队在小批量场景里用 Spark 反而更慢的原因之一**。

#### 7.3.3 扩展轴：加机器、加磁盘，还是换台更好的机器

**机制是什么**：每个引擎的扩展方向不同。加机器是否真的能提高吞吐，取决于架构里有没有中心瓶颈。

**它在各候选中的实现差异**：

| 候选 | 扩展方式 | 中心瓶颈 | 扩展到一定规模后的表现 |
| --- | --- | --- | --- |
| Spark | 横向加 executor；**driver 是单点**（集群管理器只做 active/standby 的 HA，不是多主） | driver（调度与规划）、shuffle 服务、元数据 | 加机器仍能提升吞吐，但单个作业的并发度受 driver 与 shuffle 开销限制 |
| Hive | 横向（由底层引擎决定） | Metastore（元数据服务） | 元数据成为瓶颈后需要独立扩容或加缓存 |
| Trino | 横向加 worker | **Coordinator（单点规划）** | 规划阶段单点，查询并发高时先撞 Coordinator |
| DuckDB | **纵向**：换更大的单机 | 单机 CPU / 内存 / 磁盘带宽 | 无横向出路，超过单机能力就必须换引擎 |
| Doris / StarRocks | 横向，存算可分离 | FE（元数据与规划） | 与 Trino 类似 |

**由此必然导出的性质（因果句）**：因为 **Trino 的查询规划发生在 Coordinator 这个单点上**，所以它的横向扩展存在一个与 worker 数无关的上限——**并发查询数增加时，先撞到的是 Coordinator 的 CPU，而不是 worker 的算力**；这个性质意味着"Trino 慢"的排障顺序应当是"先看 Coordinator 负载，再看 worker"。反过来，因为 **DuckDB 完全没有分布式执行**，所以它的扩展轴只有"纵向"一条：**它不是"扩展性差"，而是"根本没有扩展问题"**——它的设计目标是让单机能做的事尽量多，超过单机就该换引擎而不是给它加编排层。

**公开证据**：Trino 官方架构文档把 Coordinator 描述为接收查询、解析、规划并分发的角色，并单独讨论 Coordinator 的资源配置（该章节随版本持续修订，不锚定年份，可由你所用版本的官方文档自行核验）；Spark 的 AQE 文档也在说明其目的是减少 shuffle 分区数、缩小任务规模，从而缓解调度压力（【公开】[Apache Spark 3.2 文档的 AQE 章节, 2021]，与 7.3.1 的默认开启版本一致）。判定方法：压测时观察 Coordinator 的 CPU 与 worker 的 CPU，看哪一个先饱和——这直接决定你应该加哪一种节点。

**失效条件**：当单机规格足够（例如 128–256 核的大机器 + NVMe、内存配到 TB 级【经验】，大内存与存储优化实例的具体档位随硬件代次变化，可按云厂商实例清单核对）时，**只要数据能装进这台机器**（从百 GB 级到 TB 级），DuckDB 这类单机引擎的聚合就可能比分布式方案更快——**因为省掉的是 shuffle 与调度，而不是算了更少的数据**；此时分布式架构的横向扩展能力完全用不上，却要照付运维成本。

#### 7.3.4 元数据与表格式的耦合方式

**机制是什么**：SQL 引擎必须知道"表在哪、有什么字段、什么格式"。这份元数据由谁管、与引擎绑得多紧，决定了你能不能多引擎共存、迁移要付多少代价。

**它在各候选中的实现差异**：

| 候选 | 元数据归属 | 表格式 | 换引擎要动什么 |
| --- | --- | --- | --- |
| Hive | Hive Metastore 为权威 | Hive 表 / 或指向 Iceberg 外表 | 不动元数据，但方言与函数要适配 |
| Spark | Connector 读取 Metastore 或表格式 | Hive / Iceberg / Delta 等 | 不动元数据，SQL 基本兼容 |
| Trino | Connector 松耦合，可同时挂多源 | 由 Connector 决定（Hive / Iceberg / Kafka / 关系库） | 不动元数据，但联邦查询下推能力不同 |
| DuckDB | 无中心元数据，直接读文件或 attach | Parquet / Iceberg / DuckDB 本地文件 | 不动任何服务，改文件路径即可 |
| Doris / StarRocks | 自有元数据 + 外部表 | 自建存储 / 外表 | 需要建外部表映射 |

**由此必然导出的性质（因果句）**：因为 **Hive 把元数据放在独立于计算引擎的 Metastore 里、把计算交给可替换的引擎**，所以它成了存量迁移中"改动最小"的入口——**你的表定义、分区、权限都不用动，只换执行引擎**；但同一机制也意味着**Hive 自身的"性能"是个伪命题**：它由背后的 MR / Tez / Spark 决定，团队按 Hive 的心智调优往往是在调一个自己并不掌握的引擎。反过来，因为 **DuckDB 根本没有元数据服务、直接把文件当表**，所以它的接入成本接近于零（省掉一整套 Metastore 与权限体系），但也因此在"多用户共享、统一权限、血缘可追"这些维度上先天薄——**它把服务端要解决的问题留给了文件系统与外围工具。**

**表格式是这一层里真正的主角**（下述机制可由各项目的表规范文档自行核验，各项目规范按规范版本号而非年份迭代，故此处不锚定年份、不标【公开】）：Iceberg / Delta / Hudi 这类表格式把"表定义"从 Metastore 抽到数据文件旁边的元数据文件里，于是**同一份数据可以被 Spark 写、被 Trino 读、被 DuckDB 直读**，多引擎共存才在工程上成立。判定方法：查看目标引擎的版本矩阵——它支持的表格版本（如某 Iceberg 规范版本）与你的写入引擎是否一致；**多引擎共存的故障，八成出在这个矩阵上，而不是 SQL 方言上。**

**公开证据**（该兼容接口的覆盖面跨多个项目与版本，无单一年份可锚定，故按"可由官方文档自行验证"处理）：Hive Metastore 被 Spark、Trino、Iceberg 等广泛实现为兼容接口，这是"元数据与计算解耦"最直接的证据。判定方法：把你实际使用的 Spark 与 Trino 的 catalog 指向同一个 Metastore 地址，看两边能否列出同一批表——能列出即是该兼容层在生效。

**失效条件**：当组织只需要一个引擎、且不打算多引擎共存时，松耦合带来的复杂度是净负担——**解耦的价值只在"会有第二个消费方"时兑现**；单引擎场景下，绑得越紧往往越省心。

### 7.4 成本结构对比（不是价格表，是成本函数）

离线计算的成本函数与向量检索不同：它**几乎完全由"算力 × 小时数"驱动**，存储是次要项。

```
月成本 ≈ 算力(vCPU 数 × 单价) × 月运行小时数
        + 中间结果与 shuffle 落盘
        + 元数据 / 调度等常驻服务
        + 人力（调优与排障）
```

**关键区分项是"月运行小时数"**，它由交付形态决定，而不是由引擎决定：

| 形态 | 运行小时数 | 主导成本项 | 适用前提 |
| --- | --- | --- | --- |
| 按需临时集群（Spark 常见） | 等于**作业时长**（例如每天 2 小时） | 算力 × 小时 | 作业有明确起止，能接受分钟级启动 |
| 常驻集群（Trino 常见） | 24 × 30 = **720 小时** | 算力 × 小时（大部分是空转） | 要求随时可查、不能接受冷启动 |
| 常驻调度 + 按需算力（YARN / K8s 混合） | 调度常驻、算力按需 | 调度小头 + 算力大头 | 多团队共享、需要排队与配额 |
| 单机（DuckDB） | 等于**使用时长**，且规格便宜 | 单机小时成本 | 单机能装下、不需要并发隔离 |

**【推算】同一份算力的两种交付形态**（单价为【公开】：通用型实例约 **$0.045/vCPU-小时** on-demand，可由 [AWS EC2 定价页, 2024] 核验；总价为【推算】）：

- **按需**：100 vCPU 的临时集群，每天跑 2 小时 → 100 × $0.045 × 2 × 30 ≈ **$270/月**【推算】。
- **常驻**：同样 100 vCPU 常驻 → 100 × $0.045 × 720 ≈ **$3,240/月**【推算】。
- 两者的小时数相差 12 倍，账单同比例——**这个 12 倍与选哪个引擎无关，只与"要不要常驻"有关**。

把同一口径拉到年度看，量级差异更清楚（仍按同一单价推算，仅换算时长）：

| 交付形态 | 月有效运行小时 | 年度账单量级（100 vCPU）【推算】 |
| --- | --- | --- |
| 按需 · 每天 2 小时 | 约 60 | 约 $3.2k/年 |
| 按需 · 每天 8 小时 | 约 240 | 约 $13k/年 |
| 常驻 | 720 | 约 $39k/年 |

（算术过程：vCPU 数 × $0.045 × 月小时数 × 12；实际会因实例类型、预留折扣、竞价实例而显著低于此值【经验】。）

所以正确的问法不是"Spark 和 Trino 哪个便宜"，而是"**我的查询密度是否足以支撑 12 倍的常驻溢价**"。判断标准是集群的**日有效利用率**：若常驻集群每天实际被查询的时间只有 2–6 小时（即利用率 8%–25%），那么大部分账单买的是"随时可用"这个属性；把它与"按需跑批 + 结果落表供查询"的方案对比，后者的成本量级明显更低，代价是查询的是已有结果而不是任意 SQL。

**存储项在小规模下可忽略，在大规模下不可忽略**：shuffle 落盘与中间结果通常写本地盘（可由实例 NVMe 承载），但当作业规模超过本地盘容量、必须把 shuffle 放对象存储时，成本要从"实例小时费"里单独算一笔，且**它随 shuffle 放大倍数增长，而不是随输入大小增长**——一个输入 1 TB、放大 5 倍的多轮 JOIN 作业，中间产物是 5 TB 级，而不是 1 TB 级。

**人力项常被算成零，其实是最不稳定的一项**：分布式引擎的排障（数据倾斜、shuffle 失败、OOM、小文件）需要持续投入，且投入量随作业数与引擎种类增长。**每新增一种引擎，就新增一条排障路径**——这也是 7.7 里"多引擎并存"要付的隐性成本。

**把成本写成函数之后，选型问题就变成了三个可算的数**：（1）每日有效查询/作业小时数（决定交付形态）；（2）shuffle 放大倍数（决定存储与容量规划）；（3）需要支持的引擎数（决定人力）。这三项都能在选型前实测或估出来，**凡是估不出来的，说明你还没到需要做这个决策的信息量。**

### 7.5 决策树（每个分支都要有阈值依据）

```
[首要问题：这个负载的形态是什么？]
   │
   ├── 固定调度的重 ETL，多轮宽依赖（JOIN / GROUP BY）────► Spark
   │        └── 存量表在 Hive Metastore 里？ → Spark 直接读，不动元数据
   │        └── 需要跨源（库 / 消息 / 对象存储）？ → Spark + Connector
   │
   ├── 分析师即席查询、要多源联邦、延迟敏感 ──────► Trino
   │        └── [日有效利用率 < 30%？] → 考虑"按需批处理 + 结果表"替代常驻集群
   │        └── 已绑定 Presto？ → 同族，按生态与经验选，不必迁移
   │
   ├── 单机可容纳的分析 / AI 数据准备 ───────────► DuckDB
   │        └── [单次扫描量 > 内存约 5 倍（64 GB 内存下约 320 GB）？] → 换族一或族三
   │
   └── 存量 Hive 资产为主，暂不迁移 ─────────────► 保留 Metastore，逐个换执行引擎
            └── [有明确的"必须换"的作业？] → 先迁高频、大额、出问题的作业
```

**阈值依据**（与树上的 7 个判断节点一一对应，按树的出现顺序）：

- **"多轮宽依赖"是分族的硬条件，不是规模条件**：只要作业含多轮 JOIN/GROUP BY，中间结果就必然超过内存，故障恢复粒度就会变成决定性问题——这类作业必须落在族一（Spark），与数据是 1 TB 还是 1 PB 无关。反过来，单轮扫描聚合的作业在任何族都能跑，此时才轮到规模与延迟说话。
- **"存量表在 Hive Metastore 里？"**：这不是数值阈值，而是一个**接入成本判定门**。因为 Spark 与 Trino 的 catalog 都实现了 Metastore 兼容接口，表在 Metastore 里时"迁移"只等于"换执行引擎"，元数据、分区、权限都不动（7.3.4）；反过来，若表只是对象存储上的一堆路径，接入前得先补一层表格式与注册流程，工作量从"零"变成周级到月级【经验】。判定方法：列一遍你要用的表，看它们有 Metastore 条目，还是只有一个 URI。
- **"需要跨源（库 / 消息 / 对象存储）？"**：这一条判的不是能力而是**架构契合度**——Spark 的强项是"读一批数据、算很久"，跨源读取要么先抽数落地（多一次落盘与一轮调度），要么依赖各源 Connector 的谓词/投影下推；而族三（Trino）的 Connector 模型本来就是为"原地读多源、只取所需"设计的。判定方法：把跨源查询的过滤条件下推给引擎，看源端实际返回了多少行——下推不到的跨源查询会把整表拉进计算集群。**树上这一支给的是"Spark + Connector"，但这条判定门的真实含义是：如果跨源是常态而不是例外，它会把你推向族三。**
- **"日有效利用率 < 30%？"**：常驻集群的账单按 720 小时计，而按需求只要作业时长。设常驻集群的日有效服务时间为 t 小时，则"常驻溢价"= 24 / t：

  | 日有效服务时间 t | 常驻溢价（相对按需） | 结论 |
  | --- | --- | --- |
  | 2 小时（约 8%） | 约 12 倍 | 常驻几乎纯粹为"随时可用"付费 |
  | 7.2 小时（30%） | 约 3.3 倍 | 临界：取决于"随时可用"值不值这个价 |
  | 16 小时（约 67%） | 约 1.5 倍 | 常驻合理，按需反而会被启动开销拖累 |

  **这张表就是"30% 阈值"的全部推导**，读者按自己的 t 重算即可；表内比值为精确算术（24 / t），不是估算。
- **"已绑定 Presto？"**：Trino 与 PrestoDB 同源分叉，能力上基本等价（见 7.2 的同族表），所以这里的阈值不是性能而是**迁移成本**：只有当存在一个可指名的缺口（某个必需的连接器只有一侧有、版本线不再修安全问题、本地招不到维护者）时才值得迁移，否则迁移本身是净成本。判定方法：把它当"替换一个还能用的东西"来立项——若立项材料里写不出那个具体缺口，答案就是不迁。
- **单次扫描量超过内存约 5 倍（64 GB 内存下约 320 GB）**【经验】：DuckDB 的 out-of-core（溢出到磁盘）在扫描量约为内存的 1.5–5 倍（64 GB 下约 96–320 GB）时仍能维持可交互的体验，超出后磁盘往返成为主导——**这是一个区间而非精确值**，取决于磁盘带宽与查询的选择性。**树上取的是区间上界而不是下界**：1.5 倍（约 96 GB）是"开始溢出、开始变慢"的拐点，5 倍（约 320 GB）才是"机制优势消失"的点；判断节点应落在优势消失点上，否则会把仍能胜任的单机负载过早推给分布式，多付 7.4 里那份常驻与运维账单。区间上下界之间是**渐变段**，此时看的不是绝对值而是**趋势**：把同一查询在 1×、2×、5× 内存的数据量上各跑一次，若耗时随数据量呈超线性上升（而不是近似线性），说明磁盘往返已经主导，该换族——**这个判定不依赖任何具体硬件数字**。DuckDB 官方长期公布 TPC-H 单机结果，可用 SF100 / SF300 的实际耗时按自己的硬件比例外推（[DuckDB 官方 benchmark 页面]）。
- **"有明确的'必须换'的作业？"**：存量迁移的阈值不是规模而是**痛点密度**——高频访问、金额大、事故多、维护成本高的作业优先；把这三类挑出来的投入产出比，通常远高于按表数量平均推进【经验】。**先迁哪几个是"有没有痛点"的判定门，不是"数据多大"的阈值。**

**上树之前先做的三项验证**：

1. **作业的 shuffle 放大倍数**：跑一次全量，记录 shuffle 落盘量与输入量之比。这个比值是选族的硬指标（对应 7.3.1）。
2. **失败重跑的实际代价**：故意 kill 一个 worker，测作业恢复耗时。它决定了长作业是否必须用族一（对应 7.3.2）。
3. **一套真实查询的方言清单**：把生产里最复杂的 20 条 SQL 拿出来，逐条试跑。引擎之间的函数与语法差异会在这里暴露，而不是在选型会议上。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| T+1 全量重算，10 万级任务/日【公开】（量级与来源见 [§6 案例 6.1](08-offline-compute-section-6-sec6.md)：字节 10 万+ 任务/日，[字节技术博客, 2019–2024]） | Spark + 表格式（Iceberg / Hudi） | Hive on Tez（存量兼容） | 单机引擎装不下；流水线引擎失败即整条重跑 |
| 分析师偶发查询，多源联邦 | Trino | Doris / StarRocks（单源高频） | Spark 的启动延迟对交互查询不可接受 |
| 单机百 GB 到数百 GB 级数据探索 / AI 数据准备 | DuckDB | 单机 Spark（已熟悉 Spark 的团队） | 分布式方案在这个量级只剩调度开销 |
| 传统企业存量数仓迁移 | 保留 Hive Metastore，新增 Spark 执行 | Trino 直读 Hive 表 | 一次性替换元数据层的迁移风险远高于收益 |
| 报表类高频聚合查询 | Doris / StarRocks（预聚合） | Trino + 物化视图 | 每次现算的成本随查询频次线性上升 |
| 混合：批量出表 + 交互查询 | Spark 出表 + Trino 查表 | DuckDB 处理单机小批量 | 用同一引擎包打天下会在某一侧付出代价 |

**常见组合（各件职责边界与运维代价）**：

1. **Spark + Iceberg + Trino**（对应 [§6](08-offline-compute-section-6-sec6.md) 的湖仓形态）：Spark 负责写入与重加工，Iceberg 负责表格式与快照，Trino 负责查询。职责边界是 **Spark 是唯一写入方**——如果多个引擎同时写同一张表，必须约定提交协议与冲突处理，否则快照会互相覆盖。运维代价：三套组件的版本兼容（表格式与两个引擎的版本矩阵）是长期负担。
2. **Spark + DuckDB**：Spark 做大规模 ETL，DuckDB 在本地/单机上做结果集的交互分析。职责边界是 **DuckDB 只读、不承担共享写入**。运维代价很低（DuckDB 无服务），但要注意"结果集"的体量上限——一旦分析师真去 `read_parquet` 整个湖，单机会被打爆。
3. **Hive Metastore 保持 + 引擎逐个替换**：元数据层不动，把执行引擎从 MR/Tez 换成 Spark 或 Trino。职责边界是 **Hive 只负责"表在哪"，不负责"算得多快"**。运维代价：短期内三种引擎并存，排障路径变多，但迁移风险最低。
4. **常驻 Trino 服务 BI + 按需 Spark 跑批**：Trino 保交互延迟，Spark 保批量吞吐。职责边界是 **Trino 只查、Spark 只算**。运维代价：两套资源池，且要防止有人把重 ETL 丢到 Trino 上（见 7.7 反模式）。
5. **按需算力 + 结果表分层**：夜间的重加工全部按需起集群，产出若干张按查询模式预先聚合好的结果表；白天的分析查询只读这些结果表（可由 Trino 或 MPP OLAP 提供）。职责边界是 **用"预计算"换掉"常驻"**。运维代价：需要维护结果表的刷新链路与口径，且**任意 SQL 的灵活性被削弱**——这是它唯一的真实代价。

> 组合的第一原则是**让"写"集中、"读"分散**：写入路径越单一，表格式与提交协议越可控；读取方可以有很多个，因为它们只需要遵守同一份元数据契约。
>
> 组合的第二原则是**先问"这个负载本来会不会被问到"**：如果一类查询本来就是固定几种形态（报表、看板），那么"预先算好"比"常驻一个能算任意 SQL 的集群"便宜得多——**灵活性的价格，往往就是那份常驻账单。**

### 7.7 选错的代价与迁移成本

**反模式：用交互式引擎跑重 ETL** —— 症状：为了"统一技术栈"把多轮 JOIN 的批量作业放到 Trino 上，初期因为延迟低而效果很好；随数据量增长，作业开始因为内存不足或 worker 故障而失败，且**失败即整条重跑**，重跑又更容易失败。后果：夜间批处理窗口被重试吃掉，事故频率上升。正确的做法：按 7.3.1 的分界——**含多轮宽依赖的作业留给屏障型引擎**，交互引擎只接单轮扫描与联邦查询。

**反模式：把 Hive 当成"默认引擎"而不做引擎选择** —— 症状：团队所有作业都写成 HiveQL，跑在 Hive 上，但没人说得清底层是 MR 还是 Tez；性能问题时按 "Hive 调优" 找资料，实际要调的是底层引擎的参数。后果：调优方向随机、效果不可复现，且无法解释"为什么同样的 SQL 昨天 2 小时、今天 6 小时"。正确的做法：**把"引擎"与"SQL 方言"解耦**——Hive 只保留元数据与方言兼容角色，执行引擎的选择显式化（Spark 或 Trino），并把它写进作业模板。

**反模式：给单机引擎套一层分布式编排** —— 症状：DuckDB 很好用，于是用脚本把任务切分到多台机器上，自己拼一个"分布式 DuckDB"。后果：**你得到了分布式的全部复杂度（切分、调度、合并、容错），却没有得到分布式的收益**（单机引擎没有为跨节点一致性设计），并且丢掉了 DuckDB 最大的优势——没有服务、没有集群。正确的做法：单机装不下就换族一/族三，不要自己造中间层。

**反模式：把所有作业迁到一个引擎以求"统一"** —— 症状：把批量 ETL、交互查询、报表聚合都收敛到一个引擎上。后果：三类负载对中间结果落点、并发模型、延迟的要求互相冲突，最终按最严的一类配置资源，其余两类承担不必要的成本；且一类负载的尖峰会影响另外两类（资源争抢）。正确的做法：**按"作业形态"分池，而不按"技术栈统一"分**——同族内合并，跨族分开。

**反模式：为了让报表"更快"而全量常驻一个集群** —— 症状：看板偶尔被问到慢查询，于是把批处理集群改成 24 小时常驻，账单按 12 倍上去了，而慢查询并没有被解决。后果：钱花了、指标没动，且团队会继续按"资源不够"的思路加机器。正确的做法：先按 7.4 算一遍有效利用率，再区分"慢"是因为**算力不足**还是因为**每查一次都从头算**——后者的解法是预聚合或结果表，加机器只会放大成本。

| 迁移方向 | SQL / 语义改写 | 数据与文件布局 | 元数据与权限 | 团队再学习 | 量级（【经验】） |
| --- | --- | --- | --- | --- | --- |
| Hive → Spark（执行引擎替换） | 方言与函数需逐条核对 | 一般不动（同 Metastore） | 一般不动 | 中（要懂 DAG、shuffle、倾斜） | 月级 |
| Spark 作业 → Trino | 方言差异 + 去掉依赖 Spark 特有算子的写法 | 不动 | 一般不动 | 中（要懂 Connector 与下推） | 月级 |
| 引擎 → DuckDB | 大幅简化（单机 SQL 兼容性好） | 需能直接读文件（Parquet / Iceberg） | **要另配权限与共享方案** | 低 | 周级 |
| 自建集群 → 托管服务 | 基本不动 | 不动 | 需迁移凭证与策略体系 | 低到中 | 周级到月级 |
| 本地盘 shuffle → 对象存储 shuffle | 不动 | 需改配置与容量规划 | 需给计算角色授权 | 低 | 周级 |

> 表里"元数据与权限"一列在 Hive/Spark/Trino 之间几乎是"不动"，因为它们共享 Metastore 这一层契约；**这正是 Hive 生态在存量企业里难以被替换的真正原因——替换它要动的不是引擎，是整个元数据与授权体系。**

### 7.8 小结

离线计算的对比里有一个反直觉的结论：**候选之间的能力差异，远小于交付形态之间的成本差异**。7.4 到 7.7 的所有分析最终指向同一件事：先把作业按"形态"分族（有没有多轮宽依赖），再按"要不要常驻"决定账单的量级，最后才在同族内部按生态与经验挑一个——顺序反了，就会陷入无休止的引擎对比。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 多轮 JOIN 的夜间批处理，PB 级 | Spark + 表格式 | shuffle 落盘 + 屏障带来的分区级重算是长作业能跑完的前提 |
| 分析师即席查询、多源联邦、延迟敏感 | Trino（同族 Presto 按生态选） | 无屏障的内存流水线交换给出低延迟，代价是故障即重跑 |
| 单机百 GB 到数百 GB 级、要快速拿到结果 | DuckDB | 没有分布式就没有 shuffle 与调度开销，单机更快更省 |
| 存量 Hive 资产庞大，迁移预算有限 | 保 Metastore，逐个替换执行引擎 | 元数据契约不动，迁移风险与工作量都最小 |
| 批量出表 + 交互查询都要 | Spark 出表 + Trino 查表 | 写入集中、读取分散，各自落在机制最契合的族 |
| 查询量稀疏（日有效利用率低于三成） | 按需批处理 + 结果表，而不是常驻集群 | 常驻的账单按 720 小时算，稀疏查询买的是可用性不是算力 |
| 已统一在一种引擎上，但某类作业长期不稳 | 按作业形态拆池 | 一类负载的失败模式会拖累所有负载 |
| 需要把任意 SQL 交给业务自助查询 | 常驻查询引擎 + 资源隔离与配额 | 自助查询的价值在"任意"，预计算方案满足不了它 |

> 本节小结：本章候选之间**唯一真正起决定作用的差异是"中间结果落在哪里、失败后从哪里继续"**——落盘 + 屏障（Spark）换来局部重算与 PB 级稳定，不落盘（Trino、DuckDB）换来低延迟但代价是整条重跑或单机上限。所有其他差异（方言、连接器、生态）都是在确定了这一条之后才需要权衡的第二层问题；先问"我的作业失败了要重跑多少"，再谈引擎的名字。
>
> 💡 **思考锚点**：拿你一条最重、最容易失败的作业，回答小结那句话——它失败时要重跑多少：整个查询，还是单个分区？若答案是「整条重跑」而你又在 PB 级上跑，按 7.3.1 / 7.3.2 你就是把含多轮宽依赖的负载放进了不落盘的引擎，该换的是族还是只是调参？
