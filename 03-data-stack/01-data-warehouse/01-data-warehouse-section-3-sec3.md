## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把数仓选型讲成了「按场景挑一个」：传统 BI 选分层建模，自助分析选宽表，合规场景选 Data Vault。这个讲法漏掉了真正的决策变量——**同一个场景在不同约束下，正确模式可以完全不同**。同样叫「实时数仓」，在口径已经稳定的业务里，它的收益是把产出从 T+1 提前到分钟级；在口径每周都在改的业务里，它只是把错误提前几小时送到决策层。

数仓模式的选择被三类主轴约束夹住：**写入侧**（数据是批量追加、微批还是行级更新）、**读取侧**（是固定看板聚合、还是不可预测的即席查询）、**时间侧**（要保留的是当前状态，还是变化过程本身）。这三条主轴任一条不同，同一份数据该用的物理形态就不同——而模式的名字（分层、宽表、Vault、Cube）只描述了形态，不描述你被哪条主轴夹住。下表共六行：前三行就是这三条主轴（数据形态 / 写入模式、访问模式、变更频率与历史要求），后三行是另外三条约束——一致性要求、规模与成本、团队技能与运维能力。六行要一起过：主轴决定候选形态，另外三条决定这些候选形态在你这里是否成立。

所以顺序是先立约束再讲模式。**模式不是被选的，是被约束推着走的**。下面这张表的作用是：每次选型前逐行问一遍「这一条我现在是什么状态」，答案会直接排掉一半候选。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式（追加 / 微批 / 行级更新） | 分层边界与表格式选型 | 「实时就是先进的」——写入模式决定可行的分层，而不是时髦度 |
| 访问模式（点查 / 扫描 / 多表 JOIN / 聚合） | 是否存冗余、是否预计算 | 「列存快，所以随便 JOIN」——列存加速的是扫描，JOIN 的代价在网络与重分区 |
| 变更频率与历史要求 | 维度建模方式（SCD 类型）与是否上 Data Vault | 「维度口径一致就行」——要求保留历史时，覆盖式更新直接毁掉时间分析 |
| 一致性要求（T+1 / 分钟级 / 秒级） | 离线还是实时分层 | 「T+1 不够用」——多数分析的决策周期是天，实时化换来的是双倍链路 |
| 规模与成本（TB / PB / 查询并发） | 分层粒度与预计算程度 | 「多建几层更规范」——每层都是一次全量重写，层数直接乘加工成本 |
| 团队技能与运维能力 | 是否采用 Data Vault / 语义层这类重方法论 | 「方法论越先进越好」——重方法论需要一个专职团队长期承接 |

### 3.2 模式逐个拆解（核心节）

七个模式并不是同一维度的候选：分层建模、实时分层、湖仓一体回答的是**数据怎么组织**；OBT、Cube 回答的是**查询路径怎么缩短**；语义层、Data Vault 回答的是**定义与变化怎么被治理**。把它们放在一张备选清单里选，本身就是误用——它们之间更多是叠加关系。

| 模式 | 入场条件 | 条件缺失时的后果 |
| --- | --- | --- |
| 分层建模（ODS/DWD/DWS/ADS） | 每层的粒度能用一句话说清 | 层退化成目录，变更找不到该落在哪一层 |
| OBT 宽表 | 摊平进来的维度变更频率低 | 一次维度改名触发全量历史回刷 |
| 实时数仓分层 | 口径可重放（源事件可回放 + 状态有 checkpoint） | 口径修正只能打补丁，历史不可复算 |
| 指标语义层 | 所有消费都经由这一层 | 出现逃逸 SQL，口径重新散开且更难发现 |
| 湖仓一体 | 有 compaction 与快照过期机制 | 小文件与快照堆积，读取被元数据拖垮 |
| Data Vault | 有自动化装载工具 + 专职建模角色 | Vault 只写不读，退化为归档层 |
| Cube / 预计算 | 参与物化的维度基数可控 | 组合数爆炸，物化在物理上不可行 |

下面逐个拆解，每个模式都按同一套结构给出：约束 → 结构 → 机制 → 代价 → 失效点 → 真实使用。

#### 3.2.1 分层建模（ODS / DWD / DWS / ADS）

- **被什么约束逼出来**：多源异构 + 口径不一致 + 查询负载类型不同——回溯排查要原始数据、明细分析要最细粒度、汇总报表要预聚合、应用要宽表，四类负载的物理形态不可能共用一张表。
- **结构**：

```sql
-- 每层的粒度与职责写在表定义里，而不是写在文档里
CREATE TABLE ods_order (              -- 贴源：保留原始字段与原始类型，不做清洗
  raw_json  STRING,
  dt        STRING,
  etl_time  TIMESTAMP
) PARTITIONED BY (dt);

CREATE TABLE dwd_order_detail (       -- 明细：一行 = 一个订单明细，最细粒度
  order_id     STRING,
  user_id      STRING,                -- 已完成 OneID 归一
  sku_id       STRING,
  amount       DECIMAL(18,2),
  order_status STRING,                -- 枚举值已标准化
  dt           STRING
) PARTITIONED BY (dt);

CREATE TABLE dws_user_trade_1d (      -- 汇总：公共粒度是「用户 × 天」
  user_id      STRING,
  trade_amt_1d DECIMAL(18,2),
  order_cnt_1d BIGINT,
  dt           STRING
) PARTITIONED BY (dt);

CREATE TABLE ads_user_trade_rpt (     -- 应用：面向具体报表，允许冗余
  user_id       STRING,
  user_level    STRING,               -- 冗余自维度表，避免报表期 JOIN
  trade_amt_30d DECIMAL(18,2),
  dt            STRING
) PARTITIONED BY (dt);
```

- **为什么这样设计有效**：因为每层只对上一层做一类变换（贴源 → 清洗归一 → 聚合 → 面向应用），所以任何一层出问题都能定位到「哪一类变换」失守，而不必重跑全链路排查。
- **代价**：每一层都是一次物化，存储与计算按层数放大；其中 ODS 全量保留是最贵的一层。更关键的是**可重算成本**：DWD→DWS 的汇总口径一旦变更，要么重刷历史分区，要么让历史与当期使用两套口径。按时产出率也随层数相乘——单层按时率 99% 时，4 层链路的按时率约 96%（【推算：0.99⁴ ≈ 0.961，假设各层独立】），层数不是免费的。
- **失效点**：当「为应付特例而不断加层」时（例如为某业务加一层 DWM 存中间结果），定位清晰的优点会反转成**链路冗长**，因为每加一层就多一次读写与一个失败点，而按时产出率是各层相乘——层数越多，整条链路当天能不能按时出数的概率越低，故障排查还要多翻一层。
- **真实使用**：维度建模与总线架构（一致性维度跨域共享）来自 Kimball 的方法论（【公开：Ralph Kimball《The Data Warehouse Toolkit》初版, 1996】）；企业级范式建模与自顶向下的 CIF 来自 Inmon（【公开：Bill Inmon 于 1990 年提出数据仓库的四大特征——面向主题 / 集成 / 时变 / 非易失；其系统化著作《Building the Data Warehouse》初版于 1992 年】）。国内互联网数仓普遍使用的 ODS/DWD/DWS/ADS 命名与这两条路线同源，可按这四个层名检索公开技术材料自行核验（【经验】）。

#### 3.2.2 One Big Table（OBT）宽表

- **被什么约束逼出来**：高频且不可预测的自助分析——分析人员的查询模式无法事先枚举，任何预聚合都可能答不上临时问题，而 JOIN 是这类即席查询的主要成本。
- **结构**：

```sql
-- OBT：把维度描述列直接摊平进事实表，用存储换掉运行时 JOIN
CREATE TABLE obt_order_wide (
  order_id     STRING,
  user_id      STRING,
  user_level   STRING,      -- 冗余自 dim_user
  user_city    STRING,
  sku_id       STRING,
  sku_category STRING,      -- 冗余自 dim_sku
  shop_id      STRING,
  shop_type    STRING,      -- 冗余自 dim_shop
  amount       DECIMAL(18,2),
  pay_time     TIMESTAMP,
  dt           STRING
) PARTITIONED BY (dt);      -- 真实系统中的列数常在数百列量级（【经验】）
```

- **为什么这样设计有效**：因为维度值在写入时就已解析成列值，查询期不再需要 JOIN 去补维度键——JOIN 的代价从「每次查询」变成「每次写入」，而写入次数远小于查询次数。
- **代价**：维度变更要回刷历史，一次维度改名就是重写全部历史分区；列数推高扫描与存储成本；写入端每个字段都要有明确填充逻辑，维表新增属性等于一次全表 schema 变更，且必须保证新旧分区的口径一致。
- **失效点**：当维度属性的变更频率高于事实表的刷新频率时（例如用户等级每天变、宽表每周重刷），「查询期无 JOIN」的优点会反转成**历史数据永久错误**，因为摊平动作发生在写入时刻，之后维度怎么变，已经落地的历史行都不会自己更正——而且这类错误不报错，只会在某个口径对比时突然暴露。
- **真实使用**：多数团队对 OBT 的约束是「宽度有限、只服务单域自助分析」，并把口径变更频繁的维度排除在摊平范围之外（【经验】）。

#### 3.2.3 实时数仓分层（ODS / DWD / DWS / ADS）

- **被什么约束逼出来**：业务要求产出延迟从 T+1 压到分钟级，同时不允许为此放弃分层带来的口径一致性——否则得到的不是实时数仓，而是一堆实时烟囱。
- **结构**：

```text
实时数仓分层：同一套分层语义，不同的物化介质
  ODS   消息队列（CDC / 日志）    topic 按源库表切分，保留原始事件
          │  流式清洗 / 去重 / 归一（有状态算子）
  DWD   流式明细（分钟级落表）     Flink → 表格式（Iceberg / Hudi / Paimon）
          │  按公共粒度做窗口聚合
  DWS   实时汇总（分钟级物化）     窗口结果 / 流式物化视图
          │  面向应用重组
  ADS   实时 OLAP 服务层          ClickHouse / Doris / StarRocks
  ────────────────────────────────────────────────
  与离线分层的差别不在「分层」，而在「一致性靠什么保证」：
     离线：靠 T+1 全量重算（补算容易，历史可复算）
     实时：靠状态与 checkpoint（补算要重放，口径必须可重放才算数）
```

- **为什么这样设计有效**：因为源事件留在队列里、算子状态有 checkpoint，所以「口径修正」可以靠重放与回刷完成，而不是给已经发布的结果打补丁——这让实时链路的输出是可解释、可复算的。
- **代价**：链路从「一份数据一次加工」变成「离线 + 实时双链路」，存储、计算、运维与口径对齐成本都上升（【经验：通常显著高于单链路，具体倍数取决于口径对齐所需的回刷范围】）；延迟窗口越短，乱序、重复与重放的处理成本越高。
- **失效点**：当口径频繁调整时，分钟级的低延迟会反转成**错得也快**，因为实时链路没有 T+1 的缓冲窗口，口径错误会在几分钟内落到报表并影响决策，而离线链路至少有一晚的校验机会。也就是说，链路越快，对口径治理成熟度的要求越高，而不是越低。
- **真实使用**：多数团队采用「实时看趋势、离线定口径」的双轨：核心指标以离线口径为准，实时结果用于监控与快速响应（【经验】）。湖仓表格式（Iceberg / Hudi / Paimon）是让实时链路可重放的常见选择，可按各项目官方文档核验其事务与快照能力。

#### 3.2.4 指标语义层（Metric Layer）

- **被什么约束逼出来**：同一指标在多个报表与多个团队里被重复定义，口径漂移的根因是「指标定义写在 SQL 里、散落在各处」，而 SQL 不是可治理的资产形态。
- **结构**：

```yaml
# 指标语义层：把指标定义从 SQL 里抽出来，成为可治理的独立资产
metric: trade_gmv
owner: trade-analytics
definition: 已支付订单金额之和（退款前）
source: dwd_order_detail
grain: [1d, 1h]
filter: order_status = 'PAID'
expression: SUM(amount)
dimensions: [user_level, sku_category, shop_type]
service_level:
  freshness: "T+1 06:00"
  availability: "99.9%"
# 下游不写 SQL，只声明「指标 + 维度 + 时间范围」
```

- **为什么这样设计有效**：因为口径只有一处定义，所以「两个报表数不一致」这类问题从「对数据」变成「对定义」，而定义是可 diff、可评审、可追责的文本。
- **代价**：查询要经过「语义层翻译 → SQL 生成 → 引擎执行」，多一次解析与一次服务调用；关联路径、权限过滤、默认时间口径都要在语义层维护，复杂查询的表达能力还受其 DSL 限制——它用表达力换可治理性。
- **失效点**：当业务需要语义层表达不了的计算时（窗口函数、跨指标条件、非标准时间对齐），「一次定义多处复用」会反转成**逃逸 SQL**，因为治理的价值完全依赖「所有消费都走这一层」；一旦出现绕过路径，口径重新散开且更难发现——逃逸者往往还沿用语义层的指标名，看起来仍然正确。
- **真实使用**：MetricFlow 是其中一个开源实现（【公开：dbt Labs 官方文档『About the dbt Semantic Layer』与『MetricFlow』，docs.getdbt.com；MetricFlow 由 Transform 开源、其后被 dbt Labs 收购并整合进 dbt Semantic Layer，时间线以 dbt 官方公告为准】）。该话题里常被并列提及的 `Daft` 定位是面向多模态数据的处理引擎，并非指标语义层产品，选型时建议按其官方文档当前版本核验定位；各云厂商也有各自的指标平台产品（以云厂商官方文档当前版本为准）。

#### 3.2.5 湖仓一体（Lakehouse）

- **被什么约束逼出来**：数据湖有开放性（对象存储 + 任意引擎）却没有事务与 schema 治理；数仓有治理却存储封闭、成本高——而同一份数据既要被 BI 消费、又要被 AI 训练消费。
- **结构**：

```text
湖仓一体：把 ACID 与 schema 治理下沉到「表格式」这一层
  计算引擎（可替换）：Spark / Flink / Trino / StarRocks / Doris
        │  只认表格式的开放 API
  ────────────────────────────────────────────────
  表格式层（治理都在这里）：Iceberg / Hudi / Paimon
        · 快照与事务：并发读写不互相破坏
        · Schema 演进：加列 / 改列名不必重写历史文件
        · 时间旅行：按快照读历史版本
        · 元数据与分区统计：支撑文件级剪枝
        │
  存储层（开放且廉价）：S3 / OSS / HDFS
  ────────────────────────────────────────────────
  与「湖 + 独立数仓」的差别：
     不是把数仓搬进湖，而是把数仓的治理语义做成了湖上的一个可替换组件
```

- **为什么这样设计有效**：因为治理语义（事务、schema、快照）位于引擎之下的表格式层，所以同一份文件可以被多个引擎并发读写而互不破坏，也不需要把数据复制进另一套存储。
- **代价**：每次读写都要过一层表格式元数据操作（提交冲突、快照清单、清单文件），因此必须配套 compaction 与快照过期作业；元数据服务与清单文件本身成为新的可用性依赖，读取性能对小文件数量敏感。
- **失效点**：当写入频率高、每次落盘文件很小时，「开放 + 治理」会反转成**读放大与元数据压力**，因为小文件数与快照数随提交次数增长，读取端的文件打开次数与元数据扫描随之上升——写入侧省下的成本被转移到读取侧和后台维护侧。
- **真实使用**：该形态由 Databricks 系统化提出（【公开：Databricks《Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics》, CIDR 2021】）；Netflix 把 Iceberg 用于 EB 级数仓的可规划与可回滚（见本章 §6 的 Netflix 案例）。三大表格式的能力边界可按各项目官方文档核验。

#### 3.2.6 Data Vault 建模

- **被什么约束逼出来**：源系统多且变化频繁 + 审计可追溯——业务规则会变，但「某年某月源系统里这条记录是什么样」必须可还原，所以清洗逻辑不能与原始记录压成一件事。
- **结构**：

```sql
-- Data Vault：Hub 存业务键，Link 存关系，Satellite 存时间切片属性
CREATE TABLE hub_customer (            -- 只存业务键与装载信息
  customer_hk STRING,                  -- 业务键的哈希键
  customer_bk STRING,                  -- 源系统业务键
  load_ts     TIMESTAMP,
  record_src  STRING
);

CREATE TABLE link_order_customer (     -- 只存「哪些键之间有关系」
  link_hk     STRING,
  order_hk    STRING,
  customer_hk STRING,
  load_ts     TIMESTAMP,
  record_src  STRING
);

CREATE TABLE sat_customer_detail (     -- 只存属性 + 生效区间（建议按源系统分别建）
  customer_hk STRING,
  load_ts     TIMESTAMP,
  load_end_ts TIMESTAMP,               -- 无更新即持续有效
  hash_diff   STRING,                  -- 判断是否变化，避免逐列比较
  cust_name   STRING,
  cust_level  STRING,
  record_src  STRING
);
```

- **为什么这样设计有效**：因为键、关系、属性被拆成三类正交的表，任一源系统新增或变更只影响对应的 Satellite，不改动键表与关系表——「新增一个源」的改动面被限制在少数几张表内，同时每个 Satellite 自带生效区间，历史可逐段还原。
- **代价**：要拼出一条完整记录需要 Hub × Link × 多个 Satellite 的大量 JOIN，因此几乎必然要在其上再建一层宽表或维度视图供 BI 使用，等于多养一套加工链；表数量按「源系统数 × 实体数」增长，元数据与血缘的维护面随之膨胀。
- **失效点**：当团队缺少自动化装载工具与专职建模角色时，「改动面小」的优点会反转成**没人读得懂**，因为灵活性来自正交拆分，而正交拆分的代价是理解一条记录要跨五六张表；人的理解成本随表数上升，最终团队会绕过 Vault 另建一套宽表，Vault 变成只写不读的归档层——它占着存储与加工成本，却不再支撑任何分析。
- **真实使用**：Data Vault 由 Dan Linstedt 于 1990 年代提出，其 2.0 规范由 Linstedt 与 Olschimke 系统化整理（【公开：Linstedt & Olschimke《Building a Scalable Data Warehouse with Data Vault 2.0》, 2015】），在金融、保险等对变更追溯与审计要求高的行业被较多采用；这类行业常同时要求保留历史快照，与 SCD Type 2 的目标部分重叠但粒度更细（相关行业落地可按「Data Vault 2.0」案例自行检索核验，【经验】）。

#### 3.2.7 Cube / 预计算立方体

- **被什么约束逼出来**：固定的查询模式 + 亚秒级响应要求——计算本身无法塞进延迟预算，只能把计算前移到写入侧。
- **结构**：

```text
Cube：把「维度组合 → 聚合值」在写入侧算完，查询侧只做定位读取
  维度                基数
  ──────────────────  ──────────────────────────
  日期（按天，1 年）    365
  城市                 约 300
  品类                 约 50
  渠道                 约 10
  ────────────────────────────────────────────────
  全组合上界 = ∏|Di| = 365 × 300 × 50 × 10 ≈ 5.5 × 10^7 行
  （【推算：组合式 O(∏|Di|) 见本章 §2.2；数值按上表基数相乘，
     365×300=109,500 → ×50=5,475,000 → ×10=54,750,000】）
  → 5 千万行量级尚可接受；但若再加入一个基数 10^4 的维度，上界直接 ×10^4
  ────────────────────────────────────────────────
  结论：Cube 的可行性取决于「高基数维度」的个数，而不是维度总个数
  查询侧：命中 Cube → 定位读取；未命中 → 回落到宽表扫描（设计里必须留这条路）
```

- **为什么这样设计有效**：因为查询期只做「定位 + 读取」而不做聚合，响应时间与明细数据量脱钩，只与命中模式有关，所以固定看板可以在数据量增长时保持稳定延迟。
- **代价**：存储按组合数增长，源数据每次更新都要重算受影响的分区组合（刷新有延迟，且刷新链越长延迟越不可控）；维度或口径变更需要重建，重建期间查询回落到扫描路径，性能出现可预期的劣化窗口。
- **失效点**：当出现高基数维度（用户 ID、设备 ID、订单号）时，「亚秒级响应」的优点会反转成**物理上不可物化**，因为组合数上界是各维度基数的乘积——一个 10^7 基数的维度直接把上界抬到不可承载的量级；此时正确做法是退出 Cube，改用物化视图只覆盖高频组合。
- **真实使用**：Apache Kylin 是 Cube 预计算的代表实现（【公开：Apache Kylin 官方项目页, 2015 年成为 Apache 顶级项目】）；StarRocks、Apache Doris 以物化视图 / Rollup 类能力提供同类加速，其中 Cube 一词在其文档中亦指此类预聚合物化能力（以各官方文档当前版本为准）。多数团队只对「固定看板 + 高频维度组合」建 Cube，其余走物化视图或直查（【经验】）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 传统企业 BI 报表 | 分层建模 + 离线数仓 | 宽表虽快，但口径变更要回刷全量 | 报表口径相对固定、T+1 可接受 |
| 互联网高并发自助分析 | 实时数仓分层 + 湖仓一体 | 只看实时会丢掉可重算性 | 有流式链路且有口径重放能力 |
| TB 级以下小数据深度分析 | OBT 宽表 + 物化视图 | 分层在这种规模下是纯开销 | 数据量小、JOIN 成本低于维护成本 |
| 跨域大型企业（银行 / 保险） | Data Vault + 分层建模 | 维度建模难以承载多源频繁变更 | 有专职建模与自动化装载 |
| AI / 特征工程 | 数仓 DWS 层 + Feature Store | 直接读 ODS 会把清洗成本推给算法侧 | DWS 粒度与特征口径能对齐 |
| 自然语言查询（NL2SQL） | 指标语义层 + 物化预计算 | 让模型直接读物理表必错口径 | 指标定义已集中且可机器读取 |
| 海量历史数据分析 | 湖仓一体 + 列存 + 分层 | 都塞进数仓存储成本不可控 | 冷数据占比高、查询容忍秒级 |
| 金融合规审计 | Data Vault + 历史快照 | 只留当前状态无法回答历史问题 | 审计要求可还原任一时点 |

**最常被误选的一对，是 OBT 宽表与分层建模**：误选不是「选了快的那个」，而是**把宽表当成了可以长大的分层**。团队常在上线初期用一张宽表快速交付，随后所有新需求都往这张表加列，直到某天发现——维度口径要改一次，就必须回刷全部历史分区；想复用中间结果，发现中间结果根本没被物化过；想引入治理，发现没有一层可以承接。反过来，在 TB 级以下、口径稳定的场景里硬建四层，则会把唯一的收益（查询快）换成四份加工开销。

### 3.4 组合模式：真实系统不会只用一种

**组合一：分层建模 + 指标语义层**（口径治理型）
- 职责边界：分层负责**物化**（把数据落在合适粒度上），语义层负责**定义**（口径、维度、SLA）——一个管数据在哪，一个管数字怎么算。
- 运维代价：语义层必须覆盖全部消费入口，否则出现逃逸 SQL；分层要把 DWS 粒度对齐语义层声明的 grain，两边任何一侧变更都要联调。
- 适合规模：10+ 业务域、指标数百、口径争议频繁的组织。

**组合二：实时数仓分层 + 湖仓一体**（同一份存储两套延迟）
- 职责边界：实时链路把结果写进湖仓表格式，离线链路读同一份文件做重算与回刷——延迟由实时链路提供，正确性由离线链路兜底。
- 运维代价：要维护 compaction 与快照过期，否则小文件与快照堆积拖垮读取；两条链路的口径对齐需要专人负责。
- 适合规模：要求分钟级产出、且已具备湖仓表格式管理能力的团队。

**组合三：Cube + OBT / 宽表**（固定看板与即席分析并存）
- 职责边界：Cube 服务固定看板（命中即定位读取），宽表服务分析师的自助查询（不命中时回落）——把确定性交给预计算，把不确定性交给宽表。
- 运维代价：两条刷新链（Cube 刷新 + 宽表摊平），且必须明确「未命中回落」的路径与容量预留，否则预计算失效时会直接打穿宽表。
- 适合规模：看板固化、但有稳定的自助分析需求的中大型团队。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因 | 修法 |
| --- | --- | --- | --- | --- |
| 烟囱式数仓 | 同一业务实体在不同部门有不同 ID 与口径 | 跨域口径无法对齐，同一指标出现多个版本，决策层不知信哪个 | 部门 KPI 独立，公共层没有承接方 | 建企业级公共层（一致性维度 / OneID），部门只在其上建数据集市 |
| 过度分层 | 7–8 层链路，每层数据量都很小 | 每层一次物化，存储与耗时按层数放大；按时产出率随层数相乘下降 | 用加层替代设计，把问题推到下一层 | 收敛到 4 层（ODS/DWD/DWS/ADS），必要时再加一层 DIM（维度层） |
| 忽视数据治理 | 同一「客户」在 10 张表里 ID 不同 | 关联结果错而不报错，JOIN 键不一致时表现为数据变少 | 先建表后治理，主数据没有归口 | 建 OneID 主数据体系，关键维度统一编码后再入仓 |
| 历史数据归档失败 | 热表越来越大，查询越来越慢 | 扫描量随历史累积增长，冷数据抢占热路径的资源 | 没有冷热边界与迁移触发条件 | 建立 Hot/Warm/Cold/Archive 分层，写清迁移触发条件 |
| 维度爆炸 | 一个事实表关联 50+ 维度表 | JOIN 数与中间结果规模上升，查询计划不稳定 | 维度未合并、退化维度被拆出去建表 | 合并同类维度、使用退化维度、拆分星型（按业务过程拆成多个小星型），必要时改走 OBT |
| 缺乏数据质量监控 | ETL 失败或数据漂移无人发现 | 错误数据静默进入下游报表，发现时已影响决策 | 任务成功即视为数据正确 | 建全链路数据质量监控与产出校验（见 Ch11） |
| Cube 滥用 | 任何查询都要求建 Cube | 存储组合数爆炸、刷新链复杂，重建窗口内性能劣化 | 把预计算当成通用加速手段 | Cube 只用于固定高频 OLAP 场景，其余用物化视图 |
| 实时数仓「为实时而实时」 | 业务决策周期是天，链路却按秒级建 | 双链路成本与运维面翻倍，收益接近于零 | 技术选型先于业务需求评估 | 由业务决策周期反推延迟要求，再决定是否实时化（见 §7 决策树） |

**维度爆炸**在生产中的典型暴露方式不是「查询变慢」，而是**查询计划不稳定**：维度数超过一定规模后，优化器在不同数据分布下会选出不同形状的计划（有的先聚合有的先 JOIN），同一个看板在不同日期耗时相差数倍，而团队往往会去调优某一版计划——下一次数据分布变化后，调优成果归零。

**Cube 滥用**的暴露方式是**刷新链的雪崩**：当多数查询都依赖 Cube，「源表更新 → 受影响组合重算 → Cube 重建 → 下游刷新」形成一条长链，任何一个环节延迟都会传导到看板可用时间；而重建窗口内查询回落到扫描路径，性能劣化与业务高峰叠加时最危险。

**烟囱式数仓**的暴露方式最容易被归错因：报表数字对不上时，团队的第一反应通常是「ETL 有 bug」，于是逐条排查 SQL，而真实原因是**两个部门的同名指标本来就是两个定义**——不解决归口，排查再多次也只是把口径差异重新发现一遍。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 数据量 TB → PB | OBT 宽表 | 摊平后的全量重写成本随数据量线性上升，变更一次的回刷窗口已不可接受 | 分层建模 + 湖仓一体 + 列存 | 需要重建分层与表格式治理，历史数据要迁移且要保证口径不变 |
| 看板固定 → 自助分析为主 | Cube / 预计算 | 查询空间超出预计算覆盖的组合，未命中持续回落到扫描 | 语义层 + 宽表，Cube 只保留高频看板 | 需把口径从 Cube 定义迁到语义层，两套定义要并行一段时间 |
| 单域 → 10+ 业务域 | 单域分层数仓 | 同一个词在不同域指不同东西，跨域 JOIN 结果错而不报错 | 公共层（一致性维度）+ 指标语义层 | 需要主数据归口与编码统一，历史数据的键要重映射 |
| T+1 够用 → 分钟级要求 | 离线分层 | 产出时间不满足决策节奏，但业务并不接受口径失控 | 实时分层 + 离线双链路（分清哪条定口径） | 双链路成本上升；必须先让口径可重放，否则实时只是把错误提前 |
| 团队 3 人 → 30 人 | 手写 SQL 加工 | 加工逻辑散在各人手里，变更影响面靠记忆判断 | 自动化装载 + 血缘与影响面（见 Ch11 §5） | 需要把既有 SQL 收敛进规范化加工框架，短期交付节奏会变慢 |

### 3.7 自检清单

- [ ] 事实表里是否出现过描述性文本列？出现即违反粒度纪律，应放回维度表。
- [ ] 每层的粒度能否用一句话说清（一行代表什么）？说不清即粒度未定义。
- [ ] 同一指标是否在两处以上被定义？存在即口径必然漂移。
- [ ] DWS 的粒度是否对应真实的公共查询模式，还是按猜测建的？
- [ ] 是否有 Cube 的维度包含用户 ID / 设备 ID 这类高基数字段？
- [ ] 维度改名或改口径时，需要回刷多少历史分区？答不出即未做变更影响评估。
- [ ] 实时链路的产出是否可重放（源事件可回放、算子状态有 checkpoint）？
- [ ] 是否有一条业务链路直接从 ODS 出报表？有则说明中间层未被当作唯一出口。
- [ ] 冷热边界与归档触发条件是否写死（时间 / 大小 / 访问频率）？
- [ ] 加工链路上是否有「任务成功但数据错误」的检测手段（非空、枚举、唯一性、波动）？
- [ ] 新建一张表时，是否能立刻回答它的下游有哪些？说不清即血缘缺失。
- [ ] 实时链路的口径若与离线不一致，以哪一条为准是否已明确？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 口径固定、T+1 可接受 | 分层建模（4 层） | 每层一类变换，问题可定位到变换而非全链路 |
| 查询模式不可预测、数据量中等 | OBT 宽表 + 物化视图 | JOIN 成本从查询期挪到写入期 |
| 口径争议多、消费方众多 | 指标语义层 | 定义只有一处，分歧可 diff 而非对数据 |
| 决策周期要求分钟级 | 实时数仓分层 + 湖仓一体 | 可重放才能修正口径，否则快等于错得快 |
| 多源频繁变更 + 审计可追溯 | Data Vault | 键 / 关系 / 属性正交，改动面被限制在 Satellite |
| 固定看板 + 亚秒级响应 | Cube（维度基数可控） | 计算前移，查询期只做定位读取 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**「你要的是当前状态，还是变化过程本身」**。只服务当前状态的场景（报表、看板、自助分析）可以用宽表或 Cube 换取查询速度；需要还原变化过程的场景（对账、审计、口径追溯）必须让历史以可重算的形态存在——分层、表格式快照、Data Vault 的 Satellite 都是为这条约束服务的。
>
> 一句实操建议：在选模式之前先回答「这个数字错了要多久才能改对、改对时要重算多少历史」。答不出这个问题，任何模式都只是暂时能跑。
