## 7. 与其他方法对比

> 原 § 7 共 62 行：一张 1–5 分的对比维度表、一棵决策树、4 条组合清单。打分把「取决于场景的结论」写成了绝对结论，也没有交代分数背后的机制与出处，本文件重写为约 310 行的对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

第一，分数把场景相关的判断写成了绝对判断。典型的对比表会给传统数仓的「ACID 保障」打 5 分、给数据湖打 1 分。但如果你的那张事实表只有一条写入链路、每天一次分区覆盖，ACID 的边际价值接近于零——而在同一份对比里，为 ACID 付出的代价（专用存储的单价、演进时不得不重建表、非原生引擎读不了）仍然要照付。分数不会告诉你这两件事的交换关系。

第二，同一维度在不同约束下权重相反。以「Schema 灵活性」为例：数据结构稳定、口径已定的报表场景里，Schema-on-Read 是把解释成本推给每一个读者，是纯粹的负债；而在源系统每月都在改字段的采集早期，Schema-on-Write 的严格校验会把上游每一次字段变更变成下游的一次发布。同一列的分数，在两种处境下指向相反的结论。对比表只有一个格子，装不下两个结论。

第三，打分隐含了一组权重。「8 个维度各占 1/8」是读者的默认假设，但工程上的真实决策往往是一票否决：合规要求数据不出境、或 SLA 要求秒级响应——不满足的候选直接出局，剩下的维度只在通过者之间做比较，而不是做加权平均。

所以本章的判据顺序是：**先问「它做不到什么」，再问「成本随什么增长」，最后才在通过前两问的候选里选。** 能做到的事通常可以靠加钱补，做不到的事和成本函数的形式不能。

对比表并非无用，只是必须换一种写法：把「打分」换成「带机制依据的定性排序」。例如不要写「Lakehouse 的某个维度 5 分」，而要写「Lakehouse 的跨引擎读取能力最强，因为它把表状态放在所有引擎都能解析的开放元数据里；代价是没有任何引擎会替你维护整体布局，Compaction 与快照清理转为常驻运维」。同一句话里包含了排序、机制与代价，读者可以据此判断自己的处境是否与之匹配——这正是分数无法承载的信息。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 能力边界 | 它做不到什么（而不是能做什么） | 数仓类的差异很少在「能不能算」，而在「同一份数据能不能被第二个引擎读」「字段改名能不能原地完成」——这类边界靠加资源解决不了 |
| 成本结构 | 成本随什么增长（数据量 / 扫描量 / 常备节点 / 组合数） | 数仓类的成本有四种不同的主导项，选错主导项意味着规模翻倍时账单翻的倍数不同 |
| 机制契合度 | 其表状态的权威在哪、合并成本付在写侧还是读侧 | 写入模式（追加 vs 更新）与访问模式（点查 vs 全表聚合）直接决定哪个机制占优，这是本主题唯一稳定的判据 |
| 运维复杂度 | 需要几个人、什么技能、多少常驻组件 | 数仓是常驻系统：集群要扩缩、小文件要合并、快照要清理，运维面往往比授权费更能决定总成本 |
| 生态与锁定 | 离开它要付出什么（SQL 方言 / 存储格式 / 元数据托管） | 数据仓库的锁定不在 SQL，在于表状态的解释权掌握在谁手里 |
| 演进风险 | 项目活跃度与路线图方向 | 表格式与引擎的路线图会改变「今天的最优布局」，选型要为那条路线图留出迁移路径 |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 传统数仓（Teradata / Greenplum / Oracle Exadata / Hive + Spark SQL） | 企业级集中式分析库 | 存算一体的专用 MPP，Schema-on-Write，统计信息与 CBO 由引擎自持 | 电信、金融、大型制造 | 商业授权或开源 |
| 云原生数仓（Snowflake / BigQuery / Redshift / MaxCompute / Hologres） | 托管式分析服务 | 存算分离，计算按需起停，存储与计算分别计费 | 互联网、零售、SaaS | 按用量计费 |
| 数据湖（HDFS / S3 / OSS + Parquet 或 ORC + Spark / Trino） | 原始数据的蓄水池 | 没有表状态，读时解释（Schema-on-Read），「表」等于目录里有什么文件 | 早期大数据团队、日志与归档 | 开源 |
| Lakehouse（Iceberg / Hudi / Delta / Paimon + 对象存储） | 开放存储上把表语义带回来 | 表状态是一层可被原子替换的元数据（清单 / 事务日志 / 时间线），多引擎共享同一份 | 中大型平台团队 | 开源 + 云厂商托管 |
| 实时数仓（Kafka + Flink + Doris / StarRocks / ClickHouse） | 分钟级到秒级的分析链路 | 把处理从批窗口前移到事件到达时，结果写入列存 + 排序键的 OLAP | 电商、内容、风控 | 开源 + 商业版 |
| 指标语义层 / Headless BI（MetricFlow / Cube / 阿里云指标平台 / Doris Cube） | 数据资产之上的口径层 | 指标定义从 SQL 中抽出来单独定义一次，被多个消费方复用 | BI 密集型企业 | 开源 + 商业 |
| 预计算立方体（Apache Kylin / StarRocks Cube / Doris Rollup / 物化视图） | 把聚合前移到加载时 | 存储复杂度 O(∏|Dᵢ|)，命中后查询近似 O(1) | 固定报表、亚秒级看板 | 开源 |
| AI 原生数仓 / 向量化数仓（Snowflake Cortex Search / BigQuery Vector Search / SingleStore Vector / 数仓 + 向量库 + LLM） | 让 LLM 与 Agent 消费数据 | 向量索引与关系表在同一查询里联合，或经语义层暴露给 LLM | AI 应用团队 | 托管服务 |
| 内嵌 OLAP（DuckDB / SQLite / 单机 ClickHouse） | 单机分析引擎 | 进程内向量化执行，没有服务端与网络往返 | 个人分析师、单部门、边缘 | 开源 |

这些候选其实只有四族。**A 族：专用分析引擎**（传统数仓、云数仓、实时数仓、预计算立方体、内嵌 OLAP）——表状态在引擎内部，引擎为它自己的存储布局负责；**B 族：开放存储上的表**（数据湖、Lakehouse）——表状态在文件与元数据里，没有谁自动替你优化布局；**C 族：口径层**（指标语义层）——不存数据，只存定义；**D 族：面向模型消费的接入层**（AI 原生数仓）——通常不是新存储，而是在已有存储上加索引与接口。

先分族能省掉一半比较：族内差异基本是同一机制的参数差异（按量计费还是包年、单机还是集群、单表还是分区表），跨族才是机制不同。同一族内部的对比，用单价与规格就能算清；跨族的对比，必须回到机制。

举个例子说明这个省法：在 A 族内部比较「云数仓 vs 实时数仓」，实际要回答的只是「你需不需要把处理前移到事件到达时」（维度 3 的取值）加上「你愿不愿意养一批常驻流作业」（成本主导项的变化）——这两个问题答完，选型就结束了。而比较「数据湖 vs 云数仓」时，问题完全不同：它们对「表状态由谁解释」（维度 1）给出了相反答案，因此讨论的不是费用高低，而是**数据能不能被第二个引擎原生读写**。把这两类问题混在一张表里打分，正是打分表最容易误导人的地方。

把候选映射到 §7.3 的四个机制维度上，可以一眼看出谁与谁在机制上同源：

| 方案 | ① 表状态的权威 | ② 存算组织 | ③ 数据就绪时机 | ④ 语义位置 |
| --- | --- | --- | --- | --- |
| 传统数仓 | 引擎内部 | 存算一体 | 批窗口 | SQL 里 |
| 云数仓 | 引擎内部 | 存算分离、可弹性起停 | 批窗口 | SQL 里（可叠加语义层） |
| 数据湖 | 没有表状态（文件即表） | 纯对象存储 | 批窗口 | SQL 里 |
| Lakehouse | 开放元数据 | 纯对象存储 | 批窗口或事件到达 | SQL 里（可叠加语义层） |
| 实时数仓 | 引擎内部 | 存算分离 + 常驻流作业 | 事件到达 | SQL 里 |
| 指标语义层 | 不适用（不存数据） | 不适用 | 不适用 | 指标定义里 |
| 预计算立方体 | 引擎内部 | 依附宿主引擎 | 加载时预计算 | SQL 里 |
| AI 原生数仓 | 依附宿主存储 | 依附宿主 | 随宿主 | 通常经语义层暴露 |
| 内嵌 OLAP | 引擎内部（单机实例） | 单机 | 批窗口 | SQL 里 |

读这张表的方式是看「差异出现在哪一列」：同一列取值相同的两个方案，在该维度上不需要比较；差异列才是比较的对象。比对时 ④ 列按括号前的词算——「SQL 里（可叠加语义层）」与「SQL 里」是同一个取值，括号只注明该层之上还能再叠一层。按这个读法：云数仓与实时数仓差在 ②③ 两列（存算组织与数据就绪时机），数据湖与 Lakehouse 的差别落在 ① 列，另有 ③ 列上 Lakehouse 多出的「事件到达」——它同样由显式表状态带来：没有清单或事务日志，事件到达时的 upsert 无处落账。所以后者的差别可以精确到一句话：**表状态有没有被显式写下来**。

### 7.3 机制差异：为什么它们表现不同（核心节）

本节按四个机制维度展开。四个维度相互独立，可以分别取值——一个系统在维度 1 上选「引擎内部」、在维度 3 上选「事件到达」，就得到「实时数仓」这个组合；在维度 1 上选「开放元数据」、维度 2 上选「纯对象存储」、维度 3 上选「批窗口」，就得到「Lakehouse 承接离线」这个组合。所谓「架构演进」，多数时候只是把某一个维度的取值换了一档，同时接住换档带来的代价。

四个维度之间也有联动，联动方向明确：维度 1 选了「开放元数据」，就把维度 4（语义在哪一层）的紧迫性推高了——因为多引擎读取意味着同一份数据会被多个团队各自解释，若口径仍散落在各人的 SQL 里，第二口径出现只是时间问题；维度 3 选了「事件到达」，就把维度 2 的取值锁死在「计算可独立起停」上——常驻批集群无法承接持续到达的增量。反过来看失效案例，多数不是某一维度选错了，而是选了组合之后没有接住组合自带的代价。

#### 7.3.1 表状态的权威在哪：引擎内部 vs 开放元数据

**机制是什么**：一张表的「此刻状态」（哪些文件、什么 schema、哪个版本）由谁定义、谁能解释。

**它在各候选中的实现差异**：

| 候选 | 表状态的定义者 | 换一个引擎读它需要什么 |
| --- | --- | --- |
| 传统数仓 / 云数仓 | 引擎自己的 catalog 与存储格式 | 经由该引擎的导出或联邦查询，通常无法原生读取 |
| 数据湖 | 没有表状态，只有「目录里有什么文件」 | 读者自行解释 schema 与分区约定 |
| Lakehouse | 一层开放元数据（Iceberg 的 metadata → manifest list → manifest → data file，或 Delta 的事务日志、Hudi 的时间线） | 任何实现了该规范的引擎原生读写同一份数据 |

**由此必然导出的性质**：因为数仓的表状态只有该引擎能解释，所以引擎可以在自己的格式上做很深的自适应优化（自动聚簇、自动物化视图、执行期改计划），代价是数据要进出这个引擎就必须走它的写入路径——想被第二个引擎读，就得复制一份（多一份存储、多一条同步链路、多一个口径分叉点）；因为 Lakehouse 把表状态外化成开放元数据，所以表状态的权威可以在多个引擎之间共享，代价是没有任何引擎会替你维护整体布局，Compaction、文件大小、分区演进这些「引擎本来会自己做的事」全部转为你的常驻运维责任。

**公开证据**：Iceberg 由 Netflix 开源、其后成为 Apache 顶级项目【公开】（Apache 软件基金会官方项目页 Apache Iceberg，该项目于 2020 年毕业为顶级项目；当前状态以 iceberg.apache.org 当前版本为准）；Delta Lake 由 Databricks 于 2019 年开源【公开】（Databricks 官方博客的 *Delta Lake* 开源公告，2019，见 databricks.com/blog）；Iceberg 的 V3 规范在行级删除之上加入删除向量、增量读取与 Variant 类型【公开】（Apache Iceberg 官方规范 *Iceberg Table Spec* 的 V3 章节，2024；行级删除文件机制自 v2 规范起已提供；具体条目以 iceberg.apache.org 当前版本为准）。

**失效条件**：当一份数据只有一个读者、写入路径也只有一条时，开放元数据的「可共享」收益为零，剩下的只有元数据与合并的运维成本。此时把 Lakehouse 用在单引擎场景，是把代价留在手上、把收益留在了未来。

这条机制还有一层容易被忽略的推论：**更新与删除的代价位置也随之改变**。因为数据文件不可变，一次行级更新只能表达为「写一个新文件 + 声明旧文件失效」，所以「改了多少行」与「读写多少字节」脱钩——改 1 行也可能触碰一整个文件。引擎内部的数仓可以靠原地更新或后台合并把这件事藏起来，开放表格式则必须由写入方与常驻合并任务共同承担。判断方法很直接：把该表每天的更新条数乘以「被命中的文件大小」，得到的字节数就是这条机制在你身上的实际开销；这个乘积稳定时可以靠加合并资源续命，它在增长时说明写模式与表格式已经错配。

#### 7.3.2 存算组织：一体 / 分离 / 纯对象存储

**机制是什么**：查询要用的数据离计算节点有多远，以及计算资源能否独立于存储扩缩。

**它在各候选中的实现差异**：

| 候选 | 存储位置 | 计算扩缩的粒度 | 数据到计算的路径 |
| --- | --- | --- | --- |
| 传统数仓 | 本地磁盘阵列 | 节点级（通常等于扩容一台机器） | 本地 I/O |
| 云数仓（存算分离型） | 远端对象存储或托管存储层 | 虚拟数仓 / 计算组级，秒级到分钟级起停 | 远端拉取 + 本地缓存 |
| Lakehouse | 对象存储 | 任意计算引擎，随任务起停 | 每次任务从对象存储拉取 + 引擎自带缓存 |

**由此必然导出的性质**：因为存算分离后计算可以独立于存储扩缩，所以计算成本能跟随负载的峰谷变动，而存储成本变成与「容量 × 保留时长」线性相关的一项——代价是每次冷启动都要从远端拉数据，查询的首字节延迟由网络与缓存命中率决定，而不是由本地磁盘决定；因为 Lakehouse 的存储完全交给对象存储，所以同一份数据能被任意数量的引擎挂载，代价是对象存储按请求数计费，且「列举目录」这类操作在高分区数下会变成主要开销来源之一。

**公开证据**：存算分离是云数仓的公开架构主张——Snowflake 于 2020 年上市，其对外材料中长期以「计算与存储分别计费、计算按需起停」的形态呈现【公开】（Snowflake 官方文档的架构章节与 2020 年上市材料；当前架构以 snowflake.com 官方文档当前版本为准）；DuckDB 的可嵌入分析引擎设计出自其演示论文 *DuckDB: an Embeddable Analytical Database*（SIGMOD 2019 演示论文，Raasveldt & Mühleisen）【公开】。

**失效条件**：当查询负载平稳、吞吐恒定（例如每天固定时段跑固定报表）时，弹性不产生收益，只剩网络与缓存管理的开销。此时一体化部署（本地存储 + 固定集群）反而更简单也更快。

这条机制选择的第二个后果是**缓存管理从透明功能变成架构决策**。因为数据在远端，引擎必须靠本地缓存把重复访问挡在网络上，而缓存命中率取决于「访问是否重复」——同一张报表每天跑同一天的增量分区，命中率接近满；临时探索式查询每次换分区，缓存形同不存在，所有 I/O 都走网络。所以同一条链路在不同使用方式下的延迟可以差出一个量级，而性能评估若只测「重复跑同一条查询」，测出来的正是缓存最好的那一面。评估方法应当混合两类负载：一类固定重复（代表报表），一类随机换分区（代表排障与探索）。

#### 7.3.3 数据就绪的时机：批窗口 / 事件到达 / 加载时预计算

**机制是什么**：把「从原始数据到可查询结果」这段计算放在哪个时刻。

**它在各候选中的实现差异**：

| 时机 | 归属候选 | 结果何时可见 | 主要代价 |
| --- | --- | --- | --- |
| 批窗口内 | 传统数仓、离线数仓 | 下一个批窗口结束后（典型 T+1） | 新鲜度受调度周期限制 |
| 事件到达时 | 实时数仓、流批一体的 Lakehouse | 秒级到分钟级 | 每条逻辑都要有流式等价实现，状态与乱序成为新问题 |
| 加载时预计算 | 立方体、物化视图 | 刷新完成后即 O(1) 命中 | 存储随维度基数乘积增长，刷新窗口与查询模式绑定 |

**由此必然导出的性质**：因为实时链路把处理前移到事件到达的那一刻，所以端到端延迟的下界由「上游事件何时产生」决定而不是由你的调度决定，代价是同一条业务逻辑要维护两份实现（批与流），而两份实现的口径漂移会成为长期的一致性负债；因为立方体把聚合前移到加载时，所以固定查询可以做到亚秒级，代价是存储复杂度为 O(∏|Dᵢ|)（本仓库主文件 §2.2 的形式化），维度的基数乘积一旦上升，预计算空间与刷新时间会一起膨胀——这是「Cube 必须慎用」的根本原因，也是它无法被当成通用加速器的原因。

**公开证据**：流批一体的表格式与预计算语义均有公开规范与实现——Apache Paimon 于 2024 年发布 1.0，其 changelog 机制即把「事件到达时」产生的变更直接暴露为下游可读的流【公开】（Apache Paimon 1.0 发布说明，2024，见 paimon.apache.org；具体能力以该站官方文档当前版本为准）；立方体的 O(∏|Dᵢ|) 复杂度出自本仓库主文件 §2.2 的形式化推导。

**失效条件**：当查询模式不固定时，立方体的命中率下降而刷新成本不变，此时它退化为「多存一份、多刷一遍」；当上游数据本身只在 T+1 才产出时，下游做成秒级只是把延迟前置到无人消费的时段。

三个时机并非互斥，实际系统常常叠用：实时链路保证当天数据的分钟级可见，批窗口负责历史回算与口径修正，预计算层承接固定报表——这正是本仓库 [§3.1 模式 3（实时数仓分层）](01-data-warehouse-section-3-sec3.md) 与本章 §7.6 组合二在讲的形态。叠用的问题不在技术可行性，而在**同一份口径出现了三份实现**：三处都要改，任一处漏改就产生一个新的「同名不同义」。所以叠用的前提是先有 §7.3.4 的口径层，否则延迟越低的系统，口径漂移暴露得越快。

#### 7.3.4 语义在哪一层：SQL 里 / 指标定义里

**机制是什么**：「GMV 等于什么」这句话被写在哪里、被谁复用。

**它在各候选中的实现差异**：

| 语义位置 | 归属候选 | 谁能复用 | 变更一个口径要动几处 |
| --- | --- | --- | --- |
| SQL 里 | 传统数仓、数据湖、Lakehouse 的物理表 | 只有读到这段 SQL 的人 | 每一处引用（报表 / 模型 / 接口各一份） |
| 指标定义里 | 指标语义层 / Headless BI | BI、AI、外部 API 都能按同一份定义取数 | 一处定义，各消费方按版本生效 |

**由此必然导出的性质**：因为语义层把口径从 SQL 里抽出来定义一次，所以同一口径对 BI、AI 与外部接口呈现同一个值，「同名不同义」的概率不再随消费方数量上升，代价是多出一层需要治理的资产——指标定义本身要版本化、要有 owner、要能在变更时评估影响面，而且语义层的表达能力必须覆盖真实口径，覆盖不到的地方会有人绕回去手写 SQL，形成第二套口径；因为语义留在 SQL 里时变更成本与引用处数量成正比，所以数仓越大，口径变更越倾向于「只改报表、不改下游」——这正是同名不同义的主要生成方式。

**公开证据**：指标语义层的实现已有公开工具（MetricFlow、Cube 等，能力与版本以各自官方文档当前版本为准）；本仓库主文件 §1.2 把「指标一致性」列为企业建设数仓的核心业务驱动之一，[§3.1 模式 4（指标语义层）](01-data-warehouse-section-3-sec3.md) 给出了指标语义层的定位。

**失效条件**：只有一类消费方时，语义层只是多一层治理对象；指标数量很少（几十个以内）且变更极低频时，用代码评审保证口径一致的成本更低。

到了 LLM / Agent 阶段，这条机制的重要性发生了一次跳变：**机器消费方不能像人一样「看上下文猜口径」**。人看到报表标题会知道 GMV 含不含退款，SQL 生成器不会——它只能读定义。所以语义层从「治理的加分项」变成「AI 取数的前置条件」：没有机器可读的口径，模型只能在物理表名与字段名上做统计式的猜测，猜错的成本由业务承担。这也解释了本仓库 [§5.6 未来 3–5 年：可证伪的预测](01-data-warehouse-section-5-ai.md) 为什么把「指标语义层成为标配」列为趋势之一——它与能不能用自然语言查询直接相关，而不只是治理话题。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 存储容量 × 保留时长
     + 计算（常备集群 或 按扫描量 或 按运行时长）
     + 数据搬运（物理副本数 × 副本大小）
     + 元数据与规划开销（清单 / 快照 / 分区数）
     + 运维人力（常驻组件数 × 所需技能）
```

| 候选 | 主导项 | 随什么增长 | 隐性成本 |
| --- | --- | --- | --- |
| 传统数仓 | 常备集群（按峰值配置） | 峰值并发与峰值数据量 | 扩容周期（采购与上线）长，人力技能稀缺 |
| 云数仓 | 计算按运行时长或扫描量 | 查询次数 × 单次扫描量 | 未剪裁的查询直接变成账单；跨区出网费用 |
| 数据湖 | 存储（单价低）+ 每次全量扫描 | 扫描量线性增长，与「读了多少列」无关 | 缺少治理带来的重复副本与口径修复人力 |
| Lakehouse | 存储 + 剪裁后的扫描量 | 数据量 + 元数据规模 | 元数据与 Compaction 的常驻运维、对象存储请求数 |
| 实时数仓 | 常驻流任务（开着就计费） | 作业数与并行度，与「有没有数据」无关 | 状态存储与检查点存储、双链路对账人力 |
| 指标语义层 | 定义本身的治理人力 | 指标数量与消费方数量 | 表达能力覆盖不到时出现绕行 SQL |
| 预计算立方体 | 预计算存储与刷新计算 | 维度基数乘积 O(∏|Dᵢ|) | 刷新窗口冲突、维度变更需全量重刷 |
| 内嵌 OLAP | 近乎为零的基础设施 | 不随服务规模增长 | 数据要先搬到本地：搬运成本与新鲜度 |
| AI 原生数仓 | 向量索引构建与更新 + 推理调用 | 向量条数与更新频率 | 模型或数据更新后索引静默过期，需重建 |

四条可算的账，说明「主导项」为什么值得先确定。

**账一：剪裁把「性能问题」变成「账单问题」。**【推算】设表 10 TB（10,240 GB），按 30 天分区、共 200 列；某查询只需要 5 列、且限定 1 天分区。列剪裁后读取比例 = 5 ÷ 200 = 2.5%；分区剪裁后读取比例 = 1 ÷ 30 ≈ 3.3%；两者相乘后实际扫描量 ≈ 10,240 GB × 2.5% × 3.3% ≈ 8.5 GB，与全表扫描相差约 1,200 倍。推导链只有乘除，前提是「列存 + 统计信息可被用于剪裁」。结论方向也明确：按扫描量计费的引擎里，分区与列布局的收益直接等于账单差额，因此它属于成本设计而不属于调优。

**账二：弹性只在负载有峰谷时兑现。**【推算】设某集群平时需要 100 个计算单元、每天高峰 4 小时需要 300 个。常备 300 单元的日均消耗 = 300 × 24 = 7,200 单元·小时；按峰谷弹性（其余 20 小时用 100 单元）= 300 × 4 + 100 × 20 = 3,200 单元·小时，比常备低约 56%。前提是起停足够快、且冷启动的拉数据开销可被缓存摊薄；若负载全天平坦（高峰 24 小时），这个比例归零，弹性只留下冷启动延迟。

**账三：副本数是乘法项。**【推算】若湖内 100 TB 数据中只有 20 TB 需要在仓内被高频查询，那么「全量复制到仓」与「按需物化 20 TB」的存储倍数比为 100 ÷ 20 = 5 倍；再算上同步链路的运维与两端口径对齐的人力，全量复制的真实倍数高于 5。

**账四：常驻与按需的交叉点。**【推算】设一条流式链路的常驻开销折算为每天 C 个计算单元·小时，同一逻辑改在批窗口内执行需要 B 个单元·小时；则两者相等时 C = B，流式更贵当且仅当 C > B。这条式子说明：判断「要不要实时」不该看延迟数字，而该看**常驻开销与批处理开销之比**——批处理的开销随数据量与运行时长变化，常驻开销只随作业数与并行度变化，数据量越小，流式的相对成本越高。这也是 §7.5 阈值依据 ③ 里「先量上游产出的最早时刻」的原因：如果上游本身是 T+1 产出，C 的收益为零而成本照付。

还有一个不进入账单但进决策的项：**运维人力**。它在成本函数里的形式是「常驻组件数 × 所需技能稀缺度」。数据湖与 Lakehouse 多出的是合并与元数据维护，实时数仓多出的是流作业与状态存储的运维，云数仓多出的是配额与成本看护，立方体多出的是预计算资产与刷新链的维护。这一项的特点是**不可弹性伸缩**：查询高峰可以靠加计算单元捱过去，人力不行。所以在两个候选的成本接近时，选常驻组件更少、且团队已经会的那一个。

### 7.5 决策树（每个分支都要有阈值依据）

```
分析负载进来
├─ ① 单次查询需要扫描的列存字节数，是否超过单机内存与本地磁盘能舒适承载的量？
│   ├─ 否 → 内嵌 OLAP（DuckDB / SQLite / 单机 ClickHouse）
│   │        —— 不要为一个能装在笔记本上的数据集建集群
│   └─ 是 ↓
├─ ② 同一份数据是否需要 ≥2 个引擎或多个团队原生读写？
│   ├─ 是 → ③ 端到端新鲜度要求？
│   │        ├─ 小时级 / T+1 → Lakehouse（开放表格式 + 对象存储）
│   │        └─ 分钟级 / 秒级 → Lakehouse + 流式入湖链路（LSM 主键表承接 upsert）
│   └─ 否 → ③′ 端到端新鲜度要求？
│            ├─ 小时级 / T+1 → 云数仓（存算分离，计算按需起停）
│            └─ 分钟级 / 秒级 → 实时数仓（Kafka + Flink + 实时 OLAP）
├─ ④ 是否存在被反复执行的固定维度组合查询（报表 / 看板）？
│   └─ 是 → 在已选引擎上加立方体或物化视图（而不是换引擎）
└─ ⑤ 是否出现 BI 以外的第二类口径消费方（AI / Agent / 外部 API）？
    └─ 是 → 增加指标语义层；否则口径继续留在建模层
```

**阈值依据**（与树的节点一一对应）：

- **① 单机承载阈值**：判据不是数据总量，而是「单次查询在列剪裁之后需要读取的字节数」——它才是单机引擎要放进内存的量。取「单机存储能放下的数据量」与「查询扫描量能装进内存」两者中的较小者；【经验】多数团队的这个交叉点落在数百 GB 到数 TB 之间，随内存与磁盘规格变化，应实测而非照搬。
- **② 两个引擎**：开放表格式的收益来自「第二个读者」。接入一个引擎时，表状态放在引擎内部即可，此时引入开放元数据只增加 Compaction 与清单维护；从第二个引擎开始，收益才开始与运维成本相抵。注意这里的「多引擎」指原生读写同一份数据，而不是各自读一份副本。
- **③ 小时级 / 分钟级**：这个分界的依据不是引擎能力，而是上游数据的可用时间。若上游 ODS 本身要 T+1 06:00 才产出，下游做成分钟级只是把延迟前置到无人消费的时段【经验】；反之若上游是 CDC 变更流，批处理会让本已可用的数据变陈旧。因此先量「上游产出的最早时刻」，再定下游的延迟目标。
- **③′ 同上**：同一阈值在「不需要多引擎」的分支上复用，避免为同一个物理量设两个不同的数。
- **④ 固定高频**：阈值由立方体的成本函数给出——存储复杂度为 O(∏|Dᵢ|)（本仓库主文件 §2.2）。【推算】设三个维度基数为 10⁴、10²、10²，乘积为 10⁸ 个单元；每个单元即使只存 8 字节度量值，裸数据即 0.8 GB，加上维度键、行标识与索引，实际规模通常要在裸值上再放大一到两个数量级（放大倍数取决于实现【经验】），且每次刷新都要重算。判定式是「命中率 × 单次节省的扫描量 > 刷新成本 + 预计算存储成本」；命中率低或维度基数乘积大时，直接扫列存更便宜。
- **⑤ 第二类消费方**：口径的重复实现成本与消费方数量成正比，因此阈值取「超过一类消费方」。只有 BI 一个消费方时，口径放在建模层即可；出现 AI / Agent / 外部 API 之后，每多一类消费方就多一份口径实现，「同名不同义」的概率随之上升。

关于「阈值应该从哪来」，有一个对照值得写清楚。原 § 7 的决策树在「非结构化为主」这一支上用「数据量 < 1 PB → 数据湖 + Spark + Trino；> 1 PB → 湖仓一体（Iceberg/Hudi + Trino + 对象存储）」作为分界。这条分界的问题不是数值大小，而是它不可推导：1 PB 的对象存储与 1 PB 的湖仓表在存储成本上没有量级差别，真正被这条线区分开的其实是「是否需要第二个引擎原生读同一份数据」与「是否需要表级 ACID 与 Schema 演进」——两者都与 PB 这个数字无关，1 TB 的多引擎场景同样需要湖仓，100 PB 的单引擎场景用不着它。本章的处理办法是把这条分界换成可推导的判据（节点 ① 的单机扫描量、节点 ② 的原生读者个数），并在依据里写清推导前提；若采用任何数值阈值，至少要说清它随哪个变量变化、以及超过它之后成本函数的哪一项变成主导。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 传统企业 BI 报表、T+1 | 云数仓（或既有传统数仓） | 离线数仓 + 指标平台 | 上实时链路没有消费方，只增加双链路对账 |
| 秒级看板 + 高并发点查 | 实时数仓 + 实时 OLAP | Lakehouse + OLAP 服务层 | 纯湖上规划与扫描成本给不出秒级 SLA |
| 多引擎 / 多团队读同一份数据 | Lakehouse | 云数仓 + 定期导出 | 导出产生第二份副本与口径分叉 |
| 非结构化为主、探索式分析 | 数据湖（+ 开放表格式逐步治理） | Lakehouse 从 Bronze 层起步 | 直接上重治理会使探索变形为填表 |
| 指标量大、消费方多 | 指标语义层 + 数仓/湖仓底座 | 物化视图 + 命名规范 | 靠规范维系的同名同义在规模上会失效 |
| 固定维度、亚秒级响应 | 立方体 / 物化视图（挂在已选引擎上） | 内嵌 OLAP | 换引擎不动成本结构，只是换个地方付同样的账 |
| 单部门 TB 级以下深度分析 | 内嵌 OLAP（DuckDB） | 云数仓单仓库 | 为可单机处理的数据建集群，运维面远大于收益 |
| LLM / Agent 取数 | 指标语义层 + 向量检索层 | 直接 Text2SQL 打物理表 | 缺机器可读口径时，SQL 生成只能靠猜表名与猜字段 |

**常见组合**（每条说明组合里各件承担的职责边界与组合的运维代价）：

- **组合一：Lakehouse + 实时 OLAP**
  - 职责边界：湖是事实源与历史账本，OLAP 是面向查询服务的派生副本（可从湖重建）。
  - 适用条件：湖上的规划与扫描成本给不出秒级 SLA，但数据必须保留单一事实源。
  - 运维代价：多一条刷新链路与一套监控；两侧延迟量级不同，跨两侧的查询要显式路由并解释结果。OLAP 侧必须带数据截止时间——刷新失败而监控只看「查询成功」时，看板会持续可用地展示过期数字。
- **组合二：离线数仓 + 实时数仓（Lambda / Kappa）**
  - 职责边界：离线跑全量补数与口径回算，实时跑增量，在应用层（ADS 层）合并两条链路。
  - 适用条件：对实时性与全量历史同时有要求。原 §7 把这条列为该组合的适用条件，今天依然成立。
  - 运维代价：同一份业务逻辑存在两套实现，口径必然漂移，必须配一条常设对账机制。Lambda 付的是对账成本；Kappa 用单一流式实现换掉对账，代价转为历史重放与状态规模的管理。
- **组合三：数仓 + 指标平台**
  - 职责边界：数仓（DataWorks / Snowflake 类）做底座与数据沉淀，指标平台（阿里云指标平台 / MetricFlow 类）做语义层。
  - 适用条件：指标数量多且存在 BI 以外的消费方。
  - 运维代价：语义层的表达能力必须覆盖真实口径，覆盖不到的地方会有人绕回去手写 SQL，形成第二口径；同时指标定义本身成为需要版本化与 owner 的资产。
- **组合四：数仓 + 向量库 + LLM**
  - 职责边界：数仓做事实层（订单、用户、产品这类结构化事实），向量库做非结构化检索，LLM 做自然语言接口。
  - 适用条件：问答与智能体场景需要同时给出「检索到的文本」与「可核对的事实」。
  - 运维代价：两侧权限模型要对齐，否则检索召回的内容可能绕过数仓的行级权限；向量索引与数据版本要同步重建，模型或数据更新后索引会静默过期。
- **组合五：内嵌 OLAP 作为分析师的本地层**
  - 职责边界：远端（湖或仓）管权威与新鲜度，本地（DuckDB 类）管探索速度。
  - 适用条件：单部门、TB 级以下的深度分析与自由探索。
  - 运维代价：本地副本会过期，任何以它为输入产出的结论都要标注数据截止时间；导出物本身成为一份需要治理的副本。
- **组合六：数据湖 + 数据仓库（湖仓一体，单引擎跨源查询）**
  - 职责边界：湖存原始数据与历史全量，仓存分析就绪的精化结果；由同一个查询引擎（Trino / Spark 类）跨湖仓查询，省掉一次物理搬运。
  - 适用条件：既需要湖的低成本留存，又需要仓的建模与性能，且不希望把数据复制到两边各一份。
  - 运维代价：跨源查询的谓词下推与统计信息传递受连接器实现限制，同一个 JOIN 在「全在仓内」与「跨湖仓」两种写法下性能可以差一个量级；两侧元数据仍是两套，需要额外维护表与字段的对应关系。

组合有一个共同的记账规则：**每多一个物化副本，就多一条刷新链路、一套监控与一次口径对齐**。所以组合数量的上限不是技术能力，而是「你愿意长期维护几条同步链路」。判断是否已经过度，有一个简单的问法：同一个业务指标在几个系统里各有一份可被直接消费的物理表示？超过一个的每一份，都对应一条链路与一份长期维护成本。按这条规则，上面第一至第五个组合各自只引入一个额外副本（OLAP、离线侧、指标平台的定义层、向量索引、本地导出物），第六个组合不引入额外副本、但引入一套跨源查询的连接器与下推约束——它们的运维面因此是可数的，不是「越堆越多」的模糊判断。

### 7.7 选错的代价与迁移成本

**反模式：为实时而实时**。症状是业务对新鲜度的实际要求是 T+1，但架构里同时存在批链路与流链路，两套实现、两套监控、两套口径。后果是可用性由两条链路中最脆弱的一条决定，而口径分歧的排查成本长期高于新鲜度带来的收益。正确做法是先量「上游数据最早什么时候可得」（见 §7.5 阈值依据 ③），用这个时刻减去消费方要求的时刻，得到真正需要压缩的窗口；窗口大于一个批调度周期时，流链路不产生价值。本仓库 [§3.3 反模式 8](01-data-warehouse-section-3-sec3.md) 已把「实时数仓为实时而实时」列为典型陷阱。

**反模式：把立方体当默认加速器**。症状是每次查询变慢就加一个 Cube 或物化视图，最终预计算资产的维护工时超过查询本身。后果是存储与刷新成本按 O(∏|Dᵢ|) 增长（§7.3.3），且维度或口径一变就要重刷全量，预计算资产反而成了变更的阻力。正确做法是先用 §7.5 的判定式算一次「命中率 × 节省的扫描量」与「刷新成本 + 存储成本」的大小关系，只在固定维度组合上建，其余用列存剪裁。

**反模式：湖与仓双写、且两侧都可写**。症状是同一个实体在湖与仓各有一份，两边都有写入方。后果是两份数据的时间点不同（各自的提交时刻不同），任何一张报表都无法说明它在读哪一份，对账只能事后进行——跨系统没有共同的事务边界，一致性不可能在提交时被阻止。正确做法是显式指定权威表：湖为权威、仓为派生（可重建），派生侧只读。

**反模式：先选引擎，再想口径**。症状是引擎与表格式都定了，才发现在三个报表里 GMV 有三种算法。后果是口径修正要跨报表逐处改，而 AI / Agent 接入时没有机器可读的口径可用，只能靠猜表名生成 SQL。正确做法是把口径作为与表格式并列的选择项，在 §7.5 的节点 ⑤ 上先回答「有几类消费方」。

**反模式：把「技术栈统一」当成架构目标**。症状是所有表不分读写模式都被搬进同一个引擎或同一种表格式，理由是「只维护一套」。后果是个别负载被迫在自己不适配的机制上运行——最典型的是把高频小事务表放进以大批量提交为优化目标的湖仓表格式，或反过来把需要多引擎读的明细表锁进只允许单引擎写入的专用数仓，于是每次跨引擎访问都要复制一份。正确做法是按 §7.3 的四个维度分别取值，接受「两种结构各自承担自己擅长的写模式」，代价是两套元数据与两套运维，但换来的是每一侧都不必为对方的模式付畸形成本。

这五条反模式有一个共同成因：**把选型当成一次性的技术决定，而没有把它当成一组需要长期承担的成本**。它们各自承担的代价是：

- 「为实时而实时」——承担双份实现的口径漂移与对账成本；
- 「立方体当默认加速器」——承担 O(∏|Dᵢ|) 的预计算存储与刷新成本；
- 「双写且两侧可写」——承担没有共同事务边界带来的一致性成本（只能事后对账）；
- 「先选引擎再想口径」——承担口径重复实现随消费方类别数增长的成本；
- 「技术栈统一」——承担个别负载在不适配机制上被放大的写放大或复制成本。

共同点是：这五项成本没有一项会在上线当天显现，它们都随规模、时间或消费方数量增长。因此选型评审时值得单独问一句——「这个方案在上线一年后，哪一项成本会变大」，答不上来通常意味着方案里有一个尚未被识别的耦合。

**换成另一个要动什么**（工作量量级为相对量级，随存量表数量与业务耦合度放大【经验】）：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 传统数仓 → 云数仓 | 大（全量搬迁 + 增量追平） | 中（SQL 方言与函数差异） | 中（从管集群转为管配额与成本） | 中 |
| 云数仓 → Lakehouse | 中（可原位导出 Parquet） | 中（性能特征变化需重写重查询） | 大（Compaction、清单、快照全新增） | 大 |
| 数据湖 → Lakehouse | 小（数据不动，补元数据与 Catalog） | 小（多为方言与类型对齐） | 中（新增文件与快照运维） | 中 |
| 湖泊分离 → 湖仓一体 | 大（去重与口径合并） | 中 | 大（撤销一条同步链路的监控与对账） | 中 |
| 批 → 批流并行 | 无（新增链路） | 大（逻辑要写第二遍） | 大（新增常驻流作业与状态存储） | 大 |
| 加指标语义层 | 无 | 小（消费方改为查定义） | 小 | 中（口径治理流程要立起来） |

这张表的用法是：迁移成本里最容易被低估的一列是「运维重建」——数据能搬、SQL 能改，但新形态要求的新增常驻工作（合并、清理、对账、成本看护）如果没有对应的人，迁移会在上线后半年以「系统变慢、账单变高」的形式回退成一次事故。

还有一条与迁移顺序有关的经验：**先迁口径与分层，再迁引擎**。原因是口径与分层是数据资产的语义结构，它们的变更会波及所有消费方；而引擎是执行语义结构的工具，换引擎只影响「怎么算」，不影响「算什么」。反过来做（先换引擎、再补口径）会遭遇两次全量回归：换引擎时所有下游按旧口径回归一次，补口径时再回归一次。若必须在两者之间只做一件，先做口径。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 报表固定、T+1 足够、只有 BI 一类消费方 | 云数仓或既有数仓 + 命名规范 | 表状态留在引擎内部，换取自适应优化；单消费方时语义层无收益 |
| 数据要被多个引擎读、写入以追加为主 | Lakehouse（开放表格式 + 对象存储） | 表状态外化为开放元数据，多引擎读同一份而不必复制 |
| 上游是 CDC 流、SLA 在分钟级 | 实时数仓，或 Lakehouse + LSM 主键表 | 处理前移到事件到达时，延迟下界由上游产出时刻决定 |
| 查询模式固定且高频 | 立方体 / 物化视图挂在已选引擎上 | 聚合前移到加载时；代价是 O(∏|Dᵢ|) 的存储与刷新 |
| 指标多、消费方含 AI / Agent | 指标语义层 + 数仓或湖仓底座 | 口径定义一次多处复用，避免同名不同义随消费方数量增长 |
| 单部门、TB 级以下 | 内嵌 OLAP（DuckDB） | 无服务端、无网络往返；搬运与新鲜度是唯一代价 |
| 不确定从哪开始 | 先把口径与分层定下来，引擎按 §7.5 走一遍 | 引擎可换，口径与分层错了要重来 |

> 本节小结：数仓选型里唯一真正起决定作用的那条差异是**表状态的解释权归谁**——归引擎，就换来深度自适应优化与运维简化，代价是数据难以被第二个引擎原生读写；归开放元数据，就换来多引擎共享同一份数据，代价是合并、清理、快照这些运维责任全部转到自己身上。其余维度（计价方式、是否实时、有没有语义层）都是可以事后叠加的增量，而这条差异决定了数据的可迁移性与长期锁定程度。
>
> 一个可操作的顺序是：先量上游产出的最早时刻（定新鲜度档位），再数同一份数据的原生读者个数（定表状态的归属），最后再数口径的消费方类别数（定语义层的位置）——这三个数都在 §7.5 的树上，且都不需要先选产品就能回答。
