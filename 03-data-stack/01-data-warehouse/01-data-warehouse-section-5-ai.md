## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是**没有时间维度**。同一个清单里，「引擎里已经 GA 多年的一个算子」与「产品演示里出现过一次的助手功能」被并列成五条方向，可规划性差一个量级：前者的行为写在官方文档与 release note 里，后者连能力项都还没定名。

第二个问题是清单把「AI 改了什么」抹平了。数仓这一侧的差异可以归到 [§7.3 的四条机制](01-data-warehouse-section-7-sec7.md)上——**表状态的权威在哪**（引擎内部还是开放元数据，§7.3.1）、**存算怎么组织**（§7.3.2）、**数据什么时候就绪**（批窗口 / 事件到达 / 加载时预计算，§7.3.3）、**语义在哪一层**（SQL 里还是指标定义里，§7.3.4）。本节要评估的方向里，AI 对前三条机制**一条都没有改**：数据没有搬家，存储与执行模型没变，取数延迟的下界也没变。它改的是另外三件事：**消费方是谁**（从会 SQL 的人，换成会说业务话的人与程序）、**语义的紧迫性**（第 4 条机制从一个选项变成前置条件）、以及**引擎自己多出来的算子与建议来源**（向量索引、自动优化建议）。

第三个问题是没有反方观点。清单里不会出现「这条方向今天不值得投」，于是「自治数仓」这类还停在演示阶段的条目，会和「指标语义层」这种有开放实现、有版本化文档的工程做法排在同一个列表里。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（或版本化发布的规范与文档）；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期。
- **L2 可试点**：①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

判据 ② 在本主题尤其难过，原因值得先说清：**数仓侧的公开材料绝大多数由厂商与建设单位发布**。「某客户用自然语言问数做自助分析」这类内容，是采购方与建设方的自述，不算第三方；第三方指的是一个既不参与该能力的建设、也不销售它的团队，公开描述了自己在生产里的用法与失败。按本节的口径，**② 只有「满足」与「降为 L2」两种命运**——不能改成「有公开生产记录」，不能靠「本节只评估接入层」缩小适用范围来绕过，也不存在「准 L1」。

另有一条评级规则，全节通用：**按机制分族，族内的子方向可分列成行；族的级别取族内最弱子项**。这不是放宽判据，而是读者做规划时的实际含义——族里只要有一个子项不能依赖，这一族的架构就不能整体依赖。

因此表里是**六行、四族**：五条方向各占一行（自然语言查询 → 取数侧、指标语义层 → 口径侧、AI 驱动的查询优化 → 引擎内嵌（优化侧）、向量原生数仓 → 引擎内嵌（检索侧）、AI 驱动的自动建模 → 生成侧（建模）），第六行来自「与 RAG / 向量库 / GraphRAG 的结合」，按机制归入生成侧（供给）。分成两行评级的是「引擎内嵌」与「生成侧」两族，但两族分行的依据不同：**「引擎内嵌」**的依据是族内两个子方向的 ③ 不同——优化侧的建议语义在这些版本间稳定，检索侧的索引参数与召回行为则随版本演进；**「生成侧」**两行的 ③ 同为「不满足」，分行依据是两行出处不同（一行来自「AI 驱动的自动建模」方向行，一行来自 RAG / GraphRAG 结合条目），两行的行动建议也不同。至于「自治数仓」这类合并叙事，不单列一行：它按其组成部分（自动建模 L3 + 自动优化 L2）取最弱项，见 5.1 落点表与 5.5 第 3 条。

| 演进方向（族内子方向） | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **取数侧**：自然语言查询（NL2SQL / Text-to-SQL、Schema Linking、结果自然语言化） | L2 | ① 满足：各产品的官方文档与 release note 可核验（Snowflake Cortex Analyst、Databricks Genie、阿里云通义数智、百度数据 BI 一类）；② 不满足：公开案例多为厂商发布的客户自述；③ 不满足：同一问题在不同版本上可能给出不同 SQL，口径也随之不同 | 只对已进语义层的指标开放自然语言入口；保留「生成的 SQL 与命中的表回显给人看」这一步 |

| **生成侧（建模）**：AI 驱动的自动建模（Auto-Modeling：DataWorks AutoModel、Databricks Assistant 一类） | L3 | ① 不满足：可核验的是助手类功能，行为随版本大幅变化，没有把「生成结构」作为能力项发布；② 不满足；③ 不满足 | 只把生成结果当草稿，建模结论由人签字 |
| **生成侧（供给）**：数仓增强 RAG / GraphRAG 上游（结构化事实层、OneID 作为实体层） | L3 | ① 不满足：可核到的是能力描述与方案性文章，不是「数仓向检索链路供事实」的能力项；② 不满足；③ 不满足 | 记录；先把 OneID 与字段级血缘做扎实，不要为它预留存储与链路 |

**本节没有一行达到 L1。** 四行 L2 全部卡在同一条判据上：② 拿不出。其中「引擎内嵌（优化侧）」这一行的 ①③ 最干净（自动优化在云数仓里已 GA 多年、建议语义稳定），「引擎内嵌（检索侧）」这一行还额外差在 ③（索引参数与召回行为随版本演进）；「取数侧」与「口径侧」的 ① 清楚、③ 有缺口，② 同样拿不出。本节能确认的是**机制存在、接口可用**，不能确认的是**别人用了多久、错了多少、付了什么代价**。

三类「前沿」的判别动作可以压成三句话——**拿到任何一条说法，先问它属于哪一类，再问这一类独有的那个问题**：

| 清单里的说法 | 它其实是 | 该问的问题 |
| --- | --- | --- |
| 「某数仓内置了向量检索」 | 引擎内嵌的算子（L2） | 索引类型与可调参数是什么？召回目标与重建成本谁负责？ |
| 「用自然语言就能问数」 | 接口形态的改变（L2） | 生成的 SQL 会不会回显给人看？口径从哪里来？ |
| 「AI 自动建模 / 自治数仓」 | 助手类功能 + 自动动作（L3） | 产出物是草稿还是直接落地？自动动作能不能撤销？ |

湖仓一体与实时数仓这两条常被放进「AI 时代演进」的清单里，但它们的机制与 AI 无关：前者改的是 §7.3.1 的取值（表状态的权威放在开放元数据里），后者改的是 §7.3.3 的取值（处理前移到事件到达时）。本节把它们放进 5.6 的预测行而不是方向行——**一个方向能不能算作「AI 前沿」，判据是 AI 是否改变了它的机制，而不是它的宣传材料里有没有出现 AI**。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式 release note 或版本化文档能不能找到？找不到 → L3。
2. 厂商与建设方之外的证据能不能找到？找不到 → L2。
3. 接口明年会不会变（索引参数、生成行为、指标定义格式）？会变 → 至多 L2。

第 3 句在本主题特别容易失手：**同一个能力名字在不同引擎里指的不是同一个东西**。「Cortex」是一个托管 AI 能力族的名字，不是某一项具体功能；「向量检索」在各家的索引类型、参数与限制条件上并不通用。判定方法是查官方文档里那一项能力的名字、GA 标记与限制条件（区域、数据量上限、计费项），而不是看发布会材料或 benchmark 博客。

三个常见误判，排路线图时最容易踩：

- **把「引擎内置了向量类型」误当成「数仓变成了向量库」**：向量检索与关系查询在同一引擎里联合，解决的是「少一条双写链路」，不解决召回质量与权限一致性（5.2.4）。
- **把「自动优化」误当成「自治数仓」**：自动聚簇、自动物化擅长的是一再重复的 workload，形态一变就会拿旧决策去接新查询（5.5）。
- **把「自然语言能问数」误当成「自助分析到位」**：能不能问，取决于口径有没有被抽成定义；口径还在 SQL 里时，问得越顺，同名不同义暴露得越快（5.2.2）。

### 5.2 演进方向逐条拆解（核心节）

四族按「AI 站在链条的哪一段」排序：取数侧改的是人怎么问，口径侧改的是问题指向什么，引擎内嵌改的是引擎自己多出来的算子与建议，生成侧改的是模型产出什么、消费什么。四族的级别并不一致（取数侧、口径侧、引擎内嵌三族为 L2，生成侧为 L3），但有一条共同的性质：**AI 在这里是一个新的消费方与一个新的产出方，它没有改变数仓的存储与执行模型**。

六行的代价也有一条共同结构：**它们都不报错**。取数侧给出一段能跑的 SQL、口径侧给出一份自洽的定义、优化侧给出一个已执行的自动动作、检索侧给出一组看起来相关的候选、建模侧给出一份格式正确的草案、供给侧给出一份看似有据的回答——六者在出错时都只表现为「结果不对」，而不是「系统异常」。这决定了两件事：验收必须靠抽样复核（5.2.1–5.2.3 各有一条「自验方法」；5.2.4 的验收项是两侧权限是否对齐，见其失效条件），而责任必须提前指定（5.3 表）。

#### 5.2.1 取数侧：自然语言查询（NL2SQL / Text-to-SQL）

- **旧做法与它的卡点**：业务方要数，走「提需求 → 排期 → 分析师写 SQL → 交付」这条路。卡点不在 SQL 难写，而在**人是链条上的固定环节**：口径靠人记、SQL 靠人写、结果靠人解释，延迟以天计，而提问频率被这个延迟压住了——很多问题不是没人想问，是问一次的成本太高。第二处卡点是消费方资格：只有会 SQL 的人能直接取数，业务方永远隔一层。
- **AI 改变了什么机制**：把「业务问题 → 查询」这一步从人的翻译换成一次概率性生成（Schema Linking → SQL 生成 → 执行 → 结果自然语言化）。**注意这条改变的性质：它是接口改良，不是架构变化**。数据没有搬家，表状态还在原处（§7.3.1），存算组织没变（§7.3.2），就绪时机没变（§7.3.3）——变的只是消费方的门槛，从「会 SQL 的人」变成「会说业务话的人与程序」。
- **由此得到的**：因为入口语言从 SQL 变成自然语言，**所以**提问频率不再受 SQL 技能供给限制，取数的需求第一次能被完整看见（这也是它最容易被高估的地方：需求被看见不等于需求被满足）；**又因为** Agent 是程序而不是人，**所以**取数能被接进自动化流程，变成别的系统的一个步骤。接上语义层之后（5.2.2），生成空间会从「任意表与字段的组合」缩小到「指标名 + 维度 + 过滤条件」，语义错的概率随之下降——**这是本节唯一一条 AI 与既有机制叠加后产生的新性质**。
- **由此付出的**：生成是概率性的，「这次对」不蕴含「下次对」。错误还分两类：**语法错**（执行报错，当场可见，代价低）与**语义错**（SQL 能跑，但口径与业务理解不一致，结果看起来合理）——后者才是真正贵的，因为它绕过所有校验直接进决策，而决策方没有能力复核。所以工程上必须保留「生成的 SQL 与命中的表回显给人看」这一步；把自然语言入口当黑盒（只给结果），等于把语义错的暴露面留到决策现场。第二项代价与模型无关：**schema 越大、元数据越脏（同名表、废弃表、同义字段），生成准确率越低**——这是数仓的存量问题，不是模型问题，也只能靠数仓自己治理。第三项是权限：访问控制从表级被推到了问题级，同一句问题在不同权限的人那里必须得到不同的结果，行级权限必须在生成之前生效，而不是在结果返回时过滤。
- **证据与来源**：【公开】各产品的官方文档与 release note 可核验其能力边界与限制条件（Snowflake Cortex Analyst、Databricks Genie、阿里云通义数智、百度数据 BI 一类；是否 GA 与适用范围以官方文档当前版本为准）；生成到 SQL 的准确率有公开的跨库评测基准（Spider，EMNLP 2018；BIRD，2023）【公开】，但它们测的是**学术基准**，不含企业 schema 的脏元数据，不能当生产结论；公开的语义错率与第三方生产记录：无公开可核验来源。判定方法：拿你们自己的 20 个真实业务问题（其中至少 5 个是「口径最容易搞错」的）做一次盲测，看语义错率——不看演示。
- **成熟度**：**L2**（与 5.1 表「取数侧」行一致）。① 满足、② 不满足、③ 不满足（同一问题在不同版本上可能给出不同 SQL）。

把这条链路上的失败点摊开，可以看到「回显」为什么不是可选步骤：

```text
自然语言取数链路上的四类失败，以及它们何时暴露
   ① Schema Linking 选错表     → 语法可能仍然正确，但答的是另一个问题
                                 暴露时机：几乎不暴露（数字看起来合理）
   ② SQL 生成错（语法）        → 执行报错
                                 暴露时机：当场（代价最低）
   ③ 口径理解错（语义）        → SQL 能跑、结果合理、口径不是业务以为的那个
                                 暴露时机：进入决策之后（代价最高）
   ④ 权限与隔离错              → 结果里有不该看到的数据
                                 暴露时机：审计或事故之后（合规代价）

判定方法：把「生成的 SQL + 命中的表 + 引用的人数」回显出来，让提问的人自己确认
   能回显 ⇒ ② 当场消掉、③ 变成可复核、④ 可在生成前拦截
   不能回显 ⇒ 四类失败全部推到结果之后
```

- **失效条件**：当问题需要跨域口径判断（「这个数该不该含退款」）或涉及尚未进语义层的自定义计算时，入口会把这类问题也当成可生成的对象——SQL 能跑，但口径由模型即兴决定。此时正确的动作不是换模型，而是让入口显式拒答（返回「该口径未定义」），并把它变成语义层的待办项。
- **自验方法**：从最近三个月的取数需求里挑 20 个真实问题（其中至少 5 个是口径最容易搞错的），让入口生成 SQL，然后**不看结果、先看 SQL 与命中的表**，逐条判断它答的是不是那个问题。这一步测的是语义错率，也就是唯一值得关注的指标；只测「能不能跑通」，等于把语法错率当成绩效，而那恰好是最便宜的一类错误。

#### 5.2.2 口径侧：指标语义层 / Headless BI

- **旧做法与它的卡点**：口径写在 SQL 里、写在人的脑子里、写在文档里。卡点是变更成本与引用处数量成正比：一处口径改了，报表、模型、接口各有一份实现要跟着改，于是「只改报表、不改下游」成了默认选择，**同名不同义就是这么产生的**。主文件 §1.2 把「指标一致性」列为建设数仓的核心业务驱动之一，正是因为这一项卡点先于 AI 存在。
- **AI 改变了什么机制**：严格说，**这条机制不是 AI 带来的**——把口径从 SQL 里抽出来定义一次（MetricFlow、Cube、阿里云指标平台一类）在 LLM 之前就成立，它改的是 §7.3.4 那条维度上的取值。AI 改的是这条机制的**紧迫性**：机器消费方不会像人一样「看上下文猜口径」，它只能读定义（这正是 [§7.3.4](01-data-warehouse-section-7-sec7.md) 的判断）。所以在 LLM / Agent 阶段，语义层从「治理的加分项」变成「取数的前置条件」。
- **由此得到的**：因为语义层把口径抽出来定义一次，**所以**同一指标对 BI、AI 与外部接口呈现同一个值，「同名不同义」的概率不再随消费方数量上升；**又因为**机器消费方只能读定义，**所以**自然语言取数的准确率上限由语义层的覆盖度决定，而不是由模型能力决定——**AI 取数的天花板是元数据，不是模型**，这是本节最重要的一条因果。它有一个直接推论：把预算从「换更强的模型」挪到「把指标定义覆盖全」，收益更大且可验证。
- **由此付出的**：多出一层需要治理的资产：指标定义本身要版本化、要有 owner、变更时要能评估影响面（谁引用了它）；语义层的表达能力必须覆盖真实口径，**覆盖不到的地方会有人绕回去手写 SQL，形成第二套口径**——一旦发生，AI 会同时看到两套口径，而它没有能力分辨哪一套是权威；指标爆炸（每个业务方都要自己的口径）会让语义层从解决方案变成新的口径战场。还有一条容易忽略的代价：语义层一旦成为取数的唯一入口，它就进入了关键路径——语义层不可用时，连「查个数」都做不了，可用性目标要从 BI 的档次提到数据服务的档次。
- **证据与来源**：【公开】开源实现与产品文档可核验（MetricFlow、Cube 等，版本与 GA 时点以各自官方 release note 为准）；【公开】dbt 语义层与 MetricFlow 自 2023 年起随 dbt 版本发布，具体 GA 时点与版本请以 dbt 官方 release note 为准；机制层面的对照见 [§7.3.4](01-data-warehouse-section-7-sec7.md) 与主文件 §2.4；第三方（非厂商）公开生产案例：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「口径侧」行一致）。① 满足、② 不满足、③ 大体满足（定义格式稳定，但与 BI 的对接协议各家不同）。

语义层的价值可以按「变更一处口径要动几处」来量，这也是它唯一可被直接观察的收益：

| 语义在哪一层 | 谁能复用同一份口径 | 改一个口径要动几处 | AI 取数时的后果 |
| --- | --- | --- | --- |
| SQL 里（现状多数） | 只有读到这段 SQL 的人 | 每一处引用各一份（报表 / 模型 / 接口） | 模型只能猜表名与字段名，语义错无法前置拦截 |
| 指标定义里（语义层） | BI、AI、外部接口按同一份定义取数 | 一处定义，各消费方按版本生效 | 生成空间缩到「指标 + 维度 + 过滤」，语义错率随覆盖度下降 |

- **失效条件**：当只有一类消费方（BI）、指标数量在几十个以内、且变更极低频时，语义层的治理成本高于它解决的口径漂移成本——此时用代码评审保证口径一致更便宜。判据不是「语义层好不好」，而是**消费方类别数与指标变更频率**这两个数。
- **自验方法**：随机取三个常用指标，回答三个问题——它的定义文件在哪、owner 是谁、上一次变更影响了哪些下游。三个都答得出，语义层才算在运转；答不出任何一个，说明你拥有的是一张指标清单，而不是一层可治理的口径。

#### 5.2.3 引擎内嵌的 AI：查询优化与向量原生

- **旧做法与它的卡点**：慢查询靠 DBA 看日志手调（加索引、加物化视图、改分布键），经验难以复制且随人员流动丢失；语义检索（找「意思相近」的内容）则根本做不到——只能把非结构化数据搬到独立的向量库，于是数仓与向量库之间多出一条双写链路，还多出两套权限模型要人工对齐（§7.6 组合四的运维代价）。
- **AI 改变了什么机制**：两件事都是**把判断做进引擎**。优化侧：引擎用自己的统计信息与历史 workload 预测该建什么物化视图、该给什么分桶与聚簇，形态上分「只给建议」与「直接执行」两档。检索侧：把 embedding 类型与近似最近邻索引做进引擎本身，让「结构化过滤 + 相似度排序」在同一个查询里联合。注意 §7.3 的四条机制**一条都没有被改动**——变的是引擎自己多了一个算子，与一个建议的来源。
- **由此得到的**：因为向量索引与关系表在同一引擎里，**所以**「结构化过滤 + 语义相似」不再需要跨系统双写与结果拼装，一致性与失败面各少一层；**又因为**优化建议由引擎自己的统计信息产生，**所以**调优的第一稿不再完全依赖某个人的经验——但这是「多了一个来源」，不是「不再需要人」（5.5 第 3 条）。
- **由此付出的**：向量索引是**近似的**——召回率与索引参数、数据量、维度强相关，离开这些条件谈「毫秒级检索」没有意义，营销页上的无条件性能声称不能作为事实引用。索引要占存储、要随写入维护，而且**增量写入会持续改变索引质量**：这正是 §7.4 成本表里「AI 原生数仓」那一行的隐性成本——模型或数据更新后，索引会静默过期，需要重建。第二项代价是自动动作会过时：自动物化与自动聚簇擅长处理一再重复的 workload，一旦查询形态发生结构性变化（新上一类报表、某条链路从批转实时），旧的物化还在，只是没人命中。第三项是锁定加深：数据能搬走，但索引定义与调优语义不一定能搬走（§7.1 的「生态与锁定」判据）。存储增长还要纳入 [§3 反模式 4](01-data-warehouse-section-3-sec3.md) 提到的冷热分层（Hot / Warm / Cold / Archive）——**索引与 embedding 是增长最快的那一块**。
- **证据与来源**：【公开】云数仓的自动优化能力与向量检索能力均有公开产品文档与 release note（Snowflake 的 Cortex 系列与自动优化能力、BigQuery Vector Search、SingleStore 一类；判断是否 GA 的方法是查官方文档里该特性的 GA 标记与限制条件——区域可用性、数据量上限、计费项）；【公开】内嵌 OLAP 引擎的定位出自其演示论文（*DuckDB: an Embeddable Analytical Database*，SIGMOD 2019，Raasveldt & Mühleisen），判断某版本是否真的支持多机执行，看 release note 里有没有独立的多机组件；【公开】对象存储标准层定价 $0.023/GB-月（AWS S3 定价页 2024；单价随区域与计费项不同，以官方定价页当前版本为准）；公开的第三方生产案例：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「引擎内嵌（优化侧）」行：①③ 满足、② 不满足）；**L2**（「引擎内嵌（检索侧）」行：① 满足、② 不满足、③ 部分满足——索引参数与召回行为随版本演进）。

向量检索的这笔账值得算一次，因为它的成本结构常被误读：

【推算】设 1 亿行、每条 embedding 1024 维 float32：裸向量 = 10⁸ × 1024 × 4 B = 10⁸ × 4 KB = 4 × 10⁵ MB ≈ 400 GB（十进制口径，1 MB = 10⁶ B）；按对象存储标准层 $0.023/GB-月【公开，AWS S3 定价页 2024】折算，裸向量一项 ≈ 400 × $0.023 ≈ **每月 9 美元上下**。链路只有乘法，读者可复算。结论是反直觉的：**向量存储本身几乎不花钱**，真正的成本在三处——图索引的邻居表在查询时要常驻内存【经验：每条几十到几百字节量级，远小于裸向量】，重建索引时的一次全量重算（换模型或维度变更时无法增量），以及为维持召回率而长期保留的算力。所以「向量进数仓能省多少钱」这个问题问错了，该问的是**重建一次索引要多久、要花多少算力**。

- **失效条件**：当查询形态本身变化很快（探索式分析、临时报表占多数）时，自动优化没有足够重复样本可学，建议与自动动作的收益都会归零，只剩下存储与常驻内存的开销；同理，当非结构化数据量不大时，独立向量库或单机索引的成本低于把索引做进数仓——**这个阈值取决于条目数与查询并发，而不是取决于「架构是否先进」**。
- **自验方法**：把上一次换 embedding 模型（或改维度）的过程复盘一遍：索引重建花了多久、期间检索是否可用、下游有没有感知。答不出这三件事，说明索引的运维成本还没有进入你的容量规划——而这正是它最容易静默变贵的地方。

#### 5.2.4 生成侧：AI 自动建模与「数仓增强 RAG / GraphRAG 上游」

- **旧做法与它的卡点**：建模靠人——按四步法（选定业务过程 → 声明粒度 → 确定维度 → 确定事实）逐张设计，并用总线架构保证一致性维度跨域共享；卡点是**起草是纯人力**且质量依赖少数人的经验。另一侧的卡点更根本：LLM 需要「事实」时只能用 RAG 检索非结构化文档，而企业里最硬的事实——订单、用户、产品——躺在数仓里，不在检索范围内，于是模型只能靠文档猜。
- **AI 改变了什么机制**：自动建模让 LLM 从业务描述产出模型草案，**替换的是第一稿的写作，不是建模的判断**——粒度、一致性维度、总线架构这些判断没有变，也没有被模型接管。数仓增强 RAG 改的是检索链路的输入：把 DWD / DWS（结构化事实层）与 OneID（实体层）接进来，形成「实体识别 → 数仓查事实 + 向量检索文档 → LLM 综合回答」。GraphRAG 则要求先有实体-关系图，而数仓的 OneID 与维度建模正好是这张图的上游。
- **由此得到的**：因为第一稿可以由模型产出，**所以**建模的起点从一张空白表变成一份可评审的草案，人只做删减与确认；**又因为**结构化事实能被检索链路调用，**所以**回答里第一次能出现「你上一张订单的金额是 X」这类只有数仓能给的事实，而不是模型从文档里推断——这是「数仓增强 RAG」相对普通 RAG 的全部价值所在。但要注意后一条的边界：这条链路的**价值来自数仓，代价也来自数仓**——凡是让模型产出第一稿的用法（起草结构、起草 SQL），都会把瓶颈从「生成」转移到「评审」，而评审能力不会随生成量线性增长。
- **由此付出的**：自动建模的产出是草案——它不知道你的粒度约束与一致性维度，直接把输出当模型用，会把「同名不同义」从 SQL 层带到模型层，而且更难发现（模型层的同名不同义不报错、只让效果变差）。数仓增强 RAG 的代价落在链路上：一次问答要同时打数仓与向量库，链路变长、失败面变多——数仓超时、权限拒绝、主键对不上时由谁降级，必须在设计时定下来；更危险的是**实体识别一旦错了，后面查到的「事实」会全部张冠李戴**，而错误看起来很具体（有数字、有订单号），最难被怀疑。GraphRAG 上游最难的部分不是图算法，而是**实体同一性**（同一个人在不同系统里的不同 ID），这正是 OneID 在做的事，无法用「接一个图谱库」替代。最后一条是权限：向量库的召回可能绕过数仓的行级权限，两侧权限模型必须对齐（§7.6 组合四）。
- **证据与来源**：自动建模目前可核到的是厂商的助手类功能（DataWorks AutoModel、Databricks Assistant 一类），行为随版本变化，且产出物是草稿还是直接落地需要查文档确认；数仓增强 RAG 与 GraphRAG 上游可核到的是产品能力描述与方案性文章（Snowflake Cortex Search、Databricks Vector Search、阿里云 Hologres + 通义 LLM 一类）；公开的第三方生产记录（含失败率）：无公开可核验来源。
- **成熟度**：**L3**（与 5.1 表「生成侧（建模）」行：① 不满足、② 不满足、③ 不满足）；**L3**（「生成侧（供给）」行：① 不满足、② 不满足、③ 不满足）。两行级别相同但行动建议不同：**模型产出草稿现在就可以用（人要签字），为 GraphRAG 预留链路不要做**。

数仓增强 RAG 的价值全在「事实来自数仓」这一句上，所以它必须逐段写出失败时给什么：

```text
数仓增强 RAG 的链路，以及每一段失败由谁降级
   用户问题
     → ① 实体识别（谁是「我」、哪一张订单）  失败：整条链路张冠李戴 → 应用侧判「识别不置信则先追问」
     → ② 数仓查结构化事实（点查 / 小范围聚合） 失败：超时或权限拒绝 → 降级为只答文档部分，并显式说明
     → ③ 向量检索文档（语义相似）            失败：空召回 → 降级为结构化事实，并明示「没找到相关文档」
     → ④ LLM 综合回答                        失败：把 ②③ 的结论编造出去 → 必须回显引用来源（订单号 / 文档片段）
   ────────────────────────────────────────────────
   关键：每一段都要有「失败时给什么」，而不是「失败时再说」
         没有降级路径的链路，第一次超时就会退化成「模型凭文档猜」
```

- **失效条件**：当结构化事实与文档两侧的权限模型不一致时（数仓有行级权限，向量库常只有集合级隔离），跨两侧的问答会绕过数仓的权限边界；此时要么把权限校验提到检索之前，要么把两侧的可见范围对齐。这一条不是优化项，是上线前置条件。

### 5.3 与本主题既有栈的接口在哪

数仓提供的是**事实与口径**，AI 相关内容都挂在它周边的接口上。下表写清谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Agent / BI ↔ 指标语义层 | 指标名 + 维度 + 过滤 → 返回指标值与口径版本号；不传 SQL | 语义层：查不到指标时必须报「无此指标」，不能降级成猜表 | 语义层本身可自建；版本化与影响面评估多数团队未建（L2） |
| Agent ↔ 数仓引擎（自然语言入口） | 自然语言 → 生成的 SQL（必须回显）→ 结果 | 生成方；语义错的暴露面在决策现场 | L2；回显是唯一可用的降错手段（5.2.1） |
| 数仓 ↔ 向量索引（同引擎内） | 结构化过滤 + 近邻排序在同一查询；embedding 由谁产出必须明确 | 应用侧负责召回目标；引擎负责索引维护与重建 | L2；索引参数与召回行为随版本演进 |
| 数仓 DWD / DWS ↔ 检索链路（数仓增强 RAG） | 以实体 ID 为参数的点查 / 小范围聚合，返回结构化事实 | 实体识别错则整条链路错——归因点在实体层（OneID），不在检索 | L3 |
| 查询优化 Advisor ↔ 变更流程 | 建议（建物化视图 / 改分桶 / 加聚簇）→ 人工确认后进变更 | 人负责：自动动作与 workload 变化之间的错配由容量规划承担 | L2 |
| 建模助手 ↔ 建模流程 | 草案（表 / 字段 / 关系）→ 人评审签字后进总线架构 | 人负责：粒度与一致性维度的判断不能外包 | L3 |
| 指标语义层 ↔ 血缘与质量系统 | 指标定义引用上游表与字段；变更时按引用关系算影响面 | 语义层与血缘系统共同负责；覆盖不到的引用由人工兜底 | L2；影响面评估多数团队需自建 |
| 特征与训练样本 ↔ 数仓 DWD / DWS | 按快照导出或按分区读取；口径一旦变更，下游样本随之改变 | 数仓侧负责口径变更的通知与影响面评估 | 需自建：训练样本的版本要能追回数仓的快照 |

这张表里只有两行是「有现成件可用」：一是优化建议的来源（引擎自带），二是向量索引的承载（引擎自带）。其余几行都要自建或自测，而且失败几乎都落在数据平台之外——实体识别归主数据团队，召回目标归应用团队，建模签字归业务方。把它写进接口表的用处不是分工好看，而是**事故发生时不必现场决定谁负责**；如果这张表在你们那里画不出来，说明这些接口还没有人认领。

**判定这张表有没有被用起来**：每个季度核两个数——这一季有多少次 AI 取数在回显环节被人纠错（说明回显在起作用），以及语义层里有多少指标被 AI 或外部接口实际调用过（说明口径层真的成了入口）。两个数都是零，说明 AI 取数还停在演示阶段。

这张表还有一条共同的记账规则：**AI 侧新增的每一行，都对应一个「谁在它出错时兜底」的问题**。引擎内嵌的算子由引擎兜底（它至少会报错），而语义层、实体识别、检索路由这三处**出错时不会报错，只会给出看起来合理的结果**，所以它们的兜底人必须提前指定。这就是本节把「谁负责失败」单列成一列的原因——它是这张表里唯一无法靠技术选型解决的部分。

### 5.4 公开进展与文献

- **论文与一手设计文档**【公开】：DuckDB 的演示论文（*DuckDB: an Embeddable Analytical Database*，SIGMOD 2019，Raasveldt & Mühleisen）给出内嵌 OLAP 引擎的定位与向量化执行；Snowflake 的存算分离与多租户弹性有公开的系统性描述（该公司在 SIGMOD 2016 发表的《The Snowflake Elastic Data Warehouse》是这一架构最早的一手材料，后续演进以官方文档为准）；Apache Paimon 的表格式设计文档（流式表格式 + LSM 结构，1.0 于 2024 年发布，承载「数据就绪时机」里的 upsert 与 changelog）。凡涉及「某引擎某版本支持某执行模式」的判断，一律查该版本 release note 与官方文档，不看 benchmark 博客。
- **官方 release note / 产品文档（判据 ① 的核验入口）**【公开】：云数仓的 AI 能力入口——Snowflake 的 Cortex 系列（对话式分析、向量检索）、Databricks 的助手与 Unity Catalog、BigQuery 的向量检索、阿里云 Hologres 与通义系列的组合。**判断「是否已 GA」的方法**：在这些产品的官方文档里找到该特性的 GA 标记与限制条件（区域可用性、数据量上限、计费项），而不是看发布会材料。指标语义层同样以官方 release note 为准（MetricFlow / Cube 一类，版本与 GA 时点由各自官方发布说明定义）。
- **第三方（非厂商）公开生产案例**：无公开可核验来源——这是本节没有 L1 行的直接原因。要把它变成 L1，需要一份由使用方自述、且给出失败率与降级路径的公开记录（例如某团队公开其自然语言取数的语义错率与纠错流程），并能被第三方按同一口径复核。
- **值得注意的空白**：公开材料里能查到「某产品具备某 AI 能力」，查不到「这类能力在生产里的准确率下限」。这不是因为它们不重要，而是因为数仓侧的效果高度依赖元数据质量（口径覆盖度、表注释、血缘），换一个团队结论就不同。它同时意味着：**这项判断只能自己测**。与此相关的一条取舍：本节的文献清单宁可短，只保留能给出**可检索到的标题或文档名 + 年份**的条目；凡是只能给到「厂商名 + 会议名 + 年份」的，一律改按官方文档核验，或直接不列——因为读者据一个定位不到的名字去查，只会得到一堆二手解读。
- **引用方式的调整**：Snowflake 论文（SIGMOD 2024）与 StarRocks 论文（SIGMOD 2024）两条，本节不再按「论文」引用——它们只给到厂商名、会议名与年份，给不出可检索到的论文标题，读者据此定位不到那一篇。本节的处理是：存算分离改用可定位的一手材料（Snowflake 在 SIGMOD 2016 发表的《The Snowflake Elastic Data Warehouse》）；而 StarRocks 论文列的三项（向量化执行、CBO、Pipeline 执行引擎）属既有引擎机制，与「AI 是否改变了机制」这一判据无关，**本节不再保留该条目**——StarRocks 的产品侧内容见 5.1 落点表的 AI Advisor 与 3.x 存算分离两行；Apache Paimon 一条保留，但改按官方文档核验（流式表格式与 1.0 发布说明，2024）。判定方法是自己按标题检索一次——检索不到，就不要把它写进架构假设。
- **产品与版本的锚定方式**：Databricks Data Intelligence Platform（2024）、Snowflake Cortex（2024）、阿里云通义数智（2024）、SelectDB Cloud（2024）、StarRocks 3.x 的存算分离（2024–2025）这类条目，本节只记「产品名 + 年份」，不锚定版本号与 GA 日期——同一产品在不同版本里的状态不同，写错比省略更贵。核验时以各产品官方文档当前版本为准，并优先看该能力的限制条件而不是它出现在哪一年的材料里。
- **引用纪律**：本节涉及的产品与版本迭代快，最容易出错的三类引用是——

| 引用类型 | 常见错误 | 核验方式 |
| --- | --- | --- |
| 「某引擎某版本支持某执行模式」 | 把路线图写成语态完成的既成事实 | 查该版本 release note 与官方文档里的 GA 标记 |
| 「某能力在某数仓上可用」 | 把单机内嵌引擎的能力说成分布式，或把产品族名当成单一能力 | 查该能力的文档页面与限制条件；产品族名下各子能力分别核 |
| 「某方案让查询快 X 倍」 | 用没有条件限定语（数据量 / 维度 / 召回目标 / 硬件）的性能声称 | 看基准是否给出数据量、并发、硬件与复现脚本 |

### 5.5 被过度宣传的部分

**「自然语言取数的准确率已经可以支撑自助分析」**

- *实际是什么*：演示里的问题落在少数几张干净的宽表上，而真实数仓里同名表、同义字段、废弃表并存，schema 越大越难；错误还分语法错与语义错，后者能通过执行、结果看起来合理，绕过全部校验直接进决策。
- *为什么会这样*：模型在候选表上做的是统计选择，缺少「这张表还能不能用」的元数据；口径又没有被抽成机器可读的定义（5.2.2）。
- *什么时候它才会成真*：语义层覆盖了主要指标、且表注释 / owner / 质量分 / 血缘这些元数据机器可读之后，生成空间被缩小到「指标 + 维度 + 过滤」。判定方法是 5.2.1 的盲测，不是看演示。

**「向量检索让数仓获得了毫秒级语义搜索」**

- *实际是什么*：近似检索。召回率由索引参数、数据量、维度共同决定，离开这些条件谈延迟没有意义；增量写入还会持续改变索引质量。
- *为什么会这样*：性能数字通常不写召回目标与硬件；而「毫秒」这个词描述的是索引命中之后的那一段，不包含重建索引与权限校验。
- *什么时候它才会成真*：性能声称带上四个条件（数据量、维度、召回目标、硬件），并能按官方文档复现基准时。在此之前，它只能作为候选生成器使用——**候选人由相似度给，最终判断由结构化条件与业务规则给**。

**「自治数仓（Self-Driving DW）已经可以无人调优」**

- *实际是什么*：自动动作加人的容量判断。自动物化与自动聚簇擅长处理一再重复的 workload；查询形态一旦结构性变化，旧的自动决策会变成没人命中的过时物化。
- *为什么会这样*：优化器的统计信息描述的是过去；自动动作的收益与代价（存储、刷新窗口）要由成本模型承担，而引擎不知道你的成本结构（§7.4 逐候选列出「主导项」，即这份成本随什么增长）。
- *什么时候它才会成真*：自动动作能与成本预算绑定，并在 workload 发生结构性变化时主动撤销——目前这一步仍是人的工作。

这三条有一个共同结构：它们都把「机制已经就位」说成「能力已经就位」。引擎内嵌的算子与语义层的定义格式确实已经就位，但「就位」指的是**能力存在**，不是**效果可证**。所以判断它们何时成真的办法是同一个——看公开文档里有没有出现可核验的判断依据（GA 标记与限制条件、召回参数、自动动作的撤销能力），而不是看产品页上有没有多一个带 AI 的名字。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| **指标语义层成为数仓标配** | 主流数仓与 BI 产品把指标定义做成一等对象（独立定义文件、版本、owner），且 AI 取数入口默认走语义层 | 自然语言入口继续直接对物理表开放，语义层仍是少数团队的加建 |
| 实时数仓成为新建链路的默认形态，离线只留给超大规模历史与成本敏感场景 | 新建链路默认「流式入湖 + OLAP」，批窗口主要承担回填与重算 | 多数新建链路仍以 T+1 批为主，实时按单点需求加建——常驻流作业的成本是它不会默认化的原因（§7.4 账四） |
| 湖仓一体继续收敛：数仓与湖的分界从「选哪个产品」变成「同一份表被哪些引擎读」 | 跨引擎原生读写同一份表成为默认能力，选型问题退化为「谁要读这张表」 | 各引擎继续用私有表状态换性能，跨引擎读取仍要靠导出 |
| 自治数仓停在「建议 + 自动动作」这一档，3–5 年内到不了无人调优 | 出现按成本预算自动上线 / 撤销物化、并在 workload 结构性变化后自动回退的公开能力 | 出现不依赖人的容量判断、且能自动撤销既有物化的公开生产案例 |

四条预测都能靠**公开文档**证实或证伪，不需要内部数据：

- 第 1 条看产品文档里指标定义是不是一等对象，一到两年见分晓。
- 第 2 条看新建链路的默认形态与常驻流作业的计费方式，两到三年。
- 第 3 条看跨引擎原生读写的默认支持程度，两到三年。
- 第 4 条看自动动作有没有撤销机制与成本预算绑定，三到五年。

第 2 条（实时数仓成为默认形态）与第 3 条（湖仓一体收敛）都是**与 AI 无关的架构预测**，放在这里是因为它们决定了 AI 相关能力的落点：数据在哪一侧、以什么形态被读，直接决定语义层与检索链路挂在哪里。把这两条与 AI 方向分开评估，可以避免一种常见错误——**用一条与 AI 无关的架构演进，去支撑一个 AI 相关的采购决策**。

最值得先盯的是第 1 条：它是本节唯一一条**不依赖任何新模型发布**就能观察到的信号，也是把「AI 原生数仓」从叙事变成能力的那一步——**没有机器可读的口径，模型只能在表名与字段名上做统计式的猜测**。

第 4 条（自治数仓）则相反：它是本节里最容易被当成能力采购、又最难被证伪的一条。判断它是否推进，看的不是「自动优化又多了几个动作」，而是**动作能不能被撤销、能不能与成本预算绑定**这两件机制上的事；只要这两件没出现，自动动作就仍属于「建议」，属于第 3 条的范畴，而不是自治。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 业务方天天要数、分析师排队（没有语义层） | 先建一个域的指标语义层（定义 + owner + 版本），把自然语言入口挂到它上面（5.2.2） | 主流产品是否把指标定义做成一等对象 | 不要先上「对全库的自然语言问数」——会先撞上同名不同义与废弃表 |
| 已有语义层，想接 AI 取数 | 给语义层加机器可读的口径与版本号；限定 Agent 只能调指标 API，不能直接对物理表生成 SQL | 是否出现跨引擎的语义标准 | 不要让生成式入口直连生产库并跳过回显（5.2.1） |
| 慢查询多、调优靠人 | 用引擎自带的建议做人工确认的变更，并记录每次变更的收益 | 自动动作能否与成本预算绑定、能否撤销 | 不要指望自动物化解决「查询形态刚变」的问题——它会拿旧 workload 的物化去接新查询 |
| 想给数仓加语义检索 | 先定召回目标与降级路径（检索不可用时退回关键字 / 结构化过滤），并明确 embedding 的产出方 | 增量写入下召回率是否稳定、重建一次索引要多久 | 不要把无条件限定的性能数字写进容量规划（数据量、维度、召回、硬件四个条件缺一不可） |
| 在规划 GraphRAG / 多模态 | 先把 OneID（实体同一性）与字段级血缘做扎实（5.2.4） | 实体消解是否出现可交换的标识 | 不要为一个还在 L3 的方案预留存储与链路——按需增建比预留便宜 |

「明确不要做」那一列的共用逻辑只有一句：**AI 在这里的作用是「多了一个消费方与一个产出方」，不是新的存储或执行模型**。所以预算该投在语义层、元数据质量与回显 / 降级路径这三件确定性工程上；在它们定下来之前，任何「自治数仓」「AI 原生数仓」的选型都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先做语义层的一个域**：把最常被问、最容易被记错的那批指标定义出来，配 owner 与版本。它同时是 AI 取数的前置条件。
2. **再治元数据**：表注释、废弃标记、字段单位与血缘。生成式取数的准确率上限由它决定，且这项工作与模型换代无关。
3. **然后接入口，并强制回显**：自然语言入口只对语义层开放；生成的 SQL、命中的表、引用的人数必须回显给人确认。
4. **最后才谈向量与自治**：向量索引与自动动作都会带来「随写入变化、需重建 / 需撤销」的运维面，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新的模型能力——指标定义、元数据治理、回显与降级路径，全是工程与流程，也全是可以在现有引擎上完成的。这也解释了本节为什么没有 L1：引擎内嵌的那部分（自动优化、向量索引）已经就位，但它**不改变数仓的架构**，所以不需要被宣传；而需要被宣传的那部分（自治数仓、自动建模、GraphRAG 上游）还没有成熟到能被第三方核验。真正决定 AI 取数能走多远的，是语义层与元数据这两件不出现在发布会上的工作。

### 5.8 小结

> 本节小结：数仓这一侧，AI 真正改变的是三件事——**消费方是谁**（取数入口从 SQL 变成自然语言，这是接口形态的改变，不是存储与执行模型的改变）、**语义的紧迫性**（§7.3.4 那条维度从一个选项变成取数的前置条件，5.2.2），以及**引擎自己多出来的算子与建议来源**（向量索引、自动优化，5.2.3）；§7.3 的四条机制里前三条一条都没有被改动，第 4 条的取值变化本身不是 AI 带来的（把口径抽出来定义在 LLM 之前就成立），它变的只是紧迫性。也没有改变的是「语义错比语法错贵」这件事。所以本节没有 L1 方向：能排进路线图的是「语义层 + 元数据治理 + 回显与降级」，而不是「对全库的自然语言问数」。
>
> 💡 **思考锚点**：用 5.1 的「按机制分族、级别取族内最弱子项」规则过一遍你手上的 AI 取数路线图——如果它同时挂了「引擎内嵌（检索侧）」的向量检索与「取数侧」的自然语言入口，这条链路整体该按 L2 还是 L3 对待？再按 5.7 的次序，这两行的前置（语义层的一个域 + 元数据治理）你打算先补哪一个？
