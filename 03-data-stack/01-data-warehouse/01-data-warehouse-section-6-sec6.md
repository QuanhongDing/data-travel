### 1.1 阿里巴巴"**集团 MaxCompute 5 套→1 套 + 100 万企业客户**"10+ 年（2014-2024）

**背景（Why）**

阿里 2014 年面临**集团级数仓失控**：
- **25 BU 各自一套数仓**——淘宝 / 天猫 / 支付宝 / 菜鸟 / 盒马，**存储算力 5 倍浪费**
- **口径分裂**——同指标 5 套定义，**大促复盘会吵 30 分钟口径**
- **跨 BU 不可分析**——同一用户 5 个 ID，**「天猫用户用盒马的比例」答不上**

**触发点（What）**

2014 年阿里推出**集团 MaxCompute**（[阿里 MaxCompute 2014]），目标四条：
- **5 套 → 1 套**（物理收敛）
- **OneID 覆盖 95%+**
- **指标一致性 95%**
- **100 万企业云客户**（对外输出）

**详细做法（How）**

阿里 MaxCompute 的**5 大核心组件**：

1. **MaxCompute 离线数仓（核心创新）**
   - 关键设计：**自研 PB 级 SQL 引擎 + 存储计算分离**
   - 关键能力：**EB 级数据上 SQL 跑得动**
   - 关键数字：**存储 EB 级**、**SQL 10 万+/天**
   - 关键示意：
     ```sql
     -- MaxCompute（类 SQL 语法）跨 25 BU 联邦查询
     SELECT a.user_id, b.usage_count
     FROM tmall.user_behavior a
     JOIN alipay.financial_event b
       ON a.user_id = b.user_id  -- OneID 打通后可直接 join
     WHERE a.ds = '2024-01-01'
       AND b.ds = '2024-01-01';
     ```

2. **DataWorks 一体化平台（核心）**
   - 关键设计：**开发 / 调度 / 运维 / 治理 集成**
   - 关键能力：**25 BU 在同平台协作**
   - 关键数字：**日均调度任务百万级**

3. **OneID 用户打通（核心）**
   - 关键设计：**手机号 + 设备指纹 + 行为**
   - 关键能力：**跨 BU 用户归并**
   - 关键数字：**覆盖率 70% → 95%+**

4. **指标平台（核心）**
   - 关键设计：**指标定义中心 + OSCAR 五要素**
   - 关键能力：**口径统一**
   - 关键数字：**一致性 95%**

5. **OneService 数据服务（核心创新）**
   - 关键设计：**统一 API 网关对外**
   - 关键能力：**业务自助取数**
   - 关键数字：**100 万企业云客户**

**阿里 MaxCompute 关键数字**（[阿里 MaxCompute 2014-2024 公开数据]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **数仓数量** | 5 套 | 1 套 | **-80%** |
| **存储成本** | 基线 | -80% | **-80%** |
| **指标一致性** | 60% | 95% | **+58%** |
| **OneID 覆盖** | 70% | 95%+ | **+36%** |
| **新业务接入** | 6 个月 | 6 周 | **-75%** |
| **企业客户** | 0 | 100 万+ | **∞** |
| **MaxCompute / DataWorks** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：阿里数据中台 1000+ 人
- 关键数字：**EB 级存储**；**5 套→1 套**；**100 万企业云客户**
- 业务影响：覆盖**阿里全集团 25 BU + 100 万企业**

**失败教训**

- 早期「**5 套数仓**」——5 套 ID、5 套指标，倒逼 5 套→1 套
- **先建数仓后建 OneID**——没有 OneID 时 5 套数仓 join 不起来；正解是**「OneID 与数仓同步」**
- **指标定义只发文档**——落地率不到 30%，后改为**「指标平台 + 强校验」**

### 1.2 Netflix"**Iceberg EB 级数据湖**"5+ 年（2019-2024）

**背景（Why）**

Netflix 2019 年面临**EB 级数据湖的元数据瓶颈**：
- **PB → EB 级**数据增长
- **传统 Hive Metastore**——**单点 + 不支持 schema evolution**
- **分钟级分区**——**元数据量爆炸**

**触发点（What）**

2019 年 Netflix 推出 **Iceberg**（[Netflix Iceberg 2019]），目标：
- **EB 级数据湖**
- **隐藏分区**——查询不写分区
- **Schema 演进零成本**

**详细做法（How）**

Netflix Iceberg 的**5 大核心组件**：

1. **Iceberg 表格式（核心创新）**
   - 关键设计：**元数据分层**（metadata + manifest + data file）
   - 关键能力：**支持亿级文件**、**ACID 事务**
   - 关键数字：**EB 级数据 + 分钟级分区**

2. **Spark / Flink 集成（核心）**
   - 关键设计：**主流计算引擎全部支持**
   - 关键能力：**一表多引擎**
   - 关键数字：**Spark + Flink + Trino 100% 兼容**

3. **Trino 查询（核心）**
   - 关键设计：**隐藏分区** + **分区裁剪**
   - 关键能力：**查询性能 10x 提升**
   - 关键数字：**查询 P99 < 5s**

4. **S3 存储（核心）**
   - 关键设计：**列存 + Parquet + 压缩**
   - 关键能力：**EB 级可扩容**
   - 关键数字：**EB 级**

5. **元数据服务（核心创新）**
   - 关键设计：**独立高可用元数据服务**——支持百万级分区
   - 关键能力：**元数据查询 P99 < 100ms**
   - 关键数字：**支持 100+ 数据域**

**Netflix Iceberg 关键数字**（[Netflix Iceberg 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **数据规模** | PB | EB | **+1000x** |
| **元数据查询 P99** | 秒级 | < 100ms | **-95%** |
| **Schema 演进** | 复杂 | 零成本 | **—** |
| **查询性能** | 基线 | 10x | **+10x** |
| **EB 级支持** | 不可用 | 100% | **∞** |
| **一表多引擎** | 不可用 | 100% | **∞** |
| **ACID 事务** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：Netflix 数据平台 500+ 人
- 关键数字：**EB 级数据**；**元数据 P99 < 100ms**；**2 亿+ 用户**
- 业务影响：覆盖**Netflix 全球 2 亿+ 用户**

**失败教训**

- 早期「**Hive Metastore 单点**」——大数据下元数据变成瓶颈，倒逼 Iceberg 元数据分层
- **分区爆炸**——分钟级分区导致**元数据 10 亿行**，Hive 扛不住；Iceberg 隐藏分区解决
- **Schema 演进难**——列改名 / 类型改全表重写；Iceberg 的 schema evolution 真正零成本

### 1.3 字节跳动"**Lakehouse + 多业务**"4+ 年（2020-2024）

**背景（Why)**

字节 2020 年面临**多业务数仓分裂**：
- **抖音 / TikTok / 西瓜 / 今日头条**——**四套数据湖 + 四套数仓**
- **数据冗余**——**同一份数据湖存 4 份**
- **口径分裂**——跨业务对账耗人力

**触发点（What)**

2020 年字节启动 **Lakehouse**（[字节 2020]），目标：
- **多业务统一 Lakehouse**
- **数据 0 冗余**
- **口径 95% 统一**

**详细做法（How）**

字节 Lakehouse 的**5 大核心组件**：

1. **Lakehouse 架构（核心创新）**
   - 关键设计：**Iceberg 存数据 + StarRocks / ClickHouse 查数据**
   - 关键能力：**数据 0 冗余 + 多种查询引擎**
   - 关键数字：**存储 -40%**

2. **Iceberg 表格式（核心）**
   - 关键设计：**ACID + Schema 演进 + 隐藏分区**
   - 关键能力：**PB 级可扩容**
   - 关键数字：**PB 级**

3. **StarRocks / ClickHouse OLAP（核心）**
   - 关键设计：**OLAP 直接查 Iceberg**
   - 关键能力：**秒级查询 PB 级**
   - 关键数字：**查询 P99 < 3s**

4. **Spark / Flink 计算（核心）**
   - 关键设计：**一表多引擎**
   - 关键能力：**流批共用**
   - 关键数字：**统一计算**

5. **DataLeap 治理（核心创新）**
   - 关键设计：**统一模型管理 + 指标统一**
   - 关键能力：**25 BU 同平台**
   - 关键数字：**口径 95%**

**字节 Lakehouse 关键数字**（[字节 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **数据冗余** | 100% | 0% | **-100%** |
| **存储成本** | 基线 | -40% | **-40%** |
| **口径统一** | 60% | 95% | **+58%** |
| **查询 P99** | — | < 3s | **—** |
| **PB 级支持** | 不可用 | 100% | **∞** |
| **Iceberg / StarRocks** | 不可用 | 100% | **∞** |
| **一表多引擎** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：字节 Lakehouse 团队 100+ 人
- 关键数字：**数据 0 冗余 / 存储 -40%**；**口径 95%**；**PB 级**
- 业务影响：覆盖**字节全部业务**

**失败教训**

- 早期「**多业务数仓分裂**」——四套数据湖四套数仓，倒逼 Lakehouse
- **只做 Lakehouse 不做指标**——数据统一了指标还各写各的，**后补 OSCAR 五要素**
- **不治理就上线**——谁都能建表，**数据沼泽**；后强制 **DataLeap 统一入口**

### 1.4 腾讯"**TBDS 8 年大规模**"8+ 年（2016-2024）

**背景（Why)**

腾讯 2016 年面临**全集团数仓整合**：
- **微信 / QQ / 视频 / 游戏**——数仓各建各的

- **海量用户**——**微信 13 亿+**实时数据

**触发点（What）**

2016 年腾讯启动 **TBDS 大数据平台**（[腾讯 2016]），目标：
- **集团数仓整合**
- **多业务共用**——一次建模全集团用
- **实时 + 离线统一**

**详细做法（How）**

腾讯 TBDS 的**5 大核心组件**：

1. **TBDS 一站式平台（核心创新）**
   - 关键设计：**存储（HDFS + Iceberg）+ 计算（Spark + Flink + Trino）+ 调度 + 治理**

   - 关键数字：**覆盖 8+ 事业部**

2. **统一数仓（核心）**
   - 关键设计：**OneData + 多业务共用**
   - 关键能力：**一次建模全集团用**
   - 关键数字：**新业务接入 6 周**

3. **实时数仓（核心）**
   - 关键设计：**Flink + Kafka + Iceberg**
   - 关键能力：**秒级实时**
   - 关键数字：**延迟 < 5s**

4. **OLAP 引擎（核心）**
   - 关键设计：**Trino + ClickHouse 集群**
   - 关键能力：**PB 级秒级查询**
   - 关键数字：**查询 P99 < 3s**

5. **全场景覆盖（核心创新）**
   - 关键设计：**从推荐 / 金融 / 游戏到风控全场景**
   - 关键能力：**业务广覆盖**
   - 关键数字：**100+ 业务场景**

### 1.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**MaxCompute / Spark + Hive 起步**」（**最简单**）——**10+ 业务**
- 产出：**分层规范 + 命名规范 + OneData 文档**
- 团队：**2-3 人**
- 验证标准：**跨业务指标可对齐**、**接入周期 ≤ 1 个月**

**1 → 10 阶段：6-12 个月**

- 扩展到「**100+ 业务 / PB 级**」
- 引入「**Iceberg 表格式**」——schema 演进零成本
- 引入「**Trino 查询**」——跨源秒级
- 团队：5-10 人
- 验证标准：**新业务接入 ≤ 6 周**、**口径 ≥ 85%**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务 / EB 级**」
- 引入「**Lakehouse 架构**」——存储 0 冗余
- 引入「**实时 + 离线统一**」
- 团队：10-30 人
- 验证标准：**存储 -40%**、**口径 ≥ 95%**

**100 → 1000 阶段：12-24 个月**

- 引入「**5 套 → 1 套 / 集团统一数仓**」
- 引入「**EB 级元数据独立高可用**」
- 团队：30-100 人
- 验证标准：**元数据 P99 < 100ms**、**对外输出 100 万企业**

> **本节小结**：
> - 4 个真实案例（阿里 / Netflix / 字节 / 腾讯）印证：**数仓不是「**Hive + 离线 T+1**」，是「**MaxCompute / Iceberg / Lakehouse + OneData + 指标平台**」**5 件套**。
> - 关键时间线：阿里 10+ 年 / Netflix 5+ 年 / 字节 4+ 年 / 腾讯 8+ 年 —— **数仓是 4+ 年长期工程**。
> - 选型第一原则：「**MaxCompute / Spark 起步**」（**最简单**）——**10+ 业务** → 「**Iceberg + Trino**」（**必须**）→ 「**Lakehouse + 实时离线统一**」（**生产**）→ 「**集团 5 套→1 套 + EB 元数据**」（**AI 时代**）。
> - 99% 的失败来自「**5 套分裂 + 不治理 + 实时离线两套**」——必须有 **OneData 统一 + 强入口 + 同一定义两引擎**。
> - 真正的 ROI 来自「**存储 -40~80% + 接入 -75% + 100 万企业**」——是**大厂核心数仓基础设施的命脉**。
