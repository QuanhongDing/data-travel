### 6.1 阿里 OneData：从 5 套数据仓库到统一（2008-2014）

**背景（Why）**

阿里在 2008 年面临**数据仓库碎片化**问题：
- **5 套独立数仓**——淘宝 / 天猫 / 支付宝 / B2B / 一淘
- 每套数仓**独立指标定义**——**"GMV"在 5 套数仓有 5 个不同定义**
- **同业务跨部门对账**——**每天消耗数据团队 30% 时间**
- 当时阿里的**最大数据资产**——**EB 级订单 / 用户 / 商家数据**

**触发点（What）**

2008 年阿里启动「**OneData**」项目（来自 [阿里大数据之路 2013] 与 [DAMA 中国 2014 演讲]），目标是：
- **5 套数仓**合并成 **1 套**
- **全集团**指标**统一口径**
- **OneModel / OneID / OneService** 三位一体

**详细做法（How）**

OneData 的**核心方法论**（来自《大数据之路：阿里巴巴大数据实践》原书）：

1. **OneModel（公共数据模型）**
   - 关键设计：**数据分层**（ODS / DWD / DWS / ADS）+ **公共层**（DIM 公共维度表）
   - 关键能力：每张 DWS 表**全集团共享**——**避免重复计算**
   - 关键数字：阿里 **80%** DWS 表被 3+ 业务线共享
   - 关键代码：
     ```sql
     -- OneData 公共层示例（按主题域划分）
     -- 交易域
     dwd_trade_order   -- 订单明细
     dws_trade_user_1d -- 用户日交易汇总
     dws_trade_goods_1d -- 商品日交易汇总
     -- 用户域
     dim_user_info    -- 用户公共维度
     dws_user_1d       -- 用户日活 / 留存汇总
     ```

2. **OneID（统一 ID 体系）**
   - 关键设计：**每个人 / 商家 / 商品**有**全局唯一 ID**
   - 关键能力：跨业务线**打通用户画像**
   - 关键数字：阿里 **OneID 覆盖率 99.9%+**
   - 关键代码（ID Mapping）：
     ```sql
     -- OneID 映射表
     CREATE TABLE dim_user_id_mapping (
         user_id_taobao    BIGINT,  -- 淘宝 user_id
         user_id_tmall     BIGINT,  -- 天猫 user_id
         user_id_alipay    BIGINT,  -- 支付宝 user_id
         user_id_global    BIGINT,  -- 集团统一 user_id
         mapping_type      STRING   -- 强匹配 / 弱匹配 / 推断
     );
     -- ID Mapping 算法：弱匹配 (姓名 + 手机后 4 位) → 强匹配 (身份证后 6 位)
     ```

3. **OneService（统一数据服务）**
   - 关键设计：**统一 API 网关**——所有数据消费方**通过 API** 访问
   - 关键能力：**限流 / 鉴权 / 监控** 在 API 层
   - 关键工具：**阿里自研 TopLink**（HSF / Dubbo 风格 RPC）
   - 关键数字：阿里 **90% 数据消费通过 OneService**

**OneData 实施历程**：

| 阶段 | 时间 | 关键成果 |
| --- | --- | --- |
| 第 1 阶段：成立项目 | 2008 | OneModel 规范发布 |
| 第 2 阶段：核心业务 | 2009-2010 | 淘宝 / 天猫 公共层 |
| 第 3 阶段：全集团 | 2010-2012 | 支付宝 / B2B 接入 |
| 第 4 阶段：成熟 | 2012-2014 | 全集团 5 套数仓 → 1 套 |
| 第 5 阶段：商业化 | 2017-至今 | **DataWorks** 服务外部 |

**具体数字（How much）**

- 团队规模：阿里数据中台团队 100+ 人
- 关键数字（[阿里 2013 公开数据]）：
  - **5 套数仓 → 1 套数仓**（2014 完成）
  - **指标复用率 > 80%**
  - **新业务接入时间**：从 6 个月降到 **6 周**（**4 倍**）
  - **跨部门对账工时**：从每天 30% 降到 **5%**（**6 倍**）
- 业务影响：
  - 支撑阿里**所有业务**（淘宝 / 天猫 / 支付宝 / 闲鱼 / 钉钉 / 菜鸟）
  - 商业化后服务**100 万+ 企业**（DataWorks）

**失败教训**

- 第 1 阶段**OneID 算法**——**误匹配**（不同人匹配到同一 ID）——倒逼**人工抽查 + 强匹配阈值**
- **公共层过度抽象**——**新业务接入难**——倒逼**公共层 vs 业务层**分离（业务层可独立扩展）
- **指标治理**——**业务方抵触**（「**这是 IT 的 KPI**」）——倒逼**指标 Owner 制度**（业务方必须认领）
- **数据质量**——**重大活动出错**（双 11 数据延迟）——倒逼**实时数据质量监控 + 报警**

### 6.2 字节跳动 ByteLake：4 年湖仓演进（2018-2022）

**背景（Why）**

字节 2018 年面临**「**全公司一站式数据栈**」**需求：
- **抖音 / TikTok / 西瓜 / 今日头条**——**多业务线 + 海量数据**
- **数据量 800 亿事件/天**——**传统数仓**（Hive + Spark）**扛不住**
- **业务快速迭代**——**每条业务线**有自己的**数仓**——**重复建设 + 数据不一致**

**触发点（What）**

2018 年字节启动「**ByteLake**」项目，**对标阿里 OneData**（[ArchSummit 2020 演讲]），目标：
- **统一数仓平台**
- **湖仓一体**（数据湖 + 数仓）
- **业务自助**（业务方不依赖数据团队）

**详细做法（How）**

ByteLake 的**5 大核心组件**：

1. **统一存储层（基于 Iceberg）**
   - 关键设计：用 **Apache Iceberg** 作为存储格式（vs Hive 表）
   - 关键能力：**Schema 演进 + 隐藏分区 + Time Travel**
   - 关键数字：2018-2022 迁移**30 万+ Hive 表**到 Iceberg

2. **统一计算层（Spark + Flink）**
   - 关键设计：**Spark 批 + Flink 流**统一调度
   - 关键能力：**流批一体**——**同一份代码跑批 + 流**

3. **统一指标平台（DataFinder）**
   - 关键设计：指标**定义** + **计算** + **服务**统一
   - 关键能力：**OneMetric**——**业务方自助定义指标**（不需数据团队）
   - 关键数字：字节**10 万+ 指标**——**80% 由业务方自助**

4. **数据资产目录（Datacatalog）**
   - 关键设计：**字段血缘 + 业务血缘**融合
   - 关键能力：**找数据** + **理解数据** + **信任数据** 三位一体
   - 关键工具：基于 **Apache Atlas** 自研

5. **AI 原生（DataFinder AI）**
   - 关键设计：基于 **LLM** 的数据助手
   - 关键能力：**自然语言查数据**（"上个月 GMV" → SQL）
   - 关键数字：业务方使用率**30%+**

**字节 OneData 实施历程**：

| 阶段 | 时间 | 关键成果 |
| --- | --- | --- |
| 第 1 阶段：OneData 启动 | 2018 | 指标 / 资产目录 |
| 第 2 阶段：Hive 迁 Iceberg | 2018-2020 | 30 万表迁移 |
| 第 3 阶段：Flink 流批一体 | 2020-2021 | 50+ 业务线接入 |
| 第 4 阶段：DataFinder AI | 2021-2022 | LLM 辅助 |
| 第 5 阶段：ByteLake 商业化 | 2023-至今 | **火山引擎**对外服务 |

**具体数字（How much）**

- 团队规模：字节数据中台团队 200+ 人
- 关键数字（[ArchSummit 2020]）：
  - **800 亿事件/天**
  - **30 万+ 数据资产**
  - **10 万+ 指标**（80% 业务方自助）
  - **30+ 业务线**共享
- 业务影响：
  - 支撑**抖音 / TikTok / 西瓜 / 今日头条**全场景
  - 新业务接入时间从 3 个月降到**1 周**

**失败教训**

- 第 1 阶段**OneID 误匹配**——倒逼**强匹配 + 人工抽查**
- **Iceberg 迁移**——**30 万表**耗时 3 年——倒逼**自动化迁移工具**
- **指标治理**——**业务方不认指标**——倒逼**指标 Owner 制度**
- **AI 助手**——**LLM 幻觉**（查错表）——倒逼**Schema 索引 + 结果校验**

### 6.3 美团数据中台：从「**6 套数仓**」到统一（2018-2022）

**背景（Why）**

美团 2018 年面临**多业务线**数据仓库**重复建设**问题：
- **外卖 / 到店 / 酒旅 / 电影 / 出行**——**5+ 业务线**
- 每条业务线**自建数仓**——**重复计算** + **数据不一致**
- **跨业务线分析**（如「**外卖 + 酒旅**」）——**需要 ETL 跨库**——**实时性差**

**触发点（What）**

2018 年美团启动「**数据中台**」项目（[QCon 2019 演讲]），目标：
- **统一数据资产**
- **统一指标口径**
- **业务自助**

**详细做法（How）**

美团数据中台**5 大组件**：

1. **统一存储（基于 Hive / Iceberg）**
   - 关键设计：**5 套独立数仓** → **1 套统一数仓**
   - 关键能力：**业务方不直接建数仓**——**通过数据中台**
   - 关键数字：5 → 1（迁移 2 年）

2. **统一指标（OneMetric）**
   - 关键设计：每个指标有**Owner** + **定义** + **计算逻辑**
   - 关键能力：**业务方自助定义指标**（不需数据团队）
   - 关键数字：美团**5 万+ 指标**——**80% 业务方自助**

3. **统一血缘（DataHub 自研）**
   - 关键设计：基于 LinkedIn DataHub 改造
   - 关键能力：**字段级血缘** + **影响分析**

4. **统一资产目录**
   - 关键设计：类似阿里 DataWorks 的「**资产卡片**」
   - 关键能力：**Owner / 文档 / 血缘 / 质量 / SLA**

5. **实时数仓（基于 Flink）**
   - 关键设计：**Flink + Iceberg** 流批一体
   - 关键能力：**实时大屏 / 实时监控**秒级延迟

**具体数字（How much）**

- 团队规模：美团数据中台团队 100+ 人
- 关键数字（[QCon 2019]）：
  - **5 套数仓 → 1 套**（迁移 2 年）
  - **5 万+ 指标**（80% 业务方自助）
  - **100+ 业务线**接入
  - 跨业务线分析**实时性从小时级降到秒级**

**失败教训**

- **5 套数仓迁移**——**业务方不愿改代码**——倒逼**双写期 1 年**
- **OneID 误匹配**——倒逼**强匹配 + 人工抽查**
- **指标治理**——**业务方不认指标**——倒逼**指标 Owner 制度**
- **数据质量事故**——**跨业务线大促**（外卖 + 酒旅）出错——倒逼**实时数据质量监控**

### 6.4 京东数据中台：从「**集团数仓**」到「**业务自助**」（2017-2021）

**背景（Why）**

京东 2017 年面临**「**集团 vs 业务**」**数据矛盾：
- **集团数仓**（中央团队）——**统一指标**，**但响应慢**
- **业务数仓**（各 BG）——**响应快**，**但数据不一致**
- **痛点**：**业务方想要「**快**」**+**中央想要「**准**」**——**矛盾**

**触发点（What）**

2017 年京东启动「**数据中台**」项目（[ArchSummit 2019 演讲]），目标：
- **中央 + 业务**双层架构
- **业务自助** + **中央治理**

**详细做法（How）**

京东数据中台**双层架构**：

```
┌────────────────────────────────────┐
│  中央数据中台（统一）                │
│  - 统一指标定义                      │
│  - 统一血缘 / 资产目录              │
│  - 统一数据质量                      │
│  - 统一安全合规                      │
└─────────────┬──────────────────────┘
              │ 共享
              ▼
┌────────────────────────────────────┐
│  业务数据平台（自助）                │
│  - 业务方自助查询                    │
│  - 业务方自助建模                    │
│  - 业务方自助分析                    │
│  - 业务方自助看板                    │
└────────────────────────────────────┘
```

**5 大组件**：

1. **中央 OneData（统一）**
   - 关键设计：全集团**5 大域**（用户 / 商品 / 订单 / 库存 / 支付）OneModel
   - 关键数字：京东**10 万+ 公共指标**统一

2. **业务 OneMetric（自助）**
   - 关键设计：业务方在 OneModel 基础上**自助定义指标**
   - 关键数字：业务方自助**3 万+ 指标**

3. **统一资产目录**
   - 关键设计：基于 **Apache Atlas** 自研
   - 关键能力：**字段血缘 + 业务血缘**融合

4. **数据安全**
   - 关键设计：等保 3.0 + GDPR
   - 关键能力：**字段级标签 + 数据出口 DLP**

5. **AI 助手**
   - 关键设计：基于 LLM 的数据查询助手
   - 关键能力：自然语言查数据

**具体数字（How much）**

- 团队规模：京东数据中台团队 80+ 人
- 关键数字（[ArchSummit 2019]）：
  - **10 万+ 中央公共指标**
  - **3 万+ 业务自助指标**
  - **200+ 业务线**接入
  - **新业务接入时间从 3 个月降到 1 个月**

**失败教训**

- **中央 vs 业务**——**业务方不愿走中央**——倒逼**双层架构**（中央 + 业务）
- **指标治理**——**业务方不认**——倒逼**指标 Owner 制度**
- **数据安全**——**GDPR 合规**——倒逼**字段级标签 + 自动化**
- **AI 助手**——**LLM 幻觉**——倒逼**Schema 索引 + 结果校验**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选**1-2 个核心业务线**
- 部署**OneModel 公共层**（DWD / DWS / ADS）
- 部署**OneID 映射表**
- 选**指标平台**（OneMetric）
- 团队：3-5 人

**1 → 10 阶段：6-12 个月**

- 扩展到**5-10 个业务线**
- 引入**统一资产目录**（Apache Atlas / DataHub）
- 引入**数据质量监控**
- 引入**实时数仓**（Flink + Iceberg）
- 团队：10-20 人

**10 → 100 阶段：12-24 个月**

- 扩展到**100+ 业务线**
- 引入**双层架构**（中央 + 业务自助）
- 引入**AI 数据助手**（LLM 辅助）
- 引入**数据安全**（GDPR / 个保法）
- 团队：20-50 人

**100 → 1000 阶段：12-24 个月**

- 商业化（DataWorks / ByteLake / 美团数据中台）
- 引入**跨云**（多云数仓）
- 引入**Data Mesh**（域化）
- 团队：50-200 人

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 美团 / 京东）印证：**数据中台不是「**装个 Hadoop**」，是「**OneModel + OneID + OneService + OneMetric**」**四件套。
> - 关键时间线：阿里 OneData 14+ 年 / 字节 ByteLake 4 年 / 美团 4 年 / 京东 4 年 —— **数据中台是长期工程**。
> - 选型第一原则：**业务 0 改造**（OneModel 公共层）+ **业务自助**（OneMetric）+ **强一致**（统一血缘）——**按业务规模选**。
> - 99% 的失败来自「**业务方不认 + 多套数仓迁移 + 公共层过度抽象**」——必须有**业务 Owner 制度 + 双写期 + 公共层 vs 业务层分离**。
> - 真正的 ROI 来自「**5 套 → 1 套**」+ **业务方自助**+ **跨业务线分析**——是**数据团队生产力的乘数**。
