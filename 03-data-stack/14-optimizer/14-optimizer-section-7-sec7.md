## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

一张把 RBO / CBO / AQE / AI 优化按「性能 / 稳定性 / 自适应 / AI 友好 / 工程复杂度」打 1–5 分的表看起来能直接给出结论，实际不能。原因不是分数打得不准，而是**这些维度的权重由场景决定，而表里没有场景**。同一个「稳定性」，在一张日活百万的点查表上意味着「计划不许抖动」，在一份凌晨跑三小时的批任务上意味着「跑完就行」——两者会对同一列给出相反的取舍。把加权结论印成 1–5 的整数，等于把「取决于场景的判断」伪装成「与场景无关的判断」，读者会照抄一个自己场景里并不成立的答案。

这个权重反转在优化器上有两处特别典型。**第一处是「性能」与「可预测」的反转**：交互查询追 P99，一次计划抖动就是一个用户可见的超时；批任务追吞吐，个别查询慢一点可以靠错峰消化。同一份「稳定但次优」的规则计划，在前者眼里是可接受的，在后者眼里是纯损失。**第二处是「优化充分度」的反转**：搜索空间越大，找到更优计划的概率越高，但优化耗时也越长；当执行耗时从分钟级降到亚秒级，同一套搜索策略的收益符号会从正变负。打分表把这两处反转都压平成了同一个整数。

第二层问题是把不同层级的东西并列。RBO、CBO、AQE、Calcite、自治优化**不是五个可以互相替换的产品**，而是同一条流水线上五个不同位置：CBO 与 RBO 是同一个决策位置上的两种实现，AQE 是它们在执行期的补充层，Calcite 是把这套东西做成库的形态，自治优化是加在整条流水线外面的控制回路。把它们排成一行打分，会诱导读者去做「二选一」，而真实工程里它们的正确关系是**叠加与分工**：现代引擎几乎全部同时启用规则重写、代价搜索与自适应执行。选型问题因此不是「选哪一个」，而是「在我这套约束下，哪几层必须存在、哪一层可以不存在」。把这一层说透，后面所有比较才有意义——比较的目的是确定**哪一层必须由我来补**，而不是**把哪一层换掉**。

第三层问题是门槛错位。这些模式的收益与前置条件并不相同——前几层（统计信息、运行时纠偏）的收益来自机制本身，只要数据分布符合前提就能拿到；后几层（AI 建议、自治）的收益来自**复用前面已经建好的基础设施**：没有可信的执行指标，AI 建议无法验证；没有基线，自治无法回滚；没有负载分层，单回路会在两个相反的目标函数之间震荡。把两者放在同一张表里打分，会让读者以为可以「跳过前面的层直接买最后一层」——这是本主题里代价最高的一种误读。

这里插一条容易被忽视的判据：**做比较之前，先确认你有能力读执行计划**。优化器是本主题中可观测性最差的组件——它不报错，只做选择。一个团队里若没有人能读 EXPLAIN、没有人能对照 EXPLAIN ANALYZE 判断估计是否离谱，那么无论选哪个模式，最终都会回到「凭感觉调参数」，这是所有反模式的共同起点。因此能力建设的顺序应当是**先建立读计划的能力，再引入更复杂的模式**；反过来的成本高得多。

因此本章的判据不是「谁更强」，而是**「我的约束是哪几条」**。约束一旦确定，模式基本被逼成唯一解；约束不定，任何比较都是空的。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 基数输入的可得性 | 参与 Join 的大表，能否给出行数 / NDV / 直方图 | 这是唯一能把 CBO 直接降级成 RBO 的约束；缺了它，代价模型的所有输入都是常量，argmin 退化 |
| 决策固定在哪一刻 | 你负载里最贵的那类问题，发生在优化前、stage 边界、还是回路里 | 每个模式的失效点都在它固定决策的位置之后；位置对不上，能力再强也用不上 |
| 优化预算的占比 | 查询执行耗时与优化耗时的量级关系 | 亚秒级查询给不出搜索空间；分钟级批任务相对不在乎多花几百毫秒找更优计划 |
| 元数据接口的落地工作量 | 每个数据源能否实现统计信息接口 | 用框架换实现是固定税：接口没实现，框架的代价层就是空转，且**不报错** |
| 误判可观测与人工出口 | 优化器选错时，谁能发现、谁能绕过 | 估算盲区（相关谓词、倾斜键、UDF）永远存在，没有出口的系统一旦选错只能等 |
| 升级与回退风险 | 升级引擎后，现有 hint / 计划基线 / 参数是否还能成立 | hint 与计划基线把优化器行为固化在配置里；固化的越多，升级越像一次高风险回归测试 |

这六条里有一条会最先起作用：**基数输入的可得性**。它是唯一一条无法靠加机器绕开的约束——没有统计信息，加多少节点都不会让估算变准。第二位的是**决策固定在哪一刻**，因为它把「选模式」翻译成了一句可判断的话：去看看你这套系统里最慢的那批查询，慢的原因出现在哪个时刻之后。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| RBO（规则优化） | 优化最底层，永远存在 | 按固定规则重写（谓词下推、列剪裁、子查询消除）与固定顺序，不读基数 | 自 System R 起的早期优化器；今天仍是所有引擎的规则重写层 | 内建于引擎 |
| CBO + 统计信息 | 现代引擎的默认基线 | 用离线采集的行数 / NDV / 直方图估算各候选计划的代价，取最小者 | PostgreSQL、Trino、Spark SQL、StarRocks、Doris | 内建；元数据采集自维护 |
| AQE（自适应查询执行） | 编译期之后的纠偏层 | 在 stage 边界用实测分区统计改写 Join 策略、合并小分区、拆分倾斜分区 | Spark（3.0 引入）、Trino 等 | 内建；配置开关 |
| Cascades / Volcano 框架 | 搜索框架本身（不是产品） | Memo（等价类）+ 变换规则集 + 代价上界剪枝 | 学术实现与自研引擎 | 公开框架，无单一产品 |
| Calcite 嵌入式优化器 | 自研引擎的前端标准件 | 解析 + 关系代数 + 规则 + 代价框架，由使用者实现 Adapter 与 TableStatistics | Flink Table API / SQL；自研 SQL 引擎 | Apache 开源项目 |
| 向量化 + 规则重写 | 引擎级的另一条性能路线 | 不做统计驱动的代价搜索，靠执行层向量化与规则重写拿性能 | ClickHouse 一类分析引擎 | 内建于引擎 |
| AI 驱动优化（建议） | 诊断与建议层 | 执行指标偏离基线 → 生成候选动作 → 小流量验证 → 采纳或丢弃 | Snowflake Query Insights 等；其余厂商是否属此类，按本节末尾的判定口径核验（有无「建议采纳 + 回归验证」闭环） | 厂商增值能力 |
| AI 自治优化（自治优化器） | 带安全回路的自动化 | 观测 → 决策 → 灰度执行 → 验证 →（变差则回滚） | 已建成执行指标、基线、回滚与负载分层的平台方（长期规模化效果暂无可公开核验的第三方评测，可按「autonomous query optimization」自行检索） | 厂商增值能力 |

这八项其实分三族，**同族内部差异小、跨族差异大**——先分族再选，能省掉一半比较：**编译期族**（RBO、CBO、Cascades、Calcite、向量化 + 规则重写）在查询开始前把计划定下来，族内差异只在「用什么替代真实基数」；**运行时族**（AQE）把一部分决策推到 stage 边界，用实测值替代估算；**回路族**（AI 建议、AI 自治）不改进单次计划，改的是「谁来决定改什么、改完怎么验证」。跨族比较通常没有意义——你几乎一定同时需要编译期族与运行时族，回路族则在前面两族建好之后才有讨论价值。

族内比较才有信息量：RBO 与 CBO 争的是「要不要为准确度承担估算风险」，CBO 与 Cascades 争的是「要不要为搜索空间额外付实现复杂度」，CBO 与「向量化 + 规则重写」争的是「性能该从哪里来——更聪明的计划，还是更快的算子」【经验】。最后这一对常被混淆：向量化解决的是「同一个计划跑得更快」，优化器解决的是「换一个更省的计划」，两者相乘而非相斥——一个引擎可以只做前者而照样在分析型负载上表现良好。判断某个引擎走的是哪条路，看官方文档与 EXPLAIN 输出里是否存在基于统计信息的代价比较即可，不需要看它的宣传材料。

跨族混用还有一个具体后果：**「AI 优化器」这个说法本身需要拆开看**。它可能指回路族里的「执行后建议」（改的是下一次查询的配置），也可能被用来指代「用模型替代代价模型做基数估算」（仍属编译期族）。两者的判定方法是不同的：前者的判据是「有没有建议采纳与回归验证的闭环」，后者的判据是「有没有公开、可复现的估算精度对比」。混在一句话里谈，会把两者当成同一件事，进而把该做的准备做错。

### 7.3 机制差异：为什么它们表现不同（核心节）

八个方案看起来是八个选项，实际上它们回答的是同一个问题的四个侧面：**当真实基数不可知时，你在哪一层把它补回来、花多少预算去搜、把决策固定在哪一刻、以及谁为这套机制提供输入**。下面四个机制维度各展开一次，每个维度都给出「由此必然导出的性质」与「什么条件下这条性质失效」。

#### 7.3.1 基数从哪来：规则、离线统计、运行时实测

**机制是什么**：优化器的全部难度集中在「不知道参与运算的数据到底有多少行」。每个模式都是对这四个字的一种回答：绕过它（规则）、提前估它（统计信息）、事后再量它（运行时实测）。

| 方案 | 基数从哪来 | 拿到基数的时刻 |
| --- | --- | --- |
| RBO | 不拿，按语法形状定顺序 | — |
| CBO | 离线采集的行数 / NDV / 直方图 | 优化之前 |
| Cascades | 同 CBO（Memo 里比较的是估计代价） | 优化之前 |
| Calcite | 由使用者实现 TableStatistics 提供 | 优化之前（取决于你的接入） |
| AQE | shuffle 写完后的实测分区统计 | 执行之中（stage 边界） |
| AI 建议 / 自治 | 执行指标（耗时 / 扫描字节 / shuffle 字节） | 执行之后 |

**由此必然导出的性质**：因为 CBO 的输入是离线采集的数值，所以它对「两次采集之间的分布漂移」没有免疫力——数据变了而统计没变时，它会**自信地**选出一个坏计划；而 RBO 的错是稳定、可预期的次优。这个差别很关键：一个自信的错比一个迟钝的次优更贵，因为它不触发任何告警。这条性质还解释了**为什么统计信息陈旧比统计信息缺失更危险**：缺失时会退回规则顺序（可预期的次优），陈旧时会拿着过期分布自信地做减法（不可预期的坏计划）——前者是稳定亏损，后者是概率性事故。

又一个必然推论是**估算误差会沿计划树被继承与放大**：中间结果的估算偏差会被上层算子当作输入继续计算，越往上越偏离实际，最终在最后几个算子上完全失去参考价值【经验】——这就是「估算错一次不致命、估算错在中间层才致命」的原因，也解释了为什么错误常表现为全表扫描式的极端计划，而不是温和地慢一点。

因为 AQE 把决策点推到分区已经写完之后，中间结果的大小是**数出来的而不是算出来的**，估算误差在 stage 边界被清零；代价是它只能改 stage 之间的计划——阶段内部的排序、聚合、UDF 一旦启动就不可替换，这是结构决定的边界，不是实现缺陷。所以当瓶颈落在单个阶段内部（单个超大 key 的聚合、排序落盘、慢 UDF）时，AQE 的优势反转成无力，因为**边界恰好没有出现**。

**公开证据**：CBO 的输入依赖可用 PostgreSQL 的 autovacuum 自动 ANALYZE 来维持，该能力自 8.1 版（2005）起提供【公开】PostgreSQL 官方手册；具体行为可按你所用版本在官方手册中检索 autovacuum 核验。规则重写与代价搜索的分界可追溯到 System R 的访问路径选择工作【公开】P. G. Selinger 等，*Access Path Selection in a Relational Database Management System*，SIGMOD 1979。AQE 只在 stage 边界介入这一点，可由 Spark 官方配置文档确认：Spark 3.0（2020）引入 AQE，3.2.0（2021）起默认开启，倾斜判定参数 skewedPartitionFactor 默认 5、skewedPartitionThresholdInBytes 默认 256MB【公开】Apache Spark 官方配置文档。

**失效条件**：当 WHERE 中多个谓词强相关（如 city 与 province）时，CBO 的独立性假设会把选择率直接相乘，估算偏差可达数量级【经验】——这一条不是提高采集频率能解决的，属于建模层面的盲区。判定方法：对比 `EXPLAIN` 的估计行数与 `EXPLAIN ANALYZE` 的实际行数，若常态性相差 10 倍以上，说明这套模式在你的系统里只是名义上存在。

#### 7.3.2 搜索空间怎么控：N! 与剪枝预算

**机制是什么**：N 张表的 Join 排列是 N!【推算】——5 张 120 种、10 张约 360 万种、15 张约 1.3 万亿种（推导：N 张表的连接排列数即 N 的阶乘，依次代入即得）。穷举不可行，所以「搜索」这个动作本身必须有预算，而不同模式给预算的方式不同。

**它在各候选中的实现差异**：

- **RBO**：不搜索，按固定规则顺序产出唯一计划。搜索成本为零，最优性不保证。
- **CBO（动态规划穷举）**：对小规模 Join 集合做 DP，代价约为 2^N 量级【推算】（推导：DP 在每个子集上比较，子集总数为 2^N）；表数一多就必须换成贪心或启发式枚举。
- **Cascades**：Memo 把「逻辑等价」与「物理实现」分层存储——同一子问题的最优代价被复用（动态规划的效果），变换规则集又可扩展（规则系统的效果）；新产生的计划若代价超过当前最优上界就直接丢弃，不再展开其子问题。
- **Calcite**：提供规则与代价框架，搜索能力取决于你接入的元数据；代价层拿不到输入时，搜索退化为规则重写的另一种写法。
- **AQE**：不搜索，只做局部替换（合并分区、翻转广播判定、拆分倾斜分区）。

**由此必然导出的性质**：因为 Cascades 的剪枝比较的是**绝对上界**而不是相对好坏，所以剪枝的正确性完全由代价模型精度决定——代价偏差会让上界剪掉真正的好计划，而且**这种错误不可观测**：没有任何信号告诉你「这里曾经有一个更优计划被丢了」。反过来，因为 RBO 根本不搜索，所以它的计划是可解释、可复现、可预测的，代价是它在数据分布变化后无法解释自己为什么慢。

由此还有一条工程上的必然推论：**搜索预算必须被显式写成参数，而不是留给实现默认值**。一旦搜索空间随表数增长而失控，症状不会表现为「查询变慢」，而是「同一条 SQL 的优化耗时随参与 Join 的表数上升」——这是一个只在计时里出现的信号，没有告警会替你发现它。这也是自研优化器最容易翻车的地方：团队通常低估 Memo 的实现成本（等价类分组、规则调度、上界传播都要自己维护），半年后得到一个只能在少数查询上生效、且没人敢改的搜索框架。

由此得到的判断顺序是：**先问「我的表数会不会让搜索失控」，再问「我的代价模型够不够准」**。表数决定搜索成本的上界，代价精度决定剪枝能不能剪对；顺序反了，会先花大力气校准代价模型，却在搜索空间上失控。

**公开证据**：Cascades 由 Goetz Graefe 提出【公开】G. Graefe，*The Cascades Framework for Query Optimization*，IEEE Data Engineering Bulletin, 1995；更早的 Volcano 优化器生成器见【公开】Graefe & McKenna，ICDE 1993。判断某引擎是否采用该框架的方法是可核验的：看它的优化器是否同时具备 Memo（等价类）+ 变换规则集 + 代价上界剪枝三件结构。

**失效条件**：当查询是短查询时，「充分搜索换取更优计划」的性质反转为「优化开销成为总耗时的主要部分」——因为搜索成本与收益的比值随执行时间下降而上升。判定方法：统计「优化耗时 / 执行耗时」的**比例分布**（P50、P99），而不是平均值；平均值会把「短查询里优化耗时占比极高」这一类问题完全抹平。

#### 7.3.3 决策固定在哪一刻：编译期、stage 边界、回路

**机制是什么**：每个模式都要把「计划就此确定」这件事固定在一个时刻。这个时刻之后的任何变化，它都管不着。

```text
三层决策边界（谁在什么时候还能改计划）
  编译期：规则重写 + CBO 定 Join 顺序与策略   ──► 计划初稿
        │（此后 CBO 不再参与）
  stage 边界：AQE 用实测分区统计改写            ──► 计划二稿
        │（此后 AQE 不再参与）
  stage 内部：算子已启动，不可替换
        └─ 唯一出口：人工 hint / 计划基线 / 预计算（本质是把问题提前挪出这一层）
  回路层：AI 建议在查询之外改配置（统计信息 / 索引 / 物化视图 / 参数），下一次查询才生效
```

**由此必然导出的性质**：因为每个模式都把决策固定在某一个时刻，所以**它的失效点不在它宣称的能力边界内，而在那一时刻之后发生的事**——CBO 固定在前，于是怕统计信息过期；AQE 固定在 stage 边界，于是怕瓶颈落在阶段内部；Cascades 固定在搜索预算内，于是怕短查询；回路层固定在两次查询之间，于是怕「这次查询马上就要跑，而配置还没生效」。

这张图还说明了一件事：**同一时刻只能由一层做决策**。三层同时开启时，真正执行的是「最后一层还能改的那个版本」。如果监控、归档与排障只看第一层，就会出现那种典型场景——一群人对着一个已经不执行的计划分析原因，而它在上线前就被改写过。因此开启任何一层之前，先确认你的可观测链路能拿到**最后一层**的计划。

这条因果链给出一个比功能清单更有效的判断方式：**问「它把决策固定在哪一刻」，再去检查你负载里最贵的那类问题是否恰好落在那一瞬间之后**。

**公开证据与判定方法**：这条边界可从执行计划直接核验，不需要读引擎源码——开启 AQE 前后各取一次最终计划，如果 Join 策略与分区数完全一致，说明你的查询里不存在 AQE 能改写的边界（例如全是窄依赖的 map-only 作业），此时开启它只是多付了一层阶段切分的成本。

AQE 改的是**这一次查询的计划**，AI 建议改的是**下一次查询的配置**，两者不在同一时刻生效，也就不构成互相替代的关系。

**失效条件**：当归档里只有「编译期计划」而没有「AQE 之后的最终计划」时，排障会变成对着一个已经不执行的老计划讨论——这不是模式失效，是可观测性失效，但它会造成与模式失效完全相同的后果。同类失效还有一处：**并行度与资源参数常被写在优化器之外**（executor 数、队列配额），于是「计划正确」与「跑得快」之间还隔着一层配置，而这一层不在任何优化模式的管辖范围内。

#### 7.3.4 谁提供元数据接口：嵌入式框架的固定税

**机制是什么**：Calcite 这类嵌入式优化器只处理「关系表达式 + 元数据接口」，它自己不执行、不碰数据。因此它的代价能力不是白得的，而是**由使用者的接入工作量换来的**。

**它在各候选中的实现差异**：

- **一体化引擎**（PostgreSQL、Trino、Spark SQL、StarRocks）：统计信息由引擎自己的采集任务写入自有 catalog 与自有格式，用户只需触发 ANALYZE。
- **嵌入式框架**（Calcite）：必须由使用者为每个数据源实现统计信息接口，自定义算子还要显式映射成 RelNode。
- **文件清单 + 开放表格式**：统计信息可以随表元数据一起存（如表格式的元数据文件或清单记录），从而不再依赖引擎外部的独立采集任务——这是 § 6 案例里把统计信息写进数据本身那条路线的机制来源。
- **无 catalog 数据源**（对象存储上的裸文件、外部表）：往往给不出任何统计信息，是这套机制的天然盲区。

**由此必然导出的性质**：因为框架只能重写它看得懂的树，所以**自定义算子如果没有映射成 RelNode，规则与代价都「看不见」它**——优化器会安静地绕过它，不报错、不告警。这是「用框架换实现」的固定税：你换来的是解析、关系代数与规则框架，付出的是每一层接入都要显式完成的映射与统计接口。一个可复现的判定方法：在完全不提供统计信息的前提下跑同一条 SQL，看计划是否改变；不改变，说明你只拿到了规则重写，此时把它宣传成「我们有 CBO」是过度陈述。

这条固定税还有一个组织层面的形态：**接一个数据源的成本被拆成两半**——「能查」与「能被优化」是两件事。前者接完就能跑，后者还要额外补齐统计信息接口与算子映射。把两者算作同一件工作量的团队，会得到一个「数据源接了很多、优化器却一直在猜」的系统。

**公开证据**：Apache Flink 的 Table API / SQL 使用 Calcite 做解析与优化【公开】Apache Flink 官方文档《Table API & SQL · Table Planner》（Apache Flink 1.15, 2022；该节说明规划器有 `flink-table-planner-loader` 与 `flink-table-planner_2.12` 两种加载形态，二者都以 Calcite 为规划基础）。核验方式有两处，都不需要读引擎源码：一是在 Maven Central 检索制品 `flink-table-planner_2.12` 的依赖清单，确认其中含 `org.apache.calcite`；二是在 Flink 源码仓库查看 `flink-table/flink-table-planner` 模块的构建声明。「统计信息随表元数据存储」这条路线同样可以结构性核验：检查你的开放表格式的元数据里是否包含行数与列级分布信息，以及执行引擎是否真的读取了它。

**失效条件**：当核心数据源是裸文件、无 catalog 的外部表时，代价层拿不到输入，Calcite 的代价能力静默失效、退回纯规则，「白得一个 CBO」的优势反转为「多了一层不能被优化的抽象」。此时正确的第一步不是换优化器，而是补元数据。

四个维度合起来，可以压成一句话的对照：

| 机制维度 | 它决定的问题 | 判据落在哪 |
| --- | --- | --- |
| 基数从哪来 | 估算误差的量级与方向 | EXPLAIN 估计行数 vs EXPLAIN ANALYZE 实际行数 |
| 搜索空间怎么控 | 优化耗时会不会成为负担 | 优化耗时占查询总耗时的比例分布 |
| 决策固定在哪一刻 | 能力覆盖到负载的哪一段 | 最终计划来自哪一层；瓶颈是否落在该层之后 |
| 谁提供元数据接口 | 代价能力是真的存在还是名义存在 | 去掉统计信息后计划是否改变 |

本节的主结论是：**优化器的强弱不由它启用了几个高级特性决定，而由它能否解释自己的选择决定**——一份能被读懂、能被验证、能被回退的计划，胜过一份「更快但没人说得清为什么」的计划。

### 7.4 成本结构对比（不是价格表，是成本函数）

几个方案的**主导成本项完全不同**，把它们简化成「谁更贵」会直接选错。先写出成本函数的形式：

```text
总成本 ≈ 优化耗时 × 查询次数          （搜索预算项，与候选计划数与表数有关）
       + 统计信息采集的 I/O 与存储     （估算输入项，与数据变更量有关）
       + 误判造成的额外执行成本        （主导项，与被选错的那次查询规模有关）
       + 接入与运维人力                （固定项，与数据源数量、专家数量有关）
```

把四个成本项落到各方案上，主导项与隐性成本的分工如下：

| 方案 | 主导成本项 | 隐性成本（最容易漏记的那一项） | 随什么增长 |
| --- | --- | --- | --- |
| RBO | 稳定但长期的次优执行 | 无法归因：慢查询拿不到「因为是次优计划」这个结论 | 随数据分布偏离规则假设的程度 |
| CBO | 采集 I/O 与误判执行成本 | 采集任务失败不报错，只让计划质量悄悄下降 | 采集频率与数据变更量同时上升 |
| AQE | 阶段切分与 shuffle 物化 | 排障复杂度：最终计划与编译期计划不一致 | 查询次数（无论是否被改写都要付） |
| Cascades / 自研搜索 | 搜索时间与实现复杂度 | 剪枝剪错不可观测 | 参与 Join 的表数（阶乘级） |
| Calcite 嵌入式 | 接入与运维人力 | 未映射的算子被优化器静默绕过 | 数据源数量与自定义算子数量 |
| 向量化 + 规则重写 | 执行层的算子实现工程量 | 无代价搜索时，计划层无法解释为何慢 | 数据形态（列存 / 压缩率） |
| AI 建议 / 自治 | 指标采集 + 验证 + 回滚的工程投入 | 建议无法排序时的信任流失 | 被纳管的查询数量与负载种类 |

各方案的成本特征：

- **RBO**：搜索预算项为 0，采集项为 0，接入项极低。**主导项是误判造成的额外执行成本**——它不做估算，也就不存在「估错」，但它会稳定地选出次优计划，这个代价被平摊到每一次查询上，长期累积。
- **CBO**：四个项同时存在。**主导项是采集项与误判项的组合**：采集频率太低，误判项飙升；采集频率太高，采集 I/O 本身成为负担。这两项方向相反，所以「多快算够」必须和查询收益一起算，而不是越快越好。
- **AQE**：采集项为 0（它读的是执行期实测值）。**主导项是阶段切分与 shuffle 物化**——一次查询被切成更多阶段，边界处要落盘，这笔成本发生在**每一次**开启 AQE 的查询上，无论它有没有被成功改写。
- **Calcite 嵌入式**：**主导项是接入与运维人力**，且这笔钱花在项目早期、收益出现在后期；如果统计信息接口没有全部落地，这笔人力就变成了纯支出。
- **AI 建议 / 自治**：搜索项与采集项都很低，**主导项是「指标采集链路 + 建议验证 + 回滚能力」的工程投入**。模型推理本身是这条链路里最便宜的一环【经验】。

一个【推算】的量级示例，用来说明「误判项为什么是主导项」：设一次 Join 中，小表约 1 亿行、行宽 100 字节，即 ≈ 10 GB；大表 10 倍于小表，即 ≈ 100 GB；计算节点 100 个。此时**正确选择是按 Join 键重分区**——两侧 shuffle 合计 ≈ 大表 + 小表 ≈ 110 GB；而若估算把小表判得极小（例如统计信息还停留在这张表只有几 MB 的时候）、把广播误判成划算，网络量 ≈ 小表大小 × 计算节点数 ≈ 10 GB × 100 ≈ 1 TB 级，比正确选择高约一个数量级，多付的约 900 GB【推算】（推导链：广播量 ≈ 小表大小 × 节点数；shuffle 量 ≈ 参与重分区的行数 × 行宽，两者均未计压缩与副本）。这个例子里两者的比值会随压缩比、网络条件与广播阈值浮动，但真正值得注意的是**误判的代价随节点数线性放大，而正确选择的代价只随数据量增长**——统计信息一旦落后于表的实际增长，这张表就会持续被当成小表广播出去。所以在这类查询上，统计信息的采集成本（把这张 10 GB 的表重采一遍）相对于一次误判的执行成本（≈ 900 GB 的网络与随后的落盘）可以忽略；这就是「统计信息是前提，不是可选项」这句话的成本含义。

同一条推导也解释了另一个常见现象：为什么优化器的收益往往**在少数几条大查询上集中体现**，而不是均匀分布在所有查询上。因为误差项随参与运算的数据规模放大——小查询上估错与估对都在毫秒级，大查询上估错是数量级差异。评价一次优化器改动是否有效，正确的采样口径是「按扫描字节加权的耗时」，而不是「平均查询耗时」【经验】。

### 7.5 决策树（每个分支都要有阈值依据）

```text
① 参与 Join 的大表，能否给出统计信息（行数 / NDV / 直方图）？
   ├─ 不能（裸文件、无 catalog 外部表）→ 先补元数据；
   │     在此之前任何「优化器选型」都只是规则顺序之争
   └─ 能 → 继续
        │
② 查询时长量级落在哪一档？
   ├─ 亚秒级 ~ 秒级交互查询为主 → 规则重写 + 固定计划基线
   │     （不要在这里花搜索预算）
   └─ 十秒级以上（批任务 / 分析查询）为主 → 继续
        │
③ shuffle 之后的中间结果规模是否可预测？
   ├─ 可预测（分布稳定、无热点键）→ CBO + 统计信息
   │     （表数多且查询模式收敛时，再考虑 Cascades / 自研搜索）
   └─ 不可预测 / 倾斜常见 → CBO + AQE
        │
④ 谁在写查询、谁在排障？
   ├─ 有懂代价模型的专职人员 → 可以采用复杂模式（Cascades / 自研 / 校准代价模型）
   └─ 业务方自行提交 → 必须补上「误判可观测 + 人工出口」：
        暴露估算与实际行数的偏差，保留 hint / 计划基线作为最后出口
        │
⑤ 是否已有可信执行指标、基线、回滚与负载分层？
   ├─ 无 → 停在 AI 建议（人工裁决），不要上自治
   └─ 有 → AI 自治优化（谨慎，且限定单一目标函数）
```

树上五个判断节点读的都是**可观测的事实**（能否给出统计信息、耗时量级、shuffle 之后的中间结果规模是否可预测、有没有专家读计划、能不能回滚），没有一个是成熟度标签——模式选择能落地的唯一前提是判据可验证。

**阈值依据**：

- **① 统计信息可得性**：来自成本函数——它是「估算输入项」能否存在的前提。依据是机制而非规模：缺这一项时，代价模型的所有输入退化为常量，argmin 等价于「按书写顺序挑第一个」，此时换成任何搜索框架都不会改变结果。
- **② 亚秒/秒级 vs 十秒级以上**：来自成本函数的「优化耗时 × 查询次数」项与搜索预算的关系。依据是量级比较：当执行耗时在亚秒到秒级时，一次充分搜索消耗的几十到几百毫秒会占掉总耗时的可观比例，搜索的边际收益为负；当执行耗时在十秒级以上时，同一笔优化耗时相对可忽略【经验】。分档用「量级」而非具体毫秒值，因为该阈值随集群规模与引擎实现变化。
- **③ shuffle 规模可预测性**：来自机制——AQE 唯一能起作用的位置是 stage 边界，而它改写的是「编译期对分区大小的判断」。若你的负载里编译期估算与实际分区大小经常落在同一数量级，AQE 无事可做，只为阶段切分多付一笔成本；若经常差一个数量级以上，这笔成本换回的是纠错能力。
- **④ 有无专职人员 / 业务方是否自行提交**：来自「误判可观测与人工出口」这一判据。依据是组织结构约束而非技术：估算盲区（相关谓词、倾斜键、UDF）无法消除，只能被兜底；没有专家读计划时，兜底手段必须内建（偏差记录 + hint 出口），而不能依赖某个人。
- **⑤ 基线 / 回滚 / 分层是否具备**：来自机制——回路族的每一步都必须可度量、可回滚，无人值守才成立；任一环节缺失，自治就退化成「悄悄变坏」。若同时存在交互查询与批任务两类负载，还需按队列分成不同回路，因为单回路无法同时优化 P99 与吞吐这两个方向相反的目标。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 亚秒级点查与短查询为主 | 规则重写 + 固定计划基线 | 索引与物化层预计算 | 不上搜索型优化器：优化耗时占比可能超过执行耗时本身 |
| 数据分布稳定、catalog 完整、查询模式收敛 | CBO + 统计信息 | Cascades（自研 / 专家团队） | 不选自研搜索框架：固定成本换不来额外收益 |
| shuffle 后尺寸不可预测、倾斜常见 | CBO + AQE | 倾斜键预处理（加盐 / 预聚合） | 只上 CBO：编译期估算错误会在 shuffle 后被放大 |
| 自研引擎、无优化器专家 | Calcite 嵌入式 + 向量化执行层 | 直接借用成熟引擎 | 不选自研 Cascades：Memo 与规则调度的工作量常被低估 |
| 自研引擎、有专家、查询模式极专一 | Cascades 框架 + 自有代价模型 | Calcite + 私有代价模型 | 不选 Calcite：通用抽象层会挡掉专用优化 |
| 分析型负载、无统计信息可依赖 | 向量化 + 规则重写 | 补统计信息后再上 CBO | 不硬套 CBO：代价层没有输入时，配统计信息也无处生效 |
| 慢查询长尾、排障人力是瓶颈 | CBO + AQE + AI 建议 | 人工规则库 | 不直接上自治：没有基线与回滚，自动变更风险高于收益 |
| 负载已分层、有基线与一键回滚 | AI 自治优化（谨慎） | AI 建议 + 人工执行 | 不上「全自动」：多目标下回路会震荡 |
| 数据源给不出统计信息 | 先补元数据 | 固定计划基线 | 不换优化器：没有基数输入时，任何选择都只是规则顺序的另一种写法 |

这张矩阵的使用顺序应该**从下往上读**：先落到末行的「是否能给出统计信息」（这是所有分支的前提），再往上确认第二行的「查询模式是否收敛」（决定要不要动用搜索空间），最后才轮到首行的「优化预算占比是否可接受」。反过来从上往下按场景挑模式，就会得到「用着最新能力、却仍靠 hint 兜底」的状态。

四个常见组合，重点是**职责边界与运维代价**，不是功能叠加：

1. **CBO + AQE（编译期规划 + 运行时纠偏）**：CBO 给出 Join 顺序与策略的初稿，AQE 在 stage 边界用实测分区统计改写其中一部分。运维代价——两套决策逻辑并存，EXPLAIN 必须能展示「AQE 之后」的最终计划，否则排障会对着一个已经不执行的老计划讨论。适用：单查询 shuffle 数据量在几十 GB 到 TB 级、倾斜可复现【经验】。
2. **CBO + AI 建议（自动诊断 + 人工裁决）**：CBO 负责选计划，AI 负责把「为什么选错」翻译成人能读的动作建议（刷新统计信息、改写 SQL、加索引、调分区、建物化视图）。运维代价——需要指标采集链路与建议的回归验证，否则建议无法排序。适用：慢查询长尾明显、排障时间被诊断吃掉的团队。
3. **Calcite + 自有代价模型（框架 + 专用）**：Calcite 提供解析、逻辑树与规则框架，统计信息适配与代价模型自己补。运维代价——框架与自研的边界必须一次划清，否则规则执行顺序会变成不可控变量。适用：自研引擎、查询模式相对收敛、团队里至少有一名懂代价模型的人。
4. **CBO + AQE + hint 出口（默认族 + 人工兜底）**：前两者覆盖绝大多数查询，hint 只用于估算盲区（相关谓词、倾斜键、UDF）。运维代价——hint 必须标注原因与复核日期，否则会累积成一份没人敢删、也没人说得清的历史包袱。适用：所有把优化器当「边界内近似求解器」而不是「保证」的团队。

四个组合共同的前提是**边界写在配置里，而不是写在人脑里**：CBO 与 AQE 的分工要能从最终计划上看出来，Calcite 与自研的分工要能从「哪条规则在什么顺序执行」上看出来，AI 建议与人工的分工要能从「建议是否被验证过」上看出来。边界一旦只存在于某位工程师的记忆里，组合模式就会在人员变动后退化成「谁也不敢动」。

### 7.7 选错的代价与迁移成本

**反模式一：把「开了统计信息」当成「有 CBO」。** 症状——catalog 里有采集任务，但大表长期不刷新、裸文件外部表完全没有统计信息，EXPLAIN 里的行数估计是常量。后果——代价模型失去唯一输入，build 侧可能选成大表，产生超额 shuffle；更糟的是这个状态**静默**，系统不报错，只是每条查询慢一点，直到某天遇到一个「大表 join 大表」的查询才以容量事故的形式暴露。正确做法——把统计信息刷新挂进写入链路（写入完成 = 统计信息在阈值内），并记录「最后采集时间」，把「参与 Join 却无统计信息的表」列为常态监控项。

**反模式二：把 hint 当作优化器的替代品。** 症状——hint 越加越多，最终 hint 比 SQL 还长，没人说得清每条为什么在那里。后果——维护面爆炸，且这条路径**不可回退**：当 hint 累积到与 SQL 等长时，任何引擎升级都变成一次高风险回归测试，因为 hint 的语义会随版本变化。正确做法——划定信任边界：相关列、倾斜键、UDF 之外交给优化器；边界内每一条 hint 必须记录原因与复核日期，无原因的应删除。打破这个循环的位置不在最后（删 hint），而在第一环：先把统计信息补齐，再谈 hint 是否还有必要。

**反模式三：用参数掩盖 SQL 问题。** 症状——同一条查询反复调参数，配置项越加越多，问题从 SQL 层转移到配置层。后果——优化器被当成绕开 SQL 缺陷的通道，排障成本上升，且这些参数在下一次引擎升级时又全部需要重新验证。正确做法——先判断是「SQL 本身不合理」还是「优化器选错」：前者改 SQL，后者才动计划。

**反模式四：跳过前两层直接买最后一层。** 症状——还没有可信执行指标与基线，就上自治优化。后果——没有「建议 → 验证 → 采纳 / 丢弃」的闭环，团队无法区分有效与无效建议，最终不再采纳任何建议；**因为语言模型的输出分布由语言合理性决定，不由正确率决定**，缺验证时「能批量产出看似合理的建议」这个优点会直接反转成缺点。正确做法——先把扫描字节 / shuffle 字节这类指标采集起来，并把建议落成可回滚的配置变更，再谈自动化。

**反模式五：只看计划，不看代价参数。** 症状——计划形态看起来合理，但代价公式里的关键系数（行宽、压缩比、网络代价权重、UDF 单位代价）是默认值，从未按自己的数据校准过。后果——因为代价模型是**估算的成本模型**，它对基数的敏感度高于对系数的敏感度，所以这条路在基数准确时几乎无害、在基数不准时会放大错误；团队常把这种错误归因于「优化器不行」，而真正缺的是校准。正确做法——用历史的实际执行数据核对代价模型的预测值，把偏差最大的那一类查询单独挑出来分析，而不是整体换引擎。

这五条反模式有一个共同点：**它们的代价都不是在选型当天付出的，而是在两三年后以「没人敢动」的形式出现**。选型时能算清的只有采购与工量，算不清的是这套配置未来还能不能被改动。

换成另一条路线要动什么（只标工作量量级，不给天数）：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| RBO → CBO | 无（不动数据） | 无 | **中**：加 catalog 与采集链路，采集本身占 I/O | **中**：要能读估计与实际行数的对比 |
| CBO → CBO + AQE | 无 | 无 | **中**：排障要能读懂 AQE 之后的计划 | **中高**：两套决策逻辑并存 |
| 单引擎 → Calcite 嵌入式（自研引擎） | 无 | 少量（方言差异） | **高**：每个数据源实现统计信息接口与算子映射 | **高**：需要有人懂代价模型 |
| 自研搜索 → Cascades 框架 | 无 | 无 | **高**：Memo、规则调度、上界传播都要自己维护 | **高**：等价类与规则顺序成为可控变量 |
| 人工调优 → AI 建议 → 自治 | 无 | 无 | **中**（建议）/ **高**（自治：基线、指标口径、版本化、审计、回滚） | **中**：从「改参数」转为「定义目标函数与验证标准」 |

表里可以看到一个共同点：**除了换引擎本身，这些迁移几乎都不动数据、也很少改查询，代价全部落在运维与团队能力上**。这解释了为什么优化器选型经常被低估——它看起来是一次技术选型，实际是一次能力建设决策。也正因如此，迁移的最优时机通常是**别的工程（元数据、指标采集、回滚链路）刚好要动的时候**，而不是单独发起一次优化器迁移。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 数据分布稳定、catalog 完整 | CBO + 统计信息 | 统计信息是代价模型唯一输入，估得准就不需要运行时纠偏 |
| shuffle 规模不可预测、倾斜常见 | CBO + AQE | 只能在 stage 边界用实测值纠正编译期的估算误差 |
| 查询以亚秒级交互为主 | 规则重写 + 固定计划基线 | 优化预算小于执行时间时，搜索的边际收益为负 |
| 自研引擎、无优化器专家 | Calcite 嵌入式 + 向量化执行层 | 用 Adapter + 统计信息接口换取规则与代价框架 |
| 自研引擎、有专家、查询模式收敛 | Cascades 框架 + 自有代价模型 | Memo 加代价上界剪枝，把阶乘空间压成可控的搜索成本 |
| 分析型负载、无统计信息可依赖 | 向量化 + 规则重写 | 性能可以来自更快的算子，而不必经过代价搜索 |
| 慢查询长尾、排障人力是瓶颈 | CBO + AQE + AI 建议 | 把「指标异常 → 候选动作」自动化，但必须闭环验证 |
| 有基线、有回滚、负载已分层 | AI 自治优化（谨慎） | 自治成立的前提是每一步可度量且可回滚 |
| 数据源给不出统计信息 | 先补元数据，再谈模式 | 没有基数输入时，任何选择都只是规则顺序的另一种写法 |

> 本节小结：本主题的对比中**唯一真正起决定作用的那条差异**是「真实基数在何时可知」——编译期可知就用 CBO 自己做减法，只到 stage 边界才可知就必须叠 AQE，执行之后才知道就只能靠回路去改下一次的配置。其余所有差别（框架、产品、版本、AI 与否）都能归因到这条差异上，也都是它的推论。
>
> 值得单独记住的一句：**优化器的强弱不由它启用了几个高级特性决定，而由它能否解释自己的选择决定。** 一份能被读懂、能被验证、能被回退的计划，胜过一份「更快但没人说得清为什么」的计划——前者可以持续演进，后者只能被供起来。
>
> 落到动作上，顺序只有三步：**先把统计信息补齐**（让代价模型有输入），**再把运行时纠偏打开**（让估算误差有出口），**最后才谈自动化与自治**（让优化动作有回路与回滚）。跳过第一步直接做第三步，得到的是「配置很先进、查询仍然慢」的典型状态。
>
> 💡 **思考锚点**：照本节那三步顺序盘一次你自己的栈——统计信息是「写入完成即刷新」还是「长期不刷」、运行时纠偏（AQE）开了没有；若第一步还欠着，你现在讨论自治优化，得到的会不会正是那句「配置很先进、查询仍然慢」？
