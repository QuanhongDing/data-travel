## 4. 工程实现

§3 回答的是「有哪几种优化模式、各自被什么约束逼出来、代价与失效点在哪」；本节回答另一个问题：**在引擎已经选好、SQL 已经写了三年、hint 已经攒了一堆的前提下，按什么顺序把优化能力装进去，每一步做完手上应该多出什么，以及怎么知道某一步其实没做成。**

组织方式：§4.1 给顺序与判据（从零搭建与存量改造走同一条顺序，因为优化器的前置条件不因存量而改变）；§4.2 给机制与失效条件；§4.3 给选型判据；**§4.4 单独写给存量改造**——这是本主题里读者最可能所处的状态；§4.5 给可直接套用的配置与代码；§4.9 给自检清单。

本文件面向两类读者的分工：**从零搭建**的读者看 §4.1 的 Step 1–2 与 §4.2 的第 1、2、6 条即可开工；**存量改造**的读者从 §4.4 倒着读——先判断自己处在哪种存量状态，再回到 §4.1 挑对应步骤。

### 4.1 落地步骤

**Step 1：采集统计信息，让 CBO 有输入（【经验】1–3 周，随表数量与数据源形态变化）**

- 对参与 Join 的表按引擎各自的方式采集（Spark：`ANALYZE TABLE ... COMPUTE STATISTICS` 与 `... FOR COLUMNS`；Trino：`ANALYZE TABLE`；StarRocks：`ANALYZE TABLE`），对 Join 键与高频过滤列单独提高直方图桶数。
- 把采集挂到写入链路之后，而不是挂在凌晨的独立离线任务上——独立任务失败时没有人会收到告警。
- 对拿不到统计信息的数据源（对象存储裸文件、无 catalog 的外部表）单独列一张清单，标明「此处只有规则重写，没有代价比较」。
- **产物**：一份「表 × 最后采集时间 × 是否有列级直方图」的清单，加一张统计信息盲区清单。
- **判据**：随机抽 3 张参与 Join 的大表，跑 `EXPLAIN` 与 `EXPLAIN ANALYZE`，看估计行数与实际行数是否在同一数量级；偏差常态超过 10 倍【经验】即视为这一步没做成。
- **为什么必须这一步、为什么在最前**：统计信息是代价模型的**唯一**输入。省掉它，后面所有关于 Join 顺序、倾斜、搜索预算的讨论都没有输入——代价模型会退化成「按书写顺序挑第一个计划」，而这件事在系统里是静默的，不会报错。

**Step 2：开启 CBO + AQE（【经验】1–2 周，随引擎版本与现有配置的迁移成本变化）**

- 开启 AQE 及其子能力（合并小分区、倾斜 Join、Join 策略翻转），并把参数值写进版本化配置，而不是留在某个人的会话里。
- 对同一批查询做「开启前 / 开启后」的计划对比，把差异记下来——只确认开关是 `true` 不算验证。
- 对短查询设定搜索预算上限：优化耗时必须计入查询总耗时的分母。
- **产物**：一份前后计划对照表（同一 SQL、开关两态、Join 策略与分区数各是什么），加一份参数基线文件。
- **判据**：对照表里出现至少一处「Join 策略或分区数真的被改写了」；若两态计划完全一致，说明你的负载里没有 AQE 能改写的 stage 边界，此时开启它只是多付一层阶段切分成本。
- **为什么必须这一步、为什么在 Step 1 之后**：AQE 的做法是**把决策推迟到 stage 边界**。它清零的是「编译期估算误差」，不是「没有估算」——如果 Step 1 没做，AQE 只是让一个本来就没有输入的过程多等一轮；而 AQE 之后的计划仍是基于代价的选择，输入质量决定它的上限。

**Step 3：慢查询治理（持续，从「抓一条修一条」转为「一个闭环」）**

- 以阈值抓慢查询（执行时长、扫描字节、shuffle 字节任一超标【经验】），取 `EXPLAIN` 与 `EXPLAIN ANALYZE`。
- 判定分类：**SQL 写法问题**（谓词不可下推、隐式类型转换、不必要的 DISTINCT）走改写 SQL；**计划选择问题**（估算偏差、倾斜）才动优化器配置。两者混在一起处理会让配置项越加越多。
- 每条建议必须带「前后同一指标」的对比，并记录采纳 / 丢弃的理由。
- **产物**：一个带状态的治理队列（每条含：SQL 指纹、证据、动作类别、前后指标、结论、复核日期）。
- **判据**：抽 5 条已关闭条目，问「它当时是排出来的还是测出来的」——答不出指标前后值的条目不是治理结果，只是一段文字。
- **为什么必须这一步、为什么在 Step 2 之后**：慢查询治理的输入是执行指标；没有 Step 2 的对照基线，任何「快了」都只能靠感觉，而感觉无法在两次改动之间做比较。

**Step 4：AI 集成（按需，【经验】2–4 周打通一条链路，随工具成熟度变化）**

- 先用规则 + 模板覆盖高频问题（缺统计信息、Join 顺序错、倾斜），把大模型留给规则覆盖不到的长尾。
- 模型只做两件事：把执行计划读成人话、把异常指标映射成候选动作**建议**。没有验证环节就不叫优化。
- 采纳的建议必须落成可回滚的配置变更，并留下「谁、何时、基于哪条建议」。
- **产物**：一条从「指标异常」到「候选动作」再到「回归验证」的链路，以及建议采纳率与回滚率的统计口径。
- **判据**：能当场回答两个数——建议采纳率、采纳后回滚率。答不出来，说明这条链路只是「会说话」，不是「说对了」。
- **为什么必须这一步、为什么在 Step 3 之后**：AI 诊断的价值建立在可信度量之上；Step 3 之前没有「扫描字节 / shuffle 字节」这类指标，模型给出的建议既无法排序也无法验证。

**Step 5：自治优化（持续，前置条件最重，不要在 Step 1–4 之前启动）**

- 回路四段缺一不可：观测（延迟分布、扫描字节、资源利用率）→ 决策 → 执行（灰度 + 一键回滚）→ 验证（与基线比同一指标）。
- 硬约束写进配置而不是写在规范文档里：变更窗口、最大影响面、SLO 不得低于基线。
- 按负载分组各设一条回路——交互查询与批任务的目标函数不同，不要共用一组参数。
- **产物**：每条自动动作的变更记录、回滚记录与基线快照。
- **判据**：问一个具体问题——自治系统改坏了一个配置，多久能回滚、谁批准回滚。答不上来，说明手上是「自动执行」而不是「自治」。
- **为什么必须这一步、为什么在最后**：自治的收益来自复用前四步已经建好的基础设施（指标、基线、变更流程、回滚能力）；少任何一样，自动变更的风险就高于它省下的人力。

**最常被跳过的是 Step 1 的判据环节**：采了统计信息、开关也开了，但没人对照过估计行数与实际行数。它被跳过的原因很自然——这一步的产物（清单）看起来和「采集成功」是一回事。第一次出问题的时点通常不是当天，而是**某张大表增长到 Join 规模之后**：某个查询突然把队列打满，排查发现引擎从来不知道那张表有多大。此时能用的解释只有一句「以前都好的」，因为从没有一条记录说明估计误差本来是多少。

### 4.2 关键技术点

**CBO + 统计信息**

- **做法**：数据变更后触发采集（写入链路挂钩或按变更行数阈值触发），关键列单独调高直方图桶数；把「最后采集时间」当成表级元数据暴露出去。
- **机制**：因为采集被挂进了写入链路，「统计信息准不准」这件事就从「一次离线任务有没有跑成」，变成一条随时可读的差值（估计行数 / 实际行数）——下面所有手段（刷新统计信息、加 hint、调参数）谁真的有效，都由这条差值裁决，不必再靠争论。代价是采集本身占采样 I/O，而且采集是异步的：系统里永久存在「统计信息落后于数据」的时间窗，这个窗口只能被压小、不能被消掉。
- **失效条件**：**当采集间隔长于业务写入周期时**，这条从「估算」退化成「用昨天的数据估今天的表」——而且它不报错：同一 SQL 在凌晨批任务与白天交互查询上拿到质量不同的计划，两种计划都能跑完，所以没有任何告警。观测信号：同一张表上 `EXPLAIN` 估计行数与 `EXPLAIN ANALYZE` 实际行数的比值跨天波动，常态相差 10 倍以上【经验】即视为失效；这个比值通常是**同一条 SQL 的两份计划被并排放进治理队列**时才第一次被看见。谓词强相关（市 / 省、店铺 / 品牌）造成的偏差属于估算模型的固有边界（机制见 §3.2.1 的失效点），本节对它的要求只有一条：把偏差量记进看板，**不要用加参数去修**——参数改不了相关性。
- **档位**：【公开】上述 `ANALYZE` 命令分别见于 Spark / Trino / StarRocks 官方手册，命令名与支持范围随版本变化，请按所装版本的官方文档核验；「基数估算误差是计划质量差的主因」这一结论见 VLDB 2015 的 *How Good Are Query Optimizers, Really?*。

**AQE（自适应查询执行）**

- **做法**：Spark 侧开 `spark.sql.adaptive.enabled` 与 `skewJoin.enabled`、`coalescePartitions.enabled`；显式记录 `spark.sql.adaptive.skewJoin.skewedPartitionFactor`（默认 5）与 `skewedPartitionThresholdInBytes`（默认 256MB），不要依赖默认值——默认值随版本变过。
- **机制**：因为 AQE 只是一个配置开关、不需要改任何一条 SQL，所以它是存量环境里少有的「先开、做一次计划对比、不行就关」的动作——回退成本是一次配置变更，而不是一轮业务回归。代价要提前说清：开启之后，实际执行的计划与 `EXPLAIN` 打印的编译期计划不再一一对应，排障的人必须先确认自己看的是哪一份，否则整场讨论会对着一个已经不执行的老计划进行（谁在什么时候还能改计划的三层边界见 §3.4）。
- **失效条件**：**当没有人把「AQE 之后的计划」纳入证据链时**，开启与否都无法被证明——症状是配置里写着 `true`，但治理队列里没有一条记录说明哪次查询因此变快；观测信号：结案条目的证据一栏里，写不出开关两态计划差异的条目占比接近全部。第二类失效在负载侧：**当瓶颈落在单个阶段内部时**，AQE 没有任何作用点，而团队会先按「资源不足」处理——加并行度、扩资源，因为症状看起来正是任务总数上千、少数几个跑很久。此时的判据是最长任务耗时与中位任务耗时的比值：它持续放大说明问题在倾斜或单阶段瓶颈，不是 AQE 没开（机制见 §3.2.2 的失效点）。
- **档位**：【公开】Apache Spark 官方配置文档与 release note（3.0（2020）引入 AQE、3.2.0（2021）起默认开启）；参数名与默认值请按所装版本核验。

**慢查询治理的闭环化**

- **做法**：采集指标（耗时 / 扫描字节 / shuffle 字节 / 峰值内存）而不是只采集 SQL 文本；异常判定对标历史基线而不是绝对阈值；动作分「改写 SQL」与「改计划」两条路。
- **机制**：因为闭环把「建议」与「前后同一指标」钉在同一条记录上，所以它的产物是一份可审计的决策日志——新人接手时能看出哪些配置变更是有证据的、哪些是历史遗留。代价有两笔：必须先有一层可信的执行指标采集（没有扫描字节 / shuffle 字节就没有锚点），以及每条建议都要付一次回归验证的工时；第二笔决定了闭环的吞吐上限——**产能由验证速度决定，不由提出建议的速度决定**。
- **失效条件**：**当验证这一格的产能跟不上建议产生的速度时**，闭环退化成建议堆积：团队无法区分有效与无效建议，最终整体不再采纳（机制见 §3.2.3 的失效点）。症状与观测信号：队列的进入速率长期大于关闭速率，条目数持续上升而 P50 查询耗时不变；这个信号的第一发现者通常是值班——队列长度会先进周报，查询耗时不会。此时该补的是回归对比这一格，而不是换模型。
- **档位**：【经验】

**AI 驱动优化：建议必须挂在可回滚的变更上**

- **做法**：以计划文本与执行指标为输入产出候选动作（刷新统计信息 / 加索引 / 建物化视图 / 调整分区 / 改写 SQL）；采纳前小流量对比，采纳后记录来源并保留一键回退。
- **机制**：因为你把每条被采纳的建议都落成一次**走审批流的配置变更**，一条错建议的代价就被压成「回滚一次配置」，而不是「等一轮业务回归才暴露」；变更记录里同时留下建议来源、审批人与回滚入口，事后才能把它的效果与同期其它改动分开核算。至于这类工具为什么无法靠自己判断一条建议是否真的有效，机制见 §3.2.3 的失效点。
- **失效条件**：**当建议被直接写进生产配置而不经回归时**，这条从「省人力」反转成「静默累积一堆没人说得清来历的配置变更」。症状：某次性能变化发生后，翻不出是哪个动作引起的。判据：向团队索要建议的采纳率与回滚率，而不是建议条数——条数只说明模型会说话。
- **档位**：【经验】；此类能力的**产品名与可用范围随版本变化**（诊断、顾问、助手等命名各不相同），请以各厂商官方文档当前版本核验，不要按二手对比文章选型。

**自治优化：回路、基线与回滚**

- **做法**：四段回路（观测 → 决策 → 执行 → 验证）各自留下可查记录；执行段强制灰度与一键回滚；验证段与基线比**同一**指标，而不是比「看起来快了」。
- **机制**：因为每一步都留下可查记录，自治的产出不再是一次「更快」，而是一份能被审计的变更史：出事时能定位到是哪一次自动动作、依据哪条观测、由谁批准回滚。代价是三样东西要同时做起来——稳定的基线、统一的指标口径、把优化动作当一等公民的配置管理——而且它们不是一次投入：基线会随业务漂移，需要有人定期重订，否则回路对「变好 / 变坏」的整体判断会失准（回路结构与前提见 §3.2.6）。
- **失效条件**：**当硬约束（变更窗口、最大影响面、SLO 不得低于基线）只写在规范文档里、没有写进配置时**，它会以「某次自动动作落在业务高峰执行」的方式坏掉——事后没人说得出当时为什么被允许。观测信号：自动变更的时间分布与业务高峰的重合度。第二类是目标函数：同一组参数同时服务交互查询与批任务时会来回震荡，表现为延迟与吞吐交替劣化、每次「优化」后另一侧变差；这类振荡通常由业务方在周报里先发现，而不是由值班发现。修法见 §3.2.6 的失效点——按队列分层，而不是继续调权重。
- **档位**：【经验】；判断方法是索要「自治变更的回滚率与误动作率」，而不是加速比。

**自研引擎的嵌入式优化器（Calcite 一类）**

- **做法**：Calcite 负责解析、逻辑关系代数与规则集；物理执行层原位保留（可用 Velox、DataFusion 一类向量化引擎做后端）；为每个数据源实现统计信息接口（行数 / NDV），自定义算子显式映射成 `RelNode`。
- **机制**：因为框架是别人的代码、适配层是你的代码，这条路的能力边界就等于**你实现了统计信息接口的数据源范围**——接入一个数据源，就多一类查询能进入代价比较；没接入的那些，规则能改写它、代价却比较不了它。成本曲线也是这个形状：每新增一个数据源都要再付一次接入成本，框架升级时适配层还要跟着改，所以它是一笔**按数据源计费**的固定税，而不是一次买断（完整机制见 §3.2.4）。
- **失效条件**：**当适配层没有指定 Owner 时**，它会以「每加一个数据源就延期一次」的方式坏掉——症状是规则集越加越多，而代价搜索的覆盖面停在最早接入的那个数据源上；观测信号：`EXPLAIN` 里真正出现物理实现比较的查询占比，是否随接入数据源的数量一起上升——若长期持平，说明适配层没有跟上。核心数据源给不出统计信息时整套退回纯规则这一后果，见 §3.2.4 的失效点。判据：在完全不提供统计信息的前提下跑同一条 SQL，看计划是否改变；不改变，说明你只拿到了规则重写。
- **档位**：【公开】Apache Calcite 的定位与接口形态见其 SIGMOD 2018 论文 *Apache Calcite: A Foundational Framework for Optimized Query Processing Over Heterogeneous Data Sources*。

| 引擎内建 CBO | Spark Catalyst / Trino CBO / StarRocks CBO | 引擎已定的前提下，判据是「它的 `EXPLAIN` 是否已输出基于统计信息的代价比较」——输出里有代价与行数估计，才说明它在做 CBO 而不只是规则重写 | 在已有 CBO 的引擎外再套一层优化器，要做计划表示的双向映射；这层映射在引擎升级时最先坏 |
| 通用优化器框架 | Apache Calcite | 只在自研引擎场景选；判据是「能否为**每个**数据源实现统计信息接口」 | 自己写解析 + 关系代数 + 规则 + 代价搜索：团队没有优化器专家时，这块最难被替代也最难被维护 |
| 向量化执行层 | Velox（Meta）/ DataFusion | 判据是「瓶颈在执行而不在计划」——单核扫描与聚合效率受限时才有增量 | 用向量化去治计划错误，等于让错的计划跑得更快，收益被错误吃掉 |
| 统计信息与自动整理 | 引擎自带 `ANALYZE` / 表格式自带统计 / Databricks Predictive Optimization 一类按使用情况自动整理的能力 | 判据是「统计信息刷新是不是写入链路的一部分」——是，则失败有人负责；否，则要额外指定责任人 | 选独立离线任务且不指定责任人：统计信息静默过期，代价模型失去输入（见 §3.5「统计信息陈旧」） |
| 自适应执行 | Spark AQE（3.0 引入、3.2.0 起默认开启）；其他引擎的运行时纠偏能力按各自官方文档核验 | 判据是「shuffle 后尺寸是否可预测、倾斜是否常见」——预测不了才有增量 | 不开：坏计划不再被任何一层纠偏，直接在生产上兑现——最慢的那批任务先进值班告警，根因归属却要等下一次计划对比才说得清（机制层面的后果见 §3.5「未启用 AQE」） |
| 慢查询采集与计划比对 | 引擎日志 / 系统表 + `EXPLAIN` / `EXPLAIN ANALYZE` | 判据是「能否拿到扫描字节、shuffle 字节这类度量」——拿不到就没有回归验证的基准 | 只采 SQL 文本不采度量：建议无法排序，治理退化成按印象排优先级 |
| AI 诊断与建议 | Snowflake Query Insights / StarRocks AI Advisor / Databricks Assistant / 自研 + LLM | 判据是「采纳率与回滚率能否被度量、建议能否落成可回滚的配置变更」；产品能力与命名随版本变化，以官方文档当前版本为准 | 先买工具再建指标链路：建议一批批产出、一批批没人采纳，工具被贴上「没用」的标签 |
| 自研引擎的后端 | 复用开源向量化引擎 / 自行实现 | 判据是「团队里是否至少有一名懂代价模型的人」，而不是「是否有 C++ 工程师」 | 无人懂代价模型而自研 Cascades：半年后得到一个只在少数查询上生效、且没人敢改的优化器 |

这一类里**最容易被误选的是「AI 诊断与建议」这一格**，误选方式不是买错产品，而是**在指标链路之前买**。典型后果是：工具按周产出建议清单，团队没有基线可以验证任何一条，于是清单被浏览一遍、无人采纳，三个月后同一条技术栈被判定为「AI 优化不可用」——而真正的缺口始终是「扫描字节 / shuffle 字节有没有被采集」。第二位常见的误选是向量化执行：它解决的是执行效率，团队却指望它解决计划错误，投入之后发现慢查询的形态完全没变。

这一格里还有一处口径要写清楚：Snowflake 在查询性能异常检测上的产品名是 Query Insights；**Cortex 是它的 LLM 函数族与语义服务（Cortex Analyst、Cortex Search 一类），不是查询优化的诊断产品**，把它列进「诊断」会让读者按错误的名字去找能力。要用 LLM 承载诊断与建议，走的是本行的「自研 + LLM」——由你决定喂什么输入、留不留回归记录。本格与 §3.2.3 的口径一致；两处都只给产品族与判定方向，某个能力在哪个版本可用，请以厂商官方文档当前版本为准。

### 4.4 存量迁移

存量改造与从零搭建的唯一区别是：**你不能重写 SQL，也不能要求所有下游先改好。**所以这一节的核心是「哪些能用开关解决、哪些要挂账、哪些只能留着」。

**第一件事：只做可一键回退的动作，先拿收益**

- 打开 AQE 及其子能力（配置级，可回退，不改任何 SQL）；
- 给最贵的 N 张表采集统计信息（只增加一批 `ANALYZE`，不改查询语义）；
- 打开慢查询日志与执行指标采集（只增加观测，不改行为）。

这三件都不触碰业务 SQL，因此工期通常在**一周内**【经验，随变更审批链条的长度变化】、退回动作在**一分钟内**【经验，前提是回退已被做成一条命令而不是一份流程文档】。它们能拿到的收益是**同一批 SQL 的计划质量变化**——这也是唯一能在存量环境里被干净归因的收益。

**第二件事：把存量 SQL 分成四类，分别处理**

| 存量类型 | 判据（怎么认出来） | 处理方式 |
| --- | --- | --- |
| 可自动解析的常规 SQL | 有作业定义、能取到 SQL 文本 | 交给优化器，不做人工干预；按季度抽样核对计划是否合理 |
| 带 hint 的 SQL | 语句里出现 hint / 固定计划 / 计划基线 | **打标挂账**：为每条 hint 记录「当初为什么加」与「复核日期」，不要一次性删 |
| 依赖隐式类型转换、非确定函数、动态拼接表名的 | 出现字符串拼表名、`cast` 在 Join 键上、UDF 参与过滤 | 列入盲区清单，**优先改写 SQL**而不是加配置项；这类问题加参数只会掩盖它 |
| 强依赖固定计划的关键报表 | 有 SLA、有对外口径、下游不可改 | 保留计划基线，不参与自动纠偏；把「不参与」写进配置而不是写进文档 |

**第三件事：双轨怎么维持、维持多久**

双轨不是「新旧两套引擎」，而是**同一批 SQL 上「hint 生效」与「优化器决策」两条路径并行**：

- 新查询一律不加 hint（这是双轨能收敛的前提）；
- 存量 hint 保留，但要求每条带复核日期，到期时用「同一 SQL 在 hint 开 / 关两态的计划与耗时」做一次裁决；
- 维持时长按【经验】给一个季度到半年，具体取决于 hint 的数量与复核速度：hint 越多、复核越慢，双轨越长，而双轨越长，新查询误加 hint 的概率越高。

同时维护一份**估计 / 实际偏差看板**：这是双轨期唯一能同时服务两边的指标——hint 是否还有必要、统计信息是否够用，都从它读。

**第四件事：什么信号说明可以退出双轨**

三个信号同时成立即可退出：① hint 条数不再增长，且存量 hint 都有复核日期；② `EXPLAIN` 估计行数与实际行数的偏差稳定在同一数量级（常态化超过 10 倍【经验】即不达标）；③ 一次引擎升级之后，无需人工逐条回归 hint 就能上线。三者缺一就提前退出，结果通常是半年后 hint 又长回来——因为**回退由偶发事件触发，而增长由日常习惯驱动**。

### 4.5 模板 / 示例

**模板 1：Spark —— 统计信息 + CBO + AQE 的配置基线**

```sql
-- 1) 统计信息：表级 + 关键列
ANALYZE TABLE orders COMPUTE STATISTICS;
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS user_id, amount;

-- 2) CBO
SET spark.sql.cbo.enabled = true;
SET spark.sql.statistics.histogram.enabled = true;

-- 3) AQE（含倾斜处理；参数值写进版本化配置，不要留在会话里）
SET spark.sql.adaptive.enabled = true;
SET spark.sql.adaptive.skewJoin.enabled = true;
SET spark.sql.adaptive.coalescePartitions.enabled = true;
SET spark.sql.adaptive.skewJoin.skewedPartitionFactor = 5;
SET spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes = 256mb;
```

**怎么用**：`orders` 换成你自己的表；`FOR COLUMNS` 后面只填**参与 Join 与高频过滤**的列，全列采集会让采集时间失控。两个倾斜参数不要照抄数值——先看开启后计划里分区数是否真的变化，没变化说明这份配置在你的负载上没有作用点。参数名与默认值请按所装 Spark 版本的官方文档核验。

**模板 2：Trino —— 计划前后对比（治理的证据格式）**

```sql
-- 采集统计信息
ANALYZE TABLE iceberg.orders;

-- 让引擎自行选择 Join 分布方式
SET SESSION join_distribution_type = 'AUTOMATIC';
SET SESSION query_max_run_time = '10m';

-- 证据 1：估计（不执行）
EXPLAIN (FORMAT JSON)
SELECT * FROM iceberg.orders o
JOIN mysql.users u ON o.user_id = u.id
WHERE o.amount > 1000;

-- 证据 2：实际（执行并给出各算子真实行数）
EXPLAIN ANALYZE
SELECT * FROM iceberg.orders o
JOIN mysql.users u ON o.user_id = u.id
WHERE o.amount > 1000;
```

**怎么用**：两份输出并排存进治理队列条目，**只有当证据 1 与证据 2 的行数偏差被记下来，这条治理才算有结论**。`query_max_run_time` 是兜底而不是优化手段，别把它当治理动作记进条目。跨源 Join（Iceberg × MySQL）的计划状态请以你所装 Trino 版本与连接器的官方文档为准。

**模板 3：StarRocks —— 观察 CBO 选出的 Join 策略**

```sql
-- 采集统计信息
ANALYZE TABLE orders;

-- CBO 按统计信息选择 Join 策略与分布方式
SELECT o.order_id, u.user_name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.amount > 1000;
-- 用 EXPLAIN 确认：小表一侧是否被选为广播侧

-- 资源侧兜底（防止一条坏计划拖垮整实例）
-- 排队相关的会话变量在各版本命名不统一，这里不给可直接复制的赋值：
-- 请按你所装 StarRocks 版本的官方文档，查清启用资源排队的变量名（`enable_query_queue` 一类命名）后再填
SET query_timeout = 300;
```

**怎么用**：这段的价值全在 `EXPLAIN` 那一步——**不带 `EXPLAIN` 跑一遍什么也证明不了**。队列与超时是资源侧的护栏，不是计划质量的修复手段；把它们写进治理条目会掩盖真正的计划问题。**上面那行排队变量是留白，不是可照抄的赋值**：照抄可能无效或直接报错，请按你所装 StarRocks 版本的官方文档核验后再写入配置；`query_timeout` 一类的超时变量语义较稳定，同样以官方文档为准。

**模板 4：慢查询闭环（采集 → 诊断 → 建议 → 验证）**

```python
# 1) 采集：带度量的条目，不是只有 SQL 文本
slow_queries = collect_slow_queries(
    threshold_seconds=60,          # 阈值按你的 P99 定，不要照抄
    metrics=["duration", "bytes_scanned", "shuffle_bytes", "peak_memory"],
)

for q in slow_queries:
    # 2) 取证
    plan = get_explain_plan(q.sql)          # 估计
    actual = get_explain_analyze(q.sql)     # 实际

    # 3) 分类：SQL 写法问题 还是 计划选择问题
    category = classify(q.sql, plan, actual)

    # 4) 建议（规则优先，长尾交给模型）+ 5) 验证
    suggestion = advisor.suggest(q.sql, plan, actual, category)
    if suggestion.action == "refresh_statistics":
        refresh_statistics(q.tables)
        record_before_after(q.id, before=q.metrics, after=measure(q.sql))
    else:
        open_ticket(q, category, suggestion)  # 改写类走人工，不进配置
```

**怎么用**：`threshold_seconds` 与 `metrics` 两处必须换成你自己的口径；`classify` 与 `advisor` 是你自己的实现或采购的工具。**不要照抄的是「采集就完事」这部分**——循环里真正产生价值的只有 `record_before_after` 那一行，把它删掉这段代码就退化成日志收集器。

**模板 5：LLM 诊断的输入格式（工具无关）**

```text
【任务】只做诊断与建议，不执行任何变更。

【输入】
SQL：{sql}
执行计划（含估计行数）：{plan_estimated}
执行计划（含实际行数）：{plan_actual}
指标：耗时 {duration}s；扫描字节 {bytes_scanned}; shuffle 字节 {shuffle_bytes}

【输出要求】逐条给出，每条必须包含：
1. 判断（估算偏差 / 倾斜 / 写法 / 缺统计信息 / 无法判断）
2. 证据（引用上面的哪一行数字）
3. 建议动作（改写 SQL / 刷新统计信息 / 调整参数 / 建物化视图）
4. 预期改善的**指标名**，以及如何验证（跑同一条 SQL 比哪个数）
无法从输入判断时，写「无法判断」并说明缺哪一项输入。
```

**怎么用**：把 `{...}` 逐格填上你的真实取值；**不要把「预期改善百分比」加进输出要求**——那是模型编造数字的最主要入口。第 4 条要求的是「指标名 + 验证方式」，这一步的作用是让建议天然带上可回归的判据。模板本身与厂商无关，OpenAI、Anthropic 等通用对话接口都能直接承载；各家的 SDK 接口与可用模型名随版本变化，请按对应官方文档核验。

**模板 6：Calcite 自定义优化器骨架**

```java
// 规则阶段：与代价无关，先做重写
RelOptPlanner planner = ...;
planner.addRule(FilterPushDownRule.INSTANCE);
planner.addRule(JoinReorderRule.INSTANCE);
planner.addRule(ProjectFilterTransposeRule.INSTANCE);

// 代价阶段：需要你为每个数据源实现 TableStatistics（rowCount / NDV）
// 未实现时，planner 会退回按规则顺序取第一个可用实现
RelNode optimizedPlan = planner.optimize(logicalPlan);

// 核验：在完全不提供统计信息的前提下重跑，
// 若计划与提供统计信息时完全一致，说明只拿到了规则重写
```

**怎么用**：这段是骨架，`...` 处要接你自己的 catalog 与统计信息适配器。**不要照抄的是规则清单**——规则集要与你的算子集匹配：自定义算子若没有被显式映射成 `RelNode`，规则与代价都看不见它（见 §3.2.4 中名为「**代价**」的那一条，不是名为「失效点」的那一条——后者讲的是核心数据源给不出统计信息时整套退回纯规则），于是你会以为规则生效了，实际这一支从未被重写。另外，上面几个 `*Rule.INSTANCE` 只是占位示例，**规则类名以你所装 Calcite 版本的 `CoreRules` 为准**（如 `CoreRules.FILTER_INTO_JOIN` 一类），照抄可能编译不过。

### 4.6 成本：这套东西的账单

优化器是本书里最少花钱、最多花「时间预算」的主题：它的主要成本**不是钱，而是把时间花在谁身上**——优化耗时进的是查询自己的时间预算，治理成本进的是人的工时。三项里与本主题相关的是这两项：

- **优化耗时（运行时成本，本主题特有）**：CBO 搜索不是免费的。**推算**：一条查询的总耗时 = 优化耗时 + 执行耗时，而 Join 顺序的动态规划复杂度是 O(2^N)（§2.2：状态空间就是参与 Join 的表的子集数），N 增大时优化耗时可能先于执行耗时顶上去。**为什么贵在这里**：这笔成本与你问的查询有多复杂直接挂钩，而不是与集群有多大挂钩；因此对策是**给搜索预算设上限**，并把优化耗时计入总耗时的分母（§4.1 Step 2；§4.9 第 4 条量的是它的 P50 与 P99）。
- **人力（固定项，也是产能上限）**：慢查询闭环的吞吐**由回归验证的速度决定，不由产生建议的速度决定**（§4.2 第 3 条）。**推算**：闭环周吞吐 ≈ 每周可用于回归验证的工时 ÷ 单条建议的验证工时；产出速率再高，验证这一格跟不上就会退化为「建议堆积」。**为什么贵在这里**：优化是「改一条、验一条」的手艺活，验证工时压不下去，加多少建议产能都是白费。
- **统计信息采集与 AI（小额）**：`ANALYZE` 占采样 I/O，随表数与采集频率走【经验：相对执行算力占比很小，但挂进写入链路才有人负责】；AI 诊断按 token 计费，属边际项，单价按所用模型官方定价页代入（每百万 token 落在数美元到数十美元区间【经验】）。

**硬件：与本主题无关**——优化器是软件层，不新增硬件。通用账法见 [Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节只标这个主题把钱花在哪一格。

### 4.7 容灾与故障演练

优化器没有副本、也没有可用区可切——**它是同一条 SQL 上的一层决策，编译期不产出任何需要保住的在线状态**，跨地域容灾在这里不成立（通用容灾见 [Ch12 §07](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)）。本主题独有的失效形态是**计划质量静默劣化 + 结论不可复现**：

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 统计信息陈旧 / 采集失败（§4.2 第 1 条） | 计划质量静默下降，同一 SQL 在批任务与交互查询上拿到不同质量的计划 | 留一份「上次已知良好计划」作基线，必要时回退配置 | 抽 3 张 Join 大表跑 `EXPLAIN` 与 `EXPLAIN ANALYZE`，看估计 / 实际行数偏差是否 > 10 倍【经验】 | 不适用：这是渐进劣化、不报错，判据是偏差比值而不是恢复时间 |
| hint 与优化器决策并存、且无复核日期（§4.4） | 引擎升级时无法判断哪些 hint 还能撤 | 保留 hint 生效路径，冻结新查询加 hint | 用同一 SQL 在「hint 开 / 关」两态各跑一次，逐条裁决 | RTO【经验：一次升级回归窗口，随 hint 数量】 |
| 自治回路改坏一个配置（§4.2 第 5 条） | 生产延迟或吞吐变差，且说不清是哪一次自动动作 | 一键回滚到基线快照 | 让自治系统故意改一个非关键配置，计时从发现到回滚完成 | RTO【经验：分钟级，前提是回滚被做成了一条命令而不是一份流程】 |

结论：本主题要演练的是**计划对比、hint 两态裁决、一键回滚**这三样，而不是切机房。混沌演练的通用方法见 [Ch12 §06](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)。

### 4.8 演进路线：0 → 1 → 100

优化器的每一级都把力气花在同一个前提上——**代价模型有没有可信输入**，只是每级把它放大一圈：

- **0 → 1（最小可用）**：给最贵的表采统计信息 + 打开 AQE 及其子能力（§4.1 Step 1–2）。**便宜在**两者都不改业务 SQL、退回在一分钟内【经验，前提是回退已被做成一条命令而不是一份流程文档】；**先坏的是判据本身**——采了、开了，却没人对照估计行数与实际行数（§4.1 那句「最常被跳过的是 Step 1 的判据」），于是没有任何记录说得出估计误差本来是多少。
- **1 → 100（规模化）**：慢查询闭环化、分「改写 SQL / 改计划」两条路、AI 只做长尾。**变贵的是验证产能**——每条建议都要付一次回归验证工时，吞吐卡在验证而不是建议上；**先坏的是闭环队列**：进入速率长期大于关闭速率，条目持续上升而 P50 查询耗时不变（§4.2 第 3 条的失效条件）。
- **100 →（观望方向，非必经）**：自治回路（观测 → 决策 → 执行 → 验证）。按 §5.2.3 的定级它停在 **L3**——主流引擎尚未把「由模型决定的计划选择」作为正式 GA 的默认特性，**记录即可，不要在架构里为它预留假设**；若真要往前走，**变贵的是三样基础设施要同时在线**——稳定基线、统一指标口径、把优化动作当一等公民的配置管理。**先坏的是硬约束**：变更窗口 / 最大影响面 / SLO 若只写在文档、不写进配置，它会以「某次自动动作落在业务高峰执行」的方式坏掉（§4.2 第 5 条的失效条件）——这正是 §1.4「自治优化」阶段的核心矛盾。

### 4.9 自检清单

设计与模式层的判定（模式选得对不对、哪些表根本没有统计信息、谓词相关这类估算盲区）见 §3.7 的自检清单；下面只列**必须动过系统才有答案**的项。

- [ ] 抽 3 张参与 Join 的大表，`EXPLAIN` 的估计行数与 `EXPLAIN ANALYZE` 的实际行数是否在同一数量级？偏差超过 10 倍【经验】的有几张？
- [ ] 每张大表能否查到「最后一次统计信息采集时间」？能否查到「上一轮采集失败过几次」？
- [ ] 拿当前最贵的 10 条查询，在 AQE 开关两态各跑一次：计划里被改写的（Join 策略或分区数）有几条？一条都没有的话，开启它的理由是什么？
- [ ] 「优化耗时 / 执行耗时」的**分布**（P50 与 P99）是多少？有没有一类查询的优化耗时占比超过执行耗时？
- [ ] 慢查询治理队列里，已关闭条目的验证方式写得出来吗？随机抽 5 条，能当场说出前后指标的几条？
- [ ] 随机抽 5 条存量 hint，用同一 SQL 的「hint 开 / 关」两态各跑一次：仍有必要的几条、可以撤的几条？裁决结果与复核日期写回条目的有几条？
- [ ] 是否存在强相关谓词（如市 / 省、店铺 / 品牌）被当成独立条件估算？抽样对比这列的估计与实际偏差。
- [ ] 统计信息盲区清单在不在？随机挑清单上 3 张表跑 `EXPLAIN`，确认它们的计划里确实没有代价比较，且清单上写着「此处无代价比较」。
- [ ] 下一次引擎升级前，能否用一条命令跑完全部存量 hint 的回归？上一次升级遗留的 hint 回归条目还剩几条没关？
- [ ] AI 建议的采纳率与回滚率各是多少？——答不出这两个数，说明建议链路没有验证段。
- [ ] 自治回路上一个被自动改掉的配置，是谁在什么时候回滚的？记录在哪？自动变更的时间分布与业务高峰是否重合？
- [ ] 若自研引擎使用嵌入式优化器：在完全不提供统计信息的前提下跑同一条 SQL，计划是否改变？

### 4.10 小结

> 本节小结：这条落地路径里唯一决定成败的环节是 **Step 1 的判据——统计信息是否与数据同步，并且这件事被持续观测**。因为代价模型的一切比较都以它为唯一输入，而它的失效是静默的（不报错、只是每条查询慢一点），所以它比后面任何一步都更值得投入监督成本：AQE、AI 诊断、自治回路都只是在这份输入上做更聪明的加工，输入过期时它们会一起失效，而且失效时看起来都像「工具不好用」。
>
> 存量改造的读者请把注意力放在 §4.4 的「估计 / 实际偏差看板」上——它是双轨期唯一能同时回答「hint 还有没有必要」与「统计信息够不够用」的信号。
>
> 💡 **思考锚点**：拿你当前最贵的 10 条查询过一遍 §4.9 第一条：估计 / 实际行数偏差超过 10 倍的有几条？对这几条，查得到最后一次统计信息采集时间、上一轮采集失败次数吗？——如果偏差能看见但这两个采集信息查不到，你缺的是采集任务本身，还是那块「估计 / 实际偏差看板」？
