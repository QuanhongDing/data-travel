## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

优化器是最容易被「AI 加持」这四个字带偏的主题：它本身就有「选择」这个动作，于是任何给出建议的系统看起来都像是在优化查询。所以本节按机制排，而不是按名字排——先问「它改的是这一次的计划，还是下一次的配置」，再谈成熟度。

判据只有三条：

- **①** 已 GA 且有正式 release note——能按名字与年份被第三方检索到；
- **②** 有第三方（非厂商）公开生产案例——建设方自述不算第三方；
- **③** 接口稳定——不是每次小版本都会改的预览特性。

按这三条，方向只分三级：

| 级别 | 判据（三条全中才算） | 你该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ①②③ 全中 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口或生态未稳；或仅有厂商自有案例；或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

两条执行规则写在前面，避免同一方向在两处被评成不同级别：

- **第②条不满足就是 L2**，不写「准 L1」「L1 的边界案例」这类说法；本节没有为查询优化器这一主题另立修正条文，上表三条判据在 5.2 的逐项评估里逐字沿用；
- **合并行只取一个级别**：当一个行里合并了若干支线时，取其中**最容易被读者按判据核验**的那一支定级，并把更弱的那一支写在明处（详见 5.2.2）。5.1 的表与 5.2 的逐项评估必须一致，写完 5.2 要回核一遍。

本主题在 AI 时代的可辨识方向有四个，按**机制**归入下面四行。产品版本号一律不锚定，因为同一产品在不同版本里的状态不同，写错比省略更贵。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **LLM 辅助诊断与自然语言优化** | L2 | ① 满足：Databricks Assistant 有官方文档页与公布说明（2023 年公布，其后进入 GA）；② 不满足：可指名的案例都出自厂商自身；③ 不满足：模型、提示词与语义层接口都在变 | 把可观测性补齐（最终计划 + 估算 vs 实际行数），再让诊断建议进入人的决策链 |
| **代价函数的扩项：时间窗、目标维度与作用域** | L2 | ① 满足：Databricks Predictive Optimization 按表的使用情况自动执行 `OPTIMIZE` / `VACUUM` / `ANALYZE`，有官方文档页与公布说明（2023 年前后）；② 不满足：无可指名的第三方非厂商公开生产案例；③ 不满足：目标权重与跨引擎作用域没有稳定接口 | 用它做回路层的维护自动化（统计信息、整理、预计算），不要让它决定单条查询的计划 |
| **自治优化与「AI + CBO + AQE」融合** | L3 | ① 不满足：没有把「由模型决定的计划选择」作为正式 GA 默认特性的 release note；② 不满足；③ 不满足：动作空间、回退策略与漂移监控口径都没有稳定接口 | 可以读论文、可以复现，不要在架构里预留假设 |
| **优化器的外部知识：案例 RAG 与依赖图** | L3 | ① 不满足：无可锚定的正式 release note；② 不满足；③ 不满足：语料与图的格式、更新机制均为自研 | 先确保语料带版本与年份，再谈接入决策链 |

**本节四行里没有 L1。** 原因不是优化器这个主题不成熟——恰恰相反，本主题里真正达到 L1 的能力（基于统计信息的 CBO、运行时自适应执行、统计信息自动采集）都已 GA 并在生产中普遍开启，但它们**不是 AI 带来的**，本章 §7.3 已把它们作为既有机制逐条讨论过。本节评估的是「AI 给优化器带来了什么新机制」，而这一层四个方向都卡在第②条：拿不出可指名的、非建设方自述的公开生产案例。按上面的规则，缺第②条就是 L2（或更弱），本节不做例外。

还有一件必须先说清楚的事：**这四条对优化器的改动深度完全不同。**

- 方向一（诊断）改变的是**人机分工**——读计划这一步被外包，决策权没动；
- 方向二（扩项）改变的是**目标函数**——时间窗从一条查询拉长到一段负载，目标从性能扩到成本，作用域从单引擎扩到跨引擎；
- 方向三（自治与融合）动的是**决策机制本身**——这是唯一真正动优化器内核的方向，也是四条里最不该急着接进生产的一条；
- 方向四（外部知识）改变的是**优化器可得的信息**——语料与依赖图是系统以前根本没有的资产，但它们落在引擎之外，不改变计划选择。

一句话概括四个方向的共同边界：**今天所有可落地的 AI 优化，作用点都在「回路层」——改的是下一次查询的配置，而不是这一次查询的计划。** 判断任何一项新能力属于哪一层，用下面的办法最快：把它关掉，看影响的是「本查询」还是「下一次查询」。

这也是优化器这个主题的特殊之处：**它的错误是静默的**。一个错误的计划不会报错，只会慢；等业务方来投诉时，中间的证据链往往已经断了——编译期计划被运行时自适应改写过，执行指标也可能已过保留期。所以本节对成熟度的判断最终都落到同一个可操作的问题上：**出问题时你手头有没有基线？** 没有基线的能力，即使它确实有效，也先不要接进生产路径。

### 5.2 演进方向逐条拆解（核心节）

本节展开的四个方向，读的时候请始终带着同一个问题：**它的作用点是「这一次查询的计划」，还是「下一次查询的配置」？** 前者动引擎内核，后者动引擎周边的回路——四条里只有方向三动内核，也正因如此它停在 L3。

#### 5.2.1 LLM 辅助诊断与自然语言优化：被改变的是「谁读懂计划」

- **旧做法与它的卡点**：一条慢查询的定位路径是固定的——`EXPLAIN` → 读计划树 → 找到估算与实际差得最远的那个算子 → 反推是统计信息陈旧、SQL 写法，还是数据倾斜。卡点是**门槛与信息不对称**：
  - 会读计划的人在组织里稀缺，同一条查询的三次性能波动要重来三遍分析；
  - 写 SQL 的人看不到计划，看计划的人不知道业务在问什么（主文件 §1.2 的痛点列表第 4 条「人工调优：每条慢查询都靠 DBA 手工优化」说的正是这一步）；
  - 这不是引擎能力缺失：CBO、AQE、谓词下推、列剪裁（主文件 §2.1）都在，缺的是**把观察翻译成假设**的人；
  - 还有一个隐性缺口：**可观测性不默认具备**。最终计划（运行时自适应改写之后的那个）往往要额外采集，「估算行数 vs 实际行数」的对比也不总在执行详情里——没有这两样，专家也只能凭印象。
- **AI 改变了什么机制**：把「计划 + 指标 → 可能原因」这一步由人换成模型。改变的是**诊断环节的人力成本与门槛**，不是优化器的输入——它读的是同一批 `EXPLAIN` 输出、执行指标与统计信息，没有新的观测通道；也不是决策权——建议要人采纳才生效，所以它落在回路层。
- **由此得到的**：因为门槛从「会读计划」降到「能读懂一段中文」，所以慢查询治理的**覆盖面可以扩大**：
  - 以前资源只够分析最贵的那几条查询，现在可以对全量慢查询做一遍初筛并排序；
  - 排完序之后，「值得人看」的从几十条降到几条【经验】——这是它真正省下的东西，而不是省下分析本身；
  - 收益上界很明确：**等于一个耐心的专家手动读一遍能得到的东西**，因为信息量没有增加。
- **由此付出的**：四项代价。
  1. **建议的正确率不可验证**：除非你有同口径的前后指标（行数、NDV、直方图、实际执行耗时分布），否则无法判断它是在推断还是在猜。**没有核验链路的 AI 建议，和一段随机提示词等价。**
  2. **归因会被「叙述」替代**：模型给出的解释在语言上是连贯的，而计划选择的真实原因是统计信息；两者不一致时，人会相信更好读的那一个。
  3. **幻觉的重灾区是版本与语法**：hint 写法、参数名、算子是否受支持都随版本变化。判定方法很硬——把建议里出现的每一个参数名、hint 关键字，在本版本官方文档里检索一次，**命中为 0 就不要执行**。
  4. **成本结构变了但没变小**：诊断省下的是人力，新增的是「验证与回滚」的工程；后者是一次性投入且不可省，前者是持续可变成本——两笔钱不成比例，把它当同一笔预算会在第二个月超支。
- **证据与来源**：面向 SQL 与数仓的自然语言助手有可检索的官方文档支撑——Databricks Assistant 于 2023 年公布（官方文档有独立页面，其后进入 GA）【公开】（Databricks Assistant 文档, 2023）；Snowflake 侧的同类能力以 `Snowflake Cortex` / `Snowflake Copilot` 为入口（2023 年起陆续公布，各能力的预览与 GA 时点以官方文档为准）【公开】（Snowflake Cortex 文档, 2023 起）。厂商侧的慢查询诊断与「顾问（Advisor）」类能力命名各不相同——同一个能力在不同产品里的叫法不一样，因此本节不按产品名断言具体特性，某个能力在某个版本是否可用一律以其官方文档为准。另一条更硬的公开结论是「计划质量差的主因是基数估算误差」（How Good Are Query Optimizers, Really?, VLDB 2015）——它同时给出了这类工具的天花板：**如果根因是估算误差，把结论翻译成人话并不会减小误差**，只是让误差更容易被接受。
- **成熟度**：**L2**。① 满足（Databricks Assistant 有官方文档页与公布说明，2023 年公布）；② 不满足（可指名的落地案例都出自厂商自身）；③ 不满足（模型、提示词与语义层接口都在变）。**可做试点，不要做核心依赖。**

诊断建议分三类，三类能被核验的程度差别很大——这也是「要不要接受这条建议」本身的判据：

| 建议类型 | 例子 | 谁能核验 | 落地方式 |
| --- | --- | --- | --- |
| 改配置 | 提高并行度、调整分区数、增加队列配额 | 只有压测能核验：改前后各跑一遍，比最终计划与耗时分布 | 走变更流程，下一次运行生效 |
| 改 SQL 或加 hint | 改写子查询、加广播提示 | 能在 `EXPLAIN` 里核验是否真被采纳（hint 被静默忽略是常见情况） | 改代码，随版本重评 |
| 改统计信息 | 重新采集、提高采样率、建直方图 | 能定量核验：估算行数与实际行数的差距是否缩小 | 一次动作，收益可复现 |

**三类里只有第三类可以被定量核验**，而它恰好也正是 VLDB 2015 那条结论指向的根因所在。这就是 5.2.1 的实用结论：把诊断建议当**线索**用——用它定位「该去补哪一块统计信息」，而不是当配置指令执行。

#### 5.2.2 代价函数的扩项：时间窗、目标维度与作用域

- **旧做法与它的卡点**：CBO 的目标函数是**单条查询**的执行代价，且只有三项（主文件 §2.2）：

```text
Cost = α × I/O + β × CPU + γ × Network        ← 单条查询、三项成本、编译期定值
        ────────────────────────────────────────
它结构性看不见的三样东西：
  ① 看不见未来   ：不知道这条查询会不会重复出现 → 不为「高频查询预先物化」负责
  ② 看不见别的目标：成本、能耗不在代价里 → 不能为「省一半钱、换更慢的执行」做选择
  ③ 看不见引擎之外：跨源时各源统计口径不一 → 「接得进来」不等于「算得准」
```

  第 ③ 条的具体形态是：跨引擎优化在架构上落在嵌入式优化器框架这一层（Apache Calcite: A Foundational Framework for Optimized Query Processing Over Heterogeneous Data Sources, SIGMOD 2018），它把关系表达式与元数据接口标准化，让一份计划可以指向多个源——**代价是每个源都要补齐统计信息接口**，本章 §7.3.4 把这笔工作量叫嵌入式优化器的固定税。
- **AI 改变了什么机制**：把目标从「这一次执行最便宜」改成「一段负载在未来一段时间最便宜」——用历史查询日志做预测（哪些查询会再来、该为谁建物化视图或索引），并给代价函数加项（成本、能耗）。机制上是**目标函数的扩项与时间窗的拉长**，不是搜索算法变聪明：搜索的还是那些候选，只是打分口径变了。
- **由此得到的**：因为多了一个以前没有的输入（历史负载），所以「该不该物化、该不该建索引」这类决策从「靠人拍」变成「按负载收益排序」，而收益是可以算出来的：
  - 收益 = 被物化查询的频次 × 单次节省 −（物化与刷新成本 + 额外存储）；
  - 这个式子里的每一项都来自你自己的日志与账单，不依赖任何厂商口径；
  - 这也解释了为什么这类能力在企业里**最先被接受**——它在回路层，不影响单条查询的确定性，改错了不会让今天的查询变慢。
- **由此付出的**：五项代价。
  1. **目标变多就没有唯一答案**：性能 / 成本 / 能耗之间的权重必须由人给定，一旦定错，系统不是偶尔选错，而是**按错的口径稳定地选**——错得一致，很难在抽样里被发现。
  2. **预测错了代价是负的**：为一条不再出现的查询建了物化视图，会持续付存储与刷新成本，收益为零。负载预测的准确度在这里直接变成钱。
  3. **跨引擎把「估算口径」问题放大**：不同引擎对同一列的 NDV 与直方图定义、采样率都不同，跨引擎之间的代价比较在原理上就不严谨——你得到的是**近似排序**，不是可比的分值；把它当成打分表用会得出精确的错误结论。
  4. **新增状态**：负载仓库、物化视图生命周期、权重配置，都是新的运维对象；而它们一旦存在，就有人会去改，改动的影响面比改一条 SQL 大得多。
  5. **多目标会削弱你自己的前后对比能力**：权重一旦调整，上个月的性能基线就不能再用来判断这个月的改动是好是坏——换来更宽的目标，付出的是可比性。

负载级收益必须自己算一遍，否则「该不该为它建物化视图」只能靠感觉：

- 收益 = 查询频次 × 单次节省 −（物化刷新成本 + 额外存储成本）；
- 以一条每天跑 24 次的报表查询、单次扫描 1 TB、单次耗时 10 分钟为例【推算】（推导链：每天 24 次，按 30 天算 = 720 次/月；物化后单次扫描降到 10 GB，单次减少扫描量 ≈ 1 TB − 10 GB ≈ 0.99 TB；单次耗时按 10 分钟降到 10 秒估，节省 ≈ 9.83 分钟 → 每月节省 ≈ 720 × 9.83 分钟 ≈ 118 小时）；
- 对照项是它的成本：刷新频率、额外存储、以及刷新失败造成的陈旧风险；
- **这三个量全部来自你自己的日志与账单**，不依赖任何厂商口径——这也是为什么这类判断适合做自动化而不适合做「智能」：它不需要预测未来，只需要统计过去。

- **证据与来源**：「按使用情况自动执行维护类操作（整理、统计信息采集）」已是有官方文档的产品能力：Databricks 的 Predictive Optimization 按表的使用情况自动执行 `OPTIMIZE` / `VACUUM` / `ANALYZE`，官方文档有独立页面【公开】（Databricks 文档 `Predictive optimization`, 2023 年前后）。同族能力在别的厂商侧命名不同，可按 `automatic re-clustering`（BigQuery）、`Automatic Clustering`（Snowflake）检索，但要注意后者的触发条件是数据变化、不是查询负载——「按使用情况」这四个字必须逐个产品核，可用范围与表类型限制一律以官方文档为准。判定方法：看它是不是**默认开启**的正式特性，以及它自动执行的动作清单里有没有「由历史负载驱动的自动物化 / 自动索引」；只写「推荐」字样的是回路层的建议，不是引擎的决策。另一条可核验的支撑是本章 §7.4 的成本函数写法——它把「统计信息采集的 I/O 与存储」和「误判造成的额外执行成本」拆成两项，本节只是把同一个框架往负载级拉长。
- **成熟度**：**L2**。① 满足（Databricks Predictive Optimization 有官方文档页与公布说明，2023 年前后）；② 不满足（无可指名的第三方非厂商公开生产案例）；③ 不满足（目标权重与跨引擎作用域没有稳定接口）。**这一行合并了两支**：作为定级依据的是「按历史负载预测的维护自动化」，它有 ①；同一节内的「多目标（成本 / 能耗）」与「跨引擎」两支目前只有论文与自研形态，单独看只到 L3——把弱的那支写在明处，是为了不让读者以为它和定级依据同等成熟。

#### 5.2.3 自治优化与「AI + CBO + AQE」融合：决策权能不能交出去

- **旧做法与它的卡点**：既有架构把决策权分层固定，且**同一时刻只能由一层做决策**（本章 §7.3.3 给了同一张分层图）：
  - 编译期：CBO 定关联顺序与关联策略，之后不再参与；
  - stage 边界：AQE 用实测统计改写分区数与关联策略；
  - stage 内部：算子已启动，不可替换；
  - 回路层：两次查询之间改配置（统计信息、索引、物化视图、参数）。
  卡点是**估算误差**：计划质量差的主因是基数估计（VLDB 2015），而估算依赖统计信息的新鲜度，采集频率与误判成本方向相反（本章 §7.4 的成本结构给出同一个权衡），所以「多快算够」永远是折中而不是解。
- **AI 改变了什么机制**：这条方向上有两条路径，机制完全不同，必须分开说：

```text
路径 A：替换决策层（学出来的估算与搜索）
   SQL ──► [模型：估基数 / 直接生成计划] ──► 计划
   改的是优化器内部的信息与决策机制
   代价：没有现成基线可退回；分布漂移时静默退化

路径 B：包裹决策层（在引擎的候选之间做选择）
   SQL ──► 引擎原优化器 ──► {候选计划 / 提示集合} ──► [模型：挑一个] ──► 计划
   代价模型仍在原处，被学的是「选择规则」，动作空间被引擎限定
   收益：可以一键退回引擎的默认计划 —— 这是它能落地的前提
```

- **由此得到的**：因为路径 B 把动作空间限制成引擎自己产出的候选（而不是让模型自由生成计划），所以学出来的选择**在出错时可以退回基线**——可回退是它比路径 A 更早被实践接受的机制原因；反过来也解释了路径 A 的处境：端到端的优化器一旦给出计划，你手里没有一个现成的基线可以退回去，于是「它变慢了」这件事既无法归因，也无法回滚。

两条路径的差别，可以压成一张对照表：

| 维度 | 路径 A：替换决策层 | 路径 B：包裹决策层 |
| --- | --- | --- |
| 改的是什么 | 估算与搜索本身 | 候选之间的选择规则 |
| 动作空间 | 模型自由生成计划 | 引擎产出的候选 / 提示集合 |
| 能否退回基线 | 不能（没有现成基线） | 能（一键回到引擎默认计划） |
| 失效形态 | 静默退化：不报错，只是变慢 | 退化为引擎原有水平 |
| 新的运维对象 | 模型版本、漂移监控、训练数据 | 候选集与提示集合的版本 |
| 公开代表 | Learned Cardinalities（2019）、Neo（2019） | Bao（2021） |

第三行与第四行是这张表里最实用的两行：**能不能退回基线，决定了它能不能进生产**；失效形态决定了它值不值得赌。一个失效时「退化为原有水平」的能力，可以试；一个失效时「静默变慢」的能力，必须先有监控才谈得上试。

「神经符号优化（神经优化 + 符号优化融合）」在这个二分里没有第三个位置：它的「神经」一半就是路径 A（学出来的估算与计划），「符号」一半是引擎里既有的规则与代价模型。所谓融合，落到工程上就是让学习组件挂到 Memo 与代价模型这两个既有接口上（证据与来源里那条 Graefe 的接口定义）——只要它仍在引擎产出的候选之间挑，它表现成路径 B；一旦它自己决定计划，它表现成路径 A。这不是第三条路，而是同一条接口上的两种强度，本节因此把它归入方向三。

- **由此付出的**：四项代价。
  1. **路径 A 不可解释，且会静默退化**：计划由模型给出时，你无法回答「为什么选它」，而优化器恰恰是最需要解释能力的地方（同一 SQL 明天为什么换了计划）；数据分布漂移时它不报错，只是变慢——这是最难发现的一类退化。
  2. **路径 B 的收益上界被候选集锁死**：如果引擎根本没生成那条更好的计划，选择层也挑不出来。它改善的是「在已知候选里挑得更好」，不是「想出新的候选」。
  3. **训练与推理回路本身是新成本**：采样、回放、避免「为了训练而制造采集负载」，以及模型版本归档——否则半年后没人能解释当时的计划为什么长成那样。
  4. **与 hint 的耦合**：为限制动作空间而使用 hint，等于把「计划稳定性」从优化器转移到 hint 维护上，而 hint 会随版本失效——你换来的稳定性有到期日。
- **证据与来源**：Cascades / Volcano 框架定义了候选计划空间与代价模型之间的接口（Graefe, IEEE TKDE 1994；IEEE Data Engineering Bulletin 1995），这是任何学习型组件必须挂靠的两个点（Memo 与代价模型），否则它改不了计划【公开】；两条路径各有公开代表——Learned Cardinalities: Estimating Correlated Joins with Deep Learning（CIDR 2019）与 Neo: A Learned Query Optimizer（VLDB 2019）代表路径 A，Bao: Making Learned Query Optimization Practical（SIGMOD 2021）代表路径 B【公开】。判定方法：不要去 `EXPLAIN` 输出里找某种「模型参与」的特殊标记——公开产品目前没有约定这样的标记，照这个特征去查会一无所获。要查的是另外两处：一是 release note 与官方文档里，「计划选择」是否被列为**默认**路径（而不是可选开关、也不是「建议 / 解释」）；二是这条路径能不能一键退回引擎默认计划——回退方式在文档里应当有名字（某个配置项或开关）。文档里只有「建议 / 解释」字样的属于诊断层，不是决策层。
- **成熟度**：**L3**。① 不满足（主流引擎的 release note 里没有把「由模型决定的计划选择」作为正式 GA 的默认特性）；② 不满足；③ 不满足（动作空间、回退策略与漂移监控口径都没有稳定接口）。**记录即可，不要在架构里为它预留假设。**

#### 5.2.4 优化器的外部知识：案例 RAG 与依赖图

- **旧做法与它的卡点**：优化知识以「人的经验」形式存在——某个倾斜特征该用哪种预处理、某类子查询该怎样改写、历史上哪次调优与现在这条查询相似。这份知识有两个载体问题：
  - **引擎读不到它**：引擎只读统计信息，人脑里的模式对它是不可见的；
  - **组织检索不到它**：案例散落在工单、文档与聊天记录里，同一个坑不同团队各踩一遍。
- **AI 改变了什么机制**：把两个原本只存在于人脑里的结构外化：
  - **优化器知识 RAG**：历史优化案例与规则 → 向量化 → 检索（向量库 + 检索链路；LanceDB 一类向量库与 LangChain 一类框架）；
  - **优化依赖图**：优化器与查询、视图、索引之间的依赖 → 图（图库 + 模型查询；Neo4j 一类图库）。
  **这是本节唯一一条资产始终落在引擎之外的「新增输入」**：5.2.2 的历史负载同样是引擎以前没有的输入，但它最终以配置（物化视图、索引、统计信息）的形态回到引擎里；语料库与依赖图不进引擎——它们只在人的决策环节被使用，连「回到引擎」的通道都没有。5.2.1 与 5.2.3 的模型读的则是同一批既有观测（计划、指标、统计信息），信息量没有增加。
- **由此得到的**：因为语料与图都落在引擎之外，所以它们**不改变计划选择，只改变人的决策效率**：
  - 可检索的案例把重复问题的处理时间压下来——同一类慢查询不必从零分析；
  - 依赖图把改动的影响面从「靠记忆」变成「可查询」（影响面必须由血缘系统提供而不是靠人回忆，书内「数据血缘与影响面」一章（11-cross-cutting/05-lineage-and-impact）已把这条机制与案例系统展开过）。
- **由此付出的**：五项代价。
  1. **语料质量决定一切，而且它会过期**：案例里记的是「当时那个版本的参数名与行为」，版本一变就是错的，而检索会把旧答案**高置信度地**端到端呈现——比没有答案更危险。
  2. **检索到的「相似」是文本相似，不是计划相似**：两条 SQL 措辞相近、数据分布完全不同时，召回的是噪音。判定方法：用「召回后建议被采纳的比例」度量，而不是检索命中率——命中率衡量的是它找到了东西，采纳率衡量的是它找对了东西。
  3. **图会与真实依赖漂移**：依赖靠解析与登记，解析不了的场景就是缺席；而**缺席在图上表现为「没有边」，不是「未知」**——图不会告诉你它不知道。盲区必须被单独标记并追踪，这一条书内血缘一章已有成套做法。
  4. **新增两个要运维的系统**（向量库、图库）与一条 ETL 链路，而收益是间接的（省人力），因此最难立项，也最容易在预算收紧时第一个被砍——被砍之后案例语料就停止更新，反而变成第 1 条代价里的那种「过期答案」。
  5. **语料需要有人负责维护**：它不像代码有编译器和测试把它拽回正确状态，过期与否只能靠人看；没有维护人的语料库，六个月后就是一份高置信度的错误来源。第 1 条代价说的是「语料会过期」这件事本身，这一条说的是**没有人为此负责**——两者常常同时发生。
- **证据与来源**：文献侧可核验的是路径 A / 路径 B 两条研究线（Learned Cardinalities, CIDR 2019；Neo, VLDB 2019；Bao, SIGMOD 2021）；而「把优化案例做成检索库、把依赖做成图」目前以引擎自带的案例库与自研形态存在，没有可锚定的正式 release note。可核验的相邻事实是：影响面必须由血缘系统提供——书内「数据血缘与影响面」一章的机制与案例节给了完整证据。
- **成熟度**：**L3**。① 不满足（无可锚定的正式 release note）；② 不满足；③ 不满足（语料与图的格式、更新与失效机制均为自研，没有稳定接口）。

### 5.3 与本主题既有栈的接口在哪

不写「与 X 结合」这种空话。下面每一行给出的都是**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。这张表的作用是划清责任——本节四项能力的失败都不会由优化器承担，因为它们的接入点都在引擎的决策边界之外。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 模型诊断 ↔ 优化器 | 单向只读：取 `EXPLAIN` 输出与执行指标作输入，产出文本建议；引擎不认识这些建议 | 人：建议不承担责任，采纳即由人承担；不采纳则无影响 | 无回写、无接口版本约束，因此也最安全 |
| 学习型选择层 ↔ 计划的候选空间 | 引擎吐出候选计划或提示集合，选择层挑一个并回写；双方需要一个可回退的基线 | 选择层：若基线不可用，出错即无法回退 | 只有研究原型（路径 B 形态），产品侧未见默认开启 |
| 维护类推荐 ↔ 回路层配置 | 建议改的是**下一次**查询的配置（统计信息、索引、物化视图、整理），必须走变更流程 | 变更流程：优化器对配置的正确性不负责 | 引擎自带的统计信息采集是这条线上最成熟的一环 |
| 案例库与依赖图 ↔ 向量库 / 图库 | 语料与关系存在引擎之外，经检索进入人的决策，不进引擎 | 无人负责：检索结果的对错没有校验环节 | 完全自研，无标准格式 |
| 多目标权重 ↔ 资源计量口径 | 权重必须与计费、配额口径同源，否则优化目标与账单口径打架 | 口径的所有者：口径不一致时谁也说不清选得对不对 | 口径通常分散在平台、财务与引擎三处 |
| 嵌入式优化器（Calcite 一类）↔ 数据源元数据 | 框架只处理关系表达式 + 元数据接口，统计信息由使用者为每个源实现 | 使用者：接完「能查」不等于接完「能被优化」 | 固定税，本章 §7.3.4 已给出核验方式 |
| 优化器 ↔ 表格式统计信息 | 统计信息随表元数据一起存，引擎直接读，不经独立采集任务 | 表格式与引擎双方：版本矩阵不一致时读取会静默失效 | 机制已在本章 §7.3.4 描述，落地程度按你的引擎核验 |
| AI 建议 ↔ 变更审计与回滚开关 | 建议被采纳后必须留下「谁、何时、基于哪条建议、改了什么」以及一键退回的开关 | 变更流程的所有者：没有审计与回滚时，改坏了无法归因 | 通常自建，产品一般不提供 |

这张表里最常出问题的不是第一行（诊断类能力最安全），而是**最后两行**：表格式与引擎的版本矩阵不一致时统计信息会静默读不到，而 AI 建议缺少审计与回滚时会静默累积成一堆没人说得清来历的配置变更。两者共同的特点是——**没有报错，只有后果。**

### 5.5 被过度宣传的部分

**「AI 优化器将取代 CBO，大模型能读懂 SQL 就能给出更优计划」**

- 实际是什么：到目前为止可控的公开进展发生在**包裹**而不是**取代**——把动作空间限定在引擎已有候选之间，由模型在候选里挑（Bao, SIGMOD 2021）；而模型在「读懂 SQL」这件事上做的是自然语言与结构化文本之间的转换（把计划读成人话、把意图写成人话），它不是在做代价比较。
- 为什么会这样：优化器的价值一半在「选得对」，另一半在「可解释、可退避」，端到端替换会同时失去这两样；而一条计划的优劣由**数据**决定，SQL 文本里没有数据——分布信息在统计信息里，不在语句里，所以「读懂 SQL」与「选对计划」之间隔着的正是本章 §2 讲的那套统计信息机制。生产里「今天为什么这样走」是必须能回答的问题，这两条恰好都答不上。
- 什么时候它才会成真：release note 里出现「模型参与计划选择」，并且与它一起出现的是可一键退回的默认路径与分布漂移监控，同时模型拿到的是与你引擎同源的统计信息、并据此做定量比较（而不是凭语句形态猜）。
- 信号：看「默认开启 + 可回退」，而不是看论文里的基准曲线——**一个没有回退路径的优化器，效果越好越危险**；也看它的输出里有没有「估计行数 / 实际行数」这类只有看过统计信息才写得出的量，而不是只有「建议增加索引」这类不含数据的措辞。

**「自治优化 = 无人值守」**

- 实际是什么：自治发生在回路层——改的是下一次运行的配置；而回路层的每一次变更都需要验证与回滚。
- 为什么会这样：优化器配置没有「局部生效」这一说，参数按队列生效，**爆炸半径是整个队列**；把它当「不用管」来用，会在第一次改坏队列时付出全部信任。
- 什么时候它才会成真：建议能被排序（每条带预期收益区间与置信度），并且验证与回滚自动化到「改坏可在分钟级退回」。
- 信号：产品里出现「建议的预期收益区间 + 一键回滚」，而不是一个「自动优化」的开关。

**「有了大模型，统计信息可以不用维护了」**

- 实际是什么：估算误差是计划质量的主因（VLDB 2015），而模型想替代的正是这个环节；但在替代真正发生之前，统计信息仍是唯一的定量输入——把它停掉，不是让上游更空，是让上游只剩猜测。
- 为什么会这样：模型能改变的是「怎么估」，改变不了「用什么估」——观测不到数据分布时，任何估算方法都只能退化到平均值假设，而真实分布往往高度倾斜。
- 什么时候它才会成真：模型能直接从表元数据与采样统计里读出分布，并且更新频率跟得上数据变化——那本质上还是统计信息，只是换了采集方式。
- 信号：说这句话的产品，它的文档里通常仍有一节叫「收集统计信息」（或对应的 `ANALYZE` 命令）。**把那一节读完，再决定信哪一半。**

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 学习型组件会以「可回退的候选选择」形态先产品化，而不是端到端替换优化器 | 产品文档出现「候选计划选择 + 一键回退」的组合 | 只有端到端 learned optimizer 的产品化，且没有回退路径 |
| 「估算误差是计划质量主因」这一格局不会改变 | 引擎的优化器改进集中在统计信息（增量采集、采样、基数估算精度），而不是搜索算法 | 某个引擎公开宣称「计划质量不再依赖统计信息新鲜度」，并给出可复现实验 |
| 自然语言诊断与「估算 vs 实际」的对比会成为默认可观测能力，但不会改变计划质量 | 「慢查询解释」成为默认开启、不再单独计费的能力，且「估算行数 vs 实际行数」被直接放进执行详情、不需要自己采集 | 出现可复现的第三方数据表明「开启诊断后慢查询显著减少」，且不是通过同时改了配置实现的；或三年后估算与实际的对比仍需自建采集脚本 |
| 「多目标（成本 / 能耗）」会成为配置项，而非默认行为 | 云厂商把成本或碳排作为资源的正式计量维度，并可用于计划选择 | 三年后资源计量维度仍然只有核时与字节 |

四条预测共用一个判据：**看它有没有落到「可计量、可预算、可回退」的形态上。** 只出现在论文基准与产品演示里的能力，即使名字叫优化器，作用点仍在回路层。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 慢查询多、会读计划的人少 | 先把可观测性补齐：最终计划（不是编译期计划）、估算 vs 实际行数、优化耗时占比的 P50/P99 | 诊断类工具是否开始给出引用来源与拒答 | 不要把 AI 建议直接落到生产队列参数上——在验证与回滚链路建成之前，它只是一份候选清单 |
| 计划抖动，怀疑统计信息陈旧 | 提高采集频率或改用采样估算，先修估算入口（VLDB 2015 的结论） | 自动维护类能力是否覆盖你自己的表类型 | 不要用 hint 去掩盖估算问题：hint 会随版本失效，问题会以更隐蔽的方式回来 |
| 想引入学习型优化 | 先把两样东西建好：可一键回到引擎默认计划的**回退路径**，以及估算误差随时间变化的**漂移监控** | 是否出现带回退路径的候选选择形态产品 | 不要做端到端替换决策层；不要在没有基线可退时让模型决定计划 |
| 想用 LLM 管优化知识（案例、依赖） | 先给每条语料加「适用版本 + 年份」字段，并定义「召回后采纳率」这个指标 | 语料与图是否出现标准格式 | 不要在采纳率指标建立前把它接进人的决策链——检索出来的过期答案比没有答案更危险 |
| 用嵌入式优化器框架（Calcite 一类） | 把每个数据源的统计信息接口补齐，并做一次核验：去掉统计信息后计划是否改变 | 这些元数据接口是否被新的 AI 组件读取 | 不要在没补元数据前就上「AI 优化」——代价层拿不到输入时，上层只能猜 |
| 要治理成本（云账单高） | 先把计费口径与引擎的代价口径对齐，再谈多目标 | 成本或碳排是否成为资源的正式计量维度 | 不要在权重没定死之前开启多目标——系统会按你随手填的权重稳定地选错 |
| 负载里有一批重复度高的报表查询 | 先按 5.2.2 的算式算一遍「频次 × 单次节省 − 刷新成本」，再决定要不要物化 | 自动维护类能力是否覆盖你使用的表类型 | 不要在没算这笔账之前先建一排物化视图——它们的刷新成本会长期留在账单上 |

表中第五行值得单独说一句：它和第一、二、六行一样，属于**在引入任何 AI 之前就应该做完**的事，区别在于它决定的是上层「智能优化」拿不拿得到输入——代价层没有每个数据源的统计信息接口，模型只能猜。去掉统计信息后计划是否改变，这个实验五分钟能做，结论却决定了你后面所有「智能优化」有没有作用对象。

### 5.8 小结

> 本节小结：把 5.1 的四类改动压成一条，AI 在查询优化器上真正改变的**唯一那条机制**，是把判断的作用点从「这一次查询的计划」搬到「下一次查询的配置」——5.2.1 把「读计划」这一步移出单条查询的路径，5.2.2 把打分口径从一条查询拉长到一段负载，5.2.4 把判断依据搬到引擎之外，三条都是这条位移在不同侧面上的表现；四类里唯一去动「这一次查询」决策内核的是 5.2.3，也正因如此它停在 L3。它**没有改变**的是：计划的选择仍然受制于基数估算误差，决策权仍然固定在编译期与 stage 边界两层，模型至今没有拿到「这一次查询」的决策权。
>
> 因此判断任何一项「AI 优化」能力，只问两个问题——它改的是这一次的计划还是下一次的配置；出错时能不能一键退回基线。两个都能答清楚的，可以试点；答不清楚的，无论演示多好，都还停在报告里。
>
