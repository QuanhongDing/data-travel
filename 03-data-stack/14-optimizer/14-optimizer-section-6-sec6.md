## 6. 落地实践

### 6.1 字节"**代价模型：为什么"小表广播"能省掉大表的 shuffle，以及它为什么常常选错**"（2019-2024）

**背景（Why）**

字节 2019 年面临**"复杂关联查询的计划选择不稳定"**：
- **复杂查询动辄关联十余张表**——**关联顺序与关联方式的可选组合极多，而不同选择之间性能差异可达数量级**
- **计划选错表现为全表扫描**——**一次错误的关联策略会把本可秒级完成的查询变成长达数分钟**
- **估算误差沿计划树放大**——**中间结果的估算偏差会被后续算子的估算继承并放大，最终完全偏离实际**
- **业务方无法自行处理**——**查询由业务或分析工具发出，不能要求他们理解执行计划**

**触发点（What）**

2019 年起字节在分析引擎中深化**基于代价的优化**（[字节公开材料 2019-2024]），目标：
- **复杂关联的计划稳定性**
- **估算准确度提升**
- **误判时仍可救**

**详细做法（How）**

字节优化器方案的**5 大核心组件**：

1. **代价模型：把"选哪个计划"变成"算哪个更便宜"（核心创新）**
   - 关键设计：**为每种候选计划估算总代价**（扫描代价、关联代价、聚合代价按各自公式累加），选代价最小的执行；关联代价按"构建侧行数 × 构建单位代价 + 探测侧行数 × 探测单位代价"估算
   - 关键能力：**选择依据从规则变成量化比较**——基于规则的做法只能处理预设的情况，而代价模型能对任意查询组合给出可比的分值
   - 关键数字：**估算准确度显著提升、复杂查询性能提升一个数量级**
   - 关键示意：
     ```text
     为什么"小表广播"能省掉大表的 shuffle（这一步的收益最大）
       两个大表做关联时，默认做法是：
         按关联键把两张表都按 key 重新分区（shuffle）
         → 网络传输量 ≈ 两表行数之和
       ────────────────────────────────────────────────
       如果其中一张表足够小：
         把小表完整复制到每个节点（broadcast）
         每个节点用本地已有的大表分片与小表关联
         → 省掉了大表的 shuffle
         → 网络传输量 ≈ 小表大小 × 节点数
       ────────────────────────────────────────────────
       所以关键在于：判断"哪张表足够小"
         —— 而这个判断依赖行数与宽度的估算
         —— 一旦估算超过阈值，就会错过广播策略
            或者错误地广播了一张其实很大的表
       ────────────────────────────────────────────────
     判据：这类优化"收益巨大但高度依赖估算准确"，
           所以统计信息质量是它的前提，不是可选项
     ```

2. **统计信息：直方图与去重计数支撑估算（核心）**
   - 关键设计：**采集列的取值分布（直方图）与去重计数**，并支持按比例采样
   - 关键能力：**基数估算有依据**——没有分布信息时，估算只能按平均值假设，而真实分布往往高度倾斜
   - 关键性质：**采样率不高即可达到较好准确度**

3. **自适应执行：计划错了还能救（核心）**
   - 关键设计：**运行时对比实际与估算的行数**，偏差超过阈值时动态调整后续执行方式（如切换关联策略、调整并行度）
   - 关键能力：**估算误差不再必然导致灾难**——纯静态计划一旦选错只能等待；自适应给了纠错的机会
   - 关键性质：**相当比例的误判可被运行时纠正**

4. **统计信息新鲜度作为前提（核心）**
   - 关键设计：**统计信息随数据变化及时更新**，而不是按固定长周期收集
   - 关键能力：**估算不基于过期分布**——数据分布变化后仍按旧统计决策，等于持续做出错误选择
   - 关键性质：**及时更新是有代价的**——更频繁的统计采集本身消耗集群资源，所以「多快算够」要和查询收益一起算，而不是越快越好

5. **误判的可观测与人工兜底（核心创新）**
   - 关键设计：**记录估算与实际行数的偏差并暴露出来**，同时提供人工指定计划的手段
   - 关键能力：**问题可被定位与绕过**——自适应也有改错的时候，此时需要能识别"这个查询被优化器坑了"并临时干预
   - 关键性质：**误判可被识别与人工干预**

**字节优化器方案关键数字**（[字节公开材料 2019-2024]）：

| 指标 | 改前（规则 + 陈旧统计） | 改后（代价模型 + 及时统计） | 提升 |
| --- | --- | --- | --- |
| **选择依据** | 预设规则 | 量化比较代价 | **可处理任意组合** |
| **估算准确度** | 偏差大 | 显著提升 | **计划更稳** |
| **复杂关联性能** | 基线 | 提升一个数量级 | **10x** |
| **关联策略** | 常错过广播 | 依赖准确基数判断 | **关键判断正确** |
| **统计新鲜度** | 长周期收集、易过期 | 及时更新 | **不基于过期分布** |
| **误判处理** | 静态计划只能等待 | 运行时自适应纠正 | **相当比例可救** |
| **误判可观测** | 无 | 估算与实际偏差被记录 | **可定位** |
| **人工兜底** | 无 | 可指定计划 | **可临时绕过** |

**具体数字（How much）**

- 团队规模：字节优化器相关团队 50+ 人
- 业务影响：让复杂关联查询的计划选择从"凭规则"变成"凭估算"，并在估算出错时仍有纠正手段

**失败教训**

- 早期「**基于预设规则选择计划**」——只能处理预设情况、复杂组合无从选择，倒逼**「引入代价模型做量化比较」**
- 「**统计信息按长周期收集**」——数据分布变化后仍按旧统计决策、持续选错，倒逼**「及时更新统计信息」**
- 「**关联策略靠经验固定**」——错过广播策略导致大表被 shuffle，倒逼**「依据准确基数判断是否广播」**
- 「**计划选错后只能等待**」——一次误判耗时数分钟，倒逼**「运行时自适应纠正」**
- 「**自适应改错了无人知**」——问题被隐藏，倒逼**「记录估算与实际偏差并支持人工干预」**

### 6.2 阿里"**关联策略不是拍脑袋：按表大小与有序性做决策**"（2014-2024）

**背景（Why）**

阿里 2014 年面临**"极大规模上的关联策略选择错误代价极高"**：
- **数据规模达到 EB 级**——**一次错误的关联策略意味着小时级的全量扫描，而正确策略下可在数十秒内完成**
- **关联策略种类多且适用条件不同**——**小表广播、排序合并、重分区哈希各自适用于不同的表大小与数据组织方式**
- **表大小在查询时才知道**——**同一段查询在不同分区上面对的表大小可能不同**
- **业务方无法干预**——**查询由大量业务方提交，不能要求他们指定策略**

**触发点（What）**

2014 年起阿里在数仓引擎中完善**关联策略决策与代价估算**（[阿里公开材料 2014-2024]），目标：
- **策略选择有明确依据**
- **估算准确度提升**
- **错误策略的代价被消除**

**详细做法（How）**

阿里优化器方案的**5 大核心组件**：

1. **按"表大小 + 数据有序性"选择关联策略（核心创新）**
   - 关键设计：**决策依据两类信息**——参与关联的表相对大小（决定能否广播），以及数据是否已按关联键有序（决定能否省掉排序）
   - 关键能力：**策略选择的条件明确可查**——"为什么选了这个策略"能被回答，而不是靠经验
   - 关键数字：**关联性能提升一个数量级**
   - 关键示意：
     ```text
     关联策略的选择条件（三选一，依据明确）
       条件一：一表足够小（低于广播阈值）
         → 广播哈希关联（把小的那份复制到每个节点）
         收益：省掉大表的 shuffle，收益最大
       条件二：两表都大，且已按关联键有序
         → 排序合并关联（两侧顺序扫描，边读边合并）
         收益：省掉排序与重分区
       条件三：两表都大且无序
         → 重分区哈希关联（两侧都按 key 重新分区）
         代价最高，但适用面最广
       ────────────────────────────────────────────────
     决策所需的两类输入：
       ① 表大小 → 决定能否广播
       ② 有序性 → 决定能否免排序
       两者都来自统计信息与表的物理组织
       ────────────────────────────────────────────────
     判据：如果"这个查询为什么慢"无法归因到具体策略，
           说明优化器还是黑盒；
           可归因、可解释，才谈得上持续优化
     ```

2. **统计信息作为决策输入（核心）**
   - 关键设计：**采集表行数、列去重计数、取值分布直方图与有序性信息**，作为策略选择的输入
   - 关键能力：**决策有据可依**——统计缺失时，策略选择退化为固定默认值，而默认值在极大规模上往往是最差的选择
   - 关键性质：**估算准确度达到较高水平**

3. **分区裁剪先行，把扫描量压下来（核心）**
   - 关键设计：**在策略选择之前先做分区裁剪**，让实际参与计算的数据量远小于表总量
   - 关键能力：**策略是在裁剪后的规模上选择的**——把扫描量从极大规模压到可接受规模，后续的关联策略才谈得上"快"
   - 关键性质：**扫描量随查询条件收敛，而不随表大小增长**——这条性质是后面所有策略选择成立的前提：基数估错的根源往往不是统计不准，而是根本没裁到该裁的分区

4. **自适应执行补救误判（核心）**
   - 关键设计：**运行中发现实际行数与估算严重不符时重规划**
   - 关键能力：**估算误差不演变为长时间等待**
   - 关键性质：**相当比例误判可被纠正**

5. **物化视图把重复聚合提前算好（核心创新）**
   - 关键设计：**识别高频的聚合模式并自动推荐物化，刷新异步进行**
   - 关键能力：**重复的重聚合不必每次算**——优化器再准也无法让"每次都重算同一份聚合"变快，而物化直接把这个计算消掉
   - 关键数字：**命中物化后延迟进入秒级**

**阿里优化器方案关键数字**（[阿里公开材料 2014-2024]）：

| 指标 | 改前（固定默认策略） | 改后（按条件决策） | 提升 |
| --- | --- | --- | --- |
| **策略依据** | 默认或经验 | 表大小 + 有序性 | **可解释** |
| **关联性能** | 基线 | 提升一个数量级 | **10x** |
| **估算准确度** | 依赖统计质量 | 达到较高水平 | **计划更稳** |
| **扫描量** | 直接扫全部相关数据 | 分区裁剪先行 | **大幅下降** |
| **极大规模查询** | 小时级（策略错时） | 数十秒量级（策略对时） | **数量级差异** |
| **误判处理** | 只能等待 | 运行时重规划 | **可纠正** |
| **重复聚合** | 每次重算 | 物化复用 | **消掉计算** |
| **物化命中延迟** | — | 秒级 | **大幅下降** |

**具体数字（How much）**

- 团队规模：阿里数仓引擎相关团队 200+ 人
- 业务影响：让极大规模上的关联策略选择有明确依据，并把一次错误策略的小时级代价消除

**失败教训**

- 早期「**使用固定默认关联策略**」——在极大规模上默认往往是最差选择、代价以小时计，倒逼**「按表大小与有序性决策」**
- 「**统计信息缺失就按默认估算**」——策略选择退化为默认值，倒逼**「把统计采集作为决策前提」**
- 「**先选策略再裁剪**」——在未裁剪的规模上做选择，倒逼**「分区裁剪先行，再在裁剪后的规模上决策」**
- 「**估算错了只能等**」——长时间等待且无法中断，倒逼**「运行时重规划」**
- 「**重复聚合每次重算**」——优化器再准也无法消除这份计算，倒逼**「识别高频聚合并物化」**

### 6.3 Netflix"**把统计信息写进数据本身：优化器不再依赖外部维护**"（2019-2024）

**背景（Why）**

Netflix 2019 年面临**"优化器与存储层脱节，统计维护成为长期负担"**：
- **统计信息需要额外维护**——**需要单独安排收集任务，而收集频率与实际数据变化速度难以匹配**
- **数据量极大使收集成本高**——**在极大规模上做统计采集本身消耗可观资源**
- **过期统计导致裁剪失效**——**优化器不知道数据的真实分布，就无法跳过无关的数据**
- **多个引擎需要各自的统计**——**不同计算引擎各自维护一套统计，同一份数据的统计可能不一致**

**触发点（What）**

2019 年起 Netflix 让**表格式自身携带统计信息、优化器直接读取**（[Netflix 公开材料 2019-2024]），目标：
- **统计与数据同步**——不再有过期问题
- **多引擎共享同一份统计**
- **裁剪能力提升**

**详细做法（How）**

Netflix 方案的**5 大核心组件**：

1. **统计随数据一起写，成为表格式的一部分（核心创新）**
   - 关键设计：**写入数据时同步记录列级统计**（最小值、最大值、空值数、行数）到表的元数据；任何支持该格式的引擎都能读到同一份统计
   - 关键能力：**统计不再是一份需要单独维护的副本**——独立维护意味着"两份信息可能不一致"，而且每多一个引擎就多一份
   - 关键性质：**多引擎共享同一份统计**
   - 关键示意：
     ```text
     统计放在哪（决定了它会不会过期、会不会不一致）
       ✗ 每个引擎各自维护一份统计
         引擎 A 收集一份、引擎 B 收集一份
         问题：① 两份可能不一致（收集时点不同、采样不同）
               ② 各自都要付出收集开销
               ③ 每个引擎都要"记得收集"
       ✓ 统计随数据写在存储层
         写入时记录列级 min/max/空值数/行数
         引擎读取时直接拿同一份
         → ① 只有一份，不会不一致
           ② 收集开销只在写入路径上付一次
           ③ 不存在"忘记收集"
       ────────────────────────────────────────────────
     代价：统计粒度受限（列级 min/max 与计数，而非完整分布）
           —— 但对"跳过不可能命中的数据"这类判断已足够
     ```

2. **列级区间统计支撑文件级裁剪（核心）**
   - 关键设计：**每个数据文件记录各列的取值区间**；查询条件涉及某列时，取值区间与之无交集的文件直接跳过
   - 关键能力：**不读文件内容就能判断"里面不可能有符合条件的数据"**——这让裁剪从"读完再过滤"变成"读之前先排除"
   - 关键性质：**大部分文件被跳过**

3. **元数据分层使裁剪代价可控（核心）**
   - 关键设计：**元数据自身分层**（表 → 快照 → 文件清单 → 文件），裁剪逐层收紧
   - 关键能力：**"找文件"的代价不会吃掉"跳过文件"的收益**——扁平结构下，裁剪要遍历全部文件
   - 关键性质：**裁剪逐层收窄、代价可控**

4. **快照语义保证裁剪结果的一致性（核心）**
   - 关键设计：**裁剪基于某个快照的元数据**，读取与裁剪看到的是同一个一致状态
   - 关键能力：**计划与实际读取的数据一致**——写入并发进行时，基于旧元数据的裁剪可能与实际读到的数据不符
   - 关键性质：**计划与数据一致**

5. **接口兼容保证多引擎可持续接入（核心创新）**
   - 关键设计：**元数据接口保持向后兼容**，新统计项以可选方式加入
   - 关键能力：**引擎实现方不必因升级而重做**——否则新引擎的接入意愿会逐渐消失，统计又退回"各自维护"
   - 关键性质：**接口兼容、多引擎持续支持**

**Netflix 方案关键数字**（[Netflix 公开材料 2019-2024]）：

| 指标 | 改前（引擎各自维护统计） | 改后（统计随数据写） | 提升 |
| --- | --- | --- | --- |
| **统计来源** | 各引擎单独收集 | 随数据写入存储层 | **只有一份** |
| **统计一致性** | 可能不一致 | 天然一致 | **消除分歧** |
| **收集开销** | 每引擎各付一次 | 写入路径付一次 | **大幅下降** |
| **统计过期的可能** | 由收集频率决定 | 不存在 | **消除** |
| **文件裁剪** | 依赖统计质量 | 列级区间直接排除 | **跳过大部分文件** |
| **裁剪代价** | 扁平结构下偏高 | 元数据分层 | **可控** |
| **并发下的正确性** | 可能与实际不符 | 基于快照，一致 | **一致** |
| **多引擎接入** | 各自适配统计 | 共享同一份 | **成本下降** |

**具体数字（How much）**

- 团队规模：Netflix 数据平台相关团队 50+ 人
- 业务影响：把统计从"每个引擎各自维护的副本"变成"随数据一起存在的唯一一份"，并让裁剪能力显著提升

**失败教训**

- 早期「**各引擎各自维护统计**」——两份可能不一致且各自付出收集开销，倒逼**「统计随数据写入存储层」**
- 「**统计靠独立任务收集**」——收集与写入之间存在窗口、可能忘记收集，倒逼**「写入时同步记录」**
- 「**只记录表级信息**」——无法做文件级裁剪，倒逼**「每个数据文件记录列级取值区间」**
- 「**元数据扁平存放**」——裁剪要遍历全部文件、收益被抵消，倒逼**「元数据分层，逐层裁剪」**
- 「**裁剪不指定快照**」——并发写入下计划与实际不符，倒逼**「裁剪基于一致快照」**

### 6.4 AWS"**用历史执行数据修正代价公式：把优化器估不准的地方补上**"（2014-2024）

**背景（Why）**

AWS 2014 年面临**"托管的优势是不用客户操心，但性能恰恰依赖客户不做的那些事"**：
- **统计信息需要维护**——**客户不做统计维护，而托管形态下又不能要求他们做**
- **代价公式存在系统性盲区**——**多列之间相关的谓词上，按独立性假设估算会系统性偏差**
- **慢查询长期存在**——**少量但持续的慢查询占比，会显著拉低体验并产生支持成本**
- **客户团队缺少内核专长**——**托管服务的客户多数不是数据库专家，无法自行诊断计划问题**

**触发点（What）**

2014 年起 AWS 在托管数仓中引入**基于机器学习的代价估算**（[AWS 公开材料 2014-2024]），目标：
- **修正代价公式的系统性偏差**
- **客户不必维护统计**
- **慢查询占比下降**

**详细做法（How）**

AWS 托管优化方案的**5 大核心组件**：

1. **用历史真实执行数据修正代价估算（核心创新）**
   - 关键设计：**在传统基于统计的代价公式之上，引入对历史真实执行结果的回归学习**——模型学的是"这类计划的真实耗时"，用于修正公式估算的偏差
   - 关键能力：**覆盖公式本身的盲区**——传统估算假设列之间相互独立（用选择率相乘），而现实中多列往往相关；这类偏差靠更精细的统计只能部分缓解，用实测数据修正则直接绕过
   - 关键性质：**计划质量明显提升、慢查询占比大幅下降**
   - 关键示意：
     ```text
     传统代价估算的系统性盲区（靠更多统计也补不齐）
       估算选择率时的常见假设：
         多列条件相互独立 → 选择率 = 各列选择率相乘
       ────────────────────────────────────────────────
       但现实中列常常相关：
         "城市 = 北京" 与 "省份 = 北京" 显然不独立
         "高客单价" 与 "品类 = 电子产品" 强相关
         → 相乘得到的估算可能偏差一个数量级
         → 偏差沿计划树放大 → 策略选错
       ────────────────────────────────────────────────
       ✓ 用真实执行数据修正：
         历史执行记录"这类计划实际扫了多少行、跑了多久"
         模型学到的是实际代价，不受独立性假设影响
       ────────────────────────────────────────────────
     必须守住的分界：
         学习只用于"代价估算"
         —— 不能改变查询语义
         优化器出错是性能问题，改语义是正确性问题
     ```

2. **统计采集自动化，客户不必介入（核心）**
   - 关键设计：**统计信息的采集与刷新由服务侧自动完成**
   - 关键能力：**"托管"与"性能"不再冲突**——托管形态下客户不会做统计维护，这件事必须由服务承担
   - 关键性质：**托管把统计维护的运维负担从客户侧移走**，代价是客户对统计策略的可见性与可控性下降——买卖双方要在「省事」与「可干预」之间明确取舍

3. **运行时重规划（核心）**
   - 关键设计：**执行中发现实际行数与估算偏差过大时重新规划后续步骤**
   - 关键能力：**估不准时仍有退路**——学习模型也不是万能的，遇到训练分布之外的情况仍会偏差
   - 关键性质：**相当比例的误判可被纠正**

4. **结果与中间结果复用（核心）**
   - 关键设计：**对重复出现的查询与可复用的中间结果做缓存**
   - 关键能力：**高频重复查询的成本大幅下降**——实际使用中查询分布高度集中于少数高频模式，缓存这部分收益显著
   - 关键性质：**高频查询响应明显加快**

5. **冷启动用模拟负载补齐训练数据（核心创新）**
   - 关键设计：**新集群或新负载形态缺少历史执行数据时，用模拟负载生成训练样本**，随着真实查询积累再逐步替换
   - 关键能力：**学习机制不必等待长周期积累**——否则新客户在新环境下的前几个月只能承受未经优化的计划
   - 关键性质：**冷启动期也可获得优化效果**

**AWS 方案关键数字**（[AWS 公开材料 2014-2024]）：

| 指标 | 改前（纯公式估算） | 改后（公式 + 实测修正） | 提升 |
| --- | --- | --- | --- |
| **估算依据** | 统计 + 独立性假设 | 统计 + 历史真实执行 | **覆盖公式盲区** |
| **计划质量** | 受统计与假设限制 | 明显提升 | **显著** |
| **慢查询占比** | 偏高 | 大幅下降 | **显著** |
| **多列相关谓词** | 系统性偏差 | 用实测数据绕过假设 | **偏差被修正** |
| **统计维护** | 需要客户操作 | 服务侧自动 | **客户不必操心** |
| **估不准时的退路** | 只能等待 | 运行时重规划 | **可纠正** |
| **重复查询** | 每次重算 | 结果复用 | **成本下降** |
| **冷启动期** | 无历史数据可学 | 模拟负载生成样本 | **优化不等待** |

**具体数字（How much）**

- 团队规模：AWS 托管数仓相关团队千人量级
- 业务影响：在客户不做统计维护、也不懂内核的前提下，把查询计划质量的下限抬高

**失败教训**

- 早期「**只靠统计与公式估算**」——多列相关谓词上系统性偏差、策略选错，倒逼**「用历史真实执行数据修正估算」**
- 「**托管形态下仍要求客户维护统计**」——客户不会做，倒逼**「统计采集与刷新自动化」**
- 「**让学习影响查询语义**」——把性能问题变成正确性问题，倒逼**「学习只用于代价估算」**
- 「**估不准时只能等待**」——长查询无法挽回，倒逼**「运行时重规划」**
- 「**新环境等长周期积累训练数据**」——前几个月只能承受未优化计划，倒逼**「用模拟负载生成样本补齐冷启动」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**采集统计信息 + 观察计划变化**」（**最简单**）——**1 个业务、10+ 表**
- 产出：**统计采集（行数 / 去重计数 / 取值分布）+ 同一查询在统计前后的计划与耗时对比**
- 团队：**2-3 人**
- 验证标准：**统计信息覆盖关键列**、**计划随统计变化而改变（说明它真的在用）**、**常用查询延迟下降**

**1 → 10 阶段：6-12 个月**

- 扩展到「**100+ 表 / 代价模型与关联策略**」
- 引入「**按表大小与有序性选择关联策略**」——收益最大的一步
- 引入「**分区与列裁剪先行**」——在裁剪后的规模上做策略决策
- 团队：5-10 人
- 验证标准：**"为什么选这个策略"可解释**、**小表广播被正确选用**、**扫描量随裁剪明显下降**

**10 → 100 阶段：12-24 个月**

- 扩展到「**统计随数据写入 + 运行时自适应**」
- 引入「**统计随数据写入存储层**」——消除"收集窗口"与"多引擎各维护一份"
- 引入「**记录估算与实际行数的偏差并暴露**」+「**运行时重规划**」
- 团队：10-30 人
- 验证标准：**统计不存在过期状态**、**误判可被识别**、**相当比例的误判被运行时纠正**

**100 → 1000 阶段：12-24 个月**

- 观望并记录「**用历史真实执行数据修正代价估算**」——覆盖公式本身的假设盲区；但 §5 对同一类机制（把学习组件挂到代价模型这一既有接口上）判 **L3「观望」**——**记录即可，不要在架构里为它预留假设**，故此处不作为「引入」项
- 引入「**物化高频聚合 + 结果复用**」——优化器再准也消不掉重复计算，物化可以
- 观望并记录「**模拟负载补齐冷启动 + 学习只用于代价不改语义**」——依附上述学习型机制，同按 §5 的 **L3「观望」** 口径处理
- 团队：30-100 人
- 验证标准：**多列相关条件下的估算偏差被修正**、**高频聚合不再每次重算**、**新环境无需等待长周期即可获得优化**、**学习不改变查询语义**

| 「**统计新鲜度**」 | 由收集频率决定 | 随数据写入 | **不存在过期** |
| 「**统计一致性**」 | 各引擎可能不一致 | 只有一份 | **消除分歧** |
| 「**误判处理**」 | 只能等待 | 运行时重规划 | **可纠正** |
| 「**误判可观测性**」 | 无 | 估算与实际偏差被记录 | **可定位** |
| 「**重复聚合**」 | 每次重算 | 物化复用 | **消掉计算** |
| 「**慢查询占比**」 | 偏高 | 大幅下降 | **显著** |

**关键投资回报**：
- **直接节省**：「**关联性能 10x + 扫描量下降一个量级 + 重复聚合被消掉**」——**优化器的收益直接体现在资源消耗与延迟上**，且随数据规模放大
- **业务价值**：「**复杂查询的计划稳定 + 策略选择可解释 + 误判有退路**」——**优化器的价值是让"复杂的查询"变得可用**：业务与分析工具写出的查询不必经过专家调优就能获得可接受的性能
- **AI 时代关键**：「**代价估算准确 + 统计随数据同步 + 学习只用于代价不改语义**」——**AI 生成的查询会成为查询量的主要来源之一**：自然语言转成的查询往往结构复杂且写法不优，而它们能否在可接受延迟内完成，取决于优化器是否足够强；同时"学习只用于代价、不改变查询语义"这条分界，在 AI 参与优化的场景下尤其必须守住

---

> **本节小结**：
> - 4 个真实案例（字节 / 阿里 / Netflix / AWS）印证：**优化器不是「默认配置」，是「代价模型 + 统计随数据同步 + 按条件选关联策略 + 运行时重规划 + 实测修正估算」5 件套**（其中「实测修正估算」来自 AWS 案例自述的学习型机制，§5 判同类机制 **L3**，属观望项）。
> - 关键时间线：字节 5+ 年 / 阿里 10+ 年 / Netflix 5+ 年 / AWS 10+ 年 —— **优化器是长期工程**，且**它最关键的一个前提是"统计信息是否与数据同步"**。
> - 选型第一原则：「**采集统计 + 观察计划变化**」（**最简单**）→ 「**按条件选关联策略 + 裁剪先行**」（**必须**）→ 「**统计随数据写入 + 运行时重规划 + 偏差可观测**」（**生产**）→ 「**用实测数据修正估算 + 物化与结果复用 + 模拟负载补齐冷启动**」（**AI 时代**）；末档中依附学习型机制的两项（「用实测数据修正估算」「模拟负载补齐冷启动」）按 §5 判为 **L3**——**记录即可，不要在架构里为它预留假设**，不作为「引入」项。
> - 99% 的失败来自「**凭规则选计划 + 统计过期 + 策略固定 + 选错只能等**」——必须有 **代价模型 + 统计同步 + 按条件决策 + 运行时纠错**。
> - 真正的 ROI 来自「**关联 10x + 扫描量降一个量级 + 统计不过期 + 误判可纠正**」——是**复杂查询能否不依赖专家调优的分水岭**。

> 💡 **思考锚点**：去查一下你的统计信息刷新方式：如果它仍由采集频率决定、而不是随数据写入更新，那你昨天新写的那批分区，优化器拿到的是哪一版基数估计？你会先补「统计随写入同步」，还是先上「运行时重规划」替它兜底？
