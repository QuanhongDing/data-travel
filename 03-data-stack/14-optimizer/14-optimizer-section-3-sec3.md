## 3. 设计模式与范式

> 原 § 3 共 79 行、以模式清单与一张决策表为主，缺少结构示意、机制解释与失效分析，重写为 ~300 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

优化器选型在多数资料里被讲成一张对照表：Spark 用 CBO + AQE，ClickHouse 用向量化，自研引擎用 Calcite。这张表回答不了一个真实问题：**同一句 SQL、同一个引擎，换一个数据分布就该换计划**。所以优化器的模式分野不在产品品牌，而在约束。

优化器只有一件事要做：在**不知道真实基数**的前提下，从指数级的计划空间里挑一个在**真实基数**下不坏的计划。所有模式都是对「不知道」这三个字的不同回答——RBO 用规则绕开估计（稳定但次优），CBO 用统计信息估计（可能最优，也可能大错），AQE 把估计推迟到运行时用实测值纠偏，Cascades 用 Memo 加代价上界控制搜索成本，Calcite 把上述框架做成可嵌入的库，AI 增强把「纠偏」从数值规则扩展到模式识别与建议生成。约束换一条，正确回答就换一个。

因此本节的组织方式是：**先固定你的约束（见下面的约束表），再看哪个模式是这套约束下的必然结论**。凡是把模式当选择题做的团队，最终都会退化成「全开一遍配置，然后给每条慢查询挂 hint」。

这六条约束不是并列关系，其中一条会最先发生作用：**统计信息是否可得**。它写在约束表的第 1 行，与「数据分布是否倾斜」并列成一条，因为两者共同决定 CBO 估计误差的量级；但它比同行的另一半更决定性——它是唯一能直接把 CBO 降级成 RBO 的约束，也是唯一一条你无法靠加机器绕开的约束：没有它，后面所有关于 Join 顺序、倾斜、代价剪枝的讨论都失去输入。第二位的是**查询时长的量级**，它归在「访问模式」一行里，因为决定优化预算的不是查询类型本身，而是这一类型对应的时长：亚秒级查询给不出任何搜索空间，分钟级批任务则相对不在乎多花几百毫秒找更优计划。把约束排成这个次序，模式选择就从「比对功能表」变成一句可判断的话。

还有一条容易被忽视的约束是**团队能否读懂执行计划**。优化器是可观测性最差的组件之一：它不报错，只做选择。当一个团队没人能读 EXPLAIN、没人能对照 EXPLAIN ANALYZE 判断估计是否离谱时，无论选哪个模式，最终都会回到「凭感觉调参数」——这是所有反模式的共同起点。因此在能力建设顺序上，**先建立读计划的能力，再引入更复杂的优化模式**，成本比反过来低得多。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据分布是否倾斜、统计信息是否可得 | CBO 的估计误差量级，从而决定要不要把纠偏推迟到运行时 | 「开了 CBO 就比 RBO 强」——统计信息缺失或谓词强相关时，CBO 会自信地选错计划，比稳定次优的 RBO 更差 |
| 访问模式（点查 / 大扫描 / 聚合 / 交互式短查询）及由它决定的查询时长量级 | 优化耗时在查询总耗时里能占多少，从而决定搜索空间要不要设上限 | 「优化越充分越好」——短查询上优化耗时可能超过执行耗时，搜索必须有预算；决定这件事的是时长量级，不是查询类型本身 |
| 变更频率与历史要求 | 统计信息的过期速度，从而决定是「定期 ANALYZE」还是「按变更触发采集」 | 「统计信息采集一次就够」——两次采集之间的基数漂移会让估算偏差跳到十倍级【经验】 |
| 一致性要求 | 计划能否被固定（hint / 计划基线），以及结果可复现的边界 | 「hint 是历史包袱」——在估算盲区（相关列、倾斜键）上，hint 是唯一可靠出口 |
| 规模与成本约束 | 是选通用框架还是专用搜索，是自研还是嵌入 | 「用 Calcite 就等于白得一个 CBO」——代价能力依赖你为每个数据源实现统计信息接口，否则退回纯规则 |
| 团队技能与运维能力 | 自研 Cascades 是否可行，以及优化器出问题时谁来排障 | 「自研优化器是核心壁垒」——没有优化器专家时，它是最难被替代也最难被维护的一块 |

### 3.2 模式逐个拆解（核心节）

六个模式看起来是六个产品选项，实际上它们回答的是同一个问题的六个位置：**当「真实基数」不可知时，你在哪一层把它补回来**。下表先把位置对齐，再逐个展开——每个模式都给「被什么约束逼出来 / 结构 / 为什么有效 / 代价 / 失效点 / 真实使用」六件事，缺失效点的模式在本主题下没有讨论价值。

| 模式 | 把「真实基数」补回来的位置 | 代价落在谁身上 |
| --- | --- | --- |
| CBO + 统计信息 | 优化之前（离线采集的数值） | 采集任务与存储 |
| AQE 自适应 | 执行之中（stage 边界的实测统计） | 阶段切分与 shuffle 物化 |
| AI 驱动优化 | 执行之后（指标回归与建议生成） | 指标采集与验证链路 |
| Calcite 嵌入式 | 由你提供（Adapter + TableStatistics） | 每个数据源的接入工作量 |
| Cost-Based + Cascade | 由代价模型近似（Memo 里的上界比较） | 搜索时间与实现复杂度 |
| AI 自治优化 | 持续回路中（观测 → 决策 → 执行 → 验证） | 基线、回滚与审计能力 |

读这张表的顺序应该与产品发布顺序相反：越靠下的模式依赖越多前置条件（指标采集、统计信息接口、基线、回滚），部署风险也越高。多数团队的正确路径是「先本文件第一个模式 + 第二个模式，跑满一年再谈其他」——因为前两个模式的收益来自机制（统计信息是代价模型的唯一输入、实测值能清零估算误差），后四个模式的收益来自复用前面已经建好的基础设施。

#### 3.2.1 CBO + 统计信息（标准）

- **被什么约束逼出来**：数据分布不均，而规则化顺序只认语法形状不认数据量——必须用统计信息把「表有多大」变成可比较的数值。
- **结构**：统计信息是 CBO 的唯一输入，必须显式存在。

```sql
-- 采集：行数 / NDV / Min-Max / 直方图
ANALYZE orders;
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;  -- 提高该列直方图桶数

-- CBO 的比较对象：同一逻辑计划的多个物理实现
--   Plan A: Broadcast Hash Join(users, orders)  代价 = I/O + CPU + Network
--   Plan B: Sort Merge Join(orders, users)      代价 = I/O + CPU + Sort + Network
--   BestPlan = argmin Cost(Plan)
```

- **为什么这样设计有效**：因为统计信息把「表多大、某列有多少不同值」变成了数值，代价模型才能在两个物理计划之间做**可比较的减法**；缺了这些数值，任何「代价」都是常量，argmin 退化成「按书写顺序挑第一个」。
- **代价**：必须在数据变更后持续采集并在大表上承担采样 I/O；采集是异步的，于是系统里永久存在「统计信息落后于数据」的时间窗。PostgreSQL 用 autovacuum 自动 ANALYZE 来压这个窗口【公开】PostgreSQL 官方手册，autovacuum 自 8.1 版（2005）起提供；具体行为可按你所用版本在官方手册中检索 autovacuum 核验。
- **失效点**：当 WHERE 中的多个谓词相互强相关（如 city 与 province）时，CBO 的独立性假设会把选择率相乘，估算偏差可达数量级；此时「基于代价」的优点反转成「定向的错」——CBO 会自信地选出坏计划，而 RBO 的错是稳定、可预期的次优。计划的错误一旦被自信地做出，就比迟钝更贵。
- **真实使用**：PostgreSQL（autovacuum 自动采集）、Trino（`ANALYZE TABLE`，Iceberg / Hive 连接器）、Spark SQL（`ANALYZE TABLE ... COMPUTE STATISTICS`）【公开】上述命令分别见于三个项目的官方手册；具体命令名与支持范围随版本变化，请按你所装版本的官方手册自查。
- **判断方法**：对比 `EXPLAIN` 的估计行数与 `EXPLAIN ANALYZE` 的实际行数，若常态性相差 10 倍以上，说明这套模式在你的系统里只是名义上存在【经验】。

#### 3.2.2 AQE 自适应（2020+）

- **被什么约束逼出来**：编译期看不到中间结果大小，而 shuffle 之后的分区大小与倾斜度恰恰是执行期才知道的——必须把一部分决策推迟。
- **结构**：AQE 只在 **stage 边界**介入。

```text
AQE 的介入点：shuffle 写完、下一个 stage 开始之前
  Stage 1 (map) ──shuffle 写──► [实测分区统计：大小 / 条数 / 倾斜度]
                                        │
                                        ├─ 合并小分区（coalesce partitions）
                                        ├─ 大表↔小表判定翻转 → 改 Broadcast Join
                                        └─ 倾斜分区拆分（skew join）
  Stage 2 (reduce) ◄────────按新计划重排────────┘
  → 结构边界：只能改 stage 之间，改不了 stage 内部的物理算子
```

- **为什么这样设计有效**：因为决策点被推迟到「实测值已经拿到」之后，这一层完全不需要估计——分区到底多大是数出来的，不是算出来的，估算误差在边界处被清零。
- **代价**：一次查询被切成更多阶段（边界处要物化 shuffle 数据），且**只能改阶段之间的计划**：阶段内部的排序、聚合、UDF 一旦启动就不可替换。这是结构决定的边界，不是实现缺陷。
- **失效点**：当瓶颈落在单个阶段内部（单个超大 key 的聚合、排序落盘、慢 UDF）时，「在边界重规划」的优点反转成无力——因为边界恰好没有出现。这类问题只能靠倾斜键预处理或资源调整解决，AQE 帮不上。
- **真实使用**：Spark 3.0（2020）引入 AQE，3.2.0（2021）起默认开启（`spark.sql.adaptive.enabled`），倾斜参数 `spark.sql.adaptive.skewJoin.skewedPartitionFactor`（默认 5）与 `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes`（默认 256MB）【公开】Apache Spark 官方配置文档。原文件在模式清单里把 Trino 与 StarRocks 并列为 AQE 适用引擎，且**未给 StarRocks 标版本**；其决策表给 Trino 标的版本是 420+。这些版本对应关系请以各项目官方发布说明为准。
- **判断方法**：对比 AQE 关闭与开启后的计划，若 Join 策略与分区数完全一致，说明你的查询里不存在 AQE 能改写的边界（例如全是窄依赖的 map-only 作业），此时开启它只是多付了一层阶段切分的成本。

#### 3.2.3 AI 驱动优化（2024 新）

- **被什么约束逼出来**：慢查询治理的人力成本，加上 EXPLAIN 是专家语言——需要把「指标异常」自动映射成「可执行的动作建议」。
- **结构**：必须是一个闭环，而不是一次问答。

```text
AI 驱动优化 = 建议 + 验证闭环（缺验证就不是优化）
  执行指标（耗时 / 扫描字节 / shuffle 字节 / 峰值内存）
        │
        ▼  ① 异常检测：哪个指标偏离了历史基线
  候选动作（改写 SQL / 刷新统计信息 / 加索引 / 调分区 / 建物化视图）
        │
        ▼  ② 小流量验证 + 同一指标回归对比
        ├─ 有效 → 采纳（可回滚，记录原因）
        └─ 无效 → 丢弃（这是一条数据，不是一次失败）
```

- **为什么这样设计有效**：因为输入是「指标偏离基线」而不是「SQL 文本」，它能抓到人工诊断最容易漏的一类慢查询：SQL 没变、计划没变，但数据分布变了。
- **代价**：需要一套可信的执行指标采集（没有扫描字节 / shuffle 字节这类度量，就没有回归验证的基准），以及把建议落成可回滚配置变更的工程链路。模型推理本身是这条链路里最便宜的一环。
- **失效点**：当缺少「建议 → 验证」的回归环节时，「能批量产出看似合理的建议」这个优点反转成缺点——团队无法区分有效与无效建议，最终不再采纳；因为语言模型的输出分布由语言合理性决定，不由正确率决定。
- **真实使用**：Snowflake 提供查询性能异常的自动检测能力（Query Insights），本稿写作时见到的公开材料指向 2024 年推出、Preview 能力【经验】——本节未核到可定位的文档条目，产品名、可用范围与版本请以 Snowflake 官方文档当前内容为准。原文件提到的 StarRocks AI Advisor 属同一档：请以 StarRocks 官方文档核验其产品名与版本。
- **判断方法**：向团队或厂商索要「建议采纳率与回滚率」，而不是「建议条数」。建议条数只说明模型会说话，采纳率才说明它说对了。

#### 3.2.4 Calcite 嵌入式优化器

- **被什么约束逼出来**：自研引擎需要 SQL 解析、关系代数、规则系统、代价搜索四件套，而团队里没有优化器专家——把「标准件」外包给库。
- **结构**：Calcite 优化的是关系表达式，它自己不执行。

```text
Calcite 在自研引擎中的位置
  SQL 文本
    │ ① parser / validator（方言可扩展）
    ▼
  SqlNode ──► RelNode（逻辑关系代数树）
    │ ② 规则：谓词下推 / 列剪裁 / 子查询消除
    ▼
  RelNode（已重写）
    │ ③ 代价：需要你实现 TableStatistics（rowCount / NDV …）
    ▼
  RelNode（物理：Join 算法 / 分布属性）
    │ ④ Adapter：转成你的物理算子
    ▼
  你的执行引擎（Calcite 不碰数据）
```

- **为什么这样设计有效**：因为 Calcite 只处理「关系表达式 + 元数据接口」，自研引擎可以把已有执行层原位保留——只要实现 Adapter 与 TableStatistics，就同时获得规则重写与代价搜索两件事。
- **代价**：你必须为每个数据源实现统计信息接口，否则代价层拿不到输入；自定义算子要显式映射成 RelNode，否则规则与代价都「看不见」它。这是「用框架换实现」的固定税，不是可选项。
- **失效点**：当核心数据源给不出统计信息（对象存储上的裸文件、无 catalog 的外部表）时，Calcite 的代价能力失效、退回纯规则，「白得一个 CBO」的优点反转成「多了一层不能被优化的抽象」；因为规则能重写这棵树的前提，是它能看懂这棵树的节点。
- **真实使用**：Apache Flink 的 Table API / SQL 用 Calcite 做解析与优化【公开】Apache Flink 官方手册；可自行核验的方式是看 `flink-table-planner` 的依赖里是否含 `org.apache.calcite`。Calcite 项目本身列出多个采用方。
- **判断方法**：在完全不提供统计信息的前提下跑同一条 SQL，看计划是否改变。不改变，说明你只拿到了规则重写；此时把它宣传成「我们有 CBO」是过度陈述。

#### 3.2.5 Cost-Based + Cascade 框架

- **被什么约束逼出来**：搜索空间是阶乘级（N 张表有 N! 种连接排列【推算】：N 张表的全排列即 N!），穷举不可行，但又必须保证「不比某个已知计划差」——需要带剪枝的搜索框架。
- **结构**：Memo（等价类）+ 变换规则 + 代价上界剪枝，三件缺一不可。

```text
Cascades 的两个结构件：Memo 与 变换规则
  Memo（按「等价表达式」分组的搜索图）
    Group G1 ── 逻辑表达式 e1
      ├─ 规则 r1 → G2 的等价式
      └─ 规则 r2 → G3 的等价式
    Group G2 ── 物理实现 p1（代价 12）
    Group G3 ── 物理实现 p2（代价 9）
  ─────────────────────────────────────────────
  剪枝：新产生的计划若代价已超过当前最优上界，直接丢弃，不再展开其子问题
  → 关键：剪枝比较的是「绝对上界」，不是「相对好坏」
```

- **为什么这样设计有效**：因为 Memo 把「逻辑等价」与「物理实现」分成两层存储，同一次搜索既能复用子问题的最优代价（动态规划），又能复用可扩展的变换规则（规则系统）——这就是 Cascades 同时解决搜索成本与可扩展性的方式。
- **代价**：Memo 的实现复杂度高（等价类分组、规则调度、上界传播都要自己维护）；搜索必须带节点/时间预算；代价模型的精度直接决定剪枝是否剪对了。
- **失效点**：当查询是短查询（执行时间远小于优化时间）时，「充分搜索换取更优计划」的优点反转成「优化开销成为总耗时主要部分」——因为搜索成本与收益的比值随执行时间下降而上升；同理，代价偏差会让上界剪枝剪掉真正的好计划，且这种错误不可观测。
- **真实使用**：Cascades 由 Goetz Graefe 提出【公开】G. Graefe, *The Cascades Framework for Query Optimization*, IEEE Data Engineering Bulletin, 1995；更早的 Volcano 优化器生成器见【公开】Graefe & McKenna, ICDE 1993。判断某引擎是否采用该框架的方法：看它的优化器是否具备 Memo（等价类）+ 变换规则集 + 代价上界剪枝三件结构。
- **判断方法**：统计「优化耗时 / 执行耗时」的**比例分布**（P50、P99），而不是平均值——平均值会把短查询里优化耗时占比极高这一类问题完全抹平。

#### 3.2.6 AI 自治优化（2025+）

- **被什么约束逼出来**：调优是长尾人力成本，且多数参数是「每实例每负载」的连续值——需要能持续观察效果并自我修正的回路。
- **结构**：自治优化是一个带安全边界的控制回路，不是「自动执行模型建议」。

```text
自治优化 = 带安全边界的控制回路
  观测：延迟分布 / 扫描字节 / 资源利用率
    │
  决策：刷新统计信息 / 调参数 / 加索引 / 建物化视图 / 改计划开关
    │  ← 硬约束：变更窗口、最大影响面、SLO 不得低于基线
  执行：灰度 + 一键回滚
    │
  验证：与基线比同一指标（不是「看起来快了」）
    │
  回到观测（变差 → 自动回滚，并记为负样本）
```

- **为什么这样设计有效**：因为回路每一步都可度量、可回滚，无人值守才成立；任一步不可度量，自治就退化成「悄悄变坏」。
- **代价**：需要稳定的基线与统一指标口径，以及把优化动作当成一等公民做配置管理（版本化、可回滚、可审计）。这些工程成本远高于模型调用本身。
- **失效点**：当目标函数不唯一（交互查询追 P99、批任务追吞吐）时，自治优化会在两组指标之间震荡；因为单回路无法同时优化两个方向，必须显式分层（不同队列用不同回路），否则「自动调优」会把资源在两类负载间来回搬。
- **真实使用**：截至本稿写作时（2026），完全无人工干预的自治优化器尚未见公开的长期大样本验证【经验】。判断方法：向厂商索要「自治变更的回滚率与误动作率」，而不是「加速比」。
- **判断方法**：问一个具体问题——自治系统改坏了一个配置，多久能回滚、谁批准回滚。答不上来，说明当前具备的是「自动执行」而不是「自治」。

六个模式拆完，可以看到一条共同线索：**每个模式的失效点都不在它宣称的能力边界内，而在它把决策固定下来的位置**。CBO 把决策固定在优化前，于是怕统计信息过期；AQE 固定在 stage 边界，于是怕瓶颈落在阶段内部；Cascades 固定在搜索预算内，于是怕短查询；自治系统固定在控制回路里，于是怕多目标。判断一个模式是否适合你，最有效的方法不是看它解决了什么，而是问「它把决策固定在哪一刻」——然后检查你的负载里，最贵的那类问题是否恰好落在那一瞬间之后。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 数据分布稳定、catalog 完整、查询模式收敛 | CBO + 统计信息 | 不选自研 Cascades：搜索框架的固定成本换不来额外收益 | 每个 Join 表的统计信息采集时间在一个变更周期内 |
| shuffle 后尺寸不可预测、倾斜常见 | CBO + AQE | 只上 CBO：编译期估算错误会在 shuffle 后被放大 | 计划里声明的 Join 策略与实际分区大小是否常偏离 |
| 以 StarRocks / Doris 为代表的一体化分析引擎、点查与聚合混合 | CBO + AQE + AI 建议（按引擎实际支持的能力逐项取舍） | 不换自研 Calcite：引擎已内建优化器，重做一遍没有增量 | 该引擎是否支持运行时纠偏与 AI 建议；原文件标注的版本为 StarRocks 3.x、Doris 2.1+，能力对照请以各自官方文档核验 |
| 慢查询长尾、DBA 时间被诊断吃掉 | CBO + AQE + AI 驱动优化 | 不直接上自治：没有基线与回滚，自动变更风险高于收益 | 是否已有「扫描字节 / shuffle 字节」这类可信指标 |
| 自研引擎、无优化器专家 | Calcite 嵌入式优化器（前端）+ Velox 一类向量化执行层（后端） | 不选自研 Cascades：等价类与规则调度的工作量常被低估 | 能否为每个数据源实现统计信息接口 |
| 以 ClickHouse 为代表的分析引擎、查询以全表扫描与聚合为主 | 向量化执行 + 规则重写 | 不硬套 CBO：若引擎不做基于统计信息的代价搜索，配统计信息也无处生效 | 看官方文档与 EXPLAIN 输出中是否存在基于统计信息的代价比较（原文件标注 ClickHouse 24.x；是否具备 CBO 请自行核验） |
| 自研引擎、有优化器专家、查询模式极专一 | Cost-Based + Cascade 框架 | 不选 Calcite：通用抽象层会挡掉专用优化 | 优化耗时占查询总耗时的比例是否可接受 |
| 有基线、有回滚、负载已分层 | AI 自治优化（谨慎） | 不选「AI 建议 + 人工执行」：人工环节成为吞吐瓶颈 | 每个自动动作是否可一键回滚 |

表下说明：本主题下**最常被误选**的一对是「Calcite 嵌入式」与「Cost-Based + Cascade 自研」。误选 Calcite 的团队往往以为「用了 Calcite 就有了 CBO」，上线后发现代价层没有统计信息输入、退回纯规则重写；误选自研 Cascades 的团队则低估了 Memo 的实现与规则调度成本，半年后得到一个只能在少数查询上生效、且没人敢改的优化器。两者的实际后果相同：**优化器存在，但无法解释自己的选择**。

使用这张表的顺序是**从下往上读**：先确认「是否具备基线、回滚与负载分层」，再确认「统计信息接口是否可得」，最后才看查询模式是否收敛。反过来从上往下按场景挑模式，就会得到「用着最新能力、却仍靠 hint 兜底」的状态。另外注意表中「关键判据」一列写的都是**可观测的事实**（采集时间、指标是否采集、能否回滚），不是成熟度标签——模式选择能落地的唯一前提是判据可验证。

### 3.4 组合模式：真实系统不会只用一种

1. **CBO + AQE（编译期规划 + 运行时纠偏）**：职责边界——CBO 给出 Join 顺序与策略的初稿，AQE 在 stage 边界用实测分区统计改写其中一部分。运维代价——两套决策逻辑并存，EXPLAIN 必须能展示「AQE 之后」的最终计划，否则排障会对着一个已经不执行的老计划讨论。适合规模：单查询 shuffle 数据量在几十 GB 到 TB 级、倾斜可复现。
2. **CBO + AI 驱动诊断（自动执行 + 人工裁决）**：职责边界——CBO 负责选计划，AI 负责把「为什么选错」翻译成人能读的动作建议。运维代价——需要指标采集链路与建议的回归验证，否则建议无法排序。适合规模：慢查询长尾明显、DBA 时间紧张的团队。
3. **Calcite + 自有代价模型（框架 + 专用）**：职责边界——Calcite 提供解析、逻辑树与规则框架，统计信息适配与代价模型自己补。运维代价——框架与自研的边界必须一次划清，否则规则执行顺序会变成不可控变量。适合规模：自研引擎、查询模式相对收敛、团队里至少有一名懂代价模型的人。

三种组合共同的前提是**边界写在配置里，而不是写在人脑里**：CBO 与 AQE 的分工要能从「最终计划」上看出来，Calcite 与自研的分工要能从「哪条规则在什么顺序执行」上看出来，CBO 与 AI 的分工要能从「建议是否被验证过」上看出来。边界一旦只存在于某位工程师的记忆里，组合模式就会在人员变动后退化成「谁也不敢动」。

```text
CBO + AQE + hint 的三层边界（谁在什么时候还能改计划）
  编译期：CBO 定 Join 顺序与策略 ──► 计划初稿
        │（此后 CBO 不再参与）
  stage 边界：AQE 用实测分区统计改写 ──► 计划二稿
        │（此后 AQE 不再参与）
  stage 内部：算子已启动，不可改
        └─ 唯一出口：人工 hint / 预计算（本质是把问题提前挪出这一层）
```

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 不收集统计信息 | EXPLAIN 里行数估计是常量，或与真实结果差几个数量级 | 代价模型失去唯一输入，argmin 退化为「按书写顺序挑」，build 侧选成大表、产生超额 shuffle | 采集是异步任务，与写入链路解耦后无人负责 | 把统计信息刷新挂进写入链路：写入完成 = 统计信息在阈值内 |
| 未启用 AQE | 小表 join 大表仍选 Sort Merge、shuffle 出上千个小分区 | 编译期的估算错误一路传到执行，出现单任务 OOM 与长尾 | 老版本默认关闭，升级时配置未迁移 | 开启 AQE 及其子能力，并对比开启前后的计划确认真的被改写 |
| 统计信息陈旧 | 同一 SQL 在不同日期表现差异大，且数据量单调增长 | 偏差随写入累积，凌晨批任务与白天交互查询拿到不同质量的计划 | ANALYZE 是离线任务，失败无人告警 | 记录「最后采集时间」，关键表按数据变更阈值触发采集 |
| Join 顺序错误 | 执行计划里大表与大表做 Hash Join、广播对象超阈值 | 网络与内存成为瓶颈，任务堆积且难以归因 | OR 条件、相关子查询、NDV 估计偏差让优化器失去排序依据 | 先修统计信息与 SQL 写法，再把 hint 作为最后出口，并附失效条件 |
| 忽视数据倾斜 | 任务总数上千、绝大多数秒级完成、极少数跑很久 | 整个 stage 的完成时间等于最慢分区，加资源也无法缩短 | key 分布长尾（默认值、热点商户、空值） | 识别倾斜键并打散（加盐 / 拆分 / 预聚合），或在支持时开自适应倾斜 Join |
| 完全依赖 CBO | hint 越加越多，最终 hint 比 SQL 还长 | 维护面爆炸，升级引擎后 hint 语义变化引发回归 | 把优化器当成「保证」，而不是「边界内近似的求解器」 | 划定信任边界：相关列、倾斜键、UDF 之外交给它；边界内的 hint 必须记录原因与复核日期 |
| 用参数掩盖 SQL 问题 | 同一查询反复调参数，配置项越加越多 | 优化器被当成绕开 SQL 缺陷的通道，问题从 SQL 层转移到配置层，排障成本上升 | 改参数比改 SQL 快，且不需要业务方配合 | 先判断是「SQL 本身不合理」还是「优化器选错」：前者改 SQL，后者才动计划 |

三个最危险的反模式在生产中的典型暴露方式：

- **不收集统计信息**：它的危险在于**静默**。系统不会报错，只是每条查询都慢一点；直到某天遇到一个「大表 join 大表」的查询，才发现引擎从来不知道表有多大。它的暴露方式往往是容量事故，而不是性能告警。
- **忽视数据倾斜**：它的危险在于**掩盖**。加了资源、扩了并行度，完成时间不变——因为完成时间由最慢那一个分区决定，而资源全被快任务吃掉了。团队常常把它误判为「资源不足」，反复扩容。
- **完全依赖 CBO**：它的危险在于**不可回退**。当 hint 累积到与 SQL 等长时，任何引擎升级都变成一次高风险回归测试；此时团队想拆掉 hint，却发现没人能说清每条为什么在那里。

三个反模式之间存在**耦合放大**：没有统计信息 → CBO 选错 Join 顺序 → 团队加 hint 兜底 → hint 越积越多 → 优化器升级后 hint 语义变化 → 更不敢依赖 CBO。这是一个自我强化的循环，而且每一环在当时都是理性决策。打破它的位置不在最后（删 hint），而在第一环：**先把统计信息补齐，再谈 hint 是否还有必要**。

在生产中定位这些反模式，靠的不是询问，而是三个可采集的信号：**估计与实际的比值**（看 EXPLAIN 与 EXPLAIN ANALYZE 的差异，判断统计信息质量）、**任务耗时的分布形态**（看最长任务与中位任务的差距，判断倾斜）、**优化耗时的占比**（看优化与执行的耗时分布，判断搜索预算是否失衡）。三者都可在不读 SQL 的前提下获得，因此适合作为常态监控项，而不是事故后的排查手段。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：规模或访问模式跨过阈值时，原来正确的模式会变成错的。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 数据量 MB → GB，查询从批到交互 | 规则优化（RBO） | 规则顺序在数据分布变化后不再最优，且无法解释为何慢 | CBO + 统计信息 | 需要 catalog 与采集链路，采集本身占 I/O |
| shuffle 几十 GB → TB | CBO | 编译期基数误差被 shuffle 放大，Join 策略失效 | CBO + AQE | 排障要能读懂 AQE 之后的计划，复杂度上升 |
| 参与 Join 的表 5 → 十几张 | 动态规划穷举 | 搜索空间按 N! 增长【推算】，优化耗时进入秒级 | 贪心 / 启发式枚举 + 显式搜索预算 | 可能放弃真正最优顺序，需保留 hint 出口 |
| 引擎从单负载变多负载共用 | 统一参数 | 交互查询与批任务的优化目标直接冲突 | 按队列分回路，各自设预算 | 运维面分裂，配置管理成本上升 |
| 优化动作从人工变自动 | 人工调参 | 变更频次上升，回滚能力成为前提 | AI 自治优化（带回滚与审计） | 需要基线、指标口径、版本化与审计链路 |

表中最容易误判的一行是「参与 Join 的表 5 → 十几张」。多数团队认为优化器的搜索能力与表数无关，直到某个宽表查询的优化耗时进入秒级——**N 张表的连接排列是 N!【推算】**，5 张表 120 种、10 张表约 360 万种、15 张表约 1.3 万亿种，搜索必须靠剪枝或启发式才可控。识别信号不是「查询变慢」，而是「同一条 SQL 的优化耗时随表数增长而上升」。

另一行容易被忽略的是「单负载 → 多负载共用」。模式的失效往往不是数据量造成的，而是**目标函数从一个变成两个**：交互查询要 P99 低，批任务要吞吐高，两者在同一组优化参数下必然有一方受损。此时换的不是优化器，而是「优化预算的分配方式」——按队列分回路，而不是继续调参数。

跨过任一阈值时，最危险的做法是**直接切到新模式而不保留旧出口**。AQE 兜不住阶段内部瓶颈，Cascades 在短查询上可能不如规则顺序，自治系统在多目标下会震荡——每一次跃迁都应同时保留下一个跃迁可回退的通道（保留 hint 出口、保留手工计划基线、保留一键回滚）。

反向使用这张表同样成立：如果你的负载里有大量亚秒级交互查询，就不该把优化预算花在搜索上；如果你的数据源根本给不出统计信息，那么第一步不是换优化器，而是补元数据。**跃迁的判据是「疼在哪里」，不是「别人换到了哪」**——模式换早了，付出的迁移成本与获得的能力会长期不匹配；换晚了，则每一次查询都在为已经越过的阈值付费。

### 3.7 自检清单

按「统计信息 → 运行时纠偏 → 自动化」的顺序排查：前几条不通过时，后面的条目没有意义。

- [ ] 每张参与 Join 的大表，最近一次统计信息采集是否在一个数据变更周期内？有没有参与 Join 却完全没有统计信息的表（裸文件外部表、无 catalog 数据源）？
- [ ] EXPLAIN 中每个 Join 的行数估计与真实结果是否在同一数量级（偏差 > 10 倍即视为估算失效）？有没有出现过「同一查询在不同时间段拿到不同质量计划」而无人解释的现象？
- [ ] AQE 是否开启？开启后是否对比过计划，确认它真的改写了决策？
- [ ] 最热的 10 条查询是否记录了「扫描字节 / shuffle 字节 / 峰值内存」，而不是只有耗时？
- [ ] 是否有一份可复现的倾斜键清单与对应打散方案？
- [ ] 现有 hint 是否都标注了原因与复核日期（无原因的应删除）？每一次人工干预（hint / 参数 / 计划固定）是否都能在变更记录里找到负责人？
- [ ] 优化耗时是否在观测范围内（尤其短查询：优化耗时占比是否超过执行耗时）？
- [ ] 交互查询与批量任务是否共用同一组优化预算？若是，是否已分层？
- [ ] 若引入 AI 建议，是否定义了「建议 → 小流量验证 → 采纳 / 丢弃」的闭环？
- [ ] 若声称自治优化，是否具备一键回滚与变更审计？
- [ ] 引擎升级的回归用例是否覆盖「统计信息缺失 / 数据倾斜 / 谓词相关」这三类估算盲区？升级前是否用真实负载做过计划回归对比，而不是只看功能列表？
- [ ] 是否有人能在 5 分钟内读懂一条慢查询的 EXPLAIN 并指出估计失真的节点（读计划能力是其他一切的前提）？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 数据分布稳定、统计信息可得 | CBO + 统计信息 | 统计信息是代价模型唯一输入，估得准就不需要运行时纠偏 |
| shuffle 规模不可预测、倾斜常见 | CBO + AQE | 只能在 stage 边界用实测值纠正编译期的估算误差 |
| 自研引擎、无优化器专家 | Calcite 嵌入式优化器 | 用 Adapter + 统计信息接口换取规则与代价框架 |
| 自研引擎、有专家、查询模式收敛 | Cost-Based + Cascade 框架 | Memo 加代价上界剪枝，把阶乘空间压成可控的搜索成本 |
| 慢查询长尾、DBA 是瓶颈 | AI 驱动优化 | 把「指标异常 → 候选动作」自动化，但必须闭环验证 |
| 有基线、有回滚、负载已分层 | AI 自治优化（谨慎） | 自治成立的前提是每一步可度量且可回滚 |
| 统计信息接口无法提供（裸文件 / 无 catalog） | 先补元数据，再谈模式 | 没有基数输入时，任何选择都只是规则顺序的另一种写法 |
| 查询以亚秒级交互为主 | 规则重写 + 固定计划基线 | 优化预算小于执行时间，搜索收益为负 |

> 本节小结：本主题下**决定模式选择的唯一那条约束**是「你能否在编译期知道真实的中间结果规模」。知道，就用 CBO + 统计信息自己做减法；不知道，就必须在运行时（AQE）或人工出口（hint）兜底；完全不可知且要求无人干预时，才谈得上 AI 与自治——而它们的门槛不是模型能力，是基线与回滚能力。
>
> 值得单独记住的是：**优化器的强弱不由它启用了几个高级特性决定，而由它能否解释自己的选择决定**。一份能被读懂、能被验证、能被回退的计划，胜过一份「更快但没人说得清为什么」的计划——前者可以持续演进，后者只能被供起来。
>
> 落到动作上，顺序只有三步：**先把统计信息补齐**（让代价模型有输入），**再把运行时纠偏打开**（让估算误差有出口），**最后才谈自动化与自治**（让优化动作有回路与回滚）。跳过第一步直接做第三步，得到的是「配置很先进、查询仍然慢」的典型状态。
