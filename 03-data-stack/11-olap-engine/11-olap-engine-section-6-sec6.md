### 11.1 字节"**StarRocks 千亿级 OLAP**"5+ 年（2019-2024）

**背景（Why）**

字节 2019 年面临**千亿级 OLAP 查询**：
- **千亿级实时指标查询**——**传统 Hive 慢**
- **多维分析**——按 10+ 维度任意组合
- **秒级响应**——看板必须秒级

**触发点（What）**

2019 年字节采用 **StarRocks**（原 Doris 演进版）（[字节 2019]），目标：
- **千亿级查询秒级**
- **10+ 维度任意组合**
- **高并发**

**详细做法（How）**

字节 StarRocks 的**5 大核心组件**：

1. **MPP 架构（核心创新）**
   - 关键设计：**大规模并行处理 + 向量化执行**
   - 关键能力：**千亿级秒级**
   - 关键数字：**查询 P99 < 3s**

2. **列存 + 索引（核心）**
   - 关键设计：**列存 + ZoneMap + 布隆过滤器**
   - 关键能力：**扫描少**
   - 关键数字：**压缩比 10x**

3. **实时导入（核心）**
   - 关键设计：**Flink → Kafka → StarRocks Stream Load**
   - 关键能力：**秒级新鲜度**
   - 关键数字：**延迟 < 5s**

4. **CBO 优化器（核心）**
   - 关键设计：**基于成本的优化 + 自适应**
   - 关键能力：**复杂查询最优**
   - 关键数字：**复杂查询 10x**

5. **多租户（核心创新）**
   - 关键设计：**资源组隔离 + 查询路由**
   - 关键能力：**千租户**
   - 关键数字：**千业务**

**字节 StarRocks 关键数字**（[字节 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **查询 P99** | 分钟级 | < 3s | **-95%** |
| **千亿级** | 不可用 | 100% | **∞** |
| **10+ 维度** | 不可用 | 100% | **∞** |
| **压缩比** | 1x | 10x | **+10x** |
| **实时延迟** | 分钟级 | < 5s | **-99.9%** |
| **千业务** | 不可用 | 100% | **∞** |
| **CBO** | 不可用 | 100% | **∞** |
| **MPP** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：字节 OLAP 团队 100+ 人
- 关键数字：**千亿级**；**查询 < 3s**；**千业务**
- 业务影响：覆盖**字节全部实时查询**

**失败教训**

- 早期「**Hive 慢**」——分钟级查询，倒逼 StarRocks
- **列存 schema 错**——字符串 vs 整数差别巨大，**后强约束列类型**
- **CBO 估计错**——复杂 join 误判，**后采统计信息 + 自适应**

### 11.2 小红书"**ClickHouse 千亿级**"4+ 年（2020-2024）

**背景（Why）**

小红书 2020 年面临**千亿级内容分析**：
- **千亿级笔记 / 互动**——传统 Hive 慢
- **实时分析**——内容运营必须秒级
- **多维**——笔记 / 用户 / 互动多维

**触发点（What）**

2020 年小红书采用 **ClickHouse**（[小红书 2020]），目标：
- **千亿级秒级**
- **多维分析**
- **高并发**

**详细做法（How）**

小红书 ClickHouse 的**5 大核心组件**：

1. **列存 + 向量化（核心创新）**

   - 关键能力：**千亿级秒级**

   - 关键数字：**TB 级**

3. **分布式集群（核心）**
   - 关键设计：**分片 + 副本**
   - 关键能力：**横向扩展**
   - 关键数字：**百节点**

4. **实时导入（核心）**
   - 关键设计：**Kafka → ClickHouse Stream Insert**
   - 关键能力：**秒级**
   - 关键数字：**延迟 < 5s**

5. **多业务（核心创新）**
   - 关键设计：**多业务共享 + 资源隔离**

### 11.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**StarRocks 或 ClickHouse 起步**」（**最简单**）——**10+ 表**
- 关键设计：**列存 + 索引是底线**
- 团队：**2-3 人**
- 验证标准：**查询 < 5s**

**1 → 10 阶段：6-12 个月**

- 扩展到「**100+ 表 / PB 级**」
- 引入「**实时导入（Kafka / Flink）**」
- 引入「**CBO 优化器**」
- 团队：5-10 人
- 验证标准：**查询 < 3s**、**PB 级**

**10 → 100 阶段：12-24 个月**

- 扩展到「**千亿级**」
- 引入「**分布式 + 副本**」
- 引入「**实时物化视图**」
- 团队：10-30 人
- 验证标准：**千亿级**、**千 QPS**

**100 → 1000 阶段：12-24 个月**

- 引入「**Iceberg 外表（湖仓一体）**」
- 引入「**多租户 + 资源隔离**」
- 团队：30-100 人
- 验证标准：**千业务**、**PB 级**

> **本节小结**：
> - 4 个真实案例（字节 / 小红书 / 京东 / 腾讯）印证：**OLAP 不是「**Hive 离线**」，是「**StarRocks / ClickHouse + 列存 + 实时导入 + CBO**」**5 件套**。

> - 99% 的失败来自「**Hive 慢 + JOIN 慢 + 写入瓶颈**」——必须有 **列存 + 宽表预 JOIN + 分布式**。
> - 真正的 ROI 来自「**P99 分钟级 → < 3s + 千亿级 + 8 业务**」——是**大厂核心 OLAP 基础设施的命脉**。
