## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把 StarRocks / Doris / ClickHouse / Trino / DuckDB 放进同一张 1–5 分表，用「查询性能 / 实时写入 / Join 性能 / 物化视图 / 联邦查询 / AI 友好 / 内嵌能力」七个维度打分。这个做法有三个结构性错误。

**错误一：这五者不是同一层的选项。** StarRocks / Doris / ClickHouse **自带存储**，数据要搬进引擎；Trino **不拥有存储**，它读别人的数据；DuckDB 不是服务，是**可以被嵌进你进程里的库**。给「一个数据库」「一个查询网关」「一个函数库」打同一张分表，等价于比较「仓库 / 货车 / 手推车」谁更好——DuckDB 完全可以是一个 Notebook 里的执行部件，而 Trino 也可以读 ClickHouse 里的表，它们在真实系统里是**并列出现**而不是**二选一**。

**错误二：「查询性能」这一维在 OLAP 里没有主语。** 一次分析查询的耗时主体由两件事决定：**扫了多少数据块**、**搬了多少行到汇总节点**，而不是引擎内核比对手快多少。同一张表换一个排序键，同一个引擎的耗时差一个量级是常见的【经验】。打分表的「性能」比较的是引擎自己，而用户感受到的性能由**表设计 + 查询形态**决定——这是打分表无法编码的一项。

**错误三：「内嵌能力 1 分」的符号取决于场景。** 给 Trino 的内嵌能力打 1 分、DuckDB 打 5 分，隐含判据是「内嵌更好」。但在需要**数十人共享一个查询入口、且要求统一权限与审计**的组织里【经验】，能内嵌恰好意味着**没有统一的权限、审计与资源隔离**——在那里它是一张减分项。同一个数值在不同组织里符号相反，这正是打分表的典型症状：它把「取决于场景的结论」伪装成「绝对结论」。

打分表输出的是**名次**；选型要回答的是「**在我的数据形态、更新语义与并发形态的约束下，下一步该用哪一类引擎，以及它在什么条件下失效**」。

**本章采用的 6 条判据**（已针对 OLAP 主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 数据在哪 | 数据必须搬进引擎，还是能留在原处被读取 | 决定成本里有没有「第二份存储 + 一条导入链路」，也决定冷数据能不能进来（见 7.4） |
| 更新语义 | 需要 upsert / 部分列更新，还是只追加 | 决定表模型，也决定「实时写入」到底是引擎的能力还是后台合并的速度（见 7.3.2） |
| 查询形态 | 单表宽表聚合、多表 join、还是点查 | 三者要求相反：聚合要预聚合、join 要按连接键对齐分布、点查要前缀索引 |
| 数据布局可改吗 | 分区键 / 排序键 / 分桶键能不能重建 | OLAP 没有「事后补索引」这条路，布局定死之后查询侧能做的事很少（见 7.3.1） |
| 可见性要求 | 写入到可查是秒级，还是分钟级可接受 | 秒级意味着更小的微批窗口与更高的合并压力，两者在同一台机器上互相挤占 |
| 运维与生态 | 要几个常驻组件、几个人；离开它要动什么 | 常驻组件数与升级节奏是与数据量无关的固定成本（见 7.4、7.7） |

打分表的七个维度一个未丢，只是位置变了：**查询性能**与 **Join 性能** → 判据 3 与 7.3.3；**实时写入** → 判据 2；**物化视图** → 判据 3（它是把聚合与 join 前移到写入侧的一种实现）；**联邦查询**与**内嵌能力** → 判据 1（同一个问题的两端：数据在谁的进程里被算）；**AI 友好**不是独立维度——Agent 要的是「机器可读的元数据 + 一份稳定的 SQL 方言 + 能在同一查询里做结构化过滤与向量检索」，前两项是判据 1、6 的推论，第三项落在 7.3.1 的布局上，单独给它打分只会重复计权。

判据的顺序对应一个筛选顺序：**判据 1、4 是结构性的**（数据放哪、布局怎么定，一旦落地改写量以月计），**判据 2、3、5 是运行层面的**（多数可通过换表模型或调参缓解），**判据 6 是组织层面的**。**打分表的根本问题在于把这三类混在一根尺子上**：「内嵌能力 1 分 vs 5 分」这种结构性差异，和「联邦查询 2 分 vs 1 分」这种接一个连接器就能抹平的差异，在表里长得一样重。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| StarRocks | 自带存储的分布式列存 MPP | 主键模型（写入即追加版本 + 后台合并）+ 向量化 + 自动增量物化视图 | 实时数仓、高并发看板、湖仓加速 | Apache 2.0；另有 CelerData 商业发行 / 托管版（母公司一列见主文件 §2.4；许可条款以官方仓库 LICENSE 为准） |
| Apache Doris | 同上，同源的另一支系 | Unique Key 模型表达同一机制；StarRocks 由原 Doris 团队分叉而来（主文件 §1.4） | 实时与离线报表一体 | Apache 2.0 |
| ClickHouse | 自带存储、单机为第一公民的列存引擎 | MergeTree：写入追加 part + 后台 merge，排序键决定扫描区间 | 日志、事件、单表大宽表分析 | Apache 2.0 + 商业云 |
| Trino | 无自有存储的集群联邦查询引擎 | 协调节点规划、工作节点执行，数据留在源端，下推率决定代价 | 跨源即席、湖上探索 | Apache 2.0 |
| DuckDB | 可嵌入的分析型数据库 | 进程内、单机、向量化执行，无客户端/服务端之分【公开，*DuckDB: an Embeddable Analytical Database*（SIGMOD 2019 演示论文），2019】 | Notebook、本地分析、服务内嵌 | MIT |
| Apache Druid | 面向事件流的实时 OLAP | 写入侧预聚合 + 时间分区 + 不可变段 | 实时大屏、监控 | Apache 2.0 |
| Apache Pinot | 同上族 | 不可变段 + 多种索引，面向低延迟、高并发的固定查询 | 用户面向的分析 | Apache 2.0 |
| SelectDB Cloud | 云上托管服务 | 与 Doris 同源的商业发行 / 托管形态 | 希望托管而非自建的组织 | 商业 |
| Iceberg 一类表格式 | 不是引擎，是湖上的表规范 | 文件清单 + 快照，让多个引擎共享同一份数据 | 湖仓（本目录 §6 腾讯案例） | Apache 2.0 |
| LanceDB 一类向量库 | 不是 OLAP 引擎，是组合里的向量检索件 | 近似最近邻索引 + 列式存储 | RAG、多模态检索 | 开源 |

这 10 项其实分**五族 + 两类组件**：**自带存储的分布式 MPP 族**（StarRocks、Doris、SelectDB）、**单机优先的列存引擎族**（ClickHouse）、**事件预聚合族**（Druid、Pinot）、**无存储的联邦查询族**（Trino）、**进程内库族**（DuckDB）；表格式与向量库则是**组合件**，不是替代项——把组件放进替代项的表里比，是打分表的第二个错误来源。

同族内部差异小、跨族差异大。**先分族再选能省掉一半比较**：先问「数据能不能搬、算在谁的进程里」，再在族内比细节。

**打分表对比的候选全部保留**，只是重新归类：

| 选型分支 | 归入本章哪一族 | 它在选型里动的是哪一项 |
| --- | --- | --- |
| 单表大宽表聚合 → ClickHouse | 单机优先的列存引擎族 | 布局（排序键即扫描边界）+ 无通用 join 对齐 |
| 多表 Join + 实时 → StarRocks / Doris | 自带存储的分布式 MPP 族 | 更新语义 + 分布键对齐 |
| 联邦跨源查询 → Trino | 无存储的联邦查询族 | 数据在哪算（拉到集群）+ 下推率 |
| 内嵌 / Notebook → DuckDB | 进程内库族 | 进程边界为 0 + 无常驻成本 |
| AI 应用 → StarRocks 3.x + 向量索引 | 自带存储的分布式 MPP 族 | 结构化过滤与向量检索在同一查询内 |

**上表只列机制，不断言「某产品是否支持某特性」**：版本迭代很快，写死会产生过期断言。凡涉及具体能力，用下面三种判定方法自查：

- **某个引擎支不支持某特性（向量索引、存算分离、物化视图自动改写）**：查其官方文档对应章节，并以自己版本上的 `EXPLAIN` / `SHOW` 输出为准。版本号只在能从官方 release note 核到时才写；核不到就只写判定方法。
- **某张表的查询到底扫了多少**：看查询实际读取的行数与字节数、以及它们与表总量的比值。这个比值是布局是否有效的唯一判据，比任何基准数字都贴近你自己的数据。
- **某个引擎的性能**：用自己的表、自己的查询、只换引擎做 A/B。公开材料里的倍数只能用来判断「值不值得试」。

### 7.3 机制差异：为什么它们表现不同（核心节）

五族的全部差异可以归因到四个机制维度。选这四个，是因为它们分别回答选型时必然要问的四件事：**查询扫多少（7.3.1）· 写入怎么变成可读的版本（7.3.2）· 分布式执行把数据搬到哪里（7.3.3）· 存储归谁、能不能分开伸缩（7.3.4）**。

#### 7.3.1 数据布局：扫描边界在写入时就定了

**机制是什么**：列存 + 分区 + 排序键（+ 编码）共同决定「一次查询最少要读多少数据」。列存让你只读用到的列，分区与排序键让你只读落在范围内的连续区间。

**各候选的实现差异**：

| 候选 | 布局由谁决定 | 事后能改吗 | 可跳过的单位 |
| --- | --- | --- | --- |
| ClickHouse | `PARTITION BY` + `ORDER BY`，排序键在 part 内有序 | 改排序键 = 重建表 | 分区、排序键前缀命中的 granule、跳数索引 |
| StarRocks / Doris | 分区 + 排序键（前缀索引）+ 分桶键 | 同上 | 分区、前缀索引命中的区间 |
| Trino | 由源端表格式决定（分区列 + 文件级统计） | 改源端元数据即可 | 分区、文件 |
| DuckDB | 由文件自身的行组统计 | 重写文件 | 行组（row group） |
| Druid / Pinot | 由写入时的时间分区与段生成 | 重建段 | 时间区间 + 列字典 |

**由此必然导出的性质**：**因为**数据按列分开存、且行序由排序键在写入时就定死，**所以**扫描量由「查询范围占表的比例」决定，而不是由表的大小决定——只看上个月某个城市时，可以完全不读其他分区与列。这是 OLAP 能做到交互式的**全部来源**，与算力无关。**也正因为**行序在写入时定死，**所以**「加一个索引让这条查询变快」这条在 OLTP 里最常用的路径在 OLAP 里几乎不存在：改布局等于重建表，代价随数据量线性上涨。这条性质直接推出一条工程纪律——**表设计要先于查询优化，且要按未来最常见的过滤列来定**。

**算一次裁剪的量级**【推算】：一张 100 列的事实表，若查询只涉及 5 列，列存要读的字节数约为行存的 5%（推导链：5 / 100 列，按每列字节数量级相近估算，不含压缩差异）；再叠加「只扫一个月而不是一年」的分区裁剪，扫描比例再降到约 1/12（推导链：1 个月 ÷ 12 个月）。两项相乘后，实际读取量约为表总量的 **0.4% 量级**（推导链：5% × 1/12 ≈ 0.4%）。**这约 250 倍的降低全部来自「只读需要的列与分区」，与有没有索引无关**——它也是为什么宽表在 OLAP 里可行、在 OLTP 里不可行的原因。

**公开证据**：Iceberg 表规范要求清单文件记录每个数据文件的分区值与列级统计，引擎据此做分区裁剪与文件级裁剪，这是「布局决定扫描量」的规范性依据【公开，Apache Iceberg 表规范 v2，2022；清单文件字段定义可自行核验】。ClickHouse 的 MergeTree 以 `ORDER BY` 作为唯一的一级排序依据、并用跳数索引作为补充，可在其官方文档的表引擎章节核验【公开，ClickHouse 文档 · MergeTree，以官方文档当前版本为准】。可自行核验的判据：**看查询计划里输入行数是否随过滤条件收窄**——不收窄，说明过滤列没有落在布局上。

**失效条件**：当查询没有可用的过滤条件（全维度自由组合的探索式分析），或过滤列与排序列不匹配时，裁剪归零，扫描量回到全量，性能退化为「扫描带宽 ÷ 数据量」。此时正确的动作是**先物化**（见 7.6 组合）而不是换引擎。

#### 7.3.2 更新模型：upsert 的实时性由后台合并决定

**机制是什么**：列存里「更新一行」不是原地改写，而是**追加一个新版本，再由后台合并把多版本压成一个**。

**各候选的实现差异**：

| 候选 | 更新怎么表达 | 查询读到的版本 | 合并发生在哪 |
| --- | --- | --- | --- |
| StarRocks | 主键模型：写入即新版本，读取时按主键取最新 | 已提交版本 | 后台 compaction |
| Doris | Unique Key 模型（同一机制的另一实现） | 同上 | 后台 |
| ClickHouse | `ReplacingMergeTree`：同键多版本并存，需 `FINAL` 或查询时聚合 | 取决于是否已合并 | 后台 merge，时机不受控 |
| Trino | 无自有存储，更新语义由源端表格式给（如 Iceberg 的删除文件 / 读时合并） | 由快照决定 | 源端 |
| DuckDB | 单进程内更新表 | 立即 | 无 |

**由此必然导出的性质**：**因为** upsert 在列存里的实现是「追加 + 后台合并」，**所以**「实时写入」这个能力的天花板由**合并吞吐**决定，而不是由写入吞吐决定——写入端每秒都能收数据，查询端看到多少未合并版本却取决于后台的速度；**又因为**查询要在这批版本上做去重，**所以**合并长期跟不上时，表不会报错，它会**缓慢变慢**，表现为同一个查询的耗时随运行时长逐渐上升。反过来，**因为**只追加的表没有版本累积，**所以**它没有这个问题，代价是不能直接表达修正与删除——这就是「明细 append-only + 当前态主键表」两张表并存的机制来源，而不是某种实现上的权宜。

**公开证据**：ClickHouse 官方文档对 `ReplacingMergeTree` 明确说明「同一排序键的重复行在后台合并时被去重，且合并时机不受控」，并建议用 `FINAL` 或在查询中聚合以获得去重后的结果【公开，ClickHouse 文档 · ReplacingMergeTree，以官方文档当前版本为准】。主文件 §2.3 给出的 StarRocks 主键模型、Doris Unique Key 模型与 ClickHouse `ReplacingMergeTree` 三种写法，正是同一机制在三个产品里的表达。

**失效条件有两个**：其一，上游是高频、宽行、且伴随大量删除或反复更新（例如订单状态反复变更）时，合并压力会持续高于写入压力，此时该做的是**拆表**（明细与当前态分开），而不是调引擎参数；其二，**查询侧依赖「读时已去重」**，一旦漏写 `FINAL` 或去重聚合，读到的是重复行——这是静默错误，不报错，只在统计结果上表现为数值偏大。

#### 7.3.3 执行方式：聚合的搬运量与 join 的构建侧

**机制是什么**：分布式聚合与 join 把数据搬到哪、搬多少。聚合的搬运量由「是否先在本地预聚合」决定；join 的可行性由「构建侧能否被物化」与「两张表能否按连接键对齐分布」决定。

**各候选的实现差异**：

| 候选 | 聚合 | Join 的主要形态 | 对分布的要求 |
| --- | --- | --- | --- |
| StarRocks / Doris | 两阶段聚合（本地预聚合后再按分组键汇总） | shuffle / broadcast / 同分布键的本地 join | 表可按连接键对齐分桶 |
| ClickHouse | 两阶段聚合 | 右表广播或右表物化 | 无通用「按连接键对齐」的存储层约定 |
| Trino | 流水线交换 + 按分区汇总 | 分阶段 hash join，阶段间可落盘 | 无 |
| DuckDB | 单机向量化聚合 | 单机 hash join | 无（单机）；构建侧大小决定是否触发落盘与溢出量 |
| Druid / Pinot | 写入侧预聚合 | 通用（shuffle 式）join 能力受限，主流做法仍是写入侧展平 | 无 |

**由此必然导出的性质**：**因为**本地预聚合之后，跨节点传输的是分组后的中间结果而不是明细行，**所以**传输量与**分组数**成正比、与参与计算的行数无关——千亿行按十万个分组聚合，搬过去的是十万行量级。这条性质解释了一个反复出现的现象：**加机器对聚合慢查询的改善远低于预期**，因为加机器会同时增加参与搬运的节点数，搬运量不会因为并行而消失，只能因为「先聚合」而消失。**另一条性质来自 join**：**因为** hash join 必须先物化构建侧，**所以** join 的可行性由「构建侧多大」与「两张表能否按连接键对齐分布」决定，而不是由算力决定——这直接解释了为什么单表路线的引擎在多表 join 上会明显失分：不是它算不动，而是它没有为「按连接键对齐分布」设计存储层。补救方式是把 join **前移到写入侧**（写成宽表），让查询退回单表扫描；代价是数据冗余与写入时多一次加工，且宽表的字段会随着查询需求增加而继续膨胀。

**算一次搬运的量级**【推算】：设参与计算 1000 亿行、分组数 10 万。不做本地预聚合时，跨节点传输的量与行数同量级（10¹¹ 行）；本地预聚合后，传输的量与分组数同量级（10⁵ 行）。两者相差 6 个数量级（推导链：10¹¹ ÷ 10⁵ = 10⁶）；即使中间结果每行比明细行宽数倍，字节量的差距仍在 5 个数量级以上（推导链：10⁶ ÷ 10 ≈ 10⁵）。**这就是「加机器不如先聚合」的算术依据**——加机器改变的是等号左边的节点数，改变不了等号右边的搬运量。

**公开证据**：本目录 §6 的四个公开案例把「两阶段聚合（先在本地聚合，再跨节点汇总）」「物化视图 + 查询自动改写」「关联前移到写入侧」列为核心组件【经验】（来源：本目录 §6 汇总的公开案例，其标注的数字与年份以该节为准）。Trino 的执行模型（协调节点解析规划、工作节点按任务执行、节点间通过交换传递数据）在其官方文档的查询执行章节可核验【公开，Trino 文档 · Query execution，以官方文档当前版本为准】。

**失效条件**：当传输量与扫描量都已压到位，瓶颈会转移到 join 与最终聚合，此时继续优化聚合的边际收益趋零；另一处失效是**分组数本身很大**（接近主键粒度的细分组），本地预聚合压不下去，此时该改的是查询粒度（先粗后细）而不是引擎。

#### 7.3.4 计算与存储的耦合：成本函数里那一项有没有

**机制是什么**：引擎是否拥有自己的存储，以及计算与存储能否独立伸缩。

**各候选的实现差异**：

| 候选 | 存储归属 | 弹性 | 冷数据放在哪 |
| --- | --- | --- | --- |
| StarRocks / Doris | 自有存储，另有存算分离形态 | 计算可独立扩缩 | 留在引擎内则计入引擎存储预算 |
| ClickHouse | 以本地盘为主，云上有共享存储形态 | 与存储同比例扩 | 另行分层，否则占本地盘 |
| Trino | 无自有存储 | 计算纯弹性 | 只在源端，引擎侧零存储 |
| DuckDB | 文件系统 / 宿主进程 | 无（单机） | 本地 |
| Druid / Pinot | 自有段存储（深度存储常落对象存储 + 本地缓存） | 计算与深度存储可分离 | 冷段留在对象存储 |

**由此必然导出的性质**：**因为** Trino 不拥有存储，**所以**它的成本函数里没有「第二份数据」这一项，冷数据可以全部留在原处、多少都不进引擎——**代价是每次查询都要跨网络读远端**，单位数据的代价高，而且这份代价**随查询次数重复支付**；**因为** StarRocks / Doris / ClickHouse 拥有存储，**所以**它们能把扫描代价压到接近本地磁盘带宽，**代价**是数据要搬进来一份、导入链路要长期维护、冷数据也要占引擎的存储预算。两条路线的分界因此不是「谁快」，而是**「你打算为同一份数据付一次搬运费，还是每次查询都付一次跨网费」**——这个选择只由「查询频次 × 单次扫描量」与「延迟要求」决定，量级折算见 7.4。

**公开证据**：StarRocks 3.x 起提供存算分离形态（主文件 §1.4 演进历程）；Iceberg 表格式的设计目标之一就是让多个引擎共享同一份数据、把存储与计算解耦，其规范以快照与清单文件承载这一目标【公开，Apache Iceberg 表规范 v2，2022】。可自行核验的判据：**该引擎在没有任何本地数据时能否独立扩容**——能，说明存储与计算已解耦。

**失效条件**：当数据量增长到「引擎存储预算超过它带来的查询收益」时，给引擎加盘只是推迟问题；唯一的出路是把冷明细移走（回到对象存储、用外部表直查）——这正是本目录 §6 腾讯案例的约束来源。反过来，当某张表的查询频次低到「跨网络读一次也满足延迟要求」时，把它搬进引擎永远不划算。

### 7.4 成本结构对比（不是价格表，是成本函数）

五族的成本**随什么变量增长**：

```
年成本 ≈ 常驻计算（节点数 × 规格 × 8760h）              ← 自带存储族与联邦族都付
       + 引擎存储（数据量 × 副本数 × 单价 × 保留期）      ← 自带存储族独有
       + 冷读（对象存储扫描量 × 单价）                    ← 联邦 / 外表路线独有
       + 人力（表设计 + 物化视图维护 + 资源组 + 升级 + 值班）
```

**主导项与隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| StarRocks / Doris | 常驻计算 + 引擎存储（两者同量级） | 表设计一旦定错要重建表；物化视图的刷新链路要有人负责 |
| ClickHouse | 常驻计算 + 本地盘（副本数直接乘在盘上） | 无通用 join 对齐：join 需求会被迫改写成写入侧宽表 |
| Trino | 常驻计算（协调 + 工作节点，无请求时也在付费） | 每次查询的跨网读取；连接器的长期维护责任 |
| DuckDB | 使用它的进程的 CPU 与内存 | **没有**统一治理面：权限、审计、资源隔离要自己补 |
| Druid / Pinot | 常驻计算 + 段存储 | 查询模式超出预聚合范围时要重建段 |

**【推算】数量级示例**（推导链写全，便于换参数重算）：

- **一套 20 节点 8C16G 的常驻集群**：8 vCPU / 16 GiB 是 **1:2 的 vCPU:内存比**，对应云上的**计算优化型实例**（c5 / c6i 一类的 2xlarge 档），按需价 **$0.3–0.5/h 量级**【公开，AWS EC2 按需定价页 · 计算优化型族（c5/c6i.2xlarge 档），2024；实例族、规格比与价格随区域、代际与时间变动，可按 AWS 实例类型页与当前定价页自行核验】→ 年支出 ≈ 20 × $0.4/h × 8760h ≈ **$70k/年**【推算，推导链：20 节点 × $0.4/节点·小时 × 8760 小时】。
- **同一批数据留在对象存储里的费**：100 TB = 102 400 GB，按对象存储标准层 $0.023/GB-月推算 → 102 400 × $0.023 × 12 ≈ **$28k/年**【推算，单价见 AWS S3 定价页 2024，以当前定价页为准】。
- **把三项放在一起看**：**引擎自己的存储项不是上面那条 $28k**。$28k 是「同一份 100 TB 留在对象存储里」的账；一旦搬进自带存储的引擎，这一项按本条开头的成本函数放大：307 200 GB（= 102 400 GB × 3 副本）× $0.023/GB-月 × 12 ≈ **$85k/年**【推算，推导链：100 TB × 3 副本 = 300 TB = 307 200 GB，单价先沿用对象存储标准层以便同口径比较】；若引擎内每 GB 的月成本再按 **1.5 倍**计（本地 NVMe 实例通常比同 vCPU 的计算型实例贵，倍率按各云厂实例定价自行核验）【经验】，则到 **$127k/年**。也就是说，**在这组参数下引擎存储项（$85k–$127k/年）与 20 节点计算账（$70k/年）同量级、并且更大**——这是本节自己的成本函数给出的答案，而它与「把数据搬进引擎的主要代价不是存储费」这个常见直觉相反：**「搬进来」的代价里，最大的一项恰恰是被副本数与引擎内单价同时放大的存储，而不是导入链路**。结论只取量级：引擎内存储的单位成本与副本数都高于对象存储，这个差额要靠「查询次数 × 单次扫描量」省下来的计算时间来抵；抵不平，就该把冷数据留在对象存储、用外部表直查——这是 7.5 那条冷数据阈值与 7.6「冷热分层」组合的算术依据。
- **搬与不搬的分界怎么算**【推算】：设某张明细表 1 TB，每月被查约 100 次，布局做好后每次裁剪到 10 GB。则每月跨网络读 ≈ 100 × 10 GB = 1000 GB ≈ **1 TB**——与数据本身同量级。也就是说，「搬进来」省下的不是读的数据量，而是**跨网络读的延迟**与**重复解析远端文件的开销**。因此这条决策的正确判据是「跨网络读能否满足延迟要求」+「引擎存储预算是否付得起」，而不是「一共读了多少数据」。
- **人力项**【经验】：表设计与物化视图维护是**与数据量无关、与表数成正比**的固定项。常见的观察是：命中率长期只有个位数百分比的物化视图，是纯维护负担；表设计规范缺失时，重建表的工时会以「表数 × 人天」累积。

**主导项随场景切换，所以第一优先不是固定的**：

| 你的场景 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| 单表大宽表、并发高、查询固定 | 常驻计算 × 并发下的资源占用 | 先物化，再谈加节点 |
| 高频 upsert 的实时明细 | 合并能力（表现为常驻计算被后台任务吃掉一部分） | 先拆「明细 + 当前态」，再谈引擎 |
| 冷明细极大、访问稀疏 | 引擎存储 | 把冷明细移出引擎，改用外部表直查 |
| 数据散在多源、不能搬 | 跨网络读取的延迟与次数 | 先把下推与分区统计补上 |
| 个人分析、单机可容纳 | 使用者进程的 CPU | 用进程内库，别再养一套常驻集群 |

**主导项会随规模反转，所以「先省哪一项」不是固定的**：**因为**常驻计算是一条与请求量无关的固定项（20 节点 ≈ **$70k/年**【推算】，见上），**而**引擎存储随数据量与保留期线性上涨，**所以**小数据量阶段省下的是「别再养一套集群」，数据量涨上去之后省下的变成「别让冷数据留在引擎里」。这条反转给 7.5 的「冷数据访问频次」与「单机放得下」两条阈值提供了**成本侧**的依据；树上其余各条的判据不是成本，而是机制约束（布局边界、hash join 的物化要求、微批窗口、合规约束、预聚合的可枚举前提、向量检索与结构化过滤的执行顺序、预计算的经济性），逐条见 7.5 的阈值依据。

### 7.5 决策树（每个分支都要有阈值依据）

```
你的数据形态、更新语义、查询形态是什么？
├─ 单表宽表扫描 + 聚合，写入以追加为主（日志 / 事件 / 埋点），并发高
│    → ClickHouse 一族（单机优先的列存引擎）
│      前置判据：过滤列是否落在排序键上
├─ 多表 join + 需要 upsert 或部分列更新 + 写入到可查要秒级
│    → StarRocks / Doris 一族（自带存储的分布式列存 MPP）
│      前置判据：最大的那张 join 的构建侧能否被对齐分布或放进内存
├─ 数据散在多个源、不能搬动，需要统一查询入口
│    → Trino（联邦查询引擎；同类主题见 [13-query-engine §7](../13-query-engine/13-query-engine-section-7-sec7.md)）
│      代价：每次查询付一次跨网络读取
├─ 数据在本地文件、单机放得下，使用者是个人或单个进程
│    → DuckDB（进程内库）
│      代价：没有统一权限、审计与资源隔离
├─ 实时大屏 / 监控类查询：事件流、时间窗与维度组合都可枚举
│    → Druid / Pinot 一族（写入侧预聚合）
│      代价：查询模式超出预聚合范围时要重建段
├─ 冷明细极大而热数据要求低延迟
│    → 冷热分层：冷明细留湖上外部表直查，热维表放引擎内
│      判据：冷数据的访问频次是否低到「跨网络读也满足延迟要求」
├─ AI 应用需要在同一查询里做结构化过滤 + 向量检索
│    → 引擎内向量索引（StarRocks 3.x 起）或外挂向量库（LanceDB 一类）
│      判据：检索前是否主要靠结构化列收窄候选集
└─ 查询模式完全固定、结果可复用
     → 物化视图 + 自动改写（先把「重复计算」消掉，再谈加机器）
```

**阈值依据**（与树上每个判断节点一一对应）：

- **「过滤列是否落在排序键上」**（第一个分支的前置判据）：这是**结构判据**而非数值阈值，由 7.3.1 的机制直接导出——OLAP 的扫描边界由排序键与分区给出，过滤列不在其上时裁剪能力归零，此时换引擎不会有帮助。判定方法：看查询计划里扫描的输入行数是否随过滤条件收窄。
- **「最大的那张 join 的构建侧能否被对齐分布或放进内存」**（第二个分支的前置判据）：由 7.3.3 的「hash join 必须先物化构建侧」导出，**与总数据量无关**。工程近似：单机路线要求构建侧显著小于可用内存、超出部分能落本地盘；分布式路线要求两张表能按连接键对齐分桶，否则退化为 shuffle join，网络代价由构建侧大小决定【经验】。超过这条线不是变慢，是失败。
- **「写入到可查要秒级」**：由 7.3.2 的微批与合并机制导出。微批意味着一个攒批窗口，**可见性延迟的下界就是窗口长度**；秒级要求把窗口压到亚秒–秒级，这会提高写入频次与合并压力，进而吃掉一部分常驻计算。所以这条阈值同时决定「要不要主键模型」与「要不要为后台合并预留资源」，不是单纯的功能勾选。
- **「多个源、不能搬动」**：不是技术阈值而是合规与成本约束——数据出域需审批、或外流按流量计价时，「不搬」从优化目标变成硬约束【经验】；此时联邦路线的常驻成本与跨网代价是必须付的。
- **「单机放得下」**：由 7.3.3 的构建侧约束导出——单机路线的可用性由**峰值工作集**（最大一份 join 构建侧 + 聚合状态）是否放得进内存与本地盘决定，不由总数据量决定【经验】。总数据量超过单机、但单次查询工作集很小的场景（例如只查一个分区的明细）仍然可以留在单机。
- **「实时大屏、事件流、时间窗固定」**（第五个分支）：由 7.3.3 的聚合机制导出——写入侧预聚合把「每次查询都要算的聚合」变成「写入时算一次」，因此它在「查询形态可枚举 + 时间窗固定 + 写入量大」时收益最大；反过来，一旦查询形态超出预聚合的维度组合，就要重建段。这是**约束判据**（成立条件是「可枚举」，不是一个数值）；它的成本侧依据是那条预聚合与段生成的链路是一个固定项，要有人维护重建流程【经验】。
- **「冷数据的访问频次是否低到跨网络读也满足延迟要求」**：由 7.4 的推算导出。搬与不搬的分界不在读的数据量（示例中两者同为 1 TB/月量级），而在**跨网络读的延迟是否满足要求**与**引擎存储预算是否付得起**。
- **「检索前是否主要靠结构化列收窄候选集」**：由 7.3.1 的布局机制导出——向量检索是「先算距离再排序」，结构化过滤是「先缩小范围再算距离」，前者要求全量参与、后者能借分区与排序键剪掉大部分候选。**候选集在检索前能被结构化条件收窄到很小比例时，把向量索引放在已有布局的引擎内收益最大；纯向量检索（没有结构化条件）则外挂向量库同样可行**【经验】。
- **「查询模式完全固定、结果可复用」**：这一条是**约束而非阈值**——当查询形态稳定到「可以离线算好」时，物化一次的成本必然低于每次重算，否则加机器也改变不了「本来只需算一次」这个结构问题（机制见 7.3.3）。判据是「同一份聚合结果在一天里被不重复地计算了多少次」。

**把决策树展开成执行顺序**（同一棵树，按时间轴读）：

1. **第 0 步 · 先量三个数**：查询实际读取量与表总量之比（布局是否有效）、最大一份 join 的构建侧大小（单机能不能装下）、写入到可查的延迟要求（微批窗口取多大）。这三项分别决定判据 4、判据 3、判据 5。
2. **第 1 阶段 · 只动表设计**：调整分区键、排序键、编码方式。不改引擎、不改 SQL，却常常是扫描量下降幅度最大的一步——因为查询能跳过的数据块由布局决定。
3. **第 2 阶段 · 再动物化**：把高频且形态固定的聚合物化，并让优化器自动改写。验收标准是「同一份聚合结果被不重复计算的次数」下降。
4. **第 3 阶段 · 最后才动引擎形态**：换引擎、换存储归属、换冷热分层。这一步会同时改变导入链路、权限模型与运维方式，是唯一不可快速回滚的一步（迁移代价见 7.7）。
5. **持续 · 把两个指标写进看板**：查询实际读取量与表总量之比、以及未合并版本数与后台合并任务的队列长度。缺了后者，「写入没变多，为什么查询越来越慢」这个问题永远不会被回答。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单表大宽表、追加写入、高并发看板 | ClickHouse 一族 | StarRocks（宽表形态） | 用联邦引擎：每次全量重算，常驻成本随并发变紧 |
| 多表 join + upsert + 秒级可见 | StarRocks / Doris | ClickHouse + 写入侧宽表 | 只靠宽表：字段随查询需求膨胀，冗余持续增长 |
| 跨源即席、数据不能搬 | Trino | 预先落一份带统计的表 | 强行把数据搬进引擎：先要过合规这一关 |
| Notebook / 本地分析 | DuckDB | Trino（小集群） | 为一次性分析养一套常驻集群 |
| 实时大屏、事件流、时间窗固定 | Druid / Pinot | StarRocks + 物化视图 | 用通用 MPP：为固定查询付了通用能力的钱 |
| 冷明细极大、热数据要低延迟 | 冷热分层（湖上外部表 + 引擎内热表） | 全部导入引擎 | 全部导入：冷数据占用的存储预算长期大于它带来的收益 |
| 查询模式固定、结果可复用 | 物化视图 + 自动改写 | 手工汇总表 | 靠人改写查询：只有懂优化的人受益 |
| AI 取数与向量检索 | 引擎内向量索引 + 统一 SQL 出口 | 外挂向量库 + 应用侧合并 | 直连多个引擎：Agent 要面对多套方言与多套权限 |

每条说明职责边界与运维代价：

1. **StarRocks + Iceberg 外表**（适用 Lakehouse + 实时查询）：引擎负责热数据的存储与计算，Iceberg 负责湖上冷明细的权威副本。边界是**热数据归引擎、冷数据归湖**。运维代价：多一条「湖 → 引擎」的同步链路，必须明确哪一端是权威——两端都写会立刻产生口径分叉。
2. **ClickHouse + StarRocks**（适用分层查询）：ClickHouse 存明细、承担单表高并发聚合；StarRocks 存聚合结果、承担多表 join 与对外统一入口。边界是**明细归前者、聚合与 join 归后者**。运维代价：多一条明细同步链路；同一条口径在两侧各有一份实现，必须指定一侧为准。
3. **DuckDB + StarRocks**（适用开发 + 生产）：DuckDB 做本地原型与一次性分析，验证通过的逻辑再落到 StarRocks 做生产。边界是**原型归本地、生产归集群**。运维代价：两处的方言与函数覆盖不同，「原型能跑、生产语义不同」是这套组合最常见的坑。
4. **OLAP + 向量库（LanceDB 一类）+ LLM**（适用 AI 应用）：OLAP 负责结构化过滤与聚合，向量库负责近似最近邻检索，LLM 负责生成查询与总结。边界是**结构化条件归 OLAP、向量相似度归向量库、编排归应用**。运维代价：候选集要在应用侧合并，多一次跨系统调用与一次一致性风险（两边的数据不是同一时刻的快照）。

**除组合本身之外，还有两条必须随组合一起上线的支撑链路**（它们不是可选项，而是上面四个组合能否成立的先决条件）：

- **存量语法兼容层 + 新引擎**（来自本目录 §6 的湖仓一体案例）：新引擎兼容既有数仓的查询语法，使既有作业基本平移。边界是**引擎负责性能、兼容层负责降低迁移成本**。运维代价：兼容层本身是一个长期维护面，且会掩盖方言差异，使「以后要不要去掉它」这个问题年年被推迟。
- **统计信息与元数据管道**：把分区、列统计、排序键变更纳入一条独立的上线动作。边界是**引擎负责执行、元数据管道负责让优化器有的可估**。运维代价：这是一条**没有直接产出、却决定其他所有优化是否生效**的链路，最容易被裁掉，裁掉之后表现为「换了引擎也没变快」。

**组合的共同原则**：每个组合都要能回答「哪一件负责布局、哪一件负责计算、哪一件负责权威口径」。**因为**分区与排序键一旦定死就不可事后修补（7.3.1），**所以**组合里必须有一个**唯一负责表设计的角色**——它不是引擎，是工程约定；缺了这个角色，多引擎组合会退化成「同一份逻辑在几处各写一遍」，而这正是口径分叉的机制来源。

### 7.7 选错的代价与迁移成本

**反模式：把布局问题当成算力或调参问题** —— 症状有两种、根因是同一个：用 ClickHouse 一类单表优先的引擎承载大量维度 join，团队不断加节点而延迟仍不稳定，于是开始怀疑容量；或者查得慢就去过滤列上加索引，加完几乎没变化 → **因为**列存的扫描边界由分区与排序键在写入时定死，引擎能动的只剩「跳过不匹配的数据块」，**又因为** hash join 必须先物化构建侧、而这类引擎没有为「按连接键对齐分布」设计存储层，**所以**加索引只能改变跳过的效率、加节点只能加并发，两者都动不了那条边界，join 的代价由构建侧大小与广播次数决定（机制见 7.3.1、7.3.3）→ **正确做法**：先量一条数——查询实际读取的行数与表总量的比值；比值接近 1 说明布局不匹配，该做的是重建表换排序键或物化，而不是加索引；join 侧则把常用 join 前移到写入侧物化成宽表，让查询退回单表扫描；若 join 模式本身高频变动，换到自带存储的分布式 MPP 族，因为它的分布键就是为这件事设计的。

**反模式：用 OLAP 引擎承接点查与事务型写入** —— 把用户端的实时读写接口直接打到 OLAP 引擎上，随后出现「写入频繁时查询变慢」「偶发读出旧值」 → **因为** OLAP 的更新是「追加版本 + 后台合并」，点查要读前缀索引，两者对布局的要求相反，**所以**同一张表同时服务高频点查与批量扫描时，两类负载会互相挤占（机制见 7.3.1、7.3.2）→ **正确做法**：点查留给 OLTP 或 KV 层，OLAP 只承接分析型读；确需 OLAP 承接点查时，把「当前态」与「明细」拆成两张表，并明确查询读到的是哪个版本。

**反模式：把进程内库当共享数仓用** —— DuckDB 试用效果极好，于是推广给全组多人并发，随后出现偶发失败、内存打满、同一份数据每人存一份 → **因为**进程内库的形态前提是**单进程、单用户、数据在本地**，它没有资源隔离与并发调度这两层（不是实现不好，而是形态里不含这两层）→ **正确做法**：进程内库用于个人分析与服务内嵌；多人共享必须换到集群引擎，并把数据放到共享存储而不是各自的本地目录。

**换成另一条路线要动什么**：

| 迁移方向 | 数据迁移 | 查询 / SQL 改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 同族另一产品（Doris ↔ StarRocks） | 小：协议与语法接近 | 小：方言与专有函数核对 | 小：架构同族 | 差异点核对 | 1–3 人月 |
| 单表优先引擎 → 分布式 MPP | 中：需按分布键重排 | 中：join 写法与分桶键要对齐 | 中：新建集群 + 导入链路 | 分布式执行、资源组 | 3–6 人月 |
| 全部导入 → 冷热分层 | 中：冷数据要移出并落成湖上表 | 中：外部表与内表联合查询 | 中：分区与统计要补齐 | 外表查询与延迟预期 | 2–5 人月 |
| 联邦引擎 → 物化 + 引擎内表 | 中：物化一份结果集 | 大：查询要按物化粒度改写 | 中：新增刷新链路 | 物化粒度与刷新策略 | 3–9 人月 |
| 无主键模型 → 主键 / 唯一键模型 | 大：表要重建并重灌 | 小：SQL 基本不变 | 中：后台合并资源要预留 | 合并监控与版本排查 | 3–8 人月 |

> 量级按「一个熟悉本系统的 3–5 人小组」估算【经验】。按上表区间中值排序，最贵的两条是「联邦引擎 → 物化 + 引擎内表」（中值 6.0 人月）与「无主键模型 → 主键 / 唯一键模型」（中值 5.5 人月）：它们的共同点是**都要在引擎内重新落一份数据**——前者把查询结果物化成引擎内表，后者把表重建并重灌——因此都不是改 SQL 或调参能回退的。而真正「写入时就锁死、事后只能靠重建表改」的是**布局与更新语义**这两样，上表里落在这一机制上的方向是「无主键模型 → 主键 / 唯一键模型」，以及同类方向（重建表以改排序键 / 分区键）：它们动的是建表那一刻定下的东西（机制见 7.3.1、7.3.2）。这也解释了为什么「先把查询模式量清楚再建表」比「先上一套引擎」更值钱。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 单表宽表、追加写入、高并发看板 | 单机优先的列存引擎 | 排序键即扫描边界，聚合搬运量与分组数成正比 |
| 多表 join + upsert + 秒级可见 | 自带存储的分布式 MPP | 分布键可按连接键对齐；主键模型把 upsert 变成版本合并 |
| 跨源、数据不能搬 | 联邦查询引擎 | 它不拥有存储，因此冷数据可以完全不进来 |
| 本地文件、个人分析 | 进程内库 | 进程边界为 0，无网络与序列化开销，且无常驻成本 |
| 事件流、时间窗固定、大屏 | 写入侧预聚合 | 把聚合前移到写入侧，查询只做段内扫描 |
| 冷明细大、热数据要快 | 冷热分层 | 存储成本按保留期线性上涨，而查询集中在最近一段时间 |
| 查询慢 | 先看扫描行数占表的比例 | 布局定死之后，加索引改变不了扫描边界 |
| 写入频繁而查询越来越慢 | 先查未合并版本数与合并任务 | upsert 的实时性上限由合并吞吐决定，不由写入吞吐决定 |
| 加节点对某条聚合查询没用 | 先做本地预聚合或物化 | 搬运量与分组数相关，与并行度无关 |
| AI 应用要同时做过滤与向量检索 | 先看候选集能否被结构化条件收窄 | 收窄发生在算距离之前，才能借到分区与排序键的裁剪 |
| 任何引擎迁移之前 | 先量「扫描量 / 表总量」与「未合并版本数」 | 迁移解决不了的，多半是布局与更新语义的问题 |

> 本节小结：本节所比的五族候选之间**唯一真正起决定作用的差异**是——**布局在写入时定死，以及存储归谁**。前者决定了「扫描多少、加索引有没有用、upsert 的实时性上限在哪」；后者决定了成本函数里有没有「第二份数据」与「跨网络读取」这两项。其余所有维度都是这两条的**表现形式**：所谓「Join 性能」就是「能不能按连接键对齐分布」，所谓「实时写入」就是「后台合并跟不跟得上」，所谓「内嵌能力」在需要统一治理的组织里则是一张减分项。选型的正确顺序是：**先量扫描比例（是不是布局的问题）→ 再查未合并版本与合并吞吐（是不是更新语义的问题）→ 最后才动引擎形态（这一步不可快速回滚）**。
>
> 💡 **思考锚点**：在你最慢的那条查询上量两个数——「实际扫描行数 ÷ 表总量」的比值，以及那张表当前的未合并版本数；比值接近 1 指向布局问题，版本积压指向更新语义。那么还没量这两个数，你急着换掉的那台引擎，治的究竟是布局、更新语义，还是第三样东西？
