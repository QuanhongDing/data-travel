## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本主题的既有卡点写在主文件 [§1.2](11-olap-engine.md)：业务库被分析查询拖垮、传统数仓分钟级延迟、交互式体验差、实时能力弱；AI 时代又加了四条新诉求——实时特征查询、向量检索集成、Agent 即席查询、自然语言查询。**前沿之所以是前沿，是因为既有引擎在这四处卡住了，而四条新诉求里只有两条真的动了执行层（向量检索集成与 Agent 即席查询各自的引擎侧实现）。** 自然语言查询改的是"谁在写 SQL"（执行层不变，卡点在口径）；引擎内 AI 函数与相似度检索改的是**执行计划里多了一类算子**（前者的输出非确定、后者是近似结果）；自治优化、云原生、流批融合、内嵌引擎四条**与 AI 没有因果关系**——它们改的是控制面、存储接口、写路径与执行架构，把它们记成"AI 趋势"会让真正缺的那一环（可回滚的自动化边界）一直缺着。

本节用 L1 / L2 / L3 三级区分，判据必须是可核验的三条：

- **L1 生产可用**：① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定。**三条全中才算 L1**，可以排进路线图。
- **L2 可试点**：已可用但接口 / 生态未稳，或仅有厂商自有案例，或只在小规模被验证。可以做 PoC，**不要作为核心依赖**。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。记录，**不要在架构里预留假设**。

三条判据各挡住一类误判：①挡住"把路线图里的条目写成语态完成的既成事实"，②挡住"把引擎厂商自己发布的对比测试当行业现状"，③挡住"把某个版本的新算子当成稳定接口"。"感觉上大家都在用"不算判据——它在选型评审会上无法被复核。

**判据声明（本节不对 L1 判据做任何修正）**：上面三级与三条判据沿用到底，不替换、不放宽。本主题有一处特别诱人放宽的地方，先把话说死：**OLAP 是全书写得最热闹、也最容易用"评测"冒充"实践"的主题**。这个领域能公开检索到的第三方材料，绝大多数是**基准与评测**——标准基准（TPC-H / TPC-DS 一类）、学术基准（Text-to-SQL 方向的 Spider / BIRD 一类）、以及各家自建的对比测试；评测回答的是"引擎能力在一个受控 workload 下表现如何"，**不是"某个组织在生产里怎么用它"**，而且这类评测的作者常常是某个引擎的厂商或其赞助方（§5.4 单独说明了三类材料的用法）。本节的做法是：**够不到第②条的行一律降到 L2，并在判据格里写明它卡在哪一条**，而不是把"有第三方评测"改写成"有第三方生产案例"。结果是**下表没有任何一行达到 L1**——包括那几条非 AI 的既有能力行。L2 不等于"不好"，也不等于"不能现在做"，只等于"公开证据到不了 L1"；真正需要警惕的是把 L2 当 L1 排进选型结论。

写这一节时最容易混的五件事，先在这里分开：

- **产品名 vs 能力名**：同一个能力在不同平台上的命名并不通用——"在 SQL 里调用模型"这类函数，各家函数名、参数与超时语义都不同，**不要把某一家的函数名当成通用名**（§5.2.3 给了判定入口）。
- **已发布版本 vs 路线图**：判断某个引擎是否真的支持某能力（向量索引、存算分离、自动物化改写），只看一处——**该版本的 release note 或官方文档里有没有对应条目**；benchmark 博客、大会演讲、生态伙伴转述都不算。
- **单机 vs 多机**："内嵌引擎"与"分布式 OLAP"是两类系统；判断某个版本是否真的支持多机，**看它的 release note 里有没有独立的多机执行组件**，而不是看它跑出了多快的单机成绩。
- **确定性优化 vs 统计预测**：自动物化改写、自适应并行度、自动统计信息、后台 compaction，都是**按统计信息做的确定性动作**，不需要模型；把它们算进"自治 OLAP"是本主题最普遍的一处混淆（§5.2.4）。
- **论文里的原型 vs 产品里的实现**：本节提到的多数提法（自然语言查数、自动调优、引擎内模型调用）在论文与开源原型里都能找到；**判定方法**：看该能力的官方文档里有没有"配额 / 超时 / 计量"三项——有这三项的才算产品化条目，只有一段演示的还不是。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**——改变了成本函数、改变了接口边界、把人工判断换成统计判断，还是只换了个前端？本主题的答案分四类：**一条改变了接口边界**（自然语言查询把一类不写 SQL 的消费者接进链路，判定点随之移到语义层）、**两条改掉了引擎最稳的性质**（相似度检索的结果不可复现、模型调用按外部服务计费，"同一查询同一结果"不再成立）、**一条把人工判断换成统计判断**（自治优化里真正成立的那半数）、**其余方向与 AI 没有因果关系**（存算分离、流批融合、内嵌引擎的边界问题）。这个分类不是文字游戏：**只换前端的方向接入后仍要补口径与权限**，而改掉性质的方向会让你发现真正的缺口在成本模型与回滚边界，不在模型侧。

| --- | :---: | :--- | :--- |
| 列存 + 向量化 + CBO 的既有执行能力（非 AI 的基线） | **L2** | ①在所用引擎的官方文档与 release note 里逐项可核验（列存、向量化执行、CBO、Zone Map、物化视图）；③ SQL 接口多年未变。**②核不到**——本主题公开的第三方材料以评测为主，不是生产案例（§5.4） | 直接做：它是所有 AI 方向的执行底座，且与 AI 无因果关系 |

本节**不**再评估的三件事，都在其他章节里：引擎选型与建表范式（见 [§3](11-olap-engine-section-3-sec3.md)、[§7](11-olap-engine-section-7-sec7.md)）、工程步骤与监控口径（见 [§4](11-olap-engine-section-4-sec4.md)）、真实落地取舍（见 [§6](11-olap-engine-section-6-sec6.md)）。本节只回答一个问题：**在这些既有能力之上，AI 又改了哪一处机制，改了以后值不值得现在就投。**

**这三级的排法直接决定选型的顺序**：

- **先做的两件（第 1、4 行）**：把执行层基线（列存 / 向量化 / CBO / 物化视图）与引擎侧的确定性自动化开起来。它们排在所有 AI 方向之前，因为**后面每一条方向的收益都建立在"引擎能稳定地把普通查询跑好"这件事上**；这两件与 AI 无关，动作可复现，且不会引入新故障形态。
- **AI 方向里的三条 L2 先做 PoC，并先测四个数**：自然语言查询的"口径未登记问题占比"；向量检索的"过滤下推后候选集下降比例"与"召回率-延迟曲线"；引擎内模型调用的"每行 token 成本上限"。这四个数拿不出来，这三条就停在原地。
- **L3 不排进排期**：第 5、7、13 行（LLM 优化建议、自治 OLAP、"OLAP + AI 默认集成"范式断言），加上第 2、8、12 行各自的 L3 子项（复杂真实 schema 上的生产可用、"统一检索"范式、内嵌引擎的分布式扩展），都属于"等信号"。它们的共同前提（动作可回滚、建议可校验、接口可移植）比选哪家模型重要得多。
- **回填机制**：每次选型复查时回填一次级别；某个 L2 若一年内仍拿不出自己组织里的实测数字（谁在用、用了多久、失败过几次），降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次"查询变聪明了"，都对应一处被换掉的性质。

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 自然语言查询 | 写 SQL 的人换成模型，**口径必须从人的记忆搬进机器** | **接口边界**（入口换了，判定点在语义层） |
| §5.2.2 向量检索融合 | 执行计划里多了一类**近似算子** | **结果的确定性**（同一查询不再保证同一结果） |
| §5.2.3 引擎内 AI / LLM 函数 | 执行计划里多了一类**按外部计费的算子** | **成本模型**（CBO 的代价公式看不见这一项） |
| §5.2.4 自治优化与云原生 / 流批 / 内嵌 | 收益全部来自既有机制，没有一条来自模型 | **多数与 AI 无因果关系** |

读法建议：时间只够读一节就读 §5.2.3——它是本主题里唯一一条同时改掉"确定性"和"成本模型"两条性质的方向，也最容易在没算清成本的情况下被上线。

每一节末尾的「证据与来源」沿用同一套档位：【公开】指有可核验的出处（官方文档 / 论文 / 公开材料），【推算】指能写出推导链的换算，【经验】指区间估计。**本节不给版本号**：凡涉及"某产品支持某特性"的地方，一律改写成判定入口（查哪一版 release note 或哪份官方文档）。

#### 5.2.1 自然语言查询：变化的是"谁在写 SQL"，不变的是"查询必须正确"

- **旧做法与它的卡点**：取数入口是人写 SQL——业务方描述问题、分析师翻译成表和字段。卡点在**翻译成本**：主文件 [§1.2](11-olap-engine.md) 把它写成"交互式差、分析师等待时间长"，AI 时代诉求里又加了"自然语言查询"。注意这个卡点**从来不在执行层**：引擎跑一条 SQL 的能力与"这条 SQL 是不是问的那件事"无关。
- **AI 改变了什么机制**：**入口的生产者换了**，但真正的机制点在于：自然语言到 SQL 之间缺的不是语法转换，而是**口径**这一中间层——表名可以猜，口径不能猜，猜错的 SQL 语法完全正确。所以这条方向的机制应写成"**把写 SQL 的人换成模型，因此必须把口径从人的记忆里搬到机器可读的地方**"，而不是"加一个 NL2SQL 模块"。
- **由此得到的**：**因为 SQL 的语法正确性由引擎保证，而口径正确性没有人保证，所以自然语言查询的真正收益不在"少写 SQL"，而在"有没有机器可读的语义层"**——收益的兑现条件是语义层覆盖率，不是模型准确率。同一件事在不同章节有不同名字：本章叫"自然语言查询"（[§1.2](11-olap-engine.md)），指标侧叫"Text-to-Metric / 指标语义层"（[../../04-data-assetization/10-metric-platform/10-metric-platform.md](../../04-data-assetization/10-metric-platform/10-metric-platform.md)），跨源查询侧叫"NL → SQL → 跨源查询"（[../13-query-engine](../13-query-engine/13-query-engine.md)）；名字不同，缺的是同一层。

| 环节 | 谁保证正确性 | 错在哪一层时，症状是什么 |
| --- | --- | --- |
| 表 / 字段选择 | 目录与元数据（[../../04-data-assetization/08-data-catalog/08-data-catalog.md](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 选了停用表或重复表：结果存在，但不该用 |
| 口径 | 指标平台 / 语义层 | **静默错误**：SQL 语法正确、数字可信，含义错 |
| 执行 | OLAP 引擎（本主题） | 语法或权限错误：会报错，最容易发现 |
| 权限 | 引擎 + 策略下推 | 越权或误拒：前者是泄露，后者是"查不出来" |

- **由此付出的**：**其一，错误更贵**——人写 SQL 时的错误往往伴随"这人知道自己在猜"，而模型给出的答案是流畅的，**发现错误的成本取代写作成本成为主要成本**；报告里的数字没人会怀疑，这正是主文件 §1.2 里"业务库崩溃 / 交互式差"之外的新风险。**其二，评测口径不可移植**：学术基准用给定的 schema 与问题集，不含"口径从哪来"这一层，所以基准分数不能预测你环境里的表现（§5.4 会把这一点写清）。**其三，压力从引擎侧转到治理侧**：引擎要做的只是"跑得快 + 权限可下推"，剩下的缺口在语义层——**这不是引擎能力问题，换引擎解决不了**。
- **证据与来源**：【公开】Text-to-SQL 方向的学术基准与研究（Spider 一类，可按论文题名检索；BIRD 一类大规模数据库接地基准，年份与会议以论文页面为准）；各家云数仓 / 湖仓平台的自然语言查询是正式产品条目（以官方文档为准）。**②核不到**——这些是**评测**与厂商自有案例，不是第三方（非厂商）生产案例。【经验】在真实企业环境里，自然语言查询的可用性主要受语义层覆盖率限制，而不是受模型能力限制：**核心指标口径未登记齐全时，命中率的高低没有意义**——这是一条方向性判断，量化区间取决于各组织的口径治理水平，本节不给数字。
- **成熟度**：**L2**（§5.1 表第 2 行）：①成立、②核不到、③不成立（语义层接口无通行做法）；**其中"在复杂真实 schema 上达到生产可用"这一判断属 L3**。
- **判定方法**：抽 20 个业务常问的问题，先不看模型的回答，**先问"这 20 个问题的口径有没有书面定义"**；有定义的才谈准确率，没定义的先补口径。第二问是：换一批同义问法再问一次，看答案是否稳定——不稳定说明它靠的是措辞而非口径。
- **什么时候值得做**：核心指标已有书面口径，且业务方的提问集中在同一批指标上（而不是无限发散）时。
- **什么时候不值得做**：口径散在各人手里、指标口径本身还有争议时——此时自然语言入口会把口径争议放大成"数字不一致"，比没有入口更糟。
- **失效的早期信号**：把"生成的 SQL 能跑通"当成成功率；口径未登记的问题无人统计；同一个问题换一批问法得到不同答案却没人发现。
- **与相邻章节的关系**：语义层缺口的补法在指标侧（[../../04-data-assetization/10-metric-platform/10-metric-platform.md](../../04-data-assetization/10-metric-platform/10-metric-platform.md)），资产可见性的补法在目录侧（[../../04-data-assetization/08-data-catalog/08-data-catalog.md](../../04-data-assetization/08-data-catalog/08-data-catalog.md)）；本节只负责说清"引擎这一侧做不到什么"。
- **它与查询性能工作的关系**：自然语言查询不会降低引擎性能优化的价值——入口多了一类消费者，慢查询仍然要按计划与数据布局去治；指望"换成自然语言就绕过了性能问题"是这条方向最常见的误读。
- **口径争议的归属**：一旦入口开放，口径争议会立刻变成"数字不一致"的投诉并落到引擎团队头上；正确做法是在入口开放前就约定"口径归语义层、性能归引擎"的归属，并把这条写进服务目录。

#### 5.2.2 OLAP + 向量检索融合：真正的变化是"两种检索进了同一个执行计划"

- **旧做法与它的卡点**：结构化过滤与相似度检索分在两个系统（[../../04-data-assetization/04-hybrid-search/04-hybrid-search.md](../../04-data-assetization/04-hybrid-search/04-hybrid-search.md) 把两者的融合写成"混合检索"）。卡点是**过滤与召回的顺序**：先把候选搬到应用层再过滤，传输与延迟随候选集线性增长；先过滤再召回，则要求过滤条件能下推到索引侧。
- **AI 改变了什么机制**：**执行计划里多了一类算子——相似度排序。** 它与既有算子的关键差别是：**输出不是精确集合，而是"近似 + 可调召回率"**，所以行数 / NDV 这类统计信息对它不适用；同时它的代价取决于索引结构、量化方式与召回目标，而这三样都不在 CBO 已有的代价公式里（主文件 §2.2 的 Cost = α×I/O + β×CPU + γ×Network 没有为"近似算子的质量"留位置）。
- **由此得到的**：**因为过滤与召回进了同一个计划，"先按结构过滤、再在候选集内做相似度排序"可以被下推到数据侧**，避免全量候选出网；这是把向量检索放进 OLAP 的唯一机制性收益，也是它区别于"应用层拼两个结果"的地方。两级结构可以画成一句话：

```text
结构化过滤（精确） → 候选集（可比已知数量级） → 向量召回（近似，带召回率目标）→ 精排
  ────────────────────────────────────────────────
  收益点：把候选集压下去，再花算力做相似度
  判断点：过滤下推比例、召回率-延迟曲线；两个数都给不出，就不该上线
```

这条方向的判定点必须写在两处：**过滤发生在索引侧还是算子内**。写错的代价不是报错，而是把两类问题混成一个——**过滤没下推**表现为候选集变大、延迟上升（代价问题），**召回不达标**表现为结果不对（质量问题），两者症状相似，必须分开度量（§5.3 表第 3 行）。"判定落在哪一层"这件事在别的主题里也出现过：RAG 链路的合规判定要把判定点从一个变成四个（[../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-5-ai.md](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-5-ai.md)），数据 API 网关要先把鉴权主体定下来（[../../04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-5-ai.md](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-5-ai.md)）——**判定位置放错，比判定规则写错更难发现**。

- **由此付出的**：**其一，结果不再可复现**——同一 SQL 两次执行可能返回不同顺序（索引构建与量化带来的近似），这对报表与对账是新问题，而"同一查询同一结果"是 OLAP 过去最稳的性质。**其二，两套质量指标互不适用**：CBO 按行数估代价，相似度算子要按召回率目标 / 候选数人工配置，二者没有统一口径。**其三，性能声称必须带条件**：不谈数据量、维度、过滤选择性、召回率目标与硬件，"毫秒级向量检索"没有信息量（§5.5）。**其四，多了一套索引要维护**：向量索引的构建与重建会与 compaction、物化刷新抢资源，需要单独排期。
- **证据与来源**：【公开】多家引擎把向量索引作为正式功能条目（可按引擎名 +「vector index」检索核验）；召回质量的可比材料来自学术基准（近似最近邻方向），其作者与赞助方常与某个实现相关。**②核不到**——本节举不出第三方（非厂商）公开生产案例。
- **成熟度**：**L2**（§5.1 表第 3 行）：①成立、③不成立（索引类型 / 距离度量 / 参数不可移植）、②核不到。**试点门槛**：能拿出"过滤下推后候选集下降比例"与"召回率-延迟曲线"这两个数，再谈上线；拿不出就只能用于非核心场景。
- **什么时候值得做**：检索条件里**同时**有硬性结构化约束（时间、租户、类目）与语义相似需求，且约束能把候选集压下一个数量级以上时。
- **什么时候不值得做**：候选集本来就很小（纯相似度检索），或过滤条件无法下推时——这时把 OLAP 拉进来只会多一层运维成本。
- **失效的早期信号**：只用一条延迟指标衡量整条链路；召回质量与过滤效果混在一个面板里；索引重建与 compaction 抢资源却没人知道。
- **上线前要能回答的三个问题**：过滤后候选集是多少（与不下推相比）？召回率目标是多少、用什么集合测的？索引重建期间查询退化的幅度是多少？
- **与混合检索章节的分工**：检索策略（关键词与向量的融合、重排）在 [../../04-data-assetization/04-hybrid-search/04-hybrid-search.md](../../04-data-assetization/04-hybrid-search/04-hybrid-search.md)，本节只负责"过滤能不能下推、近似算子怎么进计划"这两件引擎侧的事。
- **一个常被忽略的运维成本**：向量索引需要与数据更新同步重建，而重建期间的召回质量会下降；这段时间的查询结果不能与稳定期混在同一份报表里比较。

#### 5.2.3 引擎内 AI / LLM 函数：把模型调用变成执行计划里的一个算子

- **旧做法与它的卡点**：模型调用发生在引擎外——把数据导出、调用、写回。卡点是**数据搬运与结果对齐**：一次要处理百万行时，"导出—调用—写回"的工程量与延迟都由应用侧承担（主文件 §1.2 的"AI 时代新诉求"里"Agent 即席查询"就卡在这里）。
- **AI 改变了什么机制**：**模型调用被下沉为一个 SQL 算子**，于是它获得两个既有能力：**能进执行计划（并行、分批）**、**能与其它算子组合（对结果做过滤聚合）**。它不是"引擎变聪明了"，而是"引擎的执行框架里多了一个按外部服务计费的算子"。
- **由此得到的**：**因为它是一个算子，所以"对表里每一行调用模型"变成一条 SQL**——这是本方向唯一的机制性收益，其余是接口便利。适用面也因此被限定：**它擅长长尾、低频、结果可被人工复核的路径，不是高频聚合**。
- **由此付出的**：**其一，SQL 从确定性变成非确定**——同一查询两次结果可能不同，这直接破坏报表与对账的可复现性，而主文件 §2.1 的 CBO 与物化视图都建立在"同一查询同一结果"上（物化视图尤其明显：预计算结果的正确性依赖确定性）。**其二，成本模型失效**——CBO 按 I/O + CPU + 网络估代价，模型调用按 token 计费、与处理行数线性相关，引擎的代价模型看不见这一项，成本会绕过资源管理（[../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md) 的分摊问题在这里会露出来）。**其三，延迟与失败语义不同**——行级调用意味着整条查询的耗时由外部服务决定，一次限流或超时就会打断整条 SQL，而 SQL 原本没有"部分失败"的概念。**其四，数据出域**——被调用的是外部服务，数据边界与合规判定必须在这一层重新做一次。**其五，命名极易张冠李戴**：各平台这类函数的命名、参数、超时与配额语义都不同，**不要把某一家的函数名当成通用名**。
- **证据与来源**：【公开】"在 SQL 中调用模型"在主流云数仓与湖仓平台里是文档化的正式功能（判定入口：查该产品官方文档里的函数签名、超时与配额说明）；**②只有厂商自有案例与厂商整理的客户案例**；③不成立。本章 [§6](11-olap-engine-section-6-sec6.md) 的四个案例（字节 shuffle、小红书 ClickHouse、京东物化视图自动改写、腾讯湖仓一体直查）都不涉及引擎内模型调用，**其中的数字由本书汇总，不构成第②条要求的第三方（非厂商）公开生产案例**。
- **成熟度**：**L2**（§5.1 表第 6 行）：①成立、②核不到、③不成立。**上线门槛**：算得出每行调用的 token 成本上限与超时预算，并把它纳入查询门禁；算不出就停在 PoC。
- **判定方法**：三个问题——这条 SQL 的产物会不会被下游当作可复现的事实使用？单次执行的成本上限是多少、由谁批？外部服务限流时这条查询是返回部分结果还是整条失败？三问里第二问答不上，就不该进核心链路。
- **什么时候值得做**：处理对象是长尾文本（评论归类、摘要、实体抽取）、结果允许人工复核、且行数可控时。
- **什么时候不值得做**：查询结果是报表主链路的事实来源，或行数是千万级时——前者要求确定性，后者让 token 成本失控。
- **失效的早期信号**：模型调用没有配额与超时配置；做同样事情的两次查询结果不同却无人记录；出域数据没有单独列进合规清单。
- **回到执行层的必要性**：把模型放进 SQL 以后，"慢查询"这个概念被拆成两类——引擎内部慢（还能靠计划与布局优化）与外部服务慢（只能靠超时与降级）。排查顺序必须先把这两类分开，否则会在计划上反复调优一条根本不受计划影响的查询。
- **与成本治理章节的分工**：token 成本的分摊与门禁做法在 [../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md) 一侧；本节只指出事实：**引擎自带的资源管理看不见这项成本**，所以不显式加门禁就等于没有上限。
- **可以接受的退化形态**：允许"结果不稳定"的场景有一个共同特征——**产物不被下游当作事实**（例如给内容打标签后由人抽检、给工单生成摘要供人阅读）；反过来，只要产物会进报表、进训练集、进对账，就属于不可接受。

#### 5.2.4 同组方向：收益来自既有机制，不来自模型

- **旧做法与它的卡点**：自治 OLAP、云原生 OLAP（存算分离）、实时流批融合、内嵌 OLAP（及"AI 增强优化"）都被写成未来趋势。它们的共同卡点不在 AI：自治卡在**动作的可回滚性**，云原生卡在**计算与存储的接口**，流批融合卡在**写路径的去重与延迟**，内嵌引擎卡在**单机与多机的边界**。
- **AI 改变了什么机制**：**这四个方向都只改了提问方式，没改机制**。自动物化视图改写、自适应并行度、自动统计信息是**按统计信息做的确定性动作**（[../14-optimizer](../14-optimizer/14-optimizer.md) 的 CBO 与自适应执行），不需要模型；存算分离是存储接口问题；流批融合是写路径问题；内嵌引擎的分布化是执行架构问题。
- **由此得到的**：**因为动作由统计信息驱动，"降低运维负担"今天就能排进路线图，且出问题时原因可复现**——这是它相对"AI 决策"最大的优势：可解释、可回放、可在测试环境复现。本章 [§6](11-olap-engine-section-6-sec6.md) 的"物化视图自动改写：让业务方写普通查询就命中预聚合"就是这个机制的一个实例。

| 动作 | 驱动信息 | 可回滚吗 | 能否进自动通道 |
| --- | --- | --- | --- |
| 小文件合并 / 数据重写 | 文件数、平均文件大小（主文件 §2.1 的 Zone Map） | 可（产物可再合并） | 可以 |
| 物化视图刷新 / 自动改写 | 查询模式统计 | 可（重建即可） | 可以 |
| 统计信息收集 / Join 策略 / 并行度 | 运行时行数统计 | 可（计划级，随查询消失） | 可以 |
| 分区结构与分桶键变更 | 增长与访问趋势预测 | **难**（下游依赖要同步改） | 只进建议通道 |
| 引擎 / 存储 / 表格式迁移 | 成本与性能预测 | **不可**（年级别动作） | 不自动 |

这张表的读法是**自下而上找边界**：前三行能自动，是因为它们的产物还能被下一次动作覆盖；后两行不能自动，不是因为技术不可行，而是因为**一次错误决策的后果无法用一次操作撤回**。所以"自治到什么程度"在本主题里等价于"你愿意为哪几类动作准备回滚方案"。

- **由此付出的**：**其一，自动动作的计算落在谁的账上要事先约定**（合并、重写、物化都是"看起来不增长"的那部分成本）。**其二，自动化半径由回滚能力决定**——上表后两行就是边界，把分区结构变更自动化等于把年级别的风险交给一条规则。**其三，存算分离把一部分问题移到基础设施侧**：性能上下限取决于对象存储与 catalog 的延迟与一致性，引擎侧的调优空间变小。**其四，内嵌引擎的边界容易被讲混**：单机快不等于分布式可用，判据见 §5.4。
- **证据与来源**：【公开】上述确定性能力在主流引擎的官方文档与发布说明里逐项可核验（可按「项目名 + 自适应执行 / 自动物化 / 自动 compaction」检索）；**②核不到**。内嵌引擎的分布式扩展：**判定方法**是看该版本的 release note 里有没有独立的多机执行组件，而不是看 benchmark 博客。
- **成熟度**：见 §5.1 表第 4、10、11、12 行；作为一组，**确定性部分 L2，AI 决策部分 L3**（第 5、7 行）。
- **失效的早期信号**：把自动 compaction / 自动物化算成"AI 自治"写进方案；用 benchmark 博客证明内嵌引擎支持分布式；为了"AI 友好"换引擎。
- **判定方法**：列一张"当前需要人工干预的调优动作"清单，逐个问"它的产物能不能被下一次动作覆盖"。答"能"的可以进自动通道；答"不能"的，不论引擎是否宣称支持自动化，都只能进建议通道。
- **什么时候值得做**：查询模式稳定、表与分区数量已超出人工调优能力时——确定性自动化是唯一可复现的解法。
- **什么时候不值得做**：表少、查询模式仍在频繁变化时——自动物化会跟着口径一起变，重建成本反而高于省下的时间。
- **与相邻章节的接口**：[§3](11-olap-engine-section-3-sec3.md) 给模式选择与建表范式、[§4](11-olap-engine-section-4-sec4.md) 给工程步骤与监控口径、[§6](11-olap-engine-section-6-sec6.md) 给四个真实案例的取舍；本节只回答"哪些动作今天能自动、哪些不能"。
- **为什么这四条被写进"AI 趋势"**：因为它们都与"规模变大以后人管不过来"有关，而"用 AI 管"是最容易被写进方案的答案；把它们拆成"确定性动作 + 建议通道"两半之后会发现，能进自动通道的那一半**在引擎里早就有对应配置**，不需要模型。
- **一个可用的判断句**：如果某个"自治"能力需要模型才能工作，那么必须同时具备三条——动作可回滚、判定可解释、失败可定位到规则；三条缺一条，它就只能是建议，而不是自治。

### 5.3 与本主题既有栈的接口在哪

接口的共同形状是"**过滤进来、计划出去、结果被消费**"。下面每一行都不是"与 X 结合"，而是"数据以什么形态穿过边界、失败时谁负责"：

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 自然语言查询 ↔ 语义层 / 指标平台（[../../04-data-assetization/10-metric-platform/10-metric-platform.md](../../04-data-assetization/10-metric-platform/10-metric-platform.md)） | 以"指标定义 + 维度 + 口径"穿过，引擎只收到 SQL 文本 | **语义层**：口径未登记时，语法正确、含义错误，引擎不报错 | L2；这是本主题唯一一条"引擎侧无法兜底"的边界 |
| 自然语言查询 ↔ 目录（[../../04-data-assetization/08-data-catalog/08-data-catalog.md](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 以"表 / 字段的业务含义与 Owner"穿过 | **目录侧**：选了停用表或重复表，结果存在但不该用 | 既有能力；缺的是"停用 / 重复"这两个字段 |
| 向量检索 ↔ 引擎 | 候选集与相似度分数以算子形态穿过 | **引擎侧**：过滤没下推（代价问题）；**索引侧**：召回率不达标（质量问题）——两者症状相似，必须分开度量 | L2 |
| 引擎内 LLM 函数 ↔ 模型服务 / 网关 | 请求按"行 → 提示"穿过，回答按"行 → 文本"返回 | **引擎侧（调用方）**：超时 / 限流 / 数据出域的策略必须由调用方设 | L2 |
| 优化器 ↔ 引擎（[../14-optimizer](../14-optimizer/14-optimizer.md)） | 统计信息进、执行计划出 | **优化器侧**：统计信息陈旧导致选错计划，症状是"偶发慢查询" | 既有能力 |
| 湖格式 ↔ 引擎（[../03-lakehouse](../03-lakehouse/03-lakehouse.md)） | 以表格式 + catalog 为边界 | **表格式侧**：直查的延迟与快照一致性由表格式与 catalog 保证 | L2 |
| 实时特征 ↔ 引擎（[../../02-data-science/01-feature-store/01-feature-store.md](../../02-data-science/01-feature-store/01-feature-store.md)） | 按实体键的点查 | **特征平台侧**：离线 / 在线口径不一致——这条边界上最常见的失败与 OLAP 无关 | L2；不要把点查负载塞进聚合引擎 |
| 查询网关 ↔ 引擎（[../13-query-engine](../13-query-engine/13-query-engine.md)） | 跨源下推 + 结果合并 | **网关侧**：下推不完整，数据被搬到网关侧合并，引擎的优势消失 | 既有能力 |
| 物化视图 ↔ 查询改写器 | 以"查询模式 → 预聚合"的匹配关系穿过 | **改写器侧**：改写错导致结果错（比慢查询严重得多），必须有可回滚的版本 | L2；自动改写前先做等价性校验 |
| 存算分离的存储层 ↔ 引擎 | 以对象存储 + catalog 为边界 | **基础设施侧**：延迟与一致性由存储与 catalog 决定，引擎调优空间变小 | L2；非 AI |

三处最容易漏的边界是第 1、3、7 行：**语义层缺字段**（口径、停用标记）会让引擎"算对但答错"；**召回与过滤共用一条延迟指标**会让两类问题互相掩盖；**把 KV 点查当聚合负载**会让引擎为一批它不擅长的工作扩容。这三处的共同点是：**失败都不以"报错"的形式出现**，因此比引擎自身的问题更难发现。

### 5.4 公开进展与文献

分三类列出，每条都给出可核验的入口（拿不准的只写判定方法，不写结论）：

**（1）论文与专著**

- 【公开】DuckDB 的可嵌入分析引擎论文（SIGMOD 2019，Raasveldt & Mühleisen）——内嵌 OLAP 的机制与设计取舍，可核验。
- 【公开】Snowflake 的弹性数仓论文（SIGMOD 2016）——存算分离与多集群共享数据的早期公开设计，可核验。
- 【公开】TPC-H / TPC-DS 等标准决策支持基准的官方规范——免费可下载，是"引擎能力"最中性的比对面；**注意它测的是引擎，不是 AI 能力**。
- 【公开】Text-to-SQL 方向的学术基准（Spider 一类；BIRD 一类大规模数据库接地基准，年份与会议以论文页面为准）——它们的作用是**暴露"给定 schema 与问题集"下的转换能力**，不含口径层。
- StarRocks / Doris / ClickHouse 团队各自的架构论文：按题名在论文集页面核验会议与年份后再引用，本节不复述其结论。

**（2）官方 release note 与文档（判定入口）**

- 列存 / 向量化 / CBO / 物化视图改写 / 自适应执行——逐项查所用引擎的官方文档与 release note，以当前版本为准。
- 向量索引——查引擎文档里的索引类型、距离度量、是否支持与标量过滤共用（决定过滤能不能下推）。
- 引擎内模型调用——查产品文档里的函数签名、超时、配额与计费说明；**函数名各平台不同，不要张冠李戴**。
- 存算分离 / 共享存储——查该版本是否有独立的对象存储与 catalog 条目，而不是看官网的"云原生"标签。
- 内嵌引擎的多机扩展——查 release note 里有没有独立的多机执行组件；只有单机 benchmark 不算。
- 各引擎版本与特性——一律以对应项目的官方发布页为准。
- 函数命名——查产品文档的函数签名页；不同平台的同名能力函数名不同，**跨平台移植时要重新核对语义，而不是照搬 SQL**。
- 数据出域——查该产品文档里"数据会不会被发送到外部服务""是否用于训练"的条款；这类条款会变，以签订合同时的版本为准。
- 近似检索的质量口径——查引擎文档里对索引类型与召回参数的定义；"支持向量检索"与"在你的召回率目标下达标"是两件事，后者只能自己测。
- 版本的兼容代价——查 release note 里的破坏性变更（deprecation）条目；升级一次引擎比换一次向量索引参数的风险高得多。
- 查询改写器的等价性——查文档里对"自动改写命中条件"的说明；改写错会直接产出错误结果，比不改写严重得多，因此必须有可回滚的改写版本。
- 定时任务与后台动作的可见性——查是否有"最近一次合并 / 刷新 / 统计信息更新"的记录入口；看不见的自动化动作，出问题时无法归因。

**（3）第三方（非厂商）公开生产案例**

本节不列（理由见 §5.1 判据声明）。可自行核验的替代路径：本章 [§6](11-olap-engine-section-6-sec6.md) 的四个案例是本书对公开材料与工程做法的汇总整理，**其中的数字由本书给出，不构成第三方（非厂商）公开生产案例**；要找这类材料，以"采纳方自己发布的工程文章"为准，并优先采信写清了数据量、查询形态与硬件条件的材料——本主题里"只有结论没有条件"的材料几乎都是营销。

### 5.5 被过度宣传的部分

**"自然语言查询让业务人员不用学 SQL"** —— 实际是把写作成本换成了校验成本 → 为什么会这样：语法正确性由引擎保证，口径正确性没有人保证，而错的 SQL 不会报错，**静默错误是这条链路唯一的默认失败形态** → 什么时候才会成真：口径被登记为机器可读对象、且查询能回到口径定义上做校验时。

**"OLAP 内置向量索引 = 一个引擎搞定 RAG"** —— 实际只是"同一个引擎里多了一个相似度算子" → 为什么会这样：召回质量由数据量、维度、过滤选择性、召回率目标与硬件共同决定，脱离这些条件的"毫秒级"没有信息量 → 什么时候才会成真：能给出"过滤把候选集压到多少"与"召回率-延迟曲线"这两个数时。**顺带一句**：把"统一检索"当成范式，是把两个不同性质的结果集（精确集合与近似候选）混成一个承诺。

**"自治 OLAP / AI 自动调优"** —— 实际是统计信息驱动的确定性动作加上一条建议通道 → 为什么会这样：能被自动化的动作必须可回滚，而"改分桶键 / 换存储 / 迁引擎"这类动作不具备一键退回的性质（§5.2.4 的表就是这条边界的实操版） → 什么时候才会成真：调优动作可回滚、可解释、可复现，且失败时能指出是哪条规则被触发时。

**怎么验**：把三条各写成一个可执行的小测试。"自然语言查询让业务人员不用学 SQL"——抽一批口径未登记的问题，看链路是拒答、标红还是照答（照答即口径这一环缺了）；"一个引擎搞定 RAG"——在你的数据量与召回率目标下要求给出召回率-延迟曲线；"自治 OLAP / AI 自动调优"——让观察窗口里的质量指标轻微恶化，看系统能不能说出"因为哪条判据"而回滚，再把那个自动动作回滚一次，看能否恢复到原状。三条通不过，说明它们是营销措辞而不是机制。

三条被过度宣传的说法有一个共同点：**它们都在把"更大范围的能力"当成"更明确的判据"**——把"哪些指标坏到多少要调"换成"AI 会判断"，把"这个索引在你的数据规模下召回多少"换成"支持向量检索"。识别办法是问一句：**这套机制出错时，能不能指出具体是哪一条判据被违反了？** 指不出来，就说明它还不是一个可运维的机制。

### 5.6 未来 3-5 年：可证伪的预测

四条预测都写成"预测 + 会成真的信号 + 会证伪的信号"。信号只写**外部可观察的事实**（某个能力出现在文档的哪一类条目里、哪类材料开始公开），不写"体验会变好"这类无法观察的判断。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 引擎内 LLM 函数长期停留在长尾、非核心路径，不进主查询链路 | 公开材料开始普遍给出"每行 token 成本 / 超时预算 / 与纯 CPU 算子的对比口径" | 出现把 LLM 函数用在每日报表主链路的生产实践，并公开成本与失败率 |
| Text-to-SQL 的竞争维度从"模型准确率"转到"语义层覆盖率与可校验性" | 评测集开始包含"口径定义"与"结果可否回溯到口径"两个维度 | 主流评测仍以 schema + 问题集为主，且不看语义层 |
| 向量检索与 OLAP 的融合以"两级结构 + 过滤下推"落地，而不是单引擎内建通用向量库 | 主流方案把召回与精排分开，并把"过滤下推比例"作为公开指标 | 单引擎同时承担两者，并公开召回率-延迟曲线与成本口径 |
| 存算分离在云上成为默认，但"跨云统一计算"不成立 | 主流部署形态是"存储层跨云可读、计算层各云独立" | 出现跨云统一计算面，并公开成本与性能数据 |

这四条里，前两条关于**新算子怎么被约束**，后两条关于**系统怎么分层**——它们不预测哪家引擎会赢，只预测"某类能力会不会被纳入既有的成本模型与可回滚边界"。几年后回头核：若查询门禁里确实出现了 token 成本与超时这两项、评测里确实出现了口径维度，说明本节的机制判断成立；若只有产品宣传而没有这两类痕迹，说明"AI 原生 OLAP"仍停在演示层。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 只用 OLAP 做 BI / 报表 | 把确定性优化开起来：统计信息、自动 compaction、物化视图改写 | 慢查询占比、运维工时、物化视图命中率 | 不要为"AI 原生"这个标签换引擎 |
| 想让业务方自然语言取数 | 先做语义层与口径登记，再做入口；把"口径未登记问题占比"作为验收指标 | 该占比是否下降；换同义问法后答案是否稳定 | 不要在口径没有书面定义时开放自然语言入口 |
| 要做 RAG / 混合检索 | 用"结构化过滤 + 向量召回"两级结构；把过滤下推比例作为指标 | 召回率-延迟曲线、候选集下降比例 | 不要指望一个引擎解决召回质量问题；不要采信无条件的"毫秒级" |
| 想用引擎内 LLM 函数 | 只放在长尾、可复核路径；把 token 成本与超时纳入查询门禁 | 每行调用成本、超时比例、数据出域范围 | 不要在报表主链路放模型调用；不要把某家函数名当通用名 |
| 在选型新引擎 | 按 [§7](11-olap-engine-section-7-sec7.md) 的对比表与 [§3](11-olap-engine-section-3-sec3.md) 的决策表选；"是否支持某特性"逐条查 release note | 存储接口与 catalog 的稳定度、版本升级的兼容代价 | 不要按 roadmap 选型，也不要为"AI 友好度"这个评分维度做决策 |
| 已经有引擎、在评估"要不要上向量索引" | 先用结构化过滤把候选集压到可度量的小集合，再评估索引 | 过滤下推比例、召回率-延迟曲线、索引重建期查询退化幅度 | 不要在候选集本来就小的场景引入第二套索引 |
| 被问"我们的 OLAP 什么时候能用上 AI" | 用 §5.1 表逐行回答，并先把第 1、4 行（执行基线 + 确定性自动化）做掉：开统计信息、开自动 compaction、把查询门禁建起来 | 执行基线与确定性自动化的落地清单是否清空；AI 方向的 PoC 是否仍拿不出那四个数 | 不要给一个笼统的"AI 原生 OLAP"时间表 |

读这张表的方法是**从"明确不要做"那一列往回读**：本主题里最贵的浪费不是选错引擎，而是**把顺序做反**——先为"AI 原生"买单，再回头补统计信息与查询门禁。上表每一行的"现在就该做"都是可以在一到两个迭代内完成、且可复现的动作；"一年内观察"那一列若一年后仍是空的，说明这条路没被真正走通，应当停下来而不是加大投入。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一一条机制**是**执行计划里多了两类算子**——相似度排序（近似、结果不再可复现）与模型调用（非确定、按 token 计费）。两者共同换掉了 OLAP 最稳的性质：**同一查询同一结果**，代价是可复现性下降与 CBO 成本模型失效；而自然语言查询的成败仍取决于语义层，自治优化的可用部分仍然是统计信息驱动的确定性动作。它**没有**改变的是：列存 + 向量化 + CBO 这条执行骨架，"数据要放得离计算近"这条物理约束，以及"慢查询要先归因到计划还是数据布局"这条排查顺序。
>
> 本节的三级与三条判据未做任何修正（§5.1），因此表里没有 L1 行；这不代表本主题不成熟，只代表**公开材料到不了 L1**——这个领域的公开文化是比性能，不是讲实践。规划时按"表里的 L2 先做、L3 只记录"推进，并在自己组织内积累第②条要求的那类记录。
>
> 💡 **思考锚点**：把 5.2.4 那张表的读法用在你自己的引擎上——列出当前还需要人工干预的调优动作，逐个问「它的产物能不能被下一次动作覆盖」。被划进自动通道的清单里，有没有混进「分区结构与分桶键变更」或「引擎 / 存储 / 表格式迁移」这两类？如果有，你为它准备的是回滚方案，还是回滚的信心？
