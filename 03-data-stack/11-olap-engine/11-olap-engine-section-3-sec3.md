## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把 OLAP 讲成「按场景选一个引擎或一种搭法」：实时大屏选实时 OLAP、多维分析选物化视图、AI 场景加向量索引、云上选存算分离。但真实的模式选择被一条机制推着走：**OLAP 引擎里没有免费的查询加速——每一次「让查询变快」的动作，都必须在写入时或后台提前付掉代价**。列存（主文件 §1.1：只读需要的列，I/O 降低 10-100x）把代价付在「排列式重写」上，排序键把代价付在「写时排序」上，物化视图与 Cube 把代价付在「写时预聚合 + 每次上游写入的维护」上，外表与即席查询把代价留到「查询时现算」上。所以**本节的所有模式，都只是「在哪个阶段付这笔钱」的不同回答**；判断一个模式是否用错，等价于判断「这笔钱付的阶段与工作负载的变更频率是否匹配」。

第一条约束由此推出：**数据的物理布局在写入时就基本锁死了查询能有多快**。列存 + 分区 + 排序键 + 分桶键，这四件事一旦定下来，查询侧能做的事只剩「跳过不匹配的数据块」（Zone Map、Bloom Filter、前缀索引）。主文件 §1.1 把 OLAP 的索引形态概括成「列存 + 压缩 + Zone Map」，原因也在这里：**OLAP 没有 B+ 树那种"事后补一个索引就能加速任意查询"的路径**。所以「查询慢 → 加个索引」在 OLTP 是常识，在 OLAP 常常只能通过重建表（换排序键/分桶键）解决。用一个可算的例子感受裁剪的收益：一张 100 列的事实表，若查询只涉及 5 列，列存需要读的字节数约为行存的 5%【推算】（100 列 → 5 列，按列与行存每列字节数相近估算，不含压缩差异；主文件 §1.1 给出的 I/O 降低区间 10-100x 覆盖这个量级）。**这 20 倍的裁剪收益来自「只读需要的列」，与有没有索引无关**——它也是为什么宽表在 OLAP 里可行、在 OLTP 里不可行的原因。

第二条约束：**更新在列存里不是原地改，而是"追加新版本 + 后台合并"**。主文件 §2.3 给出的 StarRocks 主键模型、Doris Unique Key 模型、ClickHouse ReplacingMergeTree，三种写法表达的是同一件事。这条约束的推论很反直觉：列存**可以**做实时更新，但实时性由「合并能力」而不是「写入能力」决定；写入端看起来每秒都在收数据，查询看到的版本数却由后台合并速度决定。这直接解释了为什么「实时写入」既是本主题最受欢迎的模式（3.2.1），也是最容易翻车的模式（见 3.5 的「实时写入不当」）。

第三条约束：**新鲜度、查询延迟、成本三者不能同时最优**。实时导入意味着微批窗口，窗口就是可见性延迟的下界；物化视图意味着查询快但结果滞后于上游；外表查询意味着数据零拷贝但每次都要跨网络读远端文件；存算分离意味着弹性但冷读要付对象存储的延迟。任何声称三者兼得的方案，通常是把某一项悄悄丢给了上游（例如让 ETL 承担预聚合）或下游（例如让 BI 做结果缓存）。这三条是**机制层面**的约束；下表把它展开为选型时必须逐条确认的**六个约束输入**，两者不是一一对应——机制一、二主要落在「数据形态与写入模式」「访问模式」两行上，机制三主要落在「一致性 / 可见性」「规模与成本」两行上，而「变更频率与历史要求」「团队技能与运维能力」两行不是引擎机制推出来的，它们由业务节奏与团队现实决定。所以读下表时不要试图把它归并回三条，而要逐行确认自己项目的取值。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态与写入模式（追加 + 合并，不是原地更新） | 更新、删除、去重的实现方式与实时性上限 | 「列存不能做实时更新」——能，但形式是版本合并，实时性由合并能力决定 |
| 访问模式（扫描 / 聚合 / 高并发点查） | 排序键、分区键、分桶键的选择；点查与扫描对布局的要求相反 | 「加索引就能变快」——OLAP 没有通用二级索引，只有 Zone Map / Bloom / 前缀索引 |
| 变更频率与历史要求 | 物化视图刷新策略与预计算深度是否值得 | 「预计算越多越快」——每条上游写入都要维护所有相关预计算结果 |
| 一致性 / 可见性要求 | 微批窗口、合并延迟、查询读到的是哪个版本 | 「写入即可见」——微批下存在一个攒批窗口，窗口内查询读不到 |
| 规模与成本约束 | 冷热分层、存算分离、外表与内表的取舍 | 「全放 SSD 就行」——成本随保留期线性上涨，而查询集中在最近一段时间 |
| 团队技能与运维能力 | 自建存算分离还是用云原生；MV 的规模上限 | 「MV 越多越好」——命中率为零的 MV 是纯维护负担（见 3.5） |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 实时 OLAP（Kafka → OLAP）

- **被什么约束逼出来**：业务要求「数据产生后秒级可查」，而传统链路（入湖 → T+1 调度 → 导入）的最小延迟是一天。约束来自「可见性延迟必须小于业务决策的周期」。
- **结构**：

```text
  Kafka（原始变更/事件流）
        │
        ▼
  Flink / 导入任务：攒批 + 去重 + 主键归并 → Stream Load / CDC 写入
        │
        ▼
  OLAP 表：主键模型 + 排序键（写入 = 追加新版本）
        ├─► 后台合并（Compaction）把多版本压成一个版本
        ├─► 查询（永远读"某个已提交版本"的快照）
        └─► 物化视图（3.2.3）在写入链路上增量维护
```

```sql
-- StarRocks / Doris：主键模型 + 分桶 + 排序键，写入即追加版本
CREATE TABLE dwd_order_realtime (
  order_id   BIGINT,
  user_id    BIGINT,
  status     VARCHAR(16),
  amount     DECIMAL(18, 2),
  updated_at DATETIME
)
PRIMARY KEY (order_id)
DISTRIBUTED BY HASH(order_id) BUCKETS 32      -- 分桶键 = 点查与 JOIN 的主键
ORDER BY (updated_at);                        -- 排序键 = 最常见的范围过滤列
-- 注意：ORDER BY 与 DISTRIBUTED BY 一旦定下，改它等于重建表
```

- **为什么这样设计有效**：因为写入是「按主键追加新版本」，所以同一条记录被反复更新不会触发行级锁与随机写，写入路径退化成顺序追加；因为后台合并把多版本收敛成一个版本，查询只需扫过当前版本，所以**查询性能与写入频率解耦**——这是实时 OLAP 能同时做到「秒级可见」与「亚秒级查询」的原因。而攒批把版本产生速率压到合并能力之内，是这套机制能长期稳定运行的前提。
- **代价**：① 写入放大——同一主键在合并前存在多个版本，磁盘占用与扫描量都随版本数增长；② 合并任务与查询争抢 CPU/IO，集群容量必须为合并留出余量（这部分余量平时看起来是浪费）；③ 删除只能靠标记 + 合并落地，无法立即物理删除，也因此与「删除权」这类合规要求配合时要额外设计；④ 微批窗口（攒批间隔）是可见性延迟的硬下界，业务要求「1 秒可见」时必须先确认合并能力能否支撑对应的版本产生速率。
- **失效点**：当写入频率超过后台合并能力时，优点「实时可见」反转成缺点「版本堆积」——查询要扫过越来越多未合并的版本，表现为**查询 P99 随时间缓慢上升而写入量并没有变化**（这个现象极易被误判为"数据量增长"）。机制上，版本积压会同时放大读放大与磁盘占用，且它会自我强化：合并跟不上 → 查询变慢 → 集群负载升高 → 合并更慢。修法是降低版本产生速率（加大攒批间隔）或提高合并资源，而不是加缓存绕过——缓存只会掩盖症状。
- **自验方法**：查「未合并版本数 / 表数」与「合并任务平均滞后时间」这两个指标，若滞后时间在持续增长，就处在失效边缘，与 QPS 高低无关。
- **真实使用**：主文件 §2.3 用三个建表示例给出 StarRocks 主键模型、Doris Unique Key 模型与 ClickHouse ReplacingMergeTree（书内记录，见 [§2](11-olap-engine.md)）；主文件 §1.2 把「实时报表 / 双 11 大屏秒级刷新」列为驱动场景（书内记录）。这三个产品各自对「写入即产生新版本、后台合并」的语义说明见其官方文档【公开】（来源形态：StarRocks 官方文档的 Primary Key table 章节、Doris 官方文档的 Unique 模型章节、ClickHouse 官方文档的 ReplacingMergeTree 引擎章节，2025 年核查；页面标题以各文档站当前版本为准）。「Kafka + Flink + StarRocks/Doris」是实时数仓的常见组合【经验】。

#### 3.2.2 Lakehouse 外表查询

- **被什么约束逼出来**：同一份数据要被多个引擎消费（Spark 批算、Flink 流算、OLAP 交互查询），而把数据复制进每个引擎的私有格式，会带来三份存储、三套口径、三次导入延迟。约束来自「一份数据、多引擎」。
- **结构**：

```text
   对象存储（S3 / OSS / HDFS）
     ├── 数据文件（Parquet / ORC，列存）
     └── 表格式元数据（Iceberg / Hudi / Paimon）：快照 + 清单 + 分区裁剪
              │ 读清单做文件级裁剪；写：提交新快照
              ▼
        OLAP 外表（CREATE EXTERNAL TABLE / Catalog 直连）
              ▼
        本地缓存层（热数据落本地盘，命中即不走网络）
```

```sql
-- OLAP 侧只做计算，数据留在对象存储；表格式负责快照与裁剪
CREATE EXTERNAL TABLE ext_orders
ENGINE = iceberg                              -- 或 hive / hudi / paimon
PROPERTIES (
  "iceberg.catalog.type"  = "rest",
  "iceberg.catalog.uri"   = "http://catalog:8181",
  "iceberg.database"      = "prod",
  "iceberg.table"         = "orders"
);
-- 同一张 iceberg 表同时被 Spark / Flink / 本引擎读，无需导入
```

- **为什么这样设计有效**：因为数据由表格式管理快照、由对象存储承载文件，任何支持该格式的引擎都能读同一份数据，**新增一个引擎的边际成本是"实现一个 reader"，而不是"复制一份数据"**；因为 OLAP 只承担计算，存储成本从「按引擎份数」变成「按数据本身一份」，存算的账第一次可以分开算。
- **代价**：① 每次查询都要读远端清单再读远端列块，对象存储的取数延迟比本地盘高一个数量级【经验】；② 小文件与清单规模决定元数据解析开销——文件数上万后，查询时间可能大半花在解析清单上；③ 缓存层成为性能关键（缓存容量、置换策略、失效时机都要调），而它是引擎私有实现，替换引擎等于重做缓存策略；④ 表格式自身的运维（快照过期、小文件合并、孤儿文件清理）要单独建任务，不做就会随时间劣化。
- **失效点**：当查询从「扫描聚合」变成「高并发点查」时，外表的优点「一份数据多引擎可用」反转成缺点「每次点查都要跨网络读远端文件」，因为点查的延迟主要由元数据解析 + 网络往返决定，而列存裁剪在这种查询形态下帮不上忙。判据是可测的：对比同一份数据在内表与外表的点查 P99，若差距显著且点查占比高，就应当把热数据导入内表，外表只留冷数据与联邦场景。
- **自验方法**：统计「查询耗时中用于读清单 + 打开远端文件的比例」；这个比例高于扫描本身时，瓶颈不在引擎算力而在文件布局。
- **真实使用**：主文件 §1.4 记录 2023 年 StarRocks 3.0 与 2024 年 SelectDB Cloud、Apache Doris 2.1 的演进（书内记录）；[§7.6 组合使用](11-olap-engine-section-7-sec7.md)的「组合 1：StarRocks + Iceberg 外表」正是这一形态（书内交叉引用）。表格式侧 Iceberg / Hudi / Paimon 均为 Apache 软件基金会项目【公开】（来源形态：Apache Iceberg、Apache Hudi、Apache Paimon 三个项目的官网与 ASF 项目页，2025 年核查；各自当前处于顶级项目还是孵化器，以上述页面为准）。是否用外表替代内表，取决于点查占比与延迟要求【经验】。

#### 3.2.3 物化视图加速

- **被什么约束逼出来**：查询模式固定（同一批看板、同一批报表反复跑同样的聚合），而每次现算都要扫全量明细。约束来自「查询重复度高、且对延迟敏感」。
- **结构**：

```text
  上游明细表（每次写入 = 新版本）
        ├─► 增量刷新：只处理本次变更涉及的分组
        ▼
  物化视图（按 (维度, 时间粒度) 预聚合）
        ▼
  查询改写：优化器发现查询形态与 MV 匹配 → 自动改写为查 MV
        （命中条件：聚合函数、分组列、过滤条件都需匹配）
        ▼
  BI / 看板 / API
```

```sql
-- 预聚合把扫描量压到分组数级别；增量刷新只处理变更部分
CREATE MATERIALIZED VIEW mv_trade_daily
DISTRIBUTED BY HASH(shop_id) BUCKETS 16
REFRESH ASYNC EVERY(INTERVAL 5 MINUTE)      -- 刷新间隔 = 新鲜度上限
AS SELECT
    shop_id, dt,
    SUM(amount) AS gmv,
    COUNT(DISTINCT user_id) AS buyers
FROM dwd_order
GROUP BY shop_id, dt;
-- 注意：COUNT(DISTINCT) 与自定义函数常导致"不可增量"，退化为全量重算
```

- **为什么这样设计有效**：因为结果已经按某个分组粒度算好，查询退化成对预聚合结果的扫描，**扫描量从"明细行数"降到"分组数"**——若 10 亿行明细聚合成 100 万个分组，扫描量约为原来的千分之一【推算】（10⁹ → 10⁶，按行数比估算，实际收益还受 MV 的列数与压缩影响）；因为增量刷新只处理变更涉及的分组，维护成本与「变更量」而不是「总量」相关，这让它在持续写入的明细表上也成立。
- **代价**：① 存储按 MV 数量线性增长，且 MV 自身的压缩率通常低于明细（聚合值列少、去重性差）；② **写放大随 MV 数量增长**——每条上游写入要触发的维护量正比于相关 MV 数，MV 越多，写入路径越重；③ 命中依赖查询改写，SQL 形态不匹配（换一个聚合函数、加一个表达式）就命中不了，此时 MV 只贡献成本不贡献收益；④ 刷新间隔就是新鲜度上限，看板数据与明细存在时间差，且这个差要能向用户解释。
- **失效点**：当 MV 的刷新跟不上上游写入频率、或维度组合变化快时，优点「查询快」反转成「维护成本大于收益」——因为每条上游写入都要维护全部相关 MV，而命中率可能很低。机制上的判据很直接：**统计每个 MV 的命中次数与它的维护成本（写入放大 + 存储 + 刷新时间）之比**，命中率接近零的 MV 是纯负担，而它不会自己暴露——它只表现为集群整体写入变慢。
- **自验方法**：把 MV 全部禁用后重跑一批真实查询，比较总耗时与资源消耗；如果差距很小，这批 MV 的价值实际上来自集群缓存而不是预计算。
- **真实使用**：主文件 §2.3 给出 StarRocks 物化视图的建表示例，§2.4 的引擎对比把「物化视图极强、支持自动增量」标在 StarRocks 一列、ClickHouse 一侧偏弱——这两处都是本书自己的对比结论（书内记录），引用它们时应作为书内结论而不是外部出处。产品侧「物化视图是否支持自动 / 增量刷新」以各自官方文档为准【公开】（来源形态：StarRocks 官方文档的物化视图（同步 / 异步）章节与 ClickHouse 官方文档的 MaterializedView 引擎章节，2025 年核查；页面标题以各文档站当前版本为准）。多数团队长期有效的 MV 数量在个位数到几十个之间【经验】，超过之后维护成本通常开始压过收益。

#### 3.2.4 Cube / Rollup（谨慎）

- **被什么约束逼出来**：固定维度的多维分析要求「任意维度组合都秒回」，而任意组合意味着查询前无法预知 GROUP BY 形态，只能把组合**穷举**预计算出来。约束来自「维度组合未知 + 延迟要求极低」这一对矛盾的组合。
- **结构**：

```text
  明细表
    ▼
  维度组合枚举（全部子集）：(全部 3 维) → (任意 2 维) → (任意 1 维) → (总计)
    ▼
  每个组合一张结果表（或一个物化块）
    ▼
  查询时按请求的维度组合直接命中，不做聚合
  ────────────────────────────────────────────
  N 个维度 → 2^N - 1 个非空组合；存储 = Σ(各组合的分组数)
```

```sql
-- 物化视图用 GROUPING SETS 表达多维组合（本质是 Cube 的一种实现形态）
CREATE MATERIALIZED VIEW mv_sales_cube
DISTRIBUTED BY HASH(dt) BUCKETS 8
REFRESH ASYNC EVERY(INTERVAL 1 HOUR)
AS SELECT
    dt, region, channel, category,
    SUM(amount) AS amount, COUNT(*) AS cnt
FROM dwd_sales
GROUP BY GROUPING SETS (
    (dt, region, channel, category), (dt, region, channel),
    (dt, region), (dt)
);
```

- **为什么这样设计有效**：因为查询时不再做聚合，响应时间与明细数据量**脱钩**——它只与命中的那个组合的分组数有关。在维度少、基数低、查询必须亚秒返回的传统 OLAP 场景（主文件 §1.4 记录的 1995 年 Oracle Express、IBM Essbase 那一代）里，这是唯一能满足「任意组合任意切」的结构。
- **代价**：① 存储复杂度是 O(∏ Kᵢ)（主文件 §2.2）——把维度基数代进去会立刻失控：8 个维度、每维平均 1000 个取值，全组合数是 10²⁴【推算】（1000⁸ = 10²⁴），即便每个组合只存 8 字节的聚合值也是 8 × 10²⁴ B ≈ 8 YB（= 8000 ZB）【推算】（10²⁴ × 8 B；1 ZB = 10²¹ B，1 YB = 10²⁴ B）；② 构建时间随维度数与基数指数增长，刷新窗口会先于存储成为瓶颈；③ 只能回答**预先枚举过的**维度组合，新增一个维度要重算全部；④ 维度基数会漂移（一个高基数维度被加入后，某些组合的分组数暴增），而漂移在构建时才发现。
- **失效点**：当维度数增加或任一维度的基数显著上升时，优点「查询恒定快」反转成「存储与构建时间不可控」——因为组合数是维度数的指数函数、存储量是基数的乘积函数，这两个增长都不线性。此时正确的替代不是「把 Cube 建得更大」，而是切换到物化视图（3.2.3）或按需预聚合：**只预计算真实查询用到的组合，而不是全部组合**。
- **自验方法**：统计过去 30 天实际出现过的维度组合数，与 Cube 预计算的组合数相比；若后者远大于前者，说明在为不存在的查询付存储成本。
- **真实使用**：Cube / Rollup 是传统 MOLAP 的核心结构（主文件 §1.4 的时间线记为 1995 年 Oracle Express、IBM Essbase，2000 年代 SSAS / SAP BW；该时间线是书内记录）。这四个产品的首次发布年份可在各厂商的产品页 / 文档中核验【公开】（来源形态：Oracle、IBM、Microsoft、SAP 各自官方文档与发布公告中标注的产品版本与年份，2025 年核查；具体页面以各厂商站点当前内容为准）。现代列存 OLAP 里它的位置大部分被物化视图与按需预聚合取代；仍在使用 Cube 的场景通常维度数与基数都被严格约束【经验】。

#### 3.2.5 OLAP + 向量检索（2024 新）

- **被什么约束逼出来**：AI 应用的检索往往是**混合条件**——「按标量条件过滤 + 按向量相似度排序」（例如「在售商品中找与这张图最像的 10 个」）。只用向量库要两阶段拼接，只用 OLAP 没有近邻能力。约束来自「标量过滤与向量近邻必须在同一次查询里协同」。
- **结构**：

```text
   一张表里同时有：标量列（可分区/排序/过滤） + 向量列（数组）
        │
        ├─► 标量列：沿用列存的分区、Zone Map、前缀索引
        └─► 向量列：建向量索引（HNSW / IVF 一类），常驻内存
        │
        ▼
   混合查询：WHERE 标量条件 AND ORDER BY 距离(向量列, ?) LIMIT k
        │
        ▼
   优化器决定顺序：先按标量过滤再做近邻，还是先近邻再回表过滤
   （两种顺序的代价随选择率反转，见失效点）
```

```sql
-- StarRocks 3.x 向量检索示例形态（写法与主文件 §2.3 一致；索引类型与语法以官方文档当前内容为准）
ALTER TABLE products ADD COLUMN description_embedding ARRAY<FLOAT>;
CREATE VECTOR INDEX idx_embedding ON products(description_embedding);
SELECT product_id, l2_distance(description_embedding, [0.12, 0.08, ...]) AS dist
FROM products
WHERE status = 'ON_SALE'                 -- 标量过滤列
ORDER BY dist ASC
LIMIT 10;                                 -- 向量近邻 + 标量过滤一次查询完成
```

- **为什么这样设计有效**：因为向量列与标量列在同一张表的同一份数据上，**过滤条件与近邻排序可以在一个执行计划里协同**，避免「向量库取 top-k → 再按标量条件回表过滤 → 结果不足 k 条要重取」这个两阶段拼接的常见错误；同时标量列继续享受列存的分区裁剪与 Zone Map，不需要为混合查询复制第二份数据。
- **代价**：① 向量索引通常常驻内存，容量与「行数 × 维度」相关，这部分内存不能与查询缓存共享；② 建索引是重操作，向量列的写入会带出索引重建/增量插入开销；③ 向量列几乎不可压缩，破坏列存原本的压缩假设，表体积明显上升；④ 优化器要同时估计标量选择率与近邻代价，而这套统计信息在多数引擎里还不成熟——**代价模型估错时，执行计划会选到差一个量级的那条路径**。
- **失效点**：当标量过滤的选择率很低（几乎不过滤任何行）时，混合查询退化成全表近邻扫描，向量索引的收益消失；反过来当过滤极强（只剩几百行）时，「先过滤再算距离」比「先近邻再过滤」便宜得多，而优化器未必选对。所以这套模式的可用性取决于**能否观测到实际走了哪条路径**：查执行计划里近邻算子与过滤算子的先后顺序，并针对两类查询分别固定计划。
- **自验方法**：分别用「过滤掉 99% 行」与「过滤掉 1% 行」两种查询跑一次，比较耗时与扫描行数；若后者显著慢且无法调优，说明这套混合查询只在某一类选择率下成立，应当拆成两条路径。
- **真实使用**：主文件 §1.4 与 §2.1 记录 2024 年 StarRocks 3.x 的向量索引与 Snowflake 侧的向量检索能力（书内记录）。产品侧「向量列与标量过滤能否在同一查询里协同」以各自官方文档为准【公开】（来源形态：StarRocks 官方文档的向量索引章节与 Snowflake 官方文档的向量数据类型 / 向量相似度函数章节，2025 年核查；页面标题以各文档站当前版本为准）。「一个引擎同时做 OLAP 与向量」是否成立，取决于两类工作负载是否都重：只有向量检索重、标量分析轻时，专用向量库更合适【经验】。

#### 3.2.6 OLAP + 指标语义层

- **被什么约束逼出来**：同一个业务指标被多个消费方（BI 看板、对外 API、Agent 取数）用不同 SQL 各写一遍，口径必然漂移。约束来自「一个指标只能有一个定义，而消费方数量在增长」。
- **结构**：

```text
   指标定义（语义层，与物理表解耦）
     · 实体：订单 / 门店 / 用户
     · 度量：gmv = SUM(amount)，buyers = COUNT(DISTINCT user_id)
     · 维度：dt / region / channel，过滤器与口径说明
              │ 按请求生成物理 SQL
              ▼
        OLAP 引擎（列存 + 向量化执行）
              ▼
   BI 看板 / 对外 API / Agent（三者拿到同一条 SQL）
   ────────────────────────────────────────────
   关键：口径只在"语义层 → 物理表"的映射里存在一份
```

```yaml
# 指标定义独立于物理表；换表只改映射，不改口径
metric: trade_gmv
measure:  { expr: "SUM(amount)", type: sum }
dimensions: [dt, region, channel]
filters:  ["status = 'PAID'"]
source:   { table: dwd_order, join: [dim_shop, dim_region] }
grain:    [1d, 1h]
```

- **为什么这样设计有效**：因为指标定义（度量、维度、过滤、粒度）集中存放、查询由它生成，**口径只在「语义层 → 物理表」这一处映射里存在**，消费方数量增长不再增加口径副本；因为生成的是标准 SQL，OLAP 侧的 CBO 仍能正常优化，语义层不必自己实现执行引擎（这也是 Headless BI 与"自建聚合服务"的关键分野）。
- **代价**：① 语义层成为新的单点与口径争议的集中地——所有分歧都汇到它这里，需要明确的 Owner 与变更流程；② 指标定义与物理表结构耦合，换表、改列名都要改映射，且映射错误**不会报错，只会静默算出另一个数**；③ 复杂查询（多维交叉、自定义窗口、跨实体对比）表达不了时要回退到裸 SQL，口径防线被绕过；④ 多一层查询翻译，生成的 SQL 形态可能让谓词下推、分区裁剪失效，性能需要实测而不是假定。
- **失效点**：当业务方开始绕过语义层直接写 SQL 时，优点「口径统一」反转成「两套口径并存且无法区分」——因为语义层不掌握所有查询入口就无法强制，而强制又会挡住必要的即席分析。这个失效可以量化：**从查询日志按用户/工具分组，统计绕过语义层发出的查询占比**；这个比例上升到一定程度后，语义层的口径就不是"唯一真相"而是"某一个选项"。
- **自验方法**：任取一个指标，问「用语义层算出的值与用裸 SQL 手算的值是否一致」；再问「如果不一致，谁的算对——有没有一份可核验的口径说明来判断」。
- **真实使用**：Headless BI 与 MetricFlow / Cube 属于这一类形态（书内记录，不是外部出处）。产品侧形态与写法以 dbt Labs 官方文档的「About the dbt Semantic Layer」与 MetricFlow 一节（docs.getdbt.com）、Cube 官方文档的「Data Modeling」「Pre-aggregations」（docs.cube.dev）为准【公开】（来源形态：上述两处官方文档，2025 年核查；两站文档随产品版本更新、无固定出版年份，页面标题以当前版本为准）。语义层的收益大小取决于组织是否真的需要「一个指标一个口径」——单团队单看板场景下这层往往是多余的一跳【经验】。

#### 3.2.7 云原生 OLAP（存算分离）

- **被什么约束逼出来**：工作负载有明显峰谷（白天查询多、夜间导入多），而存算一体的集群要按峰值配置，低谷期资源闲置；同时多业务要读同一份数据但各有各的隔离要求。约束来自「计算需求随时间波动，数据量却只增不减」——把两者绑在一起，弹性就必须在数据侧做，而数据搬迁的代价极高。
- **结构**：

```text
            共享存储（对象存储：数据文件 + 表格式元数据）
                        ▲
        ┌───────────────┼───────────────┐
   写集群（导入/合并）  读集群 A（BI）   读集群 B（Agent/即席）
        │               │               │
   本地缓存盘       本地缓存盘       本地缓存盘（各自独立、可缩到 0）
   ────────────────────────────────────────────────────────
   关键：计算节点无状态 → 扩缩容 = 加/减节点，不搬数据；缓存命中率
         决定它"看起来像本地盘"还是"每次都走网络"
```

- **为什么这样设计有效**：因为计算节点无状态、数据在共享存储，扩缩容退化成「加/减无状态进程」，**弹性与数据量解耦**；因为多个计算集群读同一份数据，读写隔离、多业务隔离、按业务单独升降配都可以用"多一个集群"实现，而不是"多一份数据"。
- **代价**：① 冷读要跨网络取远端数据，缓存命中率直接决定性能表现——**存算分离把「本地盘 I/O 便宜」这个前提拿掉了**，缓存容量与置换策略成为核心调优项；② 对象存储按 API 调用计费，小文件与高频点查会放大请求数与账单，成本从「容量」部分转移到「请求」；③ 计算与存储两套组件的版本协同、网络链路成为新的故障面；④ 本地缓存是引擎私有实现，选择引擎时实际上在选择它的缓存策略。
- **失效点**：当缓存命中率低（工作集大于缓存容量，或访问模式高度随机）时，优点「弹性 + 一份数据多集群」反转成「每个查询都在付对象存储的延迟与请求费」——省下的闲置算力成本被存储请求成本吃掉，而这笔账在压测里看不出来，只在月账单和 P99 曲线里出现。判据是**缓存命中率与「冷读查询占比 × 单次冷读增量延迟」的乘积**，而不是集群的平均 CPU 利用率。
- **自验方法**：把计算集群全部停掉，确认数据仍在、并能用另一个新集群立刻查到——查不到说明所谓的存算分离其实还把状态留在了计算侧。
- **真实使用**：主文件 §1.4 记录 2023 年 StarRocks 3.0 的存算分离与 2024 年 SelectDB Cloud、Apache Doris 2.1 的路线（书内记录）；「云原生 OLAP」把 SelectDB Cloud、Snowflake、BigQuery 列为代表（书内记录）。Snowflake 在 SIGMOD 2016 的论文《The Snowflake Elastic Data Warehouse》中描述了共享存储 + 多虚拟数仓的架构【公开】（Snowflake，SIGMOD 2016）。这三家产品公开的存算分离形态，其组件划分与缓存策略以各自官方文档的架构章节为准【公开】（来源形态：Snowflake 官方文档的架构 / 虚拟数仓章节、BigQuery 官方文档的架构章节、SelectDB Cloud 官方文档的架构章节，2025 年核查；页面标题以各文档站当前版本为准）。云原生形态是否划算，取决于峰谷比——峰谷差异小的稳态负载上，存算一体的缓存优势更明显【经验】。

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 要求秒级可见，写入持续且带更新 | 3.2.1 实时 OLAP（主键模型） | 不用 T+1 导入：可见性延迟大于决策周期 | 未合并版本数与合并滞后是否在增长 |
| 报表/看板查询模式固定且重复度高 | 3.2.3 物化视图 | 不用逐个查询调优：重复计算应被消除一次而非优化 N 次 | 每个 MV 的命中次数 / 维护成本之比 |
| 任意维度组合都要秒回、维度少且基数低 | 3.2.4 Cube / Rollup | 不用明细扫描：现算的延迟不可能压到亚秒 | Σ(各组合分组数) 是否在可控量级内 |
| 多维分析：维度集合固定、组合多但未穷举 | 3.2.1 实时 OLAP 内表 + 3.2.3 物化视图 | 不用 Cube：组合未穷举时，穷举预计算的存储是维度基数的乘积 | 真实出现过的维度组合数是否远小于全组合数 |
| 一份数据要被多引擎消费、且以扫描聚合为主 | 3.2.2 Lakehouse 外表 | 不做多份导入副本：口径会分裂、导入延迟叠加 | 点查占比是否高于扫描聚合 |
| 查询以高并发点查为主 | 内表（3.2.1 的表形态）+ 冷数据落外表 | 不用外表承载热数据：点查延迟由网络与文件解析决定 | 内表/外表点查 P99 的差距 |
| 峰谷明显、多业务要隔离读 | 3.2.7 云原生 OLAP（存算分离） | 不按峰值配置存算一体集群 | 峰谷比与缓存命中率 |
| 多消费方共用一个指标口径 | 3.2.6 指标语义层 | 不让每个消费方各写 SQL：口径会漂移且无人负责 | 绕过语义层的查询占比 |
| AI 检索=标量过滤 + 向量近邻 | 3.2.5 OLAP + 向量检索 | 不用「向量库 top-k → 回表过滤」两阶段拼接 | 两类选择率（极强/极弱过滤）下是否都能接受 |
| 早期 0→1（数据量小、查询不固定） | 单机 / 轻量列存 + 内表 | 不上 Cube、MV、存算分离：前两者的收益依赖查询形态稳定，后者的收益依赖负载有明显峰谷 | 查询形态是否已经稳定下来 |

表后要单独说清**最常被误选的一对**：「物化视图（3.2.3）」与「Cube（3.2.4）」被当成同一种东西，都是"预计算"，于是团队常先选了更"全"的那个。误选的后果在机制上是确定的：Cube 的存储是维度基数的**乘积**，MV 的存储是真实查询分组的**并集**——前者随维度数与基数指数/乘积增长，后者只随实际查询增长。所以 Cube 在查询尚未稳定时就建，代价是替不存在的查询付存储与刷新时间；而 MV 在查询已稳定时不用，代价是每次看板刷新都重算一遍明细。判据只有一个：**维度组合是穷举出来的，还是从真实查询日志里统计出来的**。

第二对容易被混的是「实时 OLAP（3.2.1）」与「外表查询（3.2.2）」：两者都能做"实时查询"，但一个是把数据搬进来的快，一个是把计算推出去的省。混淆的后果是**把点查压到外表上**——延迟由对象存储的网络往返决定，而这一步在压测环境（本地对象存储）里往往测不出来。还有两类场景不属于"选哪个模式"而属于"这笔钱付在哪里"：「大宽表聚合」是「写入时不做任何预计算」的极端形态，代价全部留到查询时、靠列裁剪与向量化执行扛，因此它天然不能承受高频更新；「即席联邦查询」把代价付在每次跨源连接上（主文件 §2.4 已把查询引擎与 OLAP 引擎的分工讲清：OLAP 适合固定查询模式，查询引擎适合即席跨源），推荐的引擎候选是 Trino、典型栈 Trino + 多 Connector，也就是说它属于「由查询引擎而不是 OLAP 引擎承担」的选项，成立的判据是查询低频且对延迟不敏感。同理，「多维分析」推荐的引擎候选是 StarRocks / Doris、典型栈 StarRocks + Iceberg，按本节的分类它落在「内表聚合 + 外表历史」（3.2.1 + 3.2.2）而不是 Cube 上——把「多维分析」直接读成「建 Cube」是最常见的归类错误。

### 3.4 组合模式：真实系统不会只用一种

**组合一：实时入内表 + 物化视图加速 + 冷数据落外表。** 构成是「Kafka → Flink 攒批 → 主键模型内表（3.2.1）+ 少量 MV（3.2.3）+ 历史分区转外表（3.2.2 / 3.5 冷热分层）」。职责边界：内表承担最新窗口内的写入与点查，MV 承担固定看板的聚合，外表承担历史与合规留存；三者用同一套分区口径衔接。运维代价是「热转冷」要成为常规任务（分区级别迁移 + 校验），且迁移后的查询路径不同、P99 会跳变，需要在上层显式区分。适合的规模：日增 TB 级以内、看板数十个、有明确保留期要求【经验】；数据量小且查询不固定时，随便节省掉 MV 这一层反而更省事。

**组合二：主键模型 + 攒批写入 + 合并资源预留。** 构成是「上游 CDC/消息 → 攒批（3.2.1 的微批窗口）→ 主键模型表 → 后台合并独占一部分资源」。职责边界：攒批控制版本产生速率，主键模型保证更新语义，合并资源保证查询侧不退化；三者是一个闭环，缺一条就会在 3.2.1 的失效点上暴露。运维代价是必须为合并预留资源（这部分资源在监控上看起来长期"空闲"），以及合并策略（何时触发、并发多少）需要按写入峰值调，而不是按平均值调。适合的规模：写 QPS 从几百到几十万都可能成立【经验】，关键不是绝对量而是**版本产生速率与合并能力的比值**。

**组合三：存算分离 + 多计算集群 + 统一表格式。** 构成是「共享存储上的 Iceberg/Paimon 表 + 写集群 + 多个读集群（3.2.7）+ 语义层（3.2.6）统一口径」。职责边界：表格式负责"一份数据多引擎可读"，存算分离负责"读集群按业务升降配"，语义层负责"多消费方一个口径"；三者叠加后，隔离靠加集群、口径靠语义层，都不需要复制数据。运维代价是缓存命中率与对象存储请求成本要看住（否则弹性收益会被请求费吃掉），以及语义层与物理表的映射错误会静默传播到所有消费方。适合的规模：多业务线、有明显峰谷、且已经有多引擎（批/流/交互）诉求的组织。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 用 OLTP 做 OLAP | 分析查询与业务事务跑在同一实例；慢查询告警与业务超时同时出现；DBA 在给分析 SQL 加缓存 | 行存要读整行、无裁剪，一条大聚合就可能吃光缓冲池，把事务延迟一起拖崩 | 数据就在那里、连上就能查；分离要建新链路，短期成本更高 | OLTP + OLAP 分离；分析流量走列存副本或 CDC 到 OLAP |
| 过度依赖 Cube | 每个新看板都要求"再建个 Cube"；刷新窗口不断变长；存储增长快于数据增长 | 存储与构建时间随维度基数的乘积增长，而查询只用到其中少数组合 | 把 Cube 当成"什么都快"的通用加速器，而不是穷举预计算的特定结构 | 统计真实出现的维度组合，只预计算它们；改用 MV（3.2.3）并按命中率淘汰 |
| 忽视数据倾斜 | 少数 Tablet / 分桶明显大于其他；查询 P99 远高于 P50；某几个节点磁盘先满 | 并行度被最慢的那个分片决定，集群里其余节点在等它；扩容也不成比例地改善 | 分桶键选得随意（用了低基数列），或数据本身长尾且未做打散 | 用高基数列分桶；长尾键用随机分桶打散；JOIN 时让分桶键与 JOIN 键对齐 |
| 未优化 Join | 大表 JOIN 大表；执行计划里出现全量 Shuffle；内存溢出告警集中在 Join 算子 | Shuffle 把网络变成瓶颈，且内存不足时落盘进一步放大延迟 | 默认认为"优化器会搞定"，而代价模型依赖统计信息，统计过期就会选错 | 小表走 Broadcast（注意内存上限）、同分桶键走 Colocation Join；先 ANALYZE 再看计划 |
| 实时写入不当 | 写入批次极小且频率极高；查询 P99 缓慢上升而数据量没变；合并任务长期积压 | 版本数爆炸带来读放大与写放大，且会自我强化（合并慢 → 查询慢 → 负载高 → 合并更慢） | 「越快越好」的直觉；把小批量高频写入当成"更实时" | 攒批写入，按引擎的合并能力定窗口（常见量级为秒级到数十秒）【经验】；监控合并滞后 |
| 未做冷热分层 | 全部数据都在 SSD / 高配存储；成本随保留期线性上涨；而查询集中在最近一段时间 | 为几乎不查的数据付最贵的存储，且它同时拖长备份、迁移与重建索引的时间 | 分层要动数据生命周期任务，属于"不紧急"的工作，一直往后排 | 按查询频率与保留期分层：热数据内表 SSD，冷数据对象存储 / HDD 或外表 |
| MV 只建不淘汰 | MV 数量持续增长；每个 MV 的调用次数无人统计；上游写入变慢 | 每条上游写入要维护全部相关 MV，命中率低的 MV 只贡献写放大与存储成本 | 建 MV 有明确诉求（某次查询慢），删 MV 没有诉求，于是只增不减 | 定期统计命中次数/维护成本，命中率为零的 MV 直接下线；设 MV 数量上限并走审批 |
| 语义层被绕过 | 看板数字与裸 SQL 手算不一致；查询日志里有大量非语义层来源的查询 | 口径副本重新出现，"唯一真相"退化成其中一个选项，且差异无法自动发现 | 语义层表达不了复杂查询，业务方只能绕；绕过没有成本 | 统计绕过占比并作为治理指标；把高频绕过形态补进语义层而不是禁止绕过 |

**最危险的三条，在生产中这样暴露。** 第一是「实时写入不当」：它的危险在于**症状与直觉相反**——写入越"实时"，版本积压越快，而团队看到的是查询变慢，于是第一反应是加缓存或加节点，掩盖了合并滞后这个真实原因。它的暴露方式通常是某次大促或补数之后 P99 突然台阶式上抬，且降不下来。识别方法是看「未合并版本数」与「合并任务滞后时间」这两个指标，而不是看 QPS。第二是「忽视数据倾斜」：它的危险在于**扩容无效**——加节点只增加分片数，最慢分片的绝对工作量没有变小，所以钱花掉、P99 不动。第三个是「用 OLTP 做 OLAP」：它的危险在于**故障是跨系统的**——分析 SQL 吃掉的资源会以"业务接口超时"的形式暴露，排查方向天然会被引向应用侧，而根因在另一条查询上。

**这些反模式会互相掩盖。** 「MV 只建不淘汰」会掩盖「实时写入不当」——两者都表现为写入变慢，而 MV 的维护开销更隐蔽；「未做冷热分层」会掩盖「忽视数据倾斜」——冷热不分时，慢分片往往被归因为"数据太多"；「未优化 Join」与「忽视数据倾斜」几乎总是同时出现，因为大表 JOIN 的 Shuffle 结果是否倾斜，取决于 Join 键的分布，而这一点只有在计划里才看得见。因此诊断顺序应当是：**先看执行计划（有没有 Shuffle、有没有裁剪），再看分片分布（有没有倾斜），最后才谈加资源**——反过来做，通常得到的是一个更大但仍然倾斜的集群。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单机 → 集群 | 单机列存 + 全量扫描 | 扫描量超过单机 IO 上限，加盘不如加节点 | MPP 分区分桶 + 分布式执行 | 必须选分桶键与分区键，这一步不可事后无痛修改 |
| 明细查询 → 看板固定 | 每次现算聚合 | 重复计算消耗集群，看板刷新互相挤占 | 物化视图（3.2.3） | MV 带来写放大与新鲜度延迟，需要定刷新间隔与淘汰机制 |
| 维度组合穷举 → 组合不定 | Cube / Rollup（3.2.4） | 维度或基数一涨，存储与刷新时间指数上升 | 按需预聚合 + MV 覆盖真实组合 | 需要先有查询日志统计，短时间看板延迟会上升 |
| 批量导入 → 秒级可见 | 定时批量导入 | 可见性延迟大于决策周期 | 实时 OLAP（3.2.1 主键模型 + 攒批） | 引入版本与合并，集群必须为合并预留资源；删除语义变复杂 |
| 数据量超过本地盘经济容量 | 全量内表（SSD） | 成本随保留期线性上涨，而查询集中在最近一段 | 冷热分层 + 外表查询（3.2.2） | 热转冷要成为常规任务；冷查询 P99 跳变需要在上层区分 |
| 单集群 → 多业务隔离 | 一套集群多租户排队 | 一个业务的突发查询拖慢其他业务；升降配要整体做 | 存算分离 + 多计算集群（3.2.7） | 缓存命中率与对象存储请求成本成为新的核心指标 |
| 高并发点查比例上升 | 外表承载热数据 | 点查延迟由网络往返与文件解析决定 | 热数据入内表，外表只留冷数据 | 需要定义"热"的时间边界，并维护热转冷任务 |
| 多消费方口径分裂 | 各消费方各写 SQL | 同一指标不同数字，无人能裁决 | 指标语义层（3.2.6） | 要把现有 SQL 反推成指标定义，且必须解决绕过问题 |

**跃迁的共同规律**：上表八次跃迁里有四次是「把绑在一起的东西分开」——冷与热分开、计算与存储分开、口径与物理表分开、点查与扫描分开；唯一方向相反的是「维度组合穷举 → 组合不定」，它把穷举的预计算收回到按需计算。原因是预计算的收益与「查询形态的稳定性」成正比，而规模跃迁几乎总带来查询形态变化（新业务、新看板、新消费方），于是旧预计算的命中率下降、维护成本不变，净收益转负。方向性结论是：**预计算只应覆盖已被日志证明稳定出现的查询形态**，每一次跃迁之后都要重新验证这句话。

### 3.7 自检清单

- [ ] 表的分区键、排序键、分桶键分别服务哪一类查询？能否各自指出一个真实的慢查询案例？
- [ ] 「未合并版本数」与「合并任务滞后时间」是否被监控？合并落后时会不会告警？
- [ ] 是否存在大表 JOIN 大表的执行计划？统计信息最近一次 ANALYZE 是什么时候？
- [ ] 分桶键的基数是多少？最大的桶与最小的桶相差几倍（倾斜度量）？
- [ ] 每个物化视图的命中次数是多少？有没有命中率接近零却仍在维护的 MV？
- [ ] 热数据与冷数据是否分层？最后一次「热转冷」是什么时候，冷数据还能被查吗（延迟是多少）？
- [ ] 若采用存算分离，本地缓存命中率是多少？冷读查询占比与单次冷读增量延迟分别是多少？
- [ ] 是否存在以高并发点查为主、却落在 Lakehouse 外表上的查询？内表与外表点查 P99 的差距是多少？
- [ ] 同一指标在两个消费方（看板 / API / Agent）算出的值是否一致？不一致时以哪一份为准、谁来裁决？
- [ ] 绕过指标语义层发出的查询占比是多少？这个比例在上升还是下降？
- [ ] 写入的攒批窗口是多少？把它从当前值减半，合并能否跟上（用合并滞后指标验证）？
- [ ] 云账单里「存储容量」与「对象存储请求数」的占比各是多少？后者是否在超预期增长？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 可见性延迟是硬指标、写入带更新 | 实时 OLAP（3.2.1，主键模型 + 攒批） | 更新靠追加版本 + 合并实现，实时性上限由合并能力而非写入能力决定 |
| 一份数据多引擎消费、以扫描聚合为主 | Lakehouse 外表（3.2.2） | 边际成本是"多一个 reader"而不是"多一份数据" |
| 查询形态已稳定、重复度高 | 物化视图（3.2.3） | 把重复计算消除一次，比优化 N 次查询更省 |
| 维度少、基数低、组合必须穷举 | Cube / Rollup（3.2.4，谨慎） | 延迟与数据量脱钩，但存储随维度基数的乘积增长 |
| 峰谷明显、多业务要隔离读 | 云原生 / 存算分离（3.2.7） | 弹性与数据量解耦，代价是缓存命中率成为新的性能上限 |
| 多消费方需要同一口径 | 指标语义层（3.2.6） | 口径只保留一份映射，才可能只有一个答案 |
| AI 检索带标量过滤 | OLAP + 向量索引（3.2.5） | 过滤与近邻在一次计划里协同，避免两阶段拼接丢结果 |

> 本节小结：决定 OLAP 模式选择的唯一那条约束，是**「每一次让查询变快，都要在写入时或后台预先付掉代价」**——列存付在排列式重写上、主键模型付在版本合并上、MV 与 Cube 付在预聚合与维护上、外表与即席查询付在每次查询的现算上。所谓选型，本质是判断这笔钱该由谁在什么阶段支付；当工作负载的变更频率超过预计算能承受的频率时（查询形态不稳定、写入频率高于合并能力、维度基数漂移），预计算就从资产变成负债，这是 3.5 与 3.6 反复出现的同一个机制。
>
> 💡 **思考锚点**：翻出你集群的查询日志，数一下每个物化视图与 Cube 覆盖的查询占比——本节说「预计算只应覆盖已被日志证明稳定出现的查询形态」，你有几个命中率接近零却仍在刷新的 MV？把它们的刷新资源收回，能不能让你现在那个「合并任务滞后时间」降下来？
