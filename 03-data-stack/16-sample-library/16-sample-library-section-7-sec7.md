## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自建样本库 / 开源标注工具 + 自建资产层 / 商业标注平台 / 标注外包服务 / 纯人工整理"打分是常见做法，但它有三个结构性问题：

① **同一列在不同处境下方向相反**——"标注界面好用"对**非工程角色参与标注**的团队是必需，对**标注量小、口径稳定**的团队是**风险**（越容易标，越容易在没有口径的情况下标）。
② **打分表隐含"这些选项互斥"**，而真实做法是组合（**开源标注工具 + 自建回填与切分 + 外包做批量**是常见组合）。
③ **最关键的判据不是可打分的维度，而是门槛**——**"回填能不能按时点"**与**"切分能不能防三种泄漏"**这两条是门槛。**一个标注体验极好、但回填用最新值的平台，会让你的全部离线结论建立在一个虚高的基准上。**

**本节采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| **回填可否做到点时** | 它能不能按 `event_time` 取历史特征值、且历史保留期够？ | **这是门槛不是权重**——不能则全链路离线结论虚高 |
| **切分可否防三种泄漏** | 实体 / 时间 / 近重复检测是内置还是可插？ | 不防 → 结论乐观且**无法察觉** |
| **样本元数据可否导出** | 五个字段能不能导出成不依赖产品的材料？ | 不能 → 换平台要重建样本资产 |
| **污染检查与台账** | 有没有跨集比对与**来源登记**能力？ | 无台账 → 间接污染不可发现 |
| **口径的载体** | 边界案例能不能写进任务配置（而不是文档）？ | 不能 → 一致性靠口头交接，规模无法扩大 |
| **运维承接** | 谁维护口径、谁做检查、谁负责样本增补？ | 本主题人力是主项，**没有承接人的方案会在样本衰减后失效** |

**这 6 条里，前两条是门槛（不满足直接出局），后四条是权重的输入。**

**还有一条隐藏得更深的缺陷**：打分表的每一列都是**方案属性**，没有一列是**我的约束**。约束决定候选的上界，属性只在候选之间分配名次——所以本节的第一张表不是评分表，而是一组能淘汰候选的判据——**6 条里没有一条问"它有多好"：4 条问能力（"能不能 / 有没有"），第 2 条问形态（"是内置还是可插"），第 6 条问承接人（"谁维护、谁检查、谁增补"）**。**因此本节后面每一处排序都带一列依据**：§7.6 的矩阵带"不选它的原因"、§7.8 的处境表带"关键理由（机制层面）"——**凡是要给出顺序的地方，都由相邻列给出机制依据**；给不出依据的顺序，就是把场景相关的结论写成了绝对结论。

**判据的使用顺序**：先答第 1、2 条（两条门槛，它们决定候选出不出局），再答第 6 条（运维承接，它决定方案落地后会不会在样本衰减时失效），最后才用第 3、4、5 条在剩下的候选里分配名次。**顺序反了最常见的后果**是：先按第 5 条（口径的载体）挑了标注体验最好的平台，回头才发现它的回填用最新值——**此时迁移的成本已经按"以季度计"来算了**（§7.7 表的第一行与第四行）。**第二常见的后果**是漏答第 6 条：一个门槛全过、口径载体也合格的方案，若没有承接人，会在一年内退化成"没人碰的样本集"（§7.3.4）。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| **纯人工整理（表格）** | 最简 | 样本以表格形式在各人手里 | 样本量极小、一次性 | **无血缘、无版本、不可复现** |
| **开源标注工具 + 自建资产层** | 现实默认 | 工具管标注，回填 / 切分 / 检查自建 | 多数团队 | 资产层要自己建（**而它才是门槛所在**） |
| **商业标注平台（含资产层）** | 成品能力 | 标注 + 样本库 + 版本 + 检查一体 | 要快上线、非工程角色要参与 | **回填与切分的口径由产品定**，需压测 |
| **标注外包服务** | 人力补充 | 把标注执行外包（口径由你定） | 批量标注、内部人力不足 | 口径仍需你维护；**质量靠抽检** |
| **弱监督 / 主动学习框架** | 成本优化 | 规则投票 + 按信息量分配人力 | 标注预算受限的团队 | 需留出集估权重；**会改变训练集分布** |
| **ML 平台的样本模块** | 复用既有 | 复用 ML 平台的样本与实验管理 | 已有 ML 平台的团队 | **回填与切分未必可控**（它常按平台自己的约定） |

**这六个候选其实分三族**：

- **生产族**（开源工具、商业平台、外包服务）——**解决"标得出来"**，差别在**口径的载体与人力弹性**。
- **资产族**（自建资产层、ML 平台的样本模块）——**解决"样本是什么、什么时候看到的"**，差别在**回填与切分的可控性**。
- **优化族**（弱监督 / 主动学习）——**解决"省人力"**，差别在**是否改变训练集分布**。

**族内可替换，跨族不可换**：生产族内部换代价可控（**前提是样本元数据能导出**）；从生产族换到资产族**不是替换而是补齐**；而**优化族建在资产族之上**——**回填与切分没做对时，省下的标注人力会被虚高的指标吃掉**（更多样本让错误结论更"显著"）。

**选型的第一刀是选族，不是选产品**：跨族的差别是机制差别（回填归谁、切分怎么切、口径写在哪、增补谁触发），同族内部的差别多数是接口、许可与运维形态的差别。因此**同族内换方案，代价通常以周计；跨族换，代价以月或季度计**（§7.7）。表里"典型使用者"一列常被当成免责声明，其实它是判据：**一个方案被多数团队选，通常是因为它在门槛上不出错，而不是因为它在某个维度得分高。**

**"主要代价"是这张表里最该读的一列**——它列的不是"功能少"，而是**这个方案会把哪一类错误引入你的链路**：无血缘与无版本（结论不可复现）、回填与切分的口径由产品定（**两条门槛不在自己手里**）、质量靠抽检（引入有偏采样）、改变训练集分布（评测集必须另用随机抽样）。**把这一列按"它会把哪类错误带进来"读一遍，就能看出 §7.1 的门槛检查为什么必须排在选择之前**：门槛检查问的正是"这类错误会不会进到我的结论里"。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 回填的归属：你的脚本、产品的约定，还是没有回填

**机制是什么**：特征值的取得方式只有三种——**你的回填脚本**（连接条件含时点约束）、**产品按自己的约定取**（通常是"当前最新值"）、**没有回填概念**（样本自带特征副本，且不知道是什么时点的值）。

**它在各候选中的实现差异**：自建资产族**可以完全控制连接条件**（也能把唯一入口做成 CI 检查）；商业平台**按它的约定取**（能不能配时点语义取决于产品，**而这是压测时最该问的一句**）；纯人工整理的样本**特征值往往是"当时导出的那一份"**——它的时点不明，且**从样本本身看不出来**。

| 入口 | 谁决定连接条件 | 时点语义可查否 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建回填脚本（唯一入口） | 你（写死在脚本里） | 可查（脚本里有没有 `feature_ts <= event_time`） | 脚本被绕过——出现了第二处组装路径 |
| 商业平台的样本模块 | 产品（按它自己的约定取） | 只能压测（问它能不能配时点语义） | 约定其实是"当前最新值"，而界面上看不出来 |
| 纯人工整理的表格 | 导出那一刻的那个人 | 不可查（连"这是哪个时点的值"都不知道） | 样本看起来完整，时点已永久丢失 |
| 无回填（样本自带特征副本） | 产出样本的那一步 | 不可查 | 副本是"生成时的值"，与 `event_time` 无绑定 |

**由此必然导出的性质**：因为**穿越会让离线指标更好看**，所以**回填错了不会引起任何怀疑**——它表现为"模型效果好"，而团队会继续在此基础上做一切决策（选型、调参、扩量）。**这条性质决定了回填的归属是本节最硬的一条门槛**：**它不可观察、只能机械检查，因此必须在自己手里。**

**公开证据**：主文件 §1.4 把"样本库 + 特征回填"单独记为一个阶段（【公开】，主文件 §1.4 的年份条目），也就是说回填的归属是这一阶段的分界，而不是某个产品的功能差异。特征平台一侧有具名实现可核：`02-data-science/01-feature-store/01-feature-store.md:112` 把 2017 年记为"Uber 提出 Michelangelo Palette——公开披露最早的生产级特征存储"，该主题 `01-feature-store-section-3-sec3.md` 的 `真实使用` 进一步给出 Uber Michelangelo Palette 与 Feast 的离线存储 + `materialize` 两个具名形态，另有 Tecton 一行（主打实时特征视图与流式聚合）（【公开】，同上两文件）。同主题 `01-feature-store-section-7-sec7.md` 还给出一句与本单元同源的判据——"**Point-in-Time 是取数协议，不是平台功能**"，即它不随采购预算增长（【公开】）。本主题这一侧的证据是 §4.3 工具链把"特征回填"一格的选型要点写成"看**历史保留期**与**时点精度**"，§4.2（3）把实现分成"从特征历史表按 ts 取"与"从特征快照表按 ds 取"两种并各自写明边界，§5.2 把这一方向判为全节唯一的 L1（【公开】，本主题 §4.2、§4.3、§5.2）。**各产品"能否配时点语义、保留期有多长"请以其官方文档当前版本为准**——本节不引产品文档作据。

**失效条件**：当"离线好、线上差"的差距持续存在且无法归因时，先查回填——**而不是继续调模型。**

#### 7.3.2 切分的归属：三种检查，还是只做一种

**机制是什么**：切分是**按规则脚本切**（可跑三种泄漏检测），还是**按产品的默认切**（随机切，不管实体与时间）。

**它在各候选中的实现差异**：自建族**三种检测都能跑**；平台族**通常只做随机切分**（对"同一实体多样本"的场景会产生实体泄漏）；ML 平台的样本模块**可能支持按实体或时间切**，但**检测是否内置要核**。

| 切分动作 | 谁决定切法 | 三种检测由谁跑 | 典型失败形态 |
| --- | --- | --- | --- |
| 自建切分脚本（唯一入口） | 你（规则写死 + 种子 + 快照） | 你（三脚本进 CI，失败即阻断） | 新鲜感过去后有人手工改了一版切分而没留快照 |
| 平台的默认切分 | 产品（多半是随机切） | 通常没有，要自建 | 实体交集不为零，而界面上显示"已完成切分" |
| ML 平台的样本模块 | 平台（可能支持按实体或时间） | 是否内置要核 | 按实体切了，而时间与近重复两项无人跑 |
| 手工切（导出后分文件） | 切的人 | 没有 | 结论不可复现——连"上一版是哪个文件"都答不出 |

**由此必然导出的性质**：因为**三种泄漏各自有确定的检测方法**（§2.2），所以**"防泄漏"不是能力问题而是配置问题**——**而它的收益（结论可信）与成本（几行检查代码）严重不对称**。**这条性质说明：任何"只能做随机切分"的方案，在"一个主体贡献多条样本"的业务上都不合格。**

**公开证据**：本主题这一格**没有可点名的产品实现**——§4.3 工具链把"切分与快照"一格写成"自建（脚本 + 快照表）或 ML 平台"，并明写选型要点是"看**三种泄漏检测是否内置**，只做一种的不够"（【公开】，本主题 §4.3）；§3.2.7 的 `真实使用` 已先声明"产品侧只到这一层，平台族的默认切分行为不可核"。可具名的是**算法侧与评测侧**：跨集近重复的现实做法是"向量近似 + 抽样"（本主题 §4.2（4）的三条 SQL 与"失败即阻断"），其算法族在全书他处被具名为 MinHash / LSH——`01-modeling/03-data-vault/03-data-vault-section-8-sec8.md` 记"用 MinHash 做近似相等"，`11-cross-cutting/01-data-quality/01-data-quality-section-8-11-6-数据质量监控规则与告警.md` 记"MinHash / LSH 估算集合相似度"（【公开】，上述两文件；本主题 §4.2）。评测侧的可照做量级在 `02-data-science/07-eval/07-eval-section-4-sec4.md`：抽一批 Holdout 用户、在曝光表里逐个查、应没有任何曝光记录（该处的抽查量在那份材料里标为【经验】）；同主题的 `07-eval-section-3-sec3.md` 把"评测集被反复用于优化后就不再是独立的测试集"列为反模式（【公开】）。**按实体与按时间的切分该怎么配，请以你所选平台官方文档的切分章节为准。**

**失效条件**：当"评测指标明显高于线上表现"而鼓捣不出原因时，先跑三种检测。

#### 7.3.3 口径的载体：任务配置、共享文档，还是个人记忆

**机制是什么**：口径写在哪——**任务配置（含边界案例）**、**共享文档**、还是**在人的脑子里**。

**它在各候选中的实现差异**：开源工具与平台族**都能把边界案例写进任务**（区别是操作是否方便）；外包服务**要求你把口径交出去**（因此载体必须能被外部读懂）；而纯人工整理**根本没有载体**（口径随人走）。

| 载体 | 改一次口径要动什么 | 分歧可见否 | 典型失败形态 |
| --- | --- | --- | --- |
| 任务配置（含边界案例） | 改配置并发布一版（可回滚） | 可见（抽样重复标注算 κ 与分歧分布） | 配置停在引入时那一版，新样本落在它没覆盖的边界上 |
| 共享文档 | 改文档（与任务的对应靠人维护） | 可见但要人去对 | 文档更新了，任务里还是旧口径；没人知道哪份生效 |
| 口头交接 / 人的记忆 | 重新口头交接一遍 | 不可见 | 每加一个人就重新校准一遍，规模无法扩大 |
| 无载体（样本散在各人手里） | 无法回答"当时的口径是什么" | 不可见 | 历史样本的口径**事后补不回来**（只能标"未知"） |

**由此必然导出的性质**：因为**分歧集中在"口径未覆盖的边界"上**（§3.2.1），所以**口径的载体决定了一致性**——**载体是任务配置时，补一个边界案例就能立刻改善一致性；载体是文档时，改动与任务的对应关系靠人维护；载体是记忆时，规模无法扩大。** 这条性质给出一条排序：**先写边界案例，再谈多人标注**。

**公开证据**：本主题 §4.3 把"标注平台"一栏的选型要点写成"看**任务配置是否支持边界案例**与**一致性计算**"（【公开】，本主题 §4.3），也就是本节题眼那两件结构物；§6.1 的案例给出的正是任务配置五部分的完整形态与一条失败教训——"第一版把口径写在一份共享文档里"，结果是"分歧恰好集中在文档没覆盖的情形上"（【公开】，本主题 §6.1）。书内可点名的载体有：Label Studio（§4.3 工具链、§6.1 案例；`07-agent-evolution/02-feedback-loop/02-feedback-loop-section-8-sec8.md` 记其为开源、由 HumanSignal 维护、支持多种模态、可自托管）、Argilla（同名工具行，**原生支持偏好数据**，判据是"界面能不能把『打平』与『弃答』记为合法选项"）、Doccano（本主题 §4.3 与 `01-modeling/05-ontology-modeling/05-ontology-modeling-section-8-sec8.md` 的工具行）（【公开】，上述各文件）。全书他处还给出这条流水线的具名形态——`07-agent-evolution/02-feedback-loop/02-feedback-loop-section-4-sec4.md` 记"任务分片 → 多人重复标注 → 黄金集校验 + 一致率 → 仲裁，指南版本化"，并给出两条选型判据"能不能自建（数据不出域）、能不能做冗余标注 + 黄金集"（【公开】）。**任务配置到底支持哪些配置项，本节不引产品文档作据，请以各产品官方文档当前版本为准。**

**失效条件**：当新人标注需要"跟着老人标两周"时，说明口径的载体不合格。

#### 7.3.4 样本衰减的归属：谁负责增补

**机制是什么**：样本会随时间失效（§4.6），**而"谁来增补"决定了样本集是活的还是死的**。

**它在各候选中的实现差异**：外包服务**能按需增补**（只要你愿意继续付费），但**它不负责判断"该重标哪些"**（那是口径与漂移的问题）；自建族**可以按漂移监控触发增补**（三轴指标 → 触发重标 / 增补）；平台族**通常只提供存储与版本，不提供触发机制**。

| 触发信号来源 | 谁判断"该重标哪些" | 信号可观测否 | 典型失败形态 |
| --- | --- | --- | --- |
| 漂移监控三轴（特征 / 标签 / 关系） | 你（按轴定位到桶，再定动作） | 可观测（超阈值即告警） | 只看前两轴，漏掉"关系变了"这一主因 |
| 效果下降的体感 | 最先抱怨的那个人 | 不可观测（等到体感时已晚） | 效果下降被归因为"业务变难了"，样本层从未被怀疑 |
| 外包服务按需增补 | 你（外包不动口径） | 需你主动发起 | 一直在增补，而增补的正是模型已能判的那一类 |
| 无触发（样本标完就放着） | 没有人 | 不可观测 | 用一年前的样本反复训模型，失效静默发生 |

**由此必然导出的性质**：因为**样本失效是静默的**（不报错、只是效果慢慢差），所以**"增补"必须有触发信号**——**没有漂移监控时，增补只能靠"感觉效果变差了"，而彼时团队通常已经怀疑过模型、怀疑过业务，最后才会怀疑样本。** 这条性质决定了"漂移监控三轴"（§4.5 模板 3）不是可选项。

**公开证据**：本主题 §4.3 工具链把"漂移监控"一行写成"复用质量平台（Ch11 §01）"，选型要点是"看是否**同时覆盖特征侧 / 标签侧 / 关系侧**"（【公开】，本主题 §4.3、§4.5 模板 3）；§4.6 把样本的第二笔账写成"样本的有效期 ≈ min(业务口径稳定期, 分布稳定期)"，并给出判据"重标 / 增补应当被算进常态预算，而不是当成一次性项目"（【公开】，本主题 §4.6）；§4.8 的 10 → 100 阶段把"先坏的是样本的时效性"写成本阶段的特征（【公开】，本主题 §4.8）。分布稳定性一侧有一组全书通用的档位可引——PSI 的常用分档（小于 0.1 视为无漂移、0.1–0.25 轻度、大于 0.25 严重），出处是 `11-cross-cutting/01-data-quality/01-data-quality.md:194`（Ch11 §01 数据质量主文件 §2.2 的 PSI 条目，该处自己标注为"阈值经验值"）（【经验】，同上文件；同族档位另见 `07-agent-evolution/02-feedback-loop/02-feedback-loop-section-8-sec8.md:555`"PSI > 0.25 显著、0.1~0.25 中等"）。**"触发信号该定在哪个阈值上"没有可引的统一数字**——它随业务季节性变化，本节不给具体阈值，请先用三轴各自跑一段基线再定档。

**失效条件**：当团队用一批一年前的样本反复训模型、并把效果下降归因为"业务变难了"时，说明增补没有触发机制。

#### 7.3.5 元数据与证据的归属：在你的表里、在产品库里，还是在人的表格里

**机制是什么**：样本资产的"证物"只有三类——样本的五个元数据字段（时点 / 来源 / 快照 / 切分 / 血缘）、各类检查的结果（泄漏 / 污染 / 一致性）、以及来源台账。**它们在谁手里决定三件事**：换平台时能不能带走、结论能不能复现、出了事能不能回答"当时是什么状态"。**§7.1 的第 3 条判据（样本元数据可否导出）问的就是这一件事**——它在 §7.3 的前四个单元里没有对应机制单元（那四个讲的是处理机制，这一个讲的是资产与证据的存放位置），因此单列在此；第 4 条判据里的"来源登记"也落在本单元。

**它在各候选中的实现差异**：

| 证物掌在谁手里 | 元数据可否导出 | 检查结果可迁移否 | 典型失败形态 |
| --- | --- | --- | --- |
| 你的样本表 + 快照表（自建） | 可（导出即一张表） | 可（检查脚本与运行记录都在自家仓里） | 表结构改了而检查脚本没跟着改，历史结论与现行口径对不上 |
| 产品库 / ML 平台的样本模块 | 要看有没有导出接口 | **多数不可迁移** | 换平台要重导数据并重建口径，历史检查结果作废 |
| 各人的导出文件 | 不可（要先知道有哪些文件） | 不可 | "上一版训练用的是哪批"无法回答 |
| 只存在任务配置里 | 随任务一起被删 | 不可 | 任务下线后历史标注成了"来历不明的数据"，且**补不回来** |

**由此必然导出的性质**：因为**元数据的缺失只在需要它的时候才暴露**（要复现一次评测、要回答一条样本当时看到了什么、要向外部举证来源），所以它是一笔**收益完全滞后的成本**——引入它当期的代价是"多写几列、每次写入多一处"，而它的价值要等到第一次审计、第一次污染追问、第一次换平台时才兑现。**这条性质决定了它必须被做成"必填"而不是"可补录"**：字段一旦不是必填，它就会在补录时被跳过，而**"谁标的、当时的口径版本"这类字段事后推不出来**（§4.4 把这条写成存量迁移里最硬的约束）。第二条性质是**归属决定迁移代价的形状**：放在自家表里时迁移是"导出一张表"，放在产品库里时迁移是"重导数据 + 重建口径 + 历史检查结果作废"——这正是 §7.7 把"平台锁定之后的收回"列为八条迁移里最贵一条的原因：**丢失的不是数据，是"过去那些结论是否可信"的依据。**

**公开证据**：本主题 §4.1 把"定五个元数据字段"写成八步里的第一步，理由是"它是一张表的改动，而它是后面所有机制（回填、切分、污染检查）的挂载点"（【公开】，本主题 §4.1）；§4.3 工具链把"样本存储与血缘"一格的选型要点写成"看**能不能导出**样本元数据（锁死则迁移代价高）"（【公开】，本主题 §4.3）；§4.4 的存量迁移表把"散在各人手里的 CSV / 表格"的处置写成"收进样本库 → 补元数据（能补的补，不能补的标『未知』）"，并明写"**不要假装补全**：`event_time` 可以从数据里推，『谁标的、当时口径版本』推不出来"（【公开】，本主题 §4.4）。台账这一半的书内对照物是 `04-data-assetization/08-data-catalog/08-data-catalog-section-7-sec7.md` 把"数据契约 / 资产登记台账"记为一类治理载体、并说明它"以协议而非页面为核心"（【公开】）；其产品化形态在全书他处有名可核——数据集文档化的经典出处是 Datasheets for Datasets 与 Model Cards for Model Reporting，工程化版本是 Data Provenance Initiative 对公开语料做来源与许可审计，治理侧的工业实现是 Netflix 的 Data Card 与 Uber Databook 的数据评分 / 数据卡（【公开】，`11-cross-cutting/09-data-lineage/09-data-lineage-section-5-ai.md`、`11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-8-11-7-数据治理体系融合与实践.md`）。**跨集比对能力的产品化实现本书未给具名**（§4.3 已写"多数只做近重复比对"），这一项按【经验】处理。

**失效条件**：当团队答不出"上一版训练用的是哪批样本、哪一版口径"时，证物就不在自己手里——此时该补的不是新工具，而是把字段改成必填、并把检查结果落成可导出的记录。反过来，若这块样本只用于一次性模型、既不再复现也不对外举证，本单元的收益会显著变小（但 §7.3.1 与 §7.3.2 两条门槛仍然成立——它们关乎结论本身对不对，不关乎**举证**）。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| **生产族** | 标注人力（或外包费用） | 口径维护、一致性诊断、外包质量的抽检 | 随**样本数 × 任务数**增长 |
| **资产族** | 人力（回填 / 切分 / 检查的维护） | 特征历史保留期的存储成本、检查脚本的持续运行 | 随**样本跨度与样本量**增长 |
| **优化族** | 框架集成 + 迭代重训 | **分布偏移带来的评测重建**（评测集须保持随机抽样） | 随**迭代轮次**增长 |

**成本函数的三条判据**：

① **生产族的成本随时间线性**，且**边界样本永远要人标**（无论弱监督多强）——**因此它的下界不是零**。
② **资产族是"台阶 + 低斜率"**——建回填与检查是台阶，之后维护便宜；**但"特征历史保留期"是一笔随跨度增长的存储成本**（要提前与上游谈）。
③ **优化族的成本藏在"分布偏移"里**——它省下的标注人力，可能被"评测集要重建"吃掉；**表面上省得多，实际要看评测重建的频率**。

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：N = 样本数   n_label = 需人工标注的比例   t = 单条标注时长   c_h = 人力单价
    N_e = 边界样本数（永远要人标）   S = 样本跨度（月）   c_keep = 单位跨度的历史保留成本
    K = 主动学习迭代轮次

生产族：  Cost_prod(N, n_label) = N × n_label × t × c_h + N_e × t × c_h
                                    ↑ 弱监督与主动学习压的是前者；后者压不动
资产族：  Cost_asset(S)         = 回填与检查的维护人力 + S × c_keep
                                    ↑ 随跨度线性 —— 这是"要提前与上游谈"的那一笔
优化族：  Cost_opt(K)           = 迭代重训 + K × 评测重建成本

反直觉的一条【推算】：当 N_e × t × c_h 在预算里占比很大（边界样本多）时，
   继续投入弱监督的回报会迅速下降 —— 因为边界样本恰恰是规则判不了的那些。
   此时正确的动作是：把边界样本单独管理（难例库），并提高它们的标注优先级。
```

**另外两条量级推导（都可换参数重算）**：

- **重复标注的诊断成本**【推算】。人力口径同 §6.1（"抽出比例 × 1"的额外人力），这里只把它落成式子：额外人力 ≈ `N × p_dup × t × c_h`（推导链：样本数 × 抽出做重复的比例 × 单条时长 × 人力单价）。**这个数本身多大不是重点，重点是它只换回"分歧可见"、不产出任何标签**——因此它是**诊断成本，不是生产成本**，不该进标注预算去和产出比；由此推出的设计约束（一致性只能**抽样重复**，全量重复换回来的是同一件事）同 §6.1。
- **跨集近重复比对的代价**【推算】。精确比对的计算量随 `N_train × N_test` 增长（推导链：两组样本数的乘积），而向量近似 + 抽样把它降到与"抽样条数 × 候选集规模"同阶。**这条推导决定了它只能用近似而不是精确比对**：样本量涨一个数量级时，精确比对的代价涨两个数量级，而近似的代价与库规模同阶增长。**它同时解释了 §4.3 为什么把"污染检查"一格的选型要点写成"是否含来源台账"而不是"比对得多准"**——比对准不准是算力问题，台账有没有是机制问题。

**这个式子的用法**：**先量 `n_label` 与 `N_e`**——前者决定弱监督值不值得投，**后者决定你的人力下界在哪**。**边界样本是弱监督的边界**：它们规则判不了，因此**无论怎么优化，这部分人力都在**。

### 7.5 决策树（每个分支都要有阈值依据）

1. **一个主体会不会贡献多条样本？**
   - **会** → 切分**必须按实体**，且三种泄漏检测都要跑；进入第 2 问。
   - 不会 → 随机切分可接受，但**时间与近重复检测仍要做**。
2. **样本跨度多长（样本最早到现在的时长）？**
   - **超过特征历史保留期** → **先与上游谈保留期**，否则老样本永远回填不出当时的值；进入第 3 问。
   - 在保留期内 → 进入第 3 问。
3. **能不能把回填做成唯一入口并加 CI 检查（按 0.3–0.6 人年的常备投入量级估算【经验】）？**
   - 能 → **自建资产层**（回填、切分、检查都在自己手里）；生产工具可外购。
   - 不能 → 买平台，但**必须压测两条门槛**：回填能否按时点、切分能否按实体与时间。
4. **标注需求里"规则能判"的比例大概多少？**
   - **一成以上** → 值得投入弱监督（先估这个比例再投入）。
   - 一成以下 → 直接用人工标注 + 主动学习分配人力。
5. **要不要对外举证（交付 / 审计 / 对外评测）？**
   - 要 → **来源台账必须自建**（没有任何产品会替你登记"你的数据从哪来"）。

**各分支的阈值依据（为什么分叉点落在这里）**：

- **第 1 问**：依据是实体泄漏的定义——**同一实体的样本跨集出现即泄漏**，因此这一问的答案直接决定"按实体切分"是否必要（§2.2 三种泄漏之一）。判据不是样本量大小，而是**"一个实体在样本里出现几次"的分布**：出现次数全为一，随机切分合法；出现多次，随机切分必然泄漏。
- **第 2 问**：依据是回填的**物理约束**——特征历史保留期由上游（特征平台 / 数仓）决定，**保留期短于样本跨度时，任何工具都回填不出当时的值**（§3.2.6 的代价③）。所以这一问必须在写模型之前问；等到回填失败再问，代价是整批老样本要么作废、要么静默穿越。
- **第 3 问的"0.3–0.6 人年"**：这是【经验】区间，随特征表数量与历史版本数浮动（§6.3 给过这个口径）。它的用法是**区分"能不能常备"**——这个量级意味着它是**常备预算**而不是一次性项目；按项目立项的后果是它会在下一次赶工期里被绕过，而**绕过不报错**。
- **第 4 问的"一成"**：依据是 §7.4 的成本式子——弱监督压的是 `N × n_label` 那一项，而 `N_e`（边界样本）压不动；因此只有当"能规则化的比例"足够高时，省下的那部分才盖得住标注函数的设计与维护成本（§6.2 把这条写成"先估它，再决定投入是否划算"）。低于这条线时，正确动作是"人工标注 + 主动学习分配人力"，而不是继续写函数。
- **第 5 问**：依据是台账的机制位置——**没有任何产品会替你登记"你的数据从哪来"**，而间接污染**没有检测手段**（改写形态不是近重复，比对发现不了，§3.2.8）。所以它不是"产品能力可以替代"的一问：能替代的是比对，不能替代的是登记。

**阈值的诚实说明**：上表的"一成""0.3–0.6 人年"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的比例与排期校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 样本量极小、一次性 | 表格 + 元数据字段 | 开源工具 | 上平台是治理过剩；**但元数据字段仍要写** |
| 样本量大、要多人参与 | 开源工具 + 自建资产层 | 商业平台 | 平台的回填与切分口径要压测 |
| 非工程角色参与标注 | 商业平台（**核边界案例可写性**） | 开源工具 + 培训 | 载体不合格则一致性靠口头交接 |
| 内部人力不足、要扩量 | 外包（**口径自持 + 抽检**） | 弱监督 + 人工 | 外包不负责判断"该重标哪些" |
| 预算受限、样本池大 | 弱监督 + 主动学习 | 纯人工 | **须先估"能规则化的比例"** |
| 已有 ML 平台 | ML 平台的样本模块 + **自建回填与检查** | 全自研 | 平台的回填约定未必按时点 |
| 要对外交付 / 过审计 | 自建（**台账 + 授权链 + 快照**） | 平台（核台账能力） | 无台账则间接污染无解 |
| 样本跨度长（跨年） | 自建 + **先谈历史保留期** | —— | 保留期不足时，任何工具都回填不出当时值 |

**组合的两条次序原则**：① **先把回填与切分收成唯一入口，再谈标注效率**——顺序反了会让"省下的人力"被"虚高的指标"吃掉（§7.2 的族间关系）；② **先把口径的载体做对（边界案例进配置），再扩标注规模**——载体不合格时，加人只会让分歧多样化。

**第三条原则（方向相反但同样重要）**：③ **先把漂移监控建起来，再谈样本增补**——**没有触发信号时，增补只能靠"感觉效果变差了"**（§7.3.4）。

**四个常见组合（各写清职责边界与运维代价）**：

1. **开源标注工具 + 自建资产层 + 外包做批量**（§7.1 已点名的现实默认）。工具管"标得出来"（任务配置 + 边界案例 + 一致性测量），自建资产层管"样本是什么、什么时候看到的"（回填唯一入口 + 切分与快照 + 检查），外包承接批量执行而口径自持。**职责边界：口径与检查归你，执行量可以外购。运维代价：三处都要有人——工具升级、资产层维护、外包抽检；最容易漏的是"外包返回的样本要不要重跑一次泄漏与污染检查"这一步**（它常被当成"已经标好的数据"直接入库，而外包只对标注质量负责，不对你的切分与来源负责）。
2. **弱监督 + 人工 + 主动学习**（优化族的完整形态）。弱监督吃掉"能规则化"的那部分（函数带弃权、聚合权重在留出集上锚定），主动学习把剩下的人力按信息量分配，人工只做边界样本与裁定。**职责边界：三者共用同一份样本表与同一套元数据；但评测集必须另用随机抽样，不能从这三类来源里取。运维代价：多出两个常态动作——标注函数的命中量监控（防腐化）与"每批之后有没有重训"（防退化成一次选完再标）；两个动作都不报错，只能主动查。**
3. **商业标注平台 + 自建台账**。平台提供标注界面、样本存储与版本，台账与污染检查自建。**职责边界：平台能覆盖"标得出来"与部分资产族能力，但它不会替你登记"你的数据从哪来"（§7.3.5）——台账必须自建，且它的字段要能与平台自带的来源字段对上。运维代价：来源信息会有两份，两者不一致时以谁为准要在组合之初就写成约定，否则第一次污染追问就会卡在这里。**
4. **ML 平台的样本模块 + 自建回填与检查**（"已有 ML 平台"的团队最省事的起手式）。平台管样本存储、实验记录与切分入口，回填与三种泄漏检测自建并进 CI。**职责边界：切分入口在平台、检测脚本在你——必须先确认平台的切分动作能不能被你的脚本断言（能，才谈"防泄漏"；不能，就只能把切分也搬出来自建）。运维代价：过渡期会出现"平台说切好了、脚本说还有泄漏"的局面，这时的默认约定应当是"以脚本结果为准"。**

**四个组合的共同点**：**口径、回填、切分、检查这四件留在自己手里，其余可以外购或复用**——它们是"结论是否成立"的判定点，而外包、平台与 ML 平台都不会替你对结论负责。**这也是 §7.2"族内可替换、跨族不可换"在组合层面的读法**：生产族怎么换都行（前提是元数据能导出），资产族与优化族换不动——它们换的不是供应商，是你自己的判定逻辑。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 无回填 → 点时回填 | 离线好线上差 | 建回填脚本唯一入口 + CI 检查 + 重跑评测 | **以月计**，且**离线指标会下降**（还账） |
| 随机切分 → 按实体 / 时间 | 评测乐观但说不清为什么 | 重切 + 三种检测 + 快照管理 | 以周计（**历史结果不可比，要留旧切分快照**） |
| 无元数据 → 有 | 无法回答"当时看到什么" | 补字段 + 存量样本批量标注（**部分字段补不回来**） | 以月计，且**"谁标的 / 当时的口径版本"永久未知** |
| 平台锁定 → 自建 | 换平台要重建样本资产 | 导出元数据 + 重建回填与检查 | **以季度计**，且**历史检查结果不可迁移** |
| 纯人工 → 弱监督 + 人工 | 标注预算不够用 | 写标注函数 + 留出集估权重 | 以月计（**先估"能规则化的比例"再决定**） |
| 无台账 → 有 | 无法回答语料里有无评测题 | 逐个来源补登记 | **以周计建台账，但存量来源的补登最难** |
| 评测集非随机 → 随机 | 评测高而全量低 | 重抽评测集 + 重建基线 | 以周计，**且此前的评测结论不可比** |
| 预标注无抽检 → 有 | 修正比例低而被当成模型好 | 补未修正批的独立重标 | 以周计 |

**一条硬结论**：八条里最贵的是**"平台锁定之后的收回"**——不只是元数据重建，而是**历史检查结果（泄漏 / 污染 / 一致性）不可迁移**，因此**你会失去"过去这些结论是否可信"的依据**。**所以门槛（回填能否按时点、切分能否防三种泄漏）必须在第一版就判对。**

**第二条硬结论**：上表里有两项的代价**部分不可逆**——"无元数据 → 有"里的"谁标的 / 当时口径版本"（**事后补不回来**）与"评测集非随机 → 随机"里的历史结论（**不可比**）。**其余六项都是"要花时间"**；这决定优先级：**如果只能做一件事，先把五个元数据字段写上**（成本极低），而不是先优化标注效率。

**四个反模式（它们的共同点是：都在机制层面换掉了"成本随什么增长"）**：

- **反模式：把"标注体验"当第一判据** —— 症状是选型表第一列写的是"界面好不好用" → 后果是一个标注体验极好、回填却用最新值的平台，会让全部离线结论建立在一个虚高的基准上（§7.1）→ 机制上**体验作用于效率，回填作用于结论是否成立**，两者不在同一层 → 正确做法：先做门槛检查（回填可否按时点、切分可否防三种泄漏），通过了再比体验。
- **反模式：先扩样本量、后建元数据** —— 症状是样本量上去了而字段没写全 → 后果是存量样本的"谁标的、当时口径版本"永久未知（§7.7 表里两项部分不可逆之一）→ 机制上**元数据是挂载点，晚做只能补"能推的"**（`event_time` 能推，口径版本推不出）→ 正确做法：把五个字段做成必填，而不是"以后补录"。
- **反模式：把"检查跑过"当成"检查通过"** —— 症状是三种泄漏检测与污染检查都在流水线里跑，但结果没人看、失败不阻断 → 后果与没跑等价，还多出一层"我们已经检查过"的信心 → 机制上**泄漏与污染的检测是机械动作，它的可靠性来自"失败即阻断"而不是"跑过"**（§4.2（4））→ 正确做法：写进 CI，失败即阻断，并保留运行记录。
- **反模式：用"标了多少条"汇报样本工作** —— 症状是汇报里的数是标注量 → 后果是边界覆盖差而没人发现，模型在难点上仍然差 → 机制上**"量"比"构成"更容易汇报，而边界样本的量不随总样本量增长**（§7.4 的 `N_e`）→ 正确做法：把"三种检测各返回 0"与"分歧集中在哪几类"作为这一块的第一组 KPI。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 样本量极小、一次性 | 表格 + 五个元数据字段 | 元数据写下来的当期成本几乎为零，而它决定**能不能复现与举证**（一次性用途下收益变小，但成本更低） |
| 一个主体贡献多条样本 | 按实体切分 + 三种检测都跑 | 随机切分对重复主体必然产出实体泄漏 |
| 样本跨度跨年 | 先与上游谈特征历史保留期 | 保留期不足时，任何工具都回填不出当时的值 |
| 已经出现"离线好、线上差" | 改连接条件重跑一次评测 | 穿越的唯一发现方式是机械检查，不是看指标 |
| 非工程角色要参与标注 | **商业平台或开源工具 + 边界案例进任务配置** | 口径的载体决定一致性；但界面可用性对非工程角色是**必需**（§7.1 ①），工具不能只当次要项 |
| 标注预算不够用 | 先估"能规则化的比例"再投弱监督 | 弱监督压的是 `N × n_label`，压不动边界样本 `N_e` |
| 要对外举证 / 过审计 | 来源台账 + 授权链 + 快照 | 间接污染没有检测手段，只能靠登记 |
| 已有 ML 平台 | 平台管存储，回填与检查自建 | 平台的回填与切分约定未必按时点 |
| 正在考虑换平台 | 先看元数据与检查结果能不能导出 | 锁定的代价不是数据，是"过去这些结论是否可信"的依据 |
| 效果缓慢下降、说不清原因 | 先看漂移三轴，尤其关系侧 | 只看前两轴会漏掉"关系变了"这个主因 |
| 要上合成数据 / 增广 | 先做分区隔离与来源登记 | 改写形态的污染没有事后检测手段 |
| 审核队列开始积压 | 先看裁定结论有没有回写成边界案例 | 加标注者会让口径维护面变大，反向加重积压 |

> 本节小结：六个候选之间的差异，最终都能归到四问——**回填归谁且能不能按时点**、**切分能不能防三种泄漏**、**口径的载体是任务配置还是人的记性**、**样本衰减由谁触发增补**。四问决定了它们的分族（生产族 / 资产族 / 优化族）与成本曲线（生产族随时间线性但有下界、资产族台阶 + 随跨度增长的保留成本、**优化族的成本藏在评测重建里**）。**选型顺序不可颠倒**：先用"主体是否重复"与"跨度是否超过保留期"筛掉不可行，再用"能不能把回填与切分收成唯一入口"决定自建还是外购，最后才用标注比例与举证需求在剩下的里选——**把门槛当权重，是第二年最常见的失效原因**。**本主题有一条与其它主题不同的推论**：**优化族的回报有一个硬下界——边界样本永远要人标**（`N_e × t × c_h`，§7.4），因此**弱监督投到一定程度后，正确的动作是把边界样本单独管理并提高优先级**，而不是继续加函数。

> **补一条线（§7.3.5 与 §7.1 第 3 条判据的对应）**：上面四问管的是"处理机制"（回填归谁、切分怎么切、口径写在哪、增补由谁触发），而 §7.1 的第 3 条判据（**样本元数据可否导出**）问的是**资产与证据的存放位置**——它决定了另一件事：**换平台时你的元数据、检查结果与来源台账能不能带走**。这两类问题的失效形态不同：前四问做错，**错的是结论本身**——但它们的错都不报错（回填表现为"模型效果好"、切分表现为"结论乐观"、口径表现为"一致性靠人盯"、增补表现为"效果缓慢下降"，§7.3.1～§7.3.4），只能靠机械检查发现；第五问做错，**结论本身可能仍然是对的**，错的是**"过去那些结论是否可信"的依据**——它不影响当期指标，要到第一次复现、第一次审计、第一次换平台时才暴露。**因此它们的补救顺序也不同**：前四问按"以周计 / 以月计"补得回来，第五问里"谁标的、当时的口径版本"**事后补不回来**。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次**门槛检查**（不是打分）：回填可否按时点、切分可否防三种泄漏、元数据可否导出、污染台账、口径载体、运维承接——**哪一条是"不满足"而不是"分数低"**？那一条就是你最可能被迫迁移的方向（§7.7）；而你今天的补救成本，是否还落在"以周计 / 以月计"的那几格里？**另一问更具体**：如果明天换掉现在的样本平台，**你的元数据、检查结果与评测集快照能不能带走**？答不出，说明样本资产还没有真正掌握在自己手里。
