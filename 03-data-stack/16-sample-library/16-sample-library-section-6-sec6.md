## 6. 落地实践

> **本节的材料纪律（先说清楚）**：样本库的公开材料以**开源工具与工具文档**为主，而**标注一致性、穿越幅度、污染排查结果这类真正有用的数据几乎无人公开**——它们直接暴露"此前的离线指标里有多少是借来的、有多少结论要打折"。因此本节 4 例的构成是：
>
> - **§6.1–§6.2** 是**开源项目文档层面的机制复述**（任务怎么被配置化、标注函数怎么被审计与聚合），**不是对任何一家公司内部实现的转述**；方括号内是**来源类型 + 年份**，属**建设方自述**，不构成本书 §5 判据里要求的「第三方（非厂商）公开生产案例」。
> - **§6.3–§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证。
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 Label Studio"**把口径写进任务流：标注从个人劳动变成可配置的流水线 3+ 年**"（2021-2024）

**背景（Why）**

标注最初是"每个人拉一批数据、自己标完给自己用"：

- **口径在人的脑子里**——新人接手要口头交接，而交接必然失真；
- **没有一致性度量**——两个人对同一输入判得不一样时，**没人知道**；
- **样本散在各人的导出文件里**——"上一版训练用的是哪批"无法回答。

**约束与代价（这一例真正压着的两条）**

- **约束是"判定只有人看得准"**（§3.1 约束 1 的另一侧）——能写成规则的那部分不在这里解决，因此**这一模式的成本上限由"不能规则化的那一块有多大"决定**，而不是由工具好不好用决定。
- **代价是"口径从此成为一份要维护的资产"**：任务配置一旦版本化，每次口径变更都要走一次版本发布，且**任务数越多、维护面越大**（§3.2.1 代价①）。这条代价的机制是：**把口径从人脑搬到配置里，省掉的是"每加一个人就重新校准一遍"，换来的是"每次口径变更都要有人负责"**——可传递性不是免费的。

**触发点（What）**

Label Studio 一类开源标注工具把**标注任务做成可配置的对象**（[Label Studio 公开材料 2021-2024]，核验入口是其官方文档 / 仓库，**按当前版本核**）：输入展示、判定问题、取值域、审核流都在配置里，**而配置可版本化**。它给出的判断是**"口径要写进任务流，而不是写在交接文档里"**：

- **配置即口径**（改口径 = 改配置，有版本可回滚）；
- **多人独立标注 + 一致性计算**让分歧第一次可见；
- **任务与样本分离**（样本进库，任务只是它的一次标注过程）。

**这里的两侧要一起看**：配置化解决的是"口径可传递"，**不解决"谁来定口径"**（§3.1 约束 5）。因此**上了工具而没有 Owner 的团队，会在几个月后回到原点**——新人确实能自己读配置开工，但配置停在引入时的那一版，新样本落在它没覆盖的边界上，而**一致性是缓慢下降的，看指标看不出来**（§3.1 的判据用法）。

**详细做法（How）**

**① 任务配置的五个组成部分**

```text
① 输入展示：给标注者看什么 —— 少了上下文会逼人猜，而"猜"的分歧无法通过改口径消除
② 判定问题：一个可判定的问题（不是"这条好不好"）
③ 取值域：枚举写死（自由文本只允许出现在"其他 + 说明"里）
④ 边界案例：3–5 个已知难例及其正确判定 —— 口径的主要载体
⑤ 审核规则：谁审、怎么抽、分歧怎么裁
判据：④ 是不是"真正会分歧的地方"—— 不是的话，标注者仍会各自发挥
```

**关键判据（① 的补充）**：④ 与 ⑤ 要分开检查——**边界案例决定分歧从哪来，审核规则决定分歧怎么收口**。只补审核规则而不改边界案例，积压会转成"裁定者拍板"，而**拍板的结论不进配置，同一类分歧下一批照旧出现**。

**② 一致性作为口径的诊断工具（而不是标注者的考核）**

- **关键设计**：抽样批次做重复标注，算 κ 并**看分歧分布**。
- **关键性质**：**κ 低时第一个动作是改口径，不是换人**——因为 κ 衡量的是口径的清晰程度，而不是标注者的水平。**把它当考核指标会让标注者彼此对齐（人为抬高），于是口径的真实问题被掩盖。**
- **关键能力（为什么"看分歧分布"比"看 κ 这一个数"更重要）**：κ 只给一个总分，**它无法区分"全表都模糊"与"少数几类特别模糊"**；而后者才是靠补三到五个边界案例就能修掉的那一类。**判据**：分歧是集中在少数几类上（补边界案例即可解决），还是弥散在各处（说明判定问题本身没定义清楚，该改的是 ②）。
- **落地形态**（与 §4.2（2）同口径）：一致性与标注者列表一并落进样本表的 `label_meta`（`annotators` / `kappa` / `guideline_version`，见 §4.2（1））；**κ 不进任何人的绩效**，只进口径版本的变更说明。

**③ 审核与裁定：把"积压"当成设计对象**

```text
任务队列 → 独立标注（2 人） ── 一致 ──→ 入库（label_source = human）
                    │
                    └── 不一致 ──→ 裁定者看分歧 ──→ 裁定结论
                                                    ├→ 入库（label_meta.reviewed_by = 裁定者）
                                                    └→ 若结论超出当前边界案例 ⇒ 写进下一版配置
判据：裁定结论有没有回写成边界案例 —— 不回写，同一类分歧会反复出现，而每次的裁定可能不同
```

- **关键设计**：**超时与转交规则必须显式**——审核环节会积压，这与所有人审闸门是同一个问题（§3.2.1 代价③）。
- **为什么它是设计对象而不是运维琐事**：积压不会报错，**它只表现为"标注完成了但入库很慢"**，于是团队的第一反应是增加标注者，而**增加标注者会让口径维护面变大，反向加重积压**。
- **判据**：审核队列的**等待时长**有没有数；裁定结论有没有回写成边界案例。

**④ 输出结构：一条标注结果落成什么**

```yaml
label_meta:
  annotators: [a1, a2]          # 参与本条标注的人（重复标注时不止一个）
  kappa: 0.78                   # 该批次的抽样一致性（是批次的诊断量，不是个人分数）
  guideline_version: g3         # 本条标注是在哪一版口径下产生的
  reviewed_by: r7               # 裁定者；标注一致时为空
判据：能否回答"这条标注是哪一版口径下产生的、有没有经过裁定"
```

- **关键设计**：标注者 / 口径版本 / 裁定者三样落在**样本上**，而不是落在任务里（字段定义见 §4.2（1））。
- **为什么**：**任务会改、会删，样本要活过任务**——口径版本一旦只记在任务里，任务下线之后，历史标注就变成了"来历不明的数据"，而它**没法通过重标补回来**（重标是新口径下的新标注，不是旧的）。
- **代价**：元数据字段要跟随每一条标注写入，**写入路径多一处**；这也正是 §4.2（1）把它放进"最小充分定义"的理由——**字段一旦不是必填，它就会在补录时被跳过**，而补录时人已经不记得了。

**具体数字（档位标注）**

- 重复标注的人力代价：**同一批样本至少两人标** ⇒ 被抽中的批次人力翻倍【推算：口径为"抽出比例 × 1"的额外人力】——因此通常只对**抽样批次**做重复（抽多少取决于口径的稳定程度）。**这个量级决定了重复标注只能抽样**：全量重复等于把标注预算直接翻倍，而它换回来的是"分歧可见"，不是任何标签——所以它是**诊断成本，不是生产成本**，不该进标注预算去和产出比。
- 边界案例的数量：**3–5 个**通常够覆盖一个任务的常见分歧【经验：随任务主观性浮动】。**这个量级决定了补边界案例是一件"当天能做完"的事**，因此它没有"以后再做"的借口；反过来，**当一个任务里的边界案例超过十条时【经验：随任务主观性浮动，不是硬阈值】，通常不是难点变多了，而是判定问题没写清楚**——该改的是 ②，不是继续补 ④。
- 影响面的口径（本例不给团队规模）：这一例按本节开头的材料纪律是**开源项目文档层面的机制复述，不是对任何一家公司内部实现的转述**，因此不给人员编制；可登记的是 **Owner 与参与标注的人数**（§4.5 模板 1 的 `Owner` 一格），以及"有多少个任务在共用同一套口径版本"——**后者决定一次口径变更的发布面**。
- **自测动作**：让一个新人**不看口头说明**、只看任务配置开工，看他是否会被卡住——**被卡住的地方就是配置缺的部分**；再数一下上一批的裁定结论里，有几条回写进了配置。

**失败教训**

**第一版把口径写在一份共享文档里**——任务配置里只有"判定问题"与"取值域"。结果是标注者遇到文档没覆盖的情形时各自发挥，而**分歧恰好集中在这些情形上**（也就是模型最需要正确的样本上）。教训：**口径的主要载体是"边界案例"，不是"判定问题"**——判定问题决定任务看起来在做什么，**边界案例决定它实际怎么做。**

**为什么当初会写成那样**：共享文档是**零成本的默认动作**——写配置要先想清楚"判定问题与取值域"，而写文档只要把已经想到的说出来。**这类失败在本主题里的共同形状是"最便宜的载体先被选上"**（同 §6.2 的"先让函数硬投"、§6.3 的"先读最新分区"）：它们都**不是判断错误，而是默认选项从未被质疑过**。因此修法也不能靠"以后注意"，要落到一条可机械检查的判据上（上面 ④ 的"是不是真正会分歧的地方"、以及 ③ 的"裁定结论有没有回写"）。

### 6.2 Snorkel"**用标注函数替换一部分人工标注：把标注变成可审计的规则投票 5+ 年**"（2019-2024）

**背景（Why）**

标注需求里有一大块是**可以写成规则的**：

- **金额超限、字段缺失、状态异常**——这些不需要人看；
- **但没人愿意把它们做成规则**——因为"规则会腐化"，而腐化后没人知道；
- **于是这些样本也在耗人力**，而人力是最贵的。

**约束与代价（这一例真正压着的两条）**

- **约束是"判定里有一部分可以写成规则"**（§3.1 约束 1 的正侧）——这一条不成立时，弱监督不是"省得少一点"，而是**完全没有可用武之地**：把主观判断硬写成规则，只会得到一个不可审计的规则集合。
- **代价是"多出一个需要监控的软标签层"**：标签从此是概率的，下游要么接受软标签，要么按阈值切（§3.2.2 代价③）；且**规则会腐化**——业务变了规则不变，会静默产出错标签（§3.2.2 代价②）。**这条代价的机制是"腐化不报错"**：一条失效的规则仍然会命中并投票，只是投错了，而它没有任何运行期信号。

**触发点（What）**

Snorkel 一类弱监督方法把**标注变成多个标注函数的投票**（[Snorkel 公开材料 2019-2024]，核验入口是其论文与开源仓库，**按当前版本核**）：

- **每个函数可以不准**（只要比随机好），靠**聚合**得到概率标签；
- **每个函数可审计**（用规则表达，不是黑盒）——**这一点是它相对"训个模型来打标"的根本优势**；
- **允许弃权**：函数对不适用的样本投 `abstain`，而不是硬投一个值。

**这里的两侧要一起看**：可审计带来的不是"更准"，而是**"错了能改"**——出问题时你能指出是哪条规则错，而不是"模型就是这么认为的"（§3.2.2 的机制）。代价则是**你得一直改**：可审计的规则集合是一份需要人维护的资产，**没有人维护时，它的可审计性只体现在事后复盘上**。

**详细做法（How）**

**① 标注函数的三条设计要求**

```text
① 可审计：用规则表达（"金额 > X 且 状态 = 待审"），而不是模型 ——
   出问题时你能指出是哪条规则错，而不是"模型就是这么认为的"
② 有弃权：不适用的样本投 abstain ——
   硬投会把噪声均匀洒进数据，而弃权把它集中暴露出来
③ 要留置信度：聚合后给概率标签 ——
   二值化会丢掉"这条有多确定"这个信息，而下游常常需要它
判据：函数签名里有没有"不适用"这一档 —— 没有就是硬投
```

**关键判据（① 的补充）**：三条里**② 是可机械检查的那一条**（签名里有没有 `abstain`），① 与 ③ 只能靠抽查与字段检查。因此**落地顺序是先把 ② 做成硬要求**——它挡住的是最难追查的那一类错误（噪声均匀洒进数据、症状出现在子群上）。

**② 聚合权重必须在留出集上估**

- **关键设计**：用一小批人工标注作为"锚"，估各函数的准确性，再加权投票。
- **为什么**：**没有锚时，聚合权重只能凭感觉**——而权重错了会让一个不准的函数主导标签，且**它表现为"模型在某些子群上效果差"，很难追到标注层**。
- **关键能力（为什么锚定是"下限"而不是"优化"）**：锚定样本的量很小、且**不随样本量增长**，但它决定标签质量的**下限**；去掉它省下的人力是有限的，而代价是**误差来源从"某条规则写错"变成"整套权重不可查"**。
- **落地形态**：锚定样本必须与训练集分开（同 §3.2.7 的切分纪律）——**用被锚定的那批本来参与训练，等于自己评自己**（与 §6.4 的"自证"是同一类错误）。

**③ 规则腐化要有监控**

- **关键设计**：监控各标注函数的命中量随时间的变化。**命中量突变（激增或归零）通常意味着上游业务变了。**
- **判据**：某个函数连续一段时间命中为 0，说明它的条件已经不可能被满足（业务变了而规则没改）。
- **为什么命中量是有效的代理量**：**规则的"对不对"无法在不重标的情况下测量，但"它还活不活"可以**——命中量是唯一一个既便宜、又能在腐化变成标签污染之前报出来的信号。**激增同样要看**：命中量突然放大通常意味着上游字段语义变了，而规则恰好被新数据"喂饱"。

**④ 分工边界：哪些判给规则、哪些留给人**

```text
人工（不可规则化的部分）            规则（可规则化的部分）
主观判断 / 语境相关 / 首现类型  →  阈值判定 / 字段缺失 / 状态机排除 / 历史模式匹配
判据：把一条样本交给规则时，能不能写出它的判定条件 —— 写不出，说明它属于左边
```

- **关键设计**：分工不按"难易"划分，而按**"能不能写出条件"**划分——写得出条件的进规则（可审计、可复制、边际成本为零），写不出的留人工（§3.2.2 的结构：低置信进人工复核）。
- **为什么顺序是"先剔除、再花人力"，而不是"规则先上、剩下的给人"**：顺序反了会把预算花在机器能判的样本上（§3.4 组合模式的第 1 条）。而**剔除是廉价的**——它只需要一次估算（"能规则化的比例"），不需要先把函数写出来。
- **判据**：抽样若干条已经人工标过的样本，逐条问"这条的判定条件能不能写成规则"——**答"能"的比例，就是本模式还没吃掉的标注预算**。

**具体数字（档位标注）**

- 人工量的下降幅度：取决于"能规则化的比例"，而**这个比例可以在第一天估出来**【经验：随业务规则化程度浮动，请用你自己的数据估】——**先估它，再决定投入弱监督是否划算**。**这个量级决定了要不要做**：比例低于一成时，标注函数的设计与维护成本会超过它省下的人力（§7.5 的退出条件）；高于一成时，它把标注成本从"随样本数线性"改成"随难点数增长"（主文件 §1.4 的措辞）。
- 锚定样本量的量级：聚合权重的估计只需要**一小批人工标注**（相对全量很小），但**它必须与训练集分开**（同 §3.2.7 的切分纪律）。**这个量级的特点是"小但不可省"**：它不随样本量增长，却是唯一能让权重可查的东西——省掉它，症状会跑到"模型在少数子群上效果差"上去，而排查要花的时间远超这批锚定样本的标注时间。
- 影响面的口径（本例不给团队规模）：这一例同为**开源项目文档层面的机制复述**，不给内部编制；**可估的是维护成本那一侧**——标注函数条数与维护人力成正比，**按你现有的规则条数替换即可**；另一侧的量是"有多少条标签最终来自 `label_source = weak_multi`"（§4.2（1）的字段取值之一），**它决定下游对软标签的接受度要到什么程度**。
- **自测动作**：数一下你的标注需求里，**写成规则就能判的比例**是多少——这个数决定弱监督的投入回报；再数一次标注函数签名里带"不适用 / `abstain`"档的占比，以及近一个月命中恒为零的函数条数。

**失败教训**

**第一版让所有函数对所有样本硬投**——于是"不适用"的样本被硬投成噪声，而它的表现是"模型在少数子群上效果差"。排查花了两周，最后发现根因在标注层。教训：**"弃权"不是可选设计，它是让噪声可定位的唯一手段**——硬投把噪声均匀洒开，弃权把它集中成"这一批函数都没投"的可观测信号。

**为什么当初会写成那样**：**"每个函数都要给一个值"是直觉上更完整的设计**——允许弃权看起来像是"这个函数没干活"。实际恰好相反：**弃权是函数在报告自己的边界**，而边界信息正是聚合阶段最需要的东西（哪些样本谁都判不了，就该进人工）。这条与本主题其余几例同形：**默认选项（让模型/规则/流程"给出一个答案"）本身从未被要求举证**，而它的代价要等到子群效果出问题才显形。

### 6.3 某电商"**特征回填改对之后，离线指标下降了：借来的那部分被还回去 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

转化率模型的离线 AUC 一直很好，而**上线后表现明显差一截**。团队反复调特征、调模型、扩样本，效果都不稳定。

**约束与代价（这一例真正压着的两条）**

- **约束是"样本跨度长"**（§3.1 约束 3）——转化标签要等用户回访，样本跨度以月计，因此**"最近 N 天"这类窗口特征在 `event_time` 之后仍在变化**。跨度越长，穿越幅度越大。
- **代价是它"在改造之前处处占优"**：读最新分区更快、更省，且**离线指标更好看**（§3.2.6 代价①与失效点）——这条错误路径不是"有人偷懒才走"的，它是**默认路径**。因此**要防的不是错误本身，而是"默认选项恰好是错的"**。

**触发点（What）**

**一次特征平台的改造**：改造后，样本组装从"读特征表最新分区"改成"按样本 `event_time` 读历史版本"。改造上线后，**离线 AUC 明显下降**，团队第一反应是"改造引入 bug"。

**代价正好发生在这里**：把连接条件改对之后，指标必须下降——**这个下降不是退步，是借来的那部分被还回去了**（§5.3.1）。处置成本因此不落在代码上，而落在**"怎么向业务解释"**上：同一份指标，在改造前是"我们的模型很好"，改造后变成"我们此前的好是借来的"。

**详细做法（How）**

**① 先把"下降"定性：是 bug 还是还账**

- **关键设计**：对同一批样本，分别用两种回填口径算特征值，**逐条比对差异样本的特征分布**。
- **关键性质**：**如果是 bug，差异会集中在少数特征上且分布异常；如果是穿越，差异会集中在"时点后发生变化的特征"上**（例如"最近 7 天消费额"这类窗口特征）。**本例的差异集中在窗口特征上 ⇒ 是穿越。**
- **判据**：差异的特征分布与"特征的变化频率"是否正相关——**是，就排除 bug 假设**；这一步必须在改代码之前做完，否则会先花时间在"回滚改造"上。

**② 把"穿越幅度"量出来**

- **关键设计**：量化同一批样本在两种口径下的指标差（AUC 差、以及正例上的差异）。
- **为什么**：**这个数是"此前有多少结论建立在借来的信息上"**——它同时决定"要不要重做历史模型"与"怎么向业务解释指标下降"。
- **关键能力（为什么它不能只算一个总差）**：总差只给一个幅度，**按特征族拆开才知道哪一类结论受影响最大**（本例是窗口类），而"哪一类结论要更正"正是对外沟通的输入。**判据**：差异是否按特征族给出分布，而不是只给一个总 AUC 差。

**③ 把回填收成唯一入口（防止再被绕过）**

- **关键设计**：回填脚本成为唯一入口；**CI 里加一条检查**：全库搜索还有没有别处直接 JOIN 特征表做样本组装。
- **为什么**：**穿越的根因不是"某个人写错了"，而是"回填不是唯一入口"**——只要存在第二条组装路径，它就会在某次赶工期时用最新值。
- **落地形态（三条可机械执行的检查，任一不过即阻断）**：

```text
① 全库搜索"直接 JOIN 特征表组装样本"⇒ 命中数应为 1（只允许 backfill.py）
② 连接条件里必须出现 feature_ts <= event_time ⇒ 缺即不通过
③ 每条样本都要有 event_time 与 features_ref.version（§4.2（1）的字段）⇒ 缺即不通过
判据：① 的命中数不为 1 ⇒ 第二条组装路径又出现了（本案例的根因）
```

**④ 处置：把改动量限定在"记录与更正"，而不是全量重训**

- **关键设计**：受影响的历史模型结论**做标注**（"此前的离线指标含穿越，幅度见记录"），**不必全部重训**；但**对外承诺过的指标要更正**。
- **为什么**：穿越影响的是"当时的选择依据"，不是"模型现在的能力"——**已经在跑的模型不需要因为这条记录而下线**；而**用虚高指标做过的对外陈述必须更正**。两者的处置强度不同，混在一起会让处置成本被高估、进而被拖到不做。
- **判据**：能不能列出一张"受影响的历史结论清单"，并标出其中哪些对外发布过。

**⑤ 把"当时值"与"现在值"两条读路径显式区分**

```text
回填（训练 / 评测用）   → 按 event_time 取历史版本 ⇒ 连接条件 feature_ts <= event_time
实时推理（线上打分用）  → 取当前最新值             ⇒ 读特征平台的在线存储
判据：两条路径在接口上分得开吗 —— 混用时同一条样本会回填出两个值，而没人知道为什么
```

- **关键设计**：**两条路径都合法，但必须分得开**——训练侧要"当时值"，线上侧要"当前值"，它们不是同一个查询（§5.3.1 推出的第三个工程约束）。
- **为什么混用会出问题**：混用时**同一个 `(entity, event_time)` 会回填出两个不同的特征值**，而两者的差异没有任何标记——排查时表现为"同样的脚本两次跑出不同结果"，于是团队会先去怀疑随机性或缓存，而不是怀疑读路径。
- **判据**：能不能当场指出"哪个接口给当时值、哪个给当前值"，以及线上读取会不会误走回填入口。

**具体数字（档位标注）**

- 穿越幅度的量级：本例中窗口类特征的穿越幅度最大（**"最近 7 天消费额"在 `event_time` 之后仍在变化**），而**快照类特征（注册渠道）几乎不受影响**【经验：穿越幅度随特征的"变化频率"上升】——**这条分布特征本身就是诊断依据**，同时它决定了"哪些结论要更正"：**用窗口特征做的选型最不可信，用快照特征做的基本不受影响。**
- 重做的成本：受影响的历史模型结论要做标注（"此前的离线指标含穿越，幅度见记录"），**而不必全部重训**——但**对外承诺过的指标要更正**【经验：随对外程度上浮】。**这个量级决定了处置该按"记录 + 更正"走**：按"全部重训"估成本会把这件事抬成一个大项目，而它实际需要的是一次清单梳理与一次对外更正。
- 常备投入：把回填收成唯一入口并加上 CI 检查，量级在 **0.3–0.6 人年**（§7.5 的【经验】区间，随特征表数量与历史版本数浮动）。**这个量级决定了它该被当成常备预算而不是一次性项目**——按项目立项时，它会在下一次赶工期里被绕过，而**绕过不会报错**（这正是 ③ 要放进 CI 的唯一理由）。
- 影响面的口径（匿名案例不给团队规模）：本例是匿名案例，**不给人员编制**；可核的是影响面——**受影响的历史模型有几个、其中对外承诺过指标的有几条**。前者决定要重跑多少验证，后者决定要更正多少份对外材料。
- **自测动作**：把回填连接条件改成含时点约束，重跑一次评测——**下降的幅度就是你的穿越幅度**；再跑一次上面 ③ 的三条 CI 检查，看第一条的命中数是不是 1。

**失败教训**

**把"离线好"当成"模型好"**——三年里所有选型与调参都基于一个含穿越的离线指标。教训：**特征穿越的性质是"它让离线指标更好看"**，因此**没有任何指标能发现它**；唯一的发现方式是**机械地检查连接条件**——而这件事必须做成脚本（CI 检查），不能靠人记得。

**为什么当初会写成那样**：这一例的成因与"谁不小心"无关，而是**两个默认选项叠加**——读最新分区是**最省事的写法**（不需要问特征表有没有历史版本），而"离线更好"是**最省事的解释**（不需要怀疑自己的特征）。**两者都让当下更顺，代价推迟到上线后**。因此它修不好"靠注意"，只能靠把默认路径改掉：**唯一入口 + CI 检查**——判据不在人的记忆里，在检查脚本的返回行数里。

### 6.4 某银行"**评测集污染排查：一份公开语料里混着自家评测题 2+ 年**"（2022-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证。

**背景（Why）**

风控文本模型的评测集是从历史工单里挑的 3,000 条。模型迭代一直"稳定提升"，团队据此决定扩大使用范围。

**约束与代价（这一例真正压着的两条）**

- **约束是"结论要被信任 / 对外举证"**（§3.1 约束 4）——扩大使用范围意味着这些结论要被外部读到，因此**污染从这个时点起不再是内部问题**。
- **代价是"台账要人工维护，且它只在事后才显出价值"**：每个来源一条记录、含"它可能包含什么"（§3.2.8 代价①）。**在引入数据源的那一刻，登记与不登记的当期成本差得很小，而两者在出问题时的可回答性差别是全部**——这是一个**收益完全滞后的动作**，因此它总被排到最后。

**触发点（What）**

**一次内部评审**：有人问"我们的训练数据里有没有用到公开语料"。追查发现——**半年前为了扩充训练数据，引入了一批行业内公开的语料包，而那批语料包里包含该行的部分历史工单**（工单曾被脱敏后用于行业交流）。**于是 3,000 条评测里有约两成以改写形式出现在训练数据里**，而**它们不是近重复**（经过改写），跨集比对检查发现不了。

**这里的两侧要一起看**：真正被触发的不是"发现了污染"，而是**"这个问题此前无法回答"**——追问之所以要花时间，是因为语料是黑箱下载下来的，**没有任何记录说明它可能包含什么**（§3.2.8 的机制）。

**详细做法（How）**

**① 区分"直接污染"与"间接污染"，并承认后者只能靠台账**

- **关键设计**：直接污染可用比对发现（跨集近重复）；**间接污染（经语料 / 合成 / 改写）无法靠比对**——**只能靠"数据来源台账"**（每个来源登记"它可能包含什么"）。
- **为什么**：**没有台账时，"这份语料里有没有我的评测题"这个问题在那个时点已经无法回答**——语料是黑箱下载下来的，你无从得知它的构成。
- **关键能力（为什么两类污染的处理强度不同）**：直接污染有检测手段，因此可以"先检测再决定"；间接污染**没有检测手段**，因此只能"先隔离再使用"。**这个差别决定了动作顺序**：比对可以放到评测前跑，台账与分区必须在数据**引入时**就位。
- **判据**：能不能在不查历史工单、不重新跑比对的前提下，直接答出"某个来源里可能有什么"。

**② 重建评测集并标注历史结论**

- **关键设计**：重建一份**与所有已用训练数据来源隔离**的评测集；对受污染期间的结论**做标注**（不追溯改写，但要说明"该期间的结论含污染"）。
- **判据**：**"不追溯改写结论，但必须知道哪些结论要打折"**——这是与 §6.3 同一条处理纪律。
- **为什么是"标注"而不是"作废"**：污染影响的是**"这些结论还作不作数"**，而不是"模型现在对不对"。全部作废会连带把未受影响的结论一起推翻，**代价远大于收益**——而"标注"保留了它们作为趋势参考的价值。

**③ 建台账 + 分区隔离**

- **关键设计**：每个新数据源登记一条（来源描述 + 可能包含什么 + 授权状态）；**合成 / 增广流程的输入语料与评测集来源物理分开**。
- **为什么**：**分区隔离是防"自证"的唯一手段**——用它自己的来源生成数据、再用它评测，结论必然乐观，而**这条路径没有任何指标能发现**。
- **落地形态（台账的一条记录长什么样）**：

```text
| 来源 id  | 来源描述          | 引入时间 | 可能包含什么                    | 授权状态   | 与评测来源是否隔离 |
| src_014  | 行业公开语料包 v2 | 2024-01  | 含本行业历史工单（可能含本行脱敏工单）| 公开可商用 | 否（已禁止用于合成与增广） |
判据：这一行能不能回答"它可能包含什么" —— 答不出，就是只登记了来源、没登记内容
```

**④ 排查动作：从"怀疑"到"定位到那一份语料"**

- **关键设计**：**先列训练数据来源清单（时间倒序）→ 再逐源问"它可能包含什么" → 最后才做比对**。
- **为什么顺序不能反**：比对只能发现直接污染（近重复），**用它去排除间接污染，等于用一个原理上发现不了它的工具去排除它**——跑完一遍返回 0，会得到一个错误的"干净"结论。
- **判据**：能否在没有历史记忆的情况下，列出"最近一年引入的全部外部数据源"——这一步的产出就是台账的补录清单。

**⑤ 分区隔离怎么落在配置上（而不是落在约定上）**

```text
数据分区                        谁可以读
train/  （训练数据）            训练流程、合成 / 增广流程
eval/   （评测集来源）          仅评测流程；合成与增广一律禁止读
synth/  （合成产物）            训练流程；产物必须带"合成"标记（§4.2（6）②；§5.3.3 ①）
判据：合成 / 增广流程的读取白名单里有没有 eval/ —— 有，就是一条自证通道
```

- **关键设计**：隔离靠**读取白名单**表达，而不是靠约定——**合成与增广的输入必须来自 `train/`，不能来自 `eval/`**（做法同 §4.2（6））。
- **为什么必须物理分隔而不是"注意一下"**：这条通道上的污染**经过改写**，近重复比对发现不了（本例就是改写的形态），因此**它没有事后检测手段，只能在读取的那一刻挡住**。
- **判据**：能不能列出"合成 / 增广流程当前能读到的分区清单"——需要临时翻代码或问人才答得出，就说明隔离还没落在配置上。

**具体数字（档位标注）**

- 污染的规模：本例中约两成评测样本受间接污染【经验：随语料来源与评测集来源的重叠度浮动】——**这个比例决定了此前结论的可信度**。**这个量级决定了处置是"逐条更正式"还是"整段作废"**：两成处在中间——不足以让全部结论作废，又足以让"该期间的结论含污染"这句话必须写下来；因此本例的处置落在"标注而不追溯改写"上。
- 台账的维护成本：**每个数据源一条记录**【推算：随引入数据源的频率线性增长】——**这是本主题里预防成本最低、而缺失代价最高的一项**。**这个量级决定了它没有"等规模大了再做"的理由**：记录数与来源数同阶，而不是与样本量同阶，所以**它在样本量增长时不增长**——这正是它可以立刻开始做的原因。
- 影响面的口径（匿名案例不给团队规模）：本例是匿名案例，**不给人员编制**；可换参数的量是**"引入数据源的频率 × 每个来源一条台账记录"**，排查侧则是**"受污染期间对外发布过多少条结论"**——后者决定更正范围，前者决定常备成本。
- **自测动作**：问一句"我上个月引入的那份公开语料，里面可能有我们的评测题吗"——**答不出来就是台账缺失**；答"可能有"而训练仍在用它，就是分区隔离缺失。

**失败教训**

**把"评测集是自己挑的、训练数据是自己整理"当成"两者隔离"**——它们来源上确实不同，而**中间隔着一份公开语料**。教训：**污染不只是"直接混入"，还有"经由第三方语料间接混入"**；而**第二类只能靠"来源台账"防**——它要求把"我用的数据从哪来"变成一条需要被登记的陈述，**而不是一个事后可以回忆的记忆**。

**为什么当初会写成那样**：引入公开语料在那个时点上**是一笔纯粹的收益**——样本量上去了、标注成本为零、来源看起来正规（行业内公开）。**登记它"可能包含什么"在读起来像是在给自己找麻烦**：既不能增加样本，也不改变任何当期的指标。这条与本主题其余几例同形：**失效都藏在"当期只有收益的动作"里**（§6.3 的读最新分区、§6.1 的写共享文档），因此**它们不能靠怀疑精神发现，只能靠把检查做成机械动作**——台账、比对、隔离三件，各对应一类只能靠它发现的污染。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条顺序固定的路径，与 §4.1 的八步对应：

1. **先定五个元数据字段**（§6.3 的改造前提）——没有它们，回填、切分与污染检查都无处挂。
2. **再把回填收成唯一入口，并做 CI 检查**（§6.3）——**穿越的唯一发现方式是机械检查，不是看指标**。
3. **然后跑三种泄漏检测 + 污染检查**（§6.4 的排查前提）——**这一步常常会发现问题，而它必须在模型工作之前做**。
4. **接着把口径写进任务流**（§6.1）——任务配置的五个部分，核心是**边界案例**。
5. **最后把能规则化的部分规则化**（§6.2）——**先估"能规则化的比例"，再决定投入。**

**上面五步的阶段版本**（**0 → 1 段另给产出**，其余段给扩展方向，**与本章其余主题 §6.5 同形**；**每段的验证标准逐条在本主题内可指到出处**——主体是 §4.1 的八步判据、§4.5 的三张模板与 §4.9 的自检清单，其中几条在本节案例里已有落地形态（§6.1 的配置自测、§6.2 的弃权档、§6.3 的三条 CI 检查、§6.4 的台账与分区、§6.7 的常态预算），属**组装而非新造**）。**阶段时长与团队档位沿用本章其余主题 §6.5 的同一组默认档位**【经验：与案例组织规模无关；本节 §6.1–§6.4 已逐例声明不给内部人员编制】。

**0 → 1 阶段【经验：3-6 个月】**

- 选「**五个元数据字段 + 唯一回填入口 + 三种泄漏检测**」（**最简单**）——**单一业务域 / 一张样本表**
- 产出：**五个字段写进样本表结构 + 回填脚本（连接条件含 `feature_ts <= event_time`）+ 三种泄漏检测各返回 0 的记录 + 一次"改对前后离线指标之差"的记录**
- 团队：**2-3 人**【经验：本章 §6.5 的默认档位，非本主题案例的编制】
- 验证标准：**抽一条样本能回答"它当时看到了什么、谁标的、属于哪一版、在哪个切分里"**、**全库搜索"直接 JOIN 特征表组装样本"的命中数为 1**、**三种泄漏检测各返回 0**、**改对连接条件后指标确实下降、且下降幅度已入档**（下降不是退步，是借来的那部分被还回去，§6.3）

**1 → 10 阶段【经验：6-12 个月】**

- 扩展到「**口径、一致性与来源三件事都开始成规模**」——多个标注任务、多个外部数据源
- 引入「**标注任务配置化（含 3–5 个边界案例【经验：随任务主观性浮动】）+ κ 与分歧分布**」——把口径从人脑搬进配置（§6.1）
- 引入「**弱监督：带弃权档的标注函数 + 在留出集上估权重**」——把能规则化的部分从人力里剔除，人力留给边界（§6.2）
- 引入「**污染检查三件 + 数据来源台账 + 合成与评测的分区隔离**」——间接污染没有检测手段，只能在引入的那一刻挡住（§6.4）
- 团队：**5-10 人**【经验：本章 §6.5 的默认档位，非本主题案例的编制】
- 验证标准：**新标注者不看口头说明、只看任务配置就能独立开工**、**分歧集中在少数几类（补边界案例即可解决）而不是弥散在各处**、**标注函数签名里带"不适用 / `abstain`"档**、**不查历史工单也能答出"某个来源里可能有什么"**、**合成 / 增广流程的读取白名单里没有 `eval/`**

**10 → 100 阶段【经验：12-24 个月】**

- 扩展到「**样本集作为资产**」——多个数据源、多个标注任务常态并存
- 引入「**样本集资产卡（§4.5 模板 1）成为常态，并在数据目录中登记**」——治理的边际成本随"每加一个数据源、每加一个标注任务"上升（§4.8）
- 引入「**漂移监控三轴（特征 / 标签 / 关系，§4.5 模板 3）+ 把"样本增补"算进常态预算**」——样本在衰减，而增补没进预算时，效果下降会被归因成"业务变难了"
- 团队：**10-30 人**【经验：本章 §6.5 的默认档位，非本主题案例的编制】
- 验证标准：**每个新数据源在台账里都有一条记录（记录数与来源数同阶，不与样本量同阶）**、**漂移监控覆盖特征 / 标签 / 关系三个轴（§4.5 模板 3）**、**"样本增补"出现在常态预算里**、**资产卡能在不查历史记录的前提下答出样本集的来源构成与口径版本（§4.5 模板 1）**

**为什么这里没有第四档（100 → 1000）**：本主题的材料只到"治理与自服务"（§4.8 自述的演进路线就是 0 → 1 → 100 三阶段），而**第四档需要的材料（跨组织交换样本集、多域共用同一套口径）在本主题内不存在**——唯一沾边的方向（数据集卡片 / 跨组织交换）在 §5.3.5 被判 **L3「只有提案与局部实践、核不到」**。因此这一档**留空**：**不为凑满体例而把别的主题的第四档搬过来**。

**顺序的反面**：**先扩样本量、后建元数据与检查**（§4.1 的反面）——扩量之后存量样本缺元数据（**"谁标的、当时口径是什么版本"补不回来**），且**污染与泄漏的概率随规模放大**。**第二条反面**：**先用预标注 / 合成数据扩量、后做分区隔离**（§6.4）——**生成类方法会把评测题带进训练集，而它不是近重复，比对发现不了**。

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 口径只在共享文档里 | 标注者遇到未覆盖情形各自发挥 | 分歧集中在模型最需要的样本上 | 边界案例写进任务配置（§6.1） |
| 拿 κ 考核标注者 | 一致性人为抬高 | 口径的真实问题被掩盖 | κ 作口径诊断（§6.1） |
| 弱监督函数硬投 | 少数子群效果差、追溯到不标注层 | 噪声均匀分布 | 函数加**弃权**档（§6.2） |
| 聚合权重凭感觉 | 不准的函数主导标签 | 同上 | 留出集估权重 |
| 规则腐化无监控 | 命中量长期为 0 | 静默产出错标签 | 监控各函数命中量（§6.2） |
| 回填用最新值 | 离线好线上差 | 特征穿越，**且离线指标更支持这个错误** | 连接条件含 `ts <= event_time`（§6.3） |
| 回填不是唯一入口 | 赶工期时又用最新值 | 穿越复发 | CI 检查"有无第二处组装"（§6.3） |
| 只做实体切分 | 实体交集 0 而结果仍乐观 | 时间与近重复泄漏 | 三种检测各跑（§3.2.7） |
| 用主动学习样本做评测 | 评测高而全量低 | 评测集不代表线上 | 评测集随机抽样（§3.2.3） |
| 只做跨集比对、无台账 | 无法回答语料里有无评测题 | 间接污染不可发现 | 建来源台账（§6.4） |
| 合成流程能读到评测来源 | 自证风险 | 结论必然乐观且无指标可查 | 分区隔离 + 来源登记（§6.4） |
| 预标注无独立抽检 | 修正比例极低被当成模型好 | 人在盲从、偏差固化 | 抽未修正批独立重标（§3.2.4） |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——样本库的收益形态是"结论可信、人力省下、返工避免"，前两者可量，第三者只能用"有没有发生"来判。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 结论可信度 | 三种泄漏检测 + 污染检查的结果 | 从**未做过**到**各返回 0** | 各跑一次并留记录 |
| 穿越幅度 | 改对回填后离线指标的变化 | **下降的幅度就是此前借用的未来信息量**（本例集中在窗口特征上） | 改连接条件重跑一次 |
| 标注人力 | 单条标注时长 × 条数 × 人数 / 复用率 | 弱监督 + 主动学习可显著下降；**边界样本永远要人** | 量"单条时长"与"能规则化的比例" |
| 标注一致性 | κ 与分歧分布 | 补边界案例后通常可显著提升（幅度取决于原口径的模糊程度） | 抽样重复标注算一次 |
| 返工避免 | 因穿越 / 泄漏 / 污染导致的结论作废次数 | 从**偶发**到"由检查从机制上排除" | 数最近一年此类返工 |
| 排障时间 | 从"效果异常"到"定位到样本层"的时长 | 版本标识齐全时可从**天级**降到**小时级** | 取最近一次复盘实际耗时 |
| 代价 | 标注 + 口径维护 + 治理（回填/切分/检查） | **人力为主，且样本本身在衰减** | 按月核算，并把"样本增补"算进常态预算 |

**读法**：前两项是**可信度收益**（检查通过、穿越还账），第三、四项是**成本与质量收益**（人力、一致性），第五项是**返工避免**，第六项是**排障效率**，最后一项是**代价**。**本主题最容易出现的错位是只算"标注省了多少人力"，不算"结论是否可信"**——前者是一次性节省，后者决定**每一次实验结果是否作数**。**另一条读法**：最后一项里"样本增补"常被当成一次性项目，而**样本在衰减**——把它漏出预算的后果是"用一年前的样本反复训模型，并把效果下降归因为业务变难"。

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**元数据先行**（回填、切分、污染检查都挂在它上面），**回填收成唯一入口并做 CI 检查**（穿越只能机械发现），**泄漏与污染检查在模型工作之前做**（它们常常会发现问题），**口径写进任务流**（核心是边界案例），**最后把能规则化的规则化**（先估比例再投入）。四次失败教训指向同一件事：**样本层的失败几乎都不是"标得不准"，而是"看起来干净而实际不干净"**——回填用了未来信息（离线更好看）、切分留了泄漏（结论更乐观）、语料带来污染（无指标可查）。**而这三种"不干净"有一个共同点：它们都让指标更好看，因此都不会引起怀疑。**

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你处境最像的案例，只做一件最小的事——按它的"判据"跑一次自测（让新人只看配置开工 / 数能规则化的比例 / 改回填连接条件重跑一次 / 问语料里有没有评测题）。哪一件**今天就能做**就先做它：**这一块的腐化不会报错，只会让结论越来越乐观、而模型上线越来越差。**
