## 7. 与其他方法对比

> 原 § 7 共 58 行、为 1 张 1–5 分的打分表 + 1 棵决策树 + 4 条组合，缺少机制解释与可溯源证据，重写为 ~310 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

打分表最危险的地方不是分数不准，而是它把**场景相关的结论伪装成绝对结论**。「HDFS 扩展性 3 分、对象存储 5 分」——3 分与 5 分的差别是什么？在什么规模、什么读写下成立？表里没有回答，读者只能猜。更麻烦的是同一维度在不同规模下**权重相反**：「成本」在百 GB 规模下权重近乎为零（一个月的存储差价抵不上一次讨论的工时），在 PB 规模下是主导项；「一致性」在单团队 T+1 批处理下几乎无法察觉，在多引擎共读同一份数据时它直接决定能不能上线。用一张不标权重的表去比这两端，比出来的排序在两端都是错的。

第二条更隐蔽：打分表会掩盖「同一套系统可以同时属于两行」。HDFS 上照样能挂 Iceberg / Hudi，这时它既有存算一体的扩容曲线，又有随事务提交的 schema（见 7.3.1）。一旦读者用打分表的行去对应真实系统，就会把「HDFS 得 1 分的 ACID」当成 HDFS 的天花板，从而漏掉「留住 HDFS、补一张表格式」这条最省钱的路径。

第三条是**阈值没有来处**。原决策树按 `< TB` / `TB - PB` / `> PB` / `EB 级` 分成四档，却没有说明分界是怎么来的：读者无法判断它是来自单机的物理上限、来自成本曲线的交点，还是来自某个厂商白皮书的推荐值——不同来处意味着不同的可调整空间：物理上限不可调，成本交点会随单价变化而移动（今天成立的 PB 阈值，在容量单价下降一半之后未必还成立）。本章的决策树（7.5）里每个分档都会给出推导链或可观测的判定指标，读者可以据此把分档改成自己环境里的值，而不是照抄。

所以本章的比较方式是：**先固定出几条与场景无关的判据，再让每个候选在判据上给出机制层面的解释，最后把选择落到可观测的指标上**。判据本身不排序，排序由你的约束决定：一个两三个人的团队与一个两百人的平台团队，看同样六条判据会得到不同的行——这正是打分表做不到的事，也是它会被误用的原因。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 一致性归属 | 表结构变更与数据写入是不是同一个原子提交 | 这一条决定「改结构要不要重写数据」以及「下游会不会读到中间态」，它是湖与仓最本质的分界，不是性能优化 |
| 扩容曲线形状 | 扩容要不要搬数据、边际成本是台阶式还是线性 | 存算一体的扩容要先采购再搬迁（台阶式），存算分离的扩容是加一个对象（近似线性）；两种形状各自要付的代价见 7.3.2 |
| 剪枝结构 | 你的每种查询各靠什么跳过数据 | 点查靠排序键 / 索引、范围扫描靠列存统计与分区、相似度靠向量索引——**查询类型与剪枝结构错配时加机器无效** |
| 成本随什么增长 | 容量 / 对象数 / 请求数 / 计算时长，哪一项是主导项 | 小文件会把主导项从容量换成请求数，此时单价折扣一文不值（见 7.3.3） |
| 常驻组件与人力 | 需要几个常驻服务、几个人长期维护 | 轻量方案的优势是**零常驻**而不是性能；小团队选错这一条，代价是系统上线数月后无人敢动【经验：量级为月到季】 |
| 锁定与迁移代价 | 离开它要重写什么：数据、查询、约定还是运维体系 | 专有格式锁数据、外部 metastore 锁约定、表格式锁 catalog——三者迁移成本差一个量级（见 7.7） |

> 这 6 条不并列：**一致性归属与剪枝结构**是技术的硬边界（错了以后加钱解决不了），**成本与人力**是经济边界（错了可以熬），**锁定**是时间边界（错了要按季到半年量级还债【经验：量级为季到半年】）。

用这张表时不要逐条打分再求和——那样又回到了本章反对的做法。正确的用法是：**先用「一致性归属」把候选砍掉一半**（它是一条二值的硬边界：schema 随写事务提交，还是不随），**再用「剪枝结构」砍掉与你查询类型错配的**（点查与相似度是两种完全不同的剪枝），剩下的候选才轮到成本与人力来排序。锁定与演进风险放在最后，因为它们的代价只在你要离开时兑现，而前四条决定了你能不能走到那一天。

### 7.2 候选方案全景

比较的第一层是**架构级候选**——它决定数据落在哪、schema 归谁管：

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| HDFS 数据湖 | 自建机房的数据湖基座 | 存算一体 + 表外 Hive Metastore：数据局部性好，但结构与文件分属两个系统 | 自建机房、历史资产重的企业 | Apache 开源（自运维） |
| 对象存储裸文件湖 | 云上低成本蓄水池 | 存算分离 + 外部约定管 schema：扩容便宜，但结构变更无事务边界 | 早期云上团队 | 对象存储按量计费（S3 / OSS / COS 等） |
| Lakehouse（湖仓一体） | 多引擎共读的唯一事实来源 | 表语义下沉到开放表格式（Iceberg / Hudi / Delta / Paimon），schema 随写事务提交 | 多引擎（BI / 流 / ML）共存的平台 | 表格式开源；catalog 可开源可托管 |
| 专有数据仓库 | 高并发点查与报表的加工区 | 封闭存储 + 列存 + CBO + 索引，读路径为点查与复杂查询深度优化 | 报表 / BI 为主、结构化数据为主 | 商业许可（按计算单元计费） |
| 轻量级单机方案（DuckDB / SQLite） | 百 GB 量级的分析 | 进程内引擎直接读 Parquet / 对象存储，无常驻服务 | 个人、小团队、临时分析 | 开源（内嵌，无服务端） |
| 多云联邦数据湖 | 数据不能集中时的联合视图 | 跨域只交换元数据与查询计划，不动数据本体 | 多法域、跨国集团 | 各域自建 + 联邦层 |

第二层是**组件级候选**——同一个架构选择下，换组件解决的是不同问题，不能互相替代：

| 组件位 | 候选 | 它决定什么 |
| --- | --- | --- |
| 存储底座 | S3 / OSS / COS / MinIO | 容量单价、请求单价、一致性语义（以厂商文档为准） |
| 表格式 | Iceberg / Hudi / Delta / Paimon | schema 演进、快照隔离、时间旅行、合并原语 |
| 计算 / 查询引擎 | Spark / Flink / Trino / StarRocks | 批、流、联邦查询、点查分别是四种不同优化方向的引擎 |
| 派生索引 | 向量库（Milvus 一类）、知识图谱 | 相似度与多跳关系的剪枝结构，都是派生态而非事实来源 |

组件位之间有一条纪律值得先记住：**表格式与引擎是两个可以分别更换的位，而它们经常被当成一套绑定产品来选**。同一张表格式上的表，Spark 能写、Flink 能流写、Trino 能联邦查、StarRocks 能点查——判断一个平台是不是真的把这两层分开了，方法就是看它能不能在**不搬数据**的前提下换掉其中一个（这与 7.3.2 的存算分离是同一条判断）。

这两层的关系是：**架构级选错，组件级无法补救**；组件级选错的代价通常是一个季度量级的迁移【经验：量级为季，见 7.7】。先分层再比较，可省掉一半的比较量。

候选还可以再按「族」归一次，同族内部差异小、跨族差异大：

- **自建重型族**（HDFS 数据湖、专有数据仓库）：共同点是存算一体或准一体、有常驻服务、依赖专业运维；族内选择主要取决于历史资产与合规，而不是性能。
- **云上分离族**（对象存储裸文件湖、Lakehouse、多云联邦）：共同点是存算分离、容量按量计费；族内的真正分歧只有一个——schema 与一致性由谁承担（表外约定还是表格式），这正是 7.3.1 的内容。
- **轻量族**（DuckDB / SQLite）：共同点是零常驻服务，随用随起；它不是「小号的 Lakehouse」，而是另一种产品形态——没有权限、没有共享、没有并发写。

**分族的意义在于：跨族比较时要问「我能不能换族」，族内比较时才问「选哪一个」。**绝大多数选型事故不是选错了族内的那一个，而是选了不属于自己约束条件的族（7.7 的反模式三）。

### 7.3 机制差异：为什么它们表现不同（核心节）

这一节的四个机制不是并列的四条优劣，而是有依赖顺序的：**7.3.1 决定一致性**，它是最上游的一条；**7.3.2 决定扩容与读取要付什么代价**；**7.3.3 决定这些代价的量级**（同样的机制下，文件布局可以把成本放大一个数量级）；**7.3.4 决定画出能力边界**——哪些查询根本不在这个架构的能力范围里。前三条都在「花多少」，第四条在「能不能」。比较候选时应按这个顺序问，因为下一条的问题总是由上面几条的答案决定的。

#### 7.3.1 schema 与一致性由谁承担

**机制是什么**：表结构变更与数据文件变更是不是**同一个原子提交**；如果不是，两者之间就存在一个「已经改了结构、还没改完数据」的窗口期。

| 承担层 | 代表 | 表结构存在哪 | 变更是否原子 |
| --- | --- | --- | --- |
| 表外 metastore | HDFS + Hive Metastore、对象存储 + 外部约定 | 独立元数据服务 | 否：结构推送与文件写入是两条路径 |
| 查询引擎（读时解释） | 裸 Parquet + 引擎按文件 schema 解析 | 文件头或口头约定 | 否 |
| 表格式（随写事务提交） | Iceberg / Hudi / Delta / Paimon | metadata.json / manifest / 事务日志 / 快照 | 是 |
| 专有仓库（封闭） | 数仓内部目录 | 引擎内部 | 是，但只在自家引擎内成立 |

**由此必然导出的性质**：因为表外 metastore 没有把结构推送与文件写入纳入同一个提交动作，所以当上游以「覆盖写某个分区」的方式更新数据时，下游必然存在一个能读到新旧混杂状态的窗口期，代价是排障时无法区分「数据算错了」与「读到了中间态」——这两类症状在监控指标上完全一样（§3.2.1 的失效点给的是同一条机制）。

**公开证据**：Iceberg 于 2018 年进入竞争（0.1 版本）、Delta Lake 于 2019 年由 Databricks 开源、Hudi 与 Paimon 各自形成流式合并路线——这批时间点可按各项目的官方 release note 与开源公告检索核验（主文件 §1.4 演进历程记录了同一批年份）【公开】；各项目的 release 与规范请按官方仓库当前版本核验。§3.2.3 给出的 Iceberg DDL 示例中，schema 与分区随写事务提交，而不是由另一条流程推送。

**失效条件**：当写入并发极低、上游从不覆盖写分区、且下游都能容忍读到中间态时（典型如每天一次的批处理、分区互不重叠），表格式的收益近乎为零，剩下的只有它的运维成本（catalog 常驻、合并调度、元数据层级要理解）。

一致性归属还决定了第二件事：**回滚是不是一次读旧快照**。因为表格式的写入产生的是不可变快照，所以「回滚到改动之前」在机制上等于把读取指针指回上一个快照，不需要另建一套备份；而表外 metastore 的方案里，改错了只能靠下游重跑或从备份恢复，恢复的时间上界由备份策略决定。这条差异在选型时经常被忽略，因为它只在出事那天才显形——判断方法很简单：问一句「上一次改错数据之后，你们是怎么回去的」，如果答案里出现了「找备份」，就说明当前方案没有快照级回滚。

#### 7.3.2 存储与计算是耦合还是分离

**机制是什么**：扩容时要不要搬数据、每次读取要不要付一次网络往返。

| 形态 | 代表 | 扩容动作 | 每次读的额外代价 |
| --- | --- | --- | --- |
| 存算一体 | HDFS 集群 | 加机器 + 搬数据（按副本数放大物理容量） | 无网络往返，但容量与计算必须一起买 |
| 存算分离 | 对象存储 + 临时计算集群 | 加一个按量计费的对象存储桶 | 每次 LIST / GET 走网络，重命名退化为逐对象复制 |

**由此必然导出的性质**：因为是存算分离，所以容量与计算各自伸缩、扩容不再需要搬数据，冷数据可以长期躺在低单价层上；代价是每一次扫描都要付一次网络与请求代价，而这一次代价的单价与**对象个数**正相关而不是与数据量正相关——于是同一条查询的成本会随文件数变化（与 7.3.3 咬合）。反过来，存算一体的本地读取没有这次往返，代价是容量与计算必须同步采购，且按主文件 §2.1 记载的默认副本系数（3 份）计，**每存 1 TB 数据要占 3 TB 物理容量**【推算：以默认副本数 3 为推导前提，有效容量单价 = 名义单价 × 3；具体集群配置请按 Apache Hadoop 官方配置文档当前版本核验】。

**公开证据**：2016 年 S3 + Athena 让「无 Hadoop 的数据湖」成为可能——这一时间点可按 AWS 官方的产品发布公告检索核验（主文件 §1.4 演进历程记录了同一年份）【公开】；主文件 §2.4 对比了 HDFS 与对象存储的扩展性、成本、性能与运维复杂度两条曲线。对象存储的一致性以「读后写」为语义，具体以厂商文档为准。

**失效条件**：当作业形态是「大量小文件随机读」时，存算分离的单价优势被请求数吃掉——每次打开文件都是一次网络请求，按请求计费的部分会超过按容量计费的部分，此时给计算集群加机器只能让更多小文件并行打开，压不掉单位文件的那次往返。

还有一条常被忽略的代价：**对象存储没有真正的目录**。文件系统里的「重命名一个目录」是一次元数据操作，在对象存储上退化为对每个对象逐个复制再加删除，而且这个过程不是原子的。所以任何依赖「先写临时目录再整体改名」来保证可见性的作业模式，在存算分离之后都会失效——它要么改为依赖表格式的提交动作，要么改为按对象单独提交并接受中间可见态。判断方法：搜索代码库里的「rename / move 目录」调用，逐个确认它在对象存储上的语义。

#### 7.3.3 文件布局：对象数与剪枝结构

**机制是什么**：数据在物理上被切成多少个对象，以及每个对象带不带**能用来跳过它的统计信息**。

- 表格式都提供「目标文件大小」一类的写入属性（§3.2.3 的 Iceberg DDL 把 `write.target-file-size-bytes` 设为 134217728 字节 = 128 MB；各项目的属性名与默认值以官方配置文档当前版本为准）【公开】。
- 列存格式（Parquet / ORC）在文件内部按 row group 组织，每段带 min / max、字典与行程编码，剪枝的最小单位是「文件 + 文件内的段」。
- 分区是**元数据对象**：查询规划阶段要枚举分区，分区数与规划时间同向增长。

**由此必然导出的性质**：因为列存把同列同质数据放在一起，所以扫描能按列剪裁并跳过统计信息不相交的文件；但这个收益的单位是「文件」，一旦写入侧把数据切成大量小对象，剪枝的单位从文件退化成目录，**剪枝收益被对象数反向吃掉**——代价表现为：作业成功、代码没改、过一段时间（典型是数月之后）同样的查询明显变慢【经验】，而加内存与加机器都无效，因为瓶颈是每个对象的那一次打开。

**产物量化**【推算：以 §3.2.3 DDL 中 128 MB 的目标文件大小为推导前提】：同一份 100 TB 数据，按 128 MB 落盘约 **82 万个对象**（100 TB = 100 × 2²⁰ MB ≈ 1.05 亿 MB，除以 128 MB ≈ 82 万）；若被高频微批写成 8 MB 的小对象，则约 **1310 万个对象**（除以 8 MB ≈ 1310 万）——对象数放大 **16 倍**，而查询规划要为每个对象付一次元数据读取与一次打开。这个推导的结论不是「必须 128 MB」，而是**对象数是一个独立的成本维度**：它不受容量单价影响，也不由数据量决定。

**公开证据**：主文件 §2.3 的「关键算法 / 方法」共列 6 项，其中第 5 项是「小文件合并（Compaction）」，并指出它在三个项目里的名字分别是 Iceberg 的 `rewrite_data_files`、Hudi 的 compaction、Delta 的 `OPTIMIZE`（三个命令名可按各项目官方文档当前版本核验）【公开】。判断方法：看「平均文件大小」与「每分区文件数分布」两个指标，它们可直接从目录清单或表格式元数据算出。

**失效条件**：当中游作业每天一次、每个分区输出一个大文件时，小文件治理的收益为零，此时引入常驻 compaction 只会白占计算资源。

同一套机制还有第二个出口：**分区与小文件的元数据条目数，会同时压制写入与规划**。表格式要为文件维护一层清单，清单的条目随写入次数单调增长；查询规划必须先读完清单才能确定要打开哪些文件，于是规划阶段的耗时与被维护的条目数同向变化。分区过度膨胀是同一个问题的另一种形态——分区本身也是元数据对象，按业务维度顺手分区、又从不清理历史分区，会让规划阶段被大量永不查询的分区拖住。两条修法一致：写入侧设目标文件大小与分区过滤检查，运维侧把「过期快照清理」与「历史分区归档」做成常驻任务，而不是等出了事故再补。

#### 7.3.4 模态决定了有没有可用的剪枝结构

**机制是什么**：不同查询类型需要不同索引结构；列存只服务于等值与范围的剪枝，不服务于相似度与多跳关系。

| 查询类型 | 可用的剪枝结构 | 放进列存文件后的后果 |
| --- | --- | --- |
| 点查（按主键取少量行） | 排序键、主键索引、catalog 级文件裁剪 | 需要扫描大量文件才能定位，规划开销大于取数开销 |
| 范围 / 聚合 | 分区 + 列存 min / max + 列剪裁 | 这是列存的主场 |
| 相似度（向量近邻） | 向量索引（HNSW / IVF 一类，由向量库提供） | 退化为全表扫描 + 逐行距离计算 |
| 多跳关系 | 图存储的邻接遍历 | 每一跳都要在列存上做一次全扫或大 join |

**由此必然导出的性质**：因为列存不提供相似度可用的剪枝结构，所以把 Embedding 直接存进 Parquet 后做近邻检索会退化成「全表扫描 + 逐行算距离」，代价是你只能靠加大计算资源换延迟——而加机器不改变扫描的数据量，只改变并行度，于是延迟改善会在某个点之后停滞。正确的位置是**派生索引**：原始事实留在湖里，向量与图谱都是可以从湖重建的派生态（§3.4 组合三给的正是这个职责边界）。

**公开证据**：本节这一条里**可公开核验的部分**是「列存格式不含为近邻检索设计的索引段，向量索引是另建、另刷的一份索引文件」——它体现在 Parquet / ORC 的文件结构定义与各向量库的索引构建文档中，可按各项目官方文档当前版本自行核验。同一条机制在书内也可回查：主文件 §1.1 的「是什么」把 Embedding 与二进制数据列为数据湖要承载的形态之一（原文：「多源异构：日志、JSON、Parquet、图片、视频、Embedding 都可以存」）；§3.2.5 多模态数据湖的「被什么约束逼出来」段，以及 §3.1 约束表「相似度查询与等值查询要不同的索引结构」一行，写的是同一条。后三处是书内交叉引用，不构成公开来源，故不挂【公开】档。具体向量索引类型与参数请按各向量库官方文档当前版本核验。

**失效条件**：当检索规模小到可以每次全量算距离（比如万级向量）时，引入向量库的收益为负——多出来的是一套需要刷新与版本管理的派生索引。

派生索引真正难的不是建立，而是**保持它与事实来源一致**：嵌入模型升级一次，全量向量都要重算，否则新旧向量在同一个索引里不可比；图谱的抽取规则改一次，历史节点的属性就与新节点来自两套口径。所以这两类派生索引都必须具备两个性质：**有明确的版本标记**（哪批向量由哪个模型产生），以及**可从湖全量重建且重建过程幂等**。缺少这两条时，派生索引会悄悄变成第二个事实来源，而这正是 7.7 反模式二的起点。判断方法：问「上一次全量重建是什么时候、用了多久、重建期间线上还能不能查」，答不上来说明它已经不可重建了。

### 7.4 成本结构对比（不是价格表，是成本函数）

把上面三节的机制写成式子，湖类方案的成本函数大致是：

```
成本 ≈ 容量单价 × 有效保留容量            （受副本数、压缩比、分层策略影响）
     + 请求单价 × (对象数 × 访问次数)      （受文件布局影响，与数据量无关）
     + 计算单价 × 扫描量                  （受剪枝结构与引擎影响）
     + 常驻服务的固定成本 + 人力           （catalog、合并调度、元数据服务）
```

各候选的**主导项**与**隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| HDFS 数据湖 | 常备集群容量（含副本放大） | 扩容要搬数据；元数据服务的内存被文件数消耗 |
| 对象存储裸文件湖 | 容量 + 请求 | 小文件的请求费；没有表格式时要额外养一套治理人力 |
| Lakehouse | 容量 + 合并计算资源 | catalog 成为单点与共享依赖；快照与清单本身占存储 |
| 专有数据仓库 | 常备计算容量（闲置也付） | 数据装载与搬运；封闭格式让换引擎等于换仓库 |
| 轻量级单机 | 单机内存与磁盘 | 无并发共享；无权限与治理能力，多人协作要靠拷文件 |
| 多云联邦 | 各域本地成本之和 | 跨域查询反复付费（不物化中间结果）；跨域元数据映射的维护 |

【推算：冷数据分层，以对象存储标准层约 $0.023/GB-月为推导前提（主文件 §1.1 把这笔单价标为「S3 Standard-IA」，而 $0.023/GB/月 这个量级对应的是标准层——本节按标准层取值，具体档位与单价以云厂商定价页当前版本为准）】1 PB 按 10⁶ GB 计：标准层月费 ≈ 10⁶ × 0.023 ≈ **2.3 万美元/月**，年费 ≈ **28 万美元量级**；若把这批只读冷数据挪到归档读层（约 $0.004/GB-月 量级，仍按 10⁶ GB）：月费 ≈ 10⁶ × 0.004 ≈ **4 千美元/月**，年费 ≈ **5 万美元量级**——两者相差约 **5–6 倍**。这条推算的结论不是「一定该分层」，而是**分层的收益由「访问概率随数据变老的衰减速度」决定**：如果热数据占比很高，分层只是把热数据的读延迟换成了冷数据的存储费；反过来，如果 90% 以上容量是三年不动的原始数据，分层是这份成本函数里唯一量级级别的杠杆。

【经验】小团队最常低估的不是容量，而是**常驻组件的人力**：Lakehouse 全家桶需要有人管 catalog、管合并调度、管元数据层级；这个角色一旦空缺，系统会在「不报错但越跑越慢」的状态里运行很久才被发现（与 7.3.3 的失效形态一致）。在百 GB 到个位数 TB 的规模上，把这三件事的工时折算进去之后，轻量级方案往往是净胜的。

【推算：合并成本的量级，以「重写前的数据必须被完整读一遍」为推导前提】合并（compaction）的代价 ≈ **读一遍 + 写一遍被重写的字节数**。设某湖每天新增 1 TB 数据、全部以小文件形式落盘，且当天就把它们合并成大文件：则每天多出约 2 TB 的读写量（读 1 TB + 写 1 TB），是一份**与写入速率成正比**的固定开销，而不是与总数据量成正比——这份开销不随湖里存量变大而变大，只随写入变快而变快。这解释了两个常见现象：以「读为主、写入低频」的湖几乎不需要为合并做预算；而以流式持续写入的湖，合并会与查询争抢同一批计算资源，出现「查询变慢不是因为数据多了，而是因为合并任务同时在跑」。控制手段有两条且必须同时用——写入侧把文件写大（减少需要合并的量），运维侧给合并单独规划资源与优先级（避免它和查询互相踩）。

**在哪一项花力气：读三个数就够了**。成本函数里四项主导项各自对应一个可观测信号：**平均文件大小与每分区文件数分布**（持续下降说明请求项在变大）、**对象存储请求费用在总存储费用中的占比**（占比超过容量项说明访问形态已经是「大量小对象」）、**合并滞后量（未合并文件数与未合并字节数）**（持续上升说明写入速率已经超过合并吞吐）。这三个信号都不需要新埋点，从现有元数据与账单里就能读出，比「数据量到了多少 PB 该换架构」这种判断可靠得多（§3.6 给的是同一组信号）。

**这份成本函数还有一个用法：判断「加钱能不能解决问题」**。四项里，容量项与计算项是可以靠花钱买到的（分层、加机器）；请求项与固定人力项买不到——请求项随**对象数**增长，而对象数由写入形态决定；固定人力项随**治理复杂度**增长，而复杂度由元数据层级数决定。所以当一份账单里请求项或人力项开始占主导时，正确的动作是改架构（写入侧控制文件大小、减少常驻组件），而不是加预算——这也是 7.7 三条反模式的共同经济根源。

### 7.5 决策树（每个分支都要有阈值依据）

用这棵树的方式是**从上往下依次问，第一个命中你的分支就是你的位置**，不需要把全部节点答完。前两个节点（T1、T2）是硬约束，答完之后基本已经锁定族；中间的 T3–T5 决定你要不要补一致性、要不要先治文件布局；后面的 T6–T8 是能力扩展，**它们与 T5 的答案正交**（入湖时效、派生索引、法域都不由查询形态决定），所以树里两支到 T5 之后合流，无论落在哪一支都要继续答这三项——只有当你确实有那类查询或那类合规要求时，答案才会改变你的架构。树上每个带编号的节点，都在树后的「阈值依据」里有且仅有一条对应解释，并且给出了**在你自己的环境里怎么重新算这个阈值**的方法——阈值是可以被替换的，机制不能。

```
T1 一次典型查询要扫的数据，能装进一台机器吗？
├── 能（百 GB 量级）且没有任何常驻运维
│     └── DuckDB / SQLite 直接读对象存储或本地 Parquet
└── 不能 → 继续
    │
    T2 数据必须留在自建机房，或历史资产搬迁不可行？
    ├── 是 → 底座选 HDFS + Hive Metastore（存量延续）
    └── 否（数据可以在云上）→ 底座选对象存储 + 临时计算集群
        │
        T3 上游会覆盖写分区，或有并发写同一分区吗？（两种底座都要问）
        ├── 会 → 补一张开放表格式把一致性补上
        │        （HDFS 上 Iceberg / Hudi；对象存储上 Iceberg / Paimon / Delta 均可）
        └── 不会 → 维持裸文件 + 外部约定，但必须监控 T4
            │
            T4 平均文件大小是否持续低于写入侧目标值的 1/2？
            ├── 是 → 先做 compaction（rewrite_data_files / compaction / OPTIMIZE
            │        是同一件事的三个名字），不要先想着换引擎——换引擎不改变对象数
            └── 否 → 继续
                │
                T5 读模式以「按主键取少量行」和报表为主，还是以「按条件扫大量行」为主？
                ├── 点查 / 报表为主 → 再问一个节点（T5b）：湖与仓要不要各存一份全量？
                │   ├── 数据量 < PB → 不必：湖仓一体（一份数据 + StarRocks 一类点查引擎）即可
                │   └── 数据量 ≥ PB → 仓侧只保留聚合结果，不让湖与仓各存一份全量
                └── 扫描 / 聚合为主 → 对象存储 + 开放表格式（Iceberg / Paimon）
                    + Spark / Flink + Trino

                ※ 两支在此合流。T6–T8 与 T5 的答案正交——入湖时效、派生索引、法域都不由查询形态
                  决定，所以无论上面落在「点查 / 报表为主」还是「扫描 / 聚合为主」，都继续答下面三项。

                T6 入湖时效要求是 T+1，还是分钟级？
                ├── 分钟级 → 实时数据湖（流式表格式 + 常驻 compaction）
                └── T+1 → 上面那条批量入湖路线即可
                    │
                    T7 是否需要相似度检索或多跳关系推理？
                    ├── 相似度 → 数据湖 + 向量库（Milvus 一类），向量是派生态
                    ├── 多跳关系 → 数据湖 + 知识图谱（GraphRAG），图谱是派生态
                    └── 都不需要 → 保持单一事实来源，不引入派生索引
                        │
                        T8 数据是否不允许离开某一法域？
                        ├── 是 → 多云联邦数据湖（跨域只交换元数据与查询计划）
                        └── 否 → 单一区域集中存储
```

**阈值依据**（与树上每个带编号的判断节点 T1–T8、T5b 一一对应）：

- **T1「能装进一台机器」**：依据是**单机的物理上限而非成本**。进程内引擎把工作集放在本机内存与磁盘上，一旦一次查询的工作集超过单机容量，收益会迅速消失（磁盘溢写与内存不足是同一件事的两个阶段）。判定方法不是看数据总量，而是看「一次典型查询要扫的列与分区能不能装进一台机器」。
- **T2「搬迁不可行」**：依据是**出网带宽与合规审批的共同下限**，不是数据量数字。判定方法：如果「把全量数据搬一次」所需的窗口期长于业务可接受的中断窗口，即视为不可行。
- **T3「上游会覆盖写分区」**：依据是 7.3.1 的机制——**只要存在「结构或数据被覆盖写」这种非原子更新，就一定存在能被下游读到的中间态**；这条与规模无关，几十 GB 的集群同样成立，所以它在两种底座（HDFS 与对象存储）上都要问，不该被规模判断跳过。
- **T4「平均文件大小低于写入侧目标值的 1/2」**：依据是 7.3.3 的机制——剪枝与打开的单位是文件，持续低于目标的一半说明写入侧在造小文件，而这与容量单价无关。用「目标值的比例」而不是一个绝对兆字节数，是为了让它随你的目标文件大小设置一起移动。
- **T5「点查为主 vs 扫描为主」**：依据是**同一份数据上两种剪枝结构不通用**：点查的成本几乎与表总量无关、与定位路径有关；扫描的成本与扫描量线性相关。判定方法从现有监控即可读出：比较「单次查询扫描的数据量 / 返回行数」的比值——比值大说明走的是扫描型通道，把这类查询交给扫描引擎，加机器不会降低单位查询的扫描量。
- **T5b「数据量 < PB 时不必让湖与仓各存一份全量」**：依据来自 7.4 的成本函数——在 PB 量级、冷数据占比高时，**容量项是主导项**，保留两份全量等于把主导项翻倍，并额外买下一条同步链路与一次口径漂移风险；在 PB 以下，容量的绝对金额还没有大到需要为此牺牲一份数据的完整性，此时「湖仓一份数据 + 支持点查的引擎」是更省的形态。判定方法：把你的容量单价乘以两份全量与一份全量的差额，再对比为点查单独维护一套仓副本的固定成本（常驻计算容量 + 同步链路 + 运维人力）——差额更大时选一份全量，反之选两份。
- **T6「T+1 vs 分钟级」**：依据是写入频率与对象数的关系——按批到达可以用批写控制文件大小；持续到达只能靠高频微批或流式写入，前者在目录里堆小文件（T4 的成因），后者要求表格式支持流式写并配常驻 compaction。
- **T7「是否需要派生索引」**：依据是 7.3.4 的机制——**列存没有为相似度设计的剪枝结构**，所以这类查询要么退化，要么另配索引。判定它是否值得引入，看的不是查询类型，而是「全量算一次的代价 × 查询频次」是否超过一套派生索引的刷新与运维成本。
- **T8「法域」**：依据是合规约束而非技术约束——数据驻留要求与「一处集中存储」在机制上直接冲突，只能靠联邦（交换元数据与计划、不动数据本体）绕开。判定方法是盘点：是否存在某个法域的数据被要求不得出现在该法域以外。

**树上的 T4 值得单独强调**，因为它排在其他能力扩展之前：文件布局是**唯一一项「不换架构也能改善」**的项。把目标文件大小写进表属性、把合并做成常驻调度，这两件事在任何一种湖上都能做，而且做完之后前面几个节点的压力会一起下降——扫描变快（规划的对象变少）、请求费下降（对象变少）、合并成本可控（写入侧不再造小文件）。反过来，如果跳过 T4 直接去换引擎，多半会得到「换完了还是慢」的结论，因为瓶颈根本没在引擎上。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 自建机房、历史资产搬迁不可行 | HDFS + Hive Metastore 存量延续 | HDFS + 开放表格式 | 对象存储方案在这里要额外承担搬迁带宽与合规审批 |
| 云上、批量入湖、扫描聚合为主 | 对象存储 + Iceberg / Paimon + Spark / Flink | 对象存储 + Hudi / Delta | 裸 Parquet + 外部约定无法原子提交结构变更 |
| 同上有高并发点查 / 报表 | 湖仓一体（表格式 + StarRocks 一类点查引擎） | 湖 + 仓两份，仓侧只留聚合结果 | 让扫描引擎兼做点查：加机器不改变扫描量，改变的是并发数 |
| 报表与 BI 为主、结构化数据为主 | 继续用数据仓库 | Lakehouse + 点查引擎 | 全量迁湖会把数仓已有的 CBO 与点查优化换成全表扫描 |
| 分钟级入湖 | 实时数据湖 + 常驻 compaction | 高频微批 | 高频微批在目录里堆小文件，成本在数月量级后才出现【经验：量级为月】 |
| AI 相似度检索 | 数据湖 + 向量库（Milvus 一类） | 湖内向量列 + 引擎侧向量算子 | 没有向量索引时相似度退化为全表扫描与逐行计算 |
| 实体关系推理 | 数据湖 + 知识图谱（GraphRAG） | 关系表存边 + 多跳 SQL | 多跳遍历在列存上每一跳都要重扫 |
| 多法域 / 跨国 | 多云联邦数据湖 | 单一集中集群 | 数据驻留要求与集中存储直接冲突 |
| 百 GB、无常驻运维 | 轻量级（DuckDB / SQLite + 对象存储或 MinIO） | 最小化 Lakehouse | 湖仓全家桶的常驻组件在这个规模下无人维护 |

**这张矩阵里最容易被误选的一对，是「湖仓一体」与「湖 + 仓两份」**。两者读起来都是「湖 + 仓」，差别只在数据被存了几份：湖仓一体是一份数据、两种引擎通道；湖 + 仓是两份数据、一条同步链路。误选的实际后果不是「慢一点」——两份全量意味着**同一个口径有两个物理实现**，当两边对不上时没有任何机制能判断谁对，排障时间会从「查一次血缘」变成「对两套数」；而同步链路一旦中断，仓库侧的数据会静默变旧，看板上不会报错，只会给出昨天的答案。所以这一对的选择不该由性能决定，而应由 7.4 的成本函数决定：容量项是主导项时选一份，不是主导项时再谈两份带来的点查收益。

**四条组合的共同代价，是「多出来那一件的刷新责任」**：向量要刷、图谱要刷、仓侧的聚合要刷。它们各自的刷新触发条件不同（上游变更事件、模型版本、调度周期），但都遵循同一条规则——**派生件的刷新必须由上游变更驱动，不能靠人工调度去追**。人工调度的派生副本会在某个不忙的季度被停掉，然后以「数据看起来是对的、其实慢了两周」的形式存在很久。

**常见组合及其职责边界**（组合的价值在于**边界清楚**，不在于件数多）：

- **组合一：数据湖 + 数据仓库（湖 + 仓两份）**。这里指的是上文定义的「两份数据」形态，不是「一份数据两种引擎通道」的湖仓一体：湖存原始与长尾数据（Schema-on-Read、低成本），仓存加工结果与高并发点查；口径收敛只发生在仓侧，湖侧不做清洗。运维代价：两套元数据与两套权限体系，需要一条明确的「湖 → 仓」同步链路，并处理两边同名不同义的口径漂移。
- **组合二：数据湖 + 向量库**。湖存原始与事实，向量库存 Embedding 与索引（联邦查询引擎可经向量库连接器把两边拼在一次查询里）；**向量是派生态，由上游变更事件驱动刷新**。运维代价：嵌入模型版本与索引版本要成对管理，跨系统查询多一层编排。
- **组合三：数据湖 + 实时数仓**。湖存全量历史，实时数仓存近实时聚合。运维代价：同一口径两处实现，必须事先规定「谁是真源、对不上时以谁为准」，否则排障会变成两套数打架。
- **组合四：数据湖 + 知识图谱（GraphRAG）**。湖存原始事实，图谱存从湖中抽取的实体与关系。运维代价：图谱 schema 版本管理、抽取质量校验、以及抽取任务的幂等重建能力（图谱必须是可重建的，否则它就成了第二个事实来源）。

这四条组合有一个共同的选型纪律：**每引入一件，就要能回答「它的刷新由谁触发、它坏了由谁发现」**。答不上来的一律先不加——多一件派生件带来的不是能力，而是多一条会静默失效的链路。

### 7.7 选错的代价与迁移成本

**反模式：把裸文件湖当数据仓库用** —— 症状是报表查询直接跑在湖的全量文件上，与其他批作业争抢同一批计算资源；后果是扫描型引擎做点查，代价随数据量线性增长，团队把这种互相拖累误判为「资源不足」，继续加机器，而加机器既不能把扫描变成点查，也补不上没有的原子提交（§3.5 的同一条机制）；正确做法是按 7.3.3 先把文件布局与分区收干净，再按 7.5 的 T5 为点查单独配一条通道，而不是把两类查询放在同一个引擎上排队。

**反模式：派生索引反客为主** —— 症状是向量库或图谱被当成「数据在哪就以哪为准」，而上游湖里的原始数据被当成历史遗留；后果是派生副本一旦与事实来源不一致，就没有任何机制能判断谁对，重建也不敢做（重建会丢掉副本上独有的内容）；正确做法是把「湖是唯一事实来源、向量与图谱可随时从湖重建」写成硬约束，并定期做一次全量重建演练来验证这条约束是真的。

**反模式：为「以后可能要」先上湖仓全家桶** —— 症状是百 GB 规模、两三个人的团队，已经需要维护 catalog、合并调度、流作业与两套权限；后果是常驻组件的人力被摊薄到无人专精，任何一次升级都要停摆，最后团队退回去用导出文件；正确做法是按 7.5 的 T1 先接受轻量方案，把模式切换点绑在可观测信号上（平均文件大小、查询扫描量 / 返回行数比值、对象存储请求费占比），而不是绑在「未来业务会增长」这句话上。判断自己是否已经在犯这条错误，有一个很直接的问题：**上一次有人完整升级过这套栈里的每个组件，是什么时候？** 如果答不出来，说明组件数量已经超过了团队的运维带宽。

**换成另一个要动什么**：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| HDFS → 对象存储 + 表格式 | 全量搬迁一次，受出网带宽限制【经验：量级为周】 | 路径与 `LOCATION` 语义改为 catalog 语义【经验：量级为周】 | 新建 catalog、合并调度、权限体系【经验：量级为月】 | 表格式元数据层级、快照与合并【经验：量级为月】 |
| 裸文件湖 → 表格式（原地） | 无需搬数据，只需注册已有文件【经验：量级为天】 | 外部约定与 glob 表达式改为 catalog 语义【经验：量级为周】 | 新增 catalog 与合并调度【经验：量级为月】 | 变更流程要接影响面分析【经验：量级为周】 |
| 数据仓库 → 湖仓一体 | 存量数据导出为开放格式，受导出吞吐限制【经验：量级为月】 | 专有 SQL 方言与优化器提示要重写【经验：量级为月】 | 从「买容量」变成「运维 catalog 与引擎」【经验：量级为季】 | 引擎调优与表格式维护是两套技能【经验：量级为季】 |
| 单一集群 → 多云联邦 | **不搬数据**，只做元数据映射与统一资产 ID【经验：量级为月】 | 跨域查询要改写并接受跨域延迟【经验：量级为周】 | 各域本地运维 + 联邦层【经验：量级为月】 | 从技术问题变成权责与合规谈判【经验：量级为季】 |
| 轻量单机 → 湖仓一体 | 文件布局要重新整理（分区、目标文件大小），不是简单拷目录【经验：量级为周】 | 「文件路径即表名」的约定整体替换为 catalog 语义【经验：量级为周】 | 从零建 catalog、合并调度与权限【经验：量级为月】 | 单机 SQL 与分布式引擎的执行模型不同【经验：量级为月】 |

这张表有一列值得单独看：**「数据迁移」这一列最容易被我低估，而最难的那一列其实是「团队再学习」**。搬数据有工程手段（限速拷贝、双写、双读校验），可以按周排期；而一个团队从「改完就发」转到「先看影响面再发」所需要的习惯改变，只能用月甚至季来计——这也是 7.7 三条反模式的共同修复成本：**它们要修的不是系统，是流程与习惯**。所以最省钱的时机永远是把这一列的成本提前算进去，而不是在迁移启动之后。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 百 GB 量级、无常驻运维 | DuckDB / SQLite + 对象存储或 MinIO | 无并发共享需求时，常驻组件的人力成本大于它带来的任何收益 |
| 自建机房、资产搬不动 | 留在 HDFS，但按 T3 判断是否补表格式 | 存算一体的扩容曲线不可变，能改的只有一致性归属 |
| 云上、批量 + 扫描为主 | 对象存储 + 开放表格式 + Spark / Flink + Trino | schema 随写事务提交，把一致性从流程问题变成结构问题 |
| 云上、另有高并发点查 | 湖仓一体，或湖 + 仓且仓侧只留聚合 | 点查与扫描是两种剪枝结构，不通用 |
| 需要分钟级入湖 | 实时数据湖 + 常驻 compaction | 持续写入与「大文件」是一对矛盾，只能靠常驻合并维持 |
| 需要相似度 / 多跳关系 | 湖 + 派生索引（向量库 / 图谱） | 列存没有为这两类查询设计剪枝，派生索引必须可重建 |
| 多法域 | 多云联邦数据湖 | 数据驻留与集中存储机制上冲突，联邦交换的是元数据而非数据 |
| 报表为主、结构化为主 | 留在数据仓库，或让仓承担这一层 | 专有引擎的点查与 CBO 在扫描型引擎上没有对应物 |

上面八行可以压缩成一句话：**先确认你的约束落在哪一族，再在族内按「一致性归属」和「剪枝结构」两个机制选一个**。落到具体动作上，第一次选型时最值得做的三件准备是：① 用现有监控量出「平均文件大小 / 每分区文件数 / 扫描量对返回行数的比值」这三个数（它们决定你走 T4 还是 T5）；② 数一下愿意长期投入的运维人数（它决定 T1 与财力的边界）；③ 把「上游会不会覆盖写分区」问清楚（它决定 T3 的答案，而 T3 是唯一与规模无关、却最容易出事故的一条）。

三个最容易被忽略、但会在半年量级后显形的检查项【经验：量级为季到半年】：

- **你有没有一条可观测的「平均文件大小」指标？** 没有它，小文件积累的过程是静默的，等被发现时已经是一整年的写入习惯。
- **catalog 或元数据服务是不是共享依赖？** 是的话，它的可用性等于全平台写入的可用性，需要按核心系统的标准做备份与演练。
- **回滚路径是不是「指回旧快照」？** 如果答案是「从备份恢复」，说明当前方案的写入不是快照语义，出事那天的时间上界由备份策略决定（7.3.1）。

> 本节小结：这一组候选之间**唯一真正起决定作用的差异是「schema 与一致性由谁承担」**——它决定了改结构要不要重写数据、下游会不会读到中间态；其余差异（扩容曲线、文件布局、剪枝结构、模态索引）都在它的下游，都是可以逐个补上的工程问题，而这一条补不上就只能迁架构。
