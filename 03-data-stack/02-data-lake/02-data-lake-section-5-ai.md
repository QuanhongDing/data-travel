## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

「向量原生」「AI 原生」「自治」这三个词的问题在于，它们把改动究竟发生在哪一层这件事藏了起来。摊开看：向量进湖改的是**剪枝结构**——列存格式没有为相似度检索设计的索引段，把 Embedding 存进 Parquet 之后做近邻查找会退化成「全表扫描 + 逐行算距离」（[§7 §7.3.4](02-data-lake-section-7-sec7.md) 把这条机制写成了「模态决定有没有可用的剪枝结构」）；AI 元数据改的是**元数据的生产成本**，不是元数据的定义权；自然语言入湖改的是**配置链路的作者**；Agent 触达改的是**调用者的身份**。四件事不在同一层，既不能一起排期，也不能互相替代：把「AI 元数据」做完，不会让近邻检索变快一分。

第二个问题是没有时间维度。同一个清单里，「已 GA 且有人在生产用」与「路线图里的条目」被并列成同样的句式，读者据此排路线图就会踩空：前者值得投人，后者连预算都不该批。本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（或版本化发布的规范）；② 有第三方（非厂商）公开生产案例；③ 接口稳定、可预期。
- **L2 可试点**：①③ 大体满足但 ② 不满足；或能力可用而判定标准尚未形成共识。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。

为什么是这三条，而不是「有没有厂商在推」：厂商在推是营销事实，不是成熟度。① 回答「它是发布过的，还是演示过的」；② 回答「出问题时我能不能找到别人的经验，而不是厂商的承诺」；③ 回答「我明年会不会为它重写一遍」。**② 只有两种命运：满足，或降为 L2。** 不存在「L1 的边界案例」这种写法。

第三个问题是本主题特有的三处易错，写到时必须逐条避开：

- **产品名与能力名混淆**。「向量原生数据湖」是能力名，不是产品类别；「Iceberg V3 支持向量类型」这句话的判定入口只有一个——Iceberg 官方规范的类型（Types）章节里有没有向量 / 定长浮点数组的类型定义。这里有一个几乎必然发生的张冠李戴：**「删除向量（deletion vector）」是行级删除的实现细节，「向量类型」是列类型**，两者名字相近、毫无关系，读到「向量」二字就下结论是本节最常见的错误。
- **预览与 GA 混淆**。各平台的自然语言取数能力在不同年份处于不同状态（预览 / GA），判断某个能力现在能不能依赖，看该产品的发布说明里这一条目的状态与生效条件，不看发布会。
- **论文里的原型与产品里的实现混淆**。论文提出的机制与产品是否采用它是两件事；产品是否采用，只能查该产品官方文档的配置与类型章节。

其余方向为什么不够格，只有两种原因：**② 拿不出 → L2**（向量原生、AI 元数据、AI 治理、Agent 触达、多模态 RAG、湖 + RAG）；**① 不成立 → L3**（自然语言入湖、GraphRAG）。湖 + RAG 虽同样归 L2，性质却与前面几项不同——**它的机制就是第 1 行那条 L1**，缺的是「把它落成一套可运维的检索层」的第三方材料（重建脚本、双版本共存、分数口径），所以 §5.3 接口表把它记作「需自建（L2）」，级别与这里一致。L2 不是永久档位，给 L2 方向预先写好升 L1 的条件比年底重评一次更有效：向量原生的升级条件是**表格式规范的类型章节里出现向量类型、且索引随快照版本化**；AI 元数据的升级条件是**第三方公开可复现的质量评估方法**；AI 治理的升级条件是**分类器的漏检率口径被公开**；Agent 触达的升级条件是**权限模型里出现「非人主体」这一档**；湖 + RAG 的升级条件是**出现第三方公开的重建演练材料**（全量重建耗时、重建期间线上可用性）。五条都是可观察的，不是感觉。

读这张表时有三个动作，顺序不能换：

1. **先定位事实来源**——你的向量、图谱、搜索索引，哪一份是权威？答不出权威在哪，后面所有评估都没有基准。
2. **再验可重建性**——派生件能不能从湖全量重算？上一次全量重建是什么时候、用了多久、期间线上还能不能查？答不上来说明它已经不可重建（[§7 §7.7](02-data-lake-section-7-sec7.md) 的「派生索引反客为主」正是从这个缺口开始的）。
3. **最后才看 AI 功能清单**——元数据生成、PII 分类、自然语言取数都是在这两件事确定之后才需要精算的第二层问题。

### 5.2 演进方向逐条拆解（核心节）

下面四个小节（覆盖 5.1 表里的八个方向，第 7 行「湖 + RAG」放在 §5.3 的接口表里讲）都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向在评审时应被直接打回：本主题里每一次「AI 让数据湖更好用」，都对应着一处被搬到别处的成本。

读这套结构有两个约定。**第一个，「机制」必须落在介质、结构或责任归属上**——是「向量变成表的一列」，是「元数据的生产成本下降」，还是「调用者从人变成 Agent」。落不到这几件事上的，都只是评价。**第二个，「代价」必须是一个可被观测的量**——重建窗口、刷新滞后、索引规模、格式硬约束。写成「需要投入学习」的，不算代价。

#### 5.2.1 湖作为唯一事实来源：本主题唯一的 L1（派生件的重建是它的运维要求，另判 L2）

- **旧做法与它的卡点**：AI 要用的向量索引与图谱，常常被建成第二个事实来源——它们自己接收写入、自己保留独有内容，于是「湖里的数据和检索到的数据哪份对」变成一个无法回答的问题（[§7 §7.7](02-data-lake-section-7-sec7.md) 把这条列为反模式之二）。卡点不在检索性能，而在**权威的归属**：只要有两个可写副本，就没有机制能判断谁对。
- **AI 改变了什么机制**：**把「唯一真源」钉在湖上，把向量与图谱降级为可从湖重建的派生态**。注意这不是新增一个组件，而是改变一条责任边界：湖持有原始二进制与事实，索引只持有「指向资产 ID 的嵌入」，模型版本记在事实侧而不是索引里（[§3 §3.2.5](02-data-lake-section-3-sec3.md) 给出的 `embed_model` / `embed_version` 两列正是这条边界的落地形态）。
- **由此得到的**：**因为事实来源唯一、派生件可重建，所以「AI 检索结果与报表口径对不上」这类问题被降级成一次重算的工程问题，而不是一场对账**；**因为重建是幂等的全量动作，所以换嵌入模型从一次数据迁移变成一次可排期的作业**——这两条合起来，才是「AI 可以放心把湖当数据源」的真正含义：它靠的不是湖大，而是湖可回退。

```text
派生件的三个问题，答不上来就先别建
  ① 谁是真源？      湖（原始二进制 + 事实 + 模型版本）
                    索引只持有 (asset_id, embedding)
  ② 谁触发刷新？    上游变更事件，不是人工调度
                    —— 人工调度的副本会在某个不忙的季度被停掉，
                       然后以「数字看起来对、其实慢了两周」的形式存在很久
  ③ 重建要多久？    全量重建的时间上界 + 期间线上是否还能查
                    —— 答不出这一条，等于把检索层做成了不可替代的黑盒
  ────────────────────────────────────────────────
  关键：这三问都不涉及算法，只涉及责任归属；
        它们决定了换模型那天是「跑一个作业」还是「做一次迁移」
```

- **由此付出的**：**其一，刷新链路成为新的静默失效点**——它坏掉时不报错，只安安静静地保留旧版本，所以每个派生层都必须携带「数据截止时间」并被下游读到，否则「查询成功」会被误读成「数据新鲜」；**其二，重建窗口内要处理双版本共存**——新旧模型产出的向量不在同一个向量空间，混在一起做相似度比较没有意义，而重建需要时间（[§3 §3.2.5](02-data-lake-section-3-sec3.md) 的失效点给的是同一条）；**其三，派生件本身就是第二份数据的成本**——它的容量与刷新费用不会因为「它是派生的」而消失，见 §5.2.2 的量级估算。
- **证据与来源**：【公开】表格式一侧有版本化规范与 release note（Apache Iceberg 的官方规范与各版本 release note、Delta Lake 的 `_delta_log` 文档、Apache Hudi 的 timeline 文档、Apache Paimon 的 release note 与快照文档，均为可点开的官方文档，核验时以你所用的那个版本为准）；对象存储 API 与 Parquet 读取接口多年稳定。第三方（非格式厂商）生产案例见本目录 [§6](02-data-lake-section-6-sec6.md) 的字节（Iceberg 数据湖，流批共写一张表）；同节的 Netflix 是 Iceberg 的**发起方**（2017 年启动该项目，开源后捐给 Apache 基金会），它的自述属「厂商自有案例」，不计入这一条。**本节不给任何「湖上检索多少毫秒」的数字**：那类数字缺少数模、维度、召回目标与缓存状态这些条件，跨场景不可比。**判定方法**：这条 L1 判的是「生产写入是不是都落到同一张表、有没有第二个可写副本」；同一小节标题里那条「派生件的重建」另有判定方法——问「上一次全量重建是什么时候、用了多久、重建期间线上还能不能查」，三个答案都能给出，「派生件可重建」在你环境里才算成立。
- **成熟度**：**L1（只发给「湖是唯一事实来源」这半条）。** 判据：① 版本化规范与 release note（上一条列了各处文档名，以你所用的那个版本为准）；② 第三方非格式厂商生产案例（§6 的字节：它是用 Iceberg 的公司，不是定义它的公司，材料内容是流批共写一张表；Netflix 是发起方，不计入）；③ 接口多年稳定。**本节一并讨论的「派生件可重建」不在这条 L1 内**：它是一条运维要求，其第三方材料（全量重建耗时、重建期间线上可用性）本节列不出来，按 §2.1 的判据只能是 L2——5.1 表第 7 行给的就是这个级别，与本段一致。**降级条件**（说的是级别会不会掉，与上面那条口径是两件事）：若某个你依赖的表格式把「快照 / 权限」相关能力退回实验性条目，或③不再成立（例如强制绑定某一家的 catalog 实现），本方向降回 L2。
- **失效条件**：当湖里根本没有需要被检索的非结构化资产时（纯结构化报表场景），把向量与图谱做成「可重建的派生件」不带来任何收益，只多出两套刷新链路——此时正确的动作是不引入它们（[§7 §7.5](02-data-lake-section-7-sec7.md) 的 T7 给的是同一条判断）。**判定方法**：统计生产查询里真正需要相似度或多跳关系的请求占比，接近零就说明「派生件可重建」这条要求与你无关。
- **自验方法**：挑一个派生件，从零开始做一次全量重建，记录三件事——耗时、期间线上是否可查、重建后与重建前的召回差异。这次演练是**派生件可重建**这条运维要求在你环境里唯一的实证；没做过演练的「可重建」只是设计意图（这条要求自己的级别见上一条）。

三类派生件的边界不同，混成一类管理就会出错：

| 派生件 | 交接物 | 过期有几种来源 | 判定它是否过期的方法 |
| --- | --- | --- | --- |
| 检索索引（向量 / 全文） | 资产 ID + 嵌入 + 模型版本 | 两种：数据更新、模型更换 | 比对数据版本，同时比对索引构建时所用模型版本 |
| 知识图谱 | 实体 / 关系 + 抽取规则版本 | 两种：数据更新、规则更换 | 看抽取作业的截止时间与规则版本号 |
| 实时 OLAP 副本 | 聚合结果 + 刷新批次 | 一种：刷新链路滞后 | 看查询结果里附带的「数据截止时间」，不看服务是否存活 |

这张表的意义在于第三列的差异：**「模型换了、数据没变」这一类过期无法通过比对数据版本发现**，只能靠记录「这份索引是用哪个模型 / 哪版规则构建的」——而这一列最容易在建索引时被省略，事后补不回来。

#### 5.2.2 向量原生与多模态 RAG：列进了表，索引还在表外

- **旧做法与它的卡点**：非结构化资产的处置一直是两套——原始二进制放在对象存储里，嵌入放在向量库里，两者靠一个 ID 硬关联。主文件 §1.1 把「图片、视频、Embedding 都可以存」列为数据湖要承载的形态，但**存得下不等于查得动**：列存格式（Parquet / ORC）按 row group 组织，带 min / max 与字典编码，它的剪枝单位是「文件 + 段」，里面**没有为近邻检索设计的索引段**（[§7 §7.3.4](02-data-lake-section-7-sec7.md)）。
- **AI 改变了什么机制**：**把向量变成湖表的一列**，于是变化的是**存储层的类型与治理归属**——向量与结构化数据同源同权，权限、时间旅行、血缘可以直接复用表格式已有的机制。但必须说清这里的边界：**变的是「列」，不是「索引」**。索引仍然由检索引擎自持，它是表外的旁挂件。
- **由此得到的**：**因为二进制只存一份、只有嵌入进索引，所以重建索引的成本远低于重建原始数据**；**因为模型版本记在事实侧而不是索引侧，所以「这条向量是哪个模型生成的」永远可回答**——这两条与 §5.2.1 是同一个机制的两个面：把「可重建」这件事做成结构事实，而不是运维约定。

| 检查项 | 这检查什么 | 判定方法 |
| --- | --- | --- |
| 「原生支持向量」指的是哪一层 | 是列类型，还是检索引擎 | 查表格式规范的类型章节（有没有向量类型），再查引擎文档（有没有近邻检索算子） |
| 索引随不随快照走 | 时间旅行能不能回到旧索引 | 查规范里有没有索引条目的提交语义；没有就是旁挂件 |
| 索引规模算进容量规划了吗 | 它是第二份数据 | 见下面的量级估算 |
| 换了嵌入模型怎么办 | 新旧向量可不可比 | 问「重建期间线上能不能查」；答不出说明没有双版本方案 |

- **由此付出的**：**其一，索引规模是第二份数据**【推算：10⁸ 条 768 维、每维 4 字节的浮点存储，裸向量为 10⁸ × 768 × 4 B = 3.072 × 10¹¹ B；这条换算链只有乘法与单位换算，两种单位口径是同一个量——按 1 GB = 10⁹ B 计约 307 GB，按 1 GiB = 2³⁰ B 计约 286 GiB（3.072 × 10¹¹ ÷ 2³⁰ = 286.1），读者可自行复算，下同；近邻检索索引除原始向量外还要存邻居结构，其规模通常与原始向量处于同一量级或更高，具体倍数取决于索引实现与召回参数；与 [03-lakehouse §7.4](../03-lakehouse/03-lakehouse-section-7-sec7.md) 的账四用的是同一组前提】；**其二，模态对齐错了不报错**——不同编码器产出的向量在同一索引里混合时距离分数不可比，查询不会失败，只会「不那么准」，这类失败只能靠元数据记录模型版本来发现；**其三，写入可见性由提交节奏决定**——先在湖里落地、再在检索侧立刻可查这件事不成立，把它用在实时问答上，用户会稳定看到「刚上传的文档搜不到」。
- **证据与来源**：【公开】Parquet / ORC 的文件结构定义里没有为近邻检索设计的索引段，这一点可在各项目的格式文档中自行核验；列存格式的原始出处是 Dremel 论文（VLDB 2010，主文件 §2.1 记录了 Parquet 是 Dremel 的工程化）；多模态列式格式（Lance 一类）与 Iceberg 的规范 / release note 是判定「向量类型是否进入规范」的入口。**核验纪律**：在这个主题上，「项目名对而会议 / 年份错」是最常见的引用事故——任何「某项目在某某会议某某年发表论文」的说法，请查会议论文集与项目官网的 publications 页，不要采信二手博客。
- **成熟度**：**向量原生 L2 / 多模态 RAG L2**（两行的 ①②③ 与 §5.1 表逐条一致）。向量原生行的判据：① 部分满足（多模态列式格式有版本化发布，表格式侧的向量类型须逐版本核对）；② 不满足：列不出第三方在生产中用「湖内向量列」承担在线检索的公开材料；③ 未稳：索引与表格式的耦合方式各产品不同。多模态 RAG 行的判据：①② 同上；③ 未稳（编码器与索引之间的接口未定型）。
- **失效条件**：当检索规模小到可以每次全量算距离时（万级向量量级），把向量放进湖表并另配索引体系是负收益——多出来的是一套需要刷新与版本管理的派生结构，而代价是实打实的。**判定方法**：算「全量算一次的代价 × 查询频次」是否超过一套索引的刷新与运维成本；不超过就先别建索引，直接把向量当普通列存着。
- **自验方法**：拿一批真实资产，构造一个「刚更新完、立刻检索」的场景，测量检索侧看到新内容的滞后——这个数就是这套架构在你手里的**可见性延迟**，它由提交节奏决定，不由模型或索引类型决定。

#### 5.2.3 元数据与治理的 AI 化：降低的是补全成本，不是定义权

- **旧做法与它的卡点**：元数据靠人补，人一忙就补不完；补完的元数据没有机制保证不过期——本目录 [§6](02-data-lake-section-6-sec6.md) 里 AWS 案例的两条教训（「湖里只有对象没有表定义」「Schema 登记靠人工写文档」）说的就是这个缺口；「过期」这一面在 [数据目录 §6](../../04-data-assetization/08-data-catalog/08-data-catalog-section-6-sec6.md) 的案例里有原话：靠人工填的元数据「3 个月后就过期」，倒逼出「SQL 自动解析 + 人工只补业务含义」。PII 与密级同理：人工标注的覆盖率上不去，而新增字段还在持续产生。两个卡点的共同形态是**补全成本高，而补全的产出是「给人和机器看的说明」**。
- **AI 改变了什么机制**：**改变的是元数据的生产成本**，不是元数据的定义权。LLM 把「从数据本身推断出描述」（字段含义、值域、枚举、可能的关联）这件长尾工作的单位成本降下来，第一次让覆盖率不再受人力线性限制；但它不决定「这个字段算什么口径」——口径是业务决策，不是推断结果。
- **由此得到的**：**因为补全的单位成本下降，所以「关键元数据缺项就不能发布」这条硬规则第一次在规模上可执行**——这正是 [§6](02-data-lake-section-6-sec6.md) 里「Crawler 自动登记 catalog + 统一表语义」这类机制的前提：不是说它能自动填对，而是说人只需要处理模型给出的待确认项，而不是从空白开始；**因为模型能读样本与统计，所以敏感字段的初筛覆盖面不再受标注人力限制**，人从「全量标注」退到「复核与裁定」。
- **由此付出的**：**其一，错误的元数据比缺失的元数据更危险**——它是「看起来对的错说明」，且会被下游当成事实复制和传播，而缺失至少会触发一次核对；**其二，历史被讲反了会导致漏做复核**——这一层的分类与打标能力早于 LLM 存在（规则 + 统计模型的分类器是这条路的起点，具体上线时间以各厂商官方公告为准），把「AI 治理」讲成新能力，会让人以为它需要的是模型而不是复核流程；**其三，新增了一个数据出口**——把样本送进模型意味着多一条数据流出的链路，它必须进合规盘点，与「数据不离开某法域」一类约束直接相关。
- **证据与来源**：【公开】各平台的元数据生成与敏感数据发现能力均有官方文档条目（判定入口是文档里的能力条目、该条目标注的预览 / GA 状态、调用方式与计费维度，不是产品首页；状态逐年不同，不按首页措辞判）。**判定方法**：随机抽 50 个由模型生成的字段描述，让人逐条判断「它与真实口径是否一致」——这个比例比任何准确率声称都可靠，因为它用的是你自己的表。② 不满足：列不出第三方公开的、含规模与验收口径的生产案例。
- **成熟度**：**AI 元数据 L2 / AI 治理 L2**（两行的 ①②③ 与 §5.1 表逐条一致）。AI 元数据行的判据：① 判定方法（本节不代平台断言状态）——查该平台文档里「元数据 / 描述生成」是否为一等条目、标的是预览还是 GA、生效条件是什么；② 不满足；③ 未稳（生成质量的判定方法未定型）。AI 治理行的判据：① 满足（分类器的主体是规则与统计模型，早于 LLM 存在，能力已 GA，上线时间以各厂商官方公告为准）；② 不满足；③ 未稳（漏检率的判定口径未公开）。**共同升级条件**：出现第三方公开可复现的质量评估方法（评测集、抽样口径、由谁判定）时升 L1。
- **失效条件**：当表与字段本身有清晰的命名规范与业务语义时（团队自己就写得出准确的描述），模型生成的边际价值很低，而复核成本照付——此时更省的做法是把命名规范与登记要求做实，而不是引入一层生成。**判定方法**：看现有元数据里「缺项」的分布——缺的是「写不出来」还是「没人写」，前者模型能帮，后者模型也能帮一时，但三个月后会复发。
- **自验方法**：取 20 张最常用的表，让模型生成字段描述，再让最熟悉这些表的分析师逐条标注「对 / 部分对 / 错」。三类占比中「错」的那一部分，就是这套能力必须配复核的直接证据；把它做成一条可持续的抽样指标，比一次性的准确率宣传有用。

#### 5.2.4 自然语言入湖、Agent 触达与 GraphRAG：三件要逐件问「改了哪一层」的事

- **旧做法与它的卡点**：三条各自要解的题不同——入湖链路要人写代码与配置（原方向 4）；取数要人写 SQL、还要先知道表名（原方向 5）；多跳关系查询要在应用层先取数再遍历（原 §5.2 第二组）。它们的共同卡点是同一个：**人的知识（怎么配、问哪张表、关系在哪）没有被写进任何机器可读的地方**，所以每次都要由人临时提供。
- **AI 改变了什么机制**：**三件事改的层完全不同**——自然语言入湖改的是**配置链路的作者**（生成的是可编辑的代码 / 配置，而不是直接生效的生产链路）；Agent 触达改的是**调用者身份**（权限、审计与限额都必须以「非人主体」为前提重做）；GraphRAG 改的是**检索的第二跳**（图与列存的联合执行没有标准化接口，join 目前发生在应用层）。**把这三件并列成「AI 原生数据湖」会掩盖一个事实：没有一件改变了湖本身的存储或一致性机制。**

| 原方向 | 改了哪一层 | 由此得到的 | 由此付出的 |
| --- | --- | --- | --- |
| 自然语言入湖 | 配置的作者 | 入湖链路的编写不再要求懂引擎细节 | 生成物仍需人评审；错误配置的后果是数据缺失或错位，且在链路跑完前不显形 |
| Agent 触达 | 调用者身份 | 取数不必发明新协议，SQL 已可被约束 | 权限模型必须新增非人主体，否则只能给过大的权限 |
| GraphRAG | 检索的第二跳 | 关系与事实可分别演进 | 两边没有自动一致性保证；图谱必须可重建，否则它成了第二个事实来源 |

- **由此得到的**：**因为取数接口（SQL）已经成熟且可被约束**（参数化、只读账号、行 / 列级权限、限额），所以给 Agent 开放取数不必发明新协议，也不必换引擎——Agent 不会让引擎变快，但也不必换；**因为图侧仍靠应用层 join，所以「湖 + 图谱」的收益上限由应用层的编排质量决定，而不是由湖决定**。
- **由此付出的**：**其一，口径错误会被规模化放大**——人在写 SQL 时会迟疑，Agent 不会；**其二，「非人主体」这一档权限一旦缺失，团队最省事的做法是共享一个高权限账号**，这一步会把前面所有治理设计一次性作废；**其三，生态未稳**——工具协议仍有带日期的修订版本在演进，绑定某一版会带来迁移成本。
- **证据与来源**：【公开】模型上下文协议（Model Context Protocol）由 Anthropic 于 2024 年 11 月首次公开，其后有带日期的规范修订版本——判断某个客户端 / 服务端支持哪一版，看它声明的规范版本号，不看生态清单页；各平台文本转 SQL 能力的预览 / GA 状态以其发布说明为准。② 不满足：列不出第三方公开的、把自然语言入湖或 Agent 直连放进关键路径的生产材料。
- **成熟度**：**自然语言入湖 L3（只能观望）/ Agent 触达 L2（可试点）/ GraphRAG L3（只能观望）**——三行的 ①②③ 与 §5.1 表逐条一致。自然语言入湖行：① 不满足（没有「用一句自然语言生成可生产入湖链路」的正式发布能力项，公开材料以演示为主）；② 不满足（列不出第三方把它放进生产链路的材料）；③ 未定（生成物是「可编辑的代码 / 配置」还是「直接生效的链路」没有统一形态）。Agent 触达行：① 判定方法（查该平台文档里文本转 SQL 是不是一等条目、状态是预览还是 GA，以该版本的发布说明为准）；② 不满足；③ 满足（接口形态为「生成 → 解析校验 → 执行」，多年未变）。GraphRAG 行：① 不满足（没有「图 + 列存联合执行」的正式发布能力项）；② 无；③ 不满足（图查询与列存查询的联合执行没有标准化接口，join 落在应用层）。**Agent 触达另有一条实施项，不计入判据**：权限模型需要新增「非人主体」这一档，它是这一行的落地成本，不是它的评级依据（判据③ 说的是接口形态稳不稳）。**一个通用判据**：问「这个能力失效时，系统是变慢还是变错」——变慢是接口问题，可以试；变错是架构问题，必须先把校验补上。
- **失效条件**：当 Agent 只需要一两个固定指标时，直接给只读 API 比开放 SQL 更安全也更便宜——统一接口的收益随数据源数量与问题种类的增加而增长，源少时它只是负担；当业务问题里「关系」本身没有被建模过（连人都说不清实体关系）时，GraphRAG 只是把不确定性搬进了图谱。**判定方法**：统计最近一个月里跨源查询与多跳查询的真实次数，两者都接近零就不必开这两扇门。
- **自验方法**：取 50 条真实业务问题，先让模型生成 SQL / 配置，再让人复核，分别记录「需要改口径的条数」与「需要改语法的条数」。前者占比高说明问题在元数据，不在模型；这个分法比任何「准确率」都更能指出该修哪里。

### 5.3 与本主题既有栈的接口在哪

AI 能力不是新引擎，而是挂在湖周边的调用方与派生方。下表写清接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 入湖链路（CDC / 流）→ 湖原始区 | 交接物 = 原始文件 + schema 版本；写入侧设目标文件大小 | 入湖侧：小文件与 schema 漂移都在这里产生 | 既有能力（L1） |
| 湖（权威）→ 向量索引 / 搜索索引（派生） | 湖是源、索引是缓存；交接物 = 资产 ID + 嵌入 + 模型版本 | 检索侧：必须能从湖全量重建，重建脚本与时间上界写进运维手册 | 需自建（L2） |
| 湖（权威）→ 知识图谱（派生） | 交接物 = 实体 / 关系 + 抽取规则版本 | 图谱侧：抽取质量与幂等重建由它负责 | 概念与自建阶段（L3） |
| 湖 ↔ 表格式与 catalog | 表状态随写事务提交；权限与列级统计在 catalog 侧 | 表格式管数据，catalog 管权限：两侧都不可绕过 | 既有能力（L1） |
| 湖 → 自然语言取数 | 单向读元数据（表、字段、指标、枚举值）注入；生成的 SQL 先解析校验再执行 | 口径错归元数据侧（谁维护定义谁负责）；语法错归模型侧 | 需自建（L2） |
| 湖 → Agent 工具层 | SQL 作为工具：参数化 + 只读账号 + 行 / 列级权限 + 限额 | 越权必须在执行前拒绝，且由工具层负责 | 需自建（L2） |
| 湖 ↔ 冷热分层与保留期 | 生命周期策略：热 / 温 / 冷 / 归档 + 快照过期 | 湖侧（策略是配置，不是自动的） | 既有能力（L1） |
| 湖 ↔ 跨法域共享 | 只交换元数据与查询计划，不动数据本体 | 各域本地；联邦层负责计划下发与结果合并 | 合规前置（L2） |

一句话概括：**AI 没有在这张图上新增调用关系，只改了两件交接物的形态**——模型版本（进入元数据）与分数口径（进入检索结果）。这两样东西决定了 AI 用到的数据能不能被审计、换模型后能不能复现。

表里三条「既有能力」行（表格式与 catalog、入湖链路、冷热分层）与 AI 无关，却决定 AI 方向的上限：**自然语言取数的准确率取决于元数据与统计信息的质量，检索的代价取决于剪枝结构，而这两件事都不会因为加了一个模型而变好**。把它们当成 AI 项目的前置工序，而不是可以并行跳过的旁支。

表里那些标为「需自建」或「合规前置」的行，其失败归属必须在设计阶段写清，否则会退化成扯皮：

- **口径错**归元数据侧。把口径错记成「模型不行」，会让团队去换模型，而问题在指标定义。
- **越权**必须在执行前拒绝，且由工具层负责。事后告警等同于事故已经发生。
- **检索结果过期**归刷新链路的责任方，而它必须能被下游看见——没有「数据截止时间」的检索结果，等于把新鲜度判断推给了用户。
- **跨法域**的失败归各域本地与合规约定，联邦层只负责把计划下发下去；把它记成「联邦引擎的问题」，会让人去换引擎，而约束在合规那一侧。

围绕这张图有三条接口纪律，评审时可以逐条念：

1. **谁的副本可以被重建，谁就不必被备份**——反过来，不可重建的派生件必须按核心数据对待。判断方法是问「它丢了能不能从湖重算」，而不是问「它重不重要」。
2. **口径错归元数据侧，不要记成模型不行**——把口径错记成模型问题，会让人去换模型，而问题在指标定义。
3. **能在一个介质内完成的，不要跨系统完成**——每跨一次系统就多一个静默失效点，而这类失败的模式是「不报错、只是不太准或者慢了两周」（[§3 §3.4](02-data-lake-section-3-sec3.md) 给的是同一条职责边界纪律）。

### 5.4 公开进展与文献

分「规范与 release note / 论文 / 第三方生产案例」三类列，**宁少勿假**。规范与 release note 一类给的是「用哪份文档的哪一节自行核验」，这类文档持续更新，写死年份会过期，所以只给文档名与核验位置——**这是本节显式声明的例外，不是省略**。核验时以**你所用的那个版本**的 release note 为准，而不是以站点上的当前版本为准。

**规范与 release note（判定入口）**

- Apache Iceberg 的官方规范与各版本 release note——核验 V3 的条目清单与**类型（Types）章节里有没有向量类型**；这是本节反复强调的那处张冠李戴的唯一出口（见 §5.1 第一条易错）。
- Delta Lake 的事务日志（`_delta_log`）文档与 UniForm 的官方文档章节——核验「一份数据多种引擎读」的机制边界，注意它属于官方文档而不是论文。
- Apache Hudi 的 timeline 文档、Apache Paimon 的 release note 与快照 / changelog 文档——核验流式写入与主键合并的语义；流式表格式的写入侧通常与 Flink 一类流计算引擎配套，「秒级入湖」这类说法要同时核对两边的文档与背压 / 检查点配置，只查一边不足以判定。
- Lance 一类多模态列式格式的格式文档与版本化说明——核验「列式格式如何承载向量与标量、在对象存储上如何版本化」。
- 各平台的元数据生成 / 敏感数据发现 / 文本转 SQL 能力的官方文档条目——核验该能力的当前状态（预览或 GA）、调用方式与计费维度。
- **各厂商湖仓产品与版本里程碑的官方文档**——Databricks Lakehouse Platform（核验 Unity Catalog / AI Functions / Vector Search 在文档里是不是一等条目）、Snowflake Iceberg Tables（核验 External Catalog 与三云支持写在文档的哪一节）、腾讯云与阿里云的湖仓解决方案文档，以及 Paimon 与 LanceDB 各自 release note 里的毕业 / 1.0 版本条目。**核验的是「文档里有没有这一条目、状态是什么」，不是「哪一年发布过」**：原文件给这几项各挂了年份，本节不照抄年份，版本里程碑一律以对应版本的 release note 为准。
- **联邦查询引擎（Trino 一类）的 connector 与 catalog 文档**——核验「统一 Catalog + 统一查询」这条联邦路线落地到哪一步：connector 支持哪些 catalog、谓词下推到什么程度、失败由谁重试。

**论文**

- Dremel: Interactive Analysis of Web-Scale Datasets（VLDB 2010）——列式嵌套格式的原始出处，理解「为什么列存能按列剪裁、却又没有为相似度设计的剪枝单位」要从这里开始（主文件 §2.1 记录了 Parquet 是 Dremel 的工程化）。
- 其余论文条目（Paimon 的表格式设计、Delta 的存储设计、多模态列式格式）本节**不写会议名与年份**，只给核验入口：查该项目的官方 publications 页或对应会议的论文集。在这个主题上，「项目名对而会议 / 年份错」是最常见的引用事故，照抄二手来源的会议名比不写更有害。

**第三方生产案例**

- 本目录 [§6](02-data-lake-section-6-sec6.md) 的四家（Netflix 的 EB 级 Iceberg 湖、字节的 Iceberg 数据湖、阿里的湖仓一体与五套合一、AWS 的存算分离与治理下沉）——用于核验 §5.2.1 的**「湖是唯一事实来源」**这半条的工程代价；年份与规模的表述以该节的标注为准。**这四家都没有给出派生索引的重建演练材料**（全量重建耗时、重建期间线上可用性），所以它们证不了同一小节里「派生件可重建」那半条——那半条本节按判据只给到 L2。四家里只有字节同时够得上判据②意义上的「第三方」，原因见下一条。
- 判定「是不是第三方」的方法是两步，缺一步就出局：**第一步看发布者是不是所评机制的定义方**——Netflix 是 Iceberg 的**发起方**（§6 记录其于 2017 年启动该项目，并记其开源后捐给 Apache 基金会），它讲的机制就是它自己定下来的，不计入；**第二步看这份材料讲的是不是发布者自己的产品**——阿里与 AWS 的案例落点分别是「内部踩过的坑直接变成对外产品的能力」与「存算分离 + 权限下沉，100 万+ 企业」（§6 的原文表述），属「厂商自有案例」，只能按 §2.1 归入 L2 的口径。两步都不命中的才计入判据②：字节讲的是自己在生产里怎么用 Iceberg（流批共写一张表、小文件自动合并），落点不是自家的湖仓产品，因此是四家里唯一够得上的一条。反过来，一处「有公开生产案例」的说法如果不写清案例方与产品方是不是同一方，就会被读成「厂商自述也算」。
- **值得注意的空白**：本节列不出「第三方在生产中用自然语言入湖 / Agent 直连数据湖」的公开材料，也列不出含规模、模态与召回目标的第三方统一评测。这个空白本身是结论：本主题的性能数字一律要带条件读——没有条件限定语的「毫秒级」「秒级入湖」，都不可用于选型。

**怎么用这份清单**：核「某个能力是不是真的可用」看该版本的 release note；核「某个机制是不是真的存在」看规范与文档的机制章节（更新慢，但一条条目抵十篇博客）；核「它到底要花多少」只能自己算——没有任何公开材料能代替这一步。

三类材料的效力不同，读的时候要分开：

- **规范与 release note** 是唯一能回答「这一版到底有没有这个条目」的材料。它们的时间切片由版本号而不是年份决定，所以引用时要带版本，不能只写年份。
- **论文**能回答「机制是什么、为什么成立」，不能回答「产品里有没有」。这两件事之间隔着一整条工程路径，本节里最容易出错的就是把它们混为一谈。
- **第三方生产案例**能回答「别人踩过什么坑」，但它评的是「在什么条件下用了什么」。读到这类材料时先找条件（规模、模态、召回目标、是否含缓存），找不到条件的经验不可迁移。

### 5.5 被过度宣传的部分

**「向量原生数据湖」** —— 实际是什么：向量作为表的一列被存下来、被快照与权限覆盖，这件事成立；**向量作为表上的一等检索路径，不成立**——索引仍在表外，由检索引擎自持，不随快照版本化。为什么会这样：列存格式的剪枝单位是文件与段，它的统计信息只服务于等值与范围条件，近邻检索需要另一种索引结构（[§7 §7.3.4](02-data-lake-section-7-sec7.md) 给的是同一条机制）。**什么时候它才会成真**：表格式规范的类型章节出现向量类型，且索引条目的提交语义被写进规范、随快照原子切换——两个条件要看的是规范，不是产品首页。

**「自治数据湖：自动 compaction、自动优化、自动治理」** —— 实际是什么：这一层的自动化早于 LLM 存在，靠的是统计信息与规则（文件大小阈值触发合并、按查询模式选聚簇列）；LLM 改变的是**解释与建议的接口**，不是决策机制。为什么会这样：布局优化的输入是文件统计与查询历史，这两样都不是语言模型能凭空生成的；把它叫做 AI，会让团队以为换一个模型就能解决布局问题，而真正要改的是写入侧的文件大小与合并调度。**什么时候它才会成真**：产品的自动动作具备三件事——可解释、可回滚、有明确的失败回退路径；判定方法是看文档里它是建议还是自动执行，以及自动执行有没有单步撤销。

**「Agent 直连数据湖，不再需要治理」** —— 实际是什么：Agent 拿到的仍是同一份权限与同一份元数据，它没有绕开任何东西，只是把「谁来问」换成了模型。为什么会这样：模型不产生口径，它读到的就是你写下来的东西；[§6 的小结](02-data-lake-section-6-sec6.md)把「manifests 里存列级统计 + 权限下沉到 catalog」写成 AI 取数的前提，说的正是这件事——**没有元数据与权限，Agent 只会更自信地猜错表名**。**什么时候它才会成真**：当元数据覆盖到「业务问题 → 指标口径」这一层（而不只是「表 → 字段」），且权限模型里有「非人主体」这一档时，Agent 才可能成为默认入口；在那之前它是「多一个入口」。

三条合起来看，被过度宣传的部分有同一个形状：**它们都把「概念包了一层」讲成了「技术前进了一步」**。向量原生是列类型的事被说成检索能力；自治是规则自动化被说成 AI；Agent 直连是调用方变化被说成治理可以被跳过。识别方法因此很简单——**把宣传句里的名词换成「列类型」「统计数据」「调用者身份」，看它还成不成立**：只有在换过之后仍然成立的说法，才是关于架构的。

要补一句的是：这三条被过度宣传的说法里，**没有一条是「假的」**——向量确实能作为列存下来，自动合并确实在跑，Agent 确实能取数。它们的问题是把「在某一层成立」讲成了「整体成立」，而架构决策恰恰只关心后一句。所以在评审会上更有效的问法不是「这是不是真的」，而是「它在哪一层成立、代价落在谁身上」。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 湖仓形态成为新建平台的默认起点，「要不要建湖」不再是一个独立议题 | 新建数据平台的默认方案里表格式 + 对象存储是起点，讨论集中在选哪个格式与哪个 catalog | 三年后新建平台仍在「先建仓、再考虑湖」，或湖被当作归档层而不是事实来源 |
| 「向量原生」的落地形式是「派生索引 + 可重建」，而不是「湖内原生近邻检索」 | 表格式规范出现索引条目的提交语义，且索引随快照版本化；索引重建成为标准运维脚本 | 出现「把向量列当普通列就能做近邻查询」的标准做法，且不再需要独立索引与重建流程 |
| 「自治」叙事收敛为「可回滚的自动动作」，不再自称 AI | 产品文档把自动动作写成「建议 + 单步撤销 + 失败回退」，并把触发条件与阈值公开 | 三年后仍以「自治 / 自驱」为卖点，而文档里查不到自动动作的触发条件与撤销路径 |
| 跨域 / 跨云的数据湖由合规驱动，而不是由性能驱动 | 多云形态的公开案例里，触发原因是数据驻留要求而不是查询性能；元数据映射与统一资产 ID 成为标配 | 出现「联邦查询比集中存储更快」的公开可复现对比，且性能成为主要驱动力 |

写这四条时的共同约定：**信号必须是外部可观察的**（规范条目、产品文档的配置与回退章节、第三方公开案例），而不是「我觉得会」。凡写不出证伪信号的判断，本节不写。

四条里前两条是**形态**预测、后两条是**叙事与驱动力**预测。它们每年可以按固定动作复评一次：

- 查一次你所用的表格式规范的类型章节与索引条目——这是预测 2 的判定入口。
- 查一次产品的自动能力文档里有没有触发条件与撤销路径——这是预测 3 的判定入口。
- 问一次团队「上一次全量重建派生索引是什么时候、用了多久」——答不上来，说明预测 2 在你这里还没成立。
- 查一次跨域数据湖的引入原因是合规要求还是性能诉求——这是预测 4 的判定入口；如果原因是性能，那多半是一次被包装过的架构迁移，代价评估要重做一遍。

四条预测的可证伪性来自同一个来源：**它们判断的都不是「某产品会不会做」，而是「判断依据会不会出现在公开文档里」**——规范条目、配置项、文档章节、案例方自述的动机，这些都是外部可查的。这也是本节用「机制 → 证据 → 成熟度」换掉趋势清单的原因：趋势清单永远正确，因为它从不承诺可以被核对的信号。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已经有向量库 / 搜索索引，且它接收独立写入 | 把它降级为派生件：补上全量重建脚本与时间上界，做一次重建演练 | 重建耗时与期间线上可用性；模型版本是否记在事实侧 | **不要在无法全量重建的前提下换嵌入模型**——那等于把数据押在一个黑盒里 |
| 业务提出「湖上做相似度检索」 | 先把索引与事实的边界写清（湖是权威源），再谈检索实现 | 表格式规范的类型章节与索引条目 | **不要为「统一向量空间、原生近邻检索」预留 schema**；把列类型当成检索能力来采购 |
| 元数据覆盖率低，想用 AI 补齐 | 先用模型生成待确认项、人只做裁定；把「关键项缺项不可发布」这条规则做出来 | 抽样复核的一致率（抽 50 个字段描述人判） | **不要取消人工复核**；也不要因为「AI 能补」就放宽关键项的定义 |
| 元数据与权限已有基础，想开放 Agent 取数 | 给 Agent 单列只读身份 + 行 / 列级过滤 + 限额 + 审计 | 权限模型是否出现「非人主体」这一档 | **不要共享一个高权限账号**，也不要让越权靠事后告警发现 |
| 有分钟级入湖要求 | 上支持流式写入的表格式，并把 compaction 变成常驻调度（这与 §7.5 的 T6 是同一条路） | 合并滞后量（未合并文件数与字节数）是否持续上升 | **不要用高频微批替代实时入湖**——它会在目录里堆小文件，成本在数月量级后才出现【经验：量级为月】 |
| 数据不允许离开某一法域 | 先做统一 catalog 与分级权限，再谈联邦查询 | 跨域查询频率是否从偶发变成高频 | **不要在没有统一元数据的前提下先拆组织**；也不要假设「零复制」是永久状态 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的（重建一次、改一次 schema、改一次权限模型、改一次写入形态），而收益依赖一个尚未在你自己的数据上验证过的假设**（规模会继续涨 / 模型会变得更准 / Agent 会自己守规矩 / 跨域查询不会变高频）。等 §5.6 的信号出现再投入，损失的只是时间。

这张表的六行不是互斥选项，而是同一支团队会依次遇到的处境。真正**不可逆**的决定只有一个：**事实来源与派生件的边界画在哪里**。它决定了你在换模型、换引擎、换模态时是「跑一个作业」还是「做一次迁移」；至于用哪个向量库、要不要上联邦、元数据用哪家的能力，都是在边界确定之后还可以替换的选项。**把不可逆的决定与可逆的决定分开排期，比把它们一起放进路线图更重要。**

如果只能排一个顺序，按这条走：

1. **先量**：生产查询里需要相似度与多跳关系的比例、一次典型查询要扫的数据量、写入侧的平均文件大小与每分区文件数。这三项决定后面所有选型，且不需要新采购。
2. **再定边界**：把事实来源与派生件的责任写下来，补上每个派生件的全量重建脚本与时间上界，并做一次演练（§5.2.1 的自验方法）。
3. **然后补元数据与权限**：关键项缺项不可发布、字段级密级标注、权限下沉到 catalog。这一步不改存储、不改引擎，却同时是自然语言取数与 Agent 开放的前置条件。
4. **最后才谈 AI 功能**：元数据生成、PII 分类、自然语言入湖、Agent 直连。它们都是可以替换的接口层；换一次模型或换一家产品，不应该牵动前三步任何一件事。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**事实来源与派生件的边界被重新划定**——湖持有原始资产与事实，向量、图谱、搜索索引一律降级为可幂等重建的派生态，模型版本记在事实侧。因为这一点，排进 L1 的是**「湖是唯一事实来源」**这个机制（紧接着它的那条运维要求「派生件可重建」按 §2.1 另判 L2），而不是「AI 原生数据湖」这个概念；向量原生、AI 元数据、AI 治理、Agent 触达全部停在 L2，判它们的不是「模型强不强」，而是「谁是权威、刷新由谁触发、重建要多久」。
>
> 它**没有**改变的是存储层的两条硬约束：**列存没有为相似度设计的剪枝结构**（[§7 §7.3.4](02-data-lake-section-7-sec7.md)），**表状态与权限各自都要有唯一的承担者**——表状态随写事务提交（[§7 §7.3.1](02-data-lake-section-7-sec7.md)），权限下沉到 catalog 而不是每个引擎各配一套（[§6](02-data-lake-section-6-sec6.md) 的阿里与 AWS 两个案例：权限绑在计算引擎上必然漂移，倒逼它挂到 catalog 层）——这两条决定了 AI 要说「湖是我的数据源」，得先接受湖的剪枝与一致性规则，而不是绕开它们。
>
