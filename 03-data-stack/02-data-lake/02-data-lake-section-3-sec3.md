## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把数据湖讲成了「按场景选一个」：传统企业选 Hadoop，云上企业选对象存储，现代企业选 Lakehouse。但真实的选型是被一条硬约束推着走的：**schema 与一致性语义由哪一层承担**——是表外的元数据服务（Hive Metastore）、查询引擎（读时解释）、表格式（随事务提交）、流存储的合并结构，还是各模态各自的索引。这一条决定了五件事，而且这五件事彼此无法单独优化。

第一件是**写入的原子性从哪来**。schema 放在表外时，数据文件的变更与元数据的变更之间没有事务边界，两者会漂移；schema 随写事务提交时，「表结构」与「表数据」在机制上不可能不一致。这是「忽视 Schema 演进」这类事故的物理起点，也是 Lakehouse 相对裸文件湖最本质的差别——它不是性能优化，是把一致性从一个流程问题变成了一个结构问题。

第二件是**读取要付出多少代价**。Schema-on-Read 把解释成本放到读侧：写入快、灵活，但每次查询都要解析、且解析结果不可复用；Schema-on-Write 把成本放到写侧：读得稳，但改结构要重写数据。数据湖的整个分层体系（原始层 / 清洗层 / 精化层）本质上是在这条成本轴上选位置：原始层偏向读时解析，越往下游越偏向写时固化。

第三件是**元数据与数据是不是同一个系统**。它们同源的方案（表格式）一致性强但被绑定在特定格式上；异源的方案（外部 metastore）接入任意格式但会漂移。这个取舍在「接入一个新数据源要多久」和「读到的会不会是过期结构」之间直接对撞。

第四件是**扩容的边际成本曲线形状**。存算一体时，扩容是台阶式的（先买容量，再填数据）；存算分离时，扩容是线性的，但每一次读取都要付跨网代价。两条曲线在什么规模下相交，决定了存在规模跃迁点（见 3.6）。

第五件是**分层与模态数量的乘数效应**。每增加一层物化、每增加一种模态索引，都会同时增加存储、延迟与刷新责任；它们不是加法而是乘法——三层的多模态湖，同时要维护三层的新鲜度与两种索引的一致性。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| schema 与一致性的承担层（表外 metastore / 引擎 / 表格式 / 合并结构 / 各模态索引） | 写入有没有原子性、结构变更要不要重写数据 | 「先存原始数据，结构以后再说」——以后要付的是一次全量重写 |
| 数据形态（结构化 / 半结构化 / 二进制 / 向量） | 用什么格式落盘、能不能只读需要的列 | 「湖能存一切就等于湖能查一切」——相似度查询与等值查询要不同的索引结构 |
| 访问模式（点查 / 扫描 / 聚合 / 相似度） | 文件格式、分区与索引的选择 | 「Parquet 是万能的」——点查靠文件格式拿不到优势，它服务的是扫描与聚合（主文件 §2.3） |
| 变更频率与写入形态（批量覆盖 / 追加 / 高频小写） | 需要不需要流式表结构，以及合并资源的投入 | 「写进去就行了」——高频小写的代价不在写入那一刻，在之后的合并 |
| 规模与扩容成本曲线 | 存算分离与否、元数据是否分片 | 「上云一定便宜」——小文件与跨网读取会把单价优势吃掉 |
| 合规与数据主权 | 能否有一份物理集中的副本 | 「建一多云联邦就一劳永逸」——联邦不物化中间结果，高频跨域查询要反复付费（3.2.7 失效点） |

把 8 个模式放回这条主线上，它们的关系就清楚了：3.2.1 与 3.2.2 的差别在第三件与第四件（元数据是否同源、扩容曲线）；3.2.3 把第一件从流程问题变成结构问题；3.2.4 不改任何一致性归属，它决定数据落在哪一层；3.2.5 与 3.2.6 应对的是新的数据形态与写入频率；3.2.7 是被合规约束推出来的；3.2.8 是被运维能力约束推出来的。**把「谁的 schema」和「数据落在哪一层」当成同一个问题，是湖选型出错的典型形式。**

### 3.2 模式逐个拆解（核心节）

下面 8 个模式按「schema 归属 → 分层组织 → 新形态与新约束」排列：3.2.1–3.2.3 回答一致性归属，3.2.4 是分层组织，3.2.5 与 3.2.6 回答新数据形态与新写入频率，3.2.7 与 3.2.8 由合规与团队能力两条外部约束逼出。

#### 3.2.1 传统 Hadoop 数据湖

- **被什么约束逼出来**：数据必须落在自己机房（合规、历史资产、带宽成本），且计算要贴着数据跑——把 PB 级数据搬到计算侧不现实，只能把计算搬到数据侧。
- **结构**：HDFS 存文件、Hive Metastore 存表结构，两者互不绑定。

```sql
-- 传统 Hadoop 数据湖：schema 在表外的 Metastore，数据在 HDFS
CREATE EXTERNAL TABLE ods_order (
  order_id  STRING,
  amount    DECIMAL(18,2)
)
PARTITIONED BY (dt STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY '\t'
STORED AS TEXTFILE
LOCATION 'hdfs:///warehouse/ods_order';
-- 关键：EXTERNAL + LOCATION 意味着「表结构」与「目录里的文件」
--       被分别管理 → 文件被外部覆写时 Metastore 不会知道
--       →「元数据与数据两套真相」是这个结构的默认状态，
--          不是使用不当
```

- **为什么这样设计有效**：因为计算与存储同机（数据局部性），跨节点搬运的是计算结果而不是全量数据；因为 schema 在表外，任意格式的文件都能挂上表结构，接入新数据源不需要改造数据本身——这是它在数据格式高度混乱的年代仍然可用的原因。
- **代价**：① 元数据服务与数据文件没有事务绑定，两者会漂移，且漂移只能靠人工比对发现；② 文件级操作没有原子性，并发写同一分区会产出重复或部分可见的数据；③ 扩容必须搬数据（存算一体），冷数据的单价无法单独下降。
- **失效点**：当上游以「覆盖写某个分区」的方式更新数据时，「任意格式直接建表」反转为「读到的可能是半份数据」——因为 HDFS 上多文件覆盖没有原子性，下游查询可能在覆盖进行中读到新旧混杂的分区，而 Metastore 里的分区信息此时仍然指向旧文件列表。机制上，没有「提交」这个动作可供对齐，只能靠约定调度时间窗规避，而时间窗会随作业数量增加而相互冲突。
- **真实使用**：HDFS + Hive Metastore 是这一模式的经典组合，HDFS 的数据块大小与副本系数都有出厂默认值（主文件 §2.1 记为 128MB / 3 份；以 Apache Hadoop 官方配置文档当前版本为准）【公开，可自行核验】；「表外的 Metastore」与「目录里的文件」分属两个系统、各有一套真相，是这个结构的要点。今天它的存量主要在自建机房与历史集群；判断方法看它是否同时具备「存算一体」与「表外 metastore」两个特征。

#### 3.2.2 云原生数据湖

- **被什么约束逼出来**：数据增长的边际成本不能是台阶式的——本地机房要扩容就得先采购、再上架、再搬迁，而这个周期跟不上数据的增长速度；把存储换成按量计费的对象存储，是让成本曲线变成线性增长唯一可行的方式。
- **结构**：对象存储存数据、独立 metastore 存表结构、计算集群临时拉起并按需释放。

```text
云原生数据湖：存算分离（两边各自伸缩）

  计算集群（Spark / Flink / Trino / StarRocks）
     · 按需拉起，任务结束即释放
     · 无本地数据副本 → 每次读取都走网络
        │                        ▲
        │ 读：LIST + GET 对象     │ 写：PUT 对象
        ▼                        │
  对象存储（S3 / OSS / COS / MinIO）
     · 扁平命名空间，无真实目录
     · 一致性以读后写为语义（以厂商文档为准）
        ▲
        │  表结构另外存放
  独立 Metastore / Catalog
  ────────────────────────────────────────────────────────
  关键：存储与计算的容量互不相关 → 扩容不再需要搬数据
        代价：每次读都要付网络与请求的钱，且重命名这类
        文件系统操作在这里退化为逐对象复制
```

- **为什么这样设计有效**：因为存储与计算解耦，所以两者可以各自独立伸缩——计算峰值不需要常备容量，冷数据只需留在对象存储上。对象存储的容量单价与专用数仓存储不在同一档位（主文件 §1.1 给出了与标准存储档位对应的数量级对比；具体单价以云厂商定价页当前版本为准）【公开，可自行核验】，这让「原始数据长期保留」第一次成为可负担的默认动作。
- **代价**：① 每次读取都走网络，元数据操作（LIST）的延迟与请求费用不可忽略；② 一致性语义从文件系统变成对象存储，重命名目录退化为逐对象复制、且不是原子的；③ 权限模型变成「桶策略 + IAM + 引擎侧策略」三层叠加，任一层配错都会造成越权或不可用。
- **失效点**：当作业形态是「大量小文件随机读」时，「弹性伸缩」反转为「网络往返成为主要成本」——因为每次打开文件都是一次 HTTP 请求，延迟与请求费用随文件数增长而不是随数据量增长，按请求计费的部分会超过按容量计费的部分。此时正确的动作是先做 compaction 再读（见 3.5「小文件爆炸」），而不是给计算集群加机器：加机器能让更多小文件并行打开，却压不掉单位文件的那一次往返。
- **真实使用**：S3 / OSS / COS 上的 Iceberg / Hudi / Delta 组合，以及自建场景里的 MinIO（主文件 §2.1）。判断一个平台是不是真存算分离，看的不是它用不用云，而是「删掉计算集群后数据是否完好无损、拉起来能否直接继续读」。【公开，可自行核验】（来源：主文件 §2.1 的对象存储与开放表格式条目；各厂商的对象存储定价页与 API 文档，以当前版本为准）

#### 3.2.3 Lakehouse（湖仓一体）

- **被什么约束逼出来**：多引擎（BI、流、机器学习）都要以同一语义读同一份数据，而裸文件湖没有事务边界——上游在写、下游在读，中间裂开的窗口期必然被读到；同时数据仓库的专有格式又把数据锁在单一引擎里。两个约束夹出来的位置，就是「把表语义下沉到开放表格式」。
- **结构**：对象存储 + 开放表格式（Iceberg / Hudi / Delta / Paimon）+ 多引擎读写。

```sql
-- Lakehouse：表语义下沉到表格式（Iceberg 概念示意）
-- schema / 分区 / 统计信息随写事务提交到 metadata.json 与 manifest
-- → 「表结构」与「表数据」的一致性由格式保证，不由流程保证
CREATE TABLE lakehouse.ods_order (
  order_id  STRING,
  amount    DECIMAL(18,2),
  dt        DATE
) USING iceberg
PARTITIONED BY (dt)
TBLPROPERTIES (
  'write.target-file-size-bytes' = '134217728',  -- 目标文件大小：抗小文件的第一道闸
  'write.distribution-mode'      = 'hash'        -- 写分布：控制单次提交的文件数
);
-- 任一引擎（Spark / Flink / Trino / StarRocks）读同一张表：
SELECT dt, sum(amount) FROM lakehouse.ods_order
WHERE dt BETWEEN DATE '2025-01-01' AND DATE '2025-01-31'
GROUP BY dt;
-- 时间旅行 / 快照隔离 / schema 演进由表格式承担（主文件 §2.1）
```

- **为什么这样设计有效**：因为 schema 与数据在同一个事务里提交，所以「下游读到的结构」与「上游写入的结构」在机制上不可能不一致；因为快照不可变，回滚与时间旅行是读取一个旧快照，不需要额外备份体系；因为这一切都在开放格式上，所以换引擎不需要搬数据——这正是它相对「数据湖 + 专有数仓」组合的核心优势。
- **代价**：① catalog 成为所有写事务的汇聚点，它的可用性等于全平台的可用性；② 维护任务常驻——快照过期、manifest 重写、小文件合并（Iceberg 的 `rewrite_data_files`、Hudi 的 compaction、Delta 的 `OPTIMIZE` 是同一件事在三个项目里的名字，主文件 §2.3），不做就会持续劣化；③ 排查要理解 metadata 层级，出问题时「表里到底有哪些文件」不再是一个 `ls` 能回答的问题。
- **失效点**：当小文件的产生速率超过合并调度能力时，「开放格式 + 高频写入」反转为「查询越来越慢、元数据越来越重」——因为每一次写入都可能产生新文件与新 manifest 条目，而表格式只提供合并**原语**，合并本身要消耗计算资源与时间。于是症状会出现在查询侧（扫描计划变慢、文件打开次数暴涨），根因却在写入侧。正确动作是提高合并资源并把「目标文件大小」写进表属性（上面 DDL 里的第一项），而不是换查询引擎。
- **真实使用**：Lakehouse 概念由 Databricks 于 2020 年提出，其系统化论述见 Armbrust 等《Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics》（CIDR 2021）——2020 是概念起点、2021 是论文发表年份，两者所指不同，不可相互替代【公开，2021】（来源：主文件 §1.4 演进历程把「2020 年 Databricks 提出 Lakehouse 概念」记为概念起点；论文标题与年份可按上述标题在 CIDR 2021 论文集中核验）；Iceberg / Hudi / Delta / Paimon 是它的开源载体（主文件 §2.1、§2.3）。判断方法：换一个引擎能不能直接读同一张表、且读到同一份快照。

#### 3.2.4 Medallion（铜银金架构）

- **被什么约束逼出来**：排障要原始数据、分析师要口径统一的清洗数据、业务方要聚合结果，三类消费者同时存在；把三种需求压在一张表上，任何一次清洗都会永久丢失排障所需的原始信息。
- **结构**：同一份数据的三个物理落点，按可信度分层，每层有独立 Owner 与 SLA。

```text
Medallion：按可信度分层（每层都是一次物理落盘 = 一个回滚点）

  Bronze（原始）      Silver（清洗整合）       Gold（面向应用）
  ─────────────       ─────────────────       ────────────────
  · 原样落地           · 去重 / 类型规整         · 聚合 / 宽表 / 指标
  · 可重放             · 统一口径 / 关联维度      · 服务 BI / 特征 / Agent
  · Owner=接入方       · Owner=数据工程          · Owner=业务分析
  · 保留期最长         · 保留期中等              · 保留期按需
        └──────────────────┴────────────────────────┘
        主文件 §2.1 的同义层名：Raw Zone / Cleansed Zone / Curated Zone
  ────────────────────────────────────────────────────────
  关键：层的边界是「物理物化边界」，不是视图边界
        → 上游修正要沿三层依次重放才能到达 Gold
```

- **为什么这样设计有效**：因为每层都是物理落盘，所以重跑任何一层的失败都不会污染上游，回滚点是结构自带而不是靠备份；因为口径收敛集中在 Silver，所以「同一指标多个算法」的问题被限制在一层之内，下游拿到的口径是可追溯的。
- **代价**：① 存储随层数增长——同一份数据在三层各存一份，实际倍数通常小于层数（Gold 是聚合结果，行数远少于 Bronze）【推算】（推导链：存储量 ≈ Σ（各层行数 × 压缩后单行字节）；Bronze 保留最全的列与最长的保留期，是上界；分层做得越好，Gold 相对 Bronze 越小）；② 端到端延迟等于各层调度周期之和，层越清晰延迟越高；③ 每层的 Owner 与 SLA 必须真的写下来，否则分层退化为三个无人负责的目录前缀。
- **失效点**：当上游修正变得频繁时（源系统补数、重跑历史），「分层清晰、各层可独立重跑」反转为「一次修正要沿三层依次重放」，因为修正在 Bronze 发生后必须逐层重算才能抵达 Gold，而每层各有自己的调度周期——越靠下游，端到端修复时间越长。此时正确的动作是给高频修正的链路开一条直通分支（Silver 直供特定的 Gold 输出），而不是压缩每层调度间隔：压到比作业执行时间还短，调度只会堆叠而不是变快。
- **真实使用**：Bronze / Silver / Gold 的定义见 Databricks 官方术语页与官方博客（起于 2021 年前后，以站点当前内容为准）【公开，可自行核验】；主文件 §2.1 同时记录了 Raw / Cleansed / Curated 这组同义层名。判断是不是同一模式，看的是「是否按可信度物化分层」，而不是层名叫什么。

#### 3.2.5 多模态数据湖

- **被什么约束逼出来**：AI 应用要消费的不再只是结构化事实，还有文档、图像、视频与它们的嵌入向量；而这两类资产的查询语义根本不同——结构化事实靠等值与范围，非结构化资产靠相似度。把它们塞进同一个索引结构不可行，分开存又会让「一个资产」的元数据被割裂。
- **结构**：湖仓持有事实与原始二进制（外加可检索的元数据），向量索引持有嵌入；两者靠资产 ID 关联，向量索引是派生副本。

```sql
-- 湖仓侧：事实与原始二进制（资产 ID 是唯一的桥）
CREATE TABLE lakehouse.asset (
  asset_id      STRING      NOT NULL,   -- 全局唯一，向量侧引用同一个 ID
  modality      STRING      NOT NULL,   -- TEXT / IMAGE / VIDEO / TABLE
  storage_uri   STRING      NOT NULL,   -- 原始二进制在对象存储里的位置
  extracted_text STRING,                -- 抽出的可检索文本（可为空）
  embed_model   STRING      NOT NULL,   -- 生成本条嵌入时所用的模型版本
  embed_version BIGINT      NOT NULL,   -- 索引版本：模型升级即 +1
  updated_at    TIMESTAMPTZ NOT NULL
);
-- 向量侧（示意）：只有嵌入与资产 ID，不含原始内容
--   index_doc_v3: (asset_id, embedding)
-- 查询路径：向量召回 asset_id 列表 → 回湖仓按 ID 取详情与原文
-- 关键：嵌入是派生副本，可整体重建；原始二进制只存一份
--       embed_model + embed_version 记在事实侧而不是索引里
--       → 「这条向量是哪个模型生成的」永远可回答
```

- **为什么这样设计有效**：因为原始二进制只存一份、只有嵌入进索引，所以重建索引的成本远低于重建原始数据；因为「模型版本」记在事实侧而不是索引侧，所以换嵌入模型时可以按版本整体重建、并能在重建期间区分新旧向量，而不是面对一个来源不明的混合索引。
- **代价**：① 两类存储的容量与刷新节奏不同，必须各有一套监控；② 一次查询要跨两个系统（先向量召回、再回湖仓取详情），跨系统 JOIN 的延迟与成本不可忽略；③ 嵌入模型变更意味着索引全量重建，成本与语料规模成正比，且重建期间要处理双版本共存。
- **失效点**：当嵌入模型升级时，「索引可重建」反转为「重建窗口内检索必须同时服务两个版本」——因为新旧模型生成的向量不在同一向量空间，混在一起做相似度比较没有意义，而重建需要时间。若不处理，会出现「同一批资产召回结果莫名变化」这类难以定位的现象。缓解办法是索引按版本分片、查询层按 `embed_version` 路由（写入侧完成切换后再切查询侧），代价是双份索引存储与一段时间的双写。
- **真实使用**：Iceberg / Delta 一类的多模态表达与 Milvus / Pinecone / LanceDB 一类的向量存储组合出现在主文件 §5 与 §7 的选型提示中【经验】；具体能力边界（例如表格式对向量列的支持程度、向量库的过滤能力）请以各自官方文档当前版本为准【公开，可自行核验】。判断方法：同一份资产能不能同时给出「等值查询」与「相似度查询」两条路径，且两条路径指向同一个资产 ID。

#### 3.2.6 实时数据湖（Streaming Lake）

- **被什么约束逼出来**：入湖不再接受 T+1，而对象存储本身没有「追加一条记录」这种操作——它只能整体覆盖对象。要在对象存储上同时做到「持续高频写入」与「随时可查询」，需要的是一套把增量变更组织成可查询结构的表格式。
- **结构**：消息层 + 流计算 + 支持流式读写的表格式（LSM 结构 + 持续合并）。

```text
实时数据湖：高频小写入 → LSM 层级 → 持续合并 → 可查询快照

  Kafka / Pulsar（变更流）
        │
   Flink（去重 / 关联 / 聚合，状态由 checkpoint 承载）
        │  写入
        ▼
  表格式（Paimon 一类，LSM 组织）
     · L0：最近写入的小文件（可能有重叠）
     · L1..Ln：逐层合并后的有序文件
     · 后台持续 compaction：把 L0 合并进更深层
        │  读
        ▼
  查询引擎（同一张表既可按批读快照，也可按流读 changelog）
  ────────────────────────────────────────────────────────
  关键：写放大与读放大是一对必须同时接受的量
        写入带宽的一部分用于"写进去"，另一部分用于"合并"
        合并滞后 → 读要扫的层数增加 → 查询变慢
```

- **为什么这样设计有效**：因为 LSM 把高频小写入缓冲成有序的层级文件，所以「持续写入」不需要每次都对大文件做随机更新；因为写入进的是 changelog，所以同一张表既可以按快照做批查询、也可以按变更做流消费——批与流读的是同一份物理事实，不需要两份数据。
- **代价**：① LSM 的合并带来写放大，写入带宽的一部分被合并吃掉（写放大随层数增长，通常在数倍到十几倍区间【经验】，随键分布与合并策略变化）；② 有状态流作业需要 checkpoint、状态后端与扩缩容运维，状态规模随 key 数量增长；③ 读放大与读延迟随合并滞后增大，滞后本身需要监控。
- **失效点**：当写入速率持续超过合并吞吐时，「实时入湖、查询实时」反转为「读越来越慢、元数据越来越重」——因为未合并的 L0 层持续累积，查询需要读的层数与文件数增加，症状出现在查询侧而根因在写入侧；这与 3.5 的「小文件爆炸」同源，只是一个发生在表内部，一个发生在目录里。此时的动作是提高合并资源、或把写入改成微批以降低文件产生速率，而不是给查询引擎加资源。
- **真实使用**：Kafka / Pulsar + Flink + Paimon / Iceberg 的组合是主文件 §1.4 记录的演进方向（Paimon 的前身 Flink Table Store 于 2022 年进入这一领域，主文件 §1.4、§2.3）【公开，可自行核验】（来源：主文件 §1.4 演进历程；Paimon 项目文档与 release note 以当前版本为准）。判断方法：同一张表能不能既按快照做批读、又按 changelog 做流读，而只维护一份物理数据。

#### 3.2.7 联邦数据湖

- **被什么约束逼出来**：数据不允许离开某一法域（数据驻留与合规要求），或跨区读取的延迟与出网成本不可接受——在这两类约束下，「一份物理集中的副本」在机制上就不可能存在。
- **结构**：各域各自持有存储与表数据，中央只有统一 Catalog（元数据、口径、权限），查询时联邦下发、结果汇总。

```text
联邦数据湖：数据不复制，只有元数据与权限是统一的

   域 A（法域 A）      域 B（法域 B）      域 C（法域 C）
   存储 + 表数据        存储 + 表数据        存储 + 表数据
        └──────── 统一 Catalog（元数据 / 口径 / 权限）──────┘
                          │
                 查询引擎（联邦下发）
        跨域查询 = 各域各自执行 → 结果在汇总侧合并
  ────────────────────────────────────────────────────────
  关键：没有物化的中间结果 →「零复制」不是永久性质，
        而是每次查询都要重新支付的代价（延迟由最慢的域决定，
        流量按域结算）；当跨域查询从偶发变成高频，就必须在某处
        物化一份副本，而那正是这个模式当初要避免的事
```

- **为什么这样设计有效**：因为数据不跨域复制，所以「数据没有离开法域」是可自证的结构事实，而不是靠访问日志事后举证；因为元数据与权限是统一的，所以跨域查询在**语义**上仍然是一张表——口径、字段名与访问控制有唯一来源，这解决了「同名表在不同域里指不同东西」的问题。
- **代价**：① 跨域查询现场 fan-out，整体延迟由最慢的域决定，且出网流量按域结算；② 各域的引擎与表格式版本差异要长期兼容，升级任何一个域都要评估对其他域查询的影响；③ 全局盘点（如「全公司有多少张表、多少 TB」）没有预聚合的答案，每次都要现场汇总。
- **失效点**：当跨域查询从偶发需求变成高频需求时（一张核心宽表被多个域反复引用），「零复制」反转为「每次查询都重新付一遍跨域流量」——因为联邦不物化中间结果，同一份跨域聚合会被反复计算、反复传输。此时必须在某个域物化一份衍生副本并接受它是派生的（要处理刷新与一致性），而**这正是这个模式当初要避免的动作**。所以「零复制」是设计目标而不是永久状态，它的可持续性取决于跨域查询的频率。
- **真实使用**：多云表格式 + 统一 Catalog 的形态（跨国 / 跨云）【经验】；AWS Lake Formation 的跨账号共享、Google Cloud Dataplex 的跨项目 catalog 是同类思路的方向性提示，具体能力与限制请以各自产品文档当前版本为准【公开，可自行核验】。

#### 3.2.8 轻量级数据湖

- **被什么约束逼出来**：数据规模小（百 GB 量级）、团队小，既没有容量压力，也没有能力运维 Hadoop 或湖仓全家桶——此时主导成本不是存储与计算，而是**运维开销本身**。
- **结构**：本地目录或 MinIO 存 Parquet 文件，嵌入式引擎（DuckDB 一类）直接在文件上查询，目录结构即 catalog。

```sql
-- 轻量级数据湖：嵌入式引擎直接读列存文件，没有服务要部署
-- 表 = 一组 Parquet 文件；分区 = 目录层级（Hive 风格路径）
SELECT dt, count(*) AS orders, sum(amount) AS gmv
FROM read_parquet('data/orders/dt=*/part-*.parquet', hive_partitioning = true)
WHERE dt BETWEEN DATE '2025-01-01' AND DATE '2025-01-31'
GROUP BY dt;
-- 对照 Lakehouse 的 DDL：这里没有 catalog、没有事务、没有并发控制
--   —— 表名就是一个 glob 表达式；没有原子提交 → 写与读不能同时进行
```

- **为什么这样设计有效**：因为查询引擎嵌在进程内、直接读列存文件，所以没有任何常驻服务需要部署与运维；Parquet 的列剪裁与谓词下推在嵌入式引擎里同样生效（主文件 §2.3），而小规模下需要扫描的数据量本身就不大——**在这个规模上，省掉的运维成本大于放弃的性能与并发能力**。
- **代价**：① 并发能力受限于单进程与单机内存，写并发基本不存在（谁先写完谁算）；② 没有 ACID 与并发控制，schema 变更靠重写文件，且没有原子提交点；③ 向上迁移时成本集中爆发——「文件路径即表名」的约定要整体替换成 catalog 语义，下游脚本里的 glob 表达式都要改写。
- **失效点**：当数据量或并发用户数越过单机内存与磁盘上限时，「零运维」反转为「每个人各自拷一份文件」——因为共享查询要么排队要么失败，用户会自然地退化为下载副本、在自己机器上分析。这是治理失效的起点，也正是「数据沼泽」的形成机制：不是没人想管，而是共享路径在机制上撑不住。正确的动作是在越过阈值之前先建最小 catalog 与权限，而不是继续给单机加内存。
- **真实使用**：MinIO + DuckDB（个人 / 小团队）【经验】；DuckDB 对 Parquet 与对象存储的读取能力以其官方文档当前版本为准【公开，可自行核验】。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 数据必须留在自建机房 + 有 Hadoop 运维能力 | 传统 Hadoop 数据湖 | 对象存储方案在这里要额外承担跨机房带宽，且历史资产无法一次性搬迁 | 是否存在**物理搬迁不可行**的存量数据 |
| 云上 + 数据量持续增长 + 只有小型运维团队 | 云原生数据湖 | 存算一体在小团队手里意味着每次扩容都要走采购与搬迁流程 | 扩容是否需要**搬数据** |
| 多引擎共读一份数据 + 需要 ACID / 时间旅行 | Lakehouse | 裸文件湖没有事务边界，上游写、下游读时中间态必然被读到 | schema 是否**随写事务提交** |
| 三类消费者共存（排障 / 分析 / 业务）+ 需要回滚点 | Medallion | 全部压在一张表上时，任何一次清洗都会丢掉排障所需的原始信息 | 是否同时需要**原始可回溯**与**口径已收敛** |
| AI 训练与推理 + 非结构化资产占比高 | 多模态数据湖 | 只上湖仓时，相似度检索拿不到可用的剪枝结构；只上向量库时，原始资产无处存放 | 是否同时存在**等值查询**与**相似度查询** |
| T+1 不可接受 + 入湖要求分钟级 | 实时数据湖 | 纯批量入湖在这个时效下只能靠高频微批，而高频微批会在目录里堆出小文件 | 写入是否**持续**（而不是按批到达） |
| 数据不允许离开某一法域 / 跨云 | 联邦数据湖 | 单集群集中存储与数据驻留要求直接冲突 | 数据是否**不允许离开某一法域** |
| 百 GB 量级 + 个人或小团队 | 轻量级数据湖 | 上湖仓全家桶的运维成本在这个规模下远大于它带来的性能收益 | 是否**没有任何常驻服务**也有人能维护 |
| 大型集团统一平台 + 已有仓的加工能力 | Lakehouse + 仓（湖存原始、仓存加工） | 全部放在湖里时，高并发点查与 BI 报表会在扫描型引擎上付出不必要的代价 | 查询是否以**高并发点查 / 报表**为主 |

这张表里最常被误选的一对是 **云原生数据湖（裸文件 + 外部约定）与 Lakehouse**：两者的差别不在用不用对象存储，而在 schema 与一致性由谁承担。误选的实际后果不是「慢一点」：裸文件湖上跑报表意味着每次查询都是全量扫描加现场聚合，同时与其他批作业争抢同一批计算资源，于是报表延迟与批作业完成时间互相拖累，团队会把这种互相拖累误判为「资源不足」，继续加机器——而加机器既不能让扫描型查询变成点查，也补不上没有的原子提交。这正是 3.5 里「直接把数据湖当数据仓库用」与「忽视 Schema 演进」两条反模式的共同成因。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Lakehouse + Medallion + 实时数据湖（默认的现代湖仓）**

- 构成：表格式承担 ACID、快照与 schema 演进；Medallion 承担可信度分层与回滚点；实时数据湖承担分钟级入湖与流批同读。
- 职责边界：表格式不管治理（谁负责、SLA 多少）；Medallion 不管一致性（它只是分层落点）；实时入湖只管写入路径的时效，不改分层与口径。
- 运维代价：三套技能并存（表格式与 catalog 运维、有状态流作业、合并与 compaction 调度），且 catalog 是共享依赖——它故障时三层同时不可写。
- 适合规模：已上湖仓、表数量在千级以上的组织。【经验】

**组合二：数据湖 + 数据仓库（湖存原始、仓存加工）**

- 构成：湖保留原始与长尾数据（Schema-on-Read、低成本），仓承担高并发点查与报表；两者之间由调度或联邦查询衔接。
- 职责边界：湖是原料仓与唯一全量保留点，仓是成品区；口径收敛发生在仓侧，湖侧不做清洗。
- 运维代价：两套元数据与两套权限体系，需要一条明确的「湖 → 仓」同步链路，并处理两边口径漂移（同名字段在湖仓两侧含义不同是常见事故源）。
- 适合规模：已有成熟数仓、又要接入大量非结构化或长尾数据的组织。【经验】

**组合三：数据湖 + 向量库 / 知识图谱（多模态与关联检索）**

- 构成：湖存原始与事实，向量库存嵌入，图谱存实体关系；三者靠同一个资产 ID 关联。
- 职责边界：湖是唯一事实来源，向量与图谱都是派生副本；派生副本的刷新由上游变更事件驱动，不由人工调度。
- 运维代价：多出两类派生索引的刷新与版本管理（嵌入模型版本、图谱 schema 版本），以及跨系统查询的编排成本。
- 适合规模：AI 应用为主、非结构化资产占比高、且需要「事实可追溯」的组织（GraphRAG 一类）。【经验】

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 数据沼泽 | 表在、数据也在，但没人能说清哪张可信；业务方宁可用导出文件 | 无主资产 + 口径分叉 → 检索结果不可信 → 没人用 → 更没人维护，进入负循环 | 湖的写入门槛极低（Schema-on-Read 本身不校验），而治理是「二期再说」 | Owner 具体到人 + 关键元数据缺项不可发布 + 按可信度分层 |
| 直接把数据湖当数据仓库用 | 报表查询直接跑在湖的全量文件上，与其他批作业互相拖累 | 扫描型引擎做高并发点查，代价随数据量线性增长 → 加机器无效（机器不改变扫描量） | 湖上「什么都能查」让人误以为「什么都能高效查」 | 分层固化聚合结果，或引入支持点查的引擎读湖上的表格式 |
| 忽视 Schema 演进 | 上游改了一个字段类型，下游大面积任务同时失败 | 表结构变更没有事务边界时，变更与读取之间必然存在裂开的窗口期 | 早期用裸 Parquet + 外部约定管理 schema，变更靠口头通知 | 改用支持 Schema Evolution 的表格式；变更走发布流程并跑影响面 |
| 小文件爆炸 | 作业成功但越跑越慢；目录里文件数远多于应有的分区数 | 每个文件都要一次元数据与一次打开开销 → 延迟与请求成本随**文件数**增长；NameNode 一类的元数据服务内存被文件数消耗 | 每个微批作业独立提交，且没人设「目标文件大小」 | 定期 compaction（`rewrite_data_files` / compaction / `OPTIMIZE`）+ 写入侧设目标文件大小 |
| 分区过度膨胀 | 分区目录数远多于查询会用到的分区，查询计划阶段明显变慢 | 分区是元数据对象，每个分区都要在计划阶段被枚举 → 分区数与计划时间同向增长 | 按业务维度「顺手」分区，且从不清理历史分区 | 按时间分区 + 保留期策略 + 写入侧分区过滤检查 |
| 忽视数据安全 | 湖对所有人可读，PII 字段没有分级标记 | 对象存储的默认权限粒度是桶与对象，不区分列 → 一次授权泄露整表 | 湖被当成「内部数据存放处」，权限沿用了文件系统时代的心智模型 | 列级 / 行级权限 + 字段级密级标注 + 授权走 catalog 而不是桶策略 |
| 缺乏生命周期管理 | 三年前的原始数据仍放在高单价存储层上；快照越积越多 | 存储成本随保留期线性增长，而访问概率随数据变老快速衰减 → 成本与价值错配 | 删除比保留需要更多决策，「先留着」是最省事的默认选项 | 明确保留期 + 自动分层（热 / 温 / 冷 / 归档）+ 快照过期策略 |

**「数据沼泽」**。它是本主题七条反模式的**共同终局**，也是最难被发现的一条，因为它的暴露方式是**沉默**：任务全部成功、目录里什么都有。机制上，数据湖的写入门槛被 Schema-on-Read 刻意放低——这是它的优点（灵活的接入能力），但这个优点不可逆地带来了「无主资产」的默认状态：谁来负责、口径是什么、能不能用，这三件事没有任何机制强制回答。只要能回答这三件事的元数据在检索结果里可见（主文件 §2.1 的 Medallion 与元数据条目描述的正是这件事），沼泽就不会形成；反过来，一旦业务方养成了「搜不到就去导出文件自己算」的习惯，湖就失去了作为共享事实来源的地位，而恢复这个地位的成本远高于初次建设治理。

**「小文件爆炸」**。它的暴露方式是**性能随运行时间缓慢劣化**：上线时很快，三个月后同样的查询慢了好几倍，而代码一行没改。机制是文件数而非数据量在驱动开销——每次查询要为每个文件付出打开、读取元数据、判断统计信息的代价，对象存储上每一次打开还是一次网络请求。所以修法的关键不是调大内存，而是把文件数压回去：写入侧设目标文件大小（见 3.2.3 的 DDL）、并让 compaction 成为常驻调度而不是应急动作。判断是否需要 compaction 的指标很直接：**平均文件大小**与**每分区文件数分布**。

**「忽视 Schema 演进」**。它的暴露方式是**大面积同时失败**，而不是个别任务出错：上游改一个字段的类型，所有直接与间接引用它的下游在同一时刻全挂。机制层面，裸文件 + 外部约定的 schema 管理没有事务边界，上游的变更与下游的读取之间必然存在一段裂开的窗口期，而窗口期的长度恰好等于「变更到所有下游被通知并改完」的时间——这个时间不可能为零。所以修法不是「通知得更快」，而是把结构变更变成一次有原子性的提交：这正是表格式（主文件 §2.1 的开放表格式条目）要解决的问题，也是它比「更完善的变更流程」更可靠的原因——**流程会漏，结构不会**。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 百 GB → TB 以上 | 轻量级数据湖 | 单机内存与磁盘越过上限，共享查询开始排队或失败，用户退化为各拷一份副本 | 云原生数据湖 / Lakehouse | 「文件路径即表名」的约定整体替换为 catalog 语义，下游 glob 表达式与脚本全部改写 |
| 单域 → 跨国 / 跨云 | 单集群数据湖 | 数据驻留要求与集中存储冲突；跨区读取延迟与出网成本不可控 | 联邦数据湖（多云表格式 + 统一 Catalog） | 从「改代码」变成「谈权责与合规」；需要跨域元数据映射与统一资产 ID |
| T+1 入湖 → 分钟级入湖 | 云原生数据湖（批量入湖） | 时效要求收紧后只能靠高频微批，而高频微批会在目录里堆出小文件 | 实时数据湖（表格式支持流式写 + 常驻 compaction） | 写入链路改造为流作业；新增有状态作业的 checkpoint 与状态运维；compaction 从偶发变常驻 |
| 结构化为主 → 多模态 | Lakehouse | 列存格式对相似度查询没有剪枝结构，向量检索退化为全表扫描 | Lakehouse + 向量库（多模态） | 新增一类派生索引与它的版本管理（嵌入模型版本），以及双版本切换期 |
| 单引擎读 → 多引擎共读同一份数据 | S3 + 裸 Parquet + 外部约定 | 没有事务边界，schema 变更与写入之间有裂开的窗口期，下游读到中间态 | Lakehouse（表格式承担 ACID 与快照） | 存量数据要注册进表格式（元数据重建）；外部约定与脚本要迁移到 catalog 语义 |
| 写入速率接近合并吞吐 | 实时数据湖（LSM 默认策略） | 未合并层数累积，查询要扫的层数与文件数增加，症状出现在查询侧 | 提高合并资源 / 写入改微批 / 冷热分层 | 需要给 compaction 单独规划资源与优先级（它会与查询争抢同一批资源） |

这六行的共同点是：**触发换模式的从来不是「数据量」这个数字，而是某个具体的结构性矛盾**——单机并发上限、数据不允许跨域、批量入湖压不出时效、列存没有相似度剪枝、没有事务边界、合并吞吐跟不上写入。数据量增长让模式失效的方式，一定是通过上述某个具体矛盾，而不会是「PB」这个词本身。

因此判断该不该换，看的是一组能从现有监控与日志里直接取到的量。最容易读到的三个是：**平均文件大小与每分区文件数分布**（前者持续下降说明写入侧在造小文件，后者右尾过长说明分区策略需要调整）；**compaction 的滞后量（未合并文件数 / 未合并字节数）**（持续上升说明合并吞吐已经跟不上写入）；**对象存储的请求量与请求费用占比**（按请求计费的部分超过按容量计费的部分，说明访问形态已经是「大量小对象」，这在存算分离架构下是成本结构变化的先行指标）。跨域与合规这类跃迁读不出这样的现成指标，它靠的是合规清单与数据流向盘点——但它的前兆同样具体：某个法域的数据出现在另一个法域的存储桶里。

### 3.7 自检清单

- [ ] schema 与数据是不是**同一个提交动作**？如果结构是另一条流程单独推送的，那段裂开的窗口期会被谁读到？
- [ ] 每张表有没有一个**具体到人的 Owner**？出现团队名即视为无主资产（数据沼泽的起点）。
- [ ] 有没有一条可观测的**平均文件大小**与**每分区文件数**指标？没有就无从判断小文件是否在累积。
- [ ] compaction 是不是**常驻调度**？上一次执行是什么时候，滞后量是多少？写入侧有没有设置目标文件大小？
- [ ] 分区策略是按时间（或明确的高频过滤维度）选的，还是「顺手」按业务维度分的？分区数在查询计划阶段的枚举代价测过吗？
- [ ] 历史分区与快照有没有保留期策略？三年前的原始数据是不是还放在最高单价的那层存储上？
- [ ] 权限是在 catalog 层按列 / 行控制，还是只在桶策略层？出现「授权一张表等于授权它的所有字段」即视为不满足。
- [ ] PII / 敏感字段有没有字段级标注？能不能一键回答「哪些表含 PII」？
- [ ] 如果用了分层（Bronze / Silver / Gold 或同义名），每层的 Owner、SLA 与保留期是写下来的，还是口头约定？
- [ ] 如果用了向量索引或图谱，它们作为**派生副本**的刷新是由上游变更事件驱动，还是人工调度？嵌入模型的版本记在哪里？
- [ ] 如果跨域查询已经是高频动作，「零复制」还成立吗？是否已经在某处物化了一份需要维护的副本？
- [ ] 如果是从轻量级方案迁移而来，下游脚本里的文件路径 / glob 表达式是否都替换成了表名？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 数据必须留在自建机房 | 传统 Hadoop 数据湖 | 计算贴着数据跑，搬运的是结果而非全量数据；代价是元数据与数据两套真相 |
| 云上 + 团队小 + 数据持续增长 | 云原生数据湖 | 存算分离让扩容不必搬数据；代价是每次读付网络与请求费用 |
| 多引擎共读 + 需要 ACID | Lakehouse | schema 随事务提交，一致性由格式保证；代价是 catalog 成为汇聚点与常驻合并任务 |
| 三类消费者 + 需要回滚点 | Medallion | 每层物理落盘即一个回滚点；代价是端到端延迟等于各层周期之和 |
| 非结构化资产 + AI 检索 | 多模态数据湖 | 原始只存一份、索引可整体重建；代价是索引版本管理与跨系统查询 |
| 入湖要分钟级 | 实时数据湖 | LSM 把高频小写缓冲成有序层级；代价是写放大与合并滞后 |
| 数据不允许跨法域 | 联邦数据湖 | 数据不复制是可自证的结构事实；代价是高频跨域查询要反复付流量 |
| 百 GB 量级 + 无运维人力 | 轻量级数据湖 | 没有常驻服务要维护；代价是越过单机上限后共享路径失效 |

> 本节小结：本主题下决定数据湖模式选择的唯一那条约束是**「schema 与一致性语义由哪一层承担」**——放在表外 metastore 会漂移（3.2.1），放在引擎读侧会付出重复解释成本，放在表格式里才成为结构问题而不是流程问题（3.2.3），放在合并结构里才能承受持续写入（3.2.6），放在各模态索引里则必须承认它是派生副本（3.2.5）；分层（Medallion）、联邦与轻量化都是在这一条确定之后才展开的次级选择。
>
> 💡 **思考锚点**：从你的湖里读出三个量——平均文件大小、每分区文件数分布、compaction 滞后量（未合并文件数 / 字节数），哪一个在持续恶化？它对应的正是「schema 与一致性语义被放在了哪一层」的薄弱处：小文件说明写入侧还停在裸文件语义，滞后说明合并结构跟不上写入——你现在更疼的是读放大还是写放大，被哪个量读了出来？
