## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本节要解的第一个问题不是「AI 能做什么」，而是**时间刻度**。把"上游任务返回成功后下游自动触发"（Airflow 2015 年前后就在做）与"LLM 预测任务时长并决定调度顺序"（本节核到的是厂商演示与自研路线图）并列写成"演进方向"，读者据此排路线图时无法判断哪一条今天能进流程。判断一条调度方向能不能落地，本主题有一条比别处更前置的约束可用：本章 [§3.1](12-scheduler-section-3-sec3.md) 已经论证过，**决定调度行为的第一性问题是「依赖判定建立在哪一层事实上」**——Cron 说"时间到了"，任务依赖说"上游返回成功了"，Sensor / 资产依赖说"数据真的就绪了"。这条约束不会被 AI 改动：模型可以把时长预测得更准、把失败日志归因得更好，但它不能让"任务返回成功"重新等于"数据正确"。

本节用 L1 / L2 / L3 三级区分，判据必须是**可核验**的三条：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条各挡住一类误判：① 挡住"把路线图当既成事实"，② 挡住"把厂商自述当行业现状"，③ 挡住"把演示当工程"。**三条全中才算 L1**，可以排进路线图；只满足一部分、或只有厂商自有案例，算 **L2**，可以做 PoC、不要作为核心依赖；只有路线图 / 论文 / 演示的，算 **L3**，记录即可、不要在架构里预留假设。"感觉成熟"不算判据——它在评审会上无法被复核。

本主题还有一条自己的证据形态问题，必须先说清：**调度系统的成效指标（准时率、误报率、资源利用率、"能否按时"的可回答性）都是各家内部运行数据**，公开材料里最多到"我们做了这件事"，很少到"因此指标变成多少、口径是什么"。因此判据第②条在本主题上是**系统性空缺**的（见 §5.4），这会直接压低所有方向的级别，且不因方向本身的优劣而改变。

**判据声明**：本主题对上面这三条 L1 判据做了如下修正：**第②条在"非能力方向"上读作"有第三方（非厂商）组织公开描述过的生产做法"，不要求这些材料同时给出成效指标**；理由是：本主题的成效指标（准时率、误报率、资源利用率）是各家内部运行数据，公开材料到不了那一层（见 §5.4），而下表标 L1 的两行**都不是能力方向**——一行是既有的工程做法（分级与抢占、按原因分类重试、补数独立队列），一行是既有生产能力（字段级血缘 + 图遍历）；这两行的收益是"可控"与"可查"，本身不需要靠成效指标来证明，它们的可核验入口是官方文档的正式功能条目与公开的生产做法描述。**这条修正只适用于这两行；所有 AI 能力方向一律按三条原始判据判定，因此表里没有一条 AI 能力方向到 L1**——这是本节最重要的一句话。

本主题还有三处最容易写错的混淆，先在这里分开——它们会在下面反复出现：

- **产品名 vs 能力名**：Kubernetes 里那个叫 scheduler 的组件做的是 **Pod 到节点的放置**，不是业务 DAG 编排；主文件 [§2.4](12-scheduler.md) 已经把"调度系统 vs 资源调度器"分成两层。本节所说的"调度"一律指业务任务的 DAG 编排，凡把集群侧资源调度算进本节能力的地方，都要先把两层拆开再判级别。
- **已发布版本 vs 路线图**：判断某调度器是否真的支持某个能力，只看一个地方——**该版本 release note 或官方文档里有没有对应条目**；benchmark 博客、首页文案、生态伙伴的转述都不算。"某版本 + 某特性"的组合，至少要核一次版本归属（下面 §5.4 给了一个归属可核验为不成立的例子）。
- **单机 / 单进程 vs 分布式**：调度状态机能不能水平扩展，决定的是容量上限（本章 [§3.6](12-scheduler-section-3-sec3.md) 的"千级 → 万级"跃迁）。判断方法同上：看 release note 里有没有**独立的调度状态组件**，而不是看它宣称"支持大规模"。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**——改变了成本结构、改变了接口边界、把人工判断换成统计判断，还是只换了个前端？本主题的答案是：**两条改变了判断依据**（异常检测的基准、时长预测的形态），**一条只改了接口入口**（自然语言生成编排定义），**其余全部只换了包装**（自治调度里真正成立的是策略工程）。这个分类不是文字游戏：**它决定了一个方向能不能靠"引入能力"落地**——改变判断依据的，接入后立刻见效；只改入口的，接入后仍要补治理与门禁。

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| AI 异常检测（任务时长 / 运行形态异常） | **L2** | ①③ 成立：可观测性与调度平台的作业异常检测是正式发布条目、接口稳定；**②（第三方非厂商、含误报率基线的生产案例）本节核不到**（§5.4），三条不全即为 L2 | 先只用它做"分级告警"，先测误报率；不要让它直接进自动重跑 / 自动阻断 |
| 运行时长预测与「能否按时」的可回答性 | **L2** | 单作业时长分布是统计可解的问题（分位数即可），模型只在 DAG 频繁变化 / 带协变量时才有边际增益；"因此准时率提升多少"无公开对照材料 | 先把时长序列与分位数做出来，再谈模型；输出必须带区间 |
| 自治调度：确定性自动化那一半（"自动调度 / 自动重试"） | **L1**（非 AI） | 非能力方向，按上面的判据声明判定：官方文档列为正式功能条目（①）＋第三方（非厂商）组织公开描述过运行做法（②）＋配置接口多年稳定（③），材料见 §5.4 | 排进路线图：分级抢占 / 按原因分类重试 / 补数独立队列先做掉 |
| 自治调度："LLM 自动修复"那一半 | **L3** | 公开信息停留在厂商演示与厂商自研路线图，生成物形态与回滚条件没有通行做法（①③不成立） | LLM 归因只进"建议"通道，不进执行通道 |
| 自然语言生成编排定义（「AI 原生调度」） | **L3** | 只有厂商演示与预览，生成物的形态与校验规则没有通行做法，接口不稳定 | 记录；若试用，生成的 DAG 必须走评审与版本库，且统计"边里有多少条是数据依赖" |
| 调度知识 RAG | **L2** | 检索组件本身可用（第①③条）；但权限过滤位置与新鲜度口径无通行做法，效果无公开材料 | 先补"权限域 + 新鲜度 + 责任人"三个字段，再谈语义召回 |
| 依赖图 → 影响分析 | **L1**（能力本身，**不是 AI**）/ **L3**（"GraphRAG 让它更好"） | 影响分析来自**字段级血缘 + 图遍历**，是已在生产里被反复验证的能力（[11-cross-cutting/05 §6](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-6-sec6.md) 四个案例）；LLM 只改提问入口，不产生新的事实 | 按血缘体系推进（见 §5.3）；不要为了"用上 LLM"把图查询换成自然语言 |
| 联邦调度 | **L2** | 多集群 / 多云调度有正式实现的条目；但"统一联邦 DAG"的语义与接口没有稳定形态；**与 AI 无因果关系** | 先解数据边界与账号边界，不预留"联邦 DAG"这个假设 |
| 资产导向调度（Dagster 类） | **L2** | 以资产为中心编排已有正式文档与实现（本章 [§3.2.7](12-scheduler-section-3-sec3.md)）；"取代任务导向"无公开证据；**与 AI 无因果关系** | 若你的核心问题是"资产新鲜吗"，按 §3.2.7 评估；不要挂 AI 的名义 |

> 表里的两个 L1 一拆就清楚：一个是**工程做法**（分级抢占 / 分类重试 / 补数独立队列），一个是**既有生产能力**（字段级血缘 + 图遍历），**没有一条来自 LLM 或 GraphRAG**——读这两行时必须先看清级别说的是哪一半，否则会把已经解决的问题重新立项一次。其余方向卡住的原因各不相同：异常检测卡在第②条（缺含基线的第三方材料）；时长预测卡在"分位数就够、模型是增量"；生成编排卡在接口不存在；自治调度里偏 AI 的那半卡在"自动"与"智能"被混为一谈；RAG 卡在治理（权限与新鲜度）；联邦与资产导向卡在**它们根本不是 AI 问题**。

**这三级的排法直接决定路线图的顺序**：

- **先做的两条（就是上表的两行 L1）**：一是分级与抢占 + 按原因分类重试（让"资源不足时谁让位"可控）；二是把影响分析建在**字段级血缘 + 图遍历**上（收益是"可查"，接口见 §5.3）。**在这两条之前还有一件不属上表演进方向的事**——把依赖判定下沉到数据：关键链路的分区就绪 / 空分区判定（本章 [§3.6](12-scheduler-section-3-sec3.md) 的"依赖从任务成功 → 数据就绪"跃迁）。它们排在 AI 之前，因为异常检测与时长预测都建立在"这次运行是否正常"上，而**只有数据层判定才能发现"任务全绿、数字错了"这一类**。
- **L2 做 PoC，并先测两个数**：异常检测的误报率（占全部告警的比例）、时长预测的区间覆盖率（真实时长落在预测区间内的比例）。这两个数拿不出来，L2 就停在原地。
- **L3 不排进排期**：自然语言生成 DAG、LLM 自动修复都属于"等信号"。它们的共同前提（生成物可静态校验、动作可回滚且任务幂等）在你这里是否成立，比选哪家模型重要得多。
- **回填机制**：每次调度器大版本升级或某个方向出现含基线的公开材料时，回填一次级别；某个 L2 若一年内仍拿不到自己组织里的实测数字，降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次"判断变快"，都对应一处新的判据来源与新的故障形态。

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 异常检测与失败归因 | 判断依据从"固定阈值"换成"该作业自己的条件分布" | **判断依据**（同一批人、同一套告警，换的是基准） |
| §5.2.2 时长预测与"能否按时" | 基准从"一次观测 / 均值"换成"分布 + 协变量" | **判断依据**（让"能否按时"从事后变成事前） |
| §5.2.3 自然语言生成编排定义 | 编排定义的入口从代码 / UI 换成自然语言 | **接口形态**（入口前移，依赖判定的层次没变） |
| §5.2.4 自治调度及其同组方向 | "自动"与"智能"被混为一谈：前者是策略，后者才是模型 | **半数是策略工程，不是 AI** |

读法建议：如果时间只够读一节，读 §5.2.1——它是本主题里唯一一条"引入能力就能立刻降低运维噪声"的方向；§5.2.2 的收益要等你有了稳定历史数据才兑现；§5.2.3 与 §5.2.4 里偏 AI 的那一半，都卡在同一个前提上（生成物可校验、动作可回滚）。

#### 5.2.1 异常检测与失败归因：把判定基准从阈值换成分布

- **旧做法与它的卡点**：静态阈值告警——"这条链路跑超过两小时就告警"。阈值靠人拍，而任务时长随时长本身在变（数据量增长、上游多跑一次、大促当天分区翻倍）。阈值定松了漏报，定紧了误报，而**误报的代价不是"多看一眼"，是告警疲劳**：当误报长期占多数，值班就退化成"全部点掉"，真故障和噪声一起被点掉。本章 [§3.5](12-scheduler-section-3-sec3.md) 把"缺乏重试机制"的症状写成"告警里反复是同一批任务"，描述的正是这条退化路径——它是信噪比问题，不是态度问题。
- **AI 改变了什么机制**：把判断依据从**绝对值**换成**相对分布**——用同一作业自身的历史时长分布（必要时加上数据量、分区规模这类协变量）判断"这一次是否偏离"。这里要说清一个机制界限：**分位数（P50 / P95）就能做到大部分**，模型（本章 [§4.5](12-scheduler-section-4-sec4.md) 示例里的 Isolation Forest 一类）的边际增益主要出现在作业形态频繁变动、或需要多协变量联合判断时。它改变的是**判定基准**，不是"能不能检测"。
- **由此得到的**：**因为基准从"全局阈值"换成"该作业自己的分布"，所以告警第一次可以分级**——"比历史 P95 长"和"比历史最长还长"是两条不同严重度的信号，值班才有可能把注意力收回真故障。这也是它在本主题里唯一稳定的收益：它降低噪声，不解决错误。
- **由此付出的**：**其一，统计判断没有解释**——模型说"异常"时说不出是"上游数据量翻倍"还是"真的卡住了"，归因仍要人做，而**归因才是值班真正花时间的地方**；**其二，它检测不到本主题最危险的那类故障**——"任务全绿、数字算错"（[§3.5](12-scheduler-section-3-sec3.md) 的硬编码依赖）在运行指标上完全正常，需要空分区判定与数据校验，不是异常检测；**其三，它自己变成新的判据来源**——一旦异常判定参与"是否重跑 / 是否阻断"，误判的代价就从"看一眼"升级为"误停一条关键链路"。所以它进自动化链条之前，必须先有误报率的实测数字。

| 异常类型 | 例子 | 运行指标上可见吗 | 该用什么 |
| --- | --- | --- | --- |
| 运行异常 | 时长突增、重试次数上升、资源打满 | 可见（这是异常检测的作用域） | 分布基准 + 分级告警 |
| 依赖异常 | 上游没写全分区就返回成功 | **不可见** | 分区就绪判定 / 空分区检查 |
| 数据异常 | 任务成功、口径变错、静默少算 | **不可见** | 断言 + 数据质量校验（非本主题） |

- **证据与来源**：【公开】可观测性与调度平台把"作业 / 指标异常检测"列为正式发布条目，核验入口是各自的官方文档（判断方法：看它标注的是正式功能还是预览，以及阈值 / 基线能否按作业配置）；**本节未能核到任何"因此误报率降到多少"的第三方公开材料**（见 §5.4）。工具（Datadog 一类）的具体能力与计费以各自官方文档为准，本节不给版本号。
- **成熟度**：**L2**。判据：①③ 成立（能力已正式发布、接口稳定、多家供应商可选），②（第三方非厂商、含基线的公开生产案例）本节核不到 → 按 §5.1 判 L2：可以小范围开分级告警，不要让它直接进自动动作。
- **判定方法**：连续两周把告警分成三类数一遍——真故障、季节性 / 数据量导致的误报、判不准。**判不准那一类的占比不下降，说明你的判定基准还没有换成分布。**
- **什么时候值得做**：告警量大、值班靠点掉，且关键链路已有可比的运行历史（同一作业跑过几十次以上）时。它降低的是噪声，代价很低。
- **什么时候不值得做**：关键链路还建在"任务成功"这一层依赖判定上时——先补分区就绪判定。在那种链路上加异常检测，等于给一个检测不到故障的环节再套一层检测。

#### 5.2.2 时长预测：让"能否按时"从事后变成事前

- **旧做法与它的卡点**：产出时刻靠人估——"这条链路大概两小时"。卡点有两层：**一是估算会失效**，估的人调岗或链路改造后，判断没有依据；**二是它回答不了"能不能"**。阿里案例（[§12.2](12-scheduler-section-6-sec6.md)）给出的思路是**先定义必须产出的时刻，再倒推调度**（基线），而基线要能持续回答"今天能否按时"，前提是能持续预测"还剩多少时间"。用上一次运行时长做预测，会在数据量跨台阶或资源竞争时系统性低估——而这类低估恰好集中在最不能迟到的那几天。
- **AI 改变了什么机制**：把基准从**一次观测 / 均值**换成**分布 + 协变量**。机制界限同样要说清：**单作业时长的预测是统计问题，不是模型问题**——分位数解决大部分；模型的增量出现在 DAG 结构频繁变化、或必须把上游数据量、分区大小、集群负载联合进来的时候。所以"LLM 预测任务执行时间"这个说法里，真正起作用的部分通常不是 LLM。
- **由此得到的**：**因为预测从"一个数"变成"一个区间"，所以"这条链路今天能否按时"第一次可以在产出之前回答**——注意措辞是"能否"，不是"一定几点"。这是基线机制（[§12.2](12-scheduler-section-6-sec6.md)）与"资源不足时结果可控"（[§12.1](12-scheduler-section-6-sec6.md)）这两件事共同需要的数据基础。
- **由此付出的**：**其一，预测偏差会被误读成承诺**——一旦"能否按时"有了数字，组织就会拿它当 SLA，模型的方差从此变成某个人的责任，所以输出必须带区间，并且写清"这是预测不是承诺"；**其二，它要求历史形态稳定**，作业刚改造、参数刚变、数据量刚跨台阶时，历史分布不再代表未来，此时预测给出的是**错误的信心**——比没有预测更危险，因为有人会据此不介入；**其三，它是一条新的常驻成本**：时长序列的采集、留存、漂移监控（谁维护、保留多久、按哪个粒度）会长期存在。

| 预测方式 | 依据 | 典型失败形态 |
| --- | --- | --- |
| 人估 / 固定时长 | 经验 | 估的人调岗或链路改造后判断失效，且没人知道它已经失效 |
| 上一次运行时长 | 单次观测 | 数据量跨台阶时系统性低估——恰好落在最不能迟到的那些日子 |
| 分位数（P50 / P95） | 同作业历史分布 | 作业改造后分布失效；答不了"为什么这次慢" |
| 分位数 + 协变量（数据量 / 分区规模 / 集群负载） | 条件分布 | 需要特征采集与漂移监控，多一条常驻成本与新的误判面 |

这四行依次说的是**基准在往哪走，不是模型在换**：从人估走到分位数这一步收益最大，而它对模型没有任何要求——所以"先做分位数、再谈模型"在本主题里不是保守，而是省一轮返工。

- **证据与来源**：【公开】主流调度器官方文档把"任务时长 / 超时 / SLA miss 告警"列为正式功能条目（以各调度器官方文档为准）；**【本节未能核到】"用模型预测时长因此准时率提升多少"的第三方公开材料**——这类数字属于各家内部运行数据（§5.4）。本节因此不引用任何提升幅度。
- **成熟度**：**L2**。判据：能力所在的组件层第①③条成立；但"预测 → 准时"这条因果链没有第三方公开材料，且它的收益高度依赖你自己历史数据的质量 → 先做分位数，再谈模型。
- **判定方法**：把预测区间与实际时长连续比对两周，数两件事——**区间覆盖率**（真实值落在区间内的比例）与**跨台阶后的失准次数**。跨台阶时失准是正常的，忽略它就是事故的前兆。
- **什么时候值得做**：已经有人对产出时刻做了承诺（有 SLA 或基线），且这些作业的历史运行次数已经够算出分位数时。
- **什么时候不值得做**：作业本身不稳定（每天重构、参数天天改）或没人对产出时刻负责时——预测会被当成承诺用，而这不是你要的东西。

#### 5.2.3 自然语言生成编排定义：入口前移一层，判定层次没变

- **旧做法与它的卡点**：编排定义要么写在 Python / YAML 里（要懂 API 与算子），要么在 UI 里连（一次要几个人天）。卡点是**门槛落在人身上**：业务方与分析师的依赖表达不出来，只能找平台团队排期，平台队列于是成为全链路的瓶颈。本章 [§3.1](12-scheduler-section-3-sec3.md) 的约束表里"团队技能与运维能力"这一行，决定的就是声明式还是代码定义、自管还是托管。
- **AI 改变了什么机制**：把编排定义的入口从**代码 / UI 换成自然语言**——用户描述"先抽单，再按门店汇总，跑完通知我"，模型给出候选 DAG。**机制上变的是入口，依赖判定建立在哪一层事实上一点没变**；这正是 [§3.2.2](12-scheduler-section-3-sec3.md)「DAG 被降级成一份可被读写的数据」的同一条思路，只是把入口再往前推了一层。
- **由此得到的**：**因为表达门槛下降，候选拓扑第一次能被非工程师自己写出来**，平台团队不再是唯一入口（[§3.2.2](12-scheduler-section-3-sec3.md) 的收益在这里被放大）。这是真的收益，但它买到的是**候选**，不是**定义**——"可编辑的数据"要靠评审与校验才成为可执行的定义。
- **由此付出的**：**其一，生成物天然偏好"时间依赖"**——从一段文字里能直接读出来的只有先后顺序与周期，读不出"分区就绪"这类数据事实，所以生成的边很容易落在"多久跑一次"上。而 [§3.5](12-scheduler-section-3-sec3.md) 把这一条列为最危险的反模式：依赖判定退化成时间猜之后，故障形态是**数据错而不是任务失败**，任务全绿、SLA 全过，只有数字不对。【经验】判定方法：拿一批生成结果统计"边里有多少条是数据依赖而非时间依赖"，这个数不测就没法评估；**其二，它必须落回版本库**——[§3.1](12-scheduler-section-3-sec3.md) 已经指出"UI 生成的 DAG 定义默认落在元数据库，而非版本库"，自然语言生成会把这一点放大（原文是口语，改一次就没人知道改了哪句），所以生成物必须有一次"翻译进代码 / 声明文件"的动作；**其三，它不承担署名责任**——DAG 进生产后出事故，责任在提交与评审的人，模型在那里没有位置。

```text
        同一句需求，两种生成结果（差别在依赖判定落在哪一层）
        需求："抽完订单，按门店汇总，跑完通知我"
        ────────────────────────────────────────────────
        ✗ 时间依赖（生成物的默认倾向）
          extract_orders (每天 02:00)
             └─► agg_by_shop (每天 03:00)      ← 边是"时间差"，不是"数据就绪"
                    └─► notify (每天 04:00)
          上游迟到 40 分钟 → 汇总照跑、读到半个分区
          → 数字错了，而任务全绿、SLA 全过
        ✓ 数据就绪依赖
          extract_orders
             └─► wait_for_partition(dwd_order, dt={{ ds }})   ← 边是数据事实
                    └─► agg_by_shop
                           └─► notify
        ────────────────────────────────────────────────
        判定方法：数生成出来的边里"数据依赖 : 时间依赖"的比例
        ——这个数不测，就无法判断生成物能不能进生产
```

- **证据与来源**：**无公开可核验来源**：本节未能核到任何"自然语言生成 DAG 进入生产调度"的第三方材料，公开信息以厂商演示与预览功能为主；【公开】可核验的相邻事实是"AI 辅助开发"类功能已进入云厂商数据平台的正式条目（DataWorks 智能升级属此类；具体形态与版本以该产品官方文档为准），但它作用于**开发环节**，不作用于调度决策。
- **成熟度**：**L3**。判据：仅有厂商演示 / 预览，生成物的形态与校验规则没有通行做法（第①③条不成立）→ 记录，不要在架构里预留假设。**若你要试用，先立两条门禁**：生成的 DAG 必须通过拓扑环检测与"关键链路是否有数据就绪判定"的静态检查，且必须进版本库走评审。
- **什么时候值得做**：只在你需要把"候选拓扑"交给非工程师自己表达、且你已经有能力对生成物做静态校验时。收益是平台团队的排期不再是唯一入口。
- **什么时候不值得做**：当你期待它直接产出可上线的 DAG 时——它产出的是草稿，而把它变成定义的那一步（补数据就绪判定、进版本库、过评审）人工成本一分没省。

#### 5.2.4 自治调度，以及同组被误归到 AI 名下的四个方向

- **旧做法与它的卡点**：人盯。失败人工看、重试人工点、资源不足人工排队——[§3.5](12-scheduler-section-3-sec3.md) 的"未做资源隔离"与 [§12.1](12-scheduler-section-6-sec6.md) 的字节案例说的都是这件事：资源不足时如果没有分级，唯一的结果是"所有人一起慢"。
- **AI 改变了什么机制**：**必须把"自动"与"智能"分开算。** 重试分类、指数退避、抢占、按优先级让位、按原因分流——这些是**策略与规则**，不需要模型，也不需要 LLM；模型真正能增益的是**归因**（把失败日志聚类成几类原因、把"这次该重跑还是该上报"变成建议）。所以"自治调度（Self-Driving Scheduler）"里，**已经成立的那一半是确定性自动化，未成立的那一半才是 AI**；把它们合成一个词，是本主题最普遍的一处混淆。
- **由此得到的**：**因为确定性那一半在生产里被反复验证过，所以"资源不足时谁让位""哪些失败能自愈"今天就能排进路线图**——[§6](12-scheduler-section-6-sec6.md) 的四个案例全部是这一半。反过来，LLM 那一半的收益到目前为止是"让归因更快"，而不是"让调度更对"。
- **由此付出的**：**其一，自动化的爆炸半径由幂等性决定**——自动重跑一个非幂等任务是重复写，[§3.5](12-scheduler-section-3-sec3.md) 与 [§6](12-scheduler-section-6-sec6.md) 都把"补数独立队列 + 任务幂等"列为前置条件；不满足时，自动化的正确策略恰恰是"不动"；**其二，LLM 归因一旦接进执行通道，误判就直接变成动作**（误重跑、误降级），所以它只能先进"建议"通道；**其三，"自修复"会降低故障的可见性**——问题被自动绕过，根因没人修，本章 [§3.7](12-scheduler-section-3-sec3.md) 自检清单第 11 条问的那种"无下游、无人认领的僵尸任务"就是这么长出来的。
- **证据与来源**：【公开】分级与抢占、按原因分类重试是主流调度器 / 集群管理器的正式功能条目（以各自官方文档为准），并有公开的工程材料描述其运行做法（本书 [§12.1](12-scheduler-section-6-sec6.md) 字节、[§12.2](12-scheduler-section-6-sec6.md) 阿里所引公开材料）；**【本节未能核到】LLM 驱动的自动修复进入生产的第三方材料**。
- **成熟度**：这一个方向要拆成两半分别评级（§5.1 表第 3、4 行）。**确定性自动化那一半是 L1**：它是非能力方向，按 §5.1 判据声明修正后的第②条判定（官方正式功能条目 + 配置接口多年稳定 + 多家彼此独立的组织公开描述过运行做法，材料见 §5.4）；**"LLM 自治"那一半是 L3**：公开信息停留在厂商演示与厂商自研路线图。

同一组里还有四个方向，逐条给全六项：

| 方向 | 旧做法与卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据 / 成熟度 |
| --- | --- | --- | --- | --- | --- |
| 调度知识 RAG（历史 DAG + 调度策略 → 向量 → RAG，LanceDB + LangChain） | 找相似 DAG、找"这段逻辑谁写的"靠问人与翻目录，前提是你知道名字 | 发现入口从"知道名字"变成"描述问题" | 长尾编排资产（临时脚本、一次性补数）第一次可被找到，复用不必先找到人 | 权限过滤放在召回前还是后是一条显式设计决定；过期作业被检索到会以"有出处"的形式给出错误依据（治理成本高于组件成本） | 组件可用、无跨团队共享索引的公开效果材料 → **L2** |
| 依赖图 GraphRAG（DAG → 图谱 → 影响分析，Neo4j + LLM） | 改表前列影响面靠经验估计与发公告 | **没有改变影响分析的机制**——影响面来自血缘与图遍历；LLM 只把"写图查询"换成"提问题" | 提问门槛下降（不知道血缘系统的查询语法也能问），这是真的、但只影响使用频率 | 自然语言层会引入"答得不对但很流畅"的新失败形态；而影响面答错比答不出更贵（本章 [§3.4](12-scheduler-section-3-sec3.md) 组合三的运维代价：三套系统的依赖真相各记一份时，「任一方漏采都会让影响面失真」） | 【公开】字段级血缘 + 图遍历是既有生产能力（[11-cross-cutting/05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)）→ **L1（能力本身）/ L3（GraphRAG 增益）** |
| 联邦调度 | 跨云 / 跨集群各有一套调度与资源池，任务跨边界要人搬数据、人拼状态 | **与 AI 无因果关系**：它改变的是控制面与数据边界的划分，不是判断方式 | （若成立）跨集群的产出时刻可以统一回答，资源可以在更大池子里腾挪 | 联邦语义一旦不统一，故障定位会跨两套控制面；账号与数据出域通常是**合规问题而不是技术问题**，成本落在法务与安全 | 多集群调度有正式实现条目；"统一联邦 DAG"无稳定接口 → **L2** |
| 资产导向调度 | 任务级调度只能回答"任务跑完了吗"，回答不了"这张表的分区物化了吗" | **与 AI 无因果关系**：它把依赖从"任务成功"下沉到"资产与分区就绪"，是编排范式的变化 | "该重算哪一段"可由依赖直接推出，影响分析与它同源 | 存量 DAG 要翻译成资产依赖，资产边界定义本身就是治理工作；与现有调度器常常并存，依赖真相要定期对账 | [§3.2.7](12-scheduler-section-3-sec3.md) 已述；"取代任务导向"无公开证据 → **L2** |

**这一组四行的共同读法**：它们的收益都真实存在，但**没有一条的收益来自模型**——两条来自治理（RAG 的权限与新鲜度、联邦的边界划分），一条来自范式（资产导向），一条本就是既有能力（影响分析）。把它们写成"AI 时代的调度演进"，会让真正要做的三件事（补字段、划边界、翻存量）一件都排不进排期。

- **什么时候值得做**（针对本节的自治调度）：资源不足已经成为常态、补数与日常产出互相拖慢、且有明确的优先级分级可用时。确定性那一半见效快，且不引入新故障形态。
- **什么时候不值得做**：任务幂等性还没验证就上自动重跑；或者你真正的问题不是"没人点重试"，而是"没人知道该不该重跑"——后者要的是失败原因分类与责任划分，不是模型。

### 5.3 与本主题既有栈的接口在哪

调度与 AI 之间不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比"AI 能做什么"更能决定它能不能落地。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 调度器 → 血缘 / 影响面（[11-cross-cutting/05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)） | 交接物 = 依赖边（任务级 / 字段级）；调度器提供"谁依赖谁"的事实 | 调度侧若只给任务级依赖，字段级影响面就缺一段；血缘侧负责把盲区标出来并可追踪 | L1（非 AI） |
| 编排定义 ↔ 版本库 | 交接物 = DAG 定义文件；**定义在库里还是只在元数据库里，是一个设计决定** | 提交与评审的人（模型没有署名位置） | L1（评审 + 环检测）/ L3（AI 生成的草稿，须补静态校验） |
| 异常检测 ↔ 告警与值班 | 交接物 = 异常判定 + 严重度分级；**是否附带归因是接口的一部分** | 配置判定基准的人；误报率不被度量时，责任事实上无人承担 | L2 |
| 异常检测 / 自愈 ↔ 执行通道 | 交接物 = 跑 / 不跑 / 重跑的动作；**幂等是入场券** | 任务作者（非幂等任务被自动重跑，是任务侧的债） | L2（重跑）/ L3（LLM 决定动作） |
| 时长预测 ↔ 基线 / SLA | 交接物 = 带区间的产出时刻；**必须标记"预测值"而非"承诺值"** | 把预测当承诺使用的那一方（这是最常见的责任错位） | L2 |
| 训练 / 推理任务 ↔ 调度 | 交接物 = 制品与实验追踪（KFP 类）+ 资源形态描述 | ML 平台侧（任务成功不等于指标达标） | L1（调度能力）/ L2（制品与实验追踪的接口无统一标准） |
| 调度器 ↔ 资源层（YARN / K8s） | 交接物 = 队列 / 命名空间 / 配额；两层独立扩缩 | 资源侧管隔离与容量，调度侧管顺序与重试——**耦合后扩缩容要改调度器**（[§12.4](12-scheduler-section-6-sec6.md)） | L1 |
| 顶层编排 ↔ 子编排（跨 DAG 触发） | 交接物 = 触发条件与执行日期语义；**跨 DAG 触发是最容易丢掉数据就绪判定的接缝** | 下游 DAG 的 Owner——上游只保证"触发了"，不保证"数据齐了" | L1（机制）/ L2（在接缝处保持数据就绪判定） |
| 调度器 ↔ 可观测 / 值班 | 交接物 = 调度器自身指标（队列深度、状态转换延迟），而不只是任务成败 | 平台侧；"只监控任务成败不监控调度器自身"是 [§12.6](12-scheduler-section-6-sec6.md) 里四个案例都踩过的坑 | L1 |

一句话概括：**AI 没有给调度新增任何交接物，只改了两处输入的形态**——告警的判定基准，和"能否按时"的预测区间。它带来的第一个新问题也随之出现：**这两个输入过去是"人对情况的判断"，错了由人负责；现在它们是模型输出，错了谁负责？**由此得到三条约定。

**第一条约定：模型输出必须与自己组织的基线挂钩，而不是与厂商的默认阈值挂钩。**异常检测的分级线、预测区间的覆盖率，都要能报出"按我们自己两周数据算出来的数是多少"。报不出来，就不该进值班流程。

**第二条约定：凡是"模型建议 → 自动动作"的链路，中间必须有一个可回滚的闸门。**可回滚的含义很具体：动作前后状态可比较、重跑安全（幂等）、且有一条能停下它的开关。做不到这三条时，模型输出只能进"建议"通道。

**第三条约定：预测与承诺要在数据模型上分开。**"预测 T+1 06:30 产出（区间 ±40 分钟）"与"承诺 T+1 07:00 可用"是两条不同性质的记录，前者可被模型改写，后者只能由人签署。把它们合成一个字段，模型换代的那一天，SLA 会被无声地改写。

### 5.4 公开进展与文献

分三类列，只列能给出标题 / 出处 + 年份的条目；**宁少勿假**。第二类整类都是**判定入口**——给的是"去哪个页面核"，版本与年份随版本发布，类内已注明。

**论文（可核验）**

- Google, "Large-scale cluster management at Google with Borg", EuroSys 2015——优先级、配额与抢占在大规模生产集群里的公开描述；本主题"分级与抢占"这一做法的机制依据。
- Schwarzkopf et al., "Omega: flexible, scalable schedulers for large compute clusters", EuroSys 2013——把调度做成可并行扩展的控制面，是"调度器不成为单点"（[§12.3](12-scheduler-section-6-sec6.md)）的机制依据。
- Burns, Grant, Oppenheimer, Brewer, Wilkes, "Borg, Omega, and Kubernetes", ACM Queue 2016——三者在调度架构上的取舍对照，也是"调度与资源分层"的原始出处。
- Vavilapalli et al., "Apache Hadoop YARN: Yet Another Resource Negotiator", SoCC 2013——**资源调度器**这一层的公开设计文档；它对应主文件 [§2.4](12-scheduler.md) 里"调度系统 vs 资源调度器"的下半句，本节凡说"资源不足时谁让位"，说的都是这一层与业务调度层之间的接口。
- **三条"论文"本节无法核验**：「Argo Workflows 论文（2024）」「Dagster 论文（2024）」「Airflow 2.x 论文（2024）」——它们给的是主题名而非可检索的标题与作者。**处理办法**：保留它们所指的方向（K8s 原生 DAG、资产编排、TaskFlow API），但不把它们当证据；其中 TaskFlow API 的版本归属是可核验的（见下）。

**官方 release note / 文档（判定入口）**——这一类列的是**核验去处**（去哪一页、看哪一条），不是进展断言：本节不据此声称任何产品已具备某能力，版本与年份以页面自身标注的为准；能定位到确切版本与发布日期的条目，在下面直接标注。

- Apache Airflow 的版本发布说明——一个可核验的锚点：**TaskFlow API（`@task` 这类装饰器）是 Airflow 2.0（2020-12）的发布内容**，不是 2.9 的新增项；**EdgeExecutor 属于哪个版本、执行侧是否已解耦，都要以该版本的官方 release note 与 AIP 文档为准**。**要核"调度与执行是否已解耦"，看 release note 里有没有独立的任务执行接口 / SDK 组件，而不是看 benchmark 博客。**
- Apache DolphinScheduler、Argo Workflows 的官方 release note——核验"K8s 集成""性能优化"这类条目的具体内容与版本；**项目治理状态（如是否已从 CNCF 毕业、版本号序列）以基金会公告与官方仓库的 release 页为准**。
- Kubernetes 的 CHANGELOG——核验"Pod 优先级与抢占"何时从 beta 进入稳定（**Kubernetes 1.14 发布于 2019-03**，该特性在其前后进入稳定，具体以对应版本的 CHANGELOG 为准）；这也是"分级与抢占是 L1"这一判断的可核验依据之一。
- Dagster 官方文档——核验"以资产为中心编排""分区物化"这些概念的产品化程度；判定方法：看文档里是否把资产与分区作为一等对象，以及"该重算哪一段"能否由依赖直接推出（本章 [§3.2.7](12-scheduler-section-3-sec3.md)）。
- Apache Airflow 的 AIP（Airflow Improvement Proposal）文档——**核验"调度与执行解耦""DAG 版本化"这类架构变化的第一手入口**：AIP 的编号、状态与目标版本公开可查。凡看到"某调度器完成了架构级解耦"这类说法，先在这里找对应的 AIP；找不到，就当成尚未发布。

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含指标与口径的第三方"AI 改变调度"生产案例。公开材料里能核到的是调度做法的自述（分级抢占、基线、调度与资源解耦——本书 [§6](12-scheduler-section-6-sec6.md) 已整理），以及厂商对异常检测能力的正式发布条目；**缺的是"因此在误报率 / 准时率 / 资源利用率上从多少变到多少"这类带基线的第三方材料**。**这个空白本身是结论**——它正是本节把所有 AI 能力方向判为 L2 / L3 的直接原因：**AI 能力方向的**第②条核不到，就不许靠改写判据把它补上（§5.1 判据声明里那处修正只适用于两行 L1 的非能力方向）。
- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——把你们自己的误报率、区间覆盖率、幂等任务覆盖率算出来并留存口径，下次评审时它就是"含基线的生产材料"。这比引用任何厂商案例都更有说服力，也正好是 §5.2 每条给出的"判定方法"。

**怎么用这份清单**：要核"能力存不存在"看官方文档与 release note（最快）；要核"机制成不成立"看论文（最慢但最稳）；要核"在我这里值不值得做"看 §5.2 给出的判定方法——**第三类问题没有任何公开材料能替你回答**。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **异常检测**：查你所用量测 / 调度平台的官方文档，确认异常检测是正式条目还是预览；再数两周告警里三类各占多少。
2. **时长预测**：用你库里已有的运行历史先算分位数，看区间覆盖率——**先做分位数再谈模型**。
3. **自然语言生成 DAG**：若已试用，统计生成结果里"数据依赖边 : 时间依赖边"的比例，并跑一次环检测与空分区检查。
4. **自治调度**：随机挑三个"会自动重跑"的任务，确认它们幂等；不幂等的任务，自动化就是重复写。
5. **影响分析**：问一次"改这个字段会破坏谁"，看答案能不能在十分钟内从系统里查出来（对应 §5.1 表第 7 行那条 L1）。
6. **调度知识 RAG**：先数跨域检索被权限拒掉的比例。

### 5.5 被过度宣传的部分

**「自治调度 = AI 自动调度、自动重试、自动修复」**——实际是：这句话把三件性质不同的事捆在一起。**自动重试是策略**（按失败原因分类 + 退避 + 幂等判断），**自动让位是策略**（分级与抢占），两者都不需要模型；真正需要模型的只有**归因**（这次失败属于哪一类、该重跑还是该上报）。原因：调度里"该做什么"这个问题的答案，早就写在了优先级、SLA 与幂等这三条事实里，模型能加速的是"读日志"，不是"定规则"。**它什么时候才会成真**：出现公开的、把"LLM 归因 → 自动动作"跑在生产上并披露**误修率与爆炸半径**的材料（两者缺一不可——只报"自动修复了多少次"没有意义，要看**修错的代价**）。

**「LLM 预测任务执行时间，因此调度的产出时刻可以自动保证」**——实际是：产出时刻的可保证性来自 [§12.2](12-scheduler-section-6-sec6.md) 的基线机制（先定必须产出的时刻，再倒推）与 [§12.1](12-scheduler-section-6-sec6.md) 的分级抢占，预测只是其中一个输入；而**预测的作用是把"能否按时"变成可回答，不是把"一定按时"变成可承诺**。原因：预测的错误形态是**在数据量跨台阶时给出错误信心**——恰好是在最不能迟到的日子里最不准。**它什么时候才会成真**：当预测区间在跨台阶场景下的失准可被自动识别（例如把"历史分布已漂移"做成一条显式告警），且组织把它当预测而不是承诺来用。**判定方法**：统计预测值被写进 SLA 文档的次数——这个数不为零，说明它已经被误用了。

**「依赖图 + GraphRAG 让调度具备影响分析能力」**——实际是：影响分析的能力来自**字段级血缘 + 图遍历**，这条能力已经在生产里被反复验证（[11-cross-cutting/05 §6](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-6-sec6.md) 四个案例），与 LLM 无关；GraphRAG 改的是**提问入口**（不用学查询语法也能问）。原因：影响面要求的是**可枚举且可复核**的答案，而"答得不对但很流畅"恰好是语言层最容易引入的失败形态；而本章 [§3.4](12-scheduler-section-3-sec3.md) 组合三已经指出，依赖真相只要各记一份，「任一方漏采都会让影响面失真」——错误的影响面比没有影响面更糟。**它什么时候才会成真**：语言层能被约束成"只生成图查询、不生成结论"，且生成的查询在评测集上有可披露的正确率。

这三条的共性：**它们都把"读日志、估时长、写查询"这些动作的成本下降，当成了"调度决策质量上升"**。而本主题的质量判据只有三条——依赖判定在哪一层、资源不足时结果可不可控、失败能不能按原因分类；这三条一条也没有因为 AI 而改变。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 调度侧对 AI 的采纳会集中在"告警分级 + 失败归因 + 建议"这一层，人仍然拍板 | 调度 / 可观测产品的正式发布条目集中在异常检测与归因；自动化动作仍需要显式开关与幂等前置 | 出现第三方公开材料，披露"LLM 决定重跑 / 降级"在生产中的误修率与事故复盘 |
| 自然语言生成 DAG 会先以"草稿 + 门禁"的形态落地，而不是直接进生产调度 | 编排工具开始内置"生成物的静态校验"（环检测、依赖类型检查）作为正式功能；生成物默认进版本库 | 出现把生成定义直接下发到生产的公开生产案例，且不设人工评审环节 |
| 调度系统的下一次实质变化来自"依赖判定下沉到资产 / 分区"与"调度 / 执行解耦"，两者都与 LLM 无关 | 各调度器公布的架构变化集中在执行侧解耦（[§12.4](12-scheduler-section-6-sec6.md) 的「调度与资源管理两层解耦」）与资产 / 分区语义（[§3.6](12-scheduler-section-3-sec3.md) 的「资产级编排（软件定义资产）+ 分区级物化记录」，产品化形态见 [§3.2.7](12-scheduler-section-3-sec3.md)）；依赖与血缘共用同一份元数据（[§12.3](12-scheduler-section-6-sec6.md)） | 架构讨论的焦点转向"由模型决定依赖与顺序"，且出现可核验的生产成效 |
| 联邦调度（跨云 / 跨集群统一 DAG）的进展会慢于宣传，瓶颈在数据与账号边界 | 落地材料以"同云多集群""同账号多租户"为主；跨云案例附带大量合规说明 | 出现跨云的统一联邦 DAG 生产案例，且不附带数据出域与账号边界的例外条款 |

写这四条时的共同约定：**信号必须是外部可观察的**（发布条目、架构文档、第三方公开案例），而不是"我觉得会"。凡写不出证伪信号的判断，本节不写。**被检验得最快的是第二条**——编排工具的下一个版本发布说明里有没有"生成物校验"，一年内就能看到；**最慢的是第一条**——它是一条否定式预测，需要有人长期公开误修率，而这类数字恰好是最少被公开的。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 关键链路仍靠 Cron + 任务依赖 | 先补分区就绪 / 空分区判定（[§3.6](12-scheduler-section-3-sec3.md) 的依赖下沉） | 观察"数据错但任务全绿"这类事故是否还在发生 | 不要在依赖还建在"任务成功"上时先上异常检测——它检测不到这一类 |
| 告警噪声大、值班靠点掉 | 把阈值换成按作业自身的分位数，并做严重度分级 | 观察误报占比与"判不准"占比的变化 | 不要让异常判定直接触发重跑 / 阻断；不要把误报率排除在指标之外 |
| 被问"今天能不能按时" | 先定义必须产出的时刻（基线），再用历史分位数给出带区间的预测 | 观察区间覆盖率与跨台阶后的失准次数 | 不要把预测写进 SLA 文档；不要在没有历史数据时先买模型 |
| 想做自然语言生成 DAG | 先立两条门禁：环检测 + "关键链路是否有数据就绪判定" | 观察生成物里数据依赖边的占比、生成物是否都进了版本库 | 不要让生成结果直接下发生产；不要跳过"翻译进版本库"这一步 |
| 想上"自治调度" | 先把确定性那一半做掉：分级与抢占、按原因分类重试、补数独立队列 | 观察失败自愈比例与幂等任务的覆盖率 | 不要自动重跑未验证幂等的任务；不要让 LLM 直接进执行通道 |
| 已自研异常检测 / 预测模型 | 给模型输出加上"基准来自我们自己两周数据"的出处与责任人 | 观察模型换代时 SLA 与判定线有没有被无声改写 | 不要把模型输出与承诺字段合并成一个字段 |
| 想做调度知识 RAG | 先补"权限域 + 新鲜度 + 责任人"三个字段 | 观察跨域召回被权限拒的比例、Top-K 中超新鲜度窗口的占比 | 不要在没定召回前 / 后过滤时合并跨域编排资产 |
| 要跨云 / 跨集群调度 | 先划清数据边界与账号边界，再谈统一语义 | 观察落地案例是否都带合规例外条款 | 不要在架构里预留"联邦 DAG"这个假设；不要把它包装成 AI 演进 |
| 核心痛点是"这张表新鲜吗" | 按 [§3.2.7](12-scheduler-section-3-sec3.md) 评估资产级编排 | 观察"该重算哪一段"能否由依赖直接推出 | 不要挂 AI 的名义重做一次编排范式迁移 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改依赖层次、翻存量 DAG、动合规边界、扩大自动化半径），**而收益依赖一个尚未成立的假设**（模型能归因对 / 生成物可静态校验 / 联邦语义可统一）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**判断依据的来源**——告警的基准从"人拍的静态阈值"换成"该作业自身的条件分布"，"能否按时"从"人估的一个数"换成"带区间的预测"。它改变的是**判断的入口与基准**，**没有**改变本章 [§3.1](12-scheduler-section-3-sec3.md) 那条更前置的约束：**依赖判定建立在哪一层事实上**。所以"任务全绿、数字算错"这类故障，一条 AI 能力都检测不到；它要的是把依赖下沉到数据与分区，那是范式与治理问题，不是模型问题。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是"读日志 / 估时长 / 写查询"的成本，还是"依赖判定在哪一层"这件事？** 前者今天就有用（本节判 L2 的那几条），后者不是 AI 能解的。第二条同样快的判断：**它需要任务幂等吗、动作可回滚吗、输出能被指标度量吗**——三条答不上来的方向，只能停在"建议"通道。
>
> 如果只能带走一句话：**先把依赖判定下沉到数据（分区就绪 / 空分区），再让 AI 去改判断的基准**；顺序反过来，就是把一个检测不到故障的模型接在一条本来就会静默出错的链路上。
>
