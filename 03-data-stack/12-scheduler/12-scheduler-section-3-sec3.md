## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

把这些调度器排成一道选型题：复杂 DAG + Python 用 Airflow、国产易用用 DolphinScheduler、阿里云用 DataWorks、K8s 原生用 Argo、ML 用 KubeFlow、现代数据栈用 Prefect / Dagster。这张表的隐含假设是「它们在竞争同一件事」——但它们其实在**两个正交的轴**上做不同取舍：**调度什么**（任务，还是数据资产），以及**执行归谁管**（调度器自带 Worker、交给容器编排、还是交给托管算力）。

决定第一根轴的那条底层机制是：**依赖判定建立在哪一层事实上**。Cron 说「时间到了」；任务依赖说「上游任务返回成功了」；Sensor / 资产依赖说「上游数据真的就绪了」。这三句话在正常路径上等价，在异常路径上完全不同——上游任务返回成功码却只写出半个分区，任务级依赖会照常触发下游，错误于是沿链路静默传播，表现为「数据错了」而不是「任务失败了」。主文件 §2.1 里 Trigger 与 Sensor 的区分，本质就是这条分界线。

第二层筛选才是执行归谁管。调度器的状态机（谁在跑、跑到哪、要不要重试）与执行资源（CPU / 内存 / 队列）如果耦合在同一个进程里，想扩缩容就等于改调度器本身；本章 [§ 6.4 LinkedIn 案例](12-scheduler-section-6-sec6.md) 把调度层与资源层拆成两层各自扩缩，[§ 6.3 Netflix 案例](12-scheduler-section-6-sec6.md) 把调度状态机做成可横向扩展的服务，走的都是这条线。

所以下表不是选型表，而是「本主题下最容易被约束推翻的直觉」清单。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 依赖判定依据（任务成功 / 数据就绪） | 下游在什么信号上被触发，直接决定错误会不会静默传播 | 「上游任务绿了，数据就对了」——任务返回码与数据正确性是两件事 |
| 执行资源归谁管 | 调度器要不要自己扛弹性与隔离 | 「调度器也做强做大」——把状态机与资源耦合后，扩缩容要改调度器 |
| 任务规模与日调度量 | 调度状态机必须是单进程还是可横向扩展 | 「开源自建扛得住」——单调度进程的解析与状态写入是硬上限 |
| 数据就绪的粒度（分区 / 文件 / 事件） | 用 Cron、Sensor 还是资产依赖 | 「等上游就绪就挂个轮询 Sensor」——轮询在分区迟到时会空转并占住并发槽 |
| 产出时刻是否有承诺（SLA / 基线） | 要不要引入「基线」这层抽象 | 「SLA 就是告警阈值」——告警在超时之后响，基线在超时之前倒推 |
| 团队技能与运维能力（Python / K8s / 云） | 声明式定义还是代码定义，自管还是托管 | 「UI 拖拽最省事」——UI 生成的 DAG 定义默认落在元数据库，而非版本库 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 Airflow + Python DAG（任务级、自管执行的通用形态）

- **被什么约束逼出来**：链路依赖复杂到必须被表达成图、且团队以 Python 为主，希望编排定义能进代码评审；同时不愿把执行载体锁死——同一份 DAG 要能跑在本机、Celery 集群或 K8s 上。
- **结构**：DAG 是调度器扫描的一等公民，边就是依赖；依赖判定的依据是 TaskInstance 的状态。

```python
from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.sensors.external_task import ExternalTaskSensor
from datetime import datetime, timedelta

with DAG(
    "daily_etl",
    schedule="0 2 * * *",                       # 触发：时间到了
    start_date=datetime(2025, 1, 1),
    catchup=False,
    default_args={"retries": 3, "retry_delay": timedelta(minutes=5)},
) as dag:
    wait = ExternalTaskSensor(                 # 触发：上游 DAG 的任务成功了
        task_id="wait_upstream", external_dag_id="ods_load", poke_interval=300)
    extract = BashOperator(task_id="extract", bash_command="python extract.py")
    transform = SparkSubmitOperator(task_id="transform", application="transform.py")
    wait >> extract >> transform               # 边 = 依赖，DAG 图就是真相
```

```text
调度循环（单调度器形态下，它同时是控制面与瓶颈）
  扫描 DAG 目录 → 解析 DAG 文件 → 判断本轮该跑哪些 TaskInstance
        ├─► 写元数据库（task_instance 状态行）
        └─► 交给 Executor（Local / Celery / K8s）→ Worker 心跳回写状态
  ────────────────────────────────────────────────
  依赖判定的依据：TaskInstance 的状态（不是"数据是否就绪"）
  → 想知道"表新不新鲜"，得另建一层资产视图
```

- **为什么这样设计有效**：因为 DAG 是文件、状态在共享元数据库，所以编排可以被版本管理、评审与回滚，而调度进程本身可以随时重启并从库中恢复进度；代价是调度器必须周期性解析所有 DAG 文件并高频写状态行，元数据库因此成了全局共享的写热点。
- **代价**：DAG 解析发生在调度循环里，DAG 文件里写重逻辑（连数据库、拉接口）会拖慢整个调度；TaskInstance 状态行随「DAG 数 × 时间」线性增长，历史数据清理是常驻工作；XCom 只适合传小数据，大数据传参会把元数据库撑起来。
- **失效点**：当日调度量增长到「一轮调度循环跑不完解析与派发」、或元数据库写入成瓶颈时，集中式调度从「统一控制」反转成「全局延迟」，因为所有 DAG 共用同一个调度周期——它不是某个 DAG 慢了，而是所有人的触发时刻一起被推后。
- **真实使用**：Airflow 由 Airbnb 于 2014 年前后创建、2015 年开源，后进入 Apache 基金会 【公开】（Apache Airflow 项目公开历史，可自行核验）；其单实例调度形态在万级任务以上需要改造，见本章 [§ 6.3 Netflix](12-scheduler-section-6-sec6.md) 与 [§ 6.4 LinkedIn](12-scheduler-section-6-sec6.md)。

#### 3.2.2 DolphinScheduler + UI DAG（声明式定义、UI 优先）

- **被什么约束逼出来**：DAG 的日常维护者大量是数仓 / SQL 开发而非 Python 工程师，需要「看得见的图 + 点得动的改」；同时任务类型要覆盖 Hive / Spark / Flink / SQL / Shell 等既有生态，接入成本必须低于自研。
- **结构**：工作流是一份定义数据（任务列表 + 关系列表 + 调度配置），不是代码文件。

```text
DolphinScheduler 3.x 的工作流定义（workflow-definition 接口的形态）
  { "name": "daily_etl",
    "taskDefinitionJson": [
      {"code": <客户端生成的雪花 id>, "name": "extract",   "taskType": "SQL"},
      {"code": <客户端生成的雪花 id>, "name": "transform", "taskType": "SPARK"} ],
    "taskRelationJson": [
      {"preTaskCode": <extract 的 code>, "postTaskCode": <transform 的 code>} ],
    "schedule": {"crontab": "0 0 2 * * ? *", "releaseState": "ONLINE"} }
  ────────────────────────────────────────────────
  图的边 = taskRelationJson 里的记录（存元数据库）
  依赖判定的依据：上游任务实例的状态（与 3.2.1 同一层事实）
  可核验点：任务的 code 与关系的 postTaskCode 必须是同一个雪花值，
            否则接口会因"关系指向不存在的任务"而失败
```

- **为什么这样设计有效**：因为 DAG 被降级成一份可被读写的数据，所以图可以被 UI 编辑、被复制成模板、被跨项目引用，非工程师也能独立交付一条链路；代价是它同时失去了代码形态带来的所有能力——diff、评审、单测、一键回滚。
- **代价**：定义进不了版本库的常规流程（除非团队改用 SDK 声明式地生成并上传定义），"这次改动改了什么"只能靠平台的操作记录；逻辑分两层（SQL 在平台里、脚本在机器上），排障要跨两处看；跨环境同步依赖导入导出，口径容易漂移。
- **失效点**：当链路数量增长到「一次误改的影响面无法预估」时，UI 定义从「易用」反转成「不可治理」，因为定义存放在元数据库而非文件系统，版本控制工具无从介入——没有 diff 就没有回滚点，改错了只能靠人回忆刚才点过什么。
- **真实使用**：Apache DolphinScheduler 源自国内团队（早期名为 EasyScheduler），后进入 Apache 孵化并成为顶级项目 【公开】（Apache DolphinScheduler 项目公开历史，可自行核验）；国内企业用它编排数仓任务是常见做法 【经验】。

#### 3.2.3 DataWorks 一站式（托管 + 基线）

- **被什么约束逼出来**：组织需要把「几点必须产出」变成可被系统管理、可被追责的契约，而不是事后才知道迟到；同时不愿自建调度集群、租户隔离与算力调度，希望算力由平台托管。
- **结构**：核心抽象是「基线」——一个被持续预测、会提前告警、能自动升级的产出承诺。

```text
基线（baseline）：把"必须产出的时刻"变成系统对象
  基线：这份报表 09:00 前必须产出，责任方 = 某域 Owner
        │
        ├─ 持续计算：当前进度 → 预计完成时刻
        ├─ 预计 > 基线时刻 → 提前告警 + 指出关键路径上的瓶颈任务 + 提权
        ├─ 严重偏离 → 自动升级到责任方与管理者（而非静默等待）
        └─ 资源紧张 → 按基线紧急度与业务重要性排序（而非提交顺序）
  ────────────────────────────────────────────────
  它同时回答两个问题：任务跑完了吗（调度）+ 能不能按时到（承诺）
  依赖判定的依据：任务状态 + 产出时刻契约（比 3.2.1 多一层）
```

- **为什么这样设计有效**：因为把「产出时刻」当成了倒推的锚点——由基线时刻反推最晚开始时刻，再由关键路径判断资源该给谁，所以「会不会迟到」在还来得及的时候就被暴露；代价是这条承诺只有在算力可被平台统一调配时才兑现得了。
- **代价**：与云平台强绑定，DAG 与调度语义不随组织迁移，换平台等于重写；调度与算力耦合在一套产品里，容量与成本的调整空间受平台规格限制；按任务量与算力计费，成本随规模线性上行 【经验】。
- **失效点**：当多条基线挤在同一时间窗、而可分配资源不足以覆盖它们的总时长时，基线从「承诺」退化成「每天滚动升级的告警」，因为它能排优先级、不能创造资源——优先级只决定谁先被满足，不改变总供给。
- **真实使用**：阿里自 2014 年起建设以基线为核心的调度体系，跨业务单元共用一套调度，见本章 [§ 6.2 阿里案例](12-scheduler-section-6-sec6.md) 【公开】（阿里 DataWorks 公开材料，2014-2024）。

#### 3.2.4 Argo Workflows + K8s（K8s 原生，调度器不管执行）

- **被什么约束逼出来**：执行载体已经是 K8s、任务制品已经是镜像，组织不希望调度器再自建一套 Worker 池与资源模型——资源隔离、配额、扩缩容都应由容器编排承担。
- **结构**：每个任务就是一个 Pod，调度器只负责「依赖是否满足」与「何时创建 Pod」。

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata: {name: daily-etl}
spec:
  entrypoint: etl
  templates:
  - name: etl
    dag:
      tasks:
      - {name: extract,   template: extract-task}
      - {name: transform, dependencies: [extract], template: transform-task}   # 边 = 依赖
  - name: extract-task
    container:
      image: registry/extract:2025.01.15        # 制品是镜像：环境一致性由镜像保证
      resources: {requests: {cpu: "2", memory: 4Gi}, limits: {cpu: "4", memory: 8Gi}}
```

```text
谁负责什么（两层各自演进）
  调度层（Argo）：依赖判定、顺序、重试、工作流状态
  资源层（K8s）：Pod 调度、配额、抢占、节点扩缩
  ────────────────────────────────────────────────
  换资源层不改工作流定义；调度层扩容不影响配额策略
  代价：每个任务都要走一次 Pod 生命周期（创建 / 拉镜像 / 回收）
```

- **为什么这样设计有效**：因为执行单位退化成 Pod，调度器就只剩一张很薄的状态机，容量问题被转手交给 K8s；代价是「任务」与「镜像」被强绑定——连一段三行的 Shell 也得先有个镜像，从脚本到可运行之间的距离被拉长了。
- **代价**：镜像构建、版本管理与仓库治理成为新的常驻流水线；Pod 启动与拉镜像的开销与任务数成正比、与任务时长无关，大量秒级任务不划算；K8s 的 RBAC、网络策略与调度语义叠加，排障要跨两层。
- **失效点**：当日调度量由「大量短任务」构成时，Argo 从「弹性好」反转成「开销量大」，因为每个任务都要支付一次 Pod 生命周期成本，而这个成本与任务本身的计算量无关；此时把一批小任务合并进同一个 Pod 才划算。
- **真实使用**：Argo Workflows 是 CNCF 项目（Argo 系列于 2022 年从 CNCF 毕业）【公开】（CNCF 公开项目材料，可自行核验）；K8s 上的数据与 ML 流水线大量使用 【经验】。

#### 3.2.5 Prefect + Python DAG（动态拓扑，运行期成图）

- **被什么约束逼出来**：拓扑在运行前无法确定——要按上游结果决定下游跑哪些分支、按数据规模决定扇出多少并行子任务；数据量又不值得上集群，团队要的是「像写 Python 一样写编排」。
- **结构**：编排定义是运行期构造的对象，不要求在调度器启动时全量注册。

```python
from prefect import flow, task

@task(retries=3, retry_delay_seconds=300)          # 失败语义写在任务上
def transform(partition: str) -> str: ...

@flow
def daily(partitions: list[str]):
    done = transform.map(partitions)               # 扇出：并行度由运行期数据决定
    if any_failed(done):                           # 分支：拓扑由运行期结果决定
        flow_run = notify_failure()
    return load(done)
```

- **为什么这样设计有效**：因为图是在运行期长出来的，所以「按数据决定规模、按结果决定分支」这种拓扑可以被直接表达，不必预先声明所有可能的路径；代价是调度器在提交前不可能知道这次到底会跑多少任务。
- **代价**：容量规划与依赖体检只能事后做；「这条链路今天有几个任务、要吃多少资源」要先跑起来才知道；算子与生态规模小于 Airflow 系，很多集成要自己写 【经验】。
- **失效点**：当组织需要「变更前就能回答影响面与产出时刻」时（承诺型报表、合规口径），动态拓扑从「灵活」反转成「不可承诺」，因为提交前算不出这次 Run 的规模，也就无法反推最晚开始时刻与所需资源——此时需要的是 3.2.3 那种以产出时刻为锚点的模式。
- **真实使用**：Prefect 是 Python 原生编排引擎，同时提供自托管与托管（Cloud）两种形态 【公开】（Prefect 官方文档，可自行核验）；现代数据栈团队采用较多 【经验】。

#### 3.2.6 KubeFlow + ML Pipeline（制品与实验追踪优先）

- **被什么约束逼出来**：ML 流水线的「成功」不在任务返回码，而在指标；同一份数据要在多组参数下反复跑，需要把数据集、模型、指标这些**制品**当作一等公民追踪，否则「这个模型是哪次跑出来的」无法回答。
- **结构**：组件之间传的是制品引用，不是控制流。

```python
@dsl.pipeline(name="train-and-eval")
def pipeline(data_uri: str, lr: float = 1e-3):
    prep   = preprocess(data_uri)                    # 制品：数据集
    train  = train_model(prep.outputs.dataset, lr=lr)  # 制品：模型
    metric = evaluate(train.outputs.model)           # 制品：指标（用于比较实验）
    # 每一步都是容器；制品进元数据存储，"哪次跑用了哪份数据"可追溯
```

- **为什么这样设计有效**：因为依赖的载体是制品引用与追踪记录，所以同一套流水线换参数重跑时，每次的输入输出都能被关联与比较，模型复现与回滚有据可依；代价是每一步都要容器化、每类制品都要有元数据登记。
- **代价**：为 ML 场景做重——通用 ETL 用它属于过度工程；与 K8s 深度绑定，本地开发与调试体验弱于纯 Python 方案；制品存储与分析侧元数据要另建一套治理 【经验】。
- **失效点**：当场景退化为「纯 ETL、没有复现与对比需求」时，KFP 从「可追溯」反转成「每一步都要包容器 + 管制品」的纯开销，因为它的机制优势（制品与实验追踪）在这类场景里没有任何收益——此时 3.2.1 的一条 SQL 任务更省。
- **真实使用**：Kubeflow Pipelines 是 Kubeflow 项目的流水线组件 【公开】（Kubeflow 官方文档，可自行核验）；ML 平台团队用来承载训练与评估流水线 【经验】。

#### 3.2.7 Dagster + 资产编排（Asset-first）

- **被什么约束逼出来**：日常最痛的问题不是「任务跑没跑」而是「这张表 / 这个模型是不是最新的」，以及「它由哪些上游决定、改了会波及谁」；依赖需要建立在数据资产上，而不是任务上。
- **结构**：调度的单位从 Task 换成 Asset，调度器持有「资产 ↔ 资产」的依赖图与每个资产的物化记录。

```python
from dagster import asset, DailyPartitionsDefinition

daily = DailyPartitionsDefinition(start_date="2025-01-01")

@asset(partitions_def=daily)
def dwd_orders(): ...                       # 资产的物化记录：哪天产出了、产的是什么

@asset(partitions_def=daily, deps=[dwd_orders])
def dws_trade_1d(): ...                     # 依赖写在资产之间，不写在任务之间

# 调度器据此回答的是资产问题：
#   "dws_trade_1d 的 2025-01-15 分区物化了吗？"
#   "改了 dwd_orders 的哪一段，需要重算 dws_trade_1d 的哪些分区？"
```

- **为什么这样设计有效**：因为依赖的节点是资产、且每个节点带分区级的物化记录，所以「哪些分区没算、该重算哪一段」可以直接由调度器推出，不必让人把任务图手工翻译成数据图；代价是这张资产图必须被显式维护，存量 SQL / 脚本要先改造。
- **代价**：资产边界要人工或半自动界定，界错了会出现「资产显示新鲜、实际缺一天分区」；与既有任务式调度器混用时，会同时存在两套依赖真相（任务图与资产图）需要对齐；资产级重算的幂等性要自己保证。
- **失效点**：当大量资产由调度器之外的系统写入时，资产图从「唯一真相」反转成「过期地图」，因为调度器只知道自己编排过的那部分物化记录，外部写入它看不见——此时必须靠分区契约与外部就绪信号补齐，否则「新鲜」是假的。
- **真实使用**：Dagster 提出 software-defined assets（软件定义资产）的概念，把编排单位从任务移到数据资产 【公开】（Dagster 官方公开材料，2020 年前后，可自行核验）；现代数据栈团队采用较多 【经验】。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 复杂 DAG、Python 团队、定义要进代码评审 | Airflow + Python DAG | 不选 UI DAG：定义进不了版本库，没有 diff 与回滚点 | 编排定义的维护者是不是工程师 |
| 数仓 / SQL 开发为主、要可视化自助 | DolphinScheduler + UI DAG | 不选纯代码方案：非工程师交付一条链路要排平台团队的队 | 变更是否需要预先评审与回滚 |
| 有明确产出时刻承诺、要事前预测 | DataWorks 一站式（基线） | 不选纯任务级调度：它只能回答"跑完了吗"，答不了"能不能按时到" | 有没有可考核的产出时刻 |
| 执行载体已是 K8s、任务已容器化 | Argo Workflows | 不选自管 Worker：资源隔离与扩缩被重复造一遍 | 任务镜像是否已存在 |
| 大量秒级短任务 | 任务级调度 + 打包执行（合并进同一 Worker / Pod） | 不选 Argo：每个任务一次 Pod 生命周期，开销与任务数成正比 | 平均任务时长是否远小于 Pod 启动开销 |
| 拓扑运行期才确定、数据量在单机量级 | Prefect + Python DAG | 不选 Cron + 静态 DAG：分支与扇出无法预先表达 | 提交前能否算出这次要跑多少任务 |
| 要追踪制品与实验、多组参数反复跑 | KubeFlow / KFP | 不选通用 ETL 调度：任务成功不代表指标达标 | 是否有复现与模型回滚需求 |
| 核心问题是"资产新不新鲜、改了波及谁" | Dagster（Asset-first） | 不选任务级调度：任务图与数据图之间要人工翻译，会分叉成两套真相 | 是否按资产/分区提问 |

本节最常被误选的一对，是**把「DolphinScheduler 的 UI DAG」与「Airflow / Argo 的代码化 DAG」当成同一个东西的两种界面**。它们的机制差别不在好不好看，而在**真相存在哪里**：代码化定义的真身在版本库里（可 diff、可评审、可回滚、可对定义本身做单测），UI 定义的真身在元数据库里（每次修改只留一条操作记录）。误选的实际后果是——上线三年后，没人能回答「这条链路上周改了什么、当时是怎么改的」，一次误改只能靠人回忆，而链路越关键、越不敢动它。

### 3.4 组合模式：真实系统不会只用一种

**组合一：任务级调度器 + 独立资源层（谁决定何时跑、谁决定在哪跑）**

- 构成：Airflow / DolphinScheduler / Azkaban 承担依赖判定与顺序，执行交给 Celery / K8s / YARN 队列；调度只声明资源需求，不实现资源分配。
- 职责边界：调度层管「何时、按什么顺序、依赖是否满足」，资源层管「在哪跑、给多少、什么时候抢占」，两层通过标准接口对接。
- 运维代价：多一层接口与状态对账（调度以为任务在跑、资源层已经杀了 Pod，这类不一致必须有兜底）；两层的容量要分别规划。
- 适合规模：任务从千级走向万级以上、且执行载体已经开始多样化的组织，见 [§ 6.4 LinkedIn 案例](12-scheduler-section-6-sec6.md)。

**组合二：任务级调度 + 数据就绪信号（把依赖下沉到数据层）**

- 构成：调度仍由 Airflow / DolphinScheduler 承担，但关键边不由「上游任务成功」触发，改由分区就绪 / 文件到达 / 事件触发（Sensor、外部信号、分区契约）。
- 职责边界：调度器管调度，数据的「就绪」由数据侧自己声明；调度器不再替数据判断它是否可用。
- 运维代价：每条关键链路都要补就绪判定与空分区识别，Sensor 轮询本身的并发占用与超时策略要治理（轮询会占住 Worker 槽位）。
- 适合规模：数据来源跨系统、上游存在静默失败的链路（多源入湖、外部数据接入）。

**组合三：资产级编排 + 任务级执行 + 血缘/影响面（谁的地图，谁的腿）**

- 构成：Dagster 类资产图回答「哪些资产、哪些分区该被物化」，实际执行下发给 Airflow / K8s；DAG 的依赖关系同时作为血缘的一条采集来源，反哺变更影响面分析。
- 职责边界：资产层管「该算什么」，执行层管「怎么算」，血缘层管「改动会波及谁」——三者共用同一份依赖关系，而不是各记一份。
- 运维代价：三套系统之间的依赖真相必须定期对账，任一方漏采都会让影响面失真；资产边界定义本身就是治理工作。
- 适合规模：已有血缘 / 目录体系、且已经因「任务图与数据图分叉」付过代价的组织，见 [11-cross-cutting/05 血缘与影响面](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 硬编码依赖 | DAG 图上上下游互不相连；脚本里出现 `sleep 3600`、直接 `subprocess` 调上游脚本 | 依赖判定退化成「时间猜」，上游延迟→下游空跑，上游失败→下游照样算，故障表现为数据错而非任务失败 | 从 Crontab 迁移过来时逐个脚本加 sleep 最省事，图上一眼看不出来 | DAG 显式依赖 + Sensor / 事件触发；把「等待」从脚本搬回图里 |
| 缺乏重试机制 | 告警里反复是同一批任务，失败原因多为连接超时、资源不足等临时性原因 | 临时性失败被当永久失败处理，数据延迟到下一次人工介入；运维人力被固定占用 | default_args 没配全，或配了重试但没配退避，重试风暴打垮上游 | retries + retry_delay + 指数退避 + 区分可重试 / 需人工 |
| 未做 SLA 监控 | 报表没出是业务方先发现的，系统没有先告警；没人能回答「上周准时率是多少」 | 发现问题的时间点 = 使用者发现的时间点，补救窗口被吃掉；「能否按时」无法被度量，也就无法被改进 | SLA 被理解成「超时告警」这一条配置，而不是产出时刻的契约 | SLA Miss 告警 + 基线式产出时刻 + 超时自动升级链 |
| 单点故障 | 调度器重启期间所有任务停摆；重启后出现大量「卡在 running」的任务实例 | 调度器是全局控制面，它的可用性等于全链路可用性；状态不确定时重跑可能重复写，事故从「延迟」升级为「数据错」 | 单机部署、元数据库同机，先跑起来再说 | 多副本调度器 + 元数据库高可用 + 任务幂等（重跑安全） |
| DAG 过深 | 一条链路串联上百个任务【经验】阈值，一个节点失败整条链等它；关键路径长到无法承诺产出时刻 | 关键路径长度就是全链路延迟的下限，本可并行的任务被串行排队，重试成本被链路长度放大 | 按 ODS→DWD→DWS 一路画到底，画图时只考虑「谁依赖谁」不考虑「层」 | 并行执行 + 分层编排（拆 DAG / 跨 DAG 触发）+ 只对真实依赖建边 |
| 未做资源隔离 | 补数一开，日常产出全线变慢；大促期间非核心任务挤占核心链路资源 | 共享队列里一次突发拖慢全链路，故障半径等于整个资源池 | 一个集群一套队列最省事，隔离被当成"以后再说" | YARN 队列 / K8s Namespace + 配额 + 补数独立队列 + 优先级与抢占 |

**「硬编码依赖」是最危险的一条，因为它的故障形态是数据错误而不是任务失败。** 生产里的暴露方式通常是：某个上游任务因为要等多一个小时的分区，被人手动改成了延迟启动，下游的 `sleep` 还按老时长等——报表照样产出、数字照样有，只是少算了当天的尾巴。这类事故平均发现时间以天计 【经验】，因为没有任何告警会响：任务全绿、SLA 全过，只有某个数字不对。

**「单点故障」的代价不止是停机时长，还有状态的不确定性。** 机制上，调度器的状态机与元数据库一起决定了「这个任务到底跑没跑、跑到哪一步」；当它们同时不可用时，重启后只能靠猜测恢复，而猜测的两种结果都不便宜——判成「没跑」会重复写（需要任务幂等兜底），判成「跑过了」会漏数（需要事后补数核对）。这也是 [§ 6.3 Netflix 案例](12-scheduler-section-6-sec6.md) 要把调度做成可横向扩展服务的原因：容量与可用性在单实例形态下是同一个上限。

**「未做资源隔离」不会以「慢」的形式暴露，而是以「一起慢」的形式暴露。** 一次补数（可能一次重算数月分区）与日常任务共用资源池时，被拖慢的不只是那条链路，而是所有链路；[§ 6.1 字节案例](12-scheduler-section-6-sec6.md) 的做法是把补数放独立队列并强制幂等，让「补数不影响日常产出」变成一条可验证的性质，而不是一句期望。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 千级 → 万级任务/天 | 单调度器 + 本地执行 | 调度循环被 DAG 解析与状态写入拖长，所有 DAG 的触发时刻一起后移 | 分布式执行器 + 元数据库独立部署，或调度状态机横向扩展 | 拆执行载体、元数据库独立与调优；历史任务实例清理策略要补 |
| 依赖从「任务成功」→「数据就绪」 | Cron + 任务依赖 | 上游返回成功但分区没写全，下游静默算错，全绿无害报 | Sensor / 分区就绪 / 事件触发，关键链路补空分区判定 | 每条关键链路补就绪检查；轮询占用并发槽，超时策略要治理 |
| 单团队 → 多租户共用调度 | 共享队列 | 一次补数或大促拖慢全链路，故障半径等于整个资源池 | 队列 / 命名空间隔离 + 配额 + 优先级与抢占 | 配额与排队策略成为常驻治理；抢占要求任务可被暂停/重跑 |
| 调度器成为全局依赖 | 单实例调度器 | 调度器故障 = 全部数据产出停止；重启后状态不确定 | 多副本 + 状态可恢复 + 任务幂等 | 幂等改造是最贵的一步：重跑不能重复写 |
| 「跑完了吗」→「资产新鲜吗」 | 任务级调度 | 每个团队自建「表 ↔ 任务」映射表，任务图与数据图分叉成两套真相 | 资产级编排（软件定义资产）+ 分区级物化记录 | 存量 DAG 要翻译成资产依赖；资产边界定义本身是治理工作 |
| 通用 ETL → 加入训练 / 推理 | 复用数仓调度器 | 任务成功不代表指标达标，多组实验无法比较与复现 | 制品与实验追踪（KFP 类）+ 制品元数据 | 制品存储、模型版本与追踪体系要另建一套 |
| 单云 → 多云 / 私有化 | 云托管一站式 | 托管调度不可迁移，DAG 与算力语义被锁在平台里 | 开源调度器 + 自建资源层 | 迁移期要重写 DAG 与调度语义，运维面显著扩大 |

补一句判据：**当「任务成功」与「数据可用」已经不是同一件事时，就该换依赖判定的那一层**——要么把依赖下沉到数据，要么允许两边同时存在但必须定期对账。

### 3.7 自检清单

1. 随机挑一条关键链路，图上能不能看到它依赖的全部上游？看不到即「硬编码依赖」。
2. 这条链路上游任务返回成功但只写了半个分区，下游会不会照常跑？会，说明依赖判定还在任务层。
3. 关键表是否都有分区就绪检查或空分区判定？没有，则静默算错只是时间问题。
4. 失败重试是否配了退避策略，且区分了可重试与需人工？只配 retries 不配退避，会变成重试风暴。
5. 「这批数据几点必须产出」有没有被系统管理？只在文档里 = 没有基线。
6. 有没有一个数字能回答上周「准时产出率」？答不出，说明 SLA 监控还停留在告警配置。
7. 调度器重启一次会发生什么？能明确回答「任务从哪继续、会不会重复写」才算通过。
8. 元数据库是否与调度器同机、单实例？是，则单点风险与容量上限是同一个问题。
9. 最长的一条关键路径有多少个串行节点？超过两位数，先查其中有多少边是真实依赖。
10. 补数任务与日常任务是否共用资源池？共用，则一次补数会拖慢全部产出。
11. 是否存在无下游、无人认领的僵尸任务？存在，说明依赖图已经与实际脱节。
12. 编排定义的真相在哪里——版本库还是元数据库？在库里，就要回答「谁能给出上周的 diff」。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| Python 团队、定义要评审 | Airflow + Python DAG | 定义是文件、状态在库，可版本管理，可重启恢复 |
| 数仓 / SQL 开发自助、要可视化 | DolphinScheduler + UI DAG | DAG 降级成可编辑的数据，非工程师可独立交付 |
| 有产出时刻承诺 | DataWorks 基线 | 从产出时刻倒推，迟到在还来得及的时候暴露 |
| 执行载体已是 K8s | Argo Workflows | 调度只留薄状态机，隔离与扩缩交给编排 |
| 大量秒级短任务 | 任务级调度 + 打包执行 | Pod 生命周期开销与任务数成正比，短任务不划算 |
| 拓扑运行期才定 | Prefect | 图在运行期长出来，才表达得了分支与扇出 |
| 要追踪制品与实验 | KFP | 制品是一等公民，换参数重跑仍可比较复现 |
| 核心问题是资产新鲜度 | Dagster | 依赖画在资产与分区上，"该重算哪段"可直接推出 |
| 规模上万级、多租户 | 任务级调度 + 独立资源层 + 隔离与抢占 | 控制面与资源面独立扩缩，故障半径才可收窄 |

> 本节小结：本主题下决定模式选择的**唯一那条最前置的约束，是「依赖判定建立在哪一层事实上」**——任务返回码、还是数据实际就绪。它比「选哪个调度器」更前置，因为选错了工具只是不方便，选错了依赖层次则会让错误静默传播：任务全绿、告警全静、数字却是错的。执行归谁管（自管 Worker / 容器编排 / 托管算力）是在这条线之后才轮到筛选的第二层约束。

> 💡 **思考锚点**：用 §3.7 第 2 条自检你的关键链路——上游返回成功但只写了半个分区，你的下游会不会照常跑？若会，依赖判定就还停在任务返回码这一层；要下沉到「数据就绪」，§3.6 那一行列出的代价（每条关键链路补就绪检查、轮询占并发槽）你准备先补给哪几条链路？
