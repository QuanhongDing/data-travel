## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把「场景相关的结论」伪装成「绝对结论」。同一维度在不同规模下的权重是相反的：在「团队以数仓开发为主、每天几十条链路」的场景里，「易用性」压倒一切；同一套系统放到「日调度量万级、多租户共用一套资源池」的场景里，决定生死的是「定义能不能进版本库、状态机能不能横向扩展」，易用性排到最后。打分表没有位置表达这个反转——它给出的是一个与规模无关的名次，而选型恰恰是规模相关的。

第二，被打分的维度本身不可比。「性能 4 分 vs 5 分」里的「性能」，在调度系统里有三个互不相同的含义：调度循环能多快派发任务、任务能多快开始执行、全链路能多快产出。Airflow 的瓶颈通常不在任务执行速度，而在调度循环与元数据库写入；Argo 的任务执行速度取决于 K8s 与镜像拉取，而它自己要为每个任务付一次 Pod 生命周期；托管方案的「性能」还包含平台配额。把三个含义压成一个分数，等于把机制解释删掉了——而机制才是能迁移到你自己场景里的东西。

第三，打分表跳过了成本结构。调度系统的成本不是一个数，而是一条函数：自建开源调度器有常驻控制面成本（与**峰值并发**相关，几乎不随任务总量增长）；K8s 原生方案按 Pod 时长计费（随**任务数 × 时长**线性增长）；托管服务按调度量与算力计费（随规模线性上行，并把运维人力换成账单）。这三条曲线在同一张表里都可以是「5 分」，但当业务量翻倍时它们的行为完全不同——一条几乎不动，一条按比例涨，一条涨的同时省掉了人力。选型要选的是**曲线**，不是分数。

第四，也是最具体的缺口：决策树的分支只用「业务需求」这类描述性判据，节点上没有阈值，因此它无法回答「多少任务量以上就该换形态」。本章的树给每个判断节点配一条可推导的依据（见 7.5），阈值要么来自成本函数，要么来自公开的规格上限，要么来自团队结构。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 依赖判定依据 | 下游是在「上游任务成功」还是「数据就绪（分区 / 文件 / 事件）」上被触发 | 它决定上游失败会不会静默传播成下游数据错误；任务返回成功与数据正确是两件事 |
| 执行资源归谁管 | 调度器要不要自己扛弹性、隔离与配额 | 决定扩容时改的是调度器还是资源层；两者耦合后扩缩容要动控制面 |
| 编排定义的载体 | 定义是文件、元数据库记录，还是 K8s 对象 | 决定它能否进代码评审、能否 diff 与回滚，以及谁能改它 |
| 状态与故障边界 | 单次运行的状态放在哪、恢复路径是什么 | 调度器是全局控制面，它的可用性等于全链路可用性 |
| 产出时刻承诺 | 「几点必须产出」是系统对象，还是告警阈值 | 决定你能不能在上游迟到之后、还来得及的时候知道要迟到 |
| 运维承接能力 | 有没有人维护元数据库、注册中心、镜像与集群 | 决定自建与托管的分界；没有人承接时「开源可控」只是纸面优势 |

> 这 6 条与 [§ 3 设计模式与范式](12-scheduler-section-3-sec3.md) 的约束表同源：那里用约束推导模式，这里用约束推导选型。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Apache Airflow | 通用任务级编排 | DAG 是调度器定期解析的 Python 文件，状态写在自己的元数据库 | 数据工程团队 | Apache-2.0，自建；另有多个托管服务 |
| Apache DolphinScheduler | UI 优先的声明式编排 | 工作流是元数据库里的一份定义数据（任务列表 + 关系列表 + 调度配置） | 数仓 / SQL 开发为主的团队 | Apache-2.0，自建 |
| Argo Workflows | K8s 原生工作流 | 编排是 K8s CRD，每个任务是一个 Pod，调度器只剩薄状态机 | 平台 / SRE 团队 | Apache-2.0（CNCF），自建 |
| 阿里云 DataWorks | 托管一站式 | 依赖、调度、算力与「基线」承诺都在平台内，按量计费 | 阿里云上的组织 | 商业云服务，不可自建 |
| Kubeflow Pipelines | ML 流水线 | 流水线编译成 K8s 上的工作流，制品与实验追踪是一等公民 | ML 平台团队 | Apache-2.0，自建 |
| Prefect | Python 原生编排 | 图在运行期长出来，不要求提交前全量注册 | 现代数据栈团队 | 开源核心 + 托管服务 |
| Dagster | 资产（Asset）编排 | 依赖画在数据资产与分区上，调度单位是资产而不是任务 | 现代数据栈团队 | 开源核心 + 托管服务 |

表中「许可」一列属【公开】信息，可按各项目官方仓库的 LICENSE 文件核验；「商业模式」一列中，DataWorks 为商业云服务，Prefect 与 Dagster 为开源核心加可选托管。

这些候选其实分四族，同族内部差异小、跨族差异大——**先分族再选，能省掉一半比较**：

1. **任务级调度器（Airflow、Prefect、Dagster）**：都以「任务 / 资产 + 依赖」为单位，状态在自己手里。族内差异只有两处：图在提交前成形还是运行期成形，依赖节点是任务还是资产。历史形态还有 Oozie、Azkaban、Luigi，它们与本族共享同一层事实，今天主要存在于存量系统里。
2. **声明式 UI 调度器（DolphinScheduler，以及 DataWorks 的依赖调度部分）**：定义是数据不是代码，维护者是数仓 / SQL 开发者，接入既有 SQL / Spark / Flink 任务的成本最低。
3. **K8s 控制器（Argo Workflows、Kubeflow Pipelines）**：调度与执行分层，调度器不管资源；KFP 的差异是它把制品与实验追踪加在同一条流水线上。
4. **通用工作流引擎（Camunda、Flowable）**：面向业务流程与人工审批节点，不是数据批次编排；混用会让分区、补数、幂等这些数据链路的语义无处安放。

还有一族经常被忽略、但在小规模下确实成立：**裸执行形态**（crontab + 脚本、K8s CronJob、云函数定时触发）。它没有依赖判定这一层，因此只在「单任务、任务之间没有先后关系」时成立；一旦出现跨任务依赖，团队通常会自己在脚本里写等待或 `sleep`，这时它就退化成 7.7 的第一个反模式。把它列出来是因为选型的第一步往往是**确认自己是否需要编排**，而不是直接比较调度器。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 编排定义的载体：文件 / 元数据库 / K8s 对象

**机制是什么**：DAG 定义落在哪里，决定了谁能改它、改完能不能评审与回滚、以及改动的代价落在哪个环节。

**它在各候选中的实现差异**：

| 方案 | 定义落在哪 | 改一次定义要做什么 |
| --- | --- | --- |
| Airflow | Python 文件（调度器扫描 dags 目录） | 提 PR → 评审 → 等调度器重新解析 / 重新部署 |
| DolphinScheduler | 元数据库里的 workflow-definition（任务列表 + 关系列表） | 在 UI 或 SDK 里改定义 → 上线新版本 |
| Argo Workflows | K8s 对象（Workflow / WorkflowTemplate CRD） | 改 YAML → `kubectl apply`（可放进 GitOps） |
| DataWorks | 平台内的可视化定义 | 在平台里改并发布 |
| Prefect / Dagster | Python 代码（Dagster 另有资产定义） | 与普通代码一样走提交与部署 |

```text
「改一次 DAG 定义」分别要付什么
  文件形态（Airflow / Prefect / Dagster）
      改代码 → 提交 → 评审 → 合并 → 重新解析 / 部署 → 生效
      付出的是流程成本；换回 diff、单测、一键回滚、责任可查
  元数据库形态（DolphinScheduler）
      在 UI 点改 → 保存 → 上线 → 生效
      付出的是"不可回溯"；换回非工程角色自助、变更不用排研发期
  K8s 对象形态（Argo）
      改 YAML → apply → 生效（可纳入 GitOps 流水线）
      付出的是"用声明式表达动态拓扑"；换回与集群同一套权限与工具
  ────────────────────────────────────────────────
  关键：三者不是"好不好用"的差别，而是"改动的成本落在流程上
        还是落在不可回溯上"的差别 —— 这一条决定了谁能改 DAG
```

**由此必然导出的性质**：因为 Airflow、Prefect、Dagster 的定义是文件，所以它可以被 diff、被评审、被单测、被回滚，代价是定义由调度进程解析——Airflow 的解析发生在调度循环里，DAG 顶层一旦写上重逻辑（连数据库、拉接口、import 重型库），被拖慢的不是那一个 DAG，而是所有人共用的调度周期。因为 DolphinScheduler 把定义降级成一份可读写的数据，所以非工程角色能独立交付一条链路，代价是定义进不了版本库的常规流程：没有 diff 就没有回滚点，改错了只能靠平台的操作记录回忆「刚才点过什么」。

**公开证据**：【公开】Airflow 官方 Best Practices 要求 DAG 文件顶层避免重型代码与 import（可按 Apache Airflow 官方文档当前版本核验）；【公开】DolphinScheduler 的工作流定义以 `taskDefinitionJson` + `taskRelationJson` 落在元数据库，其 `code` 与 `postTaskCode` 必须指向同一个雪花值（可按其官方文档核验，另见 [§ 3.2.2](12-scheduler-section-3-sec3.md)）；【公开】Argo Workflows 的 Workflow 是 K8s CRD，该项目属 CNCF，Argo 系列于 2022 年从 CNCF 毕业。

**失效条件**：当链路数量增长到「一次误改的影响面无法预估」时，UI 定义从「易用」反转为「不可治理」；反过来，当 DAG 的维护者不是工程师、且变更以每天数十次微调的形式发生时，代码定义从「可评审」反转为「交付要排队」。

#### 7.3.2 执行资源归谁管：常驻 Worker 池 / 每任务一个 Pod / 平台托管

**机制是什么**：调度器判定「该跑了」之后，谁提供算力、以什么单位分配、按什么计价。

**它在各候选中的实现差异**：

| 方案 | 执行单位 | 伸缩单位 | 弹性上限由谁决定 | 空闲时的成本 |
| --- | --- | --- | --- | --- |
| Airflow（Celery） | Executor 派发的 TaskInstance | Worker 进程 / 容器 | Worker 池大小与队列 | 池子仍常驻 |
| Airflow（KubernetesExecutor） | 一个 Pod / 任务 | Pod | 集群可调度容量 | 近零 |
| Argo Workflows | 一个 Pod | 直接向 K8s 要 Pod | 集群容量与配额 | 近零 |
| DolphinScheduler | Master 分派、Worker 执行 | Worker 分组 | Worker 组规模 + 关系库写入 | JVM 常驻 |
| DataWorks | 平台算力 | 平台规格 | 平台配额 | 按规格计费 |
| Prefect / Dagster | Worker / Agent + 运行环境 | Worker 池或 K8s Job | 同 Airflow 或集群 | 取决于形态 |

```text
同一个 5 分钟任务在三种形态下的生命周期
  Airflow + Celery
      调度判定 → 进队列排队 → Worker 取走 → 起子进程 → 执行 5 分钟 → 回写状态
      ↑ 多出一段"排队时间"，长短取决于池子忙不忙；池子空着也要付费
  Airflow + KubernetesExecutor
      调度判定 → 建 Pod → 拉镜像 → 执行 5 分钟 → 回收 Pod
      ↑ 多出 Pod 启动；空闲不花钱，但突发时受集群容量约束
  Argo Workflows
      依赖满足 → 建 Pod → 拉镜像 → 执行 5 分钟 → 回收 Pod
      ↑ 与上一行同；差别在调度器只剩"依赖是否满足"这一层薄状态机
  ────────────────────────────────────────────────
  关键：三种形态的固定开销来源不同（排队 / Pod 启动 / Pod 启动），
        但都不是任务本身的计算 —— 任务越短，固定开销占比越高
```

**由此必然导出的性质**：因为 Argo 没有常驻 Worker 池，所以空闲时几乎不花执行资源、突发时直接受集群容量约束，代价是每个任务都要走一次 Pod 生命周期（创建、拉镜像、启动、回收）——这笔开销与任务**时长**无关、与任务**数**成正比，因此大量秒级任务在 Argo 上不划算，应当把一批小任务合并进同一个 Pod 才成立。因为 Airflow 的 Celery 形态靠常驻 Worker 消费队列，所以吞吐上限由池子大小决定，且「调度已判定该跑」与「任务真正开始」之间隔着排队时间；换成 KubernetesExecutor 能去掉排队与空转，代价是把成本换成每个任务一次 Pod 启动——**同一套调度器，换 Executor 就等于换了一条成本曲线**，这是打分表最看不出来的地方。

**公开证据**：【公开】Airflow 提供 Local / Celery / Kubernetes 等多种 Executor，各自的执行语义按官方文档不同（可按 Apache Airflow 官方文档当前版本核验）；【公开】Argo Workflows 以 Pod 为执行单位、调度层只保留薄状态机（见 [§ 3.2.4](12-scheduler-section-3-sec3.md)）。

**失效条件**：当平均任务时长与 Pod 启动开销处于同一量级（秒级）时，容器化带来的隔离与弹性被固定开销吃掉；当日调度量到上万量级【经验】、一轮调度循环跑不完解析与派发时，集中式调度从「统一控制」反转为「全局延迟」，因为所有 DAG 共用同一个调度周期——不是某个 DAG 慢了，而是所有人的触发时刻一起后移。

#### 7.3.3 依赖判定的依据：任务成功 / 数据就绪 / 产出时刻

**机制是什么**：下游到底等「上游任务返回成功」、等「数据（分区 / 文件 / 事件）就绪」，还是等「一个被持续预测的产出时刻」——这决定了错误的传播方式与迟到的暴露时点。

**它在各候选中的实现差异**：

| 方案 | 默认的依赖依据 | 要表达「数据到了才跑」需要什么 |
| --- | --- | --- |
| Airflow | 上游 TaskInstance 的状态 | Sensor（轮询）或 dataset / asset 触发 |
| DolphinScheduler | 上游任务实例状态 | 工作流依赖 / 等待节点 / 补数联动 |
| Argo Workflows | 上游任务（Pod）完成 | 额外的事件或传感器组件，或把等待写进模板 |
| DataWorks | 任务状态 + 基线承诺 | 平台的分区依赖与基线预警 |
| Dagster | 资产的物化记录 | 分区就绪即依赖本身；外部写入要补就绪契约 |
| Prefect | 运行期计算出的结果 | 由流程代码自行判断 |

```text
"按时间排" vs "按数据就绪"：上游迟到的两种下场
  按时间排（上游 2:00 → 下游 3:00）
      上游实际 3:20 才写完 → 下游 3:00 已开跑 → 读到 T-1 或半成品
      → 全绿、无告警 → 口径悄悄错，直到使用者发现
  按数据就绪（下游等分区就绪信号）
      上游 3:20 写完 → 信号到达 → 下游 3:20 起跑
      → 迟到 20 分钟，但数据是对的，且迟到可见
  ────────────────────────────────────────────────
  代价对比：前者省掉就绪信号的建设与维护，把错误推迟到使用者；
            后者要维护信号本身，还要处理"信号永不到达"的超时与告警
```

**由此必然导出的性质**：因为 Airflow 与 DolphinScheduler 的依赖边是**任务实例之间**的边，所以「上游产出物是否齐全」不是它们的依赖依据，必须额外用 Sensor、工作流依赖或数据集触发表达——这解释了为什么跨团队「数据到了就触发」在这类调度器里通常表现为轮询，而轮询要么在等待期占住并发槽（poke 模式），要么靠反复起停释放（reschedule 模式），两者都是在延迟与资源之间二选一【经验】。因为 Dagster 把依赖画在资产与分区上，所以「哪些分区没算、该重算哪一段」可以由调度器直接推出，代价是这张资产图必须显式维护、存量 SQL 与脚本要先改造。因为 DataWorks 多了一层「基线」，所以它能回答的不只是「任务跑完了吗」，还有「能不能按时到」——由承诺时刻反推最晚开始时刻，迟到在还来得及的时候暴露；代价是这条承诺只有在算力可被平台统一调配时才兑现得了。

**公开证据**：【公开】Airflow 2.4（2022 年）起引入 dataset，把数据更新变成一等触发条件，2.x 同时为 Sensor 提供 reschedule 模式以减少等待期对 worker slot 的占用（以官方 Release Notes 为准）；【公开】DataWorks 以基线管理产出承诺、由承诺时刻倒推预警（[阿里 DataWorks 公开材料, 2014-2024]，另见 [§ 3.2.3](12-scheduler-section-3-sec3.md)）。

**失效条件**：当上游产出时刻不稳定（延迟数小时）时，「按时间排」的链路会持续读到半成品数据；反之，当上游是外部系统、根本产生不了就绪信号时，资产依赖会退化成一张过期地图——调度器只知道自己编排过的那部分物化记录，别的写入它看不见。

#### 7.3.4 状态与故障边界：自持元数据库 / K8s 对象 / 平台

**机制是什么**：单次运行的状态存在哪，决定了故障时的恢复路径、可查询的历史深度，以及规模上限。

**它在各候选中的实现差异**：

- **Airflow**：状态在自己的元数据库（TaskInstance 状态行）；调度器可重启并从库中恢复进度，历史可按 dag 与时间范围查询。
- **DolphinScheduler**：状态在关系库，注册中心负责选主与分派；有状态组件比 Airflow 多一个。
- **Argo Workflows**：状态在 Workflow 对象的 status 里，也就是在 etcd；观测手段就是 `kubectl`。
- **DataWorks**：状态在平台内，用户不接触存储，可观测的是平台给出的视图。
- **Kubeflow Pipelines**：流水线运行记录 + 制品元数据存储，另有实验追踪。
- **Prefect / Dagster**：状态在服务端数据库（自托管或托管），Dagster 另有资产与分区的物化记录。

**由此必然导出的性质**：因为 Argo 把工作流状态放在一个 K8s 对象里，所以运维与观测意味着和集群同一套权限与工具（不必再学一套 API），代价是这个对象受 API Server / etcd 的对象大小限制约束——单工作流节点越多、每个节点写入的状态越大，越可能撞上限，这正是「超宽工作流要拆分」的机制原因（推导见 7.5）。因为 Airflow 把每个 TaskInstance 的状态写进关系库，所以历史与重跑能力很强（可审计、可按范围重跑），代价是元数据库随「DAG 数 × 时间」线性膨胀：清理历史、元数据库独立部署、控制 XCom 体积成了常驻工作，而不是一次性的上线动作。

**公开证据**：【公开】etcd 的 `--max-request-bytes` 默认值为 1.5 MiB（etcd 官方配置文档，可自行核验）；【公开】Airflow 元数据库的增长与历史清理是官方文档与运维实践中的明确议题（可按 Apache Airflow 官方文档当前版本核验）。

**失效条件**：当调度器是全局唯一控制面且不能横向扩展时，它的可用性等于全链路可用性；而「重启后状态不确定」会把事故从「延迟」升级为「重复写」——所以任务幂等是这套架构的前置条件，不是优化项。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 控制面常驻成本(峰值并发) + f(任务数 × 时长) + g(元数据与历史保留) + h(运维人力)
```

| 方案 | 主导项 | 隐性成本 | 成本随什么增长 |
| --- | --- | --- | --- |
| Airflow（自建） | 常驻控制面：元数据库、队列、调度器、Web、Worker 池 | 元数据库膨胀、DAG 解析开销、为峰值预留的空转 Worker | 峰值并发与运维人力；**几乎不随任务总量增长** |
| DolphinScheduler（自建） | 常驻 Master / Worker（JVM）+ 注册中心 + 关系库 | 有状态组件多：HA 与升级要停或滚动、JVM 调优 | 峰值并发与组件数 |
| Argo Workflows | Σ(Pod 规格 × 时长) | 每任务一次 Pod 生命周期；集群与 etcd 运维 | **任务数 × 时长**，线性 |
| DataWorks | 平台按调度量与算力计费 | 迁移不可逆（DAG 与调度语义锁在平台） | 任务量与算力规格，线性上行【经验】 |
| Prefect / Dagster | 常驻 Worker / Agent + 代码托管 | 生态集成要自写；Worker 空转同 Airflow | 峰值并发 |

```text
两条成本曲线什么时候交叉（决定自建还是按执行计费）
  vCPU·小时/月
      ▲
      │                      按执行计费：随任务数 × 时长线性上行
      │                    ╱
7,300 │──────────────────●──────────────── 自建常驻：与任务总量几乎无关，
      │                ╱ │                   随峰值并发呈台阶式上升
      │              ╱   └─ 交叉点：执行量 ≈ 常驻量（约 7,000 vCPU·小时/月）
      │            ╱
      └──────────────────────────────────────► 任务量
  低于交叉点：自建的机时多半在空转；高于交叉点：常驻被摊薄，
  选型的主要变量从"空转"转为"峰值并发与运维人力"
```

**一个【推算】示例**（前提写全，读者可换成自己的数）：设 2000 个日任务、平均 5 分钟、每任务 2 vCPU。

- 月执行量 = 2000 × 5 ÷ 60 × 30 天 × 2 vCPU = **10,000 vCPU·小时/月**。按云上通用型按需折算的 **$0.03–0.05 / vCPU·小时**量级假设，执行成本量级为 **$300–500 / 月**。
- 自建 Airflow 的最小可用控制面约 5 类组件（元数据库、队列、调度器、Web、Worker 池），按每类 2 vCPU 量级、常驻 730 小时/月估算 ≈ **7,300 vCPU·小时/月**，即同比**数百美元 / 月**的机器成本——但其中大部分机时并不在执行任务。
- 于是分界线落在「执行量与常驻量相当」的位置：执行量低于约 **7,000 vCPU·小时/月** 时，自建的常驻成本占总成本一半以上（空转）；执行量到 **5 万 vCPU·小时/月** 时，常驻占比降到 13% 量级以下（7,300 ÷ (7,300 + 50,000)），此时选型的主要变量从「空转」转变为「峰值并发与运维人力」。

**怎么判断你的主导项**：把过去 30 天的运行记录按「任务数 × 平均时长 × 单任务规格」折成 vCPU·小时（这就是 f 项），再把现有控制面组件的规格 × 730 小时折成常驻量，两者一比就知道自己站在分界线哪一侧。这个换算不需要新工具，只需要调度器已经存下的历史数据。

【经验】托管服务把上表里的**运维人力**换成了账单：省掉的不是机器钱，而是「有人管元数据库清理、注册中心、版本升级与事故演练」这件事；反过来，托管成本随规模线性上行，而自建的常驻成本近乎固定，规模越大差距越明显。**所以自建与托管的分界，本质是「月执行量能不能把常驻成本摊薄」与「有没有人承接运维」两个条件的合取**——只满足前者的团队，通常会在两个季度内把省下的钱以事故的形式还回去。

### 7.5 决策树（每个分支都要有阈值依据）

```
你的执行载体现在是什么？
├── 已经是 K8s，任务制品已经是镜像
│   ├── 平均任务时长 < 1 分钟 → 合并执行（批量打包进一个 Pod），或回到常驻 Worker 池的调度器
│   ├── 单工作流任务数 ≥ 1,000 → 先拆分工作流，再谈选型
│   ├── 是 ML 训练 / 评估、要按制品与实验对比 → Kubeflow Pipelines
│   └── 其余（任务分钟级、容器已就绪） → Argo Workflows
├── 自建集群（YARN / 物理机 + 关系库），团队以数据工程为主
│   ├── 只是单任务、任务之间没有先后关系 → 裸执行形态（cron / CronJob）就够，先别上调度器
│   ├── DAG 维护者是工程师、定义要进代码评审 → Airflow
│   ├── 拓扑在运行期才确定（按结果分支、按数据扇出） → Prefect
│   ├── 核心问题是资产新鲜度与重算范围 → Dagster
│   └── 维护者是数仓 / SQL 开发、要可视化自助 → DolphinScheduler
└── 主要数据与算力都在一家云上
    ├── 「几点必须产出」是可考核的承诺 → DataWorks（基线）
    ├── 月执行量 ≥ 约 7,000 vCPU·小时 且有人能承接运维 → 自建开源方案
    └── 月执行量低于该值，或没有平台运维人力 → DataWorks（托管）
```

**阈值依据**（与树上的判断节点一一对应）：

- **平均任务时长 1 分钟**：来自 7.3.2 的机制——Pod 生命周期（调度、拉镜像、启动、回收）是与任务无关的固定开销，量级在秒到十秒【经验】；当任务时长与固定开销同量级时，容器化换来的隔离与弹性被开销吃掉。同一判据见 [§ 3.3](12-scheduler-section-3-sec3.md) 的「大量秒级短任务」一行。
- **单工作流任务数 1,000**：【推算】以 etcd 默认 `--max-request-bytes` = 1.5 MiB（【公开】，etcd 官方配置文档）为前提，一个工作流节点的状态记录按 1 KB 量级估算：1.5 MiB ÷ 1 KB ≈ 1,500 个节点为理论上限；工程上取 1,000 作安全线，给状态膨胀与并发更新留余量。
- **是否有 ML 制品 / 实验对比需求**：依据 7.2 的分族与 [§ 3.2.6](12-scheduler-section-3-sec3.md)——KFP 的机制优势（制品与实验追踪）只在有复现与对比需求时才有收益，纯 ETL 用它等于每一步多付一层容器与制品登记。
- **任务之间有没有先后关系**：依据 7.2 末段——裸执行形态没有依赖判定这一层，跨任务依赖一旦出现，只能靠脚本内的等待或 `sleep` 冒充，依赖就退化成时间猜测。
- **DAG 维护者是不是工程师**：依据 7.3.1 的定义载体机制——定义是文件则可评审与回滚，定义是元数据库数据则非工程角色可自助交付；两者互斥，因为代码定义不可能让非工程师改完还在版本库里留下评审记录。
- **拓扑是否在运行期才确定**：依据 7.3.3 的依赖判定机制与 [§ 3.2.5](12-scheduler-section-3-sec3.md)——静态 DAG 要求提交前能算出这次要跑多少任务，而按数据扇出、按结果分支的拓扑提交前算不出来；Prefect 的图在运行期长出来，代价是容量规划与影响面只能事后做。
- **核心问题是资产新鲜度还是任务成败**：依据 7.3.3——依赖节点是任务时，「表新不新鲜」要人工翻译成任务状态；依赖节点是资产时，可由分区物化记录直接回答。人工翻译会分裂成两套真相。
- **是否有可考核的产出时刻承诺**：依据 [§ 3.1](12-scheduler-section-3-sec3.md) 的约束表——基线在超时**之前**由进度倒推预测并预警，SLA 告警在超时**之后**才响；只有前者能在还来得及的时候暴露迟到。
- **月执行量约 7,000 vCPU·小时**：来自 7.4 的【推算】（自建常驻 ≈ 7,300 vCPU·小时/月）；低于此值时自建机时一半以上在空转，按执行计费或托管形态更省。
- **「有人能承接运维」**：依据 7.1 的第 6 条判据与 7.4 的隐性成本项——元数据库清理、版本升级、注册中心与 HA 演练是持续性工作；没有承接人时，自建方案会在几个季度内退化为事故源，省下的钱以事故形式还回去。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单团队 100+ 日批任务、Python 团队、定义要评审 | Airflow | Prefect | 不选 UI 定义：改 DAG 要走平台操作，没有 diff 与回滚点 |
| 数仓 / SQL 开发自助交付、链路每天微调 | DolphinScheduler | DataWorks | 不选 Airflow：非工程角色交付一条链路要排平台团队的队 |
| 执行载体已是 K8s、任务已容器化、任务在分钟级 | Argo Workflows | Kubeflow Pipelines | 不选自管 Worker：资源隔离与配额要重造一遍 |
| ML 训练与评估流水线、要按制品与实验对比 | Kubeflow Pipelines | Argo Workflows | 不选通用 ETL 调度：任务成功不代表指标达标 |
| 核心问题是资产新鲜度与重算范围 | Dagster | Airflow + 资产视图 | 不选任务级调度：任务图与数据图要人工翻译，会分成两套真相 |
| 阿里云上、无平台运维人力、有产出时刻承诺 | DataWorks | 自建开源调度器 | 不选自建：常驻控制面与值班成本要先落地 |
| 日调度量万级、多租户共用一套资源 | 任务级调度 + 独立资源层 + 队列隔离与抢占 | Argo Workflows | 不选单队列共享：一次补数会拖慢全链路，故障半径等于整个资源池 |
| 单任务、无跨任务依赖 | 裸执行形态（cron / CronJob） | 任一调度器 | 不选调度器：为不存在的依赖付一整套控制面成本 |

**常见组合（职责边界与运维代价）**：

1. **Airflow + K8s**：Airflow 负责 DAG、依赖、重试、SLA；K8s 负责资源分配与隔离（Pod Operator 形态）。边界是「编排逻辑归调度器、资源规格归集群」。代价是两套升级面（调度器与集群），且每个任务多付一次容器启动。适合「编排逻辑复杂、执行规格不一」的团队。
2. **Argo + Spark/Flink Operator**：Argo 只做流程与依赖，Operator 把「提交一个 Spark / Flink 应用」翻译成 Job 与 Service。代价是 Operator 版本与应用引擎版本耦合——升级引擎前要先验 Operator 兼容性。适合执行引擎已统一在 K8s 的数据栈。
3. **DolphinScheduler + Airflow**：DolphinScheduler 做可视化监控、补数与跨系统触发的入口，Airflow 承载复杂 Python DAG。代价是两套元数据——谁是真源要约定清楚，跨系统依赖只能靠「一张表 + Sensor」桥接，这往往是最脆弱的一环。只在迁移期或组织确实分裂时使用。
4. **DataWorks + 自建 Argo（混合云）**：平台内的数仓任务与基线承诺留在 DataWorks，K8s / 多云与 AI 任务用 Argo。代价是双轨的依赖、时区与告警口径要对齐，且缺一条统一的依赖图；适合「计算在云上、AI 在自有集群」的组织。

组合的运维代价可以归到一句：**每增加一套调度器，就多一份「谁是真源」的约定与一次跨系统的依赖桥接**。桥接点（通常是「一张表 + 一个 Sensor」）会成为新的事故高发区，因此组合应当有明确的退出条件，而不是永久并存。

### 7.7 选错的代价与迁移成本

**反模式：把调度器当成执行引擎** —— 症状：DAG 顶层连数据库、拉接口、import 重型库，或在调度进程里直接跑数据转换 → 后果：DAG 解析被拖慢，所有人的触发时刻一起后移；一个坏 DAG 会让整个调度循环失败（解析是共享的），故障半径等于全公司 → 正确做法：DAG 只描述编排，执行交给 Operator 或外部引擎，顶层代码保持轻量。

**反模式：用时间表代替依赖** —— 症状：把「上游 2:00 跑完」硬编码成「下游 3:00 启动」，或在脚本里写 `sleep` 等上游 → 后果：上游延迟时下游照样开跑，读到半成品且不报错——数据错比任务失败更难发现，因为任务全绿 → 正确做法：依赖表达成任务依赖或数据就绪信号（分区 / 文件 / 事件），跨系统用 Sensor 或数据集触发显式表达。

**反模式：把补数当成重跑** —— 症状：补历史数据时直接重跑整条链路，且这些任务与日常产出共用同一个队列 → 后果：任务不幂等时重复写（数据翻倍），共用队列时一次补数拖慢当日全部产出；两种后果都要到事故时才被发现 → 正确做法：补数以分区为单位、先验证幂等再放量，并把补数放到独立队列 / 配额里，与日常产出隔离。

**反模式：自建调度器却没有值班能力** —— 症状：开源调度器装起来了，但没有人负责元数据库清理、HA、版本升级与注册中心运维 → 后果：几个季度后元数据库膨胀、升级卡住、调度器仍是单点；调度器故障等于全部数据产出停止，恢复靠人肉 → 正确做法：先按 7.4 算常驻成本与人力，没有承接能力就选托管；有承接能力就把「元数据库清理、版本升级、HA 演练」写成常驻职责。

**换成另一个要动什么**：

| 迁移方向 | 数据迁移 | 定义改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| Airflow → Argo Workflows | 无 | 全部 DAG 改写成 CRD YAML，Operator 换成容器 | 执行层从 Worker 池改为集群 | YAML 与 K8s 排障 | 大（定义全量重写） |
| Airflow → DolphinScheduler | 无 | DAG 改为 UI / SDK 定义，依赖语义基本可映射 | 增加注册中心与 JVM 组件 | UI 与平台概念 | 中 |
| DolphinScheduler → Airflow | 无 | 定义导出后重写为 Python 文件 | 引入队列与元数据库 | Python 与代码评审流程 | 中–大 |
| 自建开源 → DataWorks | 计算与数据也要一起搬 | 定义与依赖语义重写 | 取消自建，接受平台规格 | 平台概念与基线 | 大，且**单向** |
| 任务级 → 资产级（Dagster 类） | 无 | 任务图翻译成资产图，分区要重新定义 | 补幂等与分区重算 | 资产建模 | 大（要先做资产治理） |

- 上表量级为【经验】：迁移的主要成本不是工具替换，而是「定义要重写一遍」与「重跑 / 补数的幂等性要重新验证」；历史运行记录一般不迁移，因此事故复盘的可追溯性会断档一段时间——这一点要在迁移计划里显式写成风险项。
- 一条不可逆的边界：**托管方案是单向门**——从自建迁到托管要连计算与数据一起搬，从托管迁回自建没有任何导出路径。做「先上托管、以后再自建」的计划时，这条要写进决策记录。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| Python 团队、定义要评审、任务级依赖复杂 | Airflow | 定义是文件、状态在库：可评审可回滚，调度器可重启恢复；代价是解析开销与元数据库膨胀 |
| 执行载体已是 K8s、任务在分钟级 | Argo Workflows | 调度只留薄状态机，隔离与配额交给 K8s；代价是每任务一次 Pod 生命周期 |
| 大量秒级短任务 | 常驻 Worker 池的调度器 + 打包执行 | Pod 生命周期开销与任务数成正比、与任务时长无关，短任务摊不掉它 |
| 数仓自助交付、可视化优先 | DolphinScheduler | 定义降级成数据，非工程师能独立交付；代价是没有 diff 与回滚点 |
| 有可考核的产出时刻承诺 | 平台基线（DataWorks）或自建补齐「事前预测」 | 从承诺时刻倒推，迟到在还来得及的时候暴露；SLA 告警在超时后才响 |
| ML 流水线、要复现与对比 | Kubeflow Pipelines | 制品与实验追踪是一等公民，换参数重跑可比；代价是每步都要容器与制品登记 |
| 日调度量万级、多租户 | 任务级调度 + 独立资源层 + 隔离与抢占 | 控制面与资源面独立扩缩，故障半径才收得窄 |
| 单任务、无依赖 | 裸执行形态 | 没有依赖可判，一整套控制面是纯成本 |

> 本节小结：调度系统选型里真正起决定作用的那条差异只有一条——**依赖判定的依据是什么**（上游任务成功、数据就绪，还是产出时刻承诺）。它决定了错误会不会静默传播、扩容时改的是调度器还是资源层、以及「会不会迟到」是事前可知还是事后才发现；定义载体、执行单位与成本结构都在这条差异之下派生。
>
