## 5. 前沿演进（AI 时代）

> 原 § 5 共 96 行、为方向清单（5 条演进方向 + 3 条 RAG / GraphRAG + 4 条学术条目 + 5 条工业条目 + 5 条趋势），缺少机制与成熟度判断，重写为 ~300 行前沿评估。

### 5.1 先分清三类「前沿」

本节要解的第一个问题不是「AI 能往 Kafka 里塞什么」，而是**时间刻度**。把"兼容 Kafka 协议、把数据主体放进对象存储"（这一侧有正式的产品条目与公开仓库）与"由模型预测流量并自动调优"（这一侧公开材料以厂商演示为主）并列写成"演进方向"，读者据此排路线图时无法判断哪一条今天能进架构。判断能不能落地，本主题的约束写在主文件 [§1.1](04-streaming-store.md)：流式存储的核心模型是**「日志（Log）+ offset」**——顺序写入、可重放、可长期保留；写入侧的确认语义（交易上的 ACK、副本与 ISR 三件套）是主文件 [§2.1](04-streaming-store.md) 的条目定义与 [§2.2](04-streaming-store.md) 的副本一致性模型。这条语义没有被 AI 改动，由它推出的三条物理前提也没有：**分区内有序、offset 单调、写入要等够副本**。本节要判的不是"AI 能不能接进来"，而是新增的写入者与消费者会不会撞上这三条前提——比如把会话事件按错误的分区键打散，就会让"可回放"这件事在语义上失效。

第二条要提前立住的判据来自主文件 [§1.2](04-streaming-store.md) 的痛点清单：流式存储的真实代价从来不是"能不能存"，而是**保留期、成本与多消费者之间的取舍**。本节对每个 AI 方向都会追问同一件事：它让保留期变长了、变短了，还是让"该保留多久"这个问题第一次有了硬约束。

本节用 L1 / L2 / L3 三级区分，判据必须是**可核验**的三条：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条各挡住一类误判：①挡住"把路线图当既成事实"（原清单里"Kafka 4.0 路线图（KIP 编号）"这一条本身就是路线），②挡住"把厂商自述当行业现状"（本主题这一条最贵：**成本与延迟的对照数字几乎都出自这些产品自己的博客**），③挡住"把演示当工程"。**三条全中才算 L1**，可以排进路线图；只满足一部分、或只有厂商自有案例的算 **L2**，可以做 PoC、不要作为核心依赖；只有路线图 / 论文 / 演示的算 **L3**，记录即可、不要在架构里预留假设。

**判据声明（本节不对 L1 判据做任何修正）**：上文那三级与三条判据沿用到底，不替换、不放宽。本主题最诱人放宽的地方正是第②条：这个领域的产品几乎都提供"兼容 Kafka 协议"的公开仓库、都有"对象存储原生"的架构文档，于是很容易把"有公开的机制性材料"当成"有第三方生产案例"——但公开仓库与架构文档出自**产品提供方本身**，按判据读就是"厂商自有案例"，正是 L2 的定义；把同一条判据换成"有公开的工程记录""可被第三方复核"这类措辞，读者按新措辞照样核验不了。本节的做法是：**够不到第②条的一律降为 L2，并在判据格里写明它卡在哪一条**。结果是**下表没有任何一行达到 L1**；其中"**没有任何一条 AI 能力方向到 L1**"是本节最重要的一句话。**L2 不等于"不好"，只等于"公开证据到不了 L1"**——真正需要警惕的是把 L2 当 L1 写进选型结论。

写这一节时最容易混的四件事，先在这里分开——它们会在下面反复出现：

- **产品名 vs 能力名**："无服务器 Kafka""对象存储原生流存储"是**形态名**，不是某个产品的专属能力。判定方法只有三条：**写路径是否也落在对象存储（还是先落本地盘再上传）**、**元数据存在哪**、**最小可部署形态是什么**。三条问清楚，任何产品都能被放进同一个坐标系里比较。
- **已发布版本 vs 路线图**：判断某版本是否真的具备某能力，只看**该版本的 release note 或 KIP 页面**。本主题有一处现成的例子：「Kafka 4.0 路线图（含 KIP 编号）」是**路线**，不是既成事实；而"KRaft 何时被标记为生产可用、ZooKeeper 何时被移除"，都以官方 release note 与对应 KIP 为准，不写死年份。
- **项目归属与血脉**：把 Apache Fluss 记成「前 Flink Table Store 衍生」是**不成立的**——Flink Table Store 更名后成为 Apache Paimon，与 Fluss 不是同一条血脉；**判定方法**：分别查两个项目的官方仓库、发布记录与孵化状态，归属问题只看这些一手材料。
- **单集群 vs 多集群**：流优先存储与流式数据库维护的是**常驻状态**（[§3.1](04-streaming-store-section-3-sec3.md) 的模式 7 那一族），它的容量上限由单集群决定；"扩到多集群"是另一套语义，不能拿单集群的延迟与容量数字去推算跨集群的结论。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**——改变了成本结构、改变了接口边界、把人工判断换成统计判断，还是只换了个前端？本主题的答案很集中：**没有一条改变了日志的语义**。真正落在机制上的只有三条：**一条改变了"为什么要记"**（Agent 的推理过程必须被记录下来，理由不是吞吐而是可复现——存储因此多了一类"为以后能重看一遍"而写的数据），**一条改变了存储的物理位置与计费单位**（把主体搬到对象存储后，单位成本从"预置容量"变成"字节 + 请求次数"，延迟由对象存储的往返决定），**一条把物化时机从"按周期"改成"按事件"**（只为发生变更的对象重算，新鲜度第一次与全量重算成本解耦）。另有一条只换了前端（token 级流式输出是 HTTP 传输层的问题），其余全部**与 AI 没有因果关系**。

**这三级的排法直接决定路线图的顺序**：

- **先做的是表里的非 AI 行**：把保留期与冷热分层算清楚（它同时决定成本与"可回放窗口"）、把分区键与 schema 兼容性策略定下来、把确定性的自动均衡开起来。它们排在所有 AI 方向之前，因为**前三行 AI 方向（事件流、RAG 索引、流式特征）全部建立在"保留多久、按键怎么分、写完能不能读回来"这三件事上**。

- **L3 不排进排期**：token 流进队列、模型决定扩缩容、流式 GraphRAG 都属于"等信号"。它们的共同前提（有多个消费者需要回放 / 动作可回滚 / 生成物可静态校验）比选哪家产品重要得多。
- **回填机制**：每次集群大版本升级或某项目发布新的成本 / 延迟对照材料时回填一次级别；某个 L2 若一年内仍拿不到自己组织里的实测数字，降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，在评审时应被直接打回——本主题里每一条"记下来"，都对应一处新的留存成本与一处新的合规义务。

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 Agent 事件流 | 记录的动机从"给下游消费"变成"为了以后能重看一遍" | **改变了接口边界**（存储多了一类写入目的与一类保留理由） |
| §5.2.2 Serverless / 对象存储原生 | 存储的物理位置从本地盘搬到对象存储，计费单位随之改变 | **改变了成本结构**（从预置容量变成字节 + 请求次数） |
| §5.2.3 流式 RAG 索引与流式特征 | 物化时机从"按周期"变成"按事件" | **改变了成本结构**（新鲜度与全量重算成本解耦） |
| §5.2.4 同组七条 | 其中五条的收益来自既有能力、运维策略或传输层，没有一条来自模型；另两条只有演示，没有可验收的动作定义 | **与 AI 无因果关系 / 只换了前端 / 只有演示** |

读法建议：如果时间只够读一节，读 §5.2.1——它是本主题里唯一一条"AI 改变了这类数据存在的理由"的方向，也是唯一一条会反过来改写你的保留策略的方向；§5.2.2 的收益要用**你自己的消息大小分布**验证之后才算收益；§5.2.3 的收益要等你把删除传播与同源问题解决之后才兑现。

#### 5.2.1 Agent 事件流：日志第一次为了"以后能重看一遍"而写

- **旧做法与它的卡点**：Agent 的调试与追责靠应用日志与 SDK 自带的 trace。卡点是**复现的提供者换了**：传统链路里同一输入必得同一输出，所以复现只需要保存输入；LLM 的输出不是输入的确定性函数，要复现的不是"输入"，而是**"当时实际的请求与响应，含每一次工具调用与返回值"**。日志文件留不下这个——它不保证顺序可回放，也不与下游写入对齐（[§4.2](04-streaming-store-section-4-sec4.md) 的手动提交与幂等消费讲的正是"消费位置要能被明确记住"）。
- **AI 改变了什么机制**：**记录的动机变了**。流式存储过去是为"给下游消费"而写：消费完即可删，保留期是个成本参数。Agent 事件流的写入目的是**"以后能重看一遍"**，于是保留期从成本参数变成了**功能参数**——它决定的不是省钱，而是"事故复盘能回溯多久"。这是本主题里唯一一处 AI 真正改动了存储侧语义之外的东西：**它改的是保留策略的判据来源**。
- **由此得到的**：**因为可复现性被下沉到存储层，所以"它当时看到了什么"第一次可以逐条回放**——不依赖 SDK、不依赖应用侧写日志的自觉，而是依赖日志本身的可重放性（顺序 + offset + 保留）。[§3.1](04-streaming-store-section-3-sec3.md) 的模式 8（事件溯源）由此从"审计场景的可选模式"变成"AI 链路的基础设施"，但它用的完全是既有机制，没有新增任何接口。
- **由此付出的**：**其一，写进去的内容可能含个人信息且会长期留存**——prompt 与工具返回值经常夹带用户数据，保留期一拉长，删除请求就来了，而**只追加日志里"删掉某个用户的数据"要靠墓碑 + 索引重建**，成本远高于关系库的一行删除；这类问题先定"记什么"比先选存储重要（合规面见 [11-cross-cutting/07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)）。**其二，消息条数与 token 数同阶，而消息比 token 贵**——每条消息都有固定开销（序列化、索引、网络往返），token 级记录会把一个按字节计的问题变成一个按条数计的问题，这一点在 §5.2.2 会再次出现。**其三，"可重放"不等于"可复现"**——重放给出的是"当时的上下文"，外部模型仍可能给出不同答案；所以事件流是**审计证据**，不是回归测试；要做回归测试必须另建一套"固定模型版本 + 固定输入 + 断言输出"的东西。**其四，分区键成了新难点**——会话要保序就得用会话 ID 做 key，而单个热点会话会让某一个分区倾斜，[§2.2](04-streaming-store.md) 的"按业务实体选 key"在这里要补一句：**选 key 时同时要问"这个实体的流量分布会不会长期不均"**。

```text
        同一条链路，两种"记什么"（差别在记录粒度与保留期怎么定）
           Agent 运行 ──► 事件流 ──► 长期保留（供回放与审计）
          ────────────────────────────────────────────────
          ✗ 只记最终结果 + 状态码
            能回答"失败了"，回答不了"它当时看到了什么"
            → 复盘只能靠猜，且每次都靠猜
          ✓ 记"一次决策所需的上下文"
            模型请求摘要 / 工具调用与返回 / 关键中间状态 / 模型版本
            保留期按"最长复盘窗口"定，而不是按"下游消费完就删"
          ────────────────────────────────────────────────
          判定方法：取一次失败会话，只用手上的事件回答三个问题——
                   调了哪些工具、每次返回什么、在哪一步开始偏离
```

- **证据与来源**：【公开】日志型存储的持久化、按 offset 重放、按时间 / 容量保留、以及事务性与幂等写入，都是其官方文档中的正式条目，接口多年未变（核验入口见 §5.4）；原清单点名的"对象存储原生的流存储让 Agent 事件流更便宜"属**厂商自述**，按 §5.1 判据第②条读是"厂商自有案例"。**【本节未能核到】Agent 事件流进入生产并披露"回放能覆盖多少比例的失败会话"或"重放一致性"的第三方材料**——公开材料多为框架与可观测类产品。
- **成熟度**：**L2**。判据：①③成立（持久化 / 重放 / 保留是正式条目、接口稳定），②核不到 → 可以做 PoC；**前置条件是先定"记什么"（粒度）与"记多久"（保留期）**，这两件不定，事件流只是把日志换了个地方存。
- **判定方法**：拿一次真实失败会话，只用手上的事件记录还原它的全过程；能给出一份"哪一步开始偏离"的时间线，说明粒度够了。**第二个动作**：数一次事件流里被写入的字段中，有几个是个人信息；答不上来就先别拉长保留期。
- **什么时候值得做**：Agent 已经进入面向用户的链路、且"它为什么这么答"会被追问时。收益是审计与复盘的能力，成本是一条要长期维护的写入链路。
- **什么时候不值得做**：把逐 token 的事件全量落盘——粒度应按"能否复现一次决策"来定，而不是按"能不能全记下来"；也不要在没有脱敏规则与保留期的情况下先把内容记下来"以后再说"。
- **一条与 §3 / §4 对齐的提醒**：本方向用的完全是既有机制，所以 [§3.3](04-streaming-store-section-3-sec3.md) 的反模式在这里一条不少——**Topic 过细**会让事件流变成一堆无人消费的分区（而它偏偏是为"以后再看"写的，所以更不容易被清理），**消费者未做幂等**会让回放本身产生重复动作，[§4.1](04-streaming-store-section-4-sec4.md) Step 4 的 schema 管理在这里从"推荐"变成"必需"：事件 schema 一旦演进失控，历史事件就再也拼不回一次完整的决策。

#### 5.2.2 Serverless / 对象存储原生流存储：成本从"预置容量"变成"字节 + 请求次数"

- **旧做法与它的卡点**：经典架构里 Broker 带本地盘，容量靠加盘与加节点；卡点是**扩容要搬数据**——扩分区意味着跨节点复制，而重建一个副本的时间与数据量成正比，容量规划因此必须提前做，且冷数据长期占着最贵的介质。主文件 [§2.3](04-streaming-store.md) 把这一组机制写得很清楚：顺序写、PageCache、以 1 GB 为单位的日志段；它们的共同前提是**数据在本地盘上**。
- **AI 改变了什么机制**：**与 AI 无关**，但它是本节所有 AI 方向的成本底座：把数据主体放到对象存储之后，Broker（或 agent）变成**无状态**的——扩缩容从"搬数据"变成"换实例"，冷数据的介质换成对象存储。**代价随之换了位置：计费单位从"容量"变成"容量 + 请求次数 + 出网流量"**。这一点对 AI 侧的小消息链路特别关键：**请求次数与消息条数成正比，与字节数无关**。
- **由此得到的**：**因为主体数据在对象存储上，所以"存多久"这件事第一次可以按对象存储的单价来算，而不是按本地 SSD 的单价来算**——保留期从"能不能负担"变成"愿不愿意为别的东西付费"（[05 冷热分层](../05-cold-hot-tiering/05-cold-hot-tiering.md) 讲的就是这件事）。这条推论对 §5.2.1 的事件流是直接收益：长保留第一次变得可负担。
- **由此付出的**：**其一，单位成本可能不降反升**——小消息高吞吐场景下，请求次数按消息条数走，而 Agent 事件与 token 级记录恰好是"多而小"的形态【经验，量级差异随云厂商定价与消息大小变化，用下面 §5.4 判据动作第 5 条复算】；**其二，延迟的物理来源变了**——本地盘是亚毫秒级，对象存储是往返级，冷读路径因此显著变长，所以几乎所有这类实现都保留了一层本地缓存或预取，**而"缓存命中率"从此成为这套架构最该监控的指标**；**其三，可用性依赖外部服务**——对象存储的可用性与配额直接决定链路可用性，故障排查会跨两个控制面；**其四，把数据放到对象存储并不自动满足合规**——数据在哪里、谁有权限、能否就地删除，仍然要按 [11-cross-cutting/07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md) 那一类要求逐条回答。

| 形态 | 数据主体位置 | 成本怎么算 | 扩容的代价 |
| --- | --- | --- | --- |
| 经典 Broker + 本地盘 | 本地盘（可配分层卸载冷段） | 容量 + 实例 | 跨节点复制，时间与数据量成正比 |
| Broker + 分层存储 | 冷段在对象存储，热段在本地 | 容量 + 分层后的对象存储单价 | 热段仍在本地，扩容仍要动盘 |
| 对象存储原生（无状态节点） | 对象存储（本地只做缓存 / 预写） | 字节 + 请求次数 + 出网流量 | 换实例，不搬数据 |

- **证据与来源**：【公开】对象存储原生的流式存储在 2024 年前后出现多个项目的正式发布与公开仓库（核验入口见 §5.4）；**判定方法**：查它的文档里**写路径是否也落在对象存储上**（还是先写本地预写日志再上传）、**元数据存在哪**、以及**它是否要求一个额外的元数据服务**。**【本节未能核到】第三方（非厂商）给出的、含消息大小分布与读写模式的成本 / 延迟对照材料**；原清单把它记为一次成本下降，本节**不引用任何具体倍数**，理由是这类数字高度依赖消息大小、请求单价与访问模式。
- **成熟度**：**L2**。判据：①③成立（兼容协议的正式产品条目、协议接口多年未变），②核不到（成本对照材料出自产品提供方）→ 可以小范围试用，不要作为核心链路的唯一依赖。
- **什么时候值得做**：容量规划长期跟不上（冷数据占比高、扩容窗口短）、且单条消息不算太小时。此时容量与实例解耦的收益立刻可见。
- **什么时候不值得做**：消息很小、条数极高、且对端到端延迟有硬要求时——先按 §5.4 判据动作第 5 条把三项成本分开算一遍，再决定；**不要因为"省容量"而换来一张按请求计费的账单**。
- **一个容易被忽略的推论**：这套架构把"扩容"从"搬数据"变成"换实例"之后，**分区重分配的代价也随之变小**，于是"分区数留余量"这条老经验开始松动——但只松动了一半：分区归属的变更仍会打掉本地缓存，冷读随之上升。所以真正该跟着变的不是"要不要留余量"，而是**把"冷读比例"提升为一等监控指标**（它同时出现在延迟与账单两处，见 §5.3 的接口表）。

#### 5.2.3 流式 RAG 索引与流式特征工程：把"按周期物化"改成"按事件物化"

- **旧做法与它的卡点**：索引与特征都由周期性批任务产出。卡点是**物化成本与总量成正比**——全量重建一次的成本随文档总量上升，所以缩短间隔的价格是线性的；对特征还有一条更硬的约束：**训练与推理必须用同一份变换逻辑**（[02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md) 把 Train-Serving Skew 列为首要问题，[§3.2.7](../10-stream-batch-unified/10-stream-batch-unified-section-3-sec3.md) 把"同一份 UDF"写成消除漂移的手段）。两条约束合起来，卡点很具体：**要么两侧各写一份（漂移），要么两侧共用一份但都跑批（不新鲜）**。
- **AI 改变了什么机制**：**把物化时机从"按周期"改成"按事件"**，只对发生变更的对象重算。机制上变的是**成本函数**（从总量驱动变成变化量驱动），不是"检索算法或特征算法变好了"。要特别说清一点：**AI 没有改变"两侧必须同源"这条约束**——流处理恰好是实现同源的手段之一（同一份逻辑跑流与批），这也是 [10-stream-batch-unified](../10-stream-batch-unified/10-stream-batch-unified.md) 那一章的价值所在；把流式特征写成"AI 让特征实时了"，会掩盖真正的问题在别处。
- **由此得到的**：**因为每次只为变更付费，所以"新鲜度"第一次与"全量重算成本"解耦**——实时特征与实时索引可以由同一份逻辑产出，训练-服务一致性从"靠事后对账"变成"靠结构保证"。这是本方向最实的收益，也是它值得与主文件 [§1.2](04-streaming-store.md) 的"实时计算"诉求放在一起看的理由。
- **由此付出的**：**其一，回填变难**——上线一个新特征要对历史样本重算，而事件流只保留了保留窗口内的历史（**保留期同时决定了可回填窗口**，这笔账与 §5.2.1 是同一笔）；**其二，时点正确性更难保证**——特征必须按事件时间对齐，而事件到达按处理时间，迟到事件会造成"用了当时还不该知道的信息"（[02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md) 的 Point-in-Time 正确性）；**其三，两套存储要一致**——在线库与离线表之间要么双写（一致性风险），要么由同一条流产出（可用性风险），没有第三种免费方案；**其四，版本要一起记**——特征口径版本、模型版本、索引版本三者不同步，线上回滚会退回到一个"口径已经变了"的过去。
- **证据与来源**：【公开】CDC 采集、流处理算子、向量写入与按元数据过滤、在线特征库的读写，各自都是其官方文档中的正式条目（核验入口见 §5.4）；原清单点名的组合（Confluent Cloud + Pinecone + LangChain 一类；向量库一侧是 Milvus / LanceDB / Pinecone，特征库一侧是 Feast / Tecton）出自这些组件各自的提供方，按判据读是**厂商自有整合**，即 L2。**【本节未能核到】"实时索引或实时特征带来多少质量提升"的第三方对照材料**——这类数字高度依赖评测集、切分策略与查询分布，本节不引用任何提升幅度。
- **成熟度**：**L2**。判据：①③成立（三段管道各自是正式条目、接口多年未变），②核不到 → 可以做 PoC，不要作为核心依赖。
- **判定方法**：抽 10 个已下架的文档，看它们还能不能被检索到（删除传播）；把离线重算与在线特征按同一批样本逐行比对，数不一致率（同源）；把最近一周的迟到事件比例数出来（时点正确性）。**三个数里任何一个答不出来，说明这条链路还没有可评估性。**
- **什么时候值得做**：变更量远小于总量、且"看到最新的东西"本身是业务要求（工单知识、风控规则、商品与价格）时。此时增量物化才比周期重建更省。
- **什么时候不值得做**：总量小、变更占比高（每天替换掉大半内容）时——两种方案总成本接近，而增量方案多出删除传播与版本一致性两件事要维护，是净增负担。
- **一条与 [§7.6](04-streaming-store-section-7-sec7.md) 的接口要说清**：特征与索引的写入端不是新东西，它就是 [§7.6](04-streaming-store-section-7-sec7.md) 的组合 1 与组合 2（流式存储 + 流计算 + 湖表）换了一个下游——从"写进表"变成"写进索引或在线库"。因此那边的取舍（驻留多久、由谁消费、失败谁负责）在这里一条不少，只是可回填窗口由**队列保留期**而不是由**表快照保留期**决定，这一点常被忽略。

#### 5.2.4 与 AI 无因果关系、只换了前端、或只有演示的七条

| 方向 | 旧做法与卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据 / 成熟度 |
| --- | --- | --- | --- | --- | --- |
| LLM 流式输出与流式网关（原方向 4） | 用户等待完整答复，首字延迟长；卡点是**交互体验**，不是吞吐 | **只换了前端**：token 级传输是 HTTP 层的流式（SSE / WebSocket 一类）问题，队列不参与其中 | 首字延迟由生成速度决定，与消息队列无关 | 若把 token 塞进队列，换来的是按条计费的写入与一堆无消费者的分区；**多个消费者 / 回放 / 审计**这三件才是队列真正能提供的东西 | 传输层是既有规范条目；"队列承载 token 流"无通行做法 → **L3** |
| AI 驱动的流式存储运维：确定性那一半（原方向 5 的一半） | 靠人盯磁盘、滞后与分区倾斜；卡点是**滞后与不可复现** | 把"人盯"换成**基于指标的确定性动作**（自动均衡、按滞后扩缩、分区重分配）；模型只贡献预测与建议 | 动作可解释、可在测试环境复现，且不需要新责任方 | 自动动作产生的流量与计算要约定记在谁的账上；"自愈"降低故障可见性，根因没人修 | 平台与工具的正式功能条目、配置接口稳定 → **L2（非 AI）** |
| AI 驱动的流式存储运维：LLM 归因 / 预测那一半（原方向 5 的另一半） | 故障归因与容量预测靠人翻仪表盘与工单；卡点是**归因慢，且同一条滞后曲线两个人能读出两个结论** | **把"人读指标"换成"模型给假设与预测"**：判断者换了，动作本身没变（扩容、均衡、调参还是那几个） | 归因与预测可以进**建议通道**，帮人更快定位；预测的区间可以当作容量评审的一个输入 | 建议不进执行通道，就只是又一份没人签字的报表；进了执行通道，则"由模型决定扩缩容"这个动作**没有可回滚的定义**，失败责任没有归属方，且模型版本一变，同一条滞后曲线会得到不同结论 | 公开材料只有演示与自研路线图，动作没有可回滚定义 → **L3** |
| 分层存储（原趋势 4、原 §5.3 工业条目） | 所有数据占本地盘，保留期越长成本越高；卡点是**容量单价** | **与 AI 无因果关系**：它换的是数据的物理位置（冷段卸载到对象存储） | 保留期可以拉长而不必按本地盘单价付费——这是 §5.2.1 能成立的成本前提 | 冷读路径变长（首次读回源），因此要监控冷读比例；**"单集群 PB → EB"这一量级说法本节不作为事实使用**——它取决于对象存储配额与计费，不是分层存储本身的性质 | 各项目官方文档与 KIP 中的正式条目（KIP-405 一类）→ **L2（非 AI）** |
| KRaft / 去元数据服务（原趋势 5） | 元数据依赖外部协调服务，部署与扩缩容都要多维护一套系统；卡点是**运维面** | **与 AI 无因果关系**：它换的是元数据的存储与选举方式（内聚到集群自身的一致性协议） | 部署面变小、元数据可扩展性提升 | 迁移是一次不可逆的运维动作，要按官方迁移文档逐步走；**"去元数据服务是趋势"不能推出"你现在就该迁"** | 【公开】KIP-833（2022）把 KRaft 标记为生产可用，配置接口多年稳定 → **L2（非 AI）** |
| 流式 GraphRAG（原 §5.2 第 2 条） | 关系分析靠离线图谱构建，更新滞后；卡点是**抽取质量而非时效** | **没有改变关系分析的机制**——关系来自图谱与遍历；流只决定"什么时候更新" | 图谱更新的时效提高（真实，但只影响时效） | 抽取的非确定性使图谱自身成为需校验对象；实体消歧规则不吃一轮调参不会稳定；**把它当影响分析用，错误的影响面比没有影响面更贵** | 公开材料以原型与演示为主 → **L3** |
| CDC 中的 LLM 加工（原 §5.2 第 3 条，此处只评"加工"这一段） | 变更数据抓下来之后靠规则做字段加工（清洗、归一、打标）；卡点是**规则写不完**——源系统一多，长尾字段的规则维护成本线性上升 | **把规则换成统计判断**：只改了管道中"加工"这一段，抓取（CDC）、传输（流式存储）、下游写入三段没变 | 长尾字段不必逐条写规则；适合做**旁路富化**（给事件补标签）而不阻塞主链路 | 加工从此非确定：**同一条变更重放可能得到不同标签**，于是"可重放"在这一段不再等于"可复现"；标签口径要与模型版本一起记，否则回填会退回到一个口径已经变了的过去；模型调用还引入一个新的失败点与一项新的按次成本 | 管道三段（CDC → 流式存储 → 下游）是正式条目、接口多年未变；把 LLM 放进加工步骤只有演示与厂商示例（原清单点名的示例是 Flink CDC + OpenAI 提取客户情感一类）→ 管道 **L2** / LLM 步骤 **L3** |

**这七行的共同读法**：收益真实存在的五条里，**没有一条的收益来自模型**——三条来自既有能力与运维策略（自动均衡、分层与迁移），一条是传输层的既有能力（流式 HTTP），一条本就是既有能力（图谱与遍历），它的收益是"时效"而非"质量"。把它们写成"AI 时代的流式存储演进"，会让真正要做的三件事（定保留期、算请求成本、把同源逻辑做成一份）一件都排不进排期。**剩下两行（运维的 LLM 归因 / 预测、CDC 的 LLM 加工步骤）连"可验收的动作定义"都还没有**——它们停在 L3 不是因为效果不够好，而是因为失败时没有人能说清"这一次算是错的"的判定条件。

- **什么时候值得做**（针对本组可做的四条）：磁盘成本长期是账单大头（先分层）、元数据服务已经成为运维负担（再迁 KRaft）、分区倾斜反复引发事故（开自动均衡）、首字延迟是用户抱怨的主因（改传输层）。这四条的动作都可回滚，收益立即可见。
- **什么时候不值得做**：把"趋势"当成动工理由——分层存储要先算冷读频率，KRaft 迁移要排出一个可回滚的窗口，自动均衡要有容量余量（均衡动作本身要搬数据），**没有余量的集群上开自动均衡，等于把一次故障变成一个长期的慢**。

### 5.3 与本主题既有栈的接口在哪

流式存储与 AI 之间不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比"AI 能做什么"更能决定它能不能落地。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 流式存储 ↔ Agent 运行时 | 交接物 = 事件 schema + 分区键 + 保留期；**三者一起决定"能不能回放一次决策"** | 记录方（Agent 侧）；schema 与保留期定错，回放能力就是空的 | 既有机制 / schema 与保留期未定 |
| 流式存储 ↔ 向量索引 | 交接物 = 变更事件到向量的物化；删除事件必须走同一条流 | 索引侧；删除未传播时检索会给出**有出处但已下架**的依据 | 删除语义因产品而异（未定） |
| 流式存储 ↔ 在线特征库（[02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md)） | 交接物 = 同一份变换逻辑 + 事件时间；**保留期同时是可回填窗口** | 特征 Owner；双写不一致时，业务侧表现为"离线好、上线垮" | 既有机制（同源靠人保证） |
| 流式存储 ↔ 计算引擎（[03-data-stack/09](../09-realtime-compute/09-realtime-compute.md)） | 交接物 = 消费位点与提交语义（是否端到端精确一次）；**位点记在哪决定重放从哪里开始** | 引擎与 sink 的接缝处；把"至少一次"承诺成"精确一次"是设计侧的错 | 既有机制（[§4.2](04-streaming-store-section-4-sec4.md) 的手动提交是标准做法） |
| 流式存储 ↔ 表格式（[10-stream-batch-unified](../10-stream-batch-unified/10-stream-batch-unified.md)） | 交接物 = 变更捕获入口；队列只承担传输与近期重放 | 入湖作业；队列保留期短于重算窗口时，"可重算"会被静默收回 | 既有机制 / 两侧保留策略要一起设计 |
| 流式存储 ↔ 冷热分层（[05 冷热分层](../05-cold-hot-tiering/05-cold-hot-tiering.md)） | 交接物 = 保留期与冷读路径；**冷读比例是这套架构最该监控的指标** | 存储侧；冷读比例失控时，账单与延迟一起变差 | 既有机制（指标常被漏掉） |
| 流式存储 ↔ 成本（[11-cross-cutting/03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)） | 交接物 = 计费三项（字节 / 请求次数 / 出网流量）的分账 | 平台与财务的接缝处；**没有分账时，小消息链路的成本会在一次流量翻倍后失控** | 分账口径未定 |
| 流式存储 ↔ 审计与合规（[11-cross-cutting/07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)） | 交接物 = 写入内容的留存与删除规则；**只追加结构里的删除要靠墓碑与索引重建** | 记录方；"先记下来再说"会把合规问题推迟到数据主体提出请求那天 | 规则未定（无通行做法） |
| 流式存储 ↔ 可观测（[11-cross-cutting/04](../../11-cross-cutting/04-observability/04-observability.md)） | 交接物 = 滞后、磁盘与对象存储用量、冷读比例、无消费者分区数 | 平台侧；只监控滞后不监控"没有消费者"的分区，会长期为没人读的数据付费 | 既有机制（常被漏掉一半） |

一句话概括：**AI 没有给流式存储新增任何语义，只新增了两类写入者与一类保留理由**——Agent 的运行记录、以及被增量物化的向量与特征。由此得到三条约定。

**第一条约定：保留期是一个要签字的数字，不是配置项。** 它同时决定三件事：可回填窗口（§5.2.3）、可回放窗口（§5.2.1）、以及账单。把"最长回放 / 回填窗口 = N 天"写成一句可以被签署的话，再由它反推保留策略，顺序不能颠倒。

**第二条约定：写进日志的内容按"它会被长期保留"来对待。** 脱敏要在写入前完成，而不是在检索时靠权限反查——后者在只追加结构里等于没有做。

**第三条约定：小消息链路的成本要按三项分开算。** 字节、请求次数、出网流量分别估一遍，再看合计；只算其中一项的评估，会在流量涨一倍时得出相反的结论。

这三条约定的共同来源是同一个事实：**本主题的成本与能力都挂在保留期这一个数字上**——它决定可回填窗口、可回放窗口与账单三项，所以它必须由人签字，不能由默认值决定。凡是把保留期交给"平台默认配置"的组织，**实际上是把"能回溯多久"交给了一个没人看过的数字**。

**官方 release note / KIP / 文档（判定入口）**——这一类列的是**核验去处**，本节不据此声称任何产品已具备某能力。

- Apache Kafka 的 KIP 页面与 release note——核验三件事：**KRaft 何时被标记为生产可用**（KIP-833，2022）、**ZooKeeper 何时被移除**（以对应主版本的 release note 为准）、**分层存储从早期访问到正式的版本**（KIP-405 一类）。**判定方法：看的是 KIP 的状态字段与目标版本的 release note，不是博客与路线图页。**
- Kafka 的消费与提交相关 KIP——核验"重平衡协议""位点提交语义"这类条目，因为它们直接决定 §5.2.1 事件流的回放起点从哪算起。
- 对象存储原生流存储项目（AutoMQ、WarpStream、Apache Fluss 一类）的官方文档与仓库——核验四件事：**写路径是否落在对象存储**、**元数据存在哪**、**最小可部署形态**、**许可与厂商归属**（这类项目近两年发生过更名、收购与许可调整，写进长期路线图之前看官方公告与仓库 LICENSE）。
- Apache Pulsar 的官方文档——核验计算存储分离与分层存储的正式条目；**判定方法：看分层是由存储层原生支持还是靠额外卸载组件**，这决定故障面在多处还是在一处。
- Apache RocketMQ 的官方文档——核验事务消息与去协调组件这类条目的正式状态（[§3.1](04-streaming-store-section-3-sec3.md) 的模式 6 与 [§4.3](04-streaming-store-section-4-sec4.md) 的工具表指的都是这一族，能力以官方文档为准）。
- Schema Registry 类工具的官方文档——核验兼容性检查策略（向后 / 向前 / 全兼容）是否是正式配置项；**它决定 §5.2.1 的事件 schema 能不能演进**，比选哪家实现更重要。
- 向量库、特征库与编排框架的官方文档（原清单点名的候选：Milvus / LanceDB / Pinecone 一类向量库，Feast / Tecton 一类特征库，LangChain 一类编排框架）——核验三件事：**变更事件的删除传播是不是文档化的正式能力**（还是只能自行重建索引）、**特征库的时点正确性（Point-in-Time）如何保证**、**提供的整合是产品原生能力还是示例代码**。这三件正是 §5.2.3 的收益能否兑现的前提。
- 集群自身的监控指标文档（[§4.1](04-streaming-store-section-4-sec4.md) Step 5 列的那一组）——核验"滞后""磁盘与对象存储用量""无消费者分区数"这三项里，后两项是否有现成指标；**判定方法：如果"无消费者的分区"没有指标，说明你在为没人读的数据长期付费**，这一项比滞后更值得先补。

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含指标与口径的第三方"AI 改变流式存储"生产案例。公开材料里能核到的是流式存储的运行做法自述（本书 [§6](04-streaming-store-section-6-sec6.md) 的四个案例已整理为"可重放日志 / 千节点集群与分层 / 事务与顺序消息 / 峰值可预测"四条路径），以及各产品对分层、托管与对象存储原生的正式发布条目；**缺的是"因此在单位成本 / 冷读延迟 / 回填窗口上从多少变到多少"这类带基线的第三方材料**。**这个空白本身是结论**——它正是本节把整张表压在 L2 / L3 的直接原因：第②条核不到，就不许靠改写判据把它补上。
- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——把你们自己的"消息大小分布""每千条消息的请求成本""冷读比例""可回填窗口（天）"四个数算出来并留存口径，下次评审时它就是带基线的生产材料。
- 这三类里**最容易造假的是第三类**：产品方给出的成本对照通常只写单价、不写消息大小分布与访问模式，而这两项恰好决定结论。判定方法：只接受同时给出"口径（消息大小、读写模式）+ 规模（条数、字节数）"的材料；缺一项就只当方向记录，不当证据。

**怎么用这份清单**：要核"能力存不存在"看官方文档与 release note（最快）；要核"机制成不成立"看论文（最慢但最稳）；要核"在我这里值不值得做"看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。

**核验 §5.1 表里其中六条宣称的最小动作**（都不需要采购）：

1. **Agent 事件流**：取一次失败会话，只用手上的事件回答"调了哪些工具、返回什么、在哪一步偏离"；再数一次写入字段里有几个是个人信息。
2. **流式 RAG 索引**：抽 10 个已下架文档看还能不能被检索到；数一次索引里有几种模型版本。
3. **流式特征**：把离线重算与在线特征按同一批样本逐行比对，数不一致率；再数最近一周的迟到事件比例。
4. **LLM 流式输出**：问"这条 token 流有几个消费者、需不需要回放"——答案是"一个消费者、不需要回放"时，就不要引入队列。
5. **Serverless / 对象存储原生**：取一个真实 topic，按"字节 × 存储单价 + 条数 × 请求单价 + 出网流量"三项分开算一遍，再和自己本地盘的账单比。
6. **分层存储 / KRaft**：数一次冷读比例与本地盘占用；查一遍 KIP 状态与官方迁移文档是否覆盖你的版本跨度。

### 5.5 被过度宣传的部分

**「Serverless / 对象存储原生流存储让流式存储更便宜」**——实际是：它改的是**成本结构**（从预置容量变成"字节 + 请求次数 + 出网流量"），便宜与更贵取决于你的消息形态；**在小消息高吞吐场景下，请求次数与条数成正比、与字节数无关**，而 Agent 事件与 token 级记录恰好是"多而小"的形态，单位成本完全可能不降反升；同时延迟的物理来源从本地盘变成对象存储往返，冷读路径显著变长。原因：这类材料由产品提供方发布，而它们几乎不披露**消息大小分布与访问模式**这两个决定结论的变量。**它什么时候才会成真**：出现第三方按"消息大小 + 读写模式"分档给出的成本与冷读延迟对照材料。**判定方法**：按 §5.4 判据动作第 5 条把三项成本分开算一遍——算出"请求成本占比"，这个问题就有答案了。

**「LLM 流式输出需要流式存储 / 流式网关」**——实际是：token 级响应是**HTTP 传输层**的既有能力（SSE / WebSocket 一类），与消息队列无关；把 token 塞进队列，换来的是按条计费的写入和一堆没有消费者的分区。原因：把"流式"这个词在传输层与消息层之间混用——两者都叫 streaming，但一个解决"边生成边展示"，另一个解决"多消费者、可回放、可长期保留"。**它什么时候才会成真**：当 token 流真的需要**多个消费者、按序回放或审计留痕**（内容审核、计费对账、质量回溯）时，队列的角色是"记录"，不是"传输"。**判定方法**：问这条 token 流有几个消费者、需不需要回放；两个问题都答"不需要"，就不要引入队列。

**「Agent 事件流 = 把 Agent 日志接到 Kafka」**——实际是：可复现性要求的不是"把日志换个地方存"，而是**记下"这次决策看到了什么"**——请求摘要、每次工具调用与返回、关键中间状态、模型版本；粒度、分区键、保留期三件不定，接过来只是一份更大的日志。另一处混同是"可重放 = 可复现"：重放给出的是当时的上下文，模型仍可能给出不同答案，所以事件流是**审计证据，不是回归测试**。原因：日志工程的习惯是"先接过来再想用途"，而在 AI 链路上，"记什么"就是能力本身。**它什么时候才会成真**：事件 schema 能回答"这次决策看到了什么"，并且有明确的保留期与脱敏规则。**判定方法**：见 §5.4 判据动作第 1 条。

这三条的共性：**它们都把"传输更省事、容量更便宜、日志更集中"这类动作成本下降，当成了"这条链路更可信"**。而本主题的质量判据只有三条——分区内顺序与 offset 是否被保住、保留期是否覆盖回放与回填窗口、单位成本是否按真实的消息形态算过；这三条一条也没有因为 AI 而改变。补一句读法上的提醒：这三条被过度宣传，**并不是因为相关技术没有价值**（对象存储原生与分层存储的收益是真实的，事件流对 Agent 链路也是必需的），而是因为它们的收益被说成了另一种东西——把"容量更便宜"说成"这条链路更可靠"，会让评审会上该问的三个问题（保留期多长、删除怎么落、请求成本占几成）一个也问不出来。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| Agent 事件流会成为一类**默认被记录**的数据，保留期与删除请求的冲突随之公开化 | 存储与可观测产品把"Agent trace 的保留期与脱敏"做成正式配置项；合规材料开始讨论只追加日志里的删除请求 | 出现"Agent trace 长期全量保留"且不讨论删除与脱敏的公开生产做法 |
| 对象存储原生流存储的采用会先集中在**大消息与顺序读**场景，而不是小消息高吞吐 | 公开实践材料普遍带"消息大小分布"与"冷读比例"两个数字；分层仍然保留在写路径上 | 出现第三方材料，证明小消息高吞吐场景下单位成本也低于本地盘方案 |
| 存储侧的**向量与特征能力会继续留在独立组件里**，而不是被吸收进日志或表格式 | 各项目的发布条目集中在 CDC / 物化 / 索引同步这类接口上，而不是"存储内置索引" | 出现跨多个独立实现一致的"日志或表格式内置向量索引 + 统一删除语义"规范条目 |
| 与 AI 相关的下一轮实质变化在**保留与删除语义**（谁能被忘掉、多久被忘掉），而不是在吞吐或延迟 | 产品把"按主体的删除 / 过期"做成正式能力；审计材料开始要求可证明的删除 | 讨论继续集中在吞吐、延迟与成本曲线上，删除仍靠人工修数 |

写这四条时的共同约定：**信号必须是外部可观察的**（规范条目、发布说明、第三方公开案例），而不是"我觉得会"。**被检验得最快的是第二条**——只要有一份带消息大小分布的第三方对照材料出现，一年内就能看到；**最慢的是第四条**——它要求行业把"忘记"当成一项能力，而这件事通常由一次数据主体请求推动。这里还有一条共同的读法：**这四条里没有一条的证伪信号是"模型变强了"**——它们全部落在成本结构、保留策略与合规上，这正是本主题的特征：它的卡点大多不在模型那一层。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 准备把 Agent 的运行记录接进事件流 | 先定事件 schema、分区键、保留期三件；脱敏在写入前做 | 观察可用事件还原多少比例的失败会话 | 不要在保留期与脱敏规则没定时先把内容记下来"以后再说" |
| 磁盘成本长期是账单大头 | 先算冷读比例与保留期，再开分层存储 | 观察冷读比例与"首次读回源"的延迟 | 不要把"分层能让单集群从 PB 到 EB"当成事实写进方案 |
| 想用对象存储原生的流存储降本 | 按"字节 + 请求次数 + 出网流量"三项分开算一遍 | 观察请求成本占比与冷读延迟 | 不要在消息小、条数高、延迟要求硬的链路上只按容量单价选型 |
| 要做实时特征或实时索引 | 先把同一份变换逻辑做出来，再验证时点正确性 | 观察离线 / 在线不一致率与迟到事件比例 | 不要在"两侧同源"没有保证时先上实时——那会把漂移变快 |
| 想做流式 RAG | 先解决删除传播与模型版本一致性 | 观察已下架内容的召回情况与索引里的版本数 | 不要在没有评测集与口径时把"实时"当成质量提升的证据 |
| 首字延迟是用户抱怨主因 | 改传输层（流式 HTTP 一类），不要动存储 | 观察首字延迟与完整响应时间各占多少 | 不要把 token 流塞进队列——除非它真的需要多消费者或回放 |
| 分区倾斜反复引发事故 | 先确认有容量余量，再开自动均衡 | 观察均衡动作搬动的数据量与耗时 | 不要在余量不足的集群上开自动均衡——它会把一次故障变成一个长期的慢 |
| 元数据服务已成运维负担 | 按官方迁移文档逐步迁到内聚的元数据模式，并排好回滚窗口 | 观察迁移后元数据侧的故障面是否真的变小 | 不要把"去协调服务"当成必须提前规划的重构 |
| 老板要求"AI 原生事件流平台" | 把目标拆成"schema + 保留期 + 删除语义"三段，分别给验收口径 | 观察三段的负责人是否明确 | 不要签"由模型决定扩缩容与保留期"式的目标——它没有可验收的失败定义 |
| 事件 schema 已经开始演进 | 给每个 topic 定兼容性策略（向后 / 向前 / 全兼容），并把它进 CI | 观察一次加字段与一次改类型是否都按策略通过 | 不要靠"通知下游"来管 schema——回放历史事件时才发现的兼容问题，代价最大 |
| 想为"AI 取数"复制一份事件到分析侧 | 先确认这份复制能不能承载"回放 + 回填"，还是只够做看板 | 观察两侧的保留期是否被分别维护、是否存在两套口径 | 不要复制第二份真相；分析侧要的是可用性，不是又一条要维护的链路 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（拉长保留期、换存储介质、动分区与元数据、扩大自动化半径），**而收益依赖一个尚未成立的假设**（请求成本可忽略 / 同源已被保证 / 生成物可校验）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**记录的动机**——流式存储过去为"给下游消费"而写（消费完即可删，保留期是成本参数），Agent 链路里的写入目的是"以后能重看一遍"，于是保留期第一次变成**功能参数**：它决定的是可复现与可回溯的窗口。**它没有改变**主文件 [§1.1](04-streaming-store.md) 那条更前置的约束：日志的顺序、offset、可重放与保留语义，以及分区内有序这条物理前提——把会话事件按错误的分区键打散，"可回放"就在语义上失效了，这跟用不用 AI 无关。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是"为什么要记、记多久"，还是"吞吐与延迟的数字"？** 前者是 AI 带来的真问题（保留期、删除语义、粒度），后者今天大多已有解，且与模型无关。第二条同样快的判断：**它需要几个消费者、需不需要回放、单位成本按哪一项算**——三条答不上来的方向，只能停在记录里。
>
> 还有一条与本章其余小节一致的读法：**流式存储的价值由它承载的"以后还能重放的东西"界定，而不是由它的峰值吞吐界定**。任何以吞吐或成本曲线为主要论据的"AI 演进"，都应当先被问一句——它让哪一段历史第一次可以被重新读一遍？答不上来，它就不是演进，只是换了个部署形态。
>
> 如果只能带走一句话：**先定保留期与删除语义，再接 AI 的事件流**；顺序反过来，就是为一条还没想清楚"该记多久、怎么忘掉"的链路拉长留存。
>
