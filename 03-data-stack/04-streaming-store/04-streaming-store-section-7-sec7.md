## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表在这类产品上会失效，原因不在分数不准，而在**每一列都没有口径**。以「运维复杂度」为例：按「常驻组件数」这一可数的口径，Broker 之外还要另配存储层与元数据服务的形态比单体 Broker 多；按「单集群人数 / 千节点故障率」这一口径，结论又可能反过来。同一个词在两套口径下指向相反的判断，而表里的 3 分与 4 分不写口径，读者只能按自己的口径去理解——**这正是打分把「取决于场景的结论」伪装成「绝对结论」的方式**。同一张表里还有一类更硬的混淆：只给了列名、没给任何列口径定义，若按最自然的读法去还原，「扩展性」一列问的其实是「扩分区要不要搬数据」，「Serverless」一列问的其实是「计费单位是不是按用量」——两个问题都由同一个机制（数据主体放在哪）决定，分开打分会被读成两项独立优势。

第二个问题是**这一列的权重在不同规模上反转**。小集群里，多一个常驻组件（存储层、元数据服务）的运维代价是实打实的；到了需要独立扩计算与存储的规模，这个代价反而被「扩计算不用搬数据」抵掉。同理，保留期短时分层存储是纯增复杂度，保留期长且冷数据占比高时它决定成本曲线能不能成立。所以「哪一列更重要」本身是被规模与保留期决定的，而不是被产品决定的。

第三个问题是**打分表会把不是同一层的东西放在一起**：这里有产品（Kafka / Pulsar / RocketMQ / AutoMQ / Warpstream）、有协议族（兼容 Kafka 协议意味着生态与 SDK 可复用）、还有做法（分层存储、对象存储原生、事务消息）。产品决定「谁来做运维与取证」，做法决定「成本与延迟的物理来源」。把三者并列打分，等于把「选路线」和「选实现」压成一次决策。

第四个问题是**打分表默认所有候选都在解决同一个问题**。而这里的候选实际覆盖两种不同负载：一种是**事件流**（多消费者、可回放、可长期保留），另一种是**任务分发**（一条消息只该被处理一次、处理完就该消失）。把两者放进同一张表，会让人以为自己在同一批选项里挑更强的那个，实际是先在两种负载里选一种——选错这一层的代价是长期为没人重放的历史付费，或为「消费即删」付出重复开发的成本。

本章的做法是：不做排序，只立判据。判据立住之后，多数场景里「选哪个」会被一两条约束直接决定。这些约束来自主文件 [§1.1](04-streaming-store.md) 的核心模型——**日志（Log）+ offset**：顺序写入、按 offset 可重放、分区内有序；链路上的确认语义则来自主文件 [§2.1](04-streaming-store.md) 的三件套——ACK 三档、副本与 ISR。**任何候选的差异，最终都能归到三个机制上——数据主体存在哪、元数据与协调放在哪、写入要等多少确认——再加上一条语义边界：分区内有序 / 全局有序 / 事务消息是三件不同的事（§7.3.4）。**

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 顺序与事务边界 | 你要的是分区内有序、全局有序，还是事务消息 | 只有一类实现把「全局有序 + 事务」做进中间件（半消息 + 本地事务 + 回查）；选错这一条，业务侧要自建状态机与对账 |
| 保留期与冷读频率 | 保留多久、谁还会去读冷段 | 它同时决定成本曲线与「可重放窗口」；冷读频繁时分层带来的单价收益会被回源延迟与流量吃掉 |
| 扩容的代价 | 扩容要不要搬数据、窗口有多长 | 决定是否值得为「计算存储分离 / 无状态」多付一层常驻组件与一套控制面 |
| 成本函数的形状 | 成本随容量、请求次数还是实例数增长 | 单看容量单价的评估，会在消息变小、条数变多时得出相反的结论 |
| 运维面 | 常驻组件几个、元数据谁管、故障要跨几个控制面排查 | 它决定「几个人能扛住」以及一次故障的归因成本 |
| 生态与协议锁定 | 换引擎要不要改代码、连接器与引擎侧集成是否可复用 | 兼容既有协议意味着上层的作业、连接器、监控可以不动；私有协议意味着迁移成本落在每个下游 |

这六条里，第 1 条（顺序与事务边界）与第 6 条（生态与协议锁定）是**能力边界**——答案由业务直接给出，不需要测量任何运行时数据；第 2、3、4、5 条是**代价边界**，每一条都要先有你自己组织里的一个数。经验上，两条能力边界（对应 7.5 树上的 N1 与 N2）走完就能把候选压到一两个族【经验】——因为「全局有序 / 事务」会直接分出 RocketMQ 一族，「换引擎要不要改代码」会直接分出「兼容协议 / 私有协议」两支，剩下的才是同族内的工程选择。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| **Kafka** | 日志型流存储的默认选项 | 分区日志 + 顺序写 + 零拷贝 + ISR 副本，生态与协议最广 | 大数据流处理、连接器生态最丰富的场景 | Apache-2.0；托管版为商业服务 |
| **Pulsar** | 计算存储分离的流存储 | Broker 无状态、数据落在专用存储层（BookKeeper 一类）、元数据另置 | 云原生、多租户、要独立扩计算与存储 | Apache-2.0；托管版为商业服务 |
| **RocketMQ** | 面向交易语义的消息中间件 | 事务消息（半消息 + 本地事务 + Broker 回查）与顺序消息写进中间件 | 电商订单、支付、分布式事务 | Apache-2.0；云上为商业服务 |
| **AutoMQ** | 对象存储原生、兼容 Kafka 协议 | 数据主体放对象存储，节点无状态，扩容不搬数据 | 云上、容量规划长期跟不上、要按用量付费 | 开源 + 商业版（以官方发布为准） |
| **Warpstream** | 对象存储原生、兼容 Kafka 协议 | 同上：无状态 agent + 对象存储，按字节与请求计费 | 云上 Serverless 化的事件流 | 商业托管服务（以官方发布为准） |
| **Apache Fluss** | 面向「流 + 表」的流式存储 | 流式原生存储，面向列式 / 分析型读取 | 实时数仓、与表格式协同的流存储 | Apache-2.0（以仓库 LICENSE 为准） |
| **RabbitMQ / ActiveMQ** 一类传统 MQ | 队列语义的边界对照 | 队列 + 消息确认，ACK 后删除，不保留历史 | 业务解耦、异步通知、任务分发 | 各自开源许可 |
| **表格式（Paimon / Iceberg / Hudi）** | 不是流式存储，但同链条的对照项 | 承担「一份存储两种读法」，与队列搭配决定可重算窗口 | 流批一体的湖侧 | Apache-2.0 等 |

许可与商业模式一栏按各项目与产品页的常见标注写；这类项目近年发生过更名、收购与许可调整，写进长期路线图之前，请以仓库 LICENSE 与官方公告的当前版本为准。

这些候选分**四族**：① **本地盘自持**（Kafka / RocketMQ：Broker 带盘，扩容要动盘）；② **计算存储分离**（Pulsar：Broker 无状态，数据在专用存储层）；③ **对象存储原生**（AutoMQ / Warpstream：数据主体直接落对象存储，计费单位随之改变）；④ **面向表与分析的流存储**（Fluss 一类）。传统 MQ 是**族外对照**——它不保留历史，与前面四族在语义上就不同层。**跨族差异大于同族差异**：先按「保留期 + 冷读」分到族，再比同族的工程细节，能省掉一半比较。

八个维度被拆开而不是被丢掉：**吞吐与延迟** → 7.3.1（延迟的物理来源）与 7.3.3（acks 换延迟）与 7.4（成本函数）；**扩展性** → 7.3.1 的「扩容要不要搬数据」；**Tiered Storage 与 Serverless** → 7.3.1 的存储归属一栏（这两列其实是同一个机制的两个投影）；**事务消息** → 7.3.4 的语义边界；**生态** → 7.2 的协议与许可一栏、7.7 的迁移成本；**运维复杂度** → 7.3.2 的组件数与控制面，且必须写明口径（常驻组件数，还是单集群人均运维工时）。

### 7.3 机制差异：为什么它们表现不同（核心节）

四个机制维度，每个只回答一件事：这条性质被哪个机制逼出来，以及它必然带来哪笔代价。

#### 7.3.1 存储归属：本地盘 / 专用存储层 / 对象存储，决定扩容代价与延迟的物理来源

**机制是什么**：数据主体落在什么介质上、由谁来管这份介质，直接决定三件事——扩容要不要搬数据、读延迟的物理下限、以及账单按什么单位计。

**它在各候选中的实现差异**：

| 形态 | 数据主体位置 | 扩容的代价 | 延迟的物理来源 | 账单的主导项 |
| --- | --- | --- | --- | --- |
| 本地盘自持 | Broker 本地盘（可配分层卸载冷段） | 跨节点复制，时间与数据量成正比 | 本地 SSD，亚毫秒量级【经验】 | 容量 + 实例 |
| 计算存储分离 | 专用存储层（另有副本与一致性协议） | 计算侧换实例，存储侧独立扩 | 计算与存储之间的网络往返 | 存储层容量 + Broker 实例 |
| 对象存储原生 | 对象存储，本地只做缓存与预写 | 换实例，不搬数据 | 对象存储往返；命中缓存时接近本地 | 字节 + 请求次数 + 出网流量 |
| 分层存储（叠加在前两族上） | 热段本地、冷段对象存储 | 热段仍要动盘 | 热读走本地、冷读回源 | 本地容量（热）+ 对象存储（冷） |

**由此必然导出的性质**：因为本地盘自持形态的扩容要跨节点复制，而重建一个副本的时间与数据量成正比，所以**容量规划必须提前做**，且保留期越长、本地盘单价越高，成本越按「预置容量」走——代价是冷数据长期占着最贵的介质。因为对象存储原生把数据主体搬出节点，所以扩容从「搬数据」变成「换实例」，容量与实例第一次解耦；代价是**计费单位同时从「容量」变成「容量 + 请求次数 + 出网流量」，而请求次数与消息条数成正比、与字节数无关**——这与主文件 [§2.2](04-streaming-store.md) 给的分区吞吐口径无关，是另一套账。因为分层存储只换数据的位置、不动写入路径，所以它可以在现有集群上渐进启用；代价是冷读路径变长（首次读要回源），于是**冷读比例成为这套架构最该监控的指标**——它同时出现在延迟与账单两处。

**公开证据**：【公开】日志型流存储的原始模型出自 Kreps, Narkhede, Rao, "Kafka: a Distributed Messaging System for Log Processing", NetDB 2011；「以可重放日志替代批层」的公开表述出自 Kreps, "Questioning the Lambda Architecture", O'Reilly Radar 2014；分层存储（Tiered Storage）在 Kafka 侧以 KIP-405（2020）为正式条目【公开】；Pulsar 的计算存储分离与分层存储以其官方文档为判定入口【公开】。对象存储原生这一类产品（AutoMQ / Warpstream）的开源与首个公开版出现在 2023 年前后【经验】，与主文件 [§1.4](04-streaming-store.md) 的演进时间线一致（该时间线另把 2024 记给 Apache Fluss，Fluss 在本节归入第四族），**具体日期以各仓库的 release 记录为准**；且**成本与延迟的对照材料多出自产品提供方本身**——这类数字在采用前宜按 7.4 的成本函数用自己的账单复算一遍。**判定方法**：查它的文档里**写路径是否也落在对象存储上**（还是先写本地预写日志再上传）、**元数据存在哪**、**最小可部署形态是什么**——三条问清楚，任何产品都能被放进上面这张表。

**失效条件**：当消息很小、条数极高、且端到端延迟有硬要求时，「数据在对象存储上」带来的单价优势会被请求项与冷读往返抵消——**判定方法**：取一个真实主题，按「字节 × 存储单价 + 条数 × 请求单价 + 出网流量」三项分开算一遍，再和自己的本地盘账单比。反过来，当冷数据占比很低或保留期本来就只有几天时，分层存储是净增复杂度：它多了一条要监控的冷读路径，却没有可观的单价差可省。

#### 7.3.2 元数据与协调：外部协调服务 vs 内聚共识

**机制是什么**：集群的元数据（分区归属、副本分布、leader 是谁）存在哪里、由谁选举，决定部署面有多大、扩缩容要动几个系统，以及一次故障要跨几个控制面排查。

**它在各候选中的实现差异**：

| 实现 | 元数据与选举放在哪 | 部署面 | 代价 |
| --- | --- | --- | --- |
| 单体 Broker + 外部协调服务（历史形态） | 独立的协调服务负责元数据与选主 | 多一套集群要维护 | 组件多、扩缩容要联动；协调服务自身成为关注点 |
| 内聚共识（KRaft 一类） | 协调能力内聚到集群自身的一致性协议 | 部署面变小 | 迁移是一次不可逆的运维动作，要按官方迁移文档走 |
| 计算存储分离 | 元数据与数据分属不同系统（另加一层元数据服务） | 控制面最多 | 独立扩缩容的收益，换来跨控制面的排障与容量规划 |
| 对象存储原生 | 元数据仍需一个放置点（内聚或外挂） | 取决于实现 | **判定方法**：看它是否要求一个额外的元数据服务 |

**由此必然导出的性质**：因为内聚共识把元数据与选举收进集群自身，所以部署面变小、元数据可伸缩性提升；代价是这次迁移把「一次安装配置」变成「一次不可逆的运维动作」，必须按官方迁移文档逐步走并排出回滚窗口。因为计算存储分离把数据与元数据分到不同系统，所以计算与存储可以各自按需扩展；代价是**故障归因要跨两个控制面**——一次读取变慢可能是计算侧、存储侧或它们之间的网络，排查路径比单体形态长。这两条代价方向相反，选型的落点是**你更缺「部署面小」还是更缺「独立扩缩容」**。

**公开证据**：【公开】KRaft 被官方标记为生产可用对应 KIP-833（2022），判定入口是该 KIP 的状态字段与目标版本的 release note；分层存储对应 KIP-405 一类条目；Pulsar 的组件构成以其官方文档为判定入口。**核验方法**：看的是 KIP 的状态字段与 release note，不是博客与路线图页——「某版本是否默认启用某模式」这类说法，一律以该版本 release note 为准，不写死年份。

**失效条件**：把「去协调服务」当成一次需要提前规划的重构。当集群规模小、元数据压力根本不构成瓶颈时，这次迁移的收益接近零而风险不变；反之当元数据操作已成为扩缩容的阻塞点时，它才从「趋势」变成「该做的事」。另一个失效条件是**迁移跨度**：官方迁移文档通常覆盖有限版本跨度，跨太多版本时要分步走，这一步的窗口规划比技术本身更费时间。

#### 7.3.3 写入确认与读取边界：ISR / acks / High Watermark 决定「读得到什么」

**机制是什么**：写入要等多少副本确认（acks），以及消费者能看到哪个位置之前的数据（High Watermark），共同决定「丢不丢」与「读得到什么」。这是本主题里最容易被忽略但最影响正确性的一对参数。

**它在各候选中的实现差异**：

| 维度 | 常见取值与含义 | 由此得到的 | 由此付出的 |
| --- | --- | --- | --- |
| acks=0 | 不等确认 | 延迟最低 | 可能丢，且生产者不知道 |
| acks=1 | 等 leader 写入 | 延迟与安全的折中 | leader 挂掉时未同步的部分可能丢 |
| acks=all（等 ISR 确认） | 等同步副本集合确认 | 单机故障不丢 | 每次写入要等确认链，跨可用区部署时延迟随 RTT 上升 |
| 副本数 | 副本数 = 1 / 2 / ≥ 3 | ≥ 3 才能同时容忍单机故障与选举 | 存储与网络成本成倍，ISR 收缩时要防写入停滞 |
| High Watermark | 消费者只能读到 HW 之前 | 未被足够副本确认的数据不会被读到，避免读到随后回滚的数据 | 极端情况下消费者可见位置滞后于写入位置 |

**由此必然导出的性质**：因为 acks=all 要求等待 ISR 中所有副本确认，所以**写入延迟的下限由确认链的长度与跨可用区 RTT 决定**——副本分布在三个可用区时，这条下限是物理的，不是配置能绕过的；代价是吞吐与延迟都要为这个保证付费。因为消费者只能读到 High Watermark 之前的数据，所以「读到的数据」与「写入成功的数据」之间存在一段设计上的滞后；代价是极端场景下消费者可见位置落后于写入位置，这在按写入时间做业务判定时会被误读成「数据没写进去」。这两条合起来给出一个判据：**先定「丢一条的代价」和「跨几个可用区」，再定 acks 与副本数**——顺序反了就会出现「为了延迟把 acks 调低，事后靠业务对账补洞」的形态。

**公开证据**：【公开】副本、ISR 与提交语义是日志型存储官方文档中的正式条目，接口多年未变；主文件 [§2.1](04-streaming-store.md) 与本章 [§4.2](04-streaming-store-section-4-sec4.md) 把 acks 三档与位点提交语义写成可查条目。**判定方法**：核「端到端精确一次」时不要看产品的宣传语，而要分别核**队列侧的事务/幂等能力**、**计算引擎侧的 checkpoint 与提交语义**、以及**汇端是否幂等**——三段里缺一段，端到端保证就不成立。

**失效条件**：当把「至少一次」的承诺当成「精确一次」来设计时，这一对机制保护不了你——重放会带来重复动作，而重复动作要靠消费端幂等消化。另一个失效条件是 ISR 收缩：当同步副本数掉到最低可写副本数时，写入会被拒绝以保数据（这是设计意图），但对只监控滞后、不监控 ISR 与副本不足事件的团队，这表现为一次「莫名其妙的写入失败」。

#### 7.3.4 语义边界：分区内有序、全局有序、事务消息是三件不同的事

**机制是什么**：顺序与事务不是同一个维度上的强弱，而是三条互不包含的语义：**分区内有序**（日志模型的天然性质）、**全局有序**（要么单分区，要么在消费侧重排）、**事务消息**（消息发送与本地事务要么都成功要么都失败）。

**它在各候选中的实现差异**：

| 语义 | 怎么实现 | 代价 | 谁把它做进中间件 |
| --- | --- | --- | --- |
| 分区内有序 | 同一 key 落同一分区 | 热点 key 会让单个分区倾斜 | 日志型存储的默认性质 |
| 全局有序 | 单分区（吞吐受限）或消费侧按序号重排 | 吞吐与分区数成反比，或把排序成本推给消费侧 | 面向顺序消息提供专门支持的一族 |
| 事务消息 | 半消息 + 本地事务 + Broker 回查 | 多一次回查往返与一套事务状态存储 | 把事务消息作为核心能力的消息中间件 |
| 端到端精确一次 | 队列侧事务/幂等 + 引擎侧 checkpoint + 汇端幂等 | 三段都要对，任一段缺失即不成立 | 队列与计算引擎协作完成，非单一产品能力 |

**由此必然导出的性质**：因为顺序保证的粒度只到分区，所以**「按业务实体保序」要靠分区键，而选 key 时要同时问「这个实体的流量分布会不会长期不均」**——一个热点会话或热点商户会让某个分区长期倾斜，保序的收益被倾斜的代价吃掉。因为全局有序在日志模型里只能靠单分区，所以**要求全局有序就等于要求放弃水平扩展**；代价是要么忍受吞吐上限，要么在消费侧按序号重排并自己承担乱序窗口。因为事务消息把「发消息」与「本地事务」绑在一起，所以它解决的是「本地库改了、消息没发出去」这一类不一致；代价是多一次回查往返与一套事务状态存储，且回查逻辑要幂等——**这三条语义得分开评估，不能用一个「一致性更强」的说法概括**。

**公开证据**：【公开】分区内有序、按 key 选分区、副本与提交语义都是日志型存储官方文档中的正式条目；事务消息（半消息 + 本地事务 + 回查）与顺序消息是面向交易场景的消息中间件官方文档中的正式条目（本章 [§3.2.6](04-streaming-store-section-3-sec3.md) 与 [§6.3](04-streaming-store-section-6-sec6.md) 的案例指向同一族，能力以官方文档为准）。**判定方法**：要「全局有序」的承诺时，问它靠什么实现——答案若不是「单分区」或「消费侧重排」，那这条承诺就还没有落地形态。

**失效条件**：把分区内有序当成全局有序。跨分区消费时没有任何顺序保证，而按分区并行处理又会让「先发生的事件后到达下游」；上游业务若依赖事件间的因果顺序，必须把因果相关的实体收敛到同一个 key。另一处失效是 key 的基数过低：分区数多于 key 的取值数时，多出来的分区永远拿不到数据，扩容换不来吞吐。

**与这一节相邻的一条：位点存在哪，决定了重放从哪里开始。** 消费位置（offset 或等效的消费进度）由中间件侧保存还是由消费方自己保存，决定了三件事：换一个消费程序时能不能接着上次的位置读、重放要从哪个位置起算、以及「重复消费」会不会发生。本章 [§4.2](04-streaming-store-section-4-sec4.md) 把「手动提交 + 消费端幂等」写成标准做法，理由正在这里：**自动提交把「处理成功」与「位点前移」绑在同一个动作上，而这两件事在业务上并不等价**——先提交后处理会丢，先处理后提交会重，工程上只能选一种并把补偿做出来。判定方法：问一次「重放从哪里开始、重复消费靠什么消化」，两个答案都能给出来，这套语义才算被定住。

### 7.4 成本结构对比（不是价格表，是成本函数）

把 7.2 那**四族**的账写成同一个形式（**分层存储**是叠加在前两族上的做法、**传统 MQ** 是族外对照，两者都不计入四族，只在下面单列一段）：

```
总成本 ≈ 实例与常驻组件成本（Broker / 存储层 / 元数据服务）
        + f(数据量 × 保留期, 介质单价)          ← 与保留期成正比的一项
        + g(消息条数 → 请求次数)               ← 与条数成正比、与字节数无关的一项
        + h(跨区复制与出网流量)
        + i(运维人力 × 常驻组件数)
```

**各候选的主导项与隐性成本**：**本地盘自持**的主导项是 f（本地盘单价 × 保留期）与实例数；隐性成本是「保留期越长、集群越大」这条线性关系的运维复杂度。**计算存储分离**的主导项是「存储层容量 + Broker 实例」两项之和；隐性成本是控制面变多之后的排障与容量规划工时。**对象存储原生**的主导项从 f 转到 g（请求次数）与 h（出网）；隐性成本是冷读命中率——它同时影响延迟与账单。**面向表与分析的流存储（Fluss 一类）**的主导项在「实例 + 存储层」这一项上起步，冷数据下沉到湖侧介质后 f 项随之转移；隐性成本是**流式写入与列式读取共用一份数据时的转换与元数据维护**，以及它与表格式组合后的保留期对齐——两者的保留期必须一起设计，否则「可重算」会被静默收回（见 7.6 组合 1）。**分层存储**把 f 拆成「热段按本地盘、冷段按对象存储」，主导项随之变成冷热比。**传统 MQ（族外对照）** 的 f 接近零（ACK 即删），主导项是实例数与 i，隐性成本是「不可重放」带来的业务侧重复开发。

**三项【推算】，推导链写全**：

- **【推算】分层存储省的是哪一部分**。设本地盘单价为对象存储的 k 倍、冷数据占比为 s（其余为热段，仍留本地），则只按存储单价计的总成本约为原来的 `(1 − s) + s / k` 倍。代入 k = 10、s = 0.7：`0.3 + 0.07 = 0.37`，即约为原来的三分之一。**结论方向**：冷数据占比越高、两类介质单价差越大，收益越明显；但这个结论只覆盖存储单价一项——冷读频繁时回源流量与延迟会把差额吃掉，所以要用**自己的冷读比例**复算，而不是用别人的倍数。这条推导同时说明为什么「单集群容量能涨到多少」这句话不能当事实使用：它取决于对象存储的配额与计费，而不是分层机制本身的性质。
- **【推算】小消息为什么会让账单换一个方向**。设总字节数固定为 B、平均消息大小为 b、每次请求携带固定条数（合批），则请求次数 ≈ `B / (b × 合批条数)`。b 缩小到十分之一时，请求次数上升约十倍，而字节数不变。**结论方向**：当成本函数里 `g` 项按请求计费时，**「消息变小」会让成本上升而不是下降**——这与按字节计费的直觉相反。所以小消息高吞吐链路（Agent 事件、逐条变更、token 级记录）在改用对象存储原生或按请求计费的形态之前，必须先把自己的消息大小分布算出来。
- **【推算】分区数怎么估**。按主文件 [§2.2](04-streaming-store.md) 的口径，单分区吞吐量级为写 ~10 MB/s、读 ~30 MB/s【经验，属业界常用经验量级，不是保证值，实际随消息大小、批处理与副本确认方式变化】。若峰值写入为 1 GB/s，则 `1000 MB/s ÷ 10 MB/s ≈ 100` 个分区；按「留 2 倍余量」的常用做法为 200 个。**结论方向**：分区数的下限由这个除法给出，上限由「每个分区都要占内存与文件句柄、重平衡要搬动它的归属」给出——所以分区数是**两端都有代价**的参数，不是越多越好。分区更细的经验值（例如多少分区对应多少实例）不建议直接套用，因为单分区吞吐本身随消息形态变化。

**变化方向不同，才是选型的难点**：本地盘自持的成本随「容量 × 保留期」线性增长；对象存储原生的成本随「条数」与「出网」增长而与实例数脱钩；分层存储位于两者之间（热段仍线性、冷段脱钩）。因此**「换成对象存储能不能省钱」这个问题没有统一答案，它取决于你的消息大小分布与冷读比例**——这两个数不测出来，任何单价对比都是无效的。

| 成本对哪个变量敏感 | 本地盘自持 | 计算存储分离 | 对象存储原生 | 面向表与分析的流存储 | 传统 MQ（族外对照） |
| --- | :---: | :---: | :---: | :---: | :---: |
| 保留期长短 | **高**（线性推高容量） | 中（存储层线性） | 低（按字节计） | 中（长保留通常靠下沉到湖侧介质） | 低（ACK 即删） |
| 数据总量 | **高** | 中 | 中（字节项） | 高 | 低 |
| 消息条数 | 低 | 低 | **高**（请求项） | 低 | 中 |
| 跨区复制 / 出网字节 | 中 | 中 | **高** | 中 | 低 |
| 实例 / 常驻组件数 | 中 | **高**（Broker + 存储层 + 元数据） | 低（节点无状态） | 中（含元数据与协调组件） | 中 |
| 冷读频率 | 低 | 低 | **高**（回源往返 + 回源流量） | 低（分析型读取是设计目标，不是异常路径） | 不适用（不可读历史） |
| 分区数与重平衡 | **高** | 中（存储侧解耦） | 中（缓存会被打掉） | 中 | 低 |

读这张表的方法：先在你的场景里找出**会涨的那一列**，再看候选在这一列上是高还是低。不做这一步而只比单价，就会出现「按容量单价选型、按请求次数结账」这种事后才发现的错配。「面向表与分析的流存储」这一列按 7.2 给它的机制（流式原生存储 + 面向列式 / 分析型读取 + 与表格式协同）推导，具体到某一实现时，请按 7.3.1 的三条判定方法（**写路径是否也落对象存储、元数据存在哪、最小可部署形态是什么**）复核它的写路径与存储归属，再决定它在你这张表上落在哪一格。

### 7.5 决策树（每个分支都要有阈值依据）

```
N1 需要事务消息，或者需要全局顺序吗？
├── 需要 ──► 面向交易语义的消息中间件（事务消息 + 顺序消息）
└── 不需要 ► N2

N2 需要直接复用既有的引擎侧生态（连接器、作业、SDK、监控）吗？
├── 需要 ──► 兼容既有协议的实现族（生态不动，这是最大的一笔省）
└── 不需要 ► N3

N3 容量规划长期跟不上（保留期长、冷数据占比高）吗？
├── 是 ──► N4
└── 否 ──► N6

N4 冷段还会被频繁读取吗？
├── 冷读频繁 ──► 先留在本地盘（或加大热段比例）；此时单价差抵不过回源
└── 冷读稀疏 ──► N5

N5 扩容窗口短、不接受搬数据吗？
├── 是 ──► 对象存储原生（无状态节点 + 对象存储）
└── 否 ──► 分层存储（保留既有写入路径，渐进启用）

N6 需要独立扩计算与存储，或多租户强隔离吗？
├── 需要 ──► 计算存储分离（Broker 无状态 + 专用存储层）
└── 不需要 ► 本地盘自持的单体形态（默认选项）

（走到上面任一支的成形方案之后，都接着问这一问）► N7
N7 元数据服务已成为运维负担、且集群规模已到元数据操作成为阻塞点？
├── 是 ──► 迁到内聚共识形态（按官方迁移文档，排回滚窗口）
└── 否 ──► 不动（等它真的成为阻塞点）
```

**阈值依据**（与树上节点一一对应）：

- **N1**：依据是语义边界的三分——分区内有序、全局有序、事务消息互不包含（见 7.3.4）。前两者是日志模型的天然性质或消费侧重排可以替代的，事务消息不是：它要求「发送」与「本地事务」原子绑定，而这件事必须在中间件侧实现，业务侧替代方案是自建对账。因此这一条不需要数量阈值，是**能力边界**上的分叉。
- **N2**：依据是「换引擎要动什么」（见 7.7 的迁移表）。兼容既有协议意味着连接器、流处理作业、SDK 与监控面板可以不动；私有协议意味着这些成本逐项落到每个下游。这条同样是能力边界分叉，不设数量阈值。
- **N3**：阈值是「保留期长到集群规模不能再随它线性增长」。这个拐点不能用固定天数给出，它的判据是**保留期驱动的容量增长是否已构成持续运维负担**（磁盘用量长期是账单大头、扩容窗口跟不上数据增速）；若保留期只有几天且冷数据占比低，这一支就不成立。
- **N4**：阈值是**冷读频率**，而不是数据年龄。判据是「冷段是否还会被常规消费」：慢消费者、回溯读、盘查与合规取数都算常规读取。冷读频繁时，分层的单价收益被首次回源延迟与回源流量抵掉，所以先留在本地盘更划算。
- **N5**：阈值是**扩容窗口的长度与「能否接受搬数据」**。判据很具体：一次扩容里，跨节点复制副本的时间是否超出业务可接受的窗口；超出，且不希望为此提前预置容量，就落在对象存储原生这一支。
- **N6**：阈值是**是否需要把计算与存储分别按不同节奏扩展**，以及是否有多租户强隔离要求。判据不是集群大小，而是「扩容时你更缺实例还是更缺容量」：两者需求经常不同步时，分离才值那一层额外组件。
- **N7**：阈值是**元数据操作是否已成为扩缩容与运维的阻塞点**。判据是运维事实而不是趋势判断：分区归属变更、元数据备份恢复、集群启动时间这几件事里，是否已有被协调服务卡住的记录；有，才轮到迁移。

**怎么用这棵树**：N1 与 N2 是**能力边界**上的分叉，答案由业务给出，不需要任何测量；N3 到 N7 是**代价边界**上的分叉，每一条都要求你先有一个自己组织里的数（冷数据占比、冷读频率、扩容窗口、两类扩展需求是否同步、元数据阻塞记录）。这也解释了为什么「先把候选排个序」这件事无法在纸面上完成——**排序所需的输入有一半来自你自己的运行时**。实用的做法是：先把 N1 / N2 走完锁定候选族，再去把上面列出的那几个数逐个采集出来，最后在同族里挑工程形态。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 电商订单 / 支付（要事务消息与顺序） | 事务消息 + 顺序消息写进中间件的一族 | 日志型存储 + 业务侧对账 | 用日志型存储做这件事，等于把「本地事务与消息的一致性」搬到每个业务系统里重写一遍 |
| 大数据流处理与连接器生态（要复用既有作业） | 兼容既有协议的日志型存储 | 计算存储分离 | 私有协议会让每个连接器、每个作业、每个监控面板都要改 |
| 长期保留 / 合规与审计（冷读稀疏） | 分层存储 | 对象存储原生 | 冷读频繁时单价的收益被回源延迟吃回 |
| 云上容量规划长期跟不上 | 对象存储原生 | 分层存储 | 小消息高吞吐时请求项主导，单位成本可能不降反升 |
| 多租户 / 要独立扩计算与存储 | 计算存储分离 | 本地盘自持 + 业务侧隔离 | 单体形态下两类扩展需求互相牵连，扩容要一起做 |
| 传统业务解耦与异步通知（无重放需求） | 队列语义的中间件 | 日志型存储 | 用日志型存储承载纯任务分发，会长期为没人重放的历史付费 |
| 实时数仓 / 与表格式协同 | 流式存储 + 表格式 | 队列只做传输 + 湖侧重算 | 两者保留期要一起设计，队列保留期短于重算窗口时「可重算」会被静默收回 |
| AI 侧的事件流（要长期回放） | 日志型存储 + 分层或对象存储原生 | 队列语义的中间件 | 队列 ACK 即删，不满足「以后能重看一遍」 |

**四个常见组合**（组合内各件承担的职责边界与运维代价）：

- **组合 1：日志型流存储 + 流计算引擎 + 表格式（入湖）**。职责边界：队列承担**传输与近期重放**（分区内有序、按 offset 可回放），流计算引擎承担变换与写入语义（checkpoint 与位点提交绑定），表格式承担**长期结构化的表数据**与「一份存储两种读法」。运维代价：两侧保留策略必须一起设计——**队列保留期短于重算窗口时，「可以从流里重算」这件事会被静默收回**；此外端到端精确一次要靠三段协同，任一段缺失就不成立。
- **组合 2：变更捕获 + 队列 + 数据湖表格式**。职责边界：变更捕获负责从源库抓取（含删除与更新），队列负责解耦与缓冲，湖侧表格式负责合并与可查询。运维代价：变更语义要在两侧对齐——**源库的删除如何表达、更新如何落成 upsert**，是这条组合最容易含糊过去的地方；此外变更流会把「源库结构变更」一路带到下游，schema 兼容性策略要进流程。
- **组合 3：日志型流存储做主干道 + 事务消息中间件做交易语义**。职责边界：主干道承担高吞吐的事件流与重放，事务消息中间件只在「本地事务与消息必须原子」的那几条链路上承担一致性。运维代价：**两套中间件并存**，容量、监控与值班都要双份；收益是把两套语义各自放在它擅长的位置上，而不是让其中一套硬撑另一种语义。组合的边界要写清楚：**同一条业务链路不要既走主干道又走事务消息**，否则排障要跨两套位点与两套事务状态。
- **组合 4：分层存储 + 离线计算引擎直读冷段**。职责边界：队列负责写入与近期消费，离线引擎按需读冷段做回填与重算，**两层共享同一份数据、不复制第二份真相**。运维代价：冷读路径变长，回填作业要能容忍回源延迟；且「直读冷段」的接口与权限要单独设计——否则离线作业会绕过队列的消费语义，把重放变成对存储层的直接扫描。

四个组合的共同点是：**它们都在把「可重放窗口」这件事显式地定下来**。组合 1 与组合 4 靠保留策略与分层决定窗口，组合 2 靠变更日志决定窗口，组合 3 则把「哪条链路需要事务」单独收口。反过来说，如果一个方案的拓扑图上没有标注任何保留期，那它的「可回放 / 可重算」都还只是一句期望。

| 组合 | 它换来什么 | 失效边界（哪一环先崩） | 运维代价落在谁身上 |
| --- | --- | --- | --- |
| 1：队列 + 流计算 + 表格式 | 传输与长期表数据各归其位，一份存储两种读法 | 保留期：队列保留期短于重算窗口时，「可从流里重算」被静默收回 | 平台与湖侧团队；两侧保留策略必须一起改 |
| 2：变更捕获 + 队列 + 湖表格式 | 源库变更近实时进入湖侧 | 变更语义：删除与更新没在两侧对齐时，湖侧会长期带着已被删除的数据 | 采集与湖侧共同；schema 变更要一起走流程 |
| 3：主干道 + 事务消息中间件 | 两套语义各就各位，不必让一套硬撑另一种 | 边界重叠：同一条链路既走主干道又走事务消息时，排障要跨两套位点与事务状态 | 平台团队；两套中间件的容量、监控、值班都是双份 |
| 4：分层存储 + 离线直读冷段 | 回填与重算不必复制第二份数据 | 权限与接口：离线作业绕过消费语义直接扫冷段时，重放会变成对存储层的全量扫描 | 存储侧；冷读比例与回源流量要有指标 |

### 7.7 选错的代价与迁移成本

**反模式：按吞吐与延迟打分选型，忽略语义边界** —— 症状：选型材料里的比较维度是吞吐、延迟、社区活跃度，没有一条问「要不要事务消息、要不要全局顺序」。后果：挑了性能更好的一族，却发现业务需要「本地事务与消息原子」，于是每个业务系统各写一套对账与补偿逻辑——**这笔成本从中间件移到了所有业务团队**，且分散在几十个仓库里，比在中间件里做一次要贵得多。正确的做法：N1 与 N2 两条先过，再比性能。

**反模式：为省容量把数据主体搬到对象存储** —— 症状：决策依据是「对象存储单价比本地盘低一个量级」。后果：账单从容量项变成「容量 + 请求次数 + 出网流量」三项，在消息小、条数高的链路上，**请求次数与条数成正比、与字节数无关**，单位成本可能不降反升；同时冷读路径变长，首次回源延迟进入用户可见链路。正确的做法：按 7.4 的三项分开复算一遍，把「请求成本占比」算出来再决定；并把**冷读比例**提升为一等监控指标。

**反模式：用「加分区」解决一切容量问题** —— 症状：吞吐不够就加分区，节点不够就加分区。后果：分区数超过实例承载后，每个分区占用的内存与文件句柄、以及重平衡要搬动的归属数据一起增长，**一次节点变动引发的大范围重平衡会让可用性显著下降**；同时热点 key 的存在使多出来的分区拿不到流量。正确的做法：先按 key 分布检查倾斜，再按 7.4 的除法估下限、按重平衡代价估上限，并预留的是**余量**而不是无限加。

**反模式：把「至少一次」承诺成「精确一次」** —— 症状：方案的语义一栏写「端到端精确一次」，实现里只有队列侧的幂等生产者，**汇端没有幂等**。后果：重放与重试会带来重复动作（重复扣款、重复计数一类），而这类问题通常在业务侧被当成「偶发的脏数据」处理，长期消耗排查工时。正确的做法：把端到端语义拆成队列侧、引擎侧、汇端三问，逐问给出可核验的答案。

| 从 → 到 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 本地盘自持 → 对象存储原生 | 有：存量段要迁移或按保留期自然过期 | 低：兼容协议时上层不动，私有协议则要改 | 有：一套新控制面、新的容量与账单口径 | 中：请求计费模型、冷读指标、缓存命中率 |
| 本地盘自持 → 分层存储 | 无（冷段按策略卸载） | 无 | 中：新增冷读监控与回源路径 | 低：主要是保留策略与冷读比例 |
| 单体 → 计算存储分离 | 有：数据要迁到专用存储层 | 中：客户端与权限模型要跟着调整 | 高：常驻组件变多，故障要跨控制面排查 | 中：两套系统的容量与排障 |
| 外部协调服务 → 内聚共识 | 无（元数据迁移按官方文档） | 无 | 中：一次不可逆的运维动作，要排回滚窗口 | 低：日常操作变化不大 |
| 队列语义 → 日志型存储 | 无 | 有：消费模式要从「确认即删」改成「位点 + 幂等」 | 中：新增位点与滞后监控 | 高：位点提交语义、重放、分区键设计 |
| 加大分区数 → 改为按 key 重分配 | 无 | 低 | 中：重平衡要排窗口 | 低：主要是倾斜与 key 设计 |
| 至少一次 → 端到端精确一次 | 无 | 有：汇端要加幂等键与去重状态 | 中：事务与位点提交进流程 | 高：三段协同的验收方法 |

这张表里最贵的一行是「队列语义 → 日志型存储」：它看着只是换个中间件，实际要重写的是**整个消费模型**——从「拿到消息、处理完确认」变成「记位点、可重放、幂等」。反过来最便宜的是分层存储：写入路径不变，动的只是保留策略与一条冷读监控【经验】。

迁移本身只有两条路径，代价方向相反：**双跑**（新旧并存、双写或双消费，按对账确认一致后再下线）把风险摊成一段时间内的双份存储与双份运维；**一次性切换**（在某个位点切过去，靠回放补齐）省掉了双跑的成本，但风险集中在切换点上——**位点与语义在那一刻如何对齐，是这类迁移唯一真正的技术难点**。两条路径的判据相同：**切换点前后，同一个业务的「已处理」定义是否一致**；不一致时，重复或遗漏会以「个别数据不准」的形态长期存在，而不是在上线当天暴露。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 要事务消息或全局顺序 | 面向交易语义的中间件 | 只有它把「发送与本地事务原子绑定」做进中间件；否则这笔成本落到每个业务系统 |
| 要复用既有连接器、作业与 SDK | 兼容既有协议的一族 | 协议是生态的接口；私有协议会让迁移成本逐项落到每个下游 |
| 保留期长、冷读稀疏 | 分层存储 | 把冷段的单价换成对象存储，保留期与集群规模解耦 |
| 保留期长、冷读频繁 | 先留本地盘或加大热段 | 单价差抵不过首次回源的延迟与流量 |
| 容量规划长期跟不上、扩容窗口短 | 对象存储原生 | 扩容从「搬数据」变成「换实例」，但计费单位同时改变 |
| 消息小、条数极高 | 先算「请求成本占比」再定 | 请求次数与条数成正比、与字节数无关 |
| 要独立扩计算与存储、或多租户强隔离 | 计算存储分离 | 两类扩展需求解耦，代价是多一层常驻组件与控制面 |
| 纯任务分发、异步通知、无重放需求 | 队列语义的中间件 | 日志型存储会让没有消费者的历史长期占着容量 |
| 元数据操作已成扩缩容阻塞点 | 迁到内聚共识形态 | 部署面变小；但要按官方迁移文档排窗口 |
| AI 侧事件流要长期回放 | 日志型存储 + 分层/对象存储 | 可回放窗口是功能参数，不是成本参数 |

> 本节小结：本主题的对比里**唯一真正起决定作用的差异是「可重放窗口挂在什么介质上、由谁付它的账」**——它同时决定了扩容代价（要不要搬数据）、成本函数的形状（容量 / 请求次数 / 出网）、以及延迟的物理下限（本地盘还是对象存储往返）。第二重要的是**语义边界**：分区内有序、全局有序、事务消息是三条互不包含的语义，选错这一层，代价会从中间件转移到所有业务团队，且分散在几十个仓库里。
>
> 判断任何一提法是否值得投入，只需问三句：**保留期多长、按哪一项计费、端到端语义由哪一段保证**——三句答不上来的方向，只能停在记录里。凡是拿「吞吐更高」「容量更便宜」来论证的方案，也应该先被要求补齐这三项。
>
> 一个可执行的收尾动作：把这几个数写进架构文档的第一页——**保留期（天）、它是否同时是可回放与可重算窗口、冷数据占比、冷读比例、端到端语义由哪一段保证**。这五项一旦能被签署，本节的整棵决策树就不必再走第二遍；反过来，把保留期交给平台默认值配置的组织，等于把「能回溯多久」交给了一个没人看过的数字。
>
> 💡 **思考锚点**：把 §7.7 表里你正打算走的那一行找出来——迁移代价落在「数据迁移 / 查询改写 / 运维重建 / 团队再学习」四项里的哪几项？如果它正是最贵的「队列语义 → 日志型存储」一行（消费模型要从「确认即删」改成「位点 + 幂等」），你还认为这只是换一个中间件吗？
