## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

流式存储的模式选择，看起来是「Kafka / Pulsar / RocketMQ / AutoMQ 选一个」。真实的决定因素不是品牌，而是几条具体约束：**持久层放在哪里**（Broker 本地磁盘 / 独立存储集群 / 对象存储）、**元数据由谁管理**（外部协调系统 / 集群内部一条日志）、**扩容时数据要不要搬**、**保留多久与谁来付这份存储费**，以及延迟预算与运维能力。同一批业务，这些约束一变，正确架构就变。

先看被推翻的第一个直觉：「更先进的产品一定更好」。Pulsar 的计算存储分离在「扩容不搬数据」上确实占优，但它把每一次读写都变成一次跨网络访问独立存储集群的操作；如果你的负载是低延迟小消息且集群规模不大，这个代价换不到任何东西——分离带来的收益在「需要独立扩计算与扩存储、且多租户隔离」时才兑现。

第二个被推翻的直觉：「保留久 = 存储贵 = 必须删数据」。真正决定成本的不是保留时长本身，而是**热数据窗口有多大**：只要本地只保留最近被频繁读取的那一段、把更早的段卸载到对象存储，保留一年的成本结构就与保留一天接近（差别在对象存储的容量费用与出流量费用上）【经验】。所以「保留多久」这个问题必须先拆成「热窗口多长」与「冷数据多久访问一次」两个问题。

第三个：「副本数就是可靠性」。副本数决定的是「机器坏掉时数据在不在」，不决定「确认写入时数据在不在」——后者由确认策略（acks）与最小同步副本数共同决定。两个配置分开看都对、合在一起看才有效。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式 | 是「只追加、只读历史」的事件流，还是需要原地更新状态；是否要求每条消息可被单独追踪 | 「消息队列就是发完即删」——流式存储的持久层是可回放的日志，删除是保留策略的结果，不是消费的结果 |
| 访问模式（顺序消费 / 回放 / 点查） | 读取是「从头到尾按位点推进」，还是「随机跳到某个历史时刻」；这决定存储层能否只做顺序 IO | 「能存就能查」——按位点顺序读和按业务主键点查，是两种完全不同的存储结构 |
| 保留时长与成本归属 | 热窗口多长、冷数据多久被访问一次、存储费算在哪个团队账上 | 「保留久一定贵」——真实成本由热窗口大小与冷数据访问频率决定，不由保留时长单独决定 |
| 一致性 / 顺序 / 投递语义 | 是否需要分区内严格有序、是否需要不丢不重、是否需要与业务库变更原子生效 | 「acks=all 就等于不丢」——它只保证已确认的写入不丢，不保证生产端在重试时不会写出重复 |
| 规模与弹性要求 | 峰值吞吐、分区数量级、扩容是否需要搬数据、能否按量付费 | 「分区越多越能扛」——分区数是元数据与运维成本的放大系数，不是免费的并行度 |
| 团队技能与运维能力 | 是否有能力运维有状态存储集群、做容量规划与故障演练 | 「架构越先进，运维越省」——分离式与无服务器架构把运维成本从「机器」搬到了「排障路径」上 |

### 3.2 模式逐个拆解（核心节）

原文件列出 8 个模式，本节逐个拆成 8 个小节，每个模式给足约束、结构、机制、代价、失效点与真实使用。

#### 3.2.1 Kafka 经典架构（单体）

- **被什么约束逼出来**：需要一份高吞吐、可回放、分区内有序的持久日志，且团队有能力运维若干台带本地盘的机器——不看云厂商的对象存储脸色，也不要求跨机架级别的弹性。
- **结构**：

```text
Kafka 经典架构（单体：Broker 自带持久磁盘）
  Producer ──► ┌──────── Broker 集群（数台节点）─────────┐
               │ Partition P0  日志：[Segment][Segment]… │ ← 顺序追加
               │   leader = B1   ISR = {B1,B2,B3}         │
               │ Partition P1   leader = B2   …           │
               └──────────────────────────────────────────┘
                          ▲ 元数据：ISR / leader / topic 配置
                          │  外部协调系统
  Consumer Group：Partition 与组内消费者一一绑定（并行度上限 = Partition 数）
  ────────────────────────────────────────
  约束落点：持久层 = Broker 本地磁盘；扩容 = 把 Partition 迁到新 Broker
```

- **为什么有效（因果句）**：因为每个 Partition 是一条只追加的顺序日志、消费位点由消费者自己持有，所以 Broker 不需要为每个消费者维护投递状态，读取退化为「按 offset 顺序读文件」；代价是这一切都建立在「Partition 的日志就在这台机器的这块盘上」这个假设之上。
- **代价**：扩展的基本单位是 Partition，而 Partition 是物理绑定在 Broker 磁盘上的——加机器不等于加容量，必须搬数据（副本同步与 Leader 迁移）；本地磁盘的价格与容量上限由机器规格决定，无法只对存储单独扩容。
- **失效点**：当单集群的存储需求增长到「必须扩机器才能放下」时，「顺序写 + 本地盘」的成本优势会反转成「扩容即搬迁」，因为数据位置被 Partition 与 Broker 的绑定关系锁死，每一次扩容都要把已有 Partition 的副本复制到新节点并切换 Leader，搬迁流量与业务流量争抢同一块磁盘与网络；集群越大，单次扩容能一次做成的概率越低。
- **真实使用**：Kafka 由 LinkedIn 内部孵化后开源，随后进入 Apache【公开】（可查 Apache Kafka 官方项目页的发布历史）。它仍是绝大多数实时链路的主干道【经验】，尤其在「已有机器资源、团队熟悉 JVM 运维」的组织里。

#### 3.2.2 Kafka KRaft 无 ZK 架构（2022+）

- **被什么约束逼出来**：元数据规模增长到「外部协调系统撑不住」——大量 Topic 与 Partition 让元数据变更成为集群操作的瓶颈，同时运维两套分布式系统（消息集群 + 协调集群）的成本高。
- **结构**：

```text
KRaft 无 ZK 架构（元数据自己也是一条日志）
  ┌──── Controller Quorum（Raft，3 或 5 节点）────┐
  │  活跃 Controller ──► 元数据日志（追加写）      │
  │  状态机回放 ──► 内存元数据 + 快照             │
  └───────────────────┬──────────────────────────┘
                      │ 元数据变更：建 Topic / ISR / Leader
                      ▼
  ┌──────────── Broker 集群（只跑数据面）────────┐
  │  Partition 副本读写、日志存储（与经典架构同） │
  └──────────────────────────────────────────────┘
  ────────────────────────────────────────
  关键：元数据不再写进外部协调系统，而是集群内部一条可回放的日志
        → 元数据变更 = 追加 + 广播，变更后靠回放重建内存状态
```

- **为什么有效（因果句）**：因为元数据被统一成一条由 Raft 复制的日志，所以元数据的变更路径与数据面解耦、可回放、可快照重建，集群不再需要在两套系统之间做一致性协调；代价是引入了一个新的、对多数派敏感的控制器集群。
- **代价**：控制器是新的故障域与容量规划对象——它的 quorum 规模、磁盘与网络都要求独立规划；升级与迁移期需要一次性做元数据格式切换，且切换是不可逆的（回退需要重建集群）。
- **失效点**：当控制器 quorum 失去多数派（可用的控制器节点少于一半）时，「元数据自管理、可扩展」会反转成「集群不可变更」，因为 Raft 需要多数派才能提交日志——此时已有 Partition 的读写仍能继续，但建 Topic、扩 Partition、Leader 选举、ISR 收缩全部停摆；故障表现是「业务看起来还活着，但任何运维动作都做不了」。
- **真实使用**：KRaft 由 KIP-500 引入，Kafka 2.8（2021）以早期访问形态提供、3.3（2022）宣布生产可用【公开】（以 Apache Kafka 官方发布说明为准）；新集群默认走 KRaft 是当前的主流选择【经验】。

#### 3.2.3 Kafka Tiered Storage（分层存储）

- **被什么约束逼出来**：数据必须长期保留（合规、审计、事件回溯），但本地磁盘的价格与「扩容要搬数据」这两条约束同时存在——需要让存储上限不再由 Broker 磁盘决定。
- **结构**：

```text
Tiered Storage（同一个 Partition 的日志被切成两段存储）
  Partition 日志（逻辑上是一条连续的 offset 流）
  ├── Local（Broker 磁盘）：最近 N GB / 最近 N 小时 —— 热，顺序读极快
  └── Remote（对象存储）  ：更早的 Segment          —— 冷，按需取回
  读路径：
    消费者追在本地尾部   → 只读本地，延迟与不分层时相同
    消费者落后到已卸载区 → Broker 直接从对象存储取，不触发全量回迁
  ────────────────────────────────────────
  约束落点：本地磁盘只保留「正在被频繁读的窗口」，容量上限改由对象存储决定
  前提：上传与读取都走对象存储 API，因此受其延迟与出流量计费影响
```

- **为什么有效（因果句）**：因为日志天然是顺序的、Segment 天然是不可变的整块文件，所以「旧段整体上传、需要时整体取回」不需要任何格式转换，分层只是把存储介质从本地盘换成对象存储；代价是这条日志的读取延迟不再均匀——本地读是微秒到毫秒级，远程读要经过对象存储请求与网络传输。
- **代价**：多了一个分层组件与一份远程元数据要维护；冷读路径的延迟与出流量费用进入成本模型；卸载策略（何时卸载、卸载多远）成为需要调参并回归验证的配置项。
- **失效点**：当出现「消费者长时间停滞后追赶」或「重放很久以前的历史」时，「低成本长期保留」会反转成「回归性能问题」——本地没有这段数据，每一个被读取的冷段都要向对象存储发起请求，恢复速度从「被本地磁盘带宽限制」变成「被对象存储的请求延迟与吞吐限制」，追赶一小时的积压可能变成数小时；因为冷读路径的首字节延迟比本地 PageCache 高若干数量级，且这个代价与被跳过的数据量成正比【经验】。
- **真实使用**：Kafka 的分层存储由 KIP-405 定义，3.6（2023）以早期访问形态发布、后续版本转入生产可用【公开】（以 Apache Kafka 官方发布说明为准）；典型使用场景是合规与审计所需的长期保留【经验】。Pulsar 侧也在较早版本就提供分层卸载能力【公开】（可查其官方文档的 tiered storage 章节）。

#### 3.2.4 Pulsar 计算存储分离

- **被什么约束逼出来**：多租户、云原生部署，要求计算与存储能各自独立扩缩容，且节点故障后恢复要快——不能出现「扩容要搬数据」这种把扩容与数据量绑在一起的操作。
- **结构**：

```text
Pulsar 计算存储分离
  Producer / Consumer ──► Broker（无状态，可随时增减）
                             │ 读写都经网络到独立存储集群
                             ▼
  ┌──────────── BookKeeper 集群（有状态，隔离部署）────────────┐
  │  Ledger（一个 Partition 的连续片段，追加写）               │
  │  写 quorum 示例：WQ=3 / AQ=2（写 3 份，等 2 份确认即返回） │
  └────────────────────────────────────────────────────────────┘
  元数据层（ZooKeeper 等）：Broker 归属、Topic 归属、Ledger 位置
  ────────────────────────────────────────
  关键：Broker 无状态 → 扩容与故障转移都不搬数据
        代价：每次读写都多一跳网络，必须由存储集群扛住聚合吞吐
```

- **为什么有效（因果句）**：因为 Broker 不持有持久状态、只负责协议与投递，所以计算层可以按流量弹性伸缩、故障节点可直接被替换而不涉及数据复制；代价是把「顺序写本地盘」换成了「写一个远程的、需要 quorum 确认的存储集群」。
- **代价**：写放大——一条消息要写 WQ 份并等待 AQ 份确认才算落定（示例配置见上）【经验】；网络往返进入关键路径，P99 延迟对存储集群与网络的健康度高度敏感；运维面从一套集群变成三套（Broker / 存储 / 元数据）。
- **失效点**：当存储集群出现局部热点或单个存储节点慢时，「计算存储独立扩展」会反转成「木桶效应」——Broker 侧扩容无法改善写入延迟，因为延迟的决定权已交给存储集群的 quorum 确认路径；慢节点会通过 AQ 等待把尾延迟传导到所有相关分区，而扩容 Broker 只会增加对同一个存储集群的压力。
- **真实使用**：Pulsar 由 Yahoo 开源，2018 年成为 Apache 顶级项目【公开】（以 Apache 官方项目页为准）；云原生与多租户场景采用较多【经验】，选型时常见理由是「计算与存储要能分别买单」。

#### 3.2.5 AutoMQ / Warpstream（云原生无服务器）

- **被什么约束逼出来**：云上成本结构变了——对象存储的容量单价与本地盘相差一个数量级，而按量付费要求集群能在低峰期真正缩到很小；同时团队不想再承担「扩容要搬数据」与「按峰值预留机器」的成本。
- **结构**：

```text
云原生无服务器流存储（对象存储是唯一持久层）
  Producer ──► 无状态接入层（可秒级弹性 / 按量付费）
                    │
                    ├── 写入缓冲 / 预写日志（内存或小规格块设备，
                    │   用于把对象存储的高延迟挡在确认路径之外）
                    ▼
           对象存储（容量近乎无限、按量付费、天然多副本）
  ────────────────────────────────────────
  关键差别：本地磁盘从「持久层」降级为「可丢弃的缓存」
            → 节点挂掉不需要搬数据，只要能读到对象存储就能接续
  两种落法：
    ① 对象存储是唯一持久层（写路径上依赖缓冲遮蔽延迟）
    ② 本地盘做有限期 WAL，随后转对象存储
```

- **为什么有效（因果句）**：因为持久层换成了按量付费的对象存储，所以「按峰值预留磁盘」这件事被消掉了，节点在无流量时可以缩到零、故障节点可以直接替换而不涉及数据搬迁；代价是写入确认路径上多了一层高延迟介质，必须靠缓冲与批处理把它的延迟藏起来。
- **代价**：延迟的下限由对象存储的首字节延迟与批处理策略共同决定，小消息高频写入的形态最难优化；多租户共享对象存储时，成本与限流进入同一份账单；排障路径变长——延迟高时要在「接入层缓冲」「对象存储限流」「网络」之间定位。
- **失效点**：当工作负载是「高频小消息、要求毫秒级端到端确认」时，「无本地磁盘、按量付费」会反转成「延迟受介质支配」；因为确认写入必须经过对象存储（或依赖一层会把消息攒成批的缓冲），批处理越大成本越低、延迟越高，两者在同一个旋钮上反向耦合，任何「既要低延迟又要极致成本」的配置都只能取折中。
- **真实使用**：AutoMQ 于 2023 年开源，主打用对象存储替换 Kafka 的本地存储层【公开】（可查其官方仓库与文档）；WarpStream 走「BYOC + 对象存储直接作为持久层」的路线【公开】（可查其官方文档对架构的描述）。这类实现的共同前提是**兼容 Kafka 协议**，从而复用既有生产者与消费者生态【经验】——这也意味着选型时的风险不在协议，而在延迟与成本的实际曲线。

#### 3.2.6 RocketMQ 事务消息

- **被什么约束逼出来**：业务侧需要「本地数据库写入」与「消息投递」原子生效——订单创建了但消息没发出去（或反过来）会造成下游状态不一致，而引入分布式事务协调器成本过高。
- **结构**：

```text
RocketMQ 事务消息（两阶段提交 + 状态回查）
  ① 发半消息（Half Message）→ 进驻 Broker 但对消费者不可见
  ② 生产者执行本地事务（例如写业务库的订单表）
  ③ 生产者按本地事务结果提交或回滚二选一
        ├── Commit   → 半消息转为可见，消费者可消费
        └── Rollback → 丢弃半消息
  ④ 若 ③ 没有到达 Broker（进程崩溃 / 网络中断）
        → Broker 定时回查生产者的本地事务状态，
          生产者查自己的本地事务表后回答，再决定 Commit / Rollback
  ────────────────────────────────────────
  关键：Broker 不裁决业务事务，只保证「消息可见性」与
        「业务侧本地事务最终一致」这两件事不脱节
```

- **为什么有效（因果句）**：因为消息先以「不可见」的形态落盘、再由业务侧的真实结果决定是否转可见，所以消费者只会看到「业务确实提交了」的消息，实现了本地事务与消息投递的最终一致；代价是事务的**判定权在业务侧**，Broker 只能回查、不能裁决。
- **代价**：每个生产者的本地事务必须可被回查（要有事务状态表，并保证回查接口幂等）；消费侧仍需幂等，因为「消息已提交」不等于「下游只处理一次」；多了一套事务状态与回查超时的运维观测项。
- **失效点**：当业务侧的本地事务状态无法被可靠回查（回查接口不稳定、状态表被清理、生产者实例长期下线）时，「最终一致」会反转成「不确定悬挂」，因为半消息的归宿只能由回查结果决定——回查得不到答案时，消息会长期停留在半消息状态：既不被消费，也不被删除，占用存储且让下游看到的状态与业务库不一致。这个失效模式不会立刻报错，只会表现为「某类订单的下游动作偶尔缺失」。
- **真实使用**：RocketMQ 由阿里开源并进入 Apache【公开】（可查 Apache 官方项目页）；事务消息是其官方文档中独立成章的能力【公开】（可查官方文档「事务消息」章节），电商订单与资金相关链路采用较多【经验】。

#### 3.2.7 流批一体存储（Paimon / Fluss）

- **被什么约束逼出来**：同一条数据要被两种方式使用——实时链路要「秒级可见」，离线链路要「可批量重算、可回溯到某个时刻」。分别建两套存储意味着两份数据、两套口径和两次 ETL。
- **结构**：

```text
流批一体存储（用流的写入方式 + 表的读取方式）
  Kafka（事件流）──► Flink（流式写）──► Paimon / Fluss（表格式）
                                              │
                                    持续产生快照（snapshot）/ 小文件
                                              ▼
                          查询引擎（批读与流读读同一份数据）
  ────────────────────────────────────────
  关键：一条管道同时满足「秒级可见」与「可批量重算」
        代价：表侧必须持续做 compaction（合并小文件 + 清理过期快照）
  与纯事件流的区别：
    事件流：事实按写入顺序排列，读的是「发生了什么事」
    流式表：事实按主键归并出当前状态，读的是「现在是什么样」
```

- **为什么有效（因果句）**：因为写入侧保持追加语义（新快照追加、旧快照延迟清理），而读取侧按快照提供一致性视图，所以实时写入与批量重算读的是同一份物理数据；代价是这套「追加 + 快照」的结构必须由持续的后台合并来维持，否则文件数会无限增长。
- **代价**：compaction 是常驻成本（CPU、IO 与调度），且与写入争抢资源；快照保留策略一旦放长，存储会以「每次写入都留一份历史」的速度增长；调参项多（文件大小阈值、快照保留数、合并频率），参数不合适时要么小文件堆积、要么合并永远追不上写入。
- **失效点**：当写入速率长期高于合并能力时，「流批共用一份数据」会反转成「读放大与查询抖动」——查询要先跨过大量小文件才能拼出一个完整视图，元数据操作成为瓶颈，表现为「写入没变慢，查询忽快忽慢」；因为快照与文件数随写入线性增长，而合并是后台尽力而为的，两者之间没有硬性背压。
- **真实使用**：Apache Paimon 前身为 Flink Table Store，2023 年更名并成为独立项目【公开】（可查 Apache Paimon 官方项目页）；Apache Fluss 于 2024 年进入 Apache 孵化器，定位为流式原生存储【公开】（以 Apache 官方项目页为准）。湖仓侧同时提供流式读写格式的方案还有 Iceberg 等【公开】（可查 Apache Iceberg 官方项目页的流式写入与增量读取文档，具体能力边界与版本支持以官方文档当前版本为准）。

#### 3.2.8 Event Sourcing（事件溯源）

- **被什么约束逼出来**：需要回答「当时到底发生了什么」——审计、合规、事故重放、以及「同一份事实要供多个下游按不同方式聚合」；而只保存当前状态的表会在每次更新时丢掉历史。
- **结构**：

```text
Event Sourcing（事实不可变，状态是投影）
  命令 ──► 事件（append-only 日志，永不修改、永不删除）
              │
              ├──► 投影 A：当前状态表（读模型，可随时重建）
              ├──► 投影 B：审计 / 合规视图
              └──► 投影 C：下游分析（湖仓 / 实时数仓）
  ────────────────────────────────────────
  关键：状态可以被删掉重算，事件不行；
        所以「改数据」在这个模型里只能表现为「追加一条补偿事件」
  投影的代价：每个投影都要自己维护位点、幂等与重放能力
```

- **为什么有效（因果句）**：因为事实只追加不修改，所以任何读模型都可以随时被丢弃并从事件流重建，同一份事件能同时支撑状态查询、审计与重算；代价是「当前状态」不再是数据的源，而是一个需要持续维护、可被重建的副本。
- **代价**：读模型数量与维护面成正比，每个投影都要处理位点、重复消费与重建；事件 schema 一旦发布就进入兼容性约束（旧事件永远存在）；存储按「事件数量」增长，而不是按「实体数量」增长。
- **失效点**：当事件 schema 演进而重放路径没有版本转换（upcast）机制时，「全量可重放」会反转成「重放不动」——早期事件按旧结构写入，新代码读不了它们，于是「从零重建读模型」这个本来最大的优势变成不可执行的操作；因为事件是不可变的，修正只能靠补写转换逻辑或追加补偿事件，历史越长这个缺口越大。
- **真实使用**：以事件日志作为事实源、状态由投影生成，是流式架构中被广泛采用的模式【经验】；Kafka 的长保留与分层存储让它在大规模下变得可行【经验】。金融与审计场景采用较多，因为「可复现当时状态」通常是合规硬要求。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 传统企业本地部署、机器资源已有 | Kafka 经典架构 | 不选分离式：没有弹性与多租户需求，却要多运维两套集群 | 峰值可预估，扩容频率低，团队熟悉 JVM 运维 |
| 云原生 / 多租户、计算与存储要分别买单 | Pulsar 计算存储分离 | 不选单体：租户隔离与独立扩缩容在单体上做不干净 | 需要租户级隔离，且存储与计算的增长速度不同 |
| 业务要「本地事务与消息」原子生效 | RocketMQ 事务消息 | 不选普通投递：需要自己在消费侧补偿，一致性责任散落到各个消费者 | 存在明确的本地事务边界，且能提供幂等回查接口 |
| 云上 Serverless、成本要求按量 | AutoMQ / Warpstream 等对象存储实现 | 不选自建单体：按峰值预留磁盘的成本结构不划算 | 能接受批处理换来的延迟下限，且负载不是高频小消息 |
| 长期保留 / 合规 / 审计 | Kafka Tiered Storage | 不选只删数据或只加磁盘：删数据违反合规，加盘遇到扩容搬迁 | 冷数据访问频率低，热窗口可量化 |
| 流批一体 / 实时数仓 | Kafka + Flink + Paimon / Fluss | 不选「流一份、批一份」双写：两份数据必然产生两套口径 | 同一份数据同时需要秒级可见与可重算 |
| AI Agent 事件流（tool call / action 需回放） | Kafka + 长保留（配合分层存储） | 不选短保留队列：Agent 的轨迹需要可回放、可审计 | 事件需要被重放用于评测、复盘与审计 |
| 海量日志采集 | Kafka / Pulsar + Connect 类采集 | 不选让业务系统直写数仓：耦合且无法削峰 | 日志量大、消费者多、允许秒级延迟 |

本主题下**最常被误选的一对是「Pulsar 计算存储分离」与「Kafka 经典架构」**：把「分离」当成普遍更优的架构而选它，随后发现全部读写流量都要跨网络到独立存储集群，而团队既没有多租户需求、也没有「计算与存储分别扩」的真实痛点——得到的只是更高的网络依赖与三套集群的运维面。反向的误选同样常见：业务确实需要独立扩存储（例如存储增长远快于流量增长），却仍用单体架构，于是每次扩容都在做数据搬迁，扩容节奏被搬迁窗口限制。判据只有一条：**你的存储增长是否真的与流量增长脱钩**；若两者同比例增长，分离带来的收益接近于零。

### 3.4 组合模式：真实系统不会只用一种

**组合一：日志主干 + 分层存储 + 入湖。** 构成是「Kafka（短保留热窗口）+ Tiered Storage（冷段落对象存储）+ Connect 类采集入湖」，职责边界是「Kafka 负责秒级投递与回放，湖仓负责长期结构化分析」；运维代价是多了一条「冷读路径」要观测（追赶延迟、出流量费用）；适合的规模是中大型组织，数据保留需求超过本地磁盘能承受的范围。

**组合二：分离式集群 + 多租户 + 分层卸载。** 构成是「Pulsar 计算存储分离 + 租户级隔离 + 冷数据卸载到对象存储」，职责边界是「Broker 承担协议与隔离，存储集群承担持久化，对象存储承担长期保留」；运维代价是三套集群同时在线，且尾延迟的排障要跨 Broker 与存储两侧；适合的规模是提供流服务给多个内部团队或外部租户的平台型组织。

**组合三：事务消息 + 长保留事件流。** 构成是「RocketMQ 事务消息保证业务一致性，Kafka 长保留承载事件溯源与回放」，职责边界是「一致性走事务消息、可回放走事件流」，两者以业务主键对齐；运维代价是同一份业务事实在不同系统里各存一份，需要明确的「哪份是权威源」的约定，否则排查时会出现两个不一致的真相；适合的规模是交易类业务已经用了事务消息、同时又要做事件回溯与审计的场景。

### 3.5 反模式与失效分析

原文件列出的 8 条反模式全部保留，逐条补齐「症状 → 后果 → 成因 → 修法」。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| Topic 设计过细 / 过粗 | 过细：Topic 数量随业务表增长；过粗：一个 Topic 里混着多种消费语义 | 过细时分区内并行度被切碎、元数据与运维面按 Topic 数放大；过粗时消费者被迫读不需要的数据，还会被不相关的写入拖慢位点 | 按数据表而不是按业务域划分 Topic | 按业务域划分（如订单 / 用户 / 支付），同一域内用消息类型字段区分 |
| Partition 数不足 | 消费者组内有的消费者空转，写入端出现发送超时 | 并行度上限就是 Partition 数，分区数不够时空转消费者无法分担负载；扩容分区会改变同一 key 的分区映射 | 按当前峰值而不是未来峰值规划 | 按「峰值吞吐 ÷ 单分区实测吞吐」估算并预留余量；单分区吞吐以自己压测为准【经验】，不要照搬常数 |
| 副本数不足 | 一台 Broker 下线即出现分区不可用 | 副本数决定「机器故障时数据在不在」；副本数太少时任何一次节点故障都直接变成业务中断 | 为省磁盘与网络而压副本数 | 副本数至少 3（容一次节点故障后仍有 2 份可供确认）【经验】，并配合最小同步副本数与确认策略一起设定 |
| 忽视 ACK 设置（确认策略） | 压测跑得很好，故障演练时丢消息 | 确认策略决定「返回成功时数据落在几份副本上」：只等主副本确认时，主副本故障会丢掉已返回成功的写入 | 为了延迟把确认调低，没有区分业务等级 | 关键业务用「等所有同步副本确认 + 最小同步副本数约束」，非关键链路再放松 |
| 消费者未做幂等 | 重平衡或重试后出现重复订单 / 重复计数 | 投递语义是「至少一次」，重复不可避免；没有幂等键时重复会直接变成业务重复 | 把「消息只发一次」当成默认保证 | 消费端用主键去重或状态表实现幂等，别把幂等寄托在「不重复投递」上 |
| 未做监控告警 | Lag 突增、Broker 掉线靠业务方投诉才发现 | 流式系统的故障多表现为「延迟累积」而不是「报错」，没有 Lag 与磁盘监控就没有可观测性 | 把中间件当成不需要监控的基础设施 | 监控消费 Lag、Broker 健康度、磁盘水位、ISR 收缩与重平衡事件 |
| 不分层存储 | 磁盘水位持续攀升，扩容节奏被数据保留需求推着走 | 全部数据留在本地盘的架构里，存储成本与保留时长线性耦合，扩容必须搬数据 | 保留需求是后加的，初始架构没留分层出口 | 引入分层存储：本地只留热窗口，冷段卸载到对象存储 |
| 滥用 Topic 数量（把 Topic 当表用） | Topic 数量与业务表数量同阶 | 每个 Topic 的分区副本都要占元数据与文件句柄，数量越多启动、重平衡、元数据操作的代价越高 | 用「一个业务对象一个 Topic」的直觉代替了流建模 | 合并相关 Topic，用 schema 区分消息类型；确需隔离时再用多租户或命名空间隔离 |

三条最危险的反模式，在生产中的典型暴露方式：

**「忽视 ACK 设置」** 的暴露方式通常是「平时没事，一次机器故障丢一批数据」。机制是：确认策略决定了写入返回成功的最低保证，如果只等主副本确认，那么在主副本故障切换时，那些「已返回成功但还没同步到其他副本」的写入就消失了——而生产端已经在业务库里把这条消息标记为已发送。它的隐蔽性在于压测完全发现不了：压测不杀节点。验证方法是做一次故障演练（强制杀掉主副本所在节点），观察是否有已确认写入丢失。

**「消费者未做幂等」** 的暴露方式是「数据量对不上，且对不上得毫无规律」。机制是投递语义本身是「至少一次」：重平衡、网络抖动、消费者重启都会造成同一批消息被重复投递。没有幂等键时，重复会以「重复扣款」「重复计数」的形式出现在业务语义里，而不是出现在中间件指标里。识别方法是查消费者代码里是否存在「按消息唯一键去重」或「状态表条件更新」这两类结构之一。

**「未做监控告警」** 的暴露方式是「故障以业务指标变差的形式被间接发现」。流式系统的故障很少表现为请求失败，而是表现为消费 Lag 缓慢累积、或者磁盘水位逼近上限；等到业务方发现数据没更新，问题往往已经积累了数小时。最小可用的监控集合是：每个消费者组的 Lag、Broker 节点存活与磁盘水位、ISR 收缩次数、重平衡次数——这四类指标能覆盖绝大多数「静默退化」。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的。分区数量级、保留时长、租户数、延迟要求跨过某个量级时，原来正确的模式会开始产生结构性错误。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单集群磁盘不够装要保留的数据 | Kafka 经典架构 | 扩容必须搬迁 Partition，存储增长与扩容节奏绑死 | 加分层存储（旧段卸载到对象存储） | 新增冷读路径与出流量费用，追赶延迟成为新的观测项 |
| 元数据规模（Topic / Partition 数）上量 | 外部协调系统管元数据 | 元数据变更成为集群操作瓶颈，且要运维两套分布式系统 | KRaft（元数据内部成一条日志） | 需一次性切换元数据格式且不可回退；控制器 quorum 成为新的规划对象 |
| 从单租户到多租户 | Kafka 经典架构 | 租户之间无法独立扩缩容与隔离故障 | Pulsar 计算存储分离 | 迁移要重做投递路径与运维体系，多两套集群要观测 |
| 从「按峰值预留」到「按量付费」 | 自建集群 + 本地盘 | 低峰期资源闲置，磁盘按峰值成本买单 | 对象存储为持久层的实现（AutoMQ / Warpstream 类） | 延迟下限被介质决定，小消息高频形态需重新压测 |
| 从「只投递」到「本地事务与消息要一致」 | 普通投递 + 消费侧补偿 | 一致性责任散落到每个消费者，补偿逻辑重复实现 | 事务消息 | 生产者必须提供幂等的状态回查，并新增事务观测项 |
| 从「流一份、批一份」到统一口径 | 双写（流一套、批一套） | 两份数据必然产生两套口径，对账成本持续存在 | 流批一体表格式（Paimon / Fluss 类） | 引入常驻 compaction 成本与快照保留策略调参 |
| 从「消费后即可丢」到「需长期回溯」 | 短保留 Topic | 事故无法复现、Agent 轨迹无法回放 | 长保留 + 分层存储 | 存储成本模型改写，位点管理与重置能力要补齐 |

### 3.7 自检清单

- [ ] 每个 Topic 是否对应一个业务域，而不是一张业务表？按表建 Topic 即属于把 Topic 当表用。
- [ ] Partition 数是否按「峰值吞吐 ÷ 单分区实测吞吐」估算并留了余量？单分区吞吐以自己压测为准，不要照搬常数。
- [ ] 副本数是否 ≥ 3，且最小同步副本数与确认策略是否配套设定？三个配置分开看都对、合起来才有效。
- [ ] 关键链路的确认策略是否等所有同步副本？只等主副本确认时，节点故障会丢掉已返回成功的写入。
- [ ] 消费者是否具备幂等能力（唯一键去重或状态表条件更新）？投递语义是至少一次，重复不可避免。
- [ ] 是否监控了每个消费者组的 Lag、Broker 存活与磁盘水位、ISR 收缩与重平衡次数？
- [ ] 是否有分层存储（本地只留热窗口）？没有分层时，保留需求会直接变成扩容搬迁。
- [ ] 保留策略是否按「热窗口多长 + 冷数据多久被访问一次」两个问题分别定义，而不是只写一个天数？
- [ ] 是否做过「杀掉主副本节点」的故障演练，并验证了已确认写入没有丢失？
- [ ] 分区键是否选用了能保证同一业务实体有序的字段（如实体 ID）？用随机值会牺牲顺序保证。
- [ ] 若使用了事务消息，生产者的本地事务状态是否可被幂等回查？回查不可靠会让消息悬挂在半消息状态。
- [ ] 若使用流批一体表格式，compaction 是否跟得上写入速率？跟不上时表现是查询抖动而不是写入变慢。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 机器已有、峰值可预估、扩容不频繁 | Kafka 经典架构 | 顺序写本地盘的成本最低，代价是扩容必须搬数据 |
| 元数据规模大、要少运维一套系统 | KRaft | 元数据成为集群内部一条可回放日志，代价是控制器多数派成为新故障域 |
| 保留久但访问稀 | Tiered Storage | 不可变的顺序段可整块迁移介质，代价是冷读延迟不均 |
| 存储增长与流量增长脱钩、要多租户 | Pulsar 计算存储分离 | Broker 无状态使扩容不搬数据，代价是每次读写跨网络与写放大 |
| 按量付费、能接受更高延迟下限 | 对象存储为持久层的实现 | 持久层按量付费、节点可丢弃，代价是延迟受介质与批处理支配 |
| 本地事务要与消息原子生效 | RocketMQ 事务消息 | 消息可见性由业务真实结果决定，代价是判定权在业务侧 |
| 同一条数据要秒级可见又可重算 | 流批一体表格式 | 追加写入 + 快照读取共用一份数据，代价是常驻 compaction |
| 需要回答「当时发生了什么」 | Event Sourcing + 长保留 | 事实只追加、状态可重建，代价是 schema 兼容成为长期约束 |

> 本节小结：本主题下**决定模式选择的唯一那条约束，是「持久层放在哪里」**——Broker 本地磁盘、独立存储集群、还是对象存储。它同时决定了扩容是否要搬数据、保留时长如何影响成本、以及延迟的下限在哪里；确认策略与副本数决定的是「你的数据在故障中会怎样」，与持久层选型是两条独立的轴，不能用一个配置项互相顶替。
