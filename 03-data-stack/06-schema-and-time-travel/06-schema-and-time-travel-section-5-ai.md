## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是**没有时间维度**。同一个清单里，「AI 驱动的 Schema 推断」与「Variant / 向量类型进表格式」被并列成两条方向，可规划性差一个量级：后者是表格式规范里的一次类型决定，状态写在规范文档与引擎 release note 里；前者是「让模型猜结构」，它的正式能力项在哪儿都还没有。

第二个问题是清单把机制差异抹平成了同一类词。§7.3 把本主题的差异归到四条机制上——**列的身份**是名字还是编号（§7.3.1）、**兼容性判定**发生在写入侧还是读取侧（§7.3.2）、**历史**是引用计数还是副本（§7.3.3）、**变更的表示**把代价记在写侧还是读侧（§7.3.4）。本节要评估的方向里，AI 对这四条机制**一条都没有改**。它改的是另外三件事：Schema 的**起草者**、表里要装的**数据形态**、以及要**复现的对象**。

本主题的「前沿」之所以还是前沿，卡点在既有栈上：主文件 §1.2 的痛点（上游加字段、下游全部报错；每次变更都要建新表再迁移；误操作无法恢复；AI 训练无法复现）在表格式出现之后已被解决了一多半——这恰好说明本主题的核心机制是**成熟的**，不需要 AI 来救。真正没被解决的只有 AI 带来的三件事：(a) 结构改由模型起草，起草量放大后评审与语义信息成为新瓶颈；(b) 表里要装的数据形态不再由建模规范定义，而由模型与上游应用定义；(c) 复现的边界从「一份数据」扩到「数据 + 代码 + 参数」。本节评估的就是这三件事，以及围绕它们的那十几个方向。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（或版本化发布的规范）；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期。
- **L2 可试点**：①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

判据 ② 在本主题尤其难过，原因值得先说清：**表格式与序列化规范大多由项目或厂商自己发布并维护**，「谁在生产里用了、效果如何」这类材料要么是建设方自述，要么根本不公开。所以本主题的绝大多数方向会停在 L2——这不是保守，而是判据的必然结果。**② 只有「满足」与「降为 L2」两种命运**：既不能改成「有公开生产记录」，也不能靠「本节只评估某一层」把它的适用范围缩小来绕过去。

另有一条评级规则，全节通用：**合并方向取最弱子项**。「Schema 自动生成 + 兼容性自动测试」就是一条合并项，本节把它拆成「兼容性自动测试与 CI 门禁」与「Schema 自动生成」两行分别评级——拆开是因为这两半的行动建议正好相反：一半现在就能做，一半只能观望。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |

**本节没有一行达到 L1。** 四行 L2 全部卡在同一条判据上：②（第三方非厂商公开生产案例）拿不出。其中「Schema 演进与 Time Travel 本身」「兼容性自动测试与 CI 门禁」「联邦 Schema 管理」三行的 ①③ 最干净——规范版本化、文档可查、接口形态也已固定；「半结构化类型进表格式」这一行还额外差在判定标准未成共识（各格式各自定义该类型语义）。本节能确认的是**机制存在且接口稳定**，不能确认的是**别人用了多久、付了什么代价**。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式规范或 release note 能不能找到？找不到 → L3。
2. 厂商之外的证据能不能找到？找不到 → L2。
3. 接口明年会不会变？会变 → 至多 L2。

第 3 句在本主题特别容易失手：**表格式规范的版本门槛与引擎的实现进度经常不同步**，同一句 SQL 在两个引擎上、或同一引擎的两个版本上行为不同。判定方法不是看博客，而是看规范文档里该能力标记为正式还是提案，以及引擎 release note 里它出现在哪一版。

三个常见误判，排路线图时最容易踩：

- **把「有类型可用」误当成「标准已统一」**：某个引擎支持某个类型，不等于规范里已有该类型，更不等于别的引擎按同一语义读它。
- **把「元数据统一」误当成「类型语义统一」**：统一登记点解决的是「去哪找」，不是「两边的 decimal 精度与默认值规则一致」。
- **把「快照还在」误当成「能复现」**：表格式给的是数据一侧，缺代码与参数版本时复现依然失败（5.2.4）。

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 兼容性判定与登记点：把失败挪到写入侧

- **旧做法与它的卡点**：改表结构是编辑时动作，兼容性靠人或文档记着；不兼容的后果出现在**下游第一次读取**时（§7.3.2 的表：表格式的判定点在读侧）。卡点在于**暴露时间取决于下游的调度频率**——一张每周跑一次的下游作业，坏结构可以潜伏一周，而那时变更已经进了不可变历史，回滚要还原元数据版本，而不是改文件。
- **AI 改变了什么机制**：没有。这一节里唯一有效的机制改动是**把判定点前移**：让「新旧两个 schema」的比较发生在提交这一刻（注册中心的形态），或让「这次写入合不合法」在写入时就被拒绝（表格式的形态）。AI 在这条链路上没有位置。
- **由此得到的**：因为注册时判定只需要两个 schema、不需要读数据，**所以**它能在字节进入链路之前给出确定答案，不兼容的变更根本发不出去；**并且**因为判定不依赖下游是否跑过，**所以**「谁承担阻塞」从下游变成了写入侧（§7.3.2 的表）——这是本节唯一一条现在就能排进路线图的动作。用它之前必须先确认两件事：列身份是编号还是名字（决定改名是一次纯元数据编辑，还是一次需要读侧配合的操作，§7.3.1），以及消费者最多落后几个版本（决定选非传递还是传递级别：非传递级别只与最近一次注册的版本比较，消费者落后一个以上版本时 FULL 并不足够，§7.3.2）。
- **由此付出的**：判定看不见语义——字段名与类型都没变、单位从元改成分，检查全绿（§7.3.1 的失效条件）；因此门禁必须与列注释、单位、血缘这类**语义信息**配套，而它们的维护成本正是元数据侧那一项（§7.4）。第二项代价更现实：当消费者全部同步升级时，注册时判定是纯阻塞、收益为零——此时该补的不是更严的检查，而是写入侧的准入白名单。
- **证据与来源**：【公开】Confluent Schema Registry 的兼容级别定义（官方文档；级别清单随产品版本演进，以当前版本为准）；【公开】Apache Avro 规范的 schema resolution 规则（官方规范可核验）；【公开】Iceberg 表规范规定字段以 id 标识且 id 不可复用（Iceberg 2018 年进入 ASF 孵化）；Delta 与 Hudi 侧的结构历史分别记在事务日志与 commit 元数据里（Delta Lake 2019 年开源；Hudi 2017 年开源、2019 年进入 ASF）。这几条只证明机制存在，不证明谁在生产里用了多久——本节不指名采用方。
- **成熟度**：**L2**（与 5.1 表「兼容性自动测试与 CI 门禁」行一致）。本节同时覆盖的「Schema 演进与 Time Travel 本身」与「联邦 Schema 管理」两行同为 **L2**，判据同上。

```text
兼容性判定放在哪一侧，决定失败在哪出现
  写入侧判定（注册中心形态）
     提交新版本 ──► 比较新旧两个 schema（不看数据）──► 不兼容：注册不进去
     失败出现在：生产者本地；谁承担阻塞：写入侧
  读取侧判定（表格式形态）
     写入 ──► 只校验元数据合法性 ──► 提交
     下游第一次读取 ──► 按身份投影、缺列补默认值 ──► 不兼容这时才暴露
     失败出现在：下游作业；谁承担阻塞：下游（暴露时间 = 下游调度周期）

判定方法：在预发环境推一次真实变更，记录最早报错的是谁
   生产者报错 → 判定点在写入侧
   下游报错   → 判定点在读取侧
   谁都没报错但数据不对 → 这类变更根本没被判定覆盖（见下面的失效条件）
```

- **失效条件**：当变更不是改名或加列，而是类型收窄与列语义变更时，两种判定点都保护不了你——编号没变、类型可能仍算兼容，下游静默算错。此时要补的不是更严的检查，而是语义信息与变更评审。
- **自验方法**：在测试表上依次做改名、删列、加列，然后用**第二个引擎**读改名前写入的老文件。三个动作都通过，才说明列身份在你的引擎组合里真的稳定（§7.3.1 的自验方法）；只有写入侧引擎通过时，你依赖的是这个引擎的宽容，而不是规范。

判定点定下来之后，剩下的选择就是兼容级别——级别怎么选，取决于消费者的落后程度（判据见 §7.3.2：非传递级别只与最近一次注册的版本比较）：

| 消费者的落后情况 | 该选的级别 | 为什么 |
| --- | --- | --- |
| 全部随发布同步升级，窗口极短 | NONE，或最宽松的 BACKWARD | 没人读旧结构，传递检查是纯阻塞，收益为零 |
| 可能落后 1 个版本 | BACKWARD / FORWARD / FULL | 只与最近一次注册的版本比较，够用 |
| 可能落后多个版本 | BACKWARD_TRANSITIVE / FORWARD_TRANSITIVE / FULL_TRANSITIVE | 非传递级别只比最近一版，落后多版时读不通 |
| 只要求「未升级的消费者能读新数据」 | FORWARD_TRANSITIVE | 单向要求，比 FULL_TRANSITIVE 便宜 |

这张表里唯一需要现场核对的数是「消费者最多落后几个版本」——它不能靠猜，看每个消费进程里缓存的 schema 版本就能数出来。

#### 5.2.2 AI 起草 Schema：换掉的是起草者，不是兼容性语义

- **旧做法与它的卡点**：结构由人设计——读需求、定类型、写 DDL、写注释。卡点有两处：**起草是纯人力**（新建一张宽表要写几十个字段），以及**注释与语义信息没人补**（列名 `amt` 是元还是分、`status` 有哪些枚举值），而后者正是 5.2.1 那道门禁看不见的那一半。
- **AI 改变了什么机制**：改变的是**候选的生成方式**：模型能读业务需求起草 DDL，也能读样本数据猜类型、批量生成列注释与分类。**没有改变的是判定的语义**——AI 起草的结构与人写的结构要过同一道兼容性检查（5.2.1），因为那道检查比较的是两个 schema 的解析规则，与谁写的无关（§7.3.2）。
- **由此得到的**：因为兼容性判定的输入只有 schema 本身，**所以**模型的产出天然被同一道门禁约束——它既不能让不兼容的变更变兼容，也不能让语义丢失被发现；**又因为**起草成本几乎归零，**所以**真正被释放的是**元数据补全**这件事（列注释、单位、分类），而它恰好落在 5.2.1 门禁的盲区上。也就是说，AI 在本主题上最有价值的用法不是「生成结构」，而是「把已有结构写清楚」。
- **由此付出的**：生成量上来之后，评审成为新瓶颈（补全工作量与对象数成正比，§7.4）；更实际的代价是**模型会丢掉类型里的精度与单位**——它倾向于把什么都写成字符串或大整数，而「类型没变、语义变了」正是 §7.3.1 失效条件里那种不报错、只静默算错的变更；另外把样本数据送进模型，多了一条数据出境的边界。
- **证据与来源**：【公开】可核验的正式能力项是「自动生成列注释 / 数据分类」这一类窄能力——它在目录与元数据产品的官方文档里以「列注释 / 标签 / 分类建议」这类名字出现（相关版本在 2024 年前后引入，产品侧见 §4.3 的「元数据目录」；以各产品文档当前版本为准），**把它当作「Schema 推断」是命名混淆**；「从需求生成整份结构」没有可核验的能力级发布，② 更谈不上。判定方法：查产品文档里该项能力的名字与作用范围，以及它是否需要人工确认后才生效。
- **成熟度**：**L3**（与 5.1 表「Schema 自动生成」「AI 驱动的 Schema 推断」两行一致）。这两行都记 L3，但行动建议不同：**补注释与分类现在就能做**（它服务于 5.2.1 的门禁），**让模型决定结构不要做**。

一句话的边界：让模型做「把已有结构写清楚」，不要让模型做「决定结构应该是什么」。前者的错误可以被检查发现，后者的错误以静默算错的形式出现——两者的故障模式不同，所以不能放在同一句「AI 辅助建模」里讨论。

**一个可执行的分解方式**（下面的字段数只是常见量级【经验】）：新建一张 40 字段上下的宽表时，让模型给出字段名、类型候选与注释草稿；人只做三件事——定类型（精度与单位）、定主键与分区、定口径。模型产出的那部分可以出错，因为它们会被检查；人承担的那部分不能出错，因为它们不会被检查到。自验方法是抽查其中 20 个上下【经验】，看有没有「类型名义上正确、语义已经丢了」的例子（金额字段被写成整数、时间字段丢掉时区、枚举被压成自由文本）。

#### 5.2.3 表里要装的东西变了：向量、半结构化与 RAG 文档

- **旧做法与它的卡点**：表里装的是行与列，类型是数值、字符串与时间。AI 场景要求同一张表里装 embedding 向量、半结构化字段，以及「文档 → 表」的映射结构。卡点有三层：**类型系统里没有这些类型**（要靠 `array<float>` 之类的近似表达）；**维度是类型的一部分**（换 embedding 模型就改类型）；**文档结构不在表格式的保护范围内**。
- **AI 改变了什么机制**：改变的是**数据的形态与它的生产方式**：向量的维度由模型决定，而建表时并不可知；半结构化数据由上游应用定义，而不是由建模规范定义。表格式要做的是「把不可控的形态装进可控的容器」，机制上仍然是 §7.3.1 的列身份与 §7.3.2 的判定点，只是被保护的对象换了。
- **由此得到的**：**因为向量的维度被声明在类型里**，**所以**「换一个 embedding 模型」在这套体系里不是换模型，而是一次破坏性的 Schema 变更——它要走 §7.3.2 的兼容性判定，而多数判定规则下这类变更不兼容，于是正确做法只能是「加新列 + 回填 + 双写一段时间 + 切换 + 删旧列」，这是一次完整的迁移，不是一次配置修改。**又因为**检索索引（ANN 一类）不属于表格式的元数据，**所以**它不在表格式的原子提交里——索引必须单独重建，而**回滚表快照不会把索引一起回滚**：这是本方向最容易被忽略的一处不一致。
- **由此付出的**：双列并存期间存储与查询复杂度同时上升（两列、两套索引、两套召回），而这段时间的长度由下游切换速度决定；半结构化字段把类型错误推迟到读取时才发现；RAG 的文档结构（title / content / metadata / embedding）由应用自定义，**表格式不为它提供兼容性保护**，只能靠应用侧契约与它自己的版本管理——这一段是 schema 管理的缺位区，谁做谁负责。
- **证据与来源**：【公开】Confluent Schema Registry 的兼容级别与 Avro 的 schema resolution 规则说明「读侧宽容」的边界（§7.3.2）；【公开】Iceberg 表规范的列身份机制说明改名可以作为纯元数据编辑（§7.3.1）；【公开】Delta 与 Hudi 的结构历史记在事务日志与 commit 元数据中（§7.3.1）。**关于向量类型与半结构化类型本身，本节不给版本断言**——各格式对该类型的状态与版本门槛随版本变化，判定方法是查该格式规范文档中该类型标记为正式还是提案，以及引擎 release note 里它出现在哪一版。
- **成熟度**：**L2**（半结构化类型进表格式：可用但判定标准未成共识，见 5.1 表）；**L3**（向量 Schema 管理、Schema for RAG、Schema for 向量库 / GraphRAG 三行）。这几行级别不同，不要合并使用：**能装半结构化数据，不等于向量与文档结构也已被规范接住。**
- **失效条件**：当 embedding 模型半年一换时，「加列 + 回填 + 双写」的迁移成本可能高于它带来的收益；此时该考虑的不是更快的 Schema 演进，而是**把向量放到表格式之外**（独立向量库），并接受两套系统之间的对账成本。
- **自验方法**：取一次真实的模型升级（维度变化），把下面五步的耗时分别记下来——最慢的一步就是你下一次升级的成本下界。

把这次迁移拆开看，才知道成本记在哪一步（维度写在类型里，所以第一步就没有别的选项）：

```text
换 embedding 模型（768 → 1024 这类常见维度变更【经验】）在这套体系里是一次什么操作
   ① 加新列         维度写在类型里 ⇒ 只能新增一列，不能原地改类型
   ② 回填历史       全量重算 embedding（成本 = 数据量 × 每行推理成本，与保留窗口无关）
   ③ 双写           新旧两列并存，两套索引同时维护
   ④ 切换消费       下游逐一切到新列（切换期长度由下游排期决定，不由平台决定）
   ⑤ 删旧列并清索引  旧列可删，但索引要单独重建或删除——它不在表格式的提交里

判定方法：把 ①–⑤ 的耗时分别记下来，最慢的一项就是下次升级的成本下界
   ③ 最慢 → 瓶颈在下游排期，先谈排期再谈技术
   ⑤ 最慢 → 瓶颈在表格式之外，换表格式不会改善
   回滚时注意：还原表快照不会还原索引，索引要另行重建
```

#### 5.2.4 Time Travel for AI：要复现的是数据、代码与参数三样

- **旧做法与它的卡点**：训练要复现，常见做法是「记住大概是哪天的数据」或「按日期分区回放」。卡点在**快照不等于可复现**：表格式的 Time Travel 给的是「表在某一时刻的内容」（§7.3.3 的引用计数），它不知道那次训练用了哪些表、哪版代码、什么参数与什么特征定义。
- **AI 改变了什么机制**：没有改机制，改的是**复现对象的范围**——从「一份数据」扩展到「数据快照 + 变换代码 + 模型与特征定义」三样同时可回到当时的状态。前两样各有承载（表格式与版本控制），第三样（特征与模型定义）在多数团队里根本没有版本化。
- **由此得到的**：因为 Time Travel 的物理基础是「旧版本仍被引用」（§7.3.3），**所以**「数据可回到某时点」的成本是**日重写量 × 保留窗口**，与表的总量无关——纯追加表的回溯几乎免费，而每天回填分区的表会让这一项成为存储账单里增长最快的一项；**又因为**保留窗口默认往往很短、而且以 commit 数或天数配置（例如 Hudi 的 `clean` 按保留最近 N 个 commit），**所以**「能复现半年前那次训练」这件事会在无人察觉时失效——回溯能力不是被关掉的，是被一次配置悄悄缩短的。
- **由此付出的**：把窗口拉到与复盘周期一致，就要按 §7.3.3 的口径为被取代的旧文件付费；每次训练落一份「快照 + 代码版本 + 参数」清单是流程成本，且它只有在**下次复盘真的用到**时才体现价值，所以它是最容易被跳过的一步；此外窗口变长会同时抬高读放大（更新以删除文件表示时，删除文件数随窗口累积，§7.3.4）。
- **证据与来源**：【公开】Iceberg 的 `expire_snapshots`、Delta 的 `VACUUM` 保留期、Hudi 的 `clean` 与保留 commit 数配置（各自官方文档可核验，§7.3.3 引用同一组来源）；【公开】模型与数据集的文档化规范——Model Cards for Model Reporting（FAT* 2019）与 Datasheets for Datasets（arXiv 2018；CACM 2021）——它们定义了「可复现应当记录哪些元数据」，正是本方向的需求来源；成本换算可用对象存储标准层定价（S3 定价页 2024，$0.023/GB-月，§7.3.3 同一口径）【公开】。
- **成熟度**：**L3**（与 5.1 表「Time Travel for AI」行一致）。注意别把两行混为一谈：**底层 Time Travel 本身是 L2**，卡在「训练复现」这一层的是清单与流程，不是存储能力。

**「能不能复现」的判定方法（可自行核验）**：任取一次三个月前的训练，试着回答三个问题——它用了哪些表的哪个快照、哪一版变换代码、哪一组参数与特征定义。三个都有答案才算可复现；有一个答不出，缺的不是 Time Travel 能力，而是那份清单。

那份清单要记的四项，以及它们各自缺了会怎样：

| 复现清单的项 | 记在哪 | 缺了会怎样 |
| --- | --- | --- |
| 数据侧：表名 + 快照 / 版本号 | 训练任务的输出元数据 | 只能按日期猜，回不到同一次读取 |
| 代码侧：变换代码的 commit | 版本控制 | 同一份数据重跑出不同结果，且无法解释差异 |
| 参数侧：超参与随机种子 | 训练配置 | 结果不可复算，只剩「近似复现」 |
| 特征定义版本 | 特征平台或语义层 | 特征口径变过，复现出来的是另一个模型 |

**把清单落进流程的做法**：不要要求「每次训练都写文档」——它会被立刻跳过。可行的做法是让训练任务在启动时自动写下这四项：读取的表与快照号从执行计划里取，代码版本从工作区取，参数从配置里取，特征定义版本从特征平台取。**因为**这四项都能从执行环境里自动取得，**所以**清单的边际成本接近零，缺的只是一个「谁写这段代码」的决定；**代价是**它需要训练框架侧的配合，而这部分工作通常不在数据平台的预算里。

**表中其余方向为什么停在这里**：

- **联邦 Schema 管理（L2）**：机制是「把登记点从每个平台各一个，变成跨平台一个」（落点即 §7.2 表第 8 行的「统一元数据目录（catalog）」），承载形态是目录协议与目录实现。但**统一登记不等于统一类型语义**：同一列在不同格式下的投影、默认值与类型提升规则要逐对测，而这类跨实现的行为差异恰恰是 ② 拿不到材料的地方。
- **自治 Schema 管理（L3）**：与「自治数据中台」是同一类混淆——被叫作「自治」的能力里，一部分是检测与规则闭环（与 LLM 无关），一部分是生成式建议。结构变更一旦自动执行，就会绕过 §7.3.2 的判定点与责任主体；安全边界只能写成「自动提议 + 门禁可验证 + 人工批准」。
- **AI 原生 Schema（L3）**：作为合并叙事，按最弱组成项（自动生成 L3、自动演进 L3）取 L3。主文件 §1.4 的「AI 原生 Schema 管理」是历史分期，不是能力清单。

### 5.3 与本主题既有栈的接口在哪

表格式与注册中心提供的是**机制**，AI 相关内容都挂在它们周边的接口上。下表写清谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 变更提交 ↔ 兼容性检查 | CI 阶段调用注册中心或表格式 API，比较新旧两个 schema | 写入侧（生产者） | 注册中心侧是既有能力；表格式侧是写入时校验 + 读取时投影（§7.3.2） |
| 列身份 ↔ 多引擎读取 | 按编号投影（编号身份）或按 schema 版本解析（名字身份） | 读侧的引擎组合——只有写入侧引擎通过时，依赖的是它的宽容而非规范 | 需自测（§7.3.1 的自验方法） |
| Embedding 模型 ↔ 向量列 | 维度写进列类型；换模型 = 加新列 + 回填 + 双写 + 切换 | 应用侧（谁提模型升级谁出迁移方案） | 需自建；索引重建不在表格式提交内 |
| 训练任务 ↔ 数据快照 | 训练启动时记录：表名 + 快照 / 版本号 + 代码 commit + 参数 | 训练侧（谁发起训练谁落清单） | 需自建 |
| 联邦目录 ↔ 各引擎 | REST 形态的目录协议 + 统一凭证；只统一登记点 | 目录侧（谁提供目录谁负责一致性） | 需核验协议版本；跨格式类型语义逐对测 |
| 文档 / RAG 结构 ↔ 表 | 应用自定义结构，表格式只负责存储 | 应用侧（表格式不保护它） | 缺位，必须自建契约 |

表里唯一「既有能力」行是第一行的前半（注册中心的写入侧判定），其余五处都要自建或自测。**失败归属必须在设计阶段写清**，否则会退化成扯皮：跨引擎读不出来归谁？表格式说它按规范实现了，引擎说它按自己的版本解释规范——这类争议的根源是「谁有能力证明自己是规范的」，而唯一的证明方式是 5.2.1 的自验方法（用第二个引擎读老文件）。

这张表还有一个共同点值得写出来：凡是「需自建 / 需自测」的行，失败最终都落在**平台团队之外**——要么是应用侧（向量列与文档结构），要么是训练侧（复现清单）。把它写进接口表的意义不是分工好看，而是**让事故发生时不必现场决定谁负责**；反过来，如果这张表在你们那里画不出来，说明这些接口还没有人认领。

**判定这张表有没有被用起来**：每个季度核对两个数——这一季有没有变更在 CI 阶段被拦下，有没有哪次训练是靠清单复现出来的。两个数都是零，说明表还停留在文档层面，而不是落在流程里。

- **联邦登记点**：【公开】Iceberg REST 目录规范（Iceberg 项目随版本发布的目录规范文档，查其中该部分的标记与所属版本）；【公开】目录实现与其年份——Unity Catalog（Databricks，2021 年发布、2024 年的联邦目录形态）与 Polaris（Snowflake，2024），§4.3 的「元数据目录」已列出。判定联邦能力看协议版本，不看集成清单。
- **消息侧的兼容性标准**：【公开】Kafka 生态与注册中心的兼容级别（Confluent 的七级清单，2024 年前后版本；§6.1 的 LinkedIn 案例有 2014–2024 年的公开工程材料，判据见 §7.3.2）。判断某级别够不够用，看消费者最多落后几个版本，而不是看配置界面给了几个选项。
- **复现要记哪些元数据**：【公开】Model Cards for Model Reporting（FAT* 2019）与 Datasheets for Datasets（arXiv 2018；CACM 2021）给出了「数据与模型应当被记录哪些字段」的清单，是 5.2.4 的需求来源。
- **成本换算口径**：【公开】对象存储标准层定价 $0.023/GB-月（AWS S3 定价页 2024），用于把保留窗口换算成年度成本（§7.3.3 已有完整推导链，本节不重复）。

**引用纪律**：本节涉及的项目多、版本快，最容易出错的引用有三类——「某项目在某会议某年发表论文」（查会议论文集或项目官网 publications 页）；「某版本支持某类型」（查该版本 release note 与规范文档里该类型是正式还是提案）；「某引擎的版本号」（查官方发布页与发布日历，不要用博客里的旧数字）。

**值得注意的空白**：本节列不出「第三方（非厂商）公开的生产级 AI Schema 推断 / 自治 Schema 落地效果」材料，也列不出向量类型与半结构化类型在跨引擎读取时的公开互操作结论。这不是因为它们不重要，而是因为这类跨实现行为差异通常只出现在实现方的测试与问题上——它同时意味着：**这类判断只能自己测，不能外包给别人的结论**。

**一条给读者的提醒**：本节里凡涉及「某版本是否支持某类型」的判断，都不要凭印象——这类条目的状态在两个版本之间就会变化，而一旦被写进架构假设，改它的成本远高于核一次文档的成本。

### 5.5 被过度宣传的部分

**「AI 自动管理 Schema」**

- *实际是什么*：被包装成「自动演进」的能力，多数是列注释自动生成、类型映射的启发式规则，以及检测与工单闭环（与 LLM 无关）。
- *为什么会这样*：真正的演进决策（改名、类型收窄、删列）要承担下游静默算错的责任（§7.3.1 的失效条件），而责任不能交给一个概率模型；自动执行还会绕过 §7.3.2 的判定点。
- *什么时候它才会成真*：当自动动作被限制在「提议 + 门禁可验证 + 人工批准」的范围内，例如只自动生成注释与候选类型，结构变更仍然走 CI 判定。

**「Variant / 向量类型标准化之后，一份结构处处生效」**

- *实际是什么*：类型可用不等于语义一致。各格式各自定义该类型的投影与默认值规则，跨引擎读取仍要逐对核验，而「支持某格式」的清单页证明不了这一点。
- *为什么会这样*：类型进规范只统一了**怎么存**，没有统一**怎么解释**；解释差异在读取时暴露，而读取侧的宽容度又取决于引擎版本。
- *什么时候它才会成真*：当出现由发起方之外的实现共同通过的跨实现兼容性测试时——那时「支持」才有一个不依赖厂商自述的定义。

**「Time Travel 让 AI 训练天然可复现」**

- *实际是什么*：快照只给出数据一侧。缺代码版本与参数清单时，复现依然失败；而且默认保留窗口常常在无人察觉时缩水（按 commit 数配置的清理策略会随表的使用频率变化）。
- *为什么会这样*：Time Travel 保护的是「表在某一时刻的内容」，而「一次训练用了什么」是跨系统的引用关系，它不属于任何一张表的元数据。
- *什么时候它才会成真*：当训练产物里带一份「数据快照 + 代码版本 + 参数」的清单，且保留窗口 ≥ 复盘周期时。判定方法就是 5.2.4 的三个问题。

这三条有一个共同结构：它们都把「机制已经就位」说成「能力已经就位」。所以判断它们何时成真，看的都是同一件事——**公开文档里有没有出现可核验的判断依据**，而不是产品页上有没有多一个带 AI 的标签。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 兼容性判定继续从读侧前移到写入侧 | 规范或引擎文档把「写入时拒绝不兼容变更」写成默认行为，CI 集成被列为推荐路径 | 主流路线仍是读侧宽容，下游第一次读到才发现，CI 门禁仍靠自建脚本 |
| 向量与半结构化类型进入表格式正式规范，但跨格式语义仍不统一 | 正式规范版本里出现该类型（不是提案），且至少两个非发起方实现按同一语义读它 | 五年后仍是引擎私有扩展，跨引擎读取仍要逐对核对 |
| 训练复现的「快照 + 代码 + 参数」清单成为规范字段 | 数据与模型文档化规范里出现数据版本与代码版本的必填字段，或被平台写进训练任务模板 | 复现仍靠「当时谁记得」，清单停留在个别团队的约定 |
| 跨平台的目录协议版本成为选型依据 | 采购与选型文档里开始出现协议版本号与兼容性测试结果 | 选型仍按「支持哪些格式」的清单页来做 |

四条预测都能被**公开文档**证实或证伪，不需要内部数据：

- 第 1 条看规范与引擎文档里「拒绝 vs 宽容」的默认值，一到两年见分晓。
- 第 2 条看正式规范版本里有没有该类型，两到三年。
- 第 3 条看文档化规范与平台模板的字段，三到五年。
- 第 4 条看选型材料里是否出现协议版本，一到两年。

这四条里最值得先盯的是第 1 条：它是本节唯一一条**不依赖任何新产品发布**就能观察到的信号——判定点前移会直接改变规范与引擎文档里「兼容性」那一节的默认行为，而不只出现在发布会里。

提醒一句：这四条都不是「某产品会不会做」，而是「**判断依据会不会出现在公开文档里**」。前者无法证伪，后者可以被逐条核对——这正是本节用成熟度分级换掉趋势清单的原因。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 表还在「改列就崩」 | 先确认列身份（改名是否只改元数据），再把兼容性检查接进 CI（5.2.1） | 引擎是否把「写入时拒绝」做成默认行为 | 不要先上「AI 自动改结构」，它绕过的正是判定点 |
| 消息链路多团队消费 | 选兼容级别时看消费者落后几个版本，必要时用传递级别（§7.3.2） | 注册中心的协议与 API 版本 | 不要拿非传递的 FULL 当保障 |
| 要做 RAG / 向量检索 | 先定「维度写在列类型里」的迁移方案：加列 + 回填 + 双写 + 切换 + 重建索引（5.2.3） | 表格式正式规范是否纳入向量类型 | 不要指望 Time Travel 帮你回滚索引 |
| AI 训练要可复现 | 在训练任务里落「快照 + 代码版本 + 参数」清单，并核对保留窗口 ≥ 复盘周期（5.2.4） | 保留策略是否被改小（按 commit 数配置的尤其要盯） | 不要把「有 Time Travel」当成「可复现」 |
| 多平台 / 多引擎并存 | 统一目录与协议版本，逐对测跨引擎读取（5.2.1 的自验方法） | 目录协议的版本节奏与兼容性测试是否公开 | 不要按「支持 Iceberg / Delta」的清单页选型 |
| 刚开始做 Schema 治理 | 先定义两件事：改名在你的引擎组合里意味着什么、兼容级别该选哪一档 | 团队能不能说出「消费者最多落后几个版本」 | 不要先买目录产品再定判定点，工具决定不了判据 |

「明确不要做」那一列的共用逻辑只有一句：**本节真正变了的是起草者与要装的数据形态，四条机制（列身份、判定点、历史的存在形式、变更的表示）一条都没变**。所以预算应当投在判定点、列身份与保留窗口这三件确定性工程上；在它们定下来之前，任何「AI 原生 Schema」的选型都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先量**：写入形态是不是纯追加、日均被重写的数据量、当前保留窗口（§7.3.3 的自验方法三项）。这三项决定回溯成本，且不需要新采购。
2. **再定判定点与列身份**：兼容性检查进 CI，并确认改名在跨引擎读取时真的只是元数据编辑。它同时是本节唯一有明确收益的动作。
3. **然后补语义信息**：列注释、单位、枚举值——它补的是门禁的盲区，也是 AI 起草能被验收的前提（5.2.2）。
4. **最后才谈 AI 与联邦**：这两类都会改变登记点与责任归属，回滚成本高于前两步（见 §7.5 的决策树）。

最后一条提醒：本节所有「现在就能做」的动作都不需要 AI，也不需要新采购——兼容性检查进 CI、列身份确认、保留窗口与复盘周期对齐，全是配置与流程。这也解释了本节为什么没有 L1：真正成熟的那部分（表格式与注册中心）不需要被宣传，而需要被宣传的那部分，还没有成熟到能被第三方核验。

### 5.8 小结

> 本节小结：AI 在本主题上**没有改动任何一条机制**——列的身份（§7.3.1）、兼容性判定发生在哪一侧（§7.3.2）、历史是引用计数还是副本（§7.3.3）、变更把代价记在写侧还是读侧（§7.3.4），四条一条都没变；它改的是**起草者**（结构由模型起草）与**要装的东西**（向量、半结构化字段、文档结构），以及**要复现的对象**（从数据扩展到数据、代码、参数三样）。本节没有一行达到 L1：最接近的三行 L2 都卡在「第三方（非厂商）公开生产案例」这一条上——所以现在该投的是判定点、列身份与保留窗口，而不是「AI 原生 Schema」。
>
> 💡 **思考锚点**：把 §5.7 的「先量」三项套到你自己的表上：写入是不是纯追加、日均被重写多少数据、保留窗口是几天——如果复盘周期比保留窗口还长，你落的那份「快照 + 代码版本 + 参数」清单里，真正还能复现的是哪一项？
