## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

原表把「传统 DDL / Avro SR / Iceberg / Delta / Paimon」五列放进同一张 1–5 分的表，用「Schema 演进 / Time Travel / 兼容性检查 / 跨引擎 / AI 友好度」五个维度打分。这个做法有三个结构性错误。

**错误一：五列不在同一个抽象层。** 传统 DDL 是**关系库存储引擎的行为**（`ALTER TABLE` 直接作用于表定义与物理存储）；Avro SR 是**消息契约的注册与裁决服务**（它管的是一段字节该用哪一版 schema 解析，管不到文件）；Iceberg / Delta / Paimon 是**表格式**（管文件如何组织、快照如何引用、列的身份如何标识）。给「存储引擎行为」「契约注册中心」「表格式」打同一张分表，等于给「海关 / 报关单 / 集装箱」打分——它们在一条链路的不同环节，多数情况下不是二选一。**只有跨环节才会互斥**：消息上的契约与文件里的契约是两种形态，谁也替代不了谁，这恰好是 7.5 决策树第一刀切在「数据形态」上的原因。

**错误二：同一维度的符号会随约束反转。** 原表给「兼容性检查」打出 Avro SR 5 分、Iceberg 4 分的差别，但这一维的高低取决于**你的消费者是否同步升级**：消费者全部同步升级时，注册时的兼容性判定是纯阻塞——每次发文多一道流程，收益为零；升级不同步时，它是唯一的安全网，此时「检查越严越好」才成立。同理，「跨引擎 4 分 vs 5 分」问的是产品名，而跨引擎能否成立取决于**各引擎是否都实现了同一套语义**（按 id 投影、缺列补默认值、快照解析），这取决于版本而不是取决于名字。

**错误三：「AI 友好度」没有说明判定对象。** 原表给 Avro SR 2 分、Iceberg 5 分。但 AI 训练复现需要三样东西：**当时的数据**、**当时的 schema**、**这份数据由哪次变更产生**。第二样恰恰是注册中心的强项——它把 schema 版本做成可按 subject 与 version 列举、可按 id 取回的**可查询对象**；表格式提供的是第一样（快照）与第三样的半截（提交历史），完整口径追溯还要靠血缘。给 Avro SR 2 分，说明这一维量的是「这个产品像不像一个 AI 数据平台」，而不是「它能否支撑训练复现」。

打分表输出的是名次；选型需要回答的是「在**我的数据形态、写入形态、消费者升级节奏**下，下一步该换成哪一种，以及它在什么条件下失效」。本章因此只保留原表五个维度所指向的问题，但把它们重新组织成可判定的判据。

**本章采用的 6 条判据**（每条针对本主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 变更的代价落在哪一层 | 这次变更是只改元数据，还是要动/重写数据文件 | 因为「只改元数据」的变更可以不停机完成，「要动数据」的变更必须排迁移窗——它决定的是**可行性**，不是效率 |
| 兼容性判定发生在哪一侧 | 靠注册时比较两个 schema，还是靠读时按列身份投影 | 因为判定位置决定坏 schema 是被**写入路径**拒绝，还是推迟到**下游第一次读取**才暴露 |
| 历史版本的存在形式 | 历史是「快照指针 + 仍被引用的旧文件」，还是一次次完整拷贝 | 因为形式决定保留窗口的成本是随「日重写量 × 窗口」增长，还是随「数据量 × 副本数」增长 |
| 写入形态 | 只追加，还是 upsert / delete 密集 | 因为行级更新与快照不变性互斥，必须用删除文件或重写来表示，代价会落到读侧或写侧 |
| 列身份的持有者 | 名字、字段 id、提交版本，还是注册中心 | 因为持有者决定「改名是不是破坏性变更」，也决定**除你之外还有谁能改表的形状** |
| 迁移与锁定 | 换掉它要重写多少数据、多少作业、多少下游约定 | 因为表格式承载数据布局，换格式的成本远高于换注册中心——这一项决定你今天能承受多少「以后再改」 |

原表五个维度都还在，只是位置变了：「Schema 演进 → 判据 1」「Time Travel → 判据 3」「兼容性检查 → 判据 2」「跨引擎 → 判据 6 的前半」「AI 友好度 → 判据 1、3、5 的推论」——**它不该单独占一栏**，因为复现能力是那三条判据的合成结果，单独打分只会重复计权。判据的顺序也不是中性的：按**回滚成本**从低到高，这六条分属三层——判据 2–3 属**配置层**（兼容模式取哪一档、保留窗口与清理策略多长，改完随时可调），判据 5 属**身份层**（列身份由谁持有），判据 1、4、6 属**形态层**（变更动不动数据、写入是追加还是 upsert、换掉它要重写多少数据与作业）。三层与 7.5 的执行顺序严格对应（第 1 阶段只动配置、第 2 阶段收敛列身份、第 3 阶段才换存储形态），顺序不能颠倒的原因很实际：形态层一旦落地，改动要付 7.7 那张表里最高一档的成本——最贵的两行（追加表 → 主键表 6–18 人月、传统 DDL → 湖表格式 3–9 人月）都在这一层；反过来把配置层的问题当成结构问题处理，这笔钱就白付了。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 传统 DDL（关系库 `ALTER TABLE`） | 存储引擎自身的行为 | 表定义与物理布局绑定，变更由存储引擎在元数据或数据上直接执行 | 单体关系库、数据量可控 | 随数据库许可 |
| Avro / Protobuf + Schema Registry | 消息契约的注册与裁决 | 消息体只带一个 schema id，消费者按 id 取写者 schema、用自己的 reader schema 解析；兼容性在**注册时**按规则判定 | Kafka 为主干的消息链路 | Apache 2.0 + 各 Registry 实现自带许可 |
| Confluent Schema Registry / Karapace / Apicurio | 契约注册中心的具体实现 | 同一套「subject + version + 兼容模式」模型的不同实现；是否实现 Confluent 线格式决定客户端能否互通 | 消息契约集中治理 | 商业版 / 开源版并存 |
| Iceberg（含 V3 规范方向） | 开放表格式 | 列以 **field id** 标识且 id 不复用；快照以元数据引用文件清单；行级删除用独立删除文件表达 | 多引擎共读的湖仓 | Apache 2.0 |
| Delta Lake | 开放表格式 | 事务日志按版本追加，每个版本记 `metaData`（含 schemaString）；回溯按版本号或时间戳 | Databricks / Spark 生态 | Apache 2.0 / 托管服务 |
| Apache Hudi | 开放表格式（增量写入） | schema 挂在 Timeline 的 commit 上；`clean` 策略单点决定回溯窗口 | 增量入湖、需要按提交点回溯 | Apache 2.0 |
| Apache Paimon | 主键表格式 | 主键分桶 + LSM 文件组，`merge-engine` 决定同一主键的合并语义 | 实时数仓、CDC 入湖 | Apache 2.0 |
| 统一元数据目录（catalog） | 元数据治理层 | 管「同一张表在各引擎里叫什么、谁有权读」，不管快照与列身份 | 多引擎、多团队 | 开源 / 商业 |
| 血缘 × Time Travel 组合 | 组合模式（不是单一产品） | 快照回答「当时的数据长什么样」，血缘回答「这份数据由哪次变更产生」 | 合规审计、AI 训练复现 | 视组件而定 |

上表 9 项其实分**四族**：**存储引擎行为族**（传统 DDL）、**契约与元数据层族**（各 Registry 实现、统一目录、血缘）、**表格式族**（Iceberg / Delta / Hudi / Paimon）、**组合族**。同族内部差异小、跨族差异大——**先分族再选，能省掉一半比较**：你首先要在「换形态」「换契约层」「换表格式」里选一种动作，而不是在九个名字里挑一个。真正互斥的选择只有一次：**消息与表是两种数据形态**，各自只能由本族的候选处理。

**原文件对比过的候选与决策树分支全部保留**，只是重新归类：

| 原决策树分支 | 归入上表哪一行 | 机制归属 |
| --- | --- | --- |
| Kafka 消息流 → Avro/Protobuf + Schema Registry | 契约层族 | 契约外置到注册中心，消息里只留一个 id |
| Lakehouse 表 → Iceberg（最灵活） | 表格式族 | 列身份是 field id，改名与加列是元数据操作 |
| Lakehouse 表 → Delta（Spark 生态深） | 表格式族 | schema 是事务日志里的一个版本 |
| Lakehouse 表 → Paimon（实时数仓） | 表格式族 | 主键 + LSM，演进与合并语义绑定 |
| 跨场景 → Iceberg V3 + Schema Registry | 组合族 | 消息契约与表契约两层各自演进，中间靠映射连接 |

**上表只列机制，不断言「某个产品是否支持某特性」**：表格式与注册中心的能力随版本变化很快，把结论写死会立刻过期。凡涉及具体能力，用下面三种**判定方法**自查，而不是相信任何静态清单：

- **某表格式是否支持你要的变更**：查其官方文档的 `ALTER TABLE` / Schema Evolution 章节里的**受限变更清单**（哪些变更需要重写数据、哪些只改元数据）。有「改主键」「改分区」字样的，逐条看清是否被列为受限。
- **某注册中心实现能否与既有客户端互通**：比对它是否实现 Confluent 线格式（magic byte + 4 字节 schema id）。不通用的实现需要客户端替换或网关转换。
- **跨引擎共读是否真的成立**：在第二个引擎上读同一张表，且**先做一次改名和一次加列**再读。只有这时通过，才说明你依赖的是规范而不是某个引擎的宽容。

### 7.3 机制差异：为什么它们表现不同（核心节）

四族的全部差异可以归因到四个机制维度。选这四个，是因为它们分别回答选型时必然要问的四件事：**列的身份是什么（7.3.1）· 兼容性判定在哪发生（7.3.2）· 历史怎么被保存（7.3.3）· 变更怎么被表示（7.3.4）**。每个维度给出「机制 → 因果 → 公开证据 → 失效条件 → 自验方法」。

#### 7.3.1 列身份：名字还是编号

**机制是什么**：写进文件的每一列，用什么当身份——**名字**，还是一个**独立于名字的编号**。名字身份下，「改名」改变的是列的标识；编号身份下，名字只是编号的一个别名。

**各候选的实现差异**：

| 候选 | 列的物理身份 | 「改名」是什么操作 | 老文件怎么读 |
| --- | --- | --- | --- |
| 传统 DDL | 名字 + 列序 | 改表定义，部分引擎会连带重写数据 | 按新定义解释老数据 |
| Avro | 字段名 + 声明顺序（二进制体按顺序排列，**不携带字段标签**） | 需在 reader 侧声明 alias，否则读不到 | 由 writer schema 与 reader schema 做 schema resolution |
| Protobuf | 字段编号（tag 写在线格式里，字段名不进字节） | 二进制解析不受影响，但生成的代码与 JSON 映射要同步改 | 按字段编号解析，未知编号被跳过 |
| Iceberg | field id（写进 metadata） | 纯元数据：只改 name 映射 | 按 id 投影，缺的列补默认值 |
| Delta | 名字 + 日志里的 schemaString 版本 | 追加一个 schema 版本 | 按该版本的 schemaString 解析该版本的文件集合 |
| Hudi | 名字 + 挂在 commit 上的 schema | 与提交一起记录 | 按该 commit 的 schema 解析该 commit 的文件组 |
| Paimon | 名字 + 表 schema（主键列参与分桶） | 加列是元数据；改主键是重新分布 | 按当前 schema 统一投影新旧格式的文件 |

**由此必然导出的性质**：**因为** Avro 的二进制体里没有列的身份标签（字段按 schema 声明的顺序依次排列），**所以**「这段字节该怎么解析」完全由外部提供的那一版 schema 决定——注册中心不是可选组件，而是这套编码成立的前提；**因为** Iceberg 让每列在文件里带着 field id，**所以**改名退化成一次元数据编辑，读侧按 id 投影、改名对读者不可见；**代价是** id 必须终生不复用——某列一旦删掉，它的 id 从此作废，任何一次 id 复用都会让新列读到旧列的字节，而**这个错误不会报错，只会静默算错**。**因为** Delta / Hudi 把 schema 存成「某个版本」「某次提交」的属性，**所以**「读某个历史版本」与「拿到那时的 schema」天然配套，不需要额外对齐；代价是它们的列身份仍建立在名字之上，改名要靠写入侧与读取侧同时接受新名字。**Protobuf 是这一维度上的一个中间态**：它的身份是字段编号且编号就在字节里，所以改名不影响二进制解析——**但它保护的是「解析」，不是「含义与工具链」**，列名仍要跟着改代码、JSON 映射与上下游约定。

**公开证据**：Apache Iceberg 表规范规定字段以 id 标识且 id 不可复用（Iceberg 2018 年进入 ASF 孵化，规范可自行核验）【公开】；Delta 的 schema 历史写在其事务日志的 `metaData` 中（Delta Lake 2019 年开源，官方文档可核验）【公开】；Avro 规范的 schema resolution 规则明确了「writer 有、reader 没有的字段直接忽略」（Apache Avro 官方规范可核验）【公开】。**这三条只证明机制存在，不证明谁在用、用了多久、付了什么代价**——本文件不指名采用方。

**失效条件**：当变更不是改名/加列，而是**类型收窄或列语义变更**时，编号身份的保护完全失效——id 没变，类型可能仍算「兼容」（例如 `decimal` 精度不变但单位从元改成分），下游不报错、静默算错。编号身份保护的是「列的身份」，不是「列的含义」；后者只能靠血缘与变更评审。

**自验方法**：在测试表上依次做改名、删列、加列，然后用**第二个引擎**读改名前写入的老文件。三个动作都通过且老文件仍可读，才说明该表格式的列身份在你的引擎组合里真的稳定；只有写入侧的引擎通过时，你依赖的是这个引擎的宽容，而不是规范。

#### 7.3.2 兼容性判定发生在哪一侧

**机制是什么**：兼容性判定需要输入（新旧两个 schema）和一个**执行点**。注册中心把执行点放在「提交新版本」这一刻；表格式把执行点放在「读某个文件」这一刻。

**各候选的实现差异**：

| 候选 | 判定点 | 判定依据 | 不兼容的后果在哪出现 | 谁承担阻塞 |
| --- | --- | --- | --- | --- |
| Avro / Protobuf + Registry | 注册新版本时 | 两个 schema 的解析规则比较（不看数据） | 生产者本地，新版本根本注册不进去 | 生产者 |
| Iceberg / Delta / Hudi | 写入时校验元数据合法性 + 读取时投影 | 元数据类型规则 + 读时补默认值 | 下游第一次读取时 | 下游 |
| Paimon | 改表 schema 时 + 读取时投影 | 表 schema 与主键、分桶约束 | 受限变更当场拒绝，其余读时才生效 | 表 Owner |
| 传统 DDL | 执行 `ALTER` 时 | 数据库的类型转换规则（能否强制转换） | `ALTER` 当场失败，或老数据的语义被改写 | DBA |

**由此必然导出的性质**：**因为** 注册时判定只需要两个 schema、不需要读数据，**所以** 它能在字节进入链路之前给出确定答案——这就是「不兼容的 schema 根本发不出去」的机制来源；**代价是** 它看得见结构、看不见含义：字段名不变、类型不变、语义从元改成分，兼容性检查全绿。**因为** 表格式的判定发生在读侧（按身份投影、缺列补默认值），**所以** 它允许的变更范围更大、几乎不需要停机；**代价是** 不兼容的后果从「写入失败」变成「下游第一次读到才发现」，而暴露时间取决于下游的调度频率——一张每周跑一次的下游作业，坏 schema 可以潜伏一周，等它报错时，变更已经进入不可变历史，回滚要还原元数据版本而不是改文件。

**公开证据**：Confluent Schema Registry 定义并执行**七种**兼容级别——NONE、BACKWARD、FORWARD、FULL，以及后三者的传递变体 BACKWARD_TRANSITIVE / FORWARD_TRANSITIVE / FULL_TRANSITIVE，注册不合规直接拒绝（Confluent 官方文档 Schema Compatibility 一节，级别清单随产品版本演进，以当前版本为准，可自行核验）【公开】。这里有一处容易踩空：**非传递级别只与「最近一次注册的版本」比较**，所以当消费者可能落后一个以上版本时，FULL 并不足以保证它解析得通——那一支需要的是传递级别 FULL_TRANSITIVE（对所有已注册历史版本、读写两个方向都兼容；若只要求「未升级的消费者能读懂新数据」，FORWARD_TRANSITIVE 即可），这正是 7.5 树上第一支的口径；Avro 规范的 schema resolution 规则同时规定了「reader 有、writer 没有的字段按默认值补」（Apache Avro 官方规范可核验）【公开】。判定你的主题当前处于哪一档，方法很直接：看该 topic 的 `<topic>-value` 名下有几个注册版本，以及消费者进程里有没有指向注册中心的连接与本地 schema 缓存。

**失效条件**：当消费者全部同步升级时，注册时判定是纯阻塞，收益为零【经验】；当写入方是外部伙伴、你无法要求它过 CI 时，读侧判定的「宽容」反而是唯一能让管道跑起来的形态——此时你该补的不是更严的检查，而是**列名白名单**这类写入侧准入。

**自验方法**：在预发环境推一次真实的 schema 变更，记录**最早报错的是谁**。报错在生产者 → 你的判定点在注册侧；报错在下游分析师 → 你的判定点在读侧；谁都没报错但数据不对 → 你的判定点根本没覆盖这类变更。

#### 7.3.3 历史的存在形式：引用计数，不是副本

**机制是什么**：Time Travel 的物理基础是「旧版本仍被引用」。表格式下的历史是**元数据指针 + 尚未被清理的旧文件**；备份式历史是**完整副本**。

**各候选的实现差异**：

| 候选 | 历史的物理形式 | 保留窗口由谁决定 | 窗口内成本随什么增长 | 过期后 |
| --- | --- | --- | --- | --- |
| Iceberg | 快照元数据 + 旧数据/删除文件 | `expire_snapshots` 策略 | **被取代的文件量**（日重写量 × 窗口）+ 元数据对象数 | 清理孤立文件 |
| Delta | 事务日志版本 + 旧文件 | 日志保留 + `VACUUM` 保留期 | 同上（日志版本数 + 被取代文件） | `VACUUM` 删除不再被引用的文件 |
| Hudi | commit 时间戳 + 文件组的旧版本 | `clean` 策略（按提交数或按时间） | 同上 | `clean` 删除旧文件版本 |
| Paimon | 快照 + 分桶文件的多版本 | 快照保留策略 | 同上，另加 compaction 产生的中间版本 | 快照过期 + 文件清理 |
| 传统 DDL | 无（除非外部备份） | 备份策略本身 | 数据量 × 副本数 | 备份介质轮转 |

**由此必然导出的性质**：**因为** Time Travel 读的是「旧快照引用的那批文件」，**所以** 保留历史的增量成本不是「再存一份数据」，而是「这批文件在过期前不能被物理删除」——它是**一个引用计数，不是一次拷贝**；**又因为** 每次提交都会产生新文件、并让一部分旧文件失去最新快照的引用，**所以** 窗口内真正多付的存储量 ≈ **日重写量 × 保留窗口**，与表的**总数据量无关**。**这条推论有一个反直觉的副产物**：对只追加的表（日志、事件、不可变事实），历史快照引用的文件与当前数据几乎完全重叠，**Time Travel 的增量存储成本接近零**；而一张每天回填 5% 分区的 1 TB 表，Time Travel 反而可能是存储账单里增长最快的一项。

**公开证据**：Iceberg 的 `expire_snapshots` 与孤立文件清理、Delta 的 `VACUUM` 保留期、Hudi 的 `clean` 与 `hoodie.cleaner.commits.retained`（分别为 Apache Iceberg 官方文档、Delta Lake 官方文档、Apache Hudi 官方文档可核验；Iceberg 2018 年进入 ASF 孵化、Delta Lake 2019 年开源、Hudi 2016 年开源并于 2019 年进入 ASF）【公开】。**可自行核验的判断**：Hudi 的 `clean` 若按「保留最近 N 个 commit」配置，那么一张低频表的 N 个 commit 可能只覆盖几天——回溯能力会在无人察觉时缩水。

**【推算】数量级示例**（推导链完整给出，便于换参数重算）：设某表 1 TB、每天有一批 50 GB 的分区被 upsert 重写、保留窗口 30 天。窗口内被取代但仍需保留的旧文件量 ≈ 50 GB × 30 = 1500 GB【推算】（= 日重写量 × 窗口天数，假设每次重写的分区不重复）。按对象存储标准层 $0.023/GB-月（AWS S3 定价页 2024）【公开】换算，1500 GB × $0.023/GB-月 × 12 ≈ **$414/年**【推算】；而这张 1 TB 表本身的年存储约 1024 GB × $0.023 × 12 ≈ **$283/年**【推算】。**也就是说，仅这一项就相当于把存储账单翻了一倍以上**；把窗口从 30 天拉到 365 天，这一项按比例升到约 **$5.0k/年**【推算】（50 GB × 365 × $0.023 × 12）。反过来，若该表是纯追加（日重写量为 0），这一项为 0——**Time Travel 的降本手段只有两个方向：缩短窗口，或分层（近期全量 + 关键节点用 tag/branch 永久保留）。**

**失效条件**：当回溯需求是「复现某个业务节点」而不是「随时回看任意时点」时，长窗口是错误工具——用一次性的 tag / branch（Iceberg 提供分支与标签能力，具体版本门槛以官方文档当前版本为准）把关键节点钉住，成本远低于把整个窗口拉长。

**自验方法**：量三个数——日均写入量、**日均被重写（upsert / 回填）的数据量**、当前保留窗口天数。第二个数接近 0 时，Time Travel 对你几乎免费；不为 0 时，用它乘窗口天数，就是你要额外付的存储量。

#### 7.3.4 变更的表示：写放大与读放大的跷跷板

**机制是什么**：快照隔离要求**已提交快照的内容永不改变**，所以行级 update / delete 不能原地改文件，只能追加删除标记，或重写所在数据文件。

**各候选的实现差异**：

| 候选 | 变更的表示 | 写入代价 | 读取代价 | 与 Time Travel 的耦合 |
| --- | --- | --- | --- | --- |
| 传统 DDL 表 | 原地更新 | 低 | 低 | 无快照，回滚靠外部备份 |
| Iceberg | 独立的位置 / 等值删除文件 | 低（不重写数据文件） | 每次扫描都要合并删除文件 | 删除文件在窗口内不能清理，读放大随窗口累积 |
| Delta（未启删除向量） | 重写所在数据文件 | 高（写放大 ≈ 更新量 × 文件大小） | 低 | 同一份数据在窗口内存在多个物理版本，重复付费 |
| Delta（启删除向量） | 删除向量 + 不改写数据文件 | 低 | 中 | 同 Iceberg |
| Hudi MOR | 增量日志 + 异步合并 | 低 | 取决于是否按时合并 | 未合并的日志版本在窗口内累积 |
| Paimon 主键表 | LSM 文件组 | 低 | 读时合并多层 | compaction 产生的中间版本在窗口内保留 |

**由此必然导出的性质**：**因为** 快照内容不可变，**所以** 更新只能以「新增删除文件」或「重写数据文件」两种方式表示。前者把代价记在写侧一次、读侧每次——**读放大随删除文件数增长，而删除文件数随「更新频率 × 保留窗口」增长**；后者把代价一次性记在写侧，但同一份数据在保留窗口内会存在多个物理版本，于是**窗口越长、写放大越是重复付费**。**这就是两个机制的交点**：Time Travel 越「深」（窗口长）、upsert 越「密」，你同时在为读放大与写放大付费——而这两件事在打分表里被分别记成「Time Travel 5 分」与「Schema 演进 5 分」，谁也看不出它们背后是同一笔账。

**公开证据**：Iceberg 表规范以独立删除文件表达行级删除（可自行核验）【公开】；Delta Lake 官方文档给出 `VACUUM` 与数据文件重写的关系（可自行核验）【公开】；Paimon 官方文档的 `merge-engine` 选项说明其在 upsert 场景下如何产出变更（可自行核验）【公开】。**可自行核验的判断**：任何声称「开箱即得完整变更流」的说法都要打问号——完整变更流只有三种来源：源头的 CDC、写入时的回查、或 compaction 时的物化，三者各有代价。

**失效条件**：当写入是**纯追加**时，本节全部讨论失效——没有「更新前的值」可丢，也没有删除文件要合并，此时表格式的选择空间比 upsert 场景大得多。**判断自己的写入形态是不是真的纯追加，本身是要验证的一件事**：把过去一周的写入按操作类型统计一次，`UPDATE` / `DELETE` 占比是不是真的接近 0。

**自验方法**：对同一份数据分别用「密集 upsert」与「纯追加」跑一轮，记录写入吞吐、查询 P95、小文件数与合并作业消耗的 CPU 时。若查询 P95 与小文件数同时上升，说明你欠了一次 compaction；若写入吞吐先崩，说明你选的格式在把代价记在写侧。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
年成本 ≈ 活跃数据存储(数据量 × 副本数 × 存储单价)
       + 历史保留(日重写量 × 保留窗口 × 存储单价)        ← Time Travel 的增量项，纯追加表上为 0
       + 元数据与请求(提交频率 × 对象数 × 请求单价)      ← 通常最小，但会摊进查询规划时间
       + 重写与合并(upsert 量 × 重写次数 × 计算单价)     ← 最容易失控的一项
       + 契约与治理人力(注册中心 + 目录 + 值班)
```

**主导项与隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| 传统 DDL | 计算项（类型变更触发的表重写） | 重写期间的锁与停机窗；回滚只能靠备份 |
| Avro / Protobuf + Registry | 治理人力项（兼容模式的选择与评审） | 注册中心成为可用性单点：它不可用时生产者的注册与消费者的首次解析都会失败（已缓存的解析结果通常仍可用） |
| Iceberg | 历史保留项（删除文件 × 窗口）+ 合并项 | 每次扫描都要合并删除文件，**规划时间随对象数上升**，账单上看不见 |
| Delta | 重写项（写放大） | 未启用删除向量时，每一次更新都重写整个数据文件 |
| Hudi | 合并项（compaction 消耗的 CPU 与写入窗口） | `clean` 策略同时决定回溯窗口；按提交数配置时，回溯能力会静默缩水 |
| Paimon | 合并项 + 分桶重分布风险 | 一次「改主键」的迁移成本是全量重写，而它在文档里看起来只是一次 DDL |

**为什么把「隐性成本」单列**：显性成本（存储、集群）在账单上可见，于是被高估；隐性成本（删除文件合并、compaction、清理策略、重写与锁）不出现在账单上，于是被系统性低估。**因为** 显性成本随数据量近似线性增长，**而** 合并与重写成本与「更新频率」成正比、与数据总量无关，**所以** 小数据量、高更新频率的表上，账面上最贵的是存储，实际最贵的是合并——这正是 7.3.4 那条跷跷板的财务形态。

**【推算】一次全表重写的量级**：因为传统 DDL 的多数类型变更需要重写整张表（是否重写取决于新旧类型之间是否存在二元强制转换，PostgreSQL 文档 `ALTER TABLE` 一节列明了这条判定），所以一次变更的 I/O ≈ 表大小 × 2（读一遍 + 写一遍）【推算】——1 TB 表即 2 TB I/O，它在账单上体现为计算时长与写入请求，而不是一条「迁移费」。**这类成本只在迁移时出现一次，但它决定迁移窗口要排几个小时**，这是它比钱更重要的地方。

**主导项随场景切换，所以优先级不是固定的**：

| 你的场景 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| 只追加、下游多、改名加列频繁 | 存储项 + 元数据项 | 选列身份是 id 的表格式，把改名变成元数据操作 |
| 高频 upsert + 长回溯窗口 | 历史保留项 + 合并项 | 先缩短窗口或改用 tag 钉关键节点，再谈格式 |
| 消息链路、消费者升级不同步 | 治理人力项 | 把兼容模式从默认的 BACKWARD 提到传递级别（消费者可能落后一个版本以上时用 FULL_TRANSITIVE，只落后一个版本以内 FULL 够用） |
| 多引擎共读同一批表 | 元数据与目录项 | 先定「哪一层是权威」，再选目录 |
| 数据量可控、变更稀疏 | 计算项 | 传统 DDL 常常仍然够用，不要为了「先进」引入表格式 |

### 7.5 决策树（每个分支都要有阈值依据）

```
你的处境？
├─ 数据形态是「流上的消息」、消费者升级不同步
│    → Avro/Protobuf + Schema Registry，兼容模式取 FULL_TRANSITIVE
│      消费者只落后一个版本以内可退到 FULL；能全量同步升级时才退到 BACKWARD
├─ 数据形态是「湖上的表」、下游多、改名与加列频繁
│    → 列身份用字段 id 的表格式（Iceberg 一类）
├─ 写入方不受控（外部伙伴直写）、管道不能脆
│    → Delta 显式 mergeSchema + 列名白名单校验
│      不愿意接受「表的形状由写入方决定」→ 保持严格元数据变更，让写入方失败
├─ 增量写入 + 需要按提交点回溯
│    → schema 挂在 commit 上的形态（Hudi 一类）
├─ 实时数仓 + 同一主键多次更新
│    → 主键表格式（Paimon 一类）；记住「改主键 = 全量重写」
├─ 需要「回到某个历史时点读当时的数据」
│    → Time Travel，但先按 7.3.3 算保留窗口的成本
│      表是高频 upsert 且窗口需要跨季度 → 改用分层：短窗口 + 关键节点打 tag
├─ 合规 / 审计要求回答「这份数据由哪次变更产生」
│    → Time Travel + 血缘；只有快照不够
└─ 链路同时跨「消息」与「文件」两种形态
     → 组合模式：Registry 管消息契约、表格式管表契约，中间映射显式声明并纳入评审
```

**阈值依据**（与树上每个判断节点一一对应）：

- **「消费者升级不同步」**：判定方法而非经验值——数一下消费同一个 topic 的独立消费者有几个、以及是否存在「发布周期与生产者不同步」的一方。存在即落入本节点，并据**可能落后的版本数**选档：落后一个版本以内 FULL 够用，可能落后更多就必须用传递级别（7.3.2 说明了非传递级别为何挡不住跨版本解析失败）。全部同步升级时，注册时校验是纯阻塞（7.3.2 失效条件），收益为 0。**这条不设数字阈值**，因为决定因素是有没有第二个发布节奏，而不是人数。
- **「下游多、改名与加列频繁」**：阈值取「改名/加列是否已成为每周级别的常规动作」【经验】——到这个频率，靠人工通知下游必然漏件，列身份必须由 id 承载（7.3.1）；低频表上，靠评审 + 通知仍可能更便宜。
- **「写入方不受控」**：判定方法是看**写入方的发布是否受你的 CI 管辖**——不受管辖即落入本节点，此时读侧的宽容是唯一能让管道跑起来的东西（7.3.2 失效条件）；受管辖则回到严格元数据变更。
- **「增量写入 + 按提交点回溯」**：判据是回溯粒度是否必须精确到「某一次提交」【经验】。只要粒度是「某个时间点」，快照式回溯足够；只有需要「对齐某次上游提交」时，schema 与 commit 绑定才成为硬需求。
- **「同一主键多次更新」**：不需要估数——统计过去一周写入里 `UPDATE` / `DELETE` 的占比即可。**占比接近 0、只有零星回补时可视为追加为主**【经验】，此时 7.3.4 那张表里「删除文件」「LSM 合并」两栏的代价都不落在你头上，主键表不再是必需。这里刻意不给百分比阈值，因为决定因素不是占比高低，而是**有没有「按主键取最新值」的查询**：占比很低但每条修正都必须被查到最新值时，追加表会把成本转嫁给每个查询（重复行要下游自己去重）。
- **「需要回到某个历史时点读当时的数据」+「保留窗口需要跨季度」**：依据来自 7.3.3 的推算——窗口内多付的存储 ≈ 日重写量 × 窗口天数，且与窗口**成正比**。当这个乘积对应的年成本开始与「多留一份备份」同量级时（推导链已给出，换成你自己的日重写量与存储单价重算），应改用分层保留：短窗口覆盖日常回溯 + 关键节点用 tag / branch 钉住。**它不是行业常数**：日重写量越接近 0，这条线越往后移，纯追加表上它可以不设限。
- **「合规要求回答计算依据」**：判定方法是问一个问题——「给我去年的这份报表，你能说清它由哪次变更产生吗？」只有快照能答出「当时长什么样」，答不出「为什么是这个值」；后者需要血缘，这是两种不同的能力（7.1 错误三）。
- **「链路跨消息与文件两种形态」**：判据是链路里是否存在「Kafka → 湖」的入湖作业且两侧各有人维护。存在即落入本节点，且这个分支不设阈值：只要两种形态并存，就需要两层契约与一张必须评审的映射表（7.6 组合一）。

**把决策树展开成执行顺序**（同一棵树，按时间轴读）：

1. **第 0 步 · 先统计事实**：过去一周的写入操作类型占比、日均写入与被重写的数据量、消费同一 topic 的独立消费者数。这三项分别喂给判据 4、判据 3、判据 2，缺了它们，树上每个节点都只能靠印象回答。
2. **第 1 阶段 · 只动配置**：兼容模式（BACKWARD → FULL，消费者可能落后多个版本时取 FULL_TRANSITIVE）、保留窗口与清理策略、是否显式开启合并。这些都可回滚，且能在一周内排除掉一批「其实是配置问题」的工单。
3. **第 2 阶段 · 收敛列身份**：把还在靠「改名 + 通知」协作的表，逐个改成由 id 承载列身份；存量表按访问热度分批，新建即合规。
4. **第 3 阶段 · 才换存储形态**：换表格式、把追加表改成主键表。这一步会同时改变数据布局、写入路径与下游读法，是唯一不可快速回滚的。
5. **持续 · 把保留与清理做成看板**：当前窗口覆盖到哪一次业务承诺、被取代文件量、元数据对象数、清理作业上次成功时间。缺了第一项，「能回溯」永远是文档里的一句话而不是事实。

> 这条顺序的机制依据是：**配置 → 身份 → 存储** 三层的回滚成本依次上升一个量级，而它们的收益并不按同一比例上升。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 消息链路、消费者升级不同步 | Avro/Protobuf + Registry（FULL_TRANSITIVE） | Protobuf + 自研校验 | 只保 BACKWARD、或只用非传递的 FULL：一次删字段上线会让未升级的消费者集体解析失败，落后一个版本以上的消费者连 FULL 也救不回来 |
| 湖表、下游多、改名加列频繁 | 字段 id 表格式（Iceberg 一类） | Delta + 显式元数据变更 | 用自动合并：表的形状由写入方随机决定 |
| 写入方是外部伙伴、管道不能脆 | Delta + `mergeSchema` + 列名白名单 | 严格元数据变更 + 写入侧适配器 | 纯严格模式：上游每加一列都会断管道 |
| 实时数仓 + 主键 upsert | 主键表（Paimon 一类） | Hudi MOR | 纯追加表：去重与取最新值的成本被转嫁给每个查询 |
| 增量写入 + 按提交点回溯 | Hudi（schema 挂 commit） | Iceberg 快照 | 用表外注册中心管表 schema：会与 commit 版本错配 |
| 合规审计要回答「计算依据」 | Time Travel + 血缘 | 只做 Time Travel | 只做快照：能复现数据、复现不出口径 |
| 多引擎共读同一批表 | 开放表格式 + 统一元数据目录 | 各引擎各自的 catalog | 各自 catalog：同一张表在两个引擎里解析出两种列 |

**原文件的四组组合全部保留，并补一组**；每条说明职责边界与运维代价：

1. **Iceberg + Schema Registry**：边界是**消息契约与表契约分层**——Registry 只裁决「生产端能不能发」，Iceberg 只裁决「老文件还能不能读」。运维代价：入湖作业里那张「Avro 字段 → field id」的映射必须显式声明并评审，它的正确性没有任何组件自动保证；映射漂移时，一次上游改名会在湖里多出一列而不是重命名一列（详见 [§3 设计模式](06-schema-and-time-travel-section-3-sec3.md) 组合一）。
2. **Delta UniForm + Iceberg**：边界是**一份数据、多套元数据**——UniForm 的机制是为同一份 Delta 数据额外生成 Iceberg 元数据，让 Iceberg 读取器读懂它。原文件把它写成「支持 Iceberg / Hudi 读取」；**能不能被某个具体引擎读，以该引擎与表格式的官方文档当前版本为准，不要假定所有格式互通**。运维代价：多一层元数据要随每次提交同步生成，出问题时「哪一层元数据是权威」必须有明确答案。
3. **Paimon + Flink Schema Evolution**：边界是**表契约归表格式、作业契约归流作业**——加列在表这一侧是元数据操作，但**正在运行的流作业里的数据结构需要重启或热更新才跟得上**（详见 [§3 设计模式](06-schema-and-time-travel-section-3-sec3.md) 3.2.5）。运维代价：改主键这类变更会退化为全量重写（分桶依据变了），必须走迁移流程而不是一次 DDL。
4. **Lakehouse + 血缘 + Time Travel**：边界是**快照管「当时的数据」、血缘管「这份数据的来源与影响面」**。适用于合规审计与 AI 训练复现。运维代价：两套元数据要一起维护，且快照的保留窗口必须覆盖「重跑一次衍生数据所需的最长回填周期」——上游窗口短于下游重建周期时，口径变更后衍生数据无法重建。
5. **统一元数据目录 + 多表格式（补）**：边界是**目录管命名与权限，表格式管快照与列身份**。运维代价：目录与表格式之间也有一层映射，这层映射的权威性必须在制度上确定，否则两个引擎会对同一张表给出两种解析。

**组合的共同原则**：每个组合都必须能回答「哪一层是权威」，其余层是它的派生物；回答不出来时，你得到的是两层契约的复杂度，却没有任一层提供的确定性。

### 7.7 选错的代价与迁移成本

**反模式：把 Time Travel 当备份用** —— 保留窗口按「越久越安全」配置，两年后存储与元数据对象数同时膨胀，而真正需要恢复的那个时点早已滑出窗口 → 因为 7.3.3 的成本是「日重写量 × 窗口」的线性项，而它**不提供**跨介质恢复能力（介质损坏、误删整表都不在快照保护范围内）→ **正确做法**：短窗口覆盖日常回溯 + 关键业务节点用 tag / branch 钉住 + 真正的备份另建一套。

**反模式：用「改名 + 通知下游」代替列身份** —— 上游改了列名，靠发公告 + 下游同步修改，某一次漏了一个下游，三个月后它的作业静默算错 → 因为改名在下游视角是「不存在的事件」，没有任何机制会产生告警（7.3.1）→ **正确做法**：列身份由字段 id 承载，同时把改名纳入血缘影响面，改前先列出受影响下游。

**反模式：打开自动合并却不设准入** —— 写入方把 `amount` 拼成 `amout`，静默并成新列；半年后表里躺着三个近义列，没有一次变更被评审过 → 因为「自动兼容」把准入判断交给了写入方（7.5 决策树第三支「写入方不受控」）→ **正确做法**：自动合并只对受管辖的写入方开放，且必须配列名白名单与拼写校验。

**反模式：用消息契约管表契约** —— 以为注册中心能管住湖表的 schema，于是湖表侧没有任何变更校验，直到某天某引擎改了解析行为，同一张表在两处读出不同的列 → 因为注册中心看不到文件、表格式看不到消息，两者的裁决对象根本不同（7.2 四族分类）→ **正确做法**：消息契约归注册中心、表契约归表格式，中间映射显式声明。

**反模式：把「兼容性检查通过」当成「语义没变」** —— 单位从元改成分、枚举值含义调整，类型检查全绿，下游静默算错 → 因为兼容性检查只比较结构与类型，看不见含义（7.3.2）→ **正确做法**：语义变更走独立通道——改血缘、改口径定义、走评审，而不是靠 schema 变更流程。

**换成另一条路线要动什么**：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 传统 DDL 表 → 湖表格式 | 大：全量导出一次 + 增量追平 | 中：方言与回溯语法 | 中：新增 catalog、保留与清理策略 | 快照与列身份语义 | 3–9 人月 |
| 表格式 A → 表格式 B（Iceberg ↔ Delta） | 中：元数据转换或重写文件 | 小到中：多在元数据层 | 中：保留策略与清理作业重排 | 较小（同为表格式） | 1–4 人月 |
| 追加表 → 主键表（Paimon / Hudi） | 大：全量重写一次（分桶依据变了） | 大：下游去重逻辑要下推 | 大：compaction 作业常驻 | 主键合并语义与流作业改造 | 6–18 人月 |
| 靠约定 → 引入 Schema Registry | 无（存量消息不受影响） | 无 | 中：新增高可用组件 + 注册门禁 | 兼容模式的选择与评审流程 | 0.5–2 人月 |
| 无 Time Travel → 开启 Time Travel | 无 | 小：只多回溯语法 | 小：保留与清理策略 | 保留窗口的成本模型 | 0.5–1 人月 |

> 量级按「一个熟悉本系统的 3–5 人小组」估算【经验】。**表里最贵的一行是「追加表 → 主键表」**，因为它的成本不在数据搬运，而在**下游读法要整体改写**：一旦引入主键，所有基于行数、基于到达顺序的逻辑都要重写（[§3 设计模式](06-schema-and-time-travel-section-3-sec3.md) 3.6 给同一结论）。**最便宜的两行之所以便宜，是因为它们不触碰数据布局**——这也说明一件反直觉的事：换注册中心、开 Time Travel 这类「看起来更现代」的动作，风险远低于换表格式。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 消息链路、消费者升级不同步 | Registry + 传递级兼容（FULL_TRANSITIVE） | 判定在注册时发生，不兼容的 schema 根本发不出去 |
| 湖表、改名加列频繁 | 字段 id 表格式 | 改名是元数据编辑，读侧按 id 投影，老文件不动 |
| 写入方不受控 | 显式合并 + 列名白名单 | 准入判断必须在写入侧，读侧的宽容补不了它 |
| 增量写入、按提交点回溯 | schema 挂 commit 的表格式 | 数据与 schema 天然配套，不会错配 |
| 高频 upsert + 长回溯窗口 | 先分层保留，再谈格式 | 历史保留成本是「日重写量 × 窗口」的线性项 |
| 只追加的表 | 放心开长窗口 | 旧快照与当前数据重叠，增量存储成本接近 0 |
| 合规审计 | Time Travel + 血缘 | 快照答「当时是什么」，血缘答「为什么是这个值」 |
| 需要一次性的时点复现 | tag / branch 钉住节点 | 用一次引用替代一条按天计算的保留窗口 |
| 多引擎共读 | 定权威目录 + 显式映射 | 同一张表两个引擎两种解析，根因是权威不清 |
| 语义变更（单位 / 枚举含义） | 走血缘与评审，不走 schema 流程 | 兼容性检查看不见含义 |

> 本节小结：本章四族方案（存储引擎行为 = 传统 DDL；契约与元数据层 = 注册中心 / 目录 / 血缘；表格式 = Iceberg / Delta / Hudi / Paimon；组合族）之间**唯一真正起决定作用的差异**是——**数据文件的每一列有没有一个独立于名字的身份**（写在线格式里、元数据里，或由提交版本代为持有）。有这一层身份时，改名与加列退化成元数据编辑、历史退化成引用计数，代价转移到「id 不可复用」的纪律与读时的投影；没有这一层时，每一次演进都必须动数据、每一段历史都必须靠拷贝或注册中心代为解释，代价转移到停机窗与外部组件的可用性。其余所有维度（Time Travel、兼容性检查、跨引擎、AI 友好度）都是这一条差异在具体场景里的**表现形式**，不能与它并列比较。
