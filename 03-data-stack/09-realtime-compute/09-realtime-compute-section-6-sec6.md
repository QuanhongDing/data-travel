### 9.1 阿里"**Blink 实时计算 EB 级**"8+ 年（2016-2024）

**背景（Why）**

阿里 2016 年面临**双 11 实时计算极限**：
- **订单峰值 60 万笔/秒**——离线 T+1 完全不够
- **多业务实时**——推荐 / 风控 / 营销 / 库存
- **Storm 老化**——**吞吐量 + 状态管理**都不够

**触发点（What）**

2016 年阿里推出 **Blink**（Flink 内部增强版）（[阿里 2016]），目标：
- **双 11 实时 7x**
- **EB 级流处理**
- **毫秒级延迟**

**详细做法（How）**

阿里 Blink 的**5 大核心组件**：

1. **Flink 流批一体（核心创新）**
   - 关键设计：**同一份代码流与批**——流是真持续，批是有界流
   - 关键能力：**一套代码解决流批**
   - 关键数字：**EB 级**

2. **状态管理（核心）**
   - 关键设计：**RocksDB 状态后端 + Checkpoint**
   - 关键能力：**Exactly-once**
   - 关键数字：**TB 级状态**

3. **Flink CDC（核心）**
   - 关键设计：**从 MySQL / Binlog 实时入湖**
   - 关键能力：**数据库变更秒级入数据湖**
   - 关键数字：**延迟 < 5s**

4. **维表关联（核心）**
   - 关键设计：**MySQL / HBase / Redis 维表**
   - 关键能力：**流与维表 join**
   - 关键数字：**P99 < 100ms**

5. **双 11 抗住（核心创新）**
   - 关键设计：**自适应并发 + 反压**
   - 关键能力：**7x 平滑**
   - 关键数字：**双 11 7x**

**阿里 Blink 关键数字**（[阿里 2016-2024 公开数据]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **双 11 峰值** | 基线 | 7x | **+600%** |
| **EB 级** | 不可用 | 100% | **∞** |
| **延迟** | 分钟级 | 毫秒级 | **-99.9%** |
| **Exactly-once** | 不可用 | 100% | **∞** |
| **Flink CDC** | 不可用 | < 5s | **∞** |
| **状态管理** | 不可用 | TB 级 | **∞** |
| **流批一体** | 不可用 | 100% | **∞** |
| **维表关联** | 不可用 | < 100ms | **∞** |

**具体数字（How much）**

- 团队规模：阿里 Blink / Flink 团队 200+ 人
- 关键数字：**EB 级**；**双 11 7x**；**延迟毫秒级**
- 业务影响：覆盖**阿里全集团实时 + 双 11**

**失败教训**

- 早期「**离线不够**」——双 11 实时性差，倒逼 Blink
- **Storm 状态难管**——Storm 状态管理弱，**复杂聚合难**；Flink + RocksDB 解决
- **流批两套代码**——同一逻辑写两遍，**必然漂移**；Flink 流批一体解决
- **双 11 雪崩**——第一版高峰拉垮，**后加反压 + 自适应并发**

### 9.2 字节"**Flink PB 级实时特征**"5+ 年（2019-2024）

**背景（Why)**

字节 2019 年面临**实时推荐特征**：
- **抖音 / TikTok**——**亿级用户实时特征**
- **秒级特征新鲜度**——离线 T+1 不行
- **Feature Store 集成**——**Flink → Redis**

**触发点（What)**

2019 年字节启动 Flink 实时特征（[字节 2019]），目标：
- **秒级特征**
- **亿级用户**
- **Feature Store 集成**

**详细做法（How）**

字节 Flink 实时特征的**5 大核心组件**：

1. **Flink 流式特征（核心）**
   - 关键设计：**埋点 → Flink → 特征计算 → Redis**
   - 关键能力：**秒级特征**
   - 关键数字：**特征延迟 < 5s**

2. **窗口聚合（核心）**
   - 关键设计：**滑动窗口 / 会话窗口**
   - 关键能力：**实时行为统计**
   - 关键数字：**窗口 5 分钟**

3. **状态管理（核心）**
   - 关键设计：**RocksDB + Checkpoint**
   - 关键能力：**Exactly-once**
   - 关键数字：**TB 级状态**

4. **Feature Store 集成（核心）**
   - 关键设计：**Flink 作业直写 Redis + Iceberg**
   - 关键能力：**离线实时同源**
   - 关键数字：**一致性 99.9%**

5. **亿级用户支撑（核心创新）**
   - 关键设计：**Kafka + Flink + Redis + Iceberg 流水线**
   - 关键能力：**亿级用户实时**
   - 关键数字：**6 亿+ 用户**

| **EB 级** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：字节 Flink 团队 100+ 人
- 关键数字：**EB 级**；**特征 < 5s**；**6 亿+ 用户**
- 业务影响：覆盖**字节全部业务**

**失败教训**

- 早期「**特征小时级**」——推荐效果差，倒逼 Flink 秒级

- **Redis 写入瓶颈**——亿级用户写入 Redis 慢，**后预聚合 + Pipeline**

### 9.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**Flink + Kafka 起步**」（**最简单**）——**10+ 任务**
- 关键设计：**Exactly-once + Checkpoint 是底线**
- 团队：**2-3 人**
- 验证标准：**延迟 < 5s**、**无丢失**

**1 → 10 阶段：6-12 个月**

- 扩展到「**100+ 任务**」
- 引入「**RocksDB 状态后端**」
- 引入「**Flink CDC（数据库入湖）**」
- 团队：5-10 人
- 验证标准：**TB 级状态**、**EB 级吞吐**

**10 → 100 阶段：12-24 个月**

- 扩展到「**1000+ 任务 / 跨多业务**」
- 引入「**流批一体**」
- 引入「**Feature Store 集成**」
- 团队：10-30 人
- 验证标准：**流批一致**、**离线实时同源**

**100 → 1000 阶段：12-24 个月**

- 引入「**自适应并发 + 反压**」——大促抗住
- 引入「**多区联邦**」——全球实时
- 团队：30-100 人
- 验证标准：**双 11 7x**、**千万订单/日**

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / Netflix / Uber）印证：**Flink 实时计算不是「**Storm 简单流**」，是「**Flink + RocksDB + 流批一体 + CDC + 自适应**」**5 件套**。
> - 关键时间线：阿里 8+ 年 / 字节 5+ 年 / Netflix 5+ 年 / Uber 4+ 年 —— **实时计算是 4+ 年长期工程**。
> - 选型第一原则：「**Flink + Kafka + Exactly-once**」（**最简单**）——**10+ 任务** → 「**RocksDB + CDC**」（**必须**）→ 「**流批一体 + Feature Store**」（**生产**）→ 「**自适应 + 多区联邦**」（**AI 时代**）。
> - 99% 的失败来自「**Storm 状态弱 + 流批两套 + 双 11 雪崩 + 状态丢失**」——必须有 **Flink + RocksDB + 流批一体 + 反压**。
> - 真正的 ROI 来自「**毫秒延迟 + 千万订单/日 + 双 11 7x**」——是**大厂核心实时计算基础设施的命脉**。
