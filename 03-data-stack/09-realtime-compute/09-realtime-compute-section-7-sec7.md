## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

原表把「Flink / Spark Streaming / Kafka Streams / Storm」四列放进同一张 1–5 分的表，用「实时性 / 状态管理 / Exactly-Once / 生态 / AI 友好」五个维度打分。这个做法有三个结构性错误。

**错误一：四列不在同一个抽象层。** Flink 是**引擎 + 集群 + 运行时**的整体（自己调度、自己管状态、自己容错）；Spark Streaming 是**一种执行模式**（把无界流按批间隔切片，复用批引擎的调度与容错）；Kafka Streams 是**一个库**（跑在你的应用进程里，没有集群可运维）；Storm 是**消息级流运行时**（拓扑 + 逐条确认）。给「引擎 / 执行模式 / 库 / 运行时」打同一张分表，等于给「汽车 / 变速箱 / 车载电台 / 发动机」打分——它们有的是整机、有的是零件，而零件决定不了整机能不能跑。**打分表还漏掉了交付形态这一层**：同一套引擎自建与用托管服务，运维面差一个量级，而原表五个维度里一条也不含运维。

**错误二：「实时性」这一维没有说明是哪个延迟。** 原表给 Flink、Kafka Streams、Storm 都是 5 分，给 Spark Streaming 4 分。但延迟不是一个数，至少有两层：**引擎内部的处理延迟**，和**结果对外可见的延迟**。而可见延迟的下限由**提交边界**决定——数据要等到一个快照点完成才对外可见（见 7.3.4）。给 Flink 与 Kafka Streams 都打 5 分，掩盖了它们下限的成因完全不同：前者的下限是快照间隔，后者的下限是自己的处理与提交节奏。**同一个分数背后是两套机制时，这个分数就不再是信息。**

**错误三：「AI 友好」把两个问题取了平均。** 它至少混了两件事：**实时特征能不能喂给在线推理**（这是数据新鲜度与状态存活期的问题，机制在 7.3.2、7.3.3）、**能不能在流里调用模型**（这是连接器与 UDF 的问题，属于生态）。原表给 Flink 4 分、Kafka Streams 3 分，但这两件事在这两个产品上的相对高低并不一致——一个团队可能因为「特征新鲜度」选 Flink，也可能因为「只有几个简单转换、不想养集群」选 Kafka Streams，而这两种诉求在原表的同一格里被平均掉了。

打分表输出的是名次；选型需要回答的是「在**我的延迟要求、状态规模、并行度伸缩方式、团队运维人力**下，下一步该选哪一种，以及它在什么条件下失效」。本章因此只保留原表五个维度所指向的问题，但把它们重新组织成可判定的判据。

**本章采用的 6 条判据**（每条针对本主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 「一次处理」被定义成什么 | 逐条事件、一批事件，还是一个应用进程内的循环 | 因为它同时决定延迟下限、容错怎么做、以及状态归谁管——三条下游结论都由它导出 |
| 状态存在哪、上限由什么决定 | 进程堆内存 / 本地磁盘 / 远程存储 | 因为状态规模一旦越过内存，访问路径就从「指针」变成「序列化 + I/O」，吞吐换容量的交换从此不可逆 |
| 时间语义是不是一等公民 | 有没有事件时间与水位线，迟到数据怎么处理 | 因为只有处理时间的引擎无法区分「事件发生时刻」与「处理时刻」，乱序与重放都要另建链路 |
| 端到端一致性的上限停在哪一层 | source、引擎、sink，谁参与提交 | 因为引擎内部一致不等于端到端一致，承诺的档位由最弱的一环决定 |
| 并行度的伸缩单位 | 加并行度要不要重分布状态、要不要重建上游 topic | 因为扩容是常态化动作，它的代价决定你的容量规划是「加机器」还是「改架构」 |
| 生态与运维面 | 连接器、SQL 方言、常驻组件数、值班人力 | 因为组件数不乘进账单，乘进人力与故障面——这是打分表最擅长掩盖的一项 |

原表五个维度都还在，只是位置变了：「实时性 → 判据 1 与判据 4」（下限由执行模型与提交边界共同决定）「状态管理 → 判据 2」「Exactly-Once → 判据 4」「生态 → 判据 6」「AI 友好 → 判据 2、3 的推论 + 判据 6」。判据的顺序也不是中性的，它对应一个筛选顺序：判据 1–3 做**结构性筛选**（处理模型、状态位置、时间语义一旦定了，改动成本最高），判据 4–6 做**运行参数权衡**（提交配置、并行度、连接器选择）。顺序不能颠倒的原因很实际：换执行模型等于重写作业，而调快照间隔、加并行度大多只是配置。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Apache Flink | 独立集群的流处理引擎 | 逐条处理 + 分布式快照（checkpoint）+ keyed state | 大状态、CEP、实时数仓 | Apache 2.0 / 云托管 |
| Spark Structured Streaming（及更早的 Spark Streaming） | 一种执行模式（微批） | 把无界流按批间隔切成连续的有界批，复用批引擎的调度与容错 | 已全面使用 Spark 的团队 | Apache 2.0 / 托管服务 |
| Kafka Streams | 应用内嵌的流处理库 | 处理逻辑跑在应用进程里，状态在本地、以变更日志主题兜底，精确一次借 Kafka 事务 | 与 Kafka 紧耦合的轻量转换、聚合 | Apache 2.0 |
| Apache Storm | 消息级流运行时 | 拓扑 + 逐条确认（ack），保证至少一次；状态管理与事件时间不是内建能力 | 2010 年代前期的实时链路 | Apache 2.0 |
| Apache Beam | 可移植 API 层 | 一份 Pipeline 由不同 runner 执行，引擎可替换 | 多云、可移植诉求 | Apache 2.0 |
| 流式 SQL 数据库（RisingWave / Materialize 一类） | 流原生存储 + SQL | 物化视图随输入做增量更新，结果本身可直接查询 | 想把流结果直接当表读 | Apache 2.0 / 商业 |
| Flink CDC / Debezium | 采集层（不是计算引擎） | 从数据库日志捕获变更；Flink CDC 提供无锁的增量快照读法 | 业务库入湖 / 入仓 | Apache 2.0 |
| 托管流计算服务（云上 Flink 托管 / Confluent / Decodable 一类） | 交付形态（横跨各族） | 引擎语义不变，容量、升级与容错交给服务方 | 人力薄、不想养集群 | 商业（按用量） |
| Flink + AI Functions（含流式 LLM 调用） | 组合能力 | 在流作业内以 UDF / 连接器形式调用模型服务 | 实时特征、实时推理 | 取决于模型服务 |

上表 9 项其实分**五族**：**独立引擎族**（Flink、Storm）、**微批族**（Spark Structured Streaming）、**内嵌库族**（Kafka Streams）、**可移植 API 层**（Beam）、**流原生 SQL 库**（RisingWave / Materialize 一类）。托管服务是**交付形态**，横跨各族；CDC 是**采集层**，它经常被混进引擎选型里，但它决定的是「变更怎么进来」，不是「一次处理被定义成什么」。同族内部差异小、跨族差异大——**先分族再选，能省掉一半比较**：你首先要在「换执行模型」「换状态归属」「换运维形态」里选一种动作，而不是在九个名字里挑一个。

**原文件对比过的候选与决策树分支全部保留**，只是重新归类：

| 原决策树分支 | 归入上表哪一行 | 机制归属 |
| --- | --- | --- |
| 复杂流处理（CEP / 状态）→ Flink | 独立引擎族 | 逐条处理 + keyed state + 事件时间都是一等公民 |
| 微批流处理 → Spark Streaming | 微批族 | 无界流按批间隔切片，容错复用批引擎 |
| 简单流处理 → Kafka Streams | 内嵌库族 | 库跑在应用进程里，无需独立集群，伸缩单位是分区 |
| AI 原生 → Flink + AI Functions | 组合行 | 在流作业内调用模型服务，与前三条不是同一层选项 |

**上表只列机制，不断言「某个产品是否支持某特性」**：连接器与语义细节随版本变化很快，把结论写死会立刻过期。凡涉及具体能力，用下面三种**判定方法**自查，而不是相信任何静态清单：

- **某 sink 是否支持端到端精确一次**：查它的官方文档里出现的是「两阶段提交 / 参与式提交」，还是只有「幂等写入」或「至少一次」。前者能进 7.3.4 的最高档，后者不能。
- **某引擎的状态能不能超过内存**：查它的状态后端选项里有没有基于本地磁盘 / 嵌入式 KV 的那一档，以及增量快照是否要求配这一档。
- **某方案的并行度上限**：查它的并行单位由什么决定（分区数？算子并行度？分片数？），再做一次扩容演练——把并行度调大，观察状态是否触发重分布、耗时多久。

### 7.3 机制差异：为什么它们表现不同（核心节）

五族的全部差异可以归因到四个机制维度。选这四个，是因为它们分别是四个必答问题的答案：**「一次处理」是什么（7.3.1）· 状态归谁管、能长多大（7.3.2）· 时间怎么被理解（7.3.3）· 一致性承诺停在哪一层（7.3.4）**。每个维度给出「机制 → 因果 → 公开证据 → 失效条件 → 自验方法」。

#### 7.3.1 「一次处理」的定义：逐条、一批，还是一段进程内循环

**机制是什么**：引擎把「处理一个单元」的边界划在哪里。逐条处理以「一个事件」为一个单元；微批以「一批事件」为一个单元；内嵌库以「一次轮询 / 一个记录循环」为一个单元。

**各候选的实现差异**：

| 候选 | 处理单元 | 延迟下限由什么决定 | 容错怎么做 | 状态归谁管 |
| --- | --- | --- | --- | --- |
| Flink | 单个事件 | 快照间隔 + 提交开销（见 7.3.4） | 分布式快照：屏障随数据流传播、算子对齐后异步持久化 | 引擎（keyed state + 状态后端） |
| Spark Structured Streaming | 一批事件（微批） | 批间隔 | 每个微批复用批引擎的调度与重算 | 引擎（按批边界更新，与批任务同生命周期） |
| Kafka Streams | 一次记录循环中的一条记录 | 自身处理节奏 + Kafka 事务提交 | 本地状态以变更日志主题兜底，重启后从主题恢复 | 库（进程内状态store，后台主题备份） |
| Storm | 单个元组 | 拓扑内处理耗时 | 逐条确认（ack），端到端为至少一次；精确一次需借助更高层抽象 | 不内建（用户自己往外部存储写） |

**由此必然导出的性质**：**因为** Flink 的容错单位是「事件流上的一个一致点」（快照），**所以**它的处理延迟不依赖批间隔，但每次快照会带来对齐与写入开销——**延迟下限与快照间隔绑定，而不是与处理能力绑定**；**因为** 微批的执行单位是「一批」，**所以** 延迟下限直接等于批间隔，批间隔越小、调度与任务启动的固定开销占比越高【经验】，同时批内可以整批优化（这是它能复用批引擎全部优化的原因）；**因为** Kafka Streams 的处理逻辑就在应用进程里，**所以** 没有额外集群、没有第二套调度，**代价是**它没有独立的资源池——你的处理能力与你的应用实例同生共死，一次 GC 或一次线程池打满，直接影响处理进度。

**公开证据**：分布式快照的原始方法由 Chandy 与 Lamport 提出（[Chandy & Lamport, *Distributed Snapshots: Determining Global States of Distributed Systems*, ACM TOCS, 1985]）【公开】，Flink 的检查点机制建立在这一类快照思想之上（Apache Flink 官方文档 · Checkpointing 一节，可自行核验）；微批的模型源自 Spark Streaming 的离散化流（[Zaharia et al., *Discretized Streams: Fault-Tolerant Streaming Computation at Scale*, SOSP, 2013]）【公开】。**可自行核验的判断**：任何关于「处理延迟」的对比数字，先问它量的是哪一段——是从事件产生到结果对下游可见，还是引擎内部算完就停表。两者在同一次对比里可以差一个量级。

**失效条件**：当业务对延迟的要求是分钟级（例如 T+1 的补充跑批、小时级报表）时，微批的全部劣势消失，而它带来的调度与容错复用成为净收益；当业务需要「每个事件都触发一次外部动作」（风控拦截、告警推送）时，微批的批间隔就是不可接受的——**因为动作发生在批边界，一批里的事件会被一起处理**。

**自验方法**：埋一个带唯一标识的事件，从它进入 source 到它出现在下游可见位置，记录端到端时间；重复多次取高分位。这个数才是「实时性」，而不是任何引擎文档里的处理耗时。

#### 7.3.2 状态的位置与伸缩单位

**机制是什么**：算子状态放在哪里、由谁负责它的容错，以及**扩容时状态如何重新分布**。这三件事通常由同一个设计决定。

**各候选的实现差异**：

| 候选 | 状态位置 | 状态上限由什么决定 | 扩容的代价 |
| --- | --- | --- | --- |
| Flink（基于本地磁盘的状态后端） | keyed state 按 key 分区，落在任务本地（可配磁盘型 KV） | 可由磁盘容量承担，但访问要序列化，吞吐换容量 | 按 key 组重分布：恢复时间与状态规模同向增长 |
| Flink（内存状态后端） | 任务堆内存 | 单机内存 | 同上，且受 GC 影响 |
| Spark Structured Streaming | 状态存于执行器的内存 / 外部存储，按批演进 | 受执行器与存储层限制 | 与批任务生命周期绑定，恢复按批重放 |
| Kafka Streams | 进程内状态store + 变更日志主题 | 单实例磁盘 / 内存 | **并行度上限等于上游分区数**：加 task 需要先加分区，而加分区会重新分布 key |
| Storm | 不内建（通常外置到数据库或缓存） | 由外部存储决定 | 与引擎无关，但一致性要业务代码自己保证 |

**由此必然导出的性质**：**因为** Flink 的 keyed state 按 key 分区，**所以**状态可以随并行度水平扩展，**代价是**扩容触发 key 组重分布、恢复时间与状态规模同向增长——**一个 1 TB 状态的作业，扩容不是「加两台机器」而是「等一次全量状态迁移」**；**因为** 把状态放到本地磁盘一档要付出「每次访问都序列化 / 反序列化」的代价，**所以**同一套作业在「内存后端」与「磁盘后端」之间的吞吐差是结构性的，不是调优能补回来的；**因为** Kafka Streams 的任务数由上游分区数决定，**所以**它的伸缩单位不是「机器数」而是「分区数」——**分区只能增不能减，加分区会让 key 重新分布，历史上按 key 聚合过的结果需要重算**，这条约束在选型时极少被算进去，却常在上线半年后变成架构级问题。

**公开证据**：Flink 提供多种状态后端与增量快照选项，且增量快照通常与基于本地磁盘的状态后端配合使用（Apache Flink 官方文档 · State Backends 一节，可自行核验）【公开】；Kafka Streams 以变更日志主题承载本地状态的容错，其任务与分区一一对应（Apache Kafka 官方文档 · Kafka Streams 架构一节，可自行核验）【公开】。**可自行核验的判断**：查目标引擎文档里「状态后端」这一节的选项数——只有一个选项的实现，等于把「状态能不能超过内存」这个问题的答案写死成了「不能」。

**失效条件**：当作业是**无状态转换**（清洗、格式转换、字段映射）时，本节全部讨论失效——没有状态要重分布、没有快照要搬，此时内嵌库族的零运维优势最大；反之，当状态规模接近单机可用内存时，全量快照的序列化与内存回收会先于容量成为问题。

**自验方法**：做一次扩容演练——把并行度调大一倍，记录「状态重分布耗时、期间的处理延迟、恢复后是否重复计算」。这三个数决定你的容量规划能不能靠加机器解决。

#### 7.3.3 时间语义：事件时间与水位线是不是一等公民

**机制是什么**：引擎理解的「时间」是哪个——数据产生的时刻（事件时间）、进入系统的时刻，还是算子在处理它的时刻（处理时间）。乱序与迟到数据的处理方式，完全由这个选择决定。

**各候选的实现差异**：

| 候选 | 默认时间语义 | 事件时间 | 乱序处理机制 | 迟到数据 |
| --- | --- | --- | --- | --- |
| Flink | 处理时间（但事件时间是一等能力） | 支持 | 水位线（watermark）+ 允许迟到窗口 | 可在窗口关闭前计入，之后走侧输出 |
| Spark Structured Streaming | 处理时间（事件时间需显式声明） | 支持 | 水位线 + 事件时间窗口 | 超出水位线的记录被丢弃或单独处理 |
| Kafka Streams | 可基于记录时间戳 | 支持（按记录时间戳） | 以时间戳做窗口划定与宽限期（grace period） | 超出宽限期后，晚到记录不再更新窗口结果 |
| Storm | 处理时间 | 不作为内建能力 | 需自行设计 | 需自行设计 |

**由此必然导出的性质**：**因为** 水位线是一个「单调推进的进度估计」（主文件 §2.2 给出其形式：已见最大时间戳减去允许的乱序度），**所以**它必然在两件事之间取一个平衡——推得慢，迟到数据被纳入但结果延迟；推得快，结果快但迟到数据被丢弃。**这个平衡点不能同时最优化，只能按业务的「可修正性」选**：报表可以慢一点但必须全，告警必须快但可以事后修正。**因为** 只有处理时间的引擎把「事件发生时刻」丢掉了，**所以**它既无法重放历史（重放时处理时间会变），也无法处理乱序（顺序即真相）——**这类引擎的「重算」只能靠重跑整条链路，而不是重放输入**。

**公开证据**：把「事件时间 / 处理时间」与「水位线 / 触发器 / 累积模式」形式化为统一模型的工作集中在 Dataflow 模型论文（[Akidau et al., *The Dataflow Model*, VLDB, 2015]）【公开】；Flink 与 Spark 的事件时间与水位线语义均以各自官方文档为准（可自行核验，注意不同版本对迟到数据的默认处理不同）。

**失效条件**：当输入天然有序、或上游时间戳不可信（采集时间与业务时间差得远）时，强上事件时间只会带来复杂度而没有收益；此时以处理时间 + 幂等重算反而更简单可靠。

**自验方法**：往测试链路里注入一批乱序事件（把时间戳打乱 N 分钟量级），观察两件事：结果是否最终与有序输入一致、以及结果稳定下来需要多久。前者检验正确性，后者就是你要写进 SLA 的「结果延迟」。

#### 7.3.4 提交边界：端到端一致性的上限停在哪一层

**机制是什么**：数据从「被处理」到「对外可见」要跨过一个提交点。source 的读取进度、引擎的内部状态、sink 的写入结果，三者只有落在同一个提交点里，才可能做到端到端精确一次。

**各候选的实现差异**：

| 候选 | 提交单位 | 引擎内部一致 | 端到端上限 | 数据可见的延迟下限 |
| --- | --- | --- | --- | --- |
| Flink + 参与式提交的 sink | 快照边界 | 是 | 端到端精确一次（当 source 进度与 sink 参与同一提交时） | ≈ 快照间隔 + 提交开销 |
| Flink + 普通对象存储写出 | 依赖写入方式 | 是 | 通常只能到「至少一次 + 幂等键」 | 同上 |
| Spark Structured Streaming | 微批边界 | 是 | 通过幂等写入与检查点做到精确一次语义 | ≈ 批间隔 |
| Kafka Streams | 事务边界 | 是 | 在 Kafka 内部可做到精确一次（读-处理-写同一事务） | 与事务提交节奏同阶 |
| Storm | 元组树确认 | 否（不内建状态） | 至少一次 | 与拓扑延迟同阶 |

**由此必然导出的性质**：**因为** 引擎的检查点只覆盖「自己的状态 + 已读到的位置」，**所以** 端到端一致性的上限由**最弱的一环**决定——sink 不参与提交时，无论引擎内部多严格，重启后重复写出的那一批仍然会出现在下游；**又因为** 把数据变成「对外可见」只能在提交点发生，**所以** 你要承诺的可见延迟下限就是提交间隔——**把快照间隔配成 5 分钟，再对外承诺秒级可见，在机制上不可能**。**Kafka Streams 是这条规律的一个特例而不是例外**：它的精确一次之所以成立，是因为读、处理、写发生在同一个 Kafka 事务里，一旦写出目标不是 Kafka（或不是支持事务的组件），它就退回到「至少一次」，与其它引擎在同一条线上。

**公开证据**：Kafka 在 0.11（2017）引入幂等生产者与事务，这是 Kafka Streams 精确一次语义的基础（Apache Kafka 官方文档，可自行核验）【公开】；Flink 官方文档的「端到端精确一次」一节说明了两阶段提交 sink 与检查点的关系（可自行核验）【公开】。**可自行核验的判断**：查目标 sink 的文档里有没有「两阶段提交 / 参与式提交」字样——只有「幂等写入」的，属于另一档，两档在故障恢复时的表现完全不同。

**失效条件**：当业务本身可以容忍重复（幂等聚合、可覆盖写入的宽表、可去重的指标）时，精确一次带来的提交开销与连接器限制是净负担；当延迟要求宽松（分钟级以上）时，提交间隔不再是瓶颈，一致性可以先于延迟优化。

**自验方法**：在测试环境杀掉一个任务实例，观察下游结果里是否出现重复行、缺失窗口或部分可见的批次。出现任一者，说明你实际处在「至少一次」档——此时任何「端到端精确一次」的说法都还没有被验证。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
年成本 ≈ 常驻计算(并行度 × 单并行度规格 × 8760h)
       + 状态与快照存储(状态大小 × 保留份数 × 存储单价)      ← 通常不是大头
       + 快照带宽(状态大小 ÷ 快照间隔)                       ← 常被忽略，且与延迟下限绑定
       + 传输层存储(日写入量 × 队列保留期 × 存储单价)
       + 运维人力(常驻组件数 × 值班面)
```

**主导项与隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| Flink（自建） | 计算项（常驻并行度）+ 人力项（集群、状态后端、快照存储的运维） | **快照带来的带宽与暂停**：状态越大、间隔越短，这部分越接近硬上限，且它不出现在任何一张账单行里 |
| Spark Structured Streaming | 计算项（批引擎常驻或按需） | 微批的**调度固定开销**：批间隔越小，单位时间内启动的任务数越多 |
| Kafka Streams | 近似为零的额外集群成本 | **伸缩单位被分区数锁死**：容量规划的自由度其实在你建 topic 的那一天就定下了 |
| Storm（存量系统） | 计算项 + 人力项（两套技能栈并存） | 状态外置带来的**一致性维护成本**：由业务代码自己承担，出错时最难定位 |
| 托管服务 | 按用量的计算项（单价更高） | **可控性下降**：参数上限、版本节奏、诊断深度都受服务方约束 |

**为什么把「快照带宽」单列**：它不落在存储账单上，而是落在**网络与磁盘吞吐**上，并且它直接压缩了延迟的优化空间。**因为** 快照要一次性搬运状态、**而** 搬运时间正比于状态大小、反比于间隔，**所以**状态越大，「缩短间隔」这条路越早走到头。

**【推算】快照带宽的量级**（推导链完整给出，便于换参数重算）：设某作业状态 1 TB（= 1024 GB）、快照间隔 60 秒、全量快照。则每次快照需要写出的数据量为 1024 GB，持续带宽 ≈ 1024 GB ÷ 60 s ≈ **17 GB/s**【推算】。按一张 10 Gb/s 网卡 ≈ 1.25 GB/s 的有效带宽估算，仅搬运这部分数据就需要约 **14 个节点**（17 ÷ 1.25 ≈ 13.6）【推算】。**这条推算的用途不是算钱，而是回答一个设计问题**：大状态必须走增量快照或延长间隔，靠加节点解决不了——因为搬运量本身与状态同阶。把它换成状态 100 GB、间隔 5 分钟的情形，带宽降到约 **0.33 GB/s**（100 ÷ 300）【推算】，此时全量快照完全可接受。

**【推算】集群账单的量级**：一套 20 节点、每节点 8 vCPU 的常驻集群，按通用型 / 计算型 8 vCPU 档的按需价 **$0.3–0.5/h 量级**（AWS EC2 按需定价页 2024）【公开】，取中值 $0.4/h：20 × $0.4 × 8760 ≈ **$70k/年**【推算】。**同一套预算下，快照存储（保留 3 份 1 TB 状态 ≈ 3072 GB × $0.023/GB-月 × 12 ≈ $848/年，按 AWS S3 定价页 2024 的标准层单价【公开】推算）【推算】还不到它的百分之二**——这说明快照的成本几乎全部在**带宽与暂停**上，而不是在存储上；把「快照省钱」当成优化目标，方向从一开始就错了。

**主导项随场景切换，所以优先级不是固定的**：

| 你的场景 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| 无状态转换、量不大 | 计算项 | 选内嵌库族，别引入独立集群 |
| 大状态 + 秒级可见 | 快照带宽项 | 先做增量快照与状态瘦身，再谈缩短间隔 |
| 简单聚合、已在用 Kafka | 计算项（近零增量） | Kafka Streams；但先确认分区数够不够未来的并行度 |
| 已有 Spark 团队、延迟要求分钟级 | 计算项 + 调度开销项 | 用 Structured Streaming，别为「更像流」重训一个团队 |
| 只要不断线、不想养值班 | 人力项 | 托管服务；用可控性换运维面 |

### 7.5 决策树（每个分支都要有阈值依据）

```
你的处境？
├─ 已经在用 Kafka、逻辑是简单转换 / 聚合、延迟要求秒级以上
│    → Kafka Streams（不引入独立集群）
│      前提：上游分区数 ≥ 你未来一年的期望并行度
├─ 需要复杂事件处理、大状态、或事件时间与乱序处理
│    → 独立引擎族的流引擎（Flink 一类）
│      状态规模超过单机内存时，必须配磁盘型状态后端 + 增量快照
├─ 团队已全面使用 Spark、延迟要求是分钟级而非秒级
│    → 微批执行模式（Spark Structured Streaming 一类）
├─ 对外承诺秒级以内可见、且要求端到端精确一次
│    → 先确认 source 进度与 sink 是否参与同一次提交，再选引擎
│      当前 sink 只支持幂等写入时，先换 sink 或降低承诺
├─ 需要实时特征喂在线推理
│    → 流引擎 + 特征库（Feast 一类）；先定状态存活期与新鲜度要求
├─ 需要在多个引擎 / 多云之间保持可移植
│    → 可移植 API 层（Beam 一类）；代价是吃不到单引擎最新特性
├─ 值班人力薄、不想自建集群
│    → 托管流计算服务；代价是参数上限与版本节奏受服务方约束
└─ 想把流处理结果直接作为可查询的「表」
     → 流原生 SQL 库（RisingWave / Materialize 一类）；先量清常驻内存
```

**阈值依据**（与树上每个判断节点一一对应）：

- **「已经在用 Kafka、简单转换 / 聚合、延迟秒级以上」**：判定方法而非经验值——数一下作业里有没有跨事件的状态（窗口聚合、去重、Join）以及状态规模是否超过单实例可用内存。没有跨事件状态、或状态量很小，即落入本节点；一旦出现大状态或 CEP，Kafka Streams 的伸缩单位（上游分区数）就会成为硬约束（7.3.2）。
- **「上游分区数 ≥ 期望并行度」**：这不是经验值，是由机制导出的等式——Kafka Streams 的任务数与分区一一对应，**并行度上限 = 分区数**（7.3.2）。因此阈值就是「你未来一年期望的并行度」，而分区只能增不能减，加分区会触发 key 重新分布（7.2 判定方法第三条给验证做法：直接做一次扩容演练）。
- **「需要复杂事件处理、大状态、或事件时间与乱序处理」**：来自判据 1–3，不是经验值——这三样恰好是内嵌库族与微批族最不擅长的三件事：跨事件的模式匹配要状态、大状态要独立的状态后端、乱序要水位线（7.3.1–7.3.3）。判定方法：把作业里所有「需要参照其他事件才能决定」的规则列一遍，数量为 0 时本节点不成立。
- **「状态规模超过单机内存」**：由 7.3.2 导出——状态一旦越过内存，访问路径变成序列化 + I/O，全量快照的搬运量也与状态同阶（7.4 的推算：1 TB 状态 / 60 秒间隔 ≈ 17 GB/s）。它没有固定数值，判定方法是把「状态大小」与「单个任务可用内存」比一次，再按 7.4 那条公式算出快照带宽是否已接近集群网卡总量。
- **「团队已全面使用 Spark、延迟要求分钟级」**：由 7.3.1 导出——微批的延迟下限等于批间隔，且批间隔越小、调度固定开销占比越高【经验】。**判据是「你的业务动作会不会因为等待一个批间隔而出错」**：不涉及即时外部动作（拦截、告警、扣减）时，分钟级即可落入本节点；涉及即时动作时，批边界就是不可接受的。另一半「团队已全面使用 Spark」是组织结构判据：换引擎的成本落在人的再学习上，与数据量无关。
- **「对外承诺秒级以内可见、且要求端到端精确一次」**：由 7.3.4 导出——可见延迟下限 ≈ 提交间隔，一致性上限由最弱的一环决定。**这条不设数值阈值，只设一个检查**：先在测试环境制造一次故障（杀掉一个实例），若下游出现重复或部分可见的批次，则当前档位不是精确一次，承诺必须先降下来。
- **「实时特征喂在线推理」**：判定方法是量两个数——**特征的新鲜度要求**（推理请求能接受多旧的特征）与**状态的存活期**（特征在在线存储里保留多久）。两者必须匹配：新鲜度要求高于流转的时间跨度时，任何流引擎都补不上这个差距（7.3.3 的「结果延迟」）。它对应 [§3 设计模式](09-realtime-compute-section-3-sec3.md) 的模式 5 与模式 6。
- **「跨引擎 / 多云可移植」**：来自**锁定约束**，不是技术优劣。判定方法是数两件事——你计划使用的引擎数（≥ 2 才是硬需求），以及云厂商合同期限（长期承诺会降低可移植这份期权的价值）。
- **「值班人力薄」**：判定方法是列出这套方案需要常驻的组件与需要人介入的场景（集群升级、状态后端扩容、快照存储清理、上游 schema 变更），再对照你实际的值班安排【经验】。**关键是组件数而不是人数**：当常驻组件数超过你能持续维持的运维面时，托管服务的单价虽高，但省下的是故障面。
- **「想把流结果直接当表查」**：由 7.3.1 的机制导出——流原生 SQL 库把结果做成可直接查询的对象，代价是常驻资源承担了维护成本。判定方法是 1–2 周内用真实基数跑出一份内存占用曲线【经验】；跑不出来就不该放进生产路径。

**把决策树展开成执行顺序**（同一棵树，按时间轴读）：

1. **第 0 步 · 先量事实**：端到端可见延迟的高分位、状态规模、期望并行度、上游分区数。这四项分别喂给判据 1（一次处理）、判据 2（状态规模）、判据 5（伸缩单位）与判据 4（提交边界），缺了它们，树的每个节点都只能靠印象回答。
2. **第 1 阶段 · 只动配置**：快照间隔、状态存活期（TTL）、水位线允许的乱序度、checkpoint 的保留份数。这些都可回滚，且能在一周内排除掉一批「其实是配置问题」的延迟与内存告警。
3. **第 2 阶段 · 收敛状态**：给状态加 TTL、去掉不必要的 keyed state、把全量快照换成增量快照。这一步的验收标准不是「内存降了多少」，而是 7.4 那条带宽公式的输入值下降。
4. **第 3 阶段 · 才换执行模型**：从微批换到逐条流、或从内嵌库换到独立引擎。会连带重写作业、重建状态与调度，是唯一不可快速回滚的一步。
5. **持续 · 把四件事做进看板**：端到端可见延迟（不是处理耗时）、快照耗时与大小、反压时长占比、状态规模曲线。缺了第一项，「秒级」永远是文档里的一句话而不是事实。

> 这条顺序的机制依据是：**配置 → 状态 → 执行模型** 三层的回滚成本依次上升一个量级，而收益并不按同一比例上升。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 简单转换 / 聚合、已在用 Kafka | Kafka Streams | Flink | 为「更专业的引擎」引入独立集群：多一套运维，换来的是一个你不需要的调度器 |
| 大状态、CEP、事件时间 | Flink | Spark Structured Streaming | 微批的事件时间语义是可用的，但状态按批演进，复杂状态机不自然 |
| 团队已熟 Spark、延迟分钟级 | Spark Structured Streaming | Flink | 为「更像流」重训团队：成本落在人身上，收益落在延迟上 |
| 秒级以内可见 + 精确一次 | 参与式提交的 sink + 逐条流引擎 | 幂等写入 + 至少一次 | 用幂等兜底：下游必须能自己去重，且去重逻辑要单独验证 |
| 实时特征 → 在线推理 | 流引擎 + 特征库 | 流结果直写在线 KV | 直写 KV：缺少特征版本与回填能力，训练/推理一致性难保证 |
| 多个引擎 / 多云可移植 | 可移植 API 层（Beam 一类） | 直接用目标引擎 | 直接用：锁死在单引擎，但能吃全该引擎的最新能力 |
| 不想养集群 | 托管流计算服务 | 自建集群 | 自建：省下的单价换来的是常驻值班面 |

**原文件的四组组合全部保留，并补一组**；每条说明职责边界与运维代价：

1. **Flink + Kafka + Paimon（实时数仓）**：边界是**流作业负责算、主键表负责存与回溯**，事件流只是传输层。运维代价：表侧的合并（compaction）作业必须常驻，它不进流作业的看板，但它的积压会直接表现为查询变慢（机制见 [06 Schema 与 Time Travel §7](../06-schema-and-time-travel/06-schema-and-time-travel-section-7-sec7.md) 7.3.4）。
2. **Flink + CDC + Iceberg（实时入湖）**：边界是**CDC 只负责把变更送达，不做业务聚合**。运维代价：源库 schema 的每一次变更都要在采集链路与湖侧各验证一次；采集层与计算层是两套语义（前者关心变更事件，后者关心处理语义），故障时要先分清是哪一层断的。
3. **Flink + ClickHouse（实时监控）**：边界是**流作业负责聚合、OLAP 引擎负责高频固定模式的查询**，明细归湖、聚合归 OLAP。运维代价：多一条「流 → OLAP」的写入链路，它是新的口径分叉点——必须先明确哪一端是权威。
4. **Flink + 特征库（Feast 一类）（实时特征 → 在线推理）**：边界是**流作业产出特征值、特征库负责在线读取与训练侧回填**。运维代价：特征库同时要服务在线与离线两条读取路径，其**在线存储的存活期必须长于特征的流转延迟**，否则会出现「在线读到旧值、离线回填新值」的不一致。
5. **Flink + 流式模型调用（AI Functions / 流式 LLM）（补）**：边界是**流作业负责事件编排与限流，模型服务负责推理**，模型不持有事实来源。运维代价：模型服务的延迟与限额会成为整条链路的反压源，且它通常是唯一一个不可水平扩容任意倍的组件——必须在流作业侧做超时、降级与旁路。

**组合的共同原则**：每个组合都必须能回答「哪一件持有事实来源、哪一件只是可重建的派生物」；回答不出来时，你得到的是两条链路的复杂度，却得不到任一条链路的确定性。

**组合里最容易出错的四处边界**（每一条都对应一个结构性冲突，与具体产品无关）：

- **批边界被当成事务边界**：以为「一批处理完就等于一次原子提交」，于是在批处理逻辑里做外部副作用；批边界只保证引擎内部状态与进度，不保证外部系统与它同时可见（7.3.4）。
- **状态存活期短于业务窗口**：为了省内存把状态存活期调到最小，结果跨窗口的计算静默漏算——**漏算不会报错**，只会让指标长期偏低，且很难与业务变化区分开。
- **并行度与分区数解耦失败**：以为扩容是引擎侧的事，忘了内嵌库族的并行度上限由上游分区数决定（7.3.2）；等需要扩容时才加分区，等于同时触发 key 重分布与历史结果重算。
- **反压被当成容量问题**：看到反压就加资源，而反压根因常常在下游（写入目标、外部模型服务）；此时扩容把压力更快地推给下游，同时引入一次状态重分布。

### 7.7 选错的代价与迁移成本

**反模式：用微批引擎承诺秒级以下的端到端可见** —— 业务方要求「事件到达后 1 秒内可见」，团队用微批引擎把批间隔配到最小，上线后延迟时好时坏、批间隔越调越小而集群越调越贵 → 因为微批的延迟下限等于批间隔，且批间隔越小、调度固定开销占比越高（7.3.1），把间隔压到极限换来的不是稳定的低延迟而是持续的高开销 → **正确做法**：先确认业务动作是否真的需要亚秒触发；需要就换逐条处理引擎，不需要就把承诺调到批间隔之上。

**反模式：把「开了精确一次配置」当成端到端精确一次** —— 引擎配置里打开了精确一次，下游仍偶发重复数据，团队反复检查引擎参数 → 因为端到端上限由最弱的一环决定（7.3.4），sink 不参与提交时，任何引擎内配置都覆盖不到写出这一步 → **正确做法**：先用 7.3.4 的自验方法（杀一个实例看下游）定出实际档位，再据此要么换 sink、要么在下游补幂等键。

**反模式：用内嵌库做需要大状态的重作业** —— 起初只是几个聚合，半年后状态涨到单机放不下，扩容时才发现在用的库没有独立的状态后端 → 因为内嵌库把处理逻辑与状态都放在应用进程里，它的伸缩单位是上游分区数而不是机器数（7.3.2）→ **正确做法**：先判断状态规模与并行度演进方向；一旦预计需要独立的状态后端与资源池，就换到独立引擎族，而不是给应用实例加内存。

**反模式：把反压当成「需要加机器」的信号** —— 看到反压就扩并行度，扩完短时间好转、随后反压回来，且状态重分布耗时越来越长 → 因为反压常常来自下游（外部接口、写入目标）而不是本算子算力，扩并行度只是把压力更快地灌给下游，同时触发一次状态重分布 → **正确做法**：先看反压发生在哪一个算子、它的下游是谁，区分「算力不足」与「下游慢」，后者只能靠背压协议、批量与限流解决。

**换成另一条路线要动什么**：

| 迁移方向 | 数据迁移 | 逻辑改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| Storm → Flink | 无（流上无长期状态可迁） | 大：拓扑 API 换成流 API / SQL，确认语义差异 | 大：引入集群、状态后端、快照存储 | 事件时间、状态、快照语义 | 6–18 人月 |
| 微批 → 逐条流 | 无 | 中到大：批内全量逻辑要改成增量 | 中：新增常驻集群与状态后端 | 事件时间与状态 | 3–9 人月 |
| 内嵌库 → 独立引擎 | 小：状态本身就在变更日志主题里，可直接作为初始数据 | 中到大：拓扑与状态定义都要重写 | 大：新增集群与状态后端 | 状态后端与快照 | 3–9 人月 |
| 自建 → 托管服务 | 无 | 小：连接器与 SQL 方言的差异 | 中：运维面转移，但保留策略、权限、网络要重建 | 托管平台的操作面 | 1–3 人月 |
| Spark Streaming → Spark Structured Streaming | 小 | 中：DStream 换成结构化 API | 小 | 事件时间与水位线 | 1–4 人月 |

> 量级按「一个熟悉本系统的 3–5 人小组」估算【经验】。**表里最贵的一行是「Storm → Flink」**，因为它的成本不在数据搬运（流上没有长期状态），而在**语义模型整体更换**：从「元组 + 确认」换成「事件 + 时间 + 状态」，作业的重写比例接近重写一遍。**最便宜的两行之所以便宜，是因为它们不换执行模型**——这也说明一件反直觉的事：换运维形态（自建 → 托管）的风险远低于换执行模型。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 简单转换、已在用 Kafka | Kafka Streams | 库跑在应用进程里，没有额外集群；但并行度上限等于分区数 |
| 大状态、CEP、事件时间 | Flink | 逐条处理 + keyed state + 事件时间都是一等公民 |
| 状态超过单机内存 | 磁盘型状态后端 + 增量快照 | 全量快照的搬运量与状态同阶，加节点解决不了 |
| 承诺秒级以内可见 | 先核对提交间隔与 sink 的提交能力 | 可见延迟下限 ≈ 提交间隔，配置不改，承诺就不可兑现 |
| 需要端到端精确一次 | 选参与式提交的 sink | 上限由最弱的一环决定，引擎内部一致不等于端到端一致 |
| 乱序输入、结果必须完整 | 事件时间 + 水位线 + 侧输出 | 水位线把「快」与「全」变成一个必须显式选择的平衡点 |
| 团队已熟 Spark、延迟分钟级 | 微批执行模式 | 批间隔即延迟下限，而它换来了批引擎的全部复用 |
| 值班人力薄 | 托管服务 | 组件数乘进人力与故障面，不乘进单价 |
| 需要多云可移植 | 可移植 API 层 | 用「吃不到单引擎最新特性」换「不锁死在单引擎」 |
| 想在流里调模型 | 组合：流作业做编排与限流 | 模型服务会成为反压源，必须准备超时、降级与旁路 |

> 本节小结：本章五族方案（独立引擎族 = Flink / Storm；微批族 = Spark Structured Streaming；内嵌库族 = Kafka Streams；可移植 API 层 = Beam；流原生 SQL 库）之间**唯一真正起决定作用的差异**是——**「一次处理」被定义成什么**：一个事件、一批事件，还是一段跑在应用进程里的循环。定义成事件，延迟下限只受提交边界约束、状态必须由引擎自己容错，代价是多一套集群与状态后端；定义成一批，延迟下限直接等于批间隔，代价转移到调度开销与「动作只能发生在批边界」；定义成进程内循环，没有额外集群、状态与应用的生死绑定，代价是并行度被上游分区数锁死。**实时性、状态管理、Exactly-Once、生态、AI 友好这五个维度，全部是这条定义的展开，而不是可以与它并列比较的独立分数。**
