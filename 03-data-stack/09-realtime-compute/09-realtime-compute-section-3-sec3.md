## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

实时计算的七个模式（Lambda / Kappa / 流批一体 / CDC 入湖 / 实时特征 / 流式 ML / 流式 LLM）常被讲成「按场景挑一个」。但决定它们彼此不同的，只有三条底层约束：**输入是有界还是无界**、**历史能不能被重放**、**端到端要不要 Exactly-once**。第一条区分了「批」与「流」；第二条决定了出错后能不能靠重放修正，因而决定了 Lambda 与 Kappa 的分野；第三条决定了状态、检查点与 Sink 提交协议必须付出什么代价。

这三条之所以是底层约束，是因为它们都不是「配置项」：输入边界由业务决定，重放能力由日志保留期决定，Exactly-once 由连接器能力决定。你可以在同一套代码里切换执行模式，但不能在没有保留日志的前提下宣称「随时可以回算历史」，也不能在 Sink 不支持事务的前提下宣称「端到端只处理一次」。

因此本节的组织方式是：**先立约束，再谈模式与引擎**。每个模式先回答「它被什么约束逼出来」，再给结构示意；结构决定机制，机制决定代价，代价决定它在哪个规模上失效。下面这张表是后面所有讨论的前提。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式（有界 vs 无界） | 是同一条链路还是有冷热两条；代码是一份还是两份 | 「流批一体 = 一份代码」——严格说是一份口径定义 + 两个执行计划 |
| 访问模式（点查 / 聚合 / 关联） | 状态规模、维表关联方式、是否需要 CEP | 「引擎快就够了」——维表关联与去重才是吞吐瓶颈的常见来源 |
| 变更频率与历史要求 | 是否需要保留冷路径与重放能力 | 「口径改了重算就行」——重算能力取决于日志/快照保留期，不是取决于引擎 |
| 一致性要求 | 状态后端、检查点间隔、Sink 提交协议 | 「开了 Checkpoint 就有 Exactly-once」——端到端语义还取决于 Sink 是否支持事务 |
| 规模与成本约束 | 状态放内存还是落盘、并行度与峰值倍率 | 「状态大就加内存」——TB 级状态必须落本地盘并配增量检查点 |
| 团队技能与运维能力 | 维护一套还是两套实现、能否读懂反压指标 | 「先上流，批后面再说」——批路径缺席时，历史数据永远无法被修正 |

一句话：**实时计算的模式差异，最终都落在「这条链路能不能重算历史」与「这条链路在故障后从哪里继续」这两件事上**；引擎选型、并行度、窗口大小都是它们的下游结果。

### 3.2 模式逐个拆解（核心节）

七个模式在下面逐个拆解：Lambda（3.2.1）、Kappa（3.2.2）、流批一体（3.2.3）、Flink CDC 实时入湖（3.2.4）、实时特征工程（3.2.5）、流式 ML 与在线学习（3.2.6）、流式 LLM 与 Agent（3.2.7）。它们的区别可以用三个问题一次问清：**输入有没有边界、历史能不能重放、状态与产物落在哪**。前两个就是 §3.1 的前两条约束；第三个不是第三条约束本身，而是第三条约束（端到端语义要求）留在架构上的落点——正因为语义要求的高低决定了状态、检查点与 Sink 提交协议要付什么代价，速览表里这一列才会在七个模式之间拉开差异。先给速览表。

| 模式 | 输入边界 | 历史重放 | 状态/产物落点（第三条约束的下游） | 主要代价 |
| --- | --- | --- | --- | --- |
| Lambda | 有界 + 无界并存 | 靠批层全量重算 | 批视图 + 实时视图 | 同一口径两份实现、服务层要合并两个来源 |
| Kappa | 无界 | 靠日志重放 | 结果存储 | 重放范围受日志保留期约束 |
| 流批一体 | 同一份定义的两种执行 | 靠湖表快照/批读回算 | 湖表（Paimon/Iceberg） | 小文件与快照管理的持续运维成本 |
| CDC 实时入湖 | 无界（变更日志） | 靠日志位点 + 快照 | 湖表 + 源库 binlog | 依赖源库日志配置与主键，DDL 会传导 |
| 实时特征工程 | 无界 | 靠离线侧同一份定义回填 | 在线 KV + 离线湖表 | 存储翻倍、TTL 与训练时间窗必须对齐 |
| 流式 ML / 在线学习 | 无界 | 靠样本流重训 | 模型仓库 + 特征存储 | 持续训练算力 + 版本与回滚机制 |
| 流式 LLM / Agent | 无界 | 靠决策日志回溯 | prompt/输出日志 + 工具状态 | 外部配额固定、尾延迟与降级路径 |

#### 3.2.1 Lambda 架构（流 + 批）

- **被什么约束逼出来**：批引擎吞吐高但不能秒级出结果，流引擎能秒级出结果但当时无法重算历史——两者能力互补，于是被迫在同一份业务逻辑上摆两条链路。
- **结构**：

  ```text
  同一份业务逻辑，实现两遍
    ┌─ 批处理层（Spark）：全量、可重算、小时级 ──▶ 批视图
    └─ 速度层（Flink）：只算增量、秒级 ─────────▶ 实时视图
                                    └─▶ 服务层合并两个视图（合并规则要人为定义）
  关键：两条链路的"同一指标"由不同代码产生，差异靠对账而非结构保证
  ```

  ```sql
  -- 实现 1：批（T+1 全量重算）
  INSERT OVERWRITE TABLE ads_gmv_daily
  SELECT dt, shop_id, SUM(amount) AS gmv
  FROM   dwd_order WHERE dt = '${bizdate}' GROUP BY dt, shop_id;

  -- 实现 2：流（同一口径要再写一遍，窗口/迟到数据处理方式与批不同）
  INSERT INTO ads_gmv_daily
  SELECT DATE_FORMAT(TUMBLE_START(et, INTERVAL '1' DAY),'yyyy-MM-dd'), shop_id, SUM(amount)
  FROM   dwd_order_stream GROUP BY TUMBLE(et, INTERVAL '1' DAY), shop_id;
  ```

- **为什么这样设计有效**：因为批层持有全量、可以随时重算并纠正错误，而流层只承担「最近一段时间的近似正确」，所以系统对外表现是秒级可见且最终可由批层校正——「实时视图不要求完全正确」这条让步，换来了不需要在流层解决全部历史问题。
- **代价**：一份业务逻辑两份实现：口径定义、过滤条件、迟到数据与去重规则都要各写一遍；两套资源常驻；服务层必须定义「批视图与实时视图如何合并、谁覆盖谁」，而这个合并规则本身就是一条需要维护的业务逻辑。
- **失效点**：当口径变更频率上升时，「批层可纠错」这个优点会反转成「两套口径长期并存」——因为批视图与实时视图是两条独立代码路径，变更只能分批上线，中间必然出现一段时间两者口径不同；而差异只能靠对账发现，表现是「同一指标两个数字、没人能立刻说清哪个对」。
- **真实使用**：Lambda 架构由 Nathan Marz 提出并命名，2011 年前后成形、2015 年通过《Big Data》一书系统化（可按「Lambda Architecture Nathan Marz」自行核验）【公开】；主文件 §1.4 的演进时间线记录 2013-2016 年间的典型实现是 Storm + Kafka + HBase。

#### 3.2.2 Kappa 架构（仅流）

- **被什么约束逼出来**：如果日志能长期保留、且作业可以重跑，那么「批层」就不是必需的——重放同一份日志即可重算历史，第二套代码带来的口径漂移才是真正的问题。
- **结构**：

  ```text
  只保留一条日志与一套代码
   写入 ──▶ 不可变日志（Kafka，长期保留）
                  │
            流作业（Flink）──▶ 结果存储
                  ▲
   需要回算 / 修 bug 时：重置 offset，从日志重放（同一份代码）
  前提：日志保留期 ≥ 需要重放的历史；且重放必须幂等
  ```

- **为什么这样设计有效**：因为历史与实时走的是同一份代码、同一条日志，所以「口径漂移」在结构上不可能发生——任何一次口径修正在重放之后对全历史自动生效；这也让修 bug 与回算变成同一个动作。
- **代价**：重放成本随保留期与数据量线性增长，重放期间要额外占用集群资源；日志保留期直接决定了「能回算多远」，而这个决定通常由存储成本而不是由业务需求做出；作业必须保证重放幂等（同一 offset 段重跑不产生重复结果）。
- **失效点**：当需要回算的历史超过日志保留期时，「只有一套代码」这个优点会反转成「历史不可重建」——因为结果的唯一来源就是那条日志，日志一旦清理，任何口径变更都无法回溯历史；此时必须补一条批路径，也就是退回 Lambda。
- **真实使用**：Kappa 由 Jay Kreps 在 2014 年提出（"Questioning the Lambda Architecture"，O'Reilly Radar；可按标题自行核验）【公开】。多数团队的现实选择是「日志保留期覆盖一个季度到一年」的有限 Kappa【经验】——保留期一到，能力边界就到了。

#### 3.2.3 流批一体（Flink + Iceberg/Paimon）

- **被什么约束逼出来**：同一份业务口径同时要被实时看板与离线报表消费，而两套代码必然漂移——如果存储层能同时被流式写入与批量读取，口径差异就只剩下「执行计划」这一层。
- **结构**：

  ```sql
  -- 存储层：既能被流式增量写入，也能被批式读取（同一张表、同一份数据）
  CREATE TABLE dws_trade_1d (
    dt DATE, shop_id BIGINT, gmv DECIMAL(18,2),
    PRIMARY KEY (dt, shop_id) NOT ENFORCED
  ) WITH ('connector' = 'paimon', 'changelog-producer' = 'lookup');

  -- 流：无界输入 + 窗口，增量更新
  INSERT INTO dws_trade_1d
  SELECT CAST(TUMBLE_START(et, INTERVAL '1' DAY) AS DATE), shop_id, SUM(amount)
  FROM   dwd_order_stream GROUP BY TUMBLE(et, INTERVAL '1' DAY), shop_id;

  -- 批：有界输入（历史分区）读同一张表，重算/补数
  INSERT OVERWRITE dws_trade_1d
  SELECT dt, shop_id, SUM(amount)
  FROM   dwd_order WHERE dt = '2026-10-18' GROUP BY dt, shop_id;
  ```

- **为什么这样设计有效**：因为聚合表达式、过滤条件与表结构在两种执行计划之间共用，差异被压缩到「输入有没有边界、是否开窗口」这一个维度，所以口径漂移从「两份代码的漂移」降级为「同一份定义在不同执行计划下的差异」——可枚举、可测试；同时批作业读的是同一张湖表，补数与回算不需要另建链路。
- **代价**：存储层要持续付小文件合并（compaction）与快照过期（snapshot expiration）的运维成本；流式入湖是小批量高频写入，天生产生大量小文件；读批的人越多、保留快照越多，元数据服务压力越大。此外窗口语义只在流式执行中可用，所以严格说这不是「字符串完全相同的一份 SQL」，而是「一份口径定义 + 两个执行计划」。
- **失效点**：当写入频率高、分区粒度细时，「一份数据两种读法」这个优点会反转成「存储运维成为主要负担」——因为每次流式提交都可能产生新文件与新快照，compaction 跟不上写入速度时，读取延迟与元数据查询都会抖动；表现是批读变慢、快照过期策略挤占存储，而不是流作业报错。
- **真实使用**：阿里主导的 Blink 合并回 Flink 主干（主文件 §1.4 的演进时间线记为「2018–2019：Blink 合并入 Flink 上游主线，阿里主导」，合入的具体版本与年份以 Apache Flink 官方发布说明为准）【公开】；Blink 作为阿里内部的 Flink 增强分支何时出现、从哪一年起成为集团内实时主链路的默认形态，属业界通说而非 §1.4 所载，可按「阿里 Blink」「Flink release notes」等关键词检索官方发布说明自行核验【经验】；Paimon 在 2023 年前后从 Flink 社区衍生（主文件 §1.4 的演进时间线）【公开】。可自行核验的判断方法：看它的存储是否同时提供「流式写入」与「批式读取」，并且批读能否读到一致快照。

#### 3.2.4 Flink CDC 实时入湖

- **被什么约束逼出来**：维表与业务表的变更必须秒级可见，而「定时全量刷新」的新鲜度由刷新周期决定——当维度变更频率高于刷新周期时，定时刷新在结构上就不成立。
- **结构**：

  ```sql
  -- 变更捕获直接读数据库日志，作业内完成"全量快照 + 增量追平"
  CREATE TABLE orders_cdc (
    order_id BIGINT, status STRING, amount DECIMAL(18,2),
    PRIMARY KEY (order_id) NOT ENFORCED
  ) WITH ('connector' = 'mysql-cdc',
          'hostname' = 'mysql-primary',
          'database-name' = 'orders',
          'table-name' = 'order_info',
          'scan.incremental.snapshot.enabled' = 'true');

  INSERT INTO ods_order_lake SELECT * FROM orders_cdc;
  -- 前提：源库开启日志复制、表有主键、日志保留期覆盖最长断点恢复窗口
  ```

- **为什么这样设计有效**：因为变更流来自数据库自身的日志（顺序、完整、可定位），入湖不再需要外部同步组件或定时全量拉取，所以「维表新鲜度」由日志延迟决定（通常远小于分钟级【经验】）而不是由刷新周期决定；同时全量快照与增量追平在同一作业内衔接，省掉了「先导全量再切增量」的胶水层。
- **代价**：把依赖从应用层下沉到数据库层——需要开启日志复制、给复制权限、保证表有主键、并让日志保留期覆盖最长断点恢复窗口；源库的 DDL 会沿链路传导到湖表结构，因此 schema 演进策略必须显式定义（加列通常可自动、改类型与删列必须人工确认）。
- **失效点**：当源库存在大量无主键表或频繁 DDL 时，「无需定时全量刷新」这个优点会反转成「入湖链路不稳定」——因为无主键表无法做可靠的增量快照与去重，频繁 DDL 会让下游表结构反复演进；表现是作业重启后长时间处于快照阶段（长尾追平），或湖表结构与源库不一致导致下游查询报错。
- **真实使用**：Flink CDC 自 2020 年（Flink 1.11 起）进入主流（主文件 §1.4 的演进时间线）【公开】；实时入湖的主流形态是「CDC + 湖表（Paimon / Iceberg）」【经验】。

#### 3.2.5 实时特征工程

- **被什么约束逼出来**：在线推理要的时效是秒级，而训练样本必须带事件时间才能做正确的时点对齐——同一份特征要同时满足两种读法，靠「批算一套、流算一套」必然训练/推理不一致。
- **结构**：

  ```text
  一份特征定义，两个物化结果
   事件流 ──▶ Flink 特征作业 ──┬─▶ 在线存储（KV，毫秒读）──────▶ 推理服务
                                └─▶ 离线存储（湖表，含事件时间）──▶ 训练样本
  纪律：定义一份、物化两份；离线回填按事件时间对齐，避免样本穿越到未来
  ```

  ```python
  # 特征定义示意：同一份定义同时落在线与离线两个 store
  driver_stats = FeatureView(
      name="driver_stats",
      entities=["driver_id"],
      ttl=timedelta(hours=2),      # 在线侧的新鲜度上限
      source=stream_source,        # 同一个流做为在线与离线的共同来源
      online=True,
  )
  ```

- **为什么这样设计有效**：因为训练与推理读的是同一份特征定义的两次物化，所以「离线指标好、在线效果差」这类问题从结构上被消掉大半——差异只剩「物化时间点不同」这一项，而它可以被时点对齐与新鲜度指标直接量化。
- **代价**：同一份特征要写两处（在线 KV + 离线湖表），存储与写入成本翻倍；在线侧的 TTL 与离线训练样本的时间窗必须对齐，否则训练样本里的特征在推理时已过期；回填必须走与在线相同的计算逻辑，否则又回到两套实现。
- **失效点**：当特征需要长窗口（如近 30 天累计）时，「在线与离线同源」这个优点会反转成「在线侧必须维护大状态」——因为在线存储通常只保留 TTL 内的值，长窗口要么由流作业用状态维护（状态随 key 数线性增长），要么在离线算完再回灌（新鲜度下降、又出现两个来源）；二者必须选一个，没有第三条路。
- **真实使用**：字节的推荐特征链路以秒级新鲜度为目标（见同章 [§ 6 落地实践](09-realtime-compute-section-6-sec6.md)）【经验】；Feast、Tecton 是常用的特征平台，判断方法是看它能否把同一份定义物化到在线与离线两个 store，以及能否做时点正确的回填。

#### 3.2.6 流式 ML / 在线学习

- **被什么约束逼出来**：分布漂移的时间尺度短于「重训—评估—发布」的周期——如果模型更新要按天甚至按周走人工流程，它的效果会在下一次更新之前就已经衰减。
- **结构**：

  ```text
  在线学习的闭环（不是"流处理 + 模型"两件事）
   事件流 ──▶ 特征 ──▶ 推理 ──▶ 结果与反馈 ──▶ 训练样本流（带事件时间）
                                        │
                            按窗口持续训练 ──▶ 新模型版本
                                        │
                            校验（离线评估 + 影子流量）──▶ 灰度上线 / 回滚
  纪律：训练样本与线上打分必须来自同一份特征；模型版本必须可回滚
  ```

- **为什么这样设计有效**：因为反馈样本以流的形式持续产生、模型更新走同一条可回滚的发布通道，所以模型能跟着分布漂移走，而不需要等一次完整的离线重训周期；「持续跟上分布」这条能力由此成立。
- **代价**：需要常驻的持续训练算力与一套模型版本管理 / 回滚机制；标签往往延迟到达，必须显式处理「样本已入流、标签未到」的中间态（否则会把无标签样本当成负样本）；线上效果波动会直接来自训练侧，排障要同时看数据链路与模型链路。
- **失效点**：当系统存在反馈回环（模型只曝光它已经偏好的内容、反馈样本由自己的决策生成）时，「持续跟上分布」这个优点会反转成「模型自我确认」——正反馈会放大既有偏好、使样本分布收窄；表现是离线指标持续变好而线上多样性下降，且这种退化不会触发任何数据质量告警。
- **真实使用**：【经验】在线学习在推荐与风控场景被广泛讨论，但多数团队实际落地的是「近线训练 + 定期发布」而不是严格意义的逐样本在线更新；可自行核验的判断方法是问两件事——模型多久更新一次、更新是否需要人工审批。

#### 3.2.7 流式 LLM / Agent

- **被什么约束逼出来**：实时决策链路需要「语义判断」（这段文本是不是投诉、这条日志是不是异常），而规则引擎维护成本随时间上升——LLM 补上了判断能力，但它是一个外部的、有配额与尾延迟的依赖。
- **结构**：

  ```text
  事件流 ──▶ 触发条件（规则 / CEP）──▶ 组装上下文（检索 + 会话状态）
                                            │
                                   异步调用 LLM（超时 / 重试 / 并发上限）
                                            │
                                   结构化输出校验 ──▶ 动作（工具调用 / 写库 / 告警）
  纪律：LLM 调用必须是异步算子 + 有并发上限；输出必须校验后才能落库
  ```

- **为什么这样设计有效**：因为流作业只承担「触发、组装上下文、校验输出」这三件确定性工作，把不确定性最大的生成步骤隔离在带超时、重试与降级的异步算子里，所以上游的实时链路不会被 LLM 的尾延迟与限流拖垮；同时输出经结构化校验后才落库，错误输出不会污染下游数据。
- **代价**：必须为外部调用设置并发上限、缓存与规则兜底（没有兜底路径就等于把流链路的可用性绑定在第三方配额上）；必须记录 prompt 版本、模型版本与原始输出，用于回溯与合规；单次调用的成本随上下文长度增长，而流式场景的事件量通常远大于人工触发场景。
- **失效点**：当事件速率超过外部调用的配额上限时，「实时决策」这个优点会反转成「排队放大延迟」——因为配额是固定的而输入速率可变，积压会随峰值累积，且越晚处理的事件价值越低；表现是决策延迟从秒级涨到分钟级，而链路本身没有任何组件报错，只是队列越来越长。
- **真实使用**：【经验】多数团队把 LLM 调用放在流作业的异步算子中，并对上游做限流 + 规则兜底。可自行核验的判断方法是看两处：这条链路上有没有独立的「降级到规则」的路径，以及能否按模型版本回溯历史决策。

七个模式共享同一条判据与同一组代价：

- **共享判据**：**这条链路能不能重算历史？** 答案来自日志保留期与湖表快照策略，而不是来自引擎能力。Lambda 用批层回答，Kappa 用日志回答，流批一体用湖表回答——回答不了的模式，在生产里都会变成「错误只能向前修，历史没法改」。
- **共享代价**：状态必须落盘并配检查点（不只内存）、反压必须可观测、峰值必须靠机制而不是人工加并行度。这三项与选了哪个模式无关。
- **共享前提**：端到端语义的下限由**最弱的一环**决定——Source 可重放、状态有检查点、Sink 支持事务/幂等，三者缺一，端到端就退回至少一次。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 / 引擎 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 复杂事件处理（CEP）、需要按事件时间做模式匹配 | Flink（DataStream / CEP）+ RocksDB 状态 + Kafka | 微批引擎的窗口边界与 CEP 语义不匹配 | 是否需要跨事件序列匹配与超时触发 |
| 实时数仓：同一份口径要同时供实时看板与离线报表 | 流批一体（Flink + Paimon），服务层用 StarRocks 一类 OLAP | Lambda 会让同一口径存在两份实现 | 口径变更频率与能否接受两次上线 |
| 实时监控：指标秒级刷新、查询以聚合为主 | Flink 或 Spark Structured Streaming + ClickHouse | 用 Kafka Streams 做跨源聚合时状态与运维能力不足 | 查询是聚合还是点查；是否需要跨源关联 |
| 实时特征：推理侧读特征、训练侧读样本 | 实时特征工程（Flink + Feast / Tecton） | 不引入特征平台会让训练与推理各算一遍 | 平台能否把同一份定义物化到在线与离线 |
| 简单流处理：单源、无跨流 Join、逻辑轻 | Kafka Streams（内嵌库） | 上 Flink 集群的运维成本高于收益 | 是否已有 Kafka、是否需要独立集群与多源 Join |
| 历史可重放且保留期足够长 | Kappa（仅流） | Lambda 的第二套代码会带来口径漂移 | 日志保留期是否覆盖需要回算的历史 |
| 历史超出保留期、或需要频繁全量重算 | Lambda（流 + 批） | 纯 Kappa 在日志过期后无法重算 | 需要回算的最远时间点 vs 日志保留期 |
| 只要求「不丢」，可接受重复 | 至少一次（重放 + 幂等 Sink） | 强行上端到端 Exactly-once 会拉长检查点间隔 | Sink 是否支持事务；重复是否可通过幂等消除 |
| 实时入湖：库表变更要秒级进湖 | Flink CDC + Iceberg / Paimon | 定时全量刷新的新鲜度由刷新周期决定 | 源表是否有主键、日志保留期多长 |
| AI Agent 实时决策：需要语义判断 | 流式 LLM / Agent（Flink + Kafka + LLM） | 纯规则引擎的维护成本随时间上升 | 是否有规则兜底路径与并发上限 |
| 峰值不可预测、日常水位低 | 上述任一模式 + 反压自适应并发 | 人工调并行度在零点脉冲下来不及 | 背压与滞后指标能否驱动自动扩缩 |
| 内部小流量、逻辑一次性 | 单作业 + 处理时间语义（不上 Watermark） | 事件时间与状态是为规模与正确性付的费 | 迟到数据是否可丢弃 |

表后要点：**最常被误选的一对是「Kappa」与「Lambda」**。误选的实际后果有两种，且都不在当期报错。其一，日志保留期只有几天却按 Kappa 建链路——半年后一次口径修正需要回算，才发现历史日志早已清理，只能接受「新口径只对以后生效」，历史数据永久性地与报表对不上。其二，在口径每月都要调整、且需要频繁全量重算的场景里坚持 Lambda——每次口径变更都要改两处、分两次上线，中间的时间窗里两个视图口径不同，业务方看到的是「同一指标两个数字」，而信任一旦丢失，后续每次数字分歧都会被重新质疑。判据只有一句：**先量「需要回算的最远时间点」与「日志/快照能保留多久」，再选模式。**

### 3.4 组合模式：真实系统不会只用一种

- **流批一体 + CDC 入湖**：CDC 负责把源库变更秒级搬进湖表，流批一体负责让同一份湖表既能被实时聚合读取、也能被批式重算。职责边界是「采集」与「计算」分开——CDC 作业不做业务聚合，聚合逻辑只存在于流批一体的那一份定义里。运维代价是两条链路的延迟叠加（入库延迟 + 聚合延迟），因此端到端新鲜度必须分段监控。适合规模：需要实时数仓、且源库以 MySQL/PostgreSQL 一类有日志的关系库为主【经验】。
- **实时特征 + 流批一体**：特征由流作业写入，训练样本与实时特征共用一份定义；湖表同时作为特征回填的来源与历史样本的存放处。职责边界是「特征定义」只有一份、物化两份；一旦出现「离线一套特征代码、在线另一套」，这个组合的收益立刻消失。运维代价是存储翻倍、TTL 与训练时间窗必须一起评审。适合规模：在线推理对特征新鲜度敏感、且已经建了湖表【经验】。
- **流式 LLM / Agent + 在线学习**：Agent 的决策与反馈构成训练样本流，模型更新后回到 Agent 的决策路径。职责边界是「触发与校验」留在流作业内、「判断与生成」交给模型；运维代价是要同时管理模型版本与 prompt 版本，且必须保留「降级到规则」的开关。适合规模：事件量稳定、外部调用配额可控、且决策可回滚的场景【经验】。

这三组组合有一个共同点：**实时链路的价值来自「新鲜」，而新鲜必须有人为它的错误买单**——流批一体的买单方式是湖表维护，实时特征的买单方式是存储与对齐，LLM 链路的买单方式是配额与兜底。设计组合时先写清谁买单，比先画架构图更有用。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 忽视状态管理 | 作业运行数小时后内存持续上涨、GC 时间变长，最终 OOM 或频繁重启 | 状态无上界时，key 数随数据量增长，内存必然被吃穿；重启后又要从头恢复 | 认为状态是「运行时的东西」，没有把状态生命周期当成设计的一部分 | 状态落盘（RocksDB 一类）+ 显式 TTL + 定期清理；对无界 key 空间设上界并告警 |
| 未启用 Checkpoint | 故障重启后结果出现缺口或重复；作业无法升级（没有可恢复点） | 没有检查点就没有一致恢复点，语义退化为「尽力而为」；Savepoint 也无从产生 | 开发环境默认不开、上线忘了显式开启，且没有把「检查点成功率」纳入监控 | 显式开启检查点并设置语义；监控检查点时长与失败率；升级前先打 Savepoint |
| 窗口设置不合理 | 状态量随窗口长度线性膨胀；或结果周期性缺失、迟到数据被大量丢弃 | 窗口大 → 状态与乱序容忍度一起变大；窗口小 → 结果不完整、被下游当成最终值 | 用「看板刷新间隔」直接当窗口大小，没有考虑乱序与状态成本 | 窗口与水位线一起定：先估乱序容忍度，再定窗口；用允许迟到 + 侧输出处理边界数据 |
| 数据倾斜 | 少数子任务 CPU / 状态远高于其他，整体吞吐由最慢的子任务决定 | 按 key 分区时热点 key 落在同一子任务上，并行度再高也无法摊开 | 按业务含义选 key（如按大客户 ID），没有做 key 分布分析 | 两阶段聚合（加盐打散再合并）、单独处理热点 key、或对热点维度改用广播/维表 |
| 滥用 Timer | 定时器数量随数据量增长，检查点变大、恢复变慢 | Timer 与状态一起被快照，数量级放大后检查点耗时与恢复时间同步放大 | 把「延时触发」当成业务的自然表达，没意识到它是有状态的 | 优先用窗口与水位线表达时间语义；确需 Timer 时限制其数量并定期清理 |
| 未做反压监控 | 上游延迟持续上升但各算子 CPU 都不高；端到端延迟阶梯式恶化 | 反压是下游变慢向上游传导的结果，不监控就看不到「谁慢」，只能看到「整体慢」 | 只监控作业是否存活与延迟数值，没有把背压指标当作一级信号 | 用引擎自带的反压指标 + 滞后指标做告警；把「背压持续时间」纳入发布门禁 |
| 依赖过时 API | 升级引擎版本时编译或运行失败；新旧算子在同一个作业里混用 | 状态与序列化格式随版本演进，跨版本迁移需要专门的重启/升级步骤 | 沿用旧版本模板，没人维护版本升级这条路径 | 跟随官方升级说明逐版本升级，把「可升级性」当成验收项；保留 Savepoint 迁移演练 |

展开三个最危险的：

**忽视状态管理**最危险，因为它在开发与小流量下完全正常。状态的机制特性是「按 key 累积」，而 key 空间通常随用户与设备增长——只要没有上界，它就一定会随业务增长吃穿内存。它在生产中的典型暴露方式是**大促或流量翻倍当天 OOM 重启**，而此前几周的监控曲线看起来只是「内存缓慢上升」，很容易被当成正常波动。

**未启用 Checkpoint**的危险点在「它平时不产生任何成本，只在故障时决定损失量级」。没有检查点，作业在故障后只能从头消费或从某个外部位点重启，语义退化为至少一次甚至更差；更隐蔽的后果是**作业无法升级**——没有 Savepoint 意味着每次改逻辑都要停链路并接受数据缺口。可操作的防呆方式是把「检查点成功率」纳入发布门禁：成功率长期低于阈值就不允许上线新逻辑。

**数据倾斜**的暴露方式是「并行度加了，耗时没变」。它的机制是分区键与数据分布不匹配，热点 key 永远落在同一个子任务上；因此加并行度只会增加空转的子任务。它在生产中的典型形态是**大客户 / 头部商家 / 热门商品导致的单点慢**，而整体吞吐由这个最慢的子任务决定——与「Cell 化系统里的热点用户」是同一类问题，只是发生在流作业的分区层。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：**规模或负载形态跨过某个阈值时，原来正确的模式会变成错的**。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 状态从 GB 级涨到 TB 级 | 内存状态后端 + 全量检查点 | 内存装不下、检查点耗时随状态线性增长 | RocksDB 一类本地盘状态 + 增量检查点 | 中：要评估本地盘 IO 与检查点存储带宽 |
| 从「能跑」到「峰值不可预测」 | 固定并行度 + 人工扩容 | 零点脉冲下来不及调度，背压堆积成雪崩 | 反压自适应并发 + 分级限流降级 | 中：要先把背压与滞后指标接到调度上 |
| 从实时监控扩到实时数仓（口径要与离线报表对齐） | 流侧单独一套实现 + 离线另有一套（事实上的 Lambda） | 口径每月都要改，两份实现无法同时上线，两个数字同时存在 | 流批一体（一份定义 + 两个执行计划） | 大：要换存储并重写聚合链路 |
| 日志保留期覆盖不了需要回算的历史 | Kappa（仅流） | 口径修正时历史已不可重建 | 补一条批路径（退回 Lambda），或将需要长历史的主题单独延长保留 | 中偏大：要重建批链路与对账 |
| 从定时全量同步到秒级维表 | 定时全量刷维表 | 维表变更频率高于刷新周期，新鲜度不达标 | Flink CDC 入链路 + 维表本地缓存 | 中：要开源库日志、处理主键与 DDL |
| 从「离线训练 + 在线推理」到分钟级更新 | 人工触发的训练发布流程 | 分布漂移快于发布周期，效果在下一次更新前衰减 | 持续训练 + 模型版本自动灰度 | 大：要建样本流、版本管理与回滚机制 |
| 链路开始调用外部 LLM | 同步调用 + 无并发上限 | 配额固定而事件速率可变，队列随峰值累积 | 异步算子 + 并发上限 + 规则兜底 + 缓存 | 中：要补降级路径与决策日志 |

一条规律：**迁移成本最高的是「历史可重建能力」的变化**（Lambda ⇄ Kappa ⇄ 流批一体），因为它要动存储与重算路径，而这两者一旦上线就有大量下游依赖；并行度、状态后端、窗口大小这类调整是可增量执行的。可操作的做法是把迁移拆成「新链路旁路跑一段，与旧链路比对差异并对账 → 差异清零后切读 → 最后切写并下线旧链路」三段，每段之间留一次完整的对账周期。

补充两点判据。其一，**跃迁的触发条件应该是可观测的**——「状态量连续数周超阈值」「检查点耗时逼近间隔」「背压持续时长超阈值」「口径变更频率超过每月一次」这类信号应该由监控直接给出，而不是等一次事故来宣布。其二，**每次跃迁都要留可回退路径**：状态后端与存储格式的更换要靠 Savepoint 或双写过渡，语义从至少一次升级到 Exactly-once 要确认 Sink 是否支持事务，否则升级只会把重复从「可见」变成「不可见」。

- [ ] 端到端语义是否被逐环核过：Source 可重放 + 状态有检查点 + Sink 支持事务或幂等？最弱的一环在哪里？
- [ ] 状态是否有明确上界（TTL / key 空间上界 / 清理策略）？有没有状态量监控与告警？
- [ ] 检查点间隔与实际耗时之比是否留有余量？检查点失败率是否被监控并纳入发布门禁？
- [ ] 每个有状态算子的 key 分布是否被分析过？有没有已知的热点 key 及其处理方案？
- [ ] 窗口大小与水位线是一起定的吗？允许迟到多长时间，被丢弃的数据有侧输出可查吗？
- [ ] 定时器（Timer）的数量是否随数据量增长？检查点里 Timer 占比是多少？
- [ ] 反压指标是否接到告警与自动扩缩？能不能从监控上直接看出「是哪个算子慢」？
- [ ] 维表是定时全量刷新还是变更捕获？变更到可见的延迟是多少？
- [ ] 训练样本与线上打分是否来自同一份特征定义？离线回填是否按事件时间对齐？
- [ ] 链路里所有外部调用（LLM、外部 API、下游库）是否都有超时、并发上限与降级路径？

自检的用法：**上面 12 项里只要有 3 项以上答不上来，这条链路在故障时大概率只能靠人工兜底**，因为答不上来的项集中在「恢复点、语义、状态上界」这三类——它们平时不产生任何运行成本，只在故障与变更时决定损失量级。反过来说，能答完这 12 项的链路，即使当前规模不大，也已经具备了随规模演进而不重写的能力。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 历史可重放、保留期覆盖回算需求 | Kappa（仅流） | 一份代码一条日志 → 口径漂移在结构上不可能 |
| 历史超出保留期、需频繁全量重算 | Lambda（流 + 批） | 批层持有全量，可随时纠正；代价是两套实现 |
| 同一口径要供实时与离线，且变更频繁 | 流批一体（Flink + Paimon/Iceberg） | 一份定义两个执行计划，漂移从「两份代码」降为「两种计划」 |
| 维表变更要秒级可见 | Flink CDC 实时入湖 | 变更流来自数据库日志，新鲜度由日志延迟决定 |
| 训练与推理必须一致 | 实时特征工程（一份定义物化两份） | 同源定义 + 时点对齐，消除训练/推理口径差 |
| 分布漂移快于重训周期 | 流式 ML / 在线学习 | 反馈样本持续入流，模型更新走可回滚通道 |
| 需要语义判断的实时决策 | 流式 LLM / Agent（异步 + 兜底） | 生成步骤隔离在带超时重试的算子里，不拖垮主链路 |
| 单源、逻辑轻、已用 Kafka | Kafka Streams（内嵌库） | 无独立集群运维成本；代价是状态与多源能力有限 |
| 只要求不丢、可接受重复 | 至少一次 + 幂等 Sink | 语义下限由最弱一环决定，幂等比事务便宜 |

> 本节小结：本主题下**决定模式选择的唯一那条约束，是「这条链路能不能重算历史」**——它决定了要一条链路还是两条（Kappa vs Lambda）、决定了存储要不要支持流写批读（流批一体）、也决定了出错时只能向前修还是可以回头改。状态、检查点、窗口、反压全部是这条约束的下游工程：因为它们只决定「故障后从哪里继续」，而重放能力才决定「错了以后还能不能改」。
>
> 判断顺序由此确定：**先量「需要回算多远」，再确认「能保留多久」，最后才选模式与引擎**。端到端语义则按最弱一环判定——Source、状态、Sink 三者缺一，链路实际就只会退到至少一次。
>
> 💡 **思考锚点**：按 §3.3 表后的顺序给自己算一次——写下你需要回算的「最远历史时间点」和日志/快照实际能保留的天数，再指出 Source、状态、Sink 三段里端到端语义最弱的那一段；这三个答案把你推向 Kappa 还是 Lambda？
