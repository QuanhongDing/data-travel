## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

清单的问题不是列错了方向，而是**没有时间维度**：「Flink 集成 LLM」与「Flink 2.0 路线」被并列写成同一批「演进方向」，读者据此排路线图时，无法判断哪一行下周就能动工、哪一行还要等两年。同一个清单里，「已发布且有稳定接口」与「路线图里的一句话」混在一起，排期必然踩空。

具体会踩三种空：

- **把路线图排成工期**：某一项写的是「2024 路线」，读者按已发布能力给它排了三个月，实际它可能连预览都没进。工期一旦许出去，后面每一步都被这一项拖着。
- **把既有能力当成新增能力**：某一项其实是引擎早就有的通用机制（例如异步 I/O），只是换了个调用目标（模型服务）。它记账记在「AI 能力」上，于是在选型会上被当成新特性重新评估一遍。
- **把建设方自述当成生产验证**：某一项有公开文章、有数字、看起来像案例，但那篇文章是建设方写自己系统。它证明的是「有人这么做」，不是「这件事在别人的生产里被验证过」。

本节把每个方向放进三级里。判据是可核验的三条，而不是「感觉成熟」：

- **L1 生产可用**：① 已 GA 且有正式 release note；② 有第三方（非厂商、非建设方）公开生产案例；③ 接口稳定。**三条全中才算。**
- **L2 可试点**：已可用但接口或生态未稳，或公开案例只有建设方自述，或只在小规模被验证。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

三条判据的顺序不是中性的：**① 看有没有正式发布，② 看有没有建设者之外的人在生产里用过，③ 看接口稳不稳**。其中 ② 最容易被悄悄放宽 —— 把建设方自己写的工程博客算成「第三方案例」，就等于把 L2 写成 L1。本节不做这种折算：**缺 ② 就是 L2，没有「准 L1」「L1 的边界案例」这种级别。** 降级不是贬低，是准确：L2 对应的动作是「做 PoC、不做核心依赖」，这恰好是大多数「前沿」当前应有的位置。

「L3 观望」也不是「别管它」。它对应的动作是**记录，并且不预留假设** —— 不要在接口设计里留一个「以后接模型」的空位，不要在容量规划里留一笔「以后要跑 Agent 的算力」。预留的假设会在评审里被当成已定方案，最后变成一项没人认领的欠账。

读这张表时还有一个技术：**级别不是对能力的评价，而是对证据的评价**。同一项能力，随着公开证据增加会沿着 L3 → L2 → L1 移动，而移动所需的不是它自己变好，是**别人开始证明它**。所以每一行都可以问一句：「它的 ② 在哪？」答不出来，就按当前级别排事。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| 流内调用模型 | L2 | ① 所需机制（异步 I/O、UDF、连接器）在官方文档中有正式条目；② 公开案例均为建设方自述；③ 接口无标准，各家自封装 | 在非关键链路做 PoC：异步算子 + 并发上限 + 规则兜底 + 结果缓存，先量配额与 p99 |

| 实时特征工程（Flink + Feast / Tecton） | L2 | ① 特征平台有正式发布记录；② 公开案例来自建设方自述；③ 在线与离线的一致性靠平台约定而非保证 | 直接做 PoC：本节里机制最清楚、代价可算的一项；别把「同源」当自动保证 |

| 流式 GraphRAG（Flink + Neo4j Connector） | L3 | ① 无标准链路；② 无建设方之外的公开生产案例；③ 抽取结果的版本与回滚无约定 | 图是累积状态，误抽取不可逆；先做离线抽取 + 定时重建 |
| Flink 2.0 这条发布线 | L2 | ① 官方 release notes 可核验；② 无建设方之外的公开生产案例；③ 新执行能力与状态后端仍在演进 | 不要为它改架构；只在小作业上验证升级路径与状态兼容性 |
| 流批一体（Flink + Paimon / Iceberg） | L2 | ① Apache Paimon 1.0.0（2024）与 Apache Iceberg 的 1.x 发布线（2022 年前后进入 1.0）的官方 releases 页可核验【公开】；② 公开案例来自建设方自述；③ 提交协议各 sink 不一致 | 按同章 [§7.3.4](09-realtime-compute-section-7-sec7.md) 逐 sink 核对提交边界，再决定对外的承诺等级 |
| 自治流处理（AI 自动调优、自适应） | L3 | ① 「AI 自动调优」无正式发布条目；② 无建设方之外的公开生产案例；③ 与既有规则式自适应混在一起，难以区分 | 别把已 GA 的规则式自适应当成 AI 能力记账 |
| 边缘流处理（Flink on 边缘 / IoT） | L3 | ① 无面向边缘的正式发行版；② 无建设方之外的公开生产案例；③ 资源约束下的状态与提交语义未定义 | 观望；边缘侧先用轻量本地聚合，不要把状态机搬过去 |

> 本节没有任何一行同时满足 ①+②+③，**因此 5.1 表里没有 L1 行**。最容易被误标成 L1 的是「流内调用模型」与「实时特征工程」：它们依赖的机制（异步 I/O、特征平台）确实有正式发布记录，① 站得住，缺的是 ② 与 ③ —— 公开可查的生产记录几乎都由提供能力的厂商或建设方自己发布，接口也还没有跨厂商的标准形态。按本节 5.1 的三条判据，缺 ② 就是 L2，这不是贬低：L2 对应的动作是「做 PoC、不做核心依赖」，与这两个方向的现状一致。若你的组织手上有一条由建设方之外的第三方独立验证过的记录、且接口已收敛到可对齐的稳定形态，补上 ② 与 ③ 即可升 L1 —— 判据是公开的，升级只需补证据。

**既有卡点：前沿之所以是前沿，是因为既有方案在这里卡住了**

把 AI 加进实时链路之前，先看既有栈卡在哪（其中状态、时间语义与反压三类在 [§ 2 核心原理](09-realtime-compute.md) 里已经定义过；「提交边界：端到端一致性的上限停在哪一层」见同章 [§7.3.4](09-realtime-compute-section-7-sec7.md)，运维面见同章 [§7.5](09-realtime-compute-section-7-sec7.md) 的「值班人力薄」分支）。能绕开它们的方向才是真演进，绕不开的就只是换了个前端：

- **状态的位置与规模**：大状态要落盘、要配检查点，快照的搬运量与状态同阶（同章 [§7.4](09-realtime-compute-section-7-sec7.md)）。AI 方向里凡是要维护大状态的（长窗口特征、会话上下文、图），都会撞回这一条。
- **时间语义与乱序**：事件时间与水位线是一等公民，迟到数据必须有明确归宿。模型调用带来的额外延迟会把「结果可见时间」推后，但不会改变水位线的语义。
- **提交边界**：端到端语义的上限由最弱的一环决定（source 可重放、状态有检查点、sink 参与提交），而 AI 引入的外部调用全在这条边界之外。
- **反压与峰值**：峰值必须靠机制而不是人工加并行度；配额固定的外部依赖无法通过加并行度消化掉峰值 —— 这是本节新增的唯一一条真正的新约束。
- **运维面**：集群升级、状态后端扩容、快照存储清理、上游 schema 变更，这些常驻工作与是否上 AI 无关，却决定这条链路能不能长期活着。

对照这五条可以看出：本节没有一个方向改变了前三条中的任何一条。它们改变的是「算子内部算什么」，以及「链路新增了哪个外部依赖」—— 后者恰好落在第四条上。

### 5.2 演进方向逐条拆解（核心节）

下面四条展开的是 5.1 表里最需要机制解释的四个方向：5.2.1 与 5.2.2 是「模型进流」（调用与检索），5.2.3 是「特征与样本」（AI 训练对实时链路提出的老要求），5.2.4 是「多步决策与抽取」。表里其余各行（在线学习、Flink 2.0、流批一体、自治与边缘流处理）没有独立展开：它们要么不缺机制说明，要么机制部分尚未形成可评估的形态。

每条都按同一组六行写：旧做法与它的卡点、AI 改变了什么机制、由此得到的、由此付出的、证据与来源、成熟度；再补一行失效点与一行真实使用。

写这六行时，**真正承重的是第二行** —— 「机制」那一行必须落在某一处具体的替换上：成本函数的系数、接口边界的位置、人工判断换成统计判断、或者只是换了个前端。落在「换前端」上的方向，会在第三行立刻暴露：因为它说不出真正的收益来自哪一步。

#### 5.2.1 流内调用模型：把「判断」放进算子

- **旧做法与它的卡点**：规则引擎（正则、阈值、CEP 模式）承担流上的语义判断。卡点不在算力，而在**维护成本**：
  - 规则数量随业务分支线性增长，每条规则的例外又要再加一条规则；
  - 规则一旦没人维护，它的失效是静默的 —— 不报错，只是判错；
  - 判断需要「语义」时（这段文本是不是投诉），规则只能靠关键词堆叠，覆盖率的天花板很低。
- **AI 改变了什么机制**：把「人工枚举规则」换成「按概率做判断」。这是**判据来源的替换**（确定性规则 → 统计模型），不是执行引擎的变化：引擎仍逐条处理事件，变的只是算子内部那一步算什么。
- **由此得到的**：因为判断能力不再来自人工枚举，所以「同一类语义判断覆盖到长尾分支」成为可能 —— 原来新增一个话术要写一条规则，现在改一次 prompt 或换一版模型就够，覆盖成本从「每条分支一次开发」变成「一次配置」。
- **由此付出的**：确定性下降，而且是两处。
  - 其一，模型输出受采样与版本漂移影响，同一批事件重放不保证同一结果，于是本书贯穿的那条判据 —— 「这条链路能不能重算历史」—— 从确定性丢失变成概率性丢失：复盘、审计、A/B 归因都失去可复现性。必须靠 prompt 版本、模型版本、采样参数留痕 + 结果缓存，把首次结果固化下来。
  - 其二，模型服务是链路里唯一**不能靠加并行度扩容**的组件：配额固定，而输入速率可变。

  ```text
  「在流里调模型」的形态（不是新执行模型，是一个受约束的异步算子）
    事件流 ──▶ 触发条件（规则 / CEP）
                 │
                 ├─ 命中缓存 ──▶ 直接输出（重放时读缓存，而不是再调一次）
                 └─ 未命中 ──▶ 异步调用（并发上限 C，超时 T，重试 N 次）
                                 ├─ 成功 ──▶ 结构化校验 ──▶ 落库 / 动作
                                 └─ 超时 / 限流 ──▶ 降级到规则 ──▶ 落库 / 告警
  ```

  【推算】吞吐上限由并发与尾延迟共同决定：上限 ≈ C / T_p99。取 C = 32 并发、T_p99 = 2 秒，则上限 ≈ 32 / 2 = **16 次/秒**。触发率高于这一值的部分会累积成积压，积压量 = ∫(λ(t) − Q)dt（λ 为触发率、Q 为上限），而越晚处理的事件价值越低。推导链只有除法与积分两项，换成你自己的 C 与 T_p99 可复算出同一个形式。这条推算解释了为什么「实时决策」在配额被击穿时会退化成「排队放大延迟」，而此时链路里没有任何组件报错。
- **证据与来源**：Apache Flink 官方文档的「Asynchronous I/O」页与 SQL「User-defined Functions」章节就是这两项机制的正式条目 —— 异步 I/O 在 Flink 1.x 早期（2017 年前后）就已进文档，它服务的是「调用外部系统」这个通用问题，与调用目标是模型还是数据库无关【公开】；同章 [§7.2](09-realtime-compute-section-7-sec7.md) 已把「Flink + AI Functions（含流式 LLM 调用）」归入**组合能力**这一层，而不是引擎特性。**判定方法**：打开目标引擎的官方 release notes，看有没有一项引擎内建的模型调用能力；若只有连接器与 UDF 示例，说明它是「在流里调模型」的工程模式，不是引擎新语义。
- **失效点**：当事件速率超过配额上限时，「实时判断」这个优点反转成「越晚处理越没价值」—— 因为配额是固定的而输入速率可变，积压随峰值累积；表现为决策延迟从秒级涨到分钟级，而链路本身没有任何组件报错。
- **成熟度**：L2。① 站得住，缺 ② 与 ③（②：公开案例来自厂商与建设方自述；③：接口无跨厂商标准，各家自封装）。
- **真实使用**：【经验】可核验的落地形态是「异步算子 + 上游限流 + 规则兜底」，并把降级期间产生的结论单独打标，以便事后区分哪些结论来自模型、哪些来自规则。

#### 5.2.2 流式 RAG：把索引的新鲜度搬进流里

- **旧做法与它的卡点**：RAG 的 Embedding 由离线批任务生成，索引新鲜度等于批周期。对「新文档刚上传就要能被检索到」的场景，卡点是**批周期这个时间常数**，不是算力 —— 加机器也缩短不了它，只能改链路形态。
- **AI 改变了什么机制**：Embedding 从「批作业里的一个步骤」变成「流上的一个算子」，判据从「多久跑一次批」换成「事件到索引的端到端可见延迟」。变的不是模型，是**索引的更新时间常数**。
- **由此得到的**：因为索引更新与事件到达走同一条链路，所以「新文档已可见」从一句承诺变成链路自身的性质，可以被端到端延迟这个指标直接度量，而不是靠对齐批作业的调度时间。
- **由此付出的**：
  - 向量库的写入路径成为新的故障点（写放大、索引重建），它此前不在实时链路的关键路径上；
  - **删除路径**最常被漏掉：合规要求「某个文档的向量必须消失」，在「流写入 + ANN 索引」下删除往往要靠墓碑标记或重建索引，删除的可见延迟与写入的可见延迟不是同一个量级，必须单独设计，而不是当成写入的一个分支；
  - 召回质量出现「新旧不一致窗口」（新文档已索引、旧文档还没重算），窗口长度等于旧文档的重算周期；
  - 向量检索的性能声称必须带条件 —— 数据量、维度、召回率目标、硬件、是否含过滤。不带这些限定语的「毫秒级检索」，不构成可比较的技术事实。
- **证据与来源**：向量库与开放表格式当前支持到什么范围，以各自的官方文档「delete / upsert」章节与官方 releases 页为准（可按这两个入口逐条核验，不引用二次转述的博客）；「实时特征 + 向量库 → 在线推理」与同章 [§3.2.5](09-realtime-compute-section-3-sec3.md) 的「一份定义、两处物化」是同一机制的两个用例。**判定方法**：在向量库官方文档里找「删除 / 更新向量」与「索引重建」两节，若删除要靠全量重建，则写入实时性带来的收益会被删除的代价抵掉一半。
- **失效点**：当写入速率远高于索引重建能力时，「新文档秒级可见」反转成「索引持续重建、查询 P99 抖动」—— 因为重建期间的索引不可服务或降级服务，而写量与文档到达率同阶。
- **成熟度**：L2。① 站得住，缺 ② 与 ③（前者无建设方之外的公开生产案例，后者写入与删除接口未统一）。
- **真实使用**：【经验】常见形态是「热文档走流式索引、冷文档按批补齐」，而不是全量走流式 —— 全量走流式会把写入与索引重建的压力集中到同一条链路上。

#### 5.2.3 实时特征工程：一份定义、两处物化

- **旧做法与它的卡点**：训练用批算的特征、推理用流算的特征，于是有两套实现，口径漂移，表现为「离线指标好、在线效果差」且难以归因。卡点是**两套实现**，不是延迟 —— 延迟问题可以调参数，两套实现的问题只能靠改结构。
- **AI 改变了什么机制**：把「算一份写出去」换成「定义一份、物化两份」—— 一份定义（实体、来源、TTL）挂在两个 store 上：在线 KV（毫秒读）与离线湖表（带事件时间）。变化落在接口边界上，不在算法上。
- **由此得到的**：因为训练与推理读的是同一份定义的两次物化，所以两者差异只剩「物化时间点不同」这一项，而它可以被时点对齐与新鲜度指标直接量化 —— 归因从「猜测」变成「量一个数」。这是本节所有方向里唯一能给出这种性质的方向。
- **由此付出的**：
  - 同一份特征写两处，存储与写入成本翻倍；
  - 在线侧 TTL 与离线训练窗口必须对齐，否则训练样本里的特征在推理时已经过期；
  - 回填必须走与在线相同的计算逻辑，否则又回到两套实现；
  - 一个反转：当特征需要长窗口（如近 30 天累计）时，「在线与离线同源」这个优点会反转成「在线侧必须维护大状态」—— 在线存储通常只保留 TTL 内的值，长窗口要么由流作业用状态维护（状态随 key 数线性增长），要么离线算完再回灌（新鲜度下降、又出现两个来源）。二者必须选一个，没有第三条路。
- **证据与来源**：Feast 官方文档的「Point-in-time joins」与「Online store」章节就是上述两项能力的正式条目（可按这两个关键词在其官方文档中核验，年份以文档当前版本与 release 记录为准）；字节的秒级特征新鲜度案例见同章 [§6 落地实践](09-realtime-compute-section-6-sec6.md)（建设方自述，不构成第 ② 条）；同章 [§7.5](09-realtime-compute-section-7-sec7.md) 把「实时特征喂在线推理」列为决策树的独立分支，判据是「新鲜度要求 vs 状态存活期」。**判定方法**：问平台两个问题 —— 能否把同一份定义物化到两个 store，能否做时点正确的回填。
- **失效点**：当新鲜度要求高于状态存活期时，「训练与推理同源」反转成「在线读到旧值、离线回填新值」—— 因为两者读的是同一份定义的两个物化点，而物化点之间的时差由 TTL 与回填周期决定，不由模型需要决定。
- **成熟度**：L2。① 站得住，缺 ② 与 ③（前者无建设方之外的公开生产案例，后者在线与离线的一致性靠平台约定，没有跨平台的稳定接口）。这是本节最值得先做 PoC 的一项：机制清楚、代价可事先算，且不依赖任何未发布的特性。
- **真实使用**：【经验】常见的落地顺序是「短窗口特征走流、长窗口特征走批 + 回灌」，再用同一份定义把两边的口径对齐；先从短窗口开始，是因为它对在线状态的规模要求最低。

#### 5.2.4 流式 Agent 与流式 GraphRAG：把决策与抽取搬进流里

- **旧做法与它的卡点**：事件流的响应是「触发预设动作」（阈值告警、固定路由）；需要跨步骤的判断（先查、再判、再动作）只能靠人或事后批处理。卡点是**多步判断没有自动化载体**。
- **AI 改变了什么机制**：把「人做多步判断」换成「按概率走多步外部调用」。这不是新的执行模型：Agent 环路在流里就是一串异步算子加外部工具调用；GraphRAG 则是「抽取算子 + 图写入」。
- **由此得到的**：因为判断步骤不再需要人，所以「事件驱动的多步决策」在理论上可以做到秒级 —— 这是本节里唯一由 AI 直接带来的新可能性。注意前面还站着「理论上」三个字：可行性取决于下面那条代价。
- **由此付出的**：
  - 延迟不再是单次调用，而是**调用步数 × 每步尾延迟**（乘法关系），尾延迟被放大成 p99 不可控；
  - 图是累积状态，抽取错误写进图之后不可逆，必须预留「抽取版本 + 可重建」这条路，否则一次模型换版就会污染历史结论；
  - Agent 的动作常有外部副作用，而流引擎的 Exactly-Once 覆盖不到外部系统 —— 提交边界止于 sink（同章 [§7.3.4](09-realtime-compute-section-7-sec7.md)），幂等键必须由业务侧提供，引擎只能保证「不跳过」或「可能重放」；
  - 多步调用把 5.2.1 的配额约束再乘上步数：假设一条决策链有 4 步调用、每步 p99 为 2 秒，则这条链路的延迟下限已接近 8 秒（【推算】，各步串行的最坏情况；实际取决于能否并行与是否有缓存）。
- **证据与来源**：LangChain（2022 年开源）与 AutoGen（2023 年发布）这类编排框架都有自己的官方发布记录【公开】，但它们不是流引擎组件；同章 [§3.2.7](09-realtime-compute-section-3-sec3.md) 已给出纪律 —— 「LLM 调用必须是异步算子 + 有并发上限；输出必须校验后才能落库」。**判定方法**：数一下这条决策链里有几步外部调用，再把每步的 p99 相加，看结果是否还落在业务的等待窗口内；加不出来就不该放进实时路径。
- **失效点**：当模型换版带来抽取口径变化时，「多步决策自动完成」反转成「历史结论不可复现」—— 因为图与缓存里的旧结论由旧版本产生，而新版本不会重新给出同样的答案，除非有版本隔离与重建机制。
- **成熟度**：L3。单步分类 / 抽取可视为 5.2.1 的一个用例（随之标 L2）；多步自主决策与流式图构建保持 L3。
- **真实使用**：【经验】公开可核验的形态集中在「单步抽取 / 分类 + 结构化校验 + 规则兜底」；多步自主决策目前没有可核验的生产形态，这也正是它停在 L3 的原因。

**四个方向共享的判据与代价**

| 方向 | 改变的机制 | 得到 | 主要代价 | 级别 |
| --- | --- | --- | --- | --- |
| 5.2.1 流内调用模型 | 判据来源：规则 → 统计模型 | 长尾语义分支的覆盖成本下降 | 不可重算 + 配额固定 | L2 |
| 5.2.2 流式 RAG | 索引的更新时间常数：批周期 → 事件级 | 「新文档已可见」可被度量 | 写入与删除路径成为新故障点 | L2 |
| 5.2.3 实时特征工程 | 接口边界：算一份 → 定义一份、物化两份 | 训练与推理的差异可量化 | 存储翻倍 + 长窗口反转成大状态 | L2 |
| 5.2.4 流式 Agent / GraphRAG | 判断步骤的承担者：人 → 多步外部调用 | 多步决策理论上可秒级完成 | 延迟按步数相乘 + 图不可逆 | L3 |

四条共享同一条判据：**这条链路还能不能重算历史？** 5.2.1 与 5.2.4 的答案被模型输出的不确定性削弱；5.2.2 的答案取决于索引能否重建；5.2.3 的答案取决于回填是否走同一份逻辑。答不出来时，生产里都会变成同一个后果 —— 错误只能向前修，历史改不动。

四条也共享同一组前提：**外部依赖必须有并发上限、降级路径与观测**。这三件与选哪个引擎无关，与链路里有没有外部依赖有关。

### 5.3 与本主题既有栈的接口在哪

这一节不写「与 X 结合」。**接口边界只有三种形态**：

- **同步调用**：调用方等结果。失败责任全在调用方（超时、重试、熔断），代价是调用方的延迟被外部依赖锁死。
- **异步投递 + 回执**：调用方不等结果。必须额外定义「回执丢了怎么办」——否则得到的是「发出去过」而不是「做成了」。
- **写库后再查**：把一致性推迟到查询时刻。失败不再表现为链路报错，而表现为结果偏旧，这是最难查的一类故障。

三者的失败责任归属不同，混着用就会出现「某个环节挂了但链路不报错、只是数字变旧」的局面。判据只有一条：**边界两侧能不能各自独立失败** —— 一侧挂了，另一侧要么降级，要么明确停在哪儿。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 流作业 → 模型服务 | 异步请求，一次请求一次响应，带配额；结果经结构化校验后落库 | 流作业侧：超时、重试上限、降级到规则、结果缓存 | 无标准接口，各家自封装（同章 §7.2 归为组合能力） |
| 流作业 → 向量库 | upsert 写入；删除单独设计，不是写入的一个分支 | 写入方（补偿与索引重建）；删除的合规责任在业务侧 | 连接器多靠社区与自研 |
| 流作业 → 特征库 | 在线 KV（毫秒读、带 TTL）+ 离线湖表（带事件时间） | 特征定义方：定义唯一，物化两处 | 需要平台承担一致性与回填 |
| 流作业 → 湖表（Paimon / Iceberg） | 提交边界止于 sink | 最弱的一环：source 可重放、状态有检查点、sink 参与提交，缺一即降级 | 端到端上限需逐 sink 核对（同章 §7.3.4） |
| 流作业 → 外部动作（告警、扣减、写业务库） | 有副作用的调用，不可回滚 | 业务侧：幂等键；引擎只能保证「不跳过」或「可能重放」 | 无统一语义 |
| 在线检索 → 冷向量 / 冷特征 | 查询时的跨介质取回（不是流作业的职责） | 查询侧：预热、降级到热层结果 | 跨层取回延迟是业务的可见代价 |

读这张表只需要抓住一点：**流的可重算性只延伸到它能控制边界的最后一层**。越过这条边界（模型服务、工具调用、业务库写入），一致性就从「引擎保证」变成「业务自己保证」—— 幂等键、结果缓存、可回滚的动作设计，全都落在这一侧，而它们不属于引擎的配置项，属于应用设计。

还有一条容易漏掉的接口：**降级路径本身也是接口**。当模型服务不可用时，链路要回到哪个行为？如果答案是「回到规则」，那么这套规则必须一直在维护 —— 它不能是「上模型之前的那版规则、之后就没人管了」。否则链路在正常情况下依赖模型、在异常情况下依赖一份三个月没人碰过的规则表，可用性是两份不确定性的乘积。

最后一条边界在数据侧的体现：**流作业写到下游的字段，要能被下游判断出「这条结论是模型给的还是规则给的」。** 只写一个结论字段，下游无法区分来源，也就无法在模型降级期间调整它对数据的信任度；加一个来源标记的成本很小，缺了它，一次降级会在下游变成一场口径争论。

三种接口形态之间的选择也有判据：**看调用方能不能承受等待。** 决策要影响当下这一条事件的处理路径时，只能同步（并把超时压到业务能接受的范围）；决策只影响后续动作时，应该走异步投递 + 回执；对一致性要求高但不要求即时可见的，走写库后再查，并接受「查到的可能是旧结论」。同一套链路里混用三种形态是正常的，不正常的是**不写清哪一段属于哪一种**。

### 5.5 被过度宣传的部分

**「在流 SQL 里一行调用大模型」**

- 实际是：连接器与 UDF 层的工程模式，不是引擎语义的变化（同章 §7.2 已把它归入「组合能力」）。
- 为什么会这样：调用外部模型需要的三件事 —— 异步、限流、序列化 —— 都是引擎早就有的通用机制，模型只是这个通用机制的一个新调用目标。
- 什么时候才会成真：引擎把「外部调用」做成一等语义（调用结果可随检查点恢复、可参与重放），而不只是一段 UDF。

**「端到端 Exactly-Once 能保证模型只被调用一次」**

- 实际是：检查点覆盖的是 source 进度、算子状态与 sink 的提交，**外部副作用不在其中**。
- 为什么会这样：这套语义是为「可重放的确定性算子」设计的，模型调用恰好不满足这个前提；而且模型输出不确定，重放不等于同样的结果，同一条事件重放两次可能落两个不同的结论。
- 什么时候才会成真：调用结果被按 key 缓存并随检查点一起恢复 —— 那时「重放」读的是缓存，而不是再调一次模型。

**「自适应调度就是自治流处理」**

- 实际是：自适应调度是规则式的既有能力（官方 release notes 可核验），与「AI 自动调优」不是同一件事。
- 为什么会这样：两者都表现为「作业自己调整并行度与资源」，但一个的依据是资源可用性这类确定性信号，另一个的依据是模型对负载的预测。
- 什么时候才会成真：出现公开的、可回滚的、能被第三方复现的自动调优记录，而不是一次演示。

三条说法的共同结构是：**把一个通用机制（UDF、检查点、自动伸缩）的既有能力，换了一个 AI 味的名字。** 识别方法只有一句 —— 问「它新增的是哪一个语义」。答不出新增语义的，就是换名；答得出（例如「外部调用结果参与检查点恢复」）的，才是真变化。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 「流内调用模型」会被固化成一个标准形态：异步算子 + 并发上限 + 结果缓存 + 规则兜底，而不是被包装成引擎新特性 | 主流引擎的官方文档同时给出这四件套的示例；出现可复用的开源算子库 | 官方文档只给同步调用示例；各团队继续各写一份异步 UDF |
| 向量写入会成为流作业的一等输出（含删除与更新），而不是靠批任务重建索引 | 向量库或开放表格式出现与流引擎共用的提交 / 删除协议条目 | 索引重建仍以「停写 + 全量重建」为主 |
| 「近线训练 + 定期发布」仍是主流，逐样本在线学习停在少数场景 | 公开材料讨论的是「模型多久更新一次」，而不是「逐样本更新」 | 出现被多家复用、有统一接口的在线学习运行时 |
| 流引擎选型会新增一条判据「对外部依赖的限流与降级能力」，取代「AI 友好」这类混合打分 | 选型清单里出现「降级路径 / 配额上限 / 兜底策略」栏 | 选型仍以吞吐与延迟 benchmark 为主，外部依赖只当连接器问题 |

逐条说明它依赖什么：

- **第一条**依赖的是收敛动因 —— 四件套不是行业约定，而是由配额与尾延迟这两个约束逼出来的，约束不变，形态就会收敛。
- **第二条**依赖的是删除需求真正进入合规清单；如果合规侧仍然只要求「原始文档被删除」而不追问索引，这条预测会推迟。
- **第三条**依赖的是标签延迟 —— 只要标签仍然晚到，逐样本更新的样本就无法对齐，近线训练就会一直是主流。
- **第四条**依赖的是外部依赖的故障真正出现在事故复盘里；没有事故，选型表就不会长出新的一栏。

四条预测的共同来源是同一个机制判断：**AI 进入流链路的方式是「给算子加一个外部依赖」，而外部依赖的可用性由配额和尾延迟决定，不由引擎的吞吐决定。** 只要这条判断成立，围绕它的工程实践会收敛成四件套；若哪一天调用被做进引擎语义（第一条的证伪信号），这四条要重写。

四条都需要同一个前提才能被观测：**团队把「端到端可见延迟」和「外部依赖的失败率」放进同一块看板**。只看引擎指标（吞吐、反压、检查点耗时）时，这四条预测既不会被证实也不会被证伪 —— 因为出问题的那个环节不在看板上。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有实时链路，想加语义判断 | 把模型调用放进独立异步算子，配并发上限 + 规则兜底 + 结果缓存；先量配额与 p99 | 官方文档是否给出「异步 + 限流 + 缓存」的标准示例 | 不要同步调用；不要把决策正确性压在一次模型输出上；没有降级路径就不要接进主链路 |
| 训练与推理的特征口径不一致 | 先把定义收敛成一份、物化两处；回填走与在线相同的逻辑 | 平台能否做「同一份定义 → 两个 store」与「时点正确回填」 | 不要为在线再写第二套特征逻辑；不要把长窗口特征硬塞进在线 KV |
| 想做到「新文档尽快可检索」 | 只对「新文档必须尽快可见」这一条需求试点；同步设计删除路径 | 向量库与流引擎之间是否出现统一的写入 / 删除接口 | 不要把删除当成写入的一个分支（延迟量级不同）；不要相信没有条件限定语的检索性能声称 |
| 想在流链路里做多步自主决策 | 先退回单步分类 / 抽取；多步决策放到事后批处理或人工确认 | 引擎是否把「外部调用结果」做进检查点 | 不要让调用步数进乘法级延迟放大；不要指望 Exactly-Once 覆盖外部副作用 |
| 团队正被「要上 AI 实时链路」推着排期 | 先把 5.1 表当验收清单：每一行问一句「它的 ② 在哪」，答不出就按 L2 排 PoC，不给生产承诺 | 你所在组织能否独立产生一条可被第三方核验的生产记录 | 不要在架构里为 L3 方向预留假设（接口空位、容量预留）；不要为新概念买单而放弃「可重算历史」这条判据 |

「明确不要做」这一列的共同点是同一件事：**不要让不确定的能力承担确定的承诺**。本节十行里最贵的错误，是在选型评审上把某个 L2/L3 方向说成「我们准备用它支撑核心链路」—— 一旦这样定调，后面所有的接口、SLA 与人力都会被它绑住，而它缺的那条证据（第 ② 条）并不会因为被写进方案就出现。

反过来，也有三件现在做一定不亏、且与级别无关的事：

- **把端到端可见延迟与外部依赖失败率放进同一块看板**（见 5.6 末段）—— 没有这两项，本节任何一条预测都无法被证伪，你也无法判断自己的实现是对是错。
- **把「这条链路能不能重算历史」写进每一次评审的模板** —— 它的答案不随技术选型变化，只随日志保留期、快照策略与模型版本留痕变化。
- **给每条外部依赖写明降级行为与责任人** —— 降级路径没人维护，等于可用性是两份不确定性的乘积。

### 5.8 小结

> 本节小结：AI 在本主题真正改变的**唯一一条机制**是 —— 流上「判断」这一步的判据，从人工枚举的确定性规则换成了统计模型的概率输出。它改变的是成本函数与可解释性：覆盖长尾分支的成本大幅下降，代价是链路失去可重算性、并引入一个配额固定且尾延迟不可控的外部依赖。
>
> 它**还没有**改变的是执行模型本身：一次处理仍然是一个事件，状态仍然要靠检查点落盘，提交边界仍然停在 sink，「能不能重算历史」仍然是最硬的那条判据 —— 这条判据反而因为模型输出的不确定性而变弱了。任何把 AI 加进流链路的方案，都应当先回答这条判据，再谈收益。
>
> 本节十行里没有 L1：这不是结论说「都不能用」，而是判据说「现在都用不到核心依赖的位置」。缺的那一条证据是公开可核验的第三方生产记录 —— 它与能力本身是否可用无关，与这件事被验证到了哪一步有关。
>
