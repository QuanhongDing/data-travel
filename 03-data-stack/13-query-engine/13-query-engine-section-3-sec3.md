## 3. 设计模式与范式

> 原 § 3 共 75 行、为模式条目与陷阱列表（6 个模式 + 5 条反模式 + 6 行场景决策表），缺少结构示意、机制解释与失效分析，重写为 ~320 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表读起来像一道选型题：跨源选 Trino、Lakehouse 选 Trino + Iceberg、传统生态选 Trino + Hive、AI / 边缘选 DataFusion、定制源写 Connector、实时要 Impala + Kudu。但把它放到真实约束里就会散架：同样是「跨源即席查询」，一个源端支持谓词下推与分批读（联邦查询很划算），另一个源只能整表吐数据（联邦查询立刻变成最贵的方案，该把结果落一份到 OLAP）。同一个场景，正确模式相反。

决定这件事的底层机制只有一个：**计算在哪里执行**。数据被拉到引擎内算、被下推到源侧算、还是被物理搬一份到加速层——三种选择各自决定了传输量、延迟与一致性由谁承担。而「能下推多少」不取决于引擎本身有多快，取决于**源的 Connector 声明了什么能力**（主文件 §2.1）。这就是为什么同一个引擎在两个数据源上的表现可以差出量级。

所以本节先立约束、再谈模式。下表不是选型表，而是「本主题下最容易被约束推翻的直觉」清单。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据能否移动 / 数据在哪 | 计算放哪：联邦下推、物理搬运还是加加速层 | 「先同步到一处再查最省事」——第二份副本一出现，「哪份对」就再也没有答案 |
| 源端有无计算能力（能否过滤 / 聚合 / 分批） | 下推能推多远，直接决定传输量 | 「引擎快就够了」——联邦查询的代价由没被下推的那部分数据决定 |
| 查询形态（点查 / 扫描 / 聚合 / 高频报表） | 是否需要另一类引擎承担重活 | 「统一入口 = 所有查询都走它」——高频固定报表走联邦层是重复支付搬运成本 |
| 延迟预算与负载类型（交互式 / 批） | 资源隔离方式（资源组、独立集群） | 「一套集群跑所有查询」——一次长任务就能拖垮全部交互用户 |
| 一致性 / 快照语义要求 | 能否允许"规划期之后元数据变化" | 「读到就行」——快照或分区在查询中途被换掉时，结果既不是旧快照也不是新快照 |
| 团队与生态（能否自研引擎） | 基于开源构建还是自研 | 「自研一版更贴合业务」——优化器与连接器生态的长期维护成本通常被严重低估 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 Trino 联邦查询（标准）

- **被什么约束逼出来**：数据分散在 Hive / MySQL / Kafka / S3 等多源，全量搬到一处既慢又会造出第二份不一致的副本；而源端大多具备过滤与聚合能力，缺的只是一个统一入口。
- **结构**：一次查询被拆成「源侧分片 + 引擎内合并」，能推多远由 Connector 声明决定。

```text
一次跨源查询的物理分解（Hive + MySQL）

  逻辑计划
    SELECT o.order_id, c.user_name
    FROM hive.sales.orders o
    JOIN mysql.crm.customers c ON o.user_id = c.id
    WHERE o.dt = DATE '2025-01-01'

  分片 1（hive connector，尽量在源侧执行）
    SELECT order_id, user_id FROM orders WHERE dt = DATE '2025-01-01'

  分片 2（mysql connector，用分片 1 的结果构建动态过滤后下发）
    SELECT id, user_name FROM customers WHERE id IN (:动态过滤集合)

  引擎内只剩：无法下推的算子（这里是跨源 JOIN 与最终汇总）
  ────────────────────────────────────────────────
  代价的固定位置：分片 1、2 的结果集要经 Exchange 进引擎
                  下推越多，进引擎的数据越少
```

能力边界不是抽象概念，它落在连接器配置与运行时开关上（与 [§4.2 关键技术点](13-query-engine-section-4-sec4.md) 同一组配置）：

```properties
# etc/catalog/hive.properties —— 这条源能并行读到什么粒度、由谁决定
connector.name=hive
hive.metastore.uri=thrift://metastore:9083   # 元数据入口：统计信息的来源
hive.config.resources=/etc/hadoop/conf/hive-site.xml
# 仓库目录（hive.metastore.warehouse.dir）不是 Hive 连接器的 catalog 属性，
# 它由这里引入的 hive-site.xml 决定；数据始终留在 S3 原路径，不进引擎存储
```

```sql
-- 运行时决定"能不能少搬"的几个开关
SET SESSION join_distribution_type = 'AUTOMATIC';  -- Join 分发方式：广播还是分区
SET SESSION query_max_run_time     = '10m';        -- 兜底：防一条查询长期占资源
EXPLAIN (FORMAT JSON)                              -- 核对下推是否真的发生
SELECT * FROM hive.sales.orders o JOIN mysql.crm.customers c ON o.user_id = c.id
WHERE o.dt = DATE '2025-01-01';
```

- **为什么这样设计有效**：因为过滤与投影被下推到源侧执行，网络里只传「过滤后的结果集」，所以联邦查询的代价与结果集大小成正比、而不是与源表大小成正比；代价是这个性质完全寄生在 Connector 的下推能力上，源端不支持就得由引擎自己扛。
- **代价**：无法下推的算子必然要拉数据进引擎，跨源 JOIN 是网络瓶颈的固定位置；规划阶段要对每个 Catalog 取元数据与统计信息，Catalog 一多，规划本身就成延迟来源；引擎侧必须有内存管理与磁盘溢写兜底，否则大查询直接失败。
- **失效点**：当查询形态从「过滤后的小结果跨源关联」变成「两张大表全量关联」或「高频点查」时，联邦查询从「省掉搬运链路」反转成最贵的一条路，因为每一行都要跨网络进引擎，而这里既没有源端的本地索引，也没有预聚合可用。
- **真实使用**：Presto 诞生于 Facebook，用于跨 Hive 等数据源的交互式分析 【公开】（Presto: SQL on Everything，ICDE 2019）；社区分叉出的 PrestoSQL 后来更名为 Trino 【经验】（治理分家与代码分叉发生在 2018 年末至 2019 年初这一区间内，「Trino」这一名称则是 2020 年末之后才启用，两者相隔约两年——可对照 Trino 项目的更名公告，以及其发布记录里版本编号的连续性自行核验）；大规模生产实例见 [§6 落地实践](13-query-engine-section-6-sec6.md)（字节、Uber、Netflix、美团四个案例）。

#### 3.2.2 Trino + Iceberg（Lakehouse）

- **被什么约束逼出来**：源是对象存储上的开放表格式——没有索引、没有本地缓存，唯一能依赖的是元数据；同时多个引擎要共享同一份数据，必须能读到一致的快照。
- **结构**：剪裁发生在元数据层，数据文件只在通过剪裁后才被打开。

```text
Iceberg 的三层元数据（剪裁的着力点）

  metadata.json            ← 当前快照的指针（现实中"表"的所在）
    └─ manifest list       ← 这个快照由哪些 manifest 组成
         └─ manifest files ← 每个数据文件的 分区值 + 列级 min/max + null 计数
              └─ data files (Parquet / ORC)   ← 只有通过剪裁的才被打开

  查询：
    SELECT * FROM iceberg.sales.orders
    WHERE dt = DATE '2025-01-01'    -- 分区剪裁：只留命中分区
      AND amount > 1000;            -- 文件级 min/max 剪裁：跳过不可能命中的文件
```

剪裁是否真的发生，可以直接查元数据表验证——这也是判断「小文件是否在拖慢规划」的办法：

```sql
-- 看这个快照里有多少数据文件、每个文件多大（小文件多 → 规划阶段变慢）
SELECT file_path, record_count, file_size_in_bytes
FROM iceberg.sales."orders$files"
ORDER BY file_size_in_bytes ASC
LIMIT 20;

-- 看分区级统计：分区的行数与文件数，用于判断分区是否切得过细
SELECT partition, record_count, file_count
FROM iceberg.sales."orders$partitions";
```

- **为什么这样设计有效**：因为剪裁所需信息全在元数据里、且元数据整体代表「某一个快照」，所以查询既能跳过大量文件、又不会读到「一半是旧快照一半是新快照」的中间态；代价是写入侧必须维护元数据，每次提交都要产生新的 manifest 与快照。
- **代价**：写放大（一次提交要写数据文件 + manifest + manifest list）；小文件越多，规划阶段要打开的 manifest 越多，慢在规划而不是执行；必须配套小文件合并（compaction）与快照过期清理，这两件事没有自动终点，属于常驻运维成本。
- **失效点**：当写入持续产生大量小文件、或统计不可用（半结构化数据、深层嵌套列拿不到 min/max）时，剪裁从「跳文件」退化成「按顺序打开全部文件」，因为剪裁粒度是文件级、没有行级索引；此时它的扫描成本与「直接把目录扫一遍」没有本质区别。
- **真实使用**：Iceberg 由 Netflix 开发并开源、2018 年捐入 Apache 基金会孵化器、2020 年毕业为顶级项目 【公开】（时间线可在 Apache 基金会的项目公告与 Apache Iceberg 官网自行核验）；Trino 是查询 Iceberg 的主要引擎之一 【公开】（Trino 官方文档的 Iceberg Connector 章节；该页随版本持续更新、无单一年版本，落地前以当前版本页面为准）；本章 [§13.3 Netflix 案例](13-query-engine-section-6-sec6.md) 给出「统计信息随数据一起写」的做法。

#### 3.2.3 Trino + Hive 兼容（传统）

- **被什么约束逼出来**：已有 Hive Metastore 与按目录组织的分区数据，PB 级历史资产不可能重写；查询还必须兼容既有语义（分区、类型、UDF），否则旧作业会集体失效。
- **结构**：分区就是目录，剪裁靠分区列表；列级统计要显式收集。

```sql
-- 传统 Hive 布局：分区就是路径
-- s3://warehouse/sales.db/orders/dt=2025-01-01/000000_0
--                              ^^^^^^^^^^^^^^ 分区 = 目录名

-- 命中分区的查询：引擎只列举命中的分区路径，不读其它分区
SELECT * FROM hive.sales.orders WHERE dt = DATE '2025-01-01';

-- 缺列统计时 CBO 只能按默认值估行数，Join 计划可能选错：
ANALYZE TABLE hive.sales.orders;
EXPLAIN (FORMAT JSON) SELECT * FROM hive.sales.orders WHERE dt = DATE '2025-01-01';
```

- **为什么这样设计有效**：因为表结构由 Metastore 描述、过滤条件能直接映射成目录前缀，所以分区剪裁在「零数据迁移」的前提下就能生效，历史资产不重写也能提速；代价是元数据能力止步于 Hive 语义，列级统计与更新能力都要另外补。
- **代价**：没有列统计时基数估计靠默认值，Join 顺序与分发方式可能选错；单表分区数增长到万级以上（【经验】阈值，随 Metastore 部署与硬件浮动）时，Metastore 列举与规划阶段共同变慢；小文件与行级更新受 Hive 表类型限制（ACID 表才有更新，且写入开销更高）。
- **失效点**：当分区数增长到「列举分区」成为规划瓶颈，或统计信息长期缺失导致基数估计严重偏差时，「零迁移兼容」从优势反转成计划劣化，因为每次规划都要向 Metastore 请求候选分区，而错误的基数会把大表当成小表广播，直接把工作节点内存打满。
- **真实使用**：Meta 的 Presto 建在 Hive 数仓之上，服务大规模交互式查询 【公开】（Presto: SQL on Everything，ICDE 2019）；传统 Hadoop 生态的企业普遍沿用这一形态 【经验】。

#### 3.2.4 DataFusion 内嵌（AI / Edge）

- **被什么约束逼出来**：计算发生在进程内——库、Notebook、边缘节点、数据预处理管线，没有集群可调度；数据已经在内存或本地文件里，先上传到服务端在网络与合规上都不划算；宿主语言是 Python / Rust，要求零拷贝互通。
- **结构**：库调用代替服务调用，执行器直接消费 Arrow 列存。

```python
import datafusion
ctx = datafusion.SessionContext()
ctx.register_parquet("orders", "s3://lake/orders/")   # 或 from_arrow / from_pandas
ctx.sql("""
    SELECT region, SUM(amount) AS gmv
    FROM orders
    WHERE dt = DATE '2025-01-01'
    GROUP BY region
""").to_pandas()
# 关键：数据不经过网络；算子对 Arrow 列存直接做向量化计算
```

两种形态的成本构成不同，这一点决定了它们各自适用在哪：

```text
服务化引擎： 序列化 ─ 网络传输 ─ 服务端排队与调度 ─ 扫描计算 ─ 结果回传
内嵌引擎：   本地读取 ─ 扫描计算 ─ 结果留在本进程
→ 内嵌省掉的是"两次序列化 + 网络 + 排队"这一段固定成本，省不掉扫描计算
→ 数据量不大时内嵌更快；一旦扫描计算成为主体，内嵌没有并行度可加，服务化引擎可以加机器
```

- **为什么这样设计有效**：因为执行器与宿主在同一进程、中间表示是 Arrow 列存，所以「序列化 → 网络 → 反序列化」这段固定成本被整段省掉，扫描与聚合在本地按列批量执行；代价是并行度与内存都被单机上限锁死，也没有多租户与资源隔离。
- **代价**：单机内存是硬上限，超限只能分块或溢写；没有资源组与队列，一个查询可以占满整个进程；连接器与生态（多源连接、权限、元数据）远少于服务化引擎，能力边界要自己补；版本与依赖由调用方自己维护。
- **失效点**：当数据量超过单机内存 / 磁盘，或需要多用户并发共享同一份数据时，内嵌从「零网络开销」反转成「做不下去」，因为它的前提是「数据在旁边、算力独占」；前提一旦不成立，唯一的出路是外挂一个集群——那时你要的其实是 3.2.1。
- **真实使用**：DataFusion 是 Apache Arrow 项目下的 Rust 查询引擎 【公开】（Apache Arrow 官方文档的 DataFusion 章节；该文档随版本持续更新、无单一年版本，年份以官方发布记录当前内容为准）；InfluxData 在其下一代时序引擎 InfluxDB 3.x（原 IOx）中用 DataFusion 作为查询执行引擎 【经验】（可在 InfluxData 官方工程博客与 InfluxDB 3.x 开源仓库的依赖清单中自行核验）；DuckDB 是同类内嵌分析引擎的另一形态 【公开】（DuckDB: an Embeddable Analytical Database，SIGMOD 2019）。AI 侧用法见 [§5 前沿演进](13-query-engine-section-5-ai.md)。

#### 3.2.5 PrestoDB + 自定义 Connector

- **被什么约束逼出来**：内部系统跑私有协议 / 私有存储（自研 KV、内部 API、私有消息系统），没有现成 Connector；而组织已经标准化在 Presto / Trino 的 Connector SPI 上，希望新增一个源的成本是「写一个插件」而不是「建一条链路」。
- **结构**：四个扩展点决定这个 Connector 的能力上限。

```java
// 自定义 Connector 的四个扩展点（下推能力就写在这四个实现里）
public interface Connector {
  ConnectorMetadata           getMetadata();            // 表 / 列 / 统计信息：CBO 的输入
  ConnectorSplitManager       getSplitManager();        // 如何切分并行度：决定能否并行扫
  ConnectorPageSourceProvider getPageSourceProvider();  // 如何读数据：决定批量与列剪裁
  ConnectorHandleResolver     getHandleResolver();      // 计划与执行之间的句柄解析
}
// 注意：谓词下推不是自动获得的，要在过滤 / 聚合下推的入口显式实现；
//       没实现就等于「引擎把整表拉进来再过滤」——反模式 2 的成因
```

- **为什么这样设计有效**：因为 Connector 是「能力声明 + SPI 实现」的边界，接入新源的成本是一次实现而不是一条常驻 ETL 链路，数据留在原处也就不会有第二份副本；代价是引擎的性能上限完全由这些实现决定，插件写得薄，联邦查询就退化成全量搬运。
- **代价**：分片、下推、类型映射、统计信息四件都要自己实现并长期维护，少一件就有可观的性能损失；Trino 与 PrestoDB 分叉后插件 SPI 各自演进，为一方写的 Connector 通常不能直接用于另一方，选型一次就锁定了后续维护方向。
- **失效点**：当 Connector 未实现分片与下推（默认按单分片读整表）时，自定义 Connector 从「接入成本低」反转成「比搬数据还慢」，因为它把整表拉进引擎内存再过滤，代价随源表线性放大，同时把内存压力转嫁给整个集群。
- **真实使用**：Connector SPI 是 Presto / Trino 的公开扩展接口，社区与厂商据此接入各类数据源 【公开】（Trino / PrestoDB 官方文档的 Connector 开发页面；两份文档随版本持续更新、无单一年版本，以当前版本页面为准）；为一方编写的 Connector 通常不能直接用于另一方 【经验】（可对照 Trino 与 PrestoDB 官方开发者文档中的 Connector 接口定义自行核验，两者已各自演进出一套 SPI）；企业自研 Connector 接入私有系统是常见做法 【经验】。

#### 3.2.6 Impala + Kudu（实时）

- **被什么约束逼出来**：业务既要「大范围扫描聚合」又要「对单行做更新」——对象存储 / HDFS 上的不可变文件做不到后者，只能靠重写整个分区来模拟，写入延迟不可接受；同时延迟预算在秒级。
- **结构**：列式存储 + 主键有序 + 行级更新，同一张表承担扫描与点查两类负载。

```sql
-- Kudu 表（语法示意）：列式存储 + 主键有序 + 支持行级更新
-- 硬约束：范围分区列必须取自主键列且与主键同序 → ts 必须进主键，否则建表被拒
CREATE TABLE kudu_orders (
  order_id BIGINT,      -- 主键首列：点查与前缀剪裁的依据
  ts       TIMESTAMP,   -- 主键次列：范围分区只能从主键列里取
  shop_id  INT,
  amount   DOUBLE,
  PRIMARY KEY (order_id, ts)
)
PARTITION BY HASH (order_id) PARTITIONS 16,   -- 哈希分区：决定写并行度
             RANGE (ts) (                     -- 范围分区：决定扫描剪裁粒度
               PARTITION '2025-01' <= VALUES < '2025-02',
               PARTITION '2025-02' <= VALUES < '2025-03'
             );

-- 同一张表上的两类查询：
SELECT SUM(amount) FROM kudu_orders WHERE ts >= '2025-01-15';  -- 范围扫描聚合
SELECT * FROM kudu_orders WHERE order_id = 12345;              -- 主键前缀点查
```

- **为什么这样设计有效**：因为数据按主键有序存放、且支持行级写入（不必重写整个分区），所以同一份数据既能被大范围扫描聚合、又能被窄范围点查、还能就地更新；代价是这份能力被内化进存储——写入要经过 tablet 复制与 compaction，主键与分区一旦定死就只能重建表。
- **代价**：主键必须在建表时确定，改主键等于重建并回灌数据；写入放大与 compaction 是常驻后台成本，写入吞吐与扫描性能之间需要在参数上做取舍 【经验】；生态（工具、连接器、社区规模）明显小于 Hive / Iceberg 系，跨引擎共享数据的能力有限。
- **失效点**：当写入形态变成「大吞吐追加」、查询却以全表聚合为主时，Kudu 从「可实时更新」反转成「更贵」，因为行级更新能力来自按主键维护的有序结构加复制与 compaction，这套机制对批量追加没有任何帮助，而不可变的列存文件在这种负载下扫描更便宜。
- **真实使用**：Cloudera 将 Impala + Kudu 作为 CDH / CDP 栈上的实时分析组合对外发布 【经验】（这一产品定位可在 Cloudera 官方文档中 Impala 与 Kudu 各自的组件页面核验）；Kudu 由 Cloudera 开源、后进入 Apache 并毕业为顶级项目 【经验】（毕业发生在 2015-2016 之间，时间线可在 Apache Kudu 官网与 Apache 基金会的项目记录中自行核验）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 多源即席查询、源端支持下推、结果集不大 | Trino 联邦查询 | 不选先搬数据：搬运链路要维护，且第二份副本与源不一致 | 源端能否过滤 / 分批（看 Connector 能力） |
| 湖上多引擎共享、需要快照一致 | Trino + Iceberg | 不选 Hive 兼容：列统计与更新能力都受限，快照语义要另做 | 是否需要跨引擎读到同一快照 |
| 历史资产在 Hive、不能重写 | Trino + Hive 兼容 | 不选重写为 Iceberg：PB 级回灌的窗口与成本通常不可接受 | 分区数是否还在 Metastore 可承受范围内 |
| 计算在应用进程内、数据已在本地 | DataFusion 内嵌 | 不选服务化引擎：把本地小数据上传到集群换不来任何收益 | 数据能否装进单机内存 |
| 私有协议 / 私有存储的系统 | 自定义 Connector | 不选自建 ETL 链路：新增一个源就要多一条常驻链路 | 接入的源是否只有一个系统用 |
| 既要扫描聚合又要行级更新 | Impala + Kudu | 不选不可变文件：更新只能靠重写分区，写入延迟不可接受 | 是否存在稳定的按主键更新需求 |
| 大宽表聚合（宽表上的大范围扫描聚合） | 专用 OLAP（ClickHouse / StarRocks） | 不选联邦查询：单表聚合的性能来自列存与向量化执行，联邦层提供的是跨源而不是这个 | 聚合是否集中在少数宽表上、且列数远多于查询用到的列 |
| 高频固定报表 / 高并发点查 | OLAP 引擎（StarRocks / Doris 类），联邦层只做编排 | 不选联邦查询：每次重扫重算，搬运成本被重复支付 | 同一条 SQL 是否按分钟被重复调度 |
| 交互查询与大批任务共用集群 | 资源组 + 独立集群（按工作负载隔离） | 不选单集群排队：队列管提交速率，管不住单查询占满内存 | 一次长任务是否会拖垮交互 P99 |
| 数据不得出域、源端无下推能力 | 源侧就地计算 + 只取聚合结果 | 不选拉全量进引擎：数据量与合规都过不去 | 源端能否承担部分聚合 |

本节最常被误选的一对，是**把「统一查询入口」当成「所有查询都该走联邦层」**。它的机制差别很直接：联邦层的价值在于「跨源拼接与免搬运」，而高频固定报表要的是「重复计算的最小化」。误选的实际后果是——同一份明细数据每分钟被重新扫描、重新跨网络搬运一次，集群利用率很高、P99 却持续抖动，而每一次执行得到的结果完全相同。

### 3.4 组合模式：真实系统不会只用一种

**组合一：联邦编排层 + OLAP 加速层（谁编排、谁做重活）**

- 构成：联邦查询引擎负责跨源拼接、口径统一与长尾即席查询；OLAP 引擎承载固定模式的高并发聚合与点查；两者之间用同步或物化链路衔接。
- 职责边界：联邦层不做重活（不承担重复的大规模聚合），OLAP 层不做长尾（不为一次性查询建模），两边靠「查询模式是否稳定」划线。
- 运维代价：两套系统 + 一条同步链路，多出的是「哪份对」的一致性校验与同步延迟监控；加速层要建模（分区、排序键、物化视图），建模决策本身是长期成本。
- 适合规模：已有稳定高频报表、同时存在长尾跨源即席需求的团队（本章 [§13.4 美团案例](13-query-engine-section-6-sec6.md)）。

**组合二：联邦查询 + 开放表格式 + 统计随写（湖上多引擎）**

- 构成：Iceberg 承担快照、分区与文件级统计；联邦引擎承担剪裁、下推与执行；统计信息由写入侧随数据一起产出，而不是事后扫描收集。
- 职责边界：表格式管「元数据与一致性」，引擎管「怎么剪、怎么算」，统计由写入路径负责新鲜度。
- 运维代价：compaction 与快照过期是常驻作业；写入链路多一步生成统计，写放大上升；统计缺失时要有可观测指标（否则剪裁失效是静默的）。
- 适合规模：湖上 PB 级数据、多个引擎（批、流、联邦）共享同一份表的组织（本章 [§13.3 Netflix 案例](13-query-engine-section-6-sec6.md)）。

**组合三：内嵌引擎 + 服务化引擎（本地预处理 + 集群重活）**

- 构成：Notebook / 应用进程内用内嵌引擎处理能装进单机的数据（清洗、抽样、特征预处理）；超出单机规模的部分提交给服务化引擎。
- 职责边界：内嵌引擎只处理「已在本地」的数据，不做多用户共享，不承担 SLA；集群引擎承担共享、并发与 SLA。
- 运维代价：两套 SQL 方言与两套类型 / 时间语义，容易出现「本地跑对、集群跑出另一个数」；需要有意识地统一口径（例如固定时间函数与 NULL 语义的处理）。
- 适合规模：数据科学团队日常探索 + 生产侧集中查询的组织。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成那样） | 修法 |
| --- | --- | --- | --- | --- |
| 用 Trino 做高频大查询 | 同一条 SQL 按分钟被调度；集群忙、P99 抖动，每次结果却都一样 | 重复支付跨网络搬运与重算成本，长任务挤占交互资源 | 把「统一入口」理解成「所有查询都走它」 | 固定模式下沉到 OLAP / 物化视图，联邦层只做编排 |
| 未优化 Connector | 跨源查询慢，`EXPLAIN` 里源侧分片是「整表读」 | 全量数据进引擎再过滤，传输量与内存压力随源表线性放大 | 先接通再优化，Connector 只实现了「能读」 | 谓词下推 + 列剪裁 + 分区剪裁 + 分片并行，逐项补并验证 |
| Join 顺序差 | 大表 Join 大表时工作节点内存打满或广播失败 | 错误的基数估计把大表当小表广播，单点内存成为天花板 | 缺列统计，CBO 只能按默认值估行数 | 收集统计信息，必要时显式指定 join 分发方式，用 EXPLAIN 核对 |
| 忽视资源管理 | 一条大查询开始后，全体交互查询同时变慢 | 单查询占满工作节点内存与队列，故障半径等于整个集群 | 默认配置直接上线，没有按工作负载分组 | 资源组 / 独立集群隔离 + 查询超时 + 溢写与并发上限 |
| 未启用 AQE（运行时自适应优化） | 计划在编译期定死，运行时的真实基数与估计相差很大 | 缺运行时反馈，计划质量停留在统计信息的准确度上 | 沿用其他引擎的经验（AQE 是 Spark 侧的机制名），以为开关一开就万事大吉 | 在联邦引擎上对齐的等价能力是：可用统计 + 动态过滤 + 运行时决定 Join 分发，逐项确认，而不是找一个叫 AQE 的开关 |

**未优化 Connector 是最危险的一条，因为它是「联邦查询很慢」这一印象的真正来源。** 生产里的暴露方式通常是：一条跨源查询在测试环境（小表）跑得飞快，上线后源表增长到远超测试时的规模，查询时间随之线性上涨——而团队会先去查引擎参数，实际上是 Connector 每次都把整表拉进来。判据很短：看 `EXPLAIN` 里源侧分片是否带上了过滤条件，没带就是没有下推。

**忽视资源管理不会以「慢」的形式暴露，而是以「一起慢」的形式暴露。** 机制上，工作节点的内存与队列是共享资源，一条不设上限的大查询会把它们占满，故障半径等于整个集群；因此这条反模式的代价不是某个查询慢了，而是所有查询的可用性同时被一个用户绑定。

**用 Trino 做高频大查询的隐蔽性在于指标好看。** 集群利用率高、没有报错，只是 P99 持续抖动；直到有人把这条报表下沉到 OLAP 层，抖动才消失——问题从来不在引擎，而在「这条查询被放在了错误的层」。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单源 → 跨源 | 直连单库 | 每加一个源就多一条 ETL 链路，副本还会不一致 | 联邦查询（统一 Connector） | 建 Connector 与权限映射；查询能力受源端下推能力限制 |
| 数据量超过「能拉全量」 | 朴素联邦（全部拉进引擎算） | 传输量随数据量线性上涨，内存打满 | 最大化下推 + 动态过滤 | 每个 Connector 都要补下推实现并逐个验证 |
| 出现固定模式的高频查询 | 联邦查询 | 每次重扫重算，搬运成本被重复支付 | 下沉到 OLAP / 物化视图，联邦层做编排 | 重建同步链路与一致性校验，「哪份对」的问题回归 |
| 单用户 → 多租户并发 | 单集群共享 | 长任务拖垮交互体验 | 资源组 / 独立集群 / 队列 + 超时 | 配额与容量规划成为常驻治理工作 |
| 需要跑长时查询 | 无溢写、无容错的交互集群 | 工作节点内存不足即整条查询失败 | 磁盘溢写 + 容错执行（失败分片重试） | 磁盘 IO 成为新瓶颈，需要额外存储与重试配置 |
| 单机内嵌 → 超出单机 | DataFusion / DuckDB 内嵌 | 内存与并行度撞上硬上限 | 服务化引擎（联邦或数仓） | SQL 方言与语义差异要重新验证（时间、类型、NULL 处理） |

补一句判据：**当「每次查询都要重新搬运的那部分数据」占执行时间的主要部分时，就该换模式**——要么把计算推得更深，要么把结果提前算好。

### 3.7 自检清单

1. 随机抽一条跨源慢查询，`EXPLAIN` 里源侧分片是否带上了过滤条件？没带即「未优化 Connector」。
2. 每个 Connector 是否有明确的「支持下推的算子清单」？答不出，说明下推能力处于未知状态。
3. 关键表的列级统计最近一次收集是什么时候？从未收集即 CBO 一直在猜。
4. 是否存在被按分钟调度的查询跑在联邦层？存在即应下沉。
5. 交互查询与大批任务是否在同一资源池？是，则故障半径等于整个集群。
6. 是否设置了单查询内存上限与查询超时？没有，则一条查询可以打满集群。
7. Iceberg 表最近一次 compaction 与快照过期清理是什么时候？没做过，则规划成本在持续上涨。
8. 单表分区数量是否已到万级以上（【经验】阈值，非硬界限）？是，Metastore 与规划阶段是首要怀疑对象。
9. 联邦层读到的数据与源是否可能不一致（有无物化或缓存链路）？有链路就要有新鲜度指标。
10. 查询是否会在中途遇到「快照 / 分区被换掉」？会，则结果一致性需要显式定义，不能默认。
11. 内嵌引擎与服务化引擎的 SQL 语义是否经过一致性验证（时间、NULL、类型转换）？
12. 是否存在为自研 Connector 而承担长期维护的插件，且只有一个人懂？是，就是单点风险。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 多源即席、源端可下推 | 联邦查询 | 只传过滤后的结果集，代价与结果集成正比而非与源表成正比 |
| 需要快照一致、多引擎共享 | 联邦 + 开放表格式（Iceberg） | 剪裁信息在元数据层，能跳文件又不读到中间态 |
| 历史资产不可重写 | 联邦 + Hive 兼容 | 过滤映射成目录前缀，零迁移即可剪裁 |
| 算在进程内、数据在本地 | 内嵌引擎（DataFusion / DuckDB） | 省掉序列化与网络的固定成本，本地向量化执行 |
| 私有协议 / 私有存储 | 自定义 Connector | 接入成本是一次实现；但下推不写，性能就全丢 |
| 扫聚合 + 行级更新并存 | Impala + Kudu | 主键有序 + 行级写入，同一份数据两类负载通吃 |
| 高频固定查询 | 下沉到 OLAP，联邦层做编排 | 避免每次重复支付搬运与重算 |
| 交互与批混合 | 资源隔离 | 共享内存与队列时，故障半径等于整个集群 |

> 本节小结：本主题下决定模式选择的**唯一那条最前置的约束，是「源端能不能被下推」**——它决定了数据要不要跨网络搬家，而搬家这件事一旦发生，延迟、内存、一致性三样东西会同时被绑住。其余约束（快照语义、延迟预算、并发隔离、生态成熟度）都是在下推能力划定的可选集合里做二次筛选：能下推的走联邦，不能下推又高频的加加速层，量大到不该进网络的（或合规上不允许出域的）就留在源侧或进程内算。
