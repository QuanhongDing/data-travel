## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是没有时间维度。同一个清单里，「已经 GA 且有人在生产用」和「路线图里的条目」被并列写在一起，读者据此排路线图就会踩空：前者值得投人，后者连预算都不该批。

第二个问题是判据不是判据，而是方向名。§1.4 把演进划成五阶段（单源 → SQL-on-Hadoop → 联邦 → Lakehouse 集成 → AI 原生），这是历史叙事；而「AI 原生」这个词不能回答架构师真正要问的那一句：**我现在能不能靠它上线**。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（或版本化发布的规范）；② 有厂商之外的公开证据；③ 接口稳定、可预期。
- **L2 可试点**：①③ 大体满足，但 ② 不满足；或能力可用而判定标准尚未形成共识。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。

为什么是这三条，而不是「有没有厂商在推」：厂商在推是营销事实，不是成熟度。① 回答「它是发布过的，还是演示过的」；② 回答「出问题时我能不能找到别人的经验，而不是厂商的承诺」；③ 回答「我明年会不会为它重写一遍」。

**本主题对 ② 的判据修正（声明后全表按此判级，5.2 逐项一致）**：对**交换格式与执行运行时**这一层，② 的等价证据是**由发起方之外的独立实现共同通过的跨实现兼容性测试**（互操作测试）。理由是：这一层的生产事实恰恰是「第三方能否独立实现并互通」，而互操作测试套件与任何单一实现分离、可被读者复跑，比厂商自述的「已兼容」强得多。本主题只有「列式内存格式与向量化执行」这一行符合该形态；其余各行仍按原始 ② 判，拿不出就是 L2 / L3——**② 只有「满足」与「降为 L2」两种命运**。

修正条文的**适用对象是「规范」，不是「产品」**，这一条决定了修正管到哪一行：② 取互操作测试的前提，是这一行的对象为一份**可被独立实现分别实现、且实现之间必须互通**的规范。同一层里的两个行分属两种对象——「列式内存格式与向量化执行」的对象是格式规范（互操作即其全部意义，故适用修正）；「嵌入式 OLAP（DataFusion / DuckDB 一类）」的对象是具体引擎产品，它要回答的仍是原始 ②「谁在生产里用了、效果如何」，属产品采用问题，与该引擎内部用了什么格式无关，所以该行不适用本修正，按原始 ② 判为 L2。判级时先问「这一行评的是规范还是产品」，再套对应判据。

另有一条评级规则，用于**合并方向**：若一个方向本质是若干子能力的合并（例如「AI 原生查询」= 自然语言查询 + 自治优化，后者即下表的「自治查询引擎（自动调优 / 自适应）」行），其级别取其中**最弱**的一项。这条规则在表里的「AI 原生查询」行被实际使用。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| 自然语言查询（NL → SQL） | L2 | ①③ 满足（各平台有 GA 的文本转 SQL 能力与版本化文档）；② 不满足：真实库上的第三方生产准确率不公开，公开材料以评测基准为主 | 先补元数据与指标定义，再谈启用；用「需要改口径的条数」验收 |
| AI 驱动的查询优化（LLM 预测查询模式） | L3 | ① 不满足：无正式发布的能力项；② 仅有论文与厂商演示 | 记录，不要把它写进性能规划 |
| 自治查询引擎（自动调优 / 自适应） | L3 | ①③ 不成立：被冠以「自治」的现有能力是运行时统计 + 规则驱动的自适应执行（见 §2.1 的 AQE），不是 AI；真正的自治没有正式发布的能力项，「什么算自治」也无可核验定义。② 不满足 | 现有自适应能力照用，但不要把它算作 AI 收益 |
| AI 原生查询（「自然语言查询」+「自治优化」的合并叙事） | L3 | 按合并规则取最弱项：自然语言查询 L2、自治优化 L3 → L3 | 把它当作章节标题，不要当作能力清单 |
| 联邦向量检索（结构化 + 向量统一查询） | L2 | ①③ 满足（连接器 / 表函数形态可用）；② 不满足：跨源联邦到独立向量库的公开生产案例不公开 | 先验证距离过滤能否下推，再决定是否走联邦 |
| 查询引擎 + RAG（向量库 + LLM） | L2 | ①③ 满足（接口可拼装：SQL 取结构化、向量取非结构化）；② 不满足 | 把「检索到什么」写进查询计划可观测项，否则无法归因 |
| 查询引擎 + GraphRAG（图 + SQL） | L3 | ① 不满足：图查询与 SQL 的联合执行没有标准化接口；② 无 | 记录为方向，不要在架构里为它预留假设 |
| 统一取数接口（SQL 作为工具，MCP 一类协议） | L2 | ①③ 部分满足（协议规范有带日期的修订版本，但仍在演进）；② 不满足：第三方非厂商生产案例不公开 | 给 Agent 单列只读身份，先把权限与限额做出来 |
| 嵌入式 OLAP（DataFusion / DuckDB 一类） | L2 | ①③ 满足（版本化发布、SQL 接口稳定）；② 不满足：可核验的非厂商生产案例列不出（本行评的是引擎产品而非规范，不适用 5.1 的修正条文，按原始 ② 判） | 单机 / Notebook 场景可用，但别当共享入口（见 §7.4） |
| 列式内存格式与向量化执行（Arrow 原生） | L1 | ① 版本化发布的规范：Apache Arrow 的 *Columnar Format* 规范（源文件 `format/Columnar`，规范中定义元数据格式版本 `MetadataVersion` 并给出向后兼容承诺；每个 Arrow 版本配一份以版本号命名的 release note）+ 内嵌引擎的正式论文（Apache Arrow DataFusion，SIGMOD 2024）；② 按本节修正：由发起方之外的独立实现共同通过的跨实现互操作测试——`apache/arrow-testing` 用例集，由 `archery integration` 驱动，C++ / Java / Rust / Go / JavaScript 等实现互为生产者与消费者；③ 格式规范版本化、规范中写明兼容性承诺 | 优先用它对接你的宿主进程与引擎，它使「换一层」变得可行 |
| 联邦数据网格（跨域 / 跨云 / 跨厂商统一查询） | L2 | ①③ 满足（联邦查询本身生产可用）；② 不满足：作为组织形态无可核验的公开判据 | 先做「统一入口 + 分级权限」，不要先做组织重构 |

本主题下**唯一**处在 L1 的方向是「列式内存格式与向量化执行」这一层。它之所以能过判据，是因为它可被独立核验：格式规范随版本发布，跨实现互操作由 `apache/arrow-testing` 用例集（`archery integration` 驱动）判定，任何声称「Arrow 原生」的实现都要被同一套测试检验。

其余方向为什么不够格，与上表除 L1 外的 10 行逐行对应，原因分三类：

- **② 拿不出 → L2**（共 6 行）：自然语言查询、联邦向量检索、查询引擎 + RAG、统一取数接口、嵌入式 OLAP、联邦数据网格——能力可用，但「谁在生产里用了、效果如何」没有可引用的第三方公开材料。
- **①③ 不成立 → L3**（共 3 行）：AI 驱动的查询优化、自治查询引擎、查询引擎 + GraphRAG 连正式发布的能力项都还没有，判定标准（什么算「自治」）每年在变。
- **合并叙事取最弱组成项 → L3**（共 1 行）：AI 原生查询不是独立能力，它按上面的合并规则取「自然语言查询（L2）」与「自治优化（L3）」中最弱的一项，因而停在 L3。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式 release note 或规范能不能找到？找不到 → L3。
2. 厂商之外的证据能不能找到？找不到 → L2。
3. 接口明年会不会变？会变 → 至多 L2。

三句都过得去，才是 L1。注意第 3 句最容易被忽略：**接口稳定性比能力有无更难满足**，而它直接决定你要不要为它写一层适配。

以两条方向走一遍这个问法：

- **列式内存格式与向量化执行**：有版本化规范与正式论文（第 1 句过）、有 `apache/arrow-testing` 用例集由发起方之外的实现共同通过（第 2 句过）、规范版本化并给出兼容性承诺（第 3 句过）→ L1。
- **自然语言查询**：有 GA 的能力与文档（第 1 句过）、第三方生产案例拿不出（第 2 句不过）→ L2，不必再看第 3 句。

三个常见误判，排路线图时最容易踩：

- **把「能力可用」误当成「可以排进路线图」**：能力可用只说明能试；能不能排进去，取决于 ② 与 ③。
- **把「厂商 benchmark 领先」误当成第三方证据**：跑分是厂商自述；第三方证据是别人在别处跑出来的生产结果。
- **把「协议被广泛采用」误当成接口已稳定**：生态清单每月在变，规范版本号才是可核验的东西。

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 自然语言查询：换的是 SQL 的编写者，不是执行者

- **旧做法与它的卡点**：取数靠人写 SQL。它卡在**口径知识不在 SQL 里**：同一个指标的三种写法都能跑通，差别只存在于文档与人脑；而这个瓶颈无法靠加快引擎解决——引擎再快，写错口径也是错的（§1.2 把「口径不一致」列为没有查询引擎的代价之一，但有了引擎它同样存在）。
- **AI 改变了什么机制**：把「写 SQL 的人」换成模型。执行路径完全没变——仍是同一个解析器、优化器与执行器；变的是**人机分工与接口形态**。这是接口改良，不是架构变化，这一点必须先说清。
- **由此得到的**：因为模型能读元数据并生成候选 SQL，所以「会写 SQL」第一次不再是取数的前置条件，自助查询的面可以扩大。**因为**生成是概率性的，**所以**必须有一道确定性工序兜底：把生成的 SQL 与语义定义对照后再执行——这直接推出「NL2SQL 的上限由元数据覆盖决定，而不是由模型大小决定」。
- **由此付出的**：错误模式从「报错」变成「看起来对的错答案」。口径错、join 错、过滤条件漏都会正常返回结果，而错误更难被发现；延迟与成本增加（一次自然语言查询 = 模型推理 + 可能的重试 + 引擎执行）；并且引入新的权限主体（模型以谁的身份读数据）。
- **证据与来源**：文本转 SQL 的公开评测以**基准**为主：Spider（EMNLP 2018）面向跨域语义解析，其数据库是规整、干净的一类；BIRD（NeurIPS 2023）的设计目标则是「真实库、脏数据、大 schema」，正是为补上这类基准与生产环境之间的落差【公开】。至于「某产品在生产中准确率多少」，判定方法是看它的官方文档是否给出评测条件（数据集、schema 规模、是否允许人工澄清）；没有条件的百分比不构成证据。
- **成熟度**：**L2** —— 能力可用（①③），但第三方公开生产案例拿不出（②），且准确率强依赖元数据质量。

把失败类型分开，才能知道该修哪里：

| 失败类型 | 表现 | 该修的地方 |
| --- | --- | --- |
| 语法 / 结构错 | 执行直接报错 | 模型侧：提示与示例、schema 描述质量 |
| 口径错 | 跑得通但数不对 | 元数据侧：指标定义与语义层，不是模型 |
| 权限错 | 跑得通但读了不该读的 | 平台侧：权限体系（见 5.3） |

一条可控的自然语言取数链路（关键在于第二步是确定性的）：

```text
问题（自然语言）
   │
   ├─① 选表与口径：读元数据 / 指标定义 / 枚举值（不确定性来源在这一步，不是 SQL 语法）
   ▼
候选 SQL
   │
   ├─② 确定性校验（不依赖模型）：语法解析 → 只读校验 → 权限与行级过滤注入 → 限额检查
   ▼
执行（同一套优化器与执行器，与手写 SQL 完全一致）
   │
   └─③ 回写：把这次「问题 → SQL → 结果」作为一条记录留下（供口径错复盘）

判定方法：把 ② 的每一项做成能单独失败、且失败原因可读的检查
   检查不能只返回「拒绝」，必须返回「哪一项没过」——否则口径错会被误判成权限问题
```

- **失效条件**：当目标库的表 / 字段命名没有业务语义、也没有指标口径定义时，NL2SQL 会把「猜表名」升级成「猜口径」，此时它比手写 SQL 更慢、更难审计。
- **自验方法**：取 50 条真实业务问题，先让模型生成 SQL，再让人复核，分别记录「需要改口径的条数」与「需要改语法的条数」。前者占比高 → 问题在元数据，不在模型。

#### 5.2.2 联邦向量检索：把「一列向量」接进联邦查询

- **旧做法与它的卡点**：结构化数据走 SQL，非结构化走向量库，两边各一套 API；跨两类的问题要人肉拼接（先检索、再回填、再过滤）。它卡在**算子不在查询语言里**：SQL 能跨源，但不能表达「相似度」这个算子，于是跨源优化（下推、剪裁）在这里全部失效。
- **AI 改变了什么机制**：把相似度变成一个可以出现在 SQL 里的算子 / 函数，使向量列与普通列一样参与过滤、排序与 join。改变的是**执行计划的边界**——距离计算落在哪个节点上。
- **由此得到的**：因为相似度被表达成算子，所以「先按元数据过滤、再算距离」这类混合检索原则上可以下推（过滤推到源端，只对候选集算距离）。**因为**过滤能下推，**所以**结果集规模可控，代价差按过滤率放大【推算：候选集为全量的 1% 时，距离计算量与传输量约为全量的 1%，端到端耗时随之下降——前提是距离计算与 ANN 检索能在源端完成，而不是把向量列拉回引擎】。
- **由此付出的**：ANN 索引是近似的，漏召回是设计的一部分而非缺陷，召回率与延迟之间是一条可调曲线，需要按业务定目标；更现实的代价是**跨源联邦场景下距离过滤往往下推不了**——引擎读不到向量库内部的索引结构，只能拉向量列到本地算，这会把联邦查询最贵的部分（网络传输）放大一个数量级。
- **证据与来源**：本节不给「某连接器性能如何」的断言，只给判定方法——对一条混合检索查询跑 `EXPLAIN`，看距离过滤与 top-k 落在 connector 侧还是引擎侧；落在引擎侧就意味着全量拉取【经验，判定方法而非性能结论】。连接器是否支持该下推，以该引擎连接器文档的当前版本为准。
- **成熟度**：**L2** —— 连接器形态可用（①③），但跨源联邦到独立向量库的第三方公开生产案例拿不出（②）。

```text
混合检索的代价分水岭（用 EXPLAIN 判定，而不是看宣传语）
  写法 A：向量列拉到引擎内算距离
     Scan(向量库) ──► 全量向量列 ──► 引擎内过滤 + 距离计算
     代价 ≈ 传输(全量) + 距离计算(全量)      ← 联邦引擎最贵的一档

  写法 B：过滤 + ANN 在源端完成
     Scan(向量库, filter=..., ann=topk) ──► 候选集 ──► 引擎内合并
     代价 ≈ 传输(候选集) + 距离计算(候选集)   ← 过滤率决定收益

判定方法：把 EXPLAIN 里的「距离算子所在节点」当成唯一依据
  在 connector 侧  → 可以按联邦方案走
  在引擎侧        → 等价于全量拉取，此时两步走（向量库召回 + SQL 回表）通常更便宜
```

- **失效条件**：当候选集大、维度高、元数据过滤率低时，「统一查询」不如两步走；当数据能在同一个存储内共存（例如向量列与业务列同库）时，跨源联邦的必要性本身就不成立。
- **自验方法**：取一条真实混合检索查询，分别测「联邦单条 SQL」与「向量库 top-k + SQL 回表」两种走法的端到端耗时与传输字节数。两者接近说明下推有效；差一个数量级说明下推没发生。

#### 5.2.3 列式内存格式与向量化执行：唯一能过 L1 判据的那一层

- **旧做法与它的卡点**：引擎内部按行解释执行；引擎之间靠中间文件或私有序列化交换。它卡在**两道边界**上：同一进程内，逐行解释执行填不满 CPU 流水线；跨进程 / 跨引擎时，数据要么落盘（IO 与运维成本），要么走私有协议（换引擎就得重写对接）。
- **AI 改变了什么机制**：改变的是**执行层与引擎之间的边界**——列式内存格式被标准化之后，执行运行时可以从 SQL 前端与优化器里独立出来（机制见 §7.3.4）；向量化执行则把逐行处理换成按批处理。两件事本来与 AI 无关，AI 时代让它们成为必需：AI 数据流把结构化、向量与文本混在一起，能同时被内嵌引擎、集群引擎与训练 / 推理进程读取的格式，只剩列式内存格式这一个候选。
- **由此得到的**：因为格式是标准化的、且由多个独立实现共同实现，所以「换引擎」第一次可以只换**一层**而不重写数据链路；**并且**这一层的兼容性可以被测试套件独立验证，不依赖任何厂商声明——这正是本节唯一能标 L1 的原因。
- **由此付出的**：格式统一解决的是**数据搬运**，不是治理。权限、审计、资源隔离、多租户这些「引擎之外」的能力，内嵌族仍然要自己补（隐性成本清单见 §7.4，成本天平反转见 §7.5）；而且标准只覆盖内存表示，不覆盖**计划表示与函数语义**，所以「同一个 SQL 在不同实现上结果一致」仍要逐个核验，不能因为格式通了就默认语义也通了。
- **证据与来源**：【公开】Apache Arrow 的 *Columnar Format* 规范随版本发布（源文件 `format/Columnar`，每个版本配一份以版本号命名的 release note），其跨实现互操作由 `apache/arrow-testing` 用例集校验、`archery integration` 驱动，各语言实现互为生产者与消费者——这套测试读者可自行复跑，不必采信任何实现方「已兼容」的自述（核验时以该仓库与官方文档当前版本为准）；内嵌引擎一侧有正式论文（Apache Arrow DataFusion，SIGMOD 2024）。向量化执行的加速幅度随算子类型、批大小与缓存命中率变化，任何单一加速比数字都要带条件才成立【经验，区间而非定值】。
- **成熟度**：**L1** —— ① 版本化发布的 *Columnar Format* 规范（含 `MetadataVersion` 与兼容性承诺）与正式论文；② 按 5.1 声明的修正：`apache/arrow-testing` 用例集由发起方之外的独立实现共同通过；③ 格式规范版本化并给出兼容性承诺。

```text
三层可分离之后，「选引擎」变成「选一层」（机制见 §7.3.4）
  ┌──────────────┬──────────────┬───────────────────────────┐
  │ SQL 前端      │ 优化器        │ 执行运行时                  │
  │ 解析 / 语义    │ 计划 / 代价   │ 列式 / 向量化 / 算子        │
  └──────────────┴──────────────┴───────────────────────────┘
        ▲               ▲                    ▲
        │   列式内存格式是这三层之间（以及进程之间）的公共边界
        │   它被标准化 ⇒ 执行层可被不同前端复用、可被宿主进程内嵌
        └─ 但「格式通」≠「语义通」：计划表示与函数语义仍逐实现核验
```

这一层带来什么、不带来什么（决定你该怎么用它）：

| 它带来的 | 它不带来的 |
| --- | --- |
| 进程内零拷贝交换：内嵌执行层可直接读宿主进程的数据 | 权限与审计：内嵌族没有统一治理面（见 §7.4） |
| 执行运行时与前端解耦：可换一层而不重写链路 | 计划与函数语义一致：不同实现的同名函数可能语义不同 |
| 兼容性可被独立测试套件验证（不依赖厂商自述） | 统计信息与下推：这两项仍由数据侧与连接器决定 |
| 多语言实现共用同一内存布局，跨语言传递不必序列化 | 多租户与资源隔离：共享入口场景要自己补 |

- **失效条件**：当查询瓶颈在扫描与源端下推上（下推率低，见 §7.3.2）时，换一个更快的执行运行时不会改善端到端耗时——省下的是算子时间，浪费的是传输与扫描时间。
- **自验方法**：按 §7.3.4 的做法分别测「扫描层耗时」「算子耗时」「规划耗时」。规划占比高 → 瓶颈在优化器与统计信息；扫描层占比高 → 先解决下推与分区，而不是换执行层。

#### 5.2.4 统一取数接口：Agent 成为查询引擎的调用者

- **旧做法与它的卡点**：让 Agent 取数，要么走 BI 的私有 API，要么给每个数据源手写一个工具。卡点是**工具数量随数据源增长**（n 个源 × m 类问题），而每个工具的参数语义、权限与错误码都不一致，Agent 侧要么学不会，要么学错——这与 §1.2「统一数据访问」的诉求是同一件事，只是调用方换成了 Agent。
- **AI 改变了什么机制**：把「SQL 作为唯一的取数动词」暴露给 Agent（Trino 一类联邦查询引擎本来就是「一份 SQL 访问所有数据」的入口，见 §1.1），并用工具协议把这个能力标准化。真正改变的是**调用者的身份**：以前是人 / BI 工具，现在是 Agent，于是权限、审计、限额都必须以「非人主体」为前提重做。
- **由此得到的**：因为 SQL 是一个已经成熟、且**可被约束**的接口（参数化、只读账号、行 / 列级权限、限额），所以给 Agent 开放取数不必发明新协议；**因为**执行仍在引擎内，**所以**既有的下推率、统计信息与优化器继续有效——Agent 不会让引擎变快，但也不必换引擎。
- **由此付出的**：权限模型必须新增「Agent 身份」这一维，人 / 服务账号两档不够——否则要么给 Agent 过大的权限，要么每次靠人代签，Agent 的自动化价值被抵消；自然语言 → SQL 的生成环节会把「错误的口径」带进系统（见 5.2.1），而错误口径在 Agent 手里会被**规模化放大**；协议本身仍在演进（③ 不满足），绑定某一版会带来迁移成本。
- **证据与来源**：【公开】模型上下文协议（Model Context Protocol）由 Anthropic 于 2024 年 11 月首次公开，其后有带日期的规范修订版本——判断某个客户端 / 服务端支持哪一版，看它声明的规范版本号，而不是看生态清单页。第三方（非厂商）公开生产案例不公开，故 ② 不满足。
- **成熟度**：**L2** —— 协议与接口可用，但生态未稳、第三方生产案例缺失。

工具层必须自己承担的检查项（缺一项就不要给 Agent 开放取数）：

| 检查项 | 为什么必须在工具层做 | 缺了会怎样 |
| --- | --- | --- |
| Agent 身份与授权 | 引擎多数只认人 / 服务账号，无法区分「谁的 Agent」 | 权限只能给大，无法按会话收窄 |
| 只读账号 + 语句类型白名单 | 生成式模型会产出写入 / DDL 语句 | 一次误生成就可能改数据 |
| 行 / 列级权限过滤 | 越权必须在执行前拦（不能事后告警） | 数据外泄，且日志成为证据链负担 |
| 限额（并发 / 扫描量 / 返回行数） | Agent 会高频、无节制地重试 | 单个 Agent 拖垮共享入口 |
| 审计记录（谁 / 何时 / 查了什么） | 「非人主体」若不留痕就无法复盘 | 出事后无法定位到具体会话 |

- **失效条件**：当 Agent 只需要一两个固定指标时，直接给只读 API 比开放 SQL 更安全也更便宜——统一接口的收益随数据源数量与问题种类的增加而增长，源少时它只是负担。
- **自验方法**：统计最近一个月 Agent 侧的工具调用，分别计数「因参数 / 权限被拒」与「生成了错 SQL」。前者高 → 接口与说明设计问题；后者高 → 语义层问题，不是工具层问题。

**表中其余方向为什么停在这里（判据一句话）**：

- **AI 驱动的查询优化**：没有正式发布的能力项，公开材料只有论文与厂商演示（① 不成立）→ L3。
- **自治查询引擎**：现有的自适应能力（§2.1 的 AQE）是运行时统计与规则，把它算作 AI 是命名混淆；真正的「自治」没有可核验定义（①③ 不成立）→ L3。
- **AI 原生查询**：作为合并叙事，按最弱组成项（自治优化 L3）评级 → L3（§1.4 的「AI 原生」阶段是历史分期，不是能力清单）。
- **查询引擎 + RAG**：接口可拼装、能力可用，但第三方生产归因方法（检索质量如何影响答案）没有公开可引用的做法（② 不成立）→ L2。
- **查询引擎 + GraphRAG**：图查询与 SQL 的联合执行没有标准化接口，联合计划的代价模型也不存在（① 不成立）→ L3。
- **嵌入式 OLAP**：版本化发布与稳定 SQL 接口都满足，但「谁在生产里用它做分析」列不出可核验的第三方公开材料（② 不成立）→ L2。
- **联邦数据网格**：联邦查询能力本身生产可用，但「数据网格」作为组织形态无可核验判据，且它要求的是权限与组织配套，不是引擎特性（② 不成立）→ L2。

**具名工具 / 项目的落点**（只给归属与核验方式，不对其能力下断言）：

| 具名工具 / 项目 | 归属本节的哪一行 | 核验方式 |
| --- | --- | --- |
| 对话式取数产品（Databricks Genie、Snowflake Cortex 一类） | 自然语言查询 | 查该产品文档中文本转 SQL 功能的当前状态与评测条件（数据集、schema 规模） |
| Trino + LLM | 自然语言查询 / 统一取数接口 | 查是否有官方维护的 MCP 一类工具接入，以及其权限模型 |
| Trino + 向量库（LanceDB、Milvus 一类） | 联邦向量检索 | 查连接器是官方还是社区维护，以及能否下推距离过滤与 top-k |
| Trino + Neo4j | 查询引擎 + GraphRAG | 查连接器文档；联合计划的代价模型是否公开 |
| DataFusion + Arrow | 列式内存格式与向量化执行（§5.2.3） | 版本发布说明 + 论文（SIGMOD 2024） |
| Velox 一类独立执行运行时 | 列式内存格式与向量化执行 | 机制见 §7.3.4（执行层与 SQL 层解耦） |
| Impala 与 Iceberg 集成 | 联邦 / Lakehouse 集成的既有能力，**不是**本节的新方向 | 查该版本 release note |
| MCP | 统一取数接口 | 查它声明的规范版本号 |

### 5.3 与本主题既有栈的接口在哪

AI 能力不是新引擎，而是挂在既有引擎周边。下表写清接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 元数据 / 语义定义 ↔ 自然语言查询 | 单向读：元数据（表、字段、指标、枚举值）注入提示；回写：生成的 SQL 先解析校验再执行 | 口径错归元数据侧（谁维护指标定义谁负责）；语法错归模型侧 | 需自建；多数团队缺「指标 → 字段」的映射 |
| 向量索引 ↔ 查询引擎 | 连接器或表函数：向量列当普通列读 + 距离算子 + top-k | 距离过滤没下推 → 引擎侧（传输成本）；漏召回 → 索引参数侧 | 需验证下推能力，见 5.2.2 |
| Agent 工具层 ↔ 查询引擎 | SQL 作为工具：参数化 + 只读账号 + 行 / 列级权限 + 限额 | 越权 → 工具层必须在**执行前**拒绝 | 需自建；引擎侧多数不认「Agent 身份」 |
| 权限与审计 ↔ 引擎 | 需要「非人主体」这一新维度：审计能回答「这次查询是人还是 Agent 发起的」 | 平台侧（身份与留痕都在平台） | 需扩展身份模型，见 5.2.4 |
| 统计信息 ↔ 优化器 | 优化器的输入就是统计信息（§7.3.2、§7.3.4） | 统计缺失 / 过期 → 数据侧（写表的人负责维护） | 既有能力，与 AI 无关但决定上限 |
| 列式内存格式 ↔ 宿主进程 / 多引擎 | 零拷贝交换：内嵌执行层跑在宿主进程里，不落中间文件 | 宿主进程（生命周期与资源都由它管） | 既有能力，见 5.2.3 |

这张表里有两条「既有能力」行（统计信息、列式格式），它们与 AI 无关，却决定 AI 方向的上限：自然语言查询的准确率取决于元数据与统计信息的**质量**，向量检索的代价取决于下推能力，而这两件事都不会因为加了一个模型而变好。

另外四条「需自建」行的失败归属必须在设计阶段写清，否则会退化成扯皮：

- **口径错**归元数据侧。把口径错记成「模型不行」，会让团队去换模型，而问题在指标定义。
- **越权**必须在执行前拒绝，且由工具层负责。事后告警等同于事故已发生。
- **Agent 身份**缺失时，最省事的做法往往是共享一个高权限账号——这是本节最危险的一步，因为它把前面所有设计一次性作废。

### 5.4 公开进展与文献

- **论文**：Apache Arrow DataFusion（SIGMOD 2024），把内嵌式、Arrow 原生的分析引擎作为设计目标写进论文；Apache Calcite（SIGMOD 2018），异构数据源上的优化与查询处理框架，是「SQL 前端与优化器可分离」的机制来源之一；Presto 的工程论文（ICDE 2019）记录了联邦查询引擎的早期形态【公开，会议论文】。
- **评测基准**：Spider（EMNLP 2018）与 BIRD（NeurIPS 2023）是文本转 SQL 的公开基准，后者以「真实库、脏数据、大 schema」为设计目标，正好对应生产环境的失败来源【公开】。用基准成绩选型时，先看它是否公开了评测条件：
  - 评测集与 schema 规模（是否是真实的、带脏数据的库）；
  - 是否允许人工澄清、允许多少轮；
  - 是否按「执行结果一致」还是「字符串相似」计分。
- **官方 release note 与规范**：判断「某版本是否支持某特性」（Iceberg 新格式、向量类型与距离算子、连接器更新、内嵌接口变化），唯一可靠来源是该版本的 release note 与连接器文档的当前版本。列式内存格式一侧，判据是 Apache Arrow 的格式规范与跨实现集成测试是否通过【公开，版本化发布】。
- **协议规范**：模型上下文协议（Anthropic，2024 年 11 月首次公开，其后有带日期的修订版本）【公开】。判断支持情况看规范版本号，不看生态清单。
- **引用纪律**：项目名对而会议 / 年份错，是「某项目发表了某论文」这类引用最常见的错误；核验方法是查会议论文集或项目官网的 publications 页，而不是看二手博客。同理，任何「某引擎比某引擎快 N 倍」的说法，先看它有没有给出数据量、并发、硬件、是否含下推与缓存等条件。
- **容易被张冠李戴的三类条目**（趋势清单里几乎必然出现，也几乎必然出错）：
  - 「某项目在某会议某年发表论文」——查会议论文集或项目官网的 publications 页；同一个项目在不同年份可能有多篇，不要凭印象合并。
  - 「某版本支持某特性」（例如某引擎对 Iceberg 新格式、向量索引、内嵌接口的版本变化）——查该版本的 release note 与该连接器文档的当前版本。
  - 「某引擎的版本号」（联邦查询引擎的版本号按月递增，跨年记忆极易错位）——查官方发布页与发布日历，不要用博客里的旧数字。
- **值得注意的空白**：本节列不出「第三方（非厂商）在生产中使用自然语言查询 / 联邦向量检索」的公开材料。这不是因为这些方向没用，而是因为这类内部效果数据很少公开——它同时意味着：如果你的团队要做，你大概率是第一批，收益与风险都得自己承担。

### 5.5 被过度宣传的部分

**「AI 自动优化查询」**

- *实际是什么*：运行时的统计反馈 + 规则切换（自适应执行一类，见 §2.1 的 AQE），与 LLM 无关。
- *为什么会这样*：优化器的输入是基数与代价估计，模型不能凭空造出统计信息；统计缺失或过期时，任何「智能优化」都会退化成规则式优化（机制见 §7.3.4）。
- *什么时候它才会成真*：当优化从「单查询」走到「负载级」——能预测查询模式并提前调整布局与物化，且这些动作可度量、可回滚。

**「自然语言查询会替代 SQL」**

- *实际是什么*：换掉的是 SQL 的编写者，不是执行者（见 5.2.1）。SQL 仍然是引擎侧的稳定接口，仍然需要权限、下推与统计信息。
- *为什么会这样*：取数正确性由口径定义与权限决定，而这两者都不在模型里——模型只能读到你给它的元数据。
- *什么时候它才会成真*：当元数据覆盖到「业务问题 → 指标口径」这一层（而不只是「表 → 字段」）时，自然语言才可能成为默认入口；在那之前它是「多一个入口」，不是「换一个入口」。

**「联邦查询 + 向量一步到位」**

- *实际是什么*：距离过滤往往下推不了，引擎会把向量列拉上来算——混合检索退化成「全量传输 + 全量距离计算」。
- *为什么会这样*：ANN 索引在向量库内部，外部引擎读得到向量值、读不到索引结构，因此无法把「过滤 + 距离 + top-k」整段委托出去。
- *什么时候它才会成真*：当连接器能下推这一整段（把 ANN 执行交给源端）时；判断方法是看 `EXPLAIN`（见 5.2.2 的代码块），而不是看连接器列表里有没有这个源。

**「嵌入式引擎会取代集群引擎」**

- *实际是什么*：内嵌族缺的不是性能，而是治理面——权限、审计、资源隔离、多租户（见 §7.4 的隐性成本与 §7.5 的天平反转）。
- *为什么会这样*：集群引擎的常驻成本里本来就包含这些能力；把它们去掉降低的是成本，不是把它们变成了别处自动会有。
- *什么时候它才会成真*：当内嵌引擎生态出现被多家共同实现、且可被独立测试套件验证的权限 / 审计规范时——那一天之前，内嵌适合单机与宿主进程，不适合共享入口。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 元数据 / 语义层成为自然语言查询的显式前置条件 | 产品把「元数据覆盖率 / 指标定义完整度」作为该功能的开启条件，写进配置项与文档 | 产品继续只宣传模型能力，不暴露元数据依赖；准确率宣传仍无评测条件 |
| 向量检索被吸收进通用引擎，而不是长期独立 | 主流引擎 release note 出现**原生**向量类型、距离算子、ANN 索引条目（不是外部连接器） | 引擎侧长期只有薄连接器，向量能力继续停在独立系统 |
| 权限模型出现「非人主体」，Agent 成为一等身份 | 出现服务账号之外的 Agent 身份对象 + 工具级授权 + 可撤销的会话授权 | 三年后权限模型仍只有人 / 服务账号两档 |
| 内嵌引擎补上最小治理面 | 内嵌生态出现被多家共同实现、可被独立测试套件验证的权限 / 审计规范 | 每个内嵌部署仍各写一套，规范长期空缺 |

四条预测都能被**外部文档**证实或证伪，不需要内部数据。逐条看观察方式：

- **第 1 条（语义层成为前置）**：看产品的功能开关与文档，不看发布会。最可能在一年内见分晓。
- **第 2 条（向量被吸收进引擎）**：看引擎 release note 里是否出现原生类型与算子——外部连接器不算。通常一到两年。
- **第 3 条（非人主体权限）**：看权限模型的对象类型有没有新增一档；这类改动会写进产品文档的权限章节。通常三年以上。
- **第 4 条（内嵌引擎的治理面）**：看是否出现可被独立复跑的兼容性 / 合规测试，而不是看是否成立了基金会。时间不可预测。

一个提醒：这四条预测都不是「某产品会不会做」，而是「**判断依据会不会出现在公开文档里**」。前者无法证伪，后者可以被逐条核对——这正是本节用成熟度分级换掉趋势清单的原因。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有联邦查询入口，想接 AI 取数 | 先补元数据与统计信息（下推率优先，见 §7.3.2）；给 Agent 单列只读身份 | 连接器的向量 / ANN 下推能力；原生向量类型是否进 release note | 不要为了「AI 优化」换引擎——瓶颈通常不在执行层 |
| 正在做自然语言自助取数 | 先做指标定义与语义层，再用「需要改口径的条数」验收 | 真实库基准的评测方法论；产品是否暴露元数据依赖 | 不要在元数据缺失时把它放进面向客户的产品 |
| 需要结构化 + 向量统一查询 | 先确认两者能否同库共存（同库才谈得上下推） | 连接器能否把「过滤 + 距离 + top-k」整段下推 | 不要为了「统一查询」再上一个独立向量系统去桥接 |
| 单机 / Notebook / 边缘分析 | 用内嵌引擎，先确认最大一份 join 的构建侧放得下（见 §7.5） | 内嵌侧的权限与审计规范是否出现 | 不要把内嵌引擎当多租户共享入口 |
| 数据散在多源、权限要求高 | 把「谁在查」写进权限与审计（人 / Agent 分开），越权在执行前拦 | Agent 身份权限对象的出现；工具协议规范的版本节奏 | 不要按厂商 benchmark 博客选引擎，也不要用共享高权限账号图省事 |

「明确不要做」那一列的共用逻辑只有一句：**这一节里真正变了的是调用方与编写者，不是执行**。所以预算应当投在元数据、权限与下推这三件「引擎之外、但决定引擎上限」的事上；把它们做完之前，任何「AI 原生查询引擎」的选型都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先量**：最重查询的下推率、最大一份 join 的构建侧数据量、并发形态（见 §7.5 的第 0 步）。这三项决定后面所有选型，且不需要新采购。
2. **再补元数据与统计信息**：不改 SQL、不改引擎，通常就能拿到最大的时延改善，同时它也是自然语言取数的前置条件（见 5.2.1）。
3. **然后做权限与身份**：给 Agent 单列只读身份、行 / 列级过滤、限额与审计（见 5.2.4 的检查项表）。没有这一步，前面两步的成果无法安全地开放给 Agent。
4. **最后才选引擎形态**：换内嵌 / 换集群 / 换连接器都会同时改变权限模型、审计路径与运维方式，是唯一不可快速回滚的一步（见 §7.5 第 3 阶段）。

### 5.8 小结

> 本节小结：AI 在查询引擎上真正改变的机制只有两处——**取数的编写者**从人换成模型（SQL 的执行路径没变），**调用者的身份**从人 / BI 换成 Agent（于是权限与审计必须以非人主体为前提）。它**还没有**改变的，是执行本身：下推率、统计信息与代价模型仍然是性能上限（见 §7.3.2、§7.3.4），换模型不会让引擎变快。本节唯一能过 L1 判据的是**列式内存格式与向量化执行**这一层——不是因为它更「AI」，而是因为它是唯一能由发起方之外的独立实现与独立测试套件核验的方向。
>
> 💡 **思考锚点**：按 §7.5 的第 0 步给你最重的那条查询量三个数——下推率、最大一份 join 的构建侧数据量、并发形态；若瓶颈是下推率，那么给 Agent 单列只读身份并不会让引擎变快，这会改变你"先补元数据还是先做权限"的排序吗？
