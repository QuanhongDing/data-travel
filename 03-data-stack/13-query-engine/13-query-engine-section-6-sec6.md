### 13.1 字节"**把计算送到数据所在处：代价控制的全部要点都在"下推多少"**"（2018-2024）

**背景（Why）**

字节 2018 年面临**"数据散在多种存储里，跨源分析要么搬数据要么做不了"**：
- **数据分布在多种系统中**——**离线湖仓、元数据仓库、消息流、实时分析库、关系库各存一部分，访问方式各不相同**
- **跨源分析需要先把数据搬到一起**——**搬运链路要维护、有延迟，而且搬出来的那份会与源不一致**
- **数据量增长使全量拉取不可行**——**把一个大数据集的全部明细拉到引擎里再过滤，网络传输量会失控**
- **使用门槛高**——**每种存储有自己的查询方式，使用者要学多套**

**触发点（What）**

2018 年起字节以**联邦查询引擎作为统一查询层**（[字节公开材料 2018-2024]），目标：
- **跨源可查、数据不动**
- **统一查询入口**
- **代价可控**

**详细做法（How）**

字节查询引擎方案的**5 大核心组件**：

1. **计划在协调节点生成、数据在源侧过滤（核心创新）**
   - 关键设计：**查询计划由协调节点统一解析与拆分**，各分片任务下发到工作节点；**过滤、投影、部分聚合尽可能下推到数据源执行**，只有无法下推的部分才被拉到引擎内处理
   - 关键能力：**跨源查询的传输量被控制住**——如果所有数据都先拉到引擎内再计算，跨源查询的网络传输量会随数据量失控，而这正是"联邦查询"最容易被诟病的地方
   - 关键数字：**查询尾延迟进入秒级**
   - 关键示意：
     ```text
     联邦查询的代价在哪里（决定了优化该往哪里使劲）
       一个跨源查询的代价构成：
         ① 源侧执行（过滤 / 聚合）
         ② 源 → 引擎的数据传输
         ③ 引擎内计算（跨源关联、最终聚合）
       ────────────────────────────────────────────────
       朴素做法：几乎不把计算下推
         → ① 很少 ② 巨大 ③ 巨大
         → 数据量增长时，②③ 同步增长
         → "联邦查询很慢"的印象由此而来
       ✓ 最大化下推：
         WHERE / 列裁剪 / 聚合尽可能推到源侧
         → ② 只传"过滤聚合后的结果"
         → ③ 只做无法下推的跨源关联
       ────────────────────────────────────────────────
     判据：联邦查询能不能用，取决于
           "有多少计算被下推到了源侧"
           而不是取决于引擎本身有多快
     ```

2. **统一的连接器接口屏蔽存储差异（核心）**
   - 关键设计：**各种数据源通过统一接口接入**（元数据读取、谓词下推能力声明、分片方式），新数据源接入 = 增加一个连接器
   - 关键能力：**新数据源接入成本极低**——不必为每个新源建一条抽取链路，而这在数据源数量增长时差别巨大
   - 关键数字：**接入数十种数据源**

3. **查询层的资源隔离（核心）**
   - 关键设计：**交互式查询与大批量任务使用不同集群与资源池**，避免长任务占满资源
   - 关键能力：**交互体验稳定**——一个跑数小时的任务不应拖垮所有交互用户
   - 关键性质：**交互查询延迟稳定**

4. **基于被广泛验证的引擎构建（核心）**
   - 关键设计：**使用经过大规模生产验证的开源查询引擎作为基础**，把精力放在下推优化、连接器与运维上，而不是从零实现查询引擎
   - 关键能力：**能力演进可借力生态**——优化器、连接器、执行引擎的改进来自社区
   - 关键性质：**引擎能力随社区演进**

5. **多地域就近查询（核心创新）**
   - 关键设计：**各区域部署查询集群**，就近访问本区域数据
   - 关键能力：**跨区域传输量可控**——所有查询发往一个中心区域时，跨区网络会成为瓶颈
   - 关键性质：**多区域部署**

**字节查询引擎方案关键数字**（[字节公开材料 2018-2024]）：

| 指标 | 改前（搬数据） | 改后（联邦查询） | 提升 |
| --- | --- | --- | --- |
| **跨源分析** | 需先建抽取链路 | 统一查询层直接查 | **无搬运链路** |
| **数据新鲜度** | 由抽取周期决定 | 源侧数据天然最新 | **不滞后** |
| **数据一致性** | 桶出副本可能不一致 | 只有一份 | **无"哪份对"** |
| **传输量** | 全量拉取 | 下推后只传结果 | **大幅下降** |
| **新数据源接入** | 建一条链路 | 增加一个连接器 | **成本大降** |
| **查询入口** | 多套工具与语言 | 一套查询语言 | **统一** |
| **交互体验** | 与批任务混用资源 | 资源隔离 | **稳定** |
| **可支撑规模** | 受搬运能力限制 | 数十种源、秒级 | **可扩展** |

**具体数字（How much）**

- 团队规模：字节查询引擎相关团队 50+ 人
- 关键性质：**下推最大化**；**统一连接器接口**；**资源隔离**；**多区域部署**
- 业务影响：让跨异构源的分析不必先建搬运链路，同时把查询入口统一成一套语言

**失败教训**

- 早期「**跨源分析靠建抽取链路**」——链路多、数据滞后、副本不一致，倒逼**「统一查询层，数据留在原处」**
- 「**所有数据拉到引擎内再计算**」——传输量随数据量失控、被诟病"联邦查询慢"，倒逼**「最大化下推，只传结果」**
- 「**为每个新数据源建一条链路**」——接入成本随源数量线性增长，倒逼**「统一连接器接口」**
- 「**从零自研查询引擎**」——优化器与连接器生态难以跟上，倒逼**「基于被验证的引擎构建」**
- 「**交互与批任务混用资源**」——长任务拖垮交互体验，倒逼**「按工作负载隔离资源」**

### 13.2 Uber"**用一层查询屏蔽实时与离线的存储差异：业务只写一次 SQL**"（2020-2024）

**背景（Why）**

Uber 2020 年面临**"同一业务问题要跨实时与离线两套存储回答"**：
- **实时与离线数据存在不同系统**——**实时数据在列存分析库（面向低延迟点查与聚合），离线数据在湖与仓里**
- **使用者要自己拼接两处结果**——**"最近一小时 + 最近一个月"这类查询要在两套系统各查一次再手工合并**
- **两套查询方式不同**——**存储不同导致查询能力与写法不同，使用者要学两套**
- **口径难以对齐**——**两处各算一遍，同一个指标在两个系统里的定义可能不同**

**触发点（What）**

2020 年起 Uber 把**实时存储接入统一查询层**（[Uber 公开材料 2020-2024]），目标：
- **一次 SQL 查实时与历史**
- **屏蔽存储差异**
- **口径统一**

**详细做法（How）**

Uber 统一查询方案的**5 大核心组件**：

1. **用统一查询层屏蔽"数据存在哪里"这一事实（核心创新）**
   - 关键设计：**实时存储与离线存储都通过连接器接入同一个查询引擎**，使用者写一次查询即可同时访问两处；查询引擎负责把各部分下推到相应存储执行
   - 关键能力：**业务不必知道数据的存储形态**——这是这类统一层最直接的价值：把"数据分布的技术事实"从业务问题里移除
   - 关键性质：**一次查询覆盖实时与历史**
   - 关键示意：
     ```text
     屏蔽存储差异的价值在哪（不只是"方便"）
       ✗ 业务自己拼两处结果
         ① 要在两套系统各写一遍查询（两套语法、两套能力）
         ② 要手工对齐两边的口径（实时库里的"订单数"与
            离线仓里的"订单数"很可能定义不同）
         ③ 要手工合并结果（时间边界怎么衔接？）
         ④ 每个业务重复做一遍上述三件事
       ✓ 统一查询层
         业务写一次查询，引擎负责拆分与下推
         → ① 只学一套
           ② 口径在统一定义处对齐
           ③ 时间边界由引擎处理
           ④ 做一次，所有业务共用
       ────────────────────────────────────────────────
     关键：把"实时与离线怎么接起来"
           从每个业务各自的工程问题，
           变成平台做一次、所有人共用的一层
     ```

2. **实时存储承担低延迟点查与聚合（核心）**
   - 关键设计：**面向低延迟的分析库承载实时数据**（列存 + 索引），查询引擎把实时部分的过滤与聚合下推到它
   - 关键能力：**实时路径延迟达标**——实时数据如果是"分钟级延迟写入的批处理结果"，那它就不是实时的
   - 关键数字：**实时数据延迟进入秒级**

3. **离线存储承担历史与大规模扫描（核心）**
   - 关键设计：**离线数据以开放表格式存放在湖上**，查询引擎直接读取其元数据与数据文件
   - 关键能力：**历史数据不必再导入一份**——为查询而导入意味着额外存储与一条要维护的链路
   - 关键性质：**历史数据无需二次导入**

4. **下推与跨源关联的代价控制（核心）**
   - 关键设计：**实时部分与离线部分的过滤聚合各自下推**，只在需要关联时把必要的中间结果拉到引擎内
   - 关键能力：**跨存储查询的代价可控**——把两边的明细都拉到一起做关联，代价会随数据量爆炸
   - 关键性质：**大幅下推、引擎内只做必要关联**

5. **多业务共用同一套查询入口（核心创新）**
   - 关键设计：**各业务使用同一个查询层**，而不是各自搭一套"实时 + 离线"的拼接逻辑
   - 关键能力：**口径与实现只做一次**——每个业务各自拼接时，口径对齐会在每处重复并各自出错
   - 关键性质：**多业务共用同一入口**

**Uber 统一查询方案关键数字**（[Uber 公开材料 2020-2024]）：

| 指标 | 改前（业务自己拼两处） | 改后（统一查询层） | 提升 |
| --- | --- | --- | --- |
| **查询方式** | 两套系统各写一遍再合并 | 一次查询覆盖两处 | **只学一套** |
| **口径对齐** | 每个业务各自对齐 | 平台统一次 | **做一次共用** |
| **存储差异** | 使用者需了解 | 被查询层屏蔽 | **从业务问题里移除** |
| **实时延迟** | 受批处理延迟决定 | 实时库写入 | **秒级** |
| **历史数据** | 需导入查询系统 | 直接读湖上表 | **无二次导入** |
| **跨存储代价** | 明细全拉后关联 | 下推后只拉必要结果 | **可控** |
| **多业务** | 各自拼接 | 共用同一入口 | **重复消除** |
| **时间边界处理** | 各业务自行衔接 | 引擎处理 | **一致** |

**具体数字（How much）**

- 团队规模：Uber 查询引擎相关团队 30+ 人
- 关键数字：**统一查询层屏蔽存储差异**；**实时秒级**；**历史直读湖上表**；**多业务共用**
- 业务影响：让"实时 + 历史"的联合分析从每个业务各自的工程问题，变成平台提供的一层能力

**失败教训**

- 早期「**业务自行拼接实时与离线结果**」——两套语法、口径各自对齐、时间边界各自处理，倒逼**「统一查询层做一次」**
- 「**用批处理结果充当"实时"数据**」——延迟由批处理周期决定，倒逼**「实时数据由实时存储承载」**
- 「**为查询把历史数据导入分析系统**」——额外存储与要维护的链路，倒逼**「直接读取湖上表」**
- 「**把两处明细都拉到引擎内关联**」——代价随数据量爆炸，倒逼**「最大化下推，只拉必要结果」**
- 「**各业务各搭一套拼接逻辑**」——口径对齐在每处重复且各自出错，倒逼**「多业务共用同一入口」**

### 13.3 Netflix"**把统计信息随数据一起写：让优化器永远拿到新鲜的基数**"（2019-2024）

**背景（Why）**

Netflix 2019 年面临**"查询性能高度依赖统计信息是否新鲜，而统计维护本身是负担"**：
- **传统方式需要额外维护统计信息**——**需要单独运行收集任务，而收集频率与数据变化速度往往不匹配**
- **统计过期导致计划选错**——**数据分布变化后仍按旧统计做估算，可能选择明显更差的计划**
- **大规模数据下收集成本高**——**在极大数据量上做全量统计收集，本身要消耗大量资源**
- **优化器与存储格式脱节**——**优化器不知道数据的真实分布，只能依赖被单独维护的统计**

**触发点（What）**

2019 年起 Netflix 让**优化器直接使用表格式自带的元数据统计**（[Netflix 公开材料 2019-2024]），目标：
- **统计免维护**——随数据写入自动更新
- **估算更准**——计划选择更稳定
- **大范围裁剪**——只扫描相关数据

**详细做法（How）**

Netflix 方案的**5 大核心组件**：

1. **统计信息随数据一起写，取消独立的收集环节（核心创新）**
   - 关键设计：**数据写入时同步记录列级统计**（每列的最小值、最大值、空值数量、行数），保存在表的元数据中；优化器直接读取这些元数据做估算
   - 关键能力：**统计永远与数据同步**——独立的收集任务不可避免地存在"上次收集到现在"的窗口，而写入时同步记录把这个窗口消除
   - 关键性质：**无需单独维护统计、估算准确度明显提升**
   - 关键示意：
     ```text
     统计信息的两种来源（决定了它会不会过期）
       ✗ 独立收集任务
         数据写入 → （等下一次收集）→ 统计更新
         问题：① 收集与写入之间有窗口 → 窗口内统计是旧的
               ② 收集频率要在"准确"与"开销"之间取舍
               ③ 忘记收集 → 优化器长期按旧统计决策
       ✓ 写入时同步记录
         写入数据的同时写下列级统计到元数据
         → ① 没有窗口，统计与数据同步
           ② 没有独立的收集开销
           ③ 不存在"忘记收集"这种状态
       ────────────────────────────────────────────────
     代价：写入路径要承担统计计算的成本
           且统计粒度有限（列级 min/max/空值数，而非完整直方图）
         —— 换取了"永不过期"
     ```

2. **列级统计直接支撑大范围裁剪（核心）**
   - 关键设计：**利用列的取值区间跳过不可能命中的文件**——查询条件在时间范围上时，可跳过绝大部分数据文件
   - 关键能力：**扫描量下降一个量级**——不需要读文件内容就能判断"这份文件里不可能有符合条件的数据"
   - 关键性质：**大部分文件被跳过**

3. **元数据分层使裁剪代价可控（核心）**
   - 关键设计：**元数据自身也是分层的**（表 → 快照 → 文件清单 → 文件），裁剪在每一层做一次，越往下越细
   - 关键能力：**裁剪本身的代价也低**——如果裁剪要遍历全部文件清单，那么"跳过文件"省下的时间可能被"查找文件"吃掉
   - 关键性质：**裁剪层次化、代价可控**

4. **读不锁写、写不阻塞读（核心）**
   - 关键设计：**提交产生新快照，读取固定在某个快照上**，读写互不阻塞
   - 关键能力：**长查询与持续写入可以共存**——没有快照隔离时，一边在写一边在查是最容易出问题的场景
   - 关键性质：**读写互不阻塞**

5. **元数据接口保持兼容（核心创新）**
   - 关键设计：**元数据接口保持向后兼容**，新能力以可选方式加入
   - 关键能力：**基于该格式的引擎实现不会因升级而失效**——接口频繁变更会让所有实现方持续付出适配成本，最终选择退出
   - 关键性质：**接口兼容、实现方可持续跟进**

**Netflix 方案关键数字**（[Netflix 公开材料 2019-2024]）：

| 指标 | 改前（独立收集统计） | 改后（随数据写入） | 提升 |
| --- | --- | --- | --- |
| **统计来源** | 独立收集任务 | 写入时同步记录 | **无窗口** |
| **统计新鲜度** | 由收集频率决定 | 与数据同步 | **永不过期** |
| **收集开销** | 需在准确与开销间取舍 | 无独立开销 | **消除** |
| **估算准确度** | 受统计陈旧影响 | 明显提升 | **计划更稳** |
| **文件裁剪** | 依赖统计质量 | 列级 min/max 直接裁剪 | **跳过大部分文件** |
| **裁剪代价** | — | 元数据分层，逐层裁剪 | **可控** |
| **读写并发** | 可能互相干扰 | 快照隔离 | **互不阻塞** |
| **接口兼容** | — | 保留兼容承诺 | **实现方敢投入** |

**具体数字（How much）**

- 团队规模：Netflix 查询与数据平台相关团队 50+ 人
- 关键性质：**统计随写入同步记录**；**列级 min/max 裁剪**；**元数据分层**；**快照隔离**
- 业务影响：让优化器始终基于与数据同步的统计做决策，并把扫描量通过裁剪压下去

**失败教训**

- 早期「**统计靠独立收集任务维护**」——收集与写入之间存在窗口、且可能忘记收集，倒逼**「写入时同步记录统计」**
- 「**只维护表级统计**」——无法做文件级裁剪，扫描量居高不下，倒逼**「列级 min/max 随文件记录」**
- 「**裁剪时遍历全部文件清单**」——裁剪的代价吃掉了裁剪的收益，倒逼**「元数据分层，逐层裁剪」**
- 「**读写不加隔离**」——长查询与写入互相干扰，倒逼**「快照隔离」**
- 「**元数据接口频繁不兼容变更**」——实现方持续付出适配成本并逐渐退出，倒逼**「接口保持兼容」**

### 13.4 美团"**联邦编排 + OLAP 加速层：谁做编排、谁做重活**"（2020-2024）

**背景（Why）**

美团 2020 年面临**"业务既要跨源灵活查询，又要看板级的低延迟响应"**：
- **跨源需求真实存在**——**业务分析常常要同时看湖里的明细与仓里的维表**
- **看板对延迟要求严格**——**交互式看板要求秒级响应，而跨源关联本身就慢**
- **重聚合查询占比高**——**看板类查询以聚合为主，且形式高度重复**
- **两套需求混在同一层处理**——**把跨源编排与重聚合计算都压在一个引擎上，两边的性能都被拖累**

**触发点（What）**

2020 年起美团构建**联邦查询 + 专用 OLAP 加速层的分层方案**（[美团公开材料 2020-2024]），目标：
- **跨源编排与重聚合各归其位**
- **看板秒级响应**
- **多业务共用**

**详细做法（How）**

美团分层方案的**5 大核心组件**：

1. **把"编排"与"重计算"分到两层（核心创新）**
   - 关键设计：**联邦层负责跨源查询的解析、拆分与编排**，识别出落在同一份大数据上的重聚合部分后**下推给专用的 OLAP 加速层**；加速层用适合分析的计算方式完成，结果回到联邦层做最后的跨源合并
   - 关键能力：**两类需求互不拖累**——联邦层擅长"把多个源连起来"，加速层擅长"在一个大表上快速聚合"；把重活放在错误的层上，两者都会变差
   - 关键数字：**看板查询尾延迟进入秒级**
   - 关键示意：
     ```text
     两层分工的依据（决定了各自的性能上限）
       联邦层的能力：
         解析多源查询 / 拆分下推 / 跨源关联与合并
         —— 强项是"连接",弱项是"在大数据上做重聚合"
       OLAP 层的能力：
         列存 / 向量化 / MPP 并行 / 本地预聚合
         —— 强项是"在大表上快速聚合",弱项是"跨源编排"
       ────────────────────────────────────────────────
       ✓ 让查询落在各自强项上：
         联邦层判断："这部分重聚合完全落在一张 OLAP 表上"
                  → 整段下推给加速层
         加速层：向量化执行完成聚合
         联邦层：只做剩余部分的跨源合并
       ────────────────────────────────────────────────
     判据：如果某类查询"每次都慢、且慢在同一个环节"，
           就该考虑把那个环节交给更擅长的组件，
           而不是继续优化当前这个组件的短板
     ```

2. **谓词与聚合尽可能下推到加速层（核心）**
   - 关键设计：**过滤条件与聚合操作下推到加速层执行**，联邦层只接收聚合后的结果
   - 关键能力：**跨层传输量可控**——如果聚合在联邦层做，就要把明细拉上来，代价随数据量增长
   - 关键性质：**跨层传输的是聚合结果而非明细**

3. **向量化执行提升单位扫描效率（核心）**
   - 关键设计：**加速层按批次向量化处理数据**，而不是逐行计算
   - 关键能力：**同等扫描量下 CPU 效率成倍提升**
   - 关键数字：**扫描吞吐成倍提升**

4. **多业务共享加速层并隔离资源（核心）**
   - 关键设计：**各业务共用同一套加速层**，通过资源组与队列隔离
   - 关键能力：**成本被多业务分摊**——单业务建一套加速层在成本上不成立
   - 关键性质：**多业务共用、资源隔离**

5. **查湖仓两处而不搬数据（核心创新）**
   - 关键设计：**联邦层直接读取湖上表**（含其元数据），不必先把湖数据导入加速层
   - 关键能力：**避免二次导入**——为查询把数据搬进加速层，意味着额外存储与一条要维护的同步链路
   - 关键性质：**湖上数据无需二次导入**

**美团分层方案关键数字**（[美团公开材料 2020-2024]）：

| 指标 | 改前（一层承担全部） | 改后（分层） | 提升 |
| --- | --- | --- | --- |
| **职责划分** | 编排与重计算混在一层 | 联邦层编排 + 加速层重计算 | **各落强项** |
| **看板查询尾延迟** | 分钟级 | 秒级 | **大幅下降** |
| **跨层传输量** | 明细上拉 | 只传聚合结果 | **大幅下降** |
| **扫描效率** | 逐行处理 | 向量化 | **成倍提升** |
| **大表聚合** | 在联邦层做，慢 | 下推加速层 | **显著加快** |
| **湖上数据** | 需导入加速层 | 直接读取 | **无二次导入** |
| **多业务** | 各自建一套 | 共用 + 资源隔离 | **成本分摊** |
| **可支撑规模** | 受单层能力限制 | 分层各自扩展 | **可扩展** |

**具体数字（How much）**

- 团队规模：美团查询引擎相关团队 30+ 人
- 关键性质：**编排与重计算分层**；**下推聚合**；**向量化执行**；**湖上数据直读**
- 业务影响：让跨源灵活查询与看板级低延迟同时成立，并把多业务的成本分摊到同一套加速层上

**失败教训**

- 早期「**用一层承担编排与重聚合**」——两类需求互相拖累、两边的性能都不理想，倒逼**「按强项分层，重聚合下推给专用加速层」**
- 「**聚合在联邦层做**」——要把明细上拉、传输量随数据量增长，倒逼**「谓词与聚合尽量下推」**
- 「**逐行处理扫描结果**」——同等数据量下 CPU 效率低，倒逼**「向量化执行」**
- 「**为查询把湖数据导入加速层**」——额外存储与同步链路，倒逼**「直接读取湖上表」**
- 「**各业务各建一套加速层**」——成本重复且规模不经济，倒逼**「共用并做资源隔离」**

### 13.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**统一查询层接入 2-3 种数据源**」（**最简单**）——**1 个业务域**
- 产出：**一个统一查询入口 + 跨源查询不搬数据的验证 + 下推前后的传输量对比**
- 团队：**2-3 人**
- 验证标准：**跨源查询不需要预先建抽取链路**、**过滤与投影确实被下推到源侧**、**查询延迟可接受**

**1 → 10 阶段：6-12 个月**

- 扩展到「**十级数据源 / 资源隔离**」
- 引入「**统一连接器接口**」——新数据源接入成本 = 增加一个连接器
- 引入「**按工作负载隔离资源**」——交互查询与大批量任务分离
- 团队：5-10 人
- 验证标准：**新源接入不需要建链路**、**交互延迟不被长任务影响**、**传输量随下推比例下降**

**10 → 100 阶段：12-24 个月**

- 扩展到「**实时与历史统一入口**」
- 引入「**实时存储接入同一查询层**」——把"实时 + 历史"从各业务的拼接问题变成平台的一层
- 引入「**统计信息随数据写入**」——优化器永远拿到新鲜基数
- 团队：10-30 人
- 验证标准：**一次查询可覆盖实时与历史**、**统计无需单独收集也不过期**、**文件裁剪跳过大部分数据**

**100 → 1000 阶段：12-24 个月**

- 引入「**按强项分层：联邦层做编排、专用加速层做重聚合**」
- 引入「**元数据接口兼容承诺 + 快照隔离保证读写互不阻塞**」+「**多地域就近查询**」
- 引入「**多业务共用同一入口与加速层，资源隔离**」
- 团队：30-100 人
- 验证标准：**重聚合落在强项组件上**、**读写并发不互相干扰**、**接口升级不破坏已有实现**、**多业务共用而互不影响**

### 13.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**跨源分析方式**」 | 先建抽取链路 | 联邦查询、数据不动 | **无搬运链路** |
| 「**数据新鲜度**」 | 由抽取周期决定 | 源头天然最新 | **不滞后** |
| 「**数据源接入成本**」 | 每源一条链路 | 增加一个连接器 | **大幅下降** |
| 「**传输量**」 | 全量拉取 | 下推后只传结果 | **大幅下降** |
| 「**实时与历史的联合查询**」 | 各业务自行拼接 | 统一入口一次查询 | **做一次共用** |
| 「**统计新鲜度**」 | 由收集频率决定 | 与数据同步 | **永不过期** |
| 「**文件裁剪**」 | 依赖统计质量 | 列级 min/max 直接裁剪 | **跳过大部分文件** |
| 「**交互查询延迟**」 | 受批任务影响 | 资源隔离 | **稳定** |
| 「**看板查询延迟**」 | 分钟级 | 秒级 | **大幅下降** |
| 「**多业务重复建设**」 | 各自拼接与各自建加速层 | 共用一层 | **重复消除** |

**关键投资回报**：
- **直接节省**：「**无需搬运链路 + 传输量下降 + 历史数据不必二次导入 + 多业务不再各自建设**」——**联邦查询层的收益主要是"不再复制数据"**：每条搬运链路都对应一份存储、一份延迟与一份维护成本
- **业务价值**：「**跨源可查 + 实时与历史一次查完 + 统计永不过期**」——**查询层的价值是让"数据在哪里"不再是一个业务问题**：使用者面对一套入口，而存储分布、下推策略、裁剪优化由平台承担
- **AI 时代关键**：「**统一查询入口 + 语义与统计可被机器读取 + 分层各落强项**」——**AI 生成的查询要在正确性之外保证性能**：自然语言转成的查询往往"能跑但很慢"，而"最大化下推""统计随数据写入""按强项分层"正是让自动生成的查询也能达到可接受延迟的前提

---

> **本节小结**：
> - 4 个真实案例（字节 / Uber / Netflix / 美团）印证：**查询引擎不是「**装一个 SQL 引擎**」，是「**最大化下推 + 统一连接器 + 统计随数据写入 + 按强项分层 + 资源隔离**」**5 件套**。
> - 关键时间线：均 4~6 年 —— **查询层是长期工程**，且**它最关键的一个判断是"有多少计算被下推到了数据所在处"**。
> - 选型第一原则：「**统一查询层 + 2-3 种数据源**」（**最简单**）→ 「**统一连接器 + 资源隔离**」（**必须**）→ 「**实时与历史统一入口 + 统计随写入**」（**生产**）→ 「**编排与重计算分层 + 接口兼容 + 快照隔离 + 多地域**」（**AI 时代**）。
> - 99% 的失败来自「**跨源靠搬数据 + 全量拉取 + 统计靠独立收集 + 用一层承担编排与重计算**」——必须有 **数据不动 + 最大化下推 + 统计随写入 + 按强项分层**。
> - 真正的 ROI 来自「**无搬运链路 + 传输量大幅下降 + 统计永不过期 + 多业务重复消除**」——是**"数据在哪里"能否不再是业务问题的分水岭**。
