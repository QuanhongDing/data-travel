## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把「Trino / Presto / Impala / DataFusion / DuckDB」放进同一张 1–5 分的表，用「联邦查询 / 性能 / 内嵌能力 / AI 友好 / 易用性」五个维度打分。这个做法有三个结构性错误。

**错误一：这五者不是同一层的选项。** Trino 与 PrestoDB 是**集群形态的联邦查询引擎**；Impala 是**与数据节点同址的常驻 MPP 引擎**；DuckDB 与 DataFusion 是**可以被嵌进你的进程的库**。给「一台服务器」和「一个函数库」打同一张分表，等价于给「机场 / 自行车」打分——它们不是替代关系，DuckDB 完全可以是一个 Trino 连接器背后的执行部件。

**错误二：「性能」这一维在联邦查询里没有主语。** 一次跨源查询的耗时，绝大部分由「有多少过滤与聚合被下推到了源端执行、多少数据被拉进引擎」决定，而不是由引擎自身快多少决定。同一个 Trino 集群，接一个能下推谓词与聚合的 Iceberg 连接器和接一个只能全表扫的连接器，性能差一个量级是常见的【经验】。打分表的「性能 4 分」比较的是引擎自己，而用户感受到的性能是比较的对象里**没有出现**的那一项。

**错误三：「内嵌能力」不是能力分数，是形态区别。** 给 Trino 的内嵌能力打 1 分、给 DataFusion 打 5 分，隐含判据是「内嵌更好」。但在需要**数十人共享一个查询入口**（经验上十人以上）的企业里【经验】，能内嵌恰好意味着**没有统一的权限、审计与资源隔离**——那里它是一张减分项。这条规模线的依据见 7.5 的阈值依据。同一个数值在不同组织里符号相反，这正是打分表的典型症状。

打分表输出的是**名次**，选型需要回答的是「**在我的数据在哪、谁来用、并发形态是什么的约束下，下一步该用哪一类引擎，以及它在什么条件下失效**」。

**本章采用的 6 条判据**（每条针对查询引擎主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 进程边界 | 引擎跑在**我的进程里**，还是跑在**它自己的集群里** | 决定有没有常驻成本、有没有横向扩展能力、故障面归谁 |
| 数据在哪算 | 能下推多少，剩下的必须拉多少 | 联邦查询的单位成本由**未下推的数据量**决定，而不是引擎快不快 |
| 方言与统计信息 | SQL 方言与上游是否一致；CBO 的统计从哪来 | 没有统计信息时，基于代价的优化器退化成规则式优化器 |
| 容错要求 | 一个工作节点掉线，是重跑整条查询，还是能容忍 | 决定「流水线交换」与「边界物化」的取舍 |
| 并发形态 | 高并发固定查询，还是低并发探索式查询 | 两者单位成本差一个量级，用错引擎会同时更贵更慢 |
| 连接器与生态成本 | 接一个新数据源要多久 | 连接器数量决定联邦的**边界**，也决定长期的人力面貌 |

打分表的五个维度都还在，只是位置变了：「联邦查询 → 判据 2」「性能 → 判据 2 与 5」「内嵌能力 → 判据 1」「易用性 → 判据 3」。「**AI 友好**」同样不是独立维度：Agent 要的是「能被当作库调用（判据 1）+ 元数据与统计信息机器可读（判据 3）+ 一份稳定的 SQL 方言」，这三样都是已有判据的推论；单独给它打分只会重复计权。

判据的顺序对应一个**筛选顺序**：判据 1、2 是**结构性**的（进程边界与下推边界一旦定下，改写量以月计），判据 3–6 是**运行与组织**层面的（多数可调）。**打分表的根本问题在于把这两类混在一根尺子上**——「内嵌能力 5 分 vs 1 分」这种结构性差异，和「易用性 5 分 vs 4 分」这种可以靠一次培训抹平的差异，在表里长得一样重。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Trino | 集群联邦查询引擎 | 协调节点解析规划、无共享工作节点执行；存算分离、无本地存储 | 跨源即席分析的企业（Presto 由 Facebook 2013 年开源，社区于 2018 年底分叉出 PrestoSQL、2019 年 1 月发布首个独立 release，PrestoSQL 于 2020 年更名 Trino【公开，Presto Foundation 成立公告，Linux Foundation，2019；Trino 项目更名说明，2020，均可自行核验】） | Apache 2.0 |
| PrestoDB | 同上，另一支系 | 同样是协调 + 工作节点的 MPP；由基金会治理 | 沿用原 Presto 生态的组织 | Apache 2.0 |
| Impala | 与数据同址的常驻 MPP | 常驻守护进程与存储节点同址，扫描尽量在本地完成 | 传统 Hadoop / CDH 存量栈 | Apache 2.0 |
| DataFusion | 可嵌入的查询库（Rust） | Arrow 原生：内存格式即接口，前端与执行在同一个库内 | 需要把 SQL 嵌进服务或 Python 的项目 | Apache 2.0 |
| DuckDB | 可嵌入的分析型数据库 | 进程内、单机、向量化执行，无客户端/服务端之分【公开，*DuckDB: an Embeddable Analytical Database*（SIGMOD 2019 演示论文），2019】 | Notebook、数据科学、边缘与本地分析 | MIT |
| Spark SQL | 批处理引擎兼 SQL 入口 | 阶段之间物化落盘、靠血缘重算实现容错 | 已有 Spark 生态的组织 | Apache 2.0 |
| 数据虚拟化（Denodo 一类） | 查询中间件 | 尽量把计算留在源端执行，只把结果传回 | 联邦源以数据库为主、且不希望数据外流的组织 | 商业 |
| 向量化运行时（Velox、Photon 等） | 执行层组件 | 把列式向量化运行时从 SQL 前端里独立出来（【公开，Meta Engineering 博客，2022】；【公开，Databricks 官方博客，2021】） | 引擎自研者、希望复用执行层的团队 | 开源 / 商业 |

这 8 项其实分**四族**：**集群 MPP 族**（Trino、PrestoDB、Impala）、**内嵌库族**（DuckDB、DataFusion）、**批处理兼 SQL 入口族**（Spark SQL）、**可分离组件族**（数据虚拟化、向量化运行时）。同族内部差异小，跨族差异大——**先分族再选能省掉一半比较**：先决定「引擎在我的进程里还是别人的集群里」，再在族内比细节。

**打分表对比的候选全部保留**，只是重新归类：

| 选型分支 | 归入本章哪一行 | 它在选型里动的是哪一项 |
| --- | --- | --- |
| 跨源即席查询 → Trino | 集群 MPP 族 | 进程边界（拉到集群算）+ 连接器覆盖 |
| 内嵌 / Notebook → DataFusion / DuckDB | 内嵌库族 | 进程边界（在同一进程内算）+ 无常驻成本 |
| 传统 CDH 生态 → Impala | 集群 MPP 族 | 数据与计算同址，扫描尽量本地化 |
| AI 原生 → DataFusion + Arrow | 内嵌库族 | 内存格式即接口，避免跨进程序列化 |

**上表只列机制，不断言「某产品是否支持某特性」**：连接器能力与引擎版本变化很快，写死会产生过期断言。凡涉及具体能力，用下面三种**判定方法**自查：

- **某个连接器能下推什么**：查该项目连接器文档里的下推能力说明（是否支持谓词、投影、聚合、连接下推），并用自己的查询跑一次 `EXPLAIN`，看计划里过滤条件出现在源端的扫描节点上，还是出现在引擎内的过滤节点上。
- **某个引擎用哪套 SQL 前端与优化器**：查其源码依赖与官方架构文档。举例说明为什么必须自查：「Trino / Spark SQL / Flink SQL 是不是都基于 Calcite（一类通用 SQL 框架）」这种概括式断言，就是一个**可以核验但不宜照抄**的说法——不同引擎在「采用通用 SQL 框架」与「自研前端 + 自研优化器」上是两条路线，路线差异体现在「新语法支持速度」与「优化规则可定制程度」，而不直接体现在性能上。判定方法：在项目源码或依赖清单里查找相应框架的包。
- **某个引擎的性能**：用自己的查询与自己的数据源做 A/B（同一份 SQL、同一份数据、只换引擎），公开材料里的倍数只能用来判断「值不值得试」。

### 7.3 机制差异：为什么它们表现不同（核心节）

四族的全部差异可以归因到四个机制维度。选这四个，是因为它们分别回答选型时必然要问的四件事：**引擎在谁的进程里（7.3.1）· 计算在哪一侧发生（7.3.2）· 中间结果落在哪（7.3.3）· 这三层能不能拆开买（7.3.4）**。每个维度给出「机制 → 因果 → 公开证据 → 失效条件 → 自验方法」。

#### 7.3.1 进程边界：网络交换是免费的吗

**机制是什么**：引擎的执行与调用方的进程之间的边界。内嵌库族把这个边界消除到 0，集群族把它变成一次跨机器数据传输。

**各候选的实现差异**：

| 候选 | 引擎进程 | 数据到引擎的路径 | 横向扩展 |
| --- | --- | --- | --- |
| DuckDB / DataFusion | 调用方进程内 | 内存/本地文件，无序列化 | 无（单机 / 单进程） |
| Trino / PrestoDB | 独立集群 | 连接器协议 + 跨节点交换 | 加工作节点即可 |
| Impala | 常驻守护进程，与存储同址 | 本地磁盘优先，跨节点交换 | 与存储集群同比例扩展 |
| Spark SQL | 独立集群 | 阶段边界物化 + shuffle | 加执行器即可 |

**由此必然导出的性质**：**因为**内嵌库族把数据与执行放在同一个进程里，**所以**它的单位数据代价可以逼近本地磁盘带宽，没有任何网络与序列化开销——这是它能在单机分析上表现突出的**全部原因**，而不是某种算法优势；**同时也因为**同一个原因，它天然没有跨机 shuffle，横向扩展能力为零，单机装不下的数据它就不处理。**反过来**，**因为**集群族把计算与存储彻底分离，**所以**扩容只需加工作节点、也不要求数据与计算同址，代价是**每一次扫描都要付一次网络与协议开销**——单位数据的代价高于本地，且这个差距随跨源 join 的数量累积。

**公开证据**：DuckDB 的定位在 SIGMOD 2019 的演示论文标题里就说清了——「可嵌入的分析型数据库」【公开，2019】；Apache Arrow 作为列式内存格式的项目，其公开目标之一正是消除进程间与语言间的序列化成本（这是该项目 2016 年立项时即写明的设计目标）【公开，Apache Arrow 项目主页，2016】。可自行核验的判据：**看一个引擎是否要求你把数据「注册」进去**——需要注册的，数据与执行之间必然存在一次搬运或一次适配（可能是零拷贝的映射，也可能是一次真实拷贝，这两者要分别确认）。

**失效条件**：当数据量超过单机可处理范围（内存 + 本地盘），内嵌族的所有优势归零——它不会变慢，它会失败。**这条界限的判据不是「总数据量」，而是「最大一份 join 构建侧的数据量」**：hash 连接的构建侧必须物化，所以决定成败的是最大的那个构建侧，而不是全表大小。

**自验方法**：拿你最重的一条查询，在内嵌引擎与集群引擎上各跑一次，记录「读取字节数 / 实际扫描字节数」的比值。内嵌引擎这个比值通常接近 1（本地读取），集群引擎会明显偏离 1（网络与协议开销）——偏离的幅度就是你在为进程边界付的钱。

#### 7.3.2 计算在哪一侧：联邦查询的性能上限由下推率决定

**机制是什么**：一条跨源查询里，有多少过滤、投影、聚合、连接被下推到数据源执行，剩下的部分才需要把数据拉到引擎内处理。

**各候选的实现差异**：

| 候选 | 下推的主体 | 下推能力的上限由什么决定 | 典型不可下推项 |
| --- | --- | --- | --- |
| Trino / PrestoDB | 连接器实现 | 各连接器文档声明的能力矩阵 | 跨源 join、源不支持的函数与类型 |
| Impala | 存储层（HDFS/表格式） | 表格式与统计信息 | 非本地存储的读取 |
| Spark SQL | 数据源实现 | 数据源接口（v1/v2）声明的能力 | 复杂 UDF 与部分聚合 |
| DuckDB / DataFusion | 直接读文件，无「源端」 | 文件格式的统计信息（分区、行组、zone map） | 无源可推，只能做扫描剪裁 |
| 数据虚拟化 | 源端数据库 | 源库自身的优化器 | 源库不支持的算子 |

**由此必然导出的性质**：**因为**联邦查询的代价主体是「被拉进引擎的那部分数据」，**所以**一个引擎的跨源性能主要由**它的连接器与你的数据源的组合**决定，而不是由引擎本身决定——这就是为什么「Trino 和 PrestoDB 谁快」这类问题在跨源场景里通常不是决定性变量：两者的连接器覆盖面与下推能力的差异，往往比引擎内核差异更能解释你实测到的差距。**因为**下推能力由源端声明，**所以**接一个「只能全表扫」的源时，正确解法是换接入方式（先落到对象存储形成带分区与统计的表），而不是换引擎。

**公开证据**：Trino 官方文档为每个连接器单列「下推 / 查询能力」说明【公开，Trino 文档 · Connector，2024】；Iceberg 的连接器路径上，分区裁剪与谓词下推的效果取决于表上的分区与元数据，这一点在 Iceberg 规范中有明确的结构依据（清单文件记录了每个数据文件的分区值与列级统计）【公开，Apache Iceberg 规范 v2，2022】。可自行核验的判据：**用 `EXPLAIN` 看过滤条件落在哪一层**——落在源端扫描节点上才算下推成功。

**失效条件**：当下推率已经很高（只拉聚合后的结果）时，继续优化下推的边际收益趋零，瓶颈转移到引擎内的跨源 join 与最终聚合；此时该动的是查询写法（先聚合再连接）与资源隔离，不是连接器。

**自验方法**：对同一条查询记录两个数——源端在这条查询上涉及的表**全量行数**（取自表的统计信息，或临时关掉该连接器的下推、看源端扫描节点未过滤前的输入行数）、连接器**实际回传**引擎的**行数**。源端替你挡下的比例（1 − 回传行数 ÷ 源端全量行数）就是下推率——它测的是「多少数据根本没离开源端」。不能拿「引擎内算子处理的行数 ÷ 连接器读取的行数」来算：下推好与坏时这两个数会同向收缩，比值恒在 1 附近，根本测不出下推。这个比例长期低于 1/10 量级时，说明绝大部分数据仍被拉进了引擎，联邦查询的经济性尚未成立【经验】。

#### 7.3.3 中间结果落在哪：流水线交换 vs 边界物化

**机制是什么**：一个查询被切成若干阶段，阶段之间传递数据的方式：**不落盘的流水线传输**，还是**落盘的物化**。

**各候选的实现差异**：

| 候选 | 阶段间传输 | 中间结果落盘 | 单个工作节点失败时 |
| --- | --- | --- | --- |
| Trino / PrestoDB | 内存流水线交换 | 默认不落盘（可显式开启溢出到磁盘） | 查询失败，需重跑 |
| Impala | 内存流水线交换 | 主要依赖内存 | 与 Trino 属同类：把容错交给重跑（以各项目当前文档为准） |
| Spark SQL | 阶段边界 shuffle 落盘 | 每个 shuffle 边界写入磁盘 | 靠血缘重算丢失的分区 |
| Differential 数据流系统（Materialize 一类） | 增量差分传播 | 状态常驻 | 依赖状态快照恢复 |

**由此必然导出的性质**：**因为**流水线交换不在阶段边界设同步屏障，**所以**它没有「等最慢的一个分区写完盘」的固定开销，延迟下限低——这是交互式查询引擎能承诺秒级响应的机制来源；**又因为**同一个原因，它没有任何可恢复的中间状态，**所以**一个工作节点掉线就意味着整条查询从头再来，长查询的失败代价与已跑时长成正比（这就是为什么长查询通常被强制设置超时上限，而不是被设计成可容错的）。**反过来**，**因为** Spark SQL 在 shuffle 边界物化，**所以**它能容忍执行器失败并只重算丢失的部分，代价是每一次 shuffle 都是一次真实落盘——对跑 30 分钟但只出错一次的批作业，这笔账是划算的；对跑 3 秒的交互查询，它是纯亏。

**公开证据**：Trino 的执行模型在官方文档的「查询执行」章节有说明：协调节点负责解析规划与调度，工作节点按任务分工执行，节点之间通过交换传递数据【公开，Trino 文档 · 查询执行，2024】；Trino 另提供「溢出到磁盘」选项，用于缓解内存不足，这本身就说明其默认路径是内存中的流水线【公开，Trino 文档 · Spill to disk，2024】。Impala 与 Trino 同属「查询级容错靠重跑」的形态，这一点可由各项目文档中是否存在「查询级容错 / 部分重试」的描述来自验。

**失效条件**：当查询规模大到一个工作节点必然失败（长时间、大 shuffle、跨地域源），流水线模型的「重跑」代价会超过物化模型的开销，此时该换到边界物化的执行模型，或者把这类查询从交互路径挪到批处理路径。

**自验方法**：在测试环境杀一个工作节点，记录「查询是否完成、耗时增加多少」。完成不了的，就是流水线模型；耗时只增加一个分片比例的，就是边界物化 + 血缘重算。

#### 7.3.4 三层可分离：你买的是引擎，还是引擎里的某一层

**机制是什么**：一个查询引擎可以拆成三层——**SQL 前端**（解析与语义）、**优化器**（计划与代价）、**执行运行时**（列式、向量化、算子实现）。历史上它们被打包成一个产品卖。

**各候选的实现差异**：

| 层 | 自研打包的代表 | 采用通用组件的代表 | 可观测的差异 |
| --- | --- | --- | --- |
| SQL 前端 | 自研解析与语义分析 | 复用通用 SQL 框架的引擎 | 新语法（新表格式、新类型）支持速度不同 |
| 优化器 | 自研 CBO / 规则集 | 复用框架的优化规则 | 优化规则可定制程度不同 |
| 执行运行时 | 与引擎绑定 | 独立的向量化运行时（Velox、Photon 一类） | 同一运行时能否被多个前端复用 |

**由此必然导出的性质**：**因为**执行运行时已经被证明可以从 SQL 前端里独立出来（同一个 C++ 向量化运行时被不同前端复用的做法已经公开出现），**所以**「选哪个引擎」这个问题正在分裂成「选哪一层」——你可能需要的只是一个嵌进现有服务的执行层（选内嵌库族），而不是又一个 SQL 网关（选集群 MPP 族）。**因为**优化器的输入是统计信息，**所以**在统计信息缺失或过期的数据源上，基于代价的优化器会退化成规则式优化器——这解释了同一个引擎在不同数据源上表现差异巨大，而这一项常常被误读成「引擎性能不稳定」。

**公开证据**：Meta 公开了其 C++ 向量化执行引擎 Velox，并将其用于多个 SQL 前端之下；Databricks 公开介绍过 Photon 这一同类做法的 C++ 向量化引擎（【公开，Meta Engineering 博客，2022】；【公开，Databricks 官方博客，2021】）。两者对应同一条机制：**执行层可以与 SQL 层解耦**。至于「某引擎是否复用通用 SQL 框架或优化器」，用 7.2 的依赖自查法核验，不要凭印象断言。

**失效条件**：当团队的痛点不在执行效率、而在连接器覆盖与统一权限时，三层可分离带来的选择空间毫无价值——你需要的是一个已经接好了所有源的网关，而不是一个更快的运行时。**判断方法**：如果过去一个季度最耗时的三件事是「接新数据源」「管权限与审计」「查慢在哪」，那么可分离性不在你的收益面上。

**自验方法**：取一条典型查询，分别测「扫描层耗时」「算子耗时」「规划耗时」。规划耗时占比高说明瓶颈在优化器与统计信息，此时换执行运行时没有帮助；扫描层耗时占比高，才轮到执行层与下推。

### 7.4 成本结构对比（不是价格表，是成本函数）

四族的成本**随什么变量增长**：

```
年成本 ≈ 常驻集群(工作节点数 × 规格 × 8760h)          ← 集群族独有
       + 扫描量 × 单位扫描成本(由下推率决定)          ← 集群族与内嵌族共有
       + 元数据服务与连接器维护(连接器数量)
       + 人力(SQL 方言数 + 连接器维护 + 值班面)
```

**主导项与隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| Trino / PrestoDB | 常驻工作节点（无请求时也在付费） | 连接器维护：每接一个源就是一份长期维护责任 |
| Impala | 常驻守护进程，随存储集群规模同比例增长 | 与存量 Hadoop 栈的耦合：升级路径受整个栈约束 |
| DuckDB / DataFusion | 使用它的进程的 CPU 与内存 | **没有**统一治理面：权限、审计、资源隔离要自己补 |
| Spark SQL | 执行器集群（多为弹性） | 交互延迟：为容错付的物化开销 |
| 数据虚拟化 | 商业许可 | 源端负载：把计算推给源库，可能挤占业务库 |

**为什么把「隐性成本」单列**：显性与隐性成本的相对量级会随规模反转。**因为**常驻集群成本是**与请求量无关的固定项**，**而**内嵌引擎的成本只在使用时才发生，**所以**小数据量、低频使用的团队用内嵌族，账单接近于零；一旦使用频次升到「多人数十次并发」量级，内嵌族缺失的统一治理面就会变成真实的人力成本，天平反转。这条反转只构成 7.5 决策树里**两条阈值**的成本侧依据——「跨源 join 源超过 3 个」（ETL 管道数按组合增长、而引擎常驻成本不变）与「多人共享入口 vs 十人量级以内」（固定项要由使用人数摊平）；树上另外两条数值阈值——「最大一份 join 的构建侧放得下吗」与「数百 QPS 级」——分别来自 hash 连接的物化约束与并发 × 单查询资源，与成本反转无关，见 7.5 的阈值依据。

**【推算】数量级示例**（推导链完整给出，便于换参数重算）：

- **一套 Trino 集群 20 台 8C16G 常驻**：8 vCPU / 16 GiB 属 **1:2 的 vCPU:内存比**，对应云上的**计算优化型实例**（c5 / c6i 一类的 2xlarge 档），按需价 **$0.3–0.5/h 量级**【公开，AWS EC2 计算优化型实例按需定价页，2024；价格随区域与代际变动，此处取量级】→ 年支出 ≈ 20 × $0.4 × 8760 ≈ **$70k/年**【推算】。这是集群族无论用不用都要付的钱，也是「内嵌族零成本」这句话的参照物。
- **同一批数据的存储费**：10 TB 放对象存储标准层，10240 GB × $0.023 × 12 ≈ **$2.8k/年**【推算，单价见 AWS S3 定价页 2024】。**约 25 倍，跨一个数量级**——它说明联邦查询引擎的账单几乎全在「常驻计算」，不在数据。任何以「省存储」为理由的引擎选型，量级上都不值得当作主要理由。
- **内嵌族的对照**：把同样的查询放到一台已存在的 8C32G 机器上跑，**增量成本近似为 0**（那是本来就要付的服务器或笔记本成本）【经验】；真正的成本是「没有统一入口」造成的协作损耗，这项不出现在账单上。
- **下推率的换算**：若一条查询要从源端拉 1 TB 而不是 10 GB，在集群族里这笔差额同时体现在网络传输、引擎内算子与工作节点内存上；**按「拉取量相差 100 倍」估算，同一查询的耗时与资源占用会呈同数量级差异**【推算，前提：瓶颈在传输与算子而非源端计算】。这就是为什么 7.3.2 把下推率放在性能讨论的中心。

**主导项随场景切换，所以优先级不是固定的**：

| 你的场景 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| 单机分析、数据在本地文件 | 使用者进程的 CPU | 内嵌引擎；先确认最大 join 构建侧放得下 |
| 多人共享入口、数据散在多源 | 常驻集群 | 集群引擎；先把最贵的那条源的下推做上去 |
| 高并发固定报表 | 常驻集群 × 并发下的资源占用 | 别用联邦引擎：物化到 OLAP 引擎 |
| 低频长查询、数据在对象存储 | 扫描量 | 先把分区与列统计补齐，再谈引擎 |
| 已有 Spark 生态 | 执行器集群（弹性） | 复用现有栈；交互式场景另配一个内嵌或集群引擎 |

### 7.5 决策树（每个分支都要有阈值依据）

```
你的数据在哪、谁要用？
├─ 数据在本地文件 / 单机可容纳，使用者是个人或单个服务
│    → 内嵌库族（DuckDB / DataFusion）
│      前置判据见下：最大一份 join 的构建侧放得下吗
├─ 数据散在多个源、不能被搬动，需要统一入口
│    → 集群 MPP 族（Trino / PrestoDB）
│      先验证下推率，再决定要不要保留这个入口
├─ 传统 Hadoop / CDH 存量，数据与计算同址是既成事实
│    → Impala（或同族的 Trino + Hive 连接器）
│      换引擎的收益要能覆盖整个栈的升级约束
├─ 已经有 Spark 生态、查询多为长时批量
│    → Spark SQL，不必新引入引擎
│      但交互式查询别塞进它：为容错付的物化开销是纯亏
├─ 查询模式固定、并发高（数百 QPS 级）
│    → 不用上述任何一类：物化到 OLAP 引擎
│      联邦引擎的单位成本是按"探索式查询"设计的
├─ 引擎要嵌进 Rust / Python 服务、需要零拷贝对接 Arrow
│    → DataFusion（内嵌库族）
│      代价：没有集群、没有统一治理面
├─ 源端数据库自己就能算，且不希望数据外流
│    → 数据虚拟化中间件
│      代价：源库负载可能被查询挤占
└─ 需要跨源 join 的源超过 3 个、且查询频繁
     → 先考虑把数据落到一份带统计信息的表，再查
       （每多一个跨源 join 就多一次网络交换与一次不确定性）
```

**阈值依据**：

- **「最大一份 join 的构建侧放得下吗」**：这是内嵌族可用性的唯一硬判据，因为它由 hash 连接必须物化构建侧这一机制直接导出，与总数据量无关。**工程近似：构建侧数据量应显著小于可用内存，超出部分要能落到本地盘**——多数实践把「构建侧 ≤ 可用内存」当作首选区间，把「构建侧 ≤ 内存的 2–5 倍量级 + 本地盘」当作可接受区间【经验】。超过这个区间不是变慢，是失败。
- **「跨源 join 的源超过 3 个」**：由下推率的机制推出。每多一个源就多一次「能否下推 / 是否要拉全量」的不确定性。**2–3 个源时，两条路的开销通常还在同一量级**：一侧是联邦引擎的常驻成本（**$70k/年** 量级【推算】，见 7.4，约相当于一个人年的全成本【经验】），另一侧是维护这几条 ETL 管道的人力（开发 + 调度 + 监控 + 值班）——2–3 个源两两同步就是 1–3 条管道（条数按 n(n−1)/2 直接算出，不是估计），经验上落在 **0.5–1.5 人年**区间【经验】。两侧的具体数值都随工资水平与管道复杂度浮动，所以这里只做量级对比，不做精算。源继续增加时，ETL 管道的数量按组合增长（n 个源两两同步就是 n(n−1)/2 条管道），而引擎的常驻成本不变——**这才是「源多之后联邦引擎变划算」的真实原因：不是引擎变快了，是 ETL 的复杂度按平方增长**。
- **「数百 QPS 级」**：由并发形态判据推出。集群 MPP 引擎的每个查询都要占用一定的工作节点内存与 CPU，**并发 × 单查询资源就是集群容量的下限**。这条线只能给到量级，因为单查询的工作集是经验量：以 7.4 的 20 台 8C16G 为例，留一半内存给查询约 160 GiB，按单查询工作集 0.2–1 GiB 估，可同时在跑的查询约 160–800 个；查询若在 1–2 秒内返回，对应约 **80–800 QPS**【经验】——**「数百 QPS」正落在这一段的中上部，已经是集群 MPP 引擎的上沿而不是舒适区**：它是「该换形态」的信号而不是「该加节点」的信号，因为固定查询模式下把结果**物化一次**的成本远低于每次查询都重算一遍。这条线随单查询资源占用浮动，请用自己集群的并发实测曲线把它定位到自己的数字上，不要照搬这个量级。
- **「数据不能被搬动」**：不是技术阈值而是合规与成本的约束——当数据出域需要审批、或外流成本按流量计价时，「不搬数据」从优化目标变成硬约束，此时联邦引擎的常驻成本是必须付的【经验】。
- **「使用者是个人或单个服务」与「多人共享入口」的分界**：就是决策树第一行「谁要用」这个节点。它不是技术阈值，而是由**常驻成本的摊薄方式**推出：集群族的 $70k/年量级（见 7.4）是一条与使用人数无关的固定项，必须由共享入口的实际使用人数摊平。**十人量级以内、且尚无共享入口的团队，内嵌族的增量成本近似为 0；使用人数升到数十人量级后，内嵌族缺失的统一治理面转为真实人力成本，天平反转**【经验】。判据是「过去一个月有多少人真的查过数据」，而不是名义团队人数——这条线随人均查询频次浮动，请按自己的实测曲线定位。

**四个不含数值阈值的分支，依据来自约束而不是阈值**：传统 Hadoop / CDH 存量、已有 Spark 生态、引擎要嵌进 Rust / Python 服务、源端数据库自己就能算且数据不能外流——这四条之所以不给数字，是因为触发条件是硬约束，成立时根本没有可比较的替代项：**数据与计算同址是既成事实**，换引擎要脱离整个存量栈的升级节奏（成本见 7.7 的迁移表）；**已有 Spark 生态**时，复用现有栈的收益大于新引入一个引擎，且边界物化对长时批作业划算（机制见 7.3.3）；**要把引擎嵌进宿主进程**时，集群族在结构上做不到（机制见 7.3.1）；**源端能算且数据不能外流**时，「不搬数据」是合规硬约束（见 7.4）。判据是：**这四条的门槛是「能不能」，不是「多少」**——约束成立时无需阈值，约束不成立时再回到上面那几条数值阈值。

**把决策树展开成执行顺序**（同一棵树，按时间轴读）：

1. **第 0 步 · 先量三件事**：最重查询的下推率（源端挡下的行数占源端全量行数的比例，口径见 7.3.2 的自验方法）、最大一份 join 的构建侧数据量、查询的并发形态（探索式还是固定报表）。这三项分别决定判据 2、判据 1、判据 5。
2. **第 1 阶段 · 只动元数据**：补分区、补统计信息、把常用过滤列做成分区或排序键。这一步不改引擎、不改 SQL，却常常是下推率提升幅度最大的一步——因为优化器的输入就是这些统计信息。
3. **第 2 阶段 · 再动查询写法**：先聚合后连接、只读需要的列、把不可下推的过滤改写成可下推的形式。验收标准是同一个 `EXPLAIN` 里源端扫描节点的输入行数下降。
4. **第 3 阶段 · 最后才动引擎形态**：换引擎、换内嵌/集群形态、换连接器。这一步会同时改变权限模型、审计路径与运维方式，是唯一不可快速回滚的一步。
5. **持续 · 把两项指标写进看板**：下推率、以及「常驻集群的利用率峰值」。缺了后者，「我们是不是养了一套用不上的集群」这个问题永远不会被回答。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 跨源即席分析、数据不能搬 | Trino | PrestoDB | 选内嵌引擎：数据搬不动，单机放不下 |
| 传统 Hadoop / CDH 存量 | Impala | Trino + Hive 连接器 | 强行换引擎：升级约束在整个栈上，不在引擎上 |
| Notebook / 本地分析 | DuckDB | DataFusion | 上集群引擎：为一次性分析养一套常驻节点 |
| 服务内嵌 SQL、Rust / Python | DataFusion | DuckDB | 用集群引擎：跨进程调用与序列化成为主要开销 |
| 已有 Spark 生态的长时批查询 | Spark SQL | Trino | 新引入联邦引擎：收益不抵生态割裂 |
| 高并发固定报表 | OLAP 引擎（StarRocks / Doris 一类） | 预计算 + 缓存 | 用联邦引擎：每次全量重算，常驻成本随并发线性变紧 |
| 源端能算、数据不能外流 | 数据虚拟化中间件 | Trino + 受限连接器 | 用自建 ETL：外流本身就违反约束 |
| AI Agent 的统一取数入口 | Trino（统一 SQL 出口） | 内嵌引擎 + 元数据层 | 直连各源：Agent 要面对多套方言与多套权限 |

每条说明职责边界与运维代价：

1. **Trino + Iceberg + OLAP 引擎（StarRocks / Doris 一类）**：Trino 负责跨源探索与表格式上的即席查询，OLAP 引擎负责高频固定聚合。边界是**探索归 Trino、固化归 OLAP**。运维代价：多一条「湖 → OLAP」的同步链路，它是新的口径分叉点，必须明确哪一端是权威。
2. **Trino + DataFusion**：Trino 做跨源联邦与统一入口，DataFusion 嵌进具体的服务或 Python 进程做局部计算。边界是**跨源归 Trino、单进程内归 DataFusion**。运维代价：同一份逻辑可能被写在两处（SQL 与宿主代码），需要明确哪一侧是唯一实现——否则又回到「两份实现」的老问题。
3. **Trino + AI Agent**：Trino 提供统一查询接口，Agent 通过 SQL 访问所有数据。边界是**Trino 负责可查询性与权限，Agent 负责选表与生成 SQL**。运维代价：Agent 生成的查询是**未知负载**，必须配资源组与查询上限，否则一条失控的生成查询会占满整个集群——这是这套组合里最常见的事故形态。
4. **内嵌引擎 + 元数据层（补）**：内嵌引擎负责执行，元数据层（表格式 + 目录）负责「有哪些表、口径是什么、谁能读」。边界是**执行与治理分离**。运维代价：权限与审计要在元数据层与宿主应用两处实现，容易只做一处。
5. **联邦引擎 + 物化层（补）**：联邦引擎负责探索，物化层把高频查询的固定结果持久化。边界是**探索用联邦、复用用物化**。运维代价：物化结果的刷新策略本身是一条需要有人负责的链路，刷新失败时下游看到的是过期数据而不是错误。

**组合的共同原则**：每个组合都要能回答「哪一件负责可查询性、哪一件负责性能、哪一件负责权限」。**因为**联邦引擎把权限摊到了每个连接器上，**所以**任何组合里都必须有一个**集中的授权与审计点**——它通常是元数据层而不是引擎本身，这一点在 AI 取数场景里尤其关键：Agent 会访问你没预料到的表，而这个组合里唯一能拦住它的地方就是那个集中授权点。

**组合里最容易出错的四处边界**（与具体产品无关，来自结构性冲突）：

- **权威端不清**：湖 → OLAP 的同步链路一旦变成双向，就重新出现了「两份实现」，口径分叉只是时间问题。
- **未知负载缺上限**：Agent 或分析师的临时查询是不可预测的负载，没有资源组与查询上限时，一条失控查询就能占满整个集群。
- **治理面缺位**：内嵌引擎嵌进服务后，权限与审计要在元数据层与宿主应用两处实现，实践中通常只做了一处。
- **刷新链路无人认领**：物化结果的刷新策略是一条独立链路，刷新失败时下游看到的是**过期数据而不是错误**——这类失败最不容易被发现。

### 7.7 选错的代价与迁移成本

**反模式：把联邦引擎当 OLAP 引擎用** —— 把一份固定口径的日报改成每次从湖上现算，并发一上来集群被打满，团队开始扩节点；扩到一定规模后发现「加节点也不能让这条查询更快」→ 因为集群 MPP 引擎的每次查询都要重新扫描与计算，而固定查询模式下这些计算**本来只需算一次**；加节点解决的是并发能力，解决不了「本来就不该重算」这个结构问题 → **正确做法**：把固定口径的聚合物化到 OLAP 引擎或预计算层，联邦引擎只留给探索式查询。

**反模式：在统计信息缺失的数据源上指望基于代价的优化器** —— 换了更强的引擎，查询计划却依然是把大表全量拉过来连接，团队开始怀疑引擎选错了 → 因为优化器的输入是统计信息，**没有行数、没有分区分桶信息时，代价模型无从估计，优化器只能给出保守计划**，此时引擎内核再强也用不上 → **正确做法**：先补元数据（分区、列级统计、排序键），再用 `EXPLAIN` 验证计划变化；把「补统计信息」当成一次独立的上线动作，而不是引擎迁移的附带事项。

**反模式：把内嵌引擎当共享数仓用** —— 小规模试用效果极好，于是推广给全组多人并发使用，随后出现「偶发查询失败」「内存打满」「同一份数据每人存一份」→ 因为内嵌引擎的形态前提是**单进程、单用户、数据在本地**，它没有资源隔离与并发调度这两层（不是实现不好，而是它的形态里不包含这两层）→ **正确做法**：内嵌引擎用于个人分析与服务内嵌；多人共享必须走集群引擎或 OLAP 引擎，并把数据放在共享存储上而不是各自的本地目录。

**反模式：用引擎选型解决治理问题** —— 因为「权限管不住、审计查不到」，决定换一个更"现代"的查询引擎，迁移完成后权限仍然管不住 → 因为权限与审计的落点在**元数据与连接器层**，不在执行引擎内核；换引擎换掉的是执行路径，不是授权点 → **正确做法**：先把授权与审计收敛到一个集中层（元数据/目录），再考虑引擎；否则迁移会同时失去旧系统里已有的那部分审计记录。

**换成另一条路线要动什么**：

| 迁移方向 | 数据迁移 | SQL / 连接器改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| Trino ↔ PrestoDB | 无 | 小（方言接近） | 小（架构同族） | 差异点核对 | 1–2 人月 |
| 集群引擎 → 内嵌引擎 | 中：数据要能落到单机可读的格式 | 中：方言差异 + 单机限制下的写法调整 | 大：失去统一治理面，权限审计要另建 | 单机执行模型与限制 | 3–6 人月 |
| 内嵌引擎 → 集群引擎 | 中：本地文件要纳入共享存储 | 中：方言差异 | 中：新建集群 + 权限体系 | 分布式执行、资源组 | 2–5 人月 |
| 自建 ETL → 联邦引擎 | 无（数据不动） | 大：管道逻辑改写为 SQL | 中：新增引擎集群与连接器 | 下推、`EXPLAIN` 读计划 | 6–12 人月 |
| 联邦引擎 → 物化 + OLAP | 中：物化一份结果集 | 大：查询要按物化粒度改写 | 中：新增刷新链路 | 物化粒度与刷新策略 | 3–9 人月 |
| Impala / CDH 存量 → Trino | 无 | 中：方言与 Hive 特性差异 | 大：脱离整个存量栈的升级节奏 | 连接器与下推模型 | 6–18 人月 |

> 量级按「一个熟悉本系统的 3–5 人小组」估算【经验】。**最贵的两条迁移都有一个共同点：它们要脱离一个既成的技术栈**（CDH 的升级节奏、或各源的方言与权限体系）——代价不在引擎本身，在于**引擎是那个栈的入口**，换入口等于重排整条链路。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 单机数据、个人或单服务使用 | 内嵌引擎 | 进程边界为 0，无网络与序列化开销，且无常驻成本 |
| 数据散在多源、不能搬动 | 集群 MPP 引擎 | 只有它提供跨源统一入口；代价是需要常驻集群 |
| 传统 Hadoop 存量 | 数据与计算同址的引擎 | 扫描尽量本地完成，避免为搬数据付两次代价 |
| 已有 Spark 生态、长时批查询 | Spark SQL | 边界物化换来的容错，对长时作业是划算的 |
| 高并发固定报表 | 物化到 OLAP 引擎 | 联邦引擎按探索式查询设计，重算是结构性的浪费 |
| 查询慢但引擎没换 | 先补分区与统计信息 | 优化器的输入是统计信息，缺了它，内核强弱用不上 |
| 接了一个新数据源后变慢 | 先查该连接器的下推能力 | 联邦查询的成本主体是「被拉进来的数据量」 |
| 需要 AI Agent 统一取数 | 引擎之上加集中授权点 | Agent 会访问你没预料到的表，授权点必须在元数据层 |
| 团队在十人量级以内、还没有共享入口 | 先内嵌，别急着上集群 | 常驻集群的 $70k/年量级（【推算】，见 7.4）是与使用人数无关的固定项：共享入口的收益要由实际使用人数摊平，人数不足时摊不平【经验】 |
| 任何引擎迁移之前 | 先用 `EXPLAIN` 量一次下推率 | 迁移解决不了的，多半是元数据问题而不是引擎问题 |

> 本节小结：本节所比的四族候选之间**唯一真正起决定作用的差异**是——**引擎在谁的进程里执行，以及数据在哪一侧被算**。进程边界决定了常驻成本、横向扩展能力与治理面的有无；下推边界决定了跨源查询的单位成本上限。其余所有维度（联邦能力、性能、内嵌能力、AI 友好、易用性）都是这两条的**表现形式**：所谓「联邦查询能力」就是「有多少种连接器能下推」，所谓「性能」在跨源场景里就是「下推率」，所谓「内嵌能力」在需要统一治理的组织里则是一张减分项。选型的正确顺序是：**先量下推率（是不是引擎的问题）→ 再补统计信息（是不是元数据的问题）→ 最后才动引擎形态（这一步不可快回滚）**。
>
> 💡 **思考锚点**：挑你最近抱怨「慢」的那条跨源查询，按 §7.3.2 的自验方法记两个数——源端全量行数、连接器实际回传引擎的行数，被源端挡下的比例落在 1/10 以上还是以下？若已低于 1/10 量级，按本节的顺序你下一步该补分区与统计信息，还是该动引擎形态？
