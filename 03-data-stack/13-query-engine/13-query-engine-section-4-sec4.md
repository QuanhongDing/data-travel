## 4. 工程实现

本节按「落地步骤 → 关键技术点 → 工具链 → 存量迁移 → 模板 → 自检」组织。术语定义分两处：**Connector**、**Coordinator / Worker**、**Stage / Task / Driver**、**Exchange**、**CBO**、**谓词下推**、**列剪裁** 沿用主文件 [§ 2.1 关键概念定义](13-query-engine.md)；**统计信息**、**分区剪裁**、**快照**、**溢写**、**资源组** 沿用 [§ 3](13-query-engine-section-3-sec3.md) 的口径，依次见 §3.4 组合二与 §3.5、§3.2.2 与 §3.2.3、§3.2.2、§3.2.1 与 §3.2.4、§3.1 约束表与 §3.5。本节沿用这两处的口径，不另立定义。

读者分两类，本节都覆盖。**从零搭建**的团队按 4.1 的六步往下走，4.4 可略读；**在存量上改造**的团队（已经有 Presto / Impala / Hive 集群、有一批跑在旧引擎上的报表与作业）建议先读 4.4 再回到 4.1——存量改造最贵的不是把新集群装上，而是让已经在跑的查询在新引擎上跑出同样的数、同样的延迟。

### 4.1 落地步骤（六步，顺序不能换）

**Step 1：先定进程边界与计算位置，再定引擎（1-2 周【经验，随待接入源数量与合规评审层级变】）**

1. 回答三个问题并写下来：数据能不能搬（合规 / 体量）、**源端能不能下推**（能否过滤与分批）、查询形态是即席跨源还是固定高频（§3.1 的约束表）。
2. 按答案选族：跨源联邦取 Trino 一类；计算发生在应用进程内取 DataFusion / DuckDB 一类内嵌引擎；已有 CDH / CDP 栈且要行级更新的取 Impala + Kudu 一类。
3. 同时定下**边界**：这套引擎不做哪类查询（高频固定报表下沉到 OLAP 层，不与联邦层混跑）。

- **产物**：一页选型结论，含上述三问的答案、选定引擎、以及明确写出的「不承担哪类负载」。
- **判据**：拿这页纸去问一个已知的高频报表，看它是否落在「不承担」那一栏；若答不上来，说明边界没定，第 5 步的资源隔离将无从设计。再核对一次：源端是否真的支持过滤（不能只看引擎文档，要看那个 Connector 在你的源上实际下推了什么）。
- **为什么必须第一步**：进程边界（服务化还是内嵌）一旦定错，后面所有工作都建立在错误的前提上——内嵌引擎没有资源隔离与多租户，为它设计的权限与监控全部要重做；反之，把本地小数据送上集群，付的是序列化与排队的固定成本（§3.2.4）。

**Step 2：装出最小可跑集群（Coordinator / Worker + 高可用）（2-4 周【经验，随是否要上高可用与 Worker 规模变】）**

1. 先单 Coordinator + 少量 Worker 跑通一条查询，再谈多机与高可用（模板 1）。
2. Coordinator 承担解析、规划与调度，**它是规划侧的单点**：高可用要么做多副本加路由，要么接受中断窗口并写清恢复步骤。
3. Worker 无状态，可水平扩；配置里先把 JVM 堆与查询内存上限、溢写目录定下来。
4. 把版本号钉死（镜像 tag 写具体版本，不写浮动标签），并记录升级方式。

- **产物**：一套可重启的集群 + 一份配置基线（版本号、堆大小、内存上限、溢写目录、并发上限）+ 一条能跑通的样例查询。
- **判据**：故意重启一个 Worker，看正在跑的查询是失败还是被重新调度——这决定了你对「容错执行」的实际预期；再执行一条会超内存的查询，看它是溢写落地还是直接失败（失败说明溢写没配，第 5 步的隔离要重排优先级）。
- **为什么必须排在 Connector 之前**：连接器调试需要用 `EXPLAIN` 反复看计划，而计划质量与内存、并发设置有关。配置基线没有，后面把「计划不对」与「资源不够」两种现象混在一起排查。

**Step 3：Connector 接入与下推验收（2-4 周【经验，随源类型数量与是否支持动态过滤变】）**

1. 按消费顺序接入：先接主数据源（Hive / Iceberg），再接关系库（MySQL 一类），最后接流式源（Kafka 一类）。
2. 每个 Catalog 单独一个 properties 文件（模板 2），凭证走密钥管理而不是明文；权限映射（谁在源端能读哪些库表）在接入时就定，不后补。
3. **逐个源做下推验收**：对同一张表跑一条带过滤与投影的查询，用 `EXPLAIN` 看源侧分片是否带上了过滤条件（§3.5「未优化 Connector」的判据）。
4. 把「每个 Connector 支持下推的算子清单」记进文档，而不是凭印象。

- **产物**：每个源的 properties 文件 + 权限映射表 + 一张「Connector × 支持下推算子」清单 + 每个源的 `EXPLAIN` 基准样例。
- **判据**：随机抽一个源，用 `EXPLAIN` 验证过滤与投影是否下推；抽不到下推条件的那个 Connector，在清单里标为「整表读」，并据此判断它能不能承接生产查询。
- **为什么必须排在统计信息之前**：统计信息与 CBO 都是在「下推已经生效」的前提下才有意义——如果每次都要把整表拉进引擎，优化器怎么选计划都改变不了传输量（§3.1 的机制）。

**Step 4：统计信息与 CBO（持续）**

1. 对关键表收集列级统计（`ANALYZE TABLE`），或在写入侧随数据一起产出统计（把新鲜度交给写入路径）。
2. 用 `EXPLAIN` 核对基数估计与实际的差距，重点看 Join 分发方式（广播还是分区）。
3. 慢查询治理：按扫描量与耗时列出 Top 查询，逐条判断是「下推不足」「统计不准」还是「查询本身该下沉」。
4. 给统计新鲜度定一个可观测指标（最后收集时间），否则统计过期是静默的。

- **产物**：统计收集作业（或统计随写的写入链路）+ 慢查询清单 + 每条慢查询的归因结论。
- **判据**：抽 3 张关键表，看它们最近一次统计收集时间；从未收集的表，其 Join 计划按默认基数估算，遇到大表 Join 大表时工作节点内存会被打满（§3.5）。再对一条历史慢查询做 `EXPLAIN`，确认改动后计划是否真的变了——只看耗时变短不算证据。
- **为什么必须排在资源隔离之前**：计划层面的错误（广播了大表）会以「内存打满」的形式暴露，若没有先排除计划问题，就会把资源不足当成根因去加机器。

**Step 5：资源隔离、监控与调优（持续）**

1. 按负载分组：交互查询与大批任务分属不同资源组或不同集群，单条查询设内存上限与超时。
2. 监控三件：集群层（队列、内存、Worker 存活）、查询层（P99、扫描量、失败率）、源端（每次查询搬了多少数据）。
3. 用 Trino Web UI 看单查询的 Stage 与 Task 分布，用 Prometheus + Grafana 看趋势与告警。
4. 为大查询开溢写与容错执行，并确认溢写盘的空间与 IO 不是新瓶颈。

- **产物**：资源组与配额配置 + 三层指标的看板与告警阈值 + 溢写盘容量规划。
- **判据**：构造一条会占满内存的查询，看交互查询的 P99 是否被它拖垮（被拖垮即隔离没有生效）；再看这条查询是被杀掉、被排队，还是被允许跑完——三种处置要在配置里是显式选择的。
- **为什么必须排在 AI 集成之前**：AI 生成的查询与人的查询走同一条执行路径，会绕过人的谨慎（§5 的自然语言查询一节）。在没有配额与超时的集群上接入生成式入口，等于把「不可预测的查询量」直接接到共享内存上。

**Step 6：AI 集成（按需）**

1. 先接的是**读路径**：自然语言 → SQL 的生成接口，把生成的 SQL 交回同一套执行与权限体系，不做旁路。
2. 再接**诊断路径**：把 `EXPLAIN` 结果与慢查询归因作为输入，让助手给改写建议（建议由人确认后执行）。
3. 生成入口必须带元数据上下文（表、列、口径、粒度、权限），并记录「这条 SQL 由谁生成、依据哪一版元数据」。
4. 配额与审计与人工查询一视同仁。

- **产物**：生成入口 + 元数据上下文接口 + 查询审计记录（含生成来源）+ 生成 SQL 的抽检机制。
- **判据**：抽 20 条生成 SQL，人工核对口径与权限边界，统计**跑得通但口径错误**的比例——这个比例是这一步唯一有意义的验收指标，而不是「生成成功率」。达不到要求就缩小可生成范围（先只放开已登记口径的度量）。
- **为什么排在最后**：这一步复用前五步的全部产出（连接器与权限、统计与元数据、配额与监控）。前面缺哪一块，生成式入口就会把哪一块的缺口放大：没有元数据时它猜表名，没有配额时它把集群打满。

**最常被跳过的是 Step 3 的下推验收**：接入的连接器「能查到数」就算通过，是这类项目里最普遍的做法，因为下推不足不会报错，只是慢。跳过之后**第一个出问题的时点通常不是上线当天，而是源表增长到远超测试规模之后**——表现是某条跨源查询的时间随源表线性上涨，团队先怀疑引擎参数、加 Worker、调并发，往往要 1-2 周【经验，随排查路径与集群规模变】才在 `EXPLAIN` 里看到源侧分片一直是「整表读」。此时排查成本已经花掉，而修法只是补一个下推实现。

### 4.2 关键技术点

**1. Connector 配置即能力声明**

- **做法**：每个数据源一个 Catalog properties 文件（`connector.name` 与各连接参数），凭证走密钥管理；把「这个 Connector 支持下推哪些算子」写进文档。
- **机制**：因为「能下推多少」由 Connector 声明并实现，而不是由引擎决定，所以同一个引擎在两个源上的表现可以差出量级（§3.1）；代价是每个源的接入都是一次实现与验证，不是一次配置。
- **失效条件**：**当一个源只被接入、从未做过 `EXPLAIN` 验收时，这条失效**。症状是跨源查询慢，而 `EXPLAIN` 里源侧分片没有过滤条件；可观测信号是「查询耗时」与「源表行数」同步上涨。
- **档位**：【经验】。

**2. 下推与剪裁的验收方式**

- **做法**：固定用 `EXPLAIN (FORMAT JSON)` 而非 `EXPLAIN`（前者给基数与分发方式）；对每个源留一份基准样例，回归时比对。
- **机制**：因为下推失效是**静默的**——查询照样返回正确结果，只是多搬了数据——只有把「计划长什么样」变成可回归的产物，它才会在版本升级或配置变更时被发现。
- **失效条件**：**当源端只支持整表读（源端无计算能力）或数据在对象存储上没有可剪裁的元数据时，这条失效**。症状是剪裁率接近 0；此时正确的动作不是继续调引擎，而是把计算推得更深（源侧就地算）或提前物化（§3.3 的两条分支）。
- **档位**：【经验】。

**3. Iceberg 一类的元数据剪裁与快照一致性**

- **做法**：从元数据表（如 `orders$files`、`orders$partitions` 一类）核对文件数与分区统计；写入侧配置目标文件大小与分布模式，并配 compaction 与快照过期作业。
- **机制**：因为剪裁所需信息全在元数据里、且元数据整体代表某一个快照，所以查询既能跳过大量文件、又不会读到「一半旧快照一半新快照」的中间态（§3.2.2）；代价是写入侧要维护 manifest 与快照，文件布局直接决定读性能。
- **失效条件**：**当写入持续产生小文件、或统计不可用（半结构化 / 深层嵌套列拿不到 min/max）时，这条失效**。症状是剪裁退化成按顺序打开全部文件，慢在规划而不是执行；可观测信号是平均文件大小持续下降、查询的规划耗时占比上升。
- **档位**：属性名与元数据表命名【公开，可按所用引擎与表格式版本的官方文档核验】。

**4. 关系库 Connector 与动态过滤**

- **做法**：JDBC 类连接器显式设连接数与队列上限；确认过滤与投影下推到关系库；对两表关联，确认引擎是否用一侧的结果集把过滤下发给另一侧（动态过滤）。
- **机制**：因为关系库的算力与连接数是**有限的共享资源**，联邦查询在它上面的代价不只由数据量决定，还由并发占用决定；把连接池与下推同时管住，才不会出现「一条跨源查询拖慢在线业务库」。
- **失效条件**：**当源库同时承载在线业务、而联邦查询没有单独账号与配额时，这条失效**。症状是业务侧出现与查询任务时间吻合的抖动；可观测信号是源库连接数在批任务时段触顶。此时应给联邦查询单独的只读账号与连接上限，必要时改读从库。
- **档位**：【经验】。

**5. 统计信息与 CBO**

- **做法**：关键表收集列级统计并在写入侧随数据产出（让新鲜度跟上数据变化）；用 `EXPLAIN (FORMAT JSON)` 核对基数估计，必要时显式指定 Join 分发方式。
- **机制**：因为 CBO 的全部依据是统计信息，统计缺失时基数估计退回默认值，优化器会把大表当小表广播，单点内存成为天花板（§3.5「Join 顺序差」）；所以统计的新鲜度是计划质量的上限。
- **失效条件**：**当表由外部系统持续写入、而统计只在迁移时收集过一次时，这条失效**。症状是同一 SQL 在不同时间给出差别很大的耗时；可观测信号是「最后统计时间」与「最近写入时间」的间隔持续拉大。
- **档位**：【经验】。

**6. 资源隔离与查询上限**

- **做法**：按负载分资源组或分集群；单查询设内存上限与超时；开启溢写与分片重试。
- **机制**：因为 Worker 的内存与队列是共享资源，一条不设上限的查询会把它们占满，**故障半径等于整个集群**（§3.5）；隔离开销低于事故开销，是这项配置的全部理由。
- **失效条件**：**当资源组按提交人而不是按负载类型划分时，这条失效**。症状是同一类查询在不同组里行为不一致，长任务仍能找到一条不打配额的路；可观测信号是「大批任务时段交互查询 P99 抬升」反复出现。
- **档位**：【经验】。

**7. 内嵌引擎的进程边界**

- **做法**：内嵌引擎（DataFusion 一类）只处理已在本地、且能装进单机内存的数据；超出部分提交给服务化引擎；两边的 SQL 语义（时间、类型、NULL）做一次一致性验证。
- **机制**：因为内嵌省掉的是「两次序列化 + 网络 + 排队」这段固定成本，省不掉扫描计算（§3.2.4），所以数据量不大时它更快，一旦扫描成为主体，它没有并行度可加。
- **失效条件**：**当数据量超过单机内存 / 磁盘，或需要多用户并发共享时，这条失效**。症状是本进程内存触顶、查询被拆成多段；此时唯一的出路是外挂集群，而那意味着你要的其实是服务化引擎。
- **档位**：【经验】。

**8. AI 集成的落点**

- **做法**：生成式入口只做「自然语言 → SQL 草稿」与「计划诊断建议」，执行、权限、配额全部复用既有体系；每条生成 SQL 记录来源与所用元数据版本。
- **机制**：因为查询引擎是**执行者**而不是语义定义者，AI 在这里改变的是 SQL 的编写者，不是执行者（§5.2.1）；把它接成执行链路上的一等调用方，才不会绕过权限与配额。
- **失效条件**：**当元数据（表、列、口径、粒度、权限）不完备时，这条失效**。症状是生成 SQL「跑得通但口径错」，错误在结果被使用后才暴露；可观测信号是生成 SQL 的抽检错误率不降反升——此时应缩小可生成范围，而不是继续放宽。
- **档位**：【经验】。

### 4.3 工具链与平台

工具表给的是**类别与选型判据**，不是推荐组合。产品是否仍以表中的能力在售、以及属性与参数名，以厂商官方文档与 release note 的当前版本为准。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 联邦 / 服务化查询引擎 | Trino、PrestoDB、Apache Impala、Spark SQL | 源端能否下推、查询是即席跨源还是固定高频；分叉后的插件 SPI 各自演进，**选一次就锁定了后续 Connector 的维护方向** | 选错一支后，为另一边写的 Connector 与经验不能迁移，重写成本落在接入阶段 |
| 内嵌查询引擎 | Apache DataFusion（Rust）、DuckDB | 计算是否发生在应用进程内、数据是否已在本地、有无多用户共享与 SLA 要求 | 拿内嵌引擎当服务化引擎用，并发与共享需求一来就得换架构，前面的集成代码全部作废 |
| 优化器 / 查询框架 | Apache Calcite | 是否自研引擎、是否需要一套可扩展的 SQL 解析与优化底座 | 自研解析与优化器意味着长期维护一套规则体系，成本通常被严重低估 |
| 表格式与元数据服务 | Iceberg、Hudi、Paimon；Hive Metastore 一类 catalog | 有几个引擎要读同一张表；写入是追加还是更新；**Metastore 的列举能力决定了分区规模上限** | 历史资产零迁移的前提是保留 Metastore；换 catalog 要评估写入链路的改造面 |
| 搜索源与键值源 | Elasticsearch、Redis | 查询要不要把全文检索或按主键点查的结果与湖仓表拼进同一条 SQL；这两类源的下推是按查询形态实现的（检索条件、键取值），不是通用算子下推 | 不在源侧过滤就等于放弃索引换来的优势：网络里传的是过滤前的结果集，点查退化回扫描 |
| OLAP 加速层 | StarRocks、Doris、ClickHouse | 是否存在被按分钟调度的固定查询模式；聚合是否集中在少数宽表上 | 不加速就会让同一份明细被反复跨源搬运，集群利用率高而 P99 持续抖动 |
| 客户端与 BI | Apache Superset、Grafana、Metabase | 是否能只用 SQL 接入、语义口径能否与指标平台共用一份定义 | 看板各建一份计算逻辑，会形成不可审计的第二口径 |
| 监控与可观测 | Prometheus + Grafana（引擎自带的查询 Web UI 作为单查询视图） | 指标是否覆盖三层（集群 / 查询 / 源端搬运量），而不只是引擎自身的健康度 | 只看引擎可用性，会漏掉「查询变慢但没报错」这一整类问题 |
| 资源与调度 | 资源组 / 独立集群、Kubernetes 上的 Worker 弹性 | 交互与批是否分池；扩缩容是否按队列深度而不是 CPU 使用率 | 共享内存与队列时，故障半径等于整个集群 |

**这一类里最容易被误选的是「内嵌查询引擎」。** 它常被当成「轻量版联邦引擎」引入，判据却是进程边界：内嵌引擎没有资源组、没有多租户、没有溢写之外的内存兜底。误选的典型后果是先用它跑通一个原型，接入两三个系统后并发与共享需求出现，此时唯一的出路是外挂一个集群——而原型阶段写的那些「直接读本地文件」的路径、以及与宿主语言零拷贝绑定的代码，都要重新验证一遍。

### 4.4 存量迁移

存量迁移的目标不是「把旧引擎换掉」，而是**让已经在跑的查询在新引擎上跑出同样的数与可解释的延迟**。下面四步按「可回退 → 分类 → 双轨 → 收口」排，最后一组是这一步最常见的三个错误。

**① 先做一次只读盘点（2-3 周【经验，随查询日志覆盖范围与源表数量变】，完全可回退）**

不动任何集群，用现有查询日志与 `EXPLAIN` 采样跑四张清单：**Top 查询按扫描量与耗时排序**、每条慢查询的源侧分片是否下推、源表的规模与分区数（分区数是否已到 Metastore 列举变慢的量级）、BI 与应用的直连清单（谁在读哪一层）。这一步不迁移任何东西，只产出**一次事实基线**；它可回退，因为结论只是设计输入，不进任何配置。

**判据**：拿「未下推的查询」这份清单去问两位互不相干的负责人「哪一条迁移风险最高」，两人指向同一条，说明证据已足够支撑决策；给出不同答案，说明归因还没做（分不清是下推问题还是统计问题），先回到 Step 3 / Step 4。

**② 存量资产分类处理（不要全部重写）**

| 存量资产 | 处置 | 理由 |
| --- | --- | --- |
| 跑在旧引擎上的**交互式即席查询** | 优先迁移，逐条做 `EXPLAIN` 对照，留基准样例 | 这类查询收益最直接（省掉搬运），且数量可控 |
| **高频固定报表** | 不迁到联邦层，直接下沉到 OLAP 层或物化视图 | 联邦层每次重扫重算，搬运成本被重复支付（§3.3 的误选）；迁移只会把问题换个地方 |
| 已有 Hive 表与 Metastore | 保留，连接器直接读，不做格式重写 | 零迁移即可剪裁（§3.2.3）；重写 PB 级数据的窗口与成本通常不可接受 |
| 自研 / 私有的数据源 | 评估写 Connector 还是继续走 ETL 链路：只有一个系统用、且能用只读接口的，才值得写 | Connector 的四个扩展点（元数据、分片、读路径、句柄）要自己实现并长期维护；下推不写就等于把整表拉进引擎 |
| 旧引擎的参数与调优经验 | 不回搬，作为**对照组**：同一 SQL 在两个引擎上跑一次，解释差异来自哪里 | 把旧引擎的参数照搬到新引擎，多数不适用，且会掩盖真正的瓶颈 |

**判据**：随机抽 3 条已迁移的查询，与旧引擎的基线（耗时、扫描量、结果行数）对照——若结果不一致，先查语义差异（时间函数、NULL、类型转换），不要先调性能。

**③ 双轨怎么维持、维持多久**

双轨的形态是**按查询类型分线，而不是两套引擎并行跑同一批查询**：新提交的即席跨源查询走新引擎，固定报表按计划下沉到加速层，旧引擎在迁移窗口内保留但只接受存量查询的白名单。维持 **1-2 个季度**【经验，随报表数量与发布节奏变】。

双轨期有三条纪律：同一条查询只在一个引擎上跑（避免两套结果不一致时无法判断谁对）；两套环境的数据快照时间必须写进结果说明；新引擎上的查询计划要留档，收口时用它解释性能差异。这三条把双轨的成本限在「解释」上，而不让它渗进结果。

**④ 什么信号说明可以退出双轨**

三个可观测信号，同时出现两个即可收口：① 白名单里的存量查询在一个周期内没有新增（说明没人再往旧引擎写新查询）；② 新引擎上的慢查询清单里，「未下推」与「统计缺失」两类都已归零；③ 抽 10 条同时在两边跑过的查询，结果完全一致——这一条最难满足，也最能说明语义差异已经处理完。

若经过两个季度三个信号全不成立，正确的动作是**缩小迁移范围**（只迁即席查询，固定报表直接下沉加速层），而不是继续维持双轨：双轨的隐性成本是同一份数在两处产生，且没有机制保证它们一致。

**⑤ 迁移期最常见的三个错误**

1. **把「统一入口」理解成「所有查询都迁过来」。** 联邦层的价值是跨源拼接与免搬运，高频固定查询要的是重复计算的最小化；判据是看同一条 SQL 是否被按分钟调度——是，它就不该由联邦层承担。
2. **只对结果、不对计划。** 迁移验收只看「数对不对」，不看 `EXPLAIN`：结果一致但计划退化的查询会带着一个隐藏的容量问题进入生产，通常要等到数据量再涨一轮才暴露。
3. **忘了把权限与配额一起迁。** 权限映射、资源组、单查询上限都是执行路径的一部分；只迁查询不迁配额，等于把旧集群上的隔离水位原样带到新集群，迁移后「大家一起慢」的问题会重现。

### 4.5 模板 / 示例

**模板 1：集群部署（Coordinator / Worker，先跑通再谈高可用）**

```yaml
# docker-compose.yml：最小可跑形态，生产上 Coordinator 与 Worker 分机部署
services:
  trino-coordinator:
    image: trinodb/trino:420          # 版本号钉死，不用浮动标签
    ports:
      - "8080:8080"                   # Web UI 与查询入口
    volumes:
      - ./etc:/etc/trino              # catalog 与配置目录
  trino-worker:
    image: trinodb/trino:420
    environment:
      - COORDINATOR_URL=http://trino-coordinator:8080
```

**怎么用**：这份只用来跑通链路，不能照抄上线。三处必须改：镜像 tag 换成你验证过的具体版本并记录在配置基线里；`/etc/trino` 下要放 `config.properties`（内存上限、溢写目录、并发上限）与 `jvm.config`（堆大小），这两项决定了第 5 步的资源隔离能不能生效；生产上 Coordinator 是规划侧单点，需要多副本加路由或写明中断窗口与恢复步骤，Worker 才适合按队列深度弹性扩。
除这三处，还有一处必须自己确认：片段里用环境变量区分 worker 角色，只是这份 compose 的写法；节点角色最终由 `config.properties` 决定（`discovery.uri` 与 `node-scheduler.include-coordinator` 一类配置项）。照抄前请对照你所用的镜像与版本，确认这个镜像从哪里读角色——读错了，两个容器会都按 Coordinator 启动。配置项名称与默认值以当前版本文档为准。

**模板 2：Connector 配置（能力就写在这里）**

```properties
# etc/catalog/iceberg.properties —— 湖上表格式
connector.name=iceberg
hive.metastore.uri=thrift://metastore:9083
iceberg.catalog.type=hive
warehouse=s3://lake/warehouse
```

```properties
# etc/catalog/mysql.properties —— 关系库（凭证走密钥管理，勿明文入库）
connector.name=mysql
connection-url=jdbc:mysql://mysql:3306
connection-user=${MYSQL_USER}
connection-password=${MYSQL_PASSWORD}
```

**怎么用**：两个文件的差别就是「源端能力」的差别——Iceberg 侧的性能取决于元数据剪裁与文件布局，MySQL 侧取决于过滤能否下推、以及连接数上限会不会拖累源库。落地时必做三件事：把凭证从明文换成环境变量或密钥服务；给关系库连接器单独设只读账号与连接上限（源库常同时承载在线业务）；对每个配好的 Catalog 跑一次模板 4 的 `EXPLAIN` 验收并把结果留档。连接参数名随版本演进，以当前版本文档的 Connector 属性表为准。

**模板 3：联邦查询（跨 Iceberg 与关系库）与流式查询**

```sql
-- 跨源关联：过滤条件下推后，网络里只传过滤后的结果集
SELECT o.order_id, o.amount, c.user_name, c.email
FROM iceberg.sales.orders o
JOIN mysql.crm.customers c ON o.user_id = c.id
WHERE o.dt BETWEEN DATE '2025-01-01' AND DATE '2025-01-31'
  AND c.vip_level = 'gold';
```

```sql
-- 流式源：按事件时间过滤后聚合；分区 / 位移等信息由连接器的隐藏列暴露，
-- 隐藏列命名随版本变化，落地前以当前版本 Kafka Connector 文档为准
SELECT user_id, COUNT(*) AS events, SUM(amount) AS total_amount
FROM kafka.events.orders_stream
WHERE order_time >= TIMESTAMP '2025-01-15 00:00:00'
GROUP BY user_id;
```

**怎么用**：模板 3 的价值是两条**判据**，不是两条 SQL。第一条：跑完立刻 `EXPLAIN`，看 Iceberg 侧分片是否带上了日期过滤、关系库侧是否收到过滤或动态过滤——没带，就是 §3.5 的「未优化 Connector」。第二条：流式查询要确认读的是「一次快照式的历史」还是「持续变化的分区集合」，这决定了同一条 SQL 隔一分钟跑会不会得到不同的数；这个语义必须写清楚，不能默认。

**模板 4：优化与诊断会话（先证明计划变了，再说变快了）**

```sql
-- 1) 收集统计信息：CBO 的全部依据
ANALYZE iceberg.orders;

-- 2) 让引擎自行决定 Join 分发方式（广播还是分区）
SET SESSION join_distribution_type = 'AUTOMATIC';

-- 3) 单查询超时：是兜底，不是优化开关
SET SESSION query_max_run_time = '10m';

-- 4) 核对计划：用 JSON 格式才能看到基数估计与分发方式
EXPLAIN (FORMAT JSON)
SELECT * FROM iceberg.orders WHERE user_id = 12345;
```

**怎么用**：把这四步当一次**回归**跑，而不是当调优技巧。第 1 步之后必须回看第 4 步的基数估计有没有变化——只看到耗时变短不算证据，因为缓存与数据分布都会影响耗时。第 3 步容易被误当成「自适应执行的开关」：它是超时兜底；联邦引擎上与运行时自适应对应的是「可用统计 + 动态过滤 + 运行时决定 Join 分发」这几项的逐条确认，而不是找一个叫 AQE 的开关（那类机制名属于 Spark 侧）。参数名与可取值以当前版本文档为准。

**模板 5：DataFusion 内嵌（计算在进程内，不经过网络）**

```python
import datafusion
import pyarrow as pa

ctx = datafusion.SessionContext()

orders = pa.table({
    "order_id": [1, 2, 3, 4],
    "user_id":  [100, 100, 200, 200],
    "amount":   [99.99, 199.99, 299.99, 399.99],
})
users = pa.table({
    "user_id":   [100, 200],
    "user_name": ["Alice", "Bob"],
})

# 具名注册：SQL 里 FROM 的表名，就是这里传入的字符串
ctx.register_record_batches("orders", [orders.to_batches()])
ctx.register_record_batches("users", [users.to_batches()])

result = ctx.sql("""
    SELECT u.user_name, SUM(o.amount) AS gmv
    FROM orders o
    JOIN users u ON o.user_id = u.user_id
    GROUP BY u.user_name
""").to_pandas()
```

**怎么用**：这段代码的边界比它的写法更重要——数据必须已经在本地（或能装进单机内存），算完之后结果也留在本进程，所以它省掉的是序列化与网络这一段固定成本，省不掉扫描计算。三处按你的场景替换：数据源换成读文件（`register_parquet` 一类）或先把 DataFrame 转成 Arrow 再注册，**注册这一步不能省**——只把对象交给返回 DataFrame 的读取入口、没有具名注册，SQL 里 `FROM orders` / `JOIN users` 这两个表名就解析不到；聚合前先把过滤做完，内嵌引擎没有源端可下推，读多少就算多少；一旦数据量超过单机内存或需要并发共享，正确的动作是把它提交给服务化引擎，而不是在这里分块硬跑。注册接口的名称与签名随版本演进，以当前版本官方文档为准。

### 4.6 自检清单

1. 随机抽一条跨源慢查询，`EXPLAIN` 里源侧分片是否带上了过滤条件？没带即「未优化 Connector」。
2. 每个 Catalog 是否有一份「支持下推算子」清单与一份 `EXPLAIN` 基准样例？两份都缺，下推处于未知状态。
3. 关键表最近一次统计收集是什么时候？比最近一次大批写入还早，CBO 一直在按默认值估。
4. 是否存在被按分钟调度的查询跑在联邦层？存在即应下沉到加速层或物化视图。
5. 交互查询与大批任务是否分属不同资源组或集群？同池则故障半径等于整个集群。
6. 单查询是否有内存上限与超时？都没有，一条查询可以打满共享内存。
7. 溢写目录的空间与 IO 有没有被监控？开启溢写但磁盘打满，会把新瓶颈引到存储上。
8. 湖仓表最近一次 compaction 与快照过期清理是什么时候、有没有归属人？
9. 关系库 Connector 用的是不是单独账号，且设了连接上限？与在线业务共用连接池是最常见的连带故障源。
10. 内嵌引擎与服务化引擎的 SQL 语义（时间、NULL、类型转换）是否做过一致性验证？
11. 生成式入口生成的 SQL 是否与人工查询走同一套权限与配额？走旁路就是绕过权限。
12. 抽 20 条生成 SQL 人工核对口径：跑得通但口径错的有几条？这个数不降就不该扩大放开范围。

### 4.7 小结

> 本节小结：六步里唯一不可替代的是 **Step 3 的下推验收**——它不产出新功能，只产出证据（源侧分片有没有过滤条件），而后面每一步都建立在它之上：统计信息与 CBO 只在「数据没被整表搬进来」时才改变代价，资源隔离只在计划已经正常时才轮得到背锅，AI 生成的 SQL 也共享同一条执行路径。它比其余环节更值得投入，是因为**下推失效是静默的**：结果永远正确，只有代价在上涨，而没有证据时团队会先怀疑引擎、再加机器，把一次实现缺失当成容量问题处理。
>
> 💡 **思考锚点**：抽你已接入的三个源各跑一条带过滤与投影的查询，用 `EXPLAIN` 看源侧分片到底带没带上过滤条件——这正是 Step 3 的下推验收。抽到"整表读"的那个 Connector，它现在承接的生产查询代价会随源表怎么涨？按 §4.1 的说法这个缺口通常在源表长大之后才暴露：届时你能从 `EXPLAIN` 一眼认出它，还是要先加一批 Worker 才发现？
