## 4. 工程实现

本节按「**先做什么 → 每件事盯什么信号 → 选型怎么判 → 存量怎么接 → 拿什么套 → 怎么自检**」组织。4.1 给六段顺序与判据，4.2 给实施层的机制与失效条件，4.3 给选型判据，4.4 给存量改造，4.5 与 4.9–4.10 两类读者共用（4.6–4.8 为本章各主题通用的成本 / 容灾 / 演进三节）。

**这份指南主要写给存量改造的读者。** 现实中绝大多数公司已经有数仓、有报表、有若干业务域各自的 ADS 表，问题从来不是「从零搭一套 OneData」，而是「在既有资产上把主体与口径收成一个定义点」。因此 4.1 的顺序是给从零起步的团队看的（它同时是最容易讲清依赖关系的顺序），**存量改造的团队请直接从 4.4 开始**，再回头按 4.1 的顺序补缺。本节不重复模式的论证：每个模式被什么约束逼出来、机制为什么有效、代价与失效点是什么，[§3](15-one-data-section-3-sec3.md) 已给（含各模式的选用判据与规模跃迁表），本节只回答装的时候怎么知道装对了。

### 4.1 落地步骤

**Step 1：OneModel 建模（4–8 周【经验：随业务域数量与存量表规模变，单域小规模可压到数周内】）**

- 业务调研：拉出各业务域现有的事实表与报表，逐张标出「主体是谁、粒度是什么、口径现在由谁认」；产物是一张表清单，不是访谈纪要 —— 后面每一步的分类都要落回这张清单。
- 数据分层（ODS / DWD / DWS / ADS 四层，外加旁挂的公共维度层 DIM）：先给现有表逐张打层标（哪张是 ODS、哪张名为 DWD 实为 ADS），再定新表的命名与分区键；打层标不能跳过，跳过就分不清哪些表本来是对的、哪些要改。
- 公共层抽取：把多个域重复计算的维度与汇总抽成 DIM / DWS，抽取顺序按「被引用次数」排，而不是按域的大小排 —— 先抽引用最多的那一批，收益兑现最快。

- **产物**：一份分层与命名规范、一张公共维度表（DIM）、第一批公共汇总表（DWS）。
- **判据**：抽 3 张现有报表【经验：抽样量随报表与资产规模变】，看它引用的表能否被映射到某一层、且只引用紧邻下层；再抽一个「按主体聚合」的指标，看它的主体键是否只来自 DWD 的 OneID，而不是在 ADS 里各算一遍。
- **为什么必须这一步**：分层是承载地点。指标平台的 `measure` 必须指向一张已经存在的公共层表 —— 没有公共层，Step 3 的指标就没有落点。而分层规则一旦被大量任务引用之后再改，改动成本是按引用数计的，不是按规范文档的页数计的。

**Step 2：OneID 治理（4–8 周【经验：随 ID 种类与数据量变，图计算的全量重跑通常是这一段的时间大头】）**

- 强 ID 收集（手机、身份证、UID）：从各业务库与登录日志抽取，逐类记录**来源与采集时点**；没有时点的 ID 不参与时态映射，只能降级为弱 ID。
- 弱 ID 关联（设备、Cookie、邮箱）：按共现建边，并把**共现窗口**（同一设备在多长时间内出现才算关联）写进作业参数；窗口值是后面调合并准确率的唯一旋钮。
- ID-Mapping 图计算：跑连通分量得到主体，结果落成**带映射版本的独立结果表**，不直接写回业务库；同一批作业按分量规模设上限，超限的分量不进映射、转人工抽检队列。

- **产物**：一份 ID-Mapping 结果表（带映射版本与生成时间）、一份主体合并规则、一个合并准确率的定期抽检动作。
- **判据**：抽同一自然人在两个业务域内的标识，看是否映射到同一个主体；**同时**抽 3 台共享设备【经验：抽样量随设备共享率变】（家庭共用、公共终端），看是否被错误合并成一个主体。两个方向都要做 —— 只查前者会漏掉「合并过头」，而合并过头比漏合并更难发现。
- **为什么必须这一步 / 为什么在这个位置**：主体键要在 DWD 落表时贯穿（见 4.5 模板 2 的 `dwd_trade_orders.user_one_id`），所以 ID-Mapping 的产出**形式**（离线结果表还是在线映射服务）与更新频率，必须在 DWD 定表之前定下来。主体键一变，所有以主体为粒度的汇总表都要重算 —— 这个顺序颠倒的代价，等于把 Step 1 的公共层重做一遍。

**Step 3：指标平台建设（4–8 周【经验：随指标数量与是否需要覆盖实时链路变】）**

- 指标梳理：把现有报表的取数 SQL 反解成指标清单，按「还有谁在用」排序；不要发问卷收指标，收上来的是愿望不是现状。
- 指标定义：逐条填定义 / 公式 / 源表 / owner / 版本，`source_table` 只允许填公共层表；填不出来的先挂在待办清单上等公共层补齐，不要为了方便临时指向明细表。
- 指标服务化：把语义层开放成一个统一查询入口（只收「指标名 + 维度 + 时间」），同时**登记每一处仍直连明细库的调用**（BI 连接串、分析师库表权限），这份登记就是 Step 4 收紧权限的清单。

- **产物**：一份指标登记（定义 / 公式 / 源表 / owner / 版本）、一套语义层定义（原子指标 + 派生指标）、一个统一查询入口。
- **判据**：「口径是否唯一」的核验动作见 [§3](15-one-data-section-3-sec3.md) §3.7 第 1 条，本节要看的是实施期信号 —— 语义层入口上线后，直连明细库的查询还在增长、且没有登记，说明「口径只此一处」在可达性上还没成立；抽 3 个指标看 `owner` 是不是一个具体的人【经验：抽样量随指标数量变】，以及这个指标现在有几个版本还在被引用 —— 有旧版本仍被引用，说明下游还没切完，切换清单要跟着更新。
- **为什么必须这一步 / 为什么在 OneModel 之后**：指标的 `measure` 与 `filters` 必须落在 Step 1 的公共层上；先建指标平台再补分层，会得到一批指向明细表的指标定义，之后每改一次分层就要重定义一次指标。

**Step 4：OneService 数据服务（2–4 周【经验：随需要暴露的接口数与权限模型复杂度变】）**

- API 化数据服务：按域组织接口，接口只接收「指标名 + 维度 + 时间」、只回传结果集，过滤条件一律不在接口实现里出现；每个接口登记它依赖的指标版本。
- Quick BI / 自助分析：把业务人员的取数入口指向语义层而不是直连数仓；切换期内保留原报表的只读权限，用于逐张对照切换前后的数字，对不上的先记录再解释。

- **产物**：一组按域组织的 API、一份「接口 ↔ 指标 ↔ 版本」的映射、一份数据访问权限登记。
- **判据**：抽一个 API 的返回字段，能否追溯到某个指标定义的某个版本；做一次口径变更演练，能否列出受影响的接口清单。
- **为什么必须这一步 / 为什么在指标平台之后**：接口一旦被外部消费就难以变更。把口径冻结在语义层之后再做服务化，接口只需要传递「指标名 + 维度 + 时间」，不必传递口径；反过来先做 API 再补语义层，过滤条件会写死在接口实现里，之后每次口径调整都要动一遍所有接口。工期短是它排在后面的另一个原因：这一层是薄的，价值兑现快，但它不是难度所在。

**Step 5：数据治理（持续【经验：随表数量与门禁强度变，没有结束点】）**

- 血缘追踪：从调度 SQL 解析出任务级血缘并下推到字段级；解析不了的作业（动态拼接表名、存储过程、外部脚本、手工导入）进盲区清单，这份清单自己也要有 owner 和更新频率。
- 数据质量：规则先挂在公共层的关键字段上（主体键、金额、时间），阈值按历史分位数先设一条宽线，再逐月收紧【经验：收紧周期随误报率与门禁变更量变，误报多就先松、变更陡增就放慢】；收紧的依据是误报率，不是感觉。
- 数据安全：字段级密级标完之后，必须接到查询入口的鉴权上 —— 只标在文档里、没接到入口的密级等于没标。

- **产物**：血缘覆盖清单（含「解析不了的盲区」清单）、质量规则与告警、字段级密级标注。
- **判据**：抽一次最近的变更，看它进入发布前有没有真的跑过一次影响面分析；再看盲区清单的条目数是在增加还是在下降，以及这份清单最近一次更新时间。
- **为什么必须这一步 / 为什么在指标平台与公共层之后**：门禁要挂在有东西可拦的地方 —— 指标与公共层存在之后，影响面分析才有对象、口径变更才有审批点。同时它是六步里唯一「不做也不会立刻出事、但拖着做成本按表数量增长」的一步（参见 [§3](15-one-data-section-3-sec3.md) §3.6 千表 → 十万表的跃迁）。

**Step 6：AI 集成（按需【经验：随语义层覆盖度变，覆盖度不到三分之二时通常还不到接入点】）**

- AI 驱动指标生成：按批次补机器可读属性（语义类型、默认时间维度、粒度、枚举值），每批补完先拿已覆盖的提问跑一轮检索验证，能召回预期指标才把这批开放给模型；补全比例不到约定的下限之前，模型侧只做只读试跑，不进生产取数链路。
- 自治数据中台：把「检索 → 生成 → 校验 → 执行」这条链路的每一跳都留痕（用了哪个指标的哪个版本、校验拦下了什么、拒答了多少次），并给模型侧单独划一份调用配额，不与人共用同一池子。

- **产物**：一份机器可读的指标属性补全清单（语义类型、默认时间维度、粒度、枚举值）、一条受约束的取数链路（检索 → 生成 → 校验 → 执行）。
- **判据**：抽一次模型生成的查询，看它是否只引用了候选集合内的指标、有没有出现自造的度量表达式；再看这条链路有没有留痕 —— 从执行记录里能否查出「这个数字用了哪个指标的哪个版本、由谁授权」。答不出，说明 AI 集成只接了个界面、没接上语义层。覆盖率的核验动作见 [§3](15-one-data-section-3-sec3.md) §3.2.4。
- **为什么必须这一步 / 为什么放在最后**：它完全依赖前三步的产物 —— 没有分层与公共层，模型没有可信的源表；没有语义层，模型没有可检索的候选。而且属性补全的工作量与指标数同阶，且必须在开放给模型之前完成 —— 并行会让模型先看到半覆盖的候选集，而先跑出去的数字没人会回头重算，所以它只能是最后一段，不能与 Step 3 并行。

**最常被跳过的是 Step 5 里的血缘。** 它不产出业务价值、不进入任何报表，只在事故发生时被想起。跳过后第一个出问题的时点很清楚：**第一次改动公共层字段之后的下一个早晨** —— 症状不是任务报错，而是下游报表的数字悄悄变了，而没有人能立刻列出下游清单；等到有人发现时，已经被影响的是几天前就已经发出的数字。

### 4.2 关键技术点

**OneModel 分层与粒度固化**

- **做法**：把分层写进命名与调度依赖 —— 主链四层 ODS（贴源）→ DWD（明细，主体键为 OneID）→ DWS（公共汇总，粒度与口径固定）→ ADS（应用），逐层引用、每层只引用紧邻下层；DIM（公共维度）不在主链上 —— 它是旁挂的公共维度层，各层都可引用它；粒度写进表名与分区键，命名次序为「域_实体_周期」（如 `dws_trade_shop_1d`）。
- **机制**：因为依赖由调度系统从作业 SQL 里解析得出，所以「明细层直接出汇总」这类捷径会表现为依赖图上一条本不该存在的边，而不是表现为口头违规 —— 违规在结构上可见，是这一步能被自动检查的原因。粒度写进表名，则让「粒度不一致」在命名阶段就暴露。
- **失效条件**：**当中心建模团队的评审周期长于业务迭代节奏时**，域团队会申请「临时 ADS 表」；一旦临时表被下游引用，它就成为事实上的第二层，且不在规范覆盖范围内。**症状**：依赖图里出现 `ods_*` → `ads_*` 的直连边；或命名带 `tmp_` 前缀但下游引用数持续上升的表。
- **档位**：【经验：层数与粒度随业务域数量与人均可维护的模型数变，域越多、人均维护面越大，层数越要压扁】；判据是「跨层引用的条数是否在增加」，不是「层数是否够多」。

**OneID 图计算的合并不可逆性**

- **做法**：把每个 ID 值建成节点、每次共现建一条边，用连通分量（Connected Components）求主体；结果落成带**映射版本**与生成时间的结果表；对分量规模设上限。
- **机制**：因为连通分量在新增一条边时会**合并**两个已有分量，所以主体的合并不可逆 —— 一次错误合并（一台多人使用的设备）会把两个真实主体永久绑成一个，之后所有以主体为基数的指标同时失真。它和口径问题不同：口径改了可以重算，主体错了会沿着所有下游扩散，而且没有一个天然的时点提醒你它错了。
- **失效条件**：**当共享设备比例上升时**（家庭共用平板、公共终端、企业统一发放设备、模拟器与爬虫），图里会出现远超业务常识的超大分量。**症状**：分量规模分布的长尾突然变厚；或某个域的人数口径在两个版本之间无解释地下降。**干预**：给分量规模设上限，超限的分量不做合并、转人工抽检队列；映射结果打版本，保证同一批报表用同一版映射。
- **档位**：连通分量是图计算的长期基础算法，Neo4j / GraphX 一类图库都提供实现，具体过程名与参数以各自官方文档当前版本为准（可按「connected components + 图库名」自行检索核验）；分量规模上限的取值【经验：随业务主体规模与设备共享率变，共享设备越多、上限越要收紧】。

**指标口径的代码化与变更流程**

- **做法**：原子指标与派生指标只在语义层定义一处，`measure` 与 `filters` 进版本控制；变更走评审、历史版本可查；对外只暴露「指标名 + 维度 + 时间」。
- **机制**：口径为什么以代码形式存放、变更为什么必须走版本控制，机制见 [§3](15-one-data-section-3-sec3.md) §3.2.2。实施层要看的是另一件事：**语义层的合并与报表的发布是两个团队、两条发布节奏** —— 一次口径变更合并进主干，与下游报表真正用上新定义之间隔着一个非零的窗口，窗口里下游拿到的仍是旧口径的数字，而**先发现异常的是下游报表的 owner，不是改口径的人**。所以每次口径变更的评审必须同时产出「受影响报表清单」并指定一个跟进人，否则第一张工单一定开给下游。反过来说，任何绕过语义层直连明细库取数的行为，都会在口径层面制造第二处定义。
- **失效条件**：**当语义层不是唯一入口时**（BI 工具仍能直连明细库、分析师仍有库表权限），第二处定义会在无人察觉的情况下出现。**症状**：同一个指标名在两个报表里数字不同，且各自的 SQL 都能自圆其说；或历史报表在某天之后整体平移（口径改了，但没人重算历史）。**干预**：把「口径只此一处」从规范变成可达性约束 —— 对直连明细库的查询做登记或收紧权限。
- **档位**：【经验：评审周期随业务节奏与月度变更量变，变更越密越要压缩评审队列，否则门禁会被绕过】；判据是门禁**误拦率**的月度趋势（数据取自门禁系统的放行日志），不是某一个月的误拦比例。

**任务开发、依赖与血缘同源（DataWorks）**

- **做法**：数据加工用可解析的作业定义提交（SQL 节点、受管的 Python 节点），依赖与公共层的产出时间在作业上显式声明。
- **机制**：因为依赖图与血缘图来自同一次解析，所以「调度能跑起来」与「血缘看得见」是同一件事 —— 解析器读不懂的作业，两样都缺。这解释了一个常见困惑：血缘的盲区不是采集得不全，而是那类作业压根没有可解析的定义（动态拼接表名、存储过程、外部脚本、手工导入）。
- **失效条件**：**当任务里出现拼接表名、存储过程或外部脚本时**，依赖丢失；上游变更不会被拦，下游会以「数据不对」而不是「任务失败」的形式暴露 —— 后者会告警，前者不会。**症状**：依赖图里存在没有上游输入却明显在读表的任务；或盲区清单长期不更新（说明没有人维护这份清单本身）。
- **档位**：DataWorks 的任务开发、调度依赖与血缘能力，可按阿里云官方产品文档当前版本自行核验（本节不引用具体发布年份，也不含版本主张）。

**实时链路里的映射新鲜度（Flink + Hologres）**

- **做法**：实时与离线复用同一份指标定义；实时侧用维表关联（按时态语义取映射表在事件时刻的版本）把 `user_id` 映射到 `one_id`；每日跑一次实时与离线的对账【经验：对账频率随实时窗口长度与下游结算时点变，结算时点越晚、窗口越长，对账可以越稀】。
- **机制**：因为实时侧取到的是**某一时刻的映射版本**，而映射表本身在持续被重算，所以实时结果的正确性取决于「映射更新延迟」与「实时窗口长度」的相对大小，而不是取决于计算逻辑对不对。对账如果只比总量，这个延迟在观测上完全不存在。
- **失效条件**：**当映射更新延迟大于实时窗口时**，同一用户在实时链路归属旧主体、在离线链路归属新主体，两边的以主体为粒度的指标同时「正确」却对不上。**症状**：实时与离线对账在总量上吻合、在主体维度（人数、人均）上对不上。第二种失效更要紧：**映射发生回撤时（一个 `uid` 从 `one_id A` 改到 `B`），已经发出的实时结果不会更正** —— 如果下游已把它用于结算或发券，回撤在数据层是修不回来的，只能走业务侧补偿。
- **档位**：【经验：映射更新频率与可接受的归属误差，随实时窗口长度与业务对归属误差的容忍度变，用于结算的链路容忍度最低】；判据是「对账是否覆盖主体维度，而不只是总量」。

**AI 增强指标的取数链路（LLM 受约束取数）**

- **做法**：模型只允许从检索到的候选指标中选，不允许自造度量表达式；生成结果一律先过校验器（校验项清单见 [§3](15-one-data-section-3-sec3.md) §3.2.4），而校验器的责任人、每一次放行与拦截的记录、以及拦截率报表都要有 owner，拦截率进值班看板；执行时记录「用了哪个指标的哪个版本」。
- **机制**：因为模型的查询走的是与人工完全相同的一套语义层 API，所以它的调用量、配额、权限默认与人的调用混在同一池子里 —— 一个 Agent 循环（往往要十几次调用才收敛【经验：次数随 Agent 的规划步数与工具粒度变，工具越细、步数越多】）会以数量级的差异占掉人工查询的配额，而这类流量在调用来源上没有任何默认区分。
- **失效条件**：**当模型侧使用统一的服务账号时**，它的权限与提问者不一致，可能取到提问者本人无权访问的数据域并把它展示出来；**当语义层覆盖不足时**，失效形态与判断方法见 [§3](15-one-data-section-3-sec3.md) §3.2.4，本节补的是它在运维上留下的痕迹。**症状**：语义层 API 的调用来源分布里单一服务账号占绝大多数；审计日志里出现「服务账号查询了与其调用者不匹配的数据域」；或拒答计数长期为 0 而同期的检索命中率没有同步上升。
- **档位**：覆盖率的核验方法见 §3.2.4（抽样业务提问比对命中指标）；配额划分【经验：随调用量与成本模型变，模型侧与人侧的比例越低，越要先划出独立池子】

### 4.4 存量迁移

**① 先做什么：只做口径登记，不碰任何链路。**

把现有报表里被引用最多的那批指标（十来个量级即可【经验：随报表数量与业务域数量变】）抽出来，登记为「定义 / 公式 / 源表 / owner / 版本」，**不修改任何任务、不重建任何表**。这一步当天就能见效，且完全可回退 —— 登记是元数据，撤销它不会影响任何生产链路。

判据：任取一个现有报表上的数字，能不能沿着登记表说清它由哪个指标的哪个版本、从哪张表算出来。能，说明登记表已经开始承担「口径唯一」的职责；不能，说明登记的是表而不是指标。

**② 历史资产怎么分类：三条路，逐类处理。**

- **同粒度、同口径**（可以挂靠）：把它们指向公共层，**只改引用、不改逻辑**。这是最省的一条路，应优先扩大它的覆盖面。
- **口径一致但粒度不同**：不要在原 SQL 上改，而是在公共层里补一张正确粒度的汇总表，让原任务改为引用它。改原 SQL 的代价是这份逻辑会变成第二处口径定义。
- **同名不同义**（口径本身就不一致）：**打标挂账**。建一份「同名不同义清单」，逐条记录：指标名的两种含义、各自的报表、各自的 owner、当前影响谁；冻结新增引用，但**不强制返工**。历史资产不返工是可以接受的，让第二处定义继续扩散是不可以接受的。

判据：抽 3 张高频 ADS 表【经验：抽样量随 ADS 表数量变】，逐字段回溯到 DWD；能回溯且口径一致的进第一条路，回溯不到的进清单。判断动作本身必须真的做一遍 —— 这一步「凭印象分类」的比例，直接决定后面双轨要维持多久。

**③ 双轨怎么维持、维持多久。**

存量改造期至少有两条双轨：公共层与既有 ADS 表并存；语义层口径与 BI 里的口径并存。第二条尤其要小心 —— 允许并存，但**必须标注哪一份是权威**，否则使用者会在两份数字里挑对自己有利的那一份，而这恰好会让「口径统一」在组织上失去合法性。

维持时间由两个信号决定，不由排期决定：对账差异率是否收敛、下游切换比例是否在上升。额外成本按**峰值**留，不要按均值留：公共层要承接既有查询量，指标平台要承接既有报表的查询频次，否则切换期一到大促就会有人被迫切回旧表。

**④ 什么信号说明可以退出双轨。**

四个信号，缺一个都不算退出：既有 ADS 表的下游引用数降为 0（不是「没人维护」，是引用数为 0）；「同名不同义清单」不再新增条目（说明新问题被门禁拦住了）；实时与离线对账稳定，且覆盖主体维度而不只是总量；域团队不再申请新的「绕过公共层」例外。最后一个信号最有价值 —— 它说明规范的力量来自「遵守它比绕过它更省事」，而不是来自审批。

**存量改造里最常见的两种失败，都不是技术失败。** 第一种是**把改造做成重做**：借统一口径的名义重建数仓、重写所有任务，结果改造启动一年后仍没有一个域完成切换【经验：随存量表数量与双轨期长短变，存量越大越容易拖成重做】，期间所有新需求仍建在旧结构上，改造对象反而变得更大。识别信号很直接 —— 改造启动后新建的表，落在公共层与落在既有结构的比例是在变化还是不动。第二种是**只出规范不动系统**：发布了命名规范与分层规范，但没有任何一处工具阻止跨层引用、没有任何一处入口强制走语义层，于是规范只约束了愿意遵守的人。

### 4.5 模板 / 示例

**模板 1：指标登记表**

```sql
CREATE TABLE metric_registry (
  metric_name   VARCHAR(128) NOT NULL,
  metric_type   VARCHAR(16)  NOT NULL,   -- atomic / derived
  definition    TEXT         NOT NULL,   -- 一句话：这个指标回答什么业务问题
  formula       TEXT         NOT NULL,   -- 度量表达式
  source_table  VARCHAR(256) NOT NULL,   -- 必须指向公共层表，不直接指向 ODS
  granularity   VARCHAR(64)  NOT NULL,   -- 可用的时间与维度粒度
  owner         VARCHAR(64)  NOT NULL,   -- 具体到人，不是团队
  version       VARCHAR(16)  NOT NULL,
  effective_at  TIMESTAMP    NOT NULL,
  deprecated_at TIMESTAMP,               -- 非空即视为已下线，查询应当拒绝
  PRIMARY KEY (metric_name, version)     -- 同一个指标名可以有多行：一版一行，版本历史都留在这里
);
```

**怎么用**：两格不能含糊 —— `source_table` 只填公共层表（填 ODS 说明这个指标还没落到正确的层），`owner` 填团队名的行应被视为未完成。`deprecated_at` 是非空即拒查，不要做「标记废弃但仍然可查」的软状态，否则下线等于没下线。同一个 `metric_name` 会有多行（一版一行），「这个指标现在有几个版本还在被引用」就是数 `deprecated_at IS NULL` 的行数 —— 主键写成单列，这个判据没地方落。

**模板 2：OneModel 四层 + DIM 完整 DDL**

```sql
-- ODS：贴源，保持原样以便回溯
CREATE TABLE ods_trade_orders (
  order_id BIGINT, user_id BIGINT, amount DECIMAL(18,2),
  status STRING, order_time TIMESTAMP) PARTITIONED BY (dt DATE);

-- DIM：公共维度层，旁挂于主链之外，主体唯一键在这里统一
CREATE TABLE dim_user (
  one_id BIGINT, user_id BIGINT, phone STRING, device_id STRING, email STRING,
  age INT, city STRING, vip_level STRING, effective_dt DATE, expire_dt DATE) STORED AS ORC;

-- DWD：明细 + OneID 贯穿，不做聚合
CREATE TABLE dwd_trade_orders (
  order_id BIGINT, user_one_id BIGINT, product_one_id BIGINT,
  amount DECIMAL(18,2), coupon_amount DECIMAL(18,2), pay_amount DECIMAL(18,2),
  order_time TIMESTAMP) PARTITIONED BY (dt DATE);

-- DWS：公共汇总，粒度写进表名
CREATE TABLE dws_trade_user_1d (
  user_one_id BIGINT, gmv DECIMAL(18,2), orders BIGINT, paid_orders BIGINT) PARTITIONED BY (dt DATE);

-- ADS：应用层，只引用公共层
CREATE TABLE ads_user_rfm (
  user_one_id BIGINT, recency INT, frequency INT, monetary DECIMAL(18,2), rfm_segment STRING);
```

**怎么用**：这五张表里只有两处是真正的判断点 —— DWD 的主体键（必须是 OneID，不是业务库的 `user_id`）和 DWS 的粒度（写进表名，改表名等于改粒度，必须走评审）。`dim_user` 的 `effective_dt` / `expire_dt` 是拉链字段，没有它就无法回答「当时的归属是什么」—— 凡是要做历史对比的指标都依赖这两个字段。`amount` / `coupon_amount` / `pay_amount` 三列并存不是冗余：订单原额与券后实付是两个口径，删掉中间列，后来的人就无从判断某个指标当初用的是哪一个。

**模板 3：OneID 连通分量（工程约束说明）**

```text
输入：ID 对（strong_id, weak_id）—— 手机↔设备、UID↔设备、邮箱↔设备
构建：每个 ID 值一个节点，每次共现一条边
计算：连通分量（Connected Components）→ 每个分量一个 one_id
输出：id_mapping_result(uid, device_id, phone, email, one_id,
                     mapping_version, effective_at, expire_at, generated_at)

三条工程约束（比算法本身更重要）：
  1) 分量规模上限：超过上限的分量不合并，转人工抽检
  2) 映射版本化：同一批报表必须使用同一版映射，每版带生效区间（实时侧按事件时刻取当时生效的那一版）
  3) 回撤可查：一个 uid 换了 one_id 时，要能查到从哪一版开始变
```

**怎么用**：`one_id` 用分量内可复现的取值生成（最小 ID 值或哈希）即可，关键是**可复现**与**带版本**；三条工程约束里第一条最容易漏 —— 不设分量上限，一次共享设备的误合并会永久留在映射里，且没有任何一步会报错。连通分量的具体算法实现与参数按你所用图计算引擎的官方文档当前版本填。

**模板 4：语义层定义**

```yaml
metric:
  name: gmv
  type: simple                 # 原子指标
  measure: total_order_amount  # 度量只有一处定义
  filters: ["{{ Dimension('order__is_paid') }} = 'true'"]
  granularity: [1d, 1h]
  owner: zhang.san             # 具体到人；这一格填团队名（如 trade-analytics）视为未完成
  version: 1.0

derived_metric:
  name: arpu
  type: ratio                  # 派生指标
  numerator: gmv
  denominator: paid_users
  description: 单用户平均收入

derived_metric:
  name: conversion_rate
  type: ratio
  numerator: paid_orders
  denominator: total_orders
  description: 订单转化率
```

```python
# 消费侧：只传指标名 + 维度 + 时间，过滤条件留在语义层
# 伪代码：client 由所用语义层的 SDK 提供，参数名以该 SDK 的官方文档为准
client.query(metrics=["gmv", "arpu", "conversion_rate"],
             group_by=["region"],
             time_range="2025-01-01~2025-01-31")
```

**怎么用**：`measure` 与 `filters` 一旦被下游引用就不要再原地修改 —— 改口径等于换指标，应当发新版本并保留旧版本的 `effective_at` 区间（字段名以你所用语义层平台的官方文档为准，本文与 [§3](15-one-data-section-3-sec3.md) §3.2.2 统一写作 `filters`）；`granularity` 是给消费者看的契约，实时链路必须与它对齐（见 4.2 的映射新鲜度一条）。这两个派生指标里只有 `arpu` 直接引用 `gmv` 这个度量，`conversion_rate` 走的是 `paid_orders / total_orders` 这一条度量、不经过 `gmv` —— 所以「gmv 改口径要发新版本」的实际影响范围是 `gmv` 与 `arpu` 两个定义、加它们各自的下游，变更评审按这个范围通知，而不是按单个指标、也不是按全部派生指标。

**模板 5：受约束的自然语言取数 Prompt**

```text
你是数据分析助手。只允许从下面的候选指标中选择，不允许自行构造度量表达式。

候选指标（含口径 / 粒度 / owner / 版本）：
{candidate_metrics}

用户问题：{question}

输出要求：
1. 选择的指标（逐个说明理由；若没有合适指标，直接回答"无匹配指标"，不要用相邻指标近似）
2. 维度与时间范围（必须落在指标的 granularity 之内）
3. 查询参数（不是 SQL 文本）
4. 该结果的口径与 owner（供使用者复核）
```

**怎么用**：`{candidate_metrics}` 必须来自检索结果，不要把全部指标塞进上下文 —— 既贵，也更容易选错；模型与调用方式按你所用语义层平台的当前官方文档接入。「无匹配指标」这条分支要真的能走通，并保留一个可观测的拒答计数：拒答率突然降到 0，通常意味着有人在提示里加了「无论如何都要给答案」。

**模板 6：实时链路的时态映射关联（OneID 维表关联）**

```sql
-- 实时侧把 user_id 映射到 one_id：取事件时刻生效的那一版映射，不是当前最新版
INSERT INTO dws_trade_shop_rt
SELECT o.shop_id,
       o.ts AS window_end,
       SUM(o.amount) AS gmv,
       COUNT(*)      AS paid_ord
FROM kafka_orders AS o
LEFT JOIN id_mapping_result FOR SYSTEM_TIME AS OF o.ts   -- 时态关联：版本对齐事件时刻
       ON o.user_id = id_mapping_result.uid
GROUP BY o.shop_id, o.ts;
```

**怎么用**：`FOR SYSTEM_TIME AS OF` 后面必须是**事件时间**，不是处理时间 —— 写成处理时间，补数时就会把「今天最新的一版映射」套到昨天的数据上，实时与离线从此对不上，而且对不上的是主体维度、总量仍然吻合。`id_mapping_result` 要带版本与生效区间（列见模板 3），离线侧的重算与实时侧的读取用的必须是同一份定义；维表连接器与具体语法以你所用流计算引擎的官方文档当前版本为准。

### 4.6 成本：这套东西的账单

OneData 的成本与数据字节量关系很弱，与**协调面**关系很强。三项里与它真正相关的是人力与算力 / 在线查询，硬件只在自建时相关：

- **人力（通常最大）**：建模评审、OneID 合并仲裁、口径冲突裁决——都是「所有域都要经过同一个定义点」逼出来的持续工作。单域建模 4–8 周【经验】（见 4.1），但治理（Step 5）没有结束点【经验】：它不是项目成本，是常设岗位成本。**为什么贵在这里**：OneData 卖的就是「单一定义点」，它把原本分散在各域、各自优化的重复开发成本，集中成一处治理成本——贵不在字节，在所有人都得排队过同一个评审队列。
- **算力尖峰**：ID-Mapping 的全量重跑是周期性尖峰，与日常增量不在一个量级。它的计算量 ∝ 图的边数（弱 ID 共现对数），边数 ≈ Σ 各类弱 ID 的共现次数【推算】——所以随「ID 种类数 × 事件量」增长，不随表数增长。这是 OneData 相对普通数仓多出来的一处固定开销。
- **在线 / 查询**：语义层是唯一入口，其查询量由**调用来源数**决定，模型侧一轮 Agent 循环要十几次调用【经验】（见 4.2）。配额与成本必须按来源分池，否则模型流量会挤占人工查询。

云上（MaxCompute / Hologres / 图计算）的单价按各云官方定价页当前版本核验；自建时才把 HDFS / Spark 的机器折旧与机房电力计入硬件项。**通用 FinOps 方法（预留、竞价、闲置回收）见 [11-cross-cutting/03-data-cost-finops](../../11-cross-cutting/03-data-cost-finops/)**，本节只讲 OneData 多出来的那三处。这份清单里最容易漏的是人力：它不出现在任何账单上，却常常是三项里最大的一项。

### 4.7 容灾与故障演练

OneData 几乎不持有在途交易，跨地域多活不是它的主矛盾；它的容灾对象是两样——**唯一定义点的可用性**与**定义 / 映射的可回滚性**。跨地域与多活设计见 [12-architecture/07-disaster-recovery](../../12-architecture/07-disaster-recovery/)，混沌注入方法见 [12-architecture/06-chaos-engineering](../../12-architecture/06-chaos-engineering/)；本节只讲本章特有的失效。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 语义层 / 指标平台不可用（唯一入口） | 全线取数中断 | 只读回落直连公共层（DWS）+ 最近一次物化值 | 停掉语义层，验证回落链路能否出数 | RTO 分钟级【经验】，RPO 0（数据在公共层） |
| 主体误合并（共享设备） | 所有以主体为基的指标同时失真并向下游扩散 | 分量规模上限 + 人工抽检队列 | 注入一台多人共享设备，看是否被上限拦住 | 不可原地撤销；发新映射版本，恢复随下游重算 |
| 映射回撤（uid 改 one_id） | **已经发出**的实时结果（结算 / 发券） | 数据层无法更正，只能业务侧补偿 | 改一个 uid 的 one_id，追一遍下游补偿动作 | 取决于下游结算窗口【经验】 |
| 口径变更后历史未重算 | 历史报表整体平移、无人察觉 | 评审强制产出「受影响报表清单 + 跟进人」 | 回滚一个指标版本，看历史是否被重算 | 重算代价 = 该口径影响过的全部历史 |

这张表前两行的共同点是**系统不报错**——所以它们的恢复目标只能是「发新版本 + 重算」，而不是「切回备用」。跨地域热备对 OneData 的价值有限：它不持有有状态的在途交易，真正的风险是定义错了却不报警。

### 4.8 演进路线：0 → 1 → 100

这条路线是 [§1.4 演进历程](15-one-data.md) 五阶段的工程视角：历史讲范式怎么变，这里讲成本怎么涨、先坏什么。

- **0 → 1（单域最小可用）**：一个域的分层 + 一份口径登记（纯元数据，当天可回退，见 4.4 ①）+ 一个实体的 OneID。**变贵的是**：几乎不贵，一个建模小组即可。**先坏的是**：登记表没人更新，公共层与既有 ADS 表各说各话（双轨漂移）。
- **1 → 100（多域规模化）**：语义层收成唯一入口、治理门禁上线、实时链路接入。**变贵的是**：①治理人力——评审队列成为瓶颈；②ID-Mapping 全量重跑算力；③跨域主体仲裁。**先坏的是**：当中心评审周期长于业务迭代节奏，域团队申请「临时 ADS 表」，依赖图里出现 `ods_* → ads_*` 直连边（见 4.2）。
- **100 →（下一道坎）**：千表以上时治理成本按表数增长；口径要扩到**机器可读**（语义类型、默认时间维度、粒度、枚举值），并把 AI 取数按来源分池。**变贵的是**：治理场地与 AI 配额。**先坏的是**：模型先看到半覆盖的候选集，跑出去的数字没人回头重算。方向见 [§5 前沿演进](15-one-data-section-5-ai.md)。

### 4.9 自检清单

> 下列条目都是**动了系统才有答案**的检查 —— 坐下来想一想就能回答的那些（粒度合不合理、模式选得对不对、口径该由谁裁决）在 [§3](15-one-data-section-3-sec3.md) §3.7，本节不重复。条目里的抽样规模与时间窗（3 台、近一周、30 天一类）都只是起点【经验：随资产规模、调度周期与报表发布节奏变，资产越大、周期越长，抽样量要跟着放大】—— 它们是让你现在就能动手的量，不是结论。

1. 语义层入口上线后，统计**直连明细库的查询**（BI 用的连接串、分析师的库表权限）：这批调用还在增长、且没有任何一处登记，说明「口径只此一处」在可达性上还没成立（口径是否唯一的判定动作见 §3.7 第 1 条）。
2. 抽一个对外 API 的返回字段，能否追溯到某个指标的某个版本？答不出即服务层与语义层已脱节。
3. 从调度系统导出近一周的依赖边，看有没有「明细层直出汇总」或 ADS 跨层引用；分层纪律本身的判定见 §3.7 第 2 条，本节要问的是**这类边出现时有没有被自动拦住** —— 没有门禁、只靠抽查，违规会一直存在到下一次有人抽查为止。
4. 从 ID-Mapping 结果表里抽 3 台共享设备（家庭共用、公共终端）【经验：抽样量随设备共享率变】，看它们是否被并进了同一个主体 —— 正向的「同一自然人是否映射到同一主体」见 §3.7 第 5 条；合并过头只能在结果表上查，且记录必须写明用的是哪一版映射，这份记录就是下一版调分量上限的依据。
5. 跑一次实时与离线对账，看它是否覆盖主体维度（人数、人均），还是只比总量；更要看**破线之后告警落到谁的工单上** —— 跑了没人看、或看了没人认领的对账，等同于不存在。
6. 在血缘系统里查最近一条变更，看它进入发布前有没有真的跑过影响面分析。
7. 看血缘盲区清单：条目数在增加还是下降，最近一次更新是什么时候。
8. 抽一次 OneID 映射更新，看它对已发出的实时结果是否需要更正；需要的话，下游的结算 / 发券动作靠什么补偿。
9. 调一次模型的取数，看它的调用来源是不是同一个服务账号，权限与提问者是否一致。
10. 统计语义层 API 的调用来源分布：模型流量占多少，是否挤占了人工查询的配额。
11. 盯语义层 API 上两条曲线：**拒答计数**与检索命中率。拒答率降到 0 而命中率没有同步上升，通常是提示里被加了「无论如何都要给答案」（覆盖率本身的核验方法见 §3.2.4）。
12. 统计公共层各表最近 30 天的下游引用数，对引用为 0 的表分两类处理：被绕过的进「绕过登记」找 owner，本来就不该建的走下线流程 —— 下线要在评审上留下结论，不能只出一张表。

### 4.10 小结

> 本节小结：OneData 落地里唯一决定成败的环节，是**主体与口径这两件事各自只有一个定义点**（OneID 一处、指标口径一处）；分层、服务化、治理门禁、AI 取数都是在这一条成立之后才有意义的放大器。它比其余环节更值得投入，原因是这两种错误的共同形态是**系统不报错**：任务照跑、报表照出、数字都能自圆其说，只是不再可解释 —— 而一个不可解释的数字要修回来，成本通常等于重算它影响过的全部历史。所以投入顺序应当倒过来看：先把口径登记与 ID-Mapping 的抽检机制做掉，再去补语义层属性、AI 取数与治理门禁。

> 💡 **思考锚点**：去数一下你系统里直连明细库的查询量——它还在增长、且没有一处登记吗？按本节的定义，这意味着「口径只此一处」在可达性上还没成立（4.9 第 1 条）。再抽一次 OneID 映射更新，看它对**已经发出去的**实时结果要不要更正、下游的结算 / 发券靠什么补偿——答不上来，主体这条定义点就还有一个无人负责的出口。
