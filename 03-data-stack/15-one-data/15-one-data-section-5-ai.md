## 5. 前沿演进（AI 时代）

> 原 § 5 共 96 行、为方向清单，重写为 ~280 行前沿评估。

### 5.1 先分清三类「前沿」

趋势清单的根本问题是**没有时间维度**。同一个清单里，「AI 驱动的指标生成」与「自治 OneData」被并列写成两条方向，读者据此排路线图就会踩空：前者今天可以在产品文档里查到功能状态，后者连「什么算自治」都还没有共识。

第二个问题是清单把**机制差异**抹平成了同一类词。把 §7.3 的四条机制拉出来看——口径的裁决落点（§7.3.1）、数据要不要跨边界移动（§7.3.2）、计算路径有几条（§7.3.3）、消费接口面向人还是面向模型（§7.3.4）——本节要评估的方向里，绝大多数**一条机制都没有改**；改的是起草者、入口形态与调用方三件事。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（或版本化发布的规范与文档）；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期。
- **L2 可试点**：可以做出 PoC，但不要做成核心依赖。具体是 ①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

三条判据分别在回答三个问题：① 它是发布过的，还是演示过的；② 出问题时我能不能找到别的团队的经验，而不是厂商的承诺；③ 我明年会不会为它重写一遍。**② 是最难过的一条**，而且它只有两种命运——满足，或降为 L2；不存在「换个说法算满足」，也不存在「把适用范围缩小到某一层」就绕过去。

另有三条评级规则，后面会用到：

- **合并方向取最弱子项**。「AI 原生 OneData」是若干子能力的合并叙事，它的级别取其中最低的一项。
- **命名待复核项不算证据**。原清单里的产品名（如「通义数智」）在公开材料中无法逐条核验名称与版本，本目录 §7.3.4 已把它降为待复核；本节沿用该结论，只给核验方式，不对其能力作断言。
- **能力名与产品名要分开判**。「Snowflake Cortex」是一组托管 AI 函数的产品名，取数只是其中某个组件的能力；把整个产品名当成「自然语言查询」来评级，级别会被高估。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |

**本节没有一行达到 L1。** 五条 L2 全部卡在同一条判据上：②（第三方非厂商公开生产案例）拿不出。其中「AI 驱动的指标生成」与「自然语言查询」两行的 ①③ 最干净——功能状态与产品文档可查，入口形态也已固定；其余三条 L2（向量库 / RAG、Agent 接口、Data Mesh 演进）的卡点同样是 ②：其中「Agent 接口」一行的 ①③ 只到「部分满足」（工具协议仍在演进），「向量库 / RAG」与「Data Mesh 演进」两行的 ①③ 在表里记为满足——它们满足 ① 的方式分别是既有接口的拼装与契约的承载形态（catalog），不是某个产品级能力的正式发布。它们缺的不是能力，是别人踩过坑的记录：**能力可用只说明能试，能不能排进路线图取决于有没有别人踩过坑的记录**。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式 release note 或版本化规范能不能找到？找不到 → L3。
2. 厂商之外的证据能不能找到？找不到 → L2。
3. 接口明年会不会变？会变 → 至多 L2。

第 3 句最容易被忽略：**接口稳定性比能力有无更难满足**，而它直接决定你要不要为它写一层适配。以「自然语言查询」走一遍：产品文档与功能状态都查得到（第 1 句过）、第三方生产效果拿不出（第 2 句不过）→ L2，不必再看第 3 句。

三个常见误判，排路线图时最容易踩：

- **把「能力可用」误当成「可以排进路线图」**：能力可用只说明能试；能不能排进去，取决于判据 ② 与 ③。
- **把「厂商演示或自有案例」误当成第三方证据**：建设方自述的案例属于 L2 的定义（「仅有厂商自有案例」），它说明这条路走得通，不说明别人走通了。
- **把「技术栈里有向量库」误当成「中台已经面向模型」**：§7.3.4 量的是**指标定义是否机器可读**，不是清单里有没有向量库。

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 指标生成：换掉的是「写口径的人」，不是口径的裁决点

- **旧做法与它的卡点**：指标从业务需求到可用，走的是「提需求 → 建模评审 → 平台改定义 → 下游生效」（§7.3.1）。卡点不在某一步慢，而在**每一步都只能人做，并且无法批量**：翻译一个指标的成本是小时级【经验】，公共层的覆盖速度在指标数上千级时就追不上业务提需求的速度【经验】；追不上的那部分需求，最后以「域内自建 ADS」的形式出现（§7.4 把它记成隐性成本，也正是 §7.3.1 失效条件里那条绕行路径）。
- **AI 改变了什么机制**：生成方向反转——过去人读需求写定义，现在模型读需求产出候选定义（主文件 §2.3 的示例输出 name / description / type / formula / source）。**但裁决点没有变**：候选仍要落进同一份语义层、走同一条评审通路（§7.3.1）。所以它改的是起草成本，不是正确性的来源。
- **由此得到的**：因为模型能把自然语言需求转成结构化候选，**所以**起草环节的成本从小时级降到秒级【经验】，同一个人可以覆盖更多指标；**并且**因为候选必须落进唯一那份语义层（§7.3.4），**所以**新增速度不会带来第二份口径——这正是 §7.3.3 说的「AI 增强模式不新增计算路径」。
- **由此付出的**：生成是概率性的，模型会产出**语法正确但口径错**的候选，而口径错不会报错——它的暴露方式与 §7.3.3 描述的链路分叉同源：不以「发现不一致」的形式出现，而以「业务不再信任数据」的形式出现，只能靠 §7.3.1 的评审通路拦在前面；评审负担从「写」转移到「看」，指标数到万级时评审自己成为新瓶颈【经验】（§7.4 的 f 项：逐指标补机器可读属性，工作量与指标数成正比）；此外把业务需求描述与表名送进模型，多了一条数据出境的边界。
- **证据与来源**：【公开】「需求 → 结构化定义」类任务的公开评测以基准为主（Spider，EMNLP 2018；BIRD，NeurIPS 2023），后者以「真实库、脏数据、大 schema」为设计目标，正好对应生产环境的失败来源；【公开】面向模型的口径承载形态（语义层）可由 dbt Semantic Layer 官方文档与 MetricFlow 开源仓库核验（见 §7.3.1）。至于「某平台自动生成指标的准确率」，判定方法是看它的文档是否给出评测条件（指标数、schema 规模、是否允许人工澄清）——没有条件的百分比不构成证据。
- **成熟度**：**L2**（与 5.1 表「AI 驱动的指标生成」行一致）。同一主题的另一半「整模型 OneModel 生成」是 **L3**——因为「生成若干指标候选」与「生成一份自洽的分层模型」不是同一件事：后者要求一致性约束（粒度、维度、命名、主体标识）同时成立，而今天承担这些约束的仍然是规范与评审，不是模型。

**一个可自验的验收口径**：取 50 条真实业务需求，让模型起草指标定义，再由建模同学复核，分别记录「需要改口径的条数」与「需要改语法的条数」。前者占比高 → 问题在语义层的定义文案与覆盖度；后者占比高 → 问题在提示与输出格式。这个区分决定了预算该投向语义层还是投向模型。

模型要被喂进去的那份定义，长什么样（示例，字段名取自主文件 §2.2 的 Metric 六元组，并按 §7.3.4 的要求扩到可判定的粒度）：

```yaml
# 一个「机器可读」的指标定义：AI 取数的最小输入
metric: trade_order_paid_cnt
display_name: 已支付订单数
definition: 统计已支付订单数；含全渠道；不含已退款订单   ← 口径要写成可判定的句子，不是形容词
measure: count(order_id)
source: dwd_trade_order
source_fields: [order_id, order_status, pay_time]
filters: order_status = 'PAID'
granularity: [1d, 1h]
time_semantics: {event_time: pay_time, timezone: Asia/Shanghai, late_window: 2d}
owner: trade-analytics@            ← 具体到人 / 组，不是「数据团队」
version: 3

判定方法：把上面十一项逐一标注「有 / 没有」——标注为「没有」的项，
         就是模型接下来一定会猜的那一项（猜错的后果见 5.2.2 的失败类型表）
```

#### 5.2.2 自然语言查询：入口变了，口径没变

- **旧做法与它的卡点**：业务取数要么提需求排队，要么自助但得先会用指标名与维度名。卡点在**业务词汇与指标名之间的翻译**：没有语义层时，这道翻译只能靠人与文档；而若把表名当作翻译对象，一个简明的问题会被降解成「猜表名 + 猜口径」。
- **AI 改变了什么机制**：把「选指标 + 拼维度 + 写查询」这一串动作从人换成模型。执行路径没变——仍是「读语义层 → 生成查询 → 引擎执行」，变的是**入口形态与人机分工**。这是接口改良，不是架构变化；把它当架构变化，就会去换引擎，而引擎从来不是这里的瓶颈。
- **由此得到的**：因为模型是在语义层的**候选集合内**做检索与选择（§7.3.4 的「检索 → 候选 → 校验」回路），**所以**模型的错误被压缩成「选错指标」这一类可以在结果里被发现的问题，而不是「编出一个没人能发现的口径」；**因为**选择发生在候选集合内，**所以**开放范围可以按覆盖率分级——高频指标先补齐属性并开放，长尾明确拒答。
- **由此付出的**：覆盖面扩大，也放大了「看起来对的错答案」的暴露面（业务方不再经过取数同学这道人工复核）；候选不足时模型会用最相似的可用指标填空（§7.3.4 的失效条件），而这类错在数值上完全合理；并且新增一个权限主体——模型以谁的身份读指标（见 5.3）。
- **证据与来源**：【经验】自然语言取数的产品形态可落到具体产品与文档域上核验（例如 Databricks Genie 见 docs.databricks.com、Snowflake Cortex 见 docs.snowflake.com，形态在 2024 年前后陆续出现），判定方法是查该功能当前是否 GA、是否给出评测条件（数据集、schema 规模、是否允许澄清），而不是看发布会的演示；这些材料是厂商自证，不构成第 ② 条。【公开】文本转 SQL 的公开基准 Spider（EMNLP 2018）与 BIRD（NeurIPS 2023）说明这类系统的评价方式以「执行结果是否一致」为计分口径。第三方公开生产案例不公开，② 不满足。
- **成熟度**：**L2**（与 5.1 表「自然语言查询 OneData」行一致）。

失败类型要分开，才知道该修哪里：

| 失败类型 | 表现 | 该修的地方 |
| --- | --- | --- |
| 选错指标 | 跑得通，但答的是另一个问题 | 语义层：指标口径文案与覆盖度 |
| 维度 / 时间语义错 | 量级对但口径不对（含不含退款中、算不算跨天迟到） | 语义层：时间维度与状态枚举的定义 |
| 越权 | 跑得通，但读了不该读的指标 | 平台侧：指标级权限与行级过滤 |
| 幻觉指标 | 生成了一个不存在的指标名 | 工具层：只允许在候选集合内选择，不做自由生成 |

一条可控的取数链路（关键在于第二步是确定性的）：

```text
业务提问（自然语言）
   │
   ├─① 选指标：在语义层的候选集合内检索（不确定性来源在这一步，不在查询语法）
   ▼
候选指标 + 维度 + 时间范围
   │
   ├─② 确定性校验（不依赖模型）：指标是否存在 → 维度是否合法 → 权限与行级过滤注入 → 限额
   ▼
生成查询 → 执行（与手写查询走同一套优化器与执行器）
   │
   └─③ 回写：留下「提问 → 选中指标 → 结果」记录（口径错复盘的唯一依据）

判定方法：让 ② 的每一项能单独失败，并返回「哪一项没过」
   只返回「拒绝」时，口径错会被误判成权限问题
```

- **失效条件**：当高频指标的机器可读属性覆盖不到真实查询的覆盖面时，系统会从「回答」退化成「用最相似的指标近似」——此时它只是比排队更快地把错答案送到业务手里。
- **自验方法**：抽样约 20 个真实业务提问，人工认定每个问题对应的正确指标，再看系统命中的是不是同一个；命中比例即覆盖率的下界（做法与 §7.3.4 一致）。

#### 5.2.3 自治 OneData：先把「自治」拆成三类机制

- **旧做法与它的卡点**：指标平台的运维（异常发现、覆盖率维护、僵尸指标清理、影响面分析）全由人做，而**台账的维护量随资产数线性增长**（§7.4 的 f 项）。规模一上来，最先坏掉的不是查询，是没人再核对某个指标是否还有人在用。
- **AI 改变了什么机制**：这里必须先做一次命名拆分，否则预算会投错地方：

| 被叫作「自治」的三类机制 | 输入 | 与 LLM 的关系 | 现状 |
| --- | --- | --- | --- |
| 统计检测（异常、突变、趋势） | 指标时间序列（已在平台里） | **无关** | 既有能力，不需要 AI 也能做 |
| 规则闭环（阈值触发工单、超期下架） | 元数据 + 策略 | **无关** | 既有能力 |
| 生成式判断（归因、解释、分类、候选建议） | 指标变化 + 血缘 + 变更记录 | 有关 | 本节真正要评估的部分 |

  也就是说，三类里只有第三类是新的。把前两类记成 AI 收益是记账错误——它会让「自治」的预算流向模型，而问题本来在台账维护上。

  **三类里最该先做的不是归因，是影响面。** 口径变更的影响面（这次改动会碰到谁）可以从血缘与元数据直接算出来，属于前两类机制，不需要模型；而「为什么这个数掉下来了」才需要生成式判断。顺序倒过来，就会出现「解释写得很漂亮、但没人知道这次改动影响了谁」的局面。
- **由此得到的**：因为异常检测的输入是平台里已有的指标时间序列，**所以**「指标坏了要有人知道」这件事今天就能做，且不依赖任何模型；**因为**生成式判断能把「为什么异常」写成可读的候选解释，**所以**值班同学的处理路径可以从「从零排查」变成「核对候选归因」；**代价是**归因是生成出来的，**它可能给出看起来合理的错误原因**，因此必须把原始指标、血缘与变更记录一并呈现，让人有对照物。
- **由此付出的**：自治系统一旦自动改口径或自动下架资产，变更就不再经过 §7.3.1 的评审通路——**审计痕迹与责任主体同时消失**，而这两样正是公共层口径能被信任的前提；因此安全边界只能写成「自动提议、人工批准」，与 §7.3.1 的裁决落点保持一致。另一项代价更隐蔽：解释性文本会给人「已经查清」的错觉，反而降低人工复核的严格程度。
- **证据与来源**：本方向无公开可核验来源，属 L3。判断某平台是否真的自治，方法是查其文档里哪些动作是全自动的、哪些需要审批、留痕覆盖到哪一步——**只有全自动那部分的「自动」是自治，其余叫自动化建议**。
- **成熟度**：**L3**（与 5.1 表「自治 OneData」行一致）。

#### 5.2.4 OneData 作为 Agent 的工具：调用方变了，接口就要重做

- **旧做法与它的卡点**：OneData 的对外接口一直是给人看的（看板、数据集）或给 BI 用的（SQL 与 API）。让 Agent 取数只有两条路：给每个指标写一个工具，或直接给它一份 SQL。前者的卡点是**工具数量随指标数增长**，且每个工具的参数语义、权限与错误码都不一致；后者的卡点在权限——**引擎侧的权限模型里没有「Agent 身份」这一档**。
- **AI 改变了什么机制**：把 OneData 的消费接口从「面向人」改成「面向模型」（§7.3.4 的那条判据），并把「统一 API」标准化成工具协议（MCP 一类）。真正改变的是**调用方的身份**：以前是人或 BI 工具，现在是 Agent，于是限额、只读约束与审计都必须以「非人主体」为前提重做。
- **由此得到的**：因为指标是一份集中定义、且自带 owner 与版本的对象（主文件 §2.2 的 Metric 六元组），**所以**开放给 Agent 的不是裸表，而是一组有名字、有口径、有责任人的对象——这让错误可归因（错在哪条口径、谁维护它），也让授权可以按指标而不是按表来切分；**因为**执行仍在既有平台内，**所以**口径约束继续有效，Agent 不会让平台变快，但也不必换平台。
- **由此付出的**：权限模型要新增一维，否则只能在「给太大权限」与「靠人代签」之间二选一，而后者的自动化价值为零；Agent 会高频、无节制地重试，必须有限额，否则单个 Agent 可以拖垮共享入口；5.2.2 的口径错在 Agent 手里会被并发**规模化放大**；协议本身仍在演进，绑定某一版会带来迁移成本。
- **证据与来源**：【公开】MCP 由 Anthropic 于 2024 年 11 月首次公开，其后有带日期的规范修订版本——判断某客户端或服务端支持哪一版，看它声明的规范版本号，而不是看生态清单页。第三方（非厂商）公开生产案例不公开，② 不满足。
- **成熟度**：**L2**（与 5.1 表「Agent 经统一 API / 工具协议访问 OneData」行一致）。

工具层必须自己承担的检查项（缺一项就不要给 Agent 开放取数）：

| 检查项 | 为什么必须在工具层做 | 缺了会怎样 |
| --- | --- | --- |
| Agent 身份与授权 | 平台多数只认人与服务账号，无法区分「谁的 Agent」 | 权限只能给大，无法按会话收窄 |
| 只读约束 + 指标白名单 | 生成式模型会产出写入或改结构的语句 | 一次误生成就可能改数据 |
| 指标级授权与行级过滤 | 越权必须在执行前拦（不能事后告警） | 数据外泄，且日志反过来成为证据链负担 |
| 限额（并发 / 扫描量 / 返回行数） | Agent 会高频、无节制地重试 | 单个 Agent 拖垮共享入口 |
| 审计记录（谁 / 何时 / 查了哪个指标） | 「非人主体」若不留痕就无法复盘 | 出事后无法定位到具体会话 |

**表中其余方向为什么停在这里**：

- **OneData + 向量库 / RAG（L2）**：机制是「把指标文案与元数据做成检索层」，它能提升**找到候选**的召回，但不能提升**选对候选**的正确率——后者由语义层决定（§7.3.4）。接口可拼装，但「检索质量如何影响取数正确率」的第三方归因做法没有公开可引用的材料，② 不成立。
- **多模态数据中台（L3）**：机制是让非结构化内容（图像 / 音视频 / 文本）与结构化指标共享一个检索面。它与本节其余方向的关系要分清：多模态改变的是「还能检索到什么」，**没有**改变口径的正确性来源——口径仍由语义层决定（§7.3.4），所以把非结构化内容接进来不会让取数更准。新增的代价是两套索引的一致性：结构化侧的刷新与向量侧的重建各有周期，两者不一致时表现为「搜得到、但对不上量」。技术形态在数据湖一侧已有成型章节（03-data-stack/02-data-lake 的 §3.2.5 多模态数据湖），中台一侧的联合接口还没有版本化规范，故记 L3。
- **OneData + GraphRAG（L3）**：图查询与语义层查询没有标准化的联合接口，也没有联合代价模型；实体图谱的价值集中在 OneID 一侧（主文件 §2.1 的 ID-Mapping），而那部分今天用图计算就够了，不需要 LLM。
- **整模型 OneModel 生成（L3）**：一致性约束（粒度、维度、命名、主体标识）必须同时成立，而模型给出的模型「看起来合理但彼此不自洽」，这类缺陷不会报错，只会在下游对账时才暴露。
- **联邦 OneData（L3）**：跨组织的指标交换没有版本化格式，落地要靠合同与人工对齐；它的主导成本项是 §7.4 的 h（跨域查询与协调），而失败面叠加会把多域抖动变成整条查询抖动。
- **AI 原生 OneData（L3）**：作为合并叙事，按最弱组成项（整模型生成 L3、自治 L3）取 L3。主文件 §1.4 的「AI 原生」是历史分期，不是能力清单；把它当清单用，会把三个不同成熟度的东西一起排进路线图。
- **Data Mesh 演进（L2）**：作为组织范式它不是产品，① 无从判定；作为「契约裁决」这条路线，它的承载形态是 catalog（§7.3.1），那部分技术可用。但「Data Mesh 落地效果」的第三方公开判据拿不出，② 不成立。

### 5.3 与本主题既有栈的接口在哪

AI 能力不是新平台，而是挂在既有平台周边的几层。下表写清接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 业务需求 ↔ 指标定义（模型起草） | 单向读：需求文本 + 既有指标清单注入；产出为候选定义，必须落语义层并过评审 | 口径错归语义层 owner（谁维护指标定义谁负责） | 需自建；候选不能直接进生产 |
| 语义层 ↔ 自然语言查询 | 只读：指标名、维度、时间语义、状态枚举；不写回语义层 | 选错指标归语义层覆盖度；越权归平台 | 需自建；覆盖率不够时按分级开放 |
| Agent ↔ 统一 API | 工具协议：参数化调用 + 只读身份 + 指标级授权 + 行级过滤 + 限额 | 越权必须在执行前由工具层拒绝 | 需自建；平台侧多数不认 Agent 身份 |
| 统计检测 ↔ 指标时间序列 | 读：指标序列 + 血缘 + 变更记录；写：告警与工单（不写口径） | 误报归阈值 owner；错误归因归人 | 需自建，但不需要模型 |
| 向量库 / 图谱 ↔ 语义层 | 读：指标文案与元数据做索引与建图；口径变更时必须同步重建 | 检索召回不足归语义层文案质量 | 需自建；索引与口径必须同源 |
| 口径变更 ↔ 计算路径 | AI 增强不新增计算路径，只在消费侧加一层（§7.3.3） | 链路分叉归各链路 owner | 既有约束，必须守住 |

表里最容易出事的是第三行。**Agent 身份缺失时，最省事的做法往往是共享一个高权限账号**——这一步会把前面所有设计一次性作废，而且它不会立刻出问题，只会在某次事故复盘时暴露。

另外两行的失败归属必须在设计阶段写清，否则会退化成扯皮：**口径错归语义层**——把它记成「模型不行」，团队就会去换模型，而问题在指标定义；**召回不足归语义层文案**——把向量库换一遍，不会让指标定义变清楚。

**这张表的自验方法**：任取一个高频指标，沿「提问 → 选指标 → 校验 → 执行 → 回写」走一遍，把每一步的失败归属写下来。写不出归属的那一步，就是将来会扯皮的那一步；而它通常正好是「需自建」的三行之一。

### 5.4 公开进展与文献

- **方法论的公开书面来源**：【公开】《大数据之路：阿里巴巴大数据实践》（2017）记录了 OneModel / OneID / OneService 与公共层建模的形态，是本主题方法论的公开源头，也是「口径必须有一处唯一定义」这个主张的依据。
- **口径裁决路线的公开源头**：【公开】Dehghani「How to Move Beyond a Monolithic Data Lake to a Distributed Data Mesh」（ThoughtWorks，2019；同目录 §7.2「候选方案全景」的表里给出完整标题），它把「域自治 + 平台自助 + 契约治理」写成范式。
- **口径即代码的现实形态**：【公开】dbt Semantic Layer 官方文档与 MetricFlow 开源仓库（MetricFlow 由 Transform 开发、后被 dbt Labs 收购，收购公告发布于 2023 年 2 月；年份以公开公告为准，本仓库另有文件把它记作 2022 年开源，属人工复核项）。
- **取数接口的协议**：【公开】模型上下文协议（Anthropic，2024 年 11 月首次公开，其后有带日期的修订版本）——判断支持情况看规范版本号，不看生态清单。
- **文本转 SQL 的公开基准**：【公开】Spider（EMNLP 2018）与 BIRD（NeurIPS 2023）。用基准成绩选型时，先看它是否公开评测条件：评测集与 schema 规模是否真实、是否允许人工澄清、按「执行结果一致」还是「字符串相似」计分。
- **元数据与血缘的开放规范**：【公开】OpenLineage 的血缘事件规范（Linux Foundation AI & Data 托管，该项目自 2021 年起公开；规范随版本发布，要引用具体版本以该项目仓库的 release 页为准）——它是「口径变更的影响面能被自动算出来」的前置，也是本节多数方向的共同依赖。
- **平台能力的核验面**：【公开】阿里云侧的平台能力（DataWorks / MaxCompute / Hologres）以各产品官方文档与 release note 为准，它们给出的是**能力清单**，不是效果数据——「平台能做什么」看文档就能核，「做了之后值不值」只能拿自己的基线量。
- **值得注意的空白**：本节列不出「第三方（非厂商）在生产中使用 AI 增强 OneData」的公开材料。这不是因为这些方向没用，而是因为这类内部效果数据（口径命中率、返工量）很少公开——它同时意味着：如果你的团队要做，你大概率是早期的一批，收益与风险都得自己承担。同理，原清单里 OneData 1.0 / 2.0 / 3.0 / 4.0 的版本年表在公开材料中查不到，本目录 §7.3.3 已把它降为待复核，本节不把版本号当年表断言。

**引用纪律**：项目名对而会议或年份错，是「某项目在某会议发表论文」这类引用最常见的错误；核验方法是查会议论文集或项目官网的 publications 页，而不是看二手博客。任何「某平台自动生成指标准确率 N%」的说法，先看它有没有给出指标数、schema 规模、是否允许人工澄清等条件。

### 5.5 被过度宣传的部分

**「自然语言一问，指标自动出来」**

- *实际是什么*：换掉的是提问方式与编写者，不是口径的裁决点（5.2.2）。上限由语义层的覆盖率与定义文案决定，而不是由模型规模决定。
- *为什么会这样*：模型的输入只有你给它的元数据；它无法知道「已支付」在你的业务里含不含退款中，因为这条知识从来没有被写下来过（§7.3.4）。
- *什么时候它才会成真*：当高频指标的机器可读属性覆盖到真实查询的覆盖面时。判定方法是抽样真实提问看命中比例（5.2.2 的自验方法），而不是看发布会的演示。

**「AI 自动建模 / 自治中台」**

- *实际是什么*：多数被称为「自治」的能力是统计检测与规则闭环——输入是平台里已有的指标时间序列，与 LLM 无关（5.2.3 的三类拆分）。
- *为什么会这样*：口径裁决是一项**要承担后果的决策**，不是统计问题；模型可以给出候选与解释，但不能承担「这个口径错了由谁负责」。
- *什么时候它才会成真*：当平台文档能明确写出「哪些动作全自动、后果由谁承担、留痕覆盖到哪一步」时；也只有「自动提议 + 人工批准 + 可追溯」这一形态能进生产。

**「Data Mesh / 联邦是复杂组织的解药」**

- *实际是什么*：它把统一从强制降为约定，并新增一项成本——跨域查询与协调（§7.4 的 h 项），同时把跨域失败面叠加起来。
- *为什么会这样*：它解决的是**中心评审成为瓶颈**这个组织问题，不是技术问题。没有这个瓶颈的组织采用它，只会增加协调成本而拿不到收益。
- *什么时候它才会成真*：当域团队能承担契约评审、且平台自助能力（§7.3.4 面向模型的接口）已经建好时。判定方法是清点还有多少 ADS 绕过公共层直读明细。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 机器可读的指标属性成为 AI 取数的显式前置条件 | 产品把「语义层覆盖率 / 属性完整度」写成该功能的开启条件与配置项 | 产品继续只宣传模型能力，取数准确率仍不给评测条件 |
| 权限模型出现「非人主体」这一档，Agent 成为一等身份 | 产品的权限章节新增一类主体对象 + 指标级授权 + 可撤销的会话授权 | 三年后权限仍只有人 / 服务账号两档，Agent 只能借人账号 |
| 口径变更的影响面成为发布门禁的一部分 | 变更流程文档要求附影响面清单与下游通知记录，且可自动校验 | 变更仍靠公告与人工通知，影响面只在事后复盘时才算 |
| 跨组织的指标交换出现带版本的契约格式 | 出现可被多方引用的指标契约规范（含口径、粒度、时间语义、版本） | 跨组织口径仍靠合同文本与人工对齐 |

四条预测都能被**公开文档**证实或证伪，不需要内部数据：

- 第 1 条看功能开关与文档，最可能在一年内见分晓。
- 第 2 条看权限模型的对象类型有没有新增一档，通常三年以上。
- 第 3 条看变更流程文档里有没有「影响面」这一步，一到两年。
- 第 4 条看是否有跨组织规范出现，而不是看是否又发布了一个产品。

提醒一句：这四条预测都不是「某产品会不会做」，而是「**判断依据会不会出现在公开文档里**」。前者无法证伪，后者可以被逐条核对——这正是本节用成熟度分级换掉趋势清单的原因。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 指标已在平台上（千级） | 逐指标补机器可读属性，按查询频次分级开放（§7.3.4） | 产品是否把语义层覆盖率作为功能开启条件 | 不要先买「AI 取数」再补语义层——顺序反了就是给模型喂猜表名 |
| 指标散在各域 ADS 里 | 先定口径裁决落点（跨域消费的指标归公共层，§7.3.1） | 契约评审的质量与覆盖 | 不要用自然语言查询绕过口径统一，它只会把漂移藏得更深 |
| 要给 Agent 开放取数 | 单列只读身份 + 指标级授权 + 限额 + 审计（5.2.4） | 是否出现「Agent 身份」这类权限对象 | 不要共享一个高权限账号图省事 |
| 想上「自治指标平台」 | 先把异常检测与工单闭环做出来（不需要 LLM，5.2.3） | 平台的自动动作是否有审批与留痕说明 | 不要让系统自动改口径或自动下架资产 |
| 业务方催自助取数 | 先做高频指标的覆盖度分级与明确拒答 | 拒答率与命中率的变化 | 不要在覆盖率不足时把它放进面向客户的产品 |
| 团队刚建指标平台 | 先把高频指标的六元组（主文件 §2.2：Name / Definition / Formula / Source / Owner / Version）补齐 | 是否出现覆盖率或属性完整度的配置项 | 不要并行开「自然语言取数」与「AI 生成指标」两个新入口，它们抢的是同一份元数据预算 |

「明确不要做」那一列的共用逻辑只有一句：**本节里真正变了的是口径的起草者与消费接口的朝向，不是口径的裁决点与计算路径**。所以预算应当投在语义层、权限与影响面这三件「平台之外、但决定平台上限」的事上；把它们做完之前，任何「AI 原生 OneData」的选型都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先量**：高频指标有哪些、它们的机器可读属性缺哪些、有多少条 ADS 绕过公共层（§7.3.1 的判定方法）。这三项决定后面所有动作，且不需要新采购。
2. **再补语义层**：按查询频次分级补齐属性与拒答路径。它同时是 5.2.2 与 5.2.4 的前置条件，不改代码就能拿到最大的收益。
3. **然后做权限与身份**：给 Agent 单列只读身份、指标级授权、限额与审计。没有这一步，前两步的成果无法安全地开放给模型。
4. **最后才选产品形态**：产品选型会同时改变口径落点、评审通路与权限模型，是唯一不能快速回滚的一步（见 §7.5 的决策树）。

### 5.8 小结

> 本节小结：AI 在 OneData 上真正改变的只有两处机制——**口径的起草者**从人换成模型（裁决点没变，仍在语义层，§7.3.1），以及**消费接口的朝向**从面向人改成面向模型（§7.3.4）。它**还没有**改变的，是口径的唯一裁决点、计算路径的条数（§7.3.3）与机器可读属性的补全工作量（§7.4 的 f 项，与指标数成正比）。本节没有一行达到 L1——最接近的两行都卡在「第三方（非厂商）公开生产案例」这一条上，所以当下的正确顺序是先做确定性工程（语义层 + 权限 + 影响面），再谈模型。
