## 7. 与其他方法对比

> 原 § 7 共 51 行、为打分表 + 决策树 + 组合罗列，缺少机制解释与可溯源证据，重写为 ~320 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

**打分把场景相关的结论伪装成绝对结论。** 「中心化」这一栏给 5 分还是 1 分，本身没有意义——单一法人主体、数据允许集中时，中心化把口径裁决收敛到一处，**全部收益都来自这一点**；而存在跨法人主体或数据驻留要求时，同一个中心化方案**根本不可实施**，不是「分数低一点」。给「中心化」打分，等于把「你的合规边界决定你能选哪个」这个前提从表里删掉，只留下结论。

**同一维度在规模两端的权重是相反的。** 在百张表量级【经验】，中心评审是一种低成本的质量控制，评审人还读得完每一张表；到十万表量级【经验】，同一套中心评审变成上线路径上的排队点。把两端的分数加权平均，等于假设「评审成本随规模不变」——而它恰恰是本主题下变化最剧烈的量。同理，「表数」这一维度在千表以下【经验】几乎不影响选型，在十万表量级下【经验】会直接决定「元数据能不能靠人工保鲜」。

**打分表回答不了真正要回答的问题。** 读者拿着「阿里 OneData 5 分、Data Mesh 3 分」，仍然不知道：换成另一个要动什么？数据要不要搬？查询要不要改写？已建的调度与权限要不要重建？团队要不要重新学？本章把「迁移成本」单列成 7.7 一节，就是因为它是选型里最容易被忽略、却最难反悔的一项。

**同一个维度在不同约束下的符号可以相反，本主题内就有两个例子。** 「中心化」在单主体、数据可集中的组织里是全部收益的来源；在跨法人主体的集团里是**不可实施**——不是分数低，是方案不存在。「AI 友好」在消费方是分析师时几乎不影响选型（人是靠问同事消歧的），在消费方是 Agent 时它直接决定指标能不能被消费——同一栏 5 分在两种处境下含义完全不同。打分表把这两端压成一个数，读者据此排序，排出来的顺序必然只对其中一种处境成立。

**更实际的害处是它把顺序弄反了。** 打分表的隐含用法是「先比分数、再定方案」，而正确的顺序是**先用硬约束划掉一批候选，再在剩下的候选里比**。数据能不能集中、要不要审计留痕、能不能换栈，这三问的答案来自合规与存量事实，不来自比较——它们问完，候选表通常只剩两三行，比较才真正有意义。

**本章用下面 6 条判据替代评分**，每条判据都是一个必须先用事实回答的问题，而不是一个可以打分的形容词：

**打分表的 5 个维度（易用性 / 中心化 / 灵活性 / AI 友好 / 跨域）没有一个能回答「换成另一个要动什么」。** 而迁移成本恰恰是选型里最难反悔的一项：口径可以改、架构可以调，但数据搬过一次、团队重建过一次技能栈，这些代价都留在组织记忆里——它在打分表这种表达形式里没有位置，所以本章把它单列成 7.7 一节。

**这 6 条判据不是并列打分项：先用两条否决性的把候选划掉，再用其余四条在剩下的候选里比优劣。** 边界与驻留、迁移与曝光成本属于「不满足就出局」；统一的落点、裁决权归属、计算路径条数、消费方形态属于「满足之后比优劣」。下面那张表按「落点 → 边界 → 裁决 → 路径 → 消费方 → 迁移」排列，行序与这个使用顺序无关——被判作否决性的两条在表里分别是第 2 行与第 6 行（第 6 条在 7.8 里被拆成「能不能换栈」与「要不要审计留痕」两问，合起来仍是本条判据）。顺序颠倒的典型后果是：团队花几个月比较三种技术方案，最后发现其中两种因数据驻留要求根本不能选——比较本身没有错，错在它发生得太早。

| 判据 | 问的问题 | 它为什么决定选型 |
| --- | --- | --- |
| 统一的落点 | 「统一」落在规范、代码还是契约上 | 落点决定口径变更要经过几条通路，通路越多，漂移能发生的位置越多 |
| 边界与驻留 | 数据能不能集中到一个湖 | 合规与驻留是硬约束，它直接划掉候选，与成本、性能都无关 |
| 裁决权归属 | 口径由中心裁决还是由域裁决 | 决定评审是否成为业务上线路径上的排队点，也决定谁为口径负责 |
| 计算路径条数 | 需不需要第二条（实时）链路 | 每条链路都是一份口径的候选副本，加一套常驻运维 |
| 消费方形态 | 消费的是人还是模型 | 模型不能靠问人消歧，机器可读属性缺失即等于该指标不存在 |
| 迁移与曝光成本 | 离开它要动什么，以及它把什么暴露给谁 | 存量栈与审计留痕是既成事实；跨域曝光范围是合规事实，都不随选型改变 |

### 7.2 候选方案全景

下表的 10 行分三种角色，不要把它们当成一组可以逐项打分的并列项：**互斥主干**（选一个，4 行）——阿里 OneData 标准模式、开源 OneData 模式、联邦 OneData、Data Mesh 模式；**叠加项**（挂在选定的主干之上、不改变主干，3 行）——实时 OneData 模式、AI 增强 OneData、Data Fabric 形态的自动化采集（这最后一项是平台能力而非治理选择，见下段）；**配套件**（正交组件，只决定主干能否落地，3 行）——Lakehouse 表格式、向量库 / 语义检索层、LLM 消费层。原表的四个打分对象（阿里 OneData / 开源 OneData / Data Mesh / Data Fabric）当时是被平铺在一张表里、按同一组维度打分的；本节把其中 Data Fabric 从主干候选中移出（理由见下段），配套件（表格式、向量库、消费层）在表里被单独归为第三类角色，不参与主干之争，只在 7.6 的「常见组合」里作为「主干之上挂什么」讨论。原表把治理选择（口径由谁裁决）与平台能力（自动化采集）放在同一组维度上打分，读者既看不出哪些选项互斥，也看不出哪些根本不属于同一角色——这正是「比较了半天选不出结论」的一个直接来源。

| 方案 | 家族 | 核心机制（一句话） | 典型使用者 / 触发条件 | 来源与可核验依据 |
| --- | --- | --- | --- | --- |
| 阿里 OneData 标准模式 | 中心裁决 | 口径定义只存在于指标平台一处，分层只引用紧邻下层 | 单主体、可上云托管、需要跨单元可比数字 | 2016 年起推进，公开形态见《大数据之路：阿里巴巴大数据实践》（电子工业出版社，2017）【公开】 |
| 开源 OneData 模式 | 中心裁决（口径即代码） | 口径以文件进版本控制，变更走合并请求，自带审计痕迹 | 已有 Hadoop / Spark 资产、不能换栈、需审计留痕 | dbt Labs「dbt Semantic Layer」官方文档与 MetricFlow 开源仓库，2022 起；dbt Labs 收购 MetricFlow 的开发方 Transform 的公告发布于 2023 年 2 月【公开】 |
| 实时 OneData 模式 | 中心裁决 + 第二链路 | 实时与离线引用同一份度量表达式，差异只剩时间语义 | 决策窗口压缩到分钟级（大促、履约、风控） | 阿里云 Hologres 与 Flink 的官方产品文档可核验该形态 |
| AI 增强 OneData | 中心裁决 + 机器可读接口 | 生成被限制在候选指标集合内，模型不能自造度量表达式 | 消费方是 LLM / Agent，且语义层已存在 | 同类形态见 Databricks Genie 与 Snowflake Cortex 的官方产品文档 |
| 联邦 OneData | 契约裁决（跨边界） | 只统一命名、契约与权限，计算下推到各域，数据不搬 | 跨云、跨国、多法人主体，数据不允许集中 | Databricks Unity Catalog（2021 发布）、Apache Polaris（2024 进入 Apache 孵化器）【公开】 |
| Data Mesh 模式 | 契约裁决（域内） | 口径责任随组织边界落到域团队，平台只提供自助能力 | 域多、变更快，中心团队已无法逐个理解各域语义 | Zhamak Dehghani，"How to Move Beyond a Monolithic Data Lake to a Distributed Data Mesh"，ThoughtWorks，2019【公开】 |
| Data Fabric | 自动化集成 | 以元数据驱动的自动化采集与集成，把多源统一寻址做成平台能力 | 多源多云、需要统一寻址与自动化血缘 | 该术语主要由 Gartner 的分析报告推广，报告名称与年份请以 Gartner 官网当前版本为准 |
| Lakehouse 表格式（Iceberg / Paimon） | 配套件（存储侧） | 表格式提供 ACID 与快照，让多个引擎读同一份数据而不互相污染 | 现代数据栈、多引擎并存 | 可按项目名检索 Apache 官方文档与 Release Note 核验 |
| 向量库 / 语义检索层（LanceDB 等） | 配套件（消费侧） | 按语义而非表名检索指标与先例 | 消费方含模型、指标数量已超出可记忆范围 | 接口与能力以所选组件官方文档当前版本为准 |
| LLM 消费层（通义 LLM 等） | 配套件（消费侧） | 自然语言映射到受约束的指标查询 | 希望业务方不写 SQL 取数 | 厂商产品文档自行核验，注意区分演示与正式发布 |

**Data Fabric 与前面四个主干不属于同一角色。** 它描述的是「用元数据驱动的自动化把多源集成起来」这一**平台能力**，而不是「口径由谁裁决」这一治理选择：它既可服务于中心裁决（自动采集供中心评审），也可服务于契约裁决（自动同步各域契约）。把它当成第四个并列选项，会引出「Data Fabric 与 Data Mesh 该选哪个」这类没有答案的问题——正确的问法是「在我的主干之外，需不需要一层自动化采集与统一寻址」。

**先分族再选，能省掉一半比较。** 上表四个互斥主干之间的差异都落在两条轴上：**裁决权放在哪一族**（中心裁决 / 契约裁决）、**数据能不能跨边界**（集中 / 联邦 / 自治）；两条轴组合起来就是那四个主干——中心裁决 + 集中对应阿里 OneData 标准模式与开源 OneData 模式，契约裁决 + 联邦对应联邦 OneData，契约裁决 + 自治对应 Data Mesh 模式。同族内部（例如「阿里 OneData 标准模式」与「开源 OneData 模式」）差异只在实现载体（托管套件 vs 自建代码）与审计方式上，换族才需要重新设计治理结构。原表把四个候选平铺打分，读者会以为四者可以逐项比较后组合；实际上「阿里 OneData」与「Data Mesh」分属两族，它们之间要比的是**治理结构**（裁决权归属、口径变更要经过几条通路），而不是同一组维度上的高低分——这正是跨族候选并列打分时失效的地方。

**这张表的排序不是市场占有率的排序。** Data Mesh 的实际使用者数量远少于云托管套件，但在「域数已超过中心理解带宽」这一处境下它是唯一解；反过来，域数很少时它是最差解。候选表的价值在于**覆盖处境**，不在于统计谁的用户多——按用户数量选型，等于假设你的处境与多数人相同，而这个假设在本主题下几乎从不成真。

**开放性换来的不只是成本，还有锁定风险的方向。** 托管套件把运维成本换成订阅费用，同时把「离开它」的代价推到最高：口径、调度、权限、血缘都在厂商的产品语义里，迁出要逐项重建；开源模式反过来——离开的代价低，但留在里面的代价是自建组件的运维人天【经验】。这两者不能同时最优化，只能选你更能承受的那一种锁定：**是被人锁定，还是被自己的人力锁定**。

**候选之间有三种关系，混在一起就会选出不成立的组合。** 一是**互斥**：阿里 OneData 标准模式与 Data Mesh 不能同时作为主干（前者要求中心裁决，后者要求域裁决）；把它们写成「两者结合」时，实际形态是「中心裁决限定在公共层、域裁决限定在域内」，也就是 7.6 组合三，而不是两个主干相加。二是**叠加**：实时模式、AI 增强层、Data Fabric 形态的自动采集都是在某一主干之上叠加的能力，叠加改变的是链路条数与消费接口，**不改变主干**——其中 Data Fabric 是平台能力而非治理选择，因此它不构成第四个主干候选。三是**正交配套**：Lakehouse 表格式、向量库、LLM 消费层与任一主干都可以组合，它们不参与「裁决权放在哪一族」的争论。

### 7.3 机制差异：为什么它们表现不同（核心节）

本节按 4 个机制维度展开。每个维度都给出「因为 A，所以 B，代价是 C」的因果链，并说明它在什么条件下失效。判据与用词与 [§ 3 设计模式与范式](15-one-data-section-3-sec3.md) 保持一致。

**四个维度不是并列的四张考卷。** 7.3.1（统一的落点）决定治理成本，7.3.2（数据边界）是硬约束，这两个是**选型维度**——它们决定你选哪一个主干；7.3.3（计算路径条数）决定运维工作量，7.3.4（消费接口）决定消费方能不能自助，这两个是**叠加维度**——它们决定你在选定的主干上再加什么。把四个都当选型维度，就会出现「选了 Mesh 又要求中心统一口径」这类互相抵消的组合。

#### 7.3.1 统一的落点：规范裁决、代码裁决还是契约裁决

**机制是什么**：口径的唯一定义被放在哪里——中心的规范与平台里、版本控制的代码文件里、还是域之间约定的契约里。这个落点决定了**口径变更必须经过几条通路**。

| 候选 | 落点 | 变更通路 | 审计痕迹 |
| --- | --- | --- | --- |
| 阿里 OneData 标准模式 | 指标平台（中心） | 提需求 → 中心建模评审 → 平台改定义 → 下游生效 | 平台内变更记录 |
| 开源 OneData 模式 | 语义层文件（代码库） | 改文件 → 合并请求 → 评审 → 发布 | 版本控制天然完整 |
| 联邦 / Data Mesh | 契约（catalog 登记 / data product 契约） | 域内改 → 契约评审 → 消费方按契约适配 | 契约版本与评审记录 |

**由此必然导出的性质**：因为标准模式把口径定义收敛到平台一处，**所以**两个业务不可能在各自的 ADS 里各写一版过滤条件，口径漂移在结构上失去了发生的位置；**代价是**中心建模团队成为每一条口径变更的通路上一站，新增公共模型要排队评审。因为契约裁决把定义权连同责任交给域，**所以**中心不再是瓶颈，**代价是**「统一」的强度从强制降为约定，跨域一致性依赖契约评审的质量——评审一旦松懈，域各自的方言会重新长出来，而这一次没有中心规范可以对照。

**公开证据**：口径即代码这一路线的现实形态可由 dbt Labs「dbt Semantic Layer」官方文档与 MetricFlow 开源仓库核验（2022 起；MetricFlow 由 Transform 开发并开源，后被 dbt Labs 收购，收购公告发布于 2023 年 2 月——本仓库另有文件把它记作 2022 年开源，见 04-data-assetization/10-metric-platform，年份以公开公告为准，列为人工复核项）【公开】。契约裁决路线的承载形态是 Unity Catalog（2021）与 Apache Polaris（2024）这类 catalog【公开】。阿里口径一致率与复用率的**具体数值阿里未公开**，本文不做数字推断【经验】。

**审计痕迹的差别值得单列一句**：因为口径以文件形式进版本控制时，任何变更都必须经过一次合并请求，**所以**「谁在什么时候、以什么理由改了 gmv」天然留下记录；托管平台上改口径往往只是一次点击，要留下同等记录得额外埋点。这不是谁做得更好，而是落点差异的必然结果——把它读成「开源更规范」的评价，就会错过这条判据真正在量的是什么。

**失效条件**：当业务变更速度持续快于中心评审周期时，规范裁决的优势消失——域团队绕过公共层自建 ADS 的当期收益（今天就能上线）大于遵守规范的远期收益（口径统一），而远期收益无法进入当期排期【经验】。判断方法（可自行核验）：清点有多少 ADS 直接引用明细层而非公共汇总层。

**现实中更常见的是混合落点，而它需要说清分工。** 形态是「中心公共层 + 域内语义层」：公共层负责跨域可比的主体与公共模型（OneID、公共 DWS），域负责域内指标与看板。这样能在不放弃跨域可比的前提下把域内变更的通路缩短。**代价是**双落点必须划清边界——边界一旦模糊，同一个指标会同时出现在公共层与域内，变成两份定义；划分规则通常写成「跨域消费的指标归公共层，域内自用的归域」【经验】。

**判定方法（可自行核验）**：任取一个高频指标，在代码库、平台配置与看板定义里搜索它的过滤条件；出现超过一处，即说明口径已不再是唯一裁决——无论文档上写的是哪一种落点。

#### 7.3.2 数据要不要跨边界移动

**机制是什么**：统一的是**数据本身**，还是**数据的名字与契约**。集中式把数据搬到一处再统一加工；联邦与 Mesh 让数据留在域内，只统一可寻址的元数据与接口。

**它在各候选中的实现差异**：

- 阿里 OneData 标准模式：数据集中在同一计算平台，跨域 JOIN 是本地操作，延迟与失败面等于单个平台。
- 联邦 OneData：catalog 只登记位置与权限，计算下推到各域，只回传结果或聚合值。
- Data Mesh：消费只通过 data product 契约，不允许跨域直读物理表，跨域组合由消费方在自己的域内完成。

**由此必然导出的性质**：因为联邦只让元数据与契约跨越边界、数据不出域，**所以**「数据驻留合规」与「跨域可比口径」这两个原本对立的目标可以同时成立；**代价是**跨域查询的延迟与失败面等于各域之和，命名与类型对齐需要持续仲裁——一个域改字段类型、另一个域会静默出错。因为集中式让数据在同一处，**所以**跨域分析没有额外的网络与协调成本；**代价是**它把「能不能集中」变成一道前置闸门，闸门不过，后面所有技术讨论都是空的。

**公开证据**：Dehghani 的 Data Mesh 论文（ThoughtWorks，2019）把「域自治 + 平台自助 + 契约治理」写成范式，是契约裁决路线的公开源头【公开】。联邦形态的技术承载为 Unity Catalog（2021）与 Apache Polaris（2024）【公开】。

**失效条件**：当跨域需求从「口径级一致」升级到「行级实时一致」时，联邦反转成反复搬运数据——因为联邦的机制是数据不动、计算动，而行级实时一致要求计算贴着数据做，跨域时无法下推，只能同步副本。

**集中式的隐性前提是「同一份事实只被加工一次」**，而这要求跨域的主体标识先统一（OneID 的 ID-Mapping）：主体没统一时，跨域 JOIN 得到的是「同一个人被算成两个人」的结果，而这类错误不会报错，只会让所有以主体为粒度的指标基数虚高。因此集中式并非「把数据放到一起就自动统一」，它只是把统一的任务前移到了主体标识上。

**判定方法（可自行核验）**：把「跨域查询」的清单拉出来，逐条问「这条查询的数据是否离开了原域」。若答案与合规清单不一致，说明选型与合规事实已经脱节——此时换技术方案解决不了问题，要改的是边界设计。

#### 7.3.3 计算路径有几条

**机制是什么**：同一指标存在几条独立的代码路径。批链路是一条，叠加实时链路就是两条——两条路径就是两份口径的候选副本。

**它在各候选中的实现差异**：标准模式与联邦模式默认单条（批）路径；实时 OneData 模式显式维护两条路径并强制它们引用同一份度量表达式；AI 增强模式不新增计算路径，但在消费侧新增一层（检索 + 校验）。

**由此必然导出的性质**：因为实时与离线共用同一份度量表达式，**所以**两条链路的差异被压缩到「时间语义与迟到数据处理」这类可在对账里被发现的技术性差异；**代价是**同一指标要养两套运维（状态管理、检查点、背压、回补）与两种技能，且实时层为低延迟通常常驻内存，单位数据的计算成本高于批。反过来，如果两条链路各写一遍 `SUM(x) WHERE y`，两者的差异是**算法差异**，没人能靠肉眼发现——它不会以「发现不一致」的方式暴露，而是以「业务不再信任数据」的方式暴露。

**公开证据**：阿里把实时链路并入统一建模的形态（流计算 + 实时数仓 + 实时指标平台）可对照阿里云 Hologres 与 Flink 的官方产品文档核验【经验】。需要说明：OneData「1.0 / 2.0 / 3.0 / 4.0」的版本年表在公开材料中查不到，且项目内不同章节对同一版本的记法也不一致（01-modeling/08-one-data 把它记成 2018–2020 区间，本目录 §5 已按此不记年份），因此本文只按「批次 → 实时 → AI」的阶段描述，不把版本号当年表断言【经验】。

**失效条件**：当实时链路的延迟压力大到有人在流任务里手写口径时（例如为减少回刷临时加一个过滤条件），「一份口径」反转成「两份口径加一个看起来一致的假象」——因为对账通常只比总量，偏差会长期隐藏在小类目、退款与跨天迟到数据里。

**第二条链路真正贵的地方在技能，不在机器。** 流任务的调试靠状态与检查点，批任务靠重跑分区，两套心智模型不同；因此叠加实时链路之前，应先确认团队里有人能独立处理背压与状态膨胀。没有这个人时，实时链路会以「偶发数据不对但复现不了」的形式长期消耗团队，而不是以一次明显的事故暴露出来【经验】。

**判定方法（可自行核验）**：比较两条链路的度量表达式来源；实时链路里若存在手写过滤条件，即已分叉。再检查对账任务是否覆盖长尾维度——只比总量的对账是分叉的掩护，不是分叉的检测。

#### 7.3.4 消费接口：面向人还是面向模型

**机制是什么**：指标口径以什么形态对外——给人读的文档与看板，还是机器可读的结构化定义（唯一名字、语义类型、粒度、时间维度、owner、版本）。这决定了消费方能不能不靠人消歧。

**它在各候选中的实现差异**：标准模式的接口是看板与数据集；开源模式是语义层查询 API；AI 增强模式在语义层之上加一层「检索 → 候选 → 校验」回路；配套件里的向量库与 LLM 都只是这层回路的组件。

**由此必然导出的性质**：因为生成环节被限制在「从候选指标里选」，而不是「自由写公式」，**所以**模型的错误被压缩成「选错指标」这一类可在结果里被发现的问题，而不是「编出一个看起来合理的口径」这一类无人能发现的问题；**代价是**每个指标都要补齐机器可读属性，工作量与指标数量成正比，且必须在开放给模型之前完成——属性缺失的指标在检索里等同于不存在。

**公开证据**：面向模型的语义层与自然语言查询接口，可由 Databricks Genie 与 Snowflake Cortex 的官方产品文档核验；阿里云侧「语义层 + 自然语言查询」的产品形态出现在 2024 年前后（本目录 §4、§5 记为「通义数智」），该名称与版本号本文无法在公开材料中逐条核验，降为待复核，不作公开断言【经验】。

**覆盖率不够时的正确做法是分级，不是推迟。** 把指标按查询频次分成两档——高频（例如支撑核心看板与对外报表的指标）先补齐机器可读属性并开放给模型，长尾指标暂不开放、遇查询时明确拒答。**因为**模型在候选不足时会用最相似的可用指标近似，**所以**「部分开放 + 明确拒答」严格优于「全部开放」；代价是需要维护一份「当前已开放」的清单，并在拒绝时给出替代路径。

**失效条件**：当语义层对高频指标的覆盖率低于实际查询的覆盖面时，AI 自动取数反转成「看起来对但口径错」——模型在候选不足时倾向用最相似的可用指标填空。判断方法（可自行核验）：抽样约 20 个业务提问，人工认定正确答案对应的指标，再看系统命中的是否为同一个，命中比例即覆盖率的下界。

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本分五项（固定平台成本加上下面四个成本函数项），各候选的差别**不在单价，而在哪一项是主导项、哪一项被记在了别人账上**：

```
总成本 ≈ 固定平台成本（集群 / 套件 / 常设团队）
       + f(表数与字段数)          —— 元数据与血缘由谁来维护
       + g(口径变更次数 × 评审路径长度) —— 治理的通路成本
       + h(域数 × 跨域查询次数)     —— 跨边界的网络与协调成本
       + i(计算路径条数)           —— 每条路径的常驻运维
```

**主导项与隐性成本，逐个候选看**：

- **阿里 OneData 标准模式**：主导项是固定平台成本与 `g`（评审路径长）；隐性成本是「公共层覆盖不到的长尾需求」——它们不体现为账单，而体现为域团队自建 ADS 的重复开发。
- **开源 OneData 模式**：把固定平台成本从「许可费」换成「运维人天」。同一份能力由 5 个以上自建组件拼成时，人天是主导项，且它随组件数线性增长，不随数据量增长【经验】。
- **实时 OneData 模式**：主导项是 `i`（第二条链路的常驻运维），且实时侧的成本随**活跃键数（维度基数）**增长，而不是随数据量增长——因为流任务要维护窗口状态，状态大小由窗口内活跃键数与每键状态字节数决定，与事件到达速率无关。
- **AI 增强 OneData**：主导项是 `f` 的一部分——逐指标补机器可读属性，工作量与指标数成正比，且必须在开放前一次性补齐；这笔投入在指标数以百计时是可接受的，在数以万计时需要先做覆盖度分级。
- **联邦 / Data Mesh**：主导项是 `h` 与契约仲裁的人力；隐性成本是跨域查询的**失败面叠加**（一个域的抖动会变成整条查询的抖动）。

**把「谁承担哪一项」写下来，选型才会变清楚**——同一项成本由不同的人承担，会导向完全不同的谈判结果：

| 候选 | 主导项 | 最容易被记在别人账上的成本 | 该项成本的实际承担者 |
| --- | --- | --- | --- |
| 阿里 OneData 标准模式 | 固定平台成本 + `g`（评审通路） | 公共层覆盖不到长尾需求导致的重复开发 | 域团队 |
| 开源 OneData 模式 | 自建组件的运维人天（随组件数线性增长） | 组件间版本耦合带来的联合升级窗口 | 平台团队 + 所有引用方 |
| 实时 OneData 模式 | `i`（第二条链路的常驻运维） | 两套技能并存的招聘与排班压力 | 团队负责人 |
| AI 增强 OneData | `f` 中的机器可读属性补全 | 属性缺失的指标在检索里等同「不存在」导致的取数失败 | 业务方 |
| 联邦 OneData | `h`（跨域查询与协调） | 跨域失败面叠加带来的排障复杂度 | 值班团队 |
| Data Mesh 模式 | 契约仲裁人力 + 平台自助能力建设 | 域各自采购工具造成的第二套烟囱 | 域团队 + 财务 |

**一个【推算】示例（元数据本身的成本可以忽略，元数据操作次数才是主导项）**：设一个中台有 10 万张表、每张表平均 50 个字段，则字段级条目约 500 万条；按每条条目含名称、类型、描述与血缘边约 1 KB 估算，元数据本体约 5 GB 量级。按对象存储标准层 $0.023/GB-月推算，5 GB 的存储月成本约 $0.12（推导链：5 GB × $0.023/GB-月），相对下面要说的操作量可以忽略【推算】。但 SQL 解析、血缘刷新、发布门禁校验这些**操作**随「表数 × 变更频率」增长——10 万张表、每表每月变更数次（按 2–5 次估），即每月数十万次（10 万 × 2–5）元数据写与索引更新，这才是元数据侧真正会咬人的成本项。推导链：存储量 = 条目数 × 单条字节数（随表数线性、不随变更频率增长）；操作量 = 表数 × 单位时间变更次数（随两者乘积增长）。前者是一次性的 GB 级存量，后者随时间持续累积，因此在表数足够大时主导项必然是后者【推算】。

**一个【推算】示例（实时链路的状态成本随维度基数增长，而不是随数据量增长）**：设某实时汇总做 1 万个键的窗口聚合，每个键的状态（累计值、计数、时间戳等）约 100 字节，则常驻状态约 1 MB 量级；把键换成 100 万（例如维度从类目下钻到商品），状态放大到约 100 MB 量级。推导链：状态规模 ≈ 窗口内活跃键数 × 每键状态字节数，**与事件到达速率无关**，而事件速率正是决定数据量的那个量【推算】。这解释了为什么实时链路的扩容常常不是加机器就够，而要先收敛维度基数。

**一个【推算】示例（治理通路成本随评审路径长度线性增长）**：设一次口径变更从提出到生效要经过 k 个必经环节（域内评估、中心建模评审、平台变更、回归验证），每个环节平均等待 1 个工作日，则生效周期下限约为 k 个工作日；去掉中心评审这一环（改为域内裁决），k 减少 1，生效周期下限同比下降 1/k。推导链：生效周期 ≥ 环节数 × 单环节等待时间，而环节数由 7.3.1 的落点决定【推算】。治理成本不体现在账单上，它体现为**业务等口径的时间**——这正是「口径裁决权在谁手上」能成为本章唯一主线的原因：它同时决定 `g` 这一项的大小。

**这个成本函数的用法是排序，不是算总额。** 评审时不必把五项都折算成钱，只需要回答三件事：我的规模下哪一项最大、它在未来一年以什么速度增长、以及它落在谁的预算里。能回答这三问的讨论通常比逐项报价更快收敛，也更容易在半年后复盘——因为当初的判断依据被写下来了【经验】。

**五项成本里，最容易被记到别人账上的是 `g`。** 它不出现在平台账单里，而出现在域团队「等口径评审」的工期与「绕过公共层自建 ADS」的重复开发里。因此若只比较平台费用与人力编制，`g` 会被系统性低估，最终以「公共层没人用」的形式暴露出来。

**规模跃迁时主导项会换人。** 千表以下，主导项通常是固定平台成本（人比机器贵）；千表到十万表之间，`f` 里元数据的维护开始主导，人工登记难以保鲜，自动采集（SQL 解析）从「优化」变成「必需」；十万表以上，`g` 的评审通路成本成为瓶颈，此时要么扩大中心建模团队，要么把裁决权下放——而扩大团队只是把瓶颈推后，不改变机制【经验】。

### 7.5 决策树

下面每个判断节点都在「阈值依据」里有对应条目（编号一一对应）。树的顺序是刻意的：**先问硬约束，再问组织，最后才问技术**——前两类问题的答案会直接划掉候选，先问技术只会得到一堆需要推翻的结论。

```text
① 数据能否集中到一个湖？（驻留 / 跨法人 / 跨云）
   ├─ 不能 → 联邦 OneData：只统一命名、契约与权限，数据不出域
   └─ 能 ↓

② 中心团队还能逐个理解各域的口径细节吗？（域数门槛）
   ├─ 不能 → Data Mesh 模式：裁决权连同责任下放，先补齐平台自助能力
   └─ 能 ↓

③ 允许更换现有数据栈吗？需要审计留痕吗？
   ├─ 不能换栈 / 需要审计留痕 → 开源 OneData 模式：口径即代码
   └─ 可换栈 / 可用托管套件 → 阿里 OneData 标准模式

④ 决策窗口是否已压缩到分钟级？
   ├─ 是 → 在③选定的主干上叠加实时 OneData（批流双链路 + 每日对账）
   └─ 否 ↓

⑤ 消费方里是否已有 LLM / Agent 需要自助取数？
   ├─ 是 → 叠加 AI 增强层（语义层 + 检索 + 校验回路），不新增计算路径
   └─ 否 ↓

⑥ 是否需要跨多云统一寻址与自动化血缘采集？
   ├─ 是 → 叠加 Data Fabric 形态的 catalog 与自动采集
   └─ 否 → 维持③选定的主干，按 § 3.6 的跃迁表定期复核
```

**阈值依据**（与树上编号一一对应）：

- **① 能否集中**：这不是阈值而是硬约束，依据是法律与合规事实（数据驻留、法人边界），不由成本或规模导出。判断方法：由法务或合规给出「哪些数据不得离开哪个司法辖区」的书面清单，而不是由架构师凭印象判断。
- **② 域数门槛（约 10 个域以上）**：依据是组织结构约束——中心团队的人数有限，逐个理解一份域的口径细节需要持续投入；超过约 10 个域后，中心评审会稳定地滞后于域的业务节奏，此为经验区间，**不是公开统计数字**【经验】。判断方法：统计近三个月的口径变更请求从提交到生效的中位等待时间，若持续长于域自身的发版周期，即已越过门槛。
- **③ 是否允许换栈**：依据是既成事实而非阈值——存量 Hadoop / Spark 资产、已有的调度与权限体系、以及「口径变更必须留下可审计痕迹」的合规要求，这三项都不随选型改变。判断方法：问一次「把现有任务全部迁到托管套件需要几个月、谁做」，答案超过团队可承受范围即视为不能换栈。
- **④ 分钟级决策窗口**：依据是物理约束——T+1 批链路在当天拿不到数，不是「慢一点」。当业务动作（补货、限流、风控拦截）的反馈周期短于批链路的产出周期时，该节点必然为「是」。
- **⑤ LLM / Agent 自助取数**：依据是消费方形态变化，不是覆盖率阈值。真正的阈值在叠加之后：语义层对高频指标的覆盖率需先达到可接受水平（可用 7.3.4 的 20 问抽样法给出下界），否则叠加会得到「看起来对但口径错」。
- **⑥ 跨多云统一寻址**：依据是环境事实——同时存在两个以上云或引擎、且需要一份统一的血缘与权限清单时，自动化采集的成本低于人工维护。判断方法：清点当前有多少个互不相通的元数据源，超过可人工维护的数量（通常是个位数）即需要自动化。

**树的读法是「从上往下删」，不是「从下往上比」。** ① 与 ② 会直接否掉一整类主干（不能集中就否掉集中式；中心读不完各域就否掉中心裁决），③ 在剩下的主干里二选一，④⑤⑥ 则是在选定主干上做叠加。还要注意 ① 与 ② 的**问题对象不同**：① 问的是数据（能不能搬），② 问的是人（中心还读不读得完）——一个组织完全可能数据能集中、但中心已经读不完各域语义，此时正确结论仍然是下放裁决权，而不是「既然能集中就集中」。

**树上的分支多少与组织规模无关，与约束多少有关。** 一个 30 人的公司若同时有跨法人主体与实时需求，同样会走到 ① 和 ④；反过来，一个上万人的企业若域数很少、数据可集中，也只走到 ③。这也是本章不给「按团队规模选模式」的原因——规模影响的是阈值何时被越过，不是路径本身【经验】。

**这棵树不回答的两件事**：一是「这次统一值不值得做」（那是投资决策，取决于口径不一致当前造成的损失规模）；二是「谁来做」（那是组织决策，见 7.6 组合三与 7.5 节点②）。把这两件事塞进决策树，会让树长得无法使用，而它们本来该由另一场评审回答。

**阈值要定期复核，因为节点②的答案会随时间变化。** 域数只增不减是常态，一个三年前答案在「能」的组织，今天可能已经在「不能」一侧——而组织通常不会因为域数增长而主动重跑一次选型评审。因此建议给节点②设一个固定的复核节奏（例如每半年重跑一次 7.5 的①与②），并在域数或口径变更等待时间触发阈值时提前触发。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 单主体、域少、口径需中心可比 | 阿里 OneData 标准模式 | 开源 OneData 模式 | 不选 Mesh：域数不够时自治只带来重复建设，没有收益 |
| 不能换栈、需审计留痕 | 开源 OneData 模式 | 标准模式 | 托管套件换不来已有资产与合规要求，迁移期本身是风险 |
| 决策窗口分钟级 | 实时 OneData 模式 | 标准模式 + 准实时补数 | 不选纯批：T+1 不是慢，是当天拿不到数 |
| 消费方是模型 | AI 增强 OneData | 语义层 + 人工取数 | 不选文档：模型读不了文档，只能猜表名与口径 |
| 数据不能集中 | 联邦 OneData | Mesh + 联邦 | 不选集中式：合规上不可实施，与技术优劣无关 |
| 域多、节奏快、平台已就绪 | Data Mesh | 联邦 + 域内标准模式 | 不选中心裁决：中心无法逐个理解各域语义，必然排队 |
| 多源多云、需要统一寻址 | Data Fabric 形态的 catalog | 联邦 OneData | 不选纯手工：元数据源数量超过人工维护上限后会持续过期 |

**备选列不是「也可以」，而是「主干某项前提不成立时的替代路径」。** 例如「决策窗口分钟级」这一行，备选写「标准模式 + 准实时补数」——它适用于实时需求只覆盖少数看板、不值得为此养第二条链路的场合。把备选当成并列推荐，会退回到打分表的思路；它的作用是在你发现自己对某个前提判断错误时，给出代价最小的一步退路。

**常见组合**（原列的 4 组全部保留，每组说明职责边界与运维代价）：

- **组合一：主干 + Lakehouse 表格式（Iceberg / Paimon）**。职责边界：表格式负责存储层的 ACID 与快照，使多个引擎读同一份数据而不互相污染；OneData 负责口径与分层，**不把口径写进表格式的元数据**。运维代价：多一个组件、多一套版本升级节奏，且表格式的小文件与清单维护需要定期作业——它与 § 3.6 的「千表 → 十万表」跃迁同时变贵。
- **组合二：主干 + 向量库 / 语义检索层（LanceDB 等）**。职责边界：向量库只负责**检索召回**，口径与权限判定仍在语义层，命中后必须回到语义层校验。运维代价：多一份需要与指标定义同步的索引，指标一变索引就要重建，否则检索返回过期口径。
- **组合三：主干 + Data Mesh（中心化公共层 + 域自治）**。职责边界：公共层提供跨域可比的公共模型与指标，域团队在域内拥有 data product 与自己的 schema。运维代价：两类治理议题叠加（公共层评审 + 契约评审），且必须先把平台的调度、目录、权限做到位，否则自治会退化为各建一套。
- **组合四：主干 + AI 原生消费（LLM 消费层）**。职责边界：语义层是唯一入口，LLM 只做自然语言到指标的映射，**不新增口径**。运维代价：逐指标补机器可读属性的工作量与指标数成正比，且必须在开放给模型之前完成；这决定了它的推进节奏由指标治理进度决定，而不是由模型能力决定。

**组合的运维代价不是相加，而是相乘。** 每多挂一个组件（表格式、流引擎、向量库、catalog），就多一条版本升级路径、多一次跨组件的兼容性验证；真正的成本高点是「必须同时升级」的时刻——例如语义层引擎升级会波及所有引用它的任务。因此组合数量应当有上限：多数团队在 3–5 个常驻组件之后，升级窗口开始无法在一个季度内排完【经验】。

**本主题下最常被误选的一对，是「阿里 OneData 标准模式」与「Data Mesh」。** 两种误选都有具体后果（下列域数门槛为经验区间，非公开统计数字【经验】）：只有三五个域就抄 Mesh，会把「统一口径」从一次中心评审变成五份契约协商，跨域一致性反而更差，且每个域都要自己养一套平台能力；已有几十个域、每个域变更以周计却硬撑中心化评审，则公共层成为排队瓶颈，域团队开始绕过它自建 ADS——绕过一旦开始，公共层的复用率与可信度同时下降，系统变成「名义上的 OneData + 事实上的烟囱」。判断该不该换的那条判据是：**中心团队是否还能逐个理解各域的口径细节**；还能，就该集中；不能，就必须把裁决权连同责任一起下放，并先补齐平台能力。

**组合的排序原则**：先定主干（7.5 的节点①②③），再叠加（节点④⑤⑥），最后挂配套件（组合一、二、四）。顺序反过来——先挂向量库或先上表格式——会得到一个「有 AI 但没有口径」的体系：检索能在过期口径上飞快地返回答案，而这比检索不到更危险。

### 7.7 选错的代价与迁移成本

**反模式：先选栈，再补统一。** 症状 —— 决策起点是「买哪套平台」，统一口径被写成上线后的待办。后果 —— 套件买到了，但各域的 ADS 仍然各写一版过滤条件，于是得到「昂贵的烟囱」：工具是统一的，口径不是。机制上，平台提供的是**能力**，口径唯一性来自**裁决权与通路设计**，前者不能推出后者。正确做法：先确定口径的唯一裁决点（平台、代码库还是契约），再据此选工具。

**反模式：三五个域就抄 Data Mesh。** 症状 —— 团队少、域少，却先把「域自治 + 契约治理」铺开。后果 —— 「统一口径」从一次中心评审变成五份契约协商，跨域一致性反而更差，且每个域都要自己养一套平台能力。机制上，自治的收益来自「域的数量超过中心的理解带宽」，域不够多时这项收益为负：协调成本上升，而没有换回任何东西【经验】。正确做法：先用「中心团队是否还能逐个理解各域口径细节」这条判据确认是否越过了门槛（见 7.5 节点②）。

**反模式：在实时链路里手写口径。** 症状 —— 为减少回刷或压延迟，在某条流任务里临时加了过滤条件。后果 —— 同一指标出现两个值，且**差异藏在长尾维度**（小类目、退款、跨天迟到数据），总量抽查发现不了，直到某次汇报口径被质疑，团队才发现两条链路早已分叉。正确做法：度量表达式只有一份来源，实时链路不允许出现手写过滤条件；同时保留覆盖长尾维度的每日对账。

**三个反模式有一个共同点：都把「技术选择」当成了唯一可以选择的变量。** 事实上选型里能被选的不只是工具，还有**裁决权放在哪里、评审路径有多长、口径定义在几处**——这三样里任意一样改动，都会改变同一个工具的实际表现。反过来，只换工具而不动这三样，得到的通常是与原来相同的结果和一张更大的账单。

**换成另一个要动什么**（工作量量级为相对比较，不是工期承诺）：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 标准模式 → 开源模式 | 无（同存储） | 中（SQL 迁到新引擎方言） | 高（5 个以上组件自建） | 中 |
| 标准模式 → 实时模式 | 无（新增链路） | 低（实时侧新增） | 中（多一套流运维） | 高（需流与批两种技能） |
| 集中 → 联邦 | 低（数据留在原处） | 高（跨域查询改为下推） | 中（新增 catalog 与仲裁） | 中 |
| 中心裁决 → Mesh | 无 | 中（消费改为走契约） | 高（平台自助能力先补齐） | 高（组织与责任边界变化） |
| 任一 → AI 增强 | 无 | 无 | 低（叠加检索与校验） | 中（指标要补机器可读属性） |

**迁移成本是不对称的，方向比目标更重要。** 从集中式迁向联邦，数据不搬但查询要改写，成本集中在工程侧；从联邦迁回集中式，数据要搬，成本集中在合规与协调侧，而且可能根本不被允许。因此当两类方案的收益接近时，选「取消起来更容易」的那一个——把不可逆性本身当成一项判据。

**迁移的顺序比迁移的工作量更决定成败。** 上表按四个维度给出了工作量量级，但真正会拖垮项目的是顺序：应先收敛口径定义（把度量表达式抽到一处并确定裁决点），再迁计算与查询，最后才动运维与组织边界。顺序反过来——先迁计算再收敛口径——会在迁移期内同时维护两份口径，把「一次迁移」变成「一次迁移 + 一次口径对账」。

**推进顺序上有一条可复用的最小路径**（任何迁移方向都适用）：

1. **先收敛口径**：任选 3–5 个最高频指标，把度量表达式抽到一处并指定 owner；这一步不迁任何计算，只解决「口径有几份」。
2. **再迁计算与查询**：把消费方（看板、报表、API）切到收敛后的口径上；此时新老链路并存，靠对账保证一致，且对账必须覆盖长尾维度。
3. **最后动运维与组织边界**：换引擎、换调度、改裁决权归属属于这一步。放在最后，是因为前两步完成后，第三步的收益与代价才可度量；放在最前，则会同时面对口径分叉与平台不稳两件事。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 单主体、域少、口径需中心可比 | 阿里 OneData 标准模式 | 口径唯一裁决点 + 不跨层引用，漂移在结构上无处发生 |
| 不能换栈、需要审计留痕 | 开源 OneData 模式 | 口径即代码，变更走版本控制，自带审计痕迹 |
| 决策窗口分钟级 | 实时 OneData 模式 | 实时与离线共用一份度量表达式，差异只剩时间语义 |
| 消费方是模型 | AI 增强 OneData | 生成被限制在候选集合内，错误从「编口径」降级为「选错指标」 |
| 数据不能集中 | 联邦 OneData | 只统一契约与命名，数据不出域，合规与跨域可比同时成立 |
| 域多、节奏快、平台已就绪 | Data Mesh 模式 | 口径责任随组织边界落到具体团队，不再需要跨团队协调 |
| 多源多云、需要统一寻址 | Data Fabric 形态的 catalog | 元数据自动采集，把「谁能找到谁」从人的记忆换成平台能力 |
| 消费方仍是分析师、无实时需求 | 标准模式 + 语义层 | 口径唯一裁决点已足够，再叠加只增加运维面而不改变结论 |
| 已有大量 Hadoop 资产且口径事故频繁 | 开源 OneData 模式 | 审计留痕来自版本控制，是事故复盘与追责的前提 |

**不要按分数选，按顺序删。** 本主题的候选里有三条硬约束（能不能集中、能不能换栈、要不要审计留痕），它们与候选优劣无关，只与你的合规与存量事实有关；先用它们删掉不成立的候选，剩下的通常只有两三个，再按机制契合度选。这样做还有一个副作用是好的：删掉的理由是可复核的事实（合规清单、存量系统清单），而打分的理由是不可复核的印象——前者在半年后换人重做时仍然成立。

> 本节小结：本主题下真正起决定作用的**只有一条差异——口径的裁决权在谁手上，以及它能否覆盖业务的变更速度**。中心覆盖得了就集中，覆盖不了就把裁决权连同责任一起下放给域，并先补齐平台能力。数据能不能集中只决定「统一的是数据还是契约」，时效只决定「要不要第二条链路」，消费方形态只决定「接口要不要机器可读」——这三条都会改变方案的形态，但都不会改变上面这条主线。
