## 3. 设计模式与范式

> 原 § 3 共 75 行、为模式表格（6 个模式 + 5 个反模式的名称清单），缺少结构示意、机制解释与失效分析，重写为 ~310 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

**OneData 的模式差异，本质不是技术栈差异，而是「统一这件事被放在哪一层做」。** 阿里标准模式把统一放在建模规范与分层上，开源模式把统一放在语义层代码里，实时模式把统一放在同一份口径定义上，联邦模式把统一放在 catalog 的命名与契约上，Data Mesh 把统一放在 data product 契约上。技术栈（MaxCompute / Hive / Flink / Unity Catalog）是这个选择的结果，不是原因——先选栈再补统一，就会出现「买了套件但口径仍然各写各的」。

**下面 7 条约束里，最要紧的三件互相拉扯：口径由谁裁决、数据能不能集中、时效要多快。** 三件事任意一件不同，同一业务场景的正确模式就不同：同一个「实时看板」需求，在单主体公司里是「实时 OneData」，在跨主体集团里必须先解决「哪些域允许数据出域」，否则实时链路根本搭不起来——此时它已经不是技术选型问题。

**约束决定失效线，这是本节最想传递的一点。** 下面每个模式的失效点都写成「当某个约束变化时」——规模、变更频率、一致性要求、团队运维能力任一条越过阈值，原来正确的模式就变成错的。模式不是选一次就完了，3.6 给的是换挡信号。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态与加工层级 | 分层怎么切、公共层放什么 | 「分层越细越好」——层数超过业务可维护的粒度后，跨层引用必然出现 |
| 主体与合规边界（数据能否出域） | 集中式中台 / 联邦 / Mesh | 「统一口径必然要求数据集中」——联邦与 Mesh 证明可以只统一契约 |
| 时效与访问模式（T+1 / 分钟级 / 交互式） | 是否引入第二条实时链路 | 「实时就是把离线任务改快」——实时的真实代价是第二条代码路径 |
| 变更频率与口径稳定性 | 治理门禁的严格程度与评审成本 | 「门禁越严越好」——超过业务节奏的门禁会被绕过，规范只剩名义 |
| 一致性要求（口径级 / 行级） | 统一放在规范层还是执行层 | 「都要求一致」——行级实时一致会推翻整个联邦式设计 |
| 规模与成本约束 | 自建还是托管、单引擎还是多引擎 | 「开源一定更省」——省的是许可费，贵的是运维人天 |
| 团队技能与运维能力 | 能自建几个组件 | 「自建可控」——超过运维上限后，可控会变成失控 |

### 3.2 模式逐个拆解（核心节）

> 6 个模式按「统一被放在哪一层」排列：从中心裁决（3.2.1）到契约裁决（3.2.6）。

#### 3.2.1 阿里 OneData 标准模式

**被什么约束逼出来**：多个业务单元各自建仓，同一份业务事实被重复加工且每次口径略不同，而决策层需要跨单元可比的数字——这要求口径有一个唯一裁决点。

**结构**：

```sql
-- 分层职责固定：每层只引用紧邻的下层；指标口径不在 SQL 里，而在指标平台
CREATE TABLE dwd_trade_order (          -- 明细层：清洗 + 主体统一，不做聚合
  order_id   BIGINT,
  one_id     BIGINT,                    -- ← OneID：跨业务域统一的主体标识
  shop_id    BIGINT,
  pay_amount DECIMAL(18,2),
  pay_time   TIMESTAMP
) PARTITIONED BY (dt DATE);

CREATE TABLE dws_trade_shop_1d (        -- 公共汇总层：粒度与口径固定，一次加工多处复用
  shop_id  BIGINT,
  dt       DATE,
  gmv      DECIMAL(18,2),               -- 口径由指标平台唯一裁决，不在此重新定义
  paid_ord BIGINT
) PARTITIONED BY (dt DATE);
```

**为什么这样设计有效**：因为 `gmv` 的定义只存在于指标平台一处，两个业务不可能在各自的 ADS 里各写一版过滤条件，口径漂移失去了发生的位置；又因为每层只引用紧邻下层的产物，重复加工无法通过「明细层直接出汇总」这类捷径悄悄发生。

**代价**：中心建模团队成为变更通路上的一站，新增公共模型要排队评审；公共层必须覆盖长尾需求，否则业务会被迫绕过它——而绕过一旦成为惯例，复用率与公共层的可信度会同时下降。

**失效点**：当业务变化速度持续快于中心评审周期时，「一次定义多处复用」会反转成「公共层追不上业务」，因为域团队绕过公共层自建 ADS 的即时收益（今天就能上线）远大于遵守规范的远期收益（口径统一），而远期收益无法在当期排期里被看到。

**真实使用**：阿里自 2016 年起推进 OneData 建模方法论（分层、命名、口径统一），覆盖全集团多个业务单元【公开】（《大数据之路：阿里巴巴大数据实践》，阿里巴巴数据技术及产品部著，电子工业出版社，2017——书中 OneModel / OneID / OneService 与 ODS→DWD→DWS→ADS 的分层职责即该模式的公开形态；案例展开见本目录 §15.1）。「持续 8+ 年」按时间跨度推算【推算】（起点 2016 年，截至本仓库材料覆盖的 2024 年，为 8 年以上）。口径一致率与复用率的具体数值阿里未公开，本文不做数字推断【经验】。

#### 3.2.2 开源 OneData 模式

**被什么约束逼出来**：已有 Hadoop / Spark 资产与合规要求使得无法整套采用云厂商托管套件，但「口径唯一」这个目标不能放弃——于是把口径从产品能力改造成代码资产。

**结构**：

```yaml
# 语义层：口径是代码，走 Git 与 code review，因此自带审计痕迹
metric:
  name: gmv
  measure: total_pay_amount      # 度量只有一处定义
  filters: ["order_status = 'PAID'"]
  dimensions: [shop_id, dt]
  owner: trade-analytics
  version: 1.0
```

```text
调度依赖显式化（Airflow 风格 DAG）
  ods_trade_order ──► dwd_trade_order ──► dws_trade_shop_1d ──► 语义层查询 gmv
                          ▲
                自研 OneID 图计算（dwd 的上游依赖）
```

**为什么这样设计有效**：因为口径以文件形式进版本控制，任何口径变更都必须经过一次合并请求，所以「谁在什么时候、以什么理由改了 gmv」天然留下记录；托管套件里改口径往往只是一次点击，审计要靠额外埋点补。

**代价**：语义层、调度、血缘、质量、权限全部自建，运维面约等于托管模式的全部产品之和；这些组件彼此有版本耦合（语义层引擎升级会同时波及所有引用它的任务），升级是一次跨团队的联合行动，团队必须为此预留固定窗口。

**失效点**：当自研组件数超过团队实际运维能力时，「自建可控」反转成「自建失控」，因为统一口径的收益是间接的（避免未来返工），而运维告警的成本是每天直接的——团队时间必然被后者占满，治理动作被无限延期。判断方法（可自行核验）：看近三个月排期里治理类工作的占比是否持续下降。

**真实使用**：MetricFlow 由 Transform 开发并开源，后被 dbt Labs 收购并成为其语义层的实现，是这套组合的现实形态【公开】（dbt Labs，"dbt Semantic Layer" 官方文档与 MetricFlow 开源仓库，2022 起；收购公告发布于 2023 年 2 月）。多数企业在语义层之上仍保留自研 OneID 与指标平台，组件拼装方式因团队而异【经验】。

#### 3.2.3 实时 OneData 模式

**被什么约束逼出来**：决策窗口从「第二天」压缩到分钟级（大促、履约、风控），而 T+1 批链路在物理上无法在当天给出数字。

**结构**：

```sql
-- 流式汇总表：与离线 DWS 同名、同粒度、同口径，差异只在时间语义
CREATE TABLE dws_trade_shop_rt (
  shop_id     BIGINT,
  window_end  TIMESTAMP(3),
  gmv         DECIMAL(18,2),
  paid_ord    BIGINT,
  PRIMARY KEY (shop_id, window_end) NOT ENFORCED
);
-- 关键：gmv 的度量表达式来自同一份指标定义，
--       不在这里手写过滤条件（手写那一刻，两份口径就开始了）
```

```text
两条链路、一份口径
  Kafka ──► 流处理（Flink，窗口聚合） ──► 实时 OLAP（Hologres / StarRocks） ──► 实时指标平台 ──► 实时看板
  ODS   ──► 批处理（T+1 全量）        ──► 离线 DWS（MaxCompute / Hive）      ──► 报表 / 对账
        两者引用同一个 metric 定义（measure / filters 同一份）
        每日任务：对账实时与离线的差异，超阈值告警
```

引擎候选是可替换的，本模式不绑定某一款：实时侧为 **Kafka + Flink + Hologres / StarRocks + 实时指标平台**（同目录 §4 的实时 OneData 示例用 Flink + Hologres，主文件 §2.1 也把 Hologres 列为阿里云实时交互式分析引擎；StarRocks 是同一位置上的可替换项），离线侧为 MaxCompute / Hive + 调度（Airflow 等）。换引擎不改变本模式，换掉「同一份 metric 定义」才会。

**为什么这样设计有效**：因为实时与离线共用同一份度量表达式，两条链路的差异被压缩到「时间语义与迟到数据处理」这类技术性差异上，前者能在对账里被发现；而各写一遍 `SUM(x) WHERE y` 时，两者的差异是算法差异，没人能靠肉眼发现。

**代价**：同一指标有两条代码路径、两套运维（状态管理、检查点、背压、回溯补数），团队需要同时具备流与批两种技能；实时层为低延迟通常依赖常驻内存或高性能存储，单位数据的计算与存储成本高于批。

**失效点**：当实时链路的延迟压力大到有人开始在流任务里手写口径（例如为减少回刷临时加一个过滤条件）时，「一份口径」反转成「两份口径加一个看起来一致的假象」，因为对账通常只比总量、不比长尾维度，偏差会长期隐藏在小类目、退款与跨天迟到数据里。

**真实使用**：阿里在 2019 年前后把实时链路并入统一建模（形态是流计算 + 实时数仓 + 实时指标平台），公开形态可对照阿里云 Hologres 与 Flink 的官方产品文档自行核验【经验】。需要说明的是，OneData「1.0 / 2.0 / 3.0 / 4.0」的版本年表在公开材料中查不到，因此本文只按「批次 → 实时 → AI」的阶段描述，不把版本号当年表断言（判断方法：检索阿里官方书籍与云产品文档，若找不到版本号年表的权威出处，就不应引用它）【经验】。字节、美团的实时数仓实践广泛，但口径一致性的具体做法因团队而异，本文不做逐家断言【经验】。

#### 3.2.4 AI 增强 OneData（OneData 4.0）

**被什么约束逼出来**：消费方从人变成 LLM / Agent。人可以靠问人消歧，模型不能——口径必须以机器可读形式存在（唯一名字、明确类型、粒度、所有者、时间语义），否则模型只能猜。

**结构**：

```text
LLM 只能引用检索到的指标，不能自造度量表达式
  业务问题 ──► 指标检索（向量 + 关键词） ──► 候选指标（含口径 / owner / 版本）
                                                   │
                                   LLM 生成查询（只允许引用候选）
                                                   │
                                   校验：类型 / 粒度 / 权限 / 口径一致性
                                                   │
                             通过 ──► 执行        不通过 ──► 拒答或转人工
```

```yaml
# 机器可读的指标定义：这些字段必须先补齐，AI 增强才有前提
metric:
  name: gmv
  semantic_type: amount
  default_time_dim: pay_time
  granularity: [1d, 1h]
  owner: trade-analytics
  version: 1.2
```

**为什么这样设计有效**：因为生成环节被限制在「从候选里选」，而不是「自由写公式」，模型的错误被压缩成「选错指标」这一类可在结果里被发现的问题，而不是「编出一个看起来合理的口径」这一类无人能发现的问题。

**代价**：每个指标都要补齐机器可读属性（owner、粒度、时间维度、枚举值、版本），工作量与指标数量成正比，且必须在开放给模型之前完成；属性缺失的指标在检索里等同于不存在，而模型遇到候选不足时会用相邻指标近似。

**失效点**：当语义层覆盖率低于实际查询需求的覆盖面时，「AI 自动取数」反转成「看起来对但口径错」，因为模型在候选不足时倾向用最相似的可用指标填空，而使用者无法从结果上分辨。判断方法（可自行核验）：抽样约 20 个业务提问，人工认定正确答案对应的指标，再看系统命中的是否同一个，命中比例即覆盖率的下界。

**真实使用**：阿里云「语义层 + 自然语言查询」的产品形态公开出现在 2024 年前后（本仓库 §4、§5 记为「通义数智」；该名称与版本号本文无法在公开材料中逐条核验，降为待复核，不作公开断言）【经验】。厂商侧的同类形态是 Databricks 的 Genie 与 Snowflake 的 Cortex，两者的官方产品文档都提供「自然语言 → 受约束的语义层查询」这一入口，可按各自官方产品文档与发布说明自行核验；具体发布年份与功能边界本文不做公开断言【经验】。其余多为厂商路线图层面，不作事实断言【经验】。

#### 3.2.5 联邦 OneData

**被什么约束逼出来**：数据与合规边界（跨云、跨国、多法人主体）不允许把数据集中到一个湖，但集团级决策仍需要跨边界可比的口径。

**结构**：

```text
联邦：统一的是名字、契约与权限，不是存储
  域 A 存储 ──┐
  域 B 存储 ──┼──► 统一 Catalog（命名空间 / Schema / 权限 / 血缘）
  域 C 存储 ──┘        只登记，不搬迁
                         └─► 计算下推到各域执行，只回传结果或聚合值
```

```sql
-- 联邦里"统一"的产物不是一张本地表，而是一份可寻址的契约
CREATE EXTERNAL TABLE federated.dws_trade_shop_1d (
  shop_id BIGINT,
  dt      DATE,
  gmv     DECIMAL(18,2)
)
USING iceberg
LOCATION 's3://domain-a-warehouse/dws_trade_shop_1d'   -- 数据留在域 A
TBLPROPERTIES ('owner'='domain-a', 'sla'='T+1 06:00', 'residency'='A');
```

**为什么这样设计有效**：因为只有元数据与契约跨越边界、数据不出域，合规上的驻留要求与「跨域可比口径」这两个原本对立的目标可以同时成立——统一被降级为「可寻址 + 可理解」，而这已足够支撑大部分跨域分析。

**代价**：跨域 JOIN 只能下推或物化副本，跨域查询的延迟与失败面等于各域之和；命名与类型对齐需要持续仲裁，否则一个域改字段类型、另一个域静默出错；catalog 本身成为新的单点，其权限模型必须比任何单个域都更保守。

**失效点**：当跨域需求从「口径级一致」升级到「行级实时一致」时，联邦反转成「反复搬运数据」，因为联邦的机制是数据不动、计算动，而行级实时一致要求计算贴着数据做，跨域时无法下推，只能同步副本——此时统一口径反而成了同步副本的理由。

**真实使用**：Databricks Unity Catalog 于 2021 年发布、Apache Polaris 于 2024 年进入 Apache 孵化器，是现实中承载这类 catalog 的两个形态【公开】（Databricks，Data+AI Summit 2021 的 Unity Catalog 发布公告；Apache 软件基金会，2024 年的 Polaris 孵化公告——两者均可按公告标题在本仓库外检索核验）。企业把它用于联邦治理的深度差异很大，本文不做逐家断言【经验】。

#### 3.2.6 Data Mesh 模式

**被什么约束逼出来**：域的数量与业务节奏超过中心团队的理解带宽——中心团队既不懂每个域的语义细节，也跟不上每个域的变更速度，却仍被要求对所有域的口径负责。

**结构**：

```text
Data Mesh：把"统一"从中心下放到契约
  平台团队 ──► 提供自助能力（存储 / 计算 / 调度 / 目录 / 权限）
  域团队   ──► 拥有并发布 data product（自己的 schema、SLO、owner）
  治理     ──► 只规定契约必须长什么样：可发现 / 可寻址 / 有 SLO / 有 owner
  消费     ──► 只通过 data product 契约消费，不跨域直读物理表
```

```yaml
# data product 契约：被统一的对象从"表"变成"契约"
data_product:
  name: trade_shop_daily
  domain: trade
  owner: domain-trade-analytics
  interface:
    columns: [shop_id, dt, gmv, paid_ord]
    semantics: {gmv: "已支付订单金额之和，含税"}
    freshness: "T+1 06:00"
  consumers: [marketing, finance]
```

**为什么这样设计有效**：因为「谁最懂这份数据谁负责它的口径」被写成组织边界而不是流程要求，口径责任不需要跨团队协调就落在具体团队身上；平台团队只需保证能力可用，不必理解每个域的语义。

**代价**：统一的强度从「强制」降为「契约约定」，跨域一致性依赖契约评审的质量；平台团队必须先把自助能力做到位，否则域团队各自采购工具，反而制造出比原状态更多的烟囱；重复建设从「表」下沉到「能力」。

**失效点**：当平台自助能力覆盖不了域团队的实际需要、而域数量仍在增长时，Data Mesh 反转成它本要解决的问题——烟囱式建设，因为在没有共享平台的前提下，「自治」的实际含义就是「各建一套」。判断方法（可自行核验）：清点域团队自建了多少不在平台清单上的基础组件（调度、存储、血缘），数量持续增长即为反噬信号。

**真实使用**：Data Mesh 概念由 Zhamak Dehghani 于 2019 年提出（"How to Move Beyond a Monolithic Data Lake to a Distributed Data Mesh"）【公开】（ThoughtWorks，2019）。它主要是一套组织与治理范式，技术栈不唯一，各家落地深度差异大，本文不做逐家断言【经验】。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 单主体、云托管可用、口径需中心裁决、批为主 | 阿里 OneData 标准模式 | 不选 Mesh：域数量不够时，自治只带来重复建设而无收益 | 域的数量是否已超过中心团队能逐个理解的上限 |
| 已有 Hadoop 资产、不能换栈、要审计留痕 | 开源 OneData 模式 | 不选标准模式：托管套件换不来已有资产与合规要求 | 团队能否承受 5 个以上自建组件的运维【经验】 |
| 决策窗口分钟级、批链路物理上赶不上 | 实时 OneData 模式 | 不选标准模式：T+1 不是「慢一点」，而是当天拿不到数 | 实时与离线是否共用同一份口径定义 |
| 消费方是 LLM / Agent、语义层已存在 | AI 增强 OneData | 不选标准模式：给人看的文档对模型不可读 | 语义层对高频指标的覆盖率 |
| 数据有驻留 / 合规边界、不能集中 | 联邦 OneData | 不选标准模式：口径统一并不要求数据集中 | 跨域需求是口径级一致还是行级实时一致 |
| 域多、节奏快、中心建模已成瓶颈、平台能力已就绪 | Data Mesh | 不选标准模式：中心裁决在这种规模下必然排队 | 平台自助能力是否已覆盖域团队的必需项 |

**本主题下最常被误选的一对，是「阿里 OneData 标准模式」与「Data Mesh」。** 两种误选都有具体后果（下文的域数门槛为经验区间，非公开统计数字【经验】）：只有三五个域就抄 Data Mesh，会把「统一口径」从一次中心评审变成五份契约协商，跨域一致性反而更差，且每个域都要自己养一套平台能力；已有几十个域、每个域变更以周计却硬撑中心化评审，则公共层成为排队瓶颈，域团队开始绕过它自建 ADS——绕过一旦开始，公共层的复用率与可信度同时下降，系统变成「名义上的 OneData + 事实上的烟囱」。判断该不该换的那条约束是：**中心团队是否还能逐个理解各域的口径细节**；还能，就该集中；不能，就必须把裁决权连同责任一起下放，并先补齐平台能力。

### 3.4 组合模式：真实系统不会只用一种

**组合一：标准模式（批）+ 实时模式。** 分工是离线作基线与对账、实时作增量窗口，口径定义只有一份。运维代价是同时养两套引擎和一套每日对账任务，且对账必须覆盖长尾维度而非只比总量。适合规模：已有 T+1 公共层、又出现分钟级决策需求的团队，通常在千表量级开始值得单独立项【经验】。

**组合二：标准 / 开源模式 + AI 增强。** 分工是语义层作唯一入口、LLM 作消费层——前者保证口径唯一，后者只负责把自然语言映射到已有指标，不新增口径。运维代价是语义层的元数据补全工作量与指标数量成正比，且必须在开放前完成。适合规模：语义层已稳定运行、业务提问集中在已覆盖指标上的团队。

**组合三：Data Mesh + 联邦。** 分工是 Mesh 解决「域内谁为口径负责」、联邦解决「跨域如何在不搬数据的前提下可寻址」，两者共享同一份 catalog 契约。运维代价是两类治理议题叠加（契约评审 + catalog 仲裁），且两套机制都要在平台能力就绪后才成立。适合规模：多个已自治的域，并存在跨法人或跨地域数据边界的集团。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 烟囱式建设 | 同一业务事实在多个域各有一套表，同名不同义 | 同一指标多套实现，跨域问题无法回答，改动一处不知影响谁 | 自建是当期最快路径，中心规范的收益是远期的 | 统一 OneModel 公共层，并把「绕过公共层」变成需要审批的例外 |
| 指标无 owner | 指标变更没人审批，口径漂移靠下游反馈发现 | 口径变更无审计痕迹，事故无法追溯到具体变更 | 指标被当成 SQL 的副产品而不是独立资产 | 每个指标登记具体到人的 owner，变更需 owner 会签 |
| OneID 不准确 | 同一用户在不同域表现为多个主体，人数口径对不上 | 以主体为粒度的所有指标基数虚高，跨域聚合失真 | ID-Mapping 只做单源映射，未处理多 ID 冲突与时间维度 | 强 ID + 弱 ID 联合建模（图计算）+ 定期校验合并准确率 |
| 指标平台不治理 | 平台里堆积大量未维护、未使用、口径重复的指标 | 检索结果被无效指标污染，使用者不再信任平台，退回问人 | 平台建设被当成一次性项目，没有生命周期机制 | 指标生命周期管理：定义、评审、监控使用、下线 |
| 实时 + 离线口径不一致 | 实时与离线数字对不上，对账靠人工解释 | 同一指标两个值，决策层对数据失去信任 | 两条链路各写一遍过滤与聚合条件，差异不在总量而在长尾 | 同一份代码 + 同一份存储 + 同一份指标定义 + 每日自动对账 |

**最危险的三条，在生产中的典型暴露方式：**

**实时 + 离线口径不一致**，几乎不会以「发现不一致」的方式暴露，而是以「业务不再信任数据」的方式暴露。它是静默的：两个数字都查得到、都能自圆其说，直到某次汇报口径被质疑，团队才发现它们来自不同链路。机制是差异被藏在长尾维度里——总量对得上，是因为主要场景一致，差异集中在小类目、退款与跨天迟到数据上，而抽查通常只抽大数。

**指标无 owner**，暴露方式是「变更无法追溯」。事故发生时团队能定位到某张表昨天变了，却说不清是谁、为什么、经过什么评审——因为指标定义从未作为独立资产被登记，它散落在多条 SQL 里。修复的第一步不是加流程，而是先把指标从 SQL 里抽出来，成为有名字、有 owner、有版本的对象；缺这一步，任何流程都落在空处。

**烟囱式建设**，暴露方式是「公共层没人用」。公共层的表在目录里存在，业务看板却仍指向自建表——这通常意味着公共层的粒度或时效覆盖不了业务需求，而不是业务方不守规范。机制上，规范的力量来自「遵守它比绕过它更省事」，一旦不成立，规范只能靠审批维持，而每一次例外都在削弱它。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单域 → 多域（约 10 个域以上【经验】） | 中心裁决的口径定义 | 中心团队无法逐个理解各域语义，评审排队 | 契约化：口径裁决与责任一起下放到域 | 需先补齐自助平台（调度 / 目录 / 权限），否则自治变烟囱 |
| T+1 → 分钟级 | 纯批链路 | 决策窗口物理上赶不上，业务开始用离线数近似 | 增加实时链路（标准 + 实时组合） | 两套引擎运维 + 每日对账；口径定义必须先收敛到一处 |
| 人消费 → 模型消费 | 给人读的文档与规范 | 模型读不了文档，只能猜表名与口径 | AI 增强：语义层 + 检索 + 校验回路 | 逐指标补机器可读属性，工作量与指标数成正比 |
| 单主体 → 多主体 / 跨地域 | 集中式中台 | 数据驻留与合规不允许集中 | 联邦：只统一契约与命名 | 建立 catalog 仲裁机制，接受跨域查询的延迟与失败面 |
| 千表 → 十万表 | 人工登记与人工评审 | 人工维护的元数据难以长期保鲜【经验】 | 自动采集（SQL 解析）+ 门禁校验 | 建设解析与血缘能力，人工只做校正与仲裁 |

### 3.7 自检清单

- [ ] **口径是否只有一处定义？** 任取一个指标，在代码库与平台里搜索它的过滤条件；出现超过一处，即违反口径唯一。
- [ ] **每层是否只引用紧邻的下层？** 抽查 10 个任务的输入表，出现「明细层直接出汇总」或应用层跨层引用，即违反分层纪律。
- [ ] **每个指标是否有具体到人的 owner？** owner 写成团队名、或指向已离职者而无接收人，均视为无 owner。
- [ ] **公共汇总层是否真的被复用？** 统计引用公共层表的下游任务数；若多数 ADS 直接引用明细层，说明公共层没被用起来。
- [ ] **OneID 是否处理了多 ID 冲突？** 抽查同一自然人在不同域的标识是否映射到同一主体，是否出现同一主体被拆成两个。
- [ ] **实时与离线是否共用同一份口径定义？** 比较两条链路的度量表达式来源；实时链路里若存在手写过滤条件，即已分叉。
- [ ] **是否有跨链路对账任务？** 且对账是否覆盖长尾维度（小类目、退款、迟到数据），而不只是总量。
- [ ] **指标是否有生命周期状态？** 无使用、无 owner、口径重复的指标是否会被标记并下线，还是永久留在平台里。
- [ ] **语义层对高频指标的覆盖率是多少？** 抽样业务提问，检查命中的指标是否为人工认定的那一个（可自行核验）。
- [ ] **门禁是否与业务节奏匹配？** 统计被阻断的变更中有多少最终被判为误拦；误拦比例高的门禁会被绕过。
- [ ] **绕过公共层的路径是否存在？** 域团队能否不经评审直接建表；能，则规范的实际强度为零。
- [ ] **模式是否仍匹配当前约束？** 域数量、时效要求、消费方三者任一变化，都应重新走一遍 3.6 的跃迁表。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 单主体、域少、口径需中心可比 | 阿里 OneData 标准模式 | 口径唯一裁决点 + 不跨层引用，令漂移在结构上无处发生 |
| 不能换栈、要审计留痕 | 开源 OneData 模式 | 口径即代码，变更走版本控制，自带审计痕迹 |
| 决策窗口分钟级 | 实时 OneData 模式 | 实时与离线共用一份度量表达式，差异只剩时间语义 |
| 消费方是模型 | AI 增强 OneData | 生成被限制在候选集合内，错误从「编口径」降级为「选错指标」 |
| 数据不能集中 | 联邦 OneData | 只统一契约与命名，数据不出域 |
| 域多、节奏快、平台已就绪 | Data Mesh | 口径责任随组织边界落到具体团队，不再需要跨团队协调 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**口径的裁决权在谁手上、以及它能否覆盖业务的变更速度**——中心覆盖得了就集中，覆盖不了就把裁决权连同责任下放给域，并先补齐平台能力。数据能不能集中只决定「统一的是数据还是契约」，时效只决定「要不要第二条链路」，两者都不改变这条主线。
