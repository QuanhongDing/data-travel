## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

Lakehouse 的所有模式差异，根子上都落在同一条机制上：**对象存储上的文件是不可变的，表的「此刻状态」由一层可以被原子替换的元数据定义**。谁写下这层元数据、写到哪、什么时候替换它，决定了这个表格式能不能扛住某类写入。Iceberg 用「元数据文件 → manifest list → manifest → 数据文件」的多层清单描述表状态；Delta 用按序追加的事务日志回放快照；Hudi 用一条操作时间线记录提交；Paimon 用 LSM 的层与主键桶组织增量。四者结构不同，但都在回答同一个问题。

由此派生出第二个轴：**合并成本放在写路径还是读路径**。写时合并（COW）在写入时重写受影响的数据文件，代价是写放大、收益是读路径干净；读时合并（MOR、LSM）在写入时只追加增量文件或日志，代价是读路径要现场合并、收益是写入成本与「被更新数据的大小」解耦。所有关于「选哪个表格式」的讨论，最终都要落到这两个轴的取值上 —— 写模式是追加还是更新，读模式是点查还是大范围扫描，这两个答案基本决定了正确答案。

这也是本节要纠正的一个直觉：表格式不是「选一个更好的」，而是「选一个把合并成本放对位置的」。同一份数据、同一批 CDC，用 COW 承接和用 MOR 承接都能跑起来，区别只在成本落在写侧（写放大、小文件、Compaction 压力）还是读侧（读放大、合并延迟、过期风险）。写在选型文档里的第一个问题不该是「社区最大的是哪个」，而是「这张表的主键每天被更新几次、每次更新命中多少文件」。

还有一条约束藏在组织一侧：**元数据的权威只能有一个**。表格式负责「表是什么」，但这层元数据由谁托管、谁能改、改动如何被审计，是另一件事。同一个团队里两套 Catalog 并存、或某个引擎只认文件系统路径时，多引擎读到同一份数据这件事就已经不成立了 —— 而这一点在单引擎阶段完全看不出来，它只在第二个引擎接入时才暴露。所以选型的顺序是先定元数据的托管方式，再定表格式。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 写入模式（追加 / 主键 upsert / CDC 更新） | 决定合并成本放在写路径还是读路径 | 「先用最流行的格式」—— 更新密集场景下 COW 会产生写放大 |
| 访问模式（点查 / 大范围扫描 / 聚合 / 增量流读） | 决定文件布局、聚簇方式与是否需要聚簇索引 | 「分区越多越快」—— 分区与小文件膨胀会先把规划拖慢 |
| 变更频率与历史要求（快照保留、审计回溯） | 决定保留窗口、清理策略与时间旅行的可用范围 | 「保留越多越安全」—— 保留窗口同时放大存储与清理成本 |
| 一致性要求（跨引擎可见性、并发写冲突） | 决定 Catalog 选型与提交协议 | 「多引擎天然一致」—— 没有统一 Catalog 就是各读各的指针 |
| 规模与成本约束（对象存储请求数、元数据规模） | 决定目标文件大小、Compaction 频率、清单层级 | 「对象存储便宜」—— 请求次数与列举成本被忽略 |
| 团队技能与运维能力 | 决定能同时维护几套表格式与几个 Catalog | 「多格式共存更灵活」—— 每套格式都要独立的合并与治理人力 |

### 3.2 模式逐个拆解

下面按原文件列出的 7 个模式逐个拆解。前四个是表格式与引擎的绑定关系，后三个是组织与分层形态；每个都给出结构示意、机制、代价与失效点，并在末尾保留该模式的**典型栈** —— 原 § 3 为模式 1–4 各写了一行「典型栈」、决策表另有一列「典型技术栈」，其中的候选组件（S3/OSS、StarRocks/Doris、Unity Catalog、MLflow、Vector Search）在这里逐一落回，便于按团队既有栈对照。

先给一张总览，把每个模式与它把合并成本放在哪里对应起来 —— 后文的失效点，基本都是这个位置选错或没被运维住：

| 模式 | 合并成本位置 | 表状态的权威在哪 | 首要约束 |
| --- | --- | --- | --- |
| Iceberg + Spark/Flink + Trino | 写侧（每次提交产生一批清单） | Catalog 里的当前快照指针 | 多引擎读、追加为主 |
| Paimon + Flink | 读侧 + 后台 LSM 合并 | 表自身的 LSM 层与主键桶 | 分钟级持续 upsert |
| Delta Lake + Databricks | 写侧（乐观并发 + 日志提交） | 事务日志的最后一个版本 | 单一生态、治理一体化 |
| Hudi + CDC | 读侧（MOR）/ 写侧（COW） | 操作时间线 | 更新密集、需幂等重放 |
| 多表格式共存 | 两套各付一处 | 需人工显式约定的权威表 | 实时与离线需求分叉 |
| Medallion 架构 | 不涉及（分层组织方式） | 各层各自的表 | 多种质量契约并存 |
| Lakehouse + 实时 OLAP | 读侧（查询走 OLAP） | 湖是权威、OLAP 是派生 | 秒级点查 SLA |

这张表只回答一件事：当有人问「为什么这张表慢」时，先看它的合并成本放在哪一侧，再看这一侧的运维是否真的在做（Compaction 有没有常驻调度、清单与快照有没有被清理、Catalog 是不是唯一权威）。绝大多数湖仓的性能与成本问题，都能在这个二维定位里找到位置。

#### 3.2.1 Iceberg + Spark/Flink + Trino（最常见，跨引擎默认）

- **被什么约束逼出来**：同一份数据要被多个引擎读写，且不能把表状态存在某个引擎或某个厂商的私有服务里；同时表的规划成本不能随文件数线性膨胀。
- **结构**：

```sql
CREATE TABLE lake.db.orders (
  order_id   BIGINT,
  user_id    BIGINT,
  amount     DECIMAL(18,2),
  order_time TIMESTAMP
) USING iceberg
PARTITIONED BY (days(order_time))
TBLPROPERTIES ('write.format.default' = 'parquet', 'format-version' = '2');

-- 表状态不靠"目录里有什么"，而靠这条元数据链：
--   metadata/vN.metadata.json（schema + 分区规范 + 当前快照指针）
--     └─ manifest list（本次快照引用了哪些 manifest）
--          └─ manifest（每个数据文件的路径 + 分区 + 列级 min/max/null_count）
--               └─ data file（Parquet，不可变）
-- 提交 = 原子替换 metadata.json 里的快照指针
```

- **为什么这样设计有效**：因为数据文件不可变、每次提交只做一次「指针替换」，所以读者任一时刻只能看到某个完整快照，并发写不会产生半可见状态；因为查询规划只读元数据树、不列举对象存储目录，所以规划成本与「文件数量」相关、与「目录层级和分区数量」解耦 —— 这正是能扛住千万级分区的原因。
- **代价**：元数据本身就是一批需要维护的文件。高频小批提交会持续产生 manifest 与 manifest list，必须额外付出元数据重写（重写 manifest、合并清单）与过期快照清理的运维；行级删除需要在读路径上按删除文件做过滤，读取成本高于纯追加表。
- **失效点**：当每个分区只装很少数据、而提交又非常频繁时，本模式「规划与目录解耦」的优点会反转成**元数据自身成为瓶颈**，因为每一次规划都要读大量清单、每一次提交都要新增一批清单并触发清理，清单的数量比数据文件下降得更慢；此时要么提高单次写入批量，要么把这张表交给带主键合并的 LSM 型格式。
- **真实使用**：Iceberg 由 Netflix 开源、后进入 Apache 基金会并成为顶级项目（【公开】来源形态：Apache 软件基金会官方项目页 Apache Iceberg，该项目 2020 年毕业为顶级项目，2025 年核查；当前状态以该页面为准）；Netflix 用它改造 EB 级数据湖场景见本仓库 [§ 6 落地实践](03-lakehouse-section-6-sec6.md)。
- **典型栈**：对象存储（S3/OSS）+ Iceberg + Spark/Flink + Trino + StarRocks/Doris。分工是 Spark/Flink 负责写入与合并、Trino 负责跨源联邦读、StarRocks/Doris 承接湖之上的高频查询服务层 —— 服务层那一段即 3.2.7 的组合。

#### 3.2.2 Paimon + Flink（流批一体首选）

- **被什么约束逼出来**：入湖要按分钟甚至秒级持续写入，同一主键被反复更新，且下游既要能批读全量、又要能读到增量变更，不能为每条链路另建一套 CDC 管道。
- **结构**：

```sql
CREATE TABLE lake.orders_rt (
  order_id   BIGINT PRIMARY KEY NOT ENFORCED,
  user_id    BIGINT,
  pay_status STRING,
  amount     DECIMAL(18,2),
  updated_at TIMESTAMP(3)
) WITH (
  'bucket'             = '4',              -- 主键按 hash 落到 bucket，决定 upsert 落点
  'merge-engine'       = 'partial-update', -- 同主键的更新按字段合并，而不是整行覆盖
  'changelog-producer' = 'input'           -- 把写入流本身暴露为下游可读的变更日志
);

-- 写路径：写入先落内存表 → 刷成有序文件 → 后台按层合并（LSM）
-- 读路径：批读按 bucket + 层合并；流读直接消费 changelog
-- 关键：单条 upsert 只影响它落到的 bucket，不重写全表
```

- **为什么这样设计有效**：因为写入是向 LSM 追加有序文件、而不是重写数据文件，所以单条 upsert 的成本与表的总规模无关，只与命中 bucket 的文件数相关；因为 changelog 由写入侧直接产出，所以下游流任务与批任务共用一份存储，省掉了一条独立的变更捕获链路。
- **代价**：LSM 结构必然持续产生多层文件，Compaction 是常驻工作而不是一次性任务；未合并时一次读可能跨越多个文件与多层，读放大与层数相关；bucket 数是容量规划参数，改了往往要重写数据。
- **失效点**：当写入主键分布严重倾斜（少数 key 承担绝大多数更新）时，本模式「单条 upsert 成本与表规模无关」的优点会反转成**热点 bucket 串行化**，因为主键哈希分桶会让同一个热点 key 永远落进同一个 bucket，该桶的写与合并被串行化，积压会沿写队列向后传播。
- **真实使用**：Paimon 前身为 Flink Table Store，后成为 Apache 项目并于 2024 年发布 1.0（【公开】Apache 项目发布说明，2024）；与 Flink 的原生集成以官方文档当前版本为准。
- **典型栈**：对象存储（OSS）+ Paimon + Flink + StarRocks。Flink 既写主键表、又通过 changelog-producer 直接产出下游可读的变更流，StarRocks 承接其上的对外查询。

#### 3.2.3 Delta Lake + Databricks（AI/ML 一体化）

- **被什么约束逼出来**：团队已深度使用 Spark，且要求训练数据、特征与模型资产处在同一份治理边界内（同一套权限、血缘与目录），不愿为多引擎改造多付一次格式迁移的成本。
- **结构**：

```sql
CREATE TABLE lake.silver_orders USING delta
LOCATION 's3://bucket/silver/orders';

-- 表状态 = 一条按序追加的事务日志
--   _delta_log/00000000000000000010.json
--     · add / remove file（本次提交新增与失效的数据文件）
--     · schema 与列统计（供文件级剪裁）
--     · commitInfo（谁、何时、什么操作 —— 审计与回溯的原始记录）
-- 读路径：回放日志重建快照 → 定位 Parquet → 按统计剪裁
-- 写路径：乐观并发控制，冲突提交重试
```

- **为什么这样设计有效**：因为表状态是可由日志回放出的确定快照，所以历史版本与变更记录天然可得，审计不需要额外埋点；因为训练、批处理与治理工具在同一生态内共享 catalog 与权限模型，所以「同一份数据既训练又分析」不需要再建一条搬运链路，治理策略只需维护一套。
- **代价**：生态收益的另一面是绑定 —— 非该生态引擎的原生读写能力由格式规范与各引擎实现节奏决定，通常滞后于原生引擎；要让其它引擎以原生方式读到同一份数据，需要额外的格式互转机制，多出一个需要监控的转换环节。
- **失效点**：当组织里 Flink 或 Trino 需要高频读写同一张表时，本模式「生态最深、工具最齐」的优点会反转成**格式边界成为工程瓶颈**，因为「能不能读」取决于各引擎对该格式的实现进度，而不是取决于你的需求；此时要么演进到开放格式，要么引入跨格式读取层。
- **真实使用**：Delta Lake 由 Databricks 开源（【公开】Databricks 公告，2019）；Delta UniForm 让一份 Delta 数据可被其它格式的读者读取（【公开】随 Delta Lake 3.0 公布，2023；论文见 SIGMOD 2024）；Medallion 分层命名来自 Databricks 文档（【公开】来源形态：Databricks 官方文档的 Medallion 架构（Bronze / Silver / Gold）章节，2025 年核查；页面标题以官方文档站当前版本为准）。
- **典型栈**：对象存储（S3）+ Delta + Databricks 计算 + Unity Catalog + MLflow + Vector Search。权限与目录由 Unity Catalog 统一、实验与模型资产由 MLflow 记录、向量检索由 Vector Search 承担 —— 这正是上文「训练、特征与模型资产处在同一治理边界内」在工具层的落点。

#### 3.2.4 Hudi + CDC（更新密集场景）

- **被什么约束逼出来**：数据以 CDC 流的形式持续到达，同一主键被频繁更新，写路径不能再承担「重写整个数据文件」的成本，同时需要能按主键幂等重放。
- **结构**：

```sql
CREATE TABLE lake.dwd_orders USING hudi
TBLPROPERTIES (
  'type'              = 'mor',        -- COW: 重写数据文件；MOR: 追加日志、读时合并
  'primaryKey'        = 'order_id',
  'preCombineField'   = 'updated_at', -- 同一批内按此字段取最新，实现去重
  'hoodie.cleaner.policy' = 'KEEP_LATEST_COMMITS'
);

-- COW：upsert 命中 N 个文件 → 重写这 N 个文件本身
-- MOR：upsert 只追加 delta 日志 → 读时把 基础文件 + 日志 合并出结果
-- 代价位置不同：COW 付在写侧，MOR 付在读侧
```

- **为什么这样设计有效**：因为 MOR 把更新写成对基础文件的增量日志、读时才合并，所以写入成本与「被更新文件的大小」解耦、只与变更条数相关；因为主键加 preCombine 字段，同一主键在一批内的多次变更可以在合并阶段收敛成一次，重复投递不会产生重复行。
- **代价**：读路径要现场合并基础文件与日志，读放大随未合并日志量增长；必须把 Compaction 与清理当作常驻调度来运维；表状态依赖一条操作时间线，任何时间线上的延迟都需要被监控，否则下游会读到比预期更旧的合并结果。写放大的量级可以直接算出来：【推算】设单次 upsert 命中 N 个数据文件、目标文件大小为 F 字节、该批变更的原始数据量为 D 字节，则写放大 ≈ N·F / D；以 F 落在 128MB~512MB 区间【经验】、D 取 1KB 量级为例，N = 1 时比值即到 10^5 量级 —— 这就是 COW 在更新密集场景下必须被否掉的量化依据。
- **失效点**：当写入停止、读流量集中上来（例如夜间批量报表）时，本模式「写路径便宜」的优点会反转成**读放大集中爆发**，因为累积的日志文件必须在读路径上合并，而读请求越多、可用的合并预算越紧；正确做法是在读高峰前主动触发 Compaction，而不是等读请求把合并代价摊到自己身上。
- **真实使用**：Hudi 由 Uber 发起并开源（【公开】Uber 工程博客，2017），后成为 Apache 项目（【公开】来源形态：Apache 软件基金会官方项目页 Apache Hudi，2025 年核查；当前处于顶级项目还是孵化器以该页面为准）；CDC 入湖是该格式文档给出的主要场景之一，具体能力以官方文档当前版本为准。
- **典型栈**：对象存储（OSS）+ Hudi + Flink CDC + Spark。Flink CDC 负责把变更流写进 MOR 表，Spark 负责 Compaction 与批读。

#### 3.2.5 多表格式共存（Iceberg 主 + Paimon 流）

- **被什么约束逼出来**：离线主仓已经选了跨引擎的开放格式，但实时入湖若用批量写模拟，延迟与写放大都不可接受；用一个格式同时满足两端会牺牲其中一端的成本。
- **结构**：

```text
实时链路：CDC → Flink → [主键表，LSM]  ← 承担分钟级 upsert
                              │ 定时 / 准实时导出
离线链路：[主键表] → Spark 批写 → [分区表，开放格式]  ← 承担统一口径与跨引擎读
服务层：  查询引擎分别挂两个 catalog → 联邦查询按引擎下推
边界纪律：同一业务实体只能有一个「权威表」，另一份是导出的派生结果（可重建）
```

- **为什么这样设计有效**：因为两种格式各自在它被设计用来承担的写模式上工作（主键表承接连续 upsert，开放格式承接批写与跨引擎读），所以双方都不必为对方的模式付出畸形成本；因为两套 catalog 都能挂到同一查询引擎上，跨格式的联邦查询仍然可以完成，不必把数据再搬一次。
- **代价**：两套元数据、两套 Compaction、两套快照与保留策略、两份容量规划；跨格式没有共同的事务边界，一致性只能靠调度与校验保证，任何跨格式的对账都是「事后发现差异」而不是「提交时被阻止」。
- **失效点**：当「哪个是权威表」没有写进流程与工具时，本模式「各用所长」的优点会反转成**口径分裂**，因为两套系统都可被写入、各自快照的时间点又不同，两条链路会同时产出同一实体的两个版本，而任何一份报表都无法说明它在读哪一个。
- **真实使用**：多格式共存是大型湖仓组织的常见过渡形态【经验】；本仓库 [§ 7 与其他方法对比](03-lakehouse-section-7-sec7.md) 也把它列为组合方案之一。
- **典型栈**：对象存储（OSS/S3）+ Iceberg（离线主仓，承接批写与跨引擎读）+ Paimon（实时主键表，承接分钟级 upsert）+ 两个各自独立的 Catalog。

#### 3.2.6 Medallion 架构（铜银金）

- **被什么约束逼出来**：一份数据要同时服务三种互斥诉求 —— 原始可追溯（不可变）、清洗结果可复用（幂等）、指标可直接消费（可重算）—— 而它们的质量契约与更新频率都不同。
- **结构**：

```text
Bronze（原始）：只追加、不做业务清洗、保留原始载荷与来源信息 → 可重放
Silver（清洗整合）：去重、规范化、实体对齐、增量合并 → 面向复用
Gold（应用）：聚合与指标、面向具体消费场景（报表 / 特征 / 向量）→ 面向 SLA
数据流单向：Bronze → Silver → Gold
反向只有"重放"：修正上游后从 Bronze 重算，而不是向银层回写覆盖
```

- **为什么这样设计有效**：因为每一层只承担一种质量契约（原始不可变 / 清洗幂等 / 聚合可重算），所以任一层出错都能从上一层重放修复，不必回到外部系统重新抽数；因为复用发生在清洗层，新增消费场景通常只需在其上再加一条聚合，边际成本低。
- **代价**：同一份数据至少存在三份物理副本，且越往上刷新越频繁、单位存储越贵；层与层之间形成一条需要治理的调度 DAG，任何一层的延迟都会沿链路传导；契约需要被检查，否则分层会退化。
- **失效点**：当分层被当成目录命名而不写契约时，本模式「任一层可重放」的优点会反转成**无法重放**，因为原始层里被塞入了加工结果、原始载荷已经丢失，任何上游修正都必须从外部系统重新采集一次；此时三层只增加了复制次数与存储成本，没有增加任何可恢复性。
- **真实使用**：Medallion 分层是 Databricks 文档推广的组织方式（【公开】来源形态同 3.2.3：Databricks 官方文档的 Medallion 架构（Bronze / Silver / Gold）章节，2025 年核查；页面标题以官方文档站当前版本为准）；也是湖仓项目最常见的起步范式【经验】。
- **典型栈**：不绑定具体技术栈 —— 分层是组织方式而非格式选型，3.2.1–3.2.4 的四种表格式任何一种都能承载 Bronze / Silver / Gold 三层，绑定的是每层的质量契约而不是引擎。

#### 3.2.7 Lakehouse + 实时 OLAP

- **被什么约束逼出来**：BI 与看板要求秒级响应与高并发点查，而湖上查询引擎的规划与扫描成本给不出这个 SLA，同时数据必须保留湖上的单一事实源。
- **结构**：

```text
写入路径（两条，任选或并存）：
  A. 湖 → 批量导入 / 物化视图刷新 → OLAP 表
  B. 流 → OLAP 表（与湖上同一实体按日增量对齐）
查询路径：BI → OLAP（点查 / 聚合）
          湖只在需要全量明细、跨源联邦或历史回溯时被访问
一致性要求：OLAP 表必须带"数据截止时间"，报表需标注它落在哪个湖快照上
```

- **为什么这样设计有效**：因为 OLAP 引擎用列存加排序键把「扫描」换成「定位」，高并发点查不必触碰湖上的文件清单与规划流程，所以秒级 SLA 可以在保留湖上单一事实源的前提下达成；因为 OLAP 表可以从湖重建，它的正确性不依赖自身持久性。
- **代价**：同一份数据出现两个物理副本与两条刷新链路；OLAP 侧容量与成本单独核算；跨两侧的查询（明细对账、历史回溯）需要显式路由或联邦层，且两侧延迟量级不同，查询改写与结果解释都要额外说明。
- **失效点**：当刷新链路失败而监控只看 OLAP 侧「查询成功」时，本模式「秒级响应」的优点会反转成**秒级地读到过期数据**，因为查询路径不经过湖、没有任何前置校验能发现 OLAP 表的截止时间已经落后；失效的典型表现是看板始终可用，而数字停在昨天。
- **真实使用**：湖仓加实时 OLAP 是常见生产形态【经验】；本仓库 [§ 7 与其他方法对比](03-lakehouse-section-7-sec7.md) 把它列为组合方案之一。
- **典型栈**：对象存储（OSS/S3）+ 开放表格式做存储与事实源 + StarRocks/Doris 做查询服务层；导入侧用批量导入或物化视图刷新，也有链路改由 Flink 直接写入 OLAP 表（即上文写入路径的 B）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 跨引擎、联邦查询为主 | Iceberg + Trino（+ Spark/Flink） | 私有或单一生态格式会让非原生引擎的读写能力受制于对方实现进度 | 需要接入的引擎个数与它们的实现成熟度 |
| 实时入湖、流批一体 | Paimon + Flink | 批写格式承接秒级 upsert 会产生写放大与小文件 | 主键每日更新次数与可接受入湖延迟 |
| AI / 机器学习一体化 | Delta Lake + Databricks 生态 | 开放格式需要自建训练与治理的集成层 | 训练与治理工具是否已在同一生态内 |
| CDC 频繁 upsert | Hudi（MOR）+ Flink CDC | COW 承接更新密集会重写整个文件组 | 单批变更条数与被命中文件大小之比 |
| 通用默认（无强更新需求） | Iceberg（默认选型） | 为不存在的需求选复杂结构只会增加运维面 | 写模式是追加还是更新 |
| 多模态 AI（向量与结构化共存） | Iceberg 新版本（V3 及以后）+ 向量索引 / 专用向量库（LanceDB 类） | 把向量塞进普通列会失去向量检索的索引能力 | 是否需要近邻检索及其召回要求 |
| 跨国 / 多云统一口径 | Iceberg + 统一 Catalog（REST / Nessie / Polaris 类） | 各区域各建一套 Catalog 会让「同一张表」在多处指向不同快照 | 是否存在跨区域读者与写入方 |
| 秒级看板、高并发点查 | Lakehouse + 实时 OLAP（湖为权威） | 湖上规划与扫描成本给不出这类 SLA | 点查 QPS 与响应时间要求 |
| 强审计回溯、保留期长 | 分层保留（近期快照 + 归档） | 单一保留窗口会与审计要求的保留时长直接冲突 | 审计要求的保留时长与可接受回溯延迟 |

本主题下最常被误选的一对是「Iceberg 默认选型 ↔ 主键更新格式」在 CDC 场景上的错位：团队按「社区最大、跨引擎最好」选定开放格式，然后把分钟级 CDC upsert 直接写进去，结果每个微批都重写命中文件组，写放大、小文件与 Compaction 压力同时出现，而这三件事会互相放大 —— 文件越多、清单越多，合并越慢，合并越慢、文件越多。误选的实际后果不是「延迟略高」，而是**维护成本从一次性选型变成一条永远追不上的运维队列**：Compaction 的产出速度长期低于小文件的产生速度，只能靠不断加大投入维持。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Medallion 分层 + 统一 Catalog**。分层负责「同一份数据对不同消费者给出不同质量契约」，Catalog 负责「所有层、所有引擎看到同一张表」。职责边界是：层管内容与契约，Catalog 管指针与权限。运维代价是必须为每一层写清契约检查（原始层是否被写入加工结果、聚合层是否可重算），并维护一套跨引擎都生效的权限模型 —— 一旦某层绕过 Catalog 直接写文件，整个治理面就出现盲区。适合从百级表起步、需要长期演进的中大型数据平台。

**组合二：主键表承接实时 + 开放格式承接离线 + 实时 OLAP 承接服务**。这是把写入模式、读模式、SLA 三种约束分别交给三种结构的做法：LSM 主键表承接连续 upsert，开放格式表承接批写与跨引擎读，OLAP 表承接高并发点查。职责边界清楚，但运维代价最高：三套元数据与三条刷新链路，且必须显式定义「哪一份是权威」，否则同一指标会在三个系统里给出三个数。适合分钟级入湖 + 秒级看板同时被要求的场景。

**组合三：Lakehouse + 向量索引 / 多模态（AI 组合）**。湖承担结构化与原始非结构化文件的统一存放与版本管理，向量索引承担近邻检索，两者用「实体 id + 版本」对齐。职责边界是：湖管事实与版本、索引管召回。运维代价是索引需要与湖上的数据版本同步重建（模型或数据更新后索引会静默过期），且要额外处理删除与权限对齐。适合检索增强类应用起步之后、向量规模与更新频率都上升的阶段。

三种组合的共同纪律是：**先指定权威，再谈同步**。分层的权威在原始层，OLAP 组合的权威在湖上，多格式共存的权威必须被人为指定 —— 没有指定权威的组合一定会演化出两份都可写的数据，对账只能事后进行。判断组合是否已经过度，最快的方法是一句话：同一个业务指标在几个系统里各有一份可被直接消费的物理表示？超过一个的每一份，都对应一条刷新链路、一套监控和一次口径对齐的长期成本。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 选错表格式 | 更新密集的表上有持续的 Compaction 积压；某引擎写入报兼容性错误 | 合并成本被放在了不适合的一侧（写侧写放大、读侧读放大） | 按社区热度或已有技能选格式，而不是按写模式选 | 先量化主键更新频率与被命中文件大小，再定格式 |
| 不建 Catalog | 同一张表在不同引擎里指向不同位置或不同快照；权限在两处各配一遍 | 表状态没有唯一权威，多引擎共享同一份数据这件事失去前提 | 先用本地或文件系统元数据起步，后来又没迁移 | 统一用 REST Catalog / Hive Metastore / Glue / Nessie / Polaris 类服务管理 |
| 忽视 Compaction | 平均文件大小随时间下降；查询规划耗时与文件数一同上升 | 小文件让规划与列举成本上升，收益被运维成本吃掉 | 只监控写入是否成功，不监控文件与清单的健康度 | 把 Compaction 做成常驻调度，并设文件数与平均大小的告警 |
| Schema Evolution 不规范 | 下游任务在列类型变更后静默给出错值或空值 | 类型收窄与删列会改变读取语义，下游按旧假设解析 | 把改 schema 当成改配置而不是改契约 | 遵循「列可加、类型可展宽、列慎删」，变更前查影响面 |
| 把所有表都建在 Lakehouse | 高频小事务表的端到端延迟远高于业务容忍度 | 湖仓的表语义以大批量提交为优化目标，小事务被放大 | 追求「技术栈统一」的架构美感 | 高频小事务留在 OLTP，分析负载留在湖仓 |
| 忽视 Time Travel 成本 | 存储用量持续增长而数据量没有对应增长；历史快照查询变慢 | 未过期的快照与其引用文件不能被回收，历史查询还要读旧清单 | 只看到「可回溯」的收益，没设保留窗口与清理策略 | 显式设置快照保留与文件清理策略，并以官方文档当前版本为准 |
| 分区过度膨胀 | 表的分区数从百级升到万级以上后，规划耗时开始主导端到端延迟 | 规划要遍历的分区与清单条目远超数据文件本身的需要 | 用「按查询条件建分区」的直觉替代分区设计 | 合理分区粒度 + 隐藏分区，让剪裁由元数据完成 |

几个反模式在生产中的暴露方式，值得单独说清：

**忽视 Compaction** 的隐蔽性在于它不报错。修改数据的作业一直成功，慢下来的是别人：查询规划要读更多清单、对象存储要响应更多列举请求。它的机制是一条正反馈 —— 文件越小、数量越多，合并一次要处理的对象越多、单次合并越慢，于是合并产出跟不上产生速度。可观测的先行指标是**平均文件大小**与**每个快照的清单条目数**，它们的趋势比查询延迟更早反映问题。

**Schema Evolution 不规范**的危险在于改名与改类型都是「静默变更」。删列在读取侧通常表现为该列变空值，类型收窄在部分引擎里表现为溢出或截断，两者都不会让任务失败，只会让下游数字错。它的机制是：表格式记录的是列标识与类型的映射，下游代码里假设的是旧语义，两者的差异只在运行到特定数据时才暴露。修法是把 schema 变更当作契约变更 —— 先查下游影响面，再加列、再迁移消费方、最后才删列。

**分区过度膨胀**的代价常常被误判为「查询引擎慢」。它真正的机制是规划阶段的工作量失控：查询还没开始扫描数据，就已经在读大量分区与清单条目。可观测信号是「规划耗时占总耗时比例」随分区数上升而上升。修法不是换引擎，而是回到分区设计本身：粒度由数据量与查询条件的选择性决定，而不是由业务字段的数量决定。

**不建 Catalog** 的危险在于它不会立刻出问题。起步阶段用本地或文件系统元数据完全能跑，一个引擎读写同一张表也一切正常；出问题是在第二个引擎接入、或第一个工程师离开之后 —— 此时「表在哪里」没有权威答案，权限、保留策略、血缘各配一遍，而且没有任何机制能发现两套配置已经分叉。修法是把元数据服务当作与存储同等的基础设施来运营：它决定了「同一张表」这句话在多引擎环境里还成不成立。

这 7 条里有 4 条（忽视 Compaction、Schema Evolution 不规范、忽视 Time Travel 成本、分区过度膨胀）是同一个成因：**把表当成了「写完就不动」的静态对象**。而表的真实对象是「元数据 + 一批会持续增删的文件」，它的健康度由文件数、清单条目数、快照数与分区数四个量共同描述，任何一个脱管都会以查询变慢或账单变高的形式回到团队身上。所以在湖仓里，上线一个表只是开始，后续的常驻运维才是它能不能长期用的决定因素。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 表数百级 → 万级 | 本地或文件系统元数据 | 表状态没有唯一权威，权限与血缘无法集中 | 统一 Catalog 服务 | 存量表注册与权限迁移，期间需要双读校验 |
| 更新频率小时级 → 分钟级 | 批写 COW 表 | 每个微批重写命中文件组，写放大随频率线性增长 | 主键表（LSM / MOR） | 重写入湖作业、重建主键与去重口径 |
| 单引擎 → 多引擎 | 单一生态格式 | 非原生引擎读写能力受制于对方实现进度 | 开放表格式 + 统一 Catalog | 格式迁移与双写期，查询结果需要对账 |
| 日级文件 → 每分钟新增大量文件 | 批式 Compaction | 合并产出速度低于小文件产生速度 | 流式 / 自动 Compaction + 文件数告警 | 增加常驻调度资源，调整保留与清理策略 |
| 结构化 → 多模态与向量 | 单一 Parquet 列存 | 近邻检索没有索引支撑，只能全表算距离 | 新版本表格式的向量类型 + 专用向量索引 | 索引与数据版本需同步重建，删除与权限要重做 |
| 单区域 → 跨国多集群 | 各区域独立 Catalog | 同一张表在多处指向不同快照，口径不可比 | 统一 Catalog + 跨区域元数据同步 | 网络与一致性成本，写入方需要归属约定 |
| 固定保留窗口 → 强审计回溯 | 定期清理快照 | 清理策略与审计要求的保留期互相冲突 | 分层保留（近期快照 + 归档快照 / 冷存） | 存储分层改造成本与回溯查询延迟上升 |
| 只追加 → 行级删除频繁 | 分区表 + 批重写 | 每次删除都重写命中文件，与追加时代的成本模型完全不同 | 支持行级删除语义的格式版本 | 格式版本升级、删除语义与下游读取口径需重新对齐 |

判断该不该换，看的不是查询一年慢了多少，而是**主键更新次数 × 每次命中文件大小**这个乘积的趋势：它决定了写放大与 Compaction 压力是否在指数增长。这个乘积稳定时，加资源（扩容 Compaction、加大文件目标）就能续命；它在增长时，换结构比加资源更便宜。

保留窗口与快照数量的代价同样可以算出来：【推算】设每天提交 S 次、每次提交新增的数据量占表内数据的比例为 g、保留窗口为 K 天，则可被引用的历史文件量约为活跃数据 × (1 + S·K·g)（上界，忽略同一文件被多个快照共享的去重）；把提交频率从每天 1 次提到每小时 1 次（S 放大 24 倍）而保留窗口不变时，同一口径下可回收的对象数量按相近倍数增长。这就是「忽视 Time Travel 成本」在账单上的形态 —— 它不是某一类查询贵了，而是可回收空间被保留窗口按住不动。

### 3.7 自检清单

- [ ] 是否写清了每张表的写模式（只追加 / 主键 upsert）与主键每日更新次数，并据此选择了表格式？
- [ ] 是否量化了「单批变更条数 ÷ 被命中文件字节数」这个比值？（它直接决定写放大与是否该用读时合并）
- [ ] 是否有一个统一 Catalog 作为表状态的唯一权威，且所有引擎都通过它读写？
- [ ] 是否监控了平均文件大小与每个快照的清单条目数，并把它们做成告警而不是仪表盘摆设？
- [ ] Compaction 是否有常驻调度与产出/产生的对比指标，而不是靠人工发现慢查询后再补跑？
- [ ] schema 变更是否走契约流程：先查下游影响面、只加列与展宽类型、删除列前先让消费方迁移？
- [ ] 快照保留窗口与本表的时间旅行需求是否显式对齐，并写清了清理策略？
- [ ] 分区设计是否说明了它对应的查询条件选择性，且分区数增长会不会反过来拖慢规划？
- [ ] 高频小事务是否留在了 OLTP，而不是被统一进湖仓？
- [ ] 每一次「湖 → OLAP / 索引」的派生有没有数据截止时间，报表上是否标注了它落在哪个快照？
- [ ] 多格式共存时，「权威表」是否被写进流程与工具，而不是靠团队口头约定？
- [ ] 分层（原始 / 清洗 / 聚合）的契约是否可被检查，而不是只体现为目录命名？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 多引擎读、写入以追加为主 | Iceberg + Spark/Flink + Trino | 规划只读元数据树，与目录层级和分区数解耦 |
| 分钟级持续 upsert、要读增量 | Paimon + Flink | 写路径是向 LSM 追加，单条 upsert 与表规模无关 |
| 团队在单一 Spark 生态内 | Delta Lake + 该生态 | 表状态由事务日志回放，历史与审计天然可得 |
| CDC 更新密集且要幂等重放 | Hudi（MOR）+ CDC | 更新写进增量日志，写成本与文件大小解耦 |
| 实时与离线各有最优格式 | 多表格式共存 | 各格式只承担自己的写模式，代价不互相转移 |
| 需要对上多层质量的消费者 | Medallion 分层 | 每层一种契约，任一层可从上一层重放修复 |
| 秒级高并发点查 + 湖上事实源 | Lakehouse + 实时 OLAP | 点查用定位替代扫描，副本可从湖重建 |

> 本节小结：Lakehouse 模式的选择最终只由一条约束决定 —— **这张表的合并成本应该付在写路径还是读路径**。写模式是追加、读模式是点查，就把合并放在读侧（主键表 / MOR）；写模式是更新密集、读模式是大范围扫描，就把合并放在写侧并接受批处理带来的延迟；跨引擎与多消费者的诉求则决定元数据必须放在一个所有引擎都认的 Catalog 里，而不是某个引擎内部。其余差异（引擎生态、分层命名、OLAP 组合）都是这条主线的延伸。
>
> 落地顺序上，一条经验路线是：先做「统一 Catalog + 单一格式 + 追加为主」的最小闭环，把分区、文件大小与保留策略定下来；出现秒级入湖需求时再引入主键表承接实时链路，并显式定义权威表；点查 SLA 压不进湖时才加实时 OLAP 派生物；向量与多模态检索要在结构化链路稳定之后再叠加，否则索引与数据版本会先失去对齐。
>
> 判断演进方向时还有一个可用的经验信号：如果团队每周花在「合并、清理、对账」上的工时已经超过花在「建模与消费」上的工时，说明当前的格式或分层结构已经与服务规模不匹配，此时应当换结构，而不是继续给运维加人。
