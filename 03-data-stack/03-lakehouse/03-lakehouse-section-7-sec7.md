## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

第一，分数把场景相关的判断写成了绝对判断。典型的表会给数据湖的「存储成本」打 5 分、给数据仓库打 2 分，但同一行里的另一半信息被丢掉了：数据湖的低存储单价之所以成立，前提是它不对文件布局负责——你把更新直接写进去，低单价会被读放大、小文件与规划开销吃掉。分数只保留了「便宜」这一半，去掉的是「为什么便宜」以及「便宜在什么条件下消失」。

第二，同一维度在不同约束下权重相反。以「ACID 保障」为例：一次批量追加、无人并发写的表，ACID 的价值接近零；而一张每分钟接收 CDC upsert 的主键表，没有事务与快照隔离就无法给出「某个时刻的确定结果」，此时 ACID 不是加分项而是一票否决。对比表把两件事压成同一列，读者无从判断自己属于哪一类。

第三，打分隐藏了权重，也隐藏了候选的层次。湖仓选型其实是两层题：**架构层**（数据湖 / 数据仓库 / Lakehouse / 服务层）与**表格式层**（Iceberg / Hudi / Delta / Paimon）。把两层混在一张表里比较，必然得出「Lakehouse 样样都 4–5 分」这种既正确又无用的结论——因为格式层的取值决定了架构层的表现：同样是「Lakehouse」，用 Iceberg 承接追加、用 Paimon 承接分钟级 upsert，成本结构完全不同。

第四，打分表还会把「可选」与「必选」混为一谈。湖仓架构里的多数组件（Catalog、实时 OLAP、向量索引、图谱）都是**可选层**：它们不改变数据怎么存，只在上面加能力。可选层的正确问法不是「它好不好」，而是「它的收益能否覆盖它带来的那条刷新链路」。一张把必选项与可选项放在同一维度里打分的表，会让人误以为「分数高的那套架构更先进」，而实际上更高的分数往往意味着更多的常驻组件。

所以本章的判据顺序是：**先问写入与读取的形状（写模式决定合并成本的位置，读模式决定文件布局），再问元数据由谁托管，最后才比较引擎与生态。** 顺序不能颠倒：写模式选错，后面所有优化都在错误的成本结构上做微调。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 能力边界 | 它做不到什么（而不是能做什么） | 湖仓类的边界不在「能不能存」，而在「单条 upsert 会不会重写整个文件」「第二个引擎能不能原生读到今天的快照」 |
| 成本结构 | 成本随什么增长（数据量 / 文件数 / 提交次数 / 副本数） | 对象存储让存储不再是主导项，主导项转向请求数、清单规模与合并计算——这三项都随「文件数」而非「数据量」增长 |
| 机制契合度 | 表状态的写法和合并成本的位置是否匹配我的写模式 | 追加、主键 upsert、CDC 更新三种写模式各自只有一类结构能不付畸形成本 |
| 运维复杂度 | 需要几个人、多少常驻组件（合并调度、Catalog、快照清理） | 表格式的收益是「查询时省事」，代价是「运维时常驻」；没有常驻预算的团队会把收益全部退回 |
| 生态与锁定 | 离开它要付出什么（格式规范的实现进度、Catalog 托管方） | 多引擎读取的承诺由各引擎对该规范的实现进度决定，不由你的需求决定 |
| 演进风险 | 规范版本与路线图方向（新版本引入了什么能力、谁在实现） | 表格式的能力是按版本发布的，选型要为「下一版才有我要的能力」留出等待或迁移路径 |

### 7.2 候选方案全景

先看**架构层**候选（它们回答「数据放在哪、谁来优化布局」）：

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 数据湖（MinIO / S3 / OSS + Parquet + Spark） | 原始数据的低成本蓄水池 | 没有表状态，「表」等于目录里有什么文件，读时解释 schema | 早期大数据团队、归档与探索 | 开源 |
| 数据仓库（Snowflake / BigQuery / Doris） | 托管或自建的分析就绪库 | 表状态在引擎内部，引擎为存储布局自适应优化 | 传统 BI、报表为主的企业 | 按用量计费或开源 |
| Lakehouse（Iceberg / Paimon + Trino / Flink + StarRocks） | 开放存储上把表语义带回来 | 表状态是一层可原子替换的元数据，多引擎共享同一份数据 | 中大型平台团队 | 开源 + 云厂商托管 |
| AI 原生 Lakehouse（Iceberg 新版本 + LanceDB / 向量索引 + LLM） | 让结构化与多模态数据在同一处被检索与生成 | 在湖的表语义之上再叠一层向量或多模态索引，供近邻检索调用 | AI 应用与智能体团队 | 开源 + 托管服务 |
| 实时 OLAP 服务层（StarRocks / Doris / ClickHouse） | 承接秒级点查与高并发聚合 | 列存 + 排序键 + 主键索引，用「定位」替代「扫描」 | 电商、内容、风控 | 开源 + 商业版 |
| 向量库 / 知识图谱（专用向量数据库、图谱存储） | 承接近邻检索与实体关系检索（GraphRAG） | 专用索引结构（近邻图 / 三元组），与列存表的访问方式不同 | RAG 与知识问答团队 | 开源 + 托管服务 |

再看**表格式层**候选（它们回答「表状态怎么写下来」）：

| 表格式 | 表状态的写法 | 主要写入模式 | 强项 | 2024–2025 状态【公开】 |
| --- | --- | --- | --- | --- |
| Apache Iceberg | 多层清单：元数据文件 → manifest list → manifest → 数据文件 | 追加 + 批式更新 | 跨引擎生态最广、分区演进与隐藏分区 | V3 规范加入删除向量（deletion vectors）、增量读取与 Variant 类型；行级删除文件机制自 v2 规范起已提供，V3 在其之上降低删除开销（Apache Iceberg 社区规范说明，2024） |
| Apache Hudi | 一条操作时间线（commit / delta_commit / clean / rollback） | CDC 更新密集（COW 与 MOR 双模） | 主键索引与幂等重放、增量拉取 | 1.0 系列已发布（Hudi 官方发布说明，2024–2025；具体版本与日期以官网为准） |
| Delta Lake | 按序追加的事务日志（`_delta_log`） | 追加 + 批式更新 | 单一生态内的治理与工具链最深 | UniForm 让一份 Delta 数据可被其它格式的读者读取（随 Delta Lake 3.0 公布，2023；论文见 SIGMOD 2024，具体时间线以官方发布说明为准） |
| Apache Paimon | 表自身的 LSM 层与主键桶 | 分钟级持续 upsert | 流批一体、changelog 直接供下游流读 | 1.0 于 2024 年发布（Apache 项目发布说明，2024） |

这些候选同样只有四族。**A 族：把表状态写在引擎内部**（数据仓库）——优化最深、被第二个引擎读最难；**B 族：把表状态写在开放元数据里**（数据湖为「没有」、Lakehouse 为「有」）——共享最容易、布局运维全归自己；**C 族：派生服务层**（实时 OLAP、向量索引、图谱）——数据可从 A 或 B 重建，它的正确性不依赖自身持久性；**D 族：多模态接入层**（AI 原生 Lakehouse）——通常不是新存储，而是在 B 族之上加索引与接口。

先分族能省掉一半比较：族内是同一机制的参数差异（哪个格式的清单写得更省、哪个 OLAP 的点查更快），跨族才是机制不同。而本章最常被混起来比较的一对，恰好跨了族：**「Lakehouse 的查询性能」与「数据仓库的查询性能」**——前者取决于你有没有把合并与布局运维住，后者由引擎自己保证。这两者不是同一件事，分数无法表达这个区别。

两层候选之间是耦合的，而不是并列的：**架构层的承诺由格式层兑现**。选了 Lakehouse，就同时承诺了「多引擎共享同一份数据」与「布局由自己维护」两件事；前者的实现取决于格式规范被各引擎接受到什么程度，后者的实现取决于你选了哪种写模式。所以选型时应当先定格式层（它决定写入能不能承受），再定架构层（它决定谁能读到）——反过来做，通常会得到一个「架构先进但写不动」的方案。

### 7.3 机制差异：为什么它们表现不同（核心节）

本节按四个机制维度展开。前两个维度决定「写入成本落在哪」，后两个决定「读到的数据是谁的、有多新」——湖仓的绝大多数事故都能归到这两组问题上。

这四个维度也可以反过来当作失效排查的顺序：查询变慢时先看维度一（元数据规模是否随提交次数膨胀），再看维度二（合并是否跟得上产生速度），然后看维度三（是不是有第二个 Catalog 或绕过 Catalog 的写入方），最后看维度四（派生层的数据截止时间是不是落后了）。按这个顺序查，比按「哪个组件报错」查更接近根因，因为湖仓的故障通常不报错——它表现为变慢、变贵、数字停在昨天。

#### 7.3.1 表状态怎么写下来：没有 / 引擎内部 / 多层清单 / 时间线 / LSM

**机制是什么**：一张表的「此刻状态」（哪些文件有效、schema 是什么、哪个快照是当前版本）以什么形式被记录下来。

**它在各候选中的实现差异**：

| 候选 | 表状态的载体 | 谁来解释它 | 提交的原子单位 |
| --- | --- | --- | --- |
| 数据湖 | 没有载体，只有目录内容 | 每个读者自行解释 | 没有提交概念，文件出现即生效 |
| 数据仓库 | 引擎内部 catalog 与存储格式 | 只有该引擎 | 引擎的事务机制 |
| Iceberg（Lakehouse） | 元数据文件 → manifest list → manifest → 数据文件 | 任何实现该规范的引擎 | 原子替换元数据文件里的快照指针 |
| Delta Lake（Lakehouse） | 按序追加的事务日志 | 能回放该日志的引擎 | 追加一个日志版本 |
| Hudi（Lakehouse） | 操作时间线 | 能读该时间线的引擎 | 时间线上的一次 commit |
| Paimon（Lakehouse） | LSM 的层与主键桶 + 快照 | 能读其快照的引擎 | 快照提交（后台持续合并） |

**由此必然导出的性质**：因为数据湖没有表状态，所以「表」这个概念不存在，任何两个读者对同一份目录可以给出不同解释（schema 漂移、分区约定不一致都无人拦截），代价是这个自由会以「同目录不同结果」的形式在协作时集中爆发；因为 Lakehouse 把表状态显式写成可原子替换的元数据，所以任意时刻只存在一个完整快照、并发写不会产生半可见状态，代价是这层元数据本身成为需要维护的资产——提交越频繁，产生的清单越多，规划时要读的元数据越多。

这里有一个容易被忽略的定量关系：**元数据规模由清单条目数决定，而清单条目数随活跃文件数与提交次数增长**——活跃文件数 ≈ 数据量 ÷ 目标文件大小，所以真正把它推高的是「文件切得多碎、提交多频繁」，不是字节数本身：一批数据翻倍而文件大小不变，清单条目也会翻倍；同样的数据量若文件更大、提交更少，元数据就小得多。于是「每天提交一次、每次几十 GB」与「每分钟提交一次、每次几十 MB」在数据量上相同，在清单数量上却相差约三个数量级【推算】（每天 1 次 vs 每分钟 1 次 = 24 × 60 = 1,440 ≈ 1.4 × 10³ 倍，推导只用到两侧的提交频率之比）——后者会把规划阶段先压垮。

**公开证据**：Iceberg 由 Netflix 开源，其后进入 Apache 基金会并于 2020 年毕业为顶级项目【公开】（Apache 软件基金会官方项目页 Apache Iceberg，2020 年毕业；项目当前状态以官网当前版本为准）；Hudi 由 Uber 发起并开源【公开】（Uber 工程博客，2017）；Delta Lake 由 Databricks 于 2019 年开源【公开】（Databricks 官方公告，2019）；Paimon 前身为 Flink Table Store，2024 年发布 1.0【公开】（Apache 项目发布说明，2024）。

**失效条件**：当每批写入的数据量小于「一个合理大小的数据文件」时，清单与数据文件的数量比会向元数据一侧倾斜，此时「规划与目录解耦」的优势反转成「元数据自身成为瓶颈」。修法不是换格式，而是提高单批写入量，或改用具主键合并能力的 LSM 型格式。

#### 7.3.2 合并成本放在写路径还是读路径

**机制是什么**：一次更新到达时，代价是「当场重写」还是「先记下来、读的时候再合」。

**它在各候选中的实现差异**：

| 位置 | 归属候选 | 写入成本 | 读取成本 | 需要的常驻运维 |
| --- | --- | --- | --- | --- |
| 写侧（COW） | Iceberg / Delta / Hudi COW 表 | 与「被命中文件的大小」相关 | 读路径干净 | 文件大小与批次的调优 |
| 读侧（MOR / LSM） | Hudi MOR、Paimon | 与「变更条数」相关 | 需要现场合并，读放大随未合并量增长 | Compaction 是常驻工作，不是一次性任务 |

**由此必然导出的性质**：因为 COW 在写入时重写命中文件，所以单条 upsert 的成本与文件大小挂钩、与表的总规模无关，代价是写放大会被「文件大小 ÷ 单批变更量」这个比值放大——文件越大，为了改几行而重写的字节越多；因为 MOR / LSM 只追加增量，所以写入成本与「被更新文件的大小」解耦，代价是读路径要合并，且必须有人常驻做 Compaction，否则读放大持续累积直到查询不可用。

**公开证据**：Hudi 官方把 COW / MOR 两种表类型作为并列选项对外说明，MOR 以「写入时追加日志、读取时合并」为定义【公开】（Apache Hudi 官方文档的表类型章节，2024–2025 年版本；以官网当前版本为准）；Paimon 的 changelog 机制把写入流本身暴露为下游可读的变更日志【公开】（Apache 项目发布说明，2024）。写放大的量级可以由公式直接算出来，见 §7.4。

**失效条件**：写入集中在少数主键上时，主键哈希分桶会把同一个热点 key 永远路由到同一个桶，该桶的写入与合并被串行化——此时「单条 upsert 与表规模无关」的优势反转成热点桶排队。判断方法是看主键分布的倾斜度，而不是看平均写入速率。

#### 7.3.3 元数据的权威在哪：引擎内部 / 各引擎各读各的 / 统一 Catalog

**机制是什么**：「当前快照指针在哪、谁能改它」由谁负责。

**它在各候选中的实现差异**：

| 权威位置 | 归属候选 | 「同一张表」成立的范围 | 典型故障 |
| --- | --- | --- | --- |
| 引擎内部 | 数据仓库 | 仅该引擎 | 第二个引擎要么不能读，要么读到自己那份副本 |
| 无权威（文件系统路径） | 数据湖、部分 Lakehouse 起步态 | 取决于路径约定 | 两个引擎各写一份元数据，指向不同文件集 |
| 统一 Catalog 服务 | 采用 REST / 元数据服务形态的 Lakehouse | 所有通过该 Catalog 读写的引擎 | Catalog 自身成为单点，可用性与变更流程需按基础设施对待 |

**由此必然导出的性质**：因为表状态的权威只能有一个，所以只要出现两个 Catalog（或一个 Catalog 加一个「直接写路径」的引擎），「同一张表」这句话就已经不成立——两侧会在无人察觉的情况下指向不同快照，读出来的数字都对，但不可比；因为 Catalog 决定的是指针而不是数据，所以它出故障时的表现不是「查不到数据」而是「查到的数据停留在某个旧版本」，这类故障比宕机更难发现，监控必须盯「当前快照的时间戳」而不是只看服务存活。

**公开证据**：Lakehouse 概念由 Databricks 于 2020 年提出，其形态即以「开放表格式 + 统一元数据服务」为前提【公开】（Databricks 官方博客，2020）；Snowflake 于 2024 年开源其 REST Catalog 实现（Apache Polaris）并将其捐入 Apache 基金会孵化【公开】（Snowflake 官方公告，2024；版本号与毕业时间以官方发布说明为准）；这条路线被多家厂商同时采纳这一点，可由各厂商 Catalog 产品页自行核验。

**失效条件**：单引擎、单写入方时，Catalog 的价值不兑现，只剩多一个需要运维与升级的常驻组件。此时把表状态留在引擎内部是更经济的选择。

#### 7.3.4 服务层是派生还是权威

**机制是什么**：当数据被复制一份给查询服务层（实时 OLAP、向量索引、图谱）时，那一份的地位是「可重建的派生」还是「可被写入的副本」。

**它在各候选中的实现差异**：

| 派生载体 | 数据来源 | 正确性依赖 | 失效表现 |
| --- | --- | --- | --- |
| 实时 OLAP（StarRocks / Doris / ClickHouse） | 湖上表批量导入或流式写入 | 刷新链路的成功与时效 | 查询始终成功，但数字停在某个更早的时间点 |
| 向量索引（含 Iceberg 新版本里的向量类型与专用向量库） | 湖上表 | 索引与数据版本同步 | 召回结果对应旧版本的文本或旧模型产出的 Embedding |
| 知识图谱（GraphRAG 的实体与关系） | 湖上原始文本 | 抽取作业是否跟上数据变更 | 关系过时，生成内容基于已被修正的事实 |

**由此必然导出的性质**：因为派生副本可以从湖重建，所以它的持久性不重要、可以随时重算，代价是**它没有自我纠错能力**：刷新链路失败时它不会报错，只会安安静静地保留旧版本——因此每个派生层都必须携带「数据截止时间」并被下游读到，否则「查询成功」会被误读成「数据新鲜」；因为向量索引与图谱都依赖模型或抽取逻辑，所以它们的过期有第二重来源（模型换了、数据没变，索引也需要重建），这类过期无法通过比对数据版本发现，只能通过记录「索引构建时所用模型版本」发现。

**公开证据**：Iceberg V3 规范加入了向量类型，多模态表格式的探索也在公开进行【公开】（Apache Iceberg 社区规范说明，2024；具体条目以官方规范当前版本为准）；LanceDB 等面向 AI 的多模态列式库在 2023–2024 年间进入可生产阶段【经验】（成立时间与版本号以官方发布说明为准）；本仓 [§ 5 前沿演进](03-lakehouse-section-5-ai.md) 的 §5.2 给出了 Lakehouse + 向量库、Lakehouse + GraphRAG 的公开实现方向。

**失效条件**：当派生层的更新频率低于湖上的变更频率、且没有截止时间标注时，秒级响应的优势会反转成「秒级地读到过期数据」。此时应当先把刷新链路做成可监控、可对账的常驻作业，再谈 SLA。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 对象存储容量 × 保留时长
     + 对象存储请求数（列举 + 读写，随文件数增长）
     + 合并计算（Compaction 的读写字节量）
     + 元数据规模（清单 / 快照 / 分区数）与其规划开销
     + 派生副本（OLAP / 向量索引 / 图谱）的存储与刷新
     + 运维人力（常驻组件数 × 所需技能）
```

| 候选 | 主导项 | 随什么增长 | 隐性成本 |
| --- | --- | --- | --- |
| 数据湖 | 存储（单价低） | 数据量 | 无表状态导致的重复副本、口径修复与全量扫描 |
| 数据仓库 | 计算（常备或按用量） | 查询次数 × 扫描量；数据规模 | 数据离开引擎要复制；存储单价高于对象存储 |
| Lakehouse | 合并计算 + 元数据规模 | 文件数与提交次数（不是数据量） | 常驻 Compaction、Catalog 运维、对象请求数 |
| AI 原生 Lakehouse | 向量索引的构建与重建 | 向量条数 × 维度 × 更新频率 | 索引与数据版本、模型版本双双需要对齐 |
| 实时 OLAP 服务层 | 常驻 OLAP 集群 | 副本规模 + 查询并发 | 两份副本、两条刷新链路、跨侧查询的改写 |
| 向量库 / 图谱 | 索引存储（与原始向量同量级或更高） | 实体与关系数量 | 抽取与索引重建算力、权限对齐 |

五条可算的账，把「主导项」落到数字上。

**账一：写放大的量级。**【推算】设单次 upsert 命中 N 个数据文件、目标文件大小为 F 字节、本批变更的原始数据量为 D 字节，则写放大 ≈ N·F ÷ D。取目标文件大小 F = 128 MB【经验】（对象存储场景常见的文件大小区间下沿，实际取值随引擎与场景变化），单批变更量 D = 1 KB，N = 1 时写放大 ≈ 128 × 10⁶ ÷ 10³ ≈ 1.3 × 10⁵。推导链只有乘除，前提是 COW 需要重写被命中的整个文件。结论是：更新密集场景下写放大可以到五个数量级，这正是 CDC 场景应当选读时合并的依据。

**账二：元数据规模随提交次数增长。**【推算】设每天提交 S 次、每次提交新增一批清单；把提交频率从每天 1 次提到每小时 1 次（S 放大 24 倍），在数据量与保留窗口不变的前提下，规划阶段需要遍历的清单条目按相近倍数增长。这条账说明为什么「把批改成微批」在数据量不变时也可能让查询变慢：增长的项是元数据，不是数据。

**账三：派生副本省的是比例，不是绝对值。**【推算】设湖内 1 PB 数据中只有 5% 需要秒级点查，则派生 OLAP 副本的规模约为 1 PB × 5% = 50 TB；相比把 1 PB 全量复制一份（100% 复制），省下 20 倍。前提是「只有一小部分数据有高 SLA 需求」——如果 80% 的数据都被要求秒级，派生层的成本会接近全量复制，此时应当先质疑 SLA 是否真的需要被满足。

**账四：向量索引本身是一份数据。**【推算】设 10⁸ 条向量、每条 768 维、每维用 4 字节浮点存储，则裸向量约为 10⁸ × 768 × 4 字节 ≈ 3.1 × 10¹¹ 字节 ≈ 307 GB；近邻检索索引（如基于近邻图的实现）除原始向量外还要存储邻居结构，其规模通常与原始向量处于同一量级或更高（具体倍数取决于索引实现与召回参数【经验】）。结论是索引不能用「加个字段」的方式对待，它需要与数据同等的容量规划、版本管理与重建流程。

**账五：刷新频率决定派生层的真实成本。**【推算】设某 OLAP 派生表每天刷新一次，其读写量记为「副本大小 × 1」；若在没有增量刷新能力的前提下改为每分钟刷新一次，则每天的读写量按 24 × 60 = 1,440 倍增长。即使采用增量刷新，每天的调度次数同样放大约 1,440 倍，调度与状态管理的开销随之上升。推导链只有乘法，结论方向明确：把刷新频率从「天」提到「分钟」时，被放大最猛的是**作业次数与状态管理**，而不只是数据量。

还有一个不进入账单但进决策的项：**常驻运维**。它在成本函数里的形式是「常驻组件数 × 所需技能稀缺度」，而在湖仓里这一项比在多数架构里更重，因为表格式把「引擎本来会自己做的事」（合并、清理、布局优化）交给了使用方。判断两个方案是否真的成本接近时，应当先把这一项补齐：它不会出现在账单上，但会以「每周有几天在救火」的形式出现。

### 7.5 决策树（每个分支都要有阈值依据）

```
湖仓选型进来
├─ ① 这张表是否存在按主键的更新、删除或 CDC 变更？
│   ├─ 否（只追加、一次写多次读）→ 开放格式的分区表（Iceberg 默认）
│   └─ 是 → ② 单批变更量相对目标文件大小的比值？
│            ├─ 变更量 ≥ 文件大小量级（批式重写可接受）→ COW 表（Iceberg / Delta / Hudi COW）
│            └─ 变更量 ≪ 文件大小（持续小批 upsert）→ 读时合并结构（Hudi MOR / Paimon 主键表）
├─ ③ 需要多少个引擎原生读写同一份数据？
│   ├─ 1 个 → 表状态可留在引擎内部（数据仓库形态也成立）
│   └─ ≥2 个 → 开放表格式 + 统一 Catalog
├─ ④ 是否存在点查 / 高并发聚合的响应时间要求？
│   └─ 是 → 加实时 OLAP 派生层（湖为权威、OLAP 为派生，带数据截止时间）
├─ ⑤ 是否存在近邻检索或多模态消费？
│   └─ 是 → 向量索引 / 图谱作为派生层，与数据版本、模型版本同时对齐
└─ ⑥ 是否存在跨区域或跨云读者？
    └─ 是 → Catalog 必须统一（REST 形态），并接受跨区域元数据同步成本
```

**阈值依据**（与树的节点一一对应）：

- **① 有无更新**：这是最硬的一条分界，因为它决定「数据文件是否必须可变」。只追加的表任何时刻都能用文件级统计做剪裁，不需要删除文件、不需要合并读路径；一旦出现行级更新，数据文件不可变的前提就要求把更新表达为新文件加失效声明。判定方法很直接：数一下该表每天有多少条针对存量行的变更，而不是看它每天有多少条新数据。
- **② 变更量 ÷ 文件大小**：阈值取「变更量达到文件大小的同量级」。依据是 §7.4 账一：写放大 ≈ 被命中文件字节数 ÷ 单批变更字节数。当变更量本身已经与文件同量级时，重写整个文件的相对浪费有限，COW 的读路径干净更划算；当变更量比文件小几个数量级时，写放大会达到数万倍以上，必须改用读时合并。文件大小的合理区间取 128 MB 到 512 MB 量级【经验】，随引擎默认值与对象存储特性变化。
- **③ 两个引擎**：开放表格式的收益来自第二类读者。只有一个读者时，表状态留在引擎内部可以获得更深的自动优化（自动聚簇、自动物化视图），引入开放元数据只增加 Compaction 与清单维护。注意「两个引擎」指原生读写，不包含「通过导出物间接访问」。
- **④ 点查响应要求**：阈值是「湖上引擎能否在要求的响应时间内给出答案」。湖上查询要先读元数据树再剪裁文件，其成本随文件数与清单规模变化，与点查所需的「按主键直接定位」不是同一种成本结构；当要求落在百毫秒到秒级且并发较高时【经验】，需要一层带主键索引或排序键的存储来把扫描换成定位。具体响应时间应以目标引擎的实测为准，不宜照搬某个数字。
- **⑤ 近邻检索需求**：阈值是「是否需要按相似度而非按相等条件筛选」。列存与分区剪裁只能回答相等与范围条件，近邻检索需要专门的索引结构；且如 §7.4 账四所示，索引规模与向量数据同量级，因此这条一旦成立，容量规划就要把索引当作第二份数据来算。
- **⑥ 跨区域读者**：阈值取「是否存在不同区域的读写方」。依据是 §7.3.3：只要出现两个 Catalog，两侧就会指向不同快照；跨区域环境下各区域自建 Catalog 是最自然的做法，也最容易让「同一张表」在不同区域给出不同结果。因此需要在「统一 Catalog 的同步成本」与「口径不可比」之间做显式取舍。

树的用法是按顺序自问，并在每个节点上留下一条可被复核的记录：节点 ① 与 ② 决定表格式，节点 ③ 决定要不要统一 Catalog，节点 ④ ⑤ 决定要不要加派生层（实时 OLAP、向量索引或图谱），节点 ⑥ 决定元数据是否跨区域统一。前三个节点答完之后再考虑引擎与生态——引擎是执行者，它无法弥补写模式选错带来的成本结构问题。若某个节点的答案暂时无法确定，正确的动作是先去量（每天多少条存量更新、每批变更多少字节、有几个原生读者），而不是先选一个「看起来通用」的方案。

### 7.6 选型矩阵与组合

**表格式选型矩阵**（格式层的取值决定架构层的表现）：

| 场景 | 首选格式 | 备选 | 不选备选的原因（机制层面） |
| --- | --- | --- | --- |
| 跨引擎读、写入以追加为主 | Iceberg | Delta | 非原生引擎的读写能力取决于对方对该格式的实现进度 |
| 分钟级持续 upsert、要读增量 | Paimon | Hudi MOR | 读路径要现场合并基础文件与日志，读放大随未合并日志增长，且清理与保留策略要单独配 |
| CDC 更新密集、需要幂等重放 | Hudi（MOR） | Paimon | 其合并语义由 merge-engine 配置决定，与 Hudi 的 preCombine 需逐项对照，迁移时要重建主键与去重口径 |
| 团队深度在单一生态内、要训练与治理一体 | Delta | Iceberg | 开放格式需要自建训练与治理的集成层 |
| 多模态与向量检索 | Iceberg 新版本 + 专用向量索引 | 独立向量库 | 索引与数据版本需要双份对齐，多一条索引重建链路 |
| 跨国 / 多云统一口径 | Iceberg + 统一 REST Catalog | 各区域自建 Catalog | 多套 Catalog 会让「同一张表」在多处指向不同快照 |
| 只追加、但表数量极大（万级及以上） | Iceberg + 统一 Catalog 服务 | 文件系统路径约定 | 表数量跨过「百级 → 万级」这一跃迁区间后，权限、血缘、保留策略无法按表逐个人工维护【经验】（区间口径与 [§ 3 设计模式与范式](03-lakehouse-section-3-sec3.md) 的规模跃迁表一致；具体拐点随团队人数与表的粒度变化） |
| 需要保留长期历史并支持快照回溯 | 任一开放格式 + 显式保留策略 | 只保留当前版本 | 没有保留窗口时无法回溯；保留窗口过大时存储与清理成本同时上升 |

**架构层选型矩阵**：

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 传统 BI 报表为主、T+1 | 数据仓库（Snowflake / BigQuery / Doris） | Lakehouse | 单引擎、无多模态诉求时，开放元数据只增加运维 |
| 超低成本、以归档与探索为主 | 数据湖（MinIO / S3 + Spark） | Lakehouse 从原始层起步 | 上重治理会把探索变成填表 |
| 多源异构 + 多引擎 + 同时服务 BI 与 AI | Lakehouse | 数据仓库 + 定期导出 | 导出产生第二份副本与口径分叉 |
| 秒级看板、高并发点查 | Lakehouse + 实时 OLAP | 纯数据仓库 | 湖上规划与扫描成本给不出这类 SLA |
| AI 平台 + 多模态 | AI 原生 Lakehouse（+ 向量索引 / 图谱） | 湖 + 独立向量库 | 索引与数据版本需要双份对齐 |

**常见组合**（原 §7 的 5 条组合在这里逐一保留，并补一条格式混合的边界纪律）：

- **组合一：Lakehouse + 实时 OLAP**（StarRocks / Doris 做查询层，湖做存储层）
  - 职责边界：湖是权威与历史账本，OLAP 是派生副本，可随时从湖重建。
  - 适用条件：实时 BI、秒级查询，且数据必须保留单一事实源。
  - 运维代价：第二条刷新链路与第二套监控；OLAP 表必须带数据截止时间，否则刷新失败会表现为「看板一直可用，数字停在昨天」。
- **组合二：Lakehouse + 传统数仓**
  - 职责边界：湖存原始与历史全量，仓存精化后的分析就绪结果。
  - 适用条件：超大规模企业，既有仓的建模资产要保留，又要引入多源与多模态数据。
  - 运维代价：跨湖仓查询的下推与统计信息传递受连接器限制，同一逻辑在两种写法下性能可以差一个量级；两侧元数据需人工维护对应关系。
- **组合三：Iceberg + Paimon（混合）**
  - 职责边界：Iceberg 做离线主仓（承接批写与跨引擎读），Paimon 做实时入湖（承接分钟级 upsert 与 changelog）。
  - 适用条件：复杂业务、离线与实时需求同时存在且各自对格式有不同最优解。
  - 运维代价：两套元数据、两套 Compaction、两套快照与保留策略；跨格式没有共同事务边界，且必须显式指定「哪个是权威表」，否则同一实体会出现两个版本。
- **组合四：Lakehouse + 向量库**
  - 职责边界：湖存结构化数据与原始文档，向量库存 Embedding，联合查询时以实体 id 对齐。
  - 适用条件：AI 应用需要同时给出结构化事实与非结构化召回。
  - 运维代价：索引与数据版本必须同步重建（模型或数据更新后索引会静默过期）；两侧权限模型要对齐，否则召回内容可能绕过湖上的权限。
- **组合五：Lakehouse + 知识图谱**
  - 职责边界：湖存原始文本与实体，图谱存关系，用于 GraphRAG 的关联检索。
  - 适用条件：智能问答需要在多跳关系上检索，而非只在向量相似度上检索。
  - 运维代价：实体与关系的抽取是另一条作业链路，其延迟与错误会直接反映为生成内容基于过时关系；图谱的 schema 演进与湖上表的演进需要分别治理。
- **组合六：多表格式共存下的权威纪律**（[§ 3 设计模式与范式](03-lakehouse-section-3-sec3.md) 已给出，此处作为组合的补充约束）
  - 职责边界：同一业务实体只能有一个权威表，另一份必须是可重建的派生结果。
  - 适用条件：实时与离线各需一种格式时。
  - 运维代价：当「哪个是权威」没有写进流程与工具时，两套系统都可被写入，报表无法说明自己在读哪一份——这是组合三最常见的失效方式。

组合的共同记账规则：**每多一个物化副本，就多一条刷新链路、一套监控与一次口径对齐**。判断组合是否过度的问法是：同一个业务实体在几个系统里有可被直接写入的表示？多于一个的每一份，都需要一条对账机制。

### 7.7 选错的代价与迁移成本

**反模式：用开放格式承接高频小批 upsert**。症状是按「社区最大、跨引擎最好」选定 Iceberg，然后把分钟级 CDC 直接写进去。后果是每个微批都重写命中文件，写放大按 §7.4 账一可以到数万倍以上，同时产生大量小文件与清单；这三件事互相放大——文件越多、清单越多，合并越慢；合并越慢、文件越多。维护成本从一次性选型变成一条永远追不上的运维队列。正确做法是先量化「主键每日更新次数 × 每次命中文件大小」，再决定 COW 还是读时合并。

**反模式：没有统一 Catalog，却要求多引擎一致**。症状是两套元数据并存，或用文件系统路径当作「表」的定位方式。后果是两侧指向不同快照，读出来的数字都对但不可比，且故障表现为「数据停在旧版本」而不是报错。正确做法是把 Catalog 当基础设施运营：它决定「同一张表」这句话是否成立。

**反模式：把 Compaction 当成一次性任务**。症状是上线时做过一次合并，之后只监控「写入是否成功」。后果是平均文件大小持续下降、规划耗时持续上升，而这条反馈是正反馈（文件越碎越难合并）。正确做法是把 Compaction 做成常驻调度，并把「平均文件大小」与「每个快照的清单条目数」做成告警而不是仪表盘摆设。

**反模式：派生层不标数据截止时间**。症状是 OLAP 表、向量索引从湖刷新，但下游看不到它们对应哪个快照/哪个模型版本。后果是刷新失败时查询依然成功，看板继续展示旧数字；索引过期时召回结果与当前事实不符。正确做法是每个派生层都携带「数据截止时间 + 索引所用模型版本」，并让消费方能读到。

**反模式：为了技术栈统一把不合适的负载搬进湖仓**。症状是所有表（含高频小事务表）都被统一到同一种格式与同一个 Catalog。后果是这些负载在不适配的机制上被放大（写放大、规划开销），而湖仓的收益（多引擎共享）对它们并不存在。正确做法是按 §7.3 的四个维度分别取值，接受「两种结构各承担自己擅长的写模式」。

**反模式：只按查询性能选格式，不看写入形状**。症状是选型材料里只有「TPC 类查询跑得多快」的对比，没有「主键每日更新次数」与「每批变更字节数」。后果是格式与写模式错配，性能测试里的好成绩在生产上被写放大与合并积压抵消——而且这类问题不会在上线当天出现，通常在一个季度后以 Compaction 追不上小文件产生速度的形式暴露。正确做法是把写模式的量化指标放在选型材料的第一页。

这六条反模式有一个共同成因：**把湖仓当成一个「产品选型」问题，而没有把它当成一份需要长期履行的运维契约**。它们各自承担的代价是：

- 「开放格式承接高频小批 upsert」——承担数万倍量级的写放大与随之而来的合并积压；
- 「没有统一 Catalog」——承担「数据停在旧快照」且不报错的隐性一致性成本；
- 「Compaction 当一次性任务」——承担一条永远追不上的运维队列；
- 「派生层不标截止时间」——承担「查询成功但数据过期」的误判成本；
- 「为技术栈统一牺牲适配性」——承担个别负载被放大后的成本与延迟；
- 「只看查询性能」——承担写模式错配在数月后集中爆发的成本。

共同点是这六项都不在上线当天显现。因此选型评审值得单独问一句：「这个方案在投入生产一个季度后，哪一项成本会变大」——答不上来，通常意味着方案里有一个尚未被识别的耦合（最常见的是文件数、提交次数或快照保留窗口）。

**换成另一个要动什么**（工作量量级为相对量级，随存量表数量与并发写入方数量放大【经验】）：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 数据湖 → Lakehouse | 小（数据不动，补元数据与 Catalog） | 小（多为类型与函数对齐） | 中（新增文件、清单与快照运维） | 中 |
| 数据仓库 → Lakehouse | 中（可导出为开放格式） | 中（性能特征变化需重写重查询） | 大（Compaction、Catalog、保留策略全新增） | 大 |
| COW 表 → 读时合并表 | 中（格式转换 + 主键与去重口径重建） | 小（查询基本不变） | 大（Compaction 从调优变成常驻） | 中 |
| 单一格式 → 多表格式共存 | 小（新增链路） | 中（跨格式查询需显式路由） | 大（两套元数据、两套合并、两套保留） | 中 |
| 无 Catalog → 统一 Catalog | 小（注册存量表） | 小 | 中（权限与血缘迁移、双读校验期） | 中 |
| 结构化 → 多模态 / 向量 | 无（新增索引） | 大（新的检索接口与召回评估） | 大（索引与模型版本的同步重建） | 大 |

这张表里最容易被低估的一列仍是「运维重建」：格式与 Catalog 都能换，但换完之后新增的常驻工作（合并、清理、对账、索引重建）如果没有对应的人，迁移会在半年后以「查询变慢、成本变高」的形式回退成事故。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 追加为主、多引擎读同一份数据 | Iceberg + 统一 Catalog | 表状态是开放的多层清单，规划与目录层级解耦 |
| 分钟级持续 upsert、要读增量 | Paimon + Flink（或 Hudi MOR + CDC） | 写路径是向 LSM 追加，单条 upsert 与表规模无关 |
| 更新密集且要幂等重放 | Hudi MOR | 更新写进增量日志，写成本与文件大小解耦 |
| 团队在单一生态内、要训练与治理一体 | Delta + 该生态 | 表状态由事务日志回放，历史与审计天然可得 |
| 湖上事实源 + 秒级点查 | Lakehouse + 实时 OLAP（湖为权威） | 用定位替代扫描，派生副本可从湖重建 |
| 实时与离线各有最优格式 | Iceberg + Paimon 共存 | 各格式只承担自己的写模式，但必须显式指定权威表 |
| 多模态检索 / 智能问答 | 向量索引或图谱作为派生层 | 近邻与关系检索需要专门索引，且规模与数据同量级 |
| 只有 BI 一类消费方、无并发写 | 数据仓库 | 单引擎时表状态留在引擎内部，换来自动优化与更少常驻组件 |

> 本节小结：Lakehouse 选型里唯一真正起决定作用的那条差异是**合并成本被放在了写路径还是读路径**——写模式是追加、读模式是点查，就把合并放在读侧（主键表 / MOR / LSM）并把 Compaction 变成常驻工作；写模式是更新密集、读模式是大范围扫描，就把合并放在写侧并接受批处理带来的延迟。其余维度（Catalog 形态、是否加 OLAP、是否加向量索引）都是在这条主线确定之后的增量：它们决定的是「谁能读到」和「多久读到」，而不是「写入能不能承受」。
>
> 一个可操作的顺序是：先数每天有多少条针对存量行的更新（定 COW / MOR），再数同一份数据的原生读者个数（定表状态放在引擎内还是开放元数据），最后才看点查 SLA 与检索需求（定要不要加派生层）——这三个数都在 §7.5 的树上，且都不需要在选完产品之后才能回答。
>
> 最后一条提醒与规模跃迁有关：湖仓的模式不是选一次就不变的。当更新频率从「小时级」升到「分钟级」、表数量从「百级」升到「万级」、原生读者从一个引擎变成三个引擎时【经验】（这三条跃迁区间与 [§ 3 设计模式与范式](03-lakehouse-section-3-sec3.md) 的规模跃迁表同一口径，具体拐点随团队人数、表的粒度与负载形态变化），原来的模式会开始疼——疼的位置每次都不一样，但判断方法相同：看文件数与清单条目的趋势，而不是看查询延迟的趋势，因为前者总是先动。
>
