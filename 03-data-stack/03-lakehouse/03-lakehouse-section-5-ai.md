## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

Lakehouse 这一层的特殊性在于：**它是所有 AI 方向的前置条件，本身却很少是 AI 方向**。把五条方向摊开看，四条改的是湖仓之上的接口——AI 元数据改的是「说明是谁写的」，自然语言查询改的是「谁来问」，Agent 触达改的是「调用者是谁」，表格式自动优化改的是「调参的接口」（决策仍由统计信息与规则做出，模型换掉的只是解释与建议的表达方式，见 §5.2.3）；只有一条真的碰到湖仓自己的机制：**把向量变成湖表的一列**，即表格式类型系统的变化（见 §5.2.2）。五件事不在同一层，因此既不能一起排期，也不能互相替代：把「AI 元数据」做完，不会让合并变快一分，也不会让近邻检索可用；反过来，最容易被「自治」这个词包装的那条（表格式自动优化）恰恰没碰到湖仓的机制——它换的是调参的接口，不是决策机制。

第二个问题是没有时间维度。同一个清单里，「已 GA 且有人在生产用」与「路线图里的条目」被并列成同样的句式，读者据此排路线图就会踩空：前者值得投人，后者连预算都不该批。本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（或版本化发布的规范）；② 有第三方（非厂商）公开生产案例；③ 接口稳定、可预期。
- **L2 可试点**：已可用但接口 / 生态未稳；或仅有厂商自有案例（表现为 ①③ 大体满足而 ② 不满足）；或只在小规模被验证。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。

为什么是这三条，而不是「有没有厂商在推」：厂商在推是营销事实，不是成熟度。① 回答「它是发布过的，还是演示过的」；② 回答「出问题时我能不能找到别人的经验，而不是厂商的承诺」；③ 回答「我明年会不会为它重写一遍」。**② 只有两种命运：满足，或降为 L2。** 不存在「L1 的边界案例」这种写法，也不存在「把 L1 的适用范围缩小到某一层」的写法——那等于换了判据却不动名字。

**本主题对本书的 L1 判据做了如下修正：第②条里的「厂商」在本主题读作「该机制的发布方」，即表格式的发起方**——Iceberg 的 Netflix、Delta 的 Databricks、Hudi 的 Uber、Paimon / Flink 生态的阿里。判定「第三方」的标准因此是**发布方与发起方不是同一方**，发起方自己的自述不计入 ②（那正是 L2 定义里「厂商自有案例」的形态）。理由是：本主题评的是**机制**，而这条机制由四个分属不同组织、且都已捐入基金会或开源治理的表格式共同承载，不存在传统意义上的「卖方」，② 要排除的风险在这里只可能表现为「发起方自述」。**这条修正不放宽门槛，只收紧**；除它之外，本节不对本书的 L1 判据做任何其它修正，所有 AI 能力方向一律按原判据判定。

第三个问题是本主题特有的三处易错，写到时必须逐条避开：

- **「自治」不是可核验的判据**。被冠以「自治 / 自驱」的现有能力（自动合并、自动聚簇、自适应执行）靠的是统计信息与规则，这些机制早于 LLM 存在；真正的「自治」目前没有可核验的定义。判定方法：看产品文档里这个动作是**建议**还是**自动执行**，以及自动执行有没有**单步撤销与失败回退**——只有前者没有后者，就还是一个规则引擎。
- **预览与 GA 混淆**。各平台的自然语言取数、向量检索一类能力在不同年份处于不同状态，判断某个能力现在能不能依赖，看该产品的发布说明里这一条目的状态与生效条件，不看发布会。
- **引用事故**，本主题高发三处：把「Iceberg V3 的**删除向量**（deletion vector，行级删除的实现细节）」读成「**向量类型**（列类型）」——两者名字相近、毫无关系；把论文的会议与年份记错（项目名对而会议错是最常见的形态）；把「某版本支持某特性」写成语态完成的事实而实际是路线图条目。三处的核验入口都在官方：规范的类型章节、会议论文集与项目 publications 页、该版本的 release note。

> 本主题下唯一处在 L1 的是表里的第 1 行：**表状态与元数据权威收敛到一层**。这个 L1 发给**机制**，不发给「Lakehouse」这个概念或任何一个产品——它成立的条件是「表状态随写事务原子提交」与「同一张表只有一个权威」这两件事真的发生了（[§7 §7.3.1、§7.3.3](03-lakehouse-section-7-sec7.md) 给的是同一条机制的两面）。「Lakehouse + RAG」长得像既有形态（湖是源、检索是缓存），但判它不是看形态眼熟，而是看第②条：第三方有没有在生产中用湖表承载在线检索——这一条与第 3 行（向量原生）面对的是**同一处证据缺口**，两行因此给同一个级别（L2）。判据一旦按形态放宽，同一处缺口就会同时给出两个级别。

其余方向为什么不够格，分两类：**② 拿不出 → L2**（向量原生、Lakehouse + RAG、向量库联邦、AI 元数据、自然语言查询、Agent 触达）；**① 不成立 → L3**（自治表格式优化、GraphRAG）。L2 不是永久档位，给每个 L2 方向预先写好升 L1 的条件比年底重评一次更有效：向量原生与 Lakehouse + RAG 卡在同一处证据缺口（① 只部分满足、② 拿不出、③ 未稳），升级条件因此是同一条——**规范的类型章节里出现向量类型、索引条目的提交语义被写入规范，且出现第三方在生产中用湖表承载在线检索的公开材料**（前半条补 ①③，后半条补 ②，缺任一半都升不上去）；向量库联邦的升级条件是**出现第三方把跨源联邦用在关键路径上、并公开规模与验收口径的材料**；AI 元数据的升级条件是**第三方公开可复现的质量评估方法**；自然语言查询的升级条件是**真实库上的第三方生产归因方法被公开**；Agent 触达的升级条件是**权限模型里出现「非人主体」这一档**。这五条覆盖上面列的六个方向，每一条都是可观察的信号，不是感觉。

读这张表时有三个动作，顺序不能换：

1. **先确认权威唯一**——「同一张表」在你们这里只有一个 Catalog 吗？有没有绕过 Catalog 直接写路径的引擎？出现两个权威，「同一张表」这句话就已经不成立（[§7 §7.3.3](03-lakehouse-section-7-sec7.md)）。
2. **再验派生件的可重建性**——实时 OLAP 副本、向量索引、图谱，各自能不能从湖全量重算？它们有没有携带「数据截止时间」？答不上来说明它们已经不可重建。
3. **最后才看 AI 功能清单**——元数据生成、自然语言查询、Agent 直连都是在上面两件事确定之后才需要精算的第二层问题。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向在评审时应被直接打回：本主题里每一次「AI 让湖仓更好用」，都对应着一处被搬到别处的成本。

读这套结构有两个约定。**第一个，「机制」必须落在结构或责任归属上**——是「表状态的权威收敛到一层」，是「向量变成表的一列」，还是「调用者从人变成 Agent」。落不到这几件事上的，都只是评价。**第二个，「代价」必须是一个可被观测的量**——元数据规模、写放大、刷新滞后、索引容量。写成「需要投入学习」的，不算代价。

#### 5.2.1 表状态与派生层的权威归属：本主题唯一的 L1

- **旧做法与它的卡点**：湖仓最早被当成「能存就行」的一层，表状态散落在目录结构与口头约定里，而派生层（实时 OLAP、向量索引、图谱）各有一份可写副本。卡点是**权威不唯一**：一旦出现两个可写副本，就没有机制能判断哪份对，排障时间从「查一次血缘」变成「对两套数」（[§7 §7.3.1、§7.3.4](03-lakehouse-section-7-sec7.md)）。
- **AI 改变了什么机制**：**把「表状态」与「数据」分开，并把权威收敛到一层**——表状态由可原子替换的元数据（元数据文件 / 事务日志 / 时间线 / 快照）描述，任何时刻只存在一个完整快照；派生层则被明确为**可从湖重建的派生态**。AI 没有发明这两条，但它把它们的价值放大了：模型要用湖，就必须能问出「这份数据是谁的、有多新」。
- **由此得到的**：**因为表状态可原子替换、派生件可从湖重建，所以「AI 看到的数据与报表对不上」被降级成一次重算的工程问题，而不是一场对账**；**因为单一权威决定的是指针而不是数据，所以换引擎、换查询层都不必搬数据**——这两条合起来，才是「湖仓能同时服务 BI 与 AI」的真正含义：它靠的不是引擎快，而是权威唯一、副本可弃。

```text
一条链路上的三种失败，各归各的负责人
  权威数据（表快照） ──刷新 / 重建──► 派生层（OLAP / 向量 / 图谱） ──查询──► BI / RAG / Agent
       │                                     │                              │
   快照提交失败                          刷新链路滞后                    分数不可比 / 结果过期
   → 数据没更新，旧快照仍可读        → 查询成功但数字停在旧版本        → 不报错，只是「不太准」
  ────────────────────────────────────────────────
  关键：中间那一段是唯一一条「不报错」的链路——
        所以每个派生层都必须把「数据截止时间」带进查询结果，
        否则「查询成功」会被读成「数据新鲜」
```

- **由此付出的**：**其一，元数据本身成为需要维护的资产**——提交越频繁，产生的清单与快照越多，规划阶段要读的元数据越多；把它推高的不是字节数，而是「文件切得多碎、提交多频繁」（[§7 §7.3.1](03-lakehouse-section-7-sec7.md) 给出了这条的定量关系）；**其二，Catalog 成为单点与共享依赖**——它的故障表现不是「查不到数据」而是「查到的数据停在某个旧版本」，监控必须盯当前快照的时间戳，而不是只看服务存活；**其三，派生层的过期有第二重来源**——模型换了、数据没变，索引同样需要重建，这类过期无法通过比对数据版本发现，只能靠记录「索引构建时所用模型版本」发现。
- **证据与来源**：【公开】表格式一侧有版本化规范与 release note（Apache Iceberg 由 Netflix 开源、其后进入 Apache 基金会并成为顶级项目；Hudi 由 Uber 发起并开源；Delta Lake 由 Databricks 于 2019 年开源；Paimon 前身为 Flink Table Store、2024 年发布 1.0——各项目的年份与版本以官方公告与 release note 为准）；Catalog 的 REST 形态有公开规范，[§7 §7.3.3](03-lakehouse-section-7-sec7.md) 记录了 Snowflake 于 2024 年开源其 REST Catalog 实现并捐入基金会孵化。第三方（**非发起方**）生产案例：字节的 Iceberg 数据湖——流批共写同一张表、四个业务共用一套 catalog、元数据服务独立扩容（见 [Ch3-02 §2.2](../02-data-lake/02-data-lake-section-6-sec6.md)），它是用这个格式的公司，不是定义它的公司；本目录 [§6](03-lakehouse-section-6-sec6.md) 的 Netflix 是 Iceberg 的发起方，按 §5.1 的判据修正归入「发起方自述」，不算第三方（四家案例各自能证明什么、不能证明什么，见 §5.4）。**本节不给任何「查询性能提升多少倍」的数字**：那类数字缺少数模、并发与缓存状态这些条件。**判定方法**：问三个问题——「同一张表只有一个权威吗」「每个派生层都带数据截止时间吗」「上一次全量重建是什么时候、用了多久」。
- **成熟度**：**L1**。判据：① 版本化规范与 release note（各表格式项目的官方文档可核验）；② 第三方（**非发起方**）生产案例：字节的 Iceberg 数据湖（流批共写同一张表、多业务共用一套 catalog，[Ch3-02 §2.2](../02-data-lake/02-data-lake-section-6-sec6.md)）——本目录 §6 的 Netflix 是 Iceberg 的发起方，按 §5.1 的判据修正不计入 ②；③ 接口多年稳定（对象存储 API、表格式读写接口、Catalog 的 REST 形态）。**降级条件**（说的是级别会不会掉，与上面那条口径是两件事）：若你依赖的实现要求绑定某一家的专有 Catalog，或把快照 / 权限能力退回实验性条目，③ 不再成立，本方向降回 L2。
- **失效条件**：单引擎、单写入方时，「统一 Catalog + 独立派生层」的价值不兑现，只剩多一两个需要运维与升级的常驻组件——此时把表状态留在引擎内部更经济（[§7 §7.5](03-lakehouse-section-7-sec7.md) 的节点③给的是同一条判断）。**判定方法**：数一下原生读写这张表的引擎个数，是 1 还是 ≥2。
- **自验方法**：从一个派生层开始做一次全量重建，记录耗时、期间线上是否可查、重建后与重建前的差异；再做一次「指向旧快照」的回滚演练。两次演练都没做过，说明这套架构的回退路径只是设计意图。

三类派生层的过期来源不同，混成一类管理就会出错：

| 派生层 | 交接物 | 过期有几种来源 | 判定它是否过期的方法 |
| --- | --- | --- | --- |
| 实时 OLAP 副本 | 聚合结果 + 刷新批次 | 一种：刷新链路滞后 | 看查询结果里附带的「数据截止时间」，不看服务是否存活 |
| 向量索引 | 主键 + 嵌入 + **模型版本** | 两种：数据更新、模型更换 | 比对数据版本，同时比对索引构建时所用模型版本 |
| 知识图谱 | 实体 / 关系 + 抽取规则版本 | 两种：数据更新、规则更换 | 看抽取作业的截止时间与规则版本号 |

这张表的重点是第三列：**「模型换了、数据没变」这一类过期无法通过比对数据版本发现**，只能靠记录「这份索引是用哪个模型 / 哪版规则构建的」。这一列最容易在建索引时被省略，而它事后补不回来——省略之后，你只能靠人工回忆来判断一份索引是不是过期了。

#### 5.2.2 向量原生与三类结合：列进了表，索引还在表外

- **旧做法与它的卡点**：向量与结构化数据分家——向量在一个系统里、业务表在湖仓里，两者要 JOIN 就得把数据搬来搬去，而权限、血缘、生命周期这三件事要在两处各维护一遍。三条结合（RAG、向量库、GraphRAG）都是在处理这个分裂，但处理方式差别很大：一条把检索结果喂给模型，一条在查询期做跨源联邦，一条把关系抽出来另存。
- **AI 改变了什么机制**：**其中只有一件是湖仓自己的机制变化——把向量变成湖表的一列**（列类型与治理归属的变化：权限、时间旅行、血缘可以直接复用表格式已有的机制）。另外两件改的是**检索的编排位置**：RAG 改的是「谁消费检索结果」，跨源联邦改的是「距离计算落在哪个节点」。**变的是「列」，不是「索引」**——索引仍由检索引擎自持，它是表外的旁挂件。

| 方向 | 改了哪一层 | 由此得到的 | 由此付出的 |
| --- | --- | --- | --- |
| 向量进表（列类型） | 存储与治理归属 | 向量与事实同源同权，权限与时间旅行复用表格式机制 | 索引旁挂在表外，不随快照版本化；重建不受提交保护 |
| Lakehouse + RAG | 检索结果的消费者 | 分析型检索不必把数据搬出湖 | 写入可见性由提交节奏决定，实时问答会稳定看到「刚上传的搜不到」 |
| Lakehouse + 向量库（跨源联邦） | 距离计算的执行位置 | 过滤若能下推，候选集规模可控 | 下推不了时退化为「拉全量向量回引擎算」，把联邦最贵的部分放大 |
| Lakehouse + GraphRAG | 检索的第二跳 | 关系与事实可分别演进 | 两边没有自动一致性保证，join 在应用层，图谱必须可重建 |

- **由此得到的**：**因为二进制只存一份、只有嵌入进派生索引，所以重建索引的成本远低于重建原始数据**；**因为模型版本可以记在事实侧，所以「这条向量由哪个模型产生」是可回答的**——这两条决定了换嵌入模型那天是「跑一个作业」还是「做一次迁移」。反过来看跨源联邦：**因为距离过滤能否下推决定候选集大小，所以「统一查询」的收益上限由连接器的下推能力决定，而不是由查询语言决定**（判定方法是看 `EXPLAIN` 里距离算子落在 connector 侧还是引擎侧，与 [Ch3-13 §5](../13-query-engine/13-query-engine-section-5-ai.md) 用的是同一条判定）。
- **由此付出的**：**其一，索引规模是第二份数据**【推算：10⁸ 条 768 维、每维 4 字节的浮点存储，裸向量约为 10⁸ × 768 × 4 字节 ≈ 3.07 × 10¹¹ 字节；按 1 GB = 10⁹ 字节的十进制换算为 ≈ 307 GB，若按 1 GiB = 2³⁰ 字节换算则为 ≈ 286 GiB；近邻检索索引除原始向量外还要存邻居结构，其规模通常与原始向量处于同一量级或更高，具体倍数取决于索引实现与召回参数——推导链只有乘法与单位换算，读者可自行复算，与 [§7 §7.4](03-lakehouse-section-7-sec7.md) 的账四用的是同一组前提与同一档单位】；**其二，可见性由提交节奏决定**——量级在分钟到天级【经验】，把它用在用户在等页面的场景上会稳定失效；**其三，跨源联邦多一次序列化与网络跳转，且两侧的代价模型不共享**，优化只能各自为政。
- **证据与来源**：【公开】Apache Iceberg 的规范是版本化发布的（各版本的规范与对应 release note 以官方仓库与文档站为准）——判定「V3 里到底有哪些条目、有没有向量类型」的正确入口是**规范的类型章节**，不是讨论帖或博客；Trino 一类引擎的向量连接器须逐插件核验其是否把过滤下推（判定方法：构造一个高选择性过滤，比较「先过滤后检索」与「先检索后过滤」的召回差）。**核验纪律**：多模态列式格式（Lance 一类）的论文与 Design Doc 请查项目官方仓库与 publications 页；在这个主题上「项目名对而会议 / 年份错」是最常见的引用事故。
- **成熟度**：**向量原生 L2 / 向量库联邦 L2 / Lakehouse + RAG L2 / GraphRAG L3**（与 §5.1 表逐条一致）。向量原生的判据：① 部分满足（多模态列式格式有版本化发布）；② 不满足（列不出第三方在生产中用湖表承载在线检索的公开材料）；③ 未稳（索引与数据版本的耦合方式各产品不同）。向量库联邦的判据：①③ 满足（连接器形态可用）；② 不满足（列不出第三方用跨源联邦承担关键路径的公开材料）。Lakehouse + RAG 的判据：① 部分满足（该组合有官方文档条目）；② 不满足（与向量原生是同一处证据缺口）；③ 未稳（索引与数据版本的耦合方式、分数的可比口径各产品不同）。GraphRAG 的判据：① 不满足（联合执行无标准接口）；② 无。
- **失效条件**：当检索规模小到可以每次全量算距离时（万级向量量级），把向量放进湖表并另配索引是负收益；当候选集大、维度高、元数据过滤率低时，「统一查询」不如「向量库召回 + SQL 回表」两步走。**判定方法**：算「全量算一次的代价 × 查询频次」，以及测两种走法的端到端耗时与传输字节数——差一个数量级说明下推没发生。
- **自验方法**：拿一个已知正样本对（同一实体的文本与图像），在混合索引里查它并对两次结果打分——分数不可比就说明编码器没有对齐，而这类失败不会报错。

#### 5.2.3 AI 元数据、自然语言查询与表格式自动优化：三件改「谁在写、谁来问、谁在调」的事

- **旧做法与它的卡点**：三条各自要解的题不同——元数据靠人补，人一忙就补不完，而补完的元数据没有机制保证不过期（本目录 [§6](03-lakehouse-section-6-sec6.md) 的四条案例里，与元数据有关的失败教训是「用目录列举当元数据」「元数据单点」两条机制性问题，以及 Apple 案例的「隐私属性不进入数据资产元数据 → 审计时无法逐项举证」）；取数要人写 SQL，而且要先知道表名与口径；表格式的布局优化（目标文件大小、聚簇列、合并时机）依赖资深工程师逐项判断。三条的共同卡点是同一个：**判断的依据藏在人的经验里，没有被写成机器可读的东西**。
- **AI 改变了什么机制**：**三件事改的层不同**——元数据改的是**说明的写手**（从数据本身推断描述的成本下降）；自然语言查询改的是**提问的人**（执行路径完全没变，仍是同一套解析器、优化器与执行器）；表格式优化改的是**调参的接口**（统计信息与规则做决策，模型把它换成自然语言解释与建议）。**没有一件改变了湖仓的存储或一致性机制。**

| 方向 | 改了哪一层 | 由此得到的 | 由此付出的 |
| --- | --- | --- | --- |
| AI 驱动的元数据管理 | 说明的写手 | 长尾表与长尾字段第一次有可能被覆盖；「关键项缺项不可发布」在规模上可执行 | 错误的元数据比缺失的更危险，会被下游当事实复制；新增一个把样本送出系统的数据出口 |
| 自然语言查询 | 提问的人 | 「会写 SQL」不再是取数的前置条件 | 错误从「报错」变成「看起来对的错答案」；上限由元数据覆盖决定，而不是由模型大小决定 |
| AI 驱动的表格式优化 | 调参的接口 | 诊断知识的传递成本下降 | 决策仍由统计与规则做出；给自动动作权限意味着把一次错误建议变成一次生产事故 |

- **由此得到的**：**因为生成是概率性的，所以必须有一道确定性工序兜底**——把生成的 SQL 与语义定义对照、把生成的字段描述交给人裁定之后再发布；**因为口径知识不在 SQL 里而在元数据里，所以自然语言取数的上限由元数据覆盖决定**，而不是由模型大小决定。这两条推出同一个动作：先把元数据与指标定义做实，再谈启用。
- **由此付出的**：**其一，错误模式从「报错」变成「看起来对的错答案」**——口径错、join 错、过滤条件漏都会正常返回结果，错误更难被发现；**其二，元数据是新的信任依赖**——下游会把生成的描述当成事实，而它没有经过与口径定义同等的评审；**其三，元数据规模与提交频率一起增长**，在启用自动生成之后，清单与描述在元数据侧的体量会以另一种方式变重（[§7 §7.3.1](03-lakehouse-section-7-sec7.md)）。
- **证据与来源**：【公开】产品侧入口：Databricks 的 Data Intelligence Platform / Unity Catalog 与 Snowflake 的 Iceberg Tables，Databricks Genie、Snowflake Cortex Analyst。元数据生成与文本转 SQL 能力在官方文档里是正式条目，**逐条的 GA 状态与生效条件以该产品对应版本的 release note 为准，不以产品首页为准**（这是本节 ① 的核验方式）；文本转 SQL 的公开评测以**基准**为主，例如 Spider（EMNLP 2018）面向规整、干净的跨域语义解析，BIRD（NeurIPS 2023）的设计目标则是「真实库、脏数据、大 schema」，正是为补上基准与生产环境之间的落差【公开，会议论文】——**用基准成绩选型时先看它是否公开了评测条件**（评测集与 schema 规模、是否允许人工澄清、按执行结果一致还是字符串相似计分）。表格式的自动合并与聚簇能力早于 LLM 存在，其证据在产品文档的配置章节。② 不满足：列不出第三方公开的、含规模与验收口径的生产案例。
- **成熟度**：**AI 元数据 L2 / 自然语言查询 L2 / 表格式自动优化 L3**（与 §5.1 表逐条一致）。AI 元数据的判据：① 满足（能力项有正式文档条目，逐条的 GA 状态与生效条件见对应版本的 release note）；② 不满足（仅有厂商自有案例）；③ 未稳（生成结果写回的是各平台自定义的元数据字段与标注格式）。自然语言查询的判据：①③ 满足（产品侧有正式文档条目；链路形态稳定：NL → 语义层 → SQL → 既有执行器）；② 不满足（真实库上的第三方生产准确率不公开）。表格式自动优化的判据：① 不满足（无正式发布的能力项，且「自治」也无可核验定义）；② 不满足。
- **失效条件**：当目标库的表 / 字段命名没有业务语义、也没有指标口径定义时，自然语言查询会把「猜表名」升级成「猜口径」，此时它比手写 SQL 更慢、更难审计；当写入形态稳定、文件布局本来就在目标区间内时，引入自动化布局优化只是多一个会改配置的东西。**判定方法**：取 50 条真实业务问题，分别记录「需要改口径的条数」与「需要改语法的条数」——前者占比高说明问题在元数据，不在模型。
- **自验方法**：抽 50 个由模型生成的字段描述交给人逐条判定，把「错」的比例做成可持续的抽样指标；这个数比任何准确率宣传都更能决定要不要保留人工复核。

#### 5.2.4 Agent 触达：换的是调用者身份，不是接口

- **旧做法与它的卡点**：让程序取数要么走 BI 的私有 API，要么给每个数据源手写一个工具，工具数量随数据源与问题种类相乘增长，而每个工具的参数语义、权限与错误码都不一致。湖仓这一侧的问题更具体：**引擎多数只认「人 / 服务账号」两种身份**，无法区分「谁的 Agent」，于是权限只能给大。
- **AI 改变了什么机制**：**把「SQL 作为取数动词」暴露给 Agent，并把这个能力标准化**（湖仓本来就是「一份数据，多种引擎」的入口——同一份表可被 Spark / Flink / Trino 一类引擎读写，见主文件 §1.1；对外的接口形态仍是各引擎自己的 SQL，跨引擎的是数据不是语句）。真正改变的是**调用者的身份**：以前是人 / BI 工具，现在是 Agent，于是权限、审计与限额都必须以「非人主体」为前提重做。**引擎一行代码都没变，变的是它需要回答「你是谁」。**
- **由此得到的**：**因为 SQL 是一个已经成熟、且可被约束的接口**（参数化、只读账号、行 / 列级权限、限额），所以给 Agent 开放取数不必发明新协议，也不必换引擎；**因为执行仍在既有引擎内，所以下推率、统计信息与优化器继续有效**——Agent 不会让湖仓变快，但也不必为它改造湖仓。
- **由此付出的**：**其一，权限模型必须新增「Agent 身份」这一维**，人 / 服务账号两档不够——否则要么给 Agent 过大的权限，要么每次靠人代签，自动化价值被抵消；**其二，错误口径会被规模化放大**——人在写 SQL 时会迟疑，Agent 不会；**其三，工具协议本身仍在演进**，绑定某一版会带来迁移成本。
- **证据与来源**：【公开】模型上下文协议（Model Context Protocol）由 Anthropic 于 2024 年 11 月首次公开，其后有带日期的规范修订版本——判断某个客户端 / 服务端支持哪一版，看它声明的规范版本号，不看生态清单页。第三方（非厂商）公开生产案例不公开，故 ② 不满足。
- **成熟度**：**L2**。判据：①③ 满足（接口可拼装、SQL 与 Catalog 的权限语义稳定）；② 不满足：第三方非厂商的 Agent 取数生产案例列不出；权限模型需要配套新建。

工具层必须自己承担的检查项（缺一项就不要给 Agent 开放取数）：

| 检查项 | 为什么必须在工具层做 | 缺了会怎样 |
| --- | --- | --- |
| Agent 身份与授权 | 引擎多数只认人 / 服务账号，无法区分「谁的 Agent」 | 权限只能给大，无法按会话收窄 |
| 只读账号 + 语句类型白名单 | 生成式模型会产出写入 / DDL 语句 | 一次误生成就可能改数据 |
| 行 / 列级权限过滤 | 越权必须在执行前拦（不能事后告警） | 数据外泄，日志成为证据链负担 |
| 限额（并发 / 扫描量 / 返回行数） | Agent 会高频、无节制地重试 | 单个 Agent 拖垮共享入口 |
| 审计记录（谁 / 何时 / 查了什么） | 「非人主体」若不留痕就无法复盘 | 出事后无法定位到具体会话 |

- **失效条件**：当 Agent 只需要一两个固定指标时，直接给只读 API 比开放 SQL 更安全也更便宜——统一接口的收益随数据源数量与问题种类的增加而增长，源少时它只是负担。**判定方法**：统计最近一个月 Agent 侧的工具调用，分别计数「因参数 / 权限被拒」与「生成了错 SQL」；前者高是接口与说明的问题，后者高是语义层的问题。

### 5.3 与本主题既有栈的接口在哪

AI 能力不是新引擎，而是挂在湖仓周边的调用方与派生方。下表写清接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 表格式 ↔ 读写引擎 | 表状态随提交原子切换；写入产生不可变快照 | 表格式侧（提交失败则旧快照仍可读） | 既有能力（L1） |
| Catalog ↔ 多引擎 | 当前快照指针的唯一权威 | Catalog 侧；它故障时表现为「数据停在旧版本」而非「查不到」 | 既有能力（L1） |
| 湖（权威）→ 实时 OLAP 副本 | 交接物 = 快照 + **数据截止时间** | 刷新链路；查询成功不等于数据新鲜 | 需自建（L2） |
| 湖（权威）→ 向量索引 / 图谱 | 交接物 = 主键 + 嵌入 / 关系 + **模型或规则版本** | 派生侧；必须能从湖全量重建 | 需自建（L2 / L3） |
| 元数据 / 语义定义 ↔ 自然语言查询 | 单向读：表、字段、指标、枚举值注入；生成的 SQL 先解析校验再执行 | 口径错归元数据侧；语法错归模型侧 | 需自建（L2） |
| Agent 工具层 ↔ 湖仓 | SQL 作为工具：参数化 + 只读账号 + 行 / 列级权限 + 限额 | 越权必须在**执行前**拒绝，且由工具层负责 | 需自建（L2） |
| 训练 / 特征 ↔ 湖仓表 | 交接物 = 快照 ID + 版本；训练样本应可复现 | 训练侧；保留策略必须留住所需的历史窗口 | 既有能力，需保留策略配合（L2） |
| 跨区域 / 跨云读者 ↔ Catalog | 元数据与查询计划的下发，数据本体不动 | 各域本地；联邦层负责计划与结果合并 | 合规前置（L2） |

表里两条纯「既有能力」行（表格式、Catalog）与 AI 无关，却决定 AI 方向的上限：**自然语言查询的准确率取决于元数据与统计信息的质量，检索的代价取决于下推能力**，这两件事都不会因为加了一个模型而变好。表里四条「需自建」行可归成三类失败归属，必须在设计阶段写清，否则会退化成扯皮：

- **口径错**归元数据侧。把口径错记成「模型不行」，会让团队去换模型，而问题在指标定义。
- **越权**必须在执行前拒绝，且由工具层负责。事后告警等同于事故已经发生。
- **数据过期**归派生侧（实时 OLAP、向量索引、图谱都归这一类），而它必须能被下游看见——没有「数据截止时间」的副本，等于把新鲜度判断推给了用户。

### 5.4 公开进展与文献

分「规范与 release note / 论文 / 第三方生产案例」三类列，**宁少勿假**。规范与 release note 一类给的是「用哪份文档的哪一节自行核验」，这类文档持续更新，写死年份会过期，所以只给文档名与核验位置——**这是本节显式声明的例外，不是省略**。核验时以**你所用的那个版本**的 release note 为准，而不是以站点上的当前版本为准。

- **值得注意的空白**：本节列不出「第三方在生产中用湖表承载在线向量检索」「第三方在生产中把 Agent 取数放进关键路径」的公开材料，也列不出含规模、维度与召回目标的第三方统一评测。这个空白本身是结论：本主题的性能数字一律要带条件读——没有条件限定语的「毫秒级」「X 倍」，都不可用于选型。

**怎么用这份清单**：核「某个能力是不是真的可用」看该版本的 release note；核「某个机制是不是真的存在」看规范与文档的机制章节（更新慢，但一条条目抵十篇博客）；核「它到底要花多少」只能自己算——没有任何公开材料能代替这一步。

三类材料的效力不同，读的时候要分开：

- **规范与 release note** 是唯一能回答「这一版到底有没有这个条目」的材料，它回答的是**能力有无**。它们的时间切片由版本号而不是年份决定，所以引用时要带版本，不能只写年份。
- **论文**能回答「机制是什么、为什么成立」，不能回答「产品里有没有」。这两件事之间隔着一整条工程路径，本节里最容易出错的就是把它们混为一谈：论文里的原型与产品里的实现是两个不同的东西。
- **第三方生产案例**能回答「别人踩过什么坑」，但它评的是「在什么条件下用了什么」。读到这类材料时先找条件（规模、并发、模态、召回目标、是否含缓存），找不到条件的经验不可迁移。

另外要提醒一句：本主题的公开材料里，**厂商的基准跑分与「营销页上的性能声称」不算第三方证据**。跑分是发布方的自述；第三方证据是别人在别处跑出来的生产结果。核「某引擎比某引擎快 N 倍」这类说法时，先看它有没有给出数据量、并发、硬件、是否含下推与缓存这些条件——没有条件的倍数不可用于选型。

### 5.5 被过度宣传的部分

**「自治 Lakehouse：自动合并、自动布局、自动扩容」** —— 实际是什么：这一层的自动化早于 LLM 存在，靠的是统计信息与规则（按文件大小触发合并、按查询模式选聚簇列）；模型改变的是**解释与建议的接口**，不是决策机制。为什么会这样：布局优化的输入是文件统计与查询历史，模型不能凭空造出统计信息；把它叫做「自治」，会让团队以为换一个模型就能解决布局问题，而真正要改的是写入侧的文件大小与合并调度（[§7 §7.3.2](03-lakehouse-section-7-sec7.md)）。**什么时候它才会成真**：自动动作同时具备三件事——触发条件公开、可单步撤销、有明确的失败回退路径；判定方法是看文档里它是建议还是执行。

**「实时 Lakehouse：端到端延迟 < 1 秒」** —— 实际是什么：流式表格式（LSM 组织 + 持续合并）确实把「写入到可查询」的延迟压到了分钟级以内，但「端到端 1 秒」是一个**没有条件限定语的声称**：它取决于写入速率与合并吞吐是否平衡、查询是点查还是扫描、以及读的是最新快照还是要跨多层合并。为什么会这样：LSM 的读放大随未合并层数增长，而合并会与查询争抢同一批资源——延迟是这两个变量的函数，不是表格式的属性。**什么时候它才会成真**：给出四个条件——写入速率、查询类型、合并资源配额、以及「读的是最新版本还是要读历史」，并公开在这组条件下的分位延迟；判断方法是让产品用**你自己的写入速率**演示合并滞后量。

**「向量原生：把向量列当普通列就能做近邻检索」** —— 实际是什么：向量作为表的一列被快照与权限覆盖，这件事成立；**把向量列当成检索路径，不成立**——索引仍在表外、由检索引擎自持，不随快照版本化。为什么会这样：列存与分区剪裁只回答相等与范围条件，近邻检索需要专门的索引结构（[§7 §7.3.4](03-lakehouse-section-7-sec7.md) 给的是同一条机制）。**什么时候它才会成真**：规范的类型章节出现向量类型，且索引条目的提交语义被写入规范、随快照原子切换——两个条件都要看规范，不看产品首页。

三条合起来看，被过度宣传的部分有同一个形状：**它们都把「在某一层成立」讲成了「整体成立」**。自治是规则自动化被说成 AI；实时是用无条件的「1 秒」代替一组条件；向量原生是列类型的事被说成检索能力。识别方法因此很简单——**把宣传句里的名词换成「统计数据」「写入速率与查询类型」「列类型」，看它还成不成立**：只有在换过之后仍然成立的说法，才是关于架构的。

要补一句的是：这三条被过度宣传的说法里，**没有一条是「假的」**——自动合并确实在跑，流式写入确实把延迟压到了分钟级以内，向量确实能作为列存下来。它们的问题是把「在某一层成立」讲成了「整体成立」，而架构决策恰恰只关心后一句。所以在评审会上更有效的问法不是「这是不是真的」，而是「它在哪一层成立、代价落在谁身上」。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 开放表格式的竞争焦点从「哪个格式」转向「Catalog 与治理」，格式本身趋于收敛 | 讨论集中到 Catalog 的 REST 规范、权限与血缘的位置；新项目默认兼容主流格式而不是另起一套 | 三年后仍在争「哪个表格式更好」，且各自的专有能力继续不可互操作 |
| 「AI 原生 Lakehouse」的落地形式是「派生索引 + 可重建」，而不是「湖内原生近邻检索」 | 规范出现索引条目的提交语义且随快照版本化；索引重建成为标准运维脚本 | 出现「把向量列当普通列就能做近邻查询」的标准做法，且不再需要独立索引与重建流程 |
| 「自治」叙事收敛为「可回滚的自动动作」，不再自称 AI | 产品文档把自动动作写成「触发条件 + 建议 + 单步撤销」，并把阈值公开 | 三年后仍以「自治 / 自驱」为卖点，而文档里查不到触发条件与撤销路径 |
| 「实时 Lakehouse」的竞争指标从「端到端多少秒」转向「写入到可查询的延迟 + 合并滞后量」两个可观测指标 | 产品文档与案例开始并排给出这两个指标，并附写入速率与查询类型 | 三年后仍只有无条件的秒级声称，且不公开合并滞后量的监控方式 |

写这四条时的共同约定：**信号必须是外部可观察的**（规范条目、产品文档的配置与回退章节、第三方公开案例），而不是「我觉得会」。凡写不出证伪信号的判断，本节不写。

四条里前两条是**生态与形态**预测、后两条是**叙事与指标**预测。它们每年可以按固定动作复评一次：

- 查一次你所用的表格式规范的类型章节与索引条目——这是预测 2 的判定入口。
- 查一次产品的自动能力文档里有没有触发条件与撤销路径——这是预测 3 的判定入口。
- 查一次产品文档里「实时」这个说法旁边有没有条件限定——这是预测 4 的判定入口。
- 问一次团队「同一张表在你这里只有一个权威吗」——这是预测 1 的判定入口，也是本节全部结论的地基。

四条预测的可证伪性来自同一个来源：**它们判断的都不是「某产品会不会做」，而是「判断依据会不会出现在公开文档里」**——规范条目、配置项、文档章节、案例方自述的动机，这些都是外部可查的。这也是本节用「机制 → 证据 → 成熟度」换掉趋势清单的原因：趋势清单永远正确，因为它从不承诺可以被核对的信号。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有湖仓，但不确定「同一张表」是不是只有一个权威 | 盘点所有能写这张表的路径（含绕过 Catalog 的直写引擎），把权威收敛到一处 | Catalog 故障时的表现是「查不到」还是「停在旧版本」 | **不要在权威唯一之前接任何 AI 查询入口**；两套快照各自查到的是两组数，且不可比 |
| 业务要求实时 / 秒级看板 | 加派生副本（实时 OLAP），并让它携带数据截止时间 | 刷新链路失败时下游能否发现（这决定 SLA 是什么） | **不要假设湖上扫描引擎能直接给出点查 SLA**；两份全量数据不是解法 |
| 业务提出「湖上做相似度检索」 | 把索引做成可从湖重建的派生态，补上重建脚本与时间上界 | 规范里是否出现向量类型的类型定义与索引条目的提交语义 | **不要为「湖内原生近邻检索」预留 schema**；不要因「以后要 AI」提前上向量索引 |
| 元数据覆盖率低，想用 AI 补齐 | 先用模型生成待确认项、人只做裁定；把「关键项缺项不可发布」这条规则做出来 | 抽样复核的一致率（抽 50 个字段描述人判） | **不要取消人工复核**，也不要用「AI 能补」为由放宽关键项的定义 |
| 想对业务开放自然语言取数 | 先做指标定义与语义层，再用「需要改口径的条数」验收 | 产品是否暴露元数据依赖、是否允许人工澄清 | **不要在元数据缺失时把它放进面向客户的产品** |
| 想给 Agent 开放湖仓取数 | 给 Agent 单列只读身份 + 行 / 列级过滤 + 限额 + 审计 | 权限模型是否出现「非人主体」这一档 | **不要共享一个高权限账号**，也不要让越权靠事后告警发现 |
| 跨区域 / 跨云读者出现 | 先把 Catalog 统一（REST 形态）并把元数据同步成本算进预算 | 各区域是否出现了第二套 Catalog | **不要在各区域各建一套 Catalog 之后才发现口径不可比** |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的（重建一次、改一次权限模型、多维护一套派生链路、多一个 Catalog 分叉），而收益依赖一个尚未在你自己的数据上验证过的假设**（规模会继续涨 / 模型会变得更准 / 业务会真的用自然语言取数 / 跨域查询不会变高频）。等 §5.6 的信号出现再投入，损失的只是时间。

这张表的七行不是互斥选项，而是同一支团队会依次遇到的处境。真正**不可逆**的决定只有一个：**权威落在哪一层、派生件能不能被丢弃**。它决定了你在换引擎、换模型、换模态时是「跑一个作业」还是「做一次迁移」；至于用哪个表格式、要不要上向量索引、元数据用哪家的能力，都是在权威确定之后仍然可以替换的选项。**把不可逆的决定与可逆的决定分开排期，比把它们一起放进路线图更重要。**

如果只能排一个顺序，按这条走：

1. **先定权威**：把能写这张表的路径列全，确认「同一张表」只有一个 Catalog 是权威（[§7 §7.3.3](03-lakehouse-section-7-sec7.md)）。这一步不改代码、不花钱，却决定了后面每一步的结论是否可信。
2. **再量两个数**：平均文件大小与每分区文件数分布（它决定对象数与请求费），以及合并滞后量（未合并文件数与字节数，它决定读放大是否在累积）。这两个数从现有元数据与账单里就能读出（[§7 §7.4](03-lakehouse-section-7-sec7.md)）。
3. **然后做两个演练**：派生层的全量重建演练、指向旧快照的回滚演练。没做过演练的「可重建」与「可回滚」只是设计意图（§5.2.1 的自验方法）。
4. **最后才接 AI 层**：元数据生成、自然语言查询、Agent 直连都是可以替换的接口层；换一次模型或换一家产品，不应该牵动前三步任何一件事。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**调用者与编写者的身份发生迁移**——提问的人从分析师变成模型与 Agent，说明的写手从人工补录变成模型生成，而执行路径（表状态、快照、Catalog、优化器）一行都没变。因为这一点，排进 L1 的不是任何一个「AI 功能」，而是它们共同依赖的那一层：**表状态与元数据权威收敛到一层**（派生件因此被明确为可弃的派生态）；自治表格式优化与 GraphRAG 停在 L3，向量原生、Lakehouse + RAG、向量库联邦、AI 元数据、自然语言查询、Agent 触达停在 L2，判它们的不是「模型强不强」，而是「谁是权威、数据截止时间在哪、权限模型里有没有非人主体」。
>
> 它**没有**改变的是湖仓的两条硬约束：**提交频率决定元数据规模**（[§7 §7.3.1](03-lakehouse-section-7-sec7.md)），**「同一张表」只能有一个权威**（[§7 §7.3.3](03-lakehouse-section-7-sec7.md)）——这两条决定了 AI 上层能问出多准的答案，而没有任何模型能把它们变好。
>
> 💡 **思考锚点**：从你自己湖表的元数据与账单里读出两个数——**每分区文件数分布**与**合并滞后量（未合并文件数/字节数）**。按它们反推：你的读放大是稳定在一个水平，还是随提交在持续累积？答案决定你该先做合并优化、还是可以先接 AI 层，你怎么排？
