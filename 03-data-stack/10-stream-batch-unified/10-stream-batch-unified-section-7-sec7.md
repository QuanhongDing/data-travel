## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

把「Lambda / Kappa / 流批一体」三列放进同一张 1–5 分的表，用「代码复用 / 存储复用 / 性能 / 复杂度 / AI 友好」五个维度打分（Materialize 不在打分表里，它只出现在决策树的「流原生方案」分支）。这个做法有三个结构性错误。

**错误一：这三列不在同一个抽象层，而决策树里的 Materialize 又是第四种东西。** Lambda 与 Kappa 是**链路拓扑**（同一份业务逻辑被实现几遍、被拆成几条链路）；流批一体是**执行与存储的统一机制**（同一引擎的两种执行模式 + 同一份表同时支持流式写与批量读）。给拓扑和机制打同一张分表，等价于给「中央厨房 / 冷链」打分——它们不是二选一，是可以叠加的。而 Materialize 既不是拓扑也不是机制，是**一个具体产品形态**（流式 SQL + 增量维护的物化视图）：它被放进决策树、没有被放进打分表，本章仍把它纳入候选全景（7.2），因为它确实是读者会考虑的方向；但要看清这一点——**打分表的尺子连「拓扑 vs 机制」都撑不住，更没有位置安放一个具体产品**。

**错误二：「复杂度」这一维的符号会随组织规模反转。** 在一个同时有实时团队与离线团队的 500 人组织里，Lambda 的双链路**不增加**沟通成本（两条链路各有人负责），反而是权责最清晰的形态；在 10 人的团队里，同样的双链路意味着**同一批人写两遍、半夜处理两套告警**。打分表给 Lambda 复杂度 3 分，是把「小团队视角」写成了绝对结论。

**错误三：性能这一维没有说明比的是什么。** Lambda 的批层用批处理引擎、速度层用流式引擎，**各自都是自己场景下的最优解**，所以「性能 5 分」只在「单条链路 vs 单条链路」的比较里成立；一旦比较的是「一次口径变更从提出到双方一致」的端到端时间，双链路反而更慢——因为要改两处，还要证明两处一致。

打分表输出的是**名次**，选型需要回答的是「**在我的延迟要求、写入形态、团队结构下，下一步该选哪条链路，以及它在什么条件下失效**」。本章因此只保留那五个维度所指向的问题，但把它们重新组织成可判定的判据。

**本章采用的 6 条判据**（每条针对流批主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 同一份逻辑要被实现几遍 | 1 遍 / 2 遍 | 实现份数决定口径漂移的**概率**，不只是维护工作量 |
| 同一份数据要有几个物理副本 | 1 份 / 2 份（流存 + 批存） | 副本数直接乘进存储成本，并决定两侧会不会读到不同时间点的输入 |
| 写入形态是追加还是更新 | 只 append / 大量 upsert / 大量 delete | 它决定表格式的哪一侧代价（写放大还是读放大）落在你头上 |
| 延迟与「可修正性」的交换点 | 多快出结果；结果错了或迟到了，能不能改 | 流链路的修正成本远高于批链路，这是拓扑选择的第一约束 |
| 重算 / 重放窗口有多长 | 重放 1 天还是 1 年 | 窗口长度决定「历史放在哪」：消息队列还是对象存储 |
| 常驻组件数与 SQL 方言数 | 几个引擎、几套方言、几个值班人 | 组件数不乘进账单，乘进**人力与故障面**——这是打分表最擅长掩盖的一项 |

五个维度都还在，只是位置变了：「代码复用 → 判据 1」「存储复用 → 判据 2」「复杂度 → 判据 6」「性能 → 判据 4 的交换点」。**「AI 友好」不是独立维度**：AI 取数要的是「一份机器可读的口径、一份可枚举的血缘、一个可回溯的变更记录」，这三样分别是判据 1、2、5 的推论，给它单独打分只会重复计权。

判据的顺序也不是中性的，它对应一个**筛选顺序**：先用判据 1–3 做**结构性筛选**（这三条问的是「系统里会有几份实现、几份数据、变更怎么表示」），再用判据 4–6 做**运行参数权衡**（延迟、重算窗口、人力）。顺序不能颠倒的原因很实际：结构性选项一旦落地，改动它要付出 7.7 那张表里最高一档的迁移成本；而运行参数（同步点间隔、合并频率、保留策略）大多是配置项，随时可调。**打分表的根本问题在于它把这两类东西放在同一根尺子上**——于是「性能 4 分 vs 5 分」这种可以随时调的差异，和「实现份数 1 份 vs 2 份」这种几年内不可逆的差异，在表里长得一样重。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Lambda 架构 | 拓扑：双链路 | 批层周期重算得到准确历史，速度层给近实时近似值，服务层合并两侧 | 2010 年代前期的互联网公司（Hadoop + 流引擎时代） | 方法论，无许可 |
| Kappa 架构 | 拓扑：单链路 | 只保留流处理，历史重算靠**重放消息**（[Kreps, *Questioning the Lambda Architecture*, O'Reilly Radar, 2014]） | 事件流主导的业务 | 方法论，无许可 |
| 流批一体 · Flink + Paimon | 机制 + 产品组合 | 同一引擎的流/批两种执行模式；主键表以 LSM 组织文件，按 changelog-producer 产出变更流 | 实时数仓、Lakehouse | Apache 2.0 |
| 流批一体 · Flink + Iceberg v2/v3 | 机制 + 开放规范 | 删除以独立删除文件表达；规范 v3 引入删除向量与行谱系 | 需要多引擎共读同一份表 | Apache 2.0 |
| 流批一体 · Spark SS + Delta | 机制 + 产品组合 | 同一份 DataFrame 代码的两种触发；事务日志 + 列文件 | Databricks 生态 | Apache 2.0 / 托管服务 |
| Apache Beam | 可移植 API 层 | 一份 Pipeline 由不同 runner 执行，引擎可替换（Beam 入 Apache 孵化 2016、成为顶级项目 2017；来源：Apache 基金会公告）【公开】 | 多云、可移植性诉求 | Apache 2.0 |
| Materialize | 流式 SQL 数据库 | 增量物化视图：视图随输入变化做**差分更新**，不重算全量 | 需要「永远新鲜的物化视图」的场景 | 商业产品（部分组件开放） |
| 流式数据库 / 流优先存储（RisingWave、Apache Fluss 等） | 把「流」当一等存储对象 | 不把消息队列当存储，直接持久化流并支持变更查询 | 新系统选型；公开使用者以各项目披露为准 | Apache 2.0 / 商业 |

这 8 项其实分**三族**：**拓扑族**（Lambda、Kappa）、**统一族**（流批一体的几种组合、Beam）、**流原生存储族**（Materialize、RisingWave、Fluss）。同族内部差异小，跨族差异大——**先分族再选能省掉一半比较**：你首先要在「改拓扑」「换统一机制」「换存储形态」里选一种动作，而不是在 8 个名字里挑一个。

**对比过的候选全部保留**，只是重新归类：

| 归入本章哪一族 | 它的机制归属 |
| --- | --- |
| 拓扑族 | 用「两份实现 × 两份存储」换「每条链路各用最优引擎」 |
| 拓扑族 | 用「重放窗口」换「一份实现」 |
| 统一族 | 用「表格式的写放大/读放大」换「一份实现 + 一份存储」 |
| 流原生存储族 | 用「常驻内存状态」换「无重算的物化视图」 |

**上表只列机制，不断言「某个产品是否支持某特性」**：表格式与引擎的集成状态变化很快，把结论写死会产生过期断言。凡涉及具体能力，用下面三种**判定方法**自查，而不是相信任何静态清单：

- **某个表格式是否支持你需要的变更类型**：查其官方文档里「更新 / 删除 / 变更流」章节是否存在、以及该能力的版本门槛。只有「快照隔离」字样而没有行级更新说明的，不要假设它支持高频 upsert。
- **某个引擎组合的提交语义**：查 sink 文档里出现的是「两阶段提交 / 参与式提交」，还是只有「幂等写入」。两者对应 7.3.4 的两个不同档位。
- **某个组合的性能**：用自己的数据做 A/B——同一份 SQL、同一份输入、只切换执行模式或表格式，比一次内部结果；公开材料里的倍数只能用来判断「值不值得试」，不能用来下采购结论。

### 7.3 机制差异：为什么它们表现不同（核心节）

三族的全部差异可以归因到四个机制维度。选这四个，是因为它们分别回答选型时必然要问的四件事：**逻辑被实现几遍（7.3.1）· 变更怎么被表示（7.3.2）· 历史放在哪（7.3.3）· 结果什么时候算数（7.3.4）**。每个维度给出「机制 → 因果 → 公开证据 → 失效条件 → 自验方法」。

#### 7.3.1 实现份数：漂移是结构必然，不是执行失误

**机制是什么**：同一份业务逻辑在系统里存在几份**独立实现**。两份实现意味着两个独立演进的代码路径。

**各候选的实现差异**：

| 候选 | 业务逻辑实现份数 | 数据物理副本数 | 一处变更要改几处 |
| --- | --- | --- | --- |
| Lambda | 2（批 + 流） | 2（批存 + 流存） | 2 处，且必须证明一致 |
| Kappa | 1（流） | 1（队列） | 1 处 |
| 流批一体 | 1（同引擎两执行模式） | 1（同一张表） | 1 处 |
| Materialize | 1（SQL 定义） | 1 | 1 处 |

**由此必然导出的性质**：**因为**差异来自「存在两份实现」这个结构，**而不是**来自某处写错，**所以**两份实现之间的数值不一致是**时间问题不是能力问题**——边界值、窗口闭合方式、迟到数据的处理策略，两侧只要有一处判断不同就会分叉，而这种判断在两次独立开发中几乎必然不同。**因为** Kappa 把重算能力押在「重放」上，**所以**它实现份数降到 1，但代价转移到 7.3.3 的重放窗口；**因为** 流批一体把两份实现变成「一份定义派生出两种执行」，**所以** 漂移的来源从「两处实现」变成「一处定义 + 两种执行模式的语义差」，这是更小但**不为零**的残余风险。

**公开证据**：Flink 1.12 的发布说明把「流批统一」（同一个 API 增加批处理执行模式）作为该版本的头条特性（[Apache Flink 1.12 Release Announcement, 2020]）。可自行核验的判据是：**同一份 SQL 在流模式与批模式下的结果是否必须一致**——如果某个引擎的两种模式对迟到数据、对窗口边界有不同默认行为，那它就是「一套 API 两种语义」，而不是真正的统一。查任何引擎时，直接查其文档中「流批两种执行模式差异」这一节是否存在、有多长。

**失效条件**：当业务只需要一种模式时（例如纯离线 T+1 报表，或纯实时风控告警），统一执行模式带来的抽象与约束全是纯开销。此时「一份实现」的收益为 0，而它要求你接受的引擎选型约束是真的。

**自验方法**：取一个含迟到数据与窗口闭合的业务指标，用流、批两种执行模式各跑一次，比对结果差异的条数与原因。差异条数为 0 才说明你的实现是统一的；不为 0 时，差异原因就是你的漂移风险清单。

#### 7.3.2 变更怎么被表示：写放大与读放大的跷跷板

**机制是什么**：湖仓表格式要支持 upsert 与 delete，就必须把「变更」表示成某种可被扫描时合并的结构。表示方式决定了代价落在写入侧还是读取侧。

**各候选的实现差异**：

| 表格式 | 变更的表示 | 写入代价 | 读取代价 | 谁承担维护 |
| --- | --- | --- | --- | --- |
| Paimon（主键表） | LSM 分层文件 + 主键合并；按 `changelog-producer` 选项产出变更流 | 低（追加写小文件） | 读时合并多层 | compaction 作业 |
| Iceberg v2 | 独立的位置/等值删除文件 | 低（不重写数据文件） | 每次扫描都要应用删除文件 | compaction + 删除文件重写 |
| Hudi MOR | 增量写入日志文件，异步合并进列文件 | 低 | 取决于你是否按时合并 | compaction 作业（可异步） |
| Hudi COW / 直接重写 | 更新即重写所在数据文件 | 高（写放大 ≈ 更新条数 × 文件大小） | 低 | 写入路径本身 |
| Delta Lake | 事务日志 + 列文件；较新版本引入删除向量以避免删除时重写文件（[Delta Lake 官方发布说明, 2023]） | 取决于是否启用删除向量 | 低到中 | 写入路径 + 日志合并 |

**由此必然导出的性质**：**因为** Paimon 把写入累积成 LSM 的 L0 小文件、由 compaction 再往下层合并，**所以** upsert 写入便宜、但**读放大随层数与小文件数上升**——这不是缺陷而是记账方式的选择：写的时候少花钱，读的时候补；**因为** Iceberg v2 把删除记成独立文件而不是重写数据文件，**所以**删除操作本身很便宜，但**每一个查询都要把删除文件与数据文件做合并**，且删除文件数随更新频率增长——高更新频率的表因此表现为「写入量不大、读取越来越慢」，直到一次 compaction 把删除物化进新数据文件。**因为** COW 每次更新重写整个数据文件，**所以**当更新稀疏且单文件很大时写放大极高——这也是 MOR 存在的原因。

**一个常被忽略的推论**：**读放大不是由表格式的名字决定的，是由「你有没有按时 compaction」决定的**。同一种表格式，跑了 compaction 的和没跑的，查询性能差一个量级是很常见的【经验】。所以选型时该问的不是「Paimon 和 Iceberg 谁快」，而是「这套表格式的 compaction 是自动触发的还是要我自己排作业」——这个问题的答案决定了它需要几个人。

**公开证据**：Paimon 官方文档的 `changelog-producer` 选项列出了 `none` / `input` / `lookup` / `full-compaction` 等模式，并说明它们的差异：`input` 只反映输入记录的变更（upsert 场景下拿不到更新前的旧值），`lookup` 需要回查前值，`full-compaction` 的变更完整性与其合并节奏绑定（[Apache Paimon 官方文档 · Changelog Producer]）。可自行核验的判据：**任何声称「开箱即得完整 changelog」的说法都可疑**——完整变更流只有三种来源：源头的 CDC、写入时的回查、或合并时的物化，三者各有代价。

**失效条件**：当写入是**纯追加**（日志、事件流、不可变事实表）时，上述全部讨论失效——追加场景下没有「更新前的值」可丢，也没有删除文件要合并，此时表格式的选择空间比 upsert 场景大得多。**判断自己的写入形态是不是真的是纯追加，本身是要验证的一件事**：把过去一周的写入按操作类型统计一次，`UPDATE`/`DELETE` 占比是不是真的接近 0。

**自验方法**：对同一份数据分别用「密集 upsert」与「纯追加」跑一轮，记录「写入吞吐、查询 P95、小文件数、compaction 消耗的 CPU 时」。如果查询 P95 与小文件数同时上升，说明你欠了一次 compaction；如果写入吞吐先崩，说明你选的格式在把代价记在写侧。

#### 7.3.3 重放窗口：历史放在队列里，还是放在对象存储里

**机制是什么**：当上游逻辑变了、需要重算历史时，历史数据从哪里读。Kappa 的答案是「重放队列中的消息」，流批一体的答案是「重读对象存储上的表快照」。

**各候选的实现差异**：

| 候选 | 历史的物理位置 | 可重算窗口由什么决定 | 窗口延长一倍的边际成本 |
| --- | --- | --- | --- |
| Lambda | 批存（对象存储/数仓） | 批存的保留策略 | 对象存储单价，低 |
| Kappa | 消息队列 | 队列保留期（时间或容量上限） | 队列存储单价，高于对象存储 |
| 流批一体 | 对象存储上的表快照 | 表的保留策略（快照过期策略） | 对象存储单价 + 快照元数据 |
| Materialize | 物化视图的状态 + 上游可回放的输入 | 上游可回溯窗口 | 取决于上游，通常最短 |

**由此必然导出的性质**：**因为**队列是按「为传输而设计的常驻存储」定价，**所以**把重算窗口寄存在队列保留期上，等于用最贵的一层存储保存历史——**按 AWS S3 标准层 $0.023/GB-月（AWS S3 定价页 2024）【公开】与 Amazon MSK 存储 $0.1/GB-月（Amazon MSK 定价页 2024）【公开】两组单价估算，同一份 10 TB 历史，寄存在队列里比放在对象存储上每年多花约 $9.5k，月存储成本约为对象存储的 4 倍量级**（10240 GB × ($0.1 − $0.023)/GB-月 × 12 ≈ $9.5k【推算】）。**因为**流批一体把历史放在对象存储的表快照上，**所以**它把「可重算窗口」与「队列保留期」解耦——你可以只保留 1 天的消息用于传输，同时保留 3 年的表快照用于重算；**这也是「Kappa 需要无穷保留期的 Kafka」这个常见说法背后的真实成本结构**。

**公开证据**：Kappa 的原始论述（[Kreps, *Questioning the Lambda Architecture*, O'Reilly Radar, 2014]）本身就承认重放依赖「可重放的消息日志」，其可行性取决于保留策略【公开】；上述量级差异所依据的两个单价，分别取自 AWS S3 与 Amazon MSK 的定价页（2024）【公开】。可自行核验：把你现在队列的实际保留配置（时间 + 容量上限）换算成 TB，再乘队列存储单价，就是你为「随时可重算」支付的年费。

**失效条件**：当重放窗口短（例如只需重算最近 1–3 天）时，队列保留期的成本可以忽略，Kappa 的简洁性就是净收益；当业务对「历史可重算」的需求本身就弱（只修正最近窗口）时，流批一体的表快照保留策略带来的元数据开销反而是多余的。

**自验方法**：问一个问题——「如果口径定义今天变了，我需要重算多久的历史？」把答案写成天数，乘上日均写入量得到 TB 数，用两个单价各算一次年成本。这条算式就是 7.5 决策树里「重放窗口」这个节点的阈值来源。

#### 7.3.4 提交边界：端到端一致性的上限在哪，延迟下限也在哪

**机制是什么**：流式写入的一致性靠「同步点（checkpoint） + 参与式提交」实现。写出去的数据只有在一个同步点完成时才对外可见。

**各候选的实现差异**：

| 候选 | 提交粒度 | 端到端一致性上限 | 数据可见的延迟下限 |
| --- | --- | --- | --- |
| Flink + 表格式 sink | 同步点边界 | 端到端精确一次（当 sink 参与两阶段提交时） | ≈ 同步点间隔 + 提交开销 |
| Flink + 普通对象存储写出 | 依赖写入方式 | 通常只能到「至少一次 + 幂等键」 | 同上 |
| Spark Structured Streaming | 微批边界 | 通过幂等写入与检查点做到精确一次语义 | ≈ 微批间隔 |
| Kappa | 队列自身的提交语义 | 取决于消费者提交策略 | 与队列延迟同阶 |

**由此必然导出的性质**：**因为**参与式提交要求下游 sink 在同步点边界原子地完成可见化，**所以**承诺的端到端延迟下限是**同步点间隔**——把同步点间隔配成 1 分钟，再对外承诺秒级端到端可见，在机制上就不可能；**又因为**同步点也是故障恢复的边界，**所以**把它调小会同时收紧延迟与提高开销，这两件事无法分别优化。**因为**不参与两阶段提交的下游只能靠幂等键兜底，**所以**选型时「这个 sink 支不支持参与式提交」比「这个 sink 快不快」更该先问。

**公开证据**：Flink 官方文档的「端到端精确一次」一节说明了两阶段提交 sink 与检查点的关系（[Apache Flink 文档 · End-to-End Exactly-Once]）。可自行核验：查目标 sink 的文档里有没有「两阶段提交」或「参与式提交」字样；只有「幂等写入」字样的，属于另一档。

**失效条件**：当业务本身可以容忍重复（例如幂等聚合、可去重的指标），精确一次带来的清空写放大与延迟下限是净负担；当延迟要求宽松（分钟级以上）时，同步点间隔不再是瓶颈，一致性反而可以先于延迟优化。

**自验方法**：在测试环境里杀掉一个任务管理器，观察下游表里是否出现重复行或缺失分区。出现任一者，说明你的组合实际处在「至少一次」档，此时任何「端到端精确一次」的说法都还没有被验证。

### 7.4 成本结构对比（不是价格表，是成本函数）

三族的成本**随什么变量增长**：

```
年成本 ≈ 计算(引擎数 × 集群规格 × 8760h)
       + 历史存储(保留窗口 × 日均写入量 × 副本数 × 存储单价)
       + 小文件与元数据维护(写入量 × 合并频率 × 层数)
       + 人力(SQL 方言数 × 实现份数 × 值班面)
```

**主导项与隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| Lambda | 计算项（两套引擎常驻）+ 人力项（两份实现） | 口径不一致带来的**对齐成本**：每一次分歧都要一轮人肉对数 |
| Kappa | 历史存储项（队列保留期 × 写入量） | 重算时的**回放峰值**：重算会与实时流量抢同一套集群 |
| 流批一体 | 计算项（一套引擎常驻） | **小文件维护**：compaction 消耗的 CPU 与它占用的写入窗口，账单上看不见 |
| Materialize | 内存项（物化视图状态 × 基数） | 视图数量与输入基数的增长会把常驻内存推高，且难以预估 |

**为什么把「隐性成本」单列**：显性成本（集群、存储）在账单上可见，于是被高估；隐性成本（口径对齐、回放峰值、compaction、常驻内存）不出现在账单上，于是被系统性低估。**因为**显性成本随数据规模近似线性增长，**而**口径对齐成本大致与「变更频率 × 实现份数」成正比而与数据量无关，**所以**小数据量团队上 Lambda 时，账面上更贵的是引擎，实际上更贵的是对齐；数据量上去之后关系反转。

**【推算】数量级示例**（推导链完整给出，便于换参数重算）：

- **一套 Flink 常驻集群 20 台 8C16G**：按 AWS EC2 通用型 / 计算型 8 vCPU 档的按需价 **$0.3–0.5/h 量级**（AWS EC2 按需定价页 2024）【公开】→ 年支出 ≈ 20 台 × $0.4/h × 8760 h ≈ **$70k/年**【推算】。Lambda 模式要两套常驻 → **$140k/年量级**【推算】。这就是「双链路成本翻倍」这句话里唯一可算的那一半。
- **历史寄存位置的差**：10 TB 历史 = 10240 GB（按 1024 GB/TB 换算）。放对象存储标准层，单价 $0.023/GB-月（AWS S3 定价页 2024）【公开】→ 10240 GB × $0.023/GB-月 × 12 ≈ **$2.8k/年**【推算】；同样 10240 GB 寄存在云托管 Kafka，单价 $0.1/GB-月量级（Amazon MSK 定价页 2024）【公开】→ 10240 GB × $0.1/GB-月 × 12 ≈ **$12k/年**【推算】。差额约 **$9.5k/年**，与上面一条 20 台机器的账单相比是零头——**这说明「换存储省的钱」在流批选型里通常不是决定项，决定项永远是「要养几套计算集群」**。
- **compaction 的成本量级**：它约等于把「被合并的数据」再读写一遍，因此其年成本 ≈ 写入量 × 合并频率 × 存储吞吐单价。若日均写入 1 TB、每份数据平均被合并 1–2 次，就等于把 365–730 TB 的数据多读写了一遍【推算】。**它在账单上体现为 CPU 与 S3 请求费，而不是「compaction 费」这一行**——这也解释了为什么很多团队上线流批一体后「存储变便宜了、计算变贵了」。

**主导项随场景切换，所以优先级不是固定的**：

| 你的场景 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| 团队 < 10 人、日均写入 < 100 GB | 人力项（实现份数 × 方言数） | 减少实现份数，而不是优化引擎 |
| 日均写入 TB 级、只追加 | 计算项 + 存储项 | 表格式选型（追加场景下选项最多） |
| 日均写入 TB 级、upsert 密集 | 小文件维护项 | 先算清 compaction 要花多少 CPU，再谈表格式 |
| 重算需求频繁（口径常变） | 历史存储项 + 回放峰值 | 把历史放对象存储，别放队列保留期 |
| 实时风控 / 告警，无需历史重算 | 计算项 | 只要流链路，别引入批链路 |

**这条成本函数该怎么用**：不要拿它算绝对值——其中最不确定的一项（人力）恰好也是最大的一项，而它在候选之间往往部分抵消。要算的是**两个候选之间的差**，而算差的第一步只需要三样可以从现有系统里直接量出来的输入：**常驻集群数、日均写入量、重放窗口天数**——前两样定出计算项与元数据项的差，第三样配合 7.3.3 的两个单价定出历史存储项的差（这一步确实要用厂商单价，公式已给出，换成你自己的合同价重算即可）。**这三样覆盖不到另外几类判断**：写入形态要靠「过去一周的写入操作类型占比」量出来，常驻内存能不能估准要靠「1–2 周的内存实测曲线」量出来，跨引擎诉求要靠「引擎清单与合同期限」列出来，团队结构要靠「两侧是否存在独立的责任边界」判定——它们与上面三样一起，构成 7.5 决策树**全部判断节点**的依据来源。

### 7.5 决策树（每个分支都要有阈值依据）

```
你的处境？
├─ 业务只需要一种模式（纯 T+1 报表，或纯实时告警）
│    → 不要上流批一体：统一是给"两种都要"的场景准备的
│      （纯批：直接用批处理引擎；纯流：单一流链路）
├─ 业务逻辑复杂、需要各自场景的最优引擎、且已经有两支独立团队
│    → Lambda（双链路）。此时双链路的"复杂度"由组织吸收，不落到个人身上
├─ 只要实时、历史重算窗口 ≤ 约 74 天、且能接受回放与实时抢资源
│    → Kappa（单一流链路 + 重放）
│      窗口 > 约 74 天时改走下一支（窗口越长，队列寄存历史的成本越接近一套批引擎；约 74 天时天平反转，见下方阈值依据）
├─ 需要一份代码 + 一份存储，且写入以 upsert / delete 为主
│    → 流批一体 + 主键表（Flink + Paimon 一类）
│      必须同时排定 compaction 作业，否则读放大必然失控
├─ 需要一份表被多个引擎共读（不只 Flink）
│    → 流批一体 + 开放规范表格式（Iceberg v2/v3 一类）
│      前提：写入以追加为主，或能接受删除文件带来的读放大
├─ 只需要"永远新鲜的物化视图"、不做历史重算
│    → 流原生方案（Materialize / RisingWave 一类）
│      前提：常驻内存成本可估、视图数量可控
└─ 需要在多个引擎（Flink / Spark / 云服务）间保持可移植
     → 可移植 API 层（Beam 一类）
       代价：吃不到任何单个引擎的最新特性
```

**阈值依据**（与树上每个判断节点一一对应）：

- **「业务只需要一种模式」**：依据来自 7.3.1 的失效条件——统一执行模式的收益等于「你实际会同时用到两种模式的场景数 × 每场景的漂移风险」，只有一种模式时收益为 0，而引擎的选型约束照旧要接受。判断方法：把过去一个月的作业按「输入是否有界」分类（有界 = 批，无界 = 流），其中一类占比可忽略即落入本节点【经验】。
- **「重放窗口 ≤ 约 74 天」**：由 7.3.3 的成本函数给出。设日均写入 1 TB、按 1024 GB/TB 换算：队列寄存比对象存储每年每 GB 多花 ($0.1 − $0.023)/GB-月 × 12 ≈ $0.924/GB-年，折合每延迟一天约 **$946/年**（1024 GB × ($0.1 − $0.023)/GB-月 × 12 ≈ $946）【推算】；窗口短时差额很小（3 天约 **$2.8k/年**【推算】：3072 GB × ($0.1 − $0.023)/GB-月 × 12 ≈ $2.8k），远小于额外养一套批引擎的 **$70k/年量级**，Kappa 的简洁性是净收益；差额随窗口线性上升，约 **74 天**时（75776 GB × ($0.1 − $0.023)/GB-月 × 12 ≈ **$70k/年**）【推算】追平额外养一套批引擎的 $70k/年量级，天平反转——**这就是成本函数的净收益转向点，也是本节点阈值的出处**。**这条线不是行业常数**：日均写入量、你实际拿到的两个单价、以及你回放时是否需要第二套集群，都会移动它，公式已给出，请用自己的参数重算。该分支的另一半条件「能接受回放与实时抢资源」不对应独立阈值，它对应 7.4 里 Kappa 的隐性成本项——回放峰值会与实时流量抢同一套集群，可容忍则该项不计入。
- **「业务逻辑复杂、需要各自场景的最优引擎」**：不是阈值而是机制结论。实现份数为 2 时，两条链路才可能各用自己场景的最优引擎（7.3.1）；若两侧的引擎要求本来就相同，双链路换不来任何额外最优性，收益为 0。
- **「已经有两支独立团队」**：这是**组织结构判据，不是人数判据**。门槛不是一个 N 人，而是「实时侧与离线侧是否各自拥有独立的发布节奏与值班责任」——只要两侧的责任边界存在，双链路的对齐成本就落在组织接口上而不是某一个人身上（7.1 错误二）；同一批人同时负责两侧时，这个接口不存在，对齐成本全额落到个人。它无法用数据量阈值表达，只能按责任边界是否存在来判定。
- **「upsert 密集 / 追加为主」**：判据不是主观印象，而是过去一周写入操作的类型占比。**`UPDATE`/`DELETE` 占比长期低于 5% 时可视为追加为主**【经验】——此时 7.3.2 那张表里「删除文件」「LSM 合并」两栏的代价都不落在你头上，表格式的选择空间显著放宽。占比高时反过来。
- **「需要一份表被多个引擎共读」**：判定方法而非经验值——列出所有需要直接读这张表的引擎清单（含临时排查用的引擎），再看目标表格式的官方文档里是否提供这些引擎的读取连接器与能力说明。只要清单长度 > 1 且写入侧引擎不是唯一，7.2 的候选就收敛到「开放规范表格式」那一行；此时该分支的附加前提「写入以追加为主」由上面那条占比判据给出——占比高则删除文件的读放大小到可忽略，占比低则必须先把 compaction 排上。
- **「常驻内存成本可估」**：物化视图方案的成本主导项是内存，而内存需求与「视图数量 × 输入基数」同向增长，难以从小规模测试线性外推。**判据是：能否在 1–2 周内用真实基数跑出一份内存占用的实测曲线**【经验】；跑不出来就不该把它放进生产路径。该分支的另一半条件「不做历史重算」由 7.3.3 给出——物化视图的状态对应的是当前输入，不提供可回溯到任意历史时点的输入版本，要重算就得回到上游重新灌一遍。
- **「需要在多个引擎间保持可移植」**：来自**锁定约束**，不是技术优劣。判定方法是数两件事——你计划使用的执行引擎数（≥ 2 才是硬需求），以及你与云厂商的合同期限（长期承诺会降低可移植这份期权的价值）。
- **「compaction 必须排定作业」**：由 7.3.2 的机制直接导出，不是经验值——主键表或删除文件模式的读放大随时间单调增长，没有合并动作就没有上界。

**把决策树展开成执行顺序**（同一棵树，按时间轴读）：

1. **第 0 步 · 先统计事实，再谈选型**：过去一周的写入操作类型占比（append / update / delete）、日均写入量、两侧结果不一致的工单数。这三项分别喂给判据 3、判据 5、判据 1，缺了它们，树的每个节点都只能靠印象回答。
2. **第 1 阶段 · 只动配置**：同步点间隔、表快照保留期、队列保留策略、合并触发频率。这四项都是可回滚的，且能在一周内把「配置型问题」排除掉——很多「流批不一致」的工单，根因是两侧读的快照时间点不同，而不是逻辑不同。
3. **第 2 阶段 · 收敛实现份数**：把两份实现改成「一份定义派生两种执行」。这一步的验收标准不是「代码行数减少」，而是 7.3.1 的自验方法——同一输入在两种执行模式下结果差异为 0。
4. **第 3 阶段 · 才动存储形态**：换表格式、换历史寄存位置。这一步会同时改变写入路径、读放大与提交语义，是三阶段里唯一不可快速回滚的。
5. **持续 · 把维护动作写进看板**：小文件数、每分区文件数、合并消耗的 CPU 时、同步点间隔与实际端到端可见延迟。缺了最后一项，「秒级可见」永远是文档里的一句话而不是事实。

> 这条顺序的机制依据是：**配置 → 逻辑 → 存储** 三层的回滚成本依次上升一个量级，而它们的收益并不按同一比例上升。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 实时数仓 + 明细可回溯 | Flink + Paimon | Flink + Iceberg v3 | 选流原生方案（Materialize 一类）：历史重算能力弱，口径变更时要重搭 |
| 一份表要被 Spark / Trino 一起读 | Flink + Iceberg | Flink + Paimon + 导出 | 选主键 LSM 表：非 Flink 引擎的读取路径通常不是它的最优路径 |
| Databricks 生态、团队已熟 Spark | Spark Structured Streaming + Delta | Flink + Iceberg | 为统一而换引擎：团队再学习成本高于收益（见 7.7） |
| 纯事件流、重算窗口短 | Kappa（单流链路） | Lambda | 上双链路：多一套引擎只为覆盖很少发生的重算 |
| 两支独立团队、两侧各自最优 | Lambda | 流批一体 | 强行统一：把两个团队的边界之争变成一次平台迁移 |
| 只要「永远新鲜的物化视图」 | Materialize 一类流原生方案 | 流批一体 + 定时刷新 | 用流批一体做：刷新间隔决定了新鲜度，做不到持续新鲜 |
| 多云可移植 | Beam | 直接用目标引擎 | 直接用：锁死在单引擎，但能吃到全部新特性 |

**三组组合全部保留，并补两组**；每条说明职责边界与运维代价：

1. **流批一体 + 实时 OLAP（Doris / StarRocks 等）**：湖仓表负责「一份存储、可回溯、可重算」，OLAP 引擎负责「高频、固定模式的聚合查询」。边界是**明细归湖、聚合归 OLAP**。运维代价：多一条「湖 → OLAP」的同步链路，它是新的口径分叉点——必须明确哪一端是权威，否则又回到双链路的老问题。
2. **流批一体 + 向量库（LanceDB / Milvus 等）**：湖仓表负责原始事件与特征的可回溯版本，向量库负责近邻检索索引。边界是**向量索引是可重建的派生物，不承担事实来源**。运维代价：索引重建需要把上游全量重跑一次，因此上游的重算窗口不能短于索引重建周期。
3. **流批一体 + 知识图谱（Neo4j 等）**：湖仓表产出实体与关系的变更流，图谱做增量更新。边界是**图谱不持有唯一真源**。运维代价：图数据库的写入是逐条事务式的，吞吐远低于批量导入，变更流必须做背压与批量聚合，否则图库成为整条链路的瓶颈。
4. **统一执行模式 + 多引擎共读表格式（补）**：同一份定义派生两种执行模式，表格式选开放规范以便非 Flink 引擎共读。边界是**执行模式归 Flink，元数据与规范归表格式**。运维代价：两条路径（流写、批读）的统计信息与文件布局优化目标不一致，需要额外的元数据整理作业。
5. **CDC 入湖 + 联邦查询（补）**：变更捕获链路把源库变更持续写入湖表，查询侧用联邦引擎按需读取。边界是**入湖链路只负责把变更送达，不做业务聚合**。运维代价：源库 schema 的每一次变更都要在入湖链路与查询侧各验证一次。

**组合的共同原则**：每个组合都必须能回答「哪一件是事实来源」，其余全部是可重建的派生物；回答不出来时，你得到的是双链路的复杂度加上流批一体的运维面。

**组合里最容易出错的四处边界**（每一条都对应一个结构性冲突，与具体产品无关）：

- **权威端不清**：湖 → OLAP 的同步链路一旦变成双向，就等于重新制造了两份实现，双链路的老问题原样回来。
- **派生物被当成真源**：向量索引与图谱一旦被下游当作事实来源，任何一次索引重建都会表现为「数据短暂不存在」。
- **缺背压**：增量变更的写入速率与下游逐条事务式写入的能力不匹配时，下游必须能拒绝或缓冲，否则它自己变成新的瓶颈。
- **保留期错配**：上游的重算窗口短于下游派生物的重建周期时，口径变更后派生物无法重建——这要求上游保留策略的设定必须参考下游最慢的重建周期。

### 7.7 选错的代价与迁移成本

**反模式：把「流批一体」理解成「把所有批处理都改成流处理」** —— 用流式引擎跑全量历史重算，状态规模随历史长度单调增长，重算一次占满集群数小时 → 因为流式执行模式的设计目标是**处理无界输入的增量**，用它做有界全量就是把一台为「持续小步」设计的机器用来做「一次性大搬」→ **正确做法**：同一个引擎的**两种执行模式**各归其位——增量归流模式，历史重算归批模式；这正是流批一体区别于「一切都是流」的地方。

**反模式：用拉长队列保留期来实现 Kappa 的可重算** —— 为了「随时能重放一年」，把消息保留期调到一年，最终账单里消息存储占了一半以上 → 因为队列是按为传输设计的常驻存储定价，用最贵的一层存历史（7.3.3 的推算：约 4 倍于对象存储）→ **正确做法**：把历史放到对象存储的表快照上，队列只保留传输所需的窗口。

**反模式：只看表格式名字，不排 compaction 作业** —— 上线时读写都正常，三个月后查询越来越慢、小文件数上万，团队开始怀疑「这个表格式不行」→ 因为主键表与删除文件模式的**读放大随时间单调增长**，没有合并动作就没有上界，问题不在格式而在运维缺失 → **正确做法**：上线同一天就排定 compaction 与文件重写作业，并把「小文件数」和「每分区文件数」做成看板指标。

**反模式：用打分的办法做平台决策** —— 拿一张五维评分表选定技术栈，两年后发现真正的痛点是「两份实现的口径对齐」，而这一项在表里只占「代码复用」一格 → 因为打分把**结构性成本**（实现份数、副本数）与**运行期指标**（性能、复杂度）混在同一根尺子上 → **正确做法**：先用 7.1 的六条判据筛掉结构性不匹配的方案，再在剩下的候选里比运行期指标。

**反模式：把「统一」当成组织问题的解药** —— 实时团队与离线团队对同一个指标的口径长期争执，于是引入统一执行模式，期望技术统一能结束争论 → 因为技术只能保证「同一份定义产出的两个结果相同」，**不能决定这份定义归谁写**；定义权仍在组织里，争执会原样搬到「谁来维护这份定义」上 → **正确做法**：先明确指标定义的负责人与变更审批流程，再谈执行模式统一；顺序颠倒等于把一次组织决策包装成一次平台迁移。

**换成另一条路线要动什么**：

| 迁移方向 | 数据迁移 | 逻辑改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| Lambda → Kappa | 中：批存逐步废弃，历史转队列或转表快照 | 中：批逻辑要改成可重放形态 | 中：少一套批引擎，多一套重放与回放容量 | 单链路调试、重放演练 | 3–9 人月 |
| Lambda → 流批一体 | 大：两份存储要合并成一份表 | 大：两份实现要收敛成一份定义 | 大：新引擎 + 新表格式 + 新提交语义 | 表格式、compaction、精确一次 | 6–18 人月 |
| Kappa → 流批一体 | 小：队列历史迁到表快照 | 小到中：逻辑基本可复用 | 中：新增批执行模式与表维护作业 | 表格式与同步点语义 | 3–6 人月 |
| 流批一体 → Lambda（回退） | 大：从一份表拆出两条链路 | 大：一份逻辑要裂成两份 | 中：新增一套专用引擎 | 双链路一致性验证 | 6–12 人月 |
| Materialize 一类 → 流批一体 | 大：物化视图状态无法直接迁移 | 大：增量视图定义要改写成表 + 调度 | 大：常驻内存模型换成集群 + 存储 | 表格式与调度 | 6–15 人月 |

> 量级按「一个熟悉本系统的 3–5 人小组」估算【经验】。**回退方向（流批一体 → Lambda）之所以昂贵，是因为它要重新制造出你当初花力气消除的「两份实现」**——这条迁移的价值主要在于提醒：**「实现份数」是一个结构性选择，改动它无论朝哪个方向都要付本表最高一档的迁移成本**（把两份实现收敛成一份是 6–18 人月，把它再拆回两份是 6–12 人月），所以它不是可以按需来回切的开关。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 只需一种模式 | 不要上流批一体 | 统一的收益来自「两份都会用到」，只用一份时收益为 0 |
| 两支独立团队、两侧各自最优 | Lambda | 实现份数为 2，但组织能吸收由它产生的对齐成本 |
| 重算窗口短、只要实时 | Kappa | 重放窗口短时，队列保留期的成本可以忽略 |
| upsert 密集、要一份存储 | 流批一体 + 主键表 | LSM 把写代价记在写侧，读侧由 compaction 兜住 |
| 多引擎共读 | 流批一体 + 开放规范表格式 | 删除文件的读放大可用 compaction 换取多引擎兼容 |
| 只要永远新鲜的视图 | 流原生方案 | 增量维护视图避免重算，代价转移到常驻内存 |
| 承诺秒级端到端可见 | 先把同步点间隔压到秒级 | 延迟下限由同步点边界决定，配置不改，承诺就不可兑现 |
| 上线任何表格式方案 | 同一天排定 compaction | 读放大随时间单调增长，没有合并动作就没有上界 |
| 需要跨引擎可移植 | 可移植 API 层 | 用「吃不到单引擎最新特性」换「不锁死在单引擎」 |

> 本节小结：本章三族方案（拓扑族 = Lambda / Kappa；统一族 = 流批一体的各组合与 Beam；流原生存储族 = Materialize / RisingWave / Fluss）之间**唯一真正起决定作用的差异**是——**同一份业务逻辑与同一份数据，在你这里存在几份**。拓扑族用「两份实现」换每条链路的最优性；统一族把份数压到一份，代价转移到表格式的写放大/读放大与 compaction 运维；流原生族把份数压到一份且免去重算，代价转移到常驻内存。其余所有维度（性能、复杂度、AI 友好、延迟）都是这三笔代价的**表现形式**，而不是可以与它们并列比较的独立分数。
>
> 💡 **思考锚点**：先报一个数——同一个业务指标，你这边有没有两份实现（离线一套 SQL、实时再写一遍 Flink），还是共用一份定义？若是两份，Lambda 的对齐成本由谁在吸收；若是一份，请当场指认代价转移到了哪一笔——表格式的写放大/读放大与 compaction 运维，还是流原生方案的常驻内存？说不出转移点的那一笔，你打算拿什么证据说它已经省下来了？
