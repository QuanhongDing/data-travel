## 3. 设计模式与范式

> 原 § 3 共 81 行、为模式清单 + 场景决策表 + 反模式清单，缺少结构示意、机制解释与失效分析，重写为 8 小节模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

决策表把设计讲成「按场景选一个」，但同一句「实时数仓 + Lakehouse」，在三个团队手里会落到三个不同的组合上。原因不是偏好，而是约束不同：写入是纯追加还是高频 upsert、读是点查还是全表扫描、历史要能重算多久、端到端一致性承诺到哪一档、以及有没有人愿意长期维护 compaction 作业。约束一变，正确的模式就变。

流批一体这个主题里，有一条约束是决定性的：**流与批的差异不在引擎，而在「这份数据能不能被当作无界变更流来读」**。引擎同时支持两种执行模式，只把统一做到代码层；只有当存储能把「更新前后」的差异外化成一条变更流，同一份数据才能既被流式增量消费、又被批量全量扫描。所以本节反复出现的判据是同一个：**这张表能不能产出变更流，产出变更流的代价记在写侧还是读侧。**

另一条容易被忽略的约束是**重放窗口**：口径定义改一次，要重算多久的历史？重算的历史放在队列保留期上还是表快照上，决定了「随时可重算」这件事的年成本量级（量级推导见 [§ 7 与其他方法对比](10-stream-batch-unified-section-7-sec7.md)）。下面每个模式的第一句都先写它被哪条约束逼出来——写不出约束的模式，不要选。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式（追加 vs 高频 upsert） | 表格式要不要主键、要不要 LSM、要不要 changelog | 「选最流行的表格式」——纯追加场景下主键表与 changelog 全是净开销 |
| 访问模式（点查 / 扫描 / 聚合） | 代价记在写侧还是读侧，以及要不要独立查询引擎 | 「一份存储解决所有查询」——点查与全表聚合的最优结构相反 |
| 变更频率与历史要求 | 重放窗口放在队列还是表快照，快照保留策略定多长 | 「流批一体就不需要保留策略」——可重算窗口由快照保留决定，不设就是不可重算 |
| 一致性要求 | 同步点间隔、sink 是否参与两阶段提交、能否承诺端到端精确一次 | 「用流式引擎就等于精确一次」——不同步点即不可见，间隔就是延迟下限 |
| 规模与成本 | compaction 是自动还是自己排班，以及值不值得自建 | 「统一存储一定更省」——统一后的运维面从两套变成一套，但这一套的技术门槛更高 |
| 团队技能与运维能力 | 选托管特性还是自建目录与调度 | 「架构先进就选它」——没人维护 compaction 的表格式，退化成比朴素的批量表更差 |

这些约束之间有优先级，顺序错了会白做功：**先看写入形态（追加还是 upsert），再看访问模式（点查还是扫描），最后才是引擎与生态。** 反过来做的团队，通常会落在「引擎选好了，但表格式不适合自己的更新频率」这个位置上，后面所有调优都是补丁。下面 3.2 的每个模式，都在同一组问题下回答：它被哪条约束逼出来、结构长什么样、代价记在谁头上、以及什么时候它会从对变成错。

### 3.2 模式逐个拆解（核心节）

以下 7 个模式覆盖原文件列出的全部模式（原 §3.1 的模式 1–6，外加原 §3.2 决策表中列出的「流批 + AI 原生」一条），并保留原有名称。

#### 3.2.1 Flink + Paimon 流批一体（原模式 1，最主流）

- **被什么约束逼出来**：上游是 CDC / 事件流，写入含大量 upsert，而下游既要「秒级看到变更」又要「对全量做批扫描」——主键表必须同时便宜地接住更新，并把更新当成流交出去。
- **结构**：

```sql
CREATE TABLE paimon_orders (
  order_id BIGINT, user_id BIGINT, amount DECIMAL(18,2), ts TIMESTAMP(3),
  PRIMARY KEY (order_id) NOT ENFORCED
) WITH (
  'connector'            = 'paimon',
  'path'                 = 's3://lake/paimon/orders',
  'changelog-producer'   = 'lookup',   -- 写入时回查前值，产出完整变更流
  'snapshot.time-retained' = '7 d'     -- 可重算窗口由快照保留决定
);
-- 流读同一张表（变更流）：SELECT * FROM paimon_orders;
-- 批读同一张表（快照）：  SELECT ts, SUM(amount) FROM paimon_orders GROUP BY ts;
```

- **为什么这样设计有效**：因为写入先落成 LSM 的 L0 小文件、由 compaction 再向下列合并，所以 upsert 以追加方式落地、写放大低；又因为 `changelog-producer` 把「更新前后的差异」外化成变更流，所以同一份存储既满足流式增量读、也满足批量快照读——这就是「统一」落在存储层而不是只落在代码层的含义。
- **代价**：LSM 把成本系统性地挪到读侧与后台：读放大随层数与小文件数增长；compaction 是一条必须有人排班或调参的后台作业链；`lookup` 让每次写多一次回查，`full-compaction` 则把变更流的完整性与合并节奏绑死（合并不跑，变更流就不完整）。
- **失效点**：当写入是**纯追加**（日志、事件、不可变事实表）时，「更新前的值」根本不存在，changelog 的三种产出方式全部是净开销，但仍要付 LSM 合并与小文件维护的成本——此时优点（upsert 便宜 + 变更流完整）反转成缺点（白付读放大与运维面），因为机制解决的是一个你的场景里不存在的问题。
- **真实使用**：Paimon 原名 Flink Table Store，是 Flink 生态原生的流式表格式，更名与毕业时间以 Apache 官方公告为准（[Apache Paimon 官方文档, Primary Key Table / Changelog Producer, 2024]）；本目录 [§ 6 落地实践](10-stream-batch-unified-section-6-sec6.md) 记录的阿里（2016–2024）与字节（2019–2024）的推进路径，重点正是「统一的对象到底是定义、存储、引擎还是平台层」【公开，转引本仓库 §6 案例，年份与该文各案例小标题一致】。
- **上线前必须验证的一件事**：用同一份带更新的数据，分别以流模式与批模式读这张表，逐行比对结果条数与差异原因；差异不为 0，说明变更流的产出方式还没对齐你的写入形态。

#### 3.2.2 Flink + Iceberg V3 流批（原模式 2）

- **被什么约束逼出来**：数据已经在 Iceberg 上（历史资产、跨引擎消费者已固定），不能为了拿到流能力而迁表；同时需要「改一个字段/删一行」而不重写整个数据文件。
- **结构**：

```text
写入：Flink 流作业 ──► Iceberg 表（v2：行级删除文件；v3：增量读取增强）
                        ├─ data files      （只追加，不改写）
                        ├─ delete files    （位置删除 / 等值删除，独立文件）
                        └─ snapshots       （快照即增量读的边界）
读取：① 增量（流） SELECT * FROM t FOR SYSTEM_TIME AS OF <snapshot> / 增量快照
      ② 批量（批） SELECT ... FROM t  → 每次扫描都要把 delete files 与 data files 合并
```

- **为什么这样设计有效**：因为删除与更新被记成**独立文件**而不是重写数据文件，所以写入本身很便宜，且任意引擎（Flink / Spark / Trino）都能用同一份快照读出一致结果——这是 Iceberg 作为开放表格式的核心价值：**统一发生在规范层，而不是某个引擎的运行时里**。
- **代价**：读取代价被系统性地抬高：每次扫描都要把删除文件应用一遍，删除文件数量随更新频率增长，表因此表现为「写入量不大、查询越来越慢」，直到一次 compaction 把删除物化进新数据文件。此外快照本身有元数据成本，保留策略要单独设计。
- **失效点**：当表是**高频 upsert 的主键表**（例如每分钟更新一次的订单状态表）时，优点（写入便宜）会反转成缺点（读越来越慢），因为删除文件累积的速度超过 compaction 消化的速度；此时正确动作是换成主键表（LSM 型）或把更新收敛到小范围分区，而不是继续加查询引擎的算力。
- **真实使用**：Iceberg 的行级删除由表规范 v2 引入、增量读取在 v3 中强化（【公开】[Apache Iceberg 官方表规范, Format Version 2 · Row-level Deletes 与 Format Version 3 增量读, 2024]；具体版本措辞以规范原文为准）。判定自己的表是否踩在上面的失效点上，用一条可自行核验的判据：**查最近一次快照的 delete file 数量与扫描计划里的文件数**，如果两者同步增长，说明读放大已经在累积。
- **上线前必须验证的一件事**：统计这张表一周内 `UPDATE`/`DELETE` 占写入的比例。若明显高于你预估的水平，先做一次 compaction 前后查询 P95 的对比，再决定是否继续用这套存储结构。

#### 3.2.3 Spark Structured Streaming + Delta 流批（原模式 3）

- **被什么约束逼出来**：团队与资产已经在 Spark / Databricks 生态里，流与批必须共用同一份 DataFrame 代码与同一套调度，不希望为一个实时链路再引入第二套运行时。
- **结构**：

```python
# 同一份代码，两种触发方式 —— 统一发生在「一次触发 = 一个有界批次」
q = (spark.readStream.format("kafka").option("subscribe", "orders").load()
        .writeStream.format("delta").option("checkpointLocation", "s3://ck/orders")
        .trigger(availableNow=True)      # 消费积压后停止：流式接口 + 批语义
        .start())
# 批读同一张表
spark.read.format("delta").load("s3://lake/delta/orders")
```

- **为什么这样设计有效**：因为 Spark 把流抽象成「连续的有界微批」，所以「补历史」与「跑实时」是同一个算子的两种触发方式；又因为 Delta 的事务日志是唯一事实来源，批读与流读看到的是同一个版本——**一致性由日志提供，而不是由两条链路的对账提供**。
- **代价**：延迟下限等于微批间隔，秒级以下的实时性拿不到；每个流作业必须维护 checkpoint 目录，checkpoint 的结构一旦变更（算子拓扑改动）就要重建；此外删除向量的引入让「删除代价低、读取代价取决于是否按时合并」这一跷跷板依然存在。
- **失效点**：当业务要求**亚秒级端到端可见**时，这个模式的优点（一份代码、一个运行时）反转成缺点（微批间隔成为硬延迟下限），因为你无法在保持微批语义的同时把可见延迟压到比一个批次更短；此时应把该链路判定为流处理而非流批一体，另选运行时。
- **真实使用**：`Trigger.AvailableNow` 由 Spark 3.3 引入，用于「按可用数据量消费一轮后停止」的场景（【公开】[Apache Spark 3.3 发布说明 · Trigger.AvailableNow, 2022]）；Delta 的删除向量让「删除」不必重写数据文件，并自 3.0 起默认开启（【公开】[Delta Lake 3.0 官方发布说明 · 删除向量, 2023]；该特性的预览形态出现在更早版本，具体版本号与默认值以官方发布说明为准）。
- **上线前必须验证的一件事**：把微批间隔按目标延迟配一遍，实测「事件产生 → 表里可见」的端到端 P99。若目标延迟小于实测值，先改触发方式或运行时，不要先加资源——提交边界不是靠算力缩短的。

#### 3.2.4 Apache Beam 跨引擎流批（原模式 4）

- **被什么约束逼出来**：同一段逻辑需要在多云 / 多引擎上运行（合规、成本、既有资产迁移），且不希望为每个运行时维护一份实现——约束是**运行时可替换性**，而不是性能。
- **结构**：

```text
                 ┌── Flink Runner
Beam Pipeline ───┼── Spark Runner        ← 同一份 DAG，多个执行后端
（一份代码）      ├── Google Cloud Dataflow Runner
                 └── Direct Runner（本地测试）
约束点：可移植性换来的是「只能用各 Runner 共同支持的、已定义的语义子集」
```

- **为什么这样设计有效**：因为 Beam 把「逻辑 DAG」与「执行运行时」显式分离，所以同一份代码可以在不同引擎上跑出语义一致的结果；又因为可移植层只暴露各后端共同支持的语义，所以跨引擎行为差异被限制在一个已知的、可测试的子集里——**可移植性的本质是「主动接受语义损失以换取可替换性」**。
- **代价**：你必须放弃后端特有的优化与特权特性（自定义 source/sink、引擎专属的状态与调优开关），性能通常低于为该引擎手工优化的实现；跨后端的语义差异需要在 CI 里用多 Runner 对账，这是一条长期维护的测试成本。
- **失效点**：当业务对性能或对某个引擎的独有能力（如与湖表格式的两阶段提交集成）有硬要求时，可移植性的优点反转成缺点——为一个你不打算更换运行时的问题，付出了性能与能力上的双重代价，因为抽象层无法穿透到后端的提交协议里。
- **真实使用**：Beam 由 Google 捐给 Apache 软件基金会并成为顶级项目（【公开】[Apache 软件基金会公告 · Beam 毕业为顶级项目, 2017]），其定位就是「一套 API 多运行时」；本目录 [§ 5 前沿演进](10-stream-batch-unified-section-5-ai.md) 把「跨云、跨引擎流批一体（Beam + 开放表格式 REST 接口）」列为演进方向之一。
- **上线前必须验证的一件事**：列出你实际使用到的引擎独有能力（自定义 source/sink、专属状态后端、与表格式的提交协议集成），逐个确认 Beam 是否覆盖；覆盖不到的，就要提前决定「这条链路不做可移植」。

#### 3.2.5 Flink CDC + Iceberg/Paimon 实时入湖（原模式 5）

- **被什么约束逼出来**：分析侧已有的查询引擎（Trino / StarRocks）不能改，业务库的变更必须进来，而队列的历史保留期太短、不足以承担重算——需要一条「业务库变更 → 湖表 → 既有查询引擎」的通道。
- **结构**：

```sql
-- 入湖作业：CDC 源 + 主键表 sink（关键在 changelog 的产出方式）
INSERT INTO paimon_orders           -- 或 iceberg.orders
SELECT order_id, user_id,
       CAST(amount AS DECIMAL(18,2)) AS amount,
       ts
FROM   mysql_orders_cdc;            -- 'connector'='mysql-cdc'，快照 + 增量日志
-- 查询侧：Trino / StarRocks 直接读湖表，不感知流的存在
-- SELECT shop_id, SUM(amount) FROM paimon_orders WHERE dt = CURRENT_DATE GROUP BY shop_id;
```

- **为什么这样设计有效**：因为 CDC 源提供的是「先快照后增量」的完整变更序列，所以入湖作业可以一次写清「历史 + 增量」，不需要为初始化单独跑一套批链路；又因为湖表格式把数据与元数据放在对象存储上，查询引擎可以独立于写入引擎扩容——**写入与查询解耦，是这条通道能同时服务实时与批量的原因**。
- **代价**：CDC 的初始快照阶段会对源库产生读压力（大表尤其明显），增量阶段则长期占用源库的日志读取通道；入湖作业的并行度、分桶与 compaction 策略直接决定查询侧的小文件数量，需要专门的调优；源表 DDL 变更（加列、改类型）需要一条明确的下游同步流程。
- **失效点**：当源表是**高频大范围更新**（例如全表批量刷新的批处理业务表）时，CDC 通道把每一次更新都变成一次入湖写与后续读放大，优点（实时性 + 解耦）反转成缺点（写入与 compaction 双双成为瓶颈），因为变更流的价值建立在「更新是局部的、有主键的」这一前提上。
- **真实使用**：本目录 [§ 6 落地实践](10-stream-batch-unified-section-6-sec6.md) 记录的 LinkedIn 案例即「把变更捕获做成入湖入口，流写湖、批读湖，两种时效共享一份存储」【公开，转引本仓库 §6 案例，2019–2024】。
- **上线前必须验证的一件事**：在源库上先量出「初始快照阶段的读压力」与「增量阶段的日志读取带宽」两条曲线，再决定入湖并行度与目标分桶数；大表初始快照直接压生产库是这条链路最常见的第一次事故。

#### 3.2.6 Materialize 流式 SQL 数据库（原模式 6）

- **被什么约束逼出来**：需求不是「湖上跑 SQL」，而是**「把一条持续变化的查询结果始终维持在最新状态」**——即结果必须常驻可用，查询方拿到的不是快照而是当前值。
- **结构**：

```sql
-- 声明式：定义「结果应该是什么」，由系统持续维护它
CREATE SOURCE orders FROM KAFKA CONNECTION kafka_conn (TOPIC 'orders');
CREATE VIEW paid_orders AS SELECT shop_id, SUM(amount) AS gmv
  FROM orders WHERE status = 'PAID' GROUP BY shop_id;
CREATE MATERIALIZED VIEW shop_gmv AS SELECT * FROM paid_orders;  -- 结果常驻并增量更新
```

- **为什么这样设计有效**：因为物化视图的维护是**增量式**的（输入变化只重算受影响的部分，而不是重跑整条查询），所以「结果常驻最新」的代价不随数据总量线性增长；又因为 SQL 定义同时是血缘与口径，逻辑只有一份实现——这正是 §7 所说的「实现份数 = 1」在查询侧的表现。
- **代价**：常驻状态是成本本身——维护视图所需的内存/存储随「被维护的数据量 × 查询复杂度」增长，而不是随查询频率增长；它依赖上游可回放的输入来重建状态，重建窗口由上游保留期决定；此外它与湖表生态的集成度弱于 Flink/Spark 组合，历史数据仍要另建存储。
- **失效点**：当被维护的数据量或视图链路复杂度超过单集群容量时，优点（查询即查结果、延迟极低）反转成缺点（维护成本高于收益），因为增量维护的状态必须常驻内存且不能像批作业那样随时中断重启；此时正确动作是缩小被维护的范围（只维护高频查询的聚合），而不是无限扩容。
- **真实使用**：Materialize 的实现基于增量数据流计算（Timely / Differential Dataflow 语义），其定位为「流式 SQL 数据库」（【公开】[Materialize 官方文档, 物化视图 / 增量维护与状态管理, 2024]；本目录 [§ 5 前沿演进](10-stream-batch-unified-section-5-ai.md) 将「流式数据库」列为趋势之一）。可自行核验的判据：查它的文档里「状态占用」是不是与数据量同阶——是，则你的成本模型应按常驻状态算，而不是按查询次数算。
- **上线前必须验证的一件事**：压测一条最复杂的视图链路，记录状态占用与重建时间；再用「上游回放」演练一次状态重建，确认上游保留期足够长——上游保留期短于重建时间，这个模式的可靠性承诺就是空的。

#### 3.2.7 Flink + AI Functions（原 §3.2 决策表中的「流批 + AI 原生」）

- **被什么约束逼出来**：同一段特征/推理逻辑既要服务实时链路（事件到达即算），又要服务离线链路（对历史全量重算），而两条链路各写一份实现就会产生与 Lambda 相同的漂移——约束是「训练与推理必须用同一份变换逻辑」。
- **结构**：

```text
Flink SQL / DataStream
  Kafka 事件 ──► 规则过滤（确定性算子）──► AI Function 调用（LLM / Embedding）
                                   │              │
                                   │              └─► 失败走旁路输出（不阻塞主链路）
                                   └─► Sink：paimon_features（同时写入 embedding 列 + model_version 列）
批侧：对同一份 UDF、同一份 model_version 重算历史 → 与流侧结果比对
```

- **为什么这样设计有效**：因为 UDF 与模型版本被固定在算子里、且随结果一起落表，所以流侧结果与批侧重算结果可以逐行对账；又因为推理调用被放在条目级算子中，异常可以走旁路（dead letter）而不阻塞主链路——**「AI 算子化」的价值在于让模型调用获得与普通算子相同的失败语义与重放语义**。
- **代价**：把外部有状态服务（模型端点）引入数据管道，带来三类必然成本：调用延迟成为管道延迟的一部分、失败重试可能重复计费、以及模型版本变更后历史不可重现（同一份输入在不同模型版本下产生不同输出）。这些成本无法靠调参消除，只能靠「版本与输出一起落表 + 旁路」来隔离。
- **失效点**：当需要**对历史数据重放出一致结果**（模型审计、回溯归因）时，优点（一份逻辑、两侧一致）反转成缺点（不可重放），因为外部模型不是确定性算子，除非把模型版本与输出一起物化——这一点在纯规则管道里不存在，是引入 AI 算子后新增的失效面。
- **真实使用**：本目录 [§ 5 前沿演进](10-stream-batch-unified-section-5-ai.md) 记录的 2024 年路线方向即「Flink 内置 LLM / Embedding，同一份代码同时跑 ETL 与 AI」。这一条目前应作为方向而非成熟方案评估——可自行核验的判据：目标引擎是否提供「把模型调用纳入同步点语义（参与式提交 / 幂等重试）」的书面说明；没有，就还处在「至少一次」档。
- **上线前必须验证的一件事**：制造一次模型端点超时与一次重复投递，观察主链路是否被阻塞、下游是否出现重复计费或重复行；再把模型版本号与输出一起查一遍，确认历史结果能被解释。

这 7 个模式的共同点值得单独指出：**它们没有一个在消除「代价」，全都在选择「代价记在哪里」**。3.2.1 把代价记在读取侧与后台作业，3.2.2 记在读取侧的删除合并，3.2.3 记在提交间隔，3.2.4 记在语义子集，3.2.5 记在源库的 CDC 通道，3.2.6 记在常驻状态，3.2.7 记在外部模型的不确定性上。所以选型时真正要问的不是「哪个更快」，而是「这笔账记在我这边还是别人那边、有没有人愿意付」。

表中最常被误选的一对是 **3.2.2（Iceberg v2）与 3.2.1（Paimon 主键表）**：两者看起来都是「湖上流批读写」，但前者的删除是独立文件、后者是 LSM 分层合并。误选的实际后果不是「性能差一点」，而是**随更新频率增长的读放大**——一张每分钟更新一次的订单状态表放在 Iceberg v2 上，写入会一直很通畅，查询却逐周变慢，团队最终把问题归因为「查询引擎不够强」，去买更大的集群，而真正的修法是换存储结构。反过来，把纯追加的日志表放进主键表同样错：白付 LSM 合并与 changelog 的成本。

用这张表的正确方式是**从「关键判据」一列倒着读**：先量出自己表的更新比例、微批/同步点能接受的间隔、以及重算窗口，再去表里找匹配行；直接按「约束组合」一列对号入座，很容易把自己的场景描述成表里最吸引人的那一行。特别提醒：**「推荐模式」一列永远不是排他的**，前四行可以共存于同一个数据栈，只是各自承接不同的表。

### 3.4 组合模式：真实系统不会只用一种

下面三个组合是真实系统里最常见的同时并存形态：每个组合都等于「入湖 / 存储 / 查询」三层各选一个之后的形态，而不是某个单一模式的放大版；读的时候重点看每条的「运维代价」——组合的收益与代价往往不在同一层。

**组合 A：CDC 入湖 + 湖表 + 读侧按查询特征分派**

- 构成：3.2.5（入湖）+ 3.2.1 或 3.2.2（存储）+ 读侧两选一：Trino / StarRocks 直读快照，或 3.2.6 流式数据库常驻维护高频结果。
- 职责边界：入湖作业只负责「把变更准确地写进湖表」，不承担查询；湖表是唯一的历史与重建来源；查询侧只读快照（或读被维护出来的结果），不感知流的存在。
- 读侧分派之一（独立查询引擎）：点查与批扫都直接读湖表快照，元数据缓存、资源组与扩容都由查询引擎自己配——运维面最小，代价是每次查询都要现算。
- 读侧分派之二（流式数据库）：只把「被高频查询的那几个结果」交给 3.2.6 常驻维护，它重建状态时从湖表回填而不是从队列重放——查询即查结果，代价是常驻状态占用。
- 运维代价：一条入湖链路的稳定性 + 湖表的 compaction 排班 + 查询引擎的元数据缓存；三处任一处出问题都表现为「数据看起来是旧的」。带上流式数据库后还要多担两件事：两条链路的口径必须同源（否则「实时数」与「离线数」打架），且回填链路的正确性要单独演练——重建状态是这类系统唯一不能靠滚动重启解决的故障。
- 适合规模：表数从几十到几千、读多写少、需要同时服务 BI 与实时看板【经验，量级取自常见实践】；只有「有几条明确的高频查询、其余查询可以走湖表批扫」时，才值得在 A 之内再引入流式数据库【经验】。
- 失效边界：当高频查询只有一两条、且它们本身就是低频扫描可以替代的看板时，流式数据库带来的常驻状态与回填演练是净开销——此时读侧只保留独立查询引擎。

**组合 B：队列承担重放窗口 + 湖承担长历史**

- 构成：Kafka（短保留）+ 3.2.1/3.2.3 的表快照（长保留）。
- 职责边界：队列只负责传输与「最近几小时的重放」；更早的历史由湖表快照承担，重算读湖不读队列。
- 运维代价：两套保留策略要一起设计（队列保留期 > 最大可容忍的下游中断时长；快照保留期 > 最大重算窗口），任何一侧被临时调小都会让「可重算」这件事静默失效。
- 适合规模：需要「随时重算一周以上历史」的场景。量级对比见 [§ 7 与其他方法对比](10-stream-batch-unified-section-7-sec7.md) 的成本结构一节。
- 失效边界：当需要重算的窗口本身只有几小时（短于队列保留期）时，湖表快照只是多一层要维护的元数据与过期策略，此时队列单独承担重放更省事。

**组合 C：一份定义 + 双执行模式 + 调度编排**

- 构成：统一 SQL 定义 + Flink 流模式（常驻）+ Flink/Spark 批模式（按需重算）。
- 职责边界：定义只有一份，流模式负责增量，批模式负责补齐与重算；口径变更时两侧同时生效而不是各自改一遍。
- 运维代价：两条执行路径的**结果对账**必须自动化（否则漂移不可见）；批任务的资源调度与流任务的常驻资源要分开配额，避免互相抢占。
- 适合规模：有专人维护指标平台、且指标口径变更频繁的组织。
- 失效边界：没有专人维护指标平台时，这份「唯一定义」会退化成又一处需要同步的配置——此时两份 SQL 加上自动对账反而更便宜。

三句选择建议：**组合 A 解决「变更怎么进来、读侧按什么分派」，组合 B 解决「重算窗口放哪」，组合 C 解决「定义怎么只有一份」。** 三者不互斥，但每加一条，就多一条必须有人负责的链路——先决定可以接受几条长期维护的链路，再决定加哪一个。

组合的公共前提只有两条，缺任何一条组合都会退化成「两套系统各跑各的」：**一是口径/定义同源**（否则组合内部先漂移），**二是结果可对账**（否则组合之间的问题会以「数字对不上」的形式在业务侧爆发，而不是在平台侧告警）。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 强行流批一体 | 只有流需求或只有批需求，却先选引擎后找场景；流作业里一半算子从未被增量触发 | 抽象层与状态后端的开销全部落在一条单模式链路上，延迟与资源双输 | 技术选型从技术榜开始，而不是从访问模式开始 | 先写清访问模式（点查 / 扫描 / 增量），单模式够用就不统一 |
| 选错表格式 | 写入吞吐正常但查询逐周变慢；小文件数持续上升 | 代价被记账到读侧或被记账到写侧，选反了就是长期补丁 | 按生态亲和度选（Flink 选 Paimon、Spark 选 Delta）而没看更新频率 | 按「更新频率 + 是否需要变更流」选，而不是按引擎品牌选 |
| 忽视 Changelog | 流式查询读不到变更或读到不完整的变更；下游对账口径总差一截 | 变更流的完整性取决于产出方式（源头 CDC / 写入回查 / 合并物化），选错档位就无法兑现「流读」承诺 | 表建好了、能写能读，就以为流批一体已经完成 | 显式配置并验证 `changelog-producer`：`input` 拿不到旧值，`lookup` 加写回查，`full-compaction` 依赖合并节奏 |
| 状态爆炸 | 任务稳定一段时间后 checkpoint 越来越大、恢复时间越来越长 | 流状态按 key 累积且无 TTL，恢复时要从头重建状态，RTO 与延迟一起恶化 | 只按业务字段做 key，没有为「状态该保留多久」设一个显式决定 | 设状态 TTL + 重设 key 粒度 + 评估是否改用湖表存中间结果 |
| 性能预期过高 | 上线后发现端到端延迟由同步点间隔或微批间隔决定，而不是由吞吐决定 | 一致性与延迟是同一个旋钮的两端，「统一」不会让任何一端免费变好 | 把「统一」理解成「更快」，而不是「更少实现份数」 | 先定义延迟承诺，再决定同步点/微批间隔；用实测 P99 而不是宣传口径 |
| 忽视 Schema Evolution | 上游加列/改类型后，流或批一侧先失败、另一侧静默算错 | 两侧的 schema 演进能力不同步，失败形态是「静默算错」而不是报错 | schema 变更没有纳入 CI，靠人记得通知下游 | schema 变更进 CI + 两侧契约测试 + 明确「加列 / 改类型 / 删列」各自的兼容策略 |
| 统一了引擎，但没统一保留策略 | 上游口径变更后想重算，却发现快照已过期、队列已清空 | 「可重算」这个能力被静默收回：系统仍能跑，但历史再也回不去 | 保留策略被当成成本项而不是能力项，且没人知道它决定重算窗口 | 把「最长重算窗口」写成天数，反推快照与队列的保留期，并纳入变更评审 |

其中四条最危险，另有两条容易忽略的边界条件，值得一并展开：

**忽视 Changelog。** 它危险在于「看起来一切正常」：表能写、SQL 能查、批任务能出结果，只有依赖**流读**的那一条链路在静默地缺变更。典型暴露方式是一次对账：批侧与流侧的数字在某一天之后持续偏离，而两侧的作业都没报错。根因是变更流的完整性与产出方式绑定——`input` 只反映输入记录的变更，在 upsert 场景下拿不到更新前的旧值；`lookup` 需要回查前值；`full-compaction` 的完整性绑在合并节奏上。任何「开箱即得完整变更流」的说法都应当被要求给出证据。

**状态爆炸。** 它的暴露方式是渐进的：先是 checkpoint 变大（存储成本悄悄上升），再是恢复变慢（故障时 RTO 从分钟级变成小时级），最后在流量的高峰遇到反压。根因是流状态按 key 累积，而团队从未显式回答「这个 key 的状态需要保留多久」。修法不是加内存，而是给状态设 TTL，并回答「窗口关闭后这个状态还有谁用」——如果没人用，就应该在窗口结束时清掉。

**性能预期过高。** 它的成因是把「流批一体」误读为一次性能升级。机制上，统一带来的是**实现份数从 2 降到 1**（见 [§ 7](10-stream-batch-unified-section-7-sec7.md) 的实现份数一节），而端到端延迟的下限仍由提交边界（同步点间隔或微批间隔）决定。因此正确的问题是「我的延迟承诺是多少，这个间隔能不能满足」，而不是「换成流批一体能快多少」。

**统一了引擎却没统一保留策略。** 它比前三条更隐蔽：系统一切正常，只是某个时刻业务提出「口径变了，把过去几个月的数重算一遍」，团队才发现快照保留期只有几天、队列保留期更短——「可重算」这个能力从来没有被真正拥有过。原因是保留策略在预算表里是成本项，在能力表里却被写成「支持随时重算」。修法很简单也很难：把「最长重算窗口」当成一个需要签署的承诺，写进天数，再从它反推保留期。

**两条容易被忽略的边界条件。** 一是**备份逻辑与重算逻辑不是一回事**：保留快照的动机是「口径变了要重算」，保留备份的动机是「数据被写坏了要回到过去」，两者的保留期通常不同、凭据也必须隔离，用同一套存储承载会在一次误删中同时失去两者。二是**表格式的失效模式与业务增长方向相反**：读放大在数据量增长时暴露、写放大在更新频率提高时暴露，而这两件事在企业里往往同时发生——所以决策时不能只按当前指标选，还要问「写完量翻倍、更新频率翻倍之后，这套结构会先疼哪一侧」。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 表数从数十到数千 | 3.2.2 Iceberg 为主 | 小文件与删除文件的维护从「顺手清」变成一条需要排班的作业链 | 引入 3.2.1 主键表承接高频更新，Iceberg 只保留追加类资产 | 双表格式并存，目录与权限要覆盖两套；查询侧要认识两种表 |
| 更新频率从天级到分钟级 | 3.2.2 / 直接重写文件 | 写放大变成瓶颈（重写数据文件）或读放大变成瓶颈（删除文件累积） | 3.2.1 主键表（LSM） | 需要为 compaction 设配额与告警；历史表的转换要一次全量重写 |
| 需要重算的历史从 3 天到 3 年 | 队列保留期承担重放 | 队列存储单价高于对象存储，年成本随窗口线性上升 | 3.2.1/3.2.3 的表快照承担长历史，队列只留传输所需 | 快照保留策略要重新设计（保留多久、元数据成本多少、过期策略谁执行） |
| 消费者从 1 个引擎到多引擎 | 单引擎组合（3.2.1 或 3.2.3） | 每个新引擎都要重做一套适配与血缘，接入成本线性增长 | 3.2.2 开放表格式 + 独立查询引擎，或 3.2.4 可移植层 | 放弃部分引擎专属优化；需要额外的跨引擎一致性对账 |
| 端到端可见性从秒级收紧到亚秒级 | 3.2.3 微批（或任何以同步点/批次为提交边界的模式） | 提交边界就是延迟下限，调小间隔同时抬高开销 | 把该链路判定为纯流处理（状态计算 + 直接服务），湖侧退化为旁路落档 | 结果不再天然与批侧同源，必须显式设计对账 |
| 单表数据量从 GB 到 TB | 单作业 + 全量扫描 | 批扫描时间线性增长，compaction 单次耗时超过调度间隔 | 按分区/分桶拆分写入与合并，或把大表拆成「热表（近期，主键表）+ 冷表（历史，追加）」 | 拆分点要一次定好并写进血缘；查询侧要能透明地看到两张表 |
| 团队从 3 人扩到 3 个组 | 一个人负责全链路 | 表格式、保留策略、对账规则都只存在于某个人的记忆里，变更没有评审入口 | 把「表格式与保留策略」变成登记项（谁改、为什么改、影响哪些下游），并纳入 CI | 需要一套元数据登记与影响面查询，这本身就是一条要维护的链路 |
| 从「单 Region 单栈」到「多 Region 同时消费同一份数据」 | 单 Region 的入湖 + 单 Region 查询 | 跨 Region 读的对象存储流量与延迟不可忽略，而跨 Region 复制通道的时效承诺通常是分钟级 | 把「近实时」的消费方留在写入 Region，跨 Region 只承接批与重算 | 需要按消费方拆分读写归属，并在路由层显式区分「近实时」与「可延迟」两类请求 |

一句话总结这一节：**模式不是被「规模」淘汰的，是被「约束的变化」淘汰的**——写入形态变了、更新频率变了、重算窗口变长了、消费者变多了，这四个变化中的任何一个，都会让原来正确的组合开始疼。

### 3.7 自检清单

- [ ] 每个表的写入形态（追加 / upsert）是否**实测统计过**（按操作类型统计一周的写入），且所选表格式的失效模式（写放大还是读放大）与这个频率匹配？
- [ ] 每张需要流读的表，是否**验证过**变更流完整（包含更新前值），而不只是配置里有 `changelog-producer`？
- [ ] compaction 是否有人**负责**排班、小文件数与读放大是否有监控告警，且每条新增链路都有明确的长期维护责任人（没有人名的那条，应当先不建）？
- [ ] 端到端延迟承诺的下限，是否与同步点间隔 / 微批间隔对得上（承诺秒级却把间隔配成 1 分钟即违反）？
- [ ] 「重算历史」需要多久，是否写成天数，并据此设定了快照/队列的保留策略？
- [ ] 流侧与批侧的结果是否**自动对账**，且差异会告警（而不是等人发现）？
- [ ] schema 变更是否进了 CI，且「加列 / 改类型 / 删列」在两侧的兼容策略是否明确？
- [ ] 每个有状态的流作业，是否都显式设定了状态 TTL，并回答了「窗口关闭后状态给谁用」？
- [ ] 是否评估过「这个场景只需要流或只需要批」，而不是默认上流批一体？
- [ ] 是否有一个可运行的演练/回放脚本，能在不碰生产的条件下验证重算链路的正确性？
- [ ] 「最长重算窗口」是否是一个被签署过的天数（而不是「取决于保留策略」这种回答）？
- [ ] 是否区分了「重算用的快照」与「防写坏的备份」——两者的保留期和凭据是否已经分开？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 高频 upsert + 需要变更流 + Flink 生态 | 3.2.1 Flink + Paimon 主键表 | LSM 把写放大压到最低、changelog 产出可控，代价落在读侧与 compaction |
| 既有湖上资产 + 多引擎消费 + 低频更新 | 3.2.2 Flink + Iceberg v3 | 删除记成独立文件使写入便宜、规范层统一使引擎可替换 |
| Spark / Databricks 生态 + 秒级以上延迟 | 3.2.3 Spark + Delta | 微批语义让「补历史」与「跑实时」共用一份代码与一个事务日志 |
| 运行时可替换性优先 | 3.2.4 Apache Beam | 逻辑与运行时解耦，代价是只能用各后端共同支持的语义子集 |
| 业务库变更入湖 + 查询引擎不改 | 3.2.5 Flink CDC + 湖表 | 快照 + 增量一次写清，写入与查询解耦 |
| 结果常驻最新 + 高频查询 | 3.2.6 Materialize 类 | 增量维护让「结果最新」的代价不随查询次数增长，而随状态量增长 |
| 训练与推理共用变换逻辑 | 3.2.7 Flink + AI Functions | 一份 UDF 消除漂移，代价是模型调用的延迟、计费与不可重放性 |
| 只有 BI、T+1 新鲜度 | 不引入流批一体 | 没有主键、没有增量需求时，统一抽象只带来常驻资源与运维面 |

> 本节小结：本主题下决定模式选择的**唯一那条约束**是——**这张表是否真的有主键（即写入是追加还是 upsert）**。它决定了变更流是否必须存在、代价记在写侧还是读侧、以及 compaction 是否成为一条必须有人负责的作业链；其余约束（延迟、成本、团队技能）都在它之下做微调。
