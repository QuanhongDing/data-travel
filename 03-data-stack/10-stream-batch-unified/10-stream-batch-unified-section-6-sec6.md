### 10.1 阿里"**Flink + MaxCompute 流批一体**"8+ 年（2016-2024）

**背景（Why）**

阿里 2016 年面临**流批分裂**：
- **离线 = MaxCompute**——SQL 写一份
- **实时 = Blink（基于 Flink）**——SQL 又写一份
- **同指标 8% 漂移**——两套 SQL 必然漂移
- **维护双倍**

**触发点（What）**

2016 年阿里启动**流批一体**（[阿里 2016]），目标：
- **一套 SQL 流批都跑**
- **口径 100% 一致**
- **0 漂移**

**详细做法（How）**

阿里流批一体的**5 大核心组件**：

1. **Flink 流批一体（核心创新）**
   - 关键设计：**同一份 SQL → 流 + 批两种执行**
   - 关键能力：**一套代码**
   - 关键数字：**口径一致 99%+**

2. **MaxCompute 批（核心）**
   - 关键设计：**离线 SQL 大规模执行**
   - 关键能力：**PB 级**
   - 关键数字：**EB 级**

3. **Blink 流（核心）**
   - 关键设计：**Flink 实时执行**
   - 关键能力：**毫秒级**
   - 关键数字：**延迟 < 5s**

4. **统一数据湖（核心）**
   - 关键设计：**Iceberg + OSS 共享**
   - 关键能力：**流批同源**
   - 关键数字：**数据 0 冗余**

5. **统一指标平台（核心创新）**
   - 关键设计：**指标定义 → 自动生成 Flink SQL + MaxCompute SQL**
   - 关键能力：**0 漂移**
   - 关键数字：**漂移 -100%**

**阿里流批一体关键数字**（[阿里 2016-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **口径漂移** | 8% | 0% | **-100%** |
| **EB 级** | 不可用 | 100% | **∞** |
| **延迟** | 分钟级 | < 5s | **-99.9%** |
| **维护成本** | 2x | 1x | **-50%** |
| **流批一体** | 不可用 | 100% | **∞** |
| **数据 0 冗余** | 不可用 | 100% | **∞** |
| **指标平台** | 不可用 | 100% | **∞** |
| **MaxCompute + Blink** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：阿里流批一体团队 200+ 人
- 关键数字：**EB 级**；**漂移 -100%**；**维护 -50%**
- 业务影响：覆盖**阿里全集团**

**失败教训**

- 早期「**流批漂移 8%**」——两套 SQL 必然漂移，倒逼流批一体
- **完全统一太难**——Flink 流批语义有差异，**窗口计算不同**；后**批重算部分 + 流增量部分**
- **指标平台集成难**——定义生成 SQL 跨引擎有差异，**后逐引擎适配**

> **本节小结**：
> - 4 个真实案例（阿里 / Netflix / 字节 / LinkedIn）印证：**流批一体不是「**两套 SQL 拼起来**」，是「**Flink + Spark 共享 Iceberg + 同源同定义**」**5 件套**。
> - 关键时间线：阿里 8+ 年 / Netflix 5+ 年 / 字节 5+ 年 / LinkedIn 5+ 年 —— **流批一体是 5+ 年长期工程**。
> - 选型第一原则：「**Flink + Spark 共享 Iceberg**」（**最简单**）——**10+ 表** → 「**Flink CDC + Trino 联邦**」（**必须**）→ 「**统一指标平台 + Time Travel**」（**生产**）→ 「**全球 + 跨云**」（**AI 时代**）。
> - 99% 的失败来自「**流批两套 + 漂移 5-10% + 完全统一难**」——必须有 **同源同定义 + 流增量批重算 + 冻结 API**。
> - 真正的 ROI 来自「**漂移 0% + 维护 -50% + 8 亿+ 用户**」——是**大厂核心流批一体基础设施的命脉**。
