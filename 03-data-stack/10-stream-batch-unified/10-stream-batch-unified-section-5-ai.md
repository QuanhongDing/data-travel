## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本节要解的第一个问题不是「流批一体能不能接 AI」，而是**时间刻度**。把"引擎的 SQL 里能调用一个模型"（这一侧有正式的功能条目，核验入口见 §5.4）与"由 Agent 决定流处理的拓扑与并行度"（这一侧公开信息以框架演示为主）并列写成"演进方向"，读者据此排路线图时无法判断哪一条今天能进架构。判断能不能落地，本章有一条比别处更前置的约束可用，写在 [§3.1](10-stream-batch-unified-section-3-sec3.md)：**流与批的差异不在引擎，而在「这份数据能不能被当作无界变更流来读」**。这条约束不会被 AI 改动——模型可以把 embedding 算得更准、把失败日志归因得更好，但它不能让一张没有主键的表产出变更流，也不能让一个纯追加的表自动获得"更新前的值"。

第二条约束出自 [§3.2.7](10-stream-batch-unified-section-3-sec3.md)，本节要把它放到中心：流批一体的承诺是**「同一份代码」应当等价于「同一份结果」**（[§7.3.1](10-stream-batch-unified-section-7-sec7.md) 把"实现份数 = 2"写成漂移概率的结构性来源）。AI 恰好把**一个不在你控制下、也不是确定性函数的外部服务**放进了那份代码里。本节的全部评估都围绕这件事：它改的不是引擎，改的是"同一份代码"与"同一份结果"之间的等号。

本节用 L1 / L2 / L3 三级区分，判据必须是**可核验**的三条：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条各挡住一类误判：①挡住"把路线图当既成事实"（"AI Functions"这一条本身就是以路线形态出现的），②挡住"把厂商自述当行业现状"，③挡住"把演示当工程"。**三条全中才算 L1**，可以排进路线图；只满足一部分、或只有厂商自有案例的算 **L2**，可以做 PoC、不要作为核心依赖；只有路线图 / 论文 / 演示的算 **L3**，记录即可、不要在架构里预留假设。"感觉成熟"不算判据——它在架构评审会上无法被复核。

**判据声明（本节不对 L1 判据做任何修正）**：上文那三级与三条判据沿用到底，不替换、不放宽。本主题有一处特别诱人放宽的地方，先把话说死：流批一体的成效指标（端到端延迟、两侧对账差异、单位数据成本、compaction 资源占用）**全部是各家内部运行数据**，公开材料最多到"我们做了这件事"，很少到"因此某个指标从多少变到多少、口径是什么"。于是连"既有能力"那几行也凑不齐第②条：把"没有第三方公开案例"重写成"有公开生产记录""有可被复核的机制性材料（论文 / 规范 / 官方文档）"，只是给同一条判据换措辞，读者按新措辞照样核验不了。本节的做法是：**够不到第②条的行一律降为 L2，并在判据格里写明它卡在哪一条**，而不是为它重新定义"什么叫合格的第三方案例"。结果是**下表没有任何一行达到 L1**；其中"**没有任何一条 AI 能力方向到 L1**"是本节最重要的一句话。**L2 不等于"不好"，也不等于"不能现在做"，只等于"公开证据到不了 L1"**——真正要警惕的是把 L2 当 L1 排进核心链路。

写这一节时最容易混的三件事，先在这里分开：

- **产品名 vs 能力名**：同一个能力在不同引擎、不同发行版里叫法不同（把模型推理写进 SQL 的那一类表函数就是例子）。本节因此**刻意不写具体函数名**：写死一个名字，读者换一个引擎就会误引。要核"你们用的引擎有没有这个能力"，看该引擎 ML / AI 模块官方文档里有没有推理表函数这一条目、以及它的版本门槛，而不是看博客里的函数名。
- **已发布版本 vs 路线图**：判断某个引擎 / 表格式是否真的支持某能力，只看一处——**该版本的 release note 或官方文档里有没有对应条目**；项目官网的路线图页、benchmark 博客、生态伙伴的转述都不算。"某能力（2024 路线）"这类措辞本身就是路线，不能当作既成事实。
- **单集群 / 分布式**：流式数据库与流优先存储维护的是**常驻状态**，它的容量上限由单集群决定，横向扩展要换一套语义（[§3.2.6](10-stream-batch-unified-section-3-sec3.md) 把"常驻状态占用"写成本身就是成本）。判定方法：看文档里"状态占用"是否与数据量同阶——是，则你的成本模型按状态算，而不是按查询次数算。

本主题的证据形态还要单独说一句：**它会系统性地压低全表的级别**，且不因方向本身的优劣而改变。读表时请把这一层看进去：L2 说的是"公开证据到不了 L1"，不是"这个能力不好用"；真正需要警惕的是把 L2 当 L1 排进核心链路——那意味着你在向组织承诺一件公开证据支持不了的事。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**——改变了成本结构、改变了接口边界、把人工判断换成统计判断，还是只换了个前端？本主题的答案有三条落在机制上，分别展开 §5.2.1 / §5.2.2 / §5.2.3 三组（§5.1 表 11 行当中，AI 侧共 6 行，即第 1–5、8 行）：**§5.2.1 改变了确定性**（把外部模型调用放进 Logic，"一份代码 = 一份结果"这条等号被打破），**§5.2.2 改变了成本结构**（embedding 从"周期性批量物化"变成"事件驱动增量物化"），**§5.2.3 改变了接口边界**（事件流从"传输与解耦"变成"唯一可复现来源"：存储多了一类记录目的，而日志本身的语义没变）。余下的 5 行（第 6、7、9、10、11 行，即 §5.2.4 那一组）**与 AI 没有因果关系**。这个分类不是文字游戏：**改变确定性的方向，接入后必须补"版本与输出一起落表"，否则你会先得到一份对不上的对账表**；只改接口边界的方向（§5.2.3），接入后仍要面对"生成物可校验、动作可回滚"这个前提，收益只兑现到只读的 trace 与回放上。

| --- | :---: | --- | --- |

三条判据在本主题里各自挡掉了什么，值得逐条看清楚：**第①条**挡掉的是"路线图当既成事实"——"AI Functions（2024 路线）"这条本身就是路线，而"某引擎内置 LLM"这类说法要先落到具体条目上（是表函数、是独立的 AI 模块，还是仅有一篇博客）；**第②条**挡掉的是"把厂商自述当行业现状"——整合案例（"流处理 + 向量库"，加上 LangChain / AutoGen 一类编排框架）出自这些组件各自的提供方，按判据读就是"厂商自有案例"，正是 L2 的定义；**第③条**挡掉的是"把演示当工程"——"Agent 决策进流水线""模型改拓扑"这类方向，卡的不是效果，是**没有稳定的接口形态**，因此无法被测试、无法被回滚，也就无法被验收。

**这三级的排法直接决定路线图的顺序**：

- **先做的是表里那些已经落在正式条目上的非 AI 行**：把确定性的自适应能力打开、把变更流的产出方式按写入形态对齐（[§3.2.1](10-stream-batch-unified-section-3-sec3.md) 的 `changelog-producer` 那一组选择）、把两侧对账自动化。它们排在所有 AI 方向之前，因为**模型调用要么进一条本来就能对账的链路（收益立刻可见），要么进一条本来就对不上的链路（把对不上变成对不上且更贵）**。
- **AI 方向里值得尽早试的是 §5.2.1 与 §5.2.2 那两条 L2**，并且先测两个数：**推理延迟的 P99**（它决定检查点能开多密）与**模型输出的可对账率**（模型版本 + 输出一起落表后，流侧与批侧重算结果逐行一致的条数占比）。这两个数拿不出来，两条就停在原地。
- **L3 不排进排期**：Agent 决定拓扑、模型改参数、流式 GraphRAG 都属于"等信号"。它们的共同前提（生成物可静态校验、动作可回滚、外部模型版本可固定）比选哪家模型重要得多。
- **回填机制**：每次引擎或表格式大版本升级时回填一次级别；某个 L2 若一年内仍拿不到自己组织里的实测数字，降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次"把 AI 接进来"，都对应一处新的不可复现点与一笔新的外部计费。

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 模型调用算子化 | Logic 从确定性函数变成对外部有状态服务的调用 | **改变了确定性**（"一份代码 = 一份结果"的等号被打破） |
| §5.2.2 流式 RAG / 向量索引 | embedding 的物化时机从"按周期批量重建"变成"按事件增量写" | **改变了成本结构**（新鲜度与重建成本解耦） |
| §5.2.3 流式 Agent 与流式 GraphRAG | 事件流从"传输与解耦"变成"唯一可复现来源" | **接口边界**（存储多了一类目的：为了可复现而记录） |
| §5.2.4 同组五条 | 收益来自接口标准、既有产品能力或范式，没有一条来自模型 | **与 AI 无因果关系** |

读法建议：如果时间只够读一节，读 §5.2.1——它是本主题里唯一一条"接进来就必须改表结构"的方向（模型版本要进列）；§5.2.2 的收益要等你把删除传播与版本一致性处理完之后才兑现；§5.2.3 里真正可用的是只读的 trace 与回放，其余部分都卡在"生成物可校验、动作可回滚"这同一个前提上。

#### 5.2.1 模型调用算子化：一份代码不再等于一份结果

- **旧做法与它的卡点**：特征与推理逻辑在流链路与批链路各写一份，卡点是**漂移是结构必然而不是执行失误**——[§7.3.1](10-stream-batch-unified-section-7-sec7.md) 已经论证过：边界值、窗口闭合、迟到数据的处理策略，两侧只要有一处判断不同就会分叉，而两次独立开发几乎必然不同。写成算子（UDF）只把"两份实现"压成"一份实现"，没有回答另一个问题：这份实现的输出是不是可复现的。
- **AI 改变了什么机制**：**它把 Logic 从确定性函数变成了对「外部有状态服务」的调用**。规则算子给定输入必得同一输出，所以"重跑一遍"是可靠的验证手段；模型端点不是——它的行为随模型版本变、也随服务方的一次静默更新变。[§3.2.7](10-stream-batch-unified-section-3-sec3.md) 给了这条路的价值：模型调用放进条目级算子后，它获得与普通算子相同的失败语义与重放语义（失败可走旁路、不阻塞主链路）。本节要补的是它**丢掉了什么**：可复现性。
- **由此得到的**：**因为不可复现的那一步可以被限制在"只发生一次"，所以流批两侧仍然可以逐行对账**——做法是把模型输出当成**输入数据**来物化：同一份 UDF、同一份 `model_version`，输出与版本一起落到同一张表（[§3.2.7](10-stream-batch-unified-section-3-sec3.md) 的结构）。此时批侧读到的不是"再跑一次模型"，而是"读流侧当时写下的那一列"。这是本方向真正的落地形态，也是它区别于"在管道里插一个 API 调用"的地方。
- **由此付出的**：**其一，调用延迟成为管道延迟的一部分**，而它会挤进同步点间隔——推理 P99 直接决定检查点能开多密，也就是说**它同时动了延迟和一致性这两件事**；**其二，重试的代价从"重复一行"变成"重复一次付费调用"**，幂等键必须带在请求上而不是只带在表主键上；**其三，语义档位要退回一档**：外部端点不参与 sink 的两阶段提交，端到端精确一次要求外部服务支持幂等键（判定方法：看引擎文档里有没有把模型调用纳入同步点语义的书面说明——没有，就还处在"至少一次"档）；**其四，它把模型变成了血缘上的一个上游**：不记录版本号，历史结果就不可解释，而"解释不了的历史"在模型审计与回溯归因的场合等于没有历史。
- **证据与来源**：【公开】模型推理以表函数形态进入 SQL，是引擎 ML / AI 模块官方文档中的正式条目（函数名与版本门槛因引擎与发行版而异，核验入口见 §5.4）；【公开】"流式接口 + 批语义"这一侧的成熟度有可核验锚点——Spark 的 `Trigger.AvailableNow` 出现在 3.3 发布说明（2022），Delta 的删除向量出现在 3.0 发布说明（2023）。**【本节未能核到】"同一份含模型调用的代码，流侧与批侧重算后逐行差异为 0"的第三方公开材料**（§5.4）。
- **成熟度**：**L2**。判据：①③成立（推理表函数是正式条目、算子接口多年未变），②核不到（无第三方含对账口径的生产案例）→ 可以做 PoC，前置条件是"版本随输出落表 + 旁路"两件都落地。

| 放进算子的东西 | 是否可复现 | 该不该物化 |
| --- | --- | --- |
| 规则 / 表达式 / 聚合 | 是 | 不必单独物化，重算即得同一结果 |
| embedding | 否（随模型版本变） | 要：向量 + `model_version` 一起落表 |
| LLM 生成结果 | 否（同输入也可能不同输出） | 要：输出 + `model_version` 一起落表，请求侧摘要另存 |
| Agent 的动作（带副作用） | 否，且不可回滚 | 不能只物化输出，要物化"谁批的、依据是什么" |

- **判定方法**：取一条已上线的含推理算子的链路，把模型端点停掉十分钟——观察主链路是阻塞、降级还是把请求落进旁路，以及旁路积压有没有人处理。**第二个动作**：把两条链路的输出按输入主键做一次全量比对，数出"批侧重算与流侧原值不一致"的条数；不为零时，逐条看差异来源里有没有"多跑了一次模型"。
- **什么时候值得做**：同一段推理逻辑确实要同时服务实时与历史重算，且你已经有能力把模型版本与输出一起落列时。它的收益是"一份逻辑"，而这个收益只在两侧都要跑时才成立。
- **什么时候不值得做**：只有实时一条链路、或历史重算根本不需要模型输出的场景——此时把模型调用放进流批作业，买到的是一次不必要的版本绑定，代价是延迟与计费两笔新账。
- **一个容易被忽略的推论**：本方向的价值不在"跑得动"，而在**它把模型的不确定性关进了一个可以验收的边界里**——"版本进列"让历史可解释，"旁路"让失败不阻塞，"幂等键"让重试不重复付费；三件事缺任何一件，这条链路就无法给出"可对账"的结论。反过来说，只要这三件齐了，接不接 AI 就不再是架构问题，而是内容问题。

#### 5.2.2 流式 RAG 与向量索引：把 embedding 的物化时机从"按周期"改成"按事件"

- **旧做法与它的卡点**：索引由离线批任务周期性重建，卡点是**新鲜度与重建成本被绑死**——全量重建一次的成本与文档总量成正比，所以缩短重建间隔的成本是线性上升的（[§7.3.3](10-stream-batch-unified-section-7-sec7.md) 讨论"历史放在队列还是对象存储"时用的是同一种读法：成本随窗口线性增长）。它不是"做不到实时"，是"实时的价格由总量而不是由变化量决定"。
- **AI 改变了什么机制**：**把物化时机从"按周期"改成"按事件"**——只对发生变更的文档重算 embedding，并把结果增量写入索引。**机制上变的是成本函数（从总量驱动变成变化量驱动），不是"检索算法变好了"**；召回与排序那一段没有因为流处理而改变。
- **由此得到的**：**因为每次只为变更付费，所以"新鲜度"这个旋钮第一次与"全量重建成本"解耦**——这与本章 [§3.1](10-stream-batch-unified-section-3-sec3.md) 里"代价记在写侧还是读侧"是同一个问题的一次重演：把成本从周期性的大额支出，改成持续的、随变化量走的小额支出。收益是真实的，但它只在**变化量远小于总量**时成立。
- **由此付出的**：**其一，删除传播**——日志式链路里"删除"通常是一条 tombstone，而索引里的向量是否真的不可检索，取决于向量库的删除语义；两侧不对齐的结果是"下架内容仍被检索到"，这是本方向最容易被忽略的失效形态；**其二，模型版本混用**——不同批次用不同版本产出的向量在同一索引里不可比，一次静默的模型升级会让检索质量无声下降，而**没有任何一层会报警**；**其三，实时把错误也变快了**——新鲜度提高的同时，错误内容进入检索结果的速度也提高，[§3.5](10-stream-batch-unified-section-3-sec3.md) 的"忽视 Changelog"那类静默故障在检索链路上的表现正是"答得流畅、依据是错的"；**其四，每次变更产生一次调用费用**，单位成本模型从"每天一次批量"变成"每文档一次"，小文档多变更的场景下这笔账可能比全量重建更贵。

```text
        同一份索引，两种新鲜度来源（差别在"删除与版本"怎么处理）
          文档变更 ──► 事件流 ──► embedding（带 model_version）──► 向量库
          ────────────────────────────────────────────────
          ✗ 只写不删、不记版本
            下架文档仍被检索到；模型升级后新旧向量混在一个索引里
            → 检索质量下降，且没有任何一层会报警
          ✓ 写入即带 model_version，删除走同一条事件流
            检索按版本过滤；删除事件与写入事件保持同一顺序
          ────────────────────────────────────────────────
          判定方法：随机取 10 个已下架文档，看它们还能不能被检索到；
                    再数一次索引里存在几种 model_version
```

- **证据与来源**：【公开】CDC 采集、流处理算子、向量库的写入与按元数据过滤，各自都是其官方文档中的正式条目（核验入口见 §5.4）；判定方法：查向量库文档里"按元数据过滤"与"删除"是否正式条目，以及删除是软删还是立即不可检索。**【本节未能核到】"实时索引让检索质量或答案准确率提升多少"的第三方对照材料**——这类数字高度依赖评测集、切分策略与查询分布，公开材料通常不披露口径，因此本节不引用任何提升幅度。工具（Flink + 向量库 + 编排框架的组合）属于**厂商自有整合**，按 §5.1 判据的第②条只能算 L2 那一档。
- **成熟度**：**L2**。判据：①③成立（三段管道各自是正式条目），②核不到（公开材料是厂商自述的云服务组合）→ 可做 PoC，不要作为核心依赖。
- **流批 + 向量库为什么是 L3**：把向量类型与索引直接做进表格式，要跨两套规范对齐"向量的精度、距离度量、索引版本、删除语义"，这些在表格式侧没有统一语义；公开材料是集成示例与预告，不是正式规范条目。**判定方法**：查该表格式官方文档里"向量类型 / 向量索引"是不是正式条目、以及它是否声明了索引版本与距离度量；只有一篇集成示例的，说明这条还处在 L3，**不要为一个尚未成型的能力改你的表格式选型**。
- **什么时候值得做**：文档变更频率高、且变更量远小于总量（每次只改少量文档），或"看到新内容"本身是业务要求（工单知识、风控规则、商品信息）时。这两个条件同时成立，增量物化才比周期性重建更省。
- **什么时候不值得做**：总量小、变更量占比高（例如每天替换掉大半文档）时——此时"按事件"与"按周期全量重建"的总成本接近，而前者多出删除传播与版本一致性两件事要维护，是净增负担。
- **与 §3 的接口要说清**：这条链路的写入端不是一个新东西，它就是 [§3.2.5](10-stream-batch-unified-section-3-sec3.md) 的 CDC 入湖（或事件流直接消费）；改变的只是写下游的形态——从"写进表"变成"写进索引"。因此 §3.2.5 记下的那几条代价与上线前验证动作——初始快照对源库的读压力、源表 DDL 变更（加列、改类型）的下游同步、先在源库量出初始快照读压力与增量日志读取带宽两条曲线——在这里一条不少，只是问题的下游从查询换成了检索。

#### 5.2.3 流式 Agent 与流式 GraphRAG：把「不可复现」放进流水线

- **旧做法与它的卡点**：Agent 的调试与追责靠应用日志——一次失败会话结束后，无法重放"它当时到底看到了什么"。卡点不在吞吐，而在**可复现性的提供者换了**：传统链路里同一输入必得同一输出，所以复现只需要保存输入；LLM 的输出不是输入的确定性函数，此时要复现的不是"输入"，而是"当时实际的请求与响应（含工具返回）"。日志文件留不下这个，因为它不可按序回放、也不与下游写入对齐。
- **AI 改变了什么机制**：**事件流从"传输与解耦"变成"唯一可复现来源"**——把 thought / tool_call / 工具返回 / 动作结果持久化成可回放的事件，这一步的目的不是吞吐，是审计与调试。这是主文件 [§1.2](10-stream-batch-unified.md) 那几条"AI 时代新诉求"在存储侧唯一站得住的落点：**它改变的是这类数据的记录目的（为了可复现），而不是日志本身的语义（顺序、offset、可重放、保留）**。
- **由此得到的**：**因为可复现性被下沉到存储层，所以"这次为什么这么答"第一次可以逐条回放**，Agent 的行为也因此进入可审计范围。对只读的 trace 与回放而言，这条能力今天就能用——它用的完全是既有机制（持久化 + 按序重放 + 保留策略），不依赖任何新接口。
- **由此付出的**：**其一，落盘的内容可能含个人信息**——prompt 与工具返回里经常夹带用户数据，一旦进日志就进了保留期，而"删掉某个用户的记录"在只追加的结构里是最难回答的问题（这类问题属于 [11-cross-cutting/07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md) 的合规面，不是技术面，先定"记什么"比先选存储重要）；**其二，"可重放"不等于"可复现"**——重放同一个请求，外部模型仍可能给出不同答案，所以回放能证明"当时看到了什么"，不能证明"现在还会这么答"，这两个结论在事故复盘里不能互换；**其三，GraphRAG 那一支还多一层**：抽取结果的非确定性使图谱本身需要校验，实体消歧规则不经过一轮调参不会稳定，而一旦图谱被当成影响分析使用，**错误的影响面比没有影响面更贵**——[11-cross-cutting/05 §6](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-6-sec6.md) 的四个案例给出的影响分析来自字段级血缘 + 图遍历，不是来自 LLM 抽取。
- **证据与来源**：【公开】日志型存储的持久化、按 offset 重放、按时间或容量保留，是正式功能条目且接口多年未变（核验入口见 §5.4）；"事件溯源"作为一种模式的公开表述见 [03-data-stack/07 §3.2.6](../../03-data-stack/07-architecture-decisions/07-architecture-decisions-section-3-sec3.md)（Fowler《Event Sourcing》，2005）与 [03-data-stack/04 §3.2.8](../../03-data-stack/04-streaming-store/04-streaming-store-section-3-sec3.md)。**【本节未能核到】Agent 事件流进入生产并披露"回放成功率"或"重放一致性"的第三方材料**——公开材料多为框架与可观测类产品。
- **成熟度**：**L3**（作为"Agent 决策进流水线"这个方向）。判据：①不成立（"Agent 决策作为算子"没有稳定接口），③不成立（动作不可静态校验、不可回滚）→ 记录，不要在架构里预留假设。**若要用，只把事件流用在只读的 trace 与回放上**，那属于既有能力，不受本方向的级别限制；凡让 Agent 的动作直接改数据或改拓扑的想法，先按 §5.1 表第 8 行（"由模型改拓扑"那一类）归到 L3。
- **判定方法**：取一次已结束的失败会话，只用手上的事件记录回答三个问题——它当时调用了哪些工具、每次返回什么、在哪一步开始偏离。答不完整说明事件的粒度还不够细；**能答完整，才轮到讨论"能不能自动重试"**。
- **什么时候值得做**：Agent 已经进入面向用户的链路、需要回答"它为什么这么答"时。此时 trace 是唯一可用的答案来源，且它完全建立在既有存储能力之上。
- **什么时候不值得做**：把 trace 当成"顺便省下的日志"来建——没有保留期与脱敏规则的 trace，会在第一次数据主体请求时变成一笔要还的债；也不要为了 trace 而把逐 token 的事件全部落盘，粒度按"能否复现一次决策"来定，而不是按"能不能全记下来"。
- **一条与 §3 对齐的提醒**：本方向真正的难度不在存储，而在**记录粒度**——记太细（每次工具返回的全文）会把保留成本与敏感面一起放大，记太粗（只有一次请求的时间戳与状态码）就回答不了"它当时看到了什么"。可核验的做法是拿一次真实失败会话做回放演练，用"能否逐步解释偏离点"来定粒度，而不是先定 schema 再想用途。

#### 5.2.4 与 AI 无因果关系的五条：收益来自规范、既有能力或范式，没有一条来自模型

| 方向 | 旧做法与卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据 / 成熟度 |
| --- | --- | --- | --- | --- | --- |
| 统一流批 + 联邦 | 一段逻辑要在多云 / 多引擎上跑，只能按引擎各写一份；卡点是**运行时可替换性**而非性能 | **与 AI 无因果关系**：它换的是运行时的绑定方式（逻辑与执行分离），不是判断方式 | 一份代码可在多个后端跑出语义一致的结果；代价前置且已知 | 只能用各后端共同支持的语义子集，放弃引擎专属优化；跨后端语义差异要在 CI 里长期对账 | 可移植层与开放表格式 REST 接口都是公开规范条目 → **L2（非 AI）** |
| 自治流批里的确定性那一半 | 靠人盯并行度、状态大小、小文件数；卡点是**滞后与不可复现** | 把"人盯"换成**基于指标的确定性动作**（自适应并行度、自动扩缩、自动合并）；模型只贡献预测与建议 | 动作由统计信息驱动，出问题可解释、可在测试环境复现 | 自动动作产生的计算要事先约定记在谁的账上；"自愈"会降低故障可见性（根因没人修） | 引擎与平台的正式功能条目 + 配置接口稳定 → **L2（非 AI）** |
| 流式数据库与流优先存储 | 结果要么现算（反复扫同一批数据），要么按批刷新（不新鲜） | **与 AI 无因果关系**：它换的是"结果常驻并被增量维护"这一存储与计算形态 | "结果最新"的代价不再随查询次数增长，而随**被维护的状态量**增长 | 常驻状态不能像批作业那样随时中断重启，重建必须依赖上游回放；与湖表生态的集成度弱于主流引擎组合 | 增量物化视图是这些产品的正式条目 → **L2（非 AI）** |
| 流批一体成为默认 | 流批两套代码两套存储，口径要对账 | **与 AI 无因果关系**：它改的是表格式与引擎的统一语义（变更流的产出方式） | 一份代码一份存储，维护面收敛，对账从"人证明"变成"结构保证" | 表格式与引擎的版本耦合、存量迁移与对账成本；**"Lambda 已退出"这类断言本节不作为事实使用** | 表格式官方文档中的正式条目 → **L2（非 AI，既有能力）** |
| 边缘流处理 | 数据全部回中心处理，带宽与回传延迟是瓶颈 | **与 AI 无因果关系**（"边缘 AI 决策"是部署位置的变化，不是数据机制的变化） | （若成立）就近处理可减少回传量与端到端延迟 | 边缘节点上的模型分发、版本回滚与数据补齐没有通行做法；算力受限时表格式与合并策略都要重选 | 公开材料以试点与演示为主 → **L3** |

**这五行的共同读法**：收益都真实存在，但**没有一条的收益来自模型**——按表逐行看，一条来自接口标准（**统一流批 + 联邦**：可移植层与开放 Catalog），三条来自既有能力（**自治流批里的确定性那一半**：自适应调度与自动扩缩；**流式数据库与流优先存储**：增量物化视图；**流批一体成为默认**：表格式的流批读写），一条来自部署形态（**边缘流处理**）。把它们写成"AI 时代的流批演进"，会让真正要做的三件事（对齐变更流的产出方式、把两侧对账自动化、定清保留与重算窗口）一件都排不进排期——而这三件事恰好是 §3.3 决策表里最靠前的判据。

- **什么时候值得做**（针对本组第 1、3、4 行：统一流批 + 联邦、流式数据库、流批一体成为默认）：变更流的产出方式与写入形态已经对不上（表现为流读缺变更、批读越来越慢）时；跨云 / 跨引擎的运行时可替换性确实会被用到（不是"以后可能用"）时；已有若干条高频查询、希望它们不必每次现算时。三条的收益都立即可见，且不引入新的故障形态。
- **什么时候不值得做**：只有一条链路、一个引擎、一种消费者时——可移植层与联邦带来的语义子集限制是真成本，而你用不到它的收益；高通查询只有一两条且能被低频扫描替代时，增量物化视图的常驻状态是净开销。

### 5.3 与本主题既有栈的接口在哪

流批一体与 AI 之间不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比"AI 能做什么"更能决定它能不能落地。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 作业 ↔ 模型端点 | 交接物 = 请求 + 响应 + `model_version`；**幂等键必须带在请求上** | 模型服务方负责可用性，作业侧负责旁路与降级；**没有旁路时失败会直接阻塞主链路** | 幂等键是否被支持因服务而异（未定） |
| 作业 ↔ 同步点 / 检查点 | 交接物 = "模型调用是否参与两阶段提交"；它决定延迟下限与语义档位 | 作业作者：把"至少一次"的链路承诺成"精确一次"，是设计侧的错 | 多数停在"至少一次 + 幂等"（未定） |
| 作业 ↔ 表格式 | 交接物 = 输出列 + `model_version` 列；**版本不进列，历史就不可解释** | 建模者（[§3.2.7](10-stream-batch-unified-section-3-sec3.md) 的"版本与输出一起落表"） | 既有机制（列设计是人定的） |
| 作业 ↔ 向量索引 | 交接物 = 向量 + 主键 + `model_version`；删除要走同一条事件流 | 索引侧；删除未传播时，检索会给出**有出处但已下架**的依据 | 删除与版本过滤是否正式条目因产品而异 |
| 作业 ↔ 特征库（[02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md)） | 交接物 = 同一份变换逻辑 + 时点正确性；实时与离线必须同源 | 特征 Owner；两套实现的分叉在业务侧表现为"离线好、上线垮" | 既有机制（同源这件事是人保证的） |
| 作业 ↔ 指标与口径（[04-data-assetization/10](../../04-data-assetization/10-metric-platform/10-metric-platform.md)） | 交接物 = 指标定义；AI 算子使口径里多了一处外部依赖 | 定义 Owner：口径里含模型时，模型的版本变更等同于一次口径变更 | 既有机制（口径的唯一定义处） |
| 作业 ↔ 血缘（[11-cross-cutting/05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)） | 交接物 = 模型与版本作为一类上游实体；**只有覆盖到列级，影响面才算得准** | 血缘侧；漏采模型这一层，影响面会失真 | 既有机制（采集方式是自动解析还是人工登记决定它会不会过期） |
| 作业 ↔ 成本（[11-cross-cutting/03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)） | 交接物 = 单位成本从"CPU 时"变成"token 数 + 调用次数" | 平台与财务的接缝处；**没有归属约定时，重试产生的重复调用没人认领** | 归属约定未定 |
| 作业 ↔ 审计与合规（[11-cross-cutting/07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)） | 交接物 = prompt / 输出的保留期与脱敏规则；**只追加结构里的删除请求是最难回答的一类** | 记录方；"先记下来再说"会把合规问题推迟到数据主体提出请求那天 | 规则未定（无通行做法） |
| 作业 ↔ 调度与编排（[03-data-stack/12](../../03-data-stack/12-scheduler/12-scheduler-section-3-sec3.md)） | 交接物 = 依赖判定所在层次；**推理算子的成功不等于数据就绪** | 调度侧；上游"跑成功"只保证作业退出码为 0 | 既有机制 / 接缝处未定 |
| 作业 ↔ 可观测（[11-cross-cutting/04](../../11-cross-cutting/04-observability/04-observability.md)） | 交接物 = 外部调用的延迟与失败率，以及旁路积压量 | 平台侧；只监控作业吞吐不监控外部调用，链路会先以"延迟莫名变长"的形式退化 | 既有机制（常被漏掉一半） |

一句话概括：**AI 没有给流批一体新增任何算子类型，只给 Logic 增加了一处外部依赖**——模型端点与向量索引。由此得到三条约定。

**第一条约定：凡"不可复现的调用"，结果必须物化成数据。** 判断标准很具体：把流侧写下的输出当成批侧的输入来读，两侧能否逐行对上。对不上，说明还有一次外部调用发生在重算路径上。

**第二条约定：模型版本是口径的一部分。** 口径变更要走评审，模型版本变更也一样——把它写进表列、写进血缘、写进口径定义，三者缺一，历史结果就解释不了。

**第三条约定：外部依赖必须在链路上有出口。** 推理失败走旁路而不是阻塞主链路（[§3.2.7](10-stream-batch-unified-section-3-sec3.md) 的结构），并且要能回答"旁路积压了多少、有没有人处理"——没有旁路的 AI 算子，等于把模型的可用性变成了整条链路的可用性。

### 5.4 公开进展与文献

分三类列，只列能给出标题 / 出处 + 年份的条目；**宁少勿假**。第二类是**判定入口**——给的是"去哪个页面核"，版本与年份随发布更新。

**论文（可核验）**

- Akidau et al., "The Dataflow Model: A Practical Approach to Balancing Correctness, Latency, and Cost in Massive-Scale, Unbounded, Out-of-Order Data Processing", VLDB 2015——把无界数据、事件时间与水位线写成一套模型，是"同一份逻辑既能处理历史也能处理实时"的理论起点。
- Carbone et al., "Apache Flink: Stream and Batch Processing in a Single Engine", IEEE Data Engineering Bulletin 2015——**同一个引擎、两种执行模式**这一提法的公开出处，也是本章 [§7.3.1](10-stream-batch-unified-section-7-sec7.md) "流批两种模式的结果是否必须一致"这条判据的来源。
- Armbrust et al., "Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics", CIDR 2021——表格式承担"一份存储两种读法"的范式出处（与本仓库 [03-data-stack/07 §5](../../03-data-stack/07-architecture-decisions/07-architecture-decisions-section-5-ai.md) 引的是同一篇）。
- Murray et al., "Naiad: A Timely Dataflow System", SOSP 2013；McSherry et al., "Differential Dataflow", CIDR 2013——增量维护"结果最新"的机制源头，对应本章 [§3.2.6](10-stream-batch-unified-section-3-sec3.md) 的流式数据库一族。
- Kreps, "Questioning the Lambda Architecture"（O'Reilly Radar, 2014）——Kappa 的原点：以可重放日志替代批层，本章 [§7.2](10-stream-batch-unified-section-7-sec7.md) 的候选全景以它为一族。
- Zaharia et al., "Discretized Streams: Fault-Tolerant Streaming Computation at Scale", SOSP 2013——微批模型的公开出处，对应本章 [§3.2.3](10-stream-batch-unified-section-3-sec3.md) "流 = 连续的有界微批"这条设计；也是"延迟下限等于批间隔"这一代价的来源。
- **三条"学术进展"本节无法核验**：「Apache Paimon 论文（VLDB 2024）」「Apache Beam 论文（2024）」「Materialize 论文（SIGMOD 2024）」——它们给的是主题名而非可检索的标题与作者。**处理办法**：保留它们所指的方向（流批融合表格式、跨引擎可移植、增量物化视图），但不把它们当证据；判定方法是按"项目名 + 论文"在会议论文库里检索标题与作者，核不到就改用该项目的官方文档作为依据。

**官方 release note / 文档（判定入口）**——这一类列的是**核验去处**，本节不据此声称任何产品已具备某能力。

- Apache Flink 的官方文档与 release note——核验"流批两种执行模式"与"模型推理表函数"的具体条目：**要看函数是否被标为正式功能、是否声明了版本门槛与幂等/重试语义**，而不是看博客里的函数名。
- Apache Paimon / Iceberg / Hudi 的官方文档与规范仓库——核验"变更流产出方式"（Paimon 的 `changelog-producer` 一组选项）、"行级更新"、"增量读取"是正式条目还是预览；**这是 §5.1 表第 11 行判据①的核验入口**。
- Apache Spark 与 Delta Lake 的发布说明——核验"流式接口 + 批语义"的触发方式（`AvailableNow` 一类）与删除向量这类结构是哪个版本引入、默认是否开启。
- Apache Beam 的可移植性文档——核验"跨 runner 的语义子集"边界：**看文档里有没有把各 runner 的差异单独成节**，有则说明语义损失是被显式承认的。
- 各向量库 / 向量索引的官方文档——核验"按元数据过滤""删除语义""索引版本"三项是否正式条目；**判定方法见 §5.2.2 代码块末尾的两条动作**。
- Materialize / Decodable / Apache Fluss 等流式数据库与流优先存储项目的官方文档与发布记录——核验增量物化视图、状态占用、对象存储原生的实际形态；**同时核一次项目归属与许可**（这类项目近两年发生过更名、收购与许可调整，写进长期路线图之前看官方公告与仓库 LICENSE）。
- **Apache Fluss 的归属待核**——「Flink Table Store 更名后成为 Paimon」这一点可核；至于 Fluss 由它「衍生」的说法，本节没有一手材料可确认或否证，因此既不照抄、也不作反向断言，只给判定方法：分别查两个项目的官方仓库、发布记录与孵化状态，归属问题只看这些一手材料。

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含指标与口径的第三方"AI 改变流批一体"生产案例。公开材料里能核到的是流批统一的运行做法自述（本书 [§6](10-stream-batch-unified-section-6-sec6.md) 的四个案例：阿里的"指标定义唯一真源"、Netflix 的 Keystone"把流与批统一在同一套平台层"、字节的"先在一个业务上跑通再横向复制"、LinkedIn 的"把变更捕获做成入湖入口"；§6 的"真实落地路径"一节另给出 0→1 / 1→10 / 10→100 / 100→1000 的分阶段路径），以及厂商对推理表函数与向量能力的正式发布条目；**缺的是"因此在延迟 / 对账差异 / 单位成本上从多少变到多少"这类带基线的第三方材料**。**这个空白本身是结论**——它正是本节把整张表压在 L2 / L3 的直接原因：第②条核不到，就不许靠改写判据把它补上。
- 对要做技术评审的人：**自测记录不构成第②条证据**（它既非第三方生产案例、也未公开），但足以支撑本组织内的决策——把你们自己的"推理 P99""模型输出可对账率（流侧与批侧重算逐行一致的占比）""向量版本数"算出来并留存口径，下次评审时它就是本组织内可复用的基线材料；对外仍只算自有案例，不能用来填平第②条。
- 这三类里**最容易造假的是第三类**：厂商案例通常省略口径（怎么算的、样本多大、基线是什么），开源项目案例通常省略规模（多少表、多少条链路、多少人维护）。判定方法：只接受同时给出"口径 + 规模"的案例；缺一项就只当方向记录，不当证据。

**怎么用这份清单**：要核"能力存不存在"看官方文档与 release note（最快）；要核"机制成不成立"看论文（最慢但最稳）；要核"在我这里值不值得做"看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。

**核验 §5.1 表里六条宣称的最小动作**（对应表第 1、2、3、4、6、7 行，都不需要采购）：

1. **模型调用算子化**：把已有推理算子的链路按 §5.2.1 的判定方法验一遍（停端点十分钟 + 两侧逐行比对），两个结果都拿到才算"可对账"。
2. **流式 RAG**：抽 10 个已下架文档看能否被检索到；再数一次索引里存在几种 `model_version`。
3. **流批 + 向量库**：查表格式官方文档里有没有向量类型与索引的正式条目——只有集成示例的，按 L3 处理。
4. **流式 Agent**：拿一次失败会话，只用手上的事件记录回答"它看到了什么、在哪一步偏离"。
5. **统一流批 + 联邦**：列出你实际用到的引擎专属能力，逐个确认可移植层是否覆盖；覆盖不到的链路，明确不做可移植。
6. **自治流批**：把最近一个月的自动动作（扩缩、合并、重分区）拉出来，看触发次数与资源占用，并对比关掉它的窗口。

### 5.5 被过度宣传的部分

**「流批一体 + AI：一份代码同时跑 ETL 和 AI」**——实际是：把模型调用放进 Logic 之后，Logic 就不再是确定性函数，**"一份代码 = 一份结果"这条等号随之失效**；要做到两侧结果一致，必须把模型输出当成**输入数据**物化（版本 + 输出一起落列），而不是靠"同一份代码"这个事实本身。原因：等号的成立条件是"给定输入必得同一输出"，而外部模型不保证这一点——它是有状态、会变更的服务。**它什么时候才会成真**：引擎能把外部模型调用纳入同步点语义（参与式提交或幂等重试）并且模型版本可固定。**判定方法**：查引擎文档里有没有这两条书面说明；没有，就先把结论写成"至少一次档"。

**「流式 RAG 让知识库实时更新，因此答案更准」**——实际是：变的只是**索引的物化时机**（新鲜度与全量重建成本解耦），答案质量的判据是切分策略、召回与重排，与"实时"无关；而实时把**错误内容的可达性也提高了**。原因：本方向改变的是成本函数，不是检索质量函数——把这两个函数混为一谈，会让人以为加了流处理就解决了召回问题。**它什么时候才会成真**：索引里每条向量带 `model_version` 且检索按其过滤、删除走同一条事件流、并且有一次公开的评测口径。**判定方法**：抽 10 个已下架文档看还能不能被检索到；数一次索引里有几种 `model_version`。这两个数不为零/大于一，说明缺口在治理侧。

**「流式 GraphRAG 让流处理具备关系推理能力」**——实际是：关系推理与影响分析的能力来自**图遍历与字段级血缘**（[11-cross-cutting/05 §6](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-6-sec6.md) 的四个案例都是这一条），流只提供"什么时候更新"；LLM 抽取带来的非确定性，使图谱本身成了需要校验的对象。原因：抽取质量不进评测集、消歧规则不固定，图谱的正确性就无法被回答，而**影响面答错比答不出更贵**——它会让人凭一份看起来权威的清单去改表。**它什么时候才会成真**：抽取结果有可披露的评测集与消歧规则，且图谱能被指出"哪条边是抽取的、哪条边是血缘解析的"。**判定方法**：随机取三条边，问它是从 SQL 解析出来的还是从文本抽取出来的；答不出来，就不要把它接进变更门禁。

这三条的共性：**它们都把"算得更快、写得更少、问得更顺"这类动作成本下降，当成了"数字更对"**。而本主题的质量判据只有三条——变更流能不能被读出来、两侧结果能不能对上、代价记在写侧还是读侧；这三条一条也没有因为 AI 而改变。补一句读法上的提醒：这三条被过度宣传，**并不是因为它们没有价值**（§5.2.1 与 §5.2.2 的收益是真实的），而是因为它们的收益被说成了另一种东西——把"接入成本下降"说成"结果质量上升"，会让评审会上该问的三个问题（对账口径是什么、评测集是什么、影响面答错谁负责）一个也问不出来。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 模型调用进流批作业会先在"旁路 + 版本落表"的形态下落地，而不是作为主链路的同步算子，并被拆成"引擎侧推理算子"与"治理侧版本与血缘"两件事分别采购 | 引擎与表格式的正式条目集中在"推理表函数 + 幂等/重试语义 + 与表格式的版本列"这类接口上，实践材料普遍带旁路与降级描述；采购与评审材料里出现"模型版本是否进血缘""推理是否参与同步点"这类验收项 | 出现第三方公开材料，描述把模型调用作为**参与两阶段提交**的同步算子并长期运行的形态；或该说法继续作为一个打包概念存在，且没有可复核的验收口径 |
| 表格式内的向量支持会先停在"类型 + 距离度量"这一层，索引与删除语义统一得更晚 | 表格式规范里出现向量类型与距离度量的正式条目，但索引构建仍由外部组件承担 | 出现跨多个独立引擎一致实现的"表格式内置向量索引 + 统一删除语义"规范条目 |
| 流批一体的下一次实质变化来自"变更流的产出方式"与"保留 / 重算窗口"，与 AI 无关 | 表格式与引擎的发布条目集中在 changelog 产出方式、快照保留、小文件与合并调度上 | 架构讨论的焦点转向"由模型决定流批边界与拓扑"，且出现可核验的生产成效 |
| Agent 事件流会成为一类**默认被记录**的数据，随之而来的是保留期与删除请求的冲突公开化 | 存储与可观测产品把"Agent trace 的保留期与脱敏"做成正式配置项；合规材料开始讨论只追加日志里的删除请求 | 出现"Agent trace 长期全量保留"且不讨论删除与脱敏的公开生产做法 |

写这四条时的共同约定：**信号必须是外部可观察的**（规范条目、发布说明、第三方公开案例），而不是"我觉得会"。**被检验得最快的是第二条**——表格式规范的下一次版本发布里有没有向量索引条目，一两年内就能看到；**最慢的是第四条**——它要求组织先公开承认这个冲突，而冲突的暴露通常来自一次数据主体请求。

还有一条共同的读法：**这四条里没有一条的证伪信号是"模型变强了"**——它们全部落在接口、规范与合规上，这正是本主题的特征：它的卡点大多不在模型那一层。

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 想把模型调用放进流批作业 | 先做旁路 + `model_version` 落列 + 幂等键三件；再测推理 P99 | 观察推理 P99 与检查点间隔的相互约束、旁路积压有没有人处理 | 不要在模型调用参与不了同步点语义时承诺端到端精确一次 |
| 两条链路数字对不上 | 先用流、批两种模式跑同一个含迟到数据与窗口闭合的指标，数差异条数与原因 | 观察对账差异是否在归零，而不是总分 | 不要在链路本来就对不上时先接 AI——那只是把错误变得更贵 |
| 要做流式 RAG / 实时索引 | 先把删除传播与 `model_version` 过滤做出来 | 观察已下架文档的召回情况、索引里的版本数 | 不要在评测集与口径定下来之前拿"实时"当质量提升的证据 |
| 想让 Agent 决策进流水线 | 只先做只读的 trace 与回放 | 观察回放能否解释一次失败会话的全过程 | 不要让 Agent 的动作直接改数据或改拓扑；"可回放"不等于"可复现" |
| 表格式选型被问到"要不要支持向量" | 把向量交给独立索引组件，表里只存引用 | 观察表格式规范里向量索引条目是否出现、是否跨引擎一致 | 不要为一个尚未成型的规范能力改表格式选型 |
| 运维靠人盯并行度与小文件 | 打开引擎侧确定性的自适应与自动合并，并设配置边界 | 观察自动动作产生的计算量记在谁账上 | 不要让不可回滚的动作（改拓扑、改分桶）进自动通道 |
| 要跨云 / 跨引擎跑同一段逻辑 | 先列清用到的引擎专属能力，再决定哪条链路不做可移植 | 观察跨 runner 的语义差异是否被 CI 覆盖 | 不要把可移植性包装成 AI 演进；不要为它牺牲关键链路的提交语义 |
| 老板要求"AI 原生流批架构" | 把目标拆成"旁路 + 版本落列 + 对账自动化"三段，分别给验收口径 | 观察三段的负责人是否明确 | 不要签"由模型决定流批边界"式的目标——它没有可验收的失败定义 |
| 保留策略从没被写下来过 | 把"最长重算窗口"写成天数，再从它反推快照与队列的保留期（[§3.7](10-stream-batch-unified-section-3-sec3.md) 自检清单的一条） | 观察一次真实重算请求能不能在承诺窗口内完成 | 不要在"可重算窗口"还没成文时讨论 AI 取数——模型要有历史可读，而你先把历史丢掉了 |
| 想用 AI 做失败归因 | 先按失败原因把现有作业分好类，并数出各类占比 | 观察归因建议被采纳的比例与采纳后是否真的止住复发 | 不要在失败原因还没被分类时先上模型——归因的输入是分类，不是日志全文 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改列结构、动提交语义、翻存量、扩大自动化半径），**而收益依赖一个尚未成立的假设**（模型输出可对账 / 生成物可校验 / 向量语义可统一）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**确定性**——它把 Logic 从"给定输入必得同一输出"变成了对外部有状态服务的一次调用，于是 [§3.1](10-stream-batch-unified-section-3-sec3.md) 那条"流批差异在变更流能不能被读出来"的约束之外，多了一条同样前置的约束：**"同一份代码"不再自动等价于"同一份结果"**。它**没有**改变的是代价的记账位置——代价依旧只在写侧与读侧之间搬（[§3.2](10-stream-batch-unified-section-3-sec3.md) 的七个模式没有一个在消除代价），AI 也没有让任何一侧免费变好。
>
> 判断本主题下任何新提法的快捷方式：**它动的是"变更流能不能被读出来"，还是"外部的哪一步不可复现"？** 前者是本章 §3 的老问题（由写入形态决定，不由模型决定）；后者才是 AI 带来的新问题，答案只有一句话——**把不可复现的那一步限制在"只发生一次"，并把它的输出连同版本一起物化成数据**。
>
> 如果只能带走一句话：**先把两侧的对账做成自动的，再让 AI 进这条链路**；顺序反过来，就是在一套本来就对不上的链路里再插一个不可复现的环节。
>
> 💡 **思考锚点**：把你的「最长重算窗口」写成天数——你现在的快照与队列保留期是从它反推出来的，还是另拍的？如果一次真实重算请求的窗口比你的保留期还长，本节说模型接进来之前历史就已经对不上；这两个数你今天对得上吗？
