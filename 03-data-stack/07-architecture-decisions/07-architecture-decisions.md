## 1. 概念与定位

### 1.1 是什么

**学术定义**：

- **Lambda 架构**（Nathan Marz, 2011）：将数据处理分为**批处理层（Batch Layer）+ 速度层（Speed Layer）+ 服务层（Serving Layer）**。批层保证全量准确性，速度层保证实时性，两层合并输出。
- **Kappa 架构**（Jay Kreps, 2014）：简化 Lambda，**只保留流处理层**，用 Kafka 等可重放存储替代批层。
- **Lakehouse 架构**（Databricks, 2020）：融合数据湖 + 数据仓库，让一份数据同时支持 BI + AI。
- **流批一体（Stream-Batch Unified）**：Flink / Spark 等计算引擎统一流批，一份代码、一份存储。

**工程定义**：在数据架构师手里，架构决策是**根据业务需求（实时性 / 一致性 / 成本 / 复杂度）选择合适的架构范式**。核心特征：

- **业务驱动**：从业务需求出发，不是技术驱动。
- **权衡取舍**：每个架构都有优缺点，没有"银弹"。
- **可演进**：架构随业务演进（Lambda → Kappa → Lakehouse）。
- **可治理**：所有架构都需要治理、可观测、可演进。

### 1.2 为什么需要

**业务驱动力**：

- **业务多样性**：不同业务对实时性 / 一致性 / 成本要求不同。
- **技术演进**：Lambda → Kappa → Lakehouse，技术在演进。
- **避免决策失误**：选错架构导致返工（成本百万级）。
- **决策可解释**：架构决策需要可解释、可追溯（ADR）。
- **AI 时代演进**：传统架构无法满足 AI 需求。

**痛点（没有架构决策框架的代价）**：

1. **选错架构**：实时业务用了 Lambda，成本翻倍；全量业务用了 Kappa，延迟高。
2. **架构僵化**：业务变了架构不变，效率下降。
3. **决策无据**：架构师凭经验决策，无法解释。
4. **重复建设**：每条业务线独立选型，浪费资源。
5. **缺乏 ADR**：架构决策没有文档记录。

**AI 时代的新诉求**：

- **AI 原生架构**：AI 应用需要 Lakehouse + 向量库 + LLM——注意这是**产品组合说法**、不是可判定的架构范式，取数链路真正缺的是机器可读的语义层与权限下推（见 [§5](07-architecture-decisions-section-5-ai.md)）。
- **Agent 友好**：架构需支持 Agent 调用（统一 API）。
- **自治决策**：AI 辅助架构决策。

### 1.3 在 AI 时代数据架构中的位置

```
业务需求
  ↓
架构决策（Lambda / Kappa / Lakehouse / 流批一体）
  ↓
技术选型（存储 + 计算 + 查询）
  ↓
落地实施
```

**架构决策是数据栈的"灵魂"**：决定了整个技术栈的方向。

### 1.4 演进历程

**第一阶段：Hadoop 单层（2006-2012）**

- Hadoop + Hive + MR 单一架构。
- T+1 批量处理。

**第二阶段：Lambda 架构（2011-2018）**

- 2011：Nathan Marz 提出 Lambda。
- 2013-2016：Storm + Hadoop Lambda 落地。
- 2017-2018：Flink + Spark Streaming 替代 Storm。

**第三阶段：Kappa 架构（2014-2020）**

- 2014：Jay Kreps 提出 Kappa。
- 2015-2018：Kafka + Flink Kappa 实践。
- 2019-2020：Kafka + Flink + Iceberg 流批一体萌芽。

**第四阶段：Lakehouse 主流（2020-2024）**

- 2020：Databricks Lakehouse 概念。
- 2021-2022：Iceberg / Hudi / Delta 三足鼎立。
- 2023-2024：Lakehouse 成为事实标准。

**第五阶段：AI 时代的方向提法（2024-至今，不是架构范式）**

- 2024：「AI 原生架构 = Lakehouse + 向量库 + LLM」的**产品组合提法**开始流行——它不是可判定的架构范式，取数链路真正缺的是机器可读的语义层与权限下推（见 [§5](07-architecture-decisions-section-5-ai.md)）。
- 2024-2025：AI 辅助选型（LLM 读需求 → 推荐范式）停留在演示与小范围试用（判为 L3）。
- 2025：自治架构（Self-Driving Architecture）——成立的一半是确定性优化，由模型决策的那半尚未成立（见 [§5](07-architecture-decisions-section-5-ai.md)）。

**一句话总结**：**架构范式从"Hadoop 单层"→"Lambda 双层"→"Kappa 单层"→"Lakehouse 融合"演进，今天 Lakehouse 是主流；第五阶段（「AI 原生」「自治架构」）是方向提法、不是可判定的范式。**

## 2. 核心原理

### 2.1 关键概念定义

**Lambda 架构**：

- **批处理层（Batch Layer）**：全量数据、历史计算，Hadoop/Spark。
- **速度层（Speed Layer）**：增量数据、实时计算，Storm/Flink。
- **服务层（Serving Layer）**：合并两层输出，Druid/HBase。
- **优缺点**：准确（批）+ 实时（流），但**双链路维护复杂**。

**Kappa 架构**：

- **单一流处理层**：所有数据走流，Kafka + Flink。
- **可重放存储**：Kafka 长期保留，可重新消费。
- **优缺点**：架构简单，但**历史计算能力弱**。

**Lakehouse 架构**：

- **统一存储**：对象存储 + 开放表格式（Iceberg/Hudi/Delta/Paimon）。
- **多种计算**：Spark/Flink/Trino/StarRocks 共享一份数据。
- **优缺点**：灵活 + 性能 + 治理好，但**架构复杂度高**。

**流批一体（Stream-Batch Unified）**：

- **统一引擎**：Flink / Spark 同一份代码同时跑流 + 批。
- **统一存储**：Iceberg / Hudi / Paimon 同时支持流批读写。
- **优缺点**：架构最简，但**对引擎 / 存储有特定要求**。

**Medallion 架构（Bronze / Silver / Gold）**：

- **Bronze（原始）**：原始数据，几乎不处理。
- **Silver（清洗）**：清洗、整合、统一口径。
- **Gold（精化）**：面向应用的精化数据。

**Event Sourcing（事件溯源）**：

- 所有状态用事件流记录，不直接存储状态。
- 通过回放事件重建状态。

**CQRS（Command Query Responsibility Segregation）**：

- 读写分离，写走流，读走专门查询层。
- 与 Kappa / Lakehouse 结合紧密。

### 2.2 数学 / 形式化基础

**Lambda 架构的一致性模型**：

- 批层：最终一致性（T+1 全量准确）。
- 速度层：实时（近似准确）。
- 合并：服务层做合并（基于时间窗口）。

**Kappa 架构的一致性模型**：

- 流层：端到端 Exactly-Once。
- 重放历史：从指定 offset 重新消费。
- 状态重建：从 checkpoint + offset 重启。

**Lakehouse 的一致性模型**：

- 表格式 ACID：Snapshot Isolation。
- 跨引擎：MVCC（多版本并发控制）。

**CAP 定理的工程权衡**：

前提：网络分区（P）必然发生，是分布式系统的前提而非可选项；分区发生时只能在 C（一致性）与 A（可用性）之间二选一（不是「三选二」）。据此对照：

- Lambda：批层 T+1 全量准确、速度层实时近似，服务层按窗口合并——以放宽 C（一致性）换实时可用。
- Kappa：流层端到端 EOS，重放历史 + checkpoint 状态重建——单链路，代价是历史计算能力弱、强依赖流引擎。
- Lakehouse：表格式 ACID（单表事务给 C）+ 跨引擎 MVCC（跨引擎最终一致）——并非「三者兼顾」。

### 2.3 关键算法 / 方法

**1. Lambda 批流合并**：

```python
# 服务层合并批 + 流
def get_view(query):
    batch_result = batch_view.query(query)  # 批层（全量准确）
    stream_result = speed_view.query(query)  # 速度层（实时增量）
    return merge(batch_result, stream_result, window=batch_window)
```

**2. Kappa 状态重建**：

```java
// Flink 从指定时间点重新消费（回溯）
StreamExecutionEnvironment env = ...;
KafkaSource<String> kafkaSource = KafkaSource.<String>builder()
    .setStartingOffsets(OffsetsInitializer.timestamp(
        Instant.parse("2025-01-01T00:00:00Z").toEpochMilli()))  // 指定起始时间点
    .build();
env.fromSource(kafkaSource, ...).process(...).sinkTo(...);
```

**3. Lakehouse 跨引擎查询**：

```sql
-- Iceberg 表可被多个引擎查询
-- Spark
SELECT * FROM iceberg.orders;

-- Trino
SELECT * FROM iceberg.iceberg.orders;

-- StarRocks
SELECT * FROM orders_iceberg;
```

**4. 流批一体（Paimon + Flink）**：

```java
// 同一份代码同时跑流批
TableEnvironment tEnv = ...;

// 批模式
Table batchResult = tEnv.from("paimon.orders")
    .filter($("dt").between("2025-01-01", "2025-01-31"))
    .select($("region"), $("amount").sum());

// 流模式
tEnv.executeSql("""
    INSERT INTO paimon_orders
    SELECT * FROM kafka_orders
""");
```

**5. 架构决策记录（ADR）**：

```markdown
# ADR-001: 选择 Lakehouse 而非 Lambda

## 状态
- Accepted

## 背景
- 业务：实时数仓 + 历史分析 + AI 训练

## 决策
- 采用 Lakehouse 架构（Iceberg + Spark/Flink + StarRocks）

## 后果
- 优点：一份数据多引擎、ACID、性能好
- 缺点：架构复杂度高、需要专业团队

## 备选方案
- Lambda：双链路维护成本高
- Kappa：历史计算能力弱
```

### 2.4 与相邻概念的关系

**Lambda vs Kappa**：

- Lambda：批 + 流并行，双链路。
- Kappa：只流，不行就重放。
- **Kappa 简化了 Lambda，但增加了对流引擎的依赖**。

**Lakehouse vs Lambda/Kappa**：

- Lakehouse = 融合方案：存储层支持流批 + 计算层支持流批。
- Lambda/Kappa = 计算范式：Lambda 强调双链路、Kappa 强调单一链路。

**Lakehouse vs 数据仓库**：

- 数据仓库：结构化、强治理、高成本。
- Lakehouse：开放、灵活、低成本。

### 2.5 全栈组合与失效顺序

**本节补的是本章最贵的一处缺口：单点都定了，方案仍然串不起来。**

本章 16 个主题各有一棵决策树（都写在各自的 §7.5），每棵树的判据单独看都成立，但它们的输出互为输入，且这个方向不是双向的。最典型的处境是报一条「12 Cell × 3 Region × 同城双活 × 双轨峰值」的年度预算：四个乘数分属三个主题（12 Cell 与 3 Region 的形态见 [Ch12 §01 单元化](../../12-architecture/01-cell-based-architecture/01-cell-based-architecture.md)，同城双活与异地多活的分档见 [Ch12 §02 多 Region](../../12-architecture/02-multi-region/02-multi-region.md)，双轨容量的计价口径见 [Ch12 §04 容量规划](../../12-architecture/04-capacity-planning/04-capacity-planning.md)），而「Region 层冗余与 Cell 层冗余是不是同一笔开支」这两篇都没写——它落在 2.5.3。反过来也一样：被问一句「表格式定了没有」，答完才发现这个答案会依次约束特征在线存储的存活期、样本回填的特征历史保留期、以及调度该按任务成功还是按数据就绪。

#### 2.5.1 顺序表：16 棵树，先定什么、后被什么约束

表的顺序不是主题编号的顺序，而是**依赖顺序**：把某一行的答案改掉，跟着改的行都在它下游。五段的划分与理由如下——**一 · 口径与归属**（决定后面所有层各自的「分母」）；**二 · 契约与底座**（决定数据怎么存、怎么演进、怎么变老）；**三 · 时效与运行时**（决定数据多久可见、状态放哪、失败要重跑多少）；**四 · 服务与消费**（决定谁读得到、读得多快）；**五 · 资产与节奏**（决定这条链由谁按什么节奏跑、样本从哪来）。

| 四 | 14 | 真实基数在何时可知（编译期、stage 边界、还是执行之后） | [14 查询优化器 §7.5](../14-optimizer/14-optimizer-section-7-sec7.md) | 统计信息不刷新时，代价模型的所有输入退化为常量，此时换任何搜索框架都不改变结果 |
| 五 | 15 | 依赖判定的依据是「任务成功」「数据就绪」还是「产出时刻承诺」 | [12 调度系统 §7.5](../12-scheduler/12-scheduler-section-7-sec7.md) | 用任务成功代替数据就绪时，上游迟到而下游照常开跑、读到半成品却不报错——调度特有的静默故障 |
| 五 | 16 | 回填归谁且能不能按时点、切分防不防三种泄漏、口径的载体是任务配置还是人的记忆 | [16 样本库 §7.5](../16-sample-library/16-sample-library-section-7-sec7.md) | 回填用「当前最新值」时，特征穿越会让离线指标更好看，于是错误不会被怀疑，只会被继续放大 |

**这张表有三条读法。**

其一，**每一行只问一个问题，答完才轮到下一行**。单棵树内部本来就是这么用的（每棵树都把自己的第一节点当硬约束），本表只是把这套做法搬到跨主题的层面。判断依赖方向的方法很直接：把某一行的答案改掉，看有多少行的答案跟着改——跟着改的都在它下游。

其二，**下游不能回头否定上游**。最常见的错法是在第五段讨论「为了出数准时，要不要把依赖改成任务成功」——而这其实是第三段的问题：数据的可见性与就绪信号由表格式与提交边界决定（表中第 8、9 行），上游没定时，用调度层去补一个上游缺口，补出来的东西不报错，只会在上游迟到时照常开跑（第 15 行的失效条件）。

其三，**「定错了会怎样」一列写的几乎全是静默失效**。全表 16 行里，第 7 行（分层与留史解耦）是**最**不可逆的一处——历史被物理删除、连备份也回不来；另有两行的失效属**不可逆或部分不可逆**：第 16 行的回填保留期不够会让整批老样本作废、元数据字段漏记会让「谁标的 / 当时口径版本」永久补不回来（[16 §7.5 第 2 问、§7.7](../16-sample-library/16-sample-library-section-7-sec7.md)），第 15 行所引的 12 §7.5 树里托管支是单向门、迁移不可逆（[12 §7.4 / §7.7](../12-scheduler/12-scheduler-section-7-sec7.md)）。其余各行的失效都不报警：数字慢慢不可比、账单慢慢变形、或者一个本来能拆开的问题被当成引擎问题治了一遍。这正是必须按依赖顺序读的原因——**静默失效不会给你一个回来重排顺序的信号**。

#### 2.5.2 四个跨主题接口（散点在本章各处，此前没有一处把它们并排放过）

**接口一 · 保留期：同一个参数，被两个方向各引用两次。**

- [09 实时计算 §7.6 组合四](../09-realtime-compute/09-realtime-compute-section-7-sec7.md) 写明：特征库的**在线存储存活期必须长于特征的流转延迟**，否则出现「在线读到旧值、离线回填新值」的不一致；同文件 §7.5 把这一支的判据落成「量两个数——特征的新鲜度要求与状态的存活期，两者必须匹配」。
- [16 样本库 §7.5 第 2 问](../16-sample-library/16-sample-library-section-7-sec7.md) 把同一个参数用在下游：**样本跨度一旦超过特征历史保留期，老样本永远回填不出当时的值**，所以「先与上游谈保留期」必须排在写模型之前；§7.4 把它记成一笔「随跨度增长的存储成本」。
- 反方向的三处：[04 流式存储 §7.5](../04-streaming-store/04-streaming-store-section-7-sec7.md) 的节点 N3 把阈值落在「保留期驱动的容量增长是否已构成持续运维负担」，[10 流批一体 §7.5](../10-stream-batch-unified/10-stream-batch-unified-section-7-sec7.md) 给出「重放窗口 ≤ 约 74 天」这个成本函数转向点（【推算】，推导链见该文件 §7.5），[07 §7.5](07-architecture-decisions-section-7-sec7.md) 的 Q3 要求重放窗口**短**于你能承受的恢复时间。

**接口在于：这四处是同一个参数名（保留期）在不同上游存储上的取值，而要求的符号相反。** 09 与 16 要它长（长于流转延迟、长于样本跨度），04 / 07 / 10 三棵树要它短（短于扩容窗口、短于恢复 SLA、短于成本转向点）。此前没有任何一处把这两个方向写在同一行上。**判定方法**：把四个方向的上下限并列写出来取交集，但先别把它们当成一份存储——09 说的是特征库的**在线存储存活期**、16 说的是**特征历史保留期**（其长度由上游特征平台 / 数仓决定），04 / 07 / 10 说的是**可重放窗口**，前两者与后三者分属特征库与消息 / 历史存储两个介质族。族内取交集为空，说明你要的不是一个 TTL，而是**两份存储**——一份长保留的重放源，加一份短保留的在线层，而不是把两个相反的要求塞进同一个参数里调。顺带一句：16 的第 2 问必须在写模型之前问，因为它不是调参问题——保留期不够时，任何工具都回填不出当时的值。

**接口二 · 每层权威只一处。** [07 §7.6](07-architecture-decisions-section-7-sec7.md) 已把它写成纪律：「权威层可以只有一处，且必须写进 ADR」，并给出四条组合各自的权威所在（迁移完成后的湖、湖侧、定义文件、语义层定义）。这条纪律在本章另外三处各自出现一次：[03 §7.6 组合六](../03-lakehouse/03-lakehouse-section-7-sec7.md) 的「同一业务实体只能有一个权威表，另一份必须是可重建的派生结果」、[01 §7.7](../01-data-warehouse/01-data-warehouse-section-7-sec7.md) 的「湖与仓双写且两侧都可写」反模式（正确做法是显式指定权威表、派生侧只读）、以及 [09 §7.6 组合四](../09-realtime-compute/09-realtime-compute-section-7-sec7.md) 对流与特征库的职责划分。**判据**：权威声明要能回答「出现两个不一致的数时，顺着哪一层的声明去找」；答不出，与会讨论就没有终点。它在样本层的形态很具体——16 要求样本的五个元数据字段里必须有时点与快照，「评测结论必须绑定快照 id」，否则结论绑定的不是一份具体的表状态。这也是 [07 §7.7](07-architecture-decisions-section-7-sec7.md) 那条反模式的另一面：先分层再定契约，每一层的「可信」都无法被元数据表达。

**接口三 · 先契约、再分层、最后才动运行时。** 三处顺序完全一致，且都不是偏好而是机制结论：[07 §7.7](07-architecture-decisions-section-7-sec7.md) 的「先定表格式契约，再在其上分层——顺序颠倒的代价不会立刻显现，它会在第一次需要行级更新时一次性结算」；[01 §7.7](../01-data-warehouse/01-data-warehouse-section-7-sec7.md) 的「先迁口径与分层，再迁引擎」（口径与分层是语义结构，引擎只是执行它的工具）；[05 §7.5](../05-cold-hot-tiering/05-cold-hot-tiering-section-7-sec7.md) 的「先统一入口，再分层」（多入口时分层会在短期内被绕过）。**这三条合起来给出一个可复核的顺序**：契约 → 分层 → 运行时，每一步都只在它前一步已可被元数据表达时才生效。

**接口四 · 「第二个原生读者」这一个阈值在三棵树里各出现一次。** [01 §7.5 节点 ②](../01-data-warehouse/01-data-warehouse-section-7-sec7.md)、[03 §7.5 节点 ③](../03-lakehouse/03-lakehouse-section-7-sec7.md) 与 [07 §7.3.2](07-architecture-decisions-section-7-sec7.md) 用的是同一个数：**契约的价值等于「能被几个引擎正确解析」这个数目**。**判据**：三处必须引用同一份读者清单，且清单里只算**原生读写**、不含「通过导出物间接访问」。一处按 1 算、另一处按 2 算，就会出现最难查的半开状态——为第二个读者付了 Compaction 与 Catalog 的运维，却没有为它保留契约能力。

#### 2.5.3 冗余乘数的合并口径：Region 层与 Cell 层是不是同一笔开支

「12 Cell × 3 Region × 同城双活 × 双轨峰值」这四个乘数里，**只有两个是冗余**（Cell 层、机房层），另两个分别是**切分**与**计价结构**：3 Region 是归属切分（[Ch12 §01 单元化 §3.2.4](../../12-architecture/01-cell-based-architecture/01-cell-based-architecture-section-3-sec3.md) 记录的形态是「3 Region 按 user_id 哈希归属 + 单元内闭环 + 邻区可接管」；「容量按归属分摊」是本文推论、原文未写），双轨峰值是同一份容量的两种计价方式（[Ch12 §04 §3.2.1](../../12-architecture/04-capacity-planning/04-capacity-planning-section-3-sec3.md)：「双轨容量 = 常驻基线 + 弹性峰值」，基线按长期承诺价、峰值按按需价，且只有 `T_peak > T_ready` 时才成立）。**把四个当成同一种数直接相乘，是这笔预算最容易错的一处。**

两个冗余项的算式，书内各有一处：

- **Cell 层**（[Ch12 §01 §4.6](../../12-architecture/01-cell-based-architecture/01-cell-based-architecture-section-4-sec4.md)）：冗余口径取**接管目标**而不是均值。若设计为单 Cell 故障由其余 Cell 承接，每 Cell 按 `N/(N−1)` 备容量——N=12、接管目标 N−1 时系数为 12/11 ≈ 1.09，即 **+9%**；接管目标 N−2 时为 12/10 = 1.20，即 **+20%**（两值均为【推算】，原文推导链见该文件 §4.6）。该文件明写这条算式就是「每 Cell 资源 = 总资源 / Cell 数 + 冗余」里「冗余」那一项的取值依据——**由接管目标定，不由经验拍板**。
- **机房层**（[Ch12 §02 §4.6](../../12-architecture/02-multi-region/02-multi-region-section-4-sec4.md)）：「同城双活把资源翻倍即可」，而异地多活额外付的不是资源、是跨 Region 复制的出网流量，它随「进入多活的表数 × 每张表写入量 × 对端数」线性增长，而不随业务条数增长（该文件给了一条可换参数重算的推算与一句「单价按官方价目表现价核，不给固定价」【经验】）。

**书内没有一句话回答「这两个是不是同一笔开支」，但两处的分母都写出来了，比对即得答案。判定分三步：**

1. **写下 Cell 层系数的分母**：`N/(N−1)` 这个式子里的「总资源」指的是**一个机房内的总量**，还是**多地合计的总量**？Ch12 §01 §4.6 的原文没有把这一层写死——这是三步里唯一需要你自己填的一格。
2. **写下机房层系数的分母**：Ch12 §02 §4.6 给的是「同城双活把资源翻倍」，它的分母是**一份可独立承接全量的完整站点**。
3. **比对两个分母是否指向同一份容量**：若第 1 步填的是「多地合计」，则机房层的 ×2 已经把 Cell 冗余包在里面，两个乘数是**对同一份容量计提了两次**，正确写法是「（多地合计 ÷ 12）+ 一次接管冗余」，而不是「（单地 ÷ 12）× 1.09 × 2」；若第 1 步填的是「单机房」，则两层覆盖不同故障域（Cell 级与机房级），各自计提一次，不重复。

**一个不依赖第 1 步怎么填的现场判定**，问一句就够：**邻 Cell 接管时，接管方是同机房内的邻 Cell，还是另一个机房的同名 Cell？** 接管发生在机房内 → `12/11` 只在单机房内计提，机房层的 ×2 是第二笔，不重复；接管跨机房 → 两个系数覆盖同一个故障域，重复。这个问题在演练里就能回答，不必等预算评审。

**Region 层为什么没有同形的算式，以及它该怎么取值。** 书内只给出 Cell 层的 `N/(N−1)`（Ch12 §01 §4.6 与 Ch12 §01 §8 的面试题都写的是「容量系数约 N/(N−1)，12 个 Cell 时约 +9%」；该值在 §4.6 与 §3.2.1 均标【推算】），Region 数一侧给的是形态与边界——「3 Region 按 user_id 哈希归属 + 单元内闭环 + 邻区可接管」，以及 §3.4 组合模式里的「跨地域只同步、不并写关键业务键」。**因此 Region 层的系数不能照抄 12/11**：两者的分母不同，12/11 说的是「12 份里坏掉 1 份」，而 3 个 Region 若按接管目标 2 取值，按同一形式算出的是 3/2（即 +50%，【推算】，套用同一条 `N/(N−1)` 形式），量级完全不同。取值时要把接管目标写进决策记录，而不是只写「预留了冗余」——这正是 Ch12 §01 §4.9 自检清单里那一问的意思。

#### 2.5.4 看这一节就够了的路径（3–4 个主题）

如果你的目标只是**把全栈方案的骨架定下来**，按下面的路径读，其余主题在你被具体问题卡住时再回查。

**最小路径（3 个主题）**：

1. [15 OneData §7.5](../15-one-data/15-one-data-section-7-sec7.md)——定**口径的裁决权**在中心还是域。它必须排第一，因为口径定义有几份、由谁改，就是 07 第一条判据（实现份数）的第一份输入。
2. [07 架构决策 §7.5](07-architecture-decisions-section-7-sec7.md)——定**实现份数与数据契约**（「同一份逻辑允许有几份实现」「谁是唯一的读写接口」）。
3. [03 Lakehouse §7.5](../03-lakehouse/03-lakehouse-section-7-sec7.md)——定**合并成本放写路径还是读路径**，它同时把表格式与写入形态一起定下来。

这三棵树的判据都不依赖其他 13 棵的输出，而其他 13 棵都要引用它们的输出——这就是「最小」的含义。

**再加 1 个，按你的第一约束选**：

- 第一约束是「**多久可见**」→ 加 [09 实时计算 §7.5](../09-realtime-compute/09-realtime-compute-section-7-sec7.md)，它给出延迟下限（提交间隔）与端到端一致性的上限（由最弱一环决定）。
- 第一约束是「**谁读得到、读得多快**」→ 加 [11 OLAP 引擎 §7.5](../11-olap-engine/11-olap-engine-section-7-sec7.md)，它给出的顺序是「先量表设计 → 再动物化 → 最后才动引擎形态」。

**什么时候这 3–4 个不够。** 方案里出现**模型训练**或**跨天依赖编排**时，必须补读 [16 样本库 §7.5](../16-sample-library/16-sample-library-section-7-sec7.md) 与 [12 调度系统 §7.5](../12-scheduler/12-scheduler-section-7-sec7.md)——它们的约束方向与上面几条**相反**：16 要保留期长于样本跨度，与 04 / 10 / 07 要保留期短于扩容窗口与恢复 SLA 正好相抵（见 2.5.2 接口一）；12 要依赖按数据就绪而不是按任务成功，而「数据什么时候算就绪」又由第 3 步的表格式与提交边界决定。还有一处要一并读：报表预算里的冗余乘数，其算式与边界在 [Ch12 §01 §4.6](../../12-architecture/01-cell-based-architecture/01-cell-based-architecture-section-4-sec4.md) 与 [Ch12 §02 §4.6](../../12-architecture/02-multi-region/02-multi-region-section-4-sec4.md)，双轨口径在 [Ch12 §04 §3.2.1](../../12-architecture/04-capacity-planning/04-capacity-planning-section-3-sec3.md)——**这三处不并排读，四个乘数就会重复计入**（判定方法见 2.5.3）。

> 💡 **思考锚点**：把你当前架构按 §2.2 的 CAP 三行对一遍——你为了保实时（分区时取 A）牺牲的是哪一层的一致性（C）？如果你选的是 Lambda，服务层那个 `merge(..., window=batch_window)` 里的窗口具体是多久，它直接决定了你的"近似值"要漂多久才被批层收敛掉。
