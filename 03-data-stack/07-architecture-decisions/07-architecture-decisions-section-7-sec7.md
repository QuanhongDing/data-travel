## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把「取决于场景的结论」伪装成「绝对结论」。`一致性：Lambda 5 分、Kappa 4 分` 这样的格子回答了「这个方案好不好」，而选型要回答的是「在我的约束下它会怎样」。同一个维度在不同场景下权重相反：对账与资金链路里「两条链路的数对不上」是事故，在内容推荐里只是当日看板略有偏差；`成本 3 分 vs 5 分` 更是完全没有回答「成本随什么增长」——而后者才是选型的输入。

「实时性 5 分」这一类打分问题更大：**实时性不是某个方案的属性，而是链路上最慢一环的属性**。Kappa 标 5 分、Lakehouse 也标 5 分，但两个 5 分来自完全不同的机制——Kappa 靠「只有一条流链路，没有要等的批层」，Lakehouse 靠「表格式 + 流引擎写同一张表」。当写入频率或数据量变化时，两者掉下去的顺序完全不同：前者受制于重放窗口，后者受制于元数据与小文件规模。把两个机制不同的结论缩写成同一个数字，等于把「什么条件下失效」这条最有用的信息删掉了。

第三个问题是**混层**。这一章的候选其实分属四类正交的问题：Lambda / Kappa 回答「同一份业务逻辑在系统里存在几份实现」；Lakehouse / 数据湖 / 传统数据仓库回答「数据有几份、谁是读写契约」；Medallion 回答「数据按可信度分几层对外供给」；Event Sourcing + CQRS 回答「状态与查询如何分离」。四者可以同时成立——本章 [§6](07-architecture-decisions-section-6-sec6.md) 的四个案例都是叠了两到三层（四层同源、存算分离、三引擎分工、流批一体）。把它们放进一张打分表排名，得到的是一张不可比的表。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 实现份数 | 同一份业务逻辑在系统里存在几份实现 | 它决定「改一次要改几处」，是长期维护成本的主项，也是口径漂移的根源 |
| 数据份数与存储契约 | 同一份数据有几份副本，谁是唯一的读写接口 | 副本越多同步链路越多；契约不唯一时，换引擎就等于迁数据（[§6](07-architecture-decisions-section-6-sec6.md) 的两条收敛经验） |
| 一致性由什么保证 | 端到端精确一次、批层对账，还是表格式快照 | 它决定事故的形态：会报错，还是会「悄悄算错」 |
| 恢复与回算成本 | 出错后要重算多久、重算窗口多大 | 它把「实时性」换算成可比较的量——恢复时间；只谈延迟不谈恢复，等于只谈一半 |
| 元数据与文件规模 | 提交频率会带来多少快照、清单与小文件 | 湖仓最容易被低估的成本项，判定方法见 [§5.4](07-architecture-decisions-section-5-ai.md) |
| 组织与决策成本 | 需要几个人、什么技能、多少常驻组件、变更谁签字 | 架构范式的成本最终落在组织上（[§3.3](07-architecture-decisions-section-3-sec3.md) 的六条反模式有共同成因） |

这六条的排列同样是结论：前两条决定「几份」，中间两条决定「出错时怎么办」，后两条决定「长期养得起吗」。**顺序不能颠倒**——在副本数与契约没定之前讨论恢复方式，讨论的是不存在的系统。

用这六条去读打分表里的「实时性」一列，会得到一个不同的结论：实时性并不是被比较的那个维度，**它是「恢复与回算成本」在正常情况下的投影**。一个架构能多快给出正确结果，取决于它出错后能否快速重算；只比较正常路径的延迟，会把「快但错了要重来」的方案评得过高。

最后一条关于判据本身的纪律：**判据必须能回答，而不是能打分**。上表每一行都能落到一个具体动作上——数一次副本数、跑一次回算、数一次快照对象数、问一次谁签字。凡是你无法在一天内取到答案的判据，就不该出现在选型表里，因为它只会变成又一次印象分投票。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Lambda | 计算范式：批 + 流双链路 | 批层出全量准确结果，速度层出增量近似结果，服务层按窗口合并 | 对账、风控等要求「全量可重算」的场景 | 方法论公开（Marz 2011 提出，Marz & Warren 2015 系统化）【公开，2015】 |
| Kappa | 计算范式：只有流 | 以可重放的日志为唯一写模型，历史靠重放而非批层重建 | 纯实时、事件溯源型业务 | 方法论公开（Kreps 2014）【公开，2014】 |
| Lakehouse | 存储范式：开放格式 + 表格式 | 对象存储上以表格式（Iceberg / Hudi / Delta / Paimon 一类）提供快照、ACID 与时间旅行 | 现代数据栈（BI + 特征 + 训练共读一份） | 开源项目 + 商业发行版（概念由 Databricks 于 2020 年提出，论文见 CIDR 2021）【公开，2021】 |
| 流批一体 | 计算范式：一份定义、两个运行时 | 同一份 SQL / 代码由 source 有无边界决定跑批还是跑流，输出写同一张表 | 实时数仓（Flink + Paimon 一类组合） | 开源（Flink / Spark / Paimon 等） |
| 传统数据仓库 | 存储 + 计算耦合 | 专有列存格式、强治理、按峰值预置资源 | 报表与 BI 为主的组织 | 商业许可（含云托管） |
| 数据湖（无表格式） | 开放文件存储 | 文件为契约，无表级语义；分区约定靠人遵守 | 早期 Hadoop 数据湖 | 开源为主 |
| Medallion（Bronze / Silver / Gold） | 组织范式：按可信度分层 | 原始 → 清洗整合 → 面向应用，每层可被独立消费与回滚 | 湖仓项目的默认分层（Databricks 提出并推广） | 概念公开，无独立许可（官方术语页与博客，起于 2021 年前后）【公开，可自行核验】 |
| Event Sourcing + CQRS | 应用范式：写模型与读模型分离 | 状态由事件流重放推出，查询侧单独物化读模型 | 审计严格场景（金融、医疗） | 模式公开，无单一产品 |
| AI 原生（Lakehouse + 向量库 + LLM） | 产品组合说法 | 在湖仓上叠加向量索引与模型调用 | 已上线 AI 应用的团队 | 各组件分别授权；本节只当作组合记录（见 [§5.5](07-architecture-decisions-section-5-ai.md)） |
| 自治架构（Self-Driving） | 方向，不是范式 | 拆分后成立的是确定性自动化（自动合并 / 自动物化 / 自适应并行度），未成立的是「由模型决定架构怎么演进」 | 尚无可核验的生产案例 | 以厂商能力条目为准【公开，可自行核验】 |

这十个候选分四**族**：**计算范式族**（Lambda、Kappa、流批一体）——差异在「批层是否存在、实现有几份」；**存储范式族**（数据湖、传统数据仓库、Lakehouse）——差异在「谁是读写契约、有没有表级语义」；**组织范式族**（Medallion、Event Sourcing + CQRS）——不改引擎也不改格式，只改数据怎么分层、状态怎么表达；**方向族**（AI 原生、自治架构）——按 [§5.5](07-architecture-decisions-section-5-ai.md) 的判定，它们目前都还不是可判定的架构范式。

分族带来一个直接的操作结论：**选型要按族逐层做，每层只回答一个问题**。计算族问「同一份逻辑允许有几份实现」；存储族问「数据有几份、谁是契约」；组织族问「谁需要按什么可信度消费」。三层做完，方案组合自然出现——这也是为什么 [§6](07-architecture-decisions-section-6-sec6.md) 里四个案例的答案都不是「选了哪一个」，而是「每一层各选了什么」。

分族的第二个用处是**快速排除**。同族内换方案通常只是换实现，跨族换方案才需要重建：把「从 Lambda 换到 Kappa」和「从 Lambda 换到 Lakehouse」放在一起比较是错的——前者是换计算范式的实现（同一层内），后者是引入存储契约（新增一层）。表里每一行都应该能回答「它在回答哪个问题」，答不上来的候选说明它不是一个范式，而是一个产品名。

关于「方向族」的处理需要说明清楚：AI 原生与自治架构在表里被保留，是因为它们是本章讨论范围内的真实方向（[§5](07-architecture-decisions-section-5-ai.md) 有专节），但**保留候选不等于承认它们可比较**。选型纪律是：只有能给出「什么条件下失效」的候选，才能进决策树；给不出的，就只作为方向记录。

### 7.3 机制差异：为什么它们表现不同（核心节）

以下四个机制维度覆盖全部候选，也是「为什么它们表现不同」的全部原因。顺序不可颠倒：7.3.1 决定实现份数，7.3.2 决定数据份数与契约，7.3.3 决定消费侧的供给方式，7.3.4 决定出错之后怎么办。

用这四节做比较时有一个固定动作：**每节只问一个「因为它有什么机制，所以在什么条件下必须表现成什么样」**，把答不上来的候选从决策树里删掉。四个维度里只要有三个能答上，这个候选就已经比你手上的打分表可靠——因为打分表一个机制都答不上来。

四节之间有两条交叉影响值得先点明，避免后文看起来自相矛盾：一是 7.3.2 的元数据成本会被 7.3.4 的恢复方式放大（恢复要读快照）；二是 7.3.3 每多一层物化，就多一份需要在 7.3.4 里被恢复的对象。**它们不是四个独立维度，而是同一份状态在四个不同角度上的代价。**

#### 7.3.1 实现份数：批层是否存在

**机制是什么**：同一份业务逻辑在系统里存在几份实现，以及两份实现之间靠什么缝合。

| 方案 | 实现份数 | 缝合点 | 口径分歧从哪里来 |
| --- | --- | --- | --- |
| Lambda | 2（批层 + 速度层）+ 1（服务层合并） | 服务层按时间窗口合并两层结果 | 两层对「同一个窗口的边界」理解不一致 |
| Kappa | 1 | 无缝合点，但历史要靠重放补 | 重放窗口与实时窗口的重叠处理 |
| 流批一体 | 1 份定义 | 无缝合点（同一份 SQL 两个运行时） | 只可能来自 source 的边界声明写错 |

**由此必然导出的性质**：因为 Lambda 的速度层结果是「近似 + 临时」，所以它必须先有一个确定的窗口把速度层结果丢弃、由批层结果接管；这个窗口就是两条链路之间的缝合线，也是「同一指标两个值」的来源——业务方看到的差异通常不是两条链路都错，而是**一条在被读、另一条也在被读**。代价是这条缝合线必须被持续对账，而对账是纯开销、不产出新数据。因为流批一体只有一份定义，口径漂移在结构上不可能发生；代价是它要求引擎与存储同时支持两种运行时，且对 source 有无边界的声明成为新的出错点（[§6](07-architecture-decisions-section-6-sec6.md) 的字节与 Netflix 两个案例都是沿着这条路线收敛的）。

**公开证据**：Lambda 三层的原始表述见 Marz & Warren《Big Data: Principles and Best Practices of Scalable Realtime Data Systems》（2015）【公开，2015】；Kappa 以可重放日志替代批层的论证见 Kreps《Questioning the Lambda Architecture》（2014）【公开，2014】；流批一体的 API 与运行时统一程度请以 Apache Flink 与 Apache Spark 的官方 release note 为准，**判定方法是看 release 页里有没有独立条目，而不是看项目路线图**【公开，可自行核验】。

**失效条件**：当「全量重算」不再是一个被要求的动作时，Lambda 的批层就是纯负担，此时 Kappa 更简单；反过来，当重放窗口超过你能承受的恢复时间时，Kappa 的单一链路会成为事故恢复时间的地板（推导见 7.4）。

**缝合线长什么样**，这是判断一个 Lambda 实现是否被真正设计过的入口。服务层合并两层结果只有两种合法形态：按时间窗口相加（批层给某时间点之前的全量，速度层给之后的增量），或按时间点切换（某时间点之前读批、之后读流）。前者的典型错误是**重复计数**（窗口边界两侧都被计入），后者是**空洞**（边界处两边都没覆盖）。判定方法：问「批层跑完之后，速度层的哪些结果会被丢弃」——答不出具体的丢弃规则，说明缝合线只是被容忍，没有被设计。

由此还能纠正一个常见混淆：因为批层是唯一权威，所以**批层延迟直接决定「最快什么时候能看到准确的数」**，速度层不能缩短这个时间，只能提前给出近似值。把「能提前看到近似值」记成「准确结果的延迟」，是打分表里「实时性」那一列错误的根源。

#### 7.3.2 谁是数据契约：湖、仓与湖仓

**机制是什么**：多引擎读同一份数据时，靠什么保证大家看到同一个版本。

| 方案 | 契约 | 读到的版本一致性 | 换引擎的代价 |
| --- | --- | --- | --- |
| 传统数据仓库 | 专有格式 + 元数据服务 | 强（由同一套引擎保证） | 大：数据要导出并转换 |
| 数据湖（无表格式） | 文件与目录约定 | 无保证，靠分区命名与时间对齐 | 中：文件可读，但语义要重新约定 |
| Lakehouse | 表格式规范（快照 → 清单 → 数据文件） | 每个引擎各自读同一快照，看到同一版本 | 小：换引擎不迁数据（[§6](07-architecture-decisions-section-6-sec6.md) 阿里案例的存算分离与加速层直读） |

**由此必然导出的性质**：因为表格式把「一组文件」提升为「一个带快照语义的表」，所以多个引擎可以各自读同一份数据而看到同一个版本，这是一个团队能同时用 SQL 引擎、批引擎与 OLAP 引擎服务同一批消费方的技术前提；代价是**元数据本身成为新的状态**：提交越频繁，快照与清单对象越多，查询规划要读的清单越多、小文件越多——这条成本随写入频率增长，而不随数据量增长，因此它经常在「数据量没变、但写入频率提高」时突然出现。反过来，数据湖因为文件就是契约，读写都便宜，但任何一次 schema 变更或行级修正都没有语义位置可放，只能靠人遵守约定——**便宜在写入侧，昂贵在正确性侧**。

**公开证据**：Lakehouse 的表格式与多引擎一致性论述见 Armbrust 等《Lakehouse: A New Generation of Open Platforms…》（CIDR 2021）【公开，2021】；对象存储上的 ACID 表格式见 Armbrust 等《Delta Lake: High-Performance ACID Table Storage over Cloud Object Stores》（VLDB 2020）【公开，2020】；某能力（行级更新、变更日志、时间旅行）在你所用的引擎与版本里是正式功能还是预览，**判定入口是官方 release note 与规范仓库的当前版本**，不是首页宣传语【公开，可自行核验】。

**失效条件**：当写入以秒级频率发生、且没有合并与清理机制时，表格式的优势会被元数据膨胀抵消——查询规划成本随提交次数累积，而此时数据量可能并不大。

**「换引擎不迁数据」这句话的成立条件**必须写清楚：它成立的前提是新引擎能正确解析同一份元数据。规范通常允许实现只支持其中一部分，于是跨引擎时会出现「能读但语义不同」的数据——最危险的一种是某个引擎对未支持的特性静默降级。判定方法很直接：**拿同一张表用两个引擎各做一次时间旅行读取，比对结果**；两者不一致，就说明你的「不迁数据」是建立在约定而不是规范上。

由此得到一条选型纪律：**契约的价值等于「能被几个引擎正确解析」这个数目**，而不是「规范里写了多少能力」。这也是为什么升级表格式版本与升级引擎要一起排期——单边升级会让契约的有效解析范围暂时收窄。

#### 7.3.3 供给方式：分层与读写分离

**机制是什么**：消费方怎么拿到数据——直接读原始层、读一个「可信层」，还是读一个专门为查询物化的读模型。

| 方案 | 谁回答「这份数据可信吗」 | 副本/物化数量 | 主要代价 |
| --- | --- | --- | --- |
| 单层湖仓（不分层） | 每个消费方自己判断 | 1 | 可信度判断被复制到每个消费方，且各不相同 |
| Medallion（Bronze / Silver / Gold） | 由「它在哪一层」回答 | 2 份全量（Bronze、Silver）+ 1 份聚合（Gold） | 三条加工与质量链路；任一层口径改动都要评估下游（[11-cross-cutting/05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)） |
| Event Sourcing + CQRS | 由事件流的完整性回答 | 写模型 1 份 + 每个查询一个读模型 | 每个读模型都要自己重放与记录一致性位置 |

**由此必然导出的性质**：因为 Medallion 把可信度做成「层」而不是「标签」，所以「这份数据可不可信」有一个组织级答案，不需要每个消费方各自判断；代价是同一份数据在链路上被物化两次以上，任意一层的口径变化都会沿链路传导——**分层把判断成本集中了，同时把变更的传导路径也集中了**。因为 Event Sourcing 把事件流作为唯一写模型，所以任何新查询都可以通过新建读模型来满足、不需要改动写入侧；代价是每个读模型都是派生的第二份状态，都必须自己维护重放逻辑与一致性位置，而重放成本与读模型数量成正比。这两条性质指向同一个结论：**读模型与分层都不是免费的复制品，它们是「用确定性的重放/重算换取消费灵活性」的交易。**

**公开证据**：Bronze / Silver / Gold 的定义见 Databricks 官方术语页与官方博客（起于 2021 年前后，以站点当前内容为准）【公开，可自行核验】；CQRS 与事件溯源作为模式的公开论述早于本章讨论的湖仓体系，常见于 2010 年前后的模式文章与演讲，具体出处与年份请按这两个关键词检索核验【公开，可自行核验】。

**失效条件**：当 Gold 层被当作「唯一真相」而 Bronze / Silver 无人负责时，分层会退化成三份互不相关的数据——判断成本没有集中，反而变成了三份都要维护。

分层与语义层解决的不是同一个问题，这一点经常被混淆：**分层回答「可不可信」，语义层回答「叫什么名字、怎么算」**。把 Gold 层直接当成语义层，会让口径定义随物化表的结构走——表改一列，口径就变一次，而没有任何一处声明说它变了。正确的边界是：分层提供可信的输入，语义层在输入之上声明口径，两者都只被读取、不互相替代。

由此还得到一条可观测性上的好处，值得明确写出来：因为每一层都是物理物化，所以每一层的新鲜度都是独立可测的指标。这是分层相对「标签式可信度」的唯一硬优势——**你可以对 Bronze、Silver、Gold 分别设新鲜度告警**，而标签做不到这一点。代价是同一份数据有三个新鲜度，消费方必须先知道自己该看哪一层。

#### 7.3.4 恢复与回算：出错之后怎么办

**机制是什么**：数据或逻辑出错后，把正确结果重新做出来要花多久、动多少东西。

| 方案 | 恢复动作 | 恢复时间由什么决定 | 恢复期间消费方看到什么 |
| --- | --- | --- | --- |
| Lambda | 重跑批层对应窗口 | 批层的回算能力与窗口大小 | 速度层继续出近似结果（此时它是错的） |
| Kappa | 从某个 offset 重放 | 重放窗口 × （日均吞吐 / 重放吞吐） | 取决于是否双跑，通常有一段无更新期 |
| 流批一体 + 表格式 | 用批模式重写受影响分区 | 受影响分区数 × 单分区重算成本 | 快照语义使旧快照仍可读（时间旅行） |
| Event Sourcing | 重放事件流重建读模型 | 事件总量 / 重放速率 | 读模型在重建完成前不可用或落后 |
| Medallion | 从受影响的那一层重跑 | 层数 × 每层重算成本 | 下游在重算完成前读到旧值 |

**由此必然导出的性质**：因为表格式把历史版本留在元数据里（快照 + 时间旅行），所以「回算」是一次分区重写而不是全链路重建，恢复时间与**受影响分区数**成正比而不与历史深度成正比；代价是这套能力依赖元数据保持健康（7.3.2），元数据一旦损坏或膨胀，恢复路径本身要先修好。因为 Kappa 只有一条链路，它的恢复时间与**重放窗口**成正比——这解释了为什么 Kappa 的可用性上限其实是「你能接受多长的重放时间」，而不是「流引擎有多快」。

**公开证据**：回算与重放成本的具体量级无法给出统一公开数字，它取决于引擎、集群与分区布局；**判定方法**：拿你自己的表做一次实测——挑一个分区用批模式重写它，记录耗时，再乘以你的历史分区数；这个乘积就是你在这套架构下的最坏恢复时间【经验】。

**失效条件**：当恢复动作需要停机或需要下游全部暂停时，「快照 + 回算」的优势消失——恢复能力必须在消费方不必知情的前提下成立，否则它只是把事故时间换算成协调时间。

**恢复能力必须被演练，否则等于不存在。**推荐一个可执行的判定方法：每季度挑一个分区，从快照回算并与原结果比对，记录耗时；连续两次演练都拿不到可重复的结果，说明这条恢复路径在事故当天不可用。理由很直接——恢复路径会随表格式版本、引擎版本与存储布局变化，没有演练的路径没人知道它还在不在。

最后一个可调参数常被忽略：**分区粒度**。因为恢复成本与受影响分区数成正比，所以分区过粗会让单次回算代价陡增，分区过细则元数据与文件数上升——这两端的代价正好落在 7.3.2 与本节两个机制上，也说明湖仓里没有任何一个参数是孤立最优的，只能按「你的恢复 SLA 与写入频率」一起定。

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本是五项之和，每一项都随不同的变量增长：

```
总成本 ≈ 存储(份数 × 数据量) + 计算(常驻作业数 × 运行时长) + 元数据(对象数)
          + 一致性维持(对账范围 × 频次 + 重放窗口) + 组织(组件数 × 人)
```

| 方案 | 主导项 | 隐性成本（上线时不计入、三年后计入） | 什么条件下反转 |
| --- | --- | --- | --- |
| Lambda | 计算（双链路常驻）+ 组织（两套技能） | 对账与缝合窗口的持续人工投入 | 业务不再要求全量可重算时，批层变纯负担 |
| Kappa | 计算（流作业常驻）+ 重放 | 恢复时间随重放窗口增长 | 历史回算从月度变成周度时，重放窗口成为瓶颈 |
| Lakehouse | 存储（线性，便宜）+ 元数据（随提交频率增长） | 小文件与清单膨胀；规划成本上升 | 写入频率提高而合并策略没跟上时 |
| 流批一体 | 计算（一份定义双运行时） | 对引擎与存储的版本要求；边界声明的正确性 | 引擎版本落后于表格式能力时 |
| 传统数据仓库 | 计算（按峰值预置） | 存算耦合导致的扩容搬迁 | 数据量增长快于预算时 |
| 数据湖（无表格式） | 存储（最便宜） | 正确性成本：schema 变更与行级修正无处安放 | 上游开始做行级更新或删改时 |
| Medallion 分层 | 存储 + 加工链路（层数 × 每层成本） | 每层的新鲜度监控与 Owner | Gold 层被当成唯一真相、无人负责上游时 |
| Event Sourcing | 存储（事件只追加）+ 重放计算 | 每个读模型各自的重放与一致性维护 | 读模型数量增长时，重放成本按数量累加 |

三项量级示例（参数可自行替换后重算，档位见各项）：

- **Kappa 的重放时间**：设日均入湖 10 TB，重放吞吐为日常处理吞吐的 2 倍，则重放 30 天历史约需 15 天（30 天 × 10 TB/天 ÷ 20 TB/天 = 15 天）【推算】。这个数直接决定了「历史逻辑改一次要等多久」。
- **Lakehouse 的元数据对象数**：若每 5 分钟提交一次，一年约 10.5 万次提交（365 天 × 24 小时 × 12 次/小时 = 105,120 次）【推算】；每次提交留下快照与清单，规划期要读的对象数与「自上次合并以来的提交次数」同阶。这条成本随**提交频率**增长——同样的数据量、写入频率翻一倍，元数据对象数就翻一倍。
- **Medallion 的物化份数**：Bronze 与原始数据同阶，Silver 与 Bronze 同阶（清洗不删行），Gold 是聚合结果，行数通常比前两层小 1–3 个数量级——条件是聚合比（明细行数 ÷ 分组组合数）落在 10¹–10³，即分组基数远小于事实表行数；按明细粒度出 Gold（聚合比接近 1）时这个量级不再成立【经验】。因此全量副本约 2 份，而「看起来只有一份 Gold」的直觉会低估存储与加工链路成本。

**成本对比里不该出现的数字**：任何形如「成本节省 63%」「延迟降低 47%」的结论，如果没有给出数据量、写入频率、查询形态与基线口径，就没有可迁移性。上表把主导项与反转条件写出来，就是为了让读者能用自己的参数替换后重算一遍【经验】。

**组织成本是唯一不会被压降的那一项**，值得单独形式化一次：

```
组织成本 ≈ 常驻组件数 × 每个组件的维护人数 + 决策链长度 × 变更频率
```

一个可自行替换参数的推算：若每个常驻组件平均需要 0.5 人维护，Lambda 引入批处理、流处理、服务层三套则约 1.5 人，收敛到流批一体一套后约 0.5–1 人；两者的差额是 0.5–1.0 人（1.5 − 1 = 0.5，1.5 − 0.5 = 1.0），对一个 10 人的数据团队即 5%–10% 的人力差异【推算】。这笔差额不会被硬件降价抵掉，也不会随数据量变化——**它是架构选型里最稳定、也最容易被漏算的一项**，因为它在立项时表现为「先按 Lambda 做，之后再优化」。

### 7.5 决策树（每个分支都要有阈值依据）

```
开始：架构范式选型
├─ Q1 同一份业务逻辑，是否必须同时提供「全量准确结果」与「秒级增量结果」两个可用输出？
│    ├─ 是 → 进入 Q2
│    └─ 否（一个可用输出即可）→ 进入 Q3
├─ Q2 两条链路给出不同数值时，业务能否接受（差异不影响决策）？
│    ├─ 能接受 → Lambda（批层 + 速度层 + 服务层）
│    └─ 不能接受 → 流批一体：一份定义 + 两个运行时，写同一张表格式表
├─ Q3 历史回算是否低频（月度或更低），且重放窗口 < 你能承受的恢复时间？
│    ├─ 是 → Kappa（可重放日志为唯一写模型）
│    └─ 否 → Lakehouse（表格式承载历史 + 批引擎做回算）
├─ Q4 是否需要多个引擎（BI / 特征 / OLAP / 训练）读同一份数据？
│    ├─ 是 → 必须引入表格式，把「表」而不是「文件」作为契约
│    └─ 否，消费方与查询形态单一 → 专用数仓或 OLAP 库即可，不必上湖仓
├─ Q5 是否存在「同一份数据、不同消费方对可信度要求不同」的情况？
│    ├─ 是 → Medallion 分层（Bronze / Silver / Gold），每层有 Owner 与新鲜度
│    └─ 否 → 不分层，避免三条链路各自漂移
├─ Q6 是否存在「状态必须能按任意时间点重建」的审计要求？
│    ├─ 是 → Event Sourcing + CQRS（事件流为唯一写模型）
│    └─ 否 → 用表格式的时间旅行即可满足，不必引入事件溯源
├─ Q7 写入提交频率是否高到会让元数据膨胀（秒级提交、无合并策略）？
│    ├─ 是 → 先打开引擎侧的合并与清理，并设阈值告警，再决定是否上表格式
│    └─ 否 → 元数据不构成主导项
└─ Q8 消费方是否包含 Agent / 自然语言取数？
     ├─ 是 → 先补语义层与权限下推（见 [§5.5](07-architecture-decisions-section-5-ai.md)），不要把「加向量库」写进架构决策
     └─ 否 → 不立项
```

**阈值依据**（与树上节点一一对应）：

- **Q1**：依据是 [§2.1](07-architecture-decisions.md) 对 Lambda 的定义——批层与速度层的存在意义是「两个输出」。若业务只要求一个可用输出，批层的唯一作用就只剩回算，而回算可以由表格式 + 批引擎在需要时提供，不必常驻一条链路。
- **Q2**：判据不是「差异有多大」，而是「差异会不会改变决策」。同一份逻辑两份实现时，两侧对不上是常态，量级常见在个位数百分比【经验】；这个量级在报表场景可容忍、在对账场景不可容忍。**这条由业务方回答，不由架构师估算。**
- **Q3**：它有两半阈值，两半都不是独立的日历数，而是同一条判定式在两个方向上的投影——「两次回算之间必须留得下走完一次全量重放的时间」。① **回算频率「月度或更低」**：判定式为「回算间隔 − 单次全量重放耗时 > 0，且留得下余量」。按 7.4 的推算（重放 30 天历史约需 15 天）：月度回算的间隔是 30 天，扣掉 15 天后还剩 15 天，链路有一半时间可用于正常处理；若降到周度（间隔 7 天），7 − 15 < 0，重放根本走不完，Kappa 不成立【推算】。所以这里阈值的形式是「单次重放耗时 ÷ 回算间隔」这个比值，而不是「月度」这个日历数——重放吞吐翻一倍，阈值就向更高频移动。② **重放窗口 < 你能承受的恢复时间**：它把 Kappa 的重放窗口换算成一个可比较的量——同样按 7.4 的推算，日均入湖 10 TB、重放吞吐为日常 2 倍时，重放 30 天约需 15 天【推算】。所以阈值不是「30 天」这个数字，而是「你能接受的最长恢复时间」。判定方法：写下事故恢复的 SLA，再除以你的重放吞吐。
- **Q4**：判据是「消费方数量与引擎数量」，不是数据量。只要有两个以上异构引擎要读同一份数据，文件契约就会开始漏——因为每个引擎对分区与 schema 的理解都需要重新约定（7.3.2）。
- **Q5**：判据是「可信度要求是否因消费方而异」。若所有消费方对数据质量的要求相同，分层只会带来两份同阶的全量副本与三条链路（7.4 的推算）【推算】。
- **Q6**：判据是「审计要求的时间点粒度」。「能查到某个快照」用表格式的时间旅行即可；「必须能按任意事件时点重建、且每次重建结果一致」才需要事件溯源——因为前者是元数据能力，后者要求事件流本身完整且不可变。
- **Q7**：阈值形式是「提交频率 × 无合并时长」。判定方法直接可测：数一次最近的快照与清单对象数，再看引擎的自动合并是否开着、能否按表关闭（[§5.4](07-architecture-decisions-section-5-ai.md) 把它列为判定入口）。
- **Q8**：依据是 [§5.5](07-architecture-decisions-section-5-ai.md) 的结论——「AI 原生 = Lakehouse + 向量库 + LLM」是产品组合说法，取数链路真正缺的是机器可读的语义层与权限下推，而向量库属于索引选型。所以它的落点是「补语义层」，不是「换架构范式」。

两条使用说明。第一，**这棵树假设你已经知道自己的约束**；如果 Q1 的答案本身就没人能确认（例如没人说得清业务是否真的要求全量重算），那要先做的是把这个问题问到有答案，而不是继续往下走——决策树的价值在收敛，不在替你做需求确认。第二，Q2 是全树唯一一条**由业务方而不是架构师回答**的节点；把它交给技术团队估算，得到的会是「差异很小可以忽略」这种在事故复盘时站不住的答案。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单一消费方、报表为主、变化慢 | 传统数仓或单一 OLAP 库 | 湖仓（若已有对象存储底座） | 不选 Lambda：为一个输出养两条链路 |
| 全量准 + 秒级增量，两条链路的差异不影响决策 | Lambda | 流批一体 | 不选 Kappa：批层承担的历史回算没有替代品 |
| 两条链路差异必须消除 | 流批一体（一份定义 + 两个运行时） | Lakehouse + 批回算 | 不选纯 Lambda：缝合线的对账成本是长期的 |
| 历史回算低频、重放窗口可接受 | Kappa | 流批一体 | 不选 Lambda：为低频动作常驻一条批链路 |
| 多引擎共读一份数据 | Lakehouse（表格式为契约） | 数仓 + 定期导出 | 不选无表格式的湖：schema 变更与行级修正无处安放 |
| 消费方可信度要求分层 | 表格式 + Medallion | 在 Gold 层之上做视图隔离 | 不选「不分层 + 靠标签」：判断成本会被复制到每个消费方 |
| 审计要求按任意时点重建 | Event Sourcing + CQRS | 表格式时间旅行（够用时） | 不选事件溯源：每个读模型都是一份要自己重放的状态 |
| 消费方是 Agent | 在既有架构上补语义层与权限下推 | —— | 不选「加向量库」：那是索引选型，不是架构决策 |
| 已有 Hadoop 数据湖、不想推倒重来 | 在湖上加表格式（契约先于消费方接入） | 保持文件约定并加治理 | 不选重建：重建的成本集中在迁移期，而补契约可以逐表推进 |
| 写入频率极高、合并策略无法开启 | 热路径用专用 OLAP 或数仓承接 | 湖仓 + 严格的分区与合并阈值 | 不选无合并的湖仓：元数据与小文件会先于数据量成为瓶颈 |

四条**常见组合**（补齐职责边界与运维代价）：

1. **Lambda → Lakehouse 迁移**：组合的职责边界是**过渡期两套并存**——旧 Lambda 继续服务存量消费方，新 Lakehouse 承接新需求，直到某个可判定的时点旧链路下线。运维代价：并存期间两份数据与两套口径同时在用，必须有一个明确的「以哪边为准」声明，否则迁移期本身就是口径事故的高发期。可行的做法是本章 [§6](07-architecture-decisions-section-6-sec6.md) 记录的收敛路径：新作业必须用统一定义写，存量按域分批迁移，每批观察一段时间再继续。
2. **Lakehouse + Kappa**：Lakehouse 承担「一份数据、多引擎共享、可回算」的职责，Kappa 承担「实时链路只有一份实现」的职责，边界是——**流链路不做历史回算，回算一律交给湖仓上的批引擎**。运维代价：两套运行时并存，流侧与湖侧的 schema 演进必须同步发布，否则会出现「流写进去的字段湖里还没有」这类问题。
3. **Lakehouse + 流批一体**：一份定义、两个运行时写同一张表格式表，湖仓提供表级语义与历史，引擎提供两种运行时。边界是——**口径定义只在定义文件里出现一次，湖仓不新增第二份口径**。运维代价：对引擎与表格式的版本耦合较强，升级需要两边同时验证；source 的边界声明成为新的出错点。
4. **AI 原生架构**：按 [§5.5](07-architecture-decisions-section-5-ai.md) 的判定，它应当拆成两件可交付的工程——**语义层（口径、粒度、密级、Owner 的机器可读）** 与 **权限下推（作用域在被调用方强制、调用留审计）**；向量库与 LLM 是这两个前提下各自的选型，不构成架构范式。运维代价：语义层成为取数链路单点，且它只读；任何写入类动作仍要人工确认。

组合的共同代价结构是：**每多一层范式，就多一份需要与上游保持同步的状态**（速度层、流链路、Bronze / Silver 物化、读模型、语义层声明）。因此组合的原则与 [§6](07-architecture-decisions-section-6-sec6.md) 的「新组件准入三问」一致：**能不能落在现有层？会新增几份副本或派生状态？谁来长期维护？**三问答不上，就不要加这一层。

每条组合还都应该能回答一个问题：**哪一层是权威**。没有这个答案的组合，在出现两个不一致的数时会退化成开会讨论，而不是顺着声明去找。四条组合的权威层分别是：组合 1 的权威在迁移完成后的 Lakehouse；组合 2 的权威在湖侧（流链路只做增量）；组合 3 的权威在定义文件（两个运行时都从它生成）；组合 4 的权威在语义层定义（口径）、在权限服务（可读性）。**权威层可以只有一处，且必须写进 ADR。**

### 7.7 选错的代价与迁移成本

下面六条反模式都写成「症状 → 后果 → 正确的做法」三段式。它们有一个共同结构：**症状里都有一个当天成立的合理理由**，所以选择发生时没人觉得在做决策——这正是架构反模式最难被发现的原因。

**反模式：为「实时」而上 Lambda，而业务其实只需要一个可用输出** —— 症状：架构图上有批层与速度层，但没有任何一个消费方同时需要两者。后果：同一份逻辑两份实现，维护成本按份数增长（不是精确倍数，而是量级）【经验】，且每一次需求变更都要评估两条链路；更隐蔽的后果是口径漂移会成为常态议题。正确的做法：先回答 7.5 的 Q1，答案为「否」时，用一条链路加表格式的历史能力即可覆盖回算需求。

**反模式：用 Kappa 承担历史回算** —— 症状：每次逻辑变更都触发一次全量重放，重放窗口逐月变长。后果：**恢复时间的地板被重放窗口锁死**（7.4 的推算：日均 10 TB、重放吞吐 2 倍时，重放 30 天约需 15 天）【推算】，事故恢复 SLA 无法达成，团队开始用「先改下游」这类临时手段绕过。正确的做法：把历史回算交给有批模式的引擎与表格式，流链路只负责增量。

**反模式：先把数据堆进对象存储，之后再补表格式** —— 症状：湖里是一堆按约定命名的目录，没有表级元数据。后果：一旦出现行级修正、schema 变更或需要多引擎一致读，就要回去补一份契约，而补的过程等于一次全量重写与重新登记；下游在此期间已经按文件约定写了大量作业，迁移面被放大。正确的做法：**契约要在第一个消费方接入之前就位**，哪怕此时只有一个引擎在读。

**反模式：把「加向量库」当成架构升级** —— 症状：架构决策文档里写「引入向量库，实现 AI 原生」。后果：语义层与权限这两个真正的缺口排不进排期，而它们才是机器取数正确率的约束；向量索引是选型问题，放在这一层讨论会把预算导向错误的账户。正确的做法：把 AI 需求拆成「机器能不能找到」（语义层与检索派生表）与「机器能不能越权」（作用域与审计），两者都不改变架构范式（[§5.5](07-architecture-decisions-section-5-ai.md)）。

**反模式：以 Kappa 之名行 Lambda 之实** —— 症状：架构图上只有流链路，但流链路之外悄悄长出一套离线纠偏作业，且它开始被消费方直接读取。后果：缝合线以「纠偏」的名义回来了，却没有任何机制保证两侧的权威关系——**这是比显式 Lambda 更差的形态，因为显式 Lambda 至少知道自己的缝合线在哪**。正确的做法：要么承认这是 Lambda 并按 Lambda 治理（明确权威层与合并规则），要么把纠偏结果限制为回灌上游、不对外直供。

**反模式：先分层再定契约** —— 症状：Bronze / Silver / Gold 三层目录都建好了，但底层仍是文件约定，没有表级元数据。后果：每一层的「可信」都无法被元数据表达，分层退化成目录命名习惯；等要做行级修正或 schema 变更时，三层都要一起返工。正确的做法：**先定表格式契约，再在其上分层**——顺序颠倒的代价不会立刻显现，它会在第一次需要行级更新时一次性结算。

**换成另一个要动什么**：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| Lambda → 流批一体 | 中（两条链路的结果对账后收敛到一份） | 大（同一逻辑要重写成一份定义，边界声明要重写） | 中（下线批层或速度层之一） | 大（一份定义两个运行时的调试方式） |
| Lambda → Lakehouse | 小（数据本就落地，改的是契约与消费入口） | 中（消费端改直读湖表） | 中（引入表格式的合并与元数据治理） | 中（表格式、快照、时间旅行） |
| Kappa → Lakehouse | 小（流链路保留，新增批回算路径） | 小 | 中（新增元数据与小文件治理） | 中 |
| 无表格式的湖 → Lakehouse | 大（要重新登记表契约，历史分区要补元数据） | 大（所有按目录约定写的作业要改） | 中（引入表格式的维护作业） | 大 |
| 传统数仓 → Lakehouse | 大（数据要迁出专有格式） | 大（SQL 方言与函数差异，性能特征不同） | 大（从预置资源转为弹性与元数据治理） | 大 |
| 单层 → Medallion | 中（增加两次物化与加工链路） | 小（消费端改读对应层） | 中（每层都要 Owner 与新鲜度监控） | 小 |

这张表里最容易被低估的一格是「无表格式的湖 → Lakehouse」的**查询改写**：迁移的难点不在把文件重新登记成表，而在于大量既有作业是按目录约定写的，它们不会报错，只会继续读到不该读的分区——**这类迁移的错误形态是静默的**，必须靠对账而不是靠测试发现。

### 7.8 小结

下表把 7.5 的决策树压成八行。读法是：先找到与你最接近的处境，再回看它对应的 7.3 小节确认理由是否成立；理由不成立就换行。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 只有一个可用输出、消费方单一 | 一条链路 + 表格式历史 | 批层的存在意义是第二个输出，不需要就不该常驻 |
| 全量准与实时增量都要，且差异可容忍 | Lambda | 两条链路各自最优，靠服务层缝合；代价是对账 |
| 两条链路的差异必须消除 | 流批一体 | 只有一份定义，口径漂移在结构上不可能 |
| 历史回算低频、恢复时间可接受 | Kappa | 单一流链路 + 重放；恢复时间由重放窗口决定 |
| 多引擎共读一份数据 | Lakehouse | 表格式把「一组文件」变成「一个有快照语义的表」 |
| 消费方可信度要求分层 | Medallion | 可信度由「在哪一层」回答，判断成本集中 |
| 审计要求按任意时点重建 | Event Sourcing + CQRS | 事件流是唯一写模型；代价是每个读模型各自重放 |
| 消费方是 Agent | 补语义层与权限下推 | 缺的是机器可读的口径与作用域，不是向量索引 |

上表回答的是「每一层各选什么」，不回答「先做哪一层」。顺序上有一条经验规则：**先把契约定下来，再谈分层与运行时**——契约是唯一一个改动会波及全部消费方的决定，而分层与运行时可以在契约之上渐进调整【经验】。反过来做（先收敛运行时、再补契约）的团队，通常在引入第二个引擎时才发现要重做一遍登记。

最后提醒一句关于这张表怎么用：它同样不是八选一。真实系统的答案是每一族各选一行，然后在 ADR 里写清哪一层是权威——**架构决策的产物是一份带权威声明的组合，而不是一个范式的名字**。

> 本节小结：这一组候选里**唯一真正起决定作用的差异**是「同一份逻辑、同一份数据在系统里存在几份」。实现份数决定口径会不会漂移与改一次要改几处；数据份数与契约决定换引擎是否要迁数据；派生状态的份数决定长期运维成本落在谁头上。其余维度（实时性、成本、AI 友好度）都是这条差异在不同约束下的投影，因此不该被当成独立判据。
