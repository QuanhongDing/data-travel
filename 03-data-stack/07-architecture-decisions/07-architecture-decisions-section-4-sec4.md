## 4. 工程实现

本节按「落地步骤 → 关键技术点 → 工具链 → 存量迁移 → 模板 → 自检」组织，术语与主文件 [§2 核心原理](07-architecture-decisions.md) 和 [§3 设计模式与范式](07-architecture-decisions-section-3-sec3.md) 逐字一致：**口径的物理路径条数**、**全量重算的载体**、**决策带宽**、**重评触发条件**、**结果级校验**这几个词，在本节里指的就是 §3 里那几条结构，不另立口径。模式被什么约束逼出来、代价与失效点见 §3；本节只回答「选定之后怎么装进去」。

读者分两类，本节两栏都覆盖。**从零搭建**的组织直接按 4.1 的六步往下走，4.4 可以略读。**在存量上改造**的组织（已经有 Lambda 双链路、已经有按目录约定写的作业、已经有若干份 ADR）建议先读 4.4 再回到 4.1——因为存量组织最贵的成本不是把新架构搭起来，而是让旧链路、旧契约与旧决策记录在新架构下仍然可解释，而这件事的顺序与从零搭建完全不同。

### 4.1 落地步骤

**Step 1：业务需求分析（2-4 周【经验】，工时随业务域数量增长）**

1. 把每个业务域的需求落成五个**可计量**的问题：时效（结果必须在多久内可见）、规模（当日增量与最长需重算的历史窗口，单位是天）、一致性（是否要求某个历史时点的结果能被**独立复现与审计**）、AI 消费（有没有机器消费者要先读元数据再读数据）、成本（当前单价与预算上限）。
2. 记下每个取值**来自哪个系统**（调度日志 / 账单 / 合规清单 / 监控），而不是记「大概」「看情况」。
3. 单独记一列：**同一业务结论当前由几条物理路径产出**（1 条还是 2 条）。这一列是后面所有决策的分母。

- **产物**：一份需求基线表，一行一个业务域，列为上述五项 + 路径条数 + 取值来源。
- **判据**：抽 3 个业务域追问两个问题——「最长需重算的历史窗口是多少天」「这个结论现在有几份实现」。答案必须是数字与数字，出现「视情况而定」即该行未填完；再把五项的取值与来源系统对一次，来源栏为空的行按未填处理。
- **为什么必须第一步**：§3.1 的三条主约束（路径条数、重算载体、谁做决定）在这里取到具体值，Step 2 决策矩阵的**权重**直接由它决定。跳过这一步，权重只能靠评审会拍，而拍出来的权重无法复核——这正是 §3.5「决策无据」的成因。

**Step 2：架构选型并输出 ADR（1-2 周【经验】）**

1. 用 [§3.3 模式选择决策表](07-architecture-decisions-section-3-sec3.md) 逐行核对约束组合，先定位候选集，再用决策矩阵在候选集内打分。
2. 矩阵的权重从需求基线表取，不从评审会取；打分只用于**暴露分歧**，不用于代替判断。
3. 输出 ADR：背景 / 决策 / 后果 / 备选方案，外加**后果一栏必须有的重评触发条件**（时效要求变化、路径份数从 1 变成 2、某个派生副本刷新滞后持续越线、成本占比越线）。
4. ADR 进版本库、走 PR 评审；同一决策的多次修改保留历史版本，不覆盖。

- **产物**：一份带版本号的 ADR，含备选项各自的「不选它的代价」与一条可观测的重评触发条件。
- **判据**：抽 3 份 ADR，做两个动作——① 看「后果」一栏能不能指出「在什么观测值变化时应该重评」；② 问一个反事实问题「为什么不用另一个方案」，答案必须落在机制上（例如「纯 Kappa 的重放窗口覆盖不上监管要求的最长需重算窗口」），答成「经验上这样更稳」即不合格。
- **为什么必须排在 POC 之前**：POC 证明的是「某个引擎能不能承载这套约束」，它无法证明「哪个范式对」。顺序反了，POC 会把架构倒推成它擅长的那一种——跑得通的那条路径成为结论，而跑得通与否取决于数据量与团队熟悉度。

**Step 3：技术选型与 POC（2-4 周【经验】，随候选引擎对现有算子的支持度变）**

1. 存储 + 计算 + 查询三层分别选（见 4.3 的选型判据），每层保留一个降级候选。
2. POC 用与生产**同量级的采样数据**，不用玩具数据：小数据量下多数反模式都能跑通。
3. 每个候选至少产出三个数：**写事务提交 p99 与失败重试率**、**同一指标在批视图与流视图之间的差异条数**、**单位算力成本**（按自己的单价折算，不引用厂商口径）。
4. 写下「POC 不通过就退回哪一档」的判据。

- **产物**：一份 POC 报告，含上述三个数与一份降级方案（主选失败时回到哪条路径）。
- **判据**：看报告里有没有一条**能证伪主选方案**的判据。若通篇结论只有「跑通了」，说明这份 POC 无法证伪任何方案，应补一项压力测试（写事务并发提交、迟到数据比例、跨引擎并发读同一张表）。
- **为什么必须排在 ADR 之后**：POC 的输入是 ADR 里的约束，输出是「这套引擎在这套约束下是否成立」；没有 ADR 时 POC 变成「哪个跑得快选哪个」，而快慢依赖数据分布，换一个业务域结论就反转。

**Step 4：架构落地（4-12 周【经验】，随首个业务域的表数量与依赖深度变）**

1. 按**业务域**分阶段，不按组件分阶段：一个业务域端到端打通（接入 → 契约 → 分层 → 消费）之后再动下一个。
2. **契约先于数据**：表格式与元数据登记在第一个消费方接入之前就位，哪怕此时只有一个引擎在读。
3. 灰度用双链路并行：新链路按分区产出，与旧链路**按分区级聚合值对账**，差异可解释才扩大范围。
4. 每个阶段留一个回滚点，并把回滚动作写进发布清单。

- **产物**：一套分阶段的发布清单（每阶段含回滚点）+ 一份分区级对账脚本。
- **判据**：第一个业务域上线后，抽样一天，看同一指标在旧链路与新链路上的分区级聚合值差异是否为 0；不为 0 时，差异能不能用日志解释（迟到数据、口径变更时间点）。解释不清就停在当前范围，不扩大。
- **为什么必须分阶段、且契约在前**：§3.2.3 的失效点是元数据服务成为全局争用点，一次性全量迁移会把写事务提交压力压在同一个时间窗内；而契约缺失时下游会按目录约定写作业——这类作业**不报错、只读到不该读的分区**，迁移面在发现之前一直在放大。

**Step 5：治理与监控（持续，从第一次上线开始）**

1. 最小治理面（Owner、粒度声明、血缘、密级）与架构上线**绑在同一次发布**里，不排进「二期」。
2. 监控按「业务结果是否正确」建，不按「进程是否存活」建：每层至少一条结果级校验（行数、主键唯一、分区聚合值对账），再加**派生副本刷新滞后**与**元数据的最后更新时间**。
3. 血缘覆盖接入作业与查询日志，字段级优先于表级。

- **产物**：一份结果级校验清单（每层至少一条）+ 一张核心表的元数据登记（Owner / 粒度 / 血缘 / 密级四格都有值）。
- **判据**：抽 3 张核心表，看能否用一条查询回答「它由谁负责、上游是谁、上次刷新是什么时候」。三个都答不出即治理面未落地；再打开监控看有没有任何一条告警是**基于结果**的（只有进程存活率的，等于没有）。
- **为什么必须在第一次上线就做**：§3.5「忽视治理」的机制——治理要素（Owner、口径、血缘）在上线后再补，需要重新盘点历史资产；而「缺乏可观测」的暴露方式是**沉默**：任务全部成功、监控全绿，业务方在两天后才发现数字不对。

**Step 6：定期 Review 与证据级别回填（季度【经验】）**

1. 按 ADR 里的重评触发条件逐条核，把观测值的实际数字抄进复查记录。
2. 对每一个正在依赖的前沿方向回填一次证据级别（**L1 / L2 / L3**，三条判据见 [§5.1](07-architecture-decisions-section-5-ai.md)）；某个 L2 方向若一年内仍拿不到自己组织里的实测数字，降 L3 并停止投入。
3. 结论只有两种：沿用，或更换；更换时必须附上迁移代价的对照（[§7.7](07-architecture-decisions-section-7-sec7.md) 的迁移矩阵按「数据迁移 / 查询改写 / 运维重建 / 团队再学习」四列给出量级）。

- **产物**：一份复查记录，含触发的条目、观测值、结论，以及（若更换）迁移代价四列。
- **判据**：拿上一次的复查记录问「这次复查改变了什么决定」。连续两次结论都是「无变化」，说明重评触发条件写得不可观测，应重写 ADR 的这一栏，而不是继续每季度开会。
- **为什么必须排在最后且周期固定**：§3.6 的结论是——触发换模式的从来是结构性矛盾，不是数据量；结构性矛盾只会在监控里以具体量出现。把「何时重评」写进 ADR，是唯一让它不依赖某个人记得的方式。

**最常被跳过的是 Step 1**。写需求基线表是缓慢、不产生当期交付物的工作，而 ADR、POC、灰度都是当期可见的动作，于是前者被系统性地推迟。跳过之后**第一个出问题的时点通常不是当季**，而是第一次口径变更：团队发现「同一指标有两份 SQL」这件事没人知道（Step 1 的路径条数问题没有答案），于是变更要同时改两条链路，还要重新议一次对账口径——这笔账在 §3.2.1 的代价里已经写好，只是延迟到期。

### 4.2 关键技术点

**1. 决策矩阵**

- **做法**：四行（Lambda / Kappa / Lakehouse / 流批一体）× 五列（时效、一致性、成本、复杂度、AI 友好度）打分；权重来自 Step 1 的需求基线表；打分结果只用于暴露分歧（见 4.5 模板 1）。
- **机制**：因为打分把**不可比的东西**强行放进同一把尺子，所以矩阵的价值不在分数高低，而在**逼出权重**——写权重时团队必须回答「时效与成本谁优先」，而这个回答是可复核的、下次可以拿来对照的。
- **失效条件**：当权重来自「评审会共识」而不是观测值时失效。**症状是同一份需求在两次评审里得到两个不同的推荐架构**，或矩阵结论与「不选它的代价」一栏互相矛盾。另一个可观测信号：所有候选的总分落在很窄的区间内【经验】，说明权重对结论不敏感，矩阵没有在区分任何东西。
- **档位**：分值为团队自评【经验】；权重必须来自 Step 1 的观测值。

**2. Medallion 分层落地**

- **做法**：Bronze 原样落地、可重放；Silver 清洗整合、口径收敛、关联维度；Gold 聚合成宽表与指标；每层写独立 Owner、SLA 与回滚点（DDL 见 4.5 模板 2）。
- **机制**：因为每层都是**物理落盘**，所以重跑 Silver 不污染 Bronze、重跑 Gold 不污染 Silver，回滚点天然存在；同时口径只能收敛在 Silver 一层之内，这限制了「同一指标多个算法」的扩散范围。
- **失效条件**：当业务节奏快过分层调度频率时失效。**症状是端到端新鲜度等于各层周期之和**，而不是最慢的那一个——数据看起来是对的、其实已经旧了。可观测信号：把各层调度间隔相加，与该指标的业务容忍窗口相比，比值逼近 1 时减层，或给对新鲜度敏感的链路开一条直通分支。
- **档位**：层数与保留期为【经验】，按业务容忍窗口定。

**3. 流批一体（同一份 SQL 两种执行模式）**

- **做法**：同一份表达式，有界输入换无界输入；**保留一条低成本的抽样对账**（例如每日比对一次分区级聚合值，不做全量）。
- **机制**：因为统一的只是表达式与优化器，执行层（状态后端、水位线、checkpoint、shuffle）仍是两套，所以「一份代码」把差异来源收窄成一份可枚举的清单（水位线、状态 TTL、排序），而不是消灭差异。
- **失效条件**：当团队因为「一份代码」而删掉对账时失效。**症状是迟到数据在两种执行模式下的归属不同**——差异只出现在有迟到数据的分区上。可观测信号：分区级聚合值的差异条数不为零且长期存在；此时正确动作是补回抽样对账，而不是把差异归因为「数据质量问题」。
- **档位**：对账频率为【经验】。

**4. 契约先于数据（表格式 + 元数据登记）**

- **做法**：第一个消费方接入之前就把表格式与元数据登记就位，schema 变更与数据写入提交在同一事务里；下游只允许按表名读写，不允许按存储路径读写。
- **机制**：因为 schema 变更与写入提交同事务，所以「目录里的结构」与「数据真实的结构」不可能不一致；反之，按目录约定写的作业不会报错，只会继续读到不该读的分区——**错误形态是静默的**。
- **失效条件**：当第一个消费方已经在读文件时失效。**症状是这类迁移没有报错、没有测试失败，只有数字错**。判据：随机抽 3 个下游作业，问它读的是表名还是存储路径；路径占比高，说明必须先解决「谁在读文件」再谈迁移。
- **档位**：无。

**5. 元数据服务的高可用与提交吞吐**

- **做法**：把 catalog 元数据库当作与线上库同等级的依赖来规划（容量、高可用、备份与恢复演练）；写入侧批量提交、降低提交频率、控制小文件数量。
- **机制**：因为写事务最终要串行化提交到 catalog 的元数据表，所以它的可用性就是全平台的可用性，提交吞吐是全局约束——这是 §3.2.3 失效点的机制表述。
- **失效条件**：当写并发升高、多个引擎同时对同一张表提交时失效。**症状是写事务提交 p99 上升、失败重试率上升，同时小文件数量增长**，维护作业（快照过期、manifest 重写、小文件合并）从偶发变成常驻。可观测信号就是这三个量，它们都能从现有监控直接取到。
- **档位**：阈值按自己的 catalog 与提交模式实测，不设通用数字。

**6. 结果级校验**

- **做法**：每层至少一条结果级校验（行数、主键唯一、分区聚合值对账），并把**派生副本的刷新滞后**与元数据的最后更新时间做成指标。
- **机制**：因为故障可发生在任意一层，进程级监控全绿时数据仍可能已经旧了；唯一能发现这种沉默失效的是**基于结果**的校验，而不是更多进程指标。
- **失效条件**：当校验只建在入口层时失效。**症状是任务全部成功、监控全绿、业务方两天后发现数字不对**。修法是给每一层都补一条，而不是给入口层加更多告警。
- **档位**：无。

### 4.3 工具链与平台

工具表给的是**类别、候选与选型判据**，不是推荐组合。某产品是否仍以表中的能力在售、某个能力条目是否属于正式功能，以该项目或厂商官方文档与 release note 的当前版本为准。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 批层与批计算 | Hadoop、Hive、Spark | 存量作业与调度依赖在哪一边；迁移收益是否大于改写成本 | 换引擎等于重写全部批作业，且改写期两条链路都要养 |
| 流层与流计算 | Kafka、Flink、Spark Streaming（Kafka Streams） | 是否需要端到端精确一次、状态规模有多大、团队能否运维有状态作业 | 有状态作业缺运维能力时会被绕过，绕过的方式通常是「先落库再批处理」 |
| 服务层与 OLAP | Druid、HBase、Pinot、StarRocks、Doris、ClickHouse | 点查还是聚合、并发量级、是否要求行级更新 | 用点查引擎扛聚合查询时，延迟随并发下降的斜率最陡 |
| 日志与可重放存储 | Kafka + Tiered Storage、Pulsar | **最长需重算窗口**是否长期短于保留期与重放吞吐 | 缩短保留期就直接削减了可重算的历史长度（§3.2.2 的失效点） |
| 表格式 | Iceberg、Hudi、Delta、Paimon | 判据只有一条：换一个引擎能不能**直接读同一张表**；再看所需能力（流读、行级更新）在该格式规范里是不是正式条目 | 锁定在单一引擎后，多引擎共读要重建一份导出链路 |
| 交互查询引擎 | Trino、StarRocks、Doris | 是否要跨源联邦查询、是否要读写同一张湖表 | 只读引擎无法承担写路径，增量链路要另建一套 |
| Catalog 与元数据服务 | Hive Metastore、Glue、Polaris、Unity Catalog | 迁移成本与并发提交能力；是否支持多引擎并发写同一张表 | 它是所有写事务的汇聚点，选错后要迁移的是**所有表的元数据**（迁移面与量级见 [§7.7](07-architecture-decisions-section-7-sec7.md) 迁移矩阵中「无表格式的湖 → Lakehouse」一行的「数据迁移 / 运维重建」两列） |
| 流批一体组合 | Flink + Paimon / Iceberg / Hudi；Spark Structured Streaming + Delta / Iceberg | 统一引擎对现有算子的支持范围（不支持的要改写） | 支持范围不够时，改写的算子会成为两套实现的新来源 |
| 决策与记录工具 | ADR 模板（Git + Markdown）、决策矩阵（Python + 评分模型）、AI 辅助决策（LLM） | 产出物能否**静态校验**（模板必填栏）、能否带版本进库 | 无固定模板时决策记录散在会议纪要里，事后无法归因 |

**这一类里最容易被误选的是「表格式 + Catalog 这一组」**：团队按「哪个社区最热、哪家云主推」选，而判据其实是「换一个引擎能不能直接读同一张表」。误选的典型后果不是性能问题，而是**迁移面**——一旦下游按目录约定写完作业，再补契约就要连同所有消费方一起改，且这类迁移的错误形态是静默的（4.2 第 4 条）。同理，判断某个引擎是否真的支持某项能力，只看一处：该版本的 release note 或官方文档里有没有对应条目；项目路线图页、benchmark 博客、生态伙伴的转述都不算（判据同 [§5.1](07-architecture-decisions-section-5-ai.md)）。

### 4.4 存量迁移

存量组织的迁移目标不是「换成新架构」，而是**让旧链路、旧契约与旧决策在新架构下仍然可解释**。下面四步按「可回退 → 分类 → 双轨 → 收口」排，最后一组是这一步最常见的三个错误。

**① 先做一次只读盘点（2-3 周【经验】，完全可回退）**

在不改动任何链路的前提下，用现有日志与监控跑三张表：每个业务域的**同一指标物理路径条数**；**最长需重算窗口**与当前日志保留期、快照保留期的对照；**写事务提交 p99 与失败重试率**的近三个月趋势。这一步不产出架构，只产出一次**事实基线**——它的价值是后面每一步都能对回这份基线；它可回退，是因为结论不进任何人的考核，只作为设计输入。

**判据**：拿三张表分别去问两位互不相干的架构师「哪一条链路最危险」，两人给出同一条，说明现有数据已足够支撑讨论；给出不同答案，说明约束的观测口径还没统一，先回到 Step 1。

**② 历史资产分类处理（不要全部返工）**

| 存量资产 | 处置 | 理由 |
| --- | --- | --- |
| 按目录约定写的湖作业 | **打标挂账**：先登记为外部表，只给新分区补元数据；旧分区标「未登记」并统计消费方数量 | 全量重新登记等于一次全量重写，而下游在此期间会继续按目录约定写新作业 |
| 已有的 Lambda 双链路 | 只改「下一次变更会触发」的部分：口径下一次变更时收敛成一份实现，其余不动 | 全部返工等于把过去积累的口径历史重做一遍，且期间没有对照基线 |
| 已有的 ADR 与架构文档 | 不回改，作为新 ADR「重评触发条件」一栏的**回测集**：用新条件回看 3-5 个历史决策 | 回改历史记录等于宣布过去的结论无效，代价是一次无法真正补偿的信任支出 |
| 已有的派生副本（向量索引 / 特征视图 / 投影） | 先补两个指标（刷新滞后、最后更新时间），观测一个周期再决定是否重建 | 没有滞后数据时，「要不要重建」只能靠印象 |

**判据**：随机抽 3 个下游作业，看它读的是表名还是存储路径——路径占比高，说明静默失效面大，应先解决「谁在读文件」，而不是先上表格式。

**③ 双轨怎么维持、维持多久**

双轨的形态是：**新链路承接新消费方，旧链路维持现有消费方并对账**；两侧按分区级聚合值比对，差异逐日归档。维持 **1-2 个口径变更周期**【经验，随口径变更频率变——季度级变更时约 3-6 个月】。

双轨期有三条纪律：① 不比较两条链路的绝对延迟或绝对耗时（载体不同，比较没有意义），只比对账差异；② 口径变更**只改一处**，并在双轨期内两侧同步验证，不允许「先改新链路、旧链路下次再说」；③ 旧链路的产出降级为**只读参考**，禁止新消费方接入——这一条是双轨能在有限时间内结束的前提。

**④ 什么信号说明可以退出双轨**

三个可观测信号，同时出现两个即可收口：① 连续两个口径变更周期，两侧分区级聚合值差异为 0 且可解释；② 访问日志显示没有新的消费方接入旧链路；③ 旧链路的**下线演练**做过一次（关停一个周期，看有没有人报警）。

若两个周期后三个信号全不成立，正确的动作是**回到 Step 1 重取约束值**，而不是继续双轨：双轨的隐性成本是所有人都说不清「哪条链路是权威」，它比架构暂时落后更伤下游信任。

**⑤ 迁移期最常见的三个错误**

1. **把灰度做成「两条链路都对外供数」。** 消费者会在两条之间各取所需，缝合线以「纠偏」的名义回来，却没有任何机制保证两侧的权威关系——这比显式 Lambda 更差，因为显式 Lambda 至少知道自己的缝合线在哪（[§7.7](07-architecture-decisions-section-7-sec7.md)）。
2. **先搬数据、后补契约。** 下游已经按目录约定写完作业，迁移面被放大；补契约的过程等于一次全量重写与重新登记。
3. **只迁移引擎、不迁移重算能力。** 新链路跑通后才发现「最长需重算窗口」超出了新载体的保留期（Kappa 的失效点），此时补建批层不是优化，是返工。

### 4.5 模板 / 示例

**模板 1：架构决策矩阵**

```python
# decision_matrix.py —— 权重必须来自需求基线表（4.1 Step 1），不来自评审会
import pandas as pd

ARCHITECTURES = {
    # 键为候选项，值为各维度自评分（1-5，团队自评【经验】）
    'Lambda':                {'real_time': 4, 'consistency': 5, 'cost': 3, 'complexity': 3, 'ai_friendly': 2},
    'Kappa':                 {'real_time': 5, 'consistency': 4, 'cost': 5, 'complexity': 4, 'ai_friendly': 3},
    'Lakehouse':             {'real_time': 5, 'consistency': 5, 'cost': 5, 'complexity': 4, 'ai_friendly': 5},
    'Stream-Batch-Unified':  {'real_time': 5, 'consistency': 5, 'cost': 4, 'complexity': 5, 'ai_friendly': 4},
}

def architecture_decision(weights):
    df = pd.DataFrame(ARCHITECTURES).T
    df['score'] = df.apply(lambda r: sum(r[d] * weights[d] for d in weights), axis=1)
    df = df.sort_values('score', ascending=False)
    spread = df['score'].max() - df['score'].min()
    if spread < 0.2:                      # 【经验】阈值：结论对权重不敏感
        print(f'[warn] top1 与 last 相差 {spread:.2f}，矩阵没有区分度，先回来重取权重')
    return df

# real_time 与 consistency 两项建议由「最长需重算窗口」与「时效要求」直接推
print(architecture_decision({
    'real_time': 0.3, 'consistency': 0.3, 'cost': 0.2, 'complexity': 0.1, 'ai_friendly': 0.1,
}))
```

**怎么用**：只填 `ARCHITECTURES` 的五列自评分与 `weights` 五项权重；**权重一栏不要照抄示例值**，它必须逐项对到需求基线表的取值——对不上就说明 Step 1 没做完。输出里唯一要看的不是排序，而是 `[warn]` 那一行是否触发：触发了说明这份矩阵当前不能支撑决策，应先把权重与评分口径定清，而不是硬选第一名。

**模板 2：Medallion 三层 DDL 骨架**

```sql
-- Bronze：原样落地，可重放，保留原始列
CREATE TABLE bronze.orders (
  order_id     BIGINT      NOT NULL,
  user_id      BIGINT      NOT NULL,
  amount       NUMERIC(18,2),
  order_time   TIMESTAMPTZ,          -- 业务发生时间
  _ingested_at TIMESTAMPTZ NOT NULL  -- 入库时间：重放与排查边界
) PARTITIONED BY (day(_ingested_at));

-- Silver：清洗整合 + 口径收敛（同一指标的不同算法只在这一层出现）
CREATE TABLE silver.orders AS
SELECT order_id, user_id, amount, order_time,
       COALESCE(u.user_name, 'unknown') AS user_name   -- 维度填充
FROM   (SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id
                                     ORDER BY _ingested_at DESC) AS rn
        FROM   bronze.orders
        WHERE  order_id IS NOT NULL) o                  -- 有效性收敛：主键非空
LEFT JOIN silver.user_dim u ON o.user_id = u.user_id
WHERE  o.rn = 1;                                        -- 去重：同一 order_id 只留最新一版

-- Gold：面向应用的聚合，可随时从 Silver 重建
CREATE TABLE gold.user_daily_orders AS
SELECT user_id, day(order_time) AS dt,
       SUM(amount) AS gmv, COUNT(order_id) AS orders
FROM   silver.orders
GROUP BY user_id, dt;
```

**怎么用**：只照抄**三层的职责划分**与 `_ingested_at` 这一列，列名与分区键按自己的现状改；三层各自要补的是 Owner 与 SLA（表注释里写），不是更多字段。两个 `WHERE` 里的收敛与去重条件不要照抄——去重键与「保留最新一版还是最早一版」取决于自己的业务口径，照抄会把与业务无关的过滤条件一起带进生产。

**模板 3：流批一体（Flink + Paimon）**

```java
// 同一份代码两种执行模式；注意：统一的是表达式与优化器，不是执行层
TableEnvironment tEnv = TableEnvironment.create(EnvironmentSettings.inStreamingMode());

tEnv.executeSql("""
    CREATE TABLE paimon_orders (
      order_id BIGINT,
      user_id  BIGINT,
      amount   DECIMAL(18, 2),
      ts       TIMESTAMP(3),
      PRIMARY KEY (order_id) NOT ENFORCED
    ) WITH ('connector' = 'paimon', 'path' = 's3://lake/paimon/orders')
""");

// 流模式：无界输入，持续更新
tEnv.executeSql("INSERT INTO paimon_orders SELECT * FROM kafka_orders");

// 批模式：有界输入，同一份表达式换一个输入
Table batch = tEnv.from("paimon_orders")
    .filter($("ts").between("2025-01-01", "2025-01-31"))
    .groupBy($("user_id")).select($("user_id"), $("amount").sum());
```

**怎么用**：`PRIMARY KEY ... NOT ENFORCED` 与 `connector` 两项按自己的表格式与版本改（具体支持情况以所用引擎与表格式的官方文档当前版本为准）；两个 `executeSql` 之间**不要共用状态配置**——水位线与状态 TTL 是两种模式产生差异的地方，配置要分别写明并各自记录在案。这段代码的用途是演示「一份表达式两种输入」，不是可直接上线的作业骨架。

**模板 4：ADR 模板（含重评触发条件）**

```markdown
# ADR-001: 选择 Lakehouse 而非 Lambda

- 业务需要：{实时数仓 / 历史分析 / AI 训练}

  路径条数现值 = {1 / 2}；来源：{调度日志 / 合规清单 / 账单}
- 团队现状：{有状态流作业运维能力：有 / 无}

## 决策
- 采用 {架构范式}；存储 / 计算 / 查询 / 治理四层分别写明所选与其版本

## 备选方案与不选它的代价
- 选项 A: Lambda —— 代价：{同一口径两份实现 + 一个合并点，对账义务永久化}
- 选项 B: Kappa —— 代价：{重算能力托付给日志保留期，最长需重算窗口覆盖不上}
- 选项 C（选中）: Lakehouse —— 代价：{catalog 成为全局争用点；元数据与小文件维护成为常驻任务}

## 后果
- 优点 / 缺点 / 风险各一条，指向具体的观测对象

## 重评触发条件（每条都要能从监控取到）
- 时效要求从 {T+1} 变为 {分钟级}
- 同一指标物理路径条数从 1 变为 2
- 写事务提交 p99 连续 {N} 天高于 {阈值}，或失败重试率上升
- 某个派生副本刷新滞后连续 {N} 天超过业务容忍窗口
- 成本占比越线：{某项} 占平台总成本超过 {x}%

## 演进路径
- Q1: POC + 培训　Q2: 首个业务域上线　Q3: 扩大范围（按业务域）　Q4: 优化 + AI 消费方接入
```

**怎么用**：必填的是「约束取值及其来源」与「重评触发条件」两块，其余可精简；触发条件一栏**不要照抄行文**，每一条都要能指到一个现有监控项——指不到的删掉，否则季度 review 会退化成「看一眼架构图」。`{}` 里是待填项，不是示例值；`状态` 一栏在决策被推翻时改为 `Superseded by ADR-00N`，不要删除旧文件。

### 4.6 成本：这套东西的账单

这个主题的账单有一个反直觉的结构：**做决策本身几乎不花钱，钱都在决策定下之后才花出去**。一份 ADR 是版本库里的一个 Markdown 文件，成本趋近于零；它锁定的是后面几个月谁要重写作业、哪条链路要长期对账。

**人力：流程工时是可估算的一次性投入。** 4.1 六步的区间相加为 9–22 周【推算：Step 1 的 2–4 周 + Step 2 的 1–2 周 + Step 3 的 2–4 周 + Step 4 的 4–12 周，逐项取自 4.1 各步自己标注的【经验】区间，季度复查的持续人力未计入】。这笔投入在 Step 4 之前不产出可交付物，因此最容易被压成「跳过 Step 1 直接上 POC」——它的代价不体现在当期，而体现在第一次口径变更（4.1 末段）。

**云账单：本主题多出来的一项叫「回补」。** 平台上线后的经常性账单由所选架构的存储 / 计算 / 查询三层决定，通用拆解与单价口径见 [成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)；这个主题自己独有的成本项是**历史回补**——口径错误或迟到数据出现时要重跑的算力与读放大。其量级由两个约束相乘得到：`回补成本 ∝ 最长需重算窗口(天) × 日增量(GB) × 单次重算的扫描放大量`【推算，公式；前两个因子分别取自 Step 1 需求基线表的「最长需重算窗口」列与当日增量，扫描放大量按自己 Catalog 与表格式实测，不设通用数字】。架构越「单层」（纯 Kappa），这个窗口越容易被保留期卡住，回补就从「贵」直接变成「做不到」（4.4 第⑤组错误第 3 条）。

**为什么贵在这里，而不是贵在许可证。** 表格式、Catalog、流引擎多为开源件，授权费趋近于零；贵的是**一次决策的后果面**：同一指标多一条物理路径，就多养一条常设对账（4.4 双轨纪律）；按目录约定写的存量作业不报错、只静默读错分区（4.2 第 4 条），修它的成本是重新盘点「谁在读文件」。这个主题的成本不在工具 SKU 上，而在**这次决策把多少未来变更绑定成了返工**。

### 4.7 容灾与故障演练

这个主题的「灾」不在机房，而在**决策与元数据**两处；跨地域多活对「一份 ADR」不成立，真正需要冗余的只有 Catalog，其通用方案见 [容灾与多活](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)，这里只写本主题特有的三种失效。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| **决策不可复现**：ADR 没记「约束取值及来源」，结论随人走 | 该业务域的下一次口径变更要么改错一处、要么两条链路重议 | 回填 Step 1 需求基线表，用现有监控现值重建权重 | 抽一份历史 ADR，让两位工程师独立按「后果」一栏的触发条件复现推荐结论，看两人是否一致 | 不设 RTO——这是一次性返工，不是可用性指标 |
| **Catalog 不可用 / 元数据丢失** | 全平台**写**路径停摆（4.2 第 5 条：catalog 可用性即平台可用性）；只读查询可继续 | 切只读模式：已有表可读、冻结写入与 schema 变更 | 在隔离环境用备份恢复一次元数据库并计时；顺带验证「按路径读」的作业在只读期是否报错 | RTO【经验】分钟到小时级，取决于备份频率与元数据库规模；RPO 取最近一次快照间隔【经验】 |
| **静默失效**：下游按存储路径读，迁移后读到不该读的分区 | 数字错但不报错、监控全绿，业务方滞后发现 | 回退到旧链路的只读参考副本，同时跑分区级对账定位差异 | 把分区级聚合值对账做成常驻任务，并定期注入一条错分区看它是否报警 | 恢复时点 = 对账发现的时点，发现得越晚越贵 |

**不适用跨地域容灾的部分**：本主题的「决策」产物是版本库里的文本，天然多地多副本，不需要、也不该为它建多活。真正的跨域要求落在 Catalog 与表格式快照上——那是 [容灾与多活](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md) 与 [混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md) 的题，本文不重复通用方法。

### 4.8 演进路线：0 → 1 → 100

**0 → 1（写下约束，跑通一个业务域）**：产出一份需求基线表、一份带触发条件的 ADR、一个业务域端到端上线。这一步**变贵的是「把取值写下来」的工时**（Step 1，且不产出可交付物），**先坏的也正是它**——跳过时不会当季报错，会在第一次口径变更时一次性还账（4.1 末段）。判据：能否用一条查询回答三张核心表的「谁负责 / 上游是谁 / 上次刷新」。

**1 → 100（多业务域、治理与 Catalog 规模）**：按业务域复制落地流程，把最小治理面（Owner / 粒度 / 血缘 / 密级）绑进每次上线，Catalog 从「能跑」升级为「要按线上库等级运维」。这一步**变贵的是元数据服务的提交吞吐与运维**（小文件合并、快照过期从偶发变常驻），**先坏的是 Catalog**：写事务提交 p99 与失败重试率上升、小文件同增（4.2 第 5 条）。判据：写并发升高时提交 p99 是否稳定、结果级校验是否每层都有。

**100 →（结构性矛盾触发范式切换）**：触发换模式的从来是结构性矛盾（如时效要求从 T+1 跨到分钟级），而不是数据量涨了（§3.6）。这一步**变贵的是迁移**——按「数据迁移 / 查询改写 / 运维重建 / 团队再学习」四列计价（[§7.7](07-architecture-decisions-section-7-sec7.md)）；**先坏的是最长需重算窗口**：新载体的保留期覆盖不上要求的历史长度，此时补建批层不是优化而是返工（4.4 第⑤组错误第 3 条）。这也是 ADR「重评触发条件」一栏最该写全的一条。

### 4.9 自检清单

1. 打开最近一份 ADR，看「后果」一栏有没有重评触发条件；没有，说明这次决策只会发生一次。
2. 数一遍每个业务指标的**物理路径条数**（1 还是 2）；超过 1 的，有没有一条**常设**对账（不是一次性的迁移比对）？
3. 查「最长需重算的历史窗口是多少天」，与当前日志保留期、快照保留期对一次账；覆盖不上时，是哪一份存储承担长期历史？
4. 抽 3 个下游作业，问它读的是表名还是存储路径——路径占比高，说明迁移的错误形态是静默的。
5. 打开监控，找出至少一条**基于结果**的校验（分区聚合值对账 / 主键唯一 / 派生副本刷新滞后）；全部都是进程存活率的，等于没有。
6. 抽 3 张核心表，能否用一条查询回答「谁负责、上游是谁、上次刷新是什么时候」？
7. 写事务提交 p99 与失败重试率是多少？最近三个月是不是在上升？小文件数量是否同步增长？
8. 上一次架构复查是什么时候、结论改变了什么决定？连续两次「无变化」就要重写 ADR 的触发条件。
9. 对每个正在依赖的前沿方向记一次证据级别（L1/L2/L3，判据见 [§5.1](07-architecture-decisions-section-5-ai.md)）；L2 超过一年拿不到自己组织实测数字的，降级并停止投入。
10. 若在用分层：把各层调度间隔相加，与该指标的业务容忍窗口比一比；比值逼近 1 时，减层或给敏感链路开直通分支。
11. 若在用流批一体：抽样对账还在跑吗？把它删掉，第一次出现批流差异会从哪里被发现？
12. 元数据服务（catalog）的备份与恢复演练做过吗？它的 RTO 是否写进了平台的 SLA？

### 4.10 小结

> 本节小结：六步里唯一不可替代的是 **Step 1 把约束的取值写下来**——ADR、POC、灰度、监控全部建立在这份取值上，它缺失时其余五步不会立即报错，而是在第一次口径变更或第一次历史回补时一次性还账。它比其余环节更值得投入，是因为**它把「选哪个架构」从评审会的判断换成了可对照的观测值**：一旦「最长需重算窗口」「路径条数」「写事务提交 p99」被写下来，争论对象就从「谁的经验更可信」移到了「哪条约束不满足」，后面所有环节的返工量才会下降。
>
> 💡 **思考锚点**：打开你最近一份 ADR，按 §4.9 第 2、3 条量两个数——每个业务指标的物理路径条数（1 还是 2）、最长需重算的历史窗口是多少天——再把后者和你当前的日志 / 快照保留期对一次账；对不上的那条约束，是不是就是你下一次历史回补时要一次性还的账？
