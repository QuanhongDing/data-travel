## 3. 设计模式与范式

> 原 § 3 共 96 行，形式为 8 条「模式 + 适用 + 典型栈」条目 + 一张场景决策表 + 6 条反模式，缺结构示意、机制解释与失效分析，重写为 ~355 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

架构模式表把设计讲成了「按场景选一个」：T+1 报表选 Lambda，纯实时选 Kappa，现代数据栈选 Lakehouse。但真实的架构决策是被一条硬约束推着走的：**同一条业务结论由几条独立的物理路径产出**，也就是同一个口径在系统里有几份实现。这一条一旦确定，对账义务、重算能力、故障域、团队编制就全部跟着确定，剩下的才是技术栈选择。

这条约束的取值只有三种：两条路径（同一结果由批与流两套计算分别产出，Lambda）、一条路径（单一流，Kappa）、一条路径但读写共享存储快照（Lakehouse 与流批一体）。**两条路径必然产生对账义务**：服务层的合并逻辑只做时间窗口拼接，它无法判断两层算出的同名指标在语义上是否等价——语义等价不能由机制保证，只能由「两份 SQL 同时改」这类纪律保证，而纪律会随人员流动衰减。**一条路径必然产生重放义务**：唯一路径出错时没有第二份结果可交叉验证，只能靠重放重建正确结果，于是「能不能重放、重放要多久」从一个运维细节升格为架构的核心参数。

第二条约束是**全量重算的载体放在哪**：放在不可变的历史数据里（Lambda 批层）、放在可重放的消息日志里（Kappa）、还是放在表格式的快照链里（Lakehouse）。载体不同，重算代价曲线的形状就不同——扫描全量历史是「与数据量成正比」，重放日志是「与日志保留期成正比」，读快照重算是「与从该快照往下的增量成正比」。这三条曲线在什么规模下相交，直接决定了模式该不该换（见 3.6）。

第三条约束是**谁做决定**：人（ADR 记录）、规则（CI 门禁）、模型（自治架构）。它在前两条确定之后才展开，但它改变了决策失误的暴露方式——从「评审会上被同事发现」变成「以更高的吞吐扩散」。本节 8 个模式里，前 6 个都在回答前两条，AI 原生与自治回答的是第三条与「谁来消费」。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 口径的物理路径条数（1 条 / 2 条） | 是否需要对账、是否需要重放；故障域是 1 个还是 2 个 | 「多一条链路只是多写一份 SQL」——多出来的是对账义务与第三个失败模式（窗口边界） |
| 全量重算的载体（历史数据 / 日志 / 快照） | 重算代价随什么增长 | 「能重算就行」——代价曲线不同，「能重算」与「重算得起」是两件事 |
| 时效要求（T+1 / 分钟级 / 秒级） | 窗口粒度与状态规模 | 「越实时越好」——窗口越细，状态规模与迟到数据的裁决成本越高 |
| 一致性要求（可对账 / 端到端精确一次 / 快照隔离） | 用哪一层的机制来保证正确性 | 「上了精确一次就没有误差」——它能约束链路内部，约束不了外部系统的非幂等写入 |
| 规模与成本约束 | 存算是否分离、状态放内存还是放对象存储 | 「存算分离一定更便宜」——省下的是扩容成本，加上的是跨网读取代价，请按你自己的扩容单价与跨区读取单价逐项核算 |
| 团队技能与运维能力 | 能同时养几条物理链路、能否运维有状态作业 | 「架构选好了人自然就有了」——有状态流作业与表格式运维都要专门技能，缺什么就会被绕开什么 |

把这 8 个模式放回上面三条主线上，它们的关系就清楚了：Lambda（3.2.1）、Kappa（3.2.2）、Lakehouse（3.2.3）、流批一体（3.2.4）在回答前两条——路径条数与重算载体；Medallion（3.2.5）不改变路径条数，它决定的是数据落在哪一层；Event Sourcing + CQRS（3.2.6）把「两条路径」正式化为写路径与读路径的职责划分；AI 原生（3.2.7）与自治（3.2.8）不碰前两条，它们改的是「谁来消费」与「谁来做决定」。**把不同层次的问题当成同一个单选题，是选型出错的典型形式。**

### 3.2 模式逐个拆解（核心节）

下面 8 个模式按「路径条数 → 落地分层 → 决策归属」排列：3.2.1–3.2.4 回答「几套物理实现、载体在哪」；3.2.5 与 3.2.6 是在同一载体上的组织方式与职责划分；3.2.7 与 3.2.8 叠加在它们之上，改的是消费方与决策方。

#### 3.2.1 Lambda 架构

- **被什么约束逼出来**：「全量结果必须能独立重算」与「秒级可见」这两个要求在物理上无法由同一条路径同时满足——准确来自对历史的完整扫描，及时来自对最近窗口的增量计算，两者只能分给两条路径。
- **结构**：两条物理路径，外加一个由人手写规则的合并点。

```text
Lambda：两条物理路径 + 一个合并点（合并逻辑本身是第三个失败模式）

  原始数据（只追加，不可变）
      ├──► 批层 Batch Layer：全量重算 [T0, T-1]
      │      → 批视图（正确，但滞后一个周期）
      └──► 速度层 Speed Layer：只算最近窗口 (T-1, now]
             → 增量视图（及时，但只有近似正确性）
      服务层 Serving Layer：按时间边界拼接
        结果 = merge(批视图.query(), 增量视图.query(), batch_window)
  ────────────────────────────────────────────────────────────
  关键：边界内的正确性靠「两层口径实现一致」来保证 ——
        没有任何机制能强制它，只能靠纪律
```

- **为什么这样设计有效**：因为批层每次都对全量历史重算，所以任意历史时点的结果都能被独立复现与审计；因为速度层只覆盖最近窗口，所以它的状态量不随历史积累增长——两层各自的代价都是常数级的，一个按周期全量、一个按窗口滚动。
- **代价**：① 同一口径要写两遍（批 SQL 与流 SQL），测试面与监控面各 ×2【推算】（推导链：一条链路对应一次口径实现、一套测试、一组监控；两条链路即各两份，且合并点多出第三种失败模式——窗口边界不一致）；② 迟到数据的归属必须由人工规则裁决；③ 两条路径的运维技能不同（批调度与有状态流作业），团队要同时具备两种。
- **失效点**：当两层的口径实现开始分叉时（一侧改了过滤条件而另一侧没改），「准确 + 实时」反转为「把两份不同真相按时间边界拼接」，因为合并层只按时间取数、不做语义等价校验，结果是同一个指标在一个时间点前后给出两个值。此时正确的动作是收敛口径实现（走向 3.2.4），不是加对账人力。
- **真实使用**：三层表述最早由 Marz 于 2011 年提出，并由 Marz & Warren 于 2015 年系统化【公开，2015】（来源：Marz & Warren《Big Data: Principles and Best Practices of Scalable Realtime Data Systems》，同 [§ 7](07-architecture-decisions-section-7-sec7.md) 的证据条目）。今天采用它的场景集中在「结果必须能全量重算」的领域（对账、风控、监管报送）【经验】；判断一个系统是否真在用 Lambda，看它有没有两份独立的产出物（批视图与流视图），而不是看它有没有同时装 Kafka 与 Spark。

#### 3.2.2 Kappa 架构

- **被什么约束逼出来**：批层的存在本身就是对账义务与两份口径的来源——如果日志可长期保留且可重放，「批」在机制上就退化为「一次从保留期起点开始的流计算」，没有必要再养第二条链路。
- **结构**：单一写模型是日志，历史靠重放而非批层重建。

```text
Kappa：唯一写模型 = 可重放日志，历史 = 一次重放

  原始数据 ──► 日志（Kafka / Pulsar，可指定 offset 重放）
                    ▼
              流作业（Flink / Spark Structured Streaming）
                    │  checkpoint + offset = 状态的唯一真相
                    ▼
              服务层（同一份流视图，无合并）
  ────────────────────────────────────────────────────────
  「重算」在这里被定义为：把 offset 拨回起点再跑一遍。
  → 重算代价 = 重放窗口 × 消费吞吐
  → 日志保留期就是「可重算的历史长度」，而它是线性计费的存储成本
```

- **为什么这样设计有效**：因为只有一条路径，所以不存在「两份口径分叉」这类问题——同一个指标只有一份实现，改一次就全链路生效；因为历史由重放重建，所以「补数据」不需要重跑批作业，只需要把 offset 拨回去。
- **代价**：① 重算时间与重放窗口成正比，窗口越深越慢，而 SLA 是固定的；② 状态必须由 checkpoint 与 offset 精确对齐，否则重放会产出重复或缺失；③ 完全依赖流引擎的成熟度——引擎的状态后端、水位线语义、扩缩容行为都成为业务的直接风险面。
- **失效点**：当需要重放的历史窗口超过日志保留期，或重放一次的耗时超过可接受窗口时，「架构简单」反转为「历史不可得、重算不可行」，因为 Kappa 把重算能力完全托付给消息层的保留期与重放吞吐，而这两项都是按量计费的成本项——保留期越长成本越高，缩短保留期就直接削减了可重算的历史。此时必须回到 Lambda 或 Lakehouse，把「长期历史」落到比日志更便宜的存储上。
- **真实使用**：以可重放日志替代批层的论证见 Kreps《Questioning the Lambda Architecture》（2014）【公开，2014】（同 [§ 7](07-architecture-decisions-section-7-sec7.md) §7.3.1 的公开证据块）。它最适用的形态是「事件本身就是业务事实、且历史深度需求有限」的系统（日志管道、监控告警、状态同步）【经验】；判断方法同上——看它有没有除了日志之外的"长期历史"落点，有就不是纯 Kappa。

#### 3.2.3 Lakehouse 架构

- **被什么约束逼出来**：多引擎（批、流、交互查询、机器学习）都要读同一份数据，而数据仓库的专有格式把数据锁在某一个引擎里；同时湖上的原始文件又缺 ACID 与 schema 治理——两个约束夹出来的，就是「把表语义下沉到存储格式」。
- **结构**：真相在表格式的元数据里，引擎退化为「读取某个快照的读者」。

```sql
-- Lakehouse：表语义下沉到存储格式（Iceberg 概念示意）
-- schema / 分区 / 统计信息在 metadata.json 与 manifest 中，与数据写入
-- 在同一事务里提交 → 「目录里的结构」与「数据真实的结构」不可能不一致
CREATE TABLE catalog.table_pointer (
  namespace          TEXT   NOT NULL,
  table_name         TEXT   NOT NULL,
  metadata_location  TEXT   NOT NULL,   -- 指向当前 metadata.json
  current_snapshot   BIGINT NOT NULL,   -- 当前快照 ID
  PRIMARY KEY (namespace, table_name)
);
-- 任一引擎（Spark / Flink / Trino / StarRocks）读同一张表：
SELECT region, sum(amount) FROM lakehouse.orders
WHERE dt BETWEEN DATE '2025-01-01' AND DATE '2025-01-31'
GROUP BY region;
-- 对照：没有表格式时，"改 schema"与"写数据"是两件无关的事，
--       裂开的窗口期必然被下游读到（判据见 3.3 决策表 Lakehouse 一行）
```

- **为什么这样设计有效**：因为 schema 变更与数据写入提交在同一个事务里，所以「表结构」与「表数据」的一致性由存储格式保证，而不是由采集流程的及时性保证；因为快照是不可变的，所以时间旅行与回滚是读取一个旧快照，不需要额外备份；因为格式是开放的，所以换引擎不需要搬数据——「多引擎共享同一份事实」正是这个模式的立足点，也是它相对 3.2.1 与 3.2.2 最本质的差别。
- **代价**：① 表格式的元数据服务（catalog）成为所有写事务的汇聚点，它的可用性就是全平台的可用性；② 元数据与 manifest 需要定期维护（快照过期、manifest 重写、小文件合并），这些是常驻运维任务而非一次性工程；③ 跨引擎读写依赖各引擎对表格式的实现程度，同一个格式在不同引擎上的行为并不完全一致。
- **失效点**：当写并发升高、多个引擎同时对同一张表提交时，「一份数据多引擎共享」反转为「一份元数据成为全局争用点」——因为写事务最终要串行化提交到 catalog 的元数据表，提交吞吐受该表约束。此时要靠降低提交频率（批量化小文件提交）或改用支持更高并发提交的表格式与锁策略来缓解，而不是简单给存储加带宽。
- **真实使用**：Lakehouse 概念由 Databricks 于 2020 年提出，论文见 CIDR 2021【公开，2021】（同 [§ 7](07-architecture-decisions-section-7-sec7.md) §7.3.2 的公开证据块）；Iceberg、Hudi、Delta、Paimon 四个开源表格式是它的工程载体（见 [§ 5 前沿演进](07-architecture-decisions-section-5-ai.md)）。判断一个平台是不是真 Lakehouse，看的是「换一个引擎能不能直接读同一张表」，而不是用了哪个存储桶。

#### 3.2.4 流批一体

- **被什么约束逼出来**：同一口径的两份实现（批 SQL 与流 SQL）是对账成本的根源——把两份实现合并成一份，是消除 3.2.1 失效点的唯一机制性手段，而不是靠对账纪律。
- **结构**：同一份代码 + 同一个存储格式，两种执行模式。

```sql
-- 流批一体：一份 SQL，两种执行模式（Flink / Spark 概念示意）
-- 批模式：有界输入，处理 [2025-01-01, 2025-01-31] 的历史
SELECT region, sum(amount) AS gmv
FROM lakehouse.orders
WHERE dt BETWEEN DATE '2025-01-01' AND DATE '2025-01-31'
GROUP BY region;

-- 流模式：同一份 SQL 换成无界输入，产出持续更新的结果
--   （有界输入被替换为 Kafka / changelog 流，其余表达式不变）
INSERT INTO lakehouse.gmv_1d
SELECT region, sum(amount) AS gmv
FROM kafka_orders
GROUP BY region;

-- 关键：统一的是「表达式与优化器」，不是「执行层」
--   状态后端、水位线语义、checkpoint 与 batch shuffle 仍是两套
--   → 所以"一份代码"并不能自动保证"一份语义"
```

- **为什么这样设计有效**：因为口径只有一份表达式，所以「批结果与流结果不一致」这类问题在机制上被大幅压缩——不一致的残余来源被限定在执行层的语义差异上（水位线、状态 TTL、排序），而不是散落在两套人工维护的 SQL 里，可排查范围收窄了一个量级。
- **代价**：① 引擎必须同时支持两种模式，选型自由度下降为「支持流批一体的引擎」；② 统一的行为边界需要学习——哪些算子在有界与无界输入下语义等价、哪些不等价，是团队必须掌握的知识；③ 批模式的调度与流模式的常驻作业需要两套发布与运维流程，只是共用同一份代码。
- **失效点**：当团队因为「一份代码」而放弃对账时，「口径统一」反转为「差异长期潜伏」——同一份 SQL 在流模式下受水位线与状态 TTL 影响、在批模式下按全量快照计算，迟到数据在两种模式下的归属不同，结果必然出现差异。机制上，统一的只是 API 与优化器，执行层仍是两套；正确做法是保留一条低成本的抽样对账（例如每日比对一次分区级聚合值），而不是把它删掉。
- **真实使用**：Apache Flink 自 1.12（2020）起把流批一体的 API 与 SQL 引擎列为 release 的独立条目，Apache Spark 自 2.0（2016）起以 Structured Streaming 把批与流收敛到同一套 Dataset 表达式（来源：flink.apache.org 与 spark.apache.org 的官方 release 页，版本号与条目名请以该页当前内容为准）【公开，可自行核验】。判定方法是看 release 页里有没有独立条目，而不是看项目路线图（同 [§ 7](07-architecture-decisions-section-7-sec7.md) §7.3.1 的公开证据块）。Paimon 一类的流式表格式把「同一份存储同时支持流读与批读」补齐（见 [§ 5](07-architecture-decisions-section-5-ai.md)），二者常成对出现。

#### 3.2.5 Medallion 架构（Bronze / Silver / Gold）

- **被什么约束逼出来**：同一份数据要被三类消费者同时使用——排障要原始数据、分析师要清洗后的口径、业务方要聚合结果；把三种需求压在一张表上，任何一次清洗都会损失排障所需的原始信息。
- **结构**：同一份数据的三个物化落点，按可信度分层，每层有独立 Owner 与 SLA。

```text
Medallion：按可信度分层（每一层都是一次物理落盘）

  Bronze（原始）      Silver（清洗整合）      Gold（面向应用）
  ────────────       ─────────────────      ────────────────
  · 原样落地          · 去重 / 类型规整        · 聚合 / 宽表 / 指标
  · 可重放            · 统一口径 / 关联维度     · 直接服务 BI / 特征
  · Owner=接入方      · Owner=数据工程         · Owner=业务分析
  · 保留期最长        · 保留期中等             · 保留期按需
        └────────────────┴───────────────────────┘
        每层有独立 SLA 与独立回滚点：重跑 Silver 不污染 Bronze，
        重跑 Gold 不污染 Silver
  ────────────────────────────────────────────────────────
  代价：每增加一层就多一次全量落盘与一次端到端延迟
        —— 层的边界是「物理物化边界」，不是「逻辑视图边界」
```

- **为什么这样设计有效**：因为每层都是物理落盘，所以重跑任何一层的失败都不会污染上游——回滚点天然存在，且下游可以按自己的节奏重算；因为口径收敛集中在 Silver，所以「同一指标多个算法」的问题被限制在一层之内。
- **代价**：① 存储随层数增加——同一份数据在 Bronze、Silver、Gold 各存一份，实际倍数小于层数（Gold 是聚合结果，行数远少于 Bronze），但 Bronze 通常是最大的一份且保留期最长【推算】（推导链：存储量 ≈ Σ 每层数据量 × 压缩后单行字节；Bronze 保留原始列与全量行，是上界）；② 端到端延迟等于各层调度间隔之和，层的边界越清晰，延迟越高；③ 各层的 Owner 与 SLA 必须真的写下来，否则分层就退化为三个无人负责的目录。
- **失效点**：当业务节奏快过分层调度频率时，「分层清晰」反转为「数据总是旧的」——因为每层各按自己的调度周期运行，端到端新鲜度是所有周期之和，而不是最慢的那一个。此时正确的动作是减少层数、或把对新鲜度敏感的链路单独走出分层（例如 Silver 直接供 Gold 的实时分支），而不是压缩每层调度间隔（压到比作业执行时间还短会让调度堆叠）。
- **真实使用**：Bronze / Silver / Gold 的定义见 Databricks 官方术语页与官方博客（起于 2021 年前后，以站点当前内容为准）【公开，可自行核验】（同 [§ 7](07-architecture-decisions-section-7-sec7.md) §7.3.3 的公开证据块）。它是湖仓项目的默认分层，但层名在不同组织里可能叫 Raw / Cleansed / Curated，判断是否同一模式看的是「是否按可信度物化分层」，而不是层名。

#### 3.2.6 Event Sourcing + CQRS

- **被什么约束逼出来**：审计要求「谁在什么时候把状态改成了什么」必须可逐条追溯，而只存当前状态时，这个信息在写入的那一刻就已经丢失；同时读写两侧的最优存储形态天然不同（写侧要追加、读侧要随机查）。
- **结构**：写侧只追加事件，读侧是从事件派生的投影。

```sql
-- 写侧：只追加的事件存储（不存当前状态）
CREATE TABLE event_store (
  stream_id     TEXT        NOT NULL,   -- 聚合根 ID（订单号 / 账户号）
  sequence_no   BIGINT      NOT NULL,   -- 该流的严格递增序号（并发控制的依据）
  event_type    TEXT        NOT NULL,   -- OrderPlaced / OrderCancelled / ...
  payload       JSONB       NOT NULL,   -- 事件内容（不可变，写入后不更新）
  occurred_at   TIMESTAMPTZ NOT NULL,   -- 业务发生时间（与写入时间不同）
  recorded_at   TIMESTAMPTZ NOT NULL,   -- 入库时间（排查与重放边界）
  PRIMARY KEY (stream_id, sequence_no)
);
-- 没有任何 UPDATE：状态是事件的派生物，不是存储对象
-- 读侧：投影（派生副本，可随时丢弃重建）
CREATE TABLE order_read_model (
  order_id      TEXT PRIMARY KEY,
  status        TEXT NOT NULL,
  total_amount  NUMERIC NOT NULL,
  last_event_seq BIGINT NOT NULL        -- 投影消费到哪个位置，用于校验
);
-- 重建投影 = 清空读表 + 从 event_store 按 sequence_no 重放
```

- **为什么这样设计有效**：因为事件只追加、不更新，所以「某一时刻的真实状态」可以被完整复现——审计不需要额外的日志表，事件存储本身就是审计记录；因为读模型是派生的，它可以在任何时候被丢弃并从事件重建，读侧的 schema 演进不影响写侧事实。
- **代价**：① 读取当前状态要么经过投影（有滞后）、要么现场重放事件（慢），"直接查一条记录"这种简单需求变得需要设计；② 投影是派生副本，必须处理重复消费与乱序，且要能校验「消费到哪个位置」；③ 事件的序列化格式成为长期契约，改一次影响所有消费者。
- **失效点**：当事件 schema 需要多次演进时，「状态可重建」反转为「重建逻辑永不可清理」——因为追加不可变是它的根本约束，旧事件不能被改写，读取端必须永久携带每一个历史版本的兼容分支，兼容代码只增不减，重建路径逐年变复杂。缓解办法是给事件加显式版本字段、并把兼容逻辑集中在反序列化层，但这只能约束增长形态、不能消除增长。
- **真实使用**：CQRS 与事件溯源作为模式的公开论述早于本章讨论的湖仓体系：事件溯源的表述可见 Fowler 的 bliki 条目《Event Sourcing》（2005），CQRS 一词由 Greg Young 于 2010 年前后提出并推广，其后在 Fowler 的《CQRS》条目（2011）中被进一步阐述【公开，可自行核验】（来源：martinfowler.com 上的这两个条目，标题与年份请以该站点当前内容为准；同 [§ 7](07-architecture-decisions-section-7-sec7.md) §7.3.3 的公开证据块）。它在工程上最常与 Kappa 组合（写路径事件、读路径投影、重放即重建，见 3.4 组合二），适用于审计严格且事件密度高的场景（金融、医疗）【经验】。

#### 3.2.7 AI 原生架构（Lakehouse + 向量库 + LLM）

- **被什么约束逼出来**：训练与推理消费的是同一份数据，但两者的读法完全不同——训练要列存的全量扫描与点时间快照，推理要低延迟的相似度检索；同时模型上下文需要从非结构化数据里抽取，「一份数据同时喂 BI 与模型」是它要解决的约束。
- **结构**：在原有湖仓之上，把「向量 / 非结构化资产」作为一等公民接进来，训练与在线推理共享同一个特征与语料来源。

```text
AI 原生：同一份事实，三种消费形态

  湖仓（表格式 + 列存）              向量索引                  特征/语料视图
  ─────────────────────           ──────────────           ──────────────
  · 结构化事实（点时间快照）        · 非结构化切块 + 嵌入      · 特征定义（口径唯一）
  · 全量扫描 / 聚合                 · 近似最近邻检索           · 训练与推理同源
        └──────────────┬─────────────────┴────────────────────────┘
                       ▼
                模型 / Agent（检索 → 生成 → 校验）
  ──────────────────────────────────────────────────────────────
  关键约束：向量索引与特征视图都是湖仓的派生副本
           → 必须随上游变更增量刷新，否则训练与推理读到不同世界
           点时间正确性（point-in-time）：训练样本只能看到
           该时刻已发生的事实，否则指标虚高
```

- **为什么这样设计有效**：因为向量索引与特征视图都是派生副本，所以它们的重建不需要新的事实来源——上游一旦修正，下游可以整体重建；因为训练与推理共享同一个特征定义，训练-服务偏差的来源被限制在「读取时点」这一项上，而不是「两边各写一套特征」。
- **代价**：① 多出两类需要持续刷新的派生副本（向量索引、特征视图），刷新滞后会直接变成模型效果问题；② 点时间正确性需要在读取层实现（按事件时间取该时点的版本），这是湖仓原生查询不一定免费提供的能力；③ 在线推理路径接进来之后，分析集群的故障域扩展到线上——分析作业的资源争用会变成线上延迟抖动。
- **失效点**：当训练与在线推理对同一特征的时间语义不一致时（训练取点时间快照、在线取最新值），「数据栈与 AI 栈融合」反转为「融合反而放大训练-服务偏差」——因为一个特征是同一份存储、同一个名字，团队会默认两边同源，于是不会做一致性校验；偏差只在模型上线后以效果不稳的形式暴露。正确做法是把「特征读取时点」写进特征的元数据并做成可查询的，而不是靠文档提醒。
- **真实使用**：主流湖仓平台自 2024 年前后开始把 AI 能力做进查询层（主文件 §1.4 记录该阶段为「AI 原生架构」）【公开，2024】（来源：主文件 §1.4 演进历程的 2024–2025 年条目；各厂商的具体能力边界请以官方文档当前版本为准）。「多模态」形态（Iceberg 一类表格式 + 向量库）也出现在原 § 3 的决策表中，是这一模式的一个分支。【经验】

#### 3.2.8 自治架构（Self-Driving）

- **被什么约束逼出来**：数据栈的可调参数（分区、并行度、资源配额、小文件合并时机）数量已远超人工评审的带宽，而每个参数的误配都会在成本或时效上显形——「决策带宽不足」是这条路线唯一的驱动力。
- **结构**：把「观测 → 决策 → 执行」做成闭环，并且**决策必须留痕**，否则不可复核。

```text
自治架构：闭环的每一步都要可复核，否则它只是"自动化"

  观测（指标 / 血缘 / 成本 / 时效）
        │
  决策（规则 or 模型）──► 决策记录（决策日志 / ADR）
        │                     · 依据了哪些指标
        │                     · 为什么选这个动作
        │                     · 预期影响与回滚条件
        ▼
  执行（改配置 / 改资源 / 改分区策略 / 合并小文件）
        │
  验证（动作是否真的改善了目标指标？没改善就回滚）
        └────────► 回到观测
  ────────────────────────────────────────────────────────
  关键：没有决策记录的自动化，等于把"无法解释的变更"
        以更高的吞吐写进生产
```

- **为什么这样设计有效**：因为决策依据被显式记录，所以自动动作的失败可以被定位到「依据错了」还是「模型错了」，而不是只能整体关掉——这是自治与「黑盒调参脚本」在工程上的分水岭。
- **代价**：① 决策记录本身成为新的数据资产，要归档、要能被查询、要有人复核；② 执行动作需要幂等与限速，否则一次误判会放大成大面积变更；③ 闭环里的验证环节需要"可观测的目标指标"——没有它，自治就退化为开环的定时脚本。
- **失效点**：当决策记录不完整时，「AI 驱动、减少人肉评审」反转为「决策不再可解释、不可复核」——出问题时无法判断是数据异常、模型误判还是策略本身错了，只能整体停掉自治；而反馈回路还会让偏差自我强化（模型按自己的历史决策做训练样本）。因此在本主题下，自治的可用性上限由「决策可复核性」决定，而不是由模型能力决定。
- **真实使用**：该方向在 2025 年被主文件 §1.4 记为「自治架构（Self-Driving Architecture）」阶段【公开，可自行核验】（来源：主文件 §1.4 的 2025 年条目；厂商是否给出可核验的自动化闭环，请以其官方文档当前版本为准——判定方法是看文档有没有写清触发条件、动作清单与回滚方式，而不是看产品页上的形容词）。就本节覆盖的 8 个模式而言，它是成熟度最低的一个，落地时应先保证前 6 个模式的路径与载体已经稳定。【经验】

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 结果必须能全量重算 + 监管/对账 + 有批调度能力 | Lambda | 纯 Kappa 无法提供一份可独立审计的全量结果，监管口径上说不清 | 是否存在「必须能独立复现某个历史时点结果」的要求 |
| 历史深度需求有限 + 事件即事实 + 只有一支流团队 | Kappa | Lambda 的双链路在这个场景只增加对账义务，不带来任何准确度收益 | 需要重放的窗口是否长期**短于**日志保留期与重放 SLA |
| 多引擎共读一份数据 + 需要 ACID 与时间旅行 | Lakehouse | 纯湖上直接读文件时，schema 变更与写入没有事务边界，下游必然读到裂开的中间态 | schema 是否**随写事务一起提交** |
| 已经有两个口径实现 + 对账成本高 | 流批一体 | 继续维持 Lambda 是把对账成本永久化，且每次口径变更要改两处 | 是否存在**同一指标的批/流两份 SQL** |
| 需要分层治理 + 三类消费者共存（排障/分析/业务） | Medallion | 全部压在一张表上时，任何一次清洗都会丢掉排障所需的原始信息 | 是否同时需要**原始可回溯**与**口径已收敛** |
| 审计要求逐条可追 + 读写形态差异大 | Event Sourcing + CQRS | 只存当前状态时，变更历史在写入那一刻就丢失，事后无法补齐 | 是否必须回答「谁在何时把状态改成了什么」 |
| 训练与推理共用数据 + 非结构化资产占比高 | AI 原生（Lakehouse + 向量库） | 训练用湖、推理用独立检索库且互不同源时，两边的时点与口径会分叉 | 训练与推理是否**读同一份特征定义** |
| 多模态（结构化 + 文本 + 图像 + 向量） | Lakehouse + 向量库（多模态分支） | 只上湖仓时，高维向量的相似度检索得不到有效的剪枝结构 | 是否存在**以相似度为条件**的查询（不是等值或范围） |
| 跨国 / 跨云 + 数据主权约束 | 联邦（多云表格式 + 统一 Catalog） | 单集群集中存储会与数据驻留要求冲突，且跨区读取延迟不可控 | 数据是否**不允许离开某一法域** |
| 决策带宽不足 + 参数数量已超人工评审能力 | 自治（先建决策日志，再谈自动执行） | 跳过决策记录直接自动执行时，误判无法定位、只能整体关停 | 能否回答「上次自动变更的依据与回滚方式」 |

表中在本主题下最常被误选的一对是 **Lambda 与 Kappa**。误选的方向几乎总是「先上 Lambda，再想简化成 Kappa」——因为 Lambda 在演示阶段最稳（批层保底、流层加分），而 Kappa 的代价（重放窗口、状态规模）要到上线后才显形。机制上，这两者不是「完整版与简化版」的关系：Lambda 付的是**对账成本**（两份口径 + 一个合并点），Kappa 付的是**重放成本**（日志保留期 + 重放吞吐）。选错的实际后果不是性能问题，而是**重算能力与业务要求错配**：监管要求能复现三年前的某日结果时，一个只保留 7 天日志的 Kappa 系统在机制上就交不出这份结果——这时候补建批层不是优化，是返工。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Lakehouse + Medallion + 流批一体（默认的现代数据栈）**

- 构成：表格式承担快照、ACID 与时间旅行；Medallion 承担可信度分层与回滚点；流批一体承担入湖与增量计算。
- 职责边界：表格式只管「一份数据能被多个引擎以同一语义读到」，不做治理；Medallion 只管「数据落在哪一层、谁负责、SLA 是多少」，不改路径条数；流批一体只管「口径只有一份实现」，不定义分层。
- 运维代价：三套技能并存（表格式运维与元数据服务、有状态流作业、查询引擎调优）；元数据服务成为共享依赖，它的故障会同时打穿三层。
- 适合规模：已上湖仓、表数量在万级以上的组织。【经验】

**组合二：Event Sourcing + CQRS + Kappa（写事实、读投影）**

- 构成：事件存储定义写模型（只追加、不可变）；投影定义读模型（可丢弃重建）；Kappa 定义计算路径（只有流、历史靠重放）。
- 职责边界：事件存储只回答「发生了什么」，不做查询优化；投影只回答「现在是什么」，不承担审计；Kappa 只负责把事件推到投影，不做语义转换。
- 运维代价：投影重建时间随事件总量增长，必须有「定期快照 + 从快照增量重放」；事件的 schema 兼容层长期存在，只增不减。
- 适合规模：审计严格、事件密度高、历史深度需求有限的场景（金融交易流水、医疗记录）。【经验】

**组合三：Lambda + 流批一体（迁移中的过渡形态）**

- 构成：批层与速度层由同一个引擎的批模式与流模式承担，代码尽量共享，物理路径仍是两条。
- 职责边界：统一引擎降低口径重复的实现成本，但不消除两层在执行语义上的差异（水位线、状态 TTL、排序）——所以它**不替代对账**。
- 运维代价：必须保留对账作业（抽样比对分区级聚合值即可，不需要全量），并在口径变更时同时验证两种执行模式。
- 适合规模：正从 Lambda 迁移到流批一体、或存在强对账要求而不能一步到位的组织。【经验】

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 盲目追求 Lambda | 只有 T+1 与当日看板两类需求，却维护着两套计算链路与一份对账脚本 | 多出一条必须长期维护的物理链路与第三个失败模式（窗口边界），准确度却没有因此提高 | 演示阶段批层最稳、流层加分，于是把「能力齐全」误当成「需求匹配」 | 先用一张表核清时效需求分布；没有任何需求要求秒级时，撤掉速度层 |
| 盲目追求 Kappa | 大量历史回补与全量重算需求落在一条流上，重放排队 | 重放窗口与 SLA 直接冲突，补数变成需要排期的项目 | 「架构更简单」在评审时最容易被接受，重放代价要到第一次补数才显形 | 把「最长需重算窗口」与「日志保留期」对照；缺口不补则以 Lambda / Lakehouse 承担长期历史 |
| 架构僵化 | 业务已从 T+1 走到分钟级，架构图、选型文档与调度周期仍是三年前的形态 | 模式与约束错配后，所有优化都在错误的路径上做，投入不产生效果 | 架构变更没有触发条件与责任人，也没有把「何时重评」写进 ADR | 给每个 ADR 写一条「重评触发条件」（时效要求变化、路径数变化、成本占比越线），并定期 review |
| 决策无据 | 问「为什么不用另一个方案」，回答只能是「经验上这样更稳」 | 决策不可复核 → 出问题时无法区分是选型错还是实现错，返工范围无法界定 | 决策发生在评审会上而非文档里，唯一记录是会议纪要 | 每个关键决策写 ADR（背景 / 决策 / 后果 / 备选项），并给出可观测的验证指标 |
| 忽视治理 | 架构上线很快，但血缘、质量、权限三项都没排期 | 无治理的湖仓在机制上会退化为数据沼泽：无主、口径分叉、不可信（见 3.2.5 与 3.2.7 的派生副本刷新要求） | 治理见效慢、不产生新功能，被当作「二期再说」 | 把最小治理面（Owner、粒度、血缘、密级）与架构上线绑在同一次发布里 |
| 缺乏可观测 | 架构跑起来但出问题时不知道是哪一层、哪个作业、哪份状态 | 三层结构下故障可发生在任意一层，缺观测时定位成本随层数增长 | 监控按「进程存活」建，而不是按「业务结果是否正确」建 | 为每一层建结果级校验（行数、主键唯一、分区聚合值对账），并把派生副本的刷新滞后做成指标 |

**「盲目追求 Kappa」**。它在本主题的 6 条反模式里最隐蔽，因为它在很长时间里看起来都工作正常。暴露方式是**一次补数**：某个上游数据出错需要回溯三个月，团队发现日志只保留 7 天，于是要么接受三个月的数据无法修复，要么临时重建批链路。机制层面，这是把「重算能力」外包给了按量计费的日志保留期——保留期越长成本越高，缩短保留期就直接削减了可重算的历史长度。所以在选 Kappa 之前，必须先回答一个数：**最长需重算的历史窗口是多少天**，再对照日志保留策略与重放吞吐能否覆盖，而不是先看架构简不简单。

**「架构僵化」与「决策无据」是同一条链上的两个环节**。前者让模式与约束错配，后者让错配无法被事后归因。它们的共同机制是：架构决策没有被赋予**触发条件**，于是决策只发生一次。ADR 的价值不在于记录「选了什么」，而在于记录「在什么观测值变化时应该重评」——例如时效要求从 T+1 变为分钟级、口径实现的份数从 1 变成 2、某个派生副本的刷新滞后持续超过阈值。没有这些触发条件，架构 review 会退化为「按季度看一眼架构图」，而架构图看不出状态规模、窗口边界与小文件数量这些真正会反转结论的量。

**「缺乏可观测」在组合架构下会被放大**。单链路架构出问题时，排查范围就是那条链路；而 3.4 里的三个组合都是多组件叠加（表格式 + 元数据服务 + 有状态流 + 投影 + 派生副本），任何一环滞后都表现为「数据看起来是对的、其实已经旧了」。这类问题的暴露方式是**沉默**：任务全部成功、监控全绿、业务方在两天后发现数字不对。修法不是加更多进程级指标，而是加**结果级**校验——分层聚合值对账、派生副本的「消费到哪个位置」、以及元数据的最后更新时间。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| T+1 报表 → 分钟级时效 | Lambda（双链路） | 时效要求收紧后，合并层的窗口边界越来越频繁地被下游看见（同一指标在两个时间点给出两个值） | 流批一体 / Lakehouse 增量计算 | 口径实现从两份收敛成一份，需要重建测试与对账基线；流作业的状态与并行度要重新设计 |
| 单批次口径变更频繁 → 两份 SQL 长期分叉 | Lambda | 每次口径变更要改两处，总有一处落后；对账差异成为常态 | 流批一体（保留抽样对账） | 需要评估统一引擎对现有算子的支持范围，不支持的算子要改写 |
| 千级表 → 万级表、单引擎 → 多引擎并发写【经验】 | Lakehouse（单 catalog） | 写事务汇聚到同一个元数据表，提交吞吐成为全局约束；且维护任务（快照过期、小文件合并）从偶发变成常驻 | 支持更高并发提交的表格式与锁策略 + 批量提交 | 提交路径改造（批量小文件提交、降低提交频率）；元数据服务的容量与高可用要单独规划 |
| 单域 → 跨国 / 跨云 | 单集群 Lakehouse | 数据驻留要求与单集群集中存储冲突；跨区读取的延迟与出网成本不可控 | 联邦（多云表格式 + 统一 Catalog） | 从「改代码」变成「谈权责与合规」；需要跨区元数据映射与统一的 URN |
| 人工评审 → 决策带宽不足 | 无自治（人工调参 + 定期评审） | 参数数量超过评审带宽，误配在成本与时效上显形，而评审会看不到细节 | 半自治（先建决策日志与可观测指标，再逐步放开执行动作） | 决策记录与回滚机制要先建；不能跳步直接自动执行 |

这五行的共同点是：**触发换模式的从来不是「数据量」本身，而是某个具体的结构性矛盾**——合并层的窗口边界被下游看见、同一口径有两份实现、元数据的提交吞吐成为瓶颈、数据不允许跨域、决策带宽不足。数据量增长让模式失效的方式，一定是通过上述某个具体矛盾，而不是通过「规模」这个数字本身。

因此判断该不该换，看的不是「表有多少张」，而是一组能从现有监控与日志里直接取到的量。最容易读到的三个是：**同一指标在批视图与流视图之间的差异条数/比例**（不为零且持续存在，说明 3.2.1 的失效点已经发生）；**写事务提交的 p99 与其失败重试率**（上升说明元数据服务正在成为争用点）；**派生副本（向量索引、特征视图、投影）的刷新滞后**（超过业务容忍窗口，说明 3.2.7 的训练-服务偏差已经在积累）。后两行的成因（数据主权、决策带宽）读不出这样的现成指标，通常要靠合规清单与变更记录来盘点——但这两类跃迁的前兆同样具体：一个是「某法域的数据出现在另一个法域的存储桶里」，一个是「说不清上一次自动变更的依据」。

### 3.7 自检清单

- [ ] 同一业务指标在系统里有**几份实现**？如果超过一份，有没有一条常设的对账（而不是一次性的迁移比对）？
- [ ] 最长需要「重算/回补」的历史窗口是多少天？它与当前的日志保留期、快照保留期是否覆盖得上？覆盖不上时，哪一份存储承担长期历史？
- [ ] 批视图与流视图在最近一次口径变更后，差异条数是否为 0？查得到这个数字吗？
- [ ] 表格式的 schema 变更是否与数据写入在**同一个事务**里提交？如果 schema 是另一条流程单独推送的，中间那段窗口期会被谁读到？
- [ ] 是否有分层（Bronze / Silver / Gold 或同义分层）？每层的 Owner 与 SLA 是写下来的，还是口头约定？
- [ ] 每一层（或每一个派生副本）是否有一个**结果级**校验（行数、主键唯一、分区聚合值），而不是只有进程存活告警？
- [ ] 向量索引、特征视图、读模型这类派生副本的**刷新滞后**有指标吗？超过多少算不可接受？
- [ ] 训练样本与在线推理读的是同一份特征定义吗？读取时点（点时间快照 / 最新值）写进元数据了吗？
- [ ] 写事务的提交 p99 与重试率是多少？元数据服务是不是所有写路径的必经点？
- [ ] 每一个关键架构决策是否有 ADR？ADR 里有没有**重评触发条件**（时效要求变化、路径数变化、某个派生副本滞后越线）？
- [ ] 若已引入任何自动变更（自动扩缩、自动合并、自动调参），它是否留下了决策记录，并能回答「依据了哪些指标、错了怎么回滚」？
- [ ] 最小治理面（Owner、分层、血缘粒度、密级）是否与架构上线绑在同一次发布里，而不是排在「二期」？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 结果必须能独立重算 + 有批调度能力 | Lambda | 批层对全量历史重算，任意历史时点可复现；代价是两份口径 + 一个合并点 |
| 历史窗口短于日志保留期 + 只有流团队 | Kappa | 只有一条路径，不存在口径分叉；代价是重算能力被日志保留期与重放吞吐绑定 |
| 多引擎共读 + 需要 ACID 与时间旅行 | Lakehouse | schema 随事务提交，一致性由存储格式保证；代价是元数据服务成为全局争用点 |
| 已有两份口径实现 + 对账成本高 | 流批一体 | 口径收敛成一份表达式，差异来源从"两套 SQL"缩减到"执行层语义"；代价是选型自由度与执行语义的知识负担 |
| 三类消费者共存 + 需要回滚点 | Medallion | 每层物理落盘 → 重跑不污染上游；代价是端到端延迟等于各层调度周期之和 |
| 审计逐条可追 + 读写形态差异大 | Event Sourcing + CQRS | 事实只追加，状态可重建；代价是投影滞后与事件 schema 兼容层只增不减 |
| 训练与推理共用数据 + 非结构化资产多 | AI 原生（Lakehouse + 向量库） | 派生副本可整体重建，训练-服务偏差来源收窄到"读取时点"；代价是故障域扩展到线上 |
| 决策带宽不足 + 可观测指标已就位 | 自治（决策日志先行） | 决策依据可复核，误判可定位到"依据错"还是"模型错"；代价是决策记录本身成为新资产 |

> 本节小结：本主题下决定架构模式选择的唯一那条约束是**「同一口径由几条独立物理路径产出」**——2 条必然带出对账义务，1 条必然带出重放义务，两条路线的成本形态完全不同；重算的载体（历史数据 / 日志 / 表格式快照）决定代价曲线随什么增长，而分层（Medallion）、职责划分（ES + CQRS）、消费与决策层（AI 原生、自治）都是在这一条确定之后才展开的次级选择。
