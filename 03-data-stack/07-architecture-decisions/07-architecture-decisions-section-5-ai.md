## 5. 前沿演进（AI 时代）

> 原 § 5 共 81 行、为方向清单（4 条演进方向 + 2 条 RAG / GraphRAG + 3 条学术条目 + 3 条工业条目 + 5 条趋势），缺少机制与成熟度判断，重写为 ~300 行前沿评估。

### 5.1 先分清三类「前沿」

本节要解的第一个问题不是「AI 能给架构决策带来什么」，而是**时间刻度**。把"引擎按统计信息自动选物化视图、自动合并小文件"（现代查询引擎与数据湖在本章 [§1.4](07-architecture-decisions.md) 的"Lakehouse 主流"阶段就有了，见 [03-data-stack/02 §2.3](../../03-data-stack/02-data-lake/02-data-lake.md) 的小文件合并）与"由模型决定架构该怎么演进"（本节核到的是厂商演示与自研路线图）并列写成"演进方向"，读者据此写 ADR 时无法判断哪一条今天能进方案。本主题有一条比别处更前置的约束，写在主文件 [§1.2](07-architecture-decisions.md) 的痛点清单里：排在前面的不是"选得不够先进"，而是**"决策无据"与"架构僵化"**——即决策依据来自哪一层事实、以及决策记录会不会过期。这条约束不会被 AI 改动：模型可以把候选技术栈列得更全、把 ADR 写得更工整，但它不能让选型矩阵里的权重从"拍的"变成"有依据的"。

本主题还有一处独有的困难：**架构决策的质量以年为单位才显形**（返工与迁移成本），所以"某个方向有没有价值"几乎不可能靠短期 benchmark 判断。本节因此用 L1 / L2 / L3 三级区分，判据必须是可核验的三条：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条各挡住一类误判：①挡住"把路线图当既成事实"，②挡住"把厂商自述当行业现状"，③挡住"把演示当工程"。**三条全中才算 L1**，可以排进路线图；只满足一部分、或只有厂商自有案例的算 **L2**，可做 PoC、不要作为核心依赖；只有路线图 / 论文 / 演示的算 **L3**，记录即可、不要在架构里预留假设。"感觉成熟"不算判据——它在选型评审会上无法被复核。

**判据声明（本节不对 L1 判据做任何修正）**：上文那三级与三条判据沿用到底，不替换、不放宽。本主题有一处特别诱人放宽的地方，先把话说死：架构决策的产出物是**企业内部的 ADR 与选型结论**，它不是产品，成效指标（决策周期、返工率、迁移成本、取数正确率）几乎不会以第三方口径公开（见 §5.4）。于是**连"既有能力"那几行也很难凑齐第②条**——但证据少不等于判据可以改：把"没有第三方公开案例"重写成"有公开生产记录""有可被第三方复核的机制性材料（论文 / 规范 / 官方文档）"，只是把同一条判据换了种说法，读者按新措辞照样核验不了。本节的做法是：**够不到第②条的行一律降到 L2，并在判据格里写明它卡在哪一条**，而不是为它重新定义"什么叫合格的第三方案例"。结果是**下表没有任何一行达到 L1**（包括那几条非 AI 的既有能力行）；其中"**没有任何一条 AI 能力方向到 L1**"是本节最重要的一句话。

写这一节时最容易混的四件事，先在这里分开：

- **产品名 vs 能力名**：原清单里的"AI 原生架构（Lakehouse + 向量库 + LLM）"是**产品组合说法**，不是可判定的架构范式；对应的能力名是"**机器可读的语义层**"（元数据 + 口径 + 血缘 + 密级策略）。凡看到"某平台是 AI 原生的"，先问它在能力名上提供了什么。
- **已发布版本 vs 路线图**：判断某个表格式 / 引擎是否真的支持某能力，只看一处——**该版本的 release note 或官方文档里有没有对应条目**；项目官网的路线图页、benchmark 博客、生态伙伴的转述都不算（§5.4 给了本主题具体例子与判定入口）。
- **确定性优化 vs 统计预测**：优化器按统计信息重排计划、后台服务合并小文件，都是**确定性动作**，不需要模型也不需要 LLM；把它们算进"自治架构"是本主题最普遍的一处混淆。
- **论文里的原型 vs 产品里的实现**：本方向大量提法（自动调优、自然语言选型、Agent 编排）在论文与开源原型里都能找到，但**能否在生产里开箱使用是另一回事**。判定方法：看产品的官方文档里该能力有没有"SLA / 配额 / 计费"三项——有这三项的才是产品化条目，只有一段演示的还不是。

本主题的证据形态还要单独说一句：**架构决策的成效指标（决策周期、返工率、迁移成本、取数正确率）几乎全部是企业内部数据**，公开材料最多到"我们做了这件事"，很少到"因此某个指标从多少变到多少、口径是什么"。所以本节的表里，**十行没有一行拿得出第②条要求的第三方（非厂商）公开生产案例**（§5.4）——非 AI 的既有能力行与 AI 方向行一样躲不开这一点，它会**系统性地压低全表的级别**，且不因方向本身的优劣而改变。读表时请把这一层看进去：**L2 不等于"不好"，也不等于"不能现在做"，只等于"公开证据到不了 L1"**；真正需要警惕的是把 L2 当 L1 排进核心路线图。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**——改变了成本结构、改变了接口边界、把人工判断换成统计判断，还是只换了个前端？本主题的答案分四类：**一条改变了接口边界**（取数链路多了一类机器消费者，它读的不是数据而是元数据）、**一条把人工判断换成统计判断**（自治架构里真正成立的那部分）、**一条只改了接口形态**（Agent 工具接口与架构即代码——边界与判定层次没变）、**其余方向与 AI 没有因果关系**（架构推荐、ADR 生成与自然语言查询只是换了前端；流批一体与联邦改的是引擎语义与控制面划分）。这个分类不是文字游戏：**只换前端的方向接入后仍要补语义层与权限**，而改接口边界的方向会让你发现真正的缺口在治理侧，不在模型侧。

**这三级的排法直接决定路线图的顺序**：

- **先做的两条（§5.1 表前两行那两条非 AI 的能力）**：一是把语义层做出来——元数据登记、口径、字段级血缘、质量分（本书 [04-data-assetization/08 §6](../../04-data-assetization/08-data-catalog/08-data-catalog-section-6-sec6.md) 把它写成"Text2SQL 与 Agent 取数的**成像条件**"）；二是把引擎侧的确定性自动化开起来（自动合并、自动物化、自适应并行度）。它们排在所有 AI 方向之前，因为**后面每一个 AI 方向的收益都建立在"机器能读懂你的数据"这件事上**。注意它们的级别**仍是 L2**——第②条拿不出来；所以动作可以今天就开始，但不要在 ADR 里把它们写成"行业已普遍验证"的前提。
- **AI 方向里的那两条 L2 先做 PoC，并先测三个数**：工具接口暴露给 Agent 后，**越权尝试被拒的比例**与其**误拒比例**；架构知识 RAG 的"过期 ADR 命中率"。这三个数拿不出来，这两条就停在原地（它们与上一条"先做"的区别是：上一条可以直接进方案，这两条必须先有可观测的数字）。
- **L3 不排进排期**：LLM 推荐架构、AI 决定架构演进、AI 生成治理策略，都属于"等信号"。它们的共同前提（输出物可静态校验、动作可回滚、有可复核的评审记录）比选哪家模型重要得多。
- **回填机制**：每次选型复查（本章 [§4.1](07-architecture-decisions-section-4-sec4.md) Step 6 的季度 review）时回填一次级别；某个 L2 若一年内仍拿不到自己组织里的实测数字，降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次"决策变快"，都对应一处新的责任空位。

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 AI 原生架构 | 取数链路上多了一类**机器消费者**，它先读元数据再读数据 | **接口边界**（多一个消费面，不是多一个组件） |
| §5.2.2 自治架构 | 把"人盯容量与布局"换成"统计信息驱动的确定性动作" | **判断依据**（AI 只贡献预测与建议） |
| §5.2.3 Agent 工具接口与架构即代码 | 能力的暴露方式从 SDK 换成统一协议，声明物从文档换成版本库 | **接口形态**（边界与判定层次没变） |
| §5.2.4 同组方向 | 收益全部来自治理或范式，没有一条来自模型 | **多数与 AI 无因果关系** |

读法建议：如果时间只够读一节，读 §5.2.1——它是本主题里唯一一条"改了接口边界"的方向，也是唯一一条能直接推导出"下一步该补什么"的方向；§5.2.2 的收益要等你把引擎侧的配置边界划清之后才兑现；§5.2.3 与 §5.2.4 的方向，共同前提都是"权限与语义能不能被机器读、变更能不能回滚"。

每一节末尾的「证据与来源」采用同一套档位：【公开】指有可核验的出处（官方文档 / 论文 / 公开材料），【推算】指能写出推导链的换算，【经验】指区间估计。**本节不给版本号**：凡涉及"某产品支持某特性"的地方，一律改写成判定入口（查哪一版 release note 或哪份官方文档），因为本主题的产品名与能力名错配率最高。

#### 5.2.1 AI 原生架构：变化的是"多了一类消费者"，不是"多了一个向量库"

- **旧做法与它的卡点**：取数入口是人写 SQL——业务方描述问题、分析师翻译成查询。卡点不在查询引擎，而在**语义与权限没有机器可读的形态**：表和字段的业务含义、口径、质量、密级、谁能读，散在文档、口头与各系统里。主文件 [§1.2](07-architecture-decisions.md) 把这一点写成 AI 时代新诉求（AI 原生架构 / Agent 友好），目录侧把它写成"**AI 数据不可见**：Agent 不知道有哪些表 / API 可用"（[04-data-assetization/08 §1.2](../../04-data-assetization/08-data-catalog/08-data-catalog.md)）。同一个缺口，两侧的名字不同。
- **AI 改变了什么机制**：**接口边界**变了——出现了一类机器消费者，它在生成查询之前必须先回答三个问题：有什么数据、口径是什么、我能不能读。也就是说，**它读的不是数据，而是元数据**。这解释了为什么"加一个向量库"不构成本方向的机制：向量索引解决的是"怎么找到相似文本"，而机器取数要的是**确定性的语义与权限事实**，这两件事不在同一层。
- **由此得到的**：**因为消费者从人换成了机器，所以"机器可读的语义层"（元数据 + 口径 + 字段级血缘 + 质量分 + 权限策略）从治理成本项变成了取数链路的必要组件**——它的收益第一次可以脱离"治理的道理"来论证：没有它，模型只能靠猜表名与猜口径（[04-data-assetization/10](../../04-data-assetization/10-metric-platform/10-metric-platform.md) 把指标定义作为一等对象，正是这条链路上最容易缺的一环）。

| 机器消费者必须先回答的问题 | 答案由谁提供 | 未登记时会发生什么 |
| --- | --- | --- |
| 有哪些数据 | 目录（元数据 + 业务含义 + Owner） | 模型猜表名；选中了停用表或重复表，且它不会报警 |
| 这个数是什么口径 | 指标 / 语义层的口径定义 | 生成语法正确、口径错误的 SQL——**静默错误** |
| 我能不能读 | 下发到查询层的行 / 列级策略 | 校验留在应用层就变成批量越权；留在提示词里等于没有校验 |

- **由此付出的**：**其一，责任面从一处变三处**——取数错了，可能错在语义层（口径没登记）、权限（策略没下推）、或模型（生成错误），默认无人负责，必须在 ADR 里写明判定顺序（先查口径、再查权限、最后查模型）。**其二，语义层成为新的瓶颈**——口径未登记齐全时，模型仍会给出"看起来对"的 SQL，这类错误比人写错更难发现，因为输出更流畅、更少语法错误，而**发现错误的成本才是这里真正的新增成本**。**其三，权限必须下推到查询层**——若策略只留在应用层，机器消费者会把"一次越权"放大成"批量越权"（同一类问题在 [11-cross-cutting/07 §5.2.2](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-5-ai.md) 被写成"判定位置从一个变成四个"，那里逐条列了"过滤未下推"与"策略与源系统不同源"的失效形态）。
- **证据与来源**：【公开】元数据 / 口径 / 字段级血缘 / 质量分是多家彼此独立的组织已投产的能力——可被第三方复核的是**机制性材料**（各目录与平台产品的正式功能条目、元数据接口与规范文档，可按「OpenLineage 列级血缘」「Apache Atlas 元数据模型」这类「项目 / 规范名 + 能力名」自行检索核验）。运行做法自述见本书 [§6](07-architecture-decisions-section-6-sec6.md) 与 [11-cross-cutting/05 §6](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-6-sec6.md)、[04-data-assetization/08 §6](../../04-data-assetization/08-data-catalog/08-data-catalog-section-6-sec6.md) 三处；**这三处附有改前 / 改后的数字，但它们是本书自撰的汇总估计（口径与样本由本书给出），不构成第②条要求的第三方（非厂商）公开生产案例**；**本节未能核到"因为补了语义层，取数正确率提升多少"的第三方公开对照材料**（§5.4）。
- **成熟度**：**L2（语义层这一能力，非 AI 方向）**——①③成立、②核不到（§5.1 表第 1 行）；**L3（"Lakehouse + 向量库 + LLM 作为一种架构范式"）**——它是产品组合名，没有可核验的判据，本节不给版本也不给产品能力断言。
- **判定方法**：随机抽 20 张核心表，数"业务含义 / 口径 / 密级 / Owner"四项齐全的有几张；再问一句"这四项缺一个时，机器消费会失败还是继续猜"。**第二问的答案决定你有没有资格谈 AI 取数。**
- **什么时候值得做**：已经明确要让 Agent / LLM 参与取数，或有跨团队口径争议时。它是所有后续动作的前置条件，且不引入新故障形态。
- **什么时候不值得做**：如果当前主要痛点是"分析师查得慢"而不是"机器读不懂"，先做查询性能与建模，语义层的投入可以按域分批推进。

#### 5.2.2 自治架构：确定性优化是既有能力（L2），"AI 决定怎么演进"是 L3

- **旧做法与它的卡点**：架构与容量靠人盯——小文件多了跑一次合并、查询慢了加索引或换引擎、容量不够扩容。卡点是**滞后与不可复现**：等到告警响了才动，而"上次为什么这么调"只留在某个人的记忆里（[§1.2](07-architecture-decisions.md) 的"架构僵化"与"决策无据"）。
- **AI 改变了什么机制**：**必须把"自动"与"智能"分开算。** 分层合并、分区裁剪、物化视图选择、自适应并行度、成本路由——这些是**优化器与后台服务按统计信息做的确定性动作**（机制侧见 [03-data-stack/14](../../03-data-stack/14-optimizer/14-optimizer.md) 的 CBO 与自适应执行；逐项核验入口见 §5.4「官方 release note / 文档」一栏），不需要模型；模型真正能增益的是**预测与建议**：下一季容量、哪张表该重分区、哪次变更影响面最大。所以"自治架构（Self-Driving）"里，**已经成立的那一半是统计信息驱动的确定性优化，未成立的那一半才是 AI**。
- **由此得到的**：**因为动作由统计信息与规则驱动，所以"降低运维负担"今天就能排进路线图，且出问题时原因可复现**——这是它相对 AI 决策最大的优势：可以解释、可以回放、可以在测试环境复现。本章 [§6](07-architecture-decisions-section-6-sec6.md) 的四个案例（双写收敛、Keystone 流批一体、存算分离、三引擎分工 + 热数据物化）讲的都是工程动作而非模型决策；其中"热数据物化"就落在本页表格里"可自动"的那一侧。

| 动作 | 驱动信息 | 可回滚吗 | 能否进自动通道 |
| --- | --- | --- | --- |
| 小文件合并 / 重写数据文件 | 文件数、平均文件大小 | 可（产物可再合并） | 可以 |
| 物化视图 / 汇总表刷新 | 查询模式统计 | 可（重建即可） | 可以 |
| 分区裁剪 / Join 策略 / 并行度 | 运行时行数统计 | 可（计划级，随查询消失） | 可以 |
| 分区结构变更 / 表重构 | 增长与访问趋势预测 | **难**（下游依赖要同步改） | 只进建议通道 |
| 引擎 / 存储 / Catalog 迁移 | 成本与性能预测 | **不可**（年级别动作） | 不自动 |

这张表的读法是**自下而上找边界**：前三行能自动，是因为它们的产物还能被下一次动作覆盖；后两行不能自动，不是因为技术不可行，而是因为**一次错误决策的后果无法用一次操作撤回**。所以"自治到什么程度"这个问题，在本主题里等价于"你愿意为哪几类动作准备回滚方案"。

- **由此付出的**：**其一，成本归属会变模糊**——自动动作触发的计算（合并、重写、物化）落在谁的账上，需要事先约定，否则成本分账对不上，而这类计算恰恰是"看起来不增长"的那部分（[11-cross-cutting/03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md) 的分摊问题在这里会露出来）。**其二，自动化半径由回滚能力决定**——上表最后两行就是边界：改分区结构与迁引擎都不具备"一键退回"的性质，把它们自动化等于把年级别的风险交给一条规则。**其三，"自愈"降低故障可见性**——问题被绕过后根因没人修，与本书 [03-data-stack/12 §3.7 自检清单](../../03-data-stack/12-scheduler/12-scheduler-section-3-sec3.md) 第 11 条记的"僵尸任务"是同一条教训。
- **证据与来源**：【公开】确定性自动化的取证形式是**判定入口而不是集合断言**——在所用引擎的官方文档与 release note 里逐项核验「自适应查询执行 / 自动小文件合并 / 自动物化（物化视图刷新）」是否为**正式功能**（而非预览）、能否按表 / 按目录配置、产物能否被下一次动作覆盖。**本节不对"各引擎都有这三项"作断言**：覆盖范围因引擎而异，「自动物化」在部分引擎里是可选功能、或由独立服务提供。**【本节未能核到】"由模型决定架构演进决策"进入生产的第三方材料**。
- **成熟度**：**L3（"AI 自动演进架构"那一半）**——只有演示与自研路线图，①不成立；至于"确定性优化"那一半，它不是本方向新增的东西，就是 §5.1 表第 2 行的 **L2（非 AI）**——级别与判据随该行（官方文档里的正式功能条目 + 配置接口稳定；第②条核不到）。
- **什么时候值得做**：小文件数、元数据操作延迟、合并积压这类指标已经在影响查询时。先开自动合并与自适应执行，收益立刻可见，且不需要新责任方。
- **判定方法**：把最近一个月的自动动作（合并 / 物化 / 重写）拉出来，按月统计触发次数与产生的计算量，并对比"关掉它"的窗口期查询延迟。**触发次数在涨但延迟没变好，说明自动动作在追一个移动的目标，而不是在解决瓶颈。**
- **什么时候不值得做**：如果你的表布局本身还在频繁变（模型天天改、分区策略未定），自动优化会一直在追一个移动的目标——此时它稳定的产出是"账单上的额外计算"，不是稳定性能。

#### 5.2.3 Agent 触达的架构与架构即代码：接口形态变化，不是范式变化

- **旧做法与它的卡点**：工具能力经各自 SDK / API 暴露，每个消费者（BI、脚本、调度、服务）各自对接一次；架构声明物散在文档、Wiki 与人的记忆里。卡点是**对接成本与不可核查**：接入一个消费者要一次工程，而"当前架构长什么样"无从机器校验（[§4.3](07-architecture-decisions-section-4-sec4.md) 的"ADR 模板 + 决策矩阵"是人写的，写完就过期）。
- **AI 改变了什么机制**：**只是接口形态**——把"能做的事"暴露成模型可发现、可调用的统一协议（MCP 类是公开规范），把架构声明物从文档搬进版本库。**判断依据与执行边界一点没变**：工具被调用时权限仍要校验、变更仍要评审。这也是本节四个核心方向里唯一一条被归为**接口形态**的方向（见 §5.2 开头的分类表；"只换前端"的方向另有架构推荐、ADR 生成与自然语言查询，前两者的落点是 §5.1 表第 3 行、§5.4 的核验动作第 4 条与 §5.7 表的第 5 行，自然语言查询的落点是 §5.7 表第 2 行）——但它换的位置很关键（工具清单与权限），所以仍然值得单列。
- **由此得到的**：**因为工具清单与权限成为机器可读的，所以"能不能让 Agent 直接查数 / 直接改配置"第一次可以被当做一个权限与审计问题来讨论，而不是能力问题**——这是真的收益：它把讨论从"能不能"推到"谁能、谁批准、怎么留痕"。同理，架构即代码的价值来自**声明物进版本库、变更走 diff 与评审**，与模型无关；模型只改了书写入口。
- **由此付出的**：**其一，新的越权面**——工具一旦暴露给模型，权限校验必须落在被调用方，靠调用方自觉等于没有校验。**其二，审计对象增加一条链**——要能回答"谁授权它做的、它做了什么、结果谁复核"，而"模型"在这条链上不是责任主体，提交与评审的人才是。**其三，生成物必须落回声明文件并过策略检查**——否则架构的"可解释"会退化成"模型说的"；本章 [§4.1](07-architecture-decisions-section-4-sec4.md) 的 Step 2 要求"输出 ADR"，对生成物同样成立，只是要多一道机器校验。

```text
        同一件事，两种暴露方式（差别在权限校验落在谁身上）
        需求："让 Agent 能查这张表的近 7 天 GMV"
        ────────────────────────────────────────────────
        ✗ 只给能力（把库连接 / 工具交给模型）
          Agent ──► 数据访问工具 ──► 存储
          权限校验：在调用方（提示词 / 编排逻辑里写"不要查敏感的"）
          → 一次越权会被放大成批量越权，且无法枚举它做过什么
        ✓ 能力 + 边界一起暴露
          Agent ──► 工具清单（带作用域与配额）
                       └─► 被调用方校验：身份 / 作用域 / 行级策略
                              └─► 审计：谁授权、调了什么、返回什么
        ────────────────────────────────────────────────
        判定方法：随机取三个已暴露的工具，问"如果模型越权调用，
                  哪一层会拒绝、日志里能看到谁"
        ——答不出来，就还没到可放生产的程度
```

- **证据与来源**：【公开】MCP 有公开的协议规范与多家彼此独立的厂商采纳公告（规范在 2024 年底公开，2025 年起陆续被多家厂商宣布支持；具体支持范围以各家官方文档为准）；架构即代码侧，声明式基础设施工具是正式产品条目、接口多年未变。**【本节未能核到】"Agent 经统一协议操作生产数据栈"的第三方可核验材料**。
- **成熟度**：**L2**（协议与实现可用，第①③条成立；但权限模型、审计边界无通行做法，且第②条核不到 → 可做 PoC，不要作为核心依赖）；架构即代码 **L2（非 AI 工程实践）**，"AI 辅助架构治理" **L3**。
- **边界提醒**：本方向的成熟度看两件事——**协议有没有稳定版本**（决定它能不能写进技术选型）、**被调用方能不能强制作用域**（决定它能不能写进权限方案）。两者不同时成立时，先上后者，因为它直接决定风险边界；协议版本可以等，权限落点不能等。
- **什么时候值得做**：你已经有多套系统要对同一个模型暴露能力、且重复对接成本已经明显时。收益是把"接入 N 次"收敛成"暴露一次"。
- **什么时候不值得做**：在你还没有统一身份与权限模型时——把工具暴露给模型的前提是"每个调用都可归属到人或服务账号"，缺这个前提，暴露只是把越权面扩大一次。

#### 5.2.4 被挂到 AI 名下的五个方向：收益来自治理或范式，没有一条来自模型

| 方向 | 旧做法与卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据 / 成熟度 |
| --- | --- | --- | --- | --- | --- |
| 架构知识 RAG（原 §5.2 第 1 条） | 找回"上次为什么这么选"靠问人与翻 Wiki，前提是你知道该搜什么 | 发现入口从"知道关键词"变成"描述处境" | 长尾决策记录（一次性专题、废止的 ADR）第一次可被找到 | **过期 ADR 被检索到会以"有出处"的形式给出错误依据**，比搜不到更贵；适用范围要显式设计 | 组件可用、无效果材料 → **L2** |
| 架构依赖图 GraphRAG（原 §5.2 第 2 条） | 改组件前列影响面靠经验估计与发通知 | **没有改变影响分析的机制**——影响面来自字段级血缘与图遍历；LLM 只把"写图查询"换成"提问题" | 提问门槛下降，使用频率上升（真实、但只是频率） | 引入"答得不对但很流畅"的新失败形态；影响面答错会让变更门禁被绕过（[11-cross-cutting/05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)） | 血缘 + 图遍历是既有生产能力（可按「OpenLineage 列级血缘」一类公开规范核验），但①③之外的②核不到 → **L2（能力本身）/ L3（GraphRAG 增益）** |
| 流批一体与表格式成熟（原趋势 3，以及原 §5.3 里 Paimon / Flink 两条所指的方向） | 流批两套代码两套存储，口径要对账 | **与 AI 无因果关系**：它改的是引擎与表格式的统一语义（本章 [§2.1](07-architecture-decisions.md)、[03-data-stack/03](../../03-data-stack/03-lakehouse/03-lakehouse.md)） | 一份代码一份存储，维护面收敛 | 表格式与引擎的版本耦合、存量迁移与对账成本 | 【公开】①③成立、②核不到（§5.4） → **L2（既有能力，非 AI）**；"Lambda 退出"这一断言本节不作为事实使用 |
| 联邦架构（原趋势 4） | 跨云 / 跨国各有一套目录与权限，跨边界要靠人搬数据 | **与 AI 无因果关系**：它改的是控制面与数据边界的划分 | （若成立）跨域的资产与权限能统一回答 | 联邦语义不统一时故障定位跨两套控制面；数据出域通常是**合规问题而不是技术问题** | 多集群 catalog 有正式条目；"统一治理"无稳定接口 → **L2** |
| 厂商"数据智能平台"（原 §5.3 前两条工业条目：Databricks Data Intelligence Platform、Snowflake Cortex；第三条 Apache Paimon 1.1 的落点见「原条目去向对照」表） | 语义层、自然语言查询、向量检索由客户自己拼 | 把上面几层**打包成产品**（这一层确实与 AI 有关，但它是产品形态） | 少拼几个组件，入口统一 | **产品名与能力名混同**：宣传语里的"AI 原生"要逐条落到能力名上核对 | 判定入口：查官方文档标的是正式功能还是预览 → **L2（可试点）** |

**这五行的共同读法**：收益都真实存在，但**没有一条的收益来自模型**——两条来自治理（RAG 的过期与适用范围、联邦的边界划分），一条来自引擎与表格式（流批一体），一条本就是既有能力（影响分析与图遍历），最后一条是产品打包。把它们写成"AI 时代的架构演进"，会让真正要做的三件事（补语义层、开确定性优化、划数据边界）一件都排不进排期。

- **什么时候值得做**（针对本组前两条）：你的 ADR 已经积累到"翻不到、翻到了也不敢信"的程度时，知识 RAG 的成本很低；你的变更事故已经出现过"改一个字段引爆下游"时，影响分析的投入是刚性的。
- **什么时候不值得做**：ADR 总量还不到几十份时，检索的价值不如一份目录；跨云治理还没划清数据与账号边界时，谈"联邦"只是把合规问题推迟到实施期。

### 5.3 与本主题既有栈的接口在哪

架构决策与 AI 之间不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比"AI 能做什么"更能决定它能不能落地。**「现状」列只写接口契约本身的状态（既有机制 / 未定），不写 L1 / L2 / L3**——它描述的是接口，不是演进方向；表里出现的十个接口大多不在 §5.1 的十行里，本节不给它们另立级别。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 架构 ↔ 机器可读的语义层（[04-data-assetization/08](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 交接物 = 元数据 / 口径 / 血缘 / 质量分；**机器消费者只读这一层** | 登记与 Owner 维护那一侧；口径未登记时"猜"的责任在下游消费者 | 既有机制 |
| 架构 ↔ 指标与口径（[04-data-assetization/10](../../04-data-assetization/10-metric-platform/10-metric-platform.md)） | 交接物 = 指标定义作为一等对象（口径的唯一定义处） | 指标 Owner；口径变更未联动时，事故责任在变更发起方 | 既有机制（口径的唯一定义处） |
| 架构 ↔ 权限与合规（[11-cross-cutting/02](../../11-cross-cutting/02-data-security/02-data-security.md)、[11-cross-cutting/07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)） | 交接物 = 策略的**执行点**：应用层 / 查询改写 / 引擎行级策略 | **谁把校验放错层，谁负责**——这是本节最常见的责任错位 | 执行点未定（无通行做法） |
| 架构 ↔ Agent / 工具接口 | 交接物 = 工具清单 + 作用域 + 配额；**被调用方是校验方** | 暴露工具的那一方（模型不是责任主体） | 执行点未定（作用域如何强制无通行做法） |
| 架构 ↔ 调度与编排（[03-data-stack/12](../../03-data-stack/12-scheduler/12-scheduler-section-3-sec3.md)） | 交接物 = 依赖判定所在层次（任务成功 / 数据就绪） | 调度侧；架构若只提供"任务成功"这一层信号，静默算错就是架构选型的问题 | 既有机制 / 接缝处未定 |
| 架构 ↔ 优化器与后台服务（[03-data-stack/14](../../03-data-stack/14-optimizer/14-optimizer.md)） | 交接物 = 统计信息 + 配置边界（自动动作在哪一层、能否按表关闭） | 平台侧；**统计信息不准时自动优化会稳定地选错** | 既有机制（配置边界是新的） |
| 架构 ↔ 可观测（[11-cross-cutting/04](../../11-cross-cutting/04-observability/04-observability.md)） | 交接物 = 引擎自身指标（小文件数、元数据操作延迟、合并积压、缓存命中） | 平台侧；只监控业务查询不监控引擎自身，是这套能力最常被漏掉的一半 | 既有机制（常被漏掉一半） |
| 架构 ↔ 成本（[11-cross-cutting/03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)） | 交接物 = 自动动作的计费归属与预算闸门 | 平台与财务的接缝处；**没有归属约定时，自动优化会变成"没人认领的计算"** | 归属约定未定 |
| 架构 ↔ CI / 架构即代码 | 交接物 = 声明文件 + 评审 + 策略检查 | 提交与评审的人（生成物也一样） | 既有机制（评审）/ AI 生成物未定 |
| 架构 ↔ 数据质量（[11-cross-cutting/01](../../11-cross-cutting/01-data-quality/01-data-quality.md)） | 交接物 = 断言与校验规则挂在哪一层（入湖 / 加工 / 出口） | **把校验挂在下游的那一方**；错误一路传播到最后一次校验才被发现，是上游缺校验的后果 | 既有机制 / 挂载位置未定 |

一句话概括：**AI 没有给架构新增任何层级，只新增了一个消费面**——机器消费者。它带来的第一个新问题就是责任问题：**语义层与权限策略过去是"人查一下"，错了由查的人负责；现在它们被机器消费，错了谁负责？**由此得到四条约定。

**第一条约定：语义层与权限的"未登记"必须显式可见。**做法是让"口径未登记 / 密级未标注"在机器消费时**默认拒绝并报错**，而不是回退到猜测。回退即静默错误，而静默错误恰好是本主题最贵的故障形态。

**第二条约定：凡"模型建议 → 改架构 / 改配置"的链路，动作必须可回滚且可 diff。**可回滚的含义很具体：变更落在声明文件里、能重放、有一键回退。做不到这三条时，输出只能进"建议"通道；这条与本章 [§3](07-architecture-decisions-section-3-sec3.md) 的「反模式与失效分析」只有一处交集——那里的**决策无据**（凭经验决策、无法解释）与这里要"可 diff、有评审记录"是同一要求的两面；**那一节的六个反模式里并没有"回滚"与"diff"这两条判据**，它们是本节针对"模型建议 → 改配置"这条链路补的。

**第三条约定：把"机器可读"当成验收标准写进 ADR。**一份 ADR 若只写了"选 Lakehouse"，它不可被复核；写清"哪些语义（元数据 / 口径 / 血缘 / 密级）已经机器可读、由谁维护、未登记时如何失败"，它才成为可验收的决策记录。

**第四条约定：给自动动作指定计费归属。**上表里"架构 ↔ 成本"这一行的现状栏写的就是"归属约定未定"，原因是归属没有通行做法。落地做法很朴素：在开启任何自动优化前，先约定它产生的计算记在平台账还是业务账，并在指标里能被单独看到——**看不见的成本，一定会在下一次预算评审时以"说不清"的形式回来**。

### 5.4 公开进展与文献

分三类列，**其中论文与生产案例两类只列能给出标题 / 出处 + 年份的条目**；release note / 官方文档一类是判定入口，给核验标准而不给年份，理由见该类开头。**宁少勿假**。

**论文（可核验）**

- Armbrust, Ghodsi, Xin, Zaharia, "Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics", CIDR 2021——**原清单把它标为 CIDR 2023，这个归属按论文集页面判定是不成立的**；主文件 [§1.4](07-architecture-decisions.md) 把"2020 年 Databricks 提出 Lakehouse 概念"记为概念起点，与论文年份的差别就在这里。
- Armbrust et al., "Delta Lake: High-Performance ACID Table Storage over Cloud Object Stores", VLDB 2020——对象存储上的 ACID 表格式，是本章 [§2.1](07-architecture-decisions.md) "表格式 + 多引擎"这条线可核验的技术依据。
- Kreps, "Questioning the Lambda Architecture"（2014）——Kappa 的原点：以可重放日志替代批层（本章 [§1.1](07-architecture-decisions.md) 记 Jay Kreps 2014 年提出 Kappa）。
- Marz & Warren, *Big Data: Principles and Best Practices of Scalable Realtime Data Systems*（2015）——Lambda 三层的原始表述（批层 / 速度层 / 服务层）。
- **原文件所列的三条"学术进展"里，两条本节无法核验**：「Paimon 论文（VLDB 2024）」与「Flink 2.0 路线图（2024）」；第三条（原标为 CIDR 2023 的 Lakehouse 论文）**已按论文集页面重新归属为 CIDR 2021**，见上。处理办法：**三条各自所指的方向都保留**（流批融合表格式、流批一体的引擎演进、Lakehouse 范式），但前两条不当证据使用；判定入口见下。

**官方 release note / 文档（判定入口）**

**这一类不给年份，只给核验标准**：release note 与官方文档是持续更新的，某条能力对应哪一年取决于你查的那一版，写死一个年份反而会先于能力本身过期。本类的核验标准只有一句——**以官方文档当前版本为准**，在官方文档或 release note 的对应条目里看到该能力被标为"正式功能"（而不是预览 / 路线图），即算核验通过。下面六条各给出核验入口。

- Apache Paimon 与 Apache Flink 的官方 release 页——核验"流批融合""引擎 2.0 演进"的具体内容与版本归属；**判定方法：看 release 页里有没有独立条目，而不是看项目官网的路线图或 benchmark 博客**。路线图里的东西在架构上不能预留假设。
- Apache Iceberg / Hudi / Delta 的官方 release note 与规范仓库——核验"表格式能力"（行级更新、变更日志、时间旅行）是正式条目还是预览。
- 各查询 / 湖仓引擎的官方文档——核验"自适应查询执行、自动小文件合并、自动物化"三项是否都是正式功能、能否按表关闭；**这是 §5.1 表第 2 行判据①的核验入口**。
- 各表格式项目的官方规范仓库——核验"表级语义"（快照、变更日志、行级更新）的实现状态；**判定方法：看规范文档里该语义是"已实现且有测试"还是"规划中"**，这一条决定它能不能承载跨引擎的一致读。
- Model Context Protocol 的公开规范——核验"工具清单 / 作用域 / 传输"这些条目是否存在、有无稳定版本；**判定方法：看规范里有没有"被调用方如何声明并强制作用域"，没有这一条就说明权限边界尚未成规范**。
- Databricks Data Intelligence Platform、Snowflake Cortex 等产品——它们的**具体能力以各自官方文档为准，本节不给版本号也不断言某项特性存在**；判定方法同上：看官方文档里该能力标的是正式功能还是预览。

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含指标与口径的第三方"AI 改变架构决策"生产案例。公开材料里能核到的是架构演进的运行做法自述（双写收敛、Keystone 流批一体、存算分离、三引擎分工 + 热数据物化——本书 [§6](07-architecture-decisions-section-6-sec6.md) 的四个案例已整理），以及各家对元数据 / 血缘能力的正式发布条目；本书 [§6] 与 [04-data-assetization/08 §6](../../04-data-assetization/08-data-catalog/08-data-catalog-section-6-sec6.md)、[11-cross-cutting/05 §6](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-6-sec6.md) 另附改前 / 改后的数字，但那是**本书自撰的汇总估计**（口径与样本由本书给出），不是第三方口径；**缺的是"因此在取数正确率 / 变更事故 / 决策周期上从多少变到多少"这类带基线的第三方材料**。**这个空白本身是结论**——它正是本节把整张表压在 L2 / L3 的直接原因：第②条核不到，就不许靠改写判据把它补上。
- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——把你们自己的"语义层覆盖率（口径 + 血缘 + 密级可机器读取的比例）""机器取数被拒绝的越权尝试数与误拒数"算出来并留存口径，下次评审时它就是带基线的生产材料。
- 这三类里**最容易造假的是第三类**：厂商案例通常省略口径（怎么算的、样本多大、基线是什么），项目方案例通常省略规模（多少参与方、什么数据量）。**判定方法**：只接受同时给出"口径 + 规模"的案例；缺一项就只当方向记录，不当证据。

**怎么用这份清单**：要核"能力存不存在"看官方文档与 release note（最快）；要核"机制成不成立"看论文（最慢但最稳）；要核"在我这里值不值得做"看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **语义层**：抽 20 张核心表，数"业务含义 / 口径 / 密级 / Owner"四项齐全的比例。
2. **权限执行点**：找一个已暴露给 Agent 的查询入口，问"越权发生在哪一层被拒绝"。
3. **确定性自动化**：数引擎的自动合并 / 自动物化是否开着、能否按表关闭。
4. **架构推荐**：若试用过，统计候选清单里有多少条最终进了 ADR、多少条事后被推翻。
5. **知识 RAG**：数 Top-K 里过期 ADR 的占比。
6. **影响分析**：问一次"改这个字段会破坏谁"，看能否十分钟内从系统里查出。

### 5.5 被过度宣传的部分

**「AI 原生架构 = Lakehouse + 向量库 + LLM」**——实际是：这是一个**产品组合说法**，不是可判定的架构范式；取数链路真正缺的是机器可读的语义层与权限下推，而向量库是索引选型，属于 [04-data-assetization/02](../../04-data-assetization/02-vector-lake/02-vector-lake.md) 那一层的事。**为什么会这样**：LLM 选表、生成 SQL 依赖的是元数据与口径，不是向量索引；把"加了向量库"当成"AI 原生"，会让语义层与权限这两个真正的工程缺口排不进排期。**它什么时候才会成真**：出现可复核的评测——同一份数据、同一组问题，语义层做好前后机器取数的正确率差是多少。**判定方法**：数一次"口径未登记的表占比"，这个数不降，说明缺口在治理侧而不在模型侧。

**「自治架构（Self-Driving Architecture）」**——实际是：拆开看，成立的是**确定性优化**（自动合并 / 自动物化 / 自适应并行度，L2 的既有能力），未成立的是"由模型决定架构怎么演进"（L3）。**为什么会这样**：架构演进动作（改分层、换引擎、迁存算分离）的爆炸半径是年级别的，没有回滚与 diff 闸门时，自动化只能停在"建议"。**它什么时候才会成真**：出现公开材料，披露"由模型决策的架构变更"的**回滚率与代价**——只报"自动化了多少次"没有意义。

**「架构即代码 + AI 让架构治理自动化」**——实际是：架构即代码的价值来自**声明物进版本库、变更走 diff 与评审**，与 AI 无关；AI 只改了书写入口（从 HCL / YAML 到自然语言）。**为什么会这样**：治理的判据是"变更能否被 diff、能否被回滚、谁签的字"，这三条由版本控制与评审流程提供，模型既不提供也不替代。**它什么时候才会成真**：生成物能稳定落回声明文件并通过策略检查（policy as code），而不是直接对云资源动手。**判定方法**：数一次"最近十次基础设施变更里，有几次是先在版本库里看到 diff 才知道要发生什么"——这个数不接近十，说明声明物还不是架构的真实来源。

这三条的共性：**它们都把"写候选清单、调参数、写声明文件"这些动作的成本下降，当成了"架构决策质量上升"**。而本主题的质量判据只有三条——决策依据来自哪一层事实、变更能不能回滚、决策记录会不会过期；这三条一条也没有因为 AI 而改变。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 架构侧对 AI 的投入会集中在"补语义层 + 暴露工具接口"，而不是"让模型选架构" | 选型材料的重心从"用哪个模型推荐"转到"元数据 / 口径 / 密级的覆盖率"；目录类产品的正式条目集中在机器可读性 | 出现公开材料，披露"模型推荐架构"在生产中的采纳率与决策回溯 |
| "AI 原生架构"这个说法会退潮，被"语义层成熟度"这类可度量的说法取代 | 采购与评审材料里出现"机器可读比例""未登记即拒绝"这类验收项 | 该说法继续作为产品营销语存在，且没有可复核的验收口径 |
| Agent 消费数据会先以"只读 + 强作用域 + 全审计"落地，写入类动作更晚 | 数据平台的正式条目集中在只读工具、行级策略与调用审计；写入仍需人工确认 | 出现 Agent 直接改生产配置或改口径、且不设人工复核的公开生产案例 |
| 流批一体与表格式的下一步变化来自"表格式与引擎的语义统一"，与 AI 无关 | 各引擎的发布条目集中在变更日志 / 行级更新 / 增量物化这类语义 | 架构讨论的焦点转向"由模型决定流批边界"，且出现可核验成效 |

写这四条时的共同约定：**信号必须是外部可观察的**（正式发布条目、验收口径、公开案例），而不是"我觉得会"。**被检验得最快的是第三条**——数据平台的下一个版本发布说明里有没有"只读工具 + 作用域 + 审计"，一年内就能看到；**最慢的是第二条**——它要求行业换一套度量语言，而这通常要等一轮采购周期；**第一条最可能出现"半对半错"**：语义层的投入会上升（对），但"让模型选架构"的说法不会消失（错），所以这一条要按"预算流向"而不是"话语是否消失"来判。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 准备写"AI 原生"相关的 ADR | 先量化语义层：口径、字段级血缘、密级的机器可读比例 | 观察未登记项在机器消费时是否默认拒绝 | 不要把"引入向量库"写进架构决策——它是索引选型 |
| 团队抱怨取数靠猜表名 | 把元数据、口径、质量分补到可机器读取，并给未登记项一个显式失败行为 | 观察取数返工次数与"猜错口径"的事故数 | 不要在语义层空缺时先上自然语言查询——它只会让猜得更快 |
| 运维靠人盯容量与小文件 | 打开引擎侧的确定性自动化，并给它设配置边界 | 观察合并 / 物化触发的计算量落在谁账上 | 不要让不可回滚的动作（改分区结构 / 迁引擎）进自动通道 |
| 想让 Agent 直接查数 | 先把工具清单、作用域、配额、审计四件定下来，校验放在被调用方 | 观察越权尝试被拒数与误拒数 | 不要靠提示词约束权限；不要让调用方能自证清白 |
| 被问"能不能让模型推荐架构" | 把候选集落回 ADR 模板走评审，并把权重来源写清楚 | 观察生成建议的采纳率与事后回溯准确率 | 不要用模型的输出替代权重讨论；不要让它直接改配置 |
| 已有架构知识库 / RAG | 先补"过期标记 + 责任人 + 适用范围"三个字段 | 观察 Top-K 里过期文档的占比 | 不要把废止的 ADR 与现行 ADR 混在一个索引里 |
| 想用 GraphRAG 做影响分析 | 先把字段级血缘与图遍历做出来（[11-cross-cutting/05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)） | 观察"改这个字段会破坏谁"能否十分钟内查出 | 不要用自然语言层替代图查询——影响面答错比答不出更贵 |
| 要跨云 / 跨国统一治理 | 先划数据边界、账号边界与合规边界 | 观察落地案例是否都带合规例外条款 | 不要在架构里预留"联邦 Lakehouse"假设；不要把它包装成 AI 演进 |
| 团队想上"架构即代码" | 声明物进版本库、变更走 diff 与评审、加策略检查 | 观察回滚一次变更需要多久 | 不要在没有评审与回滚能力时先做生成式改配置 |
| 老板要求"三年内实现自治架构" | 把目标拆成"确定性自动化 + 容量预测 + 建议通道"三段，分别给验收口径 | 观察三段各自的负责人是否明确 | 不要签"模型自动决定架构演进"式的目标——它没有可验收的失败定义 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改语义层、动权限边界、翻存量、扩大自动化半径），**而收益依赖一个尚未成立的假设**（模型推荐得对 / 生成物可校验 / 联邦语义可统一）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**取数链路的接口边界**——链路上多了一类机器消费者，它先读元数据再读数据，于是"机器可读的语义层"从治理成本项变成取数链路的必要组件。它**没有**改变主文件 [§1.2](07-architecture-decisions.md) 那两条更前置的约束：**决策依据来自哪一层事实**，以及**决策记录会不会过期**。所以"模型推荐架构""模型决定架构演进"这一类方向，改变的是写候选清单的成本，不是决策质量的判据。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是"写清单 / 调参数 / 写声明文件"的成本，还是"机器能不能读懂你的数据、变更能不能回滚"这两件事？** 前者今天就有用（本节判 L2 的那两条），后者不由模型决定。第二条同样快的判断：**它需要语义层吗、动作可回滚吗、输出能被验收口径度量吗**——三条答不上来的方向，只能停在"建议"通道。
>
> 如果只能带走一句话：**先把语义层做出来，再让 AI 去用**；顺序反过来，就是把一个靠猜表名的模型接在一套本来就没人说得清口径的数据上。
>
