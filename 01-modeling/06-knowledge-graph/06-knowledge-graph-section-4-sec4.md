## 4. 工程实现

本节按「定范围 → 定 schema → 接数据源 → 建抽取 → 校验 → 存储与索引 → 查询与推理 → 发布」八步组织，每一步给三件事：**产物**（这一步结束手上多出什么可检查的东西）、**判据**（怎么知道做对了）、**为什么必须在这一步**（换序或省掉会让哪一步返工）。六种模式（本体驱动 / 开放抽取 / 联邦 / 层次 / 事件 / 多模态）的机制、代价与失效点在 [§ 3](06-knowledge-graph-section-3-sec3.md) 已给出，本节不复述模式取舍，只处理「选定之后怎么装进去」。

**本文件面向两类读者。** 4.1–4.3 与 4.5 面向**从零搭第一张图谱**的团队：按顺序执行，第一件事是把「这张图回答哪些问题」写清楚。**4.4 存量迁移**面向**已经有一个数仓、关系散落在一批表里，或已经有一堆文档语料**的团队：这类读者的第一步不是 Step 2 的 schema 设计，而是「先决定哪些关系可以自动推导、哪些必须抽取」，请先读 4.4 的第 ② 小节再回到 4.1。两类读者在 4.9 用同一份自检清单。

### 4.1 落地步骤

**Step 1：业务边界与领域识别（1–2 周【经验，随业务域数量与干系人层级变化】）**

- 圈定 KG 要覆盖的业务域，**从一个域开始**（如「客户域」「产品域」）；识别核心实体类型（**5–30 个起步**）与核心关系类型（**10–50 个起步**）【经验，区间随领域规模与业务问题数量变化】。数量是提示不是标准：判断依据是「加上这一种，能多回答哪个原先答不了的问题」。
- 列出这张图**要回答的问题清单**（10 条以内，每条一句话）。
- **产物**：**KG 范围说明书（KG Requirements Specification, KGRS）**，含实体/关系类型清单与问题清单。
- **判据**：把 KGRS 交给一个没参与建模的业务方，让他复述「这张图回答哪些问题」——复述不出或复述成「所有数据」的，范围还没定下来。再抽 3 条问题，逐条指出「图上哪条路径能答它」；指不出的问题现在就该删掉，而不是等建完之后发现答不了。
- **为什么必须这一步 / 为什么在这个位置**：实体与关系类型的数量直接决定 schema 的评审成本与图的可维护性（[§ 3.5](06-knowledge-graph-section-3-sec3.md) 已把类型无边界列为失效形态）。放到后面做，等于先按「把数据都放进来」建图、再回头删——而删的成本远高于不建。

**Step 2：Schema 设计（2–6 周【经验，随是否复用既有本体变化】）**

- 设计实体类型 / 关系类型 / 属性；**优先复用既有本体**（FOAF、Schema.org、FIBO、SNOMED CT、UFO 等），能复用的一律不新造。
- 决定用 **RDF 三元组模型**还是**属性图模型**（Cypher 风格），以及走**本体驱动**还是**开放抽取**策略——后者的判据见 [§ 3.3](06-knowledge-graph-section-3-sec3.md) 模式选择决策表；前者的判据见 [§ 7.2](06-knowledge-graph-section-7-sec7.md)（判据是「查询模式是否需要引擎预想不到的连接方式」，机制见 § 7.3.1），本节不重复。
- **产物**：**KG Schema（OWL 或 Cypher DDL）** + 一份属性的**受控清单**。
- **判据**：抽 10 条 Step 1 的问题，逐条写出它需要的关系类型——有 1 条写不出对应类型，schema 就还没定完。再核一件事：每个关系的**定义域与值域**（从哪类节点连到哪类节点）是否逐条写明；只写「有关系」不写两端的 schema 无法用于校验，等价于没有 schema。
- **为什么必须这一步 / 为什么在这个位置**：schema 是「推理与校验能否成立」的开关（[§ 3.1](06-knowledge-graph-section-3-sec3.md)）；在本节的落地顺序里它还有第二个作用——它是下一步抽取管线的输出形态（见 Step 4）。先建抽取再补 schema，等于让抽取输出的形态反向决定模型，之后每加一条约束都要重跑存量数据。

**Step 3：数据源识别与对接（1–3 周【经验，随源类型数量与是否需要打通权限、网络通道变化】）**

- 列出所有相关数据源（业务库、数仓、日志、文档、API、第三方）；评估每个源的**可抽取价值**；设计「数据源 → 中间层 → KG 实例」的 ETL 链路。
- 决定批处理（Airflow / DolphinScheduler）还是流处理（Flink / Kafka Streams）——判据是「这张图允许多久不同步」，而不是技术偏好。
- **产物**：数据源清单（源 → 抽取方式 → 频率 → 贡献哪些实体/关系类型）+ ETL 链路图。
- **判据**：对每个源回答「它贡献哪些实体类型、哪些关系类型」，答不出的先不接。再挑一个冷门但关键的实体类型（例如某类资质、某个罕见的关联关系），看它在清单里有没有源——没有，说明清单是按系统目录抄的，不是按问题倒推的。
- **为什么必须这一步 / 为什么在这个位置**：抽取管线的工作量按「源类型 × 抽取方式」增长，源的形态（结构化 / 半结构化 / 纯文本）直接决定管线复杂度与校验方式。放在 schema 之后，才能在这一步就发现「某类关系根本没有数据源」，而不是等抽取阶段才发现。

**Step 4：抽取 pipeline 构建（4–12 周【经验，随源数量与文本占比变化】）**

- 四项能力各自选型并连成一条管线：**实体识别（NER）**、**关系抽取（RE）**（均为基于规则 / ML / LLM 三选或混用）、**实体链接（Entity Linking）**（基于字符串 / 嵌入 / LLM）、**属性对齐（Property Alignment）**（跨源 schema 对齐）。
- 每条产出的三元组必须随行携带：来源（哪份原文或哪张表）、抽取方式、置信度、抽取批次号。
- **产物**：**候选三元组集合**（含来源与状态字段）。
- **判据**：抽 200 条候选三元组，逐条回到原文核对是否被支持，得到**幻觉率**；再把原文里明显存在但没被抽出的关系单列，得到**漏抽率**。两个数必须分开记——处置方式相反：幻觉靠加校验与提高门槛，漏抽靠扩语料与替换抽取方式。第二个判据：随便挑一条，能否回答「谁抽的、依据什么」。
- **为什么必须这一步 / 为什么在这个位置**：图的收益来自覆盖率，而覆盖率由抽取决定（[§ 7.2](06-knowledge-graph-section-7-sec7.md) 已就此立过判据）。它必须排在 schema 之后（抽取的目标是 schema 里的类型）、校验之前（校验需要可检查的输入）。

**Step 5：质量校验（2–4 周【经验，随校验层数与专家抽检比例变化】）**

- 三层校验串联，缺一层就会漏掉一类错误：**语法校验**（三元组是否符合 schema）、**语义校验**（SHACL、本体约束、reasoner 校验）、**业务校验**（专家抽检，例如 10% 抽样；比例随单条核对成本与可接受漏检率调整【经验】、业务规则校验）。
- 入库时必须落**状态**：自动抽取 / 已确认 / 已驳回。
- **产物**：**可信三元组集合** + **校验报告**（含各层拦截量与拒绝原因分布）。
- **判据**：从已确认子集抽 20 条，看能否回答「谁确认的、什么时候」；从自动抽取子集抽 20 条，看能否回答「哪一批抽出来的」。更硬的一条：两个子集能否在**查询层被分别取出**——只能整体取出的「可信集」不是可信集。
- **为什么必须这一步 / 为什么在这个位置**：这是把「抽取结果」变成「可举证事实」的唯一环节。它必须在入库前完成：入库之后再补，需要区分哪些三元组被确认过，而这个信息在那时通常已经不存在了，只能重建。

**Step 6：图存储与索引（2–6 周【经验，随自建还是托管、以及是否需要迁移既有存量变化】）**

- 选择图数据库（Neo4j / NebulaGraph / TigerGraph / JanusGraph / Stardog 一类，选型判据见 4.3）；确定数据模型（属性图 / RDF 三元组）。
- 建立索引（按实体类型、关系类型、关键属性）；配置副本、分片、备份策略。
- **产物**：**可用的 KG 存储** + 索引清单（哪个查询走哪个索引）+ 一次**恢复演练记录**。
- **判据**：把负载形状对一遍——高频点查与全图分析（PageRank、社区发现、特征回填）是否跑在同一套资源上；是，则先分离再上线。再验一次恢复：从备份恢复到干净实例，记录耗时与图规模的关系；没做过恢复演练的备份不算备份。
- **为什么必须这一步 / 为什么在这个位置**：存储与索引决定的是查询的**成本曲线**，而这条曲线一旦被下游依赖就难以调整。它必须排在查询与推理之前，因为查询契约（能查到什么、多久返回）由它决定。

**Step 7：查询与推理（3–8 周【经验，随对外查询契约条数与是否引入图算法 / GNN 变化】）**

- 暴露 **Cypher / SPARQL / GQL** endpoint；配置**图算法**（PageRank、Community Detection、Path）；集成 **KG Embedding / GNN** 模型（推荐 / 风控 / 反欺诈）。
- 为每个模型与向量登记**版本**，与它生成的数据绑定。
- **产物**：**KG 服务**（查询接口 + 图算法作业 + 模型与向量版本登记表）。
- **判据**：对每条对外承诺的查询写清「是精确查询（给出全部匹配）还是近似查询（Top-K 召回）」，并给出延迟预算。判据的动作：逐条问「这条查询返回的是全部答案还是最相似的 K 个」，答成「应该是全部」的就是没人核实过。
- **为什么必须这一步 / 为什么在这个位置**：这一步开始产生对外承诺。放到发布之后再做，下游会按「近似查询也很完整」的假设写业务，纠回来的成本远高于当时写清楚。

**Step 8：发布到下游（持续）**

- 三类消费方各自给形态：**BI / 数据分析应用**、**AI 应用（GraphRAG、QA、推荐、风控）**、**数据目录 / 血缘（KG 形式）**。
- 每个消费方按权限与密级在**视图层**裁剪，裁剪由平台执行而不是靠文档约定。
- **产物**：**KG 应用矩阵**（应用 → 用到的视图/子图 → 依赖的关系类型 → Owner）。
- **判据**：抽 2 个下游应用，问「如果某个关系类型明天改口径，你怎么知道」——答不出即没有依赖登记。再核一次权限：视图层是否由平台强制裁剪，还是靠约定。
- **为什么必须这一步 / 为什么在这个位置**：发布是把图从「一个项目」变成「一份资产」的那一步——它建立了依赖关系，而依赖关系是后面所有变更评审的输入。它必须排在最后，因为前七步的任何改动在发布后都会变成跨团队的协调成本。

**最常被跳过的一步是 Step 5 的「业务校验」那一半**：语法与语义校验有现成工具可跑，专家抽检只能靠人，因此在排期压力下最先被压成「先上线，抽检以后补」。跳过后第一个出问题的时点**不是上线时，而是第一次有人依据图上的结论做决策并被证伪时**——症状是团队发现无法区分「哪些三元组被确认过」，于是无法只回滚出错的那一批，只能整图重建。

### 4.2 关键技术点

**1. 图数据库选型**

- **做法**：按**负载形状**分档选，而不是按「是不是图数据库」选：OLTP 点查与局部遍历、海量数据的分布式遍历、原生并行分析、以 RDF/OWL/SHACL 语义栈为主、需与既有大数据存储共用后端、国产化与金融级合规，各自对应不同档位（候选与判据见 4.3）。
- **机制**：因为属性图的邻接是指针、多跳遍历是 O(V+E)，而关系库的每一跳都要再做一次连接代数运算，所以「多跳」在两类引擎上的成本结构不同——这是选型的物理依据，不是调优能抹平的差距。
- **失效条件**：**当同一套引擎上同时跑点查与全图分析时**，这条会坏：点查依赖局部性（缓存命中、索引命中），全图分析依赖吞吐（扫描全部节点与边），后者会持续冲刷前者的缓存。症状是两类查询**同时**变慢——团队通常先看到分析任务超时，扩容后又发现点查 P99 变差。
- **档位**：【经验】。

**2. 属性图 vs RDF 三元组**

- **做法**：属性图（Cypher 风格）把属性挂在节点与边上，工程实现与 OLTP 查询更省；RDF/OWL 走 W3C 标准栈，适合需要语义推理、跨组织交换与合规举证的场景。工业级图谱以属性图为主【经验】。
- **机制**：因为 RDF 把属性也写成三元组、并为任意连接模式维护多套索引排列，它用**存储放大**换取「引擎预料不到的连接方式也能查」；属性图把属性直接挂上去，读写更省，代价是查询原语被限定在引擎给定的模式匹配里。
- **失效条件**：**当查询模式需要引擎预想不到的连接方式时**，属性图会以「要写一堆变体查询、或先把数据导出到别处」的形式失效；反过来，**当只需要固定的几种模式匹配时**，RDF 的多套索引是纯成本——症状是存储与导入耗时显著高于同规模属性图，而查询收益为零。
- **档位**：【经验】。

**3. KG Embedding 模型**

- **做法**：按关系的代数性质选——**TransE**（平移假设，最基础）【公开，Bordes 等，NeurIPS 2013】、**RotatE**（把关系建模为复数空间旋转）【公开，Sun 等，ICLR 2019】、**ComplEx**（双线性，能表达对称关系）【公开，Trouillon 等，ICML 2016】、**R-GCN**（关系图卷积，处理多关系图）【公开，Schlichtkrull 等，ESWC 2018】。工具见 4.3。
- **机制**：因为这类模型把「关系」当成向量空间里的一种代数运算（平移、旋转、双线性型），它回答的是「这条边最可能连到谁」（链接预测），**不是**「这条边是否成立」——这决定了它只能用在召回与补全这类容错位置。
- **失效条件**：**当业务要求结论可举证时**，这条路会以「给出一个最可能的答案、但说不出依据」的形式失效，风控与合规场景无法上线。第二个失效点是模型换代：旧向量与新向量不在同一空间，而系统通常不记录向量由哪一版模型生成——症状是**检索结果整体退化且没有任何报错**。
- **档位**：【经验】。

**4. 抽取 pipeline 架构（LLM 抽取 + 规则校验 + Reasoner 验证 + SHACL 校验四步流水线）**

- **做法**：四步串联，顺序不可换——① **LLM 抽取**：用提示产出候选三元组；② **规则校验**：格式、类型、定义域/值域等硬规则先挡掉明显非法的；③ **Reasoner 验证**：用本体约束做一致性推导，矛盾即拒收；④ **SHACL 校验**：形状约束批量校验【公开，SHACL 于 2017 年成为 W3C 推荐标准】。把最贵的 LLM 放在最前是为了保召回，把便宜的规则校验紧随其后，是为了让最贵的 Reasoner 只处理已过滤的输入。
- **机制**：因为四步的失败模式互不重叠（LLM 是幻觉、规则是覆盖面、Reasoner 是逻辑矛盾、SHACL 是形状不符），串起来才能各拦一类错误；单用任何一步都会漏掉另外几类。
- **失效条件**：**当某一层被跳过时**（最常见的是把 LLM 抽取直接入库），流水线会以「幻觉与真实事实在同一张图里长得完全一样」的形式失效——没有确认状态、没有置信度、没有出处。症状是某次结论被证伪时无法定位是哪一批抽取引入的，只能整图重建。
- **档位**：【经验】；幻觉率与漏抽率的度量口径见 4.1 Step 4。

**5. 实体合并（Entity Resolution）**

- **做法**：三条互补判据并用——**基于规则**（字符串相似度、ID 规范化）、**基于嵌入**（向量近邻）、**基于图**（Graph-based ER，用邻域结构判定同一实体）；结果进候选池，按**版本化的合并规则**执行，并保留证据（谁和谁合并、依据哪条规则、什么置信度；表结构见 [§ 3.2.4](06-knowledge-graph-section-3-sec3.md) 的 `kg_entity_merge_evidence`）。
- **机制**：因为「同一实体」在真实数据里没有唯一判据（ID 不同、名称有变体、有错别字），合并本质上是**概率判断**；把它写成可回放的规则加证据，判断被质疑时才能回退重算。
- **失效条件**：**当合并规则随业务演进被改动时**，若没有规则版本与证据，已合并的存量无法重放——症状是「改完规则后新旧数据形态不一致」，且无法判断哪些合并是旧规则留下的。第二个失效点：阈值调松导致错误合并（两个人被并成一个），而错误会**沿关系传播**，症状是下游推荐/风控出现「明显不该有关联的两个实体有了关联」。
- **档位**：相似度阈值随语料与语言变化，不给通用值【经验】。

**6. 图数据库性能调优**

- **做法**：索引（按实体类型、关系类型、关键属性）、缓存、分片、副本、查询计划五项一起看；对多跳查询**显式限定起点与跳数**，无界遍历是这类系统最常见的性能事故来源。
- **机制**：因为遍历成本随「从起点出发实际访问到的节点与边」增长，而不是随全图规模增长，所以杠杆在「起点有多确定、跳数有多界」，不在硬件档位。
- **失效条件**：**当图规模进入亿级三元组量级【经验，量级提示，不是任何一家公司的实测阈值】而查询仍是无界遍历时**，这条会以「核心查询 P99 随规模持续劣化」的形式坏掉；此时加机器收效递减，因为瓶颈在访问面。判断方法是看 P99 随规模的变化趋势，而不是看总三元组数。
- **档位**：【经验】。

**7. 混合查询（Hybrid Query：图查询 + 向量召回）**

- **做法**：先用图的结构条件缩小候选集（限定类目、时间窗、关系可达），再在候选集内做向量近邻；**Neo4j 5+ 提供内置向量索引**，可与 Cypher 写在同一个查询里（具体能力边界请以官方文档当前版本为准）。每条向量必须记录生成它的模型与版本。
- **机制**：因为结构条件把候选集从全量压到一个小集合，ANN 检索的召回率与延迟都会变好（候选越少，近似越不容易漏掉真近邻），所以「先结构、后相似」在成本与质量上同时优于「先全量相似、再过滤」。
- **失效条件**：**当结构条件写得过窄或过宽时**，这条会坏——过窄把正确答案排除在候选之外（症状是「明明有这条数据却搜不到」），过宽则退化成全量 ANN。第二个失效点是向量与原件不同源更新：症状是「原文已改，检索仍返回旧语义」，属于静默失败。
- **档位**：【经验】。

**8. 图可视化**

- **做法**：按用途分三类选——探索与调试（**Neo4j Browser / Bloom**、**Neovis.js**）、演示与叙事（**GraphXR** 这类三维可视化）、嵌入业务的商业组件（**Cambridge Intelligence** 的 KeyLines / ReGraph 一类）。候选见 4.3。
- **机制**：因为可视化的瓶颈是「一屏能承载多少节点」而不是渲染速度，所以正确用法是**先查询收敛、再画**，而不是把全图摊开。
- **失效条件**：**当直接对全图或上万节点渲染时**，这条路会以「画出来看不出结构、前端卡死」的形式失效。更隐蔽的坏法是把图当监控用：图是关系结构不是指标，「图上密度变大」无法对应到任何可告警的阈值，于是它既不会报警也不会被看。
- **档位**：【经验】。

**9. KG 治理（Owner 制度 / 版本管理 / 变更评审 / 质量 SLA）**

- **做法**：每个实体类型与关系类型有 Owner（落到人）；schema 变更走评审并按版本发布；质量指标（准确率、覆盖率、一致性、完整性）定期度量并设 SLA。**目标值必须由消费场景反推，不给通用阈值**——例如对外问答所依赖的可信子集，其抽样准确率目标应由「答错一条的代价」倒推，不同场景落在 90%–99% 区间内都可能是合理的【经验，区间与场景挂钩】；覆盖率同理，先问「漏掉的那部分会不会被当成『不存在』回答」。
- **机制**：因为图上的一个错误会沿关系传播（错误合并、错误关系），而使用者默认「查到的就是全部」，所以治理的对象不是单条数据，而是**证据链与状态**：每条三元组要能回答「谁抽的、依据什么、是否被确认」。
- **失效条件**：**当质量指标只被度量、没有被消费时**，治理会以「报表天天发、无人据此改动」的形式失效——判断信号是「最近一次因质量指标触发的改动是什么」，而不是「最近一次报表什么时候发的」。第二个失效点是 Owner 写成团队而不是人：变更会停在评审队列里，没人被点名。
- **档位**：【经验】。

**10. LLM 增强抽取**

- **做法**：四种手段并用——**Few-shot prompting**（少量示例固定输出格式）、**Self-Verification**（让模型复核关系是否有原文支持）、**Chain-of-Thought**（先定位证据句再抽关系）、**Tool-Use**（让模型调用既有 NER / RE 工具，而不是全靠生成）。工具见 4.3。
- **机制**：因为 LLM 的主要失败模式是「生成看起来很合理、原文却不支持的关系」，而 Self-Verification 与 CoT 都把「先找到证据再下结论」写进流程，它们降低的是**幻觉率**而不是漏抽率——两个指标必须分开看，否则会把「模型变保守」误读成「抽取变好」。
- **失效条件**：**当抽取对象是长文档或术语密集的领域文本时**，这条路会以「幻觉率下降而漏抽率上升」的形式偏移（模型倾向于不抽），表现为覆盖率上不去；此时要补的是分段策略与领域词典，不是再加提示词。第二个失效点是把 LLM 抽取结果直接当已确认事入库——等于取消了 Step 5，症状与上面第 4 条相同。
- **档位**：【经验】；用 4.1 Step 4 的幻觉率与漏抽率两个抽检指标度量。

### 4.4 存量迁移

**① 先做什么：一个已确权的主题域 + 一张只读派生图（立刻见效、可一步回退）**

不改数仓、不改业务库：选一个 Owner 明确、口径相对稳定的主题域（例如客户域），从其明细层用 **SQL 解析**把已经存在的关联关系直接转成图上的边，先建**只读派生图**——**图是派生物，不是真源**。回退动作是「删掉这张派生图」，不触及任何真源。这一步立刻就能交付一个可见产物：把原本散落在多张表、多个 JOIN 里的关系显式化成边。判据：挑 3 个 Step 1 里的业务问题，看这张小图能不能答；答不了通常不是图的问题，而是主题域选错了（选了关系稀疏或口径还在变的域）。

**② 历史资产怎么分类处理（三类，处置方式不同）**

- **可从 SQL 直接推导的**：数仓里已经用 JOIN、外键或关联表表达出来的关系——按 SQL 解析直接转边，**不需要 LLM 抽取**。这是最快见效的一批，也应当是第一批：不需要标注、不需要抽检，出错也最容易定位到源 SQL。
- **需要抽取的**：文档、日志、客服记录、工单这类文本资产。按 [§ 3.3](06-knowledge-graph-section-3-sec3.md) 的决策表选路线，并且**先抽可核验的那一小片**（有明确术语表、有对照答案的领域），而不是从最脏的语料开始——从脏语料开始会让幻觉率与漏抽率同时不可解释。
- **打标挂账的**：本轮无法处理的资产（历史遗留系统、外部采购数据、来源无法确权的数据）。处置方式是在数据源清单上**标注「未纳入」与原因**，而不是假装它们不存在。挂账清单每季度复核一次：它的价值是让「这张图的覆盖面」有一个诚实的边界，而不是一个看起来完整的数字。

**判据（对应上面三类）**：从图上随机抽 100 条边，统计多少条能追到具体的源表 / 源字段、多少条来自文本抽取、多少条来自人工录入。追不到源的边即为**孤儿边**——它们允许存在，但必须有登记与责任人；孤儿边占比不下降，说明抽取管线在往图里灌没有出处的数据。

**③ 双轨怎么维持、维持多久**

双轨期的第一件事是**显式声明真源**：**数仓 / 业务库是真源，图是派生**（[§ 7.6](06-knowledge-graph-section-7-sec7.md) 的组合一已就此立过边界）。维持期要同时做三件事，缺一件双轨就会变成两份真相：

- **抽取管线与真源口径联动**：真源的口径变更必须触发图上实例重跑。否则同一条关系会在两处独立维护并逐渐分叉，而分叉不报错。
- **对外服务优先走可信子集**：先用图上「窄而可信」的部分承接业务，把覆盖面作为独立的、可增长的目标，而不是一开始就把抽取结果与已确认结果混着发出去。
- **把不一致做成指标**：抽取滞后、孤儿边占比、口径变更后的重跑覆盖率——这三项要能被度量，否则「图是否跟得上真源」只能靠感觉。

双轨时长与真源的口径变更频率同量级【经验，随领域稳定性变化】：口径一周一变，双轨就不可能短期退出；口径一年一变，双轨可以在几个季度内收口。

**④ 什么信号说明可以退出双轨**

四条同时成立才退：其一，真源口径变更后，图上实例能在约定的重跑窗口内追平，且**不需要人工介入**；其二，对外查询中依赖「未确认抽取结果」的比例已降到可接受范围，且这个比例被持续度量（而不是估过）；其三，孤儿边数量不再增长——仍在增长说明还有人在往图里塞没有出处的数据；其四，图上回答的关键业务问题已有实际调用量。最后一条最容易被忽略：**没有消费方的图谱退出双轨，只是把一套没人用的东西固定下来**，此后每次真源变更都要为它付一次维护成本。

### 4.5 模板 / 示例

**模板一：Neo4j Cypher —— 客户-订单-商品图谱建模**

```cypher
// 先建唯一性约束，再灌数据：重复实体的第一道防线
CREATE CONSTRAINT customer_id IF NOT EXISTS FOR (c:Customer) REQUIRE c.customer_id IS UNIQUE;
CREATE CONSTRAINT product_id  IF NOT EXISTS FOR (p:Product)  REQUIRE p.product_id  IS UNIQUE;
CREATE CONSTRAINT order_id    IF NOT EXISTS FOR (o:Order)    REQUIRE o.order_id    IS UNIQUE;

// 幂等写入：MERGE + SET，重跑不产生重复节点与重复边
MERGE (alice:Customer {customer_id:'C001'}) SET alice.name='Alice', alice.city='Beijing';
MERGE (bob:Customer   {customer_id:'C002'}) SET bob.name='Bob',   bob.city='Shanghai';
MERGE (phone:Product  {product_id:'P001'})  SET phone.name='某机型', phone.category='手机';

MERGE (o:Order {order_id:'O001'}) SET o.placed_at = datetime('2025-10-08T10:00:00'), o.amount = 14998;
WITH o MATCH (a:Customer {customer_id:'C001'}) MERGE (a)-[:PLACED]->(o);
WITH o MATCH (p:Product  {product_id:'P001'})  MERGE (o)-[:CONTAINS {quantity:1}]->(p);
MATCH (b:Customer {customer_id:'C002'}), (a:Customer {customer_id:'C001'}) MERGE (b)-[:REFERRED_BY]->(a);
```

**怎么用**：照抄的是「先建唯一性约束、再灌数据」这个顺序，以及「数量挂在边上（`CONTAINS {quantity}`）而不是节点上」这个建模判断；节点属性名与取值换成你自己的。**不要照抄 `CREATE` / `MERGE` 混用**——批量导入请统一成幂等写法，否则重跑一次就多一批重复边。

**模板二：复杂图查询（Cypher / 多跳推理）**

```cypher
// 近似推荐：朋友买过、自己没买过的商品，按路径数打分
MATCH (me:Customer {customer_id:'C001'})-[:REFERRED_BY]-(friend)-[:PLACED]->(o:Order)-[:CONTAINS]->(p:Product)
WHERE NOT (me)-[:PLACED]->(:Order)-[:CONTAINS]->(p)
RETURN p.name AS recommendation, count(*) AS score
ORDER BY score DESC LIMIT 10;

// 结构判定：同一设备在 1 小时内被多个账号登录（时间条件写在“这一次登录”上）
MATCH (d:Device)<-[l:LOGIN_FROM]-(c:Customer)
WHERE l.at > datetime() - duration({hours: 1})
WITH d, collect(DISTINCT c) AS accounts
WHERE size(accounts) > 1
RETURN d.device_id, [a IN accounts | a.customer_id] AS suspicious
```

**怎么用**：两个查询示范两种不同的判据——第一种是**打分排序**（结果近似，返回 Top-K），第二种是**结构判定**（结果要么成立要么不成立）。别把两者混着用。注意第二个查询把时间条件写在**边**上：登录时间属于「这一次登录」这个事件，不属于客户；若模型把时间挂在客户节点上，这个查询会静默返回错误结果。

**模板三：KG Embedding（PyKEEN 训练 RotatE）**

```python
from pykeen.pipeline import pipeline
from pykeen.datasets import Wikidata5M

result = pipeline(
    model='RotatE',
    dataset=Wikidata5M(),                 # 示例数据集，换成你自己的三元组集
    training_kwargs={'num_epochs': 100},
    optimizer='Adam',
    optimizer_kwargs={'lr': 1e-3},
    evaluator='RankBasedEvaluator',
    random_seed=42,                       # 固定种子：评估结果才可复现、可比
)

from pykeen.predict import predict_triples
predictions = predict_triples(
    model=result.model,
    triples=result.dataset.validation.mapped_triples,
    k=10,
)
print(predictions.df.head(10))
```

**怎么用**：照抄的是「训练 → 链接预测 → 人工看 Top-K」这个流程与固定随机种子的做法。数据集与超参必须换成你自己的；划分验证集时优先按**时间**切分而不是随机切分，否则评估分数会把「模型已经见过测试边」算成能力。输出的 Top-K 是候选不是事实，落库前仍要走 4.2 第 4 条的校验流水线。

**模板四：LLM 抽取三元组（Python / LangChain）**

```python
# LangChain 0.1 起模型与提示模板拆成独立包：模型走 langchain-<厂商>，提示模板走 langchain-core
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

llm = ChatOpenAI(model="<你的模型>", temperature=0)   # 抽取任务用 temperature=0

prompt = ChatPromptTemplate.from_template("""
请从文本中抽取实体与关系，遵守 schema：
- 实体类型：Customer, Order, Product
- 关系类型：PLACED (Customer->Order), CONTAINS (Order->Product), REFERRED_BY (Customer->Customer)

输出 JSON，且每条关系必须附上支持它的原文片段：
{{"entities":[{{"type":"Customer|Order|Product","name":"...","attrs":{{}}}}],
  "relations":[{{"type":"PLACED|CONTAINS|REFERRED_BY","from":"...","to":"...","evidence":"原文片段"}}]}}

文本：{text}
""")

result = llm.invoke(prompt.format_messages(text="（你的文本）"))
# 之后依次：格式与类型校验 → 逐条核对 evidence 是否真在原文里 → 通过后才进可信子集
```

**怎么用**：照抄的是「temperature=0 + 强制输出 `evidence` 字段」这个结构——`evidence` 是这版提示词里最重要的字段，它把 4.1 Step 4 的抽检从「人对整段文本」变成「人核对片段」。模型名与文本换成你自己的；输出**不要直接入库**，要走完校验流水线。

### 4.6 成本：这套东西的账单

知识图谱的账不是按「节点数」结的，是按**抽取次数 × 抽取单价 + 人工核验量**结的。存储只占那张图的地方；真正随「文档量 × 关系类型数」放大的，是抽取与核验。

- **抽取算力随「schema 变更重跑」放大。【推算】** 抽取成本 ≈ 文档数 × 单文档抽取调用单价；本体 / schema 一改（§4.1 Step 2 要求能复用的一律不新造），已抽过的语料要按新 schema 重抽，成本按「文档数 × 改动次数」累积，而不按节点数。这是本主题最反直觉的一格——**改一次 schema，账单不是增量，而是增量 × 存量**。单文档单价取自你所用模型服务官方定价页的当期价格。
- **人工核验是最大项，且不可省。【推算】** 核验工时 ≈ 待入库三元组数 × 单条核对耗时；LLM 抽取把「人读整段」压成「人核对 evidence 片段」（§4.5 模板四），但没有取消这一步——§4.1 Step 5 的质量校验是唯一没工具包办的环节，也就必然按人时结账。**为什么贵在这里**：抽取对象是概率生成的，入库前的证据核验只能靠人，量随「文档量 × 关系类型数」而非节点数涨。
- **存储与索引：常态不大，但点查与分析要分账。【经验】** 图库存储多落在 GB 到 TB 量级；真正贵的是把高频点查与全图分析挤在同一套资源上——它会逼出一次为扩容而做的引擎改造（§4.3「图存储」一行的误选代价），账单形态是点查 P99 恶化后被迫分离计算引擎。KG Embedding / GNN 训练（PyKEEN、PyG）的算力通常不是主项。
- **「文档语料 → 图」这条路有可核验的成本锚点。【公开】** 微软 2024 年开源的 GraphRAG 在其仓库文档里给出了索引构建的成本量级提示，可作为这条链路的成本参照自行核验；厂商材料只当锚点，不当行业事实。
- 通用账法（分账、单位成本）见 [§11 数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节只标这个主题把成本放在「抽取次数」这一格。

### 4.7 容灾与故障演练

图库能不能切可用区是通用题（多副本即可，[§12 灾备](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)）。本主题独有的失效形态是**「图还在，一条结论却证不出来」**——它是派生物，真源在数仓与语料里，所以容灾的靶心是**抽取可重放**与**边可溯源**。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 真源口径变更、图未联动重跑 | 图上结论与真源静默分叉 | 以真源为准，关闭对外可信子集的自动发布 | 改一次真源表结构，看抽取管线能否自动触发重跑并追平 | 【经验】随重跑窗口与口径变更频率变 |
| 抽取管线升级 / 换模型 | 已入库三元组与新版本不一致，偏差无法解释 | 冻结可信子集，新版只进灰度 | 用旧版重放同一批语料，比对三元组差异率 | 【推算】RPO≈0（语料与登记在版本库，可重放重建），暴露靠重放频率 |
| 图库索引损坏 | 多跳遍历不可用 | 从真源 + 重放抽取重建（图是派生物，见 §4.4 ③） | 隔离环境重放一个小主题域，验证能否还原边与证据 | 【经验】小时级到天级，随语料量变 |

**为什么不适用跨地域容灾**：图是派生资产，其真源（数仓 / 语料）本就有自己的容灾方案；把图做成跨地域双活，保的是一份可重放重建的派生物，收益不抵运维。本主题真正的失效是**结论不可复现**——同一批语料用登记的抽取器与随机种子能不能重放出同一张图（§4.5 模板三固定随机种子就是为这一条）。它只能用「固定语料集 + 重放比对」暴露，不适合多云切换演练。

### 4.8 演进路线：0 → 1 → 100

这个主题的三级坎都踩在同一个关系上——**图是派生物、真源在别处**，只是每级把它绷紧的程度不同：

- **0 → 1（最小可用）：一个已确权主题域的只读派生图，SQL 解析直接转边、不上 LLM**（§4.4 ①）。此阶段**变贵的是**人力——把散在 JOIN 里的关系显式化，本身不烧算力；**先坏的是「图是派生物」这条边界**：一旦有人往图里直接写而不回真源，真源就分裂成两份。
- **1 → 100（规模化）：多域铺开 + 抽取管线 + evidence 核验 + 图与向量混合查询**（§4.2、§4.4）。此阶段**变贵的是**抽取次数（见 §4.6）与人工核验；**先坏的是覆盖率与孤儿边**——边只增不减，孤儿边占比不下降，说明抽取管线在往图里灌没有出处的数据（§4.9 第 3 问）。
- **100 →（下一道坎）：GraphRAG 这类「文档语料 → 图 + 社区摘要」的工业路径、Agent 自主构建图谱、跨源融合与本体对齐**（§1.4 AI 原生阶段）。此阶段**变贵的是本体的对齐与融合成本**——多来源合并时要逐条仲裁冲突；**先坏的是 schema 与证据的一致性**：同一实体的两条来源给出矛盾属性却无仲裁规则时，图上会出现「都对、也都举不出证」的结论。

### 4.9 自检清单

- [ ] 抽 20 条三元组，能否逐条回答「谁抽的、依据哪句原文 / 哪张表的哪个字段、是否被人工确认」？
- [ ] 抽 3 条对外回答用到的事实，能否从图上还原出一条追到源表 / 源字段的路径？
- [ ] 图上随机抽 100 条边，有多少条追不到真源（孤儿边）？孤儿边是否逐条有登记与责任人？
- [ ] schema 是否写明了每个关系的定义域与值域？只写「有关系」的，按未定义 schema 处理。
- [ ] 实例层有多少属性未在 schema 中声明？兜底类型（`Other` 一类）下的实例占比是多少？
- [ ] 核心查询的 P99 是否随三元组规模增长而持续劣化？是，则考虑按主题拆分或分离分析负载。
- [ ] 高频点查与全图分析是否跑在同一套资源上？
- [ ] 向量存储里每条向量是否记录了生成它的**模型名与版本**？
- [ ] 混合查询中，「返回 Top-K」与「返回全部匹配」是否在对外文档里被分开写明？
- [ ] 实体合并是否留有证据（谁和谁合并、依据哪条规则、规则版本）？能否用旧规则重放一遍？
- [ ] 对外服务使用的是全部三元组还是已确认子集？两个集合能否在查询层被分别取出？
- [ ] 最近一次因质量指标而发生的改动是什么？答不出，即指标只被度量、没有被消费。

### 4.10 小结

> 本节小结：整条落地链里唯一那个决定成败的环节，是 **Step 5 的质量校验**——它决定图上的一条结论能不能被举证，而它既不产出可展示的界面、也没有现成工具包办（业务抽检只能靠人），因此在排期压力下最容易被压成「先上线，以后补」。它被跳过后不会立刻报错，代价要等到第一次有人依据图上的结论做决策并被证伪时才结清，而那时已经无法定位是哪一批数据引入的。
>
> 判断自己是否已经越过那条线，只需回答一句：**图上的一条结论被质疑时，你能不能拿出它的证据与来源？**
>
> 💡 **思考锚点**：把 4.4 的三类存量（SQL 可直接推导 / 需抽取 / 打标挂账）套到你手上已存在的图谱上——随机抽 100 条边，三类各占多少、追不到真源的孤儿边又有多少？若孤儿边占比这一季没有下降，你现在的抽取管线是在补覆盖，还是在往图里灌没有出处的边？
