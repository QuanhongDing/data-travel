## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

原表把「能力」与「代价」压进了同一个 1–5 刻度。十行里高分意味着「强」，但「工程门槛」一行给本体建模打最高分 5、给知识图谱 4 分，而表下的结论把「工程门槛」列为**知识图谱**的劣势之一；「学习曲线」一行直接写成「5（陡）」——同一个 5，在别的行是优点，在这一行是账单。这不是笔误，而是等权刻度混用两种方向之后的必然后果。同一类错位在 05 本体建模的对比章里以相反的形式出现过：那里「工程门槛」一栏同样把最高分给了本体建模，而那里的结论也把「工程门槛」列为劣势——同一条维度，一张表里 4 分是劣势，另一张表里最高分 5 分也是劣势，可见这个刻度本身不携带方向。

原表的可核对性也值得说一句：结论行写「KG 在『多跳关联查询、推理能力、AI 友好度』4 项满分」，而该列实际拿到满分的是 3 项——一处逐格就能数出来的出入。这类出入本身不致命，但它说明这张表在成文时没有被数值核对过；而**一张没有被数值核对过的表，恰好是最好的证据：它的分数不是测量结果，是排版结果**。

比算术更实质的问题有两层。第一层：这十行不在同一根轴上——五行量「能力」（多跳查询、聚合、推理、语义检索、AI 友好度），两行量「代价」（工程门槛、学习曲线），三行量「团队与生态」（多源对齐、可演化性、工具成熟度）。把它们等权相加得到的顺序没有意义。

第二层：**同一行的含义随架构位置翻转**。「大数据量聚合」一列给 KG 打 3 分并被视为两项劣势之一，但主文件 §1.3 把 KG 定位为 DWS / ADS 之上的「关联层」——在这个形态里聚合根本不落在图上，这一行不构成约束；只有当你把明细也塞进图、让图承担分析时，它才是否决项。同一份 3 分，一种架构里是无关项，另一种架构里是致命的。

第三种混淆是「能不能」与「好不好」。关系数据库在「多跳关联查询」上得低分，并不是「差几分」：SQL 用递归 CTE 完全能表达多跳，主文件 §2.2 把 Cypher 的 `MATCH` 表述为带变量的图模式匹配，两者语义等价、**差别只在执行模型**（7.3.1）；而「推理能力」一栏得最低分是**结构上不具备**——主外键只能拒绝非法写入，推不出「A 与 C 间接关联」这类未写下的事实。这两类差距不能用同一个刻度表达，这也是本节把第一批判据设成「能力边界」而不是「能力评分」的原因。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 查询的出发点 | 我是从少数实体的邻域出发做有界跳数遍历，还是对一个集合做全量统计 | 这是决定「邻接指针」与「连接代数」谁便宜的**唯一源头**（7.3.1）。这一条答错，后面所有比较都失去意义 |
| 关系是数据还是约束 | 我只要查出关系，还是要机器判断「两个实体必然有关系」 | 推出未写下的事实是本体 + 图这条路的独占能力，也是它全部代价的来源。只要前者，引入公理层就是纯开销 |
| schema 的时机 | 实体类型先定，还是从数据里事后归纳 | 先定 schema 换可校验性，事后归纳换覆盖率，两者都不可逆（本章 §3.1 把这条写成模式分岔的源头） |
| 多源标识是否需先判同 | 同一客户在两个系统里是不是同一个节点 | 判同（实体链接 / OneID）是建图的前置工序而不是图的一部分；判错一次，图上每一跳都连带错 |
| 结论要可举证还是要能泛化 | 给监管 / 风控举证的结论，还是给推荐一个排序分 | 决定推理落在「路径」上还是「向量」里——两种结论形态不可互换（7.3.3） |
| 图的度数分布 | 我的图是近似均匀的，还是少数节点度数极高 | 决定遍历代价的量级：幂律图上一个超级节点会把「一跳」变成一次大范围扩展（7.4 给推导） |

六条里最容易被跳过的是第一条与第六条。第一条非黑即白，答完就能淘汰一半候选；第六条不看，则会在「POC 用均匀的测试图跑得很好、上线换成真实幂律图后慢一个量级」上返工（这一量级属于【经验】，推导见 7.4 第一条）。使用顺序建议是：先答 1、2（要不要图、要不要推理），再答 3、5（图长什么样、结论要不要能举证），最后答 4、6（工程量与数据形状）。

**关于排序**：本节不取消排序能力，只把排序的依据摆到明处——7.6 的矩阵每行都带「不选它的原因」列，7.8 每行都带「关键理由（机制层面）」列。凡是要给出顺序的地方，都要求相邻列给出机制依据；**给不出依据的顺序，就是把场景相关的结论写成了绝对结论**。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型实现 / 使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 关系数据库 | 精确事实查询与事务 | B+ 树索引 + 关系代数：一次连接 = 索引查找 + 中间结果（哈希 / 排序合并） | PostgreSQL、MySQL、Oracle | 开源与商业并存 |
| 维度建模 / 数仓 | 面向聚合与 BI 的物理组织 | 事实表 + 维度表 + 列式存储与向量化执行，按列读 | 各 MPP / 列存数仓 + dbt 生态 | dbt-core 开源；数仓商业 |
| 属性图存储（知识图谱的常见载体） | 实例层的关系网络 | 节点 + 边，引擎用无索引邻接（邻接指针）做多跳遍历 | Neo4j、NebulaGraph、TigerGraph、蚂蚁 TuGraph、GraphScope、HugeGraph、JanusGraph、Amazon Neptune | 社区版开源与商业版并存 |
| RDF 三元组库 | 标准化的图（主体-谓词-客体） | 三元组的多索引排列 + SPARQL 图模式匹配；语义由 RDFS / OWL 分层给出 | Stardog、GraphDB、Apache Jena、Virtuoso | 开源与商业并存 |
| 本体建模（OWL） | 可推理的 schema 契约 | 描述逻辑公理 + reasoner 推导蕴含事实（详见 [05 本体建模](../05-ontology-modeling/05-ontology-modeling.md)） | Protégé、Apache Jena、ELK / HermiT / Pellet | W3C 开放标准；工具链开源与商业并存 |
| 向量数据库 | 语义近邻检索 | ANN 索引（HNSW / IVF 一类）用「访问候选子集」换延迟，返回 Top-K 与分数 | Milvus、pgvector、Qdrant、Faiss | 开源与云服务 |
| 图嵌入 / GNN | 把关系结构压进向量的推理 | 关系三元组在向量空间的代数约束（TransE 的 h + r ≈ t、RotatE 的相位旋转）；GNN 走消息传递 | PyG、DGL、OpenKE、PyKEEN、AmpliGraph | 框架开源 |
| 大模型（隐式知识层） | 不建图谱的事实问答 | 知识压在参数里，靠上下文提示取用；不提供可枚举的关系 | 通用 LLM + RAG | 按调用计费的 API 与自托管 |

这八行分三层、四族。**按层分**：关系库、维度建模、本体描述 schema（或物理结构），属性图 / RDF 库描述实例，向量库与图嵌入描述表示——「谁替代谁」这个提法在跨层时基本是错的。**按族分**：**集合代数族**（关系库、维度建模）以「集合运算」为原语，聚合与筛选最便宜；**遍历族**（属性图、RDF 三元组库）以「点 + 邻域」为原语，多跳最便宜；**向量族**（向量库、图嵌入 / GNN）以「相似度」为原语，泛化能力最好但结论不可逐跳解释；**符号族**（本体、大模型）一个管可推理的 schema，一个管隐式知识。**先分层再分族，能省掉一半无意义的比较**——把知识图谱和维度建模放在一行打分的做法，跳过的正是这一步。

同族内部的差别比跨族小，但仍有两处必须问清：**第一，语义标准要不要跟着走**——属性图与 RDF 三元组库在遍历性能上同向，差别在 RDF 走 W3C 标准栈（RDF / RDFS / OWL / SPARQL），跨组织交换与合规举证时这份标准本身就是资产。**第二，推理发生在哪一侧**——路径匹配在查询期、公理推导在加载期、嵌入在训练期，三者对「结论能否举证」的回答完全不同（7.3.3）。

还有一个常被当成实现细节、其实是选型变量的差别：**属性图与 RDF 三元组库的存储形态不同**。RDF 把属性也写成三元组，为了让任意连接模式可用，通常要为同一份数据维护多套索引排列（按主体、按谓词、按客体一类），存储因此成倍放大；属性图把属性直接挂在节点与边上，读写更省，代价是查询原语被限定在引擎给定的模式匹配里。判据因此是：**查询模式是否需要引擎预想不到的连接方式**——需要，就为 RDF 的索引放大付钱；不需要，属性图更省。

还有一层常被漏掉的候选：**抽取与对齐管线**（命名实体识别、关系抽取、实体链接、图谱融合，代表方法与工具见主文件 §2.3 与本章 §4.3）。它不参与「图与表谁快」的比较，却常常是项目成败的分水岭——图的收益来自覆盖率，而覆盖率由抽取决定。选型时要先问「我的实体和关系从哪来、能不能自动抽出来」：文档稀疏、术语混乱、标注缺失的领域里，抽取覆盖率上不去，再强的图引擎也只能回答很少的问题。本章 §3.1 把这件事写成约束：**先行本体在文档密集场景里常导致抽取覆盖率极低**。

最后一列（许可与商业模式）常被放到最后看，但它的机制后果很清楚：**开源社区版与商业版的分界通常落在「集群 / 高可用 / 细粒度权限 / 审计」这些运维能力上，而不是查询能力上**。因此许可带来的风险不是「功能不够」，而是「规模上去之后必须重新采购或自建这些运维能力」。判断方法是逐条核对开源版与企业版的功能对照表，把差异项翻译成运维工作量——这项工作在选型阶段做，成本最低。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 遍历原语：无索引邻接 vs 连接代数

**机制是什么**：图引擎把「关系」存成物理邻接——节点记录直接指向它的边记录，一次跳转是指针解引用（业界称无索引邻接 / index-free adjacency）；SQL 把关系存在索引与中间结果里，一次连接是索引查找加上中间结果的构建（哈希表或排序归并）。两者表达的是同一件事，代价结构不同。

**它在各候选中的实现差异**：

| 候选 | 一跳的代价 | 第 k 跳的代价由什么决定 | 全量聚合 |
| --- | --- | --- | --- |
| 关系数据库 | 索引查找（B+ 树） | 每一步中间结果的基数（连接顺序可被优化器改写） | 列存缺失时按行读，代价高 |
| 列存数仓 | 分区裁剪 + 列读取 | 中间结果的列式批次大小 | **最优**（向量化 + 列裁剪） |
| 属性图 | 邻接指针解引用 | 当前边界上所有节点的出边总数（受关系类型索引削减） | 需要额外的列式导出 |
| RDF 三元组库 | 索引排列查找 | 多索引选择与连接顺序 | 需要额外的列式导出 |
| 向量库 | 不适用（没有「关系」原语） | 不适用 | 不适用 |

**由此必然导出的性质**：因为邻接是物理指针，所以从少数起点出发的有界 k 跳遍历，代价正比于**触及的边界宽度**、与全表规模基本无关；而 SQL 的同一查询，代价由**每一步的中间结果基数**决定，每加一跳就要与下一张表再做一次连接并可能物化中间结果。**因为跳数进入指数，所以两条曲线的差距随跳数放大而不是保持固定倍数**——这就是「三跳以内差别不大、五跳以后不可同日而语」的机制来源。代价是三项：一是**切分图会切断邻接**——跨分片一跳变成一次网络往返，所以图库的水平扩展比键值存储难，分布式图要把「跨分片跳数占比」当容量指标看；二是**写放大**——新增一条边要同时维护两个端点的邻接（无向边更甚）；三是**超级节点**——邻接指针不改变「必须枚举该节点的出边」这件事，一个百万度节点的单跳扩展就是百万次指针解引用（7.4 给量级）。

主文件 §1.1 把图遍历写成 O(V+E)：那是**访问整个连通分量**（PageRank、连通分量一类全图算法）时的复杂度上界；从少数实体出发的有界深度遍历只触及深度内的边界。两者不矛盾，但它们对应两种截然不同的负载，**混用同一套引擎去跑，就是本章 §3.1 所列「图数据库选型错误」反模式的机制根源**。

还有一处工程细节值得写进判据：**能不能按关系类型过滤边，比引擎的基准测试数字更重要**。一次扩展若只能枚举全部出边、再在内存里筛类型，超级节点的代价就会实际发生；若引擎支持按关系类型的物理索引，同样的扩展只触碰目标类型的边。判断方法是看官方文档里「关系类型索引 / 标签索引」的实现方式，并在压测时把类型过滤条件加上与去掉，观察耗时是否同阶。

**公开证据**：图查询语言已经标准化——GQL 于 2024 年成为 ISO 标准（ISO/IEC 39075:2024），主文件 §2.1 已把 GQL 与 Cypher / nGQL / SPARQL 并列为图查询语言【公开】；RDF 侧 SPARQL 1.1 与 RDF 1.1 分别是 W3C 在 2013 年与 2014 年发布的推荐标准【公开】（来源：W3C 推荐标准；具体条款与勘误请以 W3C 官方规范页面当前版本为准）。标准化的意义是：语义被固定后，「同一句多跳查询在不同引擎上等价」才成为可验收的事，迁移成本才可估。

**失效条件**：当查询不落在「少数起点的邻域」上时（全表统计、全图算法、全量特征回填），邻接优势归零，列存直接胜出。判断自己的负载落在哪一侧，只需统计一段时间内「从多少个百分点出发、平均触及多少实体」——触及集合接近全量时，图就是错的载体。

#### 7.3.2 schema 的时机与硬度：先验定义 vs 事后归纳

**机制是什么**：schema 是「能进入图的形状」。它同时决定两件事：写入端能否拒绝不合规数据，查询端能否推理——本章 §3.1 的原话是「没有类与属性的约束，系统能做的是『检索』而不是『推理』」。

**它在各候选中的实现差异**：

| 候选 | schema 从哪来 | 有多硬 | 写入端能否拒绝 |
| --- | --- | --- | --- |
| 关系数据库 | 先验 DDL | 强 | 能（类型 / 非空 / 外键） |
| 维度建模 | 先验模型 + ETL 约定 | 中（约定靠流程） | 部分（靠作业与测试） |
| 属性图 | 可选：标签与关系类型，约束可加可不加 | 弱到中 | 取决于是否启用约束 |
| RDF 三元组库 | 由 RDFS / OWL 分层给出，可选择用哪一层 | 可弱可强 | 需要形状约束（SHACL 一类）才生效 |
| 本体（OWL） | 先验公理集 | 强（语义层） | 不直接拒绝数据，但能检出公理集自相矛盾 |
| 向量库 | 无 schema，只有维度与距离度量 | 无 | 不能 |

**由此必然导出的性质**：因为图允许先写数据后定类型，所以新业务形态可以当天进图，不需要迁移表结构——这是「开放抽取型」在文档密集场景里覆盖率远高于先行本体的原因（本章 §3.1 已把「先定本体更严谨」列为被该约束推翻的直觉）。代价是**写入端没有任何东西阻止同一含义被两个谓词名表达、以及孤岛节点的产生**：治理成本从「上线前」推迟到「上线后且随时间复利」——图越大，事后统一谓词的代价越高，因为要同时重写数据与已经被下游固化的查询。这正是主文件 §1.2 所列「关系散落」「跨域融合难」两条痛点的机制解释，也是主文件 §2.4 那句「没有本体的 KG 是数据沼泽」的准确含义。

这条机制还有一个可操作的推论：**schema 的硬度可以分级引入，也应当分级引入**。写入端的最小约束（关系类型清单 + 命名空间 + 类型断言）成本极低，却拦掉了最难治理的一类脏数据（谓词同义）；公理层（可推理）成本高，只应该用在确实需要推出结论的地方。把两者混为一谈，会出现「为了拿到一点校验能力，先背上整套推理成本」这种事前不划算的决定。

**公开证据**：RDF / RDFS / OWL 的分层与 SHACL 的校验定位是 W3C 的公开规范体系（主文件 §2.1 已把 RDF / RDFS / OWL 列为 KG 的语义基础）；OWL 2 引入 EL / QL / RL 三个 profile 的公开动机是控制推理复杂度【公开】（W3C 于 2009 年发布 OWL 2 为推荐标准；各 profile 的具体条款请以 W3C 官方规范页面当前版本为准）。逐条判断某个图库「能不能约束写入」只看一个问题：**它的约束是在写入路径上执行，还是靠离线校验事后发现**——前者才拦得住，后者只能告诉你已经脏了。

**失效条件**：当只有一个写入方、关系类型不超过几十个（这一档属于【经验】）、且团队稳定时，schema 缺位的代价还没累积到需要治理的量级；只要出现多团队写入或人员流动，谓词发散必然发生，届时只能做一次全量归一。

#### 7.3.3 推理发生在哪一层：路径 / 公理 / 向量

**机制是什么**：三种显式推理载体——查询期的路径匹配（Cypher 的可变长路径、SPARQL 属性路径、规则挖掘出的规则集）、加载期的公理推导（reasoner 把蕴含物化）、训练期的向量压缩（KG Embedding 与 GNN 把关系结构压进连续空间）。下表按这三种逐项对照；末行「大模型直接回答」不属于三种显式推理，它只作对照——生成期的自然语言输出不可枚举，也不产生可复算的推理步骤。

**它在各候选中的实现差异**：

| 推理的承载方式（末行仅作对照） | 发生在何时 | 输出形态 | 能否逐跳举证 | 能否泛化到未连通的实体对 |
| --- | --- | --- | --- | --- |
| 路径 / 规则匹配 | 查询时（规则挖掘在离线） | 一条路径、一条规则 | **能** | 弱：没有连通就没有结论 |
| 公理 + reasoner | 加载 / 重算时 | 新增断言 | 能（推导链） | 中：只在公理作用域内 |
| 图嵌入 / GNN | 训练时 | 分数 / 向量 | 弱：给得出 0.87，给不出路径 | **强**：可预测未观察到的边 |
| 大模型直接回答 | 生成时 | 自然语言 | 不可靠 | 强（但不可枚举、不可审计） |

**由此必然导出的性质**：因为嵌入把关系压成连续空间中的代数约束，所以它能对图上没有连通的实体对给出打分——这是链接预测与推荐冷启动的能力来源（主文件 §1.2 把「推荐 / 风控的『冷启动』」列为需要基于实体关系推理的痛点）。代价是**结论不可逐跳解释**：你能拿到一个分数，拿不到「为什么」；分数随时间与训练数据漂移，本身也需要版本管理。反过来，路径与规则给出的每一步都可举证、可写进审计报告，但推不出图上不存在的连接。**这不是强弱之分，是两种结论文档**——金融风控要后者（可举证），推荐要前者（可泛化）。把它们混在一个打分表的「推理能力」一栏里，正是 7.1 所说的那类误导。

工程上还有一处容易忽略的差别：**上述三种显式推理的可复现性不同**。路径匹配与公理推导是确定性的——同一份图、同一句查询，结果可复算；嵌入与 GNN 的结果依赖模型版本、训练数据与随机种子，**同一份图在两次训练后可能给出不同分数**。因此凡是要求「结论可复算」的地方（审计、合规、对账），嵌入类方法只能用在校验之前的候选生成环节，不能作为最终判定的依据。

**公开证据**：TransE 把关系建模为平移（h + r ≈ t，Bordes 等，2013），RotatE 把关系建模为复数空间的相位旋转、可建模对称 / 反对称 / 组合关系（2019）；GNN 一侧 GCN（2017）、GraphSAGE（2017，归纳式，支持新节点）、R-GCN（面向多关系图）；规则挖掘一路的代表工作是 AMIE 3——这一组方法在主文件里逐条列名：嵌入与 GNN 见 §2.1 与 §2.2，规则学习见 §2.3【公开】。各条的会议与年份如有出入，请以论文官方页面当前版本为准。工程上可自行核验的判据是问一句：**这套推理能不能回答「这条结论依据哪三条边」**——答不上来的，就不要把它放进需要举证的链路。

**失效条件**：路径推理在稀疏图上几乎无路可走（连通度不足时退化为查不到）；嵌入与 GNN 在图上没有出现过的实体（冷启动节点）上，转导式方法完全失效，只有归纳式方法才能处理——这也是选型时要问「新节点多久出现一次」的原因。

#### 7.3.4 语义检索与关系检索的分界：像不像 vs 是不是

**机制是什么**：向量检索以近似最近邻为原语，用索引把「全量比对」压成「访问一小部分候选」；关系检索以谓词为原语，给定谓词与参数，结果集是确定的。

**它在各候选中的实现差异**：

| | 向量检索（向量库 / 嵌入） | 关系检索（图 / 关系库） |
| --- | --- | --- |
| 原语 | 距离 / 相似度 | 谓词 / 路径 |
| 结果形态 | Top-K + 分数 | 精确集合 |
| 召回保证 | 不保证找到最近邻，只保证高概率 | 完整 |
| 能否回答「A 的经理的经理是谁」 | 不能（关系未写成谓词就无法保证） | 能 |
| 能否回答「和这张图最像的另外 5 张」 | 能 | 不能（要先定义相似度函数） |

**由此必然导出的性质**：因为 ANN 用「访问候选子集」换延迟，所以**召回率是被索引参数显式交易的量**——它不承诺完整。这条性质直接给出一个工程结论：**「用向量库做关系推理」在机制上不成立**，相似度高不等于关系成立；反过来，图也回答不了「最像的 K 个」这类没有谓词可写的意图。因此二者组合的正确形态是**向量召回入口 + 图精确校验**：先用语义相似度找候选实体，再用图上的谓词把候选裁到真正成立的那一部分。主文件 §2.4 把这种 Hybrid 架构写成 2024 年的主流；本章 §5 进一步把它的机制写清——GraphRAG 把「在文档集合上打分」换成「在图上游走并按约束剪枝」，Hybrid RAG 被拆成「向量召回 / 图谱遍历 / 本体约束」三件套，KG 在其中承担事实层（答案的依据从「模型隐式记忆」换成「一条可检索的路径」）。

**公开证据**：这条组合形态有一个可回查的公开节点——微软的 GraphRAG 于 2024 年开源，本章 §5 与主文件 §1.4 都把它记为把 KG + RAG 推向工业级的一步【公开】（来源：主文件 §2.4、主文件 §1.4 与本章 §5 的相关条目）；该开源实现的索引构建流程与成本提示可按其仓库文档自行核验，具体接口与版本请以官方文档当前版本为准。

这条分界也解释了「AI 友好度」这一行的真正含义：AI 应用对载体的要求不是「更先进」，而是**能否把上下文组装成模型可用的形态**——图能给出可枚举的邻域与路径（上下文可控、可裁剪），向量能给出语义近邻（召回面宽但边界模糊）。所谓 AI 友好度高，指的是**这两种能力都有入口**，而不是某个引擎的跑分更高。

**失效条件**：查询本身带精确谓词时（「状态为已支付」），向量侧的近似性纯属开销；查询本身是模糊意图时（「找相似案例」），关系侧无法启动。两侧都可能出现的混合查询，才是唯一需要同时维护两套索引的场景——代价是同一份数据要分别更新两套索引，向量索引过期会表现为「召回不到」这种静默失败。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 图存储与内存驻留（节点数 + 边数 × 每条边量级）
      + 遍历与算法（触及边界宽度 × 跳数或算法迭代轮数）
      + 抽取与对齐（来源两两组合 × 概念数²）
      + schema 缺位的治理（谓词归一 + 孤岛清理 + 重跑查询）
      + 变更成本（schema 改一次要重跑抽取与回填）
```

各候选的**主导项**与**隐性成本**：

| 候选 | 主导项 | 隐性成本 | 增长方式 |
| --- | --- | --- | --- |
| 关系数据库 | 连接与中间结果 I/O | 多跳查询的调优人力（改写、物化、缓存） | 随跳数与表数增长 |
| 维度建模 / 数仓 | 存储与扫描量 | 一致性维度的协商成本 | 随业务过程数增长 |
| 属性图 | 邻接的存储与内存驻留 | schema 缺位导致的谓词发散与孤岛 | 随节点与边数线性增长 |
| RDF 三元组库 | 三元组数量 × 索引排列数 | 推理物化带来的膨胀与重算 | 随三元组数增长 |
| 向量库 | 维度 × 条目数 × 索引类型的内存 | 索引重建与召回率调参 | 随条目数与维度线性增长 |
| 本体建模 | 建模人力（前期）→ 推理与物化（后期） | 变更时的重验面 | **主导项会换位** |
| 图嵌入 / GNN | 训练（加速器时长）与推理延迟 | 特征与模型版本管理；不可解释带来的信任成本 | 随训练频率与图规模增长 |
| 大模型事实层 | 每次查询的 token 成本 | 幻觉兜底与人工复核 | 随查询量增长（不随数据量） |

**三条量级推导**：

1. **遍历代价由度数决定**（【推算】）。设平均出度 d，从 1 个实体出发、深度 k 的候选路径数 ≈ d^k。d = 20、k = 3 时约 8,000 条；d = 50、k = 3 时约 125,000 条（推导链：每扩展一跳，边界数乘以平均出度，20³ = 8,000、50³ = 125,000）。因此**同一句「三跳查询」在两个图上的代价可以差一到两个量级**——幂律图里「平均出度」还会被少数超级节点主导，均值本身失去代表性。可自行核验的判据：把起点从普通实体换成最大的店铺 / 最热的商品，看耗时是否跳变；跳变幅度就是你的图偏离均匀假设的程度。

2. **存储量级与内存上限**（【推算】）。以边为口径，一条有向边需要承载两端引用、关系类型与属性；假设两端各自维护邻接（各一次引用）、类型用整数 ID、属性独立存储，单条有向边的邻接结构落在数十字节量级（这一档属于【经验】）。按 10⁹ 条边推算：10⁹ × 32 字节 ≈ 32 GB，即邻接结构本身就是数十 GB 量级（推导链：边数 × 每条边字节数，32 字节是上述假设下的取整值）。这解释了图库的常见形态——**邻接常驻内存、属性放外存**，也说明为什么**内存容量而不是磁盘容量，通常是图规模的第一个硬上限**。可自行核验的判据：看目标图库官方文档中「推荐内存 / 边数」一类的容量建议是否与该量级同阶。

3. **跨来源判同的工作量按组合数增长**（【推算】）。设来源数为 n、每个来源的概念数为 m，跨来源两两判同的候选对比对数量级 ≈ C(n,2) × m²（推导链：每两个来源之间有 m × m 个候选对，共 C(n,2) 对来源）。n = 2、m = 100 时约 10⁴；n = 5、m = 100 时约 10⁵。也就是说**参与者从 2 个增到 5 个，判同量涨 10 倍而不是 2.5 倍**——这解释了为什么「先把多源合并成一张大图」在来源变多后一定会卡住，也印证了本章 §3.2.3 联邦型写下的失效点：参与方增多时「解耦」会反转成「对齐成本主导」，因为对齐工作量随参与方对数的组合增长。

**一条经验判据**（【经验】）：在实体规模不大、且查询是「点出发的有界跳数遍历」时，单机或主从形态的图库通常够用；规模上去之后才进入分布式图，而分布式把邻接切开，跨分片跳数成为新的成本项——因此**「该不该上分布式图」的判据不是节点总数，而是跨分片遍历的占比**。判断自己是否真的需要 KG，也可以数一个量：**有多少业务问题必须经过两次以上「实体 → 关系 → 实体」的跳转才能回答**；数得越少，说明你需要的可能只是一个更好的宽表或一套向量检索。

成本函数里最容易被忽略的一项是**变更成本**：它不是随图规模线性增长，而是随「被引用的边类型数 × 改写面」增长——改一次 schema，要重跑抽取、回填断言、重写所有用到旧谓词的查询。控制这项成本的手段不是少建模，而是**把变更的作用域限制住**（命名空间、按域拆图、谓词版本化），代价是边界需要设计并有人持续维护。另外提醒一条读法：表中「增长方式」一列比「主导项」一列更值得看——主导项决定今天的账单，增长方式决定三年后的账单。

成本函数里的「抽取与对齐」也常被当成一次性投入，实际不是：只要上游数据形态或业务概念在变，抽取器就要跟着改，而每次改动都要重新评估覆盖率与准确率。**抽取成本随「源形态种类」增长，而不是随数据量增长**——这解释了一个常见现象：数据量翻十倍不一定让抽取变难，接入一种新形态的数据源（扫描件、聊天记录、外部导入）则一定会。

### 7.5 决策树（每个分支都要有阈值依据）

```
[我要回答的问题是什么？]
 ① 答案集是「全量的子集」、且以聚合与统计为主？
    └── 是 → 维度建模 / 列存数仓（图遍历在这里不产生优势）
 ② 答案是「某个确定实体的一条或一组记录」，跳数 ≤ 1？
    └── 是 → 关系数据库（换图库换不来任何东西）
 ③ 问题形态是「多跳、可达、路径」，起点是少数实体？
    └── 是 → 知识图谱（属性图存储）★
 ④ 问题形态是「最像的 K 个」，且写不出谓词？
    └── 是 → 向量数据库（结果带分数，不带证明）
 ⑤ 是否存在「推不出但必须成立」的关系（分类、等价、传递）？
    └── 是 → 本体建模叠在图或表上（schema 层）
 ⑥ 同一实体在多个系统里标识不同？
    └── 是 → 先做标识解析（实体链接 / OneID 体系），再谈建图
 ⑦ 结论要不要给监管、风控或算法审计举证？
    ├── 要 → 走路径 / 规则推理，不用向量打分
    └── 不要 → 向量与嵌入可选（泛化优先）
 ⑧ 图是否是幂律分布（少数节点度数极高）？
    ├── 是 → 先定超级节点的处理方案（剪边、分片、类型索引），再选引擎
    └── 否 → 按常规规模选引擎
 ⑨ 用途是 AI 取数 / 问答？
    ├── 只要事实投影 → 知识图谱 + 向量
    └── 还要语义约束与校验 → 本体 + 知识图谱 + 向量
 ⑩ 以上多种需求同时成立？
    └── 是 → 数仓 + 本体 + 知识图谱 + 向量「四件套」
```

这棵树由两组彼此独立的判断组成：**①–⑥ 选载体**（按问题形态与标识状况），**⑦–⑩ 选配置**（按举证要求、数据形状与消费方式）。两组不能互相替代——一个只需报表的系统，若还要对外交换数据，同样要走 ⑤ 的语义层决策。

**阈值依据**：

- **①「聚合与统计为主」**：判据是答案集的形态而不是数据量——聚合的结果是「一个数」，它不需要知道任何一个实体的邻域；列存按列读直接作用于收益，图的邻接结构在这条路径上无从发挥。
- **②「跳数 ≤ 1」**：一跳在关系库上只是一次索引查找，无索引邻接带来的常数级优势换不回一套新存储的运维成本；判据是「外键（或等价索引）能否直接命中」。
- **③「多跳、起点少数」**：**跳数阈值不是绝对数，而是两条代价曲线的交点**——主文件 §1.1 把三到五跳列为 SQL 的实际困难区，那一档属于【经验】；可自行核验的判据是压测：把跳数从 1 依次加到 4，记录 SQL 与图库耗时的比值，比值随跳数上升则说明你落在遍历优势区，反之说明你的查询本质上是「宽表能解决的事」。
- **④「写不出谓词」**：判据是「能否用一句可判定的条件描述你要找什么」。写得出条件就用关系 / 图；写不出（找相似、找风格接近）才轮到向量，这条分界在 7.3.4 已给出机制解释。
- **⑤「推不出但必须成立」**：沿用 05 本体建模对比章给的自验方法——抽查若干条「应该自动成立」的结论，逐条问它能否从图上的边直接读出；只有当确实存在读不出的结论时，公理层才在做它唯一不可替代的那件事。
- **⑥「标识不同」**：判据是「各系统各自发号」这一事实，而不是数量。标识不统一时，任何多跳结论都可能因为「中间那一段不在图上」而缺失——**缺失不是「少一点」，而是断链**，且下游常把它误读成业务发现。
- **⑦「要举证」**：判据是审计方要什么形态的证据——路径与规则可以逐跳复算，向量分数不能；这与模型精度无关，是结论文档形态的选择（7.3.3）。
- **⑧「幂律分布」**：判据是度数分布的尾部——用「最大度数与中位度数之比」这个比值自查，比值拉开若干数量级时，7.4 的度数推导即适用；此时选型重点从「引擎功能」转向「超级节点方案」（类型索引、按类型分片、对高热度节点单独建表）。
- **⑨「AI 取数」**：判据是消费方要「事实」还是要「约束」。本章 §5 把这类形态写成「向量召回 / 图谱遍历 / 本体约束」三件套，并把图定位为可举证的事实层（依据是一条可检索的路径）；若还要模型判断「什么不能做」，就必须再叠一层本体的边界约束（05 本体建模对比章的选型矩阵把「智能体的世界模型」一行的首选定为本体建模，理由正是「只有工具清单没有语义约束时，Agent 无法判断『什么不能做』」）。
- **⑩「四件套」**：依据是约束组合——「报表 + 语义对齐 + 关系网络 + 语义检索」四种需求没有单一载体能同时满足，只能分层组合（本章 §3.4 的组合模式给出了各层职责边界）。

树里没有「预算」节点：预算决定你能投多少人维护图与抽取管线，不决定哪种载体成立。把预算写进选型树，最常见的后果是**为省钱选了机制上不够用的载体，两年后再拆一次**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 推荐 / 风控 / 反欺诈 / 社交 | 知识图谱 + 图推理 | 属性图存储 + 规则引擎 | 无 schema 的图会退化为「一堆节点」，治理成本随时间上升 |
| 精确事实查询（单实体、一跳） | 关系数据库 | 图库的点查接口 | 图库在一跳上没有优势，却带来一套新存储 |
| BI / 大数据量聚合 | 维度建模（数仓） | 图 + 列式导出 | 聚合不落在邻域上，图的邻接结构无用武之地 |
| 语义检索 / 相似召回 | 向量数据库 | 图 + 嵌入索引 | 向量结果不可举证，行不通于需要定论的场景 |
| 跨域语义对齐 / 数据治理 | 本体建模 | 受控词表 + 图的轻约束 | 只做图不做 schema，谓词发散不可避免（7.3.2） |
| AI 事实层 / GraphRAG | 知识图谱 + 向量 | 本体 + 图 + 向量 | 只有向量时结论不可验证；只有图时召回入口过硬 |
| 智能体世界模型 / 推理引擎 | 本体 + 知识图谱 + 向量 | 结构化工具定义 + 图 | 只有工具清单没有语义边界，Agent 无法判断「不能做什么」 |
| 企业级数据基础设施 | 数仓 + 本体 + 知识图谱 + 向量 | 分阶段只上其中两件 | 单独任一载体覆盖不了「聚合 + 语义 + 关系 + 检索」四种需求 |

矩阵的读法是：**先按「问题的形态」选载体，再按「约束」加配置**。每行「不选它的原因」都不是能力不足，而是**机制不落在收益点上**——判断矩阵用对了没有，只需回答一个问题：我的痛点是否出现在我准备引入的机制所作用的位置上。

矩阵里有一处需要防的误读：「首选」列按问题形态给出，不代表同场景只能用这一件。把「推荐 / 风控」的首选与「AI 事实层」的首选叠起来看，会发现真实系统里这两条需求常同时成立——此时组合的边界（谁是真源）比选择本身更决定成败。

**五个常见组合**（各说明职责边界与运维代价）：

1. **数仓 + 知识图谱（事实层 + 关联层）**：数仓提供 DWD / DWS / ADS 的事实与指标，KG 从 DWD 抽取实体与关系、承载多跳关联。运维代价：抽取管线成为新负债——数仓口径一改，图上实例要跟着重跑；必须写明「数仓是真源、图是派生」，否则同一条关系会在两处独立维护并逐渐分叉。
2. **本体 + 知识图谱（schema + instances）**：本体定义 Class / Property / Axiom，KG 填充实例。运维代价：两道治理线——schema 变更要评估对存量实例的影响，实例侧的脏数据要靠形状约束或图侧校验拦住；只有一层治理时，脏数据会安静地流到下游。
3. **知识图谱 + 向量（关联查询 + 语义检索）**：图做精确关联与路径推理，向量做语义近邻召回，合成 Hybrid RAG / GraphRAG。运维代价：同一份实体要维护两套索引，且更新必须同源——向量索引落后会表现为「召回不到」这种静默失败，比报错更难发现。
4. **知识图谱 + 大模型（事实层 + 自然语言组织）**：图提供可枚举、可举证的事实，模型负责理解问句与组织输出。运维代价：需要维护一层「面向模型的投影」（把图结构化成模型容易消费的形态），并保证投影与图同步；否则模型会按旧定义回答，而这类错误不会报错。
5. **数仓 + 本体 + 知识图谱 + 向量（四件套）**：分别承担物理存储与指标体系、语义骨架、关联网络、语义检索。运维代价：四套东西各有重算周期与 Owner，必须明确「谁是真源、谁负责追平、谁能发布」——这四个归属不清时，组合会在半年后以「两份数据不一致」的形式暴露【经验】。

五个组合的共同点是**入口与内核分离**：入口追求低门槛（谁都能查、谁都能接入），内核追求强约束（不合规进不来）。反过来设计——入口强约束、内核无约束——是本主题最常见的形态错误。

### 7.7 选错的代价与迁移成本

**反模式：用向量库做关系推理** —— 症状是把「A 的上级的上级是谁」当成相似度问题，用嵌入近似出一个「最可能的上级」 → 后果是结论不可举证、召回不保证，风控与合规场景无法上线；机制上这是用「相似」替换「成立」，7.3.4 已说明两者是不同的判定原语（ANN 用访问候选子集换延迟，本就不承诺完整） → 正确做法：能写成谓词的一律走图或关系库，向量只用在没有谓词可写的那一步（入口召回）。

**反模式：无 schema 先上图，治理留到以后** —— 症状是半年内谓词名从几十个涨到几百个【经验】，同一含义多个名字，没人说得清哪个是正名 → 后果是跨域关联查询要先做一次谓词归一，而图越大这项工程的代价越高；机制上是 7.3.2 的复利：治理成本随图规模与被固化的查询数增长 → 正确做法：写入端先立最小约束（标签 / 关系类型清单 / 命名空间），哪怕不带任何公理。

**反模式：把图库当分析引擎** —— 症状是在 OLTP 图上跑 PageRank、社区发现、全量特征回填 → 后果是图库被拖垮，且这些算法的存储与执行形态与列存差一个量级【经验】；本章 §3.1 已把这条写成「图数据库选型错误」反模式的机制根源（同一套引擎跑两种负载） → 正确做法：遍历在图上，全图算法在列存或图计算框架上跑，两边用导出对齐。

**反模式：跳过标识解析直接建图** —— 症状是同一客户在两个系统里成了两个互不相连的节点，图上「查不到」被当成「不存在」 → 后果是多跳结论系统性缺失，而下游会把差异当成业务发现；机制上见 7.5 的⑥：断链不是「少一点」 → 正确做法：先做实体链接 / 标识合并（OneID 是 KG 的一个特例，见主文件 §2.4），再建关系。

四个反模式的共同点是**它们都在机制层面改变了「代价随什么增长」**：向量替代谓词改变了判定的可靠性，弱 schema 改变了治理成本的复利方式，图库当分析引擎改变了遍历代价的假设，跳过判同改变了结论的完整性。评估一次选型风险时，看的不是功能清单里缺哪一项，而是**你的用法有没有让 7.4 表里「增长方式」那一列换项**。

**换成另一个载体要动什么**：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 关系库 → 属性图 | 按点边重抽（高） | JOIN 与递归 CTE 改写为图查询（高） | 新增图库运维与容量规划（高） | 图建模与图查询（中高） |
| 单机图 → 分布式图 | 需重新切分并接受跨分片跳（高） | 部分多跳查询要拆成分段查询（中高） | 集群、分片策略与热点治理（高） | 分布式图的分区与热点处理（中高） |
| 无 schema 图 → 本体 + KG | 边与节点可保留，需补类型断言（中） | 增加 schema 校验与推理（中） | 新增本体治理与校验门禁（中） | 本体建模与形状约束（中高） |
| 全量抽取 → 增量 / 事件驱动 | 需补事件通道与幂等加载（中） | 语义从「某日快照」变为「当前状态」（中） | 新增流式链路的运维与背压处理（中高） | 流处理与幂等设计（中） |
| 无向量 → 加向量入口 | 需生成并持续维护嵌入（中） | 查询改为「召回 + 校验」两段（中） | 新增索引更新与重建周期（中） | 检索效果评估（中） |

这张表最容易被低估的是「查询改写」与「团队再学习」两列：**载体一换，之前所有基于旧载体调优出来的查询都要重写并重测**。迁移计划里必须给这两项留预算——它们通常比数据搬运本身更长，且加人不易缩短。表里还有一条规律：**从「无 schema」迁到「有 schema」的代价明显高于反向迁移**——前者要给存量数据补类型断言并重验结论，后者只是放弃一部分约束。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 查询是聚合与统计 | 维度建模 / 列存数仓 | 聚合不落在邻域上，邻接结构用不上 |
| 查询是单实体一跳 | 关系数据库 | 索引查找已是这一问的最优解 |
| 查询是多跳、可达、路径 | 知识图谱（属性图）★ | 邻接指针让代价随边界宽度而非全表规模增长 |
| 要「最像的 K 个」 | 向量数据库 | 谓词写不出来时，相似度是唯一可用的原语 |
| 有「推不出但必须成立」的关系 | 本体建模（叠在图上） | 只有公理层能推出未写下的事实 |
| 同一实体在多系统标识冲突 | 先做标识解析（OneID） | 判同是建图的前置工序，断链无法靠图算法弥补 |
| 结论要给监管 / 风控举证 | 走路径与规则推理 | 逐跳可复算才叫证据，分数不是 |
| 图是幂律、有超级节点 | 先定超级节点方案，再选引擎 | 度数决定扩展代价，均值失去代表性 |
| 抽取覆盖率上不去 | 先修抽取与对齐，再谈引擎 | 图的收益来自覆盖率，覆盖率由抽取决定 |
| 长尾实体查不到，但业务在扩张 | 允许先写后治（弱 schema） | 换取覆盖率，代价是谓词发散会随时间复利 |
| AI 取数要事实投影 | 知识图谱 + 向量 | 图保证成立，向量保证召回 |
| AI 要语义约束与边界 | 本体 + 知识图谱 + 向量 | 只有图没有公理时，模型无法判断「什么不能做」 |
| 多种需求同时成立 | 数仓 + 本体 + 知识图谱 + 向量 | 单载体无法同时满足四种需求 |

> 本节小结：这些方法之间真正起决定作用的差别只有一条——**你的查询是从「少数实体的邻域」出发，还是从「一个集合的全体」出发**。前者必然划算在邻接指针上（多跳代价随边界而非全量增长），后者必然划算在列式集合运算上；而「关系能不能被推出」「结论要不要能举证」这两问，决定的是你要不要在本章之上再叠 schema 层与向量层。**其余维度（工具成熟度、社区规模、学习曲线）都是这条选择的下游后果，而不是与它并列的比较项。**
