## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

**知识图谱的模式差异，本质是「schema 从哪来、有多硬、谁维护」。** 本体驱动型是 schema 先验定义且不可被数据改写；开放抽取型是 schema 事后从数据里归纳；层次型是在 schema 之上再叠一层治理；联邦型是多个由不同主体维护的 schema 之间做显式对齐；事件型是 schema 围绕时间线组织；多模态是 schema 必须容纳非文本的表示。引擎选型（Neo4j / NebulaGraph / TigerGraph）只是这条线的下游结果。

**其中最容易被讲错的一点：schema 的软硬不是风格偏好，而是能力的开关。** 推理与一致性校验都建立在 schema 之上——没有类与属性的约束，系统能做的是「检索」而不是「推理」。这解释了为什么「无 schema」被列为反模式：它换来的灵活性，代价是永久失去可验证性。

**约束还有一个不那么显性但决定成败的维度：查询负载的形状。** 图数据库原生的多跳遍历（O(V+E) 复杂度）在点查与局部遍历上远优于 SQL 的多次 JOIN；但同一套引擎去做全图扫描式的分析（PageRank、社区发现、全量特征回填）时，性能特征完全不同——这是「图数据库选型错误」反模式的机制根源，而不是配置问题。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| schema 从哪来（先验定义 / 事后归纳） | 本体驱动型还是开放抽取型 | 「先定本体更严谨」——文档密集场景里先行本体常导致抽取覆盖率极低 |
| schema 有多硬（强约束 / 轻量 / 无） | 能否推理与校验 | 「schema-less 更灵活」——没有 schema 就没有推理，只剩检索 |
| 规模量级与查询负载（点查 / 多跳 / 全图） | 存储与引擎选型 | 「图数据库都一样」——OLTP 图库跑全图分析会直接崩 |
| 数据模态（文本 / 图像 / 音视频 / 结构化） | 是否需要多模态表示层 | 「先把文本做好」——被排除的模态往往正是业务主体 |
| 参与方数量与自治程度 | 集中式 / 分层 / 联邦 | 「统一成一张图最干净」——跨组织时统一图的权限与节奏无法成立 |
| 时效与历史要求（当前状态 / 可回溯） | 实体快照还是事件为中心 | 「只存当前状态更省」——一旦要求「当时看到的是什么」就无法回答 |
| 变更频率与领域稳定性 | 本体维护成本是否可承受 | 「本体一次建好」——领域变化快时，过严的本体会被实例层逃逸绕过 |

**还有一点常被忽略：模式迁移不是免费的。** schema 一旦以某种方式落地，图里的数据就带着那个形状——从开放抽取迁到本体驱动要对全部存量实例重新对齐，从集中式迁到联邦要重建映射并接受部分推理能力不可用，从快照型迁到事件型要补历史事件。所以 3.6 的换挡信号要在疼之前看，而不是等到不得不动时才动。

### 3.2 模式逐个拆解（核心节）

> 6 个模式按「schema 从哪来、有多硬」排列，最后一个（多模态）改的是表示层而非 schema 来源。

#### 3.2.1 本体驱动型（Ontology-driven）

**被什么约束逼出来**：领域有明确的语义约定与审计要求（医疗、金融、政务），结论必须能被复现和解释——这要求约束先于数据存在，且不能被数据自行改写。

**结构**：TBox（约束层）与 ABox（实例层）分离，约束只写一次，实例只声明事实。

```text
TBox（schema 层，可推理的约束所在）
  Customer  ──holdsAccount──►  Account
  约束：holdsAccount 的定义域是 Customer、值域是 Account
ABox（实例层，只声明事实）
  (Customer:张) ──holdsAccount──► (Account:A001)
  → Account:A001 属于 Account 类型，由约束推导得出，不在实例里重复声明
```

```cypher
// 查询依赖的也是约束，而不是数据里的冗余字段
MATCH (c:Customer)-[:holdsAccount]->(a:Account)-[:issuedBy]->(bank:Bank)
WHERE bank.region = 'CN'
RETURN c, a, bank LIMIT 50;
```

**为什么这样设计有效**：因为约束只存在于 TBox 一处、实例只声明事实，所以「同一约束被两处定义且互相矛盾」在结构上无法发生；推理结论由约束推导而非人工录入，因此可复现、可审计——这正是强合规领域愿意付本体建设成本的原因。

**代价**：修改 TBox 的影响面是全量的（改一个属性的定义域会改变大量既有实例的类型归属），因此本体评审以周为单位；领域专家是稀缺资源，本体的维护能力天花板通常等于能长期投入的专家数量，而不是工程团队的规模。

**失效点**：当领域边界快速变化、本体评审跟不上时，「可推理、可验证」反转成「无法扩展」，因为新出现的实体类型在现有本体下无处安放，团队只能塞进 `Other` 类或把属性直接挂到实例上（逃逸），本体随即失去约束力。判断方法（可自行核验）：统计实例层出现了多少未在 TBox 中声明的属性，以及 `Other` 类下的实例占比。

**真实使用**：医疗、金融、政务类知识图谱多采用这条路线，技术基础是 W3C 的 RDF 1.1 与 OWL 2 推荐标准【公开】（W3C，RDF 1.1 于 2014 年、OWL 2 于 2009 年成为推荐标准）。具体企业项目对外披露有限，本文不做逐家断言【经验】。

#### 3.2.2 开放抽取型（Open Information Extraction）

**被什么约束逼出来**：语料以自然语言为主且规模巨大，先定义 schema 会让绝大多数内容「不符合格式」而无法入库；业务诉求是「先能查到」。

**结构**：不预设谓词表，先抽三元组，再从事后数据里归纳出轻量 schema。

```text
文档 ──► 抽取 (实体, 关系短语, 实体) ──► 三元组（谓词是自由文本，无固定词表）
                                            │
                                            ├─► 实体链接：把 mention 归一到已有实体
                                            └─► 关系聚类：把同义谓词归并 → 事后归纳的轻量 schema
```

```text
抽取结果的形态（谓词不是受控词表，而是句子里的原话）
  (Apple)  "was founded by"     (Steve Jobs)
  (Apple)  "founded by"         (Steve Wozniak)
  → 两条关系需要被聚类为同一谓词 foundedBy，否则查询必须枚举所有写法
```

**为什么这样设计有效**：因为抽取不依赖预定义谓词表，任何文档都能立即入库，覆盖率随语料增长近似线性提高；schema 从事后数据里归纳，避免了「为覆盖长尾而无限扩张本体」的评审成本。

**代价**：谓词是自由文本，同一关系有多种表达，查询质量完全依赖实体链接与谓词聚类的准确率；错误入库时没有任何约束能拦住它，只能靠事后抽检发现，因此「图谱里有这条关系」不等于「事实成立」。

**失效点**：当查询需要完整答案时（例如「列出全部供应商」），「覆盖广」反转成「不可信」，因为开放抽取不保证闭合性——缺失的、抽错的、以及「确实不存在」三种情况在结果上无法区分，而使用者会默认「查到的就是全部」。

**真实使用**：Microsoft GraphRAG（2024）是这条路线在工业界的代表形态：从文档语料抽取实体关系图并用于检索增强【公开】（Microsoft Research，2024）。它也被广泛用作辅助人工构建图谱的初筛手段【经验】。

#### 3.2.3 联邦型（Federated KG）

**被什么约束逼出来**：多个图谱由不同组织维护、各有独立演进节奏，物理集中不可行（跨组织权限不允许，或法律上不允许集中）。

**结构**：各图谱保持自治，连接点是一张显式的映射表。

```text
   KG-A（自有本体 A）          KG-B（自有本体 B）
        │                            │
        └──► 本体对齐（类 / 属性 / 关系映射）◄──┘
                    │
         联邦查询层：查询拆解 → 各图谱执行 → 结果合并
                    │
         冲突消解：同一实体的两个属性值不一致时，按显式规则取舍（并记录冲突）
```

```text
映射表示例（连接点是数据，不是代码）
  KG-A:CustID      ── 等价 ──►  KG-B:PartyNo
  KG-A:residesIn   ── 等价 ──►  KG-B:livesAt
  KG-A:Person      ── 子类 ──►  KG-B:Individual
  → 每条映射可单独复核、可回滚；不做映射即视为不可互联
```

**为什么这样设计有效**：因为对齐只发生在映射层、各图谱保持自治，任一方的新增与变更不要求另一方同步停机；连接点是显式的、逐条可审计的数据，而不是隐含在查询代码里的假设。

**代价**：映射表是持续维护成本，参与方为 N 时映射关系的规模按组合增长，且每一方的本体变更都会让相关映射失效；跨图谱的推理无法用任何单方的推理机完成，需要查询重写与结果合并，部分推理能力在联邦下直接不可用。

**失效点**：当参与联邦的图谱数量增长时，「解耦」反转成「对齐成本主导」，因为对齐工作量随参与方对数的组合增长，而每一方的变更都会连带作废一批映射。判断方法（可自行核验）：统计映射表中超过一个复核对周期未复核的条目占比。

**真实使用**：跨企业、跨行业的数据互联多采用这条路线，标准层面的支撑是 W3C SPARQL 1.1 的联邦查询规范【公开】（W3C，SPARQL 1.1 Federated Query 于 2013 年成为推荐标准）。企业侧的实施细节很少公开，本文不做逐家断言【经验】。

#### 3.2.4 层次型（Layered KG）

**被什么约束逼出来**：企业级图谱既要保留原始抽取证据（含冲突与出处），又要对外提供可治理、可授权的业务视图，两种需求对 schema 刚性的要求正好相反。

**结构**：原始层 / 核心层 / 视图层三层，层间职责固定。

```text
L0 原始层：来源三元组（保留出处、抽取置信度，允许冲突与重复）
   │ 归一（实体链接 + 冲突消解 + 证据留存）
L1 核心层：统一实体与关系（一个主体只有一个节点，是"事实层"）
   │ 业务化（按主题域裁剪、补业务属性、挂权限与密级）
L2 视图层：面向具体业务的子图（客户视图 / 商品视图 / 风控视图）
   → 原始证据与业务结论可以同时存在，且互不污染
```

```sql
-- L1 的每个结论都应能回指到 L0 的证据（否则合并判断无法被质疑与修正）
CREATE TABLE kg_entity_merge_evidence (
  canonical_id  STRING,        -- L1 的统一实体
  source_id     STRING,        -- L0 的来源实体
  source_system STRING,
  confidence    DOUBLE,
  merged_at     TIMESTAMP,
  rule_version  STRING         -- 合并规则版本：规则变了能重放
);
```

**为什么这样设计有效**：因为原始层保留出处与冲突、核心层只保留归一结果，当核心层的合并判断被质疑时可以回退到原始证据重算，而不是无从追溯；L2 按权限裁剪，同一份图可以服务不同密级的消费方，不必为每个业务复制一份图谱。

**代价**：一次抽取要落三层并维护层间依赖，任一层变更都要评估对上层的影响；层间一致性校验本身是额外工程，且 L1 的每条结论都要能追溯到 L0 的证据，否则「可回退」只是口号。

**失效点**：当上游修正频繁时，「可治理」反转成「同步成本」，因为同一事实在三层各有一份，一次修正要穿透三层重算；若缺少层间依赖追踪，L1 与 L2 会带着旧值长期存在——过期图谱比没有图谱更危险，因为它会给出错误的信心。

**真实使用**：大型企业级图谱的常见组织方式，与数仓分层（贴源 / 明细 / 汇总 / 应用）同构【经验】。各家的层数与命名差异很大，本文不点名断言某家公司采用了几层结构。

#### 3.2.5 事件型（Event-centric KG）

**被什么约束逼出来**：业务的核心问题是「发生了什么、按什么顺序、彼此如何触发」，而不是「现在有哪些实体」——实体属性会随时间过期，已经发生的事件不会。

**结构**：把事件建模为一等节点，实体作为事件的参与者。

```text
事件是节点，不是实体之间的边
  (Event:下单#E1) --participant{role:买家}--> (Customer:张)
                  --participant{role:商品}--> (Product:某机型)
                  --at-->                    (Time:2025-10-08T10:00)
                  --triggered-->             (Event:支付#E2)
                  --triggered-->             (Event:发货#E3)
  → 事件不可变、只追加；实体在任一时刻的状态由事件序列推导得到
```

```text
为什么不能把事件写成边：
  (Customer) --下单--> (Product)   ← 这条边没有时间，也没有"这一次"的身份
  两次下单会被折叠成一条边，或者变成两条无法区分的重复边
  → 一旦需要回答"当时看到的是什么"，边模型无法承载
```

**为什么这样设计有效**：因为事件不可变且只追加，任何时点的实体状态都能由事件重放得到，所以「当时系统看到的是什么」可复现——这是审计与纠纷场景的硬需求，也是「实体快照 + 覆盖更新」模型做不到的。

**代价**：事件节点数量随业务量增长，同一实体挂着大量事件，长链路遍历的成本高于快照模型；只建事件层时，实体的稳定属性（客户等级、商品类目）会被反复冗余，需要额外的实体层与之配合。

**失效点**：当查询以「当前状态的聚合」为主（日活、总量、排名）时，事件型的优势反转成负担，因为每次聚合都要重放事件序列，代价随历史长度线性增长；此时需要在事件图之外维护派生的状态视图（典型的读写分离），否则实时看板会被重放拖垮。

**真实使用**：事件溯源在交易、IoT、运营审计场景广泛使用【经验】；把事件作为图谱一等公民的做法与事件溯源同源，采用范围随场景差异很大，本文不做逐家断言。

#### 3.2.6 多模态 KG（Multimodal KG）

**被什么约束逼出来**：内容主体本身就是图片、视频、音频，实体与关系不只存在于文本里——只处理文本，等于把业务的主要内容排除在知识之外。

**结构**：不同模态共享同一实体空间，只在表示层分开。

```text
                     ┌── 文本 ──► 文本嵌入 ──┐
同一实体             ├── 图片 ──► 图像嵌入 ──┤  必须落在同一向量空间
(Product:某机型)     ├── 视频 ──► 多帧嵌入 ──┤  才能做跨模态比较
                     └── 属性 ──► 结构化字段 ┘  （价格 / 上市时间 / 类目）
   → 跨模态检索：把查询编码到同一空间做近邻检索，再回到图上做关系收敛
   → 向量必须记录"由哪个模型版本生成"，否则换模型后旧向量不再可比
```

```cypher
// 结构化关系与向量检索的组合：先用图缩小范围，再在同一范围内做近邻
MATCH (p:Product)-[:belongsTo]->(c:Category {name: '手机'})
WHERE p.embedding_image IS NOT NULL
RETURN p.id, p.name, vector.similarity(p.embedding_image, $queryVec) AS score
ORDER BY score DESC LIMIT 20;
```

**为什么这样设计有效**：因为不同模态共享同一个实体节点、只在表示层分开，同一商品的文本描述、图片与结构化属性会收敛到同一个节点，跨模态检索的结果仍能回到图上做关系推理，而不是停留在一堆互不相干的向量里。

**代价**：跨模态嵌入对齐是持续工程（新增模态或更换模型都会破坏既有对齐）；存储成本按模态与副本叠加；每种模态一套抽取管线，任一环节失败都会让该实体的多模态表示不完整，而「不完整」在检索时表现为悄悄少召回，不会报错。

**失效点**：当嵌入模型更换或升级时，「跨模态检索效果好」反转成「检索结果整体退化」，因为不同版本的模型产出的向量不在同一空间，而系统通常不记录每条向量由哪个模型生成——向量一旦入库就与生成它的模型脱钩，旧向量成为无法解释的残留。判断方法（可自行核验）：检查向量存储中是否记录了模型名、模型版本与生成时间；没有记录即无法做可控的模型升级。

**真实使用**：电商、内容平台、自动驾驶等多模态场景广泛采用【经验】；公开的图谱结构细节有限，本文不做逐家断言。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 语义约定明确、结论需审计（医疗 / 金融 / 政务） | 本体驱动型 | 不选开放抽取型：结论必须可复现、可解释，抽取结果无法承担这一职责 | 是否有人能长期投入维护本体（专家资源） |
| 语料以文档为主、需要先能查到 | 开放抽取型 | 不选本体驱动型：先行本体让大量内容因不合格式而进不来 | 查询是否需要「完整答案」（需要则要补约束） |
| 多个主体维护、各有演进节奏 | 联邦型 | 不选层次型：集中分层的前提是能集中，跨组织时不成立 | 对齐映射是否有专人定期复核 |
| 单主体、需要保留原始证据与业务视图并存 | 层次型 | 不选本体驱动型：强本体无法同时容纳冲突证据与业务裁剪 | 层间能否追溯（L1 结论能否回到 L0 证据） |
| 核心问题是过程与顺序（交易 / IoT / 审计） | 事件型 | 不选实体快照型：属性会被覆盖，历史状态无法复现 | 查询以「过程」为主还是以「当前聚合」为主 |
| 内容主体是图像 / 视频 / 音频 | 多模态 KG | 不选纯文本 KG：被排除的模态往往是业务主体 | 向量是否记录了生成它的模型版本 |

**本主题下最常被误选的一对，是「本体驱动型」与「开放抽取型」。** 两种误选都有具体后果：在文档密集的情报分析或客服问答场景强行先建本体，项目通常会停在建模阶段——专家评审以周为单位，而可供入库的数据一条也没有，团队最终为了交付而偷偷放宽本体，得到一个既没有约束力也没有覆盖率的中间产物；反过来，在医疗、金融这类需要审计的场景里图快去抽取，会把幻觉三元组与真实事实混在同一张图里，且没有任何约束能把它们分开，等到结论被质疑时，整张图的证据链都无法自证。判断该选哪边的约束是：**这个领域的结论是否需要被第三方复核**；需要，就必须有先验约束与证据留存；不需要，就先求覆盖、再逐步归纳 schema。

### 3.4 组合模式：真实系统不会只用一种

**组合一：开放抽取 + 层次型（宽进严出）。** 分工是开放抽取负责入口与 L0 原始层、层次型负责归一与对外视图：抽取阶段不设门槛以保覆盖率，治理阶段靠实体链接与冲突消解收敛质量。运维代价是两套管线（抽取与归一）都要单独监控，且归一规则的每次调整都要考虑已入库存量如何重算。适合规模：语料持续增长、且质量要求随消费方分级的内容型图谱。

**组合二：本体驱动 + 事件型。** 分工是本体承载稳定的实体与关系（客户、账户、产品），事件承载过程与顺序（交易、状态变更），两者通过事件参与者关联。运维代价是两套 schema 要一起演进——事件类型的新增往往牵动本体，反之亦然。适合规模：强合规的金融风控与审计，实体数量可控但事件量巨大的场景。

**组合三：联邦 + 多模态。** 分工是联邦解决「各参与方保留自己的本体与模态、只对齐映射」，多模态解决「每一方内部如何统一表示不同模态」。运维代价是叠加了两类持续成本（映射复核 + 嵌入对齐），且两套机制各自都有失效模式。适合规模：跨组织共享的媒体或商品网络，各方都不愿也无力把原始数据集中到一处。

三种组合有一个共同前提：**被组合的两种模式必须各自有明确的职责边界，且边界由平台机制保证而不是靠约定。** 边界一旦模糊（例如开放抽取的结果被直接当作本体驱动图谱的事实层），组合就会退化成两者缺点的叠加——抽取的噪声加上本体的刚性，而不是两者优点的叠加。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「一锅烩」 | 节点与关系类型持续膨胀，无人能说出图谱的边界 | 类型爆炸后查询无法优化，治理动作无处下手，图谱退化为不可维护的大杂烩 | 建图被当成「把数据都放进来」，而不是「回答一组问题」 | 按主题拆分（客户 KG / 商品 KG / 交易 KG），明确每个图的回答范围 |
| 「无 schema」 | 同一含义的关系有多种写法，属性名靠约定 | 无法推理、无法验证，只剩下不精确的检索能力 | schema 设计被当作可以后补的工作 | 必须有 schema，哪怕只是轻量的词表与关系类型表 |
| 「本体过严」 | 业务方频繁要求新增类型，实例层出现大量逃逸属性 | 本体被实例层绕过，约束名存实亡 | 用本体表达所有业务细节的冲动 | 本体只管核心语义，实例层与扩展属性留出空间 |
| 「抽取无验证」 | 抽取结果直接入生产，抽查发现事实性错误 | 幻觉与真实事实无法区分，整张图的可信度被连带拉低 | 追求入库速度，验证被放到「以后再说」 | 三重校验：约束校验（如 SHACL）+ 推理机检查 + 人工抽检 |
| 「忽视图谱质量」 | 图谱里存在重复实体、过期关系、冲突属性 | 同一问题有多个答案，使用者需要二次判断，图谱失去权威性 | 建图被视为一次性项目而非持续运营的资产 | 建立质量评估体系（正确性、覆盖率、一致性、完整性）并定期度量 |
| 「盲目追求大规模」 | 三元组规模持续堆高，核心查询变慢 | 规模超过查询负载所需后，收益不再增长而查询成本持续上升 | 把规模当成 KPI | 规模匹配查询负载，必要时按主题拆分图谱 |
| 「图数据库选型错误」 | 用 OLTP 图库跑全图分析，或用分析型引擎做高频点查 | 资源被错误负载占满，两类查询互相拖慢 | 选型只看「是不是图数据库」，不看负载形状 | 按负载选型：OLTP 点查与局部遍历、海量数据分布式、生态与集成需求分别对应不同引擎，并允许共存 |
| 「LLM 替代 KG」 | LLM 直接回答事实性问题，图谱被绕开 | 事实性结论无法溯源，模型更新或上下文变化后答案不可复现 | 图谱建设成本高，LLM 直接回答见效快 | 保留图谱作为事实层，LLM 负责语言与推理路径，事实由图谱兜底 |

**最危险的三条，在生产中的典型暴露方式：**

**「抽取无验证」** 的暴露方式最隐蔽。它不会以「图谱报错」的形式出现，而是以「有人相信了错的结论」的形式出现——因为抽取入库的三元组与人工确认的三元组在图里长得完全一样，没有确认状态、没有置信度、没有出处。等到某次决策依据被证伪时，团队才发现需要从零重建整张图，因为无法区分哪些三元组被确认过。修法的第一步不是加校验器，而是给每条三元组加上来源与状态（自动抽取 / 已确认 / 已驳回），让「可信子集」这个概念先能被查出来。

**「图数据库选型错误」**，暴露方式是「两类查询同时变慢」。团队通常先发现某个分析任务超时，扩容后又发现点查的 P99 变差——因为两类负载对资源的需求结构不同，扩容只会让互相挤占更明显。机制上，点查依赖局部性（缓存命中、索引命中），全图分析依赖吞吐（扫描全部节点与边），在同一套资源池里，后者会持续冲刷前者的缓存。可行的处理不是换掉某一边，而是把分析类负载移到独立的计算引擎或副本上。

**「一锅烩」**，暴露方式是「没人敢改 schema」。当节点与关系类型增长到无人能列全时，任何一次模型调整都要先做一次不确定的影响面排查，于是调整被无限推迟，图谱的内容与业务实际逐渐脱节。机制上，类型爆炸让「这张图回答什么问题」这个判断失去边界——没有边界就无法判断新增是否合理，也无法判断已有的是否该删。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单主题 → 多主题 | 一张大图 | 类型膨胀，schema 无人敢改，查询无边界 | 按主题拆分为多个图谱 + 显式跨图映射 | 跨主题查询从一次遍历变成跨图拼装，需要额外查询层 |
| 十万级 → 亿级三元组【经验】 | 单机图库 | 全图分析与长链遍历的资源争抢，扩容收益递减 | 分布式图存储 + 分析负载独立引擎 | 迁移期需重建索引与分区策略，查询重写 |
| 抽取探索 → 生产可用 | 开放抽取成果直接对外 | 幻觉与真实事实无法区分 | 加入约束校验与证据留存，区分可信子集 | 需补齐来源、置信度与确认状态，存量数据要回填 |
| 单组织 → 多组织 | 集中式图谱 | 权限与演进节奏无法统一 | 联邦：保留各自本体，只对齐映射 | 建立映射表与复核机制，接受部分推理能力不可用 |
| 纯文本 → 含图像 / 音视频 | 文本图谱 | 业务主体内容被排除在图之外 | 多模态：共享实体空间 + 分模态表示 | 跨模态对齐工程 + 向量与模型版本元数据 |
| 快照型 → 需可回溯 | 只存当前状态 | 「当时看到的是什么」无法回答 | 事件型（或快照 + 事件双写） | 事件层重建 + 派生状态视图，聚合查询需改写 |

> 表中的量级（如十万级 → 亿级三元组）是量级提示【经验】，不是任何一家公司的实测阈值。判断自己是否越过了阈值，看的是核心查询的 P99 是否随规模持续劣化——而不是三元组总数。

### 3.7 自检清单

- [ ] **这张图回答哪些问题？** 能一句话说清范围且不包含「所有数据」；说不清即已进入「一锅烩」。
- [ ] **schema 是否存在？（哪怕是轻量的）** 关系类型与属性名是否有受控清单；没有，则推理与校验都无从谈起。
- [ ] **本体是否正在被实例层绕过？** 统计实例层中未在 schema 声明的属性数量，以及兜底类型（如 `Other`）下的实例占比。
- [ ] **抽取结果是否有来源、置信度与确认状态？** 抽查 20 条三元组，能否回答「谁抽的、依据什么、是否被人工确认」。
- [ ] **是否存在可信子集？** 对外提供服务时，使用的是全部三元组还是已确认子集；混用即把幻觉与事实一并发出去。
- [ ] **是否有质量指标在定期度量？** 正确性、覆盖率、一致性、完整性中至少有两项有可复现的度量口径。
- [ ] **重复与冲突实体是否有消解记录？** 同一实体被合并时，是否留有证据与规则版本，能否重放与回退。
- [ ] **规模与查询负载是否匹配？** 核心查询的 P99 是否随三元组规模增长而持续劣化；是，则考虑按主题拆分。
- [ ] **引擎是否按负载形状选型？** 高频点查与全图分析是否在同一套资源上互相挤占；是，则需分离。
- [ ] **层次型图谱能否追溯到证据？** 核心层的每条结论是否可回指原始层；不能，则「可治理」不成立。
- [ ] **向量是否记录了生成它的模型与版本？** 没有记录，就无法做可控的模型升级。
- [ ] **LLM 回答事实性问题时是否经过图谱？** 若是直接回答，检查结论能否溯源与复现。
- [ ] **权限与密级是否落在图上而不是嘴上？** 视图层是否按消费方裁剪，且裁剪由平台执行；靠文档约定即等于没有隔离。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 结论需审计、有专家可长期维护本体 | 本体驱动型 | 约束先于数据且只定义一处，推理结论可复现可解释 |
| 语料以文档为主、先求覆盖 | 开放抽取型 | 不依赖预设谓词表，覆盖率随语料近似线性增长 |
| 多主体维护、无法集中 | 联邦型 | 只对齐映射、各方保持自治，变更无需同步停机 |
| 单主体、要同时保留证据与业务视图 | 层次型 | 原始层留证据、核心层留结论，合并判断可回退重算 |
| 核心问题是过程与顺序 | 事件型 | 事件不可变只追加，任一时点状态可由重放复现 |
| 内容主体是图像 / 视频 / 音频 | 多模态 KG | 各模态共享同一实体节点，检索结果仍可回到图上推理 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**领域知识能不能被事先写清楚、写完由谁维护**——能写清且有人维护，就上本体驱动（并接受评审以周计的代价）；写不清或写不快，就先开放抽取求覆盖，再从事后数据里归纳轻量 schema。其余约束（规模、模态、参与方数量）改变的是表示层与存储层，不改变「schema 从哪来」这条主线。
>
> 💡 **思考锚点**：用 §3.7 的抽查口径数一下：你图谱里能回答「谁抽的、依据什么、是否被人工确认」的三元组占几成？按这个比例回看 §3.4，你现在这张图更像哪一种组合——宽进严出的开放抽取 + 层次型，还是本体驱动 + 事件型？两者都不像时，缺口落在「schema 从哪来」这条主线的哪一段？
