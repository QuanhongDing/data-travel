## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

§6 的四个案例（Google 2012–2024、字节 2020–2024、阿里 2019–2024、Meta 2020–2024）已经把另一件事说清楚了：**图谱的骨架在 LLM 之前就定型了**。实体与类型化边见 §6 案例 6.1（Google，2012 年起）；离线图嵌入进推荐特征见 §6 案例 6.2（字节，GraphSAGE 一类图嵌入离线预计算）；图数据库商业化与 KG Embedding / GNN 成熟，见主文件 §1.4 的「大数据阶段（2010–2020）」。LLM 加在这一层之上的是三件事——抽取、检索、解释。所以本节的第一件事，是把**骨架**与**AI 加在骨架之上的那一层**分开：骨架可核验、已在生产里跑了十年以上；AI 那一层多数停在可试点，而级别最高的一档（L1）本节没有任何方向达到——原因见下面的表后说明。

本节沿用三条可核验的判据，**三条全中才是 L1**：**①** 已 GA 且有正式 release note；**②** 有第三方（非厂商）公开的生产案例；**③** 接口稳定。**L1 生产可用** = 三条全中，可以排进路线图；**L2 可试点** = 已可用但接口或生态未稳，或只有建设方自有案例，可以做 PoC、不要做核心依赖；**L3 观望** = 仅路线图、论文、厂商演示或预览特性，记录，不要在架构里预留假设。

趋势清单的根本问题不是列错了，而是**没有时间维度**：同一个清单里，「已经有人在生产里用了十年」的实体与类型化边，和「路线图里的某个标准」被并列展示，读者据此排路线图就会踩空。更麻烦的是，图谱这一节的条目横跨三种时间尺度——**底层机制（十年量级）、检索范式（三年量级）、产品能力（一年量级）**——它们混在一张清单里时，看起来像是同一批「前沿」。所以本节给每个方向标级别，级别只回答一个问题：**今天能不能把它写进路线图**。

本主题的第②条有它自己的麻烦：**图谱方向的公开案例基本由建设方自己发布**（搜索公司、内容平台的官方博客与工程文档）。本目录 §6 的四个案例虽然来自**四家互不相关的组织**（Google / 字节 / 阿里 / Meta）、各自给出了规模与口径，但它们的身份就是**图的建设者**——按判据，这类材料属于 **L2 的证据形态**，既不写成「准 L1」，也不在单格里把第②条换一个说法。**第②条只有两种命运：满足，或降为 L2**，没有第三种解释；本节按未放宽的判据执行，于是得到一个不太好看但可复现的结论：**本主题今天没有一个方向够格 L1**，包括看起来最像的那一个。这不是把底座说小了，而是把「谁在说」与「说了什么」分开——底座的规范与接口有十年生产形态（见 5.2.1 的①③），它缺的是**非厂商来源**的公开案例。5.2 各处的评级与判据说明，与本节表格逐条一致。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **图底座：实体 + 类型化边 + 图查询语言 + 离线图嵌入**（未单列，但它是 §6 四个案例的共同核心，也是其余方向的前置条件） | **L2** | ① 满足：已 GA 且有正式发布记录——W3C 的 RDF 1.1（2014）与 OWL 2（2009）推荐标准【公开】，ISO GQL（2024 发布，记于主文件 §2.1）【公开】；③ 满足：属性图与三元组两种模型、Cypher / GQL / SPARQL 这组表达十年未变；② **未满足**：§6 案例 6.1（Google 五亿级实体）、6.2（字节亿级视频节点）、6.3（阿里十亿级商品节点）、6.4（Meta 三十亿级用户节点）全部由建设方自行发布，构不成非厂商的第三方生产案例 | 可以试点且优先级最高（见 5.2.1）：先建实体 + 类型化边的**最小图**并同步建边；②未满足意味着没有非厂商先例可抄，规模与成本要自己先量出来 |
| LLM 增强图谱构建：抽取 / 消歧 / 补全 / 本体扩展 | L2 | 方法有公开论文与开源实现（GraphRAG 2024 年开源，见 5.4），但缺非厂商的、含准确率与语料口径的生产案例；抽取结果的 schema 随模型与提示版本漂移，接口未定 | 在有约束校验与人工抽检的条件下试点；把它当候选生成器，不当入库通道 |
| KG 增强 LLM：GraphRAG / Hybrid RAG / Agent-driven RAG | L2 | ① 开源实现与公开材料齐（5.4）；② 缺跨组织公开的效果口径；③ 索引与检索管线随版本变化，且索引成本 ∝ 语料 token 数（5.2.3 的推算） | 只在「多跳占比高、语料稳定」的语料上试点；先测多跳占比再决定建不建图 |
| Agent-driven 图谱演化 | **L2（只读检索接口）/ L3（写图）** | 只读侧有正式规范可依（MCP 一类工具调用规范带版本日期）；写图侧没有公开的、含误合并率与回滚机制的生产案例，该方向目前仍处 PoC 阶段 | 只开只读；改名、合并、改本体这三类写操作一律不做 |
| KG ⇄ LLM 双向增强与 Neuro-Symbolic（多模态条目） | **L2（KG → LLM 的事实校验与路径解释）/ L3（统一框架、多模态 KG、KG-Agent 标准协议）** | 读方向是检索增强的一种，随 5.2.3 一并定级；统一框架与多模态图谱只有论文与演示，没有可核验的接口 | 小规模验证「答案能不能点回一条边」；不要为「统一框架」预留架构假设 |

> 本主题下**今天没有一个方向处在 L1**，最接近的是图底座（5.2.1）：它 ①③ 满足、② 未满足，按判据就是 L2——而它恰恰不是 AI 带来的：它的公开能力在 LLM 之前就存在（W3C 的三元组与本体规范、图数据库的商业化、离线图嵌入），生产形态见 §6 案例 6.1–6.4。AI 只是把它从「关联密集型业务的选型」变成「检索管线的必需候选族」。§6.7 把它说成 GraphRAG 的地基；本节把它展开成一条可判定的机制：**模型只能沿着已建好的边走**——图上没有建模的关系，模型给出的是措辞流畅但没有依据的答案。

> 底座与四个 AI 方向停在 L2 / L3 的原因并不相同：**底座缺的只是第②条这一条证据**（规范与接口都有十年生产形态，公开材料却全部是建设方自述）；**四个 AI 方向缺的是机制条件**——抽取卡在**没有约束校验就没有正确性口径**（错误从答案层前移到了索引层，更难发现）；GraphRAG 卡在**索引成本与语料稳定度**（它不是性能问题，是你的语料有多稳定的问题，见 Ch4 · 04 混合检索 §7.3.4「结构增强的代价：KG 与 Agentic 贵在哪」）；Agent 写图卡在**误合并不可回滚**；Neuro-Symbolic 卡在**只有范式没有接口**。四个瓶颈不在一处，**成熟时间不会同步**——把它们打包成「AI 原生知识底座」一次采购，一定会被最慢的那件拖住。

两点说明：**其一**，工具条目不逐个给能力判断——版本、年份与能力边界以各自官方文档为准，本节只给「去哪里核验」；**其二**，一批条目（GNN 与 LLM 融合、KG Embedding 新方法、Neuro-Symbolic 项目、多模态图谱的数据集与论文）名称与年份在转述中极易变形，本节不重复断言，只给判定入口。

还有一处结构性错位值得写明：**「Neuro-Symbolic 标准化」与「KG + Agent 标准协议」不是应用方向，是规范与接口问题**。前者说的是「会出现主流框架支持图与模型混合编程」，后者说的是「会出现承载『图谱作为智能体世界模型』的协议」——这两件事只能落在接口上（见 5.3 的 Agent 接口行与 5.6 的第四条预测），不能落在「标准化」这种形容词上。判断方法同样是看三件事有没有写死：谁调用谁、数据以什么形态穿过边界、失败时谁负责。写不出来的「标准化」，在工程上等于没有接口。

**本节与 §3、§4 的分工**：§3 的「开放抽取型」与「事件型」模式（本目录 §3.2.2、§3.2.5）回答「这类图谱长什么样、什么时候选它」，§4 的抽取 pipeline（本目录 §4.2）回答「这条流水线怎么搭」，本节回答「流水线上的每一件能力现在能不能用」。同一件能力在几节里的结论必须一致——§3.5 的反模式表已经写明「抽取无验证」是失效形态，本节把它落成判据（5.2.2 的 L2 评级与「逐条绑定原文」的入库闸），而不是换个说法重讲一遍。

读表的两条纪律：**第一，级别是发给「机制」的，不是发给产品的**——同一款图数据库里，存储与图查询的成熟度、它自带的向量索引的成熟度、它自称的「LLM 知识图谱构建」的成熟度是三个独立的判断，按产品名定级会把三者混成一档。**第二，级别只能靠证据变**——不靠「今年大家都在讲 GraphRAG」升，也不靠「去年有人用错过」降，只靠 §5.4 里官方文档与生产案例这两类证据是否出现。把这条写成回填机制（见上文），比每次争论「它到底成熟没有」省事得多。

**三级各自该怎么用**：**L1 排进路线图**——本节今天没有方向够格 L1（原因见上表），所以这一条写成「升到 L1 的目标形态」：图底座 ①③ 已满足、只缺②，一旦出现非厂商的第三方公开生产案例，它第一个够格。**L2 只做 PoC，并先测出一个数**——抽取测「抽样三元组的可溯源率与漏抽率」（5.2.2）、GraphRAG 测「多跳问题占比」与成本（5.2.3）、事实校验测「答案能点回边的比例」（5.2.3 的校验方向）。测不出数就不上量。**L3 只登记，不做架构假设**——不要在权限模型与本体治理制度上预先为 Agent 写图留位置，留了位置就会有人往里填事。**回填机制**：任何方向一旦出现第三方公开的、含口径与规模的生产案例，升一级；一个 L2 方向一年内仍拿不到你自己语料上的实测数字，降为 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

五个方向都按同一结构写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**。只写收益不写代价的方向应在评审时直接打回——本主题每一次能力提升，都对应一项成本或责任的转移。5.2 展开四个小节，其中 5.2.3 一节写两个同族方向（5.1 表第 3 行与第 5 行）：它们卡在同一条判据上，理由见该节开头。

| 方向 | 机制上发生了什么变化 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 图底座 | 这一层的机制不由 AI 改变：AI 改变的是**谁来走这张图**（分析师手写查询 → 模型按问题生成候选路径） | **需求侧重新定价**（从「关联密集型业务的选型」变成「检索管线的必需候选族」） |
| §5.2.2 LLM 增强构建 | 抽取从「为每类关系训一个监督模型」换成「提示 + 校验」 | **成本结构**（新关系的边际成本从标注与训练掉到改一条提示） |
| §5.2.3（读方向）GraphRAG / Hybrid RAG | 检索从「在文档集合上打分」换成「在图上游走并按约束剪枝」 | **控制流**（候选从哪来变了，答案仍由 LLM 写） |
| §5.2.3（校验方向）KG 作为事实层 | 答案的依据从「模型隐式记忆」换成「一条可检索的路径」 | **接口边界 + 责任**（可解释的是路径，不是边的真假） |
| §5.2.4 Agent 维护图谱 | 维护从「人改图」换成「事件触发 + 候选 + 人审」 | **触发方式 + 判定来源**（误判的代价不对称） |

有一类条目必须提前分出去：**「给知识图谱加一个自然语言问答框」是接口改良，不是架构变化**。判断方法是问三句——图的 schema 增加了类型吗？抽取链路增加了来源吗？权限模型增加了判定点吗？三句都是「没有」，那它只是消费侧的一个新前端，应记入工具升级，而不是写进架构演进。本节把它并入 5.2.3 的 L2，一半原因就在这里：**接口改良的风险低，但它也不解决图的质量问题**。

#### 5.2.1 图底座：把「JOIN 到崩溃的关联查询」换成「在边上走」

- **旧做法与它的卡点**：卡点写在主文件 §1.1 的第一条：传统 SQL 做 3-5 跳 JOIN 性能崩溃，而图数据库做多跳遍历是 O(V+E) 复杂度。这两句不是同一量纲的比较：前者的代价随**跳数**和中间结果集膨胀，后者随**图的规模**（顶点数 + 边数）线性增长。真正的卡点不在单次查询的常数，而在**关联深度的可预测性**——SQL 侧写 5 跳 JOIN 时，优化器能不能走通取决于统计信息与索引，同一条 SQL 在不同数据分布下会从秒级掉到分钟级；图侧把「走几跳」变成一次有界的邻居扩展，成本可以按图规模做容量规划。
- **AI 改变了什么机制**：严格说，**这一层的机制不是 AI 改的**。实体 + 类型化边 + 图查询语言 + 离线图嵌入在 LLM 之前就已定型（主文件 §1.4 的「大数据阶段（2010–2020）」）。AI 改变的是**谁来走这张图**：从分析师手写查询，换成模型按问题生成候选路径（5.2.3）。对底座本身，这是一次**需求侧的重新定价**——它从「关联密集型业务的选型」变成「检索管线的必需候选族」。
- **由此得到的**：因为上层只能沿着已建好的边走，**底座的建模范围直接决定了 AI 那一层的上限**：图上没有建模的关系，模型给出的是措辞流畅但没有依据的答案。反过来说，这条机制对时间的依赖最小——今天做与明年做，差别只在于晚一年才有数据。
- **由此付出的**：**其一，成本前移**——卡点从查询侧挪到建模侧，schema 设计、本体维护、主数据对齐（5.3 的 OneID 行）都成了固定投入，且这些投入在前两个季度看不出收益。**其二，只建节点不建边，图会退化成标签库**（§6 案例 6.2 的教训：节点与边要同步建）。**其三，新的故障形态是尾延迟**——单机扛不住时先做热图 / 冷图分层与场景裁剪（§6 案例 6.3 的教训），而不是先接 LLM 抽取；抽取只会让边数再上一个量级。**其四，方言与迁移成本**：Cypher / GQL / SPARQL 表达各有差异，跨引擎迁移落在查询重写上（5.3 把「能否导出 RDF / 有无正式图查询语言条目」列为选型项，原因就在这里）。
- **证据与来源**：【公开】W3C 的 RDF 1.1（2014）与 OWL 2（2009）推荐标准、ISO GQL（2024 发布，记于主文件 §2.1）；生产形态见本目录 §6 案例 6.1（Google，2012 年起）、6.2（字节）、6.3（阿里）、6.4（Meta），四例都给了规模口径——**但这四例都是建设方自行发布**，按 5.1 的判据属于 L2 的证据形态，不是第三方生产案例。判定方法：拿你自己的关联查询问三个数——现在需要几跳、当前 P95 是多少、跳数再加一跳时成本怎么变。
- **成熟度**：**L2**。判据：① 满足（已 GA 且有正式发布记录：W3C 的 RDF 1.1 / OWL 2、ISO GQL）；③ 满足（属性图与三元组两套模型、Cypher / GQL / SPARQL 十年未变）；② **未满足**（公开生产案例全部来自建设方自述，缺非厂商来源）。与 5.1 表格中该行逐条一致。
- **什么时候值得做**：当关联查询已经让 SQL JOIN 崩溃、或「需要几跳」这个问题在业务侧反复出现时，最小图（实体 + 类型化边）今天就值得建。**什么时候不值得做**：关联深度长期在两跳以内、且现有宽表加索引就够用时，图的建模与运维成本换不来收益。
- **诚实的定位**：它解决的是**「关联深度的代价不可预测」**这一类失败，不解决**「图上的边对不对」**这一类失败——后者属于抽取层（5.2.2）。把两件事混在一起验收，会让底座背上一堆它无解的问题。

#### 5.2.2 LLM 增强图谱构建：把「训练专用抽取模型」换成「提示 + 校验」

- **旧做法与它的卡点**：抽取靠两代方法。第一代是规则与词典（高准确、低召回，见主文件 §2.3 对 NER 的列法），第二代是监督模型（CRF、BiLSTM-CRF 一类）与远程监督——远程监督用已有图谱自动标注训练数据，噪声大。卡点不在效果而在**边际成本**：每新增一类关系，就要重新标注一批语料、重训一次模型、重跑一次评测。业务侧的关系类型是持续增加的，于是「图上能表达什么」被标注预算锁住。
- **AI 改变了什么机制**：把「为每类关系训练一个抽取器」换成「一次提示 + 校验 + 抽检」。抽取器的产出来源从**标注数据**变成**提示词与模型版本**，于是新增一类关系的边际成本从「标注 + 训练 + 评测」掉到「改一条提示 + 跑一遍抽检」。注意这里机制落在**成本函数**上，不在准确率上：它不是「抽得更准」，而是「改起来更便宜」。
- **由此得到的**：因为新增关系的成本大幅下降，所以图谱的**关系类型覆盖面第一次可以跟着业务走**，而不是跟着标注预算走。但这条收益换掉的是**新增一类关系的边际成本**，不是**约束与抽取的先后顺序**——抽取结果在写图前仍至少要过写入端最小约束（关系类型清单 + 命名空间 + 逐条绑定原文，见下面的两道闸、§3.5 对「无 schema」的修法「哪怕只是轻量的词表与关系类型表」，以及 §7 的写入端最小约束），无约束的抽取不得入生产图（§5.3、§3.5「抽取无验证」）；可以「跑起来之后再逐步补」的是本体与 SHACL 的**细化程度**，不是入库前的那道校验——§3.5 把「验证被放到『以后再说』」列为「抽取无验证」的成因，§4 的落地顺序也写明「先建抽取再补 schema，等于让抽取输出的形态反向决定模型」。
- **由此付出的**：**其一，正确性从一个可测量的模型指标（F1）变成一个随提示与模型版本漂移的产物**——提示一改、模型一升级，同一批语料抽出来的图就不一样，而「上一次的图是哪个版本抽的」往往没被记下来。**其二，错误形态从「漏抽」变成「抽出一条看起来很合理的关系」**——漏抽让图缺东西，能发现；幻觉边让图多出东西，且因为写得通顺而更可信，这就是 §3.5 把「抽取无验证」列为反模式的原因。**其三，代价转移**：人力成本换成了推理成本与校验成本，后者随**语料量**增长，前者随**关系类型数**增长，两者不是同一条曲线。**其四，本体层面的越权**：让模型「提议新实体类型与关系类型」等于让它参与 schema 决策，而 schema 一旦分散，跨图谱对齐的成本会成倍上升（主文件 §2.4 那条「没有本体的 KG 是数据沼泽」，在这里表现为没有约束的抽取）。
- **证据与来源**：【公开】微软的 GraphRAG 于 2024 年开源，其公开材料把「实体与关系抽取 + 社区摘要」作为回答全局性问题的机制，可自行核验其仓库文档中的索引构建流程与成本提示；本目录 §4.2 把这类流水线写成「LLM 抽取 + 规则校验 + Reasoner 验证 + SHACL 校验」四步，§3.5 的反模式表把「抽取无验证」列为失效形态；主文件 §2.3 列出了 NER 与 RE 的三代方法（规则 / 监督 / LLM）。判定方法：抽 200 条抽取出的三元组，逐条回到原文核对是否被支持，得到**幻觉率**；再把原文里明显存在但没被抽出的关系单列，得到**漏抽率**。这两类数必须分开记——它们的处置方式相反。
- **成熟度**：**L2**。判据：① 有公开论文与开源实现；② 缺非厂商的、含语料口径与准确率的公开生产案例；③ 抽取结果的 schema 随模型与提示版本漂移，接口未定。
- **什么时候值得做**：当你要抽的关系类型会持续增加、且语料已有稳定来源时，边际成本优势真实存在。**什么时候不值得做**：关系类型已经固定、语料规模在千篇级时，规则 + 词典的准确率与可解释性都更好，且没有版本漂移问题。
- **失效条件**：当语料本身是短文本、关系稀疏（工单、评论、日志摘要）时，抽出来的边既少又难复核，图谱的收益抵不上校验成本；此时正确做法是继续用向量检索，把关系留给已有的结构化字段。
- **诚实的定位**：它解决的是**「关系类型覆盖不了业务」**这一类失败，不解决**「抽出来的关系对不对」**这一类失败——后者只能靠约束与抽检，与模型大小无关。把两类失败混在一起验收，会让抽取这一层背上一堆它无解的问题。
- **上线前的最小验证**：抽 200 条三元组逐条回原文核对（幻觉率），同时统计漏抽率；再把「无法被原文支持」的部分按关系类型分组——如果某类关系的幻觉率明显高于其他类，先停用该类关系的自动抽取。

```text
    抽取入库的两道闸（缺一道，错误就会变成「图上的事实」）
      语料 ──► [LLM 抽取] ──► 候选三元组
                                  │
        闸 1：逐条绑定原文片段（没有出处的边不入库）
        闸 2：约束校验（本体类型 + 基数为真 + SHACL 形状）＋ 人工抽检
                                  │
                                  ▼
                            可审计的图（每条边可回原文）
    ────────────────────────────────────────────────
    登记项：抽取模型版本 + 提示版本 + 抽检时间
      理由：换模型等于换图；不登记就分不清「源变了」和「抽取变了」
```

#### 5.2.3 KG 增强 LLM + KG 作为 LLM 的事实层：从「候选从哪来」到「依据怎么呈现」

这一节写两个同族方向：**读方向**（GraphRAG / Hybrid RAG）改变的是**检索的控制流**，**校验方向**（KG 作为 LLM 的事实层）改变的是**答案的依据来源**。两半合成一节，是因为它们卡在同一条判据上——② 缺非厂商公开的效果口径；5.1 表第 5 行本来就写着「读方向随 5.2.3 一并定级」。两半各按同一套六行结构写，成熟度分别给。

**读方向：把检索从「文档上打分」换成「图上走 + 约束剪枝」**

- **旧做法与它的卡点**：向量检索的卡点，三条今天依然成立：**检索靠相似度、无法做多跳**；**没有关系约束**，多个片段可以互相矛盾而都被召回；**没有「实体类型 / 关系类型」的概念**，因此无法回答「这个答案是哪个实体、经由什么关系得到的」。主文件 §1.1 把这条优势写成「传统 SQL 做 3-5 跳 JOIN 性能崩溃，图数据库做多跳遍历是 O(V+E) 复杂度」——注意它换掉的是代价的自变量：图遍历的成本随**图的规模**（顶点 + 边）线性增长，跳数只决定一次有界扩展的范围，而不是「每多一跳就再套一层 JOIN」。这条优势在纯向量检索里完全用不上。
- **AI 改变了什么机制**：GraphRAG 一类方案把「在文档集合上打分」换成「在图上游走并按约束剪枝」，同时把「社区摘要」作为回答全局性问题的候选来源。它改变的是**检索的控制流**——候选从哪里来、经过哪几跳——而不是答案由谁写。索引侧新增了 LLM 抽取与社区摘要两步，查询侧新增了关系遍历与摘要读取——对应 GraphRAG 的四阶段：Indexing、Community Detection（用 Leiden）、Community Summary、Local 与 Global Search（Ch4 · 04 §7.3.4 把这一族统一称为「结构增强」，并给出它与 Agentic 的成本对照）。
- **由此得到的**：因为候选不再只来自语义近邻，所以**多跳与全局问题第一次可以靠一次查询回答**——「这家公司的供应链上还有谁」「这批文档整体在讲什么」这类问题，打分式检索没有表达力，而图遍历与社区摘要天然是为此设计的。这也正是 §6.7 把图谱称为 GraphRAG 地基的机制含义。
- **由此付出的**：**其一，建图成本 ∝ 语料 token 数**：抽取与摘要都要把语料过一遍 LLM，成本随语料量线性增长，而向量索引的构建成本与之相比低一个量级。**其二，更新成本远高于插入**：一篇文档变更后通常要重新对齐实体、重算受影响的社区摘要——这是「建图必须当数据加工流水线运维」的原因（有分区、有重跑、有版本、有失败重试）。**其三，抽取质量随模型版本漂移，换抽取模型等于换图**，历史结论无法直接复核。**其四，它不擅长精确事实查询**：结构化事实仍应走 Cypher / GQL / SPARQL，用图去「生成」答案是两件事——这条局限成立，且值得写成接口约定（见 5.3）。**其五，社区摘要引入了一层不可核对的中介**：摘要由模型写，读者无法从摘要反推它省略了哪部分社区内容。
- **证据与来源**：【公开】微软的 GraphRAG 于 2024 年开源（论文见 5.4），公开材料含索引构建流程与成本提示；主文件 §1.4 记 2024 年 GraphRAG 把 KG + RAG 推向工业级。成本量级见 Ch4 · 04 混合检索 §7.3.4 的推算（100 万篇、平均 500 token，则一次全量抽取约五亿 token 输入）。判定方法：在你的问题集上标注**需要跨文档汇总或多跳的比例**；该比例 ≲ 10–20%【经验】（同 Ch4 · 04 §7.3.4）或语料每天大幅变更时，先别建图——为少数问题把全部语料做成图，是把成本摊在不需要它的部分上。
- **成本量级（【推算】增量更新一侧）**：沿用 Ch4 · 04 §7.3.4 的全量口径（100 万篇 × 500 token），另设日变更率 1%【经验】，则每天需重抽 1 万篇【推算】（100 万 × 1% = 1 万）；单篇输入 = 正文 500 token + 提示模板约 300 token = 800 token/篇【经验】，故增量抽取约 **800 万 token/天**【推算】（1 万篇 × 800 token）。再乘平台单价即得日成本，并要加上受影响的社区摘要重算。**要点不是这个数，而是它的自变量是语料变更频率**——语料越活跃越贵，而向量索引的成本自变量是数据量本身。
- **成熟度**：**L2**。判据：① 有开源实现与公开论文；② 缺非厂商的、含语料口径与效果对照的公开案例；③ 索引与检索管线随版本变化，接口未定。
- **什么时候值得做**：三个条件同时成立时收益最确定——问题集里多跳与汇总类占比高、语料更新频率低、且这类问题的错误代价高（合规问答、尽调、排障溯源）。**什么时候不值得做**：语料每天大幅变更（建图当天就过期），或问题集中在「找一篇具体文档」时，图与社区摘要都属于过度设计。
- **失效条件**：当图上的关系覆盖不足时，能力会反转——从「答不了」变成「沿着仅有的一条边走出一段看起来完整的推理」。判断方法很直接：抽查 30 个多跳答案，看每一步跳转的边是否都存在于图上，还是有几步是靠常识补的。
- **诚实的定位**：它解决的是**「打分式检索对关系没有表达力」**这一类失败，不解决**「图上的边是假的」**这一类失败。前者靠控制流，后者靠 5.2.2 的入库闸；把两者当成一件事，会在抽取质量差时误判为「GraphRAG 这条路走不通」。

```text
    Hybrid RAG 的三路分工与各自的失败归属
      问题 ──► [意图识别]
                 ├── 向量召回   → 语义近邻       失败形态：召回不到（不报错，只答错）
                 ├── 图遍历     → 多跳与汇总     失败形态：图上没有这条边（缺建模）
                 └── 本体约束   → 类型与基数校验  失败形态：边存在但不合约束（脏数据）
                 ▼
            候选融合 ──► 生成答案 ──► 逐条标注依据（哪条边、哪段原文）
    ────────────────────────────────────────────────
    三种失败必须分别埋点：召回缺失、关系缺失、约束冲突的修法完全不同
      合并成一个「答得不对」的指标，等于放弃定位
```

**校验方向：把「模型的记忆」换成「一条可核对的路径」**

- **旧做法与它的卡点**：LLM 的知识是隐式的、有截止日的、无法溯源的（主文件 §2.4 的对照：大模型是隐式 / 概率 / 不可溯源，图谱是显式 / 形式化 / 可推理 / 可溯源）。卡点有两个：一是**无法回答「你为什么这么说」**，二是**无法在事实变化后被纠正**——纠正一个模型的事实远比改一条边贵。
- **AI 改变了什么机制**：把答案的依据从「模型隐式记忆」换成「一条可检索的路径」。这件事可以拆成四条链路（LLM 抽取 → KG、KG 校验 → LLM、KG 推理 → LLM、LLM 解释 → KG）；机制上只有**前两条是架构变化**——抽取改变了图的生产方式，校验改变了答案的依据来源；后两条（推理结果交给 LLM 措辞、查询结果翻译成自然语言）是**表达层的工作**，不改变谁掌握事实。
- **由此得到的**：因为答案可以被指回具体的节点与边，所以「可解释」第一次不依赖模型的自我陈述——它变成一次可以复核的查询。这是在审计与合规场景里唯一站得住的解释形态：审计要的不是一段说明，而是**一条可以自己走一遍的路径**。
- **由此付出的**：**其一，可解释的边界被高估**——路径能回答「答案用了哪条边」，回答不了「这条边本身对不对」；一条错误的边会让错误答案**看起来更可信**，因为现在它有出处了。**其二，覆盖面的错觉**——图只对已建模的关系构成事实层，未建模的维度模型依然靠猜，而用户无法区分这两种情形。**其三，三元组只表达真值，不表达「谁在什么口径下认为它是真的」**（时效、来源、置信度需要另外建模），这正是主文件 §2.4 把「没有本体的 KG」称为数据沼泽的原因：缺的从来不是节点数，是约束与出处。**其四，多模态与统一框架那一层（多模态图谱）目前只有论文与厂商演示**，把它当作可规划的架构会踩空。
- **证据与来源**：读侧证据与上面的读方向同源（微软 GraphRAG 于 2024 年开源，见 5.4）；Neuro-Symbolic 与多模态图谱本节不重复断言其项目名称与年份，只给判定入口（见 5.4）。判定方法：取 30 个问答，逐条检查答案里的每个断言能不能点回一条具体的边；再抽查被点回的那些边，统计其中无法回到原文支持的比例——**这两个比例一起看才有意义，只看第一个会得出「可解释性很好」的结论**。
- **成熟度**：**L2（KG → 事实校验与路径解释，作为检索增强的一部分）/ L3（Neuro-Symbolic 统一框架、多模态 KG、KG-Agent 标准协议）**。判据：读方向随上一半的 GraphRAG 一并停在「② 缺非厂商公开效果口径」上；统一框架与多模态图谱只有论文与演示，没有可核验的接口。
- **什么时候值得做**：当错误答案的代价高到需要「逐条指认依据」（合规问答、对外披露、跨部门结算）时，读方向今天就值得做，而且它不依赖任何未发布的能力。**什么时候不值得做**：问答场景本身就是探索性的、答案不需要引用时，加这一层只会增加延迟与成本。
- **失效条件**：当问题的答案不在图上、而模型又擅长给出通顺回答时，这个架构反而**降低了错误的可见度**。正确做法是把「图上没有」显式返回（拒答或降级到文档检索并标注来源），而不是让模型用图以外的知识补齐。
- **两半分界**：同一节里的两半容易混。**读方向管「候选从哪来」，校验方向管「依据怎么呈现」**；前者的验收指标是命中率一类可对照的数，后者的验收指标是「答案能不能点回一条边」。同一个系统里两者可以一起上，但回归测试必须分开做——否则一次措辞改进会让「依据链」这一项看起来也变好了。

#### 5.2.4 Agent 驱动的图谱演化：把「人改图」换成「事件触发 + 候选 + 人审」

- **旧做法与它的卡点**：图的维护是周期性动作——上一次本体评审、数据源 schema 变更靠人发现、质量问题靠下游报上来才处理。卡点是**触发依赖人的注意力**：源系统改了、图没人跟着改，并且这种落后不会被报错暴露，只会表现为答案慢慢变旧。这套想法可以拆成四个角色（schema 变更监听、业务事件更新实例、质量问题检测与修复提议、与人协作审批）。
- **AI 改变了什么机制**：把治理动作从「周期性项目」换成「事件触发」，并把判定来源从「规则」换成「统计判断」——漂移从字段名比对扩展成语义判断，质量问题从约束报错扩展到「这条边看起来不合理」。**改变的是触发方式与判定来源，不是治理目标**。
- **由此得到的**：因为触发不再依赖下一次评审，所以图的**陈旧度第一次可以被度量并要求**（每条边带「最后核验时间」）。四个 Agent 要拆成两类看：**变更同步与漂移检测是自动化**（有明确规则：DDL 差异、枚举值新增、约束校验失败），**本体修改与实体合并才需要模型判断**——前者今天就该做，后者是 L3。
- **由此付出的**：**其一，误合并不可回滚**——把一个实体错误地并入另一个实体，这张图上的所有下游结论同时被污染，且很难逐条撤回；而漏合并只是少了一批关联。两者代价不对称，阈值必须偏保守，**自动化率注定达不到宣传里的水平**。**其二，写操作需要审计与回滚**——Agent 改图（改类型、合并实体、删边）必须能回答「谁在什么时候改的、依据什么、怎么回滚」。**其三，判定随模型版本漂移**——「这条合并是哪个版本判的」要可查，否则历史决定无法复核（与 5.2.2 对抽取版本的要求同源）。**其四，图的可信度是整体的**：一条被误合并的边不会只影响它自己，它会顺着路径传播到所有引用它的结论上——这是图与表在故障形态上最大的不同。
- **证据与来源**：只读侧有可核验的接口规范【公开】（MCP 由 Anthropic 于 2024 年 11 月公开发布、规范带版本日期；判定方法是看它有没有独立规范文档 + 版本日期 + 变更记录，而不是看产品页上有没有「支持 MCP」这句话）；写图侧本节不引用任何公开案例——ontology-agent / kg-monitor / auto-kg 一类项目 2025 年仍在 PoC。判定方法：写下「它代谁执行、依据什么、怎么回滚」三句话，写不全就说明接口还没成立。
- **成熟度**：**L2（只读检索接口）/ L3（写图：改名、合并、改本体）**。判据：只读侧有正式规范可依；写侧没有公开的、含误合并率与回滚机制的生产案例。
- **什么时候值得做**：当「源系统改了、图没跟上」已经成为反复出现的抱怨，且你已有可自动计算的漂移定义时，检测与告警值得立刻做。**什么时候不值得做**：图规模在万级实体以内、变更频率低时，人工评审更省事，且不会引入误合并风险。
- **诚实的定位**：它解决的是**「图没人维护就慢慢变旧」**这一类失败，不解决**「维护动作本身会不会做错」**这一类失败。前者靠触发方式（事件 vs 周期），后者靠权限分级（可逆与不可逆分开）——把两者合成一个「自动化率」指标，会逼着团队把不可逆的操作也交给模型。
- **上线前的最小验证**：取 100 处源系统的真实变更，看检测机制能不能全部命中（漏报），再看它报出来的变更里有多少其实是噪声（误报）；两类数分开记。合并类操作另做一次「反向抽查」：随机取 20 组被判定为同一实体的记录，人工复核。

```text
    图谱维护的权限分级（按可逆性分，不按能力分）
      检测 / 告警（只读 + 提示）      → 可自动，错了只是多一条待办
      同步既有 schema（照 DDL 走）    → 可自动，且有据可查
      新增实例与边（带出处）          → 可自动，但必须逐条绑定原文与来源
      ────────────────────────────────────────────────
      改类型 / 合并实体 / 改本体约束  → 必须人工定案
        理由：这三类是唯一「一次错误就污染全图且难以逐条撤回」的操作
```

### 5.3 与本主题既有栈的接口在哪

本节不写「与 X 结合」这类空话，只写三件事：谁调用谁、数据以什么形态穿过边界、失败时谁负责。「现状」一列只回答「这项交接今天能不能用」，用的不是 5.1 那套要求第三方生产案例的级别刻度——本节没有任何方向达到 L1，原因见 5.1 表后段。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 数仓 / 湖仓 ↔ 图谱（实体与边的抽取） | 交接物 = 抽取出的实体与关系 + **抽取模型版本 + 源记录标识** | 抽取侧；下游必须能分辨「源变了」与「抽取器变了」 | 既有技术（今天可用） |
| 本体 / SHACL ↔ 图谱 | 交接物 = 约束文件 + 校验报告；**约束是抽取的验收条件，不是文档** | 本体侧；无约束的抽取不得入生产图（§3.5「抽取无验证」） | 既有技术（今天可用） |
| 图谱 ↔ 检索层（结构增强这一族） | 交接物 = 子图 / 路径 + 节点标识；**图只提供候选与依据，不写答案** | 检索侧；图遍历超时要能降级回向量与关键词 | 可试点 |
| 图谱 ↔ 向量库（Hybrid RAG） | 交接物 = 两路候选 + 融合参数；两路的模型与索引版本要能一起升级 | 检索侧；一次升级要重建两路，运维面成对增加 | 组件既有可用 / 方案可试点 |
| 图谱 ↔ LLM（事实校验与路径解释） | 交接物 = 可点回的路径；**模型只解释，不改图** | 图谱侧管事实，应用侧管措辞 | 可试点 |
| 图谱 ↔ Agent（MCP 一类工具调用） | 交接物 = 工具调用 + 调用者身份 + 预算；**只读优先** | 组织侧；越权与误写不可归因于模型 | 只读可试点 / 写入观望 |
| 主数据 / OneID ↔ 图谱 | 交接物 = 实体标识；**图谱不新造标识**（主文件 §2.4：OneID 是 KG 的特例） | 主数据侧；同一实体两个 ID 会让图分叉，且分叉后影响面按跳数放大 | 既有技术（今天可用） |
| 图谱 ↔ 指标 / 特征（图嵌入进下游模型） | 交接物 = 离线算好的节点与边表示；在线只查表 | 图谱侧；在线直查图是尾延迟的常见来源（§6 案例 6.2 的教训） | 既有技术（今天可用） |

一句话概括：**AI 没有新增调用关系，只把「走图的人」从分析师换成了模型**。因此接口上多出来的只有三样东西——**身份与权限域、依据（这条结论指回哪条边或哪段原文）、版本（抽取与索引的版本）**。三样缺一，AI 那一层就不能接。

三条最容易出错的约定，单独写清：

**第一，约束校验必须在入库前，而不是事后巡检。** 事后巡检发现一条幻觉边时，它可能已经被下游引用了若干轮——而图上的错误会顺着路径传播，撤回等于要重跑所有引用过它的结论。这一条与 §3.5 把「抽取无验证」列为反模式是同一件事：**验证的位置决定了纠错成本的数量级**。判定方法：看你的流水线里，约束校验跑在「写图之前」还是「写完之后的巡检任务里」。

**第二，派生副本（向量、社区摘要、图嵌入）必须可重建、可过期。** 这三样都是从图派生出来的，图一变它们就要跟；跟不上时出现的不是报错，而是「看起来合理但已经过期」的答案——这是 AI 层最隐蔽的失效形态。所以每个副本都要记录「最后刷新时间与抽取版本」，并在超期时降级或拒答，而不是继续拿旧副本回答。判定方法：随便挑一条上个月改过的边，看它在向量与摘要里是不是也更新了。

**第三，写操作必须审计，改名、合并与本体修改不允许自动执行。** 这三类操作的错误不会当场暴露，而没有当场暴露的错误需要一个人来负责。注意这条不只是流程要求，它同时决定了接口形态：**只读接口可以把身份、权限与预算都省略掉，写接口一个都不能省**。

三条约定的共同点：**它们都不是技术接口，而是责任接口**。本主题所有的失效最后都落在这一层——模型能抽、能走、能解释，但不能负责。

再补一条失败责任的划法，因为它决定事故电话打给谁：**「图上没有」与「图上有错的边」是两件性质不同的事，不能混在一个告警里。** 前者是能力问题，可降级（退回向量检索）、可告警；后者是事故，因为它会被当成依据使用，且无法用「模型不准」解释。这条划法与 5.2.3 的埋点要求一致——**召回缺失、关系缺失、约束冲突必须分成三条路径**，前两条允许自动降级，第三条必须人工介入并回溯是哪一次抽取带进来的。

还有一处交接物容易被忽略：**图谱与下游模型的边界**。当图嵌入作为特征进入推荐或风控模型时（§6 案例 6.2 的形态），交接物是「离线算好的节点与边表示」，而失败时最危险的不是特征缺失，而是**特征悄悄地变了**——图上的边被重抽过、或合并规则改过，模型看到的分布就变了，而模型侧看不到这件事。所以这份交接物必须带上「图的版本与生成时间」，由图谱侧负责登记，模型侧负责在版本变化时决定是否重训。这条与 5.2.2 的抽取版本登记是同一件事的两端。

### 5.4 公开进展与文献

**第三方生产案例（本节缺项）**

- 本节**没有**第三方（非厂商）的生产案例可列，而这正是本节没有任何方向够格 L1 的原因。最有力的可用材料是本目录 §6 案例 6.1（Google）、6.2（字节）、6.3（阿里）、6.4（Meta）——实体与类型化边、离线图嵌入、图规模与治理，四例都给出了规模口径，但**发布方就是图的建设方**，按 5.1 的判据只构成 L2 的证据形态；具体数字与口径回该节核对。

**四类材料的更新速度不同**：论文与「检索入口」（持续更新的产品文档页）最快（以年为单位），正式标准与官方发布记录次之（以数年为单位），生产案例最慢。**不要用其中一类的结论去推另一类**——拿今年的开源实现去论证「组织的图谱质量已经跟上」，是本主题最常见的一步跳空。

**核验 §5.1 表里五个宣称的最小动作**（都不需要采购、不需要新版本，也不用等厂商路线图）：

1. **底座**：拿你自己的关联查询问三个数——需要几跳、当前 P95、跳数再加一跳时成本怎么变；再抽 20 个实体，看它们的边有没有「抽取来源 + 模型版本」这类条目，没有的边就是不可复核的边，按不可信对待（见 5.2.1）。
2. **抽取**：抽 200 条三元组回原文核对（幻觉率），并统计漏抽率——两类数分开记（见 5.2.2）。
3. **GraphRAG**：在你的问题集上标注多跳与汇总类占比；同时统计语料日变更率——两个数决定要不要建图（见 5.2.3）。
4. **事实校验**：取 30 个问答，统计「答案能点回一条边」的比例，再抽查这些边里无法回到原文支持的比例（见 5.2.3 的校验方向）。
5. **Agent 写图**：写下「它代谁执行、依据什么、怎么回滚」三句话；写不全就说明接口还没成立（见 5.2.4）。

这五条动作的共同点：**它们用的都是你自己的图、你自己的问题集和公开文档**。归类方式也说明一下：**这五条与 §5.1 表的五行一一对应**——第 1 条对图底座（5.2.1），第 2 条对构建（5.2.2），第 3、4 条同属 5.2.3 的两半（建图的条件与依据链），第 5 条对 Agent 写图（5.2.4）；展开次序与 5.2.1–5.2.4 相同。第 1 条同时是其余四条的前提，这也是 5.2.1 排在最前的原因。本节把方向判成 L1 / L2 / L3，依据的是 5.1 的三条判据，以及 5.2.1–5.2.4 各自写出的核验动作——**能做出结论的，才有资格进路线图**。

**怎么用这份清单**（先看结论再看出处，能省一半时间）：要核「图底座该不该现在做」→ 看第 1 条；要核「能不能让模型抽边」→ 看第 2 条；要核「要不要上 GraphRAG」→ 看第 3 条；要核「可解释性够不够」→ 看第 4 条；要核「Agent 能不能改图」→ 看第 5 条。五条都不需要采购。

> 上面这四类材料的用法不同：**论文**给机制（为什么这样设计有效），**官方文档 / release note / 官方发布记录**给接口形态与判定入口，**检索入口**给「去哪里核验、按什么标准判断」，**第三方生产案例**给可用性证据。落到分级上，5.1 的三条判据各有对应的证据类——①（已 GA 且有正式 release note）与 ③（接口稳定）靠官方文档与标准发布记录，②（第三方非厂商的生产案例）靠生产案例——**三条都进判据**；论文解释机制但不单独给级别。**厂商材料**（产品博客、厂商案例）只给线索、不进判据：本节清单里凡属厂商发布的条目都标明了发布方身份，只作时间锚点或检索入口。不做这个区分，本节就会退回成趋势清单。

### 5.5 被过度宣传的部分

**①「GraphRAG 让 RAG 不再幻觉」与「知识图谱就是 LLM 的事实层」** —— 实际是：前者换掉的是**候选从哪来**，没有换掉**答案由谁写**，抽取阶段没有本体约束时，图本身就是模型产物，错误从答案层前移到了索引层，而且更难发现——因为它现在以「事实」的形态存在；后者只对**已建模的关系**才是事实层，对未建模的维度它什么也不是，而这两种情形在用户侧看起来完全一样，更根本的问题是三元组只表达真值、不表达「谁在什么口径下认为它是真的」（时效、来源与置信度需要另外建模，主文件 §2.4 的「没有本体的 KG 是数据沼泽」说的就是这件事）。原因：**把「结构变显式」当成了「内容为真」**。**它们什么时候才会成真**：当抽取结果逐条绑定原文（幻觉率可测）、有约束校验、抽取模型版本随图登记，并且「图上没有」能被显式返回、每条边都带出处与时效时——这些都是工程动作，换一个模型解决不了。

**②「Agent 自主维护图谱」与「LLM-first 建图：人只做审核」** —— 实际是：前者能自动做的是**有明确规则的同步**（schema 变更、枚举值新增、约束失败告警），不能自动做的是**本体修改与实体合并**——而后者才是图失效的主因；后者把「人做审核」当成了一个便宜动作，而审核恰恰是瓶颈：一亿条边里抽检多少条才够，这个问题不解决，「人只做审核」等于「没人真的看过这张图」。原因：**责任不能自动化**，而且「能生成」不等于「能验收」。**它们什么时候才会成真**：出现公开的、含误合并率与回滚机制的生产案例，以及写明了抽检比例与验收口径的建图制度；在此之前，Agent 只开只读。

**③「KG 治理 SaaS 化 / KG Hub 会出现」与「多模态图谱主流化」** —— 实际是：图的治理对象是本体、约束与实体标识，这三样恰恰是最难跨组织标准化的部分，而托管服务能标准化的是运行环境（存储、备份、查询算力）；多模态那一侧则是在文本图上的抽取质量还没做稳之前，把同一批未解决的问题搬到更贵的模态上（视频与传感器数据的抽取成本更高、可复核性更差）。原因：**把「运维托管」当成了「治理托管」，把「能生成」当成了「能验收」**。**它们什么时候才会成真**：出现带版本与 SLA 的托管图谱服务，并且它明确规定了本体变更的审批与回滚流程；多模态则要先看到公开的、含各模态抽取质量口径的材料——只有前者没有后者，那还是一次基础设施托管。

这三条的共性值得点明：**它们都把「结构变显式了」说成了「内容变对了」**，而本主题的瓶颈始终是抽取质量与责任归属。反过来说，这些方向不是不能做：它们都是图谱质量的**放大器**——质量好时放大收益，质量差时放大错误。先量幻觉率与漏抽率、再决定放不放大，是本节最省钱的一条习惯。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 图底座会作为**检索管线的一个候选族**进入默认架构，而不是作为独立平台存在 | 主流检索框架与向量库的官方文档里，把「图遍历」列为与稠密、稀疏并列的一路召回（有正式条目） | 三年后图仍以独立项目形式存在、检索栈里没有它的位置；或反过来，图把向量完全替代 |
| 「可溯源率」会成为独立于图规模的一等验收指标（图上多少条边能回到原文） | 产品元数据模型里出现「抽取证据 + 模型版本」字段（官方文档条目可见）；治理制度要求未绑定出处的边不入生产 | 三年后验收仍只说实体数与边数，仍以规模论成败 |
| 行业图谱标准会继续由监管与专业学会驱动（医疗、金融），而不是由通用模型厂商定义 | 出现新的公开行业本体规范及其版本记录，并规定「术语与约束必须机器可读」 | 三年后行业标准仍停留在「要不要建图谱」；或标准把模型选型写成了合规要求 |
| KG 与 Agent 之间的协议会先以**只读查询规范**的形式出现，而非「图的读写全权委托」 | 出现带版本日期的公开规范，且范围限于查询与身份传递 | 三年内没有任何带版本日期的公开规范；或第一版规范就包含写操作且不含审计与回滚条款 |

写这四条的约定：**信号必须是外部可观察的**（官方文档条目、公开规范、产品字段），不是「我觉得会」。**被检验得最快的是第一条与第二条**——一年内就能从产品文档里看到；**最慢的是第三条**，标准发布以年计，本节对它不给时间预期。凡写不出证伪信号的判断，本节不写。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 关联查询已经让 SQL JOIN 崩溃、但图谱还没建 | 先建实体 + 类型化边的最小图并同步建边（§6 案例 6.2 的教训：只建节点会退化成标签库） | 观察多跳查询 P95 与「需要多跳的比例」 | 不要先上 LLM 抽取；先用规则或既有主数据把主干实体与边建齐 |
| 已经有图，想接 LLM 做抽取 | 先定约束（本体 + SHACL），再让模型抽 | 观察幻觉率与漏抽率两类数（不能合成一个准确率） | 不要让抽取结果未经出处绑定直接入库；不要让它参与 schema 决策 |
| 业务抱怨「RAG 答不了汇总与多跳问题」 | 先在问题集上标注多跳与汇总问题占比，再决定建不建图 | 观察建图后多跳问题的命中增量、以及索引与更新的成本曲线 | 不要在语料每天大幅变更时建图；不要为 10–20% 的问题把全部语料做成图 |
| 图规模已经很大、答案倒查不到依据 | 先做「答案 → 边 → 原文」的可点回链路 | 观察可溯源率，以及被点回的边里无法回原文支持的比例 | 不要把「有路径」当成「已解释」——路径不证明边的真假 |
| 想接 Agent 做图谱问答 | 只开只读：身份 + 权限域 + 每条结论带依据 | 观察越权与「答案过期」两类问题 | 不要开放写图权限；不要让它改名、合并实体、改本体 |
| 源系统变更频繁、图总是滞后 | 先做漂移检测与告警（有明确规则的那一半） | 观察漏报与误报两类数 | 不要让 Agent 自动执行类型变更或实体合并 |
| 图规模已经很大、单机扛不住 | 先做热图与冷图分层、按场景裁剪（§6 案例 6.3 的教训） | 观察尾延迟与冷查询占比 | 不要在存储分层没做之前先接 LLM 抽取——抽取会让边数再上一个量级 |
| 正在选图数据库 | 把「能否导出 RDF / 是否有正式图查询语言条目」作为选型项（③ 接口稳定性） | 观察产品文档里这些条目是否为一等能力、是否标注 GA | 不要为「AI 原生知识平台」这个标签支付溢价；不要在图上没有约束时先定模型供应商 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（幻觉边入库、误合并污染全图、越权读取、答案看起来更可信），**而收益依赖一个尚未成立的假设**（抽取已经可信 / 模型能判断合并对错 / 图能覆盖业务问题）。等 §5.6 的信号出现再投入，损失的只是时间。

另外注意顺序：第一行是其余各行的前提。**底座没做完就上 AI 层，会出现「AI 表现得还行、但没人知道它对不对」的状态**——这比明显不可用更危险，因为它会让人停止补本体与约束。判据很简单：**AI 的答案能不能点回一条已登记的边**；点不回去的答案，无论多流畅都只是文本。

最后一条通用习惯：**每当有人提议引入一个「AI 图谱能力」，先问它接在 5.3 表的哪个交接物上**。接不上的，说明它要解决的问题还没被定义清楚——此时该做的是补那份交接物（谁来抽、谁校验、什么时候刷新），而不是先买能力、再回头补流程。本主题的失效几乎都发生在这个顺序被颠倒的时候。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**检索的控制流**——从「在文档集合上打分」换成「在图上游走并按约束剪枝」，于是多跳与全局性问题第一次可以靠一次查询回答。因为这一点，本节级别最高的方向是**图底座**（实体 + 类型化边 + 图查询语言 + 离线图嵌入，见 5.2.1），**而它是 L2、也不是 AI 带来的**：它的公开能力在 LLM 之前就存在（W3C 的三元组与本体规范、图数据库的商业化、离线图嵌入），生产形态见 §6 案例 6.1–6.4；它停在 L2 只因为缺一条证据（非厂商的第三方公开生产案例，见 5.4），不是因为能力或接口。AI 只是把它从「关联密集型业务的选型」变成「检索管线的必需候选族」。它**没有**改变的是两件事：一是**模型只能沿着已建好的边走**——图上没有建模的关系，模型给出的是措辞流畅但没有依据的答案；二是**可解释不等于正确**——一条路径能回答「用了哪条边」，回答不了「这条边是不是真的」，而一条错误的边会让错误答案看起来更可信。
>
> 判断本主题任何新提法的快捷方式：**它改变的是「候选从哪来」（控制流），还是「图上的边可不可信」（质量）？** 改控制流的，先量多跳占比与语料稳定度再决定；改质量的（约束、出处、版本、抽检），直接做——它衔接图底座（5.2.1：本节唯一把 ① 与 ③ 都写明为满足、只缺②的一行），也是其余所有方向的前置条件。
>
> 还有一个判断同样好用：**这个能力的第一天和第三十天，成本曲线长什么样？** 向量索引与图底座的成本随数据量增长、可以容量规划；抽取与社区摘要的成本随**语料变更频率与模型版本**增长，不可直接外推。前者可以排预算，后者只能先试点再量。
>
> 💡 **思考锚点**：本节说抽取与社区摘要的成本随**语料变更频率 × 模型版本**增长、不能按数据量外推（向量索引与图底座才可容量规划）。代进你自己的两个频率：语料多久批量变一次、embedding/抽取模型多久换一版？这个乘积决定抽取层一年要重跑几次全量——在你的场景里，它是能写进季度预算的固定项，还是只能先试点再量？
