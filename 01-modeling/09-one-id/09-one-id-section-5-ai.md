## 5. 前沿演进（AI 时代）

> 原 § 5 共 188 行、为方向清单（4 条 LLM / Agent 方向 + 3 组 RAG / 图谱结合 + 7 条学术条目 + 7 条工业条目 + 4 条开源项目 + 8 条趋势），其列出的条目在本节 5.1 表与「原条目去向对照」一段里逐条保留并重新归类，重写为约 280 行的机制与成熟度评估。

### 5.1 先分清三类「前沿」

主文件把 OneID 定义为**实体解析（Entity Resolution）的工程化产物**（主文件 §1.1）：这件事由两步组成——先由规则 / 概率 / 图决定「哪两条记录是同一个人」（成对判定），再由连通分量把判定闭包成一个全局编号（主文件 §2.2.1 的似然比、§2.2.2 的连通分量）。本章的既有卡点不在判定算法本身，而在四条被反复验证过的性质上（[§ 7](09-one-id-section-7-sec7.md) §7.3）：**错误的方向不对称**——误合并不可逆、漏合并可补（§7.3.3）；**召回上限在分块阶段就被封死**，换更强的模型对召回无效（§7.3.2）；**传递性同时放大覆盖率与错误**，一条错边会跨簇传染且无法局部回滚（§7.3.1）；**成本的主导项会随规模换两次**，十万级以下主导项是人力、亿级以上是重算与服务化（§7.4）。

所以本节要判的不是「AI 能不能接进 OneID」——它当然能接，接口就是一个「记录对 → 判定」的函数——而是 **AI 改变的到底是这四件事里的哪一件**。答案是：它只动了其中一件事的一半——**判定这一步的边际成本从「人的注意力」换成了「算力 + 抽检」**（[§ 3](09-one-id-section-3-sec3.md) §3.2.5 的三档分流）。其余三件一件没变：误合并仍然不可逆，分块仍然封死召回上限，重算成本仍然随图规模增长。

本节用 L1 / L2 / L3 三级区分，判据必须可核验，而不是「感觉成熟」：

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口 / 生态未稳，或**仅有厂商与建设方自有案例**，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

**本节不对 L1 判据做任何修正，也不缩小它的适用范围。** 本主题最容易放宽的是第②条：OneID 领域有一批公开的工程文章、云厂商的实体解析服务、开源的 ER 库，很容易把「有公开的机制性材料」读成「有第三方生产案例」。但**厂商与建设方的自述按判据读就是 L2 的定义**——[§ 6](09-one-id-section-6-sec6.md) 的阿里 / 字节 / 美团 / Meta 四个案例，出处是「机构名 + 年份区间」，属建设方自述。另有一条纪律：**已经在生产里跑了很多年的既有能力**（强匹配、图闭包、批流双轨、服务化）**不是 AI 方向**，本节只在对照时提及，不为它们单独立项评级。唯一的例外是被原清单当成方向或工具列出的两条——表里第 9 行的实时 OneID（形态即批流双轨）与并入第 11 行的托管实体解析服务——它们留在表里、按同一套判据评级，并在表里各自注明了它不是 AI 方向：第 9 行的判据栏写的是「它不是 AI 能力」，托管服务那一条的机制栏（§5.2.4 表内）写的是「改变的是谁运维与数据在哪里，不是判定机制」。读它们的级别时按「值不值得现在做」理解，不要读成「它是不是 AI」。

还有四件容易混的事，先在这里分开：

- **产品名 vs 能力名**：「LLM 边界复核」「实体解析服务」是**能力名**，不是某个产品的专属功能；同一能力在不同材料里挂在不同的产品名下（[§ 4](09-one-id-section-4-sec4.md) 的 §4.3.3 与 §4.3.5 把它分别列在「云厂商实体解析服务」与「LLM 增强工具」两栏）。判定方法：按**产品全名 + 该能力的输入与输出**核对，而不是按能力名归类。
- **论文原型 vs 产品实现**：论文演示的是**方法可行性**，产品实现要受分块、阈值标定与图闭包三处工程约束（§3.1 的约束表）。判定方法：看该实现有没有把「分块后的候选对数量」与「复核队列长度」显式暴露出来。
- **已发布版本 vs 路线图**：本节不给任何产品条目断言时点与版本；判定入口是**各家产品的发布说明与官方文档当前版本**，而不是介绍性文章里的年份。
- **同一主体内的打通 vs 跨主体的打通**：同企业内的合并与跨企业（PSI / 联邦 / TEE）的合并是两套约束（§3.2.7、§7.3.4），不能拿前者的能力推算后者——后者改变的是**可做的合并集合**。

这四件事的共同点：**它们都是「判定方法」问题，不是「能力有无」问题**。凡是你无法在自己组织内复算出判定标准的宣称（送检比例、重复送检的一致率、空交集的原因），就先把它改成「我用哪一步能验它」，再去比对各家的材料——**能被复核的宣称才有资格进方案**。

本节对每个方向都问同一句：**AI 改变了哪个机制**——改变了成本函数、改变了接口边界、把人工判断换成了统计判断，还是只换了个前端？本主题的答案集中在**两条**：**第一条**是判定环节的边际成本从人的注意力挪到算力（§3.2.5），它改变的是**中间区间可以有多宽**；**第二条**是 OneID 多了一类消费方（检索、模型样本、Agent 记忆），它改变的是**谁在按 OneID 取数**，不改变 OneID 是怎么算出来的。**没有一条改变了判定的性质**。

**这三级的排法直接决定路线图的顺序**：

- **先做的三件事不在表里**，因为它们是 AI 之前的既有能力，却又是每个方向的评估前提：把合并留痕与图版本做出来（§3.5 反模式 4 的修法）→ 把分量规模分布做成常规指标（§7.3.1、§3.7 第 3 条）→ 把「不报错的那类失效」做成可观测项（§3.5）。没有这三件事，模型判得准不准、Agent 告警有没有用，都无从判定。
- **L2 做 PoC，并先测两个数**：送检比例（成本的分母）与假合并率（质量的分母）。这两个数拿不出来，L2 就停在原地，与选哪家产品无关。
- **L3 不排进排期**：写路径、GraphRAG、多模态、区块链都属于「等信号」，它们的共同前提是**读路径与写路径的门槛必须先分开定**。
- **回填机制**：每次 OneID 复盘时回填一次级别；某个 L2 若一年内仍拿不到你自己组织里的实测量（送检比例、假合并率、拆链次数），降 L3 并停止投入。

**原条目去向对照**：原 §5.3.1 的七条学术条目给的是「主题名 + 会议 + 年份」的简写、没有可检索的标题与作者，本节保留它们所指的四个方向（零样本判定 / 深度匹配 / 联邦 ER / 跨模态），判定入口见 §5.4。原 §5.3.2 的七条工业条目按能力落点归位：阿里「全域智能 OneID」、字节「OneID 4.0 引入 LLM 边界复核」、腾讯「LLM 地址匹配」→ 第 1 行；Salesforce Data Cloud Zero-Copy ID Resolution、AWS Entity Resolution、Snowflake 与 Databricks 互通的 ID 解析 → 第 11 行（托管与跨平台形态，[§ 7](09-one-id-section-7-sec7.md) 的 §7.2 候选方案全景表与 §7.3.4 已把「托管实体解析服务」单列），其中具体能力与版本以各家发布说明为准；美团「OneID 白皮书」是建设方自述材料，原清单没有给出可检索的标题与年份，本节不为它指认具体行（它的位置与 [§ 6](09-one-id-section-6-sec6.md) 的美团案例同类）。原 §5.3.3 的四条开源项目全部落第 12 行。原 §5.4 的八条趋势落在第 2、11、8、9、10、4 与 5、11、13 行（第 6 条「AI 原生 OneID 平台」的监控半落第 4 行、执行半落第 5 行），一条不丢。原 §5.1.1–5.1.4 落第 2、1、3、4 行（原 5.1.4 的四步全是读路径动作——写路径那半来自原趋势 6），原 §5.2.1–5.2.3 落第 6、8、7 行。

### 5.2 演进方向逐条拆解（核心节）

下面把方向分成四组：**前三组按同一套结构逐条写**（旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度），**第四组用一张表覆盖同一套要素**，因为那一族的共同点恰恰是「机制没变」。四组共用 §5.1 的两条机制（判定成本、消费方），差别在**它落在哪一层**。

| 方向 | AI 改变了什么机制 | 这条变化落在哪一层 |
| --- | --- | --- |
| §5.2.1 LLM 边界复核 | 判定的边际成本从人的注意力挪到算力 + 抽检 | **成本函数**（中间区间第一次可以放宽） |
| §5.2.2 LLM 生成合并理由 | 「分数 → 解释」这一步由人写换成模型生成 | **说明层的接口边界**（面向非技术角色的交付物） |
| §5.2.3 Agent 治理回环 | 状态检查的触发从人的排期换成调度 | **执行边界**（本主题里唯一可能写到 OneID 图的方向） |
| §5.2.4 机制没变的那一族 | 大多没有改变机制 | **消费侧与既有能力的延伸**（换入口 / 换落点 / 与 AI 无因果关系） |

读法建议：时间只够读一节就读 §5.2.1——它是本主题里唯一**已经在生产里发生**的变化（[§ 6](09-one-id-section-6-sec6.md) 把 LLM 复核列在「生产」阶段，依据同此），而它带来的问题（成本随阈值带宽线性放大、判定不可复现）不需要任何新产品就能验证。§5.2.2 与 §5.2.3 的收益要等你把合并留痕做出来之后才兑现。

只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次「判定更容易了」，都对应一处新的判断成本：**模型复核过的对要人去抽检，模型写出的理由要人去分辨，Agent 提出的异常要人去裁决**。这也是 §5.2.3 的级别低于 §5.2.1 与 §5.2.2 的原因：不是它的技术更难，而是它的错误落在写路径上。

三节的顺序同时给出了实施的顺序：**先把复核的成本算清楚（§5.2.1），再把合并结论变成可解释、可校验的产物（§5.2.2），最后才考虑让回环自动跑（§5.2.3）**。反过来做——先让 Agent 每天告警、再补留痕——得到的是一个天天喊异常、却一次都退不回去的系统，而它在两周内就会被忽略。

#### 5.2.1 LLM 边界复核（原 5.1.2；原 5.1.1 的低频高价值用法）

- **旧做法与它的卡点**：三档分流把候选对按分数切成三份——高于上阈值的自动合并、低于下阈值的自动排除、中间区间的进复核队列（§3.2.5 的结构）。卡点在第三档：**复核成本 = 对数 × 人的注意力**，而人的注意力不随数据规模摊薄。于是团队只有两条退路——把队列清空（放宽阈值、用误合并换吞吐，§3.5 反模式 2 的成因），或者把阈值带收窄（用漏合并换可控的队列），两条路都要拿精度或覆盖率去垫。这就是 §3.2.5 的失效点所描述的那件事：**带宽一变，队列与账单同时变**。
- **AI 改变了什么机制**：**判定的边际成本从人的注意力换成算力 + 抽检**——成本函数的形状变了，而且判定能调用属性之间的常识关联（称呼、缩写、行政区划沿革），这类证据无法被字段级相似度特征表达，也无法被预先枚举成规则（§3.2.5 的有效性论证）。
- **由此得到的**：**因为判定成本不再由「这对有多难」决定，所以中间区间第一次可以从「尽量窄」放宽到「尽量宽」**——过去为了省人力而收窄阈值带、用误合并换吞吐的那笔交易，现在可以用账单去换。这是本主题在 AI 前后唯一一处真正被放松的约束，也是 §7.4 里「覆盖率 85%–95% 区间投入产出最陡」这条经验判据在 AI 之后可能被上推的原因。

```text
       同一条边界样本，在两条路径上的处理不同（这是本方向的全部收益）
       ────────────────────────────────────────────────
       旧路径（人复核）
          中间区间的对送进队列 → 人力预算固定 → 队列涨到上限后
          只有两条退路：清空队列（放宽阈值，误合并上升）
          或收窄阈值带（漏合并上升）        ← 拿精度或覆盖率去垫
       ────────────────────────────────────────────────
       新路径（模型复核 + 人工抽检）
          阈值带可以放宽 → 送进模型的对按同一比例增加
          → 成本按对数线性上升，而与「这一对有多难」无关
       ────────────────────────────────────────────────
       结论：放宽阈值带是这次机制变化的全部收益，
             而它与账单共用同一个旋钮
       判定方法：把送检比例乘以单对成本，做成一个日更的数
```

- **由此付出的**：**其一，成本随阈值带宽线性膨胀**——带宽翻倍，账单与队列同时翻倍，而每对都是一次完整调用（§3.2.5 的失效点）。**其二，判定不可复现**：同一个记录对在不同调用下可能给出不同结论，而合并是要落库的状态——「重跑一遍」会得到另一个 OneID。**其三，它产出的是一类「读起来像证据的理由」**，而可解释性在审计场景里要的是可复算的推导路径（哪条边、哪条规则、什么置信度）。
- **证据与来源**：【公开：本书 §3.2.5 给出三档分流的结构、有效性论证与失效点，均可逐行核对】【推算：§7.4 给出「LLM 只能作用于边界集合」的推导——日候选对 5×10⁷、边界样本占 5% 即 2.5×10⁶ 对、按每对约 10³ token 计约 2.5×10⁹ token/日；全量送检则 5×10¹⁰ token/日，相差 20 倍；推导链见 §7.4，本节不重复】。产品侧的代表见 [§ 4](09-one-id-section-4-sec4.md) 的 §4.3.3 与 §4.3.5，其具体能力与版本以各家官方文档当前版本为准。**【本节未能核到】第三方（非厂商）公开生产案例**——即「某非厂商组织公开过它的送检比例与假合并率」这类带口径的材料。
- **成熟度**：**L2**。判据：① 核不到（形态在书内可核验，产品侧只有厂商材料）；**②核不到**；③ 送检比例、输出 schema 与阈值带各家不同 → 可做 PoC，不要做核心依赖。
- **判定方法**：取一个月的历史边界样本，一半走人工、一半走模型，比三件事——判对率、单对成本、以及**同一样本重复送检两次的结论一致率**。第三个数低到某个程度，这套判定就不能直接落库。
- **什么时候值得做**：中间区间的队列已经长到「要么清空、要么积压」，且合并留痕与图版本已经就位（否则复核产生的每一次改动都无法回滚，§3.5 反模式 4）。
- **什么时候不值得做**：候选对还没被分块压下来的时候——**先解决数量，再解决难度**，否则你是在用最贵的手段处理本该被分块排除掉的对（§7.3.2）。

#### 5.2.2 LLM 生成合并理由（原 5.1.3）

- **旧做法与它的卡点**：合并留痕能记下「哪条边、哪条规则、什么置信度」（§3.5 反模式 4 的修法、§3.7 第 5 条把这两列列为必查项），但记不下「为什么这几个字段指向同一个人」。当判定来自模型给出的分数时，非技术角色读到的只有一个数——于是客服、合规与审计场景的提问「你们凭什么把我家和隔壁老王合并」在结构上没有答案。
- **AI 改变了什么机制**：**把「分数 → 自然语言解释」这一步从人写换成模型生成**。这一变化的定位很关键：理由成为**判定记录的一个渲染产物**，与 [08 OneData §3](../08-one-data/08-one-data-section-3-sec3.md) §3.2.6 里「口径文档是指标定义表的渲染产物」同构——它不产生新的事实，只换了一种呈现。
- **由此得到的**：**因为解释可以被生成，所以合并决策第一次可以面向非技术角色交付**——把「解释一条合并」从需要工程师查图，变成客服与合规可以自查。这是收益里最实在的一条：它不提高判定质量，它降低的是解释的排队时间。
- **由此付出的**：**其一，理由不是证据**——它由模型生成，与边上的规则、权重之间没有强制一致关系；两者冲突时，读者会信更可读的那一个（理由是自然语言，分数不是）。**其二，理由会被误当成权威**：它躺在库里、格式规整、语气确定，而它恰恰是本主题里「最容易被默认接受、最难被验证」的一类生成物（与 [08 OneData §3](../08-one-data/08-one-data-section-3-sec3.md) §3.2.6 对生成式元数据的判断同构）。**其三，生成物必须与权威分开存放**，否则「按理由回滚」会成为一条走不通的路径——回滚要按边，不按文本。
- **证据与来源**：【公开：本书 §3.2.5 把 `reason` 列为三档分流的副产品、§3.7 第 5 条把「合并原因与置信度」列为必查项、§3.5 反模式 4 给出「合并留痕 + 图版本 + 撤回链路」，均可逐行核对】。**【本节未能核到】**可点名材料给出「理由与边的一致率」这类口径；也未能核到第三方（非厂商）公开生产案例。
- **成熟度**：**L2**。判据：① 核不到（`reason` 是书内定义的形态，不是某个产品的发布物）；**②核不到**；③ 理由与边的对应关系没有校验约定 → 可以做 PoC，前提是它与边分开存。
- **判定方法**：抽 50 条已生成理由的合并，逐条核对理由里提到的字段是否真的出现在边上、置信度是否与边一致；再用同一对记录换一次措辞重跑，看理由是否稳定。**对不上的比例就是这条链路的实际错误率。**
- **什么时候值得做**：合并结论已经会对外解释（客服、合规、监管问询），且合并留痕已存在时。
- **什么时候不值得做**：留痕还没有的时候——此时生成的理由没有可对照的权威，它只是给一个没有依据的判定配了一段读起来合理的话。

#### 5.2.3 Agent 治理回环（原 5.1.4 的四步；原趋势 6 的「自动异常检测」与「自动调阈值」）

- **旧做法与它的卡点**：§3.7 的 12 条自检里，最常被跳过的是第 3 条（分量规模分布）与第 6 条（可回滚快照）——因为它们问的不是算法，而是**运行状态**，而要「定期看状态」就得有人记得看。更根本的卡点是：**失效的方式恰好是不报错的那一类**（巨型分量、死链累积、拆链次数上升），它们只在指标的缓慢漂移里可见（§3.5 的两个最危险反模式）。
- **AI 改变了什么机制**：**状态检查的触发从人的排期换成调度器的节奏**——把「发现异常 → 采样 → 判定 → 告警」串成按固定频率执行的回环，判定环节由 5.2.1 的边界复核承担。机制上它改变的是**治理动作的发生频率**，不是判定的质量。
- **由此得到的**：**因为检查不再依赖「有人记得看」，所以那些只在指标上缓慢漂的失效第一次有了常规的发现路径**。这一条与 [08 OneData §3](../08-one-data/08-one-data-section-3-sec3.md) §3.2.7 模式 G 里「治理团队有限、资产变化持续」是同一个约束的两个面：**把检查频率补齐，比把算法换掉便宜得多**。
- **由此付出的**：**其一，告警疲劳**——每天提出上百条疑似异常而误报率高，Owner 会在两周内学会全部忽略，此时系统在运行、治理没有发生（[08 OneData §3](../08-one-data/08-one-data-section-3-sec3.md) §3.2.7 给出的同一代价）。**其二，边界必须划在读路径上**：回环一旦越过「提案」进入「执行」（自动合并、自动拆分、自动调阈值），它动的就是写路径，而误合并不可逆（§7.3.3），拆链还要重算全部派生资产。**其三，抽检样本不再随机**——如果人工复核的样本由模型的怀疑决定，那么「抽检」就变成了「按模型的口味抽检」，这会系统性地掩盖模型不敏感的那一类错误。
- **证据与来源**：【公开：本书 §3.7 的 12 条自检清单给出可被自动化的检查项（第 3、6、9、10 条等），§3.5 反模式 4 给出「合并留痕 + 图版本 + 撤回链路」这一最小前提，[08 OneData §3](../08-one-data/08-one-data-section-3-sec3.md) §3.2.7 给出提案式治理的结构与代价，均可逐行核对】。**【本节未能核到】**可点名材料描述「Agent 自主执行合并 / 拆分 / 调阈值」在生产中运行；原 5.1.4 的示例代码里 `AlertTeam()` 之后的动作由人执行，本节判 L3 的正是它之后的那些动作。
- **成熟度**：**读到告警这一侧是 L2**（判断：① 核不到，形态在书内可核验；**②核不到**；③ 告警口径与精度指标无通行做法）；**写到图上那一侧是 L3**（① 无正式条目；③ 回滚语义无约定；② 不适用——「合并对不对」的判据要求边可信，而边是否可信本身要先能回答）。
- **判定方法**：问它两个问题——「这次告警的依据是哪条边、哪个指标」和「如果它自动改了一条边，怎么退回去」。**第二个问题答不出来，写路径就不能开**；它们不是实施细节，是权限本身。
- **什么时候值得做**：§3.7 的检查项里已经有三条以上被做成了常规指标，且分量规模分布已经在看板上时。
- **什么时候不值得做**：连「最大连通分量占比」都没有度量的时候——此时 Agent 只能对着一个没有基线的系统喊异常。

#### 5.2.4 被写进「AI 时代」但机制没变的那一族（原 5.2.1–5.2.3；原趋势 2–5、7、8）

这一族有八个方向，它们的共同点是：**收益真实存在，但没有一条的收益来自判定能力的提升**。它们要么只是换了消费入口（RAG、GraphRAG），要么只是换了落点（向量聚合、实时双轨），要么与 AI 没有因果关系（隐私计算与跨主体、托管服务、区块链）；只有多模态是新增了一类证据来源（判定逻辑不变）。把它们一起写成「AI 时代的 OneID 演进」，会让真正要做的三件事——**合并留痕与图版本、分量规模指标、读路径与写路径的门槛分开定**——一件都排不进排期。

| 托管实体解析服务 | 自建分块、匹配、复核工作台，运维成本要自己扛 | **改变的是「谁运维」与「数据在哪里」，不是判定机制**（§7.3.4） | 成本可预测、可外购，团队可以把人力挪到治理而不是算法 | 分块与阈值由服务方决定，客户能调的只有字段映射与匹配范围；成本可预测但**几乎不可优化**，且图谱进了黑盒 | ① 判定入口是各厂商的发布说明与产品文档；**②核不到**；③ 各家接口与阈值口径不同 → **L2** |
| 区块链辅助合并审计（原趋势 8） | 合并记录可能被改，审计时无法证明「当时的记录就是这样」 | **与 AI 无因果关系，且机制错位**：OneID 的失效模式是**错合并**，不是**记录被篡改**（§7.3.3） | 合并决策的记录具备不可否认性 | 不可篡改只保证「这条记录没被人改过」，不回答「这条合并凭什么成立」；它还给系统加了一条新的写路径与其运维面 | ① 无正式条目；② 不适用；③ 链上数据结构无约定 → **L3** |

**读这张表的方式是看「AI 改变了什么机制」这一列**：八行里没有一行是判定机制的延伸，只有「用户向量的聚合」与「多模态」是真正把新的一类数据接进同一套流程，其余六行要么只换入口或落点、要么与 AI 无因果关系。**这解释了为什么它们都停在 L2 / L3**——判据②核不到只是表层，深层原因是**它们的好处不来自模型能力，所以也不会因为模型变强而变得可核验**。

顺带说清一件常被省略的事：这八行里的**实时双轨、隐私计算、托管服务**不是「以后要做」，而是「现在就该做」——它们与 AI 无关，却是 §5.1 表里所有 L2 方向变得可评估的前提（例如没有双轨的「即时视图 / 已校准快照」语义，就无法回答 5.2.1 的复核结论落到了哪一版图上）。把这**三件事**与 AI 方向放在同一张排期表里竞逐资源，是本主题最常见的一次排序错误。

这一族还有一个共同点值得单独指出：**它们的价值全部要在「主体键可信」之后才兑现**。RAG 按主体键取回上下文、向量按主体键聚合、记忆按主体键落库——三件事的正确性都等于 OneID 本身的正确性，而它们**都不会报错**。因此这一族的方向不是「接不接」，而是「先接哪一个」：托管服务与实时双轨可以并行推进（它们改的是运维形态），检索与记忆类入口则应排在合并留痕与分量指标之后（它们改的是错误的影响面）。

### 5.3 与本主题既有栈的接口在哪

OneID 与 AI 之间不是「结合」关系，而是**交接物**关系：谁把什么交给谁、数据以什么形态穿过边界、失败时谁负责。下表「现状」一列用同一套 L1 / L2 / L3 判据，但评的是**这个接口本身**，不是 §5.1 表里的演进方向——两者不要互相引用，否则同一个 L2 会在两处指两件事。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| OneID ↔ LLM 复核服务（§3.2.5） | 交接物 = 边界样本对 + 结构化输出（decision / confidence / reason） | **OneID 侧**；输出未用 schema 约束时下游无法消费，而「同一对两次结论不同」在流水线里不会被发现 | L2（送检口径与一致性要求无通行做法） |
| OneID ↔ 图计算 / 图存储（§3.2.2、§7.3.1） | 交接物 = 边集合（含阈值与来源）+ 图版本 | **OneID 侧**；一条过松的边进图后由闭包放大，错误无法局部回滚 | L2（① 核不到：图与并查集是既有做法；**②核不到**；③ 图版本与边来源无标准） |
| OneID ↔ 特征平台与模型服务（[../../02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md)） | 交接物 = 样本与特征的主体键（去重键） | **OneID 侧**；错误合并表现为离线评估与线上 AUC 的系统性偏差，不报错 | L2（口径与去重位置各家不同） |
| OneID ↔ RAG / 向量库（[../../04-data-assetization/05](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md)） | 交接物 = 主体键 + 权限过滤条件 | **OneID 侧**；过滤条件命中的主体错时，检索会把两个人的记忆一起交给模型，且不报错 | L2（权限过滤与主体标识的对齐无共识） |
| OneID ↔ Agent 长期记忆（[../../07-agent-evolution/01](../../07-agent-evolution/01-long-term-memory/01-long-term-memory.md)） | 交接物 = 记忆挂载的主体（谁的经验） | **OneID 侧**；记忆一旦按错误主体写入即被固化，后续推理都在错的主体上累积 | L3（写入即固化，而撤回链路要求下游清单先存在） |
| OneID ↔ 客服与合规解释（原 5.1.3） | 交接物 = 合并理由与依据（边 + 规则 + 置信度） | **OneID 侧**；理由由模型生成而未被校验时，它会成为一份「读起来像证据」的材料 | L2（理由与边的对应关系无校验约定） |
| OneID ↔ 审计与撤回（[../../11-cross-cutting/07](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)） | 交接物 = 合并留痕 + 图版本 + 撤回链路（§3.5 反模式 4 的修法） | **OneID 侧**；撤回要能触发下游重算，而下游清单若不先存在，撤回就只是删了一行 | L3（① 核不到：形态是书内定义；**②核不到**；③ 撤回的下游范围无通行做法） |
| OneID ↔ 跨主体合作方（§3.2.7） | 交接物 = 加密集合或交集结果（PSI）；协议前必须先对齐 ID 规范化与加盐方案 | **双方共同**；表示不一致 → 空交集，且密文下与「确实无交集」不可区分 | L2（跨主体规范化与对齐无标准） |
| OneID ↔ 湖仓实时链路（[../../03-data-stack/10](../../03-data-stack/10-stream-batch-unified/10-stream-batch-unified.md)） | 交接物 = 增量边 + 校准快照的版本号 | **OneID 侧**；不声明「读到的是即时视图还是已校准快照」，下游无法判断结果可信度（§3.7 第 12 条） | L2（双轨同步无通行做法） |

一句话概括：**AI 没有给 OneID 新增任何一条判定，它新增的是「判定的成本函数换了一种形状」与「多了一类按 OneID 取数的消费方」**。

**「谁负责失败」这一列不是修辞，它决定了排查路径。** 表中除跨主体合作方一行外，失败责任全部落在 OneID 侧：不是因为这些结合点不重要，而是因为下游的每一个消费方都**默认主体键是对的**——特征平台不会去校验样本主键是否重合，向量库不会去校验过滤条件命中的是不是同一个人，Agent 记忆不会去校验记忆挂载的主体是否一致。所以这些接口的正确性无法由下游兜底，只能靠 OneID 侧的两样东西：**边的来源与图版本**。这也解释了为什么 §5.1 表里所有 L2 方向都要求先做那三件事。

表的读法是**从下往上看**：后三行（合并留痕与撤回、跨主体对齐、快照语义）是前六行的共同前提——没有它们，「即时视图还是已校准快照」说不清、「跨主体能不能打通」评不了、复核产生的结论落到哪一版图上也无从追溯。第二至第六行的失败责任全部在 OneID 侧，且失败形态一致：**不报错，只在下游以偏差的形式出现**。第一行（LLM 复核）是唯一引入新成本与新不确定性的一行，也是唯一必须先算账再上线的一行。由此得到三条约定。

**第一条约定：判定必须可复现，否则必须一次性固化。**（合并是要落库的状态，不可复现的判定不能反复重跑；§3.7 第 5、6 条要求每条边留合并原因与置信度、并保留可回滚的上一版快照。）这条约定今天是可选的，一年后会变成必需的——因为图上会出现模型判定过的边，而系统必须知道自己在信什么。

**第二条约定：读路径与写路径的门槛分开定。** 同一条边，用来提醒人时够用，用来改 OneID 图时不够——读路径上一条错边只是让人多看一眼，写路径上它会让两个人被永久合并，并触发全部下游派生资产重算（§7.3.3）。

**第三条约定：先把「不报错的那类失效」做成指标，再谈自动化。** 分量规模分布（§7.3.1）、拆链次数、死链占比、置信度与边的一致率——这四个数里有三个是可以直接从图里统计出来的。**它们比任何厂商案例更能决定该不该上模型。**

```text
   AI 新增的两样东西，落在不同的边界上，谁也不能替谁兜底
   ────────────────────────────────────────────────
   新判定手段（LLM 复核） ──► 落在「成本函数与可复现性」这条边界上
       必须回答：这一对凭什么合并？重跑一遍结论一样吗？
   新消费入口（RAG / 记忆 / 图） ──► 落在「主体标识与权限」这条边界上
       必须回答：它凭什么不把一次错合并放大给更多下游？
   ────────────────────────────────────────────────
   两者都没有改变：合并仍是连通分量级的决策（§7.3.1），
                   误合并仍不可逆（§7.3.3），
                   召回上限仍在分块阶段封死（§7.3.2）
   判定方法：任意一条合并结论，先问它依据哪条边，再问这条边
             能不能被单独撤销——两问都答不出，这条结论就只能当推断
```

**第三方生产案例**

- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——把送检比例与单对成本、假合并率、拆链次数、分量规模分布这四组数算出来并留存口径。前三组在 §3.7 的自检清单与 §7.4 的成本函数里各有对应提问；**分量规模分布没有现成的检查项**，要按 §7.3.1 的描述自己从图里统计。这几组数在 OneID 评审里的分量超过任何厂商案例。
- 三类证据里**最容易造假的是「准确率」**：只报一个准确率而不说样本怎么抽、边界样本占比多少、是否含无人能判的对，无法复核。**判定方法**：只接受同时给出「样本来源 / 边界样本占比 / 人工与模型的分歧率」三者的准确率。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **LLM 边界复核**：取一个月的历史边界样本，一半走人工、一半走模型，比判对率、单对成本与重复送检的一致性。
2. **LLM 生成理由**：抽 50 条已生成的合并理由，逐条核对它提到的字段是否出现在边上。
3. **Agent 治理**：问它「这次告警依据哪条边」与「它改过的那条边怎么退回去」——两问都答不出就不具备写路径的资格。
4. **RAG / 记忆类入口**：试一次「问一个确定不存在的主体」与「问一个主体键确实缺采的实体」，看两者是否被答成同一句。
5. **GraphRAG**：拿一个跨实体问题分别用图查询与模型答一次，看答案能不能指回一条具体的边。
6. **跨主体打通**：问一次双方的 ID 规范化与加盐方案是否书面确认过——没有这份确认，协议性能的对比没有意义。

**怎么用这份清单**：要核「能力存不存在」看官方文档与发布说明（最快）；要核「这条合并可不可信」看它的边、来源与图版本（最慢但最稳）；要核「在我这里值不值得做」看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。三类证据之外还有一种最没用、却最常见的形式：把「某平台支持 LLM 实体解析」写进方案而不写判定入口——它既不能被复核，也不能被证伪。

### 5.5 被过度宣传的部分

**「用 LLM 替掉 ID-Mapping 流水线」**——实际是：它替换的是流水线里**最便宜**的那一段（打分），而成本落在**最贵**的那一段（候选对数量）。**为什么会这样**：候选对数量由分块与数据规模决定——§7.3.2 的推算给出，日增 100 万条时不分块约 5×10¹¹ 对、按「城市 + 号段前缀」分块后约 5×10⁷ 对，相差四个数量级；而 LLM 的账单随「送进模型的样本数」线性增长（§7.4 的成本函数 g 项）。**它什么时候才会成真**：当分块把候选集压到与预算同量级时——那时它也仍然只覆盖中间那一档（§3.2.5）。**判定方法**：算一遍「候选对数量 × 单对成本」，再和你的分块后的对数比。

**「OneID 挂进 GraphRAG 就能跨实体推理」**——实际是：OneID 给的是**同一性**（哪个 ID 是同一个人，主文件 §1.1），图给的是**关系**（谁和谁有关系，主文件 §2.4 已把两者分开）；把主键挂到图上不会让「是不是同一个人」变准，也不会让「谁和谁有关系」自动出现。**为什么会这样**：两者的判定单位不同——连通分量是一次性闭包（§7.3.1），边是逐条的、各自有来源的；用图算法替代阈值判定，等于把边的可信度问题藏进了可达性里。**它什么时候才会成真**：当图上的每条边都带来源与生效期，且跨实体问题的答案必须能指回一条具体的边时。**判定方法**：拿一个跨实体问题（「哪些客户与竞争对手 X 有合作」）分别用图查询与模型各答一次，对不上就以图查询为准——**在 OneID 里，「查不到」比「查错了」安全**。

**「区块链让 OneID 合并可审计」**——实际是：OneID 的失效模式是**错合并**，不是**记录被篡改**；不可篡改保证的是「这条合并记录没被人改过」，而审计要问的是「这条合并凭什么成立」。**为什么会这样**：§7.3.3 已经说明误合并的代价随下游资产数量与时间放大，且在业务指标上才暴露——问题出在边的可信度，不出在记录的完整性。**它什么时候才会成真**：当监管明确要求「合并决策记录须不可否认」，且组织已经能回答「这条合并依据哪条边」时——顺序不能反。**判定方法**：问一句「这条合并如果本来就是错的，链能帮我发现吗」。

这三条的共性：**它们都把「成本更低」或「记录更完整」当成了「判定更可信」**——LLM 让判定更便宜、图让关联更易得、链让记录更不可否认；而 OneID 的稀缺资源从来不是算力、不是关联、也不是记录，**是「这条边可不可信」这个判断**。

### 5.6 未来 3–5 年：可证伪的预测

这一节写了**五条**，比常规的三到四条多一条，理由是 §5.2 里三处最需要外部信号的位置各要至少一条可证伪的线：判定手段（第 1 条）对应 §5.2.1、说明产物（第 2 条）对应 §5.2.2、写路径（第 3 条）对应 §5.2.3；此外 §5.2.4 那一族里两条与 AI 无因果关系、却决定前三条能不能被核验的事——跨主体对齐（第 4 条）与回滚单元（第 5 条）——各占一条。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| LLM 判定会停在「中间区间」这一档，不会走进全量判定 | 产品文档里出现「按分数带送检」的配置项与「送检比例」指标 | 出现默认把全部候选对送检的条目，或公开材料只谈效果不谈送检量 |
| 模型生成的合并理由会成为**一次性的说明产物**，不会成为审计依据 | 审计材料要求的是「边 + 规则 + 置信度」，理由只作附注 | 监管或审计材料把自由文本理由列为可采信证据 |
| Agent 会停在「提案」这一档，自动调整阈值不会成为默认能力 | 产品文档把输出定义为提案，并公开误报率一类的精度指标 | 出现默认自动生效的阈值调整条目，且回滚说明写得清楚 |
| 跨主体打通的进展会先落在 **ID 规范化与加盐方案的对齐**上，而不是协议性能 | 公开材料把「双方先对齐规范化与哈希」写成前置步骤（§3.2.7 的前提） | 先出现协议性能的公开对比，而规范化仍各家一套 |
| 「合并的可回滚单元」会从「整图重算」变成「受影响的连通分量」 | 公开材料或产品文档出现增量重算 / 分量级回滚的表述 | 大规模拆链仍然只能靠全量重算，且被写成常规做法 |

写这五条时的共同约定：**信号必须是外部可观察的**（正式功能条目、发布说明、带口径的公开案例），而不是「我觉得会」。**被检验得最快的是第二条**——看一次审计问询的清单里有没有「理由」这一项，一年内就能看到；**最慢的是第四条**，跨主体标准的形成周期通常以年计；最后一条是**本节唯一一条关于「本主题自己的工程约定」的预测**，它的信号落在你自己的图里。

前三条的落点都在产品侧，因此可以用产品文档的版本变化来证伪；后两条的落点在你自己的系统里，证伪它们不需要外部材料——**只需要把分量规模分布和拆链次数做成一张按月的图**。这也是本节反复把「先做三件事」写在行动建议里的原因：L2 与 L3 的差别，最终要靠你自己的数来判。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有 OneID，但没有合并留痕与图版本 | 先做合并留痕 + 图版本 + 撤回链路（§3.5 反模式 4） | 观察一次误合并能不能被单独撤销 | 不要先上 LLM 复核——复核产生的每一次改动都无法回滚 |
| 边界样本队列已经积压 | 先量出送检比例与单对成本，再决定阈值带宽度（§7.4） | 观察同一样本重复送检的结论一致率 | 不要把模型判定直接落库而不留依据 |
| 想让客服与合规自助解释合并 | 把「边 + 规则 + 置信度」做成可查的说明，理由只作附注 | 观察 50 条理由里有多少与边对不上 | 不要用生成的理由代替边——回滚要按边，不按文本 |
| 想上 Agent 治理 | 只做「发现异常 + 告警」，先接入 §3.7 第 3、6 条 | 观察告警的误报率是否被你自己的数据量出来 | 不要让 Agent 直接写 OneID 图；不要在没有回滚语义时开写权限 |
| 想接 RAG / Agent 长期记忆 | 先统一主体键与权限过滤，再上入口 | 观察「查不到」与「查错了」在接口上是否被分开表达 | 不要让检索层绕过权限；不要让记忆按未校准的主体写入 |
| 想上 GraphRAG | 先用图查询把常见问题做进百毫秒量级【经验】 | 观察图检索与图遍历两条路线的公开对比材料 | 不要用图推理代替阈值判定；不要为它改 OneID 的决策单位 |
| 有人提议跨企业打通 | 先书面确认双方的 ID 规范化与加盐方案（§3.2.7） | 观察先出现协议对比还是先出现规范化标准 | 不要在表示未对齐时上 PSI——算完空交集还不知道是为什么 |
| 有人提议多模态 / 区块链 | 记录，不进排期 | 观察公开案例是否出现在商品 / 内容侧而非人身份侧 | 不要在人员身份判定上用生物特征；不要把链当审计依据 |
| 预算有限，只能做一件事 | 把分量规模分布与拆链次数做成常规指标（§7.3.1、§3.7 第 3 条） | 观察长尾分量是否在变厚、拆链次数是否在上升 | 不要一上来先补 AI 能力——缺口在哪都还不知道 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改图结构、开写权限、扩采集面、引入新的运维面），**而收益依赖一个尚未成立的假设**（边已经可信 / 模型判定可复现 / 下游清单已经存在）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的机制只有**一条**——**判定环节的边际成本从「人的注意力」换成了「算力 + 抽检」**（§3.2.5 的三档分流），它换来的唯一一样东西是**中间区间可以放宽**；顺带还有一条非判定的变化：OneID 多了一类按它取数的消费方（RAG、模型样本、Agent 记忆）。它**没有**改变的是判定的性质：合并仍是连通分量级的决策（§7.3.1），误合并仍不可逆、漏合并仍可补（§7.3.3），召回上限仍在分块阶段封死（§7.3.2），重算成本仍随图规模增长（§7.4）。
>
> 判断本主题下任何新提法的快捷方式：**它是在产生判定，还是在消费判定？** 产生判定的（LLM 复核、自动调阈值）要立刻回答「这条边凭什么可信、重跑一遍结论一样吗」；消费判定的（RAG、记忆、GraphRAG、向量聚合）要立刻回答「它凭什么不把一次错合并放大给更多下游」。第二条判断同样快：**它需要的是同一性还是关系？** 需要同一性的，别交给图算法。
>
> 如果只能带走一句话：**先把合并留痕、分量规模指标、读路径与写路径的门槛这三件事做完，再谈用不用模型**——这三件事做完，本节表里所有 L2 都变得可评估；这三件事没做完，L2 与 L3 的差别只体现在演示视频里。
