### 7.1 先立判据：为什么打分表会误导

评分表最大的问题是把**取决于场景的结论**写成了绝对排序。同一个维度在不同规模、不同数据形态下的权重会整个反转：「性能」在每日全量重算的离线批里是硬约束，在「只对边界样本做二次复核」的流程里几乎不构成约束，因为复核根本不进入线上查询路径。原表在两个维度上给出的排序本身就是相反的——性能一栏规则匹配最高、LLM 最低，长文本一栏规则匹配最低、LLM 最高——但表里没有说明在什么条件下该看哪一栏。读者拿着这样一张表，只能记住「各有优劣」，无法做决定。

更隐蔽的问题是：分数掩盖了**能力边界**。规则匹配在长文本字段上不是「精度低 1 分」，而是**表达不了**——手机号 hash 相等是确定性的，而「杭州市余杭区」与「杭州余杭」是不是同一个地址，规则匹配根本没有可用的算子。这类差异是「能不能」而不是「好不好」，用 1–5 的量表表达，会让人误以为「调一调参数就能追上」。同理，「冷启动友好度」一栏把 LLM 评到最高，却没有说清它高的原因是有没有标注数据都不影响它出结果——而这恰恰是它成本高的同一个原因。

因此本节不用分数，而用一组能落到机制上的判据。判据的作用**不是给候选排序，而是先筛掉在你的约束下不可能成立的候选**——筛完之后，多数场景里真正可选的只剩两三种，比较的重点也随之从「谁更强」变成「哪条代价我付得起」。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 无锚点人群的能力 | 在没有手机号 / 实名 / 登录态的人群上，它还剩下什么能力 | OneID 的价值由**覆盖率**决定，而强标识只覆盖登录且实名的部分人。所有候选在「有锚点」时表现都好，差别全部出在无锚点人群上——判据必须只问这部分 |
| 错误的不对称性 | 误合并与漏合并，哪一个在你的业务里更贵 | 合并是一个会被下游固化的写操作（画像、样本、特征、Agent 记忆都按 OneID 组织），误合并的代价随时间与下游资产数放大；漏合并只表现为覆盖率不足。这决定了阈值该往哪边偏，而方向比数值重要 |
| 机制契合度 | 它的核心机制是否匹配你的数据形态（强标识密度 / 结构化字段 / 长文本 / 仅行为序列） | 分块键、相似度函数、模型输入序列都必须与数据形态匹配。错配不是调参能修的——用编辑距离去匹配地址变体，提高阈值只会同时压低精度与召回 |
| 成本函数的形状 | 成本随什么变量增长（比较对数 / 边界样本数 / 人工复核量） | 两个方案的当期月成本可能相近，但一个随记录数线性增长、一个随候选对数增长、一个随人工量增长。**能承受的增长方式比当期价格更重要** |
| 运维形态与可迁移性 | 线上 P99 与离线重算窗口是否要同时满足；迁走要付什么 | OneID 同时是批任务与在线服务，两者约束方向相反（前者要吞吐与全量一致，后者要低延迟与增量可用）。且迁走的真实代价在「ID 图谱与映射数据」，不在算法 |
| 合规前置性 | 合并这件事本身是否需要同意、能否撤回与拆链 | 跨主体场景下合法性的约束先于精度：一个不可拆链、不能追溯同意来源的方案，即使精度更高也不可用 |

六条里最容易被忽略的是第二条。它在数据结构上很直白：合并是**传递闭包上的写操作**，一次误合并会把两个人的历史行为写进同一条链路，而事后拆分要重算所有按该 OneID 生成的派生资产；漏合并则只是少一条边，补上即可。因此工业界普遍的取舍是「先定精度下限，再谈召回」（本章 §3.5 反模式 2 的修正），而不是先追覆盖率。

这六条判据的权重还会随规模换位【经验：以下分档是量级界线，不是硬门槛】，这一点值得单独说明。用户量很小的时候，「无锚点人群的能力」几乎不构成约束——候选对数量小到可以全部人工复核，精度下限由人保证，此时唯一重要的是「能不能做出来」；到了百万级，人工复核变成瓶颈，成本函数的形状取代精度成为主导判据；到了亿级，离线重算窗口成为硬约束（7.3.2 说明分块决定它是否跑得完），而线上查询的延迟要求又迫使结果必须服务化。**同一张判据表在不同规模下会指向不同的首选方案——这正是打分表无法表达的部分**：分数不随规模变，判断必须随规模变。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 / 实现 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 规则强匹配（Strong Match） | 用确定性标识做合并 | 对手机号 / 身份证 / 邮箱等的 hash 做相等判断，相等即合并，无相似度概念 | MDM 套件时期的主力做法（IBM InfoSphere MDM / Informatica MDM / Oracle MDM / Talend MDM 等商业套件）；今日多为自建 SQL | 套件商业；自建无许可成本 |
| 图聚合（Graph Aggregation） | 用图的连通性定义 OneID | 节点 = 各来源 ID，边 = 已知匹配关系，**连通分量共享一个 OneID**（主文件 §2.2.2） | Spark GraphX 的连通分量、图数据库的 WCC、阿里 GraphScope 一类大规模图计算 | 计算框架开源为主；图数据库开源与商业并存 |
| 概率匹配（Probabilistic / LTR） | 逐对打分再分割阈值 | Fellegi-Sunter 的似然比（λ = ∏mᵢ/uᵢ）或排序学习模型输出匹配分数，再按上/下阈值分割、中间区送人工复核 | 金融、政企数据治理；模型多用 LightGBM / XGBoost 一类可解释集成模型 | 算法公开；实现自建 |
| Embedding-based 匹配 | 用向量近邻替代字段比较 | 把记录的上下文特征编码为向量，余弦相似度 ≥ τ 判为匹配（主文件 §2.2.3） | 编码侧：行为序列用 DIN / SASRec 一类序列模型、文本用 BERT / E5 / BGE、ID 图用 GraphSAGE / Node2Vec（编码侧清单同主文件 §2.2.3）；检索侧用 FAISS 一类向量近邻索引 | 编码模型开源与商业并存 |
| 端到端深度匹配（Deep ER） | 把匹配做成文本分类 | 序列化属性对 → 预训练语言模型 → 匹配 / 不匹配（主文件 §2.3.5 的 DeepER / Ditto / HierMatcher / ZeroER 一线） | 有标注数据的团队；学术与工业混合 | 论文与模型开源为主 |
| LLM 辅助（生成式 ER） | 用大模型做边界裁决 | 把候选对与判断标准写进 prompt，模型输出 `decision / confidence / reason` 的 JSON | 本章 §1.4 阶段 5 列出的新增做法；商用实体解析服务也在其内部使用 | 按 token 或按次计费；模型可自建或调用 |
| 隐私计算 ID 打通 | 在不暴露明文的前提下求交与匹配 | PSI 求加密集合交集 / 联邦学习聚合模型参数 / TEE 在可信硬件内计算（本章 §3.2.7） | 广告归因（媒体 × 广告主）、跨机构数据合作 | 密码学库开源；可信硬件与平台商业 |
| 托管实体解析服务 | 把分块 + 匹配 + 复核流程做成托管能力 | 服务商提供候选生成、匹配规则/模型与人工复核工作台，客户只做字段映射 | AWS Entity Resolution、Salesforce Data Cloud、Palantir Foundry、阿里云实体解析等（见本章 §1.4 阶段 5 的产品清单） | 商业 SaaS / 云服务，按量计费 |

表里「核心机制」一列是选型的实际依据：**同一族方案的差别集中在阈值与特征上，跨族方案的差别在机制上**。因此这张表不是用来逐行比的，而是用来确认「我需要的机制在这一族里有没有」——例如，如果你的匹配依据里包含大量地址与公司名的变体，那么符号族里没有任何一行能解决它，此时表的作用是提前结束比较。可增补候选时也应守同一条：新增一行必须能说清它的**核心机制与已有行不同在什么地方**，否则它只是同一个机制的另一种实现。

这八种方案实际只分三族，**同族内部差异小、跨族差异大**：第一族是**符号与统计算法族**（规则、图聚合、概率匹配），它们的决策过程可复算、成本可离线摊平，缺的是对自由文本的表达力；第二族是**表示学习族**（Embedding、深度 ER、LLM），它们能处理前一族表达不了的长文本与变体，代价是依赖模型与（对前两者）标注数据；第三族是**部署形态族**（隐私计算、托管服务），它们改变的不是「怎么判」而是「谁能看到明文、谁负责运维」。选型的第一步是选族——族选错了，族内怎么挑都救不回来。

分族之后只需再答三个问题，选项基本就收敛了。**第一，我的匹配依据是不是确定性的**（是，就留在符号族，不要为一个已经确定的问题引入模型）；**第二，我缺的是召回还是精度**（缺召回多半是分块或数据源问题，缺精度才轮到换模型）；**第三，合并结果会不会跨主体流动、被谁审计**（会，就直接跳到部署形态族）。这三个问题都不涉及具体工具，但会决定你该不该启动一个模型项目——多数代价高昂的 OneID 工程，是在第二个问题上判断反了：召回不足，却去训模型。

全景表最后一列（许可 / 商业模式）在这一主题下有特殊含义，值得单独点出：**实体解析这件事买不到「匹配质量」，能买到的只有「运维」与「被托管的流程」**。匹配质量来自你自己的数据形态（标识密度、字段质量、无锚点人群比例），没有哪家产品能替你把手机号覆盖率提高；因此比较商业方案时，真正该问的是它把工作台、分块策略与阈值暴露到什么程度，而不是它宣称的准确率——准确率离开数据集无法比较。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 决策单位：连通分量 vs 逐对阈值

**机制是什么**：图聚合的决策单位是**一个连通分量**（一个整体、传递闭包的结果），概率匹配的决策单位是**一对记录**（局部、彼此独立）。

**它在各候选中的实现差异**：

| 候选 | 决策单位 | 传递性 | 一次错判的影响面 |
| --- | --- | --- | --- |
| 图聚合（WCC） | 连通分量 | 有（A~B、B~C ⟹ A、B、C 同一 OneID） | 沿整个分量扩散 |
| 概率匹配 | 记录对 | 无（每对独立判定） | 局限在该对 |
| 强匹配 | 记录对（但边本身是确定性的） | 结果上仍要走到连通分量才算完成 | 取决于后续聚类 |
| LLM 复核 | 记录对 | 无 | 局限在该对 |

**由此必然导出的性质**：因为连通分量是传递闭包，所以一条弱边可以把两个本来很大的簇焊成一体——**传递性同时是最好的特性和最大的风险**：它让「手机号 A → 用户 1 → 邮箱 B → 用户 2」这类多跳关系自动成立，也让一次错边跨簇传染、事后无法局部回滚；反过来，逐对阈值没有传染性，所以一次错判只影响一对，代价是它不产出「簇」——要得到 OneID 还得再加一步聚类，而这一步会把互不相同的对重新连起来，链式关系上的漏合并（A~B、B~C 但 A≁C）就发生在这一步。

**公开证据**：Fellegi-Sunter 的似然比框架把匹配定义为逐对决策（[Fellegi & Sunter, *A Theory for Record Linkage*, JASA, 1969]）【公开】；工业 OneID 则普遍用连通分量作为最终归属（主文件 §2.2.2 给出 WCC 与并查集的工程做法）。两件事并不矛盾——**逐对打分负责「边」，连通分量负责「簇」**，但它们对错误的态度相反，混用时必须明确谁是决策者。可自行核验的判定方法是：把图版本回退一版，看一次错误合并能不能被单独撤销。

这条机制还给出了一个不需要标注数据的运维指标：**连通分量的规模分布**。健康的 ID 图里，绝大多数分量只有几个节点，少数大分量对应真实的家庭共用设备或企业共享账号；如果分布的长尾突然变厚（例如出现成批的千节点以上分量），说明有一条阈值过松的边在批量连接彼此无关的人。这个指标比精度指标更早报警，而且可以直接从图里统计出来。

分量本身的**赋值方式**也是一处实现差异，且影响下游：一种做法是把分量内的某个既有 ID 提升为 OneID（取最小或最大值作代表，主文件 §2.2.2 的示例即取 `max(user_id_1, user_id_2, anon_id_3)`），另一种是为分量生成全新的代理键并用映射表关联。前者的代价是**一次合并或拆分会让这个 OneID 的值发生变化**，所有按 ID 建的缓存与下游快照都会失效；后者不变值，代价是多维护一层映射，并要在服务化路径上多一次查表。这一条在选型时常常被当成实现细节，但它决定了「合并」这个动作对下游是不是一次并不频繁但影响面很大的事件。

**失效条件**：当弱边比例升高（例如把入图阈值从经验区间下调到 0.6 附近）时，分量的规模会迅速变大，跨簇误合并的概率随分量规模上升，图聚合的可解释性与可回滚性同时下降。这就是本章 §3.5 反模式 2 与反模式 4 的机制解释。

#### 7.3.2 成本与召回的第一性变量：分块（Blocking）

**机制是什么**：实体解析的原始复杂度是两两比较 N²，分块（blocking）把比较限制在同一个块内，用「分块键」把不可能匹配的记录对提前排除。

**它在各候选中的实现差异**：

| 候选 | 分块方式 | 分块的角色 |
| --- | --- | --- |
| 强匹配 | 无需显式分块——hash 相等本身就是分块键 | 天然且精确 |
| 图聚合 | 分块决定**边**的来源，边集合一旦生成，后续成本与分块无关 | 决定图的规模 |
| 概率匹配 | 需要人工或学习式 blocking key（同手机号前缀 / 同城市 / 同 IP 段，见本章 §3.2.3） | 最关键的工程参数 |
| Embedding / 深度 / LLM | 必须先压候选集，否则每对都要过模型 | 决定成本能否成立 |

**由此必然导出的性质**：因为候选对只在块内生成，所以**召回率的上限在分块阶段就已经封死**——同一个人落进不同块的记录对，后面的模型再强也永远看不到它们；这意味着「换更强的模型」对召回无效，只有改分块键才有效。代价是分块键的选择通常是折中：键越粗，块越大、比较次数越多（成本）；键越细，越容易把同一个人切到不同块（召回）。

**推导链与量级**（【推算】）：设日增 100 万条待匹配记录，不做分块需比较 100 万 × 999,999 / 2 ≈ 5×10¹¹ 对；按「城市 + 手机号前 3 位」分块，该组合键的基数落在地级市数百个 × 号段前缀数十个的水平，即 10⁴ 量级；100 万条记录摊到 10⁴ 个块上，平均块大小约 100，于是候选对数 ≈ 100 万 × (100 − 1) / 2 ≈ 5×10⁷ 对。两者相差 10⁴ 倍（4 个数量级）——**分块不是优化技巧，它决定这个任务能不能在每日窗口里跑完**。

写成公式更清楚：候选对数量 ≈ Σ 各块内对数 ≈ 记录数 × (平均块大小 − 1) / 2，而平均块大小 = 记录数 / 分块键基数，代入后即候选对 ≈ 记录数² / (2 × 分块键基数)（块大小远大于 1 时）。**只有当分块键的基数随记录数同比例增长、块大小因而受控时，成本才与记录数保持线性**——一旦分块键的区分度不足（例如用「省份」这类低基数字段），块大小会随总记录数一起增长，成本退回超线性，这就是同一个系统在数据量翻十倍后突然跑不完的原因。也正因为成本由**键基数**而非记录数单方面决定，分块键的取值分布必须被显式设计（见下文三种来源）。可自行核验的做法是统计块大小的**分位数而不是平均数**：拖垮任务的是长尾的大块，平均数看不出来。

分块键的来源也有三种，工程代价依次上升：**人工设计**（手机号前缀、城市、姓名首字母——最便宜，但跨语种与地址类字段上很快失效）；**从数据分布学习**（按字段取值的频率与区分度自动生成键组合，或对低频值单独成块）；**先粗聚类再分块**（用 Embedding 把记录聚到若干桶里，再在桶内精确比较——把分块本身交给表示学习族）。第三种是「长文本字段为主」场景下唯一能让召回率上去的做法，代价是分块结果不再可解释，且桶的质量依赖模型质量。

**公开证据**：分块不是工程上的取巧，它写在 Fellegi-Sunter 建模框架的原论文里——该文给出的匹配流程是「先用分块变量把记录切成小簇、再在簇内逐对计算似然比」的两段式，而不是朴素的两两比较（[Fellegi & Sunter, *A Theory for Record Linkage*, JASA, 1969]）【公开】。它的当代对应物是各开源 ER 库的配置面：Splink、dedupe、recordlinkage 一类工具都把 blocking rule / blocking 变量放在流水线的首位，并对块大小的诊断或上限给出可调参数（可按「库名 + blocking」检索其官方文档当前版本核验）。可自行核验的判定方法是：统计你自己数据上分块键的基数与块大小分位数，看候选对总量是否落在记录数 × (平均块大小 − 1) / 2 的数量级上——若实测值远高于该式，说明长尾大块已在偷偷抬升成本。

**失效条件**：当「同一实体的标识在不同来源中形态差异大」时（跨语种姓名、地址描述、多语言公司名），精确分块键会大量漏切，此时要么改用模糊分块（成本上升），要么在分块前先做规范化——这也是 LLM 与 Embedding 真正能帮上忙的位置：不是替代分块，而是为分块提供更粗但对齐后的键。

#### 7.3.3 错误的方向：误合并不可逆，漏合并可补

**机制是什么**：合并是一个会写入共享资产的操作——OneID 一旦生成，下游的画像、标签、特征、样本、Agent 记忆都按它组织；漏合并只是少识别出一个人。

**由此必然导出的性质**：因为合并结果会被下游消费并被固化，所以误合并的代价随「下游资产数量 × 时间」放大，而漏合并的代价只随覆盖率线性体现。因此正确的做法是**先定精度下限、再补召回**（本章 §3.5 反模式 2 的修正），而不是先追覆盖率再补精度。代价是：覆盖率会在一个区间里提前触顶——无手机号、无登录态的人群长期停留在盲区，只能靠设备指纹（主文件 §2.1 给出的工业命中率区间为 70%–90%【经验】）与行为序列补一部分，这部分人群的画像精度天然低于实名用户。

**证据**：强标识（手机号、身份证）的匹配在 Fellegi-Sunter 框架下的似然比极高，可以直接合并且几乎不产生争议——按主文件 §2.2.1 的算例，m=0.95、u=0.0001 时 λ = 0.95 / 0.0001 = 9500，远高于上阈值【推算】；而弱匹配的阈值（主文件 §2.1 给 0.7–0.95，本章 §3.2.5 把 0.6–0.85 划为需要复核的边界区间）本身就是这个取舍的产物【经验】。

**两个方向的代价结构**：

| 维度 | 误合并 | 漏合并 |
| --- | --- | --- |
| 触发条件 | 相似度过线的假配对；弱边进入连通分量 | 分块没覆盖到，或阈值过严 |
| 直接表现 | 两个人被写成同一条链路 | 一个人被算成多条链路 |
| 代价随时间的变化 | 放大（派生资产随 OneID 生成并被固化） | 不放大（每次只是少覆盖一部分） |
| 受影响的下游 | 画像、特征、样本、归因全部受影响 | 覆盖率与人群规模 |
| 修复方式 | 拆链 + 重算派生资产 | 补一条边，或放宽阈值 |
| 可观测性 | 差：往往在下游指标异常时才暴露 | 好：覆盖率本身可测 |

两者可观测性的差异是问题的关键——**误合并的症状出现在下游，漏合并的症状就在覆盖率指标上**。因此工程上必须为误合并单独设一组指标：冲突检测的触发率（例如同一 OneID 下出现年龄差过大的证件号，见本章 §3.5 反模式 3）、分量规模分布、以及合并后一段时间内的拆链次数。缺了这组指标，团队只看得到漏合并，于是会持续放宽阈值，直到误合并积累到无法收拾。

各候选对两种错误的**控制手段**也不同，且多数是互相拉扯的：

| 候选 | 控制误合并的手段 | 控制漏合并的手段 | 两者的关系 |
| --- | --- | --- | --- |
| 强匹配 | 无需额外控制（确定性相等本身即高置信） | 没有可用手段，只能补数据源 | 不冲突 |
| 图聚合 | 提高入图阈值、为分量规模设告警 | 放宽入图阈值 | **直接冲突**：同一个旋钮 |
| 概率匹配 | 抬高上阈值、扩大中间复核区 | 降低下阈值、扩充特征 | 部分解耦，可两段分别调 |
| LLM 复核 | 采用「不确定即不合并」的裁决口径 | 用边界区间把可疑对包进来 | 可解耦，代价是边界变宽推高成本 |

这张表解释了图聚合方案的一个固有难点：**它的两个目标共用同一个旋钮**。因此实践中总是把弱边的判定从图里拆出去（先用概率模型决定边是否生成），再让图只负责连通性——这就是「图聚合 + 概率匹配」这个组合存在的机制原因，而不是组合偏好。

**失效条件**：偏好会在特定场景反转——广告归因与反欺诈常常**宁可错杀**：一次漏合并意味着一次欺诈未被拦住，而一次误合并只是少投了一个人。此时精度下限应下调，但必须配套「合并可拆链」的机制。

#### 7.3.4 明文边界：隐私计算改变的是「可做的合并集合」

**机制是什么**：PSI、联邦学习、TEE 把「比较」这一步搬到密文、分布式本地或可信硬件里，使参与方在不暴露明文标识的前提下得到交集或匹配结果（本章 §3.2.7）。

**由此必然导出的性质**：因为比较必须在不暴露明文的前提下完成，所以可用的特征被限制为**可加密比较的量**——集合交集的元素、可聚合的模型参数、可信硬件内可执行的规则与模型。自由文本相似度、行为序列这类需要暴露原始值的特征要么不可用、要么只能近似；因此跨主体的实体解析召回率**结构性地低于**同企业内场景，这不是实现质量问题，是协议本身的约束。代价还包括：参与方每增加一个，协议与密钥管理复杂度就上升一档，且匹配结果的正确性无法被单方独立验证。

**证据**：三类技术（PSI / 联邦学习 / TEE）各自的适用面在本章 §3.2.7 中已列出；设备侧的授权收紧是同一个趋势的另一面——iOS 14.5 起 IDFA 需用户显式授权（[Apple, App Tracking Transparency, 2021]）【公开】，这直接压缩了跨主体用设备标识打通的可行空间。

这一族还有一个容易被忽略的成员：**托管实体解析服务**。它把分块、匹配与复核工作台打包对外，客户只做字段映射与阈值确认。它的机制效果与自建没有本质差别，改变的是「谁运维」和「数据在哪里」——因此选它的真正判据不是精度对比，而是**数据能否出域**，以及组织是否具备自己维护图谱与重算链路的工程能力。反过来说，如果数据不能出域，托管服务在精度上的任何优势都无法通过评审。

三类技术改变「可做的合并集合」的方式并不相同，落到工程上要按可用特征来选：

| 技术 | 参与方能看到的 | 可用的匹配特征 | 主要限制 |
| --- | --- | --- | --- |
| PSI | 交集本身，或交集的大小 | 只能基于集合成员关系 | 不直接产出「簇」，相交之后仍需在交集上再建 OneID |
| 联邦学习 | 模型参数或梯度 | 可在各方本地同构计算的数值特征 | 要求各参与方有同构可用的特征，冷启动阶段难以覆盖 |
| TEE | 可信环境内的计算结果 | 硬件内可执行的规则与模型 | 依赖硬件信任链与远程证明，且平台能力受限 |

**失效条件**：当合作方数量少、且同属一个集团（不存在「不信任对方」的前提）时，密码学开销换不来等价收益——此时用组织内的权限与审计控制更划算。反过来，一旦涉及不同法人主体之间的数据交换，这一族就从「可选」变成「前置条件」。

### 7.4 成本结构对比（不是价格表，是成本函数）

把 OneID 的总成本写成函数形式：

```
成本 ≈ 图谱与服务常驻成本
      + f(待匹配记录数 × 分块后平均块大小)      # 候选生成与打分
      + g(边界样本数 × 单次复核成本)             # 人工或 LLM 复核
      + h(重算频率 × 图规模)                     # 全量重算与拆图
      + i(规则与阈值的维护人力)                   # 治理成本
```

各候选的**主导项**与**隐性成本**：

| 候选 | 主导项 | 隐性成本 | 增长方式 |
| --- | --- | --- | --- |
| 规则强匹配 | f 项（全量 join / 扫描） | i 项：规则条数膨胀，规则之间的优先级冲突难以排查 | 随数据量近线性 |
| 图聚合 | h 项（连通分量重算与图存储） | 一次误合并引发的拆图重算，成本不可预测 | 随边数与分量规模增长 |
| 概率匹配 | f 项（候选对 × 特征计算） | 标注数据与阈值调参的人力，且换数据源要重标 | 随候选对数量增长 |
| Embedding / 深度 ER | f 项（推理算力） | 训练数据构建与模型再训练周期；换业务要重训 | 随记录数线性但常数远大于规则 |
| LLM 辅助 | g 项（token 消耗） | 边际成本随候选对线性放大，且需要额外的行为约束与结果校验 | 随「送进模型的样本数」增长 |
| 隐私计算 | 协议固定开销 | 参与方数与集合规模带来的协议复杂度；召回率下降带来的业务损失 | 随参与方数与集合规模增长 |
| 托管服务 | 按量计费（近似 f + g 的打包） | 数据出域评估与字段映射的持续维护 | 随匹配量线性，可预测性最好 |

**两个量级推导**（【推算】）：

1. **blocking 的价值**：见 7.3.2——日增 100 万条时，不做分块的 5×10¹¹ 对与分块后的 5×10⁷ 对相差 10⁴ 倍（4 个数量级）。它决定了「每日全量重算」这个运维模式是否成立。
2. **LLM 复核的边界**：设每日候选对 5×10⁷（同 7.3.2 的量级），边界样本占 5% 即 2.5×10⁶ 对，按每对约 1×10³ token 计，约 2.5×10⁹ token/日；若改成把全部候选对送 LLM，则是 5×10¹⁰ token/日，差 20 倍。**结论方向是明确的：LLM 只能作用于边界集合，这不是省钱的技巧，而是唯一可行的口径**——一旦边界比例随阈值调松而升高，成本按同一比例线性放大。

**一条被普遍低估的隐性成本是 h 项（重算）**。图聚合的全量重算窗口随图规模增长，而每一次阈值调整、每一次错误合并的拆分都会触发一次重算；因此在生产系统里「阈值能不能在线调」通常等价于「敢不敢动配置」。把重算做成增量的（只重算受影响的连通分量）是控制这一项的唯一有效手段，代价是要额外维护「分量 ↔ 增量事件」之间的关系——这部分成本无法外包给存储引擎，是图聚合方案必须自己承担的。

从规模看，成本的主导项还会换两次（【经验】）：**十万级以下**，主导项是 i 项（人维护规则与阈值），此时上模型是净亏；**百万到千万级**，主导项变成 f 项（候选对与特征计算），分块质量直接决定账单；**亿级以上**，h 项（重算与服务化）成为硬约束，架构问题取代算法问题成为主要矛盾。判断自己落在哪一段只需要一个可数的量：**每日候选对的数量级**。

**一条经验判据**：多数团队的覆盖率在 85%–95% 区间内投入产出最陡，再往上每提高一点覆盖率，通常需要引入**新的数据来源**（合作数据、线下数据）而不是换算法——因为无锚点人群缺的是标识本身，不是更强的模型（【经验】；本章 §6 落地实践中「真实落地路径」一节把「亿级用户 / 5+ 业务 + LLM 复核 + OneService」放在 10 → 100 阶段，而不是 0 → 1 阶段，依据同此）。

托管服务的成本结构与自建**形状不同**，不只是「打包价」：它把 f 与 g 两项按量计费，因此**成本可预测、但几乎不可优化**——分块与阈值由服务方的实现决定，客户能调的只有字段映射与匹配范围。这在选型上意味着一次取舍交换：用「优化空间」换「可预测性与运维人力」。反过来，如果 ID 规模还会涨两个数量级，先想清楚计费曲线的斜率，再决定要不要把图谱放进黑盒。

### 7.5 决策树（每个分支都要有阈值依据）

```
Q1 是否有实名 + 稳定的强标识（手机号 / 身份证 / 三要素）？
├── 有 → 强匹配优先（承担大头）+ 图聚合做骨架
│         │
│         └── Q1a 未登录 / 无手机号人群是否足够大？
│               ├── 是（经验线：三成左右）→ 补设备指纹 + 行为弱匹配，且只做疑似
│               └── 否 → 只做强匹配 + 图聚合，不要为少数人引入整套弱匹配链路
│
└── 没有 → Q2
    │
    Q2 是否有结构化可比较字段（设备指纹 / IP / 地址 / 邮箱）？
    ├── 有 → 图聚合 + 概率匹配（阈值分割 + 中间区复核）
    │
    └── 没有 → Q3
        │
        Q3 是否有大量长文本字段（地址描述 / 公司名 / 商品名）？
        ├── 有 → Embedding / Ditto 风格的深度匹配 + LLM 辅助
        │
        └── 没有 → 仅有行为序列 → Embedding-based 匹配
Q4 是否需要跨主体（跨企业 / 跨机构）打通？
├── 需要 → 隐私计算（PSI / 联邦学习 / TEE），并接受召回率结构性下降
└── 不需要 → 自建，不外发明文
Q5 是否涉及需要同意才能合并的个人信息？
├── 是 → 合并前置同意校验 + 可撤回即拆链，且保留合并溯源
└── 否 → 仍需保留合并理由与图版本，以便回滚
```

这棵树其实由两条彼此独立的路径组成：**Q1–Q3 决定「用哪一族机制」**（有没有强标识 → 有没有结构化字段 → 有没有长文本），**Q4–Q5 决定「加什么约束」**（跨主体就加隐私计算，涉及个人信息就加同意与拆链）。两条路径互不覆盖：一个已有强标识的系统仍然可能因为要跨主体合作而必须走 Q4，一个走 Q3 的系统也同样要回答 Q5。把它们画在一棵树里只是为了压缩篇幅——判断时分别回答两次更不容易漏。

**阈值依据**：

- **Q1「有强标识」的判定**：不按「有没有手机号字段」判，而按**活跃用户中可被强标识覆盖的比例**判——判据是覆盖面的量级而不是字段的存在性；只有单一来源时，强标识几乎一定覆盖绝大多数登录用户，图聚合只需处理少量跨端（【经验】）。
- **Q1a 的「三成左右」**（【经验】，量级推导如下）：这条阈值由两个**不同口径**的量相乘得到，混用会把结论放大一倍以上，因此先写清各自测的是什么。第一个口径是主文件 §2.1 给出的**设备指纹工业命中率 70%–90%**【经验】——分母是「能采集到设备信号的设备」，问的是指纹能否重新认出这台设备；第二个口径是**无锚点人群中能稳定采集到设备信号的子集占比**（多设备、清缓存、隐私受限的浏览器与系统落在这个子集之外），本推导按一半计（这是推导的显式前提，可由各端自身的设备信号覆盖率统计核验）。两者相乘，整个无锚点人群中能被弱匹配接住的比例约为 0.35–0.45。若无锚点人群占比为 p，弱匹配带来的整体覆盖率增量约为 0.35p–0.45p：p=10% 时增量只有 3.5–4.5 个百分点，却要引入弱边入图、复核链路与常驻组件，不划算；p 达到三成时增量进入两位数区间（按上式约 10–14 个百分点），才与这套常驻成本相称。因此把「未登录人群占比达三成左右」作为引入弱匹配的经验线，p 显著低于此值时优先用强匹配的图聚合。
- **Q1a「只做疑似」**：依据是 7.3.1 的机制——弱边一旦进入连通分量就获得传递性，错边会跨簇传染。因此弱匹配的输出只能作为候选与提示，入图阈值必须显著高于复核线。本章 §3.2.5 把 0.6–0.85 划为复核区间、主文件 §2.1 把弱匹配阈值放在 0.7–0.95，两条合起来给的就是「复核线」与「入图线」的位置【经验】。
- **Q2「结构化字段」**：判据是「是否存在可稳定比较的中间标识」。设备指纹的工业命中率区间为 70%–90%（主文件 §2.1【经验】），这个区间就是 Q2 分支的可行性上限——若你的场景命中率远低于该区间，走 Q2 等于把覆盖率押在一个不稳定的量上，应直接走 Q3。注意它与 Q1a 中那个 0.35–0.45 是两个口径：这里问的是**设备级**命中率（分母是能采集到设备信号的设备），Q1a 还要在此基础上再乘「无锚点人群中能稳定采集设备信号的子集占比」，所以后者必然明显更低，两者不可互相代入。
- **Q3「长文本」**：判据是「是否存在规则无法表达的变体」——一旦出现地址、公司名、商品名的变体，规则匹配不是精度不够而是表达不了（见 7.1），此时才值得引入表示学习族，成本按 7.4 的 g 项计。
- **Q4「跨主体」**：判据不是数据量而是**主体边界**——只要匹配双方是两个法人主体，明文出域就需要法律与合规评估，此时隐私计算从「可选」变为「前置」。代价在 7.3.4 已说明：召回率结构性下降。
- **Q5「同意与撤回」**：判据是「该标识是否属于需要单独同意的个人信息」。设备侧授权的收紧是同一约束的实例——iOS 14.5 起 IDFA 需用户显式授权（[Apple, App Tracking Transparency 文档, 2021]）【公开】。落到工程上就是：合并前校验同意状态、撤回时能沿链路拆链，且每次合并记录理由（merge_reason）与置信度（merge_confidence）。

树里没有出现的分支也值得说明：**没有任何一条路径通向「哪个方案最准」**。精度是这棵树的输出，不是输入——它是「分块覆盖 + 匹配依据 + 阈值方向」三者的共同结果，所以它不该出现在任何一个判断节点上。同理，树里也没有「预算多少」这类节点：在 OneID 里成本的主导项由分块质量与重算频率决定，而这两者都是可工程调节的量；真正不可调节的是**数据源能覆盖多少人**（7.4 的经验判据）。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 电商跨端（Web / App / 小程序）打通 | 强匹配（手机号）+ 图聚合 | 概率匹配 + LLM 复核（补地址变体） | 纯规则会漏掉无手机号的游客，纯弱匹配会把同写字楼的人合并 |
| 广告投放闭环（平台回传 × CRM） | 概率匹配 + LLM 复核 | 托管实体解析服务 | 强匹配不可行：两侧 ID 异构、匹配率低，且属跨主体场景 |
| 金融风控（一人多户识别） | 强匹配（身份证）+ 图 + 规则 | 概率匹配 | 监管要求决策可解释、可追溯，黑盒模型不能单独作为合并依据 |
| 反欺诈（一机多号、设备农场） | 设备指纹 + 行为 + 图 | Embedding 相似 | 强标识会被黑产刻意规避；此场景偏好「宁可错杀」，阈值应下调 |
| 客户 360 / CRM 会员统一 | 图聚合 + 概率判定 | 主数据套件 | 只做单域匹配会导致跨域口径永远对不齐 |
| 跨企业数据合作 | PSI / 联邦学习 / TEE | 托管服务（需满足出域要求） | 明文交换不可行；且此场景召回率天然低于同企业内 |
| 跨境业务（多语言地址匹配） | LLM 辅助 + Embedding | 深度 ER 模型 | 分块键在跨语种下失效，规则匹配的召回上限被分块封死 |
| 商品 OneID（SKU / SPU 统一） | 强匹配（条码 / 型号）+ LLM 商品名匹配 | Embedding 相似 | 商品名的变体密度高于人名，纯规则覆盖不足 |
| Agent 长期记忆 | OneID + 向量记忆 | 仅按会话隔离 | 不打通则记忆碎片化，且无法按用户做隔离与删除 |
| 媒体内容 ID（图文视频） | 内容指纹 + Embedding | 深度学习匹配 | 跨模态下没有可比的强标识 |

这张矩阵的读法是：**先用最便宜的机制把候选筛掉，再把贵的机制留给少数样本**。下面五个组合其实都在做同一件事——把「判定」拆成多道闸门，分辨力递增、单位成本也递增。判断一个组合是否成立，只需看一个可核验的量：**进入最后一道闸门的样本占比**。这个比例一旦越过几个百分点，就说明前面的闸门太松，成本会按同一比例膨胀（见 7.4 对 LLM 复核的推导）。

**五个常见组合**（各自说明职责边界与运维代价）：

1. **强匹配 + 弱匹配**（互联网最常见）：强匹配（手机号 / 身份证 hash）承担主合并，弱匹配（设备 + 行为 + LLM）只做疑似与候选。运维代价：弱边入图会推高连通分量的误合并风险，必须保留合并理由、置信度与图版本，并为拆链准备回滚路径。
2. **图聚合 + 概率匹配**（图原生 ID-Mapping）：图聚合（WCC）作骨架，概率分数作边权重，阈值决定哪些边入图。运维代价：边阈值与重算周期是常驻成本，且阈值一改就要全图重算——这条组合的可运维性取决于「重算窗口」而非算法本身。
3. **隐私计算 + OneID**（数据合作）：密码学层负责「不暴露明文」，OneID 层负责「合并与拆分」。运维代价：参与方每增加一个，协议与密钥管理复杂度上升一档；召回率低于同企业内（见 7.3.4），需在业务侧事先接受这个上限。
4. **LLM + 传统模型**（成本可控）：传统模型处理绝大多数候选对，LLM 只复核边界样本（本章 §3.2.5 的边界区间）。运维代价：边界比例是成本的总开关——阈值调松会把 g 项按比例放大（7.4 的推导），因此阈值变更必须与成本评估一起走评审。
5. **OneID + 知识图谱**（图融合）：OneID 节点挂载到知识图谱的 Person / Device 节点上，图谱的多跳关系补充弱匹配，检索侧可用 GraphRAG 一体化查询。运维代价：两套图必须保证实体对齐不漂移；OneID 重算会引起 KG 节点重建，两个重算周期要错开设计。

五个组合有一个共同点：**它们都要求有人对「重算」「边界比例」「拆链」这三件事负责**。这三件事的共同特征是「不出事的时候没有信号，出事的时候影响面很大」——重算跑不完会静默延后、边界比例升高只会体现为账单、拆链请求往往来自业务方的一次投诉。所以在组合落地的同时要把它们变成三个可观测指标并指定 Owner；否则组合在纸面上成立，在生产里会退化成「谁也不动的黑盒」。

### 7.7 选错的代价与迁移成本

**反模式：把连通分量当成最终决策** —— 症状是「只要相似度过线就入图」，图规模随数据增长而膨胀 → 后果是一条错边把两个大簇焊成一体，误合并沿分量扩散，且因为下游画像、样本、特征已按该 OneID 生成，拆分必须重算全部派生资产 → 正确做法：弱边只产出候选、不入图；入图阈值显著高于复核线；每次合并留 merge_reason 与 merge_confidence，图带版本号，支持按版本回退与单点拆链（本章 §3.5 反模式 2 / 4 的机制成因）。

**反模式：用模型替换分块** —— 症状是「召回上不去，于是换更强的模型」→ 后果是召回毫无改善，因为同一个人落进了不同的块，模型根本没机会看到这对候选；成本却按新模型的常数上升 → 正确做法：先度量分块的召回上限（可自行核验的方法是：抽样若干已知同人记录，检查它们是否落在同一块内），再决定是否投资模型。

**反模式：让 LLM 承担主力匹配** —— 症状是「LLM 在长文本上确实更准，于是全量送模型」→ 后果是成本随候选对线性放大（7.4 推导：全量比边界复核高约 20 倍），且决策难以复现、难以审计 → 正确做法：用便宜模型把候选压到边界集合，LLM 只做复核；同时把「边界比例」作为线上监控指标。

**反模式：跨主体先打通、后补合规** —— 症状是先做数据合作、把两边 ID 合起来再说 → 后果是补同意与撤回机制时，已合并的历史全部需要重审与拆链，返工面覆盖所有下游 → 正确做法：同意状态作为合并的前置条件，撤回路径与合并路径同期设计。

这四条反模式有一个共同结构：**它们都表现为「模型或引擎被寄予了它机制上做不到的期望」**——指望相似度替代分块、指望大模型替代成本控制、指望先合并后补合规、指望图自动区分「该连」与「不该连」。识别方式也很统一：**在问「换什么工具」之前，先问「这个期望对应哪条机制」**；找不到对应机制的期望，就是下一笔返工。

**换成另一个方案要动什么**：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 规则强匹配 → 图聚合 + 概率 | 把 ID 对重建成边与图（中） | SQL join → 图查询或服务查询（中） | 引入图存储与重算调度（中） | 图算法与阈值调优（中） |
| 图聚合 → 加入概率匹配 | 需要标注样本与特征管道（高） | 决策从连通分量改为阈值 + 聚类（高） | 引入模型训练与在线打分服务（高） | 排序学习与特征工程（高） |
| 全自建 → 托管实体解析服务 | 数据出域评估与字段映射（中，含合规成本） | 内部实现替换为 API 调用（低） | 常驻组件减少（负，即成本下降） | 服务商的概念模型与工作台（低） |
| 用户 OneID → 扩展到商品 / 设备 / 订单 OneID | 每类实体各自一套锚点与阈值（高） | 查询需带实体类型（中） | 并行维护多张图谱（高） | 多实体建模与冲突检测（中） |
| 补 LLM 复核 | 无（增量） | 边界样本路由（低） | 模型服务调用与限流（低） | Prompt 设计与结果校验（低） |

这张表里最容易被低估的一列是「数据迁移」：算法可以一个月重写一遍，但**ID 图谱、映射数据与合并历史是长期积累的资产**，它们的形态决定迁移的下限与上限。如果第一版把边与合并理由只写进了某个引擎的私有存储、且没有导出格式，那么无论后面的方案多好，迁移都会先卡在「拿不到历史」。因此更稳的做法是在第一次选型时就要求**图谱可导出、边与合并理由可读**——这一条约束的成本几乎为零，收益却决定了三年后还有没有选择权。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 强标识覆盖大部分活跃用户，未登录人群小 | 强匹配 + 图聚合 | 强匹配的边是确定性的，图聚合只负责跨端连通，误合并风险最低 |
| 无锚点人群占三成以上 | 加设备指纹与行为弱匹配，只做疑似 | 弱边进入连通分量即获得传递性，只能以「不入图」控制传染面 |
| 候选对数量已让日批跑不完 | 先重做分块键，再考虑模型 | 召回上限由分块决定，模型只影响块内的排序精度 |
| 有大量地址 / 公司名变体 | 表示学习族 + LLM 边界复核 | 规则族对这类字段是表达不了，不是不够准 |
| 跨主体数据合作 | 隐私计算，并接受召回上限 | 明文边界由协议决定，与实现质量无关 |
| 需要可审计、可回滚 | 图版本 + 合并理由 + 置信度 | 合并是会被下游固化的写操作，可拆链是唯一的事后手段 |
| 已有一套私有存储的 ID 图谱，但要换方案 | 先解决「图谱能否导出」，再谈换什么 | 算法一个月可重写，图谱与合并历史是长期资产 |
| 候选对全量人工可复核（小规模） | 先不上模型，把规则与复核流程做扎实 | 此阶段唯一的主导成本是人力，模型只会抬高常数 |

> 本节小结：这些候选之间真正起决定作用的差别只有一条——**「合并」这件事发生在哪个粒度上，以及那个粒度是否具有传递性**。图聚合把决策放在连通分量上（多跳打通与跨簇传染来自同一个机制），概率与 LLM 把决策放在记录对上（错误可隔离，但要另做聚类才能得到 OneID）。其余维度——精度、成本、可解释性——都要先由这条机制定下方向，再看阈值与模型。换句话说，选型的第一问不是「谁的算法更好」，而是「我的错误应该被限制在多大范围内」。
