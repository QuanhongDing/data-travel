## 6. 落地实践

### 6.1 阿里电商"**OneID 10 亿用户跨端打通**"8+ 年（2016-2024）

**背景（Why）**

阿里电商 2016 年面临**多端用户割裂**：
- **淘宝 / 天猫 / 支付宝 / 菜鸟 / 闲鱼**——**5 端各有自己的 user_id**
- **同一人 5 个 ID**——跨端推荐 / 风控 / 营销全做不了
- **DAU 重复计数**——「全平台 DAU」把 5 端相加，**虚高 30-50%**
- **营销重复触达**——同一个人被 5 端各推一次

**触发点（What）**

2016 年阿里启动**电商 OneID**（[阿里 2016]），目标四条：
- **OneID 覆盖率**——**70% → 98%+**
- **跨端识别准确率**——**99%+**
- **DAU 去重**——修复 30-50% 虚高
- **查询规模**——**千亿级/天**

**详细做法（How）**

阿里 OneID 的**5 大核心组件**：

1. **锚点（手机号 + 设备指纹）（核心创新）**
   - 关键设计：**手机号是一级锚点**（最强），**设备指纹是二级**
   - 关键能力：**登录态 + 未登录态都能打通**
   - 关键数字：**覆盖率 70% → 98%+**
   - 归并逻辑示意：
     ```text
     一级锚点：手机号（哈希后）      →  强连通分量合并
     二级锚点：设备指纹（IDFA/OAID/IMEI）→  补充未登录场景
     弱匹配：收货地址 + 时间窗 + 支付账号尾号 → 仅做「疑似」提示
     LLM 复核：地址 / 公司名变体（如「阿里巴巴」vs「阿里」）
     ```

2. **弱匹配（行为序列）（核心）**
   - 关键设计：**同一收货地址 + 同一时间窗 + 同一支付尾号** 三条件同时满足只出「疑似」提示，不做强合并（见 §6.6 与小结）
   - 关键能力：**只在三条件同时命中时才扩召回，宁可漏合并也不把陌生人合并**
   - 关键数字：**弱匹配召回 +8%，误合并率 < 0.1%**

3. **LLM 复核（核心）**
   - 关键设计：**地址 / 公司名 / 昵称的变体识别**（「杭州市余杭区」vs「杭州余杭」）
   - 关键能力：**规则失效时兜底**
   - 关键数字：**变体识别准确率 96%**

4. **OneService 服务（核心）**
   - 关键设计：**图存储 + 多级缓存**，支持**超高并发**
   - 关键能力：**缓存层挡住绝大部分请求，图存储不被海量查询直接压垮**
   - 关键数字：**P99 200ms → < 10ms**、**QPS 百万级 → 千万级**

5. **千亿级查询（核心创新）**
   - 关键设计：**热数据（最近 30 天活跃）内存 + 全量磁盘**
   - 关键能力：**热数据常驻内存、全量落磁盘，活跃用户的查询不必回盘**
   - 关键数字：**1000 亿+ 次查询/天**

**阿里 OneID 关键数字**（[阿里 2016-2024 公开数据]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **OneID 覆盖率** | 70% | 98%+ | **+40%** |
| **跨端识别准确率** | 80% | 99%+ | **+24%** |
| **DAU 去重率** | 0% | 30-50% | **修复** |
| **查询 QPS** | 百万级 | 千万级 | **+900%** |
| **查询 P99** | 200ms | < 10ms | **-95%** |
| **误合并率** | 2% | < 0.1% | **-95%** |
| **千亿级查询** | 未建设 | 已覆盖 | **新增能力** |

**具体数字（How much）**

- 团队规模：阿里 OneID 团队 200+ 人
- 关键数字：**OneID 覆盖率 98%+**；**千亿级查询/天**；**误合并 < 0.1%**
- 业务影响：覆盖**淘宝 / 天猫 / 支付宝 / 菜鸟 / 闲鱼**

**失败教训**

- 早期「**5 端各有自己的 user_id**」——跨端推荐 / 风控 / 营销全都做不了、「全平台 DAU」虚高 30-50%，倒逼**「手机号锚点 + 设备指纹 + 弱匹配 + LLM 复核的组合归并」**
- **只用设备指纹**——刷机 / 换机导致**同一人变多 ID**，且**一台设备多人用**导致误合并，倒逼**「手机号为主、设备指纹为辅」**
- **弱匹配过于激进**——第一版「同一 Wi-Fi 即合并」，**把写字楼同事全合并成一个人**，倒逼**「三条件同时满足」**
- **没有反合并机制**——发现误合并后无法拆分，倒逼**「合并溯源 + 可回滚」**

### 6.2 字节跳动"**抖音 / TikTok 6 亿用户 OneID**"5+ 年（2019-2024）

**背景（Why）**

字节 2019 年面临**跨端 + 全球 OneID**：
- **6 亿+ 抖音用户** + **TikTok 全球**——**国内外两套体系**
- **多端**——抖音 / 抖音极速版 / 抖音火山版 / TikTok **多 App 同人**
- **合规约束**——GDPR 下**国内外数据不能简单互通**

**触发点（What）**

2019 年字节启动 **OneID + 抖音 / TikTok**（[字节技术博客 2019]），目标：
- **6 亿+ 抖音 OneID 统一**
- **跨端识别 95%+**
- **全球合规**——国内 / 国外分区

**详细做法（How）**

字节 OneID 的**5 大核心组件**：

1. **设备指纹（核心创新）**
   - 关键设计：**多端设备指纹统一**（IDFA / OAID / 自研指纹）
   - 关键能力：**不依赖登录也能打通**
   - 关键数字：**6 亿+ 用户覆盖**
   - 指纹组成示意：
     ```text
     设备指纹 = hash(
       硬件型号 + 系统版本 + 屏幕参数 + 时区
       + 运营商 + 首次启动时间 + 安装渠道
     )   # 无权限依赖，合规友好
     ```

2. **行为序列匹配（核心）**
   - 关键设计：**高频行为模式比对**（同一时段、同一内容偏好序列）
   - 关键能力：**用户换设备、换端之后仍能被认成同一个人**
   - 关键数字：**召回 +10%**

3. **跨端识别（核心）**
   - 关键设计：**登录态优先，未登录态靠指纹 + 行为**
   - 关键能力：**登录与未登录两类场景都覆盖，未登录用户不留识别盲区**
   - 关键数字：**准确率 95%+**

4. **OneService 服务（核心）**
   - 关键设计：**多级缓存 + 分区部署**
   - 关键能力：**多级缓存 + 分区部署，国内与海外各自就近访问**
   - 关键数字：**P99 < 15ms**

5. **全球 TikTok 集成（核心创新）**
   - 关键设计：**国内 / 国外分区 OneID**，遵守数据出境合规
   - 关键能力：**合规与统一兼得**
   - 关键数字：**合规审计通过率 100%**

**失败教训**

### 6.3 美团"**OneID + 5+ 业务**"4+ 年（2020-2024）

美团 2020 年面临**5+ 业务用户割裂**：
- **5+ 业务**（外卖 / 到店 / 酒店 / 出行 / 买菜）——**一人多业务、多 App、多账号**
- **超级 App 内的小程序**——同一 App 里 5 个业务**各自有 session**
- **跨业务分析**——「外卖用户订酒店的比例」做不了

**触发点（What）**

2020 年美团启动 **OneID + 5+ 业务**（[美团技术博客 2020]），目标：
- **5+ 业务 OneID 打通**
- **OneID 覆盖**——**70% → 90%+**
- **跨端准确率**——**95%+**

**详细做法（How）**

美团 OneID 的**5 大核心组件**：

1. **手机号锚点（核心创新）**
   - 关键设计：**美团生态手机号统一**——外卖 / 酒店 / 出行大多需手机号
   - 关键能力：**手机号作为跨业务主锚点，外卖 / 酒店 / 出行共用同一套归并结果**
   - 关键数字：**覆盖率 70% → 90%+**

   - 关键数字：**召回 +8%**

3. **跨端识别（核心）**
   - 关键设计：**App + 小程序 + H5 三端统一**
   - 关键能力：**同一个人在 App / 小程序 / H5 里归到同一条 ID，不再被算两次**
   - 关键数字：**准确率 95%+**

4. **OneService 服务（核心）**
   - 关键设计：**图存储 + 双层缓存**
   - 关键能力：**双层缓存吞掉高峰查询，外卖 / 到店大促期间归并服务不降级**
   - 关键数字：**P99 < 10ms**

5. **5+ 业务集成（核心创新）**
   - 关键设计：**OneID 作为业务中台的公共能力**

### 6.4 Meta"**OneID + 30 亿用户跨平台**"6+ 年（2018-2024）

**背景（Why）**

Meta 2018 年面临**30 亿用户跨三平台**：
- **Facebook / Instagram / WhatsApp**——**三个 App、三套 ID**
- **隐私监管最严**——GDPR / CCPA 下**跨 App 关联本身敏感**
- **广告归因**——跨 App 才能算出真实投放效果

**触发点（What）**

2018 年 Meta 启动 **OneID + 30 亿用户**（[Meta 2018]），目标：
- **30 亿用户跨平台打通**
- **跨平台准确率 98%+**
- **合规**——用户可查 / 可删

**详细做法（How）**

Meta OneID 的**5 大核心组件**：

1. **设备指纹 + 账号锚点（核心创新）**
   - 关键设计：**账号（FB 登录）为主锚点，设备指纹为辅**
   - 关键能力：**用 FB 账号登录 IG，天然打通**
   - 关键数字：**30 亿+ 用户**
   - 分层示意：
     ```text
     L1 账号锚点：FB 账号 / 邮箱 / 手机号        → 强合并
     L2 设备指纹：IDFA / GAID / 自研软指纹       → 跨 App 补充
     L3 行为序列：内容偏好 + 活跃时段            → 弱召回
     L4 合规层  ：同意状态（consent）校验        → 合并前置门禁
     ```

2. **行为序列匹配（核心）**
   - 关键设计：**内容偏好向量相似度**（看同一批 Reels、关注同一批账号）
   - 关键能力：**未登录跨 App 识别**
   - 关键数字：**召回 +9%**

3. **跨平台识别（核心）**
   - 关键设计：**三平台统一 ID Graph**
   - 关键能力：**广告归因跨 App 可见**
   - 关键数字：**准确率 98%+**

4. **OneService 服务（核心）**
   - 关键设计：**图查询 + 强一致缓存**
   - 关键能力：**强一致缓存保证同一用户不会在两个请求里拿到两个 ID**
   - 关键数字：**P99 < 20ms**

5. **FB / IG / WhatsApp 集成（核心创新）**
   - 关键设计：**合规优先**——用户关闭「跨 App 关联」时**立即拆链**
   - 关键能力：**每条合并链都能追溯到同意来源，用户撤回时当场拆链**
   - 关键数字：**合规审计通过率 100%**、**用户可查可删 100%**

| --- | --- | --- | --- |
| **用户覆盖** | 30 亿（分散） | 30 亿（统一） | **统一** |
| **OneID 覆盖率** | 70% | 95%+ | **+36%** |

**具体数字（How much）**

- 团队规模：Meta OneID 团队 500+ 人
- 关键数字：**30 亿+ 用户**；**OneID 95%+**；**三平台统一**
- 业务影响：覆盖**Facebook / Instagram / WhatsApp**

**失败教训**

- 早期「**三个 App 三套 ID**」——IG 与 FB 用户无法归并、广告归因失真，倒逼**「统一 ID Graph」**
- 「**默认开启跨 App 关联**」——未获用户明示同意、被监管处罚，倒逼**「关联需显式同意 + 可随时撤回」**
- 「**用户注销后未拆链**」——注销 FB 但 IG 仍能关联到旧身份、构成合规事故，倒逼**「注销即全图拆链」**
- 「**行为序列匹配未纳入合规前置**」——在用户未同意的场景下仍做匹配，倒逼**「把同意状态作为合并的前置门禁」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**手机号锚点（一级）**」（**最简单**）——**1 万+ 用户**
- 产出：**归并规则文档 + 可回滚的合并日志**
- 团队：**2-3 人**
- 验证标准：**误合并率 < 0.5%**、**合并可回滚**

**1 → 10 阶段：6-12 个月**

- 扩展到「**百万+ 用户 / 2-3 端**」
- 引入「**设备指纹（二级）**」**（**必须**）**——覆盖未登录场景
- 引入「**行为序列匹配（弱召回）**」——只做疑似不做强合并
- 团队：5-10 人
- 验证标准：**覆盖率 ≥ 85%**、**准确率 ≥ 90%**

**10 → 100 阶段：12-24 个月**

- 扩展到「**亿级用户 / 5+ 业务**」
- 引入「**LLM 复核**」**（**生产**）**——地址 / 名称变体识别
- 引入「**OneService 服务**」——图存储 + 多级缓存
- 团队：10-30 人
- 验证标准：**覆盖率 ≥ 95%**、**P99 < 20ms**

**100 → 1000 阶段：12-24 个月**

- 引入「**千亿级查询**」**（**AI 时代**）**——热内存 + 全量磁盘
- 引入「**合规层**」——同意 / 撤回 / 注销拆链
- 团队：30-100 人
- 验证标准：**误合并 < 0.1%**、**合规审计 100%**

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 美团 / Meta）印证：**OneID 不是「用户 ID 拼接」，是「手机号锚点 + 设备指纹 + 行为匹配 + LLM 复核 + OneService」5 件套**。
> - 关键时间线：阿里 8+ 年 / 字节 5+ 年 / 美团 4+ 年 / Meta 6+ 年 —— **OneID 是 4+ 年长期工程**。
> - 选型第一原则：「**手机号锚点（一级）**」（**最简单**）——**1 万+ 用户** → 「**设备指纹 + 行为匹配**」（**必须**）→ 「**LLM 复核 + OneService**」（**生产**）→ 「**千亿级查询 + 合规层**」（**AI 时代**）。
> - 99% 的失败来自「**行为匹配过激 + 无回滚机制 + 关联同意缺失**」——必须有 **弱匹配只做疑似 + 合并可回滚 + 合规前置**。
> - 真正的 ROI 来自「**覆盖率 95%+ + DAU 去重 30-50% + 误合并 < 0.1%**」——是**大厂核心 ID 基础设施的命脉**。
