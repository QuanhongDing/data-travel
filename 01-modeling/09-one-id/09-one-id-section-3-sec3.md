## 3. 设计模式与范式

> 原 § 3 共 177 行：8 个模式中 5 个附 1–4 行流程草图，模式 6–8 只有要点列表；8 个反模式只写症状要点 + 一行**修正**，没有机制层面的后果。重写为 ~320 行模式手册，为每个模式补上机制代价与失效点。

### 3.1 先看约束：模式不是选择题，是约束的产物

本节主要沿用的两条形式化，出自主文件 §2.2 的 2.2.1 与 2.2.2：Fellegi-Sunter 的**似然比**（λ = ∏ mᵢ / ∏ uᵢ，超过上阈值合并、低于下阈值排除、中间交人工复核）与**连通分量**（把 ID 当节点、匹配关系当边，一个连通分量一个 OneID）。八个模式里的多数分歧，都可归结为它们在这两条形式化上做了不同的取舍——但不是全部：3.2.4 与 3.2.5 是打分环节的另外两种实现，分别对应主文件 §2.2.4（端到端匹配概率）与 §2.2.5（LLM 辅助实体解析的概率形式）；3.2.8 向量化 OneID 则建在 §2.2.3（Embedding 相似度）之上。

最关键的一条分界线是：**合并决策有没有传递性**。「强匹配优先」与「概率判定」产出的是**成对判定**——它们回答「A 和 B 是不是同一个人」；「图聚合」产出的是**成对判定加传递闭包**——它额外回答「A~B 且 B~C，那么 A 和 C 也是」。传递性买到的是覆盖率（同一个人经由不同 ID 落地的「桥接」自动闭合），付出的代价是错误也会被传递放大，且决策无法局部撤销。

第二条分界线是**决策发生在哪一层**：是先出边再闭包（强匹配优先、图聚合），还是先打分再切阈值（概率判定、端到端深度匹配），还是把一部分决策外包给复核环节（LLM 辅助）。这条决定了成本花在「算」上还是花在「判」上。

所以正确的顺序是先立约束、再谈模式。同一个「跨端打通」的需求，在有稳定唯一标识的域里答案是强匹配优先，在没有标识的域里答案是概率判定加人工复核队列；而**这两个答案是同一支团队在同一个季度里给出的**——约束不同，不是能力不同。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态（有唯一标识 / 只有模糊字段） | 走成对规则还是走概率打分 | 「先做手机号就够了」——强匹配的覆盖率上限等于该字段的填充率 |
| 访问模式（在线点查 / 离线全量重算 / 图查询） | 决策发生在流式链路还是批式链路 | 「实时和全量都要」——两者在算法上是全局与局部的关系 |
| 变更频率与历史要求 | 合并结论是否需要版本、是否要能回滚 | 「合并是一次性的」——结论会随新证据变化，必须可重算 |
| 一致性要求（可传递 / 只成对） | 用不用连通分量，用不用图的闭包 | 「多跳关联当然要打通」——传递会同时放大覆盖率与错误 |
| 精度与召回的优先级 | 阈值定在哪、中间区间有多宽 | 「先提覆盖率」——误合并的修复成本远高于漏合并 |
| 规模与成本约束 | 用不用 LLM 复核、用不用图计算引擎 | 「把难判的都交给 LLM」——成本与中间区间的对数成正比 |
| 合规与数据边界 | 明文能否出域、能否留存同意记录 | 「打通了再补合规」——拆链与撤回同意是设计约束，不是运营动作 |
| 团队技能与运维能力 | 是否自建图计算 / 是否上服务化 | 「算法对了就行」——OneID 是长期服务，不是一次跑批 |

### 3.2 模式逐个拆解（核心节）

八个模式里，3.2.1 与 3.2.3 都产出成对判定（前者靠规则、后者靠打分），3.2.2 在它们之上加一层传递闭包；3.2.4 与 3.2.5 是打分环节的两种实现（模型与生成式）；3.2.6 至 3.2.8 不改变判定逻辑，而是改变**判定被放在什么链路、什么边界、什么用途上**。下面统一沿用主文件 §2.1 的术语：强匹配（阈值 1.0）/ 弱匹配、Blocking、连通分量（WCC）、LTR。

#### 3.2.1 强匹配优先（Strong-Match-First）

**被什么约束逼出来**：数据里存在**天然唯一且稳定的标识**（手机号、证件号、邮箱），而团队需要可解释、可审计、成本极低的合并。

**结构**：

```sql
-- 分层：强规则先出「边」，弱匹配与图闭包处理剩下的
INSERT INTO id_graph_edge (src_id, dst_id, rule, weight, batch_date)
SELECT a.user_id, b.user_id, 'phone_hash', 1.0, :d FROM user a JOIN user b
  ON a.phone_hash  = b.phone_hash  AND a.user_id < b.user_id
UNION ALL
SELECT a.user_id, b.user_id, 'id_card_hash', 1.0, :d FROM user a JOIN user b
  ON a.id_card_hash = b.id_card_hash AND a.user_id < b.user_id;
-- 命中任一强规则 → weight = 1.0（不参与阈值判定，直接成为边）
```

**为什么这样设计有效**：因为两条随机记录的手机号碰巧相同的概率（u-prob）极低，**单条强规则的似然比就已经远超接受阈值**，所以这一步不需要模型参与——判定可以逐条追溯到「因为手机号相同」，这让它在监管与审计场景里几乎无法被替代。

**代价**：强匹配字段必须先规范化（去空白、大小写、国家码前缀、统一哈希加盐），这条规范化链路本身是一份独立交付物，且它的任何变更都会同时改变所有历史匹配结果；更实质的代价是**覆盖率上限由字段填充率决定**——没有该字段的记录在这一层不产生任何边。

**失效点**：当无强标识的流量占比升高时（PC 游客、未授权设备标识、匿名会话），**「大部分合并在第一步完成」会反转成「大部分流量在第一步入不了门」**，因为强匹配只把「带该标识的记录」连成边，不携带该标识的记录在这一层不参与任何判定，只能落到被排在后面的弱匹配与图传递上——而这两步恰恰被「强匹配优先」的组织方式压到了资源最少的环节。

**真实使用**：广告与 CRM 场景的通行起点，金融 KYC 场景因监管要求以证件号一类强标识为主【经验】。判断是否适用只需一个问题：**这个域里有多少比例的记录带唯一标识**——低于一定比例，就该把重心放到概率判定与图闭包上。

#### 3.2.2 图聚合（Graph Aggregation / WCC）

**被什么约束逼出来**：同一实体经由不同 ID 落地在多处（手机号、设备、邮箱、Cookie），而这些 ID 之间的关系**天然具有传递性**，需要给出一个**全局唯一编号**。

**结构**：

```text
把 ID 当节点、匹配关系当边，连通分量即 OneID

  手机号_A ── 账号_1 ── 设备_X ── 账号_2 ── 邮箱_B
  └────────────── 同一个连通分量 = 同一个 OneID ──────────────┘

  实现：Union-Find（并查集）做全量；图引擎的 WCC（弱连通分量）算子做规模化
  关键：一条边的加入可能把两个原本独立的分量合成一个 → OneID 编号需要整块改写
```

**为什么这样设计有效**：因为连通分量在图上算的是**等价类的传递闭包**，A~B、B~C 会自动推出 A~C，所以「同一个人经不同 ID 落地」的桥接关系不需要额外规则——这正是单条规则永远追不上的那一类覆盖率。

**代价**：计算是**全图问题**，不是局部问题。一条新边连接两个已有大分量时，需要做一次批量 ID 改写（把其中一个分量的全部成员重新指向新的 OneID）；这意味着增量更新不能只写一行，而可能触发一次与分量规模成正比的重编号。并且决策**不可局部撤销**——分量是一个整体，任何一条边的错判会改变整块成员的归属。

**失效点**：当弱匹配边的精度下降时，**「天然处理多跳关联」会反转成「误差沿链路聚合」**，因为传递闭包不做任何误差衰减，链条越长、把两个不同的人连成一片的概率越高，最终会形成吞噬大量用户的「巨型分量」；而一旦形成，整块用户的标签与画像会同时被污染，且由于分量是整体，修复不是改一条边而是一次全图拆分。

**真实使用**：以连通分量作为 OneID 的载体是主流 OneID 平台的共同形态【经验】；图计算框架普遍提供连通分量 / 弱连通分量算子，可按其所用引擎的官方文档核验。本章 [§ 6 落地实践](09-one-id-section-6-sec6.md) 的 4 个案例中，3 个明确以图存储 / 图查询承载 OneID（阿里的「图存储 + 多级缓存」、美团的「图存储 + 双层缓存」、Meta 的「图查询 + 强一致缓存」），另 1 个（字节）的 OneService 自述为「多级缓存 + 分区部署」，图存储不出现在其关键设计里。

#### 3.2.3 概率判定（Probabilistic Decision）

**被什么约束逼出来**：字段模糊、没有唯一标识，但业务需要**可调的精度 / 召回权衡**，且必须能解释每一条判定。

**结构**：

```text
Blocking → 特征 → 打分 → 双阈值（Fellegi-Sunter 的工程落地）

① Blocking：把 O(N²) 的比较降到可算范围
     同手机号前缀 / 同城市 / 同 IP 段 / 同设备型号 → 只比较同桶内的对
② 特征：字段相似度（Jaro-Winkler、编辑距离）、共现（同 IP 段、时间窗）、图结构（共同邻居）
③ 打分：λ = ∏（mᵢ / uᵢ），或由 LTR 模型融合成单一分数
④ 双阈值：λ ≥ 上阈值 → 合并；λ ≤ 下阈值 → 判不同；中间区间 → 人工 / LLM 复核
```

**为什么这样设计有效**：因为判定被写成似然比，**精度与召回的权衡就变成了一个可调的旋钮**（上下阈值），而不需要新增枚举规则——这是它能覆盖「字段不唯一、规则列不全」场景的根本原因：你不需要预先想到所有情况，只需要给出一个阈值。

**代价**：m 概率与 u 概率**必须从标注样本估计**，没有标注就没有可信的 λ；Blocking 本身有漏检，被分桶漏掉的候选对不会被任何阈值救回；双阈值还引入了一个**必须有人处理的中间区间队列**——这个队列不会自己消失，它是一份持续的运营成本。

**失效点**：当标注样本与线上分布发生漂移时，**「概率可控」会反转成「阈值不可信」**，因为 m 与 u 是从样本估出来的参数，样本所代表的分布一旦改变，同一个 λ 数值背后的判定语义也随之改变——阈值没有变，它筛出来的东西变了。

**真实使用**：Fellegi-Sunter 是该形式化的经典来源【公开：Fellegi & Sunter, "A Theory for Record Linkage", JASA, 1969（可按期刊卷期与年份核验）】；工业上在其之上叠 LTR 做分数融合是主流做法【经验】。

#### 3.2.4 端到端深度匹配（Deep End-to-End）

**被什么约束逼出来**：姓名、地址、公司名这类字段的变体（跨语言、缩写、称呼、行政区划变迁）**无法用字段级相似度表达**，而这些字段常常是唯一可用的证据。

**结构**：

```text
把「记录对」当成一个文本分类任务（Ditto 风格）

输入序列：
  [COL] phone [/COL] 138xxxxxxxx [COL] name [/COL] 张三 [COL] city [/COL] 北京
  [SEP]
  [COL] phone [/COL] 138xxxxxxxx [COL] name [/COL] Zhang San [COL] city [/COL] Beijing
输出：match / non-match

关键：列名本身也进序列，让模型知道「现在在比哪个字段」
```

**为什么这样设计有效**：因为记录对被拼成同一个 token 序列、列名也作为 token 进入，模型可以在属性之间做**交叉注意力**，所以「手机号相同 + 姓名跨语言」这类跨字段证据能被联合使用，而不是每个字段各自打分再线性融合。

**代价**：需要**对级别的标注数据**；推理是每个候选对一次前向传播，成本随候选对数量线性增长，因此它必须挂在 Blocking 之后；并且模型只回答「这一对像不像」，**不提供合并的传递闭包**——闭包仍要由图聚合或后续步骤补上。

**失效点**：当 Blocking 的召回不足时，**「捕捉复杂语义」会反转成「语义没有机会被用上」**，因为深度模型只对进入候选集的对打分，被分桶漏掉的对再相似也永远不会被判分——模型越强，越容易让人忽略它上游的漏检。

**真实使用**：把实体解析做成序列化文本分类任务，是这条路线被广泛引用的代表做法；采用它的多是学术与工业混合的实体解析团队，主要在**公司名、地址这类长文本字段是主要证据**的场景里使用。代表工作是 Yuliang Li 等的论文《Deep Entity Matching with Pre-Trained Language Models》（常被以其模型名「Ditto」引用）【公开：Yuliang Li 等, "Deep Entity Matching with Pre-Trained Language Models", 2020】——发表会议在不同转述中口径不一，请按题名与作者检索原文核验，不要按二手转述的会议名对号；本主题下另有若干同类工作可按「deep entity resolution」检索核验。

#### 3.2.5 LLM 辅助生成式（Generative LLM-Augmented）

**被什么约束逼出来**：一部分**边界样本**连人工复核都难以判定，而它们集中在长文本、跨语言、非结构化字段上，没有可枚举的特征。

**结构**：

```text
三档分流：让 LLM 只碰它擅长的那一档

第一档 分数 ≥ 高阈值      → 自动合并        （不送模型）
第二档 分数 ≤ 低阈值      → 自动判不同      （不送模型）
第三档 高阈值 > 分数 > 低阈值 → 送 LLM 复核
        输入：记录对 + 判定要求（要求输出结构化 JSON）
        输出：decision（merge / split / unsure）+ confidence + reason
        副产品：reason 可入库，成为合并决策的可解释依据

→ 成本模型：总成本 ∝ 落在第三档的对数 × 单次调用成本
```

这条带取多宽是一个经验参数：本主题常见的落法是把 **0.6–0.85** 划为需要复核的边界区间——落在这条带里的对送 LLM 或人工复核，带宽直接决定队列长度与账单规模【经验】。

**为什么这样设计有效**：因为 LLM 的判定是「读完整个记录再生成结论与理由」的生成式决策，它能调用属性之间的常识关联（称呼、缩写、行政区划沿革），这类证据**无法被字段级相似度特征表达**，也无法被预先枚举成规则。

**代价**：单次判定的时间与金钱成本比传统打分高若干数量级【经验】；输出是自由文本，必须用 schema 约束成结构化的三态决策才能进入流水线，否则下游无法消费；此外它引入了一个新的不确定性来源——同一个对在不同调用下可能给出不同结论，需要靠低温度与一致性抽样来压制。

**失效点**：当阈值带被放宽时（为了提召回而调低上阈值），**「只复核极少数边界样本」会反转成「复核量随带宽线性膨胀」**，因为落在中间区间的对数由阈值宽度直接决定，而每一对都是一次完整的 LLM 调用——带宽翻倍，账单与队列同时翻倍，且这笔成本与「样本有多难」无关。

**真实使用**：用 LLM 复核边界样本、而不是让它处理全部候选对，是【经验】主流做法；多家云厂商的实体解析服务已把变体识别纳入产品能力，具体覆盖范围与定价请以各厂商实体解析产品文档的当前版本为准。

#### 3.2.6 实时增量（Streaming Incremental）

**被什么约束逼出来**：OneID 的判定**依赖全局图**（一条新边可能改变一整块归属），但业务要求事件到达时就能立刻查到「这个设备属于哪个 OneID」。

**结构**：

```text
双轨各取一个性质

  批式轨（每日/每小时）：全量重算 → 全局一致、可纠错、可回滚的 OneID 快照
  流式轨（事件驱动）   ：新 ID / 新边到达 → 增量合并 → 立即入图，低延迟可查
  查询侧               ：优先读流式（即时），并周期性被批式快照校准覆盖

  配对方式：批式产出的快照是「真相」，流式是「尚未被校准的即时视图」
```

**为什么这样设计有效**：因为「全局一致」与「即时可用」在算法上不可兼得——全量重算是全局操作，增量合并是局部操作——所以系统把它们**分配给两条链路，各取一个性质**，再让查询侧按场景选择读哪一条。

**代价**：两条链路必须共享同一套判定规则，否则结论会分叉；增量侧必须处理「一条新边连接两个已有大分量」的重编号问题（一次批量 ID 改写）；批式与流式的口径一致性需要持续的回归测试来维持，这是一笔长期成本而非一次性投入。

**失效点**：当两条链路的规则演化不同步时，**「实时加最终一致」会反转成「同一个设备在两条链路指向不同的人」**，因为增量链路用的是「事件到达时生效的规则」、批式链路用的是「当前规则」，一次重算会把增量期内产生的全部合并结论整段改写——如果下游已经按旧结论落了库或发了券，这份分歧不会自动收敛。

**真实使用**：批流双轨并以批式快照校准是 OneID 平台的常见形态【经验】。判断是否需要双轨，看一个问题：**业务能不能接受「今天答的和明天答的不一样」**——不能，就必须有批式校准；能，则单轨增量更省。

#### 3.2.7 隐私计算 OneID（Privacy-Preserving OneID）

**被什么约束逼出来**：参与方的**明文标识不能出域**（跨企业数据合作、广告归因、跨境合规），但双方确实需要对同一批人做打通。

**结构**：

```text
三种实现路径，共同点是把「数据出域」换成「计算出域」

① PSI（私有集合交集）：双方各自加密自己的 ID 集合，求交，不交换明文
② 联邦学习：各方本地训练 ID-Mapping 模型，只交换参数更新，不交换样本
③ TEE（可信执行环境）：把计算搬进可信硬件，明文只在隔离环境内出现

前提（最容易被忽略）：双方必须先对齐同一个 ID 的表示方式
   —— 国家码、空格、大小写、哈希算法与加盐方式，全都必须一致
```

**为什么这样设计有效**：因为 PSI 求的是**加密表示的精确匹配**，双方最终只得到「哪些记录对得上」这一结果，所以可以在不交换明文标识集合的前提下完成打通——出域的是计算结果，不是数据本身。

**代价**：密文运算与多轮交互使开销显著高于明文 JOIN【经验】；交集结果本身仍是信息（交集大小、命中模式都会泄露一定量的分布信息）；此外它要求双方在协议之外先完成一轮工程对齐，这份协调成本常常高于计算成本。

**失效点**：当双方对「同一个 ID」的表示不一致时，**「不暴露明文也能打通」会反转成「算完一轮交集为空」**，因为 PSI 是精确匹配算法、没有任何模糊匹配能力，任何规范化差异都会把本该匹配的记录判为不匹配；更麻烦的是，在密文下这种失败与「确实没有交集」在结果上完全无法区分，只能靠双方离线比对样本才能定位。

**真实使用**：跨企业数据合作与广告归因是主要场景【经验】；各家隐私计算平台的具体能力边界与性能特性差异较大，请以其官方文档的当前版本为准。

#### 3.2.8 向量化 OneID（Embedding-based OneID）

**被什么约束逼出来**：业务要回答的是「**哪些用户彼此相似**」（分群、Look-alike、召回），而不是「这两个是不是同一个人」——前者没有唯一正确答案，也写不出规则。

**结构**：

```sql
-- 把 OneID 当作向量的主键承载，而不是当作合并判据
CREATE TABLE oneid_embedding (
  one_id      BIGINT,
  window_date DATE,            -- 向量按时窗重算（画像会变，向量会漂）
  embedding   VECTOR(256),
  PRIMARY KEY (one_id, window_date)
);
-- 近邻检索（ANN，近似而非精确）
-- SELECT one_id FROM oneid_embedding
--  WHERE window_date = :d ORDER BY embedding <-> :q LIMIT 100;
```

**为什么这样设计有效**：因为 OneID 聚合出的行为与属性被压成一个稠密向量，**「找相似」就变成了向量空间的近邻检索**，一次查询即可返回 Top-N 候选，而不需要为每一类相似度定义一条规则——这正是它在分群与召回场景不可替代的机制。

**代价**：向量**按时窗重算**，同一 OneID 在不同时窗的向量不可直接比较（画像漂移）；ANN 索引返回的是近似近邻，召回率不是 100%；向量的可解释性低于规则，业务方很难回答「为什么这两个人相似」。

**失效点**：当把 embedding 相似度接到**合并决策**上时，**「能表达相似」会反转成「误合并率上升」**，因为 Look-alike 的语义是「像，但不是同一个」，而合并判据要求的是「是同一个」——两个判定方向相反，越相似的用户越容易被错合并；更糟的是这类错误集中在人群密集处，而那恰是标签与分层最需要准确的部分。

**真实使用**：把 OneID 作为向量检索的主键承载（用户向量、内容向量）【经验】。使用它之前先确认一件事：**这个场景要的是「像」还是「是」**——答案是「是」，就不该用这条模式。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 有唯一位标识、要求可审计、成本敏感 | 强匹配优先（+ 图闭包） | 概率判定在唯一标识上属于过度设计，且引入了不可解释的分数 | 带唯一标识的记录占比 |
| 标识分散、需要跨多跳收敛到一个编号 | 图聚合（连通分量） | 成对规则无法闭合「A~B、B~C」这类桥接 | 是否需要传递性 |
| 无唯一标识、字段模糊、需要可调权衡 | 概率判定（Blocking + 双阈值） | 强匹配在此域几乎不产生边 | 是否有标注样本可估 m / u |
| 姓名 / 地址等文本变体是主要证据 | 端到端深度匹配 | 字段级相似度无法表达跨语言与称呼变体 | Blocking 召回是否足够 |
| 边界样本人工也难判、字段非结构化 | LLM 辅助生成式 | 全量交给 LLM 成本不可控 | 边界样本占比与预算 |
| 在线点查要求毫秒级、判定依赖全图 | 实时增量（批流双轨） | 单轨批式无法满足在线时效 | 业务能否接受当日不一致 |
| 明文标识不能出域 | 隐私计算 OneID | 明文 JOIN 直接违反合规边界 | 数据能否出域 |
| 要回答「谁和谁像」而非「是不是同一人」 | 向量化 OneID | 规则与图都回答不了相似度连续值 | 目标是「像」还是「是」 |
| 多端多业务、规模到十亿级 | 图聚合 + 实时增量 + 服务化 | 单靠批式全量无法支撑在线查询 | 在线 QPS 与可接受延迟 |

表里最常被误选的一对，是**「图聚合」与「概率判定」的先后关系**被搞反。很多团队先上图、把弱匹配边按一个偏低的阈值直接灌进图里，指望闭包来提覆盖率——实际后果是**误合并被传递放大**：单条边的错误率在图里不是相加而是沿链传播，最终形成巨型分量，而这类错误无法通过调阈值回退（阈值已经写进边里了）。正确的顺序是先用概率判定把边的精度压到可信范围，再让图去做闭包。判据很直接：**图上任何一条边的错误，都会被当作整块的错误结算。**

按业务场景对号入座时，表是一样的：电商跨端打通、客户 360 / CRM 会员统一落在「有唯一标识」与「需跨多跳收敛」两行；广告投放闭环（媒体 ID 与 CRM ID 异构）落在「无唯一标识 + 边界样本占比可控」；金融风控（一人多户）与反欺诈（一机多号、设备农场）以强标识为主干、设备指纹与行为序列补边；媒体内容 ID 与商品 OneID（SKU / SPU 统一）是同一条方法论平移到非人实体上——它们的判据是名称与属性变体，因此走概率判定或端到端匹配，而不是证件号；跨境业务（多语言地址）落在「文本变体是主要证据」；智能体长期记忆（Agent Memory）落在「要回答『谁和谁像』」——它要的是按人隔离记忆的相似检索，而不是判定两个会话是不是同一个人。

### 3.4 组合模式：真实系统不会只用一种

真实系统里极少出现「只用一条模式」的情况，更常见的是**判定、闭包、时效、边界**四件事分别由不同层承担。下面三条组合覆盖了绝大多数落地形态。

**组合一：强匹配优先（出高置信边）+ 图聚合（做传递闭包）。** 职责边界是：强匹配负责**精度**，只产出 weight = 1.0 的边；图负责**覆盖率**，把同一个人经不同 ID 落地的桥接闭合起来。组合的运维代价是两件事：规范化链路（决定强匹配能出多少边）与巨型分量监控（决定图会不会失控）。适合规模：**万级到亿级实体、多端但以注册用户为主的业务**。

**组合二：概率判定（覆盖主体）+ LLM 复核（只判边界）。** 职责边界是：模型负责**吞吐与成本**，处理绝大多数对；LLM 负责**疑难与可解释性**，只处理落在双阈值中间区间的那一小部分，其输出的理由还顺带成为合并决策的审计依据。组合的运维代价是中间区间队列本身——它的长度会随阈值带宽变化，必须有人负责它的积压与质量抽检。适合规模：**候选对量级在模型打分能力范围内、且团队有能力维护标注集与阈值回归**。

**组合三：图聚合（底图）+ 实时增量（时效）+ OneID 服务（接口）。** 职责边界是：批式全量重算给出**全局一致且可回滚**的快照，流式增量给出**即时可用**的视图，服务层对上层屏蔽两者差异并提供统一的查询与订阅接口。组合的运维代价最高：两条链路必须共用同一套判定规则、增量侧要处理分量重编号、服务层要定义清楚「读到的是即时视图还是已校准快照」——这个语义必须在接口上写明，否则下游无法判断结果的可信度。适合规模：**十亿级实体、多端多业务、在线查询与离线分析并存的平台**。

三条组合有一个共同的失败前提：**把「一次性打通」当成交付终点**。OneID 的结论会随着新证据、规则变更与合规要求持续变化，因此组合方案里必须内建「重算 + 回滚 + 审计」三个动作，否则第一次错误合并就会变成一次无法收敛的事故。

### 3.5 反模式与失效分析

下表覆盖本主题的 8 个反模式，每条按「症状 → 后果 → 成因 → 修法」四段给出，「后果」一栏写成机制层面的结果。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 过度依赖强匹配 | 无强标识的流量在一人一档里长期为空；PC 游客与未授权设备覆盖率显著低于注册用户 | 强匹配只把「带该标识的记录」连成边，不携带标识的记录不参与任何判定，覆盖率上限被字段填充率锁死 | 强匹配见效最快，容易把它当成整套方案 | 补设备指纹 + 行为序列 + 图传递，把强匹配降级为「高置信边来源」 |
| 弱匹配阈值定得过低 | 为提覆盖率把阈值从 0.9 调到 0.6，误合并告警随之上升 | 阈值直接决定边的密度，边密到一定程度后传递闭包会把大量不同的人连成一片巨型分量，且由于边已写入图，无法靠回调阈值回退 | 覆盖率是可观测指标，误合并常常要等业务侧反馈才可见 | 先定精度下限再谈召回；阈值调整必须走离线回放评估，不能直接上线 |
| 不做合并冲突检测 | 同一个 OneID 下挂着生日相差数十年的证件号；同一人的性别在两个来源上不一致 | 冲突证据被丢弃后，后续所有标签都建立在一个自相矛盾的主体上，误差会随聚合链路放大且无法定位 | 合并流程只关注「怎么连起来」，没设计「连起来之后怎么校验」 | 合并时触发冲突检测（出生日期、性别、证件类型等强矛盾字段），矛盾超阈值即拒绝合并并进入复核 |
| 一次性大合并、无回退机制 | 某次跑批后一人一档的主体数骤降一个量级，且说不清是哪些边引起的 | 连通分量是整体，没有版本与留痕就无法定位是哪条边造成的变化，拆分只能靠全量重算 | 把合并当成一次性的数据处理任务，而不是一个持续演化的状态 | 维护图版本号与合并留痕（合并原因、置信度、批次），保留可回滚的上一版快照 |
| 用 UUID v4 当 OneID 写库 | 主键列是无序随机值，写入热点集中、索引页分裂频繁、存储占用明显偏高 | 无序主键在 B 树索引上退化为随机插入，页分裂与回表成本随数据量放大 | 把「全局唯一」当成主键的唯一要求，忽略了「有序」对存储结构的价值 | 用 ULID / UUID v7 / 雪花 ID 这类时间有序主键；老系统兼容雪花 ID |
| 服务化但没考虑回溯 | 上游数据被删除后，OneID 表里残留指向已不存在实体的映射，且没有清理路径 | 死链不会自己消失，反向查询会返回不存在的实体，随时间累积成稳定的错误率 | 服务化聚焦在「查得到」，没有同时定义「什么情况下该失效」 | OneID 表接入 CDC、软删除与周期性对账，把「上游删除 → 映射失效」做成常规链路 |
| 只做用户 OneID，不做商品 / 订单 / 设备 OneID | 跨域推荐里同一商品在不同域不同名；跨设备风控只能看到单设备 | 只有用户这一条主轴被打通，其它实体仍是孤岛，跨实体的关联查询无从建立 | 用户维度收益最直接，其它实体的价值要等到跨域场景出现才显现 | OneID 是多实体工程（人 / 设备 / 商品 / 订单 / 内容），按同一套方法论平行建设 |
| 完全交给 LLM 解决 | 候选对的总量与模型调用量处于同一量级；单次跑批成本与业务量线性绑定 | LLM 的调用成本与候选对数量成正比，而实体解析的候选对数量本身就极大，成本随规模不可控 | 用演示样例验证效果时，小规模下 LLM 表现最好，掩盖了成本随规模线性增长这件事 | 传统模型处理绝大多数对，LLM 只复核边界样本；用三档分流把成本锚定在中间区间的对数上 |

两个最危险的反模式值得单独展开。

**「弱匹配阈值定得过低」在生产中的典型暴露方式是「静默污染」**：调低阈值的那次变更会立刻提升覆盖率，指标变好看；真正的代价要等到下游标签、画像、归因开始出现无法解释的偏差时才浮现，而那时错误的边已经进了图，靠把阈值调回去并不能让它们消失——**已经合并的主体不会自己分开**。它的成因是把覆盖率与召回率当成了同一件事：覆盖率看得见，误合并率通常要等业务方投诉才看得见，而两者的调节旋钮是同一个。

**「一次性大合并、无回退机制」的典型暴露方式是「说不清是哪一次变更造成的」**：没有合并留痕时，一人一档的主体数发生跳变，团队只能看到结果变了，无法回答「是哪条边带来的」。这使得事故复盘退化为「重跑一遍看看」，而重跑本身又会引入新的差异。它的成因是把合并当成数据处理任务的一次执行，而没有意识到**合并结论是一个需要版本管理的状态**——凡是会随新证据变化的状态，都必须能被回放和回滚。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的。跨过某个阈值后，原来正确的结构会开始反向收费。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 候选对从万级涨到亿级 | 概率判定全量打分 | Blocking 桶内对的数量随数据量平方级增长，打分时间不可控 | 加强 Blocking 维度 + 候选对分层抽样 | 漏检率上升，需要重新标定召回 |
| 弱匹配边密度上升 | 图聚合（单层阈值） | 传递闭包把边密度放大成分量爆炸，出现巨型分量 | 边分级 + 分量规模上限 + 人工复核闸门 | 需重跑历史图并重新分配 OneID |
| 从单端到多端、多业务 | 强匹配优先 | 无标识流量占比升高，强匹配覆盖率见顶 | 概率判定 + 图闭包 | 需要标注集与阈值标定周期 |
| 在线 QPS 从百级涨到十万级 | 批式全量重算 | 全量重算的窗口期无法满足在线查询时效 | 批流双轨 + OneID 服务化 | 两条链路的规则同步与回归测试 |
| 单次跑批成本与业务量线性绑定 | LLM 全量复核 | 成本随候选对数量增长，规模越大越不可承受 | 三档分流，LLM 只碰中间区间 | 阈值带宽需重新标定，边界样本口径变化 |
| 从内部打通到跨企业合作 | 明文 JOIN | 明文标识出域直接触发合规问题 | PSI / 联邦学习 / TEE | 双方需先对齐 ID 规范化与哈希方案 |
| 从「查得到」到「可审计、可撤回」 | 无版本的合并状态 | 无法回答「这条合并的依据是什么、能否撤回」 | 合并留痕 + 图版本 + 撤回链路 | 需为历史结论补建留痕 |

### 3.7 自检清单

以下 12 条都是可验证的问题，任意一条答「否」都应记录为待处理项。

1. 一人一档主体上，是否存在**没有任何强标识**的记录？若这些记录占比显著，强匹配优先就不足以支撑覆盖率，须确认弱匹配与图闭包已就位。
2. 图上的弱匹配边，其阈值是**离线回放标定**出来的还是经验设定？后者即为「阈值定得过低」的高危信号。
3. 是否监控**最大连通分量占总体量的比例**？缺少这个指标，巨型分量的形成不会被及时发现。
4. 合并流程里是否有**冲突检测**（出生日期、性别、证件类型等强矛盾字段）？没有即意味着矛盾证据被静默丢弃。
5. 每条边是否留存**合并原因与置信度**？缺这两列时，任何回滚都无法定位到具体变更。
6. 是否有**可回滚的上一版快照**？只保留当前状态，等于把全量重算当作唯一的修复手段。
7. OneID 主键是否为**时间有序**（ULID / UUID v7 / 雪花 ID）？使用随机主键须确认写入放大已被评估。
8. 上游记录被删除时，OneID 映射是否有**明确的失效路径**（CDC + 软删除 + 对账）？没有即为死链累积。
9. 若使用 LLM 复核，其调用量是否被**锚定在中间区间的对数**上，而不是候选对总量上？后者会让成本随规模线性上涨。
10. 若涉及跨企业打通，双方是否已就 ID 的**规范化方式与哈希方案**书面确认？PSI 的精确匹配对表示差异零容忍。
11. 使用向量相似度的场景，其判定目标是**「像」还是「是」**？把相似度接到合并决策上，方向即为反的。
12. 是否写明了「读到的是即时视图还是已校准快照」？这个语义未在接口上声明时，下游无法判断结果的可信度。

其中第 3、第 6 两条最常被跳过，因为它们问的不是算法，而是**运行状态**。但从事故的分布看，这两条恰恰决定了 OneID 能否在出错后回到正轨。

### 3.8 小结

把本节八个模式收成一句话：**它们全都是「怎么在精度、覆盖率与成本之间选一个落点」的不同兑现方式**，差别只在决策发生在成对判定、全局闭包，还是复核环节。下表按约束重排一遍，便于在选型会上直接对照。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 有唯一标识、要可审计 | 强匹配优先 + 图闭包 | 似然比远超阈值，判定可逐条追溯到具体字段 |
| 需要跨多跳收敛到一个编号 | 图聚合（连通分量） | 传递闭包自动闭合桥接关系，覆盖率不依赖枚举规则 |
| 无唯一标识、要可调权衡 | 概率判定（Blocking + 双阈值） | 阈值是可调旋钮，不需要预先枚举所有情况 |
| 文本变体是主要证据 | 端到端深度匹配 | 列名进序列后，跨字段证据可被联合使用 |
| 边界样本人工难判 | LLM 辅助生成式 | 生成式判定能用常识关联，且输出理由可入审计 |
| 在线点查依赖全图 | 实时增量（批流双轨） | 全局一致与即时可用分属两条链路，各取一个性质 |
| 明文不能出域 | 隐私计算 OneID | 出域的是计算结果而非数据 |
| 要回答「谁和谁像」 | 向量化 OneID | 相似度是连续值，规则与图都表达不了 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**「合并决策要不要传递」**——要传递就得上图（覆盖率上涨、错误也被放大且不可局部撤销），不传递就停在成对判定（精度可控、覆盖率有上限）。所有失败模式最终都能回溯到这条约束被误用：要么在边精度不足时就上传递（巨型分量），要么该传递时仍停在成对规则（覆盖率见顶）。
