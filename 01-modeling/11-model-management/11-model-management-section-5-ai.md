## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

模型管理这一节最容易被写成一张清单：LLM 辅助规范检查、Agent 自动评审、自然语言建模、AI 增强目录、GraphRAG、数据契约规范并列排开。这张清单的问题不是内容错，而是**没有时间维度**：「已经能挂在 CI 上跑的静态检查」与「只在厂商演示里出现过一次的 Agent 评审」被写成同类项，读者据此排路线图必然踩空——把第三类排进 Q1，等于给团队安排一个交付不了的里程碑，而失败的原因会被归到「团队执行力」，掩盖真正的因果。

本节改用 L1/L2/L3 三级，级差由三条**可核验**的事实决定，而不是「感觉成熟」：

- **L1 生产可用**：已有正式 release note、有第三方（非厂商）公开生产案例、接口稳定。可以排进路线图。
- **L2 可试点**：可用但接口或生态未稳，或只有厂商自有案例，或只在小规模被验证。可以做 PoC，不要做核心依赖。
- **L3 观望**：只有路线图、论文、厂商演示或预览特性。记录，不要在架构里预留假设。

第二类要拆开的混淆是**能力名与产品名**。同一个能力在不同平台的命名不同，按名字去找产品会漏掉真正的机制；同一个产品名也可能指代不同形态（内嵌的单机引擎与独立服务的目录产品都可能被叫作 Catalog）。本节一律写能力名；产品名只在「证据与来源」里出现，且只写到能核验的粒度——厂商官方材料 + 年份。版本号不确定就不写版本，改为「在某年前后进入预览」这类可核验的区间表述。

第三类混淆是本主题特有的：**「模型管理的 AI 化」常被等同于「让 AI 写模型」**，但变化实际发生在三个不同位置——

- **生成侧**（写 DDL）：接口边界改变；
- **检查侧**（读 DDL 做形式判定）：成本函数改变；
- **检索侧**（把元数据变成可检索、可推理的语料）：检索键改变。

三处机制不同、成熟度也不同：检查侧最接近可用（判定规则本来就在人脑里，只是人读得太慢），检索侧卡在新鲜度而非能力，生成侧则是「形式可生成」属 L2、「语义可负责」属 L3，两者被混成一句话。

判断一个方向值不值得投入，先看它有没有碰到本主题的**既有卡点**（§1.1、§1.2、§2.2）。模型管理的卡点从来不是「没有工具」，而是四件事：

- **同名不同义 / 同义不同名**：各自建模、各自命名导致口径冲突，模型数量一多就不可收拾；
- **变更影响不可枚举**：改动前列不全下游，事故靠事后发现；
- **责任不落地**：Owner 写团队不写人，出问题无人负责；
- **合规不可自证**：来源、修改人、修改时间无法逐条追溯。

前沿之所以是前沿，判据就在这里：一个方向只有在**改变上述四条之一的机制**时才值得投入；只让界面更好看的，本节一律标为接口改良。

本节所有数字按三档标注：**【公开】**（带来源 + 年份）、**【推算】**（写出推导链）、**【经验】**（用区间）。凡是给出无来源精确数字的说法（形如「准确率提升 X%」），本节一律不采信——本主题的 AI 能力评测缺少公开标注集，任何精确率数字都无法核验。

表前给一条通用判定方法：任何一个声称「AI 重建模治理」的能力，先问它把你的**模型事实放在了哪个接口上**——PR 评论、公开 API，还是只有一个网页对话框。只有落在 PR 或 API 上的能力才能被别的系统消费，才可能进路线图；只能落在对话框里的，给人的操作加了个助手，没有给系统加任何能力。

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 契约文件化 + CI 校验（声明式模型契约：列名 / 类型 / 可空 / 分级） | **L2** | ① 有正式公开发布条目（Bitol 的开放数据契约规范，2023–2024 年间公开，发布日期以项目官方页面为准）；③ 接口稳定——列名 / 类型 / 可空 / 分级为稳定字段，且不依赖任何 AI 能力；缺②：无具名的非厂商组织采用案例，采用痕迹只在公开仓库的契约工件里 | 现在就做——它是本节其余方向的前提 |
| LLM 辅助规范检查（读 DDL 判命名、注释、Owner、分级缺失） | L2 | 有厂商官方发布说明；无第三方公开的覆盖率与误报率；同一输入两次结论可能不同 | 挂在 PR 上出建议，不做阻断 |
| AI 增强目录（自动生成标签、描述、口径说明） | L2 | 同上；生成的描述未经人签署就没有治理效力 | 只对「描述缺失」的资产启用，入库前必须有人确认 |
| 自然语言建模 NL2Model（自然语言 → DDL / SQL 草案） | L2 | 生成物的**形式**正确性可自动验证；**业务语义**正确性无外部标注 | 只允许产出 PR 草案，禁止直连生产库 |
| Agent 自动评审与自进化治理（读血缘图推演影响面、主动建议变更） | L3 | 无第三方公开生产案例；其上游「字段级血缘」在多数组织尚未达标 | 记录，不在架构里预留假设 |
| 语义图层与图检索（目录向量化、本体化、GraphRAG） | L2 | 论文与开源实现公开可核验；产品侧多为厂商自有案例；新鲜度问题未解 | 先解决元数据自动采集与新鲜度，再谈图 |

表后一句话说明本主题的级别分布：**本主题目前没有任何方向满足 L1 的三条判据，最接近的是「契约文件化 + CI 校验」（缺第二条，L2），而它恰恰不是 AI 方向**。这不是怀旧，而是因果：没有机器可读的契约，「AI 检查」只能对无标注文本猜，「影响面推演」也没有可比对的基准。其余五个方向也停在 L2/L3，原因各不相同——检查与目录缺第三方生产数据，NL2Model 缺语义评测，Agent 自进化缺上游数据（字段级血缘），图检索缺新鲜度机制。**五个方向缺的不是同一件东西（第三方生产数据 / 语义评测 / 上游血缘 / 新鲜度机制），意味着它们的成熟时间不会同步**，把它们捆成「AI 治理套件」一起采购，一定会被最慢的那个拖住。

契约这一行停在 L2 的理由要说清楚，否则「缺第二条」会被读成标准太严：**本节确实没有列出具名的非厂商组织采用案例**。契约的采用痕迹留在公开仓库里的工件上（YAML 声明一类，与 CI 配置放在一起），采用者通常不会为它单独写一篇署名案例，公开可检索的具名案例因此很少；但判据要的就是具名来源，写不出就记 L2，本节不为它重新定义判据。对读者而言，判断这一行值不值得先做，最省的办法不是去找别人的案例，而是在自己的仓库里挑一张核心表写一份契约、接进 CI，用一次真实的违约失败验证它——这一次失败比任何外部案例都更能说明这一层在你们的环境里成不成立。

### 5.2 演进方向逐条拆解（核心节）

本节把方向合并为四条主线，合并依据是**机制相同**而不是主题相近：同一个机制拆成几条写，会让读者以为有四个独立的投入项，实际上它们共用同一套前提、同一批代价。

#### 5.2.1 LLM 辅助规范检查与 AI 增强元数据

- **旧做法与它的卡点**：命名规范、字段注释、Owner、敏感分级这些要求早就写在制度里（命名规范与 Owner 制度见 §4.2；字段注释与敏感分级的检查项见 §4.5 的 LLM 检查 prompt），卡的是**执行成本随模型数量线性增长**——10 万张表的抽查覆盖率取决于评审人力，而人力不随表数增长。所以问题从来不是「不知道规范」，是「读不完」：制度存在而覆盖不足，两者并不矛盾。附带一个更隐蔽的卡点：抽查制下**未覆盖区间的风险不可见**，没人知道没被抽到的那部分表里有什么，所以「合规」这个词在抽查制下没有准确含义。
- **AI 改变了什么机制**：把「人读 DDL」换成「模型对全量 DDL 做一次批量分类」。落在机制上是**成本函数的变化**（评审的边际成本从「每文件几分钟」压到「一次扫描的算力费」），不是判定标准的变化——判定标准仍由人写在规范里，模型只是执行者。这是本方向唯一值得记住的一句话：它没有让判定变准，只让判定变便宜。
- **由此得到的**：因为边际成本被压到接近零，所以「全量检查」第一次成为可选项，制度可以从「季度抽查」变成「每次 PR 重复执行」。这是因果，不是程度差别：抽查制下必然存在未覆盖区间，而覆盖率本身就是治理效果的上限——覆盖不到的地方，等价于没有制度。
- **由此付出的**：
  - **确定性下降**：同一份 DDL 两次运行可能给出不同结论。若直接接成 CI 阻断，就会出现「同名变更这次拦下次放」，团队在三个月内一定会绕过它——被绕过的门禁比没有门禁更糟，因为它让「合规」变成形式。
  - **新的成本项**：低置信度建议占用的是最稀缺的资源——评审人的注意力。当建议量大到无法逐条读时，团队的行为是「全部忽略」，于是密度越高、价值越低。
  - **供应商锁定**：规则行为随模型换代漂移，而规范本应是稳定的。把规范检查绑死在某个模型服务上，等于把治理标准的稳定性交给了外部发布节奏。
- **证据与来源**：厂商官方层面有公开材料（目录与模型平台内置的助手类能力：阿里 DataWorks AI Copilot、Atlan AI、Secoda AI、Databricks Unity Catalog 的 AI 辅助一类，标注为 2024 年前后，本节的核验入口见 §5.4 二；「编辑器 + 建模工具」的组合属社区工作流，不是单一产品特性）。**无第三方公开的覆盖率与误报率数据**——凡给出「准确率 X%」的说法，先看它的标注集是否公开；本主题的公开标注集基本不存在，所以这类数字无法核验。
- **判定方法与成本推算**：拿你们已知的 200 条违规 DDL 做一次回放，统计漏报与误报，用你自己的数决定是否进 CI——这是唯一有意义的验收方式。【推算】全量扫描的成本量级：假设 10 万张表、平均每表 DDL 约 500 token【经验：中小型数仓每表 DDL 的经验区间是数百 token，本节按 500 作量级取值】，单次全量输入约 5×10⁷ token（10 万 × 500，档位为量级估计）；按 2024-2025 年主流商用 API 每百万输入 token **数美元**量级（取 2～9 美元）【经验】，单次全量扫描约**百余至数百美元**【推算：5×10⁷ ÷ 10⁶ = 50（百万 token）；50 × 2～9 ≈ 100～450 美元】；若改用每百万输入 token **数十美元**的更强模型档位（取 20～90 美元）【经验】，则为**千余美元**量级【推算：50 × 20～90 ≈ 1000～4500 美元】。两个档位都写出来，是因为「用哪个模型做这件事」能把结论差一个数量级——只扫本次变更的增量方案成本可忽略，而「每日全量扫一次」在低价档是每月数千美元量级、在强模型档是每月数万美元量级，属需要预算决策的持续支出，单价须按季度重核。
- **成熟度**：**L2**（有官方说明、无第三方生产量化证据、判定不确定）——可以试点，不可作为门禁。

本方向与旧做法的差别可以压成一张表；注意最后一行才是真正的取舍所在：

| 维度 | 人工抽查 | 机器全量检查 |
| --- | --- | --- |
| 覆盖率 | 取决于评审人力，通常远低于 100% | 可接近 100%（解析失败的除外） |
| 边际成本 | 随表数线性增长 | 随 token 量增长，量级低得多【推算见上】 |
| 结论稳定性 | 稳定（人的规则一致） | 不稳定（同一输入两次可能不同） |
| 失败形态 | 漏检（未覆盖的区间没人看） | 误报（噪声淹没真问题） |
| 适合挂在哪 | 季度审查报告 | PR 建议（不是阻断） |

#### 5.2.2 Agent 自动评审与自进化治理

- **旧做法与它的卡点**：影响面分析并不缺工具，血缘图反向遍历早就能列出下游（见 §2.3 影响分析）。卡点在**把影响面结论变成评审意见**这一步仍然是人做的：人看图、写评论、判断「这算不算大」。判断权留在岗位上而不是系统里，于是评审质量取决于当周谁值班、谁熟悉这块模型。第二个卡点更根本：评审是**串行瓶颈**——评审人必须逐个上下文切换，模型数量一涨，排队就发生，最后被简化为「看一眼没大问题就过」。
- **AI 改变了什么机制**：把「人看图下判断」换成「模型读图 + 读变更说明 + 生成评审意见草案」。落在机制上是**人机分工的改变**（人从写意见变成仲裁意见），不是判定标准的改变；但对外它常被描述成「评审自动化」，这个落差正是下面代价的来源。这一点必须说透，否则验收标准会被定错——它的产出是**候选意见**，不是**结论**。
- **由此得到的**：因为第一遍意见不再占用人的写作时间，所以评审响应可以从「天」压到「小时」，人的时间集中到有争议的少数条目上。这是注意力重新分配带来的收益，而不是判断力提升带来的——两者的可持续性差别很大：前者随模型数量增长仍然有效，后者依赖人的经验积累。
- **由此付出的**：
  - **责任真空**：Agent 给出「无影响」而实际有影响时，追责对象是一个无主体的系统。组织只能把责任压回提变更的人，于是评审退化为「我提交、它说没问题、我签字」——签字的人没有真的审过。
  - **漏报不可见**：缺项的影响面清单，看起来和完整清单一模一样。验证它的成本高于自己重算一遍，所以实际上没人验证；这是本方向最贵的代价。
  - **没有反馈闭环**：模型输出的对错无人标注回流，评审质量不随时间上升。这与 §2.2 里「∀ e ∈ E(t+1)：影响分析已执行」这条约束形成冲突——那条约束默认影响分析是正确的，而这里它只是「看起来执行过了」。
- **证据与来源**：厂商侧有目录产品内置的助手与评审类功能（Atlan AI、Secoda AI 一类，标注为 2024 年，核验入口见 §5.4 二，本节不复述其效果）。模型厂商公开的研究针对的是**通用** Agent 能力，不是「模型变更评审」这一具体任务，因此不构成本方向的证据。**无第三方公开的生产量化案例，也无公开的漏报率评测**。判定方法：拿过去 12 个月真实发生过的变更事故反查——若 Agent 在变更前给出过「无影响」，看它是否命中；同时统计它给出「有影响」的条目里，被人工判定为真问题的比例。这个回放比任何演示都有说服力，且不需要新数据。
- **成熟度**：**L3**（仅官方演示与厂商自有案例；且上游字段级血缘在多数组织未达标）。

本方向的上游依赖必须显式写出来，否则投入会打在错误的一层：

| 依赖层 | 现状 | 若未达标，Agent 评审的后果 |
| --- | --- | --- |
| 字段级血缘覆盖 | 多数组织未达标（§6 的案例里，字段级血缘通常经历多年建设） | 影响面漏项，且漏得看不出来 |
| 变更语义可读（DDL diff + 变更说明） | 部分具备；变更说明经常缺失 | 模型只能靠 DDL 猜意图，误判口径类变更 |
| 结论可验证（有历史事故可回放） | 通常具备，但没人用它做验收 | 没有反馈闭环，质量不可度量 |

#### 5.2.3 自然语言建模（NL2Model）

- **旧做法与它的卡点**：建模的输入一直是「业务方口述 → 建模者翻译成逻辑模型与物理模型」。卡点在**翻译环节的带宽**：需求排队等建模者，而建模者同时要处理命名、分层、分区策略、成本，于是积压。加人不解决问题——翻译质量依赖对既有模型的熟悉度，新人产出的是「语法正确但与其他模型不一致」的结果，反而制造更多「同义不同名」。
- **AI 改变了什么机制**：把输入从「人对图形化工具的操作」变成「自然语言 → DDL / SQL 草案」。落在机制上是**接口边界的改变**：建模的入口从工具 UI 变成文本通道，意味着它可以被别的系统（需求系统、工单系统）直接调用，建模从「一个岗位的动作」变成「一条流水线上的一步」。
- **由此得到的**：因为生成草案不再占用建模者时间，所以可以「多方案并行」——同一需求生成若干分层 / 分区方案供选，建模者的角色从「写」转向「选与改」。但这条收益受一个硬约束：生成的表必须落回既有分层与命名体系（分层 ODS / DWD / DWS / ADS 见主文件 §1.2，命名规范见 §4.2），否则生成得越多、命名沼泽越大，「同义不同名」这个 §1.1 的核心问题会被放大而不是缓解。
- **由此付出的**：
  - **形式正确、语义空白**：模型能产出语法正确、命名合规的 DDL，但不知道这个实体该按什么粒度建模、口径归谁、与已有模型是否同义。空白本身不致命，致命的是空白处看起来是满的。
  - **评审负担上移**：草案变多后，人的动作从「写」变成「批」。批错的成本高于写错——错在写的阶段会被人看见，错在批的阶段不会，因为签字被理解为「已审」。
  - **一致性风险**：同一需求两次生成可能给出不同结构。若无契约与评审兜底，它会直接加剧「同名不同义」；而这类不一致只有在两个模型被同一个下游引用时才会暴露。
- **证据与来源**：厂商官方发布说明层面有模型平台的自然语言建表 / 助手类能力（Databricks Assistant、Snowflake Cortex、阿里 DataWorks AI Copilot 一类，这三项均标注为 2024 年；**这些材料证明的是「厂商在卖这个能力」，不是「自然语言到 DDL 的链路已被第三方验证」**，本节未逐项核验谁的链路完整，按下面的判定方法自行核验）。**无第三方公开的语义正确率数据**——这类声称通常测的是「SQL 可执行率」或「结构合法率」，与「口径正确率」不是一回事，两者不可互换引用。判定方法：拿 20 个已上线的历史建模需求重跑，比对生成结果与真实上线模型在**粒度、主键、口径**三项上是否一致；三项里任何一项不一致，就说明它生成的是结构而不是模型。
- **成熟度**：**L2**（可试点产出草案，不可作为生产建模入口）。

生成物的可验证性分三层，把这三层分开看，就能明白为什么「形式正确」不能推出「可以上生产」：

| 层次 | 内容 | 能否自动验证 | 谁来负责 |
| --- | --- | --- | --- |
| 形式层 | 语法、命名前缀、注释存在、分级字段 | 能（静态规则即可） | 工具 |
| 结构层 | 分层归属、分区策略、主键唯一性、与既有表是否重复 | 部分能（需要元数据比对） | 工具 + 建模者 |
| 语义层 | 粒度是否符合业务事实、口径是否与既有指标冲突 | **不能**（无外部标注） | 业务 Owner + 数据 Owner 双签（§4.2） |

这张表的用法是验收，而不是分类：任何声称「AI 辅助建模」的能力，问它覆盖到第几层。只覆盖形式层的，是规则引擎加了个自然语言外壳（需求方写下 DDL 也一样能过）；覆盖到结构层的，需要既有元数据可比对，价值真实但有边界；声称覆盖语义层的，要求它给出「口径与哪张既有表冲突、依据是什么」——给不出来，就是没覆盖。

#### 5.2.4 语义图层：目录向量化、本体化与图检索

- **旧做法与它的卡点**：模型目录解决的是「找得到」，卡点在**检索键只有名字与描述**。业务方问的是「谁有用户最近 7 天活跃度」，目录里存的是表名与注释，两者之间要靠人的翻译，于是「找数靠问熟人」。传统血缘图还只在「表—字段」这一种关系上遍历，回答不了「所有引用了 email 的模型」这类跨实体多跳问题——不是算不出来，而是图里根本没有「模型」这个实体。
- **AI 改变了什么机制**：把元数据从「表清单」变成「可检索语料 + 可推理图」。向量化让检索键从名字变成语义相似；图谱化让回答从「命中一张表」变成「多跳可达的实体集合」。落在机制上是**检索接口从精确匹配变成近似匹配 + 关系推理**——前者改变召回，后者改变能回答的问题类别。
- **由此得到的**：因为检索不再要求提问者知道表名，所以不懂表名的业务方第一次能自助取数；因为图可以多跳，所以「变更影响面」与「合规盘点」（哪些表含敏感字段且被模型消费）可以用同一张图回答，不必各写一套查询。这两件事是同一机制的两种用法，这也是它值得单独列为一个方向的原因。
- **由此付出的**：
  - **近似匹配的错误形态是「似是而非」**：返回的表名与语义都沾边，但不是口径相符的那张。错误沿链路放大，最终表现为「数字不对，但没人知道错在选表」——排查时会先怀疑计算逻辑、再怀疑数据质量，最后才怀疑检索。
  - **图会腐化**：模型改名、口径变更、表下线若未回流到图中，图给出的是错误的信心，这比没有图更危险。血缘与元数据的「新鲜度」因此不是运维细节，而是这个方向能否成立的前提。
  - **建图成本是长期投入不是一次配置**：把模型建成 class、字段建成 property、关系建成 objectProperty 需要显式的关系定义与推理规则，与「把描述灌进向量库」不是一个量级的工作——前者要回答「模型之间到底有哪几种关系」，这个问题的答案因组织而异，没有可买的成品。
- **证据与来源**：图检索方向有公开论文与开源实现（微软研究院 2024 年公开的 GraphRAG 方法与对应开源仓库）；实体—关系式的元数据图在开源目录中多年公开可查；本体化治理（把模型建成 class、字段建成 property、关系建成 objectProperty）目前只在厂商与实施方自身的公开材料里出现，本节核验不到「非厂商 + 带规模数字」的第三方生产案例——按本节口径，这个子方向**无公开可核验来源**，核验动作就是去找这类案例，找不到即为无外部证据。**两处必须分清**：论文里的原型与产品里的实现不是一回事；「目录接进向量库」与「本体化推理」更不是一回事——前者是索引，后者要显式关系与推理规则。
- **成熟度**：**L2**（检索侧可用，推理侧仍属试点；新鲜度机制未解决）。判定它是否已成熟的唯一方法是查两件事：元数据的新鲜度是否能被查询（有「最后更新时间」字段），以及是否有非厂商的公开生产案例给出了规模数字。

```text
同样是「找一张用户活跃度的表」，两种检索键的差别

  名字检索（现状）：
    query = "用户 活跃"  ──匹配──▶ 表名 / 描述 / 标签
    命中「用户活跃表」，其实际口径可能是「登录活跃」，
    而提问者要的是「最近 7 天有过下单的活跃」→ 命中但错

  契约检索（目标）：
    query = {实体: 用户, 口径: 最近7天有交互, 粒度: 用户级, 时点: T+1}
      ──过滤──▶ 契约层（口径 / 粒度 / 主键 / 分级）
      ──排序──▶ 语义相似度
    命中：口径相容的候选，且能回答「为什么是它」

  关键：近似匹配必须后置于契约过滤，而不是替代它
        → 顺序反了，错误形态就从「找不到」变成「找错」
```

### 5.3 与本主题既有栈的接口在哪

不写「与 AI 结合」这类空话，写清接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。三条贯穿原则先立在前面。

**第一，接口必须落在 PR 或 API 上。** 只提供对话框形态的能力，无法被别的系统消费，也就无法进入自动化流程；它给人的操作加了个助手，没有给系统加能力。这条原则会把下面的多数结合点直接限定为「人工辅助」。

**第二，失败责任必须与能力边界对齐。** 一个概率性判定器，不能承担确定性判定的责任。把 LLM 检查设成 CI 阻断，等于让一个「可能误报」的组件拥有「阻止发布」的权限——误报时没人能申诉，因为结论没有可复现的依据。

**第三，契约与血缘这两条机器可读通道是前提，不是配套。** 它们不依赖 AI，但决定 AI 能力能否发挥作用：没有契约，「AI 检查」只能对着无标注文本猜；没有字段级血缘，「影响面推演」没有可比对的基准。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| LLM 规范检查 ↔ CI / PR 流程 | 由 PR 事件触发，输入 = 本次变更的 DDL 与上下文，输出 = 评论 + 检查状态 | 误报导致门禁被绕过，责任在定规则的人（不是模型）；漏报责任须在采购合同里切分 | L2：只出建议，不阻断 |
| NL2Model ↔ 建模仓库（Git） | 自然语言 → DDL 草案 PR；通道不接触生产库 | 语义对错由**提交者（人）**负责；平台只保证「产出可解析、可入仓」 | L2 |
| 模型元数据 ↔ 向量索引 / 图索引 | 元数据按版本导出为索引快照，快照带新鲜度戳；查询侧只读，不回写源 | 索引过期由平台负责；索引里缺失的属性由模型 Owner 负责 | L2 |
| 模型契约 ↔ 消费方与 CI | 契约文件入 Git → CI 校验（列名 / 类型 / 可空 / 分级）→ 违约即失败 | 违约由变更方修复；契约本身写错由业务 Owner 修复 | **L2（见 5.1：缺第三方案例）**：规范与工具公开，不依赖 AI |
| 影响面推演 ↔ 字段级血缘 API | 变更单 → 影响面查询 API → 返回下游集合（表 / 字段 / 看板 / 责任人） | 漏项由血缘覆盖度负责（平台）；结论被误读由评审人负责 | L3（上游覆盖度未达标） |
| 模型目录 ↔ Agent 取数 | 目录以「工具」形式暴露：搜索资产、取元数据、取样例（工具调用协议，如 2024 年公开的 MCP 一类规范） | 选错表由**应用 Owner** 负责；工具接口不稳定由目录平台负责 | L2（协议公开，生态未稳） |

契约校验落在流水线里的位置，决定了它是「文档」还是「门禁」——这是本主题里与 AI 无关、但比任何 AI 能力都关键的一步：

```text
契约放在哪一环，决定了它有没有用

  建模者改 DDL ──► PR ──► CI
                          │
                    ① 契约校验（列名 / 类型 / 可空 / 分级）
                       · 违约束然失败，必须改契约或改实现
                    ② 血缘影响面（已有能力，§2.3）
                       · 列出下游，超阈值需 Owner 会签
                    ③ LLM 建议（L2）
                       · 只在评论区出现，不改变流水线结果
                          │
                          ▼
                    合入 → 契约版本 + 影响面记录一并留痕

  关键：①②③ 的顺序不是随意的
       契约在最前（确定）、影响面居中（可算）、AI 建议在最后（不确定）
       顺序反了，不确定的判断就会挡住确定的判断
```

这条顺序还有一层容易被忽略的含义：**AI 建议必须放在「不改变流水线结果」的位置**。一旦把它接成阻断，团队遇到误报时的第一反应是改流水线配置，而改配置的权限通常在下游团队手里——于是门禁被绕过的路径不是「申诉」，而是「在配置里加一行」。把 AI 放在最后、只输出文本，避开的正是这条退化路径。

### 5.5 被过度宣传的部分

**一、「Agent 自动评审可以替代人工模型评审」**

- **实际是什么**：能替代的只有形式可判定的那一段——命名是否合规、类型是否完整、注释是否缺失、契约是否被违反、影响面是否超阈值。业务语义是否正确（这个「成交额」是不是业务要的那个成交额）不可自动判定。
- **为什么会这样**：语义正确性没有外部标注，模型只能靠上下文相似度猜；而猜错的形态恰好是「看起来合理」，最不容易被人工复核抓住。形式判定之所以可行，是因为规则可以被写下来；语义判定之所以不可行，是因为「正确」的判据本身还没被写下来——它散在业务 Owner 的判断里。
- **什么时候它才会成真**：当口径本身被外部化为**可执行的契约**（指标定义可执行、有断言、有测试）时，「语义正确」降级为「断言通过」，自动判定才有依据。在此之前，AI 评审的产出只能定位为建议——这不是保守，而是把能力的边界与事实对齐。

**二、「自然语言建模让业务方自己建模型」**

- **实际是什么**：降低的是写 DDL 的门槛，不是决定粒度与口径的门槛。业务方拿到的仍是需要人签署的草案。
- **为什么会这样**：粒度与口径的决策依赖跨系统约束（上游有什么、下游谁在用、成本多少、是否与既有模型同义），这些信息不在业务方的那句话里，而在组织元数据里。输入里没有的信息，模型生成不出来。
- **什么时候它才会成真**：当契约与口径定义可复用且可执行时，业务方给出的是「我要一个口径」，系统返回的是「已有口径可复用」而不是新建一张表。换言之，成真的前提是**复用先于生成**。

**三、「把模型目录接进 RAG，Agent 就不会取错表」**

- **实际是什么**：向量检索优化的是「名字与描述的相似」，不是「口径相容」。它把错误从「找不到表」变成「找到一张看起来对的表」——错误被推到更晚才暴露、更难归因。
- **为什么会这样**：检索键里没有口径、粒度、时点这些约束维度，近似匹配对它们天然无感；而描述文本通常也不含这些维度，因为没人写。
- **什么时候它才会成真**：检索必须先过一层契约 / 口径过滤再排序（见 5.2.4 的示意），即检索键从「描述相似度」改成「契约相容性 + 相似度」。这一步不依赖新模型，只依赖契约——又一次回到本节最该先做的那一层。

### 5.6 未来 3–5 年：可证伪的预测

写不出「会成真 / 会证伪」两种信号的说法，本节一律不写。下面四条都给出了可观测的信号，读者可以在一年后自行对照。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 模型变更的影响面检查会成为 CI 的默认必过项（像编译一样），而不只是目录里的一个可视化页面 | 主流建模 / 目录产品的 CI 集成里出现「影响面超阈值阻断」且**默认开启**；出现非厂商团队公开自己的拦截规则与阈值 | 两年内主流工具仍只提供血缘可视化页面，没有任何默认阻断能力 |
| 数据契约会成为跨组织交换「模型事实」的载体，而不是各家私有格式 | 至少一个非厂商主导的契约规范被两个以上商业目录产品原生导入 / 导出；出现跨组织违约处理的公开案例 | 各厂商各定义契约格式、互不兼容，导出后仍需人工对照 |
| LLM 生成的元数据描述仍必须人工签署，且「谁确认过」将成为元数据字段 | 目录产品里出现「描述来源（模型 / 人）」与「确认人 / 确认时间」的审计字段 | 三年内这些字段仍未出现，说明治理重心不在可追溯 |
| 本体化推理在模型治理中会停留在试点，不会成为主流做法 | 三年内出现两个以上非厂商、带规模数字的本体化生产公开案例 | 公开案例仍只有厂商博客与内部演示，规模与收益均不可核验 |

需要说明的是，第三条（生成的描述仍必须有人签）看起来保守，其实是最可能成真的一条：可追溯性是合规的硬要求（本主题的模型评审与变更管控正是为它服务的，见 §4.1），而生成式描述天然带不确定性，两者相遇的结果一定是「必须有人签」。它同时是对 5.5 第一条的复述——同一个机制，两种说法。

第四条才是真正「唱反调」的那一条：它赌「语义推理」这类能力在治理场景里不会成为主流。理由不是算力或成本，而是治理要的是**可申诉的判据**——「这条约束被违反了」可以被争辩，「这张图推出来你受影响」不能被争辩。判据不可申诉的能力，在这类场景里只能用于探索，不能用于执行。

四条预测有一个共同特征：**它们的信号都出现在公开的产品行为或公开案例里，而不是出现在某篇展望文章里**。这是本节拒绝写「AI 原生治理是未来」这类句子的原因——那种话永远正确，因此没有信息量；而「CI 里有没有默认开启的影响面阻断」是一个可以在一年后打开产品文档核对的二值事实。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 模型 < 100 张、协作团队 < 3 个 | 先把命名规范与 Owner 落到人（§4.1 前 4 步） | 目录产品的契约支持与 CI 集成成熟度 | 不要上任何 AI 建模 / 评审能力——此时瓶颈是规范缺失，不是阅读速度 |
| 100–1000 张、已有 Git + PR 流程 | 把契约文件化并入 CI 校验；把 DDL 检查做成 PR 建议 | LLM 检查在你们自己标注集上的漏报 / 误报 | 不要把 LLM 检查设成阻断——误报会训练团队绕过门禁 |
| 万张以上、多业务域 | 先修**字段级血缘覆盖度**与元数据新鲜度，再谈 Agent 推演 | 索引 / 图的新鲜度机制是否产品化 | 不要在没有新鲜度机制时建图或建本体——错误的信心比没有更贵 |
| 已在用 LLM 生成 DDL | 强制「草案只进 PR、必须人签」；记录生成来源与模型版本 | 语义评测集（粒度 / 主键 / 口径三项）能否公开获得 | 不要把「SQL 可执行率」当作口径正确率的证据 |
| 强合规（金融 / 医疗 / 跨境） | 契约 + 分级 + 影响面留痕，先满足可追溯 | AI 评审结论能否进审计证据链 | 不要用 LLM 结论替代审计留痕——它无签名、无版本、不可复现 |

「明确不要做」这一列的共同点是：**它们都不是「现在做太早」，而是「现在做会主动制造错误」**。上一节提到的「没有新鲜度就建图」是典型——它产出的不是未完成的能力，而是一份看起来权威的错图，后续所有基于它的判断都会被污染。相比之下，什么都不做的团队只是慢，做了错图的团队要走更长的路回来。

### 5.8 小结

> 本节小结：AI 在本主题上真正改变的**唯一一条机制**是「模型事实的读取成本」——把只存在于人的阅读里的 DDL 与元数据，变成机器可批量处理、可批量判定的对象，于是评审的瓶颈从「人能读多少」移到「机器能判定多少」。它没有改变的是另一件事：**语义正确性必须由人签字**。机器能判定形式（命名、类型、契约违反、影响面超阈值），判定不了「这个口径是不是业务要的那个口径」。这正是本节没有把任何 AI 方向列进路线图、却把「契约文件化」排在行动第一位的原因：契约是把语义变成可执行断言的唯一载体，没有它，AI 越能干，错误越像真的。
>
> 💡 **思考锚点**：先数两个数——你们目录里登记的模型张数落在 §5.7 表里的哪一行，以及 CI 里默认开启且会阻断合并的门禁有几条。本节把「CI 默认阻断影响面」当作判断 AI 是否真改变了评审瓶颈的二值信号，你这两个数落在表里那一行的建议内，还是差一整档？
