## 7. 与其他方法对比

> 原 § 7 共 56 行、为打分表（7 维度 × 4 个治理层）+ 决策树（按团队规模与模型数分支）+ 5 组组合清单，缺少机制解释与可溯源证据，重写为 ~305 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

原表把「模型管理 / 元数据管理 / 主数据管理 / 数据治理」四者放进同一张表，用「抽象层次 / 关注点 / 灵活度 / 学习成本 / 可演进性 / AI 友好度 / 生态成熟度」七个维度打分。这个做法有四个结构性错误。

**错误一：这四个不是候选，是层。** 元数据管理覆盖的是模型之外的资产（任务、看板、指标、API）；主数据管理只覆盖少数核心实体；数据治理是包含前三者的框架。给它们打分，等价于给「楼层 / 房间 / 家具 / 物业」评「灵活度 4 分 vs 3 分」——它们不是替代关系。你在真实项目里最终会同时拥有其中几个：主文件 §1.3 给出的关系图正是嵌套的（模型管理 → 数据资产目录 → 数据治理体系），而不是并列的。

**错误二：打分把「覆盖范围」与「判定深度」压在一个数上。** 元数据管理的生态成熟度最高，但它的强项是**覆盖广**（什么资产都能登记成条目）；模型管理的强项是**判定深**（命名、粒度、口径、Owner 是否真的成立）。这两个性质在不同组织里价值相反：资产多、变更少的组织需要覆盖广；变更频繁、跨团队的组织需要判定深。同一个分数在两种组织里符号相反。

**错误三：「学习成本 5 分」被当成缺点。** 数据治理的学习成本高，是因为它要求跨部门共识；在监管报送这类「同一口径只能有一份定义」的场景里，这笔成本是**必须付的**——把它当缺点打分，等于建议读者回避了唯一可行的路线。这条的机制解释见 7.3.2 与 7.5 的阈值依据。

**错误四：打分不区分「判据的载体」。** 本章真正的变量不是「治理力度打几分」，而是**判定由人的判断完成，还是由可执行制品完成**。本目录 §3 已给出这条机制：判据若只存在于人的判断里，治理成本 ∝ 变更数 × 单次判定耗时，而能承担判定的人力带宽是一个常数；成本线性增长、带宽水平不动，两者必然相交。分数把这条曲线压成了一个点。

**本章采用的 6 条判据**（已针对模型管理主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 作用对象 | 你管辖的是模型、元数据、还是少数核心实体 | 决定工具能不能处理你的对象类型，也决定「哪些对象必须登记」 |
| 判定发生在哪 | 判定是人做的，还是可执行制品做的 | 决定治理成本随变更数的增长曲线（见 7.3.2） |
| 登记与发布的先后 | 登记是发布的前置条件，还是发布后的补录 | 决定目录可信度，以及治理动作有没有作用对象集合（见 7.3.3） |
| 写入权与部署路径 | 有几条路径能改生产、哪一条是权威 | 决定审计能不能回答「谁改的」（见 7.3.4） |
| 变更频率与域数 | 每月多少次变更、跨几个团队 | 决定判定带宽够不够、要不要引入跨团队的共同判据 |
| 不可撤销的约束 | 是否监管报送、是否有外部口径唯一性要求 | 约束成立时没有替代项，此时分数无关紧要 |

原表的七个维度一个未丢，只是位置变了：**抽象层次 / 关注点** → 判据 1；**灵活度** → 判据 2（可执行的判据越多，能放宽的余地越大）；**学习成本** → 判据 3 与 6；**可演进性** → 判据 2（判据写在制品里才可演进，写在人脑里会随人流失）；**生态成熟度** → 判据 1（工具能覆盖的对象类型）；**AI 友好度**不是独立维度——Agent 要的是「判据可被机器执行」+「元数据机器可读」，前者是判据 2、后者是判据 3 的推论，单独打分只会重复计权。

判据的顺序对应一个筛选顺序：**判据 1 是范围性的**（先确定你管多宽），**判据 2、3、4 是结构性的**（一旦选错，改写量以季度计），**判据 5、6 是组织与合规的**。**打分表的根本问题在于把这三类混在一根尺子上**：「登记前置 vs 事后补录」这种结构差异，和「灵活度 4 分 vs 3 分」这种换个模板就能改的差异，在表里长得一样重。

### 7.2 候选方案全景

候选分成两族。**族一是治理层次**（彼此不是替代项，是嵌套关系）；**族二是模型管理的实现路线**（彼此才是替代项）。把这两族混在一张表里打分，是本章要避免的第一个错误——**族一之间比较没有意义（它们不是二选一），族二之间比较才有意义**。

**族一：治理层次**（原打分表的四列，全部保留）

| 方案 | 管辖对象 | 核心机制（一句话） | 它回答而别人回答不了的问题 |
| --- | --- | --- | --- |
| 模型管理（本文） | 概念 / 逻辑 / 物理模型及其字段、口径、Owner | 把模型形式化为带版本的图演化 M(t) = ⟨V, E, A, O⟩，判定集中在 A（属性）与 O（Owner）的正确性上（主文件 §2.2） | 「这个字段该不该存在、该叫什么、归谁、改了影响谁」 |
| 元数据管理 | 更广：表、字段、任务、看板、API、血缘、标签 | 把资产登记成可检索条目，覆盖优先于判定 | 「有哪些资产、在哪、谁在用」 |
| 主数据管理（MDM / OneID） | 少数核心实体（用户、商品、组织、商家） | 为跨系统重复表示的实体建立唯一标识与权威副本 | 「同一个人在两个系统里是不是同一个」 |
| 数据治理 | 模型 + 元数据 + 主数据 + 质量 + 安全 + 合规 | 用组织机制（决策权、评审、度量、激励）约束全部数据活动 | 「谁有权决定口径、出了事谁负责」 |

**族二：模型管理的实现路线**（原决策树与组合清单里出现过的全部模式与工具）

| 路线 | 定位 | 核心机制（一句话） | 代表工具（[§ 4 工程实现](11-model-management-section-4-sec4.md) 的 §4.3） | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 轻量版：Git + 文档 | 单团队、模型数少 | 命名规范与模型清单入 Git，判定靠 PR 评论 | Git / GitHub、Markdown | 开源 / 免费 |
| 集中式建模 | 变更少、要求全局一致的建模 | 中央团队持有写入权，会议式评审 | PowerDesigner、ER/Studio、IBM InfoSphere | 商业 |
| 联邦式 + GitOps | 域各自持有写入权 | 可执行规范 + CI 校验 + PR 流程 | dbt、SQLMesh、Coalesce、GitHub PR | 开源 + 托管 |
| 目录化（Catalog-First） | 以登记为发布前置 | 强制登记项（分层 / 域 / 粒度 / Owner / 上游），缺项不能发布 | DataHub、OpenMetadata、Unity Catalog、Apache Atlas、阿里 DataWorks | 开源 / 商业 |
| 语义层（本体建模） | 面向机器推理的模型层 | 把实体与关系写成可被图查询与向量检索消费的语义制品 | 本体 / 知识图谱 + GraphRAG 一类组合（[§ 5 前沿演进](11-model-management-section-5-ai.md) 的 §5.2.4） | 开源 / 商业 |
| AI 增强 | 判定的建议层 | LLM 读 DDL 做规范与口径检查，Agent 基于血缘推演影响 | Cursor + dbt、Databricks Assistant、AI Code Review | 商业 / 订阅 |
| 数据契约 | 跨团队接口 | 把字段的语义、SLA、PII、Owner 写成机器可读契约 | Bitol、Data Contract Specification | 开源规范 |

**先分族再选能省掉一半比较**：族一回答「你要管多宽」，族二回答「判据放在哪」。**先定族一**——如果你的问题其实是「不知道有哪些表」，那么无论选哪条族二路线都解决不了它，因为那是元数据管理的范围；**再定族二**——如果你已经有可枚举的 `V(t)`（模型清单），那么比较才是有效的。

| 原决策树的路径 | 归入本章哪一行 | 它在选型里动的是哪一项 |
| --- | --- | --- |
| 小团队 / 模型 < 100 → 轻量 Git + 文档 | 轻量版 | 判据载体 = 人 + 文件 |
| 中团队 → 联邦式 + GitOps | 联邦式 + GitOps | 判据载体 = CI 校验 |
| 大团队 → 集中式 + 目录化 | 集中式建模 + 目录化 | 写入权归属 + 强制登记 |
| 模型 100–1000 → dbt + DataHub | 联邦式 + 目录化 | 可执行规范 + 登记前置 |
| 模型 > 1000 → Apache Atlas + 自动化 | 目录化 | `V(t)` 可枚举 + 自动采集 |
| AI 增强 → Cursor + dbt + LLM | AI 增强 | 判定下沉到建议层 |
| AI 增强「否」→ 传统工具链 | 集中式建模 | 判据载体 = 人的判断 + 商业建模工具 |

**上表只列机制，不断言「某工具是否具备某能力」**：产品的功能边界与版本变化很快，写死会产生过期断言。凡涉及具体能力，用下面三种判定方法自查：

- **某工具是否支持字段级血缘、强制登记、CI 阻断**：查其官方文档的能力清单，并在自己的环境里跑一次端到端验证（改一个字段，看它能否列出下游字段与责任人）。
- **某个团队是否真的在执行判据**：取过去一个月的变更记录，随机抽 10 条，看其中有多少条能回答「谁改的、依据哪条规范、谁批准的」。答不出的比例就是「判据其实在人脑里」的比例。
- **语义层是否值得建**：先问消费方是谁。没有消费方（Agent、图检索、自然语言取数）时，本体建模只是一份更贵的文档【经验】。

### 7.3 机制差异：为什么它们表现不同（核心节）

族一与族二的全部差异可以归因到四个机制维度。选这四个，是因为它们分别回答选型时必然要问的四件事：**你管的对象有多宽（7.3.1）· 判定由谁做（7.3.2）· 登记的先后顺序（7.3.3）· 写入权是否唯一（7.3.4）**。

#### 7.3.1 作用对象：覆盖广与判定深是两条不同的曲线

**机制是什么**：一条治理能力要「覆盖一个对象」，就必须为这个对象定义它属于哪个集合（表？字段？指标？实体？），并为集合里的每个成员记录属性。**集合扩大得越快，单位成员能承载的判定就越浅**——因为记录属性是机械的、可以自动化，而判定属性是否成立需要有人或机器能执行的规则。

**各族一的实现差异**：

| 方案 | 覆盖的单位 | 判定的深度 | 覆盖面扩大时的第一反应 |
| --- | --- | --- | --- |
| 模型管理 | 模型 / 字段 | 深：命名、粒度、口径、Owner 都要成立 | 判据必须先被外部化，否则判定带宽不够 |
| 元数据管理 | 任意资产 | 浅：条目存在、可检索、带上血缘与标签 | 采集自动化程度决定覆盖能不能跟上 |
| 主数据管理 | 少数核心实体 | 最深：唯一标识与权威副本必须跨系统一致 | 作用对象必须被限定，扩大即失败 |
| 数据治理 | 全部数据活动 | 浅到中：靠决策权与度量驱动，不逐条判定 | 靠组织机制，不靠逐条检查 |

**由此必然导出的性质**：**因为**「把某个对象纳入治理」的成本由「有没有一条能处理它的规则」决定，而不是由对象本身决定，**所以**覆盖面可以靠采集自动化迅速扩大（登记、检索、标签都可自动），而判定深度不能——它受限于可执行规则的数量。这解释了一个常见现象：**上了目录之后，覆盖率的数字很好看，但变更事故并没有减少**——因为事故来自「判定没发生」，而不是来自「对象没被登记」。**反过来**，**因为**判定深度需要跨系统的一致语义，**所以**主数据管理的作用对象必须是少数核心实体：把「每个模型都做全局统一」当作 MDM 的目标，等价于把它的判定成本乘上模型总数，这在规模上不成立。

**公开证据**：DataHub 由 LinkedIn 内部项目演进而来并开源，把「元数据登记 + 检索 + 字段级血缘」作为公开的产品能力【公开，LinkedIn Engineering 博客的 DataHub 开源公告，2019；可自行核验】。**判定方法**：一个平台宣称的「治理能力」里，哪些是登记的（自动、可批量）、哪些是判定的（需要规则或人）——把这两类分开看，就能判断它能不能承担你的那类问题。

**失效条件**：当作用对象大而判定需求深（例如「所有字段都要求口径唯一」）时，两者的矛盾直接暴露，此时唯一的出路是**缩小作用对象**（只对核心指标做口径唯一）或**把判据外部化**（把口径写成可执行的契约），而不是扩大治理团队。

#### 7.3.2 判据的载体：治理成本随什么增长

**机制是什么**：判定「这次变更是合规的」这件事，由谁来完成——人的判断，还是可执行的制品（命名正则、数据契约、DDL diff、血缘影响面阈值、CI 门禁）。

**各族二路线的实现差异**：

| 路线 | 判定发生在哪 | 判据载体 | 成本随什么增长 |
| --- | --- | --- | --- |
| 轻量版 | 变更前，PR 评论 | 人的判断 + 一份文档 | 与变更数成正比，且需全职人盯着 |
| 集中式建模 | 变更前，会议 | 人的判断 | 与变更数成正比，受会议带宽限制 |
| 联邦式 + GitOps | 变更前，CI / PR | 可执行规范 + 测试 | 一次编写 + 每次近零边际执行 |
| 目录化 | 发布时 + 查询时 | 强制登记项 | 与对象数成正比，与变更数的关系较弱 |
| AI 增强 | 变更前，建议层 | 规则 + 相似度判断 | 与变更数成正比，但单次耗时大幅下降 |
| 数据契约 | 变更前 + 运行时 | 机器可读契约 | 一次编写 + 每次近零边际执行 |

**由此必然导出的性质**：**因为**人的判定带宽是一个常数（一个人一周能认真读完的变更是有限的），**所以**当变更数超过这个带宽时，「更严格的评审」不会让治理更严，只会让它**更快地变成橡皮图章**——这是流程在压力下的必然退化，不是执行者不认真。**反过来**，**因为**可执行制品的判定成本与变更数解耦，**所以**在变更频繁的组织里，把判据外部化是唯一能让治理与规模同时成立的路径；**代价是**判据必须写成机器能读的形式，而这要求团队先就「什么算合规」达成共识——共识的成本被提前付掉，且一旦写错，错误会被一致地执行到每一次变更上。这就是「AI 增强」必须先有可执行规范的原因：**AI 只能执行你写下来的判据，写不下来时它只是把不确定性搬到了门禁上**。

**公开证据**：本目录 §3 已把这条机制与算例给出（20 次变更/周 × 52 周 × 2 人时/次 ≈ 2080 人时/年，约 1.2 人年【推算，推导链：20 × 52 × 2 = 2080 人时/年；2080 ÷ 1700 人时/人年 ≈ 1.2 人年；三项输入，变更频率、单次判定耗时、年有效人时，均按经验取值，只用于量级判断】，且**与模型总数无关、只与变更数成正比**）；§3 的结论与本节一致，数字与推导链以该节为准。**判定方法**：取一次真实的模型变更，记录「从提交到获批」里有多少时间花在**人可以照着念的检查**上——这部分就是可以外部化的部分。

**失效条件**：当变更频率低（季度级）且总量小（模型数在千级以内）时，可执行制的编写与维护成本可能高于它省下的判定成本，此时集中式 + 人的判断是更经济的选择——**判据外部化不是普适的正确，它是一条随变更数增长的收益曲线**。

#### 7.3.3 登记与发布谁先：顺序决定目录可信度

**机制是什么**：同一个目录，可以用两种顺序建设——**登记是发布的前置条件**（Catalog-First），或**发布之后再补录**。两种顺序产出的是同一种产品，可信度却不同。

**各族二路线的实现差异**：

| 路线 | 登记的时点 | `V(t)` 是否完整 | 目录过期的自愈能力 |
| --- | --- | --- | --- |
| 目录化（Catalog-First） | 并入发布流水线，缺项发布失败 | 强制完整 | 每次发布都刷新，不依赖事后补 |
| 目录化（事后补录） | 发布之后由人或脚本补 | 随时间衰减 | 无：绕过流程的改动不会反映 |
| 轻量版 / 集中式 | 无强制登记，靠文档 | 不可枚举 | 无 |

**由此必然导出的性质**：**因为**治理动作（评审、下线、通知、影响分析）都必须先有一个**作用对象集合**，**所以**当 `V(t)` 不可枚举时，所有治理动作都会退化成「人工盘点」，而盘点的保质期以周计（本目录 §3 的 Catalog-First 一节已给出这条推导）。**又因为**查询者对目录的信任是一次性的，**所以**被过期信息误导过一次的工程师会永久回到「问熟人」——目录的价值完全由使用频次决定，一次误导造成的使用量流失不可逆。这两条合起来解释了为什么「上了 Catalog 但没人维护」不是工具问题：**登记动作没有挂在必经路径上**。

**公开证据**：本目录 §6 的四个公开案例里，把「Owner 到人 + 缺项不能发布」写成制度性设计的只有两例——阿里（「每张表必须有 Owner，否则禁止发布」）与美团（「新表必须 Owner + 评审，两个条件缺一不可」）；Netflix 的发布门禁不挂在 Owner 上，而挂在 PII 标注上（「自动扫描 + 人工确认 + 发布门禁」）；字节的 Owner 只作为「模型 = 表 + 指标 + 任务 + Owner」的聚合视图出现，没有强制登记门禁。**「人工填的东西会过期」这条失败教训同样只出现在两例**：字节的「血缘靠人工登记——登记三个月后就过期」与 Netflix 的「PII 靠人工标注——标了三个月只覆盖 60%」【经验】（来源：本目录 §6 汇总的四个公开案例，其标注的数字与年份以该节为准）。这正好印证了本节的机制：**门禁挂在哪个字段上，那个字段才有人维护；没挂在门禁上的登记（字节早期的血缘）会随时间衰减**。**判定方法**：随机抽 10 张生产表，看它们在目录里的最后更新时间是否等于它真实的最后变更时间——不等，说明登记没挂在必经路径上。

**失效条件**：把登记做成发布门禁会**增加发布路径的长度**（每次变更多一次登记动作），在变更极频繁、且登记项需要人工判断（例如粒度、业务含义）的场景里，这一步会成为瓶颈；此时应把登记项分成「机器可填」与「必须人填」两类，只对后者设门禁。

#### 7.3.4 写入权与部署路径：决定审计能不能回答「谁改的」

**机制是什么**：生产上的模型有几条路径可以被修改，以及哪一条是权威路径。

**各族二路线的实现差异**：

| 路线 | 写入权 | 部署路径数 | 能回答「当前状态是什么」 | 能回答「当时状态是什么」 |
| --- | --- | --- | --- | --- |
| 集中式建模 | 中央唯一一份 | 1（模型库导出） | 是 | 弱：靠模型库版本 |
| 联邦式 + GitOps | 域各自持有 | 1（仓库部署） | 是 | 是：commit 记录 |
| 目录化 | 不限 | 取决于有没有门禁 | 是（登记时间戳） | 弱 |
| 轻量版 | 域各自持有 | 可能多条 | 勉强 | 否 |

**由此必然导出的性质**：**因为**可回放性取决于**部署路径是否唯一**，而不取决于用了几个工具，**所以**「同时上了 GitOps 和目录、却仍然答不出是谁改的」这个现象有确定的成因：写入权分散、部署路径有三条（仓库部署 / 手工改库 / 平台界面改）时，任何一档的可回放性都不成立（本目录 §3 已给出这条对照）。**又因为**审计问的恰好是「当时状态是什么」，**所以**只有目录而没有变更记录，在审计场景下是不合格的——目录能回答「现在是什么」，变更记录才能回答「谁在哪一次变更里改成了它」。

**公开证据**：主文件 §1.2 记录的监管报送案例（上游模型被私下加字段、未走变更评审，导致下游报送模型引用未授权字段）正是这条机制的后果【经验】（来源：主文件 §1.2 的汇总案例，量级以该节为准）。**判定方法**：列出所有能改到生产的入口（仓库、控制台、SQL 客户端、运维脚本），逐个确认它是否留下不可篡改的记录——留下记录的那条才有资格当权威路径。

**失效条件**：当组织里不存在「事后追责」的需求（无监管、无跨部门结算）时，可回放性的价值大幅下降，此时把资源投在「登记完整」上比投在「变更可回放」上收益更大。

### 7.4 成本结构对比（不是价格表，是成本函数）

模型管理的成本**随什么变量增长**：

```
年成本 ≈ 治理与平台的固定人力（人 × 年）                    ← 与模型数无关的固定项
       + 变更判定成本（年变更数 × 单次判定耗时）              ← 与变更数成正比
       + 登记与目录维护（对象数 × 补录率 + 采集管道）
       + 工具与许可（商业建模工具 / 托管服务）
       + 冲突修复成本（口径冲突被发现的时间点决定它有多大）    ← 低频、巨额
```

**各条路线的成本主导项与隐性成本**：

| 路线 | 主导项 | 隐性成本 |
| --- | --- | --- |
| 轻量版（Git + 文档） | 判定人力（全压在少数人身上） | 判据只存在于人脑里：人一走，判据消失 |
| 集中式建模 | 中央团队固定成本 + 商业工具许可 | 会议带宽是硬上限；中央成为所有变更的排队点 |
| 联邦式 + GitOps | 规范与 CI 的一次性编写 | 规范必须被所有域一致解释，误解会被一致地执行 |
| 目录化 | 登记与采集管道 | 补录率随时间衰减；登记项若不含治理所需字段，等于白登记 |
| AI 增强 | 工具订阅 + 提示与规则的维护 | 判据没外部化时，AI 只是把不确定性搬到了门禁上 |
| 数据契约 | 契约的编写与版本管理 | 契约与实际实现漂移时，契约变成一纸空文 |

**【推算】数量级示例**（推导链写全，便于换参数重算）：

- **变更判定成本**：设每周 20 次模型变更、每次判定 2 人时（提交人整理材料 + 评审人读材料各约 1 小时）→ 20 × 52 × 2 = **2080 人时/年**；按每年约 1700 人时折算 ≈ **1.2 人年**【推算，推导链：20 次/周 × 52 周 × 2 人时/次 = 2080 人时；2080 ÷ 1700 人时/人年 ≈ 1.2 人年；"20 次/周""2 人时/次""1700 人时/人年"三项输入按经验取值，只用于量级判断】。**关键在这一项与模型总数无关、只与变更数成正比**——所以模型越多、变更越频繁，把判据外部化的相对收益越大（推导与结论与本目录 §3.3 一致）。
- **口径冲突的修复成本**：主文件 §1.2 记录的案例里，一次指标口径治理消耗约 200 人月的量级【经验】（来源：主文件 §1.2 的汇总案例，量级以该节为准）→ 折算约 **16.7 人年**【推算，推导链：200 人月 ÷ 12 月/人年 ≈ 16.7 人年】。
- **把判据提前外部化的成本**：命名规范 + 数据契约 + CI 门禁 + Owner 制度，按「3 人投入 3 个月」估 → 9 人月 ≈ **0.75 人年**【推算，推导链：3 人 × 3 月 = 9 人月；9 ÷ 12 = 0.75 人年；投入规模按经验取值】。
- **上面两条放在一起看，量级差一个数量级以上**，但**不能直接相减**：事前外部化的成本是**确定要付**的，而冲突修复成本是**概率事件**——它会不会发生、什么时候被发现，取决于你的域数与跨域耦合度。**正确的读法**是把它当作一条不对称的赌注：外部化的成本有上限（人月级），而冲突修复的成本没有明显上限（它随影响面与外溢到业务方的程度放大）。
- **目录维护的隐性项**【经验】：事后补录的完整度随时间衰减，且衰减速度取决于「有多少人真的需要查自己负责的那张表」。所以维护成本的正确度量不是「登了多少条」，而是「抽查 10 张表的最后更新时间是否等于其真实变更时间」。

**主导项随规模反转，所以「先省哪一项」不是固定的**：

| 你的处境 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| 单团队、变更季度级 | 判定人力（可被少数人吸收） | 别引入门禁，先把命名规范写下来 |
| 多域、变更周级 | 判定人力（已超出带宽） | 把形式检查外部化到 CI，人只看语义 |
| 模型数不可枚举 | 登记与目录维护 | 先做 Catalog-First，让治理动作有作用对象 |
| 监管报送 | 冲突修复成本（低频但巨额） | 先做不可篡改的变更记录与唯一口径定义 |
| 已有 AI 编码工具 | 工具订阅 + 规则维护 | 先把判据写成可执行形式，再上 AI |

### 7.5 决策树（每个分支都要有阈值依据）

```
你的模型数、变更频率与组织形态是什么？
├─ 模型 < 100 且变更 < 每周一次 且 单团队（协作方 ≤ 3）
│    → 轻量版：Git + 文档（判据在少数人手里，规模还撑得住）
├─ 模型 100–1000 且域 3–10 且已有 CI 能力
│    → 联邦式 + GitOps（dbt 一类）+ 轻量目录（DataHub / OpenMetadata 一类）
├─ 模型 > 1000，或域 > 10，或模型数不可枚举
│    → 先做目录化（登记前置 + 自动采集），再谈门禁
├─ 监管报送 / 审计要求回答「当时状态是什么」
│    → 集中式 + Catalog-First + GitOps（并配漂移检测）
├─ 核心实体跨业务不一致（同一个用户在多个系统有多种表示）
│    → 主数据管理（OneID），且严格限定作用对象
├─ 有机器消费方需要语义（Agent 选表 / GraphRAG / 自然语言取数）
│    → 语义层（本体建模）+ 目录化
└─ 团队已在用 AI 编码工具，希望把判定下沉
     → AI 增强（LLM 规范检查 + Agent 影响分析），但必须先有可执行规范
```

**阈值依据**（与树上每个判断节点一一对应）：

- **「模型 < 100 且变更 < 每周一次 且 单团队（协作方 ≤ 3）」**：这三条正是主文件 §2.4 的三条门槛（模型数量 > 100、跨团队协作 > 3 个团队、模型变更频率 > 每周一次）的反面，本节补上它们的机制依据——① **模型数**：一次人工盘点能覆盖的对象数是有限的，规模一过，治理动作就必须能靠「一次查询列出作用对象集合」来完成，否则动作（评审、下线、通知）找不到对象，退化成盘点（机制见 7.3.3）；② **协作方数**：判据成立的前提是「同一条规则在几个团队里被读成同一个意思」——一条命名规则在两个域里被读成两种做法，等于没有规则；团队数一过 3，共享上下文不再存在，判据必须落到可执行制品上（机制见 7.3.2）；③ **变更频率**：这一条与模型数、协作方数都无关，它量的是判定带宽被占用的速度，推导见下一条（同一个带宽在另一个刻度上的读法）。
- **「模型 100–1000 且域 3–10」**（对应主文件 §2.4 的「跨团队协作 > 3 个团队」）：**上界由「判定带宽 ÷ 单个对象的年变更数」推出——分母这一环缺了，上界就只是断言**。带宽一侧：单次人工判定按 2 人时计【经验】，能长期投入评审的人力约每周 10–20 次判定【经验】，折合 20–40 人时/周，即约 0.5–1 个全职人力；按 52 周折算约 520–1040 次判定/年【推算，推导链：10–20 次/周 × 52 周 = 520–1040 次/年；两项输入均按经验取值】。分母一侧：单个模型平均每年产生的、需要人工判定的变更按 1 次计【经验】（多数模型一年内不改结构，少数高频改，均值落在 1 次量级）。**模型数上界** = 520–1040 ÷ 1 → 约 **1000 个模型**，恰好是带宽的上沿；越过它，判定量超过带宽，评审不会变得更严，只会从「排进队列」退化为走过场（本目录 §6 记录的美团「评审变橡皮图章」正是这次退化）。**域数上界是同一个带宽在另一个刻度上的读法**：按每域约 100 个模型、每模型年均 1 次变更计【经验】，一个域一年消耗约 100 次判定 → 520–1040 ÷ 100 ≈ **5–10 个域**，取上沿即 10。两个刻度互相自洽：10 个域 × 每域约 100 个模型 = 约 1000 个模型，正好回到模型数上界。**下界一侧由共同判据的必要性推出**——单一团队内的口头约定可以运转，因为它有共享的上下文，跨到 3 个以上团队后，判据必须能被每个域一致解释，也就必须写成制品（机制见 7.3.2）。所以这个区间的可行前提是「形式检查交给 CI，人只看语义」。
- **「模型 > 1000，或域 > 10，或不可枚举」**：由 `V(t)` 的可枚举性推出。治理动作必须先有一个作用对象集合；集合不可枚举时，一切动作退化为人工盘点，保质期以周计。因此这一档的第一件事是目录化，而不是加门禁——**门禁拦不住一个你看不见的集合**。
- **「监管报送 / 审计要求回答『当时状态是什么』」**：**约束而非阈值**——外部要求「同一指标只能有一份口径定义」且审计要能追溯变更时，联邦式留下的语义冲突口子在结构上不可接受；且目录只能回答「现在是什么」，只有变更记录能回答「当时是什么」（机制见 7.3.4）。
- **「核心实体跨业务不一致」**：**约束而非阈值**——主数据管理的价值只在「同一实体在多个系统被重复表示」时成立；没有这个前提，MDM 会变成「对所有模型做全局统一」的昂贵尝试，而那条路在规模上不成立（机制见 7.3.1）。
- **「有机器消费方需要语义」**：**约束而非阈值**——语义层的收益只在存在消费方（Agent、图检索、自然语言取数）时兑现；没有消费方时，它只是一份更贵的文档【经验】。
- **「已在用 AI 编码工具、希望把判定下沉」**：**约束而非阈值**——AI 增强的输入是「可执行的判据」；判据尚未外部化时上 AI，得到的是把不确定性放大到门禁上（机制见 7.3.2）。判定方法是：先看你能把多少条判据写成一条规则或一个断言。

**把决策树展开成执行顺序**（同一棵树，按时间轴读）：

1. **第 0 步 · 先量三个数**：一次变更从提交到获批里，有多少时间花在「人可以照着念的检查」上（可外部化的比例）、抽查 10 条变更能答出依据的比例（判据还在人脑里的比例）、以及生产有几条可写入路径（可回放性的前提）。**前两项测的是同一条判据，即判据 2**（判定由人做还是由制品做，机制见 7.3.2）——它们不过是同一个量的两种读法：可外部化的比例越高，「答不出依据」的比例就越低；**第三项测判据 4**（写入权是否唯一，机制见 7.3.4）。**判据 3（登记是发布的前置，还是发布后的补录）由另一个抽查测**：取目录里的 10 张生产表，看它们的最后更新时间是否等于其真实的最后变更时间——不等，说明登记没挂在发布路径上（判定方法见 7.3.3）。
2. **第 1 阶段 · 只写规则**：把命名、分层、粒度、必填项写成可执行形式，不改流程、不买工具。这一步的产出是可被 CI 执行的规范，也是后面所有档位的输入。
3. **第 2 阶段 · 再挂门禁**：把形式检查接进 CI，并让登记成为发布的前置条件。验收标准是「抽 10 张表的目录更新时间等于其真实变更时间」。
4. **第 3 阶段 · 最后才动组织形态**：下放或集中写入权、引入主数据管理、引入语义层。这一步改变的是决策权归属，是不可快速回滚的一步（迁移代价见 7.7）。
5. **持续 · 把两个指标写进治理月报**：判据的可执行比例、以及「谁改的」这类问题的可回答率。缺了后者，治理工作会退化成覆盖率数字的攀比。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单团队（协作方 ≤ 3）、模型数少、变更季度级 | 轻量版（Git + 文档） | 联邦式 + 轻目录 | 上集中式要先养一个中央团队，这个规模付不起固定成本 |
| 多域、变更周级、已有 CI | 联邦式 + GitOps | 集中式 + 强评审 | 集中式的判定带宽是常数，排不起队 |
| 模型数不可枚举、Owner 缺失 | 目录化（登记前置） | 先做一轮人工盘点 | 盘点保质期以周计，且动作找不到对象 |
| 监管报送、口径必须唯一 | 集中式 + Catalog-First | 联邦式 + 强契约 | 联邦式的语义冲突口子在监管场景不可接受 |
| 核心实体跨业务不一致 | 主数据管理（OneID） | 模型层做映射表 | 把 MDM 目标泛化到所有模型：判定成本乘上模型总数 |
| 有 Agent / 图检索消费方 | 语义层 + 目录化 | 只做目录化 | 没有语义层时，机器读不懂口径与粒度 |
| 判定形式化程度已足够高 | AI 增强 | 人工评审 | 判据没外部化就上 AI：把不确定性搬到了门禁上 |
| 跨时区 / 跨公司协作 | GitOps + 目录化 | 集中式 | 会议式评审跨时区不可行 |

**原文件的五组组合全部保留，并补一组**；每条说明职责边界与运维代价：

1. **模型管理 + 元数据管理 + 数据目录**（原组合 1，适用于多数企业级数据中台【经验】——原稿此处写「适用 90%」，该比例没有统计口径，按经验只宜读作「多数」）：模型管理是核心（判据与流程），元数据管理是工具（采集与索引），数据目录是对外界面（可发现）。边界是**模型管理决定「什么算合规」，目录决定「有什么、在哪」**。运维代价：三者叠加后最容易出现的是「目录登记项与模型的评审项各写一份」，必须指定哪一份是唯一来源，否则两处会随版本漂移。
2. **模型管理 + 主数据管理 + OneID**（原组合 2，适用跨业务线中大型企业）：模型管理覆盖所有模型，OneID 专攻核心实体。边界是**OneID 只管「谁是谁」，模型管理管「长什么样」**。运维代价：主数据的权威副本一旦与业务库不同步，映射错误会沿所有下游模型扩散，因此这条同步链路要有明确的对账与告警。
3. **模型管理 + 本体建模 + GraphRAG**（原组合 3，适用 AI 智能体平台、知识密集型企业）：模型管理是基础，本体建模把实体与关系语义化，GraphRAG 提供推理与检索。边界是**模型管理保结构、本体保语义、GraphRAG 保消费**。运维代价：本体是第二份模型描述，与物理模型的一致性需要额外的校验，否则会出现「语义层说的口径」与「数仓里算的口径」不一致。
4. **模型管理 + DataOps + GitOps**（原组合 4，适用 DevOps 文化浓厚的团队）：DataOps 提供工程化流程，GitOps 提供版本化与漂移检测。边界是**模型文件归仓库、部署只有一条路径**。运维代价：漂移检测必须开着——一旦有人走命令行改生产，仓库就不再是权威，可回放性随之失效（机制见 7.3.4）。
5. **模型管理 + AI 增强（Agent 自治）**（原组合 5，适用 AI 原生数据团队）：LLM 做规范与口径检查，Agent 基于血缘推演影响面并给建议。边界是**AI 只做建议与形式检查，语义责任仍在人**。运维代价：建议的质量取决于判据的可执行程度；建议被长期忽视会训练团队忽略它的习惯，撤销比上线更难。
6. **模型管理 + 数据契约（补）**：把跨团队接口的字段语义、SLA、PII、Owner 写成机器可读契约，模型的变更与契约的变更必须一起过门禁。边界是**契约定接口、模型定实现**。运维代价：契约与实现漂移时它变成一纸空文，所以必须有一条自动比对（契约字段 vs 实际 DDL）的检查。

**组合的共同原则**：每个组合都要能回答「谁拥有写入权、判据写在哪、哪一份是唯一来源」。**因为**可回放性由部署路径是否唯一决定（7.3.4），**所以**任何组合都必须先收敛到**一条权威部署路径**——否则工具叠加得越多，「谁改的」这个问题反而越难回答，因为每多加一个入口就多加一处无记录的空间。

### 7.7 选错的代价与迁移成本

**反模式：把元数据管理当成模型管理** —— 采购并上线了目录平台，覆盖率做到很高，一年后的变更事故却没减少，于是继续加工具 → **因为**目录解决的是「对象在哪、叫什么」，而事故来自「判定没有发生」；覆盖是机械的、可自动化的，判定需要一条能被机器或人执行的规则（机制见 7.3.1）→ **正确做法**：把模型管理的判据（命名、粒度、口径、Owner 是否成立）先写成可执行制品，再让目录去承载它的登记与检索；顺序反了，就会得到一个好看但拦不住任何事的面子工程。

**反模式：先下放写入权，再补规范** —— 团队看到「互联网公司都用联邦式」，就把建模权下放到各域，但没有同时建立可执行的规范与 CI 门禁 → **因为**联邦式对中央团队的要求比集中式**更高**（规范必须能被机器执行、能被所有域一致解释），下放写入权而不给共同判据，得到的不是联邦式，而是**无治理**（机制见 7.3.2）→ **正确做法**：先把判据外部化成规范与门禁，再下放写入权；顺序反了的后果不是「一致性弱一点」，而是口径冲突直到跨域 JOIN 时才在下游报表上暴露，修复成本此时已经落在业务方的信任上。

**反模式：用目录的时间戳当审计证据** —— 监管或内部审计要求「谁在哪一次变更里改了这个字段」，团队提交的是目录页面上的一条记录与它的更新时间 → **因为**目录回答的是「当前状态是什么」，它只在每次发布都刷新时可信；而审计问的是「当时状态是什么」，这只有变更记录（commit、变更单、审批链）能回答（机制见 7.3.4）→ **正确做法**：把权威部署路径收敛到唯一一条并留下不可篡改的变更记录，同时开漂移检测；目录是导航，不是凭证。

**反模式：把主数据管理的作用对象泛化** —— 把 OneID 的目标扩成「所有模型全局统一」，项目在第二年变成一场无边界的一致性运动 → **因为**主数据管理的成本由「唯一标识与权威副本跨系统一致」决定，把作用对象从少数核心实体扩到全部模型，等于把这项成本乘上模型总数，而收益并不随之增加（机制见 7.3.1）→ **正确做法**：严格限定作用对象（谁是核心实体、跨几个系统重复表示），其余不一致交给模型层的映射表解决。

**换成另一条路线要动什么**：

| 迁移方向 | 数据迁移 | 流程 / 规范改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 轻量版 → 联邦式 + GitOps | 无（模型文件入仓） | 大：规范要写成可执行形式 | 中：新建 CI 门禁与评审模板 | 用 PR 表达模型变更 | 2–5 人月 |
| 事后补录目录 → Catalog-First | 中：存量登记要补齐 | 中：发布流水线要加登记门禁 | 小：采集管道已有 | 登记是发布的一部分 | 2–4 人月 |
| 联邦式（无规范）→ 联邦式（可执行判据） | 无 | 大：判据从共识变成制品 | 中：CI 与契约比对 | 规范即代码 | 3–6 人月 |
| 集中式 → 联邦式 | 无 | 大：写入权下放 + 评审改异步 | 中：目录与血缘要补齐 | 自治 + 共同判据 | 6–12 人月 |
| 引入主数据管理（OneID） | 大：核心实体要建立唯一标识与映射 | 中：跨系统对账规则 | 中：权威副本服务与同步链路 | 主数据优先于本地便利 | 6–18 人月 |
| 引入语义层（本体 + 图检索） | 中：语义制品要从模型导出 | 中：本体与物理模型的一致性校验 | 中：语义服务与检索链路 | 本体与物理模型的边界 | 4–10 人月 |

> 量级按「一个熟悉本系统的 3–5 人小组」估算【经验】。**最贵的两条迁移有一个共同点**：它们要改的是**作用对象与写入权**——这两样恰好是组织结构问题而不是工具问题，所以代价主要落在协调与再学习上，而不是工程上。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 单团队、模型数少、变更慢 | 轻量版（Git + 文档） | 判定量还在人力带宽之内，外部化不划算 |
| 多域、变更周级、已有 CI | 联邦式 + GitOps | 判据写成制品后，判定成本与变更数解耦 |
| 模型数不可枚举、Owner 缺失 | 先做目录化 | 治理动作必须有作用对象集合，否则退化成盘点 |
| 监管报送、口径必须唯一 | 集中式 + Catalog-First | 语义冲突口子在监管场景不可接受；审计要变更记录 |
| 核心实体跨业务不一致 | 主数据管理，且限定对象 | 唯一标识的收益只在「同一实体被重复表示」时成立 |
| 覆盖率很高但事故没减少 | 先查判据写在哪 | 覆盖是机械的，判定需要可执行的规则 |
| 评审变成了走过场 | 把形式检查搬进 CI | 人的判定带宽是常数，超出后必然退化为橡皮图章 |
| 目录里的信息经常过期 | 看登记是否挂在发布路径上 | 事后补录的完整度随时间衰减，且不能自愈 |
| 答不出「谁改的」 | 收敛到一条权威部署路径 | 可回放性取决于路径唯一，不取决于用了几个工具 |
| 想让 AI 做评审 | 先把判据写成制品 | AI 只能执行你写下来的判据 |
| 任何治理工具采购之前 | 先量「抽查 10 条变更能否答出依据」 | 答不出的比例，就是判据还在人脑里的比例 |

> 本节小结：本节所比的候选之间**唯一真正起决定作用的差异**是——**判据写在哪里，以及登记与发布谁先**。判据写在人脑里，治理成本就与变更数成正比、受一个常数带宽限制；判据写成可执行制品，成本才与变更数解耦。登记挂在发布路径上，目录才可信；事后补录，目录会随时间衰减且不能自愈。其余所有维度都是这两条的**表现形式**：所谓「灵活度」就是「可执行的判据越多、能放宽的余地越大」，所谓「可演进性」就是「判据有没有被写下来」，所谓「AI 友好」就是「判据能不能被机器执行」。选型的正确顺序是：**先确定作用对象（你要管多宽）→ 再把判据外部化（能不能写出规则）→ 最后才选工具与门禁**。
