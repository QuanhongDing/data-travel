## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模型管理看起来是「选一种治理力度」——严一点还是松一点。但真实的模式选择是被一个量推着走的：**每单位时间需要被人判定的模型变更数**。判定的载体决定了治理成本随规模的增长曲线，而这条曲线的形状，才是区分模式的真正变量。

主文件 §2.2 把模型管理形式化为带版本的图演化：`M(t) = ⟨V(t), E(t), A(t), O(t)⟩`，变更操作 `δM ∈ {CREATE, ALTER, DROP, RENAME}`。这个形式化里最贵的一项不是 `V(t)`（表与字段），而是 `A(t)` 与 `O(t)` 的**正确性判定**：命名是否合规、口径是否与既有模型重复、Owner 是否真的会为这个模型负责。`V(t)` 可以由系统自动枚举，`A(t)`/`O(t)` 的正确性不能——它今天仍主要表现为某个人的判断。

这就给出了本节的核心机制：**判据若只存在于人的判断里，治理成本 ∝ 变更数 × 单次判定耗时；而能承担判定的人力带宽是一个常数。成本线性增长、带宽水平不动，两者必然相交。** 判据若能写成可执行制品（命名正则、数据契约、DDL diff、血缘影响面阈值），则成本变成"一次编写 + 每次近似零边际执行的机器判定"，与变更数解耦。

所以本节五个模式不是五档严格程度，而是**判据载体的五种选择**：人的判断（集中式）、域的判断 + 可执行规范（联邦式）、版本控制系统的 diff（GitOps）、机器读得到的元数据（Catalog-First）、规则化检查的自动化（AI 增强）。你已经有能力外部化哪些判据，决定了你此刻能站在哪一档——而不是反过来。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 模型变更频率（月级 / 周级 / 日级） | 判定是否必须可执行 | 「治理越严越安全」——频率一高，重治理先变成阻塞 |
| 模型数量与域数 | `V(t)` 是否可枚举，决定治理动作有没有作用对象 | 「先建模型再建目录」——顺序反过来，目录信息天生不全 |
| 语义判定的可外部化程度 | 哪些检查能交给机器、哪些必须留给人 | 「AI 能替代评审会」——语义正确性没有外部标注，判不出来 |
| 团队工程能力（Git / CI / 测试） | 门禁能挂多深（PR / CI / 发布） | 「上了 Git 就等于可追溯」——没有漂移检测，Git 记的是希望的模型 |
| 合规与审计要求 | 是否必须有具体到人的 Owner 与不可篡改记录 | 「Owner 写团队名也算 Owner」——审计要的是主体，不是群体 |
| 历史与回滚要求 | 变更是否需要被保留成可回放的记录 | 「回滚就是撤稿」——没有版本化，回滚是重做而不是 undo |

上一张表为什么读起来像"按场景挑一个"的菜单？因为**模式表丢掉了成本随规模变化的形状**。集中式的成本曲线是"固定高、斜率小"（要养一个中央团队，但每次变更的边际成本不高）；联邦式的成本曲线是"固定低、斜率由语义冲突决定"（规范写一次就行，但每次跨域冲突都要人来裁）；GitOps 的固定成本是"基础设施 + 工程能力"，边际成本近零；Catalog-First 的固定成本是"登记动作永久化"。四条曲线的交点位置不同，所以同一个"场景"在不同规模上对应不同模式——这正是模式表看不见的东西。

最后一条约束常被忽略但影响最大：**变更本身是不是数据**。如果每一次模型变更只是一个被覆盖的操作，那么所有治理都只能发生在变更的那一刻（事前评审或事中门禁）；如果变更被保留成可回放的记录（commit、评审记录、登记时间戳），治理就可以在事后进行（审计、追责、复盘）。前者要求带宽，后者要求介质。

### 3.2 模式逐个拆解（核心节）

每个都按同一骨架：约束 → 结构 → 机制 → 代价 → 失效点 → 真实使用。「真实使用」里的【公开】一律给出可检索的文档 / 材料名与年份，本节未核到可引用的公开出处、未逐条附链接，按所给名称自行核验即可。

#### 3.2.1 集中式建模（PowerDesigner 时代）

- **被什么约束逼出来**：合规要求全企业一套口径，而当时不存在任何跨团队可执行的规范载体——一致性只能靠"一个人写、其他人不许写"来保证。
- **结构**：

```text
集中式建模：唯一写入权 + 三层模型 + 单向导出到物理库

  业务方 ──提需求──► 中央建模团队（唯一写权限）
                        ├─ 概念模型（业务语言）
                        ├─ 逻辑模型（不依赖 DB 方言）
                        └─ 物理模型（DB 方言 DDL）
                              │ 人工导出 / 脚本生成
                              ▼
                        生产库（Oracle / DB2 / …）
                        ↑ 这一侧没有写入约束：谁有 DDL 权限谁就能改
  ────────────────────────────────────────────────
  一致性由「人的权限」保证，不由机制保证
  → 模式成立的前提是「写权限只有一份」，而不是「工具足够强」
```

- **为什么这样设计有效**：因为 `V(t)` 的命名与 `O(t)` 的分配在整个企业内只有中央团队一个来源，所以"同名不同义"在流程上无法发生——不是因为大家治理得好，而是因为**没有人有权制造分歧**。这是一种把问题从"约束人"降级为"约束权限"的解法。
- **代价**：写入带宽 = 中央团队的人力，且不可弹性扩容。任何模型变更都要排队，队列长度随业务线数量线性增长；同时"生产库侧无写入约束"意味着模型库与生产库必须人工同步，两处状态必然漂移。工具链本身也重：概念/逻辑/物理三层模型的维护、方言适配、导出脚本都需要专人。
- **失效点**：当变更频率从季度级升到周级时，「一致性高」反转成「阻塞交付」；因为中央团队的判定带宽是常数，而变更请求数随域数线性增长，队列发散。被阻塞的团队会绕过中央团队直接在库里建表（影子模型），实际一致性反而比上线前更差——这是集中式最常见的崩塌形态，且崩塌时的状态比未治理更糟：一份权威模型 + 若干份影子模型。
- **真实使用**：SAP PowerDesigner（SAP Help Portal 的 PowerDesigner 产品文档）、ER/Studio（Idera 官方产品页与文档）、IBM InfoSphere Data Architect 是这一代的代表工具【公开：各产品的官方文档与产品页，可自行核验；本节未核到可引用的公开出处，具体版本与在售状态以厂商页面为准】。金融与监管报送场景长期是这一模式的密集区【经验：这一判断的核验方法是查看该企业是否存在"模型提交排队"的制度描述，而非看它买了什么工具】。

#### 3.2.2 联邦式建模（dbt 时代）

- **被什么约束逼出来**：变更频率升到周级、业务域数量超过中央团队能覆盖的范围，但跨域口径仍需要可比——一致性不能再靠"一个人写"，只能改靠"一份所有人都要过的规范"。
- **结构**：

```yaml
# 联邦式：中央定「可执行的规范」，域自己建模
# 中央团队维护：命名规范 / 分层定义 / 粒度必须声明 / 测试基线
# 域团队维护：域内的 model 与 schema（在规范之内自由）
models:
  - name: dwd_trade_order_created
    config:
      materialized: incremental          # 域自己决定物化策略
    meta:
      layer: dwd                         # 中央规范：分层必须声明
      domain: trade                      # 中央规范：域必须声明
      owner: trade-analytics-data        # 中央规范：Owner 必填
      grain: order_id                    # 中央规范：粒度必须声明（一行代表什么）
    columns:
      - name: order_id
        tests: [not_null, unique]        # 中央规范：主键必须有测试
```

- **为什么这样设计有效**：因为"合规"被写成了 YAML 里必须出现的字段（layer / domain / owner / grain）与必须通过的 tests，所以"是否合规"这个判定从"开一次会看一遍"降级为"`dbt build` 的通过或失败"。判定成本与模型总数解耦，只与变更数相关。中央团队做的事从"替所有人建模"变成"维护这份可执行规范"。
- **代价**：可执行规范只能覆盖**形式可判定**的部分——前缀、类型、必填项、注释、测试是否存在。口径选得对不对、粒度定得合不合适，规范判不出来。于是中央团队的剩余职责是"定义规范 + 裁决语义冲突"，而语义冲突的裁决成本无法随规范改进而下降——这是联邦式必然留下的、无法机械化的一块。规范制定得越细，边界越清晰，但规范本身也越难演进（改一条规则要通知所有域重跑）。
- **失效点**：当域数超过中央团队能维持规范一致解释的规模时，「灵活迭代快」反转成「碎片化」；因为规范只约束形式不约束语义，每个域对"合规"自行解释，冲突直到跨域 JOIN 时才在下游报表上暴露。主文件 §1.2 记录的"同一指标在多个部门各有计算公式"就是这一形态【经验：这类案例的可核验特征是指标定义表里同一名称出现多于一条公式记录】。
- **真实使用**：dbt 自 2016 年起开源【公开：dbt 官方文档（docs.getdbt.com）与 dbt-core 开源仓库的发布历史，可自行核验】；"域内建模 + 中央规范与测试"在 dbt 生态中被广泛采用，可核验的入口是 dbt 官方文档的 Models 与 Tests 章节及官方项目模板——"官方推荐"这一层的表述请以文档当前版本为准，本节不代为断言【经验：本节未逐条核到文档原文】。阿里 OneData 的"统一规范 + 域自治 + 分层（ODS/DWD/DWS/ADS）"是同一思路的另一种工程实现【公开：阿里云 DataWorks 官方文档（help.aliyun.com）的 OneData / 数据建模章节，2016 年起，可自行核验】。

#### 3.2.3 GitOps 模型管理

- **被什么约束逼出来**：模型变更必须可追溯、可回滚、可评审，而评审不能靠会议——跨时区、跨团队、高频次，会议式评审的带宽一定不够。
- **结构**：

```text
GitOps：模型状态 = 仓库里的一次 commit

  域工程师 ──► PR（DDL / YAML + schema diff）
                  │
       CI 三道必过检查
         ① 命名与规范（可执行规则，确定）
         ② 影响面（血缘反向遍历，超阈值即断，可算）
         ③ 契约与兼容性（加字段须兼容、改类型须双写方案）
                  │
            人工评审（只审语义：粒度与口径）
                  │
              merge ──► 自动部署 ──► 生产库

  ────────────────────────────────────────────────
  漂移检测（必须有，否则 Git ≠ 实际）
      定期比对「仓库里的 DDL」与「生产库的 information_schema」
      不一致 → 告警，并以仓库为准重新部署
```

- **为什么这样设计有效**：因为模型的每个历史状态都是一个 commit，所以"可回滚"是版本控制系统的既有能力，回滚成本 = 一次 revert，不需要治理团队另建一套版本机制；同时 PR 让"谁在何时批准了什么"成为不可篡改的记录，责任定位不需要额外的工单系统。治理能力被直接嫁接在已有的工程习惯上，这是它相对集中式最大的成本优势。
- **代价**：模型必须以**声明式制品**存在（DDL 或 YAML），而生产库允许直接 ALTER——这两个前提之间的缺口是必然的，因为数据库的授权模型不受 CI 管辖。要么补上漂移检测作业，要么 Git 里记录的是"希望的模型"而不是"实际的模型"。漂移检测本身是一个需要长期维护、且要处理方言差异的作业，不是一次配置。
- **失效点**：当 PR 队列开始积压、而团队仍保留直连生产的权限时，「可追溯」反转成「形式合规」；因为门禁的实际强度等于"绕过它的成本"，而此时绕过成本约等于零——团队直接改库，Git 的图与实际状态持续背离，且背离程度不可测量（你不知道哪些表被绕过过）。这个失效点比集中式的影子表更隐蔽：影子表至少看得见，漂移是看不见的。
- **真实使用**：dbt 项目 + GitHub / GitLab PR 流程是公开的通用做法【公开：GitHub Docs（docs.github.com）与 dbt 官方文档（docs.getdbt.com），在各自文档内按 "pull request" / "continuous integration" 检索即可核验】；SQLMesh 等工具把"声明式定义 + CI 校验"作为产品能力公开【公开：SQLMesh 官方文档（sqlmesh.com/docs），按 "plan" / "CI" 检索即可核验；行为与版本以官方文档为准】。版本号语义方面，语义化版本 2.0.0 是公开发布的规范【公开：semver.org，2.0.0 版发布于 2013 年，可自行核验；具体版本以该站点为准】。

#### 3.2.4 AI 增强模型管理（2024+）

- **被什么约束逼出来**：形式可判定的检查项（命名、注释、Owner 完整性、契约违反、影响面超阈值）占据了人工评审的大部分时间，而这些检查项的规则是可以写下来的——可以被拿走的那部分，就应该被拿走。
- **结构**：

```text
AI 增强的放置位置（顺序不能反）

  提交 ──► ① 可执行规则（编译 / 命名 / 契约）        判定：确定
             │  失败即阻断
             ▼
          ② 影响面（血缘反向遍历 + 阈值）             判定：可算
             │  超阈值即阻断
             ▼
          ③ LLM / Agent 检查与建议                    判定：不确定
             │  只输出文本与建议，不阻断
             ▼
          人工签署（语义：粒度与口径），记录「谁确认过」

  ────────────────────────────────────────────────
  为什么 ③ 必须放在最后且不阻断：
  它的误报无法避免，把它接成阻断，团队消音的最短
  路径是「改一行流水线配置」（通常权限就在下游团队手里），
  而不是申诉。顺序反了，不确定的判定会挡掉确定的判定。
```

- **为什么这样设计有效**：因为形式可判定的检查有可写下来的规则，所以它们能被从人手里拿走，人工评审的时间从"核对规范"转向"讨论口径与粒度"——省下的是核对，不是判断。
- **代价**：语义正确性不可自动判定。"这个成交额是不是业务要的那个成交额"没有外部标注，模型只能靠上下文相似度猜，而猜错的形态恰好是"看起来合理"，最不容易被人工复核抓住。所以 AI 产物必须带"谁确认过"，治理成本没有减少，只是从"写"转移到了"审"；另外模型调用按量计费，而使用者是千百个业务方，典型的"花费者与付费者分离"，成本接口要单独界定。
- **失效点**：当 AI 检查被接成阻断、且误报率非零时，「自动化提高」反转成「门禁被系统性绕过」；因为消音成本（改配置）远低于申诉成本，门禁失效的路径不是有人公开反对，而是配置里悄悄多出一行例外。这是"不确定的判定被赋予了确定判定的权力"的必然结果。
- **真实使用**：厂商侧已公开的 AI 目录 / 助手能力——Databricks Unity Catalog 的 AI 辅助（docs.databricks.com 的 Unity Catalog 章节）、Snowflake Horizon Catalog（docs.snowflake.com）、Atlan AI（docs.atlan.com）、阿里云 DataWorks AI Copilot（help.aliyun.com 的 DataWorks 文档），均在 2024 年前后出现在各自的官方文档与发布说明中【公开：各厂商官方文档 / 发布说明，可自行核验；本节未逐条核到原文】——本节只登记"厂商发布了这个能力"与核验入口，**不登记其效果**；本主题尚未找到可核验的非厂商公开生产案例。

#### 3.2.5 目录化治理（Catalog-First）

- **被什么约束逼出来**：`V(t)` 不可枚举——不知道现存多少模型、归谁管、谁在用。在这种状态下，任何治理动作（评审、下线、影响分析、发通知）都找不到作用对象，只能退化成"人工盘点"，而盘点的保质期以周计。
- **结构**：

```yaml
# Catalog-First：登记是发布的前置条件，不是发布后的补充
model: dwd_trade_order_created
required:                # 缺任一项，发布流水线直接失败
  layer: dwd             # 分层：ODS / DWD / DWS / ADS
  domain: trade          # 业务域
  grain: order_id        # 粒度：一行代表什么
  owner:                 # 具体到人，不是团队
    business: xxx@company.com
    data: yyy@company.com
  upstream: [ods_trade_order, dim_user, dim_merchant]
  downstream: [dws_trade_user_order_1d]
  review: PR-1234        # 发布前必须有评审记录
published_at: "2026-01-01"   # 目录里的时间 = 最后一次通过评审的时间
```

主文件 §6 把这一模式的产物描述为"模型 = 表 + 指标 + 任务 + Owner 的聚合视图"，并强调新模型必须"Owner + 评审"两个条件缺一不可才算合法存在。

- **为什么这样设计有效**：因为"登记"被放进发布流水线而不是放进文档，所以 `V(t)` 是被强制枚举的，治理动作第一次有了作用对象集合——"给所有无 Owner 的表发通知"从一次人工盘点变成一次查询。**Catalog-First 与"事后补目录"的差别不在工具，在顺序**：先登记后发布，数据天生完整；先发布后补录，补录率随时间衰减，且衰减速度取决于有多少人真的需要查自己负责的那张表。
- **代价**：发布路径多一跳，每次变更都多一次登记动作，且登记内容描述的是"通过评审那一刻的模型"。模型一旦被绕过流程改动，目录与实际的偏差不能自愈——所以目录的可信度与"绕过发布的难度"绑定，而不是与目录工具的检索能力绑定。另外强制登记要求 `V(t)` 中的每个对象都有唯一的登记主体，跨系统同步（数据库、调度、BI）时会出现"同一对象两条记录"的合并问题。
- **失效点**：当登记被做成事后补录、且没有把登记项纳入发布门禁时，「可发现性强」反转成「目录不可信」；因为查询者对目录的信任是一次性的——被过期信息误导过一次的工程师会永久回到"问熟人"，而目录的价值完全由使用频次决定，一次误导的代价是不可逆的使用量流失。这也是"上了 Catalog 但没人维护"这一形态的机制解释：问题不在工具，在登记动作没有挂在必经路径上。
- **真实使用**：DataHub、OpenMetadata、Unity Catalog、阿里 DataWorks 数据地图均把"元数据登记 + 检索 + 血缘"作为公开的产品能力【公开：DataHub 官方文档（datahubproject.io）、OpenMetadata 官方文档（open-metadata.org）、Databricks 官方文档（docs.databricks.com）、阿里云 DataWorks 数据地图文档（help.aliyun.com），均可自行核验；具体能力与版本以官方文档为准】。DataHub 由 LinkedIn 内部项目演进而来并开源【公开：LinkedIn Engineering Blog 的 DataHub 发布文章与项目官方仓库，可自行核验】。

#### 3.2.6 五个模式的结构对照

把五个模式按"判定发生在哪里"排成一列，差异一目了然：

```text
       写入权           判定发生在哪    判据载体            可回放？
集中式  中央唯一一份      变更前，会议     人的判断            模型库版本（弱）
联邦式  域各自一份        变更前 + 构建    可执行规范 + 测试    取决于规范是否入 Git
GitOps  域各自一份        变更前，CI/PR    diff + 规则 + 血缘    commit（强）
AI 增强 域各自一份        变更前，建议层   规则 + 相似度        同 GitOps
目录化  不限              发布时 + 查询时  强制登记项           登记时间戳（弱）

  ────────────────────────────────────────────────
  读法：从左到右不是"越来越先进"，而是
        「判定从人手里移到制品里」的程度递增。
        每往右一步，都要先有对应的制品（规范 / 仓库 / 元数据）。
        制品不存在就跳到右边那一档，得到的只是流程名称。
```

这个对照还能解释一个常见现象：团队同时"上了 GitOps 也上了目录"，却仍然答不出"谁改的"——因为 `可回放` 这一列取决于**部署路径是否唯一**，而不取决于用了几个工具。写入权分散、部署路径有三条（仓库部署 / 手工改库 / 平台界面改）时，任何一档的可回放性都不成立。

最后要说明的是，这一列里的"弱"不代表不可用：集中式的模型库版本与目录的登记时间戳，都足以支撑"当前状态是什么"这个问题，只是不足以支撑"当时状态是什么"。区分这两个问题很重要——前者用目录就能回答，后者只有不可篡改的变更记录才能回答，而**审计问的恰好是后者**。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 变更日级 / 周级 + 域 10+ + 已有 CI 能力 | 联邦式 + GitOps | 集中式的判定带宽是常数，排不起队 | 仓库里的模型文件是否已能通过 CI 校验 |
| 变更季度级 + 监管报送 + 模型数在千级以内 | 集中式 + Catalog-First | 联邦式留下的语义冲突口子在监管场景不可接受 | 是否存在外部要求"同一指标只能有一份口径定义" |
| 模型数不可枚举 / 大量模型无 Owner | 先做 Catalog-First | GitOps 与 AI 增强都需要 `V(t)` 才能挂载 | 能否用一次查询列出现存全部模型与 Owner |
| 形式检查吃掉大半评审时间 | 联邦式基础上 + AI 增强 | 先上 AI 而不先规则化，会把不确定性放大到门禁上 | 评审记录里"规范类问题"与"语义类问题"的比例 |
| 跨地域 / 跨时区 / 跨公司协作 | GitOps + Catalog-First | 会议式评审跨时区不可行 | 评审能否完全异步完成 |
| 审计要求不可篡改的变更记录 | GitOps（必须配漂移检测） | 只有目录没有变更历史，答不出"谁改的" | 能否回答"谁在哪一次变更里改了这个字段" |
| 初创公司 / 单业务线 + 变更频率低 + 模型数 < 100 | 联邦式 + 轻量目录 | 上集中式要先养一个中央团队、上 GitOps 要先补 CI 能力，两者都是这个规模还付不起的固定成本 | 变更是否需要跨团队确认；不需要就不必引入门禁 |
| 传统数仓（Inmon 体系）+ 变更季度级 + 稳定优先 | 集中式 + 强治理 | 联邦式的语义冲突口子在"企业级单一数仓"的目标下不可接受——它要的是一份一致的 EDW，不是可拼接的域 | 是否以"企业级单一数据仓库"为目标，且建模权长期集中在一个团队 |

**最常被误选的一对是「联邦式建模」与「集中式建模」。** 团队看到"互联网公司都用联邦式"，就把写入权下放到域，但没有同时建立可执行的规范与 CI 门禁——得到的不是联邦式，而是**无治理**。联邦式对中央团队的要求比集中式**更高**（规范必须能被机器执行、能被所有域一致解释），而不是更低。误选的实际后果也不是"一致性弱一点"，而是口径冲突直到跨域 JOIN 时才在下游报表上暴露，修复成本此时已落在业务方的信任上；届时的补救通常是一次指标治理项目，量级远大于一开始就把规范外部化的成本【经验】。

这个成本可以粗算一次量级：若一次模型变更的人工判定按 2 人时计（提交人整理材料 + 评审人读材料，各约 1 小时）【经验】，团队每周发生 20 次变更，则一年判定消耗 ≈ 20 次/周 × 52 周 × 2 人时/次 = 2080 人时；按每年约 1700 人时折算，约 1.2 人年【推算：推导链 = 20 × 52 × 2 = 2080 人时；其中"20 次/周""2 人时/次""1700 人时/人年"三项输入均按【经验】取值，此处只用于量级判断，不作为精确结论】。关键不在这个数字本身，而在于：**它与模型总数无关，只与变更数成正比**——所以模型越多、变更越频繁，可执行判据的相对收益越大。

### 3.4 组合模式：真实系统不会只用一种

**组合一：联邦式（写入）+ GitOps（门禁）+ 轻量目录（检索）**

- 构成：域写模型文件；PR + CI 是唯一入口；目录从仓库元数据自动采集，不额外要求人工登记。
- 职责边界：域负责粒度与口径；中央只负责规范、CI 规则与血缘基础设施；目录只做检索与发现，不做发布门禁。
- 运维代价：CI 规则本身要有人持续维护——规则过严会被绕过，过松等于没有；漂移检测作业必须常开，否则第三层（目录）的输入就不可信。
- 适合规模：10+ 域、千级模型、有 2–5 人专职平台团队【经验】。

**组合二：集中式 + Catalog-First（强合规）**

- 构成：中央团队持写入权；目录是唯一发布入口；每次变更留评审记录与变更单。
- 职责边界：中央负责一致性与合规举证；域只提需求、不写模型；目录同时承担"发布入口"与"审计底稿"两个角色。
- 运维代价：队列与人力不可弹性；目录登记成为发布链路上的单点；需要专人运营"待办队列"与"超期未评审"告警。
- 适合规模：模型数百到千级、变更季度级、存在外部审计要求的场景。

**组合三：GitOps + AI 增强 + 目录化（平台化）**

- 构成：可执行规则与影响面进 CI；LLM 只做建议与描述生成；登记项进门禁；目录与语义层共享同一份元数据。
- 职责边界：机器负责形式判定与影响面计算；AI 负责生成候选描述与建议；人负责语义签署；AI 不持有阻断权。
- 运维代价：三条流水线都要有明确负责人（规则、血缘、模型调用成本）；AI 误报需要一条"人工消解"通道，否则团队会自行在配置里消音。
- 适合规模：模型数千级、变更周级、已具备平台团队与工程文化。

三个组合的共同点是：**每一层都要有人对"这一层判什么"负责**。组合一的第三层（目录）只做检索不做门禁，因此它可以自动采集、允许不全；组合三的目录同时做检索与登记门禁，因此它必须有人运营。把"允许不全"的层和"必须完整"的层混在一起，是组合模式最常见的失败起点——一层既要轻快又要权威，两条要求会互相抵消。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **文档化即治理** | 存在一份模型文档，但没人能说出它与生产库上次比对是什么时候 | 判据不可执行，判定成本 ∝ 变更数 × 人头；文档与实际漂移后，治理依据本身变成错误来源 | 文档是治理最容易交付的产物——写文档有可见产出，改流程没有 | 判据必须落到可执行制品（DDL / YAML / 正则 / 契约），文档只作为制品的渲染结果 |
| **Owner 摆设** | Owner 字段里出现团队名、邮箱组，或同一个人的名字出现在几十个模型上 | 责任无法落到主体，变更无人签署；事故时定位到"某个团队"，等于没定位 | 填 Owner 被当成表单字段而不是承诺；填团队名的成本最低且当期不会被拒 | Owner 必填且校验为个人邮箱；离职自动告警；定期核对 Owner 是否仍与该模型有人均相关的证据 |
| **评审走过场** | 一次评审会议在几分钟内通过大量变更；评审记录里没有任何否决 | 风险不进评审就进生产；门禁在统计上等于不存在，且团队会据此降低自身审查强度 | 评审的 KPI 被做成"通过率"或"评审吞吐"，而不是"拦住的风险数" | 按影响面分级：低影响批量过，高影响强制深度评审并留否决与反例记录 |
| **目录化形式主义** | 上了 Catalog，但检索结果里大量模型缺 Owner / 分层 / 粒度；没人维护 | 目录不可信 → 使用量流失 → 更没人维护，形成不可逆的负循环 | 目录被当成一个"要采购/要上线"的项目，而不是发布路径上的一跳 | 把登记项接进发布门禁：缺项就发不出去；目录与建模流程双向绑定 |
| **规范过严** | 规范细到每个单词、每个缩写；新人有专门文档解释命名 | 合规成本高于收益，团队优先绕过；绕过一旦发生，形式合规与实际状态分离 | 规范制定者的目标函数是"消除歧义"，而使用者的目标函数是"尽快发布" | 规范只覆盖关键字段与关键前缀；其余交给评审与工具提示，不做硬阻断 |
| **缺乏版本管理** | 模型变更没有 Git 记录；回滚需要重做而不是 revert | 变更不可追溯、不可回放，审计答不出"谁改的"；事故复盘缺证据链 | 生产库的 DDL 是长期"就地改"的，团队没意识到模型也是代码 | 模型入 Git；建漂移检测；把"仓库为准"定为唯一部署路径 |

**展开一：文档化即治理**在生产里的典型暴露方式是"文档正确、实现错误，且无人知道"。它的危险性来自延迟：文档错不会立刻报错，只会让后来的人依据文档做出错误判断——比如依据一份两年前的模型文档去评估一次变更的影响面，结论是"没有下游"，而实际下游有十几个任务【经验：示意性数字，只用于说明量级差异，本节不对应任何具体案例的记录】。这类事故的归因通常落在"某人不仔细"，机制上却是文档从未被要求与实现保持一致。

**展开二：Owner 摆设**暴露的方式是"事故发生了，通知发不出去"。它的机制不是人的责任心问题，而是**责任主体的粒度与系统记录的粒度不一致**：系统记录的是团队，需要的是一个人。修法不能靠"加强 Owner 意识"，只能靠把校验做进登记环节——Owner 字段必须是个人标识，且离职、转岗时自动触发告警，否则这条记录会在人事变动后静默失效。

**展开三：目录化形式主义**与上一条同根：治理动作如果与发布路径解耦，它的数据完整性就只能靠人的自觉维持，而人的自觉在"没人查"的时候必然下降，且下降是不可观测的。它的独特之处在于自强化：使用量下降 → 维护动机下降 → 信息更旧 → 使用量进一步下降。因此修法必须在**第一周**就把登记接进必经过路径，而不是等目录数据变干净了再推流程。

其余反模式（评审走过场、规范过严、缺乏版本管理）与上述三条共享同一个结构：**治理动作没有挂在"必经路径"上，或者判据没有可执行的载体**。诊断方法一致——问"这一步能不能被跳过，跳过后谁会知道"。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 模型数 100 → 1000 | 集中式 | 中央判定带宽是常数，请求数线性增长，队列发散 | 联邦式 + GitOps | 必须先把"合规"外部化成可执行规则，否则联邦 = 无治理；规范外部化本身是一次跨季度的改造 |
| 域数 3 → 10+ | 联邦式（无中央规范） | 语义冲突只在跨域 JOIN 时暴露，暴露时已在下游 | 联邦式 + 中央规范 + 目录 | 需要重建指标口径层；历史指标要么重算，要么接受一段时间内的口径并存 |
| 变更频率月级 → 周级/日级 | 集中式（会议式评审） | 评审带宽不够，队列积压，团队开始"先改后补" | PR + CI 门禁（GitOps） | 团队工程能力需要培养周期；CI 规则要随误报率迭代 |
| 单库 → 多引擎 / 多消费方 | 集中式（物理模型 + 方言导出） | 每次 schema 变更要重写数据，且模型只能被一个引擎消费 | 开放表格式（承接 [Ch3 湖仓](../../03-data-stack/)） | 小文件维护、元数据服务、并发提交控制都要新建 |
| 消费方从"人 + BI" → "人 + Agent" | 目录只服务人 | 人的记忆能补上未登记的口径，Agent 不能 | 目录 + 语义层 + 契约 | 口径、粒度、时点必须补成机器可读字段；补不出来的部分，Agent 就只能猜 |

表中「原模式」一列一律指回 §3.2 的五个模式，括号里注明的是它在跃迁前的主要形态——「会议式评审」是集中式的判定形态，「物理模型 + 方言导出」是集中式的结构形态。最容易被忽略的一条跃迁判据：换模式的信号不是"规模数字到了多少"，而是**某项治理成本是否已经开始按规模线性增长**。如果每次模型变更都要开一次会，而会议数随变更数线性增长，那么无论模型数是 300 还是 3000，你都该换——数字只是让成本变得可见的最晚时点，不是最早时点。

还有一条迁移顺序上的纪律：**制品的建设要早于阈值，而不是被阈值触发**。规范外部化、漂移检测、登记门禁这三件事都可以在"还不疼"的时候做，且成本与规模无关（规范写一次、作业改一次）；等到队列发散再补，就必须在带病运行的同时改造流程，此时团队的配合度最低、时间压力最大。上表每一行的"迁移代价"之所以显得高，多数是因为它被当成了被动的补救工程，而不是主动的能力建设。

### 3.7 自检清单

- [ ] 能否用一次查询列出现存全部模型及其 Owner？列不全、或需要人工盘点——先做 Catalog-First，其余模式都挂不上。
- [ ] "合规"是否有可执行的载体（正则 / 契约 / 测试 / CI 规则）？只写在文档或 PPT 里——判定成本仍与人头挂钩。
- [ ] 随机抽一张表，能否一句话回答"一行代表什么（粒度）"？答不出——粒度未声明，下游一切汇总都可疑。
- [ ] Owner 字段里是否出现过团队名、邮箱组或"待定"？出现——审计时无人可追。
- [ ] 最近一次评审记录里，"规范类问题"与"语义类问题"的比例是多少？规范类占多数——这部分可以交给机器。
- [ ] AI / LLM 检查是否被接成了阻断？接了、且误报非零——它已经在被绕过的路上了。
- [ ] 回滚一次模型变更需要多久？如果需要重做而不是 revert——缺版本化。
- [ ] 目录里的"最后更新时间"是否等于该模型最后一次通过评审的时间？不等于——目录描述的不是实际模型。
- [ ] 是否存在一条记录能回答"谁在哪一次变更里改了这个字段"？没有——变更没有被保留成数据。
- [ ] 模型变更的部署路径有几条（仓库 / 手工改库 / 平台界面）？多于一条——可回放性不成立，无论用了多少工具。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 监管 / 审计要求"一份口径"，变更季度级、模型数百 | 集中式 + Catalog-First | 一致性靠把写入权收成一个来源；登记挂在发布入口，审计底稿天生完整 |
| 域 10+、变更周级 / 日级 | 联邦式 + GitOps | 判定必须可执行，否则成本 ∝ 变更数而带宽是常数 |
| 模型数不可枚举、大量无 Owner | 先 Catalog-First | 治理动作需要作用对象集合；顺序决定数据是否完整 |
| 形式检查吃掉大半评审时间 | 联邦式 + AI 增强（只建议、不阻断） | 不确定的判定不能持有确定判定的权力 |
| 必须能回答"谁在何时改了什么" | GitOps + 漂移检测 | 责任记录必须不可篡改，且必须与实际状态一致 |
| 变更频率极低、模型 < 100 | 命名规范 + 轻量目录 | 治理强度超过变更量时，成本全部转化为团队耐心损耗 |
| 多引擎共享同一份模型 | 开放表格式 + 声明式模型（承接 §4） | 物理表模型的每次 schema 变更都要重写数据 |

> 本节小结：决定模型管理模式选择的唯一那条约束，是**"模型的正确性判据被外部化到了什么程度"**——判据只存在于人的判断里，就只能靠收窄写入权（集中式）；判据能写成可执行规则，才能让判定成本与模型数解耦（联邦式 + GitOps + AI 增强）；判据必须被机器读到时，登记就从"事后补录"变成"发布前置"（Catalog-First）。其余约束（规模、变更频率、合规要求）都只是把你推到这条线上的某个位置。
>
> 💡 **思考锚点**：数两件事——你组织的模型变更部署路径有几条（仓库 / 手工改库 / 平台界面），以及有多少条模型规则的形式检查已经写成可执行规则？把这两个数对着 §3.3 决策表找行：你是不是正卡在「判据还没外部化，所以只能靠收窄写入权」这一档？
