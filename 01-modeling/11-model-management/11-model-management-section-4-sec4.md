## 4. 工程实现

§3 把五个模式讲成「判据载体的五种选择」（见 §3.1）：判据留在人脑子里就只能收窄写入权，判据写成可执行制品才能让判定成本与模型数解耦，判据必须被机器读到时登记就从「事后补录」变成「发布前置」。本节不再比较模式，只回答执行顺序的问题：**你手上已经有一批在生产库里、被就地改过很多次的模型，从哪一步开始；每一步手上应该多出什么；怎么验证这一步做对了；存量怎么办。**

本文件以**存量改造**为主：从零搭建的读者顺序完全相同，只是 Step 1 的范围小得多（新库的表本来就数得过来）。整节的顺序依据只有一条——**治理动作需要作用对象，制品需要挂在必经路径上，AI 只能待在不确定性的下游**。这三句话分别决定了 Step 1—3、Step 4—6、Step 7 的先后。

### 4.1 落地步骤

**Step 1：枚举现存模型（2–6 周【经验】，随存量表数量与元数据源能否直接采集而变）**

- 以**只读**方式接入元数据采集：生产库的 information_schema、调度系统的作业定义、BI 的看板引用；先不改任何发布路径，只让数据进来。
- 每张表登记四个必填要素：**表 → Owner → 分层 → 标签**（口径与 §6 的「数据地图」一致），核心表追加**粒度**声明（一行代表什么）。这四个是**采集期**的最小集，用于枚举与缺口分析；发布门禁另有一张更严的必填清单（六项，见 §4.2 与 §4.5 模板一），此时不要拿它去卡存量。
- 生成缺口报告，按四类分开：无 Owner、无分层、无注释、无下游（僵尸候选的判定口径【经验】：30–90 天无访问，随表的更新周期变——日更表取短端，月更、年更表取长端；本章与 §6 的生命周期治理统一取 90 天作默认值）。

- **产物**：可查询的模型清单（一次查询能列出现存全部模型及其 Owner）+ 缺口报告。
- **判据**：不看任何文档，用一次查询列出全部模型与 Owner；若必须人工盘点才能列全，这一步未完成。再抽 20 张表，对比清单里的分层 / 粒度 / Owner 与生产库实际是否一致。
- **为什么必须第一步**：因为评审、下线、影响分析、发通知这些治理动作都需要一个作用对象集合（§3.1）。没有清单时，「给所有无 Owner 的表发通知」只能退化成人工盘点，而盘点的保质期以周计。

**Step 2：把命名规范写成可执行规则（1–2 周【经验】，随规则条数与能落成 CI 的比例而变）**

- 落到制品：分层前缀规则（ods_ / dwd_ / dws_ / ads_ / dim_ / fact_）、字段命名规则、词根词典，以及必填项的校验规则——能进 CI 的那种，而不只是一份文档。
- 表达形式按引擎能力选：能写正则的写正则，能写进模型测试或数据契约的就写进去；**写不成可执行规则的部分（语义命名）单列为「人工判定项」**。
- 存量在这套规则下**只报告不阻断**，新提交阻断。

- **产物**：规则文件 + 存量违规清单（每条附判定依据）。
- **判据**：拿规则跑一遍存量，抽 10 条被判违规的样本人工复核，判断一致；再抽 10 条被判合规的，看有无漏判。规则里若仍留着「命名要有业务含义」这类无法判定的条目，必须移到人工判定项。
- **为什么在枚举之后**：规则的作用对象是清单。先写规则再盘点，规则就只能抽查，而抽查的覆盖率支撑不了任何结论。

**Step 3：Owner 落到人（1–2 周【经验】，随需要指派的表数量与要跨的组织层级数而变）**

- Owner 必须是个人标识（个人邮箱 / 工号），不接受团队名、邮箱组、「待定」。
- 业务 Owner + 数据 Owner 双签；Owner 有义务参加季度模型评审。
- 离职、转岗自动告警；Owner 变更必须留记录（谁交接给谁、何时）。

- **产物**：Owner 矩阵 + 离职告警规则 + 交接记录格式。
- **判据**：查 Owner 字段里是否出现过团队名 / 邮箱组 / 待定；随机抽 3 个 Owner 发起一次模拟变更通知，看是否有人在约定时限内回应。
- **为什么必须在版本化之前**：没有主体的变更记录，是一份不知道谁批过的记录。审计要的是主体，不是群体（§3.5 的「Owner 摆设」说的就是这件事）。

**Step 4：模型入 Git 与漂移检测（2–4 周【经验】，随存量的声明式化程度与部署路径收敛速度而变）**

- 把模型变成声明式制品（DDL 或 YAML）入仓库，语义化版本 + changelog。
- 定义唯一部署路径：以仓库为准；若暂时允许就地改库，必须规定「就地改后须在约定期限内补登记」。
- 建漂移检测作业：定期比对仓库里的 DDL 与生产库的 information_schema，不一致即告警，并以仓库为准重新部署。

- **产物**：仓库结构（按域 / 分层组织）+ 漂移检测作业 + 漂移报表。
- **判据**：在测试环境手工改一张表的字段类型，看漂移检测是否在下一个检测周期报警；不报，检测等于不存在。
- **为什么必须这一步**：「回滚 = revert」的前提是历史状态存在于仓库里；漂移检测若晚于门禁上线，门禁会以「希望的模型」为依据，事故复盘时谁也说不清实际状态。

**Step 5：评审流程与变更管控（2–4 周【经验】，随评审分级规则的复杂程度与工单系统需改造的幅度而变）**

- PR 模板必须包含四件：DDL diff、影响面、兼容性说明、回滚方案。
- 评审按影响面分级：低影响批量过，高影响强制深度评审并保留否决与反例记录。
- 变更管控走五步：申请 → 评审 → 批准 → 发布 → 公告，由工单承载，**禁止事后补录**；紧急通道留痕并事后复核。

- **产物**：PR 模板 + 评审分级规则 + 变更工单模板 + 发布公告模板。
- **判据**：翻最近 20 次评审记录，统计「规范类问题」与「语义类问题」的比例——规范类占多数，说明可自动化的部分还没被拿走；再看高风险变更里是否有过否决记录，从无否决的评审在统计上等于不存在。
- **为什么必须在版本化之后**：评审的对象是 diff。没有版本化，评审只剩「现在长什么样」，只能靠看，不能靠比。

**Step 6：血缘追踪与影响分析（2–6 周【经验】，随作业方言的种类数与静态解析能覆盖的比例而变）**

- 血缘以**自动采集为主**：从作业定义与查询日志解析表级 / 字段级血缘，随作业变更自动更新；人工只做补充与校正；定时校准并记录最后更新时间。
- 对静态解析不了的对象（动态 SQL、脚本任务、外部导入）单独标记为**盲区**并逐步补齐，不要当成「没有依赖」。
- 影响分析 = 血缘反向遍历 + 阈值：下游数量或关键资产超阈值即进入门禁。

- **产物**：血缘图谱 + 影响分析查询入口 + 盲区清单 + 血缘新鲜度报表。
- **判据**：抽 1 个字段问「它被哪些下游字段引用」，答案须与人工核对一致；在测试环境改一个字段名跑一次影响分析，看列出的下游是否漏项；盲区清单是否可见、是否有人认领。
- **为什么必须在门禁之前**：影响面是门禁的输入。没有字段级血缘，门禁只能按整表一刀切——严格但过度，而总在拦的门禁一定会被绕过。

**Step 7：AI 辅助评审与持续运营度量（持续）**

- LLM 检查 DDL：命名是否合规、字段是否有 COMMENT、主键外键是否完整、敏感字段是否缺少分类分级、是否有违反规范的命名——**只输出问题清单与建议，不进阻断**。
- Agent 生成 PR 评审草稿，由人签署；模型调用成本必须有归属人。
- 运营度量按月出：Owner 健康度（是否具体到人、有无离职未交接）、漂移数、盲区数、孤儿 / 僵尸表数、评审中规范类问题的占比。

- **产物**：AI 检查流水线（建议层）+ 治理月报 + Owner 健康度看板。
- **判据**：检查阻断规则里是否出现 LLM 判定（出现即顺序反了）；月报里是否至少有 4 个指标能被第三方用同一条查询复算；抽 3 条 AI 建议，看是否有「人工消解」的处理记录。
- **为什么放在最后**：形式判定必须先被可执行规则拿走，AI 才只处理剩下的、真正不确定的部分（§3.2.4 的顺序）。反过来的做法是让不确定的判定持有阻断权，此时团队消音的最短路径是改一行流水线配置。

最常被跳过的是 **Step 1 与 Step 4**。跳过 Step 1 的症状：门禁只对新模型生效，存量无人认领，等审计问「有多少模型、归谁管」时答不出来。跳过 Step 4 更隐蔽——Git 里的 DDL 与生产库不一致，而**没人知道差在哪**；这类不一致只在事故复盘时暴露，且暴露时已无法判断哪些表被绕过过。

### 4.2 关键技术点

**命名规范（可执行化）**

- **做法**：前缀 + 词根 + 字段命名规则写成正则 / 校验配置并接入 CI；语义命名单列为人工判定项。
- **机制**：因为规范只有变成机器能执行的判定，判定成本才能与模型数解耦，所以「是否合规」从「开一次会看一遍」降级为「构建通过或失败」。
- **失效条件**：**当规范细到需要一份专门文档才能解释时，新人会优先选择绕过**（形态见 §3.5「规范过严」）。症状：新提交频繁触发豁免；有人写脚本自动改名以通过校验，而语义不变。
- **档位**：结构性判断，无数字。

**版本管理（Git + 漂移检测）**

- **做法**：模型入仓库、语义化版本（v1.2.3）+ changelog；以仓库为唯一部署路径；漂移检测常开。
- **机制**：因为每个历史状态都是一个 commit，所以可回滚是版本控制系统的既有能力，回滚成本 = 一次 revert，不需要另建版本机制。
- **失效条件**：**当团队仍保留直连生产改库的权限时，Git 记录的是「希望的模型」而不是「实际的模型」，且背离程度不可测量**。症状：漂移报表长期有告警但无人处理；回滚之后生产状态与预期不符。
- **档位**：结构性判断，无数字。

**Owner 制度（具体到人）**

- **做法**：Owner 校验为个人标识；业务 + 数据双签；离职 / 转岗自动告警；Owner 出席季度评审。
- **机制**：因为事故时需要的责任粒度是「一个人」，而系统最容易记录的粒度是「一个团队」，两者的差就是通知发不出去的原因；校验做在登记环节，不靠意识。
- **失效条件**：**当人事变动后没有自动重算 Owner 时，记录会静默失效**。症状：某张表的变更通知发出后无人响应，追查发现 Owner 已离职。
- **档位**：结构性判断，无数字。

**变更评审（按影响面分级）**

- **做法**：PR 必带 diff、影响面、兼容性说明与回滚方案；低影响批量过，高影响深度评审；记录保留否决与反例。
- **机制**：因为评审带宽有限，所以它只能按影响面分配而不是按提交顺序分配；否则改一个字段名与换一张核心表只获得同样的几分钟。
- **失效条件**：**当评审的 KPI 被做成「通过率」或「评审吞吐」时，评审反转成盖章**。症状：一次会议几分钟通过大量变更；评审记录里从无否决。
- **档位**：结构性判断，无数字。

**变更管控（五步 + 工单）**

- **做法**：申请 → 评审 → 批准 → 发布 → 公告，由工单系统承载；禁止事后补录；紧急通道留痕并事后复核。
- **机制**：因为变更本身也是数据——把它保留成可回放的记录，审计、追责与复盘就可以在事后进行，不必全部压在变更那一刻去解决。
- **失效条件**：**当工单允许在发布之后补录时，它变成记录工具而不是控制手段**。症状：工单时间戳普遍晚于实际发布时刻；紧急通道的使用频率逐季上升。
- **档位**：结构性判断，无数字。

**目录化（Catalog-First：登记是发布前置）**

- **做法**：把必填项（分层 / 域 / 粒度 / Owner / 上游 / 评审号）接进发布门禁，缺项发不出去；存量先只采集不阻断。**这六项就是发布门禁的完整清单**，§4.5 模板一的 `required_meta` 与之同口径；Step 1 的四个采集要素是它的前置输入，不是它的替代。
- **机制**：因为查询者对目录的信任是一次性的，被过期信息误导过一次就会永久回到「问熟人」，所以登记必须挂在必经路径上，而不是靠自觉维护。
- **失效条件**：**当登记被做成事后补录时，「可发现」反转成「不可信」**。症状：目录检索与引用次数持续下降；同一模型在目录里出现两条记录。
- **档位**：结构性判断，无数字。

**血缘追踪（自动采集 + 新鲜度）**

- **做法**：从作业 SQL 解析表级 / 字段级血缘并随作业更新；定时校准；记录最后更新时间；解析不了的对象标为盲区。
- **机制**：因为人工登记的血缘会静默过期，而过期的血缘比没有血缘更危险（它给出错误的信心），所以血缘必须由自动采集维持，并带上新鲜度这个可观测字段。
- **失效条件**：**当血缘采集一次后不再校准时，依赖关系已经变了而图谱还是旧的**。症状：影响分析列出的是半年前的下游；排查问题时工程师不信血缘，改为手动搜索。
- **档位**：结构性判断，无数字。

**影响分析（反向遍历 + 阈值）**

- **做法**：基于血缘反向遍历计算下游，含递归级联（指标 / 看板 / 特征）；按下游数量与关键资产判定，超阈值即阻断合并。
- **机制**：因为「改这个字段会破坏谁」的答案精度决定了门禁是否会被绕过——粒度不够的门禁只能整表一刀切，而过度的拦截必然被绕过，所以精度比严格程度更决定成败。
- **失效条件**：**当影响面只在发布之后以告警形式给出时，它反转成事后通知**。症状：下游任务失败后才发现，这条路径其实早就在影响面清单里列过。
- **档位**：结构性判断，无数字。

**Schema Evolution（兼容性纪律）**

- **做法**：加字段必须向后兼容并允许默认值；改类型必须给出双写 / 回填方案与切换时点；删字段必须先确认消费方已下线（公告 + 缓冲期）。
- **机制**：因为下游清单随时可查（见上一条），兼容性处理可以从「尽量小心」变成「按清单逐条处理」——风险由清单决定，而不是由记忆决定。
- **失效条件**：**当删字段只走公告、不走消费方下线确认时，风险落在「谁没看公告」上**。症状：下线之后下游任务静默产错，而不是报错。
- **档位**：结构性判断，无数字。

**AI 辅助评审（只建议、不阻断）**

- **做法**：LLM / Agent 读 DDL 检查命名、注释、主键外键、敏感字段分级与 Owner 完整性；生成评审草稿；输出带「谁确认过」；误报要有「人工消解」通道。
- **机制**：因为语义正确性没有外部标注（口径选得对不对、粒度定得合不合适），模型只能靠上下文相似度猜，而猜错的形态恰好是「看起来合理」，所以它只能进建议层。
- **失效条件**：**当 AI 检查被接成阻断且误报率非零时，自动化反转成门禁被系统性绕过**。症状：流水线配置里出现例外项，改配置的频率高于申诉的频率。另外模型调用按量计费而使用者是千百个业务方，成本接口要单独界定。
- **档位**：结构性判断，无数字。

### 4.3 工具链与平台

下表按类别给出候选、**选型判据**与**不选它的代价**。判据的共性是：先问「这一层要判定什么」，再看候选能不能承担那个判定，最后才比较功能多少。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| **集中建模** | PowerDesigner、ER/Studio、Navicat、IBM InfoSphere | 只在「写入权必须收成一个来源」时选：监管报送、企业级单一数仓、变更季度级；判据是能否接受模型提交排队 | 变更频率升到周级后队列发散，团队直接在库里建表，产出影子模型——状态比治理前更差 |
| **协作建模** | dbt、SQLMesh、Coalesce、DbSchema | 判据是「规范能否写成可执行的测试」：能写进 CI 的选它；写不进去，说明团队还没准备好联邦式 | 只引入工具而不建规范与测试，得到的是无治理，不是联邦式 |
| **数据目录** | DataHub、Apache Atlas、Unity Catalog、OpenMetadata、阿里 DataWorks | 先看能否一次枚举全部模型（采集覆盖），再看登记项能否接进发布路径（门禁能力），最后才比检索体验 | 只做检索不做门禁的目录会退化成一次性盘点，使用量随信息过期而流失 |
| **版本管理** | Git、GitHub、GitLab、Bitbucket、DataOps 方向的工具链 | 判据是「部署路径是否只有一条」；工具强弱是次要变量，路径数量直接决定可回放性 | 路径多于一条时，仓库记录的是希望的模型，回滚与审计都不可靠 |
| **血缘追踪** | DataHub Lineage、Apache Atlas、OpenLineage、Databricks Unity（Unity Catalog 的血缘能力） | 判据是能否解析你们自己的作业方言，以及能否记录新鲜度与盲区清单 | 覆盖不到脚本与长尾作业时，那些依赖变成不可见风险，事故后才被发现 |
| **变更管控** | Jira、ServiceNow、自研工单系统 | 判据是「工单能否阻断发布」：只能记录不能阻断的工单，本质是事后台账 | 工单变成事后补录，紧急通道常态化，管控形同虚设 |
| **AI 辅助评审（2024+）** | Cursor + dbt、AI Code Review 类工具、Databricks Assistant | 判据是能否配置在建议层、误报能否人工消解、成本能否归属到人 | 接成阻断且误报非零时，团队会改配置消音，而不是申诉 |
| **代码评审** | GitHub PR、GitLab MR、Phabricator | 判据是「评审记录能否回答谁在何时批准了什么」 | 没有不可篡改的批准记录，责任定位只能靠回忆 |
| **数据契约** | Bitol、Data Contract Specification、Protobuf、OpenAPI | 判据是契约格式是否被上下游同时工具化——能被自动校验才算契约 | 契约只写在文档里，等于一份没人执行的约定 |

这一类里最容易被误选的是**协作建模（dbt 一类）**：团队看到「互联网公司都用它」就把写入权下放，却没有同时建立可执行的规范与 CI 门禁——得到的不是联邦式，而是无治理（误选形态见 §3.3）。另一个常见误判在**目录**：采购标准是检索体验，而真正的分水岭是采集覆盖与登记门禁，检索体验只在数据可信的前提下才有意义。

还有一点必须说明：上表部分候选是**产品族或厂商能力名**（如「DataOps 方向的工具链」「AI Code Review 类工具」「Databricks Unity 的血缘能力」），同一族下具体产品的功能边界与在售状态会变，**请以各厂商官方文档的当前版本为准**；本节只给选型判据，不代为断言某项具体特性是否存在。

### 4.4 存量迁移

存量改造与新建的差别只有一句话：**存量里已经有一批模型被就地改过很多次，而这个过程没有留下记录**。所以迁移的第一原则是——**先补事实，再改流程**。

**① 立刻见效、且能立刻回退的动作**

- 打开只读元数据采集：立刻得到模型清单与缺口报告，关掉采集器即回退。
- 给现存模型补 Owner 与 COMMENT：**只补不删、不阻断**。
- 对新模型启用「有 Owner + 过评审才能发布」两个条件：只作用于新增，存量不受影响，出问题时把门禁摘掉即可回退。
- 建漂移检测，**先只告警不阻断**。

这四条共用一个判据：**改的是采集与新增，不动存量模型的既有行为**。因此可以在一个季度内上线，也可以在发现问题时一周内撤回。

**② 历史资产怎么分类处理**

| 历史资产 | 处理方式 | 为什么这样处理 |
| --- | --- | --- |
| 高频变更 + 有跨团队下游的表 | 优先纳入仓库与门禁 | 门禁收益与变更频率、下游数量成正比，先把门禁装在最值钱的地方 |
| 稳定、无下游的僵尸表（判定口径【经验】：30–90 天无访问，随更新周期变，本章默认 90 天） | 打标挂账，进入下线评审队列，不返工 | 给一张没人用的表补粒度与注释是净浪费，先确认它该不该存在 |
| 已合规的表（有 Owner / 注释 / 分层 / 粒度） | 只做校验，不返工 | 治理不是重写一遍，是让已有合规资产被机器认出来 |
| 绕过流程建的影子表 | 先收编登记（补 Owner 与分层），再纳入门禁 | 影子表的危险不是不规范，是它不在任何清单里 |
| 历史血缘与影响面 | 不从零重建，靠自动采集逐步覆盖，并显式标出盲区 | 人工补绘历史血缘的成本与规模成正比，且完成后立刻开始过期 |

分类原则只有一句：**能用新规则的用它，不能用的打标挂账——但不要把它悄悄删掉**。挂账项必须在下一轮评审时被显式处理，否则它会变成没人认领的历史。

**③ 双轨怎么维持、维持多久**

双轨的两条轨道是「仓库部署（声明式）」与「就地改库（允许但必须补登记）」。脆弱的不是并行本身，而是**并行期的身份不清**。

- 硬规则一：**新增表必须走仓库**，没有例外。
- 硬规则二：存量表允许就地改，但改完须在约定期限内补登记；未补登记的按未授权变更处理。
- 硬规则三：**漂移检测必须常开**——它是双轨期唯一能发现「实际状态偏出仓库」的手段。
- 维持期按季度计，通常 1–2 个季度【经验】。长度不取决于日历，而取决于**高风险表被纳入门禁的比例**：这个比例到了你们能接受的水平，就可以收口。

**④ 什么信号说明可以退出双轨**

四个信号同时满足才退出，缺一个就再等一个季度：

1. 连续 4–8 周漂移检测零告警【经验】（观察窗口随发布频率变：周更及以上取短端，月更取长端），且告警的响应时长在约定时限内；
2. 新表 100% 从仓库发布（用「仓库新增 vs 生产库新建表」的比对即可验证）；
3. 直连生产改库的权限已收回或改为审批制，且近一个季度没有走过紧急通道；
4. 至少有一次真实事故复盘是靠血缘与影响分析定位的——说明它已经进入日常，而不是摆设。

退出时要做的最后一件事：**把「以仓库为准」写进制度并公告，明确就地改库不再合法**。不宣布就不算退出——否则双轨会以更慢的速度继续存在下去。

### 4.5 模板 / 示例

**模板一：命名与必填项的 CI 校验规则**

```yaml
# model_rules.yaml —— 能写成规则的才写进来；写不进来的单列为人工判定项
table_prefix:                          # 分层前缀（层级口径见主文件 §1.2）
  - {prefix: ods_,  layer: ODS}
  - {prefix: dwd_,  layer: DWD}
  - {prefix: dws_,  layer: DWS}
  - {prefix: ads_,  layer: ADS}
  - {prefix: dim_,  layer: DIM}
  - {prefix: fact_, layer: DWD}
field_name: "^[a-z][a-z0-9_]*$"        # 字段名：小写 + 下划线
required_meta: [layer, domain, granularity, owner, upstream, review_id]  # 门禁项：与 §4.2 的目录化门禁同一套，缺任一项即构建失败
owner_must_be_individual: true         # 不接受团队名 / 邮箱组 / 待定
manual_judgement:                      # 无法机器判定的，显式列出
  - 命名是否体现了业务过程（不阻断）
  - 字段的业务含义是否准确（不阻断）
```

**怎么用**：`table_prefix` 与 `field_name` 按你们的分层定义改；`required_meta` 是**门禁项**，六项与 §4.2 同一口径（登记期的四个采集要素不含粒度、上游与评审号，别拿采集清单去搭门禁），只对新增模型生效，存量只报告不阻断。最后一节不要删——把不能机器判定的部分显式写出来，才能避免有人用正则去逼近语义。

**模板二：数据契约（跨三个以上消费方时使用）**

```yaml
# data_contracts/users_v1.yaml
version: 1.2.0
dataset: users
domain: cdp
description: 用户主数据，跨业务线统一
owners:
  business: {业务 Owner 个人邮箱}        # 团队邮箱只是格式示例，按 Owner 制度填到人
  data: {数据 Owner 个人邮箱}
schema:
  fields:
    - name: user_id
      type: string
      nullable: false
      pii: false
      description: 用户唯一标识
    - name: email
      type: string
      nullable: true
      pii: true
      classification: confidential
      description: 用户邮箱（敏感字段）
sla:
  freshness: {承诺的更新频率}
  availability: {承诺的可用性，按你们能承担的水平填}
  quality:
    completeness: {承诺值}
    accuracy: {承诺值}
lineage:
  upstream: [mysql.users, kafka.user_events]
  downstream: [ads.user_profile, ml.user_features]
```

**怎么用**：结构（版本号 / 数据集 / 域 / 双 Owner / schema / SLA / lineage）可直接套用；**owners 必须填到人**，SLA 里的三项不要照抄示例，要填你们愿意被追责的值。契约的价值不在文件本身，而在上游改动时会自动跑一次校验——只有被工具化的契约才算契约。

**模板三：变更工单（五步）**

```markdown
# 模型变更单 - {变更ID}

1. 申请：模型 ｜ 变更类型（CREATE / ALTER / DROP / RENAME）｜ 申请人 ｜ 期望发布窗口
2. 评审：影响面（下游表 / 看板 / 特征 数量）｜ 兼容性说明 ｜ 回滚方案 ｜ 评审记录链接
3. 批准：数据 Owner ｜ 业务 Owner ｜ 高风险变更需跨级批准
4. 发布：发布时刻 ｜ 发布人 ｜ 是否走紧急通道（走则填理由）
5. 公告：通知对象 ｜ 通知渠道 ｜ 缓冲期 ｜ 下游逐个确认
```

**怎么用**：第 4 步的「发布时刻」必须由系统写入，不要手工填——手工填的时间戳没有证明力；第 5 步的「下游逐个确认」不是群发通知，而是按影响面清单勾选，清单由 §4.2 的影响分析产生。变更类型一律照主文件 §2.2 的 `δM ∈ {CREATE, ALTER, DROP, RENAME}` 填写。

**模板四：LLM 规范检查的 Prompt**

```
你是一名资深数据治理专家。请审查以下 DDL 文件，检查：
1. 命名是否符合规范（ods_* / dwd_* / dws_* / ads_* / dim_* / fact_* 等前缀）
2. 字段是否有 COMMENT
3. 主键、外键是否完整
4. 是否有敏感字段缺少分类分级
5. 是否有违反命名规范的表名 / 字段名

请逐条列出问题，并给出修改建议。
输出格式：每条含「位置 / 问题 / 建议 / 置信度」，置信度低的单独列出。
```

**怎么用**：这个 Prompt 的输出**只能进建议层**，不要接成阻断（理由见 §4.2 最后一条）。第 5 条与前四条重叠，实际使用时按你们最常出问题的三类删减；输出里保留「置信度」是为了让复核的人知道先看哪几条。用它之前先确认已有的规则能覆盖第 1、2 条——能被规则判定的部分不该交给模型。

### 4.6 成本：这套东西的账单

模型管理是本书里少见的**几乎不花机器钱、几乎全花人力**的主题。三项成本（硬件 / 人力 / 云账单）里，硬件与本主题无关，账单集中在下面两项：

- **人力（主项，也是唯一的大头）**：它的计费单位是**变更次数**，不是数据字节。**推算**：一个季度纳入门禁的模型数为 N、平均每张每季变更 f 次，则双签评审事件数 ≈ N × f；单次深度评审工时按你们实测的中位数估【经验：随影响面分级，通常几十分钟量级，随跨团队数上升】。这就是「贵在这里」的机制——账单随「纳入门禁的模型数 × 变更频率」的乘积走，与库里存了多少 TB 无关；所以把门禁一次铺满全域，成本会在评审队列上一次性兑现（§4.1 Step 5 的评审分级就是为压这一项而设）。
- **云账单（固定项）**：目录 / 血缘平台（DataHub、Atlas 一类，§4.3）是常驻服务，账单≈一份固定的集群与元数据存储，与模型数弱相关【经验：小规模时单位成本摊得极差】；血缘解析是随变更触发的批处理，按作业方言的解析成本计【经验】。
- **AI 评审（人力那一格的边际项）**：LLM 读 DDL 按 token 计费。**推算**：一份数百行 DDL × 每次提交跑一遍 ≈ 数千 token/次，单价按所选模型官方定价页代入（每百万 token 落在数美元到数十美元区间【经验】），相对人力评审可忽略，但按 §4.2 末条必须记到人。

**硬件：与本主题无关**——不新增任何专用硬件，账单里没有这一栏。通用的 FinOps 归因口径见 [Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节只标这个主题把钱花在哪一格。

### 4.7 容灾与故障演练

模型管理没有「另一个可用区」可切——它的关键资产是**一个 Git 仓库加一次能列出全量模型的查询**，没有不可重建的在线状态，跨地域容灾在这里不成立（通用容灾见 [Ch12 §07](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)）。本主题独有的失效形态是**结论不可复现**：

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 漂移：仓库 DDL 与生产库不一致（§4.1 Step 4） | 回滚、审计、影响分析**全部以假基线为依据** | 以生产库为临时事实源，重新采集后重建仓库 | 测试环境手工改一张表的字段类型，看漂移检测是否在一个检测周期内报警 | RTO【经验：一个检测周期，分钟级到天级，随检测频率】 |
| 血缘图过期：采集器停摆（§4.1 Step 6） | 影响分析漏项，门禁放过本应拦住的变更 | 冻结高风险合并，退化为人工逐个核对下游 | 抽一个字段问「它被哪些下游引用」，与人工核对是否一致 | RPO【经验：随血缘新鲜度目标，通常天级】 |
| 目录不可用：平台宕机（§4.3） | 找数回退到「问熟人」；登记若挂在门禁上则发布阻塞 | 用上次导出的清单只读兜底，发布走紧急通道并留痕 | 停掉目录，验证能否仍用导出清单回答「这张表归谁」 | RTO【经验：小时级】 |

真正的判据不是「能不能切机房」，而是**换一个人、换一天，同一张表的两份答案是否一致**。混沌演练的通用方法（稳态假设、故障注入、爆炸半径）见 [Ch12 §06](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)，本节只指出本主题要注入的是什么。

### 4.8 演进路线：0 → 1 → 100

模型管理的每一级都把成本压在同一个资源上——**判定成本**，只是每级换一处去变现：

- **0 → 1（最小可用）**：只读元数据采集 + 一次查询列出「模型 → Owner」（§4.1 Step 1），只对新增表启用门禁。**便宜在**不动存量、一个现成采集器就能起步；**先坏的是清单的时效**——采集一次后就静默过期，缺口报告没人看，几个月后它退化成一张「曾经正确」的快照。
- **1 → 100（规模化）**：规则可执行化、入 Git、Owner 到人、门禁覆盖高风险表、血缘自动采集。**变贵的是运维形态与协调节奏**——多一条必须常开的漂移检测、一条双轨补登记纪律、每季度一轮双签评审；**先坏的是评审带宽**：门禁覆盖率铺到一定比例后深度评审开始排队，团队转而走紧急通道（§4.2「评审反转成盖章」）。
- **100 →（下一道坎）**：全域门禁 + AI 建议层。**变贵的是结论可信度的维护**——AI 建议引入大量「看起来合理」的误报，「人工消解」成了新的固定开销；**先坏的是陈旧还剩多少看得见**：规模越大，漂移与血缘的过期越难被单个值班发现，这正是 §1.4 那句「智能 vs 可信」在落地层的兑现。

### 4.9 自检清单

- [ ] 不看任何文档，能否用一次查询列出现存全部模型及其 Owner？
- [ ] Owner 字段里是否出现过团队名、邮箱组或「待定」？
- [ ] 随机抽一张表，能否一句话回答「一行代表什么（粒度）」？
- [ ] 最近 20 次评审记录里，「规范类问题」与「语义类问题」的比例是多少？
- [ ] 命名规范里有多少条能被执行？写不成规则的条目，是否被单列为人工判定项？
- [ ] 模型变更的部署路径有几条（仓库 / 手工改库 / 平台界面）？多于一条，可回放性不成立。
- [ ] 在测试环境手工改一张表的字段类型，漂移检测会在下一个周期报警吗？
- [ ] 随机抽一个字段，它被哪些下游字段引用？血缘图谱的答案与人工核对是否一致？
- [ ] 影响面是在 CI / 发布门禁阶段给出，还是发布之后才告警？
- [ ] 血缘的「最后更新时间」是否可查？盲区（无法解析的作业）是否有清单且有人认领？
- [ ] AI 检查是否被接成了阻断？接了、且误报非零，它已经在被绕过的路上了。
- [ ] 治理月报里的每个指标，能否被第三方用同一条查询复算出来？

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **Step 1 的枚举——让「现存模型 + Owner」成为一次查询的结果**。它比其余环节更值得投入，因为它是所有后续动作的前置条件：命名规范要作用在清单上，Owner 制度要有对象，血缘与影响分析要挂在具体实体上；清单不在，后面每一步都只能退化成抽查，而抽查的覆盖率支撑不了任何结论——**包括「我们已经治理过了」这个结论**。
>
> 💡 **思考锚点**：拿 §4.4 的四个退出信号量一下你自己的双轨期——「连续 4–8 周漂移零告警」「新表 100% 从仓库发布」「直连改库已收回」这几条里，先卡住的是哪一条？如果卡在「漂移零告警」上，往回追，是不是因为 Step 1 那份「现存模型 + Owner」清单还没出全，漂移检测连完整的比对基线都没有？
