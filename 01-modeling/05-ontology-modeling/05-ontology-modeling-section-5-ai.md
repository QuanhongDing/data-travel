## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题在于**没有时间维度**。同一份清单里，「某个本体已经在国家级医疗系统里跑了十几年」和「某个 Agent 自主演化本体的方向」被并列写成"演进方向"，而这两件事对读者的意义完全不同：前者明天就能排进路线图，后者三年内大概率还进不了生产。清单还会掩盖另一个差别——有的方向改变的是**成本函数或接口边界**，有的只是**换了个前端**（把原来的表单换成对话框）。读者按一张没有时间维度的清单排计划，踩空是必然的。本节给每个方向一个级别，级别由**三条可核验判据**决定，不由感觉决定：

- **L1 生产可用**：① 已 GA 且有正式 release note；② 有第三方（非厂商、非项目承建方）公开生产案例；③ 接口稳定。三条**全中**才算 L1——读者可以排进路线图。
- **L2 可试点**：已可用但接口或生态未稳，或只有厂商 / 建设方自有案例，或只在小规模被验证。可以做 PoC，**不要做核心依赖**。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录，**不要在架构里预留假设**。

**第②条是本节最难满足的一条，也是决定评级的关键。** 公开材料里"某团队用 X 做了 Y"的绝大多数是**建设方自述**——自己做项目、自己写文章，按上面的定义落在 L2（"仅有厂商自有案例"）里，而不是 L1。本节对②的判定要求是：案例来自既不是能力提供方、也不是项目承建方的第三方，形态只有两种——已上线系统的**采用方自己发布的公告**，或独立高校 / 研究机构对生产数据的**公开抽样统计**。法规文本与标准推荐清单不算②：它只证明义务或推荐存在，不证明有人真的在做；把一份推荐清单当成生产案例，会把 L1 判给一个没人用的能力。写不出②就写不出 L1，**第②条核不到就是 L2**——这不是贬低，是准确。同样地，本节不会把某条判据在某个单元格里"就地放宽"：判据只有一套，如果某个方向确实需要不同的判据，只能在正文里显式声明，并让 5.1 与 5.2 的判断完全一致。**本主题下唯一处在 L1 的方向是「复用已标准化的行业与通用本体」**，它恰好也是几个方向里唯一与 LLM 无关的那个。这不是巧合：AI 让本体的**生成**变便宜了，但没有让本体的**验证**变便宜，所以成熟度仍然由那些被反复验证过的老本体把持。

读本节时请守住四条命名与版本纪律，它们决定了你会不会把一份演示当成能力：

- **区分产品名与能力名**：某个能力常被记成某个产品的专属名（自然语言取数在不同平台就叫不同名字），不要张冠李戴。
- **区分已发布与路线图**：路线图条目不能写成既成事实，预览特性要写明"预览"。
- **区分论文原型与产品实现**：论文里的方法名不等于产品里的开关。
- **区分单机与分布式**：单机内嵌的推理引擎不代表能分布式扩展——判断方法是看发布说明里有没有独立的多机执行组件，而不是看基准测试博客。

判据之外还有一条取材纪律：每个方向都会给"读者可以怎么自己核验"。核验的顺序是固定的——

- 先查官方发布说明里有没有这条能力（这是①）。对按半年或按年度发布的行业本体与标准，核验方式不是找某一份固定的 release note，而是看它的发布页上有没有**下一版的日期**与历史版本列表——这类对象没有单一年份，写死一期，下一期就过期；
- 再查有没有**不是建设方**的人写过它在生产中的用法（这是②）；
- 最后看接口有没有变过：如果一年内接口改过两次，即使前两条满足，也只能按 L2 排期。
- 三条都过不了的方向不代表不重要，只代表它还不能进这一版架构；本节对它们的态度是"记录"，不是"否定"。

| 演进方向 | 级别 | 判据（① release note / ② 第三方生产案例 / ③ 接口稳定） | 现在该做什么 |
| --- | :---: | --- | --- |
| **5.2.1 复用已标准化的行业与通用本体**（Schema.org、SNOMED CT、FIBO、IOF，以及 ISO/IEC 21838、ISO/IEC 19763 一类标准） | **L1** | ① 有：两份可点名的发布物——SNOMED CT International Edition 的 Release Notes（1 月与 7 月各一期）与 schema.org 的 Releases 页（2011 年起按版本发布，每版标日期）；② 有：独立高校对生产数据的公开抽样统计（Web Data Commons（曼海姆大学）的「Structured Data」系列报告，按年度分节发布，不是本体发布方自述）；③ 有：词汇表与发布格式多年稳定 | 把已有术语钉到公开 IRI，作为实体链接与校验的锚点；不要自建顶层 |
| **5.2.2 LLM 辅助本体构建 + 符号校验**（OntoGPT、DeepOnto 一类抽取与匹配工具；SHACL 与 Reasoner 做门禁；Neuro-Symbolic 的"神经生成 + 符号验证"范式；Owl2Vec*、BoxE、BoxEL、EL 嵌入作为对齐手段） | L2 | ① 有：开源项目有版本与发布记录；② **缺**：公开案例多由工具方或使用方自述；③ 未稳：输出随模型版本与提示词漂移 | 限范围 PoC：只用于候选生成，出口必须挂校验门禁 |
| **5.2.3 本体驱动的检索**（本体 + 知识图谱 + 向量的混合检索；GraphRAG 与社区检测；图数据库的 LLM 集成） | L2 | ① 有：开源仓库持续发版、有发布记录；② **缺**：案例多为构建方自述；③ 未稳：SPARQL 是标准，但抽取—对齐—检索—校验的编排无跨实现接口 | 在已有向量检索链路上加校验层，不要一次换成图 |
| **5.2.4 本体作为智能体的运行时约束 + Agent 驱动的本体演化**（工具调用的语义层；schema 变更监听与增量提议） | L3 | ① **缺**：无专门承载领域约束的接入约定或产品发布说明；② **缺**；③ 未稳 | 记录并做技术预研；不要写进架构假设 |

表里四个方向与 5.2 的四个小节一一对应，级别与判据在两边完全一致——读者可以拿这张表与 5.2 各节的成熟度行逐条对照，两处对不上就说明有一处需要修正。需要强调的一点是：**唯一处在 L1 的是 5.2.1，而它不是 AI 带来的能力**——这本身就是本节最值得记住的结论之一。

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 复用已标准化的行业与通用本体

- **旧做法与它的卡点**：企业先自建一套顶层本体，再往下长出领域类。卡点不在表达能力，而在**维护人力**：
  - 人维护的词表约三个月后无人维护【经验】，规则最终散落到上百个 ETL 脚本里，本体沦为"只发布、不消费"的文档工程。
  - 自建顶层留下无法回收的成本——上层一旦不动，下层所有领域类都被它的划分绑死，换掉顶层的代价随领域类数量线性增长。
  - 更隐蔽的一条：自建本体没有外部采用者，划分错了也没人告诉你，错误只会以"两个团队的口径对不上"的形式在业务侧暴露。
- **AI 改变了什么机制**：本体的**消费方从人变成了程序**。LLM 要把自然语言里的实体钉到稳定标识上（实体链接），Agent 要把"能不能做"变成可查询的约束（运行时约束）。这使"复用一个被广泛采用的现成本体"从"省事"变成"必要"——因为模型见过的、搜索引擎索引过的、同行工具链里预置的，都是那份公共本体，而不是你自建的那份。这是**成本结构的变化**，不是界面改良。
- **由此得到的**：因为复用公共本体让"同一概念在不同系统里指向同一个 IRI"这件事不必逐对协商，所以实体链接、跨源对齐与检索召回可以共用一套锚点，而且这套锚点自带外部校验——划分不合理时会被其他采用者先发现。
- **由此付出的**：
  - ① 受制于人：行业本体的发布周期与弃用（deprecation）节奏不受你控制，一次版本升级可能让存量数据需要重新映射，且这个工作量集中在升级窗口里。
  - ② 差异化语义无处安放：只能在行业本体之上加一层扩展模块，扩展与原体之间的耦合点成为长期负担（原体改一处，扩展要跟着改）。
  - ③ 覆盖不全：行业本体覆盖"临床概念"，但覆盖不了你的"会员等级"，缺口要自己补，而补出来的部分没有同行校验，质量回到自建水平。
  - ④ 术语权威不等于口径权威：同一份行业术语在两家企业里的统计口径可以完全不同，复用本体只统一了概念，没有统一指标定义。

| 可复用的本体 | 覆盖领域 | 发布节奏 | 复用的判据 |
| --- | --- | --- | --- |
| SNOMED CT | 临床概念与发现 | 半年一次 | 医疗场景做实体链接与术语归一 |
| Schema.org | 通用实体与网页标注 | 按版本发布 | 对外数据交换、检索标注 |
| FIBO | 金融业务概念 | 按版本发布 | 金融监管报送、跨机构对齐 |
| IOF 一类行业本体 | 制造业等 | 各自不同 | 先查其最近一次发布与采用方名单 |
| 政务数据目录与互操作规范（DCAT-AP、CPSV-AP 一类，欧盟 SEMIC 维护，另有若干国别版） | 公共数据目录、政务服务 | 按版本发布 | 政务数据编目与跨机构交换；先确认对端平台采的是哪一版 |
| DBpedia / Wikidata 一类开放数据 | 通用实体 | 持续更新 | 可做实体链接锚点，但众包编辑意味着划分会变，不适合当强约束来源 |

- **判定方法**：
  - 判断某份行业本体能不能依赖，先看两件事：它的发布说明里有没有给出**下一版的日期**（有固定节奏才敢依赖），以及它的本体文件在主流推理机上能否在目标实例规模内加载完成。
  - 判断同事说的"我们已经在用 SNOMED CT"到了什么程度，问三个问题：用的是国际版还是国家扩展版、映射表由谁维护、升级窗口期谁值班。
- **证据与来源**：
  - 【公开】SNOMED CT International Edition 由 SNOMED International 每半年发布一次，发布说明分 1 月与 7 月两期（文档名即该版本的 Release Notes，版本号与发布日期以其发布页所列为准）。
  - 【公开】schema.org 的词汇表按版本发布（2011 年起；每个版本在其官方 Releases 页标出版本号与发布日期，请以该页当前列表为准）。
  - 【公开】第三方生产统计：Web Data Commons（曼海姆大学）的「Structured Data」系列报告，内容是对网页结构化数据标记（schema.org 一类）的抽样统计，按年度分节发布，可在其站点按年份直达具体一期。引用时写明所引那一期的年份，不要写"历年"——按年度周期发布的报告，只有点明年份才可被读者定位到具体一期。
  - 【公开】ISO/IEC 21838 与 ISO/IEC 19763 为已发布国际标准编号，可在 ISO 官网按编号查到范围与版本年份；编号可核验，年份随修订变化，本节不写死。
- **成熟度**：**L1**（① 有正式发布说明：SNOMED CT International Edition 的 Release Notes（1 月 / 7 月各一期）与 schema.org 的 Releases 页（2011 年起按版本发布）；② 有第三方生产证据：Web Data Commons（曼海姆大学）的「Structured Data」系列报告，是对网页结构化数据标记的公开抽样统计，不是本体发布方自述；③ 词汇表与发布格式已稳定多年）。

#### 5.2.2 LLM 辅助本体构建 + 符号校验

- **旧做法与它的卡点**：本体工程的成本集中在"从非结构化业务文档到形式化公理"这一步。METHONTOLOGY / NeOn 把本体工程分成规格说明、概念化、形式化、实现、维护五阶段，而卡点具体在三处：
  - 形式化与维护吃掉绝大部分人力，且这部分人力无法通过加人并行化——它依赖判断，不依赖吞吐。
  - 一句业务规则对应哪条公理，取决于业务口径，而口径通常只存在于少数人的经验里，文档里写不出来。
  - 人工建的词表会过期：源系统改了、业务线并了，本体不动，半年后它描述的世界已经不存在。
- **AI 改变了什么机制**：把"自然语言 → 候选三元组 / 候选公理"这一步的**边际成本**从人对小时改成 token 成本；但**验证成本没有同步下降**——推理复杂度由你选的 OWL 2 profile 决定（EL 是 PTime、QL 可改写为 SQL、DL 才可能踩到不可判定），SHACL 的校验开销由形状数量与实例数量决定，这两者都与"公理是谁生成的"无关。
- **由此得到的**：因为生成变便宜而验证没变便宜，所以正确的生产形态是**高召回生成 + 强精度校验**——多生成候选，再用 Reasoner 查一致性、用 SHACL 查形状、用对齐工具查跨源冲突，把绝大部分候选挡在发布之外，而不是指望"让模型一次写对"。这也解释了近两年公开材料里"LLM 生成 RDF / OWL"的案例几乎都自带一段校验逻辑：不带校验的那些，先出事的不是准确率，而是没有人敢把它的输出接进生产。

```text
业务文档 / DDL / 术语表
   │  ① 抽取（LLM，高召回，允许错）
   ▼
候选三元组（Turtle / JSON-LD）
   │  ② 形状校验（SHACL：基数 / 类型 / 值域）
   │  ③ 一致性校验（Reasoner：不可满足类、矛盾公理）
   │  ④ 跨源对齐（同义不同名 → 显式等价边）
   ▼
候选变更集 ──► 人工裁决（概念粒度、口径归属）
   ▼
已发布本体（命名图记来源、PROV-O 记变更）
── ① 便宜，②③④ 昂贵；预算要花在门禁上，不是花在"让模型更准"上
```

- **由此付出的**：
  - ① **语法合法但语义错误**成为主导错误形态：把子类方向写反（把"父母"写成"父亲"的子类）在语法上完全合法，只有 Reasoner 把它算成"某个类不可满足"时才暴露；而这类错误一旦发布，下游所有基于它的推论一起错。
  - ② 审核成本从"写"平移到"读"：能读 OWL 公理并判断业务对错的人很少，比会写 SQL 的人少一到两个数量级【经验】，于是生成量放大一到两个数量级之后，审核队列成为新的瓶颈。
  - ③ 输出不确定性带来的工程后果：同一份文档两次抽取得到不同候选集，本体版本之间的差异充满噪声，逐行 code review 基本失效，只能靠校验结果做门禁——这等于把质量责任从"评审"转移给了"工具链"。
  - ④ 依赖外移：抽取质量随模型版本变化，一次模型升级可能让既有的提示词与阈值全部失效，需要重新回归。
  - ⑤ 能力错配：把这类工具交给不熟悉描述逻辑的团队，产出的候选会以"看起来都对"的姿态通过人工评审，错误被推迟到推理阶段才暴露。

| 错误形态 | 谁能发现它 | 发现时机 |
| --- | --- | --- |
| 语法错、前缀写错 | 解析器 | 提交时 |
| 子类方向写反、等价类冲突 | Reasoner | 校验时（可能很晚才算出不可满足） |
| 基数、值域、必填缺失 | SHACL | 校验时 |
| 概念粒度与业务口径不符 | 只有人 | 审核时 |
| 同义不同名（两个 IRI 指同一个人） | 对齐工具 + 人 | 合并时 |
| 公理与业务口径不符（写得出来、但不该这么写） | 只有人 | 审核时，且常在半年后才被业务侧发现 |

- **判定方法**：
  - 判断一个"LLM 建本体"的项目能不能信，看它的流水线里有没有独立于生成步骤的校验环节，以及校验失败率是多少——失败率长期接近零，通常意味着校验写得没有意义。
  - 判断一个工具是否还值得接，看仓库最近一次提交与未关闭 issue 的积压量，而不是看 README 里的功能清单。
- **证据与来源**：
  - 【公开】OntoGPT / SPIRES 提示模式（Monarch Initiative，2023 年公开，用于从文献批量抽取本体化断言，请以项目发布说明为准）。
  - 【公开】DeepOnto（含 BERTMap 一类本体匹配基线，2023 年前后公开，请以项目发布说明为准）。
  - 【公开】本体嵌入的代表工作：Owl2Vec*（2020 年前后公开）、BoxE（NeurIPS 2020）、BoxEL 一类盒嵌入、EL 的几何嵌入（2019），以及 2024 年前后出现的"用 LLM 增强本体嵌入"一类工作（LLM-enhanced ontology embedding）——它们在本节里的定位是"对齐与匹配的候选生成器"，**不承担一致性判定**；各项目的具体版本与发布日期请以其发布页为准。
  - 关于"某国重启神经符号研究、投入多少亿"这类资助金额说法，请按资助机构官网的项目编号核验，本节不转述二手数字。
- **成熟度**：**L2**（① 有（开源项目有版本与发布记录）；② 缺（公开案例多由工具方或使用方自述）；③ 未稳（输出随模型版本与提示词漂移））。

#### 5.2.3 本体驱动的检索

- **旧做法与它的卡点**：纯向量 RAG 的检索是相似度近邻，它的问题不是"不够准"，而是能力边界：
  - 无法多跳（A 的供应商的母公司是谁），也拿不到"关系"这类只存在于图上的信息。
  - 无法判断检索回来的两条事实彼此矛盾，只能把矛盾一起交给模型去圆。
  - 主文件 §1.2 把这条列为既有痛点——LLM 输出的结构无法被机器验证；常见补丁是往提示词里加"请只依据检索内容回答"，但提示词是自然语言软约束，拦不住任何东西，也无法在发布前被测试。
- **AI 改变了什么机制**：检索的**索引结构**从"一列向量"变成"类型与关系约束（本体的 TBox）+ 图遍历（知识图谱的 ABox）+ 向量近邻"三者并联，LLM 从"唯一的检索者"退回到"查询改写器 + 答案组织器"。约束的载体从提示词（自然语言、不可校验）迁到本体（形式化、可校验）——这是**约束载体的迁移**，不是检索算法的改良；判断一个方案是不是真前进，看它的约束写在哪一层即可。
- **由此得到的**：因为约束从提示词移到了 SHACL / OWL，错误有了**前置拦截点**：违规结果在进入答案之前就被拒，而不是等用户发现；同一份本体同时约束"机器抽取的事实"和"人发起的查询"，语义只有一处裁决，两条路径不会各说各话。
- **由此付出的**：
  - ① 成本结构从 O(查询) 变成 O(语料)：图抽取、实体链接、社区检测与摘要会随语料变更整体重算；【经验】这类索引的构建开销与语料 token 数近似成正比，社区检测再叠加一次图算法开销，等于把"每次查询便宜"换成"每次更新昂贵"。
  - ② 新的单点：图错了，检索全错，而且比向量召回的错更难定位——向量召回错在"召回了不相关段落"，肉眼可查；图检索错在"关系边连错"，从答案表面看不出来。
  - ③ 对齐成本：不加本体约束会出现"同义不同类"，加上本体又多出"把抽取概念对齐到本体"这一步，而本体对齐的误配率不免费（字符串、结构、嵌入、LLM 四类方法各有其误配形态）。
  - ④ 可移植性下降：SPARQL 是标准，但"用本体约束检索"的整体编排没有跨实现约定，换一个图存储往往要重写编排层。
  - ⑤ 评估口径变化：向量检索的评测指标是召回与相关性，加上图与本体之后，评测要多一列"约束命中率"，否则改进无法被证明，团队只能靠感觉争论要不要继续投入。

| 检索形态 | 能做什么 | 主要成本 | 典型失败模式 |
| --- | --- | --- | --- |
| 纯向量 | 语义近邻、模糊匹配 | 每次查询低 | 召回不相关、无法多跳、无法判矛盾 |
| 图遍历（无本体约束） | 多跳、关系聚合 | 建图与维护 | 同义不同类、实体连错 |
| 图 + 本体约束 | 多跳且可校验 | 建图 + 对齐 + 校验 | 本体覆盖率不足，"查不到"被误当"不存在" |

- **判定方法**：
  - 判断"我们的 RAG 用上了本体"是否属实，问两件事：检索结果里有没有一条约束来自本体（而不是提示词），以及这条约束在发布前能否被测试固定下来。答不上来就是没用到。
  - 判断 GraphRAG 值不值得上，先量语料更新频率：语料每天全变的话，图索引的重建成本会吃掉全部收益。
- **证据与来源**：
  - 【公开】Microsoft GraphRAG 于 2024 年开源，配套论文《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》（Microsoft Research，2024），流程为抽取实体关系、Leiden 社区检测、社区摘要、本地与全局两类检索。
  - 【公开】Neo4j 的 `neo4j-graphrag-python`（2024）把图检索封装为可复用组件。
  - 【公开】Stardog Voicebox（2023 年公开）演示了用自然语言直接查询知识图谱。
  - 阿里云 GraphScope、蚂蚁 TuGraph 属图计算 / 图数据库平台，是否内置"本体驱动的检索编排"请按其官方文档核验，本节不代其断言；把知识图谱说成某个通用模型的"内置事实校验层"，同样应按该产品的官方文档核验。
- **成熟度**：**L2**（① 有（GraphRAG 等开源项目持续发版、有发布记录）；② 缺（案例多为构建方自述）；③ 未稳（编排无跨实现接口））。

#### 5.2.4 本体作为智能体的运行时约束 + Agent 驱动的本体演化

- **旧做法与它的卡点**：Agent 的能力边界写在代码与提示词里（"能不能给 VIP 发券"）。具体卡在三处：
  - 改一条规则就要改代码、重新评测、重新发布，规则的更新速度被研发流程锁死。
  - 工具调用的参数校验靠 JSON Schema，它只能校验形状（是不是字符串、是不是枚举值），校验不了语义（这个客户到底是不是 VIP、这张券在这个地区能不能发）。
  - 演化一侧同样是人工：源系统改结构，靠人发现、靠人改本体，发现晚了就出事故。
- **AI 改变了什么机制**：把**约束的载体**从代码与提示词改成一份可查询的形式化模型，运行顺序从"直接调用工具"变成"先查本体、再决定是否调用"。这是接口边界的变化——从"函数签名"扩到"领域公理"。要特别注意跨模型的工具接入约定（MCP，Model Context Protocol，2024 年 11 月公开）解决的是"有哪些工具、怎么被模型发现与调用"，它**不承载语义约束**；把本体挂成资源或工具是应用层自己要完成的工作。
- **由此得到的**：因为约束在运行时按查询求值，所以新增一条业务规则不必改 Agent 代码、不必重跑评测集；同一条公理同时服务人（生成文档）与机器（运行时判定），规则只有一处真源。演化侧同理：Agent 把"发现变更"这件事的成本压到接近零，把人的注意力从"找变化"挪到"裁决策略"。
- **由此付出的**：
  - ① 本体服务成为 Agent 动作路径上的**关键依赖**：本体不可用不是"降级成模糊回答"，而是"Agent 不能动作"，可用性要求被抬到与业务接口同级，这一条在压测里最容易被漏掉。
  - ② 开放世界假设与"Agent 需要明确禁止"直接冲突：在开放世界假设下"查不到"不等于"不允许"，把未知当允许会在长尾规则上出事，必须另加 SHACL 一类的闭合校验（这正是主文件 §2.1 把 OWL 与 SHACL 并列定位的原因：OWL 表达"是什么"，SHACL 表达"必须是什么样"）。
  - ③ 演化环节的瓶颈从"提议"平移到"裁决"：Agent 能低成本地提出大量增量（新概念、新属性、对齐方案），但审批要人做，结果是提议堆积，而不是本体在演化；一个塞满未合并提议的版本库，对下游的可信度低于一个长期不动的版本库。
  - ④ 责任归属变模糊：当动作由"模型推理 + 本体约束"共同决定时，出了错是模型选错了工具，还是本体少写了一条约束？没有审计记录就无法回答——这要求把"查询了哪一版本体"写进执行日志。
  - ⑤ 规则的可理解性下降：规则从"一段人能读的代码"变成"若干条公理的组合效果"，业务方不再能独立确认自己的规则有没有被正确表达，只能依赖架构师转述。

| 约束载体 | 改一条规则的成本 | 能校验什么 | 失败时的表现 |
| --- | --- | --- | --- |
| 代码 | 改代码 + 发版 | 形状与逻辑 | 明确的异常 |
| 提示词 | 改配置 | 什么都不能硬性保证 | 静默跑偏 |
| 形式化模型（本体 + SHACL） | 改数据 + 走评审 | 形状 + 语义一致性 | 被门禁拒绝（可观测） |

- **判定方法**：
  - 判断某个"Agent + 本体"的宣称能不能当真，问两件事：约束写在哪里（代码、提示词还是可查询的模型），以及本体不可用时 Agent 的行为是什么（报错还是照常回答）。第二个问题的答案通常直接暴露它有没有真的在用本体。
  - 判断一个工具接入规范能否承载领域约束，读它的规范里有没有"约束"这一节；没有的话，约束得由你在应用层自己实现。
- **证据与来源**：
  - 【公开】MCP（Model Context Protocol）于 2024 年 11 月由 Anthropic 公开，此后被多家工具链采纳（请以其官方规范仓库当前版本为准），但规范本身不含领域语义约束。
  - 关于"把 RDF / OWL 作为模型工具调用能力"的说法要格外小心：Tool Calling 是通用机制，RDF / OWL 作为工具返回值是应用层可自建的模式，不是任何模型的内置特性。
  - 社区里出现过一批以 `ontology-agent`、`onto-monitor` 一类命名的 PoC 仓库：判断这类项目是否还有人用，最省事的办法是看两项——最近一次提交时间，以及未关闭 issue 的积压量与关闭率。
- **成熟度**：**L3**（① 缺（无专门承载领域约束的接入约定或产品发布说明）；② 缺；③ 未稳）。

### 5.3 与本主题既有栈的接口在哪

本节的判断标准是接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。凡是说不清失败归属的"结合"，都还只是概念——这类说法在评审会上听起来完整，在事故复盘时提供不了任何信息。

还有一条更实际的理由：本体这一侧的组件几乎都是**可替换**的（Reasoner 可以换、图存储可以换、抽取模型可以换），真正难换的是**边界上的契约**。把契约写清楚，比选型更重要。

下表「现状」一列只在 AI 相关方向上使用 L1 / L2 / L3：标为「非 AI 能力的既有工程实践」的三行是已标准化、多年可用的做法，「本体 → 指标口径」一行讲的是语义层怎么引用本体概念、同样与 AI 无关——这四行都不参与本节的方向评级。本节唯一的 L1 仍是 5.2.1。

```text
业务侧                语义层                     数据侧
────────────────────────────────────────────────────────────
问题 / 动作  ──►  意图与实体识别（LLM）
                      │
                      ├─► 实体链接 ──► 公开 IRI（行业本体）
                      ▼
             ┌────────┴─────────┐
             ▼                  ▼
     查询重写 → SQL        图查询（SPARQL）
             └────────┬─────────┘
                      ▼
            SHACL / Reasoner 校验（前置拦截点）
                      ▼
              答案组织（LLM）──► 使用者
────────────────────────────────────────────────────────────
失败归属：识别错 → 抽取方；链接错 → 对齐方；
          改写覆盖不到 → 改写器 Owner；校验缺失 → 应用方
```

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| LLM 抽取 → 本体 | 抽取方产出 Turtle / JSON-LD 候选三元组，经 SHACL 与 Reasoner 门禁后才进命名图 | 生成方（抽取流水线的 Owner）——不是本体维护方替抽取方修错 | L2，多数团队仍在试点 |
| 本体 ↔ 关系数仓 | TBox 留在图侧，通过查询重写落成 SQL（主文件 §2.2 指出 QL 类 profile 存在的公开目的就是让这种改写成为可能） | 改写器与语义查询的 Owner；表达力够不到的地方会静默降级，这是最常被漏掉的一种失败 | 非 AI 能力的既有工程实践（QL 可改写为 SQL 是 W3C 标准里的既有结论），只在选对 profile 时成立；不参与方向评级 |
| 本体 → 知识图谱 | 本体给 TBox（Class / Property），图谱给 ABox（Individual）；接口是 IRI 命名空间与实体链接结果 | 实体链接做错的一方——把两个实体的 IRI 连错是链接方的错，不是本体的错 | L2 |
| 本体 → Agent 工具 | 约束以可查询资源暴露（资源 / 工具描述符 + 查询接口），模型消费 | 没有门禁时由应用方兜底；本体不可用应显式拒绝动作，而不是降级回答 | L3，无跨实现约定 |
| 本体变更 → 血缘 | 用 PROV-O 记 prov:Entity / prov:Activity / prov:Agent，配合 owl:versionInfo、owl:priorVersion | 发布方——版本与来源记录缺失时，下游无法判断"这条推论出自哪一版本体" | 非 AI 能力的既有工程实践（PROV-O 为 W3C 推荐标准，2013）；不参与方向评级 |
| 本体 → 数据准入门禁 | 发布流水线调用 SHACL 校验，不通过则拒绝入库；接口是一份校验报告（哪条形状、哪个节点） | 数据生产的 Owner——本体方只提供形状，不替数据方修数据 | 非 AI 能力的既有工程实践（SHACL 为 W3C 推荐标准，2017），前提是形状先被写出来；不参与方向评级 |
| 本体 → 指标口径 | 指标定义引用本体中的概念与维度，而不是引用表名 | 指标定义方——概念对不上时不能改本体去迁就某一个指标，否则会出现"为某张报表定制的类" | 取决于语义层是否已建；这一行不在本节四个 AI 方向内，不参与评级 |

### 5.5 被过度宣传的部分

**「LLM 能自动建本体，还会有平台把版本、协作、评审、发布一站管完，本体工程里的人这一环可以不在了」** —— 实际是自动的是**生成**与**记录**，不是**验证**与**裁决**。为什么会这样：生成的成本函数变了、验证的成本函数没变（推理复杂度由 profile 决定，SHACL 开销由形状与实例数决定，且无法靠"多买卡"摊薄）；版本记录与来源追溯在技术上更没有新问题——Git 加上命名图与 PROV-O 已经能记清"谁在哪一版改了什么、这条推论出自哪一版本"（见 5.3 的"本体变更 → 血缘"一行），真正卡住的是"这次变更该不该合并"要业务口径拍板，而口径只能由人给。什么时候它才会成真：两件事同时出现——校验层能自动生成形状约束、并能自动判定"哪些错误可以接受"（例如把未定义属性判为警告而非错误），校验结果能直接决定一个变更提议是否合并（例如"不可满足类为零且形状全过就自动合并"）。在那之前，瓶颈只是从"写"平移到了"读"，提议的堆积量也只与审批人力有关、与平台功能多少无关——这正是 5.6 里"候选堆积"一条要盯的信号。

**「加了本体，RAG 就不幻觉了」** —— 实际是"被校验覆盖到的那部分事实不会违反公理"。为什么会这样：它拦不住三类错——校验覆盖不到的部分（覆盖率问题）、检索不到的部分（召回问题）、公理本身写错的部分（开放世界假设下更隐蔽，因为缺值不报错）。什么时候它才会成真：当本体的**覆盖率**成为一个被公开度量的指标（答案里多少比例的事实能追到本体的一条公理），并且这个比例被接进发布门禁时。

**「本体是 Agent 的标配世界模型」** —— 实际是应用层自建的一块可查询资源。为什么会这样：跨模型的接入约定要解决的是"谁有什么工具"，而领域约束是每个行业自己的事，协议层无法统一；现有工具接入规范里没有为领域公理留位置。什么时候它才会成真：出现被两个以上互不相关的实现采纳的、专门承载领域约束的接入 schema，并有公开的兼容性测试。

### 5.6 未来 3–5 年：可证伪的预测

写不出信号与反信号的预测不写。下表的"会证伪的信号"一列，请当作给自己留的检查项，而不是修辞；如果三年后两条信号都没出现，说明这个方向还没开始动，而不是"正在路上"。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 本体的主要消费者从人变成程序 | 本体仓库的访问统计里，机器发起的查询（工具、Agent、CI 校验）占比超过人工浏览；发布说明开始把"机器可消费性"列为版本变更项 | 使用统计仍以文档导出、人工浏览、评审会议为主 |
| 本体的主要失败形态从"没人建"变成"候选堆积" | 主流本体仓库中未合并的变更提议（issue / PR）中位年龄持续超过半年【经验】 | 变更提议的中位合并时间稳定在两周以内【经验】 |
| 会出现事实上的「领域约束接入约定」（地位类似工具接入规范） | 两个以上互不相关的实现声明兼容同一份带约束的接入 schema，并有公开兼容性测试 | 三年后仍只有单厂商私有格式，跨产品迁移必须重写全部约束 |
| 行业本体的复用率上升、自建顶层本体下降 | 公开本体仓库（如 LOV 一类）的引用统计中，新项目引用外部行业本体的比例上升 | 新项目仍以自建顶层为主，行业本体只在特定监管行业被采用 |

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有数据字典或 Excel 词表，想升级 | 先把词表里每个概念钉到一个公开 IRI（术语表用 SKOS 表达，来源用命名图记录） | 你所在行业的本体发布节奏是否跟得上你的发布节奏 | 不要自建顶层本体；不要以"以后要推理"为由推迟把术语登记起来 |
| 已有一个跑起来的 RAG | 在检索链路出口加一层 SHACL 校验，先只校验"答案里出现的实体必须在本体里有类型" | 校验拦下的违规比例——长期接近零说明形状写得没有意义 | 不要先上 GraphRAG 再补本体；没有本体约束的抽取图，越建越贵 |
| 要让 Agent 按规则做事 | 把"能不能做"的规则写成可查询的形式化断言，而不是提示词里的一段话 | 是否出现"本体不可用导致 Agent 不能动作"的可用性诉求 | 不要为 Agent 单独发明一套语义格式；不要指望 Tool Calling 自带语义校验 |
| 已让 LLM 生成公理但没人把关 | 立刻加推理一致性门禁（不可满足类必须挡住），再加 SHACL 形状门禁 | 人工审核队列的积压量与积压时长 | 不要把"语法通过"当成"业务正确"；不要让未经审核的候选进发布版本 |
| 组织里有多个团队各自建词表 | 先做一次跨团队的概念对齐，把"同一个概念两个名字"的清单列出来并登记等价边 | 对齐冲突的收敛速度（是否随团队数增长而变慢） | 不要用"统一到某个团队的字表"代替对齐；那只是把冲突藏起来 |
| 正在选型图数据库 / 三元组存储 | 用目标实例规模在本机跑一次推理与查询，把 profile 支持范围、加载时间、查询延迟记下来 | 该存储对 OWL profile 的支持范围会不会变 | 不要按"支持 OWL"这种笼统描述选型；要问它支持哪个 profile |

最后一列是这个表里唯一有长期价值的：前面三列做的事，一年后都可以补；"不要做"的那几件，做错了要花一年拆掉。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一机制**是**本体的消费方从人变成了程序**——这让生成公理的成本降了一个量级，却没有让验证公理的成本下降，于是瓶颈从"写不写得出本体"平移到"能不能验证 LLM 写出的本体"。AI 还没有改变的是：概念粒度、口径归属、判同理由这三类**语义裁决**仍然只能由人做；行业本体的价值也仍然来自"有很多人在用同一套划分"，而不是来自它写得漂亮。
>
> 💡 **思考锚点**：拿你已经跑起来的 RAG 算一次：在检索出口只加一条「答案里出现的实体必须在本体里有类型」的 SHACL 形状，它拦下的违规比例是长期接近零（形状没意义）还是居高不下（真覆盖）？再照 5.6 的证伪线估一次——你让 LLM 生成的公理进人工审核队列，中位积压时长会不会越过「超过半年」那条线？
