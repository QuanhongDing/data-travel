## 4. 工程实现

[§3](05-ontology-modeling-section-3-sec3.md) 回答的是「本体该长成什么形状」：核心-辐射、联邦、分层、模块化、轻量化，以及「表达力每上一档要付多少推理与运维成本」。本节回答它之后的那个问题：**选定的形状怎么一步步做出来、每一步做完怎么知道做对了、已经存在的物理模型与词表怎么办、什么时候算做完。** 这三件事没有一件能从模式图里读出来。

本节对两类读者的入口不同。**从零建本体的团队**从 4.1 的 Step 1 顺次往下走，4.4 只需要看「历史资产分类」那张表。**已经有一份维度模型与数据字典的组织**（多数读者的实际处境）从 4.4 读起，再回头补 4.1 里被跳过的那几步——**跳过的步骤不会消失，它会在下游集成时以「同一个词指两个概念」的形式回来，而那时的返工面等于已经引用它的链路数。**

本节不重复 §3 的模式论述与模式选择表（模式判据在 [§3.3](05-ontology-modeling-section-3-sec3.md)），只给三样东西：每一步的**可检查产物与判据**、每条关键技术在什么条件下**会坏**、存量资产**怎么迁、什么时候能退出双轨**。数字分三档：【公开】给来源与年份，【推算】给推导链，【经验】只给区间与条件。产品能力与版本一律以官方文档当前版本为准，不按记忆断言。

### 4.1 落地步骤

下面八步对应本体工程「规格说明 → 概念化 → 形式化 → 实现 → 维护」的推进顺序（主文件 [§2.3](05-ontology-modeling.md) 的方法论条目）。**每一步都要求三件事：产物（手上多出来的、可被检查的东西）、判据（怎么知道做对了）、顺序理由（省掉它会让后面哪一步返工）。**

**Step 1：业务边界与领域识别（1–3 周【经验：随领域内既有词表规模与利益相关方数量变】）**

- 圈定本体要覆盖的业务域；**先只选一个域**，不要全企业一次性建——跨域裁决权在第一个域还没跑通时无法定义。
- 识别三类东西：核心概念（实体类型）、核心关系（属性）、核心业务规则（公理候选）。顺手记下「各域对同一个词的理解不一致」的那些词，它们是后续优先处理的项。
- **产物**：**本体范围说明书（Ontology Requirements Specification, ORS）**——一页「范围之内 / 明确不在范围内」+ 概念清单 + 术语清单。
- **判据**：把 ORS 里的概念逐条拿去问**两个不同业务域的人**「这个词在你们那边指什么」。答案不一致的概念必须在 ORS 里标成「待裁决」，不能直接进 Step 4。抽 10 个概念，待裁决超过 3 个，说明范围划得太大，而不是说明这些人不懂业务。
- **为什么必须这一步、为什么在最前面**：ORS 是后面每一步的验收基准。没有它，「这个类该不该加」「这条公理该不该写」只能靠建模者的个人偏好决定。而本体一旦发布，**删一个类比加一个类贵得多**——删除要迁移已经有实例的 IRI，新增只是加一行。

**Step 2：复用现有本体（1–2 周【经验：随候选本体的数量与该领域的标准化程度变】）**

- 按期分层级调研：顶层本体（BFO、DOLCE、UFO）、领域本体（SNOMED、AGROVOC、FIBO）、通用词表与交换标准（Schema.org、PROV-O、SKOS）。
- 对每个候选回答两件事：**它的表达力档位是什么**（含不含公理、有没有 profile 约束）、**它的发布节奏由谁控制**。
- **产物**：一份「复用 / 部分复用 / 不复用」清单，每一条写明理由，而不是只写结论。
- **判据**：把 ORS 里的概念逐条标出来源（公开本体 / 本组织既有词表 / 新造）。**每一个「新造」都要能说出一句「它为什么不能复用」**。复用比例本身不是达标线，它随领域的标准化程度变——在医疗、金融这类有成熟标准的领域通常能到三成以上，在新兴业务域可能接近于零（【经验】，不是健康基线）。
- **为什么必须这一步、为什么在选 Profile 之前**：**顶层本体一旦 `owl:imports`，它带的公理就变成你必须承担的推理复杂度**（[§3.2.2](05-ontology-modeling-section-3-sec3.md) 已展开这条机制）。先定复用再定 profile，profile 才可能选得下来；反过来做会出现「你想要的标准本体比你的 profile 表达力更强」这种无法调和的局面，而唯一的出路是把已经写好的公理重判一遍。

**Step 3：选择 OWL Profile（0.5–1 周【经验：随需要机器推出的结论条数与 profile 之间的取舍复杂度变】）**

- 按业务诉求选档：术语推理与分类（医疗、金融产品）→ **OWL 2 EL**；查询改写 + 大数据量（联盟数据、企业级数据目录）→ **OWL 2 QL**；规则 + 简单推理（风控）→ **OWL 2 RL**；确有复杂诉求 → 多 profile 组合（`owl:imports` 或联邦）。
- 把决定写进工程约定文件，而不是留在建模者脑子里。
- **产物**：**一份 profile 决策记录**：选了哪一档、为什么、放弃了哪些表达力、以及「什么条件下需要重新评估」。
- **判据**：**拿一条你确实需要机器推出来的结论（例如「父亲 ⊆ 父母」），在你选定的 profile 下笔算一遍它是否可推**；同时回答「表达力抬高一档之后，你的实例规模还跑不跑得完」。两个问题一起答上，才算选完。
- **为什么必须这一步、为什么在概念体系构建之前**：**profile 决定了你「能说什么」**（主文件 §2.2 给出对应关系：EL 对应 EL++、QL 对应 DL-Lite、RL 对应 Datalog）。在 profile 之前写下的公理很可能要整段重写——这不是改配置，是改语义；而语义改动的返工面等于已引用它的下游数量。

**Step 4：概念体系构建（2–6 周【经验：随概念数量与待裁决术语的数量变】）**

- 三条路选一条或混用：自顶向下（从顶层核心概念分层细化）、自底向上（从业务术语表归纳）、中向外（从核心域辐射到子域）。
- 同时定命名空间与 IRI 规则（写法与理由见 4.2 第一条）——它必须在第一次跨域复用之前定好。
- 推荐工具：Protégé、WebProtégé、TopBraid、Stardog Studio。
- **产物**：一份可加载的 TBox（类与属性层次）+ 一张「概念 → 责任域」归属表。
- **判据**：对每一个类问一句「**它在哪条公理里被引用**」（[§3.5](05-ontology-modeling-section-3-sec3.md) 的类爆炸判据）。指认不出来的先不进 TBox。再抽 5 个类，核对它们的归属域是否与 ORS 一致。
- **为什么必须这一步、为什么在公理之前**：概念层次是公理的挂载点。层次错了，后面每一条限制都建立在错误的分类上；反序（先写公理再整理层次）会得到一批「局部正确、整体冲突」的约束，而冲突要到全量推理时才暴露。

**Step 5：公理与约束建模（2–6 周【经验：随公理条数与属性链深度变】）**

- 层次用 `SubClassOf`，等价类用 `EquivalentClass`（如 `Mother ≡ Woman ⊓ ∃hasChild.Person`）。
- 数据准入用 **SHACL** 定义形状约束（cardinality、datatype、pattern）。
- 业务规则用 SWRL 或 N3 Rule——**注意 SWRL 是不可判定的**，写进去的东西会把推理推进不可终止区。
- **产物**：公理集与形状集**分文件管理**，各自可独立发布。
- **判据**：用 reasoner 跑一次全量分类并记录耗时；再**把一条业务规则从公理里挪到 SHACL，看分类结果是否不变**。不变，说明这条规则本来就不该是公理（[§3.5](05-ontology-modeling-section-3-sec3.md)「过度形式化」的判据）。
- **为什么必须这一步、为什么公理与形状要分家**：**公理表达「是什么」，SHACL 表达「必须是什么样」**（主文件 §2.1）。混在一起的结果是：一条业务规则变化就触发全库重新推理——而规则的变化频率远高于语义的变化频率。这个代价在单团队时不明显，在「一个域改公理、全库重新推理」（[§3.3](05-ontology-modeling-section-3-sec3.md) 模块化那一行的判据）出现时就无法回避。

**Step 6：实体填充与知识图谱对接（按域推进，每域 2–8 周【经验：随源系统数量、数据量与抽取输出质量变】）**

- 用本体作 schema，通过 ETL / 抽取 pipeline 把多源数据映射成实例；NER（实体识别）+ RE（关系抽取）的输出对齐到本体的 class / property。
- **先用一个小样本**（一个域、几百到几千条）把 Step 7 的校验跑通，再规模化填充。
- 来源追踪：每条数据用 PROV-O 标 `prov:wasDerivedFrom`。
- **产物**：ABox + 一张「源系统字段 → 本体属性」映射表。
- **判据**：抽取 20 条实例，**沿 `prov:wasDerivedFrom` 回走到源记录**。回走不到的属于「无出处的断言」，一旦被下游引用就无法追责。再看映射表：有没有哪个源字段被映射到两个不同属性——那是 Step 4 的账，不是本步的账。
- **为什么必须这一步、为什么先小样本**：**ABox 是本体第一次接触脏数据**，SHACL 的违规会在这里集中暴露。全量填充之后再补约束，等于把已经入库的违规数据全部翻出来重判，而重判的对象是生产数据。

**Step 7：质量校验与版本管理（持续）**

- SHACL 校验：每个新增数据必须通过形状约束，**失败即拒绝入库，不是告警**。
- 推理验证：用 reasoner 检查是否出现意外推理（unsatisfiable class、不该合并的等价类）。
- 版本管理：`owl:versionInfo` + Git + 语义化版本（MAJOR.MINOR.PATCH）。
- **产物**：一条能整包跑通的校验流水线 + 一份版本发布记录。
- **判据**：**制造一条已知违规的实例，看它能不能被拦下来并给出可定位的错误信息**；再问「上一次因为校验失败拦住的数据是什么时候」——从来没有过，说明本体没有强制力（[§3.7](05-ontology-modeling-section-3-sec3.md) 最后一条）。
- **为什么必须这一步、为什么它与 Step 6 是一个循环**：**OWL 在开放世界假设下不会因为缺值报错**，没有 SHACL，本体就只是一份词汇表。所以「填充 → 校验 → 改约束或改数据」必须成环；只有填充没有校验的流水线，产出的是「一堆看起来合法的三元组」。

**Step 8：发布到下游（持续）**

- 暴露 SPARQL endpoint（Stardog / GraphDB / Neptune / GraphScope 等）。
- 暴露 REST API——**把 SPARQL 封装成业务 API**，不让业务方直接写 SPARQL。
- 暴露成 LLM 可消费的结构化 schema（JSON-LD + JSON Schema 投影），并区分「哪类消费者走哪条路径」。
- **产物**：三类接口 + 一份消费者路径说明。
- **判据**：**找一个不了解本体的消费者（一个查询改写器或一个模型），让它只靠接口回答「要查 X 该用哪个类、哪个属性」**。答不出来，说明发布形态与消费者构成不匹配，而不是说明消费者不会用。
- **为什么必须放在最后**：**发布形态决定对外暴露的是完整公理还是受限词汇**（[§3.6](05-ontology-modeling-section-3-sec3.md) 第 5 行「只给自己用 → 要被 LLM / Agent 消费」与第 7 行「单一消费者 → 多类消费者并存」这两行的跃迁）。语义还没稳定就把完整 OWL 暴露出去，消费方会被迫理解开放世界语义，这几乎等于劝退。代价是投影层要一直与本体保持同步——投影过期时，模型看到的是一个已经改名的概念，而输出不会报错。

**八步里最常被跳过的是 Step 3（Profile）与 Step 7（校验）。** 跳过 Step 3 的症状出现在第一次上规模时：全量分类跑不完，或者换一个 reasoner 就报错——此时公理已上百条，重选 profile 等于重写。跳过 Step 7 的症状更隐蔽：**没有告警本身就是症状**——脏数据安静地流到下游指标里，直到有人拿本体去对账，才发现它从来没有拦下过任何东西。

### 4.2 关键技术点

**Namespace 设计**

- **做法**：用分层、稳定的 IRI，如 `https://{org}.com/ontology/{domain}/v{version}#`；跨域连接用 `rdfs:subClassOf` 挂载，不用 `owl:equivalentClass` 声明等价。
- **机制**：**因为命名空间是解耦的最小单位，所以它决定了「谁可以和谁独立发布」**——单一前缀会把所有域强制进同一个发布节奏；而用 `subClassOf` 而不是 `equivalentClass`，是因为等价声明会把裁决权交回给两个域，中心等于不存在。
- **失效条件**：**当第一个外部合作方要引用你的概念时，这条会坏在「改名」上**。症状：跨组织交换时发现需要重命名，而所有下游实例都要跟着改——IRI 一旦对外发布就不可撤回。迁移动线：在第一次跨域复用发生之前定好，此后只增不改。
- **档位**：【经验】；分层命名空间是行业通行做法。

**Profile 选择**

- **做法**：按 4.1 Step 3 的三档选，把决定写进工程约定，并在同一份记录里写下「什么条件下重新评估」。
- **机制**：**因为 profile 决定了可用的公理种类，所以它同时决定了可选的 reasoner 与可承受的实例规模**（主文件 §2.2）。这是一条从表达力到运维面的单向约束：表达力上调要付推理复杂度，下调要付公理重写。
- **失效条件**：**当业务方提出一条当前 profile 推不出来的推理需求时，这条会坏在「加不上」上**。症状：建模者开始用命名约定和文档去「假装」这条推理，而机器其实推不出来；更隐蔽的症状是有人悄悄把 profile 抬高一档，几周后全量分类开始跑不完。
- **档位**：【公开：W3C OWL 2 推荐标准, 2009（引入 EL / QL / RL profiles）】；档位与复杂度的对应关系见主文件 §2.2。

**Reasoner 选择**

- **做法**：按 profile 配对——HermiT、Pellet、FaCT++ 面向 OWL DL；ELK 面向 EL；Konclude 面向高性能场景；JFact 面向轻量嵌入。
- **机制**：**因为不同 reasoner 实现的是不同算法族（tableau / consequence-based），所以「能不能跑」与「跑多久」是选出来的，不是调出来的**。
- **失效条件**：**当 profile 与 reasoner 不匹配时，这条会坏成「换引擎就报错或超时」**。症状：同一份本体在两个 reasoner 下给出不同结论，或其中一个不终止——这时该检查的是 profile 声明，而不是 reasoner 的参数。
- **档位**：【经验】；工具名真实存在，各项目支持的 profile 请以官方文档当前版本为准。

**Reasoner 性能调优**

- **做法**：增量推理（只重算受影响部分）、模块化推理（按模块切分推理上下文）、并行推理、缓存与物化结论。
- **机制**：**因为全量分类的成本随「类数 × 个体数」增长，所以规模上来之后唯一的出路是不做全量**——把推理从「每次查询都推」改成「推一次、查询期查表」。
- **失效条件**：**当实例规模从万级走到百万级时，这条会坏在「物化结论过期」上**（【经验】：全量重算的耗时随「类数 × 实例数」与属性链深度增长，换 profile 或换 reasoner 都会改变量级，所以任何他人案例给出的「分钟级」都不能当作你的承诺——它多半没附场景参数）。症状：查询很快，但查到的分类结论基于几天前的数据，而且没有人知道物化任务什么时候失败过。**自己测一遍**：取三个 10 倍递增的实例规模各跑一次全量分类，记下耗时曲线，用它定物化周期；再把物化任务的最近成功时间与查询侧实际用到的结论版本对一遍，两者不一致时先修周期，再谈快慢。
- **档位**：【经验】。

**SHACL 引擎选择**

- **做法**：候选包括 TopBraid SHACL Validator、Stardog SHACL、GraphDB SHACL、EYE，以及轻量入口（SHACL Playground）与语法级校验（Manchester OWL Validator）。
- **机制**：**因为校验只有挂进数据准入流程才有强制力，所以第一判据不是「覆盖多少 SHACL 特性」，而是「能不能在你的写入路径上同步执行并阻断」**。
- **失效条件**：**当校验只能异步跑、或跑一轮要几小时时，这条会坏成「校验报告没人看」**。症状：违规数据照常入库，校验结果退化成一份周报；再过一段时间连周报也没人打开。
- **档位**：【经验】；各引擎对 SHACL 特性的覆盖范围以官方文档当前版本为准。

**本体版本管理**

- **做法**：`owl:versionInfo` + Git + 语义化版本（MAJOR 语义不兼容、MINOR 增概念、PATCH 修注释）；用本体 diff 工具（OWLDiff、SemDiff）产出两版差异。
- **机制**：**因为「删一个类比加一个类贵得多」，所以版本号必须让消费方能自己判断该不该升级**——没有 diff，升级就是一次盲签，消费方只能全量回归来确认。
- **失效条件**：**当发布节奏快于消费方的升级节奏时，这条会坏在「下游按旧定义产出数据」上**。症状：同一个实例在不同下游按两个版本的语义被解读，而数字对不上时无法判断是哪一版的问题。
- **档位**：【经验】。

**多源对齐（Ontology Matching）**

- **做法**：先用自动对齐工具（AgreementMakerLight / AML、LogMap）产出候选映射，再用人工或 LLM 做语义验证；嵌入类方法（Owl2Vec*、BERTMap）用于候选召回。
- **机制**：**因为候选映射可以自动生成、但等价声明不可自动采信，所以流程必须是「机器召回 + 人裁决」**——一条错误的 `owl:equivalentClass` 会把两个概念的实例集合合并，而这个错误会在推理层被放大。
- **失效条件**：**当被对齐的两个本体各自还在演化时，这条会坏在「映射过期」上**。症状：对齐层指向的概念在对方新版里已被拆分或改名，映射仍然生效，于是两侧越推越不一致。
- **档位**：【经验】。

**本体与 LLM 接口**

- **做法**：把 OWL 投影成 JSON-LD，再投影成 JSON Schema，让 LLM 通过工具调用消费；对外只暴露受限词汇，不暴露完整公理。
- **机制**：**因为模型缺的不是查询能力，而是「哪个字段是权威的、这个词指什么」，所以投影层的作用是把开放世界语义收敛成模型能处理的封闭集合**——这是本体的「机器可读」优势唯一能变现的地方。
- **失效条件**：**当本体变更而投影层没有同步时，这条会坏在「模型按过期定义作答」上**。症状：回答引用的是一个已经改名或已废弃的概念，而输出里没有任何报错——这是最难被发现的一类错误。
- **档位**：【经验】。

**联邦查询**

- **做法**：跨多个 SPARQL endpoint 的查询用联邦引擎（FedX、ANAPSID）做查询分解与结果合并；**能用 `owl:imports` 收拢的就不要用联邦**。
- **机制**：**因为联邦把「一次查询」拆成「多次远端查询 + 本地合并」，所以它能解耦发布节奏，代价是把性能变成不可控项**——瓶颈从本地推理转移到远端 endpoint 的响应时间与可用性。
- **失效条件**：**当被联邦的 endpoint 数量或数据量上去时，这条会坏在「查询计划失控」上**。症状：同一条查询的耗时随远端数量超线性增长，且失败原因无法归因到具体某一个源。
- **档位**：【经验】。

**本体演化（Ontology Evolution）**

- **做法**：变更走五步——影响分析 → 公理修改 → 推理验证 → SHACL 验证 → 版本发布；事先定义清「哪些变更属于破坏性」（删类、删属性、改基数、收紧数据类型）。
- **机制**：**因为本体的消费方是「编译过」它的下游（映射层、投影层、查询改写器），所以破坏性变更的作用域不在本体内部，而在所有引用点**。
- **失效条件**：**当本体被多个下游引用时，这条会坏在「改一处、断多处」上**。症状：一次看似无害的收紧让下游写入批量失败，而失败原因散布在多个系统里，没人能在第一时间把它归因到这次变更。
- **档位**：【经验】。

### 4.3 工具链与平台

下表按类目给候选与**选型判据**。判据的用法是：先在自己的约束里找出最紧的那条（[§3.3](05-ontology-modeling-section-3-sec3.md) 的约束组合，或 4.1 Step 3 的 profile 决定），再看这一行里哪一列满足它。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |

| 差异与版本 | OWLDiff、SemDiff，配合 Git 与语义化版本 | 只要本体有外部消费方，diff 就是发布流程的一部分 | 不 diff：升级变成盲签，消费方只能用全量回归来确认 |
| 联邦查询 | FedX、ANAPSID | 只在「被联邦方必须各自独立发布、且无法用 `owl:imports` 收拢」时使用 | 用联邦替代模块化：把发布解耦换成了查询性能不可控 |
| LLM 辅助构建 | OntoGPT、DeepOnto、Ontogenia、Microsoft GraphRAG | LLM 只用于起草与候选生成；入库前必须过专家验证、SHACL 校验、推理验证三关 | 让 LLM 定稿：语义冲突要到下游集成时才暴露，返工面覆盖全部依赖方 |
| 复用本体来源 | 顶层：BFO、DOLCE、UFO；领域：SNOMED、AGROVOC、FIBO；通用：Schema.org、PROV-O、SKOS | 有成熟领域标准时优先复用；只需要词汇时用 SKOS / Schema.org，不要顺带背上公理 | 全自造：跨组织交换与对齐的成本全部由自己承担 |
| 可视化 | WebVOWL、yEd | 需要给非建模者看结构时用；模型规模大时先裁子集再画 | 不画：业务方无法参与评审，本体的验收变成建模者自证 |

**这一类里最容易被误选的是「存储与推理」**，因为它常被当成一个「能连上 SPARQL 就行」的组件。真正决定成败的是两个模式问题：**推理是物化还是查询期执行、写入是批量装载还是持续更新**。误选的后果不是性能差一点，而是**迁移面等于全部实例**——等你发现要换的时候，实例已经全进来了。第二容易被误选的是对齐工具：它看起来像一个可以「先跑起来」的批处理任务，但它产出的每一条等价声明都会直接改变推理结果，所以它更需要人工裁决环节，而不是更不需要。

各产品支持的 profile 与 SHACL 特性覆盖范围随版本变化，请以各项目官方文档当前版本为准。上表的选型判据按约束写成，不依赖具体版本号——这也是它可以长期复用的原因。

### 4.4 存量迁移

**① 先做哪一件「立刻见效且可回退」的事**

不搬数据、不改物理模型。第一件事是**给已有的核心实体建一张「术语 → URI」映射表**：把数据字典里的每个术语标上「对应本体里的哪个类 / 属性，还是暂无对应」。它不改任何系统、随时可以撤销，却立刻产出两个结果——一张「同一个词在两个域指不同东西」的清单，以及后续建模的优先序。第二件可回退的事是**只读投影**：把本体投影成 JSON Schema，交给一个下游（一个查询改写器或一个模型）试用，不动它的生产路径。两件事的共同点是：失败的成本是删掉几行配置，而不是让业务停摆。

**② 历史资产怎么分类处理**

存量资产不要按「新旧」分类，按**引用面与处置成本**分三档，并给每档写明判据：

| 档 | 判据 | 处置 | 不要做什么 |
| --- | --- | --- | --- |
| 全部返工 | 被跨域口径引用，且在多个域各有一份实现（同一个客户在三处三份定义） | 按本体重新定义，让下游引用**定义**而不是复制映射 | 不要「先照抄一份原样搬过来」——照抄出来的第二份实现会立刻成为新的分叉点 |
| 只改动的部分 | 只在一个域内被引用，且仍在被使用 | 不动存量，改到它的时候顺手迁过来，迁完即登记 | 不要为它排独立迁移窗口——收益不抵调度成本 |
| 打标挂账 | 无人能说清谁在用，或访问日志显示长期无读 | 标为「待定」，挂上访问统计，到期无人认领即下线 | 不要直接删——它可能是别人的口径依据；也不要无限挂账——要设到期日 |

**③ 双轨要维持多久、怎么维持**

双轨不是过渡语气，它是**一个有截止日的状态**。维持它的成本是「同一件事有两份实现」：本体的语义一份、既有的 ETL 映射一份，每次变更要在两处同时改。可执行的规则只有一条：**每一次语义变更，必须同时改本体与既有映射，并跑一次两侧的对账**。任何一次「这次先改一边」的例外，都会让目标侧在切换前就落后于源侧，等到要切的时候发现要重新对齐一遍——而对齐是本体工程里最贵的一项工作，它的成本按概念数与域数的组合增长。

**④ 什么信号说明可以退出双轨**

退出信号必须写在开工之前，写成「哪一天、以哪个域、以哪份定义为准」，当作验收标准而不是「以后再定」。可观察的信号有三个：**映射表里「暂无对应」的条目连续若干周期不再收敛**、**下游主动从旧映射切到本体（而不是被通知）**、**既有的手写映射连续一段时间没有人改**。三者满足两个即可安排下线；只满足第三个时不要切——那说明本体只是「对得上」，还没被信任。

**四类存量迁移的具体形态**：

- **无词汇表 → 有本体**：迁的是「语义的归属权」，最慢的一步是让业务接受「跨域定义以本体为准」；
- **有数据字典 → 有本体**：字典是**被动说明**，本体是**主动约束**；迁移动作是给字典里已有的条目补上「违反它会发生什么」，补不出来的条目说明它还不该进本体；
- **有维度建模 → 加语义层**：**只加一层语义，不动物理模型**（这就是 [§3.2.6 混合型](05-ontology-modeling-section-3-sec3.md) 讨论的形态，[§3.3](05-ontology-modeling-section-3-sec3.md) 决策表里「已有维度建模，需要补语义层」那一行选的正是它）；代价是映射层成为新负债，它必须有人负责追平物理模型的变更，否则本体描述的是一份已经不存在的数仓；
- **有 LLM 起草的候选本体 → 生产本体**：只能从新版本开始收紧，**LLM 起草的部分逐条过三关**（专家验证、SHACL 校验、推理验证），不要指望一次清洗干净——一次性清洗的返工量等于整份本体重做。

### 4.5 模板 / 示例

**模板 1：电商客户本体片段（OWL / Turtle）**

```turtle
@prefix : <http://example.com/ecom#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

:Customer a owl:Class ;
    rdfs:subClassOf [ a owl:Restriction ;
                      owl:onProperty :hasCustomerId ;
                      owl:cardinality 1 ] ;
    rdfs:subClassOf [ a owl:Restriction ;
                      owl:onProperty :hasEmail ;
                      owl:minCardinality 1 ] .

:VipCustomer a owl:Class ;
    rdfs:subClassOf :Customer ;
    owl:equivalentClass [ a owl:Restriction ;
                          owl:onProperty :hasLifetimeValue ;
                          owl:someValuesFrom [ a rdfs:Datatype ;
                                               owl:onDatatype xsd:decimal ;
                                               xsd:minInclusive 10000 ] ] .

:hasCustomerId a owl:DatatypeProperty , owl:FunctionalProperty ;
    rdfs:domain :Customer ; rdfs:range xsd:string .

:placedAt a owl:ObjectProperty ;
    rdfs:domain :Customer ; rdfs:range :Order .

:VipCustomer owl:disjointWith :RegularCustomer .
```

**怎么用**：前缀声明照抄，把 `ecom` 换成你的域并加上版本段（见 4.2 的命名空间写法）。**唯一需要想清楚的是 `owl:equivalentClass` 那一行**——注意属性名是小写 e 的 `owl:equivalentClass`；写成 `owl:EquivalentClass` 多半不报错，但那只是声明了一个自定义谓词，等价公理并没有成立（`EquivalentClasses` 是公理名，不是可作谓词的 IRI）。这一行声明的是「有高 LTV 的客户就是 VIP」，而不只是「VIP 一定 LTV 高」——如果你要的是后者，把它改成 `rdfs:subClassOf`，否则任何一条 LTV 达标的记录都会被推理成 `VipCustomer`，包括你并不认可的营销名单。`owl:cardinality` 这类基数约束**不能照抄**：**OWL 2 EL 的类表达式构造子里不含基数限制**（`owl:cardinality` / `owl:minCardinality` / `owl:maxCardinality` 都不在 EL 内，EL 对「唯一性」只提供 `owl:FunctionalProperty` 这种弱形式），QL 与 RL 各自支持哪些基数形式、支持到哪一档也不相同——请按 W3C OWL 2 Profiles 文档当前版本的语法表逐条核对，不要按印象判断。若你选定的 profile 不支持，把基数要求交给 SHACL 的 `sh:minCount` / `sh:maxCount`（模板 2）——准入类约束本来就该放在那一层。

**模板 2：SHACL 形状约束（SHACL / Turtle）**

```turtle
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix : <http://example.com/ecom#> .

:CustomerShape a sh:NodeShape ;
    sh:targetClass :Customer ;
    sh:property [ sh:path :hasCustomerId ;
                  sh:datatype xsd:string ;
                  sh:pattern "^[A-Z]{2}\\d{8}$" ;
                  sh:minCount 1 ; sh:maxCount 1 ] ;
    sh:property [ sh:path :hasEmail ;
                  sh:datatype xsd:string ;
                  sh:pattern "^[^@]+@[^@]+\\.[^@]+$" ;
                  sh:minCount 1 ] ;
    sh:property [ sh:path :placedAt ;
                  sh:class :Order ;
                  sh:minCount 0 ] .
```

**怎么用**：`sh:targetClass` 决定这条形状管哪些实例，是唯一必须按你的类名改的一格。`sh:minCount` / `sh:maxCount` 与 OWL 里的基数约束**不要写成同一件事**：OWL 管「什么关系成立」，SHACL 管「什么数据能进」（主文件 §2.1）。`sh:pattern` 里的正则是业务判据，**照抄会拦掉你自己的合法数据**——先用存量数据跑一遍「只统计、不阻断」，看清违规分布再决定放行阈值。

**模板 3：SPARQL 查询（多跳）**

```sparql
PREFIX : <http://example.com/ecom#>

# 沿对象属性路径做两跳：客户 → 其订单的付款人 → 该付款人的推荐人
SELECT DISTINCT ?c1 ?c3 WHERE {
    ?c1 a :Customer .
    ?c1 :placedAt/:paidBy ?c2 .
    ?c2 :hasReferrer ?c3 .
    FILTER (?c1 != ?c3)
}
```

**怎么用**：属性路径 `:placedAt/:paidBy` 是这两跳的写法，把它换成你自己链路里的属性名即可。**注意 `FILTER (?c1 != ?c3)` 是必要的**——开放世界假设下如果你忘了排掉自反情形，同一实体出现在两端的结果会混进来而不会报错。这条查询也是检验「你的本体到底支持什么」的最快办法：如果它跑不出来，多半是图里缺了某一跳的属性，而不是 SPARQL 写错了。

**模板 4：本体变更单**

```text
本体变更单 - {变更编号}
变更类型：[ ] 增概念  [ ] 增属性  [ ] 加公理  [ ] 收紧约束  [ ] 删概念/属性（破坏性）
影响分析：引用该概念的下游（映射层 / 投影层 / 查询改写器 / 模型）共 {n} 处，已逐一列出
推理验证：全量分类耗时 {秒}；新增 unsatisfiable class {n} 个
SHACL 验证：存量数据违规 {n} 条，处置方式 {方案}
版本号：{MAJOR.MINOR.PATCH}（破坏性变更必须进 MAJOR）
退出 / 回滚：回退到 {版本号}；已发布实例的 IRI 处理方案 {方案}
```

**怎么用**：六行都要填。**填不出「影响分析」那一行就不要提交**——它是这张单子存在的理由：破坏性变更的作用域不在本体内部，而在所有引用点（见 4.2 本体演化）。**第五行最容易被漏填**：把破坏性变更塞进 MINOR，消费方就不会做回归，等到出事时也无法从版本号上看出该回溯到哪一版。

### 4.6 成本：这套东西的账单

本主题的软件授权费趋近于零——Protégé、Jena、ELK、SHACL 引擎都是开源件，这笔账单不在这里。它贵在两个非许可项：语义的**人工裁决**，和推理的**物化算力**。

**人力：主体是裁决，不是建模。** 建类、建属性是可预估的工时，真正吃掉预算的是**对齐与裁决**——4.4 已给出结论：对齐是本体工程里最贵的一项工作，成本按「概念数 × 域数」的组合增长。据此写成可代入的形式：`对齐工作量 ∝ 概念数 × 域对数`【推算，公式；增长规律取自 4.4 第③组的原话，本条只是把它写成算式】。若只自动召回、不人工裁决（4.3 对齐行），省下的工时会在下游以「一条错误的 `owl:equivalentClass` 把两类实例合并」的形式还回来，且发现时已覆盖全部依赖方。

**算力：本主题特有的成本项是「全量分类 / 物化」的周期性重算。** 查询期推理把成本摊进每一次查询，物化则把成本压成周期性的批任务；两者量级都随「类数 × 实例数 × 属性链深度」增长（机制与自测方法见 4.2「Reasoner 性能调优」，本节不重复）。年度算力预算因此写成 `年化成本 ≈ 单次全量分类耗时 × 物化频率 × 计算单价`【推算，公式；单次耗时按 4.2 给的「三档 10 倍递增实例各测一次」自测，单价用自己账单价，禁止引用他人案例的「分钟级」承诺——它多半没附场景参数】。

**为什么贵在这里，而不是贵在许可证。** 本体做的事是把**跨域定义的裁决权集中到一处**（4.2「Namespace」：用等价声明会把裁决权交回两个域，中心等于不存在）。集中裁决 = 集中成本：省下的是每个域各维护一份口径的重复，付出的是这个中心被所有人依赖后的**评审与对齐工时**。所以这个主题的成本结构是「一次裁决反复收租」，而不是「一次采购一次摊销」。

### 4.7 容灾与故障演练

本主题的「灾」不是机房故障，而是**推理结论不确定**与**派生层与本体脱钩**；本体本身是版本库里的文本，天然多地副本，跨地域多活对它不成立。真正需要可用性冗余的是推理 endpoint（联邦场景下即远端 endpoint，4.2「联邦查询」），其通用方案见 [容灾与多活](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)。这里只写本主题特有的四种失效。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| **推理结论不可复现**：同一份本体在两个 reasoner 下给出不同结论，或其一不终止（4.2 Reasoner） | 依赖推理结论的下游集体拿到不一致的分类 | 冻结 profile 与 reasoner 版本，出口只认一个已确认的版本 | 用固定版本的 reasoner 重跑一份基准本体，逐条比对结论集是否完全一致 | 不设 RTO——答案必须**恒等**，不是「多久恢复」 |
| **物化结论过期**：查询快，但分类基于几天前的数据（4.2 性能调优） | 下游读到过期分类而不报错，且无人知道物化任务何时失败过 | 回退到查询期推理：慢，但结论与当前数据一致 | 故意让物化任务失败一个周期，看查询侧是否仍在用旧版本、有无告警 | RTO【经验】一个物化周期量级；RPO = 最近一次成功物化的时点【经验】 |
| **对齐映射过期**：被对齐的本体演化后，映射仍指向已拆分 / 改名的概念（4.2 多源对齐） | 两侧越推越不一致，且差异归因不到对齐层 | 冻结跨域等价声明，退回只用 `rdfs:subClassOf` 挂载 | 对两个正在演化的本体跑一次 diff + 映射有效期检查，看过期映射能否被自动列出 | RTO 不设；处置是「重新对齐」，按概念数计工时 |
| **投影层与本体脱钩**：本体改名 / 废弃概念而投影层未同步，模型按过期定义作答（4.2 本体与 LLM 接口） | 输出引用废弃概念而毫无报错——最难被发现的一类 | 停止向 LLM 暴露该投影，退回受限词汇子集 | 每次本体发布后自动比对投影产物与本体版本号，不一致即阻断发布 | RTO 至下一次发布校验 |

**不适用跨地域容灾的部分**：本主题的「决策与定义」产物是带版本的文本（`owl:versionInfo` + Git，4.2），本就多地多副本，为它建多活没有意义。跨域要求落在推理服务的可用性上，属 [容灾与多活](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md) 与 [混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md) 的通用题，本文不复述。

### 4.8 演进路线：0 → 1 → 100

**0 → 1（只读投影 + 一张映射表，跑通一个下游）**：第一件事是 4.4 说的「术语 → URI 映射表」，第二件是只读投影给一个下游试用——都不动生产路径。这一步**变贵的是人工裁决的工时**（把数据字典的术语逐个标「对应 / 暂无对应」），**先坏的是命名空间**：若在第一次跨域复用之前没定好分层、稳定的 IRI，此后只能增不能改，改名会波及所有已发布实例（4.2「Namespace」）。

**1 → 100（多域纳入、实例上量、校验挂进写入路径）**：把 profile 决策、SHACL 校验、推理流水线逐域铺开，实例从万级走向百万级。这一步**变贵的是全量分类的算力与物化运维**（物化周期被迫缩短，或改为增量推理），**先坏的是 profile 与 reasoner 的匹配**：实例上量后才发现选错了档，症状是同一个查询有时快、有时超时（4.2）。判据：SHACL 校验是否真在写入路径上**同步阻断**（4.3），而非退化成一份没人看的周报。

**100 →（结构性矛盾触发 profile 抬档）**：触发换档的从来是「业务方提出一条当前 profile 推不出来的推理需求」（如「父亲 ⊆ 父母」，4.2「Profile 选择」），而不是数据量涨了。这一步**变贵的是物化算力与迁移工时**——profile 抬高意味着全量分类从 PTime 档进入更高复杂度（主文件 §2.2），**先坏的是全量分类耗时**：它一旦跑不完，所有周期性物化都失效。此时正确动作是重新评估「这条推理是否必须由机器推」并同步改画像层与全部下游引用点（4.5 变更单的「影响分析」栏），而不是悄悄把档位抬高一格。

### 4.9 自检清单

1. ORS 里有多少概念被标成「待裁决」？它们各自归哪个域裁决，这个裁决权写下来了吗？
2. 抽 10 个类，能指认出「它在哪条公理里被引用」的有几个？指认不出来的打算怎么处置？
3. 你的 profile 是哪一个？把它换掉（比如 EL 换成 DL），有多少条公理要重写？全量分类跑一次要多久，这个数字最近是上升还是下降？
4. 4.1 八步的产物里，哪几份是现在真的拿得出来的（ORS、复用决策清单、profile 决策记录、TBox + 归属表、公理与形状分文件、ABox + 字段映射表、校验流水线 + 发布记录、三类接口）？拿不出来的那一份，它后面哪一步的判据现在做不了？
5. 上一次因 SHACL 校验失败拦住数据是什么时候？拦下之后改的是数据还是约束，谁签的字？
6. 抽 20 条实例，能沿 `prov:wasDerivedFrom` 回走到源记录的有几条？
7. 映射表里「暂无对应」的条目，最近一个周期是在增长还是在收敛？
8. 存量资产按「全部返工 / 只改动的部分 / 打标挂账」分完档了吗？「打标挂账」那一档的每一条都有到期日和认领人吗？
9. 用例里那条最关键的机器推理（例如「父亲 ⊆ 父母」），今天能不能跑出来？跑不出来时，记录里写的是「profile 不支持」还是「还没写」？
10. 本体上一次发布到全部消费方拿到新版本，间隔多久？这个间隔里有没有下游在按旧定义产出数据？
11. 双轨期间最近三次语义变更，是不是每次都同时改了本体与既有映射、并跑过一次两侧对账？出现过「这次先改一边」的例外吗，例外之后两侧相差几个概念？
12. 退出双轨的决定，是开工前就写成「哪一天、以哪个域、以哪份定义为准」的验收标准，还是留成了「以后再定」？

上面 12 条只查 §4 的落地环节（产物、判据、迁移档位、双轨与退出信号）。**本体设计与模式层面**的自检——profile 与 reasoner 的匹配、跨域连接用 `subClassOf` 还是 `equivalentClass`、LLM 起草部分的三关、消费者能否自助——在 [§3.7](05-ontology-modeling-section-3-sec3.md) 已逐条给过，本节不重复。

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **Step 3 的 profile 决策（以及支撑它的 ORS）**。它是全流程中唯一一个「改起来等于重写」的决定：命名空间可以重定向、校验可以后补、对齐可以迭代，而 profile 与依赖它的公理集一旦铺开，重新选择意味着把全部公理重判一遍——这正是它最常被跳过、又总在规模或消费者变化时才暴露的原因。它便宜的窗口只有一个：动笔之前。
>
> 💡 **思考锚点**：按本节 Step 1 的判据，抽 10 个概念去问两个业务域的人——待裁决的超过 3 个，说明你的域划得太大；那就拿这个数回去对一下时序：你那档 profile（EL / QL / RL）是写进 Step 3 的决策记录、排在概念体系之前，还是等域划完、公理铺开才补的？如果是后者，你今天要动的是那几条待裁决的概念，还是整个 profile？
