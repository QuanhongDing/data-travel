## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

**先划清本节与主文件的分工**：主文件 §1、§2 讲的是本体「是什么」与「靠什么推进」——概念（Class）、关系（Property）、公理（Axiom）、个体（Individual）四件套，OWL 2 的三个 profile（EL / QL / RL），以及 SHACL 的校验分工。本节讲的是**同一套四件套，在不同约束下会被摆成完全不同的形状**——这些形状就是模式。

把本体模式写成一张「按场景选一个」的表格，是这一章最容易犯的错。原因是本体的成本结构不线性：**多写一条公理可能只是多一行 Turtle，也可能让推理机从秒级变成不可用**——取决于这条公理落在哪个 profile、作用在多少个个体上。所以「跨业务域用联邦、万级类用模块化」这种表格看着清楚、实际不可执行：它没告诉你，你当下的约束落在哪一档。

模式的真正来源是约束。以 OWL 2 为例：W3C 在 2009 年把它拆成 EL / QL / RL 三个 profile（【公开：W3C OWL 2 Profiles, 2009】），这不是「三个可选的档位」，而是**对「表达力 ↔ 推理复杂度」这组约束的三种妥协**。主文件 § 2.2 给过对应关系：EL 对应 PTime-Complete、QL 对应 AC0（可改写成 SQL）、RL 对应 Datalog（可改写成规则系统）。**先选 profile、再选 reasoner**不是流程洁癖，而是因为 profile 决定了「你的本体在规模上还能不能跑」。

判断自己受哪条约束支配，有一个简单的提问顺序：先问「**谁在消费这份本体**」（推理机、查询改写器、搜索引擎、还是人），这一条把选择范围砍掉一半；再问「**有几个独立主体在定义它**」（一个团队、多个团队、多个组织），这一条决定裁决权放在哪；最后问「**变更多久发生一次**」，这一条决定要不要模块化。三个问题问完，3.3 的表基本只剩一行可用。

下面 6 条约束，任何一条不同，同一个场景的正确模式就会不同。先把它们写下来，再往下读模式。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式 | 本体是纯 TBox（只有术语）还是带 ABox（含个体）；个体是批量灌入还是一条条变更 | 「本体只是 schema」——一旦带 ABox，发布节奏、回滚、推理调度全部变成数据工程问题 |
| 访问模式（点查 / 扫描 / 聚合） | 是否需要把 OWL 改写成 SQL / 图查询，是否必须预计算（materialization） | 「表达力越强越好」——需要全表扫描聚合时，OWL DL 的表达力换来的是不可用的查询延迟 |
| 变更频率与历史要求 | 模块边界画在哪、版本策略（`owl:versionInfo` / 语义化版本）与发布粒度 | 「本体应该稳定」——本体稳定的前提是它的消费者少；消费者一多，不发布才是风险 |
| 一致性要求 | OWL 与 SHACL 的分工：OWL 给开放世界假设下的推论，SHACL 给封闭世界下的准入校验 | 「有了 OWL 就不需要 SHACL」——OWL 的基数约束在开放世界假设下只能用来推矛盾，不能用来校验缺值 |
| 规模与成本约束 | profile 选择、是否在线裁剪、模块是否按需加载 | 「先建全、再上量」——全量本体先行的项目多数在得到可用产出前就中止 |
| 团队技能与运维能力 | 本体由谁维护：领域专家、本体工程师，还是 LLM 起草 + 专家复核 | 「工具能替代人」——工具能起草结构与约束，不能裁决「这两个概念是不是同一个业务概念」 |

这 6 条里只有前两条与「一致性要求」是技术约束，其余三条（变更频率、规模成本、团队技能）都是**组织约束**。而本体项目的失败多数不发生在技术约束上：一个由单团队维护的本体，被要求支撑多个团队的发布节奏，就必然从「可演化」变成「没人敢改」——**技术上它仍然能跑，组织上它已经停机了**。所以下面每个模式除了结构，都要交代它在什么组织条件下才成立；只谈结构的模式描述是不完整的。

### 3.2 模式逐个拆解（核心节）

下面 6 个模式（核心-辐射、联邦、分层、模块化、轻量化、混合），每个都按「约束 → 结构 → 机制 → 代价 → 失效点 → 真实使用」展开。

读的时候请只盯一件事：**这个模式把「裁决权」放在了哪里**。核心-辐射把裁决权放在一个中心域，联邦放在对齐层，分层放在顶层本体，模块化放在抽取机制，轻量化干脆放弃裁决。**模式的差别不在形状，在裁决权的归属**——形状只是裁决权的可见后果。所以每个模式后面的「失效点」，本质上都是同一句话：裁决权放错位置时，它的收益会反转成什么。

#### 3.2.1 核心-辐射型（Hub-and-Spoke）

- **被什么约束逼出来**：跨域概念**必须有一个唯一的裁决点**，但团队又不具备同时治理全部域的语义能力——于是把裁决权收进一个中心域，其余域只做特化。
- **结构**：

```turtle
# Hub-and-Spoke：中心域持有术语主权，辐射域只允许「特化」不允许「重定义」
@prefix :    <https://acme.com/ontology/core/v1#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

:Customer a owl:Class .
:Order    a owl:Class .
:Carrier  a owl:Class .   # hub 侧定义的跨域术语，辐射域只引用、不重定义
:placedAt a owl:ObjectProperty ; rdfs:domain :Customer ; rdfs:range :Order .

# 辐射域（物流）不重定义 Order，只挂到 hub 上
:Delivery   a owl:Class ; rdfs:subClassOf :Order .
:hasCarrier a owl:ObjectProperty ; rdfs:domain :Delivery ; rdfs:range :Carrier .
# 关键：跨域连接用 rdfs:subClassOf 挂载，不用 owl:equivalentClass 声明等价
#       等价声明会把裁决权交回两个域，中心等于不存在
```

- **为什么这样设计有效**：**因为全部跨域连接都经由 hub 的类与属性，所以「两个域说的是不是同一个概念」在整个组织里只有一处需要裁决**——对齐成本从域数的平方降到域数。这也是它被当作「简单优先」的原因：多数单域场景下，裁决点唯一比表达力强重要得多。
- **代价**：hub 团队成为全部辐射域的发布瓶颈；hub 每改一条公理，全部辐射域都要重新推理验证（推理成本随辐射域数量线性叠加）；hub 里的一个语义错误会沿 `subClassOf` 传播到所有辐射域，且**修正要等一个跨域发布周期**。
- **失效点**：当 hub 的类被多个域以「不可删除」的方式引用时，**中心过载**会反转优点——**优点是「裁决点唯一」，当裁决点的排队时间超过各域自己的迭代周期时，它变成「所有域的迭代速度被一个团队的带宽上限锁死」，因为每一次跨域变更都必须穿过同一个发布队列**。【经验】多数团队在 3–5 个域共用同一个 hub 时会开始感到这个上限。
- **自验方法**：数一数「有几个域在引用 hub 定义的类」，以及「最近一次 hub 公理变更到全部辐射域验证完成，用了多久」。后者超过一个团队自己的迭代周期时，你已经在中心过载的临界点上。
- **真实使用**：Schema.org 是公开可核验的中心词表形态——一套公共 Type / Property 由搜索引擎联盟维护，站点只消费不重定义（【公开：Schema.org 官方站点, 2011】）。企业内单业务域的本体绝大多数是这个形态（【经验】）。

#### 3.2.2 联邦型（Federated Ontology）

- **被什么约束逼出来**：没有任何一方有权力定义另一方的概念——跨集团、跨行业、跨机构（医疗 / 医保 / 药品）时，术语主权无法上收，只能靠对齐互联。
- **结构**：

```turtle
# Federated：两个本体各自拥有命名空间与发布节奏，连接只发生在「对齐层」
@prefix h: <https://hospital.example/onto/v2#> .   # 医院本体，独立维护
@prefix i: <https://insurer.example/onto/v3#> .    # 医保本体，独立维护
@prefix f: <https://align.example/links/v1#> .     # 对齐层，只放映射公理
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

h:Patient  a owl:Class .
i:Insured  a owl:Class .

f:Patient_Insured a owl:Class ;
    owl:equivalentClass h:Patient , i:Insured .   # 强对齐：风险最高的一类断言
f:hasPolicy rdfs:subPropertyOf i:hasContract .    # 弱对齐：只声明包含，不做等价

# 注意：owl:imports 会把被导入本体的「全部公理」拉进同一推理上下文，
#       它解耦的是命名空间与发布，不是推理
```

- **为什么这样设计有效**：**因为对齐公理被单独放在一个层里，任何一方改自己的本体都不需要改对方**——术语主权与集成解耦，这是跨机构场景下唯一能谈成的形态。
- **一个必须知道的机制细节**：`owl:imports` 不导入「模块」，它把被导入本体的**全部公理**拉进同一个推理上下文。所以在逻辑层面，联邦并没有把两个本体隔开——它隔开的是命名空间、版本与发布流程。这也意味着**联邦的性能上限由「最大那个成员本体」决定**，而不是由平均规模决定。真正要靠逻辑隔离时，用的不是 `owl:imports` 而是模块抽取（3.2.4）或联邦查询引擎。
- **代价**：跨本体推理的复杂度由**被导入公理的并集**决定，而不是由各方各自的规模决定（`owl:imports` 的传递闭包会把公理集合并）；对齐关系的判定（两个类是否真的等价）没有一般可判定的自动方法，只能靠字符串/结构/嵌入方法给出候选、再由人或 LLM 复核；一次跨本体查询可能同时依赖多个 endpoint，联邦查询引擎要承担部分结果合并。
- **失效点**：**当对齐关系数从「数十条」【经验：随成员本体的对齐粒度与各方可投入的复核人力变，粒度越细、同一批人能持续复核的条数越少】增长到需要排期维护时，联邦的成本会从「推理慢」反转为「对齐本身成了独立工程」**，因为每新增一个成员本体都要与已有 N 个逐一对齐——增量 O(N)、总量 O(N²)，而对齐正确率不随自动化程度线性提升，**代价是组织里的对齐工作量按平方增长，而联邦的收益（自治）却不随之增长**。
- **自验方法**：把对齐层单独拿出来数一数——现在有多少条映射公理？最近新增一个成员本体时，需要与几个已有本体逐一对齐？后者等于前者所属的本体数时，你已经在 O(N²) 的曲线上。
- **真实使用**：OBO Foundry 是公开可核验的联邦实践——一批生物医学本体各自维护、通过统一格式与导入机制互联（【公开：OBO Foundry 项目, 2007】）。跨机构场景（医院 / 医保 / 药品）用这一形态（【经验】）。

#### 3.2.3 分层型（Layered Ontology）

- **被什么约束逼出来**：需要**跨行业、跨学科复用**——如果每个领域都从零定义「什么是时间」「什么是过程」，不同领域的本体永远无法对齐；于是先固定一层不含业务名词的顶层。
- **结构**：

```turtle
# Layered：顶层（Foundational）→ 领域（Domain）→ 应用（Application）
@prefix :    <https://acme.com/ontology/healthcare/v1#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

# 顶层：只声明最抽象的分区，不含任何业务名词
:Continuant a owl:Class .
:Occurrent a owl:Class ; owl:disjointWith :Continuant .

# 领域层：把业务实体挂到顶层分区上（挂错了，应用层会跟着错）
:Person    a owl:Class ; rdfs:subClassOf :Continuant .
:Admission a owl:Class ; rdfs:subClassOf :Occurrent .

# 应用层：只做特化与局部约束，不新增顶层概念
:InpatientAdmission a owl:Class ; rdfs:subClassOf :Admission .
```

- **为什么这样设计有效**：**因为顶层的分区是跨领域共享的，所以两个从未合作过的领域本体，只要各自把概念挂到同一套顶层分区上，对齐时就已经有了公共锚点**——跨域对齐从「逐概念谈判」退化成「检查挂载位置」。
- **代价**：构建门槛高且前置——顶层本体、领域专家、本体工程师三者缺一不可；顶层挂载错误具有传染性（一个 `Person` 挂错分区，全部子类都错）；顶层本体本身的学习成本要由全部参与者承担。
- **失效点**：**当本体只在单一行业、单一监管体系内使用时，分层的收益会归零而成本全额发生**——因为顶层的价值来自「跨领域复用」，领域只有一个时不存在复用方，**你付出的是顶层本体的建模与培训成本，换回的是零次对齐收益**。此时正确做法是退回核心-辐射型。
- **自验方法**：数一数「有几个独立领域需要共用同一套抽象」。只有一个时，分层型的全部成本都是沉没成本；两个以上、且它们存在第三方对齐需求时，顶层的价值才开始兑现。
- **真实使用**：BFO 作为上层本体被纳入国际标准（【公开：ISO/IEC 21838-2, 2021】，读者可自行核验版本号与年份）；领域层则有 SNOMED CT、Gene Ontology 这类长期维护的临床与生物本体的公开材料。医疗、金融、政府这类跨机构、长期演化的域是分层型的主要场景（【经验】）。

#### 3.2.4 模块化（Modular Ontology）

- **被什么约束逼出来**：**本体规模与发布耦合**——万级类【经验】时不可能每次改动都全库重推理；且多个团队并行开发时，一个团队的改动不能让其他人全部重验。
- **结构**：

```text
模块抽取（locality-based module extraction；这是学界方法，不是规范定义的机制）
  本体 O = M1 ∪ M2 ∪ M3 … ∪ Mn          # 按公理切分，不按组织架构切分
  某任务只需要签名 Σ（它真正用到的类与属性）：
      extract(O, Σ) ─► M ⊆ O
  正确性条件：M 必须是 O 在 Σ 上的「保守扩展」
      —— 用 M 替换 O，Σ 上的推理结论不变
  ────────────────────────────────────────
  模块抽取的依据是「语法局部性」，不是业务边界
  → 模块边界必须与公理的书写方式对齐
  → 组织架构图与模块边界不一致是常态，必须显式换算
```

- **为什么这样设计有效**：**因为模块抽取的判据是局部的，所以「这次改动影响哪些模块」可以机械算出，而不是靠人判断**——发布从「全库重推理」变成「只推理受影响的模块」，多团队并行成为可能。
- **代价**：模块边界是设计决策而非自然产物，边界画错会让抽取出的模块连带上无关公理（局部性判据只看公理的作用域，不看你的意图）；模块之间的公理归属需要规则（哪条公理属于 A 域还是 B 域）并持续维护；工具链与流程复杂度显著上升。
- **一个必须知道的机制细节**：模块抽取是**按签名（signature）算出来的，不是按目录切出来的**——同一个本体，用不同的签名去抽，得到的模块不同。所以「我们的模块就是我们的业务域」这句话在多数团队里是错的：能对上的只有「公理作用域恰好与业务边界重合」的部分，其余要靠显式声明（公理归属规则）补上。
- **失效点**：**当模块切分与公理的实际书写方式冲突时，模块化的收益会反转**——如果跨模块公理大量存在（例如用全局 `owl:equivalentClass` 把两个模块的类绑死），抽取出的模块会不断膨胀，**优点是「局部改动能局部发布」，在这种写法下会变成「每次局部改动仍然拉进大部分模块，因为公理的作用域本来就是全局的」**。
- **自验方法**：随便挑一个模块，从本体里把它的公理拿掉，看有多少条「本不属于这个模块」的公理跟着失效。比例高，说明模块边界与公理作用域对不上，模块化只提供了文件切分、没有提供推理隔离。
- **真实使用**：公开可核验的模块化消费场景是临床术语发布——SNOMED CT 的国际版与各国扩展以「模块」为单位发布，消费方按需装载自己需要的模块，而不是整库导入（可在 SNOMED International 公布的发布文件与元数据中按 module 关键词核验）（【经验】）；工具侧，OWL API 等实现提供局部性模块抽取器，可直接调用。**一处需要说清的归属**：局部性模块抽取是学界方法（【公开：Cuenca Grau, Horrocks, Kazakov, Sattler, *Modular Reuse of Ontologies: Theory and Practice*, JAIR 2008】），**OWL 2 规范本身对模块化只给出 `owl:imports` 这一条支持，没有规定任何模块抽取算法**（【公开：W3C OWL 2 Structural Specification, 2009】）。把它说成「规范定义的机制」会让读者误以为它随语言绑定，实际上它是一类可替换的算法。企业内万级类、多团队并行发布的场景多数落在模块化这一档（【经验】）。

#### 3.2.5 轻量化（SKOS / Schema.org 风格）

- **被什么约束逼出来**：**消费者不是推理机，而是搜索引擎、推荐系统、LLM 与人**——它们的约束是「能读懂、能聚合」，不是「能证明」。
- **结构**：

```turtle
# 轻量化：只有概念层级与关联，没有公理、没有基数约束、没有不相交声明
@prefix :    <https://acme.com/taxonomy/product/v1#> .
@prefix skos: <http://www.w3.org/2004/02/skos/core#> .
```

- **为什么这样设计有效**：**因为放弃了公理与推理，词汇表的语法极简，所以任何消费方都能在不动用 reasoner 的前提下消费它**——门槛低到 HTML 标注级别，这是它能在全网普及的唯一原因。
- **代价**：只有「描述」没有「强制」，无法拒绝不合规的数据；无法表达基数、不相交、属性链等约束，因此**语义一致性必须靠发布流程而非本体保证**；面向 LLM 时，词表能限定用词，不能限定用法。
- **失效点**：**当业务开始要求「机器能判断这条数据是不是合法」时，轻量化的优点是它唯一的优点也是它唯一的缺点**——词表没有任何公理，**当需求从「找得到」升级为「校验得住」时，消费门槛低的优点会变成约束表达能力为零的缺点，因为你没有任何可执行的断言来拒绝坏数据**。此时应把强约束下沉到内层本体，保留 SKOS 作为对外入口。
- **自验方法**：把「你能回答的业务问题」列出来，逐条问「这需要推理还是只需要查表」。全是查表时，你要的是受控词表而不是本体；出现「必须推出隐含关系」的条目时，轻量化就到顶了。
- **真实使用**：SKOS 是 W3C 推荐标准，用于受控词表与分类法（【公开：W3C SKOS Reference, 2009】）；Schema.org 是搜索引擎联盟共同采用的中心词表（【公开：Schema.org 官方站点, 2011】）。内容标签、SEO、商品类目、职位分类是典型场景（【经验】）。

#### 3.2.6 混合型（维度建模 + 本体语义层）

- **被什么约束逼出来**：已有维度建模的物理落地（事实表 + 维度表 + 分层），但跨域语义没有载体；重建物理模型代价不可接受，于是本体只做语义层、不做物理层。
- **结构**：

```text
维度建模 + 本体语义层的职责边界
  [业务事件] → ODS → DWD（事实 + 维度，物理落地，列式存储 + 分区）
                        │
                        ▼
              本体语义层（TBox：概念 + 公理 + 约束）
                · 只回答「这个概念是什么、和别的概念什么关系」
                · 不回答「这份数据存在哪、怎么最快查出来」
                        │
                  查询改写：语义查询 → SQL（QL profile 的用途，见主文件 § 2.2）
                        │
                  BI / 指标平台 / Text2SQL
  ────────────────────────────────────────
  关键：两端必须共享同一套稳定的 ER 骨架（实体 + 关系），
        否则语义层与物理层会各自演化，改写器失效
```

- **为什么这样设计有效**：**因为本体被限制在语义层，推理规模与数据规模解耦**——推理只作用在概念与公理上（TBox），数据量增长体现为 SQL 的执行代价而不是推理机的负担，这是它能在已有数仓上叠加的唯一前提。
- **一个必须知道的机制细节**：这个模式的真实工作量不在本体上，而在**映射层**——「概念 ↔ 物理表/列」的对应关系。它是全手工的、无法从任何一侧自动推导的产物：物理模型不知道本体存在，本体也看不到分区与分桶。判断一个团队是否真的落地了这一模式，看的是映射层有没有 Owner 与变更流程，而不是本体文件有多少行。
- **代价**：需要维护「概念 ↔ 物理表 / 列」的映射层，这部分是纯工程负债：物理模型每变一次，映射就要跟着改；语义查询要经改写器落到 SQL，改写器的能力上限就是**能表达的问题的上限**（QL profile 之外的问题要靠预计算）；两套模型（语义、物理）的变更节奏必须协调，否则出现「本体说 A、表里存 B」。
- **失效点**：**当物理模型进入高频变更期时，混合型的优点会反转**——映射层是本体与物理表之间的手工耦合，**变更频率一旦超过映射层的维护速度，语义层就会开始撒谎（给出与物理数据不符的定义），因为语义层的正确性依赖映射层的时效性，而映射层没有自动同步机制时只能人工追平**。
- **自验方法**：抽查 10 个语义定义【经验：抽样数随语义定义总数与逐条回溯的成本变，定义总数不足 10 个时全查】，回溯它们的来源——如果每一个都能从物理表的 DDL 或转换逻辑自动推导出来，你的「语义层」只是文档；只有当存在无法从物理表推出的定义（例如「什么算一个有效订单」）时，你才真的在维护语义层。
- **真实使用**：BI / 指标平台 / Text2SQL 团队在已有事实表与维度表之上补一层受控词汇与公理，用查询改写器把语义查询落回 SQL，是本主题下「已有数仓、要补语义层」这一档的主流做法（【经验】）。

六个模式放在一起看，真正的差别只有三列：

| 模式 | 裁决权在哪 | 换来的性质 | 最先被哪条约束推翻 |
| --- | --- | --- | --- |
| 核心-辐射型 | 一个中心域 | 对齐成本从域数² 降到域数 | 并行发布的团队数（团队技能与运维能力） |
| 联邦型 | 对齐层 | 术语主权与集成解耦 | 成员本体数（对齐工作量按平方增长） |
| 分层型 | 顶层本体 | 跨领域有公共对齐锚点 | 领域数（只有一个领域时收益归零） |
| 模块化 | 抽取机制 | 影响面可机械计算 | 公理写法（跨模块公理多则模块膨胀） |
| 轻量化 | 不设裁决权 | 任何消费方都能直接用 | 一致性要求（要拦脏数据时无断言可用） |
| 混合型 | 语义层与物理层的映射 | 推理规模与数据规模解耦 | 物理模型变更频率 |

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 单一企业、单业务域、3–30 个核心概念【经验】 | 核心-辐射型 | 不选分层型：顶层本体的价值来自跨域复用，只有一个域时收益为零、成本全额发生 | 这些概念是否只在一个域内被引用 |
| 跨业务域、需要语义互联，但无一方能定义另一方 | 联邦型 | 不选核心-辐射型：会立刻出现中心过载，hub 团队成为全公司发布瓶颈 | 是否存在一个域有权单方面裁决别人的术语 |
| 跨行业 / 跨学科 / 政府与医疗级、长期演化 | 分层型 | 不选联邦型：没有共同顶层锚点时，对齐只能逐概念谈判，成本按平方增长 | 是否有可复用的公开顶层或领域本体，且你确实有多个领域要对齐 |
| 万级类、复杂属性、需要多团队并行发布与分布式推理【经验】 | 模块化 | 不选联邦型：联邦解耦的是发布与命名空间，不解决「一次改动引发全库重推理」 | 是否出现「一个域改公理，全库重新推理」的现象 |
| 标签 / SEO / 内容分类 / 受控词表 | 轻量化（SKOS / Schema.org） | 不选完整 OWL：表达力过剩，消费门槛直接劝退搜索引擎与业务标注者 | 消费方是搜索引擎、标签体系，还是推理机 |
| 已有维度建模，需要补语义层 | 混合型（维度建模 + 本体语义层） | 不选纯本体：重建物理模型代价不可接受，本体只应做语义层 | 语义定义的消费者是查询改写器（要能落 SQL）还是 reasoner |

表里最常被误选的一对是**联邦型与模块化**：两者都承诺「自治」，但联邦给的是**术语自治**，模块化给的是**发布自治**。有团队为了消除「大家都改同一个文件」的合并冲突而选联邦，结果发布耦合没解决（冲突只是从文件合并变成了对齐公理的归属争论），反而额外背上了跨本体推理与对齐维护。判断方法很直接：**痛点如果出现在提交环节，要用模块化；痛点如果出现在「这个字段在对方那边叫什么」的谈判环节，才用联邦。**

这张表有一个隐含前提：**约束的组合是被观察到的，不是被猜出来的**。判断自己落在哪一档，只需三个可数的量——跨域引用的概念数、需要并行发布的团队数、能被机器自动校验的规则条数。三个数都很小的时候，选最简单的那一档即可：本体工程的成本永远比它看起来高，因为开销集中在「每一次变更都要重新对齐」上，而不是集中在初次建模上。初次建模的工时可以估，后续对齐的工时只能靠约束来压。

### 3.4 组合模式：真实系统不会只用一种

1. **分层（顶层）+ 模块化（每域一块）**——顶层承担跨域对齐锚点，每个领域本体是独立模块、独立发布。职责边界：顶层只放分区与关系范畴，领域层放业务概念，模块边界按公理作用域划。运维代价：模块归属规则必须写下来并有人维护，否则模块会缓慢合并成一个文件。适合规模：多个领域本体、且需要长期跨域对齐（万级类以上【经验】）。
2. **核心-辐射（企业核心域）+ 联邦（对齐外部标准）**——企业自己的核心域用中心词表统一裁决，对外通过一层对齐公理挂到行业标准（如 Schema.org、PROV-O）上。职责边界：内部概念归中心域，外部标准只引用不修改。运维代价：对齐层需要版本管理（外部标准会升版，`owl:imports` 会把升版的差异带进推理）。适合规模：单企业内部治理 + 有对外数据交换需求。
3. **轻量化入口（SKOS）+ 强约束内核（OWL + SHACL）**——对外用 SKOS 词表给人看、给 LLM 用；对内用 OWL 公理与 SHACL 形状做准入校验。职责边界：SKOS 管「用哪个词」，OWL 管「什么关系成立」，SHACL 管「什么数据能进」。运维代价：两套词汇必须保持映射一致，映射过期就会出现「入口能搜到、内核不认」。适合规模：内容与商品这类「消费者多、但必须拦脏数据」的场景。

这三个组合的共同点是**入口与内核分离**：入口追求低门槛（谁来都能用），内核追求强约束（不合规进不来）。反过来设计的系统——入口强约束、内核无约束——是这一主题下最常见的形态错误：**它让能用的人觉得麻烦，又拦不住真正需要拦的数据**。这也解释了一个常见现象：同一个团队既抱怨「本体的学习成本太高」，又抱怨「本体根本拦不住错误数据」——这两句话指向的其实是同一个问题，即入口与内核没有分开。

| 组合 | 谁承担门槛 | 谁承担约束 | 最容易坏在哪 |
| --- | --- | --- | --- |
| 分层 + 模块化 | 顶层本体提供锚点（一次投入，长期复用） | 各模块自行声明公理 | 顶层挂载错误会传染全部模块 |
| 核心-辐射 + 联邦 | 中心域承担对内裁决 | 对齐层承担对外映射 | 对齐层随外部标准升版而漂移 |
| SKOS 入口 + OWL/SHACL 内核 | SKOS 面向人与模型，门槛最低 | OWL 与 SHACL 面向机器，约束最强 | 两套词汇的映射过期 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「一锤子买卖」 | 本体文件半年内没有提交【经验：这个时长随本体的发布节奏与下游消费者数量变，消费者越多、越要缩短】；没人能说出当前版本的 Owner | 本体与业务脱节后，下游会绕开它自己建映射，「唯一语义源」名存实亡 | 本体被当成项目交付物立项，验收标准是「文件交付」而不是「被引用」 | 明确 Owner、`owl:versionInfo` + 语义化版本、把变更纳入评审流程 |
| 「类爆炸」 | 类数量持续增长而实例数量不增长；reasoner 单次分类超过可接受时长 | 每个名词都成为 Class 后，分类（classification）的计算量上升，而表达力没有同比例增加 | 把「名词」等同于「概念」，缺少「什么才值得成为一个类」的判据 | 只把需要在公理里被引用的概念做成 Class，其余做成 Individual 或 Property；设定类数量的预算并定期审计 |
| 「无 Profile 推理」 | 换了 reasoner 就报错或超时；无法说明本体属于 EL / QL / RL 哪一档 | 用 OWL DL / Full 的表达力配上任意 reasoner，推理不可终止或不可控，项目卡在「跑不动」 | 先写本体后选工具链，profile 决策被跳过 | 先定 profile 再选 reasoner（主文件 § 2.2）；把 profile 写进工程约定 |
| 「过度形式化」 | 改一条业务规则要动公理，动公理就牵连大范围重新推理 | 业务逻辑进入公理层后，一次规则变更的作用域不可控，推理链连锁失效 | 把「凡能形式化的都形式化」当成目标，混淆了「语义」与「规则」 | 公理只表达核心语义，业务规则用 SHACL / 规则引擎承载；迁移动线是「规则变了不影响分类」 |
| 「无 SHACL 校验」 | 数据里能查到违反定义模式的实例，且没人收到通知 | OWL 在开放世界假设下不会因缺值报错，缺少 SHACL 时本体对数据没有任何强制力 | 把本体当成文档工程，没有把校验接进数据准入流程 | 为每个核心类写 NodeShape / PropertyShape，把 SHACL 校验接进发布门禁 |
| 「借 LLM 直接构建本体」 | 本体里有语法合法但业务上不成立的概念；没人能解释某个类为什么存在 | 结构错误的代价是滞后的——它在推理与下游集成阶段才暴露，届时返工面覆盖全部依赖方 | LLM 能高效产出「看起来像本体」的结构，掩盖了「专家验证不可跳过」这一步 | LLM 只用于起草与候选生成，入库前必须过三关：专家验证、SHACL 校验、推理验证 |
| 「无视命名空间」 | 全部概念挤在同一个 `example.com/...#` 前缀下；跨组织交换时要重命名 | 命名空间是解耦的最小单位，单前缀会强制所有域共享同一发布节奏 | 起步阶段只有一个域，命名空间被当成形式 | 采用分层命名空间 `{org}.{domain}.{concept}`，在第一次跨域复用前就定好 |

**最危险的两个**。第一是「无 SHACL 校验」：它最难被察觉，因为**没有报错本身就是症状**——团队以为本体在保护数据，实际本体只提供了词汇，没有任何准入约束；事故形态是「脏数据安静地流到下游指标里」。第二是「借 LLM 直接构建本体」：它的暴露方式不是报错，而是**下游集成时的语义冲突**——两个由 LLM 分别起草的模块用了同一个词指两个概念，直到有人做对齐时才发现，而那时依赖它们的链路已经建好。

第三个值得单独说的是「类爆炸」，因为它的触发条件很隐蔽：**它不发生在建模阶段，而发生在业务扩张阶段**——每来一个新名词，最省事的做法就是加一个 Class，直到某次全量分类跑不完。可用一条操作判据拦住它：**这个类是否需要在某条公理里被引用？** 不需要，它就不该是类。

这四条反模式的共同点是**它们都在「看不见的地方」生效**：无 SHACL 的症状是没有告警，「过度形式化」的症状出现在别人改规则的时候，LLM 起草的语义冲突要到集成时才暴露，类爆炸要到规模上来才显形。共同的对策也只有一条——**把「本体是否还在起作用」变成可观测的指标**：校验拒绝率、全量分类耗时、类的引用覆盖率、业务规则变更的平均影响类数。这几个数长期不动，通常意味着本体已经退出生产链路，只留在文档里。

相比之下，「无 Profile 推理」「无视命名空间」「一锤子买卖」这三条是**会立刻报错的**：推理跑不动、跨组织交换时无法重命名、评审会上没人能说出 Owner。它们更容易被修好，恰恰因为它们更难被忽略。**反模式的危险程度与它的可见度成反比**——所以自检清单应该优先检查「没有报警的那些」。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单域数十类 → 多域数百类【经验：随共用 hub 的域数与中心团队的复核带宽变，域越多、这一档越早到】 | 核心-辐射型 | 中心过载：跨域变更全部穿过同一个发布队列 | 联邦型或分层型 + 模块化 | 需要先把现有 hub 拆成域边界；历史 `subClassOf` 关系要逐个判定是「特化」还是「对齐」 |
| 纯 TBox → 百万级实例（ABox）【经验】 | 全量 OWL DL 推理 | 推理规模从「类」变成「类 × 个体」；全量分类不可用 | 降到 OWL 2 EL / RL，或改为预计算（materialization）+ 查询期查表 | 表达力被裁剪，部分公理必须重写；已有的推理结论需要重新验证并落库 |
| 无门禁 → 需要拒绝坏数据 | 只有 OWL | 开放世界假设下缺值不报错，本体没有强制力 | 增加 SHACL 层并接进发布流程 | 要为每个核心类补形状约束，且存量数据会集中暴露出违规 |
| 单团队维护 → 多团队并行发布 | 单文件本体 | 每次改动都要求全库重推理，且合并冲突频繁 | 模块化 + 版本化（模块独立发布） | 模块边界要与公理作用域对齐，需要一轮公理归属重构 |
| 只给自己用 → 要被 LLM / Agent 消费 | OWL 直接对外 | 消费方无法消费 OWL 语法，也无法处理开放世界语义 | 增加 JSON-LD / JSON Schema 投影，对外只暴露受限词汇 | 投影需与本体保持同步，否则出现「模型看到的定义已过期」 |
| 单组织 → 跨组织交换 | 单一命名空间 | 命名空间耦合强制共享发布节奏 | 分层命名空间 + 独立对齐层 | 已有 IRI 需迁移或建立永久重定向，历史数据的引用要保全 |
| 单一消费者 → 多类消费者并存（人 + 查询改写器 + LLM） | 单一层的完整本体 | 一类消费者要低门槛、另一类要强约束，同一份本体无法同时满足 | 拆成「入口层（受限词汇）+ 内核层（完整公理）」 | 要维护两层之间的映射，并定义「哪类消费者走哪条路径」 |

这张表的读法是**从左到右看「疼」的顺序**：前两行是技术规模驱动的跃迁（域数、实例数），中间两行是流程驱动的（门禁、并行发布），最后三行是边界驱动的（消费者构成、组织边界）。**边界驱动的跃迁最容易被漏掉**，因为数据量没变、类数量没变、团队也没变，只是「谁在用」变了——从人变成模型、从自己变成合作方。这类跃迁没有技术指标报警，只有需求方的一句话；而它要求的改动往往比前面几行都大（投影层、命名空间迁移）。

还有一条纪律：**迁移的代价永远包含「重新验证已有结论」**——profile 换了，之前推出来的分类结果要重验；命名空间换了，之前写下的等价声明要重判。把这一步排进计划，比省下一层本体更划算。

### 3.7 自检清单

下面 12 条按约束类别分组：1–5 技术约束、6–8 组织约束、9–12 变更与消费。每条都要求一个可数或可指认的答案，答不上来本身就是一个发现；组内优先看那些**不会自己报警**的条目——3.5 末尾给过理由：反模式的危险程度与它的可见度成反比。

- [ ] 你的本体选定了哪一个 profile（EL / QL / RL），这个决定写在文档里了吗？换 reasoner 后还能跑吗？
- [ ] 本体里每一个 Class，都能指认出「它在哪条公理里被引用」吗？指认不出来的类有几个？
- [ ] 跨域连接写的是 `rdfs:subClassOf`（特化）还是 `owl:equivalentClass`（等价）？等价的那些，裁决权归属谁？
- [ ] 每个核心类是否都有对应的 SHACL NodeShape？如果业务方要求「机器判断这条数据是否合法」，你当前的本体能给出一条可执行的断言吗？给不出，本体就只是在提供词汇。
- [ ] 业务规则有几条被写进了公理，这几条规则变更时会牵连多少类重新推理？在本体的内容里，你能分清哪一部分是机器推出来的、哪一部分是人写上去的吗？
- [ ] 你能否说清「模块边界是按公理作用域划的，还是按组织架构划的」？两者不一致时按哪个执行？
- [ ] 全部概念是否挤在一个命名空间下（跨组织交换时是否需要重命名）？跨本体的对齐关系有没有版本与复核流程，还是只存在于某个人的记忆里？
- [ ] 本体的 Owner 是人还是团队，这个人最近一次提交是什么时候？上一次发布到全部消费方拿到新版本间隔多久，这个间隔里有没有消费方在按旧定义产出数据？
- [ ] 由 LLM 起草的那部分本体，是否走完了「专家验证 + SHACL 校验 + 推理验证」三步？
- [ ] 语义定义能否从物理表自动推导？如果不能，映射层由谁负责追平物理模型的变更？
- [ ] 本体的消费者里，有多少能在不问你任何问题的情况下自己用它？（一个都答不出来，说明消费门槛与消费者构成不匹配）
- [ ] 最近一次因为本体拦下了错误数据，是什么时候？（从没发生过，说明本体没有强制力）

这 12 条里，1–5 条对应技术约束（profile、类与公理、SHACL、规则的归属），6–8 条对应组织约束（模块归属、命名空间与对齐层、Owner 与发布时效），9–12 条对应变更与消费（LLM 起草、映射层、消费者自助、拦截证据）。哪一组答不上来的多，就回到 3.1 的约束表去找对应的那一行。

如果第 4、7、12 条的答案都是「没有」，问题通常不在本体的设计上，而在这份本体还没有进入生产链路——它现在是一份文档。

### 3.8 小结

把六个模式压成一句话：**你要求机器在多大范围内替你判断，就必须付多大范围的推理与运维成本**。要求越低（只要求「词一致」），模式越轻（SKOS）；要求越高（要求「推出隐含关系」），模式越重（分层 + 模块化 + profile 裁剪）。跳过这一步去选模式，等于在没确定要解决什么问题之前先选工具。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 单域、概念少、要治理成本最低 | 核心-辐射型 | 对齐成本从域数² 降到域数，代价是 hub 成为发布瓶颈 |
| 无一方有权定义另一方（跨集团 / 跨机构） | 联邦型 | 术语主权与集成解耦，代价是对齐工作量按成员数增长 |
| 多个领域需要跨域对齐锚点 | 分层型 | 顶层分区是公共锚点，代价是前置建模门槛高 |
| 规模大、多团队并行发布 | 模块化 | 局部性判据让影响面可机械计算，代价是边界设计与维护 |
| 消费者是搜索引擎 / 标签体系 / LLM | 轻量化（SKOS / Schema.org） | 无公理所以无门槛，代价是完全无法强制 |
| 已有数仓、只补语义 | 混合型（维度建模 + 语义层） | 推理规模与数据规模解耦，代价是映射层成为新负债 |

> 本节小结：本体模式不是「按场景选一个」的清单，而是**「表达力—推理复杂度」这一组约束在不同规模下的解**——决定模式选择的唯一那条约束是**你要求机器在什么范围内替你判断**：只要词汇（SKOS）、要概念层级（核心-辐射）、要跨域推理（联邦 / 分层）、要大规模可跑（模块化 + profile 裁剪）。表达力每上调一档，就必然用一档推理成本与运维面去换。
