### 7.1 先立判据：为什么打分表会误导

打分表在这里有一个结构性问题：**同一个 1–5 刻度被用来表示两种方向相反的东西**——有的行表示「能力越强分越高」，有的行表示「代价越大分越高」。原表里「工程门槛」一栏给本体建模打 5，而表下的结论把「工程门槛」列为本体建模的两项劣势之一；「学习曲线」一栏干脆写成「**5（陡）**」——同一个 5，在别的行是优点，在这一行是代价。这不是笔误，而是把「能力」和「代价」压进一个数轴后必然出现的混乱：**读者无法知道高分到底该高兴还是该警惕**。

即使把刻度统一，分数仍然会误导，因为**权重是场景决定的**。同一个「查询性能」维度，在「分析师直接对着语义层跑聚合查询」的场景里是硬约束；在「语义层只负责给查询改写器提供定义、聚合仍落在列式数仓上」的场景里，它几乎不构成约束——因为慢的那一段根本不在这条路径上。本体建模真正的定位是后者（主文件 §1.3 把本体描述为 DWD 之上的语义中间层），但打分表把两种路径混成了一行。

更关键的是，分数掩盖了**「能不能」与「好不好」的区别**。「推理能力」一栏维度建模与 ER 建模都只能得最低分，这不是「差一点」，而是**结构上不具备**：`1:N` 主外键约束只能拒绝写入，不能推出「父亲 ⊆ 父母」这类隐含事实，无论怎么优化都不会产生推理结果。同理，「形式化严谨性」在本体上是可判定性换来的——它带来推理，也带来复杂度上界，这两件事必须一起看。

因此本节不用分数，而用一组能落到机制上的判据。判据的作用**不是给候选排序，而是先筛掉在你的约束下不可能成立的候选**——筛完之后，通常只剩一两种候选，比较的重点也随之从「谁更强」变成「哪条代价我付得起」。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 推理与非推理的分界 | 我是否真的需要机器推出「没写下来的事实」 | 推理是本体唯一不可替代的能力，也是它全部代价的来源（复杂度、reasoner 选型、变更影响面）。不需要推理却选了完整 OWL，等于用可判定性去换一份没有消费者的表达力 |
| 假设体系 | 缺值在我的场景里意味着什么；两个不同标识能不能默认判为不同实体 | 开放世界假设下「没填」不等于「不存在」，这决定你能否用语义层做数据准入。它是一道非黑即白的分界，不能靠调参弥合 |
| 落地的物理形态 | 语义要落在表、三元组还是属性图上；查询由谁发起 | 形态决定迁移成本：表上做语义层是逐表映射，三元组是重建一份存储，属性图是重写查询语言。三种的运维面完全不同 |
| 成本随什么增长 | 建模人力（概念数）还是推理与物化（实例规模） | 本体的成本函数会在实例上量时**换主导项**：从人力主导翻转为算力主导。这个拐点决定了你该不该上完整 profile |
| 变更的影响面 | 改一处定义要牵连多少下游、要不要全库重新推理 | 语义层的价值来自被引用，代价也一样——被引用得越多，一次变更的验证面越大。它决定了模块化与版本策略是否必须 |
| 消费者构成 | 谁来消费语义：人、查询改写器、LLM、还是 Agent | 不同消费者对「门槛」与「约束强度」的要求相反：人要好读，改写器要能落 SQL，LLM 要结构化投影。消费者一多，单层本体必然不够用 |

六条里最容易被跳过的是第一条。大量「本体项目」的失败不是在建模阶段，而是在立项目阶段——把本体当成数据治理的通用答案引入，结果发现真正的痛点是「两个字段叫法不同」，那属于受控词表能解决的问题（本章 §3.2.5 把它归为轻量化模式），**引入公理只会把维护成本乘以一个倍数，而不带来任何新增能力**。

六条判据的使用顺序也值得说明：**先问第一条（要不要推理）与第二条（假设体系能不能接受），这两条是非黑即白的，答完就能淘汰大部分候选；再问第三、四条（物理形态与成本函数），这两条决定方案能不能在你的存量里活下来；最后问第五、六条（变更影响面与消费者构成），这两条不决定「能不能选」，只决定「选完之后要维护什么」**。顺序反过来会浪费大量时间：先讨论消费者构成、再发现根本不需要推理，前面的讨论就全部作废。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型实现 / 使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| ER 建模 | 单库 / 单系统的业务数据结构 | 实体 + 关系 + 主外键约束；约束只能拒绝非法写入，**不能推出新事实** | ERwin、PowerDesigner、各数据库 DDL | 工具商业；模型本身无许可 |
| 维度建模 | 面向查询性能与口径一致的物理组织 | 事实表 + 维度表 + 一致性维度（Kimball 路线），以反范式换查询效率 | dbt 及各 MPP 数仓生态 | dbt-core 开源；数仓商业 |
| Data Vault | 面向可审计、可演化的历史集成 | Hub（业务键）/ Link（关系）/ Satellite（属性）分离，新增列不改历史 | Dan Linstedt 方法论；dbt 生态有对应实现包 | 方法论公开；工具开源与商业并存 |
| 知识图谱（属性图 / RDF 图） | 实例层的关系网络 | 节点 + 边 / 三元组，查询即图模式匹配；schema 可有可无 | Neo4j、NebulaGraph、TigerGraph、Stardog、GraphDB 等 | 开源（社区版）与商业版并存 |
| 本体建模（OWL） | 可推理的语义契约（schema 层） | 描述逻辑公理 + reasoner 推导隐含事实；TBox 与 ABox 分离 | Protégé、Apache Jena、ELK / HermiT / Pellet 等 reasoner | W3C 开放标准；工具链开源与商业并存 |
| 受控词表 / 轻量本体（SKOS / Schema.org） | 只统一「用哪个词」 | 概念层级 + broader / narrower / related；无公理，不产生推理 | Schema.org（Google / Bing / Yahoo 联合推出的公共词表，本章 §6 落地实践中的 Schema.org 案例）；各类标签体系 | 开放 |
| 主数据建模（OneID 体系） | 跨系统统一「同一个实体」的标识 | 标识解析与合并（ID-Mapping）+ 黄金记录；与本体正交，可叠加 | MDM 套件；自建 OneID（另见 [09-one-id](../09-one-id/09-one-id.md)） | 套件商业；自建无许可成本 |

这七种方案分三层、三族。**按层分**：ER / 维度 / Data Vault / 本体都描述 schema，知识图谱描述实例，主数据描述标识——它们不在同一层上，因此「谁替代谁」这个问法本身多半是错的。**按机制分三族**：**结构约束族**（ER、维度建模、Data Vault）靠物理实现与工程约束保证质量，无推理；**形式语义族**（本体、轻量化词表）靠公理或层级表达语义，其中只有完整本体具备推理；**实例网络族**（知识图谱、主数据建模）处理「具体有哪些实体、它们怎么关联」，schema 部分可以借用前两族。**先分层再分族，能省掉一半无意义的比较**——把知识图谱和维度建模放在一行打分的做法，就是跳过了这一步。

还有一条容易被忽略的分工：**schema 与实例的比例决定工具选择**。知识图谱的 schema 复杂度通常远低于它的实例规模，因此它在属性图存储上工作得很好；本体的表达力集中在 schema 上，实例可以完全不落地（查询期经重写访问物理表）。**当有人问「本体和知识图谱哪个好」时，正确的回答往往是「它们负责不同的层」而不是「各有优劣」**。

结构约束族内部的三者（ER、维度建模、Data Vault）最容易混淆，但它们的差别其实只有两处，问对了就不需要比分数：**第一，约束放在哪里**——ER 放在表结构（主外键），维度建模放在物理组织与 ETL 约定（一致性维度靠人和流程保证），Data Vault 放在键的设计（Hub 承载业务键、Link 承载关系、Satellite 承载随时间的属性）；**第二，变更怎么处理**——ER 改结构要迁移数据，维度建模改结构常要改历史或补 ETL，Data Vault 以插入新 Satellite 行的方式承载变更，所以它天然保留历史。由此可以直接得出结论：**要求可审计地保留历史、且源系统与变更都多，选 Data Vault；只要求当前状态查询快，选维度建模；只服务一个系统，选 ER**——这三条判断都不需要知道任何工具名称。

全景表的行不是按强弱排的：排在前面的不代表更好，只代表它更早出现、更靠近数据的物理形态。**读这张表的正确方式是从自己要解决的问题出发向下找行，而不是从上往下比**——从上往下比，第一行的 ER 建模会显得"什么都不行"，而它恰恰是单系统场景下成本最低的选择。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 表达力：公理推理 vs 结构约束

**机制是什么**：本体把约束写成**公理**（`SubClassOf`、`EquivalentClass`、`DisjointClasses`、基数约束、传递性等），交给 reasoner 计算蕴含；ER / 维度 / Data Vault 的约束是**物理的**（主外键、非空、唯一），只能拒绝违反，不能生成新事实。

**它在各候选中的实现差异**：

| 候选 | 约束的表达位置 | 能否推出隐含事实 | 一致性检查 |
| --- | --- | --- | --- |
| ER 建模 | 表结构（主外键、非空） | 不能 | 仅单库范围内 |
| 维度建模 | 物理模型 + ETL 约定 | 不能（一致性维度靠人工约定） | 靠数据质量规则 |
| Data Vault | Hub / Link / Satellite 的键设计 | 不能（历史可审计靠结构，不靠推理） | 靠加载规则 |
| 知识图谱（无 schema） | 基本无处安放 | 不能，或只能靠图查询手工实现 | 无 |
| 轻量词表（SKOS） | 层级与相关关系 | 不能（只统一词汇） | 无 |
| 本体建模（OWL） | 公理层（TBox） | **能**，由 reasoner 计算蕴含 | **能**，不一致的公理集可被检出 |

**由此必然导出的性质**：因为推理是把公理作用到图上计算蕴含，所以「人推不出但机器能推出」的关系可以自动成立（已知「父亲」与「父母」的关系，`父亲 ⊆ 父母` 会被自动纳入），代价是**表达力与可判定性绑定**——表达力越高，推理越可能不可控或不终止。工程上因此必须"先选 profile 再选 reasoner"：OWL 2 的三个 profile 分别对应不同的推理代价，EL 面向术语推理、QL 面向可改写为查询、RL 面向规则化实现（本章 §3.5 把「无 Profile 推理」列为会立刻报错的反模式，正是因为它跳过这一步）。

**公开证据**：OWL 2 于 2009 年成为 W3C 推荐标准，其引入 EL / QL / RL 三个 profile 的公开动机就是控制推理复杂度（[W3C, OWL 2, 2009]）【公开】；这套标准的完整演进时间线见本章 §1.4，其中各标准的发布档位（草案 / 候选推荐 / 推荐标准）与正式成为推荐标准的年份，请以 W3C 官方规范页面当前版本为准。把 profile 落到工程里，选择表其实只有三行：

| profile | 适合的推理形态 | 对应的落地方式 | 选它的判据 |
| --- | --- | --- | --- |
| OWL 2 EL | 概念层级与术语推理 | 小规模 reasoner，或预计算后查表 | 主要需要「由层级推出归类」，且实例规模可控 |
| OWL 2 QL | 查询期的语义展开 | 查到现有数据上（不物化），依赖查询改写 | 数据必须留在原地，且查询要能落到 SQL |
| OWL 2 RL | 规则化推理 | 规则引擎或图上的规则集 | 已有规则系统，只需要本体提供词汇与规则 |

还有一个常被忽略的差异：**只有本体这一族能做一致性检查**。ER / 维度 / Data Vault 的约束是逐条拒绝写入的，它们能告诉你不合法的那一条，但不会告诉你「这些约束放在一起是否自相矛盾」；本体的公理集则可以被 reasoner 整体检查——如果两组公理推出矛盾，问题会在建模阶段暴露，而不是等到某天数据撞上。**这项能力的价值随「术语由多方共同定义」的程度上升**：单团队建模时矛盾通常在评审会上就被人发现，多团队各自定义术语时，只有机器能查出来。

**失效条件**：当概念数量很少、且没有任何推理需求时，公理层的收益归零——此时无论用哪个 profile 都是纯开销，维度建模或 ER 建模的直接成本更低。

#### 7.3.2 假设体系：开放世界与唯一命名

**机制是什么**：OWL 默认**开放世界假设**（OWA，没被断言的不等于假）与**无唯一命名假设**（不同 IRI 可能指同一实体）；关系数据库、维度建模则默认封闭世界 + 唯一命名（表里没有的行就是不存在）。

**它在各候选中的实现差异**：

| 候选 | 缺值意味着 | 两个标识 | 因此它能保证什么 |
| --- | --- | --- | --- |
| 关系库 / 维度建模 | 不存在 | 一定不同 | 完整性 + 一致性 |
| 本体（OWL，默认假设） | 未知 | 可能相同（除非声明不相交或不同） | **一致性**，不保证完整性 |
| 本体 + SHACL | 可被形状约束判为违规 | 同上 | 一致性 + 可配置的完整性 |

**由此必然导出的性质**：因为缺值不能被推理为「不存在」，所以本体**只能保证不推出矛盾（一致性），不能保证该有的都有（完整性）**——要让机器拒绝坏数据，必须另加一层形状约束（SHACL），代价是维护两套约束并保持它们同步：OWL 管「什么关系成立」，SHACL 管「什么数据能进」；两套之间的映射一旦过期，就会出现「模型用旧定义、校验用新定义」的错位（本章 §3.4 的组合 3 正是把这两层写成「轻量化入口 + 强约束内核」）。

**公开证据**：SHACL 于 2017 年成为 W3C 推荐标准，专门用于校验 RDF 数据是否满足一组形状约束（[W3C, SHACL, 2017]）【公开】；本章 §3.5 把「无 SHACL 校验」列为最危险的反模式之一，并给出它的症状特征——**没有报错本身就是症状**。

唯一命名假设的缺失还有一个具体后果：**来自两个来源的同一实体不会自动被判为同一个**，必须显式声明等价关系（`owl:sameAs` 一类）。这意味着「多源实体统一」在本体里不是自动完成的，而是靠对齐动作显式登记——好处是**每一次「判同」都留下了可审计的依据**，这也是等保与合规场景愿意为它付成本的原因；代价是对齐工作量随来源数增长（7.4 给出它的增长方式）。如果只想要合并结果、不需要合并理由，主数据建模这条路径更直接。

**失效条件**：如果数据准入完全由上游管道保证（例如物理表本身有严格约束且写入路径受控），SHACL 层的边际收益下降；反过来，只要语义层要对外承诺「这份数据结构上合法」，这一层就不能省。

#### 7.3.3 落地路径：物化推理 vs 查询重写

**机制是什么**：推理结果可以**预先算好写进存储**（物化 / materialization），也可以在查询时把语义查询**改写成对物理数据的查询**（查询重写 / 本体驱动数据访问）。

**它在各候选中的实现差异**：

| 落地方式 | 推理发生在 | 物理数据要求 | 典型组合 |
| --- | --- | --- | --- |
| 物化（materialization） | 加载 / 重算时 | 需要一份三元组存储 | reasoner + triple store |
| 查询重写（query rewriting） | 每次查询时 | 数据留在原处（关系库 / 数仓） | 本体 + 改写器，把语义查询落到 SQL |
| 二者混用 | 热路径物化、冷路径重写 | 两者都要维护 | 大规模系统的常见形态 |

**由此必然导出的性质**：因为物化把隐含三元组提前写进存储，所以查询快、且能用便宜的存储横向扩展，代价是**数据变更后必须重算受影响部分**——写入放大与「推理结果的新鲜度」成为新的运维课题（本章 §3.6 把「纯 TBox → 百万级实例」列为一次典型跃迁，从「全量 OWL DL 推理」改为「预计算 + 查询期查表」正是跃迁后的形态）【经验】；因为查询重写不落冗余，所以物理数据永远新鲜、语义层与物理层可以各自演进，代价是每次查询都要付出重写与联邦的开销，且可用表达力受限于「能改写成什么」。QL 类 profile 存在的公开目的就是让这种改写成为可能。

**公开证据**：两种落地方式的分工写在 W3C 的规范文本里——OWL 2 QL 面向「把本体当作可改写的定义层」的查询回答，OWL 2 RL 面向规则化实现（即前向链式推演，与物化同一条路径）（[W3C, OWL 2 Profiles, 2009]）【公开】；把「数据留在原处、语义叠在其上」这条路径标准化的是映射语言——R2RML 作为 W3C 推荐标准，规定了关系数据如何按声明式映射暴露为 RDF（[W3C, R2RML, 2012]）【公开】。各 profile 与映射语言的具体条款请以 W3C 官方规范页面当前版本为准。

**一条可推导的存储量级**（【推算】）：物化会按层级展开类型断言——若某类的层级深度为 d，把 `subClassOf` 蕴含全部物化后，一条类型断言会被展开为上溯链上的 d 份，存储按层级深度线性放大（推导链：一个断言被 d 个祖先类蕴含 → 落 d 份冗余）；改成只物化「类上的直接断言」、把上溯留给查询期计算，就不放大，代价转移到查询路径上。因此**物化的实际成本不是「多存一份」，而是「乘以层级深度」**——层级越深，物化的代价越接近深度而非常数。

还有一处不常被写进选型对比、但会直接影响下游的差别：**物化会产出一份可以被任意消费者直接查询的数据（谁都能查三元组或图），查询重写则要求所有消费者都经过同一条改写路径**。前者的好处是下游不依赖任何特殊组件，坏处是它可能被当成第二份「真源」——一旦有人直接写这份存储，语义层的一致性就被破坏了；后者的好处是语义只有一处裁决，坏处是改写器成了单点，任何新消费者都要接入这条路径。选型时应当把这条差别写进治理约定，否则它会在半年后以「两份数据不一致」的形式暴露出来。

把两种落地方式的判据写清楚只有三句：**数据必须留在原处（合规、体量，或已有治理承诺）→ 走查询重写；查询延迟是硬指标、且数据变更不频繁 → 走物化；两者都占 → 混用，热路径物化、冷路径重写**。混用的代价是两条路径都要维护，并且必须保证它们对同一个语义查询给出同一答案——这需要一组常驻的一致性测试，而不是靠评审时看一眼。

**失效条件**：当语义查询里出现物理表无法表达的模式（递归关系、复杂规则链）时，查询重写会退化——要么改写失败，要么退化为拉全量再计算，此时只有物化或换 profile 两条路。

#### 7.3.4 消费门槛：谁在消费语义

**机制是什么**：同一份语义定义对不同消费者的门槛是相反的——人要好读，查询改写器要能落到 SQL，LLM 要结构化的投影（JSON / JSON-LD 之类），Agent 要可枚举的动作与边界约束。

**由此必然导出的性质**：因为消费者构成一变，「表达力」与「门槛」的权衡方向就反转，所以规模上去之后系统会自然分裂成**入口层（受限词汇，谁都能用）与内核层（完整公理，机器校验用）**；代价是两层之间的映射成为新的负债——映射过期会出现「入口能搜到、内核不认」的错位（本章 §3.4 的组合 3 与其运维代价一栏）。这不是架构偏好，而是消费者一多就必须付的成本。

**公开证据**：Schema.org 的公开做法就是只提供 Type / Property 词汇，并要求站点用 `itemscope` / JSON-LD 标注，而不是要求站点写 OWL（本章 §6 落地实践中的 Schema.org 案例）——它把门槛压到「任何人都会写标记」这一档，代价是完全没有强制性。本章 §3.6 也把「只给自己用 → 要被 LLM / Agent 消费」单独列为一次模式跃迁，并指出这类跃迁**没有技术指标报警，只有需求方的一句话**。

**失效条件**：只有一个消费者、且这个人本身就是维护者时，分两层是过早优化——此时直接维护一份本体并用文档说明即可，映射层的维护成本会超过它带来的收益。

不同消费者需要的「形态」也不同，这一列的差别比前半句更常决定架构：

| 消费者 | 需要的形态 | 能不能直接消费 OWL | 典型代价 |
| --- | --- | --- | --- |
| 人（业务 / 分析师） | 词汇表 + 定义说明 | 不能，需要入口层 | 需要维护一份面向人的说明 |
| 查询改写器 | 可改写的公理集 | 能（受限 profile） | 表达力被 profile 裁剪 |
| LLM / RAG | 结构化投影（JSON / JSON-LD）与简短描述 | 不能，需要投影 | 投影必须与本体同步 |
| 校验 / 门禁 | SHACL 形状 | 不能，需要另写形状 | 两套约束的映射要维护 |
| Agent | 可枚举的动作与边界约束 | 不能，需要动作化投影 | 语义到动作的映射需人工审校 |

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 建模人力（概念数 × 每个概念的评审次数）
      + 推理与物化（实例规模 × profile 复杂度）
      + 存储（物化后的三元组膨胀）
      + 消费门槛折算（培训、自助率、投影层维护）
      + 变更成本（每次改动引发的重新分类与对齐）
```

各候选的**主导项**与**隐性成本**：

| 候选 | 主导项 | 隐性成本 | 增长方式 |
| --- | --- | --- | --- |
| ER 建模 | 建模人力（且随模型数线性叠加） | 每个新系统一套模型，跨系统对齐靠人工 | 随系统数增长 |
| 维度建模 | 建模人力 + 物理存储与查询调优 | 一致性维度的协商成本；口径变更要改 ETL | 随业务过程数增长 |
| Data Vault | 加载与结构维护（Hub / Link 数量） | 查询要额外做连接，使用门槛高于维度建模 | 随源系统数与变更频率增长 |
| 知识图谱 | 实例存储与图查询 | schema 缺位导致的治理成本（本章 §1.2 的痛点 4） | 随实例与边数增长 |
| 本体建模 | 建模人力（前期）→ 推理与物化（后期） | profile 与 reasoner 的选型风险、变更时的重新验证面 | **主导项会换位** |
| 轻量词表 | 几乎只有人力 | 没有强制性，脏数据无人拦 | 随词汇量缓慢增长 |
| 主数据建模 | 匹配与合并的计算量 + 人工复核 | 合并错误的不可逆代价 | 随实体数与来源数增长 |

**两条量级推导**（【推算】）：

1. **主导项换位的拐点**：设类数量为 K、个体数为 N。TBox 阶段的推理规模随 K 增长；一旦实例上量，推理规模从「类」变成「类 × 个体」，全量分类的成本随 K × N 增长——本章 §3.6 把这次跃迁的经验触发点放在**百万级实例**，跃迁的解法不是换更快的机器，而是**降 profile 或改物化**。可自行核验的判据是：把实例数翻倍，观察全量分类耗时是否近似翻倍以上。
2. **对齐工作量按参与方数量增长**：联邦型与跨组织交换场景里，每新增一个成员本体，需要新增的对齐关系数量级为「新成员概念数 × 已有成员概念数」；因此参与者从 2 个增加到 n 个时，对齐工作量大致按组合数增长，而不是按成员数增长（本章 §3.3 决策表把这一条写进「联邦型」的适用判据里）【推算】。

**一条经验判据**：在**已有物理模型、且该模型变更不频繁**的条件下，「维度建模 + 语义层」的混合结构通常比纯本体或纯维度更省总成本——这条优势的边界也写在同一个模式里：**物理模型一进入高频变更期，优点就会反转**（本章 §3.2.6 的「代价」与「失效点」）【经验】；概念规模进入**万级、且多团队并行发布**时，模块化与分层命名空间从可选项变成必选项（本章 §3.3 决策表把这条经验线标在「万级类」那一行）【经验】。本章其余可回查的规模经验线只有两条：**3–30 个核心概念**（§3.3 决策表，单域够用）与**单域数十类 → 多域数百类**（§3.6 迁移表，从核心-辐射转向联邦或分层 + 模块化的触发点）——它们标的是「该换哪个模式」，而不是「该换掉维度建模」。判断自己是否真的在维护语义层，可以数一个量：**有多少定义是无法从物理表自动推导出来的**——数得越少，说明你的「语义层」越像文档。

成本函数最后一项（变更成本）最容易被低估：它不是随概念数线性增长，而是随**「概念数 × 被引用的下游数」**增长——一个被十个模块引用的顶层概念，改一次就要让十个模块重新验证与重新推理。因此控制这项成本的手段不是少写公理，而是**把公理放在作用域最小的模块里**（本章 §3.6 的模块化判据），代价是模块边界需要设计并有人持续维护——省下的是每次变更的钱，花掉的是日常治理的钱。

### 7.5 决策树（每个分支都要有阈值依据）

```
[业务问题是什么？]
 ① 是否只有一套物理系统需要建结构？
    └── 是 → ER 建模
 ② 目的是否是报表 / BI，且查询以聚合为主？
    └── 是 → 维度建模
 ③ 源系统是否多、变更是否频繁，且要求历史可审计？
    └── 是 → Data Vault
 ④ 是否需要跨系统统一「同一个实体」的标识？
    └── 是 → 主数据建模（OneID 体系；需要语义定义时在其上叠本体）
 ⑤ 问题形态是否是路径 / 多跳关系（而不是聚合）？
    └── 是 → 知识图谱 + 图推理
 ⑥ 是否存在无法从物理表推导出的定义，且这份定义要能被裁决？
    └── 是 → 本体建模 ★
 ⑦ 消费者是否只是搜索引擎 / 标签体系 / LLM，且不需要推理？
    └── 是 → 轻量词表（SKOS / Schema.org）
 ⑧ 走本体路线后：是要推出隐含事实，还是要能落到现有数据上查询？
    ├── 术语推理为主 → OWL 2 EL 一类 profile + 对应 reasoner
    └── 要落到现有数仓 → QL 一类 profile + 查询重写
 ⑨ 是否需要机器拒绝不合规数据？
    └── 是 → 加 SHACL 形状约束，并接进发布门禁
 ⑩ 概念是否上万级、且多团队并行发布？
    └── 是 → 模块化 + 分层命名空间
 ⑪ 以上多条是否同时成立？
    └── 是 → 维度建模 + 本体建模 + 主数据 + 知识图谱「四件套」
```

这棵树由两组彼此独立的判断组成：**①–⑦ 选方法**（按业务问题的形态），**⑧–⑪ 选配置**（在本体这条路径上，按推理需求、校验需求与发布方式继续细分）。两组不能互相替代——一个只需报表的系统如果还要对外交换数据，同样要走 ⑩ 的命名空间决策。

**阈值依据**：

- **①「只有一套物理系统」**：判据是「是否存在第二个需要引用同一概念的物理系统」——只有一个时不产生跨系统对齐问题，ER 建模的约束已经足够（【经验】）。
- **②「报表 / BI」**：判据是「查询是否以聚合为主、模式是否稳定」——聚合主导时维度建模的物理优化直接作用于收益，而本体的语义层在这条路径上不产生额外能力。
- **③「源系统多、变更频繁」**：判据是**源系统数量与加列频率**——Data Vault 的插入式变更（新增列不改历史）收益随变更频率上升，源系统只有一个且结构稳定时，它的额外连接成本换不回收益。
- **④「统一标识」**：判据是「同一实体的标识在系统间是否冲突或缺失」——只要各系统各自发号，就必须先做标识解析，这一步与语义层正交（可叠本体，也可不叠）。
- **⑤「路径 / 多跳」**：判据是问题形态而非数据量——「A 的供应商的母公司」这类查询在关系模型里需要递归，在图上是路径；反之，纯聚合查询在图上要额外做物化才能追上列存。
- **⑥「无法从物理表推导出的定义」**：沿用本章 §3.2.6 给的自验方法——抽查若干语义定义，逐条回溯它能否从物理表 DDL 或转换逻辑自动推导；**只有当确实存在推不出来的定义时，本体才在做它唯一不可替代的那件事**。这是整棵树里最难判、也最该先判的一条。
- **⑦「消费者是搜索引擎 / 标签 / LLM」**：判据是消费者是否具备消费公理的能力——不具备时，完整 OWL 的表达力过剩、门槛直接劝退消费方（本章 §6 落地实践中的 Schema.org 案例就是这一档）。
- **⑧「profile 选择」**：依据是推理复杂度与落地方式——EL 面向术语推理、QL 面向可改写为查询、RL 面向规则化实现（[W3C, OWL 2, 2009]）【公开】；选错的表现是「换个 reasoner 就报错或超时」（本章 §3.5）。
- **⑨「加 SHACL」**：依据是 7.3.2 的机制——开放世界假设下缺值不会报错，没有 SHACL 时本体对数据没有强制力；判据是「是否要对外承诺数据结构合法」（[W3C, SHACL, 2017]）【公开】。
- **⑩「模块化 + 分层命名空间」**：依据是本章 §3.3 的经验线——概念进入**万级**、且多团队并行发布时，单文件本体每次改动都要求全库重新推理、且合并冲突频繁；模块化的作用是让影响面可机械计算【经验】。
- **⑪「四件套」**：依据是约束组合——当「报表 + 语义对齐 + 统一标识 + 关系网络」同时成立时，没有单一方法能同时满足，只能分层组合（本章 §1.3 给出的关系图正是这一组合的形态）。

树上唯一的规模类节点（⑩）值得单独说明它**不是什么**：它问的不是「概念数量多少」，而是「这份定义要不要被多个团队并行发布」——概念数量在这里只是约束的代理量，不是判据本身。同样是一千个概念，若它们只在一个域里被引用，核心-辐射型就够；若它们分属十个需要独立发布的域，就必须模块化（本章 §3.3 用「跨域引用的概念数」而不是总数做判据）。同理，树里没有「预算」节点：预算决定你能投多少人去维护，不决定哪种语义表达方式成立；⑩ 里的「多团队并行发布」量的是**发布主体数**（一次改动要不要跨发布单元协调），与投入人数是两回事。把预算写进选型树，最常见的后果是**为省人力选了一个机制上不够用的方案，三年后再拆一次**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单系统业务库设计 | ER 建模 | 维度建模 | 单系统内没有跨域语义问题，本体的公理层没有消费者 |
| 经营分析 / BI | 维度建模 | Data Vault + 维度视图 | 本体不解决聚合性能；语义层的收益在跨域对齐时才出现 |
| 多源历史集成、频繁加列 | Data Vault | 维度建模 + 缓慢变化维 | 维度建模应对高频结构变更要改历史或做大量 ETL |
| 跨系统客户统一 | 主数据建模（OneID） | + 本体做语义层 | 只做标识不做语义，跨域口径仍对不齐；只做语义不做标识，同一人仍是两个 |
| 推荐 / 风控 / 反欺诈 | 知识图谱 + 图推理 | 属性图存储 + 规则 | 无 schema 的图会退化为「一堆节点」，治理成本随时间上升 |
| 跨域数据治理 / 语义对齐 | 本体建模 ★ | 联邦 / 分层 / 模块化组合 | 只做维度的团队最终只能靠 ETL 人工映射，口径维护成本随域数增长 |
| AI 应用的语义骨架 | 本体建模 + RAG（GraphRAG） | 轻量词表 + 向量检索 | 没有 schema 时检索结果无法验证，模型只能靠 prompt 约束 |
| 智能体的世界模型 | 本体建模 ★ | 结构化 Tool 定义 | 只有工具清单没有语义约束时，Agent 无法判断「什么不能做」 |
| 标签 / SEO / 内容分类 | 轻量词表（SKOS / Schema.org） | 完整 OWL | 表达力过剩，消费门槛劝退业务标注者与搜索引擎 |
| 企业级治理总框架 | 维度建模 + 本体建模 + 主数据 + KG | 分阶段只上其中两件 | 单独任一方法都覆盖不了「报表 + 对齐 + 标识 + 关系」四种需求 |

这张矩阵的读法是：**先按「业务问题的形态」选方法，再按「约束」加配置**。矩阵里每一行的「不选它的原因」都不是能力不足，而是**机制不落在收益点上**——例如维度建模并非「不能表达历史」，而是它的机制（反范式的事实 + 维度）不擅长承载高频结构变更，所以那一行指向 Data Vault。判断矩阵用对了没有，只需回答一个问题：**我的痛点是否出现在我准备引入的机制所作用的位置上**；答不上来，就说明还没到选工具的时候。

**四个常见组合**（各自说明职责边界与运维代价）：

1. **维度建模 + 本体建模（数仓 + 语义层）**：维度建模负责物理实现（表结构、分区、分桶），本体负责语义层（在 DWD 之上提供定义，并经查询改写落到 SQL）。运维代价：映射层成为新的负债——物理模型一改，语义映射要跟着追平，否则出现「定义描述的是上一版表」（本章 §3.2.6 的「代价」把映射层写成纯工程负债，「失效点」写明物理模型一进入高频变更期、混合型的优点就会反转；§3.7 自检清单里「语义定义能否从物理表自动推导、映射层由谁负责追平物理模型的变更」一条就是它的检查项）。
2. **本体建模 + 知识图谱（schema + instances）**：本体定义 schema（Class / Property / Axiom），知识图谱填充实例（实体、关系、属性值）。运维代价：两道治理线——schema 变更要评估对存量实例的影响，实例侧的脏数据要靠 SHACL 或图侧校验拦住；只有一层治理时，脏数据会安静地流到下游。
3. **维度建模 + 本体建模 + 知识图谱（三件套，形成企业语义基础设施）**：维度建模提供数据基础（DWD / DWS / ADS），本体是 DWD 之上的语义层，知识图谱是实例层的语义网络。运维代价：三套东西各有自己的重算周期与 Owner，必须明确「谁是真源、谁是从属」——否则同一条关系会在两处被独立维护并逐渐分叉。
4. **本体建模 + LLM + 向量（AI 原生）**：本体作语义骨架、LLM 作自然语言理解与生成、向量作语义近邻，合成 RAG / Agent 的语义底座。运维代价：本体的消费者从人变成了模型之后，需要额外维护一层面向模型的投影（JSON-LD / JSON Schema 之类），并保证投影与本体同步——投影过期会让模型按旧定义回答。

四个组合的共同点是**入口与内核分离**：入口追求低门槛（谁都能用），内核追求强约束（不合规进不来）。反过来设计的系统——入口强约束、内核无约束——是这一主题下最常见的形态错误：它让能用的人觉得麻烦，又拦不住真正需要拦的数据（本章 §3.4 已把这条现象与「抱怨学习成本高 + 抱怨拦不住脏数据」这两句话联系起来）。

四个组合还需要一组明确的职责边界，否则会在运维上互相踩：**谁是真源**（语义定义的裁决权在哪个模块）、**谁负责追平**（物理模型变更后由谁更新映射）、**谁负责校验**（脏数据由哪一层拒绝）、**谁能发布**（模块独立发布的边界在哪里）。这四问与本章 §3.7 自检清单里的组织类条目是同一组问题——组合在纸面上成立与否不难判断，难的是这四个归属在半年后还清晰。

### 7.7 选错的代价与迁移成本

**反模式：先写本体、后选 profile** —— 症状是「先建模，工具链以后再定」，本体里同时用上了公理层面的复杂表达 → 后果是换 reasoner 就报错或超时，且无法说明这份本体属于哪一档，项目卡在「跑不动」上；因为 profile 决定了哪些公理可用，它是设计约束而不是运行时选项 → 正确做法：在写第一条公理之前先定 profile，并把它写进工程约定（本章 §3.5）。

**反模式：把本体当文档交付** —— 症状是本体文件半年内没有提交，也没人说得清当前版本的 Owner → 后果是业务方绕开它自建映射，「唯一语义源」名存实亡；这个后果的机制是**语义层的价值来自被引用，不被引用就没有任何强制力** → 正确做法：明确 Owner、用 `owl:versionInfo` 一类字段做语义化版本、把本体变更纳入评审流程。

**反模式：用 LLM 直接产出本体并入库** —— 症状是「让模型读完文档生成 OWL，直接提交」→ 后果是本体里出现语法合法但业务上不成立的概念，而错误**在推理与下游集成阶段才暴露**，届时返工面覆盖全部依赖方；两处由 LLM 分别起草的模块用同一个词指两个概念，往往到做对齐时才发现 → 正确做法：LLM 只用于起草与候选生成，入库前必须过专家验证、SHACL 校验、推理验证三步。

**反模式：把业务规则写进公理层** —— 症状是「凡能形式化的都形式化」，业务规则被写成公理 → 后果是一次规则变更就会牵连大范围重新推理，影响面不可控；机制上这是把「语义」与「规则」混为一谈：公理的作用域是分类，规则的作用域是数据 → 正确做法：公理只表达核心语义，业务规则交给 SHACL 或规则引擎；一条简单的判据是「规则变了是否会引起分类结果变化」（本章 §3.5）。

四个反模式的共同点是**它们都在机械层面改变了「变更的影响面」**：profile 决定推理能否收敛，交付方式决定本体是否被引用，LLM 起草决定错误的暴露时机，规则位置决定一次改动牵连多大。因此评估一次本体变更的风险时，看的不是改动本身的大小，而是**它在上面四条里落在哪一格**。

**换成另一个方法要动什么**：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 维度建模 → 叠加本体语义层 | 物理数据不动，新增定义与映射（低） | 语义查询落到 SQL 需改写器（中） | 增加映射层的维护职责与 Owner（中） | 语义建模与查询改写（中） |
| ER 建模 → Data Vault | 需要按 Hub / Link / Satellite 重构历史加载（高） | 查询要增加连接，报表需重建（高） | 加载与结构维护流程重建（高） | Data Vault 方法论（中高） |
| 无 schema 的 KG → 本体 + KG | 已有三元组基本可保留（低） | 增加 schema 校验与推理（中） | 新增本体治理与校验门禁（中） | 本体建模与 SHACL（中高） |
| 完整 OWL → 轻量词表 + 投影 | 公理层的断言需要重写或降级（高） | 消费者改为读投影（中） | 推理组件下线，增加投影同步（中） | 从形式语义转到词表与投影工程（中） |
| 单文件本体 → 模块化 + 分层命名空间 | 需迁移 IRI 并保全历史引用（高） | 跨模块推理需重新验证（中） | 模块归属与发布流程重建（高） | 模块化设计方法（中） |
| 轻量词表 → 完整本体 | 层级与词汇可保留，公理要从零补（中） | 从「查词」改为「推理 + 改写」（中高） | 引入 reasoner、profile 约定与校验（中高） | 形式语义与描述逻辑（高） |
| 主数据建模 → 叠加本体语义层 | 黄金记录与映射不动，新增语义定义（低） | 跨域查询改为走语义层（中） | 增加语义层 Owner 与映射追平职责（中） | 语义建模（中） |

这张表里最容易被低估的一列是「查询改写」与「重新验证」：**profile、命名空间、模块边界一变，之前推出来的结论都要重验**（本章 §3.6 末尾把这一条写成纪律）。因此迁移计划里必须给「重验」留出预算——它通常比迁移动作本身更长，且无法通过加人缩短。

把这些迁移方向合起来看，会发现**代价的高低与「语义定义被引用的广度」正相关**：只在自己团队里用的语义层迁移很低（维度建模叠加语义层那一行），被全公司引用、且 IRI 已经流出去的那一份迁移最高（单文件转模块化那一行）。因此在第一次选型时值得多问一句：**三年后这份语义会被谁引用**。答案越广，越应该一开始就把命名空间、模块边界与版本机制立好——这三件事的成本在第一天最低，在第三年最高。表里还有一条隐含规律：**从「无推理」迁到「有推理」的代价，明显高于反向迁移**——因为公理要从零补、且补完之后要重新验证所有既有结论；反向下迁（完整 OWL 降为轻量词表 + 投影）虽然也要重写断言，但不需要建立新的验证体系。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 只有一套系统、要把结构建出来 | ER 建模 | 结构约束足够，公理层没有消费者，纯增成本 |
| 报表 / BI、查询以聚合为主 | 维度建模 | 物理优化直接作用于收益，语义层在这条路径上不产生新能力 |
| 多源、频繁加列、要求历史可审计 | Data Vault | 插入式变更不改历史，代价是查询要额外连接 |
| 同一实体在各系统标识冲突 | 主数据建模（OneID） | 标识解析与语义对齐是两件事，必须先解决前者 |
| 存在无法从物理表推导出的定义 | 本体建模（先定 profile） | 只有本体能推出隐含事实，代价是可判定性与变更影响面 |
| 消费者是搜索引擎 / 标签 / LLM | 轻量词表（SKOS / Schema.org） | 无公理所以无门槛，代价是完全无法强制 |
| 需要机器拒绝不合规数据 | 本体 + SHACL | 开放世界假设下缺值不报错，完整性必须另加一层约束 |
| 已有数仓、只补语义 | 维度建模 + 本体语义层 | 推理规模与数据规模解耦，代价是映射层成为新负债 |
| 多团队并行发布、概念上万级 | 模块化 + 分层命名空间 | 局部性判据让影响面可机械计算，代价是边界设计与维护 |
| 跨机构交换数据、无一方有权定义另一方 | 联邦型 + 独立对齐层 | 术语主权与集成解耦，代价是对齐工作量按参与方组合数增长 |
| 语义的消费者从人变成模型 | 增加面向模型的投影层 | 模型无法消费 OWL 语法与开放世界语义，投影是唯一通道 |
| 已有本体但没人用 | 先接一个校验或查询链路，再谈扩建 | 不被引用的语义没有强制力，扩建只会放大未使用资产 |

> 本节小结：这些方法之间真正起决定作用的差别只有一条——**你要求机器在多大范围内替你判断**。只要求「词一致」，轻量词表就够；要求「结构约束成立」，ER / 维度建模就够；要求「推出没写下来的事实」，才必须引入本体，并同时接受它的三笔代价：profile 决定的可判定性边界、开放世界假设带来的完整性缺口、以及每次变更都要重新验证的影响面。**其余维度（性能、门槛、工具成熟度）都是这条选择的后果，而不是与它并列的比较项。**
