## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

一张「模式 | 场景 | 结构 | 优点 | 缺点」表，会把设计讲成"按场景挑一个选项"。真实的模式选择不是这样发生的：它是被约束推着走的。同样是"电商交易"这件事，如果事实表一行代表一次下单，正确解是事务事实表；如果业务方问的是"每天有多少商品在售"，正确解是周期快照事实表；如果问的是"下单到收货各环节各卡了多久"，正确解是累计快照事实表。三张表都叫"订单相关的表"，结构完全不同——区分它们的不是业务领域，是**问题问的是事件、状态还是过程**。

所以本节的组织方式是：先立约束，再谈模式。约束在这里不是背景介绍，而是判据——写不出一个模式被什么约束逼出来，就说明还没理解它，也就无法判断它什么时候会失效。

维度建模里的约束最终收敛到同一个问题上：**事实表的一行代表什么，维度表的一行代表什么时点**。前者定下事实表的类型（事务 / 周期快照 / 累计快照），后者定下维度侧的 SCD 策略；星型 / 雪花 / 星座是在这两个决定之上的结构选择，OBT 宽表与语义化维度则是"把这两个决定分别搬到写入侧与检索侧"的变体。本主题的模式不是并列选项，而是同一个约束在不同环节上的投影。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 事实表一行的粒度（事件 / 周期 / 生命周期） | 事实表类型，以及度量能不能被直接 SUM | 「事实表就该像订单表一样一行一单」——被周期快照与累计快照推翻 |
| 维度是否要按历史时点还原 | SCD Type 1 / 2 / 3，以及事实表里要存多少个代理键版本 | 「保留历史总是对的」——被维表膨胀与重复计数推翻 |
| 访问模式（点查 / 扫描 / 聚合 / 检索） | 星型 vs 雪花 vs OBT vs 检索派生表 | 「范式化省存储」——在跨层次聚合查询上是负收益 |
| 跨业务过程的一致性要求 | 是否需要一致性维度、代理键是否必须统一生成 | 「代理键只是自增主键」——业务键复用会让跨事实表钻取直接失败 |
| 维度属性变更频率 | 冗余该放在维表里，还是放在写入侧宽表里 | 「宽表查询最快」——维度天天变时它变成全量回刷成本 |
| 消费方是人还是机器 | 要不要语义层、结构化维度描述、只读的检索派生表 | 「给维度表加 embedding 列就行」——那是第二份需要同步的状态 |

### 3.2 模式逐个拆解（核心节）

以下 9 个小节覆盖全部结构（星型 / 雪花 / 星座 / 事务 / 周期快照 / 累计快照 / OBT 宽表 / 语义化维度），以及决策表里出现的 SCD Type 1–3。每个都按「被什么约束逼出来 → 结构 → 为什么有效 → 代价 → 失效点 → 真实使用」写。

#### 3.2.1 星型模型（Star Schema）

- **被什么约束逼出来**：分析查询要在事先不可预知的维度组合上做聚合，而 JOIN 层数是延迟的主要变量。约束是"查询侧的维度组合不可预知"，所以必须把维度拍平，让任意维度只用一层 JOIN 就能过滤。
- **结构**：

```sql
-- 星型：1 张事实表 + N 张扁平维度表
CREATE TABLE fact_order (
  order_sk      BIGINT        NOT NULL,  -- 代理键
  order_id      VARCHAR(32)   NOT NULL,  -- 退化维度：订单号不进维度表
  order_date_sk INT           NOT NULL,  -- FK → dim_date
  user_sk       BIGINT        NOT NULL,  -- FK → dim_user
  shop_sk       BIGINT        NOT NULL,  -- FK → dim_shop
  order_amount  DECIMAL(18,2) NOT NULL,  -- 度量（可加）
  item_qty      INT           NOT NULL   -- 度量（可加）
);
CREATE TABLE dim_user (
  user_sk       BIGINT PRIMARY KEY,      -- 代理键：与业务键解耦
  user_id       VARCHAR(32) NOT NULL,    -- 业务键（自然键）
  user_city     VARCHAR(64),             -- 层次拍平进同一张表
  user_province VARCHAR(64),
  user_country  VARCHAR(64),
  user_level    VARCHAR(16)
);
```

- **为什么这样设计有效**：因为维度的所有层次都已在同一张表里，所以"按国家看销售额"与"按城市看销售额"是同一个 JOIN、只是 WHERE 不同——执行计划不随查询的维度组合变化，延迟因此可预测。
- **代价**：三项结构性成本。一是维表内冗余，省份名在每一位用户行上重复一次；二是事实表的 JOIN 数等于引用维度数，20 个维度就是 20 次 JOIN，这是下限而非调优项；三是代理键必须由统一规则生成，否则跨事实表钻取会断链。
- **失效点**：当维度需要保留历史（SCD Type 2）时，「一层 JOIN 拿全上下文」会反转成「每次查询都扫一张持续膨胀的维表」——因为拍平后的描述属性会随版本数重复，而这张维表恰恰是每次查询都要 JOIN 的那一张。
- **真实使用**：Kimball 在《The Data Warehouse Toolkit》（1996）中把星型定义为面向查询的默认结构【公开】；阿里 OneData 把维度统一在公共层定义（DIM 表）、DWS 只做"事实 + 一致维度"的汇总（阿里《大数据之路》/ OneData 公开材料，2016 年起）【公开】。多数团队的事实表就是星型【经验】。

#### 3.2.2 雪花模型（Snowflake Schema）

- **被什么约束逼出来**：维度属性存在天然层次，且层次上的描述信息在业务上被独立维护（例如地区由运营单独维护、单独变更）。约束是"层次本身是一个业务对象"，于是把层次拆成独立表。
- **结构**：

```sql
-- 雪花：维度沿层次继续拆
CREATE TABLE dim_city     (city_sk     INT PRIMARY KEY, city_name     VARCHAR(64), province_sk INT);
CREATE TABLE dim_province (province_sk INT PRIMARY KEY, province_name VARCHAR(64), country_sk  INT);
CREATE TABLE dim_country  (country_sk  INT PRIMARY KEY, country_name  VARCHAR(64));
-- 事实表只存 city_sk：层次每深一层，查询就多一次 JOIN
```

- **为什么这样设计有效**：因为层次描述只存一份，所以改"浙江省"的名字只需改一行、不必扫整张维表；也因为没有冗余，"同一个省两种写法"这类数据质量问题在结构上不会出现。
- **代价**：JOIN 层数是结构性成本——雪花化的定义就是把一张维表拆成沿层次链的 N 张，"按国家汇总"从 1 次 JOIN 变成 3 次；同时执行计划随查询进入的层次深度变化，延迟不再可预测。
- **失效点**：当查询普遍要跨层次聚合（按国家、按大区）时，「省存储」会反转成「多 JOIN」，因为省下的是层次描述的重复存储，付出的是每次查询都要沿链连接。【推算：地理维 3 级（城市 / 省 / 国家）时，星型 2 表 1 JOIN、雪花 4 表 3 JOIN（事实 → 城市 → 省 → 国家）；存储侧，1000 万行维表里地理描述约 200 字节/行，扁平存约 2 GB（10^7 行 × 200 B）；去重后的城市基数取 3 万时该维表约 6 MB（3×10^4 行 × 200 B），若只到地级市（中国约 300 余个）则约 60 KB（3×10^2 行 × 200 B）——两种口径下省下的都是同一笔约 2 GB 量级的冗余层次描述存储（扁平 2 GB 减去去重后的 6 MB / 60 KB），远小于每次跨层次聚合多出的 JOIN 的代价，取哪种口径取决于你自己维度的真实基数】
- **真实使用**：Kimball 把它列为星型的变体，并给出"以星型为默认"的建议【公开，1996 起】；TPC-DS 基准的 schema 是带层次的雪花式结构，依据是 TPC（Transaction Processing Performance Council）发布的 TPC Benchmark DS 规范——该基准首版发布于 2000 年代中期，规范此后按版本号迭代（当前版本号与发布日期见 tpc.org 的 TPC-DS 规范页，可自行核验）【公开，可自行核验】。生产中把纯雪花作为主结构的数仓较少，多见于维表成员基数很小的场景【经验】。

#### 3.2.3 星座模型（Fact Constellation）

- **被什么约束逼出来**：一个业务问题要跨多个业务过程（交易 + 支付 + 库存），而每个过程的粒度不同、度量不可相加。约束是"跨过程分析必须发生在同一个维度坐标系里"。
- **结构**：

```text
星座：多张事实表共享同一组一致性维度
   dim_date ──┬────────────────┬────────────────┐
   dim_user ──┤                │                │
   dim_shop ──┤                │                │
              ▼                ▼                ▼
        fact_order        fact_payment     fact_inventory
        （一行一订单）     （一行一支付）    （一行一天一 SKU）
              │                │
              └──► drill-across：各事实表先按一致性维度分别汇总，再在结果集上拼接
```

- **为什么这样设计有效**：因为多张事实表共用同一套维度定义与代理键规则，所以"交易额"与"支付额"可以按同一维度对齐比较；跨过程分析不需要先把事实表物理合并——合并会因粒度不同而产生重复计数。
- **代价**：一致性维度是跨团队的协商产物，每新增一个共享维度都要对齐口径与代理键生成规则，协商成本随事实表数与团队数增长；此外跨过程关联只能发生在汇总结果上，明细级关联仍需业务键或退化维度。
- **失效点**：当两个业务过程对"同一维度"的定义出现分叉（下单店铺与结算店铺）时，「共享即对齐」会反转成「同一维度承载两种语义」，因为同一个维度值在下单侧与结算侧指向不同的业务对象，drill-across 的结果因此不可解释。修法不是继续硬共享，而是退成角色扮演维度：同一张维表在事实表里出现多个外键。
- **真实使用**：一致性维度与事实星座是 Kimball 方法论的组成部分【公开，1996 起】；总线矩阵（业务过程 × 一致性维度）是它的落地清单，新业务过程必须先在矩阵上落格、才允许建表（总线矩阵的原始论述见 Kimball & Ross《The Data Warehouse Toolkit》，1996 年起）【公开，1996 起】。多数中大型数仓的汇总层是星座结构【经验】。

#### 3.2.4 事务事实表（Transaction Fact Table）

- **被什么约束逼出来**：业务事件是离散的、不可撤销的——"下单"发生过就不会变。约束是"事实只增不改"，所以取最细的一行一事件。
- **结构**：

```sql
-- 事务事实表：一行一事件，只 INSERT
CREATE TABLE fact_order_transaction (
  order_sk        BIGINT,
  event_time      TIMESTAMP,
  order_date_sk   INT,
  user_sk         BIGINT,
  order_amount    DECIMAL(18,2),   -- 可加度量
  discount_amount DECIMAL(18,2)    -- 可加度量
) PARTITIONED BY (dt STRING);
-- 事件发生过就不会变：不 UPDATE、不 DELETE，只追加分区
```

- **为什么这样设计有效**：因为写入模式是纯追加，所以事实表可以按时间分区、高压缩比存储、并且能被重放重建；又因为粒度最细，任何上层汇总都能从它重算一遍——这就是"可重述性"，也是所有下游汇总表的可验证来源。
- **代价**：行数等于事件数，是本主题里最大的那张表；同一业务对象的当前状态必须靠扫描与聚合才能还原；它无法直接回答"当时是多少"。
- **失效点**：当业务问题从"发生了什么"变成"某一时点是多少"（余额、库存、等级）时，「粒度最细最灵活」会反转成「每个状态查询都要扫全历史」——因为状态在这张表里不是被存储的，而是被推出来的，而这个推出的代价随历史深度线性增长。
- **真实使用**：三类事实表的划分出自 Kimball 方法论【公开，1996 起】；交易、点击流、支付流水这类高增长明细表普遍是事务事实表【经验】。

#### 3.2.5 周期快照事实表（Periodic Snapshot Fact Table）

- **被什么约束逼出来**：状态是经常被查询的对象（账户余额、库存、在架商品数），但状态的保持不产生事件。约束是"问题问的是某个时点的值，而事件流里没有这个值"。
- **结构**：

```sql
-- 周期快照：一行一周期一实体，即使本期无变化也写一行
CREATE TABLE fact_account_balance_daily (
  account_sk       BIGINT NOT NULL,
  snapshot_date_sk INT    NOT NULL,
  balance          DECIMAL(18,2),   -- 半可加：可跨账户 SUM，不可跨日期 SUM
  change_amount    DECIMAL(18,2),   -- 本期变化量（可加）
  PRIMARY KEY (account_sk, snapshot_date_sk)
);
```

- **为什么这样设计有效**：因为"周期"被写进了粒度，所以任意时点的状态是读一行而不是重放事件——状态查询的代价与周期数成正比，与事件数无关。
- **代价**：存储等于实体数 × 周期数，且状态没变的周期也要落一行；半可加度量不能跨时间 SUM，聚合规则必须在语义层显式声明，否则会被误加成一个没有业务含义的数。
- **失效点**：当实体基数大、周期又细（每用户每日）时，「读一行拿状态」会反转成「快照表比它要替代的事务表还大」，因为行数按实体数 × 周期数增长，而这个乘积通常大于真实状态变化的次数。【推算：1 亿活跃实体 × 每日一行 × 每行约 40 字节 ≈ 4 GB/天（10^8 × 40 B = 4×10^9 B），一年约 1.4 TB；若同期发生状态变化的实体只占 5%，则 95% 的行是"没变化也写一行"】
- **真实使用**：周期快照是 Kimball 三类事实表之一【公开，1996 起】；账户余额、库存日快照、在架商品数这类"时点状态"场景普遍用它【经验】。

#### 3.2.6 累计快照事实表（Accumulating Snapshot Fact Table）

- **被什么约束逼出来**：业务过程有确定的步骤序列，且必须度量"每一步花了多久、卡在哪一步"。约束是"过程有终点，且步骤有限、可枚举"。
- **结构**：

```sql
-- 累计快照：一行一业务全生命周期，每个步骤一列日期
CREATE TABLE fact_order_fulfillment (
  order_sk         BIGINT PRIMARY KEY,
  created_date_sk  INT,   -- 下单
  paid_date_sk     INT,   -- 支付
  shipped_date_sk  INT,   -- 发货
  received_date_sk INT,   -- 收货（终点）
  order_amount     DECIMAL(18,2),
  current_step     VARCHAR(16)   -- 覆盖式更新的"当前步骤"
);
-- 每到一个步骤 UPDATE 对应列；迟到数据要能回溯覆盖
```

- **为什么这样设计有效**：因为步骤被横向展开成列，"下单到支付耗时"是一次减法而不是自连接；漏斗各阶段的停留时长变成同一行内的列运算，查询代价与链路长度无关。
- **代价**：这张表是被更新的（打破了事实表"只追加"的惯例），因此不能按时间分区、不能只靠重放重建，必须实现幂等的 upsert 与迟到数据的回溯覆盖；新增一个步骤等于一次 DDL 变更。
- **失效点**：当步骤数或步骤顺序在业务上频繁变化时，「一步一列」会反转成「每次流程调整都要改表结构并回刷历史」，因为步骤数被写死在列的个数与含义上；更麻烦的是跳步与逆向步骤（退款、拆单、超时关闭）会让 `current_step` 失去单一含义，漏斗的分母不再可解释。
- **真实使用**：累计快照是 Kimball 三类事实表中最常用于漏斗与流程 SLA 度量的一类【公开，1996 起】；订单履约、工单处理、贷款审批这类有终点的流程适用，无终点的过程（如订阅）不适合【经验】。

#### 3.2.7 OBT 宽表（One Big Table）

- **被什么约束逼出来**：湖仓上做 Ad-hoc 与特征工程，查询模式事先不可知，而引擎的主要成本是 JOIN 与数据读取；同时扫描便宜、存储便宜。约束是"消费方多且查询形态不可预知"。
- **结构**：

```sql
-- OBT：把 JOIN 从查询时搬到写入时
CREATE TABLE obt_order_wide (
  order_id      VARCHAR(32),
  order_date    DATE,
  user_id       VARCHAR(32),
  user_city     VARCHAR(64),    -- 来自 dim_user 的属性
  user_level    VARCHAR(16),
  shop_name     VARCHAR(128),   -- 来自 dim_shop 的属性
  category_name VARCHAR(128),   -- 来自 dim_product 的属性
  order_amount  DECIMAL(18,2),
  -- 列数 100+，随消费方需求增长
  dt            STRING
);
-- 查询侧没有 JOIN：只剩列裁剪 + 谓词下推 + 聚合
```

- **为什么这样设计有效**：因为 JOIN 已经被搬到写入侧，所以查询的执行计划里不再有 JOIN，列存引擎可以在单表上做列裁剪与谓词下推——这对"每次查询用的列都不同"的 Ad-hoc 场景是最省事的结构。
- **代价**：三项结构性成本。一是存储放大，宽列在每行重复且与事实行数同阶；二是维度属性更新必须回刷历史分区，按历史时点还原的能力（SCD Type 2 的语义）在宽表里直接消失；三是治理面从"1 个事实 + N 个维度"变成"1 张表里 N 套口径"。
- **失效点**：当上游维度属性发生一次变更（改名、改口径、新增成员）时，「查询最快」会反转成「写入成本与历史深度成正比」——因为已物化的每个分区都要重刷才能与新维表一致，而重刷的代价随保留的历史长度增长。【推算：10 亿行事实、从维度引入 60 列、平均 30 字节，单份宽表约 1.8 TB 额外存储（10^9 行 × 60 列 × 30 B = 1.8×10^12 B）；若按 N 个业务视角各物化一份，存储与回刷成本再乘 N】
- **真实使用**：OBT 与"宽表化"在湖仓与 dbt 社区被广泛实践；Databricks 的 Medallion 架构把 Gold 层作为面向消费的宽表层，这套 Bronze / Silver / Gold 分层由 Databricks 在湖仓体系中提出并推广（起于 2021 年前后【经验】），其定义见 Databricks 官方术语页 databricks.com/glossary/medallion-architecture 与官方博客《What is Medallion Architecture?》——两页均为持续更新的在线文档，以站点当前内容为准【公开，可自行核验】；特征工程里"宽表 + 特征视图"是常见形态【经验】。

#### 3.2.8 语义化维度（2024+）

- **被什么约束逼出来**：消费方从"人看报表"变成"Agent 生成查询"。Agent 拿到的是自然语言描述，不是字段名，它需要先**找到**维度与度量。约束是"提问方给不出字段名"。
- **结构**：

```sql
-- 语义检索用派生表：不写进主表，可重建、可停用
CREATE TABLE dim_user_semantic (       -- 派生表
  member_sk   BIGINT NOT NULL,         -- 指回 dim_user 的代理键
  attr_name   VARCHAR(64),             -- user_level
  attr_value  VARCHAR(256),            -- '钻石会员'
  description TEXT,                    -- 人写的自然语言描述
  embedding   VECTOR(1024),            -- 由 description 生成
  updated_at  TIMESTAMP
);
-- 主表 dim_user 仍是符号匹配的唯一权威；语义表只为「找到」服务，不参与口径计算
```

- **为什么这样设计有效**：因为匹配从符号等值放宽到向量邻域，所以没写对字段名也能命中候选；又因为它是独立派生表而不是主表上的一列，所以可以整体重建、可以停用，而不会污染口径计算的权威路径。
- **代价**：第二份必须与主表同步的状态（主表行变化要增量重算，SCD Type 2 产生新版本时旧描述的归属要重新定义）；向量列与索引的存储随维度行数 × 属性数增长；近似匹配给不出"为什么命中这一条"的确定答案。
- **失效点**：当增量重算没有 Owner 时，「能命中」会反转成「稳定地命中一批已改名或已下线的成员」——因为检索仍返回结果、不报错也不告警，只是结果慢慢偏离主表，属于静默失效。判定方法：问一句"如果这个向量表停更一周，谁会先发现"，答不上来就不该上线。
- **真实使用**：图结构检索增强（GraphRAG）有可公开核验的文献——Microsoft Research 的公开论文《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》（2024）与同机构的公开博客都给出方法说明，按题名自行检索即可核验【公开，2024】；自然语言取数里"schema 链接"是独立难点，这一点在公开基准中有体现——BIRD 基准（NeurIPS 2023）把外部知识作为题目输入的一部分【公开】。语义化维度本身以厂商演示与愿景为主，**尚未见到可核验的第三方生产案例**，因此只记录，不建议在一致性维度表里预留 embedding 列。

#### 3.2.9 SCD Type 1 / 2 / 3（维度侧的历史处理）

- **被什么约束逼出来**：维度属性会变，而"去年的报表要不要保持去年的样子"这个问题必须由业务方回答——它决定了维度表一行代表"一个实体"还是"一个实体的一段有效期"。
- **结构**：

```sql
-- Type 1：就地覆盖，不保留历史
UPDATE dim_user SET user_level = '钻石会员' WHERE user_id = 'U001';

-- Type 2：新增版本行，用有效期 + 当前标志区分
--   user_sk=1001  user_id=U001  user_level='黄金'  valid_from=2024-01-01  valid_to=2024-05-31  is_current='N'
--   user_sk=1002  user_id=U001  user_level='钻石'  valid_from=2024-06-01  valid_to=9999-12-31  is_current='Y'
--   事实表按事件发生时的 user_sk 落库 → 历史时点可还原

-- Type 3：加一列存"上一版值"，只保留一次变化
ALTER TABLE dim_user ADD COLUMN prev_user_level VARCHAR(16);
```

- **为什么这样设计有效**：因为 Type 2 把"有效期"写进了维度行，所以事实表引用下单当时的代理键即可还原当时的口径——历史报表可重述；因为 Type 1 就地覆盖，所以维表行数不随变更增长、外键永远指向"当前"一行；因为 Type 3 只留一列旧值，所以它只能回答"变了没变"，不能回答"什么时候变的"。
- **代价**：Type 2 让维表行数等于每个实体的版本数之和，ETL 必须实现"比对属性 → 关闭旧行 → 插入新行"的幂等逻辑；查询要么过滤 `is_current='Y'`，要么按时间点 JOIN，任何一处漏写都会得到重复计数——这是"同一个指标两种结果"最常见的来源。
- **失效点**：当维度属性每天都可能变化（消费分档、活跃度标签）时，「保留历史」会反转成「维表按天膨胀 + 每张下游报表都必须显式过滤版本」——因为事实行的外键指向了版本，而版本数随时间累积；一次漏写过滤就让指标翻倍，且这种错误是静默的。
- **真实使用**：SCD 的 Type 1–7 分类出自 Kimball 方法论【公开，1996 起】；生产中最常落地的只有 Type 1 与 Type 2，Type 3 少见，Type 6（1+2+3 混合）更少【经验】。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 问题问"发生了什么"，需要明细 | 事务事实表 + 星型 | 不用周期快照：它会把多个事件压成一个时点值，事件细节不可恢复 | 事实表一行 = 一次事件，且事件不可撤销 |
| 问题问"当时是多少"（余额 / 库存） | 周期快照 | 不用事务表：状态要重放全部历史才能推出，代价随历史深度增长 | 能否接受状态查询扫描全历史 |
| 问题问"各环节各花了多久" | 累计快照 | 不用事务表 + 自连接：链路一变就要重写 SQL | 步骤是否有限、可枚举、有终点 |
| 多业务过程要按同一维度对比 | 星座 + 一致性维度 | 不用各自建维：跨过程钻取会因维度定义不同而失败 | 两个过程对同一维度的定义是否已被判定为同一语义 |
| 跨层次聚合是高频查询 | 星型 | 不用雪花：省下的维表存储远小于每次查询多出的 JOIN | 维度层次的基数与查询是否会跨层 |
| 查询形态不可预知、扫描便宜 | OBT 宽表（作为派生层） | 不用星型直查：JOIN 组合爆炸，Ad-hoc 每次都要重新优化 | 维度属性变更频率是否低到可以接受回刷 |
| 维度属性只在出错时被修正，业务上没有历史语义 | SCD Type 1 | 不用 Type 2：为一个不需要历史的问题付维表膨胀与下游过滤 | 业务方会不会拿去年的报表对今年的口径 |
| 维度历史必须能按当时口径重述 | SCD Type 2 | 不用 Type 1：历史会被新口径整体改写 | 业务能否接受历史报表结果变化 |
| 只需知道"是否变过"，变化次数有界 | SCD Type 3 | 不用 Type 2：为一个有界问题付无界的维表膨胀 | 变化次数是否有界、是否只要新旧对照 |
| 消费方主要是 Agent / 自然语言 | 语义层 + 星型 + 只读语义派生表 | 不用"OBT + 维度表加 embedding 列"：把检索需求写进了权威口径路径 | 主表的符号匹配权威是否仍然唯一 |

表里最常被误选的一对是**星型与雪花**：因为"雪花省存储"听起来像一条免费的优化，于是有人在维度层次上做了范式化。后果按 3.2.2 的推算就是——省下的是一张约 2 GB 量级的维表，付出的是每次跨层次聚合多出的 JOIN，而这类查询往往正是这个维度存在的理由。判断只差一句话：**这个维度会被跨层次聚合吗**？会，就别拆。

### 3.4 组合模式：真实系统不会只用一种

**组合一：星型事实表 + 一致性维度 + 代理键 + SCD Type 2（分层数仓的公共层）**

- 组合构成：事务事实表管事件，一致性维度管上下文，代理键隔离业务键变更，Type 2 保历史。
- 职责边界：事实表只负责"粒度唯一"，维度表只负责"上下文与历史"，度量口径不上移到报表层。
- 运维代价：代理键生成器成为链路依赖；每次维度属性变更要走一遍幂等 ETL 并回刷受影响的下游；一致性维度的改动是全链路改动，必须走评审。
- 适合规模：业务过程相对稳定、表数量在千级以内、有一支独立的公共层团队【经验】。

**组合二：同一业务过程用三类事实表并存（事务 + 周期快照 + 累计快照）**

- 组合构成：事务事实表回答"发生了什么"，周期快照回答"当时是多少"，累计快照回答"卡在哪一步"。
- 职责边界：三者粒度不同但共享同一组一致性维度与代理键，因此回答的是同一个业务过程的三个不同问题，而不是三份竞争的口径。
- 运维代价：同一份源数据要有三条加工链路与三份质量校验；任何一次源字段变更都要同时评估三条链路；语义层必须把"哪张表回答哪类问题"写清楚，否则同一个人会拿快照表去回答事件类问题。
- 适合规模：该业务过程是核心营收链路（交易、支付、履约），否则三条链路的维护成本不划算【经验】。

**组合三：星型（权威口径）+ OBT 宽表（派生消费层）**

- 组合构成：星型是唯一权威，OBT 由星型按需重建，供 Ad-hoc、特征工程与 Agent 取数使用。
- 职责边界：口径只在星型一侧定义，OBT 不新增任何口径，只做结构变换；因此 OBT 可以随时重建、随时废弃。
- 运维代价：要有一套"重建 OBT"的作业与新鲜度监控，否则两边会悄悄分叉；要防止有人把 OBT 当成权威去改数。
- 适合规模：湖仓上消费方超过三类、且查询形态无法事先枚举时【经验】。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因 | 修法 |
| --- | --- | --- | --- | --- |
| **巨型大宽表** | 一张事实表 500 列，列名里出现"客户姓名""商品类目" | 事实表不再是"度量 + 外键"，每一列都要跟着维度属性更新而回刷；粒度声明失效，同一指标两种结果 | 把 OBT 当成了起点而不是派生层：为了少 JOIN 直接在明细表上不断加列 | 事实表只装度量与外键；需要宽表就另建可重建的派生层（3.2.7） |
| **维度范式化过度** | "用户"被拆成 7 张表，一个报表要写 7 次 JOIN | 每次跨层次聚合都沿链条连接，延迟与维度层次深度成正比，且执行计划随查询变化 | 把 OLTP 的范式化纪律搬进 OLAP，误以为省存储是免费优化 | 维度尽量扁平，最多二级；层次的存储收益与 JOIN 成本要按 3.2.2 的推算显式比一次 |
| **维度属性混入事实表** | 事实表里出现"用户姓名""店铺名称"这类描述性文本 | 维度属性的历史（SCD）在事实表里无处存放，只能随事实行重复；一次改名要回刷全部历史分区 | 为了让报表少 JOIN，把维表属性直接物化在事实表 | 属性留在维度表；确实要宽表就把物化放进有重建路径的 OBT |
| **代理键与业务键混用** | 事实表的外键是订单号、手机号、UUID 等业务键 | 业务键一变更，历史关联断裂；SCD Type 2 无法表达"同一实体的两个版本"，因为版本只能靠代理键区分 | 早期直接从源系统同步，业务键是现成的，代理键要额外生成一套 | 统一用代理键做事实表外键；业务键降为维度表上的普通属性 |
| **SCD Type 滥用** | 所有维度都开 Type 2，包括"商品类目层级"这类低频属性 | 维表按版本膨胀，事实表被指向大量版本；每张下游报表都必须显式过滤 `is_current`，漏写即重复计数 | "保留历史总是对的"，且开 Type 2 在单表上不显贵，成本要到下游才暴露 | 按属性语义逐列选 SCD 策略：修正错误用 Type 1，需按历史时点还原才用 Type 2（3.2.9） |
| **事实表粒度混乱** | 一张事实表里有的行是"一笔订单"、有的是"一个订单行" | 同一指标两种结果，且无法从表结构判断；下游要么重复计数、要么漏计 | 需求一个个加，每来一个需求就往已有事实表加列或加行，没有人负责声明粒度 | 一行一事件 / 一行一周期 / 一行一生命周期三选一，粒度声明写进建模文档第一行 |
| **维度共享不当** | 两个业务过程共用一张维度，但各自需要的语义不同（下单店铺 vs 结算店铺） | drill-across 结果不可解释：同一个维度值在两边的含义不同 | 误把"维度名字相同"等同于"维度语义相同" | 按"通用维度 / 专属维度"分类；语义不同就退成角色扮演维度 |
| **忽略退化维度** | 事实表里没有 order_id，而它被抽成了一张只有一列的维度表 | 多一次无意义的 JOIN；订单号这类高基数键做维度表会让维表成员数等于事实行数 | 认为"维度建模就是所有东西都要有维度表" | 订单号、发票号这类没有属性的键直接作为退化维度留在事实表里 |

最危险的两条是**事实表粒度混乱**与**巨型大宽表**。前者在生产中的暴露方式很隐蔽：它不报错，只是让两个看板对同一个指标给出不同数，而争论双方都能拿出"自己的表算得没错"。要定位它，不能看 SQL，要看表结构——问"这张表的一行代表什么"，如果表的主人需要想一想才能回答，粒就已经混了。

后者（巨型大宽表）的危险在于它是**渐进**形成的：每一次加列都有一个当天成立的合理理由，所以没有任何一个时点需要做决策，直到某天维度属性要改名，才发现这张表同时是事实表、宽表和历史快照三种东西，没有一条路径能只改一处。

**SCD Type 滥用**的危险则在时间上错位：开 Type 2 的当天几乎是零成本（多一列有效期而已），代价全部延后到下游报表——而下游报表的作者并不知道上游开了 Type 2。这类反模式的修法只能从上游入手：把"哪些列开了 Type 2"变成一张可查询的清单，让下游能主动发现自己需要过滤。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 从 1 个业务过程到 10+ 个共享维度 | 星型（各自建维） | 跨过程对比要人工对齐口径，同一维度多套编码 | 星座 + 一致性维度 + 总线矩阵 | 历史表要回填新代理键；维度口径全量对齐一次；协商成本常态化 |
| 事实表从亿行到千亿行 | 事务表直查明细 | 每次状态类查询都扫全历史，代价随深度增长 | 事务表 + 周期快照（按需物化） | 多一条加工链路与质量校验；半可加度量的聚合规则要写进语义层 |
| 周期快照的实体基数从万级到亿级 | 每实体每日一行 | 行数按实体数 × 周期数增长，快照表超过它替代的事务表 | 只对发生变化的实体落行 + 变化日志表 | 下游必须改成"先取快照再回溯变化"，查询复杂度上移 |
| 维度属性从每季度一次变更到每天变化 | SCD Type 2 | 维表按天膨胀，每张下游报表都要显式过滤版本 | Type 1 + 独立的历史变更日志表 | 放弃按历史时点重述报表的能力；报告口径需重新约定 |
| 消费方从固定报表到不可预知的多方查询 | 星型直查 | JOIN 组合爆炸，每次都重新优化 | 星型（权威）+ OBT 派生层 | 多一套重建作业与新鲜度监控；要防止 OBT 被当成权威 |
| 消费方从人变成 Agent | 星型 + 裸表 | Agent 拿不到字段名，找不到 = 用不了 | 语义层（命名度量）+ 只读语义派生表 | 语义层成为取数链路单点，且口径权威从报表 Owner 转移到定义 Owner |

这张表里最容易被低估的一行是第三行：**周期快照的失效不是慢，是变大**。它的行数由实体数 × 周期数决定，而这两个数都只会向上走；等到发现它比事实表还大时，改造成本已经随历史长度累积完了。判断阈值不需要精确数字——定期把快照表与它派生自的事务表比一次行数，比值接近或超过 1 时，就该换。

### 3.7 自检清单

- [ ] 每张事实表都能用一句话回答"一行代表什么"（一次事件 / 一个周期状态 / 一个业务生命周期），并且这句话写在建模文档里而非口头约定？
- [ ] 事实表里是否出现过任何描述性文本列？出现即违反"事实只装度量 + 外键"，属于 3.5 的「维度属性混入事实表」？
- [ ] 同一张事实表里是否同时存在两种粒度的行？是则违反粒度纪律，必然出现同一指标两种结果。
- [ ] 事实表的所有外键是否为代理键？若某个外键是业务键，SCD Type 2 就无法表达版本。
- [ ] 每个维度属性的 SCD 策略（Type 1 / 2 / 3）是否逐列写明？未写明默认就是 Type 1，历史会被覆盖。
- [ ] 查询是否显式过滤了 `is_current = 'Y'`？漏写即重复计数，且不报错。
- [ ] 维度是否最多二级？超过二级的每一次拆分，是否用 3.2.2 的推算比对过它省下的存储与多出的 JOIN？
- [ ] 跨业务过程共享的维度，是否在一致性维度清单里被明确判定为"通用维度"？仅凭名字相同就共享，属于「维度共享不当」。
- [ ] 高基数的业务键（订单号、发票号）是否作为退化维度留在事实表，而不是抽成只有一列的维度表？
- [ ] 如果存在 OBT 宽表：它是否有从星型重建的作业、有新鲜度监控、且明确声明"不是权威口径"？
- [ ] 如果维度表上挂了 embedding 之类的派生列或派生表：它是否有增量重算作业、有 Owner、且不参与口径计算？
- [ ] 最近一次维度属性变更，是否能回答"哪些下游报表会变、谁去通知"？答不上来，说明影响面还没被建模。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 问题问事件，且事件不可撤销 | 事务事实表 + 星型 | 纯追加写入带来分区、压缩与可重述性 |
| 问题问时点状态，且要历史时点 | 周期快照 | 周期进粒度，状态读一行而非重放历史 |
| 问题问流程各步耗时 | 累计快照 | 步骤横向成列，耗时变列运算而非自连接 |
| 多过程要按同一维度对比 | 星座 + 一致性维度 | 共享代理键使钻取无需口径对齐 |
| 跨层次聚合高频、扫描便宜 | 星型 | 一层 JOIN 拿全上下文，执行计划不随组合变化 |
| 查询形态不可知、要极致扫描性能 | 星型 + OBT 派生层 | 把 JOIN 搬到写入侧，代价是可重建的回刷 |
| 历史必须按当时口径重述 | SCD Type 2 | 有效期写在维度行上，事实按当时的代理键落库 |
| 消费方是 Agent | 语义层 + 语义派生表 | 把"找到"与"算对"分成两条路径，主表权威不变 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**"一行代表什么"**——事实表的一行代表事件、周期还是生命周期，维度表的一行代表实体还是实体的一段有效期。粒度一旦定下，事实表类型、SCD 策略、要不要宽表都跟着定；反过来，任何"两个看板对不上数"的事故，最后几乎都能追到这一行话没有写明。
>
> 💡 **思考锚点**：把你手上的事实表逐张拿出来，能用一句话答出「一行代表什么」的有几张？答不上来的那些，落在 3.5 的「粒度混乱」还是「巨型大宽表」里？再挑一张周期快照表，把它与它派生自的事务表比一次行数——比值离 1 还有多远，决定你是否已经站到 3.6 那一行的换模点上。
