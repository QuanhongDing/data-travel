## 4. 工程实现

§ 3 把每个模式当作约束的产物来讲清了**该选哪个**；本节回答的是另一个问题：**选定之后，这件事按什么顺序做、做到哪一步算数、做完手上多了什么、已有的表和报表怎么办**。同一个模式，从零建和从存量改，第一步完全不同——从零建的第一步是"写下粒度声明再建表"，存量改造的第一步是"先把已有表的粒度声明补出来，一行结构都不改"。因此本节 4.1–4.3 是两种读者共用的顺序与判据（存量改造者请把每一步的"判据"当作补账的检查项读），4.4 专门写给存量改造者，4.5 给可套用的模板，4.6 给成本账单、4.7 给容灾与故障演练、4.8 给演进路线，4.9 是上线前逐条过的自检。

有一件事先定下来：本节所有判断都以**「一行代表什么」是否已写进明文**为分水岭。写进去了，后面的步骤都能用机器或抽查来验；没写进去，任何评审都只能靠"看的人是否正好熟悉这个业务"——那是不可复制的验收方式。

### 4.1 落地步骤

**Step 1：业务过程识别（【经验】每个业务域 3–10 天，随该域流程文档的完整度变化）**

与业务方逐条走"事件—时点—业务对象"三问，把该域发生的事写成一维的清单；存量改造时反向做一遍：拿已有事实表去对清单，看每张表回答的是哪一条过程。

- **产物**：业务过程清单（过程名 / 触发时点 / 业务对象 / 预期问答 / 归属数据域），以及总线矩阵的第一版（行 = 过程，列 = 候选一致性维度）。
- **判据**：抽 3 条过程，让写它的人**不看 SQL** 说出"这一行代表哪个事件"；再拿清单去对已有事实表，能否做到"每张事实表只对应一条过程"。出现"一张表对应两条过程"，说明清单还没收敛，此时不要进入下一步。
- **为什么必须这一步、且必须在最前**：总线矩阵的行从这里来，而第 3 步的维度清单是"行 × 列"逐格填出来的。若先建表后补清单，产出必然落到 § 3.5 的「事实表粒度混乱」那一行——一张表回答两个问题，而修它要回刷历史。

**Step 2：声明粒度（【经验】每条过程 0.5–2 天，随这张表被几方消费、以及"一行代表什么"是否已有现成的业务描述变化；是全流程里最便宜的一处返工点）**

- 写一句明文："一行代表什么"（一次事件 / 一个周期状态 / 一个业务生命周期）。
- 同一句要落到三处：建模文档第一行、**物理表的注释**（注释是唯一离表最近、又必须由人写的位置），以及语义层的粒度字段。前两处在这一步写完；第三处要等表上线、语义层挂得上这张表时才登记，由 Step 8 的发布后登记一并完成——不要因为它在上线之后就不算数。
- 标注每个度量的加性类型（可加 / 半可加 / 不可加），半可加的要写清不能跨哪个维度相加。
- 定下粒度与分区键的时间语义关系（事件时间还是处理时间）。

- **产物**：每张事实表一条粒度声明，含「一行代表什么 / 能加什么 / 不能加什么 / 分区列」四格。
- **判据**：抽一天实际 `count` 一次，与声明自洽吗；把该表上最常用的 3 条查询拿来对——有没有人在 `SUM` 一个半可加度量；表注释里那句话，与下游实际用法是否冲突。任一条对不上就不算完成。
- **为什么必须第二步**：粒度决定事实表类型（第 5 步）与 SCD 策略（第 6 步）——这是 § 3.1 立的第一条约束。它也是**唯一一处"改一句话就能省掉一次回刷"的位置**：此时改，代价是改文档；等 DDL 落了库、下游报表接上以后再改，代价变成重建表 + 回填 + 逐张改下游。

**Step 3：识别维度（【经验】每条过程 1–3 天，随候选名词的归并程度、以及需要跨过程比对语义的维度数变化）**

- 从"业务方怎么描述这件事"里抽名词，得到候选维度。
- 区分**通用维度**（两个以上业务过程共用）与**专属维度**；同一张维表在事实表里出现多个外键时，按角色扮演维度处理（下单店铺 / 结算店铺）。
- 高基数键（订单号、发票号一类）先按退化维度处理，不抽成只有一列的维度表。
- 把候选维度逐条落到总线矩阵的列上，看看有没有"矩阵上没有列、但业务问题里必须按它拆"的情况。
- 记录每个维度的成员基数与变更频率估计——这两个数在第 6 步被用来选 SCD 策略。

- **产物**：维度清单（【经验】通常 5–15 个，随该业务域里"业务方真的会拿它做筛选或分组的名词"数量变化；描述性文本字段多、还没做过名词归并的域会明显多于这个区间，做过一轮归并的域会落到区间下沿）+ **一致性维度清单**（哪些是全公司共用一份、代理键由谁生成）+ 每个维度的基数与变更频率。
- **判据**：对每个候选维度问两句——它在两个以上业务过程里出现吗；若出现，两处的语义**是否已被明确判定为同一语义**（而不是名字相同）。两句都"是"才进一致性清单。再拿 3 条真实业务问题验证：能否在不新增维度的前提下回答。
- **为什么必须这一步、且不能推迟到建表时**：一致性维度一旦被推迟，就等于"每个域先各建一份，以后再统一"——那时要做的已经是跨团队口径对齐工程，而不是建模动作。

**Step 4：识别度量（【经验】每条过程 1–3 天，随业务问题的条数、以及去重口径需要与几个下游谈定变化）**

- 把业务问题里问到的"多少 / 多久 / 多久一次"逐条写成候选度量。
- 给每个度量定**单位**与**去重口径**（去重计数的实体是谁：人、单、设备）。
- 只保留"一个业务含义一条度量"，同义的合并，不要并存两个只在拼写上不同的度量。

- **产物**：度量清单（【经验】每个事实表 3–10 个，随这张表回答的问题数变化；一条粒度声明对应一类问题，条目数远超区间上沿通常不是"度量多"，而是这张表混进了第二条业务过程的问答——那该回到 Step 2 拆表，而不是继续往清单里加行），含加性类型、单位、去重口径。
- **判据**：把清单交给一个**不看 SQL** 的分析师，让他用清单回答 3 个业务问题；每题都要能指出"用哪个度量、按哪个维度拆、能不能跨时间相加"。指不出即口径未定。再抽 2 个已存在指标，检查它是清单里的"一个度量"还是"两个度量的商"——后者常见，需要显式登记为派生指标。
- **为什么必须在事实表设计之前**：半可加的状态型度量天然指向周期快照（§ 3.2.5），不可加比率天然要留给语义层。若先建好事务表再补这些，结果往往是两张表并存、两份口径。

**Step 5：选择事实表类型（【经验】每条过程 0.5–1 天，随问题形态是否单一、以及同一条过程要并存几类表变化）**

- 按问题形态三选一：事件 → 事务事实表；时点状态 → 周期快照；有终点的流程 → 累计快照。
- 同一条业务过程允许并存多张，但必须写明"哪张回答哪类问题"。
- 与 § 3.3 的模式选择决策表逐项对一遍，把"为什么不选另外两类"写成一行记录。

- **产物**：事实表类型决定记录（含否决理由）。
- **判据**：拿该表将要承载的 5 个真实问题逐条问"这类表能不能直接回答"。出现"要重放全部历史才能答状态"或"要自连接才能算某步耗时"，就是类型选错。
- **为什么必须这一步、且不能与第 6 步合并**：类型决定了表能不能只追加——事务表纯追加，因此可分区、可重放重建；累计快照要 UPDATE，因此**不能**按时间分区。这是物理层差异，改类型等于重建表；把它压到维度表设计之后，代价是重画一遍维度关联。

**Step 6：设计维度表（【经验】每个维度 1–3 天，随属性列数与变更频率变化，SCD2 的幂等 ETL 是主要工作量）**

- 定代理键生成规则：统一由一处生成，或使用确定性规则（如 `HASH(business_key)` 一类，但要处理加盐、大小写与前后空格差异）；规则要能被回填作业复用。
- 逐列指定 SCD 策略（Type 1 / 2 / 3 / 4 / 6），不能"整表开 Type 2"；变化快、取值集合又有限的属性（活跃分档、标签一类）用 Type 4 处理——把这类属性的历史拆到独立的表（如微型维度），主维度只留当前值，避免主维度按天膨胀。
- 层次尽量拍平进同一张表，最多二级（拆得越多，跨层次聚合的 JOIN 越多）。
- 码表引用的列要注明来源码表，禁止在应用层自定义枚举。

- **产物**：维度表 DDL（代理键、业务键、有效期列、`is_current`、层次列、码表引用注释）+ 代理键生成规则说明。
- **判据**：把列清单铺开逐列问"这列的 SCD 策略是什么"，没有一列是"默认"；抽 3 个维度，用它重跑一遍**上一期报表的口径**，结果与旧版是否一致——不一致要么是改了历史（Type 1 干了 Type 2 的活），要么是漏过滤 `is_current`。
- **为什么必须在事实表之前**：事实表的外键列要按维度侧的代理键类型与生成规则定型。反过来做，就要给每个维度补一套"业务键 → 代理键"的转换，而这些转换规则必然分裂成多份。

**Step 7：设计事实表（【经验】每张 1–2 天，随外键个数与分区、回填口径的复杂度变化；不含回填本身的运行时间）**

- 列只放三类：度量、代理键外键、退化维度；再加分区列。
- 定分区与（可选的）分桶策略；分区列的时间语义要与粒度声明一致。
- 写清默认聚合方式（尤其是半可加度量的跨时间不可加）、增量与回填口径。
- DDL 注释里重复一遍粒度声明。

- **产物**：事实表 DDL + 分区 / 分桶声明 + 回填脚本 + 表注释中的粒度声明。
- **判据**：跑一次双向对账——从该表按一个季度聚合出的 KPI，与从上游明细直接算出的同一个 KPI，差异是否可解释；分区列与粒度声明的时间语义是否一致；外键是否全部指向代理键。
- **为什么必须留在评审之前**：这一步的产物是评审的**输入材料**。没有 DDL，评审会退化成表名与字段名的讨论会；有了 DDL，才能核对粒度、代理键、分区这几个不可逆项。

**Step 8：评审与发布（【经验】常规变更 1–3 天；涉及一致性维度或 SCD 策略变更时 1–2 周）**

- 设计评审：粒度、代理键、SCD、命名、分区五项逐条过。
- 影响面核对：下游有哪些（有血缘就查，没有就登记"待补"）。
- 建表门禁：命名规则、分层引用（汇总层不许直读 ODS）、码表引用、**与已有表查重**（按"度量 × 粒度 × 维度组合"查一遍）。
- 发布后登记 Owner、刷新策略与 SLA，并把粒度声明补登记到语义层的粒度字段上（Step 2 只在建模文档与表注释两处写过，第三处是这里补的）；上线第一周做一次口径回归。

- **产物**：评审记录（含否决意见与修正）、上线 DDL、Owner 与 SLA 登记、影响面清单。
- **判据**：评审能否对四件事给出"是 / 否"——粒度声明在表注释里吗；外键全是代理键吗；每列的 SCD 策略已声明吗；与已有表是否重复。四问任一为"否"，不发布。
- **为什么必须留在最后而不是"边建边评"**：评审的成本随变更的物理后果增长。DDL 之前评，代价是改文档；建表之后再评，代价是改表 + 回填 + 改下游。

**最常被跳过的是 Step 2。** 它不产出任何物理对象，在进度表上等于零——所以它总被并进"建表"里，由建表的人顺手在脑子里定一下。跳过它的第一个症状不会出现在发布当天：它出现在第一次"两个看板对不上数"的争论里，且争论双方都能证明自己的 SQL 没错。第二常被跳过的是 Step 8 的"与已有表查重"，症状延后一个季度量级【经验：随下游报表的发布与刷新节奏变化】：同一份口径出现两张等价表，此后每次改口径都要改两处，且一定会漏一处。

### 4.2 关键技术点

**代理键体系**

- **做法**：事实表外键只指向代理键；代理键由统一规则生成，跨事实表共用同一套生成逻辑；业务键一律降为维度表上的普通属性；代理键**无业务含义**（不要用日期拼业务键当代理键）。
- **机制**：因为事实行引用的是代理键，所以源系统换编码、合并实体、复用业务键时历史关联不断；同时 SCD Type 2 的多版本**只能**靠代理键区分——同一条业务键在维度表里有多个版本行，事实行必须指向其中确定的一行。
- **失效条件**：当代理键由多套规则分别生成（各域各自自增、`HASH` 加盐不同、大小写与首尾空格未归一）时，这条会坏在跨事实表钻取上：**症状**是同一天同一维度在两个事实表里指向不同代理键，drill-across 的结果偏小或重复，且不报错。**观测信号**：维度表与事实表的主键交集命中率，以及一致性维度在事实表里是否出现"一对多"。**档位**：【经验】。
- **档位说明**：具体用自增还是确定性哈希，取决于你的回填方式能否并行、是否需要跨环境比对；本节不给统一答案。

**SCD 策略选择**

- **做法**：逐列声明策略——修正错误用 Type 1（就地覆盖）；必须按历史时点还原用 Type 2（有效期 + `is_current`）；只需"新旧对照"且变化有界用 Type 3；变化频率高但取值集合有限的属性（活跃分档、标签、等级）用 Type 4，把这类属性的历史拆到独立的表（如微型维度）、主维度只留当前值；混合语义用 Type 6，但要把每列的语义写清。
- **机制**：因为 Type 2 把有效期写进了维度行，事实行按事件发生时的代理键落库即可还原当时口径；因为 Type 1 就地覆盖，维表行数不随变更增长、外键永远指向唯一一行。两者的收益方向相反，所以只能逐列选，不能整表选。
- **失效条件**：当维度属性变更频率升到"每天可能变"（活跃分档、标签、等级）时，「保留历史」会反转成「维表按天膨胀，且每张下游报表都必须显式过滤版本」——因为事实行的外键指向版本，版本数随时间累积。**症状**：某张报表的数值恰好是另一张的整数倍；**观测信号**：维表行数 ÷ 实体数（版本因子）的走势、`is_current = true` 的行数是否等于实体数。**档位**：【经验】——版本因子超过个位数时就该回头逐列重选：变更频繁但取值集合有限的那几列，正确的去处是把历史移出主维度（Type 4，或 § 3.6 提到的「Type 1 + 独立的历史变更日志表」），而不是继续留在 Type 2 里。
- **判据补充**：判断"要不要 Type 2"的问题不是"历史有没有用"，而是"业务方会不会拿去年的报表对今年的口径"。

**事实表粒度声明**

- **做法**：一句明文，三处出现——建模文档、表注释、语义层的粒度字段；前两处在 Step 2 随声明一起写，第三处是上线后的补登记（Step 8 发布后登记），不要因为那时表已经能用就漏掉。粒度变更视为破坏性变更，必须走评审与影响面检查。
- **机制**：因为下游的全部聚合正确性都建立在粒度之上，所以声明要放在"人随手能看到"的地方。放在文档里没用（没人打开），放在流程里也没用（新人不走流程）——表注释是唯一"离数据最近、且必须由建表人亲笔写"的位置。
- **失效条件**：当需求一个个加、且没有人负责声明粒度时，一张表会混入两种粒度的行。**症状**：`sum` 翻倍或漏算，不报错，两个看板对同一个指标给出不同的数。**观测信号**：粒度是怎么混进去的、以及怎么定位，见 [§ 3.5 反模式与失效分析](02-dimensional-modeling-section-3-sec3.md)；本节只补一个能被自动采集的信号——"行数 ÷ 业务单据数"这个比值突然偏离 1。**档位**：【经验】。
- **注意**：判据必须可执行。"团队对粒度达成一致"不是判据——正确做法是抽 3 张事实表、逐张问同一句话并记录响应时间。

**分区与分桶**

- **做法**：事实表按**事件时间**分区（周期取日或小时，按粒度定）；按高频 JOIN / 过滤键分桶；分区列的时间语义必须与粒度声明一致；同时定分区保留期，不要让分区无限增长。
- **机制**：因为列存引擎靠分区裁剪跳过不相干分区、靠分桶减少 JOIN 时的数据重分布，所以扫描量与延迟由"查询的时间窗"决定，而不是由表的总行数决定——这让延迟与成本可预测。
- **失效条件**：当分区列与常用过滤列不一致（按处理时间分区、查询却按事件时间过滤）时，裁剪失效、退化为全分区扫描；当单分区内文件数过多（频繁小批写入且没有合并）时，元数据开销会盖过扫描本身的收益。**症状**：加了分区后查询不快，或"扫描量远大于命中行数"。**观测信号**：每次查询命中的分区数与文件数、单分区平均文件大小。**档位**：【经验】。

**索引策略**

- **做法**：维度表用按列的统计结构（Bloom Filter、Zone Map 一类）加速等值过滤；事实表用列统计（Min/Max）、排序键或聚簇（Clustering）让相邻行按查询常用列有序；有更新语义的表（累计快照）要安排定期合并（compaction）。
- **机制**：因为列存引擎在执行前先读块的统计信息、跳过必然不匹配的块，所以把常用过滤列排到相邻位置，等于让"跳过"这个动作真正生效。
- **失效条件**：当聚簇键与真实查询的过滤列不一致、或写入是乱序（迟到数据持续追加、更新留下墓碑）时，块的统计范围互相重叠，跳过率下降。**症状**：加了聚类之后查询没有变快，甚至写变慢。**观测信号**：块级统计的实际跳过比例、单列在块内的取值范围重叠度、未合并文件数。**档位**：【经验】。

**命名规范**

- **做法**：表名 = 分层前缀 + 类型前缀 + 域 + 粒度或周期（`fact_` / `dim_` 打头）；退化维度直接进事实表、不另建表；度量名带单位或周期（`order_amount_rmb`、`order_count_30d`）；规范写成静态检查，在提交建表时**拒绝**不合规的名字，而不是写进文档等评审。
- **机制**：因为命名是"不打开文档也能猜对"的唯一信息通道，所以把类型与粒度编码进名字，能让人和工具同时少读一份文档；而只有当不合规**建不出来**时，规范才不会随时间漂移。
- **失效条件**：当规范只存在于文档而没有静态检查时，新表偏离规范就只是时间问题——尤其来自新人与外部团队的建表【经验：偏离通常在一个季度到半年内出现，随新人加入与外部团队接入的频率变化】。**症状**：同一分层出现三种前缀，同名不同义的掩码字段并存。**观测信号**：建表提交的静态检查通过率、偏离命名规则的存量表占比（这两个数只要定期统计，拐点看得见）。**档位**：【经验】。

**血缘与元数据**

- **做法**：每张事实 / 维度表登记 Owner（具体到人）、上下游依赖、刷新策略与 SLA、粒度声明、SCD 策略；血缘以**自动解析作业 SQL** 为主，人工只补业务含义与校正；记录血缘的最后更新时间。
- **机制**：因为"改表前先查影响面"这个动作只有在血缘是自动采集且新鲜时才可靠，所以人工登记的血缘能用的窗口很短【经验：一个季度到半年就会过期，随该域表的变更频率与有没有人定期维护变化】。**过期的血缘比没有血缘更危险**——它会给出错误的信心。判定方法很简单：问"如果这份血缘停更一个月，谁会先发现"。
- **失效条件**：当变更没有挂在发布门禁上时，血缘会退化成一张展示页——没人主动看，改动照样引发下游失败。**症状**：下游第二天任务失败才发现上游改过字段。**观测信号**：血缘的最后更新时间分布、自动解析覆盖率、变更记录里有没有"跑过影响面查询"的痕迹。**档位**：【经验】。
- **与 § 5 的边界**：AI 元数据补全属于 § 5 的 L2 能力，且前置条件是"已经有人负责"；在没有 Owner 的元数据上做自动补全，只会更快地生产错的元数据。

**度量命名与单位**

- **做法**：同一指标只保留一个度量名，同义的合并而不是并存；度量名里带单位（`_rmb`、`_ms`）或周期（`_30d`）；去重计数的实体写进注释；半可加度量的默认聚合方式在语义层显式声明。
- **机制**：因为下游对度量的理解来自名字与注释，而不是来自上游 SQL，所以名字里缺单位与周期时，下游只能靠猜或去读上游，而这两条路都会产生第二份口径。
- **失效条件**：当同一指标在多个域各自命名（`pay_amt` / `pay_amount` / `gmv` 并存）时，跨域对比要人工映射。**症状**：集团报表里同一个指标存在多个字段，分析师需要一份"对照表"才能取数。**观测信号**：语义层里按定义文本聚类出的同义度量数量、每季度执行的合并次数。**档位**：【经验】。

### 4.3 工具链与平台

选型判据都写成"在什么约束下选它"，而不是"它更好"。同一类里出现多个候选是正常的——它们在**不同的约束下**分别是最优解。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| **数据建模** | ER/Studio、PowerDesigner、dbdiagram.io、dbt | 需要与 DBA / 源系统反向工程、有专人维护模型仓库的选 ER/Studio 或 PowerDesigner；只要一张随时可分享的星型图选 dbdiagram.io；模型要进代码仓库、与转换作业同一份版本的选 dbt | 重型建模工具与代码仓库分离时，图与 DDL 会各自演化成两个版本，"图是对的但库里不是" |
| **ETL/ELT** | dbt、Airflow、DataWorks、Informatica | 转换逻辑用 SQL 表达、且希望粒度声明随模型进版本控制的选 dbt；只需要编排与依赖管理的补 Airflow；已在阿里云上、要与调度与治理一体的选 DataWorks；有强合规审计与图形化开发要求、且愿意为许可付费的选 Informatica | 用编排工具承载转换逻辑，会让"粒度声明"退化成注释；只买商业套件而不统一口径，只是把分散的 SQL 换成图形化配置 |
| **Lakehouse** | Databricks、Snowflake、Apache Iceberg、Delta Lake | 存量已在对象存储、且未来会出现第二种计算引擎的，选开放表格式（Iceberg / Delta）再选引擎；以分析单引擎为主、团队没有内核专家的，选托管形态（Databricks / Snowflake） | 用专有格式承载需要长期共存的数据，未来换引擎时要复制或重写全部数据 |
| **查询引擎** | StarRocks、Doris、ClickHouse、Trino | 高并发点查与实时看板为主选 StarRocks / Doris；单表极宽、聚合扫描为主选 ClickHouse；跨多个异构源联邦查询选 Trino | 用单一引擎覆盖所有形态（点查 + 联邦 + 大扫描），总有一类场景要迁就它 |
| **BI 工具** | Tableau、Power BI、Superset、FineBI | 已有 Microsoft 生态、要自助与办公集成选 Power BI；设计精度与可视化深度优先选 Tableau；要开源可定制选 Superset；国内生态与本地服务优先选 FineBI | BI 直接连裸表做自助，等于把口径定义权下放给每个报表作者——自助会加速口径分裂 |
| **元数据/血缘** | DataHub、Apache Atlas、OpenMetadata、阿里 DataWorks | 需要开源可扩展、且字段级血缘是核心诉求的选 DataHub 或 OpenMetadata；已在 Hadoop 生态内、以合规审计为主选 Atlas；已在阿里云上、要与调度血缘一体的选 DataWorks | 目录里没有 Owner 与粒度声明时，它只是一个搜索框：能搜到表，但不知道能不能用、归谁管 |
| **AI 辅助（2024+）** | Databricks Assistant、Snowflake Cortex、dbt + LLM、Cursor | 只有"模型已经想清楚、只差落 DDL"这一格适合引入；且必须配一道人工评审门禁。成熟度分级与判据见 [§ 5](02-dimensional-modeling-section-5-ai.md)，不要把 L2/L3 的能力排进关键路径 | 让生成结果直接进关键路径：语法错误会被解析器拦住，粒度错、SCD 选错这类语义错误不会——它们只在下游对不上数时暴露 |
| **自动化建模** | WhereScape、Dataform、Coalesce | 当粒度声明、一致性维度划分已完成并登记为机器可读资产后，用它们把"表达"自动化；若业务过程与粒度还在反复调整，先不要引入 | 在决策还没定的时候引入自动化，等于把未定的决策**批量固化**：改一次决策要改一批配置 |

表里最容易被误选的是**最后一类（自动化建模）**。它的销售话术是"少写 SQL、少雇人"，听起来与前面几类不冲突，于是常被放在项目早期引入。后果很具体：这类工具**假设**你已经知道粒度与一致性维度是什么，而这两件事恰恰是 Step 2 与 Step 3 的产出——顺序颠倒时，你得到的不是"少写代码"，而是"用配置把一个错误的粒度写进了几十张表"，而回退这些配置比回退 SQL 更贵，因为它没有版本化的 DDL 可读。

同一个误选还有第二种形态：把 **BI 工具**放在建模之前上线。工具本身没问题，问题是它把"口径定义"这件事交给了每一个报表作者；等口径分裂暴露出来时，改造成本已经落在几十张已发布的报表上。

### 4.4 存量迁移

存量改造与从零建立的差别在于：你 **不是** 在空地上画星型，而是在一堆已经"能用但说不清"的表上补账。这一节按四件事写：先做什么、历史资产怎么分类、双轨怎么维持、什么时候可以退出。

**① 先做只读登记，一行结构都不要改。** 第一步不是建新模型，是给存量表补元数据：粒度声明、Owner、刷新策略、每列的 SCD 策略、码表引用。这些全部写在元数据与表注释里，**不碰数据、不碰 DDL**，因此完全可回退——发现写错了，改一行说明即可。

- 顺序按"下游引用数"从高到低：先补被 3 张以上下游引用的表，它们的错误代价最大。
- **判据**：抽 10 张已登记的表，元数据里能否读到粒度声明与 Owner；以及过一周有没有人主动来纠正"声明与实现不符"——有人来纠错，说明这份声明真的被读了；没人来，说明又变成了一份没人看的文档。

**② 历史资产分三类，禁止全量返工。** 全量返工是存量改造里最常见、也最贵的一步错棋（§ 6 里"先让各 BU 自己建、事后统一"的教训属于同一类）。正确做法是先分类，分类依据必须可查（下游数量、最近一次被查询的时间）：

- **A 类｜活跃且被引用**：分阶段治理——先补声明（第①步已做），再补代理键与 SCD，**最后**才动物理结构。每一阶段之间都要有一次下游确认。
- **B 类｜活跃但没人引用**：打标"待退役"，冻结新增下游，数据不动。多数存量库里这类表占比不小，它们的存在会持续误导"资产规模"的判断【经验：这类表通常要等到有人做一次独立的下游统计才会被发现】。
- **C 类｜已停更**：冻结写权限、保留只读、登记退役责任人。**判据**：每张表都落在三类之一，且分类依据能在元数据里查到；说不出依据的表，就是还没分类。

**③ 双轨：新需求只在新模型建，旧链路保留只读。** 双轨不是"两套并行开发"，而是"只在一个方向上前进"——新需求一律进新模型，旧表只接受必要的数据修复。两栈之间用一张**业务键 ↔ 代理键映射**打通（视图或映射表），让旧报表能按老口径读到新数据。

- 双轨期最该做的动作是**对账**：行数对账（同一天、同一实体数）、聚合对账（同一定义的核心指标）、抽样明细对账（抽若干单据逐字段比）。三者都过才算对完一轮。
- 双轨期的长度由**旧链路查询量的下降速度**决定，而不是由项目计划决定【经验：3–12 个月区间，取决于旧报表的退役速度与新旧口径的差异面；差异面大则更慢】。存储与计算在双轨期至少要有一份冗余【推算：同一份数据在新旧两栈各存一份，存储与写入成本约翻一倍；若旧栈只保留最近 N 天热数据，则冗余倍数为 N 占全量历史的比例】。

**④ 什么信号说明可以退出双轨。** 四条同时满足才退，任一条不满足就继续维持：

1. 连续两个完整结算周期，三级对账零差异（不只是"没人在群里喊错"）；
2. 旧栈的查询量降到可忽略（能列出具体数字与统计口径，而不是"感觉没人用了"）；
3. 没有新作业落在旧栈上——这条要看调度系统的实际依赖图，不看谁的口头承诺；
4. 旧链路的 Owner 已提交书面的退役清单，且清单上的每一张表都有人签字。

**最容易出错的是按日期下线**：计划里写着"三个月后切换"，到点就关掉旧栈。此时还剩几张没人记得的报表、几个没人知道的定时脚本挂在旧表上，它们不会立刻报错——它们会在某个季度的口径核对里变成"这个数怎么和上季度对不上"。

两个与之配套的判断：老表若**混了粒度**，不要在原地改，建新表 + 视图兼容；老维度若是 Type 1 就地覆盖过，历史已经丢了，不要试图"从备份还原"，改为从这一刻起用变更日志重新积累。一致性维度的存量整合建议按"成员基数小、变更频率低"的先做（日期、地域、类目），高基数维度（用户、商品）放后面——它们的合并冲突最多、收益兑现最慢。

### 4.5 模板 / 示例

**模板一：粒度声明卡**（每条事实表一张，随 Step 2 写进建模文档与表注释；同一句在上线后补登记到语义层）

```markdown
| 项 | 内容 |
| --- | --- |
| 事实表 | fact_order |
| 一行代表什么 | 一次下单创建事件（不可撤销；取消不删除原行） |
| 时间语义 | 事件时间（下单发生时刻），分区列 dt = 事件日期 |
| 可加度量 | order_amount_rmb、item_count、discount_rmb |
| 半可加 / 不可加度量 | 无（若有余额类字段必须逐条列出，并写明不能跨哪个维度相加） |
| 退化维度 | order_id（高基数、无属性，不建维度表） |
| 关联一致性维度 | dim_user、dim_product、dim_channel、dim_date |
| 事实表类型 | 事务事实表（不选周期快照：问题问的是事件，不是时点状态） |
| 粒度变更历史 | 无（有变更时必须记录日期、原因、影响的下游） |
```

**怎么用**：填"一行代表什么"这一格时不要写"订单数据"这类类别词，要写成"一次 + 事件名"；"半可加 / 不可加度量"这一格宁可多写不可空着——空着就等于宣称这张表所有度量都能跨时间求和。其中最不能照抄的是"事实表类型"那一格的**理由**：它必须来自你自己的业务问题，抄别人的理由等于把别人的约束当成自己的。

**模板二：星型模型 DDL（含 SCD Type 2 维度）**

```sql
-- 维度表：用户（含 SCD Type 2）
CREATE TABLE dim_user (
    user_key        BIGINT PRIMARY KEY,      -- 代理键（无业务含义，统一生成）
    user_id         VARCHAR(64),             -- 业务键（降为普通属性）
    user_name       VARCHAR(128),
    city            VARCHAR(64),
    province        VARCHAR(64),
    country         VARCHAR(64),
    effective_date  DATE,                    -- 版本生效日
    expiry_date     DATE,                    -- 版本失效日（9999-12-31 表示当前）
    is_current      BOOLEAN,                 -- 当前版本标记；下游必须显式过滤 is_current = true（本文件统一用布尔，不用 'Y' / 1）
    -- 逐列 SCD 策略：user_name = Type 1（改名不保历史）
    --                city / province / country = Type 2（需要按历史时点归因）
);

-- 维度表：日期（带层次，成员基数小且稳定，通常是最先统一的一张维度）
CREATE TABLE dim_date (
    date_key      INT PRIMARY KEY,            -- YYYYMMDD
    date_value    DATE,
    year          INT,
    quarter       INT,
    month         INT,
    day           INT,
    week_of_year  INT,
    is_weekend    BOOLEAN
);

-- 事实表：订单（事务事实）
CREATE TABLE fact_order (
    order_key        BIGINT PRIMARY KEY,
    user_key         BIGINT REFERENCES dim_user(user_key),
    product_key      BIGINT REFERENCES dim_product(product_key),
    channel_key      BIGINT REFERENCES dim_channel(channel_key),
    order_date_key   INT REFERENCES dim_date(date_key),
    -- 度量（名字带单位或周期）
    order_amount_rmb DECIMAL(18,2),
    item_count       INT,
    discount_rmb     DECIMAL(18,2),
    -- 退化维度：高基数、无属性，不建维度表
    order_id         VARCHAR(64),
    -- V2：累计快照表需要的"当前步骤"不放这里，另建 fact_order_fulfillment
    created_at       TIMESTAMP
) PARTITIONED BY (dt DATE);
-- 粒度声明：一行 = 一次下单创建事件；dt = 事件日期
```

**怎么用**：`user_key` 的生成规则必须写进代理键生成器文档并全库共用——这一格不能照抄（自增还是确定性哈希取决于你的回填方式）；`effective_date` / `expiry_date` / `is_current` 三列是一个整体，只留其中一列就等于没有版本化；`product_key` / `channel_key` 指向的维度表若还没建，先建它们再建事实表（§ 4.1 Step 6 在 Step 7 之前）。

**模板三：SCD Type 2 的幂等合并（骨架，方言自调）**

```sql
-- ① 关闭发生变化的旧版本行
UPDATE dim_user
SET    expiry_date = :batch_date - 1, is_current = false
WHERE  is_current = true
  AND  user_id IN (SELECT user_id FROM stg_user_changed);

-- ② 插入新版本行（代理键由生成器给出，不要复用业务键）
INSERT INTO dim_user (user_key, user_id, user_name, city, province, country,
                      effective_date, expiry_date, is_current)
SELECT next_key(), s.user_id, s.user_name, s.city, s.province, s.country,
       :batch_date, DATE '9999-12-31', true
FROM   stg_user_changed s;

-- ③ 幂等校验：同一天重跑不产生第二份版本（前提见下方「怎么用」：stg_user_changed 每次重算，重跑时为空）
--    期望：SELECT user_id, effective_date, count(*) FROM dim_user
--          GROUP BY 1,2 HAVING count(*) > 1 返回空
```

**怎么用**：把 `stg_user_changed` 换成"只含发生变化的实体"的暂存表——如果它装的是全量快照，第②步会每天给人人都插一版。`next_key()` 换成本项目的代理键生成方式（自增序列或确定性哈希）。第③步的校验语句必须进每日质量校验，**不能**只在迁移当天手工跑一遍。

这段骨架的幂等**有前提，必须写进作业说明**：`stg_user_changed` 要在每次运行时按「源系统当前值 vs 维度表当前版本」重新比较得出，因此同一天重跑时它为**空**——第①步无行可关、第②步无行可插，③才可能返回空。若它其实是普通的变更增量（CDC delta，重跑仍非空），同批次重跑的后果是可推的：第①步会把上一轮刚插入的那条当前版本**再关一次**，写出 `expiry_date = batch_date - 1 < effective_date = batch_date` 的非法版本行，第②步再插一版，于是真的出现两份同 `effective_date` 的版本行，③返回非空。两种防法任选一种：把取数改成比较式（推荐，重跑天然为空），或在第①步加批次去重守卫（如 `AND effective_date <> :batch_date`，排除本批次已插入的行）。③在这里的作用正是**探测这件事有没有发生**——它一旦返回非空，先查 stg 表的取数方式，再查数据。

**模板四：建表评审清单（PR 模板片段）**

```markdown
- [ ] 粒度声明：一行代表什么？写在表注释里了吗？
- [ ] 代理键：所有外键都是代理键吗？生成规则是全局唯一那一套吗？
- [ ] SCD：逐列的 SCD 策略写明了吗？下游知道要过滤 is_current 吗？
- [ ] 命名：表名与度量名过静态检查了吗？
- [ ] 查重：按"度量 × 粒度 × 维度组合"查过已有表了吗？结果贴出来。
- [ ] 影响面：下游清单从哪来（血缘查询 / 人工登记）？登记了吗？
- [ ] Owner 与 SLA：具体到人了吗？
```

**怎么用**：这份清单的价值全在"结果贴出来"这半句——没有产物的勾选等于没评。若你的仓库支持 PR 模板，把它放在模板里；若不支持，放在工单的必填字段里，缺项不予受理。

### 4.6 成本：这套东西的账单

维度建模的账不按数据量结，按**口径对齐的会议数**和**回刷的落地面**结。三项里与本主题真正相关的是人力、回刷与存储形态——云账单的主体（存储 + 扫描）反而是被粒度声明间接决定的：

- **人力（口径对齐）**：一致性维度是全流程最贵的动作，成本随**参与团队数 × 候选维度数**增长，与数据量无关【推算：跨域维度合并的工时 ≈ 参与团队数 × 单轮评审时长 × 轮数；§4.4 已指出高基数维度（用户、商品）合并冲突最多、收益兑现最慢，是这一项的大头】。贵在这里的机制是——它买的是**组织一致性**，不是算力。
- **回刷（backfill）**：粒度或 SCD 策略变更后，落地面 ≈ **受影响下游报表数 × 逐张回归工时 + 历史分区数 × 单分区重跑时长**【推算：回刷成本 = 重算成本 + 下游回归成本；前者随保留的历史深度线性增长，后者随下游报表数与维度组合数增长】。Step 2 之所以是全流程最便宜的返工点，正因为此时式中两项还都是零。
- **存储与计算**：星型 / 雪花只是存储与 JOIN 的换算——范式化省下的是维度表的字节，多出的是跨层聚合的 JOIN【经验：维度表通常远小于事实表，范式化省下的存储一般在个位数百分比量级；事实表体积 ≈ 日增行数 × 行宽 × 保留天数，它才是云账单主体】。双轨期的存储冗余倍率已在 §4.4③ 给出。

单位成本口径、FinOps 归因这类通用账法见 [Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节只标这个主题把成本放在哪一格。

### 4.7 容灾与故障演练

维度模型是**逻辑产物**，它的「可用性」由承载引擎的副本与多活保证——那是通用题（[Ch12 §07](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)）。本主题真正的失效形态是**口径不可复现**：库还在、表还查得动，但两个看板对不上数，且谁都能证明自己没错。它只能用「抽样对账 + 审计」暴露，不适用跨地域切换演练。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 粒度被污染（一张表混入第二条业务过程） | 该表全部聚合翻倍或漏算 | 冻结新增粒度，按业务键拆表重建 | 抽一天 `count` 与粒度声明的比值是否偏离 1（§4.2 已给这个信号） | RTO【经验：天级，随数据量与回填并行度变】 |
| 代理键规则分裂（各域各自生成） | 跨事实表 drill-across 偏小或重复 | 回退到统一生成器 + 重写映射表 | 同一实体在两个事实表取代理键比对 | RPO【经验：以一次全量重算对齐，天级】 |
| 维表版本膨胀（高频属性开了 Type 2） | 某些报表数值恰为另一张的整数倍 | 逐列回退 Type 1 + 历史移出主维度 | 监控「维表行数 ÷ 实体数」与 `is_current = true` 行数是否等于实体数 | RTO【经验：随维度重刷范围变】 |
| 血缘过期（改上游未查影响面） | 下游第二天任务失败才发现 | 变更挂发布门禁 | 问「这份血缘停更一个月，谁先发现」 | RPO【经验：配合每日巡检，天级】 |

与 §4.2 的分工：那里讲每个技术点的**失效条件**，这里只把它们摆成一张「演练表」——暴露手段是抽样对账（行数 / 聚合 / 明细三级，判据见 §4.4③），不是故障注入工具；混沌演练的通用方法见 [Ch12 §06](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)。

### 4.8 演进路线：0 → 1 → 100

这个主题每一级的坎都踩在**同一处明文**上——「一行代表什么」写没写进表注释，只是每级失守的代价不同：

- **0 → 1（最小可用）**：先建一张事实表 + 粒度声明进表注释，工作流只到 Step 2 与 Step 5，不建总线矩阵、不做一致性维度。**便宜在**跳过跨域对齐；**先坏的是粒度的明文**——它不报错，只是几个月后第一次「两个看板对不上数」时，才发现声明要么没写、要么与分区的时间语义矛盾。
- **1 → 100（规模化）**：补总线矩阵、一致性维度清单与统一代理键生成器，血缘改为自动解析。**变贵的是人力**——跨域维度合并是会议与对齐成本，随团队数增长；**先坏的是高基数维度的合并**：用户、商品这类维度冲突最多、收益兑现最慢（§1.4 的「大数据阶段核心矛盾是一致性 vs 扩展性」，落到这里就是一致性先让步）。
- **100 →（下一道坎）**：粒度声明进语义层、SCD 逐列策略可回溯、口径变更走影响面门禁。**变贵的是回刷能力**——当粒度改动的落地面从一个作业变成一次跨团队协商，§4.6 那笔账里最难用钱补回来的就是这一项；§1.4 的「AI 原生阶段核心矛盾是结构化 vs 语义化」也落在这里——维度被嵌入后，口径错位比维度建模时代更难被发现。

压测与容量规划、灰度回滚这类面向服务的通用动作见 [Ch12 §04](../../12-architecture/04-capacity-planning/04-capacity-planning.md) 与 [Ch12 §09](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)；本节只说这个主题最早的坎落在哪一步。

### 4.9 自检清单

- [ ] 抽样 3 张事实表，粒度声明是否写在**表注释**里，且与分区列的时间语义一致？
- [ ] 拿一张事实表，随便挑一个半可加度量：它的"不能跨哪个维度相加"写在哪里？找得到吗？
- [ ] 把一张事实表的列清单按类型过一遍：文本型列里有几列是描述性属性（用户姓名、店铺名称一类）？数出来不是 0，就违反"事实表只装度量 + 外键"。
- [ ] 事实表的所有外键是否都是代理键？有没有哪个外键直接是订单号、手机号这类业务键？
- [ ] 代理键的生成规则是否**只有一套**？拿两个事实表，验证同一实体的代理键是否相同。
- [ ] 每个维度属性列的 SCD 策略是否逐列写明？有没有整表开 Type 2 的情况？
- [ ] 抽查一张下游报表的 SQL，是否显式过滤了 `is_current = true`（本文件统一用布尔值表达当前版本，见模板二的 DDL；若你的库用 `'Y'` / `1` 之类的字符或数值约定，全库必须只用一种，并在表注释里写明）？漏写会重复计数，且不报错。
- [ ] 数一数维度清单里"层次列全平铺进同一张表"的维度有几张、被拆成多张表的有几张？每一处拆分，把省下的存储与多出的 JOIN 各算一个数贴进评审记录——算不出数字的那几处，就是没有比对过。
- [ ] 把出现在两张以上事实表里的维度逐个对到一致性维度清单上，看判定依据那一栏写的是"两处语义已比对为同一语义"还是只有名字？依据栏只写得出名字的，就是仅凭名字共享。
- [ ] 数一数维表里"只有代理键 + 一列业务键、再无其它属性列"的表有几张？每出现一张，就有一个高基数业务键（订单号、发票号一类）本该留在事实表、却被抽成了维度表。
- [ ] 翻最近一次口径变更的记录：下游影响面清单里有没有写具体报表名、有没有写"谁去通知"的人名？两项都缺，说明影响面还没有被建模（登记动作见 § 4.1 Step 8）。
- [ ] 存量表里，能否随手点开一张就知道它属于 A / B / C 哪一类，依据是什么？

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **§ 4.1 的 Step 2「声明粒度」**——它是全流程里唯一一处"改一句话就能省掉一次回刷"的位置，也是唯一一处**跳过之后不会立刻报错**的地方。粒度一旦写进明文（表注释 + 建模文档 + 语义层），第 5 步的表类型、第 6 步的 SCD 策略、第 7 步的分区都能被逐条核对；反过来，粒度留在某人的记忆里时，代理键、SCD、命名、血缘这些技术点做得再扎实，也只是把错误的结构做得更规范——两个看板对不上数的那一天，谁都证明不了自己错。
>
> 💡 **思考锚点**：你手上的事实表里，粒度只写在某人记忆或口头约定、而没落进表注释 / 建模文档 / 语义层的有几张，每张在按 § 4.1 Step 2 补声明之前又挂着几张下游报表——这些下游报表加起来，是不是就是粒度一天不落明文时、你可能要陪跑回刷的那个面？
