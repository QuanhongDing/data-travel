## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把「取决于场景的结论」伪装成「绝对结论」。`灵活度：Data Vault 5 分、维度建模 3 分` 这样的格子回答了「这个方案好不好」，而选型要回答的是「在我的约束下它会怎样」。同一个维度在不同规模下权重相反：二十人团队的「灵活度」是加分项（改起来快），两百人团队的「灵活度」是负债（口径分叉没人负责，见 [§3.5](02-dimensional-modeling-section-3-sec3.md)）。分数把这两件事压成了一个数。

同一维度在不同方案之间往往不是「分数差」，而是两个不同机制的函数。拿「查询性能」来说：星型的延迟由**引用维度数**决定（JOIN 数固定、维表小可广播，见 [§3.2.1](02-dimensional-modeling-section-3-sec3.md)），OBT 的延迟由**扫描量**决定（零 JOIN，但要读宽列，见 [§3.2.7](02-dimensional-modeling-section-3-sec3.md)）。谁更快，取决于这次查询用了几列、事实表多大——这是查询形态的函数，不是方案的属性。把它写成 5 分与 4 分，等于把一个变量藏进了一个常量。

更关键的错位在于：这些候选不在同一层。ER(3NF)、Data Vault、Anchor 是**集成与演进**的解法（回答「源持续新增、口径未定时结构怎么长」），星型 / 雪花 / 星座 / OBT 是**查询结构**的解法（回答「给定访问模式，一条查询要连几张表」），语义层与语义化维度是**消费接口**的解法（回答「消费方能不能找到、算对」）。三者可以同时存在：一个团队完全可以在 Data Vault 集成层之上建星型汇总层，再在上面挂语义层。把三个层级的东西放进一张打分表做排名，得到的是一张不可比的表。

打分表还有第三个问题：它暗示这些方案是**互斥选项**，只能选一个。真实系统的形态是叠加——集成层选一个方案、汇总层选一个方案、消费接口再选一个方案，三者互不冲突（7.6 的四条组合就是这种叠加）。一旦接受「可以叠加」，比较的对象就从「哪个方案总分高」变成「每一层各自该选什么」，这也正是本节把候选分成三族的原因。

所以本节的组织方式是：先立判据，再按**机制**分组比较，最后给决策。本主题的判据不能是「好 / 快 / 灵活」这类形容词，必须是能回答「在我的约束下会怎样」的问题。下表六条的排列顺序本身就是一条隐含结论：前两条决定物理结构，中间两条决定变更与历史的处理方式，后两条决定要不要加一层与迁移代价——**顺序不能颠倒**，因为在结构没定之前讨论消费接口是没有对象的。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 粒度声明能力 | 这张表的一行代表一次事件、一个周期状态，还是一段生命周期 | 粒度定下后度量才能直接 SUM；粒度混了会出现「同一指标两种结果」且不报错（[§3.5](02-dimensional-modeling-section-3-sec3.md)） |
| 查询的 JOIN 层数 | 最常用的那批查询要跨几层 | 它是延迟里唯一随查询形态变化的项，也是星型与雪花、DV 与 Anchor 的真正分野 |
| 变更传导范围 | 加一个源、加一个属性、改一次口径，各要动几张表几条链路 | 决定的是三年后的维护成本，而不是上线当天的成本 |
| 历史可重述性 | 要不要按当时口径重述去年的报表 | 决定 SCD 策略，进而决定维表是否按版本膨胀、下游是否必须显式过滤版本 |
| 消费方形态 | 人写 SQL、BI 建模，还是 Agent 生成查询 | 决定要不要语义层与检索派生表；与物理结构选择正交 |
| 迁移与生态成本 | 离开它要重写多少查询、重建多少作业 | 方法论本身不绑定产品，但落地它的建模工具、语义层与表格式会绑定 |

### 7.2 候选方案全景

下表覆盖本章讨论的全部候选。**评分列被替换为「核心机制」列**——机制相同则分数必然相同，机制不同则分数无意义。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 星型模型 | 面向查询的默认结构 | 维度层次拍平成一张表，任意维度组合只一层 JOIN | Kimball 方法论；阿里 OneData 公共层（见 [§6](02-dimensional-modeling-section-6-sec6.md)） | 方法论公开，工具各异 |
| 雪花模型 | 维度的层次被独立维护 | 层次描述去重存一份，代价是沿层次链多 JOIN | 维表成员基数小的场景；TPC-DS 式的带层次 schema | 同上 |
| 星座模型 | 多业务过程共享同一坐标系 | 共享一致性维度与代理键，drill-across 无需物理合并事实表 | 中大型数仓汇总层 | 同上 |
| ER 建模（3NF） | 面向集成与写入一致 | 按函数依赖消除冗余，结构不随查询形态变化 | Inmon 企业级数仓路线（《Building the Data Warehouse》，1992 年首版）【公开，1992】 | 方法论公开 |
| Data Vault | 面向「源持续新增」的集成结构 | Hub（实体）/ Link（关系）/ Sat（属性）三类表分离，新增对象不动既有对象 | 监管行业与多源集成层 | 方法论公开；Data Vault 2.0 由 Linstedt 与 Olschimke 在 2015 年系统化【公开，2015】 |
| Anchor Modeling | 6NF 方向的极细粒度结构 | 一个属性一张表，历史天然表现为同一属性追加行 | 属性演化频繁、结构需长期存续的系统 | 方法论公开（方法论站点与示例模型可核验，以站点当前版本为准）【公开，可自行核验】 |
| OBT 宽表 | 面向不可预知查询形态的派生层 | 把 JOIN 从查询时搬到写入时，查询只剩列裁剪 + 聚合 | 湖仓 Ad-hoc、特征工程 | 工具无关 |
| 语义层 | 面向「口径唯一」的消费接口 | 度量定义从报表 SQL 搬到一处声明，BI / API / Agent 共用 | dbt Semantic Layer（含 MetricFlow）、Cube.js | 开源核心 + 商业托管 |
| 语义化维度 | 面向「能找到」的检索派生表 | 维度描述向量化，匹配从符号等值放宽到向量邻域 | Agent 取数、GraphRAG 式检索 | 开源自建或云产品 |
| 本体建模 | 面向语义互操作的模型 | 用类与关系表达业务概念并可推理 | 知识图谱、跨系统语义对齐 | W3C 的 RDF / OWL 是公开标准（OWL 于 2004 年成为 W3C 推荐标准）【公开，2004】 |

本节保留了原节列出的全部候选——对比表里的维度建模、ER 建模、Data Vault、Anchor Modeling、OBT 宽表，以及组合条目里出现的语义层（dbt Semantic / Cube.js）与语义化维度——并做了两处调整：把「维度建模」这一项拆成星型、雪花、星座三项单列（三者的机制差异足以改变结论，合成一项会把分族做错），并增补了本体建模（主文件 [§1.3](02-dimensional-modeling.md) 已把它列为相邻方法）。

这十个候选分三**族**，先分族再选，能省掉一半比较。**集成结构族**（ER 3NF、Data Vault、Anchor）：差异在于把「实体 / 关系 / 属性」切到多细，族内都走「多表 + 查询时重组」这条路线；**查询结构族**（星型、雪花、星座、OBT）：差异在于 JOIN 搬到写入侧还是留在查询侧、维表拍平还是拆开，族内都假设「已有一份可信的集成结果」；**消费接口族**（语义层、语义化维度、本体）：不改数据的物理结构，只改「谁能找到、按什么名字算」。跨族差异远大于族内差异——**族内换方案通常只是重排 JOIN，跨族换方案要重建链路**。

分族还带来一个直接的操作结论：**选型要按族逐层做，每层只需要回答一个问题**。集成层问「源会不会持续新增」（会 → 集成结构族里挑，不会 → 跳过这一层，直接用查询结构族）；查询结构层问「查询形态能否事先枚举」（能 → 星型，不能 → 星型 + OBT）；消费接口层问「消费方是不是机器」（是 → 加语义层与检索派生表）。三层做完，方案组合自然出现，不需要在一张表上给十个候选排序。

### 7.3 机制差异：为什么它们表现不同（核心节）

以下四个机制维度覆盖了全部候选，也是「为什么它们表现不同」的全部原因。每个维度给出机制定义、各候选的实现差异、由机制必然导出的性质（写成「因为 A，所以 B，代价是 C」）以及失效条件。

四个维度的顺序不是任意的：7.3.1 决定查询时的连接成本，7.3.2 决定历史落在谁身上，7.3.3 决定变更会波及多远，7.3.4 决定机器与人的入口——**前三个维度决定物理结构，第四个维度与物理结构正交**。若某个候选在第 7.3.4 节被选中而在前三节全部落空，说明你把消费接口的需求当成了结构需求（这是 7.7 最后一条反模式）。

#### 7.3.1 粒度与范式：查询时的 JOIN 层数由谁决定

**机制是什么**：结构决定了「一条查询要连接几张表才能拿到上下文」。这就是延迟里唯一随查询形态变化的那一项。

**各候选的实现差异**（同一业务过程：1 张事实 + 12 张维度）：

| 方案 | 表数量级 | 典型查询的 JOIN 数 | 维度加一个属性的动作 |
| --- | --- | --- | --- |
| 星型 | 13 | = 引用维度数（按 5 个维度过筛即 5 次） | 改 1 张维表 |
| 雪花 | 13 + 层次数 | = 引用维度数 + 进入层次的深度 | 改 1 张层次表 |
| 星座 | 事实表数 × 各自维度，共享一致性维度 | 同上，跨过程再拼一次结果集 | 一致性维度是全链路改动 |
| OBT | 1（上游仍有星型） | 0 | 回刷全部分区 |
| Data Vault | 【推算】36–54 张（12 Hub + 12–18 Link + 12–24 Sat，推导见 7.4） | Hub / Link / Sat 数量级 | 新增 1 个 Sat，既有对象不动 |
| Anchor | 【推算】与属性数同阶（100 列的维度约 100 张） | 本次查询用到的属性数 | 新增 1 个属性表 |
| 语义层 | 不改物理表 | 由语义层生成，等价于底层星型 | 改声明文件，物理表不动 |

**由此必然导出的性质**：因为星型把维度的全部层次拍平进同一张表，所以「按城市看」与「按国家看」是同一个 JOIN、只是 WHERE 不同——执行计划不随维度组合变化，延迟可预测；代价是维表内冗余随层次重复，并且事实表的 JOIN 数等于引用维度数，这是下限而非调优项。因为 Data Vault 把实体标识、关系、描述属性分成三类表，所以新增一个数据源只需新增 Hub / Link / Sat，既有对象一列不动；代价是查询必须把这三类表连接回去，JOIN 数从「引用维度数」变成「链路长度之和」——**写侧的可加性与读侧的连接成本是同一个设计的两面**。

**公开证据**：星型与雪花的结构定义出自 Kimball《The Data Warehouse Toolkit》（1996）【公开，1996】；带层次的雪花式 schema 见 TPC-DS 规范（依据与核验入口见 [§3.2.2](02-dimensional-modeling-section-3-sec3.md)）【公开，可自行核验】；Hub / Link / Sat 的三分法见 Data Vault 2.0 的系统化著作（2015）【公开，2015】。

**失效条件**：当查询形态完全不可预知、且维度属性变更频率低到可以接受回刷时，星型的「一层 JOIN」让位给 OBT 的「零 JOIN」。反转条件是属性变更频率，不是数据量——见 7.5 的 Q5 / Q6。

这一节还给出一条**反直觉的判据**：想要「查询快」，可选的路线不止 OBT 一条。当一次查询引用的维度只有少数几个、且事实表的过滤能靠分区裁剪完成时，星型的 JOIN 成本本来就小于聚合与扫描的代价，此时引入 OBT 只会平白增加一条回刷链路【经验】。判断方法很直接——把最常用的 10 条查询的执行计划拿出来看：如果耗时主要落在聚合与扫描上而不是 JOIN 上，那么换结构不会带来收益。

#### 7.3.2 历史放在哪一侧：版本膨胀落在谁身上

**机制是什么**：把「历史」表达成什么载体——维度行的一个版本、卫星表的一行、宽表的一列快照，还是根本不表达。

| 方案 | 历史的载体 | 谁因此变大 | 能否按当时口径重述 |
| --- | --- | --- | --- |
| 星型 + SCD Type 1 | 不保留（就地覆盖） | 不膨胀 | 不能 |
| 星型 + SCD Type 2 | 维度行的有效期列 | 维表，按版本数膨胀 | 能（事实表按当时的代理键落库） |
| 星型 + SCD Type 3 | 一列旧值 | 加一列 | 只能回答「变了没变」 |
| Data Vault 的 Sat | 卫星表按时间追加行，粒度是**属性组** | 卫星表；一个属性变化会让**整组**产生新版本，不同卫星表之间互不牵动 | 能（但同一 Sat 内属性成组联动） |
| Anchor | 属性表按时间追加行，粒度是**单个属性** | 属性表，粒度最细 | 能，且属性之间互不牵动 |
| OBT | 无独立载体（属性物化在事实行上） | 事实表需回刷历史分区 | 不能，除非额外保留多份快照表 |
| 语义层 | 不承载历史，只承载定义 | 历史本身不变，但历史报表的结果会变 | 取决于底层表的历史能力 |

**由此必然导出的性质**：这两条路线比 SCD Type 2 省，但省在不同的粒度上，粒度差一级，省的幅度就差一级。SCD Type 2 的版本落在**整行**上——任意一列变化，整行产生新版本，其余列被连带复制。Anchor 的版本落在**单个属性**上（一属性一表），所以一个属性的变化不会迫使同一实体的其他属性也产生新版本，这是三档里最细的一档。Data Vault 的版本落在**属性组**上——同一卫星表内的属性成组联动，组内任一属性变化会让整组产生新版本，只有分处不同卫星表的属性才互不牵动；所以它比 SCD Type 2 省，但省得比 Anchor 少——**「连带版本」的连带范围只到卫星表这一个属性组，不是整个实体；要属性级互不牵动，那是 Anchor 独有的性质**（见 7.6 的选型矩阵）。两者共同的代价是「这个实体上个月长什么样」要由查询层把多个卫星表 / 属性表按时间对齐拼出来，拼装逻辑成为新的复杂点。因为 OBT 把维度属性直接物化在事实行上，所以它查询最快、历史却丢了：一次维度改名对所有历史分区都是无效的，必须整段回刷（存储与回刷量级见 [§3.2.7](02-dimensional-modeling-section-3-sec3.md) 的推算）。

**公开证据**：SCD Type 1–7 的分类出自 Kimball 方法论【公开，1996 起】；生产中最常落地的只有 Type 1 与 Type 2，Type 3 少见【经验】；卫星表把同一 Hub 的属性切成若干属性组、每组按时间独立追加（组内属性随该组一起产生新版本）的做法见 Data Vault 2.0 著作（2015）【公开，2015】；一属性一表、历史即该属性表自身的追加行，见 Anchor Modeling 的公开方法论材料【公开，可自行核验】。

**失效条件**：当维度属性每天都可能变（消费分档、活跃度标签）时，任何「保留全部历史」的方案都会退化成维表或卫星表按天膨胀，此时正确动作是换 Type 1 + 独立变更日志表（判断方法见 [§3.6](02-dimensional-modeling-section-3-sec3.md)）。

历史策略还与**度量的可加性**相互牵制：周期快照里的余额是半可加度量（可跨账户 SUM、不可跨日期 SUM，见 [§3.2.5](02-dimensional-modeling-section-3-sec3.md)），而 SCD Type 2 让同一实体在事实表中指向多个代理键版本。两者叠加时，「按维度聚合」与「按版本聚合」的语义必须由语义层显式声明，否则同一个 SUM 会在两个看板上给出两种含义——这不是建模错误，而是聚合规则未声明。

#### 7.3.3 变更的传导范围：加一个属性要动几张表

**机制是什么**：新增或修改的对象是「表的一个局部」，还是「结构的横截面」。前者只影响本表，后者会沿链路传导到所有下游。

| 方案 | 加一个属性 | 改一次口径 | 传导范围 |
| --- | --- | --- | --- |
| ER（3NF） | 加一列，既有查询不受影响 | 改一处，但规范化结构常需连带调整 | 局部 |
| 星型 | 改 1 张维表 + 回刷下游 | 改 1 处定义 + 重算下游 | 1 张表 + 下游 |
| Data Vault | 新增 1 个 Sat，既有 Hub / Link 不动 | 新增 Sat 版本，历史可并存 | 局部（这是它的核心卖点） |
| Anchor | 新增 1 个属性表，既有查询不受影响 | 新增属性行；但视图/查询层要重生成 | 局部 + 查询层重建 |
| OBT | 加一列 → 全部历史分区回刷 | 同上 | 全表 |
| 语义层 | 改声明文件，物理表不动 | 改 1 处 → 所有消费端结果同时改变 | 全局 |

**由此必然导出的性质**：因为语义层把度量与维度的口径集中到一处声明，所以「同一指标在各消费端只有一份定义」，修一次全对；也正因为集中，一次错误的定义修改会同时改变所有消费端的结果——**集中化的收益与它的爆炸半径来自同一个机制**。这条性质决定了语义层必须进版本控制与评审，否则口径权威会落到「最后一个改文件的人」手上。同理，因为 Data Vault 的新增是「加表」而不是「改表」，所以它的演进成本与历史长度无关；而 OBT 的演进成本与历史长度成正比——这就是为什么 OBT 只能作为**可从上游重建的派生层**，不能作为权威口径的所在地。

**公开证据**：Data Vault 的「新增对象不改既有对象」这一设计目标见 Data Vault 2.0 著作（2015）【公开，2015】；语义层定义文件是否支持你需要的聚合与时间粒度，可查 dbt Semantic Layer / MetricFlow 与 Cube 的官方文档（以当前版本为准）【公开，可自行核验】。

**失效条件**：当语义层的定义没有 Owner、没有版本控制、也不进评审时，「一处定义」会反转成「一处无声的全局变更」——它的失效不表现为报错，而表现为多个看板同时给出新数而没人知道原因。

对照地看，Data Vault 走的是相反方向：把变更的爆炸半径压到最小，代价是查询侧要重建上下文。**这两条路线没有共同的最优解**，它们回答的是不同的问题——「我要口径绝对统一」与「我要演进绝对安全」；同时要两者，就得付两层结构的运维成本（见 7.6 组合 1）。

#### 7.3.4 消费方形态：符号的入口还是语义的入口

**机制是什么**：查询的入口是「表名 + 字段名」（符号匹配），还是「业务问题的自然语言描述」（语义匹配）。这决定了失败的表现形式。

| 方案 | 入口 | 谁决定「找到哪张表」 | 典型失败形态 |
| --- | --- | --- | --- |
| 星型 / 雪花 / 星座 | 表名 + 字段名 | 人 | 找不到就用不了；找到错表则算错 |
| OBT | 表名 + 宽列名 | 人 | 列名语义靠猜 |
| 语义层 | 已声明的度量与维度名 | 声明文件 | 未登记即拒绝（这是优点） |
| 语义化维度 | 向量邻域 | 相似度 | 近似命中、静默漂移 |
| 本体 | 概念与关系 | 推理 | 概念建模成本高，落地案例少 |

**由此必然导出的性质**：因为语义化维度是一张**独立派生表**而不是主表上新增的一列，所以它可以整体重建、可以停用，而不会污染口径计算的权威路径；代价是第二份必须与主表同步的状态，且近似匹配给不出「为什么命中这一条」的确定答案（见 [§3.2.8](02-dimensional-modeling-section-3-sec3.md)）。反过来，因为语义层与检索派生表都不改变事实表结构与 SCD 策略，所以「消费方是 Agent」这件事**不能用来论证物理结构的选择**——它只决定要不要在既有结构之上加一层消费接口。

**公开证据**：自然语言到 SQL 的可比口径由公开基准给出——Spider（EMNLP 2018）与 BIRD（NeurIPS 2023）【公开】；维度作节点、事实作边的检索增强方法有 Microsoft Research 的公开论文《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》与同机构的公开博客（2024），按题名即可核验【公开，2024】；语义化维度本身以厂商演示与愿景为主，尚未见到可核验的第三方生产案例（判断标准见 [§5.4](02-dimensional-modeling-section-5-ai.md)）【经验】。

**失效条件**：当有人开始拿向量检索的近似结果直接生成口径（而不只是用它找表）时，检索层就从「帮助找到」变成「第二个口径来源」，这一层的所有优势随之消失。

**本体建模在这一维度上的位置**：它的入口是概念与关系而不是表与字段，理论上能同时服务人与机器，也是跨系统语义对齐最正式的表述（RDF / OWL 为标准）。但它在这个维度上并没有「因为更强所以更值得选」——本体要求先把业务概念建模成类与关系，这份建模成本与收益只有在**跨系统语义对齐**（多套系统对同一概念的理解必须统一）时才成立。在单一数仓内引入本体，通常得到的是又一份需要与物理表同步的语义资产【经验】。

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本不是产品报价，而是五项随规模变化的量之和：

```
总成本 ≈ 建模与协商成本 + 存储成本 + 查询成本 + 变更成本 + 消费端适配成本
        ≈ c0 + f(行数 × 列宽 × 版本数) + g(JOIN 层数 × 扫描量 × 查询频次)
             + h(回刷范围 × 变更频率) + i(消费端数量 × 口径数量)
```

各方案的差别不在总量，而在**哪一项是主导项**、以及**哪一项是看不见的**：

| 方案 | 主导项 | 隐性成本（上线时不计入、三年后计入） | 什么条件下反转 |
| --- | --- | --- | --- |
| 星型 | f（维表冗余） | 事实表 JOIN 数 = 引用维度数这一下限 | 常用查询一次引用的维度数多到 JOIN 成为执行计划里的主要耗时项时【经验】（判定方法见 7.3.1） |
| 雪花 | g（多出的 JOIN） | 执行计划随层次深度变化，延迟不可预测 | 维度成员基数极小（如省级、类目级） |
| 星座 | c0（一致性维度的协商成本） | 每新增共享维度都要对齐口径与代理键规则 | 只有一个业务过程时，星座是纯负担 |
| Data Vault | f + g（表数与连接链路） | 查询层需要额外的物化或视图，否则每次查询都重连 | 源系统数量少且稳定时，可加性用不上 |
| Anchor | f（表数 ≈ 属性数） | 查询层视图的生成与维护 | 属性演化不频繁时，细粒度只是额外开销 |
| OBT | h（回刷范围 × 变更频率） | 一次属性改名要回刷全部历史分区 | 维度属性每周以上变一次，见 7.5 的 Q6 |
| 语义层 | i（口径数量 × 消费端数量） | 语义层本身成为取数链路的单点 | 度量数很少时，直接建视图更简单 |

四项【推算】示例（推导链全部写出，读者可按自己的规模替换参数）：

- **雪花省下的存储**（沿用 [§3.2.2](02-dimensional-modeling-section-3-sec3.md) 的推算）：1000 万行地理维、地理描述约 200 字节/行，扁平存法约 2 GB（10^7 行 × 200 B = 2×10^9 B）；去重后若城市基数取 3 万，则该维表约 6 MB（3×10^4 行 × 200 B = 6×10^6 B）。省下的是 MB 级，付出的是每次跨层次聚合多一次 JOIN。
- **OBT 的存储放大**（沿用 [§3.2.7](02-dimensional-modeling-section-3-sec3.md) 的推算）：10 亿行事实、从维度引入 60 列、平均 30 字节，单份宽表约 1.8 TB（10^9 × 60 × 30 B = 1.8×10^12 B）；若按 N 个消费视角各物化一份，存储与回刷成本再乘 N。
- **Data Vault 的表数放大**：表数 ≈ Hub 数 + Link 数 + Sat 数。沿用 7.3.1 的前提（同一业务过程的星型是 1 张事实 + 12 张维度 = 13 张表）：12 个维度各对应一个实体，即 **12 个 Hub**；实体间被显式建模的关系条数按「与实体数同阶、每实体平均 1–1.5 条」折算，即 **12–18 条 Link**；每个实体的属性按变化节奏切成的属性组数按「每实体 1–2 组」折算，即 **12–24 个 Sat**。代入得 12 +（12–18）+（12–24）= **36–54 张**，中值约 45 张——**表数比约 3–4 倍，查询侧对应的是链路连接长度**。关系越多、属性变化节奏越分散，Link 与 Sat 就越大；这三个量都是可替换的场景假设，读者可按自己的实体数、关系数与属性组数重算。
- **Anchor 的表数**：表数与属性数同阶。一个 100 列的维度，在 Anchor 下是 100 张量级的属性表，查询要连接本次用到的每一个属性。

**成本对比里不该出现的数字**：任何形如「性能提升 3.2 倍」「存储节省 63%」的结论，如果没有说明数据量、列宽、查询形态与基线口径，就没有可迁移性——本节的四条推算都把参数写了出来，就是为了让读者能用自己的参数替换后重算一遍。同样地，厂商与社区材料里的性能数字在拿来做选型依据前，先问三个条件：多大表、什么查询、什么硬件；三问缺一，就当方向记录而不当证据【经验】。

一个共同结论：**这七类方案的成本函数形式相同，差别只在主导项**。因此选型的第一问不是「哪个便宜」，而是「我的数据里，哪一项会先变大」。

消费端适配成本（i 项）最容易被漏算，因为它在建模阶段看不见。它的形式是：**口径数量 × 消费端数量**。举一个可自行替换参数的推算：若一个团队有 200 张核心表需要进入语义层，每张表的口径、粒度、Owner、密级四项声明平均需要 0.5 人日，则一次覆盖约 100 人日（200 × 0.5）【推算】；而覆盖之后每新增或修改一个度量仍要重复这份动作。这个量级解释了为什么语义层类落地的成本主导项是**定义覆盖度**而不是存储或算力——也解释了为什么验收要看**覆盖到了哪些度量与口径**而不是「声明文档写完没有」：覆盖范围本身就是一处要主动收敛的决策，把它摊大并不划算（[§5.7](02-dimensional-modeling-section-5-ai.md)）。

### 7.5 决策树（每个分支都要有阈值依据）

```
开始：为分析场景选建模方案
├─ Q1 业务过程与问题清单能否在一个季度内枚举完？
│    ├─ 不能（源系统持续新增、口径未定）→ Data Vault（Hub / Link / Sat）
│    │        └─ 且团队有 6NF 经验、属性演化是主要矛盾 → Anchor Modeling
│    └─ 能 → 进入 Q2
├─ Q2 事实表的一行代表什么？
│    ├─ 一次不可撤销的事件 → 事务事实表 + 星型
│    ├─ 某个时点的状态 → 周期快照事实表
│    └─ 一段有终点的流程 → 累计快照事实表
├─ Q3 最常用的那批查询是否高频跨维度层次聚合（按国家 / 按类目汇总）？
│    ├─ 是 → 星型（层次拍平，不拆雪花）
│    └─ 否，且层次描述被独立维护、成员基数小 → 雪花可接受
├─ Q4 是否存在两个以上业务过程要按同一维度对比？
│    ├─ 是 → 星座 + 一致性维度 + 总线矩阵
│    └─ 否 → 单事实星型
├─ Q5 是否存在查询形态事先不可预知的消费方（Ad-hoc / 特征工程 / Agent）？
│    ├─ 是 → 星型保持权威 + OBT 派生层（可从上游重建）
│    └─ 否 → 不加 OBT，避免多一条重建链路与新鲜度监控
├─ Q6 维度属性变更频率落在哪一档？
│    ├─ 每周一次以上 → 不建 OBT；SCD 改用 Type 1 + 独立变更日志
│    ├─ 每季度到每月一次 → SCD Type 2 可用，OBT 可用
│    └─ 每年一次或更少 → OBT 与 SCD Type 2 都不会成为负担
├─ Q7 业务方是否要求「按当时口径重述历史报表」？
│    ├─ 要求 → SCD Type 2（历史写在维度行上）
│    └─ 不要求 → SCD Type 1（不为此付维表膨胀与下游过滤）
└─ Q8 消费方是否包含 Agent / 自然语言取数？
     ├─ 是 → 在既有结构上加语义层 + 只读语义派生表（不动物理结构）
     └─ 否 → 先不加，等口径覆盖率与 Owner 机制成熟
```

**阈值依据**（与树上节点一一对应）：

读这棵树的方式是**自上而下**：Q1 决定要不要有集成层，Q2 决定事实表的粒度，Q3 到 Q6 决定查询结构，Q7 决定历史策略，Q8 决定消费接口。前面的答案不会被后面的答案推翻——如果被推翻了，说明有一层的结论下错了，而不是树画错了。

- **Q1「一个季度内枚举完」**：依据是判据「变更传导范围」。Data Vault 的可加性只在「源持续新增、无法一次穷举」时才产生收益；若问题清单能在一个季度内枚举完，星型的上线速度优势压过可加性优势。这不是规模数字，而是「约束会不会持续变化」的近似分界【经验】。
- **Q2（三类事实表）**：依据是 [§3.2.4–3.2.6](02-dimensional-modeling-section-3-sec3.md) 的机制结论——粒度只有三个合法取值（一行一事件 / 一行一周期 / 一行一生命周期），且一旦声明就决定了度量能否直接 SUM。这条不是经验值，是结构约束。
- **Q3「高频」**：判定方法是抽最近 100 条查询（或查查询日志）数其中多少条进入了二级以上层次；超过半数即按「高频」处理，此时雪花多出的 JOIN 无法被存储收益覆盖【经验】。
- **Q4**：依据是 [§3.2.3](02-dimensional-modeling-section-3-sec3.md) 的失效点——两个业务过程对「同一维度」的语义分叉会让 drill-across 结果不可解释。所以判据是「是否存在两个以上过程要按同一维度对比」，而不是「有多少张事实表」。
- **Q5**：判据是「查询是否用到了表里事先未约定的列组合」。出现了，就说明 JOIN 组合不可枚举，星型直查的每次重新优化成为常态【经验】。
- **Q6 的三档边界**：不是精确阈值，而是「回刷成本能否被单次变更的收益覆盖」的近似分界。按 [§3.2.7](02-dimensional-modeling-section-3-sec3.md) 的推算，一次属性改名要回刷 1.8 TB 量级的分区（10 亿行 × 60 列 × 30 B）；若这类变更每周发生一次以上，OBT 的写入成本就会超过它省下的 JOIN 成本【推算，推导见 7.4】。
- **Q7**：这条由业务方回答，不是技术判据——「去年的报表要不要保持去年的样子」只有业务能答。答「要」就必须付维表按版本膨胀与下游显式过滤的代价（[§3.2.9](02-dimensional-modeling-section-3-sec3.md)）。
- **Q8**：依据是 7.3.4 的结论——语义层与检索派生表只改「消费接口」，不改变事实表结构与 SCD 策略。所以它出现在决策树的末端，且不影响前面任何一条分支。

需要强调的是：这八个节点里只有 Q1、Q3、Q6 用了近似阈值，其余五个都是**结构性问题**（粒度只有三个取值、要不要跨过程、查询形态能不能枚举、要不要重述历史、消费方是不是机器），答案由约束决定，不需要估数。把可判定的问题写成阈值，是决策树最常见的画蛇添足。

### 7.6 选型矩阵与组合

矩阵按「场景」而不是「方案」组织——选型的输入是你的处境，不是候选清单。每一行的「不选它的原因」都写成机制层面的理由，而不是「性能差」这类形容词。

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单一业务过程、源稳定、报表需求明确 | 星型 + 事务事实表 | 雪花（成员基数极小时） | 不选 DV：可加性用不上，却要付 3–4 倍表数与连接链路 |
| 源系统持续新增、口径未定 | Data Vault 集成层 + 星型汇总层 | Anchor（属性演化为主矛盾时） | 不选纯星型：新源接入要改动既有维表并回刷下游 |
| 查询形态不可预知、维度属性稳定 | 星型（权威）+ OBT 派生层 | 物化视图 | 不选纯星型直查：JOIN 组合爆炸，每次重新优化 |
| 多业务过程按同一维度对比 | 星座 + 一致性维度 + 总线矩阵 | 各自建维后人工对齐 | 不选各自建维：drill-across 会因维度定义不同而失败 |
| 消费方包含 Agent | 星型 + 语义层 + 只读语义派生表 | 语义层单独落地 | 不选「维度表加 embedding 列」：把检索需求写进了权威口径路径 |
| 监管要求按当时口径重述历史 | 星型 + SCD Type 2 | DV 卫星表 | 不选 Type 1：历史会被新口径整体改写 |
| 单个维度成员基数极小（省 / 类目级） | 雪花 | 星型 | 不选星型不是为了性能，而是因为层次确属独立业务对象、需要单独维护 |
| 属性随业务频繁演化、结构要存续十年以上 | Anchor + 查询层视图 | Data Vault | 不选 DV：DV 的历史粒度是卫星表（属性组）级，属性只要同处一个卫星表，组内一个属性变化就会带出整组的新版本；「属性之间互不牵动」只有 Anchor 做得到（7.3.2） |

四条**常见组合**（保留原节列出的四种，并补齐各自的职责边界与运维代价）：

1. **维度建模 + Data Vault**（集成层 + 汇总层）：Data Vault 承担「源持续新增时的集成」职责，星型承担「面向查询的口径」职责，两者的边界是——**口径只在星型一侧定义，DV 一侧只负责实体标识、关系与属性历史的完整性**。运维代价：多一层加工链路与一套 Hub / Link / Sat 的加载逻辑；查询侧要么物化，要么每次沿链路连接；任何一次口径变化都要判断它属于哪一层的职责。
2. **维度建模 + 语义层**（dbt Semantic Layer / Cube.js）：星型承担物理结构与历史，语义层承担「度量一处定义、BI / API / Agent 共用」。边界是——**语义层不新增口径，只把已有口径声明成机器可读的形式**；未登记的表不进入语义层服务范围。运维代价：语义层成为取数链路单点，且它的变更影响所有消费端（7.3.3），必须进版本控制与评审。
3. **维度建模 + OBT**：星型是唯一权威，OBT 由星型按需重建，供 Ad-hoc、特征工程与 Agent 取数。边界是——**OBT 不新增任何口径，只做结构变换，因此可以随时重建、随时废弃**。运维代价：需要一套重建作业与新鲜度监控，否则两边会悄悄分叉；还要防止有人把 OBT 当成权威去改数（[§3.4](02-dimensional-modeling-section-3-sec3.md)）。
4. **维度建模 + 语义化维度**：主表保持符号匹配的唯一权威，语义派生表只为「找到」服务，不参与口径计算。边界是——**派生表可以停用而不影响任何口径**。运维代价：第二份必须与主表同步的状态（增量重算、SCD 产生新版本时旧描述的归属）；近似匹配给不出确定答案，因此它只能做召回、不能做判定。

四条组合有一个共同的运维代价结构：**每加一层，就多一份需要与上游保持同步的派生状态**（DV 的卫星表、OBT 的宽表、语义层的声明、语义派生表的向量），而每一份派生状态都需要新鲜度监控与 Owner。这解释了一条常见的失败路径——团队为了「一次解决所有问题」把四层全建起来，结果四份派生状态各自漂移，比只有一层时更难判断哪个数是对的。**组合的原则是：先建权威层，再按实际出现的消费需求逐层追加，而不是一次配齐。**

### 7.7 选错的代价与迁移成本

下面六条反模式中的前三条，源头是本章 [§3.5](02-dimensional-modeling-section-3-sec3.md) 的失效分析，这里补上「选型层面」的表述——同一件事在设计阶段叫反模式，在选型阶段就是「选了不该选的方案」。

**反模式：把 OBT 当起点而不是派生层** —— 症状：为「少写 JOIN」，在明细表上不断加列，直到它同时是事实表、宽表和历史快照三种东西（[§3.5](02-dimensional-modeling-section-3-sec3.md) 的「巨型大宽表」）。后果：任何一次维度属性改名都要回刷全部历史分区，且没有一条路径能只改一处；粒度声明也随之失效。正确的做法：事实表只装度量与外键；需要宽表就另建一条**可从星型重建**的派生层，并给它新鲜度监控与「非权威」的显式声明。

**反模式：为「省存储」把维度雪花化** —— 症状：把「用户」拆成 7 张表，报表要写 7 次 JOIN。后果：每次跨层次聚合的延迟与层次深度成正比，而这类查询往往正是这个维度存在的理由；省下的存储按 7.4 的推算在 MB 级。正确的做法：维度尽量扁平，最多二级；要不要拆，用 7.4 的推算把「省下的存储」与「每次查询多出的 JOIN」显式比一次。

**反模式：所有维度都开 SCD Type 2** —— 症状：连「商品类目层级」这类低频属性也开版本。后果：维表按版本膨胀，事实表外键指向大量版本，每张下游报表都必须显式过滤 `is_current`，漏写即重复计数**且不报错**。正确的做法：按属性语义逐列选策略——修正错误用 Type 1，需要按历史时点还原才用 Type 2；并把「哪些列开了 Type 2」做成可查询的清单，让下游能主动发现。

**反模式：在没有语义层与权限下推时先上自然语言取数** —— 症状：Agent 拿不到字段名，于是靠猜表名生成 SQL。后果：猜得更快，错得也更快；错的形态是「悄悄算错」而非报错。正确的做法：先把口径、粒度、Owner 补到可机器读取，并给未登记项一个显式的失败行为（拒绝而不是猜测），再开放自然语言入口（[§5.5](02-dimensional-modeling-section-5-ai.md)）。

**反模式：把 Data Vault 直接当供数层** —— 症状：报表与看板直接查 Hub / Link / Sat，每个需求都临时拼一次连接。后果：每次查询都要重组上下文，性能与可维护性同时下降；更麻烦的是口径落在了「这次查询怎么拼的」里，而不是落在某一层的定义里。正确的做法：DV 只做集成层，其上必有星型汇总层承担口径（7.6 组合 1）——**集成层的收益是写侧的可加性，不是读侧的性能**。

**反模式：用「未来的 AI 需求」为物理结构做决策** —— 症状：在维度表上预留 embedding 列、为 Agent 提前建宽表。后果：预留的列构成第二份必须同步的状态（[§3.2.8](02-dimensional-modeling-section-3-sec3.md)），而真实需求可能只是要一个语义层。正确的做法：把 AI 需求拆成可判定的两件事——「机器能不能找到」（语义层与检索派生表）与「机器能不能算对」（口径、粒度、密度的机器可读），两者都不需要改动权威表的物理结构。

**换成另一个要动什么**：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 星型 → Data Vault | 大（按 Hub / Link / Sat 重切并回填历史） | 大（查询沿链路重组，通常要在其上再建星型视图） | 中（新增一套加载与校验链路） | 大（三类表的建模纪律） |
| 星型 → OBT 派生层 | 中（不改权威表，新增派生表） | 小（去掉 JOIN） | 小（一条重建作业 + 新鲜度监控） | 小 |
| SCD Type 1 → Type 2 | 大（维表要重建版本行，事实表要重指代理键） | 中（所有下游查询补 `is_current` 过滤） | 中（幂等的比对—关行—插行逻辑） | 中 |
| 星型 → 雪花 | 小（拆维表） | 中（所有跨层次查询改写为多层 JOIN） | 小 | 小 |
| 星型 → 语义层 | 无（不改物理表） | 无（消费端换成指标名） | 中（语义层成为新单点，需 Owner 与版本控制） | 中（口径定义从报表 Owner 转到定义 Owner） |
| 星型 → Anchor | 大（属性级重切） | 大（查询层视图重建） | 中 | 大（6NF 建模能力） |

这张表里最容易被低估的一格是「星型 → Data Vault」的**查询改写**：迁移的难点不在把数据搬过去，而在于原来一条 JOIN 能拿到的上下文，之后要在查询层重新组装——所以生产中的常见形态是 DV 只做集成层，其上仍保留星型汇总层（见 7.6 组合 1）。

迁移的通用原则只有一条：**先建新的一层，让它与旧层并行跑一段，验证两边口径一致后再切换消费端**。建模方案的迁移不存在「一次性大爆炸」的成功案例——因为建模的产物是口径，而口径是否一致只能靠两套结果对账来确认，不能靠单元测试证明。这条原则同样解释了 7.4 的结论：迁移成本的主体不是数据搬运，而是「两套结构同时存在期间」的口径对账与消费端切换。

### 7.8 小结

下表把 7.5 的决策树压成六行，每行只保留「处境 → 建议 → 机制理由」三要素。**读法**：先找到与你最接近的那一行，再回看它对应的 7.3 小节确认理由是否对你的场景成立——若理由不成立，就换行。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 单一业务过程、需求明确、团队小 | 星型 + 事务事实表 | 维度拍平使执行计划不随查询形态变化，延迟可预测 |
| 源持续新增、口径未定 | Data Vault（或 Anchor）+ 其上的星型汇总层 | 新增对象不改既有对象，演进成本与历史长度解耦 |
| 跨度超过一个业务过程 | 星座 + 一致性维度 + 总线矩阵 | 共享代理键使 drill-across 无需合并事实表 |
| 查询形态不可预知 | 星型权威 + OBT 派生层 | 把 JOIN 搬到写入侧；代价是可重建、可废弃 |
| 维度属性每天在变 | SCD Type 1 + 独立变更日志 | 任何「保留全部历史」的方案都会按天膨胀 |
| 消费方是 Agent | 星型 + 语义层 + 只读语义派生表 | 把「找到」与「算对」分成两条路径，主表权威不变 |

还有一种处境值得单列：**已经有一套跑了多年的模型，想换**。此时第一步不是比较方案优劣，而是把现状的痛点归到 7.3 的哪一个机制上——若是查询慢，问题在 7.3.1；若是历史口径对不上，问题在 7.3.2；若是加一个源就要改一堆既有表，问题在 7.3.3。**痛点归错了类，换方案只会把成本从一个账户挪到另一个账户。**

> 本节小结：这一组候选里**唯一真正起决定作用的差异**是「上下文被放在哪里」——拍平在一张维表里（星型）、留在层次链上（雪花 / 3NF）、拆到属性组与单个属性上（DV 的卫星表 / Anchor 的属性表），还是物化到事实行里（OBT）。它同时决定了查询的 JOIN 层数、历史的载体和变更的传导范围；其余维度（生态、学习成本、AI 友好度）都是这条差异的下游表现，因此不该被当成独立判据。
