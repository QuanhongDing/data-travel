## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单最根本的问题不是"列错了"，而是**没有时间维度**。同一张清单里，"已经在生产环境被第三方用着"和"产品文档里写了、只在演示里跑过一次"被并列成同一行；读者据此排路线图，必然把一个不受自己控制的时间表排进关键路径。

本章 §1.4 把维度建模划成三段（传统 / 大数据 / AI 原生），但"AI 原生"内部不是一块整体。要判断一个方向能不能现在就规划，只有三条**可核验**的判据：有没有正式 release note、有没有**第三方（非厂商）**公开的生产案例、接口是否稳定。三条全中才算 L1。

这三条判据之所以必须是这三条，是因为它们各自挡住一类误判：release note 挡住"把路线图当既成事实"，第三方生产案例挡住"把厂商自述当行业现状"，接口稳定性挡住"把演示当工程"。缺任何一条都会让读者按错误的时间表做规划——比如为一条还在预览的特性预设架构假设，两年后发现它的接口换了三次。

判据必须是可核验的，而不是"感觉成熟"。「厂商博客说它已被广泛采用」不算——博客是厂商自己的产出；「GitHub star 多」不算——star 是关注度，不是部署量。可核验的意思是：你能在对方文档里指出一页 release note 或一条时间线，并且能说出一个**不是该厂商自己**的公司正在生产环境里用它。

还有一条容易被忽略的区分：**产品名与能力名是两件事**。同一个能力在不同平台上的命名不同、边界不同（自然语言生成 SQL 这件事，各家的函数名、入口位置、支持的方言都不一样），所以本节讨论的是**能力**，落到具体产品时一律以该产品的文档为准。同理，"规范里写了"和"你用的引擎支持"是两件事——表格式的新条目属于前者，能不能用属于后者。这两条是本节判断成熟度时反复用到的尺子。

还有三条尺子要拿在手里：**GA 不等于预览**（路线图上的条目不能当既成事实）、**单机不等于分布式**（内嵌引擎的扩展能力要看有没有独立的多机执行组件，而不是看 benchmark 博客）、**论文原型不等于产品实现**。看到"某引擎支持向量检索"这类描述，追问三个问题就能把它放回正确层级：这条能力在哪个版本进入 GA，还是仍在预览？它是引擎内置的还是外挂的？它支持单机部署还是分布式部署？三个问题答不清的材料，一律按 L3 处理。

按这三条判据，本主题下的分级如下。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **NL2Model / Copilot 生成模型 DDL**（Databricks Assistant、Snowflake Cortex Analyst、阿里云 DataWorks AI Copilot、dbt-codegen + LLM） | L2 | 已可用且官方文档可查；生产案例多来自厂商自有客户故事，缺第三方独立复盘；效果强依赖前置元数据质量 | 在"模型已经想清楚、只差落 DDL"的环节试点，PoC 里量化**评审通过率**而不是生成速度 |
| **度量语义层 / Headless BI**（dbt Semantic Layer、Cube、LookML 一类：度量集中定义、BI 与 Agent 共同消费） | L2 | 各实现均已可用，但**定义文件互不兼容**、无跨厂商标准；有公开生态，缺独立第三方规模化案例 | 选一套落地，把口径从报表里搬出来；不要假设换实现时迁移成本为零 |
| **AI 元数据补全**（Atlan AI、DataHub AI 一类：识别事实/维度、生成标签与血缘） | L2 | 采集与推断能力可用；准确率高度依赖数据源方言与命名规范，厂商未给出可复核口径 | 做"补全建议 + 人工确认"，不要做无人值守的自动写回 |
| **表格式演进**（Apache Iceberg v3 规范的删除向量、Apache Paimon 的主键表一类） | L3 | 规范条目与 release note 可查，但**"规范里有"与"你用的引擎支持"是两件事**，需逐个版本核验 | 只记录，不要把表结构设计建立在这些新条目上 |
| **湖仓一体 + 平台内置 AI**（Microsoft Fabric / OneLake、Databricks + Unity Catalog） | L2 | 平台本体已 GA；"内置 AI"是平台侧捆绑能力，跨云可移植性弱 | 把它当**平台选型项**，不当独立技术方向评估 |
| **语义化维度**（维度表加 embedding 列，让描述直接命中） | L3 | 公开材料以论文式演示与厂商愿景为主；无第三方生产案例，也无 embedding 的维护责任约定 | 记录，不要在维度表里预留 embedding 列 |
| **事实向量嵌入 / 维度作为 RAG 元数据 / GraphRAG 与维度建模** | L3 | 有公开论文与开源实现，但"事实行向量化"的更新成本与一致性账，没有任何可核验的生产数字 | 记录；RAG 侧先解决元数据质量，再谈向量 |
| **Agent 驱动的模型演化**（自动生成 schema migration 脚本） | L3 | 生成脚本容易，**判断"该不该改"没有公开的自动化案例**，也没有与发布门禁集成的公开证据 | 记录；先把手写迁移的**影响面查询**做成日常动作 |
| **列存与向量化执行引擎**（StarRocks / Doris / ClickHouse 一类在取数链路里的承载） | L1 | 已 GA、接口稳定（就是 SQL）、第三方生产案例大量存在 | 这是 5.1 表里**唯一**可以直接排进路线图的**演进方向**，按常规选型流程做 |
| **建模文档的自动生成与补全**（把已有表结构反向产出粒度声明与字段含义） | L2 | 能力可用且**不改变决策权**，风险低；但产出质量取决于表命名与注释质量 | 拿一个成熟业务域试一次，统计人工修正比例 |
| **语义定义互操作规范**（跨厂商交换语义层定义文件） | L3 | 属规范草案，无已发布标准、无参考实现的生产案例 | 记录；迁移成本按"零互操作"预估，不要按标准落地预估 |

> 表里唯一够得上 L1 的**演进方向**是**执行层的列存与向量化**——而它跟 AI 的关系比看起来弱得多：它不是被 AI 创造出来的能力，只是因为 AI 取数把"秒级交互"变成默认体验，它才从"优化项"变成"默认配置"。换句话说，这一格是**接口改良，不是架构变化**。
>
> 除它以外，本节列的方向全部停在 L2/L3。把这些方向放在一起看，有一条贯穿的规律：**能被"生成"出来的东西（DDL、标签、SQL、migration 脚本）已经可用；需要有人"负责"的东西（粒度、口径、影响面）仍然卡在人身上。** 5.2 逐条给出机制。

这里的 L1 只用来标注**演进方向**。5.2.3 与 5.3 的表里会给「一致性维度 + 代理键」这类**未变化的既有能力**也标上 L1，那是把它当**基线**看待：它满足 L1 的三条判据，但它不是本节新列的演进方向，AI 也没有改变它。把这两者分开，是为了不把「一个已经稳了十年的接口」和「一个刚刚可用的新方向」读成同一件事。

还有一层区分值得先说明：级别低不等于"不要看"。L3 的方向依然值得记录，因为本章 §1.4 说的"结构化 vs 语义化"这条 AI 原生阶段的核心矛盾，正是由它们定义的。区别在于**记录**与**依赖**是两件事：L3 可以写进技术雷达，但不能写进架构假设——一旦你在维度表里预留了 embedding 列，就等于已经把一条 L3 特性当成了 L1。

### 5.2 演进方向逐条拆解（核心节）

5.2 的每条方向都按同一个结构写：旧做法卡在哪、AI 改变了哪个机制、由此得到什么、由此付出什么、证据与来源、成熟度。这个结构的重点在**"付出"那一行不能空**——一个方向若写不出代价，多半是因为还没有人在规模上真正用过它；写不出代价的方向，也就不该被排进路线图。

#### 5.2.1 NL2Model：把业务描述编译成模型 DDL

- **旧做法与它的卡点**：旧做法是需求评审会 → 建模师手画星型图 → 手写 DDL。卡点不在"写得慢"。模型是 §4.1 那 8 步流程的产物，其中第 2 步"声明粒度"和第 3 步"识别维度"是**决策**，第 6、7 步"设计维度表 / 事实表"才是**表达**。旧做法把决策和表达捆在同一个人身上做，于是每来一次需求变化都要重走一遍决策，成本落在人身上，而不是沉淀成可复用资产。
- **AI 改变了什么机制**：LLM 把"表达"这一段（自然语言 → DDL）的边际成本压到接近一次推理调用。它**改变的是成本函数，不是决策方式**。
- **由此得到的**：因为生成的边际成本被压到接近零，所以"先出三版候选模型再挑"第一次在成本上成立——旧做法下不会发生，因为没有人愿意让建模师产出三份都要评审的稿子。
- **由此付出的**：确定性下降——同一需求两次生成不会得到同一份 DDL，评审的输入从"一份稿子"变成"候选 + 差异"。更麻烦的是错误形态变了：语法错误会被解析器拦住，**语义错误（粒度错、SCD Type 选错、把退化维度抽成维度表）不会**，它只在下游报表对不上时暴露。这就是本节要警惕的"幻觉"在建模场景里的样子——它通常不是编出一个不存在的字段，而是**把一段看起来合理、实则与业务过程不符的结构写出来**。代价是把校验成本从建表前移到了建表后。
- **证据与来源**：Text2SQL 方向有可公开核验的评测口径——Spider 基准（EMNLP 2018）【公开】与 BIRD 基准（NeurIPS 2023）【公开】，榜单与人类基线都在公开页面上，读者可自行对比当前差距；厂商侧能力说明见 Databricks、Snowflake、阿里云 DataWorks 官方文档（2024 年前后）【公开】。**具体 GA 状态、可用区域与限定条件以各厂商 release note 为准，本节不作断言。**
- **成熟度**：**L2**。判据：能力已可用、文档可查，但缺第三方独立生产案例，效果强依赖前置元数据。判定方法：拿自己最脏的一个业务域跑 20 条真实需求，统计生成 DDL **通过评审**（不是"语法正确"）的比例——低于你在意的门槛，它就不是 L1。

生成物能过哪一关、过不了哪一关，可以直接列成一张表：

| 生成物 | 谁来校验 | 校验不了会怎样 |
| --- | --- | --- |
| DDL 语法 / 字段类型 | SQL 解析器、建表时的引擎校验 | 建表失败，问题立刻暴露，代价最低 |
| 命名规范 / 表名前缀（§4.2） | 静态检查规则（lint） | 规范漂移，靠评审补，属于治理债 |
| 粒度声明（一行代表什么） | **只能靠人**：业务过程 + 建模评审 | 事实表混粒度，同一指标两种结果 |
| SCD Type 选择 | **只能靠人**：业务对历史的需求 | 要么丢历史，要么事实表膨胀 |
| 一致性维度划分 | **只能靠人**：跨业务过程协商 | 维度共享不当，口径冲突 |
| 分区键与分桶策略 | 部分可静态检查（有没有声明分区） | 大表全表扫描，成本问题延后爆发 |
| 度量命名与单位（§4.2） | lint + 建模评审 | 度量含义不明，下游重复建设 |

实际落地时最常见的用法不是"让 AI 建模"，而是两件小得多的事：一是**把已有模型反向生成建模文档**——把表结构翻译回自然语言描述，补上缺失的粒度声明与字段含义，顺带把"这张表到底回答什么业务问题"写清楚；二是**生成候选 DDL 供评审时挑**。这两件事的收益真实且风险低，因为它们都不改变决策权。而被宣传得最多的"从一句话需求直接产出可上线的星型模型"，恰恰是最难落地的那种用法：它需要把决策和表达一起外包出去。

```text
NL2Model 的真实分工（生成便宜了，决策没变便宜）
  业务描述 ──► [LLM] ──► 候选 DDL × N
                            │
        ┌───────────────────┴────────────────────┐
        │ 机器能负责：语法、命名规范、字段是否齐全  │
        │ 机器不负责：粒度声明、SCD 选择、          │
        │            一致性维度划分、口径归属       │
        └────────────────────────────────────────┘
  → 评审输入从「一份稿子」变成「N 份候选 + 差异」
  → 粒度若没在生成之前定死：生成越快，返工越早
```

最后提醒一句时序问题：**生成得快，不等于建模快**。§4.1 的 8 步里，生成只覆盖第 6、7 步；前面 5 步（业务过程识别、粒度声明、识别维度、识别度量、选择事实表类型）一步都没省。把生成速度当成立项指标，会得到"产出很多表、但没人敢用"的结果——它的下一步就落在本章 §3.5 反模式表的「事实表粒度混乱」那一行：粒度没在生成之前定死，生成出来的表越多，"同一指标两种结果"的面积越大。

#### 5.2.2 语义层：把度量从报表里搬出来

- **旧做法与它的卡点**：旧做法是度量写在每张报表里——BI 语义模型的 SQL 里一份、ETL 脚本里一份、指标平台配置里一份。卡点不是"重复"，而是**重复之间没有一致性约束**：同一个"复购率"在五个地方各有实现，没有一处在语义上是权威的。这正是 §1.2 那条"今天的口径对不上昨天的报表"的成因。
- **AI 改变了什么机制**：语义层把"度量定义"从**报表的产物**提升为**平台的一等资产**，消费方随之从"人看报表"扩展到"机器取数"。机制上它**改变了接口边界**：Agent 不再需要猜表名和口径，它调用的是一组有名字、有 Owner、有定义的度量。
- **由此得到的**：因为口径的定义位置从"每张报表内部"上移到"一处分层定义"，所以口径变更第一次有了**一个**可以改的地方，且 BI、API、Agent 消费的是同一份定义。这不是让 BI 更好用，而是让"机器消费"这件事有接口可调。
- **由此付出的**：第一，多出一层**必须与物理模型同步的状态**——语义层里的定义与物理表之间没有数据库级约束，漂移时不报错，只会算错，这类故障是静默的。第二，**供应商锁定**：各家语义层的定义文件互不兼容（见 5.1 表第 2 行），迁移成本真实存在。第三，是一次**权力转移**：口径的权威从"报表 Owner"转到"语义层 Owner"，这件事往往比技术改造更难推动。
- **证据与来源**：dbt Semantic Layer、Cube、LookML 的文档与各自的指标定义规范【公开，2023-2025 年间各实现并存】；跨厂商的语义定义互操作方向已有公开倡议（2025 年前后发起的 Open Semantic Interchange 一类，其发起方、成员与规范文本的状态请以该倡议官方页面为准）【公开】——本节不把它当成已发布标准，判定方法是看各厂商 release note 里是否宣布支持导入 / 导出他方格式的定义文件。**第三方独立生产案例在本节无公开可核验来源，因此不给 L1。**
- **成熟度**：**L2**。判据：实现可用、有公开生态，但接口未统一、缺独立第三方复盘。可以试点，不要把它设成取数链路的单点依赖。

度量定义本身的样子（示意，具体字段名以你所选实现的文档为准）：

```yaml
# 语义层里的度量定义：一处定义，BI / API / Agent 共用
metric: trade_order_paid_cnt          # 度量名：机器调用的入口
owner:  trade-analytics               # Owner：口径出问题时找谁
definition: 统计已支付订单数           # 一句话口径，进检索
source:  fact_order                   # 引用的物理表（本节 §4.1 的产物）
filter:  order_status = 'PAID'        # 口径里的过滤条件
grain:   [1d, 1h]                     # 支持的汇总粒度
# → 关键不在 YAML 长什么样，而在「口径只有这一份」
```

判断一个语义层能不能用，问三个问题就够了：**能不能表达你的不可加度量（比率、去重计数）？能不能给每个度量指定 Owner？改一处定义，下游是自动跟着变还是各改各的？** 第三个问题答不好的，本质仍是一批分散的定义，只是换了存放位置。

还有一个经常被忽略的代价：**语义层一旦成为唯一入口，它的可用性就变成取数链路的可用性**。物理表挂了可以换表，语义层挂了没有替代路径——除非你允许一部分人退回裸表写 SQL，而那正好会重新制造口径分裂。所以引入语义层时，"降级路径是什么"这个决定，比选哪家实现更重要。切换任何一套语义层实现，要重做的工作大致如下（这也是把"供应商锁定"从形容词变成清单的方法）：

| 切换语义层要重做什么 | 说明 |
| --- | --- |
| 度量定义文件 | **全部重写**：各实现的定义格式不同，没有通用转换器 |
| 权限与可见范围 | 重新映射：哪些人能看哪些度量，要按新实现的模型重建一遍 |
| 下游消费方 | BI 语义模型、数据 API、Agent 的调用方式各自改一遍 |
| 口径回归验证 | 逐度量比对切换前后的结果，这一步不能省，也最耗时 |
| 时间粒度与刷新语义 | 重新定义：增量方式、时区、截止时间在不同实现里含义不同 |
| 度量到字段的血缘 | 重新采集一次，否则影响面分析会在语义层这里断链 |
| 度量的默认时间口径 | 重新确认：自然月还是滚动窗口、截止到哪天，各家默认值不同 |
| 缓存与预聚合 | 重新配置：切换后原来的预聚合结果不再适用 |

这张表之外还要补一句：语义层与"指标平台"不是同一个东西，尽管两者都管口径。指标平台通常还管指标的生产（调度、加工、物化），语义层只管定义与消费。**把两者混为一谈是选型时常犯的错**——如果你的痛点是"口径分裂"，你需要的是定义集中；如果你的痛点是"指标算不出来"，那是生产链路的问题，上语义层解决不了。

把这张表放回 5.1 的判据里看，就明白语义层为什么是 L2 而不是 L1：**它的能力已经可用，但它没有稳定的接口边界**——定义文件格式、权限模型、消费方式三样都不通用。一个方向只要"换实现就得重写定义"，它在架构上就还处在可试点阶段，把它设成唯一入口是要付代价的。

#### 5.2.3 语义化维度与向量化：把上下文塞进向量空间

- **旧做法与它的卡点**：旧做法里维度的消费方式是**符号匹配**（`WHERE age BETWEEN 30 AND 40 AND gender='F'`）。卡点在于业务提问经常给不出字段名、只给得出描述——"高价值客户""iPhone 用户"这类词必须先被人翻译成字段条件，而翻译动作是人力的、不可复用的，并且会随提问者变化。
- **AI 改变了什么机制**：给维度属性加 embedding 列，把匹配从**符号等值**换成**向量近似**；配套的是事实行向量嵌入（相似订单检索）与把维度建成图节点、事实建成边（GraphRAG 式多跳推理）。机制上是**把人工判断换成统计判断**。
- **由此得到的**：因为匹配从符号等价放宽到向量邻域，所以"不知道字段名也能命中"第一次成为可能——这是自然语言取数在维度侧的入口。但要看清这个"得到"的边界：它解决的是**找到**，不是**算对**。
- **由此付出的**：三项真实代价。一是**第二份状态**：embedding 是同一属性在主表之外的另一种表示，主表更新后需要增量重算，不一致时不报错、只让检索结果慢慢偏离。二是**新的成本项**：向量列与索引随维度行数增长，一张几十个属性的宽维度表逐列向量化会成倍放大存储与写入开销【经验：随列数与行数近似线性放大，具体倍数取决于维度模型与压缩方式】。三是**可解释性下降**：近似匹配给不出"为什么命中这一条"的确定答案，而在口径场景里，可解释性比召回率更重要。
- **证据与来源**：GraphRAG 方向有可公开核验的文献（Microsoft Research 关于 GraphRAG 的公开论文与博客，2024）【公开】；语义化维度本身以厂商愿景与演示为主，**无第三方生产案例、无 embedding 维护责任的公开约定，属 L3**。
- **成熟度**：**L3**。判据：仅论文 / 演示 / 愿景，缺接口约定与生产案例。记录即可，不要在维度表里预留 embedding 列。

GraphRAG 那一路还有一层额外代价值得单说：图构建本身要花钱（抽取实体与关系需要模型调用与人工校验），而图的维护成本不随查询量下降、只随数据量上升。更麻烦的是**它的错误形态**——图里少了一条边，多跳推理就会给出一个自信但错误的答案，而这个错误只在拿它做决策时才会暴露。把它和"多粒度汇总不串口径"（L1 的一致性维度 + 代理键）放在一起看，取舍就很清楚：**确定性的入口继续用旧接口，概率性的入口只用来找线索。**

把"找到"和"算对"分开看，这两件事的成熟度差得很远：

| 能力 | 靠什么实现 | 属于哪条机制 | 现状 |
| --- | --- | --- | --- |
| 用描述找到候选维度成员 | 向量近似匹配 | 人工判断 → 统计判断 | L3：无生产案例，缺维护约定 |
| "这笔订单和哪些订单相似" | 事实行向量嵌入 | 人工判断 → 统计判断 | L3：更新成本账缺失 |
| "这批客户为什么流失" | 图结构多跳（维度作节点、事实作边） | 接口边界变化（图查询） | L3：论文承认为开放问题 |
| **算对一个指标** | 语义层的命名度量（5.2.2） | 接口边界变化 | L2：可用，但依赖定义一致性 |
| **多粒度汇总不串口径** | 一致性维度 + 代理键（§4.2） | **没有变化** | L1：旧的接口至今是唯一稳的 |

事实行向量嵌入还有一个容易被低估的问题：**事实表是持续增长的，而向量索引的维护成本不是**。维度表可以每天全量重刷（它相对小），事实表不行。于是"哪些行需要重算 embedding"本身成了一个需要规则的问题（按分区增量、按变更捕获），而这条规则一旦漏掉一部分行，检索结果就会出现"旧数据永远搜不到"的静默缺失——这比"搜错"更难发现，因为它不改变任何已有结果，只是让一部分数据从结果里消失。

```text
语义化维度的第二份状态（谁维护它？）
  维度主表 dim_user（唯一权威）       向量列 / 向量索引（派生表示）
    user_key, city, age, level   ──►   embedding(user_key)
        │                                   │
        │  SCD Type 2 产生新版本            │  需要增量重算
        │  （历史行仍然存在）               │  需要漂移检测
        ▼                                   ▼
   旧版本行仍被查询命中 ──────────► 旧 embedding 仍留在索引里？
  ────────────────────────────────────────────────────
  两者一旦不同步：不报错、不告警，
  只是检索结果慢慢偏离事实——
  因此在有人认领这份维护责任之前，
  把 embedding 放进一致性维度表是纯风险
```

#### 5.2.4 Agent 驱动的模型演化：从"生成脚本"退回到"该不该改"

- **旧做法与它的卡点**：旧做法是业务变更 → 建模师人工判断影响面 → 手写 migration。卡点分两段：判断影响面靠血缘，而血缘本身要先有；判完之后，migration 脚本仍是手写、手测。真正的稀缺资源不是写脚本的时间，而是**"这次变更会影响谁"这个判断的可靠性**。
- **AI 改变了什么机制**：LLM 让"变更意图 → migration 脚本"这一步可以被生成。**但它改变的是脚本的生产方式，不是变更的决策权。**
- **由此得到的**：因为脚本生成的边际成本下降，所以"每个变更都附带一份迁移脚本 + 一份影响面说明"这件事在形式上可以装配起来——这对变更留痕和评审是有价值的。
- **由此付出的**：新增一类故障模式：**自动化把不该做的变更做得更快**。Agent 产出的脚本语法对、影响面也列了，但它不对"这个口径该不该改"负责，而恰恰是后者决定了这次变更的代价。此外，若生成的 migration 直接进流水线而没有门禁，事故会在比人工更短的时间内放大。
- **证据与来源**：**无公开可核验的生产案例，属 L3。** 判定方法：找一份第三方公开材料，说明"Agent 生成的 migration 在发布门禁上被自动评估过影响面"——本节找不到，因此不写成事实。
- **成熟度**：**L3**。判据：仅演示与产品愿景。先做 §4.2 要求的"每个事实 / 维度表必须有 Owner、血缘、上下游依赖"，这一步的收益远大于引入 Agent。

这里有一个容易倒置的次序：**影响面分析的可靠性与血缘的采集方式直接相关**。人工登记的血缘三个月就会过期，靠它算出来的影响面比没有更危险，因为它给的是错误的信心。所以"Agent 生成迁移脚本"这件事能不能做，先决条件不是模型能力，而是**你的血缘是自动采集的还是人工登记的**——后者的情况下，生成的脚本会建立在一张已经过期的关系图上。这条判断标准与横切章的血缘体系完全一致。

这条方向的前置条件最好写成一张责任表，免得把"生成"误当成"负责"：

| 环节 | 谁做 | 做砸了谁负责 |
| --- | --- | --- |
| 判断变更该不该做 | 业务方 + 建模 Owner | 业务方与 Owner，**不可能是模型** |
| 枚举受影响的下游 | 血缘服务（自动采集优先） | 血缘的覆盖与新鲜度由平台 Owner 负责 |
| 生成 migration 脚本 | LLM 生成候选 | 提交变更的人（生成结果不能免责） |
| 判定能否合并 | 发布门禁（影响面超阈值阻断） | 门禁规则的定义者，不是 Agent |
| 生成一份"变更说明"给下游 | LLM 生成草稿 | 变更提交人——草稿发出去就代表你认账 |
| 上线后回归 | 数据质量校验 + 下游反馈 | 变更提交人 |

还有一个更根本的追问：**"模型演化"的难点从来不是脚本，而是版本管理**。同一张维度表在三个月里可能经历多次 SCD 策略调整，每次调整都会让一批历史行的语义发生变化。生成脚本解决的是"怎么写"，而"那批历史行按哪一版语义解读"没有任何生成式工具能替你决定——这件事只能靠建模文档与评审记录，也就是 §4.2 里那条最不"智能"的要求。

### 5.3 与本主题既有栈的接口在哪

本节不写"与 X 结合"。接口要看三件事：谁调用谁、数据以什么形态穿过边界、失败时谁负责。维度建模这一侧有个特殊性——**它的产物（事实表、维度表、度量定义）是下游所有能力的地基**，所以接口一旦定错，错误会沿着建模 → 开发 → 治理 → 消费一路传下去，而不会在边界上停住。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 语义层 ↔ 物理模型（dbt 模型 / 数仓表） | 定义文件引用表名与字段名，**无数据库级外键约束** | 语义层 Owner（漂移是静默算错，不由调度报错） | L2：可用，但需要人工建立"改表必须同步改定义"的评审规则 |
| Agent ↔ 目录 / 血缘服务 | 元数据 API / 事件，返回实体与字段级血缘 | **调用方（Agent 的使用团队）**——目录只保证"记录了什么"，不保证"记录是对的" | L2：目录侧能力成熟，Agent 消费侧的失败归责尚无惯例 |
| NL 查询 ↔ 语义层 vs 裸表 | 前者调用命名度量，后者直接生成 SQL | 走语义层：定义 Owner；走裸表：**提问者自己** | L2：两条路都能走，选语义层是为了把责任落到人身上 |
| 维度 embedding ↔ 维度主表 | 向量列 + 索引，需增量重算与漂移检测 | **无人负责**（现状下没有 Owner 约定） | L3：正因为找不到责任人，才不该现在落地 |
| 建模评审 ↔ 生成式工具 | 候选 DDL / 定义文件进评审流程，人做决策 | 评审人（工具不承担决策责任） | L2：流程上可行，但没有第三方公开的规模化做法 |
| 一致性维度 ↔ 多个事实表 | §4.2 的代理键体系（`HASH(business_key)` 一类） | 维度 Owner，跨事实表口径冲突由建模评审拦 | L1：这仍是本节唯一稳定的接口约定，AI 没有改变它 |
| 自然语言问答 ↔ BI 前端 | 前端把提问转成对度量的调用，返回结果与所用口径 | 前端团队；口径本身归定义 Owner | L2：可用，但前端要能显示"这次答的是哪个口径" |
| 建模文档 ↔ 生成式工具 | 文档里的粒度声明与字段含义作为生成输入 | 建模 Owner——**输入脏，输出必脏** | L2：文档质量直接决定生成质量，多数团队这一步还没做 |

这张表有一个共同点：**所有 L2/L3 接口的失败责任，都落在"人"这一侧**——定义 Owner、调用方团队、提问者自己。这不是巧合，而是因为 AI 组件本身没有承担责任的资格：它不签署变更、不持有口径、不接受复盘。所以引入任何一个 AI 组件时，先问的不是"它能做什么"，而是"它出错时谁签字"。

用这张表做接口审查还有一个便宜的好处：**每一行都可以写成一条可执行的测试**。比如"语义层 ↔ 物理模型"这一行，对应的测试是"改掉一个被度量引用的字段类型，看会不会有人被拦下来"；"维度 embedding ↔ 维度主表"这一行，对应的测试是"问一句：如果这个向量索引停更一周，谁会先发现"。答不上来测试答案的行，就是当前架构里没人负责的那一段边界。

**第三方生产案例**

- **本节未找到可核验的第三方（非厂商）公开生产案例**：能指名到公司、场景与时间的材料基本来自厂商自述。这正是 5.1 里除执行层外全部不给 L1 的直接原因——不是怀疑能力，而是没有独立证据。
- 判定一份材料够不够格当"第三方生产案例"，看四件事：**公司名**（不是"某大型银行"）、**时间**、**部署规模**（多少张表、多少个度量）、**失败教训**。四条缺两条以上，就只能算参考性材料，不能作为把某个方向升级到 L1 的依据。
- 反过来说，读者若要把某个方向从 L2 升到 L1，路径也是明确的：找一份不是该厂商写的、能指名到公司与时间的材料，并核验它的部署规模与你的场景是否可比。

### 5.5 被过度宣传的部分

**「Agent 能完成大部分维度建模工作，人只做审核」** —— 实际是：Agent 能生成 DDL 草稿，粒度声明、SCD 选择、一致性维度划分这类工作它替代不了。→ 为什么会这样：模型拟合的是"表通常长什么样"，而"这个业务过程的一行代表什么"是**组织决策**，需要跨团队协商，输入根本不是文本而是一组人的共识。→ 什么时候它才会成真：当粒度声明与业务过程清单本身被登记成机器可读资产（而不是留在建模文档里），且生成产物必须穿过带门禁的评审流程——那时"人只做审核"才成立，但审核的仍然是人。

**「维度加 embedding 列，自然语言查询就能直接命中」** —— 实际是：embedding 解决的是"描述相似"，解决不了"口径正确"。→ 为什么会这样：向量邻域是近似，不是等价；"30-40 岁女性用户"命中一组相似描述，不等于命中业务上认可的那批用户。写进维度表的 embedding 是对同一属性的第二种表示，它带来的是**第二份需要与主表同步的状态**。→ 什么时候它才会成真：当 embedding 的增量更新、漂移检测、与主表一致性都有了 Owner 和例行作业，而不再是一次性刷数。

**「新一代引擎已支持海量向量毫秒级检索」** —— 实际是：这类声称缺了条件限定语就没有技术含义。→ 为什么会这样：向量检索延迟同时取决于数据量、维度、索引类型、召回率目标与硬件，五个参数任一变化结论就变；把厂商营销页的措辞当成技术事实，是本节最容易犯的错。→ 判定方法：向对方要**带条件的 benchmark**——多少行、多少维、召回率取多少、什么硬件、什么索引；要不到条件，就把这条记为 L3。→ 什么时候它才会成真：当这类性能声称在文档里普遍附带条件列（数据量 / 维度 / 召回率 / 硬件），而不是只留在首页的一句话里。

顺带一条同类的错位：**Iceberg / Paimon 这类表格式进展与 AI 没有直接关系**。它们解决的是存储层的开放性与演进能力（主键约束、删除向量、schema evolution 之类），属于"让湖仓更好用"，不该被塞进"AI 进展"表里充数。把它们和 NL2Model 并列，只会让读者误以为它们之间存在依赖关系。

这三条说法有一个共同结构：**它们都把"生成"的能力当成了"判断"的能力**。生成 DDL、生成嵌入、生成检索结果都是可自动化的；而"这个粒度对不对""这批用户算不算""这次检索准不准"，每一项都需要一个能承担后果的主体。读到任何一条宣称时，先找它的主语是谁——主语是"模型"，那这条宣称基本都还需要再降一格。

### 5.6 未来 3–5 年：可证伪的预测

预测必须能被推翻，所以下面每条都写成「预测 + 会成真的信号 + 会证伪的信号」。写不出信号的方向本节不写——"数据架构会越来越智能"这类句子永远正确，因而是零信息。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| **口径定义会从报表里彻底搬出来，语义层成为取数链路的必经接口** | 新上线的取数应用不再直连物理表，而是调命名度量；口径事故的复盘结论开始指向"定义文件"而不是"某张报表" | 三年后多数团队仍在报表 SQL 里各写一份口径，语义层只被个别团队使用 |
| **语义化维度不会进主表** | embedding 以独立索引 / 独立表的形式存在（与维度主表分离），并配有增量重算作业与 Owner | 出现把 embedding 列直接加进一致性维度表并纳入 SCD 的主流做法 |
| **NL2Model 停留在"生成草稿"这一格** | 各厂商能力说明持续强调"建议 / 辅助"，评审环节没有被移除；企业仍在评审阶段拦下相当比例的生成结果 | 出现公开材料，说明某企业把生成 DDL 直接进发布流程且未设评审门禁，并且没有出现口径事故 |
| **"AI 原生建模"不会改变建模的方法论骨架** | 事实表 / 维度表 / 粒度声明 / 一致性维度这些概念继续出现在新工具的文档里，只是换了呈现形式 | 出现被广泛采用的新范式，明确不再区分事实与维度，并给出可核验的替代机制 |

四条预测共享同一个方向：**发生变化的是生产这些产物的成本，不是判断这些产物对错的机制**。如果三年后回看发现相反——评审环节被整体移除而事故率没有上升——那就是本节判断错了，而这个错法是有信号的（见上表第三行）。

本节刻意不预测"AI 会不会取代建模师"。这个问题的答案取决于组织愿意把决策权交给谁，而不取决于模型能力，它不是可证伪的技术判断——凡是不给出证伪信号的预测，写进书里只是情绪。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| **刚建第一个数据集市（100+ 表）** | §4.1 的 8 步流程走完，粒度声明写进建模文档第一行；把表名前缀与代理键规范（§4.2）定死 | Copilot 生成 DDL 的**评审通过率**；一致性维度是否被真正复用 | 不要为了"AI 就绪"在维度表里预留 embedding 列；不要在粒度没定死前引入生成式建模 |
| **已有数仓、口径开始分裂** | 把度量从报表里搬进语义层或指标平台，给每个度量指定 Owner | 语义层与物理表的漂移事件数量；跨厂商语义定义互操作规范的落地状态 | 不要把语义层设为唯一取数入口后再做迁移——迁移成本会高于预期，且中途没有退路 |
| **在评估自然语言取数** | 限定在"已有语义层覆盖的域"内试点；把失败样本按"找不到"与"算不对"分类统计 | BIRD 一类公开基准的差距收敛速度；厂商是否公布带条件的性能口径 | 不要在裸表上直接做自然语言取数——那不是模型问题，是口径问题 |
| **打算用 Agent 做 schema 变更** | 先把影响面查询做成日常动作（血缘 + 字段级，参考横切章的血缘体系），再谈自动生成脚本 | 是否出现第三方公开的"Agent 生成迁移 + 门禁自动评估"生产案例 | 不要让生成的 migration 绕过评审直进发布流水线——这是把事故加速 |
| **采购 / 选平台** | 把"内置 AI"当**平台选型项**评估，不当技术方向评估；白纸黑字问清 release note 入口与区域可用性 | 平台侧 AI 能力的跨云可移植性 | 不要为"AI 原生"这个标签支付溢价；本节唯一处在 L1 的**演进方向**（列存与向量化执行）不靠标签获得 |
| **团队还没人管元数据** | 先给每张事实 / 维度表落实 Owner、血缘、上下游依赖与刷新策略（§4.2 血缘与元数据一条） | 血缘是自动采集的还是人工登记的，覆盖率有没有持续下降 | 不要先上 AI 元数据补全：在没人负责的元数据上做自动补全，只会更快地生产错的元数据 |
| **已经在裸表上做自然语言取数** | 回补语义层覆盖：把高频问题涉及的度量先集中定义 | 失败样本里"算不对"的占比是否下降 | 不要继续扩大自然语言取数的表覆盖范围——范围越大，口径债越多 |
| **业务方开始自建报表** | 先把口径定义与 Owner 制度落地，再开放自助 | 自助报表与权威口径的一致率 | 不要为自助分析单独复制一套口径定义，那是把今天的问题复制成明天的问题 |

这张表的每一行都指向同一件事：**本节所有建议的动作，成本都落在"把决定写成明文并指定负责人"上**，没有一个落在"引入某个 AI 组件"上。这不是保守，而是因为判断 AI 值不值得用，取决于你手上有没有可核验的元数据与口径——有，AI 是放大器；没有，AI 是加速器，加速的还是错的那条路。

"明确不要做"这一列的共同点是：**它们都是在为一条尚未成熟的机制提前支付架构成本**。预留 embedding 列、为"AI 原生"付溢价、在裸表上做自然语言取数、让生成的迁移绕过评审——这几件事今天做的收益是假设的，代价却是当期的，而且其中几项（预留列、绕过评审）会在一年后变成很难拆掉的结构。

### 5.8 小结

> 本节小结：AI 在维度建模上真正改变的是**一条**机制——把"自然语言 → 结构化产物"（DDL、度量定义、迁移脚本）的**边际生成成本**压到接近零，因此"多出几版候选再挑""每个度量都集中定义""每次变更都附影响面说明"这些旧做法下不划算的事第一次划算。它没有改变的是**决策与责任**：粒度声明、SCD 选择、一致性维度划分、口径归属、变更该不该做，仍然是组织决策，且必须落到具体的人和具体的评审环节上——所以本节列的**演进方向**里，除执行层的列存与向量化外，没有一项够得上 L1（5.2.3 与 5.3 里标为 L1 的一致性维度 + 代理键是未变化的基线能力，不是本节新列的方向）。
>
> 💡 **思考锚点**：5.3 那张接口表里，你现在的架构能跑通几条测试——「改掉一个被度量引用的字段类型，会不会被拦下」「向量索引停更一周，谁会先发现」？答不上测试答案的行，就是你还没指定 Owner 的边界，你打算先补哪一行？
