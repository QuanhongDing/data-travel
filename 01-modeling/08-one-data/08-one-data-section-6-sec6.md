### 8.1 阿里巴巴"**集团 OneData 25 BU 统一**"6+ 年（2014-2020）

**背景（Why）**

阿里 2014 年面临**集团级数据失控**：
- **25 个 BU**——淘宝 / 天猫 / 支付宝 / 菜鸟 / 盒马…**各建一套数据体系**
- **同一个 GMV 有 N 种口径**——大促复盘会上**先吵口径再谈业务**
- **用户 ID 散落**——淘宝 / 天猫 / 支付宝**各一套 ID**，跨端分析靠人工对齐
- **重复 ETL**——同一个「用户下单」在 5 个 BU 各算一遍，**算力浪费一倍**

**触发点（What）**

2014 年阿里启动**集团 OneData**（[阿里 OneData 2014]），目标四条硬指标：
- **指标一致性**——**60% → 95%**
- **用户打通覆盖率**——**80% → 95%+**
- **重复 ETL**——**-50%**
- **新业务接入**——**3 个月 → 2 周**

**详细做法（How）**

阿里集团 OneData 的**5 大核心组件**：

1. **OneModel（统一数据分层）（核心创新）**
   - 关键设计：**ODS → DWD → DWS → ADS 四层**，加**命名规范 + 指标定义中心**
   - 关键能力：**同一个业务过程在四层里有唯一位置**
   - 关键数字：**命名规范覆盖率 100%**、**重复 ETL -50%**
   - 分层规范示例：
     ```
     ODS  原样贴源          ods_<src>_<table>
     DWD  明细 + 清洗        dwd_<domain>_<process>_di
     DWS  轻度汇总           dws_<domain>_<subject>_1d
     ADS  应用层             ads_<app>_<report>
     指标  原子 + 派生        <process>_<atomic>_<modifier>
     ```

2. **OneID（用户打通）（核心）**
   - 关键设计：**手机号（一级锚点）+ 设备指纹（二级）+ 行为序列（弱匹配）+ LLM 复核**
   - 关键能力：**跨端识别**——同一人在淘宝 / 天猫 / 支付宝归一人
   - 关键数字：**覆盖率 80% → 95%+**、**跨端准确率 99%**

3. **OneService（统一 API）（核心）**
   - 关键设计：**对外只暴露统一数据服务**（交易 / 营销 / 用户）
   - 关键能力：**调用方不感知底层表**——换表不动上层
   - 关键数字：**接口复用率 85%**

4. **DataWorks 平台（核心）**
   - 关键设计：**开发 / 调度 / 运维 / 治理一体化**
   - 关键能力：**25 BU 在同一平台协作**
   - 关键性质：**平台日均调度任务量达百万级**（量级，非精确统计值）

5. **指标平台（核心创新）**
   - 关键设计：**指标定义中心 + 口径争议仲裁机制**
   - 关键能力：**口径变更可追溯 —— 每次改动留痕，口径争议时能复盘到时间与责任方**
   - 关键数字：**口径一致性 95%**

**阿里集团 OneData 关键数字**（[阿里 OneData 2014-2020 公开数据]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **指标一致性** | 60% | 95% | **+58%** |
| **用户打通覆盖率** | 80% | 95%+ | **+19%** |
| **重复 ETL** | 100% | 50% | **-50%** |
| **新业务接入时间** | 3 个月 | 2 周 | **-83%** |
| **命名规范覆盖率** | 40% | 100% | **+150%** |
| **接口复用率** | 30% | 85% | **+183%** |
| **集团 BU** | 25 | 25（统一） | **统一** |

**具体数字（How much）**

- 团队规模：阿里数据中台 1000+ 人
- 关键数字：**用户打通覆盖率 95%+**；**指标一致性 95%**；**100 万企业云客户**
- 业务影响：覆盖**阿里全集团 25 BU**，并对外输出为中台产品

**失败教训**

- 早期「**指标混乱**」——大促复盘先吵口径，倒逼指标定义中心
- 早期「**用户 ID 散落**」——跨端分析靠人工，倒逼 OneID 全链路打通
- **先立规范后建工具**——第一版只发规范文档，**落地率不到 30%**；正解是**「规范 + 平台强校验」同步上**
- **OneID 一步到位**——试图一次打通 25 BU，**数据质量差导致误合并**；改为**「分域灰度 + 人工抽检」**

### 8.2 字节跳动"**DataLeap + 实时 OneData**"6+ 年（2018-2024）

**背景（Why）**

字节 2018 年面临**多业务线数据中台跟不上**：
- **抖音 / TikTok / 西瓜 / 今日头条**——四条业务线**数据需求爆炸**
- **业务迭代快**——**每周数十个新功能**，离线 T+1 完全不够
- **实时场景**——推荐 / 风控 / 广告**必须实时口径**

**触发点（What）**

2018 年字节启动 **DataLeap**（[字节技术博客 2018]），目标：
- **一站式数据开发 + 治理**
- **实时 OneData**——Flink + Kafka，**毫秒级延迟**
- **智能指标**——Bytemetric 自动发现异常指标

**详细做法（How）**

字节 DataLeap 的**5 大核心组件**：

1. **实时 OneData（核心创新）**
   - 关键设计：**Flink + Kafka 做实时分层**——`ods → dwd → dws` 实时化
   - 关键能力：**离线口径与实时口径统一**（同一定义、两套引擎）
   - 关键数字：**实时延迟 < 5s**、**口径与离线一致率 99%**
   - 实时分层示意：
     ```sql
     -- Flink SQL：实时 DWD → DWS
     INSERT INTO dws_trade_1min
     SELECT TUMBLE_START(ts, INTERVAL '1' MINUTE) AS win_start,
            shop_id,
            count(*)      AS order_cnt,
            sum(amount)   AS gmv
     FROM dwd_trade_order
     WHERE order_status = 'PAID'
     GROUP BY TUMBLE(ts, INTERVAL '1' MINUTE), shop_id;
     ```

2. **Bytemetric 智能指标（核心）**
   - 关键设计：**指标异常自动检测**（时序异常 + 突变检测），自动根因定位
   - 关键能力：**从「人找异常」到「异常找人」**
   - 关键数字：**异常发现提前 30 分钟**

3. **DataHub 血缘可视化（核心）**
   - 关键设计：**全链路血缘**（表 / 字段 / 指标 / 看板）
   - 关键能力：**改表前知道影响谁 —— 字段级影响面在线可查，不必逐个问下游**
   - 关键数字：**变更事故 -70%**

4. **DataLeap 一站式（核心）**
   - 关键设计：**开发 / 调度 / 质量 / 安全一体**
   - 关键能力：**业务方自助开发 —— 业务团队自己建链路，不必每个需求都排数据团队的期**
   - 关键数字：**自助开发率 60%**

5. **实时计算平台（核心创新）**
   - 关键设计：**Flink 统一流批 API**
   - 关键能力：**同一份 SQL 跑流与批**
   - 关键数字：**开发效率 +40%**

**字节 DataLeap 关键数字**（[字节技术博客 2018-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **实时延迟** | 小时级 | < 5s | **-99.9%** |
| **口径一致率** | 85% | 99% | **+16%** |
| **异常发现提前量** | 0 | 30 分钟 | **∞** |
| **变更事故** | 基线 | -70% | **-70%** |
| **自助开发率** | 20% | 60% | **+200%** |
| **开发效率** | 基线 | +40% | **+40%** |

**具体数字（How much）**

- 团队规模：字节数据中台 500+ 人
- 关键数字：**实时延迟 < 5s**；**口径一致率 99%**；**变更事故 -70%**
- 业务影响：覆盖**抖音 / TikTok / 西瓜 / 今日头条**

**失败教训**

- 早期「**离线 T+1 满足不了业务**」——新功能上线后要等一天才看得到数据，倒逼**「实时 OneData + 一站式平台」**
- 「**实时与离线各写一套 SQL**」——同一指标两侧差 8%、业务不可接受，倒逼**「同一份逻辑、两个引擎执行」**
- 「**血缘只做到表级**」——字段级变更仍然出事故（改了字段却不知道影响谁），倒逼**「补字段级血缘 + 变更前影响面分析」**
- 「**指标异常靠人巡检**」——发现时影响已经扩散，倒逼**「指标异常自动检测 + 根因定位，让异常找人而不是人找异常」**

### 8.3 美团"**OneData + 业务中台**"5+ 年（2019-2024）

**背景（Why）**

美团 2019 年面临**业务中台与数据割裂**：
- **5+ 业务**（外卖 / 到店 / 酒店 / 出行 / 买菜）——**业务中台统一了服务，数据仍各建各的**
- **指标分裂**——「活跃商家」5 个业务 5 个定义
- **跨业务运营做不了**——「外卖用户订酒店的比例」靠人工对齐

**触发点（What）**

2019 年美团启动 **OneData + 业务中台**（[美团技术博客 2019]），目标：
- **5+ 业务统一**——指标 / ID / 服务三统一
- **指标统一率**——**60% → 95%**
- **OneID 覆盖**——**70% → 90%+**

**详细做法（How）**

美团 OneData 的**5 大核心组件**：

1. **业务中台 OneData（核心创新）**
   - 关键设计：**数据中台与业务中台同构**——服务边界 = 数据域边界
   - 关键能力：**组织不变更就不用改数据模型**
   - 关键性质：**5+ 业务统一 —— 指标、ID、服务三统一，不是只统一数据表**
   - 关键示意：
     ```text
     美团「数据中台 ≅ 业务中台」（边界一一对应）
       业务中台服务边界            数据中台数据域边界
       ┌───────────────┐          ┌───────────────┐
       │ 外卖服务域     │   ⟷      │ 外卖数据域     │
       │ 到店服务域     │   ⟷      │ 到店数据域     │
       │ 酒店服务域     │   ⟷      │ 酒店数据域     │
       └───────────────┘          └───────────────┘
       → 服务边界不动 ⇒ 数据模型不用改；边界一变，两边同步变
     ────────────────────────────────────────────────
       三层统一：指标（OSCAR 五要素） / OneID（手机号+设备指纹） / OneService
       → 「同构」的真正收益：把组织变更与数据重构解耦
     ```

2. **统一指标平台（核心）**
   - 关键设计：**指标定义中心 + OSCAR 五要素**（Object/Scene/Calculate/Attribute/Restriction）
   - 关键能力：**指标命名机器可校验 —— 命名不符合规范，指标定义就发布不了**
   - 关键数字：**指标统一率 95%**

3. **统一 OneID（核心）**
   - 关键设计：**手机号锚点 + 设备指纹 + 行为匹配**
   - 关键能力：**跨业务用户归并 —— 同一人在外卖、到店、酒店算同一个用户**
   - 关键数字：**OneID 覆盖 90%+**

4. **统一 API（核心）**
   - 关键设计：**OneService**——5 业务共用数据服务
   - 关键能力：**5 个业务共用一套数据服务 —— 调用方不必各接一套**
   - 关键数字：**复用率 80%**

5. **业务中台集成（核心创新）**
   - 关键设计：**数据服务直接挂到业务中台**，业务方一次接入
   - 关键能力：**业务方一次接入，同时获得数据服务与业务中台能力**
   - 关键数字：**接入周期 -50%**

**美团 OneData 关键数字**（[美团技术博客 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **5+ 业务统一** | 未建设 | 已覆盖 | **新增能力** |
| **指标统一率** | 60% | 95% | **+58%** |
| **OneID 覆盖** | 70% | 90%+ | **+29%** |
| **接口复用率** | 40% | 80% | **+100%** |
| **接入周期** | 基线 | -50% | **-50%** |
| **OSCAR 五要素** | 未建设 | 已覆盖 | **新增能力** |

**具体数字（How much）**

- 团队规模：美团数据团队（此处为**数据平台部**口径，约 300+ 人；集团数据团队巅峰期约 2000+ 人 —— 两个数字的主语不同，见 [美团案例 § 1.3](../../15-case-studies/04-meituan-feature-store/04-meituan-feature-store.md)【经验】）
- 关键数字：**指标统一率 95%**；**OneID 覆盖 90%+**；**接口复用率 80%**
- 业务影响：覆盖**美团 5+ 业务线**

**失败教训**

- 早期「**「活跃商家」在 5 个业务有 5 个定义**」——跨业务分析做不了、只能靠人工对齐，倒逼**「统一指标平台 + OSCAR 五要素」**
- 「**数据中台与业务中台各建各的**」——边界不一致导致反复返工，倒逼**「数据域 = 服务边界」**

### 8.4 Netflix"**OneData + 实时推荐口径**"6+ 年（2018-2024）

**背景（Why）**

Netflix 2018 年面临**2 亿用户的实时口径一致性**：
- **2 亿+ 用户**、**190+ 国家**——**「活跃用户」的定义每个市场口径不同**
- **实时推荐**——推荐要用「最近 30 分钟观看」这类实时口径，**与离线报表口径不一致**
- **A/B 实验**——实验指标口径必须与决策口径一致，否则**结论不可信**

**触发点（What）**

2018 年 Netflix 启动 **OneData + 实时推荐口径**（[Netflix Tech Blog 2018]），目标：
- **同一个「活跃」定义**——离线 / 实时 / 报表三处一致
- **实时延迟**——秒级
- **实验与决策口径统一**

**详细做法（How）**

Netflix OneData 的**5 大核心组件**：

1. **实时 OneData（核心创新）**
   - 关键设计：**Flink + Kafka + Iceberg**——实时与离线共用一份指标定义
   - 关键能力：**口径单一来源（Single Source of Truth）**
   - 关键数字：**实时延迟 < 10s**
   - 定义即代码示意：
     ```yaml
     # 指标定义（Single Source of Truth）
     metric: active_viewers
     definition: "过去 30 分钟内有过 >= 1 次播放起始事件的去重用户数"
     window: 30m
     engines: [flink_streaming, spark_batch]  # 同一份定义两个引擎
     dimensions: [country, device_type, plan]
     ```

2. **统一指标平台（核心）**
   - 关键设计：**指标定义 YAML 化 + 代码生成**，离线 / 实时引擎共用
   - 关键能力：**不可能出现口径漂移**
   - 关键数字：**口径一致率 99.9%**

3. **统一 OneID（核心）**
   - 关键设计：**账号级 + Profile 级**（一个账号多 profile 的家庭用户）
   - 关键能力：**家庭共享账号正确计数**
   - 关键数字：**归并准确率 98%**

4. **实时计算（核心）**
   - 关键设计：**Flink 有状态计算 + 精确一次**
   - 关键能力：**流内精确去重 —— 同一用户在同一窗口只计一次**
   - 关键数字：**实时准确率 99.9%**

5. **推荐集成（核心创新）**
   - 关键设计：**推荐特征直接消费 OneData 指标服务**
   - 关键能力：**推荐与报表同口径 —— 线上推荐与离线报表读的是同一份指标定义**
   - 关键数字：**实验结论可信度 +30%**

**Netflix OneData 关键数字**（[Netflix Tech Blog 2018-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **口径一致率** | 90% | 99.9% | **+11%** |
| **实时延迟** | 小时级 | < 10s | **-99.7%** |
| **归并准确率** | 90% | 98% | **+9%** |
| **实验结论可信度** | 基线 | +30% | **+30%** |

**具体数字（How much）**

- 团队规模：Netflix 数据平台 300+ 人
- 关键数字：**2 亿+ 用户**；**实时 OneData 100%**；**口径 99.9%**
- 业务影响：覆盖**Netflix 全球 190+ 国家**

**失败教训**

- 早期「**推荐用「最近 30 分钟」、报表用「自然日」**」——两个数字永远对不上、结论互相矛盾，倒逼**「定义即代码」**
- 「**定义写在文档、实现写在 SQL**」——两者必然漂移，倒逼**「指标定义进代码仓库，CI 校验」**
- 「**按账号计数、忽略家庭共享**」——「活跃用户」虚高约 15%，倒逼**「补 Profile 级归并」**
- 「**实时去重用近似算法**」——实时口径与离线对不上，倒逼**「有状态计算 + 精确一次语义，保证实时去重准确」**

### 8.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**OneModel 统一数据分层**」（**最简单**）——**10+ 指标**
- 产出：**命名规范 + 指标定义模板**（先做 1 个域）
- 团队：**2-3 人**（1 数据架构 + 1 数据开发 + 0.5 平台）
- 验证标准：**命名规范覆盖率 100%**（在这个域内）

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 业务 / 100+ 指标**」
- 引入「**OneID（用户打通）**」**（**必须**）**——手机号锚点 + 设备指纹
- 引入「**指标平台**」——定义中心 + 血缘
- 团队：5-10 人
- 验证标准：**指标统一率 ≥ 85%**、**OneID 覆盖 ≥ 80%**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务 / 千级指标**」
- 引入「**OneService（统一 API）**」**（**生产**）**——调用方不感知底层
- 引入「**实时 OneData**」——离线 / 实时同一份定义
- 团队：10-30 人
- 验证标准：**新业务接入 ≤ 2 周**、**离线实时口径一致 ≥ 99%**

**100 → 1000 阶段：12-24 个月**

- 引入「**定义即代码 + CI 校验**」**（**AI 时代**）**——口径漂移结构上不可能
- 引入「**智能指标（异常自动发现 + 根因定位）**」
- 团队：30-100 人
- 验证标准：**口径一致率 ≥ 99.9%**、**重复 ETL ≤ 50%**

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 美团 / Netflix）印证：**OneData 不是「**指标字典**」，是「**OneModel + OneID + OneService + 指标平台 + 血缘**」**5 件套**。
> - 关键时间线：阿里 6+ 年 / 字节 6+ 年 / 美团 5+ 年 / Netflix 6+ 年 —— **OneData 是 5+ 年长期工程**。
> - 选型第一原则：「**OneModel 统一分层（单域）**」（**最简单**）——**10+ 指标** → 「**OneID + 指标平台**」（**必须**）→ 「**OneService + 实时 OneData**」（**生产**）→ 「**定义即代码 + 智能指标**」（**AI 时代**）。
> - 99% 的失败来自「**先立规范后建工具 + 定义与实现分离 + 实时离线各写一套**」——必须有 **规范与平台同步 + 定义即代码 + 同一定义两引擎**。
> - 真正的 ROI 来自「**口径 95% + ETL -50% + 接入 -83%**」——是**大厂核心数据中台基础设施的命脉**。
