## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

一张「组织规模 → 推荐模式」的决策表，会把 OneData 讲成"按公司大小挑一个套餐"。真实的模式选择不是这样发生的：OneModel 用维度建模还是 Data Vault，取决于**源系统表结构一年会改几次**；OneID 用强匹配还是弱匹配，取决于**你手里标识的全量可见性**；OneService 是代理物理表还是真服务，取决于**消费方是人还是应用**。同一家万人公司，这三个问题的答案可以完全不同——它们不是同一道选择题的三个选项，而是三个独立约束各自的解。

所以本节的组织方式是：先立约束，再谈模式。约束在这里不是背景介绍，而是判据——写不出一个模式被什么约束逼出来，就无法判断它什么时候会失效，而模式手册的价值几乎全部在"什么时候会失效"这一栏。

OneData 的三件套（OneModel / OneID / OneService，见主文件 §1.1）本质上是同一个约束在三处的投影：**一个企业只能有一套口径**。而这条约束之所以难，是因为它三个环节的失效方式完全不同——OneModel 的失效是**慢**（回刷成本随时间累积），OneService 的失效是**脆**（上游改名全线故障），OneID 的失效是**错而不报**（两个真人被合并，所有 UV / 复购 / 留存指标一起错，没有任何告警）。三种失效对应三种代价，因此模式不能混用。

下面六条约束是本主题下真正在做决定的东西。前两条（源系统稳定性、标识可获得性）是结构性的，必须最先回答；后四条在实现层面起作用，但每一条都能单独否决一个看起来合理的方案：

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 源系统的稳定性（表结构变更频率） | OneModel 走维度建模还是 Data Vault | 「维度建模够用」——被源系统高频变更推翻：每改一次源表就要回刷一遍历史分区 |
| 标识的可获得性与冲突代价 | OneID 用 C1 强匹配为主，还是要补 C2/C3 | 「有手机号就能打通」——被"覆盖率上限 = 最强标识的可见率"推翻 |
| 消费方的类型（人 / 应用 / 模型） | OneService 是接口契约还是物理表代理 | 「API 就是代理表」——被上游改名时消费方要改的代码量推翻 |
| 口径的变更频率与追责要求 | 指标平台是"定义中心"还是"取数工具" | 「平台能出数就行」——被"平台里的 5 个 GMV"推翻：混乱被固化了 |
| 组织权力结构（有无一把手授权） | 标准是强制门禁还是推荐规范 | 「先建标准再推广」——被业务方抵制推翻，见 3.5 的陷阱 |
| 团队技能与运维能力 | 走 AI 增强（F）还是智能体（G） | 「上了 LLM 就自动治理」——被"没有权威口径可对照"推翻 |

### 3.2 模式逐个拆解（核心节）

以下 7 个小节覆盖原文件列出的全部模式 A–G（含 C 的三个子模式 C1–C3 与 D 的四个子模式 D1–D4）。每个模式严格按「被什么约束逼出来 → 结构 → 为什么有效 → 代价 → 失效点 → 真实使用」写。

#### 3.2.1 模式 A：OneModel 维度建模主导

- **被什么约束逼出来**：业务过程可枚举（下单 / 支付 / 退款 / 发货，主文件 §2.1），且查询侧要在事先不可预知的维度组合上做聚合。约束是"业务过程稳定、查询形态不可预知"，所以模型必须按业务过程切分、按维度拍平。
- **结构**：

```sql
-- OneModel：分层单向流动 + 命名规范强制（主文件 §2.3 方法⑥）
-- 命名：<层级>_<数据域>_<业务过程>_<自定义>.dim/fact/agg
CREATE TABLE dwd_trade_order_di (              -- DWD：一行一订单（业务过程粒度）
  order_id   STRING  COMMENT '订单ID',
  shop_id    STRING  COMMENT '店铺ID',
  buyer_id   STRING  COMMENT '买家标识 → 指向 OneID，不是源系统 UID',
  pay_amt    DECIMAL(18,2) COMMENT '支付金额（原子指标的物理承载）',
  ds         STRING  COMMENT '分区'
);
CREATE TABLE dws_trade_shop_1d (               -- DWS：按主题轻度汇总
  shop_id      STRING,
  pay_amt_1d   DECIMAL(18,2),                  -- 派生指标 M = f(原子, 周期, 修饰)
  buyer_cnt_1d BIGINT,
  ds           STRING
);
-- ADS 面向应用，只引用 DWD/DWS，禁止反向引用（主文件 §2.3 方法③）
```

- **为什么这样设计有效**：因为业务过程被枚举成有限个 DWD 事实表，所以"同一业务过程只有一张明细表"变成一条**可检查的结构约束**——口径冲突从"两个人写了两段 SQL"变成"谁违反了分层纪律"这一可判定的事实；又因为 DWS 只从 DWD 派生，任何指标都能回溯到明细并重算，这就是可重述性。
- **代价**：需要一支拥有公共层的独立团队（Owner 制度落地到人），否则 DWD 会被各业务方各自加列；每个新业务过程要走一遍"过程识别 → 域划分 → 命名评审"；ADS 数量随需求线性增长，它是唯一被允许"一个需求一张表"的层，也正因如此它是规范化程度最低、最容易长出双胞胎表的地方。
- **失效点**：当源系统表结构高频变更（例如每周改字段）时，「模型稳定、一层 JOIN 拿全上下文」会反转成「回刷成本随变更次数累积」——因为 DWD 是源系统的结构化拷贝加清洗，源一变就要重刷历史分区，而分区数随保留时长单调增长。触发条件可操作化为：**一次源变更需要的回刷量（受影响分区数 × 单分区体积）是否超过当天的可用计算窗口**。
- **真实使用**：阿里《大数据之路：阿里巴巴大数据实践》（2017）公开描述了 OneData 的 OneModel 分层与命名规范【公开，2017】；维度建模方法本身出自 Kimball《The Data Warehouse Toolkit》（1996）【公开，1996】。原文件把阿里电商 / 字节电商 / 美团到店列为代表——核验方法：看对方公开的建表规范里是否同时出现 ODS/DWD/DWS/ADS 分层与"域 + 业务过程"的命名骨架【经验】。

#### 3.2.2 模式 B：OneModel Data Vault 主导

- **被什么约束逼出来**：源系统多且各自高频变更，同时要求"源系统解耦"与"任何时点可重述 + 逐条可审计"。约束是"没有哪一个源系统的结构是稳定的"。
- **结构**：

```sql
-- Data Vault：Hub（业务键）+ Link（关系）+ Satellite（属性与历史）
CREATE TABLE hub_customer (            -- 只存键与来源，源系统新增属性不触碰它
  customer_hk STRING NOT NULL,         -- 哈希键
  customer_bk STRING NOT NULL,         -- 业务键（源系统原值）
  load_dts TIMESTAMP, src STRING
);
CREATE TABLE link_customer_account (   -- 关系独立成表，可后加
  link_hk STRING, customer_hk STRING, account_hk STRING,
  load_dts TIMESTAMP, src STRING
);
CREATE TABLE sat_customer_detail (     -- 属性变更 → 追加一行，永不覆盖
  customer_hk STRING, load_dts TIMESTAMP,
  name STRING, risk_level STRING,
  hash_diff STRING,                    -- 让"属性是否变过"变成可比较的值
  src STRING
);
```

- **为什么这样设计有效**：因为只有 Satellite 承载属性且按 `load_dts` 追加，所以任何时点的属性都能重述；因为 Hub / Link 只存键与关系，源系统新增一个属性只影响一个 Satellite，**解耦从一条纪律变成一条结构事实**；因为 `hash_diff` 把"是否变化"变成可比较的值，重复加载是幂等的。
- **代价**：对象数量是 Hub + Link + Satellite 的总和，比维度建模多一个数量级；任何查询都要实现"取每个 Satellite 的最新行"再 JOIN，因此 Data Vault 必须配套一层面向查询的信息集市（这是它的必备构件，不是可选优化）；加载器的哈希去重、迟到数据与多源同键冲突处理，都比维度建模复杂。
- **失效点**：当消费侧要直接查明细、而信息集市层没有建起来时，「源系统解耦、可演化」会反转成「查询复杂度被转移到每一个消费者」——因为关系被拆进多张表，每个消费方都要自己实现取最新卫星行的逻辑；结果是同一张 Hub 被 N 个团队各写一遍取数 SQL，解耦换来的收益被重复开发吃掉，且每一份 SQL 的"最新行"定义可能都不同。
- **真实使用**：Data Vault 由 Dan Linstedt 提出，Data Vault 2.0 见 Linstedt & Olschimke《Building a Scalable Data Warehouse with Data Vault 2.0》（2015）【公开，2015】。原文件把金融 / 保险 / 电信列为代表——这三个行业的共同点是源系统多、受监管、历史必须可审计，恰好对应上面两条约束【经验】。

#### 3.2.3 模式 C：OneID 跨域主数据（C1 强匹配 / C2 弱匹配 / C3 图推理）

- **被什么约束逼出来**：同一个实体在多个源系统里有不同标识，且**没有任何一个标识是全量可见的**。约束是"标识的可见性不完整，而合并错了不可逆"。这里的"实体"不限于自然人：原文件把本模式的适用面写成"用户打通、商品打通、商家打通"三类，主文件 §2.1 也把 OneID 定义为"用户 ID（设备 ID + 手机号 + 身份证 + 微信 unionid 等）"加"商品 ID（SPU + SKU + 条形码）"。三者的**匹配机制同构**——拉通多源标识、建统一主体、供下游引用——但**标识集合不同**，因而强 / 弱匹配的分工也不同。
- **结构**：

```sql
-- OneID：一个实体一个 OneID；每条映射都留依据、留有效期（合并可回滚）
-- 三类实体（user / product / merchant）共用这一张映射表
CREATE TABLE dim_one_id (
  entity_type STRING NOT NULL,        -- user / product / merchant
  one_id      STRING NOT NULL,        -- 统一标识（对外唯一）
  id_type     STRING NOT NULL,        -- user: phone/device_id/idcard/unionid/member_card
                                      -- product: spu_id / sku_id / barcode
                                      -- merchant: 统一社会信用代码 / 平台店铺 ID
  id_value    STRING NOT NULL,        -- 加盐哈希后存储
  match_layer STRING NOT NULL,        -- C1 强匹配 / C2 弱匹配 / C3 图推理
  confidence  DECIMAL(5,4),           -- C2/C3 必填；C1 记 1.0
  evidence    STRING,                 -- 合并依据摘要：可审计、可回滚
  valid_from  TIMESTAMP, valid_to TIMESTAMP
);
```

```text
C1 强匹配：人：phone / idcard / unionid
          商品：barcode / SPU 编码        商家：统一社会信用代码
          —— 确定性并查集，出错的是数据本身
C2 弱匹配：人：设备指纹 + 行为 embedding 相似度 ≥ θ
          商品：标题 / 图片 / 属性相似度 ≥ θ —— 概率合并
C3 图推理：异构图链接预测（人-设备-地址-支付工具；商品-店铺-类目-条码）—— 概率合并，可解释性更低
                        │
                        ▼
   顺序：先用 C1 合并确定性连通分量 → C2/C3 只在「跨分量」处提议合并
         → 每条提议都落 evidence 与 confidence → 可审计、可回滚
```

- **为什么这样设计有效**：因为 C1 是确定性的，先跑 C1 不引入假合并、还能把问题规模缩小；因为 C2/C3 的每条边都带 confidence 与 evidence，错误合并可以被发现与回滚——OneID 的错误与其他数据错误性质不同：**它是不可逆的污染**，两个真人被并成一个后，UV、复购、留存、去重口径的全部下游指标同时错，且系统不会报错。三类实体共用这张映射表还额外买到一件事：商品与商家的打通复用同一套并查集、同一套回滚与同一套审计逻辑，不必为每种实体各写一个引擎——否则"多套标识并存"会以"多套 OneID 服务并存"的形式重演。
- **代价**：映射表行数等于标识总数（一个用户常有 5–10 个标识【经验】），反查要按 `one_id` 取全部标识；合并 / 拆分需要一套图上的并查集能力加回滚机制，而回滚意味着所有引用该 `one_id` 的下游指标要重算；一张表承载三类实体，意味着并查集与回滚要同时承载三种规模与三种冲突代价，不能只按"人的标识"估容量。C2/C3 的阈值 θ 需要标注样本校准，这份标注要持续维护，否则阈值会随设备与行为分布变化而失准。
- **失效点**：当只做 C1 强匹配（原文件反模式④）时，「不会错」会反转成「覆盖率被钉死在最强标识的可见率上」——因为强匹配只能连起同时暴露强标识的那部分实体。【推算：设某业务手机号可得率 40%、设备 ID 可得率 90%（这两个数是假设值，替换成你自己埋点口径下的真实值），只做 C1 时 OneID 覆盖率上限就是 40% 量级；补 C2/C3 能把剩余部分接回一部分，代价是按阈值 θ 引入假合并——θ 越低覆盖越高、错合并越多。这条代价无法靠加机器消掉，只能用"阈值 + 可回滚 + 影响面重算"来管理】
- **真实使用**：主文件 §2.3 方法⑤把强匹配 / 弱匹配 / 图匹配列为 OneID 的三类算法，并列出阿里 ID-Mapping 平台、阿里 EntityLink、神策 ID-Mapping 5.0 等工具——这类产品的能力以各产品官网当前文档为准，可自行核验【公开，可自行核验】。多数团队的 OneID 覆盖率落在 60%–90% 区间，且强匹配与弱匹配混用【经验】。

#### 3.2.4 模式 D：OneService API 主导（D1 Query / D2 Push / D3 Realtime / D4 RAG）

- **被什么约束逼出来**：消费方是人以外的对象（应用、Agent、模型），它们要的是"一个稳定的接口"，而不是"一张会被改名的表"。约束是"消费方无法跟随上游的表结构变化"。
- **结构**：

```sql
-- 服务注册表：接口是一等公民，物理表不是
-- 对应主文件 §2.2 的形式化 S = (R, I, O, P, Q)
CREATE TABLE one_service_registry (
  api_name     STRING,   -- trade.order.query
  api_type     STRING,   -- D1 Query / D2 Push / D3 Realtime / D4 RAG
  source_asset STRING,   -- 指向 DWS/ADS 或指标名，不直接指向物理表名
  contract     STRING,   -- 输入/输出 schema（JSON / Protobuf / Pydantic，即 I、O）
  sla          STRING,   -- QPS / P99 / 可用性（即 Q）
  authz        STRING,   -- 鉴权与数据范围（即 P）
  owner        STRING    -- 具体到人
);
```

```text
D1 Query API    ：点查 / 小结果集         → 读 DWS/ADS（列存点查 + 缓存）
D2 Push API     ：事件订阅（Kafka）       → 消费的是"变更"，不是"表"
D3 Realtime API ：Flink 实时计算 + 服务化 → 消费的是流上的滚动状态
D4 RAG API      ：图 + 向量混合检索       → 返回的是"证据片段"，不是数字
   ┌────────────────────────────────────────────────┐
   │ 四者共享同一件事：口径在服务内部固化，          │
   │ 消费方拿到的是"已定义好的量"，不是"原始列"      │
   └────────────────────────────────────────────────┘
```

- **为什么这样设计有效**：因为 `source_asset` 指向 DWS/ADS 或指标名而不是物理表名，上游换表、改名、换引擎对消费方不可见；因为契约、SLA、鉴权在注册表里是必填项，"代理物理表"这种形态在结构上不成立——它可以被一条查询语句检查出来。
- **代价**：每个服务多一份契约与一个必须维护的兼容期（下线旧版本要走废弃流程）；缓存引入一致性问题——缓存里的旧值与表里的新值必须显式约定 TTL 与失效策略，否则会得到"刚改完数还是旧的"这类事故；D4 返回的是证据片段，还要额外定义"消费方据此可以做什么决策"，否则会把检索结果当成口径。
- **失效点**：当 API 只是"物理表的代理"（原文件反模式⑤）时，「接入快、开发省事」会反转成「上游一改就全线故障」——因为消费方直接依赖表的列名与类型，而上游改列名时不会有任何机制通知到它；同时没有缓存与限流意味着一次热点查询直接穿透到 OLAP 集群，把在线分析一起拖垮。判定方法：问一句"上游把这张表重命名，有多少个消费方要改代码"，答不上来就说明它是代理而不是服务。
- **真实使用**：数据服务化（DaaS）与 API 网关是通用工程实践【经验】；Kafka 官方文档给出"事件推送"这一消费形态与投递语义（at-least-once / exactly-once）的定义，以 kafka.apache.org 当前文档为准【公开，可自行核验】；D4 这类接口在 OneData 体系里的位置见主文件 §1.3 的"智能体平台 → OneData 提供 RAG / Tool 的标准数据底座"一行【公开，见本仓库主文件】。

#### 3.2.5 模式 E：指标平台主导

- **被什么约束逼出来**：同一个指标被多个团队各自计算，而业务方无法阅读 SQL、也无法判断两个数是不是同一个东西。约束是"指标的消费方不具备技术判据"。原文件的表述是"指标是 OneData 的对外语言"。
- **结构**：

```sql
-- 指标定义：定义与物理实现分开，口径变更留版本
CREATE TABLE metric_definition (
  metric_name    STRING,   -- trade.gmv_1d
  metric_type    STRING,   -- 原子 / 派生 / 复合（主文件 §2.1）
  atomic_ref     STRING,   -- 派生指标必须指向原子指标，不允许悬空
  time_window    STRING,   -- 1d / 7d / 1h
  modifiers      STRING,   -- 渠道 / 地区 / 品类
  biz_where      STRING,   -- 业务限定（where 条件）
  owner          STRING,   -- 定义 Owner，不是报表 Owner
  version        STRING, effective_from TIMESTAMP
);
```

```text
指标定义（上表）──► 指标计算：由 OneModel 的 DWD/DWS 承载，不许绕过公共层
        └────────► 指标服务：由 OneService 承载，对外是 D1/D2/D3 接口
关键：一条指标只有一个定义；物理实现可以重建；
      口径变更留版本，历史报表可以按当时口径重述
```

- **为什么这样设计有效**：因为"原子 / 派生 / 复合"三级结构强制每条派生指标挂在一条原子指标上，所以"两个团队算出两个 GMV"在结构上会**自己暴露**——要么两条派生指标挂在不同的原子指标上，要么挂在同一条原子指标但 `biz_where` 不同。争议从"立场之争"变成"可定位的字段差异"，这就是原文件所说"指标是 OneData 的对外语言"的机制含义。
- **代价**：定义中心成为发布链路上的单点，任何口径变更都要走版本与评审，于是紧急取数需求的第一反应就是绕开它——绕开一次就多一个口径；原子指标层需要一次全组织的口径对齐，这轮对齐的耗时往往超过平台本身的建设周期；平台还要承担"指标计算"的算力调度，指标数上万后血缘与物化策略成为新的维护面。
- **失效点**：当指标平台只做"取数出报表"（原文件反模式③）时，「上平台、接入快」会反转成「口径混乱被固化进平台并被赋予权威外观」——因为平台把每个团队交上来的 SQL 都接了进去，而它们的口径从未被归并；此时平台不是解药，它是把"5 个 GMV"搬进同一个系统，并让冲突更难被发现（大家会默认"平台上的就是对的"）。
- **真实使用**：原子 / 派生 / 复合指标的划分见阿里《大数据之路》（2017）【公开，2017】；原文件列出阿里指标平台、字节 Bytemetric、火山引擎 DataFinder 为工具代表——这类产品的具体能力以各产品官网文档为准，可自行核验【公开，可自行核验】。多数中大型公司的指标平台在建成后还需要一到两轮口径归并才能真正收敛【经验】。

#### 3.2.6 模式 F：AI 增强的 OneData（OneData 4.0）

- **被什么约束逼出来**：命名评审、口径文档、血缘理解都是人力密集型工作，其成本随资产数线性增长，而人对"给资产写业务含义"这件事的耐心有限。约束是**元数据的增长速度超过人能维护的速度**。
- **结构**：

```text
四项能力，以及每一项在结构上依赖的"机器可读权威"：
LLM 辅助命名规范校验
   输入 = 可解析的命名语法（主文件 §2.3 方法⑥） + 候选表名 → 输出 = 违规项
   前提：规则本身要机器可读，否则模型只能"感觉一下"，无法判定对错
LLM 辅助指标口径文档生成
   输入 = metric_definition（3.2.5 的表） + 上下游血缘 → 输出 = 给业务方读的描述
   前提：口径的权威在定义表里，文档只是它的一个渲染产物
LLM 辅助血缘理解
   输入 = SQL 解析产出的字段级血缘 → 输出 = "这条链路在做什么"的解释与盲区标注
   前提：血缘由图谱给出（解析是权威），模型负责解释而不是负责推断依赖
AI 资产化
   把指标 / 主数据 / 服务打包为"带 Owner、SLA 与契约"的可调用资产
   ────────────────────────────────────────────────
   共同点：输出必须能被某个已存在的权威校验，否则它只是草稿
```

- **为什么这样设计有效**：因为每项能力的输入都是一份已存在的机器可读权威（命名语法、指标定义表、血缘图），所以模型的输出是**可判定的**——能判定对错，就能放进评审流程当辅助；反过来，任何没有权威可对照的生成物，无论读起来多合理，都只能停在草稿状态。
- **代价**：四项能力各引入一条生成链路，每条都要有"生成 → 人审 → 入库 → 可回滚"的完整流程；口径文档一旦由模型生成并被当作权威，就会与定义表分叉（定义表改了、文档没重生成）；而模型生成的业务含义恰恰是**最容易被默认接受、最难被验证**的一类元数据——它没有编译错误可以暴露。
- **失效点**：当生成物没有"人审 + 入库"这道关时，「把人力成本降下来」会反转成「污染权威元数据」——因为生成的自然语言描述看起来总是合理，而它会被检索与 RAG 直接消费；一旦错误描述进入资产库，Agent 会以它为据做决策，且没有人知道它错在哪、错了几条。
- **真实使用**：LLM 辅助建模与元数据生成在 2023 年后被多家厂商作为产品能力发布，主文件 §1.4 把 2023–2025 标为 OneData 4.0 / AI 增强阶段【公开，见本仓库主文件】。这一层目前以厂商演示与愿景为主，**未见可核验的、把模型生成的口径文档直接当作权威口径的第三方生产案例**；因此建议按"辅助 + 人审"落地，生成物一律不直接进口径链路。

#### 3.2.7 模式 G：智能体驱动的 OneData

- **被什么约束逼出来**：资产的变更与冲突是持续、分布式发生的（每天都有人新建表、改口径），而治理团队是集中且有限的。约束是**治理动作的发生频率跟不上资产变化频率**。
- **结构**：

```text
三项能力的共同结构约束：产出必须是"可裁决的提案"，不能是"已生效的变更"
Agent 自动发现指标口径冲突
   扫描 metric_definition：同原子指标 + 同修饰词但 biz_where 不同；
   同一 metric_name 存在多个实现 → 产出「疑似冲突清单」交定义 Owner 裁决
Agent 自动建议数据分层
   读新表的上下游与粒度 → 给出"应落在 ODS/DWD/DWS/ADS 哪一层"的建议
   → 建议进入建表评审，不由 Agent 直接搬运表
Agent 自动监控数据质量
   按 SLA 检查新鲜度与波动，异常时沿血缘定位到 Owner
   → 产出告警，不自动改数
   ────────────────────────────────────────────────
   判据：如果某个能力无法退化成"可被驳回的提案"，它就不该被自动化
```

- **为什么这样设计有效**：因为三个能力的输出都是提案而不是变更，Agent 犯错的最坏后果是多一次人工裁决，而不是一次错误变更已经生效；又因为提案本身可统计（漏报率、误报率），治理团队可以用数据决定要不要继续保留这个 Agent——治理自动化因此是可以被证伪的，而不是一种信仰。
- **代价**：提案疲劳——如果 Agent 每天提出 200 条疑似冲突而误报率高，Owner 会在两周内学会全部忽略它，此时系统"在运行"但治理并没有发生；必须有精度指标与分级（只把高置信提案推到人面前，其余进待办池）；此外"哪个口径是对的"本质上是业务价值判断，Agent 结构上给不出，只能把问题精确定位到人。
- **失效点**：当权威口径尚未建立时，「自治」会反转成「用同一个错误互相印证」——因为 Agent 只能对着现有的表与定义做一致性检查；如果平台上并存 5 个 GMV 且没有任何一个被宣布为权威，Agent 最多能指出它们不一致，而更糟的情况是它挑了一个错误但内部自洽的定义去"纠正"正确的那个，把污染扩散到更多资产。
- **真实使用**：主文件 §1.4 把 2025 年起列为"OneData × Agent"阶段，能力包括自动发现口径、自动溯源、自动建模【公开，见本仓库主文件】。生产上可核验的落地目前集中在**有客观判定标准的任务**（自动采集、自动标注、异常告警），"自动裁决口径"这类需要业务价值判断的动作尚无公开可核验的生产案例【经验】；相关落地形态可参见 [§ 6 落地实践](08-one-data-section-6-sec6.md)。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 业务过程可枚举、源系统结构稳定 | A 维度建模主导 | 不用 B：源系统稳定时，Data Vault 多出的表数量与查询复杂度是纯成本 | 源表结构一年改几次 |
| 源系统 10+ 且各自高频变更、要求可审计 | B Data Vault 主导 | 不用纯 A：每次源变更都要回刷事实表，回刷量随时间累积 | 是否需要"任何时点重述 + 逐条审计" |
| 一个实体多源出现、强标识不全量可得 | C OneID（C1 为主 + C2/C3 补） | 不用"只做 C1"：覆盖率被钉在最强标识的可见率上 | 能否接受假合并并支持回滚 |
| 消费方是应用 / Agent、上游会改名 | D OneService | 不用"视图 + 直连表"：列名变更直接穿透到消费方代码 | 上游改表名要改的消费方数量 |
| 同一指标被 3 个以上团队计算、争议未决 | E 指标平台（定义中心） | 不用"报表 + 文档"：口径散落在 SQL 与文档里，无法比较 | 是否存在"同一指标两种结果"的未决争议 |
| 元数据量大、人力写不完业务含义 | F AI 增强（辅助 + 人审） | 不用全自动生成：无权威可校验的生成物会污染资产库 | 命名语法 / 指标定义 / 血缘是否已机器可读 |
| 资产变化频率高于治理团队处理频率 | G 智能体（提案式） | 不用全自动裁决：对错依赖业务价值判断，Agent 给不出 | 提案误报率能否被度量并分级 |
| 单一业务、数据成熟度低 | 先只做命名规范 + Owner 制度 | 不用全套：制度成本大于收益 | 是否已有专人负责数据标准 |
| 集团级、多 BU、多子公司 | B + C + F | 不用 A 单打：多源高频变更下，公共层会被回刷拖死 | 源系统数量与变更频率 |
| AI 是核心业务、需要特征与指标统一 | E + F（指标即特征） | 不用"另建特征平台"：特征与指标两套口径，必然分叉 | 特征是否复用指标定义 |

表里最常被误选的一对是 **A 与 B**：两者都叫"OneModel 主导"，于是有人按"更先进"选了 Data Vault。后果按 3.2.2 的机制是——你为一个源系统稳定的场景，付出了一个数量级的对象数量加一层必须自建的信息集市，而它的收益（源系统解耦、任意时点重述）在这个场景里根本用不上。判断只差一句话：**源系统表结构一年会改几次**？答"基本不改"就选 A。

### 3.4 组合模式：真实系统不会只用一种

**组合一：A（维度建模公共层）+ E（指标定义中心）+ D1（Query API）**

- 组合构成：DWD/DWS 负责把业务过程与口径落到物理结构，指标定义表负责把口径变成可比较的元数据，Query API 负责把指标交给应用而不交出物理表。
- 职责边界：口径只在 E 侧定义一次，A 侧只提供计算落点，D 侧只做契约与鉴权限流；三者中任何一侧都不允许"顺手改口径"。
- 运维代价：三套 Owner 与三轮评审（建模评审 / 口径评审 / 接口评审），任何一次口径变更要同时更新定义、物化与接口文档三处，否则会分叉。
- 适合规模：已有独立公共层团队、指标数在数百到数千量级的中大型组织【经验】。

**组合二：C（OneID）+ A（DWD 以 OneID 为外键）+ E（去重类指标按 OneID 计算）**

- 组合构成：C 产出 `one_id`，A 的明细事实表用 `one_id` 而不是源系统 UID 做主体标识，E 的 UV / 复购 / 留存类指标的分母取自 OneID。
- 职责边界：OneID 只负责"这是不是同一个人"，不负责任何业务口径；事实表只负责事件；去重逻辑只在指标层出现一次。
- 运维代价：合并与回滚会触发全部下游指标重算，所以 OneID 的变更必须是可计划、可通知的；映射表的每次批量变更都要评估影响面，事实上需要一份"谁用了 OneID"的清单。
- 适合规模：跨 3 个以上业务域、且存在跨域去重指标（集团 UV）时【经验】。

**组合三：B（贴源整合层）+ A（信息集市层）+ D（服务层）**

- 组合构成：B 承担多源整合与历史可审计，A 在 B 之上建可查、可复用的公共层，D 向外提供接口。B 不是给消费方查的，A 才是。
- 职责边界：B 只负责"把源系统的历史完整、可追溯地接进来"，不承担任何业务口径；口径全部在 A 侧定义；D 侧只是出口。
- 运维代价：两层加工链路加两套质量校验，任何源字段变更要沿链路评估两次；B 的卫星表版本会持续增长，需要配套的存储与查询策略，否则信息集市层会被拖慢。
- 适合规模：集团级、源系统超过 10 个、且历史审计是硬要求（金融 / 保险 / 电信）【经验】。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因 | 修法 |
| --- | --- | --- | --- | --- |
| **① 把 OneData 当成"工具项目"** | 立项材料里全是工具选型，没有分层规范、没有 Owner 名单 | 缺少强制登记与门禁，工具只是一个空壳元数据库；表照样命名混乱，因为工具不能替人做决定 | 采购比组织变革容易，且工具交付有明确验收日期 | 先定标准与 Owner，工具只做标准的技术执行者（3.2.1、3.2.4） |
| **② 一次性建全套标准** | 立项第一天就要"统一所有命名、所有指标、所有主数据" | 工作量爆炸导致业务方抵制，标准在试点前就失去合法性；后续任何推进都会被引用为"上次也是这么说的" | 把标准当成文档而不是协商结果，误以为覆盖面越全越有价值 | 从 1 个数据域、10 个核心指标开始，用一轮试点证明收益后再扩面 |
| **③ 指标平台只是"取数工具"** | 平台里有指标报表，但没有指标定义表、没有口径版本、没有血缘 | 每个团队的口径被同时接入平台，冲突被固化并获得权威外观，比散落时更难发现 | 平台的第一个需求永远是"把报表搬上来"，搬家能立刻交付价值 | 定义中心、口径管理、血缘追踪必须与报表同时上线（3.2.5） |
| **④ OneID 只做"强匹配"** | 只有手机号 / 身份证匹配逻辑，没有 confidence 字段、没有回滚路径 | 覆盖率被钉在最强标识的可见率上；业务方发现"打通率不够"后会绕过 OneID 自己拼 ID，回到多套标识并存 | 强匹配确定性高、上线快、不需要标注样本校准阈值 | C1 定连通分量 + C2/C3 提议合并，全部留 evidence 与有效期（3.2.3） |
| **⑤ OneService 只是"代理数据库表"** | 接口参数与物理表列名一一对应，没有缓存、限流、鉴权配置 | 上游改列名即全线故障；热点查询直接穿透到数仓，把 OLAP 拖垮 | 代理表是交付最快的形态，且在没有 SLA 要求时看不出问题 | 服务注册表强制契约 + SLA + 鉴权，`source_asset` 指向资产不指向表（3.2.4） |
| **⑥ 命名规范过严或过松** | 一边是 30 个字符的命名规则让开发绕开规范，一边是无强制、全靠自觉 | 过严使规范被规避（生成一堆 alias 与临时表），过松使规范不存在；两种结局都是命名失去检索价值 | 规范由平台方单方面制定，没有考虑写规范的人的成本 | 核心规范必填 + 扩展规范推荐 + 规则机器可读、工具自动校验（3.2.6 的前提） |
| **⑦ OneData 与 AI 项目脱节** | AI 团队另建一套特征平台，特征定义与指标定义各说各话 | 同一业务量在指标侧与特征侧有两个口径，模型效果归因与业务复盘无法对齐；信任被分散到两套数字上 | AI 团队进度压力大，指标平台的接入流程又慢，另起一套更快 | OneData 升级为 AI 数据底座，指标即特征：特征复用指标定义（3.3 决策表末行） |
| **陷阱：OneData 是"一把手工程"** | 推进依赖某个部门的善意配合，跨部门协同没有正式机制 | 遇到需要业务方让出命名权 / 口径权的冲突时无裁决者，标准停在文档层 | 方法论被当成技术方案立项，而它实际是组织方案 | 立项时拿到组织授权与跨部门协同机制，把裁决权明确到具体角色 |

最危险的三条是 **③、④、⑦**，它们的共同点是**失效时不报错**。

**③ 指标平台只是取数工具**在生产中的典型暴露方式是一次口径对账：两个部门各自从平台取数，发现同一个指标差了几个百分点，追查后发现平台里本来就并存两个口径的实现——而平台的存在让双方都以为对方是错的。定位方法不是看 SQL，而是问"这个指标名在 `metric_definition` 里有几行"。

**④ OneID 只做强匹配**的暴露方式是"打通率不够"的抱怨，而真正的风险在反向：团队为了提升覆盖率后补了弱匹配，却没有留 confidence 与回滚路径，于是假合并静默发生。它的特点是**错误发生在标识层、暴露在业务层**——发现时通常已经过了一个结算周期。

**⑦ OneData 与 AI 项目脱节**的暴露方式最晚也最贵：模型上线后效果不及预期，归因时才发现特征口径与业务指标口径不是一回事，而这时要改的是特征生产线而不是一个 SQL。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 表数从百级到万级 | 命名规范靠自觉 + 人工评审 | 评审带宽成为瓶颈，规范覆盖率随表数下降 | 规则机器可读 + 建表门禁自动校验 | 要先把规范写成可解析的语法；历史表要批量整改 |
| 源系统从 1 个到 10+ 且各自高频变更 | A 维度建模直贴源系统 | 每次源变更都要回刷事实表，回刷量随历史长度累积 | 引入 B 作为贴源整合层 + 在其上重建信息集市 | 多一层加工链路与一套加载器；历史要重新组织一次 |
| 消费方从报表工具变成应用 | 视图 + 直连物理表 | 上游改列名直接穿透到消费方代码，故障面不可枚举 | D OneService（契约 + SLA + 鉴权） | 每个接口要定义契约与兼容期；缓存一致性策略要落地 |
| 指标从 10 个到 1000 个 | 口径写在文档与 SQL 注释里 | 同一指标多种实现，争议无法用结构定位 | E 指标定义中心 + 版本化 | 需要一轮全组织口径归并，耗时往往超过平台建设 |
| OneID 从"能打通"到"必须准" | 只做 C1 强匹配 | 覆盖率触顶，业务方开始绕过 OneID 自己拼 ID | C1 + C2/C3 + confidence + 可回滚 | 需要标注样本校准阈值；合并变更要联动下游重算 |
| 消费方从人变成 Agent | 指标定义 + 人工解释 | Agent 拿不到口径的自然语言含义，也判不出该不该合并两条冲突定义 | F / G：机器可读资产 + 提案式治理 | 语义层成为取数链路的单点；口径权威从报表 Owner 转到定义 Owner |

这张表里最容易被低估的是**第二行**：它不是"要不要更先进"，而是"回刷成本何时超过重建成本"。判断阈值不需要精确数字——记录每次源变更的回刷耗时，当它接近或超过当日计算窗口时，就该引入整合层。

### 3.7 自检清单

- [ ] 每个业务过程是否恰好对应一张 DWD 明细表？出现两张，说明粒度纪律已经被破坏。
- [ ] 指标定义表里是否存在"派生指标不指向原子指标"的悬空条目？存在即口径不可比较。
- [ ] 同一 `metric_name` 在 `metric_definition` 里有几行？大于 1 就是未归并的口径。
- [ ] `dim_one_id` 的每一行是否有 `match_layer` 与 `confidence`？只有 C1 且无置信度，说明二值与概率合并没被区分。
- [ ] OneID 的合并是否有 evidence 与有效期，能否回答"这次合并依据是什么、怎么回滚"？
- [ ] 是否存在绕过 OneID 自行拼接用户 ID 的作业？存在即 3.2.3 的失效点已经发生。
- [ ] 每个对外接口的 `source_asset` 指向的是资产还是物理表名？指向表名即 3.2.4 的代理反模式。
- [ ] 上游改一张表的名字时，能否在半小时内列出全部受影响接口与消费方？
- [ ] 命名规范是否机器可读（可以被工具解析成规则）？只有文档没有人能自动校验它。
- [ ] 每张表、每个指标、每条主数据是否有具体到人的 Owner（而非团队名）？
- [ ] 若已引入 LLM 辅助生成元数据：生成物是否有"人审 + 入库"关卡，且有权威元数据可供校验？
- [ ] 若已引入 Agent 治理：它的产出是"可驳回的提案"还是"已生效的变更"？后者应立刻降级。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 业务过程稳定、查询形态不可预知 | A 维度建模主导 | 业务过程枚举有限，口径冲突变成可检查的结构约束 |
| 源系统多且高频变更、要求可审计 | B Data Vault 主导 | 属性只进 Satellite，源变更只影响一个对象，解耦是结构事实 |
| 强标识不全量可得、要跨域去重 | C OneID（C1 + C2/C3 + 可回滚） | 概率合并留 evidence，错误可定位可回滚，不是不可逆污染 |
| 消费方是应用 / Agent | D OneService | 契约与物理表解耦，上游改名对消费方不可见 |
| 指标被多团队重复计算 | E 指标定义中心 | 三级指标结构让口径差异落到字段上，变成可判定的分歧 |
| 元数据增长快于人力 | F AI 增强（辅助 + 人审） | 生成物以机器可读权威为输入，才能被校验、才能进流程 |
| 资产变化快于治理带宽 | G 提案式智能体 | 产出是提案不是变更，出错代价降级为一次人工裁决 |
| 起步阶段、成熟度低 | 命名规范 + Owner 制度 | 先建立可检查的最小约束，再谈分层与平台 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**"这套口径由谁保证、出错时代价落在哪一层"**。同一个实体是同一套标识（OneID 的错不可逆）、同一件事只有一张明细表（OneModel 的错会拖慢回刷）、同一个量只有一条定义（指标口径的错会静默分叉）——三条都是"唯一性"约束，但它们的失效方式完全不同：一个错而不报，一个慢而不崩，一个脆而全线。先想清楚这条约束落在哪一层，模式自然就定了。
