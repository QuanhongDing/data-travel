## 7. 与其他方法对比

### 7.1 先立判据：为什么星级表会误导

星级表把「跨域打通 ★★★」「指标一致性 ★★」「实施成本 ★★★★」这类格子加起来做比较，问题不在评得准不准，而在**这些格子的量纲不同且方向相抵**：实施成本那一列的高分是缺点，其他列的高分是优点；把它们放进同一张表，读者必须自己在脑子里做符号翻转。更麻烦的是，「灵活度」与「指标一致性」在真实组织里不是两个独立的分数，而是**同一条机制的两端**——把口径的裁决权收到中心，一致性上升、灵活度必然下降；把它放给业务域，反过来。给同一件事的两端各打一个星，等于把一次权衡伪装成了两个得分。

第二个问题是候选不在同一层。维度建模与 Data Vault 是**建模方法**；OneModel / OneID / OneService 是**方法论里的三个部件**；指标平台是**承载口径的系统**；Data Mesh 是**组织与所有权范式**；AI 资产化与 GraphRAG / 智能体是**消费侧形态**。把它们排成一列比总分，等于问「变速箱和交通规则哪个更好」——它们分别在回答「模型怎么切」「口径存哪」「资产归谁」「谁来消费」这四个不同的问题。

第三个问题是打分表会把「取决于约束的结论」写成「绝对结论」。同一家万人公司里，OneModel 走维度建模还是 Data Vault，取决于**源系统表结构一年改几次**；OneID 用强匹配还是弱匹配，取决于**强标识的全量可见性**；OneService 是接口契约还是物理表代理，取决于**消费方是人还是应用**。这三个约束互相独立，答案可以完全不同——所以下面的判据表里没有一列叫「总分」。

**本章采用的 6 条判据**：

| 判据 | 问的问题（本主题化） | 为什么它决定了选型 |
| --- | --- | --- |
| 能力边界 | 它做不到什么——具体到「能不能表达主数据打通、服务契约、跨域口径」 | 星级表问「能做多好」，而选型中被否决的永远是「它做不到的那一条正好是你的硬约束」 |
| 成本结构 | 成本随什么变量增长（表数 × 源变更频率 / 口径数 × 归并轮次 / 标识数 × 冲突代价 / 域数） | 线性成本在百级表上无所谓，在万级表上加一层回刷就直接吃掉全年计算窗口 |
| 机制契合度 | 它的切分锚点是否匹配你的源系统稳定性与访问模式 | 锚在业务过程上的模型与锚在源系统对象上的模型，在源系统变更时的行为完全不同（7.3.1） |
| 运维复杂度 | 需要几个人、什么技能、多少个必须自建的配套层 | Data Vault 不带信息集市就是半成品，OneData 不带 Owner 制度就是空壳——配套件成本要算进去 |
| 生态与锁定 | 离开它要付什么：模型重写、口径重定义、服务契约变更、标注体系重建 | 方法论的迁移成本全部落在「模型与口径」这两类最难重写的资产上 |
| 演进风险 | 方法论没有 release note，项目被谁维护、有没有工具链支撑 | 一套没有工具承载的规范会在两年内退化为文档；有工具承载的规范才能被自动校验【经验】 |

判据的使用顺序是固定的：**机制契合度先否决**（锚点不匹配的模型，做得再标准也会在第一次源变更时崩掉），**成本结构决定能不能规模化**，**运维复杂度里的「必须自建的配套层」决定它是不是一个完整方案**，其余三条在过关者之间排序。

### 7.2 候选方案全景

| 族 | 方案 | 定位（回答哪个问题） | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- | --- |
| A 建模方法 | 维度建模（Kimball） | 模型怎么切 | 按业务过程切事实表、按维度拍平；业务过程可枚举是它的前提 | 业务过程稳定的组织 | 公开方法论 |
| A 建模方法 | Data Vault（Linstedt / 2.0） | 模型怎么切（面向源系统解耦） | Hub 存业务键、Link 存关系、Satellite 追加属性且永不覆盖 | 金融、保险、电信 | 公开方法论 |
| B OneData 部件 | OneModel：维度建模主导 | 模型怎么切（工业化落地） | 分层单向流动 + 命名规范强制 + 业务过程枚举 | 业务过程可枚举的组织 | 随方法论与工具链 |
| B OneData 部件 | OneModel：Data Vault 主导 | 模型怎么切（多源高频变更） | 贴源整合层 + 其上的信息集市 | 多个源系统各自独立变更的组织（「10+」的量级判据见 7.5 依据③） | 随方法论与工具链 |
| B OneData 部件 | OneID | 实体怎么认（主数据） | 并查集拉通多源标识，每条合并带 confidence 与 evidence，可回滚 | 有跨域去重指标的组织 | 自建为主，亦有工具 |
| B OneData 部件 | OneService | 资产怎么交付给应用 | 契约与物理表解耦，注册表指向资产而不是表名 | 消费方是应用 / Agent | 自建或服务网关 |
| B OneData 部件 | 指标平台 | 口径存在哪 | 原子 / 派生 / 复合三级结构，派生指标必须挂在原子指标上 | 口径争议未决的组织 | 自建或产品 |
| B OneData 部件 | OneData 4.0 / AI 增强 | 元数据谁来写 | 以机器可读的权威（命名语法 / 指标定义 / 血缘）为输入，输出可判定 | 元数据增长快于人力 | 厂商能力 + 自研 |
| B OneData 部件 | OneData × Agent / GraphRAG | 资产怎么被机器消费 | 资产作为 Tool 与知识库；治理产出是可驳回的提案 | 智能体平台 | 厂商能力 + 自研 |
| C 组织范式 | Data Mesh | 资产归谁 | 域内所有权 + 数据即产品 + 自助平台 + 联邦计算治理 | 多域自治的大型集团 | 公开方法论 |
| D 资产交付 | AI 资产化 | 谁来消费、以什么形态 | 把数据 / 模型 / 知识打包成带 Owner、SLA 与契约的可调用资产 | AI 优先企业 | 自建为主 |

这张表最左列就是它的用法：**A 与 B 的前两行回答「模型怎么切」，B 族的 OneID / OneService / 指标平台 / OneData 4.0 回答「标识、服务、口径、元数据各由什么承载」，C 回答「谁对资产负责」，D 与 B 族的 Agent / GraphRAG 一行回答「消费侧以什么形态拿到资产」**。同族内部通常可以互换（例如 A 族两种方法都成熟，比的是约束匹配），跨族则不可比（C 与 B 在「口径由谁裁决」上方向相反）。**先分族、再定位你缺的那一环，能省掉一半比较**；反过来按总分排序，会在「建模方法」和「组织范式」之间做无效对比。

有一处容易读错：**Data Mesh 不是 OneData 的升级版，它们是同一个权衡的两个端点**。OneData 把口径的裁决权收到中心（因此一致性高、灵活度低），Data Mesh 把它放给业务域（因此灵活度高、跨域一致性没有中心裁决者）。这一点在 7.3.3 展开。

### 7.3 机制差异：为什么它们表现不同（核心节）

四个机制维度决定了本节所有候选的行为差异。每个维度都请先读「因为……所以……代价是……」，再看失效条件——**失效条件决定它在你这里能不能用**。

选择这四个维度而不是别的，是因为它们能覆盖 7.1 判据表的六条：7.3.1 对应机制契合度（切分锚点是否匹配源系统稳定性），7.3.2 与 7.3.4 对应能力边界（口径能不能被定位、上游变更能不能被隔离），7.3.3 对应运维复杂度与演进风险（谁来维护、靠什么强制）——最后这一条同时承压两条。剩下两条不是独立维度：**生态与锁定**是这四个机制选定的结果，离开一套方法要付的模型重写、口径重定义、契约变更，分别落在 7.3.1 / 7.3.2 / 7.3.4 上；**成本结构**同样是它们的结果，在 7.4 集中算。

#### 7.3.1 分子切分的锚点：业务过程 / 源系统对象 / 实体标识

**机制是什么**：任何建模方法都要先把企业数据切成有限个可管理的分子。切分的锚点决定了「什么东西变了，要重做多少」。

**各候选的实现差异**：

| 候选 | 切分锚点 | 源系统变更时要动什么 |
| --- | --- | --- |
| 维度建模 | 业务过程（下单 / 支付 / 退款 / 发货） | 该过程的事实表要回刷历史分区 |
| Data Vault | 源系统对象（Hub / Link / Satellite） | 通常只影响一个 Satellite，新增属性加一张卫星表 |
| OneID | 实体标识（一实体一 `one_id`） | 映射变更要重算全部引用 `one_id` 的去重类指标 |
| OneModel（分层） | 层级 + 数据域 + 业务过程 | 违反单向流动时才需要动，动就是跨层返工 |

**由此必然导出的性质**：因为维度建模把事实表锚定在**业务过程**上，所以业务过程可枚举时，「同一业务过程只有一张明细表」变成一条**可检查的结构约束**——口径冲突从「两个人各写了一段 SQL」变成「谁违反了分层纪律」这一可判定的事实；代价是源系统表结构一变就要回刷该过程的历史分区，而分区数等于保留天数，**回刷成本随时间单调增长**。反过来，因为 Data Vault 把属性只放在 Satellite 且按加载时间追加，所以源系统新增一个属性只影响一个对象、任意时点可重述；代价是对象数量比维度建模多一个数量级【经验】，且必须配套一层面向查询的信息集市——**这不是可选优化，是它的必备构件**。

**公开证据**：维度建模方法出自 Kimball《The Data Warehouse Toolkit》（1996）【公开，1996】；Data Vault 2.0 的建模规则见 Linstedt & Olschimke《Building a Scalable Data Warehouse with Data Vault 2.0》（2015）【公开，2015】；阿里《大数据之路：阿里巴巴大数据实践》（2017）公开描述了 OneData 的 OneModel 分层与命名规范【公开，2017】。三类锚点（业务过程 / 源系统对象 / 实体标识）的工程后果可在 [§ 3 设计模式](08-one-data-section-3-sec3.md) 的模式 A / 模式 B / 模式 C 三节逐条核对——三种锚点各自对应其中一节（本仓库内可逐行核对）。

**失效条件**：当源系统表结构高频变更时，维度建模的「模型稳定、一层 JOIN 拿全上下文」会反转成「回刷成本随变更次数累积」。触发条件可以操作化为：**一次源变更所需的回刷量（受影响分区数 × 单分区体积）是否超过当天的可用计算窗口**——一旦接近或超过，就该引入整合层，而不是继续加机器。

**AI 时代新增的约束**：特征工程把「读一次明细」变成「按时间窗口反复回扫同一批分区」。回刷成本从「偶发」变成「常态」，于是同一个锚点选择在 AI 场景下的代价被放大——这也是「指标即特征」这条路线在机制上的合理性：特征复用指标定义时，回扫的是已物化的汇总，而不是每次都回到明细分区。

#### 7.3.2 口径的载体：SQL 与文档 / 定义表 / 服务契约

**机制是什么**：一个指标的口径总要存放在某个可被引用的东西里。载体决定了口径冲突能不能被**结构定位**，而不是靠开会。

**各候选的实现差异**：

| 载体 | 口径存在哪 | 两个团队算出两个 GMV 时，冲突如何定位 |
| --- | --- | --- |
| SQL 与文档（维度建模默认） | 各自作业的 SQL、注释、需求文档 | 不可定位——只能逐条读 SQL 比对 |
| 指标定义表（指标平台） | `metric_definition` 的一行 | 可定位——要么挂在不同原子指标上，要么同一原子指标但业务限定不同 |
| 服务契约（OneService） | 注册表里的输入 / 输出 schema 与 SLA | 可定位——契约变更要走版本与兼容期 |
| 资产元数据（AI 资产化） | 资产的 Owner / SLA / 契约字段 | 可定位，且能被机器读取用于检索与调用 |

**由此必然导出的性质**：因为指标平台强制「派生指标必须挂在一条原子指标上」，所以两个团队的口径差异会在**结构上自己暴露**——争议从「立场之争」变成「可定位的字段差异」；代价是定义中心成为发布链路上的单点，任何口径变更都要走版本与评审，于是紧急取数需求的第一反应就是绕开它，**而绕开一次就多一个口径**。反过来，因为口径写在 SQL 注释里零成本，所以它在新组织里起步最快；代价是当指标数上千时，同一指标名的多种实现在结构上不可枚举，只能靠口径对账事故来发现。

**公开证据**：原子 / 派生 / 复合指标的划分见阿里《大数据之路》（2017）【公开，2017】；指标定义须版本化、口径变更须可重述，是 [§ 3 设计模式](08-one-data-section-3-sec3.md) 模式 E 的核心机制（本仓库内可逐行核对）；服务契约与 SLA 作为接口一等公民的治理方式见 [§ 3 设计模式](08-one-data-section-3-sec3.md) 模式 D：服务注册表把 `contract` 与 `sla` 设为必填列，「代理物理表」这种形态在结构上不成立（本仓库内可逐行核对）。[§ 6 落地实践](08-one-data-section-6-sec6.md) 的四个案例给出的是服务化的结果指标（接口复用率 30%→85%、40%→80%），不含契约与 SLA 本身的治理细节。【经验】

**失效条件**：当指标平台只做「取数出报表」而不做口径管理时，它会反转成**混乱的固化剂**——把每个团队交上来的 SQL 都接进平台，冲突不但没被解决，还获得了「平台上的数就是对的」这一权威外观。判定方法只有一句：**这个指标名在 `metric_definition` 里有几行**——大于 1 就是未归并的口径。

**推论：定义中心的单点性要靠流程而不是靠可用性来消解**。因为口径定义是发布链路上的单点，任何一次口径变更都要走评审，所以「紧急取数」与「口径纪律」在结构上冲突。可行的做法不是放宽评审，而是把口径变更分成两类：**新增**（不动既有定义，走快速通道）与**修改**（动既有定义，走完整评审并触发重述）。判据是：一次变更会不会让昨天发出的报表数字变化——会，就必须走完整流程。

#### 7.3.3 所有权放在哪一层：中心团队 / 业务域

**机制是什么**：数据资产的**定义权**（口径、命名、分级）与**所有权**（谁负责产出与质量）可以放在中心，也可以放在业务域。放在哪里，决定了标准的强制力从哪里来。

**各候选的实现差异**：OneData 把定义权收在中心，通过建表门禁与命名规范强制落地；Data Mesh 把所有权下放到业务域，中心（平台）只提供自助能力与联邦计算治理；维度建模与 Data Vault 本身不规定所有权，它们只规定模型形状，因此可以被任一种组织范式承载；AI 资产化把所有权显式写进资产元数据（Owner 字段），因此它对谁持有定义权是中立的。

**由此必然导出的性质**：因为 OneData 把定义权收在中心，所以跨域口径一致性有一个明确的裁决者，争议有终点；代价是标准的落地依赖**门禁能真的阻断一次不符合规范的建表**——没有这个权力，规范就只是文档，而文档在两年内会被绕过【经验】。反过来，因为 Data Mesh 把所有权放给业务域，所以标准只能通过「平台提供的自助能力比违规自建更省事」被采用；代价是跨域口径一致性**没有中心裁决者**，集团 UV、复购率这类跨域指标只能靠联邦治理协商，协商失败时冲突会长期存在。

**公开证据**：Data Mesh 这一概念的公开源头通常归于 Zhamak Dehghani 的文章《How to Move Beyond a Monolithic Data Lake to a Distributed Data Mesh》（2019）【公开，2019】；该概念随后由其专著《Data Mesh: Delivering Data-Driven Value at Scale》（2022）系统化，四项原则通常表述为域内所有权、数据即产品、自助数据平台、联邦计算治理【公开，2022】——标题、年份与措辞请以原文当前版本为准，可按作者名与 "data mesh" 自行检索核验；中心化建模标准的落地形态见阿里《大数据之路》（2017）【公开，2017】；这两种路线各自的约束条件见 [§ 3 设计模式](08-one-data-section-3-sec3.md) 的 3.1 约束表（「组织权力结构（有无一把手授权）→ 标准是强制门禁还是推荐规范」一行）与 3.5 反模式表末行的「陷阱」（本仓库内可逐行核对）。[§ 6 落地实践](08-one-data-section-6-sec6.md) 的四个案例（阿里 / 字节 / 美团 / Netflix）都是中心化 OneData 落地，不含域自治路线的对照，取舍只能用上句那两个条件自己判。【经验】

**失效条件**：当中心没有组织授权时，「先建标准再推广」会反转成业务方抵制——因为标准的实质是让业务方交出命名权与口径权，这不是技术问题而是权力问题（[§3.5 陷阱](08-one-data-section-3-sec3.md)）。判定方法：问「中心团队能不能阻断一次不符合规范的建表上线」，答「不能」就说明你实际在走 Data Mesh 的路线，无论文档上写的是哪一套。

#### 7.3.4 交付给消费方的形态：表 / 指标 / API / 事件 / 可调用资产

**机制是什么**：资产最终以什么形态被消费，决定了上游变化时**故障面有多大**，以及变更通知能不能到达消费方。

**各候选的实现差异**：

| 交付形态 | 消费方拿到什么 | 上游把这张表重命名时，谁要改 |
| --- | --- | --- |
| 物理表 / 视图 | 列名与类型 | 每一个直接查表的作业、报表与模型特征 |
| 指标 | 一个已定义的量（口径在平台内固化） | 平台侧改映射，消费方不动 |
| API 契约 | 输入 / 输出 schema 与 SLA | 注册表内改 `source_asset`，消费方不动 |
| 事件推送（D2 Push） | 变更事件流本身（订阅的是「变更」，不是表状态） | 上游改表结构不打断订阅关系；但事件的 schema 变更要走版本，且消费方按投递语义自行去重 |
| 可调用资产（AI 资产化） | 带 Owner、SLA、契约的调用单元 | 资产定义内改，调用方与 Agent 不动 |

**由此必然导出的性质**：因为 OneService 的注册表 `source_asset` 指向资产（DWS / ADS 或指标名）而不是物理表名，所以上游换表、改名、换引擎对消费方不可见；代价是每个接口多一份契约与一个必须维护的兼容期，下线旧版本要走废弃流程。反过来，因为「视图 + 直连物理表」交付成本最低，所以它在团队规模小时最优；代价是上游改一列名会直接穿透到消费方代码——**而且没有任何机制会把这次变更通知到那些消费方**，故障面不可枚举。事件推送是这张表里唯一不以「当前值」交付的形态：因为交付的是变更本身，所以订阅方必须自己处理投递语义——**至少一次意味着可能收到重复事件，精确一次则要付出事务或去重的协调成本**；这层语义由消息中间件定义，不在交付契约里，因此事件推送不能替代 API 契约对「当前值是多少」的承诺。

**公开证据**：上表第四行「事件推送」这一消费形态与它的投递语义（至少一次 / 精确一次）的定义见 Apache Kafka 官方文档「Design」章的「Message Delivery Semantics」一节（kafka.apache.org/documentation），其中精确一次所依赖的幂等生产者与事务自 Kafka 0.11 引入【公开，2017】；该章节随版本更新、无固定出版年份，具体语义请以官方文档当前版本与对应版本的 Release Note 为准；OneData 体系里「智能体平台消费标准数据底座」这一层的位置见主文件 §1.3 的角色表（本仓库内可逐行核对）；AI 资产化与 Agent 自动取数的能力划分见 [§ 5 前沿演进](08-one-data-section-5-ai.md)。

**失效条件**：当 API 只是「物理表的代理」时（接口参数与表列名一一对应、没有缓存与限流），优点（接入快）会反转成缺点（上游一改就全线故障、热点查询直接穿透到 OLAP 集群）。判定方法是一句话：**上游把这张表重命名，有多少个消费方要改代码**——答不上来，说明它是代理而不是服务。

**AI 时代新增的约束**：Agent 会在一次任务里连续调用多个取数接口，于是「谁调用了什么」这件事从人的一次点击变成了机器的几十次调用。这对交付形态有两处影响：一是接口必须能表达「这次调用属于哪个任务」，否则审计只能记下一串无关联的请求；二是返回给 Agent 的必须是**已定义好的量**（带口径与口径版本的数值），而不是原始列——把原始列交给模型，等于把口径定义权交给模型去猜。

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本不是一个数，而是几个不同形状的函数之和：

```
总成本 ≈ 中心治理团队人力（固定项，最容易被低估）
        + f(表数 × 源变更频率 × 单次回刷量)      ← 回刷成本，随时间累积
        + g(指标数 × 归并轮次)                    ← 口径归并与评审
        + h(标识数 × 冲突代价)                    ← OneID 合并、回滚与下游重算
        + i(接口数 × 契约维护与兼容期)            ← 服务化
        + j(域数 × 每域数据产品负责人编制)        ← 自治范式的组织成本
        + k(资产数 × 权威元数据的完备度)          ← AI 消费的前置成本
```

**哪个候选的主导项是什么**：

| 候选 | 主导成本项 | 隐性成本（常被漏算的那一项） |
| --- | --- | --- |
| 维度建模 | f：回刷 | ADS 层是唯一被允许「一个需求一张表」的层，双胞胎表在这里长出来 |
| Data Vault | 对象数量带来的加载与存储 + 信息集市人力 | 没有集市时，每个消费者各自实现「取每个卫星表的最新行」，解耦收益被重复开发吃掉 |
| OneData 全套 | 固定项：中心治理团队 | 绕开定义中心的取数——它不产生账面成本，但它产生口径 |
| 指标平台 | g：口径归并 | 原子指标层的一次全组织对齐，其耗时往往超过平台本身的建设周期 |
| OneService | i：契约与兼容期 | 缓存一致性策略，处理不好会得到「刚改完数还是旧的」这类事故 |
| Data Mesh | j：每域的数据产品负责人 | 跨域指标的对账成本，发生在集团层，不在任何单域预算里 |
| AI 资产化 | k：权威元数据的完备度 | 生成物污染：没有权威可对照时，模型生成的业务含义看起来总是合理 |

【推算】回刷成本可以量化，这是「什么时候该引入整合层」的唯一判据。设某个按天分区的明细表保留 3 年、单分区体积 2 GB、当日可用计算窗口按 20 TB 量级估算（这三个数是假设值，请替换成你口径下的真实值），则一次全量回刷量 = 1095 × 2 GB ≈ 2.19 TB，占掉当日窗口约 11%（推导链：1095 × 2 = 2190 GB ≈ 2.19 TB；2.19 ÷ 20 ≈ 0.11）。若一年发生 12 次源结构变更，累计回刷 ≈ 26.3 TB，相当于 1.3 个以上的计算窗口（推导链：12 × 2.19 = 26.28 TB；26.28 ÷ 20 ≈ 1.31）——在源系统稳定时这笔钱花得没有意义，在源系统每周变更时它会把窗口吃光。

【推算】中心团队的评审带宽是另一个线性项。设中心治理团队 10 人、覆盖 1 万张表、每表年均变更 1 次、单次元数据评审 30 分钟，人均年可用工时按 1600 小时估算【经验】，则评审需求 = 10000 × 1 × 30 ÷ 60 = 5000 人时/年，团队年容量 = 10 × 1600 = 16000 人时，评审占约 31%（推导链：5000 ÷ 16000 ≈ 0.31）。表数增长 10 倍而人力不变时，需求变为 50000 人时、超过容量 3 倍以上——此时唯一可行的是把评审从「逐表」改为「规则自动校验 + 抽样 + 门禁阻断」。**这就是规范必须机器可读的机制动因，不是工具偏好。**

【经验】本主题的成本排序在百级表与万级表上会反向：百级表时人力可忽略、方法论的适配成本主导；万级表时 f 与 g 两项的线性增长超过一切工具费。因此「哪套方法更便宜」在跨规模时没有稳定答案。

还有两项常被漏算，而它们往往才是决定项。**第一是「配套层」的强制性**：Data Vault 不带信息集市、OneData 不带 Owner 制度与门禁、Data Mesh 不带各域的数据产品负责人编制，都不是「简化版」而是**半成品**——它们会在第一次真实变更时失效。评估方案时必须把配套层一并计入成本，否则比较的是两个不同完成度的东西。**第二是绕行成本**：中心化方案里，绕开定义中心的一次取数不产生账面成本，却会产生一个永久的口径；自治方案里，跨域指标的一次对账不落在任何单域预算里。这两笔成本都不出现在任何一方的账上，却决定了体系两年后还剩多少一致性【经验】。

### 7.5 决策树（每个分支都要有阈值依据）

```
① 组织里有没有一个能对「口径」做最终裁决的具体角色（不是委员会）？
├─ 否 → 先立裁决权与门禁；在此之前，任何建模方法都停在文档层（见 [§3.5](08-one-data-section-3-sec3.md) 陷阱）
└─ 是 → 下面三棵并列，逐棵问完；一棵的答案不构成另一棵的前置条件（冲突时的排序规则见表后）

【第一棵 · 模型怎么切（回答「锚点」）】
② 组织规模与业务线形态？
├─ 小型创业、单一业务线、表数百级 → 不建 OneData 全套：先做命名规范 + Owner 制度
├─ 中型、单一业务线为主、表数千级 → 维度建模公共层 + 基础 OneData（指标 + 主数据）
└─ 大型 / 集团级、多 BU、表数万级 → 继续 ③
   ③ 源系统表结构一年会改几次？
   ├─ 基本不改 → 维度建模主导（模式 A）
   └─ 高频改（或源系统 10+ 且各自变更）→ Data Vault 作贴源整合层 + 其上重建信息集市（模式 B）
      ④ 业务形态是「稳定重合规」还是「高速变化」？
      ├─ 稳定重合规（金融 / 保险 / 电信）→ Data Vault + OneData（主数据 + 指标）
      ├─ 高速变化（互联网 / 电商）→ 维度建模公共层 + OneData（指标 + 服务化）
      └─ 多元化集团 → 中心标准 + 自治分层；锚点仍由 ③ 决定，分层方式交给第二棵的 ⑥

【第二棵 · 口径、所有权与交付形态（四个问题并列，每个组织都要逐条问）】
⑤ 是否存在「一个实体在多个源系统出现、且强标识不全量可得」？
├─ 是 → 建 OneID（C1 定连通分量 + C2/C3 提议合并 + confidence + 可回滚）
└─ 否 → 不建 OneID 服务，直接用源系统主键
⑥ 标准由中心强制，还是由业务域自治？
├─ 中心有授权（一把手工程 + 建表门禁可阻断）→ OneData 全套（定义权与门禁都在中心）
└─ 中心无授权、各域已有数据负责人编制 → Data Mesh 的域内所有权 + 联邦计算治理
⑦ 同一指标是否被 3 个以上团队各自计算？
├─ 是 → 指标定义中心（三级指标结构 + 版本化）；域自治时以联邦形式落地——定义权在中心、生产权在域内（7.6 组合 3）
└─ 否 → 口径先写在文档与 SQL 注释里，等出现第一种争议再建中心
⑧ 消费方是人，还是应用 / Agent？
├─ 人（报表工具）→ 视图 + 公共层即可，不必上服务契约
└─ 应用 / Agent → OneService（契约 + SLA + 鉴权，`source_asset` 指向资产）

【第三棵 · AI 走到哪一步（与前两棵并列，每个组织都要问）】
⑨ AI 是核心业务、辅助能力，还是尚未介入？
├─ 核心 → 指标即特征（特征复用指标定义）+ AI 资产化
├─ 辅助 → 只做 AI 增强的元数据（辅助 + 人审），不上资产化
└─ 尚未介入 → 先让口径机器可读，不引入 LLM 生成链路
   └─ ⑨ 答「核心」或「辅助」时继续 —— ⑩ 元数据增长是否已超出人力能维护的速度？
      ├─ 是 → AI 增强（辅助 + 人审）；Agent 只放在有客观判定标准的任务上
      └─ 否 → 不引入生成链路（生成物无权威可对照时只能算草稿）
```

**三棵并列，但有一条排序规则**：第一棵必须先定，因为口径载体与交付形态都建在模型之上。三棵之中只有一处会反向改写第一棵——第二棵的 ⑥：域自治时，②③④ 的选择权落到域内，中心只保留标准与互操作约定（7.6 组合 3），⑦ 的问法不变（谁都不希望同一指标有两个值），但落地形态从「中心裁决」变成「联邦协商」。第三棵不改变前两棵的结构，它只决定要不要在既有口径之上再加一层机器可读的消费形态。**并列而不是嵌套，是为了让每一棵树都被问到**：一个组织有没有跨域去重需求，与它的标准是中心强制还是域自治无关；有没有 AI 需求，与前两棵的答案也无关——串成一条链，排在后面的问题就永远问不到。

**阈值依据**（与树上每个判断节点一一对应）：

- **① 有没有口径裁决角色**：依据是本主题的机制只把口径变成**可比较的元数据**，而「哪个口径对」是业务价值判断，结构上给不出（7.3.2）。没有裁决者时，定义表里并存的两行冲突无人能宣布哪一行是权威。
- **② 组织规模与业务线形态**：三个分支的边界不是人数，而是「表数 × 是否多业务线」决定的评审负荷。按 7.4 第二条推算的参数（10 人团队、年容量 16000 人时、每表年均变更 1 次、单次评审 30 分钟）代进去：百级表 = 100 × 1 × 30 ÷ 60 = 50 人时，约占容量 0.3%，规范靠自觉与人工评审就能维持；千级表 = 500 人时，约占 3%，仍不构成瓶颈，但已需要公共层来收敛重复建模；万级表 = 5000 人时，约占 31%，评审本身成为一项需要专人承接的常态工作，这时才需要中心团队与门禁。**分界点是评审需求占人力容量的比例，不是人数。**
- **③ 源结构变更频率（含「源系统 10+ 且各自变更」这一步）**：前半个判据的依据是 7.4 的回刷推算——可操作化的口径是「一次源变更所需的回刷量是否超过当天可用计算窗口」，且因为分区数等于保留天数，**这个阈值会随保留时长收紧**（保留 3 年与保留 3 个月，同样的变更频率会得到相反答案）。后半个判据「10+」要解释两件事：**(a) 为什么自变量是「独立变更的源系统数」而不是变更总量**——回刷按事件触发，不同源系统的变更落在同一批下游模型上，成本按事件相加而不互相抵消，所以决定负荷的是「有多少个源在各自变更」；**(b) 为什么量级是 10**——按 7.4 的前提（单源年均变更 1 次、单次全量回刷 2.19 TB），10 个源即 10 次/年，累计 ≈ 21.9 TB ≈ 1.1 个计算窗口（推导链：10 × 2.19 = 21.9 TB；21.9 ÷ 20 ≈ 1.1），与 7.4 里「12 次变更 ≈ 1.3 个窗口」同量级；同时 10 ÷ 52 ≈ 0.19 次/周，意味着平均每 5 周就有一次源变更要沿链路评估，维护从「一年几次的项目」变成常态负荷。**「10+」是量级标记而非悬崖**：5 个源与 20 个源之间是连续的，判据要连着保留时长一起看。
- **④ 业务形态**：依据是两类约束的组合。稳定重合规的业务要求「任何时点可重述 + 逐条可审计」，这是 Data Vault 的卫星表结构直接提供的；高速变化的业务要求「新业务过程能快速落成一张明细表」，这是维度建模的分层结构直接提供的（7.3.1）。
- **⑤ 实体是否多源出现且强标识不全量可得**：依据是只做强匹配时，OneID 覆盖率上限等于最强标识的可见率（见 [§3.2.3 的推算](08-one-data-section-3-sec3.md)）；若标识全量可得，则 OneID 服务是一层没有对应收益的常驻组件。这一步与 ⑥ 的答案无关，无论中心强制还是域自治都要问。
- **⑥ 标准由中心强制还是由域自治**：依据是 7.3.3——中心化的强制力来自「门禁能阻断一次建表」，自治的前提是「各域已有数据负责人编制」。这两个条件互斥地决定路线，判据是中心团队能否真的阻断一次不符合规范的建表上线。
- **⑦ 同一指标被 3 个以上团队各自计算**：依据【经验】——1 到 2 个团队时口径可以靠人对齐；3 个以上时对不齐的原因是各方对「这个业务量该不该含退款、含不含税」这类判断本身持不同业务立场，靠沟通无法收敛，必须落到可定位的字段差异上（7.3.2）。**这一步对 ⑥ 的两个分支都要问**——域自治改变的只是它的落地形态（联邦协商而非中心裁决），不改变「3 个以上就该落成定义」这条判据。
- **⑧ 消费方是人还是应用 / Agent**：依据是「上游把这张表重命名，有多少个消费方要改代码」——人查报表时改一处，应用与 Agent 时改 N 处且没有变更通知渠道（7.3.4 失效条件）。
- **⑨ AI 的优先级**：依据是 AI 资产化的主导成本项 k 是「权威元数据的完备度」；只有当特征要复用指标定义、且模型效果必须能归因回业务口径时，这笔成本才被摊薄。AI 只是辅助能力时，先做元数据的 AI 增强（辅助 + 人审）就够。这一步独立于前两棵：模型锚点与所有权归属不改变「AI 在这个组织里是主线还是辅助」。
- **⑩ 元数据增长是否超出人力**：依据是 7.4 的评审带宽推算（同 ② 的参数：万级表时评审约 5000 人时/年、占容量约 31%，再翻一个数量级即超过容量 3 倍）——「超出人力」的可判定形式就是这个比例。生成物能否被接受，取决于是否存在可对照的机器可读权威（命名语法 / 指标定义表 / 血缘图）；没有权威时生成物无法被判定对错，只能停在草稿（7.3.2）。这一步只对 ⑨ 答「核心」或「辅助」的组织有意义——AI 尚未介入时，不存在「生成物能不能被接受」这个问题。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 表数百级、单一业务线 | 命名规范 + Owner 制度 | 直接上 Data Vault | 不选 Data Vault：对象数量多一个数量级【经验】，收益（源系统解耦）在这个规模用不上 |
| 业务过程稳定、查询形态不可预知 | 维度建模主导 | Data Vault 主导 | 不选 Data Vault：源系统稳定时，多出的对象与查询复杂度是纯成本 |
| 多个源系统各自频繁变更（「10+」量级判据见 7.5 依据③）、要求可审计 | Data Vault 主导 + 信息集市 | 维度建模直贴源系统 | 不选纯维度建模：每次源变更都要回刷事实表，回刷量随保留时长累积（7.4） |
| 跨域去重指标（集团 UV / 复购） | OneID（C1 + C2/C3 + 可回滚） | 只做 C1 强匹配 | 不选只做 C1：覆盖率被钉在最强标识的可见率上，业务方会绕过 OneID 自己拼 ID |
| 同一指标被多团队重复计算 | 指标定义中心 | 报表 + 文档 | 不选报表 + 文档：口径散落在 SQL 与文档里，冲突在结构上不可定位 |
| 消费方是应用 / Agent | OneService（契约 + SLA + 鉴权） | 视图 + 直连物理表 | 不选直连：上游改列名即全线故障，且没有渠道通知消费方 |
| 多域自治、中心无授权 | Data Mesh（域内所有权 + 联邦治理） | OneData 全套 | 不选 OneData 全套：缺少授权时门禁无法阻断，规范会停在文档层 |
| AI 是核心业务 | 指标即特征 + AI 资产化 | 另建特征平台 | 不选另建特征平台：特征与指标两套口径必然分叉，模型归因与业务复盘对不上 |
| 集团 / 跨集团 | OneData 中心标准 + Data Mesh 自治层 + AI 资产化 | 单靠 OneData | 不选单靠 OneData：万级表下中心评审带宽会先于表数触顶（7.4 推算） |

**常见组合 1：OneData + 维度建模**

- **职责边界**：维度建模是「模型怎么切」的方法，OneData 是「怎么让它被强制执行」的工业化机制。OneModel 采用维度建模作为具体实现，分层与命名规范负责把方法变成可检查的结构约束。
- **运维代价**：多一轮建模评审与建表门禁；公共层需要一支独立团队与落到人的 Owner，否则 DWD 会被各业务方各自加列。

**常见组合 2：OneData + Data Vault**

- **职责边界**：Data Vault 处理「源系统复杂、变化频繁」的接入与历史保真；OneData 处理建模标准、指标、主数据与服务化。前者只管把源系统完整、可追溯地接进来，**口径全部在后者的指标层定义**。
- **运维代价**：两层加工链路与两套质量校验，任何源字段变更要沿链路评估两次；卫星表版本会持续增长，需要配套的存储与查询策略，否则信息集市层被拖慢。适用金融、保险、电信这类源系统多且受监管的场景。

**常见组合 3：OneData + Data Mesh**

- **职责边界**：Data Mesh 让各 BU 对自己的数据产品负责；OneData 提供联邦式的统一标准（命名、指标互操作、主数据）。这是 7.3.3 那条权衡的折中形态：**定义权在中心、生产权在域内**。
- **运维代价**：需要一套联邦治理机制（谁在什么条件下能否决一个域的口径），否则冲突会在集团层堆积；中心团队的角色从「生产者」变成「标准与裁决者」，编制与考核方式都要改。适用超大型、多 BU 的集团。

**常见组合 4：OneData + AI 资产化**

- **职责边界**：OneData 沉淀指标、主数据与服务；AI 资产化把它们打包成带 Owner、SLA 与契约的可调用资产，AI 项目直接消费而不重建口径。边界是：**OneData 负责「这个量是什么」，AI 资产化负责「它怎么被调用」。**
- **运维代价**：资产元数据的质量成为 AI 侧故障的主要来源；资产定义变更要通知到模型侧，否则会出现「指标改了、特征没重建」的静默偏差。

**常见组合 5：OneData + GraphRAG / 智能体**

- **职责边界**：OneData 的服务暴露为 Agent Tool，OneID 与指标定义作为 Agent 的知识库，指标服务承担数据问答。边界是：**图谱负责「关系」，指标定义负责「口径」，两者都不能被模型自行推断**。
- **运维代价**：语义层成为取数链路的单点，它不可用时 Agent 无法取数；治理动作须以降级为「可驳回的提案」为前提，否则一次错误提案会以变更的形式生效。

五组组合有一个共性代价值得单独说：**每一组都要维护一份「口径的权威副本」**。组合 1 与 2 里它是分层规范与命名语法，组合 3 里它是联邦治理的裁决规则，组合 4 与 5 里它是 `metric_definition` 与资产元数据。这份副本一旦与物理实现分叉（规范改了表没改、定义改了物化没重建），组合里所有组件都会各自按自己那份副本工作，而分歧只在业务对账时才暴露。因此在选组合之前先回答一个与产品无关的问题：**这份权威副本由谁维护、多久校验一次、校验失败时是阻断发布还是只告警**。这个问题的答案，比组合里选哪套方法更能决定两年后你手里还剩多少可用的口径【经验】。

### 7.7 选错的代价与迁移成本

**反模式①：把「更先进」当成选型依据** —— 症状是选型材料里列的是「谁更新、谁更火」，没有一行写「我的源系统一年改几次」；后果是在源系统稳定的场景上选了 Data Vault，付出一个数量级的对象数量加一层必须自建的信息集市，而它的收益（源系统解耦、任意时点重述）在这个场景里根本用不上；正确做法是先回答 7.5 的节点③，再谈方法。【经验】

**反模式②：指标平台只做取数** —— 症状是平台上有报表、没有指标定义表、没有口径版本；后果是每个团队的口径被同时接入平台，冲突被固化并获得权威外观，比散落时更难发现（大家默认「平台上的就是对的」）；正确做法是定义中心、口径管理、血缘追踪与报表同时上线，判定方法是查同一个指标名在定义表里有几行。【经验】

**反模式③：OneID 只做强匹配，后补弱匹配却不留置信度与回滚** —— 症状是映射表里没有 `confidence`、没有 `evidence`、没有有效期；后果是假合并静默发生——两个真人被并成一个后，UV、复购、留存、去重口径同时错，而系统不会报错；正确做法是 C1 定连通分量、C2/C3 只做提议合并，每条合并留依据与有效期，使错误可定位可回滚。【经验】

**反模式④：OneData 与 AI 项目脱节** —— 症状是 AI 团队另建特征平台，特征定义与指标定义各说各话；后果是同一个业务量在指标侧与特征侧有两个值，模型效果归因与业务复盘无法对齐；正确做法是让特征复用指标定义，把 OneData 升级为 AI 数据的信任源。【经验】

**换成另一个要动什么**：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 | 量级判断 |
| --- | --- | --- | --- | --- | --- |
| 维度建模 → Data Vault | 不动原始数据，但要重新组织一次历史 | 全部消费侧 SQL 要重写（对象结构变了） | 新的加载器、哈希去重、迟到数据处理 | 建模规则与卫星表读取方式 | 大——查询侧几乎全量返工 |
| Data Vault → 维度建模 | 同上，反向 | 全部消费侧 SQL 要重写 | 去掉信息集市层 | 分层与命名规范 | 大——同样是一次全量改写 |
| 报表 + 文档 → 指标定义中心 | 不动数据 | 消费侧从「查表」改为「调指标」 | 指标平台与物化调度 | 三级指标结构与口径评审流程 | 中到大——平台建设之外还要一轮全组织口径归并 |
| 视图直连 → OneService | 不动数据 | 消费侧从「查表」改为「调接口」 | 服务注册表、缓存、限流、鉴权 | 契约设计与兼容期管理 | 中——每个接口要定义契约与废弃流程 |
| 中心标准 → 域自治（或反向） | 不动数据 | 一般不动 | 治理机制重建：评审权、裁决权、门禁位置 | 组织角色与考核方式 | 大——这是组织变革，不是技术迁移 |
| 另建特征平台 → 特征复用指标定义 | 特征要重建或映射 | 训练与服务链路要改取数入口 | 特征生产线与指标平台打通 | 口径一致性校验流程 | 中——技术上可分批，但要求口径先归并 |

判断量级的通用口径是：**动数据 > 动查询 > 动运维 > 动培训**。本主题里最贵的一次迁移通常是「维度建模 ↔ Data Vault 互转」，因为它把查询侧几乎全部返工；而最容易被低估的是「中心标准 ↔ 域自治」，因为它看着像流程调整，实际动的是裁决权归属。

还有一条不在表里的迁移成本需要单独记：**口径的历史**。任何一次口径变更都要决定「历史数据按新口径重述，还是保留旧口径并按变更时点分段」。这两种选择会让同一张报表在迁移前后出现不同的历史曲线，而它们各自的成本落在不同团队身上——重述的成本落在平台侧（重算），分段的成本落在消费侧（每次对数都要先问「这是哪个时段的口径」）。这个决定没有技术上的正确答案，但必须在迁移方案里显式写出来，否则它会在半年后以「数据对不上」的形式重新出现。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 表数百级、单一业务线 | 命名规范 + Owner 制度 | 评审带宽够用，先建立可检查的命名与责任，不必上全套 |
| 业务过程可枚举、源系统结构稳定 | 维度建模主导（模式 A） | 业务过程有限，口径冲突变成可检查的结构约束；代价是源变更要回刷 |
| 源系统多且高频变更、要求可审计 | Data Vault 主导 + 信息集市（模式 B） | 属性只进卫星表，源变更只影响一个对象；代价是必须自建集市 |
| 强标识不全量可得、要跨域去重 | OneID（C1 + C2/C3 + 可回滚） | 概率合并留依据，错误可定位可回滚，不是不可逆污染 |
| 同一指标被多团队重复计算 | 指标定义中心 | 三级结构让口径差异落到字段上，变成可判定的分歧 |
| 消费方是应用 / Agent | OneService | 契约与物理表解耦，上游改名对消费方不可见 |
| 多域自治、中心无授权 | Data Mesh | 所有权下放后标准只能靠自助能力被采用；代价是跨域口径无裁决者 |
| 中心有授权、要跨域一致 | OneData 全套 | 定义权集中在中心，门禁能阻断违规建表；代价是评审带宽成为瓶颈 |
| AI 是核心业务 | 指标即特征 + AI 资产化 | 资产带 Owner、SLA 与契约，模型归因能回到业务口径 |
| 元数据增长快于人力 | AI 增强（辅助 + 人审） | 生成物以机器可读权威为输入才能被校验；无权威时它只是草稿 |

这张表的每一行都可以用一句可验证的话复述，因此它不依赖任何人的判断力：源系统一年改几次（行 2、3 的分界）、最强标识的可见率是多少（行 4）、上游改名时要改几个消费方（行 6）、中心团队能不能阻断一次建表（行 7、8）、生成物有没有权威可对照（行 10）。**如果一个问题答不出来，说明选型还没到可以做决定的阶段，而不是说明需要更多比较。**

> 本节小结：本主题的候选不是一堆可互换的方法，而是**四种不同问题的答案**——模型怎么切、口径存在哪、资产归谁、谁来消费。**唯一真正起决定作用的差异是「口径的裁决权放在中心还是放在域」**：它同时决定了跨域一致性、灵活度、成本函数的形状，以及标准靠什么落地（门禁还是自助能力）。其余差异（维度建模还是 Data Vault、强匹配还是弱匹配、契约还是代理）都是这条主轴上的次级选择，且各自的答案都能用一句可操作的话问出来——**源系统一年改几次、最强标识的可见率是多少、上游改名时要改几个消费方**。
