## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

主文件把 OneData 定义成三件套 **OneModel / OneID / OneService** 加数据标准与指标体系两条横线（主文件 §1.1），而本章把它反复归结到同一条约束上：**一个企业只能有一套口径**（[§ 3](08-one-data-section-3-sec3.md) §3.1）。这条约束在 AI 之前就已经决定了本章的四个卡点：**口径必须有唯一载体**，载体的形态决定两个团队算出两个 GMV 时冲突能不能被结构定位（[§ 7](08-one-data-section-7-sec7.md) §7.3.2）；**定义权收在中心**，落地就依赖门禁真的能阻断一次不符合规范的建表（§7.3.3）；**元数据的增长速度超过人能维护的速度**（§3.2.6 的约束，§7.4 还给出评审带宽的推算：1 万张表、年均变更 1 次、单次评审 30 分钟，年需求 5000 人时，占 10 人团队年容量的约 31%，表数翻十倍而人力不变时需求超过容量 3 倍以上）；**治理动作的发生频率跟不上资产变化频率**（§3.2.7 的约束）。成本上还有一条前置项：§7.4 把「资产数 × 权威元数据的完备度」单列为 k 项，它是 AI 消费的前置成本。

所以本节要判的不是「AI 能不能接进 OneData」，而是 **AI 改变了哪一件事**。答案集中在一条上：**元数据的「生成」成本从人挪到了模型，而元数据的「权威」一步也没有移动**——权威始终在三样可机器读的东西里：命名语法（主文件 §2.3 方法⑥）、指标定义表 `metric_definition`（§3.2.5）、血缘图（§3.2.6 的「SQL 解析产出的字段级血缘」；§7.2 的 B 族行也把血缘列为机器可读权威之一）。这句话是本表所有评级的依据：**凡是只改变生成成本的，值得试点；凡是试图移动权威位置的，一律停在 L3。**

本节用 L1 / L2 / L3 三级区分，判据必须可核验，而不是「感觉成熟」：

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口 / 生态未稳，或**仅有厂商与建设方自有案例**，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

**本节不对 L1 判据做任何修正，也不缩小它的适用范围。** 本主题最容易放宽的是第②条：OneData 领域有一大批公开的工程文章、开源项目与厂商能力，很容易把「有公开的机制性材料」读成「有第三方生产案例」。但**建设方与厂商自述按判据读就是 L2 的定义**——[§6](08-one-data-section-6-sec6.md) 的阿里 / 字节 / 美团 / Netflix 四个案例，出处是「机构名 + 年份区间」，属建设方自述。另有一条纪律：**与 AI 无因果关系的成熟做法**（分层规范、命名门禁、指标定义表、服务契约）**本身不是演进方向**；本节只保留原清单里确实被写进「AI 时代」的那几条（DataOps、Data Mesh、实时与湖仓），并在表里显式标注「与 AI 无因果关系」。

还有四件容易混的事，先在这里分开：

- **能力名 vs 产品名**：「指标问答」「智能血缘解读」「自动 Owner 推荐」是**能力名**，不是某个产品的专属功能。[§ 4](08-one-data-section-4-sec4.md) §4.3 的「OneData 4.0 / AI 增强工具」表用的是各家自己的措辞（如「LLM 辅助建模 / SQL 生成」「AI 辅助血缘 / 指标文档」「智能指标 + RAG」），同一能力在不同产品里既可能叫法不同，也可能只覆盖其中一项——该表里没有「自动 Owner 推荐」的对应条目。判定方法：按**产品全名 + 该能力的输入与输出**核对，两者都能对上，这条归属宣称才算成立。
- **书本的阶段划分 vs 产品版本**：主文件 §1.4 的「OneData 1.0 / 2.0 / 3.0 / 4.0」「OneData × Agent」是**本书对方法论的阶段划分**，不是任何一家厂商的产品版本号。把「4.0」当成发布物去找 release note 会找不到——要核验具体能力，只能看各产品的官方文档当前版本。
- **论文原型 vs 产品实现**：论文演示的是**方法可行性**，产品实现要受权威元数据是否存在这一前提约束（§3.2.6）。判定方法：看该实现有没有显式暴露「生成物是否经过人审、是否带来源指针」。
- **方法论 vs 产品**：Data Mesh、DAMA-DMBOK 一类是**方法论与知识体系**，不存在「它支持某特性」这回事。判断一个组织实际走哪条路线，看的是**裁决权落在谁手里、门禁能不能阻断**（§7.3.3），而不是文档里写了哪个名词。

本节对每个方向都问同一句：**AI 改变了哪个机制**——改变了成本函数、改变了接口边界、把人工判断换成了统计判断，还是只换了个前端？本主题的答案是**一条来自模型能力的机制**加**一条与模型能力无关的形态变化**：**第一条**是元数据的生成成本从人挪到模型（§3.2.6），它改变的是**元数据能被补全的规模**；**第二条**是资产的交付形态从「表 / 报表」换成「可被程序按语义调用的契约」（§7.3.4 的交付形态表），它改变的是**谁在消费资产**——而第二条与模型能力无关，它是 API 化与治理的延续。

> 表里**没有任何一行达到 L1**，原因不在技术，而在公开材料的构成：可核验的只有**厂商产品材料**、**开源项目文档**、以及**本书内部的机制定义**三类，其中没有一条可指认的第三方（非厂商）公开生产案例。而 OneData 里真正在生产跑了多年的那一半——分层规范、命名门禁、指标定义表、服务契约、CI/CD——**不是 AI 方向**，它们的公开案例（[§6](08-one-data-section-6-sec6.md) 的四个）全部是建设方自述，按同一判据同样是 L2。**L2 不等于「不好」，只等于「公开证据到不了 L1」**；要警惕的是把 L2 当 L1，于是把「可以先试」读成「可以依赖」。

**这三级的排法直接决定路线图的顺序**：

- **先做的三件事不在表里**，因为它们是 AI 之前的既有能力，却又是每个方向的评估前提：把命名规则与指标定义做成机器可读（§3.2.6 的前提）→ 把建表与口径变更挂进门禁（§7.3.3）→ 把「同名指标在 `metric_definition` 里有几行」做成一个能被查询的数（§7.3.2）。没有这三件事，模型生成的东西没有权威可对照，Agent 提出的提案也没有地方生效。
- **L2 做 PoC，并先测两个数**：生成物的采纳率（人审通过多少条）与提案的误报率（Owner 驳回多少条）。这两个数拿不出来，L2 就停在原地，与选哪家产品无关。
- **L3 不排进排期**：自动改数、Agent 直接搬运表建分层（不是给建议）、自治裁决、GraphRAG 都属于「等信号」，它们的共同前提是**权威口径先被宣布**。
- **回填机制**：每次治理复盘时回填一次级别；某个 L2 若在一年内【经验：随资产数与变更频率变，变更多的可缩到半年，资产少、变更慢的可放宽到两年】仍拿不到你自己组织里的实测量（采纳率、误报率、同名指标的行数），降 L3 并停止投入。

**本节表与 §5.2 的逐项评估是同一份结论的两种呈现**，两处的级别与「①②③哪几条满足」逐字一致：§5.2.1 对应第 1、2、3 行（均 L2），第 4 行「自然语言问数」也评在那里（同一套机制的另一个用途，L2）；§5.2.2 对应第 5、6、7 行（L2、L3、L2）；§5.2.3 对应第 8、9、10 行（L2、L3、L2）；§5.2.4 用一张表覆盖第 11、12、13、14 行（L3、L2、L2、L2）。第 15 行不单独展开——它是前四组能力的并集，机制与失效方式分别写在 §5.2.1–§5.2.3 与 §5.5 第二条里。将来若要改判，两处一起改。

**原条目去向对照**：原方向①的五项落第 1、2、3、4 行；原方向②的三项落第 8、9、10 行；原方向③的四项落第 5、6、7、4 行（第 4 项「跨部门数据发现」是消费侧入口，与指标问答同源）；原方向④落第 11 行；原方向⑤落第 12 行；原方向⑥落第 13 行。原 §5.2 的三组结合（指标 RAG / OneID × 知识图谱 / OneService × Agent Tool）分别落第 4、11、10 行。原 §5.3 的五条学术条目给的是主题名而非可检索标题（DAMA-DMBOK 3.0、指标优先设计模式、数据产品思维、AI 原生数据治理、知识图谱 × 主数据），本节保留它们所指的四个方向（元数据治理体系 / 指标优先 / 资产化 / 图谱融合），不把它们当证据，判定入口见 §5.4；九条工业条目按能力落第 2、3、4、8、9、10 行（阿里 DataWorks Copilot 的指标文档化与火山引擎 DataFinder 的智能指标平台落第 2 行；字节 DataLeap AI 的智能血缘解读与智能 Owner 推荐落第 3 行；DataFinder、Databricks Unity Catalog + Genie、神策 AI Agent 的问答落第 4 行；美团数据中台 2.0 的「OneData 与 AI 资产化」落第 8、9、10 行），其中 Snowflake Cortex、Microsoft Fabric + OneLake、京东 JD OneData 5.0 是平台级条目，本节只作方向指认，不逐条断言其能力；五条平台新特性落第 2、14、10、12、14 行。原 §5.4 的七条趋势一条不丢：趋势②③④⑤⑥分别落第 8、9、10、13、14 行，趋势⑦（AI 驱动的治理）落第 5、6 行，趋势①（Agent 自治）落第 5、6、7 行，并由第 15 行承接其平台化的一面。

### 5.2 演进方向逐条拆解（核心节）

下面把方向分成四组：**前三组按同一套结构逐条写**（旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度），**第四组用一张表覆盖同一套要素**，因为那一族的共同点恰恰是「机制没变」。四组共用 §5.1 的两条机制（生成成本、交付形态），差别在**它落在哪一层**。

| 方向 | AI 改变了什么机制 | 这条变化落在哪一层 |
| --- | --- | --- |
| §5.2.1 LLM 辅助建模与文档 | 把「同一份权威渲染成另一种形态」这一步交给模型 | **生成层的成本函数**（权威不动） |
| §5.2.2 Agent 治理回环 | 治理动作的触发从人的排期换成调度 + 扫描 | **执行边界**（提案与变更的分界） |
| §5.2.3 AI 资产化 | 同一份定义多了一类消费者 | **交付形态与接口边界**（与模型能力无关） |
| §5.2.4 机制没变的那一族 | 大多没有改变机制 | **既有能力的延伸与组织权衡**（与 AI 无因果关系） |

读法建议：时间只够读一节就读 §5.2.1——它是本主题里唯一一条**输入与输出都在书内可逐行核验**的变化（四项能力的输入各是一份已存在的机器可读权威，§3.2.6），它带来的问题（生成物与权威分叉、生成物污染）不需要任何新产品、也不必等第三方案例就能验证。[§ 4](08-one-data-section-4-sec4.md) §4.3 的「OneData 4.0 / AI 增强工具」表列的是各厂商的能力与措辞，**它证明的是能力存在，不是采用度**；这一层在一个组织里被用到什么程度，只能按该组织的生成物采纳率来量。§5.2.2 与 §5.2.3 的收益要等你把权威元数据与门禁做出来之后才兑现。

只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次「元数据成本降下来了」，都对应一处新的判断成本：**模型写出的业务含义要人去校，模型提出的冲突要人去裁，模型生成的文档要人去对**。这也是 §5.2.2 里唯一一项 L3（自动改数的写路径，表格第 6 行）比 §5.2.1 低一档的原因：不是它的技术更难，而是它的错误更容易被系统自己放大。

三节的顺序同时给出了实施的顺序：**先把生成物的来源与版本定下来（§5.2.1），再把治理动作限定在「可裁决的提案」上（§5.2.2），最后才谈把资产以契约形态交付给 AI（§5.2.3）**。反过来做——先让 Agent 每天报冲突、再补权威口径——得到的是一个用同一个错误互相印证的平台，而它看起来比原来更规范。

#### 5.2.1 LLM 辅助建模与文档（原方向①；原 5.3 的「指标平台 + LLM」）

- **旧做法与它的卡点**：命名评审、口径文档、血缘理解都是人力密集型工作，成本随资产数线性增长，而人对「给资产写业务含义」这件事的耐心有限（§3.2.6 的约束）。§7.4 把这条约束算成了数：1 万张表、年均变更 1 次、单次元数据评审 30 分钟，年需求 5000 人时、占 10 人团队年容量的约 31%；表数翻十倍而人力不变时需求超过容量 3 倍以上。**卡点不是人不会写，而是写不完。**
- **AI 改变了什么机制**：**把「把同一份权威渲染成另一种形态」这一步交给模型**。四项能力（命名规范校验、指标口径文档、血缘解读、业务含义与 Owner 推荐）的输入都是一份**已存在的机器可读权威**——命名语法、`metric_definition`、SQL 解析产出的血缘（§3.2.6 的结构把这条写死了）。**它不产生新的权威，它只换了一种呈现方式。**
- **由此得到的**：**因为每项能力的输入都可判定，所以生成物能被放进评审流程当辅助**——尤其命名的可判定性最实在：命名语法是规则级的，违规可以枚举，模型在这里补的是「语义层面的不合规」（同义异名、口径名与实现名不一致），而不是替代校验器。这是本主题里模型收益最可核验的一条。

```text
       同一份权威的两种渲染（模型的介入点在哪一格）
       ────────────────────────────────────────────────
       权威（机器可读，唯一）              渲染产物（可多份）
       · 命名语法                           · 表名 / 字段名建议
       · metric_definition                 · 指标口径文档
       · SQL 解析产出的字段级血缘            · 「这条链路在做什么」
       ────────────────────────────────────────────────
       旧做法：渲染由人做 → 成本随资产数线性增长 → 写不完
       新做法：渲染由模型做 → 生成便宜、审核仍贵
       ────────────────────────────────────────────────
       判定方法：改一次权威，看渲染产物会不会自己变
                 会 → 它是渲染产物；不会 → 它是第二份权威
```

- **由此付出的**：**其一，口径文档一旦由模型生成并被当作权威，就会与定义表分叉**——定义表改了、文档没重生成，而此时「两份权威」比没有文档更差（§3.2.6 的代价）。**其二，模型生成的业务含义是最容易被默认接受、最难被验证的一类元数据**——它没有编译错误可以暴露，而它会被检索与 RAG 直接消费；一旦错描述进入资产库，Agent 会以它为据做决策，且没有人知道它错在哪、错了几条。**其三，它把人力成本从「写」挪到「审」**——审的成本同样随资产数线性增长，只是斜率更低、且可分批；把它说成「省掉文档人力」是不准确的。
- **证据与来源**：【公开：本书 §3.2.6 给出四项能力各自依赖的机器可读权威、代价与失效点，§7.4 给出评审带宽的推算与 k 项（权威元数据的完备度）这一 AI 消费前置成本，均可逐行核对；主文件 §1.4 把 2023–2025 记为 OneData 4.0 / AI 增强阶段】。产品侧的代表见 [§ 4](08-one-data-section-4-sec4.md) 的「OneData 4.0 / AI 增强工具」表，其具体能力与版本以各家官方文档当前版本为准。**【本节未能核到】第三方（非厂商）公开生产案例**——即「某个非厂商组织公开过它生成的业务含义的采纳率与错误率」这类带口径的材料。
- **成熟度**：**L2**。判据：① 核不到（形态在书内可核验，产品侧只有厂商材料）；**②核不到**；③ 校验规则、生成物格式与来源指针各家不同 → 可做 PoC，不要做核心依赖。
- **判定方法**：抽 100 条生成物【经验：随资产数与评审带宽变，通常 50–300 条即可看出采纳率的量级】，请定义 Owner 逐条判「可直接采纳 / 需修改 / 不成立」，算出采纳率；再改一次定义表，看已生成的文档会不会自己变。**第一项决定它省不省人力，第二项决定它是不是第二份权威。**
- **什么时候值得做**：命名语法、指标定义、血缘这三样里已经有两样是机器可读的时候【经验：阈值取「两样」而不是「一样」的理由是——本节四项能力的输入分布在三种权威上，只有一样可读时生成物没有第二处可对照，错误只能靠人逐条读出来；这个阈值不随资产数或团队规模下调，资产少的团队同样按「不足两样先补第二样」处理】。
- **什么时候不值得做**：**不足两样的时候**——只有一样可读时，先补第二样，不要先上模型；三样都还停在文档与 SQL 注释里时更是如此：模型没有可对照的权威，生成的只能是「读起来都对」的草稿。
- **同一套机制的另一个用途：自然语言问数（原方向①第 5 项；原方向③第 4 项）**——把指标定义向量化后做语义检索，入口**只消费 `metric_definition`、不产生口径**。它的级别与第 2、3 行一字不差地一致：**L2**（① 核不到：检索层没有自己的发布物，向量检索是既有通用能力；**②核不到**；③ 答案能否指回定义表的那一行无共识）。**它只能当入口**：检索到的一段描述不能当作口径，因为它不指向定义表的具体一行——这正是「入口」与「权威」在本主题里的分界。

#### 5.2.2 Agent 治理回环（原方向③；原趋势①⑦）

- **旧做法与它的卡点**：资产的变更与冲突是持续、分布式发生的，而治理团队是集中且有限的——约束是**治理动作的发生频率跟不上资产变化频率**（§3.2.7 的约束）。卡点不在「不会查」，而在「没有人为一次检查专门排期」：口径冲突要等同名指标被两个部门同时取到才发现，分层违规要等下游作业出错才发现。
- **AI 改变了什么机制**：**治理动作的触发从人的排期换成调度 + 扫描**，产出形态被限定为**可裁决的提案**，而不是已生效的变更（§3.2.7 的结构把这条写成判据：如果某个能力无法退化成「可被驳回的提案」，它就不该被自动化）。
- **由此得到的**：**因为提案本身可统计（漏报率、误报率），治理自动化第一次可以被证伪**——团队可以用数据决定要不要保留这个 Agent，而不是靠信仰。这是本主题里最有价值的一条性质变化：**它把治理从「制度」变成了一项可评估的服务**，而这件事不依赖模型有多强，只依赖输出形态是不是提案。

| 治理动作 | 它需要什么输入 | 能不能自动执行 | 判据 |
| --- | --- | --- | --- |
| 发现同名指标多实现（口径冲突） | `metric_definition` 的结构（§3.2.5） | **不能**：哪个口径对是业务价值判断 | 提案 + 定义 Owner 裁决 |
| 建议新表落在哪一层 | 上下游与粒度（主文件 §2.3 方法③） | 不能：分层违规的代价要人评估 | 建议进建表评审 |
| 检查新鲜度与波动（质量） | SLA 与历史分布 | 可以**告警**，不可以改数 | 告警沿血缘定位到 Owner |
| 采集与标注（自动采集为主） | 作业定义与元数据 | 可以：有客观判定标准 | **既有能力，不是 AI 方向**；适用范围见 [§ 3](08-one-data-section-3-sec3.md) §3.2.7「真实使用」段 |

- **由此付出的**：**其一，提案疲劳**——如果每天提出上百条疑似问题而误报率高【经验：提案量随资产数与扫描频率变，从上百条到数百条都可能】，Owner 会在两周内学会全部忽略【经验：随误报率与堆积的提案量变，误报率越高越快，几天到数周】，此时系统在运行、治理没有发生；必须有精度指标与分级，只把高置信提案推到人面前（§3.2.7 的代价）。**其二，「哪个口径是对的」本质上是业务价值判断，Agent 结构上给不出**，它只能把问题精确定位到人。**其三，权威口径尚未建立时，自治会反转成「用同一个错误互相印证」**——平台上并存 5 个 GMV 而没有任何一个被宣布为权威时，Agent 最多指出它们不一致，更糟的情况是它挑了一个错误但自洽的定义去「纠正」正确的那个，把污染扩散到更多资产（§3.2.7 的失效点）。
- **证据与来源**：【公开：本书 §3.2.7 给出三项能力各自的结构约束、代价与失效点，§3.2.6 的失效点把「生成物无权威可对照」写成反转条件（把人力成本降下来 → 污染权威元数据），均可逐行核对；主文件 §1.4 把 2025 年起列为「OneData × Agent」阶段】。**【本节未能核到】**可点名材料描述「Agent 自主裁决口径」在生产中运行；原方向③的四项里，只有「自动采集 / 自动标注 / 异常告警」这类有客观判定标准的任务在公开材料里可见（[§ 3](08-one-data-section-3-sec3.md) §3.2.7「真实使用」段），本组三项里判 L3 的只有写路径（第 6 行「自动改数」）那一项。
- **成熟度**：**提案式治理（读路径）是 L2**（判据：① 核不到，形态在书内可核验；**②核不到**；③ 提案精度指标无通行做法）——这一档同时覆盖第 5 行「发现指标口径冲突」与第 7 行「建议建模分层」：两者的输出都是**可被驳回的提案**，都不能自动执行，级别与判据同列；**自动裁决与自动改数（写路径）是 L3**（① 无正式条目；② 不适用；③ 写动作的撤回语义无约定），对应第 6 行。
- **判定方法**：问它两个问题——「这条提案依据 `metric_definition` 的哪一行」和「如果它自动改了一个口径，昨天发出的报表怎么处理」。**第二个问题答不出来，写路径就不能开**。
- **什么时候值得做**：已经有权威口径（同名指标的归并已完成一轮）且提案能带上依据时。
- **什么时候不值得做**：`metric_definition` 里同一个指标名还有多行的时候——此时要先归并口径，而不是先上 Agent（§7.3.2 的判定方法：这个指标名在定义表里有几行）。

#### 5.2.3 AI 资产化（原方向②；原趋势②③④）

- **旧做法与它的卡点**：指标（报表用）与特征（模型用）是两套体系，同一份业务量在两侧各有一个口径；主数据是「表 + 服务」，知识图谱另有一套实体表示；服务是内部 API，Agent 要调用得为每个服务写一遍胶水。三处的共同代价是**同一份东西的两套表示必然分叉**，而分叉之后模型效果归因与业务复盘无法对齐（§3.5 反模式⑦）。
- **AI 改变了什么机制**：**把资产的交付形态从「表 / 报表」换成「可被程序按语义调用的契约」**——指标定义表多一个特征用途、主数据多一个图谱落点、服务多一个带描述与权限的工具入口。机制上是**同一份定义多了几个消费者**（§7.3.4 的交付形态表已把这条列成一行），而不是定义了新的东西。
- **由此得到的**：**因为口径的权威仍在定义表里，所以「特征复用指标定义」在机制上是成立的**——特征回扫的是已物化的汇总，而不是每次都回到明细分区，这同时降低了回刷成本（§7.3.1 的「AI 时代新增的约束」）。**这是本方向唯一一条真正改变成本函数的结果，而它不需要 LLM**：它要的是指标定义表被当成特征的权威，而不是另建一套特征口径。

```text
       同一份口径，三种消费者（谁在改，谁在等）
       ────────────────────────────────────────────────
       metric_definition（权威，唯一，带版本）
            ├─► 报表 / BI        口径变更 → 按当时口径重述历史
            ├─► 模型特征         口径变更 → 特征重算 + 模型重训
            └─► Agent 工具调用   口径变更 → 工具契约版本 + 兼容期
       ────────────────────────────────────────────────
       关键：三者共用的那一行定义，是它们唯一能对齐的地方
       判定方法：改一次定义，数一数有几类消费者要跟着动；
                 数不出来的，说明契约还没建立
```

- **由此付出的**：**其一，契约为多个消费方共用之后，任何口径变更要背着全部消费方改**——定义中心的单点性被放大（§7.3.2 的代价），而绕开一次就多一个口径。**其二，「主数据即知识」要求图上的边带来源与生效期**，否则 Agent 会把一条错边当作事实；而主数据本身的失效方式是**错而不报**（§3.1 的约束表：OneID 的失效是「错而不报」——两个真人被合并，所有 UV / 复购 / 留存一起错，没有任何告警），挂到图上只会让错误更易被引用。**其三，服务即工具会把权限问题抬到最前面**：工具描述写得再好，鉴权与数据边界没配好，Agent 越权调用只是时间问题。**其四，反方向的回流要单独设闸**：[§ 4](08-one-data-section-4-sec4.md) §4.2 关键技术点⑧ 把「模型预测回流到 OneData（在线学习）」列为双向打通的一半，而这条回流一旦进入权威链路，**模型的误差就会变成口径的一部分**——它比人工填错更难发现，因为它的来源正是「系统自己算出来的」。
- **证据与来源**：【公开：本书 §7.3.1 给出特征回扫与回刷成本的机制、§7.3.4 给出交付形态表、§7.3.2 给出口径载体表、§3.2.4 给出 D 系列接口与服务契约，均可逐行核对】。产品侧的代表见 [§ 4](08-one-data-section-4-sec4.md) §4.3（一张按类别分行的候选表，指标平台 / 主数据 / 数据服务网关各占一行），其具体能力与版本以各家官方文档当前版本为准。**【本节未能核到】**第三方（非厂商）公开生产案例，尤其未能核到「同一指标定义同时供 BI 与特征使用」的公开口径材料。
- **成熟度**：**指标即特征 L2**（① 核不到：机制在书内可核验；**②核不到**；③ 特征与指标的口径归属无共识）；**服务即工具 L2**（① 核不到：形态见 §3.2.4 的 D 系列接口与服务契约；**②核不到**；③ 工具描述与权限的绑定无通行做法）；**主数据即知识 L3**（① 无正式条目；③ 图上边的来源与生效期无约定；② 不适用——一次错合并会顺着图扩散）。
- **判定方法**：改一次指标定义，数一数有几类消费者要跟着动、各自多久跟上。**数不出来的部分，就是还没有契约的部分**；而「主数据即知识」要先问一句：这个实体键错了，图上会不会有人发现（答案通常是不会）。
- **什么时候值得做**：指标平台已经把 `metric_definition` 建成权威、且 AI 侧确实要复用这些量的时候。
- **什么时候不值得做**：权威口径还没建立的时候——此时把资产「资产化」，只是给并存的那几个 GMV 各配一个工具描述。

#### 5.2.4 被写进「AI 时代」但机制没变的那一族（原方向④⑤⑥；原趋势⑤⑥；原 5.3 的平台新特性）

这一族有四个方向，它们的共同点是：**收益真实存在，但没有一条的收益来自模型能力**。**一件只换了消费入口（GraphRAG），三件与 AI 没有因果关系（DataOps、Data Mesh、实时与湖仓）**。把它们一起写成「AI 时代的 OneData 演进」，会让真正要做的三件事——**把规则与定义做成机器可读、把变更挂进门禁、把同名指标的行数变成可查的数**——一件都排不进排期。

| 方向 | 旧做法与它的卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据与成熟度 |
| --- | --- | --- | --- | --- | --- |
| OneData × GraphRAG（原方向④；原 5.2 的 OneID × 知识图谱） | 业务方问「近 30 天新客 GMV 按渠道拆」，需要先知道指标名与限定词 | **没有改变机制，只换了消费入口**：口径的权威仍在 `metric_definition`（§7.3.2） | 不知道指标名的人也能问到数 | 答案不可复算——检索相似度会返回不同候选集合，而「哪个口径对」检索层回答不了；错一次就是一次错口径 | ① 无正式条目；② 不适用；③ 检索层与定义表的边界无约定 → **L3** |
| OneData × DataOps（原方向⑤；原 5.3 的三条相关新特性） | 建表与改口径在控制台里发生，谁改的、改了什么、要不要评审都没有留痕 | **与 AI 无因果关系**：它改变的是**变更的入口**，不是生成的机制 | 因为建表与改口径都走代码评审，命名与分层的门禁第一次有地方挂（§7.3.3） | 引入一套版本控制与 CI/CD 的运维面；把建模脚本化之后，紧急取数会更想绕开 CI——**绕开一次就多一个口径**（§7.3.2） | ① 判定入口是 dbt / Dataform 一类项目的 release notes；**②核不到**；③ 门禁阻断口径各家不同 → **L2** |
| OneData × Data Mesh 联邦化（原方向⑥；原趋势⑤） | 集团各 BU 自治，跨域指标没有中心裁决者 | **与 AI 无因果关系**：它是**同一权衡的另一端**，不是升级路径（§7.3.3、§7.6 组合 3） | 多域自治的组织可以在不放弃跨域口径的前提下行动（定义权在中心、生产权在域内） | 跨域指标只能靠协商，没有裁决者；且「联邦」缺的是裁决机制，不是技术——把它当趋势会掩盖这一点 | ① 方法论而非产品，按 §7.3.3 的裁决权判；**②核不到**；③ 联邦治理无标准 → **L2** |
| 实时 OneData 与湖仓（原趋势⑥；原 5.3 的两条相关新特性） | 离线指标与实时指标两套口径、两份实现 | **与 AI 无因果关系**：它是「同一份定义喂两条链路」的工程约束（§7.3.1 的回刷机制） | 实时与离线共用一份定义，指标不再分叉 | 两条链路的规则与口径同步要持续回归；把「共用一份定义」当口号而不当硬约束，分叉只是时间问题 | ① 形态见 §6 的字节案例与 §7.3.1（可逐行核对）；**②核不到**；③ 流批共用定义无通行标准 → **L2** |

**读这张表的方式是看「AI 改变了什么机制」这一列**：四行里没有一行是生成机制的延伸：**一行只换入口（GraphRAG），三行与 AI 无因果关系（DataOps、Data Mesh、实时与湖仓）**。**这解释了为什么它们都停在 L2 / L3**——判据②核不到只是表层，深层原因是**它们的好处不来自模型能力，所以也不会因为模型变强而变得可核验**。

顺带说清一件常被省略的事：这四行里的 **DataOps、Data Mesh、实时与湖仓**不是「以后要做」，而是「现在就该做」——它们与 AI 无关，却决定了 §5.1 表里的 L2 方向能不能落地（门禁挂不上，生成物就没有生效的地方；定义不能共用，特征与指标就会分叉）。把这四件事与 AI 方向放在同一张排期表里竞逐资源，是本主题最常见的一次排序错误。

### 5.3 与本主题既有栈的接口在哪

OneData 与 AI 之间不是「结合」关系，而是**交接物**关系：谁把什么交给谁、数据以什么形态穿过边界、失败时谁负责。下表「现状」一列用同一套 L1 / L2 / L3 判据，但评的是**这个接口本身**，不是 §5.1 表里的演进方向——两者不要互相引用。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| OneData ↔ 建表与发布门禁（§7.3.3） | 交接物 = 命名与分层的可判定规则（机器可读） | **中心团队**；门禁不能阻断时，规范停在文档层，而文档会被绕过【经验：两年量级，随门禁强度与评审带宽变，1–3 年】 | L2（① 核不到：形态在书内可核验；**②核不到**；③ 阻断口径各家不同） |
| OneData ↔ 指标定义表与检索层（§7.3.2） | 交接物 = `metric_definition` 的行与版本；检索层只能消费，不能定义 | **检索层**；它把「同名指标多行」这个结构问题翻译成一个读起来合理的答案 | L2（出处格式与版本指针无共识） |
| OneData ↔ 特征平台（[../../02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md)） | 交接物 = 指标定义中的原子指标与业务限定，作为特征定义的上游 | **双方共用**；特征侧另起口径时，模型效果与业务复盘无法对齐，且不报错 | L2（口径归属无共识） |
| OneData ↔ Agent / 工具调用（§3.2.4 的 D 系列、§7.3.4） | 交接物 = 服务契约（输入 / 输出 / SLA / 鉴权）+ 工具描述 | **服务侧**；契约缺失时，上游改列名会直接穿透到 Agent 的工具实现 | L2（工具描述与权限的绑定无通行做法） |
| OneData ↔ 血缘与目录（[../../04-data-assetization/08](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 交接物 = 指标的物理落点与字段级血缘；口径变更要能沿血缘列出影响面 | **OneData 侧**；影响面列不出来时，口径变更只能全量重算或祈祷 | L2（粒度与来源标注的约定无共识） |
| OneData ↔ 湖仓表格式与流批链路（[../../03-data-stack/03](../../03-data-stack/03-lakehouse/03-lakehouse.md)） | 交接物 = 同一份定义驱动的物化落点与刷新语义 | **平台侧**；两条链路各自实现定义时，指标会静默分叉 | L2（流批共用定义无通行标准） |
| OneData ↔ 组织与裁决机制（§7.3.3、§3.5 陷阱） | 交接物 = **裁决权**（谁宣布哪个口径为准）与评审带宽 | **组织**；没有裁决角色时，Agent 提出的提案无处生效，生成物也无从校验 | L3（① 核不到：形态是书内判据；**②核不到**；③ 评审带宽与裁决边界无通行做法） |
| OneData ↔ LLM 生成链路（§3.2.6） | 交接物 = 权威（命名语法 / 定义表 / 血缘）+ 生成物（带来源指针与版本） | **OneData 侧**；生成物不带来源指针时，它会成为第二份权威 | L2（来源指针与重生成机制无约定） |

一句话概括：**AI 没有给 OneData 新增任何一条口径，它新增的是「元数据的生成成本换了一种形状」与「多了一类按语义调用资产的消费者」**。

**「谁负责失败」这一列决定了排查路径。** 表中多数失败落在中心团队与 OneData 侧，原因与 §3.1 的判断一致：OneData 的三个部件的失效方式不同——OneModel 的失效是**慢**（回刷成本随时间累积），OneService 的失效是**脆**（上游改名全线故障），**OneID 的失效是错而不报**；而 AI 把这三处失效的暴露时间都推后了（生成物掩盖了元数据缺口、入口掩盖了口径冲突、契约掩盖了物理变更）。由此得到三条约定。

**第一条约定：生成物必须带来源指针与版本。**（口径的权威只能有一个载体（§7.3.2）；生成物是渲染产物，渲染产物改了而权威没改，或权威改了而渲染没重生成，都会产生两份权威。）这条约定今天是可选的：**当你的检索层或 Agent 开始引用生成物而不是定义表时，它就变成必需的**——判断信号不是日历，而是你的入口有没有开始把生成物当事实消费。

**第二条约定：权威口径必须先被宣布，自动化才有靶子。** 同名指标在 `metric_definition` 里还有多行时，任何自动化都只是在整理混乱；先归并、再自动化，顺序不能反。

**第三条约定：门禁先于生成。** 规范能不能落地，取决于中心团队能不能阻断一次不符合规范的建表——**没有这个权力，规范就只是文档**（§7.3.3）；而在没有门禁的地方加一个更会写文档的模型，只会产出更多没人执行的文档。

```text
   AI 新增的两样东西，落在不同的边界上，谁也不能替谁兜底
   ────────────────────────────────────────────────
   新生成手段（LLM 辅助建模与文档） ──► 落在「权威与渲染」这条边界上
       必须回答：它渲染的是哪一份权威？权威改了它会不会跟着变？
   新消费入口（问数 / 特征 / Agent 工具） ──► 落在「契约与权限」这条边界上
       必须回答：它凭什么不把一次错口径放大给更多消费方？
   ────────────────────────────────────────────────
   两者都没有改变：口径仍须有唯一载体（§7.3.2），
                   定义中心仍是发布链路上的单点（§7.3.2），
                   规范存亡仍取决于门禁能不能阻断（§7.3.3）
   判定方法：任意一个「AI 增强」提法，先问它改变的是生成成本
             还是权威位置——前者可以试，后者要停在 L3
```

### 5.4 公开进展与文献

按骨架分三类：**论文 / 官方 release note / 第三方生产案例**。每条的门槛是**名称 + 年份**（名称 = 会议名 / 书名 / 文档页名）。**三类里给不出这条门槛的，本节一律按同一种办法处理：写明本类暂缺、说清为什么缺，并给出判定入口**（去看哪一页、核哪一条），而不写成一条看起来像证据的条目——下面每一类的第一句都会交代它处在哪一种状态。**宁少勿假**。

**论文（可核验）**

本类的门槛是「会议或期刊 + 年份」。本主题的公开记录里，**本节给不出这样一条论文**——OneData 的公开学术产出是专著与行业方法论文本，而不是以它为对象的会议论文。因此下面列的是**专著与公开方法论文本**，它们支撑的是本节的机制来源（分层、命名、指标定义、联邦治理），不是某一项 AI 能力：

- 《大数据之路：阿里巴巴大数据实践》（2017）——公开描述了 OneData 的 OneModel 分层与命名规范、原子 / 派生 / 复合指标的划分（本章 §7.3.1、§7.3.2 均引此书）【公开，2017】。
- Kimball, *The Data Warehouse Toolkit*（1996）——维度建模的分层与一致性维度，是 OneModel 的两种实现之一（本章 §7.3.1）【公开，1996】。
- Zhamak Dehghani 的专著 *Data Mesh*（O'Reilly 出版；副标题与出版年份以出版方页面为准）——Data Mesh 四项原则（域内所有权、数据即产品、自助数据平台、联邦计算治理）的权威阐述，本章 §7.3.3 与 §7.6 组合 3 引其判断；该方法的首次公开阐述是 2019 年前后发布的系列文章，标题与具体日期以原文为准，可按 "data mesh" 检索核验【公开，可自行核验】。
- **原 §5.3 所列五条学术条目（DAMA-DMBOK 3.0、指标优先设计模式、数据产品思维、AI 原生数据治理、知识图谱 × 主数据）本节无法核验**：它们给的是主题名而非可检索的标题与作者，DAMA-DMBOK 的版本号与出版年份尤其需要以 DAMA International 的官方发布为准。处理办法：**保留它们所指的四个方向**（元数据治理体系 / 指标优先 / 资产化 / 图谱融合），不把它们当证据。

**官方 release note / 文档（判定入口）**

**本类给不出可点名的条目**：能核到的公开材料只有厂商产品材料与开源项目文档，而它们的具体条目与发布日期必须逐页核对——把一个没有核对过的年份抄进来，比留空更糟。所以本类**只列判定入口，不列证据条目**（属上面说的「暂缺 + 原因 + 判定入口」，不是条目清单）：下面每条点明去找哪一类页面，年份一律由被点名页面自己的版本记录提供。核验动作只有两个：这一页上有没有一条带年份的正式条目；条目描述的是「已发布」还是「预览」。

- **各建模与治理平台的官方文档与「产品动态 / 版本记录」页**（阿里 DataWorks、字节 DataLeap、Databricks Unity Catalog 一类，[§ 4](08-one-data-section-4-sec4.md) §4.3 有完整清单）——核验「AI 能力是 GA 还是 Preview」，以及**它输出的是「一段生成文本」还是「带来源指针与版本的生成物」**；后者才可能进入权威链路。具体能力与版本一律以各家官方文档当前版本为准。
- **dbt / Dataform 一类项目的 release notes 与 changelog**（dbt 与 Dataform 各自文档站的版本记录页、以及仓库的 Releases / 发布说明页）——核验「建模即代码、测试与部署自动化」的正式能力边界；这类页面的条目自带发布日期，是判定①最直接的入口。本节不给版本号，也不抄年份：年份就是该页自己的发布日期。
- **指标平台的官方文档与产品动态页**（阿里指标平台、字节 Bytemetric 一类，[§ 4](08-one-data-section-4-sec4.md) §4.3 候选表的「指标平台」一行有清单）——核验「指标定义是否版本化、同名指标能否被查出多行」，即 §7.3.2 的判定方法在工具侧是否可执行。
- **主文件 §1.4 的阶段划分**（本书章节而非外部文献，故不标年份）——它是**本书对方法论的阶段划分**，不是产品版本；不要拿它当某厂商的发布记录。

**第三方生产案例**

- **本节未能给出**可核验的第三方（非厂商）公开生产案例。公开材料里能核到的是两类：① 厂商产品材料与开源项目文档；② 建设方的工程自述——[§6](08-one-data-section-6-sec6.md) 整理的阿里 / 字节 / 美团 / Netflix 四个案例，出处标注为「机构名 + 年份区间」，按判据属**建设方自述**，不构成第②条。**这个空白本身是结论**：它正是 §5.1 表里没有任何一行到 L1 的直接原因。
- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——把生成物的采纳率、提案的误报率、同名指标的行数、评审带宽占用（§7.4 的推算可以换成你的数）这四组数算出来并留存口径。它们在本主题评审里的分量超过任何厂商案例。
- 三类证据里**最容易造假的是「迁移/接入效率」**：只报一个缩短比例而不说分母（多少张表、多少次变更、谁在做），无法复核。**判定方法**：只接受同时给出「资产规模 / 变更次数 / 参与人数」三者的效率数字。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **命名规范校验**：把命名规则写成一份可执行的规则文件，看它能不能自己跑出违规清单。
2. **口径文档生成**：改一次 `metric_definition`，看已生成的文档会不会自己跟着变。
3. **业务含义生成**：抽 100 条生成物【经验：随资产数与评审带宽变，通常 50–300 条】请定义 Owner 判采纳率。
4. **自然语言问数**：随便问一个指标，看它能不能给出定义表的主键与版本号。
5. **Agent 治理**：问它「这条提案依据哪一行定义」与「它自动改了一个口径后，昨天的报表怎么处理」。
6. **指标即特征**：改一次指标定义，数一数有几类消费者要跟着动。

**怎么用这份清单**：要核「能力存不存在」看官方文档与发布说明（最快）；要核「这条口径可不可信」看定义表的那一行与版本（最慢但最稳）；要核「在我这里值不值得做」看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。三类证据之外还有一种最没用、却最常见的形式：把「某平台支持自然语言问数」写进方案而不写判定入口——它既不能被复核，也不能被证伪。

### 5.5 被过度宣传的部分

**「LLM 自动生成指标文档，省下文档人力」**——实际是：省下的是**写**的人力，新增的是**审**的人力与一条生成链路，而口径文档一旦被当作权威，就与定义表分叉（§3.2.6 的失效点：定义表改了、文档没重生成）。**为什么会这样**：口径的权威只能有一个载体（§7.3.2），文档是渲染产物；两份权威比没有文档更差，因为读者会信更可读的那一份。**它什么时候才会成真**：文档由定义表在每次变更时自动重生成，且生成物带版本号与来源指针（「本文档由 `metric_definition@vN` 生成」）。**判定方法**：改一次定义表，看文档多久跟着变；如果它不会自己变，它就不是渲染产物，而是第二份权威。

**「Agent 自动裁决口径冲突」**——实际是：Agent 能做的是**发现**（同一指标名有多个实现、同一原子指标挂了不同的业务限定），不能做**裁决**——「哪个口径对」是业务价值判断。**为什么会这样**：裁决需要价值排序这个输入，而它不在任何数据里；没有它，Agent 要么指出不一致，要么挑一个内部自洽但错误的定义去「纠正」正确的那个（§3.2.7 的失效点）。**它什么时候才会成真**：组织先宣布了权威口径（约定「同名指标以定义表某一行为准」），Agent 的发现才能变成可执行的纠正。**判定方法**：问它「这 5 个 GMV 里哪个对」，答得出来才叫裁决。

**「把 OneData 升级成 GraphRAG 就能让业务自助问数」**——实际是：入口**只消费口径、不产生口径**；它把「不知道指标名」变成「问得到但不知道对不对」。**为什么会这样**：检索相似度与口径的唯一性是两件事——一个指标名在 `metric_definition` 里有几行，是检索层回答不了的（§7.3.2 的判定方法）。**它什么时候才会成真**：检索层先做「指标名唯一」这一前置约束，且答案能指回定义表的那一行与版本。**判定方法**：随便问一个指标，让它给出定义表的主键与版本号；给不出就是一次不可复核的检索。

这三条的共性：**它们都把「生成更便宜」或「入口更易用」当成了「口径更一致」**——LLM 让文档更便宜、Agent 让冲突更早出现、检索让数更好拿；而 OneData 的稀缺资源从来不是文档、不是提案、也不是入口，**是「这一份口径被谁宣布为准」这个决定**。

### 5.6 未来 3–5 年：可证伪的预测

这一节写了**四条**。选这四条的理由：§5.2.1、§5.2.2、§5.2.4 三组各要至少一条可证伪的线，§5.2.3 的「指标即特征」单独占一条——它是本主题里唯一一条真正改变成本函数、且与模型能力无关的方向，因此它的信号必须与 AI 的进展解耦来观察。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| LLM 生成的元数据会变成「带来源指针 + 版本」的结构字段，而不是一段自由文本 | 主流平台把「生成物 + 来源 + 版本」做成结构字段，并支持重生成 | 生成物继续以自由文本入库，且被检索与 RAG 直接消费 |
| 「指标即特征」会先在已有指标平台的组织里落地，而不是先在 AI 团队牵头的新项目里 | 公开材料把特征接指标定义的动机写成「回刷成本」与「口径对齐」 | AI 团队另建一套特征平台，且公开说明其口径独立于指标侧 |
| 数据治理的自动化会停在「可裁决的提案」这一档，自动裁决不会成为默认产品能力 | 产品文档把输出定义为提案，并公开误报率一类的精度指标 | 出现默认自动生效的口径修正条目，且撤回语义写得清楚 |
| 「OneData 还是 Data Mesh」的争论会转向「裁决权放在哪一层」，第一个被写进制度的会是**口径变更的裁决人**这一角色 | 组织制度里出现明确的裁决角色，以及评审带宽的上限 | 讨论继续停在方法论名词上，而「谁能宣布口径为准」始终没有答案 |

写这四条时的共同约定：**信号必须是外部可观察的**（正式功能条目、发布说明、带口径的公开材料），而不是「我觉得会」。**被检验得最快的是第三条**——看下一个版本的产品文档里有没有那个区分，一年内【经验：随产品发布节奏变，通常 6–18 个月】就能看到；**最慢的是第四条**，它落在组织制度上，而制度调整通常以年计；**最有价值的是第二条**：它能在你自己的环境里被检验，而且不需要等任何厂商——**改一次指标定义，数一数有几类消费者跟着动**。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有人提议用 LLM 生成指标文档 | 先定生成物的来源指针与版本字段 | 观察改一次定义表后文档会不会自己变 | 不要让生成文档进入口径链路；不要把它当权威 |
| 有人提议用 Agent 自动裁决口径 | 先把同名指标归并成一，并指定裁决角色 | 观察提案误报率是否被你自己的数据量出来 | 不要在权威口径未定时上自治——它会用同一个错误互相印证 |
| 想上自然语言问数 | 先让检索层能给出定义表主键与版本号 | 观察「查不到」与「查错了」在接口上是否被分开表达 | 不要用检索结果代替口径定义 |
| AI 侧要复用指标 | 先让特征复用 `metric_definition`，别另建一套 | 观察一次口径变更后特征与报表是否一致 | 不要为 AI 单独建一套特征口径 |
| 想暴露服务给 Agent 调用 | 先把服务契约（输入/输出/SLA/鉴权）配齐（§3.2.4） | 观察上游改列名时有多少消费方要改 | 不要把物理表直接代理成工具 |
| 想接 GraphRAG / 知识图谱 | 先把权威口径与主数据标识定下来 | 观察检索层有没有做「指标名唯一」的前置约束 | 不要为检索改口径的载体；不要用图上的边当口径依据 |
| 有多个 BU 各自建模 | 先定裁决权与评审带宽，再谈联邦 | 观察跨域指标的对账成本落在谁的预算里（§7.4） | 不要在没有裁决者时推「联邦标准」——它只会停在文档 |
| 预算有限，只能做一件事 | 把「同名指标在 `metric_definition` 里有几行」做成一个可查的数 | 观察这个数是否在下降 | 不要一上来先补 AI 能力——口径还没归并时，自动化只是整理混乱 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改契约、加评审、动组织权力），**而收益依赖一个尚未成立的假设**（权威口径已经建立 / 门禁能阻断 / 生成物不会被当权威）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的机制只有**一条**——**元数据的「生成」成本从人挪到了模型，而元数据的「权威」一步也没有移动**（权威仍在命名语法、`metric_definition`、血缘图这三样可机器读的东西里）。由此得到的唯一新能力是「渲染更便宜」，也因此产生了本主题唯一的新失效模式：**生成物与权威分叉、生成物被当作权威**。它**没有**改变的是 OneData 的性质：口径仍须有唯一载体（§7.3.2），定义中心仍是发布链路上的单点（§7.3.2），规范存亡仍取决于门禁能不能阻断（§7.3.3），三个部件的失效方式仍各不相同（§3.1：OneModel 慢、OneService 脆、OneID 错而不报）。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是生成成本，还是权威位置？** 改变生成成本的（文档生成、业务含义、血缘解读）可以试点，但必须带来源指针与版本；试图改变权威位置的（自动裁决口径、自治口径）一律停在 L3。第二条判断同样快：**它消费的是哪一行定义？** 答不出行号的入口，给出的答案都不可复核。
>
> 如果只能带走一句话：**先把命名规则、指标定义、血缘这三样做成机器可读，再把建表与口径变更挂进门禁，最后才谈让模型去写**——这三件事做完，本节表里所有 L2 都变得可评估；这三件事没做完，L2 与 L3 的差别只体现在演示视频里。
