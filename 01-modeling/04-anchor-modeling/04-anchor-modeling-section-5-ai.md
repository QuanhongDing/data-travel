## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

五条趋势（「Anchor 从极致规范化演化为 AI 原生数据底座」「Auto-Anchor 成为主流」「Vector-Native Anchor」「Bitemporal as a Service」「Self-Evolving Anchor」）全部是方向判断，没有一条带时间与判据；而 §6 的四个案例（2012–2024）已经把另一件事说清楚了：**Anchor Modeling 的骨架与 AI 无关**。四件套（Anchor / Attribute / Tie / Knot）、每个属性自带时态、底座 6NF + 对外 3NF 视图这三件事，见主文件 §2.1 的概念定义、§2.2.2 的时态扩展与 §2.3 的演化算法——它们都在 LLM 出现之前就成型了（规范与实现的年份见主文件 §1.4）。AI 加在这一层之上的是三件事：**建模建议、演化决策的候选、以及把属性送去给检索层消费**。所以本节的第一件事，是把**底座**与**AI 加在底座之上的那一层**分开。

趋势清单的根本问题不是列错了，而是**没有时间维度**：同一个清单里，「2010 年就有规范的建模方法」和「某厂商的 Agent 会自己改表」被并列，读者据此排路线图就会踩空。Anchor Modeling 这一节的条目横跨三种时间尺度——**建模机制（十年量级）、时态与视图的工程形态（数年量级）、LLM 与 Agent 能力（一年量级）**——它们混在一张清单里时，看起来像是同一批「前沿」。本节给每个方向标级别，级别只回答一个问题：**今天能不能把它写进路线图**。

本节沿用三条可核验的判据，**三条全中才是 L1**：**①** 已 GA 且有正式 release note；**②** 有第三方（非厂商）公开的生产案例；**③** 接口稳定。**L1 生产可用** = 三条全中，可以排进路线图；**L2 可试点** = 已可用但接口或生态未稳，或只有建设方自有案例，可以做 PoC、不要做核心依赖；**L3 观望** = 仅路线图、论文、厂商演示或预览特性，记录，不要在架构里预留假设。

**本主题对上面这三条判据做了一处修正（只动 ①，且只对底座类机制生效）**：对建模方法类条目，① 接受「公开规范 + 带版本与发布记录的开源实现」作为「已 GA 且有正式 release note」的等价物——建模方法没有产品 release note，它的等价物就是规范版本与实现版本：**Anchor Modeling 1.0 规范（2010）**、**`anchor_modeling`（Ruby 实现，2013）**、**`anchor-python`（Python 实现，2019）**（名称与年份见主文件 §1.4；可按这两个实现名检索其仓库的发布记录，以各自当前版本为准）。**② 不做修正**：它只有两种命运——满足，或按缺 ② 处理，不存在「② 另有解释」。这一点在本主题格外要紧：本主题公开能拿到的生产叙述（§6 案例 4.2–4.4，字节 / 阿里 / 美团）都是**运营方自己发布的建设方自述**，按 5.4 的判据属于 L2 的证据形态；§6 案例 4.1 更不是生产案例——它是**方法提出者本人**的材料（§6 记的是 Lars Rönnbäck 与 2012 年的规范发布），按「第三方（非厂商）」这条字面判据，它恰好是被排除的那一类。**修正一也只用在底座这一行；LLM 辅助建模、Agent 自演化、把 Attribute 送进向量与图谱这三层仍按原判据判**——这也是它们停在 L2 / L3 的原因。

> 本主题下**没有一行三条全中，因此 5.1 表里没有 L1 方向**；最接近的是四件套 + bitemporal 底座，卡住的只有 ② 这一条——它的 ①③ 站得住，公开的生产记录却全是建设方自述。**缺 ② 不等于机制不可用**：底座的落地不依赖任何未发布的版本，它差的只是那条可公开指名的生产记录；升级路径也是公开的——一旦你的组织或可指名的第三方留下带规模与口径的公开生产记录，这一行即可升 L1。底座也完全不是 AI 带来的：规范、演化算法与视图层都在 LLM 之前成型（主文件 §1.4 的「传统阶段（2007–2015）」与「大数据阶段（2015–2020）」）。AI 只是把它的一个副产品变得值钱：**因为每个属性自带时态、且是独立的一张表，它天然就是字段级、带时间的一层元数据**——这正是检索层与目录层需要的东西（主文件 §1.2「AI 时代的新诉求」的第 3 条「细粒度属性治理」与第 4 条「Schema Discovery」说的就是这件事）。**机制可用不等于采用广度**：这套方法在电信、保险、金融的时序主体上落地较多，但它的学习曲线与表数量成本也是真实的（主文件 §2.4.4 的适用边界），达标线的含义只限「机制成立」。

> 各行不够格的原因各不相同：底座卡在**第②条**（①③ 都站得住，公开的生产记录却只有建设方自述，这一条只能在你自己组织里补）；LLM 辅助建模卡在**没有 AM 专用评测口径**（生成出来的 DDL 看起来对，但拆分决策对不对没人量过）；Agent 自演化卡在**误改结构不可逆且无公开回滚案例**；接入检索层卡在**时态语义在派生副本里被稀释**（向量不保证时序，模板决定模型能看见什么）；Anchor → KG 卡在**图侧原生时态弱**（映射容易、时态对齐难）。五个瓶颈不在一处，**成熟时间不会同步**——把它们打包成「AI 原生 Anchor 底座」一次采购，一定会被最慢的那件拖住。

三点说明：**其一**，工具条目不逐个给能力判断——版本与年份以各自官方文档为准，本节只给「去哪里核验」。**其二**，论文与开源项目名这类条目本节不重复其结论与数字，改列为判定入口（5.4），因为这类条目在转述中最容易变形。**其三**，方法的提出者与规范版本的归属在公开资料中有不同说法（主文件 §1.1 与 §6 案例 4.1 记录的名字与年份并不相同），本节不重复归属声明，只按「方法规范 + 实现版本」这一层给判据，读者可按方法名与规范名自行核对。

还有一处结构性错位值得写明：**「Bitemporal as a Service」不是应用方向，是能力边界问题**。它说的是「双时态不再专属 Anchor Modeling，而是所有数据平台的标配」——这句话要成立，必须落在接口上：平台能不能回答「在加载时刻 T2 看，业务时点 T1 的状态是什么」。这只能按主文件 §2.2.2 的三类查询逐条去考（业务时态查询 / 加载时态查询 / 晚到真相查询），而不能落在「标配」这种形容词上。写不出来的「标配」，在采购时等于没有。

**三级各自该怎么用**：**L1 排进路线图**——本主题暂时没有这一级的行（缺的都是第②条），所以这一级的用法是「证据补上再排」；底座的机制不依赖任何未发布的版本，它差的只是那条可公开指名的生产记录。**L2 只做 PoC，并先测出一个数**——底座测三个数（时态字段齐全的 Attribute 表占比 / 视图物化率 / BI 直连 6NF 的比例，5.2.1）、辅助建模测「双时态正确率」（5.2.2）、漂移检测测「漏报与误报两类数」（5.2.3）、检索层测「时点问答的可答率」（5.2.4）。测不出数就不上量。**L3 只登记，不做架构假设**——不要在变更流程与权限模型上预先为「Agent 自动改 schema」留位置。**回填机制**：任何方向一旦出现第三方公开的、含口径与规模的生产案例，升一级；一个 L2 方向一年内仍拿不到你自己语料上的实测数字，降为 L3 并停止投入。

还要写明底座这一行（本主题最接近 L1 的方向）的**边界**：**它的评级说的是机制成立，不是采用广度，更不是「人人都该上」**。四件套与双时态在「属性高频变更 + 强审计」的主体上落地较多（主文件 §2.4.4 给的适用边界是字段变化 ≥ 每周十个 + 时态要求极致），而在字段稳定的场景里它是过度设计——主文件 §2.4.1 的原文是「如果业务字段变化 < 每周 10 个、时态要求不极致，用 Data Vault 更经济」。把「机制成立」读成「所以所有团队都该迁移」，是对本节判据最常见的一种误用。

### 5.2 演进方向逐条拆解（核心节）

四个方向都按同一结构写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**。只写收益不写代价的方向应在评审时直接打回——本主题每一次能力提升，都对应一项成本或责任的转移：

| 方向 | 机制上发生了什么变化 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 底座与视图层 | 不是 AI 改变的：把「改表」换成「加一张 Attribute 表」 | **成本结构**（演化成本不再随属性数线性增长到 DDL 审批上） |
| §5.2.2 LLM 辅助建模 | 拆分建议与查询语句的产出来源从架构师换成模型 | **成本结构 + 责任**（产出变便宜，定案责任没跟着转移） |
| §5.2.3 Agent 自演化 | 演化从「定期评审」换成「事件触发」，判定从规则换成统计判断 | **触发方式 + 判定来源**（误判不可逆） |
| §5.2.4 送进检索层 | 消费接口从「反规范化视图」换成「按实体 + 属性 + 时点检索」 | **接口边界**（读的人从分析师换成了模型） |

有一类条目必须提前分出去：**「给 Anchor 加一个自然语言查询入口」是接口改良，不是架构变化**。判断方法是问三句——四件套的构件增加了吗？时态字段增加了吗？视图层的语义变了吗？三句都是「没有」，那它只是消费侧的一个新前端，应记入工具升级。本节把它并入 5.2.2 的 L2，一半原因就在这里：**接口改良的风险低，但它也不解决「时点语义有没有被正确表达」这个真问题**。

#### 5.2.1 底座与视图层：把「改表」换成「加一张 Attribute 表」

- **旧做法与它的卡点**：传统 3NF 与维度建模把多个属性放在同一张表里，于是**改动的成本由最快变化的那个属性决定**——主文件 §1.2 把这条写成业务驱动力的第一条（核心实体上百个属性、每周都在变，改表要 DDL 变更加数据迁移）；§6 案例 4.1 把它说得更具体：手机号几年一改、余额秒级变，却被塞进同一张表的同一节奏里。卡点不在技术，而在**变更的审批与迁移成本与「有多少属性」无关、只与「要不要动这张表」有关**。
- **AI 改变了什么机制**：这里要说清一件事——**这条机制不是 AI 改变的**。把一个属性拆成一张独立的表、并让它自带 `(valid_from, valid_to, loaded_at)`，使得「新增属性」变成「新增一张表」，于是**任何变更都不触碰已有表**（主文件 §2.3.1 的四个场景：新增属性、修改类型、新增关系、删除属性，操作分别是加表、加新表 + 旧表失活、加 Tie 表、标记 `deleted_at`）。它与 AI 的关系是**依赖**：检索层与目录层需要的「字段级、带时间的元数据」，恰好就是这层结构本身的形态。
- **由此得到的**：因为改动不再触碰已有表，所以**演化不再需要停机窗口，也不需要一次性的数据迁移**——主文件 §1.2 记的那类「ALTER TABLE 加迁移」的窗口消失了，取而代之的是「加一张表 + 建一个视图映射」。这条性质在 AI 时代被放大：**当模型也可以提议新属性时，落地的边际成本越低，试错的意愿就越高**——这是 5.2.2 能成立的前提。
- **由此付出的**：**其一，表数量爆炸**——这是 6NF 的固有代价，主文件 §2.4.1 把表数量差距写成「数百张」对「数千张甚至数万张」；§3.5 的五个反模式里，第一个就是「过度拆分到无法维护」。**其二，查询必须先经视图层**——多 Attribute JOIN 是性能瓶颈，且同一张表里有一行就是「忽略反规范化视图层」；§6 案例 4.3 的教训是「6NF 直连 BI 会导致查询超时」。**其三，学习曲线陡**——6NF 反直觉，§6 案例 4.1 的教训是「团队看不懂就放弃」，所以视图层不是可选项而是交付物的一部分。**其四，视图层本身成为新的维护对象**：视图要物化、要随属性变化更新、要有人负责——成本没有消失，只是从 DDL 审批搬到了视图运维。
- **证据与来源**：【公开】**Anchor Modeling 1.0 规范（2010）**与两个开源实现（`anchor_modeling`，Ruby，2013；`anchor-python`，Python，2019）——名称与年份见主文件 §1.4，核验按这两个实现名查各自仓库的发布记录（以官方当前版本为准）；演化算法与类型演化算法的形态见主文件 §2.3.1 与 §2.3.5。**生产证据只有建设方自述**：本目录 §6 案例 4.2–4.4 由字节 / 阿里 / 美团自己发布，该节的来源标注是无标题的方括号标签（如 [字节技术博客 2020-2024]），可按其中的公司名与年份自行检索核验；案例 4.1 是方法提出者本人的材料。因此第②条不成立（见 5.1），本节按 L2 判。判定方法：在你的模型里挑一个最近新增的属性，看它是「加了一张表」还是「修改了已有表」——若答案以后者为主，那么这套底座你其实还没用上。
- **成熟度**：**L2**。判据：① 有公开规范与带版本记录的实现（修正一：规范 2010、两个实现 2013 与 2019，名称见主文件 §1.4）；② 缺——本主题公开的生产记录均为建设方自述（§6 案例 4.2–4.4），案例 4.1 是方法提出者本人的材料，按 5.1 缺 ② 即 L2；③ 成立但有边界：四件套的形态自 2010 年规范以来未变，而「三个时态字段齐全」是方法与主文件 §2.2.2 的形态，§6 各案例的落地模板用的是单一 `Changed` 时间戳（§6 行 49/119/202/277），两者不是同一件事。
- **什么时候不值得做**：字段变化慢（远低于每周十个，主文件 §2.4.1 给的界线）、时态要求弱、且查询以宽表聚合为主时，维度建模或 Data Vault 更经济——本节不把「机制成立」当成「都该上」的理由。
- **诚实的定位**：它解决的是**「改动成本由最快变化的属性决定」**这一类失败，不解决**「查询变慢」**这一类失败——后者要靠视图层与物化，是这套底座的配套工程，不是它的副产品。
- **上线前的最小验证**：数三个数——用 `valid_from` / `valid_to` / `loaded_at` 三个字段的 Attribute 表占比、物化视图占已建视图的比例、以及 BI 查询里直连 6NF 的比例。第一个数低说明时态没落地，后两个数高说明视图层这一环是缺口。
- **失效条件**：当视图层不物化、且 BI 直连 6NF 时，这套底座会以「查询不可用」的形式失败——§6 案例 4.2 的教训是「视图层不做物化直接对外」使尾延迟从 200ms 涨到 3s，案例 4.3 的教训是「6NF 直连 BI」使 BI 查询 join 过多直接超时。判断方法：看 BI 的查询计划里有没有出现十几张 Attribute 表的一次性 JOIN——有，就说明视图层这一环缺了。

```text
    一个属性的四种变化，对应四种操作（都不触碰已有表）
      新增属性   → 加一张 Attribute 表
      改类型     → 加一张新 Attribute 表 + 旧表标记失效（主文件 §2.3.5）
      新增关系   → 加一张 Tie 表
      下线属性   → 旧表标记 deleted_at，数据保留（不删历史）
    ────────────────────────────────────────────────
    对外只暴露视图（把 6NF 重新组装成看起来像 3NF 的形态）
      视图必须物化，且必须有人负责——否则失败形态是「查询超时」
      而不是「结构错误」，后者会报错，前者不会
```

#### 5.2.2 LLM 辅助建模：把「架构师判断」换成「模型出候选 + 架构师定案」

- **旧做法与它的卡点**：拆分决策由架构师做：哪些字段独立成 Attribute、哪些共享 Knot、Knot 的粒度多细、哪些关系值得建成 Tie。卡点是**决策依赖经验且不可批量**——主文件 §1.2 的案例 1 把它写成「字段归属争议经常出现」（VIP 等级该放人口属性还是套餐）；而当源系统有几百上千张表时，读 DDL、读 PRD、再逐一决策，是一个**随规模线性增长的人力项**。
- **AI 改变了什么机制**：把「读 DDL 与文档、产出拆分建议、写出 bitemporal 查询」这一段的**产出来源从人换成模型**，人退到定案与复核。机制上这是**产出成本的转移**：从架构师的时间换成与产出场次无关的推理；但**定案责任没有跟着转移**——主文件 §1.2 的 AI 时代新诉求里写的是「零中断演化」与「字段级治理」，这些是机制性质，不是「模型会替你做决定」。
- **由此得到的**：因为候选的产出变便宜，所以**拆分决策第一次可能从「能看多少张表」变成「能复核多少条建议」**——瓶颈从生产移到了审核。这才是它真实的机制意义：它把稀缺资源从「写」换成了「确认」，而确认的单位成本低于从零决策。
- **由此付出的**：**其一，模型不知道历史包袱**——它生成的建议只看当下的源结构与文档，看不到下游已经依赖了哪张表、哪次演化是为了绕开什么限制；照单全收会把已经付过的代价再付一次。**其二，双时态是最容易出错的地方**——业务时态（`valid_from` / `valid_to`）与加载时态（`loaded_at`）混用，产出的 SQL 会在「晚到真相」这类场景上给出错误答案，而错误不会报错，只会算错（主文件 §2.2.2 专门把三类查询分开讲，正是因为这一点）。**其三，命名与拆分策略因团队而异**，生成的 DDL 若无人统一，会在一两年后变成无人能读的表海——这也是 §3.5 反模式表里「过度拆分到无法维护」在 AI 时代的新来源。**其四，必须打标记**：哪些表是模型提议的、谁定案的、依据哪一版文档，否则演化历史会出现「无作者」的一段。
- **证据与来源**：① 有官方文档级的代码生成与语义理解条目——检索点：所列产品（dbt、Snowflake Cortex、Databricks Assistant / Genie、Microsoft Fabric Data Agent、阿里云 DataWorks Copilot 等）官方文档里「SQL 生成 / 语义模型生成 / Agent」的正式条目；**判定标准是有没有正式条目、标注的是预览还是 GA，而不是演示文案**。② 缺非厂商的、含语料与口径的 AM 专用评测（两条论文条目本节不重复其结论与数字，判定入口见 5.4）。判定方法：取 30 个真实时态问题，检查生成的 SQL 有没有把业务时态与加载时态混淆——这是该领域最常见的错误形态。
- **成熟度**：**L2**。判据：① 有正式文档条目；② 缺非厂商公开的 AM 专用评测与语料口径；③ 产出的是建议，接口（命名、拆分策略、定案流程）未定。
- **什么时候值得做**：当源系统数量大、且你已经有成文的拆分与命名规范时，它把「读 DDL」这段人力省下来是真实的收益。**什么时候不值得做**：源系统只有几十张表、或团队自己还没定下拆分规范时，先让模型生成只会把「没有规范」放大成「大量无人复核的候选」。
- **失效条件**：当模型看不到下游依赖与历史演化时，它的建议会与既有决策冲突，而冲突不会自己暴露——判断方法是把建议与「已有 Attribute 表清单」对一遍，统计其中有多少是「早就因为某次事故才那样拆的」。
- **上线前的最小验证**：取 30 个真实时态问题（含「晚到真相」类），看生成 SQL 的双时态正确率；再把其中错误按「时态混淆」「检视粒度错误（把 Knot 写成 Attribute）」两类分开记——两类错误的修法不同。

```text
    辅助建模的产出与责任边界
      模型产出：拆分建议 / DDL 草案 / bitemporal 查询草案
      人产出：  命名与拆分规范 / 定案 / 回归验证 / 生成标记
    ────────────────────────────────────────────────
    最容易出错的三处（都不会报错，只会算错）：
      ① 业务时态与加载时态混用 —— 晚到真相类问题会给出错答案
      ② 检视粒度错 —— 该建 Knot 的建成了 Attribute，字典失去共享
      ③ 看不到历史包袱 —— 下游已依赖的表被重新拆一遍，代价重付
    ────────────────────────────────────────────────
    因此定案环节不能省：模型给的是候选，不是新的规范
```

#### 5.2.3 Agent 驱动的自演化：把「定期评审」换成「事件触发 + 候选 + 人审」

- **旧做法与它的卡点**：源系统的结构变化靠人发现——DDL 改了、枚举值加了、下游用了错误的时态查询，都靠评审会或事故暴露。卡点是**触发依赖人的注意力**，而 Anchor 底座的表数量多（主文件 §2.4.1 的数千到数万张），人工巡检的覆盖必然低于变化速度。
- **AI 改变了什么机制**：把演化动作从「定期评审」换成「事件触发」，并把判定来源从「规则」换成「统计判断」——漂移从字段名比对扩展成语义判断（「这两个属性其实是一回事」），合规检查从「视图里有没有写时间条件」扩展到「这个下游用法看起来对但语义错了」。**改变的是触发方式与判定来源，不是演化目标**。
- **由此得到的**：因为触发不再依赖评审节奏，所以**底座的陈旧度第一次可以被度量**（每张 Attribute 表带「最后核验时间」与「来源系统版本」）。四个 Agent 必须拆成两类看：**漂移检测与合规检查是可自动化的那半**（它们有可判定的定义，错了只是多一条待办），**Attribute 提升与类型演化决策是需要模型判断的那半**（一次误判就会改结构，而结构改动不可逆）。
- **由此付出的**：**其一，改结构不可逆**——主文件 §2.3.5 的类型演化是「加新表 + 旧表失活」，自动执行意味着一次误判就在底座上留下一个没人认领的新表；而旧表一旦失活，下游查询会静默地少一个字段。**其二，误判的代价不对称**——「该提升的属性没提升」只是效率问题，「不该提升的提升了」会改变查询语义并波及所有下游视图。**其三，写操作需要审计与回滚**——Agent 改结构（加表、失活旧表、建 Tie）必须能回答「谁在什么时候改的、依据什么、怎么回滚」。**其四，判定随模型版本漂移**：「这条建议是哪个版本给的」要可查，否则历史决定无法复核（与 5.2.2 对生成标记的要求同源）。**其五，最危险的失败形态是静默**——时态字段用错不会报错，只会算错（主文件 §2.2.2 的晚到真相场景），而这类错误往往在审计或对账时才被发现。
- **证据与来源**：检测侧的能力属既有自动化（数据可观测性一类产品的官方文档有对应条目，可按「schema 漂移检测」自行检索核验）；改结构侧本节不引用任何公开案例——代表项目（AutoGen + Anchor、LangChain + anchor-python、Databricks Assistant）均为自建形态或厂商演示。判定方法：写下「它代谁执行、依据什么、怎么回滚」三句话，写不全就说明接口还没成立。
- **成熟度**：**L2（漂移检测与告警、时态合规检查）/ L3（自动改 schema、自动做类型演化决策）**。判据：检测侧有可判定的定义与既有产品文档；改结构侧没有公开的、含误改率与回滚机制的生产案例。
- **什么时候值得做**：当底座已经有数千张表、且有成文的命名与拆分规范（没有规范时，检测出来也只是噪声）时，检测与告警值得立刻做。**什么时候不值得做**：表数量在百级、变更频率低时，人工评审更省事，且不会引入误改风险。
- **诚实的定位**：它解决的是**「结构变化没人跟」**这一类失败，不解决**「跟的时候会不会跟错」**这一类失败。前者靠触发方式（事件 vs 评审），后者靠权限分级（可逆与不可逆分开）——把两者合成一个「自动化率」指标，会逼着团队把不可逆的操作也交出去。
- **失效条件**：当判定依赖「这两个属性其实是一回事」这类语义判断时，它会在源系统改名、口径微调、字典扩展这三类场景上持续误报，运维久了就被关掉；正确做法是把语义判断限定在可回滚的动作上（只出候选），把规则可判定的部分留成自动执行。
- **上线前的最小验证**：取 100 处真实的源结构变更，看检测机制能不能全部命中（漏报），再看它报出来的条目里多少是噪声（误报）；两类数分开记。合规检查另做一次抽查：取 20 个下游查询，人工判断它是否正确地用了业务时态与加载时态，与机制的判断对比。

```text
    底座上的操作按可逆性分级（不按「能力」分级）
      漂移检测 / 告警              → 可自动，错了只是多一条待办
      时态合规检查（规则可判定）     → 可自动，错了只是误报
      新增 Attribute 表（不动旧表）  → 可自动，回滚 = 删掉新表
      ────────────────────────────────────────────────
      旧表失活 / 类型演化 / Knot 合并 → 必须人工定案
        理由：这三类会改变既有查询的语义，且是「静默失败」
              回滚要重建全量视图，代价与一次事故同级
```

#### 5.2.4 送进检索层：把消费接口从「反规范化视图」换成「按实体 + 属性 + 时点检索」

- **旧做法与它的卡点**：底座的消费者是人与 BI——他们经过视图层拿到「当前状态」或某个时点的宽表（主文件 §2.3.3 的反规范化视图）。卡点有两个：一是**视图是预设的**，业务问的时点与属性组合没被预设时，要临时写 bitemporal 查询；二是**宽表在反规范化的那一刻把时态压平了**——视图通常取「当前有效行」，于是「历史上这个字段是什么」在视图层消失了（主文件 §2.3.3 的视图用 `valid_to IS NULL` 取当前有效），因此需要让检索层能直接问「张三 2020 年的姓名」。
- **AI 改变了什么机制**：把消费接口从「预设的视图」换成「按实体 + 属性 + 时点检索」。做法是把每个 Attribute 的**值连同它的时点**文本化或三元组化，送进向量库或同步为 RDF 三元组进图。机制上这是**接口边界的改变**：检索键从「表名 / 视图名」换成「实体 + 属性 + 时点」，而底座本身没有变。
- **由此得到的**：因为时点成了检索条件的一部分，所以**「某年某人的某属性是什么」这类问题不再需要人写拉链 SQL**——检索层可以直接按 (实体, 属性, 时点) 定位到那一行，再把值交给模型组织语言。这也让「字段级发现」成立：遍历元数据就能知道每个字段的当前值、历史值与来源（主文件 §1.2「AI 时代的新诉求」的第 3 条「细粒度属性治理」与第 4 条「Schema Discovery」）。
- **由此付出的**：**其一，文本化模板决定了模型能看见什么**——模板漏掉的时态维度（比如只写了年份没写加载时点、或没写来源系统），模型就答不出，而且它会**拿当前值当当时的值**自信地回答。**其二，时态语义在向量化时被稀释**——「2022-03 金牌 / 2022-08 白金」两段文本的向量几乎相同，除非把时点显式写进模板并做结构化过滤；向量库本身不保证时序。**其三，派生副本会过期**：Attribute 变了、向量没重建，出现的不是报错而是「看起来合理但已经过期」的答案，所以每个副本都要记录「最后刷新时间 + 底座版本」。**其四，同步到图会引入第二个一致性面**：RDF 的原生时态弱（主文件 §2.4.2 记「时态：弱，需 RDF 1.2 / Stardog 等扩展」），图的时态语义与 SQL 侧的 bitemporal 语义必须对齐，否则同一条事实在两个系统里会有两种「当时」。**其五，成本位置变了**：检索层的开销随**提问次数**增长，而底座与视图的维护成本随**属性数与变更频率**增长，两者不是同一条曲线。
- **成本量级（【推算】副本重建一侧）**：设底座有**数千张** Attribute 表【经验】（下文按 5000 张代入）、每表的**历史版本在数万行以内**【经验】（按 1 万行代入），则一次全量文本化要过 5000 × 1 万 = **5000 万行**【推算】；每行文本化在**数十 token** 量级【经验】（按 60 token 代入：实体标识 + 属性名 + 值 + 时点 + 来源），故一次全量重建约 5000 万 × 60 = **30 亿 token**【推算】。这个量级的意义不在于绝对费用，而在**它决定了副本只能做增量**：全量重建不是「加个索引」，而是一条要把全量历史过一遍 LLM 的流水线——所以「最后刷新时间」与「增量水位」必须作为副本的一等元数据。
- **证据与来源**：【公开】RAG 的公开出处是 Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", NeurIPS 2020（检索增强的机制依据）；Anchor 到 RDF 的映射关系写在主文件 §1.3（Anchor = Subject、Attribute = Predicate-Object、Tie = Predicate、Knot = Reified Object），导出本身是既有技术。「Anchor + 向量 / 图」融合项目与产品条目本节不重复其能力断言，判定入口见 5.4。判定方法：取 30 个时点问题（覆盖「当前值」「历史值」「晚到数据」三类），看检索层给出的答案有没有把时点当成提示词里的装饰——把时点改一改，答案不变的那一类，就是没真用时点。
- **成熟度**：**L2（Attribute 文本化进向量库、导出为 RDF 三元组并做图查询）/ L3（把 bitemporal 的时态过滤推进 GraphRAG 的检索路径、Anchor + Vector + KG 三层融合作为统一知识层）**。判据：转换与查询本身是既有技术且有明确映射；融合方案与时态过滤没有公开可核验的实现与评测口径。
- **什么时候值得做**：当「时点问答」是反复出现的一类真实需求（合规追溯、历史对账、客户争议），且底座已有稳定的视图层时，读方向值得做。**什么时候不值得做**：当查询集中在当前状态、或时点只精确到月时，视图层多加一个时间维度比建检索层更便宜。
- **诚实的定位**：它解决的是**「视图是预设的、时点组合没被预设就查不了」**这一类失败，不解决**「数据本身对不对」**这一类失败。后者靠底座与来源治理，与是否向量化无关。
- **失效条件**：当文本化模板省略了时点或来源时，能力会反转——从「查不到」变成「用当前值回答历史问题」，且回答得很流畅。判断方法：同一问题把时点改成过去/现在各问一次，答案完全相同就说明时点没生效。

### 5.3 与本主题既有栈的接口在哪

本节不写「与 X 结合」这类空话，只写三件事：谁调用谁、数据以什么形态穿过边界、失败时谁负责。表里「现状」一列的「既有技术（L1）」说的是**接口本身在既有栈里已经稳定**，不是 5.1 表里演进方向的评级（那一张表本主题没有 L1 行）。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 源系统 / ODS ↔ 底座（抽取与加载） | 交接物 = 属性值 + **业务时点（valid_from / valid_to）+ 加载时点（loaded_at）** | 加载侧；晚到数据要作为新版本写入而不是覆盖 | 既有技术（L1） |
| 底座 ↔ 视图层（反规范化） | 交接物 = 视图定义 + 物化策略；**视图是交付物，不是可选优化** | 视图侧；未物化的视图失败形态是「查询超时」而不是报错 | 既有技术（L1） |
| 视图层 ↔ BI / 语义层 | 交接物 = 宽表；**禁止 BI 直连 6NF**（§6 案例 4.3 的教训） | 模型侧；口径只在一个地方定义 | 既有技术（L1） |
| 底座 ↔ LLM（建模建议与查询生成） | 交接物 = 候选 DDL / SQL + **生成标记 + 定案人** | 架构师；未定案的候选不得进生产 | 可试点（L2） |
| 底座 ↔ 漂移检测与合规检查 | 交接物 = 变更事件 + 检查报告；**检查要能区分「源变了」与「检查器变了」** | 平台侧；检测错了只是多一条待办 | 可试点（L2） |
| 底座 ↔ Agent（写结构） | 交接物 = 结构变更 + 调用者身份 + 回滚方案 | 组织侧；**误改结构不可归因于模型** | 观望（L3） |
| 底座 ↔ 向量库（属性文本化） | 交接物 = 派生副本 + **最后刷新时间 + 底座版本**；副本必须可重建 | 检索侧；副本过期会出现「当时的值」用现在的值回答 | 可试点（L2） |
| 底座 ↔ 知识图谱（同步 RDF） | 交接物 = 三元组 + 时态语义的对齐规则；**图侧原生时态弱**（主文件 §2.4.2） | 图侧；两个系统的「当时」必须同义 | 映射 L2 / 时态过滤进检索 L3 |
| 底座 ↔ 湖仓（Iceberg 一类表的快照与时间旅行） | 交接物 = 表级快照；**注意它是加载时态，不等于业务时态**（主文件 §2.2.2） | 湖仓侧；两者混用会在补数据与纠错场景出错 | 既有技术（L1） |
| 底座 ↔ 指标与语义层（如 OneData 一类） | 交接物 = 视图层暴露的宽表 + 口径定义；**6NF 不直接对语义层开放** | 语义层侧；口径只在一个地方定义（§6 案例 4.3 的形态） | 既有技术（L1） |

一句话概括：**AI 没有新增调用关系，只把「读这副底座的人」从分析师换成了模型**。因此接口上多出来的只有三样东西——**时点（这条结论对应哪个业务时刻与哪个加载时刻）、依据（这条结论来自哪张 Attribute 表哪个版本）、生成标记（这条建议是模型出的还是人写的）**。三样缺一，AI 那一层就不能接。

三条最容易出错的约定，单独写清：

**第一，业务时态与加载时态不能混用，且要在接口上分开写。** 主文件 §2.2.2 把三类查询分开讲（业务时态查询、加载时态查询、晚到真相查询），正是因为这两条时间轴承担不同的语义：前者回答「业务上何时如此」，后者回答「我们何时才知道」。湖仓的表级快照属于后者，把它当成前者，会在合规与对账场景给出错误答案，而且不会报错。判定方法：拿一个「补数据」的场景问系统两个问题——补数据之前的那个时点业务状态是什么、我们当时认为它是什么；答不出两个不同的答案，就说明只有一条时间轴。

**第二，派生副本必须可重建、可过期。** 向量与图都是底座的副本，底座一改它们就要跟；跟不上时出现的不是报错，而是「看起来合理但已经过期」的答案——这是 AI 层最隐蔽的失效形态。所以副本要记录「最后刷新时间与底座版本」，并在超期时降级或拒答。判定方法：挑一个上个月改过的属性，看它在向量与图里是不是也更新了。

**第三，写结构必须审计，改结构不允许自动执行。** 这条同时决定接口形态：**只读接口（时点问答、字段级发现）可以省掉身份与预算，写接口一个都不能省**。理由是同一个——**这三类操作（旧表失活、类型演化、Knot 合并）的错误不会当场暴露，而没有当场暴露的错误需要一个人来负责**。

再补一条与湖仓的边界，因为它最容易被当成「已经有了」：**湖仓的表快照是加载时态，底座的双时态是业务时态 + 加载时态**。两者可以并存，但**不能互相替代**：快照回答「我们当时看到的是哪一版数据」，双时态还要回答「业务上当时应当是什么」。当源系统补数据时，前者只会多一个快照，后者才会产生一条新的业务时点版本（主文件 §2.2.2 的「晚到真相」）。判断方法同样具体：问系统「如果这批数据迟到两周才到，业务时点应该落在哪一天」——只能回答「落在两周后」的，是加载时态。

### 5.4 公开进展与文献

分四类列：**论文**、**官方文档 / release note**、**检索入口**、**生产记录**。**能给出论文名 / 文档名 + 年份的，才作为文献条目**；持续更新的产品文档页标一个固定年份反而不可复现，这类只作「检索入口」单列。宁少勿假——本主题的第四类公开能拿到的都是建设方自述，按 5.1 不构成第②条，所以它被单独说明，而不是被凑成证据。

**论文**

- Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", NeurIPS 2020【公开】——检索增强的原始出处，也是「把 Attribute 文本化后送检索」的机制依据。
- **判定入口（这批条目）**：Auto-Anchor Modeling、Bitemporal 数仓自动化、Type-Evolution-Aware Anchor 等——**判断这类条目是否成立，看发布方主页与论文库里是否有同名工作、以及它报的是原型还是产品**；本节不重复其结论、数字与会议名，因为这类条目在转述中最容易变形，而「准确率 X%」这类数字离开语料与口径就不可比。

**官方文档 / release note（有文档名 + 年份锚点）**

- 方法规范与开源实现的名称与年份：**Anchor Modeling 1.0 规范（2010）**、**`anchor_modeling`（Ruby 实现，2013）**、**`anchor-python`（Python 实现，2019）**【公开】（同主文件 §1.4 的记录）——这是修正一里「① 的等价物」的核验入口；核验按这两个实现名检索各自仓库的发布记录，以官方当前版本为准。
- RDF 1.1（2014）与 OWL 2（2009）推荐标准【公开】——核验「Anchor → 三元组」这条映射时，规范是判定入口；时态扩展属规范之外的部分，按主文件 §2.4.2 的提示自行核验。
- 湖仓侧的时间旅行与快照机制（各湖仓项目的官方文档，年份随版本变化）——检索点：官方文档里「快照 / 时间旅行 / 表版本」的正式条目；判定标准是**它给的是加载时态还是业务时态**（见 5.3 的第一条约定），而不是有没有「时间旅行」这个词。

**检索入口（产品文档页持续更新，只给检索点与判定标准）**

- 建模与查询助手类产品（dbt、Snowflake Cortex、Databricks Assistant / Genie、Microsoft Fabric Data Agent、阿里云 DataWorks Copilot 等）——检索点：官方文档里「SQL 生成 / 语义模型生成 / Agent」的正式条目；判定标准是**有没有正式条目、标注的是预览还是 GA**，不是效果文案。
- 湖仓融合与向量原生条目——检索点：这些产品的官方文档里有没有「属性级时态」「按属性建表」这类一等能力；本节不给能力断言，版本与年份以各自官方文档为准。

**生产记录（本主题公开能拿到的都是建设方自述——按 5.1 不构成第②条）**

- 本目录 §6 案例 4.1（Lars Rönnbäck，方法规范与实现，2012–2024）、4.2（字节，2020–2024）、4.3（阿里，2020–2024）、4.4（美团，2021–2024）：它们记的是独立属性表、属性级 `Changed` 时间戳、Knot 共享与视图层这套用法，但**来源形态决定了它们进不了第②条**——4.1 是方法提出者本人的材料，4.2–4.4 由运营方自己发布，且该节的来源标注是无标题的方括号标签（[Anchor Modeling 2012 公开数据]、[字节技术博客 2020-2024]、[阿里 OneData 2020-2024]、[美团技术博客 2021-2024]）。**读它的正确方式是当线索与口径来源，不当第三方证据**：可按这些公司名与年份自行检索核验，具体数字与口径回该节核对。
- 说明：LLM 辅助建模、Agent 自演化、Attribute 送进向量与图谱这三类的公开效果口径目前集中在厂商自有渠道（产品博客、厂商案例）。按 5.1 的判据，这类材料属于 **L2 的证据形态，不构成第三方生产案例**——这不是省略，它就是本节把这三层停在同一档位的原因，也是底座行同样停在 L2 的原因。

**三类证据的更新速度不同**：产品条目最快（以年为单位），规范与实现版本次之（以数年为单位），生产案例最慢。**不要用其中一类的结论去推另一类**——拿今年的助手上线去论证「组织的建模规范已经跟上」，是本主题最常见的一步跳空。

**为什么本节把一批条目降成「判定入口」而不是引用**：产品能力与论文结论这两类条目有同一个性质——**它们的正确性依赖版本与语料**。「某产品支持 Anchor 风格的建表」这句话在一年之内就可能不成立；「自动拆分准确率 X%」这个数离开语料与口径也不可比。**本节的选择是只给核验方法**（去官方文档找正式条目、看标注的是预览还是 GA；去论文库找同名工作、看它报的是原型还是产品），因为方法的有效期比结论长得多。这也是本节对「前沿」这一类内容的基本态度：给判定方法，不给背书。

**核验 §5.1 表里各项宣称的最小动作**（都不需要采购、不需要新版本）：

1. **底座**：挑一个最近新增的属性，看它是「加了一张表」还是「修改了已有表」（见 5.2.1）。
2. **辅助建模**：取 30 个时点问题（含晚到真相类），看生成 SQL 的双时态正确率（见 5.2.2）。
3. **自演化**：取 100 处真实源结构变更，统计检测的漏报与误报两类数（见 5.2.3）。
4. **检索层**：把同一个时点问题分别问「过去」与「现在」，答案相同就说明时点没生效（见 5.2.4）。
5. **写结构**：写下「它代谁执行、依据什么、怎么回滚」三句话；写不全就说明接口还没成立。

这五条的共同点：**它们用的都是你自己的底座、你自己的问题样本和公开文档**。

要说明它们的归类方式：**这五条按能力分，与 §5.1 表的五行不是一一对应**——第 1 条是跨方向的通用检查（它同时是其余四条的前提），第 2–4 条分别对应辅助建模、自演化、检索层三行，第 5 条对应的是自演化那一行的写侧（判 L3 的那半），而 **Anchor → KG 一行在本节没有「当场就能做」的核验动作**。本节把方向判成 L1 / L2 / L3，依据的是 5.1 的三条判据，以及 5.2.1–5.2.4 各自写出的核验动作——**能做出结论的，才有资格进路线图**。

> 四类材料的用法不同：**论文**给机制（为什么这样设计有效），**官方文档与 release note**给接口形态与判定入口，**生产记录**给可用性证据，**检索入口**（厂商文档页）只给线索。落到分级上，5.1 的三条判据各有对应的证据类——①（规范与带版本记录的实现）与 ③（接口稳定）靠标准与官方文档，②（第三方非厂商的生产案例）靠生产记录——**三条都进判据**；论文解释机制但不单独给级别，检索入口只给线索、不进判据。不做这个区分，本节就会退回成趋势清单。

### 5.5 被过度宣传的部分

**「Anchor 演化为 AI 原生数据底座」与「Auto-Anchor 成为主流 = 零建模人力」（分别来自趋势 1 与趋势 2；趋势 1 的原话是「从『极致规范化』演化为『AI 原生数据底座』」，而第三条风险讲的是反面——「关键决策仍需要架构师判断」，不是趋势 2 这个说法的出处）** —— 实际是两件事都没有发生。其一：AI 需要的确实是「字段级、带时间、机器可读」的结构，而这套底座恰好长成这样；但 6NF 的代价（表数量、多表 JOIN、视图层工程量、团队学习曲线）**一条都没有被 AI 消掉**——AI 消掉的是「读 DDL 与写建议」这段人力，不是结构本身的复杂度。其二：模型能给拆分建议，但「哪些字段独立成 Attribute、Knot 的粒度多细」是业务语义与治理决策，做错了返工成本高于人工建模；更关键的是它**没有历史包袱**（不知道下游已经依赖了哪张表、哪次类型演化是为了绕开什么限制）。原因：**把「结构恰好契合」与「产出变便宜」都当成了「问题解决了」**——趋势 1 的原话只是一句方向判断，被转述成「AI 原生的最佳数据底座」才是加码的那一步；趋势 2 则把「候选的产出成本下降」直接说成了「零建模人力」，两者跳过的都是同一件事：**责任不能自动化**。**它们什么时候才会成真**：趋势 1 要等模型能把自然语言的时点问题稳定翻译成正确的 bitemporal 查询、且在你的评测集上通过——判定方法是**把时点改一改，看答案变不变**；趋势 2 要等出现公开的、写明「提议 → 定案 → 回归验证」完整闭环与验收口径的实践，而不是「一键生成全模型」的演示。

**「Bitemporal as a Service / 双时态是平台标配」** —— 实际是：多数平台的「时间旅行」是**加载时态或表快照**，不是「业务时态 + 加载时态」的双时态；把快照当双时态，会在「补数据」与「纠错」两类场景上给出错误答案，而且不报错。原因：把「能回到过去某个版本」当成了「能回答业务在那个时候是什么样子」。**它什么时候才会成真**：平台官方文档把两个时间轴列为独立可查维度，且能回答主文件 §2.2.2 的三类查询；在此之前，判定方法是问那两个问题（业务当时如何 / 我们当时认为如何），答不出两个不同的答案就是单时态。

**「Anchor + Vector + KG 三层融合」** —— 实际是：三样东西各自的检索语义不同——向量给语义近邻、图给多跳、SQL 给精确时点，而**融合层的失败形态是「不知道该信哪一路」**：三路给出不一致的答案时，谁说了算？这个问题没有被回答。原因：把「能拼在一起」当成了「已经对齐」。**它什么时候才会成真**：出现公开的冲突消解规则（哪一路在什么问题上优先）与对照评测；在那之前，把三者做成同一条流水线上的候选而不是一个「统一知识层」。

这三条的共性值得点明：**它们都把「接口变简单」或「结构恰好合适」说成了「问题解决了」**，而本主题的瓶颈始终是两件事——**时点语义有没有被正确表达**，以及**结构变更的责任归谁**。反过来说，这些方向不是不能做：它们都是底座质量的**放大器**——底座规范、视图齐备时放大收益，底座混乱时放大错误。先量双时态正确率与视图物化率，再决定放不放大，是本节最省钱的一条习惯。

**厂商材料在这个主题里该怎么用**：产品博客、客户故事与能力清单都可以当**线索**（它们告诉你这个方向有人在做），但不能当**证据**（它们不提供语料口径、误判率与适用条件）。把线索当证据的典型后果，是把「某平台的 Agent 已经能自动建模」当成自己可以照抄的流程；而可核验的事实通常是另一副样子——**建议生成与定案是两件事，后者没有被自动化**（5.2.2 的产出与责任边界）。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| LLM 会先吃掉「建模的文档化产出」（术语表、字段说明、拆分建议），而不会先吃掉「结构调整」 | 建模与数仓工具的官方文档里出现「生成建议 → 人工确认」的成对条目；产品把建议与执行分成两项能力 | 三年后仍在演示「一键生成并上线全模型」，且拿不出定案与回归验证的流程说明 |
| 双时态会以**查询语义**而不是存储形态进入平台能力（两个时间轴成为独立可查维度） | 湖仓与数仓产品的官方文档把「业务时间 + 加载时间」列为两个独立维度，并能回答晚到数据类查询 | 三年后平台仍只提供快照式时间旅行，且没有第二个时间轴；或「双时态」只出现在与某建模方法绑定的文档里 |
| Agent 对结构的权限会先落在**检测与告警**，不会落在「自动改表」 | 产品把漂移检测与自动变更分成两项能力，并给前者标注 GA；公开材料里出现「不可逆操作必须人工」的约束 | 出现公开允许 Agent 直接改表结构（失活旧表、改类型）且无审计与回滚条款的案例 |
| 6NF 类方法不会成为 AI 时代的默认建模法，但它的两条机制（属性独立演进、双时态）会被部分吸收 | 主流建模工具与数仓产品的官方文档里出现「单属性级变更历史」或「双时态」条目，即使不以 6NF 命名 | 三年后主流建模仍以宽表 + 单时态为默认，且没有任何时态选项；或反过来，6NF 成为默认且表数量问题被证明不成立 |

写这四条的约定：**信号必须是外部可观察的**（官方文档条目、产品能力分级、公开规范），不是「我觉得会」。**被检验得最快的是第一条与第三条**——一年内就能从产品文档里看到；**最慢的是第四条**，建模方法的默认形态以数年计，本节对它不给时间预期。凡写不出证伪信号的判断，本节不写。

还要补一句关于「风险点」的读法：三条风险（过度工程化、多 Attribute JOIN 的性能、LLM 生成的局限）**不是「趋势的反面」，而是这套底座自带的成本项**。它们不会随 AI 变好而消失——前两条是 6NF 的结构性代价（靠视图层与物化缓解，不靠模型），第三条把责任推回了定案环节。**把风险点当成「待解决的技术问题」去找工具，是这一节最常见的误读**：能解决的只有第三条的一部分（更好的抽取与生成），前两条只能靠工程分工与团队能力来吸收。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 字段变化慢、时态要求弱 | 用维度建模或 Data Vault，只在需要时点追溯的实体上加时序 | 观察「时点问答案」的占比 | 不要因为「AI 原生」就上 6NF——主文件 §2.4.1 给的界线是每周十个字段变化 |
| 字段变化快、合规要时点问答 | 先做「每属性一表 + 三个时态字段 + 视图层」，并把视图物化 | 观察视图查询 P95 与物化率两个数 | 不要让 BI 直连 6NF（§6 案例 4.3 的教训） |
| 想让 LLM 帮忙建模 | 先定拆分与命名规范，再让它只产出候选与文档 | 观察建议的采纳率、以及事后的返工率 | 不要让模型直接改已有表结构、合并 Knot、或执行类型演化 |
| 已有底座、想接 Agent | 只开只读：字段级发现 + 带时点的查询模板 | 观察生成 SQL 的双时态正确率与「晚到真相」类问题的正确率 | 不要开放写结构的权限；不要让 Agent 自动失活旧表 |
| 想做自演化 | 先做漂移检测与合规告警（有可判定定义的那半） | 观察漏报与误报两类数 | 不要让 Agent 自动执行类型演化或 Knot 合并 |
| 想接检索层做时点问答 | 先定文本化模板（必须含时点与来源），再建派生副本 | 观察「改时点答案是否变化」与副本过期率 | 不要在没有副本刷新时间与底座版本的情况下开放问答 |
| 正在选时序平台或湖仓 | 用主文件 §2.2.2 的三类查询考它（业务时态 / 加载时态 / 晚到真相） | 观察官方文档是否把两个时间轴列为独立维度 | 不要把「快照式时间旅行」当双时态采购；不要为「AI 原生数据底座」这个标签支付溢价 |
| 底座已经有数千张表、元数据没人管得住 | 先建「表注册 + 命名规范 + 变更留痕」三件套 | 观察新表是否有规范命名、变更是否可追到人 | 不要在注册中心没建起来之前先上漂移检测——检出大量噪声后这套机制会被关掉 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（静默算错、结构不可逆、副本过期、把加载时态当业务时态），**而收益依赖一个尚未成立的假设**（模型能判断拆分对错 / Agent 有可回滚的权限模型 / 模板已经覆盖时点语义）。等 §5.6 的信号出现再投入，损失的只是时间。

另外注意顺序：表里第二行是其余各行的前提。**底座与视图层没做完就上 AI 层，会出现「AI 表现得还行、但没人知道它对不对」的状态**——这比明显不可用更危险，因为它会让人停止补视图与规范。要留意的是，这一行按 5.1 的判据是 L2（缺第②条），所以它「现在就该做」的含义是**先按 5.2.1 测出那三个数、在自己的语料上留下那条记录**，而不是把它当成一次不可回退的全面迁移。判据很简单：**模型的答案能不能指回一张具体的 Attribute 表与一个具体的时点**；指不回去的答案，无论多流畅都只是文本。

最后一条通用习惯：**每当有人提议引入一个「AI 建模 / 自演化」能力，先问它接在 5.3 表的哪个交接物上**。接不上的，说明它要解决的问题还没被定义清楚——此时该做的是补那份交接物（谁来定案、依据什么、怎么回滚），而不是先买能力、再回头补流程。本主题的失效几乎都发生在这个顺序被颠倒的时候。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**候选的产出成本**——LLM 把「读 DDL 与文档、提出拆分建议、写出 bitemporal 查询」这段从架构师的时间换成了推理，于是瓶颈第一次从「能看多少张表」移到了「能复核多少条建议」。而本主题最成熟的一行仍是四件套 + bitemporal 底座（Anchor / Attribute / Tie / Knot + 原生双时态 + 视图层），**它完全不是 AI 带来的**：规范、演化算法与视图层都在 LLM 之前成型（主文件 §1.4），公开记录见 §6 案例 4.1–4.4；按 5.1 的判据它只到 **L2**——①③ 站得住，缺的是第②条（公开的生产记录都是建设方自述，4.1 还是方法提出者本人的材料）。缺这一条不影响它能不能用，只影响它能不能被排成核心依赖：AI 只是把底座的一个副产品变得值钱——每个属性独立成表且自带时点，本身就是「字段级、带时间」的元数据。它**没有**改变的是两件事：一是**结构决策的责任**——加一张 Attribute 表、定一个 Knot 的粒度、做一次类型演化，仍然是不可自动化的治理决定；二是**时点语义的正确性**——业务时态与加载时态混用、模板漏掉时点、副本过期，这三类失败都不会报错，只会静默地算错。
>
> 判断本主题任何新提法的快捷方式：**它改变的是「建议从哪来」（产出成本），还是「结构与时点的正确性」（质量）？** 改产出成本的，先量双时态正确率与采纳率再决定；改质量的（视图物化、时态字段、副本刷新、定案流程），直接做——它衔接本节最成熟的那一行（底座），也是其余所有方向的前置条件。
