## 7. 与其他方法对比

> 本章的方法对比散在三处：§1.1 两张方法论对照表，§2.1 一张构件对照表，§2.4 三张（2.4.1 vs Data Vault、2.4.2 vs 本体建模、2.4.3 vs 事件溯源；2.4.4 是条目式的适用条件清单，不含表）。这些表停在「性质差异」而没有落到选型决策上，本节把它们收进同一套判据下，按「先立判据 → 讲机制 → 给证据 → 给决策」组织。

### 7.1 先立判据：为什么打分表会误导

打分表把「取决于场景的结论」伪装成「绝对结论」。本主题最容易被这样写死的一项是「粒度」：属性切得越细，写侧越省（一次变更只写它真正改动的那一个属性，见 [§3.2.1](04-anchor-modeling-section-3-sec3.md)），读侧越贵（拉一次实体全貌要对 N 张属性表做 N 次索引访问，见同一节的失效点）。同一个性质在写侧是加分项、在读侧是减分项，而这两侧的人不是同一批人。一旦写成 `灵活度 5 分 / 性能 3 分`，读者既看不出那条分界在哪里，也看不出分界两侧的收益与代价各由谁承担。规范化本身并不消灭成本，它只是把成本在读写两侧重新分配（[§3.5](04-anchor-modeling-section-3-sec3.md) 第五条反模式的成因一栏）。

第二层误导是**把不同层的东西放进同一张表排名**。本节涉及的候选分属四层：ER(3NF)、Data Vault、Anchor 是**集成与演化**的解法（回答「属性持续新增时结构怎么长」）；星型与反规范化宽表是**查询结构**的解法（回答「给定访问模式要连几张表」）；本体建模是**语义互操作**的解法（回答「多套系统对同一概念的理解怎么对齐」）；事件溯源是**状态如何被派生**的解法（回答「当前状态是算出来的还是存下来的」）。四层可以同时存在——[§3.4](04-anchor-modeling-section-3-sec3.md) 的组合三就是「6NF 底表 + 视图层 + 物化切片」这种跨层叠加。把它们压进一张打分表，得到的是一张不可比的表。

第三层误导是暗示这些方案**互斥**。真实系统的形态是分层叠加：集成层选一个方案、查询结构层选一个，消费接口再选一个。所以本节比较的对象不是「哪个方案总分高」，而是**每一层各自该选什么**。Anchor Modeling 属于第一层，因此它能被有效比较的方向只有一个——在集成层里，**一个实体要被切到多细**。这条轴上只有三个刻度：整行（3NF 原地改表、星型 SCD）、属性组（Data Vault 的卫星表）、单个属性（Anchor 的 Attribute 表）。7.3 的四个机制维度，就是用来量这三个刻度在不同条件下各自会怎样表现。

所以本节采用的判据不是「好 / 快 / 灵活」，而是六个能回答「在我的约束下会怎样」的问题。它们的排列顺序本身就是一条结论：第一条决定写侧结构，第二条决定读侧要付多少，第三、四条划出演化与时态的边界，后两条决定这份结构能不能活过第二年。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 版本粒度 | 一次业务变更产生的新版本，附着在整行、一组属性，还是单个属性上 | 它同时决定写入量、历史行的存储量与「属性之间会不会互相牵动」——三者是同一个选择的三个侧面（7.3.1） |
| 读侧组装位置 | 把 N 张属性表拼回一个实体，这份成本由视图、物化，还是消费方自己付 | 6NF 的收益在写侧、代价在读侧，两侧不是同一批人；选型必须先说清谁来付（7.3.2） |
| 变更传导半径 | 加一个属性、改一次类型，各要动几张表、要不要回刷历史 | 它决定的是三年后的维护成本，而不是上线当天的成本（7.3.3） |
| 时间轴的条数与层位 | 「业务何时发生」与「系统何时知道」记在哪一层、记到多细 | 决定能不能回答「当时的系统看到的是什么」，也决定晚到的数据有没有位置可落（7.3.4） |
| 元数据对象规模 | 一个实体对应多少张表、多少条元数据记录 | 对象数决定目录 / 语义层是可选还是必需；没有它，模型即使正确也没人能用 |
| 工具与知识锁定 | 离开它要重写什么、团队要重新学什么 | 方法论本身是公开的设计约定，但落地它的生成器、视图层与表格式会绑定；本主题的锁定主要发生在人身上，见 7.2 与 7.7 |

举一个本主题的具体例子，说明「同一维度在不同场景下权重相反」是怎么发生的：如果只按「加一个属性的成本」打分，Anchor 是满分——它确实是零 DDL、零回刷。但同一个满分机制必然带来读侧的组装成本（7.3.2）：在消费方只有 1 个、且只做「点查某个属性」时，这笔成本可以忽略；在消费方有 20 个、且都要拉实体全貌时，它就是主成本。**分数没有变，是场景变了**——而打分表恰好把「场景」这个自变量吸收进了分数里，于是读者失去了判断的依据。所以上表的判据一律写成「问一个问题」，而不是「给一个分数」。

### 7.2 候选方案全景

下表覆盖主文件 §1.1、§2.4 与本目录 §3 讨论过的全部候选。**评分列被替换为「核心机制」列**——机制相同则分数必然相同，机制不同则分数无意义。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| ER 建模（3NF） | 集成与写入一致 | 按函数依赖消除冗余，结构不随查询形态变化 | Inmon 企业级数仓路线（《Building the Data Warehouse》，1992 年首版）【公开，1992】 | 方法论公开 |
| 星型 + SCD | 查询结构与历史 | 维度层次拍平，历史以维表行的版本表达 | Kimball 方法论（《The Data Warehouse Toolkit》，1996）【公开，1996】 | 方法论公开，工具各异 |
| Data Vault 2.0 | 集成与演化（中等粒度） | Hub / Link / Sat 三类表分离，属性按**属性组**成组按时态追加 | 监管行业与多源集成层；Data Vault 2.0 由 Linstedt 与 Olschimke 在 2015 年系统化【公开，2015】 | 方法论公开；工具链含 dbtvault 与商业 ETL（见主文件 §1.1） |
| Anchor Modeling | 集成与演化（最细粒度） | 一个属性一张表，历史即该属性表自身的追加行；底座 6NF + 对外视图 | 属性演化频繁、结构需长期存续的核心实体（[§6](04-anchor-modeling-section-6-sec6.md) 的 4 个案例） | 方法论公开（Anchor Modeling 1.0 规范于 2010 年发布，见主文件 §1.4）【公开，2010】 |
| 反规范化宽表 / 物化切片 | 查询结构（派生层） | 把 JOIN 从查询时搬到写入时，代价是回刷范围等于历史长度 | 湖仓 Ad-hoc、特征工程、Anchor 之上的消费层 | 工具无关 |
| 本体建模（RDF / OWL） | 语义互操作 | 用类与关系表达业务概念并可推理；W3C 的 RDF / OWL 为公开标准（OWL 于 2004 年成为 W3C 推荐标准）【公开，2004】 | 知识图谱、跨系统语义对齐 | 标准公开，实现各异 |
| 事件溯源 | 状态派生方式 | 只存不可变事件流，当前状态由回放或投影（projection）得出 | 业务事件系统；该术语的公开系统化表述通常归于 Martin Fowler 2005 年前后的文章【公开，2005】 | 模式公开 |

本节不另设工具打分表：本主题的工具差异**不足以改变结论**。落地工具（anchor_modeling gem、anchor-python、dbt + anchor、SQLBDM）与平台（PostgreSQL、Snowflake、Databricks、阿里云 DataWorks、Materialize、RisingWave、DuckDB）的完整清单与适用场景见 [§4.3](04-anchor-modeling-section-4-sec4.md)；它们在选型中只承担一个角色——**决定你能不能把视图层与语义层做成自动生成的产物**。这一点很关键：7.3.2 会说明，Anchor 的成败取决于读侧组装是否被交付，而自动生成是让这份交付可持续的唯一现实手段。

七个候选分三**族**：**集成结构族**（3NF、Data Vault、Anchor）之间只差「切到多细」；**查询结构族**（星型 + SCD、宽表 / 物化）之间只差「JOIN 搬到写入侧还是留在查询侧」；**语义与状态族**（本体、事件溯源）不改数据的物理切法，只改「概念怎么表达」与「状态算不算得出来」。跨族差异远大于族内差异——**族内换方案通常只是重排 JOIN，跨族换方案要重建链路**。Anchor 与 Data Vault 同族，两者之间的取舍全部落在 7.3 的四个机制维度上。

表里有一行容易被读者当成靶子而不是候选：**反规范化宽表**。它在本章出现的方式是反面参照（[§3.5](04-anchor-modeling-section-3-sec3.md) 的「忽略反规范化视图层」与「把 Anchor Modeling 当成银弹」两条反模式），但在真实系统里它是**默认选项**——多数团队并没有做过选择，他们手上就是一张宽表。把它列进候选而不是只当靶子，是因为 7.5 的 Q1 一旦答「否」，它就是正确答案；把它当靶子的团队，最终会以「自建宽表副本」的形式重新把它建回来（[§3.5](04-anchor-modeling-section-3-sec3.md) 的绕过形态）。

主文件 §2.4.2 与 §2.4.3 已经分别给出过 Anchor 与本体建模、与事件溯源的对比结论（前者近乎「工程版的三元组」，后者思想相似但一个偏状态、一个偏事件）。把它们放进本节同一套判据后结论不变，但能看出这两者为什么不属于集成结构族：**它们都不以「属性切到多细」为设计变量**，所以 7.3 的四个机制维度对它们只部分适用。本节在各机制表里把它们标出来，是为了说明一件事——它们不是 Anchor 的替代品，而是另外两个问题的答案（语义对齐、状态可重放）。

### 7.3 机制差异：为什么它们表现不同（核心节）

以下四个机制维度覆盖了全部候选，也是「为什么它们表现不同」的全部原因。每个维度给出机制定义、各候选的实现差异、由机制必然导出的性质（写成「因为 A，所以 B，代价是 C」）以及失效条件。

四个维度的顺序不是任意的：7.3.1 决定写侧，7.3.2 决定读侧，7.3.3 决定演化侧，7.3.4 决定时态侧。**Anchor 的主要优势集中在 7.3.1、7.3.3 与 7.3.4，主要代价集中在 7.3.2**——记住这个分布，7.5 的决策树就是它的直接推论。

#### 7.3.1 版本粒度：一次变更产生的新版本附着在什么单位上

**机制是什么**：业务上一次变更发生时，物理层必须追加多少数据。附着单位越大，被连带重写的「没变的属性」就越多。

**各候选的实现差异**（同一实体，属性数记为 k）：

| 方案 | 新版本的附着单位 | 一次「改 1 个属性」的写入 | 历史里是否含伪变更 |
| --- | --- | --- | --- |
| 3NF 原地改 | 整行（无版本概念，就地覆盖） | 改该列 | 不适用（没有历史） |
| 星型 + SCD Type 2 | 整行 | 新增 1 个整行版本 | 有：其余 k−1 列被连带复制 |
| Data Vault 的 Sat | 属性组（同一卫星表内的属性成组联动） | 新增 1 个卫星表版本 | 有：组内其余属性被连带 |
| Anchor 的 Attribute | 单个属性 | 新增 1 个属性行 | 无：其余属性不受影响 |
| 事件溯源 | 一条事件 | 追加 1 条事件 | 无（事件本身就是变更的单位） |

**由此必然导出的性质**：因为 Anchor 把版本的单位压到单个属性，所以一次只改 1 个属性的变更，在它这里只写 1 行、在 SCD Type 2 下要写 1 个整行版本——**当属性的变化频率相差悬殊时，后者的写入量由「最快的那一个属性」决定，而前者的写入量由「实际变化的属性」决定**。这就是本节全部收益的来源，也是唯一一条能写出算式的收益（7.4 给出算式）。反过来，因为 Anchor 的每一行都要自带三组时态列（业务起、业务止、加载时），所以**它的行更宽、行数也更多**：同一个实体在 Anchor 下是「属性数 × 非空版本数」行，在宽表下是「版本数」行。**写入量的收益与存储量的代价来自同一个机制**，任何只说其一不提其二的对比都是不完整的（7.4 的推算给出了两者相抵的等值点）。

**公开证据**：6NF 这一范式（任何非平凡连接依赖都不存在，因而每个属性独立成表）的系统化表述见 Date、Darwen 与 Lorentzos《Temporal Data and the Relational Model》（2003）【公开，2003】；Anchor Modeling 把这套范式用作工程底座、并让每个属性表自带时态的做法，见本目录 [§3.2.1](04-anchor-modeling-section-3-sec3.md) 与主文件 §2.1 的结构定义。Data Vault 一侧，Hub / Link / Sat 的三分法与「卫星表内部属性成组联动」见 2015 年的系统化著作【公开，2015】。

**失效条件**：当属性之间**同频**时（一个实体的所有属性都由同一次业务事件同时改写），拆分的写入收益归零，而对象数与 JOIN 数照付——此时正确动作是合并（[§3.2.3](04-anchor-modeling-section-3-sec3.md) 的时态分组），甚至直接退回宽表。反转条件是**变化的分布**，不是变化的总次数。

上表只覆盖了属性的版本粒度，还有一条同源的线是**关系的版本粒度**。Anchor 把关系建成 Tie、同样自带时态，于是「号码过户」这类归属变更被记录为边的新版本，而不是覆盖某个字段的值（[§3.2.2](04-anchor-modeling-section-3-sec3.md)）；在星型与 3NF 下要把关系的历史表达出来，只能额外再建一张拉链表。同一条因果在这里再次成立：**把变更的单位选小，历史就是追加；选大，历史就得靠额外结构来补**——这条判据在属性与关系两侧同时适用，而 Anchor 是少数把两侧都做小的方案。

还有一处与粒度直接相关、容易被漏算的开销：**每张属性表都要携带一份实体标识**。6NF 下同一个实体标识在 N 张属性表里各存一份，而宽表里它只出现一次；属性数越多，这份重复越大。7.4 的存储推算里，那 8 字节的主键就是它——**「一属性一表」买来的是独立演化，付出的除时态头之外还有这份标识的份数放大**，这也是 [§3.5](04-anchor-modeling-section-3-sec3.md)「过度拆分」反模式在存储侧的量化来源。

#### 7.3.2 读侧组装位置：N 张表拼回一个实体，成本由谁付

**机制是什么**：6NF 把一个实体拆成 N 张表，任何一次「看这个实体」的查询都必须把 N 张表重新组装。这份组装成本不会消失，只会在三个位置之一出现：视图 / 语义层、物化切片、或消费方自己写的 SQL。

| 方案 | 读一个实体全貌的组装方式 | 组装成本落在谁身上 | 元数据对象量级 |
| --- | --- | --- | --- |
| 星型 | 1 次事实 → 维表 JOIN，层数固定 | 查询引擎（成本可预测） | 每实体 1 张维表 |
| Data Vault | 沿 Hub / Link / Sat 链路连接，通常之上再建星型 | 查询层（常见做法是再建一层） | 每实体 1 Hub + 若干 Sat |
| Anchor | 本次查询用到的**每一个属性**都要一次索引访问与 JOIN | 视图层或语义层（若由消费方付，则模型会被绕过） | 每属性 1 张表 |
| 本体 | 由查询改写 / 推理得出，与物理表解耦 | 图查询引擎 | 概念与关系数量级 |
| 事件溯源 | 回放事件或读投影 | 投影链路的维护方 | 事件类型 + 投影数量级 |

**由此必然导出的性质**：因为 Anchor 把一个实体的「列」变成了「表」，所以**读一次全貌的成本与属性数成正比**，而星型与宽表的这一成本近似为常数——这是「因为 Attribute 只含 1 个属性，所以读侧必须付 N 次索引访问」这条因果链，不是调优能消掉的下限（[§3.2.1](04-anchor-modeling-section-3-sec3.md) 的失效点）。也正因为组装成本必须落在某一处，**Anchor 的交付物里必须包含视图层或语义层，否则读侧成本会被消费方直接感受到，而消费方的应对方式一定是自建宽表副本**——[§3.5](04-anchor-modeling-section-3-sec3.md) 把这条写成「忽略反规范化视图层」反模式，并说明它的暴露方式是滞后爆雷。同一机制还有第二个后果：因为每个属性都在元数据里独立占了位置，所以「这个实体有哪些属性、各自的口径与来源」可以完全由元数据回答，机器不必读文档——这是本节与它们的 Agent 场景（主文件 §1.3、[§5](04-anchor-modeling-section-5-ai.md)）的共同基础。

**公开证据**：卫星表之上通常需要额外的 PIT / Bridge 结构才能提供可用查询，以及 6NF 底座需要对外暴露 3NF 形态视图，这两点分别见 Data Vault 2.0 的系统化著作（2015）【公开，2015】与本目录 [§3.2.1](04-anchor-modeling-section-3-sec3.md)、[§ 6 的四个案例](04-anchor-modeling-section-6-sec6.md) 记录的落地形态（案例中视图层与物化视图均为必备件）。视图层是否支持你需要的聚合与时间切片能力，可按所选查询引擎的官方文档当前版本核验；至于视图层有没有真正替消费方承担组装职责，一个可执行的自检方法是：把最常用的 10 条查询的定义写出来，数其中 JOIN 的个数，并逐条看这些 JOIN 打的是视图还是底表——**打视图的，组装已被视图吸收，消费侧应当只剩投影与过滤；仍在消费侧串联底表的，就是漏到下游的那部分成本**。这条判定只给方向、不给固定比值（同类阈值在 [§3.7](04-anchor-modeling-section-3-sec3.md) 第 4 条按【经验】档处理：下游直连 5 张以上底表即为违反）。

**失效条件**：当视图层存在但**不做物化、也不做分区裁剪**时，「组装一次」的成本会在每次查询上重复支付；当消费方被允许直连底表时，视图层形同不存在。判定的方法很直接：抽查一个下游查询，若它出现 5 张以上底表的直连 JOIN（[§3.7](04-anchor-modeling-section-3-sec3.md) 第 4 条自检项，该阈值为【经验】档），说明组装成本已经落到了消费方身上。

读侧还有一处必须计入的固定开销：**Knot**。因为枚举值被抽成共享字典，属性表引用它一次就多一次 JOIN（[§3.2.4](04-anchor-modeling-section-3-sec3.md)），所以当实体属性数已经在数百量级时，Knot 的取舍不再是「统不统一口径」的价值题，而是「多几次 JOIN 换一次字典变更」的算术题。判据在 [§3.3](04-anchor-modeling-section-3-sec3.md) 已经给出：被 ≥2 处引用才抽 Knot，单实体独占的枚举直接存值，否则收益为零而 JOIN 照付。

三种承载方式（视图层、物化切片、消费方自付）不是可以自由替换的：视图层让成本每次查询都付、但能被优化器吸收；物化让成本一次性付清、但要维护一条刷新链路与一份陈旧度指标；消费方自付则是模型即将被绕过的前兆。**所以选型时要问的不是「要不要建视图层」，而是「视图层覆盖了哪些高频切片」**——只建通用视图而不针对高频场景物化，等于把 JOIN 成本原样传给下游（[§3.7](04-anchor-modeling-section-3-sec3.md) 第 12 条自检项）。

这里还有一个常被忽略的反向情形：**点查单个属性时，6NF 反而是最快的结构**。因为该属性独占一张窄表，查询只需一次索引访问，不必像宽表那样先读到整行再取其中一列（[§3.1](04-anchor-modeling-section-3-sec3.md) 的「访问模式」一栏已把它写成约束）。所以「Anchor 读侧贵」这个结论只在**拉实体全貌**这类查询上成立；选型前应当先统计消费方的查询构成——**点查占比高时，本节的读侧成本会被大幅抵消**。这是本主题里唯一一条对 Anchor 有利的读侧机制，也是最容易被它的批评者忽略的一条。

#### 7.3.3 变更传导半径：加一个属性、改一次类型要动什么

**机制是什么**：一次结构变更影响到的对象范围——是「一张表的一个局部」，还是「所有引用它的对象」。半径越小，演化越接近免费。

| 方案 | 加一个属性 | 改一次属性类型 | 传导范围 |
| --- | --- | --- | --- |
| 3NF | 加一列（既有查询不受影响） | 原地 ALTER，视引擎而定是否需要重写整表 | 局部，但改类型可能触及全表 |
| 星型 | 改 1 张维表 + 回刷下游 | 改维表 + 回刷下游 | 1 张表 + 下游 |
| Data Vault | 新增 1 个 Sat（既有 Hub / Link 不动） | 新增 Sat 版本，历史可并存 | 局部 |
| Anchor | 新增 1 个属性表（既有表一列不动） | 新增 v2 属性表 + 旧表闭段（[§3.2.6](04-anchor-modeling-section-3-sec3.md)） | 局部 + **查询层重建** |
| 本体 | 加一个类或属性 | 改本体定义（可能触发推理） | 定义层，物理层不动 |
| 事件溯源 | 加一个事件类型（不改既有事件） | 改投影逻辑 | 投影层 |

**由此必然导出的性质**：因为「加一个属性」在 Anchor 下等价于「新建一张表」，所以它**不需要触碰任何既有对象、不需要回刷历史**，这条性质在属性每周都在新增的实体上直接把 DDL 与回填从工期里删掉（主文件 §1.2 的第一个业务驱动力）。代价是同一枚硬币的另一面：新增的属性必须**同时进入视图层与语义层的定义**，否则它对消费方等于不存在——这就是 7.1 判据表里「变更传导半径」一栏要问「要不要动下游」的原因。**锚定的不是表，而是「当前有效的那份读侧定义」**：表可以零成本加，读侧定义不能。Data Vault 在这一维度上走的是同一条思路、只是粒度粗一档：新增一个卫星表即可，且读侧通常已有一层星型承接。两者共同的失效形态是**演化次数积累后的「当前有效」这份知识无处安放**——[§3.2.6](04-anchor-modeling-section-3-sec3.md) 的失效点把它写成「查询侧的时间缝合」。

**公开证据**：「新增对象不动既有对象」是 Data Vault 的公开设计目标（2015 年的系统化著作）【公开，2015】；「加属性 = 加表、旧表闭段保留历史」这一动作在本主题的方法论里就是类型演化（Type Evolution），本节按书内定义引用——结构见本目录 [§3.2.6](04-anchor-modeling-section-3-sec3.md)，算法见主文件 §2.3.5；判定某工具链能否把这一步自动化，可查其文档是否提供「从模型定义生成 DDL 与视图」的能力（方法与核验入口见 [§4.3](04-anchor-modeling-section-4-sec4.md)）。

**失效条件**：当同一个属性被演化了三次以上时，每张表只覆盖一段互不重叠的区间，回答「任意时点的值」必须 UNION 多张表再取最新——**「零中断」会反转成「查询侧的时间缝合」**，且这段缝合逻辑没有天然的位置可放（[§3.2.6](04-anchor-modeling-section-3-sec3.md)）。此时必须给它一个统一收敛点（属性版本视图），否则每个消费方各自缝一遍。

同一条「传导半径」的思路还有一个尺度不同的例子：**Knot**。它的机制是把同一语义收敛到一个 ID 空间里，于是「改一次币种名称」变成单行更新，而不再是「在所有引用它的表里做一遍字符串替换」（[§3.2.4](04-anchor-modeling-section-3-sec3.md)）。这是一次半径**放大**换效率的交易：共享的是同一个语义对象，而不是各自的一份拷贝，所以字典里的取值一旦被重新解释（不只是改名，而是口径变化），所有引用方的历史数据会被追溯性地改变含义。正确的用法不是「枚举一律抽 Knot」，而是给它加**版本边界与变更审批**（[§3.7](04-anchor-modeling-section-3-sec3.md) 第 6 条自检项）。

上表没有单列「加一个关系」这一列，因为它在几条路线上的答案与「加一个属性」同构：Anchor 加一张 Tie 表、Data Vault 加一个 Link、星型要么给事实表加外键要么新增一张桥接表。**在这条判据上，属性与关系可以并置讨论，不必分开**——这也正是 7.1 判据表把「变更传导半径」写成一句「各要动几张表」而不区分属性与关系的原因。

#### 7.3.4 时间轴的条数与层位：「何时发生」与「何时知道」

**机制是什么**：时态字段记几条时间轴、挂在哪一层、粒度多细。它决定系统能否区分「业务何时发生」与「我们何时知道」。

| 方案 | 时间轴条数 | 挂在哪一层 | 粒度 |
| --- | --- | --- | --- |
| 星型 + SCD Type 2 | 1（业务有效期） | 维表行的起止两列 | 整行 |
| Data Vault 2.0 的 Sat | 2（加载时间 + 业务有效期，后者常由 effectivity satellite 承载） | 卫星表 | 属性组 |
| Anchor | 2–3（业务起、业务止、加载时；可加删除时） | **每个属性表各自携带** | 单个属性 |
| 本体（RDF / OWL） | 默认 0，需扩展承载 | 需靠具名图或具体化（reification）一类结构表达 | 按三元组 |
| 事件溯源 | 1–2（事件发生时间 + 记录时间，后者在双时态事件溯源中显式化） | 事件本身 | 单条事件 |

**由此必然导出的性质**：因为 Anchor 把两组时间轴**放在每一个属性表上**，所以两条时间轴是属性级的，而不是实体级的——「2018-03-15 那天系统看到的张三的姓名是什么」与「同一时刻系统看到的他的手机号是什么」，可以由两次独立的属性级查询各自回答，互不牵动；在 Data Vault 下这两问的粒度退到卫星表，在同一卫星表内的属性会成组联动。因果可以直接读出：**属性级的时态是属性级版本粒度的推论，不是独立功能**——7.3.1 选了单属性粒度，7.3.4 就自动获得单属性时态；反过来，如果只在实体级记时间轴（星型 + SCD），那么晚到的变更只能以「重写整行」的方式落地，加载时态所承载的那份认知状态就无处记录。这解释了为什么「只记两组时间」的系统在上线初期完全正常——晚到的变更占比低，问题要等到补历史或跨源回填时才暴露（[§3.5](04-anchor-modeling-section-3-sec3.md) 第四条反模式）。

**公开证据**：把「有效时间」与「事务时间」作为两条独立时间轴的时态关系模型，见 Snodgrass《Developing Time-Oriented Database Applications in SQL》（1999）【公开，1999】；RDF / OWL 本身不以时态为一等公民，用它们表达「带时态的关系」需要额外的结构（具名图、具体化（reification）一类做法），具体做法按 W3C 规范与所选三元组库的官方文档当前版本核验（OWL 于 2004 年成为 W3C 推荐标准，见 7.2 表「本体建模」一行）；Data Vault 2.0 的加载时间轴见 2015 年的系统化著作【公开，2015】。

**失效条件**：三组时态不是免费的。它让每一行更宽、让每一条查询都必须显式声明「业务时点 + 加载时点」两问，而多数消费方只会声明其中一问——**多出来的那条轴在没人会用的场景里只是查询书写负担与存储开销**。判断要不要第三条轴的方法只有一个：能不能举出一个真实需求，它必须回答「如果系统在 T 时刻跑，看到的值是什么」。举不出来，就不要为它付代价（7.5 的 Q2 / Q3）。

与事件溯源对照着看会更清楚：事件流记录的两条轴是「事件何时发生」与「我们何时记下它」（后者在双时态事件溯源中被显式化），Anchor 记录的是「某个属性的值在哪段时间内成立」与「我们何时加载了这一行」。差别在**被记录的对象**——前者记录推导状态的事件，后者记录状态本身的版本。所以「要能重放当时为什么这么算」这类可解释性需求，靠 Anchor 的时态答不了，只能靠事件流回答；反过来，「要能回答某个时点的属性值是什么」这类问题，事件流需要把整段事件回放或投影出来才能答（主文件 §2.4.3 的对比结论）。**两条轴解决的是两个不同的问题，不能互相替代。**

表里把时态列记为 2–3 组，是因为主文件 §2.2.2 还给出了第四组可选的删除时态（`deleted_at`）。它在 6NF 下的作用与物理删除完全不同：**删除属性是给它闭段（主文件 §2.3.1 场景 4），历史行一行不删**。这条设计让「这个字段曾经存在过」本身也成为可追溯的事实——对合规场景而言，它往往比「值的历史」更关键：审计要问的不只是「当时的值是什么」，还有「当时系统里到底有没有这个字段」。代价是任何下游统计都必须显式排除已闭段的属性，否则会把已经下线的字段算进属性覆盖率一类指标里。

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本不是产品报价，而是五项随规模变化的量之和：

```
总成本 ≈ 建模与协商成本 + 存储成本 + 写入成本 + 读侧组装成本 + 元数据运维成本
      ≈ c0 + f(非空值数 × 每行时态开销) + g(一次变更涉及的属性数 × 变更频次)
           + h(属性数 N × 查询频次) + i(表数 × 消费端数)
```

Anchor 与其他候选的差别不在总量，而在**哪一项是主导项**、以及**哪一项在上线时看不见**：

| 方案 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 什么条件下反转 |
| --- | --- | --- | --- |
| 3NF | c0（改表与回刷的协商成本） | 每次改类型的停机与回填窗口 | 属性不再变化时，3NF 的成本最低 |
| 星型 + SCD 2 | f（整行版本 × 列宽） | 一次改 1 列要复制 k−1 列，写放大固定为 k | 属性频率同质时，这个放大反而不浪费 |
| Data Vault | f + h（表数与链路连接） | 查询层需要额外的物化或视图，否则每次查询都重连 | 源系统少且稳定时，可加性用不上 |
| Anchor | i + h（表数 ≈ 属性数；读侧组装） | **视图层与语义层的生成与维护**——它是唯一的读侧交付物，不做则模型会被绕过 | 属性演化不频繁时，细粒度只是额外开销 |
| 事件溯源 | f（事件无限追加） | 投影链路的重建与一致性核对 | 不需要「当前状态」快照时，事件流最省 |

四项【推算】示例，推导链全部写出，读者可按自己的规模替换参数：

- **写入量的收益**：设一次业务变更平均牵动 m 个属性，实体有 k 个属性，每个值列按 8 字节估算。宽表（SCD Type 2）产生 1 个整行版本，行宽 ≈ 8k 字节；Anchor 产生 m 个属性行，每行 = 主键 8 + 值 8 + 业务起止 16 + 加载时 8 = **40 字节**。于是写入量之比 ≈ 8k : 40m。取 k = 200：宽表每版本约 1600 字节，Anchor 在 m = 1 时写 40 字节、m = 3 时写 120 字节，即约为整行版本的 **1/40 到 1/13**；等值点在 **m = 40**（1600 ÷ 40）——**一次业务变更平均要牵动 40 个以上属性时，整行版本反而更省**。这个算式也解释了收益的前提：只有当变更分摊在少数属性上（m ≪ k）时，单属性粒度才有意义。本目录 §6 的案例记录的写入量下降方向与此一致（幅度取决于 m 的实际分布，案例原始口径见 [§ 6 的 ROI 表](04-anchor-modeling-section-6-sec6.md)）。【推算】
- **存储量的代价**：沿用上一条的参数。宽表 1 行 × 200 列 × 8 字节 = 1600 字节。Anchor 只存非空值，但每行多带 40 字节的时态与主键头：若该实体的属性非空率为 40%（每行平均 80 个属性有值），则 80 × 40 = **3200 字节**，是宽表的 2 倍；等值点在非空率 **20%**（8 ÷ 40 = 0.2，即 200 列里只有 40 列有值）。**结论与直觉相反：6NF 省存储不是因为它「更规范」，而是因为属性足够稀疏**——非空率高于 20% 时，6NF 的时态头开销超过它消掉的空值槽位。本目录 §6 记录的存储降幅出现在属性极稀疏的画像场景（数百个属性中每个用户只有少量有值），与这个等值点一致；把它外推到非空率正常的交易类实体上会反向。【推算】
- **元数据对象规模**：表数 ≈ Anchor 数 + 属性表数（Σ 每个实体的属性数）+ Tie 数 + Knot 数。沿用 [§3.4](04-anchor-modeling-section-3-sec3.md) 组合一的规模假设（10 个以上 Anchor、百级 Attribute）：取 12 个实体、每个平均 20 个属性、关系按每实体 1–1.5 条计、Knot 取 5–10 个共享字典，得到 12 + 240 +（12–18）+（5–10）= **269–280 张表**；若每个实体平均 100 个属性（主文件 §1.2 的电信 / 保险场景），则为 12 + 1200 +（12–18）+（5–10）= **1229–1240 张表**。与同一前提下的 Data Vault（12 Hub + 12–18 Link + 12–24 Sat = **36–54 张**，推导见 [Ch1 §2 维度建模 §7.4](../02-dimensional-modeling/02-dimensional-modeling-section-7-sec7.md)）相比，表数是它的 **5–8 倍**（20 属性 / 实体）到 **23–34 倍**（100 属性 / 实体）。这个倍数不是「表多所以差」，而是把 7.4 表格里 i 项的量级摆出来：对象数进入的是**每一个消费端**的成本，不是一次性成本。【推算】
- **i 项（元数据运维成本）的量级**：沿用上一条的 12 个实体、每个 20 个属性。设每个属性需要在元数据里登记口径、Owner、密级与「哪张表是当前有效」四项，每项平均 5 分钟【经验】，则一个实体一次的登记量约为 20 × 4 × 5 = **400 分钟 ≈ 6.7 人时**；12 个实体一次覆盖约 **80 人时**（12 × 6.7）。而覆盖之后，每新增一个属性、每发生一次类型演化（[§3.2.6](04-anchor-modeling-section-3-sec3.md) 会新增一张表），这份登记都要重做一次。这个量级解释了为什么 Anchor 的成本主导项是 i 而不是 f：**存储与写入随数据量增长，元数据维护随「属性数 × 变更次数 × 消费端数」增长，而后者不会因为数据量小就变小**——小数据量、高变更频率的核心实体（正是 Anchor 的目标场景）恰好把这一项推到最大。【推算】

**成本对比里不该出现的数字**：任何形如「性能提升 3.2 倍」「成本节省 63%」的结论，如果不说明数据量、列宽、非空率与一次变更牵动几个属性，就没有可迁移性——上面四条推算把参数全部写了出来，就是为了让读者用自己的参数替换后重算。厂商与社区材料里的性能数字，在做选型依据前先问三个条件：多大表、什么查询、变更分布如何；三问缺一，就当方向记录而不当证据【经验】。

一个共同结论：**这些方案的成本函数形式相同，差别只在主导项**。因此选型的第一问不是「哪个便宜」，而是「我的数据里，哪一项会先变大」——对 Anchor 而言，先变大的是 i（元数据对象数），不是 f（存储）也不是 g（写入）。

还有一项常在对比中被默认为零的成本：c0，建模与协商成本。它不随数据量增长，只随「要说服多少人接受一套反直觉的结构」增长。Anchor 的 c0 在几条路线里偏高：团队要先接受「一个属性一张表」，再接受「下游只读视图、不直连底表」这条纪律，还要为 Knot 字典指定一个中央治理方（[§3.4](04-anchor-modeling-section-3-sec3.md) 末段把「职责边界有没有写下来」列为组合的失败前提）。同一个方案，在 20 人的团队里可能只需一次设计评审，在 200 人、跨 5 个业务线的组织里就是一场跨季度的协商——**这不是软性因素，它就是 c0 这一项的真实量级差异，也是同一套结构在不同组织里成败相反的原因。**

### 7.5 决策树（每个分支都要有阈值依据）

读这棵树的方式是**自上而下、且 Q1–Q4 是不可跳过的前置链**：Q1 决定「要不要细粒度这件事」，Q2 到 Q4 逐层收紧「细到什么程度、由谁交付」。Q1–Q3 答「否」都不是失败，而是把方案让给了同族的更轻量选项；只有 Q4 答「否」时，问题不在方案而在能力，此时换任何方案都不会改善结果。Q5–Q7 是落地时的三个独立开关，它们不改变前面的结论，只决定三个具体模式的取舍。

```
开始：为「属性高频变化 + 强时态要求」的核心实体选结构
├─ Q1 这个实体的属性之间，变化频率是否高度分化？
│    ├─ 否（同频或整体稳定）→ 星型 + SCD，或 Data Vault（见 7.6 的矩阵）
│    └─ 是 → Q2
├─ Q2 是否必须区分「业务何时发生」与「系统何时知道」？
│    ├─ 否 → Data Vault（卫星级时态足够）
│    └─ 是 → Q3
├─ Q3 这个区分是否需要细到单个属性？
│    ├─ 否 → Data Vault 2.0（粒度为属性组，表数与运维都低一档）
│    └─ 是 → Q4
├─ Q4 团队能否交付「视图层 / 语义层」，而不只交付表？
│    ├─ 否 → 不要选 Anchor Modeling；退回 Data Vault 或星型
│    └─ 是 → Anchor Modeling（四件套）→ 进入 Q5
├─ Q5 属性类型是否会变更，且不允许停机 ALTER？
│    ├─ 是 → 类型演化模式（新 v2 表 + 旧表闭段）
│    └─ 否 → 常规 Attribute 表
├─ Q6 多值集合（号码 / 邮箱 / 设备）是否会在主体之间流转？
│    ├─ 会流转 → 独立 Anchor + Tie
│    └─ 不流转 → 时态分组，或序列化进一个属性值
└─ Q7 时间轴上是否存在「不该出现的日期」（交易日 / 账期 / 营业日）？
     ├─ 有 → 时间 Anchor（时间可挂属性）
     └─ 无 → 事实侧直接携带时间戳
```

**阈值依据**（与树上节点一一对应）：

- **Q1「高度分化」**：依据是 7.4 的写入算式 8k : 40m。拆分的收益只在 m ≪ k 时出现，而 m 正是「一次变更牵动几个属性」——若组内所有属性同频，则每次变更牵动它们全部，m ≈ k，收益归零而对象数与 JOIN 照付（[§3.2.3](04-anchor-modeling-section-3-sec3.md) 的失效点）。判定方法是抽 20 次最近的结构变更，数每次改动涉及的属性数 m：**若 m 的中位数不超过该实体属性数的五分之一，即按「高度分化」处理**（该比例取自 7.4 算式在 k = 200 时的等值点 m = 40，读者可按自己的 k 重算）【推算】。主文件 §2.4.1 与 §2.4.4 给出的界线是「每周 10 个字段变化」（该界线本身属【经验】档）——它是这条判据的粗略近似，两者不冲突：**起作用的是变化的分布，不是变化的总次数**，一个每周变 10 个字段但集中在两个属性上的实体，比一个每两周变 3 个字段却每次都牵动全表 60% 列的实体更适合 Anchor。
- **Q2**：依据是 7.3.4 的因果链——第二条时间轴记录的是「系统的认知状态」，它的唯一用途是回答「如果当时跑一遍会看到什么」。这只是否真实存在，只有业务与合规能答；答「否」时不选 Anchor，因为多记的一条轴只会变成每个查询的书写负担。
- **Q3**：依据是 7.3.1 与 7.3.4 的联动——时态粒度是版本粒度的推论。要求「属性级时态」就等于要求「属性级版本」，于是表数进入 7.4 的 i 项。这里的分界不是量，而是**一个可验证的问题**：「有没有一个需求，它要问的是『同一个实体的 A 属性在 T1 的值』与『B 属性在 T2 的值』，且 T1 ≠ T2？」有，才是属性级；没有，属性组级就够。
- **Q4**：依据是 7.3.2 的失效点与 [§3.5](04-anchor-modeling-section-3-sec3.md) 的第三条反模式（忽略反规范化视图层）——模型即使正确，只要组装成本落到消费方身上，消费方就会自建宽表副本。**这是本树上唯一一个「前置条件」节点而不是取值节点**：它问的不是规模，而是「你有没有能力交付读侧」。答「否」时选 Anchor 是一条注定被绕过的路。
- **Q5**：依据是 [§3.2.6](04-anchor-modeling-section-3-sec3.md) 的失效点与主文件 §1.2 案例 3 的机制——原地改类型的成本与「表有多大」挂钩，而本模式下「表」只含一个属性，所以演化成本的上界被限制在「下游读哪张表」这一侧。这一条与规模无关，只在类型会变时触发。
- **Q6**：依据是 [§3.2.2](04-anchor-modeling-section-3-sec3.md) 与 [§3.2.3](04-anchor-modeling-section-3-sec3.md) 的对比结论——「会流转」意味着归属关系本身需要历史，而序列化进一个属性值只能表达「当时的集合」，无法表达归属变更。判据是**实例会不会在主体之间转移**，不是实例有几个。
- **Q7**：依据是 [§3.2.5](04-anchor-modeling-section-3-sec3.md) 的失效点——时间 Anchor 的粒度固化在 ID 空间里，粒度一旦需要变细，重建的是整个时间域及其全部引用方。所以这条只在「时间点本身带业务规则」（交易日、账期）时才该走「是」分支。

需要强调的是：这七个节点里只有 Q1 用了需要估数的阈值，其余六个都是**可判定的结构性问题**（要不要第二条时态轴、时态要不要到属性级、能不能交付读侧、类型会不会变、实例会不会流转、时间轴上有没有不该出现的日期），答案由约束决定，不需要估数。把可判定的问题写成阈值，是决策树最常见的画蛇添足。

最后核对一遍闭合关系：树上七个判断节点与上面七条依据一一对应，既没有无依据的节点，也没有无处安放的依据——**这是这棵树能直接当评审材料用的前提**。评审会上真正会卡住的通常不是「阈值取多少」，而是「这一问由谁答」：Q1、Q5、Q6 由建模方与技术方答，Q2、Q3 由业务与合规方答（它们是需求判断而非技术判断），Q4 由团队能力答，Q7 由业务日历答。答案的归属没写清，任何阈值都会被现场改成对自己有利的数。

### 7.6 选型矩阵与组合

矩阵按「场景」而不是「方案」组织——选型的输入是你的处境，不是候选清单。每一行的「不选它的原因」都写成机制层面的理由，而不是「性能差」这类形容词；与 [§3.3](04-anchor-modeling-section-3-sec3.md) 的模式选择表配合使用（那一张选模式，这一张选结构）。

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 核心实体属性数十以上、频率高度分化、要逐属性历史 | Anchor + 视图层 | Data Vault | 不选 DV：版本粒度只到属性组，组内一个属性变化会带出整组新版本，写放大由组内最快的属性决定 |
| 属性频繁新增但频率同质（整组一起变） | Data Vault 2.0 | Anchor + 时态分组 | 不选 Anchor：拆分收益归零（m ≈ k），对象数与 JOIN 照付 |
| 监管要求「何时知道」、但不需要到属性级 | Data Vault 2.0 | Anchor（仅在属性演化成主要矛盾时） | 不选 Anchor：7.4 的 i 项（表数 × 消费端数）在时态粒度不必要时会白付 |
| 字段稳定、时态要求弱 | 星型 + SCD 或 3NF | 宽表 | 不选 Anchor：加属性零成本这条收益在你的场景里根本不会发生 |
| 查询以宽表聚合为主、延迟敏感 | Anchor 底表 + 物化切片 | 纯宽表 | 不选纯 Anchor 直查：读侧组装成本随属性数线性上涨，且没有物化来吸收 |
| 需要跨系统语义对齐或多跳推理 | 本体建模 + 由 Anchor 同步出的事实 | 直接在表上加标注 | 不选「把本体当物理结构」：本体解决的是概念对齐，不解决属性级演化与写入量 |
| 业务需要「当时为什么这么算」的可重放 | 事件溯源（或 Anchor 的 Tie 记录互动） | 双时态存储 | 不选纯时态存储：它记录的是状态的历史，不是推导状态的事件序列 |
| 消费方包含 Agent / 检索层 | Anchor（四件套 + Knot）+ 语义层 | 宽表 + 人工元数据 | 不选宽表：属性的口径与来源散在列名与文档里，机器读不到稳定结构 |

四条**常见组合**。前三条对应 [§3.4](04-anchor-modeling-section-3-sec3.md) 在模式层的组合，这里补上结构层的表述与各自的运维代价：

1. **Anchor（高变化核心域）+ Data Vault（其余域）**：职责边界是「谁变化更快谁用更细的粒度」，两者共享同一份 Anchor / Hub 的实体标识口径。运维代价：**两套加载与建模纪律并存**，团队要同时掌握卫星表的属性组切分与属性表的单属性切分；更要紧的是必须有**场景边界文档**写清哪些域用哪一种，否则会退化成 [§3.5](04-anchor-modeling-section-3-sec3.md) 的「银弹反模式」——全仓统一 6NF，让字段稳定的报表域白付 JOIN 与元数据成本。
2. **Anchor 底表 + 反规范化视图层 + 物化热点切片**（[§3.4](04-anchor-modeling-section-3-sec3.md) 组合三）：底表承担演化，视图层承担 JOIN 封装，物化承担高频切片的预计算。职责边界是「谁能直连底表」。运维代价：物化视图的刷新链路成为新的故障面（刷新窗口、陈旧度、与底表的对账），且视图定义随属性增长不断被重写——把它做成**从模型定义自动生成**的产物（工具链见 [§4.3](04-anchor-modeling-section-4-sec4.md)），是从「能维护」到「可持续维护」的分界。
3. **Anchor 底表 + 语义层 / OneData 式指标层**（[§ 6 的阿里案例](04-anchor-modeling-section-6-sec6.md) 的做法）：Anchor 承担属性级时序与审计，语义层承担「业务方只看宽表」的接口。职责边界是「语义层不新增口径，只把已有口径声明成机器可读的形式」。运维代价：语义层成为取数链路的单点，其变更同时影响所有消费端——集中化的收益与爆炸半径来自同一个机制。
4. **Anchor 底表 + 同步为 RDF 进入知识图谱**（主文件 §2.4.2 的结论：Anchor ≈ 工程版的三元组）：Anchor → Subject、Attribute → Predicate-Object、Tie → Predicate、Knot → Reified Object。职责边界是**单一权威在关系侧，图侧只是派生**，因此图谱可以整段重建、也可以停用。运维代价：第二份必须与底表同步的状态（增量同步链路、删除语义的对齐——关系侧的闭段在图上通常表现为边的失效标记），以及图侧不能反过来成为口径来源这条纪律。

四条组合共同的运维代价结构是：**每加一层，就多一份需要与上游保持同步的派生状态**（视图、物化、语义声明、三元组），而每一份都需要新鲜度监控与 Owner。据此有一条可执行的次序原则：**先把 Anchor 底表 + 视图层做扎实，再按实际出现的消费需求逐层追加**；一次配齐四层的团队，通常得到的是四份各自漂移的派生状态。

矩阵的读法同 7.1 的结论：**按层选，不按候选清单选**。每一行的「首选」通常只是该场景下**集成层**的答案，而该场景在查询结构与消费接口两层上的答案可能来自另外两族——例如 7.6 矩阵第 5 行的首选「Anchor 底表 + 物化切片」已经同时写了集成层与查询结构层，7.8 小结表第 4 行的「Anchor + 物化切片 + 语义层」则把三层都占了。把「Anchor」当成一个能一次回答所有问题的整体方案，正是 7.7 四条反模式的共同起点。

若一个仓里同时存在高变化的核心域与稳定的报表域，切分的具体判据是：**把每个域的实体清单按 7.5 的 Q1 过一遍，答「是」的域进 Anchor，答「否」的域留在星型或 Data Vault**；不要按「数据量」或「业务重要性」切，因为这两者与版本粒度机制无关——一个数据量很小但属性每周都在变的核心实体，比一个百亿行但结构十年不动的交易表更需要 6NF。切完之后，跨域连接只允许发生在视图层，不允许两个域直连对方的底表；这是那份「场景边界文档」在技术上唯一需要写死的一条。

组合 2 与组合 3 的分界也值得单独说明，因为二者常被混为一谈：**视图层解决物理组装**（把 N 张表拼成一个可查对象），**语义层解决口径声明**（这个对象上的度量与维度叫什么、怎么算）。只建视图层而不建语义层的仓，消费方仍要为「同一个指标两种算法」买单；只建语义层而不建视图层的仓，语义层要自己承担全部 JOIN 逻辑，反而把组装成本锁进了声明文件。两者的先后是明确的：**先视图层，再语义层**——后者是前者的消费者。

### 7.7 选错的代价与迁移成本

**反模式：把 6NF 当默认结构，全仓统一** —— 症状：连字段稳定的报表域与即席分析域也拆成「一个属性一张表」。后果：稳定域付出了 JOIN 与元数据成本，却换不到任何演化收益（[§3.5](04-anchor-modeling-section-3-sec3.md) 的「银弹反模式」）；成本落在没参与建模的人身上，团队随后自行从底表抽宽表副本，模型仍在维护却不再被消费。正确的做法：先用 7.5 的 Q1 把域筛一遍——**只有属性频率高度分化的核心实体才用 6NF**，其余域用 Data Vault 或星型，三者共存在同一仓里是常态。

**反模式：只交付表，不交付视图层 / 语义层** —— 症状：建模阶段的验收标准是「新增属性零成本、写入量下降」，没有任何一项关于读侧。后果：滞后爆雷——问题要等第一个「拉全貌」的消费方出现才暴露，而那时底表已有可观数据量，建视图层不再是加一层 SQL，而是一次性能工程（[§3.5](04-anchor-modeling-section-3-sec3.md)）。正确的做法：把「视图层是否覆盖高频切片」写进验收标准，并在交付前抽查一个下游查询，确认它没有直连 5 张以上底表（[§3.7](04-anchor-modeling-section-3-sec3.md) 第 4 条自检项）。

**反模式：为「AI 友好」直接选结构** —— 症状：因为「每个属性一张表便于 Agent 做字段级发现」就上 Anchor，却没有元数据目录与语义层。后果：Agent 面对的是数千张互不相识的属性表——**结构细不等于语义可读**，缺了 Knot 字典与元数据口径，机器与人都无法判断哪张表是「当前有效」、某个属性属于哪个实体。正确的做法：把 AI 需求拆成两件可判定的事——「机器能不能找到」（元数据目录 + Knot 字典 + 语义层）与「机器能不能算对」（口径、粒度、密度的机器可读），前者才是要先建的（[§5](04-anchor-modeling-section-5-ai.md)）。

**反模式：先选工具，再让工具决定结构** —— 症状：因为团队已经熟悉某个生成器或某个平台，就按它当前能生成什么来反推结构，跳过 7.3 的机制判据。后果：结构由工具的能力边界决定，而不是由你的数据形态决定；一旦工具不生成视图层与语义层（本主题工具链的常见短板，见 [§4.3](04-anchor-modeling-section-4-sec4.md)），7.3.2 的读侧成本就无人承接。正确的做法：先用 7.5 定结构，再回头核验工具能否把「DDL + 视图 + 语义声明」一并生成出来——**对 Anchor 而言，工具能否生成读侧交付物，比它能生成多少张表更关键**。

**换成另一个要动什么**：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 星型 / 3NF → Anchor | 大（按属性级重切并回填时态） | 大（查询层视图重建） | 中（新增生成器与视图层） | 大（6NF 建模能力与视图层纪律） |
| Data Vault → Anchor | 中（Hub → Anchor 可对应，Sat 需按属性拆开） | 大（PIT / Bridge 失效，改走视图层） | 中 | 中（同为集成结构族，概念可迁移） |
| Anchor → Data Vault | 中（属性表需按频率重新归组） | 中（视图层改为 PIT / Bridge） | 小 | 中 |
| Anchor 内部加一层物化 / 语义层 | 无（不改底表） | 小（消费端改指向） | 中（刷新链路或语义层成为新单点） | 中 |
| Anchor → 事件溯源 | 大（状态要重述为事件，历史边界需重新定义） | 大（查询改为回放或投影） | 大（新增投影链路） | 大（建模语言不同） |

这张表里最容易被低估的一格是「星型 / 3NF → Anchor」的**团队再学习**：迁移的技术难点不在数据搬运，而在**读侧的纪律**——原来一条 JOIN 就能拿到的上下文，从此必须由视图层提供，而任何一个人绕过视图层直连底表，读侧成本就会立刻显性化并催生「还不如用宽表」的结论。这也解释了为什么本主题的失败很少表现为技术故障，而更多表现为**绕过**。

迁移的通用原则只有一条：**先让新旧两套结构并行跑一段，把两边的口径对账通过之后再切换消费端**。建模方案的迁移不存在「一次性大爆炸」的成功形态，因为建模的产物是口径，而口径是否一致只能靠两套结果对账来确认，不能靠单元测试证明。这条原则也解释了上表里「查询改写」一栏为什么普遍偏大——迁移的成本主体不是数据搬运，而是**两套结构同时存在期间的对账与消费端切换**。

反过来也要说清**什么时候不必迁移**：当痛点是查询慢、而属性变化与历史追溯都不是问题时，正确动作是给现有结构加物化切片或语义层（7.8 小结表第 4 行），而不是换建模方法；当痛点是下游口径不一致时，正确动作是加语义层。只有当痛点是「属性在持续新增、而每一次新增都要动既有表」时，换集成结构才是对症的（7.5 的 Q1–Q4）。**换结构是最后手段而不是第一手段**——它的成本主体是口径对账，而这件事在「加一层」的路径上同样要做，只是范围小得多。

四条反模式还有一个共同的形状值得单独记住：**它们都不是技术判断错误，而是「把某个机制的收益当成了普遍收益」**。把 6NF 当默认结构，是把「属性高频变化时的写入收益」当成普遍收益；只交付表不交付读侧，是把「建模阶段的验收标准」当成全部交付物；为 AI 友好选结构，是把「结构细」当成「语义可读」；先选工具，是把「工具能做什么」当成了「我的数据需要什么」。识别它们的方法只有一个：**把收益前面那个条件句补回去，看它成不成立。**

### 7.8 小结

下表把 7.5 的决策树压成六行，每行只保留「处境 → 建议 → 机制理由」三要素。**读法**：先找到与你最接近的那一行，再回看它对应的 7.3 小节确认理由是否对你的场景成立——若理由不成立，就换行。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 属性数十以上、频率高度分化、要逐属性历史 | Anchor（四件套）+ 视图层 | 版本粒度落在单个属性上，一次变更只写它真正改动的那一行（7.3.1） |
| 要区分「何时发生」与「何时知道」，但不必到属性级 | Data Vault 2.0 | 两条时间轴已在卫星表上，粒度粗一档，7.4 推算的表数低一档（同前提 36–54 张对 269–280 张） |
| 属性频繁新增但整组一起变 | Data Vault 或星型 + 时态分组 | 拆分收益随 m 接近 k 而消失，对象数与 JOIN 却照付（7.4 算式） |
| 读侧消费方多、查询形态可枚举 | Anchor + 物化切片 + 语义层 | 组装成本必须有承载方，否则消费方会自建宽表副本（7.3.2） |
| 监管要求「某时点的系统视图」可按属性追溯 | Anchor（三时态） | 加载时态是独立于业务时态的一条轴，且粒度与版本粒度绑定（7.3.4） |
| 字段稳定、时态要求弱 | 星型 + SCD 或 3NF | 加属性零成本这条收益不会在你的场景里发生 |

还有一种处境值得单列：**手上已经有一套跑了多年的宽表或星型，想换过来**。此时第一步不是比较方案优劣，而是把现状的痛点归到 7.3 的哪一个机制上——若是「加一个属性要回刷全表」，问题在 7.3.3；若是「监管问当时的属性值答不出」，问题在 7.3.4；若是「写入量被那几个变化最快的属性拖高」，问题在 7.3.1。**痛点归错了类，迁移只会把成本从一个账户挪到另一个账户**：为查询慢而上 Anchor，得到的只会是更慢——它的收益在写侧与演化侧，不在读侧。

> 本节小结：这一组候选里**唯一真正起决定作用的差异**是「版本的附着单位」——整行（星型 + SCD）、属性组（Data Vault 的卫星表）、单个属性（Anchor 的 Attribute 表），还是一条事件（事件溯源）。它同时决定了写入量、读侧的 JOIN 数、时态的粒度与变更的传导半径；其余维度（生态、工具、AI 友好度）都是这条差异的下游表现，因此不该被当成独立判据。**Anchor 的收益与代价都主要来自这一条选择，而不是来自「它更规范」。**
