## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表最容易给出一种错觉：把场景列清楚，设计就变成了「按场景挑一个」。但本节的六个模式不是六个并列的选项，它们是**同一组硬约束在不同取值下的产物**。主文件 §2.1 把这组约束写死了：Anchor 只含 ID，Attribute 只含 1 个属性，Tie 只含关系 ID，Knot 只含共享查找。四条里任何一条松动，下面的模式都会换形。

其中最关键的一条是「Attribute 只含 1 个属性」。它把**加一个业务字段**从「改一张宽表」变成「新建一张表」，这就是 6NF（不含非平凡连接依赖）在工程上的全部含义。模式之间的差别，本质上只是回答三个问题：**属性怎么切、时态记在哪一层、共享值抽不抽出去**。

所以正确的顺序是先立约束、再谈模式。约束不同，同一个业务场景的正确解就不同：同样是「客户有多手机号」，写多、读少、要求逐条历史，答案是独立 Anchor + Tie；写少、读多、只要当前值，答案反而是把号码序列化进一个 Attribute 值里。两者都叫「多值」，代价相差一个数量级。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式 | 属性是「新增一张表」还是「往表里加一列」；一次业务变更要写几行 | 「加字段就是加列」——6NF 下加字段是建表，DDL 成本从改表变成建表 |
| 访问模式（点查属性 / 拉实体全貌 / 全表扫描） | 模式选得对不对，取决于读的是「一个属性」还是「一个实体」 | 「规范化一定更省」——点查单属性时 6NF 最省，拉全貌要 join N 张表 |
| 变更频率与历史要求 | 属性是否各自独立时态；一组属性该不该共享同一条时间线 | 「属性放一起查询方便」——放一起就共享变更节奏，低频属性被高频属性拖着写 |
| 一致性要求（当前值 / 任意时点值 / 何时知道） | 时态列放两组还是三组 | 「记了生效时间就够了」——晚到的变更需要第三个时间轴承载 |
| 规模与成本约束 | Knot 抽不抽、反规范化视图物不物化 | 「Knot 越共享越好」——共享在缩小存储的同时也放大了变更半径 |
| 团队技能与运维能力 | 是否必须强制走视图层 / 语义层 | 「模型好谁都能看懂」——6NF 的结构反直觉，没有视图层就会被打回宽表 |

前五行是**技术约束**，最后一行是**组织约束**，但它对模式选择的杀伤力最大。6NF 是一个需要整个团队共同遵守约定的结构：任何一个人绕过视图层直连底表，读侧的成本就会立刻显性化，并迅速催生「还不如用宽表」的结论。所以本节把每个模式的「代价」写得比「优点 / 缺点」短语更重，不是为了让读者放弃它，而是为了让代价被**事先分配**——谁来建视图层、谁来维护 Knot 字典、谁在字典变更时负责通知引用方，这些在选型阶段就应该有答案。

### 3.2 模式逐个拆解（核心节）

下面六个模式中，3.2.2 与 3.2.3 的结构骨架相同（都是「独立 Anchor + 一条带时态的 Tie 挂回主体」），差别只在被建模的关系是**多值**还是**整体**。因此这一节沿用主文件 §2.1 的四件套术语（Anchor / Attribute / Tie / Knot），并在结构块里固定用同一套符号：`──<` 表示一条 Tie，缩进表示 Attribute 挂在哪个 Anchor 上。判断当前场景属于哪一个，只需要回答「这些值会在主体之间流转吗」。

#### 3.2.1 标准四件套模式（Standard Anchor-Attribute-Tie-Knot）

**被什么约束逼出来**：实体的属性在**变化频率与类型上都不同质**（手机号几年一改、余额秒级变、地址改了还要留旧值），而宽表只能按最快的那条频率设计。

**结构**：

```sql
-- Anchor：只有 ID 与元数据，不含任何业务属性
CREATE TABLE customer (
  customer_id BIGINT PRIMARY KEY,
  first_seen  TIMESTAMP NOT NULL
);
-- Attribute：一个属性一张表，自带三时态
CREATE TABLE customer_name (
  customer_id BIGINT, name VARCHAR(200),
  valid_from TIMESTAMP, valid_to TIMESTAMP, loaded_at TIMESTAMP,
  PRIMARY KEY (customer_id, valid_from, loaded_at)
);
-- Tie：关系本身也是一张带时态的表
CREATE TABLE customer_order (
  customer_id BIGINT, order_id BIGINT,
  valid_from TIMESTAMP, valid_to TIMESTAMP, loaded_at TIMESTAMP
);
-- Knot：被多处引用的共享查找
CREATE TABLE knot_currency (id BIGINT PRIMARY KEY, code VARCHAR(3), name VARCHAR(64));
```

**为什么这样设计有效**：因为每个属性独占一张表、独享自己的时间线，所以**一次业务变更只写它真正改动的那一个属性**——其余属性不需要因为「它们在同一张行里」而被重写一遍。这正是它能在属性变化频率相差几个数量级的实体上省下写入量的机制。

**代价**：读侧的成本是必然的，不是「略微复杂」：拉一个实体的全貌，需要**与属性数成正比的索引访问次数**（N 个属性即 N 次索引查找加 N 次 JOIN）。元数据对象的数量也从「1 实体 1 表」变成「1 实体 N 表」，这个冗长的对象清单必须由独立的目录 / 语义层来承载，否则团队无从知道某个实体到底有哪些属性。按【经验】区间，核心实体（客户、保单、账户）的属性数通常在数十到数百之间，对应的 JOIN 数也在同一量级——这个量级在明细层可接受，在即席查询与 BI 直连下不可接受。

**失效点**：当「实体属性数」增长到视图层与查询引擎无法把 JOIN 吸收掉时，**「加属性零成本」会反转成「读一次全貌的成本随属性数线性上涨」**，因为 6NF 把一次行读取拆成了 M 次独立的索引查找，只有当 M 小、或该组合可被物化时，视图才能把这笔成本藏起来。

**真实使用**：落地集中在「属性多、且属性间变化频率差异大」的场景——保险与电信的核心实体、互联网的用户画像宽表替代方案【经验】。本章 [§ 6 落地实践](04-anchor-modeling-section-6-sec6.md) 收录了 4 个以本模式为核心的案例，可直接对照其组件拆分方式。

#### 3.2.2 多值属性模式（Multi-Valued Attribute via Knot / 独立 Anchor）

**被什么约束逼出来**：同一实体对同一属性有**多个取值**（多个手机号、多个邮箱、多台设备），而每个取值各自有自己的生命周期。

**结构**：

```text
把「多值」变成「一条 Tie + 被指向的 Anchor」

  customer ──< customer_phone_relation >── phone
     (Anchor)         (Tie, 带时态)          (Anchor)
                                               │
                                     phone_number (Attribute)
                                     phone_type   (Attribute → Knot)

→ 关键：多值不是「同表多行」，而是「一条关系边」
  每个号码是一个独立 Anchor，可被多个 customer 通过 Tie 共享
```

**为什么这样设计有效**：因为「谁拥有这个号码」被建模成一条带时态的边而不是一个字段，所以**归属关系的变更（号码过户、号码解绑）被记录为边的新版本，而不是覆盖列值**——同一号码在第 3 个客户名下的那段时期可以被单独查出来。

**代价**：查询路径从「一次 JOIN」变成「至少三段跳」（主 Anchor → Tie → 被指 Anchor → Attribute），且 Tie 表本身随**关系变更次数**增长，成为一个高基数关联表；这是在「关系可变」场景下必然付的代价。

**失效点**：当多值集合的基数很高时（一个账号关联上千台设备），**「原生支持任意多值」会反转成「Tie 变成全库最大的表」**，因为每条多值关系都必须独立成行并各自携带时态与索引，行数正比于「实体数 × 平均基数」，而点查一个实体的全部取值需要扫描该实体的整段 Tie。

**真实使用**：号码 / 邮箱 / 设备这类「一个主体对多实例」的关系是它的主战场【经验】。注意这个列表里**没有「地址」**——地址的省 / 市 / 区 / 邮编是一次搬迁中成套变化的**整体**，基数恒为一、变的只是版本，属 3.2.3 而非本节；把地址按多值属性建，正是 3.3 末段那对误选模式的典型后果。判断场景是否属于它，看一个问题即可：这些取值**会不会在主体之间流转**——会流转就必须独立成 Anchor，不会流转则序列化进一个属性值更省。

#### 3.2.3 时态分组模式（Temporal Grouping）

**被什么约束逼出来**：一组属性**业务上总是一起变化**（地址的省 / 市 / 区 / 邮编在一次搬迁中同时改变），拆开写会产生大量「同一时刻的并发变更」。

**结构**：

```text
把「同变属性组」提升为一个独立 Anchor，用一条 Tie 挂回主体

  customer ──< customer_address >── address
   (Anchor)        (Tie, 带时态)      (Anchor)
                                        ├─ address_province (Attribute → Knot)
                                        ├─ address_city     (Attribute → Knot)
                                        └─ address_detail   (Attribute)

  地址整体变更 = 一条新 Tie + 一组新 Attribute 行（同一 valid_from）
```

**为什么这样设计有效**：因为整组属性共享同一条时间线，所以一次搬迁在原子里只产生**一个时间点**，而不需要在一堆互不相干的属性表里各自判断「这次变更到底改了哪几个字段」——下游按时间点切片时不必处理「半新半旧」的中间态。

**代价**：共享时态是一把双刃剑，它的代价与收益来自同一个机制——组内任何一个属性变化，都必须以「整组新版本」的形式表达。这会产生**伪变更**（没变的属性也被写了一遍新行），存储与写入量按组内**变化最频繁的那个属性**计算，而不是按平均值。

**失效点**：当组内属性的变化频率**逐渐分化**时（例如地址的「邮编」每月变、「省」三年不变），**「减少变更」会反转成「把低频属性拖到高频节奏上」**，因为共享时态意味着组内所有属性都被绑定到同一条时间线的更新频率，分化越严重，伪变更的比例越高。

**真实使用**：地址、证件信息、套餐要素、银行卡信息这类「业务上成套变化」的属性组【经验】。这些组的共同点是**基数恒为一**——同一个住址、同一张证件在时间上被改写，而不是「他有了第二个住址」；对照 3.2.2，号码 / 邮箱 / 设备才是基数会自然增长的多值实例。判断一组属性该不该归组的判据不是「查询时是否一起用」，而是「**业务事件上是否一起变**」——按查询共现来分组，会在变更侧付出伪变更的代价。

#### 3.2.4 Knot 共享模式（Knot Sharing）

**被什么约束逼出来**：同一批**枚举取值**被多个实体、多张属性表引用（国家码、币种、状态码），而这些取值的**显示名与含义会变更**。

**结构**：

```sql
CREATE TABLE knot_currency (id BIGINT PRIMARY KEY, code VARCHAR(3), name VARCHAR(64));
-- 多张 Attribute 表引用同一个 Knot，而不是各自存字符串
CREATE TABLE customer_preferred_currency (
  customer_id BIGINT, currency_knot_id BIGINT,
  valid_from TIMESTAMP, valid_to TIMESTAMP, loaded_at TIMESTAMP,
  FOREIGN KEY (currency_knot_id) REFERENCES knot_currency(id)
);
CREATE TABLE order_currency (
  order_id BIGINT, currency_knot_id BIGINT,
  valid_from TIMESTAMP, valid_to TIMESTAMP, loaded_at TIMESTAMP,
  FOREIGN KEY (currency_knot_id) REFERENCES knot_currency(id)
);
```

**为什么这样设计有效**：因为取值被收敛到一个 ID 空间里，所以「改一次币种名称」是一次单行更新，而不再是「在所有引用它的表里做一遍字符串替换」——同时代码值与显示名的分离让**同一份语义只有一个物理副本**，不会出现 A 表写 CNY、B 表写「人民币」。

**代价**：每个取值多一次 JOIN（或必须把 Knot 常驻缓存）；更实质的代价是 **Knot 变成跨域强依赖**——所有引用方共享同一个 ID 与语义，字典的任何变更没有版本边界，会同时落在所有消费者身上。

**失效点**：当 Knot 被跨团队、跨业务域广泛引用时，**「一处修改，处处生效」会反转成「一处修改，处处爆炸」**，因为引用方共享的是同一个语义对象而不是各自的一份拷贝，字典里的取值一旦被重新解释（不只是改名，而是口径变化），所有引用方的历史数据会被**追溯性地改变含义**。

**真实使用**：国家 / 地区、币种、状态码、渠道编码这类跨实体复用的字典【经验】。判断是否该抽 Knot，看两条：**是否被 ≥2 个 Anchor / Tie 引用**，以及**取值集合是否稳定且由中央治理**——独占的、只在一个实体里出现的枚举，直接放在 Attribute 值里更省一次 JOIN。

#### 3.2.5 时间锚点模式（Time Anchor）

**被什么约束逼出来**：事实发生在**有业务语义的时间点**上，而且时间轴本身不连续（交易日 / 营业日 / 账期与自然日不一致）。

**结构**：

```text
把时间本身建成 Anchor（而不是把日期塞进事实表的列里）

  trading_day (Anchor) ── trading_day_calendar (Attribute: 是否交易日 / 所属账期)

  stock (Anchor) ──< stock_price (Tie) >── trading_day (Anchor)
                          │
                    价格 (Attribute)

  → 关键：时间是一等实体，可以挂属性（账期、是否交易日、所属年度）
    自然日里没有交易的日期在事实侧根本不产生行
```

**为什么这样设计有效**：因为时间成了 Anchor，它就能**携带自己的属性**（所属账期、是否交易日、财年季度），所以「按账期汇总」这类计算不需要在查询里写日期函数，而是一次 JOIN 到时间 Anchor——时间维度的业务规则被集中在一张表里维护。

**代价**：需要一条独立的「时间 Anchor 生成与日历维护」流程；每条事实都要携带一个 day_anchor_id，事实表**多一列加一次 JOIN**；而且 Anchor 的 ID 一旦发出，**粒度就固化在 ID 空间里**。

**失效点**：当业务需要把时间粒度**变细**时（从日到小时到秒），**「时间维度规范化」会反转成「最昂贵的一次重建」**，因为粒度写死在 Anchor 的 ID 空间里，改粒度意味着重建整个时间 Anchor 域以及所有引用它的 Attribute 与 Tie——引用面越广，这次重建越接近全库重刷。

**真实使用**：行情 / 交易 / 计费 / 账期这类「时间点带业务语义」的场景【经验】。判断用不用它，看一个问题：**你的时间轴上是否有「不该出现的日期」**——有（交易日、账期、营业日）就该建时间 Anchor；纯自然日、只用于分区的场景，直接放日期列更省。

#### 3.2.6 类型演化模式（Type Evolution）

**被什么约束逼出来**：属性的**数据类型本身需要变**（金额从定点数改成整数分、年龄从数值改成可含「未知」的文本），而原地改类型要锁表、要回刷历史。

**结构**：

```sql
-- 1) 新建 v2 表承载新类型；旧表保持可读
CREATE TABLE customer_age_v2 (
  customer_id BIGINT, value VARCHAR(20),
  valid_from TIMESTAMP, valid_to TIMESTAMP, loaded_at TIMESTAMP
);
-- 2) 旧表把「当前有效」这一段闭合，作为历史归档
UPDATE customer_age SET valid_to = CURRENT_TIMESTAMP WHERE valid_to IS NULL;
-- 3) 迁移后，下游被指向「哪张表是当前有效的」——这份知识必须显式存在
```

**为什么这样设计有效**：因为新旧类型各占一张表，所以**旧数据不需要被转换就能继续读**，「改类型」这件事的破坏半径被限制在「谁来读」这一侧，而不是「数据本身」——原表不锁、历史不丢、回滚只需把下游指回旧表。

**代价**：同一语义在物理上分裂成多张表加一条失效边界；**「哪张是当前有效的」这份知识必须被显式维护**——放在视图层或元数据里，否则每个下游各自判断，很快就会有人读错表；查询复杂度按演化次数线性增长。

**失效点**：当同一属性被演化了三次以上时，**「零中断演化」会反转成「查询侧的时间缝合」**，因为每张表只覆盖一段互不重叠的时间区间，要回答「任意时点的值」就必须 UNION 多张表再按时间取最新——这段缝合逻辑没有地方可以被一次性封装，只能出现在每一个消费者里。

**真实使用**：核心系统改造期的字段升级（余额精度、证件类型、状态枚举扩容）【经验】。这条模式是「加新表 + 旧表闭段」的通用手法，在 Anchor Modeling 之外同样成立。

六个模式放在一起看，只有两条主轴：**横向切属性**（3.2.1 标准四件套、3.2.3 时态分组、3.2.6 类型演化管的都是「属性怎么分表」），**纵向切关系**（3.2.2 多值属性、3.2.4 Knot 共享、3.2.5 时间锚点管的都是「什么东西值得独立成 Anchor」）。同一个业务域里，两条主轴的决策互相独立，可以自由组合——这正是 3.4 的组合模式成立的原因。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 属性多、变化频率差异大、要逐属性历史 | 标准四件套 | 宽表只能按最快频率刷，慢变属性被反复重写 | 属性间的变化频率是否相差 ≥ 一个数量级（【经验】阈值） |
| 一个主体对多实例，且实例会在主体间流转 | 多值属性（独立 Anchor + Tie） | 序列化进一个属性值只能表达「当时的集合」，无法表达归属变更 | 实例是否会在主体之间转移 |
| 一组属性由同一业务事件驱动变更 | 时态分组 | 逐属性独立建表在搬迁类事件上产生大量并发写 | 这些属性是否「总是一起变」而不是「总是一起查」 |
| 枚举被 ≥2 处引用且由中央治理 | Knot 共享 | 各表各存字符串会导致取值不一致且改不动 | 取值集合是否跨实体复用 |
| 时间点带业务语义（交易日 / 账期） | 时间锚点 | 把日期放事实列里，账期规则会散落在每个查询中 | 时间轴上是否存在「不该出现的日期」 |
| 属性类型需变更且不能停机 | 类型演化 | 原地 ALTER 加回刷会锁表并丢失可回滚性 | 是否能接受「旧表只读归档」 |
| 需要 LLM / Agent 自动感知字段语义 | Anchor + 元数据自动发现 | 宽表与维度建模的语义藏在列名与文档里，机器读不到稳定结构 | 每个属性是否都自带结构标识（一属性一表 + Anchor / Knot 元数据）【经验】 |
| 监管要求 bitemporal（能回答「何时知道」） | Anchor Modeling（三时态） | 维度建模的 `valid_from` / `valid_to` 只有业务一条时间轴；Data Vault 2.0 也记加载时态，但时态粒度落在卫星而不是单个属性上 | 是否必须区分「业务何时发生」与「系统何时知道」，且需要按属性独立追溯 |
| 属性稳定、时态要求弱 | 维度建模（Kimball） | Anchor 的 JOIN 成本换不来演化收益 | 字段变更频率是否低于每周个位数（【经验】阈值） |
| 字段稳定、时态要求强 | Data Vault 2.0 | Anchor 的粒度比 DV 更细，收益不足以覆盖复杂度 | 是否需要逐属性时态 |

表里最常被误选的一对，是**「时态分组」与「多值属性」**。两者的结构长得很像（都是「独立 Anchor + 一条 Tie」），但语义相反：多值属性表达的是「一个主体拥有多个实例」，时态分组表达的是「一组属性构成一个整体」。误选的实际后果是**关系语义被错建模成属性语义**——把「地址」当成多值属性来建，同一个地址因为两个人住过就成了一条被共享的记录，A 改门牌号会把 B 的历史一起改掉；反过来把「多手机号」当成时态分组，就会把「换号」写成「整组联系方式变更」，把邮箱、紧急联系人一起拖进伪变更。

区分这对模式的可操作判据是**「基数的语义」**：多值属性下，基数是**业务事实**（这个人确实有 3 个号码，3 是数据不是版本）；时态分组下，「组」的每一次出现都是**同一个逻辑对象的一个新版本**（同一个住址在时间上被改写了，而不是「他有了第二个住址」）。凡是基数会随时间自然增长的对象（号码、设备、联系人），归多值属性；凡是基数恒为一、只有版本在变的对象（住址、证件、套餐要素），归时态分组。

### 3.4 组合模式：真实系统不会只用一种

真实系统里极少出现「整个仓只用一种模式」的情况，更常见的是**按域分组、在一套底表上叠加多层**。下面三条组合覆盖了绝大多数落地形态，每条都标出了「谁承担什么职责」与「代价落在哪里」——组合的难点从来不是拼装，而是把职责边界说清楚。

**组合一：标准四件套（主体）+ 多值属性（联系方式）+ Knot（字典）。** 各自承担的边界是：四件套管主体与它的单值属性，多值属性管号码 / 邮箱这类会流转的实例，Knot 管跨实体复用的枚举。组合的运维代价是**对象数**——一张「客户全貌」视图背后可能是几十张表加上若干 Knot，必须有目录与语义层来承载这份清单，否则没人说得清客户到底有哪些属性。适合规模：**核心主数据域，10 个以上 Anchor、百级 Attribute**（【经验】阈值）。

**组合二：时态分组（地址）+ 类型演化（证件）。** 前者把成套变化的属性收进一个独立 Anchor，后者让类型升级不必停机；两者的共同点是**把「变更」表达成新表 / 新版本而不是原地修改**。运维代价是**下游必须走视图层**——底表已经处于 6NF 且带多次演化，任何直连底表的查询都会立刻被 JOIN 数与表版本数同时击穿。适合规模：**监管行业的核心实体，属性数在 100 以上的主体**（【经验】阈值）。

**组合三：Anchor 底表 + 反规范化视图层 + 物化热点切片。** 这是一个**跨层**组合而非模式组合：底表极致规范化保证演化能力，视图层把 JOIN 封装掉，物化把高频访问的「当前有效切片」预计算掉。运维代价是物化视图的刷新链路本身成为新的故障面（刷新窗口、陈旧度、与底表的一致性核对），且视图定义会随属性增长不断被重写。适合规模：**需要同时满足「高频变更」与「高频查询」的场景，且团队愿意维护刷新链路**。

三条组合有一个共同的失败前提值得提前说明：**职责边界没有写下来**。同一条 Tie，如果既被当作「关系事实」被分析方直接消费，又承担着视图层的中间结果角色，那么任何一次口径调整都会同时是「模型变更」和「下游口径变更」。把边界写成文档（谁能直连底表、视图由谁维护、字典变更由谁通知），比把模型设计得更精巧更能决定这套架构能不能长期活下去。

### 3.5 反模式与失效分析

下表覆盖本主题的 5 个反模式。每一行都按「症状 → 后果 → 成因 → 修法」四段给出，其中「后果」一栏刻意写成机制层面的结果而不是形容词——因为反模式的危害只有在能说清它经由哪条机制放大时，才谈得上修法。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 过度拆分到无法维护 | 出现 `customer_enabled`、`customer_is_vip` 这类单布尔 Attribute 表；对象数远超属性数 | 每个单行布尔表都带来一次独立的写入、索引与元数据开销，读侧 JOIN 数按表数增长，而信息量几乎为零 | 把「Attribute 只含 1 个属性」当成「每个字段必须独立成表」的教条执行 | 把低变化频率的布尔 / 枚举合并进一张 flags 表；拆分的判据是**变化频率**，不是字段类型 |
| Knot 过度共享 | 出现 `knot_gender` 这类只被一处引用的字典表；查询里 JOIN 数明显高于取值数 | 每次取值多一次 JOIN，收益为零；更糟的是这类 Knot 容易被跨域误引用，把变更半径无谓放大 | 把「Knot 强制独立」理解成「枚举一律抽 Knot」 | 只对**被 ≥2 处引用的查找**建 Knot；单实体独占的枚举直接存值 |
| 忽略反规范化视图层 | 下游报「查一次客户全貌要 JOIN 上百张表」；底表被 BI 直连 | 6NF 的读侧代价没有任何一层吸收，查询延迟随属性数线性上涨，最终团队会绕过模型直接读宽表副本 | 只完成了建模，没把「读侧组装」当成交付物的一部分 | 必须交付视图 / 语义层；下游**约定只读视图不读底表**；对高频切片做物化 |
| 忽略 bitemporal 的复杂度 | 底表只有 `valid_from` / `valid_to`，没有 `loaded_at` | 晚到的变更只能覆盖已有行，系统失去了区分「业务何时发生」与「我们何时知道」的能力，历史一旦被改写就无法复原 | 把时态理解成「记录版本」，而不是「两条独立的时间轴」 | 保留三时态；下游查询显式声明「业务时点 + 加载时点」 |
| 把 Anchor Modeling 当成「银弹」 | 全仓统一 6NF，包括字段稳定的报表域与即席分析域 | 稳定域付出了 JOIN 与元数据成本，却换不到任何演化收益；团队认知成本同步上升 | 把「6NF 比 3NF 更规范」直接读成「6NF 比 3NF 更好」 | 只在高变化 + 强时态的核心域用；其余域用 Data Vault 或维度建模，二者共存在同一仓里是常态 |

三个最危险的反模式值得单独展开。

**「忽略反规范化视图层」在生产中的典型暴露方式**是**滞后爆雷**：建模阶段一切顺利（写侧确实更快了、加属性确实是零成本），问题要等到第一个「拉全貌」的消费方出现才暴露。此时底表已经积累了可观的数据量，视图层的建立不再是加一层 SQL，而是一次性能工程——而消费方在此期间通常已经自行建了宽表副本，形成了第二份口径。它的成因不是技术判断错误，而是**只把建表当成交付、没把读侧组装当成交付**。

**「忽略 bitemporal 复杂度」的典型暴露方式是「发现得越晚越贵」**：只记两组时间的系统在上线初期看起来完全正常，因为晚到的变更占比低。等到某个上游开始补历史、或做跨源回填时，被覆盖掉的旧版本已经无从恢复——损失的恰恰是合规场景最需要的那类证据。它的成因是把时态理解成「加两个时间戳列」，而没有意识到**加载时态是独立于业务时态的一条时间轴**，它记录的是系统的认知状态。

**「把 Anchor Modeling 当成银弹」的典型暴露方式是「成本落在没被建模的人身上」**：全仓 6NF 之后，建模方的指标（加属性零成本、写入量下降）全部达成，而代价被转移给了分析方与报表方——他们面对的是几十张底表的 JOIN、以及一门必须重新学习的建模语言。这类项目的失败通常不表现为技术故障，而表现为**绕过**：团队自行从底表抽出宽表副本，模型仍在维护却不再被消费，此后数据出现第二份口径。它的成因是把「规范化程度更高」当成了「方案更优」，而规范化本身只是把成本在读写两侧重新分配，并没有消灭成本。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的。跨过某个阈值后，原来正确的结构会开始反向收费。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 属性数从 20 涨到 200（【经验】阈值） | 6NF 直查底表 | JOIN 数与索引访问次数随属性数线性上涨，查询被压垮 | 语义层 + 反规范化视图 | 视图定义需重写；下游查询要改指向 |
| 单个实体的多值集合从个位数涨到千级（【经验】阈值） | 多值属性（Tie） | Tie 成为全库最大表，点查一个主体的全部取值要扫整段 | 多值实例降级为「聚合快照 + 明细分区」 | 明细与快照的一致口径要重新定义 |
| 时间粒度从日变到小时 | 时间锚点 | Anchor ID 空间固化在日粒度，改粒度即重建 | 改回事实表携带时间戳 + 时间维度表 | 时间 Anchor 域与全部引用方需重建 |
| 组内属性变化频率从一致变为分化 | 时态分组 | 伪变更比例上升，写入按最快属性计 | 拆组，把分化出来的属性独立成表 | 历史数据的归组边界要重新切分 |
| 同一属性演化超过 3 次（【经验】阈值） | 类型演化 | 查询侧要 UNION 多张表做时间缝合 | 引入统一的「属性版本视图」收敛缝合逻辑 | 一次性收口所有下游的读路径 |
| 消费方从 1 个涨到 20 个（【经验】阈值） | Knot 共享 | 字典语义变更会同时打到所有引用方 | Knot 加版本边界 + 变更走审批 | 存量引用需按版本重新指向 |

这张表里有一个共同的形状值得记住：**触发的从来不是数据量，而是「某项成本开始由谁承担」**。属性数涨到 200 时痛的是查询方，多值基数涨到千级时痛的是存储与扫描，消费方涨到 20 个时痛的是字典维护方。因此判断「该不该换模式」的时机，不应该等某个延迟指标越过阈值，而应该在**收益方与代价方不再是同一批人**的时候就启动评审——那时还来得及做渐进迁移，晚了就只能做一次停摆式重建。

### 3.7 自检清单

以下 12 条都是可验证的问题，任意一条答「否」都应记录为待处理项，而不是靠经验放过。

1. 每个 Attribute 表是否**只含一个业务属性**？出现第二个业务列即已偏离 6NF，须确认这是有意合并而非疏漏。
2. 拆出独立 Attribute 表的字段，其**变化频率**是否明显高于被合并的字段？按字段类型（布尔、枚举）而不是按频率来拆，即命中「过度拆分」。
3. 每个 Attribute / Tie 表是否都带**三组时态**（业务起、业务止、加载时）？缺 `loaded_at` 即无法支撑「晚到真相」。
4. 视图层是否已交付，且下游是否**约定只读视图不读底表**？抽查一个下游查询，若出现 5 张以上底表的直连 JOIN 即为违反（【经验】阈值）。
5. 建 Knot 的表，是否有**至少两个引用方**？只有一个引用方的 Knot 应当合并回 Attribute 值。
6. Knot 的取值变更是否有**版本边界与变更审批**？没有边界的共享字典会把一次改名变成一次全库追溯改义。
7. 被归入同一时态分组的属性，是否由**同一个业务事件**驱动变更？用「查询时一起用」做分组依据即为误判。
8. 单个主体下基数最高的多值集合，其 Tie 表行数是否已被监控？若它成为全库最大表，即需重新评估该模式。
9. 时间 Anchor 的**粒度**是否在建模时被显式声明？未声明粒度的方案，会在业务要求变细时变成一次全库重建。
10. 发生过类型演化的属性，是否有一个**统一的视图**收敛「哪张表是当前有效的」这份知识？知识散落在各消费方即为风险。
11. 是否有**明确的场景边界文档**，写清哪些域用 6NF、哪些域用 Data Vault 或维度建模？没有边界的「全仓 6NF」就是银弹反模式。
12. 反规范化视图是否覆盖了**消费方实际高频访问的切片**？只建了通用视图而没有针对高频场景物化，等于把 JOIN 成本原样传给了下游。

这 12 条里，第 4、第 11 两条经常被跳过，因为它们问的不是模型本身，而是**模型之外的交付物**。但从失败案例的分布看，这两条恰恰决定了 6NF 能不能活过第二年。

建议把这 12 条固化成建模评审的检查项，随每次新增 Attribute 或新增 Knot 一并过一遍——6NF 的收益来自于持续的小步演化，而它的风险同样来自于持续的小步演化无人复核。

### 3.8 小结

把本节六个模式收成一句话：**它们全都是「属性可以独立演化」这一条约束的不同兑现方式**，差别只在兑现的粒度与代价的落点。下表按「约束 → 模式」重排一遍，便于在选型会上直接对照。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 属性频繁新增、类型会变、要停机外演化 | 标准四件套 + 类型演化 | 加属性即加表，破坏半径限制在「谁来读」一侧 |
| 一个主体对多实例，实例会流转 | 多值属性（独立 Anchor + Tie） | 归属变更被记录为边的新版本，而不是覆盖列值 |
| 一组属性由同一事件驱动变更 | 时态分组 | 整组共享一条时间线，避免半新半旧的中间态 |
| 枚举跨实体复用且中央治理 | Knot 共享 | 消除同一语义的多份物理副本，同时接受变更半径放大 |
| 时间点带业务语义 | 时间锚点 | 时间规则集中在一张可挂属性的表里 |
| 字段稳定、时态要求弱 | 维度建模 / Data Vault | 6NF 的 JOIN 与元数据成本换不来演化收益 |

> 本节小结：本主题下决定模式选择的唯一那条约束，是**「属性之间的变化频率是否同质」**——分辨率有多高，模式就该切多细；同质就合并，异质才拆分。所有失败模式最终都能回溯到这条约束被忽略：要么拆得比变化频率更细（过度拆分、Knot 过度共享），要么合并得比变化频率更粗（宽表、把不同节奏的属性塞进同一个时态分组）。
>
> 💡 **思考锚点**：拿你手上最宽的那张底表，数它的业务列数离 3.6 表的 200 阈值还有多远、单实体多值集合的基数是否已到千级，再把列分成「一年内改过」与「多年未动」两组——两组泾渭分明时你会按变化频率切成 Attribute 表，几乎全部同频时拆分只是在替读侧多付 JOIN，你的表落在哪一侧？
