## 5. 前沿演进（AI 时代）

> 原 § 5 共 226 行、为方向清单（4 个 LLM 方向、3 个检索结合点、8 条趋势与 6 条论文条目），缺少机制与成熟度判断，重写为 ~300 行前沿评估。

### 5.1 先分清三类「前沿」

这个主题下的"前沿"之间隔着巨大的时间差。「口径写成版本化文件、由引擎编译成 SQL」是可执行模型的工程做法，模式拆解在 [§ 3 §3.2.2](10-metric-system-section-3-sec3.md) 里已经写完；「业务方直接用自然语言提问」已经有产品在卖；而「Agent 自动判定异常、自动开单、自动改口径」目前只见于演示与厂商材料。把这三件事并列写成"趋势"，读者据此排路线图就会踩空：第一件排了能落地，第二件排了要做 PoC 与评测，第三件排了会变成一个没人敢验收的项目。

本节给每个方向一个级别，级别由**三条可核验判据**决定，不由感觉决定：

- **L1 生产可用**：① 已 GA 且有正式 release note；② 有第三方（非厂商、非项目承建方）公开生产案例；③ 接口稳定。三条**全中**才算 L1——可以排进路线图。
- **L2 可试点**：已可用但接口或生态未稳，或只有厂商 / 建设方自有案例，或只在小规模被验证。可以做 PoC，**不要做核心依赖**。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录，**不要在架构里预留假设**。

**第②条是本主题最难满足的一条**，而且难在一个结构性的地方：指标平台的买方是各家的内部数据团队，卖方是云厂商、BI 厂商与开源项目方。"我们用 X 把口径治理做起来了"这类公开材料，绝大多数由卖方自己、或由卖方付费客户在卖方渠道发布——按上面的定义，这落在 L2 里。要满足②，案例必须来自既不是能力提供方、也不是项目承建方的第三方写出的生产记录（规模、用法、时间三样都要有）。**第②条核不到就是 L2**，不存在"准 L1""L1 的边界案例"这类说法；判据也只有一套，不会在某个单元格里就地放宽。

结果是：**本节四个方向没有一行达到 L1，缺口全部落在第②条**。这不是保守，而是本条判据在本主题下的真实状态；也说明这四个方向的差别不在"成熟与否"，而在"① 与 ③ 各能核到什么程度"。

读本节还要守住四条命名与版本纪律：

- **区分产品名与能力名**：自然语言取数、语义模型、指标助手这类能力，在不同平台上叫法完全不同（同一个能力在两家产品里可能一个叫 Analyst、一个叫 Genie），不要张冠李戴，也不要因为名字不同就以为是两件事。
- **区分已发布与预览**：自然语言查询类能力常以预览形式发布，预览不是既成事实；本节不写具体版本号，只写"某年前后进入预览或正式发布"这类可核验的区间。
- **区分论文里的原型与产品里的实现**：一篇讲指标问答或自动指标发现的论文标题，不等于任何产品里的开关。
- **区分语义层能力与特征工程能力**：把指标值向量化做相似人群，是特征库的工作，不是语义层的工作（主文件 §2.4 已辨析两者的分工）。

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 自然语言取数：把解码空间收缩到语义层

- **旧做法与它的卡点**：业务问题要先经分析师翻译成 SQL，翻译一次、口径判断一次，判断结果留在人脑里、不可复用（主文件 §1.2 的第 1、2 条：同名不同义，以及同一个指标有几十种 SQL 实现）。这条路上的卡点具体在三处：
  - **自由生成 SQL 在指标场景上直接失效**：模型不知道"销售额"该用哪个口径，于是编造。错的形态是显式的（字段不存在、表名不存在、SQL 跑不通），但每次错法都不一样，无法回归、无法拒答。
  - **看板路径覆盖不了长尾问题**：看板只回答"预先想到的问题"，没被做成看板的问题仍然要人写 SQL——而写 SQL 的人数是整个链条上最窄的一环。
  - **信任成本压在最后一步**：业务方拿到一个数，没有便宜的办法验证它用的是不是对的口径。
- **AI 改变了什么机制**：**把模型的解码空间从「任意 SQL」收缩到「语义层里已登记的动作」**——输出被限定为"指标 + 维度 + 时间范围 + 过滤"四类选择，口径由定义层给出（结构图见 [§ 3 §3.2.6](10-metric-system-section-3-sec3.md)）。这是**接口形态与动作空间的变化，不是模型变聪明**：换一个更强的模型不会改变动作空间，换一份更全的语义层才会。

```text
提问：过去 7 天 PC 端新用户的 GMV 是多少？

可枚举的候选动作（模型只在这一层做选择）
  指标   gmv / dau / 转化率 / 客单价 / …   ← 来自定义层，不是模型编的
  维度   channel = PC
  时间   rolling 7 天
  过滤   user_type = 新用户
        │
        ▼
  定义编译引擎 ──► SQL ──► 执行      ← 口径在这里被定死，模型碰不到
──────────────────────────────────────────────
动作空间之外的提问（模型只能拒答，或者用相近指标凑一个）
  · 语义层里没有的指标
  · 语义层里没有的过滤项（例如刚上线、还没登记的新渠道）
  · 需要跨定义组合、而定义层不支持的运算
→ 命中率 = 提问落在动作空间内的比例，它是这个入口的第一运营指标
```

- **由此得到的**：因为候选动作可枚举，错误从"不可复现的生成错误"变成"可枚举的匹配错误"——于是可以回归（拿一批已登记指标问，看命中哪个）、可以拒答（候选为空就答不了）、可以在评审时被挡住。§3.2.6 已经给出这个结论：错误从不可枚举变成可枚举。本节的推进是下一句——**可枚举不等于可发现**。
- **由此付出的**：
  - ① **失败从显式变成隐式**：编造的 SQL 跑不通、会报错；选错指标的答案则是"一个真实存在的、格式正确的、口径不对的数"。前者由系统发现，后者只能由业务方在"觉得不对"时发现——而提问者恰恰是最没有分辨能力的那一类人，这正是"降低门槛"这个收益的另一面。
  - ② **回答的边际成本从零变正**：看板是一次建好、被看一万次，边际成本接近零；问答是每次提问都付一次模型调用加一次查询。把高频的固定问题也做成问答，是用最贵的路径回答最便宜的问题。【推算：设一次问答的模型与查询成本合计为 c、一块看板的固定成本为 C，则两种路径成本相等发生在提问次数 N ≈ C / c；提问频次越低问答越划算，频次越高越应该固化成看板。推导链只有这一步除法，请用自己的 C 与 c 重算 N。】
  - ③ **语义层覆盖率从"治理指标"变成"可用性前提"**：未覆盖的问题不是答不出来，而是被用相近口径凑一个（§3.2.6 的失效点）；[§ 3 §3.3](10-metric-system-section-3-sec3.md) 的决策表在「业务方直接提问、不写 SQL」一行的「关键判据」列，写的就是「语义层覆盖了多少真实在用的指标」。覆盖率必须被度量：统计一段时间里"提问没有命中任何已登记指标"的比例，这是提问侧的指标，与 §7.3.2 末尾那条查查询日志的抽查法互补。
  - ④ **同一问题两次回答可能不同**：模型版本、温度与提示词变化都会改变结果，而指标体系的全部价值是"同名同义"（主文件 §2.2.4 的一致性约束）。这要求把"模型版本 + 语义层版本"一起记进答案的可追溯信息里，否则事后无法解释某个数是怎么来的。
  - ⑤ **供应商锁定**：语义模型文件、调用接口与能力命名各平台不同，迁移要重写语义模型与提示词，这部分没有任何标准可依。

| 消费方式 | 一致性由谁保证 | 边际成本形态 | 能覆盖的问题 |
| --- | --- | --- | --- |
| 看板 / 报表 | 报表作者（易分叉） | 趋零（一次建好、多次读取） | 预先想到的固定问题 |
| 语义层 + 查询 API | 定义编译引擎（[§ 3 §3.2.2](10-metric-system-section-3-sec3.md)） | 查询成本（随并发与扫描量） | 已登记指标的问题 |
| 自然语言取数（AI 原生） | 语义层（模型只选指标与维度） | 每次提问一次模型调用 + 一次查询 | 已登记指标 **且** 能被正确匹配的问题 |

- **判定方法**：
  - 判断某产品能不能用在指标场景：问它**是否返回所用指标的 ID 与口径版本**。不返回，答案不可追溯，不能进生产。
  - 判断入口该不该对外开放：先量"未命中率"（提问中没有任何已登记指标可匹配的比例）。这个数高，开放入口换来的不是自助，是口径争议。
  - 判断效果有没有真的变好：建一个口径回归集（一批问题 + 每题该用的指标 ID），每次模型或语义层变更都跑一遍；看**错因分布**的变化（缺定义 / 选错指标 / 生成错），而不是只看"答对率"这一个数。
- **证据与来源**：
  - 【公开】云与 BI 厂商的自然语言取数能力在 2024 年前后发布，且都要求先提供一层语义模型再提问：Snowflake 一方要求先注册语义模型文件（本章 §4.4.3 给出注册语义模型再提问的示例），Microsoft 一方把 Copilot 与 Fabric 容量档位、租户开关绑定（即它不是打开就能用）。能力范围与前置条件请以各家官方文档当前版本为准，可按「产品名 + semantic model」检索核验。
  - 【公开】dbt Semantic Layer（其 MetricFlow 引擎于 2023 年 GA）、Cube、LookML、Airbnb Minerva 是语义层的公开实现，见 §3.2.2 与 §4.3.4；每一家的定义格式请按其官方文档核验。
  - 关于"自然语言取数把取数效率提升了多少倍"的说法，本节不转述：这类数字没有可复现的评测口径，且取数效率并不是本主题的瓶颈（主文件 §1.2 列的瓶颈是口径不一致与无法复用）。
- **成熟度**：**L2**（① 有（相关能力有产品文档与版本化发布）；② 不满足（公开案例多为厂商或其客户在厂商渠道的自述）；③ 未稳（语义模型格式与调用接口各平台不同））。它是四个方向里证据最完整的一条，缺的仍是第②条。

#### 5.2.2 指标定义的机器起草与候选发现

- **旧做法与它的卡点**：定义要人写，且最贵的不是写，是对齐。
  - **上线慢**：业务方提需求 → 分析师定口径 → 评审 → 上线。主文件 §1.2 第 4 条记的量级是从需求到上线 1–2 周【经验：这是主文件 §1.2 给出的经验量级，随组织与指标复杂度变化，请用自己近三个月的实际周期校准】。
  - **去重是最贵的一段**：判断两条指标是不是同一个，过去必须读 SQL 再理解业务。阿里公开材料记录其把 30 万级指标收敛到 10 万级【公开：本书 §10.1 阿里 OneMetric 案例，转引阿里公开材料 2016–2024】——去重省下的数量，恰好说明了重复的规模。
  - **一致性靠评审执行，而评审不可扩展**：主文件 §2.2.4 的五条一致性约束（同名一致、同义一致、版本一致、维度一致、时间一致）全靠人工评审；指标数上到千级、万级后，评审排期本身成为瓶颈。
- **AI 改变了什么机制**：**把「起草」这一段的成本转移到模型，而「裁决口径」这一段的成本没有任何变化**。机制上是**成本函数的变化，而且只发生在定义生命周期的第一段**。注意这里没有新概念：OSCAR 五要素还是那五个，语义层还是那层，变的只是"谁来写第一稿"。
- **由此得到的**：因为可以低成本生成多份候选，并且可以**用数据去证伪**（把两条定义在同一粒度、同一时间窗上各跑一遍，看结果是否恒等），所以"两条指标是不是同一个"从"读 SQL 理解业务"降级为"跑数比较"。这是 §3.2.1 OSCAR 五要素比对（比结构）之外的第二条路：**比行为**。结构比对管得住"要素不齐"，管不住"要素齐但口径不同"；值域比对补的正是这一段。两条路合起来，才接近"去重"这件事的完整解法。
- **由此付出的**：
  - ① **生成的定义会稀释动作空间**——这是与 5.2.1 直接冲突的一条。5.2.1 的安全性来自"候选动作少而准"；把模型起草的定义直接发布进语义层，等于给自然语言取数提供更多"看起来合理、口径不对"的候选。**5.2.2 的产出会削弱 5.2.1 的前提**，所以生成物只能停在候选区，进生产必须过评审。
  - ② **净收益被高估**：起草时间下降，评审时间不降（候选变多时还会上升），总成本的下降幅度小于"生成速度"给人的印象。
  - ③ **形式完备而语义空转**：模型写出的五要素可以"填满"，而业务过程归属与业务对象仍可能错——这类错误在定义文件里完全看不出来，只有拿数去比才会暴露。
  - ④ **责任归属**：自动起草的定义谁签字。没人签，出错时找不到裁决人；有人签，人就要为模型的草稿负责。这条不写清楚，组织不会让它进生产。
- **判定方法**：
  - 抽一批（比如 20 条）模型起草的定义，与既有指标做**值域比对**：同粒度、同时间窗各跑一遍。重复率高，说明它做的是"重命名"而不是"发现"。
  - 判断一个"自动发现指标"的能力是不是真的：看它输出的是**候选清单**还是**可直接入库的定义**。前者可用；后者要追问它怎么处理同名与同义——答不上来就不是生产能力。
  - 判断值不值得做：先数一下过去一个季度"因为口径没定而卡住的需求"有多少条。数量少时起草不是瓶颈，做这件事解决的是不存在的问题。
- **证据与来源**：
  - 【公开】OSCAR 五要素模型是阿里公开的指标方法论（主文件 §2.2.1 给出公式与示例；本书 §10.1 转引阿里公开材料 2016–2024，记录 30 万 → 10 万级的指标收敛）。判定方法：抽两条名字相近的指标，只看五要素能否判断它们是否重复（[§ 3 §3.2.1](10-metric-system-section-3-sec3.md) 给出同一条方法）。
  - 【公开】dbt 生态在 2023 年前后把 LLM 助手做进云产品，用于生成模型与指标草稿；它能做什么、在哪些版本可用，请以 dbt 官方发布说明与文档当前版本为准。
  - 关于"自动指标发现"的学术工作，本节只保留方向，不列标题与会议名，理由与核验方式见 5.4。
- **成熟度**：**L2**（① 有（生态内已有面向草稿生成的 LLM 辅助能力，有产品文档）；② 不满足（本节列不出可指名的、非厂商非承建方的生产案例）；③ 无约定（生成物的评审与发布路径没有共同规范））。

#### 5.2.3 指标异常的自动归因与自动巡检

- **旧做法与它的卡点**：告警告诉你"越界了"，不告诉你去哪看。
  - **定位要人做**：主文件 §1.2 第 3 条记录的是"指标出错无法定位到上游哪张表、哪个 ETL，恢复时间数小时到数天"。
  - **下钻组合数不给人留余地**：设核心维度有 5 个、每个 10 个取值，任取两个维度组合下钻就是 100 种，任取三个是 1000 种【推算：单维 10 个取值 → 两两组合 10 × 10 = 100；三维 10 × 10 × 10 = 1000；五个维度全取则是 10⁵ = 100,000。请用自己的维度数与取值基数重算】。人工逐一看不现实，于是实际做法退化成"凭经验挑几个看"。
  - **结论不沉淀**：这次的归因结论留在人脑里，下一次同类异常要重新走一遍。
- **AI 改变了什么机制**：这里必须把两段分开，否则会得出完全错误的结论。
  - **(a) 偏差的加性分解是确定性计算，它一直是**——把总偏差按维度拆成贡献值，早在指标平台出现之前就能算；AI 让它从"偶尔为之"变成"默认动作"，**不是让它成为可能**。
  - **(b) LLM 承担的是把分解结果转述成自然语言**，从而让"解释"的边际成本趋零。

  所以这个方向的收益主要来自 (a) 的自动化，不是 (b) 的生成。把它讲成"AI 会归因"是错位的：**归因能力不是 AI 给的，解释成本才是 AI 降的。**
- **由此得到的**：因为偏差在多数聚合指标上可加，所以"先看哪个维度"可以被排序，而不必靠经验遍历；再加上解释成本趋零，告警从"给一个阈值"变成"给一个带排序的解释"。**但这套东西的可信度来自分解，不来自叙述**——这两件事一旦被混淆，下一个代价就出现了。
- **由此付出的**：
  - ① **可加性只对一部分指标成立**，而业务最关心的往往是另一部分（见下表）：比率指标必须分别分解分子与分母，去重计数各维之和会重复计人，分位数根本不可加。用处理总量指标的做法去处理它们，排序会错——而且错得像对的。
  - ② **相关不是因果**：输出的是"偏差集中在哪个维度值上"，不是"为什么"。一段流畅的解释，会让人把"集中"当成"原因"。
  - ③ **语言流畅度掩盖解释质量**：错误分解 + 通顺叙述，比没有解释更危险——它把一个可疑的排序变成了一句可信的结论。
  - ④ **自动巡检把误报的成本外推**：原来误报的代价是"人看一眼关掉"；一旦接上自动通知、自动开工单，误报就变成对他人时间的实体打扰。这与 §7.4 说的"预算表算的是机时、实际付的是排查时间"是同一类隐性成本，只是它落在人身上。
  - ⑤ **判定不可复现**：同一份数据两次运行可能给出不同的排序或不同的措辞，这与"指标要确定、可复现"直接冲突（主文件 §2.2.4）。所以自动巡检的产物应当是**候选清单**，不是结论。

| 指标形态 | 例子 | 偏差是否可加 | 排序是否可靠 |
| --- | --- | --- | --- |
| 求和 / 计数 | `GMV = Σ 支付金额`、`订单数 = COUNT(*)` | 可加：各维贡献之和 = 总偏差 | 可靠 |
| 比率 | `转化率 = 首单用户数 / 注册用户数` | **不可加**：必须对分子、分母分别分解 | 分别分解后才可靠 |
| 均值 | `客单价 = 总金额 / 订单数` | 同上，是比率的一种 | 分别分解后才可靠 |
| 去重计数 | `DAU = COUNT(DISTINCT uid)` | **不可加**：各维之和 ≥ 总数（同一个人被计入多个维度值） | 不可靠 |
| 分位数 | `P95 响应时间` | **不可加**：分位数不满足可加性 | 不可靠 |

- **判定方法**：
  - 判断某个"自动归因"能力可不可用：看它的输出里有没有**分解明细**（各维度的贡献值）。只有一句结论、没有明细的，你无法核验，也无法在它错的时候发现。
  - 唯一的低成本验收方式：回放一次**已知原因**的历史故障（某次发版、某次上游断流、某次口径变更），看它有没有把真正的维度排进前列。
  - 判断比率类指标有没有被正确处理：问它分解的是分子、分母，还是两个都分解。答不出来，说明它按总量指标处理了比率。
- **证据与来源**：
  - 【公开：书内可核验】主文件 §2.3.5 给出异常检测的实现骨架（时序模型 + 预测区间），§2.3.6 给出"按维度下钻、算贡献度、取 Top3"的归因函数，本章 §4.4.4 给出相应的工程示例。这些骨架的异常判定与维度分解都不依赖大模型（LLM 只出现在最后一步，把分解结果转述成自然语言）——这恰好印证了"归因的确定性部分先于 LLM 存在"。
  - 【经验】异常检测与阈值告警在监控与 BI 产品里是成熟能力；把 LLM 接在告警后面生成解释，是 2024 年前后各类产品的通行做法。具体形态与前置条件请按对应产品的官方文档核验。
  - 关于"归因准确率 xx%"的声称，本节不转述：没有公开可复现的评测集时，这个数字没有意义——唯一可用的验收方式见上一条的故障回放。
- **成熟度**：**L2**（① 有（检测、下钻与告警是监控与 BI 产品的已发布正式能力，云 BI 一侧的异常归因产品与发布时间同本章 §4.3.5 产品表口径，可按其官方发布说明核验；实现骨架见书内 §2.3.5 / §2.3.6 / §4.4.4，属机制证据而非发布说明）；② 不满足（把自动归因写进生产流程的公开材料仍以厂商材料为主）；③ 部分（告警通道稳定，但解释的格式与评测口径没有约定））。

#### 5.2.4 指标语义层作为检索与上下文锚

- **旧做法与它的卡点**：这里的问题不是"检索不到"，而是"检索到的不是事实"。
  - **答案散落**：业务问"这个 GMV 怎么算出来的""口径什么时候改的"，答案在文档、看板说明与某人的记忆里；向量检索给出的是相似段落，召回不稳定，而且检索回来的段落可能已经过期。
  - **上游定位本来是结构化的，却被当成语义问题**：指标 → 表 → ETL 任务 → Owner 是一条可以被枚举的路径，但过去没有把它做成检索骨架，只能靠关键词与相似度猜。主文件 §1.2 第 3 条把这个卡点记为"指标血缘断裂"。
  - **Text2SQL 要在全库选表**：几百上千张表里选表、选字段，一步选错则全错；选错的自由度恰恰来自"没有已声明的指标可反查"。
- **AI 改变了什么机制**：**用确定性的结构去约束概率性的检索**——把"指标 → 上游表 / 任务 / Owner"这一段从语义相似度猜测换成图遍历，把"选哪张表"从模型在全库猜换成从已声明指标反查。机制是**接口形态的变化**（检索入口从"纯向量"变成"结构 + 向量"），不是存储或建模的变化。
- **由此得到的**：因为这段路径可以被枚举，它对召回的不确定性被消除——"定义在哪、谁改的、下游有谁"这类问题是精确查询，本来就不该交给相似度；相似度应该只留给它真正擅长的那一段：口径的业务背景、为什么这么定、相关的讨论与文档。**分工清楚之后评测才有意义**：结构部分可以判对错，语义部分只能判相关性；两者混在一张评测表里，两边都说不清（这与 §7 一贯的"先立判据再比较"是同一种纪律）。

```text
遇到一个问题，先分岔，再决定用什么
  它要的是「关系」，还是「相似」？
  ├─ 关系：定义在哪、谁改的、上游是谁、下游有谁
  │     → 结构查询 / 图遍历：答案唯一，可以判对错
  └─ 相似：口径相近的指标、为什么这么定、相关的变更讨论
        → 向量检索：返回一组候选，只能判相关性
──────────────────────────────────────────────
指标定义与指标血缘是左支的输入；文档与讨论是右支的输入。
把左支交给向量检索，等于把"唯一答案"降级成"相似答案"；
把右支交给结构查询，等于假设业务背景能被建表建出来。
```

- **由此付出的**：
  - ① **图谱质量的上限 = 血缘采集质量的上限**：采集不到的地方（动态 SQL、脚本任务）就是检索锚的盲区。锚的存在会让人误以为"能查到就是全的"——**过期的血缘比没有血缘更危险，因为它会给出错误的信心**（[§ 11 血缘与影响面](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md) 的 §1.2 把"血缘不准确（自动采集漏一半、人工维护又过期）"列为既有卡点，并在其 §6 的案例里给出"记录最后更新时间、让过期可发现"的做法）。
  - ② **第二份真源**：把口径与定义向量化，等于在定义层之外再造一份可被检索的副本；权限（谁能看哪个指标）与删除（口径废弃、指标下线）要在两处分别实现。血缘章节讲的是同一类问题的另一个入口：**副本侧的权限与删除必须重新实现一遍**。
  - ③ **分块与口径天然冲突**：指标定义是**很短的结构化文档**（一段公式加几个要素），按段落切分后再嵌入，很容易把分子与分母切进两个块，检索回来的是半个口径。于是"检索到的口径"与"定义层的口径"可能不是一回事。
  - ④ **时效窗口不被标注**：向量副本的刷新与定义变更之间存在窗口，窗口内检索到的是旧口径，而答案里通常不写这个窗口是什么时候的。
  - ⑤ **收益最难度量**：检索好坏与口径对错是两个维度，混在一张表里最后会变成"感觉好像变好了"。
- **判定方法**：
  - 先分问题类型：**要关系还是要相似**。要关系（这个指标的上游是谁、谁在消费它）就走结构查询，不要向量化；要相似（找口径相近的指标、找相似的变更讨论）才做向量检索。两者混着用，出错时无法定位是哪一层错了。
  - 判断向量副本能不能上：问一句"指标定义改了或下线了，向量库里那条多久消失、由谁负责"。答不上来就先别做。
  - 判断血缘能不能当检索锚：看它的**最后更新时间**能不能查到。查不到，锚就是盲的。
  - 判断 Text2SQL 的候选表该由谁给：如果它自己在全库选表，选错率不可控；如果它从已登记指标反查候选表，选错就退化成"选错指标"——回到 5.2.1 那种可枚举、可回归的错误。
- **证据与来源**：
  - 【公开】Microsoft GraphRAG 于 2024 年开源（同一项目由 Microsoft Research 于 2024 年公开配套论文，论文标题请以该项目仓库的 publications 页为准）；它处理的是**从非结构化文本抽取**的图。把指标定义与指标血缘这类**本来就结构化**的关系当作它的图输入，属应用层组装——两者不是一回事，不要混为一谈。
  - 【公开】主流湖仓与图平台在 2024 年前后把向量检索与图查询做成平台能力（各平台命名不同，请按其官方发布说明核验）。
  - 【公开：书内可核验】主文件 §2.4 已辨析指标体系与 Feature Store 的分工：Feature Store 服务 ML，指标体系服务 BI 与决策，特征可以来源于指标。这条辨析决定了"指标值当特征"是特征工程的做法，不是语义层的新能力。
- **成熟度**：**L2**（① 有（向量检索与图检索已是主流平台与开源项目的正式能力）；② 不满足（公开案例多为平台方或承建方自述）；③ 未定（向量模型、分块方式与元数据字段都没有共同约定））。

### 5.3 与本主题既有栈的接口在哪

判断标准是接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。凡是说不清失败归属的"结合"，在评审会上听起来完整，在事故复盘时提供不了任何信息。

还有一条更实际的理由：本节涉及的组件几乎都是**可替换**的（语义层可换、BI 可换、向量库可换、流引擎可换），真正难换的是**边界上的契约**——尤其是"口径版本"与"权限"这两类必须穿透所有消费端的东西。所以下表的"现状"列沿用 §5.1 的判据口径（① 正式发布说明 / ② 第三方生产案例 / ③ 接口稳定），但**不在这里重新评级**：凡与某个 5.2.x 方向对应的行，现状与该方向的结论一致。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 语义层 → 自然语言取数 | 模型只输出「指标 + 维度 + 时间 + 过滤」，口径由定义编译引擎决定；答案必须能回指到指标 ID 与口径版本 | 语义层定义的 Owner——选错指标是"定义不全或命名有歧义"的错，不是模型的错 | 对应 5.2.1：① 有、② 不满足、③ 未稳 |
| 业务描述 / 既有 SQL → 指标定义候选 | 候选清单进评审流水线，评审通过才进定义层；接口是候选格式与评审记录 | 签字发布的人——候选只是草稿，谁发布谁负责 | 对应 5.2.2：① 有、② 不满足、③ 无约定 |
| 指标值 → 异常检测与归因 | 检测读指标时序；归因读同粒度的维度明细，输出分解明细 + 排序，而不是一句结论 | 指标 Owner——解释错是分解口径的错，不是措辞的错 | 对应 5.2.3：① 有、② 不满足、③ 部分 |
| 指标定义 + 血缘 → 检索索引 | 定义与口径以结构化文档进索引；血缘以图遍历提供上游路径；接口是分块方式、刷新窗口与权限 | 索引 Owner——权限与删除必须在副本侧再实现一遍 | 对应 5.2.4：① 有、② 不满足、③ 未定 |
| 语义层定义 → 流式执行（Flink / Doris） | 一份定义编译出离线 SQL 与流式作业；接口是事件时间、水位线、允许迟到与回撤语义 | 定义 Owner 与流作业 Owner 共同——两者用不同的时间语义算同一个指标，就是两个数，不是一个数 | 非 AI 方向：属 [§ 7 §7.3.2](10-metric-system-section-7-sec7.md) 的计算时机分工；§10.1 的阿里案例记录"同一份定义生成 Flink SQL + Spark SQL"的做法 |
| 指标 API → 产品与流程（嵌入式指标） | 程序调用指标 API 而非人看看板；接口是鉴权、配额与结果格式 | 调用方——指标平台只保证"按定义算出数"，不保证"这个数被用在正确的决策里" | 非 AI 方向：是消费端从人变成程序，属 §4.2.4 指标查询服务的延伸 |
| 元指标 → 治理（指标的指标） | 命中率、未命中率、口径漂移、查询失败率与业务指标同源采集；接口是指标 ID 与查询日志 | 平台 Owner——没有元指标就无法判断入口有没有在起作用 | 非 AI 方向：本节在 5.7 的「一年内观察」列给出最小观测项 |
| 指标平台 → Agent 工具 | 指标以工具（函数描述符）形式暴露；返回结构化结果而非自然语言 | 指标平台 Owner——平台提供事实，不提供"该不该行动"的裁决 | 对应 5.2.3 的处置侧：工具接入的约定已公开，裁决语义仍要自建 |

表里只有两件事不能在副本侧"将就"：**口径版本**（答案必须回指到它用的是哪一版定义，否则事后无法复盘）与**权限**（谁能看哪个指标，在副本侧必须重新对齐一次）。这两件事在功能演示里都"看起来没问题"，所以既不会出现在演示里，也很少出现在评审会上，只在事故复盘时出现。

### 5.5 被过度宣传的部分

**「自然语言取数让业务方人人都是分析师」** —— 实际是**降低了"把口径翻译成查询"的成本，没有降低"该用哪个口径"的责任**。为什么会这样：口径选择是业务决策而不是查询技术，它依赖对业务过程的理解（主文件 §2.2.1 的 C 要素），而这段理解从来不在数据团队手里。什么时候它才会成真：当每个答案都能回指指标 ID 与口径版本、且未命中率被持续度量时，"人人可查"成立——但**"可查"仍然不等于"可决"**，把入口开放出去的同时必须把口径回归集建起来。

**「Agent 自动治理指标」** —— 实际是**提出候选**。为什么会这样：概率系统的输出不满足"同名同义"这条约束（同一个问题两次运行可能两个答案，主文件 §2.2.4），而指标体系的全部价值恰好就是那条约束——把判断权交出去，等于放弃这套体系的立身之本。什么时候它才会成真：当 Agent 的输出被限定为"候选 + 由确定性规则裁决 + 全程留痕"时，它才能在治理链上承担一个角色；"自动开 P1 工单""自动改口径"不属于这个角色。

**「指标 + Embedding（Look-alike / 指标即特征）是 AI 原生的指标能力」** —— 实际是**特征工程的既有做法换了个名字**。为什么会这样：主文件 §2.4 已把两条线的分工写清——指标体系服务 BI 与决策，Feature Store 服务模型训练与推理，特征可以来源于指标。把指标值向量化做相似人群，是特征库的活，与语义层无关。什么时候它才会成真：当指标平台能同时保证"同一个指标在 BI、决策、特征三处同口径"时，这件事才算进了指标体系的范围——而那是口径治理的成果，不是 embedding 的成果。

这三条的共同点是：**模型把"做"变便宜了，没有把"判"变便宜**。所以判断一个"AI + 指标"的方案值不值得投，只需问一句——它省掉的是"做"的成本，还是"判"的成本。省"做"的成本，收益立刻兑现；声称省"判"的成本，先让它证明裁决规则是可复现的。

### 5.6 未来 3–5 年：可证伪的预测

写不出信号与反信号的预测不写。下表的"会证伪的信号"一列是给自己留的检查项，不是修辞。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 自然语言取数的竞争力从"模型能力"转到"语义层覆盖度与匹配率"，产品开始把未命中率当成一等运维指标暴露给管理员 | 厂商文档或控制台出现未命中率、命中指标 ID 分布一类的元指标；采购清单里出现"语义层覆盖率" | 产品仍以"直接读 schema 生成 SQL"为主路径，且答案不返回所用指标 ID |
| 指标异常的默认形态是"确定性分解 + 排序"，LLM 只做转述；以"LLM 直接读数字下结论"为核心卖点的产品会退回辅助位 | 产品文档出现贡献度分解的输出字段；出现针对比率、均值、去重计数与分位数的分解规范（而不是一律按总量处理） | 产品以"LLM 归因"为核心卖点、不暴露分解明细，且不区分指标形态 |
| 实时与离线"一份定义两处执行"仍是局部能力，不会在 3–5 年内成为默认 | 语义层文档里出现针对事件时间、水位线、迟到数据与回撤的专门章节 | 语义层继续以批处理时间窗为中心，实时指标仍靠各自的流作业手写 |
| 指标"可比较"的瓶颈从公式转到非公式约定（实体解析口径、时区、退款与冲正的记账时点、合规解释），跨组织共享指标长期停在"共享公式" | 出现跨组织公开对齐的**非公式约定**文档——对齐的是这几项约定，而不是又一份指标定义清单 | 跨组织倡议仍只发布指标定义，回避这几项约定 |

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 口径还在人脑里、同名不同义 | 先做两件事：核心指标的五要素登记（[§ 3 §3.2.1](10-metric-system-section-3-sec3.md)）；再建一个口径回归集（一批问题 + 每题该用的指标 ID） | 未命中率与口径争议次数是否同步下降 | 不要先上自然语言入口——没有语义层时，它只是更快的幻觉 |
| 已有语义层，被要求接自然语言取数 | 只在已登记指标上开入口；强制答案返回指标 ID 与口径版本 | 错因分布（缺定义 / 选错指标 / 生成错）与未命中率 | 不要把模型起草的定义未经评审直接发布进定义层（会反向削弱入口的可靠性） |
| 被要求做"AI 自动归因 / 自动巡检" | 先把分解明细做出来，AI 只做转述与排序；比率类与去重计数类指标单独处理 | 已知原因的故障回放，排序是否命中 | 不要让 Agent 自动开 P1 工单或自动通知 Owner；不要把"相关"写成"原因" |
| 指标多、消费端多，有人提"指标即特征 / Look-alike" | 先分清这是特征库的事还是语义层的事（主文件 §2.4），再确认两边口径同源 | 特征与指标是否共用同一份口径、有没有出现两个数 | 不要在语义层里做人群分群；不要把向量副本当成第二份定义源 |
| 只有离线体系，被要求"实时也要 AI" | 先把实时与离线收敛到同一份定义（[§ 7 §7.3.2](10-metric-system-section-7-sec7.md) 的计算时机判据） | 实时与离线的同名指标是不是还是一个数 | 不要让实时链路单独长出一套口径；不要把"上实时"当成 AI 能力的替代品 |
| 已在做检索增强 / Text2SQL | 只把"用精确条件查不到"的那部分口径向量化，并先写清权限与下线的传播路径 | 血缘的最后更新时间是否可查、副本刷新窗口是否被标注 | 不要把全量口径复制进向量库；不要在副本上另建一套权限却不同步 |

最后一列是这个表里唯一有长期价值的：前三列做的事一年后都能补，"不要做"的那几件做错了，要花一年拆掉。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一机制**是**候选动作空间与解释成本**——自然语言取数之所以能用，不是因为模型学会了写 SQL，而是因为它被限制在"语义层已登记的指标 × 维度 × 时间 × 过滤"这个小空间里；异常归因之所以变快，不是因为模型会分析，而是因为偏差分解本来就可算、而把结果写成话的边际成本被压到接近零。它没有改变的是：**口径该由谁定、两条指标是不是同一个、一个数能不能被用来做决策——这三件事仍然只有人能裁决**（主文件 §2.2.4 的一致性约束一条都没松）。本节四个方向全部停在 L2，缺口都在第②条：这不是判据苛刻，它测的正是"这套东西离开厂商的演示环境之后还成不成立"。
