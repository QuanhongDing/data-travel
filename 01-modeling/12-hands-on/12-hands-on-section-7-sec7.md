## 7. 与其他方法对比

> 原 § 7 共 56 行、为打分表 + 决策树 + 组合清单，缺少机制解释与可溯源证据，重写为 ~300 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

打分表把「取决于场景的结论」写成了「绝对结论」。同一维度在不同规模与组织形态下权重相反：几个人的团队「易用性」权重最高，因为没有人手维护平台；几百人的组织里「运维接管度」与「跨云能力」权重更高，因为出问题时必须有明确的接管方。一张表用同一个权重把这些场景压成一个分数，等于先假定了一个并不存在的「平均团队」。

原表的七个维度里有两对是**定义上互斥**的：「阿里生态集成」与「跨云能力」，「国产化合规」与「跨云能力」。同一列上乘同一组权重再做加权和，等于让两个方向相反的量互相抵消——这时候「4 分」的含义是「集成不错但跨不过去」，而不是「4 分好」。这是打分表最根本的缺陷：它假设各维度可加，而这两对维度不可加。判据框架必须先把不可加的维度拆成**硬约束**（满足/不满足，直接排除整族方案），剩下的才谈比较。

这两对维度造成的实际后果是可演示的：当团队把「跨云能力」的权重调高一档（评审会上一次很小的改动），排名就可能从「一体化平台第一」翻到「云原生栈第一」——因为这两项在候选之间的差异方向相反，权重的任何调整都可能把结果倒过来。也就是说，**打分表的排序结果主要由权重驱动，而不是由候选的真实差异驱动**；而权重是评审会上最容易改的一个数。反过来，前面两条机制判据给出的结论不会因为权重变化而翻转：一个候选的粒度声明写在哪，是它自身的事实，不是评审的偏好。

打分表还抹掉了「能力边界」与「当前实现」的区别。同一家平台的生成式助手，今年能做与前年能做是两件事，而分数不写版本、不写来源。「产品名不等于能力名」——自然语言生成 SQL 这件事，各平台的入口、函数名、支持的方言都不一样，落到具体产品一律以该产品文档为准（[§ 5 前沿演进](12-hands-on-section-5-ai.md) 的 5.1 已把这条写成判据）。

第三个问题是打分表**只列优点、不列代价**。任何一项能力都有它的反面：粒度锁得越早，查询越便宜、变更越贵（[§ 3.1](12-hands-on-section-3-sec3.md)）；表格式带来多引擎共享，同时带来 compaction 与 catalog 的常设作业；平台门禁带来强制登记，同时带来跨环境搬移的摩擦。打分表没有「代价」这一列，于是读者会把每一项都当成可以叠加的正收益，最后得出「全都上」的结论——而真实的选择永远是在两组代价之间挑一组更便宜的。

第四个问题是打分表**不写谁付账**。买平台的人、值班维护的人、被门禁挡住的人、以及取数的人，是四拨不同的利益相关方。一个在采购评审里得高分的方案，可能在值班表上得低分；而值班的痛感要三个月后才出现，届时决策已经落地。选型文档里最该写清的一栏是「这一项由谁承担」，打分表恰好没有这一栏。

本章改用六条判据。它们的落点**不是整齐的两分**——**粒度与口径的声明写在哪**、**引擎与存储的耦合度**是机制判据，7.3 整节展开它们（7.3.1 / 7.3.2 讲机制本身，7.3.3 / 7.3.4 讲由这两条机制导出的后果），其中「引擎与存储的耦合度」在决策树上另有落点（N3）；**生态与合规边界**、**运维接管度**是树上的两个淘汰项（N1、N2）；**AI 能力的挂载层级**既在 7.3.4 展开，也在树上作排序项（N5）；**迁移成本形状**不进决策树，用在 7.7 的迁移成本表。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 粒度与口径的声明写在哪 | 「一行代表什么」「这个数怎么算的」写在哪个制品里、由什么机制守护 | 它决定变更成本、影响面能否被计算、AI 取数能否成立（§ 3.1 的核心机制、§ 3.5 的「缺乏 AI 集成」） |
| 引擎与存储的耦合度 | 换一个引擎要不要搬数据 | 它决定多引擎共享是否可行、跨云是搬迁还是重写 |
| 生态与合规边界 | 数据与团队能不能离开当前这朵云 | 这是硬约束而不是成本项——它直接排除整族方案，讨论性价比之前就得先过关 |
| 运维接管度 | 出问题时谁值班、自己能不能修 | 开放表格式与自建栈有常设运维项，必须有人认领；没人认领的项不会消失，只会以读放大与查询变慢的形式出现 |
| AI 能力的挂载层级 | 它是底座还是底座之上的助手 | 底座与 AI 是两层，级别不同对架构的约束不同（[§ 5](12-hands-on-section-5-ai.md) 的 5.1） |
| 迁移成本形状 | 搬走的成本是一次性还是持续 | 一次性能摊销，持续项会跟着你到下一朵云，并在此后每一次议价里出现 |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 阿里 DataWorks 全家桶（DataWorks + MaxCompute + Hologres + Quick BI + PAI + Real-time Compute） | 一体化商业平台 | 粒度与口径作为平台里的登记项，由平台门禁强制 | 阿里云上的中大型互联网、国内传统行业 | 商业订阅（按用量） |

| 腾讯 WeData + TBDS + CDW | 一体化商业平台 | 同上 | 腾讯云客户 | 商业订阅 |
| Microsoft Fabric（OneLake + Power BI + 数据工厂 + Spark） | 一体化商业平台（SaaS 形态，Azure 生态） | 湖仓底座与 BI 同属一个 SaaS，共享同一份 OneLake 上的 Delta 数据 | Azure / 微软生态企业 | 商业订阅（按容量档位计费） |
| dbt + Snowflake / BigQuery + Airflow + DataHub | 云原生声明式栈 | 模型是版本控制里的文件，粒度与口径随代码走评审 | 海外 / 跨云 / 现代化数据栈 | dbt / Airflow / DataHub 为开源项目（许可以各自仓库 LICENSE 为准）+ 数仓商业订阅 |
| Databricks + Unity Catalog + dbt | 湖仓一体托管平台 | 开放表格式 + catalog + 自有引擎，AI 助手挂在其上 | AI 优先的团队 / 智能体平台 | 商业订阅 |
| 自研中台（自研 ETL + 调度 + 目录 + LLM） | 自建 | 平台自己实现上述全部机制，能力上限由自研团队的长期投入决定 | 美团 / 京东 / 拼多多一类自建路线 | 自建 |
| 开放表格式自建栈（Iceberg / Hudi / Paimon + Spark + Flink + dbt + 自建 catalog） | 自建 / 跨云 | 表格式把数据布局变成开放规范，多引擎读同一份数据 | 大数据团队 / 跨云 | 表格式与引擎为开源项目（许可以各自仓库 LICENSE 为准） |

这九个候选其实只分**三族**：**一体化商业平台**（DataWorks 系、字节系、华为系、腾讯系、微软 Fabric）、**云原生声明式栈**（dbt + 托管数仓 + 调度 + 目录）、**表格式自建栈**（Iceberg / Hudi / Paimon + 引擎 + 自建 catalog）。表里的「自研中台」不另立一族，它是**表格式自建栈这一族的极端形态**——同一族里有两个端点：一端只自建布局与 catalog，另一端连 ETL、调度、目录与取数入口都自研到底。所以 7.3.1 与 7.4 把它与表格式自建栈并列成两种**形态**，而不是两个**族**。同族内部差异小——同族之间的差别主要在入口函数名、生态适配与合规资质，机制上是同一套；跨族差异大，而且差异集中在 7.3 的两条机制上。**先分族再选，能省掉一半比较工作。** Databricks 在体验上像一族、在机制上属三族：它提供一体化的界面，但底座是表格式加多引擎；Fabric 相反，体验上像三族（底下一份开放式 Delta 数据）、机制上属一族（底座与 BI 由同一家以订阅方式一并提供）。

同族内部真正需要比的只有三件事，而它们都不是技术机制：

- **合规与资质**：能否私有化部署、是否有等保与信创适配、数据能否落在指定地域。这一条决定候选名单，而不是决定排名——不满足就出局，不参与比较。
- **计价单位是否与你的负载同构**：按扫描量计费对「大表小结果」的查询友好、对「宽表全扫」的查询昂贵；按算力单元计费则相反。同一个负载换到另一种计价单位下，账单形状会变，这一条要用你自己的查询画像去核对（计价规则以各厂商官方价目页当前版本为准）。
- **生态里已有多少你的团队已经在用的东西**：调度、IDE、CI、权限体系能不能接上现有流程，决定的是接入期的人力，而不是长期能力。

把这三件事比完，同族的差距通常落在一个可以接受的区间里；此时真正的决策变量回到跨族的两条机制上。

有一类东西**没有出现在这张表里，是刻意的**：数据网格（Data Mesh）一类的联邦组织形态。它不是可选的产品族，而是「粒度与口径的决定权交给谁」这个组织问题的答案（[§ 3.2.6](12-hands-on-section-3-sec3.md) 把它单列，正是因为只有它不由建模曲线决定）。把它与工具族并列打分是一个类别错误：选了联邦形态之后，每个域仍然要在上面三族里各自选一个。因此本节不提供「数据网格 vs DataWorks」这类比较；关于它的可操作判断（跨域依赖里有多少条走契约、多少条走共享表直连）见 [§ 3.6](12-hands-on-section-3-sec3.md)。

### 7.3 机制差异：为什么它们表现不同（核心节）

本主题的核心机制 [§ 3.1](12-hands-on-section-3-sec3.md) 已经给出：**粒度锁得越早，查询越便宜、变更越贵**。各候选的差别不在于锁不锁，而在于两件更具体的事——**这份粒度声明写在哪、由什么机制守护**（7.3.1），以及**数据布局由谁定义**（7.3.2）。7.3.3 与 7.3.4 是这两条机制的直接后果：口径的物化位置，以及 AI 能力挂在哪一层。

为什么挑这两条，而不是挑「易用性」「成本」「AI 原生」那几项？因为它们满足一个条件：**可以由机制推出可证伪的后果**。「易用性」不能——它取决于你的团队有没有用过 dbt，培训两周就变了；「成本」也不能——它是计价单位的函数，单位一换排名就变。而「声明写在哪」能推出「影响面能不能在提交前被算出来」，「布局由谁定义」能推出「加一个引擎要动什么」，这两条都是可以当场验证的。选型文档里能被追问的，只应该是后一类。

下面每条机制都按同一结构写：机制是什么 → 各候选的实现差异 → 由此必然导出的性质（因果句）→ 公开证据 → 失效条件。**失效条件那一栏最重要**：它决定这条机制的优势在你这里还能不能成立。

#### 7.3.1 粒度与口径的声明位置：代码里的文件 vs 平台里的登记项

**机制是什么**：粒度声明（一行代表什么）与口径声明（这个数怎么算）物理上存放在哪个制品里，谁有权改、改的时候会经过什么检查。

**它在各候选中的实现差异**：

| 候选 / 形态 | 声明写在哪 | 守护机制 | 是否在版本控制里 | 影响面能否被工具算出 |
| --- | --- | --- | --- | --- |
| 云原生声明式栈（dbt） | 模型 SQL + schema.yml，在 Git 仓库里 | 代码评审（PR） | 是 | 能（模型间依赖可解析） |
| 一体化商业平台 | 平台里的建模对象与元数据登记项 | 平台门禁（缺项不能发布） | 平台自带版本，不是 Git | 能（平台的血缘引擎算） |
| 表格式自建栈 | 表结构 + 表格式规范文件 | 引擎约束 + 自建 CI | 部分（表规范可版本化） | 取决于自建程度 |
| 自研中台 | 自研平台的数据结构里 | 自研门禁 | 取决于自研 | 取决于自研 |

**由此必然导出的性质**：因为 dbt 的模型是**版本控制里的文件**，所以任何一次粒度或口径变更都必然经过 diff 与评审、影响面可以被工具在提交前算出来——这是「先定粒度、再建模」这条纪律能被制度保护的原因；代价是「改一个口径」要发一次版，跨项目复用必须另造 package 机制，于是口径的收敛速度被代码发布节奏限住。

反过来，因为一体化平台的粒度是**平台里的登记项**，所以门禁可以在发布前强制——缺 Owner、缺业务含义、缺分层直接拒绝上线（[§ 6](12-hands-on-section-6-sec6.md) 12.4 的建表审批流正是这条门禁的产物：「表名 + 分层 + 域 + 业务含义 + Owner ← 缺一项直接拒」）；代价是模型与 Git 仓库之间没有天然同步，跨环境搬移要靠平台的导入导出，而「这段 SQL 是谁在什么时间改的」要用平台自己的审计记录回答，不能用 git log。

第三种形态值得单独说：**表格式自建栈的声明其实写在引擎的 DDL 里**——表结构本身即声明，落进表格式的元数据。它的守护机制是引擎约束加自建的 CI，因此它的严格度完全取决于你在 CI 里放了什么检查。这解释了一个常见现象：同一套 Iceberg + Spark + dbt 的栈，在有的团队里影响面可算、变更可控，在另一个团队里就是一堆没人管的表——**差别不在栈，在 CI 里有没有那几条检查**。这条也是可自行核验的：查一查你的变更流水线里，有没有一步会在合并前读血缘并拒绝合并。

这三种形态对应三种严格度，而严格度有一个反作用：**门禁检查的东西与它要保护的东西不是同一件事时，门禁会从两个方向同时失效**。[§ 6](12-hands-on-section-6-sec6.md) 的治理案例给出的是**漏检**那一侧——早期只做表级血缘时，改一个字段名在门禁里根本看不见，事故照样发生，最后倒逼出「字段级血缘 + CI 阶段阻断」（§6 12.4 失败教训）：门禁的粒度粗于变更的粒度，真正会出事的变更从缝里过去。而「被绕开」那一侧的真实落点在 [§ 3.5](12-hands-on-section-3-sec3.md) 的「照搬方法论」：门禁查的是形式（分层名与命名前缀）而不是内容（本地的业务过程清单）时，团队会填表交差或绕开流程——通过了门禁也不等于变更安全。两侧的修法是同一条：让门禁检查的粒度与它要保护的风险对齐。所以选型时要问的不是「哪家的门禁更严」，而是「它的门禁粒度与我的变更粒度是否匹配」。

**公开证据**：dbt 官方文档的建模分层建议（staging → intermediate → marts，并将 marts 建成星型维度模型）是持续更新的活文档，可按关键词 "How we structure our dbt projects" 在其官方文档站核验【公开，持续更新页，取版本切片】——切片取「你实际使用的 dbt 版本 + 该版本 changelog」，跨版本的行为差异以 changelog 为准；阿里 OneData 的 ODS/DWD/DWS/ADS 分层与统一指标口径见《大数据之路：阿里巴巴大数据实践》（2017）【公开】；「无 Owner 禁止发布」的门禁形态见本目录 [§ 6 落地实践](12-hands-on-section-6-sec6.md) 的建模治理案例（2020–2024）【公开，转引本仓库案例】。

**失效条件**：当**变更以探索性试错为主**时，「走评审」从保护变成瓶颈——发版周期挡住了本该快速迭代的探索；当**团队不具备代码评审纪律**时，「模型即文件」退化成一个没有人看的 SQL 仓库，此时它的可追溯性只是形式上的。

#### 7.3.2 引擎与存储的耦合度：同源定义 vs 开放规范

**机制是什么**：数据在存储上的布局（文件格式、分区、聚簇、索引、元数据清单）由谁定义——由某一家引擎私有定义，还是由一份可以被多方实现的开放规范定义。

**它在各候选中的实现差异**：

| 候选 / 形态 | 数据布局由谁定义 | 加一个引擎要做什么 | 谁承担常设运维项 |
| --- | --- | --- | --- |
| 一体化平台（MaxCompute + Hologres） | 平台自己 | 平台内开通，跨引擎靠同步链路 | 平台承担大部分，同步链路的一致性由你承担 |
| 托管数仓（Snowflake / BigQuery） | 该厂商 | 不能加，只能整体换 | 厂商 |
| 开放表格式（Iceberg / Hudi / Paimon） | 开放规范 | 接该引擎的 connector，并处理能力差异 | 你自己：compaction、文件布局、catalog 高可用 |
| Databricks（Delta + Unity Catalog） | 表格式规范 + 自有引擎优化 | 接外部引擎要接受能力差异 | 平台承担一部分，分区与布局策略仍归你 |

**由此必然导出的性质**：因为表格式把数据布局变成**开放规范**，所以批、流、ML 多个引擎可以读同一份数据，同一份数据的副本数从 N 降到 1，口径漂移的物理基础被消除；代价是 compaction 与小文件治理变成**每周都要有人做**的常设作业，catalog 成为新的单点——这两项不是一次性建设，而是持续支出（[§ 3.4](12-hands-on-section-3-sec3.md) 组合三里把它们写成「compaction 与元数据维护成为常设作业」）。

反过来，因为托管数仓的计算与存储同属一家、优化器可以假定数据布局，所以聚簇与分区裁剪能直接生效、无需你维护 compaction；代价是「换引擎」等于搬迁数据并重写查询，**引擎边界即组织边界**——你与这家厂商的谈判空间，在你把第一张表建进去的时候就锁定了。

一体化平台还有第三种形态：**同一家内两个引擎之间的一致性由同步链路承担**（离线的 MaxCompute 与实时的 Hologres 之间就是这种关系）。它既不像托管数仓那样只有一个引擎，也不像开放表格式那样多引擎读同一份文件——它是「两个引擎、两份数据、一条同步链路」。因为一致性的责任从存储层挪到了链路层，所以它的失败模式也挪了位置：存储不会不一致，**链路会**。于是运维的注意力必须放在这条链路的延迟与校验上，而不是放在存储上——这是选一体化平台时最容易被漏掉的一项常设工作。

三类形态各有各的失效点，没有任何一类是「一致性自动成立」的：同源单引擎靠的是「只有一个写入方」，开放表格式靠的是「文件级提交协议」，一体化双引擎靠的是「同步链路被监控」。选型时问一句「一致性由哪一层保证、那一层坏了会怎样」，比问「支不支持实时」有用得多。

**公开证据**：本目录 [§ 4.3](12-hands-on-section-4-sec4.md) 给出 Iceberg / Hudi / Paimon 的建表与写入示例，其中格式版本、写格式、目标文件大小、主键与增量字段等属性名均来自各项目的公开文档【公开，持续更新页，取版本切片】——切片取「你实际使用的引擎版本 + 目标表格式规范版本号」，属性名与默认值以该切片为准（同名属性在不同版本间可能改名或改默认值，跨版本迁移前请对照所用版本的官方文档与 release note）；[§ 3.2.4](12-hands-on-section-3-sec3.md) 给出湖仓一体的约束与代价【公开，本仓库主文件 § 3.2.4】。

**失效条件**：当**只有一个引擎真的需要读同一份数据**时，表格式带来的「共享」无人消费，而 compaction 与 catalog 的成本照付——此时开放表格式是纯成本。判据很直白：数一数你的数据被几个引擎读过，答案是一，就不必付这笔钱。

这条失效点还有一个不常被提到的触发方式：**第二个引擎只是「有」，但不是「真的在跑」**。团队为了将来的流式需求提前接入 Flink、为了将来的 ML 提前接入 Spark，两份作业各跑一个 demo 就停了。此时表格式的成本是全额的（catalog 要维护、文件要 compact），而共享的收益从未产生，因为两份作业读的其实是同一份被复制过的数据。判断方法是看**同一份表在几个引擎上产生了实际的计算量**，而不是看接了几个 connector——前者可以在各引擎的账单或计算日志里数出来。

#### 7.3.3 语义的物化位置：表结构 vs 指标平台 vs 看板 SQL

**机制是什么**：「一行代表什么」（粒度）和「这个数怎么算」（口径）是两件事。粒度可以写在表结构里，口径则必须被物化成一个**可被引用的对象**，否则它只能存在于写 SQL 的人的脑子里。

**它在各候选中的实现差异**：

| 候选 / 形态 | 口径存在哪 | 消费方怎么拿到它 |
| --- | --- | --- |
| 云原生声明式栈 | dbt 项目里的指标 / 语义定义，随代码走 | 下游工具读项目产物 |
| 一体化商业平台 | 平台的指标平台对象（原子指标 + 派生指标） | BI 与 API 通过指标平台查询 |
| Databricks 一类湖仓平台 | catalog 中的表与语义能力之上 | 助手 / BI 通过 catalog 读取 |
| 自研 / 自建栈 | 最常见的形态是散落在各看板的 SQL 里 | 各自重写 |

**由此必然导出的性质**：因为口径被物化成带 `metric_id`、口径、时间周期、维度与 Owner 的对象，所以 BI 与 Agent 可以引用**同一个定义**而不是各自重写；代价是每新增一个度量都要走一次定义与签署流程，口径补齐变成持续人力——[§ 3.4](12-hands-on-section-3-sec3.md) 组合三把「口径补齐需要持续人力」列为该组合的运维代价。

反过来，因为口径散在看板 SQL 里时没有任何机制强制它唯一，所以同一个「成交」可以同时存在二十种算法而无人知道——[§ 6](12-hands-on-section-6-sec6.md) 的订单域案例正是从这个起点出发的；代价是 AI 取数把这个分裂从后台搬到前台：每次生成的 SQL 都不完全一样，而使用者看不出差别（[§ 3.5](12-hands-on-section-3-sec3.md) 的「缺乏 AI 集成」反模式）。

需要把**语义层**与**指标平台**分开看，因为它们在同一个组合里承担不同职责（[§ 3.4](12-hands-on-section-3-sec3.md) 组合三里两者同时出现）。语义层是查询时的翻译：它把「GMV」这个说法翻译成一段 SQL，定义仍然可能写在代码或配置里；指标平台是**物化的对象**：每个指标有 `metric_id`、时间周期、维度、公式与 Owner，可以被引用、被签署、被审计。前者解决的是「同一句话被翻译成同一段 SQL」，后者解决的是「这个数由谁负责、口径何时改过」。因为这两件事的失败模式不同——前者错在翻译、后者错在无人负责——所以只上其中一个通常不够：只有语义层，口径改了没人知道；只有指标平台，取数入口仍然各自写 SQL。

**公开证据**：[§ 4.4](12-hands-on-section-4-sec4.md) 给出 OSCAR 模型的指标定义示例（metric_id / 指标类型 / 原子指标 / 时间周期 / 维度 / 公式 / Owner / SLA），其字段构成可直接核验【公开，本仓库主文件 § 4.4】；「无 Owner 禁止发布」与分层命名规范见 [§ 6 落地实践](12-hands-on-section-6-sec6.md)【公开，转引本仓库案例】。

**失效条件**：当**度量数量还很少、消费方只有人**时，指标平台的固定成本高于收益。[§ 3.3](12-hands-on-section-3-sec3.md) 给的判据是「同一问题换三种问法，答案与口径是否一致」——答得一致，说明口径还没有分裂，不必上；答得不一样，再上也不迟，因为此时你至少知道要统一的是哪几个。

反过来的失效条件同样存在，而且更常见：**组织以为上了指标平台，口径就统一了**。平台提供的是「唯一的位置」，不是「唯一的内容」——把二十种算法登记成二十个指标，口径并没有收敛，只是从散落在看板里变成整齐地散落在平台里。判据仍然是那一条：同一问题换三种问法，答案是否一致。若答案一致但走向不同（一个查平台、一个查看板），说明位置还没统一；若答案本身就不一致，说明内容没统一——两者的修法完全不同。

#### 7.3.4 AI 能力挂在哪一层：底座 vs 底座之上的助手

**机制是什么**：平台的底座能力（元数据、血缘、调度、表格式）与它之上的生成式能力是两件事，各自有不同的成熟度与不同的失败模式。

**它在各候选中的实现差异**：入口名各不相同——DataWorks 的 AI 助手、Databricks 的 Assistant、Snowflake 的 Cortex 系列、dbt 侧的 codegen + LLM（[§ 5](12-hands-on-section-5-ai.md) 的 5.1 表逐项列出）。用词必须分清：**那是能力，不是产品名**；自然语言生成 SQL 在各平台的入口、函数名与支持方言都不一样。

**由此必然导出的性质**：因为生成式能力读的是底座里的元数据完备度，所以同一句「查上季度 GMV」在有注释、有唯一口径、有权限边界的库里能用，在欠账的库里不能用——**AI 不会补齐底座的欠账，只会把欠账的后果搬到前台**。这是 [§ 3.5](12-hands-on-section-3-sec3.md)「缺乏 AI 集成」这条反模式的机制表述：收益不落在建模团队，而「不做」没有当期代价，于是欠账一直留着。

进一步，因为把 L2 / L3 能力设成核心依赖（唯一入口、写进数据契约、为它预留 schema 字段）等价于**已经把它当成 L1 用**，所以一旦该能力变更或退化，你的架构被迫跟着改；代价是留给自己的自由度被提前消耗——[§ 5](12-hands-on-section-5-ai.md) 的 5.1 把这句话写成「一旦你在 schema、存储或流程里为它留了位置，就等于已经把它当成 L1 了」。

判断一个平台的 AI 能力到底该放到什么位置，有一个可当场执行的办法：**从你最近一个月的取数需求里挑一批（二十条量级即可）真实的，让它在你的库里跑一遍，记录「生成即可用」「改一处即可用」「完全不可用」各占多少**。这三个数分别对应三种规划动作：第一类多，可以设成推荐入口；第三类多，说明它当前只能用来生成草稿；而如果三类都没有出现（即你根本没测过），那么任何关于「AI 能力」的判断都只是演示印象。这个测试不需要平台配合，也不需要采购决策——它测的是你自己的元数据完备度，而那才是决定结果的变量。

**公开证据**：[§ 5](12-hands-on-section-5-ai.md) 的分级表逐条给出三个判据（有没有正式 release note、有没有第三方非厂商的公开生产案例、接口是否稳定）与每项的「现在该做什么」；该表里唯一够得上 L1 的是表格式与平台底座，而那一项与 AI 没有直接关系【公开，本仓库 § 5】。

**失效条件**：当**底座元数据已经完备、口径已唯一、权限边界清晰**时，AI 入口的收益才真正落在交互成本上。如果期待的是「数据架构升级」，那是它没有承诺过的事——[§ 5.2](12-hands-on-section-5-ai.md) 的判断是：这些方向改变的是这些产物**由谁、以什么成本生产出来**，收益上限就是生产环节的人力成本。

把这一条反过来读，就是本节的选型建议：**先把收益上限已经被确认的那部分拿走**。元数据补齐、口径唯一、权限清晰这三件事，在任何一族平台上都能做、也都要做，且它们的收益不依赖你选了哪一族；而这件工作做完之后，AI 入口能不能用，就是一个可以当场测出来的事实，不再是一个需要争论的判断。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
总拥有成本 ≈ 平台 / 许可固定成本
           + f(存储量, 保留期, 介质)
           + g(计算用量, 计费单位)
           + h(元数据对象数, 血缘与目录查询量)
           + i(常设运维人力)      ← 与数据规模无关，与「族」强相关
           + j(迁移与锁定成本)
```

**一体化商业平台**：主导项是 `g`——按扫描量或按算力单元计费，随查询模式与并发增长；`h` 随表数增长（血缘与目录查询本身也吃资源）。隐性项是 `j`：生态绑定之后议价空间收窄，跨云出网成为新成本。`i` 相对低，因为 compaction、catalog 这类常设项由平台承担。

**云原生声明式栈（dbt + 托管数仓）**：主导项是 `g + f`。隐性项是仓库的最低计费粒度与出网费——「仓库一直开着是否在花钱」取决于该厂商的计费粒度，这个数必须按你自己的厂商价目页核算（以官方价目页当前版本为准）。`i` 低，但有一个容易漏的项：dbt 项目本身的测试与文档维护是活，它随模型数增长。

**表格式自建栈**：主导项是 `i`（定员）与 `f`（对象存储）。隐性项是 compaction 与小文件治理消耗的算力与人力、以及 catalog 的高可用。`i` 随表数与写入频率增长，而且**不能被弹性扩容替代**——它是人的时间。[§ 3.4](12-hands-on-section-3-sec3.md) 组合三把这三项列为常设作业。

**自研中台**：主导项是 `i`，且是最大的一项；`j` 最高——没有外部生态可迁移，替换等于重写，因此它只能作为「组织愿意长期养平台团队」这一前提下的选项。

这张成本函数真正有用的地方，是它能告诉你**优化顺序**：先动主导项。若 `i` 是主导项（自建栈、自研中台），那么每一次「先把工具补齐」的采购都会让总成本上升，因为 `i` 会随工具数增长；此时把表数压下来、把 compaction 自动化，比换一个更贵的平台更有效。若 `g` 是主导项（一体化平台、托管数仓），那么优化重点在查询画像——最贵的查询是什么形态、能不能被分区裁剪掉——**这与平台选型无关，任何平台上都成立**。

【经验】关于门槛量级的一条判断：多数组织在核心表规模处于千级、且有 2–3 人能认领治理工作时，自建栈的 `i` 与一体化平台的 `g + h` 处在同一量级，选族不会产生决定性的成本差；超过这个规模之后，`i` 通常按表数与写入频率继续增长，而 `g` 只按查询量增长——**两条曲线的斜率不同，这才是规模变大后该重新评估的原因**。这里的规模数字是量级描述而非精确门槛，请用你自己的人员时间账本校准。

**【推算】对象存储的量级**：按 10 TB 冷数据、对象存储标准层（取 S3 标准层计，$0.023/GB-月）推算，年存储成本约 $2.8k（推导链：10 TB = 10,240 GB；10,240 × $0.023 ≈ $236/月；× 12 ≈ $2.8k/年）。换到低频或归档层，单价可低一个量级，但取回费与取回延迟是新增项——把冷数据的**取回频率**乘上取回单价，才是可比的数（单价与取回规则以各厂商官方价目页当前版本为准）【推算】。

**一个可自行核验的判据**：把你五个最贵的查询各自跑一次，量出扫描量或算力单元消耗，再乘上单价与月次数——这个数落在 `g` 里，是计费单位决定的部分；它和 `i` 谁是主导项，直接决定你该先优化查询还是先招人。

成本函数里最容易漏掉的一项是 `h`——**元数据对象数**。血缘、目录与权限查询看上去是「查元数据」，但它们消耗的是与数据查询同一批资源：血缘要递归展开下游、目录要全文检索、权限要在每次查询前判定。所以在表数量进入万级（【经验】量级：与 [§ 3.3](12-hands-on-section-3-sec3.md) 判据表、[§ 3.6](12-hands-on-section-3-sec3.md) 跃迁表用的是同一批量级阈值，用于区分档位而不是精确门槛）之后，一个冻结了半年、没人写入的表仍然会持续贡献 `h`，因为它的血缘与权限条目每天都被查询。这一项与前几项的区别在于：**它不随你的业务量变化，只随表的存量变化**，因此清理僵尸表在成本上是双重收益——既省存储，也省 `h`。

### 7.5 决策树（每个分支都要有阈值依据）

```
N1 数据与团队能否离开当前云？（合规 / 数据出境 / 信创要求）
├─ 不能 → 选该云的一体化商业平台（DataWorks 系 / 字节系 / 华为 DAYU 系 / 腾讯 WeData 系 / Azure 上的 Microsoft Fabric）
└─ 能
   N2 有没有 ≥ 3 人能长期专职维护平台底座（catalog、compaction、血缘、调度）？
   ├─ 没有 → 云原生声明式栈（dbt + 托管数仓）或托管湖仓（Databricks + Unity Catalog）
   └─ 有
      N3 是否有第二个引擎真的需要读同一份数据（流 / ML / 多引擎）？
      ├─ 没有 → 停在这里：不要上开放表格式（成本照付，共享的收益无人消费）
      └─ 有 → 开放表格式自建栈（Iceberg / Hudi / Paimon + Spark + Flink + dbt）

N4 消费方是否含 Agent，且要求同一问题答案可复现？（与 N1–N3 的结果正交，走到哪个终点都要问一遍）
├─ 是 → 先补语义层 / 指标平台，再谈平台选择——它不改变上面已经选定的族
└─ 否 → 直接执行上面得到的结论
N5 AI 需求强，是否意味着现在就把生成式能力设成核心依赖？
├─ 是 → 不建议：L2 / L3 能力不能设成唯一入口
└─ 否 → 让它只落在「模型已定、只差落 DDL / SQL」的环节，用评审通过率与人工修正量验收
```

**阈值依据**：

这棵树的读法是自上而下的**排除法**：N1 与 N2 是淘汰项（不符合就出局），N3 是「不要多做」的停止项，N4 与 N5 是「先做另一件事」的排序项。原表按云厂商分支（阿里云 / AWS / Azure / 多云 / 自建）、按团队工程能力（强 / 中）分支、按 AI 需求（强 / 中）分支——这三条恰好对应这里的 N1（云与合规）、N2（工程能力）、N5（AI 需求）。本节把「云厂商」这一支换成了「能不能离开这朵云」，因为它才是那条分支真正在问的问题：选阿里云或 AWS 不是偏好，是合规、存量与团队技能的约束结果，而这些约束一旦成立，分支就没有选择余地。

两点使用上的提醒。第一，**树只做排除，不做推荐**：三个候选族都通过之后，剩下的选择取决于同族内部那三件事（合规资质、计价单位是否同构、生态接入成本），而它们不是机制问题，是采购与组织问题，本节不替你做这层判断。第二，**阈值是量级不是门槛**：N2 的「3 人」与 7.4 里的规模量级（表数量千级 / 万级，其依据就在 7.4）都用来区分「这一档」与「那一档」，实际取值请用你自己的排期积压、人时账本与表数量去校准；把量级当门槛用，会在边界上产生大量无意义的争论。

- **N1（合规与数据出境）**：这一类是**硬约束**，它排除整族方案，讨论性价比之前就得先过关。它与容量规划里「先问数据能不能动，再问哪家便宜」是同一条判据的应用；约束的强弱随行业与地域变化，具体口径请以当期监管要求与你的合规团队判断为准【经验】。
- **N2（≥ 3 人专职）**：开放表格式的常设运维项包括 compaction、文件布局与小文件治理、catalog 高可用、以及各引擎能力差异的补丁；这些是**每周都要有人做**的工作，不是一次性建设。低于这个量级时，这些作业会长期排在在线需求之后，表现为读放大与查询变慢。这是一个【经验】量级判断，取值请用你团队自己的排期积压情况校准，不是精确门槛。
- **N3（有没有第二个引擎）**：[§ 3.3](12-hands-on-section-3-sec3.md) 的原话是「表格式解决的是共享与演进，它不解决粒度与口径」。只有一个引擎读时，「共享」这项收益为零，而 compaction 与 catalog 的成本照付。这是 yes/no 判据，不需要阈值。
- **N4（消费方是否含 Agent）**：判据取自 [§ 3.3](12-hands-on-section-3-sec3.md) 模式选择决策表中「消费方含 Agent、要求答案可复现」那一行（该表第 4 行）的关键判据——「同一问题换三种问法，答案与口径是否一致」。答不一致，说明口径已经分裂，此时换平台不会让答案一致，因为没有唯一口径可被引用。
- **N5（AI 需求的强度）**：判据是 [§ 5](12-hands-on-section-5-ai.md) 的三条（正式 release note、第三方非厂商公开生产案例、接口是否稳定）三条全中才是 L1；该表里 AI 方向无一够 L1。因此「AI 需求强」不构成把它设成核心依赖的理由，只构成试点它的理由。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 阿里云上的中大型互联网（离线 + 实时 + 治理一体） | DataWorks + MaxCompute + Hologres | 表格式自建栈 + dbt | 自建栈要自带 compaction 与 catalog 运维，且实时与离线的口径要自己对齐 |
| 海外 / 跨云 / 现代化数据栈 | dbt + Snowflake / BigQuery + Airflow + DataHub | Databricks + Unity Catalog + dbt | 一体化平台的跨云与出网成本更高，且模型不在版本控制里 |
| AI 优先 / 智能体平台 | Databricks + Unity Catalog + dbt | DataWorks 全家桶 + PAI | 后者在跨云与多引擎共享上受限，而 Agent 取数往往要跨多个引擎 |
| Azure 生态、以 Power BI 为主要消费入口 | Microsoft Fabric（OneLake + Power BI） | Databricks on Azure + Unity Catalog + dbt | Databricks 一侧 BI 与湖仓分属两件产品，跨产品的元数据与权限要自己接；Fabric 一侧的代价是把消费入口绑在自家 BI 上 |
| 自建 / 跨云 / 有平台团队 | Iceberg / Hudi / Paimon + Spark + Flink + dbt | Databricks | 托管平台把布局与调优的一部分收走，但把定价权也一并收走 |
| 国产化合规 + AI 增强 | DataWorks 底座 + 自研 LLM 取数入口 | 华为 DAYU / 腾讯 WeData | 合规是硬约束，海外栈在这一条上直接出局 |
| 政企 / 传统行业（团队工程能力中等） | 云厂商一体化平台（含 DAYU 一类政企向产品） | 表格式自建栈 | 自建栈的常设运维项需要专职人手，政企团队通常不具备 |

表里的「备选」一列不是次优解，而是**另一种代价结构**。同一个场景在两族之间摇摆，通常说明两种代价在你的处境里正好相等：一体化平台的代价是迁移与出网，自建栈的代价是常驻人手。哪一边更贵，取决于两件可以量化的事——你未来两年会不会真的换云（会，则迁移代价会兑现），以及你团队目前有没有排不进队的基础设施需求（没有，则人手的边际成本低）。这两问都不需要平台知识，只需要组织事实。

**五个常见组合，以及各自承担的职责边界与运维代价**：

1. **DataWorks + MaxCompute + Hologres**（阿里云生态）。DataWorks 负责建模、调度与治理，MaxCompute 承担离线，Hologres 承担实时查询，Quick BI 与 PAI 负责消费与模型。职责边界：口径由平台的指标对象唯一持有，实时与离线各自物化。运维代价：跨引擎同步链路的一致性要长期有人盯——Hologres 与 MaxCompute 之间的一致不是自动的，它是一条需要被监控与校验的链路。适用：阿里云上的中大型互联网企业。

2. **dbt + Snowflake + Airflow + DataHub**（海外云原生）。dbt 管建模与口径（模型即文件），Snowflake 管计算与存储，Airflow 管调度，DataHub 管目录与血缘。职责边界：dbt 不做调度、Airflow 不做语义、DataHub 不只服务一个工具（血缘以 API 形式被多处消费）。运维代价：四件东西的元数据要互通，否则血缘会在工具边界断一次——而影响面分析一旦在边界断掉，就不再完整。适用：海外 / 跨云 / 现代化数据栈。

3. **Databricks + Unity Catalog + dbt**（AI 优先）。Databricks 承担湖仓一体，Unity Catalog 承担跨工作区的目录与权限，dbt 承担建模。职责边界：catalog 是权限与发现的唯一入口，dbt 只写在它管辖的表上。运维代价：Delta 的 compaction 由平台承担一部分，但分区策略与表布局仍要有人负责，否则读放大照旧积累。适用：AI 团队 / 智能体平台。

4. **Iceberg + Spark + Flink + dbt**（湖仓开源）。表格式让批（Spark）与流（Flink）读同一份数据，dbt 在批侧建模。职责边界：表格式管共享，dbt 管粒度与口径，catalog 管发现。运维代价：compaction、小文件治理、catalog 高可用三项都是常设作业。适用：自建 / 跨云 / 有平台团队的大数据组织。

5. **DataWorks + 自研 LLM 集成**（国产化 + AI）。DataWorks 做底座，自研 LLM 做取数入口。职责边界：LLM 只做翻译，不做定义——口径来自平台的指标对象。运维代价：模型调用成本要单独归口，且必须把「这次回答用了哪个口径」作为可复核的输出，否则错误口径会被放大（[§ 5.2](12-hands-on-section-5-ai.md) 的模式对每个方向都是同一句：收益上限是生产环节的人力成本）。适用：国产化合规 + AI 增强。

五个组合共享一条纪律（[§ 3.4](12-hands-on-section-3-sec3.md)）：**链路上每一跳只解决一个问题**。组合一里同步链路不管语义，组合二里 dbt 不管调度，组合三里 catalog 不管业务口径，组合四里表格式不管粒度。把两个问题的责任压到同一层上，那一层会先崩。

把五个组合的运维代价放在一起看，会发现它们其实是同一种代价的五个变体：**一份需要在两处保持一致的元数据**。组合一是「MaxCompute 与 Hologres 的口径要一致」，组合二是「dbt 与 DataHub 的血缘要接得上」，组合三是「dbt 建的表与 catalog 的权限要同一套」，组合四是「表格式里的文件与 catalog 里的条目要同步」，组合五是「LLM 引用的口径与指标平台的定义要同一份」。因此选组合时有一个通用问题可以问：**这套组合里，哪两份元数据需要保持一致？谁来保证？** 答不上来，说明这份一致性目前靠人的自觉在维持，它会在下一次组织调整时断掉。

### 7.7 选错的代价与迁移成本

**反模式：工具堆砌（选型形态）** —— 症状：没有先分族就逐项采购，同一个能力上叠了 2–3 个工具，而且这几件分属不同族（平台的调度 + 云原生栈的建模 + 自建栈的表格式同时在场）→ 后果：回到 7.4 的成本函数，它同时抬高 `h` 与 `i`——每件工具各存一份不完整的血缘、目录与权限条目（`h` 随工具数叠加），每件工具又都要有人认领（`i` 随之增长），而 `g` 一分不省，因为三族的计费单位在这套混搭里并存 → 正确做法：先分族（7.2），族内选定一件，再用**一条端到端链路**验收（源 → ODS → DWD → DWS → ADS → 指标），链路上每一跳只有一个工具。它在建模侧的完整形态（成因与修法）见 [§ 3.5](12-hands-on-section-3-sec3.md) 的「工具堆砌」一行；本节给的是它在成本函数里的落点。

**反模式：把「选存储格式」当成「选建模范式」** —— 症状：上了 Iceberg / Hudi / Paimon，就认为建模问题解决了 → 后果：表格式解决共享与演进，不解决粒度与口径，结果是「能被更多引擎读到、但没有任何一张表能回答一行代表什么」的更贵的数据沼泽；而迁移与 compaction 的成本已经先发生，欠账要在已经承载生产查询的湖面上改 → 正确做法：先做业务过程 × 维度矩阵（[§ 6](12-hands-on-section-6-sec6.md)），再据此决定存储格式，而不是反过来。

**反模式：为 AI 入口提前预留位置** —— 症状：在 schema、存储或流程里为某个 L2 / L3 能力留了位置，甚至把它设成唯一入口 → 后果：等价于已经把它当 L1 用，一旦该能力变更或退化，架构被迫跟着改；而底座（元数据、血缘、口径）的欠账一分未还 → 正确做法：L2 只做 PoC 且不设唯一入口，L3 只记录，先把元数据与口径补齐。

这三条反模式共享同一个结构：**它们在采购或验收环节都能通过，只有在下游取数的人那里过不去**。工具堆砌的验收标准是「覆盖了几项能力」，把存储格式当建模范式的验收标准是「用了开放表格式」，为 AI 留位置的验收标准是「有了生成式入口」——三条都不是「一个具体问题被回答了没有」。因此它们有一个统一的诊断方法：**把某一项拿掉，问谁会立刻知道**。没人会立刻知道的那一项，就是当时为了评审好看而加上去的。

还有一个更隐蔽的变体值得单列：**把任何一份「推荐顺序」当成结论**（包括本节 7.6 矩阵里的「首选」一列）。工具选型不存在通用顺位，任何一个排序都是某个权重下的产物，而权重是评审的偏好。真正可复用的只有判据与机制：**声明写在哪、布局由谁定义、门禁与变更粒度是否匹配**。把这三条核对一遍，你的结论自己会浮出来，而且它不会因为下一年有人换了权重而失效。

**换一个方案要动什么**（工作量量级为【经验】估计，用于排期而不是精确工时）：

| 换成 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 一体化平台 → 表格式自建栈 | 中（导出并重建元数据与权限） | 高（方言差异是最大的一项） | 高（catalog、compaction、调度全要建） | 高 |
| 表格式自建栈 → 托管平台 | 中高（存储出口费与停机窗口） | 中 | 低（平台接管大部分常设项） | 中 |
| 托管数仓 A → 托管数仓 B | 中（出网费与双跑窗口） | 中高 | 低 | 低 |
| dbt 项目内换数仓后端 | 中（适配层改写） | 低（模型本身是 SQL 文件） | 低 | 低 |
| 换 AI 取数入口 | 无 | 低 | 低（但验收口径要重建） | 低 |

这张表里最值得注意的一行是最后一行：换 AI 入口的迁移成本几乎为零，**因为它本来就不该被依赖到有迁移成本的程度**。凡是迁移成本为零的组件，也意味着它没有为你建立任何结构性优势——把资源投在迁移成本为零的地方，收益上限就是省下的人时。

迁移成本还要分**一次性**与**持续**两类，它们的可比性完全不同。数据搬迁、查询改写、团队再学习都是一次性的：做完就结束，可以按项目立项、按季度摊销。而跨云出网费、被锁定的计价单位、以及「每个引擎各备一份运维人力」是**持续的**：它们不会随时间消失，还会在每一次议价与每一次扩容里重复出现。选型时最容易犯的错，是把两类成本放进同一张表比较总和——持续项应当被折算成年度值再比较，而一次性项只应该问「这笔钱现在拿不拿得出来」。

还有一类成本既不是一次性的也不是持续的，而是**只在切换的那一刻发生的隐性损失**：切换之后，团队对旧栈的肌肉记忆归零，值班时能凭直觉定位的那批问题不再能凭直觉定位。它没有出现在任何账单上，但它会在切换后的第一个季度里以故障时长的形式出现。判断方法是问一句「上一次我们的值班同学，是靠仪表盘还是靠熟悉度解决的」——答案若是后者，这笔损失就有量级。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 合规不许数据离开当前云 | 该云的一体化商业平台 | 硬约束排除整族方案，性价比讨论在此之前没有意义 |
| 没有专职平台团队 | 云原生声明式栈或托管湖仓 | 开放表格式的常设运维项（compaction、catalog）无人认领时只会积累 |
| 有平台团队、且真有第二个引擎要读同一份数据 | 表格式自建栈 | 共享是表格式唯一的正收益来源，副本数降为 1 才值这份运维 |
| 有平台团队、但只有一个引擎 | 托管数仓或一体化平台 | 表格式的成本照付、优势无人消费 |
| 消费方含 Agent、要求答案可复现 | 先补语义层 / 指标平台，平台选择排在后面 | 没有唯一口径可引用时，换平台不会让答案一致 |
| 想用生成式能力做核心入口 | 改成试点，用评审通过率验收 | L2 / L3 能力设成唯一入口等价于把它当 L1；AI 不补底座欠账，只放大欠账的后果 |
| 模型散在看板 SQL 里、口径不止一份 | 先把口径物化成带 Owner 的对象 | 口径的分裂在 AI 取数下会从前台可见变成不可见 |
| 离线与实时由两个引擎承担 | 明确一致性由「同步链路」保证，并为这条链路配监控与校验 | 双引擎形态的一致性责任在链路层而不在存储层，不监控就不会被发现 |
| 表数量还在千级、团队也没有平台人手 | 不要为「以后会变大」提前上自建栈 | 自建栈的常设运维项从第一天就开始计费，而它的优势（多引擎共享）此时无人消费 |
| 正在两份打分表之间犹豫 | 换成核对三条机制：声明写在哪、布局由谁定义、门禁粒度是否匹配 | 排序结果主要由权重驱动，核对机制得到的结论不随权重改变 |
| 想为「以后可能的多引擎」提前上开放表格式 | 等第二个引擎产生真实计算量再上 | 提前上的成本从第一天全额计费，而共享的收益要等到那一天才出现 |
| 不确定该信任哪一家的成本说法 | 用自己最贵的五个查询与真实表数量算一遍 `g` 与 `h` | 公开材料给的是结构与规则，不是你的负载在同一结构下的账单 |

> 本节小结：本主题的对比里，真正起决定作用的只有一条差异——**粒度与口径的声明写在哪、由什么机制守护**。它同时决定了三件事：变更成本有多高（影响面能不能在提交前算出来）、AI 取数能不能成立（有没有唯一的定义可被引用）、以及换一个平台到底要重做多少（声明是文件还是平台里的对象）。易用性、成本、生态这些维度都是它的下游变量：它们随你的规模与组织形态移动，而这一条不随任何东西移动。
>
> 补一句关于「便宜」的判断：三个族里没有哪一族是长期最便宜的。一体化平台把常设运维项收进了订阅费，云原生栈把它收进了更少的人手，自建栈把它收进了你自己的值班表——**同一笔成本只是换了记账科目**。因此凡是看到「某族总成本更低」的结论，先问它把哪一项漏在了账外；把漏掉的那项补回去，多数时候三族会回到同一个量级，剩下的差别回到机制上。
>
