## 6. 落地实践

### 6.1 某电商"**维度建模实操：从 0 到 1 建订单域**"（2020-2024）

**背景（Why）**

该电商 2020 年面临**订单域建模混乱**：
- **10 亿+ 订单**——**没有统一的事实表**
- **口径分裂**——**"成交"有 20 种算法**
- **业务方查数**——**每次要 3 天**

**触发点（What）**

2020 年该电商启动**订单域维度建模实操**（[案例 2020]），目标：
- **1 张事实表**——**订单粒度唯一**
- **5 个一致性维度**——**用户 / 商品 / 商家 / 门店 / 时间**
- **口径统一 95%**

**详细做法（How）**

该实操的**5 大核心组件**：

1. **三步定粒度（核心创新）**
   - 关键设计：**先问"一行代表什么"，再建模**
   - 关键能力：**把返工挡在建表之前**——粒度是事实表的唯一主张，写在建模文档第一行才能被评审；等到下游表铺开后再发现粒度错了，只剩推倒重来一条路
   - 关键数字：**1 行 = 1 个订单商品行**
   - 关键示意：
     ```sql
     -- 第 1 步：声明粒度（写在建模文档第一行）
     -- 事实表粒度 = 订单商品行（order_id + sku_id）
     CREATE TABLE dwd_trade_order_item (
       order_id      STRING  COMMENT '订单号',
       sku_id        STRING  COMMENT '商品 SKU',
       order_sk      BIGINT  COMMENT '订单代理键',
       user_sk       BIGINT  COMMENT '用户代理键 → dim_user',
       sku_sk        BIGINT  COMMENT '商品代理键 → dim_sku',
       shop_sk       BIGINT  COMMENT '商家代理键 → dim_shop',
       date_sk       INT     COMMENT '日期代理键 → dim_date',
       pay_amount    DECIMAL(18,2) COMMENT '支付金额（可加）',
       discount_amt  DECIMAL(18,2) COMMENT '优惠金额（可加）',
       is_refund     TINYINT COMMENT '是否退款（不可加，需计数）',
       dt            STRING  COMMENT '分区'
     );
     ```

2. **一致性维度（核心）**
   - 关键设计：**5 个维度全局唯一，代理键统一**
   - 关键能力：**跨主题可 join**
   - 关键数字：**5 维**

3. **总线矩阵（核心）**
   - 关键设计：**业务过程 × 维度矩阵**
   - 关键能力：**业务过程与维度配没配齐一眼可见**——矩阵里任一空格都对应一个「这个口径算不出来」的缺口，评审时按空位补维度，而不是等上线后被业务问住
   - 关键数字：**100% 覆盖**

4. **SCD Type 2（核心）**
   - 关键设计：**商品类目 / 用户等级拉链**
   - 关键能力：**属性改动后历史事实仍按当时的取值归因**——拉链存的是属性的生效区间而非当前快照，类目调整不会连带改写过去的账
   - 关键数字：**0 归因错误**

5. **三层校验（核心创新）**
   - 关键设计：**行数校验 + 金额校验 + 主键唯一校验**
   - 关键能力：**三类错误各有对应的一道校验兜住**——行数不齐、金额不平、主键重复分别能被单独定位，剩下真正查不出的才需要人工介入
   - 关键数字：**3 类校验**

**该电商订单域建模关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**事实表**」** | 20 张散表 | 1 张统一 | **-95%** |
| **「**口径统一**」** | 40% | 95% | **+138%** |
| **「**查数时间**」** | 3 天 | 30 分钟 | **-99%** |
| **「**查询 P99**」** | 10s+ | < 1s | **-90%** |
| **「**归因错误**」** | 基线 | 0 | **-100%** |
| **「**新主题接入**」** | 3 个月 | 2 周 | **-83%** |
| **「**存储成本**」** | 基线 | -40% | **-40%** |
| **「**5 维一致性**」** | 未建设 | 已覆盖 | **新增能力** |

**具体数字（How much）**

- 团队规模：该电商数仓团队 30+ 人
- 关键数字：**10 亿+ 订单**；**口径 95%**；**查数 -99%**
- 业务影响：覆盖该电商**全部订单分析**

**失败教训**

- 早期「**先建表后想粒度**」——3 个月后推倒重来，倒逼**「三步定粒度，先写在建模文档第一行」**
- 「**20 张事实表各配一套维度**」——跨主题无法关联、口径各自漂移，倒逼**「5 个一致性维度 + 总线矩阵」**
- 「**维度只存当前值**」——类目调整后历史归因全错，倒逼**「SCD Type 2 拉链」**
- 「**没有质量校验**」——行数与金额对不上只能靠人发现，倒逼**「行数校验 + 金额校验 + 主键唯一校验三层兜底」**

### 6.2 某银行"**Data Vault 实操：从 5 套到 1 套**"（2019-2024）

**背景（Why）**

该银行 2019 年面临**5 个业务条线各建数仓**：
- **5 套独立数仓**——**存储 5 倍**
- **客户 ID 各异**——**跨条线分析做不了**
- **审计要求**——**历史必须可回溯**

**触发点（What）**

2019 年该银行启动**Data Vault 实操**（[案例 2019]），目标：
- **5 套→1 套**
- **Hub（客户）唯一**
- **Effectivity Satellite 支持审计**

**详细做法（How）**

该实操的**5 大核心组件**：

1. **先 Hub 后 Link 后 Satellite（核心创新）**
   - 关键设计：**严格按 Hub → Link → Satellite 顺序建**
   - 关键能力：**顺序错了就要反复重建**——Hub 只留业务键、Link 只留关系，先把骨架钉死，Satellite 的增删属性才不会牵动前面两层
   - 关键数字：**0 返工**
   - 关键示意：
     ```sql
     -- 第 1 步：Hub（只有业务键，无属性）
     CREATE TABLE hub_customer (
       customer_hk CHAR(32)   NOT NULL,  -- MD5(客户号)
       customer_bk VARCHAR(64) NOT NULL, -- 业务键
       load_date   TIMESTAMP  NOT NULL,
       record_src  VARCHAR(32) NOT NULL,
       PRIMARY KEY (customer_hk)
     );
     -- 第 2 步：Link（关系）
     CREATE TABLE link_cust_acct (
       link_hk     CHAR(32)  NOT NULL,
       customer_hk CHAR(32)  NOT NULL,
       account_hk  CHAR(32)  NOT NULL,
       load_date   TIMESTAMP NOT NULL,
       record_src  VARCHAR(32) NOT NULL,
       PRIMARY KEY (link_hk)
     );
     -- 第 3 步：Satellite（属性 + hash_diff 增量）
     CREATE TABLE sat_customer_attr (
       customer_hk CHAR(32)  NOT NULL,
       load_date   TIMESTAMP NOT NULL,
       hash_diff   CHAR(32)  NOT NULL,
       cust_name   VARCHAR(128),
       cust_level  VARCHAR(16),
       PRIMARY KEY (customer_hk, load_date)
     );
     ```

2. **Hash Key 统一（核心）**
   - 关键设计：**32 位 MD5，跨条线一致**
   - 关键能力：**各条线的数据可以分别装载、最后归并**——键的计算规则统一后，每条线不必等别人的主数据先落地就能开工
   - 关键数字：**5 套→1 套**

3. **Effectivity Satellite（核心）**
   - 关键设计：**关系生效区间（effective_from / effective_to）**
   - 关键能力：**「某个时点这笔关系归谁」可以直接查出来**——生效区间把关系的时间维度显式存下来，不必靠操作日志反推
   - 关键数字：**审计可答 100%**

4. **hash_diff 增量（核心）**
   - 关键设计：**只比对变化列**
   - 关键能力：**加载开销只随发生变化的列增长，不随表宽增长**——宽表新增几十个属性列也不会拖慢日常增量
   - 关键数字：**加载 -80%**

5. **5 套→1 套（核心创新）**
   - 关键设计：**5 条线共用 Hub**
   - 关键能力：**不同条线的同一客户能被归并成一个人**——共用 Hub 之后，存储、分析与审计第一次站在同一个客户视角上
   - 关键数字：**5 套→1 套**

**该银行 Data Vault 实操关键数字**（[案例 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**数仓套数**」** | 5 套 | 1 套 | **-80%** |
| **「**存储成本**」** | 基线 | -80% | **-80%** |
| **「**审计可答**」** | 60% | 100% | **+67%** |
| **「**跨条线归并**」** | 人工 | Hash 自动 | **∞** |
| **「**加载耗时**」** | 基线 | -80% | **-80%** |
| **「**新源接入**」** | 3 个月 | 2 周 | **-83%** |
| **「**返工次数**」** | 3 次 | 0 | **-100%** |
| **「**口径统一**」** | 60% | 95% | **+58%** |

**具体数字（How much）**

- 团队规模：该银行数仓团队 50+ 人
- 关键数字：**5 套→1 套**；**审计 100%**；**加载 -80%**
- 业务影响：覆盖该银行**全部业务条线**

**失败教训**

- 早期「**先建 Satellite 后建 Hub**」——顺序颠倒导致反复返工 3 次，倒逼**「严格 Hub → Link → Satellite」**
- 「**Hash Key 截断**」——百万级数据出现碰撞、归并出错，倒逼**「完整 32 位 MD5」**
- 「**漏 Effectivity Satellite**」——审计问「2019 年 3 月这笔业务归属哪个部门」答不出，倒逼**「补 Effectivity Satellite」**
- 「**全列比对做增量**」——每次加载都要比对全部属性列、加载耗时居高不下，倒逼**「hash_diff 只比对变化列」**

### 6.3 某出行"**实时建模实操：Flink 实时宽表**"（2020-2024）

**背景（Why）**

该出行 2020 年面临**实时需求爆发**：
- **千万级订单/日**——**业务要秒级看板**
- **离线 T+1**——**调度决策等不了**
- **实时与离线**——**两套口径不一致**

**触发点（What）**

2020 年该出行启动**实时建模实操**（[案例 2020]），目标：
- **实时宽表**——**Flink 实时 join 维度**
- **口径与离线一致 99%**
- **延迟 < 5s**

**详细做法（How）**

该实操的**5 大核心组件**：

1. **Flink 实时 join 维度（核心创新）**
   - 关键设计：**维度存 Redis，流侧 lookup join**
   - 关键能力：**流里的明细在写出前就补齐了维度属性**——维表以 lookup 方式挂在流上，宽表不必等离线回刷
   - 关键数字：**P99 < 5s**
   - 关键示意：
     ```sql
     -- Flink SQL：实时流 join Redis 维表
     CREATE TABLE dim_city (
       city_id  STRING,
       city_nm  STRING,
       PRIMARY KEY (city_id) NOT ENFORCED
     ) WITH (
       'connector' = 'redis',
       'lookup.cache' = 'LRU',
       'lookup.cache.max-rows' = '100000'
     );
     INSERT INTO dws_order_realtime
     SELECT o.order_id, c.city_nm, o.driver_id, o.amount,
            PROCTIME() AS proc_time
     FROM   dwd_order_stream o
     LEFT JOIN dim_city FOR SYSTEM_TIME AS OF o.proc_time AS c
            ON o.city_id = c.city_id;
     ```

2. **同源同定义（核心）**
   - 关键设计：**同一份指标定义生成离线 SQL + Flink SQL**
   - 关键能力：**看板与报表对同一个指标给出同一个数**——离线与实时共用一份指标定义，差异只可能来自数据延迟，不可能来自算法
   - 关键数字：**99% 一致**

3. **维度缓存（核心）**
   - 关键设计：**LRU 缓存 + 定时刷新**
   - 关键能力：**降低 Redis 压力**
   - 关键数字：**命中率 95%+**

4. **实时宽表（核心）**
   - 关键设计：**dws 实时宽表，供看板直查**
   - 关键能力：**看板直查宽表，不再回退到明细聚合**——查询链路缩短之后，调度决策在分钟内就能看到刚刚发生的经营状态
   - 关键数字：**延迟 < 5s**

5. **状态与 Checkpoint（核心创新）**
   - 关键设计：**RocksDB 状态 + Checkpoint**
   - 关键能力：**Exactly-once**
   - 关键性质：**状态必须外置、并由周期性快照托管**——状态规模已超出堆内存能容纳的量级，只有把状态交给磁盘式状态后端、再做增量快照，Exactly-once 才不建立在「进程一直活着」这个前提上

**该出行实时建模关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**看板延迟**」** | T+1 | < 5s | **-99.9%** |
| **「**口径一致**」** | 85% | 99% | **+16%** |
| **「**维度缓存命中**」** | 不可用 | 95%+ | **∞** |
| **「**Redis QPS**」** | 基线 | -70% | **-70%** |
| **「**状态规模**」** | 不可用 | TB 级 | **∞** |
| **「**Exactly-once**」** | 未建设 | 已覆盖 | **新增能力** |
| **「**调度决策时效**」** | 1 天 | 1 分钟 | **-99.9%** |
| **「**订单规模**」** | 不可用 | 千万级/日 | **∞** |

**具体数字（How much）**

- 团队规模：该出行实时团队 20+ 人
- 关键数字：**延迟 < 5s**；**口径 99%**；**缓存命中 95%+**
- 业务影响：覆盖该出行**全部分钟级决策场景**

**失败教训**

- 早期「**实时离线两套 SQL**」——口径一致率仅 85%、看板与报表对不上，倒逼**「同源同定义：一份定义生成两套执行」**
- 「**每次请求都查 Redis**」——Redis 被打爆、尾延迟失控，倒逼**「LRU 缓存 + 定时刷新」**
- 「**没开 Checkpoint**」——任务一挂状态就丢、重启后数据错乱，倒逼**「RocksDB 状态 + Checkpoint」**
- 「**维度变更不通知流任务**」——维表改了但流侧缓存的还是旧值，倒逼**「缓存定时刷新 + 变更事件驱动失效」**

### 6.4 某 SaaS"**建模治理实操：从沼泽到资产**"（2020-2024）

**背景（Why）**

该 SaaS 2020 年面临**数据沼泽**：
- **1 万+ 表**——**无人知道归谁**
- **僵尸表 60%**——**90 天无人访问**
- **变更事故频发**

**触发点（What）**

2020 年该 SaaS 启动**建模治理实操**（[案例 2020]），目标：
- **Owner 覆盖 100%**
- **僵尸表 -50%**
- **变更事故 -70%**

**详细做法（How）**

该实操的**5 大核心组件**：

1. **Owner 制度（核心创新）**
   - 关键设计：**无 Owner 禁止发布**
   - 关键能力：**表被改坏了知道该找谁**——Owner 是发布的前置条件而不是事后补登记的字段，责任在表诞生的那一刻就绑定到人
   - 关键数字：**Owner 100%**
   - 关键示意：
     ```
     建表审批流：
       表名 + 分层 + 域 + 业务含义 + Owner  ← 缺一项直接拒
     → 上线后 90 天无访问 → 自动通知 Owner
     → 再 7 天无响应 → 标记待下线 → 三封邮件 + 站内信 → 下线
     ```

2. **四步下线（核心）**
   - 关键设计：**标记 → 通知 → 7 天缓冲 → 下线**
   - 关键能力：**下线之前留出通知与缓冲窗口**——冷表在被清掉前有明确的申诉机会，避免把年度报表还在依赖的表当成垃圾删掉
   - 关键数字：**误删 0**

3. **字段级血缘（核心）**
   - 关键设计：**SQL 自动解析生成字段级血缘**
   - 关键能力：**改一个字段之前就能看到谁在用它**——血缘细化到列级之后，改名、改类型不必再靠人肉全库排查
   - 关键数字：**100% 自动**

4. **变更影响面阻断（核心）**
   - 关键设计：**CI 阶段跑血缘影响分析，超阈值阻断**
   - 关键能力：**风险变更在提交阶段就被挡住**——影响面超过阈值时提测直接不通过，而不是等下游报表出错再回头回滚
   - 关键数字：**拦截率 90%+**

5. **分层与命名规范（核心创新）**
   - 关键设计：**ODS/DWD/DWS/ADS 四层 + 强制命名**
   - 关键能力：**找表从翻聊天记录变成按分层与域检索**——命名规则统一之后，表名本身就说明了它属于哪一层、归哪个域
   - 关键数字：**100% 合规**

**该 SaaS 建模治理关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**Owner 覆盖**」** | 30% | 100% | **+233%** |
| **「**僵尸表占比**」** | 60% | 30% | **-50%** |
| **「**变更事故**」** | 基线 | -70% | **-70%** |
| **「**字段级血缘**」** | 未建设 | 已覆盖 | **新增能力** |
| **「**影响面拦截**」** | 0 | 90%+ | **∞** |
| **「**命名合规**」** | 40% | 100% | **+150%** |
| **「**存储成本**」** | 基线 | -35% | **-35%** |
| **「**找表时间**」** | 2 天 | 30 分钟 | **-99%** |

**具体数字（How much）**

- 团队规模：该 SaaS 数据治理团队 10+ 人
- 关键数字：**Owner 100%**；**僵尸表 -50%**；**事故 -70%**
- 业务影响：覆盖该 SaaS **1 万+ 表全部资产**

**失败教训**

- 早期「**无 Owner**」——改坏了没人修、责任无法追溯，倒逼**「无 Owner 禁止发布」**
- 「**僵尸表直接删**」——删掉了年度报表依赖的冷表、引发事故，倒逼**「标记 → 通知 → 缓冲 → 下线四步」**
- 「**只做表级血缘**」——字段改名仍然出事故，倒逼**「字段级血缘 + CI 阶段阻断」**
- 「**命名与分层各行其是**」——表找不到、同类数据散落各处，倒逼**「ODS/DWD/DWS/ADS 四层 + 强制命名规范」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）
