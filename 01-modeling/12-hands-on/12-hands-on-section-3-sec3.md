## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

六个落地方案表面上是六份工具清单（PowerDesigner + Oracle + Informatica / DataWorks + MaxCompute + Hologres / …），但工具是可替换的，真正不可替换的是它们各自对**同一个问题**给出的不同答案：**事实表的粒度在建模流程的哪一步被锁死**。主文件 §6 把这件事写成了一条纪律——"先问『一行代表什么』，再建模"；本节要补的是：这条纪律在不同方案里被放在流程的不同位置，而位置决定了整套工具链的形状。

主文件 §2.2 的工程架构图给了五层：ODS（贴源层）→ DWD（明细层）→ 指标/汇总层（DWS / ADS）→ 数据服务层（OneService）→ 数据消费层（ADS），横向贯穿元数据、血缘、质量、安全与 AI Copilot。注意前四层各自**重新声明一次粒度**：ODS 一行是一条变更记录，DWD 一行是一次业务过程事件，DWS 一行是一个"用户 × 天"的汇总，ADS 一行是一个指标在某维度组合上的值；数据服务层（OneService）不新建粒度，它把已物化的粒度包装成 API 契约（网关 / 鉴权 / 限流），数据消费层（ADS）只消费、不声明粒度。层次本身就是粒度的物化阶梯。

于是本节的核心机制是：**粒度锁得越早，查询越便宜、变更越贵；锁得越晚，集成越稳、查询越贵。** 这句话的因果链很短：分析查询的代价近似正比于"要现场做的 JOIN 与聚合次数"；如果粒度在写入时就已经按访问模式对齐（星型事实表），查询只需常数个 JOIN；如果粒度没有被锁定（3NF 或 Vault 的集成层），每一次查询都要现场推导语义关系，代价随问题复杂度上升。反过来，粒度一旦写进表结构，业务过程一变，结构就得改，历史还得回填——**变更成本与粒度的绑定程度成正比**。

六个方案就是这条曲线上的六个位置：Inmon 把粒度尽量留到逻辑模型里（3NF 保持中性）；Kimball 事前锁死（一行 = 一次业务过程）；Data Vault 刻意推迟（Hub/Link 只存键与关系）；湖仓一体允许多层粒度共存；AI 原生数据栈由消费端反推粒度；数据网格把粒度的决定权交给域。其中**只有数据网格不是由这条曲线决定的**——它由组织边界决定，所以选型时要单独判断（见 3.6 末段）。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 事实粒度在流程哪一步锁定 | 模型变更的影响面有多大 | 「先建宽表，粒度以后再调」——粒度写在结构里，改粒度 = 重做下游全部汇总 |
| 源系统 schema 漂移频率 | 集成层是否必须与源解耦 | 「加了新源只要加几个字段」——字段进了事实表就等于进了粒度 |
| 查询模式（点查 / 扫描 / 聚合 / 实时） | 事实与维度是否必须物理分离 | 「列存够快就不用建星型」——列存降的是扫描成本，不是 JOIN 与推理成本 |
| 历史与更正要求 | 变更是否必须被保留成数据 | 「更新覆盖就够了」——覆盖之后没有任何机制能回答"当时是什么样" |
| 引擎与存储的耦合度 | 是否必须换开放表格式 | 「上了 Iceberg，建模问题就解决了」——表格式解决共享，不解决粒度与口径 |
| 组织边界（域数 / 地域 / 公司边界） | 粒度的决定权归谁 | 「联邦化就是各干各的」——没有契约的自治等于割据 |

有一条约束最容易被低估：**"源系统会不会变"不是一个风险等级，而是一个频率**。源系统一年改一次 schema，维度建模的维护成本可以忽略；一年改几十次，同一套星型每年的重建与回填工作量就足以吃掉整个团队的产能【经验："一年一次 / 一年几十次"是量级上的分界，不是精确阈值，实际取值请用你自己源系统的变更记录统计】。Data Vault 与湖仓一体都是为了应对这个频率而生的，而不是因为它们的查询更快。

### 3.2 模式逐个拆解（核心节）

下面六个方案覆盖原文件列出的全部落地方案。每个都按同一骨架：约束 → 结构 → 机制 → 代价 → 失效点 → 真实使用。

#### 3.2.1 传统数仓（Inmon）

- **被什么约束逼出来**：源系统数量多【经验，量级约几十个】、业务规则尚未稳定、需要企业级"单一事实来源"。此时任何按访问模式定死的粒度都属于过早决策——模型必须能容纳尚未出现的业务过程。
- **结构**：

```sql
-- Inmon 式 3NF：实体与关系分开存，不物化任何访问路径
CREATE TABLE edw_party (            -- 实体：参与方（人 / 组织）
  party_id     BIGINT PRIMARY KEY,
  party_type   VARCHAR(16),
  create_ts    TIMESTAMP
);

CREATE TABLE edw_party_role (       -- 关系：参与方在某语境下的角色
  party_id     BIGINT,
  role_type    VARCHAR(16),         -- 客户 / 供应商 / 员工 …
  valid_from   TIMESTAMP,
  valid_to     TIMESTAMP
);

-- 新增一种业务过程 = 新增实体表或关系表，既有表结构不动
-- 查询侧不假设任何访问路径 → 所有聚合都在查询时现场 JOIN
```

- **为什么这样设计有效**：因为 3NF 把"实体"与"关系"分离、且不为任何访问路径做物化，所以新增业务过程不会改变既有表结构 → 模型能容纳它还未知的用法。这正是"粒度晚锁"换来的东西：**灵活性来自结构的中立性，不来自工具的能力**。
- **代价**：查询侧要付全部的推导成本，一次分析可能要 JOIN 十几张表；EDW 与部门集市之间必须物化，物化链长、依赖深，端到端延迟由最长链决定；建模人必须同时懂业务与范式理论，这类人难招也难替。粒度的模糊性没有消失，它只是从建模时被推到了每次查询时。
- **失效点**：当访问模式以"按维度任意组合聚合"为主、且并发查询多时，「零冗余」反转成「每次查询都重算连接」；因为 3NF 不为任何一条访问路径做物化，团队会被迫不断往中间加汇总表——加到最后，实际形态与星型无异，只是多背了一份 3NF 的维护成本。此时"企业级一致"换来的中立性已经没有任何查询在消费它。
- **真实使用**：Bill Inmon 的《Building the Data Warehouse》1992 年首版系统论述了这一方法【公开，著作；具体版次以出版信息为准】。这一代的常见组合是商业建模工具 + 关系型数仓 + 商业 ETL 工具（PowerDesigner + Oracle + Informatica 一类）【经验】；金融与监管报送场景长期是这一模式的密集区【经验】。

#### 3.2.2 维度建模（Kimball）

- **被什么约束逼出来**：分析访问模式收敛为"按维度组合聚合度量"，且业务过程可以被枚举出来——既然能事先知道怎么查，就值得把粒度在写入时对齐到查询上。
- **结构**：

```sql
-- 维度：属性直接落在维度行上，代理键 + SCD2 区间
CREATE TABLE dim_user (
  user_key       BIGINT PRIMARY KEY,   -- 代理键（事实表只引用它）
  user_id        STRING,               -- 自然键（业务键，仅供追溯）
  user_level     STRING,
  effective_from TIMESTAMP,            -- SCD2：属性变化 = 新增一行
  effective_to   TIMESTAMP,
  is_current     BOOLEAN
) PARTITIONED BY (dt STRING);

-- 事实：一行 = 一次业务过程事件（粒度已在建表时锁死）
CREATE TABLE dwd_trade_order_created (
  order_id     STRING,
  user_key     BIGINT,                 -- 事实表带代理键，不带自然键
  merchant_key BIGINT,
  date_key     INT,
  order_amount DECIMAL(18,2),          -- 度量
  order_count  INT,                    -- 度量（可加）
  dt           STRING
) PARTITIONED BY (dt STRING);
```

- **为什么这样设计有效**：因为维度被"宽表化"（属性直接落在维度行上）、事实只存代理键与可加度量，所以一条分析查询只需要"事实 JOIN 维度"，JOIN 数是常数（等于用到的维度个数，通常远小于表总数），不随模型规模增长 → 查询代价可预测、可容量规划。SCD2 用 `effective_from/effective_to` + 代理键，把"按历史属性归属"从时间推理降级为一次等值 JOIN——这是它能在列存引擎上跑得动的前提。
- **代价**：维度表行数随属性变更累积（每次变化加一行），维度会越长越宽；事实表必须携带代理键，加载时要先做维度查找（lookup），迟到事实还必须按**事件发生时间**匹配历史维度版本而不是当前版本，这一步做错就会静默算错。最关键的一条代价是：**"一行代表什么"必须事前答对**，答错不是改一条 SQL 能补救的，而要重做事实表并回填（主文件 §6 的"三步定粒度，先写在建模文档第一行"就是为这一步设的关卡）。
- **失效点**：当业务过程本身频繁新增或变更时，「查询代价可预测」反转成「模型变更频繁」；因为星型把语义压在表结构里（粒度 + 维度 + 代理键），新增业务过程要建新事实表、新增属性要改维度并回填历史——维护成本与**业务过程的增长率**成正比，而不是与数据量成正比。数据量翻倍对星型毫无影响，业务过程翻倍则要重做一半模型，这是这条失效点最反直觉的地方。
- **真实使用**：Ralph Kimball 的《The Data Warehouse Toolkit》1996 年首版系统论述了该模式【公开，著作】；dbt 官方文档的最佳实践页 "How we structure our dbt projects" 长期建议 staging → intermediate → marts 分层、并把 marts 建成维度模型（即 star schema）【公开，dbt 官方文档，docs.getdbt.com 的 Guides 下即刻可核验；该页为持续更新的活文档，年份以页面当前版本为准】；阿里 OneData 的 ODS/DWD/DWS/ADS 分层与统一指标口径见阿里巴巴数据技术及产品部《大数据之路：阿里巴巴大数据实践》（2017）【公开】——把它读作"星型 + 汇总层"的工程化实现是**本节作者的对照判断，不是该书的表述**【经验】。

#### 3.2.3 Data Vault + 维度建模

- **被什么约束逼出来**：源系统数量多且 schema 漂移频繁【经验，量级为几十上百个源、每年多次变更】、监管要求"任意时点可回看且可追溯变更"。此时既要集成层的稳定性，又要历史本身成为数据——星型做不到后者，3NF 做不到前者。
- **结构**：

```sql
-- Hub：只有业务键 + 加载信息，没有属性、没有语义
CREATE TABLE hub_customer (
  customer_hk   STRING,        -- 业务键的 hash key
  customer_id   STRING,        -- 业务键
  load_ts       TIMESTAMP,
  record_source STRING
);

-- Link：只存关系（键的组合），不存属性
CREATE TABLE link_order_customer (
  order_customer_hk STRING,
  order_hk          STRING,
  customer_hk       STRING,
  load_ts           TIMESTAMP,
  record_source     STRING
);

-- Satellite：属性，每次变化插一行（变更被保留成数据）
CREATE TABLE sat_customer_profile (
  customer_hk   STRING,
  load_ts       TIMESTAMP,
  hash_diff     STRING,        -- 只比对变化列；未变则不插行
  customer_name STRING,
  customer_tier STRING,
  record_source STRING
);
```

- **为什么这样设计有效**：因为 Hub/Link 只存"键与关系"、属性全部下沉到 Satellite，所以源系统新增属性只影响一张 Satellite，Hub/Link 不动 → schema 漂移的影响面被限制在单表之内。同时 Satellite 的追加写让"任意时点的属性值"变成一次范围查询（取 `load_ts ≤ t` 的最新一行），历史重建不需要额外机制——**变更在这里真的是数据**，而不是被覆盖的操作。
- **代价**：表数量膨胀（每个源 × 每个实体一张 Satellite，且 Link 也可能带自己的 Satellite）；查询必须经过下游集市层（Raw Vault → Business Vault → Mart）才有可用语义；纯 Vault 上键是 hash、业务方无法直读。链长与表数是主要运维成本，且这批表的生成通常要自动化——手写几百张 Hub/Link/Satellite 不可持续。
- **失效点**：当团队跳过集市层、让业务方直接查 Raw Vault 时，「加源不改模型」反转成「查不动、看不懂」；因为 Vault 的设计目标被明确限定为集成层的可扩展性——它**用放弃查询友好来换集成稳定**，被放弃的那部分不会由任何工具补回来，只能由集市层补。跳过集市层等于把这份成本转嫁给每一个查询者，且转嫁量随查询数放大。
- **真实使用**：Dan Linstedt 于 1990 年代提出该方法、2000 年前后公开论述【公开，以作者公开材料为准】；保险、银行与公共部门的监管追溯场景常用【经验】；dbt 生态中可检索到多个 Data Vault 自动化包，如 `dbtvault`（后更名 AutomateDV）与 `datavault4dbt`【公开，条目位于 dbt Package Hub（hub.getdbt.com）及各自 GitHub 仓库，可按包名检索；具体版本与维护状态需自行核验】。

#### 3.2.4 湖仓一体（Lakehouse）

- **被什么约束逼出来**：既要批又要实时、既要 SQL 又要特征与模型训练，同一份数据要被多个引擎读，而数据量已经大到"每个引擎存一份副本"不可接受。
- **结构**：

```sql
-- 开放表格式（Iceberg / Hudi / Paimon 共同思路）
CREATE TABLE iceberg.ads.user_features (
  user_id       STRING,
  feature_name  STRING,
  feature_value DOUBLE,
  dt            DATE
) PARTITIONED BY (dt)
TBLPROPERTIES (
  'write.format.default' = 'parquet',
  'format-version'       = '2'
);
```

```text
表状态与数据文件分离（湖仓的结构性差别）

  catalog
    └─ table metadata（每次提交产生一个 snapshot）
         ├─ snapshot A ──► 文件集合 {f1, f2, f3}
         └─ snapshot B ──► 文件集合 {f2, f3, f4}   ← 本次只写了 f4
  ────────────────────────────────────────────────
  schema 变更 / 分区演化 / 回滚 = 改元数据，不重写数据文件
  历史版本查询 = 读旧 snapshot 指向的文件集合
  → 同一份数据可被批、流、ML 三种引擎按各自需要的粒度读
```

- **为什么这样设计有效**：因为表格式把"数据文件"与"表状态"分离，所以改 schema、改分区、回滚都是元数据操作而不是重写数据 → **变更成本与数据量解耦**（改一次 schema 不需要扫一遍数据），这也是它能让多个引擎共享同一份存储的原因。粒度在此不再是全局唯一的一件事：ODS 的变更记录、DWD 的事件、ADS 的汇总可以共存于同一张逻辑表的时间线里。
- **代价**：小文件问题与 compaction 作业成为常设负担（流式写入天然产生小文件）；catalog 成为新的依赖点——元数据服务不可用则整个湖不可写；多引擎写同一张表必须靠 catalog 的并发提交控制，配置错误会损坏表；"存算分离"意味着查询性能高度依赖文件布局（分区、排序、文件大小），它需要的是一支长期维护的团队，不是一次性的迁移项目。
- **失效点**：当写入以高频小批（分钟级）为主、且没有常开的 compaction 时，「变更成本与数据量解耦」反转成「越写越慢、越查越慢」；因为每个数据文件都对应一次对象存储交互与元数据开销，文件数增长把固定开销乘以文件数——读放大取代了写效率。此时开放表格式还在，共享能力还在，但性能优势已经反转，而团队通常先把它归因为"引擎不够快"，从而买更多算力。
- **真实使用**：Apache Iceberg（由 Netflix 开源后捐入 Apache 基金会，现为基金会顶级项目）、Apache Hudi、Apache Paimon 的规范与文档【公开，定位符：Iceberg 的《Iceberg Table Spec》（format v1 / v2，iceberg.apache.org/spec）、Hudi 官方文档站（hudi.apache.org）、Paimon 官方文档站（paimon.apache.org）；三份规范均为持续维护的活文档，版本号以站点当前 release 为准】；Databricks 的 Lakehouse 论文（CIDR 2021）【公开】。主文件 §4.5 给出了 Iceberg / Hudi / Paimon 的建表示例。

#### 3.2.5 AI 原生数据栈

- **被什么约束逼出来**：消费方从"人 + BI"变成"人 + BI + Agent"。Agent 会自己发起大量查询，且**读不到人的记忆**——它只能消费被显式注册过的元数据。于是"口径有没有集中定义"从治理偏好升级为取数正确性的前置条件。
- **结构**：

```yaml
# 指标 / 语义层定义：机器可读，不是文档（OSCAR 模型，见主文件 §4.5）
- metric_id: gmv_1d
  metric_name: 当日 GMV
  metric_type: 派生指标
  atomic_metric_id: order_amount_sum
  time_period: 1d
  dimension: [user_id, merchant_id, city]
  formula: SUM(order_amount)
  owner:
    business: cfo@company.com
    data: data-team@company.com
  sla:
    freshness: 1h
    quality: {completeness: 0.99, accuracy: 0.99}
```

```text
Agent 取数路径（必须经过语义层，而不是直接猜表）

  业务问题（自然语言）
       ▼
  Agent ──► 语义层 / 指标平台（有 metric_id、口径、时点、Owner）
       │      匹配不到 → 明确回答「这个度量没有定义」
       │                    （而不是猜一个表名）
       ▼
  生成 SQL ──► ADS 层（ads_gmv_daily 一类，见主文件 §4.5）
       ▼
  返回 答案 + 所用口径 + 数据截止时间
       ↑ 缺了后两项，它就不是可审计的接口，只是更快的猜测器
```

- **为什么这样设计有效**：因为 Agent 只能调用它看得见的东西，所以"元数据的完备性"直接决定取数正确性——没有命名度量，模型只能猜表名与口径。这解释了为什么 AI 原生栈的第一性要求不是模型能力，而是元数据完备性：**模型再强也生成不出输入里没有的信息**。
- **代价**：元数据完备性成为真正的瓶颈，口径、粒度、时点、Owner 必须人工补齐，且"补不出来就没有入口"；AI 组件出错的责任必须落到具体的人（提交人、签署人），因为它不签署变更、不持有口径、不接受复盘；AI 能力多按调用计费，而使用者是千百个业务方，成本接口不界定清楚，上得越快账越难解释。
- **失效点**：当语义层只是把表名换个说法、没有把口径 / 粒度 / 时点写成可校验字段时，「AI 原生」反转成「错误被更快地生产出来」；因为自然语言入口把口径分裂从后台搬到前台，且近似匹配对口径天然无感——它给出的是"一张看起来对的表"，错误更晚暴露、更难归因。此时系统并没有变差，只是把原有的口径问题加速了。
- **真实使用**：Databricks Unity Catalog、Snowflake 的语义层 / Cortex Analyst、阿里云 DataWorks 的 AI Copilot（2024 年前后陆续发布）【公开，均为厂商自己的发布说明；核验入口为各自官方文档的产品页——Databricks 文档的 "What is Unity Catalog"、Snowflake 文档的 Semantic Views / Cortex Analyst、阿里云 DataWorks 的智能建模 / Copilot 产品页，确切发布日期以各页 release notes 为准】。本节只登记"厂商发布了这个能力"与核验入口，**不登记其效果**；本主题尚未找到可核验的非厂商公开生产案例。

#### 3.2.6 数据网格（Data Mesh）

- **被什么约束逼出来**：组织边界比技术边界更硬——域多、跨地域、甚至跨公司，中央团队无法承担所有域的数据交付，而每一次跨域需求都开一次协调会的成本会随域数增长。
- **结构**：

```yaml
# 跨域只走契约这一个制品，而不是每次需求开一次会
contract: trade.order_created
version: 1.2.0
domain: trade
schema:
  - {name: order_id, type: string,    nullable: false}
  - {name: pay_time, type: timestamp, nullable: true}
grain: 一行 = 一个订单的创建事件        # 粒度必须写进契约
sla:
  freshness: 1h
  availability: 99.9%
owner:
  business: xxx@company.com
  data: yyy@company.com
```

- **为什么这样设计有效**：因为跨域接口被收敛成"契约"这一个制品，所以协作成本从"每次协商"变成"一次定义 + 违约可检测" → 域数量增长时协作成本不再呈平方增长。这是数据网格**唯一**的机制性理由，也是它唯一能承诺的东西：它不承诺更快的查询，也不承诺更好的模型，只承诺协作成本的形状。
- **代价**：联邦治理要求每个域都具备工程能力（版本、测试、SLA、契约维护），这项能力不会因为"宣布自治"而出现；平台团队必须先把自服务基础设施做出来，否则"域自治"等于每个域各建一套；契约违约检测需要基础设施支撑，缺了它契约就退化成一页文档，而文档是会过期的。
- **失效点**：当组织里只有部分域具备工程能力时，「自治」反转成「割据」；因为契约只在双方都能执行时才有效，能力不足的域会用"共享一张表"绕开契约，跨域依赖重新变成隐式依赖——此时状态比集中式更糟，因为已经没有任何一方掌握全局。这也是数据网格落地最常见的真实结局：**部分采用**。
- **真实使用**：Zhamak Dehghani 自 2019 年起在 martinfowler.com 公开发表系列文章提出该范式【公开】。**落地案例的公开度低**：多数公开材料是方法论述而非可核验的生产事实（缺公司名、时间、规模、失败教训四项中的两项以上），因此本节不给出"某公司已全面实施"的断言；判断方法见 3.6 末段。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 源系统 10 个上下、业务过程可枚举、访问以聚合为主 | 维度建模（+ DataWorks 一类平台） | Inmon 式 3NF 的 JOIN 与物化链成本换不回它带来的中立性 | 业务过程能否列成一张不重不漏的清单 |
| 源系统 50+、schema 每年变多次 | Data Vault（集成层）+ 维度建模（集市层） | 星型的事实表会因源变更反复重建，历史回填成本不可控 | 过去一年源系统 schema 变更次数 |
| 批 + 流 + ML 共享同一份数据 | 湖仓一体 + 维度建模 | 物理表 + 单引擎会让每个消费方各存一份副本，口径随之漂移 | 同一份数据被几个引擎读、副本有几份 |
| 消费方含 Agent、要求答案可复现 | 指标平台 / 语义层 + 维度建模 | 直接把表暴露给模型，等于把口径分裂搬到前台 | 同一问题换三种问法，答案与口径是否一致 |
| 域 10+、跨地域、中央团队已成瓶颈 | 域自治 + 契约（理解成部分采用） | 集中式中台会让所有域的需求排同一条队 | 跨域依赖里有多少条走契约、多少条走共享表直连 |
| 监管要求"任意时点可回看且可追溯" | Data Vault 的 Satellite 或表格式时间旅行 | 覆盖式更新会销毁历史，事后无法补 | 能否回答"三个月前这条记录的属性值是什么" |
| 表数 < 100、变更季度级 | 维度建模 + 轻量治理即可 | 上湖仓或 Vault 的固定成本大于收益 | 是否有第二个引擎真的需要读同一份数据 |

**最常被误选的一对是「维度建模」与「湖仓一体」。** 团队把"选存储格式"当成了"选建模范式"：上了 Iceberg / Hudi / Paimon，就以为建模问题解决了。但表格式解决的只是**共享与演进**（多引擎读同一份数据、schema 变更不用重写数据），它不解决**粒度与口径**——用湖仓建一堆贴源宽表，得到的是一个更贵的数据沼泽：数据能被更多引擎读到，但没有任何一张表能回答"一行代表什么"。误选的实际后果是投资方向被锁定：湖仓的迁移、运维与 compaction 成本先发生，建模的欠账留到后面，届时改造要在已经承载生产查询的湖面上进行。

表里的量级阈值（源系统 10 / 50+、表数 100 / 万级）是【经验】取值，只用于区分量级；3.4 / 3.6 / 3.8 复用的是同一批量级，已在各表就地标注为【经验】。真正的判据在最后一列——例如"业务过程能否列成一张不重不漏的清单"这一条答不上来，任何方案都落不了地。

原「选型决策」表的 6 条候选是**工具组合**而非建模范式，不宜与上表的模式判据混在一列，故登记于此以免丢失——保留的是原表的「业务特征 + 推荐方案」两列，第三列「理由」未逐条保留：DataWorks + MaxCompute（阿里云生态 + 中型互联网）、DataFinder + ByteHouse（字节跳动 / 火山引擎）、自研中台 + Flink（美团 / 京东 / 拼多多）、dbt + Snowflake / Databricks（跨云 / 全球化）、Databricks + Unity Catalog + dbt（AI 优先）、华为 DAYU / 阿里 DataWorks（传统行业 / 国企）【经验：这是一份生态与组织约束的组合清单，不是模式差异；清单中的具名产品（DataWorks、MaxCompute、DataFinder、ByteHouse、Flink、dbt、Snowflake、Databricks、Unity Catalog、华为 DAYU）均为真实产品，可按名称在各自的官方文档站核验，「自研中台」则是自建路线的统称、不是产品名；同一场景可以有多种组合，选型时仍以上表最后一列的判据为准】。

### 3.4 组合模式：真实系统不会只用一种

**组合一：维度建模（域内）+ 数据网格（跨域契约）+ 自服务平台**

- 构成：每个域内用星型事实表 + 维度表交付自己的数据产品；跨域只通过契约暴露；平台团队提供调度、存储、契约校验的自服务能力。
- 各自职责边界：域负责自己的粒度、口径与 SLA；契约负责跨域接口的稳定性；平台负责基础设施与违约检测，不负责业务口径。
- 组合的运维代价：每个域都要有工程能力（这一条通常被低估）；平台要先于自治到位；契约数量随域对增长，契约本身需要一个归属方来维护版本。
- 适合的规模：域 10+【经验】、跨地域、中央团队已成瓶颈的组织；能力不齐时只做部分采用。

**组合二：Data Vault（集成层）+ 维度建模（集市层）**

- 构成：所有源先进入 Hub/Link/Satellite（Raw Vault），经业务规则形成 Business Vault，再物化成星型集市供 BI 与指标平台消费。
- 各自职责边界：Vault 只负责"接得住、历史全、加源不改模型"；语义、粒度与查询性能全部由集市层负责。
- 组合的运维代价：两层模型 + 自动化生成工具（手写不可持续）；双跑期长；Vault 与集市之间的口径需要一份对照表，否则出现"同一指标两种算法"。
- 适合的规模：源系统 50+【经验】、schema 漂移频繁、有监管追溯要求的场景。

**组合三：湖仓一体 + 维度建模 + 指标平台 / AI 原生**

- 构成：湖仓承载 ODS→DWD→DWS→ADS 的物化，表格式让批、流、ML 共享；ADS 之上由指标平台统一口径，Agent 经语义层取数（主文件 §4.5 的分层示例 + 指标定义）。
- 各自职责边界：湖仓负责存储与共享；星型负责粒度与查询；指标平台负责口径唯一性；Agent 只做翻译不做定义。
- 组合的运维代价：compaction 与元数据维护成为常设作业；口径补齐需要持续人力；模型调用成本需要单独归口，否则账单无法解释。
- 适合的规模：表数万级【经验】、消费方同时含 BI 与 Agent 的组织。

三个组合共享一条纪律：**链路上每一跳只解决一个问题**。组合一里契约不管查询性能，组合二里 Vault 不管语义，组合三里 Agent 不管口径。把两个问题的责任压到同一层上，那一层就会先崩——最常见的形态是让"贴源宽表"同时承担接入、粒度与口径三件事。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **工具堆砌** | 同一个能力有 2–3 个工具重叠；许可证与集群数远多于产出的可用模型数 | 工具之间元数据不互通，血缘每条链路都要在工具边界断一次；成本按工具数线性增长，治理能力不增长 | 采购与验收按"覆盖能力"打分，而不是按"能否回答一个具体问题"验收 | 以一条端到端链路验收（源 → ODS → DWD → DWS → ADS → 指标），链路上每一跳只有一个工具 |
| **照搬方法论** | 分层名与命名规范与某大厂公开材料逐字一致，但本公司的业务过程清单没人能列全 | 规范约束了形式却接不上本地业务过程，团队填表交差或绕开流程；模型"看起来规范"而不可用 | 照搬的产物可见（文档、命名前缀），适配的产物不可见（业务过程清单），前者更容易交付 | 先做业务过程 × 维度矩阵（主文件 §6），再据此决定分层与命名，而不是反过来 |
| **过度建模** | 几千张表、每个实体都被拆到多张表；跑批窗口越来越紧、链路越来越长 | JOIN 数与任务数膨胀，跑批时间随表数增长；模型变更影响面巨大到没人敢改，演进停止 | 规范化是"教科书上可判定正确"的事，而"够用就行"没有标准，多做不会当场被追责 | 用"业务过程粒度四问"过滤（是否产生度量 / 是否跨部门 / 是否稳定 / 是否有独立分析需求，见 [01-business-process-modeling](../01-business-process-modeling/01-business-process-modeling.md)）；答不出"一行代表什么"就不建这张表 |
| **缺乏 Owner** | 模型上线后无人负责，变更通知只能发到群；下线与修数靠"碰巧知道的人" | 问题在发现时已经扩散；没有主体就没有签署，没有签署就没有可回滚的变更 | 建模的交付物被定义为 DDL，而 DDL 里没有 Owner 字段，交付时自然被漏掉 | 无 Owner 禁止发布（主文件 §6 的做法）；Owner 必须是个人标识，转岗离职自动告警 |
| **忽略实时** | 实时需求靠"离线跑得勤一点 + 手工导出"打补丁 | 补丁链路游离在血缘与治理之外，延迟仍不达标；离线与实时两套口径开始分裂，且分裂不可见 | 实时链路建设成本高，补丁能当期交付，代价发生在几个月后才显形 | 实时 / 离线同源设计：同一份指标定义生成两套 SQL（主文件 §6 的做法） |
| **缺乏 AI 集成** | 元数据只服务于人（文档、看板），Agent 接不进来；取数仍靠人写 SQL | 缺口径与粒度的机器可读元数据，AI 取数只能猜表名，把口径分裂从后台搬到前台 | AI 集成的收益不落在建模团队，而"不做"没有当期代价 | 把元数据补齐成机器可读字段（口径 / 粒度 / 时点 / Owner），以"同一问题三种问法答案一致"验收 |

**展开一：照搬方法论。** 它在生产中的暴露方式是"规范齐全、模型不可用"：分层、命名、前缀、目录一应俱全，但当有人问"我们的订单域有哪几个业务过程"时，没人答得上来。机制上，照搬得到的是一套**形式约束**，而形式约束只有挂在本地的业务过程清单上才有效；清单不存在时，规范只能约束表长什么样，不能约束表该不该存在。它之所以危险，是因为一切检查项都通过——评审能过、CI 能过、审计能过，只有下游取数的人过不去。

**展开二：过度建模。** 它的暴露方式是"跑批窗口每年都被吃满一点"，而不是一次事故。因为每张表的规范化本身都是正确的，任何单次选址的评审都不会否决它；代价是在总量上累积的——JOIN 数、任务数、依赖深度一起增长。等到有人想改一个上游字段时，才发现影响面已经大到无法评估，于是组织事实上丧失了对这套模型的演进能力。修法不是"少建表"，而是**在入口处问粒度**：答不出"一行代表什么"的表，本来就是不该存在的那一类。

**展开三：忽略实时。** 它最隐蔽，因为补丁在当期是能跑通的。机制上，一旦实时结果由"离线结果 + 加工"拼出来，就等于**为同一份语义开了第二条实现路径**，此后每次口径变更都必须在两条路径上各改一次，而两条路径的变更通常是不同团队做的。分裂不是立即发生的事故，而是一个随着口径变更次数累积的差值；等到差值被发现时，已经无法判断哪一侧是对的。

原文件列出的其余反模式（工具堆砌、缺乏 Owner、缺乏 AI 集成）与上述三条共享同一结构：**模型的正确性判据没有落在入口处**——不在采购验收、不在发布门禁、不在元数据字段里，于是它只能靠人的责任心维持。诊断方法一致：问"这一步不做，谁会立刻知道"。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 源系统 10 → 50+【经验】、schema 每年变多次 | 维度建模（一次性建全） | 每次源变更都要改事实表并回填历史，回填成本随数据量增长 | Data Vault（集成层）+ 维度建模（集市层） | 需要建立 Hub/Link/Satellite 的生成与加载规范；双跑期长 |
| 时效要求 T+1 → 小时级 / 分钟级 | 纯离线星型 + 全量重算 | 全量重算的代价随数据量增长，跑批窗口被吃满 | 湖仓一体（增量 + 批流共用表格式） | compaction、元数据服务、并发提交控制都要新建并长期运维 |
| 消费方从 BI → BI + Agent | 指标散在各看板的 SQL 里 | Agent 读不到看板 SQL，只能猜表名与口径 | 指标平台 / 语义层（原子指标 + 派生指标） | 口径必须逐个补齐并签署，补不出来的度量就没有自然语言入口 |
| 引擎从 1 个 → 多个 | 物理表 + 单引擎 | 每个引擎存一份副本，副本之间口径开始漂移 | 开放表格式 | catalog 成为新单点；需要专职维护文件布局 |
| 域数 3 → 10+【经验】、跨地域 | 集中式中台统一交付 | 中央团队成为所有域需求的队列，队列长度随域数增长 | 域自治 + 契约（通常只做到部分采用） | 每个域都需要工程能力；平台自服务能力必须先到位 |
| 出现更正 / 追溯需求（监管） | 星型 + 覆盖式更新 | 覆盖销毁历史，无法回答"当时是什么样" | Satellite 追加写或表格式时间旅行 | 历史只能从改造之日起积累，无法回填——**拖延的每一天都是永久损失** |

换模式的判据同样不是"表数到了多少"，而是**某项成本是否已经开始按规模线性增长**：源变更次数乘以回填成本、跑批窗口的余量、口径变更时要点名通知的团队数——这三项中任何一项开始随规模增长，就该动手了。

关于数据网格，这里给一个可操作的判断方法（因为它的落地案例公开度低，不宜凭材料下结论）：**统计跨域依赖里有多少条是通过契约或服务接口达成的，有多少条是通过"共享一张表直连"达成的**。直连比例高，说明自治没有成立，此时推行数据网格只是把已有的隐式依赖换个说法；直连比例低、且契约能被自动校验，才说明具备了部分采用的条件。

### 3.7 自检清单

- [ ] 能否列出一份不重不漏的业务过程清单，并让每张事实表一一对上？对不上——粒度还锁不了。
- [ ] 每张事实表能否一句话回答"一行代表什么"？答不出——这张表不该存在。
- [ ] 事实表里是否出现过描述性文本列（备注、名称、地址）？出现即违反粒度纪律，多半是维度被塞进了事实。
- [ ] 源系统新增一个属性时，要改几张表、要不要回填历史？> 1 张且要回填——集成层没有与源解耦。
- [ ] 维度属性变化时，历史事实按事件发生时间归属，还是按当前值归属？答不清——SCD 类型未定义，数据会静默算错。
- [ ] 过去一年源系统 schema 变更了多少次？次数与数据量在同一量级——该考虑 Data Vault 或表格式。
- [ ] 跑批窗口的余量是否在逐年下降？下降——查的是"不够快"还是"模型不对"，先看 JOIN 数与任务数。
- [ ] 实时与离线对同一指标是否由同一份定义生成？两份——口径分裂已经开始，且不可见。
- [ ] 指标是否都有 metric_id、口径、时点与 Owner？没有——Agent 接不进来，只能猜。
- [ ] 湖仓表的文件数与平均文件大小是否被监控、有无归属人维护 compaction？没有——读放大正在积累。
- [ ] 链路上是否有两个工具覆盖同一能力？有——血缘会在工具边界断掉，影响面分析从此不完整。
- [ ] 跨域依赖里走契约的比例是多少？答不出——说明依赖是隐式的，数据网格还不具备条件。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 源系统 10 个上下【经验】、业务过程可枚举 | 维度建模 + 统一平台 | 粒度事前锁死，查询 JOIN 数为常数，代价可预测 |
| 源系统 50+【经验】、schema 漂移频繁 | Data Vault + 集市层 | 属性下沉到 Satellite，加源不改集成层；变更被保留成数据 |
| 批流 ML 共享同一份数据 | 湖仓一体 | 表状态与文件分离，schema 变更成本与数据量解耦 |
| 消费方含 Agent、答案要可复现 | 指标平台 / 语义层 | Agent 只能消费被注册的元数据，口径完备性是前置条件 |
| 域 10+【经验】、跨地域、中央已成瓶颈 | 域自治 + 契约（部分采用） | 协作成本从"每次协商"变成"一次定义 + 违约可检测" |
| 监管要求任意时点可回看 | Satellite 追加写或时间旅行 | 覆盖式更新会销毁历史，且历史无法事后回填 |
| 表数 < 100【经验】、变更季度级 | 维度建模 + 轻量治理 | 湖仓与 Vault 的固定成本大于收益 |

> 本节小结：决定本主题模式选择的唯一那条约束，是**"事实粒度在流程的哪一步被锁死"**——锁得越早，查询越便宜、变更越贵（维度建模）；锁得越晚，集成越稳、查询越贵（Inmon 的 3NF）；刻意推迟并让变更本身成为数据，就是 Data Vault 与湖仓一体；把锁定的决定权交给消费端或交给域，则是 AI 原生数据栈与数据网格。其余约束（数据量、引擎、工具）都只是把你推到这条线上的某个位置。
