## 5. 前沿演进（AI 时代）

> 原 § 5 共 51 行、为方向清单（AI Copilot 辅助建模 / Agent 自动评审 / 自然语言查询指标 / AI 增强目录 / RAG 与 GraphRAG / 本体化治理 / 7 条进展 / 4 条趋势），缺少机制与成熟度判断，本节重写为 ~287 行前沿评估。

### 5.1 先分清三类「前沿」

本文件的主题是**工具链**（DataWorks / MaxCompute / Hologres / dbt / 湖仓），工具链上的 AI 能力有一个特别容易被高估的地方：**演示效果最好、落地依赖最多的那个环节，恰恰是最容易被写进"进展表"的环节**。一句自然语言问出 GMV，在演示里只要三秒；在真实环境里，它要求你的表有注释、字段有含义、指标口径只有一份、权限边界清晰——这些条件本身才是工程量。

所以本节用三条**可核验**的判据给每个方向定级：有没有正式 release note、有没有**第三方（非厂商）**公开的生产案例、接口是否稳定。三条全中才是 L1。

三条判据各自挡住一类误判：release note 挡住"把路线图当既成事实"；第三方生产案例挡住"把厂商自述当行业现状"；接口稳定性挡住"把演示当工程"。工具链场景还要额外多一条尺子——**产品名不等于能力名**：自然语言生成 SQL 这件事，各平台的入口、函数名、支持的方言都不一样，本节讨论能力，落到具体产品一律以该产品文档为准。

还需要先拆掉一个混淆：**平台底座（元数据、血缘、调度、表格式）与 AI 能力是两层**。底座这一层已经 GA、接口稳定、有大量第三方生产案例，是 L1；AI 这一层压在底座之上，成熟度普遍不如底座。很多"AI 原生数据平台"的说法，实质是把底座能力重新包装了一遍。

还有一条方式上的说明：本节把原文件里出现过的**每一个方向与工具名都保留了下来**，只是重新归了类、合并了同类项（比如"DataWorks Copilot 自然语言 → DDL"与"dbt-codegen + LLM 自动生成模型代码"合成同一个方向："Copilot 辅助建模"）。分级的对象是**能力**，不是产品：同一个产品可能同时出现在 L1 与 L2 的格子里——它的存储与元数据能力是 L1，它的生成式助手是 L2。把级别打给产品名，会在选型时得出错误结论。

级别也不是标签，而是**给规划动作定条件**：L1 可以写进路线图与架构假设；L2 可以做 PoC，但不要让它可以成为核心依赖（不要设成唯一入口、不要写进数据契约）；L3 只记录——**一旦你在 schema、存储或流程里为它留了位置，就等于已经把它当成 L1 了**。本节后面每一处"明确不要做"，说的都是这件事。

最后说明本节与原稿的关系：原稿列的方向**一个都没有删**，包括那些看起来"只是工具集成"的条目（AI 增强目录、自然语言查询指标、自动生成模型代码等）。它们不是错误的方向，只是成熟度被高估了；本节要做的是把它们放回正确的位置——**做成什么、卡在哪、现在能不能依赖**。

按这三条判据，本主题下的分级如下。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **Copilot 辅助建模**（自然语言 → DDL / ETL 任务：DataWorks AI Copilot、Databricks Assistant、Snowflake Cortex、dbt-codegen + LLM） | L2 | 各平台官方文档可查、能力已可用；生产案例以厂商自述为主，缺第三方复盘；生成质量取决于平台内元数据与命名规范完备度 | 只在"模型已定、只差落 DDL / SQL"的环节试点，量化**评审通过率**与人工修正量 |
| **自然语言查询指标与报表**（Snowflake Cortex Analyst、Databricks Genie、Microsoft Fabric Copilot） | L2 | 同上；且"返回结果是否标注所用口径、是否可复现"没有统一约定 | 只在语义层 / 指标平台已覆盖的域内开放，超出范围就明确说"答不了" |
| **AI 增强目录**（自动生成模型标签、口径说明、使用示例） | L2 | 能力可用（各目录产品普遍提供）；准确率与漏检率厂商未给出可复核口径 | 一律走"建议 + 人工确认"，**不要自动写回** |
| **Agent 自动评审模型变更 / 智能评审 PR**（Atlan AI、Secoda AI、DataWorks AI Copilot 智能评审） | L3 | 无第三方公开材料说明"Agent 拦下了什么、漏过什么"；评审的权责归属没有约定 | 记录；先把评审检查项写成**可被机器执行的规则** |
| **模型元数据作为 RAG 索引**（检索对象从"数据"扩到"模型 / 指标 / 文档"） | L2 | 检索能力已可用；但命中质量取决于元数据完整性，而非检索算法 | 先把元数据补全（Owner / 口径 / 示例），再谈检索 |
| **GraphRAG 增强模型治理**（模型 / 字段 / 指标 / 报表 / 用户 / 文档 入图，多跳推理） | L3 | 公开文献与原型为主；企业内图构建与维护的成本账缺失 | 记录，不要为它预留图存储 |
| **本体化模型治理**（模型作本体 class、字段作 property、关系作 objectProperty） | L3 | 学术形态为主；无主流产品的接口约定、无生产案例 | 记录；不要为它预留本体结构，等主流产品给出接口约定再说 |
| **湖仓表格式与平台底座**（Apache Paimon、Apache Iceberg 一类，含规范演进条目） | L1（**仅表格式本身**） | 已发布、有第三方生产案例、接口（表规范 + 引擎支持面）稳定；注意**规范里的新条目 ≠ 你用的引擎支持** | 按常规选型流程用；不要把新规范条目当作设计前提 |
| **模型代码与文档的自动生成**（dbt-codegen + LLM 一类：自动生成模型代码与模型文档） | L2 | 工具已可用且开源、生成对象是版本控制里的文件（改动可评审、可回滚）；缺第三方规模化效果材料 | 在新建模型时试用，把生成结果当作候选稿进代码评审 |
| **自然语言 → 报表 / 看板**（Microsoft Fabric Copilot 一类：自然语言生成可视化报表） | L2 | 能力随平台提供、文档可查；产物是"看板"而不是"取数结果"，错误的可见性更差 | 限定在已定义的指标上生成，别让它绕过指标层直连表 |
| **智能 ETL 与告警归因**（自然语言 → SQL；告警 → 自动诊断，见主文件 §1.2 的 AI 时代新诉求） | L3 | 生成 SQL 部分可归入 L2；**"告警 → 自动诊断"没有第三方效果材料**，且归因结论错了会把排障带偏 | 记录；先把告警的上下文补全（谁负责、影响哪些下游） |
| **联邦自治的平台形态**（Data Mesh 思想下的自服务 + 数据契约） | L3（**就其与 AI 的关联而言**） | 作为一种组织形态已有多方公开讨论；但"AI 让联邦自治自动成立"没有可核验证据，反过来更接近事实：联邦化要求每个域自己有 Owner 与契约，AI 只是让缺失暴露得更快 | 记录；先把数据契约与域 Owner 落地，那是联邦化的前提 |

> 表里唯一够得上 L1 的是**表格式与平台底座**——而它跟 AI 没有直接关系。把它放进"AI 进展"表本身就是一种错位：它解决的是存储与治理的开放性问题，只是恰好被 AI 取数链路用到了。**本节列的 AI 方向没有一个够 L1**，原因集中在同一处：它们的成败都压在底座质量上，而底座质量在多数组织里还是欠账。
>
> 也就是说，工具链侧真正变的是**交互方式**（提问式入口取代菜单式入口），不是**能力边界**。5.2 逐条给出机制。

### 5.2 演进方向逐条拆解（核心节）

5.2 的每条方向都按同一个结构写：旧做法卡在哪、AI 改变了哪个机制、由此得到什么、由此付出什么、证据与来源、成熟度。注意这里**"付出"那一行不能空**——写不出代价的方向，多半还没人在规模上用过。

另一个共同点值得先说：这四个方向**都不是新的数据组织方式**。它们没有改变事实与维度的划分，没有改变 ODS-DWD-DWS-ADS 的分层，也没有改变指标口径的组织方式；它们改变的是这些产物**由谁、以什么成本生产出来**。判断一个 AI 能力值不值得上，这是最快的一把尺子：如果它只改变了生产环节，那么收益上限就是生产环节的人力成本——不是"数据架构的升级"。

#### 5.2.1 Copilot 辅助建模：把一次变更要写三遍的东西收成一遍

- **旧做法与它的卡点**：旧做法里，一次模型变更要在**多个产物**上各写一遍——建模工具里的模型定义、DDL、DWD 层的 ETL SQL（见本章 §4.5 的分层示例）、以及调度与文档。卡点不在"不会写 SQL"，而在**同一次变更要在四五个地方各表达一次，且它们之间没有强制一致性检查**。于是变更的成本随产物数量放大，团队会主动选择"少改一点"，欠账越积越多。
- **AI 改变了什么机制**：平台内的 Copilot 能读到表清单、字段、注释与血缘，于是"模型 / 需求 → DDL 与 ETL SQL"这一步的表达成本被压到接近一次推理调用。机制上是**改变成本函数**，不是改变建模方法。
- **由此得到的**：因为表达成本被压到接近零，所以"每次变更同步更新模型、SQL 与文档"第一次变成可负担的常规动作——而它在旧做法里几乎没人做全，因为三份产物各写一遍太贵。
- **由此付出的**：确定性下降，同一需求两次生成不会得到同一份 SQL。更实际的风险是**生成物与源模型不一致**：改了字段名，Copilot 生成的 ETL 可能还在引用旧名，而这类错误往往到任务失败时才暴露。此外还有**平台绑定**：Copilot 能力绑在你所用的平台上，换平台时这部分投入归零——这正是主文件 §1.3 那张开源替代对照表（dbt / Airflow / DataHub）要提醒的事。最后一条代价是流程上的：把生成的 SQL 直接接进调度，等于让未经评审的表达直接写进生产表。
- **证据与来源**：各平台官方文档【公开，2024 年前后】——阿里云 DataWorks、Databricks Assistant、Snowflake Cortex、dbt 相关文档；**第三方（非厂商）公开的生产效果材料本节未找到**，因此不给 L1。
- **成熟度**：**L2**。判据：能力可用、文档可查，但效果取决于底座元数据质量，且缺第三方复盘。判定方法：统计一次真实变更中，"生成的内容被采纳、未修改"的比例，以及生成的 ETL 首次运行的成功率。

顺带说清一件事：Copilot 覆盖的产物越多，**评审的负担变化并不是单调下降的**。生成 ① ② ③ 之后，评审要多看几份候选与差异；只有当 ⑤（文档与粒度声明）也被稳定补全时，评审才会真正变轻。所以试点时最好从"只生成候选 DDL、评审照旧"这条最保守的路径开始，确认生成质量后再逐步扩大范围。

```text
一次模型变更要写的产物（Copilot 覆盖到哪一步）
  ① 模型定义（建模工具 / dbt 项目）      ← Copilot 可生成候选
  ② 物理 DDL（建表语句）                  ← Copilot 可生成候选
  ③ DWD 层 ETL SQL（本章 §4.5 的分层示例）← Copilot 可生成候选
  ④ 调度与依赖配置                        ← 部分生成，需人工确认
  ⑤ 建模文档（粒度声明 / 字段含义 / Owner）← 可补全，责任仍在人
  ────────────────────────────────────────────────
  关键：①②③ 便宜了，不等于变更便宜了；
       真正决定变更代价的是 ④⑤ 里的依赖与责任人，
       以及"这次改动该不该做"这个判断
```

把生成物拆到校验层看，能过的关口和过不去的关口差别很大：

| 生成物 | 谁校验 | 校验不了会怎样 |
| --- | --- | --- |
| DDL 语法与字段类型 | 建表时的引擎校验 | 建表失败，立刻暴露，代价最低 |
| 命名规范 / 分层前缀（ODS-DWD-DWS-ADS） | 静态规则（lint） | 规范漂移，靠评审补，属治理债 |
| ETL 里的字段引用是否与模型一致 | 部分可静态检查（元数据比对） | 任务失败或**静默算错**，后者更贵 |
| 分区键与刷新策略 | 规则 + 人工确认 | 大表全表扫、产出时间失控 |
| 粒度声明与度量口径 | **只能靠人** | 同一指标两种结果，返工要推倒重来 |
| 调度依赖与 Owner | 人工确认 | 出事没人认领，恢复靠人肉 |

这里有个次序问题容易被搞反：Copilot 的效果由**底座元数据**决定，而底座元数据正是主文件 §1.1 里"数据治理"那一行（元数据 / 血缘 / 质量 / 安全）真正落库之后的结果。所以"先补元数据、再上 Copilot"不是保守，而是唯一有效的顺序；反过来做，会形成"生成质量差 → 团队不信任 → 弃用"的闭环，而错的结论会被记成"AI 不适合我们"。

#### 5.2.2 Agent 自动评审：把可规则化的检查项从人手里拿走

- **旧做法与它的卡点**：旧做法是模型评审会 + checklist（命名规范、粒度声明、Owner、SLA、质量规则）。卡点有两层：第一层是**规模**——表一多，评审会就退化成签字；第二层是**对象**——评审的是"文档里写的"，而实际影响面在血缘图里，人的阅读速度跟不上变更速度。
- **AI 改变了什么机制**：LLM 能读规范文档与非结构化描述，把一部分检查项从"人的记忆"搬到"可执行的规则 + 语义判断"上。机制上是**把人工判断里可规则化的那部分换成机器执行**，剩下的争议项仍留给人。
- **由此得到的**：因为可规则化的检查项被机器承担，所以评审会的时间可以集中到真正有争议的地方——口径归属、粒度取舍、跨域维度共享——这些才是评审真正该解决的问题。
- **由此付出的**：出现一种新的组合风险：**"漏检"加上"没有责任主体"**。Agent 通过不等于有人担保；一旦下游出事，"系统放过的"无法追责到具体的人，而这恰好会侵蚀评审制度的严肃性。其次是形式化之后的**规则套利**：检查项一固定，就有人学会让它通过（本章 §3.5 的"过度建模""缺乏 Owner"两条反模式，都可能在自动评审下被更高效地绕过）。
- **证据与来源**：Atlan AI、Secoda AI、DataWorks AI Copilot 的产品说明【公开，厂商文档，2024 年前后】；**没有第三方材料说明它在真实变更上拦下了什么、漏过了什么**，按纪律记为 L3，不写成事实。
- **成熟度**：**L3**。判据：仅厂商文档与演示，无独立效果证据、无权责约定。先做可落地的前一步：把检查项写成能跑的规则（命名、分区声明、Owner 必填），这一步的收益不依赖任何模型。

把常见检查项按"能不能规则化"分一下，就知道自动评审的合理边界在哪里：

| 检查项 | 能否规则化 | 该谁做 |
| --- | :---: | --- |
| 命名规范、分层前缀、表名风格 | 能 | 静态检查（进 CI，与模型无关） |
| Owner 必填、SLA 与刷新策略已声明 | 能 | 发布门禁（与模型无关） |
| 分区键是否存在、是否声明粒度 | 能（部分） | 静态检查 + 人工确认 |
| 变更影响面是否已确认、是否超阈值 | 能（依赖血缘） | 门禁（血缘自动采集的前提下） |
| 口径变更的理由与审批链 | 不能 | 人——这是承诺，不是判断 |
| 这个维度该不该和别的域共享 | 不能 | 人——跨团队协商 |

只有前四行适合交给机器，而它们**不需要模型**也能做。后两行交给机器的风险，正是 5.2.2 里说的"漏检 + 无责任主体"。

再补一句现实：多数组织连"检查项"本身都还没有写下来。在检查项没有明文的情况下引入自动评审，得到的是**不可解释的结论**——它说不能过，你说不出依据，也没法申诉；久而久之团队会绕过它。先把检查项写下来，是这项工作唯一无法跳过的部分，而它不需要任何模型。

顺带说清一个常见误解：Agent 评审**不是"把评审会搬进系统"**。评审会里有一部分是核对（可规则化），一部分是协商（不可规则化）。自动评审能替代的是前者；把它当成后者的替代品，最典型的后果是"变更都被系统放行了，但没人记得当时为什么同意"——而复盘恰恰需要的就是这个"为什么"。

#### 5.2.3 自然语言查询指标：把排队变成自助

- **旧做法与它的卡点**：旧做法是业务方提需求 → 数据团队排期 → 出报表。卡点不是技术延迟，而是**人力排队**：每一次回答都消耗一个数据工程师的时间，需求队列长，问题被"简化"成能排得上期的那种问题。这是主文件 §1.2 里"纯人工建模跟不上业务迭代速度"在消费侧的对应形态。
- **AI 改变了什么机制**：把"提问 → 指标查询"这一步变成自助，**改变了人机分工**——消费侧不再必须经过生产者。注意它并没有改变数据的组织方式：能回答什么，仍然由指标与语义层的覆盖范围决定。
- **由此得到的**：因为消费侧自助化，所以数据团队的时间可以从"重复回答"转到"定义与治理"，同时提问不再受排期约束——那些"以前不值得提需求"的小问题第一次能被回答，这往往比大问题更有价值。
- **由此付出的**：三项。一是**口径风险从后台转到前台**：同一个问题不同人问出不同口径，而没有人察觉，因为答案看起来都很合理。二是**不可复现**：同一问题的答案随问法变化，审计、复盘、监管举证都会变难——这也是本章 §4.5 里指标平台要把口径与 Owner 写死的原因。三是**成本不可预测**：自然语言查询背后是按量计费的推理调用，而需求侧没有"配额"这个概念，用量会在无人察觉时放大【经验：随活跃提问人数与问题长度增长，具体量级取决于实现与模型选择】。
- **证据与来源**：Snowflake Cortex Analyst、Databricks Genie、Microsoft Fabric Copilot 的官方文档【公开，2024 年前后】。判定方法：看它是否公开了**准确率口径**与**"答不了"的边界**（超出覆盖范围时是拒绝回答还是编一个答案）——这一条比任何演示都更能说明它是否可被生产依赖。
- **成熟度**：**L2**。判据：能力可用、文档可查，但缺第三方效果证据，且可复现性没有统一约定。只在语义层已覆盖的域内开放。

还有一个组织层面的副作用值得预判：自助取数上线后，**"答疑"的工作量不一定下降**。业务方拿到的答案如果与预期不符，仍会来找数据团队——只是问题的形态从"帮我算个数"变成"为什么你的口径是这样"。这是好事（讨论回到了口径本身），但它意味着数据团队要预留出这部分时间，否则会同时承受"旧需求没减少、新疑问又增加"的挤压。

```text
自助取数的两条路径（可复现性差别极大）
  路径 A（有指标层）：
    提问 → 匹配到命名度量 → 生成对度量的调用
         → 返回结果 + 所用口径 + 数据时间
      可复现：同一口径、同一时间，答案一致

  路径 B（直连裸表）：
    提问 → 猜表名与字段 → 现场生成 SQL → 返回结果
      不可复现：换一种问法可能落到别的表、别的过滤条件

  ────────────────────────────────────────────────
  关键：路径 B 不是"暂时不准"的问题，
       而是"同一个问题有两个都对的答案"的问题——
       审计、复盘、监管举证都会卡在这里
  → 所以范围控制比准确率更重要：
     先覆盖有度量的域，没有度量的域宁可回答"查不了"
```

落到具体问题上，可以回答与不能回答的边界大致是这样：

| 提问类型 | 能否回答 | 理由 |
| --- | :---: | --- |
| "上周各城市的 GMV" | 能 | 有命名度量 + 维度，口径唯一 |
| "上周 GMV 为什么跌了" | 不能（只能给线索） | 归因需要业务假设，不是取数问题 |
| "复购率是多少"（未定义"复购"） | 不能 | 口径未定义，任何答案都是新造一个口径 |
| "找出和这批订单相似的订单" | 不能 | 需要事实级向量与相似检索；5.1 表里没有这个方向（它不属于工具链主题，本节不为它定级） |
| "帮我做一张城市 GMV 的看板" | 视平台而定 | 属报表生成类能力，产物错更难发现 |

#### 5.2.4 AI 增强目录：让元数据从"文档"变成"接口"

- **旧做法与它的卡点**：旧做法里元数据靠人工填，且填得动的只有"表名 + 字段名"。卡点有两层：**生产成本高**（写口径说明是纯投入，没有即时回报），**没有强制消费方**（人查不到就算了，可以用嘴问）。于是治理长期欠账：目录能搜到表，但不知道能不能用、口径是什么。
- **AI 改变了什么机制**：两件事。第一，把标签、口径说明、使用示例的生产从"人写"改成"机器生成候选 + 人确认"，**降低了元数据的生产成本**。第二，也是更重要的一件：**元数据多了一个新的强制消费方——Agent**。Agent 要选表、要生成 SQL、要判断字段能不能读，全靠机器可读的元数据；人可以将就，机器不能。
- **由此得到的**：因为元数据第一次有了"不读就用不了"的消费方，所以它从文档变成了**接口**。这是本文件里真正有价值的一条机制：它把"治理"从道德要求变成了功能前置条件。这也是为什么本文件 §5.1 的两个方向（Copilot 辅助建模、自然语言查询）都把元数据质量列为前提。
- **由此付出的**：第一，**错的元数据被下游放大**。原来一条错的字段注释只误导人，现在它会直接生成错的 SQL、错的影响面、错的标签，而且以机器速度传播。第二，**多出两份状态**：GraphRAG 的图与本体化治理的本体，都是模型元数据之外的又一份表示，它们与主模型同步的责任在现状下**没有归属**——模型侧那些对象（事实表、维度表、指标、字段、Owner）一旦被复制进图与本体，就多出两处会过期的地方。
- **证据与来源**：Atlan AI、Secoda AI、DataHub AI 一类目录能力见厂商文档【公开，2024 年前后】；GraphRAG 方向有可公开核验的文献（Microsoft Research 的 GraphRAG 论文《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》及其官方博客，2024；篇名以 arXiv 与 Microsoft Research 官方页面为准）【公开】；**本体化模型治理未找到生产案例与接口约定，属 L3**。
- **成熟度**：**AI 增强目录 L2**（可用，但只做建议不自动写回）；**GraphRAG 与本体化治理 L3**（记录，不为它预留图存储或本体结构）。

```text
元数据在工具链里的角色变化（本节最关键的一条机制）
  之前：人 → 目录 → 人            （可读可不读，不读也能干活）
  现在：Agent → 目录 → 表 / SQL   （不读就选错表、写错 SQL）
  ────────────────────────────────────────────────
  → 元数据从「文档」变成「接口」：有格式、有责任方、有失败后果
  → 所以先补的应该是"机器必须读的字段"：
     表的一句话含义 / 度量口径 / Owner / 密级 / 粒度声明
  → 而不是先补"看起来漂亮"的标签和使用示例
```

这条机制有一个直接推论：**元数据的验收标准应该跟着消费方走，而不是跟着覆盖率走**。如果消费方是人，"目录里有一半表有说明"也许够用；如果消费方是 Agent，那么缺一个 Owner、缺一句粒度声明，都足以让它的输出不可信。这也是为什么本章 §3.5 把"缺乏 Owner"列为反模式——在 AI 消费元数据的场景里，这条从"治理建议"升级成了"功能缺陷"。

反过来说，这也是本节唯一一条**投入产出比明确为正**的方向：补机器必须读的元数据，同时让目录检索（人用）与 Agent 取数（机器用）都受益，而它不需要赌任何一条尚未成熟的机制。相比之下，"先把标签生成齐全"只服务了演示效果。

最后补一条边界：这里说的"AI 增强目录"指用模型补全或生成元数据，**不包括"用模型做元数据治理决策"**。后者——比如自动判定某张表该不该下线、某个字段该不该标为敏感——属于 5.2.2 那一类，责任主体问题没有解决之前不应交给机器。

### 5.3 与本主题既有栈的接口在哪

本节不写"与 X 结合"。接口要看三件事：谁调用谁、数据以什么形态穿过边界、失败时谁负责。工具链场景的特殊性是：**产物会在系统之间传递多次**（模型 → DDL → ETL → 调度 → 指标 → API），所以每个交界处都要能回答"出错时谁签字"。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Copilot ↔ 平台元数据（DataWorks / Unity Catalog 等） | 平台内的表、字段、注释、血缘作为生成上下文 | 提交人——生成的产物出问题由提交人负责 | L2：可用，但元数据越脏、生成越不可用 |
| 生成的 DDL / ETL ↔ 调度与生产表 | 产物经代码仓或建模工具进入调度 | 提交人 + 评审人，**不是 Copilot** | L2：可行，前提是把生成物纳入评审 |
| Agent 评审 ↔ 代码仓 / 建模工具 | 检查项以规则 + 语义判断执行，输出通过 / 阻断 | 门禁规则的定义者 | L3：责任主体在制度上没有约定 |
| NL 查询 ↔ 语义层 / 指标平台 | 调用命名度量（本章 §4.5 的 OSCAR 模型一类定义），返回结果并标注口径 | 度量 Owner | L2：可用，前提是口径已集中定义 |
| AI 目录 ↔ 元数据存储 | 生成标签 / 口径说明并写回 | **没有定论**——所以现阶段不要自动写回 | L2：能力可用，责任未定 |
| 图 / 本体 ↔ 模型元数据 | 第二份表示，需与主模型同步 | **无人**（无 Owner 约定） | L3：正因找不到责任人，才不该现在落地 |
| 湖仓表格式 ↔ 上一层建模 | 表规范与引擎支持面 | 平台 / 引擎选型负责人 | L1：接口稳定，但新规范条目的支持面需逐版本核验 |
| 指标平台 ↔ 建模产物 | 指标定义引用事实表与维度的字段（本章 §4.5 的定义文件） | 指标 Owner 与建模 Owner 共同——两边改动要同步 | L2：可用，但口径改动容易只改一侧 |
| 告警 ↔ 归因 / 诊断 | 告警事件 + 血缘与元数据作为上下文 | 值班人——**诊断结论只能当作线索**，不能替代判断 | L3：能力形态不清晰，责任归属更不清晰 |
| AI 能力的推理调用 ↔ 成本中心 | 按量计费的外部调用，使用方是千百个业务方 | **平台 Owner 买单，却没人负责用量** | L2：可用，但成本必须在预算里单列一项 |

这张表的共同点是：**AI 组件的失败责任一律落到人身上**（提交人、评审人、度量 Owner），这不是保守条款，而是因为 AI 组件不签署变更、不持有口径、不接受复盘。所以引入任何一个 AI 组件时，先问的不是"它能做什么"，而是"它出错时谁签字"。

还有一个常被忽略的接口：**成本接口**。工具链上的 AI 能力大多按调用计费，而使用者是千百个业务方——典型的"花费者与付费者分离"。不把这条边界写清楚，AI 能力上得越快，账单越难解释，最后往往演变成"一刀切限额"，把真正的使用场景也一起关掉。

和前面几节的接口一样，这里也可以把每一行写成一条可执行的检查。"Copilot ↔ 平台元数据"这一行对应的检查是：随便挑一张表，看它有没有粒度声明与 Owner；"NL 查询 ↔ 指标平台"这一行对应的检查是：问同一个问题两次、换一种问法一次，看三次结果与标注的口径是否一致。答案不一致的行，就是当前还不能依赖的那段边界。

### 5.5 被过度宣传的部分

**「Copilot 让建模效率提升数倍」** —— 实际是：建模的瓶颈从来不是写 DDL 与 SQL，而是粒度对齐与口径协商。→ 为什么会这样：生成只覆盖本章 §4.5 那组分层示例（ODS→DWD→DWS→ADS）的书写环节，前面的决策一步都没省；而耗时恰恰集中在前面的会议与确认上。→ 判定方法：让团队把"一次模型变更从提出到上线"的耗时做一次分解，看书写环节占多少——多数团队的答案会让这条声称不成立。→ 什么时候它才会成真：当"模型变更从提出到上线"的耗时里，书写环节真的占了大头——那意味着你的瓶颈是产能，而不是协作。

**「AI 自动评审可以替代模型评审会」** —— 实际是：Agent 能查规范、能查血缘，不能对口径负责。→ 为什么会这样：评审会的真正产物不是"通过"这个状态，而是**负责人当面作出的承诺**；承诺需要一个能承担后果的主体，而 Agent 不是。→ 什么时候它才会成真：当检查项被完全规则化、且制度上明确了"规则 Owner 为漏检负责"——到那时取消的是会议形式，不是责任。

**「自然语言取数意味着不再需要语义层 / 指标平台」** —— 实际是：恰好相反，自然语言查询的质量上限由语义层决定。→ 为什么会这样：模型只能调用它能看见的东西；没有命名度量，它只能猜表名与口径，于是把"口径分裂"从后台搬到前台，且更难被发现。→ 判定方法：在同一个域内问 10 个同义问题，看答案是否一致、是否标注了所用口径。→ 什么时候它才会成真：当自然语言入口能稳定地说出"我用了哪个口径、数据截止到什么时候"——到那时它才是一个可审计的接口，而不是一个更快的猜测器。

**附一条错位**：**Paimon / Iceberg V3 这类条目本不该出现在"AI 进展"表里**。它们与 AI 没有直接关系，解决的是湖仓格式的开放性与演进能力。把它们和 Copilot 并列，会让读者误以为两者之间存在依赖关系，而实际上前者是底座（L1），后者是底座之上的应用（L2/L3）——混淆这两层，是本节最容易犯的判断错误。

这三条说法有一个共同结构：**它们都把"生成"的能力当成了"判断"的能力**。生成 DDL、生成看板、生成 SQL 都是可自动化的；而"这个粒度对不对""这个口径算不算""这次回答可信不可信"，每一项都需要一个能承担后果的主体。读到任何一条宣称时，先找它的主语是谁。

最后一条经验：**被过度宣传的方向往往不是没价值，而是价值被安错了位置**。Copilot 生成 DDL 是有价值的，它的价值是"省一次打字"；一旦被写成"省一个建模师"，期待就会落空。把每条 AI 能力还原成"它替谁省下了哪一步、这一步占整体耗时的多少"，营销话术自然就失效了。

原文件列出的三类风险点本节都保留，且它们都能落到具体机制上：**Copilot 的幻觉**对应 5.2.1 的生成物与源模型不一致——语义错误不会被解析器拦住，往往到任务失败或静默算错时才暴露；**过度自动化引入新错误**对应 5.2.2 的"漏检 + 无责任主体"与 5.2.4 的"错的元数据被下游放大"；**AI 治理的合规边界不清**对应 5.3 那张责任表——今天绝大多数 AI 组件的合规边界只能靠"人签字"兜住，而不是靠制度。三者都不是"用不用 AI"的问题，而是"谁负责"的问题。

### 5.6 未来 3–5 年：可证伪的预测

预测必须能被推翻，所以下面每条都写成「预测 + 会成真的信号 + 会证伪的信号」。写不出信号的方向本节不写。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| **工具链的 AI 能力会收敛到"平台内助手"这一形态，独立 AI 建模产品难以存活** | 新出现的 AI 建模能力基本由平台厂商内置发布；独立的 AI 建模工具转向做插件或垂直场景 | 出现独立 AI 建模产品，在没有平台元数据支撑的情况下被大量采用 |
| **口径集中定义（语义层 / 指标平台）会成为自然语言取数的前置条件** | 自然语言取数的失败复盘结论指向"这个度量没定义"，而不是"模型不行"；上线范围按域划分而非按表划分 | 出现不依赖任何集中定义的方案，在真实企业环境里被广泛使用且答案可复现 |
| **元数据补全会从"生成标签"转向"补全机器必须读的字段"** | 治理项目的验收标准从"标签覆盖率"变成"口径与 Owner 覆盖率"；Agent 取数失败能追溯到缺失的具体元数据字段 | 三年后主流做法仍是生成大量标签，而口径与 Owner 依旧空缺 |
| **自动评审不会取代评审会，但会改变评审会的内容** | 评审会时间从"核对规范"转向"讨论口径与粒度";规范类问题在会前已被机器拦下 | 出现公开材料，说明某组织取消评审会、全部交由 Agent 把关，且未出现口径事故 |

四条预测共享同一个判断：**工具链侧真正被改变的是交互方式与元数据的生产成本，而不是治理结构**。如果三年后回看发现相反——治理结构被工具整体替代——那就是本节判断错了，而这个错法是有信号的（见上表第四行）。

本节刻意不预测"AI 会不会取代数据工程师"。这个问题的答案取决于组织愿意把决策权交给谁，而不取决于模型能力；它得不出证伪信号，因而写进书里没有信息量。本节只预测那些**能被观察到的组织行为变化**——比如验收标准、评审会内容、上线范围的划分方式。

四条预测也共享一个方法论上的自觉：它们都可以在不依赖新数据的情况下被验证（看验收标准、看复盘结论、看上线范围怎么划）。这是本节坚持的写法——**预测的价值不在于它说中了什么，而在于它事先告诉你该看哪里**。

### 5.7 给架构师的行动建议

下表按"你现在的处境"组织。**"明确不要做"一列是本节的重点**——它列出的动作今天做的收益是假设的，代价却是当期的，而且大多会沉淀成很难拆除的结构。

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| **刚选完平台、准备建模** | 先把命名规范、分层前缀、Owner 必填定成规则（本章 §3.5 的反模式清单可直接当检查项） | 平台 Copilot 的**评审通过率**与生成物首次运行成功率 | 不要为了"AI 就绪"改建模流程；不要在没有规则的情况下引入任何自动评审 |
| **业务方催着要自然语言取数** | 先确认目标域有没有集中的度量定义（OSCAR 一类指标模型） | 同义问题的答案一致率；失败样本里"算不对"的占比 | 不要在裸表上开放自然语言取数——那是把口径债搬到前台 |
| **目录里的元数据常年空缺** | 只补机器必须读的字段：一句话含义、口径、Owner、密级、粒度声明 | Agent / Copilot 取数失败能否追溯到具体缺失字段 | 不要先上 AI 标签生成；错的标签会被下游以机器速度放大 |
| **打算用 AI 自动评审 PR** | 先把规范写成能跑的规则并接进门禁（这一步不依赖模型） | 是否出现第三方公开的 Agent 评审效果材料 | 不要让 Agent 拥有"阻断但不解释、通过但不担保"的权力 |
| **准备引入 GraphRAG / 本体** | 先确认模型元数据本身已完整、已有 Owner 与血缘 | 是否出现公开的生产案例与维护责任约定 | 不要为图或本体预留存储与 schema——它们是第二份会过期的状态 |
| **在做湖仓格式选型** | 按常规选型流程评估（L1），同时核对引擎对目标规范条目的实际支持面 | 规范条目在引擎侧的落地速度 | 不要把规范里的新条目当作表结构设计的前提 |
| **预算里没有 AI 调用项** | 把推理调用成本单列一项，并指定一个用量负责人（对应 5.3 最后一行） | 月度调用量与账单是否可解释 | 不要在成本归属不清时开放全公司范围的自然语言取数 |
| **打算用 AI 生成模型文档** | 明确生成物只作候选稿，进代码评审（改动可回滚） | 人工修正比例是否下降 | 不要让生成内容直接写回目录或文档系统 |
| **告警太多、想上自动归因** | 先补告警的上下文：责任人、影响的下游、历史同类事件 | 归因结论被值班人采纳的比例 | 不要让自动归因结论直接触发回滚或改配置 |

"明确不要做"这一列的共同点是：**它们都是在为一条尚未成熟的机制提前支付架构成本**——而且这个成本大多不是钱，是结构：预留的存储、写在 schema 里的第二份状态、以及被绕过的评审流程，都会在一年后变成很难拆掉的东西。

这张表还藏着一个次序：**每一行的"现在就该做"都不依赖任何 AI 组件**。命名规范、Owner 必填、度量定义、血缘采集、成本归属——这些是工具链的底座工程，做不做与 AI 无关，但 AI 能力能不能用起来完全取决于它们。所以本节的实际建议可以压缩成一句话：先把底座补到"机器可用"，再谈 AI。

### 5.8 小结

> 本节小结：工具链侧 AI 真正改变的**不是工具的能力边界，而是两件事**——元数据与产物的**生产成本**（DDL、ETL、标签从"人写"变成"生成候选 + 人确认"），以及**交互入口的形态**（从菜单式操作变成提问式入口）。它没有改变的是治理结构：**元数据必须有人负责、口径必须只有一份、变更必须有人签字**——这三条在本章 §1、§2、§4 里就已经成立，AI 只是让不满足这三条的组织更快地暴露问题。所以本节列的 AI 方向没有一个够 L1，唯一 L1 的是它们脚下的湖仓表格式与平台底座。
>
> 如果只记一句：**工具链上的 AI 能力，本质是给底座质量做的一次压力测试**——底座合格的组织用它提效，底座欠账的组织用它把问题暴露得更快。
