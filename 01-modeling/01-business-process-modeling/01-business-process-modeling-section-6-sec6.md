## 6. 落地实践

### 6.1 阿里"**OneData 业务过程切片**"6+ 年（2014-2020）

**背景（Why）**

阿里 2014 年面临**中台口径失控**：
- **30+ 业务线**——淘宝 / 天猫 / 支付宝 / 菜鸟各自数仓，**同一个「成交」有 20 种口径**
- **指标爆炸**——报表要新指标，**直接建新表**，3 年堆出 30 万+ 指标
- **新业务接入慢**——建一套指标要 **6 个月**，业务等不起

**触发点（What）**

2014 年阿里启动 **OneData 业务过程切片**（[阿里 OneData 2014]），目标：
- **指标口径统一率**——**60% → 95%**
- **新业务接入**——**6 个月 → 6 周**
- **业务过程覆盖**——**6 大业务过程全覆盖**

**详细做法（How）**

阿里 OneData 业务过程切片的**5 大核心组件**：

1. **自顶向下业务过程识别（核心创新）**
   - 关键设计：**不按部门切，按业务过程切**——流量 / 交易 / 营销 / 履约 / 售后 / 财务
   - 关键能力：**跨部门口径对齐**——同一「成交」在 6 个过程里有唯一定义
   - 关键数字：**6 大业务过程**，覆盖 **30+ 业务线**
   - 三级映射示例：
     ```
     业务过程           原子指标          复合指标
     ─────────────────────────────────────────────
     交易.下单          order_cnt         支付率 = 支付单数 / 下单数
     交易.支付          pay_cnt           客单价 = 支付金额 / 支付单数
     交易.退款          refund_cnt        退款率 = 退款单数 / 支付单数
     ```

2. **业务过程地图（核心）**
   - 关键设计：**过程 → 事件 → 事实表**的映射表，一图看全
   - 关键能力：**新需求先查图**——已有过程直接复用，缺失才新建
   - 关键数字：**重复建模 -60%**

3. **指标体系（核心）**
   - 关键设计：**原子指标 + 复合指标**两级，**复合必须由原子组合**
   - 关键能力：**口径可追溯**——每个数字能追到原子指标定义
   - 关键数字：**口径统一率 60% → 95%**

4. **OneModel 落地（核心）**
   - 关键设计：**业务过程 → ODS/DWD/DWS/ADS 分层映射**
   - 关键能力：**建模有章可循**，不靠个人经验
   - 关键数字：**新业务接入 6 周**

5. **数据资产目录（核心创新）**
   - 关键设计：**过程 / 指标 / 表三者互相索引**
   - 关键能力：**业务方自助找数**
   - 关键数字：**自助查找命中率 80%**

**阿里 OneData 业务过程切片关键数字**（[阿里 OneData 2014-2020 公开数据]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **指标口径统一率** | 60% | 95% | **+58%** |
| **新业务接入周期** | 6 个月 | 6 周 | **-75%** |
| **业务过程覆盖** | 0 | 6 大 | **∞** |
| **重复建模** | 基线 | -60% | **-60%** |
| **自助查找命中率** | 30% | 80% | **+167%** |
| **业务线覆盖** | 30+（各自为政） | 30+（统一） | **统一** |

**具体数字（How much）**

- 团队规模：阿里数据中台千级人员规模
- 关键数字：**6 大业务过程**；**口径 95%**；**新业务 6 周**
- 业务影响：覆盖**阿里全集团 30+ 业务线**，并沉淀为对外「数据中台」方法论

**失败教训**

- 早期「**30+ 业务线各建一套指标**」——同一个「成交」有 20 种口径、新业务接入要 6 个月，倒逼**「业务过程切片」**
- 「**按部门切业务过程**」——第一版按组织架构切片，组织一调整模型就崩，倒逼**「按业务过程切，与组织解耦」**
- 「**过程切得过细**」——把「登录」「退出」拆成两个过程、过程数膨胀到 300+，倒逼**「按同一原子活动合并」**
- 「**只建过程不做治理**」——过程数自由生长、三年翻倍，倒逼**「过程变更走评审」**

### 6.2 字节跳动"**DataFinder 业务过程自动发现**"5+ 年（2019-2024）

**背景（Why）**

字节 2019 年面临**业务迭代速度碾压建模速度**：
- **每周数十个新功能**——人工梳理业务过程**根本跟不上**
- **埋点文档滞后**——新功能上线时埋点文档还没写
- **数据接入排队**——数据团队成为瓶颈，业务等 2 周

**触发点（What）**

2019 年字节启动 **DataFinder 业务过程发现**（[字节技术博客 2019]），目标：
- **业务过程识别覆盖率**——**60% → 90%**
- **新功能数据接入**——**2 周 → 2 天**
- **自动更新**——埋点变更自动触发过程地图更新

**详细做法（How）**

字节 DataFinder 的**5 大核心组件**：

1. **LLM 业务过程识别（核心创新）**
   - 关键设计：**LLM 读 PRD + 埋点定义 → 输出候选业务过程**
   - 关键能力：**人在回路**——LLM 出候选，数据同学评审 5 分钟
   - 关键数字：**识别覆盖率 60% → 90%**
   - 调用示意：
     ```python
     prompt = f"""你是数据建模专家。阅读以下 PRD 与埋点定义，
     输出业务过程候选，格式为 JSON：
     {{"process": "...", "events": [...], "atomic_metrics": [...]}}
     PRD: {prd_text}
     埋点: {tracking_spec}
     要求：只输出「有状态流转」的过程，合并同一原子活动。"""
     processes = llm.invoke(prompt)  # 结构化输出
     ```

2. **Agent 监控埋点变更（核心）**
   - 关键设计：**Agent 订阅埋点平台变更流**，新增埋点即触发识别
   - 关键能力：**无人值守——埋点平台一有变更就自动触发识别，不必人工定期巡检**
   - 关键数字：**变更响应 < 10 分钟**

3. **自动更新过程地图（核心）**
   - 关键设计：**LLM 输出 → 人工确认 → 自动写入模型元数据**
   - 关键能力：**过程地图常新——LLM 输出经确认后直接写回模型元数据，不必靠人定期重画**
   - 关键数字：**地图新鲜度 95%+**

4. **业务过程评审（核心）**
   - 关键设计：**评审只做「合并 / 否决」两件事**，降低评审成本
   - 关键能力：**评审 5 分钟/个**
   - 关键数字：**评审通过率 75%**

5. **自进化（核心创新）**
   - 关键设计：**评审结果回流**训练 prompt，逐步减少人工
   - 关键能力：**越用越准——评审结果回流训练 prompt，同类过程的判断不必每次从头做起**
   - 关键数字：**人工介入率 3 个月降 40%**

**字节 DataFinder 关键数字**（[字节技术博客 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **业务过程识别覆盖率** | 60% | 90% | **+50%** |
| **新功能数据接入** | 2 周 | 2 天 | **-86%** |
| **变更响应** | 人工（天级） | < 10 分钟 | **-99%** |
| **过程地图新鲜度** | 60% | 95%+ | **+58%** |
| **评审成本** | 30 分钟/个 | 5 分钟/个 | **-83%** |
| **人工介入率** | 100% | 60%（3 个月内） | **-40%** |

**具体数字（How much）**

- 团队规模：字节 DataFinder / 数据建模团队 30+ 人
- 关键数字：**覆盖率 90%**；**接入 2 周 → 2 天**；**LLM 自动发现 100%**
- 业务影响：覆盖**字节全部业务**的数据接入链路

**失败教训**

- 早期「**每周数十个新功能，人工梳理业务过程根本跟不上**」——数据接入排队两周，倒逼**「LLM 自动识别业务过程」**
- 「**LLM 全自动写入模型**」——无人审核时幻觉造出「不存在的业务过程」并污染模型，倒逼**「改为人机协同：LLM 出候选、人评审 5 分钟」**
- 「**只读 PRD 不读埋点**」——PRD 描述意图、埋点描述事实，只读 PRD 识别出的过程约 50% 落不了地，倒逼**「两者对齐后取交集」**
- 「**评审结果不回流**」——每次都要人从头判断、准确率不涨，倒逼**「把评审结果回流训练 prompt，人工介入率逐月下降」**

### 6.3 美团"**业务过程地图 + 5+ 业务统一**"4+ 年（2020-2024）

**背景（Why）**

美团 2020 年面临**5+ 业务过程各建各的**：
- **5+ 业务**（外卖 / 到店 / 酒店 / 出行 / 买菜）——**「下单」在 5 个业务有 5 套定义**
- **跨业务分析做不了**——「外卖用户订酒店的比例」要靠人工对齐
- **新业务接入**——3 个月

**触发点（What）**

2020 年美团启动**业务过程地图**（[美团技术博客 2020]），目标：
- **5+ 业务统一过程**——同一过程唯一定义
- **新业务接入**——**3 个月 → 2 周**
- **过程统一率**——**60% → 90%+**

**详细做法（How）**

美团业务过程地图的**5 大核心组件**：

1. **业务过程地图（核心创新）**
   - 关键设计：**统一过程库**——`下单 / 支付 / 履约 / 完成 / 退款` 五段式
   - 关键能力：**5 业务共用一套过程骨架**
   - 关键数字：**过程统一率 60% → 90%+**
   - 骨架示意：
     ```
     [下单] → [支付] → [履约] → [完成]
                  ↓
               [退款]（旁路）
     外卖：下单→支付→骑手接单→送达
     酒店：下单→支付→酒店确认→入住
     出行：下单→支付→司机接单→到达
     ```

2. **OneData 思想（核心）**
   - 关键设计：**过程 → 原子指标 → 复合指标**
   - 关键能力：**跨业务指标可比**
   - 关键数字：**口径统一 90%+**

3. **价值流图（核心）**
   - 关键设计：**从客户触点反推过程**，穷举所有触点
   - 关键能力：**防遗漏**——「补发」这类低频过程也能被发现
   - 关键数字：**过程遗漏率 < 5%**

4. **业务自助（核心）**
   - 关键设计：**业务方在过程地图上自助挂指标**
   - 关键能力：**数据团队不再是瓶颈**
   - 关键数字：**自助率 70%**

5. **过程治理（核心创新）**
   - 关键设计：**过程变更必须走评审**，防止自由生长
   - 关键能力：**过程数可控——过程变更必须过评审闸门，挡住"每个新需求都新起一个过程"的膨胀**
   - 关键数字：**过程数 3 年增长 < 20%**

**美团业务过程地图关键数字**（[美团技术博客 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **过程统一率** | 60% | 90%+ | **+50%** |
| **新业务接入** | 3 个月 | 2 周 | **-83%** |
| **过程遗漏率** | 20% | < 5% | **-75%** |
| **业务自助率** | 30% | 70% | **+133%** |
| **过程数增长（3 年）** | 失控 | < 20% | **受控** |
| **覆盖业务** | 5+ | 5+ 统一 | **统一** |

**具体数字（How much）**

- 团队规模：美团数据团队（此处为**数据平台部**口径，约 300+ 人；集团数据团队巅峰期约 2000+ 人 —— 两个数字的主语不同，见 [美团案例 §1.3](../../15-case-studies/04-meituan-feature-store/04-meituan-feature-store.md)【经验】）
- 关键数字：**5+ 业务统一**；**过程统一 90%+**；**新业务 2 周**
- 业务影响：覆盖**美团 5+ 业务线**

**失败教训**

- 早期「**5 个业务 5 套「下单」定义**」——跨业务分析只能人工对齐，倒逼**「统一过程地图」**
- 「**强推统一过程**」——第一版要求 5 个业务立刻改成同一套、业务方强烈抵触，倒逼**「新业务必须统一 + 老业务逐步迁移的双轨策略」**
- 「**只建过程不管指标**」——过程统一了但指标仍各写各的，倒逼**「强制绑定『过程 → 指标』」**
- 「**价值流图缺失**」——低频过程（如「补发」）长期被漏掉、数据缺口无人知，倒逼**「从客户触点反推、穷举全部过程」**

### 6.4 Uber"**业务过程 + 实时指标**"5+ 年（2019-2024）

**背景（Why）**

Uber 2019 年面临**全球实时业务过程**：
- **全球出行 / 外卖**——**时区跨越 24 小时**，「当天」的定义各地不同
- **实时决策**——派单 / 定价要**秒级业务过程状态**
- **线下 → 线上过程割裂**——骑手取餐 / 送达是线下事件，**如何进模型**

**触发点（What）**

2019 年 Uber 启动**业务过程 + 实时指标**（[Uber Engineering 2019]），目标：
- **全球统一过程定义**（含时区处理）
- **实时过程状态**——秒级
- **线上线下贯通**

**详细做法（How）**

Uber 业务过程 + 实时指标的**5 大核心组件**：

1. **实时业务过程（核心创新）**
   - 关键设计：**Flink + Kafka 建模过程状态机**——`trip_created → driver_assigned → picked_up → completed`
   - 关键能力：**过程状态实时可查**
   - 关键数字：**状态延迟 < 1s**
   - 状态机示意：
     ```sql
     -- Flink 过程状态机（简化）
     CREATE VIEW trip_process AS
     SELECT trip_id,
            MATCH_RECOGNIZE(
              PARTITION BY trip_id ORDER BY ts
              MEASURES
                FIRST(created.ts)  AS t_created,
                LAST(assigned.ts)  AS t_assigned,
                LAST(pickup.ts)    AS t_pickup,
                LAST(complete.ts)  AS t_completed
              PATTERN (created assigned* pickup? complete?)
              DEFINE created  AS type='TRIP_CREATED',
                     assigned AS type='DRIVER_ASSIGNED',
                     pickup   AS type='PICKED_UP',
                     complete AS type='COMPLETED'
            ) FROM trip_events GROUP BY trip_id;
     ```

2. **实时指标（核心）**
   - 关键设计：**过程状态 → 实时指标**（在线时长 / 接单时长 / 履约率）
   - 关键能力：**运营实时看板——在线时长 / 接单时长 / 履约率按当前时段呈现，而不是昨天的离线报表**
   - 关键数字：**指标延迟 < 5s**

3. **业务过程地图（核心）**
   - 关键设计：**全局过程地图**，含线上 + 线下事件
   - 关键能力：**跨市场可比**（不同城市同一套过程）
   - 关键数字：**过程统一率 95%**

4. **实时数据血缘（核心）**
   - 关键设计：**过程 → 指标 → 看板血缘实时更新**
   - 关键能力：**指标异常快速定位**
   - 关键数字：**排障时间 -60%**

5. **全球集成（核心创新）**
   - 关键设计：**时区 + 本地化过程差异**统一处理
   - 关键能力：**全球一套口径——各市场只按本地时区做呈现，底层过程定义与指标算法是同一套**
   - 关键数字：**覆盖 70+ 国家**

**Uber 业务过程关键数字**（[Uber Engineering 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **过程状态延迟** | 分钟级 | < 1s | **-99%** |
| **实时指标延迟** | 小时级 | < 5s | **-99.9%** |
| **过程统一率** | 70% | 95% | **+36%** |
| **排障时间** | 基线 | -60% | **-60%** |
| **覆盖国家** | 30+ | 70+ | **+133%** |
| **跨市场可比** | 不可做 | 可行 | **∞** |

**具体数字（How much）**

- 团队规模：Uber 数据平台团队 200+ 人
- 关键数字：**状态延迟分钟级 → < 1s**；**指标延迟小时级 → < 5s**；**覆盖国家 30+ → 70+**
- 业务影响：覆盖**Uber 全球出行 / 外卖**

**失败教训**

- 早期「**过程状态靠离线跑批**」——运营看到的是昨天的数据，倒逼**「实时业务过程状态机」**
- 「**时区当小事**」——第一版按 UTC 切「当天」，亚太区日报永远缺 8 小时数据，倒逼**「业务本地时区 + 全局 UTC 双写」**
- 「**线下事件不进模型**」——骑手「已取餐」是线下扫码，只在 App 埋点导致漏埋，倒逼**「App + 商家端 + 骑手端三路事件合并」**
- 「**跨市场过程定义不统一**」——各城市同一过程各自定义、横向对比做不了，倒逼**「全局过程地图 + 本地化只作参数」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**事件风暴工作坊**」（**最简单**）——**5-15 个业务过程**
- 工具：**Miro + draw.io**，产出「过程 → 事件 → 指标」三列表
- 团队：**2-3 人**（业务 + 数据）
- 验证标准：**核心过程 100% 覆盖**、**过程命名无歧义**

**1 → 10 阶段：6-12 个月**

- 扩展到「**30-80 个业务过程**」
- 引入「**业务过程地图**」**（**必须**）**——过程 / 事件 / 事实表三层映射
- 引入「**OneData 思想**」——原子指标 → 复合指标
- 团队：5-10 人
- 验证标准：**口径统一率 ≥ 85%**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务过程**」
- 引入「**LLM 半自动抽取 + Agent 自进化**」**（**生产**）**——应对业务高速迭代
- 引入「**实时过程状态机**」（Flink）
- 团队：10-30 人

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 美团 / Uber）印证：**业务过程建模不是「流程图」，是「业务过程切片 + 过程地图 + 价值流 + LLM 自进化 + 实时状态机」5 件套**。
> - 关键时间线：阿里 6+ 年 / 字节 5+ 年 / 美团 4+ 年 / Uber 5+ 年 —— **业务过程建模是 4+ 年长期工程**。
> - 选型第一原则：「**事件风暴工作坊**」（**最简单**）——**5-15 业务过程** → 「**过程地图 + OneData 思想**」（**必须**）→ 「**LLM 半自动抽取 + 实时状态机**」（**生产**）→ 「**GraphRAG 业务过程 + 全球统一**」（**AI 时代**）。
> - 99% 的失败来自「**按部门切过程 + 过程爆炸 + LLM 全自动写模型**」——必须有 **按过程切 + 原子活动合并 + 人在回路**。
> - 真正的 ROI 来自「**接入周期 -75% + 口径统一 95% + 实时延迟 -99%**」——是**大厂核心业务过程建模基础设施的命脉**。
