### 3.1 Dan Linstedt"**Data Vault 2.0 标准化**"11+ 年（2013-2024）

**背景（Why）**

Dan Linstedt 2013 年面临**敏捷数仓缺标准**：
- **2000 年** Data Vault 1.0 提出——**只剩 Hub + Link + Satellite 三件套**，缺方法论
- **2013 年** 传统 Inmon / Kimball 数仓——**改一次模型要动全链路**，典型「**6 个月才能上一张新表**」
- **企业痛点**——**业务变更频繁** + **审计要求历史可回溯** + **多源整合**，传统范式两头不讨好

**触发点（What）**

2013 年 Dan Linstedt 发布 **Data Vault 2.0**（[Data Vault Alliance 2013]），目标三条硬指标：
- **敏捷交付**——新源接入 **2 周**而非 **6 个月**
- **可审计**——**100% 历史可回溯**，任何时点可重放
- **可并行**——多团队同时开发同一模型不冲突

**详细做法（How）**

Data Vault 2.0 的**5 大核心组件**：

1. **Hub（业务键）**——核心创新
   - 关键设计：只存 **业务键** + **Hash Key** + **Load Date** + **Record Source**，**不含任何描述属性**
   - 关键能力：业务键唯一 + 不变性——**业务键永不变形**，变更只发生在 Satellite
   - 关键模式：
     ```sql
     CREATE TABLE hub_customer (
       customer_hk    CHAR(32)     NOT NULL,  -- MD5(business_key)
       customer_bk    VARCHAR(64)  NOT NULL,  -- 业务键，如手机号
       load_date      TIMESTAMP    NOT NULL,  -- 首次入库时间
       record_source  VARCHAR(64)  NOT NULL,  -- 来源系统
       CONSTRAINT pk_hub_customer PRIMARY KEY (customer_hk)
     );
     ```
   - 关键价值：**多源同键自动归并**——三个系统同一个手机号，Hub 里只有一行

2. **Link（关系）**——核心
   - 关键设计：只存 **参与方 Hash Key** + **Load Date** + **Record Source**，**不含度量**
   - 关键能力：**关系可追溯**——「客户 A 在 2019 年买过商品 B」这条关系本身带时间戳
   - 关键价值：**关系先于事实**——Link 建好后，事实表可后补

3. **Satellite（属性）**——核心
   - 关键设计：卫星表挂 Hub 或 Link，**每条属性变更一行**，含 `load_date` + `load_end_date` + `hash_diff`
   - 关键能力：**SCD Type 2 天然实现**——不需要额外拉链表设计
   - 关键优化：`hash_diff` 只对比变化的属性，**避免全列比对**

4. **Effectivity Satellites（时效卫星）**——核心
   - 关键设计：记录**关系生效区间**（`effective_from` / `effective_to`）
   - 关键能力：解决「**同一关系在不同时间点是否成立**」——如员工部门调动的历史归属
   - 关键价值：**审计场景刚需**——监管问「2019 年 3 月这笔业务归属哪个部门」可直接答

5. **Hash Key + 标准化**——核心创新
   - 关键设计：**所有键统一 MD5/SHA-1 32 位字符**，跨源可比对
   - 关键能力：**并行加载**——不同源可同时跑，不依赖中心序列
   - 关键价值：**天然支持实时**——无序列号冲突，流批可并行写同一 Hub

**Data Vault 2.0 关键数字**（[Data Vault Alliance 2013 公开数据]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **新源接入周期** | 6 个月 | 2 周 | **-92%** |
| **模型变更影响面** | 全链路 | 单 Satellite | **收敛到 1 张表** |
| **历史可回溯** | 部分 | 100% | **∞** |
| **并行开发冲突** | 频繁 | 无（Hash Key） | **-100%** |
| **采用企业** | 0 | 100+ | **∞** |
| **团队规模** | — | 100+ 公司 | **—** |

**具体数字（How much）**

- 团队规模：Data Vault Alliance 生态 100+ 公司
- 关键数字：**100+ 公司采用**；**Hub + Link + Satellite 标准化**；**新表上线 6 个月 → 2 周**
- 业务影响：覆盖**全球敏捷数据仓库**，成为金融 / 电信 / 航空审计型数仓的默认范式

**失败教训**

- 早期「**传统数仓改一次业务变更牵动全链路**」——新增一张表要 6 个月，倒逼**「Data Vault 2.0 的 Hub / Link / Satellite 标准化」**
- 「**把 Data Vault 理解成三张表**」——漏掉 Effectivity Satellite，审计问「历史归属」时答不出，倒逼**「把时效卫星纳入必备组件」**
- 「**过度建模**」——把明细属性也拆成 Satellite，查询要 join 十几张表、性能反而不如原始范式，倒逼**「按访问模式合并 Satellite」**
- 「**Hash Key 用截断值**」——数据量上来后出现碰撞、归并出错，倒逼**「统一完整 32 位哈希」**

### 3.2 字节跳动"**Data Vault + OneData 30 万表**"5+ 年（2020-2024）

**背景（Why）**

字节 2020 年面临**表爆炸 + 敏捷交付**双重压力：
- **30 万+ 表**——抖音 / TikTok / 西瓜 / 今日头条各建各的，**同义表重复率 > 40%**
- **业务变更**——**每周数十个新功能上线**，传统范式跟不上
- **多源整合**——同一用户在 4 个 App 的表现要归并到一张宽表

**触发点（What）**

2020 年字节启动 **Data Vault + OneData 融合**（[字节数据中台 2020]），目标：
- **表数量**——**30 万 → 收敛**
- **新业务接入**——**2 周内**
- **指标口径**——**统一 95%**

**详细做法（How）**

字节 Data Vault + OneData 的**5 大核心组件**：

1. **Data Vault 模型层**——核心创新
   - 关键设计：Hub/Link/Satellite 建在 **DWD 层**，向上提供 OneData 语义层
   - 关键能力：**源系统变更只改 Satellite**，OneData 层不动
   - 关键规模：**Hub 数万个**，Link 数十万个，Satellite 百万级
   - 关键示意：
     ```text
     ┌─ OneData 语义层（口径可变）────────────────────────┐
     │  指标定义 / OneID / 数据服务                        │
     └──────────────────▲─────────────────────────────────┘
                        │ 语义映射（口径变 → 只改这一层）
     ┌──────────────────┴─────────────────────────────────┐
     │  Data Vault 底座（实体与关系不变）                   │
     │   hub_user ──link_user_app──▶ hub_app              │
     │      │                            │                │
     │  sat_user_attr                sat_app_attr         │
     │  （属性变更 → 新增 Satellite 行，底座结构不动）       │
     └──────────────────▲─────────────────────────────────┘
                        │ 4 个 App 源系统（抖音/TikTok/西瓜/头条）
     → 源变更只影响最底层，口径变更只影响最顶层，两层互不牵动
     ```

2. **OneData 集成**——核心
   - 关键设计：DV 提供"**不变的实体与关系**"，OneData 提供"**可变的指标口径**"
   - 关键能力：**口径变更不动底座**——改指标只改语义层
   - 关键数字：**指标口径统一率 60% → 95%**

3. **Hash Key 跨源归并**——核心
   - 关键设计：**用户 ID / 设备 ID / 订单 ID 统一 MD5**
   - 关键能力：**4 个 App 同一用户自动归并**，不需要额外 ETL
   - 关键数字：**归并准确率 98%+**

4. **Effectivity Satellites**——核心
   - 关键设计：记录「**用户在某 App 的活跃区间**」
   - 关键能力：支持「**2023 年 6 月这个用户算不算抖音用户**」这类时点查询
   - 关键价值：**A/B 实验归因**必备

5. **敏捷开发流程**——核心创新
   - 关键设计：**新源接入 = 建 1 Hub + 1 Link + 1 Satellite**，模板化生成
   - 关键能力：**自动化代码生成**，无需手写
   - 关键数字：**新源接入从 4 周 → 2 周**

   - 关键设计：**5 个 BU 共用一套 Hub/Link**，差异只在 Satellite

   - 关键设计：**跨 BU 统一 Hash 算法**，同一手机号 5 个 BU 算出同一个 HK

### 3.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**Data Vault 2.0 单源试点**」**（**最简单**）**——**10+ 表**
- 建「**1 Hub + 1 Link + 1 Satellite**」，验证 `hash_diff` 增量加载
- 团队：**2-3 人**（1 建模 + 1 开发 + 0.5 平台）
- 验证标准：**新源接入 ≤ 2 周**、**增量加载正确率 100%**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 业务 / 100+ 表**」
- 引入「**Hash Key 标准化**」**（**必须**）**——跨源统一 32 位 MD5
- 引入「**OneData 语义层**」——业务方不直接看 DV
- 团队：5-10 人
- 验证标准：**口径统一 ≥ 85%**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务 / 万级表**」
- 引入「**Effectivity Satellites**」**（**生产**）**——支持审计与时点查询
- 引入「**模板化代码生成**」——新源接入全自动
- 团队：10-30 人
- 验证标准：**新业务接入 ≤ 2 周**、**存储成本 -50%**

**100 → 1000 阶段：12-24 个月**

- 引入「**5 套 → 1 套**」**（**AI 时代**）**跨 BU 物理收敛
- 引入「**实时 DV**」——流批并行写同一 Hub
- 团队：30-100 人
- 验证标准：**跨 BU 归并准确率 ≥ 98%**、**存储成本 -80%**
