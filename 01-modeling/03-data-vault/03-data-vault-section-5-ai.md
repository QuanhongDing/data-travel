## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

同一份清单里藏着巨大的时间差。Data Vault 主题下的前沿里，「把 Satellite 落在开放表格式上、用追加写 + 快照读实现全量历史」已经有版本化的规范与实现，今天就能动手；而「Agent 自动感知源系统变更、自动生成新 Satellite 并接入流水线」目前没有可指名的第三方生产案例。把这两件事并列写成"趋势"，读者据此排期就会踩空：前者按试点排期能顺利落地，后者排了会变成一个没人敢验收的项目。

本节给每个方向一个级别，级别由**三条可核验判据**决定，不由感觉决定：

- **L1 生产可用**：① 已 GA 且有正式 release note；② 有第三方（非厂商、非项目承建方）公开生产案例；③ 接口稳定。三条**全中**才算 L1——可以排进路线图。
- **L2 可试点**：已可用但接口或生态未稳，或只有厂商 / 建设方自有案例，或只在小规模被验证。可以做 PoC，**不要做核心依赖**。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录，**不要在架构里预留假设**。

**第②条是本主题最难满足的一条。** 公开材料里"我们用 X 做了 Y"的绝大多数是**建设方自述**——自己做项目、自己写文章，按上面的定义落在 L2 里。本节对②的判定要求是：案例来自既不是能力提供方、也不是项目承建方的第三方。**第②条核不到就是 L2**，不存在"准 L1""L1 的边界案例"这类说法；判据也只有一套，不会在某个单元格里就地放宽。

**本主题下没有一个方向能三条全中。** 最接近 L1 的是「Satellite 的追加语义落到开放表格式」（Apache Iceberg / Delta Lake / Apache Hudi 一类）：① 与③都满足，缺的是②——本节列不出一个具名的、既不是表格式发布方也不是项目承建方的第三方生产案例；按判据它是 **L2**，不写成"准 L1"。它恰好也是四个方向里唯一**不是 AI 带来**的一个——把它放进 §5 的理由是：另外三个 AI 方向都以它为物理前提。没有稳定的追加与快照读，上层谈检索、谈自动演化都没有意义。

读本节时请守住四条命名与版本纪律：

- **区分产品名与能力名**：自然语言取数、自动语义层这类能力，在不同平台上叫法完全不同，不要张冠李戴。
- **区分已发布与预览**：自然语言查询类能力常以预览形式发布，预览不是既成事实。
- **区分论文原型与产品实现**：一篇讲自动建模的论文标题不等于任何产品里的开关。
- **区分表格式能力与建模规范能力**：删除文件、时间旅行属于**表格式**的能力，不是 Data Vault 规范的一部分；能把它们用起来，靠的是你的物化选择，而不是某个产品"内置了 Data Vault"。

判据之外还有一条取材纪律：每个方向都会给"读者可以怎么自己核验"。核验顺序固定——先查官方发布说明里有没有这条能力（这是①）；再查有没有**不是建设方**的人写过它在生产中的用法（这是②）；最后看接口有没有变过，一年内改过两次接口的方向，即使前两条满足也只能按 L2 排期。

需要提前说明一件事：**本节四个方向都够不到 L1**，但它们卡住的位置并不相同——

- 5.2.1 缺②：①（规范与实现都按版本发布）与③（读写实现声明兼容版本）都满足，但本节列不出一个具名的、既不是表格式发布方也不是项目承建方的第三方生产案例。"这个能力在业界很普及"与"有一个能被指名的第三方案例"是两件事，前者不能替后者。
- 5.2.2 缺②、③未稳：能力可用、有正式的发布说明，但公开材料里找不到"不是建设方"的生产案例。
- 5.2.3 缺②、③部分：能力可用，但各平台语义检索接口不同、无跨实现约定。
- 5.2.4 缺①、②，③未稳：连一条来自产品发布说明的能力描述都还没有——它目前是方向，不是能力。

| 演进方向 | 级别 | 判据（① release note / ② 第三方生产案例 / ③ 接口稳定） | 现在该做什么 |
| --- | :---: | --- | --- |
| **5.2.1 Satellite 的追加语义落到开放表格式**（Iceberg / Delta Lake / Hudi 的追加写、快照读与删除文件） | L2 | ① 有：表格式规范按版本发布——【公开】Apache Hudi 1.0 于 2024 年 12 月发布（Apache 官方发布公告与 release note），Iceberg 表规范 v2 对删除文件有正式定义；② **不满足**：采用方广泛，但本节列不出具名的、非表格式发布方、非承建方的第三方生产案例——判据要求的是"能被指名的案例"，不是"到处都在用"；③ 有：表规范按版本演进，读写实现各自声明兼容版本 | 先在一个数据域试点：把 Satellite 落在开放表格式上，不要自建时态列与拉链表 |
| **5.2.2 LLM 辅助 DV 建模与自然语言取数**（DDL → Hub / Link / Satellite；业务文档 → 实体属性矩阵；自然语言 → PIT / Bridge 查询；dbt 生态的 DV 包；各平台的自然语言查询能力） | L2 | ① 有：相关工具与平台有版本化的发布说明；② **缺**：公开案例多为平台方或承建方自述；③ 未稳：自然语言转 SQL 的正确率强依赖语义层定义质量，接口跨平台不可移植 | PoC：用在元数据补全与取数入口，不要用于生成生产模型 |
| **5.2.3 DV 作为检索底座**（Hub / Link / Satellite 映射进图与 RDF；Satellite 字段向量化；GraphRAG 一类图检索） | L2 | ① 有：向量检索与图查询已是主流湖仓与图平台的正式能力；② **缺**：公开案例多为平台方或承建方自述；③ 部分：语义检索接口各平台不同，无跨实现约定 | 先做只读的一项（例如把指标定义接进检索），不要复制整份数据 |
| **5.2.4 Agent 驱动的 DV 演化**（schema 漂移监听、质量、血缘、合规四类 Agent；自动生成新 Satellite 并接入流水线） | L3 | ① **缺**：无专门的 Agent 演化产品发布说明；② **缺**；③ 未稳 | 记录并做技术预研；不要写进架构假设 |

表里四个方向与 5.2 的四个小节一一对应，级别与"哪几条判据满足"在两边完全一致，且**没有一行达到 L1**。最接近 L1 的是 5.2.1，而它恰恰不是 AI 带来的变化——这一点值得停下来想一想：如果四个方向里最有底气的那个与 AI 无关，那么"AI 时代的前沿"在这条技术线上，更可能是**使用方式的改变**，而不是建模方法的重写。

**对厂商的具名工具，本节只按能力归入对应方向，不转述其能力声称。** 它们中的大多数属于**厂商的能力声称**（"某平台自动做 Data Vault"这一类），这是核查风险最高的一档：公开材料能证明产品页这么写，不能证明它在别人的库上做对了；本节既不背书这些声称，也不因为它们核不动就当作从未存在——自然语言取数一侧如 Databricks 的 Genie，检索底座一侧如向量库 ChromaDB / Milvus。

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 Satellite 的追加语义落到开放表格式

- **旧做法与它的卡点**：把"全量追加 + 可回溯"做出来，过去要自己解决三件事：
  - 幂等写入、快照隔离、删除标记——自建方案常在并发加载与回溯查询上反复出错，且错误只在补数时才暴露。
  - 传统数仓里做同一件事靠分区重写或拉链表：前者要停机窗口，后者要给每行维护起止日期、查询时必须过滤"当前有效行"，两者都随表宽度与变更频率变差。
  - 主文件 §2.4.2 指出"用 Data Vault 做集成层、用维度建模做消费层"是最常见的组合，而集成层的物理实现过去一直缺一个既支持追加又支持快照读的标准载体。
- **AI 改变了什么机制**：**这一条与 AI 无关**。改变机制的是**存储层把"追加写 + 按快照读 + 删除文件"变成表格式的一等公民**：Satellite 的 append-only 与 Effectivity Satellite 的软删除可以直接映射到表格式的追加与删除文件上，不再需要自建拉链表。写在这里是因为它是另外三个方向的地基。
- **由此得到的**：因为"每次变更写新行"在表格式里同时是写入语义与读取语义，所以 PIT 表可以把"取某时刻的版本"下推给存储层，而不必每次都做 GROUP BY 聚合；同一份 Satellite 能同时服务"当前视图"与"某历史时点视图"两种查询，时态从"要额外维护的列"变成"存储自带的维度"。
- **由此付出的**：
  - ① 小文件问题：append-only 天然产生高频小写入，必须靠定时 compaction 合并；compaction 的调度、资源与失败重试成为新的运维项，"写入简单了"的代价是把复杂度挪到了后台任务。
  - ② 时态语义的坑：表格式的时间旅行是**快照（加载）时态**，不是**业务时态**。主文件 §2.2.2 明确区分了业务时态、加载时态与删除时态——把表快照当成业务历史，在补数、迟到数据与回放场景下会给出错答案，而且看起来完全正常。
  - ③ 删除的两套语义并存：物理删除（走独立流程并留清单）与删除文件（软删除）同时存在时，谁先谁后、删除如何传播到物化视图与副本，需要治理约定；"只删源表不删副本"是这类项目最常见的事故形态。
  - ④ 实现锁定：各表格式的元数据与目录不通用，换实现要重写快照读取路径与目录集成。
  - ⑤ 能力迁移的盲区：把时态判断从"应用层写代码"挪到"依赖存储语义"之后，团队容易忘记**业务时态仍然要自己维护**，于是补数流程成为新的风险点。

| 你想做的事 | 表格式里的对应能力 | 需要自己补的部分 |
| --- | --- | --- |
| Satellite 全量追加 | 追加写 + 每次加载产生新快照 | 幂等键与迟到数据处理 |
| 查"某时点的画像" | 按快照读 + 元数据表查询 | PIT 表的切片逻辑 |
| 软删除（Effectivity Satellite） | 删除文件（位置删除 / 等值删除） | 删除语义与业务时态的对应关系 |
| 物理删除（走独立流程并留清单） | 行级删除 + 表重写 | 跨副本、跨物化视图的删除传播 |
| 历史快照回溯（审计） | 元数据表列出全部快照 | 保留策略与过期快照的清理计划 |

- **判定方法**：
  - 判断某表格式是否真能做 DV 风格软删除：看它的规范里有没有独立的**删除文件**概念，以及删除是否区分位置删除与等值删除两类；只有"支持 UPDATE / DELETE"的表述不够。
  - 判断你们的 Satellite 有没有正确使用时态：抽一条补数记录，问它在业务时态与加载时态下各应落在哪个日期。答不上来，就是两种时态被混用了。
  - 判断 compaction 计划够不够用：看最近一周的写入文件数与小文件占比，而不是看存储总量——小文件问题从总量上完全看不出来。
  - 判断保留策略有没有人管：查一下元数据表里最老的快照是什么时候的、谁定的过期规则。没人说得出来，就说明历史数据正在无声地增长成本。
- **证据与来源**：
  - 【公开】Apache Iceberg 表规范 v2 定义了两类删除文件（位置删除与等值删除），这是软删除能落成表格式能力的公开依据（规范中的 Delete Files 一节，请以官方规范仓库当前版本为准）。
  - 【公开】Apache Hudi 1.0 于 2024 年 12 月发布（Apache 官方发布公告与 1.0.0 release note）。需要澄清一点：MOR（Merge-On-Read）是 Hudi 早已存在的表类型，不要把它记成新特性；1.0 的公开变化集中在记录级索引与非阻塞并发控制（以该 release note 为准）。
  - 【公开】Delta Lake 的时间旅行与 MERGE 属其公开文档中的既有能力（官方文档的 Time Travel 与 MERGE 章节，请以当前文档版本为准）。
  - 各家云厂商的托管表格式文档可用来交叉核对"哪些能力属于表格式规范、哪些属于某一家实现"。
- **成熟度**：**L2**（① 有（规范按版本发布、2024 年有正式发布公告）；② 不满足（采用方广泛，但本节列不出具名的、非表格式发布方、非承建方的第三方生产案例）；③ 有（表规范按版本演进，实现声明兼容版本））。升级到 L1 的条件是可观察的：出现一份由非表格式发布方、非承建方发布的生产材料，写清规模、使用方式与时间——在那之前，"业界都在用"只能记在②之外。

#### 5.2.2 LLM 辅助 DV 建模与自然语言取数

- **旧做法与它的卡点**：传统 DV 建模由架构师读源系统 DDL 与业务文档，人工识别业务键、关系与属性分组。卡点具体在三处：
  - 建模是整个链路的第一环，它慢，下游集成全在等；而它同时又是最不能返工的一环——Hub 的业务键选错，后面所有 Link 与 Satellite 跟着错，返工代价最高（主文件 §2.3.1 的并行加载优势建立在构件划分正确的前提上）。
  - 消费侧同样窄：能遍历 Hub / Link / Satellite 并正确生成 PIT / Bridge 查询的人极少，业务问题要先被翻译成建模语言。
  - 元数据补全（表的业务含义、Owner、SLA）靠人写，写完就过期——这件事在 AI 时代的代价被放大：主文件 §1.3 把 Hub / Link 元数据称为 Agent 做"数据资产发现 + 数据语义推理"的**入口**，而入口能不能用，取决于这些条目有没有人持续维护。
- **AI 改变了什么机制**：把"读 DDL、读文档"这一步的**人力成本**换成 token 成本，并把取数入口从"人写 SQL"改成"人描述问题、模型写 SQL"。两件事改变的都是 Data Vault 的**上游（建模）与下游（消费）两侧的人力结构**——这是成本函数的变化，不是建模范式的变化：Hub / Link / Satellite 的形态一条都没动。
- **由此得到的**：因为候选模型可以被低成本地生成多份、再拿真实数据做**证伪**（业务键是否唯一、Link 的基数分布是否合理、属性的变更频率是否适合独立成 Satellite），所以建模从"一次做对"变成"生成候选 + 用数据筛掉错的那几份"。这与 5.2.1 提供的物理载体正好互补：物理变更便宜，才承受得起多试几轮。
- **由此付出的**：
  - ① 业务键选择、Satellite 拆分粒度是**语义裁决**，不是文本抽取；模型给出的候选"看起来都对"，而返工成本恰恰集中在这两处。
  - ② 自然语言取数的正确率强依赖语义层（指标与维度的定义）质量；没有语义层时模型只能猜表名，错得悄无声息。主文件 §1.3 说"Hub 表 = 实体字典、Link 表 = 关系字典"——这句话只有在元数据真的完整时才成立。
  - ③ 平台锁定：自然语言取数的接口与能力名称各平台不同，迁移要重写语义层与提示词，这部分没有任何标准可以依。
  - ④ 新的可信度问题：模型生成的 SQL 语法正确、结果量级合理，但口径错了（例如把"当前已支付订单"理解成"历史上曾支付过的订单"），这类错误在结果层面看不出来，只能靠口径回归集发现。

| 用法 | 模型能承担的部分 | 必须由人承担的部分 |
| --- | --- | --- |
| 从 DDL 提候选构件 | 分组属性、提名关系与业务键候选 | 业务键唯一性与稳定性裁决 |
| 从业务文档提实体属性矩阵 | 抽取实体、属性、术语 | 口径归属与粒度决策 |
| 自然语言取数 | 生成 SQL、组织答案 | 语义层定义、口径回归集 |
| 生成加载作业 | 生成模板化的加载与校验代码 | 幂等键与迟到数据处理 |

- **判定方法**：
  - 判断某个"自动 DV 建模"能力是不是真的：看它输出的是**候选清单**还是**可直接上线的 DDL**。前者是 L2，后者要追一句它怎么处理业务键唯一性——答不上来就不是生产能力。
  - 判断自然语言取数能不能上生产：先在语义层已覆盖的指标上问十个问题，把错因分三类（语义层缺口 / 选表错 / 口径错），看哪一类占多数，再决定补哪一层。
  - 判断模型给的业务键候选能不能用：拿它去源表上做一次唯一性检验（按候选键分组看有没有重复）。这一步不需要任何 AI 能力，却能筛掉大部分错候选。
  - 判断自然语言入口该不该对外开放：先看语义层覆盖了多少个对外承诺过的指标——覆盖率低时，开放入口的成本会以"口径争议"的形式出现。
- **证据与来源**：
  - 【公开】dbt 生态的 Data Vault 包（dbtvault，后更名 AutomateDV）有版本化发布，是"用代码模板生成 Hub / Link / Satellite"的公开实现（请以社区包注册处的当前版本为准）。
  - 各平台的自然语言查询能力（湖仓与云数仓厂商各有命名）多在 2024 年前后以预览或正式形式发布，名称不同、接口不可移植；它们是否支持"遍历 Hub / Link / Satellite 生成 PIT / Bridge 查询"，请按对应平台的官方文档核验，本节不代其断言。
  - 关于"用 LLM 自动生成 Hub / Link / Satellite 能省下多少建模时间"的百分比说法，本节不转述——这类数字没有可复现的评测口径。
- **成熟度**：**L2**（① 有（相关工具与平台有版本化发布说明）；② 缺（公开案例多为平台方或承建方自述）；③ 未稳（正确率随语义层质量变化，跨平台不可移植））。

#### 5.2.3 DV 作为检索底座

- **旧做法与它的卡点**：结构化数据长期进不了检索链路，卡点具体在三处：
  - 向量检索只吃文本，业务数据要经过"取数、导出、拼成段落"的手工流程，时效性与权限都不可控。
  - 即使进了向量库，检索到的是**记录级快照**（"某客户 2024 年是 VIP、订单总额若干"），而不是**指标**；聚合、时态切片与多跳仍要回 SQL。
  - 主文件 §1.3 给出了一条既有思路：Hub 表 = 实体字典、Link 表 = 关系字典、Satellite 表 = 属性字典——它描述的正是"把 DV 的结构当作检索骨架"这件事。
- **AI 改变了什么机制**：把 DV 的元数据从"给人看的建模产物"变成"给模型用的检索骨架"——实体识别、关系遍历与语义匹配各由一层承担。机制上是**接口形态的变化**（从单一 SQL 接口变成"向量 + 图 + 关系"的多入口），不是存储层变化，也没有改变 Satellite 的任何物理性质。
- **由此得到的**：因为 Link 表天然表达了实体之间的关系，所以多跳问题不需要在向量空间里做近似——直接在关系上遍历，召回是精确的；因为 Satellite 带时态，所以"某时点的状态"可以作为检索的过滤条件，而不是把不同历史版本混进同一个向量空间、让相似度替你决定用哪一版。
- **由此付出的**：
  - ① **第二份真源**：把 Satellite 向量化等于把数据复制到另一套存储里，列级权限、行级权限与删除（合规）都要在两处分别实现。本目录 [§3 §3.5（反模式 5：不区分 Raw Vault 与 Business Vault）](03-data-vault-section-3-sec3.md) 讲的是同一类问题的一个入口——把不该直接暴露的一层暴露出去，向量副本是这类问题的另一个入口。
  - ② 时效与一致性：向量副本的刷新与 Satellite 加载之间存在窗口，窗口内检索到的是旧值；这个窗口必须在答案里被标注出来，否则无从判断。
  - ③ 成本与变更率正相关：Satellite 是全量追加表，变更率高的 Satellite 向量化代价最高——**最需要实时语义的那部分数据，恰好是最贵的那部分**。
  - ④ 评测困难：检索质量与口径正确性是两个维度，混在一张评测表里会让两边都说不清，最后变成"感觉好像变好了"。
  - ⑤ 治理面翻倍：向量副本一旦上线就会有下游直接依赖它，此后每一次源表结构变更都要同时评估两条链路。

| 需求 | 用精确条件能否满足 | 是否值得向量化 |
| --- | --- | --- |
| 查某客户某时点的状态 | 能（主键 + 时态过滤） | 不值得 |
| 按自然语言找"相似的客户群" | 不能 | 值得，但要先定权限与删除方案 |
| 查两个实体之间有没有关系 | 能（Link 表遍历） | 不值得，且图上更准 |
| 从大段描述里定位相关实体 | 不能 | 值得，配合实体链接使用 |
| 从日志里找出"和这起投诉相似的事件" | 不能 | 值得，但不要把它当成事实源 |

- **判定方法**：
  - 判断某个 Satellite 该不该向量化：先看行数与变更频率，再看查询里有多少真的需要语义近邻。用精确条件能查到的，不要向量化。
  - 判断向量副本是否可接受：问一句"源表删了一行，向量库里那一行什么时候消失、由谁负责"。答不上来就先别做。
  - 判断该用图还是该用向量：问"我需要的是关系，还是相似"。要关系就用 Link 遍历，要相似才向量化——两者混着用，出问题时无法定位是哪一层错了。
  - 判断检索增强值不值得做：先看有没有一类问题因为"取不到结构化数据"而被长期搁置。没有这类问题，就是把技术当成目标。
- **证据与来源**：
  - 【公开】Microsoft GraphRAG 于 2024 年开源（同一项目由 Microsoft Research 于 2024 年公开配套论文，论文标题请以该项目仓库的 publications 页为准），它处理的是**非结构化文本**抽取出的图；把关系数仓的 Hub / Link 直接当作它的图输入属应用层组装，实体对齐与权限要自己解决。
  - 【公开】主流湖仓平台在 2024 年前后把向量检索做成平台能力（各平台命名不同，请按其官方发布说明核验），这让"关系表 + 向量"在同一存储内的组合成为可选项。
  - 关于"Data Vault 表自动同步为 RDF 三元组"的具体产品能力，请按对应产品的官方文档核验；把 Hub / Link / Satellite 映射为类与属性本身是应用层的映射工作，不依赖某个特定产品。
- **成熟度**：**L2**（① 有（向量检索与图查询已是主流平台的正式能力）；② 缺（公开案例多为平台方或承建方自述）；③ 部分（各平台语义检索接口不同，无跨实现约定））。

#### 5.2.4 Agent 驱动的 DV 演化

- **旧做法与它的卡点**：源系统加字段、改类型、上线新业务，靠人发现。卡点在三处：
  - 多数团队的做法是"下游任务失败后倒查"。Data Vault 解决了加字段的**物理成本**（加 Satellite 不改表），但没有解决"**谁发现变化**"——发现晚一天，损失就多一天。
  - 变更通知靠公告，回应率低；合规请求（删除某主体的数据）要靠人盘点它落在哪些 Hub、哪些 Satellite、哪些副本里。
  - 质量检查靠人维护阈值规则，而规则的维护速度跟不上源系统变化，最终规则集本身成了过期资产。
- **AI 改变了什么机制**：把"发现变化"与"提出处置方案"这两步的成本压到接近零，但**没有改变"批准变化"的成本**——审批要人做，而且批准一条 Satellite 拆分决策需要业务判断。机制上是**人机分工的变化**（人从执行者变成裁决者），不是 Data Vault 规范的变化。
- **由此得到的**：因为提议可以低成本批量生成，"发现"不再是瓶颈；同时因为裁决仍是人工，系统真正需要的是**一条分流线**：把低风险变更自动放行、把高风险变更送去评审。"只新增 Satellite、不动 Hub 业务键"天然属于低风险类；"改 Hub 业务键"或"合并 Satellite"属于高风险类。这条线不建出来，自动化产出的就是待办队列而不是演化。
- **由此付出的**：
  - ① 提议堆积：一个塞满未合并提议的模型仓库，对下游的可信度低于一个长期不动的仓库——因为没人能确认哪一份是"现行版本"。
  - ② 误判风险：Agent 判断不了"新增的源字段是不是同一业务语义的另一个名字"，把同义字段建成两个 Satellite 是最常见的自动化错误，而且它不会报错，只会让下游口径悄悄分叉。
  - ③ 责任不明：自动生成的 Satellite 口径错了，是模型的责任、平台的责任，还是审批人的责任？这个问题不回答，组织不会让它进生产。
  - ④ 合规删除的复杂度：Agent 能定位数据，但删除要跨 Satellite、物化视图、向量副本与下游导出；物理删除与软删除（Effectivity Satellite 的 T_del）是两套语义，混用会既没删干净、又丢了历史。
  - ⑤ 测试形态变化：自动生成的构件没有对应的人工设计文档，回归测试要从"验证设计"转成"验证约束"，否则改动无法被证明是安全的。

| 变更类型 | 风险 | 可否自动合并 |
| --- | --- | --- |
| 新增 Satellite（不动 Hub 业务键） | 低 | 可以，配合回归校验 |
| 新增属性到既有 Satellite | 低到中 | 需校验口径归属 |
| 新增 Link | 中 | 需校验基数与关系语义 |
| 修改 Hub 业务键 | 高 | 不可以，必须人工裁决 |
| 合并 / 拆分 Satellite | 高 | 不可以 |
| 新增源系统 | 中 | 不可以，需人工确认与既有 Hub 的对应关系 |

- **判定方法**：
  - 判断一个"自演化"方案是否可用：问它把变更分成几类、哪几类自动合并、误判之后怎么回滚。三个问题答不全，就还是演示。
  - 判断你们的 DV 是否具备接 Agent 的条件：看 Hub 的业务键定义有没有唯一性约束与文档。没有这一条，任何自动提议都无从校验。
  - 判断自动化有没有失控：统计最近一个季度"自动提议被采纳"与"被驳回"的比例，以及驳回理由的重复率——重复率高说明缺的是分流线，不是模型不够好。
  - 判断该不该先做分流线再做 Agent：看现在一个月有多少次源系统变更。变更少的时候，自动化解决的是不存在的问题。
- **证据与来源**：
  - 【公开】MCP（Model Context Protocol 官方规范文档，2024 年 11 月公开；版本演进请以官方规范当前版本为准）解决的是工具发现与调用，规范本身不含"该不该改模型"这类裁决语义；把元数据平台接进 Agent 属应用层集成，请以其官方规范与对应元数据平台的文档为准。
  - 关于"某平台自动维护 Data Vault"的具体能力，请按该平台的官方文档核验；"多 Agent 自动设计 DV 模型"目前只见于演示与社区项目，本节不给生产结论。
  - 社区里出现过把 Agent 框架与 dbt 生态的 DV 包组合起来的项目：判断这类项目是否仍活跃，只看两项——最近一次提交时间，以及未关闭 issue 的积压量与关闭率。
- **成熟度**：**L3**（① 缺（无专门的 Agent 演化产品发布说明）；② 缺；③ 未稳）。

### 5.3 与本主题既有栈的接口在哪

判断标准是接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。凡是说不清失败归属的"结合"，在评审会上听起来完整，在事故复盘时提供不了任何信息。

还有一条更实际的理由：Data Vault 这一侧的构件几乎都是**可替换**的（表格式可以换、建模工具可以换、检索组件可以换），真正难换的是**边界上的契约**——尤其是"删除"和"权限"这两类必须穿透所有副本的东西。

边界上最难的两件事，恰好都不属于 Data Vault 规范的内容：

- **删除**：一条记录在 Satellite 里是"加一行失效标记"，在向量副本里是"删一个向量"，在物化视图里是"重算并覆盖"。三种动作的语义与时机都不同，而合规审查只看最后一种是否真的发生了。
- **权限**：列级权限在源表上由存储或目录执行，在副本上必须重新对齐；副本权限一旦放宽，前面为保护 Raw Vault 做的所有工作都白做。

```text
源系统变更 ──► 加载作业（幂等 + 迟到处理）
                    │  写入追加行 / 删除文件
                    ▼
       开放表格式（Satellite 表 + 快照）
                    │
      ┌─────────────┼──────────────┬───────────────┐
      ▼             ▼              ▼               ▼
  PIT / Bridge  语义层与取数   图 / RDF 映射   向量索引
 （切片下推）   （模型取数入口） （实体对齐）  （权限 + 删除要再实现）
      └─────────────┴──────────────┴───────────────┘
                    ▼
              合规删除：必须沿这张图逐跳传播
── 边界上只有两件事不能在副本侧"将就"：列级权限与删除语义
```

下表最后一列的 L 级**沿用 §5.1 的三条判据**（① 正式发布说明 / ② 第三方生产案例 / ③ 接口稳定），但评级对象是**接口**——谁调用谁、数据以什么形态穿过边界——不是 5.2.x 的演进方向。为避免读者把这里的级别读成对某个方向的改判，凡与某个 5.2.x 方向对应的行，级别与该方向**一致**，并在"现状"列注明对应关系。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Satellite → 开放表格式 | 每次加载写新行（或删除文件），读端按加载时态与业务时态取版本 | 加载作业的 Owner——写入幂等与迟到数据处理是它的责任，存储层不替它判断 | L2（对应 5.2.1，同一结论：①③满足、缺②） |
| Hub / Link 元数据 → 语义层与取数 | Hub 表作为实体字典、Link 作为关系字典（主文件 §1.3）；模型通过指标定义取数，不直接遍历物理表 | 语义层定义的 Owner——口径错不在模型，在定义 | L2（对应 5.2.2） |
| Satellite 字段 → 向量索引 | 向量由 Satellite 字段加文本化模板生成；接口是 embedding 版本、刷新窗口与列级权限 | 向量索引 Owner——权限与删除要在副本上再实现一遍 | L2（对应 5.2.3） |
| Hub / Link / Satellite → 图与 RDF | 类与属性映射，Same-As Link 作为等价边；接口是 IRI 命名与对齐结果 | 实体对齐的维护方——两个 Hub 连错是建模的错，不是图的错 | L2（对应 5.2.3，同一结论；映射是自建工作，无标准约定） |
| Effectivity Satellite → 合规删除 | T_del 标记加下游副本的同步删除，接口是一份"删除传播清单" | 谁没把删除传播到派生副本，谁负责 | L2（软删除本身属 5.2.1 的①③，跨副本传播无约定） |
| 元数据平台 → Agent | 元数据以工具 / 资源形式暴露给模型，接口是工具描述符 | 元数据平台 Owner——平台只提供事实，不提供语义裁决 | L3（对应 5.2.4：工具接入约定已公开，但裁决语义仍要自建） |
| 业务文档 → 构件候选 | 文档进抽取流水线，产出候选清单供人评审 | 签字建模的人——候选由谁签字，责任就在谁身上 | L2（对应 5.2.2） |

### 5.5 被过度宣传的部分

**「LLM 会自动把 Data Vault 建好」** —— 实际是从 DDL 与文档里提出候选构件。为什么会这样：Data Vault 的物理成本本来就低（加 Satellite 不改表），模型省下的是"读 DDL、抄结构"的时间，不是"决定拆几颗 Satellite"的时间；业务键是不是唯一、两个字段是不是同一语义，答案只在业务方手里。什么时候它才会成真：当"业务键唯一性"与"属性变更频率"能从数据本身稳定推断出来时——这一条已经在部分成立，值得持续跟踪，但它解决的是候选排序，不是语义裁决。

**「把 Satellite 向量化就能让模型直接查数仓」** —— 实际是把记录级快照放进向量库。为什么会这样：向量检索解决"找得到"，不解决"算得对"——聚合、时态切片（PIT）、多跳（Bridge）仍然是 SQL 的工作；而且列级权限与删除必须在副本上重新实现一遍，本目录 [§3 §3.5](03-data-vault-section-3-sec3.md) 对"把 Raw Vault 直接暴露给下游"的批评同样适用于向量副本。什么时候它才会成真：向量副本能继承源表的权限与删除语义，并且刷新窗口可以被答案明确标注。

**「Data Vault 会被 AI 自动演化，架构师退出」** —— 实际是提议成本下降、裁决成本不变。为什么会这样：自动化的边界由"机器能否判定风险"决定——"只新增 Satellite"可以自动，"改 Hub 业务键"不能，因为后者会改变全链路的实体身份。什么时候它才会成真：出现可被机器判定的变更风险分级，并被接进自动合并的流水线；在那之前，自动化产出的是待办队列。

这三条的共同点是：**模型把"做"变便宜了，没有把"判"变便宜**。所以判断一个 AI + Data Vault 的方案值不值得投，只需问一句——它省掉的是"做"的成本，还是"判"的成本。省"做"的成本，收益立刻兑现；声称省"判"的成本，先让它证明风险分级是准的。

### 5.6 未来 3–5 年：可证伪的预测

写不出信号与反信号的预测不写。下表的"会证伪的信号"一列是给自己留的检查项，不是修辞。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| Hub / Link 会成为 Agent 的实体与关系字典，而不只是建模中间产物 | 出现以 Hub 表为唯一实体源、被多个互不相关的工具共用的实体解析服务；Hub 的业务键定义出现在对外接口契约里 | 各 Agent 各自维护自己的实体编码，Hub 表仍只是建模时的中间产物 |
| DV 的差异化从"物理追加能力"退回建模约束——"加 Satellite 不改表"成为通用手法，而不再是 DV 的专利 | 新建项目中"开放表格式 + 手工时态列"的数量超过"按 DV 规范建模"的数量；非 DV 项目里出现"把可变属性拆成按月 / 按来源独立追加表"的普遍做法 | DV 建模工具（如 dbt 生态的 DV 包）的采用增长快于表格式本身；结构变更仍以改宽表为主，追加式建模只在强审计场景被采用 |
| LLM 在 DV 上的落地顺序是从末端（取数）向前端（建模）推进 | 一年内公开的 DV 与 LLM 案例集中在自然语言取数与文档生成，而不是自动生成 Hub / Link / Satellite | 出现公开可复现的"从 DDL 到生产模型"端到端案例，且正确率被第三方复核过 |
| DV 与表格式之间需要长期治理的接缝会集中在两处：时态语义，与 Effectivity Satellite 承担的合规删除 | 表格式文档里开始出现"业务时态与快照时态不是一回事"的专门章节，工程博客出现因混用两者导致的事故复盘；公开的合规删除方案里，把删除标记落在独立卫星表（而不是原地 UPDATE）的比例上升 | 表格式继续只讲快照，业务时态的坑仍由各团队在应用层各自踩一遍；主流方案仍以分布式事务加物理删除为主 |

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 刚决定用 DV，还没定物理载体 | 把 Satellite 落在开放表格式上，先跑通"追加写 + 按快照读"这一条 | 表格式的版本演进会不会破坏你的快照读取路径 | 不要自建时态列与拉链表；不要在没有 compaction 计划的情况下上线追加写加载 |
| 已有 DV，想接自然语言取数 | 先把指标与维度定义补进语义层，再开自然语言入口 | 取数错误的分类占比（语义层缺口 / 选表错 / 口径错） | 不要让模型直接遍历物理表取数；不要在语义层没建好时开自然语言入口 |
| 被要求做"AI 自动建模" | 把范围限定为"生成候选 + 用数据证伪"，交付物是候选清单而不是可上线 DDL | 候选的采纳率与返工原因的分布 | 不要把业务键选择交给模型；不要跳过 Hub 业务键唯一性校验 |
| 正在做向量化 / 检索增强 | 只向量化"用精确条件查不到"的那部分，并先写清删除与权限的传播路径 | 向量副本与源表的一致性窗口是否被业务接受 | 不要把全量 Satellite 都向量化；不要在副本上另建一套权限却不同步 |
| 组织要求合规删除与历史保留同时成立 | 明确两套语义的分界：软删除用 Effectivity Satellite 的 T_del，物理删除走独立流程并留清单 | 删除请求的端到端时长与遗漏率 | 不要用物理删除代替软删除；不要以为删了源表就等于删干净了 |
| 正在评估把元数据接进 Agent | 先给元数据补上唯一性约束与 Owner，再谈接口 | Agent 提议的采纳率与驳回理由的重复率 | 不要在元数据本身不完整时接 Agent；那只是把不完整放大 |

最后一列是这个表里唯一有长期价值的：前三列做的事一年后都能补，"不要做"的那几件做错了，要花一年拆掉。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一机制**是**元数据的消费方从人变成程序**——Data Vault 之所以在 AI 讨论里重新出现，不是因为它变了，而是因为它本来就以"可被机器遍历的字典"形态存在（Hub 是实体字典、Link 是关系字典、Satellite 是属性字典）；AI 改变的是这些字典的**生成速度与使用方式**，没有改变"业务键选谁、Satellite 拆几颗、口径归谁"这三类语义裁决仍必须由人做。本节没有任何方向达到 L1，最有底气的 5.2.1 恰恰与 AI 无关——这说明**物理载体的成熟度往往先于使用它的那波浪潮到来**；同时也说明"业界都在用"与"能被判据核验"是两件事，前者永远不能替后者。
>
> 💡 **思考锚点**：把你手上那个「AI + Data Vault」提案按本节三条判据标级——②（能被指名的、非建设方第三方生产案例）你能指向谁？指不到就落在 L2，那你只给它 PoC 排期还是路线图？再称一下它省的是「做」还是「判」的成本：若声称省「判」，你手上有什么证据能证明它的变更风险分级是准的？
