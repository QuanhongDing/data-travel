## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

Data Vault 的模式常被讲成「按场景挑一个」：多源整合选三件套，OneID 选 Same-As Link，软删除选生效卫星。这个讲法漏掉了真正起作用的东西——这些模式之所以长成这样，是被**同一条底层约束**推出来的：**写入是追加还是原地更新**。

Hub、Link、Satellite 三张表都不做 UPDATE：新事实来了插一行，旧行不动。这一条决定了后面的一切。因为写入只追加，表与表之间没有写入顺序依赖，加载可以并行；因为旧行不动，历史不需要额外设计，双时态（业务时态 $T_{biz}$ / 加载时态 $T_{load}$ / 删除时态 $T_{del}$）天然完整；也因为旧行不动，「当前状态」在库里并不存在——它必须由读取方在查询时拼出来。最后这一条就是 PIT 与 Bridge 存在的全部理由。

下表每一行，都是一条约束推翻一个直觉的记录——其中「读取时拼装」只是若干条约束共同的上游后果之一，而不是每一行失效的同一个原因。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 写入模式（追加 / 更新） | 决定加载能否并行、历史是否免费、当前状态是否存在 | 「表建好了就能直接查」——追加写的库里没有「当前」，当前是查询时算出来的 |
| 属性变更频率 | 决定卫星的拆分粒度 | 「一张卫星表装下所有属性最省事」——省的是建表，付的是每次变更整行复制的写放大 |
| 访问模式（点查 / 多表拼接 / 聚合） | 决定 PIT / Bridge 是否属于必备件 | 「先把 Vault 建起来，性能以后再说」——「以后」是指第一次有人做交互式查询的那天 |
| 一致性要求（审计 / 双时态） | 决定是否必须上生效卫星、是否必须存 hash_diff | 「删掉的数据反正没人要」——审计要的恰恰是被删掉的那部分 |
| 规模与成本 | 决定哈希算法选型与卫星合并策略 | 「哈希键截断几位省空间」——截断把碰撞概率从可忽略变成必须评估的量 |
| 团队技能与运维能力 | 决定 Raw Vault 与 Business Vault 的边界画在哪 | 「Raw Vault 直接对业务开放」——业务方拿到的是技术清洗结果，不是口径 |

一句话：本主题下所有模式的设计动作，都是在「追加写」这条约束下，为**读取侧**补回它失去的能力——当前状态、访问速度、口径。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 标准三件套（Hub-Link-Satellite）

**被什么约束逼出来**：源系统多个、属性天天加，但没人有权停机重跑已经投产的模型。

**结构**：

```sql
-- Hub：只有业务键与元数据，没有任何描述性字段
CREATE TABLE hub_customer (
  customer_hk   CHAR(32)    NOT NULL,   -- MD5(record_source || business_key)
  customer_bk   VARCHAR(64) NOT NULL,   -- 业务键，如手机号
  load_date     TIMESTAMP   NOT NULL,
  record_source VARCHAR(64) NOT NULL,
  PRIMARY KEY (customer_hk)
);

-- Link：只有参与方的哈希键与元数据，没有任何业务属性
CREATE TABLE link_customer_order (
  customer_order_hk CHAR(32)    NOT NULL,
  customer_hk       CHAR(32)    NOT NULL,
  order_hk          CHAR(32)    NOT NULL,
  load_date         TIMESTAMP   NOT NULL,
  record_source     VARCHAR(64) NOT NULL,
  PRIMARY KEY (customer_order_hk)
);

-- Satellite：属性 + 时态 + 来源，每次变更追加一行，永不 UPDATE
CREATE TABLE sat_customer_contact (
  customer_hk   CHAR(32)     NOT NULL,
  load_date     TIMESTAMP    NOT NULL,   -- 本版本的加载时态
  hash_diff     CHAR(32)     NOT NULL,   -- 属性集合的哈希，用于判断是否真的变了
  phone         VARCHAR(32),
  email         VARCHAR(128),
  record_source VARCHAR(64)  NOT NULL,
  PRIMARY KEY (customer_hk, load_date)
);
```

**为什么这样设计有效**：因为 Hub 里只放业务键的哈希、描述性字段全在 Satellite 里，所以「给客户加一个属性」这个动作的全部物理后果是**新建一张 Satellite**——已有表的 DDL、加载作业、下游查询一行都不用动。变更影响面因此从「整条链路」收敛到「一张新表」。

**代价**：读取被推给了查询方。取一个实体在某一时点的完整画像，要把 k 张卫星表 JOIN 起来再按 load_date 各取最新版本；JOIN 数随属性域个数线性增长，而每张卫星表的行数随**变更次数**（不是实体数）增长。存储代价同理：一个每天改一次的属性，一年为每个实体留下约 365 行【推算：变更频率 × 实体数 × 保留期】。

**失效点**：当实体属性几乎不变、且主要查询是单实体点查或宽表报表时，三件套的优点会反转成缺点——它省下的「加字段不改表」在这个场景里用不上，而它付出的「多表拼接 + 时点切片」照收。同一份数据用宽表存储，读取是一次等值查找；用三件套存储，读取是 k 路 JOIN 加窗口聚合，差距随属性域个数放大。

**真实使用**：Data Vault 2.0 规范给出了 Hub / Link / Satellite 与哈希键的完整定义（【公开：Data Vault 2.0 官方规范，Dan Linstedt，2013；版本细节请以官方文档当前版本为准】）。落地集中在金融、保险、电信、航空等审计要求高的行业（【经验】）。工程上最常见的用法是把它放在集成层（DWD），下游另用维度建模做消费层。

#### 3.2.2 PIT 与 Bridge：为追加写补回读取速度

**被什么约束逼出来**：3.2.1 把「取某时点最新版本」这件事留给了每一次查询，而这件事本身是多表 JOIN 加窗口聚合。

**结构**：

```sql
-- PIT：把每个 Satellite 在时点 T 的有效版本预先钉住
CREATE TABLE pit_customer_2019_12_31 (
  customer_hk        CHAR(32)  NOT NULL,
  snapshot_date      DATE      NOT NULL,
  sat_contact_load   TIMESTAMP NOT NULL,   -- 该卫星在 T 时刻的有效版本
  sat_address_load   TIMESTAMP NOT NULL,
  sat_status_load    TIMESTAMP NOT NULL,
  PRIMARY KEY (customer_hk, snapshot_date)
);
-- 消费查询：按 load_date 等值 JOIN 回各卫星，不再扫全部历史
SELECT h.customer_hk, c.phone, a.city, s.status
FROM   pit_customer_2019_12_31 p
JOIN   hub_customer         h ON h.customer_hk = p.customer_hk
JOIN   sat_customer_contact c ON c.customer_hk = p.customer_hk AND c.load_date = p.sat_contact_load
JOIN   sat_customer_address a ON a.customer_hk = p.customer_hk AND a.load_date = p.sat_address_load
JOIN   sat_customer_status  s ON s.customer_hk = p.customer_hk AND s.load_date = p.sat_status_load;

-- Bridge：把多跳关系提前物化（客户 → 订单 → 商品）
CREATE TABLE bridge_customer_product AS
SELECT DISTINCT l_co.customer_hk, l_op.order_hk, l_op.product_hk
FROM   link_customer_order  l_co
JOIN   link_order_product   l_op ON l_co.order_hk = l_op.order_hk;
```

**为什么这样设计有效**：因为 PIT 把「每个卫星在时点 T 的有效版本」提前算成了 load_date 指针，所以查询侧的扫描量从「实体数 × 历史版本数」降到「实体数」，窗口聚合退化成等值 JOIN。Bridge 同理：把 N 跳链式 JOIN 提前物化一次，避免每个查询各算一遍。

**代价**：PIT 不是免费视图，它自己要被调度维护——上游每加载一批，就得回填或重算受影响的时点；它的物化存储与卫星同量级，并且多出一条新的失败点（PIT 作业挂了，下游看到的是「数据没更新」而不是「报错」）。Bridge 的代价是 DISTINCT 展开带来的中间结果膨胀与刷新成本。

**失效点**：当查询时点高度任意（审计要问「任意一天」）且卫星变更极频繁时，为覆盖所有时点预建 PIT 的物化与维护成本会超过它省下的查询成本，PIT 自己变成新的全量扫描源。此时正确做法是按「固定高频时点（如月末快照）物化 + 其余时点现算」分层，而不是把时点粒度继续调细。

**真实使用**：多数生产 Vault 只对少数高频实体与固定时点建 PIT，其余实体仍走现算（【经验】）。判断自己的项目是否到了该建 PIT 的规模：看消费侧查询的 P95 里，等待「多表拼接 + 取最新版本」的那部分是否已成为主要成分。

#### 3.2.3 同义链接（Same-As Link / OneID）

**被什么约束逼出来**：同一个真实客户在 CRM、ERP、支付、设备四个源里各有一个 Hub，必须有人判定「这几个 Hub 是同一个实体」，且判错必须能回退。

**结构**：

```text
hub_customer_crm  ┐
hub_customer_erp  ├─► link_customer_same_as ─► hub_customer_unified
hub_customer_pay  ┘        │
                           └── sat_customer_same_as_evidence
                                 ├── 证据类型（身份证 / 手机号 / 邮箱 / 设备 ID）
                                 ├── 证据强度等级
                                 ├── 生效区间（effective_from / effective_to）
                                 └── 判定来源（规则 / 人工 / 模型版本）

关键约束：等价关系是数据，不是物理合并。
判错 → 撤掉一条边 → 重新求连通分量；不涉及任何表的物理还原。
```

**为什么这样设计有效**：因为「它们等价」被写成一条带证据类型、强度等级与生效区间的 Link 记录，所以合并是一次**可撤销的数据动作**，而不是一次不可逆的物理归并——判错可以回溯、可以按新证据重判，这也正是 OneID 场景里唯一可行的纠错路径。

**代价**：等价关系是传递闭包问题。n 个源两两判定产生 n(n−1)/2 条候选边【推算】；查询侧求连通分量（谁和谁最终是同一个统一实体）比等值查找贵得多，且边的数量随「证据数量」而非「实体数量」增长。

**失效点**：当源系统增多、且等价判定引入弱证据（共享设备 ID、共享邮箱）时，OneID 会从「打通」反转成「错误合并」——因为弱证据的假阳率会沿着边集按乘积方式累积，少量假阳边足以把大量本来无关的实体连成一个连通分量；而这类错误不报错，只是让下游的客户数、ARPU 一类指标系统性失真。弱证据可以用，但必须限制在「已用强证据判定过的分组内部」，不能跨组当连接器。

**真实使用**：跨域主数据与 OneID 场景中，等价判定普遍采用「强证据优先」的分级做法：证件类 > 手机号 > 邮箱 > 设备 ID（【经验】）。判断自己项目的证据分级是否有效，可做一次反向抽检：随机取 100 个合并后的统一实体，人工核验其中有多少实际属于不同自然人。

#### 3.2.4 多活动卫星（Multi-Active Satellite, MAS）

**被什么约束逼出来**：同一个 Hub 在同一时刻有多个并发属性值（一个客户有三个手机号），而标准 Satellite 的主键 `(hub_hk, load_date)` 假设一个时点只有一行。

**结构**：

```sql
-- 反例：一个时点多行，主键冲突，无法表达「这一刻这一组值是什么」
-- 正例：把「一组并发值」作为一个变更单元，用组哈希做变更判定
CREATE TABLE sat_customer_multi_key (
  customer_hk   CHAR(32)     NOT NULL,
  load_date     TIMESTAMP    NOT NULL,   -- 这一组值的时态
  hash_diff     CHAR(32)     NOT NULL,   -- 整组值的哈希：任一个值变了就换一行
  phone_key     VARCHAR(256) NOT NULL,   -- 这一组手机号（按规范排序后拼接）
  cert_key      VARCHAR(256) NOT NULL,   -- 这一组证件号
  email_key     VARCHAR(256) NOT NULL,
  record_source VARCHAR(64)  NOT NULL,
  PRIMARY KEY (customer_hk, load_date)
);
```

**为什么这样设计有效**：因为变更判定单元从「单个值」抬到了「整组值的哈希」，所以「这组值此刻是什么」在库里始终有唯一答案，不需要在执行聚合时再去猜哪个版本是整组。这也让 MAS 天然避开了「同一时点多行、无法确定完整集合」的不确定性。

**代价**：写放大等于组大小——改一个手机号也要重写整组；存储上，一次小变更付的是整行的代价。读取上，「这个客户现在有哪些手机号」必须从单行读取变成对整组的解析，聚合与去重都被推到查询侧。

**失效点**：当并发值数量大且变动频繁（例如一个账户的数百个标签）时，MAS 的「变更语义清晰」会反转成「每次改动重写数百个值」——写放大与存储成本随组大小线性上涨，而组越大，真正变化的那个值越难定位。此时应把高变动率的多值属性从 MAS 里拆出去，改建成独立的 Satellite 或独立 Link。

**真实使用**：多值属性的建模中，MAS 是处理「电话 / 邮箱 / 证件 / 账户」这类并发键的常见做法（【经验】）。判断自己是否该用 MAS 的问题只有一个：这些值在业务上是否有「同一时点整组同时有效」的语义；没有这个语义就不该用。

#### 3.2.5 生效卫星（Effectivity Satellite）

**被什么约束逼出来**：删除与失效必须留痕——审计要问「这条关系在 2019 年 3 月成不成立」，合规要求「被遗忘」也不能靠物理删除来兑现。

**结构**：

```sql
CREATE TABLE sat_customer_lifecycle (
  customer_hk     CHAR(32)     NOT NULL,
  load_date       TIMESTAMP    NOT NULL,
  effective_from  DATE         NOT NULL,   -- 业务时态：何时生效
  effective_to    DATE,                    -- NULL = 至今有效
  deletion_reason VARCHAR(64),             -- 软删除：注销 / 合并 / 合规删除
  record_source   VARCHAR(64)  NOT NULL,
  PRIMARY KEY (customer_hk, load_date)
);
-- 「是否当前有效」不落成存储列，而是读侧派生：它是该实体 load_date 最大的那一行、且未被关闭。
-- 若把它做成由加载作业维护的布尔列，关闭一条关系就得回写历史行，「只追加、不 UPDATE」的前提随之失效。
CREATE VIEW v_sat_customer_lifecycle AS
SELECT s.*,
       (s.effective_to IS NULL
        AND s.load_date = (SELECT MAX(x.load_date) FROM sat_customer_lifecycle x
                           WHERE x.customer_hk = s.customer_hk)) AS is_current
FROM   sat_customer_lifecycle s;
```

**为什么这样设计有效**：因为失效被写成一条带 `effective_to` 的追加记录，而不是对原行的覆盖或删除，所以「某时点这条关系属于谁」在库里始终有唯一答案——时态问题退化成一次区间谓词查询，而原行永远在位，审计可以逐条回放。

**代价**：所有下游查询都被要求带「当前有效」过滤（`is_current` 或区间谓词）。这是一条纪律，不是一个机制——它依赖每个消费者记得写。区间谓词的执行成本也高于等值查询，索引设计要额外考虑。

**失效点**：当消费者数量多、且大量查询只关心当前状态时，这条纪律会被漏掉：某个报表忘了过滤 `is_current`，就会把已经失效的关系算进来。于是「审计维度完整」反转成「口径系统性偏差」，而且不报错——因为过滤条件存在于消费者的自觉里，而不在数据本身。修法是把 current 过滤封进 Business Vault 视图或 PIT，让「不经过滤就取不到数」。

**真实使用**：软删除在 GDPR「被遗忘权」与内部审计场景中是通行做法（【经验】）。判断自己有没有踩到这条失效点，可以反向抽查：在 `is_current = FALSE` 的记录里挑几条，看它们是否出现在任意一张对外报表里。

#### 3.2.6 计算卫星（Computed Satellite）

**被什么约束逼出来**：模型与规则的计算结果（评分、分群、风险等级）也要可追溯、可重算、可对比，而模型版本本身在持续迭代。

**结构**：

```sql
CREATE TABLE sat_customer_risk_score (
  customer_hk          CHAR(32)    NOT NULL,
  load_date            TIMESTAMP   NOT NULL,
  score_time           TIMESTAMP   NOT NULL,  -- 业务时态：这分是什么时候打的
  model_version        VARCHAR(32) NOT NULL,  -- 模型版本，不是代码提交号
  score                DECIMAL(6,2),
  score_band           VARCHAR(16),           -- 分档
  feature_snapshot_hk  CHAR(32),              -- 特征快照的哈希 / 引用（见失效点）
  record_source        VARCHAR(64) NOT NULL,
  PRIMARY KEY (customer_hk, score_time, model_version)
);
```

**为什么这样设计有效**：因为结果是与「模型版本 + 特征快照引用」一起被追加存储的，所以「这个评分当时是怎么来的、上一版打多少」不依赖模型侧的日志或监控数据——结果与解释在同一个表里，时间线可以直接对比。

**代价**：计算卫星的存储随「重算次数 × 实体数」增长，而不是随「实体数」增长；每次重跑都是全量追加。如果快照存的是实际特征值而不是引用，空间放大更明显。

**失效点**：当所谓「可重算」其实依赖已经取不到的特征（源数据过了保留期、特征工程代码已改版）时，只存引用不存值的快照会让重算无法复现——于是「可追溯」反转成「有版本号但复现不了」，因为版本号标识的是模型代码，不是输入数据。选择存值还是存引用，取决于源数据保留期是否长于合规要求的可追溯期。

**真实使用**：风控评分、客户分群、模型输出入仓都属于这一类（【经验】）。核验自己是否真的能重算，最直接的办法是随机抽一个历史评分，用当时的特征快照和模型版本重跑一遍，看结果是否逐位一致。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 源系统 1–2 个 + 业务稳定 + 以报表消费为主 | 维度建模（Kimball） | 三件套的「加 Satellite 不改表」在这里用不上，却要付多表拼接的读代价 | 一年内的 DDL 变更次数是否接近零 |
| 源系统 ≥ 3 个 + 跨域整合 | 标准三件套 + Same-As Link | Kimball 的宽表要按域重复清洗，新增源要改多张表 | 新增一个源要改几张已有表 |
| 同一实体多业务键（手机 + 邮箱 + 身份证） | 多活动卫星 MAS | 标准 Satellite 主键假设一时点一行，装不下并发值 | 这些值是否要求「同一时点整组有效」 |
| 需要软删除 + GDPR | 生效卫星（Effectivity Satellite） | 物理删除无法回答审计的时点提问，也无法回滚 | 能否回答「某年某月这条关系成不成立」 |
| 业务变化频繁（每周加字段） | 标准三件套 + 持续新增 Satellite | 宽表要改 DDL 并回填历史，每次变更都触发重跑 | 上次加字段花了多久、影响了多少下游 |
| 需要可追溯的模型推理结果 | 计算卫星 | 把结果只留在模型侧日志里，等于把可追溯性外包给另一个系统 | 能否用当时的输入重跑出同一个结果 |
| 强合规审计要求 | 全套生效卫星 + hash_diff 变更判定 | 只存当前状态在审计场景等于无历史 | 近三次审计问题里有没有时点类提问 |
| 实时流式入仓 | 标准三件套 + 流式 CDC | 依赖中心序列号的键分配会挡住并行写入 | 写入是否依赖取号 / 全局序 |
| 跨域 OneID 主数据 | Same-As Link 链 + 证据分级 | 直接物理合并判错后无法回退 | 假阳合并有没有撤回路径 |

最常被误选的一对是**标准三件套与维度建模**，且两个方向都会错：把三件套用在「单源 + 稳定 + 报表消费」上，等于用读取代价买了一个不需要的可演化性；把 Kimball 宽表用在「多源 + 每周加字段」上，等于每次变更都要重跑链路。判别只需要问一个问题：**这张模型未来一年要吞下几个新源、几次加字段**——答案接近零就往下游走，答案在增长就往 Vault 走。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Raw Vault（三件套全覆盖）+ Business Vault（计算卫星 + 口径规则）**。职责边界：Raw Vault 只做技术清洗（去重、类型转换、完全贴源），Business Vault 承担业务规则、跨域对账与轻度汇总。运维代价：两套模型定义与两套血缘，Business Vault 的每次规则变更都要回看它引用了哪些 Raw 表。适合规模：源系统 ≥ 3 个、下游消费者 ≥ 5 个的组织——消费者少时，Business Vault 的维护成本会吃掉它带来的口径统一收益。

**组合二：标准三件套 + PIT / Bridge（读加速层）**。职责边界：三件套负责「历史全留」，PIT / Bridge 负责「查询别扫历史」，两者之间只通过 load_date 指针接触。运维代价：PIT 的调度与回填成为新的可用性依赖，PIT 晚更新会让下游看到旧快照而不报错。适合规模：查询从 T+1 批处理走向交互式、且消费侧已出现明显等待。

**组合三：Same-As Link + MAS + 生效卫星（跨源 OneID）**。职责边界：MAS 负责「一个实体在同一时点有多个键」，Same-As Link 负责「多个源里的实体是同一个」，生效卫星负责「这条等价关系何时成立、何时失效」。运维代价：等价关系会随业务漂移（换号、销户、证件更新），需要一条独立的等价关系维护作业与定期回归抽检；三者中任何一者的变更语义出错，都会在下游表现为客户数口径漂移而不是报错。适合规模：跨 4 个以上源系统的客户 / 商品主数据。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| Hub 里塞属性 | Hub 表出现了姓名、地址、状态这类列；加字段需要 ALTER Hub | 每次加属性都要改 Hub 表，三件套「不改已有表」的全部收益被抵消 | 建表时觉得「反正这个字段也要存」，省一张表 | Hub 只留 Hash Key + Business Key + Load Datetime + Record Source + 极少数元数据字段 |
| Link 里塞属性 | `link_customer_order` 里出现「下单时间」这类列 | 关系表被当成事实表用，变更语义与变更频率混在一起，无法独立演化 | 关系上确实有属性，就近存了 | 属性移到挂在 Link 上的 Satellite |
| 把所有属性塞到一个 Satellite | 存在 `sat_customer_all`；任一字段变化都产生整行复制 | 变更粒度过粗，写放大等于全表列宽；高频与低频变更字段无法差异化存储 | 一张表管理成本最低，拆分要写多份加载作业 | 按「变更频率 + 业务主题」拆：静态（性别、生日）/ 联系方式 / 地址 / 行为画像 |
| 滥用 Same-As Link 导致笛卡尔积 | 等价关系表行数远超实体数，且出现超大连通分量 | 少量假阳边把大量无关实体连成一团，下游客户数与 ARPU 系统性失真 | 把弱证据也当连接器，且等价关系全量保留 | 只保留当前有效的等价关系；等价判定按强证据优先（身份证 > 手机号 > 邮箱 > 设备 ID）；弱证据只在强证据分组内部生效 |
| 不区分 Raw Vault 与 Business Vault | 下游直接消费 Raw Vault；同一业务规则在多个下游各写一遍 | Raw Vault 的「完全贴源」让每个消费者重复实现规则，源系统一变全部下游同时失效 | 少一层就少一次等待，业务方要数要得急 | Raw Vault 只做技术清洗；业务规则、轻度汇总、主数据治理、跨域对账放进 Business Vault |

三个最危险的反模式，按暴露方式不同：**Hub 里塞属性**是最隐蔽的，它不会立刻报错，只会在下一次「加个字段」时把项目打回原形——团队当初为可演化性付了全部代价，却在第一次变更时失去了它。**滥用 Same-As Link** 是后果最重的，因为它产出的是错误但看起来正常的数：客户数少算或虚高都不会触发任何告警，只会在结算、审计或对外披露时暴露，且此时已经很难判定哪些实体被错误合并。**不区分 Raw Vault 与 Business Vault** 是扩散最快的，它让业务规则从一处变成 N 处，源系统的一次字段变更会同时打穿所有下游，而每个下游的修复方式还各不相同。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的。规模或访问方式跨过某个阈值时，原来正确的模式会变成错的。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 源系统 1 个 → 3 个以上 | Kimball 宽表 | 每个源都要在宽表上重做一遍清洗，新增源要改多张已有表 | 标准三件套 + Same-As Link | 重建集成层，并把下游消费重新指向 Business Vault |
| 查询从 T+1 报表 → 交互式 | 直接查 Satellite | 每次查询都要多表 JOIN + 取最新版本，等待随历史增长 | 三件套 + PIT / Bridge | 新增 PIT 调度与回填作业，消费侧 SQL 重写为等值 JOIN |
| 属性变更从每月 → 每天 | 单张卫星表 | 一次小变更触发整行复制，写放大按列宽计 | 按变更频率拆分卫星 | 拆分历史卫星涉及数据迁移与下游视图切换 |
| 弱证据参与 OneID 判定 | 全量等价关系 | 假阳边使连通分量膨胀，合并不再可解释 | 强证据优先 + 只留当前有效等价关系 | 等价关系需要重建与回归抽检 |
| 出现删除 / 合规要求 | 物理删除或覆盖 | 无法回答审计的时点提问 | 生效卫星 + 软删除 | 已删数据多数不可恢复，只能从生效时点起记录 |
| 规则从人工判断 → 模型批量打分 | 结果写入业务表 | 结果无法与模型版本、输入特征对齐，复盘时答不出原因 | 计算卫星（模型版本 + 特征快照） | 需要补历史快照；补不回来的历史只能标注为不可复现 |
| 离线批 → 流批一体 | 依赖取号 / 序列的键 | 并行写入同一个 Hub 时键分配产生冲突 | 三件套 + 流式 CDC（哈希键确定性） | 需要处理乱序到达，按 $T_{load}$ 与业务时态识别「晚到的真相」 |

### 3.7 自检清单

- [ ] Hub 表里是否出现过任何描述性文本列（姓名、状态、地址）？出现即违反 Hub 定义。
- [ ] Link 表里是否出现过业务度量或时间属性（下单时间、金额）？出现即说明属性放错了表。
- [ ] 是否存在某个 Satellite，其任一字段变化都会导致该表最大行宽的整行复制？若是，问它是否把高频与低频字段混在了一张表里。
- [ ] 随机抽 10 条卫星记录，能否用 `record_source` 说清这条数据来自哪个源系统的哪次加载？
- [ ] 是否存在不带区间谓词或 `is_current` 过滤就取数据的下游查询？有，就等于把生效卫星的审计收益丢掉了。
- [ ] 取「某实体在任意一天的完整画像」需要 JOIN 几张表？超过 5 张时，是否已评估 PIT？
- [ ] PIT 或 Bridge 作业失败时，下游是报错还是静默拿到旧数据？静默即缺一条新鲜度告警。
- [ ] Same-As Link 里是否混入了弱证据（设备 ID、共享邮箱）？它们有没有被限制在强证据分组内部？
- [ ] 计算卫星的 `model_version` 指向的是模型代码版本还是可复现的模型 + 特征组合？后者才可重算。
- [ ] 哈希键是否被截断？若截断，碰撞概率是否按实体数估算过？
- [ ] 下游是否直接消费 Raw Vault？若是，列出同一业务规则在几个下游各写了一版。
- [ ] 新增一个源系统，需要改动几张既有表？答案不是 0（哪怕只改一张）时，可演化性的承诺就已经不成立——新增源的正确动作是加 Hub / Link / Satellite，不是改既有表。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 单源 + 稳定 + 报表消费 | 维度建模（Kimball） | 追加写的可演化性用不上，读取代价却照付 |
| 多源 + 持续加字段 | 标准三件套 + 持续新增 Satellite | 加属性只新增表，不动既有表 |
| 多值并发键 | 多活动卫星 MAS | 变更单元从单值抬到整组，时点语义唯一 |
| 删除 / 合规 / 审计 | 生效卫星 + hash_diff | 失效写成追加记录，时点提问可答 |
| 跨源实体统一 | Same-As Link + 证据分级 | 等价关系是数据，判错可撤 |
| 模型结果入仓 | 计算卫星 | 结果与模型版本、特征快照同表，可重算可对比 |
| 交互式查询 | 三件套 + PIT / Bridge | 把时点切片从查询时挪到加载后 |
| 流批一体 | 三件套 + 哈希键确定性 | 无中心取号，写入天然可并行 |

> 本节小结：本主题下决定模式选择的唯一那条约束是**写入是追加还是原地更新**——Hub / Link / Satellite 全部只追加，于是「当前状态」在库里不存在、历史天然完整、加载天然可并行，而 PIT、Bridge、生效卫星、计算卫星都是为这条约束的读取侧后果补的账。判断一个 Data Vault 设计是否成立，不看它用了几个模式，看它有没有在某个地方偷偷做 UPDATE 或物理删除。
