## 7. 与其他方法对比

> 本节对应主文件《速读地图》里「决策树：我的业务该选 Kimball、Data Vault 还是 Anchor」这一行，答案落在 7.5 的决策树与 7.6 的场景矩阵与组合。全节不给分数，只给「因为哪个机制，所以在什么条件下必然更优、代价是什么」。

### 7.1 先立判据：为什么打分表会误导

打分表把「取决于场景的结论」伪装成「绝对结论」。给「加字段成本」这一栏填上 5 分与 2 分，它回答的是「这个方案好不好」，而选型要回答的是「在我的约束下它会怎样」。同一个维度的权重在不同规模下相反：源系统只有一个、一年加两次字段的团队，「加字段不改表」几乎是零价值的能力，而它附带的「表数 3–4 倍、读侧连接链路更长」照付不误（7.4 有推算）。反过来，每周都在接新源的团队，同样这两条的性质完全倒转。

比权重更根本的问题是：这些候选不在同一层。**Inmon 3NF、Data Vault、Anchor 是集成与演进的解法**（回答「源持续新增、结构怎么长」）；**维度建模（星型）与宽表是查询结构的解法**（回答「给定访问模式，一条查询要连几张表」）；**OneData 式的语义层与本体建模是消费接口的解法**（回答「口径在哪里声明、机器能不能找到」）；**Iceberg / Delta Lake / Hudi 一类开放表格式是承载层的解法**（回答「追加写与快照读由谁提供」）。四层可以同时存在——主文件 §2.4.2 给出的最常见形态就是「Data Vault 做集成层（DWD）、维度建模做消费层（ADS / Data Mart）」。把四个层级的东西放进一张表排名，得到的是一张不可比的表。

第三，同一维度在两个候选之间往往不是「分数差」，而是两个不同机制的函数。拿「查询性能」来说：Data Vault 的延迟由**连接链路长度**决定（属性散在若干卫星表上，取一次画像要按 $T_{load}$ 各取最新），星型的延迟由**引用维度数**决定（JOIN 数固定、维表小可广播），而 Anchor 的延迟由**本次查询用到的属性个数**决定（一属性一表）。谁更快取决于这次查询问了几件事，而不是方案本身——把它写成 5 分与 4 分，等于把一个变量藏进了一个常量。

第四个问题是它暗示互斥。真实系统是叠加：集成层选一个方案、汇总层选一个方案、承载与消费接口再各选一次，四者互不冲突（7.6 的四条组合都是这种叠加）。一旦接受「可以叠加」，比较的对象就从「哪个方案总分高」变成「每一层各自该选什么」。

所以本节的组织方式是：先立判据，再按**机制**分组比较，最后给决策。本主题的判据不能是「快 / 灵活 / 先进」这类形容词，必须是能回答「在我的约束下会怎样」的问题。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 追加还是更新 | 写入是只追加，还是定位旧行后修改 | 它同时决定三件事：历史是否免费、加载能否并行、「当前状态」在库里是否真实存在（[§3.1](03-data-vault-section-3-sec3.md) 的约束表） |
| 版本连带范围 | 一个属性变了，多少别的属性被连带复制 | Data Vault 的连带单位是卫星表（属性组）、Anchor 是单个属性、Kimball 的 SCD Type 2 是整行——粒度差一级，存储与读代价差一级 |
| 标识的确定性来源 | 键是算出来的，还是取号 / 查维表得到的 | 哈希键不需要中心取号 → 并行加载与流式写入成立；代理键需要分配 → 写入顺序成为约束（[§4.2.1](03-data-vault-section-4-sec4.md)） |
| 时点切片的落点 | 「某时点的画像」是查询时算，还是加载后物化 | 决定 PIT / Bridge 是不是必备件，也决定读侧的成本由谁承担（[§2.3.3](03-data-vault.md)、[§4.1.6](03-data-vault-section-4-sec4.md)） |
| 变更传导范围 | 加一个源、加一个属性、改一次口径各要动几张表 | 决定三年后的维护成本，而不是上线当天的成本（[§3.3](03-data-vault-section-3-sec3.md) 决策表的判据列） |
| 消费方形态 | 人写 SQL、BI 建模，还是 Agent 生成查询 | 决定要不要在之上加语义层与本体映射；这类需求与物理结构选择正交（[§2.4.3](03-data-vault.md)、[§5.2.2](03-data-vault-section-5-ai.md)） |

六条的排列顺序本身就是一条隐含结论：前两条决定物理结构，中间两条决定读侧代价落在谁身上，最后两条决定要不要再加一层——**顺序不能颠倒**，因为在结构未定之前讨论消费接口是没有对象的。

### 7.2 候选方案全景

下表不设打分列，只列核心机制——机制相同则分数必然相同，机制不同则分数无意义。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| **Data Vault 2.0** | 集成层（DWD） | Hub（业务键）/ Link（关系）/ Satellite（属性）三类表分离，哈希键 + 全量追加 | 金融、保险、电信等审计型数仓（[§1.4](03-data-vault.md)） | 方法论公开；Data Vault 2.0 由 Linstedt 与 Olschimke 在 2015 年系统化【公开，2015】 |
| **维度建模（Kimball 星型）** | 消费层 / 汇总层 | 事实 + 维度反规范化，查询时一次 JOIN 到位 | 报表与 ADS 层；主文件 §2.4.2 指定的消费层做法 | 方法论公开（《The Data Warehouse Toolkit》1996 首版）【公开，1996】 |
| **ER 建模（Inmon 3NF）** | 企业级集成与写入一致 | 按函数依赖消除冗余，结构不随查询形态变化 | 单源为主的传统企业数仓（[§2.4.1](03-data-vault.md)） | 方法论公开（《Building the Data Warehouse》1992 首版）【公开，1992】 |
| **Anchor Modeling** | 极致可演化的集成层 | 一属性一表（6NF），每个构件自带时态 | 属性基数大、且持续演化的电信 / 保险核心实体 | 方法论公开，示例模型与规范见其方法论站点【公开，可自行核验】 |
| **OneData / OneID 语义层** | 消费接口 | 度量与实体标识在一处声明，物理结构不动 | 阿里系数据中台（[§6](03-data-vault-section-6-sec6.md) 的案例主线） | 方法论公开（《大数据之路：阿里巴巴大数据实践》2017）【公开，2017】 |
| **本体建模（RDF / OWL）** | 语义互操作层 | 类、属性与公理表达业务概念，隐含事实由推理机推导 | 跨系统语义对齐、知识图谱 | W3C 公开标准（OWL 于 2004 年成为 W3C 推荐标准）【公开，2004】 |
| **开放表格式（Iceberg / Delta Lake / Hudi）** | 承载层（与建模方法正交） | 追加写、快照读与删除文件由存储层提供 | 湖仓上落 Vault 的团队（[§5.2.1](03-data-vault-section-5-ai.md)） | 开源（Apache）；Iceberg 表规范 v2 定义了两类删除文件（请以官方规范仓库当前版本为准），Hudi 1.0 于 2024 年 12 月发布（Apache 官方公告与 release note）【公开，2024】 |
| **手写时态列 / 拉链表** | 基线做法 | 在宽表或维表上人工维护起止日期与当前标记 | 存量数仓的常见现状（[§3.2.5](03-data-vault-section-3-sec3.md) 讨论的替代对象） | 无独立许可，能力取决于所在平台 |

这八个候选分三**族**：**集成结构族**（3NF、Data Vault、Anchor，3 个）——差异在于把「实体 / 关系 / 属性」切到多细，族内都走「多表 + 查询时重组历史」；**查询结构族**（维度建模星型、手写时态列 / 拉链表，2 个）——差异在于历史与上下文是留在查询侧还是写进表里，宽表是星型在「不保留历史」取向下的极端形态；**接口与承载族**（OneData 式语义层、本体建模、开放表格式，3 个）——不改建模决策，只改「口径在哪声明、追加与快照由谁提供」。

先分族能省掉一半比较：**族内换方案通常只是重排 JOIN 与改写查询，跨族换方案要重建链路**（迁移量级见 7.7）。按族逐层选，每一层只需回答一个问题：集成层问「源会不会持续新增」，查询结构层问「历史要不要留在表里」，接口层问「消费方是不是机器、谁替你提供追加写」。

表里有两行的归属需要说明，否则容易被当成可比的建模方法。**手写时态列 / 拉链表**是基线而不是竞争者：它把时态写在业务表自己身上，因此 7.3 的四个机制维度在它这里全部退化成应用层的纪律（[§3.2.5](03-data-vault-section-3-sec3.md) 的失效点就是这条纪律漏写时的表现）；之所以保留它，是因为多数团队的现状就是它，选型的真实问题是「要不要为历史单独建一层构件」。**开放表格式**是承载层的解法，与建模方法正交：同一个 Hub / Link / Satellite 设计，落在开放表格式上还是落在自建时态列上，物理后果完全不同（前者靠存储的快照与删除文件，后者靠加载作业自己维护），这也是 [§5.2.1](03-data-vault-section-5-ai.md) 把它列为其余演进方向物理前提的原因。

族内差异同样不可忽略，只是它改变的是「同一份结构长什么样」而不是「要不要这一层」：3NF 与 Data Vault 的差别是把属性留在实体表里还是拆到卫星表，Data Vault 与 Anchor 的差别是属性的切分单位是组还是单个——**两者都会改变版本连带范围，但都不会改变「先有集成层、再有消费层」这个顺序**。

上表的候选也不是穷举：任何承载技术（另一套表格式、另一套图数据库、另一套编排器）都能替换其中的一格，**但更换承载不会改变集成结构族的选择**——这正是把它标为「与建模方法正交」的含义。反过来，集成结构一旦定下，承载与接口可以分阶段替换；而结构本身的替换要走 7.7 那张迁移表。**分族的第一条操作含义就是：先定不可逆的那一层（结构），再生效可逆的那几层（承载与接口）。**

### 7.3 机制差异：为什么它们表现不同（核心节）

以下四个机制维度覆盖上表全部候选。每个维度给机制定义、各候选的实现差异、由机制必然导出的性质，以及该机制的失效条件。四个维度的顺序也是依赖顺序：7.3.1 决定历史与并行，7.3.2 决定版本连带范围，7.3.3 决定标识怎么来，7.3.4 决定读侧的账记在谁头上。

读法是**先看性质句、再看证据**：性质句是从机制推出来的（「因为 A，所以 B」），与具体产品无关；证据只是说明这条机制在公开材料里有出处，它不替代你在自己的源数据上验证一遍。若某个候选在某条机制上既找不到性质句、也找不到失效条件，通常不是资料不足，而是它在这条维度上没有可比较的内容——它可能根本不属于这一族。

#### 7.3.1 追加还是原地更新：历史、并行与「当前状态」

**机制是什么**：写入路径是「只插入新行」，还是「先定位旧行再修改或关闭它」。

| 方案 | 写入动作 | 历史载体 | 加载能否并行 | 「当前状态」在哪里 |
| --- | --- | --- | --- | --- |
| Data Vault | 只追加，Hub / Link / Satellite 均不 UPDATE | Satellite 追加行（粒度 = 属性组） | 能，键由哈希算出，无中心取号（[§2.3.1](03-data-vault.md)） | 库里不存在，读侧按 $T_{load}$ 取最新 |
| Anchor | 只追加（每个属性表各自追加） | 属性表追加行（粒度 = 单属性） | 能 | 库里不存在，读侧按业务时态切片 |
| Kimball 星型 + SCD Type 2 | 关闭旧行 + 插入新行 | 维表版本行（粒度 = 整行） | 维表上有写冲突，需串行或分片 | 表里存在（`is_current` 或 `end_date IS NULL`） |
| ER 3NF | 原地 UPDATE | 通常没有（被覆盖） | 同实体有写锁竞争 | 表里存在 |
| 宽表 / 拉链表 | 覆盖写或分区重写 | 无，除非另存快照 | 分区重写要窗口 | 表里存在 |
| 开放表格式承载 | 文件追加 + 删除文件 | 快照（加载时态） | 能 | 由读侧选快照 |

**由此必然导出的性质**：因为 Data Vault 与 Anchor 的写入路径里没有「定位旧行」这一步，所以一批加载不需要对目标表按实体加锁——同一作业里可以并行加载上百张 Satellite，任一卫星失败不影响其他卫星（[主文件 §2.3.1](03-data-vault.md)、[§3.1](03-data-vault-section-3-sec3.md)）；也正因为旧行不动，「这个实体现在长什么样」在库里没有对应的一行，必须由读侧按 $T_{load}$ 取最新拼出来。**写侧越简单，读侧越贵，这是同一个设计的两面。** 反过来，Kimball 的 SCD Type 2 把「当前」写进了表里，读侧一次等值过滤即可，但每次属性变更都要在执行顺序里定位旧行、关行、插行——这个动作与并行加载天然冲突，也让「回填历史」变成一次要重排顺序的作业。

**公开证据**：Hub / Link / Satellite 的只追加语义、以及「Hub 不含描述性字段」这条规则，见 Data Vault 2.0 的公开规范材料（2013 起；版本与细节请以官方文档当前版本为准）【公开，可自行核验】；Data Vault 2.0 的系统化整理见 Linstedt 与 Olschimke（2015）【公开，2015】；SCD 的 Type 1–3 出自 Kimball 方法论首版（1996）【公开，1996】，Type 4 及以后的编号是 Kimball Group 后续在设计要点（Design Tips）系列里陆续补出的分类（具体篇目请以该系列文章的当前版本为准）【公开，可自行核验】；开放表格式一侧的能力以规范与发布说明为准——Iceberg 表规范 v2 定义了两类删除文件，Hudi 1.0 的公开变化集中在记录级索引与非阻塞并发控制（以该 release note 为准）【公开，2024】。

**失效条件**：当实体属性几乎不变、消费又集中在「当前状态」时，追加写的好处一项都用不上，而它换来的表数与连接链路照付——此时正确做法是留在查询结构族（星型 + SCD Type 2），而不是引入集成层。

这一节还给出一条**反直觉的判据**：想要「加载快」，追加写并不是唯一路线。若日增量行数只占全量的一小部分，且每实体每天变更次数不多，SCD Type 2 的关行-插行代价就是一次按主键的 UPDATE，而它换回的是读侧不必做时点切片【经验】。判断方法很直接：统计「每实体每日变更次数」与「取某时点画像」的查询占比——前者高、后者也高时，才轮到追加写；两者都低时，追加写的读侧账没人替你还。

这条追加写的差异还会把三套时态（业务时态 $T_{biz}$、加载时态 $T_{load}$、删除时态 $T_{del}$，见主文件 §2.2.2）分别安置到不同的地方，而安置方式决定了「补数」这类动作有多难：Data Vault 把三套时态都表达成 Satellite 的列，删除另写一条生效卫星记录，于是迟到数据是「多了一行」而不是「改了一行」（[§4.2.3](03-data-vault-section-4-sec4.md)）；Anchor 的每个属性表自带业务时态，删除靠区间关闭；Kimball 的 SCD Type 2 只有业务维度的起止日期，加载时态与删除时态通常无处安放——**当要回答「上月报表当时看到的是什么」时，只有前两者能答**。这也解释了为什么 7.1 里排在第一位的判据「追加还是更新」在本主题里权重很高：「报表要不要按当时口径重述」问的不是性能，而是加载时态有没有地方存。

#### 7.3.2 版本连带范围：属性组、单属性，还是整行

**机制是什么**：变更判定与版本产生的**粒度**——一次变更会让多大的范围产生新版本。

| 方案 | 版本落在 | 一个属性变一次，被连带复制的是 | 要把连带范围降到更细，得多付什么 |
| --- | --- | --- | --- |
| Data Vault | 卫星表（属性组） | 该卫星表的整行（`hash_diff` 覆盖该表全部列） | 拆更多 Satellite → 查询要连接更多表（[§4.1.5](03-data-vault-section-4-sec4.md)） |
| Anchor | 单个属性表 | 只有这一行 | 表数 ≈ 属性数；查询层视图要生成与重建 |
| Kimball 星型 + SCD Type 2 | 维度表整行 | 该维表全部列 | 拆维表 → 星型的 JOIN 数上升 |
| ER 3NF | 不产生版本（原地覆盖） | 无 | 要历史就得手工上拉链表，复杂度回到读侧 |
| 宽表 / 拉链表 | 事实行或整表分区 | 分区按回刷范围重写 | 无（历史已被丢弃） |

**由此必然导出的性质**：因为 Data Vault 的变更判定单元是**一张卫星表的整组属性**，所以组内任一属性变化都会让整组产生新行——它比 SCD Type 2 省（连带范围收敛到属性组，而不是整个实体），但比 Anchor 贵（Anchor 的连带单位是单个属性）。**「属性之间互不牵动」只有 Anchor 做得到，这是它唯一无法被 Data Vault 覆盖的性质**；反过来，Data Vault 的表数比 Anchor 少一个量级，元数据对象数与查询层的生成成本都低得多。这条差异直接决定了选型：当「属性互相牵动」的代价比「多几张表」更贵时选 Anchor，反之选 Data Vault。本主题内部的几个模式失效点（多活动卫星的写放大、计算卫星的存储随重算次数增长）都是同一条粒度约束在不同构件上的表现。

**公开证据**：卫星表把同一 Hub 的属性切成若干属性组、每组按时间独立追加（组内属性随该组一起产生新版本）见 Data Vault 2.0 著作（2015）【公开，2015】；一属性一表、每个构件自带业务时态与加载时态，见 Anchor Modeling 的公开方法论材料与配套论文【公开，可自行核验】；SCD Type 2 的版本粒度是行，见 Kimball 方法论（1996）【公开，1996】。

**失效条件**：当消费侧查询长期只用到少数几个属性时，细粒度的收益消失、读侧成本照收。判断方法：统计最常用的 20 条查询里用到的属性落在几张卫星表 / 属性表上——若长期只落在 1–2 张上，说明拆分没有兑换成任何东西。

把这条粒度差异代回主文件 §2.3.2 的四行对比，可以读出它真正的代价位置：同一批变更下，SCD Type 2 的存储成本与 Anchor 同阶（每变更一行），但它的**每行都要维护两个日期列并被每个消费者过滤**；Data Vault 的存储成本按属性组放大（组内无关属性被一起复制），换来的是「哪一组在变」这件事在物理上可见，可以只调度受影响的卫星表作业（[§4.1.7](03-data-vault-section-4-sec4.md) 的三项监控就是按这个粒度设计的）。**粒度选择的实质是「把不相关的属性绑在一起」还是「把成本摊成更多张表」，两者都要付账，只是账户不同。**

#### 7.3.3 标识的确定方式：哈希键、代理键，还是 IRI

**机制是什么**：「谁是同一个实体」由什么决定——一个可计算的函数、一次分配、还是语义公理。

| 方案 | 标识怎么来 | 跨源同一实体怎么处理 | 判错之后的回退动作 |
| --- | --- | --- | --- |
| Data Vault | 哈希键 = MD5 / SHA(record_source ‖ 业务键) | 同一业务键在不同源算出同一个值（[§2.2.3](03-data-vault.md)） | 撤掉一条 Same-As Link 边，重求连通分量 |
| Anchor | Anchor ID（可为哈希，也可为代理键） | 等价关系需外部判定，判定结果可落成独立关系表 | 同上 |
| Kimball 星型 | 代理键（自增 / 取号），维表按业务键去重后分配 | 无原生机制，靠 ETL 人工映射表 | 重建维表并重指事实表外键 |
| ER 3NF | 主键取源业务键或代理键 | 跨源需人工映射表 | 同上 |
| OneID（物理合并） | 合并后的统一 ID | 物理合表 | **不可回退**，只能整体重跑 |
| 本体 | IRI 标识资源 | 以等价公理（如 `owl:sameAs`）表达同一性 | 撤一条公理，重新推理 |

**由此必然导出的性质**：因为哈希键由「来源 + 业务键」确定性算出，所以 Hub 的主键不依赖序列号，也不需要中心取号服务——写入可以并行、流批可以同时写同一个 Hub（[§4.2.3](03-data-vault-section-4-sec4.md)）；也正因为它是算出来的而不是分配的，哈希输入的字段顺序、分隔符、大小写规整只要改一处，全库的键会同时改变，那是一次全量重建而不是一次配置修改。反过来，代理键让「谁是谁」由维表分配，读侧更直观，代价是写入有了顺序依赖，且跨源归并要靠 ETL 再写一遍。第三条路把同一性交给带证据的等价关系，好处是判错可以撤销——这正是 OneID 场景里唯一可行的纠错路径。

**公开证据**：哈希键的构造（Hub 用 record_source + 业务键，Link 用参与方哈希键加关系类型）与「哈希键不依赖中心序列」这一设计目标见 Data Vault 2.0 的公开规范材料【公开，可自行核验】；RDF / OWL 以 IRI 标识资源、以等价公理表达同一性属 W3C 公开标准（OWL 于 2004 年成为 W3C 推荐标准）【公开，2004】；把 Hub / Link / Satellite 映射为类与属性属应用层映射工作，不依赖某个产品自带的能力【经验】。

**失效条件**：当哈希键被截断到 8 个十六进制字符（32 位）时，碰撞概率按生日界上升——在这个 2³² 的空间里插入约 6.5 万行，至少碰撞一次的概率已接近 40%【推算，推导链：1 − e^(−n²/2N)，n = 65536、N = 2³²，得 n²/2N ≈ 0.5】。症状不是报错，而是两个不同实体偶尔被合并成一条 Hub，表现为下游实体计数比源系统少（[§4.2.1](03-data-vault-section-4-sec4.md) 的同一条失效点，在选型阶段的表现就是：不要为省那点空间截断键）。

确定性也意味着不可协商：哈希键一旦上线，哈希输入的字段顺序、分隔符、大小写规整、以及业务键本身的取值范围，任何一项变更都等于换一套主键，全库 Hub / Link 的键要同时重算（[§4.2.1](03-data-vault-section-4-sec4.md)）。在选择哈希键时这不是一个「以后再说」的细节，而是要在第一天就写进规范的约束；核验路径也很具体——从源系统取 100 条记录，按登记的字段顺序与分隔符独立重算一次哈希，与库里值逐条比对，必须全等。代理键的对应代价是另一侧：它有稳定的分配顺序，但任何一次「合并两个源的同一个人」都必须在维表层面重指事实表外键，而这类改动与哈希键的重算一样是全局的。

#### 7.3.4 时点切片的落点：读侧的账记在谁头上

**机制是什么**：「某时点的画像」这件事在哪里被算出来——每次查询现算、加载后物化、消费接口声明，还是由推理机推导。

| 方案 | 时点切片在哪做 | 读侧最坏情况 | 因此多出什么要维护 |
| --- | --- | --- | --- |
| 裸 Vault（只有三件套） | 每次查询现算 | 扫全部历史 + 窗口聚合 | 无 |
| Vault + PIT / Bridge | 加载后物化成时点指针 | 按指针等值 JOIN，扫描量只与实体数有关 | PIT 的调度与回填（新的可用性依赖） |
| Anchor | 查询层视图 / 反规范化视图 | 本次用到的每个属性一次 JOIN | 视图的生成与重建 |
| Kimball 星型 + SCD Type 2 | 维表版本行 + 事实表代理键 | 一次等值过滤（`is_current`） | 每个消费者都要记得过滤 |
| OneData 式语义层 | 口径声明处（不改物理结构） | 由语义层生成查询 | 语义层的版本控制与 Owner |
| 本体 | 推理 / 查询重写 | 推理的物化或即时计算 | reasoner 与推理 profile 的选择 |

**由此必然导出的性质**：因为 PIT 把「每个卫星在时点 T 的有效版本」提前算成了 `load_date` 指针，消费查询从「扫全部历史 + 排序」退化成「按指针等值 JOIN」，扫描量与历史版本数脱钩（[§2.3.3](03-data-vault.md)、[§4.2.4](03-data-vault-section-4-sec4.md)）；代价是 PIT 自己变成一份要调度的物化资产，它落后时下游看到的是「数据没更新」而不是报错。同理，因为语义层只改「口径在哪里被声明」、不动物理结构，所以**「消费方是 Agent」这件事不能用来论证 Hub / Link / Satellite 的形态选择**——它只决定要不要在 Vault 之上再加一层，以及那一层由谁承担口径责任。

**公开证据**：PIT 与 Bridge 作为读加速构件、以及 PIT 的增量维护需求见 Data Vault 2.0 的公开方法论材料【公开，可自行核验】；开放表格式把「按快照读」做成存储层能力（Iceberg 规范 v2 的删除文件、Delta Lake 文档中的 Time Travel 与 MERGE 章节，请以当前文档版本为准）【公开，可自行核验】；至于「某平台自动维护 Data Vault」这类声称，判定方法是查该平台官方文档与解决方案库的最近更新日期与维护方，而不是看介绍文章【经验】。

**失效条件**：当查询时点高度任意（审计要问「任意一天」）且卫星变更极频繁时，为覆盖所有时点预建 PIT 的物化与维护成本会超过它省下的查询成本，PIT 自己变成新的全量扫描源（[§3.2.2](03-data-vault-section-3-sec3.md) 的失效点）。正确的分层是「固定高频时点物化 + 其余时点现算」，而不是把时点粒度继续调细。

读侧的账还有三种别的记法，选型时要和 PIT 放在一起比较，而不是只比较「建不建 PIT」：**物化视图**（由数据库负责刷新，省掉调度作业，但刷新策略与失败重试仍要看执行引擎的实现）、**消费侧快照表**（每个消费场景各存一份它需要的时点结果，读最快，但口径分叉与重复存储随之而来）、**按需缓存**（把热点时点的结果缓存在服务层，成本最低，代价是缓存失效与一致性窗口要显式声明）。三种记法的共同点是**把读侧的账换了个地方记**，没有一种能把「多表拼接 + 取最新版本」这件事消掉——它要么在加载后被算一次，要么在每次查询时被算一次。

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本不是产品报价，而是五项随规模变化的量之和：

```
总成本 ≈ 建模与口径协商成本 + f(实体数 × 属性组数 × 版本数) + g(连接链路长度 × 扫描量 × 查询频次)
                        + h(新增对象数) + i(口径数量 × 消费端数量)
```

各方案的差别不在总量，而在**哪一项是主导项**，以及**哪一项是上线时看不见的**：

| 方案 | 主导项 | 隐性成本（上线时不计入、三年后计入） | 什么条件下反转 |
| --- | --- | --- | --- |
| Data Vault | f + g（表数与连接链路） | PIT / Bridge 的调度与回填——一份要和上游保持同步的派生资产 | 源少且稳定时，f 与 g 都是白付 |
| Anchor | f（表数 ≈ 属性数） | 查询层视图的生成与维护；元数据对象数本身成为一项成本 | 属性演化不频繁时，细粒度只是额外开销 |
| 维度建模（星型） | h（改口径要回刷） | 下游每个消费者都必须记得写 `is_current` 过滤 | 维度属性每天都变时，任何保留历史的方案都按天膨胀 |
| ER 3NF | 建模与协商成本 | 加一个属性的 DDL 与回刷 | 单源、结构稳定时它是成本最低的 |
| OneData 式语义层 | i（口径数量 × 消费端数量） | 语义层本身成为取数链路的单点 | 度量数很少时，直接建视图更简单 |
| 本体 | 建模与协商成本 | 第二份必须与物理表保持同步的语义资产 | 只在跨系统语义对齐时才被收益覆盖 |
| 开放表格式承载 | h′（compaction 与快照过期） | 小文件合并的调度、资源与失败重试 | 写入频率低时，追加写不会产生小文件问题 |

这张表还有一条读法：**主导项决定「先在哪里变贵」，隐性成本决定「什么时候变成维护问题」**。Data Vault 的两项都来得早——f + g 随数据量与查询频次上升，而隐性成本（PIT / Bridge 的调度与回填）在消费侧第一次做交互式查询时就出现；这正是「源少且稳定」的组织引入 Vault 后感觉不到收益、却先感到成本的机制解释。Anchor 的建模成本在建模期就付完，此后每加一个属性只多一张表；开放表格式的隐性成本与写入频率挂钩——写入越频繁，compaction 越躲不掉。

五条【推算】示例（推导链写全，读者按自己的参数替换）：

- **表数放大**：沿用「同一业务过程在星型下是 1 张事实 + 12 张维度」的前提：12 个维度各对应一个实体，即 12 个 Hub；实体间被显式建模的关系条数按「每实体 1–1.5 条」折算，即 12–18 条 Link；每个实体的属性按变化节奏切成的属性组数按「每实体 1–2 组」折算，即 12–24 个 Satellite。合计 12 +（12–18）+（12–24）= **36–54 张**，中值约 45 张——约为星型基线（13 张）的 **3–4 倍**（36÷13≈2.8、54÷13≈4.2，取整为 3 与 4），多出来的每一张都是读侧要连接一次的对象。
- **历史不是免费的**：设 100 万实体、某属性组 20 列、单行约 200 字节、每天变更一次、保留一年。卫星侧行数 = 10⁶ × 365 = 3.65×10⁸ 行，存储 ≈ 3.65×10⁸ × 200 B ≈ **73 GB/年**；只保留当前状态的宽表是 10⁶ × 200 B = **200 MB**。两者之比约 365，正好等于平均版本数——**全量历史的存储成本就是「当前状态 × 版本数」**。把该属性的变更频率降到每年一次，上式变成 10⁶ 行 ≈ 200 MB，与宽表同阶：此时追加写的存储代价消失，可演化性仍在（这是 [§3.2.1](03-data-vault-section-3-sec3.md) 失效点的量化版）。
- **PIT 换来多少**：同一组参数下，取某时点画像若直连卫星要扫 3.65×10⁸ 行再做窗口聚合；有 PIT 后按指针等值 JOIN 只扫 10⁶ 行，**约 365 倍**（两个半数量级）。PIT 自身的存储：每实体一行、五列指针约 60 字节，单时点 ≈ 10⁶ × 60 B = **60 MB**；一年 12 个月末时点 ≈ **720 MB**，约为卫星侧的 1%。
- **Anchor 的表数**：表数与属性数同阶——一个 100 列的维度，在 Anchor 下是 100 张量级的属性表，查询要连接本次用到的每一个属性。
- **PIT 的增量维护比全量重建省多少**：同一组参数下，若一次上游补数影响 5% 的实体、涉及 12 个月末时点，增量回填要更新 10⁶ × 5% × 12 = **6×10⁵ 行**指针；若不做增量而整表重建，则是 10⁶ × 12 = **1.2×10⁷ 行**，约 20 倍【推算，推导链：两式相除 1.2×10⁷ ÷ 6×10⁵ = 20】。这也解释了为什么 PIT 的失效模式是「补数后指针静默指旧」而不是「重建太慢」——省下的正是发现它落后的那部分成本（[§4.2.4](03-data-vault-section-4-sec4.md)）。

**成本对比里不该出现的数字**：任何形如「性能提升 3.2 倍」「存储节省 63%」的结论，如果没有说明数据量、列宽、查询形态与基线口径，就没有可迁移性。上面五条推算把参数全部写了出来，就是为了让读者能用自己的实体数、属性组数、变更频率重算一遍；照抄别人的百分比之前，先问三件事：多大表、什么查询、什么硬件——三问缺一，就当方向记录而不当证据【经验】。

消费端适配成本（i 项）最容易被漏算。它的形式是「口径数量 × 消费端数量」：若一个团队有 200 张核心表需要进入语义层，每张表的定义、粒度、Owner、密级四项声明平均 0.5 人日，则一次覆盖约 100 人日（200 × 0.5）【推算】，且每新增或修改一个度量仍要重复这份动作。这解释了为什么语义层类落地的成本主导项是**定义覆盖度**，也解释了为什么验收要看覆盖到了哪些度量，而不是「声明文档写完没有」。

识别隐性成本有一个通用问法：**上线三个月后，这份资产由谁负责、它失败时谁会收到告警？**答不出 Owner 的那一项，就是未来最可能变成维护问题的那一项。PIT 的调度、语义层的声明、表格式的 compaction 都属这一类——它们在建模与选型阶段完全不可见，却决定了这套方案能不能被长期持有。

一个共同结论：**这几类方案的成本函数形式相同，差别只在主导项**。所以选型的第一问不是「哪个便宜」，而是「我的数据里，哪一项会先变大」。

### 7.5 决策树（每个分支都要有阈值依据）

```
开始：为集成层与消费层选方法
├─ Q1 未来 12 个月内，源系统数会增加，或每季度都有加字段需求吗？
│    ├─ 都不会 → 不建独立集成层：维度建模（星型 + SCD）直接建
│    └─ 至少一个会 → 进入 Q2
├─ Q2 审计或合规是否要求回答「某年某月这条关系 / 这个属性成不成立」？
│    ├─ 要 → 时态必须落在构件里（生效卫星 / Anchor 属性表 / SCD Type 2），进入 Q3
│    └─ 不要 → 不保留版本，不为时态付膨胀代价
├─ Q3 属性演化的单位是「单个属性 / 类型」，还是「属性组 / 新源」？
│    ├─ 以单属性与类型反复演化为主，且团队有 6NF 建模经验 → Anchor Modeling
│    └─ 以新增属性组、新增源为主 → Data Vault（继续 Q4）
├─ Q4 源系统是否 ≥ 3 个，且同一实体在多个源里各有业务键？
│    ├─ 是 → 哈希键 + Same-As Link（等价关系是数据，不是物理合并）
│    └─ 否 → 单源哈希键即可，不引入等价关系的连通分量维护
├─ Q5 消费侧是否存在反复的、时点明确的交互式查询？
│    ├─ 是 → 把 PIT / Bridge 排进同一期预算，别留到上线后补
│    └─ 否（T+1 批处理为主）→ 先不建 PIT，按查询 P95 观察后再建
├─ Q6 消费方是否包含 Agent / 自然语言取数？
│    ├─ 是 → 在 Vault 之上加语义层（OneData 式），不动 Hub / Link / Satellite
│    └─ 否 → 不加；先把 Hub 业务键的唯一性约束与 Owner 补上
└─ Q7 是否已有跑了几年的存量数仓？
     ├─ 是 → 单域试点 + 双轨对账，存量冻结而不推翻
     └─ 否 → 直接按落地步骤从零建，不需要双轨
```

读这棵树的方式是**自上而下**：Q1 决定要不要独立集成层，Q2 决定历史要不要留，Q3 决定集成层的构件粒度，Q4 决定标识与跨源归并的方式，Q5 决定读侧要不要提前物化，Q6 与 Q7 决定在之上加哪一层、以及存量怎么接。**前面的答案不会被后面的答案推翻**——如果被推翻了，说明有一层的结论下错了，而不是树画错了。

**阈值依据**（与树上节点一一对应；其中 Q2、Q4、Q6、Q7 是结构性问题，不需要估数）：

- **Q1「源会不会持续新增 / 会不会持续加字段」**：依据是判据「变更传导范围」——集成结构的收益只在约束持续变化时产生；若清单能在一年内枚举完，星型的上线速度压过可加性。这不是规模数字，而是「约束会不会持续变化」的近似分界【经验】，与 [§4.1.1](03-data-vault-section-4-sec4.md) 的起点判定同源。
- **Q2**：依据是结构约束而不是阈值——时态只有「记录」与「不记录」两种合法选择，问了就必须付版本膨胀，不问就一行都不该多存（[§3.2.5](03-data-vault-section-3-sec3.md)）。
- **Q3**：依据是 7.4 的成本函数——Anchor 的表数 ≈ 属性数，元数据对象数随属性数线性增长，只有当「属性演化本身是主要矛盾」时，这笔表数成本才被可演化收益覆盖；判据是过去一年新增 / 改类型的属性个数与它们落在几张表上，而不是数据量【推算，推导见 7.4 表数项】。
- **Q4**：依据是 7.3.3——哈希键让跨源同一业务键自动对齐，而等价判定一旦引入弱证据就会通过连通分量放大假阳（[§3.2.3](03-data-vault-section-3-sec3.md)）。所以判据是结构性的、不需要估数：源系统数直接可数，问题只是「同一实体是否在几个源里各有业务键」——源数 ≥ 3 与 [§3.3](03-data-vault-section-3-sec3.md) 决策表「源系统 ≥ 3 个 + 跨域整合」一行的门槛一致。
- **Q5**：依据是 7.4 的第三条推算——直连卫星扫 3.65×10⁸ 行、经 PIT 扫 10⁶ 行，差约 365 倍；若消费侧存在反复的时点查询，这笔读代价没有别的路可走。判定方法是抽最近 100 条查询，数其中多少条在做「多表拼接 + 取最新版本」【推算，推导见 7.4】。
- **Q6**：依据是 7.3.4 的结论——语义层只改「口径在哪声明」，不改变 Hub / Link / Satellite 的形态，所以它排在决策树末端，且不影响前面任何一条分支（[§5.2.2](03-data-vault-section-5-ai.md)）。
- **Q7**：依据是存量迁移的退出条件——双轨的成本主体是对账作业，只有「已有可对账的存量链路」时才需要它；源系统保留期之外的历史无法重建，只能以首次加载时点作为最早的业务时态并显式标注（[§4.4](03-data-vault-section-4-sec4.md)）。

需要强调的是：这七个节点里只有 Q1、Q3、Q5 用了近似判据，其余四个的答案由约束直接决定。把可判定的问题写成阈值，是决策树最常见的画蛇添足。

### 7.6 选型矩阵与组合

矩阵按「场景」而不是「方案」组织——选型的输入是你的处境，不是候选清单。每行的「不选它的原因」都写成机制层面的理由，而不是「性能差」这类形容词。

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 源 1–2 个、业务稳定、报表消费为主 | 维度建模（星型 + SCD） | 雪花（层次确属独立对象时） | 不选 Data Vault：可演化性用不上，却要付 3–4 倍表数（7.4） |
| 源持续新增、口径未定、跨域整合 | Data Vault 集成层 + 星型汇总层 | Anchor（属性演化为主矛盾时） | 不选纯 3NF：每次加属性都要改表并回刷下游 |
| 单个属性与类型高频演化、结构要存续十年以上 | Anchor Modeling | Data Vault | 不选 Data Vault：连带范围是属性组，组内属性互相牵动（7.3.2） |
| 强审计 + 合规删除 + 需要时点提问 | Data Vault + 生效卫星 | Anchor（属性表自带时态） | 不选物理删除：审计要问的恰恰是被删掉的那部分 |
| 跨源 OneID / 主数据统一 | Same-As Link + 证据分级 | 物理合并式 MDM | 不选物理合并：判错不可回退（7.3.3） |
| 消费方是 Agent / 自然语言取数 | Vault + 语义层（Vault 之上） | Hub / Link 直接对接 | 不选直连：Vault 提供结构，不提供口径裁决（7.3.4） |
| 湖仓上承载 Satellite | 开放表格式 + 表格式原生追加 | 自建时态列与拉链表 | 不选自建：快照读与删除文件要自己实现一遍（7.3.1） |

矩阵的「备选」列不是「也可以」，而是「在什么条件下换」：Data Vault 换成 Anchor 的条件是属性演化成为主要矛盾（7.3.2），换成物理合并式 MDM 的条件是组织接受不可回退（7.3.3）——**每一行的备选都对应 7.3 中的一条机制，而不是一次性能权衡**。这也是矩阵按场景而非方案组织的原因：把方案当行，读者会去填「我这一格该填什么」；把场景当行，读者才会先确认自己的约束属于哪一族。

四条**常见组合**（每条给出职责边界与运维代价）：

1. **Data Vault（集成层）+ 维度建模（汇总层）**。边界：Vault 只负责实体标识、关系与属性历史的完整性，**口径只在星型一侧定义**（主文件 §2.4.2）。运维代价：多一层加工链路与两套血缘，任何一次口径变化都要先判断它属于哪一层的职责；生成侧通常交给模板化工具（dbt 生态的 DV 包、商业生成器或自研平台，见 [§4.3.1](03-data-vault-section-4-sec4.md)），**但生成器的输入必须是实体 / 关系 / 属性清单，不是源系统 DDL**——否则它会忠实地把源表结构生成成模型。
2. **Data Vault + 开放表格式**。边界：表格式提供追加写、快照读与删除文件，**业务时态与幂等键仍归加载作业**——快照时态是加载时态，不是业务时态，混用会在补数与迟到数据上给出错答案（[§5.2.1](03-data-vault-section-5-ai.md)）。运维代价：compaction 与快照过期策略成为常驻任务，且它们的失败不报错、只表现为查询变慢或成本上升。
3. **Data Vault + 语义层（OneData 式）**。边界：语义层只改「度量与实体标识在哪里声明」，不新增口径、不改物理表；未登记的指标不进入服务范围。运维代价：语义层成为取数链路的单点，一次错误的定义修改会同时改变所有消费端的结果，因此它必须进版本控制与评审。
4. **Data Vault + 本体映射**。边界：Hub 映射为类、Link 映射为关系、Satellite 映射为属性，等价边来自 Same-As Link；映射本身是应用层工作，不依赖某个产品自带的能力（[§5.3](03-data-vault-section-5-ai.md)、主文件 §2.4.3）。运维代价：多出第二份必须与 Vault 保持同步的语义资产，且必须有人对「两个 Hub 连错」负责——那是建模的错，不是图的错。

四条组合共同的代价结构：**每加一层，就多一份需要与上游保持同步的派生状态**（PIT / Bridge、表格式快照策略、语义层声明、本体映射），每一份都要有 Owner 与新鲜度监控。组合的原则是先建权威层，再按真实出现的消费需求逐层追加，而不是一次配齐。

组合之间还有一个常被忽略的区别：**口径责任的落点不同**。组合 1 把口径放在星型汇总层，Vault 只对实体与关系负责；组合 3 把口径放在语义层的声明里，物理层仍由 Vault + 星型承担。两者都能做到「一处定义」，差别在于**口径的变更由谁评审**——放在汇总层时它是一次建模变更，放在语义层时它是一次声明变更，而声明变更的影响面更大（一次错误的定义会同时改变所有消费端的结果）。选组合时先回答这一问，比先比较工具更重要。

矩阵里最容易被误读的是「消费方是 Agent」那一行：它不是结构问题，而是接口问题。把它读成「要选一个对 AI 友好的建模方法」，会导向在 Hub / Link / Satellite 上预留检索字段或提前向量化——这类动作把一份需要同步的第二状态写进了权威层（[§5.2.3](03-data-vault-section-5-ai.md) 讨论的「第二份真源」就是同一件事）。正确的读法是：Vault 的形态由 Q1–Q5 决定，Agent 只影响「在它之上再加哪一层」。

### 7.7 选错的代价与迁移成本

下面三条反模式，对应的是本章 [§3.3](03-data-vault-section-3-sec3.md) 决策表里「实时流式入仓」「跨域 OneID 主数据」两行的判据列，以及主文件 [§2.4.2](03-data-vault.md)、[§3.2.1](03-data-vault-section-3-sec3.md) 给出的「Vault 做集成层、星型做消费层」这条边界——这里把它们换到选型语境里说一遍：同一件事在设计阶段叫失效点，在选型阶段就是「选了不该选的方案」。

**反模式：把 Vault 当供数层** —— 症状：报表与看板直接查 Hub / Link / Satellite，每个需求临时拼一次多表连接与取最新版本。后果：读侧成本没有预算（7.4 的 g 项无人认领），更麻烦的是口径落在了「这次查询怎么拼的」里，而不是落在某一层的定义里。正确的做法：Vault 之上必有消费层（星型汇总层或语义层），时点切片走 PIT / Bridge（[§4.1.6](03-data-vault-section-4-sec4.md)）。

**反模式：用取号 / 代理键替换哈希键** —— 症状：Hub 主键来自序列或 ID 服务，理由是「哈希键不好读」。后果：写入不再能并行，多源加载要排队等一个全局序列（7.3.3 的机制直接失效），晚到数据要靠到达顺序而非业务时态解释；跨源同一实体也不再自动对齐。正确的做法：Hub / Link 用确定性哈希键，并把字段顺序、分隔符、大小写规整登记成规范，用 100 条反向抽检验证（[§4.2.1](03-data-vault-section-4-sec4.md)、[§4.2.3](03-data-vault-section-4-sec4.md) 的失效条件）。

**反模式：把 OneID 做成物理合并** —— 症状：等价判定的结果直接落成一张合并后的客户表，旧 ID 不再保留。后果：判错时只能整体重跑，错误已经通过下游报表扩散；且这类错误不报错，只让客户数与 ARPU 系统性失真（[§3.2.3](03-data-vault-section-3-sec3.md)、[§4.2.6](03-data-vault-section-4-sec4.md)）。正确的做法：等价关系是数据——Same-As Link 加证据分级、只保留当前有效边，弱证据限制在强证据分组内部。

三条反模式按暴露方式可以排一个序。**「把 Vault 当供数层」暴露得最快**：消费方第一次做交互式查询时就会感到等待，代价立刻可见、也最容易补（补建 PIT / Bridge）。**「用取号 / 代理键替换哈希键」暴露得最隐蔽**：它在上线当天一切正常，只在第一次并行加载或第一次流式入仓时表现出约束，而那时键的设计已经写进了全库；识别信号是「同一个源的两个加载批次不能同时跑」。**「把 OneID 做成物理合并」后果最重**：它产出的是错误但看起来正常的数，且不可回退——客户数少算或虚高都不会触发任何告警，只在结算、审计或对外披露时暴露。

**换成另一个要动什么**（工作量量级，不是工期承诺）：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 星型 → Data Vault | 大（按 Hub / Link / Satellite 重切并回填历史） | 大（查询沿链路重组，通常要在其上再建星型视图） | 中（新增一套加载与校验链路） | 大（三类表的建模纪律） |
| 3NF → Data Vault | 大（按业务键重切，跨源归并要重做判定） | 大（多表拼接改由 PIT / Bridge 承接） | 中（同上） | 大 |
| Data Vault → Anchor | 大（从属性组拆到单属性，历史行要重新分配） | 大（查询层视图重建） | 中（视图生成器成为新组件） | 大（6NF 建模能力） |
| Data Vault → 语义层（叠加） | 无（不改物理表） | 小（消费端换成指标名） | 中（语义层成为新单点，需 Owner 与版本控制） | 中（口径定义的责任转移） |
| Data Vault → 开放表格式承载（换承载，不动建模） | 中（重写快照读取路径，数据本身不重切） | 小（时点切片逻辑不变） | 中（新增 compaction 与快照过期策略） | 中（时态语义的坑） |
| Data Vault → 宽表 / 星型（反向） | 中（只迁当前状态，历史通常无法带走） | 中（去掉时点切片逻辑） | 小（Vault 侧链路退役） | 小 |

这张表里最容易被低估的是最后一行的**不可逆性**：正向迁移丢的是工作量，反向迁移丢的是历史——Vault 里那些「某属性在 2021 年是什么」的行，一旦迁回只存当前状态的宽表就再也取不回来。因此退出的决策要在试点阶段就想清楚，而不是在成本压力出现时才考虑。

迁移的通用原则只有一条：**先建新的一层，让它与旧层并行跑一段，用同一个业务问题对账，验证一致后再切换消费端**（[§4.4](03-data-vault-section-4-sec4.md) 的对账作业就是这条原则的载体）。建模方案的迁移不存在「一次性大爆炸」的成功路径，因为建模的产物是口径，而口径是否一致只能靠两套结果对账确认。

上表漏算得最多的一项，是双轨期本身的人力：两份调度、两份监控、一份对账作业。它不随数据量增长，却需要稳定的常驻投入，也因此成为「迁移做了两年还没切完」的常见原因（[§4.4](03-data-vault-section-4-sec4.md) 给了退出双轨的四个条件）。**迁移的成本主体因此不是数据搬运，而是两套结构同时存在期间的口径对账与消费端切换**——这也是判断要不要迁移的第一道自检：如果旧结构上并没有人做口径对账，那新结构上线后也不会有。

### 7.8 小结

下表把 7.5 的决策树压成八行，每行只保留「处境 → 建议 → 机制理由」。**读法**：先找到与你最接近的那一行，再回看它对应的 7.3 小节确认理由是否成立——理由不成立就换行；若有两行同时像你的处境，按 7.5 的 Q1 先定要不要集成层，再往下看。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 源少、结构稳定、以报表消费为主 | 维度建模（星型 + SCD） | 追加写的可演化性用不上，读侧代价却照付 |
| 源持续新增、跨域整合 | Data Vault + 其上的星型汇总层 | 新增对象不改既有对象，演进成本与历史长度解耦 |
| 单个属性与类型高频演化 | Anchor Modeling | 版本连带范围是单属性，属性之间互不牵动 |
| 需要回答「某时点成不成立」 | 生效卫星 / 原生时态属性表 | 时态写成追加记录，时点提问退化成区间谓词 |
| 跨源实体必须统一 | 哈希键 + Same-As Link + 证据分级 | 等价关系是数据，判错可撤 |
| 消费侧出现反复的时点查询 | PIT / Bridge（与三件套同期预算） | 把切片从查询时挪到加载后，扫描量与版本数脱钩 |
| 消费方是 Agent | Vault 之上加语义层与本体映射 | 机器要的是口径与语义裁决，而 Vault 只提供结构 |
| 湖仓上落 Satellite | 开放表格式承载 + 业务时态自持 | 追加与快照由存储层提供，业务时态仍归加载作业 |

还有一种处境值得单列：**已经有一套跑了多年的数仓，想换**。此时第一步不是比较方案优劣，而是把现状的痛点归到 7.3 的哪一个机制上——若是「加一个源要改一堆既有表」，问题在 7.3.3 与 7.3.2（标识与构件粒度）；若是「加一个字段要回刷下游」，问题在 7.3.1（写入模式）；若是「取某时点的数要么等、要么对不上」，问题在 7.3.4（切片落点）。**痛点归错了类，换方案只会把成本从一个账户挪到另一个账户。**

> 本节小结：这一组候选里**唯一真正起决定作用的差异**是**「历史与上下文被放在哪里」**——写进当前表里（星型 + SCD）、拆进按属性组追加的卫星表（Data Vault）、拆进一属性一表（Anchor）、物化到事实行上（宽表），还是交给存储快照与推理层（开放表格式、本体）。它同时决定了 7.3 的四个维度：加载能否并行、版本连带范围多大、标识是否可算、读侧的账记在谁头上。其余维度（生态、学习成本、AI 友好度）都是这条差异的下游表现，不该被当成独立判据——**判断一次选型是否站得住，只问一句：三年后第一次有人要「某年某月的数据」，它是被算出来的，还是早就被存下来了。**
