## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

同一份清单里藏着时间差。「GraphRAG」与「图基础模型」被并列写在一起时，读者会以为它们是同一档成熟度的两件事：前者已经有版本化的开源实现，今天就能拿来搭一条只读的检索通路；后者到目前为止，本节列不出一个可指名的、既不是模型发布方也不是项目承建方的第三方生产案例。按同一份清单排期，前者是一个能验收的试点，后者会变成一个没人敢签收的项目。

本节给每个方向一个级别，级别由三条可核验判据决定，不由感觉决定：

- **L1 生产可用**：① 已 GA 且有正式 release note；② 有第三方（非厂商、非项目承建方）公开生产案例；③ 接口稳定。三条**全中**才算 L1 —— 可以排进路线图。
- **L2 可试点**：已可用但接口或生态未稳，或仅有厂商 / 建设方自有案例，或只在小规模被验证。可以做 PoC，**不要做核心依赖**。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录，**不要在架构里预留假设**。

这三条判据在本主题下**不做任何修正**，也不会在某个单元格里就地放宽。**第②条是最难满足的一条**：公开材料里「我们用 X 做了 Y」的绝大多数是**建设方自述** —— 自己做项目、自己写文章，按定义落在 L2 里。本节对②的要求是：案例来自既不是能力提供方、也不是项目承建方的第三方。**第②条核不到就是 L2**，不存在「准 L1」「L1 的边界案例」这类说法。

**表里没有一行是 L1。** 最接近的是 5.2.1 与 5.2.2 对应的两条（GraphRAG、LLM 生成图查询）：① 有可核验的落点，缺的是 ② —— 本节列不出一个既非模型 / 框架发布方、也非项目承建方的第三方生产案例；③ 也**没达标**：GraphRAG 判「部分」（各实现的图 schema 与检索接口不同），LLM 生成图查询判「未稳」（生成正确率随 schema 复杂度变化）。按判据它们是 L2，本章不接受「业界都在用」代替「有一个能被指名的案例」。七行里另有两条（LLM 工具调用 + 图、图作为 Agent 的长期记忆）是有①而③未稳、②同样缺；剩下三条（图上的可解释 Agent、图基础模型、多模态与联邦）连第①条都还没有落点。这一点值得停下来想一想 —— 本节最接近可用的两条，靠的都是**把建图与取数这件事变便宜**，而不是靠提升推理能力；这提示「AI 时代的前沿」在这条技术线上更可能是成本结构变了，而不是图推理方法被重写。

**L2 在实际排期上是什么意思**：它可以做 PoC，可以把「不影响主链路」的部分接上去，但不要把它写进对外承诺的能力清单。判据之外还有一条取材纪律 —— 每个方向都会给「读者可以怎么自己核验」，核验顺序固定：先查官方发布说明里有没有这条能力（这是①）；再查有没有**不是建设方**的人写过它在生产中的用法（这是②）；最后看接口有没有变过，一年内改过两次接口的方向，即使前两条满足也只能按 L2 排期。本节表的「现在该做什么」一列，就是按这个顺序推出来的。

读本节时守住四条命名与版本纪律：

- **区分产品名与能力名**：「把图查询交给 LLM」「用图做记忆」这类能力，在不同平台与框架里叫法完全不同，不要张冠李戴。
- **区分已发布与路线图**：图上的基础模型类工作绝大多数停在本章 §3.2.7 描述的「论文与公开骨干」状态，论文标题不等于产品开关。
- **区分单机内嵌与分布式**：被当作「轻量图检索」宣传的嵌入式图库，其分布式扩展要单独核验 —— 判定方法是看它的发布说明里有没有独立的多机执行组件，而不是看 benchmark 博客。
- **区分论文原型与产品实现**：一个方法在论文里跑通，与它被某产品按版本发布，是两件事；本节只在能给出「文档名 + 年份」时才算证据。

### 5.2 演进方向逐条拆解（核心节）

每个方向都按同一组问题写：旧方案卡在哪、AI 改变了哪个机制、由此得到什么、由此付出什么、有什么证据、成熟度几级。**机制一栏是本节的判别器**：只换了前端的，这里会直接写「这是接口改良，不是架构变化」。

四个方向的顺序按「离可用有多远」排，不按概念大小排：5.2.1 与 5.2.2 排在前面，是因为它们的失败模式可枚举、可回滚（索引建错了重建、查询生成错了驳回），**改错的代价可控**；5.2.3 涉及写入，错了会长期留下痕迹；5.2.4 三个方向都不具备「先小规模试一个月再决定」这个条件 —— 它们要么需要跨域语料，要么需要跨机构协商，没有低成本试错入口。排期时这条差别比「哪个更先进」重要得多。

#### 5.2.1 GraphRAG：把「关系可达」加成第二条召回通路

- **旧做法与它的卡点**：纯向量 RAG 把每个片段压成一个向量，**关系在这一步被压掉了**（[§7 §7.3.4](07-graph-reasoning-section-7-sec7.md)），于是「A 的供应商的母公司是谁」这类问题在结构上不可答 —— 不是检索参数没调好，而是那条通路不存在。另一条老路是先把本体与图谱建好再问答，卡点在人力：抽取、对齐、存边都要有人定义与维护，这件事的边际成本随文档量线性上升，于是多数团队建到一半就停了。
- **AI 改变了什么机制**：把索引期「抽取实体关系并归一」这一步的**人力成本换成 token 成本**，同时在检索期加一条通路。判决权没有被交给模型 —— 抽取负责把文本变成带出处的边，检索负责沿边走，模型只负责组织答案。这是**成本函数的变化加接口形态的变化**，不是图推理算法的变化。
- **由此得到的**：因为抽取可以批量、低成本地跑遍全部语料，所以「先请人把本体建好」这个前置条件被跳过，没有现成图谱的组织也能起步；因为边必须带出处（[§3 §3.2.6](07-graph-reasoning-section-3-sec3.md) 的结构要求），所以答案能回溯到片段与路径，而纯向量检索只能给出「参考了这几段」。
- **由此付出的**：
  - ① **成本形状变了**：索引期成本随「新增文档量」增长，而不是随「查询量」增长（[§7 §7.3.4](07-graph-reasoning-section-7-sec7.md)）—— 增量更新时只有新增文档进入这条链路，Streaming GraphRAG 一类工作针对的正是这一点。知识库天天大量新增而查询稀疏时，这笔钱永远摊不平 —— 这是它最常见的适用边界，不是性能问题。
  - ② 抽取错误沉淀进图，且**看不出是抽取错还是检索错**；错边会长期留在索引里被反复用。
  - ③ 实体归一与 OneID 口径不一致时，图会碎成互不相连的孤岛，表现为「加了图以后回答质量与纯向量持平，却付出了索引期成本」（§3.2.6 已把这条列为它的主要失效点）。
  - ④ 在线链路多出实体识别与融合两段，**第一步错了后面全错**；这一步的错误率由业务词典与别名表决定，属主数据问题而非模型问题。
  - ⑤ 各实现的图 schema 与检索接口不通用，换实现要重建索引与提示词，没有可迁移的中间格式。

| RAG 路线 | 优势 | 劣势 | 适用 |
| --- | --- | --- | --- |
| 纯向量（Naive / Hybrid 复用同一通路） | 简单、便宜、语义召回强 | 关系被压成标量距离，多跳结构上不可答 | FAQ、释义、单跳事实 |
| 混合（向量 + 关键词 + 重排） | 召回率高 | 仍无结构化通路，多跳靠巧合 | 中等复杂度问答 |
| GraphRAG（图 + 向量双路） | 多跳可达、可给路径证据 | 索引期成本前置、实体归一是硬前提 | 复杂问答、跨文档串联 |

- **判定方法**：
  - 判断一个「GraphRAG 方案」值不值得做：先看语料的新增速率与查询频次。知识库稳定、查询频繁，索引期成本摊得平；反之先别做（这是成本形状决定的，与模型好坏无关）。
  - 判断它有没有真的起作用：抽一批问题看答案里引用的实体，检查这些实体在图上是否连成一条可达路径。连不起来，就是实体归一的问题，不是模型能力的问题。
  - 判断该不该继续投：把「多跳问题在真实问题里的占比」写进验收口径；只拿挑出来的多跳题做评测，等于自证。
- **证据与来源**：【公开】Microsoft 于 2024 年公开 GraphRAG 的实现与配套论文（按其官方仓库的发布记录与论文页核验，请以当前版本为准）；【公开】2024–2025 年出现了一批公开的改进工作（LightRAG 一类，标题与年份可按论文标题检索核验）；平台侧的 GraphRAG 能力与存储选择（Neo4j / NebulaGraph / Kùzu 一类嵌入式图库等各家命名不同）请按各自官方文档核验，本节不代其断言。关于「用 GraphRAG 把回答准确率提升了多少」的百分比说法，本节不转述 —— 这类数字没有共同的评测集与口径。
- **成熟度**：**L2**（① 有；② 缺 —— 本节列不出一个既非发布方、也非承建方的第三方生产案例；③ 部分 —— 各实现的图 schema 与检索接口不同）。升级到 L1 的条件可观察：出现一份由第三方发布、写清语料规模、问题类型与评测集的生产材料。

#### 5.2.2 LLM-as-Reasoner over KG：模型生成查询，事实仍由图给出

- **旧做法与它的卡点**：图上的关系查询要么用 Cypher / SPARQL（会写的人极少，业务问题要先被翻译成查询语言），要么让模型凭空推理（幻觉、不可溯源、给不出证据链）。路径推理的人力瓶颈不在算法，而在**把业务问题写成路径模式**这一步（[§3 §3.2.3](07-graph-reasoning-section-3-sec3.md)）。
- **AI 改变了什么机制**：**接口边界变化** —— 模型从「答案生成器」变成「查询生成器」，事实仍只由图查询结果给出。判决权没有被交给模型，只是把「会写查询语言」这项技能要求从人移到了模型；这是人机分工的变化。
- **由此得到的**：因为事实只能来自图查询，所以结论可以溯源到具体路径或子图，进而能进入需要逐条举证的流程（[§7 §7.1](07-graph-reasoning-section-7-sec7.md) 的判据 3）；因为入口是自然语言，业务方不必先学会查询语言，图上的数据第一次对非工程角色可用。
- **由此付出的**：
  - ① **校验层成为新增的必需品**：生成的查询要同时校验语法与结果集，这一层要人维护，且它自身的 bug 会以「答案对不上」的形式出现。
  - ② 最难发现的是「语法正确、语义错」：时间窗写反、关系方向写反、把「曾经有过」实现成「当前成立」，结果量级看起来完全正常。判定方法是抽一批问题，把答案里的实体拿回图上验一遍可达性。
  - ③ 每多一次工具调用，延迟与失败点就多一个；多跳问题的往返次数随跳数增长。
  - ④ 路径枚举随跳数指数增长，**超级节点**（公共 IP、中间账户一类）会让 Top-K 证据失去区分度（§3.2.3 的失效点）——用了 LLM 也不会让这个问题消失。
  - ⑤ schema 变更要同步改提示词与查询模板，模型侧与图侧的口径从此绑在一起。

| 让模型做什么 | 该不该做 | 理由 |
| --- | --- | --- |
| 把问题翻成图查询 | 可以 | 结构事实仍由图给出，可复核 |
| 判断两个实体是否是同一个人 | 不可以单独做 | 这是实体归一问题，错了会让图碎成孤岛 |
| 直接回答「有没有关系」 | 不可以 | 答案无法被图查询复核，等于放弃结构约束 |
| 把查询结果讲成人话 | 可以 | 只做表述，不引入新事实 |

- **判定方法**：
  - 判断某个「自然语言查图」能力能不能上：看它输出的是**查询语句**还是**答案**。输出查询语句的可以被校验与复现；直接给答案的无法复核，等于把结构约束丢掉了。
  - 判断校验层够不够：准备二十个问题，其中至少五个是「时间窗」与「方向」这类容易反着写的问题，看校验层能不能把错的挡下来。
  - 判断该不该对外开放这个入口：先看 schema 描述是否稳定。schema 一周一变时，提示词与查询模板的维护成本会以「答案忽然不对」的形式出现。
- **证据与来源**：【公开】ToG（Think-on-Graph）、RoG 等 LLM + 图查询工作在 2024 年前后公开发表（会议与年份请按论文标题检索核验）；【公开】MCP（Model Context Protocol）规范于 2024 年 11 月公开（请以官方规范当前版本为准），它解决的是工具发现与调用，不包含「这条查询该不该被执行」的裁决语义；图库侧的自然语言查询与工具接入请按各自官方文档核验。
- **成熟度**：**L2**（① 有；② 缺；③ 未稳 —— 生成正确率随 schema 复杂度变化，跨实现不可移植）。它比 5.2.1 更适合作为第一个试点：只读、可回滚、不需要重建索引。

#### 5.2.3 图作为 Agent 的记忆与证据链

- **旧做法与它的卡点**：智能体的「长期记忆」过去就是一段会话历史加一个向量库。卡点有两个：向量召回按相似度取回片段，取不回「同一实体在三个月前是什么状态」，也无法回答两个实体之间到底有没有关系；可解释性上，它只能给出「参考了这几段」，给不出「结论依据的是哪条路径」。
- **AI 改变了什么机制**：把记忆的存储单元从**文本片段**换成**带时间戳的实体-关系**，写入与读出都从「按相似度」变成「按实体与时间」。这是索引结构的变化，**不是模型能力的变化** —— 模型还是那个模型，变的是它能取到什么。
- **由此得到的**：因为记忆按实体组织并带时间戳，所以「某主体在某时点的状态」可以被精确取回，而不是让相似度替你决定用哪个版本（这与 5.2.1 是同一件事在 Agent 侧的表现）；因为关系是显式的，所以「为什么这么答」可以给出证据链，而不是让模型自述理由。判定方法：抽一批「两个月前」型问题，看系统给的是当时状态还是当前状态。
- **由此付出的**：
  - ① **记忆写入策略成为新的责任点**：什么该入图、什么该遗忘。写入策略错了，模型会长期带着错误事实，而这类错误在对话里完全看不出来。
  - ② 记忆是**第二份真源**：列级权限、行级权限与合规删除要在图这一侧再实现一遍（与 [§4 §4.2](07-graph-reasoning-section-4-sec4.md) 的图治理是同一组问题，不是新问题）。
  - ③ 无标准：各框架的记忆抽象不同，迁移要重写；记忆格式没有跨实现约定，这一点短期看不到改善。
  - ④ 记忆增长会让检索变慢，必须另做剪枝与摘要 —— 而剪枝掉的内容就再也找不回来了，这是「精确取回」的对价。
- **判定方法**：
  - 判断该不该让记忆入图：先问「这个事实会不会被问第二次，并且会被问到时点」。不会，就不必入图，向量或会话历史更便宜。
  - 判断写入策略是否可用：问一句「源数据删了一条，记忆里那条什么时候消失、由谁负责」。答不上来就先别做。
  - 判断记忆有没有在悄悄失真：抽一批「两个月前」型问题，人工核对系统给的是当时状态还是当前状态。
- **证据与来源**：【公开】Agent 框架的长期记忆组件有版本化发布 —— LangGraph 的检查点与长期存储、LlamaIndex 的记忆模块均于 2024 年前后进入各自官方文档（请按各框架的版本历史核验其抽象与限制）；【公开】图上的事后归因方法（GNNExplainer、PGExplainer、ProtGNN、SubgraphX 一类）为公开发表工作，年份可按论文标题检索核验 —— 它们是**解释模型**的手段，不等于「可解释 Agent」；Ant Group XAI 与「风控场景解释器」属建设方自述材料，既不构成①也不构成②，本节只登记其存在，不转述能力声称。
- **成熟度**：**L2**（① 有；② 缺；③ 未稳）。同小节里的「图上的可解释 Agent」是另一个子项，单独记 **L3**：① 缺（没有针对「图 + Agent 解释」的产品发布说明）、② 缺（没有可指名的第三方生产材料）、③ 未稳 —— 与 5.1 总表里那一行的三条判据逐条一致。

#### 5.2.4 图基础模型、多模态图与联邦图学习：都停在同一个位置

这三个方向机制不同，但成熟度判据完全相同：① 缺（没有 GA 产品的正式发布说明）、② 缺、③ 未稳，因此都是 **L3**。放在同一小节里分别写，是因为它们卡住的位置恰好是同一处 —— **都缺一个能被指名、能被复核的落地场景**。

**图基础模型（GFM）**

- **旧做法与它的卡点**：每个业务从零训练一个图模型，标签少、迭代快；转导式模型学的是全图的归一化邻接矩阵，对新节点泛化差（主文件 §2.2 的归纳性 vs 转导性）；多数团队的第一版现实上限是「图特征 + 梯度提升树」（§3.5 的反模式）。
- **AI 改变了什么机制**：判决信息的载体从「单图数据」移到「跨图预训练语料」—— 与「LLM 把判决信息放进预训练语料」是同构的转移：把「每任务一次训练」换成「一次预训练 + 多次适配」。
- **由此得到的**：因为下游新增任务的边际成本从一次完整训练降到一次微调或零样本，所以**只有任务数足够多的组织**才摊得平预训练投入（§3.2.7 已给出这条判据：任务只有一两个时摊不平）。
- **由此付出的**：图没有统一的「文本」载体，节点特征跨图不可比，预训练语料与你的分布不匹配时，零样本结果可能比自建小模型更差且更贵；骨干更新会波及全部下游任务，需要统一回归验证；中小团队只能用公开骨干，等于把一个关键组件放在别人的发布节奏上。
- **证据与来源**：【公开】2023–2024 年集中出现的一批公开工作（OpenGraph、OFA、G-Retriever、LLaGA、GraphGPT、UniGraph 等），会议与年份可按论文标题检索核验；【公开】作为技术前提的图骨干网络一线（GraphGPS、Graphormer、SGFormer、Exphormer、NodeFormer、Polynormer 一类）同样可按论文标题核验，其中 Graphormer、GraphGPS 已收在主文件 §2.3.2 的模型表里 —— 本节只把它们登记为 GFM 的技术前提，不列为演进方向；本节不转述任何「在某数据集上提升 N%」的数字。
- **成熟度**：**L3**（① 缺；② 缺；③ 未稳）。

**图 + 多模态**

- **旧做法与它的卡点**：分子与蛋白、视频、3D 点云的对象不在同一表征空间，各模态各建一套管线；跨模态的问题要么把整段视频塞进上下文，要么退回单模态结论。
- **AI 改变了什么机制**：把不同模态的对象映射进同一图结构（场景图、分子图、视频图），让关系推理跨模态复用 —— 变化发生在**表征对齐**这一层，不在推理层。
- **由此得到的**：因为关系被显式化，多模态问答可以走「沿关系逐跳」，而不必依赖「相关片段恰好共现」。
- **由此付出的**：对齐质量决定一切，而跨模态对齐没有统一评测；图构建成本按模态上升（视频与点云最高）；标注更贵；对齐错的时候结论错得毫无征兆。
- **证据与来源**：场景图、分子图这类公开任务与数据集长期存在（可按任务名与数据集名检索核验）；Multi-Modal GraphRAG 归入本小节（其自述覆盖图像、表格与视频），本节只登记落点，不转述其效果声称；【经验】工业侧公开案例多为建设方自述。
- **成熟度**：**L3**（① 缺；② 缺；③ 未稳）。

**图上的联邦学习**

- **旧做法与它的卡点**：跨机构图推理（金融、政务、医疗）在合规上不能交换原始图，而单机构的图看不全链路 —— 这是合规硬约束，不是技术偏好。
- **AI 改变了什么机制**：把「交换图数据」换成「交换模型更新」，机制变化发生在**信任边界**上，不在建模上。
- **由此得到的**：因为原始图不出域，跨机构协作第一次在合规上变得可谈；这一条的价值全部来自合规，而不是来自精度。
- **由此付出的**：图上的联邦比样本联邦更难 —— 子图怎么划分本身就影响结果，跨域实体对齐要在受限条件下完成；每加一个参与方，通信与调参成本上升；收敛性与一致性也更难证明。
- **证据与来源**：联邦图学习方向的公开发表工作可按关键词检索核验；【经验】工业侧公开材料多为建设方自述，本节不把它当作判据②。
- **成熟度**：**L3**（① 缺；② 缺；③ 未稳）。

**这三个方向共用的判定方法**

- 判断该不该为 GFM 立项：先看下游任务数是否真的在增加。任务只有一个时，预训练的成本摊不平，这是算术问题不是技术问题。
- 判断「通用图模型」能不能用：先在你的图上跑零样本，与「图特征 + 梯度提升树」基线对照。赢不了，就不要进入预训练投入。
- 判断多模态图值不值得建：先看跨模态对齐有没有可复现的评测口径。没有口径时，对齐结果只能当参考，不能当事实源。
- 判断联邦图的启动条件：先看合规是否**硬性**要求原始数据不出域。只是「更安全」而不是「必须」，投入产出比通常不成立。

### 5.3 与本主题既有栈的接口在哪

判断标准是接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。凡是说不清失败归属的「与 X 结合」，在评审会上听起来完整，在事故复盘时提供不了任何信息。

本主题有一处特别的接缝：**AI 带来的新组件几乎都在读图，而不是在写图**。写图的一侧（图构建、实体归一、边口径）仍然由既有栈负责，它的 Owner 没变；于是新增的失败几乎都落在「读的一方以为图里有，其实没有」这种形态上。表里最后一列的级别沿用 §5.1 的三条判据，评级对象是**接口**；凡与某个 5.2.x 方向对应的行，级别与该方向一致，并在「现状」列注明对应关系。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 图构建 / 实体归一 → 检索层 | 实体编码（OneID 口径）加边口径声明；实体归一结果作为检索入口 | 主数据 Owner —— 归一错了是主数据的错，不是模型的错（§3.2.6 失效点） | 既有栈（主文件 §2.1、[§4 §4.2](07-graph-reasoning-section-4-sec4.md)） |
| 图数据库 → 双路召回 | 查询语言 / 图算法过程 + 向量索引；返回子图或路径，边带出处与时间戳 | 检索链路的 Owner —— 出处缺失会让答案无法复核 | L2（对应 5.2.1，同一结论） |
| KG schema → 模型生成查询 | schema 描述（节点与关系类型、属性、示例查询）作为上下文；模型输出查询语句 | schema 的 Owner —— 模型不会为「schema 里没写的关系」负责 | L2（对应 5.2.2） |
| 图查询结果 → 生成层 | 结果集（路径 / 子图 + 出处）；契约是「只依据结果作答，越界即拒答」 | 定义这条契约的人 —— 模型给不出图里没有的事实 | L2（对应 5.2.2） |
| 图 → Agent 记忆 | 写入口（哪些事件入图、何时入）+ 读出口（按实体与时间取邻域） | 记忆写入策略 Owner —— 写错会让模型长期带着错误事实 | L2（对应 5.2.3） |
| 图算法特征 → 既有 GNN / 梯度提升树 | 特征表（度、PageRank、社区标签、三角形计数一类） | 特征定义的 Owner —— 特征口径变了模型就漂 | 既有栈（[§4 §4.2](07-graph-reasoning-section-4-sec4.md)） |
| 图 → 合规删除与权限 | 删除传播清单（图、副本、索引各一跳） | 没把删除传到副本的一方 | L2（软删除与删除传播无跨实现约定） |

```text
写图的一侧（Owner 未变）             读图的一侧（AI 新增消费方）
  主数据 / OneID ──┐                    ┌── GraphRAG 检索（只读）
  业务过程事件 ────┼──► 图构建 + 实体归一 ──┼── 模型生成查询（只读）
  边口径声明 ──────┘         │           ├── Agent 记忆（读 + 写）
                             │           └── 图特征 → 既有模型（但这是既有用法）
                        权 限 / 删 除 ──► 必须在每个读侧副本上再实现一次
── 判据：新增消费方在读图，写图的责任人没有增加；失败最常出现在「读的一侧
   以为图里有」—— 判定方法是把答案里的实体拿回图上验一遍可达性
```

边界上最难的两件事，恰好都属于图推理之外的能力：

- **权限**：图上的可见性由图侧与存储侧分别执行，一旦把子图或邻域导出给检索层或记忆层，可见性必须在副本上重新对齐。副本权限放宽一次，前面为「不越权遍历」做的所有工作都白做（[§6 §6.4](07-graph-reasoning-section-6-sec6.md) 的案例里，「不能在遍历中越权」正是这条约束）。
- **删除**：合规删除要求「该主体相关的节点、边、副本、索引都消失」，而图上的删除会改变结构 —— 删掉一个中间节点可能让两条本来可达的路径断裂，进而改变已有结论。判定方法是把删除请求当一次图变更来跑：先列影响面，再删。

| 你要判断的事 | 现在能查清楚吗 | 查不清时先做什么 |
| --- | --- | --- |
| 新增的检索层有没有越权拿到点 | 能（用越权查询测试） | 先给检索层设只读账号，再谈能力 |
| 记忆层的数据是否受删除约束 | 多数情况下不能 | 先写清记忆的删除责任人与时限 |
| 图 schema 变更会影响几处消费方 | 能（查消费方清单） | 把消费方登记进图治理（§4.2） |
| 新增消费方是否改变了写图口径 | 能 | 口径只有一处定义，消费方不得自行加工 |

**第三方生产案例**

- 本节对「图与 AI 结合」这部分**没有可指名的第三方非建设方生产来源** —— 这正是 5.1 表七个方向里四个停在 L2（GraphRAG、LLM 生成图查询、LLM 工具调用 + 图、图作为 Agent 的长期记忆）、三个停在 L3（图上的可解释 Agent、图基础模型、图 + 多模态 / 联邦图学习）的原因。
- 可自行核验的入口有三处：各项目的官方仓库发布记录（对应判据①）、独立学术评测与公开数据集上的复现结果（可验证但不等同生产）、以及既非提供方也非承建方的公司工程材料（对应判据②，也是当前最缺的一类）。
- 上面第三类的判定要点是**材料来源**：一篇讲「我们把图检索接进问答」的工程博客，如果作者同时是该系统的建设方，按本节定义属于 L2 的证据，不构成判据②；这不是说它不可信，而是说它证明的是「这件事能被做出来」，不是「这件事在别人那里也被做成了」。判据②要回答的正是后一个问题，而它需要的样本量本来就比①大得多。

**三条可自行核验的公开线索**

- 想知道某个图库的自然语言查询能力处在什么状态：查它的官方文档里该能力是标为正式功能还是预览，以及首次发布的说明写在哪一版。
- 想知道某个 GraphRAG 类项目是否仍在演进：只看两点 —— 最近一次提交时间与未关闭 issue 的积压情况。
- 想知道某个「图 + 大模型」的说法是否成立：找它的原始出处，看那句话是**产品页**、**论文**还是**第三方评测**。三者能支撑的结论强度完全不同。

**一条不属于本节任何演进方向的说法**：「图作为『AI 资产化』的载体」（点名 OneData 4.0 把知识图谱纳入企业 AI 资产目录，Dataphin / DataWorks / DataFinder 原生支持 KG 管理）落在**资产目录**这一侧，判据也不同于本节的三条 —— 平台文档能证明的是该平台自己的功能清单，不能证明有第三方在用它管图。要核它，按各平台官方文档与发布说明逐项对照，并区分两件事：把图资产**列进**目录（盘点与检索，属前端能力），与图资产的**权限、血缘、删除都受目录管**（治理，才影响架构）。本节不代其断言支持到哪一层。

### 5.5 被过度宣传的部分

**「GraphRAG 一定比向量 RAG 强」** —— 实际是「在需要跨片段串联的问题上多一条通路」，在单跳事实与释义类问题上通常打平或更贵。为什么会这样：多出来的实体识别、图查询与融合三段是纯成本，只有问题的结构真的需要多跳才收得回；而评测集里多跳问题的占比，恰恰是最容易被挑高的变量。什么时候它才会成真：用同一套包含真实问题分布（而不是只挑多跳题）的评测集，把三条路线一起测，并且公开问题分布。

**「用 LLM 做多跳推理就能替代图查询」** —— 实际是把结构约束换成了概率。为什么会这样：多跳的每一步都需要**精确的邻居集合**，而模型的「跳」是语义联想，它能给出通顺的链路却无法保证每一跳在图上真实存在（§3.5 的「把 LLM 当万能推理器」）。什么时候它才会成真：模型能对「我走的这一步」给出可被图查询复核的证据，且复核通过率被公开评测。

**「图会通向 AGI / 图 + 量子计算带来加速」** —— 实际是把两类不同的判断混成了一句。为什么会这样：图是**结构化信号的载体**，它擅长的是关系与结构，而 AGI 的判据与图这种表示形式没有必然关系；量子算法在图上有理论加速，但今天的工程问题是图构建、实体归一与在线延迟，不是某个子问题的渐近复杂度。什么时候它才会成真：分别给出可测的中间目标 —— 前者需要「关系推理能力可迁移到未见任务」的公开评测，后者需要量子硬件上跑出一个端到端的、比经典实现更便宜的图构建或检索流水线。

这三条的共同点是：**模型与硬件把「算」变便宜了，没有把「判断关系是否真实存在」变便宜**。所以判断一个「AI + 图」的方案值不值得投，只需问一句 —— 它省掉的是「算」的成本，还是「验」的成本。省「算」的成本，收益立刻兑现；声称省「验」的成本，先让它证明复核环节还在。

### 5.6 未来 3–5 年：可证伪的预测

写不出信号与反信号的预测不写。下表后两列是给自己留的检查项，不是修辞。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| GraphRAG 的落地会集中在「知识库相对稳定、查询频次高」的场景，而不是所有问答场景 | 公开案例开始同时报告语料新增速率与查询量；产品文档里出现「先估索引期成本」的实施指南 | 出现大量「高频新增文档 + 稀疏查询」且被证明划算的公开案例 |
| 图上的瓶颈从「模型能力」退回「实体归一」，与主数据质量挂钩 | 公开材料开始把实体归一的准确率与主数据 Owner 写进同一张表；GraphRAG 类项目的事故复盘集中在别名与同义实体 | 检索与抽取侧继续单独报告提升，而实体归一步骤在公开材料里持续缺席 |
| GraphRAG 与专用检索会合体，而不是取代向量检索 | 主流检索框架把图查询与向量召回做成同一个可组合的检索器（[§3 §3.2.6](07-graph-reasoning-section-3-sec3.md) 的双路结构成为默认） | 出现「纯图检索全面取代向量检索」的统一架构与公开评测，且在多类问题上都不输 |
| 图基础模型在 3–5 年内仍以「公开骨干 + 小规模微调」为主，端到端自建 GFM 的组织很少 | 公开工作集中在适配与评测，而不是新的预训练语料；组织侧材料以「用了哪个公开骨干」为主 | 出现多个组织自建拳头 GFM 并公开跨域评测结果、且收益可复现 |

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 被要求「上 GraphRAG」 | 先做只读试点：抽一批真实问题，与现有向量检索在同一批问题上对照 | 多跳问题在真实问题里的占比，以及实体识别的错误率 | 不要在实体归一未与 OneID 对齐时上生产；不要用挑过的多跳题集证明它更好 |
| 已经建了图谱，想接自然语言查询 | 先固定 schema 描述与示例查询，把语法 + 结果集校验做成必经环节 | 生成查询的「语法正确语义错」占比，以及修一版 schema 要改几处 | 不要让模型直接回答「有没有关系」；不要把归一交给模型单独做 |
| 在做 Agent，想加长期记忆 | 先把记忆的写入与遗忘策略写下来，再选存储 | 写入策略引发的错例是否能在对话层被发现 | 不要在没有任何遗忘策略时把全部事件写进图；不要以为图里的记忆不需要权限与删除 |
| 被 GFM 吸引，想自建预训练 | 先用公开骨干跑零样本，与「图特征 + 梯度提升树」基线对照 | 下游任务数是否真的在增加（决定预训练摊不摊得平） | 不要在只有一个下游任务时做预训练；不要用公开数据集上的成绩作为选型依据 |
| 需要跨机构图推理（合规驱动） | 先做可行性验证：把实体对齐与子图划分这两步在受限条件下跑通 | 参与方数量增加时通信与调参成本的斜率 | 不要在合规方案未定前先建图；不要把「联邦」当成绕开合规的手段 |
| 有多模态图需求（视频 / 点云 / 分子） | 先确认跨模态对齐的误差是否可接受，再决定是否上图 | 对齐质量是否有可复现的评测口径 | 不要在没有评测口径时把对齐结果当事实源 |
| 被要求「在图上做推理来提升指标」 | 先跑「图特征 + 梯度提升树」基线，只有结构信号强于手工特征时才上 GNN | 基线与 GNN 的差距是否稳定存在（§3.5 记录的三个月效应） | 不要在没跑过基线的情况下上 GNN；不要把 Demo 上的效果当预期 |
| 已经在做图推理，想加一层 AI 解释 | 先确认解释的读者是谁：给监管看的要路径证据，给业务看的要自然语言，两者不是同一件交付 | 解释被引用进流程的比例（没人用说明读者判断错了） | 不要用模型自述的理由替代路径与子图证据（§7.1 判据 3） |

最后一列是这个表里唯一有长期价值的：前三列做的事一年后都能补，「不要做」的那几件做错了，要花一年拆掉。

同一件事换个说法：**这张表里没有一行是「上什么模型」，全部是「先弄清哪一条约束」**。这不是巧合 —— 本主题下真正决定成败的约束（实体是否已归一、关系是否真是信号、结论要不要举证、成本付在索引期还是在线期），在本节所有方向里都先于模型出现。所以本节给出的级别，实际是**这些约束的成熟度**，不是模型的成熟度。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**把「建图」的人力成本换成了 token 成本** —— 过去要人读文档、定本体、抽实体关系，现在可以批量跑；由此图从「需要专门立项才能拥有的资产」变成「可以按文档量线性支付的索引」。它**没有改变**的是：关系是否真实存在、同一实体是否只有一种表示、结论要不要能被逐条复核 —— 这三件事仍然由主数据与建图口径决定，也因此决定了所有基于图的能力的上限（[§3 §3.2.6](07-graph-reasoning-section-3-sec3.md) 与 [§7 §7.3.4](07-graph-reasoning-section-7-sec7.md) 讲的是同一件事）。本节没有方向达到 L1，最接近的两条靠的都是**把建图与取数变便宜**，而不是靠提升推理能力：这说明能把成本降下来的方向，比声称能提升能力的方向更接近可用；同时也说明「业界都在用」与「能被判据核验」是两件事，前者永远不能替后者。
>
> 💡 **思考锚点**：拿你自己的语料算一下「半年新增文档速率 ÷ 查询频次」这个比值——它落进本节 5.6 表里「知识库相对稳定、查询频次高」那一格，还是落进它的证伪信号「高频新增文档 + 稀疏查询」？若落进后者，本节说的「把建图人力换成按文档量线性的 token 成本」这笔索引期支出，你打算靠什么摊平？
