## 3. 设计模式与范式

> 原 § 3 共 132 行、列出 7 个模式与 10 条反模式，全部为文字条目、无结构示意块；本节重写为 ~300 行模式手册，为每个模式补上结构示意、机制因果句、代价与失效点。

### 3.1 先看约束：模式不是选择题，是约束的产物

「用户欺诈评分用节点分类、团伙识别用子图分类、企业问答用 GraphRAG」这类速查表把设计讲成了按业务问题挑一个。但模式之间真正的分界线不在业务名字上，而在几条更硬的约束上：图是**追加事实**还是**覆盖式更新**、查询是**点查**还是**沿关系遍历**、节点数是否跨过单机显存、以及**新节点在训练时是否已经存在**。最后一条尤其关键——它决定你用转导式还是归纳式，而这一条选错，模型上线当天就会在冷启动实体上失效，和业务场景叫什么名字无关。

另一条约束最容易被忽略：**图本身不是免费的**。图构建的代价不只在存储，而在于「边的语义必须由某个人定义并维护」。同一批业务数据，A 团队按「同一设备」连边，B 团队按「同一收货地址」连边，两张图对不上，而它们各自都能跑出不错的离线指标。所以图构建在上游是 OneData 业务过程的「图投影」——实体来自 OneID，边来自标准化的业务过程事件；这一步没做好，后面的模式选择再好也救不回来。

还有一条约束不在下面的约束表里：任务层级。节点级、边级、子图级、全图级四类任务的输出形态完全不同（一个分数、一个候选集、一个子图、一张图），而它们的评估口径、可解释性要求与上线方式也随之不同。把子图级任务当节点级做（例如用节点分类器拼团伙），通常表现为指标看起来还行、业务上却解释不通。

本节的组织方式：先给约束表，再逐个模式写清它被什么逼出来、结构长什么样、代价是什么、在什么条件下优点反转成缺点。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 边的写入模式（追加事实 / 覆盖更新）与可回放性 | 决定图能否做时间快照、模型输入能否重放 | 「图是静态的」——边的含义与权重重算会让同一张图两月不一致 |
| 访问模式（点查 / 沿关系遍历 / 聚合扫描） | 决定存储选型：遍历型任务用图数据库，聚合型任务回列存 | 「图数据库什么都能干」——它在全表聚合上比列存差得多 |
| 新节点在训练时是否存在 | 决定转导式还是归纳式架构 | 「先把模型训好再说冷启动」——转导式模型对新节点根本无法打分 |
| 变更频率与图版本要求 | 决定要不要时间快照与图血缘 | 「图不需要版本」——图漂移会直接表现为下游模型漂移 |
| 规模（节点数 / 边数 / 平均度 / 超级节点） | 决定采样方式与是否必须分布式训练 | 「加机器就能变大」——邻域采样规模随层数指数增长，不是线性问题 |
| 团队技能与运维能力 | 决定上 GNN 还是「图算法特征 + 梯度提升树」 | 「上了 GNN 才算做图」——多数团队的第一版收益来自图特征而非 GNN |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 模式 A：节点分类（Node Classification）

- **被什么约束逼出来**：标签只存在于一部分节点上，要推断其余节点——约束是「标签稀疏 + 关系本身就带信息」。
- **结构**：以消息传递为准的「构图 → 特征 → 分层采样 → 训练 → 推理 → 回写」流水，推理阶段必须能只取一个新节点的 k 跳邻域。

```python
# 节点分类的结构：一层消息传递 = 一次邻居聚合
h_v = x_v                                   # 初始特征：OneID 主数据 + 画像标签
for layer in range(K):                      # K = 层数 = 感受野跳数
    m_v = AGGREGATE({ h_u for u in sample(N(v), fanout) })   # 采样邻居后聚合
    h_v = UPDATE(h_v, m_v)                  # 更新自身状态
y_v = classifier(h_v)                       # 节点级输出：分数 / 类别
# 关键：fanout 决定每次采样取多少邻居
#   【推算】fanout=10、K=3 时单节点感受野约 10^3=1000 量级（未去重）
#   → 层数每加 1，采样成本乘一次 fanout，这就是「不能盲目加深」的来源
# 关键：AGGREGATE 取 mean/max/attention，决定模型的归纳能力与可解释性
```

- **为什么这样设计有效**：因为聚合用的是「采样出来的邻居」而不是「全图归一化邻接矩阵」，所以训练好的模型可以直接吃进一个训练时没见过的新节点，这正是它在用户、设备、商品等实体类型上都能对新节点直接打分的原因。
- **代价**：需要为每个节点构造特征并在推理时实时取 k 跳邻域，所以必须配套「特征查找服务」与低延迟邻居获取；训练侧的采样把计算量压了下来，却把成本转移到存储与随机 IO 上。
- **失效点**：当图是**同配性弱**的（邻居与自身标签不相关，例如热门内容被各类用户共同消费）时，「邻居信号=标签信号」这一前提不成立，于是越聚合越接近噪声，表现为加深层数指标不升反降——因为聚合把无关邻居的均值当成信号。
- **真实使用**：【公开】消息传递式节点分类的起点通常归于 GCN（Kipf & Welling, 2017）与归纳式采样的 GraphSAGE（Hamilton et al., 2017）（可按论文标题检索核验）；【公开】PinSage（2018，Pinterest）把该范式用于十亿级规模的推荐召回，具体规模与指标以原论文为准；【经验】多数团队的第一版是把图特征（度、PageRank、社区标签）喂给梯度提升树，而不是直接上 GNN。

#### 3.2.2 模式 B：链接预测（Link Prediction）

- **被什么约束逼出来**：要判断「一条边是否存在或应该存在」，而训练时只有正样本边、没有天然的负样本边——约束是「负样本必须造，且造法决定模型学什么」。
- **结构**：编码器（GNN）+ 打分函数 + 负采样器三段式，训练目标是让正边分数高于负边。

```text
链接预测的结构（三段式，任一段换掉都会改变结论）
  ① 编码器    GNN 把节点映射成向量 h_v
  ② 打分器    score(u, v) 的四种常见形态：
                · 双线性（如 DistMult）   —— 参数量小，适合关系型 KG
                · 平移（如 TransE）        —— 结构简单，对「一对多」关系弱
                · 旋转 / 复数（如 RotatE） —— 能表达对称、反演、组合关系
                · MLP                    —— 表达力强，但更易过拟合
  ③ 负采样    谁被抽成「不存在的边」，模型就学「什么样的边不该存在」
                · 均匀采样   → 模型只学到「与高频节点相连」这一条捷径
                · 按度分布采样 → 缓解高频节点偏置
                · 难负样本挖掘 → 指标更高，但训练更不稳
  ────────────────────────────────────────────────
  关键：负采样策略写在实验记录里，否则指标不可比
  关键：候选集怎么产生（全量排序 / 受限候选）决定这个模式能不能上生产
```

- **为什么这样设计有效**：因为把「边是否存在」变成一个可微的排序问题，所以它既能用在补全知识图谱（实体对齐、缺失关系），也能用在推荐与风控的候选生成——同一个打分器换一批负样本就换了一个业务含义。
- **代价**：需要为每个节点维护向量并要求定期重训（图变了向量就旧了）；打分是全候选还是受限候选决定了延迟量级，受限候选省算力但把召回上限锁死在候选生成器上。
- **失效点**：当负采样用均匀采样时，「能预测边」这个优点会反转成「只学会预测高频节点的边」，因为均匀采样下绝大多数负样本都涉及少数高频节点，模型学会的捷径是把分数与节点热度挂钩——表现为离线 AUC 很高、上线后在长尾实体上完全失效。
- **真实使用**：【公开】TransE（2013）、DistMult（2015）、RotatE（2019）均为公开发表的知识图谱嵌入方法，题名与年份可按论文标题核验；【经验】风控场景里链接预测常与规则并用——模型给候选，规则给否决；判定方法：把负采样策略与候选集生成方式写进评估报告，看指标能否在换一批负样本后复现。

#### 3.2.3 模式 C：路径推理（Path Reasoning）

- **被什么约束逼出来**：业务需要的不是「一个分数」，而是「一条能被人读懂、能被复核的证据链」——约束是**结论必须可举证**（风控、合规、医疗、审计）。
- **结构**：起点 + 终点 → 候选路径枚举（图查询语言 / 搜索）→ 路径打分 → Top-K 路径作为解释输出。

```cypher
// 路径推理的结构：先枚举可解释的路径，再对路径打分
// 【推算】路径数量随跳数指数增长：平均度 d、长度 L 时约 d^L 条
//   d=20、L=4 时约 1.6e5 条 —— 所以必须在下推(枚举)时就收敛
MATCH p = (a:Account {id: $src})-[r*1..4]->(b:Account {id: $dst})
WHERE ALL(rel IN r WHERE rel.ts >= $window_start)      // 时间窗收窄
  AND size([n IN nodes(p) WHERE n:HighRisk]) <= 2      // 结构约束收窄
RETURN p,
       reduce(w = 0.0, rel IN r | w + rel.confidence) AS path_score
ORDER BY path_score DESC
LIMIT $k                                              // Top-K 作为证据输出
// 关键：约束（时间窗、结构模式、节点类型）写在路径模式里，而不是事后过滤
// 关键：输出的是「Top-K 条路径」，业务看到的是路径，不是分数
```

- **为什么这样设计有效**：因为输出单元是一条具体的路径（谁 → 通过什么 → 到谁），所以结论天然可举证，人工审核可以逐条复核，这一点是任何只输出分数的模式做不到的。
- **代价**：候选路径空间随跳数指数增长，所以要么收窄搜索空间（损失召回），要么接受更高延迟；打分函数的参数需要标注数据，而无标注时只能退回规则权重（成为纯规则系统）。
- **失效点**：当图上存在**超级节点**（度数极大的公共节点，如共用出口 IP、公共中间账户）时，「路径可解释」反转成「路径爆炸且无区分度」，因为几乎任意两个节点之间都能找到一条经过超级节点的短路径——表现为 Top-K 里全是同一种无意义路径，业务的解释力反而下降。判定方法：看输出路径的分布，如果某类节点在多数路径里都出现，先做超级节点识别与关系分桶。
- **真实使用**：路径打分算法（PRA 一类，2010）与 LLM 直接生成/检索路径的做法（ToG 一类，2023 年及以后）均为公开发表的方法，题名与年份可按论文标题核验；【经验】把图遍历作为一等能力、在库内执行路径查询与图算法，是 Neo4j 一类原生图存储产品的设计路线，起始年份与版本口径以官方站点与发布记录为准；【经验】生产里常见形态是「图查询出候选路径 + 规则或模型打分 + 人工审核」，纯端到端的学习式路径推理在风控中较少直接上线。

#### 3.2.4 模式 D：子图匹配 / 子图分类

- **被什么约束逼出来**：风险或信号存在于**一组实体的整体形状**里，而不是单个实体上——「团伙」「资金环」「分子子结构」都只有作为一个整体才有意义。
- **结构**：先在图上定位候选子图，再对子图整体编码或做同构判定。

```text
子图匹配的结构（两条路线，成本差一个量级）
  ── 路线 1：精确子图同构（形状完全匹配）
     输入：模式图（如「A→B→C→A 的三人资金环」）
     做法：Ullmann / VF2 一类回溯搜索
     性质：精确、可解释；最坏情况是 NP 完全问题
     【推算】搜索空间随候选节点数组合式增长
       n=1e6 节点、模式 3 跳时，必须先用索引与标签筛到可回溯的规模（【经验】百级量级）再回溯

  ── 路线 2：近似 / 学习式子图分类（形状相似即可）
     ① 候选子图   k 跳邻域展开（【经验】k 取 1–2），限制子图大小
     ② 子图编码   GIN / 子图池化 / 子图向量
     ③ 输出       分类打分或相似度检索（可把子图向量存进向量库召回）
     代价：顶点数不确定，批处理要做图分块或子图采样
  ────────────────────────────────────────────────
  关键：选路线 1 还是 2，取决于「业务要的是完全同构，还是相似即可」
        要举证就用路线 1，要召回率与规模就用路线 2
```

- **为什么这样设计有效**：因为建模单元与业务单元对齐（一个团伙一步就是一个样本），所以标签可以按团伙给、结论可以按团伙讲，避免了「节点分数拼不成团伙」这个经典断层。
- **代价**：子图编码器要么固定子图规模（截断长尾子图），要么做图分块（引入批处理复杂度）；精确同构路线对图规模极其敏感，必须先做索引与标签筛选；子图向量库需要与主图同步更新。
- **失效点**：当候选子图靠 k 跳邻域展开时，「以整体为单位建模」反转成「子图之间高度重叠」，因为相邻实体共享大部分邻域，正负样本在输入上几乎相同——表现为离线指标虚高、上线后无法区分邻近团伙。修法是在候选生成阶段做去重叠（限制子图重叠率或按社区切分）。
- **真实使用**：精确子图同构算法（Ullmann、VF2 一类）与学习式子图编码（GIN 一类）均为公开方法，年份与作者可按论文标题检索核验；【公开】GIN（2019）在图同构判定能力上与 WL 测试的关系是其论文的核心论点（可按论文核验）；【经验】风控团伙识别的常见组合是「社区发现切分（Louvain / Leiden 一类）+ 子图打分」，而不是在全图上直接跑同构搜索。

#### 3.2.5 模式 E：异构图 + 元路径（Heterogeneous Graph + Meta-path）

- **被什么约束逼出来**：图上有多类节点与多类边，而不同类型的边携带的语义完全不同（「用户-购买-商品」与「用户-浏览-商品」不是一回事）——约束是**边必须带类型语义，且可被显式指定**。
- **结构**：先声明图 schema 与元路径，再沿元路径采样邻居并分层聚合。

```cypher
// 异构图的 schema 是元路径的前提：类型必须显式声明
// 节点标签（对应 OneID 打出来的实体）
//   (:User) (:Item) (:Author) (:Category) (:Device)
// 关系类型（对应 OneData 标准化的业务过程）
//   (:User)-[:BUY   {ts, amount}]->(:Item)
//   (:User)-[:VIEW  {ts, dwell }]->(:Item)
//   (:Item)-[:BELONG_TO]->(:Category)
//   (:Item)-[:CREATED_BY]->(:Author)
// 元路径（一条链上「每一跳的边走哪一种」）
//   U-B-U  共购：共现信号
//   U-V-I-B-U 兴趣相似：内容信号（比共购更长，覆盖更广）
//   U-D-U  同设备：风控侧信号
MATCH (u1:User)-[:BUY]->(:Item)<-[:BUY]-(u2:User)   // 元路径 U-B-U
WHERE u1 <> u2
RETURN u2, count(*) AS co_buy_cnt ORDER BY co_buy_cnt DESC LIMIT 200
// 关键：换一条元路径 = 换一个语义，而不是换一组特征
// 关键：元路径数量随「节点类型数 × 跳数」增长，必须显式挑选而不是全枚举
```

- **为什么这样设计有效**：因为每条元路径对应一个可以讲清楚的业务语义（共购、同设备、同作者），所以异构图模型天然容易被业务方接受，也可以按元路径做消融实验定位哪类信号在起作用。
- **代价**：元路径需要人工挑选（枚举成本随类型数与跳数上升）；不同类型邻居的聚合需要分类型参数，参数量随关系类型数增长，小样本团队容易过拟合；schema 变更会同时改图构建与模型输入。
- **失效点**：当单条元路径上存在高连接度的中间节点（如热门类目、公共作者）时，「语义明确」反转成「语义被稀释」，因为沿元路径取到的邻居大多来自热门节点而非真实关系——表现为共购/相似信号退化成「谁都被这条路径连着」。修法是在元路径上按路径权重或节点度做归一化。
- **真实使用**：【公开】异构图注意力与元路径聚合的代表工作 HAN（2019）、HGT（2020）均为公开发表方法，题名与年份可按论文标题核验；【经验】电商与风控是主要落地场景，通常先用 2–3 条元路径做基线，再逐步增加而不是一次堆满。

#### 3.2.6 模式 F：GraphRAG（图 + 检索增强生成）

- **被什么约束逼出来**：纯向量检索只能召回「与问题语义相近的片段」，无法回答需要跨片段连起来的多跳事实问题——约束是**答案需要把分散在不同文档里的事实沿关系串起来**。
- **结构**：索引期做实体关系抽取落成图，检索期做「向量召回 + 图查询」双路，生成期由 LLM 组织答案并给出处。

```text
GraphRAG 的结构（索引期与检索期是两件不同的事）
  ── 索引期（离线，成本主要在这里）
     文档切片 → 实体 / 关系抽取 → 实体归一（对齐到 OneID 口径）
        → 入图（节点=实体，边=文档中陈述的关系，边带出处）
        → 社区发现 + 社区摘要（为「全局性问题」预生成摘要）
  ── 检索期（在线）
     ① 实体识别：从问题里认出实体（这一步错了后面全错）
     ② 双路召回：向量召回（语义相近的片段）
                  + 图查询召回（该实体的 k 跳邻居与关系）
     ③ 融合重排：按出处、时间、关系类型加权
     ④ 生成：LLM 只基于召回内容作答，并给出处链
  ────────────────────────────────────────────────
  关键：实体归一必须与主数据（OneID）口径一致
        否则「同一实体两种写法」会让图碎成互不相连的孤岛
  关键：边必须带出处，否则生成的答案无法回溯核验
```

- **为什么这样设计有效**：因为检索不只有「语义相近」一条通路，还有「沿关系可达」这条通路，所以「A 的供应商的母公司是谁」这类多跳问题可以被逐跳检索回答，而纯向量检索结构上只能祈祷两段事实恰好落在同一片段里。
- **代价**：索引期成本高（每个切片都要做实体关系抽取，还要做实体归一与社区摘要），且抽取错误会沉淀进图；在线延迟由「实体识别 + 双路召回 + 重排 + 生成」四段叠加，比纯向量检索多出图查询与融合两段。
- **失效点**：当实体归一没做好（同一实体多种写法未合并）时，「多跳可达」反转成「多跳断裂」，因为图被拆成了互不相连的孤岛，检索期只能退化成纯文本召回——表现为加了图以后回答质量与纯向量检索持平，却付出了索引期成本。判定方法：抽一批问题看答案里引用的实体，检查图上这些实体是否连成一条可达路径。
- **真实使用**：【公开】Microsoft 于 2024 年公开 GraphRAG 的实现（可按其官方仓库当前版本与发布记录核验）；【公开，2024 年及以后】把 LLM 生成的查询语句交给图数据库执行、再回到自然语言生成的路线，与 Neo4j、NebulaGraph 等图库公开的 GraphRAG 相关工作相关（可按各自官方仓库当前内容核验）；【经验】企业私有知识问答是主要场景，落地瓶颈通常是实体归一而不是模型能力。

#### 3.2.7 模式 G：图基础模型 / 预训练（Graph Foundation Model）

- **被什么约束逼出来**：每个业务都要从零训练一个图模型，成本重复投入，而标签少、迭代快——约束是**图任务很多、标签很少、单个任务的数据不足以支撑训练**。
- **结构**：在大量异构图/文本图上预训练一个骨干，下游按任务微调或零样本推理。

```text
GFM 的结构（预训练 / 微调 / 零样本三段，投入与收益分离）
  预训练（重投入，一次）
    多图 / 多域语料 → 自监督目标（掩码节点特征 / 掩码边 / 对比学习）
      → 骨干模型（能同时吃结构 + 文本属性）
  下游（轻投入，多次）
    ├─ 微调    有标注 → 少量样本微调任务头
    ├─ few-shot 少量标注 → 提示 / 少量样本微调
    └─ 零样本  无标注 → 直接推理（能力上限最低，但可用）
  ────────────────────────────────────────────────
  关键：收益点在「下游任务数」，任务只有一两个时预训练摊不平成本
  关键：预训练语料与你的图分布是否接近，决定零样本是否可用
        分布差异大时，零样本结果不能作为选型依据
```

- **为什么这样设计有效**：因为把「为一个数据集训一个模型」换成「训一个骨干再适配」，所以下游新增任务的边际成本从一次完整训练降到一次微调，这正是它在多任务组织里被提出的动机。
- **代价**：预训练本身需要大算力与跨域图语料，中小团队通常只能使用公开模型或不做；零样本能力与预训练语料分布强相关，换域时性能下降幅度无法先验预测；骨干更新会让所有下游任务需要重新验证。
- **失效点**：当你的图与预训练语料分布差异大、且下游只有一个任务时，「通用能力」反转成「比你自己的小模型更差且更贵」，因为预训练学到的先验在这个分布上不成立，而你又没有微调数据去纠正它。判定方法：先用公开骨干在你的数据上跑零样本，与「图特征 + 梯度提升树」基线对比，赢不了就不要进入预训练投入。
- **真实使用**：【公开，2023 年及以后，可按论文标题核验】图上的「预训练 + 下游」口径在 2023 年后出现了一批公开工作（OpenGraph、G-Retriever、LLaGA、GraphGPT 等），名称与年份可按论文标题检索核验；【经验】截至目前的实际落地多数仍在公开骨干 + 小规模微调，端到端自建 GFM 的组织很少。

### 3.3 模式选择决策表

下表「数据规模」列为【经验】量级区间，用于选型分档，不是实测阈值。

| 业务问题 | 数据规模【经验】 | 推荐模式 | 关键判据 / 工具 |
| --- | --- | --- | --- |
| 用户欺诈评分 | 千万–亿节点 | A 节点分类（GNN） | 新用户是否常见（决定是否必须归纳式）；PyG 一类框架 + 库内图算法 |
| 团伙识别 | 万–百万团伙 | D 子图分类 + 社区发现 | 是否要举证（要举证走精确同构，要召回走学习式） |
| 商品推荐 | 亿级节点 | A + E（异构图 + 元路径） | 冷启动实体占比；PinSage / GraphSAGE 一类归纳式架构 |
| 反洗钱 | 万–百万账户 | C 路径推理 + D 子图匹配 | 是否存在超级节点（超级节点不处理，路径无区分度） |
| 企业知识问答 | 万–百万实体 | F GraphRAG | 实体归一是否与 OneID 口径一致；图查询 + 向量双路 |
| 长期记忆 / 工具路由 | 百万实体 | G + F | 下游任务数是否够多（决定 GFM 摊不摊得平） |
| 分子性质预测 | 万–百万分子 | 通用 GNN | 图是否小而定（小图重结构、轻采样）；PyG / DGL 一类框架 + MoleculeNet 一类公开数据集 |
| 数据血缘 / 敏感传播 | 千–十万表 | 图数据库 + 图算法 | 查询是沿关系遍历还是聚合（决定是否上图库）；Apache Atlas 一类元数据平台 |
| 告警根因 | 万–百万调用 | C 路径推理 | 是否有明确的目标事件（无目标事件则退化为遍历）；OpenTelemetry 一类调用链数据 |

表里最常被误选的一对是 **A 与 D**：团队把「团伙识别」当成节点分类来做，给每个账号打一个欺诈分，再把高分账号拼成团伙。这在机制上注定不顺——团伙的判别依据是成员之间的连接形状，而节点分类器看到的是每个节点自己的邻域聚合结果，社区结构的信息在聚合那一步就被平均掉了。表现是：模型指标看起来不错，但业务侧拿到高分名单后仍然要人工重新攒团伙。反过来，用子图模式去做单实体评分，则要付出「为每个实体展开邻域」的成本，规模上一开始就吃亏。

### 3.4 组合模式：真实系统不会只用一种

**组合一：图算法特征 + GNN 打分 + 路径证据（可解释三件套）**。图算法（度、PageRank、社区标签、三角形计数一类）负责产出可解释的结构特征，GNN 负责把结构信号变成判别能力，路径推理负责在需要解释时给出证据链。职责边界是：特征层对业务可读、模型层负责精度、证据层负责举证。运维代价是三套要共用同一份图定义，图 schema 变更时三处同步改。适合规模：风控、反洗钱这类「精度与举证都要」的场景，也是生产里最常见的形态。

**组合二：图召回 + 向量召回 + 融合排序（推荐双通路）**。图召回负责覆盖「有关系但没行为」的实体（新用户、新内容靠关系被带出来），向量召回负责覆盖「语义相近但图上不相连」的实体，两路各自出候选后统一排序。职责边界是：图负责关系覆盖，向量负责语义覆盖，两路都不负责最终排序。运维代价是两套索引都要与主数据同步，且要维护融合权重。适合规模：亿级节点的推荐系统，冷启动比例越高，图召回的价值越大。

**组合三：KG + LLM 工具调用（GraphRAG 与 Agent 路由）**。KG 提供结构化事实与关系约束，LLM 负责理解问题、生成图查询、组织自然语言答案，图查询结果作为唯一事实来源。职责边界必须写死：**LLM 不负责凭空推理关系，只负责把问题翻译成查询并解释结果**。运维代价是查询生成需要校验（语法与结果集都要检查），以及实体归一必须与主数据一致。适合规模：实体数在万到百万级的企业知识场景；再大就需要在检索期做更激进的剪枝。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「图越大越好」 | 一张图里混着风控、推荐、血缘三类边，查询与训练都慢 | 遍历要扫过无关边、训练要过无关邻居，噪声进入聚合结果 | 认为「多就是全」，而统一成大图在演示时最直观 | 多张小图 + 共享主数据，用 OneID 串联 |
| 「GNN 一定能跑赢 XGBoost」 | 【经验】三个月后指标与图特征基线持平 | 投入沉没，且模型更难维护与解释 | 图是新方向，先做的人容易跳过基线 | 先做「图特征 + 梯度提升树」基线，只有结构信号强于手工特征时才上 GNN |
| 「盲目堆叠 GNN 层」 | 层数增加后训练变慢且指标下降 | 过平滑：多层传播后节点嵌入趋同；且【推算】K 层感受野达 K 跳、采样量按 fanout^K 指数增长 | 把「深=强」从视觉模型迁移过来 | 【经验】3 层以内起步；要更深用残差、初始残差与归一化 |
| 「忽视归纳性」 | 新用户、新商品上线后打不出分 | 转导式模型对新节点没有可用的嵌入 | 训练时全图在手，感觉不到问题 | 用归纳式架构（邻居采样类）；配套特征查找服务支持冷启动 |
| 「图构建不规范」 | 两个团队画的图对不上，边语义各不相同 | 实体与边口径不一致，跨域关系无法对齐，模型不可迁移 | 图构建被当成工程细节而非数据建模 | 边必须有明确语义、口径与生命周期，并在元数据中声明；图是业务过程的图投影 |
| 「忽略可解释性」 | 业务问「为什么判这个分」答不上来 | 高精度结论无法进入需要举证的流程，人工审核接不住 | 先追指标，解释被当作后期工作 | 配套解释方案：注意力、子图重要性、路径证据、LLM 把结果翻译成人话 |
| 「忽略图上的公平性与偏差」 | 少数群体节点分数系统性偏高 | 图上偏差会被传播放大，因为邻居聚合会把已有偏差再复制一层 | 训练数据本身带历史偏差，而图结构让偏差沿边扩散 | 公平性约束、去偏采样、敏感边过滤；把敏感属性从图中分离 |
| 「把 LLM 当万能推理器」 | 模型给出「关系」但图查询能证伪 | 丢掉结构约束与精确性，答案不可复核 | LLM 调用简单，不想维护图查询链路 | 让 LLM 调用图查询，结构事实由图给出 |
| 「图数据库当万能存储」 | 全表聚合、大范围统计变慢 | 用遍历型存储做聚合型任务，性能差一个量级 | 一张库想解决所有问题，减少系统数量 | 遍历用图数据库、聚合用列存/图计算引擎；存储与计算分离 |
| 「忽视图的版本与血缘」 | 同一张图两月前后结果不一致 | 图漂移未经记录地传导到下游模型，表现为无法定位的模型漂移 | 图被当成静态资产，没有版本概念 | 图也要版本管理（时间快照、增量更新、图血缘），并记录图构建口径的变更 |

三条最危险的展开：

**「图越大越好」在生产中的暴露方式**：它不以「查不出来」暴露，而以「查出来了但不对」暴露。全公司一张大图之后，两个本来无关的实体因为某条中间边被连上，风控名单里出现业务上完全不相关的实体；团队会先怀疑模型，最后才发现是边定义被合并了。这也是把「图构建」放在数据建模而不是工程细节里的原因。

**「GNN 一定能跑赢 XGBoost」在生产中的暴露方式**：它通常在【经验】三个月后暴露，且暴露形式是「指标没输，但也不值得」。真正的判据不是 GNN 与基线的差距，而是**结构信号本身有多强**：如果只把度数与社区标签喂给梯度提升树就能拿到大部分收益，那么剩下的差距要靠更长的迭代期与更重的推理链路去维护，投入产出比不成立。实践顺序应当是：先跑图特征基线，只有当「关系链路」本身是核心信号（欺诈、社交推荐）时才上 GNN。

**「忽视归纳性」在生产中的暴露方式**：它在冷启动流量上暴露。离线评估用的是训练时已经存在的节点，指标很好看；上线后新用户与新内容因为不在训练图里而拿不到嵌入，被统一打到默认分。判定方法很简单：评估集必须按时间切分（用过去预测未来），并单独统计新节点占比与这部分的表现。

### 3.6 规模跃迁时模式何时该换

下表阈值为【经验】量级，用于判断「什么时候该换」，不是硬性分界。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 节点 < 100 万 → 100 万–1 亿 | 全图训练 + 全邻域聚合 | 【推算】全邻域聚合（不做采样，取满整层邻居）的显存占用随**平均度**与层数指数增长（平均度 d、K 层时每层要展开 d 倍），单机放不下 | GraphSAGE / PinSage 一类邻居采样 + 子图采样 | 采样引入方差，训练更不稳，需要调 fanout 与采样轮数 |
| 100 万–1 亿 → 1 亿以上 | 单机采样训练 | 单机显存与通信成为瓶颈，即使采样后仍放不下 | 分布式图训练（多机参数服务器 / 图分区） | 引入跨分区通信与切边，图分区策略本身是一个新问题 |
| 1 亿 → 10 亿以上 | 通用分布式框架 | 通用框架的分区与通信开销占比过高 | 面向图的分布式引擎或工业自研 | 迁移与运维成本高，且需要团队自建监控与调优能力 |
| 静态图 → 频繁增量 | 定期全量重建 | 全量重建周期赶不上边的产生速度，模型输入长期落后 | 增量更新 + 时间快照 + 图血缘 | 要维护多版本图与重放能力，存储成本上升 |
| 单任务 → 多任务多业务 | 每个任务从零训练 | 重复投入，且各任务口径互不可比 | 预训练骨干 + 下游微调（模式 G） | 骨干更新会波及所有下游任务，需要统一回归验证 |
| 内部可解释 → 对外举证 | 模型打分 + 事后解释 | 举证要求逐条证据链，事后解释接不住 | 路径推理 + 子图证据作为一等输出 | 查询成本上升，必须处理超级节点与路径爆炸 |

### 3.7 自检清单

- [ ] 图里的每一条边，是否都能说出它的语义、口径与生命周期？说不出即违反图构建纪律。
- [ ] 评估集是否按时间切分，且单独统计了新节点（训练时不存在）上的表现？
- [ ] 是否跑过「图特征 + 梯度提升树」基线？没有基线就上 GNN 等于没有对照。
- [ ] 采样 fanout 与层数是否写进了实验记录？【推算】fanout^层数 决定了单节点采样量的量级。
- [ ] 邻居采样是否去重？不去重时同一邻居会被重复计数，等价于给热门节点加权。
- [ ] 是否识别过超级节点（度数远超均值的节点）？未处理时路径与聚合都会退化成无区分度。
- [ ] 异构图里选了几条元路径？每一条对应的业务语义能否一句话讲清？
- [ ] 需要解释的场景，输出的是「分数」还是「路径/子图」？只输出分数就不能进入需要举证的流程。
- [ ] 图上是否存在敏感属性直接作为节点特征？存在即违反公平性纪律。
- [ ] 图查询是不是由 LLM 生成？生成结果是否经过语法校验与结果集校验？
- [ ] 聚合型查询是否被放到了图数据库上执行？是则该挪到列存或图计算引擎。
- [ ] 图是否有版本与最后更新时间？没有时间戳的图无法解释下游模型漂移。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 标签稀疏、关系带信号、新节点持续产生 | A 节点分类（归纳式） | 邻居采样聚合使模型能对训练时未见过的节点直接打分 |
| 只需要给出候选 | B 链接预测 | 打分函数可微，能把「边是否存在」变成可排序问题 |
| 结论必须可举证 | C 路径推理 | 输出单元是路径本身，人工可逐条复核 |
| 信号存在于实体集合的整体形状 | D 子图匹配 / 子图分类 | 建模单元与业务单元对齐，标签可按整体给 |
| 多类实体、边语义不可混同 | E 异构图 + 元路径 | 元路径把语义显式化，可做消融定位哪类信号有效 |
| 答案需要跨片段多跳串联 | F GraphRAG | 多一条「沿关系可达」的检索通路，不依赖语义巧合 |
| 下游任务多、标签少 | G 图基础模型 | 把「每任务一次训练」换成「一次预训练 + 多次微调」 |

> 本节小结：决定模式选择的唯一那条约束是**「信号在图上存在的最小单位是什么」**——单个节点的邻域、一条边、一组实体的形状、还是一张图本身；最小单位定下来，模式基本就定了，业务场景的名字只是它的外衣。在这条约束之外，真正决定能不能落地的是两件事：**新实体在训练时是否已经存在**（决定归纳式还是转导式），以及**你打算拿什么当第一版基线**（图特征基线没跑过就上 GNN，是本节记录的最高频失效）。
