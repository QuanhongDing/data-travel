## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表在同一把 1–5 分的尺子上量十件事：自助门槛、灵活性、多轮精修、工具调用、自主决策、业务理解、数据安全、可观测、工程门槛、工具成熟度。表里的数没有写错，但它把**性质完全不同、且没有换算率**的东西压成了同一个数。看「工程门槛」与「数据安全」两个维度：传统 BI 是 2 分与 5 分，Data Agent 是 3 分与 4 分。工程门槛低说的是「上线它要几个人」——这是可购买的成本；数据安全弱说的是「越权取数一次会造成什么」——这是不可逆的风险。一张表把它们并列，读者会自然地把两者相加，而**「多招一个人」与「泄露一次」之间不存在汇率**。

第二个问题是维度不在同一层。自助门槛、灵活性属于**入口形态**；工具调用、自主决策、多轮精修属于**能力上限**；数据安全、可观测属于**治理成本**。入口形态可以随时替换（换一个前端），能力上限由模型与编排决定，治理成本由权限与审计体系决定——三者可以同时存在、也可以单独缺失。把它们排成一行打分，等于把「你该换前端」和「你该建审计」这两件完全不同的事压成一个「总分落后几分」。

第三个、也是最关键的问题：**打分表藏起了这个主题唯一的真正变量——准确率**，而准确率不是候选的属性，是「任务 × 约束」的函数。同一批模型在三个公开基准上的差距就是这条机制的公开证据：WikiSQL（2017）把答案约束在单表，Spider（2018）要求跨表跨库，BIRD-SQL（2023）进一步引入外部知识提示与更贴近真实的大库——同一个模型在三个榜上的执行准确率逐级下降，Spider 1.0 的头部长期在 80%–90% 量级，而 BIRD-SQL 论文里当时最强的通用模型在 46% 上下，此后榜单头部才上移到 70% 量级【公开，各基准论文与官方榜单，2017 / 2018 / 2023 起，具体数值以榜单当前版本为准】。同一件事在「封闭问题集 + 小库」与「开放问题 + 大库」下的执行准确率差距可以拉到几十个百分点，而打分表把这个变量藏进了一个常量里。

第四个问题是它暗示这些候选**互斥**，只能选一个。真实系统的形态是叠加：一个组织完全可以保留 BI 做深度分析与出图、给业务开一个 ChatBI 入口处理封闭问题、再让 Data Agent 承接长尾与归因，三者共用同一套语义层与权限模型。一旦接受「可以叠加」，比较的对象就从「哪个总分高」变成「每一条链路各自承接哪一类问题、它们的口径从哪里来」——这也正是本节把候选分成三族（7.2）而不是排成一行的原因。

所以本节保留一种排序：**在给定处境下按判据逐条排除**（7.5 决策树），而不是给候选算总分。本主题的判据必须能回答「在我的约束下会怎样」，不能是「好 / 快 / 灵活」这类形容词。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 能力边界 | 遇到未定义的指标、未授权的字段，它是拒答还是猜一个 | 自然语言取数最危险的失败是「悄悄算错」而不是报错；能否拒答比覆盖率更决定信任（[§6](01-data-agent-section-6-sec6.md) 的「宁可不答」） |
| 成本结构 | 成本随什么增长：席位、问次、扫描量，还是口径数量 | 各族候选的计费维度不同（按人 / 按问 / 按治理资产），规模一变，主导项就换人（7.4） |
| 机制契合度 | 我的指标口径与权限是否已被结构化成机器可读 | 它决定准确率上限：模型只负责映射，口径只有组织自己知道（[§6](01-data-agent-section-6-sec6.md) 的结论） |
| 运维复杂度 | 要不要长期供养语义层、模板集、沙箱与审计 | 语义层与模板集都是需要 Owner 的长期资产，不是上线即完成的一次性工作 |
| 生态与锁定 | 语义定义、评测集、提示词能不能带走 | 口径资产一旦长在某家产品的私有模型里，换供应商就等于把口径重做一遍 |
| 演进风险 | 模型换代时，我的资产里哪一部分会失效 | 提示词与微调随模型版本失效，语义定义与评测集不会——这决定了力气该投在哪一侧 |

判据之间有一条隐含顺序：**前两条决定要不要上，中间两条决定上到什么程度，后两条决定投在哪一侧。**顺序颠倒，就会在结构还没定的时候先讨论供应商与产品选型。

### 7.2 候选方案全景

下表覆盖本章讨论的全部候选。**打分列被替换为「核心机制」列**——机制相同则表现必然相同，机制不同则分数无意义。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 成本结构 |
| --- | --- | --- | --- | --- |
| 传统 BI（Tableau / Power BI） | 专家模式的分析与看板 | 查询由人显式表达（拖拽 / SQL），工具只负责计算与呈现 | 已有稳定数仓、使用者会 SQL 的组织 | 商业许可，按席位（7.4） |
| ChatBI / NL2BI（QuickBI / ThoughtSpot / 网易有数） | 面向封闭高频问题的自然语言入口 | 自然语言 → 预定义查询模板或语义模型的**映射**，不自由生成 | 问题清单稳定的业务线 | 商业许可 + 模板建设与回归成本 |
| Copilot（Excel Copilot / Microsoft 365 Copilot / Tableau GPT 一类） | 在既有办公界面里就地辅助 | 补全与建议嵌在用户已在用的工具里，交互场景不变 | 交付物以 Office 文件为主的场景 | 商业许可，通常并入办公套件订阅（[§6](01-data-agent-section-6-sec6.md) 的微软案例） |
| 裸 Text2SQL（基座模型 + Prompt；DIN-SQL / MAC-SQL / CHESS 一类公开方案） | 直接由模型生成 SQL | LLM 对整个 schema 自由生成，执行反馈可选 | 技术团队内部、单库小场景 | 开源或按 token 计费；无治理层 |
| Data Agent（ReAct + Reflexion + 沙箱 + 语义层） | 企业级自助分析入口 | 语义层收窄生成空间 + 沙箱执行 + 多轮精修 | 中大型企业、口径治理诉求强的组织 | 自建（LangChain / LangGraph）或商业产品 |
| Code Interpreter（ChatGPT Code Interpreter / Advanced Data Analysis、E2B 一类） | 面向文件与计算的隔离沙箱 | 用写代码的方式算，而不是查库 | 分析师个人、数据科学探索 | 商业订阅或开源运行时 |
| Multi-Agent Data Analyst | 面向复杂归因的编排 | 按职责拆成路由 / 选表 / 生成 / 校验 / 执行 / 解读多个 Agent | 平台团队、复杂业务闭环 | 自建；成本随每次问数的调用次数上升 |
| RAG 问答（向量检索 + LLM） | 非结构化知识的问答 | 检索片段拼接后生成，不产生精确聚合 | 制度 / 文档类问答 | 自建或云产品；与前三族正交 |

这八个候选分三**族**，先分族再选能省掉一半比较。**预定义查询面族**（传统 BI、ChatBI、Copilot）的差别只在入口形态，共同前提是「访问模式可以事先被表达」；**开放生成面族**（裸 Text2SQL、Data Agent、Code Interpreter、Multi-Agent）的差别在**生成空间被约束到哪一层**——不约束、约束到语义层、约束到代码（Multi-Agent 并不新增一层约束，它是把同一条链路按职责拆开，好定位、好中断）；**非结构化族**（RAG）不解决聚合与口径问题，与前两族是互补而非竞争关系。

分族的操作结论只有一句：**选族只看一个问题——你要回答的问题能不能事先枚举。**能枚举，预定义族的成本最低、准确率最稳、可解释性最好；不能枚举，才进入开放生成族，并立刻面对「生成空间约束在哪一层」这个第二问（7.3.2）。这一条也是 7.5 决策树 Q2 的判据来源。

本表列出四列候选——传统 BI（Tableau / Power BI）、ChatBI / NL2BI（QuickBI / ThoughtSpot）、Copilot（Excel Copilot / Office Copilot）与 Data Agent，以及具名产品（OneMetric、RAG / GraphRAG、BI 工具、Python 沙箱 / Code Interpreter、Multi-Agent 协同），并增补了四个候选：裸 Text2SQL、Code Interpreter、Multi-Agent Data Analyst、RAG 问答。增补的理由是——**把 Python 沙箱、Multi-Agent 与 RAG / GraphRAG 留在「组合」而不放进「候选」，会让 7.3 的机制比较缺对象**：只有把它们当作独立候选，才能看出「用代码算」与「生成 SQL」在纠错信号上的差别。

关于最后一行（RAG 问答）需要单独说明：它**不是本章候选的替代品**。RAG 擅长「文本里有没有写」这类问题，无法回答「本月 GMV 是多少」——后者需要聚合与口径，而这两件事只能由 SQL 侧的语义层提供。把它列进候选表，是为了让 7.5 的 Q6 有落点：当同一批问题里两类同时出现时，缺的不是更强的候选，而是一次**可观测的意图分流**。

### 7.3 机制差异：为什么它们表现不同（核心节）

以下四个机制维度覆盖了全部候选，也是「为什么它们表现不同」的全部原因。每个维度给出机制定义、各候选的实现差异、由机制必然导出的性质（写成「因为 A，所以 B，代价是 C」）以及失效条件。

四个维度的顺序不是任意的：7.3.1 决定「能问什么」，7.3.2 决定「凭什么算对」，7.3.3 决定「谁有权读」，7.3.4 决定「错了能不能自己发现」。前两个维度决定能力上限，后两个决定这套能力能不能进生产。

这四维也提供了一条快速否定法：**如果一个候选在前两维表现很好而在后两维全落空，它就是一个「安全的聊天框」**——能说出不少看起来合理的话，但你不敢把它的输出写进任何需要签字的材料。反过来，一个候选在后两维很强而前两维落空，它是一套治理良好的窄工具，只适合它覆盖的那一小类问题。**生产可用的组合，是四个维度都至少不落空；而绝大多数失败项目，是把前两维的演示效果当成了四个维度的总分。**

#### 7.3.1 查询面：封闭映射还是开放生成

**机制是什么**：自然语言与可执行查询之间的关系，是「映射到一个有限集合」，还是「在无限空间里生成一个」。这决定了准确率的**上限形式**，而不只是上限高低。

**各候选的实现差异**：

| 候选 | 生成空间 | 谁保证它正确 | 超出边界时的典型失败形态 |
| --- | --- | --- | --- |
| 传统 BI | 无自然语言：查询由人写 | 人 | 写错即写错，但错误可见、可复核 |
| ChatBI | 有限模板集合 | 模板作者 | 明确回「不支持」，或错配到最接近的模板 |
| Copilot | 当前文件 / 工作簿的上下文 | 用户 | 数据不在当前上下文里就答不上 |
| 裸 Text2SQL | 整个 schema 的自由组合 | 无 | 语法正确、语义错误，**静默** |
| Data Agent | 语义层声明的指标与维度集合 | 语义层（未声明即拒绝） | 明确拒答（这是特性，不是缺陷） |

**由此必然导出的性质**：因为 ChatBI 把问题映射到**有限模板集合**，所以在集合覆盖内它是确定性映射——没有生成误差、结果可解释、单次成本近乎固定；代价是覆盖面与准确率不能同时涨：每加一个模板，歧义匹配的风险上升一点，模板的回归测试量也上升一点。这就是「**问题集合封闭且高频时，ChatBI 优于 Data Agent**」的机制原因——不是 ChatBI 更聪明，而是它把不确定性换成了确定性。反过来，因为开放生成面**没有封闭集合**，所以它的覆盖面没有上限，但错误率也没有天然的上限，只能靠 7.3.2 的约束与 7.3.4 的纠错来压。

**公开证据**：三个基准的任务设定差异本身就是这条机制的公开证据（WikiSQL 2017 约束在单表、Spider 2018 跨表跨库、BIRD-SQL 2023 引入外部知识与大库）【公开，2017 / 2018 / 2023，可按题名核验】；「自然语言 → 指标语义层 → SQL」而非「自然语言 → SQL」是本章 [§6](01-data-agent-section-6-sec6.md) 四个案例的共同做法【公开，各案例的公开材料见 §6 原始引注，2020–2024】。

**失效条件**：当问题集合每天都有新问法时，模板路线失效——但失效的表现不是报错，而是「把新问题错配到旧模板上给一个看起来合理的答案」，比明确失败更危险。判断方法：统计配到模板但用户当场否定的比例，这个比例持续上升即说明集合已经不封闭。

这一维度上还有两处容易被忽略的对照。**传统 BI 与 Copilot 的优势不来自「更聪明」，而来自「不确定性的位置不同」**：BI 把不确定性留给写查询的人（人写错，人自己知道），Copilot 把不确定性留在当前文件的上下文里（数据不在上下文里就够不着）——两者都没有「生成一个看起来对的答案」这个失败模式。**这正是它们在「能力强弱」上看起来落后、却在生产里活得久的原因。**

#### 7.3.2 生成空间的约束：裸 schema 还是语义层

**机制是什么**：把 SQL 的搜索空间从「整个 schema」收窄到「已声明的指标与维度」。它改变的不是模型的水平，而是**容错的对象**。

**各候选的实现差异**：

| 候选 | 约束来源 | 未命中时的行为 | 准确率上限由谁决定 |
| --- | --- | --- | --- |
| 裸 Text2SQL | 无 | 生成一个看起来合理的 SQL | 模型的 schema 理解能力 + 库规模 |
| ChatBI | 模板集合 | 映射到最近的模板 | 模板覆盖度（人力线性投入） |
| Data Agent | 指标定义（口径 / 维度 / 粒度 / 过滤 / Owner） | 明确拒答 | **语义完备度**（组织资产，一次性 + 长期维护） |
| Code Interpreter | 无（代码层自由） | 算出一个数 | 用户能否核对自己的输入 |

**由此必然导出的性质**：因为约束把「生成」变成「映射」，所以错误形态从**静默算错**变成**显式拒答**——这是可治理的根本：拒答可被统计、可被补语义，静默错不可发现也无法度量。代价是能力上限被语义层锁死：**语义层没覆盖的问题，Agent 一定答不了**，而此时的它比裸 Text2SQL 更「无能」——后者至少会给出一个数（尽管可能是错的）。所以「先建语义层再开自然语言入口」不是谨慎偏好，而是**主动把失败模式换成可管理的那个**。这也解释了 [§6](01-data-agent-section-6-sec6.md) 为什么把「语义完备度」当成上线前置条件而不是上线后的优化项。

**公开证据**：语义层作为独立的消费接口在 2023 年起成为一类明确产品形态——dbt Semantic Layer 于 2023 年推出、Cube 以 Headless BI 形式提供语义 API（主文件 [§2.3](01-data-agent.md) 已列）【公开，2023，可按产品文档核验】；「语义层前置、模型只做映射」是 [§6](01-data-agent-section-6-sec6.md) 四个案例的共同做法【公开，各案例的公开材料见 §6 原始引注，2020–2024】。

**失效条件**：语义层的维护若没有 Owner 与版本控制，一次口径改动会同时改变所有消费端的结果——集中化的收益与它的爆炸半径来自同一个机制。判断方法：问「谁有权改这个指标定义、改完谁被通知」，答不上来即是一条无主口径。

#### 7.3.3 执行边界：会话身份决定权限必须前移

**机制是什么**：自然语言入口把「谁能读什么」的判定，从人写 SQL 时的自觉，改成**会话身份到数据策略的匹配**。执行者从一个（人）变成了两个（人 + Agent）。

**各候选的实现差异**：

| 候选 | 取数身份 | 越权在哪一步被拦 | 审计粒度 |
| --- | --- | --- | --- |
| 传统 BI | 人（BI 账号 + 行级权限） | 查询时由 BI 权限模型拦 | 报表级 |
| ChatBI | 人的身份穿透到语义模型 | 由语义模型的权限定义拦 | 问题级 |
| Copilot | 人的身份 + 文件 / 租户权限 | 由文件与租户权限拦 | 文件级 |
| 裸 Text2SQL | 常复用人的库账号 | 常常没有这一步 | 无 |
| Data Agent | **Agent 独立只读身份** + 继承人的数据范围 | 执行前（沙箱 + 行级权限 + 限额） | 提问 / SQL / 结果三级 |

**由此必然导出的性质**：因为执行者多了 Agent 这一方，所以权限判断必须发生在 SQL 执行**之前**，且必须能区分「人问的」与「Agent 代问的」；否则越权在审计里不可归因——分不出是谁取走的，而**不可归因的越权就是破坏上限**（同一条结论在趋势章的 AI 治理一节里从治理角度写过一遍：模型可以**请求**工具，但没有权限直接**执行**）。代价是要为 Agent 建独立身份体系、配额与脱敏规则，并接受「权限被拒」是一条**正常返回路径**而不是异常；否则下游会把拒绝当故障重试，绕过权限的压力会反过来逼团队放权。

**公开证据**：把企业级权限与审计做成产品的一等能力，是 [§6](01-data-agent-section-6-sec6.md) 微软案例的核心做法【公开，微软公开材料，2021–2024】；只读账号 + 查询超时 + 返回行数限制 + 敏感列脱敏是主文件 [§2.3](01-data-agent.md) 列出的沙箱公开做法【经验】。

**失效条件**：当业务要求 Agent 做写操作（回填、打标、触发下游）时，「只读沙箱」这条边界不再成立——此时正确动作是走 Human-in-the-Loop（[§3.2.5](01-data-agent-section-3-sec3.md)），而不是把沙箱放宽。放宽沙箱同时也放弃了上面全部审计粒度的价值。

这一维度上有一处**内在张力**必须提前接受：脱敏与可解释性是反向的。为了让结果可被核对，Agent 要展示取到的字段与原始值；而敏感列一旦脱敏，核对就失去了对象——被去掉的那部分恰恰是排查时要看的。常见的折中是分级展示（聚合结果可见、明细按权限下钻），代价是「核对」这件事本身变成一次受权限约束的动作，而不是随手可做。**先想清谁能看到哪一级，再决定展示形态；反过来做，通常会在第一次合规审查时全部返工。**

#### 7.3.4 纠错信号：SQL 是少数有真值信号的 Agent 场景

**机制是什么**：自我纠错依赖反馈信号的质量。SQL 恰好可以给出**机器可客观判定的反馈**，这是它与其他 Agent 场景最大的机制差别。

**各候选的实现差异**：

| 候选 | 可用反馈信号 | 信号强度 | 每轮纠错付出的代价 |
| --- | --- | --- | --- |
| 裸 Text2SQL（无执行环节） | 无 | 无 | 只能重生成，等于再猜一次 |
| 裸 Text2SQL（带执行） | 执行错误、结果形状 | 中：语法可判，语义不可判 | 一次生成 + 一次执行 |
| Data Agent | 执行错误 + 结果形状 + Explain 计划 + 口径校验（行数 / 范围 / 非负） | **强：部分可客观判定** | 一次生成 + 一次执行 + 一次解读 |
| ChatBI | 模板不匹配 | 弱：只能换模板 | 人工介入 |
| Code Interpreter | 代码异常 + 自定义断言 | 强：断言由用户或 Agent 写 | 一次代码执行 |

**由此必然导出的性质**：因为 SQL 的正确性可以被执行器**部分客观判定**（语法、类型、空结果、行数异常、口径约束如「GMV 不可能为负」），所以 Data Agent 的自我纠错是少数「有真值信号」的闭环，不依赖模型给自己打分；代价是每轮纠错都要再付一次 LLM 调用与一次查询扫描——**延迟与成本随迭代次数线性增长**，因此必须给迭代次数封顶，并显式处理「反复生成同一个错误 SQL」的循环（[§3.2.3](01-data-agent-section-3-sec3.md) 已把这条列为缺点）。对照之下，开放问答式 Agent 没有真值信号，只能靠模型自评，纠错接近掷硬币——这是「Data Agent 比一般 Agent 更早进入生产」的机制原因，而不是它更时髦。

**公开证据**：Reflexion 的公开表述即把外部反馈作为修正信号（Shinn 等，2023）【公开，2023，可按论文核验】；DIN-SQL（2023）、MAC-SQL（2024）、CHESS（2024）一类公开方案都把「校验 + 重写」放进链路【公开，2023 / 2024，可按题名核验】。

**失效条件**：当错误是**口径理解错**而不是 SQL 写错时（用户说的「活跃」与语义层里的「活跃」不是同一件事），执行反馈是通的、结果也非空，但答案仍然错——这类错误自纠不出来，只能靠歧义澄清（[§6](01-data-agent-section-6-sec6.md) 的「遇歧义必须向用户澄清」）。判断方法：把「正确答案 + 空结果 + 有结果但口径不符」分开统计，第三类不会被任何自动纠错覆盖。

纠错这一维度还要配两个工程参数，否则优势会变成账单。**一是迭代上限**：循环必须有硬上限（常见的做法是 2–3 轮，属于实践口径而非测量值【经验】），并且上限的判定要落在「这一轮与上一轮的 SQL 是否实质相同」上，而不是单纯计次——[§3.2.3](01-data-agent-section-3-sec3.md) 已把「反复生成同样的错误 SQL」列为该模式的固有缺点，只按次数封顶会让它在限额内空转。**二是把纠错做成可观测指标**：每轮纠错的触发原因（语法 / 权限 / 空结果 / 口径校验）要分开统计，因为只有「口径校验」那一类能反映出语义层的缺口，而它恰好是能通过补语义永久消除的一类。

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本不是产品报价，而是五项随规模变化的量之和：

```
总成本 ≈ 固定投入（平台 + 语义层建设） + f(席位数)
        + g(问次数 × 单次 token 量) + h(扫描量 × 查询频次) + i(口径数 × 消费端数)
```

各候选的差别不在总量，而在**哪一项是主导项**、哪一项是上线时看不见的：

| 候选 | 主导项 | 隐性成本（上线时不计入、一年后计入） | 什么条件下反转 |
| --- | --- | --- | --- |
| 传统 BI | f 席位 | 每个看板各算一次口径，形成看板级技术债 | 使用者规模小且问题集合稳定时最省 |
| ChatBI | 模板建设与回归（随预设问题数线性） | 模板集合成为第二套口径来源 | 问题集合封闭且高频时最优（7.3.1） |
| Copilot | f 席位（通常并入办公套件） | 能力被限制在「当前文件 / 工作簿」的上下文里，数据治理进不来 | 交付物本身就是 Office 文件时最省 |
| 裸 Text2SQL | g 问次 | 静默算错的代价：没有治理层可归因 | 单库、技术用户、结果可人工复核时可用 |
| Data Agent | i（口径数 × 消费端数）+ g | 语义层成为取数链路单点；越权与注入的破坏上限 | 问题不可枚举且口径必须统一时 |
| Code Interpreter | 会话级沙箱 + g | 产物（脚本）不可复现，则答案不可追溯 | 一次性探索、无需沉淀口径 |
| Multi-Agent | g（每次问数多次调用，随 Agent 数放大） | 链路长导致出错定位难，成本随节点数上升 | 归因这类必须拆步的问题 |
| RAG 问答 | 索引与向量库的常驻维护（随语料量增长）+ g（检索片段放大输入 token） | 索引新鲜度与切分策略一变，召回分布整体漂移，答案变差但不报错；换 embedding 模型要全量重建索引 | 问题以精确聚合为主时它替代不了 SQL，只能做旁路 |

四项【推算】示例，推导链全部写出，读者可按自己的规模替换参数重算：

**算例 1 · 单次问数的 LLM 成本**：假设单次问数触发 4 次调用（澄清意图 / 选表改写 / 生成 SQL / 解读结果），每次输入 8k tokens、输出 1k tokens ⇒ 输入 32k tokens = 0.032 M，输出 4k tokens = 0.004 M。按主流商用模型公开价目上常见的区间 $0.15–$15 / M 输入 token、输出单价约为输入的 4 倍（即 $0.6–$60 / M）【公开，厂商价目页，2024 年前后，请以当前价目页为准】⇒ 输入 $0.005–$0.48、输出 $0.002–$0.24，合计 **约 $0.01–$0.7 / 次，跨约两个数量级**【推算：0.032 × 0.15 = $0.005，0.032 × 15 = $0.48；0.004 × 0.6 = $0.002，0.004 × 60 = $0.24】。换算成年：1,000 问/天 ⇒ 约 $7–$720 / 天 ⇒ **$2.6k–$260k / 年**【推算：0.0072 × 1000 × 365 ≈ $2.6k；0.72 × 1000 × 365 ≈ $263k】。两个数量级的差距主要来自**模型档次选择**，而不是问次数——所以模型选型是成本的第一杠杆，缓存命中率（重复问题、重复的 schema 与语义前缀）是第二杠杆。

**算例 2 · 席位成本的对照**：传统 BI / ChatBI 一类按席位计价。按公开挂牌价 $10–$75 / 席 / 月的区间（Power BI 与 Tableau 一类工具的公开价目）【公开，厂商价目页，2024 年前后，请以当前价目页为准】⇒ 1,000 席 = **$120k–$900k / 年**【推算：$10 × 1000 × 12 = $120k；$75 × 1000 × 12 = $900k】。这个量级高于算例 1 的 LLM 变动成本上界，但两者**不是替代关系**：Data Agent 省不下席位（分析师仍需要用 BI 做深度分析与出图，见 7.6 组合 3），它省下的是「等排期」的时间。所以选型第一问不是「哪个便宜」，而是「我的成本里哪一项会先变大」。

**算例 3 · 语义层是人力资产，不是存储资产**：若一个组织有 200 个核心指标，每个指标的首次登记（名称 / 口径 / 维度 / 时间粒度 / Owner / 同义说法）按 0.5 人日计，一次覆盖约 100 人日 ⇒ 半年内约 1 人全职【推算：200 × 0.5 = 100 人日，按每人约 200 人日 / 年计 ≈ 半年人力】；稳态维护按每月有 5%–10% 的指标被触及、每次改动含评审与上下游对账按 0.5–1 人日计，月投入约 5–20 人日 ⇒ **约 0.25–1 人全职当量**【推算：10–20 个指标 / 月 × 0.5–1 人日 = 5–20 人日 / 月，按每月 20 个工作日折算】。这两项都随**指标数与改动频率**线性增长，不随数据量增长——所以「语义层贵不贵」与存储无关，只与「你有多少指标、改得多频繁」有关。

沙箱侧还有一项容易漏算：一次自然语言问数可能触发全表扫描（用户不知道分区键），因此单查询扫描上限、超时与返回行数上限必须有默认值；常见定位是「单查询扫描量在 10^9 行以内、超时 30–60 秒、单次返回 10^4 行以内」，具体取值应按你的数据量与并发确定【经验】。

**算例 4 · 编排层数会把 g 项放大几倍**：沿用算例 1 的单次调用成本，Multi-Agent 形态把一次问数从 4 次调用变成「路由 + 选表 + 生成 + 校验 + 执行 + 解读 + 可视化」的 7 次上下，若其中校验失败再触发一轮，按 8–10 次调用计，则 **g 项是单 Agent 形态的 2–2.5 倍**【推算：8–10 次 ÷ 4 次 = 2–2.5 倍】。它买到的不是准确率，而是**可观测性与可中断性**（每步一个 Agent，出错能定位到哪一步）。所以判据是「这个问题需不需要拆步」，而不是「多 Agent 是不是更先进」——不拆步的简单查询上多智能体只是把成本乘了 2 倍多【经验】。

**成本对比里不该出现的数字**：任何形如「成本降低 63%」「效率提升 3.2 倍」的结论，若没说清问次数、模型档次、扫描量与基线口径，就没有可迁移性。本节的四个算例都把参数写了出来，目的就是让读者能用自己的参数替换后重算一遍。

四个算例指向同一条结论：**这套体系的成本主导项会随规模换人**。小规模时主导项是语义层的一次性建设（**百人日量级**——200 个核心指标约 100 人日【推算，见算例 3】），中规模时是席位与平台运维（十万至百万级年成本【推算，见算例 2】），大规模时是语义与权限的长期维护人力（若干人全职当量）——而 LLM 的变动成本在多数场景里并不是最大项，它是**最容易被误认为最大项的那一项**，因为它最显眼、最容易被单独报价。判断自己处在哪一档，只要问一句：**过去一年，团队的工时主要花在「回答问题」上，还是花在「维护口径与权限」上？**

### 7.5 决策树（每个分支都要有阈值依据）

```
开始：为「让业务用上数据」选入口
├─ Q1 使用者自己会不会写 SQL？
│    ├─ 会，且已有稳定数仓与 BI 资产 → 传统 BI（Tableau / Power BI），不加 Agent
│    └─ 不会 → 进入 Q2
├─ Q2 业务问题的集合是否封闭，且高频问题数 ≤ 50？
│    ├─ 是 → ChatBI（QuickBI / ThoughtSpot 一类）模板映射
│    └─ 否 → 进入 Q3
├─ Q3 主要交付物是不是复杂报表、且使用者以 Office 用户为主？
│    ├─ 是 → Copilot（Excel Copilot / Microsoft 365 Copilot）就地辅助
│    └─ 否 → 进入 Q4
├─ Q4 核心指标的语义（口径 / 维度 / 粒度 / Owner / 同义说法）是否已机器可读？
│    ├─ 否 → 先建指标语义层（OneMetric / dbt Semantic Layer / Cube），暂不开自然语言入口
│    └─ 是 → 进入 Q5
├─ Q5 待回答的问题里，需要多步归因的占多少？
│    ├─ 以单点取数为主 → Data Agent（ReAct + Reflexion + 沙箱）
│    └─ 归因 / 多步为主 → Data Agent + Plan-Execute（复杂时再加 Multi-Agent）
├─ Q6 同一个问题是否同时需要「文档知识」与「结构化数据」？
│    ├─ 是 → Data Agent + RAG（意图分类分流）；GraphRAG 属 L3，仅用于概念解释题，取数不要绕经图谱（§5）
│    └─ 否 → 不加检索链路，避免多一条错误来源
└─ Q7 是否涉及受监管数据或写操作？
     ├─ 涉及 → Human-in-the-Loop（执行前审批）+ Agent 独立只读身份
     └─ 不涉及 → 沙箱 + 行级权限 + 限额即可
```

**阈值依据**（与树上节点一一对应）：

读这棵树的方式是**自上而下**：Q1 决定要不要换入口，Q2 / Q3 决定换哪一种，Q4 是进入开放生成族之前的门槛，Q5 到 Q7 决定编排、检索与审批要加到什么程度。前面的答案不会被后面的答案推翻。

- **Q1**：这条不是阈值而是**结构性判据**——使用者的能力决定了「降低门槛」这件事值多少钱。若用户群本身会写 SQL，Agent 带来的门槛收益接近零，却引入生成误差与新的权限面，此时保留 BI 是更优解。
- **Q2 的「≤ 50」**：依据是模板路线的成本函数（7.4 的 ChatBI 行）。模板的成本项是「每个预设问题一份映射 + 一份回归测试」，按每题 0.5–1 人日计，50 题的首次建设与回归约 25–50 人日，仍能在一个季度内维护完；超过这个量级后，模板的建设与回归成本会超过建一层语义层的一次性投入【经验】——量级请按你自己的回归成本校准。**注意：决定性的不是「50」这个数，而是「问题集合是否封闭」**——集合不封闭时，模板数再多也覆盖不到新问法。
- **Q3**：结构性判据（交付物形态）。Copilot 的能力边界就是当前文件 / 工作簿的上下文（7.3.1），交付物在它边界之外时，它无论多强都够不着。
- **Q4**：结构性判据，同时是**上线前置门槛**。「机器可读」的判定标准沿用 [§6](01-data-agent-section-6-sec6.md) 的 0→1 验收口径（每个核心指标有名称、口径、维度、时间粒度、Owner 与同义说法六项）；**此外本节要求这六项必须进版本控制**。缺项即视为未达标——因为缺的那一项正是 Agent 会猜错的地方。
- **Q5 的「占用多少」**：判定方法是抽样 100 个真实问题，数其中需要三次以上查询或跨维度拆解的比例；超过三成即按归因场景处理，上 Plan-Execute（[§3.3](01-data-agent-section-3-sec3.md) 的适用场景表把归因归给 Plan-Execute 的理由是上下文隔离）【经验】。
- **Q6**：结构性判据（问题是否跨结构化与非结构化两类）。两类混在一个入口时，意图分类本身成为新的错误来源，必须先承认这条错误率并把它做成可观测指标，再决定是否合并入口。
- **Q7**：结构性判据（是否有监管义务或写操作）。它的机制依据是 7.3.3——权限必须在执行前定住，模型只能请求、不能执行；涉及写操作时，只读沙箱的边界不成立，只能加人工审批。

这七个节点里只有 Q2 与 Q5 用了近似阈值，其余五个都是结构性问题（会不会写 SQL、交付物形态、语义是否可读、问题是否跨两类、是否涉及监管或写操作），答案由约束决定，不需要估数。把可判定的问题写成阈值，是决策树最常见的画蛇添足。

树上每个节点的判据都能追到 7.3 的一条机制：Q1、Q2 与 Q3 追到 7.3.1（生成空间是封闭还是开放；Q3 对应 Copilot 的「能力边界止于当前文件 / 工作簿的上下文」），Q4 追到 7.3.2（约束在哪一层决定错误形态），Q7 追到 7.3.3（权限在执行前定住），Q5 追到 7.3.4（多步任务的纠错信号覆盖不到，只能靠拆步换取可中断与可定位），Q6 追到 7.3.1（两类问题混在一个入口，等于引入一种不可判定的生成失败）。**如果某条分支的理由追不到 7.3 的任何一条机制，那它就不是选型判断，而是偏好。**

### 7.6 选型矩阵与组合

矩阵按「场景」而不是「候选」组织——选型的输入是你的处境，不是候选清单。每行的「不选它的原因」都写成机制层面的理由。

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 已有数仓，使用者是分析师 / 数据工程 | 传统 BI（Tableau / Power BI） | ChatBI | 不选 Agent：门槛收益为零，却多一条静默算错的路径与一套 Agent 身份 |
| 问题清单封闭、高频问题 ≤ 50 个 | ChatBI（QuickBI / ThoughtSpot） | Copilot | 不选 Agent：封闭集合上模板是确定性映射，Agent 的生成不确定性只带来风险不带来覆盖 |
| 交付物以 Office 文件为主 | Copilot | 传统 BI | 不选 Agent：能力边界在「当前文件」之外时够不着数据 |
| 人人要查数、口径混乱 | Data Agent + 指标语义层（OneMetric） | ChatBI + 语义层 | 不选裸 Text2SQL：错误形态是静默算错，没有可归因的治理层（7.3.2） |
| 复杂归因、多步拆解 | Data Agent + Plan-Execute | Data Agent + Multi-Agent | 不选单 Agent ReAct：长链路上下文爆炸，拆步后才能中断与重试（[§3.2.1](01-data-agent-section-3-sec3.md)） |
| 知识 + 数据双消费 | Data Agent + RAG（意图分类分流） | 分别建两个入口 | 不选单一入口：意图分类的错误会以「答错来源」的形式出现，且难以归因；GraphRAG 属 L3（§5），只用于概念解释题、不排进排期，取数不要绕经图谱 |
| 受监管数据、或 Agent 要写库 | Data Agent + Human-in-the-Loop | 只读沙箱 + 更严的限额 | 不加审批：写操作下只读沙箱的边界不成立，越权不可归因（7.3.3） |
| 企业级平台、多入口并存 | Data Agent + OneMetric + BI 工具（分层建设） | 单一入口先跑通 | 不一次配齐五层：每层都带来一份需要同步的派生状态（见下方组合代价） |

五条**常见组合**（补齐各自的职责边界与运维代价）：

1. **Data Agent + 指标语义层（OneMetric）**：语义层承担「口径唯一、权限与审计绑在语义上」的职责，Agent 承担「映射与解释」的职责。边界是——**Agent 不新增口径，只消费已声明的指标；未声明即拒答**。运维代价：语义层成为取数链路的单点，必须进版本控制、有 Owner、有变更通知，否则一次口径改动会同时改变所有入口的结果（7.3.2）。这是中大型企业的必选项。
2. **Data Agent + RAG / GraphRAG**：SQL 路径负责结构化取数，RAG / GraphRAG 负责文档与实体关系问答；其中 GraphRAG 属 L3（§5），只用于概念解释题、不排进排期，取数不要绕经图谱。边界是——**两条路径的答案来源必须可区分**（哪个数字来自 SQL、哪句结论来自文档）。运维代价：意图分类本身有错误率，必须把分流准确率做成可观测指标；否则错误会表现为「答非所问」，而排查方向会被引到模型上。
3. **Data Agent + BI 工具**：Agent 做自然语言入口与自助问答，BI 做深度分析与出图。边界是——**同一份口径必须来自同一个语义层**，不允许 BI 侧另算一套。运维代价：两套权限模型要对齐（同一个用户在两个入口必须看到同一份数据），而这在实践中是数据外泄最常见的入口。
4. **Data Agent + Python 沙箱（Code Interpreter）**：SQL 负责取数，Python 负责归因、预测与统计检验。边界是——**写出的脚本要能复现答案**，否则「这个数怎么算出来的」答不上来。运维代价：多一个执行环境要隔离、配额与依赖管理；产物要落盘归档，否则审计时只有结论没有过程。
5. **Data Agent + Multi-Agent 协同**（Data Agent / 业务 Agent / 运营 Agent）：Data Agent 只负责取数与解释，业务与运营 Agent 负责执行动作。边界是——**每个 Agent 独立身份、独立限额，取数权限不随编排传递**。运维代价：链路变长，成本随节点数上升，出错定位要能追到具体一跳（这要求每跳都有 trace 记录，主文件 [§2.1](01-data-agent.md) 已把可观测与调用链追踪列为必备能力）。

五条组合有一个共同的运维代价结构：**每加一层，就多一份需要与上游保持同步的派生状态**（语义定义、检索索引、Python 产物、Agent 身份与限额），而每份派生状态都需要 Owner 与新鲜度监控。这解释了一条常见失败路径——为了「一次解决所有问题」把五层全建起来，结果五份状态各自漂移，比只有一层时更难判断哪个数是对的。**组合的原则是：先建权威层（口径与权限），再按真实出现的消费需求逐层追加。**

组合里有一条容易搞反的次序：**入口形态可以叠加，治理层不能叠加**。多开一个入口（对话、BI、Copilot、嵌入业务系统）只增加使用面，成本是可控的；但每多一套语义定义或权限模型，就多一个「哪个数是对的」的争议来源。所以正确的追加顺序是——先把语义层与权限这一层做厚（它同时服务所有入口），再逐层加入口；反之，先加四个入口、每个入口各带一套映射逻辑，等于人为制造四套口径。这条次序也是 [§6](01-data-agent-section-6-sec6.md) 「嵌入业务方既有工作流」与「复用业务系统既有数据模型」那两条经验的机制解释。

### 7.7 选错的代价与迁移成本

**反模式：先开自然语言入口，后补口径** —— 症状：语义层只覆盖了三成核心指标就上线给业务用。后果：模型对未覆盖的问题不会拒答，而是生成一个语法正确、语义接近的 SQL，错误形态是**静默算错**；信任是一次性资源，被错误答案透支一次就再难恢复。正确的做法：把语义完备度作为上线前置门槛（[§6](01-data-agent-section-6-sec6.md) 的验收口径），并给未登记项一个显式的失败行为——拒绝，而不是猜测。

**反模式：把模板数量当成 ChatBI 的能力指标** —— 症状：为覆盖长尾问题不断加模板，模板从 50 涨到 500。后果：模板的回归成本线性上升，长尾仍然覆盖不到（集合本身不封闭），而模板集合变成**第二套口径来源**——同一个指标在模板 SQL 与语义层里各有一份定义。正确的做法：把模板限制在封闭高频集内（Q2 的判据），长尾交给语义层 + Agent；并定期统计「配到模板但被用户当场否定」的比例，它上升即说明集合已经不封闭。

**反模式：给 Agent 复用人的人的数据库账号** —— 症状：为了省事，Agent 直接用某个人的库账号连接。后果：审计里分不出取数是人做的还是 Agent 做的，越权不可归因；同时因为账号本身拥有写权限，注入或误操作的破坏上限由模型行为决定，而不是由策略决定。正确的做法：Agent 独立只读身份 + 行级权限 + 扫描与返回行数限额，并把「权限被拒」实现为正常返回（7.3.3）。

**反模式：用「准确率」作为唯一验收指标** —— 症状：只统计答对的比例，把「正确拒答的未定义问题」也计入失败。后果：团队的最优策略变成教会模型去猜，静默算错的比例上升，而报表上的准确率反而更好看。正确的做法：把结果分成三类分别统计——**答对 / 正确拒答 / 有结果但口径不符**；第三类必须趋近于零，它才是这套系统能不能进生产的判据（7.3.4 的失效条件）。

**反模式：为演示选型，为生产返工** —— 症状：为了让第一场演示好看，选一个「什么都答得上来」的配置——关掉拒答、放开权限、不加限额、只测准备好的十个问题。后果：演示通过、生产翻车，返工的不是模型而是外围（语义层、权限、限额、审计），而这四样恰好是最慢的。正确的做法：把演示环境按生产配置搭（拒答打开、权限收窄、限额生效），在演示里**主动展示一次拒答与一次权限被拒**——这两个动作能做完，才说明治理层是真的，而不是演示脚本的一部分。

**换成另一个要动什么**：

| 迁移 | 数据与资产 | 查询与入口改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 传统 BI → ChatBI | 小（复用既有模型） | 大（每个高频问题要建一份模板与回归） | 中（模板版本与回归流程） | 中（从拖拽思维换成「先想清问题」） |
| ChatBI → Data Agent | 中（模板集合要迁成语义层） | 大（映射逻辑从模板改为语义层驱动） | 大（新增沙箱、Agent 身份、审计） | 大（从「配模板」换成「维护语义」） |
| 裸 Text2SQL → Data Agent | 大（要把口径补齐成机器可读语义层） | 中（生成逻辑从自由生成改为受约束生成） | 大（沙箱 + 权限 + 可观测） | 大 |
| Data Agent 换模型 / 供应商 | 中（语义定义与评测集要能导出，否则等于重做） | 中（提示词与工具描述几乎都要重调） | 小 | 中（评测口径要重建基线） |
| Copilot → Data Agent | 小 | 大（入口从文件内换成对话，交付物形态要重定） | 大 | 大（用户要学新的提问方式与核验方式） |

这张表里最容易被低估的一格是「**Data Agent 换模型 / 供应商**」的「数据与资产」列：如果语义定义长在产品私有的模型里、评测集没有沉淀，换供应商时这两样都带不走，而它们恰好是准确率的两个来源。**迁移的通用原则只有一条：先让新旧两条链路并行跑一段，用同一批问题对比三类结果（答对 / 正确拒答 / 静默算错），确认没变差再切消费端**——取数链路的正确性不能靠单测证明，只能靠对账。

还有一条迁移成本的规律值得单独说明：**在五条迁移路径里，越靠上游的那一项越贵**。「数据与资产」这一列在 ChatBI → Data Agent 与裸 Text2SQL → Data Agent 两行都是「大」或「中」偏大，因为它要求把散落在 SQL、模板、报表与人脑里的口径补齐成机器可读的定义；而越靠下游的「运维重建」「团队再学习」虽然工作量大，却是一次性的、可以按迭代推进。**所有把顺序做反的团队，都是先动了入口（下游），后来才发现真正的工作量在上游。**

### 7.8 小结

下表把 7.5 的决策树压成六行，只保留「处境 → 建议 → 机制理由」。读法是先找到与你最接近的一行，再回看它对应的 7.3 小节确认理由是否成立。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 使用者会 SQL、已有 BI 资产 | 传统 BI，不加 Agent | 门槛收益为零，却引入生成误差与新的权限面 |
| 问题集合封闭、高频问题少 | ChatBI 模板映射 | 有限集合上的确定性映射，无生成误差、成本固定 |
| 交付物以 Office 文件为主 | Copilot | 它的能力边界等于当前文件的上下文 |
| 人人要查数、口径混乱 | Data Agent + 语义层 | 把错误形态从静默算错换成显式拒答，可统计、可补全 |
| 复杂归因、多步分析 | Data Agent + Plan-Execute（+ Multi-Agent） | 拆步后上下文隔离，可中断、可重试、可定位 |
| 受监管数据或要写库 | Data Agent + Human-in-the-Loop | 权限须在执行前定住；只读沙箱边界的破法只有审批 |

还有一种处境值得单列：**已经上了 ChatBI 或裸 Text2SQL，答不准**。此时第一步不是比较候选优劣，而是把痛点归到 7.3 的哪一个机制上——若是「超出模板就乱答」，问题在 7.3.1；若是「答得通顺但是错的」，问题在 7.3.2 的语义覆盖；若是「不该让人看到的数被看到了」，问题在 7.3.3。**痛点归错了类，换方案只会把成本从一个账户挪到另一个账户。**

最后一条给做预算的人：这套体系的投入顺序与它的收益顺序是相反的。**收益**出现在最外层（业务自助、少等排期），人人看得见；**成本**压在最内层（口径定义、权限模型、评测集），只有做的人知道。所以它天然会在每一个预算季被排到最后。可行的做法是把内层的进度做成对外可见的指标——「核心指标口径覆盖率」「未登记问题的拒答率与补全率」「越权在结构上不可绕过」——让内层工作有验收物，而不是等到出事故才被承认。

> 本节小结：这一组候选里**唯一真正起决定作用的差异**是「生成空间被约束在哪一层」——不约束（裸 Text2SQL）、约束到有限模板（ChatBI）、约束到已声明的语义（Data Agent + 语义层）、约束到代码（Code Interpreter）。它同时决定了准确率的上限形式、错误的表现形态（静默错还是显式拒答）、以及治理成本落在谁身上；其余维度（自助门槛、多轮精修、工具成熟度）都是这条差异的下游表现。所以选型的第一问不是「哪个更强」，而是「**我能不能把要回答的问题事先枚举或事先声明**」——能，就用确定性的方案（BI / ChatBI）；不能，就必须建语义层，并把「拒答」做成产品行为而不是缺陷。
>
> 💡 **思考锚点**：把你团队上个季度的取数请求按「能不能事先枚举」过一遍——相同或近义问法反复出现的占几成，每次都得新写一条 SQL 的长尾又占几成？如果反复出现的那部分能收进 7.5 决策树 Q2 的「高频问题 ≤ 50」门槛以内，你会让它走模板映射、把长尾另开一个开放生成入口，还是宁可先补 7.3.2 的语义层、让两条链路共用同一套口径？
