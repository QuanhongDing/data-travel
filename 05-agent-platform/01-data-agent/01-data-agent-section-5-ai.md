## 5. 前沿演进（AI 时代）

> 原 § 5 共 154 行、为方向清单（6 个演进方向、4 段结合说明、6 条学术条目、10 条工业条目、6 条 2025 趋势、10 条未来趋势），条目以产品名与年份为主。本节按「能力 → 机制 → 证据 → 成熟度 → 现在该做什么」重写，每条原条目的去向在 §5.1 末的对照段里逐条交代。

### 5.1 先分清三类「前沿」

本章的机制在 [§ 7](01-data-agent-section-7-sec7.md) §7.3 里被拆成四维：**查询面**是封闭映射还是开放生成（§7.3.1）、**生成空间**约束在哪一层（§7.3.2）、**执行边界**上谁有权读什么（§7.3.3）、**纠错信号**从哪来（§7.3.4）。前两维决定能力上限，后两维决定这套能力能不能进生产。

这四维里，**LLM 只改了第一维**：它把「自然语言 → 有限模板集合」的映射，换成了「在无限空间里生成一个查询」。这一步的后果是连锁的——准确率不再有天然上限，但**错误形式也换了**：从「明确回一句不支持」变成「语法正确、语义错误的静默算错」（§7.3.1 的候选对照表）。**其余三维全部是为一维的变化买单的工程补偿**：语义层把开放生成收窄（§7.3.2），沙箱与权限前移限住执行面（§7.3.3），执行反馈回灌负责发现错误（§7.3.4）。

按这条标准看，本节要判的不是「Data Agent 变强了多少」，而是**补偿做到位了没有**。这个判法会得出一个与原清单不同的结论：原清单把「Self-Correction」「Multi-Agent」「指标语义层」「Code Interpreter」并列成四个平行趋势，而它们其实处在**不同的因果位置**——语义层是**前置条件**（没有它，静默错误率不降），反馈回灌是**必要条件**（不回灌时错误率上限与裸 Text2SQL 相同，§3.1 第二条约束），Multi-Agent 与 Code Interpreter 是**可选工程手段**（前者买可定位性、后者买灵活性，都不直接降低错误率）。

本节用 L1 / L2 / L3 三级区分。判据必须可核验，而不是「感觉成熟」：

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口 / 生态未稳，或**仅有厂商与建设方自有案例**，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

**本节不对 L1 判据做任何修正，也不缩小它的适用范围。** 本主题最容易放宽第②条的方式，是把本书 [§6](01-data-agent-section-6-sec6.md) 的四个案例（阿里瓴羊 / 字节 / 微软 / Salesforce）当第三方案例用——它们是**建设方自述**，正是 L2 的定义所指的「仅有厂商与建设方自有案例」；把第②条改写成「有公开的生产记录」之后，读者按新措辞照样核验不了。另一条纪律：**已经在生产里跑了多年的既有能力**（只读账号 + 行级权限 + 超时 + 行数上限 + 敏感列脱敏这套沙箱做法、Schema Linking、Headless BI 的语义层抽象）不是 AI 方向——但这不等于本节不评它们：**Headless BI 的语义层抽象就是表里的第 3 行，Schema RAG（Schema Linking 那一族）落在第 7 行**，两行都有级别、也都有「现在该做什么」；**级别评的是「公开证据够不够 L1」，而不是「LLM 有没有带来它」**，读表时不要把第 3、7 行读成 AI 方向。沙箱做法本身不占评级行：它是执行层五件套（§3.1 第三条约束），本节在 §5.2.3 的边界表与 §5.3 的接口表里用到它。

还有三件容易混的事，先在这里分开：

- **产品名 vs 能力名**：「自然语言取数」「指标语义层」「代码沙箱」都是**能力名**，不是某个产品的专属功能；同一能力在不同厂商材料里挂在不同的产品名下（[§ 4](01-data-agent-section-4-sec4.md) §4.3 把它们一并列在工具链里）。判定方法：按**产品全名 + 该能力的输入输出形态**核对，而不是按能力名归类。
- **产品 GA vs 产品预览**：原 §5.3 的 7 条平台条目里，各家的 GA 状态与命名并不一致，也随时间变化。判定方法：看该产品官方文档里这条能力标的是 GA 还是 Preview（[§ 4](01-data-agent-section-4-sec4.md) §4.3 只做归类，不裁定状态），**本节不给任何产品的 GA 时点**。
- **基准分数 vs 生产可用**：BIRD-SQL / Spider 一类基准的榜单名次与分数随时间变化，且基准语料与自有库不同分布（§3.5「盲目追求准确率」）。判定入口是基准官网，用来自有评测集的结论才可写入方案。

**这三级的排法直接决定路线图的顺序**：

- **先做的三件事不是演进方向**，因为它们是 AI 之前的既有能力，却是后面每一行的评估前提：把指标定义写成机器可读（§3.2.6 的最小字段集）→ 把执行层五件套装上（只读账号 / 行级权限 / 超时 / 行数上限 / 敏感列脱敏，§3.1 第三条约束）→ 建固定评估集（§3.7）。**其中两件在表里各有一行**——指标定义即第 3 行（行内已自注「它不是 AI 方向，而是前置条件」），固定评估集即第 8 行的评估体系——这两行照样标级别，级别评的是公开证据够不够 L1，不是「LLM 有没有带来它」。没有这三件事，「换了模型或加了 Agent 有没有变好」无从判断。

- **L3 不排进排期**：NL2DSL 直接改口径、GraphRAG 接取数、因果引擎、Marketplace 都属于「等信号」。它们的共同前提是**写路径（改口径、写回数据）与读路径的门槛必须分开定**。
- **回填机制**：每次复盘时回填一次级别；某个 L2 若一年内仍拿不到自己组织里的实测量（拒答率或分类后的重试成功率），降为 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面把方向分成四组：**前三组按同一套结构逐条写**（旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度），**第四组用一张表覆盖同一套要素**，因为那一族的共同点恰恰是「机制没变」。三组的差别在于**它补的是哪一维**：

| 方向 | 改变了什么机制 | 补的是哪一维（§7.3） |
| --- | --- | --- |
| §5.2.1 开放生成面与语义层 | 自然语言与可执行查询的关系，从映射到有限集合变成在无限空间生成 | **第一维 + 第二维**（错误形式从静默算错变成明确拒答） |
| §5.2.2 执行反馈回灌 | 把外部客观信号回灌进下一次生成 | **第四维**（决定错误率上限，不是决定上限多高） |
| §5.2.3 执行边界与职责切分 | 执行者从一个（人）变成两个（人 + Agent），决策点增多 | **第三维**（权限必须前移；职责切分只买可定位性） |
| §5.2.4 机制没变的那一族 | 大多没有改变机制 | **前端、契约与相邻领域**（换输出物 / 换边界 / 与 LLM 无因果关系） |

读法建议：如果时间只够读一节，读 §5.2.1——它是本主题里唯一**改了错误形式**的变化，而错误形式决定了后面所有治理动作有没有靶子。只写收益不写代价的方向，在评审时应被直接打回：本主题里每一次「一句话就能取数」，都对应一处新的判断成本——**口径要人写、拒答要人统计、闸门要人审、重试要人封顶**。

#### 5.2.1 开放生成面：错误形式从「明确不支持」变成「静默算错」（原方向 3；原 5.2 的 Schema RAG）

- **旧做法与它的卡点**：传统 BI 与 ChatBI 都把问题映射到一个**有限集合**——人写查询，或命中最接近的模板。卡点是覆盖面与准确率不能同时涨：每加一个模板，歧义匹配的风险与回归测试量各涨一点；而集合外的问法只能回一句「不支持」（§7.3.1 的候选对照表）。
- **AI 改变了什么机制**：**自然语言与可执行查询之间的关系，从「映射到有限集合」变成「在无限空间里生成一个」**。这改的不是准确率的高低，而是**准确率的上限形式**：开放生成面没有封闭集合，所以覆盖面没有上限，错误率也没有天然上限。
- **由此得到的**：**因为生成空间不再被模板封住，所以「任意问法」第一次成为可能**——这也是 Data Agent 相对 ChatBI 的全部增量所在。但得到「能答」的同时也得到了一种新的失败：**语法正确、语义错误、且不报错的答案**。语义层（§7.3.2 的收窄）与 Schema RAG（把表与列作为检索对象）都是针对这一种失败做的：前者把错误转成「明确拒答」，后者降低「选错表」的概率。
- **由此付出的**：**其一，错误不再自我暴露**——错的答案与对的答案长得一样，业务方会先怀疑数据、再怀疑系统、最后不再使用（§3.5「无指标语义层」的暴露方式）。**其二，能力上限被语义层锁死**——语义层没覆盖的问题 Agent 一定答不了，此时它比裸 Text2SQL 更「无能」（后者至少会给一个数），所以上线初期它看起来更弱（§3.2.6 的代价：【经验】量级数周到数月）。**其三，旁路一旦打开口径治理就回到原点**——业务在拿不到答案时会走自由生成的直连查询，而旁路的错误不会回流到语义层（§3.2.6 的失效点）。

```text
   同一个问题在三种约束下的失败形式（决定治理动作有没有靶子）
   ────────────────────────────────────────────────
   模板映射（ChatBI）   集合外 → 明确回「不支持」
                        → 可统计、可补模板
   语义层收窄（Metric-First）  未命中 → 明确拒答
                        → 可统计、可补语义（§7.3.2）
   开放生成（裸 Text2SQL）     任何问题 → 一个看起来合理的 SQL
                        → 不报错、不可统计、只能靠人发现
   ────────────────────────────────────────────────
   判定方法：统计「未命中指标而拒答的比例」，并检查是否存在
             绕过语义层的直连查询。后者非零即说明旁路已开
```

- **证据与来源**：【公开】语义层作为独立消费接口有公开产品形态（主文件 §2.3 已列 dbt Semantic Layer / Cube.js / MetricFlow / 阿里 QuickBI 指标中台 / 网易有数指标库）；「自然语言 → 指标语义层 → SQL」而非「自然语言 → SQL」是 [§6](01-data-agent-section-6-sec6.md) 四个案例的共同做法【公开，各案例原始引注见 §6，2020–2024】。**本节未能核到可点名的第三方（非厂商）公开生产案例**——即「某非厂商组织公开过它的拒答率、口径覆盖数与上线前后的错误率」这类带参数的材料。
- **成熟度**：**L2**（第 3 行；本节同时涉及的第 7 行 RAG + SQL 分流同为 L2，理由相同：形态可核验、**②核不到**、标签与评估口径无共识）。判据：① 满足（产品形态可核验，GA 时点以官方发布说明为准）；**②核不到**；③ 指标定义的字段与版本语义各家不同 → 语义层可以建，但不要假设换产品能平移。
- **判定方法**：抽 50 个真实问题，按「落在语义层内 / 未命中被拒答 / 未命中却给了数」三类统计。**第三类必须为零**——非零即说明存在旁路。
- **什么时候不值得做**：问题集合封闭且高频（≤ 50 个，§7.5 决策树的判据）时——此时模板映射的确定性更值钱，上开放生成的边际收益接近零（§7.3.1 的失效条件）。

#### 5.2.2 执行反馈回灌：本主题唯一带真值信号的纠错闭环（原方向 1；原趋势 2、4）

- **旧做法与它的卡点**：单轮生成把 SQL 交给用户就算完成，失败即报错。卡点是**错答案与对答案长得一样**——语法正确、能跑通、甚至口径也接近，唯独查的是业务库而不是数仓（§3.5「黑盒 SQL 生成」的暴露方式）。而模型自评不解决问题：自评不是外部信号，多数情况下只会重复同一个错（§3.1 第二条约束）。
- **AI 改变了什么机制**：**把外部客观信号回灌进下一次生成**。SQL 恰好能给出机器可客观判定的反馈——语法、类型、空结果、行数异常、口径约束（如「GMV 不可能为负」），这是它与其他 Agent 场景最大的机制差别（§7.3.4 的候选对照表）。回应开头那句判断：**不回灌执行反馈的 Data Agent，无论模型多强，其错误率上限与裸 Text2SQL 相同**。
- **由此得到的**：**因为纠错靠的是数据给出的信号而不是模型自评，所以系统可靠性的下限第一次不再只由模型水平决定**——换模型不至于让可靠性同步漂移。评估也因此有了可自动化的抓手：把「正确答案 / 空结果 / 有结果但口径不符」分开统计，前两类可自动判定，第三类不可。
- **由此付出的**：**其一，每轮纠错都要再付一次调用与一次查询扫描，延迟与成本随迭代次数线性增长**，所以迭代上限必须写死（§3.2.3 的约束①②、§7.3.4 的工程参数）。**其二，三类失败重试一万次也不会变对**——权限不足、数据缺失、口径类失败（分歧或未定义）不在模型可修正的范围内，重试 T 次全失败而成本恰好是单次的 T 倍（§3.2.3 的失效点）。**其三，口径类失败自纠不出来**：执行反馈是通的、结果也非空，但用户说的「活跃」与语义层里的「活跃」不是一回事，这类错误只能靠歧义澄清（§7.3.4 的失效条件）。

```text
   反馈回灌的边界：三类失败必须直接终止（否则成本是单次的 T 倍）
   ────────────────────────────────────────────────
   可自纠（执行反馈判得了）  语法错误 / 列不存在 / 类型不匹配 / 空结果异常
       → 值得重试；反思产物要写成「下一次生成能直接用的信息」
         （写「生成错了」没有用——§3.2.3 结构图里「反思产物的形态决定它的价值」）
   不可自纠（重试也不变对）  权限不足 / 数据缺失 / 口径分歧或未定义
       → 直接终止并转人工；这三类不在模型可修正的范围内
   ────────────────────────────────────────────────
   判定方法：把失败按上述原因分类统计重试成功率；
             只有「口径」一类能通过补语义永久消除（§7.3.4）
```

- **证据与来源**：【公开】Reflexion 把外部反馈作为修正信号（Shinn 等，2023，可按论文核验）；DIN-SQL（2023）、MAC-SQL（2024）、CHESS（2024）一类公开方案都把「校验 + 重写」放进链路（可按题名核验）；SQL 有可客观判定的反馈这一点，在 §7.3.4 已按四类信号列出。**本节未能核到**可点名的第三方（非厂商）公开生产案例，也未核到带参数的「重试轮数—准确率」曲线。
- **成熟度**：**L2**（第 1 行；本节判定方法同时覆盖第 8 行评估体系，两行同为 L2，判据也逐条一致——① 论文与基准可按题名核验、**②核不到**；③ 分别是「各框架对反思产物的形态无约定」（第 1 行）与「内部评估集的口径无通行做法」（第 8 行））→ 做 PoC 时要自己把这套分类定下来。
- **判定方法**：把失败按原因分四类（语法 / 权限 / 空结果 / 口径）统计重试成功率。**只有「口径」那一类能反映语义层的缺口**，而它恰好是唯一能通过补语义永久消除的一类（§7.3.4）。

#### 5.2.3 执行边界与职责切分：执行者从一个变成两个（原方向 2、4；原趋势 3、6、7）

- **旧做法与它的卡点**：BI 时代的取数身份只有一个——人，越权与否由人的自觉加查询时的权限模型判定。自然语言入口把取数门槛降到一句话，同时把越权的可能性放大：写 SQL 需要知道表名，问一句话不需要（§3.1 第三条约束）。
- **AI 改变了什么机制**：**执行者从一个（人）变成两个（人 + Agent）**，于是权限判断必须发生在 SQL 执行**之前**，且必须能区分「人问的」与「Agent 代问的」（§7.3.3）。另一半是**职责切分**：Multi-Agent 把选表、生成、校验、解读切成有输入输出契约的几段（§3.2.4），Code Interpreter 则把能力的载体从 SQL 扩到代码。
- **由此得到的**：**因为执行者可以单独标识，所以「谁取走了什么」第一次能在审计里归因**——不可归因的越权就是破坏上限（§7.3.3）。职责切分带来的是另一件东西：**故障可定位到具体一段**，并且可以让不同档位的模型承担不同职责，成本结构可控（§3.2.4）。
- **由此付出的**：**其一，拆段的收益是排障时间，不是准确率**——单步生成的准确率不因拆段提高，而调用次数从 1 次变成 5–7 次【经验，§3.2.4】；沿用 §7.4 算例 4 的口径，编排层会把每次问数的模型调用从 4 次上下变成 8–10 次，成本项约为原值的 2–2.5 倍【推算：8–10 ÷ 4】。**其二，「权限被拒」必须当成正常返回路径而不是异常**，否则下游会把拒绝当故障重试，绕过权限的压力反过来逼团队放权（§7.3.3）。**其三，Code Interpreter 把生成空间重新打开**：它在 §7.3.2 的对照表里被记作「约束来源：无」，语义层挡不住它，且产物（脚本）不可复现时答案不可追溯（§7.4）。

| 边界 | 谁负责失败 | 判定方法 |
| --- | --- | --- |
| Agent 独立只读身份 + 继承人的数据范围（§7.3.3） | 平台侧；权限模型缺失时，越权在审计里不可归因 | 问「这次取数是谁问的、用哪个身份执行的」，答不出来即边界未立 |
| 多段职责切分（§3.2.4） | 上游段；Router 分错意图时后面每段都「严格正确」 | 把某一段的输入输出打印出来，不是结构化的即说明拆分没起隔离作用 |
| 代码沙箱（原方向 4） | 使用方；脚本产物不可复现则答案不可追溯 | 同一个问题重跑一次，脚本与结果是否一致 |

- **证据与来源**：【公开】把企业级权限与审计做成产品的一等能力，是 [§6](01-data-agent-section-6-sec6.md) 微软案例的核心做法【建设方自述，2021–2024】；只读账号 + 查询超时 + 返回行数限制 + 敏感列脱敏是主文件 §2.3 列出的沙箱公开做法【经验】；DIN-SQL / MAC-SQL / CHESS 一类方案按「选表 / 生成 / 修正」分角色（可按题名核验，§3.2.4 已列）。**本节未能核到**可点名的第三方（非厂商）公开生产案例，也未核到「拆段带来的可定位性提升」的量化材料。
- **成熟度**：**L2**，三行级别相同，但**缺的判据不同**——第 2 行 Multi-Agent 与第 5 行 Code Interpreter：① 满足（形态可核验）、**②核不到**、③ 分别是「段间传什么、边界怎么定无通行做法」与「沙箱产物是否可复现无约定」；第 9 行安全与治理：**① 也核不到**（合规要求真实存在，但 Agent 级审计无独立发布物）、**②核不到**、③「审计粒度（提问 / SQL / 结果三级）无通行约定」。→ 用之前先把段间契约与审计粒度写出来。
- **什么时候不值得做**：单指标点查时——拆分买的是排障时间，而点查本来不需要排障（§3.2.4 的失效点）；合规场景下不想引入人工等待时——沙箱五件套与 HITL 是两件事，前者必须全上，后者按动作的不可逆性挂（§3.2.5）。

#### 5.2.4 被写进「AI 时代」但机制没变的那一族

这一族在表里列了六行（五行评级、一行属选型问题不评级）。共同点是：**它们都不是「AI 改变了机制」**——前五行只是换了模型的输出物（NL2DSL 把输出从查询换成定义）、换了结构存放位置（GraphRAG）、换了交付形态（Marketplace、Agent-as-a-Service），或者**要的输入根本不是 SQL 结果**（因果引擎要的是识别条件）；最后一行是「模型变强」，而模型变强不改变约束层，这是 §3.1 的第一条结论。把它们一起写成「AI 时代的演进」，会让真正决定成败的三件事——**口径写成机器可读、执行层五件套、固定评估集**——一件都排不进排期。

| 方向 | 旧做法与它的卡点 | 改变了什么机制 | 由此得到 | 由此付出 | 证据与成熟度 |
| --- | --- | --- | --- | --- | --- |
| NL2DSL：自然语言生成指标定义（原方向 5） | 定义指标要人写 YAML，业务人员被挡在门外 | **换了输出物，没换风险结构**：模型写的是定义而不是查询 | 业务人员能参与口径建设 | 写错的定义影响**所有**消费端，而查询写错只影响一次；且定义的验收需要评审流程，不能靠执行反馈 | ① 无正式条目；② 不适用；③ YAML 与语义层契约无约定 → **L3** |
| GraphRAG + Data Agent（原方向 6；原 5.2 的结合一段） | 概念与关系类问题在 SQL 里无解，在向量检索里只能召回原文 | **换了结构存放位置，没换事实来源**：数字仍必须来自结果集（§3.2.7） | 「事实 + 关系 + 数据」三类问题能分别走各自最合适的路 | 多一次分流调用，而分流错误率成为整体错误率的下限；实体标识不统一时，图谱侧会把两个同名实体合并 | ① 核不到（GraphRAG 有开源项目 2024，但无标准接法条目）；② 不适用；③ 边界无约定 → **L3** |
| 指标因果引擎（原趋势 9） | 归因靠分析师拆维度，结论依赖经验 | **与 LLM 无因果关系，且不属于取数**：从相关到因果要的是识别条件（对照、断点、工具变量） | （若接上）异常时能列出候选维度与各自贡献 | 用相关性话术冒充因果，会让决策建立在一个无法检验的结论上 | ① 无正式条目；② 不适用；③ 输入是识别条件而非结果集 → **L3** |
| Data Agent Marketplace（原趋势 10） | 每个团队各自建 Agent 与指标，重复投入 | **与 LLM 无因果关系**：它是复用契约问题，不是分发问题 | 指标与 Agent 可被跨团队复用 | 复用要求口径有 Owner 与版本、权限可迁移、SLA 可承诺；缺一样，复用就是把别人的错口径接过来 | ① 无正式条目；② 不适用；③ 契约形态无共识 → **L3** |
| Agent-as-a-Service 与 BI 工具融合（原趋势 5、8） | 每个企业自建编排、模型接入与运维 | **换了交付形态，没换能力边界** | 编排与入口可以买，省下平台建设期 | 买不来你的口径与权限边界（§7.3.3）；接口不互通时，换平台的迁移成本落在语义层与审计日志上 | ① 形态可点名（§4.3），GA / 预览状态不一，本节不裁定时点；**②核不到**；③ 接口无标准 → **L2** |
| NL2SQL 专用模型（原 5.3 工业条目：阿里通义 / DeepSeek-Coder-V2 / 智谱 GLM-4） | 通用模型的 schema 理解不足 | **模型变强，不是机制改变**：约束层不动，错误率上限就不动（§3.1 第一条约束） | 同样的语义层下，生成环节的语法错误与选表错误减少 | 换模型的收益可能被上游约束层吃掉；而每次换模型都要重跑评估集与回归 | 属选型问题，不进本节评级；落点见 §4.3 的「LLM 基础模型」清单（本节 §5.4 不设模型入口）→ **不评级** |

**读这张表的方式是看「改变了什么机制」这一列**：六行里没有一行是「LLM 让取数更准」，改的是输出物、结构位置、交付形态或契约。这解释了为什么评级的那五行全部停在 L2 / L3——判据②核不到只是表层，深层原因是**它们的好处不来自模型能力，所以也不会因为模型变强而变得可核验**。

顺带说清一件常被省略的事：**语义层、固定评估集、审计日志、执行层五件套**不是「以后要做」，而是「现在就该做」——它们与 LLM 无关，却是 §5.1 表里所有 L2 方向变得可评估的前提。把这四件事与「上一个更懂 SQL 的模型」放在同一张排期表里竞逐资源，是本主题最常见的一次排序错误。

### 5.3 与本主题既有栈的接口在哪

Data Agent 与上下游之间不是「结合」关系，而是**交接物**关系：谁把什么交给谁、数据以什么形态穿过边界、失败时谁负责。这张表的「现状」一列用同一套 L1 / L2 判据，但评的是**这个接口**，不是 §5.1 表里的演进方向——两者不要互相引用，否则同一个 L1 会在两处指两件事。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Data Agent ↔ 指标语义层（[../../01-modeling/10](../../01-modeling/10-metric-system/10-metric-system.md)） | 交接物 = `metric_id` + 口径版本 + 允许维度 + 默认过滤 + 时间语义 + Owner（§3.2.6 的最小字段集） | 语义层侧；口径无 Owner 时，改一次定义会同时改变所有消费端的结果 | L2（① 形态可核验；**②核不到**；③ 版本语义无通行做法） |

| Data Agent ↔ BI 工具（[§ 7](01-data-agent-section-7-sec7.md) §7.6） | 交接物 = 语义层 API（Headless BI）；BI 做深度分析与出图，Agent 做自助问答 | **双方共用**；口径若只在 BI 侧维护，Agent 侧会形成第二套口径 | L2（① 形态可核验；**②核不到**；③ 两侧口径的同步机制无约定） |

一句话概括：**LLM 没有让取数变得更可靠，它把「用户需要知道表名」这条前提去掉了，于是可靠性必须由语义层、执行层与评估体系重新兜住**。由此得到三条约定。

**第一条约定：口径必须有 Owner 和版本。**（§3.2.6 的最小字段集）这条约定今天是可选的，当 §5.1 表里任何一个 L2 方向真正上线后会变成必需的——因为集中化的收益与它的爆炸半径来自同一个机制：一次口径改动会同时改变所有消费端的结果（§7.3.2 的失效条件）。

**第二条约定：「拒绝」必须是一条正常返回路径。** 权限被拒、指标未命中、口径有歧义，都要能明确地拒绝或反问，并且被统计。把它们当异常处理时，下游会重试到绕过为止——而旁路一开，口径治理就回到原点。

**第三条约定：先把三组数量出来，再谈选型。** 拒答率（语义层缺口有多大）、失败原因分类后的重试成功率（哪类错误可自纠）、单次问数的调用次数与 token 成本（§7.4 算例 1 与算例 4 的推导链可直接代参数复算）。**这三组数拿不出来时，换模型、拆 Agent、上语义层都无从判断有无收益。**

```text
   开放生成面新增的成本，落在三个不同的位置上，谁也不能替谁兜底
   ────────────────────────────────────────────────
   语义层（5.2.1） ──► 把错误形式从「静默算错」换成「明确拒答」
       必须回答：拒答率是多少？旁路有没有被打开？
   执行反馈（5.2.2） ──► 决定错误率上限，不决定上限多高
       必须回答：哪几类失败可自纠？迭代上限是多少？
   执行边界（5.2.3） ──► 让越权在审计里可归因
       必须回答：这次取数是谁问的、用哪个身份执行的？
   ────────────────────────────────────────────────
   三者都没有改变：数字仍只能来自结果集（§3.2.7），
                   权限仍必须在执行层强制（§3.1 第三条约束）
   判定方法：任一「一句话取数」的提法，先问它落在上面哪一条上；
             答不出落点的，多半只是换了个入口
```

**第三方生产案例**

- **本节未能给出**可核验的第三方（非厂商）公开生产案例。公开材料里能核到的是三类：① 论文与公开基准（属方法与评测一侧）；② 厂商产品文档；③ 建设方的工程自述——[§6](01-data-agent-section-6-sec6.md) 整理的阿里瓴羊 / 字节 / 微软 / Salesforce 四个案例，出处标注为「机构名 + 年份区间」，按判据属**建设方自述**，不构成第②条。**这个空白本身是结论**：它正是 §5.1 表里没有任何一行到 L1 的直接原因。
- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——固定评估集（公开基准 + 内部真实问题）、拒答率、失败原因分类后的重试成功率、单次问数的调用次数与 token 成本。这四组数在评审里的分量超过任何榜单名次。
- 三类证据里**最容易造假的是「准确率」**：只报一个准确率而不说问题集从哪来、判定标准是什么、空结果算不算错、跨库与多轮问题占多少，无法复核。**判定方法**：只接受同时给出「问题集来源 / 判定标准 / 是否含多轮与拒答」三者的准确率。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **语义层**：抽 50 个真实问题，统计「未命中却给了数」的比例——非零即存在旁路。
2. **执行反馈**：把失败按语法 / 权限 / 空结果 / 口径四类分开统计重试成功率。
3. **Multi-Agent**：把某一段的输入输出打印出来，看它是不是结构化的。
4. **Code Interpreter**：同一问题重跑一次，看脚本与结果是否一致（不可复现即不可追溯）。
5. **评估体系**：问「上一次改动后跑没跑评估集，数字是多少」。
6. **平台产品**：问它能不能接你自己的语义层与权限模型——接不上时，买来的是入口。

**怎么用这份清单**：要核「能力存不存在」看官方文档（最快）；要核「机制是不是真的」看论文（最慢但最稳）；要核「在我这里值不值得做」看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。三类之外还有一种最没用、却最常见的形式：把「某平台的自然语言问数准确率很高」写进方案而不写问题集与判定标准——它既不能被复核，也不能被证伪。

### 5.5 被过度宣传的部分

本节列四条（常规为三条）：本主题的过度宣称都指向同一个方向——**把「组件更强」当成「结果更可靠」**。

**「Multi-Agent 更准」**——实际是：它买的是**故障可定位性**，不是准确率（§3.3 已给出这条裁决）。单步生成的准确率不因拆段而提高，被拆出去的是排障对象。**为什么会这样**：拆分改的是职责边界与产物形态，不改模型对 schema 的理解能力；而误选的实际后果是调用次数与延迟先涨上去，准确率基本不动（§7.4 算例 4）。**它什么时候才会成真**：当错误分类统计显示「同一类错误反复落在同一段职责上」——那时拆那一段才有依据。**判定方法**：先跑单体 ReAct + Reflexion 拿到基线，再看错误分类里有没有一段特别集中。

**「自然语言取数让业务自助」**——实际是：语义层没建时，自助的门槛从「会写 SQL」降到了「会提问」，而**判断答案真假的门槛反而升高了**：错的答案与对的答案长得一样（§7.3.1）。**为什么会这样**：开放生成面把错误形式换成了静默算错，而静默错误不会自我暴露。**它什么时候才会成真**：未命中指标时系统明确拒答并统计拒答率，且回答里的每个数字都能回溯到一条可重跑的查询（§3.2.7）。**判定方法**：抽 20 个真实提问，数其中有多少条能追到一条具体查询与口径。

**「Code Interpreter 让 Data Agent 无所不能」**——实际是：它把生成空间**重新打开**了，而这次连语义层也挡不住（§7.3.2 的对照表把它的约束来源记为「无」，未命中时的行为是「算出一个数」）。**为什么会这样**：代码能在任意数据上做任意计算，也就意味着没有一层能声明「这个算法是对的口径」。**它什么时候才会成真**：沙箱产物可复现、计算过程可追溯，且探索类结论与生产口径在链路上被明确分开。**判定方法**：问「这段脚本六个月后还能重跑出同一个数吗」。

**「Agent-as-a-Service 把 Data Agent 变成买来的能力」**——实际是：买得来的是编排与入口，买不来的是你的口径与权限边界（§7.3.3）。**为什么会这样**：口径是组织资产（谁定义、谁维护版本、谁当 Owner），权限是身份到数据策略的映射，两者都不在产品的默认值里。**它什么时候才会成真**：产品允许接入你已有的语义层与权限模型，并把它作为一等配置。**判定方法**：问它「未命中指标时默认是拒答还是自由生成」——答案会告诉你它把口径当成什么。

这四条的共性：**它们都把「能答」当成了「答得对」**——多 Agent、自然语言入口、代码沙箱、托管服务都让系统更「能答」；而取数场景真正的稀缺资源是**「这个数字能不能被回溯到一条口径与一次查询」**这个判断。判断被跳过时，能力越强，错得越像真的。

### 5.6 未来 3–5 年：可证伪的预测

这一节写了**五条**，比常规的三到四条多一条，理由是 §5.1 表里有五组方向只有评级没有信号就无法回填级别：语义层（第 1 条）、Self-Correction（第 2 条）、Multi-Agent（第 3 条）、评估体系（第 4 条）、以及本主题里唯一会产生写操作的那一族（第 5 条）。信号必须是外部可观察的（官方文档条目、产品默认行为、带条件的公开材料），而不是「我觉得会」。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 「未命中即拒答」会成为取数入口的**默认行为**，而不是可选配置 | 产品文档把拒答与拒答率作为默认能力暴露出来，并把「自由生成兜底」明确标为需自行开启 | 产品默认用自由生成兜底未命中问题，并把它宣传成「覆盖更全」 |
| Self-Correction 会从「一个重试次数参数」演进为**结构化的反思产物 + 失败原因分类** | 框架把反思产物定义成对象（含失败归因字段），并把权限 / 数据缺失类失败标为不可重试 | 框架仍只提供重试次数，且不区分失败原因 |
| Multi-Agent **不会**成为默认形态，默认的会是「按问题复杂度路由」 | 框架模板出现「先判复杂度、再决定拆不拆」的路由，而不是默认多段链路 | 框架的默认模板就是多段链路，并把它作为推荐起点 |
| 评估重心会从**公开基准名次**转移到**内部评估集 + 拒答率** | 采购与评审材料里出现「内部问题集 + 判定标准 + 拒答率」这一栏，与基准名次并列 | 选型仍以基准榜单名次作为唯一依据，且不给判定标准 |
| 写路径（回填口径、写回数据）**不会**与读路径同期放开 | 产品把「改口径」与「查数据」拆成两套权限与两套审批，并给出回滚语义 | 产品把写操作与查询放在同一个权限模型下默认开启 |

写这五条时的共同约定：**信号必须是外部可观察的**（产品默认行为、文档条目、带条件的公开材料），而不是「我觉得会」。**被检验得最快的是第一条**——取数产品的下一个版本里拒答是不是默认，一年内就能看到；**最慢的是第五条**——写路径的回滚语义形成周期通常以年计。**回填规则**：每年评审时把 §5.1 表里对应的行重判一次；若信号指向证伪那一列，级别下调而不是维持。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 业务想直接问数，口径还没治理 | 先建指标语义层的最小字段集与 Owner 制（§3.2.6） | 观察拒答率是否被统计、旁路是否被打开 | 不要先上自由生成——静默算错没有靶子，也没法归因 |
| 已经有语义层，想提高准确率 | 把「未命中即拒答」做成默认，并统计拒答率 | 观察拒答集中在哪一类问题（那是指标清单的缺口清单） | 不要用「更懂 SQL 的模型」去补指标清单的缺口 |
| 想加执行反馈 | 写死迭代上限、同一 SQL 不重复执行、失败原因分类 | 观察四类失败的重试成功率分布 | 不要对权限 / 数据缺失 / 口径类失败重试——它们不会变对 |
| 想拆成多 Agent | 先跑单体 ReAct + Reflexion 拿基线，记录错误落在哪一段 | 观察同一类错误是否反复集中在同一段职责 | 不要在单指标点查场景先拆——拆分的收益是排障时间，点查不需要排障 |
| 想开代码沙箱 | 与取数链路分开审计，并要求脚本可复现 | 观察探索类结论有没有被当成生产口径使用 | 不要让它绕开语义层去定义口径；不要用不可复现的脚本支撑需要签字的结论 |
| 有强合规要求 | 执行层五件套全上（只读 / 行级权限 / 超时 / 行数上限 / 敏感列脱敏），HITL 只挂不可逆动作 | 观察闸门通过率与审阅时长（长期高于 95% 且数秒级即为橡皮图章【经验，§3.2.5 的阈值】） | 不要「所有查询都审」——闸门过宽等于没有闸门 |
| 想上自然语言生成指标定义（NL2DSL） | 只做「生成候选定义 + 人工评审」，评审通过才生效 | 观察定义变更的影响面是否可列出 | 不要让模型直接改生产口径——写错定义的影响面是所有消费端 |
| 有人提议接 GraphRAG | 先分清概念解释题与取数题，只把前者交给图谱 | 观察实体标识与语义层是否已统一 | 不要让数字绕经图谱；不要在标识不统一时接图谱 |
| 想买托管 Data Agent 平台 | 先问它能否接入你已有的语义层与权限模型 | 观察未命中指标时的默认行为是拒答还是自由生成 | 不要在接不上语义层与权限时先买——买来的是入口，不是能力 |
| 预算有限，只能做一件事 | 建固定评估集 + 把数字只来自结果集这条边界写死 | 观察上一次改动后有没有可对照的数字 | 不要一上来先换模型或先拆 Agent——基线在哪都还不知道 |
| 单次问数成本失控 | 先量单次调用次数与 token 成本，再做模型分层与高频问题缓存（§7.4 算例 1 的推导链可直接代参数复算） | 观察缓存命中率与小模型承担的比例 | 不要在提示词上抠 token——调用次数是设计期定的，不是运行期能省的 |
| 运营与财务对同一个指标报出两个数 | 强制走语义层，给每个指标指定 Owner 与版本（§3.2.6） | 观察跨部门对账时是否还会出现两个都「有依据」的答案 | 不要用「换更准的模型」解决口径分歧——它只会把分歧变成随机选择 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（多几次调用、多一套权限、多一份契约），**而收益依赖一个尚未成立的假设**（口径已经治理好 / 模型更强就够了 / 闸门不会形式化）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 LLM 真正改变的是**一件事**——**自然语言与可执行查询之间的关系，从「映射到有限集合」变成了「在无限空间里生成一个」**（§7.3.1）。由此得到的全部收益是「任意问法可以问」；由此付出的全部代价是**错误形式换了**：从「明确回一句不支持」变成「语法正确、语义错误的静默算错」。**它没有改变的是**：数字仍只能来自结果集、口径仍必须有人定义（§3.2.7、§7.3.2），权限仍必须在执行层强制（§3.1 第三条约束），而正确性的判定信号仍只来自执行结果与业务规则（§7.3.4）。所以本节表里的每一条，本质都是在为这一个变化补不同的洞。
>
> 判断本主题下任何新提法的快捷方式：**它是在改错误形式，还是在改执行边界？** 改错误形式的（语义层、拒答、评估集）要立刻回答「未命中时系统说什么」；改执行边界的（沙箱、权限前移、审计、HITL）要立刻回答「这次取数是谁问的」。第二个判断同样快：**它需要的是执行反馈，还是需要模型自评？** 只有前者的纠错方向由数据决定。
>
> 如果只能带走一句话：**先把口径写成机器可读、执行层五件套装上、固定评估集建起来，再谈用不用更强的模型、拆不拆 Agent**——这三件事做完，本节表里所有 L2 都变得可评估；这三件事没做完，L2 与 L3 的差别只体现在演示里。
