## 3. 设计模式与范式

> 原 § 3 共 217 行、列出 8 个模式（ReAct / Plan-and-Execute / Reflexion / Multi-Agent Data Analyst / Human-in-the-Loop / Metric-First / RAG + SQL 混合 / Self-Ask + Tool-Use），8 个模式各带一段流程示意与「优点 / 缺点 / 适用」三行，另有一张 8 行适用场景表、一棵决策树与 8 条「陷阱」。本节重写为 305 行模式手册，8 个模式名与 8 条陷阱名一个不删，把各模式原有的「优点 / 缺点 / 适用」三行展开为约束来源、机制因果句、机制层面的代价与失效点。

### 3.1 先看约束：模式不是选择题，是约束的产物

「简单查询用 ReAct、归因分析用 Plan-and-Execute、生产环境必须加 Reflexion」这类按业务问题挑模式的速查表，漏掉了真正决定成败的那条约束：**SQL 的生成空间被约束在哪一层**。裸 schema 自由生成、收窄到指标语义层、还是根本不生成 SQL 而是写代码算（Code Interpreter 路线），这三者面对的错误形式完全不同：自由生成会给出「语法正确、口径错误」的答案，语义层约束会把错误转成「拒答」，写代码则把错误暴露为一次可复现的失败。同一个问题在三种约束下都「能答」，但只有一种会承认自己答不了。

第二条约束是**纠错信号从哪来**。Data Agent 与纯生成系统最大的差别，是它有一个外部客观信号可用：SQL 要么跑通要么报错，结果集要么落在业务合理区间要么不落。这个信号便宜、即时、且不由模型自己产生，所以只要把它回灌，系统的可靠性就不再只依赖模型水平。反过来说，**没有回灌执行反馈的 Data Agent，无论模型多强，其错误率的上限与裸 Text2SQL 相同**。而执行反馈也有它覆盖不到的地方：权限不足、数据缺失、口径类失败（分歧或未定义）这三类错误，重试一万次也不会变对——识别这三类并终止，是 Reflexion 能否上生产的分水岭。

第三条约束是**权限与不可逆动作**。自然语言入口把取数门槛降到一句话，同时把越权的可能性放大了：写 SQL 需要知道表名，问一句话不需要。因此「谁有权读哪些行与列」这件事必须在执行层强制（只读账号、行级权限、超时、行数上限、敏感列脱敏），而不能靠提示词约束；涉及写回或对外发布的动作，则必须在结构上留人工闸门。

本节的组织方式：先给约束表，再逐个模式写清它被什么逼出来、结构长什么样、代价是什么、在什么条件下优点反转成缺点。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 生成空间约束在哪一层（裸 schema / 语义层 / 代码） | 决定错误的形式：静默算错、明确拒答、还是可复现失败 | 「更准的模型就够了」——约束层不动，错误率的上限就不动 |
| 纠错信号来自哪里（执行反馈 / 业务规则 / 人工） | 决定系统能否自我修正，以及修正的边界在哪 | 「让模型再想一遍」——自评不是外部信号，多数情况下只会重复同一个错 |
| 权限与不可逆动作 | 决定执行层必须强制的五件套（只读账号、行级权限、超时、行数上限、敏感列脱敏）与人工闸门的挂载位置 | 「在提示词里写不许越权」——提示词不是权限系统 |
| 任务步数与上下文容量 | 决定走单循环还是先规划 | 「步数多就该规划」——规划错误的传播代价可能高于步数带来的上下文压力 |
| 问题类型是否可事先枚举 | 决定走语义层映射还是自由生成 | 「开放生成总比模板强」——集合封闭时模板的确定性更值钱 |
| 问数与成本约束 | 决定模型分层、缓存与调用次数上限 | 「先做准再优化成本」——调用次数是设计期决定的，不是运行期能省的 |

### 3.2 模式逐个拆解（核心节）

按本章 [§ 7 与其他方法对比](01-data-agent-section-7-sec7.md) 的四个机制维度定位这八个模式：**查询面**由 3.2.1 与 3.2.2 承担（开放生成面上的两种循环），**生成空间约束**体现在 3.2.6（收窄到指标清单）与 3.2.7（两条路径的事实来源分流），**纠错**由 3.2.3 承担，**权限与边界**由 3.2.5（人工闸门）、3.2.4（职责切分，SQL 段只吃候选集）与 3.2.8（工具注册表即能力边界）承担。四维中前两维决定能力上限，后两维决定这套能力能不能进生产——这也是为什么下面的失效点普遍落在「看起来更强的那一侧反而出问题」。

#### 3.2.1 ReAct（Reasoning + Acting）

- **被什么约束逼出来**：单轮生成处理不了链式依赖——要先知道 DAU 的口径定义，才可能写出对的 SQL——约束是**下一步该做什么取决于上一步的真实返回**。
- **结构**：Thought → Action → Observation 的受控循环，工具集合封闭、终止条件显式。

```text
ReAct 的结构：一个受控循环，不是一次生成
  loop（最多 T 轮）：
    Thought     当前还缺什么信息（自然语言，可审计）
    Action      选一个已注册工具 + 结构化参数（语义层检索 / Schema 检索 / SQL 执行 / 计算）
    Observation 工具的真实返回（不是模型编的）
    终止：答案已可给出 / 达到最大轮数 T / 连续两轮无新信息
  约束：Action 的候选集由「注册了哪些工具」决定，不由模型自由发挥
  约束：T 必须显式（【经验】常见 3-6），否则一次问数的成本无上界
  由这两条直接导出的账：单次问数的调用次数 <= T，成本上界在设计期就定了
    —— 上界不是运行期能靠优化省下来的，它写在 T 这个数字里
```

- **为什么这样设计有效**：因为每一步的 Observation 是工具真实返回而非模型叙述，所以中间结论可逐条复核，幻觉被限制在「选错工具、拼错参数」，而不是「编造库里的数」——这条性质是它能进企业环境的前提。
- **代价**：上下文随轮数线性增长，每一轮都是一次 LLM 调用，所以成本与延迟随轮数线性上升；中间产物（选了哪张表、用了哪个口径）必须落日志，否则这条链路的可审计性归零。
- **失效点**：当任务步数超出 T 的常见取值、达到 15 步以上（【经验】量级，T 的常见取值为 3-6，见上）或某一步返回大结果集时，「可解释」反转成「上下文爆炸且早期错误不可撤销」，因为每一步的新观察都塞进同一个上下文，而第二轮的选表错误会被后面所有轮次继承——表现为最终答案错、但每一步单看都「有理由」。
- **真实使用**：【公开】ReAct 由 Yao 等 2022 年提出（论文题名 *ReAct: Synergizing Reasoning and Acting in Language Models*，可按题名检索核验）；【经验】生产里的常见形态是把它当默认骨架，再用语义层与执行前校验压住它的下限，而不是靠加长推理链提高上限。

#### 3.2.2 Plan-and-Execute

- **被什么约束逼出来**：归因类问题的子任务可以并行、且各子任务需要隔离上下文，而单循环把所有观察堆在一起；约束是**规划的质量比单步执行的质量更决定结果**。
- **结构**：一次规划产出子任务 DAG，再逐子任务独立执行，最后综合。

```text
Plan-and-Execute 的结构：把「想清楚」与「做」分成两段
  Planner（只产出计划，不接触数据）
    输出：子任务 DAG（含依赖方向）
    每个子任务必写：输入 / 输出 / 验收判据
      验收判据缺失时，子任务失败会被静默吞掉，而不是报错
  Executor（每子任务一个独立上下文）
    子任务之间通过显式产物传递，不共享对话历史 ← 上下文隔离的实现方式
    DAG 的并行分支可按维度切（按地区 / 按渠道）
  Synthesizer
    只基于子任务产物组织答案，不允许引入计划外的新查询
```

- **为什么这样设计有效**：因为子任务之间不共享上下文，所以一个分支失败不会污染其他分支，且失败可以单点重跑——这正是归因分析最需要的性质（「地区维度查错了」不该让渠道维度重来）。
- **代价**：规划是一次不接触数据的大模型调用，成本前置且不一定省钱；子任务产物需要结构化（否则综合阶段又变成读散文），而这要求每个子任务都定义输出 schema。
- **失效点**：当规划阶段漏掉一个必要维度时，「隔离」反转成「系统性缺失」，因为执行阶段只能执行计划、无法发现计划本身不对——表现为拆分维度看起来齐全、数字逐项正确，而结论整体偏离（例如漏看退款或漏看新客）。判定方法：抽查计划的维度覆盖面，而不是抽查子任务结果。
- **真实使用**：【经验】LangChain 提供 Plan-and-Execute 一类 agent 类型（可按其官方文档当前版本核验；该文档的标题与年份本节无法给出，此处按【经验】档处理），生产里的折中做法是先分类再决定走单循环还是先规划——把「需要几步」当成路由判据，而不是默认全都规划（见本章 § 7 的决策树）。

#### 3.2.3 Reflexion（反思）

- **被什么约束逼出来**：执行反馈便宜且客观（跑通或报错、结果是否落在合理区间），但模型单轮用不上它——约束是**系统必须把外部反馈回灌进下一次生成**。
- **结构**：生成 → 执行 → 反思（带反馈）→ 重生成，反思累积、迭代有上限。

```text
Reflexion 的结构：反馈必须显式回灌，且必须有上限
  S0 = generate(Q, schema, metric_layer)
  for i in 1..T:
      (err_i, rows_i, plan_i) = execute(S_i)     # 三类信号：错误 / 结果 / 执行计划
      if 通过校验(err_i, rows_i, plan_i): return S_i, rows_i
      refle_i = reflect(Q, S_i, err_i, rows_i, plan_i)   # 产物是一句失败归因
      S_{i+1} = generate(Q, ..., refle_1..i)      # 反思累积，不是覆盖
  三条必须写死的约束：
    ① T 有限（【经验】常见 2-3 次）
    ② 同一个 SQL 不得重复执行（否则空转烧钱与拖库）
    ③ 反思与重试都要进审计日志——它是「最终答案是它」的证据
  分类终止：权限不足 / 数据缺失 / 口径类失败（分歧或未定义） —— 直接终止并转人工
  反思产物的形态决定它的价值：写「生成错了」没有用，
    要写「执行报错说列不存在，说明我引用的字段名不在候选集里」——可被下一次生成直接使用
```

- **为什么这样设计有效**：因为纠错依赖的是外部客观信号而不是模型自评，所以修正的方向由数据决定，模型只负责改；这让「模型换版本」不至于让可靠性同步漂移。
- **代价**：每次重试都是一次带数据的真实查询，成本与数据库负载乘 T；上下文里多出历次失败记录，会挤占用于理解问题的空间。
- **失效点**：当失败属于权限不足、数据缺失或口径类失败（分歧或未定义）时，「自我修正」反转成「反复烧钱」——因为这些失败不在模型可修正的范围内，重试 T 次全失败且没有任何进展，成本恰好是单次的 T 倍。判定方法：把失败按原因分类统计重试成功率，非模型可修正类应直接终止。
- **真实使用**：【公开】Reflexion 由 Shinn 等 2023 年提出（本章 § 2.1 已列出该机制）；【公开】DIN-SQL（2023）、MAC-SQL、CHESS（2024）一类公开方案把「生成 + 校验/修正」做成多步（名称与年份可按论文题名核验，本章 § 2.3 已列出）。

#### 3.2.4 Multi-Agent Data Analyst

- **被什么约束逼出来**：一份提示词要同时承担选表、生成、校验、解读、画图等多种互相拉扯的职责，而任何一处出错都无法定位——约束是**职责必须切开，且每段边界上要能看见产物**。
- **结构**：按职责拆 Agent，段与段之间传结构化产物，而不是自然语言对话历史。

```text
多 Agent 的结构：每条边界上必须是结构化产物
  用户问题
    → Router       意图分类（指标查询 / 归因 / 数据探索）—— 输出枚举标签，不是自由文本
    → Schema       Schema Linking：候选表与列（输出候选集 + 入选理由）
    → SQL          生成（只吃 Schema Agent 给的候选集，接触不到全库）← 这条同时是权限边界
    → Validator    语法 / 语义 / 权限 / 性能四类校验（输出通过与否 + 原因）
    → Executor     沙箱执行（只读账号 + 超时 + 行数上限）
    → Interpreter  基于结果集作答（只允许引用结果里的数）
    → Visualizer   按结果形态选图（不决定数据）
  约束：每一段之间传结构化产物。只传对话历史，等于把同一个上下文切成几段，什么也没隔离
  判断真假多 Agent 的问题：把某一段的输入输出打印出来，
    如果它不是结构化的，那这次拆分只增加了调用次数
```

- **为什么这样设计有效**：因为每段有独立的输入输出契约，所以故障可定位到具体一段，并且可以让不同档位的模型承担不同职责（分类与校验用小模型、生成用大模型），成本结构可控。
- **代价**：每加一段就多一次调用，延迟与成本随段数线性上升；上游错误沿链路传递，Router 分错意图时后面每一段都「严格正确」，且校验器无法发现这类错误。
- **失效点**：当问题本身就是单指标点查时，「可定位」反转成「净成本」——一次问数从 1 次调用变成 5-7 次（【经验】量级），而拆分买到的是排障时间，简单问题本来不需要排障。判定方法：按问题复杂度分层统计每条链路的调用次数与延迟。
- **真实使用**：【公开】DIN-SQL（2023）、MAC-SQL、CHESS（2024）一类方案按「选表 / 生成 / 修正」分角色（可按论文题名核验，本章 § 2.3 已列出）；【公开】本章 [§ 6 落地实践](01-data-agent-section-6-sec6.md) 四个案例的共同做法是「语义层前置、模型只做映射」，其中字节一例进一步把权限与数据可见范围绑定在语义层定义上（各案例公开材料见 § 6，2020-2024，与本章 § 7 的裁决一致）。

#### 3.2.5 Human-in-the-Loop

- **被什么约束逼出来**：有些动作不可逆或合规上不可自动化（对外发布、写回生产、接触敏感数据）——约束是**这些动作必须有一个可判定的人工闸门，且闸门挂在动作上而不是挂在问题上**。
- **结构**：可判定的触发条件 + 最小充分的审批内容。

```text
HITL 的结构：闸门挂在动作上
  触发条件（必须可自动判定，不能靠感觉）：
    ① 首次执行某段 SQL（新表 / 新库）
    ② 命中敏感列或跨域数据
    ③ 结果将写回生产系统或对外发布（不可逆动作）
    ④ Agent 已重试至上限仍失败，或自评置信度低于阈值
  审批人看到的内容（最小充分集）：
    SQL 文本 + 命中的敏感列 + 影响面（扫哪些表 / 多少行）+ 为什么触发
  约束：审批人看到的是 SQL 与命中项，不是「Agent 觉得要不要执行」
    看不到 SQL 的审批只能盖章 —— 这是 HITL 最常见的失效形态
```

- **为什么这样设计有效**：因为触发条件可判定、且只覆盖少数高风险动作，所以绝大多数问数不受影响，而风险动作的代价在发生之前被处理；这也让审计能把「谁批准了哪次取数」逐条还原。
- **代价**：每个闸门都是一次人工等待（秒到小时级），必须把等待时间计入 SLA；审批内容需要额外的渲染工作（把 SQL 与命中项整理成能看的形式），否则审批退化成猜测。
- **失效点**：当触发条件过宽（例如「所有查询都要审」）时，「安全」反转成「没人在看」——面对大量低风险请求，审批者会按模式放行，真正的风险请求淹没其中。判定方法：统计审批通过率与平均审阅时长；通过率长期高于 95%（【经验】阈值）且时长在数秒级，说明闸门已经形式化。
- **真实使用**：【公开】本章 § 6 的微软案例把权限与审计作为产品的一等能力（[微软公开材料 2021-2024]，见 § 6）；【经验】人工闸门最主要的落点是金融、医疗、政务这类有强合规要求的场景。

#### 3.2.6 指标驱动（Metric-First）

- **被什么约束逼出来**：开放生成面上「同一个问题有多种算对的可能」，而口径错误不会被执行反馈发现——SQL 跑得通、数也对不上业务理解——约束是**口径必须在生成之前就被确定**。
- **结构**：先映射到已声明指标，再按指标定义组装查询；未命中即拒答。

```text
Metric-First 的结构：把「生成」降级为「匹配 + 补维度」
  ① 意图 → 指标匹配：在指标清单里匹配
       未命中 → 拒答或反问，不允许自由生成（这是模式的定义，不是可选行为）
  ② 指标定义展开：formula / 维度 / 默认过滤 / 时间语义 / 粒度 / Owner / 版本
  ③ 生成：只组装「指标 + 维度 + 过滤 + 粒度」，不重写口径
  ④ 反查：生成的 SQL 必须能被反解回同一个指标定义（可自动化校验）
  指标清单的最小字段：
    metric_id | 口径公式 | 允许维度 | 默认过滤 | 时间语义 | Owner | 版本 | 生效日
  约束：口径变更走版本，历史区间用当时的版本回答（否则同比不可解释）
  与 3.2.7 的边界：语义层只管「数是什么」，不管「这段话怎么解释」；两者都要时走混合链路
```

- **为什么这样设计有效**：因为生成空间被收窄到「已声明的指标 × 维度」，所以失败形式从「静默算错」变成「明确拒答」——拒答是可被统计、可被补齐的失败，而错口径会一路走进决策。
- **代价**：覆盖率的上限由指标清单的完备度决定，而清单建设是前置投入（谁定义口径、谁维护版本、谁当 Owner）；对清单外的问题，系统能力为零，这让它在上线初期（【经验】量级：数周到数月）看起来「不如裸 Text2SQL 能答」。
- **失效点**：当业务需求长期超出清单范围、而清单维护速度跟不上时，「口径可控」反转成「不可用」，团队会打开一条自由生成的旁路——而一旦存在旁路，口径治理就回到原点，因为使用者在拿不到答案时会走旁路，而旁路的错误不会回流到清单。判定方法：统计未命中指标而拒答的比例，并检查是否存在绕过语义层的直连查询。
- **真实使用**：【公开】本章 § 6 阿里瓴羊案例的做法是「先把指标语义层立住，生成的查询必须落在已定义的指标上」（[阿里公开材料 2020-2024]，见 § 6）；【公开】本章 § 7 指出「自然语言 → 指标语义层 → SQL」而非「自然语言 → SQL」是 § 6 四个案例的共同做法。

#### 3.2.7 RAG + SQL 混合

- **被什么约束逼出来**：同一批问题里既有「文本里有没有写」（口径说明、制度、定义），也有「库里有多少」（聚合数字），两类问题的最优检索路径不同——约束是**事实来源必须被显式区分**。
- **结构**：一次可观测的意图分流 + 两条互不越权的执行路径。

```text
RAG + SQL 的结构：可观测的分流 + 不越权的事实来源
  问题 → 意图分流（输出标签：文本题 / 数据题 / 混合题；标签必须落日志）
    ├─ 文本题 → 向量检索 → 生成（只引用召回片段，附出处）
    ├─ 数据题 → 语义层 → SQL → 沙箱执行（只引用结果集）
    └─ 混合题 → 先取数：SQL 结果成为唯一数字来源
                 再取文：口径说明与制度用于解释数字
                 生成时必须标注哪句来自结果集、哪句来自文档
  约束：数字只能来自结果集，文档只能解释数字
    这条边界不能交给模型自裁 —— 一旦让模型决定「用文档里的数」，可核验性归零
```

- **为什么这样设计有效**：因为两条路径各自的事实来源被写死，所以答案里的每个数字都能回溯到一条可重跑的查询，进而可以进需要签字的流程。
- **代价**：多一次分类调用，且分类错误率直接成为整体错误率的下限（分类错则两条路都白走）；混合题的生成要维护「哪句来自哪里」的标注，这要求结果集与召回片段都带来源标识。
- **失效点**：当问题里文本与数字的边界本身模糊（「为什么按上次定的口径看这个数不对」）时，分流反转成瓶颈，因为这类问题需要的是先澄清而不是先分类——表现为系统在两条路之间来回摇摆给出两个都「有依据」的答案。
- **真实使用**：【公开】LangChain 于 2023 年推出 SQL Agent 模板（本章 § 1.4 演进时间线记为 2023-07），是把 SQL 作为结构化查询工具接入检索链路的公开形态之一（本章 § 4.5 模板 1 即基于该模板；可按其官方文档当前版本核验）；【经验】企业里更常见的落点是「制度问答」与「取数」两个入口并存，而不是一个入口硬做分流。

#### 3.2.8 Self-Ask + Tool-Use

- **被什么约束逼出来**：工具会持续增加（BI、Python、通知、外部 API），把工具选择写死在流程里就无法扩展——约束是**能力扩展不能要求改流程**。
- **结构**：工具注册表（描述即约束）+ 自问 + 调用 + 观察。

```text
Self-Ask + Tool-Use 的结构：工具表就是能力边界
  工具注册表的每一项都是可被判定的契约：
    name          名称（唯一）
    when_to_use   正向描述 + 负向描述（什么时候不要用）← 负向描述决定选错率
    input         结构化参数 schema（不接受自由文本）
    returns       返回结构（决定模型能否继续推理）
    cost / latency 让模型在「贵而准」与「便宜而粗」之间取舍
  循环：自问 → 选工具 → 调用 → 观察 → 继续自问，直到已可回答或无工具可调
  约束：工具描述由工具维护者写；描述变更等同 prompt 变更，必须回归测试
```

- **为什么这样设计有效**：因为工具集与流程解耦，所以新增一项能力只需注册一个工具而不用改装流程；把「什么时候不要用」写进描述，是压低选错率最便宜的手段。
- **代价**：选择面扩大后选错率上升，而选错的代价往往高于「工具不够用」——它不报错，只是安静地用错了工具；工具描述需要专人维护，且描述的措辞变化可能改变线上行为。
- **失效点**：当多个工具的描述高度重叠（两个工具都能查指标）时，「可扩展」反转成「不确定」——语义相近的选项上模型的选择不稳定，表现为同一个问题两次问得到两条路径、两个答案。判定方法：同一批问题重复跑 N 次，统计工具选择的一致性，不一致的工具对先合并或写明分工。
- **真实使用**：【公开】主流模型厂商自 2023 年起提供函数/工具调用接口（可按各厂商官方文档当前版本核验）；【经验】工具数超过十余个之后，常见做法是先做一层工具路由（分组）再让模型在组内选，以压住选择面。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 单指标点查、问题可枚举 | Metric-First + ReAct | 不选 Multi-Agent：拆分省下的是排障时间，点查不需要排障 | 问题是否落在已声明指标内 |
| 多步归因、维度可并行 | Plan-and-Execute + Reflexion | 不选纯 ReAct：一个上下文装不下多分支观察 | 计划的维度覆盖面能否被抽查 |
| 口径已治理、指标数百以上 | Metric-First（强制） | 不选裸生成：口径错误不报错、只算错 | 未命中指标时系统会不会拒答 |
| 有执行反馈、有业务规则 | Reflexion（必选）+ 沙箱 | 不选单轮生成：错答案与对答案长得一样 | 重试上限与失败原因分类是否已写死 |
| 强合规、含不可逆动作 | Human-in-the-Loop + 沙箱 + 审计 | 不选全自动：不可逆动作无法事后补救 | 闸门触发条件是否可自动判定 |
| 文本与数字混合的消费场景 | RAG + SQL（显式分流） | 不选单一入口硬做：数字的可核验性会归零 | 数字是否只来自结果集 |
| 多业务线共用平台 | Multi-Agent + 工具路由 | 不选单体 ReAct：职责互相拉扯，出错不可定位 | 故障能否定位到具体一段 |
| 工具持续增加、外部 API 多 | Self-Ask + Tool-Use | 不选把工具写进流程：每加一项都要改流程 | 工具描述是否含「什么时候不要用」 |

表里最常被误选的一对是 **ReAct 与 Multi-Agent**：团队在只有一个业务线、问数场景以单指标为主时先上了多 Agent，理由通常是「更准」。机制上多 Agent 并不提高单步生成的准确率——它提高的是**故障可定位性**，而可定位性只在链路长、职责冲突时才值钱。误选的实际后果是成本与延迟先涨 5-7 倍（【经验】量级），而准确率基本不动；更隐蔽的代价是排障对象从「一次生成」变成「七段链路」，团队开始怀疑 Router、Schema、Validator 每一段，最后发现问题只是模型本身就不擅长这类表。正确的顺序是先跑单体 ReAct + Reflexion 拿到基线，只有当「同一类错误反复出现在同一段职责上」时，才把那段职责拆出去。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Metric-First + Reflexion + 沙箱（生产地板）**。职责边界：语义层负责「能生成什么」（把生成空间收窄到已声明指标），Reflexion 负责「错了能不能发现」（用执行反馈与业务规则纠错），沙箱负责「越界了会怎样」（只读账号、行级权限、超时、行数上限、敏感列脱敏）。运维代价是语义层需要有人维护口径版本与 Owner，反思与重试日志需要存储与定期审阅（否则纠错链路无人验证）。适合规模：指标清单可达数百、已经有数据治理职能的中大型企业。

**组合二：ReAct + Reflexion + Human-in-the-Loop（合规场景）**。职责边界：ReAct 产出可审计的推理与取数链路，Reflexion 用执行反馈收窄失败面，HITL 只挂在不可逆动作与敏感数据上。运维代价是人工等待进入 SLA（审批人的响应时间成为系统延迟的一部分），且闸门阈值需要定期校准——过严会形式化，过松会漏放。适合规模：金融、医疗、政务等对取数与披露有硬性合规要求的场景。

**组合三：Multi-Agent + 工具路由 + RAG 分流（平台化）**。职责边界：Multi-Agent 按职责切分并把产物结构化，工具路由负责把持续增长的工具集分组以压住选择面，RAG 分流负责把文本类问题挡在数据链路之外。运维代价是调用次数成倍增加、需要完整的可观测设施（每条链路的分段延迟与成本都要可见），以及三套组件的版本需要一起回归。适合规模：多业务线共用、日问数在万级以上的平台【经验】量级。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 黑盒 SQL 生成 | 日志里只有最终 SQL，没有候选表、没有校验结论 | 错表与越权取数都无法在发生前拦截，且事后无法复盘 | 先把「能跑通」做出来，治理被排到后面 | Schema Linking → 校验 → 权限 → 沙箱 → 审计五步都进链路 |
| 无指标语义层 | 同一问题两次问出不同口径的数 | 口径分歧被执行成两个都对的答案，业务方失去信任 | 语义层建设周期长，先上自然语言更快出效果 | 强制走语义层；未命中即拒答，不用自由生成兜底 |
| 忽视沙箱执行 | 执行账号可写、无超时、无行数上限 | 一次误写或一次大扫描即可造成生产事故或拖库 | 用同一个业务账号跑通链路最省事 | 只读账号 + 行级权限 + 查询超时 + 行数限制 + 敏感列脱敏 |
| 单轮 SQL 生成 | 执行成功即回答，失败即报错给用户 | 语法正确、语义错误的答案会被当成结论使用 | 单轮实现最简单，且演示效果好 | Reflexion 强制回灌执行反馈；错误按原因分类并设终止条件 |
| 盲目追求准确率 | 绝大部分时间花在调提示词上（【经验】量级：约 80% 的精力换来几个百分点的准确率提升），业务流仍然不通 | 演示漂亮而生产不可用，高频问题未被优先解决 | 准确率是最容易量化的指标 | 先闭环约 80% 的高频问题（【经验】量级），剩余约 20% 用拒答或 Human-in-the-Loop 兜底 |
| 忽视指标血缘 | 用户问 GMV，实际查到的是支付金额一类的近似口径 | 口径错误无法被解释，也无法被追溯修复 | 血缘被当成治理部门的文档工作 | 指标血缘可视化 + 指标 Owner 制度 + 业务规则校验 |
| 成本失控 | 单次问数触发十几次模型调用，账单单月跳升 | 成本随问数线性上涨，且与业务价值不挂钩 | 调用次数是设计期的选择，运行时才发现 | 模型分层（分类与校验用小模型）+ 缓存高频问题 + 批处理 + 调用次数上限 |
| 无评估体系 | 上线后说不清准确率，也说不出错在哪类问题 | 无法判断一次改动是变好还是变坏，迭代靠感觉 | 评估集建设枯燥，且不能直接产生功能 | 固定评估集（BIRD / Spider 一类公开基准 + 内部真实问题）+ 人工抽检 + LLM-as-a-Judge 批量打分 + 用户反馈闭环 |

三条最危险的展开：

**「黑盒 SQL 生成」的暴露方式**：它不以「出错」暴露，而以「错得很合理」暴露。模型生成了语法正确、能跑通、甚至口径也接近的 SQL，唯独查的是业务库而不是数仓，或者用了某个已下线的表——没有任何一步会报错。判定方法是看日志里有没有**候选表与校验结论**这两个中间产物：只有最终 SQL 的链路，等于没有留下任何可复盘证据。

**「无指标语义层」的暴露方式**：它在跨团队对账时暴露：运营与财务对同一个指标各问一次，两次查询都跑通、都正确，得到的却是两个不同的数（【经验】这类分歧在跨部门对账时最容易被发现）。机制上，自由生成把口径分歧从「治理问题」变成了「模型的随机选择」，而分歧一旦进入答案就不可逆——业务方会先怀疑数据，再怀疑系统，最后不再使用。修法只有一条结构性的：把口径写成机器可读的指标定义，让生成空间里根本不存在第二种算法。

**「无评估体系」的暴露方式**：它不表现为事故，而表现为**迭代停滞**：每一次提示词改动都只能靠几个人试几个问题来验证，改动越多，越没人敢动。机制上，没有固定评估集就没有回归信号，团队只能凭最近几个印象深的案例做决策，于是系统在「看起来一直在优化」和「实际上停在原地」之间没有可分辨的差别。修法的四件工具各管一段，少一段就会退回人工试错：**固定评估集**给回归信号（公开基准负责横向可比、内部真实问题负责贴近业务）；**人工抽检**覆盖评估集自己没写到的问题类型；**LLM-as-a-Judge**（按该名称可检索到公开表述）把「这个答案对不对」批量化打分，使评估规模从几十条扩到成百上千条——但它自己也需要定期抽样人工复核校准，否则评分器的偏差会变成系统的偏差（【经验】）；**用户反馈闭环**负责发现线上新冒出来的问题，并把它们回灌进评估集。

### 3.6 规模跃迁时模式何时该换

下表阈值为【经验】量级，用于判断「什么时候该换」，不是硬性分界。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单库百表 → 千表多库 | 裸 Text2SQL 直读全 schema | schema 放不进上下文，选表错误率随表数上升 | Schema Linking 前置（先出候选集再生成） | 候选生成本身会漏表，漏掉的表表现为「系统说没有这张表」 |
| 无口径治理 → 指标数百 | 自由生成 | 同一问题多种算法，答案互相打架 | Metric-First（未命中即拒答） | 指标清单需要 Owner 与版本机制，建设期系统看起来更弱 |
| 无合规 → 有合规 | 自动执行 + 事后审计 | 越权取数与不可逆动作无法事后补救 | HITL 闸门 + 沙箱 + 审计留痕 | 人工等待进入 SLA，触发过宽则闸门形式化 |
| 单轮问答 → 多步分析 | 单体 ReAct | 上下文与重试成本随步数失控 | Plan-and-Execute + 子任务隔离 | 规划错误被下游全面继承，需单独抽查维度覆盖 |
| 单团队 → 多业务线平台 | 单体 ReAct | 一份提示词装不下互相冲突的职责，故障不可定位 | Multi-Agent 拆分 + 工具路由 | 调用次数成倍上升，需要完整可观测设施 |
| 日问数千级以下 → 万级以上 | 每次全量调用大模型 | 成本与延迟随问数线性上涨 | 模型分层 + 缓存高频问题 + 批处理 | 小模型承担分类与校验，引入新的错误面需单独评估 |
| 演示 → 生产 | 人工看几个典型案例 | 改动无法判断是变好还是变坏 | 固定评估集 + 回归 + 用户反馈闭环 | 评估集建设与标注成本，且需要长期维护防过期 |

### 3.7 自检清单

- [ ] 生成的 SQL 有没有可能引用未在语义层声明的指标？可能即违反口径纪律。
- [ ] 日志里是否留有 Schema Linking 的候选集与入选理由？没有候选集记录，选表错误无法复盘。
- [ ] Reflexion 的最大重试次数是否已写死在配置里？无上限的重试等于无上界的成本。
- [ ] 重试是否按失败原因分类？权限不足、数据缺失、口径类失败（分歧或未定义）这三类重试不会成功。
- [ ] 执行账号是否只读，且配了行级权限、查询超时与行数上限？缺一项即违反沙箱纪律。
- [ ] 敏感列是否在进入模型上下文之前就脱敏？在展示层脱敏时，敏感值已经进过上下文。
- [ ] HITL 的触发条件能否被自动判定？靠「感觉重要」触发的闸门会被绕过或被形式化。
- [ ] 审批的通过率与审阅时长是否被统计？通过率长期高于 95%（【经验】阈值）说明闸门已成橡皮图章。
- [ ] 语义层的每个指标是否有 Owner 与版本号？没有版本的指标，口径变更会污染同比。
- [ ] 上一次改动后是否跑过固定的评估集？没有回归就无法判断改动的方向。
- [ ] 单次问数的模型调用次数与 token 成本，是否记录在可查询的地方？没有成本数据就无法做分层设计。
- [ ] 回答里的数字是否全部来自结果集，解释性文字是否标注了来源？混在一起时读者无法分辨哪句可核验。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 问题可枚举、口径已治理 | Metric-First + ReAct | 生成空间收窄到已声明指标，错误从静默算错变成明确拒答 |
| 任务多步、维度可并行 | Plan-and-Execute | 子任务独立上下文，单点失败可重跑、不污染其他分支 |
| 有执行反馈可用 | Reflexion（必选） | 用外部客观信号纠错，可靠性不再只取决于模型水平 |
| 强合规、含不可逆动作 | Human-in-the-Loop | 闸门挂在动作上，风险在发生之前被处理并留痕 |
| 文本与数字混合消费 | RAG + SQL 混合 | 两类事实来源被显式区分，数字可回溯到可重跑的查询 |
| 多业务线、职责冲突 | Multi-Agent Data Analyst | 每段职责有输入输出契约，故障可定位到具体一段 |
| 工具集持续增长 | Self-Ask + Tool-Use | 工具与流程解耦，新增能力不改流程 |

> 本节小结：决定模式选择的唯一那条约束是**「SQL 的生成空间被约束在哪一层」**——裸 schema、语义层、还是根本不生成 SQL，这一层定下来，错误的形式（静默算错 / 明确拒答 / 可复现失败）就定了，其余模式都是在这条约束之上做的工程补充。在这条约束之外，真正决定能不能进生产的是两件事：**执行反馈是否被回灌**（不回灌时，错误率的上限与裸 Text2SQL 相同），以及**权限与不可逆动作是否在执行层被强制**（提示词不是权限系统）。
