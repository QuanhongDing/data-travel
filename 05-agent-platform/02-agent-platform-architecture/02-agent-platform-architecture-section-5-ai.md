## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

平台层近两年的变化，只有三类值得讨论，混在一起谈必然得出错误结论：

1. **机制变了**：平台的某个部件换了工作原理（例如状态从"进程内存"变成"可恢复的持久化执行"）。**这类变化会影响架构决策**，值得跟。
2. **接口标准变了**：工具 / 资源 / 提示的接入从"每家自己定"变成"协议化"（工具协议一类）。**这类变化的实质是把集成成本从平台转移到协议层**，影响的是"该自研还是该消费生态"。
3. **只多了产品**：厂商把同一套能力包装成新名字。**这类变化只在选型表里体现，不该进架构图**。

判别方法：**问"如果换一家厂商，我刚才记下的这条结论还成立吗？"**——不成立的是第 3 类。

**这个三元分类本身是一个可执行的过滤器**，因为平台层的噪声比模型层更大：模型层的新名词通常伴随能力边界的变化（上下文长度、工具调用、结构化输出），而平台层的新名词大量来自**产品包装**——同一个"控制面 / 数据面分离"在三年里被不同厂商分别命名为"Agent Studio""AgentOps""Agent Control Plane"。**去掉厂商名之后还剩下的那句话，才是本节该讨论的东西。**

三类变化的处理方式不同：第 1 类要**改架构**（例如为持久化执行引入检查点存储），第 2 类要**改成本结构判断**（例如决定"不再自建工具生态、改为治理做深"），第 3 类只改**选型表里的一行**。把第 3 类当第 1 类处理，代价是引入一套没有机制差异的新组件；把第 1 类当第 3 类处理，代价是两年后被动重构。

### 5.2 判据与分级

本节沿用本书的三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定，可预期**。三条全中才是 **L1 生产可用**；只满足部分、或只有建设方 / 厂商自有材料的是 **L2 可试点**；只有路线图、演示或论文的是 **L3 观望**。

| 演进方向 | 级别 | 机制变了什么 | ① 正式条目 | ② 第三方生产案例 | ③ 接口稳定 |
| --- | --- | --- | --- | --- | --- |
| 控制面 / 数据面分离 | **L2** | 从"一个进程既存定义又执行"变成"定义与执行分离、发布指针可回滚" | 成立（主流平台产品文档都以此组织） | **核不到**：企业内部平台很少公开"多租户隔离怎么做、超发怎么拦" | 成立（发布 / 回滚是产品级接口） |

| 多 Agent 分工与仲裁 | **L3** | 从"单 Agent 规划"到"多 Agent 分工、冲突仲裁" | 只有框架与演示 | 核不到 | 不成立（无通行做法） |
| 平台级评估与回放 | **L3** | 从"看日志"到"按会话回放、按版本对拍" | 只有自研实现与厂商演示 | 核不到 | 不成立（回放语义各家不同） |

**本节没有一行达到 L1**——卡点全部在 ②：**Agent 平台的生产案例几乎都是建设方自述**（企业内部平台很少公开"多租户隔离怎么做、配额超发怎么拦"这类细节）。这个空缺本身是结论：平台层的公开证据形态是**机制性材料**（产品文档、规范、架构说明），而不是运行数据；读者据此判断成熟度时，应把它当作"可验证的机制"而非"被第三方验证过的生产经验"。

**怎么用这张表（三条动作）**：

- **要写进架构约束的，只取 ①③ 都成立的**——它们保证"接口不会明天消失"，这是架构约束的最低要求。
- **要排进试点计划的，取 L2**——但试点必须自带退出条件（§5.7 给了每条方向的退出判据），因为 ② 的空缺意味着**没有人替你验证过它在你的规模下会不会变形**。
- **L3 的不进架构图**——不是因为它不好，而是因为它还没有"可比较的通行做法"，写进架构约束等于把一家的私有约定当成行业标准。

### 5.3 演进方向逐条拆解（核心节）

下面这些方向（§5.3.1–§5.3.6）按**同一套六线结构**写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**；**它们各自的级别见 §5.2 的那张表**——表给结论，本节给机制。只写收益不写代价的方向，在评审时应被直接打回；每条方向的 `成熟度` 一栏必须按 ①②③ 三条判据逐条说，**不允许把 §5.2 已判为"核不到"的那一条在本节悄悄写成成立**。遇到本节没列到的新名词，用 §5.2 的三条动作自己判。

#### 5.3.1 控制面 / 数据面分离：换的是"变更的落点"，不是运行时的能力

**旧做法与它的卡点**：定义（Agent、提示、工具注册、路由、配额）与执行（会话调度、模型与工具调用）同处一个部署单元——改提示等于重启运行，回滚要重新打包并重新预热；同一提示在不同环境行为不一致时，答不出"哪次改动影响了哪一个会话"（这正是 §3.5"把平台做成一个大 Demo"这条反模式的机制：发版＝改配置重启）。

**AI 改变了什么机制**：**机制确实变了——变更的落点从"部署"移到了"指针"**。原因是 Agent 的行为由四个可独立版本化的量共同决定（版本四元组 `(编排定义, 提示, 模型 / 路由, 工具集版本)`），而提示与模型路由每天都在改、正在跑的会话又不能中断；把"定义"整体上收进一个面之后，**"变更"不再等于"重新部署"**，发布与回滚都只是改控制面里的一个指针。这条机制有两个直接推论：**灰度的实现位置**可以在不改执行体的前提下按租户 / 会话分流，因此灰度策略与代码打包彻底解耦；**审计的对象**收敛成控制面的变更流，而不需要拼执行体的日志——后者的字段设计落在 §4.2（3）的 `agent_step` DDL 与 §4.5 模板 5 的那条留痕查询上。

**由此得到的**：**回滚的时间尺度**从"分钟级重新部署（且需要重新预热）"变成"秒级改指针"——而且这个"秒级"不是优化出来的、是结构决定的（改指针是常数时间，与部署时长无关）；多渠道 / 多环境行为不一致时有了唯一的比对对象（控制面变更流）；发布频率可以提到每天多次而不触发一次部署。

**由此付出的**：两条都要写进设计。① 分离**不**解决"正在跑的会话怎么办"——正在跑的会话必须**钉住启动时的版本四元组**，否则中途换版本会让行为不可解释；这一点在产品文档里通常不会强调，但它是复盘的唯一依据（§3.2.3 的失效点）。② 控制面自身成为关键路径上的单点，要做多副本 + 变更留痕 + 变更审批；并且**"控制面挂了，新会话发不出去、老会话还能跑"这个降级形态必须被设计出来而不是被发现**——可核查的做法是**真关一次控制面**，观察已建立的会话是否继续执行、并给出发起新会话时的明确错误码。

**证据与来源**：【公开】主流平台产品文档都按"定义 / 执行"组织界面与 API——本主题 §6.1 记微软把构建侧与运行侧分成两组公开接口（[微软公开材料 2019-2024]，核验入口是该产品官方文档，**按当前版本核**）；§6.3 记扣子 Coze 的构建块 + 发布渠道清单（[字节公开材料 2023-2024]）。② **核不到**（见 §5.2 的卡点：企业内部平台很少公开"多租户隔离怎么做、超发怎么拦"）。【经验】"分钟级 → 秒级"只有量级与条件、没有具名出处——请以你自己最近十次变更的端到端时长为准。

**成熟度**：**L2**。① 成立（有主流平台产品文档条目：§6.1、§6.3 各一例）；② **不成立**（第三方非厂商生产案例核不到——§5.2 已写明，本节任何单元都不得把它悄悄抬成成立）；③ 成立（发布与回滚是产品级接口，不是自研技巧）。

**判定方法**：把最近三次 Agent 行为变化找出来，逐次回答"它对应哪个版本四元组、回滚要多久"。两次以上答不上来，说明变更落点还没移过来——先补版本指针，不要先补别的。

#### 5.3.2 工具协议化：集成成本从平台转移到协议层

**旧做法与它的卡点**：每个平台各自定义工具接入格式（名称怎么描述、输入 Schema 怎么写、能力语义怎么表达），接入工作因此变成"每家自己拉生态"的项目工作；同一能力在 `N` 个平台各实现一遍，治理四项（权限 / 配额 / 审计 / 幂等）散落在各自的实现里。卡点不在于"格式不好"，而在于**接入成本随平台数线性增长，而治理质量随实现数线性下降**。

**AI 改变了什么机制**：**机制与 AI 无关**——这一条改的是**接口标准**（§5.1 的第 2 类），它不改变会话怎么跑、不改变调用链上的任何一个部件，也不改变数据的产生方式（协议侧的具名载体与公开时点见 §4.2（5）与 §8 参考资料）。它仍列在本节的理由是：它**改变了架构决策的成本结构**——自研平台在"要不要做工具生态"这件事上的判断被换掉了。

**由此得到的**：**平台的差异化从"接入多少工具"转向"治理做得多严"**（权限、配额、审计、幂等）。这是一次**价值重心的迁移**，它同时改变两件事的优先级：**自研的边界**——不必再自研"工具描述格式"，可以直接消费协议，因此自研清单上应该划掉"工具 SDK 与接入规范"这一项；**第三方工具一次实现、多处可用**，接入成本从"平台数 × 单次接入"降到"单次接入 + 平台数"。

**由此付出的**：协议里没有的部分——**权限（谁能调）、配额（能调多少）、审计（调了什么）、幂等（重调一次会不会重复）**——恰好是治理面的全部内容。**协议把集成标准化了，同时把治理的空白留给了平台。**只做协议接入不做治理，会得到一个"什么都能调、什么都不知道"的平台（§3.5 的旁路反模式的协议版本）。此外规范仍在演进，跨实现兼容要靠适配层；架构假设不能压在某个协议版本上。

**证据与来源**：【公开】协议规范与实现均公开，本主题 §8 参考资料把这个协议一类记为**由 Anthropic 于 2024 年公开**；核验入口是规范官方页面，**按当前版本核**——具体的版本与发布时间**本节不给**，一律以规范官方页面的当前版本为准。② 核不到。

**成熟度**：**L2**。① 成立（规范与实现均公开，有正式文档条目）；② **不成立**（核不到第三方非厂商生产案例）；③ 部分成立（规范仍在演进，接口按版本变化）。

**判定方法**：随机挑一个已接入的工具，回答"哪个租户在什么时候调过它、调了多少次、超配额时会发生什么"——三问答不全，说明协议接入跑在了治理前面。

**什么时候值得做**：需要接第三方工具生态、或已经在多个平台上重复实现同一能力时——这时省下的是双份维护成本。

**什么时候不值得做**：工具清单里全是一个平台内的私有能力、且治理四项还没做齐时——先补治理，再谈协议。

**读者今天该做什么**：把现有工具清单按"协议已覆盖 / 平台私有"分两栏。协议已覆盖的那一栏，检查是否已经**从平台的私有格式迁到协议**（没迁的话，你付出的是双份维护成本）；平台私有的那一栏，检查四项治理是否齐全。

#### 5.3.3 持久化执行：把"跑得久"变成"可恢复"

**旧做法与它的卡点**：长任务在进程内一次跑完——进程崩溃即失败，而且**没有恢复语义**；重试只能整段重来，而整段重来会把前面所有步骤一起重放（包括那些已经生效的写操作）。卡点因此不是"跑得慢"，而是**"跑得久"与"进程的寿命"被绑在了同一条时间轴上**。

**AI 改变了什么机制**：**是机制变化**——"一步 = 模型调用 + 工具调用"这个组合体被做成可持久、可重放的步骤，进程崩溃后从最后一步续跑（原机制句：长任务从"进程内循环"变成"可恢复的步骤执行"）。**由此"重试"从异常路径变成了常规路径**，于是幂等键的覆盖范围必须与持久化范围一致——持久化到第 `k` 步，就意味着第 `1…k` 步都可能被重放；如果幂等键只覆盖了写操作而没覆盖"有副作用的外部调用"（发送通知、调用收费 API），恢复时就会产生重复副作用（§2.3）。

**由此得到的**：长任务（`S × T` 大）从"必须一次跑完"变成"可以跨重启、跨版本升级"；**人工节点与外部回调的等待时段第一次可以被表示与恢复**（这与 §6.2 的 `requires_action` 是同一机制：等待是状态，不是异常）。这也是它区别于"定时任务"的地方：恢复点落在**步骤**上，而不是落在**整次运行**上。

**由此付出的**：状态写入不是免费的，本主题给了两处量级——§3.2.2 的"每步一次写"给出 10 万会话 × 每会话 8 步 ≈ 80 万步/日【推算：口径为会话数 × 步数】；本节给出日写入量约 `1.6–8 GB`【推算：10 万 × 8 = 80 万步，每步 `2–10 KB`；每步可能落 1 次检查点 + 1 次状态迁移，实际按你选的引擎语义打折，读者可换自己的会话数与单步字节数重算】。此外还有引擎自身的运维面、版本升级与状态迁移成本。**因此判据不是"能不能算得过来"，而是"会话是否需要跨小时存活"**——短会话引入它，收益不抵复杂度。

**证据与来源**：【公开】持久化工作流引擎的官方文档为正式条目（本主题 §4.3 工具链表"长任务与持久化执行"一行把它记为"持久化工作流引擎（可恢复的步骤执行）"）；同类引擎的**产品级具名**见全书他处——`03-data-stack/07-architecture-decisions/07-architecture-decisions-section-8-sec8.md` 的第四层"云原生调度演进"把 Temporal 记为"分布式工作流引擎，高复杂度 + 多步骤场景首选"。② 本主题给不出第三方 Agent 场景案例——**引擎本身有生产案例，"用引擎跑 Agent"没有**；这也是它停在 L2 而不是 L3 的原因：失效模式可推演，不是未知。

**成熟度**：**L2**。① 成立（引擎官方文档为正式条目）；② **不成立**（核不到第三方 Agent 场景案例）；③ 成立（恢复语义是引擎的一等接口）。

**什么时候不值得做**：会话墙钟时长的 P99 仍在分钟级以内时，先不要引入——引擎的运维面与状态迁移成本会在你还没需要它的时候就先付掉。

**读者今天该做什么**：统计会话的墙钟时长分布（P50 / P95 / P99）。**若 P99 仍在分钟级以内，先不要引入持久化执行**；若存在跨小时的长任务，先做一件事——**故意杀一次执行体**，看这些长任务是失败、重跑，还是从断点续跑。答案决定你是在补幂等，还是在补恢复语义。

#### 5.3.4 Agent 可观测：字段约定比工具更重要

**旧做法与它的卡点**：Trace 的字段各平台自定义，选观测后端时比的是"功能多少"；于是三件事同时做不到——成本只到总额（到不了会话）、回放只能靠日志拼（拼不出当时看到了什么）、出口旁路在观测侧完全看不见（旁路本来就绕过了出口）。卡点不在观测工具的能力，而在**没有一套共同的字段**。

**AI 改变了什么机制**：**机制与 AI 无关**——这一条改的是**字段的归属与切分粒度**（谁定义、按什么粒度切分会话 / 步骤 / 模型调用 / 工具调用），**不改变数据的产生方式**，因此属 §5.1 第 2 类。它仍列在本节的理由是：它决定了三项平台特有能力能不能实现——**成本归因到会话**需要"步骤"这一段携带 token 与实际模型档位；**回放与对拍**需要"模型调用"这一段携带提示版本与解码参数；**旁路检测**需要"工具调用"这一段携带出口标识（§3.2.4 的失效点就是靠它与目标系统日志对账发现的）。

**由此得到的**：跨平台对比与跨团队排障有了共同字段——换后端时"是否支持这套字段"第一次成为一个**可比条件**，而不是营销口径；三项平台特有能力（成本归因、回放、旁路检测）有了统一的落点，不必各写一套埋点。

**由此付出的**：约定是**最小集**，不是能力上限——**不要把"符合约定"当成"可观测做完了"**：成本 SLO、回放、留痕这些平台特有的东西，约定里没有。反过来，也不要为了实现约定里没有的字段而自造一套与约定冲突的命名，那会让"跨平台对比"这个唯一收益消失。此外约定仍在补充，字段会增，埋点要按版本维护。

**证据与来源**：【公开】观测领域的语义约定文档可核（本主题 §4.3 工具链表"可观测"一行记为"OpenTelemetry 语义约定 + 追踪后端"）；全书他处见 `04-data-assetization/09-unified-query-gateway/09-unified-query-gateway-section-8-sec8.md` 的 §8，用 OpenTelemetry 把 Agent → 网关 → Connector 全链路 trace 起来，审计 Agent ID、用户、SQL、命中行数与异常标记。**约定的名称、字段清单与版本本节不给**，一律以官方文档当前版本为准。② 核不到。

**成熟度**：**L2**。① 成立（观测领域的语义约定文档可核）；② **不成立**（核不到第三方非厂商生产案例）；③ 部分成立（约定仍在补充，字段会增）。

**判定方法**：从留痕 / Trace 里抽一次会话，问三个问题——"这次会话花了多少、用的哪个提示版本、有没有工具调用绕过出口"。三问分别对应"步骤""模型调用""工具调用"三段；答不出哪一问，就是哪一段的字段没带。

**读者今天该做什么**：拿一次真实的排障记录，回答"我是靠哪几个字段定位的"。如果答案里没有"步骤"与"版本"，说明你的 Trace 只做到了"有链路"，没做到"能归因"——先补字段，再谈换后端。

#### 5.3.5 沙箱执行：把不可信代码关进一次性环境

**旧做法与它的卡点**：把"让模型写代码"当成禁区直接否决，理由是**爆炸半径不可控**；或退一步，在宿主进程内直接执行（此时一次 `rm` 或一次越界读取就等于整台机器失守）。卡点在于：**当时能给出的选项只有"全禁"与"全放"两种，没有中间形态**，于是这类能力要么不做，要么在不受控的环境里做。

**AI 改变了什么机制**：**是机制变化，而且是准入条件的变化**——不可信代码的爆炸半径从"宿主能碰到的一切"收窄到"你显式挂进去的东西"，于是"能不能写代码"从**安全决策**变成**工程决策**。**但必须点明边界**：收窄的是**挂载面**，不是隔离技术本身（§3.2.8 的判据：只做隔离强度不做挂载面，等于给一台能访问内网的机器上了锁但把钥匙插在门上）；而且沙箱给出的是**进程级隔离，不是数据级隔离**。

**由此得到的**：模型生成的代码在隔离环境内执行，环境本身是"**无长期凭证**（临时凭证、最小权限）+ **有资源上限**（CPU / 内存 / 时限 / 出网白名单）+ **用完即毁**"这三件的组合（§3.2.8 的四件套）；由此模型生成代码的探索能力可以进生产路径（但必须与取数链路分开配额与审计）；可行的工程形态是**分池**——低敏资源走容器池（预热、低延迟），高敏资源走强隔离池（按需启动、接受延迟）。**判据是"代码触达的资源是否敏感"，不是"统一用最强隔离"。**

**由此付出的**：**隔离强度与冷启动延迟直接冲突**——容器级 `百毫秒–秒级`、微虚拟机更高【经验】，这是一个没有双赢的取舍。此外：镜像与依赖必须随版本四元组一起发布，否则回滚会话时找不回当时的执行环境；出网白名单与挂载面清单是常驻运维负担（不限制出网等于把沙箱变成一台能访问内网的跳板机）；模型生成的代码如果能读到挂载进来的凭证或文件，隔离强度再高也没用——**因此"给沙箱挂什么"比"沙箱用什么技术"更决定安全性。**

**证据与来源**：【公开】隔离运行时的官方文档为正式条目（本主题 §4.3 工具链表"执行与沙箱"一行记为"容器编排 + 沙箱运行时"）。**具体实现形态全书他处已具名**：同章 §01 的 Python 沙箱一节把"E2B 一类云沙箱、阿里 Code Interpreter 一类云函数 + 隔离容器、OpenInterpreter 一类本地执行"并列为三种形态（`05-agent-platform/01-data-agent/01-data-agent-section-4-sec4.md` §4 第 7 项）；`04-data-assetization/09-unified-query-gateway/09-unified-query-gateway-section-8-sec8.md` §8 第四层记 Databricks 的 SQL Sandboxing 与 Snowflake 的 Always On RBAC；`07-agent-evolution/04-agent-skill-extraction/04-agent-skill-extraction-section-6-sec6.md` §6.2 记 Cognition Devin 的 Docker 沙箱。**沙箱运行时本身的产品名（微虚拟机一类）本节不给**，请以隔离运行时官方文档的当前版本为准。② 本主题不给第三方生产案例。

**成熟度**：**L2**。① 成立（隔离运行时是成熟且有文档条目的能力）；② **不成立**（本主题不给第三方生产案例）；③ 成立（隔离运行时的接口稳定）。**这类能力的成熟度不能按"有没有沙箱"判断，只能按"隔离强度与凭证管理是否都做了"判断**——只做隔离不做凭证，沙箱就变成一台能访问内网的跳板机。

**判定方法**：做一次"逃逸演练"——在沙箱里跑一段尝试读宿主文件、尝试解析外部域名、尝试用挂进来的凭证访问内网服务的代码，看三件事分别被哪一层拦住；拦不住的那一层就是缺挂载面清单的地方。

**读者今天该做什么**：列出模型生成代码能触达的资源清单（网络、文件、凭证、数据库），逐项问"它真的需要吗"。这一张清单就是沙箱配置的全部依据。

#### 5.3.6 多 Agent 仲裁与平台评估：为什么停在 L3

**本单元含两条方向，级别都是 L3，但降级理由不同**（§5.2 的表里它们本就是两行，各自的判据落点也不同）。下面按同一套六线结构分别写。

**A. 多 Agent 分工与仲裁（L3）**

**旧做法与它的卡点**：单 Agent 的规划循环处理不了需要分工的复杂任务；勉强拆开之后，分歧靠"让模型再讨论一轮"解决——**没有轮次上界，也没有升级规则**，于是 token 成本失控、结论不可复现（§3.5 的"多 Agent 无限互相修订"正是这条反模式）。

**AI 改变了什么机制**：**是机制变化**——从一个规划器变成"多个执行体分工 + 冲突仲裁"。但可核验的机制材料**只到框架文档层**：没有"两方分歧时按什么顺序收敛"的标准答案，各家的规则不可比。

**由此得到的**：今天能拿到的最小版本只有两件——① **优先用确定性仲裁规则**（谁能改文件、谁只能建议、冲突时按什么顺序），只有分歧不可枚举时才让模型仲裁；② **必须显式设轮次上界**，超界升级给人（§2.3）。

**由此付出的**：把 L3 的方向写进架构约束，等于把一家的私有约定当成行业标准（§5.2 的三条动作已经写明这一点）；不设上界的直接代价是 token 成本失控与结论不可复现——**而这两种代价都不会报错**，只会以账单和"上次不是这样"的形式出现。

**证据与来源**：可核的是编排框架层的公开文档（§5.2 表第 6 行）；**具名框架**见全书他处——`04-data-assetization/05-rag-architecture/05-rag-architecture-section-5-ai.md` 的 §5 把 LangGraph / AutoGen / CrewAI 记为"2024 年前后成为常见编排框架"；同章相邻主题的工具链表也把同一组具名按用途归行（`05-agent-platform/01-data-agent/01-data-agent-section-4-sec4.md` §4.3 工具链与平台的"Agent 编排框架"一行，含"按角色拆多 Agent → AutoGen / CrewAI / MetaGPT"）。② 核不到。

**成熟度**：**L3**。① **不成立**（只有框架与演示，没有支撑"可依赖"的正式条目）；② **不成立**；③ **不成立**（无通行做法，仲裁顺序各家私有）。

**B. 平台级评估与回放（L3）**

**旧做法与它的卡点**：排障靠看日志，"当时为什么这么做"只能靠人回忆；模型换了档、提示改了版，行为漂移只能等用户报障。卡点在于**留痕记的是结论而不是输入与版本**（§3.5"审计留痕只记结论"这条反模式），于是回放连输入都取不回来。

**AI 改变了什么机制**：**是机制变化**——从"看日志"到"按会话回放、按版本对拍"。但这要求固定随机性、固定外部状态、固定时间，**各家定义不同**：回放要不要固定随机性、要不要固定外部状态、要不要固定时间，没有通行答案。**回放语义不统一，则"用回放定位问题"这件事本身就不可复现**（同 [Ch7 §02 反馈闭环](../../07-agent-evolution/02-feedback-loop/02-feedback-loop.md) 对"实验可复现"的要求）。

**由此得到的**：今天能做的最小版本是"**固定输入集 + 固定版本四元组 + 结果对比**"，**不做自动回放**。本主题能给的自建口径是一张留痕查询 SQL（§4.5 模板 5：按 `session_id` 拉出步骤、`intent` / `effect`、`tool_calls` 与钉住的 `agent_version`）——**这是本主题自带的字段口径，不是行业标准**。

**由此付出的**：留痕的量与保留期都随回放需求上升（§8 给的存储算例是以日活 `2,000` 会话计的年 `12–58 GB`【推算：2,000 会话/日 × 8 步 × 2–10 KB】，并按热 30 天 / 温 1 年 / 冷归档分层）；而如果只记结论不记输入与版本，这套分层存的也是取不回输入的死数据。

**证据与来源**：① 只有自研实现与厂商演示；② 核不到。（本主题 §4.5 模板 5、§8 的存储与保留算例可作自建口径的落点，但它们**不是行业标准**。）

**成熟度**：**L3**。① **不成立**（只有自研实现与厂商演示）；② **不成立**；③ **不成立**（回放语义各家不同，没有稳定接口可言）。

**判定方法**（A、B 两条共用一个动作）：从留痕里随机抽一次三个月前的会话，尝试回答"它当时看到了什么、用的哪个版本、最后为什么这么做"。三问都能答，说明评估与回放的地基已经在了；答不出第一、二问，问题在留痕字段，不在回放工具。

**两者都还没有到"能写进架构约束"的程度**，但它们各自有一个**今天就能做的最小版本**：多 Agent 场景先只做"轮次上界 + 超界转人工"（§2.3），评估先只做"固定输入集 + 固定版本四元组 + 结果对比"（不做自动回放）。这两个最小版本不依赖通行做法，且能把失控风险挡住。

### 5.4 与本主题既有栈的接口在哪

平台的每一次"接入"，本质都是**把一件事的所有权从应用搬到平台**；接口就是这次搬迁的交接物。

| 既有栈 | 接口 | 交接物（谁产出、谁消费） | 谁改 |
| --- | --- | --- | --- |
| 模型网关（[Ch6 §03](../../06-multi-model/03-model-gateway/03-model-gateway.md)） | 平台把"模型调用"全部交给网关；平台只传租户与版本标签 | 平台产出 `tenant_id` / `version_tuple` 标签；网关产出按标签的用量与账单 | 网关加"按租户计量"，平台传标签 |
| 数据资产与检索（[Ch4](../../04-data-assetization/README.md)） | 工具出口里的"只读查询 / 检索"工具，按租户裁剪可见数据 | 平台出口产出 `scope`（表级 / 文档级）；检索侧消费 `scope` 并在召回前过滤 | 平台出口加表级 / 文档级 scope |
| AI 治理（[Ch8](../../08-ai-governance/README.md)） | 分级保密、审计留痕、输出端防泄露接在出口与留痕表上 | 平台产出留痕字段（输入摘要、版本四元组、判定结果）；治理侧消费并做分级与出向判定 | 平台出口 + 留痕字段按治理要求补齐 |
| 横切工程（[Ch11](../../11-cross-cutting/README.md)） | 成本归因、可观测、血缘（会话 → 工具 → 表） | 平台输出三类标签：租户 / 版本 / 工具；横切侧把它们接进既有账本与血缘图 | 平台输出三类标签 |
| 架构与高可用（[Ch12](../../12-architecture/README.md)） | 多活、容量规划、混沌演练 | 平台产出按租户的分区归属与容量曲线；架构侧据此定多活单元与演练计划 | 平台按租户分区；演练覆盖 §4.7 的五类故障 |
| 资产沉淀（[Ch7 §01 长期记忆](../../07-agent-evolution/01-long-term-memory/01-long-term-memory.md)） | 平台上的会话是 Skill 提取的原料 | 平台产出"可判定为优秀"的会话集（带版本四元组与结果状态）；Ch7 消费并做提取 | 平台在留痕里补"结果状态"与"人工评价"字段 |

**这张表的读法**：**接口的两端都必须有交接物**，只有"我们对接了"而没有具体产物的，是没对接。上表右列的每一项都是**可以今天就检查是否存在**的东西——例如"平台是否真的输出了按租户计量的标签"，检查方法就是问网关要一份按租户拆分的账。

### 5.5 被过度宣传的部分

1. **"自治 Agent 平台"**：宣称"平台自己会优化提示、自己会改工具"。**可核验的形态**只有"确定性自动化"（自动扩缩、自动回滚、自动路由），涉及"改行为定义"的部分仍需要人审——这不是保守，而是**责任无法归属**（同 [Ch8](../../08-ai-governance/README.md) 对"自动化出候选"与"自动发布生效"之间那一次人工签字的要求）。
2. **"Agent 数量等于平台能力"**：平台的价值密度取决于**治理面**（配额、审计、回滚），不取决于注册了多少 Agent。**可核验的判据**：把注册表里 Agent 数量除以二，平台能力有没有任何一项下降？没有下降，说明注册得多不等于强。
3. **"协议接入即生态"**：接入了协议只说明"能调"，不说明"敢让人用"——权限与计量的空白，会在第一个生产事故里暴露（§5.3.2 的三问自查）。
4. **"持久化执行 = 长任务已解决"**：持久化解决的是"崩溃不丢"，不解决"任务本身跑不完"。**把它当成长任务的充分条件，会漏掉真正的瓶颈——外部依赖的超时与配额**：一个等外部 API 的长任务，即使检查点齐全，也会因为对方限流而反复重试到超界。
5. **"多租户 = 加个 tenant_id"**：租户隔离的实质是**三条隔离同时成立**——数据隔离（查得到什么）、资源隔离（占得到什么）、故障隔离（坏的时候波及谁）。只加 `tenant_id` 通常只做了第一条。

### 5.6 未来 3–5 年：可证伪的预测

每条都给出**被证伪的信号**（出现即说明判断错了）：

| 预测 | 被证伪的信号 |
| --- | --- |
| 控制面 / 数据面分离会成为平台的默认形态 | 两年内主流平台产品仍以"单体 + 配置"交付，且没有发布指针概念 |
| 工具协议的治理面（权限 / 配额 / 审计）会出现"标准化的最小集" | 两年后各家仍在自建互不兼容的治理字段，且没有跨平台的审计格式 |
| 持久化执行会成为长任务平台的标配 | 主流方案仍要求"任务一次跑完"，崩溃即失败且无恢复语义 |
| 平台级成本归因（到会话）会成为采购的硬指标 | 采购评估仍只看"单 token 单价"，不看按会话归因能力 |
| "平台"与"应用"的边界会由**治理面**而不是**能力面**来划 | 两年后仍以"支持多少种 Agent 模式"作为平台能力的比较口径 |

**这五条预测全部是【经验】档**：它们是对机制与采购行为的判断，没有具名出处，也没有可复算的推导链——**读者应按"可被证伪"来使用它们，而不是按结论使用**。

**怎么用这份预测表**：不要用它做技术选型，用它做**反向检查**——每隔半年回来看一次"被证伪的信号"有没有出现。出现了就修正自己的架构假设（例如"控制面分离是默认形态"这条若被证伪，说明你的分离投入可能做早了）；没出现也不构成"必须跟进"的理由，因为预测成立不等于**对你有收益**（收益仍取决于 §7.4 的成本函数）。

### 5.7 给架构师的行动建议

1. **今年就该做**：状态外置 + 工具出口 + 版本四元组（§4.1 的第 2、3、8 步）。这三件事不依赖任何前沿判断，且是其余所有治理的前提。
2. **可以试点（每条自带退出条件）**：持久化执行（退出条件：P99 会话时长不足小时级，或幂等键无法覆盖到有副作用的外部调用）；协议化接入（退出条件：接入后治理四项仍答不全）。
3. **先别投**：多 Agent 仲裁与平台级回放。等它们出现可比较的通行做法，再投入；在此之前只做 §5.3.6 给的两个最小版本。
4. **无论哪条**：把"成本按会话归因"作为平台的第一条 KPI——它同时是治理面、可观测与采购谈判的共同语言（§2.2 的成本归因公式就是它的口径）。
5. **一条反直觉的**：**先做"关掉演练"，再做"扩容演练"**。平台的第一类事故不是"扛不住"，而是"某个部件挂了之后没有降级路径"（控制面挂了怎么办、出口挂了怎么办、状态存储挂了怎么办）。这三条降级路径写不出来，扩容只是在放大一个没有降级设计的系统。

### 5.8 小结

> 本节小结：AI 时代对平台层的改变**只有一条是机制性的**——**变更的落点从"部署"移到了"指针"**（控制面 / 数据面分离），其余变化（协议化、持久化执行、字段约定、沙箱）都是在这条之上的接口与安全加固。平台层没有一行达到 L1，卡点都在"第三方非厂商生产案例"；因此判断成熟度时，请把它当作**机制可验证、生产未被第三方验证**的一类，而不是把它当作已被证明的实践。**给读者的动作**：先把不依赖前沿判断的三件事（状态外置、工具出口、版本四元组）做完，再谈试点。

> 💡 **思考锚点**：把你平台最近一次行为变化找出来（提示改动、模型换档、工具升级都算），回答两个问题：这次变化对应哪个版本四元组？如果当时要回滚，需要多久？如果两个答案都需要"去查一下"，那 §5.3.1 说的"变更落点"在你这里还没有成立——你打算先补版本指针，还是先补回滚演练？
