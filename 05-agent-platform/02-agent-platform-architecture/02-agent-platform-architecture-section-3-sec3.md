## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

平台形态由**五条约束**决定，顺序不能颠倒——前一条过关之前，后一条的取舍没有意义：

1. **部署边界**：能不能用公有云 SaaS？不能，则平台本体、状态存储、模型权重、工具执行体**全部**要能在客户机房内闭环（这一条直接筛掉一半候选形态）。
2. **状态持久性要求**：会话是否需要跨进程重启、跨版本升级存活？需要，则状态必须外置（模式 2 成为前提）。
3. **工具副作用**：工具有没有写操作、能不能触达生产？有，则必须有唯一出口 + 人审闸门 + 幂等键（模式 4、7 成为前提）。
4. **租户数与隔离强度**：一个团队用，还是多部门/多客户共用？隔离要求到"逻辑隔离"还是"物理隔离"（决定了是共享池还是独立 Cell）。
5. **峰值形态**：是"很多短会话"还是"少量长任务"？前者瓶颈在模型端点并发，后者瓶颈在队列与状态存储——**这一条决定调度与限流放哪一层**（§2.2 的容量模型就是为它服务的）。

> **判据的用法**：先用 1 筛掉不可行形态，再用 2、3 决定"必须有的部件"，最后用 4、5 决定"这些部件怎么部署"。反过来先选形态再补约束，几乎一定会在部署或合规那一关推倒重来。

**每条约束的"过关"是可核查的，不是判断题**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 部署边界 | 能在**从未联网**的机器上装成一次；依赖清单里没有"运行时需要公网"的项 |
| 2 状态持久性 | 做一次**滚动重启**，在跑的会话全部可恢复——不是"应该能"，是"试过" |
| 3 工具副作用 | 能拿"出口统计"与"目标系统访问日志"对账，差异可解释 |
| 4 租户与隔离 | 能回答"两个租户的数据在同一张表里还是两张表里"——并说得出为什么 |
| 5 峰值形态 | 有会话墙钟时长的分位数（P50/P95/P99），不是平均值 |

上表五条都是**半天内可以做完的验证**。它们的价值在于：**约束是被量出来的，不是被讨论出来的**——讨论出来的约束一定偏向"我们现在的做法"。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 单租户单体运行时

**被什么约束逼出来**：只有一个团队、一次会话量很小（`C` 个位数、`H` 在分钟内）、且状态可以容忍丢失。

**结构**：一个进程内含会话状态（内存）、编排循环、模型调用与工具调用；出了进程就是"没跑过"。

**为什么这样设计有效**：因为**所有状态都在同一个地址空间里**，所以"读上下文—决策—调工具—写上下文"这四步之间没有序列化、没有网络往返、没有一致性窗口——**它的有效性来自消除了部件间的边界，而不是来自某个部件的性能**。这也是它唯一的优势：一旦引入任何一个外置部件，这个优势立刻消失，而代价（运维面、故障面）立刻出现。

**代价（要量出来）**：

- **重启即丢**：丢失窗口等于"最后一次内存写入到进程退出"之间的全部会话；对 `C = 5`、`H = 3 min` 的规模，一次滚动升级可能影响十几个会话——**规模小的时候，这个代价看起来可以接受，这正是它危险的地方**。
- **并发天花板**：受单进程的 CPU 与连接数限制；按 §2.2 的容量模型，`C / H × S` 一旦超过单进程能维系的每秒调用数，延迟会非线性上升。
- **成本不可归因**：一个进程一个账单，无法回答"哪个团队花了多少"——注意这一点与规模无关，**规模再小也会被问到**。

**失效点**：一旦出现"会话跑一半被重启"或"两个团队共用"的诉求——**这个模式不是渐进演化到平台，而是必须被替换**（这也是它最危险的地方：看起来能用很久）。**迁移的代价主要在状态**：内存里的会话无法导出，只能让存量会话自然结束、新会话走新路径——所以切换不发生在发布那一刻，而发生在发布之后的"最后一个老会话结束"那一刻。

#### 3.2.2 无状态执行体 + 外置状态

**被什么约束逼出来**：会话必须跨重启存活（约束 2），同时执行体要能水平扩。

**结构**：执行体可随时被杀；每一步结束把检查点写入外置存储（关系库 / 对象存储 / 专用状态服务）；恢复时按 `session_id` 读最后一个检查点续跑。

**为什么这样设计有效**：因为**状态的可靠性与执行的可用性被解耦了**——执行体退化成一个"纯函数式的步骤执行器"（读检查点 → 执行一步 → 写检查点），于是它可以被任意替换、任意扩缩、任意滚动升级，而这些操作都不需要访问会话状态。**这条因果链是平台化的第一块基石**：没有它，后面所有的治理（配额、审计、回滚）都只能在"进程还活着"的窗口内生效。

**代价（要量出来）**：

- **每步一次写**：设每次检查点写入 `2–10 KB`【经验】，10 万会话 × 每会话 8 步 ≈ 800 万次写/日，按单写 200 字节元数据 + 正文另存，存储与 QPS 都要提前算。**这条成本是"每步"，不是"每会话"**——长任务（`S` 大）会把它放大。
- **恢复语义必须明确**：检查点存的是"意图"还是"已生效的事实"——**写操作之后的检查点必须记录"已生效"**，否则恢复会重复执行（幂等键为此兜底）。

**另一个必须提前定的东西**：**检查点的粒度**。粒度为"每步"时恢复最精确、写入最多；粒度为"每 N 步"时写入减少、崩溃窗口内的重放范围变大。**判据是"重放的副作用能否被幂等吸收"**——能被吸收就放粗（省写入），不能就必须细到"写操作之前"。

**失效点**：当"步与步之间"存在不能原子提交的外部副作用时（例如已发出转账再放检查点），崩溃窗口内的重放会产生重复动作——此时要么把副作用放进幂等键，要么改成"两阶段：先落意图、再执行、再确认"。

#### 3.2.3 控制面 / 数据面分离

**被什么约束逼出来**：多团队共用（约束 4）+ 变更需要版本化发布（本主题 §1.2 的第 4 件事）。

**结构**：控制面保存全部**定义**（Agent 定义、提示版本、工具注册、模型路由、配额策略、发布指针）；数据面只接收"某个已发布版本 + 某个会话"的执行请求，不持有定义。

**为什么这样设计有效**：因为**"变更"这件事被从执行路径上移走了**——发布与回滚改的是控制面里的一个指针，数据面读到的仍然是"一个版本号"。由此推出三件事，每一件都可以单独核查：

1. 回滚的时间与部署时长**无关**（改指针是常数时间），所以"秒级回滚"不是优化出来的，是结构决定的；
2. 灰度分流**不需要重新打包**（分流对象是会话与租户标签，不是代码）；
3. 审计的对象收敛成**一处**（控制面的变更流），因为行为只可能被它改变——**数据面里没有可以改行为的东西，这本身就是审计的简化**。

**代价**：控制面自身成为关键路径上的单点——必须做多副本 + 变更留痕 + 变更审批；且"正在跑的会话"要钉住它启动时的版本四元组，否则中途换版本会让行为不可解释。

**一个必须被设计（而不是被发现）的降级形态**：**控制面挂了，已建立的会话应当继续执行，而新会话应当快速失败并给出明确错误码**。这个"半可用"状态是分离架构的必然产物，可核查的做法是**真关一次控制面**。

**失效点**：控制面与数据面共享数据库、或数据面偷偷读控制面的表——这时"分离"只剩形式，回滚不再安全（因为两个面的事务边界纠缠在一起）。**判定方法**：看数据面的部署单元里有没有控制面的数据库连接串——**有，就是没分离。**

#### 3.2.4 工具出口收口（Tool Egress）

**被什么约束逼出来**：工具有副作用（约束 3），且要能回答"谁在什么时候用哪个工具做了什么"。

**结构**：所有工具调用经过唯一出口；出口做四件事——**鉴权**（这个租户能用这个工具吗）、**参数校验**（Schema 与范围）、**配额扣减**（预扣 / 结算）、**留痕**（请求、响应摘要、耗时、结果状态）。

**为什么这样设计有效**：因为**四件事都需要"调用发生的那一刻"这个信息**，而这四件事的判定依据又都来自平台的集中视图（租户 → 工具白名单、工具 → Schema、租户 → 配额、平台 → 留痕表）。把它们放在每个工具的代码里，意味着**同一份判定依据要在 N 个地方各维护一份**，而只要有一处漏了，治理就出现了缺口——**缺口不会平均分布，它会集中在最忙的那个工具上**。出口的有效性来自"判定依据只有一份"，不来自"网关性能好"。

**代价**：

- 出口多一跳（延迟增加，通常 `1–10 ms` 量级【经验】，取决于是否跨网络与是否做深校验）；
- 出口必须自身高可用，否则它一挂，全平台工具不可用——这一个代价反过来要求出口**极薄**：把耗时的校验（例如需要查大表的判定）异步化或缓存，否则出口的可用性会跟着它的依赖一起下降。

**失效点**：**旁路**——某个团队为了性能直接连了数据库或内部 API，绕过出口。此时配额、审计、幂等全部失效。**判定方法**：拿"出口的工具调用统计"与"被调用系统自己的访问日志"对账，差异就是旁路流量（这是可定期执行的检查动作，成本约半天）。**旁路的成因不是恶意，而是"绕过去更快"**——所以出口的延迟预算必须写出来并公布，否则每个团队都会各自决定绕过它。

#### 3.2.5 事件驱动 + 队列（长任务异步化）

**被什么约束逼出来**：峰值形态是长任务（约束 5）——`S × T` 大、单个会话可能跑几分钟到几十分钟。

**结构**：会话发起后立即返回 `session_id`；执行体从队列取任务；长任务与交互式会话**分队列**并有优先级；结果通过状态查询或回调返回。

**为什么这样设计有效**：因为**队列把"到达率"与"处理能力"之间的耦合剪断了**——请求到达时不需要有空闲执行体，只需要队列有容量；执行体的数量因此可以按**平均吞吐**而不是**峰值到达**来配置，这正是它在成本上的有效性来源。同时队列深度天然是一个容量信号：**它是唯一一个"在用户报障之前就能看出要出事"的指标**（同 [Ch11 §04 可观测](../../11-cross-cutting/04-observability/04-observability.md) 对"领先指标"的要求）。

**代价**：

- 引入"至少一次"投递语义 → **必须靠幂等键去重**；
- 用户体验从"等结果"变成"查状态"，需要状态查询接口与通知；
- 队列自身成为新的故障面（积压、重复消费、消息过期）——**积压必须告警且告警要带"预计清空时间"**，只报深度不报速率的告警会被忽略。

**失效点**：把**需要即时反馈**的会话也塞进队列（例如人机对话的每一步），用户会看到不可接受的等待——**交互式路径必须是同步的，只有长任务异步化**。判据是"这一步的延迟预算是多少"：预算是秒级的一律不能进队列。

#### 3.2.6 多租户分区（共享池 / 独立池 / 独立 Cell）

**被什么约束逼出来**：多团队或多客户共用（约束 4），且隔离强度要求不同。

**结构**：三种形态按隔离强度递增——**共享池**（同一批执行体服务所有租户，靠逻辑隔离与配额隔离）、**独立池**（每租户一组执行体与命名空间）、**独立 Cell**（每租户独立的存储 + 计算 + 出口，故障与容量都不串）。

**为什么这样设计有效**：因为**这三种形态分别消掉了三种不同的"串"**——共享池只保证数据可见性不串；独立池进一步保证**资源**不串（一个租户的峰值吃不掉别人的容量）；独立 Cell 再进一步保证**故障**不串（与 [Ch12 §01 单元化](../../12-architecture/01-cell-based-architecture/01-cell-based-architecture.md) 的原理一致：按归属切分，坏一个影响 `1/N`）。**选型问题因此变成"你被要求消掉哪一种串"**，而不是"哪种更高级"——绝大多数人只需要第一种，而被合规要求推高的往往是第三种。

**代价（可算）**：以独立池为例，若每租户常备最小执行体 `2` 副本、单副本 `1 vCPU + 2 GB`，则 20 个租户的常备开销是 `40 vCPU / 80 GB` 的**空转成本**【推算：2 × 20 = 40 副本；按云上 vCPU 月单价换算即可得月成本，单价请按你自己的采购口径代入】——这就是"隔离强度"的价格。

**一个常被忽略的第四种串**：**噪声**。共享池里两个租户的延迟分布会互相影响（同一批执行体的排队时间被共享），**因此"P99 归因"在共享池里天然困难**——如果你的 SLO 是按租户承诺的 P99，共享池需要额外的按租户队列或权重。

**失效点**：共享池里只要有一个租户发起"工具调用风暴"，同池其他租户的 P99 被拖垮；而独立 Cell 的问题是**成本与运维面随租户数线性增长**。选择判据是：**租户之间是否存在"业务上不可共用"的合规要求**——有则必须独立，没有则共享 + 配额。

#### 3.2.7 人审闸门（同步审批 / 异步工单）

**被什么约束逼出来**：有不可逆或高代价动作（约束 3）。

**结构**：同步闸门（执行体阻塞等待批准，适合分钟级决策）、异步工单（把动作落成待办，批准后由另一条链路执行，适合小时级或需要多人会签）。

**为什么这样设计有效**：因为**它把"模型的自主性"与"人的责任"切成两个可分别设计的对象**——模型侧只需要产出"待批准的意图"（一个结构化对象），人侧只需要对意图做判定；**两者之间不需要共享任何推理过程**。这条切分的直接后果是：**批准记录可以脱离模型而独立审计**——"谁批准了什么"不依赖"模型当时怎么想的"，这是责任可追溯的前提。

**代价**：吞吐被人的响应时间限制（§2.2 的 `n > λ/μ`）；且闸门本身要防"橡皮图章"（审批变成无脑点同意，等于没有闸门）——**可核查的做法是抽检批准记录并统计"否决率"**：连续两季度否决率为零，说明这个闸门没有在实际起作用。

**同步还是异步，判据是一个数**：**批准人看到请求之后，到能做出判断需要多久**。这个时间在分钟级以内用同步（执行体阻塞是可接受的），超过分钟级必须用异步工单（阻塞会吃掉并发额度，按 §6.2 的利特尔法则，挂起运行数 = λ × 平均等待时长）。**选错方向的症状是并发额度被"等人"吃掉，而 CPU 与端点的利用率都很低。**

**失效点**：① **无超时**：一个批不准的请求永久挂起，占用并发额度；② 闸门定义过宽（所有操作都要批），人力瞬间成为瓶颈；③ **批准与执行之间没有绑定**：批准发生在 T1 而执行发生在 T2，中间输入已经变了——**因此批准记录必须绑定它批准的那个输入快照**，否则"批准"这件事在语义上是空的。

#### 3.2.8 沙箱执行（隔离执行环境）

**被什么约束逼出来**：Agent 会生成并执行代码（数据分析、脚本转换），或需要访问本不该直接触达的资源。

**结构**：每次执行在隔离环境（容器 / 微虚拟机 / 受限进程）内进行；环境**无长期凭证**（临时凭证、最小权限）、**有资源上限**（CPU / 内存 / 时限 / 出网白名单）、**用完即毁**。

**为什么这样设计有效**：因为**它把"不可信代码"的爆炸半径从"宿主能碰到的一切"收窄到"你显式挂进去的东西"**——注意这个收窄的边界是**挂载面**，不是隔离技术本身。因此这条模式的有效性由两件事共同决定：**隔离强度**（它限制逃逸）与**挂载面**（它限制可达）。**只做前者不做后者，等于给一台能访问内网的机器上了锁但把钥匙插在门上**——这是本节最容易做错的一处。

**代价**：

- 冷启动延迟（容器级 `百毫秒–秒级`、微虚拟机更高【经验】）；
- 需要镜像与依赖的版本管理（否则"昨天能跑"无从解释）——**沙箱镜像必须与版本四元组一起发布**，否则回滚会话时找不回当时的执行环境；
- 出网白名单是运维负担，但它是**必需项**——不限制出网等于把沙箱变成了一台能访问内网的跳板机。

**失效点**：沙箱共享宿主内核且未限制系统调用 → 逃逸风险；或沙箱内挂了长期凭证 → 隔离形同虚设；或**沙箱被复用**（为了省冷启动而复用同一个实例）→ 上一个会话的残留数据成为下一个会话的输入，这在多租户下直接构成数据泄漏。

### 3.3 模式选择决策表

| 约束组合 | 推荐形态 | 必须同时上的部件 | 不选它的原因（反面） | 关键判据（可核查） |
| --- | --- | --- | --- | --- |
| 单团队、短会话、状态可丢 | 3.2.1 单体运行时 | 无 | 上平台会把调试复杂度提前引入 | 会话是否需要跨重启存活（否） |
| 单团队、会话需存活 | 3.2.2 无状态 + 外置状态 | 检查点存储、恢复语义、检查点粒度 | 单体模式重启即丢会话 | 过去一个月是否发生过"跑一半丢失"（是） |
| 多团队共用、频繁发版 | 3.2.3 控制面 / 数据面分离 | 版本四元组、发布指针、变更留痕、控制面降级形态 | 不分离则回滚不可安全执行 | 最近三次行为变化能否定位到版本（否→需要） |
| 工具有写操作 | 3.2.4 出口收口 + 3.2.7 闸门 | 注册表、Schema 校验、幂等键、留痕、延迟预算 | 不收口则权限与审计无法回答 | 能否对账出旁路调用（不能→未收口） |
| 长任务为主（`S × T` 大） | 3.2.5 队列 + 异步 | 优先级队列、幂等、状态查询接口、积压告警 | 同步执行会让交互被长任务饿死 | 长任务占比与单个耗时分布 |
| 多租户且合规要求隔离 | 3.2.6 独立池 / Cell | 每租户配额与审计、容量规划 | 共享池的合规边界不可论证 | 租户之间是否存在不可共用的数据边界（是） |
| 生成并执行代码 | 3.2.8 沙箱 | 临时凭证、资源上限、出网白名单、镜像版本、挂载面清单 | 直接在宿主执行，爆炸半径不可控 | 是否有模型生成的代码进入执行路径（是）；挂载面清单存不存在 |

### 3.4 组合模式：真实系统不会只用一种

平台几乎一定是**组合**，而且组合有先后依赖：

1. **底座组合**：3.2.2（无状态 + 外置状态）+ 3.2.3（控制面 / 数据面分离）——**这两条是平台化的最小充分条件**，缺任何一个，后面所有治理都无处落。
2. **治理组合**：3.2.4（出口收口）+ 3.2.7（人审闸门）——先收口，再在出口上挂闸门（闸门的位置就是出口的判定逻辑）。
3. **容量组合**：3.2.5（队列）+ 3.2.6（租户分区）——队列给积压信号，分区决定这个信号是共享的还是隔离的。
4. **安全组合**：3.2.8（沙箱）+ 出口的临时凭证——沙箱负责"跑在哪"，凭证负责"能碰什么"，**两者缺一都不成立**。

**组合的常见误配**（每条都对应一个可核查的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 上了队列却没有幂等键 | 重试变成重复副作用，且难以自动发现 |
| 上了分区却没有每租户配额 | 一个租户的峰值能吃掉整池 |
| 上了沙箱却给了长期凭证 | 隔离白做，出网白名单也拦不住"用凭证直接调" |
| 上了版本四元组却没有会话钉版本 | 中途换版本，复盘时的行为无法解释 |
| 上了闸门却没有超时 | 并发额度被未决请求吃掉（CPU 与端点利用率都很低） |
| 上了控制面分离却共享数据库 | 回滚不再安全（事务边界纠缠） |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **把平台做成一个大 Demo** | 控制面里没有版本概念，发版=改配置重启 | 行为变化不可归因，回滚不可执行 | Demo 阶段"先跑通"的惯性被带到了生产 |
| **状态留在执行体内存** | 滚动升级时大量会话报"上下文丢失" | 可用性与状态可靠性绑死，扩缩容即丢数据 | 状态外置要写检查点，比内存慢 |
| **配额只做事后统计** | 月底账单超预算，但事前没有任何拦截 | 超发发生在观测之前，配额失去约束力 | 事后统计比预扣简单 |
| **工具直连（旁路出口）** | 出口统计与目标系统日志对不上 | 权限、审计、配额同时失效 | 出口多一跳，性能诉求压过治理 |
| **重试无幂等** | 同一笔写操作出现两次 | 重复副作用，且难以自动发现 | 只考虑"失败要重试"，没考虑"重试会重复" |
| **人审无超时** | 一批请求长期挂起，占着并发额度 | 吞吐被少数未决请求锁死 | 把"等人"当成了无状态 |
| **多 Agent 无限互相修订** | 两个 Agent 来回改了十几轮不收敛 | token 成本失控，且结论不可复现 | 缺少轮次上界与升级规则 |
| **成本不归因** | 只能给出租户一个总额 | 没有人对成本负责，优化无靶点 | 归因要在出口记账，工程量大 |
| **审计留痕只记结论** | 出事时无法回答"它当时看到了什么" | 复盘只能靠猜 | 留痕字段设计时按"结果"而不是"输入+版本"设计 |
| **沙箱实例被复用以省冷启动** | 偶发的"数据串了"投诉，难以复现 | 上一会话的残留成为下一会话的输入 | 冷启动延迟是可观测的痛，数据串是偶发的痛 |
| **批准与输入不绑定** | 批准后执行的是另一份输入 | "批准"在语义上为空，责任无法归属 | 批准记录只存了动作名，没存输入快照 |
| **控制面单点无降级** | 控制面一重启，全平台新会话发不出去 | 分离架构把可用性赌在一个部件上 | 只做了"分离"，没做"分离后的降级形态" |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 单团队 → 多团队【经验：从"一个团队"到"三个以上团队共用"是常见触发点】 | 版本冲突、账单无法拆分 | 3.2.3 + 3.2.6 | 定义外置、配额与审计接进出口，**存量会话需一次性导入状态存储** |
| 短会话 → 长任务为主 | 交互式请求 P99 被长任务拖高 | 3.2.5 队列 + 优先级 | 状态查询接口、幂等键改造、前端从"等待"改"查询" |
| 共享池 → 独立池 | 合规审计要求"数据不可共用" | 3.2.6 独立 Cell | 容量翻倍（每池最小副本），运维面按租户数增长 |
| 同步执行 → 沙箱 | 模型生成的代码开始进执行路径 | 3.2.8 | 镜像与依赖版本管理、冷启动延迟、出网白名单、挂载面清单 |
| 提示直改 → 版本四元组 | 同一提示在不同环境行为不一致 | 3.2.3 的发布指针 | 需要把提示、模型路由、工具集版本一起纳入版本对象 |
| 事后统计配额 → 预扣结算 | 账单在月中就超了预算 | 3.2.4 的预扣 / 结算三段式 | 需要"预估上限"的能力，且要留三段的对照记录 |
| 单人审批 → 多人会签 | 一个人成为吞吐瓶颈，且无第二双眼睛 | 3.2.7 异步工单 | 需要工单状态机与超时策略（同步闸门做不了会签） |

**一条通用判据**：**跃迁的触发点不是"规模变大"，而是"某个失效形态第一次出现"**——例如第一次出现"我无法回答这次变化对应哪个版本"，就该上版本四元组；第一次出现"一个租户拖垮了同池的其他租户"，就该上分区或按租户队列。**按规模数字预设跃迁点，几乎一定过早或过晚。**

### 3.7 自检清单

- [ ] 平台有三个面吗（构建 / 运行 / 治理）？还是只有一个执行入口？
- [ ] 会话状态外置了吗？**做一次滚动重启**，在跑的会话是否全部可恢复？
- [ ] 每个状态都有超时吗？特别是 `waiting_human`——超时后是失败、降级还是转人工？
- [ ] 每步之后写检查点了吗？**写操作之后**的检查点是否记录了"已生效"？检查点粒度是按"副作用能否被幂等吸收"定的吗？
- [ ] 工具有唯一出口吗？能否用"出口统计 vs 目标系统日志"对账出旁路？**出口的延迟预算写出来并公布了吗**？
- [ ] 出口做了鉴权、Schema 校验、配额扣减、留痕四件事吗？缺哪一件？
- [ ] 配额是**预扣后结算**还是事后统计？超发的最后一刻有没有拦截点？
- [ ] 幂等键覆盖了所有写操作吗？键里是否包含 `tenant / session / step / tool / 归一化参数`？覆盖范围是否与持久化范围一致？
- [ ] 长任务与交互式会话分队列了吗？优先级规则写下来了吗？积压告警带"预计清空时间"吗？
- [ ] 发布单元是四元组 `(编排, 提示, 模型路由, 工具集版本)` 吗？回滚能否只改一个指针？
- [ ] 控制面被真关过一次吗？已建立的会话是否继续执行？新会话的错误码明确吗？
- [ ] 人审闸门的适用范围是什么？它的否决率统计过吗？**批准记录绑定了输入快照**吗？
- [ ] 沙箱有临时凭证、资源上限、出网白名单吗？镜像版本可追溯吗？**挂载面清单存不存在**？实例是否被复用？
- [ ] 成本能归因到租户 / Agent / 会话吗？模型成本与平台固定成本的比例是多少？
- [ ] 多 Agent 场景有轮次上界与升级（转人工）规则吗？
- [ ] 留痕记的是"输入 + 版本四元组 + 结果"吗？能否用它重放一次会话？
- [ ] 你承诺给租户的 SLO 是 P99 吗？如果是，共享池里你怎么做按租户归因（噪声串扰）？

### 3.8 小结

> 本节小结：平台形态由五条约束按序决定——**部署边界 → 状态持久性 → 工具副作用 → 租户与隔离 → 峰值形态**；八种模式都是这些约束的组合结果，其中 **3.2.2（状态外置）与 3.2.3（控制面 / 数据面分离）是平台化的最小充分条件**，其余模式（出口收口、队列、分区、闸门、沙箱）是治理与容量的加法。真正的判别标志不是架构图上有几层，而是**两句话能不能答上来**：上个月谁花了多少；这次行为变化对应哪个版本四元组。答不上来，就还在应用阶段。

> 💡 **思考锚点**：把你手上的 Agent 系统按 §3.1 的五条约束各写一行，看看第 2 条（状态持久性）和第 3 条（工具副作用）分别把你逼到了哪个模式。然后做一个最小验证：**滚动重启一次执行体**，观察在跑的会话是否全部恢复；再从出口统计与目标系统日志各取一天数据对账一次。这两个动作合起来，决定你现在最该补的是状态外置，还是工具出口——你的答案偏向哪一边？
