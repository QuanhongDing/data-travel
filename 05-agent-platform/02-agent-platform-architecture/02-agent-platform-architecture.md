# 企业级智能体平台架构（Agent Platform Architecture）

> **一句话定位**：把一个能跑的 Agent 变成一个**能被多个团队共用、能被计量、能被回滚**的平台——平台的价值不在"更聪明的模型"，而在运行时、控制面与治理面这三层。

> 本文是 data-travel 项目 [Ch5 · AI 智能体平台架构](../../README.md) 的子章节（**02 企业级智能体平台架构**）。覆盖 **核心职责① AI 智能体平台整体架构** 中"运行时与编排 / 控制面 / 多租户与配额 / 工具接入 / 发布与回滚 / 私有化部署"相关的工程实践。本主题**不**重复讲单个 Agent 怎么搭（那是 [§01 Data Agent](../01-data-agent/01-data-agent.md) 的内容），只讲"把 Agent 收进平台"这件事本身。

## 1. 概念与定位

### 1.1 是什么

**学术 / 工业定义**：企业级智能体平台（Agent Platform）是**把"Agent 的构建、运行、治理"从单个应用里抽出来，做成一组共享服务**的系统。它对外提供三类接口：**构建侧**（注册 Agent、注册工具、配置提示与模型）、**运行侧**（发起会话、观察执行、人工介入）、**治理侧**（配额、审计、成本归因、版本发布）。

**工程定义**：在数据架构师手里，Agent 平台是**一次把"谁能在什么边界内让 Agent 做什么"写进系统**的工程：

- **运行时（Runtime）**：会话生命周期、步骤调度、超时与重试、状态检查点。
- **编排（Orchestration）**：单 Agent 的规划—执行—观察循环，以及多 Agent 的分工与仲裁。
- **控制面（Control Plane）**：Agent / 工具 / 提示 / 模型路由的注册与版本，发布与回滚。
- **数据面（Data Plane）**：真正跑模型调用与工具调用的执行体（无状态、可水平扩）。
- **治理面（Governance Plane）**：身份与权限、配额与计量、审计留痕、成本归因。

**「一个 Agent 应用」与「一个 Agent 平台」的差别**（这是本主题的判据表）：

| 维度 | 一个 Agent 应用 | 一个 Agent 平台 |
| --- | --- | --- |
| 使用者 | 一个团队 | 多团队（多租户） |
| 状态 | 常放进程内存或单机 Redis | 必须外置且可恢复 |
| 工具 | 代码里直连 | 注册表 + 权限 + 出口收口 |
| 成本 | 看账单总额 | 必须能归因到租户 / Agent / 会话 |
| 变更 | 改代码重新部署 | 版本化发布 + 灰度 + 回滚 |
| 出事时 | 重启 | 熔断、限流、回滚、留痕复盘 |

**一条判据**：**当"你无法回答上个月谁花了多少 token、哪个工具被谁调用过多少次"时，你手上的是应用，不是平台。**

### 1.2 为什么需要

平台不是"更高级的架构"，而是**被四件事逼出来的**：

1. **状态无处落**：单 Agent 跑在进程里时，一次会话跨几十步、每步调外部服务，进程重启即丢——用户看到"它忘了刚才说的话"。要做长会话与人工介入，状态必须外置。
2. **工具无人管**：工具一旦能在生产库上执行写操作，"谁能用什么工具、写到哪、留什么痕"就成了权限问题，而不是代码问题。
3. **成本无处归**：多团队共用一个 Agent 能力池时，账单只有一个总额——没有配额与计量，就不会有人对成本负责（同 [Ch11 §03 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md) 的"成本必须归属到 Owner"）。
4. **变更无法收**：提示与模型版本每天都在变，而 Agent 的行为对这两个版本极其敏感；没有版本化发布与回滚，一次提示改动就是一次不可控上线。

**这四件事的共同点**：它们都不是"模型能力"问题，而是**工程与治理**问题——这正是平台的职责范围。

### 1.3 在 AI 时代数据架构中的位置

```
   [租户 / 业务团队 / Agent 开发者]
                ↓ 构建侧接口
   [Agent 平台 · 本文]  ← 控制面：注册 / 发布 / 配额 / 审计
                ↓ 运行侧接口
   [运行时 + 数据面]    ← 会话状态、队列、工具沙箱
        ↓            ↓            ↓
   [模型网关]    [工具 / MCP]   [数据与检索]
    (Ch6)         (本文 §4.2)    (Ch4 RAG / 向量)
```

- **上游**：Ch4 数据资产化与检索（Agent 的"知识"来自这里）、Ch1 建模（语义层是 Text2SQL 的前提）。
- **下游**：Ch6 多模型编排与工具调用（平台把模型调用统一交给 [模型网关](../../06-multi-model/03-model-gateway/03-model-gateway.md)）、Ch7 资产沉淀与自进化（平台上的会话是 Skill 提取的原料）。
- **横向**：Ch8 AI 治理（分级保密与审计）、Ch11 横切工程（可观测 / 成本 / 血缘）、Ch12 架构与高可用（多活与容量规划）、Ch13 决策（自研 vs 采购）。

**一句话判断**：**「不会建 Agent 平台，就只能做 Agent Demo」——平台层是把 Agent 变成企业能力的唯一路径。**

### 1.4 演进历程

- **单 Agent SDK 阶段（2022–2023）**：把 LLM + 工具调用封成库（ReAct 循环写在自己的代码里），状态与工具都归应用管。
- **编排框架阶段（2023–2024）**：出现以"图/状态机"描述流程的编排框架，把多步、多分支、人审节点显式画出来；但框架只解决"怎么编排"，不解决"谁在跑、花多少、谁批准"。
- **平台化阶段（2024–2025）**：控制面 / 数据面分离成为共识——编排定义、模型与提示版本、工具注册、配额与审计上收到控制面；执行体变成无状态、可水平扩的数据面。同期出现"Agent 互操作协议"（工具、资源、提示的标准化接入），**把"工具接入"从每个平台自己的事变成协议层的事**（这一类规范的具体版本与发布时间请以各规范官方页面的当前版本为准）【公开】。
- **私有化与合规化阶段（2024–2025）**：受监管行业要求权重与数据都不出域，平台必须能在客户机房内完整交付——这把"私有化部署"从一句口号变成一串工程项（§4.6）。

> 演进的主线只有一句话：**能力从"库"上收到"面"，再从"面"上收到"协议"**。

## 2. 核心原理

### 2.1 关键概念定义

- **会话（Session）**：一次面向目标的连续交互，是平台的**状态单元**，也是配额与审计的**归属单元**。
- **步骤（Step）**：会话中的一次「模型调用 + 工具调用」组合，是平台的**调度单元**与**计量单元**（token 与工具次数都按步骤记账）。
- **检查点（Checkpoint）**：每一步之后落盘的状态快照；恢复时从最后检查点续跑（这是"进程重启不丢会话"的实现方式）。
- **工具注册表（Tool Registry）**：所有可用工具的唯一清单，登记工具名、输入 Schema、是否可写、Owner、审计字段与权限范围。
- **工具出口（Tool Egress）**：所有工具调用的唯一出口（网关或代理），在这里做鉴权、参数校验、配额扣减与留痕；**绕过出口的直连调用是平台最常见的破口**。
- **租户（Tenant）**：平台资源的隔离与结算单元——一个业务域、一个部门、或一个客户。
- **配额（Quota）**：对租户可消耗资源的硬上限（token / 工具调用次数 / 并发会话数），**在出口处扣减，而不是在报表里统计**。
- **人审闸门（Human Gate）**：在写操作、高危工具、不可逆动作前插入的人工批准点；它必须是**有超时的状态**，否则会积压成永久挂起。
- **回放（Replay）**：用留痕的输入与版本号重跑一次会话，用于定位"当时为什么这么做"（同 [Ch11 §05 血缘](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md) 的"影响面可枚举"思路）。
- **控制面 / 数据面（Control / Data Plane）**：前者管定义与治理（注册、发布、配额、审计），后者管执行（调度、调用、写入状态）。

### 2.2 数学 / 形式化基础

**容量模型（把"会话"折算成"每秒调用"）**：

```
并发会话数 C
每个会话平均步数 S（一次任务从开始到结束经过多少步）
每步平均工具调用数 T
每个会话的墙钟时长 H（秒）

→ 峰值每秒模型调用数 ≈ C / H × S
→ 峰值每秒工具调用数 ≈ C / H × S × T
```

**这不是估算技巧，而是决定"队列与限流放哪一层"的依据**：当 `S × T` 较大（长任务、多工具）时，瓶颈在**外部工具与模型端点**，平台必须做**排队 + 配额**；当 `S` 小（一问一答）时，瓶颈在**模型端点的并发额度**，平台主要做**并发闸门**。

**代入一组数看它怎么用**（三个数字决定三件事）【推算：链路为"每秒模型调用 ≈ C / H × S"，代入 C=500、H=120、S=8 得 33.3；每秒工具调用 = 33.3 × T，T=2 得 66.7；读者可换自己的 C/H/S/T 重算】：

```text
取 C = 500 并发会话，H = 120 秒，S = 8 步，T = 2 个工具/步
  → 每秒模型调用 ≈ 500 / 120 × 8 ≈ 33 次/秒
  → 每秒工具调用 ≈ 33 × 2 ≈ 67 次/秒
  ────────────────────────────────────────────────
① 33 QPS 的模型调用 → 决定你需要的端点并发额度（是不是要排队）
② 67 QPS 的工具调用 → 决定出口的吞吐设计（它比模型调用高一倍）
③ 500 个并发会话 × 每步 2–10 KB 状态 → 决定检查点存储的写入压力
```

**关键读法**：上例中工具调用是模型调用的**两倍**——这意味着**出口的容量必须按工具调用设计，而不是按模型调用设计**。这条推论在实践中经常被漏掉，因为"平台"这个词让人先想到模型；而实际先把平台压垮的往往是工具侧（尤其是那些穿透到数据库的工具）。**先把 §2.2 的三个式子在你自己系统上算一遍，再去谈架构选型**——算不出来，说明你还没有 `H` 与 `S` 的实测分布。

**配额的形式化**：设租户 i 的 token 预算为 `B_i`，单位时间窗口为 `W`，则出口处必须满足

```
Σ_{step ∈ W} tokens(step) ≤ B_i     且     消耗在调用发生前预扣（而非事后统计）
```

**预扣（reserve-then-settle）**是唯一能防止超发的形态：先按"预估上限"扣减，调用完成后按实际用量结算并退还差额；只做事后统计的配额，在超发那一刻已经来不及了。

**成本归因公式**（同 [Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md) 的口径）：

```
单会话成本 = Σ_step [ input_tokens × 单价_in + output_tokens × 单价_out + 工具自身成本 ]
平台成本   = 模型成本 + 计算/内存（沙箱与执行体）+ 存储（状态与留痕）+ 出口自身的固定成本
```

**警报线（可自测）**：**当"平台固定成本 ÷ 模型成本"大于 1 时，说明平台的运行开销已经超过它管的东西**——此时先收敛执行体数量与状态保留期，而不是继续加租户。

**人审闸门的积压条件**：设到达率 λ（个/小时）与人均处理率 μ（个/小时·人），所需人力 `n > λ / μ`；**当 λ/μ 持续大于现有 n 时，闸门会变成事实上的阻塞点**——这时要先降级闸门的适用范围（只拦写操作），而不是加人。

### 2.3 关键算法 / 方法

**会话生命周期状态机**（平台运行时的最小正确集）：

```
created → running → (waiting_human) → running → … → completed
              ↘ failed（超时/工具异常/配额耗尽）
              ↘ cancelled（用户或策略中止）
```

**必须写进设计的三条**：① 每个状态都要有**超时**（human 状态的超时尤其重要）；② `running` 必须可从检查点恢复；③ `failed` 要区分"可重试"与"不可重试"，不可重试的失败**不能**自动重跑（写操作重跑会产生重复副作用）。

**幂等键（Idempotency Key）**：`hash(tenant, session_id, step_index, tool_name, normalized_args)`——**同一键的重复调用必须返回第一次的结果**。这是"重试不重复下单"的唯一可靠做法；只靠工具自身实现幂等是不可控的（[Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md) 把它列为不可逆动作的前置条件）。

**并发闸门与限流**：
1. **令牌桶**按租户限速（应对突发）；
2. **并发信号量**按端点限并发（保护模型端点与外部工具）；
3. **队列 + 优先级**（把长任务与交互式会话分开排队，避免长任务饿死交互）。

**配额扣减的三段式**：`预估扣减 → 执行 → 实际结算`。三段都要留痕，否则对账时无法解释"为什么显示消耗 100 而账单 130"。

**发布与回滚（Agent 版的灰度）**：Agent 的"版本"是**四元组** `(编排定义, 提示, 模型/路由, 工具集版本)`——发布单元必须是这个四元组，只回滚提示而不回滚工具集版本，会把行为变化误判成"模型不稳定"。

**多 Agent 的仲裁**：优先用**确定性规则**（谁能改文件、谁只能建议、冲突时按什么顺序），只有当分歧不可枚举时才让模型仲裁；**无限互相修订**是必须显式设上界的（例如最多 N 轮，超界升级给人）。

### 2.4 与相邻概念的关系

- **Agent 平台 vs 单个 Data Agent**：Data Agent（[§01](../01-data-agent/01-data-agent.md)）是平台上的**一个租户级应用**；平台提供它需要的会话、工具、配额与审计。把 Data Agent 做深不等于有平台。
- **Agent 平台 vs 模型网关**：[模型网关](../../06-multi-model/03-model-gateway/03-model-gateway.md)解决"请求发给谁、怎么归一、怎么计费"；平台解决"谁在跑、跑在什么状态上、谁批准"。**网关是平台的依赖，不是平台的替代**。
- **Agent 平台 vs RAG / 数据资产（Ch4）**：RAG 解决"知识从哪来"；平台解决"知识以什么权限、在什么额度内被使用"。同一套 RAG 能力在平台里必须被切成"按租户可见"的子集。
- **Agent 平台 vs 工作流引擎（Airflow / DolphinScheduler 一类）**：工作流引擎的图是**编译期确定**的，节点执行结果不影响图结构；Agent 的图是**运行期展开**的（下一步取决于上一步的输出）。**用工作流引擎硬做 Agent 会出现"图爆炸"**：状态与分支随输入组合增长。
- **Agent 平台 vs API 网关**：API 网关管南北向流量的治理（限流 / 鉴权 / 路由）；Agent 平台管的是**调用链内部的工具出口**——两者的共同点是"出口唯一"，不同点是后者的调用方是模型而不是人。

> 💡 **思考锚点**：把你手上的 Agent 系统按 §2.1 的五个面（构建 / 运行 / 控制 / 数据 / 治理）各写一行，标出哪些面已经有明确的落点、哪些还散在代码里。然后做两个可当场验证的动作：**滚动重启一次执行体**（在跑的会话是否全部可恢复）、**用入口统计与目标系统日志对账一天**（有没有绕过出口的调用）。这两个动作的答案，决定你现在的第一优先级是"状态外置"还是"工具收口"——你打算先做哪一个？
