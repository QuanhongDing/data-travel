## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研 / 框架直用 / 托管 / 买产品"打分是常见做法，但它有三个结构性问题：① 同一列在不同处境下方向相反（"可定制"对监管行业是必需、对三个人的团队是浪费）；② 打分表隐含"这些选项互斥"，而真实系统是组合（控制面托管 + 数据面自建很常见）；③ 最关键的判据（部署边界、工具副作用）**不是可打分的维度，而是门槛**——不满足就直接出局。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 部署边界 | 平台本体、状态、权重、工具执行体能否离开你的机房？ | 不能离开 → 托管方案直接出局，这一条是**门槛不是权重** |
| 治理面归属 | 配额、审计、成本归因由谁实现、落在哪一层？ | 治理面不可外包：它是你与业务方之间的责任界面 |
| 状态与恢复 | 会话状态归谁、能否跨重启与跨版本恢复？ | 决定"长任务能不能做"，也决定运维复杂度落在谁身上 |
| 工具出口 | 工具调用能否被收口到唯一出口并做四件事（鉴权 / 校验 / 配额 / 留痕）？ | 收不了口 → 权限与审计永远无法回答 |
| 变更与回滚 | 发布与回滚能否落到"改一个指针"？ | 决定你能否在事故中 30 秒内止损 |
| 团队承接能力 | 有没有人能长期维护编排、状态与出口三块？ | 自建方案的真实成本是**长期人力**，不是首版实现 |

> **读法**：先用第 1 条筛掉不可行；再用第 2、4、5 条筛掉"治理面天生不完整"的方案；最后用第 3、6 条在剩下的方案里选——**第 6 条最容易被跳过，也最容易在第二年变成账单**。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 全自研运行时与治理面 | 平台即自研产品 | 自己实现状态、队列、出口、配额、发布 | 有平台团队、且平台是核心能力 | 长期人力；首版到可用通常以季度计【经验】 |
| 编排框架 + 自建控制面 | 框架管编排、你管治理 | 编排用框架（图 / 状态机），控制面（版本、配额、审计）自建 | 多数企业的现实选择 | 框架升级与自建治理的接缝要长期维护 |
| 持久化工作流引擎 + 自建治理面 | 把长任务交给引擎 | 步骤持久化与恢复交给引擎，治理面自建 | 长任务为主（报告生成、批量分析） | 引擎的编程模型与 Agent 循环不完全契合，需要适配层 |
| 托管 Agent 平台服务 | 厂商托管控制面与数据面 | 注册即用，配额与审计由厂商提供 | 无部署边界限制、追求最快上线 | 数据与权重可能出域；治理面按厂商口径 |
| 私有化交付版商业平台 | 买产品、装进机房 | 产品自带控制面 / 数据面，交付包含离线包 | 受监管行业、且不愿自建 | 定制受产品边界限制；版本升级依赖厂商 |
| 混合：控制面托管 + 数据面自建 | 分工 | 版本与配额用托管，模型与工具执行留在机房 | 对数据敏感但想省治理工程量 | 两侧的接口成为长期契约负担 |

**这六个候选其实分三族**：**自建族**（全自研、编排框架 + 自建控制面、持久化工作流引擎 + 自建治理面）——治理面在自己手里，代价是长期人力；**托管族**（托管 Agent 平台服务）——上线最快，代价是部署边界与治理口径都由厂商定；**产品族**（私有化交付版商业平台、混合形态）——拿到成品控制面，代价是定制边界与升级依赖。

**族内可替换，跨族不可换**：三个自建候选之间换，动的是编排层与状态层；而"治理面归属"从自建族换到托管族，等于**责任界面整体外移**——这不是技术迁移，是组织决策。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 治理面的落点：在出口，还是在报表

**机制是什么**：配额与审计只有两种落点——**在调用发生前的出口**（预扣、拦截、留痕），或**在调用发生后的统计**（报表、告警）。

**它在各候选中的实现差异**：

| 候选 | 治理面落点 | 拦截时机 | 结果 |
| --- | --- | --- | --- |
| 全自研 | 出口（你实现） | 调用前 | 可拦截；出口自身成为高可用要求 |
| 编排框架 + 自建控制面 | 出口（自建） | 调用前 | 同上，但出口要与框架的执行模型对接 |
| 持久化工作流引擎 | 出口（自建） | 调用前 | 引擎的步骤边界天然适合挂检查点与配额 |
| 托管服务 | 厂商出口 | 调用前（厂商口径） | 能拦，但**口径与你的成本归属口径未必一致** |
| 私有化产品 | 产品出口 | 调用前 | 能拦，粒度受产品配置项限制 |
| 混合 | 分包：托管侧管版本、自建侧管出口 | 调用前 | 两个口径要定期对账，否则两边数字不一致 |

**由此必然导出的性质**：因为**事后统计的观测点晚于超发点**，所以任何"统计型治理"都不能防止超发——只能事后归因。因此凡是把配额做成报表的方案，其真实语义是"事后知道"，不是"事前约束"。

**公开证据**：主流平台产品的文档都把"配额 / 限流 / 审计"放在**调用链路上的执行点**（网关 / 出口 / 代理），而不是放在分析侧——可按各产品文档中「配额」「限流」章节的当前版本自行核验【公开：以官方文档当前版本为准】。

**失效条件**：当存在**旁路**（团队直连目标系统）时，出口型治理全部失效；此时先解决旁路，再谈配额粒度。

#### 7.3.2 状态归谁：进程、引擎，还是平台

**机制是什么**：会话状态存在三处之一——**执行进程内**、**引擎的状态存储**、**平台自己的状态表**。落点决定"谁能恢复"与"恢复粒度"。

**它在各候选中的实现差异**：

| 候选 | 状态落点 | 恢复粒度 | 修复问题的入口 |
| --- | --- | --- | --- |
| 全自研 | 平台状态表 | 步 | 自己的表，任意改 |
| 编排框架 + 自建控制面 | 框架的检查点 / 平台表 | 步或节点 | 框架的持久化接口 |
| 持久化工作流引擎 | 引擎存储 | 步 | 引擎的运维工具 |
| 托管服务 | 厂商存储 | 厂商定义 | 通常不可直接操作 |
| 私有化产品 | 产品存储 | 产品定义 | 需厂商支持 |
| 混合 | 自建侧状态表 | 步 | 自己掌握 |

**由此必然导出的性质**：因为**恢复粒度决定了"重试的最小单元"**，所以恢复粒度粗于步骤的方案，其重试一定会重放更多工作——当工具带副作用时，重放范围越大，幂等键要覆盖的范围也越大。

**失效条件**：当业务要求"恢复时不重复任何已生效的写操作"时，托管与产品方案若不给步骤级恢复，就必须在自己的工具出口上再加一层幂等（**代价：出口幂等表的存储与并发要求**）。

#### 7.3.3 编排模型：编译期确定 vs 运行期展开

**机制是什么**：工作流引擎的图在**提交前确定**（节点与边是定义的一部分）；Agent 的下一步取决于**上一步的输出**（运行期展开）。

**它在各候选中的实现差异**：自建族里的"持久化工作流引擎"候选必须**用引擎的方式表达运行期展开**（例如把"决策节点"做成引擎里的一个步骤，其输出决定下一跳）；编排框架族（图 / 状态机）原生支持条件跳转；托管与产品族通常两者都提供，但**表达力与调试体验差异明显**。

**由此必然导出的性质**：因为**运行期展开的图无法在提交时校验**，所以它的错误只能在运行时暴露——这解释了为什么 Agent 平台必须自带头部 SLO（§4.2（6））与回放，而不是依赖"上线前的静态检查"。

**失效条件**：当任务确实是固定流水线（如"抽取 → 清洗 → 汇总 → 推送"）时，用 Agent 的运行期展开是**过度设计**——固定流水线应该用工作流引擎，它的成本可预测、可静态校验。

#### 7.3.4 变更面：改指针，还是重新部署

**机制是什么**：变更的落点决定回滚速度与灰度能力。

**它在各候选中的实现差异**：自建族是否做到"改指针"取决于你是否实现版本四元组与发布指针（默认没有）；托管与产品族通常内置发布与回滚，但**版本对象的组成由厂商定义**（可能不包含你需要的工具集版本）。

**由此必然导出的性质**：因为**回滚的可复现性取决于版本对象的完整性**，所以只要版本对象缺一项（例如缺工具集版本），回滚后行为就仍可能不同——这不是回滚失败，而是**版本定义不完整**。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| 自建族 | 人力（首版 + 长期维护） | 框架升级、状态存储增长、出口的高可用投入 | 随需求多样性与合规要求增长 |
| 托管族 | 按量计费（token / 调用 / 席位） | 数据出域带来的合规与审计成本；口径不一致导致的对账成本 | 随会话量线性增长 |
| 产品族 | 许可 + 交付（含离线包与适配） | 版本升级依赖厂商、定制项的长期维护、信创适配的重做 | 随租户数与定制深度增长 |

**成本函数的三条判据**：① **自建族的成本曲线是"台阶形"**（人力按人年跳，不是按会话量），会话量小时极贵、大时最省；② **托管族是"线性"**，量小最省、量大最贵；③ **产品族是"阶梯 + 线性"**（许可是台阶、定制与适配是线性）。**因此选型的实质是：先量你的会话量级与合规边界，再看落在哪条曲线的哪一段。**

### 7.5 决策树（每个分支都要有阈值依据）

1. **平台本体 / 状态 / 权重能否离开你的机房？**
   - 否 → **托管族出局**；进入第 2 问。判据来源：这是合规判定，与规模无关（【经验】除极小型团队外，受监管行业一律按"不能出域"计）。
   - 是 → 进入第 4 问。
2. **你的会话是否以长任务为主（`S × T` 大、单个会话耗时可到 `分钟级以上`【经验】）？**
   - 是 → 优先**持久化工作流引擎 + 自建治理面**（复用引擎的恢复能力，别自己写状态机）。
   - 否 → 进入第 3 问。
3. **团队里有没有人能长期维护"编排 + 状态 + 出口"三块？（按 0.5–1 人年的常备投入量级估算【经验】）**
   - 有 → **编排框架 + 自建控制面**（现实默认解）。
   - 没有 → **产品族**（买私有化交付版），把控制面维护转移给厂商。
4. **数据能否出域，但要求"控制面与配额口径由自己掌握"？**
   - 是 → **混合形态**（控制面托管 + 数据面自建），并要求两侧**定期对账**（每周一次的差异核对，见 §4.4 的迁移对拍）。
   - 否（数据也要出域、且追求最快上线）→ **托管族**。

**阈值的诚实说明**：上表的"0.5–1 人年"与"分钟级"是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的排期积压与人时账本校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单团队、短会话、无合规约束 | 编排框架 + 自建控制面 | 托管服务 | 托管对单团队是"治理过剩"，但如果你只有一两个人，托管反而更省 |
| 受监管行业、长任务为主 | 持久化工作流引擎 + 自建治理面 | 私有化产品 | 产品的恢复粒度若粗于步骤，写操作重放风险落到你身上 |
| 多部门共用、行为要可复现 | 编排框架 + 自建控制面 + 版本四元组 | 私有化产品 | 产品的版本对象未必包含工具集版本 |
| 数据敏感但想省治理工程量 | 混合（控制面托管 + 数据面自建） | 私有化产品 | 混合的两个口径要长期对账，隐性成本高 |
| 追求最快上线、数据可出域 | 托管服务 | 混合 | 混合要先自建数据面，首版慢一个季度【经验】 |
| 平台本身是公司核心能力 | 全自研 | 编排框架 + 自建控制面 | 框架直用会在"表达力不足"时被迫改写，改写成本高于一开始自研 |

**组合的两条次序原则**：① **先把治理面（出口 + 配额 + 版本指针）立起来，再选编排层**——因为治理面与业务无关，可复用，而编排层随业务形态变；② **先把状态落点定死，再决定长任务怎么跑**——状态落点换了，长任务实现要重做。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 自建族 → 托管族 | 把状态、出口、配额整体外移 | 会话状态导出、工具改指厂商出口、配额口径替换、审计格式转换 | 以季度计【经验】，且**治理面的历史留痕最难迁** |
| 托管族 → 自建族 | 合规要求变化，必须收回治理面 | 用托管期间的数据重建状态与审计，重做出口与配额 | 以季度计【经验】 |
| 框架直用 → 自研运行时 | 编排表达力到顶，分支逻辑四散在业务代码里 | 把散落的规则收进状态机与决策节点 | 以月计【经验】 |
| 无版本四元组 → 有版本四元组 | 回滚不可复现 | 补四元组的采集与钉版本；历史会话按"不可复现"标注 | 以月计【经验】 |
| 无出口 → 有出口 | 权限与审计无法回答 | 收口所有调用点 + 补幂等与配额；对账消除旁路 | 以月计【经验】，**旁路排查是主要工作量** |

**一条硬结论**：六条路里最贵的迁移是**"治理面归属"的跨族迁移**——它不只是技术搬迁，还包含责任界面与历史留痕的重建。**所以"部署边界"（§7.1 第 1 条）必须在第一版就判对。**

### 7.8 小结

> 本节小结：六个候选之间的差异，最终都能归到三问——**治理面落在谁手里**（自建 / 托管 / 产品）、**状态归谁且恢复粒度多细**、**变更落在指针还是部署上**。三问决定了它们的成本曲线形状（自建是台阶、托管是线性、产品是阶梯 + 线性）与迁移代价（跨族迁移以季度计，同族迁移以月计）。**选型的顺序不可颠倒**：先用部署边界筛掉不可行，再用治理面归属与恢复粒度筛掉不完整，最后才用团队承接能力在剩下的里选——把第 6 条当权重而不是门槛，是第二年最常见的预算超支原因。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案打一次"门槛检查"（不是打分）：部署边界、治理面归属、状态与恢复、工具出口、变更与回滚、团队承接——哪一条是"不满足"而不是"分数低"？那一条就是你明年最可能被迫迁移的方向；而你今天的补救成本，是否还落在"同族迁移（以月计）"这一格里？
