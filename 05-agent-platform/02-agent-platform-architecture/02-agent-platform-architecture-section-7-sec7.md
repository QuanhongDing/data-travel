## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研 / 框架直用 / 托管 / 买产品"打分是常见做法，但它有三个结构性问题：① 同一列在不同处境下方向相反（"可定制"对监管行业是必需、对三个人的团队是浪费）；② 打分表隐含"这些选项互斥"，而真实系统是组合（控制面托管 + 数据面自建很常见）；③ 最关键的判据（部署边界、工具副作用）**不是可打分的维度，而是门槛**——不满足就直接出局。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 部署边界 | 平台本体、状态、权重、工具执行体能否离开你的机房？ | 不能离开 → 托管方案直接出局，这一条是**门槛不是权重** |
| 治理面归属 | 配额、审计、成本归因由谁实现、落在哪一层？ | 治理面不可外包：它是你与业务方之间的责任界面 |
| 状态与恢复 | 会话状态归谁、能否跨重启与跨版本恢复？ | 决定"长任务能不能做"，也决定运维复杂度落在谁身上 |
| 工具出口 | 工具调用能否被收口到唯一出口并做四件事（鉴权 / 校验 / 配额 / 留痕）？ | 收不了口 → 权限与审计永远无法回答 |
| 变更与回滚 | 发布与回滚能否落到"改一个指针"？ | 决定你能否在事故中 30 秒内止损 |
| 团队承接能力 | 有没有人能长期维护编排、状态与出口三块？ | 自建方案的真实成本是**长期人力**，不是首版实现 |

> **读法**：先用第 1 条筛掉不可行；再用第 2、4、5 条筛掉"治理面天生不完整"的方案；最后用第 3、6 条在剩下的方案里选——**第 6 条最容易被跳过，也最容易在第二年变成账单**。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| 全自研运行时与治理面 | 平台即自研产品 | 自己实现状态、队列、出口、配额、发布 | 有平台团队、且平台是核心能力 | 长期人力；首版到可用通常以季度计【经验】 |
| 编排框架 + 自建控制面 | 框架管编排、你管治理 | 编排用框架（图 / 状态机），控制面（版本、配额、审计）自建 | 多数企业的现实选择 | 框架升级与自建治理的接缝要长期维护 |
| 持久化工作流引擎 + 自建治理面 | 把长任务交给引擎 | 步骤持久化与恢复交给引擎，治理面自建 | 长任务为主（报告生成、批量分析） | 引擎的编程模型与 Agent 循环不完全契合，需要适配层 |
| 托管 Agent 平台服务 | 厂商托管控制面与数据面 | 注册即用，配额与审计由厂商提供 | 无部署边界限制、追求最快上线 | 数据与权重可能出域；治理面按厂商口径 |
| 私有化交付版商业平台 | 买产品、装进机房 | 产品自带控制面 / 数据面，交付包含离线包 | 受监管行业、且不愿自建 | 定制受产品边界限制；版本升级依赖厂商 |
| 混合：控制面托管 + 数据面自建 | 分工 | 版本与配额用托管，模型与工具执行留在机房 | 对数据敏感但想省治理工程量 | 两侧的接口成为长期契约负担 |

**这六个候选其实分三族**：**自建族**（全自研、编排框架 + 自建控制面、持久化工作流引擎 + 自建治理面）——治理面在自己手里，代价是长期人力；**托管族**（托管 Agent 平台服务）——上线最快，代价是部署边界与治理口径都由厂商定；**产品族**（私有化交付版商业平台、混合形态）——拿到成品控制面，代价是定制边界与升级依赖。

**族内可替换，跨族不可换**：三个自建候选之间换，动的是编排层与状态层；而"治理面归属"从自建族换到托管族，等于**责任界面整体外移**——这不是技术迁移，是组织决策。

### 7.3 机制差异：为什么它们表现不同（核心节）

**§7.1 的六条判据在本节逐条落位**（这一节不是六条的平铺，而是它们的机制化）：判据 2「治理面归属」→ 7.3.1；判据 3「状态与恢复」→ 7.3.2；判据 5「变更与回滚」→ 7.3.4；判据 4「工具出口」与判据 2 共用 7.3.1——**出口就是治理面的物理落点**，本主题 §4.2（4）里 `egress` 是必填项、缺它不允许注册，就是这条判据的接口形态。剩下两条**不给独立机制单元**：判据 1「部署边界」是门槛不是机制（它在 §7.5 第 1 问直接筛掉候选），判据 6「团队承接能力」是组织约束（它是 §7.4 成本函数里的 `H`）。另有 7.3.3 与 7.3.5 两节不对应 §7.1 的判据，而是本主题特有的两条机制分界：前者决定"图能不能在提交前被校验"，后者决定"计价基准把你的优化目标引向哪里"。（本节的 `A:` / `C:` / `D:` / `E:` 是文件行号简写，依次指主文件、§4 文件、§5 文件、§6 文件——即 `02-agent-platform-architecture.md` 与 `…-section-4-sec4.md` / `…-section-5-ai.md` / `…-section-6-sec6.md`，冒号后为行号。）

#### 7.3.1 治理面的落点：在出口，还是在报表

**机制是什么**：配额与审计只有两种落点——**在调用发生前的出口**（预扣、拦截、留痕），或**在调用发生后的统计**（报表、告警）。

**它在各候选中的实现差异**：

| 候选 | 治理面落点 | 拦截时机 | 结果 |
| --- | --- | --- | --- |
| 全自研 | 出口（你实现） | 调用前 | 可拦截；出口自身成为高可用要求 |
| 编排框架 + 自建控制面 | 出口（自建） | 调用前 | 同上，但出口要与框架的执行模型对接 |
| 持久化工作流引擎 | 出口（自建） | 调用前 | 引擎的步骤边界天然适合挂检查点与配额 |
| 托管服务 | 厂商出口 | 调用前（厂商口径） | 能拦，但**口径与你的成本归属口径未必一致** |
| 私有化产品 | 产品出口 | 调用前 | 能拦，粒度受产品配置项限制 |
| 混合 | 分包：托管侧管版本、自建侧管出口 | 调用前 | 两个口径要定期对账，否则两边数字不一致 |

**由此必然导出的性质**：因为**事后统计的观测点晚于超发点**，所以任何"统计型治理"都不能防止超发——只能事后归因。因此凡是把配额做成报表的方案，其真实语义是"事后知道"，不是"事前约束"。

**公开证据**：主流平台产品的文档都把"配额 / 限流 / 审计"放在**调用链路上的执行点**（网关 / 出口 / 代理），而不是放在分析侧——可按各产品文档中「配额」「限流」章节的当前版本自行核验【公开：以官方文档当前版本为准】。本主题自己的锚点更具体：§4.2（2）的 `invoke_tool` 伪代码把判定顺序写死为「在册 → 有权 → 参数合法 → 未重复 → 已批准 → 有额度」（C:39-59），§4.2（4）的工具注册条目把 `egress: gateway` 列为必填——**缺这一项的工具不允许注册**（C:100-107）。也就是说，"治理面在出口"在本主题不是一句原则，而是一个字段级的约束。

**失效条件**：当存在**旁路**（团队直连目标系统）时，出口型治理全部失效；此时先解决旁路，再谈配额粒度。

#### 7.3.2 状态归谁：进程、引擎，还是平台

**机制是什么**：会话状态存在三处之一——**执行进程内**、**引擎的状态存储**、**平台自己的状态表**。落点决定"谁能恢复"与"恢复粒度"。

**它在各候选中的实现差异**：

| 候选 | 状态落点 | 恢复粒度 | 修复问题的入口 |
| --- | --- | --- | --- |
| 全自研 | 平台状态表 | 步 | 自己的表，任意改 |
| 编排框架 + 自建控制面 | 框架的检查点 / 平台表 | 步或节点 | 框架的持久化接口 |
| 持久化工作流引擎 | 引擎存储 | 步 | 引擎的运维工具 |
| 托管服务 | 厂商存储 | 厂商定义 | 通常不可直接操作 |
| 私有化产品 | 产品存储 | 产品定义 | 需厂商支持 |
| 混合 | 自建侧状态表 | 步 | 自己掌握 |

**由此必然导出的性质**：因为**恢复粒度决定了"重试的最小单元"**，所以恢复粒度粗于步骤的方案，其重试一定会重放更多工作——当工具带副作用时，重放范围越大，幂等键要覆盖的范围也越大。

**公开证据**：这条机制在本书里有两处具名落点。其一，本主题 §6.2 记录 OpenAI 把**会话与步骤做成服务端资源**——调用方创建会话、把消息追加进去、按运行状态取结果，中间步骤是可列举对象（E:114、E:117；核验入口是该产品 API 文档的对象定义与状态说明，**按当前版本核**），这就是"状态外置"被产品化的形态；其二，本主题 §4.2（3）给出可直接照抄的三张表 DDL（`agent_session` / 追加式 `agent_step` / `idem_record`），其中步骤表**追加而不覆盖**的口径是"状态归平台"的实现前提（C:63-92）。§5.3.3 对这条方向给出的成熟度是 **L2**：①（引擎官方文档为正式条目）成立、②（第三方非厂商的 Agent 场景案例）不成立、③（恢复语义是一等接口）成立（D:95；支撑句 D:93）。【公开】（来源：本主题 §6.2；§4.2（3）；§5.3.3；主文件 §1.4「平台化阶段（2024–2025）」条目 A:92）

**失效条件**：当业务要求"恢复时不重复任何已生效的写操作"时，托管与产品方案若不给步骤级恢复，就必须在自己的工具出口上再加一层幂等（**代价：出口幂等表的存储与并发要求**）。

#### 7.3.3 编排模型：编译期确定 vs 运行期展开

**机制是什么**：工作流引擎的图在**提交前确定**（节点与边是定义的一部分）；Agent 的下一步取决于**上一步的输出**（运行期展开）。

**它在各形态上的定性差异**：

| 形态 | 图在何时确定 | 谁决定下一步 | 典型失败形态 |
| --- | --- | --- | --- |
| 固定流水线（工作流引擎的默认用法） | 提交前（节点与边都是定义） | 定义（人） | 图写错在提交时就能发现——这是它的优点；代价是表达不了"看结果再决定" |
| 编排框架（图 / 状态机） | 定义里给出**可跳转的边**，"走哪条边"在运行期选 | 定义给选项，条件或模型来选 | 分支爆炸：边数随决策点增多而增多，图从"可读"变成"读不动" |
| Agent 运行期展开（自建运行时的默认形态） | 只在"这一步"这一层确定 | 模型（上一步的输出） | 错误只在运行时暴露；同一次输入两次运行的路径可以不同 |
| 持久化工作流引擎 + 适配层 | 引擎侧仍是提交前定；"展开"由适配层表达 | 适配层把模型的输出翻译成引擎的下一跳 | 适配层自己变成一个新的状态机；翻译规则一多，引擎的可视化与静态校验同时失效 |
| 托管 / 产品族 | 由厂商定义（两类通常都提供） | 视配置 | 表达力与调试体验差异明显，且**你看到的是产品的抽象，不是引擎的原语** |

**它在各候选中的实现差异**：自建族里的"持久化工作流引擎"候选必须**用引擎的方式表达运行期展开**（例如把"决策节点"做成引擎里的一个步骤，其输出决定下一跳）；编排框架族（图 / 状态机）原生支持条件跳转；托管与产品族通常两者都提供，但**表达力与调试体验差异明显**。

**由此必然导出的性质**：因为**运行期展开的图无法在提交时校验**，所以它的错误只能在运行时暴露——这解释了为什么 Agent 平台必须自带头部 SLO（§4.2（6））与回放，而不是依赖"上线前的静态检查"。

这条性质还有一处工程后果：**"能不能在提交前校验"与"能不能把图读出来"是同一件事**。固定流水线的图可以被下游执行与审计引用——这正是工作流引擎与流程建模工具在书内他处的定位；而运行期展开的"图"是**事后从轨迹里重建**出来的，重建质量取决于留痕字段够不够，本主题 §4.2（6）的 Trace 分段与 §4.5 模板 5 的留痕查询 SQL 就是为这件事服务的。因此这不是"哪种模型更先进"的问题：**你选了运行期展开，就等于把"看懂这张图"的成本从编译期挪到了留痕系统上**，而留痕系统的成本会随会话量线性增长。

**公开证据**：主文件 §2.4 在讨论「Agent 平台 vs 工作流引擎」时给出的结论是**图爆炸**——把 Agent 的运行期决策逐条展开成工作流节点，节点与边会随决策点组合增长（A:193）。这不是推测，它是"用固定图表达运行期展开"这条路的结构性上限。具名实现侧，书内他处可核的有三类：**通用工作流引擎**（Camunda、Flowable 一类——`03-data-stack/12-scheduler/12-scheduler-section-7-sec7.md` §7 把它们列为"面向业务流程与人工审批节点"，并明确指出它们不是数据批次编排）；**分布式工作流引擎**（Temporal——`03-data-stack/07-architecture-decisions/07-architecture-decisions-section-8-sec8.md` §8 第四层记为"高复杂度 + 多步骤场景首选"；`12-architecture/08-data-consistency/08-data-consistency-section-7-sec7.md` §7 的 Saga 行把 Temporal、Cadence、Seata Saga 并列为开源编排引擎）；**编排框架**（LangGraph / AutoGen / CrewAI——`04-data-assetization/05-rag-architecture/05-rag-architecture-section-8-sec8.md` §8 把它们记为 Agentic RAG 的代表实现框架）。**本主题不给"用持久化引擎跑 Agent"的具名生产案例**——引擎有生产案例，而"把 Agent 循环当工作流跑"这一形态的第三方案例核不到（§5.3.3 已下这个结论）。各引擎与框架的编程模型与版本以各自官方文档当前版本为准。【公开】（来源：主文件 §2.4；`03-data-stack/12-scheduler/12-scheduler-section-7-sec7.md` §7；`03-data-stack/07-architecture-decisions/07-architecture-decisions-section-8-sec8.md` §8 第四层；`04-data-assetization/05-rag-architecture/05-rag-architecture-section-8-sec8.md` §8；本主题 §5.3.3）

**失效条件**：当任务确实是固定流水线（如"抽取 → 清洗 → 汇总 → 推送"）时，用 Agent 的运行期展开是**过度设计**——固定流水线应该用工作流引擎，它的成本可预测、可静态校验。

#### 7.3.4 变更面：改指针，还是重新部署

**机制是什么**：变更的落点决定回滚速度与灰度能力。

**它在各候选中的定性差异**：

| 候选 | 变更落点 | 版本对象由谁定义 | 回滚耗时与什么成正比 | 典型失败形态 |
| --- | --- | --- | --- | --- |
| 全自研 | 由你决定（**默认没有指针**） | 你 | 与部署时长（重打包 + 预热）成正比 | 改完提示就直接发，行为变了说不清是"哪一次改动" |
| 编排框架 + 自建控制面 | 框架管流程版本；提示与工具集版本要自建 | 你 + 框架 | 同上，但流程版本可单独回滚 | 流程回滚了、提示没回滚，行为仍然不同 |
| 持久化工作流引擎 | 引擎管"代码版本"，提示与模型路由在外面 | 引擎定义代码版本 | 与引擎的版本注册机制有关 | 引擎回滚到旧代码，但模型档位换了——仍不可复现 |
| 托管服务 | 厂商的发布对象 | 厂商 | 近似常数（改指针） | 版本对象里没有"工具集版本"这一项 |
| 私有化产品 | 产品的发布对象 | 厂商（你只能配置） | 常数，或与产品升级周期绑定 | 定制项不在版本对象内，回滚会丢定制 |
| 混合 | 两侧各一套 | 分侧 | 托管侧近似常数；自建侧与部署成正比 | 两侧版本不同步，同一会话跨侧时行为翻转 |

**它在各候选中的实现差异**：自建族是否做到"改指针"取决于你是否实现版本四元组与发布指针（默认没有）；托管与产品族通常内置发布与回滚，但**版本对象的组成由厂商定义**（可能不包含你需要的工具集版本）。

**由此必然导出的性质**：因为**回滚的可复现性取决于版本对象的完整性**，所以只要版本对象缺一项（例如缺工具集版本），回滚后行为就仍可能不同——这不是回滚失败，而是**版本定义不完整**。

这条性质决定了"回滚"在 Agent 平台上的**可验收形态**：它不是"我们有一键回滚"，而是"回滚之后能回答**现在跑的是哪一组东西**"。可自测的动作是：取最近若干次行为变更，逐次回答它对应哪个版本四元组、回滚要多久；连续两次以上答不出来【经验：两次是区分"偶发漏记"与"系统性没有指针"的最低样本，可按你的变更频率上调】，说明缺的不是回滚脚本，而是版本指针。本主题 §4.5 模板 3 的灰度规则（按会话失败率与单会话成本两个窗口指标触发）与 §2.3 的版本四元组是同一件事的两端——**四元组是"能回滚"的前置，guardrail 是"该回滚"的触发器**；只有触发器而没有四元组时，自动回滚会把平台带到一个说不清的状态。

**公开证据**：本主题 §6.1 记录微软把 Agent 的构建侧（提示 / 工具 / 知识源 / 渠道，带版本号）与运行侧（会话与消息）分成两组公开接口，于是**发布与回滚成为产品级操作、而不是部署动作**（E:25；核验入口是该产品官方文档的版本与发布章节，**按当前版本核**）。作者给出的量级是：回滚从"重新部署执行体"的分钟级【经验】变成"切换发布版本"的秒级【经验】（E:90），并给了自测动作——统计最近若干次变更"从提交到可控上线"的端到端时长（E:92）。§5.2 的分级表把「控制面 / 数据面分离」记为 **L2**：①（有正式产品文档条目）成立、③（发布 / 回滚是产品级接口）成立、②（第三方非厂商生产案例）在本主题核不到（D:25、D:33）。【公开】（来源：本主题 §6.1；§5.2 分级表第 1 行与表后说明；§2.3 版本四元组；§4.5 模板 3）

**失效条件**：当变更落点不在你的控制面上时（厂商托管，或产品把版本对象固定成厂商口径），"改指针"这件事在技术上成立、但在**归因上不成立**——你改了指针，却无法把观测到的行为差异映射回自己那一项（例如工具集版本）。此时正确的动作不是继续找更好的发布工具，而是**把不可控的那一项做成可控的**：工具集版本由你自己的工具注册表出（§4.2（4）的注册条目即这一项的载体，C:98-107），模型路由由你自己的模型接入层出（§4.1 第 4 步，C:9-18）。**两处都在自建侧，都不需要动托管侧的发布机制**——这是"混合"这一候选在变更面的真实价值。

#### 7.3.5 计价口径：按什么收费，决定了你把哪个指标当成 KPI

**机制差异**：三个方案家族的计价基准不同——**自建族**的实际支出是人力（人年），用量不直接进入账单；**托管族**按 token / 调用 / 会话 / 席位计费，用量与账单近乎线性；**产品族**按许可（席位或节点）+ 交付适配收费，用量藏在许可容量里。

| 家族 | 计价基准 | 支出形状 | 优化靶点被引向 | 典型反向激励 |
| --- | --- | --- | --- | --- |
| 自建族 | 人力（人年） | 台阶形 | 减少人月 | 把治理面做薄、把复杂度推给业务方 |
| 托管族 | token / 调用 / 会话 / 席位 | 近线性 | 每次调用用多少 token | 为压 token 而牺牲能力（过度压缩上下文、过度降档） |
| 产品族 | 许可（席位 / 节点）+ 交付适配 | 阶梯 + 线性 | 把许可容量用满 | 把不该上平台的 Agent 也搬上来 |

**为什么这是一个机制差异而不是商务差异**：因为**计价基准决定了"谁在为什么负责"**。

- 当账单随 token 线性增长时，**成本优化的靶点自然落在"每次调用用多少 token"**——于是提示压缩、缓存、模型分级会被主动推进（同 [Ch11 §03 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md) 的"成本必须可归因到 Owner"）。
- 当支出是人力（台阶形）时，**成本优化的靶点变成"减少人月"**——于是会倾向"把治理面做薄、把复杂度推给业务方"，而这恰好是治理缺口最常见的来源。
- 当支出是许可时，**靶点变成"把席位用满"**——于是会出现"为了不浪费许可而把不该上平台的 Agent 也搬上来"的反向激励。

**它对架构决策的影响**：**不要把"单价便宜"当成选型依据，要问"计价基准会把你的优化目标引向哪里"**。一个可核查的做法是：拿你现在的实际账本，算出三个家族口径下的**等效单价**（自建族 = 年度人力 ÷ 年会话数；托管族 = 账单 ÷ 年会话数；产品族 = 许可 + 适配 ÷ 许可容量内实际用量），再比较量级。**这一步把"感觉贵"变成"在哪一段贵"。**

**边界**：等效单价只用于**同一量级内的比较**。它不能跨量级外推（台阶形的曲线在小量级永远贵），也不能解释"合规不可迁"这类门槛（那是 §7.1 第 1 条的事，不是成本问题）。

**公开证据**：本主题**不给任何计价数字**——单价与计费口径一律以各厂商官方文档当前版本为准，这里给的只是可自查的口径结构。可核的口径纪律有两处：其一在书内他处，`11-cross-cutting/03-data-cost-finops` 把"成本必须可归因到 Owner"立为原则（即本节开头所引的 [Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)）；其二在本主题内部——主文件 §2.2 的成本归因公式与 §4.6 的成本四块是这条原则在 Agent 平台上的落地形态（A:152-157、C:227-234），主文件 §2.2 另给出一条可自测的警报线：**平台固定成本 ÷ 模型成本 > 1 时，平台自身开销成了主项**（A:159）。托管族一侧的成本机制（配额预扣、执行、实际结算的三段式）见 §2.2 的 reserve-then-settle 形式化（A:144-150）与 §4.6 的单会话成本算例【经验 + 推算】。【公开：书内可核验；外部单价与计费维度以厂商官方文档当前版本为准】

**失效条件**：当计价基准与你的增长方式**反向**时，这条机制差异才真正咬人——例如计价按席位走、而你的调用量在涨，或计价按用量走、而你的会话数在涨但单会话成本在降。反向时，"单价便宜"这个结论会被规模吃掉；只有同向时，等效单价的比较才有意义。另一处失效：当"合规不可迁"成立时（§7.1 第 1 条），计价口径完全退出决策——**它不是成本问题，是门槛问题**，把两者混在同一张表里比较，是选型会上最常见的错位。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| 自建族 | 人力（首版 + 长期维护） | 框架升级、状态存储增长、出口的高可用投入 | 随需求多样性与合规要求增长 |
| 托管族 | 按量计费（token / 调用 / 席位） | 数据出域带来的合规与审计成本；口径不一致导致的对账成本 | 随会话量线性增长 |
| 产品族 | 许可 + 交付（含离线包与适配） | 版本升级依赖厂商、定制项的长期维护、信创适配的重做 | 随租户数与定制深度增长 |

**成本函数的三条判据**：① **自建族的成本曲线是"台阶形"**（人力按人年跳，不是按会话量），会话量小时极贵、大时最省；② **托管族是"线性"**，量小最省、量大最贵；③ **产品族是"阶梯 + 线性"**（许可是台阶、定制与适配是线性）。**因此选型的实质是：先量你的会话量级与合规边界，再看落在哪条曲线的哪一段。**

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：V = 年会话数（万次）   H = 常备人力（人年）   P = 许可与交付（万元）
    c = 单会话托管成本（元/次，含 token 与调用）   u = 单位适配成本（万元/租户）

自建族：  Cost_self(V) = H × 人均年成本                    ← 与 V 无关（台阶形）
托管族：  Cost_managed(V) = V × c                          ← 与 V 线性（斜率 c）
产品族：  Cost_product(V) = P + n_tenant × u               ← 台阶 + 按租户数线性

令 Cost_self = Cost_managed，解出「自建开始划算」的会话量：
    V* = (H × 人均年成本) / c      【推算】
```

**这个式子的用法**：代入你自己的 `H` 与 `c`，`V*` 就是你该不该自建的分水岭。**注意 `H` 不是首版人力，而是常备人力**——首版做完之后，"编排 + 状态 + 出口"三块仍然要有人跟（§7.5 第 3 问给的 `0.5–1 人年` 量级【经验】就是估这一项）。**把 `H` 按首版估算，是本类选型里最常见的低估**：首版的人力是一次性投入，而它决定的是"能不能做出来"，不是"要不要长期持有"。

**成本之外还有一条不进入任何曲线的东西**：**治理面的历史留痕**。它在三个家族里的可迁移性都最差（§7.7 的硬结论），而且它的价值**随持有时间增长**（留痕越长，复盘可回溯的范围越大）。因此在接近 `V*` 的区间里，**"已经积累了多长时间的留痕"应当作为一个偏向"不迁"的权重**，而不是把两边的账单直接相减。

### 7.5 决策树（每个分支都要有阈值依据）

1. **平台本体 / 状态 / 权重能否离开你的机房？**
   - 否 → **托管族出局**；进入第 2 问。判据来源：这是合规判定，与规模无关（【经验】除极小型团队外，受监管行业一律按"不能出域"计）。
   - 是 → 进入第 4 问。
2. **你的会话是否以长任务为主（`S × T` 大、单个会话耗时可到 `分钟级以上`【经验】）？**
   - 是 → 优先**持久化工作流引擎 + 自建治理面**（复用引擎的恢复能力，别自己写状态机）。
   - 否 → 进入第 3 问。
3. **团队里有没有人能长期维护"编排 + 状态 + 出口"三块？（按 0.5–1 人年的常备投入量级估算【经验】）**
   - 有 → **编排框架 + 自建控制面**（现实默认解）。
   - 没有 → **产品族**（买私有化交付版），把控制面维护转移给厂商。
4. **数据能否出域，但要求"控制面与配额口径由自己掌握"？**
   - 是 → **混合形态**（控制面托管 + 数据面自建），并要求两侧**定期对账**（每周一次的差异核对，见 §4.4 的迁移对拍）。
   - 否（数据也要出域、且追求最快上线）→ **托管族**。

**阈值的诚实说明**：上表的"0.5–1 人年"与"分钟级"是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的排期积压与人时账本校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单团队、短会话、无合规约束 | 编排框架 + 自建控制面 | 托管服务 | 托管对单团队是"治理过剩"，但如果你只有一两个人，托管反而更省 |
| 受监管行业、长任务为主 | 持久化工作流引擎 + 自建治理面 | 私有化产品 | 产品的恢复粒度若粗于步骤，写操作重放风险落到你身上 |
| 多部门共用、行为要可复现 | 编排框架 + 自建控制面 + 版本四元组 | 私有化产品 | 产品的版本对象未必包含工具集版本 |
| 数据敏感但想省治理工程量 | 混合（控制面托管 + 数据面自建） | 私有化产品 | 混合的两个口径要长期对账，隐性成本高 |
| 追求最快上线、数据可出域 | 托管服务 | 混合 | 混合要先自建数据面，首版慢一个季度【经验】 |
| 平台本身是公司核心能力 | 全自研 | 编排框架 + 自建控制面 | 框架直用会在"表达力不足"时被迫改写，改写成本高于一开始自研 |

**组合的两条次序原则**：① **先把治理面（出口 + 配额 + 版本指针）立起来，再选编排层**——因为治理面与业务无关，可复用，而编排层随业务形态变；② **先把状态落点定死，再决定长任务怎么跑**——状态落点换了，长任务实现要重做。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 自建族 → 托管族 | 把状态、出口、配额整体外移 | 会话状态导出、工具改指厂商出口、配额口径替换、审计格式转换 | 以季度计【经验】，且**治理面的历史留痕最难迁** |
| 托管族 → 自建族 | 合规要求变化，必须收回治理面 | 用托管期间的数据重建状态与审计，重做出口与配额 | 以季度计【经验】 |
| 框架直用 → 自研运行时 | 编排表达力到顶，分支逻辑四散在业务代码里 | 把散落的规则收进状态机与决策节点 | 以月计【经验】 |
| 无版本四元组 → 有版本四元组 | 回滚不可复现 | 补四元组的采集与钉版本；历史会话按"不可复现"标注 | 以月计【经验】 |
| 无出口 → 有出口 | 权限与审计无法回答 | 收口所有调用点 + 补幂等与配额；对账消除旁路 | 以月计【经验】，**旁路排查是主要工作量** |

**一条硬结论**：六条路里最贵的迁移是**"治理面归属"的跨族迁移**——它不只是技术搬迁，还包含责任界面与历史留痕的重建。**所以"部署边界"（§7.1 第 1 条）必须在第一版就判对。**

### 7.8 小结

> 本节小结：六个候选之间的差异，最终都能归到三问——**治理面落在谁手里**（自建 / 托管 / 产品）、**状态归谁且恢复粒度多细**、**变更落在指针还是部署上**。三问决定了它们的成本曲线形状（自建是台阶、托管是线性、产品是阶梯 + 线性）与迁移代价（跨族迁移以季度计，同族迁移以月计）。**选型的顺序不可颠倒**：先用部署边界筛掉不可行，再用治理面归属与恢复粒度筛掉不完整，最后才用团队承接能力在剩下的里选——把第 6 条当权重而不是门槛，是第二年最常见的预算超支原因。

### 7.9 智能体框架横比：把 §7.1 的判据落到框架上

| # | 判据 | 问的问题 | 为什么它可判定 |
| --- | --- | --- | --- |
| 1 | 人审闸门 | 能不能在"等人工批准"这一步**停下来**、隔一段时间再**接着跑**？ | 人审只有被定义成一个**可恢复的步**才算原语；停不下来的框架里，"等"只是一句注释而不是闸门，代价被折算成**进程占用** |
| 2 | 状态与续跑 | 状态落在哪（进程内 / 框架的检查点 / 外部存储）？进程重启后能不能接着跑？ | 与 §7.3.2 同源：**恢复粒度决定重试的最小单元**；粒度粗于步骤，重放范围与幂等键要覆盖的范围同时变大 |
| 3 | 编排模型 | 下一步由**定义**定，还是由**上一步的输出**定？ | 与 §7.3.3 同源：图在提交前确定还是运行期展开，决定"能不能在提交前校验"，也决定"看懂这张图"的成本落在编译期还是留痕系统上 |
| 4 | 工具注册 | 工具是**声明式注册表**里的一项，还是代码里的一处调用？ | 与 §7.1 判据 4 同源：**只有注册表是声明式的，出口才收得了口**；调用点散在代码里，鉴权 / 校验 / 配额 / 留痕就没有唯一落点 |
| 5 | 退出成本 | 你在它上面已经**定义了多少个对象**？ | 换框架的迁移成本**不是代码行数，而是"要重写的对象数"**【经验】。本书他处已有同类做法：`13-decision/03-build-vs-buy/03-build-vs-buy-section-4-sec4.md` §4 的 Vendor Lock-in 评估表把每项锁定风险"折成什么数"时，用的正是「需重写的调用点数量」「需重写的作业数量」，并给了同一条纪律——**演练工时是最诚实的退出成本** |

> 第 5 条是本节的枢轴：**迁移成本 = 对象数**。它把"要不要换框架"从技术品味问题变成一个可以数的量——数你在框架里注册的工具、定义的节点、写的扩展点、存的检查点。**对象数少时换便宜，但那时你往往还没遇到需要换的问题；真遇到问题时对象数已经很多了**——这是框架选型的结构性两难，也是 §7.9.5 要解决的事。

#### 7.9.5 什么时候该换框架：可判定的触发信号

下面六条都是**可自测**的信号；任一条**持续**成立，就说明判据已经翻转——**翻转的理由不是"出现了新框架"**：

1. **你开始为框架写适配层**——把"框架表达不了的东西"翻译成框架能吃的形式。同一类信号在 §7.2 已经出现过：它正是"持久化工作流引擎 + 自建治理面"这一候选被记下的代价（"引擎的编程模型与 Agent 循环不完全契合，需要适配层"）。适配层一旦变成你自己的状态机，框架就只剩一个壳。
2. **你开始把分支逻辑写进业务代码**——§7.7 表里「框架直用 → 自研运行时」的症状一栏写的正是「编排表达力到顶，分支逻辑四散在业务代码里」，迁移量级记为**以月计**【经验】。
3. **你的对象数增长快于功能数**——按 §7.9.1 第 5 条数：你在框架里注册的工具、定义的节点、写的扩展点，只增不减，且换框架就要逐个重写。这时你已经在为退出成本付利息——**越晚换越贵，因为对象数只会涨**。
4. **工具出口收不了口**——调用点散落在框架的不同扩展点上，挂不到一个出口（§7.1 判据 4）。这是**门槛不满足**、不是"分数低"：出口收不了口，权限与审计永远无法回答。
5. **人审只能靠"等"**——合规要求"人批完再继续"，而框架只能做到"人批期间进程不许退出"（§7.9.1 判据 1）。它同时踩到判据 2：状态没有落在一个可恢复的步上。
6. **反向信号：状态已经不在框架里**——当检查点与状态已经落在你自己的存储上（§7.3.2 的"状态归平台"），换框架动的是编排层、状态不用搬，此时迁移落在 §7.7 的**同族**一侧。**这是唯一一种"换了不亏"的情形**，也是 §7.3.2 那条性质在框架层的用处。

**一条反向纪律**：如果触发信号来自"某个新框架发布了"，而上面六条一条都不成立，那按本章 §5.1 的三类分法它是**第 3 类（只多了产品）**——只该改选型表里的一行，不该动架构图。**把第 3 类当第 1 类处理，代价是引入一套没有机制差异的新组件**；这也正是本节把横比写成判据、而不是写成排行的原因。

**失效条件**：当框架选型被组织约束绑定时（团队已有某框架的交付记录，或平台的其他部件已经钉在同一生态上），这六条信号都成立也未必该换——此时正确的动作是**先把对象数压下来**（把工具注册、状态、出口三样收回自己手里），让下一次选择的成本变低，而不是立刻迁移。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案打一次"门槛检查"（不是打分）：部署边界、治理面归属、状态与恢复、工具出口、变更与回滚、团队承接——哪一条是"不满足"而不是"分数低"？那一条就是你明年最可能被迫迁移的方向；而你今天的补救成本，是否还落在"同族迁移（以月计）"这一格里？
