## 6. 落地实践

> **本节的材料纪律（先说清楚）**：平台层的公开材料以**产品文档与规范**为主——产品的对象模型、发布方式、部署形态是公开的，而**企业内部平台的细节（多租户隔离怎么做、配额超发怎么拦）极少公开**。因此本节 4 例的构成是：
>
> - **§6.1–§6.3** 是**产品文档层面的机制复述**（哪一组接口被设计出来了、发布与回滚以什么形式存在、部署形态覆盖到哪），**不是对任何一家内部实现的转述**；方括号内是**来源类型 + 年份**（如「微软公开材料 2019-2024」），属**建设方自述**，不构成本书 §5 判据里要求的「第三方（非厂商）公开生产案例」，读者需按其官方材料自行核验。
> - **§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证。
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的精确数值，请以你所在平台的实测口径为准。

### 6.1 微软"**把"定义"与"运行"做成两个面：发布与回滚成为产品级接口 5+ 年**"（2019-2024）

**背景（Why）**

把 Agent 能力交给业务方自助构建时，平台最先撞上的是**"定义"与"运行"混在一起**：

- **定义在变、运行在跑**——提示、工具、知识源每天都在改，而正在跑的会话不能因为改定义而中断；两者若在同一个部署单元里，"改定义"就等于"重启运行"。
- **业务方要自助、平台方要可控**——业务方希望自己改提示、加知识源；平台方需要知道"哪一次改动影响了哪一个会话的结果"。
- **交付形态不止一种**——同一套能力既要能跑在公有云，也要能进受限环境（数据与日志不出域）；如果运行时的设计假设了某个云的存在，第二种交付形态要重做一遍。

**触发点（What）**

微软在企业侧把 Agent 的构建与运行分成了两组公开接口（[微软公开材料 2019-2024]，核验入口是该产品的官方文档，**按当前版本核**）：**构建侧**是 agent 的定义对象——提示与指令、可用工具 / 连接器、知识源、发布渠道；**运行侧**是会话与消息的收发。目标有三条：

- **定义可版本化**——发布是一等操作，回滚不必重新部署；
- **渠道与核心解耦**——同一个 agent 定义可发布到多个入口（内部站点、协作工具、自定义应用）；
- **部署形态可选**——从公有云到受限环境，运行时不假设公网存在。

**详细做法（How）**

**① 定义对象与运行对象分离（核心设计）**

- **关键设计**：**构建侧的每一次改动都落在一个"定义版本"上，运行侧只按"某个已发布版本 + 某个会话"执行**——这正是本主题 §3.2.3 的控制面 / 数据面分离，只是它被产品化为两组 API 而不是一张架构图。
- **关键性质**：**回滚的对象是"版本"，不是"进程"**——因此回滚的耗时与部署时长无关，与"指针改没改"有关。
- **关键示意**：

  ```text
  平台化的最小对象模型（构建侧 / 运行侧）
    ── 构建侧（定义，改它不影响正在跑的会话）─────────────
       AgentDefinition
         instructions      ← 系统提示（版本化）
         tools[]           ← 工具 / 连接器（带 Schema 与权限范围）
         knowledge[]       ← 知识源（带可见域）
         channels[]        ← 发布渠道
         version           ← 每次发布产生一个新的版本号
    ── 运行侧（执行，按版本钉住）─────────────────────────
       Session
         agent_version     ← 发起时钉住，整个会话期间不变
         messages[]        ← 追加写
         steps[]           ← 每步：模型调用 / 工具调用 / 结果
    ────────────────────────────────────────────────
   判据：能否回答"这次行为变化对应哪个 agent_version"——
        答不出，说明定义还没被版本化，只是存在配置里
  ```

**② 发布渠道作为定义的一部分**

- **关键设计**：**渠道是定义的一个字段，不是一次额外的集成工作**。这样"同一个 agent 上多个入口"不会导致定义分叉——否则每个渠道一份提示，行为漂移只是时间问题。
- **为什么有效**：它把"多渠道"的成本从「渠道数 × 集成工作量」降到「一次定义 + 渠道配置」。

**③ 部署形态前置到设计期**

- **关键设计**：运行时不依赖公网，遥测与依赖更新都有本地路径；交付包（镜像 + 定义初始化 + 权重校验清单）是一个可离线安装的单元。
- **为什么必须**：受限环境（数据与日志不出域）不是"另一种部署方式"，而是**对运行时的一组硬约束**——设计期不满足，交付期无法补救（§6.4 的失败教训正是这一条）。

**具体数字（档位标注）**

- 发布与回滚的时间尺度：从"重新部署执行体"（分钟级【经验】）变成"切换发布版本"（秒级）——**这是本节四例共同的最大收益**，也是"变更落点"这句话的可测形式。
- 渠道复用带来的工作量差：同一定义上第 2 个渠道的边际成本显著低于第 1 个（第 1 个要建渠道适配与鉴权，其后是配置）【经验：随渠道类型差异较大，请按自己的渠道类型自测】。
- **自测动作**（替代无法核验的供应商内部数字）：取最近 10 次行为变更，统计"从提交到可控上线"的端到端时长，并回答每次对应的 `agent_version`。

**失败教训**

**第一版把"渠道"当成集成工作而不是定义的一部分**——每个渠道各自维护一份提示与工具清单，三个月后同一个 agent 在两个入口的回答风格已经不同，而团队无法解释差异的来源。教训：**多渠道的一致性不能靠纪律维持，必须由"定义唯一"这个结构保证。**

### 6.2 OpenAI"**把会话与步骤做成可查询的资源：平台化的最小对象模型 2+ 年**"（2023-2024）

**背景（Why）**

把 Agent 做成 API 时，最容易被低估的是**"状态该由谁持有"**：

- **调用方不想管状态**——如果每一步都要求调用方把整个对话历史回传，前端与后端都要维护一份"对话的本地副本"，长度、截断、并发都会成为应用侧的问题。
- **长任务需要"中途等外部"**——Agent 发起一次工具调用后，结果可能由**人**提供（审批）或由**外部系统异步**提供；这段等待必须能被平台表示出来，而不是让调用方轮询自己的逻辑。
- **排障需要"每一步可见"**——只知道"最终答案不对"无法定位；需要能取回"第几步调了什么、参数是什么、返回了什么"。

**触发点（What）**

OpenAI 的对话 / 助手类接口把会话状态做成了**服务端资源**（[OpenAI 公开材料 2023-2024]，核验入口是其 API 文档的对象定义与状态说明，**按当前版本核**）：调用方创建会话，把消息追加进去，发起一次运行，然后按运行的状态取结果；中间步骤是可列举的对象。它对平台的启示不在"能力"，而在**对象模型的取舍**：

- **会话与运行分离**——"会话"是长生命周期的容器，"运行"是一次执行尝试（失败可重试，会话不重建）；
- **步骤可列举**——模型调用与工具调用都落成步骤对象，带类型与状态；
- **"等待外部输入"是一个显式状态**——不是超时，也不是失败。

**详细做法（How）**

**① 用状态机表示"等外部输入"（本条最值得抄）**

- **关键设计**：运行的状态里包含一个**"需要外部动作"**的状态——工具调用发出后，运行挂在那里，等结果回填后**继续同一次运行**；而不是把这次运行标记成失败、让调用方重新发起。
- **关键性质**：**"等人"是一个有超时的状态，不是一个异常**。这一条直接对应本主题 §2.3 的「人审闸门必须有超时」，以及 §3.2.7 的"人审无超时会把吞吐锁死"。
- **关键示意**：

  ```text
  运行状态机（含人审闸门的最小正确集）
    queued → in_progress → { requires_action → in_progress }ⁿ → completed
                         ↘ failed      （可重试 / 不可重试要分开）
                         ↘ cancelled   （用户或策略中止）

    其中 requires_action 的语义是：
      平台发出了一次"需要外部提供结果"的动作（典型是人审，
      也可以是外部系统异步回调），运行在此挂起并等待回填。
    必须写进设计的三条：
      ① requires_action 必须有超时——超时后默认"拒绝"而不是"继续"
      ② 回填的内容必须与超时窗口绑定——过期的批准不能生效
      ③ 挂起中的运行仍占配额与并发额度，所以闸门的适用范围要收窄
  ```

**② 步骤对象作为可观测的最小单元**

- **关键设计**：把"模型调用"与"工具调用"都落成可列举、可取的**步骤**，而不是只留一条总日志。
- **为什么有效**：它让"成本归因到会话"与"回放定位到步"同时成立——**这两件事需要的是同一份数据**（§5.3.4 的字段约定正是它的行业化版本）。

**③ 失败与重试的边界划在"运行"上**

- **关键设计**：一次运行失败不等于会话失败——调用方可以就同一会话再发起一次运行。**这个划分让"重试"不必由应用自己实现**，但同时要求平台给出幂等语义（§2.3 的幂等键）。

**具体数字（档位标注）**

- 状态写入量（可自算的部分）：设每步状态 `2–10 KB`、单会话 `S = 8` 步、日活会话 `30 万`，则日写入约 `4.8–24 GB`【推算：30 万 × 8 = 240 万步；每步字节数取本节通用区间（口径=会话数 × 步数 × 单步字节数）】。**这个数字决定检查点存储的选型**，与"用哪家 API"无关。
- 挂起运行的并发占用：每个 `requires_action` 中的运行在等待期内仍占一份并发额度；设审批平均时长 `H_human`、到达率 λ，则需要的并发余量为 `λ × H_human`【推算：由利特尔法则 L = λW 直接得到】——**这就是"人审闸门会吃掉多少并发"的算法**，也是最容易被漏算的一项。
- **自测动作**：统计你系统里"等待人工 / 等待外部回调"的平均时长与并发占用；若它超过总并发的两成，先做 §3.2.7 的"收窄闸门适用范围"，而不是扩容。

**失败教训**

**第一版把"等待人工批准"实现成了一种超时**——请求在几分钟后返回"失败"，用户重新发起，而批准随后到达，于是同一个动作被执行两次。教训：**"等人"是状态，不是异常；把它当异常处理，就会同时引入"丢批准"和"重复执行"两个缺陷。**

### 6.3 字节"**扣子 Coze：把插件、工作流与知识库收进同一个构建面 2+ 年**"（2023-2024）

**背景（Why）**

面向非工程用户的 Agent 平台，第一道门槛不是模型能力，而是**"能不能不写代码就把能力拼出来"**：

- **能力来源分散**——外部 API、数据库、知识文档、固定流程，各自需要不同的接入方式；
- **业务方要自己搭**——如果每加一个能力都要工程师介入，平台就退化成了外包窗口；
- **搭出来的东西要能发布**——能跑在演示页上，不等于能挂到业务真正在用的入口上。

**触发点（What）**

扣子 Coze 把构建侧拆成**四类可复用的构建块**（[字节公开材料 2023-2024]，核验入口是平台的官方文档，**按当前版本核**）：**插件**（外部能力的封装）、**工作流**（可编排的步骤图）、**知识库**（文档与检索）、**机器人 / 智能体定义**（提示与编排的组合）；并把**发布渠道**作为定义的出口。它的启示在于**构建面的划分方式**：

- **把"能力接入"和"流程编排"分成两种构建块**——插件解决"能调什么"，工作流解决"按什么顺序调"；
- **把知识做成一个构建块**——不需要每次重讲"怎么接检索"；
- **构建面与运行面之间隔着发布**——搭好不等于上线。

**详细做法（How）**

**① 构建块化：把"集成"从项目工作变成配置工作**

- **关键设计**：每一类构建块（插件 / 工作流 / 知识库 / 提示）都有统一的描述结构与复用边界；业务方组合它们，而不是每次从零写集成代码。
- **为什么有效**：**接入的知识被沉淀在构建块里，而不是散在每个项目里**——这正是"平台"与"一堆项目"的分界（同 [Ch7 §03 资产管理](../../07-agent-evolution/03-asset-management/03-asset-management.md) 对"资产复用"的定义）。
- **代价**：构建块的抽象一旦定下，**平台的能力上限就被它框住了**——业务方要的东西落在构建块之外时，只能等平台扩展；因此构建块的粒度是这类平台最重要的设计决策。

**② 发布渠道列表化**

- **关键设计**：发布是一张渠道清单；每个渠道是一条已备案的出口。**这与 §6.1 的"渠道属于定义"是同一件事的两种表述**，两者都指向"多渠道不产生多份定义"。

**③ 运行面的配额与计量落在平台侧**

- **关键设计**：业务方自助构建之后，**用量必须回到平台侧结算**（否则自助化会直接变成账单失控）。这要求构建面与运行面共享同一套租户与配额模型（§4.2（6））。

**具体数字（档位标注）**

- 构建块复用的收益口径：**同一构建块被 `k` 个项目复用**时，平台侧的总接入工作量从 `O(k × 单次接入)` 降到 `O(单次接入 + k)`【推算：假设每新增一个构建块需要一次平台侧审核，而重复使用同一构建块只需配置；这是平台化的标准收益形状，不依赖具体产品】。
- **自测动作**（替代无法核验的内部数字）：统计你平台上"新增一个外部能力"的平均人日，以及其中"可复用的部分"占比。**若可复用部分不足三成，说明构建面的抽象还没有形成，平台只是换名字的项目空间。**

**失败教训**

**第一版只有"工作流"一种构建块**——所有能力接入都被写成工作流里的一个节点，结果是同一个数据库连接被复制进了几十个工作流；改一次连接字符串要改几十处。教训：**构建块的划分要按"变化频率"而不是按"使用位置"**——连接配置的变化频率远低于流程逻辑，它就该是一类独立的、可复用的构建块。

### 6.4 某大型制造企业"**把 Agent 平台交付进不联网的机房：部署边界在设计期输入 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

制造企业的产线数据与工艺参数不允许出域，客户的要求是**"平台装在机房里，且机房不与公网相连"**。平台团队此前交付的都是公有云版本，第一判断是"把部署方式改一下"。

**触发点（What）**

**现场安装到一半失败**：镜像需要从公网拉取、模型权重需要在线下载校验、某个依赖组件在启动时解析外部域名。客户的结论是"你们的产品装不上"——而这时距离合同约定的交付窗口只剩一周。

**详细做法（How）**

**① 把"部署边界"从交付问题提前成设计约束（核心修正）**

- **关键设计**：把 §3.1 的第 1 条约束（部署边界）写进设计评审的必答项：**平台本体、状态存储、权重、工具执行体、遥测，这五项能不能全部在无公网环境内闭环？** 每一项都要给出"依赖清单 + 替代路径"。
- **为什么必须前置**：这五项里任何一项假设公网，都不是"打补丁"能解决的——**依赖公网的是运行时行为，不是配置文件**。

**② 离线交付包的四个必须项**

| 交付项 | 内容 | 验收判据（可勾选） |
| --- | --- | --- |
| 镜像与编排文件 | 全部镜像（含基础镜像）+ Chart / 清单 | 在一个**全新断网**环境里装一次，零公网请求 |
| 权重与校验 | 权重入内网对象存储 + 哈希清单 | 哈希不匹配即安装失败（避免"装了但不知道装的是哪版"） |
| 初始化数据 | 种子数据、默认定义、示例配置 | 装完后平台可登录、可发起一次会话 |
| 运维路径 | 日志与指标的本地留存与导出、升级包的内网传递与审批 | 能导出一天的审计记录；能演练一次离线升级 |

**③ 信创适配按"算子清单"而不是按"整体跑通"验收**

- **关键设计**：把关键路径上的算子（向量检索、量化推理内核、Python 扩展、压缩 / 加密库）列成清单，在目标架构上**逐个**跑通并记录精度差异；差异不可解释的写进"不支持清单"并在合同里明确。
- **为什么这样切**：整体跑通只能给出"能启动"这个结论，而**客户真正关心的是"结果是否与 x86 上一致"**——那是逐算子的精度问题，只能逐算子回答。

**具体数字（档位标注）**

- 交付包体积：以"镜像 + 权重"两项为主，**权重通常是决定项**（参数量 × 精度位数）【推算：权重字节数 ≈ 参数量 × 每参数字节数；例如 70B 参数、FP16 约 140 GB，量化到 INT8 约 70 GB，再考虑张量并行切分的副本数】——**不给统一数字，因为任何统一数字都会在你自己的模型上失效**。
- 离线安装时长：与镜像层数、权重体积、磁盘吞吐相关，**区间比点值有意义**（同一套包在不同客户的存储上可以差数倍）【经验】。
- **自测动作**：在一台**从未联网**的机器上（不是"拔网线的机器"）完整安装一次并记录耗时与失败点——这是唯一能证明"零公网依赖"的动作。

**失败教训**

**把"私有化"当成部署方式而不是架构约束**——第一次交付后才逐项发现，平台的遥测、依赖更新、许可校验在设计上都假设了公网存在。教训：**部署边界必须在设计期作为输入，而不是交付前一周的适配工作**；这与 §5.7 第 5 条"先做关掉演练"是同一件事的两面——**没有降级路径的部件，在开发环境里永远看不出问题。**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条**顺序固定**的路径，与 §4.8 的 0→1→10→100 对应：

1. **先外置状态、再收口工具**（§6.4 的起点）——这两步做完，平台才具备"可恢复"与"可归因"；顺序反了的话，后面的每一次治理扩展都要在"状态会丢"的前提下做。
2. **再把定义版本化、把渠道收进定义**（§6.1）——解决"行为不可复现"与"多渠道漂移"。判据只有一条：**能否回答"这次行为变化对应哪个版本"**。
3. **再把会话与步骤做成可查询资源**（§6.2）——它同时给出成本归因与回放定位这两件事的数据基础。
4. **最后做构建面的抽象与离线交付包**（§6.3、§6.4）——前者是"让业务方自助"，后者是"让客户机房能装"。两者都必须建立在 1–3 之上：**没有版本与状态的自助化，等于让业务方加速制造不可解释的行为；没有状态与出口的离线包，等于把不完整的设计固化进交付物。**

**顺序的反面**：先做构建面（因为"看得见"）、后补状态与出口——业务方搭出来的东西越多，事后每改一次地基要动的存量就越多。**这是四个案例里唯一一个"越努力越难"的顺序。**

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 渠道各自维护一份定义 | 同一 agent 在不同入口行为不同 | 定义分叉，差异无法归因 | 渠道属定义的一个字段（§6.1） |
| 出口只做鉴权、不做配额 | 额度被打满，但事前无拦截 | 出口不构成拦截点 | 四件事一起上（§3.2.4） |
| 把"等人"实现成超时 | 批准到达时任务已失败并被重发 | 同时引入"丢批准"与"重复执行" | 人审是状态，不是异常（§6.2） |
| 发布只带提示 | 回滚后行为仍不同 | 版本四元组不完整 | 发布单元改四元组 |
| 状态覆盖式更新 | 复盘时无法回答"中途看见了什么" | 历史被销毁 | 步骤表追加写 |
| 配额事后统计 | 超发在观测之后才被发现 | 配额失去约束力 | 预扣后结算 |
| 人审无超时 | 待审请求长期挂起、占并发 | 吞吐被少数请求锁死 | 每个状态带超时，超时默认拒绝 |
| 构建块按"使用位置"划分 | 同一连接被复制进几十个工作流 | 改一处要改几十处 | 按"变化频率"划分构建块（§6.3） |
| 私有化假设公网 | 交付现场装不上 | 部署边界未在设计期输入 | 离线包 + 权重校验 + 断网演练（§6.4） |
| 整体跑通即验收信创 | 上线后结果与 x86 不一致 | 精度问题在算子级，整体跑通测不出 | 逐算子清单 + 不支持清单 |
| 挂起运行不计并发 | 并发额度被"等人"吃掉 | 闸门越宽，容量越假 | 按利特尔法则算余量（§6.2） |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——平台层的收益形态是"事故与时长"，不是"百分比"，硬凑一个百分比只会误导排序。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 事故减少 | 单位时间内"来源不明调用 / 超发 / 丢会话"的次数 | 从**每周数次**降到**每季度个位数**【经验，取决于改造前的治理缺口】 | 取改造前后各 90 天的同类事件计数 |
| 排障时间 | 从"行为异常"到"定位到版本"的时长 | 从**小时级**降到**分钟级**【经验】 | 拿最近一次行为异常复盘，记录实际耗时 |
| 变更效率 | 一次行为变更从提交到可控上线的时长 | 从**天级**降到**小时级**【经验】 | 统计最近 10 次变更的端到端时长 |
| 自助化程度 | "新增一个外部能力"的平均人日 | 复用构建块后显著下降【推算：见 §6.3 的 O(k×单次) → O(单次 + k)】 | 统计最近 10 次接入的人日与复用占比 |
| 交付可重复性 | 一次离线安装的失败点数量 | 从"每次都有新失败点"降到"零外网依赖"【经验】 | 在全新断网环境装一次并记录失败点 |
| 平台固定成本 | 执行体空转 + 状态存储 + 出口实例 | 加隔离会**上升**（独立池按租户数线性增长）【推算：见 §3.2.6 的 40 副本算例】 | 按月核算固定成本 / 模型成本之比 |

**读法**：前五项是治理与效率收益，最后一项是**成本代价**——平台的 ROI 从来不是"省了多少钱"，而是**"把不可控变成可控"值多少钱**。若你的口径里最后一项已经超过前五项，说明租户数或隔离强度超出了当前体量，应先回到共享池 + 配额（§3.2.6）。

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**状态外置与工具收口是平台的地基**，版本与渠道的一致性是承重墙，会话 / 步骤的资源化是管线，构建面抽象与离线交付是最后的外墙。四次失败教训指向同一件事：**平台出问题几乎都不是"能力不够"，而是"某个部件没有被设计成不可绕过"**——绕过的形式各不相同（绕过出口、绕过版本、绕过闸门、绕过公网假设），但代价的形状是同一个：**当你需要它的时候，它不在。**

> 💡 **思考锚点**：在 §6.1–§6.4 里挑一个与你当前处境最像的案例，只做一件最小的事——按它列出的"判据"跑一次自测（版本对账 / 出口对账 / 挂起并发测算 / 断网安装四选一）。哪一类的自测你**今天就能做**，就先做它：能立刻被验证的缺口，优先级永远高于推断出来的缺口。
