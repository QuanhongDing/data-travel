### 8.2 平台与应用的边界：什么时候必须上平台

#### §AP.1 你们团队现在有 3 个 Agent 脚本在跑，业务方还想再提 5 个需求。请说明：（1）什么信号出现时，"再加一个脚本"就不再是选项；（2）"Agent 平台"与"一堆 Agent 应用"在工程上的差别有哪些（至少四条）；（3）如果决定做平台，第一版应该包含什么、明确不包含什么？

**1. 考察点**

- 能否把"该上平台"这件事**判据化**，而不是凭"感觉规模大了"。
- 是否理解平台的差别不在"能力更强"，而在**状态、权限、成本、变更**这四件事的归属。
- 能否给出"第一版不做什么"——**边界的反面比正面更能看出经验**。

**2. 参考答案框架**

**第一层：判据化的信号（回答第 1 问）**。四个信号，出现任意两个就该做平台：① **状态丢过**——出现过"会话跑一半重启后丢失"；② **成本问不出**——无法回答"上个月谁花了多少"；③ **权限说不清**——无法回答"哪个团队能用哪个工具、写到哪"；④ **变更不可回滚**——改一次提示后，行为变了但无法回到上一个确定状态。**这四条的共同点是：它们都不是模型能力问题。**

**第二层：四条工程差别（回答第 2 问）**。① **状态**：应用把状态放进程内，平台必须外置并可恢复；② **工具**：应用里工具是代码调用，平台里工具是注册表条目 + 唯一出口（鉴权 / 校验 / 配额 / 留痕四件事）；③ **成本**：应用只有账单总额，平台必须能归因到租户 / Agent / 会话；④ **变更**：应用改代码重新部署，平台的发布单元是版本四元组 `(编排定义, 提示, 模型路由, 工具集版本)`，回滚改指针即可。

**第三层：第一版的边界（回答第 3 问）**。**做**：会话状态外置（追加式步骤表）+ 工具出口 + 模型接入层统一 + 版本四元组与发布指针——四件事都不依赖前沿判断。**明确不做**：多 Agent 仲裁（无通行做法）、平台级回放（语义未统一）、自治优化（责任无法归属）、以及"顺手把数据治理也做了"（那属于数据平台，见 [Ch11](../../11-cross-cutting/README.md)）。

**3. 常见陷阱**

- 把"上平台"讲成"换一套更强的框架"——框架解决编排，不解决治理；这是最典型的答偏。
- 只讲收益不讲代价：平台的代价是**长期人力**（按 0.5–1 人年的常备投入量级估算【经验】）与执行体空转（隔离越强越贵）。
- 第一版把所有东西都做（"既然做平台就一次做全"），结果是做了一个季度还没上线；正确做法是先做**不可绕过的落点**（状态、出口、指针）。

**4. 追问预测**

- 「如果只有两个业务方，也要做平台吗？」——用四信号判据回答：若四条都未出现，先用应用形态 + 一条**出口**过渡（最小治理），别先建控制面。
- 「平台和 API 网关的区别？」——网关管南北向流量治理，平台管**调用链内部的工具出口**，调用方是模型而不是人（见 [Ch4 §07 数据 API 网关](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway.md)）。
- 「平台会不会成为瓶颈？」——会：控制面是关键路径上的单点，所以它必须多副本 + 变更留痕；数据面才是可水平扩的部分。

**5. 参考资料**

- 平台分层（控制面 / 数据面 / 治理面）这一划分在主流平台产品文档中普遍可见——按各产品文档的「架构 / 概览」章节当前版本核验【公开：以官方文档当前版本为准】。
- 成本必须归属到 Owner 的口径见本书 [Ch11 §03 数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)。
- 本节没有给出具名公司的平台生产案例：平台层细节极少公开，凡见到"某公司平台化后成本降 X%"这类说法，先确认它的口径与基线【经验】。

### 8.3 会话状态、检查点与恢复语义

#### §AP.2 一个会话平均 8 步、每步可能调用写接口。请说明：（1）检查点应该记什么，为什么"写操作之后"的检查点特别关键；（2）恢复时如何避免重复执行已生效的写操作；（3）检查点的存储与写入量如何估算，长期保留策略是什么？

**1. 考察点**

- 是否理解**检查点的语义**（存的是"意图"还是"已生效的事实"），而不是"存了状态就行"。
- 能否用**幂等键**把"重试"从异常路径变成常规路径。
- 能否把存储量**算成一个数**，而不是"够了再加"。

**2. 参考答案框架**

**第一层：检查点记什么**。每步追加一条记录，至少含：`session_id / step_index / intent（打算做什么）/ effect（已生效的事实）/ tokens / tool_calls / 版本四元组摘要 / 时间戳`。**关键在 effect**：写操作返回之后必须**先落 effect，再进入下一步**；否则崩溃窗口内的重放会把已经发生的事再做一遍。

**第二层：恢复语义**。恢复规则三句话：① 从最后一个**完整**检查点续跑；② 若最后一步只有 intent 没有 effect，**重放该步**（此时靠幂等键去重）；③ 若已有 effect，**跳过该步**。幂等键取 `hash(tenant, session_id, step_index, tool_name, normalized_args)`——归一化必须处理"列表顺序"与"无关字段（时间戳、trace id）"，否则同一次调用会生成不同的键。

**第三层：存储与保留**。写入量 = `会话数 × 平均步数 × 单步状态字节数`。以日活 `2,000` 会话、每会话 `8` 步、单步 `2–10 KB`【经验】估算：**日增 32–160 MB，年增 12–58 GB**（`2,000 × 8 × 6 KB × 365 ≈ 35 GB`，取中值量级）【推算：口径为上述三项相乘，字节区间取本主题通用量级】。保留策略**分层**：热 30 天（可即时恢复与回放）、温 1 年（只保留摘要与 effect）、冷归档按合规要求（例如审计留存 180 天到数年，取决于行业）。

**3. 常见陷阱**

- 把检查点做成**覆盖式更新**——事故复盘时无法回答"它中途看见了什么"。
- 只考虑"失败要重试"，没考虑"重试会重复"——写操作重试无幂等是最常见的事故成因。
- 用"步骤号"做幂等键却允许步骤号在重试时变化（例如用自增 ID）——键不稳定，幂等失效。

**4. 追问预测**

- 「写操作在外部系统生效了，但 effect 还没落盘，怎么办？」——这是不可消除的窗口；正确做法是**把外部系统的可查证结果作为 effect 的来源**（用业务单号回查），而不是假设落盘与生效原子。
- 「恢复后用户看到的会话是同一个吗？」——取决于是否钉住版本四元组：钉住则行为可复现，不钉则同一会话可能前后用不同版本，复盘无法解释。
- 「重放会不会导致成本翻倍？」——会：重放步数 × 单价；所以恢复粒度越细，重放成本越低——这也是"步骤级恢复"的价值所在。

**5. 参考资料**

- 持久化执行 / 可恢复步骤的机制与编程模型见主流持久化工作流引擎的官方文档（按当前版本核验）【公开：以官方文档当前版本为准】。
- 幂等键与不可逆动作的前置条件见本书 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)。
- 状态存储量级算例的口径与档位说明见本主题 [§4.6](02-agent-platform-architecture-section-4-sec4.md)【推算】。

### 8.4 多租户隔离与配额（共享池 / 独立池 / Cell）

#### §AP.3 平台要为 20 个业务部门（其中 3 个有合规隔离要求）提供服务。请说明：（1）隔离强度如何分档、各档的代价是什么；（2）配额应该在链路的哪一刻扣减，为什么事后统计不行；（3）如何证明"没有旁路调用"？

**1. 考察点**

- 能否把"隔离"从形容词变成**可算的成本**（副本数、空转资源）。
- 是否理解配额的**时点**决定了它是约束还是报表。
- 能否给出**可执行的旁路核查动作**，而不是"我们会规范"。

**2. 参考答案框架**

**第一层：隔离分档与代价**。三档：**共享池**（同一批执行体 + 逻辑隔离 + 配额隔离）→ 固定成本最省，但一个租户的工具调用风暴会影响同池其他租户的 P99；**独立池**（每租户一组执行体与命名空间）→ 故障与容量不串，代价是常备副本；**独立 Cell**（存储 + 计算 + 出口独立）→ 隔离最强，代价是运维面随租户数线性增长。**算例**：每租户常备 2 副本、单副本 `1 vCPU + 2 GB`，20 个租户 = `40 vCPU / 80 GB` 空转【推算：2 × 20 = 40 副本】。**判据**：租户之间是否存在"业务上不可共用"的合规要求——有则必须独立，没有则共享 + 配额。

**第二层：配额时点**。必须是**预扣后结算**（三段式：预估扣减 → 执行 → 实际结算并退差额），且扣减点在**工具出口**与模型接入层（模型侧按 token 预扣）。**事后统计不行**，因为观测点晚于超发点：等你从报表里看到超发，钱已经花了；配额的全部价值就在"调用发生前"这一个时刻。

**第三层：旁路核查**。可执行动作两条：① **对账**——拿"出口的工具调用统计"与"被调用系统自己的访问日志"按天对账，差异即旁路流量，成本约半天/次；② **凭证收口**——目标系统的调用凭证由平台统一托管与轮换，业务代码里不持有长期凭证（这一条能让旁路从"违反规范"变成"技术上做不到"）。

**3. 常见陷阱**

- 把多租户做成"多一个 tenant_id 字段"——没有出口与配额，逻辑隔离等于没有隔离。
- 配额按"总额"给而不按"窗口"给——月底超发的概率与窗口长度成反比，长窗口更容易被一次性打满。
- 对账只做一次就认为"没有旁路"——人员与代码都在变，对账要定期做（建议每月一次）。

**4. 追问预测**

- 「Cell 化的代价什么时候值得？」——当合规要求"不可共用"或单租户峰值足以影响整池时；否则先用共享池 + 每租户配额。
- 「配额超发最后一刻的拦截点在哪？」——在出口与模型接入层；若你的链路上还有别的出口（例如某个团队直连的向量库），它也要纳入同一个配额体系。
- 「人审闸门会不会成为瓶颈？」——会：所需人力 `n > λ / μ`（到达率 / 人均处理率）；适用面收窄到"写操作与不可逆动作"是唯一可扩展的做法。

**5. 参考资料**

- 单元化 / Cell 的隔离原理与故障半径计算见本书 [Ch12 §01 单元化架构](../../12-architecture/01-cell-based-architecture/01-cell-based-architecture.md)。
- 配额与限流的实现形态（令牌桶 / 并发信号量 / 队列）见 [Ch4 §07 数据 API 网关](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway.md) 的机制章节。
- 成本归属与分摊口径见 [Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)【公开：书内可核验】。

### 8.5 工具出口治理（注册表 / 四件事 / 旁路对账）

#### §AP.4 平台要接入 30 个工具，其中 6 个可写。请说明：（1）工具注册条目应该包含哪些字段，哪几个字段是"缺了就不能注册"的硬项；（2）出口的四件事的**判定顺序**为什么重要，举一个顺序错误导致的安全边界；（3）工具接入协议（MCP 一类）能替代出口治理吗？

**1. 考察点**

- 能否把工具治理**落到字段级**（可说、可审、可自动校验）。
- 是否理解判定顺序本身是安全设计的一部分。
- 能否分清"协议解决什么"与"治理必须自己解决什么"。

**2. 参考答案框架**

**第一层：注册条目的硬项**。字段：`tool 名 / Owner / writable / input_schema / egress（出口标识）/ limits（行数、超时、扫描量）/ scope（租户、表白名单、拒绝项）/ audit（是否记参数、保留期）/ gate_ttl（可写工具必填）`。**硬项四条**：① `egress`——没有出口标识的工具不允许注册（这是"收口"的制度化）；② `writable`——决定是否需要人审闸门；③ `scope`——白名单必须由**平台强制**，不能依赖工具自我检查；④ `gate_ttl`——可写工具必须声明闸门超时（否则请求会永久挂起）。

**第二层：四件事的顺序**。正确顺序：`在册 → 有权 → 参数合法 → 未重复（幂等）→ 已批准 → 有额度`。**反例**：若把"配额扣减"放在"鉴权"之前，一个越权请求也能消耗掉租户额度——攻击者可以用越权请求把别人的额度打满，形成**资源型拒绝服务**；若把"幂等"放在"鉴权"之前，未授权方可以通过构造重复请求探测幂等表的存在与内容。

**第三层：协议与治理的关系**。工具 / 资源 / 提示的标准化协议解决的是**"怎么调"**（发现、描述、调用），不解决**"谁能调、调了记什么、超了怎么办"**。因此协议接入必须叠加：资源按租户做**可见性裁剪**、提示只允许引用已发布版本、工具调用一律走出口。**只做协议接入不做治理，会得到一个"什么都能调、什么都不知道"的平台。**

**3. 常见陷阱**

- 让工具"自己检查权限"——工具的自我约束不能算控制项（[Ch11 §02 数据安全](../../11-cross-cutting/02-data-security/02-data-security.md) 的"策略未生效的执行点"）。
- 幂等键用参数原文——归一化缺失会让"同一次调用"产生不同键。
- 把工具超时设得比出口超时还长——出口先超时，工具仍在跑，产生**孤儿写操作**。

**4. 追问预测**

- 「只读工具也要走出口吗？」——要：出口不只做权限，还做留痕与配额；只读工具不写数据，但仍消耗资源与查询预算。
- 「怎么发现团队绕过出口？」——出口统计与目标系统访问日志对账；更彻底的是把凭证收归平台托管。
- 「新增工具的平均接入成本是多少？」——一个登记条目 + 一次对账验证，量级是**半天到一天**【经验，随 Schema 复杂度与是否需要人审变更】。

**5. 参考资料**

- 工具 / 资源 / 提示的协议化接入（MCP 一类）由 Anthropic 于 2024 年公开，规范与实现可按规范当前版本核验【公开】；本书 [Ch6 §03 模型网关](../../06-multi-model/03-model-gateway/03-model-gateway.md) 讨论协议与治理的分工。
- 出口的鉴权 / 校验 / 配额 / 留痕四件事的实现骨架见本主题 [§4.2（2）](02-agent-platform-architecture-section-4-sec4.md)。
- 表级 / 文档级 scope 的裁剪口径见 [Ch8 治理](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md)。

### 8.6 发布、灰度与回滚：版本四元组与 guardrail

#### §AP.5 Agent 的"版本"由哪些东西组成？请说明：（1）为什么只回滚提示不足以解释行为变化；（2）灰度在 Agent 场景下如何定义"失败"；（3）一次可复现的回滚演练需要哪些前置条件？

**1. 考察点**

- 能否指出 Agent 的版本对象是**复合**的（少了任何一项，回滚都不可复现）。
- 是否理解"失败"在 Agent 里必须由**行为指标**定义，而不是 HTTP 错误率。
- 能否把"演练"落到可执行的清单。

**2. 参考答案框架**

**第一层：版本四元组**。`(编排定义, 提示, 模型路由, 工具集版本)`。只回滚提示的后果：行为仍可能不同（模型档位变了、工具的实现或 Schema 变了），团队于是误判"模型不稳定"——**这不是回滚失败，而是版本定义不完整**。做法：会话发起时记录版本摘要（钉版本），整段会话不变；发布与回滚只改控制面的指针。

**第二层：灰度的"失败"定义**。Agent 的失败不像 5xx 那样直观，必须由**你可定义的行为指标**来判定，至少三条：**会话失败率**（含工具错误、超时、配额耗尽、人工拒绝的比例）、**单会话成本 P95**、**工具错误率**。guardrail 用这三条做自动回滚触发（例如"失败率窗口内上升超过 2 个百分点"或"成本 P95 上升超过 20%"即暂停并回滚）——**阈值要与你的基线一起标定，本节不给通用值**【经验：阈值随任务分布与模型档位浮动】。

**第三层：可复现回滚的前置条件**。四条：① 四元组完整且被会话钉住；② 定义（提示 / 编排）有版本化存储，历史版本可取回；③ 灰度分流规则支持"会话级"（同一会话始终同一版本，否则无法归因）；④ 有一次真实演练记录，含演练前后的两组数字。

**3. 常见陷阱**

- 灰度按**请求级**分流而不是会话级——同一会话前后用不同版本，行为不可解释。
- guardrail 只看错误率——Agent 的失败常常表现为"成功返回但结论错"，错误率看不出来。
- 把"我们有回滚脚本"当成"回滚可用"——没演练过的回滚，第一次执行通常在事故中。

**4. 追问预测**

- 「模型侧提示缓存失效会不会影响行为？」——会，且它常被忽略；所以"模型档位 + 缓存策略"要一起进版本对象（至少记录在案）。
- 「灰度期发现成本上升，先回滚还是先查？」——先回滚（成本是可累积的），根因在回滚后从留痕里查；这是"止损优先于归因"的通用原则。
- 「多租户下怎么灰度？」——按租户白名单 + 会话级哈希分流；对合规租户默认不参与灰度（要可复现）。

**5. 参考资料**

- 灰度的止损机制与不可逆动作的前置条件见 [Ch12 §09 灰度与回滚](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md) 与 [Ch12 §07 容灾](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)。
- 版本与回滚在 Agent 场景的机制讨论见本主题 [§5.3.1](02-agent-platform-architecture-section-5-ai.md)【经验：本节不给第三方案例】。

### 8.7 私有化交付与平台级成本归因

#### §AP.6 客户要求"权重、数据、日志都不出机房，且交付时不能联网"。请说明：（1）交付前必须完成的工程项清单；（2）交付现场最容易在哪些环节失败；（3）平台上线后，如何用三个 SLO 证明它"能用"，并且把成本说清楚？

**1. 考察点**

- 能否把"私有化"从一句要求拆成**可验收的条目**。
- 是否知道现场失败的分布（多在镜像、权重、依赖解析、架构差异，而不在"模型跑不起来"）。
- 能否给出平台级的三条 SLO 与成本归因口径。

**2. 参考答案框架**

**第一层：交付前工程项六条**。① **离线部署包**（镜像、Chart、初始化数据、权重校验清单打成一个目录，安装零公网依赖）；② **权重分发与哈希校验**（权重入内网存储，安装时校验，不匹配即失败）；③ **断网运维路径**（日志与指标本地留存与导出、升级包的内网传递与审批）；④ **信创适配**（列关键算子清单，在目标 CPU 架构上逐个跑通并记录精度差异；差异不可解释的写进"不支持清单"）；⑤ **账号与审计对接**（与客户身份源对接，审计日志可客户自行导出）；⑥ **交付验收单**（把前五条写成可勾选项）。

**第二层：现场易失败点**。按发生概率排序：**镜像拉取需要公网**（最常见）→ **权重需在线下载** → **依赖内部解析域名** → **CPU 架构导致的算子不可用** → **身份源协议细节不匹配**。**共同点是它们都在"平台之外的周边"**，所以交付前的验证必须是"在断网 + 目标架构的等价环境里装一遍"。

**第三层：三条 SLO 与成本归因**。SLO：**交互式首步延迟**（人机第一步要快，与长任务分开度量）、**长任务完成率与时长分布**（含队列等待）、**单会话成本 P50 / P95**（按租户）。成本归因口径：`单会话成本 = Σ 步 (in/out tokens × 单价 + 工具自身成本)`，平台固定成本另计；**关键指标是"模型成本 ÷ 平台固定成本"**——比值长期小于 1 说明平台自身开销成了主项，应先收敛执行体数量与状态保留期，而不是继续加租户。

**3. 常见陷阱**

- 把私有化当"部署工作"而不是"架构约束"——等到交付前一周才发现某部件假设了公网存在。
- 只给客户"能跑起来"的证据，不给"可自行运维"的证据（断网下如何排障、如何升级）。
- 成本只给一个总额，不按租户 / 会话拆——到了扩容谈判时无法回答"钱花在哪"。

**4. 追问预测**

- 「客户机房资源有限，怎么定最小规格？」——按"每租户最小副本数 × 单副本规格"倒推，并明确"最小规格下的并发上限"（这个数要写进交付文档，否则客户会按理论峰值压）。
- 「国产化适配要重做多少？」——取决于关键算子清单的长度与目标架构差异；**先跑清单再谈工作量**，不要凭经验给数【经验】。
- 「怎么向客户证明数据不出域？」——用**可核验的动作**：断网安装、权重哈希校验、出网白名单审计、审计日志导出；这四个动作合起来比任何承诺都强。

**5. 参考资料**

- 私有化与国产化适配的定位见本书画像章节 [Ch8 治理](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md) 与 [Ch11 §07 审计与合规](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance.md)（其中"等保 2.0/3.0 无正式标准号与实施日期"这一点本书亦已指出）。
- 平台级三条 SLO 与成本归因口径见本主题 [§4.2（6）](02-agent-platform-architecture-section-4-sec4.md) 与 [§4.6](02-agent-platform-architecture-section-4-sec4.md)。
- 容灾与演练的口径见 [Ch12 §07](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)【公开：书内可核验】。

### 8.8 本章小结

本节收录 6 道题，覆盖**企业级智能体平台架构**的六个核心考点：**边界 → 状态 → 隔离与配额 → 工具治理 → 发布回滚 → 交付与成本**。六道题构成一条完整的建设链路：

- **§AP.1 边界**：先用四条信号判断"该不该做平台"，再定义第一版"做什么、不做什么"。
- **§AP.2 状态**：检查点记 intent 与 effect，恢复靠幂等键去重（平台的地基）。
- **§AP.3 隔离与配额**：隔离强度与代价成正比；配额只在"调用前"有意义。
- **§AP.4 工具治理**：注册表的硬项 + 出口四件事的**顺序** + 旁路对账。
- **§AP.5 发布回滚**：版本四元组 + 行为指标 guardrail + 演练过的回滚。
- **§AP.6 交付与成本**：私有化六件事 + 三条 SLO + 成本归因到会话。

**答题心法**：先说清约束（部署边界、副作用、租户数），再说清选项（六条路的三族），最后说清取舍与代价。平台主题下，面试官真正想听的是 **"你为什么这么选、代价落在哪、什么条件下它会失效"**——把答案落到"某个判据 + 可自测的动作"上，远比背架构分层更有说服力。
