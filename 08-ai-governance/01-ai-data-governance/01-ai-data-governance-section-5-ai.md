## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是**把不同控制点位置的东西并列**。同一张清单里，「在发布流程上登记一份卡片」与「在调用通路上拦截一次请求」，被写成同一层的两种「方向」。这两者的可规划性差一个量级：登记只能约束你**已经枚举出来的**对象，拦截能拦住**流经它的一切**。本章 [§7 与其他方法对比](01-ai-data-governance-section-7-sec7.md) 把控制点分成事后审计 / 事前登记 / 事中门禁 / 授权制四类，并给出一条因果——**一个控制点只能阻断流经它的东西**。本节按这条线分族，而不是按「传统 → AI」的时间线分族。

第二个问题是**治理对象本身在换形态**。主文件 §2.1 把 AI 资产定义为五元组 `A = ⟨T, C, I, R, X⟩`（类型 / 机密性 / 完整性 / 风险 / 可解释性）。这个定义隐含一个前提：**资产是可枚举的实体**。当对象是模型权重、数据集版本、Prompt 模板时，围着这个五元组建台账在结构上成立；当对象变成「一次调用」「一次工具动作」时，五元组里缺的那一维是**这次行为是谁被授权做的**（本章 §7.3.1 与 §7.3.3）。缺的那一维不是事后补个注释就能了的字段——它决定了台账要另起一张行数按事件增长的表。所以本节评估的四个方向里，前三个是「把既有机制扩到新对象」，第四个是「为一种新对象重建机制」，两者的成熟度不在一条线上。

第三个问题是没有反方观点。清单里不会出现「这一条今天不值得投」，于是「AI 资产入表」「Agent Card 成为标准」这类还需要先解决方法论问题的条目，会和「把 AI 调用收口到网关」这类早就有成熟工程做法的条目排在同一个列表里。治理的过度投入与投入不足一样会输：**流程重于对象数量时，治理会先被业务绕过，然后连原本有效的部分一起失效**。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note（本节对「release note」的取材口径见下方的判据修正声明）；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期（对象字段与判定语义不随版本翻烧饼）。
- **L2 可试点**：①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、草案、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

**本主题对本书的 L1 判据做了如下修正**：判据 ① 中的「正式 release note」，在本主题按「**正式 release note、版本化文档或规范与标准文本**」取——三者都要求可核验的版本号或发布 / 生效日期；含产品的 release note / what's new 页与版本化产品文档，也含版本化发布的规范与标准文本（卡片字段规范、风险分级定义、已生效的法规与标准文本）。理由是本节评估的四个族里，有相当一部分对象不由某个产品定义：卡片字段来自卡片规范，风险分级来自法规文本，知识侧的索引与元数据能力主要写在向量库 / 图库的产品文档里而不是某个版本的 release note 里。若只认「某个产品版本号的 release note」，这些已经有公开文本、可被读者逐条核验的机制会被一律记成 ① 不满足，评级反而失真。修正只作用于 ① 的取材口径，不改它的强度——②③ 一字未动（第三方非厂商生产案例 / 接口稳定），下表四行都按修正后的 ① 逐行判。本节没有任何一行达 L1 与这条修正无关——修正 ① 只是让判据文本与取材现实对得上，② 的门槛一字未动。

**判据 ② 在本主题尤其难过**，原因值得先说清：AI 治理的公开材料分两类，一类是**法规与标准文本**（它证明义务存在，不证明有人在执行），一类是**建设方与厂商自述**（平台文档由厂商写，落地案例由建设方发布）。「第三方（非厂商）公开生产案例」要求的是一个既不卖这套东西、也不靠它立论的团队，公开写出自己的控制点放在哪、拦住了什么、误拦了多少。本节的口径是：**② 只有「满足」与「降为 L2」两种命运**——不改成「有公开生产记录」，不靠「本节只评估登记类」缩小适用范围来绕过，也不存在「准 L1」「L1 的边界案例」这类说法。**法规文本尤其不能充当 ②**：它证明的是义务，不是执行。

另有一条评级规则，全节通用：**按机制分族，一族一行；族的级别取族内最弱子项**。这不是放宽判据，而是读者做规划时的实际含义——族里只要有一个子项不能依赖，这一族的架构就不能整体依赖。族内每个子方向的名字都列在「演进方向」列里，5.2 逐族拆解，两处级别与判据必须一致。

| 演进方向（族内子方向） | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |

**本节没有一行达到 L1。** 三行 L2 卡在同一条上：拿不出第三方（非厂商）的生产案例。三者的差别在 ③——**事前登记**的 ③ 最干净（字段集与风险分级都有可引用文本），缺口在「卡片由人填，所以必然滞后于产物」；**运行时拦截**的 ③ 最弱，拦截点与放行语义各家不同，策略不可移植；**知识侧治理**的 ③ 居中，容器能力（版本、元数据、审计）可核验，规则（什么算引用正确）不可核验。第四行连 ① 都不满足，因为它评估的对象在多数团队里还没有可采购的形态——**Agent Card 与「可问责的决策链」今天更像是一份提案加一个演示，而不是一个能落进发布流程的能力**。真正的缺料是「控制点放在哪、拦住了什么、误拦了多少、谁签字放行」这类材料；它比一般主题更难拿到，因为治理的失败通常是**过拦**（业务绕过流程），而过拦不会被写成事故报告。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的 ① 材料——正式 release note、版本化文档或规范与标准文本——能不能找到？找不到 → L3。
2. 建设方之外的证据能不能找到？找不到 → L2。**只有法规文本没有执行材料，同样算找不到**。
3. 它管的对象的字段与判定语义明年会不会变？会变 → 至多 L2。

第 2 句在本主题特别容易失手，因为**「有法规」看起来像证据**。区别在于：法规文本回答「义务是什么」，而判据 ② 问的是「有没有人真的在做、做对到什么程度」。判定方法很具体——把这条方向对应的义务抄成一条 checklist，然后问「上次审计时，这条是谁签的字、记录在哪」。答不上来的，说明你手上只有义务，没有执行。

三个常见误判，排路线图时最容易踩：

- **把「买了网关」误当成「有了实时合规」**：网关提供的是**执行点**，不是**策略**。策略由谁写、误拦了谁批、放行记录留多久，这三件事不在产品里。
- **把「卡片填了」误当成「资产被治理了」**：卡片是人工填的，所以它必然滞后于产物。判定方法是抽三张卡片【经验：随资产重要度与迭代速度变，迭代越快越该多抽】，去比对模型或数据集的当前版本与卡片上写的是否还一致。
- **把「解释得清楚」误当成「能被追责」**：可解释回答「模型为什么这么判」，可问责回答「这次动作是谁批的、依据哪一版策略」。前者是模型属性，后者是流程属性。

### 5.2 演进方向逐条拆解（核心节）

四族按**控制点位置**排序：先看登记（放在发布流程上）、再看拦截（放在调用通路上）、再看知识侧（放在数据结构上），最后看举证（放在事后的证据层）。四族的失败模式是同一个：**控制点与它要约束的对象错位**——用登记去管运行时才产生的动作，用拦截去管已经发布的产物。

#### 5.2.1 事前登记：Prompt 治理、Model Card 与资产台账

- **旧做法与它的卡点**：登记类治理本来管的是表、字段、指标这类可枚举对象，做法是「强制登记 + 血缘」。搬到 AI 资产上立刻卡住：模型权重是二进制、不可读；Prompt 是文本、容易被复制出仓；训练数据集来源杂、版本多。更根本的一条卡点是**登记的内容由人填，所以它必然滞后于产物**——数据集与模型在迭代，卡片不会跟着动。
- **AI 改变了什么机制**：把卡片的**可读属性**从「人写描述」往「产物自己带」的方向挪了一部分——用途、评估指标、分群表现、局限可以随训练流水线自动产出，人工只补「用途与边界」这类判断性字段。变化的是**谁填表**，不是**表管什么**。
- **由此得到的**：因为一部分字段可以由流水线产出，**所以**「卡片会不会过期」这个问题从「全靠人」变成「形成双速：自动字段随产物走，判断字段随评审走」；因为卡片字段是固定的最小集，**所以**「这个模型能不能用在我的场景」这个问题第一次有了统一答案的位置——**这是本节唯一一条能靠工程手段（而不是靠人更努力）改善的方向**。
- **由此付出的**：① 卡片给出的是**声明**，不是**证据**——它写着分群指标，不等于指标复核过；把卡片当准入依据，等于把「自述」当「举证」，出事时它反而会成为「我们以为已经审过了」的理由。② 字段越多，越没人填；字段越少，越滤不掉不该上线的用法，**这条取舍没有技术解，只能由风险等级来定**（高风险场景强制全填，低风险场景只留 Owner 与边界）。③ 跨生态字段不一致，等于卡片无法被外部系统消费，只能当文档看——这也让它无法进入自动化流程。
- **证据与来源**：【公开】模型卡片这一形式的公开出处是 2019 年的论文（Mitchell 等「Model Cards for Model Reporting」，可按题名检索核验，2019）；【公开】风险分级有法规文本的分级定义（EU AI Act 的四级风险，2024-08 生效，主文件 §2.3）；【公开】主流卡片规范有版本化文档（Hugging Face 的 Model Card 文档，以官方文档当前版本为准）；第三方（非厂商）生产案例：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「事前登记」行一致：① 满足、② 不满足、③ 大体满足）。本条覆盖：Prompt 治理（Prompt 库、审查、版本）、Model Card、资产台账、风险分级、评审签字。

卡片的事情只有两个待定项，而它们决定这条方向是「治理」还是「文档」：

```text
卡片的最小字段集（字段越多越没人填，按风险等级增减）
   asset_id        与资产台账同键——键对不上，卡片就挂不到流程上
   intended_use    用途，而非能力：风险等级由用途推导，不由参数规模推导
   out_of_scope    「不能用在哪些场景」比「能做什么」更重要
   data_ref        数据集标识 + 哈希（可寻址，不是一段描述）
   metrics         总量指标 + 分群指标（缺分群等于没测偏差）
   limitations     已知失效
   owner           具体到人——写团队的卡片等于没有 Owner
   review          评审记录号 + 签字人

   两个待定项：
     ① 挂在哪   接进发布流程 ⇒ 缺项不能发布；写在文档里 ⇒ 三个月后与产物不一致
     ② 谁填     判断性字段（用途 / 边界）由人填；可核验字段（版本 / 哈希 / 指标）
                由流水线填——把可核验字段交给人填，是卡片过期的直接原因
```

- **失效条件**：当发布流程本身没有门禁（谁都能上线）时，登记退化成一份没人看的文档——此时该做的是把卡片挂到发布流程上，而不是继续往卡片里加字段。
- **自验方法**：抽三张最有价值的资产卡片【经验：随资产重要度与迭代速度变，迭代越快越该多抽】，逐项比对卡片内容与产物的当前版本。对不上的比例，就是你这套登记已经失效的比例。

#### 5.2.2 运行时拦截：实时合规与 Agent 治理

- **旧做法与它的卡点**：合规靠季度审计与事后抽查。它有两个结构性缺口：一是**只能追责不能止损**——审计发现问题时，违规的调用已经发生；二是**抽查对长尾无效**——一次调用是运行时才产生的对象，事前无法枚举，抽样比例再高也覆盖不到那条最危险的调用。
- **AI 改变了什么机制**：把控制点从「事后审计」挪进「调用通路」——AI 网关在请求与响应路径上做策略判定（Prompt 注入防御、敏感信息检查、输出过滤、模型与工具的准入），拦截从「抽样检查」变成「逐次判定」。**变化的是控制点位置，不是审查清单的内容。**
- **由此得到的**：因为拦截发生在通路上，**所以**它拦得住那些事前无法枚举的调用——这正是 Agent 场景成立的前提（工具调用一次才产生一次，动作有副作用且不可逆）；**又因为**每一次调用都过一次判定，**所以**「这次调用是谁发起的、用了哪个模型与 Prompt 版本、命中了哪条策略」这些字段第一次可以自动落下，审计从「人工翻日志」变成「按字段查」。
- **由此付出的**：① **网关提供执行点，不提供策略**——策略由谁写、误拦了谁批、放行记录留多久，全在组织侧，产品里没有这三件；② **误拦与漏拦是一对反方向的代价**：拦得松则形同没有，拦得紧则业务绕过网关（绕过一次，这一层的全部证据同时失效）；③ **同一个策略不跨产品移植**——换一个网关，拦截点与放行语义都要重写，这是本节最重的一笔锁定；④ **它只覆盖流经它的调用**：业务为了调模型把数据导出到外部服务的路径，网关看不见，而「AI 调用出仓」恰恰是治理最想拦住的形态。

```text
控制点位置决定它能拦住什么（错位是最常见的失败）
   事前登记   只能约束「已经枚举出来的对象」→ 表、字段、模型、Prompt
   事中门禁   能拦住「流经它的任何对象」    → 一次调用、一次工具动作
   事后审计   能追责、不能止损            → 已经发生的事
   ────────────────────────────────────────────
   Agent 的动作是运行时才产生的 ⇒ 登记制在结构上不适用，只能靠拦截 + 授权
   反过来说：想让登记管住 Agent 动作，等于要求它先知道 Agent 下一步要干什么
   判据：你的策略里有多少条是「按调用内容判定」，而不是「按资产是否登记」
```

同一层还有两个对象，落点不在请求与响应上：**内存隔离**回答「一个会话的上下文存在哪、谁能读」，**跨会话审计**回答「同一个人在多个会话里做过什么」。它们是**会话边界**上的控制，而不是策略判定上的控制——策略判定可以只过网关，隔离与会话审计必须落在真正持有上下文的那个运行时里。判定方法是问三句：会话上下文存在哪、会话结束时由谁清理、谁有权跨会话检索。

- **证据与来源**：【公开】网关类产品有版本化发布说明与公开文档（Cloudflare AI Gateway / Portkey / Lakera 等，见 5.4 的实践与工具条目，以各自官方文档当前版本为准）；【公开】提示注入与 LLM 应用安全风险有公开清单（OWASP Top 10 for LLM Applications，2023 首次发布，其后有新版，版本号以项目官方页面为准）；第三方（非厂商）生产案例：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「运行时拦截」行一致：① 满足、② 不满足、③ 不满足）。

- **失效条件**：当组织的调用量小到「每条都能人工看」时，网关的边际收益低于它带来的改造与锁定成本——判据是**未过网关的调用占比**，而不是总调用量；只要有一类调用绕开了网关，这一层的证据就有缺口，此时该先收口，再谈策略。
- **自验方法**：统计一周内「被拦下的调用」与「被放行后又被用户投诉的调用」两个数【经验：随调用量与策略条数变】。只盯前者会越拦越紧，只盯后者会越放越松；两个一起看才知道策略的灵敏度是否合理。

#### 5.2.3 知识侧治理：RAG、向量库与 GraphRAG 治理

- **旧做法与它的卡点**：训练数据治理靠「数据集版本 + 来源 + PII 标签」。搬到检索增强上立刻错位：模型只训练一次，而检索源每天都在变；回答的依据不是一份数据集，而是**某几个片段的某一版本文本**。于是三件事同时失去抓手——引用正确性（这句话到底出自哪份文档的哪一版）、召回可追溯（当时检索到了什么）、索引一致性（Embedding 模型换了之后，旧向量还算不算数）。
- **AI 改变了什么机制**：把治理对象从「不可变的数据集版本」换成**可变的、被反复切分与重新嵌入的文本集合**，因此治理动作从「发布前审一次」变成「每次检索都带着版本身份」。向量库与图库能提供的是容器（集合、元数据、版本化写入、审计接口），**它们不提供「什么算引用正确」这条规则**。
- **由此得到的**：因为每个片段可以带来源、版本与 Owner 元数据，**所以**「这条回答出自哪份文档的哪一版」第一次可以是一条查询而不是一次考古；因为索引与 Embedding 模型的版本可以被记录，**所以**「换了模型之后召回变了」这类问题可以被归因到一次具体变更；**这是本节里唯一一个「不做也能上线、做错了才会发现」的方向——它是事故复盘的必要条件**。
- **由此付出的**：① **引用正确性与召回可追溯没有公共判定口径**：引用对不对、召回全不全，各家自定判据，无法横向比较；② 元数据要靠采集与人工补，而文档在业务侧的归属比表更模糊（一份产品文档的 Owner 是谁？），补不全的元数据等于没有；③ 本体（Ontology）一旦进入治理范围，就要求**专家签字**这类非工程流程，而它的改动是不可逆的语义变更——回滚一版本体比回滚一版代码贵得多；④ 索引是派生副本，**跟不上就会出现「看起来合理但已经过期」的答案**，这是 AI 层最隐蔽的失效形态，因为它不报错。
- **证据与来源**：【公开】版本控制与向量 / 图库的元数据能力有公开文档（LakeFS、Milvus 一类组件，以各自官方文档当前版本为准）；【公开】检索增强的机制出处是 2020 年的公开论文（Lewis 等「Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks」，NeurIPS 2020）；【公开】图结构与向量结合的方法有 2024 年的公开论文与开源实现（Edge 等「From Local to Global: A Graph RAG Approach to Query-Focused Summarization」，2024，可按题名检索核验；实现以官方仓库当前版本为准）；第三方（非厂商）生产案例：无公开可核验来源。
- **成熟度**：**L2**（与 5.1 表「知识侧治理」行一致：① 满足、② 不满足、③ 不满足）。

| 治理对象 | 可核验的现有件 | 必须自建的部分 |
| --- | --- | --- |
| 文档与片段版本 | 版本控制系统（如 LakeFS 一类，按各自官方文档核验） | 「哪个版本是当前生效版」的判定规则与下线流程 |
| 向量索引与 Embedding 版本 | 向量库的集合与元数据能力 | 换 Embedding 模型时的重建策略与新旧并存窗口 |
| 引用正确性 | 无标准件 | 判定口径（引用要能指回片段，且片段未被改动） |
| 召回可追溯 | LLM 观测工具的 trace 结构（Langfuse 一类） | 「召回集要不要留、留多久」的保留策略 |
| 本体与实体 / 关系置信度 | 图库的版本化写入 | 本体变更的专家签字与回滚流程 |

图这一侧还多一个别处没有的对象：**子图检索审计**——一次问答用了哪一版子图、命中了哪些实体与关系，要能事后还原。子图是从本体与数据派生出来的，所以它的版本必须跟着本体版本走；否则回滚了本体，还会留下一批按旧语义切出来的子图。判定方法是问：这次检索用的子图是哪一版本体生成的、生成它那次任务的记录在哪。

- **失效条件**：当检索源本身是不可变的历史归档（几年不改一次）时，版本治理的收益低于它的维护成本——此时该做的是把 Owner 与 PII 标签补全，而不是引入一套版本化查询。判据是：你的文档变更频率是否高到「同一份文档这个月和上个月的答案不一样」。
- **自验方法**：任取一条历史回答，回答三件事——它引用的片段当时属于哪份文档的哪一版、那一版的 Owner 是谁、这份片段今天还在不在索引里。三件都答得出，知识侧治理才算建起来了。

#### 5.2.4 可问责与举证：Agent Card、决策链与 AI 资产入表

- **旧做法与它的卡点**：可解释性工具（SHAP / LIME 一类）解释的是「模型为什么这么判」，它产出的是**特征归因**。搬到 Agent 场景立刻不够用：真正需要回答的问题是「这次退款是谁授权的、依据哪一条策略、中间调用了哪些工具、失败了怎么退」。前者是模型属性，后者是**流程属性**，而流程属性不在模型里，也不在任何一张卡片里。
- **AI 改变了什么机制**：把责任切分的最小单位从「一次预测」换成「**一次有副作用的动作**」。这要求每一段动作都有授权记录与可回放轨迹（谁发起、用哪个版本、命中哪条策略、结果是什么），而这些记录必须由运行时产生——**它们是拦截层的副产品，不是可以事后补写的文档**。
- **由此得到的**：因为授权与轨迹由运行时落下，**所以**「这条回答／这个动作能不能归因到一次具体授权」第一次可以是被查询的事实，而不是复盘时的推断；**又因为**Agent 的能力清单（可调用的工具、边界、回滚方式）可以被声明，**所以**「它能做什么、不能做什么」从一句描述变成了可核对的表。
- **由此付出的**：① **Agent Card 与「可问责的决策链」今天停在提案与预览阶段**：格式没有共识，落地案例是演示而非生产，把它排进路线图等于把假设当结论；② **可问责要求先有权责划分**：谁批的策略、谁签字放行、误拦谁负责——这三件事在组织里往往没有明确归属，技术上做得出来，流程上落不了地；③ **AI 资产入表**不但没有成熟方法学，还会产生反向激励——为了报表数字好看的估值假设，会污染治理本身的判断（「AI 资产价值评估难」说的就是这件事）；④ **留痕的成本随时间线性增长**：动作级轨迹是行数按调用量增长的表，保留期一变，成本曲线跟着变。把留痕做成「全都留」会在半年后遇到与数据湖同样的问题。
- **证据与来源**：【公开】模型可解释方法的公开论文（Lundberg 与 Lee「A Unified Approach to Interpreting Model Predictions」，NeurIPS 2017；Ribeiro 等「Why Should I Trust You? Explaining the Predictions of Any Classifier」，KDD 2016）——两篇解释的都是「模型为什么这么判」，说明可解释与可问责是两件事；【公开】责任相关的立法材料目前是**草案**（欧盟 AI Liability Directive 草案，按欧盟官方立法进程页核验其当前状态，不要写成已生效）；【公开】模型卡片形式有 2019 年的公开论文（见 5.2.1）；Agent Card 与决策级可问责：无公开可核验来源，属 L3。
- **成熟度**：**L3**（与 5.1 表「可问责与举证」行一致：① 不满足、② 不满足、③ 不满足）。本条覆盖：决策可解释 → 决策可问责（决策链、责任人、影响评估）、Agent Card（能力清单、Tool 列表、安全边界、回滚机制）、AI 资产入表。

- **失效条件**：当业务里的 AI 决策不产生不可逆后果（只读查询、草稿生成）时，动作级授权与留痕的收益低于它的成本——此时该做的是卡片与工具白名单，而不是决策链。判据是：**存在多少「错了之后无法用重跑撤销」的动作**。
- **自验方法**：取一次线上事故或一次用户投诉，试着只靠留痕回答四个问题——这次动作是谁发起的、用了哪一版 Prompt 与模型、命中了哪条策略、依据哪条记录批准放行。任一答不出，说明可问责这一层还没有建起来。

### 5.3 与本主题既有栈的接口在哪

本节不写「与 X 结合」这类空话，只写三件事：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 卡片 ↔ 发布流程（本章 [§3.2](01-ai-data-governance-section-3-sec3.md) 的 Model Card / Prompt Library） | 交接物 = 卡片字段（用途 / 数据 / 指标 / 局限 / Owner / 评审）；缺项不允许发布 | 发布流程侧；卡片过期无人负责 | L2（5.2.1） |
| 网关 ↔ 调用通路（主文件 §1.4 的输出类资产） | 交接物 = 一次调用的请求、策略判定与放行结果；拦截在通路内发生 | 网关侧管拦截，业务侧管语义正确 | L2（5.2.2） |
| 台账 ↔ 主文件 §2.1 的五元组 | 交接物 = `⟨T, C, I, R, X⟩` + **授权人**（本节补的那一维） | 治理侧；台账缺「授权人」列就覆盖不到 Agent 场景 | 五元组 L2；「授权人」一维需自建 |
| 知识侧治理 ↔ Ch4 · 05 RAG 架构 / Ch4 · 02 向量湖 | 交接物 = 文档版本 + 片段元数据 + 索引版本；回答必须能指回片段 | 检索侧管召回，治理侧管版本与引用口径 | L2（5.2.3） |
| 知识侧治理 ↔ Ch1 · 06 知识图谱 | 交接物 = 本体版本 + 实体 / 关系置信度 + 专家签字 | 图侧；本体变更要能回退到上一版 | L2（5.2.3 的 GraphRAG 子项；容器能力与族内其它子项同档，本体签字与回滚流程仍需自建） |
| 反馈数据 ↔ Ch7 · 02 反馈闭环 | 交接物 = 反馈事件（来源、留存期、二次使用授权） | 合规侧与产品侧共同；缺登记则「这条反馈训过谁」答不出 | 义务性接口，需自建 |
| 证据层 ↔ 本章 §7 的横向合规证据层（GRC） | 交接物 = 散在各个控制点的证据汇总成法规映射表 | 合规侧；技术控制点不产出法规映射 | 商业平台为主，需采购或自建 |

一句话概括：**AI 没有让治理多出新的义务类型，它把控制点从「资产」挪到了「动作」**。因此接口上多出来的只有三样东西——**授权（谁批的）、策略版本（依据哪一版）、动作级记录（做了什么）**。三样缺一，可问责就只停在文档里。

三条最容易出错的约定，单独写清：

**第一，证据必须与它证明的那次动作同源产生。** 事后补写的审批记录、月末汇总的合规报告，都无法证明「这条调用当时被拦过」。判定方法很直接：抽一次历史调用，看能不能从留痕里还原出策略版本与放行结论；还原不出的部分，就是将来审计会问到的地方。

**第二，登记与拦截要各管各的对象，不要互相替代。** 用登记去管运行时动作，等于要求登记表预先知道下一步会发生什么；用拦截去管已经发布的模型与数据集，等于把控制点放在了封面上。判定方法是问：这条控制规则约束的对象，在它生效的那一刻**是否已经存在**。

**第三，证据要能区分「拦住了」与「没人来」。** 一个只统计拦截次数的看板，会把「策略生效」与「调用量掉了」显示成同一条曲线上升。判定方法是同时看三个数：进通路的调用量、被拦比例、放行后的投诉量——只有前两个同时稳定，第三个才说明策略的灵敏度合理；调用量掉了而拦截率上升，通常是业务已经绕开。

### 5.4 公开进展与文献

分四类列，对应三种核验方式：**论文**（看题名与发表年份）、**法规与标准 / 厂商框架**（合起来是「官方 release note 与版本化文档」，法规看公布日与生效日，产品文档看版本号与 GA / 预览标记）、**检索入口**（页面持续更新，只给检索点与判定标准）、**第三方（非厂商）公开生产案例**。**能给出文本名 + 年份的才作为文献条目**；持续更新的产品文档页与标准项目页标一个固定年份反而不可复现（同一页面在不同时间检索到的内容并不相同），这类只作「检索入口」单列，给出检索点与判定标准。宁少勿假。

**论文**【公开】

- Mitchell 等「Model Cards for Model Reporting」（2019）：卡片这一形式的公开出处，5.2.1 的机制来源。
- Lewis 等「Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks」（NeurIPS 2020）：检索增强的机制出处，5.2.3 引用。
- Lundberg 与 Lee「A Unified Approach to Interpreting Model Predictions」（NeurIPS 2017）与 Ribeiro 等「Why Should I Trust You? Explaining the Predictions of Any Classifier」（KDD 2016）：可解释性方法的公开出处，5.2.4 用它区分「可解释」与「可问责」。
- Edge 等「From Local to Global: A Graph RAG Approach to Query-Focused Summarization」（2024）：图结构与向量结合的公开方法，5.2.3 引用；同名的开源实现以官方仓库当前版本为准。

**法规与标准**【公开】

- EU AI Act：2024-08-01 生效，禁止性条款 2025-02-02 适用、通用 AI 规则 2025-08-02 适用、大部分义务 2026-08-02 适用（时间表见主文件 §2.3；以欧盟官方文本为准）。它是本节唯一一条**能直接给出分级定义**的材料——但按 5.1 的口径，它证明义务存在，不充当判据 ②。
- ISO/IEC 42001（2023-12 发布）：AI 管理体系标准，可认证。核验方式是查标准号与发布年份，不是查咨询公司的解读页。
- NIST AI RMF 1.0（2023-01）与其 Generative AI Profile（2024-07）：自愿性框架，Profile 把风险清单落到生成式场景。
- 中国《生成式人工智能服务管理暂行办法》（2023-08 生效）与中国《人工智能生成合成内容标识办法》（2025 年公布、2025-09 起施行；具体日期以国家网信办公布文本为准）：两条都属于**强制**义务，涉及备案、内容审核与生成内容标识。
- 中国信通院《AI 安全标准化白皮书》（2024 版，按发布机构公开页面核验版本与年份）：国内标准体系的整理材料。

**厂商框架与规范（判据 ① 的核验入口）**【公开】

- Anthropic 的 Model Spec 与 Responsible Scaling Policy、Constitutional AI 的方法论文（Bai 等「Constitutional AI: Harmlessness from AI Feedback」，2022）、OpenAI 的 Model Spec 与 Preparedness Framework、Google 的 SAIF、Microsoft 的公开 AI 准则——核验点是**有没有「可核验的分级发布规则与评审记录」**（哪一级触发什么动作、谁签的字），而不是承诺的措辞；版本号与日期以官方页面当前版本为准。这类材料是厂商自述：可以用来说明「机制存在」，不能用来当判据 ②。
- 卡片规范类：Hugging Face 的 Model Card 文档与主流卡片模板——核验点是字段集与是否版本化，不替代各家的评审流程。
- 安全清单类：OWASP Top 10 for LLM Applications（2023 首次发布，其后有新版）与 MITRE ATLAS（持续更新）——两者都是**清单**，核验点是版本号与发布日期，看它们覆盖的条目是否包含你用的那一类接口（例如工具调用、检索注入）。

**检索入口（文档页持续更新，本节不代写文档名与年份，只给检索点与判定标准）**

- Cloudflare AI Gateway / Portkey / Lakera / NVIDIA NeMo Guardrails / Salesforce Einstein Trust Layer——检索点：官方文档里「策略」「拦截」「放行」「自托管」的正式条目；判定标准是**「策略语言怎么写、放行结论落在哪里、能不能自托管」**，不是功能页上的风险清单长度。
- AgentScope / LangGraph 一类 Agent 框架——检索点：官方文档里工具权限与中断 / 恢复原语；判定标准是「有没有授权模型与动作级审计接口」，不是「支持多少工具」。
- Langfuse / Helicone / Arize Phoenix 一类观测工具——检索点：trace 的字段结构；判定标准是「一次调用能不能被还原成可标注、可举证的记录」。

**第三方（非厂商）公开生产案例**

- 无公开可核验来源。本章 §6 的四个案例（阿里 / 字节 / 微软 / OpenAI）均为建设方自述或厂商自述，按 5.1 的口径属于「仅有厂商自有案例」，不构成本节的判据 ②——它们能用来说明机制存在，不能用来当第三方证据。这是本节没有任何方向被评为 L1 的直接原因。

**为什么把法规与厂商文档分成两类列**：两者的核验方式不同。法规与标准用**公布日与生效日**核验，回答的是「义务是否已经产生、从哪天起产生」；厂商文档用**版本号与 GA / 预览标记**核验，回答的是「这个能力是不是已经可用」。把两类混在一张表里，会出现两种典型误读——用「法规已生效」证明「治理已落地」，或用「厂商有这项能力」证明「义务已经履行」。判定方法很具体：对同一条方向，分别写下「义务从哪天起生效」与「执行点从哪版起可用」，两个日期都对得上，才谈得上可执行。

**引用纪律**：本节涉及法规与产品迭代都快，最容易出错的三类引用是——

| 引用类型 | 常见错误 | 核验方式 |
| --- | --- | --- |
| 「某法案要求 X」 | 把草案写成已生效法律，或把提案时间当生效时间 | 查官方立法进程页的当前状态与生效日；EU AI Act 的分阶段时间表见主文件 §2.3 |
| 「某平台支持某治理能力」 | 把演示或预览写成 GA，把「有拦截」当成「有策略管理」 | 查官方文档中该能力的标记（GA / 预览）与适用版本，不看案例页 |
| 「某框架/标准让合规成本下降 X%」 | 把咨询方或厂商自述当可比较结论 | 看指标定义与样本，以及有没有非建设方的复现 |

**值得注意的空白**：公开材料里能查到「义务是什么」与「产品有什么能力」，查不到「控制点放在哪、拦住了什么、误拦了多少、谁签字放行」。原因是治理的失败形态多半是**过拦**——业务绕开流程，而这不会被写成事故报告。它同时意味着：**这类判断只能自己测**——这正是 5.2 为每个方向各配一条自验方法（共四条）的原因：抽三张卡片比对版本、统计被拦与投诉两个数、任取一条历史回答回溯文档版本、取一次线上事故只靠留痕回答四个问题。

### 5.5 被过度宣传的部分

**「AI 治理自动化（AI for Governance）：用 LLM 自动生成合规报告、自动分类风险」**

- *实际是什么*：能自动化的只有「把已有证据整理成映射表」这一段——它需要先有证据；没有控制点，自动生成出来的只是措辞漂亮的报告。
- *为什么会这样*：报告里的每一句话都要能指回一次具体判定或一次签字，而这两样由运行时与流程产出，模型补不出来；「治理工具碎片化」也不会被自动化消除——碎片化的根源是治理单元不同（本章 §7 的判据一），标准只统一字段，不统一单元。
- *什么时候它才会成真*：控制点先落下可查询的证据，且出现被多方引用的证据字段口径时。它可以先做一件事：**把散落的证据汇总**，而不是**代替证据**。

**「AI 资产入表：模型权重与训练数据集作为无形资产进财务报表」**

- *实际是什么*：估值方法学尚未成熟，而入表会产生反向激励——为了让报表数字成立，团队有动机把资产评得更值钱，这个动机与治理要的审慎正好相反。
- *为什么会这样*：模型的产出价值不随使用次数线性增长，也不随参数规模线性增长；而会计口径要的是可复算，两者之间缺少可核验的换算。
- *什么时候它才会成真*：出现被监管与审计共同接受的估值口径，且它不依赖建设方自述的关键假设。在那之前，能做的是把资产台账的字段补齐（版本、来源、Owner、评审），而不是预估它的货币价值。

**「实时合规网关能替你担责」**

- *实际是什么*：网关提供执行点，不提供策略；它记录「这条被拦了」，不决定「什么该拦」。「AI 攻击向量快速演进」正是这条的边界——清单与规则永远滞后于攻击面，所以拦截只能降低暴露面，不能把责任转移给工具。
- *为什么会这样*：误拦与漏拦的取舍是一个业务判断（哪一类错更贵），业务判断必须有人签字，产品替代不了。（合规成本失控、过度治理抑制创新）说的也是同一件事的反面：拦得太紧，业务会绕开，然后这一层的全部证据一起失效。
- *什么时候它才会成真*：出现可移植的策略语言与可举证的放行结论（谁批的、依据哪一版策略），让误拦的代价可被度量。在那之前，网关的正确用法是「先把必须过网关的调用收口」，而不是「先堆策略」。

这三条有一个共同结构：它们都把「执行点已经就位」说成「治理已经就位」。执行点确实已经就位（这也是运行时拦截能评 L2 的原因），但「就位」指的是**能力存在**，不是**责任已有人负**。所以判断它们何时成真的办法是同一个——看公开材料里有没有出现可核验的判断依据（策略版本、签字记录、证据字段口径），而不是看功能页上有没有多一个带「Governance」的名字。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 可问责的落点从「模型卡片」转向「**一次动作的授权与留痕**」 | 公开材料里出现动作级授权字段（发起人 / 策略版本 / 放行结论）作为默认项的讨论与实践；卡片不再被当作可问责的主要载体 | 三年后主流做法仍以卡片与模型级说明作为唯一的问责材料 |
| 实时拦截成为对外 AI 服务的**默认件**，与安全能力合并 | 网关类产品的正式条目里，治理判定与安全防御不再是两个产品线，且默认开启 | 治理判定长期停留在独立产品，或需要额外集成才生效 |
| 跨国合规协同收敛到「**按角色分配义务**」，但不会出现单一全球文本 | 各法域的新文本继续沿用「提供者 / 部署者」这类角色划分，并出现互认或映射的公开材料 | 出现被主要法域共同采纳的单一文本；或各法域回到互不相容的分类体系 |
| 治理自动化停在「出候选」，**不与「自动发布」合并** | 公开规则与产品文档都保留「人工签字」这一环，自动化只覆盖证据汇总与候选生成 | 出现把合规判定直连发布流程、且不需要人工签字的成熟做法 |

四条预测都能靠**公开文档**证实或证伪，不需要内部数据：第 1、4 条看产品接口与流程文档的形态，一到三年见分晓【经验：随产品换代速度变，更新越慢窗口越长】；第 2 条看网关产品的条目划分，一到三年；第 3 条看各法域文本的更新，三到五年【经验：随立法周期变，不同法域差别大】。

最值得先盯的是第 4 条：它是本节唯一一条**不依赖任何新模型能力**就能观察到的信号——「自动化出候选」与「自动发布生效」之间隔着一次人工签字，这次签字是流程设计，不是技术限制。它也是判断一套治理体系是否会被业务绕开的最早指标。

**写不出信号的预测不要写**：把它记录在 5.5，比给一个永远正确的句子更有用。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有几个内部 LLM 应用，调用散落各处 | 先把调用收口到网关（5.2.2），策略先放三条：出仓、敏感信息、工具白名单【经验：随对外 / 对内与义务条数变，对外服务的起步条数比内部工具多】 | 网关产品是否出现可移植的策略语言 | 不要在调用还没收口时堆策略——绕过网关的那部分会让全部证据失效 |
| 对外提供生成式服务，受监管 | 补卡片与评估记录，并把标识与内容审核义务落进发布流程 | 标识与备案类细则的更新（5.4 的法规条目） | 不要把法规文本当执行证据——义务存在不等于有人在执行 |
| 要做检索增强 / 知识库问答 | 先做「每条回答能指回文档版本」（5.2.3），元数据先补 Owner 与版本 | 是否出现引用正确性的公共判定口径 | 不要在文档没有 Owner 时引入本体治理——语义变更的回滚比代码贵 |
| Agent 要碰写操作与资金类动作 | 先做授权与动作级留痕，最小权限的工具白名单 | Agent 卡与授权模型是否形成共识 | 不要在缺留痕时放开不可逆动作；也不要指望卡片代替授权 |
| 被要求「AI 资产入表」或上治理平台 | 先把台账字段补齐（版本、来源、Owner、评审），把证据字段口径写下来 | 是否出现被审计共同接受的估值口径 | 不要为报表数字预留字段假设；不要在证据不可查时采购自动化治理平台 |

「明确不要做」那一列的共用逻辑只有一句：**本节真正变了的是控制点的位置（从资产挪到动作），没变的是「谁签字、谁负责」**。所以预算该投在三件确定性工程上——调用收口、证据同源、授权留痕；在这三件之前，任何「自动治理」「资产入表」的投入都不会带来可度量的风险下降，反而会先被业务绕开。

如果只能排一个顺序，按这条走：

1. **先收口调用通路**：让必须过网关的调用真的都过网关，并记录放行结论。这一步不需要新采购。
2. **再补卡片与台账的最小字段集**，并把它挂到发布流程上——不挂流程的卡片不会有人填。
3. **然后给检索侧加版本身份**：回答能指回片段与文档版本。
4. **最后才谈可问责与入表**：它们要求先有权责划分，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新的模型能力——收口、字段、版本、留痕，全是工程与流程。这也解释了本节为什么没有 L1：真正已经就位的那部分（登记与拦截的实现）不需要被宣传，而需要被宣传的那部分（Agent 卡、决策级可问责、资产入表），还没有成熟到能被第三方核验。两者之间的落差，就是本节四行评级全部停在 L2 与 L3 的原因。

### 5.8 小结

> 本节小结：AI 治理里 AI 真正改变的只有一条机制——**它把治理对象从可枚举的资产换成了运行时才产生的动作**，因此控制点不得不从「事后审计 + 事前登记」挪进「调用通路之内」；它没有改变的是**责任来源**：策略由谁写、误拦由谁批、放行记录留多久，这三件事仍然落在组织与人身上，网关只提供执行点。所以本节没有 L1 方向：能排进路线图的是调用收口、证据同源、授权留痕这三件工程，而不是 Agent 卡、决策级可问责或 AI 资产入表。
>
> 💡 **思考锚点**：数一下你组织里有多少个 LLM 调用入口，其中「必须过网关的调用真的都过了」占几成——按本节判断，哪怕只有一小部分绕过网关，全部放行记录与留痕就一起失效；你会先收口调用通路，还是先补卡片与台账字段？
