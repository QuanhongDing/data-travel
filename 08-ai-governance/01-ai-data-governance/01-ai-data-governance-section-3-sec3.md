## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

有人把治理设计讲成一个按人头挑配置的问题（按公司画像与规模给推荐模式），而真实项目里公司规模几乎从不是决定因素。一家只有 30 人、但对外提供日调用量很大的生成式服务的公司，需要的治理机制比一家 5000 人、只做内部 BI 报表的公司**更重**；反过来，同一家公司内部那个「每个月跑几十次人工触发的实验」也不该被套上对外服务的同一套机制。真正在决定模式的是四条约束：治理单元在什么时刻产生、控制点能不能插进数据通路、成本随什么增长，以及团队具备哪些工程能力。

第一条约束来自治理对象的形态。主文件 §2.1 把 AI 资产定义为五元组 `A = ⟨T, C, I, R, X⟩`（类型 / 机密性 / 完整性 / 风险 / 可解释性）。这个定义隐含了一个前提：**资产是可枚举的实体**。所以当治理对象是「模型权重文件 / 数据集版本 / Prompt 模板」时，围绕这个五元组建台账的模式（模式 1 / 2 / 3）在结构上成立；而当治理对象是「一次调用」「一次工具动作」时，五元组里缺了一个维度——**这次行为是谁被授权做的**（§7.3.1 与 §7.3.3）。缺的那一维不是可以事后补注释的字段，它决定了台账要另起一张行数按事件增长的表。约束先于模式，就体现在这里。

第二条约束是控制点位置。§7.3.4 把控制点分成四类：事后审计 / 事前登记 / 事中门禁 / 授权制，并给出一条因果——**一个控制点只能阻断流经它的东西**。这条因果把 8 个模式劈成三组：登记类（1 / 2 / 3）把控制点放在发布流程上，只能约束已枚举的资产；证据类（4 / 5）把控制点放在事后或准入环节，只能追责或放行；位置类（6 / 7 / 8）讨论的则是控制点放在组织与通路的哪个位置。**选错组不是效果差一点，而是机制根本不运行**：给长尾调用建一个让人来登记的目录，登记得完的那些调用，往往本来就不需要治理。

第三条约束是成本随什么增长。登记制的成本随**资产数**线性增长，拦截制的成本随**调用量**线性增长，合规映射表的成本随**法域数 × 适用框架数**增长。三条曲线的斜率不同，谁先失控取决于业务形态而不是技术先进性。最后一条约束是团队能力：模式 6 / 7 / 8 分别要求组织具备「策略即代码」「跨目录的稳定连接键」「网关改造与通路收口」这三件工程能力，缺这些能力时，这三个模式落地后会退化成一份文档，而不是一个结构性保证。

这四条是**机制层面**的约束；下表把它们展开为设计时要逐行确认的**六个约束输入**，两者不是一一对应：「数据形态 / 写入模式」一行同时承接机制一与机制二（治理单元的产生时刻决定台账以实体为行还是以事件为行，控制点能不能插进通路决定取登记制还是拦截制），「规模与成本约束」承接机制三，「团队技能与运维能力」就是机制四；而「访问模式」「变更频率与历史要求」「一致性要求」三行不由这四条推出——它们分别取决于审计证据的读取形态（§7.3.2）、模型与 Prompt 的迭代节奏、以及同一资产要同时满足几个法域的要求（§7.3.3）。读下表时不要试图把它归并回四条，而要逐行确认自己项目的取值。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式（资产是可枚举实体，还是运行时才产生的动作） | 台账以「实体」为行还是以「事件」为行；是登记制还是拦截制 | 「先建治理平台，再让业务来登记」——长尾调用永远不会主动来登记 |
| 访问模式（点查 / 扫描 / 聚合）（审计是逐条重放还是聚合报表） | 审计明细与聚合是否分层存放 | 「日志都留着了，出事能查」——留了日志不等于能举证（§7.3.2） |
| 变更频率与历史要求（模型 / Prompt / 数据集多久迭代一次） | 登记字段是人工填还是流水线自动填；卡片会不会过期 | 「模型卡片写一次就行」——卡片的人写属性使它必然滞后于产物 |
| 一致性要求（同一模型在不同法域下的义务是否相同） | 风险等级是标量还是「法域 → 等级」的向量 | 「一份合规清单全球通用」——AI Act 的义务按角色分配，不按资产 |
| 规模与成本约束（资产数 / 调用量 / 法域数） | 哪条成本曲线先成为主导项 | 「等规模上来再治理」——登记制的成本曲线斜率天然比收益陡 |
| 团队技能与运维能力（策略即代码 / 网关改造 / 跨目录缝合） | 模式 6 / 7 / 8 是落地成结构，还是落地成文档 | 「买个商业平台就等于有了联邦治理」——工具不含组织的契约 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 Model Card（模型卡片）

- **被什么约束逼出来**：模型是二进制产物、权重不可读，而使用方必须判断「这个模型能不能用在我的场景」。
- **结构**：

```yaml
# Model Card（一页纸，字段固定；缺项不允许发布）
model_id:      md-rec-v7          # 与 Asset Registry 同键
intended_use:  商品推荐排序        # 用途，而非密级——风险等级由此推导
out_of_scope:  信贷 / 医疗等场景    # 边界比能力更重要
training_data: ds-rec-2024q1      # 数据集标识 + 哈希（可寻址，不是描述）
metrics:       {overall: …, by_group: …}   # 总量指标 + 分群指标
limitations:   冷启动商品表现存在偏差
owner:         @algo-rec          # 具体到人
review:        {assessment_id: ra-2024-11, approver: @ai-governance}
```

- **为什么这样设计有效**：因为卡片把「模型能不能用」从一次口头询问变成一份**可对比、可归档的判定输入**，所以每次评估不必重新问一遍作者；又因为 `intended_use` 与 `out_of_scope` 是必填项，风险等级（模式 5）才有一个输入而不用猜。
- **代价**：卡片是人写的文档，它与产物的绑定强度由流程保证、不由结构保证；每迭代一版模型就多一份需要维护的资产，维护面随版本数增长。
- **失效点**：当模型的迭代频率高于卡片的更新频率时，「一页纸看懂一个模型」会反转成「读者按过时信息做判断」，因为卡片的名字与内容之间没有强制约束——哪怕卡片文件名带 `v7`，也没有任何机制保证它描述的就是 v7。
- **真实使用**：Model Card 源自《Model Cards for Model Reporting》（【公开】Mitchell et al., FAT\* 2019），同族的数据集侧文档是 Datasheets for Datasets（【公开】Gebru et al., 2018）。成熟做法不是把卡片当文档挂在 Wiki 上，而是**把字段从训练与发布流水线自动填充，人工只补 `intended_use` / `out_of_scope` / `limitations` 三项**（【经验】——判断方法是看仓库里卡片的生成方式：手写 Markdown 的会过期，由流水线渲染的不会）。工具侧可自行核验的形态有三类：Hugging Face 把 Model Card 做成模型页的固定区块、MLflow 提供 Model Card API、MosaicML 侧把卡片与训练产物放在一起登记（【经验】——产品文档公开可核验）。

#### 3.2.2 Prompt Library（Prompt 库）

- **被什么约束逼出来**：Prompt 是纯文本、跨团队复制、改完看不出哪个版本在生产——文本形态使「版本」这件事必须被显式建模。
- **结构**：

```sql
CREATE TABLE prompt_template (
  prompt_id   TEXT NOT NULL,
  version     INT  NOT NULL,
  body_ref    TEXT NOT NULL,   -- 指向版本库中的文件，不把正文存进表
  model_hint  TEXT,            -- 适配的模型族，不绑定具体模型版本
  owner       TEXT NOT NULL,   -- 具体到人
  status      TEXT NOT NULL CHECK (status IN ('draft','canary','prod','retired')),
  eval_run_id TEXT,            -- 发布前必须挂一次评估结果
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (prompt_id, version)
);
-- 运行时只能按 (prompt_id, version) 取用：版本回指靠主键，不靠人工记录
```

- **为什么这样设计有效**：因为版本回指靠主键而不是靠人回忆，所以线上出现输出回归时，可以把 trace 里的 `(prompt_id, version)` 直接定位到具体正文与那次评估结果；因为 `body_ref` 指向版本库而不是存正文，正文的历史与评审走代码那一套流程，不必再发明第二套。
- **代价**：库成为调用链路的前置依赖（取不到模板就取不到 Prompt），并且每次修改都要多走一次「新版本 + 状态流转」的动作；跨团队复用的模板还要处理归属与变更通知。
- **失效点**：当 Prompt 库只是**一个让人来登记的入口**、而没有成为运行时可寻址的唯一来源时，覆盖率会持续下降——因为把 Prompt 直接写进代码字符串的边际成本更低，而登记制的覆盖只能约束「已枚举且遵守流程」的调用。这对应 §7.3.4 的通用因果：控制点不在通路上，就只能追责不能止损。
- **真实使用**：工具形态可自行核验：Langfuse / PromptLayer / LangSmith 都把「Prompt 版本 + 标签（如 prod）」做成一等公民，Dust 这类以 Prompt 与编排为中心的形态也把 Prompt 当作可发布对象（【经验】）；自研的常见形态是 **YAML + Git，让 Prompt 与代码共用同一套评审与发布流程**（【经验】）。判断方法：查这个团队的生产调用里，`prompt_id + version` 是否能从 trace 反查到提交记录。

#### 3.2.3 AI Asset Registry（AI 资产注册中心）

- **被什么约束逼出来**：模型、Prompt、Embedding、训练数据、输出五类资产分散在五套工具里，跨类影响面（改了数据集会影响哪些模型和下游应用）无法一次问清。
- **结构**：

```sql
CREATE TABLE ai_asset (
  asset_id   TEXT PRIMARY KEY,             -- 全局唯一，跨类型不重号
  asset_type TEXT NOT NULL CHECK (asset_type IN
             ('model','prompt','embedding','dataset','output')),
  conf_level TEXT NOT NULL,                -- C：机密性
  integrity  TEXT NOT NULL,                -- I：完整性
  risk_level TEXT NOT NULL,                -- R：风险等级
  explain    TEXT NOT NULL,                -- X：可解释性
  role       TEXT NOT NULL,                -- 义务归属：提供者 / 部署者（§7.3.3）
  owner      TEXT NOT NULL,
  payload    JSONB NOT NULL                -- 类型特有属性，只能进扩展位
);

CREATE TABLE ai_asset_edge (
  src  TEXT REFERENCES ai_asset,
  dst  TEXT REFERENCES ai_asset,
  kind TEXT CHECK (kind IN ('derives_from','serves','uses_context')),
  PRIMARY KEY (src, dst, kind)
);
-- ⟨T,C,I,R,X⟩ 落成列；role 是 AI 场景新增的字段（§7.3.3）
```

- **为什么这样设计有效**：因为所有类型共用一套 ID 与一张关系表，所以「这个数据集的下游有哪些模型、哪些应用」是一次图遍历而不是五次跨工具询问；因为 `role` 是行级字段，同一个模型在「自用」与「对外提供」两种角色下的义务差异可以被台账区分开。
- **代价**：统一表结构会迫使类型特有的属性退到 `payload` 里（JSON 字段不可索引、不可校验）；同时 registry 变成所有团队发布流程的强依赖，它不可用时发布流程整体停摆。
- **失效点**：当资产规模进入「万级以上、且每天新增以百计」时，「跨类影响面一次图遍历就能查清」会反转成「遍历出一张不可信的图」——因为登记的边际成本随资产数线性增长，而治理收益（可发现性）不随之增长，团队会开始填空壳字段，`ai_asset_edge` 的边（`derives_from` / `serves`）大面积缺失，于是影响面查询漏掉下游却没有任何报错，registry 保留下来的是一个**看起来完备、实际会把下游查漏**的目录。
- **真实使用**：Unity Catalog + MLflow 的组合把模型与函数注册为可治理资产（【经验】）；阿里 PAI 资产中心走的是同一条路线（【经验】——产品线公开可核验）。本章 [§6.1 阿里案例](01-ai-data-governance-section-6-sec6.md) 记录的「阿里把模型 / Prompt / 数据 / 输出四面治理收口到统一网关」是一条**出处待补**的记录：§1.1 对该材料只写了 `[阿里公开材料 2020-2024]` 这一方括号标记，没有标题、作者或链接，因此这里不按【公开】采信，降为【经验】；要按【公开】引用，需先补上可定位的原始出处。判断方法：问「上一次字段级影响面是怎么查出来的」——如果答案是「拉了三个群问」，那么 registry 要么不存在，要么不被信任。

#### 3.2.4 AI Audit Log（AI 全链路审计）

- **被什么约束逼出来**：LLM 推理默认非确定性（采样），同一输入的两次输出可以不同，所以「留了日志」与「能举证」之间差着一整层。
- **结构**：

```sql
CREATE TABLE llm_span (
  trace_id          TEXT NOT NULL,
  span_id           TEXT NOT NULL,
  parent_span       TEXT,
  model_id          TEXT NOT NULL,   -- 模型版本，不是模型名
  prompt_key        TEXT NOT NULL,   -- (prompt_id, version)
  decode_params     JSONB NOT NULL,  -- temperature / top_p / max_tokens
  retrieved_doc_ids TEXT[],          -- RAG：上下文是运行时变量
  guardrail_verdict TEXT,            -- 护栏判定结果
  subject_ref       TEXT,            -- 主体引用（化名，不落原文）
  PRIMARY KEY (trace_id, span_id)
);
-- 少任何一列，"当时为什么这样输出"就复现不了（§7.3.2）
```

- **为什么这样设计有效**：因为审计字段是从「可复现」倒推出来的而不是从「日志系统默认有什么」正推的，所以它能在不接触线上环境的前提下重建一次输出；因为 span 带 `parent_span`，一次多步调用（检索 → 改写 → 生成 → 二次校验）可以被还原成调用树，而不是一堆散落日志。
- **代价**：写入放大——一次调用往往写多行 span；存储成本随调用量线性增长（这是拦截制成本曲线的来源，§7.4）；更麻烦的是 trace 里会带上用户输入与模型输出，**日志系统本身成为新的合规面**，必须做化名与访问控制。
- **失效点**：当日志只记「输入 + 输出」而没记「当时生效的模型版本、Prompt 版本与采样参数」时，「全链路可追溯」会反转成「知道发生过什么，但证明不了为什么」——因为输出不是输入的确定函数，缺任何一项条件都无法重放。同理，只留最终输出不留检索到的文档 ID 时，RAG 场景的归因能力直接归零。
- **真实使用**：OpenTelemetry 的 GenAI 语义约定把模型名、请求参数、Token 用量等定义成 span 属性，从而使 LLM 调用可以接入既有的可观测体系（【经验】——约定文本公开可核验）；商业与开源产品（Langfuse / Helicone / Arize Phoenix）都把 trace 当作一等公民而不是附件，自研的常见形态是 OpenTelemetry 采集 + ClickHouse 一类列存落地（【经验】——产品文档与项目文档公开可核验）。判断方法：只凭留存字段、不碰线上，能不能重建上周某次输出——答不出就是证据强度不够。

#### 3.2.5 AI Risk Assessment（AI 风险评估）

- **被什么约束逼出来**：法规不治理技术，法规按**用途与角色**分配义务，所以「这个系统属于哪一级、因此要履行什么」必须在发布前被判定出来，而不是事后解释。
- **结构**：

```text
风险评估：等级由四个变量推导，而不是由主观打分
   用途 use_case      → 是否落在高风险清单（招聘 / 信贷 / 关键基础设施 / 教育评估…）
   自主性 autonomy    → 是否存在有效的人为监督
   部署规模 scale     → 影响人数、是否面向公众
   主体脆弱性 subject → 未成年人 / 患者 / 求职者 / 员工…
          │
          ▼
   风险等级 ∈ {Unacceptable, High, Limited, Minimal}
          │
   义务清单（随角色变化，不随资产变化）：
     提供者：技术文档、市场准入前登记、质量管理体系
     部署者：日志留存、人工监督、向使用者告知
```

- **为什么这样设计有效**：因为等级由「用途 + 自主性 + 规模 + 主体脆弱性」四变量决定，所以同一个模型换一个用途就会换一个等级——这把「要不要做重治理」从技术类型问题改成了业务用途问题，也解释了为什么「我们用的只是个很小的模型」不构成减免理由。
- **代价**：评估是一份需要持续维护的活文档；风险等级变化会连带义务清单变化，而义务清单又映射到控制点，因此每次用途变更都要重跑一遍映射；跨法域时等级不是标量而是向量（§7.3.3），台账字段要按最复杂的法域设计。
- **失效点**：当评估被做成**一次性准入动作**（上线前做一次、之后不再复核）时，「事前判定义务」会反转成「一份过期的合规背书」——因为风险等级随用途、自主性、部署规模变化，而这些变化通常不会触发任何流程，台账上仍写着原来的等级。
- **真实使用**：EU AI Act 把高风险系统的义务做成两层叠加——投放市场前的技术文档与登记，以及运行期的日志留存与人工监督（【公开】EU AI Act, 2024）；NIST AI RMF 1.0 用 GOVERN / MAP / MEASURE / MANAGE 四项功能把风险治理流程化（【公开】NIST AI 100-1, 2023）；ISO/IEC 42001:2023 把 AI 管理体系做成可认证对象（【公开】ISO/IEC 42001:2023）。三者的差别不在技术，而在谁向谁举证。落地时更常用的是配套工具而不是法规原文：欧盟 ALTAI 把高层要求拆成可勾选的自评清单，NIST 侧的 AI RMF Tool 与 Profile 把 GOVERN / MAP / MEASURE / MANAGE 四项功能按具体用途展开（【经验】——欧盟 ALTAI 与 NIST AI RMF 的配套材料可自行核验，本节未核到可引用的公开出处）。

#### 3.2.6 Federated AI Governance（联邦化 AI 治理）

- **被什么约束逼出来**：多法域 / 多事业部组织里，策略必须统一（否则无法对外一致举证），但执行必须本地化（否则本地合规与业务节奏无法满足）。
- **结构**：

```text
联邦化：中央定策略，边缘执行，事件回流
   中央（策略与契约）                边缘（BU / 法域）
   ├─ 策略仓库（Policy-as-Code） ──► 本地策略引擎 → 本地决策日志
   ├─ 字段与事件契约 ─────────────► 本地采集器（必须遵循同一契约）
   └─ 统一审计视图 ◄────────────── 事件回流（化名 + 统一字段）
   ─────────────────────────────────────────────
   前提是契约先于策略：契约不统一，联邦制就退化成"各处各写一套"
```

- **为什么这样设计有效**：因为回流事件共享同一套字段与语义，所以中央能在不接管本地执行的前提下做全局举证与横向比较；因为策略以代码形式下发，本地适配的每一处偏离都是可评审的差异，而不是口头解释。
- **代价**：要维护两套东西——策略仓库与事件契约；契约演进是跨组织的协调动作，一次字段变更要推动所有边缘节点升级；本地策略引擎成为本地发布路径上的依赖。
- **失效点**：当法域之间的要求**直接冲突**（同一模型在一地禁止、在另一地允许）时，「统一策略 + 本地适配」会反转成「本地各写一套」，因为联邦制假定冲突可以通过本地参数化表达，而禁止性要求无法参数化——结果回流到中央的事件字段不再同构，统一审计的前提被破坏。
- **真实使用**：把策略以代码描述并用同一个引擎在各处求值（如 Open Policy Agent 这类策略引擎）是大型组织的常见做法，OPA 为 CNCF 项目、其项目状态与毕业时间可在 CNCF 项目清单中核验（【经验】——本节未核到可引用的公开出处，落地前请以基金会项目页的当前内容为准）。

#### 3.2.7 Hybrid AI Governance（混合治理）

- **被什么约束逼出来**：传统数据治理体系已经存在并承载了大量义务（表 / 字段 / 指标），AI 资产不能另起一套与它平行的世界——否则同一次事故要在两个互不相通的流程里各查一遍。
- **结构**：

```sql
-- 混合治理的接合点：一条稳定的连接键
CREATE TABLE asset_bridge (
  data_asset_urn TEXT NOT NULL,   -- 传统目录中的 URN（表 / 字段）
  ai_asset_id    TEXT NOT NULL,   -- AI 资产目录中的 ID
  link_kind      TEXT NOT NULL CHECK (link_kind IN
                 ('trained_on','serves_feature','feeds_eval')),
  PRIMARY KEY (data_asset_urn, ai_asset_id, link_kind)
);
-- 没有这张桥表，"模型出问题"与"哪张表出问题"是两条互不相通的排查流程
```

- **为什么这样设计有效**：因为两个目录靠桥表相连而不是靠复制元数据，所以传统侧的字段级血缘与 AI 侧的资产关系可以各自演进，同时在查询时被拼成一条端到端链路（数据 → 训练集 → 模型 → 应用）。
- **代价**：桥表本身需要有人维护（新增数据源、换训练集都要补边），且两个目录的 ID 体系一旦有一侧重构，桥表就要整体重映射；跨目录查询要么做物化视图，要么接受查询时的双跳延迟。
- **失效点**：当两个目录之间**没有稳定连接键**（同一个物理资产在两边 ID 不同、或靠名称模糊匹配）时，「血缘共享」会反转成「两张表各说各话」——因为桥表的主键本身不可信，跨域影响面查出来的结果既不全也不准，而团队仍会按它做决策。
- **真实使用**：Collibra、Informatica 这类平台在既有数据目录之上增加 AI 治理模块，走的正是这条混合路线（【经验】——产品线公开可核验）；本书 §7.2 也把「横向合规证据层」单列为与四档治理并列的一族，其机制同属「不采集资产、只重新组织别人的证据」。判断方法：能否用一条查询从某个字段走到依赖它的模型——走不通就说明桥不存在。

#### 3.2.8 Embedded AI Governance（嵌入式治理）

- **被什么约束逼出来**：AI 调用的治理单元在请求到达时才产生，且服务间调用是东西向的，所以挂在每个服务旁边（每个团队自己接）的控制点一定会因新服务上线而出现覆盖缺口。
- **结构**：

```text
嵌入式：控制点插进调用通路，而不是挂在通路旁边
   应用 ──► AI 网关 ──► 模型端点
              ├─ 入向：越权字段 / Prompt 注入 / 敏感数据检测
              ├─ 出向：内容判定 / 生成内容标识 / 日志落库
              └─ 路由：模型族、配额与降级（成本控制）
   ─────────────────────────────────────────────
   仅当"所有调用必经此处"时，覆盖率才是结构性保证；
   只要团队能直连模型端点，覆盖率立刻退回流程保证
```

- **为什么这样设计有效**：因为控制点位于所有调用的必经之处，覆盖不再依赖每个团队的自觉接入，新服务上线自动被覆盖；因为入向与出向都在同一处完成，审计所需的字段（模型版本、参数、护栏判定）可以在不要求业务改造的前提下被完整采集。
- **代价**：网关进入关键路径——增加一跳延迟，并成为单点（可用性要求随之上升）；必须显式选择故障方向：内容判定类门禁通常选 fail-open（误拦等于业务中断）并事后追责，授权判定类必须 fail-close（误放等于一次越权写），这个选择决定了它能否承载核心业务（§7.3.4）。
- **失效点**：当控制点只覆盖「经过网关的调用」、而模型端点仍可被直连时，贯穿式治理会反转成「覆盖率虚高」——因为覆盖变成了流程保证（要求大家走网关），而不是结构保证（物理上只能走网关）；通常还伴随例外名单长期不回收，例外变成常态。
- **真实使用**：工具侧可自行核验的形态包括 Portkey、Cloudflare AI Gateway、阿里云 AI 网关这类以「调用即治理」为定位的网关，以及 SageMaker Role Manager 这类把「谁能以什么角色调用」做成平台内建能力的组件（【经验】——产品文档公开可核验，本节未核到可引用的公开出处，落地前请自行核对）。本章 [§6.1 阿里案例](01-ai-data-governance-section-6-sec6.md) 记录的「阿里把模型 / Prompt / 数据 / 输出四面收口到统一网关」同属这一族，但该记录在 §1.1 中同样只有 `[阿里公开材料 2020-2024]` 这一无标题、无链接的标记，此处按【经验】而非【公开】记，引用前请自行核验。判断方法：做一次绕行测试——直连模型端点，看是否被拦。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 初创公司（< 50 人），资产 < 10，内部使用 | Model Card + Prompt Library | 不选 Asset Registry：资产少到一张表能装下，手工治理成本低于建平台成本 | 资产清单能不能在一小时内人工盘完 |
| 中型企业（50–500 人），资产 10–100，跨团队消费 | 上述 + Asset Registry + Audit Log | 不选 Federated：一个法域、一套策略，联邦制的契约成本无处摊薄 | 是否存在跨团队消费（有则必须可发现） |
| 大型企业（500–5000 人），资产 100+，多事业部 | 上述 + Risk Assessment + Hybrid（桥表缝合） | 不选纯 AI 目录：传统治理体系已在承载义务，平行体系会让事故排查分裂 | 传统目录与 AI 目录能否用一条查询贯通 |
| 跨国企业（> 5000 人），多法域 | 全模式 + Federated | 不选「中央强推单一策略」：禁止性要求无法参数化，本地合规会被架空 | 法域之间是否存在直接冲突的要求 |
| 金融行业 | 优先 Risk Assessment + Audit Log + Embedded | 不选轻量组合：举证责任要求可复现证据链，而非登记完备 | 能否只凭留存字段重放一次决策 |
| 医疗行业（含行业垂直规则） | 上述 + Hybrid（数据侧字段级血缘） | 不选「只做 AI 侧」：训练数据来自患者数据，数据侧的保留与用途限制同样受管 | 模型能否追溯到具体字段与用途授权 |
| 教育 / 政府 | Risk Assessment（按用途定级）+ Federated + 透明度披露 | 不选「按技术类型定级」：等级由用途与主体脆弱性决定，与技术先进程度无关 | 系统是否落在高风险用途清单内 |
| 互联网 / 消费 | Embedded + Audit Log + 输出标识与内容判定 | 不选「登记为主」：调用量大、变更快，登记制的边际成本先失控 | 日调用量是否以百万计 |

**最常被误选的一对是「AI Asset Registry（登记制）」与「Embedded AI Governance（拦截制）」**。误选的实际后果不是效果打折，而是**覆盖率的错觉**：在高调用量场景先投入半年建注册中心，凡是能被登记的资产都登得漂亮，而那些真正需要治理的长尾调用（临时脚本、业务侧自建的直连调用、未纳入流程的实验）永远不来登记；团队拿到的是「我们已经有治理平台」的信心，实际覆盖率停在一个没人敢量化的数字上。反过来，在只有几十个资产、用途稳定的场景上先上网关，则会出现「为了拦不存在的风险，把每一次内部实验都加了一跳延迟和一次审批」——两种误选有同一个根因：**按技术先进性挑模式，而不是按治理单元产生的速率挑模式**（§7.3.1）。

**选到模式之后还有一件事是排序**：先补举证压力最大的那一环，再补可发现性。涉及对外提供、或被监管直接问到的义务（Risk Assessment + Audit Log）先做，因为它们答不出就是违规；台账（Asset Registry）次之，它答不出只是低效；网关改造与联邦契约这类结构调整最后做，因为它们要动发布链路与组织边界，工期与阻力都最大。这个次序只取决于「答不出会怎样」，与模式的技术先进性无关。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Model Card + Prompt Library + AI Audit Log（台账轻 + 证据重）**

- 组合构成：卡片与版本化 Prompt 负责「有什么、谁能改」，审计负责「当时发生了什么」。
- 职责边界：登记类模式只负责已枚举的资产，证据类模式只负责运行时，两者不互相代偿——卡片写得好不能替代 trace。
- 运维代价：需要把卡片字段与 trace 字段接到同一条流水线上（发布时写入、调用时写入），否则两套 ID 对不上，现场排查要在三个系统之间来回切。
- 适合规模：数十个资产、单法域、内部为主的中型团队。

**组合二：AI Asset Registry + AI Risk Assessment + Hybrid（桥表缝合）**

- 组合构成：统一资产台账负责可发现，风险评估负责义务映射，桥表把传统数据目录与 AI 目录连成一条链。
- 职责边界：风险评估决定「要履行什么义务」，台账只负责「这些义务挂在哪个资产上」，桥表负责「AI 资产的下游数据责任归谁」。
- 运维代价：三张表的主键必须稳定，任何一侧重构 ID 都会让桥表重映射；跨目录查询要做物化或接受双跳延迟。
- 适合规模：数百到数千资产、受监管行业、已有传统数据治理体系的大型组织。

**组合三：Embedded + AI Audit Log + Prompt Library（网关 + trace + 版本化）**

- 组合构成：网关负责在通路上完成入向检测、出向判定与路由，trace 负责证据，Prompt 库负责把「改了什么」绑定到可寻址版本上。
- 职责边界：网关只管流经它的调用，因此它必须与「禁止绕行」的网络与权限约束配套；Prompt 库提供的是变更归因，不是内容安全。
- 运维代价：网关进入关键路径（延迟与可用性成本）、trace 存储随调用量线性增长、Prompt 版本流转增加一次发布动作。
- 适合规模：日调用量以百万计、有对外生成式服务或 Agent 动作的组织。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| AI 资产裸奔 | 抽查发现权重文件在共享盘、Prompt 在聊天记录里 | 资产不可枚举 ⇒ 义务无法分配，出事连「有哪些系统受影响」都答不出 | 治理被当成上线的额外步骤，平台团队没有发布链路的所有权 | 把「登记」做成发布流水线的必经步骤，而不是可选动作 |
| 模型版本混乱 | 同一个模型名对应多个权重文件，生产在用哪个要问人 | 事后无法证明「当时生效的是哪一版」⇒ 证据链在版本这一环断掉 | 版本被当成工程细节，没被当成治理标识 | 以「版本 + 权重哈希」为标识；模型名只做展示 |
| 训练数据来源不清 | 数据集只有路径与时间戳，没有许可证与来源记录 | 无法回答用途与版权的合法性 ⇒ 合规举证从第一步就断 | 数据获取与数据治理由不同角色在不同时间完成 | 数据集进台账时就带来源、许可证、PII 标签三字段 |
| 输出无审计 | 生产调用没有 trace，只有应用侧零散日志 | 输出不可复现 ⇒ 投诉与事故都无法归因 | trace 被视为性能负担而非资产 | 审计字段从「可复现」倒推（§3.2.4），而不是从日志默认字段正推 |
| 合规应付 | 有一份为审计准备的文档，与生产实况对不上 | 举证材料与事实脱节 ⇒ 一旦被追问细节即失效 | 合规被当成交付物而不是持续动作 | 把评估与登记接入流水线，让文档是产物而不是作品 |
| 过度治理 | 所有模型一律按最高密级与最严审批处理 | 边际成本线性增长而风险不降 ⇒ 团队开始绕过流程 | 「宁严勿松」在证据不足时是最省事的选择 | 按用途与主体脆弱性分级，把重治理留给高风险用途 |
| Prompt 不版本化 | 线上输出回归，无法定位是改了 Prompt 还是换了模型 | 变更归因不可做 ⇒ 问题定位从小时级退化为天级 | Prompt 被当成配置而非代码 | Prompt 进版本控制，运行时可寻址到 (prompt_id, version) |
| 无 Owner | 资产表有资产行，责任人写着团队名或空白 | 无人应答 ⇒ 义务无法落到主体，变更无人审批 | 组织变动频繁，团队名比个人名更「稳定」 | Owner 具体到人 + 离职转交机制；团队名只作展示 |
| Embedding 黑盒 | 向量索引无元数据，检索结果无法回指来源文档 | 无法追溯 ⇒ 检索到的内容不可解释，删除请求也无法落实 | 向量库被当成性能组件而不是资产 | 每条向量带来源文档 ID 与文档版本；删除走同一条链 |
| 评估与治理割裂 | 评估报告里只有总量指标（准确率 / 满意度），没有分群与时间切片；上线后要查偏见或漂移，台账里找不到对应的评估记录 | 评估证据没覆盖偏见与漂移 ⇒ 模式 5 的风险等级失去输入，「这个模型在这类主体上公不公平」答不出，模型退化也发现不了 | 评估由算法团队主导、指标取自训练侧；治理由平台团队主导、只收流程与合规项，两边对「什么算合格证据」没有共识 | 评估与台账共用同一个 `asset_id`，评估结果按「总量 + 分群 + 时间切片」三组指标入册；缺分群或时间维度的评估不构成治理证据 |

**最危险的三个，在生产里的典型暴露方式**：

「**AI 资产裸奔**」几乎总是以「同一件事被做了三遍」的形式暴露：某次事故后需要盘一遍受影响系统，三个团队各自交出一份互不相同的清单，事后才发现漏掉了两个业务自己接的调用。它的机制后果不是「找不到」，而是**没人知道总数**——一旦总数未知，覆盖率、风险敞口、义务履行情况全部无法度量，后续所有的治理投入都失去基准线。

「**输出无审计**」的典型暴露方式是「用户投诉但无法复现」：同一个问题问两次结果不同，而系统只留了最终回复。此时团队会开始用「可能是模型随机性」解释一切，因为**没有参数与上下文快照，非确定性系统的一切行为都不可反驳也不可归因**——这不是解释力不足，而是证据结构缺失（§7.3.2）。

「**过度治理**」的暴露方式最隐蔽：流程没有被反对，而是被绕过。当一次字段变更要等两周审批、而批准条件里又有大量与本次变更无关的检查项时，团队会选择**不改名、加个别名、在应用层做转换**——技术上绕过去了，治理台账上却什么都没发生。它把一个可见的变更压力变成了一批不可见的隐性耦合，最终在最不合适的时候一起暴露。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 资产 < 10 → 10–100 | 手工台账 + Model Card | 资产数超过一个人能记住的量，「可发现」从免费变成稀缺 | Asset Registry + 自动采集 | 建 registry、把已有资产回填一遍（回填往往比建库更贵） |
| 资产 100 → 1 万+ | 人工补元数据 | 登记成本随资产数线性增长、收益不增长，字段开始被填成空壳 | 流水线自动填充 + 只保留必填业务字段 | 改造发布流水线，重设必填字段清单（旧字段无法全部保留） |
| 待判定项随资产一起涨（PII 识别 / 资产分类 / 输出判定） | 人工判定 + 规则匹配 | 判定量按「资产数 × 判定项数」增长，规则写不完，人也复核不过来 | 加一层 AI 辅助判定（「AI 治理 AI」）：模型做初判，人只复核它标为高风险的那部分 | 判定器本身要建评估集与准确率基线，否则治理结论不可举证 |
| 日调用量千级 → 百万级 | 事后审计 | 明细量与成本随调用量线性上升、没有规模摊薄，逐条在线查询先成为瓶颈 | 明细与聚合分层存放 + 采样索引 | 存储与查询分层改造；部分历史明细降采样，可追溯性有损 |
| 单一法域 → 多法域 | 风险等级取标量 | 同一资产在不同法域结论不同，单值字段必须改表 | 风险等级改为「法域 → 等级」向量 + 角色字段 | 台账整体重编号；角色字段是行级字段，不能事后补注释 |
| 无 Agent → 有 Agent | 登记制 + 内容护栏 | Agent 的下一步动作在调用前不可枚举，护栏拦的是「话能不能说」不是「动作能不能做」 | 授权制（工具权限最小化 + 额度 + 人在回路） | 新增动作级台账与会话级 trace，台账模型从「实体」变成「事件」 |
| 内部使用 → 对外提供 | 只按密级分类 | 义务按角色分配，对外提供会激活透明度与技术文档义务 | 台账增加「角色 + 用途 + 投放时间」字段 | 重跑义务映射，补技术文档与登记材料 |

**这张表里只有一行是结构断点，其余都是量变**：从「无 Agent」到「有 Agent」不是加字段能解决的——它的治理单元从「一个可枚举的实体」变成「一段会自己决定下一步的运行过程」，台账的主键从 `asset_id` 变成 `(trace_id, step_index)`。判断方法很简单：如果你现在的治理平台只能回答「我们有哪些资产」，而回答不了「这次动作是谁授权做的」，那么它覆盖不到 Agent 场景。

「AI 治理 AI」不是让模型替人做审批决定，而是替人做**初判**：PII 识别、资产分类、输出风险打分这类逐条重复的判定动作交给模型（或规则 + 模型的组合），人只复核它标为高风险的那部分。它之所以在这一档才出现，是因为它和嵌入式治理面对的是同一个前提——待判定的东西多到人力与规则都覆盖不了。它的代价是给治理体系引入了一个自己也需要被治理的模型：判定器的漏判率没有评估集做基线时，治理结论会从「有据可查」退回「凭感觉放行」，而漏判恰恰发生在最需要覆盖的那部分长尾上。判断方法：拿一批已知答案的样本喂给判定器，看漏掉的是哪一类（【经验】——评估集要按自己业务的分布去做，公开产品只给通用能力）。

### 3.7 自检清单

- [ ] 资产表里是否有「角色」列（提供者 / 部署者）？没有就无法回答义务由谁承担（§7.3.3）。
- [ ] 模型的标识是「模型名」还是「版本 + 权重哈希」？只有名字，事后无法证明当时生效的是哪一版。
- [ ] 每一次模型 / Prompt / 数据集的发布，是否强制留有一个 `assessment_id` 指向那次风险评估？
- [ ] Prompt 在运行时是否以 `(prompt_id, version)` 寻址？只存在于文档或聊天记录里的，视为未版本化。
- [ ] 审计 trace 里是否同时有采样参数与检索到的文档 ID？少任一项，非确定性输出不可复现。
- [ ] 变更进入发布流程时，是否自动跑一次影响面并作为放行条件（而不是事后告警）？
- [ ] 是否存在「全部资产按同一密级与同一审批」的情况？存在即违反分级本身。
- [ ] 向量索引的每条记录是否带来源文档 ID 与文档版本？
- [ ] 评估系统与治理台账是否共用同一个 `asset_id`？不共用就答不出「上线时评估过什么」。
- [ ] 做一次绕行测试：绕过统一入口直连模型端点，是否被拦？拦不住说明覆盖率是流程保证。
- [ ] 每季度是否有一次「未登记资产」的主动发现？（只靠业务来登记，覆盖率必然下降）
- [ ] 高风险判定是由「用途」驱动的，还是由「技术类型」驱动的？（后者会把小模型也判成低风险）

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 资产 < 10、单团队、内部使用 | Model Card + Prompt Library | 资产少到能人工盘完，建平台的成本高于收益 |
| 资产跨团队、需一次查清影响面 | + Asset Registry + Audit Log | 统一 ID 与关系表让跨类影响面变成一次图遍历 |
| 受监管、需向监管举证 | + Risk Assessment（按用途定级） | 义务按角色与用途分配，等级决定义务清单 |
| 已有传统数据治理体系 | + Hybrid（桥表缝合） | 桥表让数据侧与模型侧共用一条排查链 |
| 多法域 / 多事业部 | + Federated | 契约统一才能既本地执行又全局举证 |
| 日调用量大、有 Agent 动作 | + Embedded（网关 + 授权制） | 单元在运行期产生，只有事中门禁能阻断，授权制兜住不可逆后果 |

> 本节小结：本主题下决定模式选择的**唯一那条约束**是——**治理单元在什么时刻产生**（可枚举的实体，还是运行时才产生的动作）。它一旦确定，登记制还是拦截制、台账以实体为行还是以事件为行、控制点放在发布流程还是数据通路，其余结论基本被推导出来；公司规模、行业标签、技术先进性都只是这条约束的近似替代品，用它们挑模式，早晚会在规模跃迁时重选一次。
>
> 💡 **思考锚点**：用 §3.6 那句判定测一下你自己的平台——它只能回答「我们有哪些资产」，还是能回答「这次动作是谁授权做的」？若只能答前者，按 §3.6 你的治理单元还停在「可枚举的实体」，而 Agent 场景的主键已经是 `(trace_id, step_index)`。再对 §3.5「过度治理」自查：你们有没有流程不是被反对、而是被绕过（改名 / 加别名 / 应用层转换）？
