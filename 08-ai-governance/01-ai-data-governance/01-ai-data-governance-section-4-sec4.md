## 4. 工程实现

本节回答一个问题：**把 §3 选定的治理模式装起来时，先动哪一步、后动哪一步，每一步的验收判据是什么，已有资产怎么处理。** 组织方式按「落地步骤（4.1）→ 做晚了无法回填的工程点（4.2）→ 工具链按能力分层（4.3）→ 存量迁移（4.4）→ 可直接套用的模板（4.5）→ 自检清单（4.6）→ 小结（4.7）」展开。

**面向两类读者，读法不同**：已经跑着模型、有存量调用与历史资产的团队，从 §4.4 存量迁移读起，再回到 §4.1 确认顺序里的两处不可动点；还没有生产调用、准备从零搭的团队，从 §4.1 顺读，把 §4.2 的五项当作「必须在装平台之前定下来」的前置条件。文中工期量级一律为【经验】判断，实际取决于团队是否已有训练 / 发布流水线；法规条款属【公开】，条款号与义务内容请以官方文本当前版本为准。

### 4.1 落地步骤：8 步的顺序、产物与判据

每一步给三件事：**产物**（这一步结束时手上应多出来的、可被检查的东西）、**判据**（可执行动作，不是「评审通过」）、**为什么必须在这一步 / 为什么在这个位置**。

**Step 1：AI 资产盘点（【经验】首次 2–4 周，之后按季度增量；随资产数与新应用上线速度变）**

1. 先定「什么算一条资产」：模型 / Prompt / 数据集 / 向量索引 / 输出通道五类各自的最小可识别单元（一次训练产出的 checkpoint、一个编号化的 Prompt、一份带版本的数据集），并写清哪几类不进清单（实验脚本、临时索引）。
2. 每条资产记四列：来源系统、Owner、最近一次变更时间、当前调用方——这四列是后面分级、归因与挂账的输入。
3. 扫存量：从发布记录、模型仓库、Prompt 库、向量索引元数据四个来源各导一次，合并去重得到首次清单，并在这一步定下 `asset_id` 的分配规则（见 4.2 第 1 点）——后面每一步都引用它。
4. 定增量入口：新资产由谁在发布流程的哪个卡点登记，写进发布检查项；不登记不允许发布。

- **产物**：资产清单，一行为一个资产，带来源系统与最近一次变更时间。
- **判据**：**抽 3 个已知在跑的应用，能否从清单里反查出它们各自的模型版本与数据集版本**；查不到的那一项就是清单的缺口。
- **为什么必须第一步、且为什么在采购之前**：没有清单就无法分级，也就判断不出哪些资产需要采血缘。常见偷跑是「先买平台、再补资产」——平台能替你存，不能替你定义资产边界与连接键；平台上线后补录的历史资产，其历史血缘通常已经无法回填。

**Step 2：分类分级（【经验】首次 1–2 周）**

1. 先给 ⟨T, C, I, R, X⟩（定义见主文件 §2.1）五维各定一份取值域，枚举值写死在配置文件里，不允许各团队自造词——它是后面所有筛选与审批路径的依据。
2. 逐条填五元组：`C` / `I` 看内容本身，`R`（风险等级）由用途、自治程度、部署规模、主体脆弱性四个变量推导（见 4.2 第 4 点），推导依据写成一句话留在记录里。
3. 把分级规则落成一张判定表或规则引擎：新资产按输入自动落档，只有边界案例才进评审会。
4. 挂 Owner：每条资产的分级结果有一个可追问到人，而不是挂在评审会名下。

- **产物**：每条资产的五元组 + 一份「按密级筛选」的可用查询。
- **判据**：**按 `C = Secret` 筛一次，看筛出来的清单是不是符合你的直觉**；如果筛出来的是全部资产，说明分级没有真的发生。
- **为什么必须在盘点之后**：分级规则的输入是「这条资产是什么、给谁用」，盘点缺席时只能按团队名分级，而团队名与风险无关。

**Step 3：血缘采集（【经验】3–6 周，与训练 / 发布流水线耦合）**

1. 先定六个环节的连接键：训练数据、Checkpoint、部署、Prompt、输出、反馈各自用哪个字段与资产台账对齐（对齐到 Step 1 定的 `asset_id`）。
2. 在流水线的六个写入点各加一次上报：训练任务结束写 `dataset_hash`，发布任务写 `model_version` 与 `weights_hash`，统一入口写 `prompt_version`、`policy_version` 与输出指针——六处都写，链路才连得起来。
3. 补历史：对仍在迭代、有下游依赖的资产，从发布记录与流水线日志回填最近一到两个版本的边，更早的按 4.4 的挂账规则处理。
4. 定血缘的读法：给出「从任意一个输出节点反向走到它的数据集版本」的那一个查询，并把它固化成这一步的验收脚本。

- **产物**：端到端血缘图，可从任意一个输出节点反向走到它的数据集版本。
- **判据**：**挑一次两周前的线上输出，只靠血缘回答「它用的是哪个数据集版本、哪个 Prompt 版本」**；需要人工拼表就说明连接键还不存在。
- **为什么必须在分级之后**：不采全部血缘是刻意的取舍——采哪些资产的血缘，取决于它是不是高风险、是不是对外提供，这个判断来自 Step 2。

**Step 4：审计日志（【经验】1–3 周）**

1. 按 4.2 第 3 点的字段表把 DDL 一次写全（含 `policy_version` 与命中原因），不按「先上线、再逐步加列」的方式迭代。
2. 建追加写的调用明细表：不更新、不删除；留存策略（采样、分层、TTL）与建表语句写在一起（见 4.2 第 5 点）。
3. 写入点放在统一入口或模型调用封装层，与真实调用走同一条路径，不依赖业务代码自觉上报。
4. 建两个最小导出并固化成脚本：按 `asset_id` + 时间窗导出（审计响应用），按 `subject_id` 导出（主体告知与权利请求用）。

- **产物**：可按 `asset_id` 与时间窗导出的调用明细。
- **判据**：**不接触线上环境，只用留存字段重建出上周某一次输出**；重建不出来，缺的那个字段就是清单上的下一条。
- **为什么必须在字段冻结之后才开始**：日志表一旦上线并积了数据，再加列的收益立刻递减（历史行永远是空值），所以字段必须先定后建。

**Step 5：合规映射（【经验】每个法域 0.5–2 人月；随适用框架数与角色数变）**

1. 先列适用清单：按部署地法域与承担的角色（提供者 / 部署者，见 §7.3.3）筛出真正落到本组织头上的义务，不照抄整部法规。
2. 逐条填三列：法规条款（带条款号）↔ 控制点（拦在哪一层）↔ 证据（由哪个系统的哪个字段产生），模板见 4.5 样例 3。
3. 反向核对一遍：对每条义务问「它要的证据在 trace 里有没有字段能产出来」，产不出来的记成 Step 4 的字段待补项。
4. 定触发重核的条件与 Owner：法规版本更新、组织角色变化、用途变化三项各触发一次重核，不靠年度评审兜底。

- **产物**：映射表（模板见 4.5 样例 3）。
- **判据**：**反向逼出字段**——随便挑一条义务，问「它要的证据在 trace 里有没有字段能产出来」；产不出来的，就是 Step 4 的字段清单还没冻结。
- **为什么必须排在 Step 4 的字段冻结之前（本节最容易被做反的一步）**：合规映射看起来像「最后写文档」，实际它决定**审计日志必须留哪些字段、留多久**。法规的字段要求是硬约束——EU AI Act 对高风险系统的运行期义务包含自动记录事件日志（Art. 12）与人工监督（Art. 14）（【公开】EU AI Act, 2024），NIST AI RMF 1.0 的 MEASURE / MANAGE 两项功能同样指向运行期（【公开】NIST AI 100-1, 2023）。把映射放在日志表建好之后做，结果通常只有两种：尝试回填（做不到），或在日志表上不断加列（把 schema 变成垃圾场）。

**Step 6：风险评估（【经验】单系统 3–10 人日）**

1. 定触发表：用途变更、自治度提升、部署规模跨档、主体脆弱性变化四项各触发一次重新评估，把它写成发布流程的卡点，而不是年度动作。
2. 按用途定级：沿用 ⟨T, C, I, R, X⟩ 与 4.2 第 4 点的四个变量，不另立一套口径，避免评估等级与台账等级对不上。
3. 评估报告写四件：缓解措施、残留风险、Owner 签字、有效期；`assessment_id` 回写发布记录，形成「评估 ↔ 发布」双向引用。
4. 定复核节奏：高风险用途按固定周期复核，其余在触发表命中时复核；复核结论与上一次的差异要写出来。

- **产物**：评估报告 + 发布记录里的评估引用。
- **判据**：**抽一个正在生产的系统，看它的发布记录里能不能指到一份「为它而做」的评估**；指不到，说明评估还是准入时的一次性动作。
- **为什么排在 Step 5 之后**：评估结论要落到具体义务上，义务清单来自映射表；映射没做，评估只能给一个没有后续动作的等级。

**Step 7：持续监控（【经验】取决于存量观测栈，有现成栈时以周计）**

1. 三类信号各定一个指标与阈值：数据与输出漂移、公平性、越界（绕行与越权动作）；指标只读 Step 4 的明细，不另建一套采集。
2. 每个告警配一个系统能自己执行的动作：降级 / 切回旧版本 / 转人工复核；只发通知不触发动作的，按「未接入」计，不计入覆盖率。
3. 每条告警落到人：对照表最终是「信号 → 动作 → 人」三列，含值班、升级路径与响应时限。
4. 每季度演练一次：人为造一次漂移或一次越界动作，看动作有没有真的发生——这一步的验收方式就是演练，不是看告警配置。

- **产物**：告警 → 动作的对照表，以及每条告警的落到人。
- **判据**：**人为造一次漂移，看是否触发了一个具体动作**；只发通知不触发动作的监控，等价于没有监控。
- **为什么必须排在 Step 4 之后**：监控要读运行期明细，而明细的字段集合是 Step 4 定的；顺序反了会得到一套只能统计「调用量」而不能归因的监控。

**Step 8：合规报告与审计响应（持续）**

1. 先做自助举证接口：按 `asset_id` 与时间窗导出记录——它在 Step 4 落地后就能启动，不必等 Step 5 / 6 全量完成。
2. 报告模板的每一格绑定一个数据源字段：绑不到字段的格子先删掉或标成待补项，不留「人工填」的格子。
3. 定渲染节奏与版本：季度内部报告、年度合规报告各带版本号，历史版本留存，便于事后回答「当时报的是什么」。
4. 做一次内部演练：让一个不参与治理的人按报告里的结论去台账核对一条记录，核对不上的那一条就是报告的手工残留。

- **产物**：自动渲染的报告 + 一个按 `asset_id` 与时间窗导出的接口。
- **判据**：**让一个不参与治理的人按报告里的结论去台账里核对一条记录**；对不上说明报告是手工作品。
- **为什么必须最后、但可以提前启动一部分**：「自助举证接口」在 Step 4 落地后就可以开始做，不必等 5 / 6 全量完成——审计响应的第一版只需要能按 `asset_id` 与时间窗导出记录。

**顺序里只有两处不能动，其余可以并行。** 第一处是 **1 → 2 → 3**（清单 → 分级 → 血缘）。第二处是 **5 必须排在 4 的字段冻结之前**。可并行的部分：6（风险评估）与 7（持续监控）之间没有硬依赖，8 的自助举证接口可以早期启动。

**八步的前置条件与其缺失症状**（用来判断自己真实处在哪一步，而不是按进度表宣布的步数）：

| # | 步骤 | 前置条件 | 前置不满足时的症状 |
| :---: | --- | --- | --- |
| 1 | AI 资产盘点 | — | 分级只能按团队名做，与风险无关 |
| 2 | 分类分级 | 有资产清单 | 所有资产落进同一档，审批疲劳 |
| 3 | 血缘采集 | 资产有稳定 ID | 血缘图连不上输出节点，影响面永远不全 |
| 4 | 审计日志 | 统一 ID 与 trace 字段已冻结 | 日志表反复加列，历史行为空值 |
| 5 | 合规映射 | 有分级 + 有控制点清单 | 义务落不到具体控制点，评估结论无后续动作 |
| 6 | 风险评估 | 有分级 + 有合规映射 | 评估变成一次性准入动作，之后不再复核 |
| 7 | 持续监控 | 有审计日志 + 指标定义 | 监控只能统计调用量，不能归因 |
| 8 | 合规报告与审计响应 | 前 7 步可用 | 报告与生产实况对不上，被追问细节即失效 |

**最常被跳过的是 Step 5（合规映射）**，因为它看起来像文档工作。跳过的第一个症状不会出现在合规检查时，而会出现在**第一次真实审计**：需要举证「当时按哪一版策略判的、人工监督记录在哪」，而日志表里既没有 `policy_version` 也没有人工确认字段。此时唯一的补救是回填，而回填做不到。

**判断进度不要看「平台上线了几个模块」，看这三件东西有没有出现**：一张带 Owner 的资产清单（Step 1–2）、一次不改线上路径就能导出的调用明细（Step 4）、一份写清了字段名的义务映射表（Step 5）。三件里缺任何一件，后面几步都会以「先做一个能演示的东西」的形式返工——**因为平台能演示的功能与治理成立的判据不是同一件事**。

### 4.2 关键技术点：做晚了无法回填的五项

这五项的共同点是**做晚了无法回填**，因此它们排在「装平台」之前。每项给做法、机制与失效条件。

**1. 统一连接键（asset_id）**

- **做法**：模型 / Prompt / 数据集 / 索引 / 输出通道共用同一套实体 ID 与一张关系表（§3.2.3 的 AI Asset Registry 模式），`asset_id` 全局唯一、跨类型不重号。
- **机制**：因为治理的多数查询都是「换了个版本，影响了谁」这类跨类问题，所以**只有在所有类型共用同一套 ID 时，跨类影响面才能一次图遍历答完**；ID 不统一时，这个问题必然退化为跨系统人工拼表。代价是统一表结构会迫使类型特有属性退到 `payload` 里，字段不可索引、不可校验。
- **失效条件**：**当资产进入万级、且每天新增以百计时**，登记的边际成本随资产数线性增长而治理收益不增长，团队开始填空壳字段、关系表大面积缺边；此时**影响面查询会漏掉下游却不报错**。症状：影响面查询的返回条数长期不随资产增长而变化。
- **判据**：一次查询答完。如果需要跨三个系统人工拼表，说明连接键不存在，而不是「查询工具不好用」。
- **采购侧的自检方法**：看产品文档里的一等公民是「资产」还是「trace / span」——一等公民的定义方式暴露了它假设的治理单元（§7.3.1 展开）。
- **档位**：【经验】连接键这一项几乎总是自建——它是组织口径，不是行业标准，买来的是别人的口径。

**2. 版本化寻址，而不是把版本号写在文档里**

- **做法**：主文件 §2.2 把模型定义为 `Model = ⟨framework, arch, weights_hash, training_recipe, dataset_hash⟩`，把输出定义为带完整 provenance 的 `Model(Prompt, Context, Tools)`。工程上的落地只有一条：**运行时能被寻址的才叫版本**。
- **机制**：因为非确定性输出的复现依赖「权重 + 提示词 + 上下文」三者同时可寻址，所以版本必须作为**运行时参数**存在（`prompt_id` 与 `version` 是主键、`dataset_hash` 写进 trace），而不是作为发布邮件里的一句话。代价是每次改动多走一次「新版本 + 状态流转」的动作。
- **失效条件**：**当 Prompt 只存在于 Wiki、聊天记录或代码字符串里时**，「改了 Prompt 导致的回归」与「换了模型导致的回归」无法区分；症状是定位时间从小时级退化为天级，且团队最终用「模型有随机性」解释一切。同理，数据集与索引的 `dataset_hash`、索引快照 ID 若只写在发布邮件里，事后无法证明当时生效的是哪一版。
- **档位**：字段集合来自主文件 §2.2（形式化定义）；「运行时寻址」属【经验】判断。

**3. trace 字段最小集（从可复现性倒推，而不是从「能存就存」正推）**

- **做法**：主文件 §1.6 把「可重现性」记为传统数据的 ×5 难度——trace 是唯一补偿手段。最小集如下：

| 字段组 | 字段 | 缺了会怎样 |
| --- | --- | --- |
| 主体 | `subject_id`（谁）/ `channel`（哪个入口） | 答不出「这次是谁触发的」 |
| 模型 | `model_id` / `model_version` / `weights_hash` | 换了 checkpoint 之后旧输出无法回放 |
| Prompt | `prompt_id` / `prompt_version` | 提示词改过以后，旧输出无法解释 |
| 采样 | `temperature` / `top_p` / `seed`（若支持） | 同样的输入复现不出同样的输出 |
| 检索（RAG） | `retrieved_doc_ids` + 每个文档的版本 | 答不出「这个结论引的是哪一版文档」 |
| 工具（Agent） | `tool_call_trace`（含入参与返回值摘要） | 不可逆动作无法追责 |
| 输出 | 输出内容或其存储指针 | 无法举证 |
| 判定 | `policy_version` + 命中原因（放行 / 拦截） | 答不出「当时按哪一版策略判的」 |

- **机制**：因为输出不是输入的确定函数，所以**「留了日志」与「能举证」之间差着一整层**——字段清单必须从「可复现」倒推，而不是从「日志系统默认有什么」正推。
- **失效条件**：**当模型带 RAG 或工具调用时**，上下文本身成为运行时变量，任何一项缺失都会让重放失败；症状是出了争议只能「重放一次看看」，而结果不稳定。
- **档位**：字段清单本身是【经验】取舍（从「可复现」倒推，随 RAG / 工具调用等能力增删）；本条的保留期数字中，两个法律下限属【公开】（见下条），强监管行业的年限属【经验】。
- **成本与保留期**：要压的是**留存策略而不是字段**——trace 存储成本按容量随时间累积，压它靠采样、分层与 TTL，删字段等于自断举证链（§7.4 给了这一项的量纲对比）。保留期限取各法域要求的**最大值**并写进保留策略：中国《网络安全法》第二十一条要求按规定留存相关网络日志**不少于六个月**（【公开】《网络安全法》, 2016），EU AI Act 对高风险系统另要求运行期自动日志（【公开】EU AI Act, 2024）。【经验】金融、医疗等强监管行业，机构内部审计通常要求数年，具体年限依业务与机构而定，不能按「六个月」这一个数拍。

**4. 定级源是「用途」，不是「技术类型」**

- **做法**：主文件 §2.1 给的是 `Risk = f(use_case, autonomy, scale_of_deployment, vulnerability_of_subject)`；工程后果是**分级规则引擎的输入必须包含用途、自治程度、部署规模与主体脆弱性**四项。
- **机制**：因为义务按角色与用途分配，所以同一个模型换一个用途就换一套义务；把技术类型当输入，会把一个参数很小的招聘筛选模型判成低风险，同时把一个很大的垃圾邮件过滤器判成高风险，两个方向的误判都会发生。
- **失效条件**：**当分级被做成一次性准入动作时**，「事前判定义务」反转成「一份过期的合规背书」——用途、自治度、部署规模的变化通常不触发任何流程。症状：台账上仍写着原来的等级，而系统已经被用于新场景。
- **判据**：抽一个已上线的系统，看它最近一次用途变更是否触发过一次重新定级；再问「同一个模型如果改成对外提供 API，义务清单会多出哪几项」，答不出来说明分级的输入里没有角色与用途。
- **档位**：EU AI Act 的高风险清单本身就是按用途列举的（招聘、信贷评分、关键基础设施、教育评估、执法辅助、生物识别分类、移民 / 边境等）（【公开】EU AI Act, 2024）。

**5. 留存与采样的分层**

- **做法**：明细走追加写的日志型存储 + 采样索引 + TTL，聚合走关系库长期保留；**判定为拦截 / 高危的记录走无条件全量留存**，采样只作用于放行流量的明细。
- **机制**：因为治理单元越细、台账行数越多，「一次调用 = 一行」会把台账从「万级实体」推向「亿级事件」——这不是同一个数据模型的量变，而是存储与索引形态的质变。
- **失效条件**：**当治理单元进入「每天百万次以上」量级时**，逐条明细的**在线查询**（而不是聚合报表）会先成为瓶颈（【经验】）。症状：审计时按 `subject_id` 查一次历史调用需要等分钟级，团队因此改用「抽样查最近一周」——此时证据链已经在事实上断裂。
- **判据**：把「一次审计要回答的全部问题」列成清单，逐个记录实测查询耗时；**只要有一个问题必须靠离线任务跑数小时，就说明分层方案与审计的读取形态不匹配**（审计是逐条重放，明细与聚合分层正是为它设的）。
- **档位**：【经验】上述量级分界与分层做法随调用量与保留期变化，请按本组织实测的查询延迟定，不要照抄阈值。

### 4.3 工具链与平台：按能力分三层，而不是按品类罗列

按品类列六类工具（模型治理 / 血缘 / Prompt / 审计 / 合规 / 安全）容易让人以为「买齐六类就治理好了」。更有用的切法是按能力分三层——**存得住（记录）→ 拦得住（控制）→ 说得清（举证）**。三层必须配平，某一层单独超前不会带来覆盖率提升。

| 层 | 能力 | 可核验的工具形态 | 自建 / 采购的判据 | 不选它的代价 |
| --- | --- | --- | --- | --- |
| 记录层 | 模型与实验版本、数据版本、trace 存储、元数据与血缘目录 | MLflow / Weights & Biases（模型与实验）；DVC / LakeFS（数据版本）；Langfuse / Arize Phoenix / Helicone（trace）；OpenTelemetry 的 GenAI 语义约定（字段标准）；DataHub / Apache Atlas（元数据与血缘） | 与资产命名耦合的部分（连接键、分级规则）自建；通用记录能力采购或开源 | trace 字段缺失无法回填：历史输出永久不可复现 |
| 控制层 | 统一入口与策略、输入输出校验、授权与人工介入 | Portkey / Cloudflare AI Gateway（统一入口与策略）；Guardrails AI / LLM Guard / Lakera Guard / Azure AI Content Safety（输入输出校验） | 与自有审批流耦合的放行卡点自建；内容护栏优先采购 / 开源 | 覆盖率退回流程保证：绕行直连拦不住，例外名单长期不回收 |
| 举证层 | 合规映射、风险评估、审计报告、可解释性 | NIST AI RMF Playbook / Crosswalk、ALTAI 自查清单、ISO/IEC 42001:2023 管理体系认证；商业侧 OneTrust / Collibra / TrustArc；XAI 侧 SHAP / LIME / Captum | 与本组织法域与角色划分耦合的映射表自建 | 每次审计人工拼装：举证材料与生产实况对不上，被追问细节即失效 |

（工具形态均可在各自官方文档核验，属【公开】产品资料；「哪一层该自建」属【经验】判断。）

**记录层的自建边界要划在「命名」上，而不是「存储」上。** 判定方法是问三个问题：这个字段是行业标准还是本组织口径（连接键、分级规则、法域 → 等级向量都是后者，必须自建）；这个能力换掉时历史数据能不能迁移（能迁的优先采购）；这个东西出故障时，是发布停摆还是查询变慢（发布停摆的那一项要留退路，或者接受它作为单点）。反过来，把存储层也自建，通常只会得到一套维护成本更高、字段标准仍与社区不一致的记录层。

**第 7 步的监控工具单独说一句**：漂移与公平性监控（Evidently、Arize、WhyLabs、Fairlearn、AIF360）产出的指标属于记录层，但它的告警必须接到控制层才有意义——「检测到漂移」却不触发任何动作（降级、切回旧版本、转人工复核）的监控，等价于没有监控。

**控制层是覆盖率的唯一来源。** 因为**一个控制点只能阻断流经它的东西**（§7.3.4），所以「覆盖率 100%」这句话只有在**调用收口到统一入口**时才有技术含义；否则它表达的是流程约束，会随组织变化衰减。OWASP 把 Prompt Injection 列为 LLM 应用风险清单的第一类（【公开】OWASP Top 10 for LLM Applications, 2023/2025），而内容过滤无法根治提示注入——注入的结果是「指令被服从」，属于动作层问题，只能靠入口处的策略与授权制解决（Agent 场景见 §3.2 的 Embedded 模式）。

**控制层还必须显式选择故障方向**：内容判定类门禁通常选 fail-open（误拦等于业务中断）并事后追责，授权判定类必须 fail-close（误放等于一次越权动作）。**失效条件**：这个选择不写下来时，它会在第一次网关故障时由值班同学临场决定；症状是同一类故障在不同值班班次上表现为相反的行为（一次全放、一次全拦），而事后无法说明哪种是有意为之（§3.2.8 已把这条记为 Embedded 模式的固有代价）。

**这一类里最容易被误选的是控制层**，因为它最容易演示：一次拦截就能证明「我们有治理」。但若调用尚未收口到统一入口，控制层的覆盖率是虚高的——**判据是做一次绕行测试（直连模型端点看是否被拦），而不是看拦截日志的条数**；先买网关、后做收口，等于把最贵的一层架在覆盖率最不可靠的位置上。

### 4.4 存量迁移：在已有资产与已有数据治理体系上怎么上

**① 先做能立刻见效且可回退的一步：冻结两个「命名层」的东西，而不是改通路。** 具体是 `asset_id` 的分配规则与 trace 字段最小集。它们可回退（新增 ID 与字段，不改任何线上读写路径），且立刻产生两个可见收益：跨类影响面查询有键可用、审计导出脚本可以开始写。**不要以「先买平台」起步**——平台上线后补录的历史资产，其历史血缘与历史调用字段通常已经无法回填。

**② 历史资产按三类处理，不要一套规则套全部：**

| 类别 | 判据 | 处理方式 |
| --- | --- | --- |
| 仍在迭代、有下游依赖的模型 / Prompt / 数据集 | 近一两个季度有发布、或被多个应用引用 | **只改「被改动的部分」**：本次发布涉及的版本补 `asset_id`、补版本寻址与评估引用，其余挂账 |
| 冻结但仍被调用的资产 | 无新版本发布、但 trace 里仍有调用 | **打标挂账**：标为「冻结」，写清 Owner、保留期与调用方，不进重治理范围 |
| 无主且无调用的资产 | 无 Owner、trace 里长期无调用、无下游引用 | **不返工**：走归档或下线流程，不进入治理范围 |

**判据**：三类清单能否在一天内产出。产不出来，说明 `asset_id` 或 `trace` 采集还不存在（回到 4.2 第 1、3 点），此时任何「迁移计划」都只是清单的重新排版。

**③ 双轨怎么维持、维持多久。** 迁移期的双轨有两处：模型侧是「**旧端点直连 + 新统一入口**」并存；数据侧是「**传统数据目录 + AI 资产台账**」并存，两者靠桥表缝合而不是复制元数据（§3.2.7 的 Hybrid 模式）。维持时长不按时间定，按**迁移率**定（【经验】：当经统一入口的调用占比进入多数区间、且新增应用默认走入口时，旧路径的维护成本才开始低于迁移成本）。双轨期有两条硬要求：**旧路径的调用必须可被观测**（否则退出双轨时无从判断谁还在用），以及**每条新上线的路径都必须带退役计划**（含截止时间，写进验收项）。

**已有传统数据治理体系的组织，接合点是桥表，不是重建一套平行目录**——因为同一次事故要在两条互不相通的流程里各查一遍，是平行体系最贵的代价。桥表落地时有一项不能事后补：**`role`（提供者 / 部署者）这类义务归属字段是行级字段，不是可以事后补的注释**（§7.3.3），所以台账建表时就要带上，哪怕暂时全部填同一个值。

**「谁还在用旧路径」必须由系统回答，而不是由群里的沉默回答。** 三个可操作的观测点：① 每一个模型端点都要有独立的调用计数（按调用方 `app_id` 分组），而不是只统计总调用量；② 旧目录的访问日志按月导出，与 AI 台账的 `asset_id` 做一次对账；③ 例外名单（被允许绕过统一入口的调用方）要有到期时间，到期未续期即自动回收。**判据**：问「现在有多少个调用方在绕过统一入口」，能给出一个数和一张清单；给不出，说明双轨的退出时点无法被论证，只能靠宣布。

**④ 什么信号说明可以退出双轨：**

- **绕行测试通过**：直连模型端点的调用被拦，或返回一个被明确标记为「非受管」的结果；通往明细与日志的直连权限已按用途收紧。
- **旧路径产出归零**：连续一个完整业务周期（含月末、季末这类峰值）没有从旧入口产生的受管调用。
- **举证可自助**：只凭留存字段，不接触线上环境，能重建一次历史输出；审计响应不再需要人工拼装（对应 4.1 Step 8 的判据）。

**退不出双轨的典型形态是「新路径上线、旧路径仍在产出同一个东西」**：网关建好了但直连权限还在，Prompt 库建好了但代码里的字符串还在用。它的危险不是乱，而是**让新增能力无法真正生效**——只要旧路径还在产出，新平台就不是唯一权威。**因此退役不是收尾工作，它是每一次上新的验收项之一。**

### 4.5 模板 / 示例

这三个样例的作用是**让字段级争议提前暴露**：评审一张 Model Card，比争论「要不要做治理」快得多。

**样例 1：Model Card（YAML，字段集合对齐主文件 §2.2 与 §3）**

```yaml
model:
  name: customer-support-llm
  version: 1.2.0
  base_model: qwen2.5-7b-instruct
  artifact:
    type: lora-adapter
    weights_hash: "sha256:..."
training_data:
  - source: internal-customer-service-logs
    version_hash: "sha256:..."
    license: internal-proprietary
    pii_tags: [order_id, phone_tail]
intended_use: "产品 FAQ / 订单状态 / 退换政策的客服问答（聊天与邮件渠道）"
out_of_scope: [legal-advice, medical-advice, real-time-pricing]
risk:
  level: limited
  basis: "use_case = 通用客服问答；不产生对个人权利的决定"
metrics:
  hallucination_rate: 0.0X
  latency_p99_ms: NNN
owner: data-team@company.com
reviewers: [legal@company.com, security@company.com]
review:
  approved_at: 2025-09-15
  next_review_at: 2026-03-15
```

**怎么用**：关键不是模板长什么样，而是**哪几个字段必须由流水线自动填充**——`artifact.weights_hash`、`training_data.*.version_hash`、`metrics.*` 三项一旦靠手写，卡片会先于模型过期；人工只补 `intended_use` / `out_of_scope` / `risk.basis` 三项（【经验】——判断方法是看仓库里卡片的生成方式：手写 Markdown 的会过期，由流水线渲染的不会）。示例中的 `weights_hash` / `version_hash`（`sha256:...`）与 `metrics` 两项（`0.0X` / `NNN`）都是占位符，仅示意字段位置与类型，**不是可引用的实测指标，也不是行业基准**；实际值由评估流水线按本组织的评测集写入。字段来源是 Model Cards for Model Reporting，数据集侧对应 Datasheets for Datasets（【公开】Mitchell et al., FAT\* 2019；【公开】Gebru et al., 2018）。

**样例 2：一次调用的 trace（JSON，字段取自 4.2 第 3 点）**

```json
{"ts":"2025-09-15T10:22:31Z","subject_id":"u_8812","channel":"chat",
 "model_id":"customer-support-llm","model_version":"1.2.0","weights_hash":"sha256:...",
 "prompt_id":"cs-system","prompt_version":"17",
 "sampling":{"temperature":0.2,"top_p":0.9},
 "retrieved_doc_ids":["faq-v3#412","policy-2025-06#88"],
 "tools":[],"output_ref":"s3://ai-trace/2025/09/15/u_8812-1022.json",
 "policy_version":"guardrail-v3","decision":"allow","hit_reason":null}
```

**怎么用**：把这一条 JSON 当作**留存字段的验收样本**——每新增一类调用（多模态、Agent、工具调用），先问「这条样本上要加哪几个字段」，再改 schema；`output_ref` 用指针而不是正文，正文的留存与访问控制另算。不要照抄 `subject_id` 的写法，若你的系统里主体标识是手机号或邮箱，这里必须换成化名引用。

**样例 3：合规映射表（法规条款 ↔ 控制点 ↔ 证据）**

| 义务（条款） | 控制点 | 证据（由谁产生） |
| --- | --- | --- |
| 高风险系统运行期日志（EU AI Act Art. 12） | 网关统一记录全字段 trace | trace 存储（样例 2） |
| 人为监督（EU AI Act Art. 14） | 高风险用途调用强制人工确认 | 确认记录 + 授权制日志 |
| 高风险系统投放前登记（EU AI Act Art. 49 + Annex VIII） | 发布流程的强制卡点 | 发布记录中的 `registration_id` |
| 生成合成内容标识（《人工智能生成合成内容标识办法》, 2025） | 输出侧标识注入 | 输出留档中的标识字段 |
| 自动化决策的告知与 DPIA（GDPR Art. 22 / Art. 35） | 用途登记 + 影响评估 | 风险评估报告（Step 6） |

**怎么用**：**这张表的作用是反向逼出字段**——如果某个控制点对应的证据在 trace 里没有字段能产出来，这张表就是空的。填表时只写「证据由哪个系统的哪个字段产生」，写不出字段名的那一行就是待补项；法规条款可按官方文本核验（【公开】），而「哪一条配哪个控制点」是本组织的映射决策，不属公开事实。

### 4.6 自检清单

这 12 条的来源是五类反复出现的工程失效——它们不是「想到了就问」，而是每一次都能在真实项目里被指认出来：

| 失效 | 现象 | 后果与对策 |
| --- | --- | --- |
| 覆盖率靠业务自觉登记 | 上线时统一登记，半年后新增资产没人登记 | 覆盖率单调下降；对策是做**绕行测试**：直连模型端点，看是否被拦（对应 4.3 与下面第 9 条） |
| trace 缺采样参数或检索文档 ID | 出了争议只能「重放一次看看」，结果不稳定 | 非确定性输出不可复现，举证链断裂；对策是按 4.2 的字段表逐项核对（第 6 条） |
| 用技术类型定风险等级 | 小参数的招聘筛选模型被判低风险 | 义务清单整体错配；对策是把定级输入改为用途 / 自治度 / 部署规模 / 主体脆弱性（第 11 条） |
| 映射表做在日志 schema 冻结之后 | 结论是需要回填历史字段 | 历史不可回填，只能不断加列；对策是 5 先于 4（第 10 条） |
| 全部资产同一密级、同一审批 | 审批疲劳，真正高密的资产被淹没 | 分级失效；对策是按 ⟨T, C, I, R, X⟩ 分出至少三档，高密档单独设审批（第 2、7 条） |

下面 12 条按「清单 → 分级 → 连接键 → 证据 → 控制 → 映射 → 存量」排列，与 4.1 的顺序和 4.2 的失效条件一一对应。

- [ ] 抽 3 个在跑的应用，能否从资产清单反查出模型版本与数据集版本？反查不到的那一项就是清单缺口。
- [ ] 按 `C = Secret` 筛一次台账：筛出来是全部资产，还是符合直觉的少数？前者说明分级没发生。
- [ ] 台账里有没有「角色」列（提供者 / 部署者）？没有这一列，义务由谁承担答不出（§7.3.3）。
- [ ] 统一连接键是否存在：**换一个数据集版本，能否用一次查询答完「影响了哪些模型、哪些 Prompt、哪些线上输出」**？
- [ ] 模型的标识是「模型名」还是「版本 + 权重哈希」？Prompt 在运行时是否以 `(prompt_id, version)` 寻址？只存在于 Wiki 或聊天记录里的，视为未版本化。
- [ ] 抽一次上周的线上输出，只凭留存字段、不接触线上环境，能否重建它？重建不出，先看 trace 里是否同时有采样参数与检索到的文档 ID——少任一项，非确定性输出都不可复现。
- [ ] 抽查 5 条资产记录，看密级与审批路径是否有分布：全部落在同一密级、走同一审批的，视为分级未生效。
- [ ] 审计明细达到「每天百万次以上」量级时，按 `subject_id` 查一次历史调用要等多久？用「抽样查最近一周」代替全查，说明证据链已在事实上断裂。
- [ ] 做一次绕行测试：绕过统一入口直连模型端点，是否被拦？拦不住说明覆盖率是流程保证（对应 4.3「最容易被误选的那一层」）。
- [ ] 随便挑一条合规义务，能否说清它对应哪个控制点、证据出自哪个字段？说不出字段名，说明 5 排在了 4 之后。
- [ ] 高风险判定由「用途」驱动还是由「技术类型」驱动？上一次用途变更后，风险等级有没有被重新判定过？
- [ ] 存量三期处理表能否在一天内产出（仍在迭代 / 冻结在用 / 无主无调用）？产不出，说明迁移还没有可用的连接键。

### 4.7 小结

| 你的现状 | 先做什么 | 验收判据 |
| --- | --- | --- |
| 资产 < 10、单团队、内部使用 | 1 + 2（清单 + 分级） | 每条资产都有五元组，且能按密级筛出清单 |
| 资产跨团队、需要一次查清影响面 | 1 + 3（连接键 + 血缘） | 「换版本影响谁」一次查询答完 |
| 受监管、需要向监管举证 | 5 + 4（映射先行，字段后冻结） | 每条义务都能指向一个控制点与一份证据 |
| 日调用量大、已有 Agent 动作 | 统一入口收口 + 授权制 | 绕行直连被拦；不可逆动作有人为确认记录 |
| 已有传统数据治理体系 | 混合模式（桥表缝合） | 数据侧与模型侧共用同一条排查链 |

> 本节小结：§4 的工程主线只有一句——**先定字段与连接键，再装平台**。8 步里真正不能动的是「1→2→3」与「5 先于 4」，其余都可并行；工具按「记录 / 控制 / 举证」三层配平，其中**只有控制层能提高覆盖率**，另外两层的功能是让追溯与举证成立。这个主题下决定成败的唯一环节是**字段与连接键的冻结时点**——它比其余环节更值得投入，因为它是唯一一件「做晚了无法回填」、而后面每一步都要引用它的东西：凡是做晚了无法回填的事（连接键、字段集合、映射关系），都不该排在平台采购之后。
