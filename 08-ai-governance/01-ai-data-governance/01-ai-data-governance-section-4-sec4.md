## 4. 工程实现

> 本节回答一个问题：**把 §3 选定的治理模式装起来时，先动哪一步、后动哪一步，每一步的验收判据是什么。** 顺序按 **落地依赖（4.1）→ 必须先解决的工程点（4.2）→ 工具链按能力分层（4.3）→ 三个最小可用样例（4.4）→ 常见工程失效（4.5）→ 小结（4.6）** 展开。文中工期量级为【经验】判断，实际取决于团队是否已有训练 / 发布流水线。

### 4.1 8 步落地顺序与依赖关系

**表 4-1：8 步的顺序、前置条件与产出**

| # | 步骤 | 前置条件（不满足时的症状） | 关键产出 | 工期量级 |
| :---: | --- | --- | --- | --- |
| 1 | AI 资产盘点 | — | 资产清单：模型 / Prompt / 数据集 / 向量索引 / 输出通道 | 首次 2–4 周，之后季度增量 |
| 2 | 分类分级 | 有资产清单 | 每条资产的 ⟨T, C, I, R, X⟩（定义见主文件 §2.1） | 首次 1–2 周 |
| 3 | 血缘采集 | 资产有稳定 ID | 端到端血缘图（训练数据 → Checkpoint → 部署 → Prompt → 输出 → 反馈） | 3–6 周，与流水线耦合 |
| 4 | 审计日志 | 统一 ID + trace 字段已冻结 | 追加写的调用明细（含判定结果） | 1–3 周 |
| 5 | 合规映射 | 有分级 + 有控制点清单 | 法规条款 ↔ 控制点 ↔ 证据 三列表 | 每个法域 0.5–2 人月 |
| 6 | 风险评估 | 有分级 + 有合规映射 | 评估报告（缓解措施 / 残留风险 / Owner 签字） | 单系统 3–10 人日 |
| 7 | 持续监控 | 有审计日志 + 指标定义 | 漂移 / 公平性 / 越界告警 | 取决于存量观测栈 |
| 8 | 合规报告与审计响应 | 前 7 步可用 | 季度内部报告、年度合规报告、自助举证接口 | 持续 |

**这个顺序里只有两处不能动，其余可以并行。**

第一处是 **1 → 2 → 3**：没有清单就无法分级，没有分级就判断不出哪些资产需要采血缘。实践中常见的偷跑是「先买平台、再补资产」——平台能替你存，不能替你定义资产边界与连接键；平台上线后补录的历史资产，其历史血缘通常已经无法回填。

第二处是 **5 必须排在 4 的字段冻结之前**。这是最容易被做反的一步：合规映射看起来像「最后写文档」，实际上它决定**审计日志必须留哪些字段、留多久**。法规的字段要求是硬约束——EU AI Act 对高风险系统的运行期义务包含自动记录事件日志（Art. 12）与人工监督（Art. 14）（【公开】EU AI Act, 2024），NIST AI RMF 1.0 的 MEASURE / MANAGE 两项功能同样指向运行期（【公开】NIST AI 100-1, 2023）。把映射放在日志表建好之后做，结果通常只有两种：尝试回填（做不到），或在日志表上不断加列（把 schema 变成垃圾场）。

**可并行的部分**：6（风险评估）与 7（持续监控）之间没有硬依赖；8 的「自助举证接口」可以在 4 落地后就开始做，不必等 5 / 6 全量完成——审计响应的第一版只需要能按 `asset_id` 与时间窗导出记录。

### 4.2 必须先解决的 5 个工程点

这 5 项的共同点是**做晚了无法回填**，因此它们排在「装平台」之前。

**1. 统一连接键（asset_id）**

治理的多数查询都是「换了个版本，影响了谁」这类跨类问题：一个训练数据集换了版本，影响了哪些模型、哪些 Prompt、哪些线上输出？这要求模型 / Prompt / 数据集 / 索引 / 输出通道共用同一套实体 ID 与关系表（§3.2 的 Asset Registry 模式）。

- 验收判据：**一次查询答完**。如果需要跨三个系统人工拼表，说明连接键不存在，而不是「查询工具不好用」。
- 采购侧的自检方法：看产品文档里的一等公民是「资产」还是「trace / span」——一等公民的定义方式暴露了它假设的治理单元（§7.3.1 展开）。
- 【经验】连接键这一项几乎总是自建：它是组织口径，不是行业标准，买来的是别人的口径。

**2. 版本化寻址，而不是把版本号写在文档里**

主文件 §2.2 把模型定义为 `Model = ⟨framework, arch, weights_hash, training_recipe, dataset_hash⟩`，把输出定义为带完整 provenance 的 `Model(Prompt, Context, Tools)`。工程上的落地只有一条：**运行时能被寻址的才叫版本**。

- Prompt 必须以 `(prompt_id, version)` 寻址；只存在于 Wiki 或聊天记录里的 Prompt 视为**未版本化**（同 §3.7 自检清单的一条）。
- 数据集与索引同理：`dataset_hash`、索引快照 ID 要写进 trace，而不是写进发布邮件。

**3. trace 字段最小集（从可复现性倒推，而不是从「能存就存」正推）**

非确定性输出不可复现——主文件 §1.6 把「可重现性」记为传统数据的 ×5 难度——trace 是唯一补偿手段。最小集如下：

| 字段组 | 字段 | 缺了会怎样 |
| --- | --- | --- |
| 主体 | `subject_id`（谁）/ `channel`（哪个入口） | 答不出「这次是谁触发的」 |
| 模型 | `model_id` / `model_version` / `weights_hash` | 换了 checkpoint 之后旧输出无法回放 |
| Prompt | `prompt_id` / `prompt_version` | 提示词改过以后，旧输出无法解释 |
| 采样 | `temperature` / `top_p` / `seed`（若支持） | 同样的输入复现不出同样的输出 |
| 检索（RAG） | `retrieved_doc_ids` + 每个文档的版本 | 答不出「这个结论引的是哪一版文档」 |
| 工具（Agent） | `tool_call_trace`（含入参与返回值摘要） | 不可逆动作无法追责 |
| 输出 | 输出内容或其存储指针 | 无法举证 |
| 判定 | `policy_version` + 命中原因（放行 / 拦截） | 答不出「当时按哪一版策略判的」 |

- 成本要压的是**留存策略而不是字段**：trace 存储成本按容量随时间累积，压它靠采样、分层与 TTL，删字段等于自断举证链（§7.4 给了这一项的【推算】与量纲对比，此处不重复）。
- 保留期限取各法域要求的**最大值**，并写进保留策略：中国《网络安全法》第二十一条要求按规定留存相关网络日志**不少于六个月**（【公开】《网络安全法》, 2016），EU AI Act 对高风险系统另要求运行期自动日志（【公开】EU AI Act, 2024）。【经验】金融、医疗等强监管行业，机构内部审计通常要求数年，具体年限依业务与机构而定，不能按「六个月」这一个数拍。

**4. 定级源是「用途」，不是「技术类型」**

主文件 §2.1 给的是 `Risk = f(use_case, autonomy, scale_of_deployment, vulnerability_of_subject)`。工程后果很直接：**分级规则引擎的输入必须包含用途、自治程度、部署规模与主体脆弱性**。

- EU AI Act 的高风险清单本身就是按用途列举的（招聘、信贷评分、关键基础设施、教育评估、执法辅助、生物识别分类、移民 / 边境等）（【公开】EU AI Act, 2024）。
- 反例（§3.5 反模式同源）：把「是不是 LLM」「参数规模多大」当作分级输入，会把一个 7B 的招聘筛选模型判成低风险，同时把一个数百 B 的垃圾邮件过滤器判成高风险——两个方向的误判都会发生。

**5. 留存与采样的分层**

【经验】行业上常见的分界是：当治理单元进入「每天百万次以上」量级时，**逐条明细的在线查询**（而不是聚合报表）会先成为瓶颈，此时通常把明细与聚合分层存放——明细走追加写的日志型存储 + 采样索引 + TTL，聚合走关系库长期保留。这与 §7.3.1 的台账基数分析同源：实体台账与事件台账不是同一个数据模型的量变。

- 分层不等于丢证据：判定为拦截 / 高危的记录应走**无条件全量留存**，采样只作用于放行流量的明细。

### 4.3 工具链：按能力分三层，而不是按品类罗列

按品类列六类工具（模型治理 / 血缘 / Prompt / 审计 / 合规 / 安全）容易让人以为「买齐六类就治理好了」。更有用的切法是按能力分三层——**存得住（记录）→ 拦得住（控制）→ 说得清（举证）**。三层必须配平，某一层单独超前不会带来覆盖率提升。

| 层 | 能力 | 可核验的工具形态 | 自建 / 采购的判据 |
| --- | --- | --- | --- |
| 记录层 | 模型与实验版本、数据版本、trace 存储、元数据与血缘目录 | MLflow / Weights & Biases（模型与实验）；DVC / LakeFS（数据版本）；Langfuse / Arize Phoenix / Helicone（trace）；OpenTelemetry 的 GenAI 语义约定（字段标准）；DataHub / Apache Atlas（元数据与血缘） | 与资产命名耦合的部分（连接键、分级规则）自建 |
| 控制层 | 统一入口与策略、输入输出校验、授权与人工介入 | Portkey / Cloudflare AI Gateway（统一入口与策略）；Guardrails AI / LLM Guard / Lakera Guard / Azure AI Content Safety（输入输出校验） | 与自有审批流耦合的放行卡点自建；内容护栏优先采购 / 开源 |
| 举证层 | 合规映射、风险评估、审计报告、可解释性 | NIST AI RMF Playbook / Crosswalk、ALTAI 自查清单、ISO/IEC 42001:2023 管理体系认证；商业侧 OneTrust / Collibra / TrustArc；XAI 侧 SHAP / LIME / Captum | 与本组织法域与角色划分耦合的映射表自建 |

（工具形态均可在各自官方文档核验，属【公开】产品资料；「哪一层该自建」属【经验】判断。）

**第 7 步的监控工具单独说一句**：漂移与公平性监控（Evidently、Arize、WhyLabs、Fairlearn、AIF360）产出的指标属于记录层，但它的告警必须接到控制层才有意义——「检测到漂移」却不触发任何动作（降级、切回旧版本、转人工复核）的监控，等价于没有监控。

**控制层是覆盖率的唯一来源。** 因为**一个控制点只能阻断流经它的东西**（§7.3.4），所以「覆盖率 100%」这句话只有在**调用收口到统一入口**时才有技术含义；否则它表达的是流程约束，会随组织变化衰减。OWASP 把 Prompt Injection 列为 LLM 应用风险清单的第一类（【公开】OWASP Top 10 for LLM Applications, 2023/2025），而内容过滤无法根治提示注入——注入的结果是「指令被服从」，属于动作层问题，只能靠入口处的策略与授权制解决（Agent 场景见 §3.2 的 Embedded 模式）。

### 4.4 三个最小可用样例

这三个样例的作用是**让字段级争议提前暴露**：评审一张 Model Card，比争论「要不要做治理」快得多。

**样例 1：Model Card（YAML，字段集合对齐主文件 §2.2 与 §3）**

```yaml
model:
  name: customer-support-llm
  version: 1.2.0
  base_model: qwen2.5-7b-instruct
  artifact:
    type: lora-adapter
    weights_hash: "sha256:..."
training_data:
  - source: internal-customer-service-logs
    version_hash: "sha256:..."
    license: internal-proprietary
    pii_tags: [order_id, phone_tail]
intended_use: "产品 FAQ / 订单状态 / 退换政策的客服问答（聊天与邮件渠道）"
out_of_scope: [legal-advice, medical-advice, real-time-pricing]
risk:
  level: limited
  basis: "use_case = 通用客服问答；不产生对个人权利的决定"
metrics:
  hallucination_rate: 0.0X
  latency_p99_ms: NNN
owner: data-team@company.com
reviewers: [legal@company.com, security@company.com]
review:
  approved_at: 2025-09-15
  next_review_at: 2026-03-15
```

- 关键不是模板长什么样，而是**哪几个字段必须由流水线自动填充**：`artifact.weights_hash`、`training_data.*.version_hash`、`metrics.*` 三项一旦靠手写，卡片会先于模型过期；人工只补 `intended_use` / `out_of_scope` / `risk.basis` 三项（【经验】——判断方法是看仓库里卡片的生成方式：手写 Markdown 的会过期，由流水线渲染的不会）。
- 本节样例中的 `weights_hash` / `version_hash`（`sha256:...`）与 `metrics` 两项（`0.0X` / `NNN`）都是占位符，仅示意字段位置与类型，**不是可引用的实测指标，也不是行业基准**；实际值由评估流水线按本组织的评测集写入。
- 字段来源是 Model Cards for Model Reporting，数据集侧对应 Datasheets for Datasets（【公开】Mitchell et al., FAT\* 2019；【公开】Gebru et al., 2018）。

**样例 2：一次调用的 trace（JSON，字段取自 4.2 第 3 点）**

```json
{"ts":"2025-09-15T10:22:31Z","subject_id":"u_8812","channel":"chat",
 "model_id":"customer-support-llm","model_version":"1.2.0","weights_hash":"sha256:...",
 "prompt_id":"cs-system","prompt_version":"17",
 "sampling":{"temperature":0.2,"top_p":0.9},
 "retrieved_doc_ids":["faq-v3#412","policy-2025-06#88"],

 "policy_version":"guardrail-v3","decision":"allow","hit_reason":null}
```

**样例 3：合规映射表（法规条款 ↔ 控制点 ↔ 证据）**

| 义务（条款） | 控制点 | 证据（由谁产生） |
| --- | --- | --- |
| 高风险系统运行期日志（EU AI Act Art. 12） | 网关统一记录全字段 trace | trace 存储（样例 2） |
| 人为监督（EU AI Act Art. 14） | 高风险用途调用强制人工确认 | 确认记录 + 授权制日志 |
| 高风险系统投放前登记（EU AI Act Art. 49 + Annex VIII） | 发布流程的强制卡点 | 发布记录中的 `registration_id` |
| 生成合成内容标识（《人工智能生成合成内容标识办法》, 2025） | 输出侧标识注入 | 输出留档中的标识字段 |
| 自动化决策的告知与 DPIA（GDPR Art. 22 / Art. 35） | 用途登记 + 影响评估 | 风险评估报告（步骤 6） |

（法规条款可按官方文本核验，属【公开】；「哪一条配哪个控制点」是本组织的映射决策，不属公开事实。）

**这张表的作用是反向逼出字段**：如果某个控制点对应的证据在 trace 里没有字段能产出来，这张表就是空的。发现得越早，改 schema 的成本越低——这正是 4.1 里「5 必须排在 4 之前」的原因。

### 4.5 五类常见工程失效

| 失效 | 现象 | 后果与对策 |
| --- | --- | --- |
| 覆盖率靠业务自觉登记 | 上线时统一登记，半年后新增资产没人登记 | 覆盖率单调下降；对策是做**绕行测试**：直连模型端点，看是否被拦（§3.7） |
| trace 缺采样参数或检索文档 ID | 出了争议只能「重放一次看看」，结果不稳定 | 非确定性输出不可复现，举证链断裂；对策是按 4.2 的字段表逐项核对 |
| 用技术类型定风险等级 | 小参数的招聘筛选模型被判低风险 | 义务清单整体错配；对策是把定级输入改为用途 / 自治度 / 部署规模 / 主体脆弱性 |
| 映射表做在日志 schema 冻结之后 | 结论是需要回填历史字段 | 历史不可回填，只能不断加列；对策是 5 先于 4 |
| 全部资产同一密级、同一审批 | 审批疲劳，真正高密的资产被淹没 | 分级失效；对策是按 ⟨T, C, I, R, X⟩ 分出至少三档，高密档单独设审批 |

### 4.6 小结

| 你的现状 | 先做什么 | 验收判据 |
| --- | --- | --- |
| 资产 < 10、单团队、内部使用 | 1 + 2（清单 + 分级） | 每条资产都有五元组，且能按密级筛出清单 |
| 资产跨团队、需要一次查清影响面 | 1 + 3（连接键 + 血缘） | 「换版本影响谁」一次查询答完 |
| 受监管、需要向监管举证 | 5 + 4（映射先行，字段后冻结） | 每条义务都能指向一个控制点与一份证据 |
| 日调用量大、已有 Agent 动作 | 统一入口收口 + 授权制 | 绕行直连被拦；不可逆动作有人为确认记录 |
| 已有传统数据治理体系 | 混合模式（桥表缝合） | 数据侧与模型侧共用同一条排查链 |

> 本节小结：§4 的工程主线只有一句——**先定字段与连接键，再装平台**。8 步里真正不能动的是「1→2→3」与「5 先于 4」，其余都可并行；工具按「记录 / 控制 / 举证」三层配平，其中**只有控制层能提高覆盖率**，另外两层的功能是让追溯与举证成立。凡是做晚了无法回填的事（连接键、字段集合、映射关系），都不该排在平台采购之后。
