## 7. 与其他方法对比

### 7.1 先立判据：为什么「低 / 中 / 高」的分级表会误导

用「自动化：低 / 中 / 中-高 / 高」「实时性：低 / 中 / 中 / 高」这样的分级来对比四种治理。问题不在于分级本身，而在于**分级把场景相关的结论伪装成了绝对结论**：同一个「自动化程度」维度，在「100 张表的内部 BI」场景下权重几乎为零，在「日调用千万次的对外生成式服务」场景下却是生死线。分数高低不告诉你「在你的约束下该选谁」。

第二个问题是**分级掩盖了因果**。「Agent 治理自动化程度高」不是因为它更新，而是因为它的治理对象（运行时行为）**根本无法被事先枚举**——只能靠运行时拦截，而拦截机制天然是自动化的。如果你不知道这条因果，就会得出错误结论：以为「先上传统治理、再逐步升级到 Agent 治理」是自然路径。实际上如果你的对象里有 Agent，传统治理机制**在结构上就不适用**，不存在「逐步升级」。

第三个问题是**演进模型把并列关系写成了包含关系**。`传统 → ML → LLM → Agent` 暗示「后者取代前者」。真实情况是**四者长期共存**：一个同时做电商和生成式服务的公司，同一时刻需要「表字段级」的数据治理、「模型 + 数据集版本级」的 ML 治理、「单次调用级」的 LLM 治理——不是选一个，而是**按资产形态分别选**。所以本章的判据框架不问「哪个更强」，而问「**这个判据下，哪种治理机制在结构上成立**」。

第四个问题是**义务归属被漏掉了**。传统数据治理按「数据控制者 / 处理者」二分归属义务；AI 引入后，法规按「提供者 / 部署者」分配义务——**同一个模型在不同人手里义务不同**。这条差异决定了台账字段，也决定了本节必须把「义务归属」列为独立判据。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 治理单元 | 它把什么当作「一个可治理的对象」 | 单元**稳定可枚举**（表 / 字段）→ 登记制成立；单元**运行时才产生**（一次调用、一次工具动作）→ 只能拦截制。选错单元，机制直接失效 |
| 义务归属 | 法规把义务分配给哪个角色 | 义务归属决定了资产台账**必须多记哪些字段**；字段缺失时，出事无法举证，治理白做 |
| 证据强度 | 出事时能否**复现并举证** | 决定了审计字段清单的长度：确定性系统记「输入 + 作业版本」即可重放，概率性系统必须再加「参数 / 上下文 / 权重版本」 |
| 控制点位置 | 事前 / 事中 / 事后 | 只有事中门禁能**阻断**；事前登记只能约束已枚举项，事后审计只能追责不能止损 |
| 成本增长变量 | 成本随**什么**增长：资产数 / 调用量 / 法域数 | 决定了规模上去后哪个方案先失控。这条判据把「贵不贵」变回可计算的问题 |
| 演进断点 | 换到下一档要**重建**什么 | 判断是「加装」还是「重做」。有些迁移是加字段，有些迁移是换架构 |

**六条判据不是并列清单，它们有先后顺序**：先看「治理单元」（决定工具链形态），再看「义务归属」（决定台账字段），再看「证据强度」（决定字段长度），再看「控制点位置」（决定放在哪），最后用「成本增长变量」和「演进断点」判断**规模上限与迁移代价**。跳过前四条直接比价格，得到的一定是错的结论——因为前四条里任何一条不成立，那个方案在你的场景下**根本不运行**，它的价格再低也没有意义。

**判据的权重也不是常数**。同一家公司，在「只有一个内部 LLM 应用」阶段，「控制点位置」的权重低（业务方少、口径容易对齐）；在「几十个 BU 各自接模型」阶段，「控制点位置」跃升为第一位——因为此时失控的主要来源不是「某个应用做错」，而是「没人知道总共有多少应用」。判据权重的这种迁移，对应的正是主文件 §1.8 / §2.4 成熟度模型里 L3（已管理级：流程化）→ L4（量化级：自动化）那一跳。§2.4 把这一跳定义为「**流程化 → 自动化**」，关键在于**治理动作能否被自动触发**；而它之所以必须发生，正是因为到了「几十个 BU 各自接模型」的阶段，治理对象已经多到人力无法逐项覆盖。用一句可操作的话说：**当你的治理问题从「质量」变成「覆盖」时，判据的排序要重排一遍，治理动作也必须开始自动触发**。

**六条判据与本主题的形式化定义是对齐的**：主文件 §2.1 把 AI 资产定义为五元组 `A = ⟨T, C, I, R, X⟩`（类型 / 机密性 / 完整性 / 风险 / 可解释性）。这个定义假设资产是**可枚举的实体**——它适用于传统数据治理、ML 治理，也适用于「已登记」的那部分 LLM 与 Agent 资产。但当治理单元变成「一次调用」或「一次动作」时，五元组里缺少一个维度：**这次行为是谁被授权做的**。因此本节在判据层面把「义务归属」单列——它对应的不是资产属性，而是**行为的主体**。读者可以据此检验自己的台账：如果你的资产表里找不到「授权人」这一列，那么你的台账覆盖不到 Agent 场景。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| **传统数据治理**（DAMA-DMBOK / Collibra / Informatica Axon / Apache Atlas） | 管「表 / 字段 / 指标 / 报表」 | 以**稳定可枚举的 schema** 为治理单元，靠**强制登记 + 血缘**建立台账 | 集团 CDO / 数据治理委员会 | 商业闭源为主（Collibra / Informatica）；开源（Atlas / DataHub / OpenMetadata） |
| **ML 治理**（MLOps）（MLflow / Weights & Biases / DVC / Feast + Model Card） | 管「模型 + 数据集版本」 | 以**版本可寻址的产物**为治理单元，靠**实验追踪 + 产物登记**建立台账 | 算法平台 / MLOps 团队 | 开源（MLflow：Linux Foundation）+ 商业（W&B） |
| **LLM 治理**（LLMOps）（Langfuse / Helicone / PromptLayer / LangSmith） | 管「Prompt + 一次调用 + 输出」 | 以**运行时产生的一次调用**为治理单元，靠**网关拦截 + 全字段 trace** 建立证据 | 应用团队 + AI 平台团队 + 合规 | 开源可自托管（Langfuse / Phoenix）+ 商业 SaaS（LangSmith / PromptLayer） |
| **Agent 治理**（AgentOps）（LangGraph / AgentScope / OpenAI Agents SDK + MCP） | 管「模型 + 工具 + 记忆 + 权限」的运行时组合 | 以**一次有副作用的动作**为治理单元，靠**工具权限最小化 + 动作级审计 + 人在回路**兜住不可逆后果 | Agent 平台团队 + 安全团队 | LangGraph / AgentScope 开源（AgentScope：Apache-2.0，2024）；托管平台商业 |
| **横向合规证据层**（GRC）（OneTrust / ServiceNow GRC / Credo AI 等） | 不治理资产，只治理「**证据与法规映射**」 | 把散在各个技术控制点里的证据**汇总成可审计的映射表** | 合规 / 法务 / 内审 | 商业闭源为主 |

**这些候选其实分两族，先分族能省掉一半比较**：前三档（传统 / ML / LLM）差异在**治理单元的粒度**，属于同一族的连续演进——台账模型（实体 + 版本 + 血缘）基本可复用，迁移主要是「加一类资产」。第四档（Agent 治理）是**跨族**：它的治理对象不再是「一个东西」，而是「一段会自己决定下一步的运行过程」，台账模型从「实体 + 版本」变成「会话 + 动作序列 + 授权决策」，这是结构断点。第五档（GRC）不属于任何一族，它是**横向的证据层**，上层变不变它都存在。

**同族内部怎么选，判据完全不同**：同族内竞争的是**采集成本**而不是机制——传统治理看的是「能不能扫到你的数据源、SQL 解析得准不准」；ML 治理看的是「追踪粒度与产物存储成本」；LLM 治理看的是「trace 写入吞吐与查询延迟」；Agent 治理看的是「框架有没有中断 / 恢复这类原语」。换句话说，**跨族选机制，同族选接入成本**。绝大多数「选型纠结」其实发生在同族内部，而这类纠结用一两周 PoC 就能收敛，不该占用架构评审的时间。

**候选清单的取舍说明**：本节的候选表**完整保留「传统数据治理 / ML 治理 / LLM 治理 / Agent 治理」四档**，并增补了第五档「横向合规证据层（GRC）」。增补的理由不是补全对称性，而是因为实践中「我必须做出一张能交给审计的映射表」这个需求**不属于上述任何一档**：GRC 平台不采集资产、不拦截调用，它只把别人的证据重新组织一遍。把它显式列出来，可以让读者避免一个常见错误——指望某个技术控制点平台顺便产出法规映射表。此外，四档里的工具举例保留了全部工具名（Collibra / Informatica、MLflow / W&B、Langfuse / PromptLayer、AgentScope / LangGraph），便于对照阅读。

**没有列入候选的常见选项，以及为什么不列**：一是「纯流程制度（审批流 + 人工抽查）」——它不构成技术控制点，无法产出可复现的证据，因此不作为并列候选，而是作为所有方案的兜底层；二是「数据脱敏 / 加密类工具」——它们解决的是数据在存储与传输中的暴露面，属于主文件 §1.3 里「安全」这一行，与治理的举证机制正交；三是「模型评测平台」——评测回答的是「模型好不好」，治理回答的是「这次行为能不能发生、能不能举证」，两者可以共用数据集但机制不同。**把正交的东西放进同一张对比表，是选型讨论跑偏的最常见原因。**

**候选表的每一列都对应一个可查验的事实**：「定位」是它管什么，「核心机制」是一句话的因果，「典型使用者」告诉你组织形态是否相似，「许可 / 商业模式」决定你能不能自托管与改代码。**其中「许可 / 商业模式」在 AI 治理里常常是隐性约束**：因为 trace 里包含用户输入与模型输出，很多组织在合规上不能把这类数据送到第三方 SaaS，于是「能不能自托管」直接变成硬门槛，而不是偏好问题。选型时如果先看功能再看许可，常见结果是 PoC 做完才发现数据不能出域。

### 7.3 机制差异：为什么它们的表现不同（核心节）

四档治理的差异可以完全归因到四个机制维度：**治理单元在什么时刻产生**（7.3.1）、**可重现性的来源是什么**（7.3.2）、**义务按什么分配**（7.3.3）、**控制点放在通路内还是通路外**（7.3.4）。前两条决定「工具链长什么样」，后两条决定「台账里必须有什么字段」。

这四条不是各自独立的：**治理单元的选择（7.3.1）会强制后三条的取值**。选了「一次调用」作为治理单元，就等于承认单元不可预判（因此必须拦截）、输出不可重放（因此必须快照上下文）、举证材料必须来自运行期。反过来说，**如果你想复用传统数据治理的机制（登记 + 血缘），就必须先接受它的治理单元（表 / 字段）**——不能只要机制不要约束。这条「单元先行」的原则是本章最有操作性的一条：选型时先定单元，其余结论基本被推导出来。

#### 7.3.1 治理单元：从「可枚举的实体」到「运行时才产生的动作」

**机制是什么**：治理单元 = 一个能被**唯一标识 + 版本化 + 归属责任人**的最小对象。整个治理体系（台账模型、工具链形态、审计字段）都由这个选择决定。

**它在各候选中的实现差异**：

| 候选 | 治理单元 | 单元的标识何时产生 | 因此工具链的形态 |
| --- | --- | --- | --- |
| 传统数据治理 | 表 / 字段 | 建表时（**事先**） | 目录 + 血缘，登记制 |
| ML 治理 | 模型版本 / 数据集版本 | 训练或发布时（**事中**） | 实验追踪 + 产物登记，登记制 + 版本门禁 |
| LLM 治理 | 一次调用（prompt + 模型版本 + 上下文 + 输出） | 请求到达时（**运行时**） | 网关 + trace 流水线，拦截制 |
| Agent 治理 | 一次动作（含副作用的工具调用 + 授权决策） | Agent 决定行动时（**运行时，不可预判**） | guardrail + 权限引擎 + 人在回路，拦截制 + 授权制 |

**由此必然导出的性质**：因为传统数据治理的单元在**建表时**就已确定且 schema 可枚举，所以治理可以做成一件事前动作——「不登记不让发布」，事后不用重复介入；因为 LLM 与 Agent 的治理单元在**请求到达时**才存在，所以「不登记不让发布」这类机制在结构上无处施加，治理必须被搬到数据通路上做成拦截。**这条因果推出一个常见误判**：把 AI 治理做成「再建一个目录，让业务来登记 Prompt 和 Agent」——登记得完的项目，往往本来就不需要治理；真正需要治理的长尾调用，永远不会主动来登记。

**第二条由此导出的性质（单元粒度决定台账基数）**：因为治理单元越细，台账行数越多，所以「一次调用 = 一行」的模型会把台账从「万级实体」推向「亿级事件」。这不是同一个数据模型的量变，而是**存储与索引形态的质变**：实体台账可以放进关系库并支持复杂查询，事件台账只能走追加写的日志型存储 + 采样索引。【经验】行业上常见的分界是：当治理单元的规模进入「每天百万次以上」时，逐条明细的在线查询（而不是聚合报表）会先成为瓶颈，此时通常会把明细与聚合分层存放。

**第三条由此导出的性质（责任人会随粒度贴近运行时）**：因为治理单元越贴近运行时，责任就越靠近「谁发起这次行为」而不是「谁拥有这个资产」，所以 AI 治理的问责链必然从「资产 Owner」扩展为「发起人 + 授权人 + 资产 Owner」三段。这也解释了为什么 AI 治理的责任主体天然是跨团队的（对应主文件 §1.3 与 §2.5 的主体差异）：**表有 Owner，调用有发起人，动作有授权人**——三者很少是同一个人。

**公开证据**：EU AI Act 对高风险系统的义务是**两层叠加**的——一次性义务（投放市场或投入使用前须登记入 EU 数据库，Art. 49 + Annex VIII；技术文档，Art. 11 + Annex IV）与运行期义务（Art. 12 日志留存、Art. 14 人工监督），后者是 AI Act 在产品准入之外**另外规定**的一层（【公开】EU AI Act, 2024）。也就是说，法规并没有取消登记制，而是把义务**重心**从「登记那一刻」移到了「运行全程」：登记只覆盖「已投放市场的系统」，运行期义务要覆盖「每一次投入使用」。**这才是 LLM 与 Agent 治理必须做成拦截制的法规侧理由**——如果你的治理只到登记为止，你在法规侧覆盖的正是那个更小的集合。NIST AI RMF 1.0 的四项功能 GOVERN / MAP / MEASURE / MANAGE 中，MEASURE 与 MANAGE 都指向运行期（【公开】NIST AI 100-1, 2023）。可自行核验的方法：打开任一 LLM 可观测工具的官方文档，看它的一等公民是「资产」还是「trace / span」——一等公民的定义方式就暴露了它假设的治理单元。

**失效条件**：当一个组织的 AI 调用量极小（例如每月几十次人工触发的内部实验），拦截制带来的网关建设成本高于收益，此时登记制（把 Prompt 与模型版本登记造册）反而是正确的——**治理单元的选择要跟着「单元产生的速率」走，而不是跟着「技术先进性」走**。

#### 7.3.2 证据强度：确定性重放 vs 概率性复现

**机制是什么**：能不能在事后**证明「当时发生了什么」**，取决于系统是否可重放。可重放的审计只需要存输入；不可重放的审计必须把「产生这次输出所需的全部条件」快照下来。

**它在各候选中的实现差异**：

- **传统数据治理**：ETL 是确定性的（同一输入 + 同一作业版本 → 同一输出），所以审计字段只需「输入快照 + 作业版本 + 调度实例」。这也解释了为什么数据审计字段数通常是个位数。
- **ML 治理**：训练可复现但成本高。因此主流做法不是存「训练输入」，而是存**可寻址的产物 + 配方**：权重哈希、数据集哈希、超参、代码版本（这正是 Model Card 的字段集合，【公开】Mitchell et al., FAT* 2019）；数据集侧对应 Datasheets for Datasets（【公开】Gebru et al., 2018）。
- **LLM 治理**：推理默认是非确定性的（采样温度、top-p 等），**同一输入的两次输出可以不同**。所以审计字段必须加一层：模型版本、Prompt 模板版本、采样参数、检索到的上下文（RAG 场景）、护栏判定结果。少任何一项，「这次输出为什么是这样」就复现不了。
- **Agent 治理**：比 LLM 再多一层——**动作序列与授权决策**。Agent 的最终状态取决于中间每一步的选择，审计对象从「一次调用」变成「一棵轨迹树」；而且轨迹树的形状本身依赖运行时环境（工具返回什么、用户怎么答），**无法靠单次重放还原**。

**由此必然导出的性质**：因为 AI 系统的输出不是输入的确定函数，所以「留了日志」和「可举证」之间差了一整层——**日志记录发生了什么，证据链记录为什么必须发生**。这条因果的工程后果是：AI 治理的审计字段清单必须**从「可复现」倒推**，而不是从「日志系统默认有什么」正推。绝大多数「我们留了 trace」却举不出证的团队，缺的正是倒推这一步。

**怎样判断自己的证据强度够不够**（三个可自检的问题）：第一，「只凭留存字段、不接触线上环境，能不能重建出这次输出？」第二，「能不能证明**当时生效的是哪个模型版本**（而不是事后查到的当前版本）？」第三，「如果监管问『同样的输入，为什么上周和这周的输出不一样』，能不能给出参数级解释？」——三个都答「能」，才叫证据链；任何一个答不上，缺的那个字段就是清单上的下一条。

**证据强度决定的其实是「举证成本」而不是「是否合规」**：因为举证成本与必须留存的字段数近似线性相关，所以治理方案的选择会反过来决定组织的合规成本结构——选择全量留存的组织在被问到时能自动导出，选择「按需查」的组织每次审计都要人工拼装。【经验】一次外部审计所需的人工拼装通常落在数人周量级，而全量留存的边际成本按 7.4 的推算落在数千美元/年量级；**因此「省日志存储」几乎总是一笔算错的账**，除非留存真的进入了 TB/月量级。

**公开证据**：GDPR 第 22 条对纯自动化决策设限、第 35 条要求高风险处理做 DPIA（【公开】GDPR, 2016）——两项义务都要求能说明**决策依据**，这在非确定性系统上只能靠快照字段支撑。中国侧对生成合成内容提出标识要求，同样需要能说明内容何时、由什么生成（【公开】《人工智能生成合成内容标识办法》, 2025）。

**失效条件**：当模型被固定为贪心解码（temperature = 0，且无外部检索、无工具调用）时，输出接近确定函数，审计可以退回到「输入 + 版本」的轻量形态。**但只要模型带上 RAG 或工具调用，这条退路立刻消失**——因为上下文本身变成了运行时变量。

#### 7.3.3 义务归属：从「控制者 / 处理者」到「提供者 / 部署者」

**机制是什么**：法规不治理技术，法规**分配义务**。义务分配方式决定了资产台账上必须挂哪些角色字段——字段不齐，就无法回答「这条义务由谁承担」。

**它在各候选中的实现差异**：

| 治理体系 | 义务分配方式 | 台账必须多记的字段 |
| --- | --- | --- |
| 传统数据治理（EU） | 控制者 / 处理者二分（【公开】GDPR, 2016） | 数据主体、处理目的、法律依据、保留期 |
| 传统数据治理（中国） | 个人信息处理者 / 受托处理者（【公开】《个人信息保护法》, 2021） | 处理的合法性基础、告知同意记录、跨境传输 |
| AI 治理（EU 视角） | 提供者 / 部署者 / 进口商 / 分销商（【公开】EU AI Act, 2024） | **角色**、用途、风险等级、投放市场时间 |
| 中国生成式 AI | 服务提供者（【公开】《生成式人工智能服务管理暂行办法》, 2023）；同一主体通常兼具个人信息处理者身份（【公开】《个人信息保护法》, 2021） | 备案号、安全评估结论、内容标识 |
| 行业垂直规则 | 按行业与主体角色适用（HIPAA 的 covered entity / business associate、Basel 的受监管银行；角色定义可查各自官方文本） | 适用行业、适用条款、行业监管申报口径 |
| Agent 治理 | 尚无统一的成文法角色划分 | 授权人、被授权动作白名单、动作上限、人在回路的触发条件 |

**表内「传统数据治理（中国）」「生成式 AI 的个人信息处理者身份」「行业垂直规则」三行是既有候选**：它们分别对应个保法与行业垂直框架（HIPAA / Basel）。列出的理由不是对称性，而是这四类框架**共用同一机制**——义务按**角色**而非按资产分配，差别只在角色名与适用行业；而它们各自都进入 7.4 的 `h(法域数 × 适用框架数)` 一项，每多一个都要多做一遍条款到控制点的映射。

**由此必然导出的性质**：因为 AI Act 的义务是**按角色**而非按资产分配的，所以**同一个模型在不同组织手里，需要履行的义务完全不同**——一个只做内部部署的公司和一个对外提供 API 的公司，即使跑的是同一份权重，义务清单也不是包含关系。因此 AI 资产台账**不能只有一个「密级」维度**，必须再挂「角色 + 用途 + 风险等级」。这条因果的实践后果：把模型只登记成「一个高密的权重文件」是不够的，因为在「提供给他人使用」这个角色下，透明度和技术文档义务会被激活，而这与密级无关。

**由此导出的第二条性质（多法域叠加时字段会冲突）**：因为不同法域对同一个资产可能给出不同的分级与不同的义务，所以台账的「风险等级」不是标量而是**向量（法域 → 等级）**；把风险等级做成单值字段的系统，在跨法域时必然要改表结构。这也是「同一资产、不同结论」这一现象的来源：它不表示治理做错了，而表示治理对象本身在不同法域下被定义了两次。

**义务「转移」不等于举证责任消失**：因为提供者与部署者可以分离，「我买的是别人提供的模型」并不等于义务被买断——部署者仍要自证**用途的合法性与自身场景下的风险控制**（这正是 AI Act 把部署者单列为角色的原因，【公开】EU AI Act, 2024）。这条因果在采购谈判里经常被误用：以为拿到一份供应商合规声明就完成了举证。**正确理解是：供应商的声明是你举证材料的一部分，不是全部。**

**公开证据**：EU AI Act 的处罚上限按义务类型分层——违反禁止性实践最高 3500 万欧元或全球年营业额 7%，违反其他义务最高 1500 万欧元或 3%（【公开】EU AI Act Art. 99, 2024）。**处罚梯度本身就是义务分层的证据**。NIST AI RMF 1.0 采用自愿框架路线，与 EU 的强制路线形成对照（【公开】NIST AI 100-1, 2023）；ISO/IEC 42001:2023 则把 AI 治理做成可认证的管理体系（【公开】ISO/IEC 42001:2023）——三条路线的差别不在技术，而在「谁向谁举证」。

**失效条件**：只在一个法域内、只对内部提供、且用途不落在高风险清单内的组织，义务字段可以精简为「密级 + 用途」两项。但**一旦跨法域或对外提供，这套精简台账会被迫整体重编号**——因为角色字段是行级字段，不是可以事后补的注释。

#### 7.3.4 控制点位置：事后审计 / 事前登记 / 事中门禁 / 授权制

**机制是什么**：一个控制点只能阻断**流经它**的东西。把控制点放在数据通路之外，它就只能追责；放在通路之内，它才能止损。

**它在各候选中的实现差异**：

| 控制点 | 能做什么 | 不能做什么 | 谁主要用它 |
| --- | --- | --- | --- |
| 事后审计 | 追责、归因、改进 | 无法阻止已经发生的损失 | 传统数据治理、合规报告 |
| 事前登记 | 保证「已知资产合规」 | 拦不住未登记的长尾调用 | 传统数据治理、模型准入 |
| 事中门禁 | **阻断**违规输入 / 输出、改写、降级 | 只能拦内容，拦不住「动作本身是否该做」 | LLM 治理（网关 / guardrail） |
| 授权制 | 决定**某个动作是否被允许** | 需要预先定义动作空间与上限 | Agent 治理（工具权限 + 人在回路） |

**由此必然导出的性质**：因为 Agent 的下一步动作**在调用前是不可枚举的**（它由模型在运行时决定），所以事前登记只能登记「工具集合」，不能登记「动作序列」；能兜住后果的只剩授权制——把权限收敛到工具级与额度级，并对不可逆动作强制人在回路。**这条因果解释了为什么 Agent 治理不能复用 LLM 治理的护栏**：内容护栏判断的是「这句话能不能说」，授权判断的是「这个动作能不能做」，后者失效的代价高一个量级——内容错了可以撤回，资金划出去了不能。

**第二条由此导出的性质（控制点会向网关合流）**：因为服务之间的调用是**东西向**的、不经过统一入口的，任何「逐服务挂载」的门禁方案都会因为新服务上线而出现覆盖缺口；只有把控制点放在**所有调用必经之处**，覆盖才是结构性保证而不是流程保证。因此「AI 网关」这类组件不是架构洁癖，而是覆盖面从「流程保证」升级为「结构保证」的必要条件。本书 §6 中阿里案例把模型、Prompt、数据、输出四个面收口到统一网关，正是这条性质的直接体现。

**第三条由此导出的性质（门禁的失败模式必须分层选择）**：因为门禁本身也会故障，它在故障瞬间必须选一个方向——**fail-open（放行）还是 fail-close（阻断）**；这个选择不能靠工程直觉，只能由「误拦的代价」和「误放的代价」谁更大决定。内容判定类门禁的误拦代价是业务中断（用户看不到正常内容），误放代价是内容风险，因此这类门禁通常选择 fail-open 并事后追责；授权判定类门禁的误放代价是不可逆的资金或数据损失，因此必须选择 fail-close——**宁可暂时拒绝所有写操作，也不能放行一次越权写**。这条因果是把「授权」与「内容」分成两层的第二个理由，也是决定网关能否承载业务的前提。

**公开证据**：把工具能力与调用边界用统一协议描述，是 MCP 在 2024-11 发布时的核心主张（【公开】Anthropic, 2024）；OWASP 的 LLM 应用风险清单把 Prompt Injection 列为第一类风险（【公开】OWASP Top 10 for LLM Applications, 2023/2025），而只靠内容过滤无法根治提示注入——因为注入的结果是「指令被服从」，属于动作层问题。可自行核验的方法：查任一 Agent 框架的文档，看它是否提供**中断 / 恢复（human-in-the-loop）**这类原语；提供该原语的框架，说明其设计者已经承认「授权」是一等公民。

**失效条件**：当 Agent 只有只读工具（查询、检索、生成报告）且无写权限时，授权制的必要性大幅下降，内容护栏 + 事后审计即可覆盖。**授权制的价值与「动作的不可逆程度」成正比**，与「Agent 的智能程度」无关。

**四个机制维度的失效条件有一个共同点**：它们都发生在「单元产生速率下降」的方向上——调用少了、动作只读了、模型确定解码了。这意味着**治理机制的选择是可逆的，但方向是单向的**：业务从「确定性」走向「非确定性」很容易（加一个 RAG 就够了），从非确定性退回确定性几乎不可能。因此工程上的稳妥做法是**按可预见的非确定性程度预留字段与门禁位置**，而不是按当前状态精确配置。

### 7.4 成本结构对比（不是价格表，是成本函数）

四种治理的成本都可以写成同一个函数形式，差别只在**哪一项是主导项**：

```
治理成本 ≈ 固定组织成本 + f(资产数) + g(发布与调用频次) + h(法域数 × 适用框架数) + 事件成本
```

| 候选 | 主导项 | 隐性成本（不加预算就失控的那一项） | 规模上去后先出问题的地方 |
| --- | --- | --- | --- |
| 传统数据治理 | `f(资产数)`：每张表 / 每个字段都要登记与维护 | **人工补全的持续性**——元数据会随时间过期，补全不是一次性工程 | 元数据质量（不是元数据数量） |
| ML 治理 | `g(发布频次)` + 产物存储（每次训练一个可寻址产物） | **数据集快照的存储**——为保证可复现必须存版本，而数据集比模型大得多 | 存储成本与实验可追溯性的平衡 |
| LLM 治理 | `g(调用量)`：trace 留存与在线判定的边际成本 | **在线审核自身的算力**——护栏是一次额外推理，它随调用量线性增长 | trace 存储 + 护栏算力 |
| Agent 治理 | `g(动作次数)`，且**失败一次的成本远高于拦截一次的成本** | **动作空间的定义与维护**——权限白名单需要随工具演进而更新 | 权限漂移（新旧工具并存时的越权） |

**成本函数的「形状」比大小更重要**：传统数据治理是**阶梯式**的——资产数翻倍通常不会让成本翻倍，但每次扩域（新增一个业务域、新增一类资产）会跳一级；LLM 治理是**线性**的——成本近似正比于调用量，没有跳变也没有规模摊薄；Agent 治理介于两者之间，但它的「事件成本」项权重最高，因为一次越权动作的处置成本（冲正、赔付、对外说明）可能高于整年的拦截投入。**选型时先问形状，再问大小**：如果你的调用量预期一年内涨 10 倍，那么线性成本的那一项才是风险点。

**这条形状差异直接改变技术选择**：因为传统数据治理的成本是阶梯式，它的优化方向是「**把扩域次数压下来**」（一次扩域尽量覆盖多个业务域）；因为 LLM 治理的成本是线性的，它的优化方向是「**把单位成本压下来**」（采样率、字段裁剪、冷热分层）。同一个团队用同一套预算，做错了优化方向就会出现「业务量涨了、账单涨得一样快，但我们以为做了优化」的情况。

**【经验】关于组织成本**：行业内普遍观察是，治理的组织成本存在一个**台阶**——当资产类型或调用形态只有一种时，治理可以由一个 3–10 人的平台小组兼做；一旦同时存在「表字段 / 模型 / 调用 / Agent 动作」中的三类以上，通常需要独立的治理委员会与专职口径维护角色（主文件 §1.8 把这一级记为 **L3 已管理级：流程化**，其典型风险正是「一致性差」）。这个台阶的来源不是工作量线性增长，而是**口径统一**需要跨团队决策权——技术上能做的检查，和组织上能推得动的检查，是两件事。

**「做成一个统一平台」省的是哪一项**：因为四档的成本主导项不同，把它们合并到一个平台只有在**共享同一项主导成本**时才真正省钱。四档真正共享的是「身份与 Owner 体系」（谁是责任人、谁有权看），不共享的是「采集链路与存储形态」（实体台账 vs 事件流水）。因此统一平台通常省下的是**组织成本与接口成本**，而技术成本（存储、算力）仍按各自的函数增长。**判断要不要合并的实操问题**：合并后能不能只用一套 ID 与一套权限？能，则合并有真实收益；不能，则合并只是把四个系统的运维复杂度搬进一个更大的系统里。

**被大多数团队忽略的是 `h(法域数 × 适用框架数)` 这一项**：因为每新增一个法域，都需要把「法规条款 ↔ 控制点 ↔ 证据」重做一遍映射，而映射工作没有规模效应（不能靠自动化生成，必须有人读条款），所以这一项是**阶跃式**的而非连续的。【经验】行业上常见的量级是：首次做某个法域的映射需要 0.5–2 人月的初始工作，之后转入持续维护（法规修订时会再触发一次）；因此「我们什么时候进第 N 个法域」这个商业决策，同时也是一个治理成本决策，两者应当一起算。

**一个【推算】示例（trace 存储）**：按每次调用留全字段 trace 约 1–3 KB（prompt 版本 ID、模型版本 ID、输入摘要、输出、判定结果，不含原始输入全文）估算：日调用 1000 万次 → 10–30 GB/天 → 约 3.6–11 TB/年。按对象存储标准层 $0.023/GB-月推算（【公开】AWS S3 定价页, 2025），**在「留存 12 个月、按年末满量占用计」这一假设下**，年存储成本约 1–3 千美元量级（3.6 TB × 1024 × $0.023 × 12 ≈ $1.0k；11 TB × 1024 × $0.023 × 12 ≈ $3.1k）——这一步必须写出来，否则读者会把月度单价当成年度成本，少算 12 倍；**但若要求留存原始输入全文或完整上下文快照，量级会再上一档（数 TB 到数十 TB）**——这就是为什么「全字段审计」的字段清单必须按可复现性倒推，而不是按「能存就存」正推。**但这组数字不能直接拿去比较「护栏算力」与「trace 存储」**：前者的成本是**每次调用发生一次的推理**（∝ 调用量 × 单次推理单价），后者是**随时间累积的容量**（∝ 留存天数 × 每日新增字节 × 存储单价），两者量纲不同，写成「谁比谁贵几倍」的单一倍数一定是错的。要比较必须统一到「一次调用」这个共同口径：【推算】trace 按 2 KB/次、$0.023/GB-月计，一次调用对应的**单月**存储成本约 5×10⁻⁸ 美元；护栏按每次调用一次额外推理、合计 1–2 千 token 计，小模型档位按 $0.1–1 / 百万 token 的公开标价推算（各厂商官方 pricing 页可自行核验，2024–2025 口径），【推算】单次成本落在 10⁻⁴–10⁻³ 美元量级——**两者相差约 3.3–4.3 个数量级，且这个倍数随「护栏模型选型」与「留存月数」两个变量移动**（存储项还要再乘留存月数，护栏项不随留存变化）。所以工程结论不是「谁更贵」，而是**两者要压的杠杆完全不同**：压 trace 成本靠留存策略（采样、分层、TTL），当天就能见效，且不损失判定能力；压护栏成本只能动模型选型，或把可规则化的判定前置成规则过滤——**把这两件事合成一个「AI 治理成本」预算，钱一定会花错地方**。

### 7.5 决策树（每个分支都要有阈值依据）

**这棵树分两段，顺序不能颠倒**。上半段是**机制层**：第一层不是「规模」而是「治理对象」，因为对象决定机制；第二层才引入法规约束（是否向 EU 提供、用途是否落在高风险清单）——凡是来自法规的节点**直接标注法规来源而不写阈值**，法规的分界不需要也不应该由工程经验来定。下半段是**成本与举证层**，用横线与上半段隔开，**放在最后**：它只在机制已经选定之后回答两个问题（留存要不要采样、要不要加 GRC 证据层），因为它只影响「怎么实现」，不影响「能不能用」。**全树唯一带数值的判断节点是成本段的「月调用量是否 ≥ 3 亿次/月」**，它的依据在树后逐条解释；其余节点全部是二值（是 / 否）或对象分类，不引入可调参数——这本身就是一种防错设计：**能在树上被拧的旋钮越多，选型结论就越容易被「调参」成想看到的样子**。

```
你要治理什么？（上半段 · 机制层：对象 → 法规）
    │
    ├─ A 只有表 / 字段 / 指标（无 AI 资产）
    │      └─ 传统数据治理（登记 + 血缘），不要引入 AI 治理工具
    │
    ├─ B 有自训练 / 自微调模型，但对外只提供预测结果
    │      └─ ML 治理（产物登记 + Model Card 字段）＋ 传统数据治理
    │            └─ 是否向 EU 提供或部署 → 是 → 追加 AI Act 角色与风险等级字段
    │
    ├─ C 对外提供生成式服务 / 内部有 LLM 应用
    │      └─ LLM 治理（网关门禁 + 全字段 trace）
    │            ├─ 用途落在高风险清单（招聘 / 信贷 / 教育 / 关键基础设施 / 执法辅助）
    │            │      → 追加：数据治理义务 + 运行日志 + 人工监督 + 准确性鲁棒性
    │            └─ 提示注入 / 越权读取是主要担忧
    │                   → 追问：防护是「内容过滤」还是「能力边界收敛」？只做前者不成立
    │
    └─ D 有会自主调用工具 / 写数据 / 发起交易的 Agent
           └─ Agent 治理（工具权限最小化 + 动作级审计 + 不可逆动作人在回路）
                 └─ 是否有不可逆动作（付款 / 发货 / 删除 / 外发）
                        → 是 → 强制人在回路 + 动作额度上限（不可用事后审计替代）

════════════════════════════════════════════════════════════════
下半段 · 成本与举证层（上面选完之后才判断，不影响「能不能用」）
    │
    ├─ 月调用量是否已到「留存成本成为约束」的量级（≥ 3 亿次/月，按 3 KB/次折算约 TB/月）？
    │      ├─ 否 → trace 全量留存：采样省下的钱落在噪声里，不抵它损失的证据完整性
    │      └─ 是 → trace 采样 / 分层 / 设 TTL；护栏判定仍全量在线（它不由留存策略降本）
    │
    └─ 举证对象是否在组织外部（监管 / 客户审计 / 合作方尽调）？
           ├─ 否 → 技术控制点的原始日志足够，不引入 GRC
           └─ 是 → 追加 GRC 证据层（「法规条款 ↔ 控制点 ↔ 证据」映射表）
```

**阈值依据**：

- **「高风险清单」不是自定阈值**：它直接来自 EU AI Act 的高风险用途清单（【公开】EU AI Act, 2024）。落在清单内会激活一整套额外义务，因此它是机制层里的一条**硬分支**（凡进入 B / C 两支都要检查一次），而不是靠经验判断的软条件。
- **「有自训练 / 自微调模型」与「只调用外部 API」的分界**：分界的依据是**是否需要对训练数据举证**。自训练模型需要回答「训练数据从哪来、有没有合法性基础、有没有偏见」；只调外部 API 的组织通常由提供者承担这部分举证（角色不同，见 7.3.3）。这是一条**义务边界**，不是技术边界——用「模型是不是自己训的」来判断义务归属会判错。
- **「不可逆动作」是硬阈值而非概率阈值**：因为不可逆动作一旦执行，事后审计无法止损，所以「是否需要人在回路」按**可逆性**二值判定，不按「风险概率」连续判定。用概率判定会得到一个错误结论——「风险低所以不用人在回路」，但低概率 × 不可逆 = 期望损失不可控。
- **「≥ 3 亿次/月」（对应树下半段成本与举证层的第一个节点）取的是 7.4 区间的哪一端**：7.4 给的是每次 **1–3 KB** 的「区间」，而【推算】区间两端折算出的调用量差 3 倍——按 1 KB/次算，1 TB/月（取 10¹² 字节）≈ 10⁹ 次/月；按 3 KB/次算，1 TB/月 ≈ 3.3×10⁸ 次/月。树上写 **3 亿次/月**，即**按单次 3 KB 的上限口径**定的，目的是让成本压力**更早**被触发：宁可早一步开始采样，也不要等到更贵的字段口径下才发现账单失控。反方向同样成立——100 万次/月量级按同一区间只折算成 1–3 GB/月，成本落在噪声里，此时全量留存没有任何理由做采样。**所以这条阈值的真实形态是一个区间（3 亿–10 亿次/月），树上写的是它的保守端**；读者若知道自己的 trace 字段口径落在区间哪一端，直接按那一端换算即可，不必沿用 3 KB。
- **「什么时候才需要 GRC 证据层」（对应树下半段的最后一个节点）**：触发条件是**举证对象在组织外部**（监管、客户审计、合作方尽调）。如果举证对象只在组织内部，技术控制点产出的原始日志已足够；一旦举证对象在外部，才需要「法规条款 ↔ 控制点 ↔ 证据」的映射表，因为外部审计问的是条款，不是日志。注意这个节点是**二值**而非阈值：它不按法域数量或调用量分档，因为「外部能不能看懂你的日志」不是规模问题。

**决策树的使用方式**：这棵树每次只走一条路径，但**路径之间不是互斥的**——一个组织完全可以同时落在「LLM 治理」和「Agent 治理」两个分支上。正确用法是**对每一类资产分别走一遍**，然后把结论合并到同一份台账里；错误用法是把它当成「我们公司属于哪一档」的分类题，那样做出来的结论一定覆盖不全。另外，树里出自法规的分支（高风险清单、角色字段）**优先级高于**出自成本的分支，因为法规给的期限是外生的。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 内部 BI + 报表，无 AI 资产 | 传统数据治理（目录 + 血缘 + 分级） | 轻量自建目录 | 引入 AI 治理框架会带来与收益不匹配的组织成本 |
| 只有 API 调用的客服 / 写作类应用 | LLM 治理（网关 + trace + 护栏） | 云厂商内容安全服务 + 自建 trace | 上完整 GRC 平台属于超前建设；义务主体尚不落在自己身上 |
| 自训模型 + 对外提供 | ML 治理 + AI Act 角色与风险字段 | 一体化 MLOps 平台 | 只做 MLflow 追踪会缺「角色 / 用途 / 风险等级」三项举证字段 |
| 面向 EU 的高风险用途 | 四档全上 + GRC 证据层 | 商业 AI 治理平台 | 只靠技术控制点无法产出可审计的法规映射表 |
| 有写权限的运营 / 交易 Agent | Agent 治理（授权 + 动作审计） | Agent 框架原生 guardrail + 自建权限引擎 | 只做内容护栏：能拦不当措辞，拦不住超额退款 |
| 集团多 BU，各 BU 自建 AI 应用 | 统一下沉网关 + 集团口径 KPI | 各 BU 自行接入厂商治理服务 | 无统一收口时，「覆盖 100%」无法被证明，只能被声称 |

**5 个常见组合**（每条说明职责边界与运维代价）：

1. **元数据（DataHub / OpenMetadata）+ 模型登记（MLflow）+ 调用 trace（Langfuse）+ 网关门禁**——职责边界清晰：前两件管「资产是什么」，第三件管「发生了什么」，第四件管「能不能发生」。**运维代价**：4 个系统、至少 2 个团队、3 套身份体系需要打通（谁在哪个系统里是 Owner）；最大风险是「资产 ID 不互通」，导致 trace 里的模型版本号对不上模型登记里的版本号——这会让整条证据链在审计时断掉。**降低这一风险的办法是在项目一开始就定一个跨系统的 ID 规范**，而不是等出事后再对齐。
2. **GRC 平台 + 厂商原生治理能力**——边界：GRC 管「法规映射与证据归档」，厂商管「技术控制点」。**运维代价**：映射表必须人工维护，且云厂商的服务口径变更时映射表会滞后；适合法域多、需要外部审计的组织，不适合单一法域的中小团队。
3. **单一网关 + 全字段 trace（不做目录、不做 GRC）**——最小可用组合。**边界**：它只覆盖「运行时」这一层，管不了「资产台账」。**运维代价**极低（1 个系统），**代价**是在被监管问「你们共有多少个 AI 资产、分别用于什么用途」时答不出来——因此这个组合只在「无对外提供义务」的前提下成立。
4. **传统数据治理 + AI 资产扩充分类（不新建系统）**——把模型、Prompt、数据集当作目录里的新资产类型，复用已有的 Owner / 密级 / 血缘机制，只在被调用处加网关。**适用**：AI 资产数量少（几十到几百个）且有强数据治理基础的组织。**运维代价**：中（要教目录系统认识新资产类型）；**边界**：它覆盖不了调用级证据，需要与网关组合使用。

5. **自建最小治理层（网关 + 台账表 + 定期导出）**——不引入任何治理产品，用已有的 API 网关加一张资产台账表，配上定时导出脚本。**适用**：AI 资产在几十个以内、法域单一、暂无外部举证对象。**边界**：它靠流程而不是产品保证一致性，人员变动后容易失守；**运维代价**：前期极低，但**每次组织调整都要重新对齐一次**，这是一笔容易被忽略的长期成本。

**五种组合的运维代价对照**（量级为【经验】判断，依据是「需要常年维护的独立系统数」与「需要的专职角色数」）：

| 组合 | 独立系统数 | 需要的专职角色 | 主要长期负担 |
| --- | :---: | --- | --- |
| 元数据 + 模型登记 + trace + 网关 | 4 | 平台 / 应用 / 合规 3 类 | 跨系统 ID 对齐 |
| GRC + 厂商原生 | 2（+ 厂商黑盒） | 合规 / 平台 2 类 | 法规映射表维护 |
| 单一网关 + 全字段 trace | 1 | 平台 1 类 | 无资产台账，外部问询时无法回答 |
| 数据治理目录扩充 + 网关 | 2 | 数据治理 / 平台 2 类 | 目录系统改造成本、网关覆盖率 |
| 自建最小治理层 | 1（复用已有网关） | 无专职（兼做） | 组织调整后需重新对齐 |

**组合是可以演进的，但顺序有讲究**：合理的演进路径是「自建最小层 → 单一网关 + trace → 接入模型登记与元数据 → 按需加 GRC」，每一步都在补**一个**能力而不是换一次架构；不合理的路径是「先上 GRC 平台，再回头补 trace」——因为 GRC 要汇总的证据此时还不存在，平台会长期空转。判断处在哪一步的信号很简单：**如果你们现在还答不出「总共有多少个 AI 资产、分别在什么用途下被调用」，那就还在第一步，此时任何平台化投入都偏早。**

### 7.7 选错的代价与迁移成本

**反模式 1：把 AI 治理做成白皮书。** 症状：有原则、有委员会、有制度文档，但找不到「哪个系统在哪个环节检查哪个字段」。→ 后果：审计时拿不出证据链，只能临时人工整理，而临时整理出的材料恰恰证明平时没有控制点。→ 正确做法：**每条原则绑定一个可测指标 + 一个审核环节**；本书 §6 中微软 Responsible AI 的做法（六条原则各绑定可测指标与审核环节）就是这个模式的实例。

**反模式 2：治理单元选错——只审模型，不审调用。** 症状：模型准入流程很严（要评审、要签字），但 Prompt 是业务代码里的字符串、上下文随便拼、工具权限随手给。→ 后果：模型清单是干净的，线上行为是失控的；出事后发现「准入的是 A 版本的模型，但实际生效的是另一套 Prompt + 外部检索结果」。→ 正确做法：把控制点放在**统一网关**，让模型、Prompt、数据、输出四个面在**同一次调用**内串起来（本书 §6 阿里案例的做法）。

**反模式 3：只做内容护栏，不管动作授权。** 症状：投入大量精力做输入输出过滤，但 Agent 的写库 / 退款 / 外发权限是全开的。→ 后果：护栏拦住的是措辞，拦不住「以合规措辞执行了不该执行的动作」。→ 正确做法：区分「内容判定」与「授权判定」两层，**不可逆动作按可逆性而非概率设定人在回路**。

**反模式 4：把法规映射写死在代码里。** 症状：风险等级、保留期、需要留存的字段被硬编码进服务配置或代码常量。→ 后果：法规或口径一变就要发版，而发版周期长于合规窗口，于是「已知的不合规」被长期容忍。→ 正确做法：把「法规 → 控制点 → 字段」做成**配置化的映射表**，让合规变更走配置发布而不是代码发布；这条也是 GRC 平台存在的主要理由。

**反模式 5：把「治理覆盖率」当成一个可以声称的数字。** 症状：给出一份漂亮的覆盖率报表，但报表的分母（总共有多少个资产 / 多少条调用路径）来自各个团队自己上报。→ 后果：分母本身就是被治理的对象，用自报数据算覆盖率等于循环论证；被外部质疑时无法自证。→ 正确做法：覆盖率的分母必须来自**独立于业务的观测点**——对 LLM 场景就是网关侧的调用计数，对资产场景就是全量采集而非上报。**「100% 覆盖」只有在分母不依赖被覆盖者自报时才成立**，这也是本书 §6 各案例把能力收口到统一网关/统一平台的真正动机。

**「换成另一个」要动什么**：

| 迁移方向 | 数据迁移 | 查询 / 链改造 | 运维重建 | 团队再学习 | 量级 |
| --- | --- | --- | --- | --- | --- |
| 传统数据治理 → ML 治理 | 新增模型与数据集实体，表字段台账可复用 | 血缘需要延伸到训练作业 | 加一套产物存储与登记 | Model Card / 数据版本概念 | **小-中**（加一类资产） |
| ML 治理 → LLM 治理 | trace 是高写入流水线，与原有实体模型形态不同 | trace 与模型登记的 ID 必须打通 | 新增网关与判定链路（在线，不能离线补） | 采样参数 / 上下文 / 提示注入 | **中-大**（从登记制转拦截制） |
| LLM 治理 → Agent 治理 | 新增「会话 - 动作 - 授权」三元组 | 从调用级 trace 改为轨迹树 | 新增权限引擎与中断恢复 | 授权模型 / 人在回路设计 | **大**（台账模型换代） |
| 任一档 → 加 GRC 证据层 | 不动数据 | 需要把各控制点的证据统一格式导出 | 加映射表维护流程 | 法规条款与映射方法 | **中**（不改技术，改流程） |

（上表量级为【经验】判断，依据是「是否更换台账模型」：更换 = 大，新增一类实体 = 中，仅加字段 = 小。）

**五个反模式的共同根源只有一个**：把治理当成「事后补的材料」，而不是「运行路径上的一个环节」。凡是控制点不在运行路径上的方案，都会退化成白皮书；凡是把分母交给被治理者自报的方案，覆盖率都会退化成声称。**检验方法很简单**：问「如果这个团队明天全员离职，治理还在不在」。在，说明它是机制；不在，说明它是人。

**迁移中最容易低估的一项**：不是技术改造，而是**历史证据补不回来**。治理体系上线前的调用没有 trace，上线前的模型没有挂角色字段——这部分永远无法补齐。因此可行的做法是**给迁移设一个「证据起点日」**：起点日之后必须齐备，起点日之前只保留可获得的存量台账，并在对外材料里明确说明。试图把起点日之前的历史补成合规形态，成本极高且不可信。

**正确的迁移顺序是「先补字段，再换系统」**：因为台账的字段决定了你能不能被举证，而系统只是字段的承载者，所以先把字段（角色 / 用途 / 风险等级 / 版本 / 授权）定义清楚并让现有系统手工填报，再决定用什么平台承载。反过来先选平台再补字段，通常的结果是「平台能力很全，但我们的历史数据填不进去」。这条顺序也适用于同族内部的工具替换——**同族替换的代价几乎全在数据与 ID 规范上，而不在功能上**。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 无 AI 资产 | 传统数据治理 | 治理单元稳定可枚举，登记制成本最低 |
| 只有外部 API 调用 | LLM 治理（网关 + trace） | 单元运行时产生，只能拦截制；义务多在提供者侧 |
| 自训模型对外提供 | ML 治理 + AI Act 角色字段 | 义务按角色分配，角色字段不可缺 |
| 落地 EU 高风险用途 | 四档全上 + GRC | 高风险义务来自法规清单，非自定义阈值 |
| 有不可逆动作的 Agent | Agent 治理（授权 + 人在回路） | 单元是运行时动作，事后审计无法止损 |
| 集团多 BU 各自建设 | 统一下沉网关 + 集团口径 | 覆盖面要成为结构保证，而非流程保证 |
| 已有成熟数据治理体系 | 目录扩充 + 网关增补 | 复用已有 Owner / 密级机制，成本最低的增量路径 |
| 举证对象在组织外部 | 追加 GRC 证据层 | 外部审计问的是法规条款，不是日志 |
| 调用量预期一年涨 10 倍 | 优先压 trace 与护栏的线性成本 | 线性成本项是唯一会随规模失控的一项 |
| 只有内部实验、调用量极低 | 登记制（Prompt / 模型版本造册） | 单元产生速率低，拦截制的建设成本高于收益 |
| 审查发现「治理只在出事时才动」 | 把控制点搬进运行路径 | 控制点不在通路上，就只能追责不能止损 |

> 本节小结：四种治理的唯一决定性差异不是「自动化程度」，而是**治理单元在什么时刻产生**——表与模型在事先就存在，所以可以登记；调用与动作在运行时才存在，所以只能拦截。这条差异决定了工具链形态、审计字段长度与控制点位置，也是「逐步升级」这个直觉在 Agent 场景下失效的原因。
>
> **选型的第一句话**：先写下你的治理单元（表 / 模型版本 / 一次调用 / 一次动作），再写下这些单元一年后的数量级；这两个信息基本决定了你该用登记制还是拦截制、该不该上门禁、以及成本会往哪个方向走。
>
> 💡 **思考锚点**：整棵树唯一带数值的节点是「**月调用量 ≥ 3 亿次/月**」，它是按单次 trace 3 KB 的上限口径把 1 TB/月折算出来的。按你自己的字段口径反算一次：你的 trace 是接近 1 KB/次还是 3 KB/次，日调用量乘单次字节数落在哪个量级？低于这条线，采样省下的钱落在噪声里、不抵它损失的证据完整性；高于它，才轮到采样与分层。注意这条线只决定「怎么实现」，不改变 7.5 上半段由治理单元定的机制选择。
