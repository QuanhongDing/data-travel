## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

1. **机制变了**：保护对象或判定时点发生了结构变化（例如判定从"访问时"前移到"召回前"，保护对象从"字段"细化到"片段"）。**这类变化影响架构决策。**
2. **接口标准变了**：合规标准、密级标注格式、审计字段、密钥接口出现了跨组织约定（等保条款的修订、行业监管的实施细则、标注体系的标准化）。**这类变化影响"要准备哪些证据"。**
3. **只多了产品**：厂商把同一套能力包装成新名词（"数据安全大脑""AI 安全网关"）。**这类变化只在选型表里体现。**

判别方法仍然是那一句：**"换一家厂商，这条结论还成立吗？"**——不成立的是第 3 类。

**本主题的三类分布有一条特殊性**：**第 2 类（接口 / 标准变了）占比显著高于其他主题**——因为安全领域的"前沿"大量来自**监管与标准**（新施行日期、新增控制项、新的留痕要求），而不是来自技术。**这条观察的实用推论**：判断一个安全类"新方向"要不要跟，先问"**它改的是我的控制点，还是改的是我要提交的材料**"——改材料的（第 2 类）要跟且要快（有生效日期）；改控制点的（第 1 类）要想清楚再动。

### 5.2 判据与分级

沿用三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定、可预期**。

| 演进方向 | 级别 | 机制变了什么 | ① 正式条目 | ② 第三方生产案例 | ③ 接口稳定 |
| --- | --- | --- | --- | --- | --- |
| 判定前移（召回前裁剪） | **L2** | 从"取回后过滤"变成"把可见集下推为检索条件" | 成立（主流检索 / 向量库都有元数据过滤接口） | **核不到**（企业内部权限模型与召回实现极少公开） | 成立（过滤表达式是稳定接口） |
| 片段级脱敏与引用回指 | **L2** | 保护对象从"字段 / 文档"细化到"片段"，且引用要能指到片段 | 成立（检索与引用类接口普遍提供片段定位） | 核不到 | 部分成立（片段定义各家不同） |
| 输出端 DLP（含流式） | **L2** | 管控从"入向"扩展到"出向"，并要求覆盖流式分片 | 成立（DLP 类产品普遍有输出侧条目） | **核不到**（漏出率与误拦率几乎都来自建设方） | 部分成立（实体类型与判定口径各家不同） |
| 差分隐私的工程化 | **L2** | 从"研究性质"变成"有预算管理接口的组件" | 成立（隐私计算平台的正式功能条目） | 核不到 | 部分成立（`ε` 的口径与组合方式各异） |
| 机密计算 / TEE | **L2** | 把"信任宿主"这一前提用硬件隔离消掉 | 成立（主流云厂商有正式产品条目） | **核不到**（第三方对可信边界的验证材料稀缺） | 部分成立（远程证明的接口与格式在演进） |
| 同态加密的通用化 | **L3** | 从"特定运算"走向"通用计算" | 只有研究进展与专用方案 | 核不到 | 不成立（方案与参数差异过大） |
| 密级与策略的跨组织标准 | **L3** | 密级标注与策略表达出现跨组织通用格式 | 只有提案与行业讨论 | 核不到 | 不成立（无通行做法） |
| 国产化适配的算子级验收 | **L2** | 验收粒度从"能启动"细化到"关键算子 + 精度对照" | 成立（信创目录与适配清单为正式材料） | **核不到**（适配结果通常不公开） | 部分成立（清单会随产品版本更新） |

**本节没有一行达到 L1**——卡点全部在 ②：**数据安全的第三方生产案例几乎不可能公开**。这条空缺比其它主题更彻底，原因值得写下来：**安全配置的细节本身就是敏感信息**（公开"我们怎么防的"等于给出攻击面），而效果数据（漏出率、误拦率）又只在内部有意义。**因此本主题的成熟度判断必须换个方式**：**不看"别人用得怎么样"，看"我能不能自己证明它生效"**——这一条把证据形态从一个外部判据变成了内部判据，也解释了为什么本主题反复强调"演练"（§4.7）。

**怎么用这张表（三条动作）**：

- **有生效日期的（第 2 类）先跟**——监管实施细则、标准修订这类变化**有确定的截止时间**，晚跟的代价是"某个日期之后不合规"，而不是"效果差一点"。
- **对效果类主张保持要求证据的习惯**——DLP 的漏出率、DP 的可用性损失、TEE 的性能开销，公开数字全部不可移植。
- **L3 不进架构约束**——同态加密的通用化与跨组织密级标准都还没有通行做法；把它们写进架构约束，等于把一家的研究路线当成工程前提。

### 5.3 演进方向逐条拆解（核心节）

#### 5.3.1 判定前移：从"取回后过滤"到"下推为检索条件"

**机制**：权限判定从结果层移到**检索的输入条件**——可见集成为索引 / 引擎的过滤表达式，而不是返回后的筛选逻辑。

**证据到哪一步**：① 成立（主流检索与向量库都提供元数据过滤接口，这是稳定接口）；③ 成立；② 核不到。它是**第 1 类**（机制变了）——它改变的是"内容有没有被读出来"，因此值得进架构决策。

**它对架构决策的影响**：**它把"权限"从展示层的一行代码，变成检索层的一个必须传入的参数**。由此推出三件事：① 检索接口的签名里**必须有一个可见集参数**（没有它，实现者会自然地写成"取回后过滤"）；② 可见集必须来自**唯一权威源**（企业权限系统），否则出现第二个权限源（[Ch10 §04 §6.1](../../10-industry-agent/04-office-automation-agent/04-office-automation-agent-section-6-sec6.md) 已给出这一条的三种不一致形态）；③ **可见集为空的分支必须显式**（明确返回空，不允许回退为"不过滤"）。

**代价与边界**：① 下推的过滤会影响召回质量（可见集小时召回不足）——这是"正确但没用"的代价，**可以接受但必须被量出来**（否则会被误诊为"检索质量差"）；② 跨库引用的**可见性传染**要定义；③ 某些引擎的过滤能力有限（例如只能过滤标量元数据），需要在**索引期就把权限维度打进元数据**——这一步要提前设计，事后补不上。

**读者今天该做什么**：看一眼你的检索接口签名——**它有没有一个"可见集 / 过滤条件"参数**？没有的话，你的权限大概率是后置的。再用无权账号做一次请求，**去查这次请求的上下文构建日志或缓存**：无权内容出现在那里，就是后置过滤（用户看不到 ≠ 没读出来）。

#### 5.3.2 片段级脱敏与引用回指：保护对象继续细化

**机制**：保护与引用都细化到"片段"——脱敏可以在片段粒度上替换，引用（回指）能指到具体片段而不是整篇文档。

**证据到哪一步**：① 成立（检索与引用类接口普遍提供片段定位）；③ 部分成立（"片段"的切分方式各家不同）；② 核不到。**它是第 1 类**：保护对象的粒度变了。

**它对架构决策的影响**：**它同时改善了安全与可信两件事，而这两件事在其它方案里常常是冲突的**——更细的脱敏粒度意味着下游可用性下降（§4.6 的取舍），但**如果脱敏的载体恰好是"引用片段"，那么它同时把"用户能不能验证"这件事做成了**（[Ch10 §02 §3.2.6](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的引用回指）。**这条合流的实践含义**：**在 RAG 场景里，脱敏与引用应当是同一套片段映射的两种用法**——建一次映射，既用于"哪一段能给他看"，也用于"哪一段支持了这条结论"。分两次做，就会出现"脱敏后的文本与引用指向的原文对不上"。

**代价与边界**：① **片段映射的存储与一致性代价**（文档更新后映射要重建，否则引用指向旧片段）；② 片段级脱敏的**语义破坏**风险（截断在句子中间会改变含义）；③ 片段定义要统一（按句 / 按段 / 按语义块，口径不同则安全与引用两侧对不上）。

**读者今天该做什么**：核对一次"脱敏后的内容"与"引用指向的片段"是否同源——**如果它们来自两条流水线，就存在一处改了一处没改的必然风险**。

#### 5.3.3 输出端 DLP：管控从入向扩展到出向

**机制**：在生成输出上做敏感实体识别与策略判定，并对**流式输出**做滑窗处理。

**证据到哪一步**：① 成立；③ 部分成立（实体类型与判定口径各家不同）；② 核不到——**漏出率与误拦率几乎全部来自建设方自述，而这恰好是判断 DLP 有没有用的两个唯一指标**。

**它对架构决策的影响**：它把"泄露"从**一次动作**（把数据发出去）变成**一条链路**（数据进上下文 → 被复述 → 进输出 → 进缓存 / 日志）。**因此 DLP 的落点不是一个，而是一组**（§4.2（1）的位置清单）。这条影响对架构的实质要求是：**输出路径上必须有一个可插入判定点的位置**——如果生成是端到端不可插入的（例如厂商托管端点直接返回给用户），那么出向 DLP 在架构上就无处可放，**此时唯一的选择是把判定移到客户端侧或代理侧**，而那通常是选型阶段就该发现的事。

**代价与边界**：① **误拦与漏出的取舍**（§2.2 的两个式子：误拦随召回上升、漏出随召回下降）；② **流式分片**（滑窗拼接，延迟与漏检的取舍，§4.2（4））；③ **覆盖缓存与日志**会把检测点从一处扩成三处，**运维面随之扩大**（每一处都要有 owner，否则会出现"三处里有两处没人管"）。

**读者今天该做什么**：写一条测试用例——把一个身份证号**跨两个流式分片**发送，看它是否被检出。**这条用例能同时暴露两件事**：你有没有覆盖流式、以及你的滑窗存不存在。

#### 5.3.4 机密计算 / TEE：把"信任宿主"这个前提消掉

**机制**：用硬件隔离（可信执行环境）保证**连宿主 / 云厂商都无法读到内存中的明文**，并提供远程证明（remote attestation）让你能验证"跑在里面的确实是那段代码"。

**证据到哪一步**：① 成立（主流云厂商有正式产品条目）；③ 部分成立（远程证明的接口与格式在演进）；② **核不到**——**第三方对"可信边界是否真的成立"的验证材料非常稀缺**，而这恰恰是这一方向的关键：**它的价值全部押在"硬件隔离真的成立"上**。

**它对架构决策的影响**：它把"数据不离开你的信任域"这条要求，**从"靠部署形态保证"改成"靠硬件保证"**——于是"能用公有云吗"这个问题多了一个答案：**数据可以放在云上，但只在 TEE 内解密计算**。**这条对受监管行业的含义是**：过去必须私有化的场景里，有一部分（尤其是"算力需求大、但数据只是过路"的场景）**多了一个可选项**。

**代价与边界（三条都要提前量）**：① **可信边界的范围是有限的**——TEE 保护的是**内存中的计算**，不保护 I/O 边界之外的东西（进出 TEE 的数据谁来管、日志写在哪里、模型权重从哪加载），**因此"用了 TEE"不等于"全链路可信"**；② **远程证明是这套机制的使用前提**——不做证明，你只是"相信云厂商的话"；③ **性能与生态**（可用内存上限、系统调用受限、部分库不可用）。

**读者今天该做什么**：如果你的合规要求是"数据不外流"而算力需求又把私有化逼到成本极限——先回答一个问题：**我要保护的是"数据存哪"，还是"计算在哪发生"？** 这两个问题的答案不同，TEE 只解决后者。

#### 5.3.5 差分隐私的工程化：从研究性质到有预算管理的组件

**机制**：把 `ε` 从论文参数变成**有接口、有累计、有拒绝逻辑的运行时预算**。

**证据到哪一步**：① 成立；③ 部分成立（`ε` 的口径与组合方式各家不同）；② 核不到。**它是第 1 类（机制变了）还是第 2 类（接口标准变了）**？——**是第 1 类**：它让"隐私"第一次有了可外部审查的量化性质（§3.2.3），这改变的是保护方式本身。

**它对架构决策的影响**：**它把"查询次数"变成了一个需要被管理的资源**——这一点会反向改变产品设计：默认"看板每次刷新都发一次查询"这类行为，在 DP 下等于持续消耗预算。**因此引入 DP 通常伴随着一次产品侧的改造**（查询合并、预计算、缓存），而**这次改造的规模往往大于 DP 本身**。

**代价与边界**：① 可用性随 `ε` 下降（这是它的工作方式）；② **必须累计预算**（不累计等于没有保护，这是组合定理的直接推论）；③ **只对聚合输出有意义**（把 DP 用在行级查询上是用法错误，§3.2.3 的失效点）。

**读者今天该做什么**：如果你的场景是"对外提供统计"，先量两个数——**查询的分布**（谁在查、多频繁）与**最小可读的 `ε`**（再小就看不出趋势了）。**这两个数决定 DP 能不能用**；只有一个"我们要做差分隐私"的想法，是没法开始的。

#### 5.3.6 国产化适配的算子级验收：验收粒度的细化

**机制**：验收从"安装成功 / 能启动"细化到"**关键算子逐个跑通 + 精度对照**"。

**证据到哪一步**：① 成立（信创目录与适配清单是正式材料）；③ 部分成立（清单随产品版本更新）；② 核不到（适配结果通常不公开）。**它是第 2 类**（验收标准变了），不是机制变了。

**它对架构决策的影响**：**它把"适配"从交付阶段的一件事，变成了设计阶段的一个约束**——因为**逐算子验收要求你能枚举"哪些算子在关键路径上"**，而这份枚举依赖于**你对自身架构的了解**（不能由客户或厂商提供）。**实践含义**：在设计期就维护一份"关键算子清单"（向量检索内核、量化推理内核、压缩 / 加密库、Python 扩展），并让它可以被逐个替换与验证；否则交付时会发现某些算子的替代方案不存在，而那时改架构的成本最高。

**代价与边界**：① **成本按算子数计**（不是按系统数）；② **精度差异必须逐算子记录并给出结论**（可接受的写进验收项，不可解释的写进"不支持清单"并进合同）；③ **清单会随产品版本漂移**，需要定期复核。

**读者今天该做什么**：列出你的关键算子清单，逐个标注"国产替代方案是否存在"——**"不存在"的那几项，就是你交付时的风险点**，而不是等到客户现场才发现。

**这张表的读法**：**接口的两端都必须有交接物**，只有"我们对齐了"而没有具体产物的，是没对齐。上表右列的每一项都是**可以今天就检查是否存在**的东西——例如"检索接口是否有可见集参数"，检查方法就是打开接口签名看一眼。

### 5.5 被过度宣传的部分

1. **"上了 DLP 就防住了泄露"**：DLP 的有效性取决于**它的检测点覆盖了哪些位置**（§4.2（1）），而市面上多数产品的检测点集中在流量入口。**可核查的判据**：把它的检测点与你的十三个位置清单对一遍，**数一数它覆盖了几个**。
2. **"脱敏了就安全了"**：脱敏只处理**显式字段**，而重识别靠的是**准标识符组合**（年 + 地区 + 性别 + 入职年份）。**判据**：做一次重识别演练——**不做这一步，"脱敏"就只是一个未经检验的动作**。
3. **"用了 TEE 就全链路可信"**：TEE 保护的是内存中的计算，**不保护进出它的数据、日志与权重加载路径**；且不做远程证明时，你只是相信云厂商的话。
4. **"差分隐私可以随便查"**：有预算才叫 DP。**不累计预算的 DP 接口，等价于没有保护**——这是组合定理的直接推论，不是实现细节。
5. **"我们用了国产数据库，所以完成了信创适配"**：适配是**从芯片到权重的一条链**，任何一环仍是外部依赖，整条链的验收都不成立。

### 5.6 未来 3–5 年：可证伪的预测

每条都给出**被证伪的信号**（出现即说明判断错了）：

| 预测 | 被证伪的信号 |
| --- | --- |
| "判定前移"会成为检索 / RAG 的默认设计（可见集是检索接口的必填参数） | 两年后主流检索客户端仍以"取回后过滤"为默认范例，且接口签名里没有可见集参数 |
| 输出端检测会与输入检测合并成一套双端策略（而不是两个产品） | 主流方案仍把入向与出向做成两个独立产品，各自维护实体与策略 |
| 片段级脱敏与引用回指会合流成同一套片段映射 | 主流实现仍把脱敏与引用做成两条流水线，且两者指向的片段口径不同 |
| 机密计算的采用会受"远程证明能不能被业务方独立验证"制约，而不是受性能制约 | 主流方案在业务侧不做远程证明即可上线，且性能成为唯一的选型依据 |
| 等保类合规材料会越来越依赖"持续证据"（定期演练留痕），而不是一次性文档 | 测评 / 审查仍接受一次性提交的材料，不要求持续性证据 |

**这五条全部是【经验】档**：它们是对机制与监管行为的判断，无具名出处、无推导链——**请按"可被证伪"使用，而不是当结论**。

**怎么用这份预测表**：不要用它做技术选型，用它做**反向检查**——每隔半年回来看一次"被证伪的信号"有没有出现。**最后一条尤其值得盯**：如果"持续证据"成为常态，那么**演练留痕的价值会超过任何一次性材料**，而这件事今天就能开始做（成本很低）；反过来，如果它没有发生，你做过的演练也没有浪费——它是你自己判断机制是否生效的唯一手段。

### 5.7 给架构师的行动建议

1. **今年就该做**：暴露面位置清单（半天）+ 权限判定前移 + 每个机制的"十分钟演练"（§4.1 的 Step 1–3、Step 5）。这三件都不依赖任何前沿判断，且是其余所有能力的靶点。
2. **可以试点（每条自带退出条件）**：输出端 DLP（退出条件：误拦率无法降到业务可接受，或覆盖不到缓存与日志）；差分隐私（退出条件：查询分布不支持预算管理，或最小可读 `ε` 已看不出趋势）；机密计算（退出条件：业务侧无法独立验证远程证明）。
3. **先别投**：同态加密的通用化、跨组织密级标准。等出现可比较的通行做法，再投入。
4. **无论哪条**：把"**每一条安全要求对应一次十分钟演练**"作为这一块的第一条 KPI——它同时是机制有效性、证据完备性与合规准备度的共同语言。
5. **一条反直觉的**：**先做"关掉演练"，再做"加固演练"**——安全体系的第一类风险不是"防不住"，而是"**某个判定机制挂了之后系统会降级为放行**"（§4.7）。**凡是判定类机制，不可用时必须失败关闭**；这条不成立时，后面的加固都是在放大一个"会自己打开的门"。

### 5.8 小结

> 本节小结：AI 时代对安全机制改变**只有一条是机制性的**——**判定的时点在提前**（入库后 → 访问时 → 召回前 → 输出前），保护对象在细化（系统 → 字段 → 行 → 片段）；其余方向（输出端 DLP、机密计算、DP 工程化、国产化粒度）都是在这条之上的加固与接口变化。**本主题的三类前沿里第 2 类（标准 / 接口变了）占比高于其他主题**——因为安全领域的"前沿"大量来自监管与标准，**这类变化要跟且要快**（有生效日期）。本节没有一行达到 L1，且卡点在 ② 上比其他主题更彻底：**安全配置的细节本身就是敏感信息**，因此成熟度判断在这里必须换成内部判据——**不看别人用得怎么样，看我能不能自己证明它生效**。**给读者的动作**：先画暴露面清单、把权限判定前移、给每条要求配一次十分钟演练；然后才谈 DLP 与机密计算。

> 💡 **思考锚点**：把你的检索 / 问答接口签名打开看一眼——**可见集是它的参数，还是在它的调用者那里做的一次过滤？** 如果是后者，做一件事：用一个**无权账号**请求一段它无权看的内容，然后去翻这次请求的上下文构建日志与缓存——**无权内容出现在那里了吗**？这个答案决定你现在的第一优先级是"把判定前移"，还是"补输出端检测"——你打算先做哪一个？
