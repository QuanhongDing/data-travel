## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研安全能力 / 平台内置 / 专用安全网关 / 商业 DLP / 云原生安全服务 / 咨询 + 自建合规材料"打分是常见做法，但它有三个结构性问题：

① **同一列在不同处境下方向相反**——"检测点可扩展"对一个已有成熟网关的团队是必需（它能在既有链路上挂点），对一个刚起步的团队是浪费（它还没有链路可挂）。
② **打分表隐含"这些选项互斥"**，而真实的做法是组合（**数据侧用引擎内置、在线路径用代理、合规材料自建**是常见组合）。
③ **最关键的判据不是可打分的维度，而是门槛**——**"检测点能不能覆盖到你的暴露面清单"**与**"策略能不能下推"**这两条是门槛：不满足就直接出局，给多少分都没意义。

**本节采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| **暴露面覆盖** | 它的检测点能挂在哪几个位置？你清单上的十三个位置它能覆盖几个？ | **这是门槛不是权重**——覆盖不到的位置，无论产品多强都是空的 |
| **判定可下推性** | 策略能不能编译成检索 / 查询引擎能吃的过滤条件？ | 不能下推 → 权限只能后置 → 在原理上做不到"不读出来" |
| **密钥 / 权限的分离度** | 密钥操作的权限能不能授予与数据管理员不同的人？ | 不能分离 → 加密不构成访问控制点（§6.2） |
| **证据产出能力** | 它天然产出哪些证据（拒绝日志 / 对账 / 演练接口）？ | 机制不产出证据 → 合规时无法举证（§6.3） |
| **可移植性与锁定** | 策略与证据能不能导出？换掉它要重写多少？ | 安全能力的迁移成本通常高于技术组件（策略与历史证据最难迁） |
| **运维承接** | 谁维护策略、谁做抽检与演练？ | 本主题的成本是人力为主（§4.6），**没有承接人的方案会在半年后失效** |

**这 6 条里，前两条是门槛（不满足直接出局），后四条是权重的输入。**

**六条的使用顺序**：先答 1、2——它们问的是"覆盖不到的位置"与"下推不了的条件"，答不上来时后面四条不必看，因为不满足门槛的候选给多少分都要出局；再答 3、4——这两条决定"要不要按族叠加"（密钥归属决定吊销时间，证据归属决定哪一族不可能外包）；最后答 5、6——可移植性与运维承接是权重，它们只在候选之间排队，不淘汰候选。**最容易被跳过的是第 1 条与第 6 条**：第 1 条容易被读成"我们买了覆盖很广的产品"，而它问的是"你清单上的十三个位置，它挂在几个"（§4.2（1）给的是那张清单）；第 6 条容易被读成"团队能不能接住"，而它问的是"**谁做抽检与演练、多久做一次**"——本主题的成本是人力为主、且随"管的东西变多"增长（§4.6），没有承接人的方案会在半年后失效，而且失效时没有任何告警。

**关于排序**：本节不给出"哪个候选更好"的排序，只给出可比较的位置——§7.6 的矩阵每行带"不选它的原因"列，§7.4 给的是可以代入自己参数的式子而不是一张分数表。**凡是要给顺序的地方，都由机制给出依据；给不出依据的顺序，就是把场景相关的结论写成了绝对结论**。本主题还有一条与其它主题不同的限制：安全能力的效果数据（漏出率、误拦率、第三方生产案例）在本书的判据体系里系统性地拿不到——§5.2 那张八行的分级表里，判据②（第三方非厂商的公开生产案例）逐行都是"核不到"（§5.2、§5.3.1–§5.3.6）。因此**本节能排的是机制与成本形状，不能排的是"哪一家效果更好"**；把效果层也排成顺序，就是把别处主题的口径硬套到本主题头上。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| **引擎 / 平台内置** | 复用既有能力 | 数据库的列掩码 / 视图 / 行级安全策略；数据平台自带的权限与脱敏 | 已有成熟数据平台的团队 | 能力受引擎限制；跨引擎不一致；**部分引擎不支持把策略下推到检索** |
| **专用数据安全网关 / 代理** | 在线路径的判定点 | 在查询 / 检索路径上做代理，改写与判定都在这一层 | 多引擎、需要统一策略的团队 | 多一跳；**代理能否被绕过是唯一重要的问题** |
| **商业 DLP / 隐私计算平台** | 输出端与重武器 | 敏感实体识别 + 策略 + 动作（含 DP / TEE 等） | 合规压力大、需要现成材料的团队 | **检测点通常集中在少数位置**（多为流量入口）；实体口径与你的业务不完全对齐 |
| **云原生安全服务（KMS / HSM / IAM）** | 密钥与身份的底座 | 密钥操作独立授权、轮换与吊销是产品级接口 | 已在云上的团队 | 绑定云厂商；跨云一致性与可移植性受限 |
| **全自研** | 控制力最强 | 自建策略引擎 + 判定下推 + 证据采集 | 安全即核心竞争力、或监管要求极高 | **策略维护是常备人力**（§4.6）；短期投入最大 |
| **咨询 + 自建合规材料** | 举证路径 | 咨询给方法，材料自己维护（控制项映射表 → 控制点） | 要过测评 / 客户审查的团队 | 咨询产出的是方法而非能力；**材料必须有人持续维护** |

**这六个候选其实分三族**：

- **机制族**（引擎内置、安全网关、云原生服务）——**解决"判定在哪发生"**，它们的差别是判定点的位置与可下推性。
- **重武器族**（DLP / 隐私计算平台）——**解决"检测与计算在哪发生"**，它们的价值集中在少数需要专门能力的场景（输出端识别、密文计算）。
- **证据族**（咨询 + 自建材料）——**解决"怎么被承认"**，它的产出物是文档与演练记录，**不产生新的技术能力**。

**族内可替换，跨族不可换**：机制族之间换，动的是判定点的位置；从机制族换到重武器族，**不是替换而是叠加**（两者解的题不同）；而**证据族不能被任何一族替代**——测评方要的是映射表与演练记录，没有产品会替你产出它们。

**表里最后一列（主要代价）常被当成采购问题，其实它是机制问题**：你问的不是"贵不贵"，而是**"计价口径与我的增长方式是否同向"**。机制族的许可与人力按资源数走，而资源数正好就是你在涨的那个量（表 / 文档 / 片段），两者同向，所以它的账单会跟着业务一起长大；证据族的成本按"标准数 × 系统数"走，**它与数据量无关，只与你做了多少件事有关**——因此在"系统数不减、每年来一套新标准"的组织里，这一族会显得越来越贵（§7.4 把它写成三族里唯一会乘积增长的一族）。判断方法是把供应商公开的计价维度与 §7.4 表里"成本随什么增长"那一列并排看——**这两列一旦反向，采购就会变成长期成本陷阱**。

**这张表的读法**：先读第二列（定位）与第四列（典型使用者）判断"它解的是不是我的题"；再读第三列（核心机制）与第五列（主要代价）判断"我接不接得住它的代价"。**定位相同、机制不同才是可比较的候选**——例如"专用安全网关"与"引擎内置"都在机制族、都在解"判定在哪发生"，因此它们之间可以互相替换、可以比较；而"商业 DLP"与"机制族"解的是两道不同的题（一个管内容、一个管元数据），放在同一行比较会得出"DLP 不能做权限"这类其实不是缺陷的结论（§7.3.2）。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 判定点的位置：在引擎里、在代理里，还是在别人的服务里

**机制是什么**：判定只能发生在三个位置——**引擎内**（数据库 / 检索 / 向量库自己执行策略）、**代理层**（请求经过的一个独立组件）、**外部服务**（云厂商的 IAM / 策略服务）。

**它在各候选中的实现差异**：引擎内置的判定**离数据最近**（可以下推到扫描层，效率最高），但受引擎能力限制、且跨引擎不统一；代理层的判定**统一但多一跳**，且**它的有效性完全取决于"能不能被绕过"**；外部服务的判定**最统一、最可审计**，但引入跨域调用（延迟与可用性都受外部影响，且**它一挂，判定就没了**——§4.7 的"失败关闭"在这里是关键）。

| 候选族 | 判定的入口在哪 | 谁决定"这一次能不能看" | 典型失败形态 |
| --- | --- | --- | --- |
| **引擎内置**（列掩码 / 视图 / 行级策略） | 执行计划里，扫描之前 | 引擎自己解析的策略 | **跨引擎口径不一致**：同一个角色在两个引擎里看到的行不一样，而两边都"配置正确" |
| **代理层**（安全网关 / 查询代理） | 请求进入执行引擎之前 | 代理侧的一份策略副本 | **存在第二条取数路径**，判定被整条绕过；代理与底层库的访问数对不上 |
| **外部服务**（云 IAM / 策略中心） | 数据通路之外 | 外部服务的策略与其可用性 | 外部服务不可用时，判定要么全放行、要么全拒绝——**这个方向必须提前定，不能等故障时才定** |
| **全自研** | 由你决定放在哪 | 你自己的策略引擎 | 落地成"每个应用各写一遍过滤"，没有唯一权威源；改一条策略要改多处 |

**由此必然导出的性质**：因为**"不可绕过"比"判定得更准"重要**，所以**判定点的选择首先是"唯一性"问题**——三个位置都做，等于三处都可能不一致；只做一个而不管旁路，等于没有。**这条性质解释了一个常见的误判**：团队常按"谁的策略表达能力强"选判定点，而真正的判据是**"我怎么证明没有第二条路径"**。

还有一条与位置连在一起、但常被当成实现细节的性质：**判定点的位置决定了它的"输入身份"是什么**。引擎内置与代理层拿到的身份来自请求本身，因此当请求是服务代调用时，判定用的主语默认是**服务身份**（一个为了跨租户取数而权限很宽的身份），而不是**人的身份**——此时无论判定点做得多好，**判定都按最宽的那个身份放行**（§4.2（3）把"带 `on_behalf_of`（或等价的委托凭证）"写成硬要求）。这条性质解释了一个反直觉的观察：某些团队把判定从应用层"下沉"到引擎之后，越权反而变多了——不是下沉错了，而是下沉过程中**把人的身份换成了服务的身份**。同理，判定点越靠后（代理层、外部服务），它能拿到的上下文越多（可以同时看到调用者、对象、用途），但**它离"读出来"这个动作也越近**，而"读出来"是不可逆的。

**公开证据**：本主题内可核的锚点有三处——§4.3 的「权限」一行把选型要点写成判据而不是功能列表（"看**是否支持把判定下推**到召回条件"）；§4.2（3）给出身份链的硬要求与它的判据（"审计记录里能否回答这条数据是**谁**（具体到人）触发的访问"，只能回答"哪个 Agent / 哪个服务"说明身份链是断的）；§4.7 的失效形态表把"判定类失败必须关闭"列为纪律。【公开】（来源：本主题 §4.2（3）、§4.3、§4.7，可逐行核对）。全书他处已具名的同类实现都在查询引擎与网关侧：Apache Ranger 把行过滤与列掩码做成策略类型、Oracle Data Redaction 做查询期脱敏、阿里云 DAS 做数据库审计与安全管控（`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` 的 §3.2.4「真实使用」条目）；Trino 的 row-level security 与 Ranger / Open Policy Agent 集成（`04-data-assetization/09-unified-query-gateway/09-unified-query-gateway-section-8-sec8.md`）；阿里 DataWorks 数据 API 网关把行级权限做成网关的默认行为（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-6-sec6.md`，记为 2016-2024，**属建设方自述，不构成本书 §5 判据②要求的第三方生产案例**）；与之对照的是同一族里明确不支持行级过滤与动态脱敏的实现（Apache Sentry，见 `11-cross-cutting/02-data-security/02-data-security-section-8-5-2-ranger-sentry-权限管理基础.md`）——这说明"支持行级判定"是这一族内部**可分辨的能力差异**，不是名词差异。**本节核不到**的是"本场景的实现"：RAG / 向量检索侧的召回前判定，本书 §5.2 对它的判据②写作"核不到"、理由是"企业内部权限模型与召回实现极少公开"（§5.2、§5.3.1）。**因此本节不具名任何一家的 RAG 检索实现**，能指的只有同类机制的异地实现——**这个区分必须写进句子里，不能省成"某检索产品这样做"**。读者可自测的判定入口：先看检索 / 查询接口的签名里有没有可见集参数，再列一遍"不经过这个判定点还能取到数的路径"——列不出来的位置就是当前的安全边界。

**失效条件**：当存在**直连底层存储 / 引擎的路径**时，任何代理层或外部服务的判定都被旁路——此时唯一的修法是**收口访问路径**（同 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md)），而不是把策略写得更严。还有一条并列的失效条件：当**平台上有多个"权威"权限源**（例如平台自建一份、业务系统各有一份）时，位置选得再对也不成立——判定点的唯一性要求**输入的唯一性**必须先满足（§7.2 的"族内可替换"只在这一点成立时才谈得上）。

#### 7.3.2 策略的可下推性：条件，还是过滤

**机制是什么**：策略的产物是**一个判定条件**（可以编译进查询 / 检索的参数），还是**一个结果过滤器**（拿回数据后再筛）。

**它在各候选中的实现差异**：引擎内置通常提供真正的下推（行级安全策略会成为执行计划的一部分）；代理层能否下推取决于它与后端的协议（能改写查询就能下推，只能转发就只能过滤）；DLP 类产品大多工作在**内容层**（拿到内容才能识别实体），因此**它们在原理上是"后置"的**——这不是产品缺陷，而是它的检测对象决定的。

| 候选族 | 策略的产物是什么 | 能不能成为引擎的执行条件 | 判定的对象 |
| --- | --- | --- | --- |
| **引擎内置** | 行级策略、列掩码规则 | 通常能——它成为执行计划的一部分 | **元数据**（谁能看什么） |
| **代理层** | 改写后的查询 / 检索请求 | 取决于协议：能改写就能下推，只能转发就只能过滤 | 元数据 |
| **DLP / 内容检测** | 一段内容上有没有敏感实体的判定 | **不能**——它必须先拿到内容 | **内容**（这段文本里有什么） |
| **隐私计算（DP）** | 加噪后的聚合结果 | 不适用——它作用在输出的统计量上 | **统计输出**（个体能不能被推断） |

**由此必然导出的性质**：因为**DLP 的检测对象是"内容"，而权限的判定对象是"元数据"**，所以**这两件事在链路里的位置天然不同**：判定（元数据）可以前置到召回前，检测（内容）只能发生在内容生成之后。**这条性质给出一个清晰的分工**：**前置判定负责"不该给的别给"，后置检测负责"给出去的别是敏感的"**——两者不可互相替代，也不该混在一个组件里实现。

还有两条由"判定对象不同"直接导出的性质。第一，**可下推性不是"高级功能"，而是"同一件事能不能只做一次"**：判定若能编译成引擎条件，则"权限"与"查询"共用一次扫描，成本不随查询次数增长；判定若只能后置，则每一次查询都要额外取回全量数据再筛，**成本随查询次数线性增长，且暴露面按查询次数累积**——同一条策略，两种实现方式在账单与风险上都是两条不同的曲线。第二，**可下推性有"能力上限"，而这个上限体现在召回质量上**：当可见集很小时，下推的过滤条件会把候选集压得很小，检索质量随之下降（这是"正确但没用"的代价，§5.3.1 把它列为判定前移的第一条代价）。因此可下推性的正确判据不是"支持不支持"，而是**"支持到什么粒度"**：能在行级与片段级下推的，才能既做对又不把召回压垮；只能做表级或库级的，实际上是在"安全"与"可用"之间二选一。

**公开证据**：本主题内可核的锚点有四处——§4.3 的「DLP」一行把选型要点写成"看**能否覆盖缓存和日志**、流式滑窗"（位置清单而非功能清单），§4.3 的「权限」一行写成"看**是否支持把判定下推**到召回条件"；§4.5 模板 2 把"前置"写成**可见的设计**（`index.search(query, filter=visible)`，并注明"把 filter 参数去掉，上述任何一条断言都会破"）；§2.3 ⑤ 把输出的三道闸写成"实体识别 → 策略判定 → 动作（拦 / 脱敏 / 二次确认 / 放行留痕），三道都要留痕"；§4.2（4）给出流式分片的三种处理方式与各自代价（缓冲后再检 / 滑窗拼接 / 只检完整段）。【公开】（来源：本主题 §2.3 ⑤、§4.2（4）、§4.3、§4.5 模板 2，可逐行核对）。全书他处已具名的两侧实现：下推一侧是阿里 DataWorks 数据 API 网关的编译期注入（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-6-sec6.md`，判据是"越权在引擎层就不产生数据"，**属建设方自述**）与 Trino 的 row-level security + Ranger / OPA 集成（`04-data-assetization/09-unified-query-gateway/09-unified-query-gateway-section-8-sec8.md`）；脱敏一侧是 Apache ShardingSphere 的数据脱敏（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-4-sec4.md`，该处自注"具体配置项以其官方文档当前版本为准"）；内容检测一侧可指名的识别实现是 Amazon Macie / Google Cloud DLP / 阿里云敏感数据保护（`04-data-assetization/06-one-service/06-one-service-section-8-17-7-数据架构与-ai-ml-集成.md`）与开源侧的 Presidio（`04-data-assetization/08-data-catalog/08-data-catalog-section-5-ai.md`，该处指出它公开列出了支持的实体类型与置信度机制，可自行核验覆盖面）；DLP 产品一侧的具名条目与两条纳入试点的判据见 `11-cross-cutting/02-data-security/02-data-security-section-4-sec4.md`（Netskope / Microsoft Purview DLP / Symantec DLP / 阿里云数据安全网关 / 字节 DataGPT 安全网关；AI 场景新工具的 Nightfall AI / Microsoft Purview AI Hub / Harmonic Security / Skyflow / Privately.ai / Confident Security），两条判据是"**判定输入是内容还是对象**"与"**不可判定时默认拒绝还是放行**"——**这两条正是本节分工的可操作形态**。**本节核不到**的是效果层：漏出率与误拦率这两个判断内容检测有没有用的唯一指标，几乎全部来自建设方自述，可复核口径核不到（§5.2、§5.3.3）——因此这里给不出"某产品拦住了多少"这类数字，只能给位置与判据。

**失效条件**：当团队用 DLP 去实现"权限"时（例如靠检测输出里有没有敏感内容来防止越权），会出现两个问题：**已经读出来了**（暴露面已存在）、以及**误拦与漏出同时存在**（因为内容检测没有身份信息）。**判据**：权限问题是否被交回给有身份的判定层——没有，说明这两件事被混在了一起。

#### 7.3.3 密钥的归属：谁拿着钥匙

**机制是什么**：密钥由**你持有**（自建 KMS / HSM）、由**云厂商持有但权限分离**（云 KMS / HSM）、还是**在集成方手里**（把密钥交给安全产品）。

| 密钥在哪里 | 谁持有它 | 吊销是一次什么动作 | 谁能阻止轮换 | 典型失败形态 |
| --- | --- | --- | --- | --- |
| **自建 KMS / HSM** | 你 | 改配置 | 你（因此要靠职责分离来约束自己） | 备份与恢复没演练过，真要恢复时发现备份也解不开 |
| **云 KMS / HSM（权限分离）** | 云厂商托管，权限归你 | 改配置 | 你，但受云厂商的接口与配额约束 | 跨云一致性差；换云时密钥不可迁移 |
| **应用侧持有**（配置 / 环境变量） | 每个部署实例 | 一次发布 | 每一个持有它的组件的负责人 | "吊销"退化为"等所有实例重启"，**止损与被动的发布周期同长** |
| **集成方持有**（交给安全产品） | 外部方 | 协调第三方 | **对方** | 你失去了独立的止损能力——**对方是唯一的执行者** |
| **与数据同一套权限**（反例） | 数据管理员 | 改配置（形式上有） | 数据管理员 | 能读数据的人能读密钥，**加密退化为一次编码** |

**为什么这是一个机制差异而不是商务差异**：因为**它直接决定"吊销要多久"**（§6.2）：你自己持有密钥时，吊销是改配置（秒级）；密钥在集成方手里时，吊销要协调第三方（小时到天级）。**而密钥泄漏的损失与处理时间线性相关**——它是一道正在流血的口子。

**另一层机制差异是"谁能阻止轮换"**：密钥的所有权决定了**轮换的执行者**。如果持有密钥的人也能拒绝轮换，那么"吊销能力"在组织层面是不可执行的——**这不是技术问题，是职责分离问题**（§6.2 的核心）。

**代价与边界**：自建 KMS / HSM 的代价是运维与合规（HSM 的采购、密钥备份与恢复演练）；云 KMS 的代价是绑定与跨云一致性；**把密钥交给集成方**的代价最隐蔽——**你失去了独立的止损能力**（对方是唯一的执行者）。

**由上表导出的两条性质**。第一条：表里"吊销是一次什么动作"与"谁能阻止轮换"这两列**是正交的**——前者决定**止不止得住**，后者决定**能不能执行得下去**。因此一个团队完全可能同时具备"秒级吊销的接口"与"没有人有权执行轮换"这两个状态，而这两件事在年度报告里都会被写成"已支持密钥轮换"。第二条：这四行之间的差别**不是能力差别，是拓扑差别**——同一套 KMS 产品，密钥放在服务侧还是放在每个应用实例的配置里，吊销所需的时间完全不同（§6.2 把它写成"纯结构差异，与运维水平无关"）。这条性质决定了一件很实际的事：**"要不要上收密钥"这个决定不能靠压测或选型比较得出，只能靠清点"谁持有它"得出**——所以它是本主题里少数几个"清点即结论"的问题。

**公开证据**：本主题内可核的锚点是 §6.2（微软，2019-2024）：它给出的量都是形态量而不是数字量——吊销在服务侧是一改配置（秒级）、在应用侧是一次发布（小时到天级）【经验：随发布方式与实例数浮动】；轮换成本随"持有该密钥的组件数"增长【经验】；可核查的判据是"**一个只用数据权限、没有密钥权限的账号，能否通过正常路径读出明文**"。第二条印证是 §6.1（阿里，2019-2024）——它把"权限收敛"列为收益项，与密钥侧同属"清点即结论"的动作。第三条是 §4.7 的失效形态表：它把"密钥服务失效"与"审计写入失败"分开列，并把"判定类失败关闭、证据类告警"写成纪律——**密钥服务属于判定类**。§7.7 另给出两条迁移代价的量级：密钥交给集成方、再迁回自持，**以季度计，且迁回期间无独立止损能力**；密钥与数据同权限、再拆成两条线，**以月计，存量授权收敛是主要工作量**【经验】。【公开】（来源：本主题 §4.7、§6.1、§6.2、§7.7，可逐行核对）。全书他处已具名的同族实现：KMS 落地要点（统一密钥管理 + BYOK，密钥分层、轮转、操作审计、异地加密备份）与 HSM 的采购口径见 `11-cross-cutting/02-data-security/02-data-security-section-4-sec4.md`；Vault / HSM 一类实现见 `11-cross-cutting/02-data-security/02-data-security-section-8-5-2-ranger-sentry-权限管理基础.md`；"令牌库成为全组织最高价值的单体资产，要独立加密、独立权限、独立审计、独立备份，且密钥用 KMS / HSM 管理并支持轮转"见 `11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` 的 §3.2.4 代价条目；字段级加密以 AES / 国密 SM4 实现的写见 `13-decision/05-tech-strategy/05-tech-strategy-section-8-5-6-安全架构演进与新兴趋势.md`；"敏感字段强制 KMS 加密 + 行为审计"的金融侧记录见 `11-cross-cutting/06-data-assetization/06-data-assetization-section-8-sec8.md`。**本节核不到**的是任何一家的具体吊销时延数字——所以这里只给"改配置 / 发版"的形态差别并标【经验】，**不给秒数**；同时本节也不为"微软的密钥管理服务"补一个产品名，那只在本主题原文里以描述性指称出现（§6.2）。

**失效条件**：密钥与数据的访问控制是同一套（§3.5 的反模式"密钥 / 盐表与数据同权限"）——此时加密退化为一次编码。

#### 7.3.4 证据的归属：谁能产出证明材料

**机制是什么**：合规要的材料（控制项映射表、拒绝日志、演练记录、连接审计）由**系统天然产出**、由**产品附带导出**、还是**只能人工整理**。

**它在各候选中的实现差异**：引擎与网关类通常有拒绝日志与审计表（**天然产出**，但字段是否够用要核）；产品类通常能导出报表（**附带导出**，但口径是厂商定的）；**映射表这一项，没有任何产品或候选会替你产出**——它是"你的系统 ↔ 外部标准"的对应关系，只有你能写。

| 材料 | 谁产出它 | 拿来能不能直接用 | 空缺在哪 |
| --- | --- | --- | --- |
| **拒绝日志 / 审计表** | 引擎、网关天然产出 | 能用，但要先核字段够不够（能不能答"是谁触发的"） | 旁路路径上不产生拒绝日志——**它是"对守规矩的人生效"的证据** |
| **连接审计** | 网络与身份设施 | 能用 | 它证明"连过"，不证明"该不该连" |
| **演练记录** | 只能你自己做 | 不能买、不能导出 | 它是**唯一能证明"此刻生效"**的材料；配置截图只证明"配过" |
| **产品报表** | 产品附带导出 | 能看，但口径由厂商定 | 口径与你的控制项边界不重合时，两张表拼不起来 |
| **控制项映射表** | **只有你能写** | —— | **没有任何产品或候选会替你产出**（§7.2 的"证据族不可替代"就是这一条） |
| **证据的字段口径** | 机制侧与材料侧共同定 | 不定就拼不起来 | 两边各自正确、合起来对不上（§6.3 的失败教训） |

**由此必然导出的性质**：因为**映射关系是不可外包的**（它依赖你对自己架构的了解，同 §5.3.6 的关键算子清单），所以**证据族（§7.2）在任何组合里都必须自建**。这条推论有一个直接的实践含义：**选产品时可以问"它产出什么证据"，但不能把"证据完备"外包出去**——测评方问的是"你的控制点在哪"，而产品答不了这个问题。

**由上表导出的三条性质**。第一条：**"天然产出"与"能举证"之间还隔着一次字段核对**——引擎给你的拒绝日志里如果只有服务账号、没有人的身份，它能证明"某次访问被拒"，不能证明"某个人的越权尝试被拒"；这是同一份日志在两个问题上的两种结论。第二条：**证据族是三族里唯一"因为做事变多而成比例变贵"的一族**（§7.4）——机制可以复用（一套策略管多套系统），映射表不能（每套标准、每个系统各一份），因此它不能按"一次性文档工作"立项（§6.3 的材料投入口径是"控制项数 × 每条三问"，**以人周计**【经验】——它可估、可提前排期，但**不可分批**，因为分批做时每一批都要重新对齐三问的措辞与控制边界）。第三条：**证据的产出位置应当与判定的执行点重合**——§4.1 Step 5 把这件事写成"执行点变证据采集点"，意思是不要等测评通知下来再去补日志；这条性质让"证据族不可外包"从一句结论变成一个可排期的动作。

**公开证据**：本主题内可核的锚点最实：§4.1 的 Step 5（执行点变证据采集点）与 Step 6（合规映射）；§4.5 模板 3 是一张三问表（控制点 / 执行结果存放处 / 生效证明动作），且它**老老实实标出了"待补"与 `⊥` 的行**（§4.5）；§4.2（6）给出策略版本化与生效验证的做法；§2.2 把覆盖判据写成"映射的定义域覆盖整个控制项集合、且没有 `⊥`"；§6.3（某股份制银行，2021-2024，**匿名案例，只作机制示例、不作举证**）给出材料投入的口径——"控制项数 × 每条三问"，并写明"预评估被打回到正式通过之间的主要工作**不是补能力，而是补指认与证据**"【经验：这条经验在多数受监管行业成立】；§7.7 给出迁移代价——"没建映射表"**以人周计**（相对便宜，但要赶在审查前）【经验】。【公开】（来源：本主题 §2.2、§4.1 Step 5–6、§4.2（6）、§4.5 模板 3、§6.3、§7.7，可逐行核对）。外部标准一侧，本主题已具名的是等保 2.0 的十类控制项（§3.2.8，编号 GB/T 22239-2019 见主文件 §1.4 与 §2.1）与"GB/T 39786 一类的密码应用标准"（§3.2.8，**原文的"一类"不可去掉、本节不补实施日期**）。可与它做结构对照的公开框架见 `11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-5-ai.md`（欧盟 AI Act（2024 年通过并分阶段适用）、NIST AI RMF 1.0（2023 年 1 月）、ISO/IEC 42001:2023；同处另记 GB/T 22239-2019 的 2019-12-01 实施日期）。合规自动化一侧的具名条目有 Vanta / Drata / Secureframe / 阿里云合规中心（`11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-8-5-5-大规模集群安全架构设计与优化.md`）与 AWS Audit Manager / Microsoft Purview Compliance Manager（`11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-8-17-4-数据治理与元数据管理.md`）；金融侧"自研数据安全治理平台 + 敏感字段强制加密 + 行为审计"的记录见 `11-cross-cutting/06-data-assetization/06-data-assetization-section-8-sec8.md`。**本节核不到**的是"控制项映射表"的具名产出方——**这一类材料不存在具名实现，任何声称有现成映射表的产品都应当按"口径由厂商定"重新核对**；**本节不具名任何一家声称能替你产出映射表的厂商。**

**失效条件**：当"证据"与"机制"分属两个团队（安全团队做机制、合规团队写材料）且**没有共同的字段口径**时，材料会退化成能力清单（§6.3 的失败教训）——**两边都对，但拼不起来**。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| **机制族**（引擎内置 / 网关 / 云服务） | 人力（策略维护）+ 订阅 / 许可 | 旁路排查、策略漂移后的重新收敛、跨引擎不一致的适配 | 随**资源数 × 策略维度**增长 |
| **重武器族**（DLP / 隐私计算平台） | 许可 + 计算资源 | 实体口径与业务对齐的持续投入、误拦带来的业务成本、性能与延迟 | 随**检测点数量 × 流量**增长 |
| **证据族**（咨询 + 自建材料） | 人力（材料维护 + 演练） | 每次系统变更后的映射复核、每套新标准的重新映射 | 随**标准数 × 系统数**增长 |

**成本函数的三条判据**：

① **机制族的曲线形状是"台阶 + 线性"**——许可是台阶，策略维护随资源数线性；**它的规模化压力来自"管的东西变多"**，不来自"跑的量变大"（§4.6 的结论）。
② **重武器族的曲线是"线性 + 惩罚项"**——它随流量线性，但**误拦带来的业务成本是超线性的**（一条被拦错的输出可能触发一次投诉或一次流程中断）。
③ **证据族的曲线是"随标准数 × 系统数"的乘积**——**这是三族里唯一会"因为做了更多事而成比例变贵"的一族**，而它恰恰是不可外包的那一族。

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：R = 受管资源数（表 / 文档 / 片段，以万计）   d = 策略维度数
    T = 标准数（等保 / 行业监管 / 客户审查 …）   S = 系统数
    H_mech = 机制族常备人力（人年）   P = 许可与订阅（万元）
    H_ev   = 证据族常备人力（人年）   c_dlp = 单位流量的检测成本（元/万次）

机制族：  Cost_mech(R,T,S) = H_mech(R) × 人均年成本 + P          ← 随 R 线性、与流量无关
重武器族：Cost_dlp(V)      = V × c_dlp + 误拦的业务成本(V)        ← 随流量线性 + 惩罚项
证据族：  Cost_ev(T,S)     = H_ev(T × S) × 人均年成本             ← 随标准数 × 系统数的乘积

反直觉的一条【推算】：当 T × S 继续增长时，Cost_ev 可能超过 Cost_mech——
因为机制可以复用（一套策略管多套系统），而映射表不能（每套标准、每个系统各一份）。
```

**这个式子的用法**：如果你有多套标准与多个系统，**先把证据族的成本算出来**——它最容易被立项时忽略（被算成"一次性文档工作"），而它是三族里唯一不可外包、且随"做事变多"而乘积增长的一族。**在接近成本交叉点的区间里，"减少系统数"或"归并标准"带来的收益，可能超过任何机制侧的优化。**

**三条量级推导**（读者可代入自己的数、逐条核对推导链）：

1. **对账与旁路的成本**（【推算】）。设对账频率为每周 f 次、单次取"受控路径统计"与"目标系统日志"做差异比对需要 t 人时/次，则年人力 ≈ f × t × 每年周数。本主题给出的口径是"约**半天**一次"（§6.1，【经验：随日志字段完整度浮动】）。这条推导的结论**不是那个数值，而是它的挂载方式**：约半天一次的强度意味着它靠"想起来就做"做不下去，只能附在某件每周本来就要做的事上（对账、月度审计、值班周报）——否则第一次延后就会变成永远不做；而**它一旦不做，旁路存在与否就不再是一个已知量**，此时后面所有策略的强度都无法被评估（§4.4 把"对账差异收敛"列为三条安全判据的第一条）。

2. **抽检与演练的人力**（【推算】）。§4.6 给出的口径是"每周抽检 20 条 DLP 命中记录约 1.7 小时/周"【推算：20 × 5 分钟 ÷ 60】，加上脱敏副本的重识别演练、越权尝试演练与策略评审，**常备投入落在 0.3–1 人年量级**【经验：随合规标准数与资源规模浮动】。这条推导的意义在于**它是本主题少数几条与数据量无关的人力口径**：受管资源数成倍增长时，这部分人力的形状基本不变——所以"数据量涨了要按比例加安全人力"这个直觉在本主题不成立（§4.6 的推论：人力随"管的东西变多"增长，不随"跑的量变大"增长）。**推论**：机制族的成本压力来自资源数与策略维度，因此**评估一份安全预算时要问的第一个问题不是"数据量多大"，而是"有多少套系统、多少套标准、策略有多少个维度"**。

3. **材料与交付的成本**（【推算】与【经验】并用）。证据族 = 控制项数 × 每条三问 × 单条人时，§6.3 把它记作"**以人周计**"【经验：通常以人周计，且远低于补一套新机制的成本】；国产化适配 = **算子数 × 单算子核验工时**【推算：单算子核验含"跑通 + 精度对照 + 记录结论"三步，请按你自己的算子清单与工时口径代入】（§6.4）。两条推导的共同点是**成本的自变量都不是"数据量"或"系统数"，而是"清单上有多少条"**。因此本主题里最有效的成本优化动作是**缩短清单**——归并标准、减少系统数、把"输出不会进入业务结论"的算子移出关键路径（§6.4 的筛选判据）——而不是换一个更便宜的产品。这也正是 `Cost_ev` 会反超 `Cost_mech` 的原因：机制可以复用，清单不能。

**还有一项常被忽略的成本：策略与映射表的"僵尸项"清理**。系统下线、租户合并、标准改版之后，挂在旧对象上的策略与映射行不会自动消失——它们要么开始报错（变成噪声），要么静默地对一个已经不存在的东西求值（变成假安慰：表格看起来很全，覆盖的却已不是当前系统）。**策略越多、标准越多，这类僵尸项的绝对数量越大**，而它们会让"覆盖率"看起来比实际更高。判断方法是随机抽一批策略行，逐条问"它上次生效是什么时候、对象还在不在"；**这项清理没有产品会替你做，且它随"管的东西变多"增长，与数据量无关**（§4.6 的同一条推论）。

**一条经验判据**（【经验】）：本主题的分界线不是"表数上万"，而是**系统数与标准数**——单系统、单一标准时，机制族与证据族的成本都很低，选哪个产品差异不大；一旦进入多系统、多标准的区间，**证据族会最先变成成本主项**（§7.4 的乘积项），而此时"减少系统数 / 归并标准"的收益通常大于任何机制侧的优化。这条线是经验线而非定律，可自行核验的判据是：把过去一年新增的标准数与新增的系统数数一遍，若两者都在涨，说明证据族的成本已在乘积增长。

### 7.5 决策树（每个分支都要有阈值依据）

1. **你的暴露面清单上有几个位置是空的？**
   - **超过 3 个**（多数团队在这个区间）→ **先补清单空格，什么都不买**：空格的成因通常是"机制放错了位置"（后置过滤、只做界面脱敏），**不是缺工具**。
   - 都已覆盖 → 进入第 2 问。
2. **你的访问路径能不能被绕开（有没有直连底层存储的路径）？**
   - 能 → **先收口访问路径**（这一步不依赖任何安全产品）；收口之前上的任何策略都只是"对守规矩的人生效"。
   - 不能 → 进入第 3 问。
3. **有没有"内容级"的需求（输出端识别、敏感实体、密文计算）？**
   - 有 → 引入**重武器族**（DLP / 隐私计算平台），但**先确认它的检测点能不能挂到你的清单位置上**（多数产品只在少数位置上工作，这是选型时唯一值得压测的东西）。
   - 没有 → 进入第 4 问。
4. **是不是必须过外部审查（测评 / 客户安全审查 / 信创验收）？**
   - 是 → **证据族必须自建**（控制项映射表 + 演练留痕）；这一步**不依赖前 3 问的结果**，可以并行开始（它是纯文档工作，投入产出比最高）。
   - 否 → 进入第 5 问。
5. **有没有人能长期维护策略（按 0.3–1 人年的常备投入量级估算【经验】）？**
   - 有 → 可以自建或自托管（控制力最强）。
   - 没有 → 走**引擎内置 + 云原生服务**的组合，把策略维护的复杂度降到最低，**并接受"能力受引擎限制"**。

**阈值的诚实说明**：上表的"超过 3 个空格"与"0.3–1 人年"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的清单与排期校准，**不要当门槛用**。

**这棵树由两组彼此独立的判断组成**：第 1–2 问是**筛可行性**（覆盖不到的位置、绕得开的路径），第 3–5 问是**决定叠加什么、由谁承接**。两组不能互相替代——一个已经买了 DLP 的团队，如果第 2 问的答案是"能绕开"，仍然要先收口，而不是去扩 DLP 的检测点；**第 1、2 问的结论会让第 3–5 问的投入归零**，这也是为什么本节 §7.1 的 6 条判据里，前两条被写成门槛而不是权重。

**逐条阈值依据**：

- **第 1 问"超过 3 个空格"**：依据是 §4.2（1）那张十三格清单上一条可操作的判据——"每格能不能答出'管它的机制是什么'"，而不是某个比例。给"3"这个数是因为空格最多的几格里，成因几乎都是同一类（机制放错了位置），而不是缺产品（§7.7 的前两行正是这一类的迁移代价）。**若空格里的成因各不相同，先补最便宜的那一格，而不是按数量排序**。
- **第 2 问"能不能被绕开"**：依据是 §7.3.1 的失效条件——存在直连底层存储 / 引擎的路径时，任何代理层或外部服务的判定都被旁路。**这是一个二值判据而不是程度判据**（能 / 不能），所以它排在"要不要买"之前。
- **第 3 问"有没有内容级需求"**：依据是 §7.3.2 的分工——权限的判定对象是元数据、检测的对象是内容，"内容级需求"（输出端识别、敏感实体、密文计算）是重武器族唯一不可被机制族覆盖的那部分。
- **第 4 问"是否必须过外部审查"**：依据是 §7.3.4——映射表没有任何产品会替你产出，所以它是"必须自建"而不是"可选"；它之所以能与机制族并行，是因为它不依赖机制就位（§7.6 的第二条次序原则）。
- **第 5 问"有没有人能长期维护策略"**：依据是 §4.6 的人力口径（0.3–1 人年量级【经验】）与本主题的成本形状（人力为主、随资源数增长）。**这一问的实质不是"有没有预算"，而是"这一档人是不是常备编制"**——按项目立项的人力会在项目结束后自然消散，而策略维护没有"结束"这个状态。

**树里没有"预算"节点，这一点需要单独说明**：把"安全预算是否超过某个数"作为分叉，是本主题最常见的立项错误，因为**预算不是一个筛选条件，而是规模效应在账面上的投影**——它由 §7.4 的三条推导决定：有多少系统与标准决定证据族，有多少受管资源与策略维度决定机制族，有多少输出决定重武器族。把预算当作分叉节点，最常见的后果是**为省下一笔许可费，选了一个机制上要持续投入人力的方案，第二年发现人力成本反而更高**——许可费是一次性的账，策略维护与映射维护是按年滚的账，两者的形状不同，而立项时只看得到前者【经验】。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 已有成熟数据平台、单一引擎 | 引擎内置（列掩码 / 行级策略） | 安全网关 | 网关多一跳且可能被绕过，而引擎内置天然不可绕过 |
| 多引擎、需要统一策略 | 安全网关（**先证明它不可绕过**） | 全自研 | 引擎内置跨引擎不一致；自研成本高 |
| 输出端有复述风险 | 重武器族（DLP，**需确认检测点可扩展**） | 自研检测 | 自研的实体口径维护成本高 |
| 只提供统计输出、隐私要求高 | 隐私计算平台（DP） | 自研 DP | **必须确认它支持预算累计**（不累计等于没有保护） |
| 算力需求大、数据只是过路 | 机密计算（TEE，**要求业务侧能独立验证远程证明**） | 私有化部署 | 私有化的固定成本是台阶形且与算力需求同步上升 |
| 要过测评 / 客户审查 | **自建证据族** + 任一机制族 | —— | 没有任何产品会替你产出控制项映射表 |
| 受监管行业、断供风险 | 自建机制族 + 国产化五类清单 | 云原生服务 | 云服务的可移植性与断供替代路径要逐类确认 |
| 团队只有 1–2 人 | 引擎内置 + 云原生服务 | 全自研 | 自研的策略维护人力不会因为它小就消失 |

**组合的两条次序原则**：① **先把"不可绕过"做到，再谈策略表达力**——判定点的唯一性优先于它的强度；② **证据族与前两族并行开始**——它不依赖机制就位（映射表可以先写"这部分还没做"），而它往往是最长的关键路径（因为要外部审查）。

**第三条原则（方向相反但同样重要）**：③ **清单可以先画、机制可以后补**——暴露面清单是纸面工作（半天），但它决定了后面所有投入的靶点。**这条的价值在于它把"必须先选完型才能开始"变成"今天就能开始"**。

矩阵的读法是：**先用"暴露面覆盖"与"不可绕过"筛掉不可行，再用"有没有内容级需求"与"要不要过审查"决定叠加什么，最后才用团队承接能力在剩下的里选**。每行"不选它的原因"都不是能力不足，而是**机制不落在收益点上**。判断矩阵用对了没有，只需回答一个问题：**我的痛点是否出现在我准备引入的机制所作用的位置上**——例如"误拦太多"这个痛点的位置在内容检测的动作层，换一个更严的策略引擎并不能解决它。

**四个常见组合**（各说明职责边界与运维代价）：

1. **引擎内置 + 安全网关 + 证据族**：引擎内置管单引擎内的列掩码与行级策略（离数据最近、不可绕过），网关管跨引擎的统一判定与统一留痕，证据族管映射表与演练记录。职责边界要写死的是"**同一条规则以谁为准**"——两处都配同一类规则时必须指定一个权威源，另一处只做转发或只做兜底。运维代价：**旁路排查是这套组合的常备动作**（§7.7 的第一、二行），对账一旦停做，整套组合的有效性就变成未知量。适用面最广，也是多数团队实际会落到的形态。

2. **DLP / 内容检测 + 机制族 + 证据族**：DLP 管"给出去的别是敏感的"（输出端识别、实体识别），机制族管"不该给的别给"，证据族管举证。职责边界就是 §7.3.2 的分工，**不能让 DLP 承担权限**（§7.7 第二行，且代价部分不可逆）。运维代价：检测点会从一处扩成三处（输出、缓存写入、日志写入），**每一处都要有 owner**，否则会出现"三处里有两处没人管"；同时必须自带内部度量（自己抽检误拦与漏出），因为本书体系里外部的漏出率与误拦率口径核不到（§5.2、§5.3.3）。

3. **云原生 KMS / HSM + 引擎内置（不自建策略引擎）**：KMS 管密钥与身份底座，引擎内置管数据侧的判定，**接受"能力受引擎限制"**为代价。职责边界：密钥生命周期与数据使用生命周期是两条线，判据是"只用数据权限的账号能不能读出明文"（§7.3.3）。运维代价：三族里最低——它不需要常备的策略维护人力，适合团队只有一两人的情形（§7.6 最后一行）；代价是**跨引擎不一致与跨云不可迁移**，这两项都会在系统数增长时变成必须返工的地方。

4. **自研策略引擎 + 国产化五类清单 + 自建证据族**：自研管"控制力最强"（判定点、下推、留痕都在自己手里），五类清单管断供与信创验收，证据族管外部审查。职责边界：自研的判据不是"功能多"，而是"**策略与证据能不能导出成一份不依赖任何产品的材料**"（§7.8 的思考锚点）。运维代价：三族里最高——策略维护是常备人力（§4.6），适配清单要随产品版本漂移定期复核（§4.2（5）），映射表要随标准数增加而增加（§7.4 的乘积项）。它只在"安全即核心竞争力、或监管要求极高"时才成立（§7.2 全自研一行的定位）。

四个组合的共同点是**入口低门槛、判定点强约束**：面向全部资源走自动或引擎内置的低成本路径，面向关键链路的判定走不可绕过、能举证的路径。反过来设计——全量强约束（策略写不完、清单维护不动）或全量弱约束（关键链路只有内容检测兜底）——是本主题最常见的形态错误。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 用代理层判定但存在旁路 | 策略生效了，访问从另一边走 | 收口访问路径（改应用直连） | **以月计**【经验】，**旁路排查是主要工作量** |
| 用 DLP 实现权限 | 已读出来、误拦与漏出同时存在 | 把权限交回有身份的判定层，DLP 退回内容检测 | 以月计，且**期间暴露面仍在** |
| 检测点不可扩展的 DLP | 泄露面覆盖不到 | 换产品 / 加自研检测点 | **以季度计**（重新集成与口径对齐） |
| DP 不累计预算 | 查询次数多了等价于无保护 | 补预算管理（含产品侧查询合并改造） | 以月计，**产品侧改造往往大于 DP 本身** |
| 密钥交给集成方 | 吊销要协调第三方 | 迁回自持 KMS | **以季度计**，且**迁回期间无独立止损能力** |
| 密钥与数据同权限 | 能读数据的人能读密钥 | 拆两条权限线 + 审计现有授权 | 以月计，**存量授权收敛是主要工作量** |
| 信创只验"能启动" | 上线后数值不一致 | 逐算子核验 + 精度对照 + 差异入合同 | **以算子数计**，且**已交付部分的争议最难处理** |
| 没建映射表 | 测评 / 审查时答不出控制点 | 逐条补三问（控制点 / 证据 / 演练动作） | **以人周计**（相对便宜，但**要赶在审查前**） |

**一条硬结论**：八条里最贵的是**"把判定或密钥交给别人之后的收回"**——它不只是技术搬迁，还包括**重新建立独立的止损能力**（在收回完成前，你对外部方的故障与拒绝没有替代路径）。**所以第 1、2 条判据（暴露面覆盖、判定不可绕过）必须在第一版就判对。**

**第二条硬结论**：上表里有两项的代价**部分不可逆**——"用 DLP 实现权限"期间的暴露面（数据已经读出来过）与"信创适配已交付部分的争议"。**其余六项都是"要花时间"，这两项是"花时间也拿不回来"**——这条区分决定优先级：**如果只能做一件事，先做"把权限交回有身份的判定层"，而不是先做"把 DLPT 的检测点扩得更全"。**

**四个反模式**（症状 → 后果 → 机制解释 → 正确做法）：

**反模式一：把"上了几个产品"当安全成果** —— 症状是汇报里写"已部署网关 / DLP / KMS 若干"，而暴露面清单上的空格没有减少 → 后果是覆盖范围由产品的检测点位置决定，而不是由你的清单位置决定，**列表越长、盲区越隐蔽** → 机制上这是把**可计数的量**当成了**要度量的量**：产品数与"清单位置被覆盖的格数"之间没有函数关系（§7.1 的第一条判据问的正是后者）→ 正确做法：把汇报的分母换成 §4.2（1）那张十三格清单，逐格标注"管它的机制是什么"。

**反模式二：先把机制选完，再画清单** —— 症状是先做了产品选型，暴露面清单留到验收前再补 → 后果是选中的产品检测点与你真正的空格不重合，补的价值有限，而**换产品的迁移代价已经产生**（§7.7 第三行，以季度计）→ 机制上清单是**靶点**、机制是**弹药**，先买弹药再找靶子必然错配；而且清单是纸面工作（半天量级），它的机会成本几乎为零（§7.6 的第三条次序原则）→ 正确做法：先画清单，再按空格分类（机制放错位置的空格不需要买产品，缺检测点的空格才需要）。

**反模式三：把证据族排到机制族之后** —— 症状是"等系统稳定了再来整理材料" → 后果是材料要反查半年前的系统状态，而**日志与配置可能已经不在了**；更糟的是审查日期不会因为机制没就位而后延 → 机制上证据族的成本**不随机制就位程度变化**（它随"控制项数 × 系统数"走，§7.4），因此它是**可以并行开始的关键路径**，而不是机制的收尾工作（§7.6 的第二条次序原则）→ 正确做法：映射表先写"这部分还没做"，把 `⊥` 显式留在表里；**空行比缺席好，缺席会变成审查前的一次性赶工**（§4.5 模板 3 已经这么示范）。

**反模式四：把"能不能启动"当验收结论** —— 症状是信创适配验收以"装上、能跑"为准 → 后果是数值差异在整体跑通里测不出来，上线后以"偶发不一致"的形态出现，而**已交付部分的争议最难处理**（§7.7 第七行，部分不可逆）→ 机制上验收粒度决定验收能不能发现问题：整体跑通检验的是"装得上"，而客户关心的是"结果与基线一致吗"，那是**逐算子**的精度问题（§6.4）→ 正确做法：在设计期就维护"关键算子清单"，判据是"输出会不会进入业务结论"，把差异分三类（可解释且可接受 / 可解释但不可接受 / 不可解释）并写进合同。

四个反模式的共同点是**它们都在机制层面改错了"投入作用的位置"**：产品数替代了覆盖格数，选型替代了清单，机制替代了证据，能启动替代了一致性。评估一次安全建设方案时，看的不是它列了多少能力，而是**它有没有让 §7.4 表里"成本随什么增长"那一列换项、有没有让 §4.2（1）清单上的空格减少**。

### 7.8 小结

> 本节小结：六个候选之间的差异，最终都能归到四问——**判定点在哪且能不能被绕过**（引擎 / 代理 / 外部服务）、**策略能不能下推**（条件还是过滤）、**密钥归谁**（决定吊销要多久）、**证据由谁产出**（没有任何产品会替你产出映射表）。四问决定了它们的分族（机制族 / 重武器族 / 证据族）与成本曲线形状（机制族随资源数线性、重武器族随流量线性加误拦惩罚、**证据族随标准数 × 系统数乘积增长**）。**选型顺序不可颠倒**：先用"暴露面覆盖"与"不可绕过"筛掉不可行，再用"有没有内容级需求"与"要不要过审查"决定叠加什么，最后才用团队承接能力在剩下的里选——**把第 6 条当权重而不是门槛，是第二年最常见的失效原因**。**本主题还有一条与其它主题不同的推论**：**证据族不可外包，且它随"做事变多"而成比例变贵**——因此"减少系统数 / 归并标准"在这里可能是比任何机制优化都更有效的动作。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次**门槛检查**（不是打分）：暴露面覆盖、判定可下推性、密钥与权限的分离度、证据产出能力、可移植性、运维承接——**哪一条是"不满足"而不是"分数低"**？那一条就是你最可能被迫迁移的方向（§7.7）；而你今天的补救成本，是否还落在"以月计"的那几格里？**另一问更具体**：你手上的策略与证据，**能不能导出成一份不依赖任何产品的材料**？答不出，说明你的合规材料还没有真正掌握在自己手里。
