## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研安全能力 / 平台内置 / 专用安全网关 / 商业 DLP / 云原生安全服务 / 咨询 + 自建合规材料"打分是常见做法，但它有三个结构性问题：

① **同一列在不同处境下方向相反**——"检测点可扩展"对一个已有成熟网关的团队是必需（它能在既有链路上挂点），对一个刚起步的团队是浪费（它还没有链路可挂）。
② **打分表隐含"这些选项互斥"**，而真实的做法是组合（**数据侧用引擎内置、在线路径用代理、合规材料自建**是常见组合）。
③ **最关键的判据不是可打分的维度，而是门槛**——**"检测点能不能覆盖到你的暴露面清单"**与**"策略能不能下推"**这两条是门槛：不满足就直接出局，给多少分都没意义。

**本节采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| **暴露面覆盖** | 它的检测点能挂在哪几个位置？你清单上的十三个位置它能覆盖几个？ | **这是门槛不是权重**——覆盖不到的位置，无论产品多强都是空的 |
| **判定可下推性** | 策略能不能编译成检索 / 查询引擎能吃的过滤条件？ | 不能下推 → 权限只能后置 → 在原理上做不到"不读出来" |
| **密钥 / 权限的分离度** | 密钥操作的权限能不能授予与数据管理员不同的人？ | 不能分离 → 加密不构成访问控制点（§6.2） |
| **证据产出能力** | 它天然产出哪些证据（拒绝日志 / 对账 / 演练接口）？ | 机制不产出证据 → 合规时无法举证（§6.3） |
| **可移植性与锁定** | 策略与证据能不能导出？换掉它要重写多少？ | 安全能力的迁移成本通常高于技术组件（策略与历史证据最难迁） |
| **运维承接** | 谁维护策略、谁做抽检与演练？ | 本主题的成本是人力为主（§4.6），**没有承接人的方案会在半年后失效** |

**这 6 条里，前两条是门槛（不满足直接出局），后四条是权重的输入。**

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| **引擎 / 平台内置** | 复用既有能力 | 数据库的列掩码 / 视图 / 行级安全策略；数据平台自带的权限与脱敏 | 已有成熟数据平台的团队 | 能力受引擎限制；跨引擎不一致；**部分引擎不支持把策略下推到检索** |
| **专用数据安全网关 / 代理** | 在线路径的判定点 | 在查询 / 检索路径上做代理，改写与判定都在这一层 | 多引擎、需要统一策略的团队 | 多一跳；**代理能否被绕过是唯一重要的问题** |
| **商业 DLP / 隐私计算平台** | 输出端与重武器 | 敏感实体识别 + 策略 + 动作（含 DP / TEE 等） | 合规压力大、需要现成材料的团队 | **检测点通常集中在少数位置**（多为流量入口）；实体口径与你的业务不完全对齐 |
| **云原生安全服务（KMS / HSM / IAM）** | 密钥与身份的底座 | 密钥操作独立授权、轮换与吊销是产品级接口 | 已在云上的团队 | 绑定云厂商；跨云一致性与可移植性受限 |
| **全自研** | 控制力最强 | 自建策略引擎 + 判定下推 + 证据采集 | 安全即核心竞争力、或监管要求极高 | **策略维护是常备人力**（§4.6）；短期投入最大 |
| **咨询 + 自建合规材料** | 举证路径 | 咨询给方法，材料自己维护（控制项映射表 → 控制点） | 要过测评 / 客户审查的团队 | 咨询产出的是方法而非能力；**材料必须有人持续维护** |

**这六个候选其实分三族**：

- **机制族**（引擎内置、安全网关、云原生服务）——**解决"判定在哪发生"**，它们的差别是判定点的位置与可下推性。
- **重武器族**（DLP / 隐私计算平台）——**解决"检测与计算在哪发生"**，它们的价值集中在少数需要专门能力的场景（输出端识别、密文计算）。
- **证据族**（咨询 + 自建材料）——**解决"怎么被承认"**，它的产出物是文档与演练记录，**不产生新的技术能力**。

**族内可替换，跨族不可换**：机制族之间换，动的是判定点的位置；从机制族换到重武器族，**不是替换而是叠加**（两者解的题不同）；而**证据族不能被任何一族替代**——测评方要的是映射表与演练记录，没有产品会替你产出它们。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 判定点的位置：在引擎里、在代理里，还是在别人的服务里

**机制是什么**：判定只能发生在三个位置——**引擎内**（数据库 / 检索 / 向量库自己执行策略）、**代理层**（请求经过的一个独立组件）、**外部服务**（云厂商的 IAM / 策略服务）。

**它在各候选中的实现差异**：引擎内置的判定**离数据最近**（可以下推到扫描层，效率最高），但受引擎能力限制、且跨引擎不统一；代理层的判定**统一但多一跳**，且**它的有效性完全取决于"能不能被绕过"**；外部服务的判定**最统一、最可审计**，但引入跨域调用（延迟与可用性都受外部影响，且**它一挂，判定就没了**——§4.7 的"失败关闭"在这里是关键）。

**由此必然导出的性质**：因为**"不可绕过"比"判定得更准"重要**，所以**判定点的选择首先是"唯一性"问题**——三个位置都做，等于三处都可能不一致；只做一个而不管旁路，等于没有。**这条性质解释了一个常见的误判**：团队常按"谁的策略表达能力强"选判定点，而真正的判据是**"我怎么证明没有第二条路径"**。

**失效条件**：当存在**直连底层存储 / 引擎的路径**时，任何代理层或外部服务的判定都被旁路——此时唯一的修法是**收口访问路径**（同 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md)），而不是把策略写得更严。

#### 7.3.2 策略的可下推性：条件，还是过滤

**机制是什么**：策略的产物是**一个判定条件**（可以编译进查询 / 检索的参数），还是**一个结果过滤器**（拿回数据后再筛）。

**它在各候选中的实现差异**：引擎内置通常提供真正的下推（行级安全策略会成为执行计划的一部分）；代理层能否下推取决于它与后端的协议（能改写查询就能下推，只能转发就只能过滤）；DLP 类产品大多工作在**内容层**（拿到内容才能识别实体），因此**它们在原理上是"后置"的**——这不是产品缺陷，而是它的检测对象决定的。

**由此必然导出的性质**：因为**DLP 的检测对象是"内容"，而权限的判定对象是"元数据"**，所以**这两件事在链路里的位置天然不同**：判定（元数据）可以前置到召回前，检测（内容）只能发生在内容生成之后。**这条性质给出一个清晰的分工**：**前置判定负责"不该给的别给"，后置检测负责"给出去的别是敏感的"**——两者不可互相替代，也不该混在一个组件里实现。

**失效条件**：当团队用 DLP 去实现"权限"时（例如靠检测输出里有没有敏感内容来防止越权），会出现两个问题：**已经读出来了**（暴露面已存在）、以及**误拦与漏出同时存在**（因为内容检测没有身份信息）。**判据**：权限问题是否被交回给有身份的判定层——没有，说明这两件事被混在了一起。

#### 7.3.3 密钥的归属：谁拿着钥匙

**机制是什么**：密钥由**你持有**（自建 KMS / HSM）、由**云厂商持有但权限分离**（云 KMS / HSM）、还是**在集成方手里**（把密钥交给安全产品）。

**为什么这是一个机制差异而不是商务差异**：因为**它直接决定"吊销要多久"**（§6.2）：你自己持有密钥时，吊销是改配置（秒级）；密钥在集成方手里时，吊销要协调第三方（小时到天级）。**而密钥泄漏的损失与处理时间线性相关**——它是一道正在流血的口子。

**另一层机制差异是"谁能阻止轮换"**：密钥的所有权决定了**轮换的执行者**。如果持有密钥的人也能拒绝轮换，那么"吊销能力"在组织层面是不可执行的——**这不是技术问题，是职责分离问题**（§6.2 的核心）。

**代价与边界**：自建 KMS / HSM 的代价是运维与合规（HSM 的采购、密钥备份与恢复演练）；云 KMS 的代价是绑定与跨云一致性；**把密钥交给集成方**的代价最隐蔽——**你失去了独立的止损能力**（对方是唯一的执行者）。

**失效条件**：密钥与数据的访问控制是同一套（§3.5 的反模式"密钥 / 盐表与数据同权限"）——此时加密退化为一次编码。

#### 7.3.4 证据的归属：谁能产出证明材料

**机制是什么**：合规要的材料（控制项映射表、拒绝日志、演练记录、连接审计）由**系统天然产出**、由**产品附带导出**、还是**只能人工整理**。

**它在各候选中的实现差异**：引擎与网关类通常有拒绝日志与审计表（**天然产出**，但字段是否够用要核）；产品类通常能导出报表（**附带导出**，但口径是厂商定的）；**映射表这一项，没有任何产品或候选会替你产出**——它是"你的系统 ↔ 外部标准"的对应关系，只有你能写。

**由此必然导出的性质**：因为**映射关系是不可外包的**（它依赖你对自己架构的了解，同 §5.3.6 的关键算子清单），所以**证据族（§7.2）在任何组合里都必须自建**。这条推论有一个直接的实践含义：**选产品时可以问"它产出什么证据"，但不能把"证据完备"外包出去**——测评方问的是"你的控制点在哪"，而产品答不了这个问题。

**失效条件**：当"证据"与"机制"分属两个团队（安全团队做机制、合规团队写材料）且**没有共同的字段口径**时，材料会退化成能力清单（§6.3 的失败教训）——**两边都对，但拼不起来**。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| **机制族**（引擎内置 / 网关 / 云服务） | 人力（策略维护）+ 订阅 / 许可 | 旁路排查、策略漂移后的重新收敛、跨引擎不一致的适配 | 随**资源数 × 策略维度**增长 |
| **重武器族**（DLP / 隐私计算平台） | 许可 + 计算资源 | 实体口径与业务对齐的持续投入、误拦带来的业务成本、性能与延迟 | 随**检测点数量 × 流量**增长 |
| **证据族**（咨询 + 自建材料） | 人力（材料维护 + 演练） | 每次系统变更后的映射复核、每套新标准的重新映射 | 随**标准数 × 系统数**增长 |

**成本函数的三条判据**：

① **机制族的曲线形状是"台阶 + 线性"**——许可是台阶，策略维护随资源数线性；**它的规模化压力来自"管的东西变多"**，不来自"跑的量变大"（§4.6 的结论）。
② **重武器族的曲线是"线性 + 惩罚项"**——它随流量线性，但**误拦带来的业务成本是超线性的**（一条被拦错的输出可能触发一次投诉或一次流程中断）。
③ **证据族的曲线是"随标准数 × 系统数"的乘积**——**这是三族里唯一会"因为做了更多事而成比例变贵"的一族**，而它恰恰是不可外包的那一族。

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：R = 受管资源数（表 / 文档 / 片段，以万计）   d = 策略维度数
    T = 标准数（等保 / 行业监管 / 客户审查 …）   S = 系统数
    H_mech = 机制族常备人力（人年）   P = 许可与订阅（万元）
    H_ev   = 证据族常备人力（人年）   c_dlp = 单位流量的检测成本（元/万次）

机制族：  Cost_mech(R,T,S) = H_mech(R) × 人均年成本 + P          ← 随 R 线性、与流量无关
重武器族：Cost_dlp(V)      = V × c_dlp + 误拦的业务成本(V)        ← 随流量线性 + 惩罚项
证据族：  Cost_ev(T,S)     = H_ev(T × S) × 人均年成本             ← 随标准数 × 系统数的乘积

反直觉的一条【推算】：当 T × S 继续增长时，Cost_ev 可能超过 Cost_mech——
因为机制可以复用（一套策略管多套系统），而映射表不能（每套标准、每个系统各一份）。
```

**这个式子的用法**：如果你有多套标准与多个系统，**先把证据族的成本算出来**——它最容易被立项时忽略（被算成"一次性文档工作"），而它是三族里唯一不可外包、且随"做事变多"而乘积增长的一族。**在接近成本交叉点的区间里，"减少系统数"或"归并标准"带来的收益，可能超过任何机制侧的优化。**

### 7.5 决策树（每个分支都要有阈值依据）

1. **你的暴露面清单上有几个位置是空的？**
   - **超过 3 个**（多数团队在这个区间）→ **先补清单空格，什么都不买**：空格的成因通常是"机制放错了位置"（后置过滤、只做界面脱敏），**不是缺工具**。
   - 都已覆盖 → 进入第 2 问。
2. **你的访问路径能不能被绕开（有没有直连底层存储的路径）？**
   - 能 → **先收口访问路径**（这一步不依赖任何安全产品）；收口之前上的任何策略都只是"对守规矩的人生效"。
   - 不能 → 进入第 3 问。
3. **有没有"内容级"的需求（输出端识别、敏感实体、密文计算）？**
   - 有 → 引入**重武器族**（DLP / 隐私计算平台），但**先确认它的检测点能不能挂到你的清单位置上**（多数产品只在少数位置上工作，这是选型时唯一值得压测的东西）。
   - 没有 → 进入第 4 问。
4. **是不是必须过外部审查（测评 / 客户安全审查 / 信创验收）？**
   - 是 → **证据族必须自建**（控制项映射表 + 演练留痕）；这一步**不依赖前 3 问的结果**，可以并行开始（它是纯文档工作，投入产出比最高）。
   - 否 → 进入第 5 问。
5. **有没有人能长期维护策略（按 0.3–1 人年的常备投入量级估算【经验】）？**
   - 有 → 可以自建或自托管（控制力最强）。
   - 没有 → 走**引擎内置 + 云原生服务**的组合，把策略维护的复杂度降到最低，**并接受"能力受引擎限制"**。

**阈值的诚实说明**：上表的"超过 3 个空格"与"0.3–1 人年"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的清单与排期校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 已有成熟数据平台、单一引擎 | 引擎内置（列掩码 / 行级策略） | 安全网关 | 网关多一跳且可能被绕过，而引擎内置天然不可绕过 |
| 多引擎、需要统一策略 | 安全网关（**先证明它不可绕过**） | 全自研 | 引擎内置跨引擎不一致；自研成本高 |
| 输出端有复述风险 | 重武器族（DLP，**需确认检测点可扩展**） | 自研检测 | 自研的实体口径维护成本高 |
| 只提供统计输出、隐私要求高 | 隐私计算平台（DP） | 自研 DP | **必须确认它支持预算累计**（不累计等于没有保护） |
| 算力需求大、数据只是过路 | 机密计算（TEE，**要求业务侧能独立验证远程证明**） | 私有化部署 | 私有化的固定成本是台阶形且与算力需求同步上升 |
| 要过测评 / 客户审查 | **自建证据族** + 任一机制族 | —— | 没有任何产品会替你产出控制项映射表 |
| 受监管行业、断供风险 | 自建机制族 + 国产化五类清单 | 云原生服务 | 云服务的可移植性与断供替代路径要逐类确认 |
| 团队只有 1–2 人 | 引擎内置 + 云原生服务 | 全自研 | 自研的策略维护人力不会因为它小就消失 |

**组合的两条次序原则**：① **先把"不可绕过"做到，再谈策略表达力**——判定点的唯一性优先于它的强度；② **证据族与前两族并行开始**——它不依赖机制就位（映射表可以先写"这部分还没做"），而它往往是最长的关键路径（因为要外部审查）。

**第三条原则（方向相反但同样重要）**：③ **清单可以先画、机制可以后补**——暴露面清单是纸面工作（半天），但它决定了后面所有投入的靶点。**这条的价值在于它把"必须先选完型才能开始"变成"今天就能开始"**。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 用代理层判定但存在旁路 | 策略生效了，访问从另一边走 | 收口访问路径（改应用直连） | **以月计**【经验】，**旁路排查是主要工作量** |
| 用 DLP 实现权限 | 已读出来、误拦与漏出同时存在 | 把权限交回有身份的判定层，DLP 退回内容检测 | 以月计，且**期间暴露面仍在** |
| 检测点不可扩展的 DLP | 泄露面覆盖不到 | 换产品 / 加自研检测点 | **以季度计**（重新集成与口径对齐） |
| DP 不累计预算 | 查询次数多了等价于无保护 | 补预算管理（含产品侧查询合并改造） | 以月计，**产品侧改造往往大于 DP 本身** |
| 密钥交给集成方 | 吊销要协调第三方 | 迁回自持 KMS | **以季度计**，且**迁回期间无独立止损能力** |
| 密钥与数据同权限 | 能读数据的人能读密钥 | 拆两条权限线 + 审计现有授权 | 以月计，**存量授权收敛是主要工作量** |
| 信创只验"能启动" | 上线后数值不一致 | 逐算子核验 + 精度对照 + 差异入合同 | **以算子数计**，且**已交付部分的争议最难处理** |
| 没建映射表 | 测评 / 审查时答不出控制点 | 逐条补三问（控制点 / 证据 / 演练动作） | **以人周计**（相对便宜，但**要赶在审查前**） |

**一条硬结论**：八条里最贵的是**"把判定或密钥交给别人之后的收回"**——它不只是技术搬迁，还包括**重新建立独立的止损能力**（在收回完成前，你对外部方的故障与拒绝没有替代路径）。**所以第 1、2 条判据（暴露面覆盖、判定不可绕过）必须在第一版就判对。**

**第二条硬结论**：上表里有两项的代价**部分不可逆**——"用 DLP 实现权限"期间的暴露面（数据已经读出来过）与"信创适配已交付部分的争议"。**其余六项都是"要花时间"，这两项是"花时间也拿不回来"**——这条区分决定优先级：**如果只能做一件事，先做"把权限交回有身份的判定层"，而不是先做"把 DLPT 的检测点扩得更全"。**

### 7.8 小结

> 本节小结：六个候选之间的差异，最终都能归到四问——**判定点在哪且能不能被绕过**（引擎 / 代理 / 外部服务）、**策略能不能下推**（条件还是过滤）、**密钥归谁**（决定吊销要多久）、**证据由谁产出**（没有任何产品会替你产出映射表）。四问决定了它们的分族（机制族 / 重武器族 / 证据族）与成本曲线形状（机制族随资源数线性、重武器族随流量线性加误拦惩罚、**证据族随标准数 × 系统数乘积增长**）。**选型顺序不可颠倒**：先用"暴露面覆盖"与"不可绕过"筛掉不可行，再用"有没有内容级需求"与"要不要过审查"决定叠加什么，最后才用团队承接能力在剩下的里选——**把第 6 条当权重而不是门槛，是第二年最常见的失效原因**。**本主题还有一条与其它主题不同的推论**：**证据族不可外包，且它随"做事变多"而成比例变贵**——因此"减少系统数 / 归并标准"在这里可能是比任何机制优化都更有效的动作。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次**门槛检查**（不是打分）：暴露面覆盖、判定可下推性、密钥与权限的分离度、证据产出能力、可移植性、运维承接——**哪一条是"不满足"而不是"分数低"**？那一条就是你最可能被迫迁移的方向（§7.7）；而你今天的补救成本，是否还落在"以月计"的那几格里？**另一问更具体**：你手上的策略与证据，**能不能导出成一份不依赖任何产品的材料**？答不出，说明你的合规材料还没有真正掌握在自己手里。
