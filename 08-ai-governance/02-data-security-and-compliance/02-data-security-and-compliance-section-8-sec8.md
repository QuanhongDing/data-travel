#### §8.1 你们的检索 / 问答接口里，权限判定在哪一步发生？如果一个越权请求会被拒绝，你怎么证明它没有先被读出来？

**1. 考察点**
- 是否理解**"不返回给用户"与"没有被读出来"是两件事**；
- 是否知道判定要**下推为检索条件**（而不只是"结果不过滤"）；
- 有没有可执行的验证动作（而不是只有架构图）。

**2. 参考答案框架**

**第一层：先给出判定的三个可能位置。** ① **召回前**（可见集作为检索的过滤参数）；② **召回后、生成前**（拿到候选后筛）；③ **生成后、返回前**（对最终输出做过滤）。**只有 ① 满足"没有被读出来"**；②③ 都会让无权内容进入进程内存 / 缓存 / 上下文。

**第二层：证明动作（这是本题的关键，必须有具体动作）。**
- **第一步**：打开检索接口的签名——**它有没有一个"可见集 / 过滤条件"参数**？没有，判定大概率在 ② 或 ③。
- **第二步**：用一个**无权账号**请求一段它无权看的内容；然后**去查这次请求的上下文构建日志与缓存**——无权内容出现在那里，就是 ②/③。
- **第三步**（最强）：把 `index.search` 的过滤参数临时去掉，**断言系统应当返回越权内容的地方却没有返回**——这一步证明的是"过滤参数在链路上是有效的"，而不是"我们写了过滤代码"。

**第三层：把判定与检测分开。** 权限判定（对象是**元数据**：谁能看什么）可以前置；DLP 检测（对象是**内容**：这段文本里有没有敏感实体）**只能在内容生成之后**——因此正确的分工是"**前置判定负责不该给的别给，后置检测负责给出去的别是敏感的**"（§7.3.2）。把权限问题交给内容检测，会同时产生两个后果：**暴露面已经存在**，以及**误拦与漏出同时存在**（内容检测没有身份信息）。

**第四层：说出它的实现约束。** ① 可见集必须来自**唯一权威源**（企业权限系统），自建一份会出现第二个权限源；② 某些引擎的过滤能力有限，需要在**索引期就把权限维度打进元数据**（这一步事后补不上）；③ **可见集为空的分支必须显式返回空**，不允许回退为"不过滤"。

**第五层：把"没有被读出来"落成一条接口约定，而不是一条设计原则。** 判定前置要成为可验收的事实，就必须体现在接口签名上：检索 / 召回接口里要有一个可见集参数（§4.5 模板 2 把三个交接物写成 `visible_fields` / `row_pred` / `visible_docs`，§5.4 的接口表把同一组参数列为与下游的交接物）。**可验收的判据是"把 filter 参数去掉，上述任何一条断言都会破"**——如果去掉它系统照常工作，说明这条约定并不在关键路径上，它只是一段可以被绕过的代码。本条还有一层**身份约束**：判定用的主语必须是人而不是服务。服务代调用时请求要带 `on_behalf_of`（或等价的委托凭证），否则判定用的是服务身份，而服务账号为了跨租户取数通常权限很宽——**以服务身份判定等于按最宽的那个身份放行**（§4.2（3））。判据：审计记录里能否回答"这条数据是**谁**（具体到人）触发的访问"，只能回答"哪个 Agent / 哪个服务"，说明身份链是断的。

**第六层：说出这件事在组织上的落点（面试官常在这里追问）。** 判定前置的编码量很小，成本几乎全在策略的归属上：谁定义"哪些文档对哪些角色可见"、谁审批例外、**谁在撤权之后负责让缓存与索引失效**。这三问没有答案时，技术上做得再对，撤权也会滞后——而撤权滞后与密钥吊销滞后是同一类问题：它们都不是能力问题，而是**职责问题**（与 §7.3.3 "谁能阻止轮换"同构）。这也解释了本主题 §4.6 的推论：安全投入的主要成本是人力、且随"管的东西变多"增长——因为真正要长期维护的不是代码，是策略与例外。

**3. 常见陷阱**
- 只答"我们做了权限过滤"，说不出**它在链路的哪一步**；
- 把"用户看不到"等同于"没读出来"；
- 用 DLP 的检测结果来回答权限问题（两者对象不同）；
- 举不出一个**十分钟内能做完**的验证动作；
- 只谈"我们下沉到了引擎里"，不谈**判定用的主语是人还是服务**——下沉解决了"在哪判"，没有解决"以谁的身份判"；
- 把"可见集为空"当成边界情况不处理，默认回退为"不过滤"（一个返回全量而不是返回空的空集分支，等价于没有权限）。

**为什么这几种错法看起来都对**：因为它们在**正常路径上都能得到正确结果**。有权的人拿到了他该拿的、无权的人看不到——从用户视角看，后置过滤与前置判定没有区别；只有去查进程内存、缓存与上下文日志时，两者才分开。同理，"服务身份判定"在一个只服务单租户的服务上完全正确，只有跨租户时才暴露；"空集回退为不过滤"在可见集从不落空的系统里永远不会触发。**这三类错法（后置过滤、"服务身份判定"与"空集回退"）的共同机制是：它们的失效只出现在"无权"与"跨租户"这两类输入上，而这两类输入在功能测试里通常不存在。** 这正是本题要求"给一个验证动作"而不是"给一个架构图"的原因——没有验证动作，这三类错误无法被自查出来。

**4. 追问预测**
- "如果可见集很大（80% 的数据都可见），下推过滤会不会影响召回质量？你怎么量这个影响？"
- "跨库引用的可见性传染，你怎么定义？"
- "策略缓存在客户端，撤权之后多长时间生效？"
- "如果权限服务挂了，你的系统是拒绝访问还是放行？"

#### §8.2 一个字段要脱敏，你怎么决定用哪种方式？可逆和不可逆的界线在哪？

**1. 考察点**
- 是否知道脱敏的形态有**四类**（泛化 / 掩码 / 确定性假名 / 噪声注入），而不是"脱敏就是打星号"；
- 是否理解**可逆性的代价是把风险转移到盐表**；
- 会不会把差分隐私当成"更高级的脱敏"。

**2. 参考答案框架**

**第一层：先问用途，再选形态。** 判据是**"这份脱敏副本还要不要参与跨系统关联"**：不需要 → 不可逆（泛化 / 掩码）；需要按同一主体跨表聚合 → 必须**确定性**（同一输入总映射到同一输出），即加盐哈希或格式保留加密。

**第二层：给出选择顺序（从 ① 到 ④ 依次退让）。**
1. **泛化**（日期截断、地区聚合、金额分桶）——最安全、最便宜，**代价是精度**；
2. **掩码 / 替换**（`138****1234`）——保留格式、**代价是关联性**；
3. **确定性假名**（加盐哈希 / FPE）——保留关联、**代价是盐表本身要保护**；
4. **噪声注入**（DP）——保留统计性质、**代价是可查询次数**。

**第三层：把"可逆"的代价说清楚。** 可逆不是更高级，而是**把风险从"副本"转移到了"映射表 / 盐表"**——它一旦泄漏，脱敏全部失效。因此选用可逆方案时**必须同时给出盐表的保护方案**，而判据是**"盐表与数据的访问控制是不是两套"**（同一套权限管两样东西，等于脱敏退化为一次编码）。

**第四层：给出"脱敏是否有效"的验证动作。** 对脱敏后的副本做一次**重识别演练**：尝试用**非敏感字段的组合**还原个体（年 + 地区 + 性别 + 入职年份这种组合常能唯一定位到人）。**演练失败（还原不出来）才算数**——只看显式敏感字段是否被打码，是不构成验证的。

**第五层：区分 DP 与脱敏。** DP 保护的是**"个体能不能从统计输出里被推断出来"**，不解决"字段能不能被看到"；脱敏反过来。**两者不可互替**，且 DP 有两条硬纪律：**预算必须累计**（不累计等于没有保护，这是组合定理的直接推论）、**输出必须有人在聚合层面消费**（把 DP 用在行级查询上是用法错误——那只是给单条记录加了噪声）。

**第六层：把"选哪一档"变成可测的拐点，而不是偏好。** 泛化会损失精度，而损失到什么程度不可接受，**没有任何产品文档能替你回答**——它只能用你自己的下游任务测出来（§2.2 把这件事写成"利用率 `I / I₀` 的拐点要评测"）。可测的做法是：取同一份数据做几档递增的泛化，对每一档跑一次下游任务（模型训练、统计报表、跨表关联），把"精度"与"可辨识度"两条曲线画在同一张图上，**拐点出现在精度开始塌陷、而可辨识度还没降到安全区的那一段**——这一段是"看起来还能用、实际上两头不划算"的区间，应当直接排除。**这是本题唯一能给出量而不必编数的地方**：不同业务的拐点位置不同，跨组织不可比，所以只能给方法不能给数值。

**第七层：说清脱敏与加密的边界（面试官常用来分辨是否真做过）。** 加密解决"**拿到存储介质或备份的人读不到明文**"，不解决"**有权限的系统读到了什么**"——同一个账号既能读数据也能取密钥时，加密对越权没有任何作用（§7.3.3 的判据："只用数据权限、没有密钥权限的账号，能否通过正常路径读出明文"）。脱敏解决的是"**这份副本在流通中长什么样**"。两者的失效条件因此相反：**加密失效于"密钥与数据同权限"，脱敏失效于"副本与原件同权限"**——副本还留在能被直接访问的地方，脱敏就等于没做。这句话可以直接回答"我们既加密又脱敏，够不够"这一类追问。

**3. 常见陷阱**
- 只答"打码 / 加密"，说不出四类形态与选择顺序；
- 认为可逆方案更安全（它只是把风险挪走了）；
- 用 DP 来回答"字段怎么脱敏"；
- 说"我们脱敏了"但**说不出任何验证动作**；
- 忽略**准标识符组合**（只看显式敏感字段）；
- 把"脱敏"与"加密"当成同一件事的两种说法（它们防的是不同的事：一个防介质被拿走，一个防副本被误用）；
- 只验一次就认为完成了（数据在更新、准标识符的分布也在变，重识别演练要定期重做，而"一次通过"会让人以为这件事已经结束）。

**为什么这几种错法看起来都对**：因为它们都能通过"看一眼"的检验。打码之后的字段看起来确实不敏感了，`ε` 写进方案看起来确实更"先进"，验一次重识别演练失败看起来确实"验证过了"。**它们共同的机制是：脱敏的有效性不由"字段长什么样"决定，而由"副本还能不能被关联回个体"决定**——后者只在准标识符组合、以及跨副本关联时才显现。所以这几种错法全都在"单字段视角"下正确、在"数据集视角"下失效。其中"可逆更安全"尤其反直觉：可逆方案的输出更接近原值（更保真、更像"真实数据"），于是它看起来更专业——实际上它把风险从**看得见的副本**搬到了**看不见的映射表**（§2.2 的可逆性判据：`|m(D)| < |D|` 才是不可逆，而可逆意味着映射表成了最高密级资产）。

**4. 追问预测**
- "泛化到什么粒度之后，下游模型的效果开始不可接受？你怎么找这个拐点？"
- "可变长度字段的格式保留加密怎么做？"
- "同一张表的两个字段分别脱敏后，还能不能做关联分析？"
- "如果业务既要关联又要不可逆，有没有第三条路？"
- "如果重识别演练成功了，你的补救顺序是什么？"（答：**先撤副本、再改规则**——改规则只影响未来，已经发出去的副本不会因为改规则而变安全；§4.4 的存量迁移第一步就是"先盘点历史副本"）
- "同一份数据要同时给训练、测试与外部合作方，脱敏规则该写一份还是三份？"（答：**规则一份、用途多份**——规则是一张"密级 × 用途 → 方法"的表，新增一个用途是加一行，而不是加一套脚本；这一形态在全书的 `11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` §3.2.4 有记录）

#### §8.3 等保 2.0 的「一个中心、三重防护」，在你们的 AI 平台上分别对应哪个控制点？你怎么证明每一条此刻生效？

**1. 考察点**
- 是否知道合规的判定标准是**"可举证性"而不是"能力强度"**；
- 能不能把外部标准**逐条映射到系统控制点**；
- 有没有意识到 **AI 平台会带来通用项之外的额外组件**。

**2. 参考答案框架**

**第一层：先给映射（示例）。**

| 等保结构 | AI 平台上的控制点 |
| --- | --- |
| 安全管理中心 | 策略服务的**唯一权威源**（权限 / 出网 / 留痕不各配一份） |
| 安全通信网络 | 模型端点的**出网白名单**（按租户分级）+ 连接审计 |
| 安全区域边界 | 工具出口的鉴权与**人审闸门**（不可绕过的唯一出口） |
| 安全计算环境 | 沙箱隔离、**凭证按实例发放**、镜像与依赖可追溯 |

**第二层：给出"三问"这个形式（本题的核心）。** 对每一条要求回答：**控制点在哪**（组件 / 配置 / 代码位置）、**执行结果存在哪**（日志 / 报表）、**怎么证明它此刻生效**（一个可执行的演练动作）。**三问缺一即为 `⊥`（尚未指认）**——而 `⊥` 就是测评时的失分项。

**第三层：说明为什么"能力清单"答不了这个问题。** 材料的形态决定了它能不能被核验：能力清单（"我们有 WAF / 堡垒机 / 加密"）回答的是"我们有什么"，而测评方问的是"**这一条，你在哪里做的、证据在哪、怎么证明生效**"——后者每一条都可以被独立核验。

**第四层：点出 AI 平台的特殊性。** 通用项（网络 / 主机 / 数据库）企业通常已有控制点，而**模型端点、工具出口、沙箱、凭证发放**是 AI 平台新引入的组件——**它们不被指认，就会出现"通用项都有、AI 特有的那几条全是 `⊥`"**。

**第五层：给验证动作。** 每条的"生效证明动作"要写成可执行的一句，例如"让受监管租户的请求指向外部端点，验证被拒绝"，**并保留演练记录**。**配置截图证明的是"配过"，而配置会漂移**——只有演练记录能证明"此刻生效"。

**第六层：说清"配置会漂移"这件事的机制，并给出复核节奏。** 漂移的来源有三个，都不是"有人改错了配置"这么简单：① **系统在演进**——新租户、新模型端点、新工具出口上线时，默认是"没有对应策略"，于是白名单会漏项；② **人在轮岗**——写策略的人走了，新来的人看到的是结果不是理由，改动时倾向于放宽；③ **标准在改版**——控制项本身在变，而映射表的对象一旦变了，行还是那些行、含义已经不是原来的含义。因此**"生效证明"不是一次性的动作，而是一个有 owner、有周期、有留痕的例行项**（本主题 §4.1 的 Step 5 把它写成"执行点变证据采集点"，§4.2（6）把策略版本化与生效验证列为关键技术点）。**判据**：上一条演练记录的时间与执行人能不能说出来——说不出来，说明这项能力当前处于"配过但没人管"的状态。

**第七层：指出材料与能力分属两队时的接口（本题的高分点）。** 受监管行业的常见组织形态是：安全团队做机制、合规团队写材料。此时最大的风险不是某一方做得不好，而是**两边都对、拼不起来**——机制侧有拒绝日志但字段里只有服务账号，材料侧需要"具体到人的越权尝试记录"，两边单独看都合格，合起来缺一环（§7.3.4 的失效条件）。**可执行的解法是把"字段口径"当成接口来定**：由材料侧先列出每一条控制项需要哪几个字段，再由机制侧确认这些字段是否已经在日志里、如果不在要先补日志（这一步必须在机制上线前做，上线后再补日志意味着历史证据不存在）。这一层之所以是高分点，因为它把"合规"从"整理材料"变成了**一次架构前置约束**。

**3. 常见陷阱**
- 把测评准备当成"整理能力清单"；
- 只指认通用项，漏掉 AI 特有组件；
- 说得出控制点但**说不出证据存放处**；
- 拿配置截图当"生效证明"；
- 认为"再过一套新机制"比"把映射写全"更有效（后者投入产出比高得多）；
- 把映射表当成**一次性交付物**（标准改版、系统托管拆分、租户合并之后，映射表要跟着变；不变就会变成"行都在、含义已变"）；
- 用"我们过了等保 X 级"回答"这一条你在哪里做的"（等级是结论，控制点指认才是素材；测评方要看的是后者）。

**为什么这几种错法看起来都对**：因为它们都能产出**看起来完整的材料**。能力清单也是一份清单，配置截图也是一份证据，等级证书也是一份官方结论——三者在"评审能不能通过"这个结果上都可能短期奏效，因为外部审查看到的是文档。**它们共同的机制是：材料的形态决定了它能不能被独立核验**——能力清单回答"我们有什么"、配置截图回答"我们配过"、等级证书回答"总体是什么档位"，而这三问都不是"这一条在哪里、证据在哪里、怎么证明生效"。只有最后这一种形态可以被逐条核验，也只有在被逐条核验时，前面三种才会同时暴露：**它们缺少的是"控制点"这个中间项**，而控制点恰好是不能从外部买、也不能从结论倒推出来的那一项（§7.3.4："没有任何产品会替你产出映射表"）。

**4. 追问预测**
- "策略的'唯一权威源'这件事，如果历史上有三个系统各配了一份策略，你怎么收敛？"
- "演练记录要留多久？留痕的存储成本怎么算？"
- "如果测评方问的某一条你们确实没做，你会怎么处理？"
- "国产化适配和等保是两套要求，两者的控制点会不会冲突？"
- "AI 特有的控制项（模型端点、工具出口、沙箱、凭证发放），你们是单列成一张表还是并入通用项？"（答：**单列**——并入通用项时，它们会在"通用项都有"的结论里被掩盖，从而出现"AI 特有的那几条全是 `⊥`"；本主题 §6.3（某股份制银行，2021-2024，**匿名案例，只作机制示例、不作举证**）把 AI 场景特殊项单列表写成做法之一）

#### §8.4 你把密钥放在哪里？如果现在发现它泄漏了，多久能止住？

**1. 考察点**
- 是否理解**吊销时间是一个结构性差异**（与运维水平无关）；
- 是否知道密钥与数据的权限必须是**两条线**；
- 有没有意识到"轮换留一半等于没换"。

**2. 参考答案框架**

**第一层：直接回答吊销时间。** 密钥**在服务侧**（KMS / 网关）时，吊销是**改配置**——秒级生效；密钥**在应用配置里**时，吊销是一次**发布**——要等所有实例重启，**小时到天级**。**这是纯结构差异**：同一个团队、同一套运维水平，密钥放的位置不同，止损时间差两个数量级。而**密钥泄漏的损失与处理时间线性相关**——它是一道正在流血的口子。

**第二层：两条权限线（本题的机制核心）。** 密钥的生命周期（生成 / 轮换 / 吊销 / 销毁）与数据的使用生命周期是两个流程，**因此它们的权限天然应当分开**。可核查的判据：**一个只用数据权限、没有密钥权限的账号，能否通过正常路径读出明文？能，说明两条线没有分开**——此时加密只是**一次编码**（把数据换成另一种表示），不是一道门。

**第三层：轮换的执行者要独立。** 如果持有密钥的人也能拒绝轮换，那么"吊销能力"在**组织层面**不可执行。**判据**：轮换有独立流程与值守人吗？

**第四层：轮换要一次做完。** 旧密钥在轮换后必须**真正失效**（或设一个明确的重叠窗口），而不是"保留着以防万一"——**留一半等于没换**，而团队会以为已经换过了。

**第五层：把"谁持有密钥"做成清单。** 轮换成本随**持有该密钥的组件数**增长；没有这份清单，轮换时会发现某个无人知晓的副本。**判据**：密钥清单与"持有它的组件"清单能不能对上。

**第六层：说清轮换的执行细节（面试官用来分辨"做过"与"配过"）。** 轮换不是一次动作而是一段过程，它至少要回答四个问题：① **重叠窗口多长**——新旧密钥并存的时间必须覆盖"最长的一次批处理周期"，否则跨窗口的任务会解密失败；② **谁能同时解旧又解新**——并存期内读取方要能两把都试，这一点决定了密钥接口必须支持"按版本解"，而不是"只有当前版本"；③ **旧密钥什么时候真正失效**——设一个明确的失效时间点，且这个动作要能被演练（本主题 §4.7 的失效形态表把"密钥服务失效"列为判定类，纪律是**失败关闭**）；④ **谁在轮换后核对**——轮换完成的判据不是"发版成功"，而是"旧版本解密请求数归零"，这是一个可观测指标。**这四问只有第一问涉及数值（且是你们自己的批处理周期，不是任何产品能给的），其余三问都是形态问题。**

**第七层：把"密钥归谁"延伸到 BYOK 与断供场景。** 客户要求密钥由自己持有（BYOK）时，改的不是加密算法，而是**密钥的生命周期归属**：密钥的生成、备份、恢复、吊销都要能被客户独立执行，且云厂商在客户未授权时解不开数据——这意味着"客户能自己演练一次吊销"是验收项，而不是功能列表上的一个勾。断供场景下的判据更进一步：**密钥能不能导出、导出之后数据还能不能在别处解开**。这一层与 §7.6 矩阵里"受监管行业、断供风险"一行同源，也是本主题把"密钥可控性"单独列为收益项的原因（§6.2 的 ROI 口径：从"小时到天级"的止损时间压到"秒级"）。

**3. 常见陷阱**
- 只答"我们用 KMS"，说不出**吊销要多久**；
- 把密钥当普通配置，与数据同一批管理员；
- 认为"加密开着"就等于加密构成了访问控制点；
- 轮换后保留旧密钥；
- 没有"谁持有密钥"的清单；
- 只谈技术与产品，不谈**谁能拒绝轮换**（如果持有密钥的人也能拒绝轮换，"吊销能力"在组织层面不可执行——这是职责分离问题，不是技术问题）；
- 把"密钥服务挂了"当成和"审计写入失败"同类的故障（前者是判定类，按纪律必须**失败关闭**；后者是证据类，告警即可——两者混在一套处理流程里会让系统在密钥服务抖动时大量误拒，进而逼迫团队把"失败关闭"改成"失败放行"，而这一改会让加密彻底失去意义）。

**为什么这几种错法看起来都对**：因为它们描述的都是**已经完成的技术动作**。"用了 KMS"、"加密开着"、"轮换做过"三句在多数团队的文档里都能找到对应证据，而它们回答的是"有没有做"，不是"做了什么形态"。**它们共同的机制是：加密的价值不在"数据被加密"这个状态上，而在"谁能解密、以及这个能力能被撤回多快"这个结构上**——状态是静态的、容易核对；结构是动态的，只有演练才能暴露。所以这几种错法全都通过"查配置"这一关，只会在"演练一次吊销"或"数一遍谁持有密钥"时失效。而"轮换后保留旧密钥"这条更隐蔽：它在功能上完全正常（旧数据仍能解、新数据也能解），只有从安全角度看才是"留一半等于没换"——**它不会产生任何故障信号，只会削弱你自以为拥有的能力。**

**4. 追问预测**
- "密钥轮换期间，正在跑的批任务怎么办？重叠窗口设多长？"
- "HSM 的密钥备份与恢复怎么演练？"

#### §8.5 模型把我上一轮的机密内容复述出来了。你怎么防这一类泄露？

**1. 考察点**
- 是否理解 AI 场景下**泄露的形态变了**（从"一次动作"变成"一条链路"）；
- 知不知道 DLP 的三件事与**双端**要求；
- 有没有意识到**缓存与日志也是泄露通道**。

**2. 参考答案框架**

**第一层：先把泄露路径画出来（十三个位置）。** 一次请求里数据落的地方包括：应用日志、召回结果（内存）、检索缓存、上下文拼装、模型端点、提示缓存、生成输出、DLP 出向、响应缓存、trace / 遥测、会话留痕表、导出物、备份。**"复述"只是其中一格**——只堵那一格，还有十二格。

**第二层：DLP 的三件事（识别 → 判定 → 动作），且三道都留痕。**
- **识别**：确定性匹配（正则 + 校验位：身份证校验位、银行卡 Luhn）**先行**（精确、零误报、但对变体无能），上下文判定兜底（覆盖率高、引入误报）。**顺序反了会让模型重复一遍确定性能做的事，白白抬高误报**。
- **判定**：该实体的密级 × 场景 × 调用者身份。
- **动作**：拦 / 脱敏后放行 / 要求二次确认 / 放行并留痕。**二次确认只在"高风险 + 高置信"时启用**——作为默认动作，每一次输出都会变成人工介入，闸门退化成橡皮图章。

**第三层：双端 + 覆盖缓存与日志。** 入向阻止敏感内容进入上下文，出向阻止它离开系统；**缓存写入与日志写入也要在检测位置清单里**——它们和输出一样会把内容带出去，而"用户看不到"不等于"不在那里"。

**第四层：流式分片。** 敏感实体可能被分片切开（`138` / `0013` / `8000`）。处理方式与代价：缓冲后检（延迟上升，与首字延迟冲突）/ 滑窗拼接（需按实体长度定窗口，误报略升）/ 只检完整段（漏检上升）。**给出一条测试用例**：把身份证号跨两个分片发送，看它是否被检出——**不做这个测试，等于不知道流式侧有没有生效**。

**第五层：漏出率与误拦率必须一起报。** `漏出条数 = N × p × (1 − r)`、`误拦条数 = N × (1 − p) × fp`——两个数方向相反，因此 **DLP 的阈值不是安全参数，而是业务取舍点**，应当被画成一条曲线由业务选点。

**第六层：把"不可判定时的默认动作"提前定死。** 内容检测一定会遇到三种不可判定：检测服务超时、实体置信度落在中间区间、实体类型不在词表里。这三种情况下的默认动作必须**在架构评审阶段就定**，而不是线上第一次超时时临时决定——因为临时决定的结果几乎总是"先放行、之后再补"，而放行一次就已经出去了。可用的判据是全书他处记录的两条纳入试点的问法：**"判定输入是内容还是对象"**与**"不可判定时默认拒绝还是放行"**（`11-cross-cutting/02-data-security/02-data-security-section-4-sec4.md`）。本主题一侧的对应纪律在 §4.7：**判定类失败关闭、证据类告警**——输出端 DLP 属于判定类，所以超时的默认动作是拒绝；但"拒绝"必须配一条降级路径（例如改走不带上下文的纯检索式回答），否则一次检测抖动就会变成一次业务中断，而业务中断会反过来逼团队把纪律改成"失败放行"。

**第七层：把动作分级与 owner 一起说。** 三道闸都留痕之后，动作本身要分层：拦 / 脱敏后放行 / 要求二次确认 / 放行并留痕。**二次确认只在"高风险 + 高置信"时启用**（§2.3 ⑤）——作为默认动作时，每一次输出都会变成人工介入，闸门退化成橡皮图章，而团队会在很短的时间里学会"无脑点通过"，此时它**不仅没有防护效果，还消灭了后续改进的依据**（通过率不再有信息量）。同时要指定 owner：检测点会从一处扩成三处（输出、缓存写入、日志写入），**三处各要有一个 owner**，否则会出现"三处里有两处没人管"（§5.3.3 的第二条代价）。这一层回答的是面试官最常追问的那句"这套东西谁来维护"。

**3. 常见陷阱**
- 只答"加个敏感词过滤"，且只做在输出上；
- 不提**缓存与日志**这两条通道；
- 不说流式怎么处理；
- 把二次确认当默认动作；
- 报不出漏出率与误拦率（只有一个"我们拦住了"）；
- 把"输出端"当成唯一出口（缓存写入与日志写入同样会把内容带出去，而它们通常没有业务方盯着，**因此比输出端更容易长期失管**）；
- 用"加了一个模型做二次判定"来回答漏出率问题（这会把误报从一个可调参数变成不可解释的分布，而且它**不改变"内容已经被读进上下文"这个事实**——检测发生在生成之后，它只能减少外发，不能减少暴露面）。

**为什么这几种错法看起来都对**：因为它们在**正常输出**上都有效。敏感词过滤确实能拦住明显的复述，"加个模型二次判定"确实能提高检出，"二次确认"确实让每一次高风险输出都经过了人。**它们共同的机制是：输出端管控的覆盖面不由"检测多准"决定，而由"检测点挂了几个位置"决定**——一个位置上的检测再准也只覆盖那一个位置，而泄露是一条链路（数据进上下文 → 被复述 → 进输出 → 进缓存 / 日志），链路上任何一个没有检测点的环节都会让前面的准度失去意义。所以这几种错法都在"出口"这一格上做优化，而本题的考点是**出口不止一格**。第七种错法还额外叠加一层：把"检出率"当成可优化的目标，会诱使团队调低阈值换检出，而误拦的代价不在安全侧、在业务侧——这是这次调优的隐性账，所以 §2.2 的两个式子必须一起报。

**4. 追问预测**
- "滑窗的窗口长度怎么定？带格式变体（全角、空格、分段）怎么办？"
- "如果检测超时，你的系统是放行还是拦截？"
- "命中率与漏出率你用什么数据集评估？"
- "日志里为什么要记内容？不记内容你怎么排查？"（这题考的是"记元数据不记内容"的设计）
- "如果模型把机密内容改写（换语序、翻译、拆分）之后再复述，你的正则还能检出吗？"（答：**检出率会显著下降，而这不是参数问题**——确定性匹配对变体无能，这正是 §2.3 ① 把"确定性匹配先行、上下文判定兜底"的顺序写成硬要求的原因；顺序反了会让模型重复一遍确定性能做的事，白白抬高误报。诚实的回答是"覆盖率下降多少要自己测，且必须在架构上承认它测不出全部"）
- "你会在日志里记内容吗？"（答：**记元数据不记内容**——记实体类型、位置、判定结果与动作，不记原文；需要复核时用"重放同一输入到检测器"复现，而不是回复原文。这也是"缓存与日志也在检测位置清单里"的另一面：**既然它们是泄露通道，它们就不应当持有足够多的原文**）

**5. 参考资料**

#### §8.6 客户要求"信创适配"，你会怎么验收？为什么"安装成功"不算验收？

**1. 考察点**
- 是否知道适配是**从芯片到权重的一条链**，而不是某一个组件；
- 是否理解验收粒度是**算子级**；
- 有没有"差异要入合同"的意识。

**2. 参考答案框架**

**第一层：五类盘点。** 芯片 / 指令集（含**关键算子**）、操作系统、数据库与中间件、加密与国密、模型与权重——每类给出三态（已适配 / 适配中 / 不支持）。

**第二层：为什么"能启动"不算验收。** 因为客户真正关心的是**"结果与 x86 一致吗"**——那是**逐算子**的精度问题。整体跑通只能给出"能启动"这个结论，而**数值差异（向量检索的相似度排序、量化推理的输出精度）在整体跑通里测不出来**，它会在上线后以"偶发不一致"的形态出现。

**第三层："关键算子"的判定标准。** **它的输出会不会进入业务结论**——向量相似度排序会、量化推理精度会、日志格式化不会。**按这条标准筛，清单会比想象中短**，而这也让逐算子验收变得可行（成本按算子数计）。

**第四层：这份清单必须由平台团队自己维护，且在设计期就存在。** 它依赖对自身架构的了解——**客户与厂商都给不出**。设计期不存在这份清单，意味着"哪些能力可以用"这个决定是交付前才做的，而那时能改的空间已经很小。

**第五层：差异三类分档并写进合同。** ① 可解释且可接受 → 写进验收项（附对照数据）；② 可解释但不可接受 → 列改造计划；③ **不可解释 → 写进"不支持清单"并在合同里明确**。**不写清单，验收时所有差异都会算作你的缺陷。**

**第六层：断供替代路径。** 对每一类里的**外部组分**，给出断供时的替代路径（换哪个库、降级到什么能力、需要多少时间）——信创验收问的不只是"现在能用吗"。

**第七层：把"逐算子验收"落成可排期的动作。** 成本口径是 `成本 ≈ 算子数 × 单算子核验工时`【推算：单算子核验含"跑通 + 精度对照 + 记录结论"三步，请按你自己的算子清单与工时口径代入】（§6.4）。这条推算的意义不在数值，而在于它**把交付风险从"不可估"变成"可估"**：先数算子、再定排期；而"整体跑通"给不出任何排期依据。三个可执行约束：① 精度对照必须用业务真实数据而不是合成数据，样本要覆盖边界区间【经验：随算子类型浮动】（§6.4）；② 差异结论要**逐算子记录并给出结论**（可接受的进验收项、不可解释的进"不支持清单"），只记录不结论等于把决定推给验收当天；③ 清单会随产品版本漂移，因此要指定复核人——§4.2（5）把国产化盘点写成一项常态工作，而不是一次性表单。

**第八层：把"断供"也做成一次演练，而不是一份说明。** 断供预案的可信度由演练决定：能不能真的用替代组件跑一次、降级后的能力边界是什么、需要谁配合。**判据是形态而不是时间**——换成哪个库、降级到什么能力、谁来执行。这与 §4.7 的"演练前后两组数字"是同一条纪律：**没有演练过的预案，在评审时与没有预案几乎等价**，区别只在于前者更危险，因为它给了决策者一种虚假的安全感。

**3. 常见陷阱**
- 把适配当成"部署阶段的一次工作"；
- 只验证安装成功与功能可用；
- 说不出"关键算子"的筛选标准；
- 差异只做技术记录、不入合同；
- 换国产数据库就认为完成了整条链的适配；
- 把"适配"理解成"换国产组件"（适配是**从芯片 / 指令集到模型权重的一条链**，换掉数据库只动了这条链的一环，而**关键路径上的精度差异恰恰最容易出在向量检索内核与量化推理内核这两环**——它们是 AI 栈新增在关键路径上的算子）；
- 用"客户没提这个要求"来决定不做清单（清单的用途不只是验收，它同时是**评估"还能换什么"的唯一依据**——§6.4 的断供替代路径直接依赖它，而断供是客户提要求之前就可能发生的事）。

**为什么这几种错法看起来都对**：因为"装上、能跑"是一个**可观察的、有二值结论的事实**，而"结果与基线一致"不是——后者要逐算子对照才能给出结论，且差异往往是小概率的偶发偏差，在演示与冒烟测试里测不出来。**它们共同的机制是：验收粒度决定了验收能发现什么**——整体跑通检验的是"链路能连通"，逐算子核验检验的是"每个算子的输出是否落在可接受区间"，前者对后者的结论几乎不含信息。所以这几种错法在"能启动"这个结论上都成立，只在上线后的偶发不一致上失效。而"差异不入合同"这条更隐蔽：它在技术上是可记录的（大家都知道有差异），只是在**责任归属**上没有落笔，因此它不产生工程问题，只在上线后的一次争议里同时产生法律问题与项目问题——这正是它"看起来不是技术问题、因而不被技术团队处理"的原因。

**4. 追问预测**
- "向量检索内核换成国产实现后，召回率下降 2%，你怎么办？"
- "精度对照用什么数据？合成数据够不够？"
- "断供场景下，你的降级顺序是什么？"
- "适配清单会随产品版本漂移，谁负责复核？"
- "客户只提供了 x86 上的历史结果，你没有可用的基线怎么办？"（答：**先建立基线再谈适配**——在动手之前用当前环境跑一遍同样的输入、把结果存成对照集，否则"一致不一致"无法判定。这一步最容易被跳过，因为它在适配开始之前就要做，而那时还没有人关心它）
- "适配清单和信创目录的关系是什么？"（答：**两者不是一回事**——目录回答"有哪些可选"，清单回答"我的关键路径上用的是哪些、换掉之后能力边界是什么"；前者是采购材料，后者是架构材料。而只有后者**不能被客户或厂商提供**，§3.2.8 的国产化盘点要求点名候选产品，并指出向量库 / 消息队列 / 调度器三类最常空白）
