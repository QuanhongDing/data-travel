## 6. 落地实践

> **本节的材料纪律（先说清楚）**：安全领域有一条不同于其他主题的限制——**配置细节本身就是敏感信息**，公开"我们怎么防的"等于给出攻击面，而效果数据（漏出率、误拦率）只在内部有意义。因此本节 4 例的构成是：
>
> - **§6.1–§6.2** 是**公开材料层面的机制复述**（分级怎么变成策略、密钥与数据的权限怎么分成两条线），**不是对任何一家公司内部实现的转述**；方括号内是**来源类型 + 年份**，属**建设方自述**，不构成本书 §5 判据里要求的「第三方（非厂商）公开生产案例」。
> - **§6.3–§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证——**本主题的匿名比例高于其他主题，原因是上面那条限制，不是材料没找。**
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 阿里"**把分级变成策略、把策略下推到检索条件：安全从"人工审批"变成"系统判定" 5+ 年**"（2019-2024）

**背景（Why）**

数据平台上的权限申请，最初是**人工审批**的形态：

- **审批解决的是"这一次"，不是"这一类"**——申请一次批一次，同一个人要访问十个资源就走十次流程；
- **审批只到"表 / 字段"，不到"行"**——而业务上大量需求是"我这个部门只看自己那部分行"；
- **审批记录不构成策略**——它是一次授权事件，不是一个可被检索、可被下推的判定条件；
- **于是出现了两种坏的收敛**：要么批得越来越宽（审批疲劳），要么业务绕开平台直接连库（旁路）。

两条**约束**决定了后面每一步的顺序，还有一条**代价**不在第一天显现：

- **约束（顺序不可颠倒）**：**分级必须先于策略**——策略里含"这一级配什么机制"，分级没有落下来，策略写不出来；而分级是 [§01](../01-ai-data-governance/01-ai-data-governance.md) 的产出，**本主题在这个接口上是消费者而不是生产者**。
- **约束（人）**：**策略要有 Owner，且例外要有人接**——把"每一次"压成"每一类"之后，剩下的例外（新资源、新角色、边界情形）必须有人处理，否则例外会自然退回成"每次都要人批"。
- **代价**：这条链要付的是一道**常设流程**——**分级变更 → 复核策略**。它在第一天不疼（分级与策略各自都能独立上线），**等分级第一次被修改时才会暴露**：改一次分级要复核一批策略，没人认领就会出现"分级过期但没人敢改"（§6.1 失败教训的机制）。

**触发点（What）**

阿里在其数据平台体系里把**数据分级与权限策略做成了平台的一等能力**（[阿里公开材料 2019-2024]，核验入口是其数据安全与数据中台相关的官方文档，**按当前版本核**；本主题只描述这一类能力的**机制形状**，不比较具体产品）。它给出的启示是**"分级 → 策略 → 下推"这条链**：

- **分级是策略的输入**（哪一级配什么机制），不是终点；
- **策略是机器可读的判定条件**（主体属性 × 资源属性 × 环境），不是审批记录；
- **判定要下推到访问路径的入口**（检索 / 查询的条件里），不是结果上的过滤。

这条链的**代价落在"谁维护"上**：分级会变（新业务、新数据域、监管口径调整），策略要跟着复核，**这一环没有 Owner，链就会在下一次分级变更时断掉**——而断掉的方式是静默的（策略仍然生效，只是它对应的是一个已经作废的分级）。

**详细做法（How）**

**① 分级产出与策略产出的分离**

- **关键设计**：分级给出的是 `conf_level` 与 Owner（[§01](../01-ai-data-governance/01-ai-data-governance.md) 的产出），**策略给出的是"这一级 + 这一类主体 + 这一类动作 → 允许 / 拒绝 / 脱敏"**。两者是两次独立的产出，**分级改了策略不会自动跟着变**（因此需要一条"分级变更 → 复核策略"的流程）。
- **为什么必须分开**：把它们合成一个动作，**结果是"改一次分级要改一堆策略，于是没人敢改分级"**——分级会迅速过期。
- **判据**：随机挑一条正在生效的策略，问"它依据的是哪一次分级结果"——**答不出、或答案已经过期，就说明"分级变更 → 复核策略"这条流程没有在跑**。

**② 策略从"审批记录"变成"可下推的条件"**

- **关键设计**：策略的表达式要能编译成**检索 / 查询引擎能吃的形式**（关系库的谓词、向量库的元数据过滤）。这是 §5.3.1"判定前移"的工程形态。
- **关键性质**：**它把"这一次能不能看"变成了"查询时系统自己会算"**——于是审批从"每一次"降到"每一类"，人只处理**例外**（新资源、新角色、边界情形）。
- **关键示意**：

  ```text
  两种权限形态的差别（决定了人工审批会不会成为瓶颈）
    ── 形态 A：审批记录 ─────────────────────────────
       申请 → 人工批 → 落一条授权 → 下次申请再来一遍
       可下推吗？不能（它不是判定条件，是一条事实）
       规模上限：人工处理量（λ/μ）
    ── 形态 B：策略 + 下推 ──────────────────────────
       策略 = f(主体属性, 资源属性, 环境)
       编译 → 检索/查询的过滤条件
       人只处理例外（新资源 / 新角色 / 边界情形）
       可核查性：任意一次访问都能回答"按哪条策略允许的"
    ────────────────────────────────────────────────
   判据：同一个人申请同一类资源第十次时，还需要人批吗？
        需要 → 说明策略还没有形成（那十次是同一个判定）
  ```

- **一次产出的字段形态**（示意字段，非某厂商格式）：策略要能被编译，就必须落到**有限的一组字段**上；凡是写成自然语言、或依赖人工判断的条件，都编译不出来——它就是"审批记录"换了个存储位置。

  ```jsonc
  // 一条策略的"一次产出"：字段划分对应到执行点（可对照 §4.5 模板 2 的伪代码）
  {
    "policy_id":  "pl-<id>",          // ← 举证时的追溯键：任意一次访问都答得出"按哪条允许的"
    "conf_level": "L3",               // ← 来自分级（§01 的产出），本主题只消费
    "subject":    { "dept": "$user.dept", "role": "analyst" },
    "action":     ["read"],
    "resource":   { "domain": "order" },
    "predicate":  "row.dept = $user.dept",  // ← 编译到查询 / 检索的过滤条件（下推点）
    "mask":       ["user_id_card"],         // ← 编译到列掩码（访问时改写）
    "effect":     "allow"
  }
  ```

- **判据**：**同一个判定条件，能不能在检索 / 查询侧被编译出来？** 编译不出来（条件写成自然语言、或要人判断），它就仍然是审批记录的变体；能编译出来，它才是一个可下推的判定。

**③ 旁路对账作为收敛动作**

- **关键设计**：把"受控路径的访问统计"与"被访问系统自身的审计日志"定期对账，**差异即旁路**（§4.4 的三条安全判据之一）。
- **为什么这一步不能省**：策略形成的直接后果是"绕过去显得更省事"——**如果旁路比走策略快，团队就会旁路**；对账是唯一能把这件事从"靠自觉"变成"靠检查"的动作。
- **判据**：**对账差异能不能被逐条解释**——解释不了的差异不是"日志口径不同"，那就是一条真实的旁路。按 §4.4 的三条安全判据，**差异收敛**（而不是差异为零）才算这一条过关。

**具体数字（档位标注）**

- 旁路对账的成本：约**半天**一次（取两边一天的日志做差异比对）【经验：随日志字段完整度浮动】——**这是本主题里投入产出比最高的一类动作**：它同时发现"策略被绕过"与"出口统计不准"两件事。**这个量级决定了它必须挂进已有的巡例**：约半天一次意味着它靠"想起来就做"做不下去，只能附在某件每周本来就要做的事上（对账、月度审计、值班周报）；否则第一次延后就会变成永远不做。
- 策略维护的人力：随**资源数 × 策略维度**增长（§4.6）——**这一项在立项时最容易被算成"配置一次"**，而它是常备投入。**这个量级决定了它的曲线形状**：随**资源数 × 策略维度**增长、**不随数据量增长**（§4.6 的同一条推论）——所以它不会因为数据翻倍而变贵，只会因为"又接了一个数仓 / 又多了一个密级档"而变贵；按"配置一次"立项，就是把它当成了一条平的曲线。
- **自测动作**：任挑一次访问，回答"它按哪条策略被允许的"；再从受控路径统计与目标系统日志各取一天对账一次。**两项要一起做才算走过一遍**：前者证明"判定可追溯"（策略真的在有人的路径上生效），后者证明"出口与统计一致"（没有被绕开）——只做前一项，会得到一个自洽但可能被完全绕开的结论。

**失败教训**

**第一版把分级做完了，就认为安全做完了**——分级表很完整，但访问路径上仍靠人工审批，SQL 直连仍然存在。半年后审计问"你怎么证明机密级没有被越权访问"，团队只能拿出那张分级表。教训：**分级是输入，不是机制**；**从分级到"系统判定"之间还隔着策略与下推两步**——这两步不做，分级只是一份文件。

**为什么会写成那样（机制层）**：因为这三件东西的**生命周期不同**，而"一件事"的直觉会把它们压成一次交付——**分级随业务变**（新业务、新数据域）、**策略随分级变**（分级改了要复核）、**编译产物随引擎版本变**（过滤表达式与掩码能力随时在变）。三个生命周期意味着一份文件天然会过期，而**它过期时不会报错**：分级表看着还是完整的，只是它对应的策略已不再成立。因此这条链的关键不是"做得全"，而是**让三件东西各自有一个变更入口**（分级的来源、策略的评审、编译产物的回归），并且**在变更入口上留一个能回答"依据哪一次分级"的字段**（上面 ② 的 `conf_level` 与 `policy_id`）。

### 6.2 微软"**把密钥与数据的权限分成两条线：数据管理员也读不到密钥 5+ 年**"（2019-2024）

**背景（Why）**

加密类机制最容易被忽视的一点是**密钥的权限与数据的权限必须是两条线**：

- **加密的目的是让"拿到数据"不等于"看懂数据"**——但如果能读数据的人也持有密钥，这个目的直接落空；
- **现实中它们常常共享一套权限**——因为密钥被当成"配置"，而配置的管理权限通常跟数据管理员是同一批人；
- **后果是静默的**——加密功能全部正常，"加密"这个动作确实发生了，只是**它没有把任何人挡在外面**。

两条**约束**与一条**代价**决定了做法：

- **约束（边界只能这么画）**：这类场景里"数据不出域"是不可能的（数据本来就要被使用），因此**唯一可做的边界是"拿到数据 ≠ 看懂数据"**——而这条边界只能由权限线来画，不能由算法来画。
- **约束（吊销必须有独立执行者）**：**只要"持有密钥的人"和"能阻止轮换的人"是同一批，吊销能力就是纸面的**（§7.3.3 的机制差异：密钥的所有权决定轮换的执行者，原文写"这不是技术问题，是职责分离问题"；§8.4 第三层："轮换的执行者要独立"，判据是轮换有独立流程与值守人）。
- **代价**：两条线带来的不是新能力，而是**一道常设的值守**——密钥轮换与吊销要有值守人（§4.6 的常备人力口径），并维护一份"持有该密钥的组件"清单。这两件事都不产出可见功能，因此**最容易被排在功能需求之后**，一直排到"一次演练或一次泄漏"把它们翻出来（§4.7 的三条纪律）。

**触发点（What）**

微软在其密钥管理服务里把**密钥操作与数据操作的权限分开**（[微软公开材料 2019-2024]，核验入口是其密钥管理服务的官方文档，**按当前版本核**）：密钥的读写、轮换、删除是独立的一组权限，可以授予与数据管理员完全不同的人。它给出的启示是一条**职责分离**判断：

- **密钥的生命周期（生成 / 轮换 / 吊销 / 销毁）与数据的使用生命周期是两个流程**，因此它们的权限天然应当分开；
- **轮换与吊销必须有独立的执行者**——否则"谁持有密钥谁就能阻止轮换"，吊销能力形同虚设。

这条判断的**代价是运维面的扩大**：两条权限线意味着**两条审计线、两套演练、两份清单**（密钥清单 + 持有该密钥的组件清单）。它换来的是"吊销能力是真的"，而这一条**只能在一次演练里被验证**，靠配置审阅是验不出来的——因为审阅看到的是"权限分开了"，演练才能看到"分开的两边是不是都通着"。

**详细做法（How）**

**① 两条权限线（核心设计）**

- **关键设计**：数据侧权限回答"能不能读这份数据"，密钥侧权限回答"能不能用这把密钥解开它"；**两套授权主体不同、审计记录不同、演练不同**。
- **关键性质**：**只有两条线分开，"加密"才构成一个真实的访问控制点**——否则它是**一次编码**（把数据换成另一种表示），而不是一道门。
- **关键示意**：

  ```text
  两条权限线（分开之后，"加密"才是一道门）
    ── 数据侧权限 ──────────────────────────────
       主体：数据管理员 / 分析师 / 应用账号
       动作：SELECT / 导出 / 订阅
       审计：数据访问日志（一份）
       演练：越权取数尝试被拒
    ── 密钥侧权限 ──────────────────────────────
       主体：密钥管理员（与数据侧主体不重叠）
       动作：生成 / 轮换 / 吊销 / 销毁
       审计：密钥操作日志（独立一份）
       演练：拿数据权限去申请解密 → 必须被拒
    ────────────────────────────────────────────
   判据：一个只用数据权限、没有密钥权限的账号，
        能否通过正常路径读出明文？能 → 两条线没有分开
  ```

- **可核查的判据**：**一个只用数据权限、没有密钥权限的账号，能否通过正常路径读出明文？** 能，说明两条线没有分开。

**② 轮换与吊销的路径**

- **关键设计**：密钥轮换有独立流程与值守人；**吊销必须能立即生效**（同 [Ch6 §03 §3.2.5](../../06-multi-model/03-model-gateway/03-model-gateway-section-3-sec3.md) 的凭证托管：密钥在服务侧时吊销是一次改配置，秒级；在应用侧时吊销是一次发布，小时到天级）。
- **为什么强调"立即"**：密钥泄漏的处理时间与损失**线性相关**——它是一道"正在流血"的口子，而不是一个"已经坏了"的组件。
- **判据**：**吊销一次密钥要多久？** 这里要的不是一个数字，而是一个**形态**——改配置（秒级）还是发版（小时到天级）；答不出形态，就说明这条路径还没有被演练过。

**③ 轮换要一次做完**

- **关键设计**：旧密钥在轮换后**必须真正失效**（或设一个明确的重叠窗口），而不是"保留着以防万一"。
- **为什么**：**留一半等于没换**——旧密钥仍然是一个可用的入口，而团队会以为已经换过了（§4.4 的"轮换要一次做完"）。
- **判据**：轮换之后**拿旧密钥去解密一次，必须失败**——成功就说明"留了一半"；另一种等价判据是**重叠窗口有没有明确截止时间**（"保留着以防万一"就是没有截止时间）。

**④ 轮换的顺序：双密钥窗口，而不是"换一把"**

- **关键设计**：一次轮换实际上是**三步**——① 发布新版本，让所有持有方"能解两个版本"（读路径兼容）；② 把数据用新密钥重加密（写路径切换）；③ 确认旧密钥不再被任何读写路径使用后，再吊销。**顺序颠倒的代价是不对等的**：先吊销后切换，会让"还没升级的持有方"手里的数据直接读不出来。
- **为什么不能"停服一次换完"**：因为**持有方的数量通常大于你以为的数量**（见上面"持有该密钥的组件数"），而停服窗口由最慢的那个组件决定；这类失效的共同形状是——**故障发生在读取时，报出来的却是业务错误**。
- **关键示意**：

  ```text
  轮换的三步（读兼容 → 写切换 → 旧钥失效）
    ① 发布新版本：读路径同时支持 K_old / K_new
    ② 重加密：写路径全部写入 K_new（旧数据按批重写）
    ③ 吊销 K_old：先确认"读路径已无 K_old 命中"，再吊销
    ──────────────────────────────────────────────────
    反面：① → ③ 直接跳（"换一把更省事"）
      → 未升级的持有方在下一次读取时失败
      → 报出来的是业务错误，不是"密钥错误"（根因静默）
  ```

- **判据**：能不能说出"**当前还有哪些持有方在用旧密钥**"——答不出，第三步就不能做；而这个答案只存在于上面那张"持有组件清单"里，**不在密钥管理系统里**（密钥系统只知道密钥，不知道谁持有它）。

**具体数字（档位标注）**

- 吊销生效时间：密钥在服务侧时是**秒级**（改配置），在应用侧时是**小时到天级**（等所有实例重启）【经验：随发布方式与实例数浮动】——**这就是"密钥放哪"的价值，它是纯结构差异，与运维水平无关**。**这个量级决定了止损窗口可不可接受**：秒级意味着泄漏处置是"一次配置变更"，小时到天级意味着处置和一次发布同周期——而处置时间与损失线性相关（上面 ② 的机制），所以后者在受监管场景里常常直接不可接受，**这也是"密钥必须上收到服务侧"这条结论的唯一理由**。
- 轮换成本：随**持有该密钥的组件数**增长（每个组件都要支持新版密钥）——**因此"谁持有密钥"这个清单要维护**，否则轮换时会发现某个无人知晓的副本【经验】。**这个量级决定了轮换是一项"每次都要重新盘一遍"的例行工作，而不是一次性改造**：组件数只增不减（新服务、新副本、新导出工具都会持有它），所以这条曲线随系统规模上升，把它算成"上线时做一次"的人，第二次轮换就会卡住。
- **自测动作**：查一次你的密钥清单与"持有它的组件"清单；再确认**吊销一次密钥需要多久**（改配置还是发版）。**两项要一起看**：清单答的是"密钥有多少把、在谁手里"（可控性），演练答的是"真出事时多久能停住"（可止损性）——只有清单没有演练，等于不知道第二条线是不是真的通着。

**失败教训**

**第一版把密钥放在配置中心，而配置中心与数据仓库同一批管理员**——加密全部生效，但一次内部审计发现：能读加密表的人同时能读密钥。教训：**"配了加密"与"加密构成一道门"是两件事**——判据不是"加密开着吗"，而是"**能读数据的人是不是读不到密钥**"。

**为什么会写成那样（机制层）**：因为**密钥在默认配置里天然会落到数据管理员手里**——它是一份配置，而配置的管理权限通常跟着数据侧走；更关键的是**"加密"这个动作本身从不报错**：加密开着、解密正常、日志干净，**没有任何信号提示两条线正在合并**。因此这类失效只能靠一个反向问题发现——**"能读这份数据的人，能不能读到它的密钥？"**——问的是权限图的连通性，而不是加密是否开启；而连通性只有画出来（上面那张两条线的图）或演练一次才看得见。

### 6.3 某股份制银行"**等保 2.0 落地：把"一个中心、三重防护"逐条指认到控制点 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

该行的 AI 平台要过等保测评，团队的准备方式是**"把安全能力清单整理成一份材料"**。

这条路的**约束**是：**测评的判定标准是"可举证性"，不是"能力强度"**（§2.2 的映射覆盖判据就是这件事的形式化）——因此准备的产出物是**一张对照关系表**，而不是一套更强的安全能力。**代价**是它看起来"不像工程"：投入是文档与人周（下面给了口径），产出的东西不提升任何防护强度，因此**在排期里最容易被排在功能需求后面**，一直排到测评通知下来——而那时补证据链的时间通常比补机制更长（§3.6 的通用判据）。

**触发点（What）**

**预评估就被打回**：测评方逐条问"**这一条，你的控制点在哪里？**"，而团队的材料是"我们有 WAF、有堡垒机、有数据加密"——**能力清单回答不了"控制点在哪"**。例如"安全区域边界：访问控制"这一条，团队答"我们有人审"，测评方要的是"**哪一层在做这件事、拒绝记录在哪里、怎么证明它生效**"。

这里要看清的是**约束的形状**：能力清单答不了控制点，**不是因为材料写得不好，而是因为"能力"与"控制点"是两个粒度**——能力说的是"我们有什么"（存量描述，可以一直往上堆），控制点说的是"这一条要求由哪一层承担、留痕在哪里、怎么证明它此刻生效"（映射关系，必须闭合）。**代价**是这两层之间只能人工对一遍：**没有工具能从一份能力清单自动推出控制点映射**（下面的具体数字给的正是这次人工作业的口径），因此它是本主题里少见的"人力成本可以事先算准"的工作。

**详细做法（How）**

**① 把标准逐条展开，为每条配"三问"**

- **关键设计**：对每条要求回答——**控制点在哪**（组件 / 配置）、**执行结果存在哪**（日志 / 报表）、**怎么证明它此刻生效**（演练动作）。三问缺一即为 `⊥`（§2.2 的映射覆盖判据）。
- **关键示意**（一行是一种控制项的形态，可对照 §4.5 模板 3）：

  ```text
  映射表的一行：三问各占一列，"没有空行"就是判据
  ┌──────────┬──────────────────┬────────────────────┬──────────────┬──────────────────────────┐
  │ 要求摘要 │ 控制点在哪        │ 执行结果存在哪      │ 生效证明动作  │ 结论                     │
  ├──────────┼──────────────────┼────────────────────┼──────────────┼──────────────────────────┤
  │ 区域边界 │ 工具出口鉴权+人审 │ 拒绝日志（可查原因）│ 受监管租户请求│ m(c) ≠ ⊥  ← 已指认       │
  │ 访问控制 │ （唯一出口）      │                    │ 指向外部端点  │                          │
  ├──────────┼──────────────────┼────────────────────┼──────────────┼──────────────────────────┤
  │ 安全运维 │ （未指认）        │ （未指认）          │ （未指认）    │ m(c) = ⊥  ← 失分项       │
  │ 管理     │                  │                    │              │                          │
  └──────────┴──────────────────┴────────────────────┴──────────────┴──────────────────────────┘
  判据：整张表没有空行 —— 有 ⊥ 的行，就是测评时"这条你怎么证明"的那一行
  ```
- **为什么"三问"这个形式有效**：它把一次**开放式说明**（"我们做了什么"）变成了一次**可勾选的检查**（三问各有一个具体答案）。**测评方要的正是后者**——因为后者的每一条都可以被独立核验。
- **判据**：随机挑一条要求（不必等测评），**三问能不能各给一个具体答案**；三问缺一即为 `⊥`。这条判据可以自己对着表做，且任何一问答不出时，缺的是哪一问就已经指向了补法（缺第一问答"组件在哪"，缺第二问答"留痕在哪"，缺第三问答"演练在哪"）。

**② AI 场景的特殊项要单独指认**

| 等保结构 | AI 平台上的控制点（本例指认到的位置） |
| --- | --- |
| 安全管理中心 | 策略服务的**唯一权威源**（权限策略、出网策略、留痕表不各配一份） |
| 安全通信网络 | 模型端点的**出网白名单**（按租户分级）+ 连接审计 |
| 安全区域边界 | 工具出口的鉴权与**人审闸门**（不可绕过的唯一出口） |
| 安全计算环境 | 沙箱隔离、**凭证按实例发放**、镜像与依赖可追溯 |

- **为什么 AI 平台需要单列**：通用项（网络 / 主机 / 数据库）企业通常已有控制点，而**模型端点、工具出口、沙箱**是 AI 平台新引入的组件——**它们不被指认，就会出现"通用项都有，AI 特有的那几条全是 `⊥`"**。
- **判据**：**`⊥` 集中在哪一类控制项上？** 集中在这三处 AI 特有组件，说明是"新组件没被纳入对照表"；集中在"安全运维管理"这类管理项，说明缺的是制度与周期而不是组件——**两种缺口的补法完全不同**（前者补指认与挂点，后者补文档与责任人），看这一列就能分流。

**③ 演练动作写进材料**

- **关键设计**：每条的"生效证明动作"写成可执行的一句（例如"让受监管租户的请求指向外部端点，验证被拒绝"），**并保留演练记录**。
- **为什么**：**演练记录是唯一能证明"控制点此刻生效"的材料**——配置截图证明的是"配过"，而配置会漂移（§4.2（6））。
- **判据**：每条的"生效证明动作"**是不是一句可执行的话**——有人、有步骤、有"可以失败"的结果（例如"让受监管租户的请求指向外部端点，验证被拒绝"）。写成"定期检查"就不算：它既没有执行者，也没有失败的可能，因而既不能证明生效，也不能在漂移被发现前给出信号。

**④ 先把"定级与备案"放在映射表之前**

- **关键设计**：**定级决定后面整套控制项的范围与测评频次**——§3.2.8 的五步是"定级 → 备案 → 建设整改 → 等级测评 → 监督检查"。本例的团队第一版材料直接从"控制项"开始，**跳过了定级**：映射表本身对，但**范围是猜的**。
- **为什么这一条在 AI 平台上更容易错**：AI 平台的边界天然模糊（它读写多个业务域的数据、对外提供生成能力），**"这套系统被攻破时谁的利益受多大损害"比传统系统更难答**；答不出就只有两种走法——往低里定（监督检查阶段是明确的问题）或无限搁置（材料停在"能力清单"这一层）。**这不是文档技巧问题，是系统边界没被定义**。
- **判据**：**定级文档与备案回执在不在"建设整改"之前**——两件都应当早于映射表。如果映射表已经写完而这两件还没有，说明后面四个步骤的范围都建立在猜测上，可能要整体重做（§3.2.8 的流程图上那句"这一步定错，后面四步全部要重做"就是这个意思）。

**⑤ 把三问表接进变更流程，否则它会随系统一起过期**

- **关键设计**：映射表是一份**会漂移的产物**——它描述的是"某个版本的系统里，这一条由哪一层承担"；组件一旦替换、策略一旦迁移、责任人一旦换人，表上的答案就不再成立，而**表本身不会报错**（§4.2（6）的策略版本化讲的是同一件事）。
- **为什么"过期"比"缺项"更难发现**：缺项是空的（看得见），过期是填着的（看不见）——**一行填满的过期答案与一行填满的有效答案，在表上长得一模一样**。要让表活下来，唯一有效的做法是把它挂到已有的变更流程上：**凡涉及控制点的变更（组件替换、策略迁移、出口调整）都触发对应行的复核**，并留下最近一次复核的时间与触发它的变更记录。
- **判据**：**这张表的最近一次修订是什么时候、由哪一次变更触发的**——答不出触发变更，它就已经是一份静态文档；再抽一行问"它的控制点现在还在跑吗"，这一问能把"填满的过期答案"逼出来。

**具体数字（档位标注）**

- 材料工作的投入：**控制项数 × 每条三问**，是**纯文档工作**，但它是本主题投入产出比最高的一项【经验：通常以人周计，且远低于补一套新机制的成本】。**这个量级决定了两件事**：一是**它可以被提前排期**（人周是可估的量，"补一套新机制"不可估）；二是**它必须一次做完**——分批做时每一批都要重新对齐口径（三问的措辞、控制的边界、证据的存放约定），成本不会按批线性分摊。
- 预评估与正式测评的差距：本例中"预评估被打回"到"正式通过"之间的主要工作**不是补能力，而是补指认与证据**【经验：这条经验在多数受监管行业成立】。**这个差距决定了优先级**：既然缺口主要在指认与证据，**先补映射表就比先买设备更快通关**——这与 §4.1 的落地顺序（映射排在机制之后）是同一个判断；"可以并行开始"的依据在 §7.5 第 4 问（证据族"不依赖前 3 问的结果，可以并行开始"）与 §7.6 组合原则②（"证据族与前两族并行开始"）。
- **自测动作**：现在就能做——挑一条你所在行业的合规要求，回答那三问。**任何一问答不出，那条就是 `⊥`。** 这一步**不需要等测评通知**，也不需要测评方参与：它是本节里唯一一个"立刻可做、且结果可复现"的动作（同一张表换个人来判，结论应当一致）。

**失败教训**

**把测评准备当成"整理能力清单"**——第一版材料里全是能力名词（WAF / 堡垒机 / 加密），没有一条能回答"控制点在哪、证据在哪、怎么证明生效"。教训：**合规的判定标准是"可举证性"，不是"能力强度"**；因此最高效的动作是把**每一条要求 → 我的哪一个控制点**写全，而不是再上一套新机制。

**为什么会写成那样（机制层）**：因为**"有安全能力"与"能证明安全能力"用的是两套证据**——能力清单证明的是"我们做过什么"（存量描述，可以一直往上堆），测评要的是"这一条由哪一层承担、此刻是否生效"（映射关系，必须闭合）。**团队按"把做过的事写全"准备，会自然地产出一份没有闭合关系的材料**：每一句都是真的，但没有任何一句能回答"这一条对应哪个控制点"。另一层机制是**"能力"比"控制点"更容易获得**——设备清单可以从采购与资产系统导出来，而控制点映射只能逐条人工对；于是材料会向容易获得的那一侧膨胀（§3.5 反模式表"等保映射留白"的成因栏写的就是这句）。

### 6.4 某大型制造企业"**信创适配：按算子清单验收，把差异写进合同 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证。

**背景（Why）**

客户的采购要求包含信创适配，团队此前交付的都是 x86 环境。

这条路的**约束**是：**"结果一致"没有通用标准**——它与具体算子、精度口径、输入分布都有关，因此验收粒度**只能由采购方与交付方在设计期谈定**，事后补不上。**代价**是逐算子核验是一笔**按算子数增长的人工成本**（下面给了推导链），而且它必须付在交付之前——也就是说，**这笔成本无法用"先上线再说"推迟**，越晚开始，能改的空间越小（§7.7 的"两项代价部分不可逆"）。

**触发点（What）**

**整体跑通但结果对不上**——同一份输入在国产架构上跑出来的分析与 x86 上不一致（差异出现在向量检索的相似度排序与量化推理的输出上）。客户的问题很简单：**"哪个是对的？"** 团队答不上来，因为**他们只验证了"能启动"，没验证过"结果一致"**。

这里有一条**容易被忽略的代价**：**"结果对不上"这件事本身没有一个自然的判据**——同一个输入在两种架构上给出两个数时，**任何一方都无法单独证明自己是对的**（x86 只是"之前的基线"，不是"正确答案"）。因此逐算子验收要做的不是"证明国产算错了"，而是**记录差异、给出结论、把它写进合同**（下面 ② 的三类分档就是为此）。这也顺带决定了**对照必须用业务真实数据**：合成数据上的差异判断不了"哪一侧更贴近业务"，于是差异会永远停在"无法解释"这一档。

**详细做法（How）**

**① 维护一份"关键算子清单"（设计期就开始，不是交付前）**

| 类 | 盘点对象 | 验收粒度 |
| --- | --- | --- |
| 芯片 / 指令集 | CPU / NPU、驱动、**向量检索内核、量化推理内核、压缩加密库、Python 扩展** | **逐算子**跑通 + 精度对照 |
| 操作系统 | 发行版、内核、依赖库 | 安装与运行 |
| 数据库 / 中间件 | 关系库、消息队列、缓存、向量库 | 功能 + 性能 |
| 加密与国密 | 算法库、证书链、国密要求 | 合规清单 + 互操作 |
| 模型与权重 | 推理栈、量化格式 | **结果一致性（与 x86 对照）** |

- **关键设计**：这份清单**必须由平台团队自己维护**——它依赖对自身架构的了解，**客户与厂商都给不出**（§5.3.6）。清单在设计期就该存在，因为它会影响"哪些能力可以用"。
- **关键性质**：**"关键算子"的判定标准是"它的输出会进入业务结论"**——向量相似度排序与量化推理的精度都会，日志格式化不会。**按这条标准筛，清单会比想象中短**（这也让逐算子验收变得可行）。
- **判据**：把清单上的算子逐个问一句"**它的输出进入哪一条业务结论**"——答不出的从清单剔除（降到"安装与运行"粒度），答得出的标出它影响的是哪一类结论（排序 / 计数 / 阈值判定）；**这条判据的作用是让清单可辩护**："是否在关键路径上"这个说法谁都成立，而"输出是否进入业务结论"是可以逐条对的。

**② 差异三类分档，且写进合同**

- **关键设计**：每一条差异**必须落到三条出路之一**（下面示意），而"没有落到任何一条"这一种状态本身就是最贵的——它会在验收时被算作交付方的缺陷。
- **关键示意**：

  ```text
  差异处置的三条出路（每条差异必须落到三条之一）
    对照跑通 ──┬─ ① 差异可解释 & 可接受  → 写进验收项（附对照数据）
               ├─ ② 差异可解释 & 不可接受 → 列改造计划（换实现 / 调精度口径）
               └─ ③ 差异不可解释          → "不支持清单" → 进合同（明确边界与范围）
    ──────────────────────────────────────────────────────────────
    没有落到三条之一的差异：验收时一律算作交付方缺陷
      —— 这就是"差异不入合同"的机制：不是争议变大，而是争议变成单方面的
  ```

- **可解释且可接受**：写进验收项（附对照数据）。
- **可解释但不可接受**：列改造计划（例如换一个数值更稳定的算子实现）。
- **不可解释**：写进**"不支持清单"**并在合同里明确——**不写清单，验收时所有差异都会算作你的缺陷**。
- **判据**：**每一条差异有没有一条对应的处置**（进验收项 / 列改造计划 / 进合同）——把差异清单与合同附件对一遍，**对不上的每一条都是未来的交付争议**；这条判据在交付前就能做完，不需要客户参与。

**③ 断供替代路径**

- **关键设计**：对每一类里的**外部组分**，给出断供时的替代路径（换哪个库、降级到什么能力、需要多少时间）。
- **为什么**：信创验收问的不只是"现在能用吗"，还有"**这条链里哪一环是外部的、断了怎么办**"。
- **判据**：对每个外部组分问三问——**断了换什么、降级到什么能力、切换需要多少时间**；三问答不出（尤其是第三问），这条替代路径就还只是意愿而不是方案。这条清单之所以要进合同，是因为**断供是采购方同样关心的风险**——把它写进合同不是让利，而是把一件双方都要面对的事提前定价。

**④ 设计期做一次"能力裁剪"：哪些能力可以不做**

- **关键设计**：逐算子验收的清单越长，交付风险越大；因此设计期要做的不只是"列清单"，还有**按"输出是否进入业务结论"把能力分层**——进入业务结论的那部分必须逐算子对照，不进入的那部分可以整体降级（换通用实现、关掉、或不做）。
- **为什么必须是设计期决策**：**"不做某个能力"在架构上是一件事，在交付现场是另一件事**——现场已经没有任何可替换的空间，只能把它写进"不支持清单"并承担争议。设计期裁剪的代价是主动放弃一部分功能；交付期裁剪的代价是**用合同条款去承接一个本来可以避免的缺陷**，而且客户对后者的解读通常是"能力不足"，不是"范围约定"。
- **判据**：对每个"输出不进入业务结论"的算子，能不能说清**它降级成什么**（换通用实现 / 关掉 / 不做）——**说不清就说明它其实还在关键路径上**，只是没人愿意承认；这一问也顺带验证了 ① 的筛选标准有没有被真的执行。

**⑤ 把"什么算一致"先写成口径，再开始对照**

- **关键设计**：动手对照之前必须先约定三件事——**比什么指标**（相似度排序看 Top-k 重合率还是看分差分布）、**容差是多少**、**样本从哪来**。这不是学术细节：口径不同，同一批差异会得出两个相反的结论。
- **为什么口径要写在核验之前**：差异本身是客观的，**"算不算一致"是约定的**。先跑对照、后定口径，团队会（多半是无意识地）挑一个让结果好看的指标——而**验收时的口径由合同与客户决定，不由交付方决定**。先定口径还有一个好的副作用：它会暴露"这个指标其实测不出来"这种情况，此时正确的动作是把它降为"安装与运行"粒度（见 ④），而不是临时找一个替代指标凑上。
- **判据**：**指标、容差、样本来源三件是不是在对照开始之前就写下来的**——如果它们是跑完之后才补的，这次对照的结论只能当内部参考，不能进验收项。

**具体数字（档位标注）**

- 适配成本**按算子数计**（不是按系统数）：`成本 ≈ 算子数 × 单算子核验工时`【推算：单算子核验含"跑通 + 精度对照 + 记录结论"三步；请按你自己的算子清单与工时口径代入】——**这条推论的意义是它可被提前估算**：先数算子，再定排期。**这个量级决定了它属于"可排期"的交付风险**：给定算子清单，成本与工期都是可算的；而"整体跑通"给不出任何排期依据——这正是逐算子验收在项目管理上的价值（§6.7 的"适配可估算性"一行），也是它值得在设计期就开始的唯一理由。
- 精度对照的样本量：对会进入业务结论的算子，**用业务真实数据（而非合成数据）做对照**；样本量应覆盖边界区间【经验：随算子类型浮动】。**这个量级决定了"偶发不一致"是必须消灭的一类状态**：样本量不够时，差异会表现为偶发的、无法复现的不一致——它既解释不了（因此进不了验收项），也复现不了（因此列不出改造计划），只能一直停在合同之外；而按上面的分档，停在三条出路之外的差异，验收时全部算作你的缺陷。
- **自测动作**：列一遍你的关键算子清单（按"输出是否进入业务结论"筛），逐个标注"国产替代方案是否存在"。**"不存在"的那几项，就是你交付时的风险点。** 再做一步：把这份清单与你的**合同附件**对一遍——**清单上有、合同里没有的条目，就是将来最容易产生争议的地方**。

**失败教训**

**把信创适配当成交付阶段的一次部署工作**——第一版只验证了安装成功与功能可用，结果上线后出现无法解释的数值差异，客户据此质疑全部结论。教训：**适配的验收粒度是算子级，不是"能启动"**；而**这张算子清单必须由平台团队在设计期维护**——等交付前才开始列，能改的空间已经很小了。

**为什么会写成那样（机制层）**：因为**"能启动"是唯一一个可以自动给出答案的验收判据**，而"结果一致"必须先定义"什么算一致"——要枚举算子、约定精度口径、准备对照数据，全是人工。**于是团队会默认走那条能自动跑完的路**（装上去、跑通、看进程还在），而这条路恰好绕过了客户唯一关心的那一问。第二层机制在**时间位置**：逐算子核验只能付在交付之前（那时改架构的空间最大），但它在账面上看起来像"提前付出的成本"，于是被不断推迟——**推迟的代价不是成本上升，而是可改空间归零**：到了客户现场，能做只剩"把差异写进不支持清单"这一条（§7.7 把"已交付部分的差异争议"点名为两项"部分不可逆"代价之一——"花时间也拿不回来"；而"把密钥交给别人之后再收回"虽被 §7.7 写成八条里最贵的一项，仍归在"要花时间"那一类，两者不是同一类）。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条顺序固定的路径，与 §4.1 的七步对应：

1. **先画暴露面清单 + 把机器可读的策略立起来**（§6.1）——没有它，"我们做了安全"无法验证覆盖范围；分级不动策略，是因为两者是两次产出（§6.1 的机制）。
2. **再把密钥与数据的权限分成两条线**（§6.2）——加密类机制的准入条件不是"加密开着"，而是"**能读数据的人读不到密钥**"；轮换与吊销要有独立执行者。
3. **然后为每条要求配三问（控制点 / 证据 / 演练）**（§6.3）——它是纯文档工作，但投入产出比最高；AI 特有组件（模型端点、工具出口、沙箱）要单列。
4. **最后做算子级适配与合同化差异**（§6.4）——它的成本按算子计，因此**可以先估算再排期**；不可解释的差异必须在合同里说清。

**顺序的反面**：**先买产品（DLP / 加密网关 / 隐私计算平台），后画清单**——产品会在它自己的检测点上工作，而你真正的泄露路径（上下文、缓存、日志）不在它的视野里；结果是"上了产品"与"泄露面被覆盖"两件事都没有发生（§4.1 的反面）。**第二条反面**：先做适配验证、后做合规映射——适配的差异**需要映射表来表达**（"这一条要求，我在国产环境上怎么满足、证据是什么"），顺序反了要重做一遍材料。

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 分级做完就认为安全做完 | 审计问"怎么证明"时只有分级表 | 机制缺策略与下推两步 | 分级 → 策略 → 下推（§6.1） |
| 审批记录当策略 | 同一类资源要批十次 | 人工成为瓶颈、绕行出现 | 策略编译成可下推的条件 |
| 无旁路对账 | 策略生效了，但访问从另一边走 | 治理失效且无人知 | 受控统计 vs 目标系统日志，半天一次 |
| 密钥与数据同一批管理员 | 加密生效但挡不住任何人 | 加密退化为一次编码 | 两条权限线 + 独立轮换执行者（§6.2） |
| 轮换留一半 | 旧密钥仍是可用入口 | "换了"但没换 | 旧密钥明确失效或设重叠窗口 |
| 吊销要发版 | 泄漏处理时间以天计 | 损失与时间线性相关 | 密钥上收到服务侧（秒级吊销） |
| 把测评当整理能力清单 | 逐条问"控制点在哪"答不出 | 预评估被打回 | 每条要求配三问（§6.3） |
| AI 特有组件未指认 | 通用项都有、AI 项全是 `⊥` | 测评失分 | 模型端点 / 工具出口 / 沙箱单列 |
| 只有配置截图无演练记录 | 无法证明"此刻生效" | 配置漂移无从发现 | 演练动作写进材料并留痕 |
| 信创只验"能启动" | 上线后结果与 x86 不一致 | 客户质疑全部结论 | 逐算子核验 + 精度对照（§6.4） |
| 差异不入合同 | 验收时所有差异算作你的缺陷 | 交付争议 | 三类分档 + 不支持清单进合同 |
| 关键算子清单交付前才列 | 可改空间很小 | 改造代价最大化 | 设计期维护，按"输出是否进业务结论"筛 |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——安全与合规的收益形态是"**没有发生的坏事**与**能通过审查**"，这两者都不适合用百分比表达。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 泄露面覆盖率 | 暴露面清单上有机制的位置 / 总位置 | 从**多数为空格**到**无空格**（这是本主题最直接的一个数） | 数一次十三个位置里有几格是空的 |
| 权限收敛 | 仍需人工审批的访问次数 | 从"每一次"降到"每一类 + 例外" | 统计一周内人工审批的条数与其中"同类重复"的比例 |
| 旁路可发现性 | 受控统计与目标系统日志的对账差异 | 从**无法对账**到**差异可解释** | 取一天日志对一次账（约半天） |
| 密钥可控性 | 吊销一次密钥的耗时 | 从**小时到天级**（发版）降到**秒级**（改配置） | 记录一次演练的吊销耗时 |
| 合规可举证性 | 控制项映射表里 `⊥` 的数量 | 从**多数未指认**到**无 `⊥`** | 数一次映射表里的空格 |
| 适配可估算性 | 关键算子数 × 单算子核验工时 | 从"交付时才知道"到"排期前可估算" | 数一遍关键算子（按"输出是否进业务结论"筛） |
| 代价 | 策略维护 + 抽检 + 演练 + 合规材料 | **人力为主，随资源数与标准数增长**（不随数据量增长） | 按月核算这类人力占团队比例 |

**读法**：前三项是**机制收益**（覆盖面、收敛、可发现性），第四、五项是**可达性收益**（能不能快速止损、能不能过审查），第六项是**可估算性**（把不确定的交付风险变成可排期的工作），最后一项是**代价**。**这一块与其它主题最大的不同在于**：它的收益里有相当一部分是"**没有发生的坏事**"（没泄露、没被打回、没在交付现场发现装不上）——**这类收益无法折算成金额，但它的对立面（发生了）是可以折算的**。因此一个更实用的口径是：**量"发生了的代价"，反推投入是否值得**。

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**暴露面清单与可下推的策略先立**（没有它，后面做的机制无法验证覆盖范围），**密钥与数据分两条线**（加密类机制的准入条件），**每条要求配三问**（纯文档工作但性价比最高），**算子级适配与合同化差异最后**（成本可按算子估算）。四次失败教训指向同一件事：**安全与合规的失败几乎都不是"能力不足"，而是"机制不在不可绕过的位置上、或者生效了但没有证据"**——前者让机制形同虚设，后者让机制无法被承认。

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你处境最像的案例，只做一件最小的事——按它的"判据"跑一次自测（数一次暴露面空格 / 查一次"能读数据的人能不能读密钥" / 回答一条合规要求的三问 / 列一遍关键算子清单）。哪一件**今天就能做**就先做它：**安全体系不会因为很久没出事而变好，只会因为很久没演练而变脆。**
