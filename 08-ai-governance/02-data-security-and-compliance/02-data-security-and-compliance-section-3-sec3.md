## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

安全机制的形态由**五条约束**决定，顺序不能颠倒：

1. **数据的用途**：这份数据脱敏后还要参与**关联分析**吗（跨系统按同一主体聚合）？还是只做**一次性对外提供**？**这一条直接决定脱敏能不能可逆**（§2.2 的可逆性判据）。
2. **判定的时点要求**：同一个字段要不要对**不同角色呈现不同形态**？要，则必须**动态**脱敏（静态副本做不到"同一份数据两种呈现"）。
3. **暴露面覆盖**：数据在哪几个位置**被读出来**（用户界面之外，还有模型上下文 / 缓存 / 日志 / 遥测 / 导出物）？**这一条决定机制要放几处**——只覆盖界面是 §§3.5 里最常见的失效形态。
4. **合规标准**：要过哪一套（等保 2.0 / 行业监管 / 客户安全审查 / 信创验收）？**这一条决定要准备哪些证据**，而不是决定技术方案。
5. **人力与运维承接**：谁维护策略、谁做抽检、谁在密钥轮换时值守？（**策略是有版本、会漂移的资产**；没有人跟，半年后没人能解释某条规则为什么存在。）

> **判据的用法**：先用 1 决定脱敏家族（可逆 / 不可逆）；用 2 决定静态还是动态；用 3 决定机制要覆盖的位置清单（**这一步最容易漏**）；用 4 决定证据清单；用 5 决定策略的评审周期。**跳过第 3 条最常见的后果**：机制只做在用户界面上，而数据经由模型上下文 / 日志 / 缓存流出——**此时"我们有脱敏"这句话是真的，但脱敏没有覆盖泄露面**。

**每条约束的"过关"是可核查的**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 数据的用途 | 能回答"这份脱敏副本要参与哪几个跨系统关联"，并按此选定可逆 / 不可逆 |
| 2 判定时点 | 同一份数据以不同角色访问，能演示出两种呈现 |
| 3 暴露面 | 有一张**位置清单**（界面 / 上下文 / 缓存 / 日志 / 遥测 / 导出），每个位置都标注了管它的机制 |
| 4 合规标准 | 有一张**控制项 → 我的控制点**的映射表，且没有 `⊥`（未经指认的项） |
| 5 人力承接 | 策略有 Owner、有评审周期、有最近一次修订记录 |

上表里**第 3 条最容易被"想当然"跳过**：团队记得界面上的脱敏，却忘了数据在模型上下文与日志里也有一份。**可执行的检查**：拿一条真实请求，沿着链路把"数据出现在哪"逐个位置数一遍——数不出来的位置，就是还没被覆盖的暴露面。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 静态脱敏（出库一次性打散）

**被什么约束逼出来**：数据要交给**下游系统或外部方**使用，且这份副本**不需要与原始数据保持逐行关联**（约束 1 的"不可逆"一侧）。

**结构**：在数据**出库 / 导出 / 入湖分层**时做一次转换 → 产生脱敏副本 → 副本与原始数据**物理分离**、走不同的访问控制。

**为什么这样设计有效**：因为**它把一次性的、可离线审查的转换，放在了数据生命周期的固定点上**。机制上的三条推论：① 转换是**批处理**，因此可以离线跑、可以对结果做**全量核验**（脱敏后字段是否还有残留的敏感形态）；② 副本与原件分离后，**下游拿到的物理上就是脱敏后的数据**——因此**下游无论怎么用都无法泄露**，不依赖下游守规矩；③ 它不进入在线路径，**没有延迟代价**。

**代价**：① **可逆性是一次性决定**——选了不可逆，下游后来要做关联分析就只能重脱一遍；② **副本会失真**：泛化 / 掩码会改变数据分布，**下游模型在脱敏数据上训练出的结论，不一定适用于原始分布**（这是最隐蔽的代价，因为表现是"模型效果差"而不是"报错"）；③ **副本的增加扩大了数据拷贝面**——每多一份副本就多一处要管的数据。

**失效点**：**脱敏不彻底**——只处理了显式字段，忽略了**准标识符组合**（年 + 地区 + 性别 + 入职年份可以唯一定位到人）。**判据**：对脱敏后的副本做一次**重识别演练**（尝试用非敏感字段组合还原个体），**演练失败才算数**。

**判定方法**：对脱敏副本跑一次重识别演练——只用**非敏感字段**的组合（年 + 地区 + 性别 + 入职年份这一类）尝试还原个体，**演练失败才算通过**；再检查副本与原件是否物理分离、是否走两套访问控制。两个动作都不需要采购。

**真实使用**：这一格分两层给，两层都在书内可核验。**机制层**【公开】：去标识化把标识符拆成"直接标识符 / 准标识符"两类处理（NISTIR 8053），k-匿名则由 Sweeney 于 2002 年形式化——它给的正是"用非敏感字段组合还原个体"这条重识别演练的形式；产品侧，阿里云数据安全中心 DSC / 华为云数据安全中心 / AWS Macie / Google Cloud Sensitive Data Protection 以"识别敏感字段并提供脱敏"为公开能力。这些具名实体与出处已在全书他处逐条列出（`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` 的 §3.2「真实使用」条目），本单元只引用、不重复举证。**本主题层**：§4.3 工具链表把"静态脱敏"列在"引擎内置（视图 / 掩码）+ 自研 ETL 阶段转换"与"数据安全平台"两栏，选型要点写的是**"能不能做准标识符组合的重识别评估"**（§4.3）；§7.6 选型矩阵的对应行是"已有成熟数据平台、单一引擎 → 引擎内置（列掩码 / 行级策略）"（§7.6）；§2.2 的可逆性判据说明"一旦选了可逆，风险就转移到映射表上"（§2.2）。**本节核不到的空缺要写明**：没有任何一个具名产品公开声称自己做了"准标识符组合的重识别评估"——**这一格只能靠读者自己做一次演练得出，不能用产品文档替代**。【公开】（来源：`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` 的 §3.2「真实使用」条目；本主题 §2.2、§4.3、§7.6）

#### 3.2.2 动态脱敏（访问时按身份呈现）

**被什么约束逼出来**：同一份数据要对**不同角色呈现不同形态**（约束 2）。

**结构**：查询 / 召回时，**在结果产出前按调用者身份改写字段**（视图、列掩码、查询重写）；原始数据不变。

**为什么这样设计有效**：因为**它让"权限"和"呈现"成为同一件事**——动态脱敏本质上是**权限机制的一个视图**，而不是独立的转换：判定输入是调用者身份，判定输出是"这个字段对该身份呈现什么"。由此得到两条推论：① **不需要为每个角色维护一份副本**（副本数与角色数解耦）；② **撤权即时生效**（判定在访问时发生，没有已经发出去的副本要回收）。

**代价**：① 它**进入在线路径**，因此有延迟与实现复杂度（改写要在引擎层或代理层做，改错会破坏语义）；② **它依赖身份传递的正确性**——身份错，脱敏就错（§3.2.6 的失效点与之同源）；③ **容易被绕过**：直连底层库的路径不受脱敏约束——**判据**:与"唯一出口"是同一套检查，拿"脱敏代理的统计"与"底层库的审计日志"对账，差异就是旁路。

**失效点**：**把动态脱敏当成"静态脱敏的替代"**——两者解决不同问题：动态脱敏保护的是**访问路径**，静态脱敏保护的是**数据副本**。需要对外提供数据时只有动态脱敏是不够的（副本一旦导出就脱离了判定点）。

**判定方法**：拿"脱敏代理的访问统计"与"底层库自身的审计日志"对账**同一天**的数据，差异能被逐条解释才说明没有旁路；再把同一个字段用两个不同角色的账号各查一次，看呈现是否真的不同（不是"配置里支持按角色呈现"）。两个动作都不需要采购。

**真实使用**：**本主题层**——§4.3 工具链表"动态脱敏"一行的自建侧写"查询重写 / 代理层"、商业侧写"数据库安全网关"，选型要点是一条判据而不是功能清单：**"旁路能否被发现（对账能力）"**（§4.3）；§4.4 把它展开成三条安全判据的第一条"对账差异收敛"（§4.4）；§3.3 决策表的对应行给出"脱敏代理统计与底层库日志能否对上（能）"（§3.3）。**全书他处已具名的实现**【公开】：Apache ShardingSphere 的数据脱敏模块是这一族的常用实现，且该书处已自注"具体配置项以其官方文档当前版本为准"（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-4-sec4.md`）；Apache Ranger 的 data masking 策略类型与 Oracle Data Redaction 的查询期脱敏是同一形态的另两个具名实现（`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` 的 §3.2「真实使用」条目）。**这里要写清的因果是"同一份数据对不同角色呈现不同形态"，而不是"某产品支持脱敏"**——产品条目只能证明这一族存在，证明不了你这条访问路径没有被旁路。【公开】（来源：`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-4-sec4.md`；`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md`；本主题 §3.3、§4.3、§4.4）

#### 3.2.3 差分隐私（保护统计输出里的个体）

**被什么约束逼出来**：要对外提供**统计结果**（分布、均值、计数），而个体不能被推断出来（约束 1 的"只有统计需求"这一支）。

**结构**：在聚合结果上按隐私预算 `ε` 注入噪声 → 记录每次查询消耗的预算 → **累计预算**用尽后拒绝新查询。

**为什么这样设计有效**：因为**它把"隐私"变成了一条可证明的性质**——`ε` 给出了"多一条记录会改变输出多少"的上界（§2.2 的式子），因此**保护强度是可以被外部审查的**（这与"我们做了匿名化"这种不可证明的声明不同）。**它的有效性完全依赖两条工程纪律**：① **预算必须累计**（不加累计的 DP 接口，多查几次就等价于没有保护，这是组合定理的直接推论）；② **输出必须有人在聚合层面消费**（把 DP 输出当成单条记录的查询来用，`ε` 多少都无意义）。

**代价**：① **可用性随 `ε` 下降**——噪声会改变小样本统计的可读性（这正是它保护隐私的方式）；② **查询次数成为稀缺资源**——而稀少资源会改变产品设计（"看板每次刷新都发一次查询"这种默认行为必须改掉）；③ **它不做"字段可见性"的事**——字段还得靠脱敏（不要把 DP 当成脱敏的替代品，反之亦然）。

**失效点**：**把 DP 用在"行级查询"上**（"查张三的消费金额再加噪"）——这不是隐私保护，这是给单条记录加了噪声，用户看到的是一个**错的个人数据**，而隐私并未提升（因为输出的就是那个个体的值）。**判据**：DP 机制的输出**必须是小样本之外才可信的聚合量**；出现"某个体的 DP 结果"就说明用法错了。

**判定方法**：检查这个 DP 接口的预算**是否累计**、以及输出里会不会出现"某个体的 DP 结果"——两者出现任何一个，都说明用法错了，而不是参数没调好；再确认调用方是**聚合层**（看板 / 报表）而不是某个人的明细查询。

**真实使用**：**机制层**【公开】——差分隐私的隐私预算 `ε` 由 Dwork 于 2006 年形式化（这正是本节"`ε` 可累加、组合定理"的原始出处），Apple 亦在其平台安全白皮书相关章节公开说明了本地差分隐私的使用；两者已在全书他处具名（`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` 的 §3.2「真实使用」条目）。**引用 Apple 时必须紧跟一句限定**：那是**客户端侧的本地 DP**，与本单元讨论的"聚合输出加噪 + 预算累计"**不是同一形态**——引它是为了说明"DP 已被工业采用"，不是说明"聚合侧 DP 已被工业采用"。多技术后端的隐私计算平台有 FATE / SecretFlow / PrimiHub（`11-cross-cutting/08-privacy-computing/08-privacy-computing.md`）。**本主题层**：§4.3 工具链"DP / HE"一行把商业侧指向隐私计算平台，选型要点是"**预算累计**"与"**运算集合**"（§4.3）；§7.6 矩阵的对应行写"只提供统计输出、隐私要求高 → 隐私计算平台（DP），**必须确认它支持预算累计**"（§7.6）；§7.5 决策树把"有没有内容级需求"作为引入重武器族的开关（§7.5）。【公开】（来源：`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md`、`11-cross-cutting/08-privacy-computing/08-privacy-computing.md`；本主题 §4.3、§7.5、§7.6）

#### 3.2.4 同态加密（把计算也外包出去时的那一层）

**被什么约束逼出来**：不仅数据要离开机房，**计算也要在不受你控制的环境里进行**。

**结构**：密钥留在你自己手里（或客户的 KMS）→ 密文交给外部计算方 → 计算方在密文上做约定好的运算 → 结果回传解密（或由持有密钥方解密）。

**为什么这样设计有效**：因为**它把"信任计算方"这一前提消掉了**——计算方即使被攻破、即使有意窥探，拿到的也是密文。**这条性质在"数据要交给第三方做训练 / 联合分析"这一类场景里是唯一的解法**；其余方案（脱敏后外包）会损失精度，而 HE 不损失（在功能支持范围内）。

**代价（三条，都要提前量）**：① **计算开销**——同态运算比明文运算高数个数量级【经验：随方案（部分 / 层次 / 全同态）与运算类型差异极大，请按你自己的基准实测】；② **功能受限**——支持的是**约定的运算集合**（加法 / 乘法 / 比较的某些组合），**不是任意程序**；③ **工程栈不成熟**——参数选择、噪声预算管理、结果精度都要专门的工程能力。

**失效点**：**把 HE 当成通用的"加密查询"**——它的位置是"**把特定运算外包出去**"，不是替换日常查询路径。日常查询该用动态脱敏 + 权限；只有"计算必须在对方环境进行"时才上 HE。**判据**：能说清"哪一个具体运算必须在外方完成"吗？说不清，就说明这个场景还不需要 HE。

**判定方法**：先回答"**哪一个具体运算**必须在外方环境完成"——说不清就说明这个场景还不需要 HE，日常查询应退回动态脱敏 + 权限；再说清该运算落在"约定的运算集合"里的哪一档（加法 / 乘法 / 比较的哪些组合），以及解密密钥由谁持有。

**真实使用**：**这一格写出来的是一个具名空缺，而空缺比硬填一个名字更诚实。** 本主题内可引的只有三处，且都只能证明"这一族存在"：① §4.3 工具链把 DP 与 HE 合在同一行、商业侧指向"隐私计算平台"，选型要点里的"**运算集合**是否覆盖你的需求"就是 HE 的功能边界（§3.2.4 代价第 ② 条、§4.3）；② §7.6 选型矩阵里"算力需求大、数据只是过路"一行指向的是**机密计算（TEE）而不是 HE**——两者常被混为一谈，这一行正好把它们分开：HE 保护的是"计算方看不到明文"，TEE 保护的是"宿主看不到内存"，两者能做的运算集合与性能量级完全不同（§7.6 与 §3.2.4）；③ 全书他处已具名的隐私计算平台（蚂蚁摩斯见 `11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md`，FATE / SecretFlow / PrimiHub 见 `11-cross-cutting/08-privacy-computing/08-privacy-computing.md`）把 HE 列为**多技术后端之一**——可以这么写，但**不能写成"它们用 HE 做了生产查询"**。**本节核不到 HE 的具名公开生产实现**：§5.2 已把"同态加密的通用化"判为 L3（只有研究进展与专用方案）。【经验：本节不具名，判定入口是上面那条"哪个运算必须在外方完成"】（来源：本主题 §3.2.4 代价、§4.3、§5.2、§7.6；`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md`、`11-cross-cutting/08-privacy-computing/08-privacy-computing.md`）

#### 3.2.5 权限模型：RBAC / ABAC / 字段级 / 行级（四者叠加，不能互替）

**被什么约束逼出来**：访问者的身份与资源的关系**不是一维的**——角色的粗粒度控制不够（同一角色在不同部门、不同项目下该看的东西不同），而纯属性策略在大组织里又难以治理。

**结构**：四层叠加，**每层解决一类问题，判定时依次收紧**：

```
① RBAC        ：角色 → 功能权限（能不能用"取数"这个功能）
② ABAC        ：属性策略（部门 / 项目 / 数据域 / 密级 / 时间窗的组合）
③ 行级权限     ：同一张表里哪些行（Predicate(s, row, e)）
④ 字段级权限   ：同一行里哪些列（visible(s, r)）
```

**为什么这样设计有效**：因为**四层的"治理成本"与"表达能力"不同，按层组合才能同时可治理、可表达**：RBAC 的治理成本最低（角色数远少于人数）、表达能力最弱；ABAC 反之；行列级是**给资源加约束**，不改变主体的组织方式。**依次收紧的结构还带来一条运维性质**：误授权的排查可以**从上往下定位**（是角色错、策略错、还是行列过滤错），而不是在一张大策略表里猜。

**代价**：① 四层都要有 Owner 与评审（策略会漂移）；② **判定要前置到召回条件里**，否则退化成后置过滤（§3.2.6）；③ **身份的传递链要完整**——服务代调用时必须带 `on_behalf_of`，否则判定用的是服务身份而非人的身份（§4.2（3））。

**失效点**：**只做 RBAC 而声称"细粒度权限"**——RBAC 到角色粒度，而"同一角色的人在不同部门该看不同数据"这类需求它表达不了；此时用户会用一个"超级角色"绕过，**细粒度在形式上存在，在实际上一律放行**。**判据**：抽查一个角色，问"这个角色下的两个人，看到的行 / 列是否完全相同"——如果按业务他们不该相同，说明还缺 ABAC / 行列级。

**判定方法**：抽查一个角色，问"这个角色下的两个人，看到的行 / 列是否完全相同"——按业务他们不该相同却相同，说明缺 ABAC 或行列级；再追一次审计，看能否回答"这条数据是谁（**具体到人**）触发的访问"，答不出"具体到人"说明身份链缺 `on_behalf_of`。两个动作都不需要采购。

**真实使用**：这一格四层各有具名实现，是本主题最容易写实的一格。**策略层**【公开】：Apache Ranger 提供 row filter 与列掩码两类策略类型，Open Policy Agent 提供通用策略引擎与 Rego 语言，OASIS XACML 3.0 是访问控制策略标准，Cerbos / Immuta 被同章 §7.2 列为策略方向选项（均在 `11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` 的 §3.2.3、§3.2.6「真实使用」条目里逐条具名）。**引擎层**：Trino 的 row-level security 与 Ranger / Open Policy Agent 集成、按用户角色过滤行（`04-data-assetization/09-unified-query-gateway/09-unified-query-gateway-section-8-sec8.md`）；Databricks Assistant / Genie 的 SQL Sandboxing、Snowflake Cortex Analyst 的「Always On RBAC」、Starburst Enterprise 的表 / 列 / 行三级 Fine-Grained Access Control（同文件）是"判定跟着调用者走"的三个具名工业形态；阿里 DataWorks 数据 API 网关把行级权限做成网关的默认行为（`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-6-sec6.md` 的 §6.2 案例）。**本主题层**：§4.3 工具链"权限"一行的选型要点是"是否支持把判定**下推**到召回条件"（§4.3）；§4.2（3）在四层之上加了一条硬要求——服务代调用必须带 `on_behalf_of`（§4.2（3））；§3.3 决策表写"只做 RBAC 会用超级角色绕过"（§3.3）。**要写明的空缺**：**"同角色两人应该看到不同行列"这条需求本身，没有具名产品能替你判断**——它只能靠抽查一个角色发现（本节失效点的判据）。【公开】（来源：`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md`、`04-data-assetization/09-unified-query-gateway/09-unified-query-gateway-section-8-sec8.md`、`04-data-assetization/07-data-api-gateway/07-data-api-gateway-section-6-sec6.md`；本主题 §3.3、§4.2（3）、§4.3）

#### 3.2.6 召回期权限裁剪（先裁剪，再召回）

**被什么约束逼出来**：检索 / 问答 / RAG 把权限问题**下沉到了行与片段级**（约束 3 在 AI 场景的最强形态）。

**结构**：请求进入时先解析**可见集**（`visible(s, r)` 与 `Predicate(s, row, e)`）→ 把它**下推为检索的过滤条件** → 在可见集合内召回 → 生成时只使用召回结果。

**为什么这样设计有效**：因为**"先召回再过滤"与"先裁剪再召回"的区别不在结果，而在"内容有没有被读出来"**——后置过滤时，无权内容已经进了进程内存、可能进了缓存、可能进了日志、**可能进了模型上下文**。**在"数据出域"这类判定上，"读出来再删掉"与"不读出来"不是同一件事。** 另有一条可观测的证据：**后置过滤会让"召回 50 条、返回 3 条"这个差异暴露"存在 47 条你看不到的东西"**——召回条数本身就是信息。

**代价**：① 可见集要**接企业的权限系统**（不能自建一份，否则出现第二个权限源，同 [Ch10 §04 §6.1](../../10-industry-agent/04-office-automation-agent/04-office-automation-agent-section-6-sec6.md) 的结论）；② **跨仓库 / 跨库引用的边界要定义**——代码与文档的可见性带有"传染性"（引用了某个定义就可能暴露它）；③ 下推的过滤条件会**影响召回质量**（可见集很小时，召回不足会导致答案质量下降——这是"正确但没用"的代价，可以接受）。

**失效点**：**只过滤"最终返回给用户的"内容**——生成阶段仍在完整上下文上工作。**判据（十分钟可做）**：用一个无权账号请求一份它无权看的文档内容，然后**去查这次请求的上下文构建日志 / 缓存**——**如果无权内容出现在那里，就是后置过滤**（用户看不到 ≠ 没读出来）。

**判定方法**：用一个无权账号请求一份它无权看的文档，再查这次请求的**上下文构建日志 / 缓存**——无权内容出现在那里就是后置过滤；另打开检索接口的签名，看它有没有一个"可见集 / 过滤条件"参数（没有这个参数，实现者几乎必然写成取回后过滤）。两个动作都不需要采购。

**真实使用**：这一格**必须把"同类机制的异地实现"与"本场景的实现"分开写**。**本场景（RAG / 向量检索的召回前裁剪）本节核不到具名公开实现**——这不是材料没找：§5.2 已把这条的判据②（第三方非厂商生产案例）写作"核不到"，理由是**企业内部权限模型与召回实现极少公开**（§5.2）。**可点名的同类机制都在查询引擎侧**【公开】：Trino 的 row-level security 与 Ranger / Open Policy Agent 集成，把过滤条件下推到扫描；Snowflake Cortex Analyst 的「Always On RBAC」让所有 Agent 查询自动套用调用者的 RBAC 权限，Starburst / Databricks 同类（均在 `04-data-assetization/09-unified-query-gateway/09-unified-query-gateway-section-8-sec8.md`）。**本主题层**：§4.5 模板 2 的伪代码把"前置"写成可见的设计（`index.search(query, filter=visible)`，并注明"把 filter 参数去掉，上述任何一条断言都会破"，§4.5 模板 2）；§4.1 Step 2 把这一条列成不能往后放的一步（§4.1）；§4.2（2）给出"跨库可见性传染"与"**可见集为空必须显式返回空**"两条实现要点（§4.2（2））；§5.4 的接口表把交接物写成 `visible_fields` / `row_pred` / `visible_docs`（§5.4）。**引用时必须写明这层区分，不能写成"某 RAG 产品这样做"**。【公开】（来源：`04-data-assetization/09-unified-query-gateway/09-unified-query-gateway-section-8-sec8.md`；本主题 §4.1、§4.2（2）、§4.5 模板 2、§5.2、§5.4）

#### 3.2.7 DLP 三件套（识别 → 判定 → 动作，且三道都留痕）

**被什么约束逼出来**：AI 的输出是**生成**的，因此"入向管控"不足——模型会**复述**上下文（约束 3 的"暴露面包含生成链路"）。

**结构**：**① 识别**（敏感实体：身份证 / 银行卡 / 手机号 / 密钥 / 内部代号；确定性匹配与上下文判定分工见 §2.3）→ **② 判定**（策略：该实体的密级、所在场景、调用者身份）→ **③ 动作**（拦 / 脱敏后放行 / 要求二次确认 / 放行并留痕）。**三道都留痕**。

**为什么这样设计有效**：因为**这三件事分别由不同的输入决定，混在一起就无法调**：识别由"内容"决定（可自动、有召回与误报两个指标）、判定由"策略"决定（可配置、可解释）、动作由"业务可接受度"决定（拦得越严误拦越多，§2.2 的两个式子）。**分开之后，优化目标才清晰**：识别不够就补规则，策略不对就改策略，**而"业务嫌太吵"这个反馈落在动作层，不需要动识别**。

**代价**：① **误拦的业务代价**（用户拿不到本该拿到的结果）与漏出的安全代价方向相反，因此阈值是一个**业务取舍点**而不是安全参数；② **二次确认只在"高风险 + 高置信"时启用**——作为默认动作会让每次输出都变成人工介入；③ **性能**（在线检测加一跳，且要处理流式输出的**分段**问题：一个身份证号可能被分在两个流式分片里，**滑窗拼接是工程难点**）。

**失效点**：**只审输出不审输入**（或反之）——正确的形态是**双端**：入向阻止敏感内容进入上下文，出向阻止敏感内容离开系统。**另一条失效点更隐蔽**：**检测只覆盖明文**，而系统里存在**缓存与日志**这两条"输出之外"的通道——**判据**：把"缓存写入"与"日志写入"也列为要检测的位置（它们和输出一样会把内容带出去）。

**判定方法**：把一个身份证号**跨两个流式分片**发送，看它是否被检出（这条用例同时暴露"有没有覆盖流式"与"滑窗存不存在"）；再数一次检测点覆盖了 §4.2（1）的位置清单里的**几格**——**缓存写入与日志写入算不算在内**。两个动作都不需要采购。

**真实使用**：**具名实现集中在"识别 + 管控"这一侧，第二、三件（策略判定与动作分级）本节核不到具名产品**。识别与管控侧【公开】：阿里云 DAS（数据库自治服务）提供数据库审计与安全管控；阿里云数据安全中心 DSC / 华为云数据安全中心 / AWS Macie / Google Cloud Sensitive Data Protection 以"识别敏感数据"为公开能力（均在 `11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` 的 §3.2「真实使用」条目）；卡号实体侧的工业做法是令牌化（PCI SSC 的令牌化指引，同处）。输出侧 AI 场景只有方向指认——Microsoft Purview AI Hub、Nightfall AI、Harmonic Security、阿里云 AI 数据安全（`11-cross-cutting/02-data-security/02-data-security-section-5-ai.md` 的 §5.2.1 条目，**该处自注"只作为方向指认，其能力与版本以各家官方文档为准"，引用时照抄这个限定语**）。**本主题层**：§2.3 ⑤ 把三道闸写成"实体识别 → 策略判定 → 动作（拦 / 脱敏 / 二次确认 / 放行留痕），三道都要留痕"（§2.3）；§4.2（4）给出流式分片三种处理方式与代价表（§4.2（4））；§4.5 模板 1 的"输出"与"trace / 遥测"两行给出挂点与生效证明动作（§4.5 模板 1）；§4.3 工具链"DLP"一行的选型要点是"能否覆盖缓存与日志、流式滑窗"（§4.3）。**必须写明的空缺**：漏出率与误拦率——判断 DLP 有没有用的两个唯一指标——**几乎全部来自建设方自述，本节核不到可复核口径**（§5.2 已就这一条写明）。【公开】（来源：`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md`、`11-cross-cutting/02-data-security/02-data-security-section-5-ai.md`；本主题 §2.3、§4.2（1）、§4.2（4）、§4.3、§4.5 模板 1）

#### 3.2.8 等保对照与国产化适配（把外部标准映射到控制点）

**被什么约束逼出来**：要过测评 / 验收 / 客户审查（约束 4）。

**结构（等保）· 第一件是流程，不是映射表**：很多团队上来就做控制点映射，而**等保的第一步是"定级"**——定几级决定后面**整套控制项的范围与测评频次**。顺序写下来是五步：

```text
① 定级  → ② 备案  → ③ 建设整改 → ④ 等级测评 → ⑤ 监督检查
   ↑ 这一步定错，后面四步全部要重做（控制项范围、测评机构、频次、材料都跟着变）

定级看两个维度（业务信息受破坏时的"客体侵害程度" + "系统服务受破坏时的客体侵害程度"），
取二者中较高的一档 —— **判据**：能不能说清"这套 AI 系统被攻破时，谁的利益受多大损害"；
说不出，就没有定级依据（而为通过测评去"往低里定"，在监督检查阶段是明确的问题）。
判据（可自检）：定级文档有没有？备案回执有没有？—— 这两件在"建设整改"之前就应当存在。
```

**结构（等保）· 第二件是"技术类 + 管理类"都要指认，AI 系统的缺口通常在管理类**：等保 2.0（GB/T 22239-2019）的控制项分**十类**，五类技术、五类管理：

| 类别 | 十类控制项 | AI 系统上最常缺的那一项 |
| --- | --- | --- |
| **技术** | 安全物理环境 / 安全通信网络 / 安全区域边界 / 安全计算环境 / 安全管理中心 | 通常不缺（企业已有 IDC 与网络安全基线） |
| **管理** | 安全管理制度 / 安全管理机构 / 安全管理人员 / 安全建设管理 / **安全运维管理** | **管理类整体是 AI 系统的薄弱面**——尤其"安全运维管理"（变更、备份、日志、应急预案的**制度性**要求） |

**为什么 AI 系统的缺口在管理类**：技术类控制项对应的是**企业既有的网络与主机安全基线**（通常已做过一轮等保），而 AI 系统新引入的东西恰好落在管理类：**模型与提示的变更管理**（谁批准、怎么回滚）、**AI 资产的分级与权限台账**（[§01](../../08-ai-governance/01-ai-data-governance/01-ai-data-governance.md) 的产出）、**供应商（模型与工具）的安全管理**（资质、数据边界、退出机制）、**AI 相关应急预案**（模型端点不可用、注入攻击、批量错判）。**这些在"一个中心、三重防护"里找不到落点——它们不是设备，是制度。**

**结构（等保）· 第三件是把「一个中心、三重防护」逐条展开**——为每一条**指认控制点**（组件 / 配置 / 代码位置）、**执行结果存放处**（日志 / 报表）、**生效证明动作**（演练）：

| 等保结构 | 落到 AI 系统上的控制点（示例） |
| --- | --- |
| 安全管理中心 | 统一的策略下发与审计汇聚：权限策略、出网策略、留痕表的**单一权威源**（不是每个组件各配一份） |
| 安全通信网络 | 传输加密、**模型端点的出网白名单**、跨域调用的链路加密（[Ch6 §03](../../06-multi-model/03-model-gateway/03-model-gateway.md) 的出网判定是它的执行点） |
| 安全区域边界 | 网关侧的人审闸门与工具出口（[Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md)），**不可绕过的唯一出口** |
| 安全计算环境 | 沙箱隔离、凭证按实例发放、镜像与依赖的可追溯（[Ch5 §02 §3.2.8](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md)） |

**结构（密评）· 与等保并行的另一条赛道，别漏**：**商用密码应用安全性评估（密评）**是独立于等保的一条合规要求，依据 GB/T 39786 一类的密码应用标准，关注的是**"系统里用到的密码该不该用、用得对不对"**（合规性 / 正确性 / 有效性三个层面）：用了哪些密码算法与协议、密钥怎么产生与保管、密评结论如何进验收。**它最容易被漏的原因是"以为加密了就算合规"**——而密评问的是**用的算法与协议是否在允许范围内、密钥管理是否符合要求**，两者是不同的判断。**判据**：能不能列出一张"本系统用到的密码清单"（算法 + 用途 + 密钥来源 + 是否符合国密要求）——列不出，说明密评的准备还没开始。

**结构（国产化）**：把依赖按**五类**盘点——芯片 / 指令集（含**关键算子**）、操作系统、数据库与中间件、加密算法与国密合规、模型与权重——**逐类给出"已适配 / 适配中 / 不支持"三态清单**，并**点名候选产品**（不点名就没有清单可填：例如向量库、消息队列、调度器三类各有哪些可选，是本清单里最常空白的三格）。

**为什么这样设计有效**：因为**它的产出物是"可被外部核验的对照关系"，而不是"一个更强的安全能力"**。这一条的机制值得说清：**测评 / 审查的判定标准是"可举证性"，因此能显著提高通过率的动作是"把映射关系写全"**，而不是再上一套新机制。**把结构列成表、逐条指认控制点，是一个纯文档工作，但它是这一块投入产出比最高的动作**——§2.2 的映射覆盖判据 `m(C) 无 ⊥` 就是在说这件事。

**代价**：① **适配是按算子计的**——整体跑通只说明"能启动"，客户关心的是"结果与 x86 一致吗"，那是逐算子的精度问题（同 [Ch6 §03 §6.4](../../06-multi-model/03-model-gateway/03-model-gateway-section-6-sec6.md) 的结论）；② **"适配中"与"不支持"必须写进合同**——不写清单，验收时所有差异都会算作你的缺陷；③ 国密算法替换会带来**兼容与性能**的二次改造（证书链、库依赖、加解密开销）。

**失效点**：**把"我们用了国产数据库"当成"完成信创适配"**——适配是**从芯片到权重的一条链**，任何一环仍是外部依赖，整条链的验收就不成立。**判据**：列出整条链的组分，逐个标注"国产 / 外部"，**并说明外部组分在断供时的替代路径**。

**判定方法**：对每条等保要求问三问——**控制点在哪个文件 / 配置、执行结果存在哪里、怎么证明它此刻生效**；三问答全（映射覆盖判据里 `m(c) ≠ ⊥`）才算指认完成，缺任何一问都是测评时的失分项。再抽查一项加密，看能否说清它的算法与密钥来源（密评要的那张"密码清单"）。

#### 3.2.9 黑盒化资产封装（保护的是"物"，不是"内容"）

**被什么约束逼出来**：约束 3（暴露面）在 AI 资产上的一次**特殊形态**——前八个模式保护的都是**内容里的个体**（脱敏打散标识符、DP 保护统计输出、HE 保护计算过程），而这一格要保护的是**资产本体**：模型权重、系统提示（Prompt）、微调数据、评测集。它们的共同点是**本身就是可被拖走的物**——一份被拿走的权重不会因为"里面没有个人信息"而降低损失（[Ch11 §02 §3](../../11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md) 已把这条写成 AI 时代新增的约束：「模型权重与提示词成为与数据同等重要的资产，它们同样需要在 TEE 内被保护」）。约束 3 的位置清单里因此要多几个位置：**镜像层、配置文件、导出接口、缓存**——权重与 Prompt 也会从这些地方被读出去。

**结构**：三种姿态，由两个问题分界——**物能不能离开你的控制域？若能离开，宿主是不是可信的？**

| 姿态 | 做法 | 适用前提 | 主要代价 |
| --- | --- | --- | --- |
| **① 服务化（只给能力）** | 对方只能调用推理接口，权重与 Prompt 不出域 | 有网络可达、延迟可接受 | "交付"变成长期运维：可用性、配额、审计都成了你的责任 |
| **② 交付物加密 + 许可边界** | 必须交付时（私有化部署），交付的是**加密物 + 许可**（有效期 / 机器绑定 / 调用配额） | 宿主可信、但物会离开控制域 | 许可服务是单点；离线环境要预置许可；它一坏客户生产就停 |
| **③ 受保护执行（TEE / enclave）** | 权重在 enclave 内解密并使用，宿主只能看到输入与输出 | 宿主**不可信**、且必须交出可执行物 | enclave 内存有限；批处理在同一 enclave 内跨请求共享内存；远程证明链的取证复杂 |

**取用次序是 ① → ② → ③**：能服务化就不要交付；必须交付就先加密加许可；只有"宿主不可信且必须交出可执行物"时才上 TEE。**反过来从 ③ 起步**，会把一个能用架构解决的问题变成一个硬件与证明链的问题（与 §3.1 约束 3 的"机制要放几处"是同一类判断：先问暴露面在哪，再选机制）。

**为什么这样设计有效**：因为**它把"保护内容"换成了"保护物"**——前八个模式的失效点几乎都是"同一份数据的第二个副本"（§3.5 的重复暴露），而本格的处理方式是**让副本不存在**（①）、**让副本不可用**（②）、**让副本即使被拿到也读不出**（③）。三者的共同点是**不再依赖使用方的自觉**——这与本主题的整体逻辑一致：**架构事实 > 制度要求**（§3.2.4 的"不引具体文档作据，请以官方文档为准"与 §3.2.8 的"适配是一条链"是同一套推理）。**这条替换同时改变了判据**：不再是"敏感字段有没有被打散"，而是"**它离开控制域之后还能不能被使用**"。

**代价**：① **服务化把交付问题变成了运维问题**——客户不再买一个物，而是买一个长期可用的能力，于是 SLA、配额、按租户计量、断网降级都进了你的责任面（[Ch5 §02 §4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-4-sec4.md) 的私有化交付边界五项与离线交付包四个必须项，就是为②与①之间的这一档准备的）；② **许可是绕不过去的单点**——《离线环境要预置许可》意味着许可过期时客户的生产会停，"设计许可"本质上是在设计一个**故障模式**，必须把它写进交付文档而不是藏在代码里；③ **TEE 的代价是双份的**：性能面（enclave 内存有限、批处理必须在同一 enclave 内跨请求共享内存，**隔离边界要按"同一批次里能不能混入他人数据"重新确认**）与工程面（远程证明链让"怎么证明它此刻在受保护执行"成为一个需要留痕的独立问题）。

**失效点**：① **"黑盒化"只做了交付形态，没做调用边界**——把权重加密交付了，却同时开放着"导出当前模型"或"下载适配器"的接口，等于给物留了一扇后门；② **Prompt 没被当成资产**——权重加密了，而系统提示明文写在客户可读的配置文件里；**这是本格最常被漏的一项**，因为团队的心理模型里"Prompt 是文本"而不是"是物"；③ **许可校验只做在启动时**——运行期让校验服务不可达或把时钟回拨就绕过去了，正确的形态是**校验与使用绑定**（推理上限用许可额度扣减，而不是启动时打一次卡）。**判据**：把"物"逐个列出来（权重 / Prompt / 微调数据 / 评测集 / 词表），对每一件问一句"**它离开控制域之后还能不能被使用**"——答"能"的那些，就是还没封装的。

**判定方法**：做一次「**拖走演练**」——把自己当成客户方的运维，尽你所能把物拿出来，三个问题：**能不能从镜像里剥出权重？能不能从配置或缓存里读到系统提示？能不能导出微调数据？** 三个答案就是这一格的成熟度。再补一个动作：把 §4.5 模板 3 的三问表（控制点 / 执行结果存放处 / 生效证明）套到本格上——**"生效证明"那一列最难填**，因为它要证明的不是"我加密了"，而是"取走也用不了"。

**真实使用**：本格**没有以"资产本体封装"为公开主张的具名产品**——各家把它写在私有化交付方案里，属**建设方自述**，本节不点名（按本书 §6 的引用纪律处理）。可引的锚点在书内分三处：【公开】TEE 族与"权重与提示词也需在 TEE 内被保护"这条 AI 时代新增约束（`11-cross-cutting/02-data-security/02-data-security-section-3-sec3.md` §3）；**凭证托管与出网白名单**的形态——密钥不落在应用进程里、唯一出口是网关（[Ch6 §03 §4](../../06-multi-model/03-model-gateway/03-model-gateway-section-4-sec4.md)，含 `log_scrub` 与默认 deny 的配置写法），它是本格"不让物落到使用方手上"的最小可落形态；**私有化交付物的边界清单**（[Ch5 §02 §4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-4-sec4.md) 的"部署边界五项"与"离线交付包四个必须项"——注意这是两张表）。**判定入口**是上面的拖走演练，不是任何厂商的安全白皮书。【经验：以各家私有化交付方案的官方文档当前版本为准，本节不给文档名与年份】

### 3.3 模式选择决策表

| 约束组合 | 推荐形态 | 必须同时上的部件 | 不选它的原因（反面） | 关键判据（可核查） |
| --- | --- | --- | --- | --- |
| 副本对外提供、不需关联 | 3.2.1 静态脱敏（不可逆泛化） | 副本与原件分离、重识别演练 | 上可逆方案会把风险转移到盐表 | 能否用非敏感字段组合还原个体（不能） |
| 副本需跨系统关联 | 3.2.1 的确定性假名（加盐哈希 / FPE） | **盐表 / 映射表的独立保护** | 不可逆泛化会毁掉关联能力 | 盐表与数据的访问控制是否两套（是） |
| 同一字段需按角色呈现不同形态 | 3.2.2 动态脱敏 | 身份传递、唯一出口、旁路对账 | 静态副本做不到"一份数据两种呈现" | 脱敏代理统计与底层库日志能否对上（能） |
| 只提供统计输出 | 3.2.3 差分隐私 | **预算累计**、聚合层消费 | 用它做行级查询等于给个人数据加噪 | 输出是否有"某个体的 DP 结果"（不应有） |
| 计算也必须在外方进行 | 3.2.4 同态加密 | 密钥自持、约定的运算集合、性能实测 | 拿它替换日常查询路径，开销不可接受 | 能否说清"哪个运算必须在外方完成"（能） |
| 大组织、角色粒度不够 | 3.2.5 四层叠加 | RBAC → ABAC → 行级 → 字段级、身份链含 `on_behalf_of` | 只做 RBAC 会用超级角色绕过 | 同角色两人的可见行列是否按业务应当不同 |
| 检索 / 问答 / RAG | 3.2.6 召回期裁剪 | 可见集下推、接权限系统、跨库边界定义 | 后置过滤 = 已读出来 | 无权内容是否出现在上下文 / 缓存日志里（不应有） |
| 生成式输出、复述风险 | 3.2.7 DLP 三件套（双端） | 确定性 + 上下文识别、策略、动作、**含缓存与日志**、流式滑窗 | 只审一端会留下另一条通道 | 缓存与日志是否也在检测位置清单里（是） |
| 要过测评 / 验收 | 3.2.8 等保对照 + 国产化清单 | 控制点映射表（无 `⊥`）、五类依赖三态清单 | 再上一套新机制不如把映射写全 | 每条要求能否指到具体控制点与证据 |
| **物会离开控制域**（权重 / Prompt / 微调数据） | **3.2.9 黑盒化封装**（① 服务化 → ② 加密 + 许可 → ③ TEE） | 物的逐个清单、许可的故障模式、调用边界（关掉导出接口） | 只做交付形态不做调用边界 = 给物留一扇后门 | 每个物「**离开控制域之后还能不能被使用**」（不能） |
| 高危实体多、误拦敏感 | 3.2.7 的动作层分级 | 拦 / 脱敏 / 二次确认 / 放行留痕四级 | 全拦会让人绕开、全放等于没做 | 误拦率与漏出率是否都有数 |

### 3.4 组合模式：真实系统不会只用一种

1. **数据侧底座**：3.2.1（静态脱敏，对外副本）+ 3.2.5（四层权限，对内访问）——**一个管"出去的数据"，一个管"在里面的访问"**，两者不重叠、缺一不可。
2. **在线路径**：3.2.2（动态脱敏）+ 3.2.6（召回期裁剪）——**它们共享同一个判定输入（身份与可见集）**，因此必须共用一套策略源；分成两套策略，就会出现"查询接口脱敏了、检索接口没脱"的缺口。
3. **输出路径**：3.2.7（DLP 双端）——入向与出向都要，且**覆盖缓存与日志**。
4. **合规路径**：3.2.8（等保对照 + 国产化清单）+ 全链路的**证据采集**（拒绝日志 / 演练记录 / 连接审计）——**机制本身不产出证据，证据要在机制的执行点上采集**。
5. **重武器**：3.2.3（DP）/ 3.2.4（HE）——**按需叠加，不进默认路径**。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 只做界面脱敏 | 敏感内容出现在模型上下文 / 日志 / 缓存里 |
| 动态与静态用两套策略 | 查询接口脱敏了、检索接口没脱，或反之 |
| 权限只到角色 | 同角色跨部门的人看到不该看的行 |
| 召回后才过滤 | 召回条数暴露"存在你看不到的东西"；无权内容进上下文 |
| DLP 只做输出 | 敏感内容经由入向进入上下文，再被复述出来 |
| DLP 不覆盖缓存与日志 | 输出被拦住了，但缓存与日志里有明文 |
| DP 不累计预算 | 查询次数多了等价于无保护 |
| 等保映射留 `⊥` | 测评时"这条你怎么证明"答不出，直接失分 |
| 国产化只报"能启动" | 上线后结果与 x86 不一致，问题在算子级 |
| 盐表与数据同一套权限 | 脱敏退化为一次编码 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **脱敏只做在界面上** | 上下文 / 日志 / 缓存里有明文 | 机制没覆盖泄露面 | 把"用户看得到的地方"当成了全部 |
| **先召回再过滤** | 无权内容进内存、条数差异暴露存在性 | 读出来再删 ≠ 不读 | 后置过滤实现更简单 |
| **只做 RBAC 却声称细粒度** | 超级角色出现，越权无人察觉 | 细粒度形式存在、实际全放 | 角色模型好理解、成本低 |
| **静态脱敏忽略准标识符组合** | 副本能被重识别 | 脱敏无效 | 只看了显式敏感字段 |
| **DP 用于行级查询** | 输出是"某个人的值 + 噪声" | 数据错了、隐私没提升 | 把 DP 当成"加密" |
| **HE 当通用加密查询** | 性能不可接受、功能受限 | 用重武器解轻问题 | 名字听起来最安全 |
| **DLP 只审输出** | 敏感内容经由入向进入上下文 | 缺一半 | 泄露被想成"往外发" |
| **二次确认当默认动作** | 每次都弹确认，用户点"同意"成习惯 | 闸门退化成橡皮图章 | 把最严当成最安全 |
| **等保映射留白** | 测评时答不出控制点 | 失分 | 映射被当成文档工作、无人认领 |
| **国产化只验"能启动"** | 结果与 x86 不一致 | 验收不过 | 整体跑通比逐算子核验便宜 |
| **密钥 / 盐表与数据同权限** | 能读数据的人能读盐表 | 脱敏失效 | 把它们当成普通配置 |
| **策略无 Owner 无复核** | 半年后无人能解释某条规则 | 策略漂移、误拦积累 | 策略被当成一次性配置 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 无脱敏 → 静态脱敏 | 出现"数据要对外提供"的需求 | 3.2.1 | 副本重跑 + 重识别演练 |
| 静态副本 → 需要按角色区分 | 同一个字段对不同角色要不同形态 | 3.2.2 动态脱敏 | 接身份传递、唯一出口、旁路对账 |
| 角色权限 → 行 / 列级 | 同角色跨部门看到不该看的 | 3.2.5 四层叠加 | 策略评审机制 + 判定前置到召回 |
| 后置过滤 → 召回期裁剪 | 无权内容出现在上下文 / 缓存 | 3.2.6 | 可见集下推改造（引擎 / 索引侧） |
| 无 DLP → 输出端 DLP | 出现一次"输出里带了敏感内容" | 3.2.7 | 识别规则 + 策略 + 动作分级 + **流式滑窗** |
| 输出端 DLP → 双端 | 敏感内容经入向进入上下文再被复述 | 3.2.7 的入向分支 | 入向检测 + 上下文构建处的挂点 |
| 无合规材料 → 有 | 收到测评 / 审查通知 | 3.2.8 | 控制点映射表 + 证据采集点（**纯文档工作，投入产出比最高**） |
| 外购组分 → 信创可控 | 出现断供风险或验收要求 | 3.2.8 的五类盘点 | 逐算子核验与精度对照（**成本按算子数计**） |

**一条通用判据**：**跃迁的触发点不是"监管变严"，而是"某个位置第一次被你发现没被覆盖"**——第一次发现日志里有明文就该补日志侧；第一次发现召回条数暴露存在性就该把判定前置；第一次发现测评选项答不出就该补映射表。**按"等监管要求来了再说"驱动，几乎一定会来不及**（因为补证据链的时间比补机制长）。

### 3.7 自检清单

- [ ] 有一张**暴露面位置清单**吗（界面 / 上下文 / 缓存 / 日志 / 遥测 / 导出物）？每个位置各有什么机制管着？
- [ ] 脱敏副本是否与原始数据**物理分离**、走不同访问控制？
- [ ] 脱敏副本做过**重识别演练**吗（用非敏感字段组合尝试还原个体）？
- [ ] 用了可逆脱敏时，**盐表 / 映射表的访问控制是否与数据分离**？它有轮换路径吗？
- [ ] 同一个字段对不同角色呈现不同形态，能否**演示出来**（不是"理论支持"）？
- [ ] 动态脱敏有**旁路对账**吗（脱敏代理统计 vs 底层库审计日志）？
- [ ] 权限是**四层叠加**还是只有 RBAC？同角色两人的可见行列按业务应当不同吗？
- [ ] 服务代调用时是否带 `on_behalf_of`（判定用的是人的身份而不是服务身份）？
- [ ] 检索 / 问答是**先裁剪再召回**吗？无权文档的 id 会不会出现在召回的中间结果里？
- [ ] DLP 的**位置清单**包含缓存写入与日志写入吗？入向与出向都做吗？
- [ ] DLP 的**误拦率与漏出率**是否都有数？二次确认是默认动作还是分级动作？
- [ ] 流式输出的敏感实体**跨分片**情况处理了吗（滑窗拼接）？
- [ ] 用了 DP 的话，**预算是否累计**？输出里会不会出现"某个体的 DP 结果"？
- [ ] 把「物」逐个列出来了吗（模型权重 / 系统提示 / 微调数据 / 评测集 / 词表）？每一件问一句「**离开控制域之后还能不能被使用**」？
- [ ] **系统提示是不是明文躺在客户可读的配置里**？「导出当前模型 / 下载适配器」这类接口关掉了吗？许可是「启动时打一次卡」还是「与使用绑定」？
- [ ] 等保映射表里还有 `⊥`（未经指认的控制点）吗？每条要求的**生效证明动作**是什么？
- [ ] 国产化清单是否按**五类**（芯片 / OS / 数据库中间件 / 加密 / 模型权重）给出了三态，并说明外部组分的替代路径？
- [ ] **定级与备案**都完成了吗？（定级在"建设整改"之前；定错级别，整套控制项与测评频次都要重做）
- [ ] 十类控制项里，**管理类那五类**（制度 / 机构 / 人员 / 建设管理 / 运维管理）逐条指认了吗？AI 的缺口通常在这里，不在技术类。
- [ ] 有一张**密码清单**吗（算法 + 用途 + 密钥来源 + 是否国密）？**密评**是独立于等保的另一条赛道。
- [ ] 国产化清单里的**候选产品**点名了吗（向量库 / 消息队列 / 调度器三类最常空白）？
- [ ] 每个机制都有一条**十分钟内能做完的演练**吗？最近一次演练什么时候？

### 3.8 小结

> 本节小结：安全机制的形态由五条约束按序决定——**数据的用途 → 判定时点 → 暴露面覆盖 → 合规标准 → 人力承接**；九种模式里，**静态脱敏与四层权限是数据侧底座**（一个管出去的数据、一个管在里面的访问），**动态脱敏与召回期裁剪是在线路径的一对**（共享同一个身份与可见集判定），**DLP 必须双端且覆盖缓存与日志**，而 **DP 与 HE 是按需叠加的重武器，不进默认路径**；**黑盒化封装是这一节唯一一格把保护对象从「数据内容」换成「资产本体」的模式**——它的判据也随之从"字段有没有被打散"变成"物离开控制域后还能不能被使用"。判断这一块有没有真正建成，只看两条：**敏感数据被读出来的每一个位置，是否都有机制管着**；**每一条安全要求，能否用一次十分钟的演练证明它此刻生效**。**最后一条是本主题与其它主题最大的不同**：这里的产出物有一半是**证据**——机制做对了但不留痕，等于没做。

> 💡 **思考锚点**：从 §3.2 里挑一条你系统已有的机制，问三个问题：它**在哪个位置**生效（会不会被绕过）？它的**执行结果留在哪里**（能不能举证）？**谁**会用一次演练来证明它此刻有效（有没有人）？三问里最弱的那个，就是你下一步该补的地方——而它的补法通常不是"上一套新工具"，而是**把已有机制挪到不可绕过的位置并留下证据**。你打算先补哪一问？
