## 5. 踩坑与教训

这家公司的坑不是六件互不相干的事。把它们并排放，会看到同一条成因反复出现：**它的决策方式要求「同一个数在多处被引用」，而它的组织形态要求「每条业务线自己建自己的链路」——两个要求同时成立时，凡是需要有人「记得保持一致」的地方都会漂移。**

比坑的数量更值得看的是**代价落在谁头上**：

- 实验样本被稀释，代价由做实验的人承担——结论不显著，他只能把实验跑得更久；
- 口径出现第二份实现，代价由看数的人承担——两个数对不上，但两边都说得通；
- 训练侧与推理侧两份特征实现，代价由模型承担——效果下降，而离线指标没变；
- 资产不完备就开放给模型，代价由整个组织承担——一批回答都错了，且无法归因。

**承担者与制造者越不重合，这类坑活得越久**——这是本节要讲的主线，也是 5.3 那句判断的依据。

**证据档位**：本节【公开】只给可在仓库内指到的来源与年份；【推算】给出推导链；**沿用本案例材料的数字一律按【经验】使用——只取量级与方向、不取精确值**。【经验：本书从该案例的架构选择反推】专门标注那些**不是该公司公开承认过的故障、而是这条架构选择的必然推论**的条目。**「未能核到出处」既不构成「不存在」，也不构成「是真的」**，请按所给方向自行判定。

### 5.1 先看这家公司为什么会踩这些坑

三条约束限定了哪些错误是必然会犯的。

**第一，它的第一数据消费者是算法与实验，不是分析师**（[§3.1](03-byte-data-architecture-section-3-sec3.md)）——一个效果要上线必须先跑实验，于是「分流稳不稳、指标口径是不是只有一份」从体验问题变成了正确性问题。**因为结论会被直接用于定流量、定收入、定产品形态，所以口径错了不会被稀释，只会被放大到线上效果上。**

**第二，它的组织是多业务线并行、定义权天然分散。** 主文件记 20+ App，数据平台部约 500+ 人，而应用数据团队约 1500+ 人分散在各业务线上（【经验：主文件 §1.1、§1.3，只取量级】）——**因为定义权在业务侧、而引用方在别处，所以「同一份口径被复现成多份」是默认状态，不是异常。**

**第三，变更频率极高、消费者持续变化。** 主文件记 AB 实验每天上千个量级、推荐结果要求进入百毫秒量级、TikTok 需满足多法域合规（【经验：主文件 §2.1.4、§2.1.2、§1.2，只取量级】）——**每一次「谁在用」的扩张都会引入一类新的正确性要求，而这类要求在它刚出现时都没有载体。**

三条合起来，必然犯的错误只有三类：

| 约束 | 它决定了哪一类错误是必然的 |
| --- | --- |
| 决策依赖实验、结论直接进线上 | 口径必须唯一；出现第二份实现时，错的结论会被放大而不是被稀释 |
| 多业务线并行、定义权分散 | 实体、口径、特征都会被复现成多份；一致性只能靠人事后对齐 |
| 变更频率高、消费者持续扩张 | 新消费者的正确性要求总是先到、载体总是后到 |

反过来看，**这家公司几乎不会先犯的错误是「引擎选错了」**——那类错误可以靠一次采购或一次改造纠正。本节六条里只有一条的根在引擎上，而且它的修法也不是换引擎，而是把「运维动作的成本」从规模里拆出来。

### 5.2 坑逐个拆解（核心节）

#### 5.2.1 数据孤岛：同一个实体在多产品里是三份数据

- **症状**：
  - 问「同一个人在两个产品里的 ID 是不是同一个」，答不出来；
  - 一次跨产品分析在开工前要先开会确认「用哪一份数据」，对齐本身成了项目的前置任务。
- **机制**：
  - **因为早期每个产品一条直线链路、链路里没有任何共享层（[§3.2.1](03-byte-data-architecture-section-3-sec3.md)），所以「同一个实体」在结构里没有载体**——它只存在于各产品各自的 ID 里，「对齐」只能靠人事后做映射。
  - **因为对齐动作不改变任何一条链路的结构，所以它是可乘的**：每多一个产品，需要人工映射的组合数随产品数增长，而对齐成本落在不做产品的那个人（分析方）身上。
- **代价**：
  - 跨产品分析要先付一次对齐成本，才有资格开始算；
  - 实体合并规则一改，历史映射要回溯修正（[§3.6](03-byte-data-architecture-section-3-sec3.md) 第一行）；
  - 它是后续所有成本的放大器——任何跨产品的问题都要先解决「用哪一份数据」（[§3.5](03-byte-data-architecture-section-3-sec3.md)）。
- **改法**：
  - 建立实体对齐层（OneID）+ 可检索的资产目录；**先在「同一个实体」上归一，不要先统一全公司**（[§3.5](03-byte-data-architecture-section-3-sec3.md)）。
  - 判断方法：数一数同一个业务实体在你的系统里有几个 ID——超过一个，说明对齐层还没建（[§3.2.1](03-byte-data-architecture-section-3-sec3.md) 自验方法）。
- **出处**：【经验：本案例 [§3.2.1](03-byte-data-architecture-section-3-sec3.md)、[§3.5](03-byte-data-architecture-section-3-sec3.md)、[§3.6](03-byte-data-architecture-section-3-sec3.md)】；主文件把「多 App 数据打通」记为挑战（【经验：主文件 §2.1.1】）。

#### 5.2.2 ClickHouse 集群规模爆炸

- **症状**：
  - 集群长到某个规模后，**运维动作本身成为风险源**——改一次表结构、修一次副本、扩一次分片，需要触碰的节点数随规模上升；
  - 查「全集群有多少分区」这类元数据查询要遍历所有节点；本案例 [§8 面试真题集 §15.3.2](03-byte-data-architecture-section-8-sec8.md) 把这一阶段的瓶颈列成五项：协调组件、副本同步、元数据、小文件、升级与回滚。
- **机制**：
  - **因为原版把元数据协调放在外部协调组件上，而一次表结构变更是「涉及所有分片」的全局动作，所以节点数增长时每次全局动作的扇出同步增长**——协调组件从「一个可调参数」变成「集群规模的天花板」（[§3.2.3](03-byte-data-architecture-section-3-sec3.md)）。
  - **因为副本同步默认是异步的（写入先落本地副本，其余副本按队列后台拉取），所以写入速率与副本数上升时同步队列变长、副本落后成为常态**；而修复要靠人工触发一条系统命令——**人工动作的吞吐与集群规模成反比，这才是「规模爆炸」在运维上的真实形态**（[§8 §15.3.2](03-byte-data-architecture-section-8-sec8.md)）。

```text
规模爆炸的传导链（不是"机器不够快"）
  节点数 ↑
    ├─► 全局动作的扇出 ↑（改表结构 / 扩分片 / 升级 都要触碰所有分片）
    │     └─► 协调组件的写路径成为瓶颈 → 单次动作从分钟级变成"不可控"
    ├─► 副本数 ↑ 与写入速率 ↑
    │     └─► 异步同步队列变长 → 副本落后常态化
    │           └─► 修复靠人工触发 → 人工吞吐与规模成反比
    └─► 元数据查询要遍历所有节点 → "集群自己有多少分区"都要扫全集群
  ───────────────────────────────────────────────
  判据：把"规模指标"从节点数换成"一次全局动作的成本"
        （触碰多少节点、多少人工步骤、多久）
```

- **代价**：
  - 自研成本：把「一个开源引擎」改造成「一套能自运维的引擎」——统一管控层（把协调职责拆成配置 / 元数据 / 调度）、副本修复自动化、在线扩缩容、存算分离（[§3.2.3](03-byte-data-architecture-section-3-sec3.md)、[§8 §15.3.2](03-byte-data-architecture-section-8-sec8.md)）；
  - 更长期的**分叉成本**：上游每发一个版本，分叉面就大一点，「不回主干」会慢慢变成事实（[§3.5](03-byte-data-architecture-section-3-sec3.md)「自研分支没有退役计划」）；
  - 本案例材料把这一阶段的节点规模记在 5000+ 量级（【经验：本案例 §8 §15.3.2 记为 5000+ 节点；本节只取量级与方向，不引用精确值】）。
- **改法**：
  - **把规模指标从「节点数」换成「一次全局动作的成本」**——统计一次表结构变更 / 一次扩容 / 一次升级要触碰多少节点、多少人工步骤，用这个数判断「还能不能继续长」，因为节点数只是这个成本的自变量之一；
  - 容量与分片数要排进固定节奏复核，不能按当年数据量配一次就不再动（[§3.5](03-byte-data-architecture-section-3-sec3.md)「阈值与容量的静态假设」）；
  - 私有分支要有「回主干还是长期私有」的书面决定与时间点——**没有时间点的私有分支，等于一份没有截止日的债务**。
- **出处**：【经验：本案例 [§3.2.3](03-byte-data-architecture-section-3-sec3.md)、[§3.5](03-byte-data-architecture-section-3-sec3.md)、[§8 §15.3.2](03-byte-data-architecture-section-8-sec8.md)】。**ClickHouse 由 Yandex 以开源许可发布**（【公开：ClickHouse 官方仓库公开历史, 2016；本案例 [§7.2.2](03-byte-data-architecture-section-7-sec7.md) 已记同一出处】）。

#### 5.2.3 AB 实验「过度实验」导致决策缓慢

- **症状**：
  - 实验结果越来越不显著、要跑更久才敢下结论；
  - 同一个实验换一个指标口径，结论就反转；
  - 细分维度全部上升、而整体指标下降——本案例 [§8 §15.3.1](03-byte-data-architecture-section-8-sec8.md) 记出现过这类现象，并因此要求所有实验至少配置一个细分维度。
- **机制**：
  - **因为分流在层内互斥、而总流量是固定的，所以实验数上升时每个实验分到的样本单调下降**——样本量决定统计功效，功效不足时「真的没差异」与「没测出来」在输出上长得一模一样，于是唯一可做的动作是延长实验周期。**这条不能靠加机器解决**（[§3.2.2](03-byte-data-architecture-section-3-sec3.md) 失效点、[§3.3](03-byte-data-architecture-section-3-sec3.md) 第二对误配）。
  - **因为「效果」这个词只有在同一套指标定义下才可比，而口径只有在被复现时才有成本，所以一旦出现第二份实现，实验结论与看板数字就会对不上——而两边都说得通**（[§3.5](03-byte-data-architecture-section-3-sec3.md)「实验结论依赖口径而非变量」）。

```text
"过度实验"的算术（总流量固定时）
  实验数 ↑  ──►  每个实验分到的样本 ↓  ──►  统计功效 ↓
                                                │
                          ┌─────────────────────┴─────────────────────┐
                          ▼                                           ▼
              "没差异"与"没测出来"长得一样                  并行实验越多，整体假阳性率越高
               → 唯一动作是延长周期（组织在原地等）          → 结论进入会议室后先被怀疑
  ───────────────────────────────────────────────
  它是结构决定的：加机器改变的是集群规格，不是样本量
  （模式层面的推导见 §3.2.2 失效点与 §3.3 第二对误配）
```

- **代价**：
  - 不是服务器成本，是**决策时间与结论可信度**：实验要跑更久才有结论，会议室里反复出现「这次结论要不要信」；
  - 并行实验越多，整体第一类错误率越高（【推算：若 50 个实验相互独立、单个显著性水平 α=0.05，则至少出现一个假阳性的概率 = 1-(1-0.05)^50 ≈ 92.3%；该推导假设实验相互独立，互斥分层与多重比较校正正是为了削弱这个假设】）；
  - 本案例材料把同一流量池下并行的实验数记在 50+ 量级（【经验：本案例 §8 §15.3.1 记 50+，只取量级】）。
- **改法**：
  - 把「每个实验的最小样本量」写进实验申请单，放量前校验剩余未分配流量够不够——不够就排队，而不是照发（[§4.2](03-byte-data-architecture-section-4-sec4.md)）；
  - 实验按层做流量预算（本案例材料记有低流量实验需特批的准入机制，【经验：本案例 §8 §15.3.1；该阈值请按你的流量与效应量重新标定，不要照抄】）；
  - **判断是样本问题还是口径问题只需一个问题：把实验跑得更久，结论会不会变稳定——会则是样本量，不会则是口径**（[§3.3](03-byte-data-architecture-section-3-sec3.md)）；
  - 结论汇入口径有第二份实现的实验，先修口径再谈显著性，否则修的是噪声。
- **出处**：【经验：本案例 [§3.2.2](03-byte-data-architecture-section-3-sec3.md)、[§3.3](03-byte-data-architecture-section-3-sec3.md)、[§4.2](03-byte-data-architecture-section-4-sec4.md)、[§8 §15.3.1](03-byte-data-architecture-section-8-sec8.md)】；主文件把「AB 实验每天 1000+ 个」记为约束（【经验：主文件 §2.1.4，只取量级】）。

#### 5.2.4 实时特征「漂移」问题

- **症状**：
  - 模型上线后效果下降，而离线评估指标没变；
  - 把回填出来的历史特征与当时线上取到的值一比，对不上——本案例 [§8 §15.3.4](03-byte-data-architecture-section-8-sec8.md) 记踩过「回填逻辑与实时逻辑不一致」，并把一致性校验列为回填完成后的必做动作。
- **机制**：
  - **因为训练侧与推理侧的特征在很长时间里是两份实现（[§3.2.4](03-byte-data-architecture-section-3-sec3.md)），而「两份实现之间的差异」本身没有载体，所以差异不会报错，只会让线上分布悄悄偏离训练分布。**
  - **因为在线特征只保留「当前与近 N 天」，而训练要的是「某一天那一刻的取值」，所以没有按时间点回填的能力时，训练集只能用「现在的特征」去近似「当时的特征」**——模型因此学到了当时还看不到的信息，离线指标虚高（[§4.2](03-byte-data-architecture-section-4-sec4.md) 特征回填机制）。

```text
两份实现的差异通常不在"算法写错"，而在这三处口径
  ① 窗口边界        近 1 分钟 = [now-60s, now] 还是 [整分钟切片] ？
  ② 时间语义        按事件时间还是处理时间？迟到数据算哪一边？
  ③ 缺失值填充      上游没来时填 0、填 NULL、还是不产出这条特征？
  ───────────────────────────────────────────────
  三处都不会报错：它们只在分布上留下偏移
   → 症状出现在"模型效果"，线索却在"特征口径"，中间没有信号
```

- **代价**：
  - 模型效果下降的定位成本——排查要同时打开特征平台、实时链路与模型侧三处，而**没有任何一处会给出「是这里错了」的信号**；
  - 回填口径一旦修正，用旧口径历史特征训练过的存量模型必须重训，这件事要写进迁移计划，而不是等效果掉了再查（[§4.4](03-byte-data-architecture-section-4-sec4.md) ③）；
  - 长尾特征补不齐时，它们会长期是盲区（[§3.2.4](03-byte-data-architecture-section-3-sec3.md) 代价）。
- **改法**：
  - 每个特征声明新鲜度与回填方式、并挂血缘到上游明细表（[§4.2](03-byte-data-architecture-section-4-sec4.md)）；
  - 监控按四类设阈值——缺失率、延迟、回填一致性、分布差异（用 PSI / KS 比较当前窗口与训练窗口的分布）（[§8 §15.3.4](03-byte-data-architecture-section-8-sec8.md)）；
  - 判断方法：**抽 3 个特征，比较同一时刻离线算出与在线取到的值——差异必须能被解释；解释不出来的不许上线**（[§4.1](03-byte-data-architecture-section-4-sec4.md) Step 4 判据）。
- **出处**：【经验：本案例 [§3.2.4](03-byte-data-architecture-section-3-sec3.md)、[§4.1](03-byte-data-architecture-section-4-sec4.md)、[§4.2](03-byte-data-architecture-section-4-sec4.md)、[§4.4](03-byte-data-architecture-section-4-sec4.md)、[§8 §15.3.4](03-byte-data-architecture-section-8-sec8.md)】。

#### 5.2.5 数据合规「过度响应」

- **症状**：
  - 同一条合规要求在不同团队落地成不同范围的限制；
  - 某个新场景被合规评审挡下，却没人能指出挡住它的是哪一条法规的哪一句；
  - 数据本地化之后，能跨法域复用的资产（实体合并、特征、模型）明显变少。
- **机制**：
  - **因为合规约束是外部给定的、且按法域划线，而平台侧没有把「约束」写成可核对的参数（哪些字段必须本地化、哪些可以流动、删除权在哪些系统里必须级联），所以要求收紧时，唯一能直接执行的保守动作是「把限制范围放大到整份数据」**——限制范围大于监管需要的范围，这就是「过度响应」：**它不是一次判断失误，而是缺少「约束边界清单」时的默认动作**【经验：本书从该案例的架构选择反推】。
  - **因为「同一个用户」在法域边界两侧必须落成两份数据，所以实体对齐与特征复用这两个动作在跨境场景里天然失效**——切分面越大，可复用资产越少（[§3.2.4](03-byte-data-architecture-section-3-sec3.md)、[§3.2.5](03-byte-data-architecture-section-3-sec3.md)）。

```text
"过度响应"与"有边界响应"的差别，只在一张清单
  逐条可核对的约束清单（每行五格）
    哪一条法规 / 约束哪一类数据 / 允许的流动范围 /
    必须在哪几个系统里级联删除 / 谁有权签发豁免
  ───────────────────────────────────────────────
  有清单：限制范围 = 清单行的并集，可以逐条判定"是否过大"
  无清单：限制范围 = 整份数据，因为收紧是唯一能直接执行的保守动作
  ───────────────────────────────────────────────
  核对动作：每条实际限制必须指回清单上的一行
            指不回去的，就是可以缩小的范围
```

- **代价**：
  - 跨境场景的模型可用资产被切分——同一份特征、同一个实体合并规则要按法域各做一份；
  - 删除权要在多个系统里级联，级联清单不完整时「删除率」无法自证；
  - 数据团队的排期被合规评审占用，而评审结论无法复用——同一条法规下一次还要重新讨论一遍，成本随时间重复支出。
- **改法**：
  - **把合规约束写成一张可核对的清单**（上面那张五格表），再要求每一条实际限制都能指回清单上的一行；
  - 核对动作：抽 3 条已上线的跨境链路，把它的实际限制范围与清单逐条对照，指不回去的登记为「范围可缩小」并给出复核日期；
  - 这是判断方法，不是本案例公开承认过的整改方案——**本节不给方案，只给「怎么发现自己限制得比要求更宽」的动作**。
- **出处**：【经验：本书从该案例的架构选择反推】。主文件记该案例面临多法域合规与数据本地化、用户删除权要求（【经验：主文件 §1.2、§2.2.3】）；[§3.2.5](03-byte-data-architecture-section-3-sec3.md) 把合规与数据本地化列为产品化新增的三条结构约束之一（【经验】）。**具体法规文本、适用范围与生效时间，请以官方公报与监管机构网站当前版本为准。**

#### 5.2.6 大模型时代数据栈「演进缓慢」

- **症状**：
  - 模型能查到表、能生成 SQL，但答错的数**无法归因到具体资产**；
  - 团队把原因归结为「模型不行」；
  - 问「有多少条定义存在但已经过期」，没人报得出数。
- **机制**：
  - **因为模型对缺失的输入没有任何反馈机制，所以「资产不完备」不会表现为报错，只会表现为一个看起来合理的答案**【经验：本书从该案例的架构选择反推】——团队观察到的是「答案不对」，可归因的却是「模型能力」，于是真实问题被替换成一个可以靠花钱解决的问题（[§3.2.6](03-byte-data-architecture-section-3-sec3.md) 失效点、[§3.5](03-byte-data-architecture-section-3-sec3.md)「资产不完备就开放给模型」）。
  - **因为这一步的产出依赖前面各步的登记是否完整（指标定义、字段级血缘、Owner），而不依赖新建系统，所以它的进度不由项目排期决定，只由覆盖率决定**——「演进缓慢」的真实形态不是新系统没建起来，而是旧资产的定义长期没补完（[§4.1](03-byte-data-architecture-section-4-sec4.md) Step 7）。

```text
为什么它"慢"得看不见
  定义缺失 ─┐
  定义过期 ─┼─► 模型的输入里都表现为"空白" ─► 输出仍然是"一个合理的答案"
  血缘缺失 ─┘                                      │
                                                    ▼
                          团队看到的是"答案不对" → 归因为"模型能力"
                          ───────────────────────────────
                          真实待修的是覆盖率，而不是模型版本
                          预警信号具有迷惑性：回答不报错、引用的表也真实存在
```

- **代价**：
  - **错误被等比放大**——同一个错误口径，被人看到是「一个看板错了」，被 Agent 用是「一批回答都错了」（[§3.2.6](03-byte-data-architecture-section-3-sec3.md) 代价）；
  - 组织为「换一个更强的模型」付费，而问题在资产侧；
  - 若把模型接在表名而不是指标与字段上，错误连归因路径都没有（[§4.1](03-byte-data-architecture-section-4-sec4.md) Step 7）。
- **改法**：
  - **先度量覆盖率、再决定开放范围**——分母写清楚（指标定义 / 字段级血缘 / Owner 各覆盖多少）；
  - 每次打算扩大开放范围之前，重新数一遍「定义存在但已过期」的条目数，并把开放范围挂到这个数上（[§4.2](03-byte-data-architecture-section-4-sec4.md)）；
  - 让一个不了解数仓的人（或一个模型）只靠元数据回答「要算 X 该用哪张表、哪个字段、用了会影响谁」，答不上来就先缩小范围（[§4.1](03-byte-data-architecture-section-4-sec4.md) Step 7 判据）。
- **出处**：【经验：本案例 [§3.2.6](03-byte-data-architecture-section-3-sec3.md)、[§3.5](03-byte-data-architecture-section-3-sec3.md)、[§4.1](03-byte-data-architecture-section-4-sec4.md)、[§4.2](03-byte-data-architecture-section-4-sec4.md)；[§8 §15.3.6](03-byte-data-architecture-section-8-sec8.md) 记「消费者从人扩展为 Agent」这一变化】。

### 5.3 这些坑的共性

六条按成因归成三类：

| 成因 | 本节里的坑 | 为什么会反复产生 |
| --- | --- | --- |
| **共享资源被无约束消费** | 5.2.2 集群规模爆炸、5.2.3 过度实验 | 资源（集群、流量）是集中的，而消费决策（长规模、开实验）是分散的；**做消费决策的人不是承担代价的人** |
| **同一份定义出现多份实现** | 5.2.1 数据孤岛、5.2.4 特征漂移、5.2.3 里的口径污染 | 正确性只存在于实现里、没有可被引用的载体；**而复现一份比引用一份便宜，且当场就有效果** |
| **外部约束没有边界清单** | 5.2.5 合规过度响应、5.2.6 资产不完备就开放给模型 | 约束由外部给定、变化不由自己决定；平台侧缺一张「约束 → 数据 / 接口」的映射，**默认动作只剩全局收紧或全局开放** |

**最难改的是第二类。** 理由不是技术难度，而是**代价的承担者与制造者不重合**：

- 多复现一份口径的人，当天就拿到了自己要的数；成本由下游（做实验的人、看数的人、模型）在后面付。
- 多一份实现不会报错，只会让两个数对不上——**没有信号，就没有人能被指派**。
- 第一类可以用准入与排期管住：它有明确的可观察现象（实验越来越不显著、集群全局动作越来越慢），把现象写进准入条件就能收敛。
- 第三类可以用清单管住：约束是外生的，可以逐条对照、逐条判定范围是否过大。
- **只有第二类的修复动作落在「定义权归谁」上，而定义权是组织问题——它不会被一个技术方案关掉**（[§3.5](03-byte-data-architecture-section-3-sec3.md) 把这一条列为本案例最危险的反模式）；本案例为此付出的代价，见 [§7.6](03-byte-data-architecture-section-7-sec7.md) 对「字节的代价」那一段。

还有一条分布上的观察：**六条里只有 5.2.2 与 5.2.3 的症状是「响的」**（运维变慢、实验不显著），另外四条都是静默的——不报错、不告警，只让结论或效果慢慢偏掉。**主要成本在静默的那四条里**，这也是为什么 5.4 的检查动作大多不是「看监控」，而是「抽样比对」。

### 5.4 如果换成你，怎么提前发现

七条动作，每条写清抽什么、看什么、多久做一次：

1. **每季度**抽 3 个已跑过的实验，用当时的用户 ID 重算分桶，与实验期结果比对；同一次顺手看剩余未分配流量还剩多少（[§4.1](03-byte-data-architecture-section-4-sec4.md) Step 1 判据）。
   - 不一致 → 分流规则被改过或桶数被动过，续跑实验与历史结论要重新评估；
   - 剩余流量低于下一个实验的最小样本量 → 该排队，而不是照发。
2. **每月**数一次「同一个核心指标有几份实现」：在作业、看板 SQL、实验配置里搜同一个指标名，出现第二处实现就登记，并指定收敛日期。
3. **每季度**抽 3 个特征，比较同一时刻离线算出与在线取到的值；对不上则按窗口边界、时间语义、缺失值填充三处依次检查（[§4.1](03-byte-data-architecture-section-4-sec4.md) Step 4）。
4. **每次扩大自助分析 / Agent 取数范围之前**，数一遍三类覆盖率（指标定义 / 字段级血缘 / Owner）与「定义存在但已过期」的条目数，把开放范围挂到这个数上；数不出来就先缩小范围，而不是先换模型。
5. **每半年**做一次「全局动作演练」：改一次表结构、扩一次分片、升级一次版本，记录要触碰多少节点、多少人工步骤——用这个数（而不是节点数）当规模指标（[§3.5](03-byte-data-architecture-section-3-sec3.md)）。
6. **每半年**抽 3 条跨境链路，把它的实际限制范围指回「合规约束清单」上的一行；指不回去的登记为「范围可缩小」，并给出复核日期。
7. **每次变更**在 CI 里跑一次字段级影响面分析，把「这次变更会让哪个下游悄悄算错」变成可检查项；超阈值阻断合并，而不是等下游反馈（做法见 [§6 落地实践 6.1](03-byte-data-architecture-section-6-sec6.md) 里「血缘与质量共用一份元数据」那一节）。

这七条的共同点是**都能给出一个数**：不一致的分桶数、第二处实现的数量、解释不了的差异数、过期定义的条目数、一次全局人工步骤数、指不回清单的限制数、被阻断的合并数。**给不出数的检查动作不是检查，是表态。**

### 5.6 自检清单

- [ ] 抽 3 个写进周报或董事会材料的数字，每个能否指到**唯一**来源？指不出来的有几个？
- [ ] 同一个业务实体在你的系统里有几个 ID？跨产品 / 跨域分析时，实体对齐是自动的还是要人工映射？
- [ ] 抽 3 个已跑过的实验，用当时的用户 ID 重算分桶，结果与实验期一致吗？
- [ ] 同一个核心指标今天能数出几份实现？实验判定与看板各自引用的是哪一份？
- [ ] 剩余未分配流量是多少？最近一个实验放量前，校验过它够不够吗？
- [ ] 抽 3 个特征，同一时刻离线算出与在线取到的值，差异都解释得出来吗？
- [ ] 回填出来的历史特征与当时线上使用的值一致吗？不一致时，哪些存量模型需要重训，列出来了吗？
- [ ] 最近一次改表结构、扩分片、升级版本，各触碰了多少节点、多少人工步骤？这个数比上一次大还是小？
- [ ] 你的自研分支与上游差了多远？有没有写下来的「回主干」或「长期私有」决定与时间点？
- [ ] 抽 3 条跨境数据链路，它的限制范围能指回某一条法规的某一句吗？指不回去的有几条？
- [ ] 如果今天接一个 Agent 上来，它能读到「哪个字段是权威的、这个指标怎么算、用了会影响谁」吗？三项覆盖率的分母是什么？
- [ ] 上一次「数字对不上」，最后是改了定义，还是改了人？

### 5.7 小结

这家公司六条坑的根是同一条：**它每一次规模化的前提，都是先把一致性挂到一个可被检查的对象上**——实体挂到对齐层（OneID）、口径挂到指标定义、特征挂到一份定义加回填声明、引擎规模挂到「一次全局动作的成本」、合规挂到一张约束清单、资产挂到覆盖率的分母。

顺序反过来的每一次都付了学费：**先规模化、再补一致性的载体，规模会把每一个没有载体的假设放大成事故**，而其中最贵的一类（同一份定义有多份实现）连报错都没有。

换到别的公司也成立的只有这一条，而且它是本节唯一可执行的那句：**凡是需要有人「记得保持一致」的地方，都会漂移；只有能被机器检查的一致性，才有资格被规模化。**

> 💡 **思考锚点**：列一下你们现在靠「有人记得保持一致」撑着的地方——哪个实体的主键在几份表里各写一遍、哪个口径以谁的实现为准。挑其中最贵的一处（同一份定义有多份实现那种），问它今天挂在哪一个可被机器检查的载体上：对齐层、指标定义，还是一张约束清单？若都挂不上，按本节的判据，它就是在等规模把它放大成事故。
