## 4. 关键决策

[§ 3](03-byte-data-architecture-section-3-sec3.md) 回答的是「每一代被哪条约束逼出来」，结论由约束推出，选完就没有剩下的问题了。本节回答下一个、也更容易出错的问题：**栈选定之后，先做什么、做完怎么知道做对了、旧的东西怎么办、什么时候算做完。** 这几件事没有一件能从架构图里读出来。

本节对两类读者的入口不同。**从零搭一套「决策 + 实验」型数据栈的团队**从 4.1 的 Step 1 顺次走，4.4 只看「历史资产分类」那张表。**已经有一套数仓、一批自研作业和一堆看板的组织**（多数读者的实际处境）从 4.4 读起，再回头补 4.1 里被跳过的那几步——**跳过的步骤不会消失，它会在一个季度量级之后以「返工」的形式回来（【经验】：随下游数量与验证周期变），而返工面等于已建下游的数量。**

本节不重复 § 3 的约束分析与代际决策表（选型判据在 [§ 3.3](03-byte-data-architecture-section-3-sec3.md)），只给三样东西：每一步的**可检查产物与判据**、每条关键技术在什么条件下**会坏**、存量资产**怎么迁、什么时候能退出双轨**。证据分三档：【公开】给来源与年份，【推算】给推导链，**【经验】只给区间与量级**——沿用本案例材料的数字一律按【经验】使用，不取精确值；产品能力与版本以厂商官方文档当前版本为准。

### 4.1 落地步骤

七步的顺序**在每一段内部**与主文件 § 1.1 年表的先后一致（**段与段之间的先后服从依赖顺序，不按年份排**），分两段看：**内部能力的建设顺序**是 AB 平台（2015）→ ByteHouse（2017）→ DataLeap（2018）→ Lakehouse 与实时链路（2020）→ 能力中台化（年份据主文件 § 1.1 年表，【经验】）；**对外的那一步排在 AI 之前**——年表把火山引擎记在 2019 年起、豆包记在 2023 年、扣子记在 2024 年，所以「产品化对外」是 Step 6、「资产机器可读化 + AI / Agent 取数」是 Step 7。**这个先后不能反，理由见 [§ 3.3](03-byte-data-architecture-section-3-sec3.md) 的第三对误配。**每一步给三件事：**产物**（手上多出来、可被检查的东西）、**判据**（怎么知道做对了）、**为什么必须这一步、为什么在这个位置**。

**Step 1：先把「决策方式」平台化——分流 + 统一指标（1–2 个季度【经验：随实验数与涉及团队数变】）**

- 定分流规则：分桶键、桶数、以及「同一用户在同一实验里始终落在同一桶」这条不变量；把「未分配流量」显式留成一个池子，供后续调拨。
- 分层：按**改动面**分层（本案例材料记推荐算法 / UI 样式 / 广告策略三层），同层互斥、跨层正交。
- 把「效果」这个词的定义收到一处：指标名 / 定义 / 粒度 / 数据源 / Owner，一个指标一处定义。
- **产物**：分流 SDK + 配置下发通道 + 指标定义清单 + 一张「哪个实验在哪一层、占哪些桶」的台账。
- **判据**：抽 3 个已经跑过的实验，**用当时的用户 ID 重算分桶结果**，必须与实验期一致（同一个人不能今天在实验组、明天在对照组）；再抽 3 个指标，让两个人各自按定义写一遍 SQL，结果必须一致。不一致说明定义里有歧义——去改定义，不要去改人。
- **为什么必须这一步、为什么在最前面**：**因为本案例的第一数据消费者是算法与实验，不是分析师（§ 3.1），所以「决策方式」的平台必须先立**——它决定后面所有取数需求的形态：同一个数既被看板读、又被实验判定读。先建仓再建分流的后果不是慢一点：**它会产生两份「效果」的定义，而实验结论的可比性一旦丢失，历史实验没有重算的余地**——流量、策略与当时的分流状态都回不去了。

**Step 2：把交互式查询从批引擎里拆出来（一个季度到半年【经验：随待迁移作业数变】）**

- 先量两件事：交互式查询占多少比例、平均等多久；把「点查 / 聚合」与「大范围重算」分开统计——它们的解法不同（§ 3.2.3 的失效点）。
- 选型与改造：以列式引擎为基础做自研改造（本案例是 ClickHouse → ByteHouse），并围绕推荐侧的两类查询定制：**高并发宽表点查（特征回溯与在线召回共用一张宽表）与向量近邻检索**。
- 迁移只动**读路径**：先把 BI 与实验分析切过去，批处理与重度 ETL 留在原引擎。
- **产物**：一个独立于批引擎的交互式查询入口 + 一份《哪些作业迁、哪些不迁、为什么》清单 + 两个引擎的口径对齐说明。
- **判据**：**对同一张表、同一个指标，在两个引擎上各跑一次，差异要能被解释**（口径、时区、去重、快照时点）。解释不出来的差异不许放行。再抽 3 个常用看板，确认切到新引擎后数字不变。做到什么程度算成，可参照本案例记的结果——它承载字节内部绝大部分交互式 OLAP 查询，并成为火山引擎对外产品线中的一项（【经验】，只取量级与方向）。
- **为什么必须这一步、为什么在 Step 1 之后**：**查询量是被 Step 1 推起来的**——决策方式变成跑实验之后，查询次数才多到让批引擎的响应时间成为迭代瓶颈（§ 3.1 的「谁在用的变化先于数据量」）。反序做会得到一个没人用的引擎，因为「人等不起」这条约束还没成立。这一步的代价要写进判据里：**迁移是一个项目，不是一次升级**——SQL 方言不兼容，既有作业不能直接搬（§ 3.2.3）。

**Step 3：把开发链路收敛成一套平台（2–4 个季度【经验：随接入数据源与团队数变】）**

- 四块能力一起上，因为它们共享同一份元数据：数据集成（本案例是 DataX 字节版，基于 Flink CDC + Spark）、数据开发（可视化 DAG + Spark / Flink 任务）、数据治理（数据地图 + 血缘 + 质量监控）、数据服务（OneAPI 数据服务网关）。
- 接入顺序按「谁最疼」排——先接最常新建表、最常被下游催的团队，不按组织架构顺序接。
- **产物**：一套平台入口 + 一条「从建表到发布服务」的完整路径 + 一份接入清单（哪些团队、哪些任务已迁）。
- **判据**：**抽 3 个任务，从提交走到上线，全程不离开这个平台**（不需要某个人在本地补一步）；再抽 3 张新表，看它们的上游能不能在图里查到。
- **为什么必须这一步、为什么与 Step 2 相邻**：**因为血缘、质量、调度共用同一份元数据，所以治理动作不需要在每个工具里重做一遍**——这是「一站式」的真实收益，也是它唯一不能拆开上的理由。只把四个工具塞进一个界面而元数据各一份，得到的是四个彼此不知道对方存在的模块。代价是平台的每一次接口改动都影响所有接入方。

**Step 4：只在「结果进在线路径」处开实时链路，并把特征收口（2–4 个季度【经验：随链路数与特征数变】）**

- 对每一个「我们要实时」的需求，先写三行：**消费方是谁、延迟目标、纠错窗口**（这个数错了，最晚什么时候改还来得及）。只对「在线请求一次之内要读到」的需求开流。
- 链路形态：用户行为 → 消息队列 → 流处理 → 实时特征存储 → 模型推理 → 推荐结果；批侧保留全量、可回溯的那一份。
- 特征收口：**训练侧与推理侧引用同一份特征定义**；每个特征挂血缘（可追到上游 DWD 表）并声明回填方式（支持按历史时间点回填，用于训练）。
- **产物**：一张延迟分档表 + 一份实时特征清单（含新鲜度与回填声明）+ 一条可回放的链路。
- **判据**：**把这条链路今天关掉，业务多久会出问题**——答案不是「几小时内」的先不上；再抽 3 个特征，比较同一时刻离线算出的值与在线取到的值，差异要能被解释。
- **为什么必须这一步、为什么在 Step 2/3 之后**：**批侧的口径是判定流侧对不对的基准**——先有基准再上流，才有可能发现两侧分叉；反过来做，连「以谁为准」都定义不了。这条还有一层特性：**它先付成本后拿收益**——迟到、重复、乱序的处理逻辑与状态运维要先承担，而提前量的价值要等消费方出现才知道。

**Step 5：把推荐能力做成中台，让业务方复用（持续；首个业务接入 1–2 个季度【经验】）**

- 把四段能力分别做成可配置的：召回（向量召回 + 倒排索引 + 知识图谱）、粗排（轻量模型快速过滤）、精排（深度模型精细排序）、重排（去重、多样性等业务规则）。
- 业务方接口只留三步：**准备训练数据 → 选模型 → 一键部署**（平台提供若干预置模型，【经验】：具体数量随产品版本变，以产品文档为准）。
- 复用范围：本案例材料记抖音、今日头条、西瓜视频、TikTok 复用同一套推荐中台。
- **产物**：一套中台 API + 一份《业务方接入需要准备什么》清单 + 每个已接入业务线的 Owner。
- **判据**：**抽一个没有参与过中台建设的业务方，让它按清单独立接入一个场景**，全程不咨询中台团队的人。做不到，说明配置面还是按第一个业务长出来的。
- **为什么必须这一步、为什么在 Step 4 之后**：**中台复用的前提是「召回到重排」每一段都能被配置而不是被改代码**，而这些配置点是从多个业务的实际差异里长出来的——只有一个业务时差异还不存在，此时的抽象几乎一定是错的。这一步也是「算法工程师不必重复造轮子」这句话能兑现的唯一条件。

**Step 6：把内部能力产品化对外（以年为单位【经验】）**

- 先划清三件内部场景不存在的事：**多租户隔离、配额与计费、合规与数据本地化**；再定边界——不做基础设施、不做操作系统，做基于自有能力的应用 PaaS。
- 产品线：智能推荐、A/B 测试、ByteHouse（公有云）、DataFinder / DataLeap / DataWind 数据中台套件、豆包大模型与一站式 AI 服务。本案例材料记其客户覆盖小米、京东、长安汽车、中国移动等头部企业，并记 2024 年营收达到数百亿元量级（【经验】：只取量级与方向；这两项请以厂商公开案例与监管披露为准）。
- **产物**：一张《只在对外版本存在的约束》清单 + 接口兼容承诺 + 计费与 SLA 文档。
- **判据**：**让一个客户不经过你的工程师，自己完成开通、接入、监控、续费**。走不通就说明产品化还差一层。
- **为什么必须这一步、为什么排在 Step 7 之前**：**它的收益来自「内部平台的元数据模型、调度模型、权限模型本来就是多业务共用的」（[§ 3.2.5](03-byte-data-architecture-section-3-sec3.md)），所以只能在这些模型稳定之后做**——前五步都在让内部模型稳定，这一步才第一次把它们交给「和你没有劳动关系」的消费方。它必须排在 Step 7 之前的理由写在 [§ 3.3](03-byte-data-architecture-section-3-sec3.md) 的第三对误配里：**先产品化再开放给模型，你至少答得出「是谁在打满集群」；反过来做，Agent 会成为一个既没有合同、也没有配额归属的消费者。**代价是排期冲突与接口兼容成本——内部接口可以随时改，对外不行；两套需求一旦在代码里分叉，此后每一次改动都要改两处。

**Step 7：把已有资产机器可读化，再谈 AI / Agent 取数（持续）**

- 先把四类已有资产整理成可调用对象：数据 → 训练数据（OneID 生成）、特征 → 模型特征（Feature Store 直接对接训练）、指标 → 评估指标（指标平台计算）、实验 → 模型效果评估（AB 平台评估）。这一步几乎不新建系统，**只是给已有资产换一类消费者**（[§ 3.2.6](03-byte-data-architecture-section-3-sec3.md)）。
- 平台侧对应：扣子（Coze）一侧有 Coze Studio（智能体应用开发）、Coze 商店（应用商店）、Coze API（模型托管 + 推理 API）；豆包一侧按模态分通用模型、视觉模型（图像 / 视频理解）、语音模型（识别 / 合成）与多模态。本案例材料记其通用模型以 GPT-4 / Claude 3.5 为对标对象（【经验】：对标关系出自厂商自述，且随双方版本更迭而变，请按厂商公开评测与官方文档当前版本自行核验）。
- 只有资产的元数据可用之后，才把模型接上去——接在**指标与字段**上，不接在表名上。
- **产物**：一份指标 / 特征 / 实验接口清单 + 每类资产的覆盖率（分母写清楚）+ 一条受限词汇表。
- **判据**：**让一个不了解数仓的人（或一个模型）只靠元数据回答「要算 X 指标该用哪张表、哪个字段、用了会影响谁」**；答不上来就先缩小开放范围——此时接上去，它只能靠猜表名。再核对一次「定义存在但已过期」的条目有多少，因为模型不会告诉你它读到的是哪一种（[§ 3.2.6](03-byte-data-architecture-section-3-sec3.md) 的失效点）。
- **为什么必须放在最后**：**它的收益由前面几步攒下的资产完备度决定，不由模型能力决定**——它消费的是 Step 1 的指标定义、Step 2 的宽表口径、Step 4 的特征血缘与 Step 5 中台暴露出来的实验元数据；这些资产没到位时把模型接上去，只是把「答不上来」换成了「答得像是对的」。它也确实只能排在这里：**七步里只有这一步的产出不依赖新建系统，只依赖前面几步的登记是否完整**。代价是它会一直是个「还没做完」的步骤——正确形态是持续补定义与血缘，而不是一次性建成。

**七步里最常被跳过的是 Step 1 与 Step 7。** 跳过 Step 1 的症状出现在第一次「两个部门同一个数字对不上」，而它在本书里的代价格外重：**实验结论一旦依赖可变口径，就没有事后补救的余地**。跳过 Step 7 的症状出现在接上模型之后：能生成 SQL，但表名靠猜、答错的数无法归因到具体资产，团队会把问题归结为「模型不行」——实际缺的是资产的完备度。

### 4.2 关键技术点

**稳定哈希分流**

- **做法**：用「用户 ID + 实验标识」做稳定哈希落到固定桶数上（本案例材料记 10000 桶），实验按桶区间占流量；在线分流决策在毫秒级完成（本案例材料把这条记作「实时分流」），判定由 SDK 在本地算完、配置由平台下发。
- **机制**：这条能被大规模使用的组织侧原因是**配置可下发、分桶在 SDK 本地算完**——开一个实验不占离线任务、也不改被实验方的代码，所以「一天能跑多少实验」不再受发布流程限制；对落地更关键的是它的副产品：**分桶结果只由路由键决定、与调用时机无关**，所以补数、重跑、回放都能复现出同一批分组（模式层面的推导见 [§ 3.2.2](03-byte-data-architecture-section-3-sec3.md)）。
- **失效条件**：**当实验数增长到每天上千个量级（【经验：主文件 § 2.1.4】）、而总流量不变时，这条会坏在样本被稀释上**——分到每个实验的样本变少，结论越来越不显著（模式层面的推导见 [§ 3.2.2](03-byte-data-architecture-section-3-sec3.md) 的失效点）。本节要补的是落地判据：**把「每个实验的最小样本量」写进实验申请单，放量前校验剩余未分配流量够不够**——不够就排队，而不是照发。观测信号是「实验要跑更久才显著」；此时该动的是排期与分层治理，不是集群规格（[§ 3.6](03-byte-data-architecture-section-3-sec3.md) 第 3 行）。
- **档位**：桶数与分流算法属设计参数【经验】；稳定哈希分流与互斥分层是业内通用概念，可按关键词自行检索核验。

**互斥分层与流量调拨**

- **做法**：按改动面分层（本案例材料记推荐算法 / UI 样式 / 广告策略三层），同层实验互斥、跨层正交；未分配流量单独成池，按优先级动态调拨。
- **机制**：这套做法的可操作性全在「按什么分层」上——**按改动面分层时，同层实验天然争夺同一批用户，层内互斥才管得住冲突**；未分配流量显式成池，是为了让新实验拿流量时不必从正在跑的实验里抠（模式层面的推导见 [§ 3.2.2](03-byte-data-architecture-section-3-sec3.md)）。反过来，按团队分层时，层内互斥挡不住两个团队改同一处 UI 样式；按实验逐一分层，层数会随实验数一起膨胀。
- **失效条件**：**当分层设计跟不上业务改动面时，这条会坏在「跨层污染」上**。症状：同一个实验换一个指标口径结论就反转，或两个本应无关的实验相互影响——**这类污染通常不报错，只让结论变得不稳定**。
- **档位**：【经验】。

**显著性检验与早停**

- **做法**：平台自动算 P-value 与置信区间；达到预先声明的显著性后自动停止实验；所有实验接入统一指标平台。
- **机制**：**因为「效果」这个词只有在同一套指标定义下才可比，所以统一指标是显著性检验能跨实验比较的前提**；**因为早停是按事先声明的阈值触发的，它节省的是流量而不是判据**——阈值在开跑前就写死，不会变成事后挑结论的工具。
- **失效条件**：**当口径有多份实现时，这条会坏在「结论不可比」上**。症状：指标定义清单之外还有人在看板 SQL 里复现口径，实验结论与看板数字对不上，而两边都说得通。
- **档位**：【经验】。

**流量回放**

- **做法**：录制历史流量回放，用于验证分流改动与策略变更在真实流量分布下的表现；与实验平台共用同一份指标定义。
- **机制**：**因为回放用的是真实流量分布、且不占用实验名额，所以它能暴露实验本身发现不了的东西——分桶偏斜与改动后的指标偏移**（实验需要流量，而回放不需要）。
- **失效条件**：**当线上策略已经演化、录制的流量与当前系统状态不匹配时，这条会坏在「回放结论不可迁移」上**。症状：回放显示无差异，上线后指标却有变化——此时该检查的是录制的时效性，而不是回放工具。
- **档位**：【经验】。

**列式引擎与向量化执行**

- **做法**：交互式查询走列式引擎（本案例是 ClickHouse 自研改造后的 ByteHouse），批处理留在原引擎；围绕推荐侧两类查询定制——**高并发宽表点查（特征回溯与在线召回共用一张宽表）与 embedding 近邻检索**。
- **机制**：它的收益不来自「换了一个更快的引擎」，而来自**把查询按访问模式分成两类**——点查与聚合每次只碰一小部分数据，全量重算与跨大表关联不是；分不开时，引擎再快也只是把两类负载放进同一个队列里排队（模式层面的代价结构见 [§ 3.2.3](03-byte-data-architecture-section-3-sec3.md)）。这也是「围绕推荐侧两类查询定制」在落地时的位置：**点查与近邻检索的瓶颈不同（前者在并发与元数据开销，后者在距离计算次数），不定制时近邻检索会退化成对整个候选集算一遍距离**。
- **失效条件**：**当一个作业从批侧回流到交互式侧时，这条就坏了**——**落地判据是给交互式集群设一条「单查询扫描量上限」并在超限时告警**，把超限作业打回批侧（模式层面的失效点见 [§ 3.2.3](03-byte-data-architecture-section-3-sec3.md)）。观测信号：交互式集群被打满、实验分析响应被拖慢，而告警里排在前面的正是几个本该跑批的作业。此时该改的是作业归属，不是集群规格。
- **档位**：【经验】，只取方向与量级。本案例材料另记了两个倍数（「相比 ClickHouse 的性能提升倍数」与「规模提升倍数」）——**需要倍数级结论时，请以 ByteHouse 官方版本说明的当前版本为准**，本节只取「更快、可扩展性更强」这一层方向。

**特征一致性与特征回填**

- **做法**：训练侧与推理侧引用同一份特征定义；每个特征声明新鲜度与回填方式，支持按历史时间点回填；每个特征挂血缘，可追溯到上游 DWD 表。实时特征按来源分四类，每类都要在清单里有归属：**行为特征**（最近若干秒到分钟的点击、加购）、**画像特征**（年龄、性别、地域）、**场景特征**（时段、节日、热点）、**物品特征**（商品属性、视频属性）（【经验】）。
- **机制**：**因为「离线指标好、线上效果差」这类问题最贵的成因是两处实现的边界差异，把取数逻辑收到一处能让它从「反复排查」变成结构上不可能**；**因为回填是按时间点重算历史特征，训练数据的时间语义才与线上一致**——否则模型学到的是当时还看不到的信息。
- **失效条件**：**当线上真正在跑的模型只有一两个时，这条没有收益**——特征平台的运维对象（新鲜度、回填、一致性）是新增成本，而一致性问题还没发生。症状：特征仓库有表、有调度，但线上没有任何模型在读它。第二个失效条件是长尾特征补不齐：**它们会长期是盲区**（§ 3.2.4 的代价）。
- **档位**：【经验】。

**实时链路的分层与纠错窗口**

- **做法**：`事件 → 消息队列 → 流处理 → 实时特征存储 → 模型推理 → 结果`，每一段声明自己的延迟预算；乱序与迟到数据按**纠错窗口**处理（窗口内可修正，窗口外交给批侧修正）。
- **机制**：**因为在线请求只等一次，链路的每一段都必须有独立预算，而不是一个端到端目标**；**因为纠错窗口是显式声明的，「结果错了多久之内改还来得及」变成了一个可写下来的数**——它同时决定流链路的难度与在线侧要不要做兜底。
- **失效条件**：**上线前的准入判据只有一条——这条链路的消费方会不会在一次在线请求内读它**，答不上来的需求先不批（模式层面的失效点见 [§ 3.2.4](03-byte-data-architecture-section-3-sec3.md)）。已经建成的链路按同一条件定期复核：观测信号是两条链路的口径对不上、而遍历消费方没有一个需要毫秒级延迟——此时的正确动作是**下线这条链路或把它降级为批链路**，而不是继续投人对齐口径。
- **档位**：本案例材料记端到端在**一百毫秒量级**（【经验】，只取量级，不引用精确值）。

**可视化 DAG 与一键回滚**

- **做法**：任务用可视化 DAG 编排（Spark / Flink 任务同图）；每次发布生成可回滚版本，失败一键回退；平台自动识别慢 SQL、对作业给出自动优化建议；质量监控自动告警。
- **机制**：**因为「谁先谁后」被写成显式依赖而不是口头约定，这份知识就从人身上搬到了系统里**，人员变动时不会丢失；**因为发布有版本、回滚是一键的，上线从一次不可逆决定变成可回退动作**——这是团队敢频繁发布的唯一原因。
- **失效条件**：**当作业数量增长到「一次编排变更要重启半个平台」时，这条会坏在「没人敢改依赖」上**。症状：明明知道依赖写错了，排期表上却永远是「下个迭代再看」，而实际执行顺序靠几个人脑子里的记忆。自动优化建议的失效条件类似：**当建议与人写的作业冲突、且没有人对建议负责时，它会被集体忽略**。
- **档位**：【经验】。

**推荐中台的配置面**

- **做法**：召回、粗排、精排、重排四段各自抽象成配置；业务方接口只留「准备训练数据 → 选模型 → 一键部署」；业务特有的召回源由业务方自己接。
- **机制**：**因为四段之间的边界是固定的（候选集逐级变小），差异只发生在每段内部的策略与阈值上**——这正是可以被配置化、从而被复用的部分；边界之外的东西（业务特有的召回源、打分特征）必须留给业务方，否则中台会被某一个业务的需求拖成定制项目。
- **失效条件**：**当只有一两个业务接入时，这套配置面会坏在「抽象按一个业务长出来」上**。症状：第二个业务接入时发现要改中台代码而不是改配置——此时该做的是把差异点补进配置，而不是给这个业务开专用分支（分支一开，复用收益就没了）。
- **档位**：【经验】；预置模型数量随产品版本变，以产品文档为准。

**资产 → Agent 的接口层**

- **做法**：把数据、特征、指标、实验四类资产分别暴露成可调用对象（训练数据生成、特征供给、指标计算、实验评估）；对外只暴露受限词汇与 schema，不给库表直连。
- **机制**：这条在落地时是**一道准入检查，不是一次接口开发**——接口本身的开发量不大（资产本来就是结构化对象），真正的成本在「先度量覆盖率、再决定开放范围」这个顺序上；顺序反过来，就等于把资产完备度的问题推给模型去回答，而**模型对缺失的输入没有任何反馈机制，它只会照常输出一个结果**（模式层面的推导见 [§ 3.2.6](03-byte-data-architecture-section-3-sec3.md)）。
- **失效条件**：**当指标定义覆盖率或字段级血缘覆盖率低于你设定的门槛时，这条会坏在「回答看着合理、用的却是过期定义」上**（模式层面的失效点见 [§ 3.2.6](03-byte-data-architecture-section-3-sec3.md)）。本节要补的判据：**每次打算扩大开放范围之前，重新数一遍「定义存在但已过期」的条目数**，并把开放范围与这个数挂钩。观测信号是回答不报错、引用的表也真实存在；此时该做的是**把开放范围收回去**，而不是换一个更强的模型。
- **档位**：【经验】。

### 4.3 工具链与平台

下表按类目给候选与**选型判据**。判据的用法是：先在自己的约束里找出最紧的那条（[§ 3.3](03-byte-data-architecture-section-3-sec3.md) 的代际决策表），再看这一行里哪一列满足它。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 交互式 OLAP | Hive / Spark（批）、Presto / Impala（MPP）、ClickHouse 及其自研改造（本案例 ByteHouse） | 按五个维度权衡：**延迟量级、SQL 兼容性、生态与人才、运维复杂度、成本**。查询以点查与聚合为主、并发高 → 列式交互引擎；以全量重算与跨大表关联为主 → 留在批引擎；已有大量 Hive / Spark 作业且不能重写 → 先不要让交互引擎接管它们 | 用批引擎硬扛交互式查询：迭代速度被查询延迟卡住，而这是加机器解决不了的（产出周期有下限） |
| 数据集成 | DataX 及其字节侧改造（基于 Flink CDC + Spark）、Flink CDC | 增量与 CDC 需求重时选带 CDC 的；只需周期全量时选批量同步即可，不必顺带背上流式组件 | 每个源各写一套同步逻辑：schema 变更要人工跟进，且没有统一的失败重试与告警 |
| 流处理 | Flink、Spark Structured Streaming | 有状态、需要事件时间与一次性语义时选 Flink 一类；只需无状态过滤与转发时，轻量方案足够 | 用批调度「调密」假装实时：延迟仍不够，还把集群压满（§ 3.5 的反模式） |
| 消息与传输 | Kafka 及同类消息队列 | 需要多个消费方各自消费同一份事件时才引入；只有一个消费方时直接落存储 | 提前引入：多一个要值班的组件，收益为零 |
| 特征存储 | Feature Store、自研混合存储（本案例材料记 Redis + ClickHouse + 自研 KV 的混合形态） | 线上真正在跑的模型超过一个、且训练与在线取数由不同人负责时才引入；判据还要加上**是否真的需要按历史时间点回填** | 提前引入：有表没有读方，一致性收益为零、成本照付 |
| 开发与调度平台 | DataLeap（本案例：数据集成 / 开发 / 治理 / 服务四模块）、阿里 DataWorks 等其他一体化平台、各团队自建 | 判据是**血缘、质量、调度是否共用同一份元数据**，不是功能条数；不共用元数据的「一站式」等于四个模块拼在一个壳里 | 各自建：接入一个新源要重做一遍流程，血缘要各自解析 |
| 数据服务网关 | OneAPI（本案例）、自建 API 层 | 有多个业务方要以 API 形式取数时才建；只有一个消费者时不必 | 让业务方直连数仓：权限、限流与审计全落在人身上 |
| AB / 实验平台 | 自建（本案例）、商业 A/B 产品 | 判据是**分流能不能按你自己的路由键稳定复现**、指标能不能接入你自己的指标平台 | 用「先上后看」的手工对比：结论无法归因，且历史结论不可比 |
| 云 OLAP 与数据中台套件 | ByteHouse 公有云、DataFinder / DataLeap / DataWind、智能推荐、A/B 测试 | 只在内部平台已经稳定、外部有明确付费需求时产品化（§ 3.3 的 V5.0 行） | 把内部平台当产品卖：隔离、配额、SLA 三样都要补课式重构 |
| 大模型与智能体平台 | 豆包大模型、扣子（Coze：Studio / 商店 / API） | 判据不是「模型强不强」，而是**喂给它的资产是否完备**（指标定义覆盖率、字段级血缘覆盖率、Owner 覆盖率）；覆盖不了就先缩小自助范围 | 资产不完备就开放：错误被等比放大成「一批回答都错」，而模型不会告诉你它缺什么（§ 3.2.6） |

**这一类里最容易被误选的是「交互式 OLAP」与「特征存储」两项。** 前者被误选，通常只因为一句「取数慢」——而**慢的消费者是人还是程序，决定了该上交互式引擎还是该上流链路**（§ 3.3 的第一对误配）；选错方向的后果是人的等待时间没有改善，反而多了一套要维护、要对齐口径的链路。后者被误选，是因为它在成熟公司的架构图里出现得太多，于是被当成「到某个阶段就该有」的组件；**判据只有一条：今天有什么问题是我用现有组件解决不了的**——答不出来的不进。

上表的产品名均真实存在；具体能力、版本与配额请以厂商官方文档当前版本为准。本案例材料给的年份与量级一律按【经验】使用，只取方向与量级。

### 4.4 存量迁移

本节面向「已经有一套数仓、一批自研作业、一些看板」的组织——本案例的起点也是这样一个组织。

**① 先做哪一件「立刻见效且可回退」的事**

不搬数据、不改引擎。第一件事是**把「谁在消费什么数」写成一页纸**：列出每个会进周报、董事会材料或客户合同的数字，逐条填四格——这个数字是什么、谁拿它做决定、现在从哪来、它错了是损失收入还是损失信任。它立刻产出两个结果：一张「权威来源空白」的清单，以及后续迁移的优先序。第二件可回退的事是**只读分流**：把新的分流规则以只读方式接在流量入口上，只记录「按这套规则这个用户会落在哪一桶」，不改变任何线上行为，跑一段时间后与实际实验分配比对。两件事失败的成本都是删掉几行配置，而不是让业务停摆。

**② 历史资产怎么分类处理**

不要按「新旧」分类，按**引用面与处置成本**分三档：

| 档 | 判据 | 处置 | 不要做什么 |
| --- | --- | --- | --- |
| 全部返工 | 被对外口径引用，且在多个看板重复出现 | 按统一指标定义重建，旧实现下线 | 不要「先照抄再慢慢改」——照抄出来的第二份实现会立刻成为新的分叉点 |
| 只改动的部分 | 仍在被使用，但引用面只在一个团队内 | 不动存量，改到它的时候顺手迁过来，迁完即登记 | 不要为它排独立迁移窗口——收益不抵调度成本 |
| 打标挂账 | 无人能说清谁在用，或访问日志显示长期无读 | 标为「待定」+ 访问统计，到期无人认领即下线 | 不要直接删——它可能是别人的口径依据；也不要无限挂账——要设到期日 |

**③ 三类迁移各有各的难处**

- **引擎迁移（批 → 交互式）迁的是读路径**：写路径留在原处，先搬看板与实验分析，再搬重度 ETL。退出双轨的条件是「同一指标在两个引擎上的差异可解释且长期为零」。
- **分流平台迁移迁的是分流的权威性**：新旧两套规则要在同一段时间内同时记录、逐用户比对；**历史实验结论不做重算**（回不到当时的流量与策略状态），所以切换点必须写在前头——「某个实验编号之后的结果一律以新平台为准」。
- **特征迁移迁的是定义**：新特征与旧实现并行跑一段，比较同一时刻两侧的值。训练侧要特别注意：**回填出来的历史特征与当时线上用的是否一致，决定了存量模型能不能继续用**——不一致则存量模型必须重训，这件事要在迁移计划里写成一行，而不是等模型效果掉了再查。

**④ 双轨要维持多久、怎么维持**

双轨不是过渡语气，它是**一个有截止日的状态**。维持成本是「同一件事有两份实现」：两套分流、两套口径、两套特征各一份，每次变更要在两处同时改。可执行的规则只有一条：**每一次口径变更，必须同时改两侧并跑一次对账**。任何一次「这次先改一边」的例外，都会让目标侧在切换前就落后于源侧，等到要切的时候发现要重新对齐一遍。

**⑤ 什么信号说明可以退出双轨**

退出信号必须写在开工之前，写成「哪一天、以哪个指标、以哪个平台为准」，当作验收标准而不是「以后再定」。三个可观察信号：**对账差异连续若干周期为零且原因可解释**、**消费方主动从旧侧切到新侧（而不是被通知）**、**旧侧连续一段时间没有人查询**。满足两个即可安排下线；只满足第一个时不要切——那说明新侧只是「对得上」，还没被信任。

### 4.5 模板 / 示例

**模板 1：分流与分层配置**

```text
route_key = user_id                 # 必须用「参与实验时就已稳定存在」的 ID，不能用设备 / 会话 ID
hash_salt = layer_id                # 按「层」加盐：层内共用一套桶空间 → 层内互斥；层间盐不同 → 跨层正交
bucket    = hash(route_key + hash_salt) % 10000      # 桶数固定，上线后不要再改

layers:
  L1 推荐算法   exclusive = true
  L2 UI 样式   exclusive = true
  L3 广告策略   exclusive = true

allocation:
  experiment_A   L1   buckets 1000-1999     # 1000 桶 = 10% 流量
  experiment_B   L2   buckets    0- 499
  unallocated    pool buckets 2000-9999     # 显式保留，供高优先级实验调拨
```

**怎么用**：`route_key` 与「桶数固定」两行照抄——**改桶数等于把所有实验的分组重洗一遍**，续跑实验与历史结论会一起失效。`layers` 按改动面分，不按团队分。本案例材料把分流键记作「用户 ID + 实验 ID」的稳定哈希；要落成 `allocation` 里那种层内区间切分，**加盐必须按层而不是按实验**——按实验加盐时同层两个实验可能同时圈进同一个用户，层内互斥就不成立了。`unallocated` 必须显式写出来，否则高优先级实验只能抢别人的流量。

**模板 2：指标定义（实验与看板共同引用的唯一对象）**

```yaml
metric: 支付订单数                    # 一个指标一处定义
owner: 张某某（写人，不写团队）
definition: 统计已支付订单数
source_table: dwd_trade_order
source_fields: [order_id, order_status, pay_time]
filters: order_status = 'PAID'
granularity: [1d, 1h]                 # 粒度是定义的一部分，不是查询参数
sinks: [看板, AB 实验判定, Agent 取数]  # 三类消费者引用同一份定义
service_level: {freshness: "T+1 06:00", availability: "99.9%"}
lineage:
  upstream:   [ods_trade_order, dim_shop]
  downstream: [ads_gmv_daily, dashboard_trade_overview]
```

**怎么用**：核心是 `definition` 与 `filters` 两格，其余都是为了让它们可被机器读。`granularity` 必须填死——**粒度不写定的指标在跨粒度引用时一定会出现两个数**。`sinks` 这一格用来验证「引用的是定义还是复现的口径」：三处里任何一处自己写 SQL 复现，这格就名不副实。`service_level` 与阈值类的数字按你的承诺填，**不要照抄**。

**模板 3：特征定义与回填声明**

```yaml
feature: user_1min_click_cnt
entity: user_id
definition: 用户最近 1 分钟内的点击次数
freshness: {online: 秒级, offline: T+1}   # 两侧必须来自同一份定义
backfill:
  method: 按事件时间重算
  window: 最近 N 天                        # N 由训练窗口决定
  guarantee: 回填值与当时在线取到的值在容差内一致
lineage:
  upstream: [dwd_user_behavior]
owner: 李某某
```

**怎么用**：`freshness` 与 `backfill` 两格是这份定义的全部价值——只写 `definition` 的特征定义，和写在文档里的一句话没有区别。`backfill.guarantee` 是最容易被跳过的一格：**回填值与当时线上不一致时，用这段历史训练的模型与线上不同分布，存量模型必须重训**。`window` 按你的训练窗口定，不要照抄。

**模板 4：迁移退出条件单**

```text
迁移对象：{引擎 / 分流平台 / 特征}
以哪个指标、以哪张报表为准：{指标名 + 报表名}
新侧被认为正确的日期：{年-月-日}
对账频率与差异阈值：{频率}，{阈值}
历史结论怎么处理：{实验结论不重算 / 存量模型重训 / 历史看板保留只读 / 无}
旧侧下线后，谁负责回答「以前那个数为什么和现在不一样」：{姓名}
回退方式：旧侧保留到 {年-月-日}
```

**怎么用**：第三、四行必须事先写死。**第五行是本主题特有的一格**：分流平台与特征迁移都会产生「历史结论不重算」的问题，把它写明比留一套旧系统便宜得多。**第六行最容易被漏掉**，而它是唯一能让你在下线后不必自证清白的方式——留一份旧口径的说明，比留一个旧系统便宜。

### 4.6 自检清单

1. 抽 3 个写进周报的数字，能否各自指到一个**唯一**来源？指不出来的有几个？
2. 抽 3 个已跑过的实验，用当时的用户 ID 重算分桶，结果与实验期一致吗？
3. 同一个核心指标，今天能数出几份实现？两份以上时，实验判定与看板各自引用的是哪一份？
4. 抽 3 个常用看板，在交互式引擎与原批引擎上各跑一次，差异是否都有书面解释？
5. 每一条实时链路，消费方是谁？把它今天关掉，业务多久会出问题？答「几小时内」的有几条？
6. 抽 3 个特征，比较同一时刻离线算出与在线取到的值，差异解释得出来吗？线上有几个模型真的在读特征平台？
7. 特征回填出来的历史值，与当时线上使用的值一致吗？不一致时，哪些存量模型需要重训，列出来了吗？
8. 抽 3 张表，上游血缘能不能在图里查到？查不到的表有几个？
9. 一次任务失败到恢复，需要几个人在本地补步骤？发布能不能一键回滚，最近一次用回滚是什么时候？
10. 从接入一个新数据源到业务方能查询，平均要多久？这个数字最近是下降还是上升？
11. 把已有资产的元数据摆出来，一个不了解数仓的人（或一个模型）能只靠它回答「要算 X 该用哪张表、哪个字段、用了会影响谁」吗？不能时，缺的是定义、血缘还是 Owner？
12. 看板上的每一个数，谁能回答「它错了会影响什么」？答不上来的有几个？

### 4.7 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **Step 1——把「决策方式」平台化（分流 + 统一指标）**。它最便宜的时候就是它最早的时候：分流规则一旦上线、实验结论一旦被引用，改动的代价就从「改一份配置」变成「所有历史结论的权威性一起作废」；而它的产物（可复现的分流 + 唯一的指标定义）又是后面每一步的判定基准——没有它，你既判断不了一条新链路对不对，也判断不了引擎迁移有没有改变数字。其余步骤做错了，损失是成本高低；这一步做错了，损失是「结论还能不能被相信」。
>
> 💡 **思考锚点**：按 §4.6 第 3 条数一下，你那个核心指标（比如支付订单数）今天在系统里存在几份实现？如果不止一份，对照 §4.5 模板 2 的 `sinks`——看板、实验判定、Agent 取数这三处引用的到底是同一份定义，还是各自复现了一版口径？
