## 1. 背景

### 1.1 公司 / 业务 / 时间

字节跳动（ByteDance）成立于 2012 年 3 月，至今 13 年。数据架构演进的关键时间节点：

- **2012–2014：今日头条起步**。第一版推荐系统 + 数据栈，MySQL + Hadoop 为主。
- **2015：AB 实验平台 V1**。今日头条是字节第一个大规模 AB 实验的产品，2015 年正式建平台。
- **2016：抖音上线**。短视频推荐对实时计算要求极高。
- **2017：ByteHouse 立项**。基于 ClickHouse 自研改造，针对字节场景优化。
- **2018：DataLeap 立项**。数据集成 + 数据开发 + 数据治理的统一工作台。
- **2019：火山引擎成立**。字节 ToB 商业化平台正式成立，数据中台对外销售。
- **2020：Lakehouse 实践**。基于 Iceberg + Spark/Flink 的湖仓一体架构。
- **2021：Feature Store 平台化**。字节特征平台化，覆盖推荐 / 广告 / 搜索。
- **2022：抖音电商发力**。电商对实时数仓 + 实时推荐 + 实时风控提出新要求。
- **2023：豆包大模型发布**。字节大模型入场，数据栈向 AI Native 演进。
- **2024：Coze（扣子）智能体平台发布**。智能体应用爆款，数据中台成为"AI 中台"。
- **2025：豆包 1.5 Pro + 多模态**。大模型全面赋能业务。

**业务特点**：

- **多 App 矩阵**：今日头条、抖音、西瓜视频、番茄小说、剪映、CapCut、FaceBook（TikTok）、Lemon8、PICO 等 20+ App。
- **算法驱动**：推荐算法是核心竞争力，AB 实验是验证算法的唯一手段。
- **全球化**：TikTok 全球月活 15 亿+，数据合规要求跨多个法域。
- **数据规模**：抖音日活 7 亿+，每天产生 PB 级数据。

### 1.2 行业与监管

- **内容行业**：内容审核、合规、版权、青少年保护等强监管。
- **金融**：抖音支付、合规要求严格。
- **跨境监管**：TikTok 在美国、欧盟、东南亚多国运营，需要符合 GDPR / COPPA / CCPA 等多法规。

### 2.3 团队规模与组织

- **字节数据团队**巅峰期约 **3000+ 人**。
- **数据平台部**（基础平台）：约 500+ 人，负责 ByteHouse / DataLeap / AB 平台。
- **应用数据团队**：约 1500+ 人，分散在抖音 / 电商 / TikTok / 商业化 / 游戏。
- **算法工程师**：约 3000+ 人，与数据团队紧密协同。
- **组织文化**：**"始终创业"** + **"数据驱动"** + **"AB 实验优先"**。

## 2. 挑战

### 2.1 业务挑战

#### 2.1.1 多 App 数据打通

字节有 20+ App，每个 App 数据栈独立建设，"用户、内容、关系"等核心数据需要打通——OneID 需求强烈。

#### 2.1.2 推荐系统的实时性

抖音推荐延迟 < 200ms，AB 实验流量分配延迟 < 1 秒，这对实时计算 + 实时数仓要求极高。

#### 2.1.3 数据规模爆炸

抖音日活 7 亿+，单日用户行为数据 TB 级，单日推荐请求百亿级，存储成本与计算成本压力巨大。

#### 2.1.4 AB 实验的"小步快跑"

字节内部产品迭代极快（"AB 实验每天 1000+ 个"），对 AB 平台的要求是"分钟级启动、亿级流量稳定分流"。

### 2.2 技术挑战

#### 2.2.1 多模数据

抖音 / TikTok 是视频流，需要处理**视频、音频、文本、图片**多模态数据，对象存储 + CDN + AI 推理栈要求高。

#### 2.2.2 实时计算复杂度

推荐系统延迟 < 200ms，需要"**用户行为 → 实时特征 → 模型推理 → 推荐结果**"全链路实时。

#### 2.2.3 数据合规

TikTok 面临全球多法域合规，**GDPR（欧洲）、CCPA（加州）、COPPA（儿童）**等要求数据本地化、用户删除权。

#### 2.2.4 算法工程化

字节有 3000+ 算法工程师，每个工程师都有自己的模型、特征、AB 实验。如何**让算法工程化**——特征共享、模型共享、AB 平台共享——是核心挑战。

### 2.3 组织挑战

#### 2.3.1 AB 实验文化

字节"AB 实验优先"的文化渗透到每个角落，任何产品决策都需要 AB 验证。这要求所有产品经理 / 工程师都必须会用 AB 平台。

#### 2.3.2 数据驱动决策

字节内部不允许"凭经验决策"——必须用数据说话。这要求**数据查询速度**必须快（自助分析），否则无法驱动决策。

#### 2.3.3 全球化数据团队

TikTok 全球运营需要全球多区域数据团队，跨语言、跨时区、跨法规协同难度大。

## 3. 架构演进

### 3.1 V1.0：单产品阶段（2012–2015）

**形态**：

```
[业务] → [MySQL + MongoDB] → [Hadoop + Hive] → [Tableau]
```

**问题**：

- 数据孤岛，今日头条、抖音、悟空问答各自一套。
- 实时能力弱，推荐系统 AB 实验难以分钟级。

**教训**：早期数据栈能跑通，但不够"工程化"。

### 3.2 V2.0：AB 实验平台化（2015–2018）

**关键事件**：

- 2015：今日头条 AB 实验平台 V1 上线，覆盖所有推荐场景。
- 2016：抖音上线，AB 平台 V2，支持"亿级流量稳定分流"。
- 2017：AB 平台支持"互斥分层 + 流量调拨"。
- 2018：AB 平台对外，**火山引擎 AB 平台**（A/B 实验）成为 ToB 产品。

**核心能力**：

- **流量分桶**：基于用户 ID 哈希 + 互斥分层。
- **实时分流**：毫秒级决策。
- **统一指标**：所有 AB 实验接入统一指标平台。
- **置信度评估**：自动计算显著性。

### 3.3 V3.0：ByteHouse + DataLeap（2017–2020）

**关键事件**：

- 2017：ByteHouse V1（基于 ClickHouse 19.x 自研改造）。
- 2018：DataLeap V1（数据集成 + 数据开发）。
- 2019：ByteHouse V2（针对字节场景优化，分片、并发、副本）。
- 2020：ByteHouse V3（支持存算分离、云原生）。

**ByteHouse 关键改进**：

- **向量化执行**：相比 ClickHouse 提升 30%+ 性能。
- **分布式优化**：相比 ClickHouse 提升 10x+ 规模。
- **字节场景定制**：针对推荐场景的特征查询、向量检索。

### 3.4 V4.0：Lakehouse + 实时（2021–2023）

**关键事件**：

- 2021：基于 Iceberg + Spark/Flink 的 Lakehouse 架构。
- 2022：实时数仓 + 实时特征平台。
- 2023：Feature Store 平台化，覆盖推荐 / 广告 / 搜索。

**Lakehouse 关键能力**：

- **Iceberg 表格式**：ACID、Schema Evolution、Time Travel。
- **存算分离**：存储在 S3 / HDFS，计算在 Spark / Flink。
- **流批一体**：同一份代码同时跑批 + 流。

### 3.5 V5.0：火山引擎商业化（2019–2024）

**关键事件**：

- 2019：火山引擎成立，字节 ToB 商业化平台。
- 2020：火山引擎数据中台对外销售。
- 2021：ByteHouse 公有云版发布。
- 2022：火山引擎 + 抖音集团 + TikTok 三大业务板块成型。
- 2024：火山引擎大模型平台 + 字节豆包大模型对外服务。

**火山引擎核心产品**：

- **数据中台**：DataFinder（数据集成）+ DataLeap（数据开发）+ DataWind（BI）。
- **ByteHouse**：公有云版 OLAP。
- **AB 平台**：商业版 A/B 测试。
- **智能推荐**：基于字节推荐经验的产品。
- **大模型平台**：基于豆包 + 一站式 AI 服务。

### 3.6 V6.0：AI Native 数据栈（2023–2025）

**关键事件**：

- 2023：豆包大模型发布。
- 2024：扣子（Coze）智能体平台发布。
- 2025：豆包 1.5 Pro + 多模态，数据栈向 AI Native 全面演进。

**AI Native 数据栈关键能力**：

- **数据 → 知识**：结构化数据自动转化为大模型可消费的知识。
- **特征 → Agent**：特征平台成为 Agent 工具集。
- **指标 → Agent**：指标 API 成为 Agent Function Call。
- **AB → Agent**：AB 实验成为 Agent 自动决策工具。

## 4. 关键决策

### 4.1 决策 1：为什么 ClickHouse 而不是 Hive / Spark？

**背景**：2017 年字节推荐场景需要毫秒级 OLAP 查询，Hive / Spark 延迟秒级，ClickHouse 延迟毫秒级。

**决策路径**：

- **方案 A：Hive / Spark**：SQL 兼容、生态成熟。
  - 优点：开发成本低。
  - 缺点：延迟高。
- **方案 B：Presto / Impala**：MPP 架构。
  - 优点：相对快。
  - 缺点：并发能力有限。
- **方案 C（最终选择）：ClickHouse + 自研改造**（ByteHouse）。
  - 优点：延迟毫秒级，并发能力强。
  - 缺点：运维复杂、SQL 兼容性差、生态弱。

**Trade-off**：

| 维度 | ClickHouse | Hive / Spark |
| --- | --- | --- |
| 查询延迟 | 毫秒级 | 秒级 |
| SQL 兼容性 | 差 | 好 |
| 生态 | 弱 | 强 |
| 运维 | 复杂 | 一般 |
| 成本 | 低 | 高 |

**决策**：基于 ClickHouse 自研 ByteHouse。

**验证**：ByteHouse 2024 年承载字节 90%+ OLAP 查询，是火山引擎核心商业产品。

### 4.2 决策 2：AB 实验平台怎么设计？

#### 4.2.1 流量分桶

```
User ID → Hash(User ID) → Bucket 0-9999
Experiment → 100 流量 → Bucket 1000-2000
```

#### 4.2.2 互斥分层

不同实验层互斥，**避免实验相互干扰**：

- **Layer 1：推荐算法**（互斥）
- **Layer 2：UI 样式**（互斥）
- **Layer 3：广告策略**（互斥）

#### 4.2.3 流量调拨

支持把"未分配的流量"动态调拨到"高优先级实验"。

#### 4.2.4 显著性检验

- **P-value 计算**：自动计算显著性。
- **置信区间**：自动计算指标置信区间。
- **早停**：支持"达到显著性后自动停止实验"。

#### 4.2.5 关键技术

- **哈希分流**：基于用户 ID + 实验 ID 的稳定哈希。
- **实时分流**：RPC 调用毫秒级决策。
- **流量回放**：录制历史流量回放分析。
- **统一指标**：所有实验接入统一指标平台。

### 4.3 决策 3：DataLeap 怎么设计？

**DataLeap 是字节的数据开发平台**，对标阿里 DataWorks：

#### 4.3.1 核心模块

- **数据集成**：DataX 字节版（基于 Flink CDC + Spark）。
- **数据开发**：可视化 DAG + Spark/Flink 任务。
- **数据治理**：数据地图 + 血缘 + 质量监控。
- **数据服务**：OneAPI（数据服务网关）。

#### 4.3.2 关键能力

- **可视化开发**：拖拽即可完成数据集成 / 数据开发。
- **智能优化**：自动识别慢 SQL、自动优化 Spark 任务。
- **数据质量**：自动监控、告警。
- **一键回滚**：任务失败一键回滚。

### 4.4 决策 4：实时推荐架构怎么设计？

#### 4.4.1 抖音实时推荐链路

```
[用户行为] → [Kafka] → [Flink] → [特征存储] → [模型推理] → [推荐结果]
   (实时)    (毫秒)    (毫秒)    (毫秒)        (毫秒)       (毫秒)
```

**端到端延迟 < 200ms**。

#### 4.4.2 实时特征类型

- **行为特征**：最近 1 分钟点击、加购。
- **画像特征**：年龄、性别、地域。
- **场景特征**：时段、节日、热点。
- **物品特征**：商品属性、视频属性。

#### 4.4.3 实时特征平台

- **字节特征平台**：基于 Redis + ClickHouse + 自研 KV 混合存储。
- **特征血缘**：每个特征可追溯到上游 DWD 表。
- **特征回填**：支持历史时间点特征回填（用于模型训练）。

### 4.5 决策 5：推荐中台怎么搭？

#### 4.5.1 推荐中台能力

- **召回引擎**：向量召回 + 倒排索引 + 知识图谱。
- **粗排**：轻量模型快速过滤。
- **精排**：深度模型精细排序。
- **重排**：业务规则调整（去重、多样性）。

#### 4.5.2 多业务复用

抖音 / 今日头条 / 西瓜视频 / TikTok 都复用同一套推荐中台，业务方只需：

- 准备训练数据。
- 选择模型（系统提供 10+ 种）。
- 一键部署。

#### 4.5.3 效果

- 推荐中台覆盖 100%+ 业务方。
- 算法工程师无需重复造轮子，专注于业务。

### 4.6 决策 6：大模型 + 数据中台

#### 4.6.1 数据栈 AI 化

- **数据 → 训练数据**：OneID 自动生成训练数据。
- **特征 → 模型特征**：Feature Store 直接对接训练。
- **指标 → 评估指标**：指标平台自动计算模型评估指标。
- **AB → 模型评估**：AB 平台自动评估大模型效果。

#### 4.6.2 扣子（Coze）智能体平台

- **Coze Studio**：智能体应用开发平台。
- **Coze 商店**：智能体应用商店。
- **Coze API**：模型托管 + 推理 API。
- **2024 年爆款**：扣子成为字节 AI 应用入口。

#### 4.6.3 豆包大模型

- **豆包通用模型**：对标 GPT-4 / Claude 3.5。
- **豆包视觉模型**：视频理解、图像理解。

## 5. 踩坑与教训

### 5.1 坑 1：ClickHouse 集群规模爆炸

**问题**：2018 年 ClickHouse 集群规模达到 5000+ 节点后，**集群管理、元数据管理、副本修复**都成为瓶颈。

**根因**：

- ClickHouse 单机性能强，但分布式能力弱。
- Zookeeper 在大规模集群下成为瓶颈。
- 副本同步延迟、丢数据等问题频发。

**教训**：

- **ClickHouse 不能直接用于超大规模**——必须自研改造。
- **必须建立"统一管控层"**——屏蔽分布式细节。
- **必须有"运维自动化"**——副本修复、扩容、缩容一键完成。

**修正**：ByteHouse 自研"统一管控层" + "运维自动化平台"。

### 5.2 坑 2：AB 实验"过度实验"导致决策缓慢

**问题**：字节某业务方同时跑 50+ AB 实验，**实验互相干扰**，导致无法判断哪个实验真正有效。

**根因**：

- 流量不足时被分到 50+ 实验，每个实验流量太小，无法达到显著性。
- 互斥分层未严格执行，不同层实验相互影响。

**教训**：

- **AB 实验必须有"流量预算"**——不能无限开实验。
- **必须严格互斥分层**——避免实验冲突。
- **必须有"实验准入门槛"**——流量 < 5% 的实验不允许开。

**修正**：字节建立"实验准入机制"，流量 < 5% 的实验需要特别审批。

### 5.3 坑 3：实时特征"漂移"问题

**问题**：字节某推荐场景下，**实时特征分布与训练时差异巨大**，模型效果断崖式下降。

**根因**：

- 实时特征在生产环境的分布与离线训练时不同（如新用户占比上升）。
- 特征回填机制不完善，无法对比离线 / 在线特征。
- 特征监控缺失。

**教训**：

- **实时特征必须有"漂移监控"**——分布差异自动告警。
- **必须有"特征回填能力"**——离线训练时回填在线特征。
- **必须有"特征质量 SLA"**——延迟、覆盖率、准确率三大指标。

**修正**：字节建立"特征平台质量中心"，实时监控所有核心特征。

### 5.4 坑 4：数据合规"过度响应"

**问题**：2019–2021 年 TikTok 在美国面临监管压力，字节投入大量资源做"数据合规 + 数据本地化"，部分场景下"过度响应"。

**具体表现**：

- 数据本地化（美国用户数据必须存在美国机房）影响推荐效果。
- 用户删除权实现成本高，影响数据团队效率。
- 部分场景下过度限制，导致 TikTok 推荐算法效果下降。

**教训**：

- **合规是底线，但必须"业务可接受"**——不能为合规牺牲核心业务。
- **必须有"合规 + 业务"的双轨设计**——合规底线 + 业务灵活性。
- **必须建立"合规预审机制"**——新产品上线前先做合规评估。

### 5.5 坑 5：大模型时代数据栈"演进缓慢"

**问题**：2023 年大模型爆发后，字节数据栈从"传统数据栈"演进到"AI Native"的过程比预期慢。

**根因**：

- 数据团队对大模型不熟悉，技术栈切换成本高。
- 业务团队对"数据 → AI"的价值不清晰。
- AI Native 数据栈是新事物，没有成熟方法论。

**教训**：

- **AI Native 数据栈不是"一次性升级"**，而是"渐进式演进"。
- **必须建立"数据 + AI"双向团队**——数据团队懂 AI，AI 团队懂数据。
- **必须有"AI Native PoC"**——先用试点场景验证，再推广。

## 6. 复用经验

### 6.1 适合谁学

#### 6.1.1 内容 / 推荐 / 广告平台

- **典型**：资讯 App、短视频、电商。
- **原因**：AB 实验 + 推荐中台是核心刚需。

#### 6.1.2 强决策密集型业务

- **典型**：广告投放、电商推荐、出行调度。
- **原因**：实时决策 + AB 实验是核心竞争力。

#### 6.1.3 强 AB 实验文化的团队

- **典型**：互联网产品、SaaS 产品。
- **原因**：AB 平台是"文化载体"，没有文化等于没用。

#### 6.1.4 全球化业务

- **典型**：出海 App、跨境电商。
- **原因**：TikTok 全球化经验可借鉴。

### 6.2 不适合谁学

#### 6.2.1 传统企业（弱 AB 需求）

- **反例**：制造业、传统零售。
- **原因**：AB 实验对低频业务价值小。

#### 6.2.2 业务流程复杂但决策少的业务

- **反例**：B 端 SaaS、企业内部系统。
- **原因**：AB 实验场景少。

#### 6.2.3 单一业务线初创公司

- **反例**：早期 SaaS 公司。
- **原因**：投入产出比低。

### 6.3 关键可复用资产

#### 6.3.1 AB 实验平台

- **开源替代品**：
  - [GrowthBook](https://www.growthbook.io/)
  - [Eppo](https://www.geteppo.com/)
  - [Statsig](https://statsig.com/)
- **核心模块**：流量分桶 + 互斥分层 + 显著性检验。

#### 6.3.2 ByteHouse / ClickHouse

- **开源**：原版 ClickHouse。
- **商业版**：ByteHouse（字节云）、阿里云 ClickHouse。

#### 6.3.3 DataLeap / 数据开发平台

- **开源替代品**：DataWorks（阿里云）、Databricks Workflows。
- **核心模块**：数据集成 + 数据开发 + 数据治理。

#### 6.3.4 实时特征平台

- **开源替代品**：Feast、Tecton、Hopsworks。
- **核心模块**：特征存储 + 特征回填 + 特征血缘。

#### 6.3.5 推荐中台

- **商业产品**：火山引擎智能推荐。
- **核心模块**：召回 + 粗排 + 精排 + 重排。

#### 6.3.6 大模型（Ab 平台、豆包）

- **商业产品**：火山引擎豆包大模型、扣子（Coze）。
- **核心能力**：对话、推理、视觉、语音、多模态。

## 7. 与同类案例对比

### 7.1 对比维度

| 维度 | 字节跳动 | 阿里 | 美团 | Netflix |
| --- | --- | --- | --- | --- |
| 主导思想 | 数据驱动 + AB 实验 | 中台一体化 | 业务驱动 + 平台化 | 数据自由 + 自治 |
| 核心资产 | AB 平台 + 推荐中台 | OneData + OneID | Feature Store + 美团 ML | Iceberg + Spark + Flink |
| OLAP | ByteHouse（ClickHouse） | Hologres | ClickHouse | Iceberg + Spark |
| 实时能力 | 强实时推荐 | Blink + Flink | 实时特征 | Keystone + Flink |
| 商业化 | 火山引擎 | 阿里云 | 美团 ToB | Netflix 开源 |
| 大模型 | 豆包 + 扣子 | 通义 + 百炼 | 美团大模型 | Netflix Maia |

### 7.2 取舍

- **字节 = 数据驱动 + AB 实验 + 算法驱动**——把"实验"作为决策基础。
- **阿里 = 中台一体化 + 商业化**——把"中台"作为基础设施。
- **美团 = 业务驱动 + 平台化**——把"业务落地"作为价值核心。
- **Netflix = 自由 + 自治 + 创新**——把"工程师自治"作为组织文化。

**对架构师的启示**：

- **学 AB 实验文化**——这是字节最大的可借鉴资产。
- **学推荐中台思路**——但要按业务规模裁剪。
- **学火山引擎 ToB 模式**——字节内部能力外溢是 ToB 成功的关键。
- **不要照搬 ByteHouse**——很多场景 ClickHouse 原版够用。
