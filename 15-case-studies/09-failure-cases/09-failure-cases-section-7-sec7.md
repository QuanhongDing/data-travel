## 7. 与同类案例对比

> 原 § 7 共 29 行、为一张「类别 / 时长 / 根因 / 教训」的归档表加 4 条要点，既没有交代各案例的结构性约束，也没有可溯源证据（其中一处年份与公开事实不符），重写为 ~300 行同类案例对比。

### 7.1 先解决「可比性」

把「Facebook 十余小时」和「Cloudflare 半小时」放在「影响时长」这一列比较，是本类内容最常见的错误：**时长的差异几乎从来不是能力差异，而是「故障对象」的差异。** 一个是自治系统层的路由通告被撤回，恢复它要走物理路径；一个是边缘节点的 CPU 被一段正则表达式吃满，恢复它只需要停止下发那条规则。**比较时长之前，先要问「这个故障对象是什么、恢复它需要触碰什么」。**

原表还有一个更隐蔽的问题：它把「教训」当作案例的属性来排列（灰度 + 回退 / 命令防护 + 审计 / 熔断 / 备份 + 二次确认）。看起来四条都成立，实际它们是**同一个机制在不同故障对象上的四种投影**——它们全都指向「变更与破坏性操作的传播半径」。分开列，读者会以为是四件事要各做一遍；合起来看，才知道它们是一件事。

因此本节先列约束。故障类案例的约束与产品类案例不同，它关心的是四件事：

- **故障对象的层级**：是控制面（配置、路由、规则下发）、数据面（数据本身）、还是依赖面（恢复路径所依赖的系统）。层级决定恢复要触碰什么。
- **变更通道的传播半径**：一次变更生效需要多久、影响多少节点、能否分批。半径决定单次人为错误的爆炸半径。
- **恢复路径的独立性**：出故障后要用的工具、凭据、网络路径，是否也依赖刚刚坏掉的东西。
- **可逆性**：这个故障有没有「撤销」这个动作。可用性故障有撤销（时间成本），数据删除没有撤销（只能靠备份，而备份是否可用是另一个未知数）。

| 案例 | 故障类别 | 影响面（量级口径） | 恢复时长 | 结构性约束 | 证据档位 |
| --- | --- | --- | --- | --- | --- |
| Facebook 2019-03-13 | 控制面（BGP/DNS 配置变更） | 全球 Facebook / Instagram / WhatsApp | 十余小时量级（媒体统计常写作约 14 小时） | 变更一次全局生效；内部工具与修复路径也依赖被撤回的 DNS | 【经验/转述】时长数字来自媒体统计口径；Facebook 官方说明（Facebook Newsroom, 2019）只交代配置变更与「问题已解决」，未给小时数 |
| AWS S3 2017-02-28 | 数据面（误操作删除索引子系统） | 美东 1 区 S3，波及依赖它的 AWS 服务与大量客户 | 约 4 小时量级 | 被删的是索引子系统，重建它本身依赖同一子系统与备份 | 【公开】AWS 官方事后说明, 2017 |
| Cloudflare 2019-07-02 | 控制面（WAF 规则下发） | 全球边缘网络 | 约半小时量级 | 规则一次全量下发；缺陷是正则回溯，测试样本恰好不触发 | 【公开】Cloudflare 官方复盘, 2019 |
| GitHub 2018-10-21 | 数据面（故障转移后数据不一致） | 全站功能降级 | 约一天量级（分阶段恢复） | 43 秒网络分区触发自动切换 → 新主库数据落后 → 恢复需重建主库并校验 | 【公开】GitHub 官方事后分析, 2018 |
| Uber（本书 §3.7 记为 2018） | 数据面（数据库删除 + 备份不可用） | 部分用户数据不可恢复 | 不可逆 | 破坏性操作缺少二次确认；备份未经验证 | 【经验】该案例公开细节有限，各版本叙述年份有出入，只引用结构性教训 |
| 字节 2020（本书 §3.4） | 控制面（数据仓库迁移配置错误） | 多业务数据资产短时不可用 | 数小时量级 | 迁移缺少分批与回退路径 | 【经验】公开细节有限，只引用结构性教训 |
| Robinhood 2020 / 2021 | 容量与风控（行情剧烈波动期） | 交易不可用 / 限制买入 | 当日与后续监管后果 | 容量按常态设计；风控在流量峰值链路的关键路径上 | 【公开】公开报道与监管披露, 2020–2021 |
| 阿里中台（2018–2019 争议） | 架构治理（非宕机） | 组织与预算层面 | 以年计 | 中心化平台的响应时间随域数量增长 | 【公开】公开报道与公司公告, 2019–2023 |
| AI 项目失败（Watson Health 等） | 期望与数据（非技术故障） | 产品线被出售 | 以年计 | 训练/决策数据分散在多方且标准不一 | 【公开】IBM 官方公告《IBM Watson Health Divestiture》, 2022 |

> 本表刻意保留了三档标注。**故障案例是编造数字成本最高的地方**——一个错误的影响时长会被反复引用成「行业事实」。凡是公开复盘没有给出精确时长与规模的，本节只给量级并注明依据。

本节采用的判据是五个「先问约束」的问题：

| 判据 | 问的问题 | 为什么它决定结论 |
| --- | --- | --- |
| 故障对象层级 | 坏的是控制面、数据面，还是恢复所依赖的那一环 | 决定恢复要触碰什么，进而决定恢复时长 |
| 传播半径 | 一次错误能覆盖多少节点、能否分批 | 决定影响面，且与团队能力强弱无关 |
| 恢复路径独立性 | 「修它要用的东西」是否也依赖它 | 决定「有预案」能否变成「能执行预案」 |
| 可逆性 | 这个故障有没有「撤销」这个动作 | 决定防线要放在动作之前还是之后 |
| 归因层级 | 复盘产出落在「人」还是「系统」 | 决定改进项能否被验证、能否阻止重演 |

还要说清原稿那种「按时长排序」为什么危险：它暗示「时长短 = 做得好」。但 Cloudflare 的半小时和 Facebook 的十几小时不可比——前者的故障对象可以「停止下发即恢复」，后者需要有人物理到达机房。**把两个不同层级的故障放在同一根时间轴上，得出的结论必然是错的**：要么低估了配置类变更的风险（因为「才半小时」），要么高估了某个团队的能力（因为「恢复得快」）。

### 7.2 各案例的结构性差异（核心节）

#### 7.2.1 影响面由「变更通道的传播半径」决定，不由系统新旧决定

**差异是什么**：Facebook 一条 BGP 配置、Cloudflare 一条 WAF 规则，都能在几分钟内让全球服务不可用；而很多陈旧得多的系统反而很少造成全球性事故。差异不在技术先进程度，在**变更生效的传播路径**。

**各自的做法**：

| 案例 | 变更对象 | 生效方式 | 单次错误的爆炸半径 |
| --- | --- | --- | --- |
| Facebook 2019 | BGP 通告 / 域名系统配置 | 由自动化工具一次性整批下发 / 撤回，无分批动作 | 全公司对外服务 |
| Cloudflare 2019 | WAF 规则 | 全网边缘节点规则集 | 全球边缘网络 CPU |
| AWS S3 2017 | 运维命令 | 直接作用于生产子系统 | 一个区域的 S3 |
| GitHub 2018 | 高可用组件的自动决策 | 触发式（无需人为下发） | 全站写入路径 |
| 一般业务的常规发布 | 应用代码 | 分批 / 金丝雀 → 全量 | 一批实例 |

**这个差异由什么约束导致（因果句）**：**因为配置类变更的作用对象是「所有节点共享的那一份定义」，而代码发布的作用对象是「多份彼此独立的副本」，所以配置类变更的可分批性不取决于它是什么技术，而取决于「这份定义能不能被拆成互不影响的子集」与「下发通道能不能逐批推进」这两件事。** 这里要避免一个常见的过头结论：**「路由通告」本身并不天然不可分批**——通告是逐 peer 发送的，按 peer、按前缀逐步公布在工程上完全做得到，路由灰度是业界常见手法。Facebook 2019 真正不可分批的环节不在通告协议，而在**那套自动化审计工具对全局 BGP/DNS 定义做的一次性整批撤回**：一份定义、一个动作、全局生效，中间没有「先撤一部分、停下来看看」的位置。**判定一个变更对象能否分批，不要问它属于哪类技术，而要问三个可自行核验的问题：（1）这份定义能否拆成几个互不影响的子集？（2）下发动作能否按目标逐批执行、批与批之间能否停顿观察？（3）撤回时能否只回滚其中一批？** 三问都答「能」的对象可以走灰度；答「不能」的对象（共享的全局定义 + 单次整批动作）才必须配上「失败时能立刻停止下发并回滚定义」的终止开关。GitHub 2018 更极端：它的传播不是被人为下发的，而是**自动故障转移逻辑自己做的决策**——**因为决策是自动的，所以没有人有机会在下发前评估它**，这类变更通道必须额外回答「自动决策的上限是什么」。

**公开证据**：Cloudflare 的官方复盘把根因定位到一条 WAF 规则中的正则表达式在特定输入下产生灾难性回溯，导致边缘节点 CPU 被打满（[Cloudflare 官方复盘, 2019]）；Facebook 公开说明事故源于一次网络配置变更，恢复需要人工进入数据中心（[Facebook Newsroom, 2019]）。两者共同点：**根因都不在业务代码，而在控制面**。可自行核验的判定方法：列出你系统里所有「一次下发即全局生效」的对象（路由、证书、ACL、限流规则、WAF 规则、调度并发上限、功能开关），这些就是你真正的爆炸半径清单。

**对读者的意义**：**不要按「服务重要性」排故障风险，要按「变更通道的传播半径」排。** 应用不可能因为它「重要」就少出故障，只会因为它「可分批」而少出全球故障。这条判据还有一个推论：**排风险清单时不要问「哪个系统最重要」，要问「哪个变更通道最不可分批」**——两者的答案往往不是同一批系统。

#### 7.2.2 恢复时长由「恢复路径是否与被破坏对象共用依赖」决定

**差异是什么**：同样有备份、同样有预案，Facebook 用了十几个小时、AWS S3 用了几小时、Cloudflare 用了几十分钟。差异的关键变量是：**恢复所需要的东西，是否也坏掉了。**

**各自的做法**：

| 案例 | 恢复方式 | 恢复路径依赖什么 | 依赖是否也故障 |
| --- | --- | --- | --- |
| Facebook 2019 | 人工到现场改配置 | 内部工具、数据中心门禁、被撤回的 DNS | 是（内部工具也解析不到） |
| AWS S3 2017 | 重建索引子系统 | 索引子系统自身与备份 | 是（被删的就是它） |
| GitHub 2018 | 重建主库 + 数据校验 | 备份与新主库 | 部分（需在降级状态下完成） |
| Cloudflare 2019 | 停止下发错误规则 / 回滚 | 规则分发通道本身 | 否（分发通道仍可用） |

**这个差异由什么约束导致（因果句）**：**因为一次故障会同时破坏「服务」和「你用来修服务的那条路径」——这两者往往共享同一套网络、同一套鉴权、同一套 DNS、甚至是同一份数据，所以「有预案」并不等于「能执行预案」；恢复时间取决于预案路径上有多少环节与被破坏对象解耦。** 这条推论有一个很强的实践含义：**恢复能力必须被单独设计成一个不依赖正常路径的旁路**，它不能是对正常路径的复用。

**公开证据**：Facebook 的公开说明中提到，修复需要由现场人员执行（[Facebook Newsroom, 2019]）——这条信息本身就是「恢复路径与故障对象解耦不足」的公开证据。AWS 的事后说明描述了索引子系统被删除后需重建、且恢复过程受其自身依赖限制的经过（[AWS 官方事后说明, 2017]）。**可由读者自行验证的判定方法**：假设你的 Kubernetes 控制面、配置中心、身份提供方、DNS 同时不可用，你还有哪条路能改一行配置？如果答不上来，说明恢复路径没有独立设计。

**对读者的意义**：把「备份」和「可恢复」当成两回事。**备份是数据副本，可恢复性是一条独立的操作路径**——后者需要自己的凭据、自己的网络入口、自己的验证演练。

#### 7.2.3 可用性故障与数据丢失的修复函数不同：一个是时间，一个是不可逆

**差异是什么**：Facebook、Cloudflare 这类故障的代价是**时间**（时长 × 影响面）；数据删除类故障的代价是**状态**，而状态没有「时长」这个可恢复维度。

**各自的做法**：

| 故障类型 | 可撤销性 | 真正的防线 | 防线失效时的后果 |
| --- | --- | --- | --- |
| 控制面配置错误 | 可撤销（回滚定义） | 分批 + 立即停止下发 | 时长损失 |
| 容量过载 | 可撤销（降级 / 限流） | 冗余容量 + 熔断降级 | 短时不可用 + 用户信任 |
| 误操作删除 | **不可撤销** | 延迟删除窗口 + 二次确认 + 权限最小化 | 数据永久丢失 |
| 备份不可用 | **不可撤销** | 备份的**恢复演练**而不是备份本身 | 永久丢失（且发现时已太晚） |
| 数据不一致（GitHub 2018 型） | 半可逆（需重建与校验） | 对自动故障转移加一致性校验 | 长时间降级 + 人工校验 |

**这个差异由什么约束导致（因果句）**：**因为「删除」是一个把状态从存在变为不存在的操作，它的逆操作不是「执行反操作」而是「从副本还原」，而后者的存在性在删除发生之前是未知的，所以数据类故障的防线不能建在「动作发生时」而要建在「动作发生前」和「副本被验证过」这两个点上。** 更直接地说：Uber 型案例的教训不是「该有备份」——备份大概率是有的——而是**「备份从未被用于恢复过，因此它的可用性只是一个假设」**。这是下游所有「延迟删除 / 回收站 / 不可变备份 / 定期恢复演练」做法的共同理由。

**公开证据**：AWS 的 S3 事后说明描述了「一个本应只影响特定子系统的操作删除了远超预期的资源」这一过程（[AWS 官方事后说明, 2017]）；GitHub 的公开事后分析描述了网络分区后自动故障转移选了数据落后的副本、恢复需要重建主库并校验（[GitHub 官方事后分析, 2018]）。这两份材料的共同结构是：**故障不是「某处写错了」，而是「系统的某个自动化能力在边界条件下做了它被允许做、但不该做的事」。**

**对读者的意义**：把「备份有没有做」这个问题，换成「**备份最近一次被真实恢复过是什么时候**」。前者是配置问题，后者才是能力问题。

#### 7.2.4 复盘的归因层级，决定改进项能否被验证

**差异是什么**：同样是复盘，产出可能落在「人」这一层，也可能落在「系统」这一层。这两层的改进项性质完全不同：前者不可验证，后者可验证。

**各自的做法**：

| 归因层级 | 典型改进项 | 可验证性 | 效果 |
| --- | --- | --- | --- |
| 个人操作失误 | 加强培训、提醒注意 | 不可验证（无法证伪） | 同类事故在数月后重演 |
| 流程缺失 | 增加一次审批 | 半可验证（可统计绕过率） | 事故减少，但速度下降；审批易被形式化 |
| 系统设计 | 让这个动作在技术上不可能发生 / 出错即自动停止 | **可验证** | 该故障类别被消除 |

**这个差异由什么约束导致（因果句）**：**因为「人」不是一个可以被改造的对象，而「系统」是，所以只有当复盘的产出是一条能被代码或配置固化的约束时，它才具有阻止事故重演的能力；归因到人的复盘，其产出必然落在培训与提醒上，而这两者的效果无法被验证、也无法被持续。** 这就是「无指责复盘」的机制理由——它不是为了宽容，而是因为**归因到个人的复盘会产生一个负面激励：隐瞒信息**。当信息被隐瞒时，下一篇复盘的根因分析就失真了，整个学习循环断开。

**公开证据**：Cloudflare 在公开复盘中给出了极为具体的机制描述（正则回溯、规则的测试样本为何没覆盖它），这是「归因到系统」的形态（[Cloudflare 官方复盘, 2019]）；AWS 在事后说明中给出了恢复过程与后续措施（[AWS 官方事后说明, 2017]）。本书 [§4 FailOps 失败运营方法论](09-failure-cases-section-4-failops.md) 给了这套方法的完整流程。**可由读者自行验证的判定方法**：翻出最近三次复盘的改进项清单，数一数有几条能在三个月后被「查一下是否已上线」验证——这个比例就是你的复盘的产出质量。

**对读者的意义**：复盘的质量不由长度、深度、参与人级别决定，**只由「改进项能否被验证」决定**。

**四个维度不是并列权重，而是有层级**：

```text
故障对象（决定性质）
  ├─ 控制面  → 代价 = 时间，可撤销（7.2.1）
  ├─ 数据面  → 代价 = 状态，不可逆（7.2.3）
  └─ 依赖面  → 决定恢复时长（7.2.2）
        │
        ▼
  性质定了，才谈措施
  ├─ 限制传播半径：分批 / 终止开关 / 决策上限
  ├─ 保证可恢复：独立恢复路径 + 恢复演练 + 延迟窗口
  └─ 保证能学习：复盘归因到系统，产出可验证的约束（7.2.4）
────────────────────────────────────────────────
反过来读这张图，就是最常见的错误顺序：
先选了措施（「我们要做混沌工程」），再去找它对应哪个故障
```

**每个维度的失效条件**（机制优势在什么时候消失）：

| 维度 | 机制优势 | 失效条件 |
| --- | --- | --- |
| 分批发布 | 把全局爆炸半径降为一批 | 变更对象无法拆成互不影响的子集，或下发通道只能一次性整批执行（共享的全局定义、单次整批动作） |
| 终止开关 | 不依赖修复路径即可止血 | 开关本身的生效通道与被破坏对象共用依赖 |
| 恢复路径解耦 | 预案真的能执行 | 旁路口令/凭据长期不演练，已失效而无人知晓 |
| 延迟删除窗口 | 把不可逆转成可逆 | 窗口内无人监控，或备份才是唯一的还原手段而它未验证过 |
| 自动故障转移 | 缩短恢复时间 | 缺少一致性校验时，「切得快」会变成「切到旧数据」 |
| 无指责复盘 | 信息不被隐藏，根因才真实 | 追责文化残留 → 信息失真 → 复盘产出不可用 |
| 混沌工程 | 事前暴露问题 | 可观测性不足 → 注入的故障无法定位，等于自造事故 |

### 7.3 可迁移 vs 不可迁移

| 做法 | 可迁移？ | 为什么 | 迁移的前提条件 |
| --- | :---: | --- | --- |
| 变更分批 / 灰度发布 | 可（仅限可分批的对象） | 并非所有变更都能分批，但凡是能分批的，爆炸半径立即从全局降为一批 | 变更对象必须是可切分的 |
| 为「一次下发即全局生效」的配置建立终止开关 | 可 | 它把「回滚一个错误定义」变成一个不依赖修复路径的动作 | 存在集中下发的配置面 |
| 恢复路径与故障对象解耦 | 可 | 它只要求「不共用依赖」，与规模无关 | 愿意为一条几乎用不上的旁路付出常备成本 |
| 备份的定期恢复演练 | 可 | 它把「备份存在」这个假设变成「恢复可用」这个事实 | 有可用的隔离环境用于演练 |
| 破坏性操作的延迟窗口（回收站 / 软删除） | 可 | 它把不可逆操作转成可逆操作，成本极低 | 存储成本可接受 |
| 自动故障转移加一致性校验 | 可 | 它把「切换得快」和「切换得对」区分开 | 能接受切换延迟增加 |
| 无指责复盘 | 可 | 它是一条信息机制，不是资源投入 | 管理层真的不追责（形式化则立即失效） |
| 混沌工程主动注入故障 | 可（有前提） | 它把「演练」从事后搬到事前 | 已有基本可观测性与隔离能力，否则等于自造事故 |
| 跨区域多副本 + 异地容灾 | 部分可 | 机制通用，但成本随区域数与数据量线性增长 | 有明确的 RTO / RPO 要求支撑这笔开支 |
| 中心化平台 + 统一治理 | 需改造 | 机制可学，但它的代价随域数量增长 | 域数量尚不足以让排队成为瓶颈 |
| 100% 自动化运维 / 零人工介入 | 不可 | 故障处置的最后一环往往必须有人能物理到达 | 有等价的独立带外通道替代人工 |
| 组织级「中台化」战略 | 不可 | 它是组织与激励问题，不是技术问题 | 一把手工程 + 业务边界清晰 + 可分阶段验证 ROI |
| 对配置面建立变更对象清单 | 可 | 它只是把已有的事实写下来，零额外基础设施 | 有人负责维护并定期校对 |
| 迁移类操作的分批与双跑比对 | 可 | 它把一次性高风险动作拆成可验证的小步 | 能承担双跑期的存储与人力开销 |

**读这张表的方式**：前五行几乎是零前提条件可迁移的，它们也正是「预防性投入」里性价比最高的一组——**代价小、可验证、与规模无关**。后面几行需要前提条件，其中「混沌工程」与「多区域容灾」需要先有可观测性与明确的 RTO/RPO，否则投入会先于收益。最后两行是组织层，不属于架构师能单方面决定的范围。**判断一个做法能否搬走，问的应该是「它的前提条件我有没有」，而不是「它出自哪家公司」**——出自哪家与能否迁移无关，前提条件才有关系。

### 7.5 决策树（我该学谁）

```
第一步（与故障类型无关，先做）：翻出最近三次复盘的改进项，有几条能在三个月后
被「查一下是否已上线」验证？
│
├─ 很少 → 先修归因层级：把改进项从「加强意识 / 加强培训」改写成可查的系统约束
│         （§7.2.4）。归因层级不修，下面所有措施最终都会退化成提醒与培训
│
└─ 大部分能验证 → 进入第二步

第二步：你要防的是「时间损失」还是「状态损失」？
│
├─ 状态损失（数据删除 / 覆盖 / 不一致）
│   ├─ 删除类操作是否可逆？
│   │   ├─ 否 → 优先级最高：加延迟窗口（软删除 / 回收站）
│   │   │         + 二次确认 + 权限最小化        【学 AWS S3 2017 与 Uber 型教训】
│   │   └─ 是 → 验证延迟窗口是否真的被使用过
│   │
│   └─ 备份最近一次被真实恢复是什么时候？
│       ├─ 从未 → 立刻安排隔离环境恢复演练      【先学 GitHub 2018 的恢复代价】
│       └─ 近期演练过 → 检查恢复路径是否与故障对象共用依赖
│
└─ 时间损失（不可用 / 降级）
    ├─ 你的变更对象能否分批生效？
    │   ├─ 能 → 灰度 + 自动回滚               【学常规发布体系】
    │   └─ 不能（共享的全局定义被单次整批下发 / 撤回，中间没有停顿点）
    │       → 建立全局终止开关 + 变更前的影响面评估
    │         并把这批对象的清单显式维护起来   【学 Facebook 2019 / Cloudflare 2019】
    │
    ├─ 是否存在无需人为下发的自动决策（自动故障转移、自动扩缩容）？
    │   └─ 是 → 为它加一致性校验与决策上限；把它当成变更通道对待
    │          【学 GitHub 2018：切换得快不等于切换得对】
    │
    └─ 是否有明确的 RTO / RPO 要求？
        ├─ 有 → 按它反推多副本、异地容灾与演练频率
        └─ 无 → 先写下来；没有目标值的容灾投入无法验收
```

**阈值依据**：

- **根节点「时间损失还是状态损失」**：这是可逆性判定，不是数值阈值。依据在 §7.2.3——不可逆操作没有「时长」这个恢复维度，所以两类故障的防线位置本身就不同（一类在动作中止血，一类在动作前设限）。把它放在根上，是因为它决定后面各分支用的是同一套措施还是两套不同措施；判定只有一个动作：问「这个故障有没有『撤销』这个动作」。
- **第一步「改进项能否在三个月后被验证」**：这是复盘质量的唯一验收标准，也是整棵树的准入条件。它不是数值阈值，而是一个可执行的自检动作——翻出改进项清单，逐条问「怎么查它有没有上线」。因为归因层级决定产出形态（§7.2.4），而产出形态决定下游措施是否会被形式化，所以这一步必须在选措施之前做，不能作为分支末尾的收尾项。
- **「删除类操作是否可逆」**：这不是数值阈值，而是可逆性判定。它来自 §7.2.3 的机制——不可逆操作没有「时长」这个恢复维度，因此防线的位置必须在动作之前。
- **「备份最近一次被真实恢复过是什么时候」**：用「上次恢复演练距今」代替「备份保留天数」。保留天数是一个成本参数，恢复演练间隔才是能力参数。
- **「变更对象能否分批生效」**：由「这份定义能否拆成互不影响的子集」与「下发通道能否逐批推进」这两个可核验的问题决定，不由它属于哪类技术决定（§7.2.1，含三问判定法）。例：同一套 WAF 规则若按节点分批下发就可分批；而一份全局共享定义被单次整批撤回就不可分批——约束在「单一定义 + 单次整批动作」，不在协议本身。
- **「是否有明确 RTO / RPO」**：没有目标值就无法判断容灾投入是否足够，也无法验收。这条阈值来自「可验证性」这一原则，而非成本推导。
- **「是否存在无需人为下发的自动决策」**：这是分类阈值。存在自动决策的系统，其风险等级应按「变更通道」而非「服务」来评估。

### 7.6 各案例的失败面

**Facebook 2019 的代价** —— 为「统一的全球网络架构」付出了「单点配置错误即全局故障」的代价。这套架构带来了运维一致性，也带来了爆炸半径的全局化。它反噬的条件是：**当变更通道无法被切成可分批的物理单元时**，任何一次配置错误都没有中间状态。后续的缓解方向（把内部工具与对外解析路径解耦）本质上是给全局架构重新引入局部隔离。

**AWS S3 2017 的代价** —— 为「索引子系统的高效与集中」付出了「它被删除时恢复也要依赖它」的代价。这是典型的**耦合代价**：把能力集中到一个组件里换来了性能与简洁，代价是这个组件同时成为服务路径与恢复路径的必经点。它反噬的条件是：**当恢复动作需要与故障对象共享依赖时**，恢复时间不再由团队能力决定，而由耦合度决定。

**Cloudflare 2019 的代价** —— 为「规则表达的灵活性」（正则这种强表达力工具）付出了「测试样本难以覆盖全部边界」的代价。表达力越强的配置语言，越难穷举它的输入空间。它反噬的条件是：**当规则由强表达力工具书写、而测试只覆盖典型样本时**，缺陷会长期潜伏并在某次输入组合变化时集中爆发。缓解方向不是限制表达力，而是给所有节点加上独立于规则本身的资源熔断。

**Robinhood 2020 / 2021 的代价** —— 为「用有限容量承接爆发式增长」付出了「监管与信任后果」的代价。容量问题的特殊之处在于：**它不是技术故障的终局，而会转化为合规事件**——交易不可用与限制交易在金融场景下都直接进入监管视野。它反噬的条件是：**当容量规划以常态峰值为基准，而真实峰值由外部行情决定时**，系统会在最不能出问题的那天出问题。

**「把失败案例当故事讲」的代价** —— 这是本节最想指出的一条：案例读得越熟，越容易产生「我知道这些坑」的错觉。但案例的价值不在识别（谁都能认出灰度缺失），而在**把它变成一条你能验证的约束**。它反噬的条件是：**当复盘产出的改进项无法在三个月后被验证时**，案例就退化成了谈资——这也正是本文 7.2.4 那节要处理的问题。

**字节 2020 型（迁移故障）的代价** —— 为「一次性完成迁移以缩短双跑期」付出了「迁移过程本身成为风险事件」的代价。迁移与日常发布有本质区别：它的对象是**存量数据与存量依赖**，出错时无法像代码一样「重新发布一次」。它反噬的条件是：**当迁移不可分批、或者没有可回退的旧路径时**，迁移窗口就变成了一个不允许出错的窗口——而工程上不存在不允许出错的窗口，只存在出错了能退回来的窗口。

**阿里中台型（架构治理）的代价** —— 为「统一与复用」付出了「响应时间随域数量增长」的代价，而这类代价不会以故障的形式出现，它以「业务绕过平台」的形式出现。它比宕机更难发现：宕机有监控，绕过没有。它反噬的条件是：**当业务方开始自建「临时」能力时**——那说明平台的排队时间已经超过了业务的等待上限，而这通常是数年后才被管理层察觉的形态。

### 7.7 选型矩阵

| 你的处境 | 最该参考 | 最该避免照搬 | 理由 |
| --- | --- | --- | --- |
| 小团队，运维靠少数几人 | 备份恢复演练 + 延迟删除 | 混沌工程 / 多区域容灾 | 前两者零前提、代价小；后两者需要可观测性与明确 RTO/RPO 才有意义 |
| 有集中式配置下发（网关、ACL、限流、证书） | Cloudflare 2019 的终止开关思路 | Facebook 2019 的「全球统一」取向 | 你的配置面已具备全局生效特性，唯一解是给它加可立即停止的能力 |
| 有自动故障转移 / 自动扩缩容 | GitHub 2018 的一致性校验 | 「自动切换就是高可用」 | 自动决策是一类无人评估的变更通道，快与对是两件事 |
| 数据删除风险高（多团队共用生产权限） | AWS S3 2017 的权限与命令防护 | 只加审批流程 | 审批会被形式化；技术上不可能发生的动作不需要靠人记住 |
| 流量由外部事件驱动（行情、热点、大促） | Robinhood 型的容量与降级设计 | 按常态峰值扩容 | 峰值不可预测，必须用降级与熔断承接 |
| 正在做平台化 / 中台化 | 阿里中台争议的结构性解释 | 组织级「先建平台再接业务」 | 中心的响应时间随域数量增长，没有业务驱动的平台会先失去信任 |
| 打算上 AI 项目 | 先把训练/决策数据的可用性盘清 | 引用「80% 项目失败」来推进或劝阻 | 该数字不可溯源；能验证的是你自己的数据评估结果 |
| 正在做数据迁移 / 换引擎 | 分批 + 双跑比对 + 保留旧路径 | 一次性迁完以省双跑成本 | 迁移对象是存量数据，没有「重新发布」这个动作 |
| 复盘改进项落不到地 | 先修归因层级，再谈措施 | 增加审批环节 | 归因到人 → 产出是培训；归因到系统 → 产出是可固化约束 |
| 业务方开始绕过平台自建 | 按阿里中台型的机制诊断 | 追加治理制度 | 绕过说明排队时间已超等待上限，制度无法解决时间问题 |

**常见组合**（每条说明职责边界与代价）：

1. **分批 + 全局终止开关 + 变更对象清单**（常规发布与迁移通用）：分批负责限制半径（作用于可分批的对象），终止开关负责止血（作用于不可分批的对象），清单是前两者的前提——你无法为不认识的变更通道做防护。迁移类操作还要加**双跑比对**与**旧路径保留**：比对负责验证正确性、旧路径负责兜底，因为迁移的对象是存量数据，出错后没有「重新发布」这个动作，只有「退回来」。代价是清单需要纪律且会过期，双跑期要付存储与人力开销，并且必须显式回答「什么时候敢删旧路径」。
2. **延迟删除窗口 + 权限最小化 + 恢复演练**：三重防线对应「动作前、动作中、动作后」。代价是删除类需求的处理时长增加，以及演练要占用隔离环境。
3. **可观测性 + 降级预案 + 容量冗余**：可观测性负责发现，降级负责止损，冗余负责扛住。代价是冗余容量常年闲置——它的价值只在峰值那天兑现，因此必须由明确的 RTO/RPO 目标来支撑这笔开支。
4. **无指责复盘 + 改进项台账 + 定期核验**：机制、产出、验证三层。代价是它要求管理层在事故当下克制追责冲动；形式化的无指责复盘比不做更糟，因为它会同时失去信息与信任。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（结构性差异层面） |
| --- | --- | --- |
| 说不清自己有哪些「一次全局生效」的变更 | 先盘点变更通道 | 影响面由传播半径决定，不识别通道就无法限制半径 |
| 有备份，但从没恢复过 | 立即安排恢复演练 | 「有备份」与「能恢复」是两件事，只有演练能区分 |
| 删除操作不可逆 | 加延迟窗口与权限最小化 | 不可逆操作没有时间这个恢复维度 |
| 有自动切换 / 自动扩缩 | 加一致性校验与决策上限 | 自动决策是一类无人评估的变更通道 |
| 容量按常态峰值设计 | 改为降级 + 熔断 + 冗余组合 | 外部事件驱动的峰值不可预测 |
| 复盘产出是「加强培训」/「加强意识」这类 | 重写为可验证的系统约束 | 只有能被代码或配置固化的约束才具有阻止重演的能力（§7.2.4） |
| 想上 AI 项目 | 先盘数据可用性与评估集 | 项目失败的公开归因集中在数据与场景，而非模型 |
| 迁移计划是一次性切换 | 改为分批 + 双跑比对 + 保留旧路径 | 存量数据没有「重新发布」这个动作，只有「退回来」 |

> 本节小结：这些案例之间唯一真正起决定作用的结构性差异，是**「故障对象处在控制面还是数据面」**——控制面故障的代价是时间（可撤销，靠停止下发与解耦的恢复路径收敛），数据面故障的代价是状态（不可逆，只能靠动作前的约束与验证过的副本兜底）。**所有「我们该做哪些防护」的问题，都要先落在这条分界线上，再谈具体措施。**
>
> 本条分界线还给出一个排序建议：**先做不可逆的那一侧**。数据面的防线（延迟删除、恢复演练、权限最小化）代价小、不依赖规模、且一旦缺失就没有补救机会；控制面的防线（分批、终止开关）可以在系统演进中逐步补齐。
>
