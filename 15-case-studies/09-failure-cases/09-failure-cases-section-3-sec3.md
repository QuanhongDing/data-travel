## 3. 失败案例分析

### 3.1 案例 1：Facebook 2019 全球宕机

#### 3.1.1 事故背景

- **时间**：2019 年 3 月 13 日。
- **时长**：14 小时（部分服务 24 小时）。
- **影响**：全球 Facebook / Instagram / WhatsApp 不可用。

#### 3.1.2 事故经过

1. Facebook 日常的 BGP（边界网关协议）配置变更。
2. 配置变更导致 Facebook 域名服务器（DNS）的 IP 地址被撤回。
3. 全球用户无法解析 facebook.com。
4. Facebook 内部网络也无法访问。

#### 3.1.3 根因分析

- **直接根因**：BGP 配置错误。
- **深层根因**：
  - 缺乏配置变更灰度机制。
  - 缺乏回退机制。
  - 内部网络也基于被撤回的 IP，无法远程修复。

#### 3.1.4 解决过程

- 工程师亲自到数据中心现场修复。
- 但因数据中心访问权限系统也故障，进入数据中心耗时。
- 最终通过物理访问数据中心修复。

#### 3.1.5 教训

1. **配置变更必须灰度**——不能一次性变更。
2. **必须有回退机制**——出错能快速回退。
3. **内部网络必须独立**——不能基于被撤回的 IP。
4. **物理访问能力必须保留**——不能完全依赖远程。
5. **必须有"断舍离"机制**——即使主网络故障也能远程修复。

### 3.2 案例 2：AWS S3 2017 中断

#### 3.2.1 事故背景

- **时间**：2017 年 2 月 28 日。
- **影响**：AWS 美东 1 区 S3 服务中断 4 小时。
- **范围**：影响 AWS 自己的服务（EC2、Lambda、ELB 等）+ 全球数十万客户。

#### 3.2.2 事故经过

1. AWS 工程师在调试 S3 计费系统时，误输入了一条命令。
2. 命令删除了 S3 的一个关键子系统。
3. 该子系统负责索引 S3 对象，导致 S3 服务不可用。
4. 修复需要从备份恢复，但备份也需要该子系统。

#### 3.2.3 根因分析

- **直接根因**：人为操作错误。
- **深层根因**：
  - 缺乏高权限操作审计。
  - 缺乏"破坏性命令"防护。
  - 关键系统的严重耦合。

#### 3.2.4 解决过程

- 修复耗时 4 小时。
- 期间 S3 完全不可用。
- AWS 公开复盘并道歉。

#### 3.2.5 教训

1. **必须有"破坏性命令"防护**——删除 / 修改关键系统需要双重确认。
2. **必须有限定权限**——即使是工程师也不能随意修改关键系统。
3. **必须有"自动化操作"**——减少人工干预。
4. **必须有审计日志**——所有高权限操作可追溯。
5. **关键系统必须有"非耦合设计"**——核心系统独立运行。

### 3.3 案例 3：Cloudflare 2019 故障

#### 3.3.1 事故背景

- **时间**：2019 年 7 月 2 日。
- **时长**：30 分钟。
- **影响**：Cloudflare 全球 CDN 服务中断，影响大量客户。

#### 3.3.2 事故经过

1. Cloudflare 部署 WAF（Web 应用防火墙）规则更新。
2. 规则更新导致 Cloudflare 全球 CPU 使用率飙升。
3. 全球 Cloudflare 服务不可用。

#### 3.3.3 根因分析

- **直接根因**：WAF 规则更新触发 CPU 死循环。
- **深层根因**：
  - 规则缺乏充分测试。
  - 缺乏灰度发布。
  - 缺乏熔断机制。

#### 3.3.4 教训

1. **规则 / 配置变更必须灰度**——不能全量。
2. **必须充分测试**——尤其是边界场景。
3. **必须有熔断机制**——异常时自动回退。
4. **必须有 CPU 熔断**——CPU 使用率过高时自动熔断。

### 3.4 案例 4：字节 2020 故障

#### 3.4.1 事故背景

- **时间**：2020 年某日凌晨。
- **时长**：数小时。
- **影响**：字节内部数据平台故障，影响多个业务。

#### 3.4.2 事故经过

1. 字节数据团队进行数据仓库迁移。
2. 迁移过程中出现配置错误。
3. 部分核心数据资产不可用。
4. 多业务（抖音、今日头条、西瓜视频）受影响。

#### 3.4.3 根因分析

- **直接根因**：数据迁移配置错误。
- **深层根因**：
  - 数据迁移缺乏灰度。
  - 缺乏回退机制。
  - 缺乏完善的演练。

#### 3.4.4 教训

1. **数据迁移必须灰度**——从小数据量开始。
2. **必须有回退方案**——出问题能快速回退。
3. **必须有完善的演练**——在测试环境验证。
4. **关键数据必须多副本**——不能单点。
5. **必须有"演练日"机制**——定期演练。

### 3.5 案例 5：阿里 2018 中台争议

#### 3.5.1 事故背景

- **时间**：2018–2019 年。
- **类型**：架构争议而非宕机。
- **影响**：阿里中台战略遭遇内部质疑 + 行业反思。

#### 3.5.2 争议经过

1. 阿里中台 2016 年提出后被广泛跟进。
2. 2019 年很多企业跟风建设中台。
3. 但部分企业投入 2–3 年看不到效果。
4. 业务部门集体吐槽"中台无用"。
5. 阿里内部也反思"过度中心化"问题。

#### 3.5.3 根因分析

- **直接根因**：中台建设的"过度承诺 + 过度中心化"。
- **深层根因**：
  - 把中台当万能解药。
  - 缺乏业务驱动的中台。
  - 没有考虑组织文化差异。
  - "中台 + 业务"边界不清。

#### 3.5.4 教训

1. **中台不是万能解药**——必须有业务驱动。
2. **必须有"业务 BP"模式**——避免过度中心化。
3. **中台边界必须清晰**——平台 vs 业务。
4. **必须有"中台 ROI 评估"**——业务价值导向。
5. **中台建设是"一把手工程"**——没有 CEO 支持注定失败。

### 3.6 案例 6：Robinhood 2020 故障

#### 3.6.1 事故背景

- **时间**：2020 年 6 月 + 2020 年 9 月。
- **类型**：金融事故。
- **影响**：用户无法交易 + 系统性风险。

#### 3.6.2 事故经过（2020 年 6 月）

1. 2020 年 6 月，GameStop 等股票剧烈波动。
2. Robinhood 部分用户无法交易。
3. 部分用户被强制平仓。
4. Robinhood 暂停部分交易。

#### 3.6.3 根因分析

- **直接根因**：风控系统过载 + 交易系统卡顿。
- **深层根因**：
  - 风控系统基于实时计算，流量过大时崩溃。
  - 交易系统没有足够的容量冗余。
  - 合规监控不足。

#### 3.6.4 教训

1. **金融系统必须有"容量冗余"**——10x–100x 日常容量。
2. **风控系统必须高可用**——不能因流量过大崩溃。
3. **必须有"熔断 + 降级"**——必要时暂停交易。
4. **必须有"用户沟通"机制**——事故时及时告知。
5. **金融监管是硬约束**——必须有完善的合规监控。

### 3.7 案例 7：Uber 2018 数据丢失

#### 3.7.1 事故背景

- **时间**：2018 年某日。
- **类型**：数据丢失。
- **影响**：Uber 多个数据库被删除。

#### 3.7.2 事故经过

1. Uber 数据中心迁移。
2. 迁移过程中误删除生产数据库。
3. 备份机制不完善。
4. 部分用户数据永久丢失。

#### 3.7.3 根因分析

- **直接根因**：误操作 + 备份缺失。
- **深层根因**：
  - 数据迁移缺乏"二次确认"。
  - 备份未验证。
  - 缺乏回退机制。

#### 3.7.4 教训

1. **破坏性操作必须二次确认**。
2. **备份必须验证**——定期演练恢复。
3. **备份必须有异地副本**——多地容灾。
4. **必须有"延迟删除"机制**——删除可回退。
5. **必须有完善的权限审计**。

### 3.8 案例 8：AI 项目失败案例

#### 3.8.1 IBM Watson Health（2018–2022）

- **背景**：IBM Watson Health 是 IBM 主推的 AI 医疗项目，2018 年估值 50 亿美元。
- **失败**：2022 年 IBM 出售 Watson Health 业务，**巨亏数十亿美元**。
- **根因**：
  - **数据问题**：医疗数据分散在各家医院，标准不一。
  - **过度承诺**：Watson 早期宣传"取代医生"，实际做不到。
  - **场景问题**：医疗决策不能仅靠 AI。
- **教训**：
  - AI 不是万能解药。
  - 必须有"垂直场景"数据。
  - 必须有"业务可行性"评估。

#### 3.8.2 麦肯锡 2018 AI 项目失败率

- **背景**：麦肯锡 2018 年调研显示，**80% 的企业 AI 项目未能产生预期价值**。
- **根因**：
  - 数据质量差。
  - 业务场景不清晰。
  - 缺乏 AI 人才。
  - 缺乏"敏捷迭代"方法。
- **教训**：
  - AI 项目必须有明确业务价值。
  - 必须有"数据评估"。
  - 必须"小步快跑"。

#### 3.8.3 早期 RAG 项目失败

- **背景**：2023 年很多企业仓促上 RAG，**80% 失败**。
- **根因**：
  - 文档质量差。
  - 检索效果差。
  - 缺乏评估机制。
- **教训**：
  - RAG 不是装上向量数据库就行。
  - 必须有"文档质量"评估。
  - 必须有"检索效果"评估。
