## 4. FailOps 失败运营方法论

### 4.1 什么是 FailOps

FailOps 是从 SRE（Site Reliability Engineering）演化而来的"失败运营"实践，核心理念是"**把失败当常态，主动发现失败并恢复**"。

### 4.2 FailOps 关键实践

#### 4.2.1 混沌工程（Chaos Engineering）

- **核心理念**：主动在生产环境注入故障，验证系统韧性。
- **代表工具**：Chaos Monkey、ChaosBlade、Gremlin。
- **应用场景**：
  - 验证容灾切换。
  - 验证熔断机制。
  - 验证限流机制。

#### 4.2.2 应急响应（Incident Response）

- **关键流程**：
  - 检测（Detection）：监控系统检测异常。
  - 响应（Response）：应急小组响应。
  - 缓解（Mitigation）：采取措施缓解。
  - 恢复（Recovery）：恢复正常。
  - 复盘（Postmortem）：总结教训。
- **关键岗位**：
  - Incident Commander：指挥官。
  - Communications Lead：沟通。
  - Operations Lead：操作。
  - Subject Matter Expert：领域专家。

#### 4.2.3 复盘（Postmortem）

- **核心理念**：**"无指责"（Blameless）复盘**——找到根因，不追究个人。
- **关键输出**：
  - 时间线（Timeline）。
  - 根因分析（Root Cause）。
  - 教训（Lessons Learned）。
  - 改进项（Action Items）。
- **关键约束**：
  - 必须在 1–2 周内完成。
  - 必须有具体改进项。
  - 改进项必须有 owner 和 deadline。

#### 4.2.4 主动防御

- **预演**：定期演练应急流程。
- **灰度发布**：所有变更灰度。
- **熔断 + 降级**：必须有熔断降级机制。
- **回退机制**：必须有回退方案。

#### 4.2.5 落地步骤：五步的顺序、产物与判据

这套东西的落地不是「先买个平台」，而是**先说清这份记录给谁看，再保证止血得了，再让复盘有产出，最后才把演练做成常态**。这个次序与本章 [§3.4](09-failure-cases-section-3-sec3.md) 记的那条顺序（**先把传播半径限制住，再保证可恢复，最后才谈学习与复盘**）**同形**，只是在本节最前面多出一步；反序的典型形态与后果也写在那里（先上混沌与复盘制度、再补分批与恢复路径——事故继续发生，而复盘产出越来越长）。其中**「限制传播半径」属变更侧**，在本节的对应位置是 §4.2.4 的灰度发布与 §4.3 的「变更管理」一行，下面五步不重复展开。下面五步各给三件事：**产物**（手上多出来、可被检查的东西）、**判据**（怎么知道做对了）、**为什么必须这一步、为什么在这个位置**。

**Step 1：先写清「这份复盘给谁看、用在什么决定上」（半天量级【经验：随团队数变】）**

- 把 §4.2.3 的复盘记录从「本次事故的解释」定位成「下一次改流程的输入」，并把定位写成记录头部的**下游用途声明**：进不进绩效／晋升材料，只进流程改造的哪一块。
- 声明里要能读出两件事：追究对象是**系统与流程**（§4.2.3 的 blameless 前提），以及改进项由谁跟、跟到哪块看板上（下一格的产物在 Step 4 成型）。措辞与制度约定可参照 [14-leadership/06-postmortem-culture §4.5 模板 1](../../14-leadership/06-postmortem-culture/06-postmortem-culture-section-4-sec4.md)。
- **产物**：复盘模板头部的下游用途声明一行 + 一句「改进项由谁跟、跟到哪块看板」。
- **判据**：随机抽一份历史复盘，把它与最近一轮晋升／绩效材料交叉看一遍——它出现在后者里吗？出现了，说明声明还只是模板上的一行字（这一判据的形态取自 14-leadership/06-postmortem-culture §4 的 Step 1）。
- **为什么必须这一步、为什么在最前面**：因为披露代价在链的最上游——模板只是加工器，**输入是辩护词时加工得再精细也没有用**（§4.2.3 的 blameless 前提就是冲它来的）。而且这一步**不能补做**：第一次复盘怎么写，就会固化成此后「怎么写才安全」的写法，事后改模板改不动已经形成的习惯（这两句的出处是 14-leadership/06-postmortem-culture §4 的 Step 1——源句写「归因方法只是加工器」，其自查法是翻绩效材料里有没有引用过复盘文档，引用过即制度已破）。

**Step 2：把「先止血」制度化——排班、升级路径与四个应急岗位（2–4 周【经验：随值班人数与是否跨时区变】）**

- On-call 排班与升级条件：写清「谁在什么条件下被呼到」、每一级能批什么（回滚／降级／扩容）。
- 固定沟通入口：War Room 与频道固定下来，避免每次故障临时找地方（工具判据见 §4.3 的「应急沟通」一行）。
- 把 §4.2.2 的四个岗位（IC / 沟通 / 操作 / 领域专家）从名词变成具名的卡：**主责人 + 备位人 + 他能批什么**，卡片形态见 4.2.6 模板 2。
- **产物**：排班表 + 「分级 → 升级条件 → 谁有权批什么」对照表（分级等级沿用 14-leadership/06-postmortem-culture §4 的 Step 3 的 P0–P3 口径，本文件不另立一套）+ 四张角色卡 + 固定沟通入口。
- **判据**：随机点一个人当 IC 做一次桌面演练，问两句话——「现在一个 P1 挂了，你第一个动作是什么」「谁有权批回滚」；答出的路径能对上文档才算落地（判据形态取自 14-leadership/06-postmortem-culture §4 的 Step 2）。本节再加一条：翻上一季度【经验：观察窗口随你们的事故节奏变】的事故记录，§4.5 的第 ④ 类失效模式（应急角色缺位）还在不在——分工是照角色卡走，还是临场分的。
- **为什么必须这一步、为什么在 Step 3 之前**：复盘的四个时间点（发生 / 检测 / 缓解 / 恢复）**是响应流程的副产品**；没有流程时复盘只能靠参会者回忆，而回忆版本会**系统性地比监控数据更整齐、更连贯**（14-leadership/06-postmortem-culture §3.2.1 的失效点）。先建复盘制度再建响应流程，得到的是「时间线很顺、每个时间点却标不出在哪个系统里有对应记录」的文档。

**Step 3：先把「可恢复」补上，再谈学习（1–2 个季度【经验：随存量预案条数与可演练窗口变】）**

- 装 §4.2.4 的熔断 + 降级 + 回退：回退方案要**能当场翻出来**，且它的第一步所需凭据在「最坏情况」下仍然活着（本章 §3.7 第 8 问）。
- 降级档位事前定：停什么、保什么，且由容量／错误率信号触发，不靠现场判断（档位表见 4.2.6 模板 2 的「降级档位」一格）。
- 把恢复演练排进日历：备份不是能力，「最近一次被**真实执行**过」才是（本章 §3.3 决策表「删除类操作存在于生产」一行的判据）。
- **产物**：一份能当场翻出来的回退方案 + 一张「停什么、保什么」的降级档位表 + 最近一次恢复演练的记录（含执行人与时间点）。
- **判据**：§3.7 第 8 问——**备份最近一次被真实恢复是什么时候**？答不出日期，这一步就没有完成（本章 §3.3 也把它列为「延迟删除窗口」与「备份」这一对误选的唯一判据）。
- **为什么必须这一步、为什么在 Step 4 之前**：因为顺序是「先传播半径、再可恢复、最后学习与复盘」（本章 [§3.4](09-failure-cases-section-3-sec3.md) 的组合模式，该节最后一段给出的就是这条顺序）；另一个理由更直接——复盘的对象应该是**已经止住血的事故**，否则复盘退化成救火会议（§4.5 的降级策略：先止血再复盘）。
- **顺序的反面（最常见的错误）**：**先上混沌工程与复盘制度、再去补分批与恢复路径**——§3.4 末尾记的形态就是这样，结果是事故继续发生，而复盘产出越来越长。

**Step 4：定复盘流程与三条硬约束（2–4 周【经验：随故障频次变】）**

- 定时间盒：**1–2 周内完成**并写进记录头部（§4.2.3 的硬约束；14-leadership/06-postmortem-culture §4 的 Step 3 记的「24 小时内开完复盘会」是另一个口径【经验】——**取哪个都行，但要写死一个**，两头都写等于没有时间盒）。
- 定「完成」的定义：§4.2.3 的四个输出（时间线 / 根因 / 教训 / 改进项）齐；改进项三件齐——**具名 Owner + 期限 + 验证方式**（前两件是本节 §4.2.3 的硬约束，第三件见 4.2.6 模板 1）。
- 定跟踪：全部改进项挂到**同一块看板**，每周过一次——分散在各处就等于没有跟踪（§4.6 的规模信号要从这块看板上数）。
- **产物**：一份填完的复盘（用 4.2.6 模板 1）+ 改进项跟踪看板 + 「哪一级必须开、谁必须到场、多久内开完」的对照表。
- **判据**：抽 3 条改进项，看 Owner / Due Date / 验证方式是否三件齐，**缺验证方式的条目不计入关闭率**；再抽 1 条标「已完成」的，问一句「怎么验证它已经生效」——答案若是一份文档而不是一次能被查的验证，关闭率被高估了（判据形态取自 14-leadership/06-postmortem-culture §4 的 Step 3；其中 3 条与 1 条这两个抽样条数是源文的取值【经验：按单次复盘的改进项总数定，够逐条念完即可】）。
- **为什么必须这一步、为什么在 Step 5 之前**：因为「教训」这一环的产出质量取决于输入事实的完整度，而事实来自 Step 2 记下的时间点与 Step 3 的变更记录。先建注入能力再建复盘流程，会出现一种很难自查的失效：**注入记录很齐、结论也写了，但没有一条结论能落到一个具名的人与一个到期日上**。

**Step 5：装注入能力，并开始演练「演练」本身（首次注入 1–2 个季度【经验】；之后持续）**

- 装 §4.2.1 的注入能力，第一次只挑**一个假设**（「一个实例消失无感」还是「依赖返回错误值时降级正确」），并带稳态判据与中止条件（模板见 4.2.6 模板 3）。
- 把 §4.5 的三类演练排进日历：**game day**（故意让扮演 IC 的人中途离场）／**复盘质量抽检**（数 owner 覆盖率与关闭率，模板见 4.2.6 模板 4）／**角色轮换**。
- 每次注入必须带整改闭环：注入 → 观测 → 改进项 → 回归；改进项进 Step 4 的**同一块看板**。
- **产物**：一个可用的注入入口 + 一张演练日历 + 每次注入的改进项（进看板）。
- **判据**：注入的故障里，有没有一次真的打到了稳态判据并触发中止；注入产生的改进项有没有进看板并被关闭（§4.5 抽检要数的两个数：owner 覆盖率与关闭率）。
- **为什么必须这一步、为什么排在最后**：**它必须先有「止血」与「复盘」两件事才能产生收益**——没有回退路径时注入只是在制造事故，没有改进项闭环时注入的故障下次照旧（§4.5 第 ③ 类失效模式「混沌无人修」）。这也是 §4.6 把混沌平台放进 1 → 100 而不是 0 → 1 的原因：0 → 1 的最小可用是**一份 blameless 模板 + 一次真做完的复盘**。

**五步里最常被跳过的是 Step 1 与 Step 3。** 跳过 Step 1 的症状是复盘里「当时不知道什么」这一类信息被系统性省略——记录看起来完整，却推不出改进项（改进项只能从「当时的判断为什么不成立」里长出来）。跳过 Step 3 的症状是**复盘越写越长而事故照旧发生**（§3.4 末尾记的正是这个形态）。

#### 4.2.6 模板 / 示例：四份可填空的单元

四份单元分别对应 §4.2.3（复盘单）、§4.2.2（角色卡）、§4.2.4 + §4.5（演练单）与 §4.5 的抽检方案（抽检单）。**所有 `{...}` 都是待填项，不许照抄示例措辞**；阈值类的格子从你们自己的稳态看板与 SLO 里抄，本节不给可抄的数字。

**模板 1：blameless 复盘单（本节口径）**

```markdown
# 复盘 - {故障标题}

> 本记录不进绩效考核输入、不用于晋升评价；追究对象是系统与流程。（§4.2.3 的 blameless 前提）

## 一张表看完
- 复盘开始日：{YYYY-MM-DD}　目标完成日：{YYYY-MM-DD}     # §4.2.3 要求 1–2 周内完成
- IC：{具名}　记录人：{具名}　参与方：{团队清单}

## 时间线（取系统记录，逐条标「当时已知信息」）
| 时间点 | 系统状态 | 当时可观测到的信号 | 当时据此做的判断 |
| --- | --- | --- | --- |
| {HH:MM} | {____} | {____} | {____} |

覆盖节点至少包含：发生 / 检测 / 分级 / 缓解 / 恢复（源模板按七级列，此处取这五级；其中「发生 / 检测 / 缓解 / 恢复」即 Step 2 的四个时间点，「分级」是「把它定为哪一级」的那一刻——它是这条时间线自己的节点，与 §4.2.2 的处置环节不是同一组）

## 根因与促成因素
- 触发因素（直接触发）：{____}　促成因素（多条）：{____}
- 根因（主语写系统与流程，不写个人）：{____}

## 检测与响应
- 检测方式：{告警 / 用户反馈 / 监控}　TTD：{__}　TTM：{__}　TTR：{__}

## 改进项（缺任一列即视为未闭环）
| ID | 描述 | Owner（具名） | Due Date | 验证方式 | Status |
| --- | --- | --- | --- | --- | --- |
| AI-001 | {____} | {____} | {____} | {怎么算完成} | {Open / In Progress / Done / Blocked} |

## 教训
1. {指向可复用的机制，不写「加强培训」「下次注意」}
```

**怎么用**：三处结构不能改——头部的下游用途声明、时间线的「当时已知信息」一列、改进项表的「验证方式」一列；删掉其中任何一处，这份模板就退化成一份事后叙事（这三处与 [14-leadership/06-postmortem-culture §4.5 模板 1](../../14-leadership/06-postmortem-culture/06-postmortem-culture-section-4-sec4.md) 一致。本节是它的精简版：删去源模板的 摘要 / 影响 / 后续跟进 三段与改进项表的 Priority 列，并把时间盒收成头部一格；改进项表的 **Owner 与 Due Date 与源模板同位**，§4.2.3 只是另把这两条写成硬约束）。受影响面允许填量级、不填精确值。**判据**：改进项行里的「验证方式」若写成「已上线」「已培训」，这一行不算完成——§4.6 的关闭率只认能在事后被查一次的验证方式。

**模板 2：应急角色卡（四岗位各一张）**

```text
角色：{Incident Commander / 沟通 / 操作 / 领域专家}        # §4.2.2 的四个岗位
主责人：{具名}          备位（缺位时顶替）：{具名}
他能批什么：{回滚 / 降级 / 扩容 / 停机 / 只能建议}
他不能批什么、要跟谁对齐：{____}
他可以先不做的事：{写下来，他才不会在一个小时里什么都想管}
降级档位（停什么、保什么，由信号触发）：{档位表指向 §4.2.4 的口径}
上一任轮换日：{YYYY-MM-DD}      轮换周期：{按季度或半年【经验】}
```

**怎么用**：`备位` 一格是这张卡存在的理由——§4.5 的 game day 要故意让 IC 中途离场，看的正是这一格有没有人；备位长期由主责人兼任，说明 §4.5 第 ④ 类失效模式（应急角色缺位）没有被修。`他能批什么` 必须与 Step 2 的「分级 → 升级条件 → 谁有权批什么」对照表对得上，对不上就以对照表为准（两个口径并存时，现场会按更松的那个执行）。**不要把角色卡写成人员名单**：名单不回答「他能不能在没人同意的情况下跳级批一次回滚」。

**模板 3：game day 演练单（一次演练一张）**

```text
假设：{注入什么 / 让谁在什么时刻离场}，预期 {稳态判据} 不越界
稳态判据（演练前写死，过程中不得修改）：
  - {指标名}：越界条件 {____}　窗口 {____}　看板地址 {____}     # 阈值从你们的稳态看板抄，不现场估【经验】
  - {指标名}：……
中止条件：{哪个判据越界即停}　中止执行人：{具名}
观察项：{沟通链多久断掉、谁接手、分工是否照角色卡走}
结论：{通过 / 未通过 / 无效（未打到）}
后续：{每条：问题 → 动作 → 负责团队 → 进哪块看板}
```

**怎么用**：判据与中止条件在演练开始前填、过程中不得修改（改了就等于改裁判）；`结论` 允许写「**无效（未打到）**」——如实记下来比记成「通过」更有价值（字段形状与 [12-architecture/06 混沌工程 §4.5 模板 A](../../12-architecture/06-chaos-engineering/06-chaos-engineering-section-4-sec4.md) 的实验记录一致；本节删掉了与容器／实例绑定的那几格，因为这里演练的对象是**人**而不是节点——注入了什么不重要，重要的是**谁不在时流程还能不能启动**）。

**模板 4：复盘质量抽检单（每季度一页【经验：随复盘条数与抽检人手变】）**

```text
抽检样本：从本季度全部复盘里随机抽 {N} 份          # N 取什么量级【经验：按人手定，够当着团队逐条念完即可】
逐份填三格：
  - 时间线是否逐条标了「当时已知信息」：{是 / 否}
  - 改进项条数：{__}；其中三件齐（Owner + Due Date + 验证方式）的条数：{__}
  - 已关闭条数：{__}；其中「验证方式」在 90 天后仍能被查一次的：{__}     # 回看窗口取三个月 / 90 天【经验：与源模板 §4.5 的「90 天回看」一档一致】
两个汇总数：
  - owner 覆盖率 = 三件齐的条数 / 改进项总条数 = {__}%
  - 关闭率       = 能验证的已关闭条数 / 改进项总条数 = {__}%
抽检结论：{哪几类根因在反复出现 / 哪一处流程缺格}
```

**怎么用**：这两个数就是 §4.5 抽检方案要数的东西，也是 §4.6 的规模信号——**关闭率不随工具升级而上升，只随复盘纪律上升**，所以它连续两个季度（观察窗口【经验：随你们的抽检节奏变】）不动的正确结论是「复盘纪律没变」，不是「工具不够好」。owner 覆盖率明显低于记忆中的水平时，先查一件事：新写的这几份是谁写的（照模板写与凭习惯写，两组的覆盖率会明显不同）。抽检**不要由写这份复盘的人自己做**；这与「复盘不用于考核」不冲突——抽检的对象是**流程**（同类根因有没有重演、改进项有没有被跟），不是人。

### 4.3 FailOps 工具链

- **混沌工程**：Chaos Monkey / ChaosBlade / Gremlin。
- **监控**：Prometheus / Grafana / Datadog。
- **告警**：PagerDuty / OpsGenie。
- **应急沟通**：Zoom / 钉钉 / Slack。
- **复盘文档**：Confluence / Notion。
- **变更管理**：Spinnaker / Argo CD / Jenkins。

**逐类的选型判据与不选它的代价。** 上表只给了名字，名字本身不是判据——判据是先在自己的约束里找出最紧的那条（本章 §3.3 的决策表），再看哪一类正好顶住它：

| 类别 | 候选（上表） | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 混沌工程 | Chaos Monkey / ChaosBlade / Gremlin | 判据不是「哪个更强大」，而是**这次要验证的假设落在哪一层**，以及**中止通道与被注入对象是否共用依赖**（共用时，最需要中止的那一刻恰好中止不了）。逐候选的层级覆盖与判据见 [12-architecture/06 混沌工程 §4.3](../../12-architecture/06-chaos-engineering/06-chaos-engineering-section-4-sec4.md)；只验证「实例消失无感」一个假设时，随机终止一类就够 | 选了一个只覆盖容器与编排层的工具，于是每次演练都在验证同一个假设，而「依赖返回错误值」这类分支从未被验证过——实验记录很漂亮，实验矩阵里却始终缺那几格 |
| 监控 | Prometheus / Grafana / Datadog | 判据是**它能不能回答复盘时间线要的四个时间点**（发生 / 检测 / 缓解 / 恢复各有对应记录）与稳态判据；看板漂亮、图表多不构成判据 | 时间线里「检测」这一段取不到系统记录：TTD 长期空着，或者每次都被迫填同一个估出来的数——「这次检测慢不慢、有没有漏报」于是永远无法被验证，根因只能落在「当时没人看到」上，而这一条既不可证伪也改不动 |
| 告警 | PagerDuty / OpsGenie | 判据是**告警按人派单还是按组派单**，以及升级条件（多久没人接、升给谁）能不能配置——它决定 §4.2.5 的 Step 2 那条升级路径能不能被执行出来。值班人数少时排班表加固定群消息也够用【经验：随值班规模变】 | 按组派单的告警在群里「人人可见、无人认领」，检测时刻被值班群里的讨论时间吃掉。这一类代价不会以故障形式暴露，只以 TTR 变长暴露——所以它最容易被长期容忍 |
| 应急沟通 | Zoom / 钉钉 / Slack | 判据是**记录能不能留存、能不能被复盘检索**——复盘要取当时的沟通记录当事实，而不是取回忆 | 每次故障临时找地方开会：结论与分工没有留存，「谁在哪一刻说了什么」事后永远查不到，时间线只能靠参会者补齐 |
| 复盘文档 | Confluence / Notion | 判据是**模板能不能统一入库、能不能按失效模式而不是按故障名打标签**（标签口径见 [14-leadership/06-postmortem-culture §4](../../14-leadership/06-postmortem-culture/06-postmortem-culture-section-4-sec4.md) 的 Step 4） | 复盘散在各人空间里：同类故障重演时搜不到上一次的复盘，教训无法复用，§4.2.6 模板 4 的抽检也抽不出样本 |
| 变更管理 | Spinnaker / Argo CD / Jenkins | 判据是**能不能把发布与一组核心指标绑定、指标越界即自动回滚**（本章 §3.2.1 与 §5 已点名过这一族能力）；只有「发布有版本」而不带指标绑定，不构成这条判据 | 回退要靠人发现、人判断、人执行——一次变更的回退时长于是被测成**人的反应时间**，而它恰好在故障时刻最不可靠 |

**六类里最容易被误选的是「混沌工程」与「告警」。** 前者被误选，通常因为先挑了一个知名度高的平台、再去决定注入什么，于是演练矩阵永远缺那几格；后者被误选，通常因为「告警已经有很多条了」被当成「告警已经够了」，而判据从来不是条数，是**派单到人还是派单到组**。贯穿六类的通用判据只有 §4.4 那句：**工具买到的是「能注入故障」，买不到「注入后有人修」**——上表里只有「变更管理」与「告警」两类直接决定故障发生时的反应时长，其余四类决定的是读完故障之后能不能改进。

### 4.4 成本：这套东西的账单

FailOps 三项成本里，**硬件基本为零**；真正贵的是**演练占用的生产窗口**与**复盘的持续工时**。这一节把 §4.2 那些做法的账摊开。

- **人力（复盘与应急的固定账）**：§4.2.3 要求复盘在 1-2 周内完成、每条改进项有 owner 和 deadline。粗算一个量级：一次事故若牵动 5-8 个团队、复盘会议每次 1-2 小时、含材料准备折算 6-10 人·小时/团队，单次复盘约 **30-80 人·小时**，按每年 10-15 次重大事故估，年度复盘约 **300-1200 人·小时**【推算：5 团队 × 6 人·小时 × 10 次 = 300、8 团队 × 10 人·小时 × 15 次 = 1200 为区间两端；团队数、单团队工时、会议时长与事故频次均为【经验】量级，只取量级、不取精确值】。**这笔账不产出任何功能，因此最容易被砍**——这正是 §4.2.3 把「改进项必须有 owner 和 deadline」写成硬约束的原因。
- **演练的机会成本（本主题最贵的一项）**：§4.2.4 的预演 + 灰度 + 熔断 + 回退要占用生产窗口。混沌演练如果在业务高峰做，占用的就是**那份窗口的营收机会**；只在低峰做，又覆盖不到真实的峰值失效。这个取舍没有统一答案，量级上「每季度到每半年做一次全链路演练」是常见节奏【经验】。
- **工具（占比最小，却最容易被高估）**：§4.3 列的混沌平台（Chaos Monkey / ChaosBlade / Gremlin）、监控（Prometheus / Grafana / Datadog）、告警（PagerDuty / OpsGenie）按席位或按主机计费。**工具买到的是「能注入故障」，买不到「注入后有人修」**——§4.3 的工具清单里没有一项能替代 §4.2.3 的复盘闭环。
- **为什么贵在这里**：贵在**演练要用真实系统的可用性去换未来的确定性**——它和「多花算力换速度」的账不同，它的成本是**可用性**本身，且必须在系统还健康时主动支出。通用成本口径与单位换算见 [11-cross-cutting/03 数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)。

### 4.5 容灾与故障演练

本主题的对象就是**故障演练**本身，所以这一节不写「再建一个机房」，而是写**这套实践自己怎么失效、以及怎么演练它**。

- **失效模式 → 影响面**：①**复盘无行动项**——§4.2.3 的四个输出里前三个（时间线 / 根因 / 教训）齐、第四个（改进项）空，等于事故白发生；②**改进项无 owner / deadline**——§4.2.3 明写这是硬约束，破了的症状是「改进项从提出到现在既没关闭、也没人再提」；③**混沌无人修**——故障注入了、降级也看到了，但没有整改，下次照旧；④**应急角色缺位**——§4.2.2 的四个岗位（IC / 沟通 / 操作 / 领域专家）只挂在墙上，真出事靠临场分工。
- **降级策略**：**先止血再复盘**——§4.2.2 的检测 → 响应 → 缓解 → 恢复顺序里，缓解优先于恢复，复盘不阻塞止血。
- **演练方案（演练「演练」）**：**game day**——按 §4.2.4 的「预演」定期走完整应急流程，故意让扮演 IC 的人中途离场，看沟通链是否断裂；**复盘质量抽检**——随机抽 3 份历史复盘，数改进项的 owner 覆盖率与关闭率；**角色轮换**——让不同的人轮流当 IC，避免「只有一个人会开应急」。
- **恢复目标**：不给 RTO/RPO。本主题的「恢复」是**组织下次遇到同类事故时的反应时间**，量级是「从有人发现到有人开始处理」，随值班建制成熟度变【经验】。

> **不适用说明**：本主题是方法论而非运行系统，**跨地域容灾 / 多活切换对本主题不适用**——它没有可被切换的数据面，也就没有 RTO/RPO 可言；它的等价物是「应急流程在关键人缺位时仍能启动」，已写入上方的演练方案。通用容灾方法论见 [12-architecture/07 容灾与恢复](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)，混沌工程通用方法见 [12-architecture/06 混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)，本节不复述。

### 4.6 演进路线：0 → 1 → 100

FailOps 的三级台阶不是「买个平台」，而是**从一次复盘，到一个闭环，到一个可被验证的组织能力**。

- **0 → 1（成立复盘文化）**：最小可用是**一份 blameless 复盘模板 + 一次真做完的复盘**（§4.2.3 的四个输出齐全）。**先坏的是「怕担责」**——§2.3.3 的文化阻力：出问题推卸责任、不愿主动暴露问题；**变贵的是**承认失败那点信任成本。这一步的验收只看一件事：第一条改进项有没有 owner 和 deadline。
- **1 → 100（从复盘到主动防御）**：装上 §4.2.4 的预演 / 灰度 / 熔断 / 回退，并引入混沌平台（§4.3）与应急角色分工（§4.2.2）。**先坏的是**「混沌注入无人修」——技术到位、闭环未到位；**变贵的是**演练占用的生产窗口（§4.4）。规模信号是改进项的**关闭率**：它不随工具升级而上升，只随复盘纪律上升。
- **100 →（跨组织）**：故障一旦跨越组织边界（供应商、外包、多云组件），**先坏的是责任归属**——§4.2.2 的 IC 无权指挥外部团队；**变贵的是**把一次事故的时间线拼全所需的对齐成本。这一步的判据从「我们复盘了吗」变成「复盘能不能拼出端到端的时间线」。

### 4.7 小结

| 你的约束 / 处境 | 建议做法 | 关键理由（机制层面） |
| --- | --- | --- |
| 系统可能出你没预想到的失效 | 混沌工程：主动注入故障（4.2.1） | 趁系统还健康，用真实系统验证容灾切换、熔断与限流，而不是等故障发生 |
| 故障已经发生 | 应急响应：检测→响应→缓解→恢复→复盘 + IC / 沟通 / 操作 / 领域专家四岗位（4.2.2） | 缓解优先于恢复；角色事先固定，才不会真出事时靠临场分工 |
| 一次事故刚结束 | blameless 复盘：1-2 周内、时间线 / 根因 / 教训 / 改进项齐全，改进项有 owner 和 deadline（4.2.3） | 无指责才能暴露真根因；改进项绑上 owner 与 deadline，才不会被排期挤掉 |
| 想少出事故 | 主动防御：预演 / 灰度发布 / 熔断 + 降级 / 回退机制（4.2.4） | 让「退让」成为事前可执行的档位，而不是现场救火 |
| 要选工具 | 按能力域配：混沌 / 监控 / 告警 / 应急沟通 / 复盘文档 / 变更管理（4.3） | 工具买到的是「能注入故障」，买不到「注入后有人修」 |
| 要摊开这套东西的账 | 硬件≈0；成本花在演练占用的生产窗口与复盘的持续工时（4.4） | 真正贵的是拿系统的可用性去换未来的确定性，且必须在系统还健康时主动支出 |
| 想演练「演练」本身 | game day（故意让 IC 离场）/ 复盘质量抽检 / 角色轮换（4.5） | 检验的是「关键人缺位时流程还能不能启动」，而非 RTO/RPO |
| 从 0 起步 | 一份 blameless 模板 + 一次真做完的复盘（4.6） | 验收只看一件事：第一条改进项有没有 owner 和 deadline |
| 想上规模 | 装预演 / 灰度 / 熔断 / 回退，并引入混沌平台与应急角色分工（4.6） | 规模信号是改进项的关闭率——它只随复盘纪律上升，不随工具升级上升 |

> 本节小结：整节反复落在同一处——**工具能注入故障，闭环才能收敛失败**。§4.2.3 把「改进项必须有 owner 和 deadline」写成硬约束，§4.6 的规模信号是改进项的关闭率（只随复盘纪律上升，不随工具升级上升），§4.4 也点明混沌 / 监控 / 告警这些工具都买不到「注入后有人修」。FailOps 的成本贵在它占用的生产窗口与复盘工时（§4.4），而它最容易被砍，正因为这笔账不产出任何功能。

### 4.8 自检清单

- [ ] 翻一份近期事故的复盘记录：§4.2.3 的四个输出（时间线 / 根因 / 教训 / 改进项）齐不齐？最常空着的是不是「改进项」那一栏？
- [ ] 把那份改进项清单摊开，逐条看有没有 **owner 与 deadline**——这是 §4.2.3 明写的硬约束；有没有哪一条从提出到现在既没关闭、也没人再提？
- [ ] 数一数最近几次复盘各自用了多久——都在 §4.2.3 要求的 1–2 周内完成了吗？超期的那几次，是「没有具体改进项」还是「被排期挤掉」？
- [ ] §4.2.2 的四个应急岗位（IC / 沟通 / 操作 / 领域专家）落到具体人名了吗，还是只挂在墙上？上一次真出事时，分工是照清单走还是临场分的？
- [ ] §4.2.4 的熔断 + 降级与回退机制，有没有一份能当场翻出来的回退方案？最近一次变更是灰度发布的吗？
- [ ] 最近一次混沌演练是在业务高峰还是低峰做的（§4.4 指出只在低峰做会覆盖不到真实的峰值失效）？注入的故障覆盖到 §4.2.1 的哪几项（容灾切换 / 熔断 / 限流）？
- [ ] §4.5 的 game day 做过吗——按演练方案让扮演 IC 的人中途离场，看沟通链断了没有？
- [ ] §4.4 那笔账：一次复盘折算的 **30–80 人·小时**（以及它不产出任何功能这一点），进你团队的排期了吗——还是正因为「不产出功能」而最先被砍？

> 💡 **思考锚点**：列一下你团队近期几次复盘——它们是否都在 1–2 周内完成，且每条改进项都有具体的 owner 与 deadline？数一数有多少条改进项从提出到现在既没关闭、也没人再提——按 §4.2.3「改进项必须有 owner 和 deadline」这条约束，缺 owner 的那几条当初是怎么被放行的？
