## 4. 关键决策

[§ 3](04-meituan-feature-store-section-3-sec3.md) 回答的是「哪条约束逼出哪一层结构」——结论是「同一份特征定义要在几个地方被算几遍、以及你愿不愿意为算两遍付一致性成本」。本节回答下一个问题：**这四层是分几步装进一个「多个业务团队各自自建特征、且此前没有任何地方登记过」的组织里的**：顺序、判据、产物、存量特征怎么并进来、以及装到什么程度算装完。

> **证据档位**：本节【公开】给出来源类型与年份，【推算】写出推导链，**规模与 SLA 一类的数字一律按【经验】使用——只取量级、不取精确值**。核对路径分三类，按数去找：**特征数取「十万级」量级**（主文件 §2.2.1）、**业务方取「百级」量级**（本章 §3 的「当前状态」段）、**延迟取秒级档**（主文件 §2.1.2）；**可用性与覆盖率两项只在本节按「几个 9」「接近全覆盖」的档次出现**——它们的原始口径来自本案例对特征平台 SLA 的三档记录（延迟 / 可用性 / 准确性），本节不给精确值，需要引用精确值时请以美团官方发布或你所在平台的实测口径为准。本节用到的每一处数字都在原处标了档位与推导链。

本节对两类读者的入口不同。**已经在生产上跑特征的人**（已有离线特征表、已有在线 KV、已有一批模型）从 4.1 的 Step 1 顺着走，4.4 是重点——存量迁移在这一主题上比新建更难，因为要处理的不是空目录，而是一批已经被人依赖、但**没有任何地方登记过**的特征。**从零搭的人**先读 4.3 的选型判据，再回到 4.1：从零开始最容易犯的错不是顺序反了，是先建在线 KV 再补注册——**注册中心是所有其他能力的落点，它缺席时，一致性、血缘、治理三件事各缺一半**。

### 4.1 落地步骤

先给一张总览。五步的顺序是依赖关系，不是时间表。

| 步骤 | 手上多出来的东西 | 判据（低于这个标准就是没做） | 省掉它 / 换序后，返工会落在哪 |
| --- | --- | --- | --- |
| Step 1 特征注册与统一 Schema | 特征注册中心 + 每个特征的唯一权威定义 | 「同一个语义一共有几个实现」能按数据回答 | 后面每一步都缺落点，口径继续靠约定 |
| Step 2 双栈存储与统一服务 | 离线表 + 在线 KV + 统一取值入口 | 训练与推理取的是不是同一份定义 | 两侧各写一份实现，偏差无法发现 |
| Step 3 实时特征分档 | 四类实时特征各自的链路与 SLA | 每类特征能不能说出自己的时效档次 | 用一个时效承诺覆盖所有特征，成本虚高 |
| Step 4 回填与时间点正确性 | 生效区间 / 快照 + 回填作业 | 同一训练集能否两次算出同一分布 | 离线指标虚高、实验不可复现 |
| Step 5 血缘与质量监控 | 字段级血缘图 + 四类监控指标 + 上线门禁 | 上游改字段能否反查出受影响的特征与模型 | 治理动作没有依据，清理只能凭感觉 |

**Step 1：把特征从「代码」变成「注册条目」（典型工期：6–12 周【经验：随存量特征数、审核链长度、以及这一步是否只覆盖增量而变化】）**

- **做什么**：建特征注册中心，所有特征**先注册后使用**；每个条目给一份统一特征 Schema——特征名 + 特征类型 + 特征计算逻辑 + Owner + 版本；**特征版本管理**支持 v1 / v2 / v3 多版本并存并允许平滑过渡（旧版本在服务中不立刻下线，先让消费方切走）。注册的落点是那份可执行的**特征计算逻辑**，不是一段描述。
- **产物**：特征注册中心 + 每个特征的唯一权威定义 + Owner 到人的字段；以及一份「线上在跑但注册中心查不到」的对照清单。
- **判据**：抽 3 个特征，问「这个语义一共有几个实现」——答案应当是查询结果，不是「我去群里问一下」；再抽 1 个特征，看它的 Owner 是人名还是团队名。
- **为什么必须这一步、为什么在最前**：因为后面每一项能力都要挂在一个条目上——一致性要靠「同一份定义」这个落点，血缘要靠「特征 ← 哪些字段」这个主语，治理要靠「这个特征还有没有人在用」这个主键。**因为注册条目是时点快照、而特征在持续演进，所以登记的价值完全取决于它是自动生成还是人工填的；代价是注册会挡在特征上线的路径上，如果审核比业务自建还慢，团队就会绕过它**（§3.2.3 与 §3.5 的同一结论）。

**Step 2：双栈存储与统一取值入口（典型工期：1–2 个季度【经验：随在线服务是否已有、在线存储是采购还是自研、以及要接入的消费方数量而变化】）**

- **做什么**：把特征生产分成三条路径——离线（Hive / Spark SQL 跑批）、实时（Kafka → Flink 流处理）、请求服务（按原始数据按需现算，例如实时查询用户当前 LBS）；存储分成三层——离线存储（Iceberg / Hive 表）、在线存储（Redis + 自研 KV）、向量存储（Milvus / Faiss 一类，用于 embedding 检索）；消费侧统一成三种形态——训练消费（从离线表批量拼样本）、在线消费（从在线 KV 点查）、回填消费（离线 + 在线混合读取）。**一份定义驱动两条执行路径**，任何一侧的取值都从注册条目出发。
- **产物**：离线特征表 + 在线 KV + 一个统一的特征读取接口（RPC 或 SDK）+ 三类消费的接入文档。
- **判据**：抽 3 个有在线推理的模型，问它的训练特征与推理特征是不是来自注册条目里的同一份定义；再问「最近一次离线与在线特征值的逐条比对，差异率是多少」——答不出来等于没有验证过「一致」。
- **为什么必须这一步、为什么在 Step 1 之后**：批与点查对存储的要求相反（一个要吞吐与列存，一个要毫秒点查），没有任何单一存储能同时满足，所以双栈不是选择而是结构；而双栈的代价是**同一份定义会被两个引擎执行成两种语义**（窗口开闭、时区、事件时间与处理时间、NULL 与除零、浮点聚合顺序）。**因为一致的是文本、不是执行结果，所以两侧必须有一次独立于定义的比对，否则偏差只能等业务指标暴露。**

**Step 3：实时特征按访问模式分档（典型工期：4–8 周【经验：随要分的类数、以及流计算与在线存储是否已有而变化】）**

- **做什么**：把实时特征分成四类分别实现——行为实时特征（用户最近点击 / 加购 / 下单，走 Kafka → Flink）、画像实时特征（用户当前位置、商户当前出餐速度，走 RPC + Redis）、场景实时特征（当前时段、天气、热点，走规则 + 实时计算）、设备实时特征（设备电量、网络状态，走客户端 SDK）；链路为「用户行为 → Kafka → Flink → Redis / 自研 KV → 在线服务」；三类技术各司其职：Flink State 维护「用户最近行为窗口」，Redis Sorted Set 存时间窗口内的行为序列，自研 KV 存用户画像的实时特征；SLA 分三档写——延迟按秒级、可用性按几个 9、准确性按覆盖率的百分位【经验：三项都只取量级、不给精确值，具体档位随特征类别、业务容忍度与链路位置变化】。
- **产物**：四类实时特征各自的链路 + 三档 SLA 的书面承诺 + 每类特征的时效档次说明。
- **判据**：抽 3 个实时特征，看它能不能说出自己属于哪一类、依赖哪一类存储；再检查 SLA 是否是按类写的——如果所有特征共用同一个延迟承诺，说明档位没有真正分开。
- **为什么必须这一步**：因为**四类特征的成本模型完全不同**——设备侧特征的成本落在客户端，场景侧可以按规则算，行为侧要为每个键维护可恢复的状态，画像侧要接受 RPC 的往返。**用一个时效目标覆盖全部特征，会让便宜的特征为贵的特征付成本；代价是分了档就要维护四套链路、四套监控与四套兜底。**

**Step 4：回填与时间点正确性（典型工期：4–10 周【经验：随需要回溯的历史深度、上游表是否被重刷过、以及快照是否要从零开始留存而变化】）**

- **做什么**：为训练数据准备、A/B 实验后评估、离线模型调试三类场景提供回填；架构是「历史 DWD 表 → Spark / Hive → 特征计算 SQL → 回填特征表」；所有特征计算 SQL 化（离线与在线复用同一份定义）、支持任意时间窗口、回填作业挂在 Dolphin 调度（基于 Airflow 改造的调度系统）上；样本拼装按特征值的生效区间做时间点对齐，而不是按最新值。
- **产物**：一套按时间点拼样本的作业 + 特征值生效区间（或快照）+ 回填作业的重跑入口与记录。
- **判据**：挑一个历史日期，用当时的线上日志核对回填出来的特征值——对不上的比例就是回填可信度的下界；再检查一句断言：**训练样本的时间戳下界不得早于所引用特征值的生效上界**（违反即泄漏未来）。
- **为什么必须这一步、为什么在 Step 3 之后**：因为回填的价值取决于「当时的值」能不能被还原，而这要求在线侧已经在持续产出可留存的值；先做回填而没有在线链路，回填只能用今天的上游数据重算昨天——**因为上游被修正过，所以同一个训练集重跑两次会得到不同分布；这类失效不报错，只让实验不可复现。**

**Step 5：血缘与质量监控（把治理动作变成查询结果）（典型工期：1–2 个季度【经验：随 SQL 方言数与动态 SQL、脚本任务的占比而变化——解析器接不进来的场景越多，人工补录的工作量越大】）**

- **做什么**：血缘按五个层次串起来——源表层（MySQL / Kafka / OSS）→ DWD 层（清洗后的明细）→ 特征计算层（基于 DWD 算特征）→ 特征注册层 → 模型应用层；采集方式以**自动解析特征计算 SQL** 为主，人工只补解析器看不懂的场景；血缘存进图数据库（GDB / Neo4j 一类）以便做路径查询，对外提供可视化展示；应用分三件——影响分析（上游表变更影响哪些特征与模型）、溯源分析（模型效果下降时回溯到特征与上游）、数据治理（发现重复特征与孤儿特征）。监控按四个维度铺开——延迟（P50 / P99 / P999）、覆盖率、分布（漂移检测）、离线与在线一致性；漂移检测用 KS 检验与 PSI（Population Stability Index）一类方法，超阈值自动告警。所有监控结论接入上线门禁。
- **产物**：字段级血缘图 + 四类监控指标 + 漂移告警规则 + 一份上线门禁清单。
- **判据**：抽 1 个上游字段，看能不能反查出引用它的全部特征与模型；再抽 1 个特征，看它的延迟 P99 与覆盖率有没有数——**没有数当没有监控**。最后看门禁：最近一次特征上线，是不是因为门禁被拦过一次。
- **为什么必须这一步、为什么在最后**：因为影响分析、溯源与治理三件事都要求血缘先存在，而血缘的精度决定它们有没有用（表级血缘只能说「影响某张表」，字段级才能说「影响这个特征以及下游引用它的模型」）。**因为人工登记的血缘只在登记那一刻正确，所以它随变更累积而单调失效；代价是把血缘接进上线门禁，短期会挡住一部分交付速度**——门禁一旦比业务自建更慢，绕过就会发生（§3.5）。

**最常被跳过的是 Step 4 的生效区间与 Step 5 的监控。** 前者的症状要等一次「同一个实验跑不出同一个结果」才暴露，后者的症状要等一次模型效果断崖式下降、而没有人能说出是哪一批特征变了。这两步都没有交付压力，因此在排期上永远排在「先把在线链路跑通」之后——**而它们的替代方案是：出了问题之后，靠人力回查历史日志。**

### 4.2 关键技术点

**特征注册与统一 Schema**

- **做法**：每个特征一个注册条目（特征名 + 实体 + 类型 + 计算逻辑 + Owner + 版本 + 状态），上线前必须登记；多版本并存，旧版本在消费方切走后按生命周期下线。
- **机制**：因为注册条目是唯一落点，重复特征与同义特征第一次可被枚举——「同一语义有几个实现」变成查询结果；因为条目里带 Owner，「这个特征归谁」从社交知识变成可查属性。
- **失效条件**：**当注册变成「发布前填一张表」的行政动作、且血缘不自动解析时，这条会反转成「注册中心里的特征是过期的」**。症状：面板上覆盖率是满值，而线上存在「注册中心查不到、但正在跑」的特征；同一特征名有多个版本并存，没人说得清线上在用哪个。
- **档位**：可持续管理的特征数上限取决于血缘自动化率，而不是特征总数【推算：可持续管理量 ≈ 平台维护人能核对的特征数 × 人数 ÷ 人工介入比例；因为人工核对工作量随特征数线性增长、平台人力通常不增长】。

**双栈：一份定义、两条执行路径**

- **做法**：定义只写一份（SQL 或等价声明式），由离线批路径与在线流路径分别执行；训练走离线表，推理走在线 KV；两侧各留一份可比对的落点。
- **机制**：因为训练与推理都从同一处取特征（同一份定义、同一套注册），「两边取的根本不是同一个东西」这类错误被结构性消除；因为在线侧只做点查、特征在请求到来前已算好，延迟才能压到毫秒级。
- **失效条件**：**当两个引擎对同一段定义的语义差异恰好落在某个特征上时，「同一份定义保证一致」会反转成训练-推理偏差（Train-Serving Skew）**。症状：离线评估漂亮、上线效果打折；逐条比对时两边值对不上，而团队的第一反应是「以离线为准」。
- **档位**：偏差幅度不引用具体数值；本案例材料记录的形态是「存在显著落差」【经验：只取「存在可观测偏差」这一量级】。

**特征计算 SQL 化与时间窗口**

- **做法**：所有特征用 SQL（或等价声明式）定义，离线与在线复用同一份；计算支持任意时间窗口，窗口边界（开闭区间、时区、事件时间口径）写进定义而不是散落在代码里。
- **机制**：因为定义是文本且只有一份，变更只需改一处；因为窗口是定义的一部分，两侧执行时不需要各自解释「最近 7 天」是什么意思——这正是双栈偏差最常见的来源。
- **失效条件**：**当窗口从日级缩到分钟级、且上游存在晚到数据时，这条会反转成「同一份定义算出两个值」**。症状：两侧统计值对不上，且对不上的比例与晚到数据量同向变化。
- **档位**：窗口档位（天 / 小时 / 分钟）按业务允许的误差选，不给统一阈值【经验】。

**时间点正确性：生效区间或快照**

- **做法**：特征值记录生效区间（valid_from / valid_to）或按快照留存；样本拼装按事件时间落在生效区间内的值做连接；回填记录所依据的上游版本。
- **机制**：因为样本只能看到「事件发生时已知」的值，未来信息无法泄漏；因为历史值被留存，训练集可复现。**代价是快照与生效区间的存储随「实体数 × 特征数 × 版本变更次数」增长，且必须长期保留。**
- **失效条件**：**当上游明细表被重刷（数据修正、口径修复、上游回补）时，「可复现的训练数据」会反转成「同一份实验跑不出同一个结果」**。症状：同一训练集重跑两次得到不同分布；某次实验「效果变好了」而没人说得清原因。
- **档位**：保留期按「训练样本需要回溯多久」定【经验：随模型重训周期变化，不是常数】。

**三类实时特征存储：Flink State / Redis Sorted Set / 自研 KV**

- **做法**：行为类特征在 Flink 里用状态维护窗口（重启可从 Checkpoint 恢复），在 Redis 里用 Sorted Set 存带时间戳的行为序列以便按窗口切片，画像类特征写入自研 KV 供 RPC 点查。
- **机制**：因为三类数据的时间语义与访问模式不同（状态是「算子内部的中间结果」、Sorted Set 是「可按分数范围取的时间序列」、KV 是「按实体键取的最新画像」），各用各的结构，才能既保住恢复能力又保住点查延迟。
- **失效条件**：**当窗口类型与存储结构错配时，这条会反转成「能跑但不准」**。症状：把需要按期切片的行为序列塞进只存最新值的 KV，结果是一部分特征永远只反映最后一次行为；或用 Flink 状态替代可查询的存储，导致排障时看不到任何中间值。
- **档位**：延迟按秒级档、可用性按几个 9 档、覆盖率按「接近全覆盖」档【经验：三项都只取档次、不给精确值；同一平台内不同特征类别的承诺口径也不同，引用精确值请以平台对外公布的 SLA 为准】。

**血缘：自动解析 + 字段级 + 图存储**

- **做法**：从特征计算 SQL 自动解析「特征 ← 源表字段 ← 变换」；血缘存进图数据库（GDB / Neo4j 一类）以支持路径查询；对外给可视化界面；人工只补动态 SQL 与脚本任务，且标出未解析场景。**采集只做一次，供影响分析、溯源与治理三处共用。**
- **机制**：因为血缘是从生产事实里提取的，它不依赖额外填写、也就不会过期；因为粒度到字段，上游改一个字段时能反查出受影响的特征与模型。**代价是解析器要覆盖多种方言，接不进来的场景会成为静默盲区**——盲区不可怕，「不知道有盲区」才可怕。
- **失效条件**：**当动态 SQL、拼接表名、脚本作业的占比上升时，血缘会从「完整」退化到「看起来完整」**。症状：某次上游变更后出现没被预警的特征故障，回查才发现那条链路从未上图。
- **档位**：血缘自动化率是可持续治理的分界线，但不给统一阈值【经验：阈值随平台人力、上游变更频率与 SQL 方言数三者同向变化——自动解析覆盖率越高，可维护的特征规模越大；人工补录只有在有固定责任人时才有稳定率】，一条可以自检的结构关系是：可维护的登记正确率 ≈ 自动解析覆盖率 + 人工补录的稳定率。当人工补录没有责任人时，登记正确率的衰减周期是「一次上游变更到下一次有人核对」这段间隔（区间从数周到一两个季度，随该上游的变更频率变化），它不是一个可以按季度预算的常数。

**质量监控：延迟 / 覆盖率 / 分布 / 一致性**

- **做法**：延迟按 P50 / P99 / P999 分别监控（生产延迟与「可用的最晚时间」之差）；覆盖率 = 应该有的样本中实际有值的比例；分布用 KS 检验与 PSI 一类方法做漂移检测，超阈值自动告警；一致性靠离线值与在线值的逐日比对。四类都设阈值，超阈值进上线门禁或告警。
- **机制**：因为特征质量问题在训练之前就能被发现，而不是等模型上线效果不对再回溯；因为漂移监控盯的是「值分布」而不是「任务成功」，任务全绿而分布已经漂移这件事才可能被看见。
- **失效条件**：**当阈值定得过松或无人认领时，监控会反转成告警噪声，进而被整体静音**。症状：告警列表长期有项但没人处理；或「一致性」这项只有系统字段、没有比对作业在跑。
- **档位**：四类指标的阈值按「本业务能接受多大误差」定，不给统一数值【经验】。

**跨业务实体与特征复用：OneID 协同、推荐协同、广告协同**

- **做法**：跨业务特征以统一实体（OneID，同一手机号 / 设备 ID 在外卖、到店、酒店等业务统一识别）为连接键，「用户在外卖 + 到店的综合画像」这类特征才拼得出来；推荐侧让外卖推荐、酒店推荐、电影推荐共享「用户基础特征」；广告侧分别拼 CTR 预估特征（用户历史点击 + 商户特征 + 广告特征）与 CVR 预估特征（用户历史转化 + 商户特征 + 商品特征）。
- **机制**：因为特征挂在实体上、实体被统一，同一份基础特征才能被多个业务复用；因为 CTR 与 CVR 的特征组成不同，「一套特征喂所有模型」在结构上就走不通——**共享的是挂在实体上的基础特征，不是每个模型的全量输入**。
- **失效条件**：**当统一实体本身出错、或被上游重算时，这条会从「特征可复用」反转成「一处错、全线错」**。症状：某段时间多个业务的模型同时出现同类偏差，而各自的特征定义都没有改过——问题不在特征层，在实体映射层。
- **档位**：实体对齐受个人信息合规约束，可关联的标识类型随法域变化【经验：本案例材料未给比例，本节不给数值】。

**配送链路的实时计算：CEP + GIS + 路径规划**

- **做法**：配送链路的起点是一条时效承诺——从下单到送达必须在半小时这一档时效窗口内完成【经验：窗口随城市、品类与时段变化】，因此系统要实时决定「哪个骑手送哪个订单」（实时调度）、实时预估骑手到达时间（ETA 预估）并规划路线（路径规划）；链路为「订单事件 → Kafka → Flink → 实时特征 → 调度模型 → 骑手 App」；用 Flink CEP 做复杂事件处理（识别骑手拥堵、商户积压这类异常形态）；GIS 实时计算基于 Redis Geo 与自研算法计算骑手 — 商户 — 用户三方距离；路径规划在 A*、Dijkstra 一类算法上叠加实时路况。特征分四组：骑手（当前位置、当前订单数、电量、熟悉度）、商户（当前出餐速度、订单积压）、用户（地址准确度、历史投诉）、环境（天气、时段、路况）。
- **机制**：因为配送的决策点在下单后极短的时间内，特征必须在决策前就算好（不能等请求到来再查库）；因为三方位置关系是每一单都在变的量，地理计算必须走内存索引而不是关系表 join。**代价是这条链路与推荐链路共用同一套实时设施时，会与推荐的特征新鲜度需求争资源。**
- **失效条件**：**当 CEP 规则数量随运营策略增长时，这条会从「识别异常」退化成「规则互相覆盖」**。症状：同一事件命中多条规则、动作互相抵消；或规则发布后无人回收，半年后没人能解释某条规则为什么存在。
- **档位**：端到端延迟按秒级档；配送时效按平台对外承诺的分钟级量级使用，两项都只取量级、不锁定具体值【经验：端到端延迟随链路长度与上游数据量变化；时效承诺随城市、品类与时段变化】。

### 4.3 工具链与平台

不列「推荐组合」，列判据——在你的约束下每一类怎么重新推一遍。

先给这一整层在 ML 平台里的位置，因为这决定了下面每一类的边界：本案例把特征这一层统称 **Feature Store（特征平台）**，它是 ML 平台链路上的一段——数据集成（DataFinder）→ 特征平台（Feature Store）→ 模型训练（Spark / TensorFlow / PyTorch 一类框架）→ 模型部署（PAI / 自研）→ 在线推理（PAI / TF Serving 一类模型服务）。**每一类的选型判据只有当它落在这一段上时才成立**：特征平台不负责训练框架的选型，只负责「同一份定义在训练与推理两侧取到同一件事」。部署这一环的候选形态是「平台内置（PAI）或自研（Custom）」。这一层为什么要有人对每个特征负责、为什么要过上线门禁，机制见 [§ 3](04-meituan-feature-store-section-3-sec3.md) §3.2.3 与 §3.5；4.1 的 Step 1 与 Step 5 就是把那两条结论落成动作。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 离线特征计算 | Hive / Spark SQL / 开放表格式（Iceberg 一类） | 特征表需不需要与数仓共用同一份存储与权限；上游表会不会被重刷 | 特征表成为数仓之外的一套平行资产，权限与口径各维护一次 |
| 在线存储 | Redis / 自研 KV | 特征是不是按实体键点查；单次请求要取多少个特征；容量按「实体数 × 特征数 × 版本数」估算后在哪一档 | 用通用缓存承担画像级容量：热点与容量同时成为瓶颈，且 TTL 策略难按特征区分 |
| 向量存储 | Milvus / Faiss 一类 | 特征是 embedding、且需要在请求路径上做近似近邻检索时才引入 | 用在线 KV 存向量：点查语义与近似检索对索引的要求相反，两边都慢 |
| 流计算与消息 | Flink / Kafka | 需要事件时间语义、需要为每个键维护可恢复状态；消息要能被多个消费方各按进度读取 | 状态恢复靠重跑全量；多个消费方共用一条队列时，取数与特征计算互相偷消息 |
| 调度 | Dolphin（本案例；基于 Airflow 改造）/ 通用工作流调度 | 回填与重跑要不要按时间范围批量发起；依赖要不要声明成上游数据集的产出而不只是任务成功 | 回填靠手工起任务，历史样本的生成速度成为瓶颈，且容易漏跑 |
| 血缘存储与展示 | 图数据库（GDB / Neo4j 一类）/ 关系表 | 是否需要「沿链路递归」的查询（影响面、溯源）——需要就用图；只需「谁直接引用谁」，关系表够用 | 用关系表做递归查询：每一跳都要应用层拼，深度一上来就没法在界面里实时回答 |
| ML 平台模块 | 数据集成：DataFinder（美团版 DataX）；训练与部署：PAI；模型序列化与跨框架运行时：MLeap（选它承担实验管理或模型版本目录之前，先按该产品官方文档的序列化 / 运行时章节核对它是否覆盖这两件事）；实验分流：AB 平台；在线服务：Serving | 这一层不是选出来的而是装配出来的：先看缺哪一段——数据进不来、训练跑不动、实验与模型版本说不清、分流做不了、还是推理服务不稳 | 缺一段就用人工补：人工补的那一段不会留下记录，于是「这个模型用了什么数据」永远答不全 |
| 在线推理 | PAI / TF Serving 一类模型服务框架 | 模型框架是自研还是标准格式；要不要与特征取值在同一跳网络内完成 | 服务框架与特征服务之间多一跳，延迟预算被吃掉一截，且故障点变多 |
| 设备侧采集 | 客户端 SDK | 特征必须在客户端算（网络状态、电量一类）时才引入 | 把只能在端上取的特征搬到服务端，只能拿到近似值或用上报延迟换 |

**这一类里最容易被误选的是在线存储与向量存储这一对。** 两者看起来都是「按 key 取值的 KV」，但**点查与近似近邻检索对索引的要求是相反的**：一个要 O(1) 命中，一个要能接受扫描与近似。用一套存储通吃，短期运维面最小，代价要到 embedding 进入在线链路时才暴露——**症状是向量模型换代时在线点查的 P99 出现同向尖峰**（§3.2.5 与 §3.4 的组合三给的是同一结论）。第二容易被误选的是调度：只看「能不能定时跑」，而不看「回填能不能按范围发起」——后者决定你的训练样本生成速度，是实验迭代速度的上限。

### 4.4 存量迁移

存量迁移在这个主题上比新建难：要处理的不是空目录，而是一批已经被人依赖、但**没有任何地方登记过**的特征。目标不是「都迁到平台」，而是**让平台外的新增停止、让存量被枚举**。四件事按顺序做。

**① 先做一件立刻见效、且完全可回退的事：把偏差量出来。** 对已有的高频模型，抽一批实体做**离线值与在线值的逐条比对**，报出一个差异率，并按特征列出差异集中的位置。这件事不需要改动任何生产链路（只需读两侧），因此可回退；它立刻产生一个可讨论的数——**在差异率被报出来之前，「训练-推理是否一致」是观点；报出来之后，它是待办清单。** 判据：差异率能按特征拆开；拆不开说明比对作业没有对齐实体与时间点。

**② 存量特征分三类处理**，不要一刀切：
- **迁**：有在线消费、被多个模型引用、或口径容易产生争议的特征。动作是补登记 + 把计算逻辑收敛成 SQL + 接上线门禁。判据：这个特征被几个模型引用、有没有在线侧。
- **留但封口**：稳定、单一业务使用、逻辑简单的特征。不强行迁到统一实现，但**禁止再新增平台外的特征**，并把已有的平台外实现登记成「影子特征清单」。封口比返工便宜。
- **冻结退役**：无人引用（没有下游模型）的特征。走生命周期流程，先告警后下线——**下线必须有机制强制，因为新增特征有受益人、下线特征没有**（§3.5 的「特征沼泽 / 僵尸特征」）。

**③ 双轨怎么维持、维持多久。** 双轨在这里有两个并存项：**注册中心与平台外实现并存**、**旧定义与新定义并存**。维持时长不用日历时间定，用事件定：直到「连续 N 次特征上线都走了注册与门禁通道」为止【经验：N 取到能覆盖一次完整模型迭代周期的量级，随你的模型上线频率变化】。双轨期间必须有两张在跑的看板——**影子特征占比**与**离线 / 在线一致性差异率**；两张都没有，双轨会从过渡态变成长期态。

**④ 什么信号说明可以退出双轨**：三个同时满足——平台外新增特征停止增长、注册中心里「查不到但线上在跑」的对照清单归零、以及差异率的变化能被逐项解释（哪一项是已知的引擎语义差、哪一项已修）。第三条比前两条重要：**差异率不下降并不一定是坏事，不可解释才是**。

**两项近乎不可逆的事，要在动手前想清楚**：一是**注册条目的粒度一旦定成「每个团队一份」，后续再拆到「每个特征一份」需要逐条重登记**，成本与特征数成正比；二是**在线特征值一旦不保留生效区间，历史样本就永久失去可复现性**——后面的训练样本只能重建，不能还原。因此迁移的方向是**先把登记粒度与生效区间这两个最小结构定死，再谈平台覆盖面**；反过来做，会把两件事的难度叠加。

### 4.5 模板 / 示例

**模板 1：特征注册条目（最小字段集）**

```sql
-- 每个特征一行；注册条目本身就是"唯一权威定义"的落点
-- 各字段类型请按你自己的注册中心实际 schema 调整
feature_name    TEXT NOT NULL,      -- 如 user_ctr_7d
entity          TEXT NOT NULL,      -- 特征挂在谁身上：user / shop / rider / item
version         INT  NOT NULL,
dtype           TEXT NOT NULL,      -- scalar / array / embedding
definition_sql  TEXT NOT NULL,      -- 定义只写这一份，离线与在线共用
offline_table   TEXT NOT NULL,      -- 离线物化表（由 definition_sql 产出）
online_store    TEXT,               -- 在线存储与 TTL；不需要在线的可为空
owner           TEXT NOT NULL,      -- 具体到人，不是团队
status          TEXT NOT NULL,      -- 草稿 / 已上线 / 已下线
PRIMARY KEY (feature_name, version);
```

**怎么用**：填的是 `definition_sql`、`owner`、`online_store` 三格——**不要照抄的是 `offline_table` 的命名**，它应当由你的分层规范决定。`status` 这一格必须真的被流程使用（没有「已下线」状态的注册中心，等于没有生命周期管理）。

**模板 2：按时间点拼训练样本（point-in-time）**

```sql
-- 样本只允许看到"事件发生当时已生效"的特征值
SELECT s.entity_id, s.event_time, s.label, f.feature_value
FROM   training_sample s
JOIN   feature_snapshot f
  ON   f.entity_id     = s.entity_id
 AND   f.feature_name  = 'user_ctr_7d'
 AND   s.event_time   >= f.valid_from
 AND   s.event_time   <  COALESCE(f.valid_to, TIMESTAMPTZ 'infinity');
-- 断言（写进数据质量检查，不要只写在文档里）：
--   训练样本时间戳下界 ≥ 所引用特征值的生效上界
```

**怎么用**：把特征名与生效区间字段换成你自己的；**不要照抄的是「两条样本表直接 join」这个形态**——特征与样本的实体粒度不一致时（例如用户级特征拼到订单级样本上），必须先做粒度对齐。`COALESCE(..., 'infinity')` 这一句的作用是让"当前仍生效"的值有明确的结束语义，缺了它，最后一批样本会被静默丢掉。

**模板 3：离线 / 在线一致性比对（迁移期必须常驻）**

```text
对每个特征，每天抽样比对一次：
  ① 取数：从离线表取 T 日样本实体；从在线快照 / 日志取同一实体在 T 日的服务值
  ② 对齐：同一 entity_id + 同一时间点口径（事件时间，不是写入时间）
  ③ 输出：按特征输出 差异条数 / 比对条数 / 差异分布（是否集中在某类实体）
  ④ 分流：差异率 > 阈值 → 开单；差异集中在少数实体 → 先查上游数据质量；
           全量均匀偏移 → 先查两侧窗口与时间语义
```

**怎么用**：把①里的抽样比例按你的流量调，**不要照抄的是阈值**——阈值应当从「当前差异率」起步逐步收紧，一上来就设 0 会让作业永远红着。③ 的分布输出不要省：**只看总差异率，会把「某一类实体全错」和「全量轻微偏移」混成同一件事**。

**模板 4：特征上线门禁卡**

```text
特征：{特征名} v{版本}        提交人：{人名}        Owner：{人名}
① 注册：条目已建，definition_sql 可直接执行        —— {链接}
② 血缘：源字段已解析（未解析说明见下）              —— {链接}
③ 质量：覆盖率 {x}% / 延迟 P99 {y} / 漂移 PSI {z}  —— 是否越过阈值
④ 一致性：离线与在线比对已跑通，差异率 {r}          —— {报告链接}
⑤ 回滚：上一版本 {v-1} 仍在服务中，切回动作已演练   —— {演练记录}
未解析血缘的场景：{动态 SQL / 脚本任务} —— 已单独标记，纳入盲区清单
```

**怎么用**：③④ 两格必须填数，**填不出数就不许上线**——这正是「没有数当没有监控」的落地方式。⑤ 这一格是这张卡与「通知单」的区别：**没有回滚预案的特征上线，等于把风险留给线上**。不要照抄的是阈值：它随业务与特征类型变化。

**模板 5：配送实时特征链路（形态模板）**

```text
订单事件 ──► Kafka ──► Flink ──┬──► 实时特征（骑手 / 商户 / 用户 / 环境四组）
   (毫秒)      (毫秒)   (毫秒)  │        ├─ 骑手：位置、在手订单数、电量、熟悉度
                               │        ├─ 商户：出餐速度、订单积压
                               │        ├─ 用户：地址准确度、历史投诉
                               │        └─ 环境：天气、时段、路况
                               ├──► Flink CEP：识别"骑手拥堵""商户积压"一类异常
                               └──► GIS 实时计算：Redis Geo + 自研算法算三方距离
                                        └──► 路径规划：A* / Dijkstra + 实时路况
                                            ──► 调度模型 ──► 骑手 App
```

**怎么用**：把四组特征替换成你自己的实体与维度；**不要照抄的是 CEP 规则清单**——规则要从「运营上真正会采取动作的异常」反推，且每条规则必须带一个回收日期，否则规则集会单调膨胀。

### 4.6 成本：这套东西的账单

特征平台的账单贵在**结构**而不是某个部件：它要同时维持「同一份定义的两条执行路径」（离线表 + 在线 KV），还要为「任意时间点回填」长期留存值的历史。存储随「实体数 × 特征数 × 版本数」增长这条机制前文 4.1 Step 2 与 4.2 已展开，这里只把三项账单拆开、并说清每项为什么贵在这个主题上。

- **硬件 / 云（存储是主项）**：在线 KV 常驻容量 ≈ 实体数 × 在线特征数 × 单值字节【推算：1 亿实体 × 200 个在线特征 × 8 B ≈ 160 GB，未计副本、TTL 冗余与索引开销；按你的实际实体数与特征数替换】。本条的口径是**在线服务的那部分特征**（在线特征数），与本案例 [§7.4](04-meituan-feature-store-section-7-sec7.md) 按**全量特征数**给出的上界是两种口径——两组【推算】的实体数与特征数假设不同，不可直接代入或互比；回填侧的快照 / 生效区间存储 ≈ 实体数 × 特征数 × 版本变更次数 × 单值字节【推算：同一算式，版本变更次数是乘数——这正是 4.2「时间点正确性」里那条「必须长期保留」的账单来源】。向量特征若在线检索，另算索引常驻内存。
- **人力（这项才是大头）**：特征平台不能「上线即无人」——要有人对每个特征负责（Step 1 的 Owner）、有人维护血缘解析器覆盖的 SQL 方言、有人看漂移与一致性看板。**贵在它与特征数同向增长，而平台人力通常不增长**，所以可持续规模由血缘自动化率封顶（4.2「血缘」）。
- **计算（实时链路按类付费）**：四类实时特征的成本模型不同（4.1 Step 3）——行为类为每个键维护可恢复的 Flink 状态、画像类按 RPC 往返、设备类落在客户端、场景类按规则算。**用一个时效目标覆盖全部特征，会让便宜的特征替贵的特征付费**，这是分档存在的直接经济理由。

通用账法（单位经济、FinOps、成本归因）见 [数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)。本主题特有的那句是：**特征平台的账单不是「存了多少」，而是「同一件事算了几遍、值留了多久」**。

### 4.7 容灾与故障演练

特征平台的「灾」大多**不报错**——线上照常出分，只是取到的特征旧了、或两侧不一致了。跨地域多活（[容灾与多活](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)）、混沌演练（[混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)）是通用题，本节只列特征特有的四种失效。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 在线 KV 不可用 | 依赖在线特征的模型推理全部取不到值 | 回落到最近一次快照的批量值 / 默认值，本地缓存顶一小段 | 主动摘除一个在线存储分片，看取值是否回落 | 取值可用性 RTO 分钟级、RPO 秒级（热备）【经验：随副本策略与本地缓存时长变化】 |
| 特征陈旧（staleness 超 SLA） | 推荐 / 调度用过期行为，效果缓降而不报错 | 按类回落到上一档时效；超阈值切规则兜底 | 暂停上游 Kafka / 延后 Flink 作业，看链路能否感知 | 恢复到秒级档；检出时限必须短于业务可容忍窗口 |
| 注册中心不可用 | 新特征上不了线；存量取值不受影响 | 存量照常服务，上线动作排队等恢复 | 停注册中心，确认线上取值不受影响 | 把发布通道与取值通道解耦，取值面 RTO≈0 |
| 回填 / 上游重刷失败 | 历史样本补不出、实验不可复现；线上不受影响 | 用已留存快照重算；挂账并标注不可信区间 | 重跑一次历史回填并与当初在线值对拍 | 以「能否重放当时的值」为恢复目标，而非时钟 |

**演练要盯的不是「服务起没起来」，而是「值对不对、旧不旧」**——每条在线链路都要有一次「制造陈旧」的演练，这是特征平台与其他服务最不同的一点。跨地域容灾在特征层是成立的（在线 KV 与注册中心都是可复制的状态服务），但**它保护的是「取值可用」，保护不了「取值正确」**；后者只能靠 4.4 ① 那对常驻的一致性比对作业。

### 4.8 演进路线：0 → 1 → 100

特征平台的演进不是「规模变大」，而是**每上一个台阶，账单的结算单位就换一次**；存量迁移的四件事前文 4.4 已拆开，这里给三个阶段各自「先坏的是什么」。

- **0 → 1（最小可用）**：一个业务线、一份注册中心 + 双栈。**变贵的是注册纪律**——多出来的不是机器，是「先注册后使用」这道流程；**先坏的是注册能被绕过**：审核一旦比业务自建慢，团队就绕过去，注册中心迅速过期（4.2「注册」的失效条件）。
- **1 → 100（规模化）**：四类实时特征分档 + 血缘 + 上线门禁，铺到多个业务线。**变贵的是一致性比对与血缘解析器**（随特征数与 SQL 方言数增长）；**先坏的是统一实体**：一处 OneID 映射出错，多个业务的模型同时偏，而各自的特征定义都没改（4.2「跨业务实体复用」）。
- **100 →（下一道坎）**：把特征馈给 LLM 训练数据 / 对外输出。**变贵的是合规与实体对齐的边界**——可关联的标识类型受法域约束（4.2「跨业务实体复用」）；**先坏的是「平台能力可迁移、合规边界不可迁移」**：能复制平台，复制不了能连哪些标识。

> 判据始终一条：**能不能按数回答「这个语义一共有几个实现」**（4.9 自检清单）。答得出，你还在 1 → 100；答不出，0 → 1 其实没做完。

### 4.9 自检清单

下面 12 条问的都是**这一轮落地与迁移期**的状态——产物在不在、看板在不在跑、抽样比对与重跑有没有留下数；至于「这套平台本身设计得对不对」，那组问题在 [§ 3](04-meituan-feature-store-section-3-sec3.md) §3.7 的自检清单里，两份不要混用。

- [ ] 把 4.1 五步的产物逐件找出来——特征注册中心、统一读取接口、四类实时特征的 SLA 承诺、回填作业的重跑记录、字段级血缘图与上线门禁清单：哪几件不存在，哪几件的最近一次更新还在上一个模型迭代周期之前？
- [ ] 抽 3 个特征，问「这个语义一共有几个实现」——答案是不是查询结果，而不是「我去问一下」？
- [ ] 是不是所有特征都先注册后使用？「注册中心查不到、但线上在跑」的对照清单现在有几条？4.4 ③ 的影子特征占比看板最近一个月在降吗——降不下去，说明还有一条新增路径绕过了注册，那是哪一条？
- [ ] 抽 10 条存量特征的 Owner 字段：还有几条写的是团队名？4.4 ② 判为「迁」的那批里，改成具体人名的动作排在哪一期？
- [ ] 4.4 ② 判为「迁」的特征，最近一个月完成了几条「补登记 + 计算逻辑收敛成一份 SQL」？收敛完的那几条，跑过一次离线 / 在线逐条比对没有？
- [ ] 4.4 ① 的一致性比对是不是常驻作业？最近一次跑出的差异率有没有开单、开给谁、关掉没有？按特征拆开的分布里，「某一类实体全错」与「全量均匀偏移」有没有被分开处理？
- [ ] 抽 3 条上次回填产出的样本，把它们引用的特征值逐个还原到样本事件发生的那个时间点——有没有哪一条用到了事件发生之后才算出来的值？核不上的比例是多少，这批样本是被退回还是照用？
- [ ] 挑一个历史日期重跑一次回填，与当初上线时的在线值对一遍：差异条数是多少，差异是被逐项解释掉了还是挂账？（4.4 ④ 能不能退出双轨，判据就是这一条的数。）
- [ ] 最近一次上游表被重刷（或补跑）之后，回填结果与上一次的差异有没有写进作业记录？下一次有人追问某次实验为什么复现不出来时，这条记录能不能直接回答？
- [ ] 拿一个上游字段，能不能反查出引用它的全部特征与模型？解析器接不进来的场景（动态 SQL、拼接表名、脚本任务）有没有被单独标记成盲区清单，并且有人认领这份清单？
- [ ] 覆盖率、延迟 P50 / P99 / P999、分布漂移（KS / PSI）、一致性这四项，各自有没有数、有没有落到具体的人和周期去看？门禁最近拦下过哪一次上线？
- [ ] 4.4 ② 判为「冻结退役」的那批特征，最近一个月真的下线了几条？下线的触发是系统按使用统计跑出来的、还是人报上来的？走的是退役流程（先告警、留宽限期）还是人工删除——新增与下线在入口上是否对称（都有审批、都有记录）？

### 4.10 小结

> 本节小结：本主题下决定成败的唯一环节是 **Step 1 的注册条目是否成为「唯一权威定义」的落点**——一致性要靠它才有落点，血缘要靠它才有主语，治理要靠它才有主键；它缺席或写在别处（写在文档里、写在某人的代码里），后面每一步都会退化成一次性的整改。**它比其他环节更值得投入的原因很朴素：注册是唯一一件「做在前面很便宜、补在后面极贵」的事**——补登记的成本与特征数成正比，而特征数只会增长。
>
> 第二重要的是 Step 4 的生效区间。它没有交付压力，却决定了「实验能不能复现」与「离线指标能不能信」这两件事——**这两件事失效时都不报错**。
>
> 💡 **思考锚点**：按 4.9 抽你平台上的 3 个特征，问「这个语义一共有几个实现」「注册中心查不到、但线上在跑的有几条」——若注册中心不是唯一权威定义，补登记的成本会随特征数线性增长；再抽 3 条上次回填的样本，把特征值还原到事件发生的那个时间点，核不上（用到了事件之后才算出的值）的比例是多少，这批样本你敢照用吗？
