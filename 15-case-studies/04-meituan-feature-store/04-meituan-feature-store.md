## 1. 背景

### 1.1 公司 / 业务 / 时间

美团成立于 2010 年，至今 15 年。特征平台演进的关键时间节点：

- **2010–2014：千团大战 + 美团起步**。早期数据栈为 MySQL + Hadoop，特征散落在各团队。
- **2015：外卖业务崛起**。美团外卖成为核心业务，特征需求爆发（用户特征、商户特征、配送特征）。
- **2016：酒店旅游 + 到店业务**。新业务带来新的特征需求。
- **2017：美团 ML 平台 V1 立项**。开始系统化建设特征平台。
- **2018：Feature Store V1 上线**。覆盖外卖推荐、广告投放。
- **2019：Feature Store V2 升级**。支持实时特征 + 特征血缘。
- **2020：Feature Store 全面覆盖推荐 / 搜索 / 广告 / 风控**。
- **2021：ML 平台 V3 改造**。与 Lakehouse 架构对齐。
- **2022：美团 ToB 商业化**。美团零售 + 美团企业版对外输出。
- **2023：特征平台 + 大模型融合**。支持 LLM 训练数据管理。
- **2024：美团 ML 平台与教育认证**。

**业务特点**：

- **多业态协同**：外卖、到店餐饮、酒店旅游、电影、买菜、闪购、共享单车、共享汽车。
- **超大规模**：外卖日单量 7000 万+（峰值），商户 1000 万+，骑手 700 万+。
- **强实时**：推荐延迟 < 100ms，配送调度延迟 < 1 秒。
- **多端联动**：C 端用户 + B 端商户 + 配送骑手三方联动。

### 1.2 行业与监管

- **本地生活行业**：商家准入、消费者权益、配送员权益。
- **金融业务**：美团支付 / 美团金融，合规要求严格。
- **数据合规**：《数据安全法》、《个人信息保护法》。
- **等保 2.0 / 3.0**：合规要求。

### 1.3 团队规模与组织

- **美团数据团队**巅峰期约 **2000+ 人**。
- **数据平台部**（基础平台）：约 300+ 人。
- **ML 平台团队**：约 200+ 人（核心团队）。
- **业务算法团队**：约 3000+ 人（与数据团队紧密协同）。
- **组织文化**：**"以客户为中心"** + **"技术驱动业务"**。

## 2. 挑战

### 2.1 业务挑战

#### 2.1.1 多业务特征复用难

美团有外卖、到店、酒店、旅游、电影、买菜、闪购等 10+ 业务，每个业务都有自己的特征团队（"特征生产高度重复"是当时的核心痛点）。

#### 2.1.2 实时特征复杂度高

外卖推荐需要"实时特征"——用户最近 1 分钟点击、最近 5 分钟加购、骑手当前位置、商户当前出餐速度。**实时特征延迟 < 1 秒**，否则推荐效果断崖式下降。

#### 2.1.3 特征一致性难题

**训练时用离线特征，推理时用在线特征**，二者往往不一致（"训练 - 推理偏差" / "Train-Serving Skew"）。这是 ML 工程化的头号难题。

#### 2.1.4 特征血缘难以追溯

业务方想知道"这个特征从哪来？怎么计算？覆盖度如何？"，但特征散落在各团队，**血缘关系复杂**。

### 2.2 技术挑战

#### 2.2.1 海量特征管理

美团有 **10 万+ 个特征**，分布在推荐 / 搜索 / 广告 / 风控 / 配送 / 调度 / 客服 / 营销等多个场景。如何管理？

#### 2.2.2 高 QPS 在线服务

外卖推荐 QPS 数十万级，特征服务必须支撑**毫秒级延迟 + 高并发**。

#### 2.2.3 多源异构数据

特征来源包括：MySQL（用户基本信息）、Kafka（用户行为）、Hive（离线 DWD）、Redis（实时缓存）、日志（用户行为流）——**特征计算横跨多种数据源**。

#### 2.2.4 特征回填

训练数据需要"任意时间点的特征"——比如"用户 2024-01-01 12:00 的特征"，必须能回填。

### 2.3 组织挑战

#### 2.3.1 跨团队协作

美团算法工程师分散在 30+ 个业务团队，每个团队都有自己的特征生产代码。如何让大家都用同一套平台？

#### 2.3.2 平台 vs 业务边界

平台团队提供"通用特征能力"，但业务团队经常有"特殊需求"。如何平衡？

#### 2.3.3 投入 vs 收益

特征平台建设投入大，但短期收益不明显——业务团队看不到价值，平台团队被质疑"过度设计"。

## 3. 架构演进

### 3.1 V1.0：烟囱式特征生产（2010–2017）

**形态**：

```
[业务团队 A] → [自建特征] → [推荐模型]
[业务团队 B] → [自建特征] → [推荐模型]
[业务团队 C] → [自建特征] → [推荐模型]
```

**问题**：

- **特征重复**：30+ 团队各自实现"用户最近点击"特征。
- **口径不一致**：每个团队对"最近点击"定义不同，导致模型难以迁移。
- **难以管理**：特征生产完全无章法，无人知道"现在到底有多少个特征"。

**教训**：ML 工程化起步阶段，"烟囱式特征生产"是必经之路，但不是终点。

### 3.2 V2.0：Feature Store V1（2017–2019）

**关键事件**：

- 2017：美团 ML 平台 V1 立项，开始建设 Feature Store。
- 2018：Feature Store V1 上线，**覆盖外卖推荐、广告投放**。
- 2019：Feature Store V2 升级，支持实时特征 + 特征血缘。

**核心能力**：

- **离线特征**：基于 Hive / Spark 跑批，输出到 Hive 表 / OSS。
- **在线特征**：基于 Kafka / Flink 实时计算，输出到 Redis。
- **特征服务**：基于 RPC 暴露特征给在线推理。
- **特征管理**：特征注册、特征版本、特征上线审批。

**架构**：

```
[离线特征] → [Hive / OSS] → [训练数据]
[实时特征] → [Flink] → [Redis] → [在线推理]
[特征服务] → [统一 API Gateway] → [推荐模型]
```

### 3.3 V3.0：Feature Store V2 全面铺开（2019–2022）

**关键事件**：

- 2019：覆盖到店 / 酒店 / 旅游 / 电影。
- 2020：覆盖风控 / 配送 / 调度。
- 2021：与 Lakehouse 架构对齐，支持 Iceberg / Hudi 表格式。
- 2022：支持 100+ 业务方。

**核心能力**：

- **特征类型丰富**：用户特征、商户特征、商品特征、骑手特征、位置特征。
- **特征血缘**：从 DWD 表到特征的全链路血缘。
- **特征回填**：支持历史时间点特征回填。
- **特征质量监控**：覆盖率、延迟、准确率监控。

### 3.4 V4.0：ML 平台 V3 与 AI Native 演进（2021–2024）

**关键事件**：

- 2021：ML 平台 V3 改造，与 Lakehouse 架构深度整合。
- 2022：支持大模型训练数据管理。
- 2023：支持 LLM 微调数据 + RAG 检索增强。
- 2024：支持多模态特征（图片、文本、视频）。

**核心能力**：

- **统一数据访问**：支持 Lakehouse（Hive / Iceberg / Hudi）。
- **大模型支持**：训练数据管理 + RAG 检索 + 微调。
- **多模态特征**：图片 embedding、文本 embedding、视频 embedding。

### 3.5 当前状态（2024–2025）

- **Feature Store 覆盖 100+ 业务方**。
- **特征数量 10 万+**。
- **覆盖度：外卖、到店、酒店、旅游、电影、买菜、闪购、配送、调度、风控、客服、营销**。
- **2024 年支持大模型与多模态**，成为 AI Native 数据基础设施。

## 4. 关键决策

### 4.1 决策 1：Feature Store 核心架构

#### 4.1.1 三大组件

```
[特征生产（Producer）] → [特征存储（Storage）] → [特征消费（Consumer）]
```

- **特征生产**：
  - **离线特征**：基于 Hive / Spark SQL 跑批。
  - **实时特征**：基于 Flink / Kafka 流处理。
  - **请求服务**：基于原始数据按需计算（如实时查询用户当前 LBS）。

- **特征存储**：
  - **离线存储**：Iceberg / Hive 表。
  - **在线存储**：Redis + 自研 KV 存储。
  - **向量存储**：Milvus / Faiss（用于 embedding 检索）。

- **特征消费**：
  - **训练消费**：从离线表读取，生成训练样本。
  - **在线消费**：从在线 KV 读取，用于推理。
  - **回填消费**：从离线 + 在线混合读取，用于回填。

#### 4.1.2 关键技术

- **统一特征 Schema**：每个特征有"特征名 + 特征类型 + 特征计算逻辑 + Owner + 版本"。
- **特征注册中心**：所有特征先注册后使用。
- **特征版本管理**：支持 v1 / v2 / v3 多版本并存，平滑过渡。

### 4.2 决策 2：实时特征怎么实现？

#### 4.2.1 实时特征分类

- **行为实时特征**：用户最近点击、加购、下单（基于 Flink / Kafka）。
- **画像实时特征**：用户当前位置、商户当前出餐速度（基于 RPC + Redis）。
- **场景实时特征**：当前时段、天气、热点（基于规则 + 实时计算）。
- **设备实时特征**：设备电量、网络状态（基于客户端 SDK）。

#### 4.2.2 实时特征实现

```
[用户行为] → [Kafka] → [Flink] → [Redis / 自研 KV] → [在线服务]
   (毫秒)    (毫秒)    (毫秒)    (毫秒)        (毫秒)
```

**关键技术**：

- **Flink State**：用于维护"用户最近行为窗口"。
- **Redis Sorted Set**：用于存储"时间窗口内的行为"。
- **自研 KV 存储**：用于存储"用户画像实时特征"。

#### 4.2.3 实时特征 SLA

- **延迟 SLA**：< 1 秒。
- **可用性 SLA**：99.99%。
- **准确性 SLA**：覆盖率 > 99%。

### 4.3 决策 3：特征回填怎么实现？

#### 4.3.1 回填场景

- **训练数据准备**：生成"用户 2024-01-01 12:00 的特征"用于训练。
- **A/B 实验后评估**：评估"实验组用户在 2024-01-01 的特征分布"。
- **离线模型调试**：调试模型时需要历史特征。

#### 4.3.2 回填架构

```
[历史 DWD 表] → [Spark / Hive] → [特征计算 SQL] → [回填特征表]
```

#### 4.3.3 关键技术

- **特征计算 SQL 化**：所有特征都用 SQL 定义，离线 + 在线复用同一份 SQL。
- **时间窗口支持**：特征计算支持任意时间窗口。
- **回填调度**：美团 Dolphin 调度系统（基于 Airflow 改造）。

### 4.4 决策 4：特征血缘怎么实现？

#### 4.4.1 血缘层次

```
[源表] → [DWD] → [特征计算 SQL] → [特征注册] → [模型应用]
```

- **源表层**：MySQL / Kafka / OSS。
- **DWD 层**：基于源表清洗的明细表。
- **特征计算层**：基于 DWD 计算特征。
- **特征注册层**：特征注册中心。
- **模型应用层**：模型使用特征。

#### 4.4.2 血缘采集

- **自动解析 SQL**：从特征计算 SQL 自动解析血缘。
- **血缘存储**：基于图数据库（GDB / Neo4j）。
- **血缘展示**：可视化工具展示血缘。

#### 4.4.3 血缘应用

- **影响分析**：上游表变更影响哪些特征、哪些模型。
- **溯源分析**：模型效果下降，溯源到特征质量。
- **数据治理**：发现重复特征、孤儿特征。

### 4.5 决策 5：特征质量监控怎么实现？

#### 4.5.1 监控维度

- **延迟监控**：特征生产延迟（P50 / P99 / P999）。
- **覆盖率监控**：特征覆盖率（应该有的样本中，实际有的比例）。
- **分布监控**：特征值分布变化（漂移检测）。
- **一致性监控**：离线 / 在线特征一致性。

#### 4.5.2 漂移检测

- **KS 检验**：比较两个时间点的特征分布。
- **PSI（Population Stability Index）**：监控特征稳定性。
- **自动告警**：漂移 > 阈值自动告警。

### 4.6 决策 6：美团 ML 平台整体

#### 4.6.1 平台架构

```
[数据集成] → [特征平台] → [模型训练] → [模型部署] → [在线推理]

                 Store)      TF / Pytorch) Custom)    TF Serving)
```

#### 4.6.2 核心模块

- **DataFinder**：数据集成（美团版 DataX）。
- **Feature Store**：特征平台。
- **PAI**：模型训练与部署平台。
- **MLeap**：实验管理 + 模型版本。
- **AB 平台**：A/B 测试。
- **Serving**：在线服务。

### 4.7 决策 7：外卖配送的数据架构特殊性

#### 4.7.1 配送核心问题

- **30 分钟送达**：意味着从下单到送达 30 分钟内必须完成。
- **实时调度**：系统实时决定"哪个骑手送哪个订单"。
- **ETA 预估**：实时预估骑手到达时间。
- **路径规划**：实时规划骑手路线。

#### 4.7.2 配送数据栈

```
[订单事件] → [Kafka] → [Flink] → [实时特征] → [调度模型] → [骑手 App]
              (毫秒)    (毫秒)    (毫秒)      (毫秒)        (毫秒)
```

**端到端延迟 < 1 秒**。

#### 4.7.3 配送特征

- **骑手特征**：当前位置、当前订单数、电量、熟悉度。
- **商户特征**：当前出餐速度、订单积压。
- **用户特征**：地址准确度、历史投诉。
- **环境特征**：天气、时段、路况。

#### 4.7.4 关键技术

- **Flink CEP**：复杂事件处理（识别"骑手拥堵"、"商户积压"等异常）。
- **GIS 实时计算**：基于 Redis Geo + 自研算法计算骑手 - 商户 - 用户三方距离。
- **路径规划算法**：基于 A*、Dijkstra + 实时路况。

### 4.8 决策 8：与 OneID / 推荐 / 广告的协同

#### 4.8.1 OneID 协同

美团有"用户 OneID"——同一手机号 / 设备 ID 在外卖、到店、酒店等业务统一识别。

- **跨业务特征**：基于 OneID 关联跨业务特征（"用户在外卖 + 到店的综合画像"）。

#### 4.8.2 推荐协同

- **统一特征**：外卖推荐、酒店推荐、电影推荐共享"用户基础特征"。

#### 4.8.3 广告协同

- **CTR 预估特征**：用户历史点击 + 商户特征 + 广告特征。
- **CVR 预估特征**：用户历史转化 + 商户特征 + 商品特征。

## 5. 踩坑与教训

### 5.1 坑 1：训练 - 推理偏差（Train-Serving Skew）

**问题**：美团某推荐模型离线 AUC 0.85，上线后效果仅 0.65。

**根因**：

- 训练时用离线特征（基于 Hive 历史数据）。
- 推理时用在线特征（基于 Redis 实时计算）。
- 二者计算口径不一致（如"最近 30 天点击"在离线是 30 天历史数据，在线是 Redis 滑动窗口，存在差异）。

**教训**：

- **离线 / 在线特征必须统一计算口径**——同一份 SQL 复用。
- **必须建立"特征一致性监控"**——离线 / 在线对比。
- **必须有"特征回填能力"**——训练时回填在线特征。

**修正**：美团建立"特征 SQL 化"机制，离线 / 在线复用同一份特征计算 SQL。

### 5.2 坑 2：实时特征"晚到数据"

**问题**：美团某实时特征基于 Flink Kafka 消费，但 Kafka 消息晚到（网络抖动 / 反压）时，特征计算延迟。

**根因**：

- Flink 默认 EventTime 处理允许一定延迟，但延迟过大时丢弃。
- 没有"晚到数据处理"机制。

**教训**：

- **实时特征必须有"晚到数据处理"**——延迟 > 阈值时告警或修复。
- **必须有"双流关联"能力**——主特征 + 补充特征。
- **必须设置合理的 Watermark**。

**修正**：美团建立"晚到数据监控 + 自动修复"机制。

### 5.3 坑 3：特征数量爆炸导致"特征沼泽"（Feature Swamp）

**问题**：2020 年美团特征数量达到 5 万+，但**实际被使用的不到 30%**——大量"僵尸特征"。

**根因**：

- 缺乏特征生命周期管理。
- 缺乏特征使用统计。
- 缺乏"特征下线"机制。

**教训**：

- **必须有"特征生命周期管理"**——每个特征有"出生 + 死亡"。
- **必须有"特征使用统计"**——所有特征统计使用次数。
- **必须有"特征下线流程"**——特征 6 个月未使用自动告警，9 个月未使用自动下线。

**修正**：美团建立"特征治理委员会"，定期清理僵尸特征。

### 5.4 坑 4：实时特征对训练的反向影响

**问题**：某推荐模型上线后效果好，但导致用户行为变化，**新的实时特征分布与训练时差异巨大**，模型效果逐步下降。

**根因**：

- 推荐模型上线后，用户点击偏好变化（如新推荐的产品）。
- 实时特征基于用户新行为，与训练时的"旧行为"分布不同。

**教训**：

- **推荐模型上线必须有"反馈闭环"**——上线后监控特征分布。
- **必须有"周期性再训练"机制"——每隔一段时间重新训练。
- **必须有"特征漂移检测"**——漂移 > 阈值自动重训。

**修正**：美团建立"模型自动重训机制"——每周基于最新数据自动重训。

### 5.5 坑 5：平台化与业务灵活性矛盾

**问题**：美团特征平台团队为追求"通用性"，部分场景过度抽象，业务团队反而觉得"用平台比自己写还慢"。

**具体表现**：

- 业务团队想加一个"业务专属特征"，平台团队说"不支持"。
- 业务团队自己偷偷造一个特征，但又脱离了平台。

**教训**：

- **平台必须有"通用 + 定制"双轨**——80% 通用 + 20% 定制。
- **必须支持"自定义特征"**——业务方可以扩展。
- **必须有"特征审查机制"**——业务方自定义特征经过审查后纳入平台。

**修正**：美团建立"自定义特征注册中心"，业务方可以注册自定义特征，但必须走审查流程。

## 6. 复用经验

### 6.1 适合谁学

#### 6.1.1 强 ML 需求的企业

- **典型**：电商、金融、内容、广告、社交。
- **原因**：Feature Store 是 ML 工程化的核心基础设施。

#### 6.1.2 多业务线协同

- **典型**：平台型公司、生态型企业。
- **原因**：特征跨业务复用价值巨大。

#### 6.1.3 实时决策场景

- **典型**：外卖、出行、推荐、调度、风控。
- **原因**：实时特征是核心竞争力。

#### 6.1.4 数据规模大

- **典型**：日活 1000 万+、订单 100 万+。
- **原因**：小规模不值得做 Feature Store。

### 6.2 不适合谁学

#### 6.2.1 数据规模小的初创公司

- **反例**：日活 < 10 万 的初创公司。
- **原因**：特征数量 < 1000，Excel / 文档管理即可。

#### 6.2.2 弱 ML 需求的业务

- **反例**：传统 OA、企业内部系统。
- **原因**：基本不用 ML，不需要 Feature Store。

#### 6.2.3 业务流程复杂但 ML 应用少的业务

- **反例**：传统金融的核心交易系统。
- **原因**：规则引擎主导，不需要 ML。

### 6.3 关键可复用资产

#### 6.3.1 开源 Feature Store

- **[Feast](https://feast.dev/)**：最流行的开源 Feature Store。
- **[Tecton](https://www.tecton.ai/)**：商业版 Feature Store（基于 Feast）。
- **[Hopsworks](https://www.hopsworks.ai/)**：开源 + 商业。
- **[Databricks Feature Store](https://www.databricks.com/product/feature-store)**：Databricks 一体化方案。

#### 6.3.2 关键技术

- **离线特征计算**：Hive / Spark / Iceberg。
- **实时特征计算**：Flink / Kafka / Redis。
- **特征服务**：自研 RPC / gRPC + Redis。
- **特征血缘**：基于图数据库。
- **特征回填**：基于 Spark SQL 重跑。

#### 6.3.3 美团 ML 平台核心

- **DataFinder**：数据集成。
- **Feature Store**：特征平台。
- **PAI**：模型训练与部署。
- **AB 平台**：A/B 测试。
- **Serving**：在线服务。

## 7. 与同类案例对比

### 7.1 对比维度

| 维度 | 美团特征平台 | 字节 Feature Store | Uber Michelangelo | Airbnb ML Platform |
| --- | --- | --- | --- | --- |
| 主导思想 | 平台化 + 业务复用 | 数据驱动 + AB 实验 | 平台化 + 工程师友好 | 平台化 + 数据科学家友好 |
| 核心组件 | Feature Store + PAI | ByteHouse + AB 平台 | Feature Store + Model | Minerva + ML Platform |
| 实时特征 | 强 | 强 | 中 | 强 |
| 特征回填 | 强 | 强 | 中 | 强 |
| 血缘 | 强 | 强 | 中 | 强 |
| 商业化 | 美团 ToB | 火山引擎 | Uber Engineering | Minerva 开源 |

### 7.2 取舍

- **美团 = 平台化 + 业务落地 + 全栈整合**——把 ML 工程化做到极致。
- **字节 = 数据驱动 + AB 实验 + 实时**——把推荐效果作为第一优先级。
- **Uber = 工程师友好 + 数据自治**——让算法工程师高效工作。
- **Airbnb = 数据科学家友好 + 协作**——让数据科学家高效协作。

**对架构师的启示**：

- **学"特征 SQL 化"**——美团最重要的可借鉴经验。
- **学"训练 - 推理一致性"**——这是 ML 工程化的关键。
- **学"特征血缘"**——管理 10 万+ 特征的唯一方法。
- **学"特征生命周期管理"**——避免特征沼泽。
