## 4. 关键决策

本节按主文件导航表的分节方式展开：§4.1–§4.6 对应导航表列出的六项决策，§4.7 是与它们并列的第七项（调度主干），并兼作这七项决策共用的落地顺序、存量迁移路径、模板与自检清单。每个决策给四件事：**判据**（什么条件下这个决策成立）、**机制**（因为 A，所以 B，代价是 C）、**失效条件**（什么条件下它的优点会反转、症状是什么）与**该决策下的工程动作**。

本节主要写给**在存量数据栈上改造的读者**（已有 Hive 表、已有调度、已有报表）。从零搭建的读者可以先看 §4.7.4 的落地顺序，再回到各决策确认判据是否满足。文中工期与规模阈值一律用区间与条件表达（【经验】），可给出公开锚点的年份单独标注【公开】。

### 4.1 决策一：中心语义层（Minerva）

#### 4.1.1 决策路径与判据

- **方案 A：传统 BI 工具**（Tableau / Looker 一类）——成熟，但指标定义分散在各张报表里，无法治理。
- **方案 B：自研指标平台**（Minerva）——指标集中、口径统一；代价是自研的长期人力与生态维护。
- **方案 C：商业指标平台**（Looker / Sisense 一类）——上线快，定制化与内嵌治理能力弱。

**决策：自研 Minerva。**

**第一条判据是成本归属：口径算错了，钱从谁的口袋里出。** 如果答案是「全公司」或「要对外解释」，中心语义层就是结构性必需而不是优化项；如果答案是「各自业务线」，联邦或自治反而更省（§3.1 把这条约束记为「口径错误的成本归属」）。第二条是规模判据：**同一个口径每周被几个团队引用**——个位数时，中心层的固定成本摊不薄。

#### 4.1.2 Minerva 核心与机制

```text
[指标定义] → [OLAP 引擎] → [BI / API]
   (元数据)   (Presto /      (消费)
              Druid)
```

- **指标定义**：每个指标有「业务定义 + 计算逻辑 + 数据来源 + Owner + 版本」五项，缺项不允许发布。
- **指标分类**：**原子指标**（不可再拆分）、**派生指标**（基于原子指标计算）、**复合指标**（多个原子指标组合）。
- **指标血缘**：从指标可以追溯到 Hive 表，「口径改一次会影响谁」因此可查。
- **价值**：统一口径（所有指标有唯一来源）、自助分析（业务分析师直接引用指标）、变更追溯（指标变更可追溯）。

**机制**：因为指标从「某个人写的一段查询」变成「一个可被引用的定义对象」，所以想统一时只需改这一份，**口径分裂的源头被消除**；又因为派生指标引用原子指标，改一个原子指标会在引用图上产生级联——这既是变更传播的实现方式，也是它唯一的风险面。**代价**：中心语义层成为所有指标变更的必经之路，**它的评审带宽就是组织的指标迭代速度上限**。

#### 4.1.3 失效条件与工程动作

**失效条件**：**当口径本身还在探索期、定义的正确性尚未稳定时，这套机制会反转**——「一处定义、处处同源」变成「把试错周期拉长的一道审批」，因为每次探索性改动都要穿过中心的评审队列。**症状**：业务方在语义层之外另建一张「临时看板」，而平台上的新增定义数停滞。**修法**：区分「探索性度量」与「组织级口径」，只把后者送进语义层。

**工程动作**：

- **产物**：指标定义清单（五要素齐全）+ 一份「改一个原子指标、下游引用自动同步」的验证记录。
- **判据**：抽 5 个被跨团队引用的指标，问「它引用了哪张表的哪些字段、Owner 是谁」，答案能在系统里一次查到；再改其中一个的定义，**下游引用处不做人工通知也同步**。
- **为什么必须在这一步、为什么在采购之前**：它是后面所有决策的输入——目录要挂指标、质量断言要挂在口径上、模型取数要引用定义。语义层缺席时，这三件事各自长出一套口径，事后归一要用「改结构」而不是「改配置」的成本来还。

指标定义的可用模板（字段集合在 §6 记录的「指标定义规范」六项——度量 / 过滤 / 维度 / 时间粒度 / 数据源 / Owner——之外，另加平台运行必需的 `metric_id`、`version`、`status` 三项）：

```yaml
metric_id:   trade_gmv_daily          # 全局唯一，跨系统引用这一个键
display:     成交额（GMV）
definition:  统计已支付订单的商品金额之和
measure:     sum(order_amount)        # 度量
filters:     [order_status = 'PAID']  # 过滤
dimensions:  [date, market, listing_type, device]
granularity: [1d]
source_table: dwd_trade_order         # 数据来源（到表与字段）
owner:       @marketplace-analytics   # 具体到人，不写团队名
version:     3
status:      prod                     # draft / canary / prod / retired
```

**怎么用**：`measure / filters / dimensions / granularity / source_table` 五格由平台从 SQL 解析结果自动填，人工只填 `definition` 与 `owner` 两格；`metric_id` 一旦发布不得复用，口径改了走 `version` 递增。不要照抄示例里的 `dwd_trade_order` —— 换成你自己的 DWD 表名与真实字段。

### 4.2 决策二：元数据与血缘中枢（Dataportal）

#### 4.2.1 定位与判据

Dataportal 是 Airbnb 的元数据管理平台，是 Minerva、数据地图与数据血缘的核心。**判据**：当你回答不了「改这张表会影响谁」，或这个问题的答案要靠拉群问人才能拼出来时，元数据层就是必需的——**人工问询的问题不是「有没有人知道」，而是「知道的人是否刚好被问到」**；沉默的、离职的、自动化的下游一定漏。

#### 4.2.2 核心能力与机制

- **数据目录**：所有数据资产注册到 Dataportal。
- **数据血缘**：从 Hive 表到指标的可视化血缘。
- **数据 Owner**：每个数据集有 Owner。
- **数据 SLA**：每个数据集有 SLA。
- **数据质量**：集成数据质量监控。

```text
[数据资产] → [Dataportal 注册] → [统一目录] → [业务使用]
   (Hive)     (元数据采集)        (可视化)     (消费)
```

**机制**：元数据分两类，**技术事实**（有哪些字段、类型是什么、谁读了谁写了）可以由采集器自动获得；**业务含义**（这张表回答什么业务问题、口径的边界在哪）只能由人补，而且只有 Owner 补得对。所以**元数据层必须与 Owner 一起建设，而不是先建目录再补责任**——没有 Owner 的目录，业务含义字段会以「最后更新于两年前」的形态长期腐烂。**代价**：采集与补全是持续投入，且元数据本身成为第二个需要治理的数据集。

**价值**：数据可发现（快速找到需要的数据）、数据可治理（Owner 明确，治理有抓手）、数据可信任（血缘 + 质量共同支撑）。

#### 4.2.3 失效条件与工程动作

**失效条件一（登记制）**：**当资产进入万级、每天新增以百计时，「一次查询答完影响面」会反转成「遍历出一张不可信的图」**——登记的边际成本随资产数线性增长而收益不增长，团队开始填空壳字段，血缘边大面积缺失，**影响面查询漏掉下游却不报错**。症状：影响面查询的返回条数长期不随资产增长而变化。

**失效条件二（SLA 字段）**：SLA 写进元数据但不接监控时，它只是一句声明。**症状**：SLA 声明 T+1 07:00 产出，而下游连续三天在 11:00 才拿到数据，没有任何告警。

**工程动作**：

- **产物**：资产登记表（含 Owner、SLA、密级、业务含义四类必填字段）+ 血缘采集器接入发布流程的记录。
- **判据**：抽 3 张核心表做一次改名或加列，**血缘采集器在变更进入合并前就列出下游**（而不是上线后由下游报错）；再随机抽 5 行登记记录，看 Owner 是具体的人还是团队名。
- **为什么必须与语义层同期做**：没有血缘，指标变更找不到全部下游；没有指标定义，血缘只说明「表与表相连」而不说明「口径从哪来到哪去」。两者缺一，另一个都会退化成文档。

### 4.3 决策三：ER 骨架与维度模型

#### 4.3.1 ER 模型

Airbnb 用 ER 模型定义业务实体：

- **核心实体**：用户 / 房源 / 预订 / 房东 / 评论。
- **实体关系**：用户–预订–房源、房东–房源、用户–评论。

#### 4.3.2 维度建模

基于 ER 模型构建维度模型：

- **DWD 层**：基于 ER 实体的明细数据。
- **DWS 层**：基于主题域的聚合数据。
- **ADS 层**：基于业务场景的应用数据。

#### 4.3.3 关键经验、机制与失效条件

- **ER 模型必须稳定**——核心实体（如用户、房源）的定义不能频繁变化。
- **维度建模必须灵活**——支持业务快速变化。
- **ER 与维度模型必须联动**——ER 是「骨架」，维度模型是「肌肉」。

**机制**：因为 ER 层只描述「有哪些实体、它们之间是什么关系」，**它一旦收敛，下游的维度模型就能被复用而不是被重写**；因为维度模型面向查询而建，所以业务出现新的分析视角时只需加维度而不用动骨架。这条分工的代价是**两层的变化节奏不同**，必须有人维护「实体属性 → 维度属性」的映射，否则会出现同一属性在两处取值不同。

**失效条件**：**当核心实体还在变动（例如业务从「整租」扩展到「体验」「餐厅预订」这类新实体）时，「骨架稳定」的前提消失**，此时所有下游维度模型都要跟着返工——症状是所有仪表盘在同一个月里集体失效。**反向的失效同样存在**：骨架冻结后业务实体已扩张，而维度模型仍按旧骨架建模，结果是新业务的数据只能另建一套表，血缘从此断开。**修法**：先冻结实体的**主键与关系**，把属性（如房源的标签体系）留在可扩展的维度里。

**工程动作**：**产物**是一张实体清单（主键 + 关系 + Owner）与一张「实体 → DWD/DWS/ADS」的映射表；**判据**是随机挑一个核心实体，问「它的主键在所有下游表里是否同一个键、口径是否同一份」，答案不一致说明骨架只存在于文档里；**为什么必须在维度模型之前**：DWD/DWS/ADS 的分层与字段都落在实体主键与关系上，骨架未收敛就先分层，第一次实体扩张会连带重写全部下游表，且无法用「加维度」的方式局部完成。

### 4.4 决策四：批流双链路

#### 4.4.1 实时场景与判据

本案例讨论的实时场景有四类：**实时搜索**、**实时定价**、**实时推荐**、**实时反欺诈**。它们被并列写在一起，但**成立条件不同**：前两类的结果会在一次用户请求内被读走，第三类要看到「用户刚刚的行为」，第四类要在交易发生前给出判定。

**判据**：**你的实时结果会不会在一次在线请求内被读走？** 只是写进一张表供人次日查看的，不该进这份清单——它换不回延迟预算。

#### 4.4.2 实时架构

```text
[业务事件] → [Kafka] → [Flink / Spark Streaming] → [Hive / Druid] → [在线服务]
```

这条链路与批链路并存：同一条业务事件被算两遍，于是**「批流口径一致」从实现细节升级为架构约束**——它不再是「两个任务写得一样」，而是「两条链路引用同一份定义」（§3.2.4）。

**机制**：因为批与流是两条独立可演进的链路，任意一条的引擎换代都不必等另一条，所以实时链路的迭代速度不受批链路排期约束。**代价有三项，且都会随链路存在而长期存在**：同一份数据被算两遍（实现数、监控面翻倍）；口径变更的发布范围扩大一倍（要考虑已发出的事件、处理中的窗口、已写入在线存储的结果）；实时链路需要单独的延迟 SLA 与分级降级。

#### 4.4.3 关键技术、选型判据与失效条件

| 组件 | 在本案例中的角色 | 选型判据（什么约束下选它） | 不选它 / 选错的代价与失效条件 |
| --- | --- | --- | --- |
| **Kafka** | 事件流入口，批与流共用的事件源 | 事件要被多个消费方独立消费、且需要按 key 保序 | 分区键选错（如按时间均匀散列）导致同实体事件乱序或单分区热点，特征是「偶发的状态跳变」而非常态延迟 |
| **Flink / Spark Streaming** | 实时计算 | 需要事件时间窗口与端到端一致性时用 Flink 一类；已有 Spark 存量与生态时用 Spark Streaming | 反压未被观测时表现为延迟抖动：P99 稳定在秒级、偶发跳到十秒级（§5.2.3 记录的坑 3 即此形态），根因常在上游消费而非算子 |
| **Druid** | 实时 OLAP，供在线服务点查与聚合 | 查询形态是「时间范围 + 聚合」，且要求亚秒级响应 | 写入吞吐超预聚合刷新能力时，查询会看到部分数据（结果偏小且不报错），必须自己对「数据完整性」设一条可观测断言 |
| **Iceberg**（2022 后） | 表格式，承载批写与增量修正 | 需要 schema 演进、快照回溯、多引擎共存 | 小文件与快照不治理时，元数据操作随文件数变慢——**它换的是存储，不是代际**（§3.6 已把这条区分列为判据） |

**档位**：Kafka 由 LinkedIn 于 2011 年开源（【公开：Apache Kafka 项目页, 2011】）；Iceberg 由 Netflix 于 2018 年开源并进入 Apache 孵化（【公开：Apache Iceberg 项目页, 2018】）；本案例 2022 年后采用 Iceberg 这一点属案例记录（【经验】）。实时链路 2020 年用 Spark Streaming、2022 年换 Flink，沿用本案例 § 3 的年表（【经验】）。

**失效条件**：**当实时结果并不被在线请求读取时，双链路会反转成「一条更贵、更脆、还需要与批链路对齐口径的批链路」**。症状：流链路在跑，但它的消费方只有次日报表与人工抽查。

**工程动作**：**产物**是一份「实时场景 × 结果是否进在线请求 × 延迟 SLA × 降级策略」清单，加一份批流两条链路引用同一份定义的对照记录（§3.2.4）；**判据**是抽一条实时指标，在两条链路各取一次同期结果比对，差值落在业务可接受区间内**且不需要人工同步两处查询**——靠人改两边 SQL 才对得上的，说明定义还没有被共用；**为什么必须在这一步**：延迟预算与降级策略只有在「结果是否进在线请求」被回答之后才定得下来，先建链路再补这个答案，建出来的正是上面那条失效条件描述的形态。

### 4.5 决策五：ML 平台（Bighead）

#### 4.5.1 架构与判据

```text
[数据] → [特征] → [训练] → [部署] → [推理]
```

**判据**：**你现在有没有一条「训练时看到的特征，与推理时喂进去的特征必须一致」的要求**（§5.2.4 记录的坑 4「环境不一致」正是这条要求的失败形态）。有，就需要一个平台来承载特征定义与模型产物；没有，说明模型还停在离线实验阶段，先补版本化再谈平台。

#### 4.5.2 核心模块与选型判据

- **Deep Learning**：基于 TensorFlow / PyTorch。判据：以动态图调试与生态成熟度优先选 PyTorch 一类，以既有生产推理栈与图优化优先选 TensorFlow 一类。选错的代价是推理侧要么重写、要么长期维护两套。
- **Classical ML**：基于 Spark MLlib / scikit-learn。判据：特征已在 Spark 侧生成、样本量超单机内存用 MLlib 一类；样本可单机容纳、需要快速迭代用 scikit-learn 一类。
- **Feature Store**：基于 Hive + Redis。判据：**训练要的是历史时点的特征值（point-in-time），推理要的是毫秒级最新值**——两者是两种存储需求，用一套存储扛会两头不达标。
- **Model Serving**：基于 Kubernetes。判据：需要灰度、弹性与资源隔离时必须走编排层；单机部署只适合实验期。
- **Notebook**：基于 Jupyter + 内部工具。判据：只有当 Notebook 能与环境镜像、权限、数据访问打通时才值得作为正式开发环境。

#### 4.5.3 应用、机制与失效条件

**应用**：搜索（实时搜索排序）、推荐（房源推荐）、定价（智能定价）、反欺诈（实时反欺诈）。

**机制**：因为模型是二进制产物，**它的行为只由「权重哈希 + 特征定义 + 环境」三者共同决定**，所以「换了一版权重但没换特征定义」这种组合必须能被寻址；平台的真正价值不在训练，而在让这三者一起被版本化。**代价**：ML 平台是批链路、流链路之外的**第三个消费者**，语义资产要多维护一层投影，且训练—推理一致性的故障不可能在测试环境完全暴露。

**失效条件**：**当特征的定义只在训练代码里、而推理侧由另一个团队复现时，「离线调好、上线打折」必然发生**。症状：离线评估指标稳定，上线后 A/B 显著变差，且回滚模型版本不起作用（因为差异在特征而不在模型）。**修法**：把特征定义抽成两侧共用的同一份定义，并在 trace 里记录推理时实际取到的特征快照。

**工程动作**：**产物**是一份「特征 / 模型 → 定义版本 → 环境镜像 → 权重哈希」四列可寻址清单，加一份推理 trace 里记录实际取到特征快照的样例；**判据**是同一个模型版本在两个环境各跑一批样本，特征分布的差异能被**逐字段定位**（而不是只知道结果不同）；**为什么必须在这一步**：这三项只有一起被版本化，「离线调好、上线打折」才能被归因到具体是哪一项变了——缺任何一项，上面这条修法都执行不下去。

### 4.6 决策六：数据质量保障

#### 4.6.1 质量维度与判据

- **准确性**：数据值是否正确。
- **完整性**：数据是否缺失。
- **一致性**：数据是否一致。
- **及时性**：数据是否及时。
- **唯一性**：数据是否重复。

**判据**：**异常是由下游先发现，还是上游先发现？** 如果结论总是「业务方报错才知道」，质量体系就还没有载体。五个维度的成本不同：及时性与完整性用一条断言就能覆盖；一致性（同一事实多处存储是否同步）与唯一性（去重键是否成立）需要跨表比对，成本高，应当按资产分级配置，而不是每张表都上全套。

#### 4.6.2 工具与机制

- **断言（Assertions）**：每个数据集有断言规则。
- **监控**：实时监控 + 告警。
- **修复**：自动 / 人工修复。

**机制**：因为**校验一旦作为「任务的副产品」，就只能随任务一起被重写**，所以把校验做成**资产的属性**——属性可以被监控、可以被继承、可以被发布门禁引用，副作用不会。**代价**：断言要从存量任务里提炼出来，第一次整理需要按表逐条翻历史 SQL；自动修复则引入新的风险面。

**失效条件**：**当断言散落在任务里而没有载体时，「偶发」会变成「反复」**——每次事故的修法只覆盖了出事的那条链路。**自动修复的失效形式相反**：修复动作掩盖了上游生成逻辑的错误，症状是同一条断言反复触发而根因从未被改。

#### 4.6.3 流程与工程动作

- **事前**：数据进入前校验。
- **事中**：数据处理中校验。
- **事后**：数据入库后校验。

**工程动作**：**产物**是「资产 → 断言集合 → 责任人」三列台账 + 每个断言的告警去向；**判据**是造一次人工脏数据，看它是否在**进入下游之前**被拦截，以及告警是否落到具体人而不是一个群里。**为什么排在语义层与元数据之后**：断言要挂在「资产」或「指标口径」上，两个载体都没有时，写出来的断言只能挂在任务上，而挂在任务上的断言正是 4.6.2 描述的那种会消失的断言。

### 4.7 决策七：调度主干（Airflow）与工程落地

#### 4.7.1 Airflow 核心

```text
[DAG] = [Tasks] + [依赖关系] + [调度规则]
```

**机制**：因为 DAG 是代码而不是配置，**依赖关系就从人的记忆里搬进了版本库**——可评审、可回滚、可复用 Operator。这也是它成为本案例七项决策落地载体的原因：血缘从任务定义里解析、断言挂在任务之后、影响面卡点跑在发布之前，这三件事都要有一个「任务与被依赖关系都存在」的地方。

#### 4.7.2 Airflow 价值与选型判据

- **Python 优先**：用 Python 写 DAG，开发效率高。判据：团队以 Python 为主、且需要把调度与数据逻辑写在同一种语言里。
- **可扩展**：Operator 机制支持各种数据源。判据：数据源以长尾为主时，Operator 生态比内置连接器数量更重要。
- **可视化**：Web UI 可视化。
- **社区**：Apache 大社区。

**不选它的代价**：改用配置式 / 平台内置调度时，自定义逻辑要从调度层退回到被调度的任务里，代价是**「调度的边界与业务代码的边界合一」**，任何一次调度升级都要连带改任务。

**失效条件**：**当工作流从百级增长到万级、且使用团队不再技术同质时，DAG-as-code 的优点会反转**——「用代码定义依赖，门槛只有会写代码」变成「任何一个人的坏 DAG 都可能是所有人的故障」，因为调度器必须托管并执行用户代码。症状：一次共享调度资源的争抢导致多个无关业务同时延迟。

**工程动作**：**产物**是一份「DAG → 所属团队 → 关键路径 SLA → 共享资源配额」台账，加一次「人为提交坏 DAG」的隔离演练记录；**判据**是坏 DAG 上线后故障被限制在它自己的关键路径内（而不是无关业务一起延迟），且调度器对自托管的用户代码有一道入口检查；**为什么必须在这一步**：上面那条失效条件只在调度器已承载全部关键路径之后才显现，先量出「谁与谁共享调度资源」，配额与隔离才有落点。

#### 4.7.3 Airbnb 使用 Airflow 的演进

- **2014：内部版本**（Airbnb 自研）。
- **2015：开源**（【公开：Apache Airflow 项目页, 2015】）。
- **其后捐给 Apache 基金会、进入孵化并成为顶级项目**——各阶段的年份以项目页当前版本为准（【公开：Apache Airflow 项目页】）。
- **2024：仍是业界最流行的调度系统之一**（【经验】——按「公开项目页的活跃度与生态规模」可自行检索核验，不按单一榜单断言）。

#### 4.7.4 七项决策的落地顺序（每步给产物 / 判据 / 为什么在这个位置）

**第 1 步：冻结口径对象与连接键（【经验】1–2 个月，不依赖任何采购）**

- 动作：把被跨团队引用的指标登记成定义对象；给表、字段、指标分配跨系统不变的 ID。
- **产物**：指标定义清单 + 「资产 ID ↔ 表 / 字段 ↔ 指标」对照表。
- **判据**：抽 5 个核心指标，能一次查出它引用的字段；把某个字段改名，影响面清单能自动生成。
- **为什么在这个位置**：这是唯一一件「做晚了无法回填」的事——历史调用与历史变更没有留下 ID，回填不进去。

**第 2 步：语义层只收「组织级口径」（【经验】2–4 个月）**

- 动作：先把口径错误成本落在全公司的那些指标纳入平台，探索性度量明确排除在外。
- **产物**：平台上线的第一批指标 + 一份「什么进、什么不进」的判定规则。
- **判据**：问业务方「上次口径有争议时，你们查的是平台还是拉群」，答案从拉群变成查平台。
- **为什么在这个位置**：放进来的范围决定后面所有工作的分母；把探索性度量一起收进来，会让评审队列成为迭代瓶颈，最终整个平台被绕过。

**第 3 步：元数据与 Owner 同时上线（【经验】与第 2 步同期）**

- 动作：采集器自动填技术事实，Owner 只补业务含义；无主资产被显式列出而不是默认留空。
- **产物**：可检索的资产目录 + 无主资产清单。
- **判据**：随机抽 5 张核心表，Owner 是具体的人；再问其中一位「这张表的业务含义最近一次更新是什么时候」。
- **为什么必须在第 2 步而不是之后**：指标要挂在资产上，而资产的业务含义只有 Owner 补得对；先建目录后补责任，补出来的字段会在数月内过期。

**第 4 步：血缘自动采集接进发布流程（【经验】1–2 个季度）**

- 动作：从任务定义与 SQL 解析生成血缘，接入合并前的检查；超阈值阻断。
- **产物**：字段级血缘图 + 一份「变更被阻断」的记录。
- **判据**：让某人真实提交一次会破坏下游的字段改名，看它是否在合并前被拦下（而不是上线后由下游报错）。
- **为什么必须在语义层之后**：没有定义对象，血缘只能回答「表相连」，答不出「两个指标的口径是否会分叉」。

**第 5 步：把校验变成资产属性（【经验】与第 4 步同期或之后）**

- 动作：把散落在任务里的校验提炼为挂在资产上的断言，并指定修复责任人。
- **产物**：「资产 → 断言 → 责任人」台账。
- **判据**：人工注入一次脏数据，看它是否在下游使用之前被拦，告警是否落到具体人。
- **为什么必须在这里**：断言的载体是资产；在第 3 步之前它们只能挂在任务上，而挂在任务上的校验会随任务重写而消失。

**第 6 步：时效与消费面升级，并把旧路径退役作为验收项（【经验】12–24 个月）**

- 动作：按「结果是否进在线请求」决定是否建流链路；按「训练与推理是否必须同源」决定是否上特征平台；每次上新同时给出旧路径的下线时间。
- **产物**：流链路 / ML 平台的接入清单 + 旧路径退役计划。
- **判据**：绕行测试——直连明细表、直连模型端点，看是否仍然可达；旧入口是否已关。
- **为什么必须排在最后**：实时与 ML 的收益依赖上游语义资产的完备度；跳到这里而前面缺位，会得到「两条链路各自算一遍」与「模型靠猜表名取数」两种结果。

**最常被跳过的是第 1 步**，因为它没有可见产出（没有平台、没有看板）。跳过的第一个症状不会立刻出现——**通常会在一到两个季度后的第一次「两个数字对不上」时出现**：此时团队能拿出的证据只有各自的 SQL 与各自的看板，而系统里没有任何地方能回答「总共有几份实现」，任何一次口径变更的覆盖率都无法被论证（§3.5 已把这条列为「指标泛滥」的机制后果）。

#### 4.7.5 存量迁移：在已有 Hive + 调度 + 报表的栈上怎么上

**① 先做能立刻见效且可回退的一步**：从**给资产加连接键与 Owner**开始，不动任何线上任务。它可回退（新增字段与登记表，不改读写路径），且立即产生两个可见收益：影响面查询有键可用、无主资产有了清单。**不要以「上平台」起步**——平台上线后补录的历史资产，其历史血缘通常已经无法回填。

**② 历史资产按三类处理**，不要一套规则套全部：

| 类别 | 判据 | 处理方式 |
| --- | --- | --- |
| 会继续被改动的核心资产 | 近一两个季度有下游改动、或被跨团队引用 | **只改「被改动的部分」**：本次改动涉及的字段补血缘、补断言，其余的挂账 |
| 冻结但仍被读取的历史资产 | 只读、无写入、有明确消费方 | **打标挂账**：标为「冻结」，写清读取方与生命周期，避免被当成新资产治理 |
| 无主且无消费方的资产 | Owner 空缺、无下游引用、长期无访问 | **不返工**：走归档或下线流程，不进入治理范围 |

**判据**：三类清单能否在一天内产出；如果产不出，说明连接键还没建好（回到第 1 步）。

**③ 双轨怎么维持、维持多久**：迁移期的双轨是**语义层与直连明细并存、统一入口与旧脚本并存**。维持时长不按时间定，按**下游迁移率**定（【经验】：当引用新路径的消费方占比进入多数区间，且增量工作流已默认走新路径时，旧路径的维护成本才开始低于迁移成本）。维持期内必须做两件事：旧路径的每一次产出都被记录（否则退出双轨时无从判断谁还在用），以及每条新上线的路径都必须带退役计划。

**④ 什么信号说明可以退出双轨**：

- **绕行测试通过**：直连明细表、直连模型端点的调用被拦，或返回的是一个被明确标记为「非权威口径」的结果。
- **旧路径产出归零**：连续一个完整业务周期（含月末与季末这类峰值）没有从旧入口产生的产出。
- **变更可传播**：改一次定义，下游不做人工通知也同步；此时新路径已是唯一权威。

**退不出双轨的典型形态是「版本堆叠而不退役」**：新平台建好，旧入口与直连权限都还在，同一个数字有三条产出通路（§3.5 已列这条反模式）。它的危险不是乱，而是**让每一代的新增能力都无法真正生效**。

#### 4.7.6 模板：把血缘卡在发布流程上

```yaml
# 发布卡点（在合并前运行，而不是上线后告警）
gate:
  trigger: merge_request              # 触发时机：变更进入合并前
  analyze:
    - downstream 血缘遍历（字段级）
    - 受影响资产清单 = 下游表 / 字段 / 指标 / 看板 / Owner
  block_when:                         # 超阈值直接阻断
    - 受影响的下游 Owner 数 >= 3       # 【经验】阈值按组织协作成本设定
    - 变更字段属于「组织级口径」的 source_fields
  require:
    - 每个受影响 Owner 的确认记录（谁在何时确认）
    - 退役 / 兼容计划（若为破坏性变更）
  on_pass: 写入变更审计（变更人 / 时间 / 影响面快照）
```

**怎么用**：`block_when` 的两条阈值必须按你自己的协作成本重设——**判据是「上一次同规模变更实际花了几个团队沟通」**，把它换算成人数，而不是照抄 3。`require` 里的确认记录是这条卡点唯一不可省的字段：没有它，卡点会退化成「点一下继续」。不要照抄 `trigger`，如果你们的发布不走合并流程，就换成发布单或上线审批的对应时点。

#### 4.7.7 自检清单

- [ ] 核心指标的口径，系统里能回答「总共有几份实现」吗？上次口径争议是用「改数字」还是「改结构」结束的？
- [ ] 抽 5 个被跨团队引用的指标，`owner` 字段写的是具体的人还是团队名？写团队名的一律视为无 Owner。
- [ ] 改一次指标定义，下游引用方不做人工通知会同步吗？靠发通知的，覆盖率等于通知触达率。
- [ ] 「改这张表会影响谁」现在要多久回答？把答案按小时还是按天计？按天说明血缘还没有载体。
- [ ] 随机抽 5 行资产登记，`业务含义` 字段最近更新时间在多久以内？超过一个季度即为腐烂。
- [ ] 元数据里的业务含义是自动采集还是人工补的？如果是人工补的，追责到具体人了吗？
- [ ] 你的实时结果会不会在一次在线请求内被读走？不会的话，它的延迟预算换回了什么？
- [ ] 批链路与流链路算同一个指标时，引用的是同一份定义吗？不是的话，哪一份是权威口径，写在哪？
- [ ] 训练用的特征与推理用的特征，是同一份定义的产物吗？推理 trace 里有没有记录当时取到的特征快照？
- [ ] 质量校验是资产的属性还是任务里的代码？人工注入一次脏数据，它是被上游拦住还是被下游用户发现？
- [ ] 通往明细表、模型端点的直连权限还在吗？新平台上线的同时，旧路径的退役时间写进验收项了吗？
- [ ] 如果明天要让模型自助取数，它能不能只靠元数据回答「用哪张表、哪个字段、会影响谁」？

> 本节小结：七项决策里真正不可替代的是**第一项——把口径从「查询结果」变成「可被引用的定义对象」**。因为后面六项都在消费同一个前提：元数据要挂资产、血缘要连定义、断言要有载体、模型要有权威字段可读；**没有定义对象时，这些机制各自长出一套口径，事后再归一要用改结构的成本来还**。它之所以比其余环节更值得投入，是因为它是唯一一件「做晚了无法回填」、且每一分投入都会被后续所有机制重复引用的事。
>
> 💡 **思考锚点**：数一下你组织里被引用最广的那个口径，每周被几个团队引用——个位数时中心语义层摊不薄；再改一次它的口径，看下游引用处是不做人工通知也自动同步，还是要有人挨个去改报表。如果答案是后者，你现在缺的是「可被引用的定义对象」本身，还是五要素里的某一项？
