## 5. 踩坑与教训

### 5.1 坑 1：指标泛滥（Indicator Sprawl）

**问题**：2015 年 Airbnb 内部"GMV"在 50 个团队有 50 种定义，**每月仲裁指标冲突耗费 200+ 小时**。

**根因**：

- 没有统一指标定义。
- 每个团队自由定义指标。
- 没有指标审批流程。

**教训**：

- **指标必须集中管理**——必须有指标平台。
- **必须有指标 Owner**——每个指标有唯一 Owner。
- **必须有指标审批流程**——新指标必须审批。

**修正**：Minerva 平台 + 指标治理委员会。

### 5.2 坑 2：元数据"陈旧"

**问题**：2017 年 Airbnb Dataportal V1 出现"元数据陈旧"问题——表的元数据与实际表不一致。

**根因**：

- 元数据采集依赖手动同步。
- 表 Schema 变更后未及时更新。
- 没有自动同步机制。

**教训**：

- **元数据必须自动采集**——不能依赖手动。
- **必须有"元数据陈旧"监控**。
- **必须有"自动修复"机制**。

**修正**：Dataportal V2 引入"自动同步 + 自动修复"。

### 5.3 坑 3：实时数仓"延迟抖动"

**问题**：2019 年 Airbnb 实时数仓 P99 延迟 5 秒，偶尔抖动到 30 秒。

**根因**：

- Kafka 消费不及时。
- Flink 反压。
- Druid 写入慢。

**教训**：

- **实时数仓必须有 SLA**——P99 延迟必须 < 1 秒。
- **必须有"延迟监控"**——实时告警。
- **必须有"分级降级"机制**——延迟过大时降级。

**修正**：Airbnb 引入"实时数仓 SLA"分级（L1 / L2 / L3）。

### 5.4 坑 4：ML Platform "环境不一致"

**问题**：2020 年 Airbnb ML Platform 出现"开发环境与生产环境不一致"问题——模型在本地训练效果好，部署后效果差。

**根因**：

- 本地 Python 环境与生产环境不一致。
- 训练数据与推理数据不一致。
- 没有"环境镜像"机制。

**教训**：

- **必须有"环境镜像"**——本地 + 生产环境一致。
- **必须有"训练 - 推理一致性"保障**。

**修正**：Bighead V2 引入"环境镜像 + 特征回填"。

### 5.5 坑 5：AI Native 推进缓慢

**问题**：2023 年大模型爆发后，Airbnb AI Native 数据栈推进缓慢。

**根因**：

- 数据团队对 AI 不熟悉。
- AI 团队对数据栈不熟悉。
- 文化阻力。

**教训**：

- **AI Native 不是"一次性升级"**——是渐进式演进。
- **必须建立"数据 + AI"双向团队**。
- **必须有"AI Native PoC"**——先试点。
