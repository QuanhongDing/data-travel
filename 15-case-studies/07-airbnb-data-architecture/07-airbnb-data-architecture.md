## 1. 背景

### 1.1 公司 / 业务 / 时间

Airbnb 成立于 2008 年，至今 17 年。数据架构演进的关键时间节点：

- **2008–2012：起步阶段**。从 MySQL + Ruby on Rails 起步，数据栈简单。
- **2013：数据基础设施立项**。开始系统化建设数据栈。
- **2014：Airflow 立项 + 开源**。Airbnb 自研工作流调度，2015 开源。
- **2015：Minerva 立项**。开始研发指标平台。
- **2016：Minerva V1 + Dataportal V1**。
- **2017：Airbnb Data University 成立**。开始系统化培养数据文化。
- **2018：Minerva V2 + Dataportal V2**。
- **2019：Minerva 全面铺开**。Airbnb 内部所有 BI 报表基于 Minerva。
- **2020：疫情冲击 + 远程办公适应**。
- **2021：Dataportal 成为元数据核心**。
- **2022：ML Platform V3（Bighead）+ 实时数仓**。
- **2023：数据质量平台 + GenAI 应用**。
- **2024：AI Native 数据栈**。
- **2025：实时 AI + Agent 化数据**。

### 1.2 行业与监管

- **共享住宿行业**：监管复杂（许多城市对短租有严格法规）。
- **金融监管**：Airbnb 支付合规要求严格。
- **数据合规**：GDPR / CCPA / 全球多法域。
- **等保**：对外服务合规要求。

### 1.3 团队规模与组织

- **Airbnb 数据团队**约 **500+ 人**。
- **数据平台部**：约 100+ 人。
- **数据分析部**：约 200+ 人。
- **数据科学家**：约 100+ 人。
- **业务数据分析师**：约 100+ 人。
- **组织文化**：**"数据科学家 + 协作"** + **"Belong Anywhere"**（文化包容）+ **"Chinless"（去层级化）**。

## 2. 挑战

### 2.1 业务挑战

#### 2.1.1 双边市场与全球化

Airbnb 是典型的双边市场——房客 + 房东，跨 220+ 国家运营。

#### 2.1.2 业务多形态

房客住宿、Experiences（体验）、餐厅预订、长租——业务多样化。

#### 2.1.3 季节性峰值

夏季、节假日、特殊活动期间，Airbnb 流量峰值是日常的 5–10 倍。

#### 2.1.4 用户体验敏感

房客 + 房东对"信息一致性"敏感——同一房源在不同国家 / 不同时间显示必须一致。

### 2.2 技术挑战

#### 2.2.1 海量数据

- 全球 1.5 亿+ 用户。
- 700 万+ 房源。
- 日均数百万次预订。

#### 2.2.2 元数据治理难题

2015 年以前 Airbnb 内部有"指标泛滥"——"GMV"在 50 个团队有 50 种定义。

#### 2.2.3 实时数据

- 房客实时搜索。
- 房东实时定价。
- 实时推荐。

#### 2.2.4 数据质量

Airbnb 对"数据质量"要求极高——一个错误的房源价格可能让房东损失大量订单。

### 2.3 组织挑战

#### 2.3.1 数据驱动文化

Airbnb 是"数据驱动文化"的代表公司，所有决策必须基于数据。

#### 2.3.2 数据科学家协作

100+ 数据科学家需要高效协作——共享工具、共享数据、共享最佳实践。

#### 2.3.3 跨团队数据共享

Airbnb 内部有 50+ 团队需要共享数据——必须有"中央协作层"。

**Airflow 核心**：

- **Python 优先**：用 Python 写 DAG。

- **可视化**：Web UI 可视化 DAG。

**Minerva 立项背景**：

## 4. 关键决策

### 4.1 决策 1：为什么 Minerva？

#### 4.1.1 决策路径

- **方案 A：传统 BI 工具**——Tableau / Looker。
  - 优点：成熟。
  - 缺点：指标定义分散，无法治理。
- **方案 B：自研指标平台**（Minerva）——统一指标定义。
  - 优点：指标集中、口径统一。
  - 缺点：开发成本高。
- **方案 C：商业指标平台**——如 Looker / Sisense。
  - 优点：快速。
  - 缺点：定制化能力弱。

**决策**：自研 Minerva。

#### 4.1.2 Minerva 核心

```
[指标定义] → [OLAP 引擎] → [BI / API]
   (元数据)   (Presto /      (消费)
              Druid)
```

- **指标定义**：每个指标有"业务定义 + 计算逻辑 + 数据来源 + Owner + 版本"。
- **指标分类**：
  - 原子指标（不可拆分）。
  - 派生指标（基于原子指标计算）。
  - 复合指标（多个原子指标组合）。
- **指标血缘**：从指标可以追溯到 Hive 表。

#### 4.1.3 Minerva 价值

- **统一口径**：所有指标有唯一来源。
- **自助分析**：业务分析师可以自助使用指标。
- **变更追溯**：指标变更可追溯。

### 4.2 决策 2：为什么 Dataportal？

#### 4.2.1 Dataportal 定位

Dataportal 是 Airbnb 的元数据管理平台，是 Minerva / 数据地图 / 数据血缘的核心。

#### 4.2.2 核心能力

- **数据目录**：所有数据资产注册到 Dataportal。
- **数据血缘**：从 Hive 表到指标的可视化血缘。
- **数据 Owner**：每个数据集有 Owner。
- **数据 SLA**：每个数据集有 SLA。
- **数据质量**：集成数据质量监控。

#### 4.2.3 Dataportal 架构

```
[数据资产] → [Dataportal 注册] → [统一目录] → [业务使用]
   (Hive)     (元数据采集)        (可视化)     (消费)
```

#### 4.2.4 Dataportal 价值

- **数据可发现**：分析师可以快速找到需要的数据。
- **数据可治理**：数据 Owner 明确，治理有抓手。
- **数据可信任**：基于血缘 + 质量，数据可信任。

### 4.3 决策 3：ER 模型与维度建模

#### 4.3.1 ER 模型

Airbnb 使用 ER 模型定义业务实体：

- **核心实体**：用户 / 房源 / 预订 / 房东 / 评论。
- **实体关系**：用户 - 预订 - 房源、房东 - 房源、用户 - 评论。

#### 4.3.2 维度建模

基于 ER 模型构建维度模型：

- **DWD 层**：基于 ER 实体的明细数据。
- **DWS 层**：基于主题域的聚合数据。
- **ADS 层**：基于业务场景的应用数据。

#### 4.3.3 关键经验

- **ER 模型必须稳定**——核心实体（如用户、房源）的定义不能频繁变化。
- **维度建模必须灵活**——支持业务快速变化。
- **ER 与维度模型必须联动**——ER 是"骨架"，维度模型是"肌肉"。

### 4.4 决策 4：实时数据架构

#### 4.4.1 实时场景

- 实时搜索。
- 实时定价。
- 实时推荐。
- 实时反欺诈。

#### 4.4.2 实时架构

```
[业务事件] → [Kafka] → [Flink / Spark Streaming] → [Hive / Druid] → [在线服务]
```

#### 4.4.3 关键技术

- **Kafka**：事件流。
- **Flink / Spark Streaming**：实时计算。
- **Druid**：实时 OLAP。
- **Iceberg**：表格式（2022 后）。

### 4.5 决策 5：ML Platform（Bighead）

#### 4.5.1 Bighead 架构

```
[数据] → [特征] → [训练] → [部署] → [推理]
```

#### 4.5.2 核心模块

- **Deep Learning**：基于 TensorFlow / PyTorch。
- **Classical ML**：基于 Spark MLlib / scikit-learn。
- **Feature Store**：基于 Hive + Redis。
- **Model Serving**：基于 Kubernetes。
- **Notebook**：基于 Jupyter + 内部工具。

#### 4.5.3 Bighead 应用

- **搜索**：实时搜索排序。
- **推荐**：房源推荐。
- **定价**：智能定价。
- **反欺诈**：实时反欺诈。

### 4.6 决策 6：数据质量保障

#### 4.6.1 数据质量维度

- **准确性**：数据值是否正确。
- **完整性**：数据是否缺失。
- **一致性**：数据是否一致。
- **及时性**：数据是否及时。
- **唯一性**：数据是否重复。

#### 4.6.2 数据质量工具

- **断言（Assertions）**：每个数据集有断言规则。
- **监控**：实时监控 + 告警。
- **修复**：自动 / 人工修复。

#### 4.6.3 数据质量流程

- **事前**：数据进入前校验。
- **事中**：数据处理中校验。
- **事后**：数据入库后校验。

#### 4.7.1 Airflow 核心

#### 4.7.2 Airflow 价值

## 5. 踩坑与教训

### 5.1 坑 1：指标泛滥（Indicator Sprawl）

**问题**：2015 年 Airbnb 内部"GMV"在 50 个团队有 50 种定义，**每月仲裁指标冲突耗费 200+ 小时**。

**根因**：

- 没有统一指标定义。
- 每个团队自由定义指标。
- 没有指标审批流程。

**教训**：

- **指标必须集中管理**——必须有指标平台。
- **必须有指标 Owner**——每个指标有唯一 Owner。
- **必须有指标审批流程**——新指标必须审批。

**修正**：Minerva 平台 + 指标治理委员会。

### 5.2 坑 2：元数据"陈旧"

**问题**：2017 年 Airbnb Dataportal V1 出现"元数据陈旧"问题——表的元数据与实际表不一致。

**根因**：

- 元数据采集依赖手动同步。
- 表 Schema 变更后未及时更新。
- 没有自动同步机制。

**教训**：

- **元数据必须自动采集**——不能依赖手动。
- **必须有"元数据陈旧"监控**。
- **必须有"自动修复"机制**。

**修正**：Dataportal V2 引入"自动同步 + 自动修复"。

### 5.3 坑 3：实时数仓"延迟抖动"

**问题**：2019 年 Airbnb 实时数仓 P99 延迟 5 秒，偶尔抖动到 30 秒。

**根因**：

- Kafka 消费不及时。
- Flink 反压。
- Druid 写入慢。

**教训**：

- **实时数仓必须有 SLA**——P99 延迟必须 < 1 秒。
- **必须有"延迟监控"**——实时告警。
- **必须有"分级降级"机制**——延迟过大时降级。

**修正**：Airbnb 引入"实时数仓 SLA"分级（L1 / L2 / L3）。

### 5.4 坑 4：ML Platform "环境不一致"

**问题**：2020 年 Airbnb ML Platform 出现"开发环境与生产环境不一致"问题——模型在本地训练效果好，部署后效果差。

**根因**：

- 本地 Python 环境与生产环境不一致。
- 训练数据与推理数据不一致。
- 没有"环境镜像"机制。

**教训**：

- **必须有"环境镜像"**——本地 + 生产环境一致。
- **必须有"训练 - 推理一致性"保障**。

**修正**：Bighead V2 引入"环境镜像 + 特征回填"。

### 5.5 坑 5：AI Native 推进缓慢

**问题**：2023 年大模型爆发后，Airbnb AI Native 数据栈推进缓慢。

**根因**：

- 数据团队对 AI 不熟悉。
- AI 团队对数据栈不熟悉。
- 文化阻力。

**教训**：

- **AI Native 不是"一次性升级"**——是渐进式演进。
- **必须建立"数据 + AI"双向团队**。
- **必须有"AI Native PoC"**——先试点。

## 6. 复用经验

### 6.1 适合谁学

#### 6.1.1 强数据驱动文化的公司

- **典型**：Airbnb、Netflix、字节。
- **原因**：Minerva / Dataportal 需要文化支撑。

#### 6.1.2 指标密集型业务

- **典型**：电商、金融、SaaS。
- **原因**：指标治理价值巨大。

#### 6.1.3 数据科学家 + 业务分析师协同

- **典型**：中型 + 大型公司。
- **原因**：数据科学家友好平台价值大。

#### 6.1.4 强数据合规需求

- **典型**：金融、医疗、跨境业务。
- **原因**：Dataportal 元数据治理成熟。

### 6.2 不适合谁学

#### 6.2.1 数据规模小的初创公司

- **反例**：日活 < 100 万。
- **原因**：Minerva / Dataportal 复杂度过高。

#### 6.2.2 弱数据驱动文化的公司

- **反例**：传统企业凭经验决策。
- **原因**：没有文化支撑，平台无人用。

#### 6.2.3 单一业务线

- **反例**：单业务 B 端 SaaS。
- **原因**：元数据治理投入产出比低。

### 6.3 关键可复用资产

#### 6.3.1 开源项目

## 7. 与同类案例对比

### 7.1 对比维度

| 维度 | Airbnb | Netflix | Uber | 美团 |
| --- | --- | --- | --- | --- |
| 主导思想 | 数据科学家友好 + 元数据治理 | 数据自由 + 自治 | Marketplace + 实时 | 业务落地 + 全栈 |
| 调度 | Airflow | Maestro | Airflow | Catmaid / Dolphin |
| 指标平台 | Minerva | 内部 | 内部 | Quick BI / Quick Audience |
| 元数据 | Dataportal | 内部 | 内部 | 内部 |
| 表格式 | Iceberg | Iceberg | Hudi | Iceberg |
| 实时 | Kafka + Spark | Kafka + Flink | Kafka + Flink | Kafka + Flink |

### 7.2 取舍

- **Airbnb = 数据科学家友好 + 治理成熟**——把"指标 + 元数据"做到极致。
- **Netflix = 数据自由 + 自治**——给团队最大灵活度。
- **Uber = Marketplace 实时性**——把实时性做到极致。
- **美团 = 业务落地 + 全栈**——把 ML 工程化做成基础设施。

**对架构师的启示**：

- **学 Minerva 思路**——指标集中管理是普适需求。
- **学 Dataportal 思路**——元数据治理是普适需求。
- **学 Airflow 思路**——工作流调度的"Python 优先"理念。
- **学"ER + 维度模型"思路**——核心实体稳定 + 维度灵活。
