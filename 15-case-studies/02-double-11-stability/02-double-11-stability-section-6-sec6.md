### 2.1 阿里"**双 11 订单峰值 60 万笔/秒 10+ 年**"（2013-2024）

**背景（Why）**

阿里 2013 年面临**峰值对系统架构的终极压力测试**：
- **订单峰值从 10 万笔/秒向百万级演进**——**单机房单集群架构有物理上限**
- **零点脉冲**——**5 分钟内涌入全天 15% 流量，是平均值的数十倍**
- **不能降级核心链路**——**下单 / 支付降级等于业务失败**

**触发点（What）**

2013 年阿里把**双 11 稳定性**作为年度技术战役（[阿里双 11 技术博客 2013-2024]），目标：
- **60 万笔/秒**——峰值承载
- **0 事故**——不允许 P0
- **6 个月备战**——把不确定性压到最低

**详细做法（How）**

阿里双 11 稳定性的**5 大核心组件**：

1. **6 个月备战节奏（核心创新）**
   - 关键设计：**6 月启动 → 9 月全链路压测 → 10 月预案演练 → 11 月大促，每阶段有通关标准**
   - 关键能力：**把"大促当天靠运气"变成"分阶段消灭不确定性"**
   - 关键数字：**6 个月、4 个里程碑**
   - 关键示意：
     ```text
     双 11 备战时间线（每阶段必须通关才进下一阶段）
     6 月  容量规划：业务漏斗建模 → 预估 7x 峰值 → 资源下单
     7-8 月 系统改造：单元化扩容 / 限流阈值调整 / 缓存预热方案
     9 月  全链路压测：生产环境真实流量打到 7x，暴露瓶颈并修复
     10 月 预案演练：100+ 预案逐个演练（含机房级 Chaos）
     11/11 大促：现场作战室 + 5 分钟响应 + 灰度放量
     ```

2. **全链路压测（核心）**
   - 关键设计：**生产环境 + 真实数据 + 影子标识（压测流量与真实流量隔离但共用链路）**
   - 关键能力：**能压到 7x 而不污染真实数据，测试与生产环境差异归零**
   - 关键数字：**7x 流量、P99 全链路可见**

3. **异地多活 + 单元化（核心）**
   - 关键设计：**3 地 5 中心 + user_id 哈希单元化**
   - 关键能力：**单机房故障 5 分钟切走，单元内闭环避免跨机房放大**
   - 关键数字：**爆炸半径 < 1%**

4. **100+ 预案与自动切流（核心）**
   - 关键设计：**每个已知风险点一个预案；健康探测触发自动切流，5 分钟内完成**
   - 关键能力：**故障靠机制不靠人电话通知**
   - 关键数字：**100+ 预案、5 分钟切流**

5. **限流削峰与降级分级（核心创新）**
   - 关键设计：**限流分层（入口 / 服务 / 依赖）+ 降级分级（P0 不降 / P2 可降）**
   - 关键能力：**优先保住核心链路，牺牲非核心**
   - 关键数字：**P0 降级 0 次**

**阿里双 11 关键数字**（[阿里双 11 技术博客 2013-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**订单峰值**」** | 10 万笔/秒 | 60 万笔/秒 | **+500%** |
| **「**全链路压测**」** | 不可用 | 7x 生产环境真实压测 | **∞** |
| **「**爆炸半径**」** | 100% | < 1% | **-99%** |
| **「**切流时间**」** | 小时级（人工） | < 5 分钟 | **-95%** |
| **「**预案数**」** | 10+ | 100+ | **+900%** |
| **「**备战周期**」** | 1 个月 | 6 个月 | **6x** |
| **「**P0 事故**」** | 每次 1-2 起 | 0 | **-100%** |
| **「**核心链路降级**」** | 偶发 | 0 次 | **-100%** |

**具体数字（How much）**

- 团队规模：阿里双 11 稳定性团队 200+ 人（含中间件 / SRE / 业务）
- 关键数字：**60 万笔/秒**；**7x 压测**；**爆炸半径 < 1%**；**100+ 预案**；**6 个月备战**
- 业务影响：覆盖**双 11 全场景**，并沉淀为对外输出的高可用方法论

**失败教训**

- 早期「**只压 3x**」——真实 7x 时缓存击穿，倒逼**「生产环境 7x 全链路真实压测」**
- 「**单机房扛峰值**」——机房级故障直接全站停摆，倒逼**「3 地 5 中心 + 单元化」**
- 「**故障靠人电话通知**」——切流要 1 小时，倒逼**「健康探测自动切流 < 5 分钟」**
- 「**不区分降级优先级**」——大促时把交易链路限流了，倒逼**「限流分层 + 降级分级，P0 永不降」**

### 2.2 阿里"**双 11 7x 平滑与 GMV 增长**"（2018-2024）

**背景（Why）**

阿里 2018 年面临**稳定性与业务增长的耦合**：
- **稳定性不能只保"不挂"**——**要保"7x 流量下业务指标不降"**
- **GMV 是最终裁判**——**系统没挂但转化率掉了，等于失败**
- **技术团队与业务团队目标分歧**——**技术要稳，业务要冲**

**触发点（What）**

2018 年阿里把**"7x 平滑 + GMV 增长"**作为双 11 的统一目标（[阿里双 11 技术博客 2018-2024]），目标：
- **7x 流量下 GMV 年增 30%+**
- **系统指标与业务指标同时通关**
- **技术投入直接对应业务收益**

**详细做法（How）**

阿里 7x 平滑的**5 大核心组件**：

1. **业务漏斗建模驱动的容量规划（核心创新）**
   - 关键设计：**从流量入口到成交逐层建模，每层的流失率与峰值系数都要实测**
   - 关键能力：**容量投在哪一层最影响 GMV，一眼可见**
   - 关键数字：**漏斗 8 层、峰值系数实测**
   - 关键示意：
     ```text
     大促漏斗与容量优先级（示例）
     入口流量 1.0x  ──►  详情页 0.6x  ──►  加购 0.25x ──►  下单 0.15x ──►  支付 0.12x
       限流宽松        限流中等         重点保障       强保障        最强保障
       ↑ 可牺牲         ↑ 可降级          ↑ 缓存命中 95%+  ↑ 不降级      ↑ 不降级
     结论：容量与稳定性预算优先投向后三层，因为直接决定 GMV
     ```

2. **转化率与稳定性联动监控（核心）**
   - 关键设计：**把转化率纳入稳定性 SLO**——转化率掉 1% 即等同故障告警
   - 关键能力：**避免"系统指标全绿但业务在流血"**
   - 关键性质：**转化率纳入 SLO**

3. **自适应扩容（核心）**
   - 关键设计：**按漏斗各层实测 QPS 弹性扩缩，而非全链路等比例扩**
   - 关键能力：**成本花在刀刃上**
   - 关键数字：**资源利用 +40%**

4. **缓存分层与预热（核心）**
   - 关键设计：**本地 / Redis / CDN 三层 + 大促前全量预热**
   - 关键能力：**把峰值读数挡在数据库之外**
   - 关键数字：**命中率 99%+、DB QPS -90%**

5. **灰度放量与实时调参（核心创新）**
   - 关键设计：**零点前按 1% / 10% / 50% / 100% 灰度放量，全程看板观察转化率**
   - 关键能力：**问题在 1% 流量时就发现，而不是 100% 时**
   - 关键数字：**4 级灰度**

**阿里 7x 平滑关键数字**（[阿里双 11 技术博客 2018-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**流量承载**」** | 3x | 7x | **+133%** |
| **「**GMV**」** | 基线 | 年增 30%+ | **+30%** |
| **「**转化率 SLO**」** | 未纳入 | 纳入且不掉 | **∞** |
| **「**缓存命中率**」** | 90% | 99%+ | **+10%** |
| **「**DB QPS**」** | 基线 | -90% | **-90%** |
| **「**资源利用率**」** | 基线 | +40% | **+40%** |
| **「**灰度级数**」** | 1 级（直接全量） | 4 级 | **4x** |
| **「**漏斗建模层数**」** | 0 | 8 层 | **∞** |

**具体数字（How much）**

- 团队规模：阿里双 11 稳定性 + 业务团队 500+ 人协同
- 关键数字：**7x 平滑**；**GMV +30%**；**缓存命中 99%+**；**DB QPS -90%**
- 业务影响：覆盖双 11 全场景，稳定性投入可直接换算为 GMV 增量

**失败教训**

- 早期「**唯系统指标论**」——系统全绿但转化率掉了 3%，业务方不认，倒逼**「转化率纳入 SLO」**
- 「**全链路等比例扩容**」——入口扩容了但下单层不够，GMV 上不去，倒逼**「漏斗建模驱动的分层扩容」**
- 「**缓存不预热**」——零点第一波请求直接打穿 DB，倒逼**「三层缓存 + 大促前全量预热」**
- 「**直接全量放量**」——问题在 100% 流量时才暴露，倒逼**「零点前 4 级灰度放量」**

### 2.3 字节"**抖音春晚红包 5 亿+ 互动**"（2019-2024）

**背景（Why）**

字节 2019 年面临**分钟级脉冲型极限压力**：
- **春晚 5 亿+ 互动**——**流量集中在除夕 20:00-24:00 的几分钟脉冲内**
- **红包业务天然是"抢"**——**用户重复点击、脚本刷量，QPS 远超真实用户数**
- **一次失误全网可见**——**春晚是全国直播，卡顿即舆情**

**触发点（What）**

2019 年字节承接**抖音春晚红包**（[字节技术博客 2019-2024]），目标：
- **5 亿+ 互动**
- **春晚 0 事故**
- **P99 < 100ms**

**详细做法（How）**

字节春晚红包的**5 大核心组件**：

1. **3 个月备战（核心创新）**
   - 关键设计：**10 月启动 → 12 月全链路压测 → 1 月预案演练 → 除夕**
   - 关键能力：**把不可复现的春晚流量，用历史相似峰值反复逼近**
   - 关键数字：**3 个月、P99 目标 < 100ms**
   - 关键示意：
     ```text
     春晚流量特征与对策
     特征 1：脉冲 —— 主持人口播后 10 秒内涌入千万级请求
       → 对策：入口静态化 + CDN 承载 95% 流量
     特征 2：重复 —— 同一用户连点 20 次
       → 对策：幂等 key + 本地去重 + 限流保护
     特征 3：峰值不可预测 —— 依赖口播时点
       → 对策：准备"随时可切"的弹性容量池 + 一键扩容
     ```

2. **CDN + 边缘静态化（核心）**
   - 关键设计：**红包页 / 活动页全静态化推到边缘**
   - 关键能力：**95% 流量不进源站**
   - 关键数字：**P99 < 100ms、源站压力 -95%**

3. **Redis 集群 + 预热（核心）**
   - 关键设计：**红包库存 / 用户状态全部预热进 Redis 集群，多级分片**
   - 关键能力：**千万级 QPS 读写在内存完成**
   - 关键数字：**千万级/秒**

4. **消息队列削峰（核心）**
   - 关键设计：**领红包走异步：同步只返回"已受理"，异步发放并通知**
   - 关键能力：**把脉冲削平为可消费的流**
   - 关键数字：**5 亿+ 互动 0 丢失**

5. **幂等 + 灰度放量（核心创新）**
   - 关键设计：**每用户每活动唯一幂等 key；除夕当晚按分钟级灰度放量**
   - 关键能力：**重复点击不重复发放；问题可即时收敛**
   - 关键数字：**重复发放 0、0 事故**

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**互动量**」** | 1 亿 | 5 亿+ | **+400%** |
| **「**P99 延迟**」** | 500ms | < 100ms | **-80%** |
| **「**源站压力**」** | 基线 | -95%（CDN 承载） | **-95%** |
| **「**Redis 吞吐**」** | 不可用 | 千万级/秒 | **∞** |
| **「**重复发放**」** | 基线 | 0 | **-100%** |
| **「**春节事故**」** | 1 起 | 0 | **-100%** |
| **「**备战周期**」** | 1 个月 | 3 个月 | **3x** |
| **「**用户规模**」** | 不可用 | 6 亿+ | **∞** |

**具体数字（How much）**

- 团队规模：字节春晚红包专项团队 500+ 人
- 关键数字：**5 亿+ 互动**；**P99 < 100ms**；**源站压力 -95%**；**重复发放 0**
- 业务影响：覆盖抖音 6 亿+ 用户，除夕当天的全国级流量事件

**失败教训**

- 「**灰度只做功能不做流量**」——除夕零点多地同时切全量，倒逼**「分钟级灰度放量 + 一键回退」**

### 2.4 腾讯"**春节红包 13 亿+ 用户**"（2016-2024）

**背景（Why）**

腾讯 2016 年面临**社交裂变放大后的超大规模**：

- **红包与支付强绑定**——**失败即资金体验事故，监管敏感**
- **连续多年春晚独家**——**稳定性成为年度公众承诺**

**触发点（What）**

- **13 亿+ 用户可用**
- **春节 0 事故**
- **资金链路 100% 准确**

**详细做法（How）**

腾讯春节红包的**5 大核心组件**：

   - 关键设计：**8 月启动 → 11 月压测 → 1 月演练 → 除夕作战室；跨部门统一指挥**
   - 关键能力：**把"多团队协同"本身当作需要演练的系统能力**
   - 关键数字：**6 个月、跨部门作战室**
   - 关键示意：
     ```text
     春节红包作战室（除夕当晚）
     ```

   - 关键能力：**资金零差错，可实时发现不平**
   - 关键数字：**资金准确率 100%**

3. **CDN + 边缘 + 客户端缓存（核心）**

4. **Redis 集群 + 库存分段（核心）**
   - 关键设计：**红包库存分段（每段独立锁）+ 预热**
   - 关键能力：**消除单 key 热点**
   - 关键数字：**千万级/秒**

   - 关键设计：**按"影响资金 > 影响体验 > 影响非核心"分级，逐级降级**
   - 关键能力：**降级优先级事先定义好，当晚不争论**
   - 关键数字：**100+ 预案、资金链路 0 降级**

- 业务影响：覆盖微信 13 亿+ 用户，是年度最高等级的技术保障事件

**失败教训**

- 早期「**各团队各自备战**」——跨部门协同在当晚成为瓶颈，倒逼**「跨部门作战室 + 统一指挥」**
- 「**库存单 key 热点**」——爆款红包把单个 Redis key 打爆，倒逼**「库存分段 + 独立锁」**
- 「**资金链路无实时对账**」——差错要 T+1 才发现，倒逼**「双账本 + 实时对账」**
- 「**降级优先级未定义**」——当晚争论"能不能降这个"，倒逼**「提前分级，资金链路永不降」**

### 2.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**全链路压测 + 缓存预热**」（**最简单**）——**1 个业务、3x 目标**
- 产出：**压测方案（含影子标识）+ 三层缓存 + 预热脚本**
- 团队：**2-3 人**
- 验证标准：**生产环境压到 3x 无瓶颈**、**缓存命中率 ≥ 95%**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 业务 / 7x 目标**」
- 引入「**异地多活 + 单元化**」——单机房故障可切，爆炸半径收敛
- 引入「**限流分层 + 降级分级**」——P0 链路永不降
- 团队：5-10 人
- 验证标准：**爆炸半径 ≤ 33%**、**切流 < 5 分钟**、**P0 降级 0 次**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务 / 分钟级脉冲**」
- 引入「**100+ 预案 + 自动切流**」——故障靠机制不靠人
- 引入「**异步削峰（MQ）+ 幂等保护**」——脉冲削平、重复不发放
- 团队：10-30 人
- 验证标准：**预案覆盖 100%**、**重复发放 0**、**0 事故**

**100 → 1000 阶段：12-24 个月**

- 引入「**6 个月备战节奏 + 跨部门作战室**」——把协同本身当作可演练能力
- 引入「**业务指标纳入 SLO（转化率 / 资金准确率）**」
- 团队：30-100 人（跨部门协同）
- 验证标准：**GMV/互动量同比正增长**、**资金准确率 100%**、**核心链路降级 0 次**

### 2.7 ROI 评估（4 个公司真实数据）

**关键投资回报**：
- **直接节省**：「**0 事故 + 爆炸半径 -99%**」——**一次大促级 P0 事故的损失（GMV 流失 + 品牌 + 赔付）即千万级到亿级起**，且除夕 / 双 11 这类节点的舆情影响不可逆
- **业务价值**：「**7x 平滑 + GMV +30%**」——**稳定性不是成本中心而是收入放大器**：能承载 7x 才能承接 7x 的生意，容量规划直接决定大促 GMV 上限
- **AI 时代关键**：「**全链路压测 + 异步削峰 + 幂等**」——**LLM 服务同样面临脉冲型流量（某模型爆火 / 某功能刷屏）**，且推理成本远高于传统读写，异步削峰与限流分层是同一套解法

> **本节小结**：
> - 4 个真实案例（阿里双 11 / 阿里 7x / 字节春晚 / 腾讯春节）印证：**大促稳定性不是「压一压」，是「6 个月备战 + 全链路真实压测 + 异地多活 + 100+ 预案 + 业务指标纳入 SLO」5 件套**。
> - 关键时间线：阿里 10+ 年 / 字节 5+ 年 / 腾讯 8+ 年 —— **大促稳定性是 5+ 年长期工程**，且每一年都是对上一年的压力测试升级。
> - 选型第一原则：「**全链路压测 + 缓存预热**」（**最简单**）——**1 个业务、3x** → 「**异地多活 + 单元化 + 限流降级分级**」（**必须**）→ 「**100+ 预案 + 自动切流 + 异步削峰 + 幂等**」（**生产**）→ 「**6 个月备战 + 作战室 + 业务指标纳入 SLO**」（**AI 时代**）。
> - 99% 的失败来自「**单点故障 + 压测倍率不足 + 预案缺失 + 唯系统指标论**」——必须有 **3 地 5 中心 + 生产环境 7x 压测 + 100+ 预案 + 业务指标纳入 SLO**。
> - 真正的 ROI 来自「**0 事故 + 7x 平滑 + GMV +30% + 13 亿+ 用户**」——是**大厂核心高可用基础设施的命脉**，也是收入的上限。
