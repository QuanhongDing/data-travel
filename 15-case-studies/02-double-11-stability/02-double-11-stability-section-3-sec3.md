## 3. 架构演进

> **证据档位**：本节凡标【公开】处，均给出来源类型与年份；【推算】给出推导链；**沿用本案例材料的数字一律按【经验】使用——只取量级、不取精确值**，并在需要处给出可自行核验的方向。**「未能核到」既不构成「不存在」，也不构成「是真的」**，请按所给方向自行判定。

### 3.1 先看约束：稳定性不是「不出故障」，是「让故障的影响面有界」

**先划清本节与相邻小节的分工**：主文件 §1 给业务形态与团队规模，§2 给业务 / 技术 / 组织三组挑战，§4 给每一次选择的方案对比，§6 给可复用的做法。本节只回答一个问题：**这五代稳定性架构，各自是被哪条约束逼出来的**——不是「阿里依次做了这五件事」，而是「什么条件下只有这一条路可走」。

把大促稳定性写成能力清单，最坏的后果是让人以为这些能力可以按顺序照抄。**能力清单不是路线图，是约束的刻度。** 单元化之所以成立，前提是链路里已经有「跨系统依赖」这件事、单机房的故障半径已经不可接受；如果没有这个前提，直接做单元化只会得到一套业务改造成本极高、故障半径却没真正缩小的系统。同理，平台化（限流 / 熔断 / 降级 / 混沌工程）之所以值得建，前提是组织的故障场景已经多到「每次靠人写预案」覆盖不住；没有这个前提，限流组件只是一个没人标定阈值的开关库。

有一条约束在本案例里贯穿始终，值得先说：**可用性的时间点是外生且公开的**。零点不可推迟、大促日期不可协商、可用性承诺对外公开——**所以任何准备工作都必须在 T-0 之前完成，T-0 当天没有修复窗口**。这条约束解释了为什么本案例的建设重心始终偏向「提前验证」（全链路压测、容量基线、故障演练、预案分级），而不是偏向「故障后快速恢复」——**因为在这个场景里，恢复速度再快也已经迟了；能救场的只有「故障不发生」或「故障的影响面已经被预先圈小」**。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 峰值的可预测性（单日脉冲 vs 多波次 + 直播热点） | 容量准备方式是「预估 + 预留」还是「弹性 + 限流」 | 「上了云就该弹性伸缩」——零点峰值的斜率超过弹性伸缩「观测 → 决策 → 拉起」的周期，弹性救不了这一分钟 |
| 时间点是外生的（零点不可推迟） | 所有验证必须在 T-0 前完成：压测、演练、容量基线、值班 | 「线上发现问题随时修」——大促当天的修复窗口约等于零，能改的只有开关 |
| 故障是概率事件，不是异常 | 目标是限制故障半径，而不是消灭故障 | 「把单机可用性做高就够了」——200+ 系统的串联可用性是乘法，单点做得再好也扛不住相乘 |
| 影响面由依赖关系决定 | 隔离（单元化 / 降级）是主线，加机器是支线 | 「加机器就能扛住」——连接处的排队与跨机房容量不能靠加机器解决 |
| 人肉响应的速度上限（分钟级） | 限流 / 熔断 / 降级必须自动化，人只做阈值决策 | 「多派人值班」——人的反应是分钟级，故障扩散是秒级，数量补不上速度 |
| 成本必须在日常摊薄 | 能力要能在非大促期使用（演练常态化、压测常态化） | 「为峰值建一套常驻资源」——一年用几天的资源，闲置成本决定方案能否立项 |

这六条里，前两条决定**要不要提前验证**，中间两条决定**要不要改拓扑**，后两条决定**由谁执行、能不能立项**。本案例的五代演进，正好是这三组约束依次成为瓶颈的顺序。

还有一个顺序上的规律值得先记住：**「准备方式覆盖不住这次的不确定性」总是先于「数据量」。** 本案例从 V2.0 起的每一次推进，触发点分别是——容量决策没有依据（V2.0）、跨系统瓶颈看不见（V3.0）、故障响应速度超过人的反应速度（V4.0）、需要人工维护的参数数超过人力（V5.0）。**没有一次是因为流量变大而换代际。** 流量变大换的是机器数量与机房布局，不是代际。

**为什么本节写「被什么逼出来」，而不是写「阿里做了哪几件事」**——因为能力是可以照抄的，约束不能。单元化、限流降级、混沌工程今天都有成熟的开源实现，照抄一个组件只需要几周；**但一个组件是否值得上，取决于你被哪条约束支配，而不是取决于它是否先进**。同一份「上单元化」的提案，在一个只出过「入口过载」的组织里是错配，在一个出过「一个机房带走全站」的组织里是必需。

所以下面的写法是：每一代都给「约束 → 结构 → 机制 → 代价 → 失效点 → 真实使用」六件事。**特别值得看的是「失效点」**——它回答的是「这一代的优点在什么条件下会变成缺点」，也就是「我什么时候该往下走」。

### 3.2 架构代际逐个拆解（核心节）

下面五代覆盖本节原来列出的全部内容（V1.0 临时应对、V2.0 流量预估 + 预案体系、V3.0 全链路压测 + 单元化、V4.0 稳定性平台化、V5.0 AI + 大模型辅助，以及「当前状态」一段）。每一代都按六件事展开——**注意：五代是「约束的刻度」，不是「照抄的路线图」**。

**年份的出处先说清楚**：各代的年份区间与事件年份沿用本案例材料（【经验】，本节未能给出可交叉核验的公开出处）；与主文件 §1.1 年表不一致处一律按 §1.1 校正，并在该处注明（已知一处：异地多活 + 单元化首次启用，记 2018 年，主文件 §1.1 记 **2019** 年）。本节能给出公开锚点的只有若干开源项目的官方仓库（可按项目名检索核验，其开源与发布年份以仓库 Release 记录为准，见 3.2.4）。**核验不到年份的事件，本节一律不写成精确日期。**

#### 3.2.1 V1.0 临时应对（2009–2013）

- **被什么约束逼出来**：峰值量级还在「活动前临时加机器 + 人盯着」能覆盖的范围内，而且一年只有一天有峰值——**为一天建一套常驻体系，在当时算不过账**。
- **结构**：

```text
V1.0 临时应对（2009–2013）
  [业务系统] ──► [活动前临时扩容（本案例记约 5 倍）] ──► [活动后释放]
                            │
                            └─► [人工盯大屏] + [应急预案 Excel] + [群聊吼一嗓子]
  ─────────────────────────────────────────────
  结构特征：三个"控制面"全部由人承担
    容量控制：活动前临时加机器，没有基线、没有依据
    状态感知：人眼看大屏
    应急执行：在群里点名
  → 这三个动作都不落在系统里，只落在"当天在场的人"身上
```

- **为什么这样设计有效**：**因为峰值只有一天、量级还在单机房能承载的范围内，临时堆叠的边际成本低于建一套常驻体系**——不需要改造任何业务系统，也不需要任何平台的立项流程，速度来自「谁都不用改自己的代码」，而不是来自某个组件的性能。
- **代价**：能力不沉淀——每一次大促的应对知识留在当天在场者的记忆里，下一次要重新来一遍；容量决策没有历史依据，只能凭经验乘安全系数；监控覆盖取决于当天有多少人愿意盯屏。
- **失效点**：**当链路跨系统数增加、峰值超过一次临时扩容能覆盖的量级时，人工应对的优点会反转**——**优点是「改造成本为零」，当链路上有几十个系统、每一环都可能是瓶颈时，它变成「没有任何一处能说清瓶颈在哪」，因为感知手段是屏幕、判断手段是经验、执行手段是群聊，三者都不产生可复用的记录**。判断方法很朴素：**峰值时刻系统里跑着多少机器、由谁决定的、依据是什么——如果依据答不出来，就还在这一代**。
- **真实使用**：本案例把它记作 2009–2013（【经验】；主文件 §1.1 记 2009 年为第一次双 11，【经验】）。这是绝大多数公司大促准备的起点形态（【经验】）。
- **这一代留下的三个反模式**：没有容量基线、没有监控覆盖、没有可执行预案——三者不是三个独立问题，而是**同一个结构事实的三种表现**：控制面全部由人承担，所以既没有可查的依据、也没有可复用的感知、也没有可自动执行的响应（见 3.5）。
- **自验方法**：随机挑一次历史峰值，问「当时用了多少资源、怎么定的、事后核对过吗」。三个问题里有两个答不上来，说明你还在这条直线上。

#### 3.2.2 V2.0 流量预估 + 预案体系（2014–2016）

- **被什么约束逼出来**：**容量有采购与预留的提前期，而峰值量级已经超出「凭经验乘系数」能覆盖的误差范围**——要在 T-0 之前把资源锁定，就必须先知道要多少；同时「出事了怎么办」不能继续依赖当天谁在线。
- **结构**：

```text
V2.0 流量预估 + 预案体系（2014–2016）
  [历史数据 + 业务目标 + 行业大盘] ──► [流量峰值预测]
                                            │
  [T-6 月：启动备战] ──► [容量预留 / 采购] ──┴──► [T-1 周：单系统压测]
                                            │
                                            ▼
  [预案手册：红 / 黄 / 蓝 / 绿 四级] ◄──► [三级指挥值班（本案例记 500+ 工程师在线）]
  ─────────────────────────────────────────────
  关键变化（两条同时发生）：
    容量：从"活动前临时加"变成"提前半年锁定"
    响应：从"群里点名"变成"预案等级 → 谁执行 → 执行什么"
  但：验证手段只有单系统压测——跨系统连接处的瓶颈看不见
```

- **为什么这样设计有效**：**因为容量有提前期，预测的提前量本身就是容量能否到位的前提**——不知道要多少，就锁不定资源；**因为预案把「怎么修」从在场者的记忆搬进了文档**，响应第一次不再依赖某个人在不在线。这两件事的共同点是：**它们把「当天的决策」提前到了 T-0 之前**，这正是本节开头那条约束要求的形态。
- **代价**：预测误差直接变成成本——低估导致故障、高估导致闲置（本案例记 2015 年预测误差三成以上、2016 年仍有一成多，【经验】，只取量级）；预案是文档，文档与实际系统状态的同步只能靠人维护，**系统改了而预案没改，预案就是一份过期的承诺**。
- **失效点**：**当链路瓶颈从单系统移到跨系统依赖时，单系统压测的优点会反转**——**优点是「每个团队各自验证自己那一段，责任清楚」，当瓶颈出现在 A 调 B、B 调 C 的连接处时，它变成「每一段单独看都合格、合起来仍然崩」，因为分段压测的负载模型与真实链路的调用路径、调用比例、超时叠加方式都不同**。这也是本案例为什么必须往前走一步：**你无法靠把每一段压到极限来知道整体能扛多少**。
- **真实使用**：本案例记 2014 年建立备战体系、2015 年全面上云并首次系统化预测流量、2016 年引入全链路压测概念（【经验】；主文件 §1.1 记 2015 年阿里全面上云、2016 年首次启用全链路压测，与本节原材料方向一致）。
- **自验方法**：问「T-1 天，你有几个数字能证明系统扛得住这次峰值」。如果答案是「每个团队都压过了」，你验证的是分段，不是链路。

#### 3.2.3 V3.0 全链路压测 + 单元化（2016–2018）

- **被什么约束逼出来**：**瓶颈从单系统移到了跨系统连接处，同时单机房的容量上限与故障半径同时成为硬约束**——一个机房装不下全部峰值，而且一个机房出事就是全站出事。
- **结构**：

```text
V3.0 全链路压测 + 单元化（2016 起）+ 异地多活（2019 起）
  验证面：
    [生产流量模型] ──► [染色（压测标识）] ──► [影子链路] ──► [影子表]
                        （不写真实库；逐步延伸到全链路各系统）
  流量面：
    [用户请求] ──► [GSLB：按 LBS / 运营商 / 健康度] ──► [机房 A 上海 / B 张北 / C 杭州 / D 深圳]
                                                              │
    [统一网关] ──► Hash(UserID) % N ──► [单元 0..N-1]（各自独立的 DB / 缓存 / MQ）
  ─────────────────────────────────────────────
  关键：单元化把"用户"变成路由键——同一用户的读写落在同一单元，
        于是单机房故障的影响面从"全站"缩到"该机房的单元"
  代价：跨单元事务与跨单元查询在结构上不可行（见"代价"与"失效点"）
  前提：压测必须能走影子链路，否则全链路压测会污染真实数据
```

- **为什么这样设计有效**：**因为路由键是用户 ID，同一用户的读写不跨单元，所以局部故障不会自动升级为全局故障**——故障半径第一次成为一个可以被设计出来的量，而不是运气；**因为压测走影子链路，验证可以在生产拓扑上做而不写真实数据**，全链路压测才成为可能。这两件事是一体的：**没有隔离，压测测出来的只是「能不能扛住」，而不是「扛不住的时候会烂在哪一块」**。
- **代价**：单元化把「跨单元」变成一件必须被消灭的事——**跨单元事务无法实现、跨单元查询要走汇总库（额外链路与延迟）**，业务改造量随链路长度线性增加；单元数量（本案例记每机房 4–16 个，【经验】）决定拆分的灵活性；异地多活再叠加一层跨机房数据复制、会话一致与切换演练的长期成本。
- **失效点**：**当业务里出现「绕不开的全局对象」时，单元化的优点会反转**——**优点是「一个用户只在一个单元里，谁都不碰谁」，当存在需要全局唯一或全局排序的对象（库存、券、全局计数）时，它变成「这些对象必须被单独抽成一个中心节点」，而中心节点重新成为全站的单点，因为路由键只能切分用户维度的状态，切不动跨用户的全局状态**。正确做法不是假装没有中心，而是**显式承认它、给它单独的容量与降级方案**。
- **真实使用**：2016 年首次全链路压测（本案例记影子表 + 影子链路方案，【经验】）；2017 年首次 100% 单元化部署、首次**零故障**（【经验】；主文件 §1.1 记为「首次实现 100% 单元化部署」）；异地多活 + 单元化首次启用按主文件 §1.1 记为 **2019** 年（【经验：主文件 §1.1 年表】；**本节原材料把它记在 2018 年，此处按 §1.1 校正**）。PTS 压测平台属对外销售的商业产品，本节不引具体发布年份（读者可按产品名在阿里云官方文档检索核验）。
- **关于峰值的数字**：本节原材料记 2017 年零点峰值为 32.5 万笔/秒（【经验】，来源方向为阿里双 11 官方战报，可按该关键词自行检索核验；**本节只取量级：十万笔/秒级**）；主文件 §1.1 记 2023 年订单峰值为 70 万笔/秒（【经验：主文件 §1.1 年表】）。两者相差约一倍（【推算：70 ÷ 32.5 ≈ 2.2，两个数分别取自本案例原材料与主文件 §1.1】），方向与「峰值逐年上升」一致。**同一份原材料另记 2018 年为 26 万笔/秒，该值低于它自己记的 2017 年值**，与上面的方向不符，本节不采用该值、也不据此下任何判断。
- **自验方法**：问「如果现在挂掉一个机房，哪些业务会停、停多久、谁有权决定切哪个方向」。答不出「哪些业务会停」，说明你还没有故障半径，只有一句「我们有异地多活」。

#### 3.2.4 V4.0 稳定性平台化（2017–2020）

- **被什么约束逼出来**：**每一代大促的能力都长在「临时写的预案 + 当天在场的人」上，无法跨大促复用；而故障场景的真实验证只会在生产发生**——需要有办法在平时就确认「出事时这些保护措施真的会动作」。
- **结构**：

```text
V4.0 稳定性平台化（2017 年起）
  [入口流量] ──► [限流：QPS / 并发 / 资源水位 / 自适应]
                     │
                     ├─► [熔断：错误率 / 慢调用 / 资源水位 触发，按下游隔离]
                     │
                     └─► [降级：读降级 / 写降级 / 功能降级]（按预案等级触发）
  [验证]   ▶ [混沌工程：在生产注入故障，验证上面三层是否真按预期动作]
  [数据层] ▶ [数据库自治：水位识别与干预]
  ─────────────────────────────────────────────
  关键：把"出事了怎么处理"从预案文档搬进运行时组件——
        限流 / 熔断 / 降级 = 自动执行的预案，人只在阈值与开关上做决策
  前提：降级要能被自动执行，就必须先知道"哪些功能可以关"（业务方要事先签字）
```

- **为什么这样设计有效**：**因为保护措施被做成了运行时组件，故障响应时间从「人看到告警 → 找到责任人 → 执行预案」压缩到「组件在阈值处自动动作」**——这条压缩是必要的，因为故障扩散在秒级而人的反应在分钟级；**因为混沌工程可以在非大促期在生产验证这些组件是否真的动作**，这是从「有预案」走到「预案可信」的唯一路径——**一份没人验证过的预案，和没有预案的区别只是心理安慰**。
- **代价**：平台化把「故障处理」变成了「配置」——**配置错了会把故障放大**（限流阈值定低会拦掉正常流量，降级开关误开会让核心功能消失）；降级意味着功能取舍必须事先由业务方定义并签字，这是一项组织成本，不是技术成本；在生产注入故障本身就是一个新增的风险面，需要爆炸半径控制。
- **失效点**：**当流量结构在活动当天发生突变时，静态阈值的优点会反转**——**优点是「超过阈值就自动保护系统」，当阈值是按上一次的流量模型标定的、而本次的流量分布在时段与接口上完全不同时，它变成「把正常流量当成攻击拦掉」，因为阈值是静态的，而流量的分布不是**。典型表现是「系统看上去很健康，但某个核心接口的成功率在特定时段掉了几个点」，事后才发现是限流先动的。
- **真实使用**：本案例记 2017 年对外发布高可用平台 **AHAS**（Application High Availability Service）、2018 年发布限流降级组件 **Sentinel**、2019 年发布故障演练平台 **ChaosBlade**、2020 年发布**数据库自治服务 DAS**（【经验】）。其中 **Sentinel 与 ChaosBlade 是阿里对外开源的组件**——读者可按项目名在代码托管平台检索到其官方仓库，开源与发布年份以该仓库的 Release 记录为准；**AHAS 与 DAS 属阿里云对外商业产品，其发布年份与功能边界请以阿里云官方文档当前版本为准**，读者可按产品名自行检索核验。本节只记「本案例材料把这些能力对应到这些年份」，**不对「哪一年首次用于双 11」下判断**。
- **自验方法**：挑一个非大促的普通周二，主动关掉一个下游服务，看系统是按预期降级、还是先出现故障扩散。**没有在平时做过这件事，你的降级开关就只是一段没跑过的代码。**

#### 3.2.5 V5.0 AI + 大模型辅助（2020–2024）

- **被什么约束逼出来**：**需要人工维护的参数数量（阈值、预案等级、容量系数、告警基线）随系统数增长而超过人力，同时需要被人工消化的信息量（大屏、告警、日志）也超过了值班者能读的量**——值班人力不能随规模线性扩张。
- **结构**：

```text
V5.0 AI + 大模型辅助（2020–2024）
  输入：历史流量 · 业务事件（促销 / 直播 / 热点）· 实时指标 · 变更记录
     │
     ├─► [容量预测与智能调度]：预测峰值 → 提前锁定或自动扩缩容（2020）
     ├─► [异常检测]：识别偏离基线的流量与指标（2021）
     ├─► [智能客服]：承接咨询高峰（2022；大模型版 2024）
     └─► [值班辅助]：代码与文案生成、大屏自动解读、异常归因（2023–2024）
  ─────────────────────────────────────────────
  关键：AI 进入的是"参数维护"与"信息压缩"两个环节——
        它不改变稳定性架构（单元化 / 限流 / 降级 / 压测都还在），
        它改变的是"人需要维护多少参数、需要读多少屏"
```

- **为什么这样设计有效**：**因为容量预测的历史数据、异常检测的基线、值班要看的指标，本来就是结构化且持续积累的，所以模型接入的边际成本低于新增一套人工流程**——这不是「AI 更强」，而是「这些环节的输入恰好是模型能吃的形态」；**因为客服这类场景的「正确答案」分布集中、且容错余地大，模型能承接的比例很高**。
- **代价**：**模型的输入依赖历史数据，而大促恰恰是「历史上没发生过」的场景**（新玩法、新热点、新的流量入口）；模型输出必须配可解释与可回滚的通道，否则值班者无法判断该不该采信；**模型自身成为链路里一个新的依赖**——它也要被限流、被降级、被监控，且它的故障模式（给出一个自信但错误的结论）比普通组件更难被发现。
- **失效点**：**当流量形态出现历史数据里没有的模式时，AI 辅助的优点会反转**——**优点是「基于历史找到最可能的峰值与最可疑的异常」，当出现训练分布里没有的新玩法、新热点或新的流量入口时，它变成「把异常判成正常、把正常判成异常」，因为模型只能在历史分布内插值，而大促的形态每年都在变**。判据：**你最近一次「模型没预警但人发现了」的异常，发生在哪个环节**——如果集中在新业务上，说明这是结构性的，不是模型不够强。
- **真实使用**：本案例记 2024 年**千问**大模型深度参与双 11：**通义晓蜜**智能客服承接当天六成以上客服对话、**通义灵码**辅助工程师值班与代码生成、以及智能定价与库存预测（【经验】，只取量级；**具体口径请以阿里云 / 通义官方发布为准**，读者可按「千问」「通义晓蜜」「通义灵码」等产品名与年份自行检索核验）。
- **自验方法**：问「今年的新玩法，在去年有对应的历史数据吗」。没有，就把这部分的容量与预案按「无历史」处理，而不是交给模型。

#### 3.2.6 当前形态（2024–2025）：五代叠加，不是五代替代

本案例把当前记作「全链路稳定性 4.0」：**单元化 + 异地多活 + 限流降级熔断 + 混沌工程 + 大模型智能调度叠加**，并记「异地多活 + 单元化 100% 覆盖核心系统」「全链路压测 100% 覆盖参与大促的系统」（【经验：沿用本案例材料】）。

关于这两个「100% 覆盖」，有一条纪律必须说：**覆盖率只有在分母被定义时才有意义**。「单元化 100%」的分母是「核心系统」还是「全部系统」，「全链路压测 100%」的分母是「参与大促的服务」还是「全部服务」——**换一个分母，同一句话可以从「实至名归」变成「显然不成立」**。所以本节引用这类数字时只保留方向（覆盖得广），不把它当作可比较的指标。

这一代叠加后的结构，可以按「一层管一件事」来看：

```text
当前形态：五代叠加（2024–2025）
  [用户请求]
      │
      ├─ 谁被路由到哪台机器 ──► [单元化 + 异地多活]        （管故障半径）
      ├─ 峰值潮水打来时先做取舍 ──► [限流 / 熔断 / 降级]    （管负荷上限）
      ├─ 怎么知道撑不撑得住 ──► [容量基线 + 全链路压测]     （管验证）
      ├─ 保护措施会不会真动作 ──► [混沌工程演练]           （管验真）
      └─ 阈值与要看的信息谁来维护 ──► [AI 预测 / 检测 / 摘要]（管参数与人）
  ─────────────────────────────────────────────
  关键：五层各自回答一个不同的问题，
        把它们合并成一句"我们稳定性做得很好"，
        就等于五个问题一个都没有被回答
```

| 代际 | 它解决的不确定性 | 它引入的新成本 | 它成立的前提 |
| --- | --- | --- | --- |
| V1.0 临时应对 | 「峰值不知道够不够」——先堆上再盯 | 能力不沉淀，依赖在场的人 | 峰值一年一次、量级可被临时覆盖 |
| V2.0 流量预估 + 预案 | 「容量有提前期却不知道要多少」 | 预测误差直接变成本；预案会过期 | 历史有可外推的规律 |
| V3.0 全链路压测 + 单元化 | 「跨系统瓶颈看不见」「一机房出事全站出事」 | 跨单元事务 / 查询不可行；跨机房复制与会话一致 | 路由键能切分用户维度的状态 |
| V4.0 稳定性平台化 | 「故障响应速度超过人的反应速度」 | 阈值误标定会放大故障；降级需要业务方签字 | 有人维护阈值并定期演练 |
| V5.0 AI 辅助 | 「要维护的参数与要读的信息超过人力」 | 新形态成为模型盲区；模型自身成为新依赖 | 历史分布对本年的流量形态仍成立 |

**五代放在一起看，真正的差别只有五行**：读上表时请把注意力放在第三列——**每一代引入的新成本，都是下一代要解决的问题**。代际不是替代关系，是叠加关系；被替换掉的只有机器数量与机房布局，被继承下来的是压测链路、预案等级、单元路由与自动化开关。

### 3.3 代际选择决策表

这张表不是「选哪一代最好」，而是**「你现在的约束把你放在哪一代」**。跨代做不是不行，是要额外交学费——**学费不在迁移时交，而在上游缺位时以「补丁」的形式陆续交**：没有容量基线就直接做单元化，你会得到一套改造成本很高、容量却仍然不够的系统；没有影子链路就直接做混沌工程，你注入的故障会变成一次真实事故。

| 约束组合 | 推荐的形态 | 为什么不跳到另一档 | 关键判据 |
| --- | --- | --- | --- |
| 峰值一年一次、量级在临时扩容能覆盖的范围内 | V1.0 临时应对 + 手工容量 | 不建预案体系：体系的固定成本只有在峰值反复出现时才摊得薄 | 峰值时刻用了多少资源、依据是什么，能不能答出来 |
| 峰值量级超过经验系数误差、容量有采购提前期 | V2.0 流量预估 + 分级预案 | 不上全链路压测：预测解决「要多少资源」，压测解决「链路上哪一段先断」 | 容量决策有没有历史依据与复盘 |
| 瓶颈在跨系统连接处、单机房容量与故障半径同时触顶 | V3.0 全链路压测 + 单元化 | 不用「多买机器」替代：连接处的排队不能靠加机器解决 | 瓶颈在单机（加机器）还是在调用链（改拓扑） |
| 每次大促都要人重写一遍预案、故障场景只能等生产发生 | V4.0 平台化（限流 / 熔断 / 降级 / 混沌） | 不靠「多派人值班」：人的反应是分钟级，故障扩散是秒级 | 出事时是组件自动动作，还是人手动执行 |
| 阈值、预案等级、容量系数、告警基线已经维护不过来 | V5.0 AI 辅助（预测 / 检测 / 摘要） | 不先扩建值班团队：人力线性增长，参数超线性增长 | 你上一次复核限流阈值是什么时候 |
| 成本必须日常摊薄、能力一年只用几天 | 云上弹性 + 常态化演练 | 不为峰值建常驻资源：闲置成本决定方案能否立项 | 这套能力一年能用几天、谁来用 |
| 链路里有绕不开的全局对象（库存 / 券 / 全局计数） | 单元化 **+ 显式的中心节点** | 不追求「全链路无中心」：全局唯一性在结构上需要一个裁决点 | 单点故障半径是否被显式承认并单独保护 |

表里最常被误配的一对是 **V3.0（单元化 / 隔离）与 V4.0（限流降级）**。两者都能让系统「在大促当天活下来」，但**它们保护的是两种不同的东西**：单元化保护的是**故障半径**（一个机房炸了不会全站炸），限流降级保护的是**负荷上限**（峰值超过容量时保住核心功能）。团队在「上次大促差点挂掉」的恐惧里，常常直接去立项单元化，因为它听起来更彻底。实际后果是：**改造做完了、业务被拆成了单元，但零点过载的问题一分钟都没被解决**，因为过载不是半径问题、是负荷问题。判断方法只有一句：**上次出事是「一个局部拖垮了全局」，还是「入口一开始就顶不住」**——前者用 V3.0，后者用 V4.0；两样都要时，先做 V4.0，因为限流降级的改造面比单元化小得多、见效快得多。

第二常被误配的一对是 **V2.0（预测）与 V3.0（压测）**，症状都是「不确定能扛多少」。区别在于：**预测给的是容量数字，压测给的是链路行为**。能预测出「要多少台机器」但不知道哪个下游会先排队，问题照样在。

第三对是 **V4.0（自动化保护）与 V5.0（AI 辅助）**。自动化保护是「阈值到就动作」，AI 辅助是「帮人决定阈值和维护参数」——**前者是控制回路，后者是参数维护**。团队在被「同类故障反复发生」折磨了几轮之后，容易直接跳到 AI 异常检测，因为它看起来更先进。实际后果是：**检测能力提升了，但检测出来的异常并没有对应的自动动作，值班者只是更早知道了一件自己处理不了的事**。判据：**你的告警里，有多少条是「收到之后有明确动作」的**——如果比例很低，缺的不是检测，是动作。

### 3.4 组合模式：真实系统不会只用一种

1. **单元化 + 限流降级熔断（隔离 + 取舍）**——职责边界：**单元化决定「故障的影响边界」，限流降级决定「过载时保什么」**；前者是空间维度的切分，后者是负荷维度的取舍，两者不能互相替代——只有单元化时，再小的单元也会被自己内部的过载打穿；只有限流时，一个机房的物理故障仍然会带走它上面所有的单元。运维代价：单元带来「跨单元不可做」的清单（跨单元事务、跨单元查询走汇总库），限流阈值要在每个单元上分别标定并随拆分变化重新标定，两套配置都要有人复核。适合的规模：单机房容量与故障半径同时触顶之后。
2. **全链路压测 + 混沌工程（预演 + 验证）**——职责边界：**压测回答「容量够不够」，混沌回答「出事时保护措施会不会按预期动作」**。这两件事经常被合并成一句「我们压过测了」，但**压测是在系统健康时加压，混沌是在系统里制造故障**——前者测上限，后者测控制回路是否闭合。运维代价：影子链路必须随业务改造同步延伸（新接一个系统就要把它纳入影子链路，否则压测覆盖率会静默下降）；混沌要在生产注入故障，必须有爆炸半径控制与一键终止。适合的规模：链路有几十个以上系统、且已经有影子链路时。
3. **预测 + 预案 + 值班（计划 + 动作 + 决策权）**——职责边界：**预测只负责「要多少」，预案只负责「做什么」，值班只负责「什么时候做」**。三者失衡是这类体系最常见的病：预测准了但预案没有对应动作，预案写了但没人有权拍板，值班到岗了但预案已经过期。运维代价：预案必须随系统变更同步更新（**这是长期人力，不是一次性文档工作**）；三级指挥体系需要提前明确「谁有权降级核心功能」，这项授权在大促当天来不及临时取得。适合的规模：存在「时间点外生」的活动（大促、开服、直播）时。

三个组合放在一起，可以看出一个共同的取舍：

| 组合 | 谁承担稳定 | 谁承担变化 | 组合的失效方式 |
| --- | --- | --- | --- |
| 单元化 + 限流降级 | 单元路由规则与降级清单 | 每个单元的容量与阈值 | 阈值不随拆分重标，单元内先过载，隔离形同虚设 |
| 压测 + 混沌 | 影子链路与终止开关 | 被测系统的版本与拓扑 | 影子链路没跟着新系统延伸，压测覆盖率静默下降 |
| 预测 + 预案 + 值班 | 预案文本与决策授权 | 流量模型与系统变更 | 预案随系统更新滞后，当天执行的是过期版本 |

这张表要传达的只有一句：**组合模式的前提是「变化被限制在某一层」，一旦变化同时发生在两层，组合就退化成耦合。**

这也解释了本案例的一个可迁移经验：**它的每一次推进，都尽量只动一层。** 2014–2016 年动容量与预案，2016–2018 年动拓扑（压测与单元化），2017–2020 年动运行时组件，2020 年以后动参数与信息处理——**没有一次是把拓扑、组件与组织流程一起换掉的**。这不是保守，而是因为组合模式下的收益来自「其他层不用动」。

**组合模式还有一条验收纪律：每一层要有独立的验收标准。** 压测验收的是容量曲线，混沌验收的是保护动作是否真被触发，单元化验收的是故障影响面，限流降级验收的是过载时的核心功能成功率——**如果四者都用同一个指标（例如「大促当天没出事故」）来验收，那就等于四者都没有被验收过**，因为只要没出事，就没人知道是哪一层的功劳。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **容量靠临时堆叠**（本节原材料记 V1.0 的「活动前临时扩容、活动后闲置」） | 问「这次用多少机器、依据是什么」只能得到「去年大概这么多」 | 容量决策不可复盘，误差无法收敛——**没有基线，每一次大促都是从零开始猜** | 临时堆叠是唯一不需要立项的动作，且一年只用一次 | 建立容量基线（历史曲线 + 业务目标 + 安全系数）并强制复盘误差 |
| **状态感知靠人盯大屏**（本节原材料记 V1.0 的「几个人盯大屏」） | 告警系统里没有该指标，或阈值常年不更新 | 感知的覆盖取决于当天有几个人在，人力不在场就存在盲区；**且盯屏不产生可复用的记录** | 早期指标少，盯屏比建监控便宜 | 把要看的东西先变成指标与告警，再谈大屏展示 |
| **响应靠群聊点名**（本节原材料记 V1.0 的「群聊吼一嗓子」） | 复盘时找不到「谁在什么时候决定了什么」 | 响应时间取决于关键人是否在线；**责任链不可追溯，事故无法归因** | 群聊是零成本的协调手段，且大促当天所有人都在群里 | 预案分级 + 决策授权清单 + 操作留痕，让动作不依赖点名 |
| **把单系统压测当成链路验证**（本节原材料记 V2.0 的「压测不全面，单系统压测是关键」） | 每个团队都说自己压过了，整体峰值仍然崩 | **分段合格与整体合格之间没有推理关系**——连接处的排队、超时叠加、重试放大都不在单系统压测的模型里 | 单系统压测责任清楚、时间可控、不需要跨团队协调 | 建影子链路做全链路压测，把连接处的调用比例与超时链路一并复现 |
| **预测误差没有复盘**（本节原材料记 V2.0 的「预测误差大」，【经验】） | 每年都在预测，但没人记得去年的误差是多少 | 误差不收敛——**同一个系统性低估会年年重复，因为没有人负责把它变成下一年的修正量** | 大促结束后团队立刻投入下一件事，复盘没有排期 | 把「预测值 vs 实际值」作为大促收尾的固定交付物，误差进入下一年的安全系数 |
| **预案与降级开关常年不演练**（本书对该演进的归纳，【经验】） | 开关存在，但没人记得上次触发是什么时候、结果如何 | **未验证的保护措施在故障时提供的是虚假确定性**——值班者以为系统会自己降级，于是不做人工干预 | 演练要在生产注入故障，风险评估难过；不演练也不会立刻出事 | 把混沌演练排进日常排期，把「保护措施在上次演练中的实际动作」作为值班前必读材料 |
| **覆盖率的口径不定义**（本书对该演进的归纳，【经验】） | 「100% 覆盖」这类表述在不同团队口径不同 | 覆盖率变成不可比较的指标——**分母一换，同一句话的含义就变了**，治理进度失去度量 | 「100%」是汇报时最好听的数字，而定义分母要花时间 | 每个「覆盖」都写清分母，并接受「核心系统全覆盖、全量系统部分覆盖」这类表述 |

**最危险的一个是「容量靠临时堆叠」**，因为它不报错。它没有故障信号，只有每年一次「这次赌对了还是赌错了」；而**每一次赌错都在消耗同一个东西——组织对「准备是否充分」的判断力**。它的暴露方式是：某一年量级跨过了一个台阶，而当年的容量依据仍然是去年的经验系数，于是系统在最不该出问题的时间点过载。这也是本案例为什么把 V2.0 的容量基线当作整条演进的第一步（【经验】）。

**第二个是「预案与降级开关常年不演练」**，因为它是前面所有平台化投入的贬值机制：**你在限流降级上花的力气，与演练次数成正比**——一个从未被触发过的开关，只能证明它存在，不能证明它会动作。它的典型暴露方式是：大促当天系统过载，值班者按预案去开降级，发现开关的生效范围与预期的完全不同，或者上游的限流已经把这条路径掐断了。

**第三个是「把单系统压测当成链路验证」**，它的机制特点是**每个局部都对、整体却错**：连接处的瓶颈在任何一个团队自己的负载模型里都看不见，因此不会有人报错，直到真实流量的调用比例与超时叠加方式把那个连接处压穿。**它不是一次错误，而是一类系统性盲区**——这也是全链路压测必须排在单系统压测之后、而不是替代它的原因。

**还有一个是「覆盖率的口径不定义」**，它看起来最无害，实际上让前六条的治理成效都失去度量：**一个不可比较的指标无法驱动长期投入**。它的暴露方式通常不是事故，而是「治理汇报每年都在进步，但出事的地方还是那几处」——因为分母被换过。

把这七条放在一起看，**它们共享同一个修法**：把「准备」从**人的在场**移到**系统的状态上**。容量从经验变成基线、感知从盯屏变成指标、响应从点名变成预案与授权、验证从分段变成全链路、保护从文档变成被演练过的开关——**动作不同，方向相同：让「我们准备好了」这句话有可验证的载体，否则它和祈祷没有区别。**

### 3.6 规模跃迁时形态何时该换

| 跃迁 | 原形态 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 峰值从「单日一段脉冲」变成「零点 + 整点 + 直播热点的多波次」 | 一次性临时扩容 + 手写预案 | 脉冲次数增加且不可预测，预案的动作来不及在上一次和下一次之间重排 | 分级预案 + 自动限流降级（V4.0） | 业务方要为每个功能标注「可降级 / 不可降级」，这是一项组织工程而非技术工程 |
| 链路跨系统数从个位数到几十个以上 | 单系统压测 | 连接处的瓶颈在任何一个单系统视角里都不可见 | 全链路压测（影子链路，V3.0） | 业务系统要改造以识别压测标识；影子库与影子链路要随真实拓扑同步维护 |
| 单机房容量触顶 | 垂直扩容 / 加机器 | 单机房有物理上限，且故障半径等于全站 | 单元化（V3.0） | 跨单元事务与跨单元查询在结构上不可行，需要汇总库与业务改造；单元数一旦确定，调整成本高 |
| 单机房故障不可接受 | 同机房多单元 | 一个机房整体不可用时，上面所有单元一起停 | 异地多活 | 跨机房数据复制延迟、会话一致性、切换演练；**多活的复杂度主要不在技术上，而在「谁有权切」** |
| 故障响应速度要求快于人的反应 | 值班 + 预案手册 | 故障扩散在秒级，人的反应在分钟级，数量补不上速度 | 自动限流 / 熔断 / 降级（V4.0） | 阈值维护成为新的运维负担，误标定会放大故障；降级要事先取得业务授权 |
| 需要人工维护的阈值 / 预案 / 基线数量超过人力 | 人工配置与人工看盘 | 参数数随系统数超线性增长，值班人力只能线性增长 | AI 辅助预测与异常检测（V5.0） | 模型需要可解释与可回滚通道；**历史上没有出现过的形态会成为结构性盲区** |
| 成本压力：能力一年只用几天 | 为峰值常驻资源 | 闲置成本无法摊薄，立项越来越难 | 云上弹性 + 常态化演练 | 弹性有拉起时延，零点峰值的斜率可能超出弹性能力；常态化演练需要日常排期 |
| 出现跨用户的全局状态（库存 / 券 / 全局计数） | 纯单元化，假设「无中心」 | 路由键切不动跨用户的状态，这些对象被迫留在某处 | 单元化 + 显式中心节点 + 单独容量与降级 | 承认中心的存在会打破「无单点」的叙事，需要为它单独做容量、隔离与降级演练 |

读这张表的顺序是**先看「准备方式覆盖不住什么」，再看「响应要多快」，最后才看「有多少流量」**。八行里只有第三行（单机房容量触顶）是容量驱动的，其余七行的触发条件分别是：波次变了、链路长了、故障半径不可接受了、响应快不过扩散、参数维护不过来、成本摊不薄、出现了跨用户的全局状态。**其中最后一行最特殊**——它不是一次规模跃迁，而是一个在规模扩大后才暴露的设计假设：**「无中心」这个前提本身不成立**。

还有一条关于「跃迁时机」的判断纪律：**先确认「疼」是不是由约束变化引起的，再决定换形态**。同样是「大促当天出问题」，可能是容量不足（V2.0 的问题）、连接处瓶颈（V3.0 的问题）、响应太慢（V4.0 的问题）、或者参数没维护过来（V5.0 的问题），四者的解法完全不同。**换错形态的代价通常大于晚换**——晚换只是继续疼，换错则是把疼换成了「旧问题还在、新系统的改造成本还要长期摊」。

### 3.7 自检清单

下面 12 条按「基线 → 验证 → 半径 → 响应 → 参数 → 成本」的顺序排列，对应 3.2 每一代的失效点与 3.5 的七条反模式。

- [ ] 峰值时刻用了多少资源、由谁决定的、依据是什么？去年这个决策的误差是多少，谁负责把它变成今年的修正量？
- [ ] 你的容量决策里，「历史曲线」「业务目标」「安全系数」三个输入各来自哪里？如果只有「去年大概这么多」，你还没有 V2.0。
- [ ] T-1 天，你有几个数字能证明系统扛得住这次峰值？这些数字来自全链路压测，还是来自每个团队各自的分段压测？
- [ ] 你的压测覆盖链路里的连接处吗？新上线的系统有没有被纳入影子链路，还是压测覆盖率在静默下降？
- [ ] 如果现在挂掉一个机房，哪些业务会停、停多久、谁有权决定切换方向？这个问题能在半小时内被回答吗？
- [ ] 链路里有没有绕不开的全局对象（库存 / 券 / 全局计数）？它现在的容量与降级方案是显式的，还是被「我们无中心」这句话掩盖着？
- [ ] 出事时，是组件在阈值处自动动作，还是等人在群里点名执行？从告警出现到第一个保护动作生效，中间有多少环节依赖人？
- [ ] 你的限流阈值是按哪一次的流量模型标定的？最近一次复核是什么时候？有没有出现过「系统健康但某接口成功率掉点」的情况？
- [ ] 限流 / 熔断 / 降级开关，上次在非大促期被真实触发是什么时候？有多少个开关从未被验证过会动作？
- [ ] 哪些功能可以在大促期间被降级？这份清单是业务方签过字的，还是技术团队自己猜的？谁有权在当天决定降级核心功能？
- [ ] 预案文档上一次跟系统变更同步是什么时候？如果明天有一条链路重构，预案会在什么时候被更新？
- [ ] 你引用「100% 覆盖」时，分母是什么？换一个分母（核心系统 → 全量系统），这句话还成立吗？

### 3.8 小结

| 你的约束 | 建议形态 | 关键理由（机制层面） |
| --- | --- | --- |
| 峰值一年一次、量级可被临时覆盖 | V1.0 临时应对 + 手工容量 | 常驻体系的固定成本只有在峰值反复出现时才摊得薄；代价是能力不沉淀 |
| 容量有提前期、峰值超出经验系数 | V2.0 容量基线 + 分级预案 | 预测的提前量是容量能否到位的前提；代价是误差直接变成本 |
| 瓶颈在连接处、故障半径不可接受 | V3.0 全链路压测 + 单元化 | 用用户 ID 做路由键可把故障半径变成可设计量；代价是跨单元不可做 |
| 故障扩散快于人的反应 | V4.0 限流 / 熔断 / 降级 + 混沌演练 | 自动动作把响应从分钟级压到阈值处；代价是误配会放大故障 |
| 参数与信息量超过人力 | V5.0 AI 辅助预测与检测 | 历史数据本就结构化，接模型比加流程便宜；代价是新形态成为盲区 |
| 能力一年只用几天、成本要摊薄 | 云上弹性 + 常态化演练 | 闲置成本决定方案能否立项；代价是弹性有拉起时延 |

> 本节小结：这五代不是路线图，而是**三组约束依次成为瓶颈的刻度**——先缺依据（容量决策没有基线），再缺可见性（跨系统瓶颈与故障半径不可见），最后缺速度与人力（响应快不过扩散、参数维护不过来）。**决定你该走到哪一代的唯一那条约束是「可用性的时间点有多硬、故障半径有多大」**；流量增长只换机器与机房布局，不换代际。

把本节压成三句可执行的话：**第一，先问「T-0 之前你能完成什么」**——所有准备工作都必须在确定性时刻前做完，这是大促这类场景与日常运维最根本的区别。**第二，任何一代的成果都要能回答「半径有多大、响应有多快」**——故障会带走哪些业务、保护动作由谁在多久内触发；只要有一个答案是「不确定」，你就在欠账。**第三，改拓扑与改组件是两个预算项**——单元化改的是拓扑，限流降级改的是运行时行为，把它们塞进同一个项目，结果是拓扑改完了、过载问题还在。

还有一条属于本案例的特殊性，需要读者自行判断是否可迁移：**这套体系是十六年时间里逐步长出来的**（【经验：本案例主文件 §1.1 年表，2009–2024】），每一代都建立在上一代的成果之上。**缩短时间跨度去走同一条路，风险不在于做不出来，而在于跳过了「上一代把问题变成组织共识」的过程**——没有经历过容量赌错的组织，通常不会为全链路压测与单元化付出业务改造的代价。

最后一条判据不属于任何一代，但它决定了上面所有能力能不能在关键时刻真的被用上：**大促当天真正被消耗的不是机器，是决策带宽。** 零点前后值班者要处理的信息量远超平时，而每一次演进（更多系统、更多指标、更多开关、更多预案）都在加大这个压力。**所以 V5.0 这类演进的真实价值是压缩「需要人读的信息」与「需要人维护的参数」，而不是替代人的判断**——这也解释了为什么它必须排在前四代之后：**在一个还没有限流降级动作的系统上做智能检测，只会让你更早发现问题、同样无力处理。**

> 💡 **思考锚点**：数一下你最近一次大促给这四层各留了什么验收数——§3.4 给的是「单元化看故障影响面、限流降级看过载时的核心功能成功率、压测看容量曲线、混沌看保护动作是否真被触发」。如果你的答案全是同一个「当天没出事故」，按本节那就等于四层都没被验收过；这四个专属数你现在量得出几个，量不出的那一层由谁在下次大促前把口径定下来？
