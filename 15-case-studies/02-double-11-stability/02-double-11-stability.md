## 1. 背景

### 1.1 公司 / 业务 / 时间

双 11（"光棍节"）从 2009 年淘宝第一次造节开始，到 2024 年已经走过了 16 年。它的形态发生了根本变化：

- **2009**：淘宝 27 个品牌参加，当天 GMV 0.5 亿元，主要靠"打折 + 流量"。
- **2011**：天猫（淘宝商城）独立参与双 11，GMV 52 亿元。
- **2013**：移动端首次参战，GMV 350 亿元，移动占比 21%。
- **2015**：阿里全面上云，双 11 跑在阿里云上，GMV 912 亿元。
- **2016**：GMV 1207 亿元，**首次启用全链路压测**。
- **2017**：GMV 1682 亿元，**首次实现 100% 单元化部署**。
- **2019**：GMV 2684 亿元，**首次启用异地多活 + 单元化**。
- **2020**：GMV 4982 亿元，疫情下首次全面直播化。
- **2023**：GMV 持平增长，约 1,500 亿元（口径调整），订单峰值 70 万笔/秒。
- **2024**：GMV 公布"与去年持平"，**首次全面启用 AI 大模型于双 11**。

**业务特点**：

- **零点峰值**：双 11 零点开抢的瞬间，系统承受的瞬时流量是日常的 **10–50 倍**。
- **持续高位**：零点后 1 小时、整点（10:00、20:00）都有脉冲，**全天高位**。
- **多端联动**：淘宝 / 天猫 / 支付宝 / 菜鸟 / 阿里云 / 优酷 / 高德 / 饿了么 **多端联动**，链路复杂。
- **全链路**：从下单 → 支付 → 物流 → 售后 → 客服，链路长。

### 1.2 行业与监管

- **金融监管**：支付宝双 11 凌晨需要扛住峰值 70 万笔/秒，**断一秒就是几亿元损失**。
- **跨境监管**：Lazada / 速卖通的跨境支付链路在东南亚多国同步双 11，需要本地化合规。
- **等保**：阿里云对外服务必须满足等保 2.0 / 3.0。
- **GDPR**：欧洲业务必须符合 GDPR。

### 1.3 团队规模与组织

- **阿里集团双 11 技术保障团队**巅峰期约 **3000+ 人**。
- **作战指挥部**：约 50+ 人，包括集团 CTO、各 BU 技术负责人。
- **核心作战单元**：
  - 容量规划团队（约 30 人）：负责全链路容量评估。
  - 压测团队（约 50 人）：负责 PTS 平台与全链路压测执行。
  - 稳定性保障团队（约 200 人）：负责限流降级熔断平台。
  - 数据库保障团队（约 100 人）：负责数据库水位与分库分表。
  - 实时计算团队（约 200 人）：负责双 11 实时大屏。
  - 客服保障团队（约 100 人）：双 11 客服备战。
- **协同**：所有业务方（淘宝 / 天猫 / 支付宝 / 菜鸟 / 阿里云）参与，统一指挥。

## 2. 挑战

### 2.1 业务挑战

#### 2.1.1 流量峰值预测难

2017 年之前，双 11 流量峰值预测准确率只有 **60%**——经常是"低估"导致系统崩溃，或"高估"导致资源浪费。

#### 2.1.2 复杂链路协同

双 11 涉及 **200+ 系统**，从用户点击 → 网关 → 交易 → 库存 → 支付 → 履约 → 售后 → 客服。任何一环故障都会引发"雪崩"。

#### 2.1.3 突发热点

"口红一哥"、"李佳琦"、"薇娅"等直播带货在双 11 当天的流量冲击是**不可预测的**——某个商品突然爆单，会击穿库存系统。

#### 2.1.4 用户体验

双 11 用户对**延迟极其敏感**——3 秒内打不开页面就跳走。下单支付链路 5 秒内没响应就退款。**延迟与可用性是用户体验的硬指标**。

### 2.2 技术挑战

#### 2.2.1 数据库水位

双 11 零点开始后，MySQL / OceanBase 数据库水位从 40% 飙到 90%+，**CPU、磁盘、网络都可能成为瓶颈**。

#### 2.2.2 缓存击穿

商品详情页的缓存命中率必须维持 **99%+**，否则下游数据库直接被打挂。

#### 2.2.3 消息队列堆积

RocketMQ 在双 11 当天消息量是日常的 30 倍，**Topic 分区、Consumer 数量、Broker 容量**都需要事先规划。

#### 2.2.4 实时计算稳定性

Blink 集群在双 11 跑 2000+ 实时任务，**故障恢复时间（Failover Time）必须 < 1 分钟**。

#### 2.2.5 流量调度

双 11 不同地区的流量不均衡，需要**全局流量调度**（基于 LBS、运营商、用户行为）。

### 2.3 组织挑战

#### 2.3.1 跨 BU 协同

淘宝 / 天猫 / 支付宝 / 菜鸟 **每个 BU 都是独立 KPI**，双 11 是把它们拉到同一战场。

#### 2.3.2 值班机制

双 11 零点值班需要 **500+ 工程师同时在线**，必须有清晰的"指挥官 → 团队 Leader → 普通工程师"三级指挥体系。

#### 2.3.3 应急响应

任何系统在双 11 凌晨出现告警，**5 分钟内必须有负责人响应**，10 分钟内必须有预案执行。

## 3. 架构演进

### 3.1 V1.0：临时应对（2009–2013）

**形态**：

```
[临时堆机器] + [人工盯屏] + [应急预案 Excel]
```

**问题**：

- 双 11 之前临时扩容 5 倍机器，活动后资源闲置。
- 监控靠"几个人盯大屏"，眼睛快眨。
- 应急响应靠"群聊吼一嗓子"。

**教训**：**没有体系工程，只有临时应对**——双 11 越做越大，必须转成"体系化保障"。

### 3.2 V2.0：流量预估 + 预案体系（2014–2016）

**关键事件**：

- 2014：阿里建立"双 11 备战体系"，提前 6 个月开始准备。
- 2015：双 11 全面上云，**首次系统化预测流量**。
- 2016：引入"全链路压测"概念。

**核心能力**：

- **流量预测模型**：基于历史数据 + 业务目标 + 行业大盘，预测双 11 流量峰值。
- **预案体系**：每个系统都有"应急预案手册"（红色 / 黄色 / 蓝色 / 绿色等级）。
- **值班机制**：双 11 当天 500+ 工程师在线值班，三级指挥体系。

**问题**：

- **流量预测误差大**——2015 年预测误差 30%+，2016 年仍有 15%。
- **压测不全面**——单系统压测是关键，全链路压测仍不成熟。

### 3.3 V3.0：全链路压测 + 单元化（2016–2018）

**关键事件**：

- 2016：**首次全链路压测**，用"影子表 + 影子链路"模拟双 11 流量。
- 2017：**首次 100% 单元化部署**，双 11 零点峰值 32.5 万笔/秒。
- 2018：**异地多活 + 单元化**全面铺开。

**核心能力**：

- **全链路压测平台 PTS**：阿里云对外销售的高并发测试平台。
- **单元化部署**：把用户按 ID 哈希到不同单元，每个单元独立。
- **异地多活**：上海 / 张北 / 杭州 / 深圳多机房互备。

**关键里程碑**：

- 2017 年双 11 零点峰值 32.5 万笔/秒，**系统零故障**。
- 2018 年双 11 峰值 26 万笔/秒，**异地多活首次承担实际流量**。

### 3.4 V4.0：稳定性平台化（2017–2020）

**关键事件**：

- 2017：阿里对外发布"**高可用平台 AHAS**"（Application High Availability Service）。
- 2018：发布"**限流降级平台 Sentinel**"（Java 生态标准）。
- 2019：发布"**故障演练平台 ChaosBlade**"（基于 Chaos Engineering 思想）。
- 2020：发布"**数据库自治服务 DAS**"。

**核心能力**：

- **限流**：基于 QPS / 并发数 / 资源使用率的精细化限流。
- **降级**：自动降级非核心功能（如商品推荐、广告位）。
- **熔断**：下游服务故障自动熔断，避免雪崩。
- **混沌工程**：定期在生产环境注入故障，验证系统韧性。

### 3.5 V5.0：AI + 大模型辅助（2020–2024）

**关键事件**：

- 2020：引入 AI 智能调度（基于流量预测自动扩缩容）。
- 2021：引入 AI 异常检测（自动识别异常流量）。
- 2022：引入 AI 客服（双 11 客服备战）。
- 2023：大模型应用于客服、文案、代码生成。
- 2024：**千问大模型深度参与双 11**：智能客服、智能营销、智能决策。

**2024 年大模型应用案例**：

- **千问大模型应用于客服**：通义晓蜜智能客服，**双 11 当天承接 60%+ 客服对话**。
- **千问大模型应用于代码**：通义灵码辅助工程师值班，**自动修复低代码问题**。
- **千问大模型应用于决策**：智能定价、库存预测、流量调度。

### 3.6 当前状态（2024–2025）

- **AI 全面辅助双 11**：从容量预测到异常识别，从客服到决策，大模型渗透到双 11 全链路。
- **全链路稳定性 4.0**：单元化 + 多活 + 限流 + 混沌工程 + 大模型智能调度。
- **异地多活 + 单元化 100% 覆盖**所有核心系统。
- **全链路压测 100% 覆盖**所有参与大促的系统。

## 4. 关键决策

### 4.1 决策 1：容量规划怎么做？

**决策路径**：

- **方案 A：经验估值**（2014 前）：资深工程师凭经验"乘以 5 倍"。
  - 优点：简单。
  - 缺点：不准确，2014 年预估峰值 5 万/秒，实际 8 万/秒。
- **方案 B：基于历史 + 业务目标**（2015+）：
  - 历史增长曲线 + 业务目标 + 行业大盘 + 安全系数（1.5x–2x）。
  - 优点：相对准确。
  - 缺点：仍依赖经验。
- **方案 C：AI 智能预测**（2021+）：
  - **LSTM + Transformer 模型**对历史数据 + 业务事件建模。
  - 优点：准确率高，2024 年误差 < 5%。
  - 缺点：模型训练需要数据科学家 + 大算力。

**验证**：2024 年阿里双 11 容量预测准确率 **95%+**，远高于行业平均 70%。

### 4.2 决策 2：全链路压测怎么做？

**决策路径**：

#### 4.2.1 影子表 + 影子链路方案

```
[生产流量] → [染色（压测标识）] → [复制流量到影子库] → [影子表写入]
```

- **优点**：不影响生产数据。
- **缺点**：需要业务系统改造（识别压测标识）。

#### 4.2.2 流量回放方案

- **录制**：录制历史真实流量（如双 11 当天 0 点峰值流量）。
- **回放**：在压测环境下重放。
- **优点**：流量真实。
- **缺点**：环境依赖（数据库、缓存、消息队列都要重建）。

#### 4.2.3 阿里 PTS 平台

- **核心能力**：
  - 支持 JMeter 兼容脚本。
  - 支持云原生部署（压测流量分发到全球压测节点）。
  - 支持压测流量隔离（不会污染生产数据）。
  - 支持实时监控 + 自动诊断。

**关键节点**：2016 年双 11 **首次全链路压测 100% 覆盖** 200+ 系统。

### 4.3 决策 3：单元化怎么做？

#### 4.3.1 单元化原理

把用户按 ID 哈希到不同"单元"，每个单元独立部署：

```
User ID → Hash(User ID) % N → Unit N
Unit 0: 用户 A、E、...
Unit 1: 用户 B、F、...
Unit 2: 用户 C、G、...
Unit 3: 用户 D、H、...
```

#### 4.3.2 单元化关键组件

- **路由层**：所有请求先经过统一网关，按 ID 路由到对应单元。
- **数据层**：每个单元独立的数据库、缓存、消息队列。
- **服务层**：每个单元独立的服务实例。

#### 4.3.3 单元化的"复杂度陷阱"

- **跨单元事务**无法实现 → 必须避免跨单元业务逻辑。
- **跨单元查询**无法做 → 必须通过汇总库（成本高）。
- **单元数量有限**优化成本高。

#### 4.3.4 阿里方案

- **业务改造**：所有交易链路按用户 ID 单元化。
- **汇总库**：OLAP 场景（数据报表）从汇总库读，不走单元。
- **单元数**：每个机房 4–16 个单元。

### 4.4 决策 4：限流降级熔断怎么做？

#### 4.4.1 限流（Sentinel）

```java
@SentinelResource(value = "createOrder", blockHandler = "blockHandlerMethod")
public Order createOrder(OrderRequest req) {
    // 业务逻辑
}
```

**限流策略**：

- **QPS 限流**：每秒最多处理 N 个请求。
- **并发限流**：同时最多 N 个请求在处理。
- **资源限流**：CPU / 内存 / 数据库连接池水位。
- **自适应限流**：基于系统负载自动调整。

#### 4.4.2 降级

**降级策略**：

- **读降级**：从完整数据降级到简化数据（如商品详情从完整属性降级到基础属性）。
- **写降级**：从同步写降级到异步写（如订单提交后异步持久化）。
- **功能降级**：从完整功能降级到核心功能（如双 11 期间不显示推荐位）。

#### 4.4.3 熔断（Hystrix / Sentinel）

**熔断策略**：

- **错误率熔断**：下游错误率 > 50% 时熔断。
- **慢调用熔断**：下游 P99 延迟 > 1 秒时熔断。
- **资源熔断**：下游资源使用率 > 80% 时熔断。

### 4.5 决策 5：实时大屏怎么做？

#### 4.5.1 大屏技术栈

```
[业务系统] → [MQ] → [Blink/Flink] → [Hologres/ClickHouse] → [Grafana/自研大屏]
```

- **采集**：业务系统埋点 + 日志采集（OTel/SLS）。
- **计算**：Blink 实时计算（延迟 < 1 秒）。
- **存储**：Hologres 实时 OLAP（10 亿行级别毫秒级查询）。
- **可视化**：自研大屏 + 多种前端技术。

#### 4.5.2 大屏指标

- **GMV**（实时 + 累计）。
- **订单数**（实时 + 累计）。
- **支付成功率**（实时）。
- **品类排行**（实时）。
- **地区排行**（实时）。
- **商品排行**（实时）。

#### 4.5.3 2024 年大屏升级

- **千问大模型驱动**的大屏自动解读：实时生成"双 11 数据快讯"。
- **AI 智能异常识别**：自动识别异常指标并告警。

### 4.6 决策 6：异地多活怎么做？

#### 4.6.1 异地多活原理

```
[用户请求] → [GSLB] → [最近机房]
```

- **GSLB**（Global Server Load Balancing）按 LBS / 运营商 / 健康度路由到最近机房。

#### 4.6.2 异地多活架构

- **机房 A**：上海
- **机房 B**：张北
- **机房 C**：杭州
- **机房 D**：深圳

每个机房都承担实际流量，单机房故障不影响全局。

#### 4.6.3 异地多活关键技术

- **数据复制**：跨机房数据库同步（Otter / 自研工具）。
- **消息队列**：跨机房消息同步（RocketMQ 多活）。
- **会话一致**：用户会话跨机房共享（基于分布式 Session）。
- **流量切换**：DNS / GSLB 切换时间 < 1 分钟。

### 4.7 决策 7：值班机制怎么设计？

#### 4.7.1 三级指挥体系

```
[集团总指挥（CTO）]
   ↓
[业务域指挥（BU 技术负责人）]
   ↓
[系统负责人（核心系统 owner）]
```

#### 4.7.2 值班分工

- **总指挥部**：50+ 人，集团 CTO 坐镇。
- **业务域指挥部**：每个 BU 50+ 人，BU 技术负责人带队。
- **系统值班**：每个核心系统 5–10 人值班。
- **应急小组**：100+ 人，专项处理突发问题。

#### 4.7.3 值班工具

- **大屏**：双 11 实时大屏，所有值班人员实时查看。
- **告警平台**：SRE 告警平台，5 分钟响应承诺。
- **应急手册**：每个系统的应急预案手册，PDF / 在线版本。
- **沟通工具**：钉钉群、应急广播、电话会议。

### 4.8 决策 8：大模型如何用于双 11？

#### 4.8.1 智能客服

- **通义晓蜜**：双 11 期间承接 60%+ 客服对话。
- **效果**：人工客服成本下降 40%+，客户满意度提升 25%。

#### 4.8.2 智能代码

- **通义灵码**：辅助工程师值班，自动修复低代码问题。
- **效果**：值班工程师处理效率提升 30%。

#### 4.8.3 智能决策

- **智能定价**：基于实时供需关系动态定价。
- **智能库存**：基于预测自动调整库存分配。
- **智能流量调度**：基于实时流量预测动态调整路由。

#### 4.8.4 智能营销

- **千问大模型生成营销文案**，提升转化率。
- **千问大模型生成商品描述**，降低运营成本。

## 5. 踩坑与教训

### 5.1 坑 1：2015 双 11 凌晨数据库雪崩

**问题**：2015 年双 11 零点开始后，MySQL 数据库水位从 40% 飙到 95%+，部分查询超时，引发雪崩。

**根因**：

- 容量预估不足（低估 30%）。
- 没有限流（高并发下 MySQL 连接池被打满）。
- 没有熔断（下游故障导致上游崩溃）。

**教训**：

- **容量规划必须有安全系数**（1.5x–2x）。
- **数据库必须有连接池限流**（基于 QPS / 并发数）。
- **必须熔断 + 降级**（下游故障不影响上游）。

**修正**：2016 年阿里全面推广 Sentinel / Hystrix 限流熔断。

### 5.2 坑 2：2017 双 11 单元化路由失败

**问题**：2017 年双 11 部分用户的请求被路由到错误单元，导致数据不一致。

**根因**：

- 路由规则错误（哈希算法选错）。
- 数据同步延迟（单元间数据复制延迟）。
- 用户 ID 变更（用户改了手机号，导致路由变更）。

**教训**：

- **路由规则必须简单稳定**（基于稳定的 ID，不要基于变化的字段）。
- **数据复制延迟必须有监控**（延迟 < 100 ms）。
- **用户 ID 变更必须有保护**（保留旧单元 30 天缓冲）。

**修正**：阿里建立"**路由灰度发布**"机制，每次规则变更先灰度 1% 流量。

### 5.3 坑 3：2019 双 11 实时大屏延迟过大

**问题**：2019 年双 11 大屏延迟从 1 秒飙升到 30 秒。

**根因**：

- Blink 任务积压（消息量是日常 30 倍）。
- Hologres 查询慢（数据量太大）。
- 网络抖动（跨机房延迟）。

**教训**：

- **实时任务必须有"熔断 + 降级"**——延迟过大时降级到 T+1 数据。
- **OLAP 引擎必须有预聚合**——大屏查询走预聚合表，不走原始数据。
- **跨机房链路必须有冗余**——多链路备份。

**修正**：阿里建立"**大屏 SLA 等级**"——L1（实时）、L2（30 秒延迟）、L3（5 分钟延迟）。

### 5.4 坑 4：2020 双 11 直播带货击穿库存

**问题**：2020 年双 11 李佳琦 / 薇娅直播带货瞬间打爆库存系统。

**根因**：

- 库存扣减走同步链路，没有限流。
- 直播带货瞬时流量是日常的 100 倍。
- 库存预扣 + 异步确认机制不完善。

**教训**：

- **库存扣减必须有限流**（基于 QPS）。
- **必须支持秒杀级异步扣减**（排队 + 异步确认）。
- **直播带货需要单独的链路**（不走主链路）。

**修正**：阿里建立"**直播专属链路**"——直播带货走专用集群，与主链路隔离。

### 5.5 坑 5：2023 双 11 大模型应用"过度承诺"

**问题**：2023 年阿里对外宣传"大模型全面赋能双 11"，但部分场景功能不稳定。

**事实表现**：

- 智能客服回答错误率高。
- 智能营销文案质量参差。
- 智能决策推荐不准。

**根因**：

- 大模型在垂直场景下表现不稳定。
- 缺乏垂直场景的微调数据。
- 大模型推理延迟与成本不达预期。

**教训**：

- **大模型不是银弹**——必须垂直场景微调。
- **必须有人工兜底**——大模型不准时人工接管。
- **必须建立"模型评估指标"**——准确率、延迟、成本三大指标。

**修正**：阿里建立"**大模型 + 人工兜底**"机制，2024 年效果显著提升。

## 6. 复用经验

### 6.1 适合谁学

#### 6.1.1 任何有大促 / 高并发场景的企业

- **典型**：电商、金融、出行、游戏、社交平台。
- **原因**：高并发稳定性是普适需求。

#### 6.1.2 强实时业务

- **典型**：实时推荐、实时风控、实时调度。
- **原因**：实时 + 高并发是最大挑战。

#### 6.1.3 多端联动的复杂业务

- **典型**：跨多个子业务、跨多个客户端。
- **原因**：全链路稳定性需要。

#### 6.1.4 强监管业务

- **典型**：金融、医疗、政企。
- **原因**：稳定性 = 合规的一部分。

### 6.2 不适合谁学

#### 6.2.1 流量小的业务

- **反例**：B 端 SaaS、企业内部系统。
- **原因**：没有高并发场景，学了也没用。

#### 6.2.2 单一系统的业务

- **反例**：单一产品的 SaaS。
- **原因**：不需要全链路稳定性。

#### 6.2.3 业务尚未稳定的早期公司

- **反例**：业务模式每周变化。
- **原因**：稳定性体系需要业务稳定。

### 6.3 关键可复用资产

#### 6.3.1 容量规划

- **流量预测模型**：基于历史 + 业务目标 + 行业大盘 + 安全系数。
- **容量评估清单**：每个系统的容量评估 SOP。

#### 6.3.2 全链路压测

- **影子表 + 影子链路**：阿里 PTS 验证。
- **PTS 平台**：阿里云对外销售的商业产品。

#### 6.3.3 单元化 + 异地多活

- **路由层**：基于 ID 哈希的单元路由。
- **数据层**：单元独立数据库 + 跨单元数据同步。
- **GSLB**：基于 LBS / 运营商的流量调度。

#### 6.3.4 限流降级熔断

- **Sentinel**：阿里开源的限流熔断组件（Java 生态标准）。
- **AHAS**：阿里云商业版的 HA 服务。

#### 6.3.5 实时大屏

- **Blink + Hologres + 自研可视化**：阿里内部栈。
- **Databricks / Snowflake + Superset**：海外替代方案。

#### 6.3.6 值班机制

- **三级指挥体系**：集团总指挥 + 业务域指挥 + 系统 owner。
- **应急手册**：每个系统的应急预案。
- **沟通工具**：钉钉 / 飞书 / 企微。

### 6.4 复用清单（Checklist）

#### 6.4.1 战略层

- [ ] 是否定义了"大促稳定性 SLA"？
- [ ] 是否有"集团总指挥 + 业务域指挥 + 系统 owner"三级组织？

## 7. 与同类案例对比

### 7.1 对比维度

| 维度 | 阿里双 11 | 京东 618 | 美团外卖 | 携程节假日 |
| --- | --- | --- | --- | --- |
| 峰值流量 | 70 万/秒 | 50 万/秒 | 100 万/秒 | 10 万/秒 |
| 持续时间 | 24 小时 | 24 小时 | 每日峰值 | 节假日峰值 |
| 复杂度 | 200+ 系统 | 150+ 系统 | 100+ 系统 | 50+ 系统 |
| 异地多活 | 是 | 是 | 是 | 是 |
| 单元化 | 是 | 是 | 部分 | 部分 |
| 大模型应用 | 全面 | 部分 | 部分 | 试点 |

### 7.2 取舍

- **阿里双 11 = 极致稳定性 + 全链路 + AI 化**——每个细节都做到极致。
- **京东 618 = 自营 + 仓配一体化**——稳定性挑战在仓配而非在线。
- **美团外卖 = 实时调度 + 复杂链路**——稳定性挑战在实时调度。
- **携程节假日 = 业务集中度 + 突发性**——稳定性挑战在突发性。

**对架构师的启示**：

- **阿里模式 = "体系化 + 极致"**——适合头部企业、头部业务。
- **中型企业**：参考"单点突破"——先做限流 + 压测，再做单元化。
- **小型企业**：先做容量评估 + 预案体系，再逐步演进。
