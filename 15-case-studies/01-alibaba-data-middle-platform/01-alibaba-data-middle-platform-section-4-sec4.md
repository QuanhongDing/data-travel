## 4. 架构演进

[§ 3](01-alibaba-data-middle-platform-section-3-sec3.md) 回答的是「哪条挑战逼出了哪个应对结构、它的代价与失效点在哪」。本节回答下一个问题：**这些结构是分几步装上去的，为什么不能换序，装的过程中原来那些烟囱系统怎么办。**

> **证据档位**：本节【公开】条目标出产品与出处方向（产品线迭代快，不锁定版本年份）；**沿用本案例材料的年份与数字一律按【经验】使用——只取量级、不取精确值**；【推算】写出推导链。需要处给出可自行核验的方向（例：以阿里云各产品官方文档、阿里技术官方渠道发布的历年双 11 复盘为准）。

本文件对两类读者给的入口不同。**要把混乱的存量收进一套体系的人**（多个 BU 各自建仓、口径对不上）从 4.1 的 Step 1–3 顺着走，4.4 是重点。**已经在集中化路上、现在要引实时与 AI 的人**从 4.1 的 Step 4 起读，并把 4.4 的「双轨与退出条件」当作返工的护栏——集中化一旦做成，之后每一步都在别人的存量上动土。

### 4.1 落地步骤

**Step 1：统一存储与分层（【经验】约 3–5 年，随 BU 数量与要替换掉的存量引擎数量变）**

起点是烟囱态：淘宝用 Oracle + IBM 小型机 + Datastage（商业 ETL 工具），支付宝用 Oracle + 内存库 + BO（商业分析工具），B2B 用 SQL Server + SSIS，阿里云用 MySQL + 自研 ETL【经验：沿用案例材料的形态，产品名保留、型号与版本只按量级使用】。三个问题同时出现——单 BU 数据孤岛、跨 BU 报表只能靠 Excel 邮件合并、Oracle 单机在数据量上来后扛不住；更根本的是**没有集团视角的"用户"概念，同一个手机号在三个系统里是三个 customer_id**。案例材料记下的教训是：早期「先跑起来再说」的文化在数据领域留下了高额技术债——这也是本节每一步都要先把规范与平台校验补上的原因。

- **做什么**：先把明细放到一个引擎里——把各 BU 的明细按统一四层模型（ODS / DWD / DWS / ADS）落进同一套引擎（这一步在对外体系里对应 **OneData**，即统一存储、分层与建模规范），每个 BU 必须把数据按规范进 DWD 层；批式异构同步用统一的数据集成框架，并把不稳定的调度与旧引擎换成自研的、能承载规模的引擎与调度（对应 ODPS → MaxCompute 这条线）。
- **产物**：一套集团级分层数仓 + 分层与命名规范 + 每张表带 Owner 字段的表清单。
- **判据**：抽 3 张 DWD 表，**粒度声明是否写在表注释里且与分区键一致**、Owner 是否写到人；再抽 3 个 BU 的同一个实体，看能否在 DWD 层用同一套维度关联起来——关不上，说明这一层还只是"放在一起的方案"，不是"一层公共层"。
- **为什么必须这一步、为什么在最前**：因为"同一个数"这件事在物理上要求明细能互相连接，而连接的前提是它们在同一套引擎、同一套分层约束里；数据没放在一起时，任何统一口径的动作都只能在各 BU 的地盘上把规范抄一遍，抄完仍然对不上。代价立刻出现：**因为集团层成为所有建模动作的必经评审点，所以 BU 第一次失去了"我自己快"的选项**——这正是案例材料里"集团数仓被吐槽过度中心化"的成因，也是下一步必须马上给出口的理由。

**案例材料给出的关键节点**：2010 年基于 Hadoop 自研 ODPS（后更名 MaxCompute）、2011 年成立集团数据部门统一建设集团级数仓、2012 年双 11 数据首次全部跑在自研 Hadoop 集群上、2013 年数据平台部成立【经验：年份按量级使用，具体以阿里官方材料为准】。

这一步完成后的形态（V2 阶段的链路，案例材料给出的口径【经验】）：

```text
[业务库] → [统一集成框架：DataX / DataX-Proto] → [HDFS / ODPS 自研引擎]
        → [Hive / SQL 分层加工] → [MySQL / BI 出口]
────────────────────────────────────────────────
同期的三个遗留问题：
  · 调度系统 Oozie 与自研调度混用 → 大促前先坏的是调度
  · 实时能力薄弱，T+1 是常态 → 业务动作等不了第二天的数
  · 没有统一实体概念 → 同一个手机号在三个系统里是三个 id
```

**Step 2：统一实体（【经验】约 2–3 年；随要贯通的主实体条数与标识质量变，三条实体不要绑成一个截止日）**

- **做什么**：建统一身份中心与 ID 映射服务（ID Center / ID Mapping Service）与实体库 OneEntity（用户 / 商品 / 店铺 / 内容 / 卡券），配分布式 ID 生成器（Snowflake 一类的算法，解决"多系统各自生成、无法比对"的问题）；强标识（手机号 / 证件 / 邮箱）走 hash 比对，弱标识（设备指纹 + LBS + 行为序列）在图库上做关系匹配，字符串相似 + 向量相似（Embedding）做模糊兜底；**映射冲突进入仲裁队列，由跨 BU 治理组织裁决**，不留在服务里静默处理。
- **产物**：OneID 映射服务 + 实体库 + 冲突仲裁队列 + 一张「哪些实体已统一」的进度表（用户 / 商品 / 订单分别到什么状态）。
- **判据**：抽 3 个**能人工证实的跨 BU 同一个人**，看能否映射到同一 ID；再抽 3 条映射结果，看系统能否说出**这条映射依据的是哪一条标识**。说不出依据的映射，就是将来会错的那一批。
- **为什么必须这一步、为什么在 Step 1 与 Step 3 之间**：一句话记法是「OneID 先于统一指标」：因为指标统一的前提是"同一个实体"——实体没统一时，同一个指标名在不同 BU 的分子分母都不一样，值统一不了。它必须晚于 Step 1（要在同一套引擎里比对全量标识），必须早于 Step 3（口径建在两套实体上之后，返工要重算全部历史）。**因为事实表只引用统一代理键与一致性维度，所以"按用户汇总"在任何业务过程里都会得到同一个数；代价是实体定义成为所有变更的必经审批点，而映射服务本身是强单点——映射错一次，所有下游一起错。** 案例材料给出的完成顺序是**用户（2017）→ 商品（2018）→ 订单（2019）**【经验：年份按量级使用，具体以阿里官方材料为准】——这个顺序本身就是一条判据：先做用户，因为它是所有分析的公共维度；商品与订单随后，因为它们之间还要再对一次口径。**不要一次宣布"全部实体统一"**，那等于把三个不同量级的项目绑成一个截止日。

**Step 3：统一指标口径（【经验】约 1–2 年到平台可用；随存量指标数量与争议数量变）**

- **做什么**：建指标平台（对应 **OneMetric**），把指标争议收进登记入口：每个指标登记四件套——**业务定义 / 计算逻辑 / 数据来源 / Owner**；指标按原子、派生、复合三类分层管理；变更走审批，跨 BU 争议交仲裁；指标血缘一路可追回 DWD 表。
- **产物**：指标平台里的指标清单（含 Owner）+ 每类指标的登记模板 + 变更审批记录。
- **判据**：抽 3 个历史上的争议指标，看它是否**唯一一处定义**、引用它的看板是否都已改指过去；再数一次「同一个指标名有几处实现」，这个数必须等于 1。
- **为什么在这个位置**：必须晚于 Step 2（实体不同则口径不可比），必须早于对外发布（看板一旦上线就成事实标准，事后收敛的成本随引用数上升）。案例材料给出的起点很典型：同一指标（GMV 一类）在不同团队存在多套定义，靠月度会议仲裁【经验：数量按量级使用，本节不引用具体套数】——月度仲裁本身就是"指标平台缺位"的症状。

**Step 4：按延迟分档上实时，并让流批同源（【经验】约 2–4 年；随要求实时的消费方数量与纠错窗口的长短变）**

- **做什么**：为每条"要实时"的需求先写下消费方、延迟目标与纠错窗口。实时计算选自研引擎（Blink，基于 Flink 改造，优化方向是状态性能、精确一次语义与调度延迟，其成果后来回流到上游开源主线【经验：可自行核验的方向是 Apache Flink 代码库与版本发布说明】），首轮承压发生在 2016 年的大促【经验：年份按量级使用】。典型消费方与延迟量级【经验：大屏在秒级、风控与推荐在百毫秒量级，具体数字以阿里官方复盘为准】：实时大屏、交易风控、首页推荐。再往后把批与流做成同源——同一份业务逻辑，批模式与流模式两种执行，底层用开放表格式（Iceberg / Hudi 一类）加自研批引擎承接，这一形态在 2019 年前后大规模落地【经验：时点按量级使用】。
- **产物**：一张《延迟分档表》（毫秒 / 秒 / 分钟 / T+1，各档列出指标与消费方）+ 每档的重跑方案 + 流批同源作业清单。
- **判据**：抽 3 个实时指标，问**改一次口径要动几个文件**（同源时答案应为 1）；再问每条链路的纠错窗口有多长——答不出来的指标不该进流。
- **为什么在这个位置**：流链路的产出无法自证对错，它需要一个已被信任的批口径作为基准；先上流会出现"实时与离线哪个对"说不清的局面（§3.2.2 已给出这条结构的失效点与代价，此处只讲顺序）。

**Step 5：把稳定性做成可事先验证的（【经验】约 1–2 年；随每年可用于演练的大促窗口数量变）**

- **做什么**：影子表 + 影子链路（压测流量走完整链路但落影子表，不污染生产）、流量回放、容量规划（历史峰值 × 安全系数【经验：常见区间 1.5–2 倍，随业务对失败的容忍度变】），用阿里自研的压测平台 **PTS（Performance Testing Service）** 统一执行（案例材料记其与 JMeter 兼容，具体能力以阿里云官方文档当前版本为准）；单元化把用户按 ID 哈希进互不影响的单元，每单元独立部署、独立存储、独立流量，并做异地多活（上海 / 张北 / 杭州 / 深圳多机房互备，单机房故障不影响全局）。案例材料给出的节点是 2017 年大促实现全面单元化部署【经验：年份、机房名单与范围按量级使用】。
- **产物**：一份压测报告（含瓶颈位置与降级顺序）+ 单元化路由规则 + **全局唯一操作清单**。
- **判据**：大促前能否在不影响生产数据的前提下把链路压到目标峰值的 1.5 倍以上并指出瓶颈；清单里的"全局唯一操作"（全站唯一券、跨单元对账一类）是否**每一条都有归属**。
- **为什么必须在这一位置、且压测先于单元化**：因为单元化会否掉一切跨单元操作，而"哪些操作必须全局唯一"只有压测与演练才会暴露；先单元化再压测，得到的是无法解释的失败。它也必须晚于 Step 4——实时链路是压测里最难过的一环，先有稳定的批与流，压测才有一个不动的靶子。

**Step 6：把能力封成产品（【经验】约 2–3 年；对外售卖那一段随客户支持与版本兼容的建制速度变）**

- **做什么**：让分析师写的 SQL 经审核后自动生成 API，经统一网关与内部 RPC 框架（HSF / Dubbo 一类）暴露，算法与前端直接调用，对外按统一品牌输出数据服务（对外体系名是 **OneService**，即把"数据 → 服务"的出口收敛到一处）。再把内部能力按五类模块封成套件：**数据集成（集成框架的商业版）、数据开发（DataWorks）、数据治理（数据地图 + 指标平台）、数据服务（统一 API 产品，案例材料记为 Quick API）、数据应用（Quick BI + Quick Audience / Quick Audience for Marketing，即 BI 与人群运营类产品）**；对外客户的形态以零售、消费品、制造等行业的头部公司为主【经验：沿用案例材料的客户形态（蒙牛 / 波司登 / 星巴克 / 上汽通用一类），具体客户名单以阿里云官方公告为准】。
- **产物**：数据服务清单（每个 API 有 Owner、配额、审核记录）+ 对外产品模块与内部组件的对应表。
- **判据**：抽 3 个数据服务，能否回答**谁在调它、配额多少、谁批的**；对外模块能否一一对应回内部组件——对应不上的，说明产品化的是包装而不是能力。
- **为什么在这一位置**：因为它把"复用"从口号变成动作——消费方不再重写 SQL 而是调接口，复用率第一次可统计；但对外售卖必须晚于内部跑顺，否则客户会先发现它的缺陷。

**Step 7：AI 中台化（【经验】没有终点；首轮可用场景约 1–2 年，之后是持续的语义与权限补全）**

- **做什么**：让平台覆盖特征工程 → 训练 → 部署 → 在线推理全链路（机器学习平台一类的能力）——该平台在案例材料里的典型应用是淘宝商品推荐、支付宝风控与菜鸟物流预测【经验：应用场景沿用案例材料，年份按量级使用】；再把已有资产按四种角色映射给模型使用——数据成为知识（检索增强）、指标成为可调用工具、统一实体成为长期记忆、数据服务成为工具集；最后在大模型应用编排平台上组装应用。案例材料给出的落地形态是模型被用于客服、营销文案、代码生成与数据查询等场景，并产出过 **通义晓蜜**（智能客服）与 **通义灵码**（编程助手）这两个面向客服与编程的专门产品【经验：场景与产品形态沿用案例材料的量级描述；**具体产品名、版本号与效果数字请以阿里云官方发布记录与模型卡片为准**】。
- **产物**：一份《中台能力 → Agent 能力》映射表 + 每个"工具"的权限与口径说明 + 一份评估集。
- **判据**：抽 3 个业务问题，看 Agent 能否**只在被授权的指标与实体范围内作答**；再抽 3 个"工具"，看它的返回口径能否指回指标平台里的那一份唯一定义。指不回去，说明 Agent 拿到的是另一套口径。
- **为什么在最后**：一句话记法是「语义与工具先于模型接入」：因为 Agent 取数的可信度上限等于语义层与指标平台的完备度，而这项工作没有尽头——它的正确形态是持续补业务含义与权限，而不是一次性建成。

这一步之后的当前状态（案例材料口径【经验】）：数据中台、业务中台与 AI 中台三件套融合；基础设施侧收敛为"大规模批引擎 + 交互式分析 + 机器学习平台 + 大模型应用编排平台"这一组产品；数据开发与治理工作台把从集成到模型训练、再到应用编排的链路放进同一套工作流；方向表述是「AI Native 数据中台」，也就是"从工具平台升级为智能平台"。其中**收敛**这个词比"升级"更值得注意——它意味着中台的下一段竞争力不在新增组件，而在让已有组件被模型安全地调用。

七步与几个演进阶段的对应（阶段名沿用案例材料的版本号，年份按量级使用【经验】）：

| 步骤 | 对应阶段与大致年份 | 这一步产出的"可回退果实" | 明确不做 |
| --- | --- | --- | --- |
| Step 1 统一存储与分层 | V1 烟囱林立（2003–2009）→ V2 集团数仓与自研引擎（2010–2014） | 只读镜像与影子对账 | 不先做指标平台：实体没统一，口径统一不起来 |
| Step 2 统一实体 | V3 方法论定型期（2015–2018），贯通跨到 V4 早期：用户 2017 → 商品 2018 → 订单 2019 | 映射版本可回放、错误可局部撤销 | 不追求一次覆盖全部实体：先在用户上跑通 |
| Step 3 统一指标 | V4 中后期（案例材料记 OneMetric 为 2020 后提出） | 指标清单与唯一引用 | 不先对外发布口径 |
| Step 4 分档上实时、流批同源 | V4 实时化期（2015–2022） | 明细留存以支撑重算 | 不把实时链路当作对外权威口径 |
| Step 5 压测与单元化 | V4 稳定性期（2017 前后起） | 压测报告与降级顺序 | 不先单元化再压测 |
| Step 6 服务 API 化与对外套件 | V5 产品化期（2018–2021） | 内部无豁免期 | 不在内部跑顺之前售卖 |
| Step 7 AI 中台化 | V6 AI 中台期（2020 之后） | 评估集与被授权工具清单 | 不在语义层可用之前接入模型 |

**这张表的两列口径不同，读的时候要分清**：**步骤号是依赖顺序，年份列是案例材料对各阶段的原始划分**，两者并不单调——产品化的起步年份（V5，2018 起）早于指标统一的提出年份（2020 前后），因为对外卖的是当时已经跑顺的模块（数据开发工作台 2018 年即对外商业化），而指标统一的公共口径要等实体贯通（订单 2019）之后才具备条件。按表复述时序时以年份列为准，按表安排工期时以步骤号为准。

**这一串里最常被跳过的是 Step 2（统一实体）**：它投入大、见效慢、且大部分时间不在业务方的视野里，于是团队往往直接从 Step 1 跳到 Step 3，先做指标平台。**跳过后第一个出问题的时点出现在第一次跨 BU 口径对齐会议**：同一个指标两边都"按定义算"却仍对不上，追下去才发现分母上的用户是两套实体；此时已经有很多指标建在这两套实体之上，返工面是全部跨 BU 指标与它们的历史。

### 4.2 关键技术点

**把规范写进平台校验，而不是写进文档**

- **做法**：命名、分层、Owner、密级这些约束做成平台内的校验规则——**不填不许发布**，而不是发布后再检查；变更走统一评审入口。
- **机制**：因为规范的执行成本被转移给了工具（一次配置，长期生效），而文档规范的执行成本由每个人每次重复支付，所以只有前者能稳定。这也是 §6 反复出现的那句判断：「统一的不是系统，而是建模方法与规范」。
- **失效条件**：**当校验规则多于团队能理解的条数（【经验】：大致在十几条量级）时，这条会坏在"规则被绕过"上**——提交人开始用更长的时间做形式合规，实质内容反而没人看。症状：命名全部合规但同一主题域出现了三个近似命名，说明规则没覆盖到真正需要裁决的层面。
- **档位**：【经验】。

**ID 映射的冲突仲裁与可回滚**

- **做法**：映射结果带置信度与依据标识；冲突进队列人工裁决；**映射版本化**，支持按时间点重放（"上个月那条映射当时是怎么判的"）。
- **机制**：因为实体合并是不可逆操作——两个实体合并之后无法凭数据自行拆开，所以唯一的保护是保留裁决记录与版本，让错误可以被定位并局部回退，而不是全量重算。
- **失效条件**：**当弱标识权重被上调以提升覆盖时，这条会坏在"误合并"上**——把两三个不同用户合成一个。症状：某个"用户"的历史跨越了明显不兼容的地域或设备序列；更隐蔽的是它不会报错，只会让所有涉及该用户的指标轻微偏移。
- **档位**：【经验】。

**指标定义的四件套与唯一引用**

- **做法**：业务定义、计算逻辑、数据来源、Owner 四项齐全才允许登记；下游看板与接口**引用**定义而不是复制 SQL；口径变更前先列出全部引用方。
- **机制**：因为"改一次口径要动几个地方"这个数字可以被直接数出来，所以它同时是治理成熟度最便宜的度量——把目标定在 1 是可检验的，而定在"提升一致性"不是。
- **失效条件**：**当指标数量超过平台 Owner 能逐条审阅的规模时，这条会坏在"登记即完成"上**——指标登记了，但没人检查它是否与已有指标重复。症状：平台上出现语义重复的多个指标，各自被不同看板引用。
- **档位**：【经验】。

**流批同源（同一份逻辑两种执行）**

- **做法**：指标逻辑只写一次，批与流各自执行；明细落湖以支撑口径变更后的重算；批与流的依赖关系在同一套编排里显式描述。
- **机制**：因为两侧各写一套时，窗口语义与边界处理的差异会让数值缓慢偏离（且偏在小数点后才被发现），所以同源的真实收益不是省代码，而是**让"两侧对不上"这件事从可能变成不可能**。
- **失效条件**：**当明细没有留存（只留聚合结果）时，这条会坏在"口径改了但历史改不了"上**——新口径与旧历史长期共存，报表上出现一段无法解释的台阶。症状：某指标在某日前后系统性跳变，且没人能给出那次变更的完整影响面。
- **档位**：【经验】。

**影子链路压测**

- **做法**：压测流量带标记走完整链路，写入影子表；用历史流量回放逼近真实分布；容量按历史峰值乘安全系数配置；压测不通过的链路不允许在大促当天承担关键职责。
- **机制**：因为链路的瓶颈通常不在单个接口而在依赖组合（缓存击穿、下游限流、资源争抢），所以只有走完整链路且数据被隔离的压测才能给出可信结论——单接口压测给出的乐观结论本身就是风险。
- **失效条件**：**当影子写入与生产写入开始共享资源（同一个缓存、同一份配额）时，这条会坏在"压测把生产压垮"上**。症状：压测期间生产出现与压测无关的延迟抖动；这类事故的复盘通常落在"谁批准了这次压测"。
- **档位**：安全系数区间为【经验】。

**单元化路由与「全局唯一操作」清单**

- **做法**：路由按用户 ID 稳定哈希；消灭跨单元访问；把无法消除的全局操作（全站唯一权益、跨单元对账、全局排序）逐条列出并单独设计归属。
- **机制**：因为单元化的隔离前提是"单元之间不需要互相确认"，所以那份清单本质上是在给隔离边界上的例外做登记；不被登记的跨单元调用，就是故障时传不出去的那一段。
- **失效条件**：**当业务新增一个必须全局唯一的玩法时，这条会坏在"跨单元调用成为新的全局单点"上**。症状：单单元故障演练时，被压在单元内的故障仍然扩散，而扩散路径正是清单上没有的那几条调用。
- **档位**：【经验】。

**数据服务的 API 化与配额**

- **做法**：SQL 经审核后生成 API，服务带 Owner、调用配额、字段级权限与审计日志；对外暴露前先在内部跑一段"无豁免期"。
- **机制**：因为服务化的真正门槛不是生成 API 而是**回答"谁在调、有没有越权"**，所以配额与审计必须在服务上线之前就位；上线后再补，等于默认接受一段无法回溯的调用历史。
- **失效条件**：**当服务数量增长到无人能列出全量清单时，这条会坏在"影子服务"上**——有人绕过网关直连数据。症状：审计日志里某个上游表的访问量与看板口径对不上。
- **档位**：【经验】。

**混部下的资源声明与优先级**

- **做法**：每一个离线作业在提交时声明资源需求与优先级；大促期间可临时扩缩容，并明确"优先保在线与实时、离线按优先级让路"的顺序，把这个顺序写成规则而不是临场决定。
- **机制**：因为资源池化之后作业之间从"互不相干"变成"互相抢占"，所以声明资源与优先级不是治理要求，而是**让抢占变得可观测、可排序**的必要条件；没有声明时，抢占照样发生，只是没有任何人能解释谁抢了谁。
- **失效条件**：**当作业数量增长到"没人看过优先级字段"时，这条会坏在"重要任务被不重要任务挤掉"上**——不是调度器偏心，而是两者都被声明成了同一个级别。症状：核心报表在大促期间晚出，而占用资源的是一批无人认领的历史任务。
- **档位**：【经验】。

**变更影响面与评审（CR）门禁**

- **做法**：表结构与口径变更必须走统一评审；评审材料里必须包含血缘影响面（下游表、指标、看板、责任人）与迁移方案；影响面超阈值或涉及关键资产的变更需要 Owner 会签。
- **机制**：因为血缘的门禁作用取决于它挂在哪个环节——放在文档里没人看，挂在发布流程上则每次变更都必须正面回答影响面——所以这一条的本质是**把一条展示能力接到一个控制点上**（对照 §3.2.4 里"公共层被绕过"的失效点，门禁是唯一能拦住它的机制）。
- **失效条件**：**当门禁的粒度只到表级时，这条会坏在"过度阻断后被绕过"上**——改一个字段被当成改整张表对待，于是团队开始申请批量例外。症状：例外申请的批准率接近 100%【经验：定性描述、非统计结论；可抽查一段时间内的例外单，看驳回比例是否显著低于普通变更】，门禁形式上还在，实质上已经失效。
- **档位**：【经验】。

### 4.3 工具链与平台

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 大规模计算引擎 | 自研引擎（ODPS → MaxCompute）；开源 Hive on Hadoop | 数据量到 EB 级、且是公有云多租户共享集群时，需要的是隔离与企业级安全，这两点在开源方案上缺少成熟机制 | 沿用开源：PB 级可用，但多租户与安全要在应用层自己补，补出来的东西没人维护 |
| 数据集成 | 统一集成框架（DataX / DataX-Proto 这类内部与开源变体） | 源系统种类多、且每个源都要有失败重试与一致性校验时选统一框架 | 每接一个源写一套同步：接入成本随源数线性增长，且没有统一的重试与告警 |
| 开发与治理工作台 | DataWorks（2018 年对外商业化；前身为内部数据开发工具，案例材料记其旧名为「采云间」，以阿里云官方产品文档为准） | 规范需要被平台强制（命名 / 分层 / Owner 校验）时，选"开发 + 调度 + 治理 + 服务"一体的工作台；只需要跑 SQL 时，轻量调度即可 | 规范只写在文档里：靠自觉执行必然衰减，三个月后没人记得分层规则【经验：口语化的时间量级，非统计结论】 |
| 调度 | 自研调度；Oozie 一类早期组件 | 任务规模到十万级/日【经验：量级沿用案例材料】时，调度稳定性本身成为可用性问题 | 沿用脆弱调度：大促期间调度先宕，它下游的所有数据准备一起停 |
| 交互式分析 | 与仓同源的交互式引擎（Hologres 一类）；自建 OLAP | 需要"高并发点查 + 与仓内明细同口径"时选与仓同源的引擎 | 另建一套 OLAP：又多一份数据副本和一个要同步的口径 |
| 实时计算 | 自研实时引擎 Blink（基于 Flink 的改造版）；上游开源 Flink 主线；Spark 流式 | 有状态 + 精确一次 + 低调度延迟三个都要时，选专门为流设计的引擎 | 用批引擎近似实时：延迟不达标，业务方会绕过平台自己写脚本 |
| 表格式与流批一体 | 开放表格式（Iceberg / Hudi 一类）+ 自研批引擎 | 需要"同一份逻辑两种执行"且要被多个引擎读时，必须有开放表格式 | 两套逻辑两份口径：改一次口径要动几处、且不确定是否改全 |
| 图与实体关系 | 图数据库 GDB（实体识别与关系遍历） | 实体识别要做多跳关系遍历时，关系库的连表成本会随跳数爆炸 | 用关系库模拟图：查询写得出，但跑不动 |
| 指标与治理 | 指标平台 + 数据地图 | 口径必须有唯一登记入口、争议必须有裁决记录时，两者缺一不可 | 靠会议仲裁：同样的争议会重复出现，每次都要重新建立共识 |
| 服务暴露 | 内部 RPC 框架（HSF / Dubbo 一类）+ 统一网关（API Gateway）+ 对外数据服务品牌（**OneService** 下的 iGraph / iPush / iRec，分别面向 OLAP / 推送 / 推荐） | 数据服务要被算法与前端直接调用、且要有配额与审计时，走统一网关 | 消费方各自写 SQL：复用率无法统计，"谁在用"没有答案 |
| 大模型与 AI 应用 | 机器学习平台 PAI（训练 / 部署 / 推理）+ 大模型应用编排平台（百炼 / Model Studio）+ 通义 / Qwen 系列基础模型【公开：出处为阿里云官方产品文档；产品线迭代快，此处不锁定版本年份——具体版本与能力请以官方文档当前版本为准，可按「阿里云 PAI」「阿里云百炼 Model Studio」「通义千问 Qwen」检索核验】 | 数据与训练是否一体化，决定 AI 能不能用上已有资产 | 另起炉灶：数据资产无法成为 AI 资产，同一件事被重建一遍 |
| 稳定性验证 | 压测平台（与 JMeter 兼容的一类）+ 流量回放 | 压测必须走完整链路且不污染生产，否则得到的乐观结论本身就是风险 | 只压接口：压不出依赖组合里的瓶颈 |
| 商业化输出 | 商业套件：数据集成（集成框架商业版）/ 数据开发（DataWorks）/ 数据治理（数据地图 + 指标平台）/ 数据服务（统一 API 产品，案例材料记为 Quick API）/ 数据应用（Quick BI + Quick Audience / Quick Audience for Marketing） | 内部是否已经跑顺；跑顺之后再把模块产品化，客户名单与模块一一对应 | 未跑顺就出售：客户比你先发现缺陷，支持成本反噬内部团队 |

**这一类里最容易被误选的一条，是把「买一套工作台」当成「建成了中台」。** 工作台解决的是"有没有统一的入口"，而中台真正的门槛是"两个业务对同一指标有不同定义时，是允许两套定义，还是必须讨论出一套"——前者会让例外越加越多，最后"统一"只剩名义。误选的典型后果是：平台上线、任务迁上来、命名也合规了，但跨 BU 的同一个数仍然对不上，团队于是把问题归因于"工具不好用"，再买一套工具。判据很简单：**上次两个部门对同一指标意见不一致时，最后是谁拍的板、记录在哪。**

### 4.4 存量迁移

**① 先做一件立刻见效且可回退的事**

不要一上来就迁系统。第一件事是**只读镜像 + 来源标注**：把源表以只读方式同步进新体系，消费方一个都不动，同时给现有报表逐个标上"此数来自 X"。它不改任何业务逻辑、随时可撤销，但立刻产出两个东西——一份"没有权威来源"的清单，和一份按引用面排出的迁移优先级。第二件事是**影子对账**：在新体系里按统一口径重算几个关键指标，与旧口径逐日比对，差异先记录、先解释，不对外切换。这两件事做完，你才第一次拥有了"切换是否安全"的判断依据。

**② 历史资产按处置成本与引用面分三档**

| 档 | 判据 | 处置 | 不要做什么 |
| --- | --- | --- | --- |
| 全部返工 | 被对外数字引用、且在多个看板重复出现 | 按统一口径重建，旧实现下线 | 不要"照抄到新体系再慢慢改"——照抄出来的第二份实现会立刻成为新的分叉点 |
| 只改动的部分 | 仍在使用，但引用面只在一个团队内 | 不排独立窗口，改到它的时候顺手迁，迁完即登记 | 不要为它立项：调度成本高于收益 |
| 打标挂账 | 说不清谁在用，或访问日志显示长期无读 | 登记为「待定」+ 加访问统计，设到期日，无人认领即下线 | 不要直接删（那是别人的口径依据），也不要无限挂账（挂账必须有到期日） |

**③ 双轨要维持多久、怎么维持**

双轨不是过渡状态，是**一个带截止日的状态**。它的成本是同一件事有两份实现：两套调度、两套告警、每次口径变更要在两侧同时改。可执行的维持规则只有一条——**每次口径变更必须同时改两侧并跑一次对账**。任何一次"这次先改一边"的例外，都会让目标侧在切换前就落后于源侧，等到要切的时候发现要重新对齐一遍，于是并行期再延一期。这也解释了为什么"5 套数仓并成 1 套"用了数年而不是一个项目周期【经验：时间跨度按量级使用】：真正长的不是搬迁，是让每个 BU 停止在新旧两侧同时加东西。

**④ 什么信号说明可以退出双轨**

退出条件必须写在开工之前，写成「哪一天 / 以哪张报表 / 以哪个指标为准」，并当作验收标准。可观察的信号有三个：**对账差异连续若干周期为零且差异原因可解释**、**消费方主动切到新侧（而不是被通知）**、**旧侧连续一段时间没有任何查询**。三者满足两个即可安排下线；只满足第一个时不要切——那只说明新侧"对得上"，还不说明它被信任。

**迁移期的三条护栏**：**护栏一，新需求一律进新体系**——迁移期的最大风险不是迁得慢，而是两边同时加东西；只要新需求还允许落在旧侧，迁移的完成日就会不断后移。**护栏二，迁移批次按"重复面"排序，不按"表数"排序**——重复面最大的是用户、商品、订单这几层公共加工，先并它们，收益立刻可见；按表数最多的 BU 开刀，得到的是一个内部结构各异的孤岛换了地方。**护栏三，每一批都要有一个可下线的东西**——批次的验收标准不是"迁完了"，而是"旧侧的某个东西可以关掉了"；没有可关掉的东西，说明这一批只是在做双写。

**五类存量迁移的具体形态**：**烟囱系统 → 集团数仓**，迁的是数据的位置与建模规范（OneData），最慢的一步是让各 BU 接受"对外数字以集团口径为准"；**多套数仓 → 一套**，迁的是重复的公共层加工（同一份加工在多套里各做一遍），做法是先找出重复面最大的那几层（用户、商品、订单），而不是从表数最多的 BU 开刀；**旧引擎与旧调度 → 自研引擎与统一调度**，必须先迁任务再下线组件，中间留一段双跑期用来比对产出；**内部能力 → 对外套件**，迁的是责任边界（客户支持、版本兼容、SLA），这一步的成本几乎全在组织而不在技术；**中台 → AI 中台**，迁的是资产的"可被机器理解"程度——元数据、口径、权限先补齐，模型才有东西可用。

### 4.5 模板 / 示例

**模板 1：分层与表命名（含 DDL 骨架）**

```text
命名：<层>_<业务域>_<主题域>_<粒度>_<统计周期>
  层       ods / dwd / dws / ads（dim 单独成层）
  业务域   trade / user / item / logistics …
  粒度     1d / 1h / 1m（或实体粒度，如 user / sku）
  周期     可选，用于快照类表：day / month

CREATE TABLE dwd_trade_order_detail_1d (
  order_id      STRING  COMMENT '订单唯一标识',
  buyer_id      BIGINT  COMMENT '统一用户代理键（OneID）',
  item_id       BIGINT  COMMENT '统一商品代理键',
  pay_amount    DECIMAL(18,2) COMMENT '实付金额，币种=CNY',
  status        STRING  COMMENT '状态机取值：created/paid/shipped/refunded',
  ds            STRING  COMMENT '分区：业务日期'
)
COMMENT '一行一个订单明细；粒度=order_id；Owner=<姓名>；SLA=T+1 08:00'
PARTITIONED BY (ds);
```

**怎么用**：填四类内容——层前缀、业务域、粒度、周期；`COMMENT` 里那四项（粒度、Owner、SLA、状态机取值来源）**必须填**，它们是后面所有判据的依据。**不要照抄字段清单**，字段要按你自己的业务事实表来；也不要照抄 `ds` 这种分区键的名字，要与你的调度日期语义一致。

**模板 2：指标定义（四件套 + 分类）**

```yaml
metric: trade_gmv_paid_1d
name: 已支付成交额
class: 原子指标            # 原子 / 派生 / 复合
definition: 统计已支付订单的实付金额之和，退款订单不计入
caliber: pay_amount 求和；过滤 status in (paid, shipped)；币种统一为 CNY
source:
  table: dwd_trade_order_detail_1d
  fields: [order_id, pay_amount, status]
  grain: order_id
dimensions: [ds, business_unit, channel]
owner: <姓名>              # 写人，不写团队
approval: <变更单编号>      # 每次口径变更留痕
lineage_checked: true      # 变更前已列出全部引用方
```

**怎么用**：填 `definition` 与 `caliber` 时用一句能被两个不同的人写出同一段 SQL 的话——写不出这句话就说明定义还没定下来。`class` 一栏决定审批强度：原子指标变更要重算历史，复合指标变更通常不必。**不要照抄字段名**，`owner` 与 `approval` 两栏不要留空（留空等于没有 Owner 与没有留痕）。

**模板 3：实体映射冲突仲裁工单**

```text
冲突 ID：
候选实体 A / B（各自的标识集合与来源系统）：
判定依据：强标识命中（哪一条） / 弱标识命中（设备 / LBS / 行为序列的具体证据）
置信度与阈值：
裁决：合并 / 不合并 / 挂起
裁决人：<姓名>  日期：<年-月-日>
影响面（合并后需要重算的指标与时间范围）：
回滚方式：撤销本次映射并重放 <起始日期> 之后的指标
```

**怎么用**：填判定依据那一栏时要写到"哪一条标识、什么时间命中"，写不出具体证据的合并一定是错的。**影响面与回滚方式两栏是这份工单存在的理由**——没有它们，仲裁就只是一个人拍板，出错后无法定位。

**模板 4：中台能力 → Agent 能力映射**

| 已有资产 | 映射为模型能力的角色 | 必须一起交付的东西 |
| --- | --- | --- |
| 明细与指标（含口径定义） | 知识（检索增强的语料） | 口径版本与生效时间，避免检索到已作废的定义 |
| 指标接口 | 可调用的工具 | 权限范围、调用配额、返回口径的来源指针 |
| 统一实体（OneID / OneEntity） | 长期记忆 / 会话上下文 | 可删除与可更正的方式（合规要求） |
| 数据服务（API 集合） | 工具集 | 每个服务的 Owner 与变更通知机制 |

**怎么用**：这张表按行填，填不出"必须一起交付的东西"那一栏的资产**先不要给模型用**——因为模型不会像人一样在越权时感到犹豫。**不要照抄资产清单**，你有哪些资产由你的目录决定。

**模板 5：变更评审（CR）一页纸**

```text
变更单编号：            提交人：            日期：
变更对象：<表 / 指标 / 服务>   变更类型：结构变更 / 口径变更 / 调度变更
新口径或新结构：
血缘影响面：下游表 <n> 张、指标 <n> 个、看板 <n> 个、涉及责任人 <列出姓名>
其中关键资产（有对外 SLA / 影响对外数字）：
迁移方案：历史是否重算；重算时间范围与预计耗时
通知记录：已通知的责任人与时间
会签：<姓名>（影响关键资产时必填）
回退方式与保留期：
```

**怎么用**：填「血缘影响面」一栏时，数字必须来自血缘查询而**不是估计**——估计出来的影响面比没有更危险，因为它会被当成依据。**「通知记录」与「回退方式」两栏不要留空**：前者决定事故时责任是否清晰，后者决定出事后多久能恢复。

### 4.6 自检清单

1. 抽 3 张 DWD 表，**粒度声明是否写在表注释里、且与分区键一致**？
2. 抽 3 张核心表，`Owner` 一栏写的是**人名**还是团队名？写团队名的有几张？
3. 抽 3 个能人工证实的跨 BU 同一实体，能否映射到同一 ID？映射结果能否**说出依据的是哪一条标识**？
4. 上次两个部门对同一指标意见不一致时，**是谁拍的板、记录在哪**？
5. 数一遍「同一个指标名有几处实现」，这个数现在是几？与三个月前相比是升还是降（比对间隔按你的版本节奏定，一个季度量级即可【经验】）？
6. 抽 3 条实时链路，**消费方是谁**？把它今天关掉，业务多久出问题？它的纠错窗口有多长？
7. 改一次核心口径，需要动的文件数是几？**流侧与批侧是否同源**？
8. 明细是否留存到足以支撑口径变更后的重算？**上一次口径变更后重算了多长的历史**？
9. 单元化之后，**全局唯一操作清单**上的每一条是否都有归属？最近一次单元故障演练是否暴露过清单外的调用？
10. 抽 3 个数据服务，能否回答**谁在调、配额多少、谁批的**？
11. 上一次大促前的压测，是否走完整链路且**写入被隔离**？报告里有没有指出瓶颈位置？
12. 接入大模型之前，被授权使用的每一项资产是否都有**口径来源指针与删除方式**？

### 4.7 小结

> 本节小结：整个落地过程里唯一那个决定成败的环节，是 **Step 2（统一实体）**。它排在第二、投入最大、且成果在业务侧看不见——正因为它最像"不产出功能的工作"，它最常被跳过，而它一旦被跳过，Step 3 之后的每一个指标体系都建在两套实体上，返工面等于全部跨 BU 指标与它们的历史。**因为实体合并是不可逆的、且错误不会报错只会让数字轻微偏移，所以它必须早于指标统一；代价是它周期长、见效慢，需要有人在看不到成果的两年里持续投入（案例材料给出的贯通顺序是用户 2017 → 商品 2018 → 订单 2019，贯通周期在两年量级【经验：区间约 2–3 年，随要贯通的实体条数与标识质量变；量级由案例材料给出的年份顺序（用户 2017 → 商品 2018 → 订单 2019）相减得出，年份本身按量级使用】）。** 这也解释了本案例里一个反复出现的规律：真正难的从来不是把数据放在一起，而是先决定"什么是同一个东西"。
>
> 💡 **思考锚点**：数一下你平台「同一个指标名有几处实现」——按 §4.6 它应该收敛到 1，现在是几？再把准备纳入统一实体的范围按案例的贯通顺序（用户 → 商品 → 订单，两年量级）排一下：既然实体合并不可逆、且错误只让数字轻微偏移，你把哪个实体放在第一年，凭什么说它的标识质量撑得住？
