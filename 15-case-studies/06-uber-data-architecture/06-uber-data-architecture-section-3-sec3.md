## 3. 架构演进

### 3.1 先看约束：代际不是版本号，是约束的产物

把 Uber 的数据架构读成一张版本升级表，会得出「V1 落后、V5 先进」的错觉。真实情况是：**每一代都是被当时的约束逼出来的唯一解**，代际之间的差别来自约束变了，而不是设计水平变了。Uber 2013 年面对「单库容量上限 + 行程状态被反复更新 + 司机位置每秒百万次量级写入」这几条约束【推算】（「百万次/秒」这一量级的推导见 3.2.2，其中的司机数可替换成你自己的数），在当时的开源生态里确实没有可用解——这才是它自研 Schemaless、后来自研 Hudi 的原因。

最容易被忽略的一条约束是**实时性在不在收入函数里**。Uber 的收入来自「乘客与司机在一次请求内完成匹配」，匹配慢一秒就有人关掉 App，所以实时链路必须落在业务请求路径上。这条约束会把架构推向一个其他公司很少需要的位置：**实时计算结果必须有在线形态**，从而逼出「在线 KV + 特征存储」这一整套东西，而不是只把批处理变快一点。

第二条约束是**写入模式**。一次行程从请求到下客要经历多个状态，同一行主键会在几十分钟内被反复更新；这类数据落在「不可变文件 + 分区重写」的批处理表格式上，每次更新都要放大成一次分区重写。**表格式的选型不是偏好问题，而是写入模式决定的**——这也是本仓库 [§ 7 与同类案例对比](06-uber-data-architecture-section-7-sec7.md) 把写入模式列为第一条判据的原因。

第三条约束是**地理与法域**：多法域（GDPR / CCPA 及各地本地化要求）意味着数据不能无差别汇聚，「全局单点数仓」这个最省事的形态从一开始就不可选。第四条是**组织规模**：千级算法工程师与多个业务线意味着「靠流程统一」的成本随人数超线性增长，只能靠平台（Michelangelo 这类）而不是规范来统一。

**代际是叠加关系，不是替代关系。** 到 2025 年，五套形态仍然同时在线：批处理数仓继续服务稳定的 T+1 报表，分片 KV 与宽列存储继续承担在线点查，湖上表格式继续承载训练与账务数据，实时数仓服务在线特征，AI 数据栈新增检索与上下文层。**这条性质决定了演进策略——每一代都在原有基础上增加一条路径，而不是替换旧路径。** 也正因为旧路径不会消失，本章的「失效点」比「优点」更值得记：一次判断错误会长期留在架构里，而不是随下一次升级消失。

**约束是有价的，可以先估。** 判断某一代是否值得学，最省力的问题是「它的约束在我这里成立吗、强度是多少」：主键更新的行占比、实时结果晚一分钟的业务损失、跨区域数据的比例、在线特征的数量。这四个数字量出来，选型基本自解；量不出来时，任何对标都只是组件崇拜。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 写入模式（行级更新 vs 只追加） | 存储与表格式的选型：更新型数据必须选带主键索引与增量能力的格式 | 「扩容就能解决」——扩容解决吞吐，解决不了「文件格式不支持更新」 |
| 单次请求的延迟预算（匹配在一秒内） | 实时结果必须有在线形态，流计算与在线 KV 必须成对出现 | 「实时就是快一点」——落湖的实时结果仍然要等分钟级 |
| 数据形态多样性（状态机 / 位置流 / 文档 / 知识点） | 多存储并存与各自的契约，而不是一种存储打天下 | 「一种存储统一全公司」——统一的是访问入口，不是存储引擎 |
| 地理分布与法域 | 区域化部署 + 联邦查询 + 删除权路径 | 「中央数仓最省事」——多法域下它不可部署 |
| 组织规模（千级算法工程师、多业务线） | 统一只能靠平台与自助能力，不能靠流程与规范 | 「定好规范就能统一」——规范的效力与人数成反比 |
| 存量资产与迁移成本 | 演进而非重写：每代都保留上一代的可用部分 | 「推倒重来」——迁移成本通常大于新架构带来的收益 |

#### 3.2.1 单库 + 批处理数仓（V1.0，2009–2013）

- **被什么约束逼出来**：起步期数据量在单库容量内，且没有秒级决策需求——此时组件最少就是最优解。
- **结构**：

```text
[MySQL / MongoDB] → [Hadoop + Hive] → [Tableau]
     事务与状态          批处理数仓        呈现与取数
 写入：业务库直连        读取：T+1 全量覆盖（insert overwrite 分区）
```

- **为什么这样设计有效**：因为批处理把「写入」与「读取」在时间上完全分开，T+1 的报表查询不会占用线上事务库的资源；因为 Hive 的一个分区就是一个目录，覆盖写入简单到不需要事务——这正是起步期最需要的性质。
- **代价**：① 延迟被固定为「一天」，任何秒级需求都要另建一条链路；② 单库容量是硬墙，扩容只能停机或分库分表，而分库分表把一致性责任从数据库挪到了应用；③ Hive 表格式是「不可变文件 + 分区重写」，任何行级更新都要重写整个分区；④ 「没有统一的实时计算」意味着每个实时需求各自起一套，重复实现与口径分叉从这里开始。
- **失效点**：当核心数据变成「同一主键被反复更新的状态机」时，不可变文件格式的优点（读快、易并行）反转成缺点（写放大），因为一次字段更新要重写分区内的全部数据文件；当单库接近容量上限时，「加机器」这个最省事的扩容方式失效，因为瓶颈在单库而不在单机。
- **自验方法**：统计核心事实表「每日写入中主键已存在的行占比」；若比例不低且持续上升，说明这套形态已经在失效，而不是「还够用」。
- **真实使用**：Uber 2009–2012 年从 MySQL + MongoDB 起步（[主文件 § 1.1](06-uber-data-architecture.md)），BI 呈现为 Tableau（原 § 3.1 口径）。同类起点在 2010 年前后的互联网公司中普遍存在【经验】。

#### 3.2.2 分片 KV + 宽列存储（V2.0，2013–2017）

- **被什么约束逼出来**：MySQL 的单库容量上限、业务字段频繁变化（需要无模式写入）、司机位置与乘客请求的高写入吞吐，三条约束同时出现。
- **结构**：

```text
[Schemaless] = [MySQL] + [自动分片] + [副本同步]     ← 本仓库 § 4.2 口径
  分片：按 row_key 计算落点，容量与写入吞吐随分片数扩展
  无模式：字段以「单元格」逐条写入，新增字段不需要 DDL
  读：主键点查直读；按其他字段查 → 走二级索引表，再按 row_key 回表
  副本：异步同步到其他机房，故障时切换
──────────────────────────────────────────────
Cassandra / HBase：宽列存储，按分区键点查，面向高写入吞吐
  司机位置、乘客请求一类的连续写入场景（本仓库 § 4.2 记「Cassandra：存储司机位置（高写入）」，乘客请求见原 § 3.2 口径）
```

- **把「高写入吞吐」量化**【推算】：设峰值时在线司机约 100 万、每人每秒上报一次位置，则位置写入约 100 万行/秒（10⁶ 行/s），一天约 8.6 × 10¹⁰ 行（10⁶ × 86400）；按每行 100 B 计，单这一路数据每天就产生约 8.6 TB 写入（8.6 × 10¹⁰ × 100 B）。这个量级已在单库关系数据库的写入能力之外——**它才是「分片 + 宽列存储」在这里的唯一理由**。假设中的司机数读者可替换成自己的数，结论随它线性变化。
- **为什么这样设计有效**：因为分片把容量与写入吞吐变成「加机器」的线性问题，单库上限不再是硬墙；因为字段以单元格形式逐条写入，新增字段不需要一次表结构变更，业务迭代不必再等 DDL——这是「无模式」在 Uber 这种高频迭代业务里的真实收益。
- **与关系库分库分表的边界**：分库分表保留了 SQL 与事务语义，代价是应用自己做路由；分片 KV 放弃了跨分片事务与聚合，换来写入的线性扩展。**判据是查询形态**：主要查询都是主键点查、且写入是瓶颈时选后者；还需要跨片事务与多条件查询时，前者更合适。
- **代价**：① 分片的代价转移给应用——跨分片查询与跨分片事务不再由数据库提供，聚合要么扫全部分片、要么另建索引表；② 二级索引由应用维护，索引与主数据之间存在不一致窗口；③ **自研存储意味着所有缺陷与运维都由自己承担**，Uber 需要专门的 SRE 团队维护 Schemaless（本仓库 [§ 5.1](06-uber-data-architecture-section-5-sec5.md)）；④ Cassandra 侧默认最终一致性，跨数据中心复制有延迟，一致性必须显式设置（本仓库 [§ 5.2](06-uber-data-architecture-section-5-sec5.md)）。
- **失效点**：当查询模式从「主键点查」扩展到「多维度聚合或全局排序」时，分片 KV 的优点反转成缺点——分片键决定了只有一种访问路径是快的，其他路径都要扫全片；当一致性要求上升到跨分片事务时，最终一致性的优点反转成数据不一致风险，必须由客户端显式选择一致性级别（Uber 的修正是客户端强读 + LOCAL_QUORUM，本仓库 § 5.2）。
- **自验方法**：列出在线存储上实际的查询清单，标注每一条走的是不是分片键；不走的那些，就是下一次扩容仍然解决不了的问题。
- **真实使用**：Uber 2013 年立项 Schemaless（基于 MySQL 的水平扩展），2014 年起大规模使用 Cassandra（[主文件 § 1.1](06-uber-data-architecture.md) 并记 HBase）。本仓库 [§ 4.2](06-uber-data-architecture-section-4-sec4.md) 记录 Schemaless 的三个关键设计是「基于 MySQL / 自动分片 / 副本同步」（该处只讲设计，未记使用范围）；原 § 3.2 的「Schemaless 核心」还有第三条采用范围——**被 Uber 多个团队使用**，即它不只是单个团队的自研方案，而是被多个内部团队采纳的基础设施；Cassandra 的高写入场景见 [§ 4.2](06-uber-data-architecture-section-4-sec4.md)「Cassandra：存储司机位置（高写入）」，「乘客请求」一类场景见原 § 3.2 口径【公开】（以 Uber 公开材料原文为准）。

#### 3.2.3 湖上表格式：Hudi（V3.0，2016–2020）

- **被什么约束逼出来**：行程状态机与支付单是「同一主键被反复更新」的数据，而 Hive / Parquet 是不可变文件格式——约束来自「更新型数据 + 不可变格式」的错配。
- **结构**：

```text
Hudi 表 = 文件分组（file group）+ 时间线（timeline）+ 索引（index）
  file group   按主键分桶；一个分组内 = 1 个基础文件 + N 个日志文件
  timeline     以「提交（instant）」为单位记录每次写入
               → ACID 与 time travel 是同一机制的两个侧面
  index        主键 → file group 的映射，让 upsert 能定位要改哪个文件

两种写模式（原 § 3.3 列出的 CoW / MoR）：
  Copy-on-Write  更新时重写命中分组的基础文件 → 读快、写放大
  Merge-on-Read  更新先写日志文件，读取时合并 → 写快、读需合并
CDC：MySQL / Cassandra 的变更被采集后写入 Hudi（原 § 3.3 列出的 CDC 能力）
```

- **写放大的量级可以先算清楚**【推算】：设某分区表日均新增 1 亿行、单文件 100 万行，则当日产生约 100 个数据文件；若当天有 1% 的行（约 100 万行）被更新、且分散落在全部 100 个文件里（每个文件约摊到 1 万行，占该文件的 1%），则 copy-on-write 需重写命中文件，总写入量约 100 × 100 万 = 1 亿行，是实际变化行数的约 100 倍；merge-on-read 只追加日志，写入量约 100 万行，与实际变化行数同量级。若这 100 万行集中在 1 个文件里，copy-on-write 只需重写 100 万行，与 merge-on-read 同量级。**起决定作用的是更新的分散度，不是更新占比**——占比低但分散时收益最大，占比不低但集中时收益接近于零。
- **为什么这样设计有效**：因为时间线把「一次写入」变成一次原子提交，所以 ACID 与 time travel 由同一个机制提供——回溯到某个 instant 就是回到那次写入之后的状态；因为索引保存了主键到文件分组的映射，upsert 只需重写命中分组而不是整个分区，**这正是它与 Hive 表格式的本质差别**（update / delete 支持）。
- **代价**：① 写放大依然存在，只是从「整分区」降到「命中分组」（COW）或「追加日志」（MOR），而 MOR 需要后台 compaction 把日志合并回基础文件，compaction 积压成为新的运维面；② 索引与时间线的元数据随写入频率增长，对象存储上的小文件与元数据请求开销上升；③ CDC 链路要处理乱序与重复，语义上是至少一次，幂等性由写入方保证；④ 格式版本演进必须灰度——本仓库 [§ 5.3](06-uber-data-architecture-section-5-sec5.md) 记录 Hudi 从 0.x 升到 1.0 时遇到文件格式兼容问题。
- **失效点**：当「更新集中在当天分区、而该分区当天本来就要全量重算」时，upsert 的增量收益归零，COW / MOR 的复杂度是在为不存在的场景付费；反过来，当 compaction 长期积压时，MOR 的「写快」会反转成「读越来越慢」，因为每次读取要合并的日志文件越来越多。
- **自验方法**：取最大的事实表，统计最近 7 天写入中主键命中已有数据的行占比，以及这些命中行分散在多少个文件里；分散度不足时，upsert 能力买到的只是用不上的特性。
- **真实使用**：Hudi 由 Uber 于 2016 年在内部立项（原名 Hoodie），2020 年成为 Apache 顶级项目（[主文件 § 1.1](06-uber-data-architecture.md)；本仓库 [§ 7.2.1](06-uber-data-architecture-section-7-sec7.md) 记 Hudi 由 Uber 发起并成为 Apache 项目）【公开】。本仓库 § 4.3 记录 Uber 选择 Hudi 的理由是 CDC 友好、原生支持 upsert 且可定制（当时 Iceberg 与 Delta Lake 的能力侧重不同）。

#### 3.2.4 实时数仓：日志 + 流 + 湖 + 查询引擎（V4.0，2020–2024；实时数仓自 2018 年 V1 起）

- **被什么约束逼出来**：实时需求（ETA、定价、匹配）与离线需求（报表、训练）都要同一份数据；两套各算一遍，口径必然分叉。
- **结构**（原 § 3.4 的链路图保留并展开职责）：

```text
[业务系统] → [Kafka] → [Flink] → [Hudi] → [Spark / Trino] → [BI / ML]
   (事件)     (消息)     (实时)   (表格式)     (查询)          (消费)

四个环节各自承担的职责（缺一个链路就不成立）：
  Kafka   缓冲与重放：把生产速度与消费速度解耦，流任务可从任意位点重跑
  Flink   有状态计算：事件时间 + 水位线 + 状态存储，窗口结果可重算
  Hudi    落湖与回看：增量写入 + time travel，实时与离线共用同一份数据
  Trino   联邦查询：不搬数据的前提下提供统一查询入口（本仓库 § 6.1）
```

- **为什么这样设计有效**：因为 Kafka 把重放能力交还给消费者，实时链路因此具备与批处理同等的可修复性——出错可以从位点重跑，而不是接受一份错误结果；因为结果同时进入在线存储与湖，离线训练与在线推理可以共享同一份口径（这也是本仓库 § 6.4 里「训练与推理特征不一致」被从事故清单划掉的原因）。
- **与 3.2.3 的边界**：湖上表格式解决「写进去之后怎么改」，实时数仓解决「多久能看见」——只有表格式而没有流链路，数据仍停在 T+1；只有流链路而没有可靠的表格式，结果无法回看与重算。两者解决的是不同问题，不能互相替代。
- **代价**：① 运维面从「一套批调度」变成消息、流、湖、查询引擎四套，每套都有自己的容量与故障模式；② 有状态流任务的状态存储与 checkpoint 要与并行度、数据倾斜一起规划，扩容不是加节点那么简单；③ 落湖延迟是分钟级，所以「实时结果」不能直接当在线接口用，必须另有在线存储；④ 流写入与 compaction 会争抢同一份存储与元数据。
- **失效点**：当团队把「实时数仓」当成在线存储用时，优点反转成缺点——实时数仓的读路径要经过表格式与查询引擎，其延迟受 compaction、文件布局与查询排队影响，不可能稳定在毫秒级；在线请求必须走独立的在线 KV（Cassandra / Redis 一类）。判断方法与本仓库 § 7.2.2 一致：先问「实时结果晚一分钟会损失什么」。
- **自验方法**：把当前所有「实时」需求列出来，逐条回答「晚一分钟会损失什么」；答不出来的从实时清单划掉，剩下的才需要这条链路。
- **真实使用**：Uber 2018 年实时数仓 V1（[主文件 § 1.1](06-uber-data-architecture.md)；「2020 年 V2 铺开」一条取自原 § 3.4，主文件 § 1.1 未列）；本仓库 § 6.1 记录 Uber 用 Trino 做联邦查询（统一计算引擎但不动数据），§ 6.3 记录有状态流计算把「在线司机与在途订单」放进流任务。`Kafka → Flink → Hudi` 这条链路在主文件 § 1.1 的 2018 年条目里明记（「2018：实时数仓 V1。Kafka + Flink + Hudi。」）【公开】（以 Uber 公开材料原文为准）；本仓库 [§ 7.2](06-uber-data-architecture-section-7-sec7.md) 的横向对比表把这条链路与 Netflix / Airbnb / 美团三条链路并列，可供逐条对照——该表只是同一批案例的口径汇总，不是独立来源。

#### 3.2.5 特征与训练推理一致（Michelangelo，2017 起）

- **被什么约束逼出来**：主文件 § 2.2.4 记录 Uber 有 1000+ 算法工程师，每个工程师都有自己的模型、特征与 AB 实验；训练走批处理、推理要毫秒级，两套实现一旦分开写，离线与线上必然对不上。
- **结构**（本仓库 [§ 4.2](06-uber-data-architecture-section-4-sec4.md) 的 Michelangelo 链路保留，补上「同一份定义」这一层）：

```text
[数据] → [特征平台] → [训练] → [部署] → [推理]
          (Feature       (Spark /   (容器)    (在线
           Store)         TF / PyTorch)        服务)

特征存储 = 同一份定义的两种物化
  离线侧：Hive / Hudi（训练用，批量读取、可回放到某个时间点）
  在线侧：KV（推理用，点查、毫秒级）
  关键约束：两侧必须由同一份特征定义生成
          否则「离线评估很好、线上没效果」这类问题无法排查
```

- **为什么这样设计有效**：因为唯一的事实来源是「特征定义」而不是任何一份数据副本，离线与在线的差异变成可检测的偏差，而不是不可解释的效果损失；因为训练与推理读同一套定义，口径变更不再需要两处同步——这正是本仓库 § 6.4 总结的「把训练与推理特征不一致从事故清单里划掉」的机制。
- **在线特征的数量上限可以推出来**【推算】：设在线特征 N 个，双份实现的维护成本 ≈ N ×（一致性校验 + 口径对齐工时），近似线性增长；而效果收益随 N 递减（越靠后的特征边际贡献越小）。两条曲线的交点即上限——**因此在线特征只应保留「晚一分钟就会损失业务」的那些**，其余留在离线侧。
- **与 3.2.4 的边界**：实时数仓解决「数据多久可见」，特征存储解决「同一份特征在两侧是否一致」；只有实时链路而没有统一特征定义，离线与在线仍会漂移。两者不是替代关系——先有实时链路，特征存储才有存在的必要。
- **代价**：① 在线侧要为每个特征付存储与点查成本，特征数增长时维护成本近似线性；② 特征口径变更要同时影响两侧并保证时序正确——训练只能用「当时可知」的值，不能把未来特征漏进来；③ 平台本身要养一支团队——[主文件](06-uber-data-architecture.md) § 1.3 记「ML 平台团队（Michelangelo）：约 200+ 人」，该条在仓库内只到此量级、没有外部出处与年份，故此处按量级采信【经验】（百人量级）；人数随平台承载的特征数与模型数增长。
- **失效点**：当在线特征数量超过上面那个上限时，特征平台的优点反转成负担——一致性校验成本随特征数近似线性增长而收益递减；同时口径漂移会以「模型效果缓慢下降」的形式暴露，比报错难查得多。
- **自验方法**：随机取一个线上模型，比较它的训练样本与线上推理请求里的同一个特征值；若两侧需要用两套代码解释，问题就在口径而不在模型。
- **真实使用**：Michelangelo 于 2017 年由 Uber 公开介绍（[主文件 § 1.1](06-uber-data-architecture.md)；本仓库 § 7.2.2 引 Uber 工程博客 2017）【公开】。其公开架构主线即「离线 / 在线特征统一 + 训练与推理一致」（本仓库 § 6.4）。

#### 3.2.6 AI Native 数据栈（V5.0，2023–2025）

- **被什么约束逼出来**：模型输出质量取决于喂进去的上下文，而上下文由两类东西构成——实时特征（在线侧）与企业知识文档（不在表格式的管辖区，是另一种数据形态）。
- **结构**：

```text
[业务系统] → [Kafka] → [Flink] → [Hudi] → [Spark / Trino] → [BI / ML]
                                        ↘ 实时特征（在线 KV）↘ 模型 / LLM 推理
2023–2025 的两条新路径（原 § 3.5 只列了三条「关键事件」，没有链路结构，下面这两条链路是本节的补充）：
  ① 实时特征 → 在线推理：特征必须与训练同源，否则线上效果不可解释
  ② 企业知识 → 检索（向量索引）→ 拼装上下文 → Agent 工具调用 → 外部动作
      ⚠ Agent 一旦拥有写权限，问题性质从「答错」变成「做错」
        → 权限与留痕必须前置到工具调用层
```

- **为什么这样设计有效**：因为检索把「模型知识」与「企业事实」解耦，事实更新不需要重训模型，只要更新检索源；因为 Agent 的每次工具调用都经过数据平台，权限、审计与血缘可以沿用既有的数据治理机制，不必另建一套——这也是它与前面几代能共存而不是替换的原因。
- **代价**：① 多出一种数据形态（向量索引）与一条新的写入链路，检索源与源系统之间的一致性需要额外保证；② 上下文拼装的成本随检索条数增长，且「取哪些数据」变成模型行为的一部分，优化对象从 SQL 转到检索质量；③ 在线推理的延迟预算要同时容纳检索与生成，检索环节会成为新的尾延迟来源。
- **失效点**：当检索源与源数据不同步时，RAG 的优点反转成「自信地给出过期答案」——检索命中旧文档，而模型无法察觉；当 Agent 拥有写权限时，失效的后果从「输出不可信」升级为「动作不可逆」，此时必须先补工具调用层的权限与留痕（见 [§ 3 审计与合规 · 设计模式与范式](../../11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-3-sec3.md) 的 AI 合规审计）。
- **自验方法**：任取一次 Agent 会话，看能否只靠数据平台侧记录还原出「用了哪些实时特征、检索了哪几份文档、调用了哪些接口」；缺任何一环，问题就无法归因到数据。
- **真实使用**：Uber 2023 年起内部广泛使用大模型（「含 OpenAI / Claude 与开源模型」这一厂商细节出自原 § 3.5，主文件 § 1.1 的 2023 年只记「GenAI 应用」（Hudi 1.0 记在该年表的 2024 年），不含厂商名），2024 年推出 Uber AI Platform 整合 ML 与 LLM，2025 年推进实时 AI 数据栈（实时特征 + 大模型）（[主文件 § 1.1](06-uber-data-architecture.md) 记 2024 与 2025 两条）【公开】（具体组件与效果以 Uber 公开材料原文为准）。

**一条行程数据在不同代际里走的路**（同一份数据，五种归宿）：

```text
行程状态更新
  V1：写 MySQL；次日 insert overwrite 到 Hive 分区；Tableau 读
  V2：写 Schemaless（MySQL 分片）解决容量；司机位置写 Cassandra 解决吞吐
  V3：状态变更经 CDC 写入 Hudi，upsert 只重写命中分组，可回看任意 instant
  V4：变更同时被 Flink 消费，窗口结果写在线 KV 并落湖，在线与离线共用口径
  V5：上述结果被拼进模型上下文；若 Agent 据此发起动作，动作本身必须留痕
```

任何一代都不是「错的」，它是当时约束下唯一可行的形态；真正会出错的是把它沿用到今天。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 数据量在单库容量内、无秒级需求 | 3.2.1 单库 + 批处理数仓 | 不上分片 KV：分片的运维与一致性成本在低数据量下收不回来 | 单库是否已接近容量上限 |
| 写入中「主键已存在」的比例高、且分散 | 3.2.3 湖上表格式（Hudi 类） | 不用 Hive 表格式：不可变文件承载行级更新会把写入量顶到该分区当日全量（按 3.2.3 的推算，更新分散时，Hive 整分区重写与 COW 重写命中文件两者同为约 1 亿行，即 COW 相对整分区重写的收益为零；同一场景下带 upsert 的 MOR 只追加日志、写入量约 100 万行，与实际变化行数同量级） | 每日写入中命中已有数据的行占比与分散度 |
| 写入只有追加、没有更新需求 | 3.2.3 湖上表格式（不启用 upsert） | 不用带主键索引的形态：索引与 compaction 对只追加数据是纯开销 | 主键是否会被更新 |
| 查询几乎只有主键点查、写入极高 | 3.2.2 宽列存储（Cassandra 类） | 不用关系库分库分表：点查吞吐不是它的强项 | 是否存在多维度聚合查询 |
| 既要跨分片聚合又要频繁更新 | 3.2.2 + 3.2.3 组合 | 不用单一存储兼顾：两种访问路径无法同时最优 | 聚合查询频次是否高到值得单独建链路 |
| 实时结果被在线服务读取 | 3.2.4 + 在线 KV | 不用实时数仓直读：读延迟受 compaction 与查询排队影响 | 实时结果晚一分钟会损失什么 |
| 一次性分析为主、更新极少 | 3.2.1 或 3.2.3（不启用 upsert） | 不用实时数仓：批处理的延迟已经满足需求 | 需求的发现延迟是否可以按天计 |
| 模型要被反复迭代、特征要复用 | 3.2.5 特征存储（同一份定义） | 不让各团队各自实现：训练与推理两套实现对不上且难排查 | 是否存在在线模型 |
| 多法域、数据不能无差别汇聚 | 区域化部署 + 联邦查询（[§ 4.2](06-uber-data-architecture-section-4-sec4.md)） | 不用全局单点数仓 | 数据是否含受本地化要求约束的主体 |
| 数据要跨区域汇总但不能出境 | 上层只汇聚合、明细留在区内 | 不做全局明细汇总：汇总那一刻就是跨境传输 | 汇总结果是否需要下钻到明细 |
| 只在单区域运营、无本地化要求 | 单区部署 + 联邦查询 | 不提前铺多区域：多区域的运维成本随区域数增长 | 是否存在跨境主体数据 |
| 团队只有 2–3 人、无专职平台 | 3.2.1 或 3.2.3 单链路 | 不铺实时链路 + 特征平台：组件的运维超出团队容量 | 是否有人能覆盖流任务的日常值守 |
| 模型要基于企业事实回答、事实高频变化 | 3.2.6 检索 + 实时特征（AI Native） | 不只靠微调：事实更新不该触发重训 | 事实更新频率是否高于模型迭代频率 |

上表的判据绝大多数是定性的（查询形态、是否有在线模型、是否跨法域），其中两处数值判断的档位在此说明：「写入量顶到该分区当日全量」一格沿用 3.2.3 的写放大推算【推算】——更新分散时 Hive 整分区重写与 COW 同为约 1 亿行，MOR 约 100 万行；「团队只有 2–3 人、无专职平台」是常用的经验分界【经验】，它对应的是该行末列的判据「有没有人能覆盖流任务的日常值守」，人数只是这条判据的代理，不是统计结论。其余各行的答案要按 3.2 各节的「自验方法」量出来，而不是照抄表格。

表后要说清**最常被误选的一对**：「实时数仓（3.2.4）」与「在线存储（3.2.2）」被当成同一件事，而多数团队先建了前者。误选后果机制上是确定的——实时数仓的读路径要经过表格式、文件布局与查询引擎，其延迟由 compaction 与查询排队决定，不在业务请求的延迟预算内；用落湖的实时结果直接服务在线请求，表现是延迟随数据量增长而波动，而在线的价值恰恰是让点查延迟与数据总量解耦。

### 3.4 组合模式：真实系统不会只用一种

**组合一：湖上表格式（Hudi）+ 实时入湖（Flink）+ 联邦查询（Trino）。** 构成是 `Kafka → Flink → Hudi` 的实时链路，加上 Trino 作为统一查询入口。职责边界：Flink 负责有状态计算与事件时间窗口，Hudi 负责增量写入与版本回看，Trino 负责在不搬数据的前提下把多个源并成一个查询面（本仓库 § 6.1）。运维代价是 compaction 与索引元数据的长期维护、流任务状态与 checkpoint 的规划，以及多引擎读同一张表时的一致性验证——**同一条链路每新增一个引擎，就要多验证一次「同一份数据在不同引擎下是否给出同一个答案」**。适合的规模：既有秒级业务链路、又有跨源分析需求，且已有专职平台团队。

**组合二：在线 KV（Cassandra / Redis）+ 特征存储双面（Michelangelo）+ 湖上训练数据（Hudi）。** 构成是「在线侧 KV 提供点查、离线侧 Hudi 提供训练样本、两者由同一份特征定义生成」。职责边界：在线 KV 只承担推理所需的低延迟读，不承担分析；湖承担训练与回看；特征定义是唯一事实来源。运维代价是特征一致性校验的持续投入（随特征数近似线性增长）与训练样本的时序正确性保证。适合的规模：存在在线模型，且模型迭代频率落在「每周到每月」这一区间——低于每月一次，平台化收益很难覆盖成本【经验】。

**组合三：Docstore（统一文档模型 + 多存储后端）+ 域所有权与联邦治理（Data Mesh）+ 统一目录。** 构成是 2019 年立项的 Docstore（统一 Schemaless 与 Cassandra 之上的文档模型，后端可为 MySQL / Cassandra / S3，见 [§ 4.2](06-uber-data-architecture-section-4-sec4.md)），加上 2022 年内部讨论的 Data Mesh 四原则（域所有权、数据即产品、联邦治理、自助平台）与统一的数据产品目录。职责边界：Docstore 解决「业务团队不必关心底层用哪种存储」，Data Mesh 解决「谁对数据质量负责」，目录解决「有哪些数据、归谁管」。运维代价是跨域口径只能靠协商（协商速度受域的数量约束），以及统一存储面板要长期维护多后端的能力矩阵。适合的规模：业务线 3 条以上（常见起点 3–5 条）且各域有独立预算与考核时联邦才成立；预算仍在中心时，联邦只带来协调成本【经验】。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 单库硬扛 | 单实例容量逼近上限；扩容要停机；分库分表方案反复推迟 | 分片改造被推到最后一刻，改造期与业务高峰期重叠 | 起步期数据量确实小，扩容被当作「以后再说」的事 | 先算清年增长与单库上限的距离，提前一个季度启动分片 |
| 把最终一致性当默认值 | 跨机房读到的值不同；同一主键在两个数据中心版本不一致 | 不一致窗口在业务上表现为「偶发的错数据」，比报错更难查 | 分布式存储的默认参数对写入友好，团队没有显式设置一致性 | 显式选择一致性级别（如强读 + 本地多数派），并监控不一致窗口 |
| 在不可变文件格式上做行级更新 | 表格式是 Hive / Parquet，却要求 upsert；更新靠整分区重写 | 写入量 = 分区大小 × 更新次数，更新越频繁越慢 | 用「重跑当天分区」的批处理思维处理状态型数据 | 换成支持主键 upsert 与增量读取的湖上表格式 |
| 自研存储承载全部业务诉求 | 一个自研 KV 被要求覆盖点查、聚合、事务、分析全场景 | 每个新场景都要改内核；缺陷与运维全部由自己承担，需要专职 SRE | 自研解决了最初的容量问题，团队沿用「继续加功能」的路径 | 用统一访问层（如 Docstore）隔离业务与存储，各自选型 |
| 每个实时需求各自起一套 | 存在多套流任务与多份「实时口径」；同一指标两个值 | 口径分叉后需要人工对账，实时性的收益被抵消 | 缺统一的实时计算入口，需求方各自交付 | 建统一实时链路，需求以作业形式接入而不是各建一套 |
| 实时链路与在线存储混为一谈 | 在线接口直读湖上表；延迟随数据量增长而波动 | 延迟不可控，回压会传导到业务请求链路 | 「实时」被当成一个词，而不是两个需求（分析实时 / 在线低延迟） | 明确在线读走 KV、分析读走湖，两套口径同源但路径分开 |
| compaction 无人值守 | 日志文件持续累积；查询耗时逐周上升；存储成本超标 | MOR 的写快被读慢抵消，最终退化为「必须定期停机重写」 | 写入链路先上线，compaction 被当作后台细节 | 把 compaction 当 SLA 指标监控（积压量、最老未合并时间） |
| 两套特征各自实现 | 离线评估好而线上无效果；排查要对比两套特征代码 | 训练与推理口径漂移，且表现为效果差异而不是报错 | 训练与推理由不同团队、用不同技术栈实现 | 同一份特征定义生成离线与在线两侧（本仓库 § 6.4） |
| 表格式大版本一次性升级 | 升级后读旧文件报格式错误；回退需要重写数据 | 格式兼容问题在升级当天集中暴露，且回退代价高 | 把表格式当普通依赖升级，未按数据管理层对待 | 灰度升级（先小比例数据）+ 保留回退能力（本仓库 § 5.3） |

**最危险的两条**，在生产中这样暴露。第一条是「在不可变文件格式上做行级更新」：它不会报错，只会让写入越来越慢，而团队往往用扩容去掩盖，直到扩容也不再有效——判据是看写放大的来源，即一次更新实际改写了多少数据文件。第二条是「两套特征各自实现」：它把系统性问题伪装成模型问题，团队会去调参、换模型、加特征，而根因是两侧口径不同；这也是它比一次线上事故更难处理的原因。

**这些反模式有一个共同成因：把「当时唯一可行的解」当成「永远正确的解」。** 自研存储、批处理重跑、默认最终一致性、单点数仓，在各自的时间窗里都是理性的；它们变成反模式，是因为约束变了而架构没变。所以诊断的最小问句不是「这个做法对不对」，而是「它当时解决的那条约束，在我这里还成立吗」。

**反模式还会跨代传染，这比单次事故更麻烦。** 「用批处理思维处理状态型数据」会随数据一起被带到新的表格式上（换了 Hudi 却依然每天重跑整分区）；「每个实时需求各自起一套」会在新平台上重演（换成 Flink 之后仍然各建一套作业）；「两套特征各自实现」会随模型从离线搬到在线。**换组件不会自动修掉思维模式**——这也是每一代迁移里真正难的部分从来不是技术替换，而是把旧代际留下的默认习惯改掉。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单库容量见顶（2009–2013） | MySQL 直连 + 批处理数仓 | 单库上限是硬墙，扩容要停机 | 分片 KV + 宽列存储（Schemaless / Cassandra） | 跨分片查询与事务要应用自己实现；自建存储需要专职 SRE |
| 行级更新落在批处理格式上（2016） | Hive 表格式 | 一次更新 = 一次分区重写 | 湖上表格式（Hudi，CoW / MoR） | 存量数据要重写；compaction 成为长期运维项 |
| T+1 跟不上业务（2018–2020） | 批处理为主 | 实时需求各自起一套，口径分叉 | 实时数仓（`Kafka → Flink → Hudi → Trino`） | 新增三套组件的运维面；状态与 checkpoint 需规划 |
| 分析从天级变成小时级（不必秒级） | 批处理为主 | 全量重跑的窗口被压缩，重跑成本上升 | 微批 + 表格式增量读取 | 需要表格式支持增量读，并改造下游调度 |
| 模型数量超过手工管理（2017） | 各团队自建训练脚本 | 特征不可复用，训练与推理口径漂移 | 特征平台 + 在线特征（Michelangelo） | 在线侧存储成本随特征数近似线性增长 |
| 单区域 → 多区域多法域 | 中央数仓 | 受本地化要求约束的数据不能汇聚 | 区域化部署 + 联邦查询 + 删除权路径（[§ 4.2](06-uber-data-architecture-section-4-sec4.md)） | 需要先定义哪些字段允许跨区汇总 |
| 集中数仓 → 域所有权（2022 讨论） | 中心团队定义口径与流程 | 业务方改动排队，口径与业务节奏脱节 | Data Mesh 四原则 + 统一目录 | 域必须有独立预算与考核，否则只剩协调成本 |
| 自研内核优势收窄（2020 后） | 自研并维护内核 | 同类开源实现成熟后，维护成本归自己、生态归社区 | 消费开源 + 只在差异化处自研（本仓库 § 7.2.4） | 能力替换与团队再学习；迁移期两套并存 |
| 取数从 SQL 转向模型（2023–2025） | BI / SQL 取数 | 模型要的是上下文与实时特征，不是一张表 | 检索 + 实时特征 + 工具调用留痕（AI Native 数据栈） | 新增向量链路与一致性保证，权限与审计要前置 |

```text
五代架构在 2025 年仍然同时存在（不是替代关系）
  V1 批处理数仓   → 仍在服务稳定的 T+1 报表
  V2 分片 KV / 宽列 → 仍是在线点查的主力
  V3 湖上表格式   → 训练与账务类数据的底座
  V4 实时数仓     → 在线特征与分析实时链路
  V5 AI 数据栈    → 检索与 Agent 上下文（新增一层，不替换下层）
```

**跃迁的共同规律**：上表九次跃迁里有六次是「把原来混在一起的两件事分开」——容量与一致性分开（分片）、写入与读取路径分开（表格式）、在线与离线分开（特征）、在线与分析方法分开（实时数仓）、中心与域分开（治理）、事实与模型知识分开（检索）。原因是每一代的痛点都源于「一个组件被要求同时满足两种互相冲突的性质」，所以下一代的形态总是把这两种性质交给两个组件，代价是运维面多出一套。

**迁移成本的一般量级也可以先估**【推算】：换存储的成本 ≈ 存量数据量 × 单位迁移吞吐 + 双跑期的双份资源；换表格式的成本 ≈ 存量文件数 × 重写代价 + 下游读取方式的改造量（与表数量成正比）；换治理模型的成本 ≈ 域数量 × 跨域变更频率 × 单次协商周期。其中**换存储最便宜、换格式中等、换治理模型最贵**，因为前两者影响的是系统，后者影响的是人的协作方式与责任归属。

### 3.7 自检清单

以下 12 条自检项按「先算数字、再看路径、最后看治理」排列，每条都能用一次查询或一次盘点回答：

- [ ] 是否统计过「每日写入中主键已存在的行占比」，以及这些更新行分散在多少个文件里？前者决定表格式方向，后者决定 upsert 的收益，两者都不是团队偏好问题。
- [ ] 是否存在一条链路同时承担在线读与分析读（例如在线接口直读湖上表）？有，则延迟不可控，它就是下一次延迟事故的位置。
- [ ] 实时需求清单里，有多少条回答得出「晚一分钟会损失什么」？答不出的应从实时清单划掉。
- [ ] 训练与推理读的是同一份特征定义，还是两套代码？在线特征总数是否设过「只放晚一分钟就会损失业务」的上限？
- [ ] compaction（或等价的后台合并任务）是否被当作 SLA 监控？最老未合并时间是多少？
- [ ] 分片键是否只有一种访问路径是快的、主要聚合查询走的是不是这条路径？一致性级别是否显式设置、不一致窗口是否被监控？
- [ ] 表格式升级是否有灰度与回退路径？回退需要重写多少数据？
- [ ] 数据是否可以无差别跨区域汇聚？如果不能，区域边界是否已经落在架构里、删除权路径是否可执行？
- [ ] 口径错误的成本落在全公司还是单个业务线？它决定治理形态，与团队成熟度无关。
- [ ] 是否存在「两套事实来源」（同一指标有两条产出路径）？存在，则口径分叉只是时间问题。
- [ ] 是否有「旧代际仍然要服务谁」的清单？没有，说明迁移计划只考虑了新的使用者。这套架构里有多少组件是「当时没得选」才自研的、今天的开源生态是否已有可用解？
- [ ] Agent 是否拥有写权限？工具调用的权限与留痕是否前置到了调用层？

### 3.8 小结

| 你的约束 | 建议架构模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 数据量在单库容量内、无秒级需求 | 单库 + 批处理数仓（3.2.1） | 组件最少时延迟与成本都可控 |
| 主键被反复更新、容量见顶 | 分片 KV + 宽列存储（3.2.2） | 分片把容量变成线性问题，代价是应用自己承担一致性 |
| 更新型数据落在湖上 | 湖上表格式（3.2.3） | 索引 + 时间线让 upsert 只重写命中分组 |
| 写入只追加、无更新 | 湖上表格式（不启用 upsert） | 索引与 compaction 对只追加数据是纯开销 |
| 同一份数据要同时服务在线与分析 | 实时数仓 + 在线 KV（3.2.4） | 两种读取路径无法同时最优，必须分开 |
| 存在在线模型、特征反复复用 | 特征存储双面（3.2.5） | 同一份定义生成离线与在线，差异才可检测 |
| 模型要基于企业事实作答 | 检索 + 实时特征（3.2.6） | 事实更新不该触发重训，但写权限必须前置留痕 |
| 需要在两代之间长期共存 | 分层：旧代际只读、新代际承担写入 | 双写会产生两份事实来源，口径必然分叉 |

> 本节小结：决定 Uber 数据架构每一代形态的唯一那条约束，是**「同一份主键要被反复更新，而这份数据又要同时服务在线请求、离线分析与模型」**——它把存储、表格式、实时链路与特征平台逐代推到了今天的形态。读 Uber 的演进史，最先要问的不是「它用了什么」，而是「它的哪条约束逼出了这个选择，我有没有同一条约束」。
