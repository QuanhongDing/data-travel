## 3. 架构演进

### 3.1 先看约束：架构不是「该不该先进」，是「约束允许你走到哪一步」

创业公司的数据栈演进常被讲成一条「越来越先进」的路线图，于是「我们什么时候上湖仓」变成了一个关于技术品味的问题。它不是。**每个阶段的栈都是当阶段约束的唯一可行解**：现金只够验证产品时，任何固定人力成本都是负担；等指标口径开始分裂时，不把口径收进仓库就无法回答「上个月的用户数到底是多少」。

这里有一条与 §7 一致的判据：**采购的成本形状是「近似线性 + 零固定人力」，自建的成本形状是「固定人力 + 更低的单位价格」**。临界点出现在「单位价格 × 用量」大于一个平台团队年成本的那一刻——在这之前，任何自建都是在为不会发生的规模付费。

下面六条约束，任一条不同，同一阶段该选的栈就不同。第三列是它最容易推翻的直觉。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 现金与人力（固定成本承受力） | 能养几个专职数据人，以及能承担几个需要值班的组件 | 「先搭好以后不用改」——早期每个组件都要有人理解它、排查它，这份成本会一直存在 |
| 数据形态与写入模式 | 数据是「事件流」还是「业务库快照」，决定采集是先落地还是先入库 | 「先建模再采集」——事件形态的数据不先落地就永远补不回来 |
| 访问模式（点查 / 扫描 / 聚合） | 决定一份数据要不要为不同消费形态各留一份物理副本 | 「一份数据只存一次就够了」——点查与全表扫描的最优物理组织不同 |
| 变更频率与历史要求 | 口径多久改一次、历史是否需要可按旧口径复现 | 「改口径就是改一行 SQL」——不可复现的历史等于没有历史 |
| 一致性要求 | 实时链路要付出多少代价（迟到、重复、乱序的处理） | 「实时总是更好」——提前量的价值取决于业务动作的频率 |
| 时间窗（产品是否已成立） | 这个决定发生在「产品未验证」之前还是之后 | 「现在做的决定以后照着加就行」——同一问题在两个时间窗下答案相反 |

这张表的用法是**逐条对照、找最早被顶破的那一条**。六条里通常只有一两条在当下是真的紧的，其余都还宽裕；把宽裕的那几条当成理由去做升级，就是本章要反复指出的那类误判。举例：一家日事件几十万的公司，「一致性要求」这一条并不紧（次日到就够用），却因为有人想练流计算而提前上了消息队列——真正被顶破的不是业务约束。

另外说明一处口径：本节的团队规模台阶采用窄口径（数据团队人数）。主文件 §1.1 在对应阶段给的是含数据科学家与工程师的宽区间，与 §1.3 的给法不同——两处讲的不是同一件事，引用时请注明用的是哪一个。**A 轮这一处，本节的取值与主文件 §1.3 本身也不一致**：主文件 §1.3 写「3–5 人」；本节 3.2.2 采用 1–3，并已在结构块里注明。核这一处时请写明你用的是哪一组数。

约束不是恒定的：今天宽裕的那一条，可能因为一次业务变化突然变紧——新增一个受监管市场，会把驻留与合规从「以后再说」直接推到最紧；签下一个大客户，会把「能否按客户维度复现历史口径」从宽裕推到最紧。所以这张表要定期重估，而不是立项时看一次就归档。

### 3.2 模式逐个拆解（核心节）

本节的「模式」就是每个阶段的默认架构。它们不是并列的技术选项，而是**在各自约束下被逼到唯一解的默认形态**——把 B 轮的栈搬到种子轮会拖垮现金，把种子轮的栈留到 C 轮会答不出基本问题。每个模式下面给出六件事：约束、结构、机制、代价、反转点、真实使用。

> 读法提示：每段「结构」里都保留了该阶段的量级台阶与人力台阶。判断自己在哪个阶段，**按台阶判断，不按融资轮次判断**——融资节奏与数据量级常常并不同步。

#### 3.2.1 阶段 1（种子轮）：全 SaaS 托管，不自建任何基础设施

- **被什么约束逼出来**：现金与人力只够验证产品，而数据栈此刻唯一的任务是回答「用户还在不在」。
- **结构**：

```text
阶段 1（种子轮）：业务库 + SaaS 分析，没有仓
  [业务系统 / 业务库] ──► [SaaS 分析] ──► [决策]
                          Mixpanel / Amplitude / Segment / Heap
     营收看板：Stripe Dashboard / Chargebee / ProfitWell（SaaS 场景）
     网站看板：Google Analytics / Plausible
     A/B 测试：GrowthBook / Statsig / PostHog
────────────────────────────────
量级台阶【经验】：日活 < 1 万、日事件 < 100 万、报表 < 50 个
人力【经验】：1 个工程师兼数据 + 1 个产品经理兼分析
关键决策：不建仓、不招数据团队、只盯留存（DAU / WAU / MAU）
────────────────────────────────
结构的要害：数据归厂商所有，本地不留副本
```

- **为什么这样设计有效**：因为报表需求由厂商预先实现，所以自建仓的固定成本（建模、调度、元数据、值班）根本不必发生——这类成本不随用量下降，只会因「你买了什么」而出现。
- **代价**：数据主权与口径都在厂商手里。换来的是按用量分档的固定费用，代价是无法自定义口径、无法与自有业务库关联，导出粒度也受对方接口限制。
- **失效点**：当需要把行为数据与业务库数据按同一口径关联时，「零维护」反转成「无法回答」，因为两份数据在物理上就没有可连接的键——用户身份在 SaaS 侧是它自己的匿名标识，与业务库的用户主键对不上。
- **真实使用**：Segment 于 2020 年被 Twilio 收购（【公开：Twilio 公开公告，2020；以公告原文为准】）。多数种子轮公司的做法是「一个 SaaS 分析 + 一个营收看板」，不做任何自建 ETL【经验】。
- **这一阶段明确不做的事**：不建仓、不写 ETL、不招专职数据人（对应原决策「不建仓 / 不招数据团队」）。
- **什么时候该离开这一阶段**：出现第一句「这两个数为什么不一样」——说明口径的归属权已经从厂商转移到你自己身上。

#### 3.2.2 阶段 2（A 轮）：云数仓 + dbt，第一次把数据「搬进来」

- **被什么约束逼出来**：口径分歧开始出现，而 SaaS 工具对「这个指标怎么算」的回答方式，是把定义留给厂商。
- **结构**：

```text
阶段 2（A 轮）：第一次建仓，但只买不建
  [业务系统] ──► [SaaS 分析 + 云数仓] ──► [决策]
                  Mixpanel + Snowflake / BigQuery / Redshift
     转换：dbt
     BI：Looker / Mode / Metabase
     A/B：Statsig / GrowthBook
     特征平台：暂不需要（业务量级不到）
────────────────────────────────
量级台阶【经验】：日活 1 万 → 100 万、日事件 100 万 → 1 亿、报表 50 → 500
人力【经验】：数据团队 1–3 人（主文件 §1.3 给的是 3–5 人）
关键决策：用云数仓（不自建 Hadoop）、用 dbt 标准化指标 / 模型 / 血缘、
          用户行为走 Mixpanel + 自有数据双轨
────────────────────────────────
dbt 的结构要害：模型 = 一条 SELECT + 声明式配置，
                模型之间用 ref() 连成有向无环图 → 血缘由依赖关系自然产生
```

- **为什么这样设计有效**：因为转换在数仓内以 SQL 完成，而 SQL 的输入输出关系可以被静态解析，所以依赖顺序、血缘、测试与文档都能从同一份模型定义里推导出来，不必另建一套台账。
- **代价**：双轨意味着同一件事有两份口径（SaaS 报表一份、数仓一份），对账要长期做；且 dbt 让新增模型的边际成本极低，模型数量会随业务线性增长，重跑成本与口径维护面同步膨胀。
- **失效点**：当指标数量超过「一个人能记住」的规模时，「标准化」反转成口径分裂的加速器，因为它压低的是**新增**指标的成本、没有提高**收敛**指标的成本，于是同一指标出现多个模型、被不同看板各自引用。
- **真实使用**：dbt 把「模型 = 一条 SELECT + ref() 依赖」作为核心抽象【公开：dbt 官方文档，可按当前版本核验】；Looker 于 2019 年宣布被 Google 收购（【公开：Google 公开公告，2019；以公告原文为准】）。
- **这一阶段明确不做的事**：不自建 Hadoop、不上特征平台（对应原决策「特征平台：暂不需要，业务量级不到」）。
- **什么时候该离开这一阶段**：出现需要分钟级响应的业务动作，且已经能说清「谁在消费这条链路」。

#### 3.2.3 阶段 3（B 轮）：事件流 + ML / 特征平台，实时与模型同时入场

- **被什么约束逼出来**：等到「次日才知道昨天发生了什么」已经不可接受，同时模型开始需要可复用的历史特征。
- **结构**：

```text
阶段 3（B 轮）：从纯批到流批并存，并引入模型基础设施
  [业务系统] ──► [事件采集] ──► [云数仓] ──► [dbt] ──► [BI / ML]
                  Segment / Snowplow / RudderStack
     云数仓：Snowflake / Databricks    转换：dbt + dbt Cloud
     BI：Looker / Mode / Hex
     ML 平台：Weights & Biases / MLflow / Neptune.ai
     特征平台：Feast / Tecton
────────────────────────────────
量级台阶【经验】：日活 100 万 → 1000 万、日事件 1 亿 → 10 亿、
                  报表 500 → 5000、模型 5 → 50
人力【经验】：数据团队 10–20 人
关键决策：引入实时（Kafka / Flink）、引入 ML（ML 平台 + 特征平台）、
          指标集中管理
────────────────────────────────
结构的要害：出现了第二条链路——事件流可绕过数仓直接服务在线，
            于是同一个指标有了"流的算法"和"批的算法"两个实现
```

- **为什么这样设计有效**：因为事件先落到流再进仓，采集与建模被解耦，新增一类事件不必先改数仓表结构就能被采集；而特征平台把「训练取什么、在线取什么」的逻辑收到一处，避免线上线下特征口径分叉。
- **代价**：同一指标存在流批两套实现，两套必然在边界情况上分叉（迟到事件、重复投递、乱序），必须长期对账；特征平台则引入「特征新鲜度」这一新的运维对象与责任边界。
- **失效点**：当实时链路的消费方只有一两张看板时，「实时」反转成纯粹的复杂度与成本，因为流链路要额外承担迟到与重复处理，换来的只是几小时提前量——而这份提前量是否值钱，取决于业务动作的频率，而不是取决于技术能做多快。
- **真实使用**：Kafka 由 LinkedIn 开源并进入 Apache 基金会【公开：以 Apache 官方项目页当前版本核验】；Feast 由 LF AI & Data 基金会托管【公开：以基金会项目页当前版本核验】。多数团队在这一阶段的做法是「先上事件采集，再按消费方决定是否上流计算」【经验】。
- **这一阶段明确不做的事**：不把实时链路当作权威口径——对外的数字仍以仓里的批处理结果为准，流只负责触发与近实时近似。
- **什么时候该离开这一阶段**：同一份数据开始要为两种以上引擎各存一份，存储成本与一致性维护同时变差。

#### 3.2.4 阶段 4（C 轮）：湖仓 + 流批一体，把存储与计算解耦

- **被什么约束逼出来**：同一份数据要同时服务 BI、模型训练与在线推理，而三种消费的算力形态不同（大范围扫描、反复迭代、低延迟点查）。
- **结构**：

```text
阶段 4（C 轮）：存储与计算分开，一份数据被多种引擎读
  [业务系统] ──► [Kafka] ──► [Lakehouse] ──► [Spark / Flink] ──► [BI / ML / AI]
                  事件       存储（开放表格式）      计算
     Lakehouse：Databricks / Snowflake / Iceberg + 对象存储
     实时计算：Flink / Spark Streaming
     ML 平台：Databricks ML / SageMaker / Vertex AI
     特征平台：Tecton / Feast Enterprise / Databricks Feature Store
     BI：Looker / Tableau / Sigma
     AI 平台：OpenAI / Anthropic / Cohere + 自研 RAG
────────────────────────────────
量级台阶【经验】：日活 1000 万 → 1 亿、日事件 10 亿 → 100 亿、
                  报表 5000 → 5 万个、模型 50 → 500
人力【经验】：数据团队 30–50 人
关键决策：湖仓化、流批一体（Kafka + Flink + Iceberg）、AI Native
────────────────────────────────
结构的要害：开放表格式是"接口"，引擎是可替换的实现
            → 换引擎不必改数据，但表格式的元数据服务成为新的关键路径
```

- **为什么这样设计有效**：因为存储层用开放表格式把「一份文件 + 变更日志」暴露给多个引擎，同一份数据不必为每个引擎复制一遍，算力可以按任务调度、按查询弹性扩缩。
- **代价**：表格式的元数据服务（目录）成为新的关键路径与单点；小文件合并、快照保留、过期清理、并发写入冲突这些原本属于引擎内部的问题，全部升级为跨团队约定。
- **失效点**：当数据量还不大、消费方只有一种引擎时，「解耦」反转成纯粹的运维负担——多维护一个目录服务与一套小文件合并任务，却没有任何「引擎可替换」的收益。**湖仓的前提是至少存在两种消费形态**。
- **真实使用**：Iceberg 由 Netflix 开源并进入 Apache，是开放表格式的代表【公开：以 Apache 官方项目页当前版本核验】；Databricks 与 Snowflake 的公开文档都把存储与计算分离列为核心架构特征【公开：以各自官方文档当前版本核验】。
- **这一阶段明确不做的事**：不为了「架构更先进」把仍然只有单一的批消费方也整体搬到湖仓上——同样一份数据在一套引擎里，就没必要先解耦。
- **什么时候该离开这一阶段**：出现数据驻留要求，或中心平台本身成为跨团队交付的瓶颈。

#### 3.2.5 阶段 5（独角兽 / 后期）：多区域 + 联邦治理，架构被组织形状决定

- **被什么约束逼出来**：数据驻留与合规要求直接否掉「一个中心仓汇全部数据」这项设计；同时数据团队过百人后，中心化平台自身成为瓶颈。
- **结构**：

```text
阶段 5（独角兽 / 后期）：区域边界 = 架构边界 = 组织边界
  [业务系统] ──► [多区域 / 多云] ──► [湖仓 + 实时] ──► [AI + ML / Agent]
                  数据驻留合规        每区域一套         LLM + Agent
                                                        + RAG + 多模态
     治理形态：联邦治理（Data Mesh）——域持有自己的数据，并对质量负责
────────────────────────────────
人力【经验】：数据团队 100+ 人（本阶段不给量级台阶）
────────────────────────────────
结构的要害：跨区域不能"复制一份就完事"——复制本身可能就违反驻留要求，
            所以跨区域只能交换聚合结果，不能交换原始数据
```

- **为什么这样设计有效**：因为每区域的数据留在区域内、由该区域的域团队负责，合规边界与团队边界重合，跨区查询被限制在聚合层，同时消除了「所有变更都要中心团队审批」这个瓶颈。
- **代价**：同一份口径在多区域各实现一次，一致性靠标准与测试维持，而不是靠单点管控；全局视图必须由聚合结果拼出，各区域产出时间不一致，会导致全局报表长期有一块是旧的。
- **失效点**：当组织里实际上仍只有一个权威团队时，联邦治理反转成「没有人负责一致性」——域自治把定义权下放了，而集中裁决的机制没有同时建立，于是同一指标在不同域给出不同口径。
- **真实使用**：Data Mesh 作为组织与架构范式由 Zhamak Dehghani 于 2019 年提出【公开：ThoughtWorks 公开技术文章，2019；以原文为准】；区域化存储与处理是主流公有云公开提供的合规能力【公开：以各云厂商官方文档当前版本核验】。
- **这一阶段明确不做的事**：不追求「全局实时一致的单一视图」——这个目标与「数据留在区域内」的驻留要求直接冲突，硬做只会把数据复制出合规边界。
- **这个模式成立的前提**：域自治与集中裁决机制必须同时存在。只有前者，得到的是分散的口径；只有后者，回到中心瓶颈。

五个模式的横向对照（同一列之间是可比较的，跨列之间不可直接搬用）：

| 模式（阶段） | 解决的核心约束 | 引入的新成本 | 反转条件 |
| --- | --- | --- | --- |
| 3.2.1 全 SaaS | 固定人力成本必须为零 | 数据主权与口径归属权转移给厂商 | 需要跨源关联同一口径时 |
| 3.2.2 云数仓 + dbt | 口径必须有一个可引用的权威来源 | 双轨对账；模型数量随业务线性膨胀 | 指标数量超过一个人能记住的规模时 |
| 3.2.3 事件流 + 特征平台 | 业务动作需要分钟级提前量 | 迟到 / 重复处理；流批两套实现要对账 | 实时消费方只有一两张看板时 |
| 3.2.4 湖仓 + 流批一体 | 一份数据要服务多种算力形态 | 目录成为关键路径；小文件与快照治理上移为跨团队约定 | 只有一种引擎在消费时 |
| 3.2.5 多区域 + 联邦治理 | 合规边界否掉中心汇聚 | 口径多区域各实现一次；全局视图靠聚合拼装 | 域自治与集中裁决机制只剩其一时 |

这张表的读法是：**每一列都成对出现——一个约束被解除，换来一笔新成本**。所以「该不该升级」这个问题等价于「新成本能不能被承受」，而不等于「新技术是不是更好」。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 现金紧、无专职数据人、产品未验证 | 3.2.1 全 SaaS | 不建仓：建仓是固定人力成本，不随用量下降 | 出问题时有没有人能值班排查 |
| 有 1–3 人数据团队【经验】、口径开始分歧 | 3.2.2 云数仓 + dbt | 不自建：自建的固定人力在此用量下摊不薄 | 账单里「单位价格 × 用量」是否已大于一个平台团队年成本 |
| 存在分钟级业务动作（风控、调度、推荐） | 3.2.3 事件流 | 不先上流：迟到与重复的处理成本要先付，收益要等消费方出现 | 这条流现在有谁在消费 |
| 模型数量超过「一个人能记住」 | 3.2.3 特征平台 | 不上特征平台：没有模型消费的特征平台是空转 | 线上真正在跑的模型有几个 |
| 至少两种消费形态（BI + 训练 / 推理） | 3.2.4 湖仓 | 不湖仓：单一引擎时解耦只有成本没有收益 | 未来一年是否真的需要换引擎 |
| 多司法辖区、有数据驻留要求 | 3.2.5 多区域 + 联邦治理 | 不用中心仓：驻留要求直接否掉中心汇聚 | 合规要求是否绑定数据主体所在地 |
| 数据进入收入函数（推荐 / 定价 / 风控） | 产品化投入，而非支撑职能预算 | 不按「内部报表」定预算：错误会直接损失收入 | 数据错了是损失收入还是损失信任 |
| 团队不足 10 人【经验】 | 只引入有人能维护的组件 | 不引入需要专职值班的平台组件 | 引入后谁在凌晨三点被叫醒 |
| 合规要求已确定会生效 | 现在就把生命周期与驻留设计进去 | 不推迟：要求覆盖全生命周期，越晚做回溯的历史越多 | 现有数据能否按主体所在地分区 |
| 已有 SaaS 账套且增长快 | 双轨 + 明确的退出条件 | 不立刻全量迁移：迁移会把增长期的人力抽走 | 双轨的对账是否已自动化 |
| 模型会持续迭代、且不止一个 | 特征平台 + 湖仓 | 不只上湖仓：没有特征契约时，训练与在线取数必然分叉 | 是否有超过一个模型在读同一批特征 |
| 团队分布在多个时区 | 联邦治理 + 明确的标准与测试 | 不靠单点审批：跨时区的审批会变成全天候阻塞 | 是否已建立跨域的口径裁决机制 |
| 增长放缓、成本成为主要议题 | 先做资产清理与容量治理 | 不先扩架构：未被访问的资产与报表仍在持续付费 | 上季度有多少资产从未被访问 |

本主题下最常被误选的一对，是 **3.2.3（事件流）与 3.2.4（湖仓）被提前到 A 轮**。误选的后果不是多花钱，而是**把有限的工程人力从验证产品上抽走**：实时链路与小文件合并、目录服务、快照清理这些工作，都不产生任何一个能被用户感知的功能，却会持续消耗早期团队唯一稀缺的资源——能改产品的那几个工程师的时间。判据很简单：**如果这条链路或这套存储今天被关掉，业务会在多久之内出问题？答案不是「几天内」的，就不该现在上。**

### 3.4 组合模式：真实系统不会只用一种

**组合 1：SaaS 分析（探索）+ 云数仓（权威口径）。** SaaS 侧负责快速提问与探索，数仓侧负责对外可引用的口径；边界是「任何写进汇报的数字必须来自数仓」。运维代价是长期对账（两边的日活、转化率必须定期核对差异原因），适合的规模是「数据团队 1–3 人、报表 50–500 个」的 A 轮阶段【经验：台阶口径见 3.2.2】。这对组合必须带退出条件——对账一旦停止，双轨就退化成两套互不承认的口径。

**组合 2：事件流（增量）+ 云数仓（全量）。** 事件流承担「刚刚发生了什么」，数仓承担「历史上发生了什么、按什么口径算」；边界是流只做触发与近实时聚合，不做权威口径。运维代价是同一指标两套实现必须定期对账，以及迟到与重复事件的处理逻辑要独立于批处理维护。适合「日活百万级、业务动作对时效敏感」的阶段。

**组合 3：湖仓（存储）+ 特征平台（消费侧契约）。** 湖仓负责一份数据被多种引擎读，特征平台负责训练与在线取数的口径一致；边界是湖仓不定义业务口径，特征平台不负责存储历史全量。运维代价是两套元数据（表格式目录 + 特征注册表）必须双向可追溯——特征出问题时能否定位到它读的是哪张表的哪个分区。适合「模型数量到几十个以上、存储与算力已分成两笔预算」的阶段。

这三条组合有一个共同点：**每一条都带一条明确的边界规则**（谁是权威口径、谁只做探索 / 触发 / 契约）。组合模式的失效几乎总是从边界模糊开始——一旦两边都能定义口径，对账就失去了基准，而「哪边是对的」会退化成由谁嗓门大来决定。

### 3.5 反模式与失效分析

下表列出本主题下反复出现的反模式。它们的共同形状是：**一个在别的规模下正确的做法，被搬到了不匹配的规模上**——所以「修法」几乎都是「回到当前约束」。

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因 | 修法 |
| --- | --- | --- | --- | --- |
| 过早自建 | 种子阶段就在维护自己部署的采集 / 调度系统 | 固定人力被组件吃掉，验证产品的资源被抽走 | 「以后反正要建，不如现在建」 | 只解决已经发生的问题，写明引入每个组件的触发条件 |
| 永远不建仓 | B 轮了还没有可对外引用的权威口径 | 数据留在 SaaS 里，跨源关联在物理上不可能 | 建仓是「不产出功能」的投入 | 出现第一个「口径对不上」时立即建仓 |
| 过早建实时链路 | 流已上线但没有业务动作在消费 | 为几小时提前量长期支付迟到 / 重复处理成本 | 「实时是先进性的标志」 | 先用批处理量出提前量的价值，再决定是否上流 |
| 特征平台空转 | 特征平台有表、没有线上模型在读 | 平台成本照付，一致性收益为零 | 平台先于模型建设 | 等第一批模型稳定后再上特征平台 |
| 口径各写各的 | 同一指标在不同看板数值不同 | 口径分裂后，任何跨看板结论都不可信 | dbt 降低了新增模型的成本，却没提高收敛的成本 | 每个核心指标指定唯一 Owner 与唯一定义 |
| 双轨不做对账 | 两边的同一指标长期有差异且无人解释 | 双轨退化成两套互不承认的口径 | 对账是「没有产出」的工作 | 把对账做成定时任务并设差异告警 |
| 报表数量当成绩 | 报表数量逐级上涨，无人清理 | 未被引用的报表持续消耗口径维护成本 | 报表数量容易被当成数据能力的指标 | 定期统计引用量与访问量，清理无人使用的资产 |
| 为未来规模设计 | 架构里全是「以后会用上」的组件 | 每个组件都要有人理解与排查，成本永久化 | 把架构决策当成一次性投资 | 引入前问「现在有什么问题是我们解决不了的」 |
| AI Native 当标签 | 上了 LLM，但没有可用的语义 / 元数据层 | 模型只能靠猜表名，效果无法归因 | 把「接了大模型」等同于 AI Native | 先补元数据与语义层，再谈模型接入 |
| 迁移当一次性项目 | 迁移没有并行期与退出条件 | 两边同时维护，人力被持续摊薄 | 低估存量模型与口径的重建量 | 每个迁移设明确退出条件与截止时间 |
| 训练与在线取数分叉 | 离线指标好、线上效果差 | 同一逻辑在两处实现，必然在边界情况上分叉 | 特征由各模型团队各自实现 | 用特征平台收口训练与在线取数 |
| 元数据与目录缺席 | 找一张表要靠问人 | 资产不可发现等于不存在，复用率为零 | 目录被视为「文档工作」而非基础设施 | 先用自动采集建最小目录，再逐步补业务含义 |
| 把融资轮次当阶段判据 | 组件与真实量级不匹配（空转或撑不住） | 引入的组件与真实约束脱钩 | 融资轮次是最容易观察到的信号 | 改用量级台阶与具体痛点判断阶段 |

其中四个最容易在生产里爆掉：

**「口径各写各的」是最隐蔽的一个**，因为它在单张看板里看不出来——每张看板都自洽，只有把两张并排看才会发现数值不同。它的暴露方式通常是会议上的一句「这个数怎么和我这边不一样」，而这时往往已经有几十个模型在引用两套定义。修它的成本随引用数量上升，所以最好的修复时机是出现第一个分歧的那一周。

**「特征平台空转」的暴露方式是账单与产出的对比**：平台有表结构、有调度、有存储，但线上没有任何模型在读。它成立的前提是「训练与在线取数必须一致」这个问题已经真实发生；在此之前，特征平台的收益是零，而它的运维对象（新鲜度、回填、一致性）都是新的。

**「过早建实时链路」常以「实时性不足」的名义被反复加固**：消费方没有增加，但链路长度在增加（加中间层、加缓存、加对账任务），每一次加固都让「关掉它」变得更难。判据仍是 §3.3 那一句——如果今天关掉它，业务多久出问题。

**「迁移当一次性项目」的暴露方式是并行期无限延长**：迁移没有退出条件时，两边的口径会各自继续演进，等到要切过去时发现目标侧已经落后，于是并行期再延一期。修法只有一个——开工前就写下退出条件（哪一天、以哪张报表、以哪个指标为准），并把它当作验收标准，而不是当作「以后再定」的事。

把这张表横着看一遍会发现一个共同成因：**这些反模式几乎都不是技术选错，而是「引入组件的成本没有被算进去」。** 选型时被比较的是功能与单价，而被漏掉的是「有人理解它、有人排查它、有人升级它」这三项长期成本。因此最有效的预防不是更严格的评审，而是把 §3.7 的清单固定成引入组件前必须填的一页纸。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：**规模或访问模式跨过某个阈值后，原来正确的模式会变成错误的**。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 种子 → A 轮 | 全 SaaS、数据留在厂商侧 | 需要跨源关联与自定义口径，而数据在物理上搬不到一起 | 云数仓 + dbt | 建立第一条采集与建模链路；短期出现双轨 |
| A → B 轮 | 只有批链路 | 业务动作开始需要分钟级触发 | 事件流 + 特征平台 | 迟到与重复处理逻辑要独立维护；同指标出现两套实现 |
| B → C 轮 | 仓 + 流各自一套存储 | 一份数据要为不同引擎各存一份，成本与一致性同时变差 | 湖仓 + 流批一体 | 存量数据重写为开放表格式；目录服务成为关键路径 |
| C 轮 → 独角兽 | 单一中心仓 | 数据驻留要求否掉中心汇聚；中心平台成为组织瓶颈 | 多区域 + 联邦治理 | 口径在多区域各实现一次；全局视图改为聚合拼装 |
| 单业务 → 多业务线 | 一套指标口径、一个 Owner | 同一指标名在不同业务含义不同，却共用一张定义 | 指标分层（公司级 / 业务级）与命名空间 | 既有指标要重新归类，历史看板要重指 |

表中「C 轮 → 独角兽」这一行最容易被低估：**从「一个中心仓」到「多区域」时，被改变的不只是数据的位置，还有「谁有权定义口径」**。这一步如果不把裁决机制一起建立，联邦治理得到的就只是分散的口径，而不是更快的决策。

还有一条与跃迁本身无关、却决定跃迁时机的纪律：**台阶要按可观察信号触发，不能按时间表**。把「每 18 个月升一级」写成计划，会在用量没涨时提前引入组件（把固定成本提前背上）；写成「日事件量级到某档、且出现某个具体痛点」，才与约束挂钩。台阶表给的是顺序关系，不是排期。

另外，「单业务 → 多业务线」这一跃迁与规模无关，只与**口径的歧义**有关：同一个指标名在两条业务线上本来就该有不同的定义，共用一张定义才会出错。它提醒的是本节的主线——**驱动模式切换的从来不是数据量本身，而是约束里最先被顶破的那一条**。

### 3.7 自检清单

1. 引入的每个组件，**是否写明了「它解决的是哪个已经发生的问题」**？答不上来的，现在就可以不进。
2. 是否有**唯一权威口径**？写进汇报的每个数字能否指向同一个定义。
3. 双轨（SaaS 与数仓）的**对账是否自动化**？差异是否有人负责解释。
4. 实时链路的**消费方是谁**？关掉它，业务多久之内会出问题。
5. 特征平台的**线上读方有哪些模型**？没有读方时，它承担的是什么成本。
6. **核心指标是否有唯一 Owner**？（写团队而非写人，等于没有 Owner）
7. 报表与模型的**引用情况是否可统计**？上季度有多少资产从未被访问。
8. 数据是否**按合规边界（主体所在地）组织**？现在做比事后回溯便宜多少。
9. 迁移是否**有并行期与退出条件**？并行期预计多长、由谁在维护两份。
10. 团队里**谁能处理凌晨三点这条链路的告警**？无人能处理的组件不该进生产。
11. 当前阶段的下一个「量级台阶」**触发条件是什么**？写成可观察的信号，而不是时间表。
12. 即将开始的迁移，**退出条件是否写在开工之前**？（哪一天、以哪张报表、以哪个指标为准）

### 3.8 小结

下表是本节全部结论的收口。它的用法不是「按列找自己」，而是**先在第 1 列里找到当下真正顶破的那一条约束，再看同一行第 2 列（建议模式）有没有对得上的模式**；找不到，说明还没到换架构的时候。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 现金紧、人力少、产品未验证 | 3.2.1 全 SaaS | 清零固定人力成本，把资源全押在验证上 |
| 口径开始分歧、有 1–3 人团队 | 3.2.2 云数仓 + dbt | 转换在数仓内完成，血缘与依赖可从模型定义推导 |
| 有分钟级业务动作、有消费方 | 3.2.3 事件流 + 特征平台 | 采集与建模解耦，训练与在线取数收到一处 |
| 多消费形态、算力预算独立 | 3.2.4 湖仓 | 一份存储多引擎读，算力按任务弹性伸缩 |
| 多司法辖区、有驻留要求 | 3.2.5 多区域 + 联邦治理 | 合规边界与团队边界重合，消除中心审批瓶颈 |
| 只有一条业务线、数据不跨团队复用 | 先不建治理职能与目录体系 | 治理的收益随资产数量与被复用次数出现，早了只有成本 |
| 数据只支撑内部决策、不进入收入函数 | 按「能否归因到收入」定预算上限 | 投入上限由「错误的影响范围」决定，而非由技术先进性决定 |

> 本节小结：本主题下决定架构选择的唯一那条约束，是**「固定人力成本能不能被摊薄」**。SaaS 是零固定人力、按用量付费；自建是固定人力、更低的单位价格。早期用量小，固定人力摊不薄，所以正确的选择是尽可能买；等到用量足够大、单位价格成为账单主导项时，自建才开始成立。所有阶段的切换点，都是这条曲线的交点——而不是新技术出现的时刻。

> 💡 **思考锚点**：把你本季度最大那笔基础设施账单拆成「按用量付费」与「固定人力」两栏：固定人力那一栏摊到每个请求上的单位价格，是不是仍高于 SaaS 的报价？若是，按 §3.8 你就还没到自建的切换点。此时该做的是 §3.6 那条纪律——把「升到下一级」的触发条件写成可观察信号（哪个量级、哪个已经发生的痛点），而不是写成「每 18 个月升一级」的时间表。你现在写的是哪一种？
