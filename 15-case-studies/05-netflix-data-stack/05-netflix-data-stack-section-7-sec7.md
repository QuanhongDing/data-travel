## 7. 与同类案例对比

### 7.1 先解决「可比性」

横向比数据栈，最容易犯的错是把差异归给「能力」：Netflix 有 Iceberg、Maestro、Metaflow，Databricks 有 Delta Lake、Unity Catalog、Databricks Workflows、MLflow，Uber 有 Hudi、Michelangelo，Airbnb 有 Minerva、Airflow 生态；再往下还有一层谁都在用的**引擎与消息**候选——Kafka、Flink、Spark、Spark Structured Streaming。把这些组件列成一张表，结论必然是「谁更全」。但真正的差异几乎都来自**约束**：Netflix 的栈是**自己长出来的**（对外开源的工程传统可追溯到 2011–2012 年的 Chaos Monkey / Simian Army、Eureka、Hystrix 等基础设施组件【公开：Netflix 开源项目历史】），Databricks 的栈是**作为产品卖出去的**，Uber 与 Airbnb 的栈是**内部平台 + 开源输出**。这三种身份决定了它们在同一技术问题上必须给出不同答案。

第二个错，是把**规模数字**当成结论。Netflix 处理的事件量确实大到让「文件列举」成为瓶颈，但这个结论不能反推「你也该用分层元数据表格式」——如果你的表只有几 TB，Hive 风格的表定义完全够用，引入湖表格式只会多出一层元数据服务与清单维护的运维面。规模决定的是**必不必要**，不是**先不先进**。

第三个错，是忽略本章对比对象里最关键的一条**时间窗**。Netflix 在 2017 年立项 Iceberg 时，市面上没有可用的替代品；2025 年的读者面对的是已经毕业为 Apache 顶级项目的成熟表格式。同一件事在 2017 年是**唯一可行解**，在 2025 年是**不必要的自研**。把时间窗读掉，是抄 Netflix 案例时最常见、代价也最大的错误。

第四个错，是**把「数据栈」当成同一种东西来比**。Netflix 的「数据栈」包含内容分发网络（Open Connect）这类跟数据分析无关的部分；Databricks 的「数据栈」是一套托管产品；Uber 的「数据栈」更多指数据湖与 ML 平台的组合。比较之前必须先把「栈」的边界画一致，否则是在比不同的东西。

因此本章先固定约束，再在约束相同的对象之间比机制：

| 判据 | 问的问题 | 为什么它决定了可比性 |
| --- | --- | --- |
| 自研还是采购 | 基础设施由自己维护还是由厂商维护 | 决定团队构成、路线图归属与锁定成本 |
| 时间窗 | 立项时市面上有没有可用替代品 | 决定自研是「无替代」还是「非理性」 |
| 治理授权 | 数据所有权能不能下放 | Data Mesh 一类做法成立与否的第一前提 |
| 最严延迟 | 实时链路的延迟上限 | 决定流批一体是否必要、表格式要不要支持流式写 |
| 组织形态 | 工程师自治还是强中心规范 | 决定目录是「联邦协作层」还是「审批关口」 |

在这套判据下，四个案例与一个参照锚点的约束定位如下：

| 案例 | 规模量级 | 业务形态 | 治理模式 | 存量约束 | 时间窗 |
| --- | --- | --- | --- | --- | --- |
| **Netflix** | 日事件量数千亿量级、日均 PB 级【公开：Netflix Tech Blog, Keystone, 2018】；覆盖 190+ 个国家/地区（Netflix 官方长期口径，本节不锁年份，与 7.4 表同一处理） | 全球流媒体（内容、推荐、播放质量） | **Data Mesh 方向**：所有权下放 + 中心化协作层 | 自研传统强（对外开源自 2011–2012 年的 Chaos Monkey / Eureka / Hystrix 起持续至今） | Iceberg 2017 内部立项 / 2018 开源【公开：Apache Iceberg 项目历史】 |
| **Databricks** | 多租户商业产品 | 面向外部客户的 Lakehouse | **中央目录**（统一目录与权限模型） | Delta Lake 生态 + 托管控制面 | Delta Lake 2019 开源【公开：Databricks, 2019】 |
| **Uber** | 数据平台 100+ PB【公开：Uber Engineering, 2018】 | 出行 / 外卖的 marketplace 决策 | 内部平台 + 工程师自治 | 自研 Hudi（2016 起，后进入 Apache）【公开：Apache Hudi 项目历史】 | Michelangelo 2017 公开【公开：Uber Engineering, 2017】 |
| **Airbnb** | 平台型公司规模 | 搜索排序 / 风控 / 定价 / 运营 | 数据科学家主导 + 协作规范 | Hive / Iceberg 生态 + Airflow 生态 | Airflow 2014 年在 Airbnb 内部起步、2016 年进入 Apache【公开：Apache Airflow 项目历史】 |
| **开源编排阵营**（Airflow / Dagster 等，增补锚点） | 不适用 | 通用工作流编排 | 工具中立，治理由使用方自建 | 与表格式弱耦合 | 长期存在 |

表外一句要紧的话：**这四个案例不是四个可选项，而是四种身份下的解**。Netflix 必须自研，因为它是「在没有替代品时就要用」的那一类公司；Databricks 必须收敛，因为它卖的就是收敛；Uber 与 Airbnb 处在中间——自研一部分、依赖一部分，代价是维护面更大。

还有一条容易被忽略的差别：**这四个案例的「失败」形态不同**。自研路线的失败是「维护成本失控」，产品路线的失败是「锁定与成本曲线」，内部平台路线的失败是「业务绕过平台」。判断该学谁时，先想清楚你更能承受哪一种失败——这比比较功能清单更接近选型的本质，也是 7.6 要展开的内容。

### 7.2 各案例的结构性差异（核心节）

四者的差别可以收敛到 4 个机制维度。每个维度都是一个「因为约束 A，所以必然选路线 B」的推导。

这四个维度也有依赖顺序：**表格式（7.2.1）决定其他三件事。** 表格式一旦让「提交」成为原子事件并且显式记录版本，调度才有可能按版本判定（7.2.3）、流与批才有共同的落点（7.2.2）；治理（7.2.4）则决定前面三层由谁维护。反过来不成立：调度做得再巧，也补不回表格式层缺失的原子性。

有一层候选被本章刻意折叠掉：**引擎与消息层**（Kafka、Flink、Spark、Spark Structured Streaming）。折叠不是因为它不重要，而是因为**四个案例在这一层是同一族**——都以 Kafka 一类消息层承载事件，以 Spark / Flink 一类引擎做计算（Databricks 的原生引擎即 Spark；Netflix 的 Keystone 建立在流处理引擎与消息层之上【公开：Netflix Tech Blog, 2018】；Uber 与 Airbnb 都是 Spark 的重度使用者）。同族内部差异小、跨族差异大，先分族再比，能省掉一半比较：引擎与消息层已经收敛成一族，继续比它只会得到「都差不多」；真正把四条路线分开的，是它上面的表格式、流批定义与就绪判定。

| 机制维度 | 一句话问题 | 谁决定它 |
| --- | --- | --- |
| 表格式 | 表由什么定义：目录列举还是分层元数据 | 数据规模与演进频率 |
| 流批关系 | 同一指标算几次 | 是否存在实时与离线并存的同一指标 |
| 就绪判定 | 下游凭什么认为上游好了 | 上游提交是否原子且带版本 |
| 治理归属 | 所有权下放还是集中 | 组织授权与产品身份 |

#### 7.2.1 表格式：表由「分层元数据」定义，还是由「目录列举」定义

**差异是什么**：一张表到底是什么——是「某个目录下的所有文件」，还是「一组分层元数据指向的文件集合」。这个定义方式决定了数据规模能长多大。

| 案例 | 表格式 | 元数据组织方式 | 由此得到的性质 |
| --- | --- | --- | --- |
| Netflix | Iceberg | 表 → 快照 → 清单 → 数据文件，分层 | 打开表与文件数近似无关；提交原子化 |
| Databricks | Delta Lake | 事务日志 + 周期性检查点 | 同类性质；日志重放代价随提交数增长，需检查点 |
| Uber | Hudi | 时间线 + 文件组 | 写入（upsert）友好；读路径需按文件组合并 |
| Airbnb | Hive / Iceberg | 早期以 Hive 分区目录为主 | 迁移成本低、生态广；规模上受列举代价约束 |

**这个差异由什么约束导致**：Netflix 的规模让「列举一个目录下的文件」变成不可接受的代价——文件数增大时，打开一张表的时间随之增长。真正的分界不是「EB 级」这类累计规模说法，而是**列举目录本身成为瓶颈的量级**：按 7.4 表的推算链（1 PB ÷ 512 MB ≈ 200 万个文件/表），单表文件数进入百万级时，目录列举式表定义就不再可用。因此它必须把表的定义从「目录」提升为「元数据」。Databricks 与 Uber 面对的是同类问题，但各自的写入模式不同：Databricks 侧重通用事务语义，Uber 侧重流式 upsert，于是同一思想长成了两种形态。

**因果句**：因为 Iceberg 把表定义为一组**分层元数据**（当前快照由一次原子切换产生，快照指向清单，清单指向数据文件），所以打开表的代价与文件数近似无关，schema 演进、时间旅行、快照隔离都变成**元数据操作而非数据重写**；但同一机制必然带来另一面——**清单本身会膨胀**，查询规划要读清单，因此「重写清单、合并小文件」成为常态运维项。**你换到的是写路径的原子性与读规划的可控，付出的是持续的元数据维护成本**，这两者必须一起接受。

**公开证据**：Iceberg 2017 年在 Netflix 内部立项、2018 年开源并进入 Apache 孵化、其后毕业为顶级项目【公开：Apache Iceberg 项目历史】；Delta Lake 2019 年开源【公开：Databricks, 2019】；Hudi 2016 年在 Uber 起步、其后进入 Apache【公开：Apache Hudi 项目历史】。要核验某表格式是否具备上述性质，看它的**提交是否原子**、**是否可回看历史快照**、**加列是否需要重写数据**——三条都能自己验证，不需要看宣传材料。

**失效条件**：数据量小（单表几十 GB）时，湖表格式带来的是额外的元数据服务与清单维护成本，收益接近零；高频小块写入若不做清单与小文件维护，清单膨胀会把查询规划时间推高，优势直接反转为劣势。

顺带说清楚一个常见的混淆：**表格式与文件格式不是一回事**。文件格式（列存编码、压缩）决定单个文件的读写效率，表格式决定「一组文件如何被当作一张表」。前者影响扫描速度，后者影响元数据操作、并发语义与演进成本。选型时两者要分开评估——「我把文件换成列存了」并不能回答「我的表能不能支撑并发读写与 schema 演进」。

**对读者的意义**：分层元数据这条**思想**在今天完全可迁移，但**实现不该自研**——三个表格式都已是成熟开源或商业产品，自研的边际收益远低于维护成本。

**可核验判据**：想判断某张表用的是哪一类定义方式，用三条就能确定——① 往表里提交一次，看这次提交是不是**一次性可见**（部分写入对外不可见）；② 查这张表在**一小时前的状态**，看要不要依赖外部备份；③ 加一个列，看**历史数据文件是否被重写**。三条答案组合起来，机制类别就唯一确定了，不需要看它是哪个产品。

#### 7.2.2 流批关系：同一份定义，还是两套链路

**差异是什么**：同一个业务指标，流式链路与批处理链路各算一次，还是共用一份定义。

| 案例 | 流批关系 | 一致性靠什么 | 代价落在哪 |
| --- | --- | --- | --- |
| Netflix | Keystone 流批一体：流与批共用一份业务逻辑定义（Netflix 工程博客有公开介绍，本行不锁年份；流批一体的推进口径见 §6 案例） | 定义统一 | 流侧表达能力受定义约束；两侧语义对齐成本 |
| Databricks | 统一引擎内的流批 API（Spark 批处理与 Structured Streaming 同一套 API），同一表格式读写 | 引擎与表格式统一 | 绑定该引擎生态 |
| Uber | 内部平台统一，但历史上 Spark 批链路与实时链路并存 | 平台规范 | 口径漂移由规范约束而非结构消除 |
| Airbnb | 以批为主 + 部分实时链路 | 协作规范 | 实时需求增长时需要补链路 |

**这个差异由什么约束导致**：Netflix 的痛点是「同一个指标在实时看板与离线报表里对不上」，而它又必须同时保留两条链路（实时用于体验，离线用于复盘与训练）。当两侧都必须存在时，**用同一份定义生成两条链路**是唯一能在结构上消除漂移的办法。Uber 与 Airbnb 的场景中，实时与离线指标的重叠面更小，因此两套链路的成本低于一体的复杂度。

**因果句**：因为流与批是两套执行模型（流式受限状态与窗口、批处理可全局重算），所以「同一份定义」必然要在**表达能力的并集之外做取舍**——定义能表达的东西，一定小于两套实现各自能表达的东西之和。Netflix 选择接受这个限制以换取口径一致；如果你的组织里实时与离线指标几乎不重叠，那么接受这个限制就是纯损失。

**公开证据**：Netflix 在 2018 年公开介绍 Keystone 实时流处理平台，并给出其规模量级【公开：Netflix Tech Blog, 2018】。核验某团队是否真做到了流批一体，问一句即可：**实时看板与离线报表里同一个指标，是不是同一份定义生成的？** 如果答案需要「口径文档」来解释，就不是一体。

**失效条件**：当实时与离线服务的是不同人群、不同口径（例如实时看板只用于告警，离线报表用于结算），强行统一定义会把两个本可独立演进的东西绑死——此时两套链路更好。

**对读者的意义**：先数一数你有多少个指标**同时**出现在实时与离线两侧。这个数量决定了流批一体的价值上限；数量是零或个位数时，不要上流批一体。

还要补充一点成本结构上的差异：两套链路的成本是**双份实现 + 双份排障**（改一次要改两处、出问题要查两条链路），而流批一体的成本是**表达能力受限 + 定义元模型的维护**。前者随业务变化频率增长，后者是一次性建设 + 长期维护。你的业务口径变化越快，前者越贵——这也是为什么消费侧变化快的公司更倾向于做流批一体。

#### 7.2.3 就绪判定：按「快照版本」还是按「文件到齐」

**差异是什么**：下游作业凭什么认为上游数据已经就绪——靠等待文件到齐，还是靠上游提交产生的版本号。

| 案例 | 就绪判定依据 | 典型失败模式 |
| --- | --- | --- |
| Netflix | Maestro 按上游提交的**快照版本**判定【公开：Netflix 技术博客 Maestro 一文, 2022，可由读者自行核验】 | 与表格式强耦合：上游不是表格式写入时机制失效 |
| Databricks | 与自家表格式/工作流耦合的同类机制 | 同上，且绑定该平台 |
| Uber | 通用 DAG 编排器（Airflow 一类，与 Maestro 同层）+ 依赖信号触发 | 需要哨兵文件或轮询，存在竞态 |
| Airbnb | Airflow 生态：传感器等待分区/文件到齐 | 轮询与竞态；上游部分写入时可能被误判就绪 |

表内编排器候选的档位说明：Netflix 一行是自研的 Maestro（【公开】，见下方证据）；Uber 与 Airbnb 两行的编排层属通用 DAG 编排器一族（Airflow 一类，与 Maestro 同层，候选关系见 7.1 表）。Uber 所用编排器的具体产品与年份本节无法外部核验，故按【经验】档只写到「Airflow 一类」，读者可按 Airflow 项目的使用者清单自行核验。

**这个差异由什么约束导致**：如果上游的提交是**原子的且带版本**（表格式提交即产生新快照），下游就可以只比较版本号；如果上游是「把文件陆续放进一个目录」，下游就只能靠「文件到齐」这类启发式判定。前者是表格式带来的能力，不是调度器本身的聪明——**没有表格式的一方抄不了这一条**。

**因果句**：因为原子提交把「部分写入」这个中间态从下游视角彻底移除了，所以下游不再需要「等文件到齐 / 检查哨兵 / 轮询」这类启发式规则，也就没有对应的竞态与空闲等待；但代价是**调度与表格式强耦合**——一旦上游换了一个不具备版本语义的写入方式，这条能力立即消失，退化回文件到齐判定。

**公开证据**：Netflix 在自己的技术博客上介绍过 Maestro 这一数据与 ML 工作流编排器的设计【公开：Netflix 技术博客 Maestro 一文, 2022】。读者可按「Netflix 技术博客 Maestro」与 Maestro 开源仓库自行核验；本节其余表述与 §4.3 的 Maestro / Airflow 对比、§6 的案例保持一致。核验方法：看下游任务的触发条件里写的是**版本/快照标识**，还是**文件是否存在、分区是否出现**。

**失效条件**：上游为非表格式写入（裸文件落盘、消息队列、跨系统导入）时快照版本不可得，仍需文件到齐判定；此时把两类依赖混在一条链路上，会让整条链路的就绪语义变得不可推理。

**对读者的意义**：这条机制的可迁移性比它的名气大得多——你不需要自研调度器，只需要让**就绪判定读取一个版本标识**而不是去探测文件。多数通用编排器都支持「按上游任务/分区版本触发」，差别只在于上游能不能提供一个可信版本号；因此**先把上游写入改成原子提交，比换调度器更有效**。

把四个机制维度合起来看，会发现它们其实是同一件事的四个侧面：**把「状态的可见性」从约定变成事实**。表格式让「表处于哪个状态」成为可查询的事实；流批一体让「口径是什么」成为一份定义；快照版本让「上游是否就绪」成为可比较的事实；统一目录让「谁能读什么」成为可查询的事实。四个案例的差别，本质上是它们各自在**哪几件事上把约定变成了事实**——变少了的那些，就要靠流程与人力去补。

#### 7.2.4 治理归属：数据所有权下放，还是中央目录

**差异是什么**：数据的所有权归生产数据的业务团队，还是归一个中心化的治理机构。

| 案例 | 治理形态 | 下放的前提 | 失效模式 |
| --- | --- | --- | --- |
| Netflix | Data Mesh 方向：所有权下放 + 中心化协作层 | 自助平台抽象 + 高人才密度 | 抽象不足时，混乱被分散化 |
| Databricks | 中央目录 + 权限模型 | 无需前提（产品必须给出） | 目录与业务实际使用的工具脱节 |
| Uber | 内部平台统一 + 工程师自治 | 平台提供端到端通路 | 自治导致资产重复 |
| Airbnb | 数据科学家自治 + 协作规范 | 规范可执行 | 治理动作后置，资产膨胀 |

**因果句**：因为 Netflix 的组织前提是「高人才密度 + Freedom & Responsibility」——即团队有能力也有授权对自己产出的数据负责——所以它可以走联邦式治理；而 Databricks 作为多租户产品**必须**给出中央目录，因为「谁能读谁」在商业合同与合规层面不能靠文化解决。两边都不是「更先进」，而是**组织能承受什么**。

**公开证据**：Netflix 的 Data Mesh 相关公开材料与 Databricks 的统一目录产品定位，均为各自官方公开内容【公开：Netflix Tech Blog 与 Databricks 官方文档；本节无法逐篇核验年份，故不锁年份，可由读者自行核验】。核验某组织是否具备下放条件，问一个问题：**一个团队要发布一张新表并声明它的 SLA，需要几次人工审批、等多久？** 如果超过一次审批或超过一天，说明自助抽象还不成立，此时下放只会把瓶颈分散成多个小瓶颈。

**失效条件**：缺少自助平台抽象（自助建模、自动质量校验、统一权限与目录）时下放所有权，结果不是自治而是失控；反过来，团队规模小于 10 个数据生产方时，中心化目录的协作成本低于联邦治理，不需要 Data Mesh。

**对读者的意义**：Data Mesh 首先是一次**组织变革**，其次才是技术架构。它成立的前提是「平台把自助能力做出来了」，而不是「把责任推给业务方」。

一个便于自检的对照：把「数据所有权下放」和「微服务拆分」放在一起看，会发现两者的前置条件完全一样——**先有能降低个体成本的基础设施，再谈把责任下沉**。微服务不是把单体拆开就完事，前提是有服务发现、链路追踪、统一部署；Data Mesh 不是把域切开就完事，前提是有自助发布、统一目录、自动质量校验。缺了这层前提，两者都会得到同一个结果：**责任下去了，能力没下去**。

### 7.3 可迁移 vs 不可迁移

判据同上：该做法依赖的是**机制**，还是依赖它的**规模、组织与历史**。

区分方法很实际：**能迁移的做法，通常能用一句话说清它在消除什么结构性缺陷**（例如「消除打开表代价随文件数增长」「消除就绪判定的竞态」）；搬不走的做法，通常只能说清它「做了什么」（例如「我们自研了一套调度器」）。用这个标准过一遍下面的表，你会发现能迁移的那几行都有明确的「消除对象」，搬不走的那几行都只有一个名词。

| 做法 | 可迁移？ | 为什么 | 迁移的前提条件 |
| --- | :---: | --- | --- |
| 分层元数据表格式的**思想** | ✅ | 「提交原子化 + 元数据与数据分离」的收益与规模无关 | 直接用现成的 Iceberg / Delta / Hudi，不自研 |
| 表格式与计算引擎解耦 | ✅ | 避免「每类查询各存一份数据、哪份对成为长期问题」 | 选定的表格式有多个引擎支持 |
| 按快照版本判定就绪 | ✅ | 消除竞态与空闲等待，是被表格式保证的性质 | 上游确实以表格式写入 |
| 流批共用一份定义 | ✅ | 只要实时与离线有重叠指标就成立 | 接受表达能力受限；有统一的定义元模型 |
| 数据所有权下放（Data Mesh） | ⚠️ 有前提 | 它是组织变革，不是技术选型 | 已有自助平台抽象；人才密度足够 |
| 自研 ML 框架（Metaflow 一类） | ⚠️ 有前提 | 现成方案已成熟，自研理由变弱 | 有超出通用框架能力的特定需求 |
| 自研表格式 | ❌ | 2017 年无替代，2025 年有三套成熟方案 | 除非需求在现有方案能力边界之外 |
| 自研调度器（Maestro 一类） | ❌ | 通用编排器生态成熟，自研只在大规模下成立 | 有专职基础设施团队且规模足够 |
| 自研内容分发网络（Open Connect） | ❌ | 依赖自建机房与运营商合作关系 | 通常不具备 |
| 「工程师自治」文化 | ❌ | 由招聘与组织历史决定，抄不来 | — |

补充两点判断：

- **可迁移的是「机制」，不是「组件」**。Netflix 的贡献不是「你要用 Maestro」，而是「就绪判定应当基于原子提交的版本」——这条判断能用在任何编排器上。
- **对读者的价值排序**：上表里收益/成本比最高的是「表格式与引擎解耦」和「按快照版本判定就绪」，因为它们一次性消除两类长期问题（数据多份、竞态等待），且今天有现成实现。最低的是自研基础设施，因为它解决的是「当年没有替代品」的问题。

如果你已经决定照搬某一条做法，第一个月该验证的是它的**前提**，而不是它的功能：

| 你打算照搬 | 第一个月该验证什么 | 验证不通过时会发生什么 |
| --- | --- | --- |
| 分层元数据表格式 | 你的写入模式是否会产生大量小文件、能否承受清单维护 | 清单膨胀把查询规划拖慢，比原来的目录列举更糟 |
| 按快照版本判定就绪 | 上游能否保证原子提交并暴露版本号 | 下游要么空等，要么读到最后一次提交的中途状态 |
| 流批共用一份定义 | 实时与离线是否真的存在同一指标 | 为一组不重叠的指标付出表达能力受限的代价 |
| 数据所有权下放 | 自助发布是否需要人工审批 | 责任下沉、能力没下沉，混乱被分散到各团队 |
| 自研基础设施 | 需求是否真的落在公开方案能力边界之外 | 投入变成长期固定成本，且质量不如开源方案 |

读表注意三点。第一，**规模数字要给量级而不是精确值**：「数千亿条/日」是有信息量的，「537 亿条/日」如果说不清统计口径（含不含重试、是否含内部调用），反而误导。第二，**成本数字必须给推导链**：上面两条推算换了文件大小或存储层，结论就会变。第三，**厂商与开源项目的历史时间点是可以核验的公开事实**，也是本章最可靠的证据来源——它们不依赖于谁的宣传材料。

还须提醒一句与本节主题相关的**证据纪律**：表格式之间的性能对比，公开材料里能查到的多是各项目自己的基准，测量口径（引擎版本、数据分布、是否预热）往往不一致，因此本表**刻意不给出「谁快几倍」的数字**。正确的做法是自己用真实数据跑一遍——这个结论是可以被任何人独立验证的，比引用任何一方公布的倍数都可靠。

### 7.5 决策树（我该学谁）

判断节点用**约束**而不是规模。第一个问题不是「我的数据量多大」，而是「我准备自研基础设施吗」。

```
你准备自研数据基础设施吗？
├─ 否（绝大多数读者）
│    ├─ 已重度使用某云生态
│    │    → 学 Databricks 路线的「收敛」：
│    │      表格式 + 统一目录 + 托管调度，用锁定换零运维
│    └─ 需要多云 / 避免锁定
│         → 选开源表格式（Iceberg 一类）+ 自选引擎与编排
│           你学的是 Netflix 的「机制」，而不是它的「自研」
│
└─ 是 —— 只有两种理由成立：
     ├─ 需求落在现成方案的能力边界之外（超大规模 + 极严延迟）
     └─ 有 10–30 人以上的专职基础设施团队，且业务愿意等
          ↓ 再过一道时间窗
          ├─ 现成方案今天已能覆盖（Iceberg / Delta Lake / Hudi 任一条路线）
          │    → 自研理由不成立，回到上面「否」的分支
          └─ 确实落在能力边界之外
               → 才参考 Netflix 的自研路径
                  并且必须先回答：做完之后是否也要开源摊薄维护成本

第二条线索：数据所有权要不要下放？
├─ 已有自助平台抽象（自助发布 / 自动质量 / 统一权限）
│    → 可以下放（合作式治理）
└─ 没有
     → 先建抽象再下放；直接下放 = 把混乱分散到各个团队

第三条线索：实时与离线是否算同一个指标？
├─ 是 → 流批共用一份定义，并接受表达能力受限的代价
└─ 否 → 两条链路各留一份，一致性交给可执行的规范
```

**阈值依据**（与树中节点一一对应）：

- **「超大规模 + 极严延迟」的能力边界**：这一条是树里唯一涉及规模的节点，所以必须给出边界而不是形容词。**超大规模**用元数据规模定：按 7.4 表的推算链（1 PB ÷ 512 MB ≈ 200 万个文件/表），单表文件数进入百万级时「列举目录」才成为瓶颈；单表几百 GB 到数十 TB、文件数千级别时目录列举完全不成问题——这一条的实际含义是「单表进入数百 TB 级、文件数进入百万级」。**极严延迟**属【经验】档：指在线服务路径（推荐排序、播放质量决策）要求特征与指标秒级内生效、且延迟不随并发量成比例上升；只看看板与报表时分钟级更新够用，这一条不成立。两者必须**同时**成立才构成自研理由：只大规模不严延迟，用现成表格式即可；只严延迟不大规模，用现成的流处理引擎即可。
- **「10–30 人专职基础设施团队」**：来自自研的持续成本结构——维护、生态适配、招人三块是长期固定支出，与数据量增长无关；团队小于这个规模时，这三块会持续挤占业务需求。判断办法不是数人数，而是看「过去 12 个月有多少工时花在基础设施自身的演进上」。
- **「时间窗」**（树中「现成方案今天是否已能覆盖」）：这是时间窗阈值，依据是 Iceberg 2018 年开源、Delta Lake 2019 年开源、Hudi 进入 Apache【公开：各项目发布与基金会时间线】——**2017 年自研是唯一解，2020 年后自研需要额外理由**。同一件事在 2017 年是唯一可行解，在 2025 年是不必要的自研；凡是「某公司在某年自研了 X」的经验，都要先加回这个时间窗再判断。
- **「实时与离线是否算同一个指标」**（树中第三条线索）：流批一体的唯一判据。存在重叠指标时，一体化的收益（口径一致、模型训练与线上推理对齐）大于其成本（表达能力受限）；不存在时反之。数出**同时**出现在实时与离线两侧的指标个数，就是这条分支的答案。
- **「约 10 个数据生产团队、一次审批以内」**（树中第二条线索）：Data Mesh 的前提阈值，属【经验】档——低于此规模，中心化目录的协作成本低于联邦治理；自助发布超过一次审批，说明平台抽象未完成。

这棵树里没有一个**顶层**节点问「你有多少数据」。这不是遗漏，而是刻意的：规模只作为「自研是否成立」那一条分支内部的边界条件出现（见上），而不是整棵树的起点。**数据量决定的是「哪些机制你会用到」，上面这些阈值决定的才是「哪些机制对你成立」**。同样一批 PB 级数据，在「准备自研」和「不准备自研」两条分支上会走向完全不同的答案，而后者才是绝大多数读者的位置。

### 7.6 各案例的失败面

**Netflix 自研路线的代价** —— 它用「自研」换到了当时不存在的能力，但自研的结果最终都走向开源与社区治理（表格式捐给 Apache 基金会，ML 框架与调度器先后开源）。这本身就说明一件事：**自研基础设施的维护成本无法由单一公司长期独占**。反噬条件是：一旦失去生态（例如自研成果无法开源或无人采用），维护成本重新变成一家公司的固定负担。

**Databricks 一体化路线的代价** —— 卖的是「收敛」：你放弃自选组件，换取零运维与统一目录。代价是锁定，且成本随用量上升；当数据量与查询并发增长时，「单价 × 规模」会成为显性成本项，此时自建的经济性才开始成立——注意是**此时**，而不是一开始。

**Uber 路线的代价** —— 自研组件与内部平台并行，导致维护面扩大、生态分裂；早期流批两套链路并存时，口径漂移只能靠规范约束而非结构消除。

**Airbnb 路线的代价** —— 数据科学家自治带来生产意愿与表达自由，代价是治理动作后置：资产膨胀之后才补目录与规范，成本比一开始就做更高。

三个跨案例的**反模式**：

- **反模式：照搬「自研」而不照搬「约束」** —— 症状是把「Netflix 自研了表格式/调度/ML 框架」当成结论，忽略它当年没有替代品；后果是团队把资源投入基础设施，业务需求停滞，而基础设施质量还比不上开源方案。正确做法：先核验现成方案的能力边界，只有落在边界之外才自研。
- **反模式：把 Data Mesh 当架构图** —— 症状是先画分域所有权，再补自助平台；后果是各团队各自建工具、口径彻底分裂。正确顺序是反过来的：先有自助抽象，再谈所有权。
- **反模式：只比表格式的读写性能，忽略元数据运维** —— 症状是选型只问「谁更快」；后果是上线后才发现清单重写、小文件合并、元数据服务高可用是持续的人力投入。把「谁来做元数据维护、每天花多少时间」写进选型评审，比多跑一轮 benchmark 有用。

把四条的代价并排看，规律是清晰的：

| 路线 | 换来的 | 付掉的 | 什么条件下反噬 |
| --- | --- | --- | --- |
| Netflix（自研 + 开源） | 当时不存在的能力 | 长期维护成本，最终必须靠生态摊薄 | 无法开源或无人采用时，成本回到一家公司 |
| Databricks（一体化产品） | 零运维、统一目录 | 锁定、成本随用量上升 | 规模增长到自建更便宜 |
| Uber（自研 + 内部平台） | 写入友好的表格式与自治平台 | 维护面扩大、生态分裂 | 自研组件与主流生态分叉，人才难招 |
| Airbnb（自治 + 协作规范） | 生产意愿与表达自由 | 治理后置的成本 | 资产膨胀后补规范，成本高于一开始就做 |

### 7.7 选型矩阵

| 你的处境 | 最该参考 | 最该避免照搬 | 理由 |
| --- | --- | --- | --- |
| 单表几 TB、团队 5 人 | 现成表格式的「够用」配置 | Netflix 的分层元数据 + 自研运维 | 分层解决的瓶颈你还没遇到，元数据服务却是确定的新增运维面 |
| 单表数百 TB 以上 | Iceberg 一类的分层元数据表格式 | Hive 目录列举式表定义 | 打开表的代价随文件数增长，规模一到就不可用 |
| 实时与离线有同一指标 | 流批共用一份定义 | 两套链路 + 口径文档 | 文档不消除漂移，结构才消除 |
| 上游已用表格式写 | 按快照版本判定就绪 | 文件到齐 / 哨兵文件 | 版本判定消除竞态与空闲等待 |
| 有条件做组织变革 | 先建自助平台抽象，再下放所有权 | 先下放所有权 | 抽象不成立时，下放等于把混乱分散 |
| 想节省基础设施投入 | 托管服务 | 自研表格式 / 调度器 | 自研的成本是长期固定支出，且今天有成熟替代 |

**四种常见组合的职责边界与运维代价**：

1. **开源表格式 + 自选引擎 + 通用编排器**——最中立的组合，没有厂商锁定。职责边界清晰（表格式管元数据、引擎管计算、编排器管依赖），运维代价在于三件东西的版本兼容与各自的升级节奏。
2. **托管湖仓 + 统一目录 + 托管工作流**——Databricks 形态。运维代价最低，代价是锁定与「单价 × 规模」；适合团队小、增长快、不愿承担基础设施职责的组织。
3. **自研表格式 + 自研调度 + 内部 ML 平台**——Netflix 形态。只有在需求超出公开方案边界、且团队规模足够时才成立；运维代价是三套自研系统各自需要值班，且必须靠开源或内部平台化摊薄。
4. **批为主 + 少量实时链路 + 规范统一口径**——大多数团队的现实解。运维代价最低，代价是口径一致性靠规范与评审维持，因此**规范必须可执行、可检查**，否则它会随人员流动失效。

四个组合里，前三个的共同点是「把一致性交给结构」，第四个是「把一致性交给流程」。选型时只要回答一句话就能定位自己在哪一边：**当有人违反规范时，系统会不会自动失败？** 会，你在前三种；不会，你在第四种——那就必须为规范配一个检查动作（比如 CI 里的口径校验），否则规范只是文档。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（结构性差异层面） |
| --- | --- | --- |
| 数据量不大、团队小 | 用现成方案，不自研 | 自研的成本是固定支出，与数据量无关 |
| 单表规模大到列举成为瓶颈 | 分层元数据表格式 | 打开表的代价必须与文件数解耦 |
| 实时与离线算同一指标 | 流批共用一份定义 | 漂移要由结构消除，不能由文档消除 |
| 上游写入原子化 | 按快照版本判定就绪 | 消除竞态与轮询空闲，但强依赖上游语义 |
| 想下放数据所有权 | 先建自助抽象 | Data Mesh 是组织变革，不是架构图 |
| 团队有基础设施专长、需求超出公开方案 | 才考虑自研 | 且要预设「最终需要开源摊薄维护成本」 |
| 只想尽快可用，不追求可控 | 托管一体化方案 | 用锁定换时间，但要提前算清「规模 × 单价」的拐点 |

这些建议有一个共同点：**它们都不要求你做技术上的跃进，而是要求你把一个结构性缺陷消除掉**。数据栈演进真正难的地方从来不是「选哪个组件」，而是「愿不愿意为了一次结构性的改进付出短期成本」——Netflix 在 2017 年愿意，所以有了 Iceberg；这也是这四个案例留给读者最实用的一条。

> 本节小结：这四个案例之间唯一真正起决定作用的差异，不是「组件选型」，而是**表由什么定义**——一旦表由分层元数据定义、提交是原子的，就绪判定、流批共用一份落点、schema 演进、时间旅行都会顺下来；反过来，只要表仍由目录列举定义，规模一到，上面每一层都要靠补丁维持。
>
> 证据边界再强调一次：本章引用的公开事实限于可核验的项目历史与官方公开材料（Iceberg / Hudi / Delta Lake 的开源时间线、Netflix 与 Databricks 的官方公开内容、Uber 2017–2018 年公开博客），**所有效果与成本类判断均标注为【推算】或【经验】并写出了依据**；凡是无依据的精确数字，本章一概不给。
>
> 💡 **思考锚点**：用 7.7 那句定位语给现状归一次档——当有人违反规范时，系统会不会自动失败？会，你走的是「一致性交给结构」（开源表格式 / 托管湖仓 / 自研表格式）；不会，你走的是「一致性交给流程」，那就得说清规范配了哪个检查动作（如 CI 里的口径校验），否则它只是文档。再做一次自查：你是否正用 Netflix 的分层元数据 + 自研运维，去解决一个你还没遇到的瓶颈？
