## 4. 关键决策

[§ 3](05-netflix-data-stack-section-3-sec3.md) 回答的是「哪一代结构被哪条约束逼出来」，结论是约束推出来的，选完就没有剩下的问题了。本节回答另一个问题：**这些决策装进一个真实组织要走几步、每一步手上应该多出什么、怎么在做的过程中就知道自己偏了、以及原来那批表与作业怎么办。** 决策本身的判据不在这里重讲——表格式、流批一体、编排、所有权各自的取舍见 §3.2 与 §3.3，本节只处理落地时的顺序、判据、产物与迁移。

> **证据档位**：本节【公开】给出来源类型与年份，【推算】写出推导链，沿用本案例材料（主文件 § 1 与 § 2）的人数与规模一律按【经验】使用——只取量级、不取精确值。两处公开锚点沿用 [§ 3.2](05-netflix-data-stack-section-3-sec3.md) 的口径：Iceberg 的开源与毕业年份【公开：Apache 软件基金会 Apache Iceberg 项目页，2018 开源 / 2020 毕业；当前状态以项目页内容为准】、Maestro 的公开年份【公开：Netflix 技术博客 Maestro 一文, 2022；可按「Netflix 技术博客 Maestro」自行检索核验，仓库与版本以官方仓库当前内容为准】。事件年份若与主文件 § 1.1 年表冲突，以主文件年表为准。

本节对两类读者的入口不同。**在存量上改造的人**（已有 Hive 表、已有调度器、依赖写在各团队的脚本里）从 4.1 的 Step 1 顺着走，4.4 是重点。**从零搭的人**先把 4.3 的选型判据读一遍再回到 4.1——从零开始最容易犯的错不是顺序反了，是**把「引擎优化」当第一步**，而它恰好是唯一一步不需要说服任何人改变工作方式、因此最容易被提前做掉的。

### 4.1 落地步骤

五步的顺序不是时间表，是依赖关系。先给一张总览，后文每一步给三件事：**产物**（结束时手上多出什么）、**判据**（怎么在做的过程中就知道偏了）、**为什么必须这一步、为什么在这个位置**。

| 步骤 | 手上多出来的东西 | 判据（低于这个标准就是没做） | 省掉它 / 换序后，返工会落在哪 |
| --- | --- | --- | --- |
| Step 1 表状态权威进元数据 | 表清单 + 路径式作业欠账清单 + 唯一 Catalog | 「加一列要重写多少数据」= 零 | 后面四步都没有共同落点 |
| Step 2 流批共用一份逻辑 | 一份逻辑定义 + 两侧结果的比对作业 | 比对作业能报出一个差异率 | 两侧各一份存储，「以谁为准」变成长期争论 |
| Step 3 依赖按上游版本判定 | 可查询依赖图 + 字段级血缘 + 统一回填入口 | 上游重试那次，下游对齐到了哪一批 | 批次错配静默发生，数值上不明显 |
| Step 4 所有权登记到人 | 数据产品目录 + Owner 字段 + 常设治理机制 | Owner 字段里是人名不是团队名 | 影响面分析给出的对象无法被触达 |
| Step 5 ML 平台与面向模型的投影 | 特征表 + 实验与数据版本记录 + 只读投影 | 只靠元数据能否回答「取哪张表、用了影响谁」 | 前四步的资产缺项在这一层被等比放大 |

**Step 1：把「表状态」的权威搬进元数据（Iceberg）（数周到数月【经验：随表数量与引擎 / 消费方数量变化】）**

- **做什么**：选一种开放表格式，把「表 = 某个目录下的文件」改成「表 = 一组分层元数据指向的文件集合」；把所有作业的读写改道到表名，而不是分区路径；确定唯一的 Catalog 权威，并写下来"谁有权改快照指针"。
- **产物**：一份「已通过表读写」的表清单、一份「仍在直接读写分区路径」的作业欠账清单、一个被明示的唯一 Catalog。
- **判据**：抽 3 张核心表，问「加一列要重写多少数据」——答案不是「零」，说明表状态还是路径式的；再抽 3 个作业，看它的输入写的是表名还是某个 `.../dt=2024-01-01/` 路径。第二条抽出任何一个路径，就把这个作业记进欠账清单。
- **为什么必须这一步、为什么在最前**：并发写、结构演进、时间旅行、多引擎共读这四件事，全部派生自「表状态有没有一个可原子替换的权威」（§3.2.2 的结论）；这条权威为什么能同时承载批流两侧，机制与代价见该节，本节不重述。落地时容易漏掉的是它带进来的**新增值班项**：元数据本身成为一批必须维护的文件，Compaction 与过期快照清理从「可选优化」变成有归属、有监控的排期项——**表能读了不等于这一步做完，合并作业没人负责时，问题会在第一次高频写入之后从读路径上冒出来。** 换序的代价见 §3.3 的第三对误配：在表状态还没被元数据定义时就先加流式写入，换不来时效，只会多出两个新的运维问题（是哪两个、为什么，见该节）。

**Step 2：让流与批共用一份逻辑定义（Keystone）（数周量级【经验：随链路条数与两侧比对作业的成熟度变化】）**

- **做什么**：业务逻辑只写一份，由流式链路（Kafka → Flink）给出低延迟结果，由批链路周期性回灌与修正，两侧写同一张表、并约定迟到数据与状态恢复的处理口径；引入统一的 schema 注册中心（Schema Registry，序列化用 Apache Avro 一类，让 schema 的演进而非兼容变更在写入前被拒绝）；多团队共用集群时把租户隔离与自动监控告警一并做掉。
- **产物**：一份逻辑定义 + 一个两侧结果的逐日比对作业 + 一份 schema 注册记录。
- **判据**：同一个指标在实时看板与离线报表上，是不是来自同一份定义；以及**那个比对作业能不能报出一个差异率**。差异率答不出来的，等于从未验证过「一致」——定义共用只是必要条件，两边引擎对同一段定义的执行语义可以不同。
- **为什么必须这一步、为什么在 Step 1 之后**：流批一体能成立的前提是表状态已由元数据定义（§3.2.3）——没有共同的落点，两侧只能各自维护一份存储，「以谁为准」会变成长期争论。共享一张表为什么就足以让两条链路对齐、以及它换来什么代价，机制见 §3.2.3，本节不重述；本节要提前排进工作量的，是它带出来的两件组织动作：**提交冲突的重试与隔离策略由谁定**，以及**怎么让团队真的建立起「快照」这个概念**——概念没建立起来时，就会有人为了图快绕过表格式去动文件，这类作业平时能跑通，只在一次并发提交之后才暴露。

**Step 3：让依赖从「文件是否出现」改成「上游快照版本」（Maestro）（数周到数月【经验：随工作流数量与依赖声明的粒度变化】）**

- **做什么**：工作流用统一 DAG 模型描述，触发支持时间 / 事件 / API 三类；**依赖声明成上游数据集的某个版本，而不是「目录里有文件了」**；每个工作流可声明自己的 SLA（完成时间承诺）并由编排器据此告警；血缘由任务定义与查询自动推导、粒度到字段、批与流在同一张图上；回填与重跑在模型层实现，而不是每个脚本里各做一遍。
- **产物**：可查询的依赖图 + 字段级血缘 + 一个统一的重跑 / 回填入口。
- **判据**：找一个刚发生过上游重试的批次，问下游那次对齐到了哪一批——答不出来，说明依赖判定还停在「文件到齐」；再问「改这个字段会影响谁」，答案如果按天计，说明依赖还在人的记忆里。
- **为什么必须这一步**：因为「上游准备好了没有」这个问题的**判据**只有在依赖被提取成可查询对象之后才能被回答；文件到齐式的判定在上游分批写、重试、并发批次重叠时都会把批次对错，而且错得数值上不明显。**因为依赖边界由存储层的提交语义保证，所以批次对齐不再依赖观察文件系统的外观；代价是编排器与表格式被绑在一起**——上游一旦有绕过表格式的就地覆盖式写入，整条依赖链的判据就失效。

**Step 4：把所有权登记到人（Data Mesh 的所有权层）（首批登记数周，全部收口到人可延伸到数月【经验：随被跨团队消费的表数量变化】）**

这一步对应的是 **Data Mesh** 的所有权层：该范式由 Zhamak Dehghani 于 2019 年提出，四条原则通常表述为领域所有权、数据即产品、自助平台与联邦治理【公开：Dehghani《How to Move Beyond a Monolithic Data Lake to a Distributed Data Mesh》，ThoughtWorks，2019；标题与年份可按作者名与该标题自行检索核验】。本节只做它的落地侧，四条原则各自的代价与失效点见 §3.2.4。

- **做什么**：每张被跨团队消费的表登记为数据产品（Owner 到人 + 文档 + SLA），平台保持为基础设施而不持有业务表；跨团队的争议与例外走常设的联邦治理机制，而不是逐次临时拉群。
- **产物**：数据产品目录 + Owner 字段 + 一份常设治理机制的名单与评审节奏。
- **判据**：抽 5 张被多个下游引用的表，**看 Owner 字段里是人名还是团队名**；再挑其中一个 Owner 做一次通知演练，看通知能不能落到接收的人身上。团队名的登记等于没有 Owner。
- **为什么必须这一步、为什么排在调度之后**：调度与所有权为什么是一对（缺任何一边，切换层都失去依据），机制见 §3.2.4，本节不重述。本节只补顺序上的理由：**调度先建成，登记才有可挂靠的对象**——DAG 已经把「哪些表被谁引用」提取成可查询事实，登记 Owner 时才有一个地方去回答「这张表被谁依赖」；反过来先做所有权，登记完仍然证不出依赖关系，字段填过一遍却没人用得上。失效的形态见 §3.2.4 的失效点：缺口不报错，只在下一次跨团队变更之后表现为「下游没人知道」。

**Step 5：把 ML 平台与面向模型的投影接上（Metaflow 与特征平台）（数周到数月【经验：随特征数量与在线特征存储的选型变化】）**

- **做什么**：特征平台这一层物化在开放表格式上，在线侧另配一份低延迟存储（Redis 一类 KV / 在线特征存储；具体选哪个按你自己的点查延迟与回填一致性要求定），让训练与推理取自同一份特征定义——**这一层的验收标准不是「用了哪个在线存储」，而是训练与推理两个读取入口能不能被证明确实指向同一份定义**；ML 框架（本案例的 Metaflow：Step 抽象自行组成 DAG、本地与云端一致的执行环境、训练数据版本管理、实验管理；对外三件是客户端 SDK / 云端执行服务 / 可视化界面）负责流程与可复现；训练侧落在容器编排（Kubernetes 一类）+ Spark 上，部署走容器，推理侧由自研服务与 Titus 一类容器运行时承接；最后把 schema、列级统计、快照历史、口径与血缘整理成一层机器可读的投影，供 GenAI / Agent 取数与模型审计使用。
- **产物**：特征表清单 + 训练样本与实验的可回溯记录（这一步用了什么代码、什么参数、哪一份数据）+ 一层面向模型的只读投影。
- **判据**：让一个不了解这套数仓的人（或一个模型）只靠元数据回答「我要算 X，该用哪张表、哪个字段、改了会影响谁」。卡在哪一步，资产就缺在哪一步——§3.2.5 把这条写成了自验方法，本节沿用。另一条更早的判据：挑一次失败的实验，看能不能只靠记录复现出同样的输入。
- **为什么必须最后**：这一步几乎不新建系统，只把已有资产换一类消费者（人 → 人 + 模型）；它的可行性由前四步的完成度决定，不由这一代的技术选型决定（§3.2.5）。**因为模型的输入里区分不了「定义不存在」与「定义存在但没人维护」，所以前四步攒下的业务含义与口径补得不全时，这一层会产出形式正确、语义靠猜的结果**——越像正确答案的错误越难被识破。

**最常被跳过的是 Step 4。** 它不产生任何性能收益，验收标准又是一句「Owner 字段里是不是人名」，因此在排期上永远排在「把管道跑得更快」之后。它的代价以一次跨团队变更事故的形式出现：上游改了字段，下游没人知道；复盘时看到的是「流程执行不到位」，而真正的原因是一个字段里填了团队名——**修一个人名，比加十条流程有效。**

### 4.2 关键技术点

**表状态由分层元数据定义 + 快照隔离**

- **做法**：表的当前状态由一个可原子替换的元数据文件表达（schema + 分区规范 + 快照指针），快照引用清单、清单引用数据文件；所有写入以「产生新快照再切换指针」完成。
- **机制**：这条为什么成立（不可变的数据文件 + 可原子替换的指针、清单里的列级 min/max 与 null 计数、剪裁能力与分区设计解耦）见 §3.2.2，本节不重述。落地要记住它的两条推论：**剪裁由引擎在规划阶段完成，用户不必把分区写对**——所以「查询慢」不能拿「分区没写好」当唯一解释；**列级统计由写入路径产生**，一旦有作业绕过表格式直接落文件，统计就断供，剪裁会静默失效。
- **失效条件**：触发条件与反转形态见 §3.2.2 的失效点（写入批量小、提交频率高 → 元数据比数据增长得更快）。本节只补**发现它的观测纪律**：看板上「近一周提交次数」与「清单文件数」两个数要能一起看到，两者同阶增长时，读延迟由写节奏而不是 SQL 决定；「未合并文件数」这个指标如果没人看，等于这条失效条件没有观测信号。
- **档位**：清单文件数与提交次数的关系【推算：按上述分层结构，一次提交至少新增一个快照与一份清单列表；若单次提交只新增少量数据文件，则清单文件数 ≈ 提交次数，即元数据规模由写入频率而非数据量决定】。

**隐藏分区**

- **做法**：分区规则按转换表达式声明（例如按事件时间的天），物理布局不暴露给查询；查询按事件时间过滤即可下推。
- **机制**：机制与代价见 §3.2.2（分区值是元数据侧的属性，所以改分区方式不必重写整表）。本节只补一条落地要求：分区表达式**从查询过滤条件反推**，并在建表评审时写下来源——从上游表的分区键继承过来的表达式，等于把旧的物理布局换个地方重写一遍。
- **失效条件**：**当分区表达式长期不随查询模式演进时，这条会退化成「分区还是手工参数」**。症状：某类查询忘记带过滤条件即全表扫，而团队把它归因为「SQL 写错了」——如果分区是引擎可用的信息，这类全表扫本该在规划阶段被剪掉大部分。
- **档位**：无精确数字；判断方法见 4.9 自检清单。

**一份逻辑、两种执行，并且持续比对（Keystone）**

- **做法**：逻辑层只写一次，流式负责低延迟、批式负责回灌修正，两侧写同一张表；另配一个定期比对两侧结果的作业，差异超阈值告警。
- **机制**：漂移的来源是「有两份实现」，不是「某处写错了」——把实现收敛到一份，边界处理、窗口语义、状态管理、变更不同步这四类漂移来源被结构性消除。**代价是这不等于统一引擎**：执行特性差异太大，强行合引擎成本极高，所以统一的是语义，不是执行。
- **失效条件**：**当定义的语义差异恰好落在某个特征或指标上时，「一份定义保证一致」会反转成「离线指标好、线上效果差」**。症状：同一特征在两侧的统计值对不上，而团队的第一反应是「以离线为准」；或从没有人做过两侧特征值的逐日比对。修法不是再统一一次叙述，而是把「一致性差异率」列为一级指标。
- **档位**：本节不引用任何具体差异比例；沿用本案例材料的判断只到「存在可观测偏差」这一量级【经验】。

**依赖按上游快照版本判定（Maestro）**

- **做法**：下游依赖声明为上游数据集 / 快照的版本，上游产生新快照后触发下游；触发支持时间、事件、API 三类；回填在模型层表达。
- **机制**：因为「数据是否就绪」由存储层的提交语义保证，而不是由观察目录外观推断，所以「到齐没」「重试写成两份」「两批混算」这三类批次错配不再发生；事件驱动同时替代了轮询——轮询要么慢要么浪费。
- **失效条件**：**当上游存在绕过表格式的就地覆盖式写入时，这条会失去判据**。症状：某个数据集始终不产生新快照，下游要么永远不被触发，要么退回按时间触发后空跑；这类写入必须被单独标记出来（它们同时也是 Step 1 的欠账清单）。
- **档位**：批次错配率从「并发与重试下会发生」到「由提交语义保证」——性质描述，不给比例【经验】。

**血缘自动推导、粒度到字段、批流同图**

- **做法**：血缘由任务的输入输出定义与查询语句自动推导；粒度到字段；流式任务与批任务写进同一张图；人工只补解析器看不懂的场景（动态 SQL、脚本任务），且必须标出来源。
- **机制**：因为血缘是从生产事实里提取的，它不依赖任何人额外填写，也就不会随时间过期——人工维护的血缘通常在数周到数月内就会与实际不符【经验：区间随资产变更频率与登记覆盖面变化】，而不可信的血缘等于没有。字段级粒度的必要性来自判据：改一个字段与改整张表的影响面完全不同，表级血缘会把前者也当成后者。
- **失效条件**：**当动态 SQL、拼接表名、脚本任务的占比上升时，盲区会从「已知」变成「不可知」**——症状是改了上游却漏掉某个实时下游，而事后才发现那条链路从未上图。修法是把这些场景单独标记、可度量、逐步补齐，而不是假装它们在血缘里。
- **档位**：人工登记血缘的正确率随「自上次登记以来发生变更的资产占比」单调下降【推算：登记是时点快照，定义在持续演进；无自动解析时，可核对的正确率 ≈ 未变更资产的占比，因此随变更累积而不升】。

**引擎侧优化：Spark 与 Flink**

- **做法**：Spark 侧启用按负载的动态扩缩容（Dynamic Allocation）、运行时自适应优化（Adaptive Query Execution，AQE）、堆外内存（Off-Heap）以减少 GC 压力，并针对对象存储做多线程读取；Flink 侧使用本地状态后端（RocksDB 一类）+ 自研优化，用 Kafka 事务与 Checkpoint 组合出端到端 Exactly-Once，大状态作业按单任务 TB 级状态规划资源配置。
- **机制**：这些优化的共同点是把成本从「计算时间」挪走——动态分配让资源跟负载；自适应优化在运行时修正因统计不准而选错的分区策略；堆外内存把对象生命周期从 JVM 堆里移出去；对象存储的多线程读取针对的是「单流吞吐受往返时延限制」而不是带宽。
- **失效条件**：**当瓶颈其实在「要打开的文件多」时，这一条全部失效**——症状是引擎升级、参数调优、压测都做完了，慢的作业仍然慢，且它们的共同点是要打开的文件特别多（§3.5 把「只换引擎不换表格式」列为第二条反模式，原因与修法见该节）。本节只补一条观测纪律：**调优前后要留下三个数——任务数、shuffle 分区数、对象存储请求数**；三个都不动而结论说「快了」，说明你改的是配置，不是瓶颈。
- **档位**：所有阈值随负载形态变化，本节不给数值【经验】；「单任务 TB 级状态」是该类作业的形态描述，不是某个已核到的测量值【经验：沿用本案例材料的形态口径，请按自己作业的状态大小重新规划】。

**所有权登记到人 + 数据 SLA**

- **做法**：每个被跨团队消费的数据集登记 Owner（具体到人）、文档入口与 SLA；平台不持有业务表，只提供登记入口与查询；人员变动触发重新登记。
- **机制**：因为 Owner 是显式字段，「有事找谁」从社交知识变成可查字段——推导见 §3.2.4，本节不重述。落地要补的是**同一张卡片上的第二个字段**：SLA 把「这张表能不能被依赖」从口碑变成承诺，而承诺必须对齐到一个可被订阅的产出时间，否则它只是一个愿望。
- **失效条件**：触发条件与反转形态见 §3.2.4 的失效点（登记退化为团队名、或登记后不随人员变动更新 → 没有对接人）。本节补的是两个**可以被执行的检查时点**：登记当下抽 5 张表看 Owner 字段里是不是人名；人员变动之后，看是谁负责触发重新登记——没有触发人的登记制度会在第一次组织调整后整体过期，而下游通知照旧被发到群里。
- **档位**：登记成本与表数量成正比、且必须在下一次变更事故之前完成【推算：逐表登记、无自动化路径时，工作量 ≈ 表数量 × 单表登记与复核时间；这部分时间不可压缩，只能提前】。

**多引擎共读同一份表、实时数仓与 Compaction 的归属**

- **做法**：批（Spark）、流（Flink）、交互查询（Trino 一类）三类引擎以原生方式读同一张表——本案例材料把交互查询这一侧单记成一条能力项「高并发查询」，并发能到多高取决于查询引擎的资源组与排队策略，请按自己的并发目标与表规模实测，本节不给数值；本案例把这条链路称为实时数仓：Kafka（流）→ Flink（实时计算）→ 开放表格式（表状态）→ 交互查询引擎（查询）→ BI（消费）。小文件合并与过期快照清理以常驻作业运行，并单独排期、单独监控。
- **机制**：因为各引擎读的是同一份表状态而不是各自的副本，「哪一份是对的」这个问题消失；同时合并从一次性任务变成服务，读路径的延迟因此由合并的节奏决定。
- **失效条件**：触发条件与反转形态见 §3.2.3 的失效点（写频率长期高于合并速度 → 读的人被写的人拖慢）。本节只补处置口径：**合并作业与业务任务分开排期、单独监控**，并把交互查询 P99 与写入速率画在同一张图上——两条曲线同向尖峰时，读侧没有可调旋钮，只能回头调合并的资源与节奏。
- **档位**：合并任务的资源占用应与业务任务分开排期【经验】，具体配额随写入频率与文件目标大小变化，本节不给数值。

### 4.3 工具链与平台

本节不给「推荐组合」，给的是**判据**：在你自己的约束下，每一类该怎么重新推一遍。选型的第一原则来自 §3.2 总览的结论——**底座要按寿命最长的那条约束来选**，因为底座换一次要付大代价。

**表格式（本案例的核心选型）**

| 维度 | Hive 表格式 | Delta Lake | Iceberg | 判据（这一列在什么条件下才重要） |
| --- | --- | --- | --- | --- |
| ACID | 无 | 有 | 有 | 有没有两个任务同时写同一张表 |
| Schema Evolution | 弱 | 有 | 强 | 「加一列要不要重写历史数据」 |
| Time Travel | 无 | 有 | 有 | 出问题时能不能回到某个时间点的视图 |
| 隐藏分区 | 无 | 无 | 有 | 分区方式会不会随查询模式变化 |
| 流批一体 | 弱 | 中 | 强 | 同一份事实要不要供两个时效的消费方 |
| 引擎支持 | Hive / Spark | Spark 生态为主 | Spark / Flink / Trino 等多引擎 | **有几个引擎要以原生方式读同一张表** |
| 社区治理 | Apache | 由单一厂商主控 | Apache 开放治理 | 这套底座会不会被单一厂商的路线决定生命周期 |

Iceberg 由 Netflix 内部立项、2018 年开源并捐赠给 Apache 软件基金会、2020 年毕业为顶级项目【公开：Apache 软件基金会 Apache Iceberg 项目页，2018 开源 / 2020 毕业；当前状态以项目页内容为准】；Delta Lake 由 Databricks 开源、与 Spark 生态绑定更紧【公开：Databricks 开源公告（2019）；许可与版本现状请以该项目官方仓库当前内容为准】。**Iceberg 的生态广度本身也是选型依据之一**：本案例材料记的是 Databricks / Snowflake / AWS / Google Cloud 等厂商都集成 Iceberg【公开：上述厂商官方文档中的 Iceberg 支持条目；具体支持形态、可用区域与是否 GA 以各家文档当前版本为准】。**误选判据里最容易被忽略的是「引擎支持」与「社区治理」两行**：前六行比的是功能表，后一行比的是「谁有权决定这套底座下一步往哪走」。把这两行当成次要维度的典型后果是——功能全对，但引擎换代时你被迫跟着一个厂商的路线走，或者发现某个引擎迟迟不支持你要的那个特性。

**其余类别的选型判据**

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 目录与元数据权威 | 单一 Catalog（自建或开源实现）/ 每个引擎自带元数据 | 有第二个引擎要以原生方式读同一张表时，**必须收敛到单一 Catalog**；只有一个引擎时，权威归属可以晚一点再定 | 两套指针并存：两个引擎对「当前状态」的答案不同，且回退比前进更贵 |
| 消息与传输 | Kafka 一类可回放的日志型消息系统 | 需求里包含「多消费方各自按自己的进度读同一份流」「按分区保序」「可回放」三项中的两项以上 | 用点对点或不可回放的传输，重放与回填要靠上游重发，重放能力变成业务方的负担 |
| 流计算 | Flink / 结构化流式处理 | 需要事件时间语义、需要为每个键维护可恢复的状态时，选带状态后端与 Checkpoint 的引擎 | 状态恢复要靠重跑全量；Exactly-Once 退化成「尽量不丢」 |
| 批与交互查询 | Spark（批加工与合并）/ Trino 一类交互查询引擎 | 同一批表要被「长跑批任务」与「分钟级交互查询」同时读时，把两类负载分开：批用能扛 shuffle 的引擎，交互用能低延迟规划的引擎 | 用一个引擎通吃：交互查询被批任务的资源挤占，或批任务为交互查询的规划特性付代价 |
| 工作流编排 | Maestro（本案例）/ Airflow 一类 | 见下方对照表 | 依赖判定表达力不足，会退化成「按时间触发 + 空跑检查」 |
| ML 流程与实验 | Metaflow（本案例）/ SageMaker / Kubeflow / MLflow 一类 | 数据科学家的日常工作语言是不是 Python；是否要求「本地能跑、云端不用改代码」；是否需要把实验、数据版本与产出绑定 | 流程与实验管理分裂到多套工具，同一个模型「用什么代码、什么参数、哪份数据」回答不出来 |
| 在线特征存储 | Redis 一类 KV 存储 / 特征平台自带的在线实现 | 训练与推理要不要取自同一份特征定义；点查延迟与特征回填由谁保证一致 | 两侧各读一份特征，偏差只在生产上暴露，且发生时两边都认为自己读的是对的那份 |
| 对象存储 | S3 一类 | 是否按请求次数与列举次数计费；小文件与列举成本会不会进入账单主体 | 只比较每 GB 单价，把请求数与合并工时放到账单之外 |

**编排器对照（本章 § 7 提到本节的这组对比维度）**

| 维度 | Airflow | Maestro | 判据（你的条件下该看哪一列） |
| --- | --- | --- | --- |
| DAG 模型 | 灵活但复杂 | 统一 | DAG 是「少数人写，多数人读」还是「谁都能写」——前者可选灵活，后者要统一 |
| 触发方式 | 时间为主 | 时间 / 事件 / API | 上游是不是流式或事件式产出——是的话，只有时间触发会带来空跑或延迟 |
| 可视化编辑 | 一般 | 强（本案例材料记的是「拖拽即可完成 DAG」；是否仍支持、覆盖到什么程度以官方文档当前版本为准） | 使用者的画像：工程师还是分析师 |
| 平台适配 | 上游生态通用 | 与本案例的存储与表格式贴合 | 依赖要不要声明成「上游快照版本」——这一列决定批次对齐能不能被保证 |
| 社区 | Apache 生态大 | 由单一厂商主导 | 你要不要一个外部社区共担适配成本 |

**这一类里最容易被误选的是表格式**，因为它是唯一一个「换了以后不能回退、且收益要等第二次结构变更才出现」的选型。误选的典型后果不是性能差，而是**迁移期两套指针并存**：团队一边迁一边留旧路径，读到的「当前状态」取决于走了哪条通路；等发现要回退时，回退意味着说服两拨人各放弃一次已经上线的东西（§3.6 把它列为近乎不可逆的两项之一）。第二容易被误选的是编排器——按 UI 好不好用选，而不是按「依赖能不能声明成上游版本」选，结果换掉的是界面，批次的判据还是「文件到齐」。

### 4.4 存量迁移

存量迁移的目标不是「迁完」，而是**在迁移期间不产生第二个权威**。以下四件事按顺序做。

**① 先做一件立刻见效且可回退的事**：挑一张**被多个引擎读、且结构变更频率高**的表，把它迁到开放表格式，但**先只迁读路径**——用新格式读、与旧读取结果逐批比对，写入路径暂时不动。这件事见效快——加列不再需要重写数据、按快照可回看，在单张表上通常以周计即可验证【经验：随该表的文件数、消费方数量与比对作业的成熟度变化】，且可回退：删掉新读取入口即可，旧路径从未被改动。判据：比对期内新旧读取结果的差异条数必须为 0；不为 0 时先查元数据生成环节（列类型、时区、null 语义），不要先怀疑引擎。

**② 剩余历史资产分三类处理**，不要一刀切：
- **迁**：被多引擎消费、或变更频率高、或有回溯需求的表。判据是问两个数——下游作业数、近半年的结构变更次数。
- **留但封口**：稳定、单一消费方、从不改结构的表。不改格式，但**禁止再新增直接读写分区路径的作业**，并把已有的路径式作业登记进欠账清单。封口比返工便宜，且不阻塞迁移。
- **冻结退役**：一次性表、临时表、无人引用的表。给出退役日期并登记；治理优先清理这类，因为它们对迁移的唯一贡献是消耗评审注意力。

**③ 双轨怎么维持、维持多久**：迁移期用「双写 + 双读比对」或「旧写新读」两种形态之一，选哪一种取决于旧路径能不能被拦截——**能拦截写入就选双写，拦不住就只做只读比对**，因为拦不住的写入无法保证两套状态一致。维持时长**不用日历时间定，用事件定**：直到「连续 N 次结构变更都没有触发回退」为止【经验：N 取到能覆盖一次完整发布周期的量级，随你的发布频率变化】。双轨期间必须有一张运行中的差异看板（新旧结果差异条数、路径式作业剩余数、新格式表占比），否则双轨会从过渡态变成长期态——**双轨的成本不在迁移期，在于它一旦稳定下来就没有人负责收口**。

**④ 什么信号说明可以退出双轨**：三个同时满足——旧路径的读取在访问日志里连续一段观察期归零；新路径的写入提交成功率与「提交到快照可见」的延迟稳定；以及**做一次回退演练，发现已经不需要回退**。第三条是最容易被跳过、也最能说明问题的一条：如果团队仍然认为回退是必要的，说明差异看板上的某个数一直没被解释清楚。

**两项近乎不可逆的事，要在动手前想清楚**（沿用 §3.6）：一是**表状态的权威一旦分叉**，回退比前进更贵；二是**所有权登记的粒度一旦被定成团队**，后续再收到人需要逐表补登记，成本与表数量成正比，且必须在下一次变更事故之前完成。因此迁移的方向是**先收紧表状态与登记的最小结构，再谈规模与消费面的扩张**；反过来做，会把两件事的难度叠加。

### 4.5 模板 / 示例

**模板 1：开放表格式的建表与元数据自查（以 Iceberg 的 SQL 语法为例）**

```sql
CREATE TABLE lake.playback_events (
  user_id    BIGINT,
  title_id   BIGINT,
  event_time TIMESTAMP,
  device     STRING
) USING iceberg
PARTITIONED BY (days(event_time))          -- 隐藏分区：查询按 event_time 过滤即可下推
TBLPROPERTIES ('format-version' = '2');
-- 结构变更只改元数据；列按 field id 解析，不按位置
ALTER TABLE lake.playback_events ADD COLUMN app_version STRING;

-- 元数据自查：这三张元数据表能回答「当前状态是什么、变过几次」
SELECT * FROM lake.playback_events.snapshots;  -- 快照列表与提交时间
SELECT * FROM lake.playback_events.history;    -- 快照的切换历史
SELECT * FROM lake.playback_events.files;      -- 当前快照引用的数据文件
```

**怎么用**：把表名、字段、分区表达式换成你自己的；`USING iceberg`、`PARTITIONED BY (days(...))` 与 `metadata table` 的可用写法**以你所选表格式与引擎的官方文档当前版本为准**（不同引擎对隐藏分区表达式的支持不同）。**不要照抄的是字段与分区**——分区表达式应当从你的查询过滤条件反推，而不是从上游表的分区键继承。

**模板 2：把依赖声明成「上游版本」而不是「文件到齐」**

```yaml
# 结构模板（不是某个调度器的官方语法；字段名请替换为你的编排器实际支持的形式）
workflow: playback_daily_rollup
tasks:
  - id: build_rollup
    # ✗ 依赖写法之一（不可靠）：等目录里出现文件
    #   depends_on: {path: "s3://lake/playback_events/dt=2024-01-01/", ready_when: file_exists}
    # ✓ 依赖写法之二（可靠）：依赖上游某个数据集的具体版本
    depends_on:
      - dataset: lake.playback_events
        version: snapshot            # 由存储层的提交语义保证"这一批是什么"
    trigger:
      on: dataset_update             # 事件驱动；另可按时间或 API 触发
    on_late_data: rerun_with_same_snapshot   # 迟到数据：重跑同一快照，不追新快照
```

**怎么用**：填的是 `dataset` 与触发方式两格；`version` 一格的取值方式（快照 id、版本号还是分区水位）按你的存储层能力选，**能表达「具体哪一批」即可**。`on_late_data` 这一格不要照抄——它取决于你的业务能否接受重跑同一快照，改错会让迟到数据永远补不进来。

**模板 3：数据产品登记卡片（所有权层的最小字段集）**

```markdown
**数据集**：{数据集名}

- **Owner**：{人名}（不是团队名）；{备份人名}
- **回答什么业务问题**：{一句话}
- **口径**：{指标 / 字段的可执行定义或定义链接}
- **粒度与分区**：{粒度声明} + {分区表达式}
- **SLA**：{产出时间} + {可用性承诺}
- **上游依赖**：{数据集@版本规则}
- **已知下游**：{按血缘自动生成，不手填}
- **密级与访问边界**：{密级}；{哪些字段需要单独授权}
```

**怎么用**：`Owner` 与 `SLA` 两格必须填具体值；`已知下游`**不要手填**——手填的下游清单在数周到数月内就会过期【经验：随这张表的下游数量与下游自身的变更频率变化】，它应当来自血缘系统。`回答什么业务问题` 一句是给模型和新人看的：它是「表名之外的可检索入口」，缺了它，自助取数只能靠猜表名。

**模板 4：变更前的影响面评估卡**

```text
变更内容：{改的表 / 字段 / 口径}           提交人：{人名}
① 影响面（自动生成）：直接下游 {N 张表} / 递归下游 {M 项（含指标、看板、特征）}
② 关键资产命中：{有没有 SLA 承诺或影响资金 / 合规的资产} —— {名单}
③ 分流：
     影响面小且无关键资产 → 放行（记录本次评估结果即可）
     影响面大或命中关键资产 → 阻断，附：{迁移方案} + {下游通知记录} + {Owner 会签}
④ 回滚方案：{按快照回滚到哪个版本} + {回滚后下游需不需要重跑}
```

**怎么用**：前两格由系统生成，不手填；`③` 的阈值**要写进流程里，不要留在评审人的判断里**——没有阈值，门禁会退化成「每次都过」或「每次都拦」，后者一定被绕过。`④` 这一格是本文档区别于「通知单」的地方：没有回滚方案的变更，等于把风险留给下游。

**模板 5：训练与推理的特征一致性自证卡（Step 5 上线后的第一件交付物）**

```markdown
特征名：{特征名}                         定义出处：{哪张表 / 哪个指标定义}
① 训练侧读取入口：{表名 @ 快照版本规则}     ② 推理侧读取入口：{在线存储的 key 规则}
③ 两侧是否同一份定义：{是 / 否}             判定依据：{同一个定义文件 / 同一条血缘边}
④ 最近一次逐日比对：{日期}；差异条数 {N}；告警阈值 {阈值}；责任人 {人名}
⑤ 回填口径：{历史特征重算后，在线侧怎么被刷新}；{由谁触发}
```

**怎么用**：`①` 与 `②` 两格必须各自指到一处具体产物，指不出来，说明「训练与推理取自同一份定义」还只是一句话。`③` 的判定依据要写成「同一个定义文件」或「同一条血缘边」，**不要写成「命名规范一致」**——两个名字相同的特征各自算出来，血缘上可能根本没有交集。`④` 不要留空：没有逐日比对的结论，一致性只能在生产上暴露之后才被发现。`⑤` 取决于你的在线存储能不能被批量刷写，填错会让离线侧的修正永远到不了在线侧。

### 4.6 成本：这套东西的账单

这个案例的贵不只在"数据量大"，更在**它同时选了开放表格式、多引擎共读、所有权分散这三件互相加固的事**——每一件都把成本从"引擎内部"挪到一个必须有人负责的地方。

- **云账单（最相关的一项）**：对象存储按**请求次数与列举次数**计费，小文件多时这一项会成为账单主体，而不是每 GB 单价（4.3 表格"对象存储"一行）。估算口径【推算：一次查询的存储请求数 ≈ 规划阶段命中的清单文件数 + 实际读取的数据文件数；而清单文件数随提交频率上升（4.2「表状态由分层元数据定义」的档位），于是"写得太碎"会同时抬高清单请求与数据请求两笔钱】。Compaction 的作用正是把"存储省下的钱"换成"合并作业的算力"——两笔钱一起看，才是这张表的真实单价。
- **人力（形态上被搬走的一项）**：Data Mesh 的所有权层不省成本，它把成本从中央平台**挪**到各业务团队——本案例数据团队的规模与分散形态见主文件 [§1.3](05-netflix-data-stack.md)。每个域要养自己的数据产品 Owner 与值班，中央平台只提供登记入口与查询（4.2「所有权登记到人」一条）。
- **硬件 / 算力（被形态决定的一项）**：三类负载（Spark 批、Flink 流、Trino 交互）以原生方式读同一张表，意味着同一份数据被三类引擎各付一次算力；流批共用逻辑消掉了"两份实现"，但流式常驻（Kafka + 有状态的 Flink）是**7×24 的基础开销**，批任务才可弹性——账单的节律因此与流量峰谷解耦。

**为什么贵在这里**：这是"形态成本"而非"规模成本"。表格式把运维从引擎内部移到一批元数据文件与 Compaction 作业（4.1 Step 1 已把它列为新增值班项）；多引擎让每类负载各养一套；所有权分散把中央成本转成组织成本。通用的单位成本归因与 FinOps 看板见 [11-cross-cutting/03-data-cost-finops](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)。

### 4.7 容灾与故障演练

这个案例的"灾难"不是丢了一块数据，而是**表状态的权威分了叉**——4.4 把它列为两项"近乎不可逆"之一：一旦两个 Catalog 或两条写入路径都成了权威，"当前状态是什么"的答案就取决于走了哪条通路，而回退比前进更贵。按 SRE 顺序列本案例特有的失效形态。

| 失效模式 | 影响面 | 降级 / 处置 | 演练 |
| --- | --- | --- | --- |
| Compaction 落后，读延迟由写节奏决定 | 全部消费方被"写的人"拖慢 | 合并作业与业务任务分开排期、单独监控（4.2 多引擎一节的处置口径） | 把交互查询 P99 与写入速率画在同一张图上，看两条曲线是否同向尖峰 |
| 存在绕过表格式的就地覆盖式写入 | 依赖链判据失效（4.2「依赖按上游快照版本」的失效条件） | 把这些写入单独标记为欠账、封口（4.4 ②"留但封口"） | 找一个"始终不产生新快照"的数据集，看下游是被漏触发还是退回按时间空跑 |
| 元数据 / Catalog 成为新的单点 | 所有引擎都读不了——这是 lakehouse 区别于"文件堆"之处 | Catalog 高可用；把"谁有权改快照指针"写成唯一权威（4.1 Step 1） | 演练"唯一 Catalog 不可用"时读路径的降级 |

**关于跨地域容灾**：流式链路（Kafka → 有状态的 Flink）的状态恢复与 Checkpoint 到期确实构成一套真实的恢复能力，通用方法论见 [12-architecture/07-disaster-recovery](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md) 与 [06-chaos-engineering](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)；但本案例数据栈的"容灾"重心在**快照指针的唯一权威**上，不在多区域切换——把区域级 failover 套到表格式上是错配。**RTO / RPO 口径**：RPO 由"上一次成功提交的快照"决定（未提交的写入不进表），所以表格式把 RPO 从"文件粒度"收敛到"快照粒度"；流式侧 RTO 以 Checkpoint 间隔为下界【经验：两者都随 Checkpoint 间隔与提交频率变，本节不给数值】。演练在本案例里落地为 4.4 的"回退演练"——发现已经不需要回退，才算退出双轨。

### 4.8 演进路线：0 → 1 → 100

这条链的顺序不是时间表而是依赖顺序（4.1 总览），把它读成三阶段——每阶段标注：变贵的是什么、先坏的是什么。

**0 → 1（最小可用）**：只做 Step 1——把"表状态"的权威搬进一份元数据、定下唯一 Catalog，其余四步都挂在这份权威上。**变贵的是新增值班项**：元数据本身成为一批必须维护的文件，Compaction 与过期快照清理从"可选优化"变成有归属、有监控的排期项；**先坏的是合并作业没人负责**——问题会在第一次高频写入之后从读路径上冒出来（4.1 Step 1 已写明）。

**1 → 100（规模化）**：加装 Step 2–4——流批共用一份逻辑、依赖按上游快照版本判定、所有权登记到人。**变贵的是组织成本**：每个被跨团队消费的表要登记 Owner 与 SLA，跨团队争议要进常设治理机制；**先坏的是双轨变成长期态**——4.4 ③ 指出双轨的成本不在迁移期，而在它一旦稳定下来就没人负责收口，因此退出的信号要由**人工访问占比**归零触发，而不是总访问量。

**100 → 下一道坎**：Step 5 把 ML 平台与面向模型的只读投影接上（Metaflow、特征平台）。**变贵的是"同一份定义"的机器可读化**——训练与推理要指向同一份特征定义；**先坏的是训练 / 推理两份特征各自演化**：两侧不一致只在生产上暴露，发生时两边都以为自己读的是对的那份（4.1 Step 5 判据）。这一步正对应主文件 [§1.1](05-netflix-data-stack.md) 年表里 2019 起 Metaflow、2023 起 GenAI 的走向。

### 4.9 自检清单

- [ ] 随便挑 3 个作业，看它们的输入写的是表名还是分区路径？路径式作业的数量就是你的迁移欠账。
- [ ] 对同一张核心表问「加一列要重写多少数据」，答案是不是「零」？
- [ ] 最近一周这张表提交了多少次、产生了多少个清单文件？两个数同阶增长吗？
- [ ] 「未合并文件数」这个指标有人看吗？没人看，说明读延迟由写节奏决定。
- [ ] 同一个指标在实时看板与离线报表上，能不能指出它们来自同一份定义？比对作业报出的差异率是多少？
- [ ] 有没有下游任务在等「目录里出现文件」？把它列出来，这些就是会在上游重试时批次错配的任务。
- [ ] 「改这个字段会影响谁」现在要多久能回答？按天算，说明依赖还在人的记忆里。
- [ ] 血缘有没有覆盖流式链路？只覆盖批处理时，改了上游会漏掉全部实时下游。
- [ ] 血缘里解析不了的场景（动态 SQL、脚本任务）有没有被单独标记？盲区不可怕，「不知道有盲区」才可怕。
- [ ] 抽 5 张被多个下游引用的表，Owner 字段里是人名还是团队名？
- [ ] 上一次性能问题，最后是换引擎 / 调参数解决的，还是改表格式 / 提写入批量解决的？把结论写下来，一年后回看它猜对了几次。
- [ ] 迁移中的双轨，有没有一张差异看板在运行？没有看板的双轨会从过渡态变成长期态。

### 4.10 小结

> 本节小结：本主题下决定成败的唯一环节是 **Step 1 里那个「表状态的权威放在哪」的位置**——它不是性能优化，而是后面四步共同的落点：流批共享一张表依赖它、依赖按版本判定依赖它、血缘与影响面依赖它、面向模型的投影也依赖它。**把它放在最后一个做，前面所有工作都要返工一次；把它放对之后，其余四步都只是在这份权威上增加消费者与登记项。**
>
> 第二重要的是 Step 4 的登记粒度（Owner 到人）。它没有性能收益，因此最容易被跳过，而它失效的症状出现在一次跨团队变更事故里，与原因隔着很远。
>
> 💡 **思考锚点**：挑一张你现在被多个下游引用的核心表，问它两个数：Owner 字段里是人名还是团队名？加一列要重写多少数据——答案是不是「零」？如果 Owner 是团队名、加列还要重写，Step 1「表状态的权威放在哪」你算落定了吗？
