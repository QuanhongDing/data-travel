## 3. 架构演进

> 原 § 3 共 98 行：五代架构各一段年表与要点清单（V1.0 与 V3.0 各有一个箭头图），未展开约束、机制与失效条件，重写为约 305 行的架构模式手册。

### 3.1 先看约束：架构不是版本号的堆叠，是约束的产物

**先划清本节与相邻小节的分工**：主文件 § 1 给年表与团队规模，§ 2 给业务与技术挑战，§ 4 给每一次选型的决策依据（Iceberg、Keystone、Maestro、Spark/Flink、Metaflow、Data Mesh、实时数仓、ML Platform），§ 5 给踩过的坑，§ 6 给可复用经验。本节只回答一个问题：**这五代各自被哪条约束逼出来的**——不是「Netflix 依次做了这五件事」，而是「什么条件下只有这一条路可走」。

把架构史写成版本年表，最坏的后果是让人以为版本可以照顺序抄。**版本号不是路线图，是约束的刻度。** V2.0（把表状态交给一层可原子替换的元数据）之所以成立，前提是 V1.0 已经把「表状态只能靠列举对象存储目录推断」变成了组织级成本；没有这个前提，直接套一层表格式只会得到一份没人遵守的约定。同理，V4.0 的所有权改革之所以值得推动，前提是组织里已经出现「一个上游表被几十个下游任务依赖、改动无法通知到人」的场景；没有这个场景，联邦治理只是改个名字。

本案例有一条贯穿始终的约束值得先说：**数据的所有权分散在业务团队，而基础设施必须集中**。Netflix 的文化是「自由与责任」与工程师自治（主文件 § 1.3），但一个全公司共享的数据湖不可能让每个团队自行决定表格式与存储布局——**于是它把「集中」放在了协议层（表格式与 Catalog 规范），把「自治」留在了使用层（各团队自己建表、自己消费）**。这条约束解释了本案例的建设重心为什么始终落在开放表格式与自描述元数据上，而不是落在某个统一平台的功能清单上：**平台可以换，协议不能乱。**

还有一条规律值得先记住：**推动代际往前走的，从来不是数据量增长。** 本案例的五代里，「谁在用、他等在什么时间点上」的每次变化才是触发点——查询方从单一到多引擎（V2–V3）、消费方从中心团队扩展到业务团队（V4）、消费者从人扩展到模型（V5）。**数据量增长换的是存储与引擎，不是代际**；把吞吐问题当架构问题处理，会得到一次昂贵却没有解决原始问题的重构。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式（不可变对象追加 / 更新 / 事件流） | 表状态由谁定义、能否原子提交 | 「先把引擎换新」——S3 只提供对象追加，换引擎不产生事务语义 |
| 访问模式（批扫描 / 交互查询 / 在线点查） | 是否需要多引擎共读、要不要为查询单独建一层 | 「一个引擎通吃」——多引擎时代，读不到同一份表状态的代价是结论对不上 |
| 变更频率与历史要求（schema 演进、回溯） | 表格式的元数据层级与保留策略 | 「加列就是改元数据」——位置解析下加列会让历史文件读错 |
| 一致性要求（并发写、跨引擎可见性） | Catalog 的权威位置与提交协议 | 「读写锁在对象存储上也能做」——没有原子提交点，就只能靠约定 |
| 规模与成本约束（对象存储请求数、小文件数） | 目标文件大小、Compaction 与过期清理是不是常驻工作 | 「对象存储便宜」——请求次数、列举成本与合并工时才是账单主体 |
| 团队技能与运维能力（自治文化下的标准化程度） | 集中到什么层（协议 vs 平台） | 「自治就是不统一」——协议不统一时，自治会先变成互不可见 |

先给一张总览。它的第二列是本节的主线：**每一代真正改变的，都是「表状态的权威放在哪」**——后文每一代的失效点，几乎都能在这一列里找到位置。

| 代际 | 表状态的权威在哪 | 一次写入的表达方式 | 首要约束 |
| --- | --- | --- | --- |
| V1.0 传统数仓 | 分区目录与 Metastore 定义各一半 | 落一批文件到某个分区 | 只求能聚合出来看 |
| V2.0 开放表格式 | 元数据文件里的快照指针 | 原子替换快照指针 | 对象存储上没有事务 |
| V3.0 流批一体 | 同上（快照），但由两类引擎共同提交 | 流与批各自提交新快照 | 同一事实要供两个时效的消费方 |
| V4.0 调度 + 所有权 | 仍在快照；新增「谁拥有、谁依赖」的登记 | 由一个被平台承认的工作流驱动 | 依赖与责任超出团队可见范围 |
| V5.0 AI Native | 仍是快照与登记，但开始被模型消费 | 不新增写入方式，新增读取方 | 消费者从人扩展到模型 |

读这张总览时请把注意力放在「权威换了没有」：**从 V2.0 起，表状态的权威就再没有离开过元数据**——V3.0、V4.0、V5.0 增加的都是「谁能读到它、谁的名字写在它上面」，而不是「它存在哪里」。这条稳定性正是本案例可迁移的部分：**底座换一次要付大代价，所以底座要按最长寿命的那条约束来选。**

关于量级：本案例的日事件量只有一个可核锚点——2018 年的「数千亿条/日」【公开：Netflix Tech Blog, Keystone, 2018】。**本节因此不引用任何量级数字**——架构判断只需要「写入是批还是流、提交是整批还是持续」这两个定性答案，**量级数字在这里不增加信息量**。

#### 3.2.1 V1.0 传统数仓（2007–2015）

- **被什么约束逼出来**：这一阶段的需求只有「把数据聚合出来看」，消费者是单一的中心分析团队；而对象存储（S3）本身只提供不可变对象的追加与读取，不提供事务，能在它之上表达「一张表」的现成格式只有 Hive 表格式——**可选项本就只有一个。**
- **结构**：

```text
V1.0 传统数仓（2007–2015）
  [Oracle / MySQL] ──► [Hadoop + Hive] ──► [EMR] ──► [Tableau / 自研 BI]
  ─────────────────────────────────────────────
  表状态 = 分区目录（列举路径 = 知道表里有什么）
  表结构 = Metastore 里的那份定义，与数据文件分离：改它不校验历史数据
  一次写入 = 一批新文件落地（没有快照、没有提交点、没有列级统计）
```

- **为什么这样设计有效**：**因为表就是「一个目录 + 一份定义」，所以任何能读对象存储的引擎都能读它**——接入成本极低，且写入即追加、无需协调。在消费者只有一方、写入以整批覆盖为主的阶段，这是最省协调的形态，它买回来的东西是**普适性**，不是正确性。
- **代价**：ACID 缺失，并发读写不安全；Schema Evolution 只能靠重写数据（按位置解析时，历史文件加列即读错）；分区是物理目录，改分区方式等于重写整表；小文件与分区爆炸无法自愈；不支持时间旅行，历史版本只能靠快照目录人工保留。
- **失效点**：**当同一张表开始被多批任务并发读写、或分区字段需要变更时，本代「谁都能读、无需协调」的优点会反转成「正确性无法保证」**——**因为表状态没有原子提交点，任何一个读者都可能读到半次写入，而系统里没有任何信号能区分「这次读到的数据完不完整」**。它不会报错，只会给出一个看起来完整的错误结果。
- **真实使用**：本案例记录 2018 年以前 Netflix 使用 Hive 表格式，并列出上述四类问题（【经验：主文件 § 1.1 与 § 2.2.2】）。同时期的 Hive 表格式是行业通例，不是 Netflix 特有的选择。
- **自验方法**：拿一张核心表，问「上一次有人在它被写入时读它，读到的是什么」。答不出，说明你没有提交点这个概念。

#### 3.2.2 V2.0 S3 + Iceberg 立项（2015–2018）

- **被什么约束逼出来**：存储层已全面迁到对象存储，而对象存储不提供事务；同时表结构变更与小文件成为日常。**约束由此变成一个二选一：要么在对象存储之上自己造一层原子提交，要么永远放弃并发写与 schema 演进。**
- **结构**（表状态的权威是一棵可原子替换的元数据树，而不是目录列举结果）：

```sql
-- metadata/vN.metadata.json   ← schema + 分区规范 + 当前快照指针（提交 = 原子替换这一个文件）
--   └─ snap-*.avro            ← manifest list：这份快照引用了哪些 manifest
--        └─ *-m0.avro         ← manifest：每个数据文件的路径、分区、列级 min/max/null_count
--             └─ *.parquet    ← 不可变数据文件（写入只新增，从不原地修改）
CREATE TABLE lake.movies_events (
  user_id    BIGINT,
  title_id   BIGINT,
  event_time TIMESTAMP,
  device     STRING
) USING iceberg
PARTITIONED BY (days(event_time))               -- 隐藏分区：按时间过滤可下推，物理布局不必暴露
TBLPROPERTIES ('format-version' = '2');
-- 列演化按 field id 解析，不按位置：加列/删列不会让历史文件读错
```

- **为什么这样设计有效**：**因为数据文件不可变、每次提交只原子替换一个快照指针，所以读者在任一时刻只能看到一个完整快照**——并发写不会产生半可见状态，这就是 ACID 在对象存储上的落地方式；**因为 manifest 里带了列级 min/max 与 null 计数，所以规划阶段可以按统计剪裁文件**，剪裁能力与「分区是否被设计对」解耦，这也是「隐藏分区」能成立的原因——**分区从「用户必须写对的东西」变成了「引擎可以自己用的信息」**。
- **代价**：元数据本身就是一批必须维护的文件。高频小批提交持续产生 manifest 与 manifest list，Compaction 与过期快照清理成为常驻运维；分区演进要重写部分清单；多了一层「谁有权改指针」的问题，即 Catalog 的权威归属。
- **失效点**：**当写入批量很小而提交频率很高时，本代「提交只替换一个指针」的优点会反转成「元数据比数据增长得更快」**——**因为每次提交都新增一批清单文件，而规划一次查询要读的清单数随提交次数增长；清理如果落后于提交，规划成本会先于存储成本变成瓶颈**。此时要么提高单次写入批量，要么把 Compaction 与过期清理列为值班项而不是可选优化。
- **真实使用**：Iceberg 在 Netflix 内部立项，2018 年开源并捐赠给 Apache 软件基金会，2020 年毕业为顶级项目（【公开：Apache 软件基金会 Apache Iceberg 项目页，2018 开源 / 2020 毕业；当前状态以项目页内容为准】）。「2015 年全面拥抱 S3」「2016 年表格式选型」两条**只见于原 § 3 的 V2.0 年表**（【经验：原 § 3 年表】）——**本案例主文件 § 1.1 的 2015 条记的是「Apache Kafka 大规模使用」，且没有 2016 年条目**，按主文件逐条核对会核不到这两条；主文件 § 1.1 里与这一代对应的是「2017：Iceberg 立项，Ryan Blue 在 Netflix 内部开始研发」（【经验：主文件 § 1.1】），本节以该条为准。
- **与上一代的差别**：这一代没有新增任何「服务」，只**把表状态的权威从目录搬进了一个可以被原子替换的文件**。换来的不是速度，而是**「正确性第一次有了一个可以指认的位置」**——此后所有的并发写、结构演进与回溯能力，都是从这一个位置派生出来的。
- **自验方法**：数一下你这张表最近一周的提交次数与清单文件数。两者同阶增长时，问题不在引擎。

#### 3.2.3 V3.0 Iceberg + Spark + Flink（2018–2021）

- **被什么约束逼出来**：同一条业务事实要在两条链路里被计算（流用于低延迟、批用于全量与回溯），且查询方不再只有一个（Spark 批、Trino 交互式）。**约束是：不能让每个引擎读到的「表」是不同状态，也不能为流链路单独建一套存储。**
- **结构**：

```text
V3.0 流批一体（2018–2021）
  [Kafka] ──► [Flink] ──► [Iceberg 表] ──► [Spark / Trino] ──► [BI / ML]
   (事件)      (实时)      (表状态权威)      (批 + 交互查询)      (消费)
  ─────────────────────────────────────────────
  Flink 高频提交 → 产生小文件 → 后台 Compaction 合并 → 下一次提交指向合并后的快照
  关键：写者与读者不需要知道对方的存在，二者只共享「快照」这一个概念
        流与批的交接面不是文件布局，而是同一张表 + 同一份 Catalog
```

- **为什么这样设计有效**：**因为流与批都用「提交一个新快照」来表达一次写入，所以两条链路之间不必约定文件布局，只须约定表**——引擎换代不必连带换存储；**因为读者按快照读，所以「批任务正在跑」与「流任务在写」可以同时发生而不互相破坏**。流批一体的收益不来自某处参数调优，而来自「同一份存储同时承载两种语义」这个结构事实；**这一代能成立的前提是 V2.0 已经把表状态从目录里搬进了元数据。**
- **代价**：流写入天然产生大量小文件，Compaction 从「一次性任务」变成常驻工作；同一张表被两个引擎写时，提交冲突要有重试与隔离策略；对象存储的请求次数与列举成本随提交数增长，必须计入成本模型；团队必须理解「快照」这个概念，否则会写出绕过表格式直接操作文件的作业——而它们能跑通，直到某次并发提交把它们打乱。
- **失效点**：**当流写入频率长期高于 Compaction 的合并速度时，本代「批流共享一份表」的优点会反转成「读的人被写的人拖慢」**——**因为读路径要打开的清单与文件数由未合并的小文件决定，读放大随写入频率上升，而读者对此没有任何控制手段：他读的是同一份快照**。
- **真实使用**：Iceberg 于 2018 年开源（【公开：Apache 软件基金会 Apache Iceberg 项目页，2018；各版本的发布年份与版本号请以官方 release 页为准】）。原 § 3 的 V3.0 年表列了四条事件，本节按出处分开交代：**「2020 年内部数据栈全面基于 Iceberg」见本案例主文件 § 1.1 年表**（该处记作「2020：Iceberg 全面铺开——Netflix 内部 100% 数据栈基于 Iceberg」，【经验：主文件 § 1.1】）；**「2018 年 Iceberg 0.1.0 发布」「2019 年内部开始大规模使用」「2021 年 Iceberg 1.0 发布，Netflix 持续贡献」三条只见于原 § 3**——主文件 § 1.1 的 2018 条是「Apache Iceberg 开源」、2019 条是「Metaflow 升级」，按主文件都核不到这三条（【经验：原 § 3 年表】）。**本节因此不把这三条里的版本号写成公开事实**；Iceberg 各版本的发布年份与版本号，请以 Apache Iceberg 官方 release 记录为准。
- **与上一代的差别**：V2.0 换掉的是「表状态存在哪」，V3.0 换掉的是「**谁有权提交它**」——从单一写入者变成两类引擎共同提交。因此这一代的真问题不是「流能不能读批的表」，而是**提交冲突与合并由谁负责**；把这件事交给没人认领的后台任务，等于把 V2.0 好不容易建立的权威重新交给运气。
- **自验方法**：查一下「未合并文件数」这个指标有没有人看。没人看，就说明读路径的延迟是由写路径的节奏决定的，而不是由查询写的 SQL 决定的。

#### 3.2.4 V4.0 Maestro + Data Mesh（2021–2024）

- **被什么约束逼出来**：两个约束同时到界——**任务量与依赖关系超过了任一团队的可见范围**（依赖写在脚本与人的记忆里，重跑、回填与影响面分析都无处下手），**以及「这份数据归谁」无法被回答**（一个上游表被多个下游消费时，改动找不到对接人）。工作流与所有权都必须从「某个中心团队的记忆」里搬出来。
- **结构**：

```text
V4.0 调度与所有权的双层结构（2021–2024）
  调度层 [Maestro]：统一 DAG 模型 · 时间/事件/API 三类触发 · 可视化 · 一键回填
  所有权层 [Data Mesh]：每张表 = 数据产品（Owner + 文档 + SLA），平台不持有业务表
  ─────────────────────────────────────────────
  平台负责：DAG 模型与触发语义、回填语义、Catalog 与登记入口
  业务团队负责：表的所有权、口径、SLA
  两者唯一的交接面：一个被平台承认的工作流定义 + 一个被登记的 Owner
  反规则：Owner 登记成团队 = 没有 Owner（团队不接收通知，只有人接收）
```

- **为什么这样设计有效**：**因为所有工作流都用同一套 DAG 模型描述，依赖就从用户代码里被提取成了可查询的对象**——回填、重跑与影响面分析第一次能在模型上做，而不必在每个脚本里各做一遍；**因为 Owner 是显式登记的字段，所以「这份数据谁负责」从社交知识变成了可查属性**，跨团队改动有了固定对接人。两者是配套的：**只有统一调度而没有所有权，DAG 上每个节点都没人负责；只有所有权而没有统一调度，Owner 无法证明自己的表被谁依赖。**
- **代价**：调度层成为全公司共享组件，它的故障面等于全公司；自助意味着重复建设被合法化（各团队自己建模），平台只能用规范与评审约束质量，而规范收效更慢；联邦治理需要常设机制（委员会、评审流程），这是纯粹的管理开销，且不会随规模摊薄。
- **失效点**：**当 Owner 被登记成「团队」而不是「人」时，本代「改动有固定对接人」的优点会反转成「没有对接人」**——**因为通知只能送到人，登记粒度退化一级，影响面分析给出的对象就无法被触达；这个缺口不会报错，只会在某次改动后表现为「下游没人知道」**。
- **真实使用**：Maestro 由 Netflix 自研并开源（【公开：Netflix 工程博客, 2022；开源仓库与版本以官方仓库当前内容为准】）。**Netflix 内部推进 Data Mesh 实践**见本案例主文件 § 1.1 年表（该处记为 2022 年，【经验：主文件 § 1.1】）；而**「Iceberg REST Catalog 标准化」只见于原 § 3 的 V4.0 年表**（该处与「2023：Iceberg 1.3 发布」写在同一句，【经验：原 § 3 年表】）——主文件 § 1.1 没有这一条，本节不把它记成案例年表事实，REST Catalog 规范的版本与年份请以 Apache Iceberg 官方规范页当前版本为准。原 § 3 的 V4.0 年表另列「2024：Iceberg 2.0 发布，向量化读取优化」一条，与 1.3 同属「只有版本号、核不到公开出处」的条目，**本节同样不采用**，读者可按 Apache Iceberg 官方 release 记录自行核验。
- **与上一代的差别**：前三代动的是**数据面**（表状态、提交方式、合并），这一代第一次动**组织面**（谁拥有、谁依赖）。它不提升任何查询性能，却决定了前三代的成果能不能被安全改动——**性能问题解决「跑得快不快」，所有权问题解决「敢不敢改」**；后者决定变更的量级，前者只决定单次任务的时长。
- **自验方法**：随手挑一张被多个下游引用的表，读它的 Owner 字段。若答案是团队名，那么在「改动要通知谁」这一步上，你的体系与上一代没有区别。

#### 3.2.5 V5.0 AI Native 数据栈（2023–2025）

- **被什么约束逼出来**：**消费者从人扩展到了模型**。模型要选表、生成查询、判断字段能不能读，它依赖一份机器可读的语义资产；而前四代攒下来的资产（schema、列级统计、快照历史、Owner、血缘、指标定义）本来就是结构化的，只是此前只被人使用。**这一代的约束不在新建什么，而在已有资产的完备度。**
- **结构**：

```text
V5.0 AI Native（2023–2025）
  前几代已建成的结构化资产
    ├─ schema + 列级统计 ──► 回答「有什么、什么类型、怎么过滤」
    ├─ 快照与时间旅行   ──► 回答「这个结论基于哪个时间点的数据状态」
    ├─ Owner + SLA      ──► 回答「这个字段能不能用、出问题问谁」
    └─ 指标定义 + 血缘  ──► 回答「这个数怎么算的、改了会影响谁」
  出口一（面向人）：BI 与自助取数   —— V3.0 起已存在
  出口二（面向模型）：GenAI / Agent 取数 —— V5.0 新增的只是「投影层」
  ─────────────────────────────────────────────
  关键：新增的系统最少，对前几代资产完整度的要求最高
        模型区分不了「定义不存在」与「定义存在但没人维护」
```

**原 § 3 给这一代列了三条演进命题，本节全部沿用，并各补一句机制、代价与失效点**（三条属原稿对本案例走向的归纳，【经验】，不是可引用的行业事实）：

- **数据 → 知识**：把结构化数据（schema、列级统计、快照历史）经模型转成可检索的知识，而不只是可查询的表。**机制**：投影是只读的，元数据本来就为机器读而生，所以这条路径的边际成本最低；**代价**：知识必须能回答「基于哪一份快照」，否则同一问题在不同时间会得到互相矛盾的知识，投影与元数据的同步成为常驻工作；**失效点**：当元数据只有结构、没有业务含义时，这条路径会产出**形式正确、语义随模型先验漂浮**的知识，因为模型只能按列名与统计猜——越像知识的错误答案越难被识破。
- **指标 → Agent**：指标定义（口径、维度、血缘）不再只喂看板，而成为 Agent 可调用的工具集。**机制**：指标是把「怎么算」固化下来的产物，一旦成为工具，口径的每一次变更都会改变 Agent 的行为；**代价**：指标层从「一次计算」变成「被反复调用的接口」，容量规划、权限与灰度都要按接口而非按报表来做；**失效点**：当指标只有名字、没有可执行的硬定义时，Agent 会在两个名字相近的指标里挑一个最像的，因为工具集里没有能区分它们的依据——**这会把 V2.0–V4.0 阶段靠人兜住的「同名不同义」问题变成静默错误**。
- **Data Mesh → AI Mesh**：把 V4.0 的所有权登记从「数据产品归谁」扩展到「数据 + 模型 + 智能体归谁」，即联邦治理的对象新增两类非数据资产。**机制**：治理靠登记生效，登记对象扩展意味着同一套流程可以覆盖新资产，不必重建治理机制；**代价**：登记量与人员变动成本随登记对象数量上升，且模型的变更频率高于表，登记失效的速度更快；**失效点**：当 Owner 仍登记到团队（见 3.2.4 的失效点）时，AI Mesh 会把「通知不到人」原样复制到模型与智能体上，**且复制得更快——因为模型迭代比表结构变更频繁得多**。
- **为什么这样设计有效**：**因为表格式的元数据（schema、统计、快照）本身就是机器可读的，所以把它投影给模型消费的边际成本远低于新建一套 AI 数据栈**；**因为模型缺的从来不是查询能力，而是「哪个字段是权威的、这个指标怎么算、用了会影响谁」**——这三件事恰好是 V2.0–V4.0 留下的资产。**V5.0 的可行性由前几代的完成度决定，不由这一代的技术选型决定。**
- **代价**：需要一层投影，并保证投影与元数据同步，否则会出现「模型看到的定义已过期」；模型消费放大语义错误的后果——同一个错误定义被人看到是「一个看板错了」，被模型引用是「一批回答都错了」；权限模型也要重做，因为「给人看」与「给模型用」的授权边界不同。
- **失效点**：**当表和字段的业务含义长期没人补齐时，本代「资产可被模型消费」的优点会反转成「模型用列名与统计猜出一份看起来合理的答案」**——**因为模型无法区分「定义不存在」与「定义存在但没人维护」，两者在它的输入里都是空白，而空白会被它的先验填满**。此时应收窄自助取数范围，而不是换更强的模型。
- **真实使用**：本案例主文件 § 1.1 年表记：**2023 年内部广泛使用大模型并落地 GenAI 应用（内容理解 / 推荐 / 营销）**、2025 年探索实时数仓与 AI Native（【经验：主文件 § 1.1】）；该年表的 2024 条记的是「Iceberg 在规范层面引入删除向量、增量读取与 Variant 类型」，**不含 GenAI 应用**。**把内部 GenAI 应用记在 2024 年、并把应用清单记为「内容理解 / 营销文案 / 客服」的是原 § 3 的 V5.0 年表**（【经验：原 § 3 年表】）——与主文件相差一年，且应用清单不同，**本节以主文件 § 1.1 的 2023 年为准**，以免同一章的读者按两处核对得到两条互相矛盾的时间线。原 § 3 记的模型供应方为 OpenAI / Claude 一类服务（【经验】，本节不补具体版本与调用口径；读者可按产品名与年份自行检索核验）。
- **与上一代的差别**：这一代几乎不新增系统，只是**把已有资产换一类消费者**。所以它的风险面与前四代相反——**前四代的风险是「建不出来」，这一代的风险是「建出来的东西不完整，而模型不会告诉你它缺什么」**：人对缺失的元数据会去问人，模型只会给一个看起来合理的答案。
- **自验方法**：让一个不了解你数仓的人只靠元数据回答「我要算 X，该用哪张表、哪个字段、有什么影响」。答不出来时，缺的不是模型能力，是资产完备度。

**五代放在一起看，差别落在最后一列：**

| 代际 | 它解决的瓶颈 | 它引入的新成本 | 它成立的前提 |
| --- | --- | --- | --- |
| V1.0 传统数仓 | 「数据聚合不出来」 | 并发写不安全、schema 变更要重写、无回溯 | 消费者单一、写入以整批为主 |
| V2.0 S3 + 表格式 | 「对象存储上没有事务、表状态无处安放」 | 元数据自身成为要维护的一批文件 | 存储已迁到对象存储，且需要 schema 演进 |
| V3.0 流批一体 | 「同一份事实要在两条链路被算、还要能被多个引擎读」 | 小文件与 Compaction 成为常驻工作；提交冲突要隔离 | 表状态已由元数据定义 |
| V4.0 调度 + 所有权 | 「依赖与责任超出任一团队的可见范围」 | 共享调度 = 全公司故障面；联邦治理是常设开销 | 已有多个团队消费同一批表 |
| V5.0 AI Native | 「消费者变成了模型」 | 投影层与元数据的同步负担；错误被等比放大 | 前几代的资产完备度可度量 |

**读第三列的方式决定了这张表的用途**：每一代引入的新成本，正好是下一代要解决的问题——V2.0 的元数据维护成本逼出 V3.0 的共享快照语义，V3.0 的小文件与多引擎共读逼出 V4.0 对「谁负责、谁在依赖」的显式登记，V4.0 攒下的登记资产又成了 V5.0 的输入。**代际是叠加关系，不是替代关系：被换掉的只有引擎，被继承下来的是资产。**

### 3.3 代际选择决策表

这张表不回答「哪一代最好」，只回答**「你现在的约束把你放在哪一代」**。跨代不是不行，是要额外交学费——**而且学费不是在迁移时一次交清，它是在上游缺位时以「补丁」的形式陆续交。**

| 约束组合 | 对应的形态 | 为什么不跳到另一档 | 关键判据 |
| --- | --- | --- | --- |
| 消费方是单一分析团队、写入以整批覆盖为主 | V1.0 传统数仓形态即可 | 先别上表格式：没有并发写与 schema 演进的需求时，它买不回自己的运维成本 | 有没有两个任务同时写同一张表 |
| 存储已在对象存储、且需要 schema 演进与回溯 | V2.0 开放表格式 + 单一 Catalog | 先别上流链路：流链路会把小文件与提交冲突放大到读路径 | 「加一列要重写多少数据」能不能答成「零」 |
| 同一条事实要同时供给低延迟与全量回溯两方 | V3.0 批流共享同一张表 | 别用「为流链路单独建一套存储」代替：两套存储意味着两个口径 | 流与批是不是引用同一张表（不是同一份口径描述） |
| 多引擎共读同一批表，且引擎会各自换代 | V2.0 表格式 + V3.0 多引擎 | 别为每个引擎建一份副本：副本数即口径数 | 有几个引擎要以原生方式读同一张表 |
| 多个团队消费同一批表、改动通知不到人 | V4.0 统一调度 + 显式所有权 | 别只上调度：DAG 上每个节点仍没有人负责；也别只做所有权：Owner 无法证明被谁依赖 | Owner 字段里是团队名还是人名 |
| 数据消费者从人扩展到模型 | V5.0 语义资产的机器可读投影 | 别直接给模型开数据库连接：模型缺的是权威定义与边界，不是访问权限 | schema 与业务含义的覆盖率能不能报出一个数 |
| 只有吞吐与延迟在变，消费者与所有权结构没变 | 换引擎或换表格式，**不换代际** | 别把性能问题立项成架构改革：吞吐问题换存储，对齐问题才换代际 | 瓶颈在计算（换引擎）还是在「谁负责、有哪些下游」（换届） |

表里最常被误配的一对是 **V1.0/V2.0 的存储层与 V3.0 的引擎层**：**「批任务跑得慢」的第一反应通常是升级引擎版本或换计算框架**，因为它不需要说服任何人改变工作方式，且升级总是能做成的。实际后果是：**引擎换完了，小文件、清单堆积与并发提交冲突一个都没少**——因为这些问题出在表状态的组织方式上，不在计算框架上。判据只有一句：**慢的是「算得久」还是「要打开的文件多」**。后者要用表格式与合并解决，前者才用引擎。

第二常被误配的一对是 **V2.0（表格式）与 V4.0（所有权改革）**：数据「找不到、对不上」时，最容易立项的方案是数据所有权改革，因为它是组织层面的动作，看起来更彻底。但它解决的从来不是「这张表是什么、有哪些下游」这类元数据问题——**把所有权改完再回来补元数据，顺序反了：没有可查的血缘，Owner 依然无法回答「改这张表会影响谁」**。

第三对是 **V3.0（流链路）与 V1.0/V2.0（表状态尚未定义）**：把「数据要更新得更快」与「数据要能被多处一致地读」混成一件事。**流链路解决的是产出时延，不解决并发可见性**——在表状态还由目录定义的形态上直接加流式写入，你会同时得到两个新问题（快照不存在、小文件没人合并），而原始的时效需求只被满足了一半。

把这三对合起来，就是这张表的用法：**先定位你被哪条约束支配（并发写 / 结构演进 / 多引擎共读 / 依赖与责任 / 消费者身份），再检查那一档的前提是否具备，最后才决定要不要跨代。** 跨代本身不贵，贵的是跳过前提——**跳过前提的跨代不是提前投入，是把下一代的成本预支到了这一代。**

### 3.4 组合模式：真实系统不会只用一种

1. **开放表格式 + 多引擎分工**——**构成**：表格式负责「表是什么」（V2.0），Spark 承接批加工与合并，Flink 承接流式写入，Trino 一类引擎承接交互查询（V3.0）。**职责边界**：表格式定义表状态与提交语义，引擎只负责读写与合并，**引擎换代不重建资产**。**运维代价**：多引擎共读意味着读取权限、资源隔离与版本兼容矩阵都要有人维护；合并任务的调度优先级要与业务任务分开，否则高峰期会被挤压。**适合规模**：表数进入千级、且查询方不再只有一个引擎时。
2. **统一调度 + 所有权分散**——**构成**：调度层（Maestro）提供统一的 DAG 模型与触发、回填语义；所有权层（Data Mesh）把表的所有权、口径与 SLA 交给业务团队，平台保持基础设施而不持有业务表。**职责边界**：平台负责「怎么跑、怎么重跑、谁在依赖谁」，业务团队负责「算什么、什么时候必须出」。**运维代价**：共享调度的故障面是全公司，必须有独立的可用性目标；自助带来的重复建设无法靠集中建设消除，只能靠规范与评审约束。**适合规模**：消费方跨越多个团队、且依赖关系已超出单人记忆范围（本案例主文件 § 2.3 记有 30+ 团队共享数据的场景）。
3. **表格式 + ML 平台**——**构成**：表格式提供可回溯、可演进的训练数据来源；ML 平台（本案例的 Metaflow，主文件 § 4.1 Step 5 / § 4.3）负责流程与实验管理。**职责边界**：数据侧保证「同一批特征在训练与推理时取自同一份定义」，平台侧保证「这一步用了什么代码、什么参数可复现」。**运维代价**：训练-推理一致性是新的故障源——同一批特征在训练与推理两侧一旦走了不同的取值路径（依赖版本、特征口径、时间窗口任一处不一致），就会出现「离线指标好、线上效果差」这类只在生产暴露的偏差（【经验】，本节不锁定任何具体比例）；**本案例主文件 § 5 记录的是另外五类坑**（Hive 元数据爆炸、Iceberg 破坏性升级、S3 一致性、Metaflow 学习曲线、Data Mesh 推进缓慢），其中与 ML 平台直接相关的是 **§ 5.4 的 Metaflow 推广阻力**，不含训练-推理一致性这一条。特征的定义与表的 schema 必须同步演进。**适合规模**：模型上线频率进入周级之后。

三个组合共有的前提是**表状态有一个唯一权威**：多引擎、调度层与 ML 平台都只是这份权威的不同消费者，**权威一旦分叉，组合的收益立刻变成一致性成本**。

把三个组合放在一起，可以看出它们各自把「变化」关在哪一层：

| 组合 | 谁承担稳定 | 谁承担变化 | 组合的失效方式 |
| --- | --- | --- | --- |
| 表格式 + 多引擎 | 表状态与提交语义（协议层） | 每个引擎的版本与实现 | 各引擎实现进度不一，出现「这个引擎读得到、那个读不到」；或 Catalog 出现第二份指针 |
| 统一调度 + 所有权分散 | 交接面：工作流定义 + Owner 登记 | 各团队的表、口径与建模方式 | 交接面缺一项（工作流没登记、Owner 是团队名），组合退化为「各跑各的」 |
| 表格式 + ML 平台 | 数据的定义与可回溯性 | 模型、特征与实验流程 | 特征定义与表 schema 各改各的，训练与推理取自不同的那份定义 |

这张表要传达的只有一句：**组合模式的前提是「变化被限制在某一层」，一旦变化同时发生在两层，组合就退化成耦合。** 本案例的每一代升级也都尽量只动一层——V2.0 动存储层、V3.0 动计算层、V4.0 动组织层，**没有一次是把表格式、引擎与所有权同时换掉**。这不是保守：组合模式的收益正来自「其他层不用动」，同时动两层，收益就消失了。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **把目录列举当表状态**（原 § 3 记的「S3 上没有事务保证」） | 有人在作业里直接读/写某个分区路径；表中出现「正在写入的半批数据」 | 没有原子提交点，读者可能看到半次写入，且系统不报错——错误以「数据看起来对」的形式流入下游 | 目录就是最直观的「表」；在单写入者阶段这个直觉一直是对的 | 表状态交给可原子替换的元数据；把所有「直接操作文件路径」的作业列为待迁移清单 |
| **用位置解析代替字段解析**（原 § 3 记的 Hive「Schema Evolution」问题，主文件 § 2.2.2 记作「不灵活」） | 加列/删列要先重写历史数据；某个下游读旧分区时报类型错 | 位置与字段一旦脱钩，历史文件在结构变更后读出错误的列，错误静默传播 | 早期格式按位置存，改起来最省事；成本要等到第一次结构变更才显性化 | 让文件带上自己的 schema 标识（按字段 id 解析）；新表一律不允许位置解析 |
| **只换引擎不换表格式**（原 § 3 记的「Spark 1.x 性能不佳」） | 引擎升级完，作业仍然慢；慢的作业共同点是「要打开的文件特别多」 | 规划与读取成本由文件与清单数量决定，与计算框架无关——换引擎不触及成本来源 | 升级引擎是一次可独立交付、且一定能做成的动作；改表格式要动全链路 | 先分清是「算得久」还是「要打开的文件多」；后者做合并与提高写入批量 |
| **把分区当手工参数**（原 § 3 把「分区演进」列为 Iceberg 的一项创新能力） | 分区字段由业务约定写死；查询忘记带分区条件即全表扫 | 分区一旦写死，改分区方式等于重写数据；分区与查询模式脱钩后，过滤下推失效 | 物理目录时代分区就是路径的一部分，习惯被继承了下来 | 用隐藏分区让分区成为引擎可用的信息，而不是用户必须写对的东西 |
| **版本堆叠而不退役**（本书对该演进的归纳，【经验】） | 新版表与旧版表同时在写；同一个指标有两条产出通路 | 只要旧通路仍在产出，新表就不是唯一权威，一致性无法论证 | 关停旧路径要承担业务中断风险，建设新路径没有这个风险 | 每次上新同时给出旧路径的退役计划与截止时间，退役列为验收项 |
| **所有权登记到团队**（本书对该演进的归纳，【经验】） | 表的 Owner 字段是团队名；下游通知发到群里无人认领 | 通知只能触达人，团队名使影响面分析的结果无法被送达——缺口不报错，只在下游静默失效时暴露 | 团队名比人名稳定，登记时不用维护人员变动 | Owner 具体到人，并在人员变动时触发重新登记 |

**最危险的一个是「把目录列举当表状态」**，因为它在很长时间里看不出问题：单写入者、整批覆盖的形态下，目录列举与快照读取给出同样的结果，团队甚至会认为快照层是多余的抽象。它的暴露方式是**一次并发写**——某个下游在批任务运行期间取数，拿到一个内部一致、外部残缺的结果，然后基于它做了一天的决策。这类事故不会留下异常日志，只会留下一个事后无法复现的错误数字。

**第二个是「只换引擎不换表格式」**，因为它的成本是**以重复投入的形式分期支付**的：每次性能问题都换一次引擎，每次换完都要重新调参、重新压测，而瓶颈原地不动。它的典型暴露方式是性能评审：当被问到「这次慢的具体是哪个环节」时，答案是「扫描量大」，而没有人能说出「未合并文件数」这个数是多少。

**第三个是「所有权登记到团队」**，它的危险在于**症状与原因距离极远**：登记粒度的问题会以「下游没接到通知」的形式出现在一次变更事故里，而复盘时看到的却是「流程执行不到位」。**只要 Owner 字段里是团队名，任何影响面分析的结果都无法被送达**——修一个人名，比加十条流程有效。

这六条的差别还在于**暴露延迟**，而暴露延迟决定了哪一种最容易被长期低估：

| 反模式 | 暴露延迟 | 暴露形态 | 为什么会被低估 |
| --- | --- | --- | --- |
| 把目录列举当表状态 | 数周到数月【经验】 | 一次并发写后出现内部一致、外部残缺的结果 | 单写入者阶段完全无症状，快照层看起来像多余的抽象 |
| 用位置解析代替字段解析 | 一次结构变更之后 | 历史分区读出错误的列，静默传播 | 首次结构变更之前，它是零成本的 |
| 只换引擎不换表格式 | 每次性能问题都暴露一次 | 升级—调参—压测的循环，瓶颈不动 | 每次升级都确实「做成了」，只是没解决问题 |
| 把分区当手工参数 | 查询忘记带条件的那一天 | 单次查询成本失控（全表扫） | 归因为「SQL 写错了」，而不是分区是手工参数 |
| 版本堆叠而不退役 | 数月到数年【经验】 | 新旧通路结果不一致，且都自称权威 | 关停旧通路的风险落在当下，收益落在以后 |
| 所有权登记到团队 | 一次变更事故之后 | 下游没接到通知，复盘时看起来像执行问题 | 登记团队名在当时更省事，且短期没有任何代价 |

**这六条反模式共享同一个走向**：它们都把「正确性」寄托在**约定与自觉**上（约定不并发写、约定改结构前通知、约定记得带分区条件），而不是寄托在**结构**上（原子提交点、字段 id 解析、显式到人的所有权）。**约定的问题是它没有回报机制：遵守约定的人得不到好处，违反约定的人在很久以后才付成本。**

### 3.6 规模跃迁时形态何时该换

| 跃迁 | 原形态 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单写入者 → 多任务并发读写 | 目录即表（V1.0） | 没有原子提交点，读者可能看到半次写入 | 元数据定义表状态 + 快照（V2.0） | 需要重建写入链路与 Catalog；存量数据的元数据要生成，期间新旧并存 |
| 表结构变更从「罕见」变成「每周」 | 位置解析 + 重写历史 | 每次加列都要重写全量，变更成本与数据量成正比 | 字段 id 解析 + schema 演进 | 存量文件要带上 schema 信息；下游解析逻辑需迁移 |
| 单个批量作业 → 分钟级持续写入 | 批写 + 一次性合并 | 小文件与清单堆积进入读路径，读放大随写入频率上升 | 流式写入 + 常驻 Compaction（V3.0） | 合并从任务变成服务：要有人负责它的调度、监控与容量，且它与业务任务争资源 |
| 查询方从 1 个引擎 → 多个引擎 | 单引擎自有格式与目录 | 各引擎读到不同表状态，结论对不上 | 开放表格式 + 唯一 Catalog | 需选定唯一权威 Catalog；迁移期要处理两套指针并存的读一致问题 |
| 消费方从单一团队 → 多个团队 | 依赖写在脚本与人的记忆里 | 改动无法通知到下游，回填与重跑无人能算清影响面 | 统一调度 + 到人的所有权（V4.0） | 组织改造先于技术改造：需要常设治理机制，且收益要等依赖被登记完才出现 |
| 消费者从人 → 人 + 模型 | 面向人的表与看板 | 模型读不到「哪个字段权威、怎么算、用了影响谁」 | 语义资产的可读投影（V5.0） | 需要业务含义补齐与权限重划；错误后果从「一个看板错」放大为「一批回答错」 |

**读这张表的顺序是「谁在用 → 他要多久 → 有多少数据」，不是反过来。** 前三行的触发点是并发模式与写入频率，第四、五行的触发点是消费方数量，**只有第二行的「变更成本与数据量成正比」是随规模线性增长的**——而它换的是表格式的实现方式，不是架构代际。

还有一条判断纪律：**先确认「疼」是不是由约束变化引起的，再决定换代。** 同样是「任务变慢」，可能是并发写多了（换表状态定义）、写入变碎了（加常驻合并）、多引擎共读互相拖累（统一 Catalog）、或依赖太乱导致频繁返工（换调度与所有权）——四者的解法完全不同，而**换错的代价通常大于晚换**：晚换只是继续疼，换错则是把疼换成了「旧问题还在、新系统还要维护」。

**迁移里有两项是近乎不可逆的，要在切换前想清楚**：一是**表状态的权威一旦分叉**（两套 Catalog、两条写入通路并存），回退要比前进更贵，因为它意味着要说服两拨人各放弃一次已经上线的东西；二是**所有权登记的粒度一旦被定成团队**，后续再收到人需要逐个补登记，而这件事没有自动化路径——**它的成本与表数量成正比，且必须在下一次变更事故之前完成**。因此迁移的方向应当是**先收紧表状态与登记的最小结构，再谈规模与消费面的扩张**；反过来做，会把两件事的难度叠加。

**最后一条纪律与时间有关**：本案例相邻两代的间隔都在两年及以上（V2.0 → V3.0 约三年、V3.0 → V4.0 约三年、V4.0 → V5.0 约两年，【推算：按 3.2 各代年份区间的起点两两相减；这五段区间取自**原 § 3 各代标题**的划分（本案例主文件 § 1.1 的年表按事件逐年分档、不含区间），区间本身不是可对外引用的公开事实】），**这不是因为它走得慢，而是因为「上一代的成果被普遍用起来」本身就是一件需要数年的事**。缩短节奏的前提不是更强的团队，而是**你已经有办法度量上一代的成果被用到了什么程度**（例如：有多少作业通过表而不是路径读写、有多少表有具体到人的 Owner）。

### 3.7 自检清单

下面 12 条按「表状态 → 引擎与存储 → 调度与所有权 → 消费面」的顺序排列，对应 3.2 每一代的失效点与 3.5 的六条反模式。

- [ ] 有没有作业直接读写分区路径（而不是通过表）？把它们列出来，这份清单就是你的迁移欠账。
- [ ] 一次结构变更（加列 / 改类型）需要重写多少数据？如果答案不是「零」，说明表状态还是路径式的。
- [ ] 「未合并文件数」这个指标有人看吗？没人看，说明读延迟由写入节奏决定，而不是由查询决定。
- [ ] 上一次性能问题，最后是换引擎解决的还是改表格式解决的？把结论写下来，一年后回看它猜对了几次。
- [ ] 有几个引擎要以原生方式读同一张表？它们的 Catalog 是同一个吗？
- [ ] 同一张表里有数据正在被流任务写入、同时被批任务读取吗？如果有，它们读的是同一份快照语义吗？
- [ ] 挑一张被多个下游引用的表，Owner 字段里写的是人名还是团队名？
- [ ] 「改这张表会影响谁」现在要多久能回答？按天算，说明依赖还在人的记忆里。
- [ ] 有没有新版表与旧版表同时在写、同一个指标有两条产出通路？旧通路有没有退役截止时间？
- [ ] 如果明天要让一个模型自助取数，它能读到「哪个字段是权威的、这个指标怎么算、用了影响谁」吗？
- [ ] 你能用一句话说清「这套架构为什么长这样」吗——它被哪条约束逼出来的？答不出来，说明前面这些条目你只是在维护现状，不是在演进架构。
- [ ] 让一位刚入职的同学只靠元数据独立完成一次取数，并说出这次取数的影响面。他卡在哪一步，你的资产就缺在哪一步。

### 3.8 小结

| 你的约束 | 建议形态 | 关键理由（机制层面） |
| --- | --- | --- |
| 消费者单一、写入以整批覆盖为主 | V1.0 形态即可 | 没有并发写与结构变更时，表格式买不回它的运维成本 |
| 存储已在对象存储、需要结构演进与回溯 | V2.0 开放表格式 + 唯一 Catalog | 表状态必须有一个可原子替换的权威，否则并发写不成立 |
| 同一事实要同时供给低延迟与全量回溯 | V3.0 批流共享同一张表 | 提交快照这一个概念，让两条链路不必约定文件布局 |
| 多引擎共读、且引擎会各自换代 | 表格式与引擎分离 | 引擎换代不应重建资产；资产在协议层才留得住 |
| 多团队消费、改动通知不到人 | V4.0 统一调度 + 到人的所有权 | 依赖与责任必须先成为可查对象，才谈得上协调 |
| 消费者扩展到模型 | V5.0 语义资产的可读投影 | 模型缺的是权威定义与边界，不是查询能力或连接权限 |

> 本节小结：这五代不是路线图，而是**「表状态的权威放在哪」这条约束依次被推到极限的刻度**——先是对象存储上没有权威（V1.0），把它搬进元数据（V2.0），再让两条链路与多个引擎共享同一份权威（V3.0），随后把「谁拥有、谁依赖」也变成可查的登记（V4.0），最后把这份登记投影给模型（V5.0）。**决定你该走到哪一代的那条约束是「谁在消费这批数据、他等在什么时间点上」**；数据量增长换的是存储与引擎，不换代际。

把本节压成三句可执行的话：**第一，先查表状态有没有唯一权威**——所有并发写、结构演进与多引擎一致性问题都从这一条派生。**第二，换引擎与换表格式是两个预算项**——把它们混在一个项目里，结果是引擎换完了，瓶颈还在原地。**第三，任何一代的成果都要能回答「有几份」**——同一张表有几条产出通路、同一个口径有几份实现；答案只要不是「一份」，你就在欠账。

最后一条属于本案例的特殊性，需要读者自行判断可迁移性：**这条路径是十八年时间逐步长出来的**（【经验：本案例主文件 § 1.1 年表，2007–2025】），每一代都建立在上一代的成果上。**缩短时间跨度走同一条路，风险不在做不出来，而在跳过「上一代把问题变成组织共识」的过程**——没有经历过并发写事故的组织，通常不会为表状态的原子提交付成本；那份成本也就不会被任何人认领。

**如果只从本节拿走一个问题，那就是它**：**你这批数据「表状态的权威」写在哪个文件、哪条记录里，谁有权改它？** 这个问题回答不了的时候，讨论引擎、表格式与调度都是空的——因为无论选哪一个，都没人说得清当前这一份是什么状态。本案例的五代，本质上是在回答同一个问题的五个不同答案。
