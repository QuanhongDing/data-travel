## 7. 与同类案例对比

### 7.1 先解决「可比性」

横向比较海外案例最容易犯的错误，是**把差异归给能力**：Databricks 的 AI 能力更强、Snowflake 的数据共享更成熟、Anthropic 更重视安全、OpenAI 的模型更强。这些说法在各自公开材料里都能找到依据，却几乎没有决策价值——因为读者无法判断「我能不能也做到」，也无法判断「做不到是我的问题还是约束不同」。

真实差异的第一来源是**约束不同**。Databricks 从 Spark 生态里长出来，它的 SQL 引擎是后来补的；Snowflake 从零开始，没有历史包袱，所以它敢把存储做成专有格式；Netflix 是单一业务线的消费者，它不需要卖平台，所以把表格式开源是纯收益；Anthropic 与 OpenAI 的资产是模型而不是数据，所以它们做数据侧的路径只能是「定义接口」而不是「托管数据」。**把这些约束先摆出来，一半的「能力差距」会还原成「处境差距」。**

第二个常被忽略的问题是：这几个案例讲的其实**不是同一件事**。Databricks 与 Snowflake 在讲「用什么形态交付分析能力」，Google BigQuery 与 AWS 托管数仓在讲「把运维这件事消除掉」，Netflix 在讲「把内部解决的表格式问题变成行业规范」，Microsoft 在讲「多引擎如何共用一份存储」，Anthropic 与 OpenAI 在讲「模型如何接入外部数据与工具」。**跨问题域的排名因此没有意义**——把估值、营收、客户数并列，排出来的是问题域之间的差异，而不是做法之间的差异。本章的做法是：**不排跨问题域的名次，只挑对全部 8 个案例同义定义的机制轴**（统一发生在哪一层、成本函数长什么样、数据与模型的边界画在哪、开放还是锁定）来横向切开（见 7.2）。一条机制轴对每个案例问的是同一个问题，所以它的结论可以在任意问题域里指同一件事。

第三个问题是排序的诱惑。本章的立场是：**只给「在什么约束下该学谁」，不给「谁更好」**。任何一句脱离了约束条件的结论，在读者的组织里都会变成一句误导。

| 案例 | 规模量级 | 业务形态 | 监管强度 | 组织形态 | 存量约束 | 时间窗 |
| --- | --- | --- | --- | --- | --- | --- |
| Databricks | 万级企业客户【经验】 | 数据平台 SaaS | 中 | 单一产品线 + 平台团队 | 从 Spark 生态长出，SQL 引擎后补 | 2013 年成立【公开】；Lakehouse 形态 2020 年前后【推算】 |
| Snowflake | 万级企业客户【经验】 | 云数仓 SaaS | 中 | 单一产品线 | 从零建，无历史包袱 | 2012 年成立【公开】；2020 年上市【公开】 |
| Google BigQuery | 云客户 + 内部【经验】 | 全托管分析服务 | 中 | 服务型团队 | 从内部大规模并行查询系统长出 | 2010 年论文【公开】；2011–2012 产品化【公开】 |
| AWS 托管数仓 | 云客户【经验】 | 托管分析服务 | 中 | 服务型团队 | 继承已有 MPP 引擎血统 | 2012–2013 产品化【公开】；托管存储与加速形态 2019 起【推算】 |
| Netflix | 3 亿级付费会员【公开】 | 内容 + 推荐 | 中 | 领域自治 + 中央平台 | 存量是 Hive 表，不能停机迁移 | Iceberg 2018 开源【公开】 |
| Microsoft 统一工作区 | 云客户【经验】 | 统一分析工作区 | 中 | 服务型团队 | 从既有 SQL 系引擎与内部引擎长出 | 2015 起（Azure SQL DW）→ 2020（Synapse）→ 2023（Fabric）【公开】 |
| Anthropic | 模型公司 | 模型 + API + 企业版 | 高（AI 安全 + 企业合规） | 研究驱动 | 从零建，训练栈自建 | 2021 年成立【公开】 |
| OpenAI | 模型公司 | 模型 + API + 订阅 | 高 | 研究驱动 | 从零建 | 2015 年成立【公开】 |

**两列的证据依据**（前表「时间窗」列的同口径说明，避免用「精确到年、无公开出处」的形式）：规模量级列除 Netflix 外均为【经验】（由各家的客户数量级与业务形态估得，无单一公开数字），Netflix 会员数为【公开】（[Netflix Q4 2024 财报]）。时间窗列逐条列依据，**凡公开材料只能给出区间的，不写成精确年份**：

- **Databricks**：2013 年成立是公开事实；但「Lakehouse 2017 起」在公开材料中找不到对应节点——Delta Lake 于 2019 年开源（[Databricks 公开公告, 2019]），湖仓形态的论文与叙事出现在 2020 年前后，故写为区间的【推算】：2019 开源 → 2020 前后形态定型。
- **Snowflake**：2012 年成立、2020 年上市，均为公开事实【公开】。
- **Google BigQuery**：Dremel 论文 2010 年发表，产品化为 2011–2012 年【公开】。
- **AWS 托管数仓**：2012–2013 年产品化【公开】；面向托管的存储与服务侧自动优化形态出现于 2019 年前后【推算】（由 AWS 公开产品发布节奏推得，不取更早的年份）。
- **Netflix**：Iceberg 于 2018 年由 Netflix 开源，2020 年成为 Apache 顶级项目（[Apache Software Foundation, 2020]）【公开】。
- **Microsoft**：统一分析形态公开可考的节点是 Azure SQL Data Warehouse（2015–2016）→ Azure Synapse Analytics（2020）→ Microsoft Fabric（2023）【公开】；**不取更早的年份**——这三个发布可分别在各产品的公开公告中自行核验，再往前的「统一工作区」形态找不到对应的发布节点。
- **Anthropic / OpenAI**：分别成立于 2021 年与 2015 年，为公开事实【公开】。

从这张表里能读出三件事。第一，**时间窗普遍在十年量级**——表中没有一家是在三年内完成形态定型的，这意味着任何以「一年内做完」为目标的照抄计划都不现实；它们的结论可以学，进度不能抄。第二，**监管强度普遍是「中」而不是「高」**（两家模型公司除外），也就是说这些案例的差异并不来自合规压力——把「海外公司合规更严所以架构更先进」当成解释，是找错了变量。第三，**存量约束的差异极大**：Snowflake 从零建所以敢用专有格式，Netflix 有不能停机迁移的 Hive 存量所以只能从格式层切入——同一个技术选择在不同存量下，一边是直觉，一边是唯一解。

把约束摆出来之后的第二个问题是**判据**：不是说「约束不同」，比较就没意义了；而是要把比较限定在「约束相近的部分」里。本章用下面 4 条判据筛选出可迁移的结论。

| 判据 | 问的问题 | 为什么它决定了能否照搬 |
| --- | --- | --- |
| 约束可比性 | 我与它在规模、监管、存量栈、组织形态上差在哪一条 | 差异若来自约束，照搬做法必然失效，且失效原因会被误读成「执行不力」 |
| 动作可比性 | 它做的是**定义权**、**平台能力**，还是**格式 / 协议** | 三类动作的迁移成本差一个量级：改组织 > 改平台 > 改格式 |
| 时间窗可比性 | 它在这个问题上投入了多久 | 一个十年工程的结论不能当一年计划用；最容易被误读的就是「它做成了」四个字 |
| 证据可比性 | 结论来自官方材料、财报、工程博客，还是二手转述 | 没有来源的结论无法在自家环境里预先验证，只能等踩坑 |

### 7.2 各案例的结构性差异（核心节）

这一节按 4 个维度拆解差异。每个维度都遵循同一个写法：先说清差异是什么，再看各自的做法，再解释**这个差异由什么约束导致**，然后给公开证据，最后说清对读者的意义。凡是无法归因到约束的差异，本章一律不写——因为那样的差异无法被读者判断。

四个维度分别是：

1. **统一发生在哪一层**（引擎 / 存储 / 规范 / 接口）——决定能力边界与商业边界；
2. **成本函数长什么样**（按容量 / 按扫描量 / 按资源 / 按 token）——决定谁有优化动力；
3. **数据与模型的边界画在哪**（谁朝谁走）——决定竞争还是互补；
4. **开放还是锁定**（收益函数是固定还是随采用者增长）——决定长期成本结构。

#### 7.2.1 统一的到底是什么：引擎、存储、规范，还是接口

**机制一句话**：你消除的「重复」发生在哪一层，你对那一层的依赖就有多深。

**差异是什么**：每家平台都在消除某种「重复」，但消除的对象不同——统一的层级决定了它的能力边界与商业边界。

**各自的做法**：

| 案例 | 统一的对象 | 未统一的部分 | 由此产生的边界 |
| --- | --- | --- | --- |
| Snowflake | 引擎 + 存储（专有） | 外部引擎 | 数据共享能做到不复制，但跨出边界要导出 |
| Databricks | 开放文件格式 + 表格式（Delta Lake） | 自有引擎仍是主要入口 | 存储不被绑定，但治理面留在产品内 |
| Google BigQuery | 由服务侧统一，用户不可见 | — | 门槛降到「会写查询」，代价是完全托管 |
| Microsoft 统一工作区 | 存储层 | 引擎（多种并存） | 多引擎共享一份数据，权限跨引擎生效 |
| Netflix Iceberg | 规范层 | 不提供引擎 | 收益随采用者增长，自家不直接获利 |

把这几家的「统一层级」排成一条轴，会看到一条清晰的权衡：**接口 < 规范 < 存储 < 引擎**。层级越低，跨边界越容易、被锁定越浅，但消除的重复也越少——统一接口只能让两套系统对话，统一引擎才能把两套系统变成一套。层级越高，收益越直接（更少的组件、更好的性能、更简单的运维面），但边界越硬：统一引擎意味着你的数据、权限、作业定义全部长在这个引擎的语义上，换引擎就不再是「换一个读取方」，而是重建整个工作流。**这条轴是本章所有分歧的源头。**

**这个差异由什么约束导致**：因为 Snowflake 的存储是自研的微分区格式，所以它的跨组织共享可以做到「消费者直接读生产者的存储、不复制数据」——这是它的差异化能力，也意味着统一范围等于商业边界。反过来，因为 Netflix 不靠卖数据平台赚钱，所以它把表格式做成开放规范是纯收益（降低自家适配成本 + 换取生态位）；而 Databricks 处在两者之间：它需要格式开放来避免客户被锁定，又需要治理面留在产品里来保住商业价值。

**公开证据**：Iceberg 于 2018 年由 Netflix 开源，2018 年 11 月进入 Apache 孵化器，2020 年 5 月成为 Apache 顶级项目（[Apache Software Foundation, 2020]）；Delta Lake 于 2019 年由 Databricks 开源（[Databricks 公开公告, 2019]）；Snowflake 在 2023-2024 年推出 Iceberg Tables 支持（[Snowflake 公开材料, 2024]；该年份本书内两处口径不一，以 Snowflake 官方发布说明为准）——「专有统一」的代价被自己承认，是这条机制最直接的证据。

**对读者的意义**：当你的分析全部发生在一种引擎、一个云、一份存储里时，专有统一优于开放统一（更少的胶水、更好的性能）；一旦出现「第二种引擎」或「跨组织分享」，开放层（格式 / 协议）就是唯一能不动数据就换引擎的那一层，此时应优先统一格式而不是统一引擎。

**失效条件**：当所有分析都发生在单一引擎、单一组织内，且短期内不会出现第二种引擎时，「统一在哪一层」这个差异不产生决策影响——此时最高层的统一（统一引擎 + 专有存储）反而是最省事的，硬套开放格式只会增加一层不必要的抽象和对齐成本。判断信号是：未来 18 个月内是否会引入第二个计算引擎【经验】（时间尺度取自组织引入新引擎通常要走的选型、立项与迁移周期，无单一公开来源）。不会，就不必为开放层付费。

#### 7.2.2 商业模式决定了优化目标：卖容量、卖用量，还是卖 token

**机制一句话**：计费单位就是这套系统里唯一被所有人认真优化的那个指标。

**差异是什么**：计费方式不是商务细节，它决定了平台会去优化什么，也决定了用户的优化动力有多强。

**各自的做法**：

| 案例 | 计费依据 | 平台被激励去优化什么 | 用户被激励去优化什么 |
| --- | --- | --- | --- |
| Snowflake | 计算时间（信用点）+ 存储 | 缩短运行时间、提高并发复用 | 减少无效计算、合并小任务 |
| Google BigQuery | 扫描的数据量（按需） | 减少扫描量（裁剪、下推、物化） | 写更省扫描量的 SQL、做分区 |
| Databricks | 计算资源单元 + 云资源 | 减少运行时间与节点数 | 依赖平台提供的自动优化 |
| Anthropic / OpenAI | token 数（输入 / 输出） | 减少 token 消耗（缓存、批处理） | 压缩上下文、复用前缀 |

换一个角度看同一个差异：这四种计费方式对应四种不同的**成本函数形状**。按扫描量计费时，成本 ≈ f（查了什么，与查了多久无关），因此「少扫」是唯一杠杆；按计算时间计费时，成本 ≈ f（跑了多久 × 集群多大），杠杆在缩短运行时间与并发复用上；按计算资源计费时，成本 ≈ f（用了多少资源 × 用了多久），杠杆在利用率与自动优化上；按 token 计费时，成本 ≈ f（输入长度 + 输出长度），杠杆在缓存命中与上下文压缩上。**选型时真正要盯的不是单价，而是「这条成本函数的自变量是不是我能控制的」**——如果自变量不受你控制，你无法通过努力降本，只能通过议价。

**这个差异由什么约束导致**：因为 BigQuery 按扫描量计费，所以「列裁剪 + 分区裁剪 + 谓词下推」对用户而言是钱包问题而不是最佳实践问题，采用率天然高；因为按计算资源计费的形态下「写得省」不直接省钱，所以平台必须把优化做成默认行为（自动统计维护、实测校正、自动整理小文件），否则用户没有动力做。「优化动力的归属」是这两种模式最本质的差别。

**公开证据**：BigQuery 按需计费以扫描量为计价单位（Google Cloud 公开定价页的 BigQuery 按需计费条目，可由读者自行核验）；Anthropic 在 2024 年推出 prompt caching 并公开其定价结构（[Anthropic 公开发布, 2024]）；OpenAI 在 2024 年推出 Batch API 并公开其折扣口径（[OpenAI 公开发布, 2024]）。三者都是「把计费单位变成优化单位」的实例。

**对读者的意义**：选型时要问的不是「单价多少」，而是「我优化之后，省下来的东西会不会体现在账单上」。如果客户签的是包年容量，用量与成本的耦合被切断，优化动力会随之消失——此时平台侧的自动优化能力就变成了唯一的优化来源。

**失效条件**：当平台不以用量为收入来源时（自建平台、内部数据中台、包年容量合同），计费对优化动力的驱动作用消失。替代机制是 SLO 与成本分摊（把资源消耗折算到业务方头上）——**没有账单压力时，必须有人造一个等价的压力，否则资源浪费不会被自发纠正**。这是内部平台把「成本可见」当成一等功能来做的原因。

#### 7.2.3 数据与模型的边界：谁向上走、谁向下走

**机制一句话**：谁掌握数据的所有权，谁就有权决定「模型过来」还是「数据过去」。

**差异是什么**：数据平台向上做 AI，模型公司向下做工具——两者必然相遇，相遇点在哪一层，决定了竞争还是互补。

**各自的做法**：

| 案例 | 路径 | 做法 | 相遇点 |
| --- | --- | --- | --- |
| Databricks | 数据 → AI | 从湖仓到模型生命周期、特征、训练平台的纵向打通 | 把模型拉到数据旁边 |
| Snowflake | 数据 → AI | 在库内提供 AI 函数，不自己训基础模型 | 数据不动、能力进来 |
| Anthropic | 模型 → 数据侧 | 定义工具与上下文接口（协议 + 参考实现） | 接口层 |
| OpenAI | 模型 → 数据侧 | 工具调用、Agent 框架、订阅式产品 | 接口层 + 应用层 |

把「模型搬到数据旁边」和「数据搬到模型旁边」当成两条成本曲线会看得更清楚：前者的成本主要是**算力与部署**（在数据所在的区域、权限体系与网络边界内运行模型），后者的成本主要是**数据移动与合规**（复制或外发数据），而且外发的往往正是最敏感的那部分。因为强合规行业里客户的敏感数据几乎不可能被允许外发，所以「把模型搬到数据旁边」在那里不是优化选项而是唯一可行路径——**这解释了为什么数据平台侧的 AI 能力往往先在金融、医疗这类行业落地，而模型侧的 API 化能力先在通用场景落地**【经验】（由强合规行业普遍不允许敏感数据外发这一行业实践推得，无单一公开来源）。

**这个差异由什么约束导致**：因为 Databricks 的商业资产是「客户的数据落在它的存储上」，所以它做 AI 的路径必然是把模型能力搬到数据旁边（模型朝数据走），而不是把数据搬进模型；因为 Anthropic 与 OpenAI 的商业资产是模型而不是数据，所以它们做数据侧的路径必然是定义接口（数据朝模型走）。**一旦模型公司开始托管客户数据，它就会同时与云厂商和数据平台正面竞争——这解释了为什么它们停在接口层。**

**公开证据**：MCP（Model Context Protocol）由 Anthropic 在 2024 年 11 月开源（[Anthropic 公开公告, 2024]）；OpenAI 在 2025 年 3 月宣布在其智能体开发套件中支持 MCP（[OpenAI 公开公告, 2025]）——**一个模型厂商采纳另一个模型厂商的协议，是「竞争发生在模型层、协作发生在接口层」最直接的证据**。Snowflake Cortex 在 2023 年公布、2024 年陆续可用（[Snowflake 公开材料, 2023-2024]），是「数据侧不动、能力进来」的实例。

**对读者的意义**：如果你的组织拥有独占数据，走 Databricks 路线（把能力搬进来）更安全，因为差异化在数据；如果你的差异化在模型与产品体验，走接口路线（把数据接出去）成本更低——但要把「接口标准由谁定义」当成一项长期风险来管理。

**失效条件**：接口层的「中立」是有前提的——模型公司不碰客户数据。当模型能力趋于商品化、而客户数据成为唯一差异化来源时，模型公司向下走的动机上升，这一前提会被削弱。**实践上的对冲方式是：关键集成保持两条可替换的实现（协议实现 + 直连实现），把「换一家」的迁移成本压在配置层。**

#### 7.2.4 开放与锁定：把能力开源出去，还是留在产品里

**机制一句话**：开放的收益函数随采用者数量增长，专有的收益函数与产品边界同宽。

**差异是什么**：把内部能力做成开放格式 / 协议，还是做成产品能力——决定的是收益函数的形状：固定，还是随采用者数量增长。

**各自的做法**：

| 案例 | 开放的对象 | 保留的对象 | 收益结构 |
| --- | --- | --- | --- |
| Netflix | 表格式规范 + 参考实现 | 无（不商业化） | 随采用者增长 |
| Databricks | 表格式 / 文件格式 | 治理、运行平台 | 格式收益增长，产品收益固定 |
| Snowflake | 有限（后期支持开放表格式） | 数据共享层 | 由产品边界决定 |
| Anthropic | 工具与上下文协议 | 模型 | 协议采用越多，模型可接入面越大 |
| OpenAI | 早期为 API 特性（函数调用），2025 年起支持外部协议（[OpenAI 公开公告, 2025]） | 模型与产品 | 同上 |

把「开放」当成一次性动作是常见误解。开放是**持续投入**：规范要维护、参考实现要跟进、向后兼容要守住、社区提案要评审。因此判断一项能力该不该开放，不能只问「开放有没有好处」，要同时问「我愿不愿意为它持续付这份成本」。**只开放、不维护的项目，会在两三年内变成一个没人敢用的半成品**【经验】（时间尺度取自社区项目在维护投入不足后活跃度衰减的普遍观察，无单一公开来源）——它既没有产品的稳定性，也没有规范的权威性。

**这个差异由什么约束导致**：因为 Netflix 的收益不来自卖平台，所以开放规范的边际成本（规范维护、社区协作）远低于它换回的适配成本下降与生态位；因为 Snowflake 的收益直接来自产品边界内的功能，所以把共享层留在产品里是理性的——但它必须为此承担「跨出边界要导出」的用户成本，这也是它后来支持开放表格式的原因。**开放不是一个道德选择，是收益函数形状的选择。**

**公开证据**：Iceberg 进入 Apache 顶级项目（[Apache Software Foundation, 2020]）与 Delta Lake 开源（[Databricks 公开公告, 2019]）是数据侧的两例；MCP 被另一家模型厂商采纳（[OpenAI 公开公告, 2025]）是 AI 侧的一例。

**对读者的意义**：只有当「你解决的问题是行业共性问题」且「采用者越多你的成本越低」同时成立时，开放才是划算的；否则规范维护与社区协作就是净成本。

**失效条件**：当开放规范的演进方向与你的需求分叉——你的定制需求排在社区路线之后，而你又不是主要贡献者——「等」会变成真实成本。判定方法是看两件事：你在该项目中的投入占比，以及你需要的下一项能力是否已进入公开路线。两项都不利时，正确的做法不是退出开放，而是**在开放格式之上维护一层自己的可插拔扩展**，而不是分叉规范。

### 7.3 可迁移 vs 不可迁移

案例对比最有价值的部分不是「他们做了什么」，而是「哪一部分的结构性做法可以搬走」。

搬得走的是**机制性做法**：显存占用是算出来的不是经验值，所以状态分片是机制结论；格式是唯一不动数据就能换引擎的层，所以先统一格式是机制结论；门槛下移能扩大用户群体，是机制结论。这些结论不依赖规模与组织，换个团队照样成立。

搬不走的是**处境性做法**：自研引擎、专有存储共享、自研训练栈，它们全都依赖「作者本人就是最大使用者」或「组织已经积累了十年」这一前提。把它们当成方法论抄走，得到的通常是一份维护成本极高、收益极低的仿制品。

| 做法 | 可迁移？ | 为什么 | 迁移的前提条件 |
| --- | :---: | --- | --- |
| 统一存储层而非统一引擎 | 是 | 多引擎的差异来自计算模式，不来自数据放在哪；统一存储保留强项又消除副本 | 存储使用开放列式格式；有跨引擎的统一权限 |
| 把门槛从「会运维」降到「会查询」 | 是 | 用户群体扩大的价值远大于省下的人力，且业务侧的分析需求通常远未被释放 | 平台侧已自动化容量、统计、故障处理 |
| 按实际使用量计费 | 是 | 优化收益能同时体现为「更快」与「更省」，用户才有优化动力 | 计量准确且粒度可解释 |
| 用真实执行数据校正计划估算 | 部分 | 机制成立，但需要足够的历史执行样本；小规模场景样本不足 | 有可回归的历史执行记录；学习只用于代价估算、不改语义 |
| 把内部能力做成开放格式 / 协议 | 是 | 收益函数从固定变为随采用者增长，同时降低自家适配成本 | 问题确实是行业共性；有参考实现与向后兼容承诺 |
| 数据共享做到「不复制」 | 否 | 依赖专有存储格式的内部机制（消费者直读生产者存储） | 仅在单一厂商的统一引擎内成立 |
| 自研 OLAP 引擎 | 否 | 已有的自研引擎出自「作者本人就是最大使用者」的组织 | 你是该场景的最大用户且场景足够特殊 |
| 自研训练栈 | 否 | 依赖模型规模与卡数摊薄通信开销，且模型路线变化频繁 | 有稳定的大规模训练需求与专门团队 |
| 参数 / 梯度 / 优化器状态全分片 | 是 | 显存占用是算出来的，不是经验值；这是机制性结论 | 卡数足够多，使通信不成为新瓶颈 |
| 领域自治 + 中央只做基础设施 | 部分 | 需要领域团队具备数据工程能力，且规范被执行 | 业务线单一、实体边界清晰 |
| 用协议替代 SDK | 是 | 协议可被第三方重新实现，SDK 不能——**能被重新实现是生态的前提** | 协议有参考实现且承诺向后兼容 |
| 以「实验」而非「经验」作为决策依据 | 部分 | 机制成立，但依赖样本量与指标口径统一；小样本与长周期效果会给出错误结论 | 有足够流量、统一指标、能计算显著性 |

表里「部分可迁移」的那几行最容易被误读成「可以照搬」。它们的共同点是：**机制成立，但成立条件依赖你的处境**——样本量够不够、团队能力够不够、业务形态是否匹配。读这一列的正确方式是把它当成「迁移前提条件」清单逐条核对，而不是当成难度等级。

第二个【推算】说明「按扫描量计费 → 建表设计直接等于账单」这条机制：一份按天分区的事实表每天新增约 500 GB，宽表 30 列而某类查询只用到 3 列。只命中单分区并做列裁剪时，扫描量约 500 GB × 3/30 = 50 GB；按每 TB 扫描约 $6.25 的按需单价（Google Cloud 公开定价页的 BigQuery 按需计费条目，可自行核验）推算，单次查询成本从约 $3.1 降到约 $0.31，相差一个量级（推导：0.4883 TB × $6.25 ≈ $3.05；0.0488 TB × $6.25 ≈ $0.31）。**结论不是「要优化」，而是「这类优化不需要靠规范推动」——因为收益直接落在用的人身上。**

第三个【推算】说明「格式中立」真正买到的是什么：假设 1 PB 数据以某个引擎的专有格式存放，换引擎需要重写全部数据。按对象存储标准层约 $0.023/GB-月（单价可在厂商公开定价页自行核验）推算，1 PB 单独一份的月成本约 2.4 万美元（推导：1,048,576 GB × $0.023 ≈ $24,117/月），重写期间两份共存只额外多出这一笔。**这笔钱并不吓人；真正吓人的是重写期间两条链路必须同时正确，以及切换窗口内一旦出错就要回滚整个数据集。** 这才是「格式中立」值钱的地方——它买到的是可逆性，不是存储费。

### 7.5 决策树（我该学谁）

下面这棵树的分支条件全是**约束**（合规强度、存量技术栈、团队能力、商业化诉求），不是偏好。约束不满足时，照搬做法不会得到同样的结果。

```
你的处境里，哪一条约束最硬？
        │
        ├─ 合规 / 数据主权约束强（数据不能出境、必须能自证删除）
        │       ├─ 买 → 学 Microsoft 路线：统一存储层 + 权限跨引擎统一定义
        │       └─ 自建 → 先统一元数据与权限，再谈统一引擎
        │
        ├─ 存量技术栈是 Hive / 自研 MPP（有历史包袱）
        │       └─ 学 Netflix：先统一「表格式」这一层，不要先换引擎
        │              （格式是唯一「不动数据就能换引擎」的层）
        │
        ├─ 从零开始
        │       ├─ 团队 < 20 人、无内核专家 → 学 BigQuery 路线：
        │       │      把门槛从「会运维数仓」降到「会写查询」
        │       └─ 团队有内核能力、且成本主导项是数据量 → 自建 + 开放格式
        │
        ├─ 你的能力会被外部消费（有客户、有生态）
        │       └─ 学 Anthropic：把接口做成开放协议
        │              （接口层的收益随采用者数量增长）
        │
        └─ 你的能力只服务内部
                └─ 学 Databricks：把统一留在自己的边界内，
                        但至少让存储格式保持开放
```

**阈值依据**：

- **「团队 < 20 人」**：托管形态消除的是容量规划、分区与索引设计、故障处理这三类专家工作；在自建形态下，这几类工作通常需要若干人专职投入【经验】。当团队规模不足以长期供养这类岗位时，自建的边际成本会持续高于使用托管服务。
- **「格式是唯一不动数据就能换引擎的层」**：表格式把「表」定义为数据文件清单加元数据，数据文件本身是开放列式格式，任何实现了该规范的引擎都能读（[Apache Iceberg 规范, 2024]）。因此换引擎时不需要重写数据，只需要换读取方——这与换引擎同时换存储格式的成本差一个量级。
- **「能力会被外部消费」**：判断依据是「是否存在第三方（客户、合作伙伴、其他团队）需要调用你的能力」。存在则协议层的投入有回报，不存在则规范维护是净成本。
- **「成本主导项是数据量」**：由成本函数判断——当存储与扫描成本在总成本中占比持续高于计算资源成本时，自建 + 开放格式的收益才成立；否则托管形态的自动化收益更大。
- **「合规强度高」**：判断依据是「是否存在要求数据不出境、或要求能按主体删除数据的外部约束」。有则权限与删除能力必须先于性能优化建设；因为删除权要求「能找到某主体的全部数据」，而这依赖元数据与血缘的完整度，与查询引擎的选择无关。
- **「存量技术栈是 Hive / 自研 MPP」与「从零开始」**：这一对是**二值约束**而不是程度问题——表由外部系统（Hive Metastore / 自研元数据服务）定义时，换引擎必然要同时换数据定义，所以有存量时先动格式层；从零开始时不存在这一层约束，直接选引擎即可。判断方法是问一句「我的表定义现在由谁持有」：答案不在引擎里，就先统一格式；答案已经在新引擎里，就不必为格式层单独付一次迁移。
- **「团队有内核能力」**：不看团队人数，看两件事——是否有人维护过自研引擎或格式的生产实例，以及是否有面向内核的调优经验（执行计划、存储布局、资源隔离）。两者都没有时，自建的真实成本通常被低估【经验】。
- **「数据能否出境 / 能否按主体删除」**：这是**二值约束**而不是程度问题。不能出境，就意味着必须做区域化部署与本地元数据；能按主体删除，就意味着必须能按主体找到它的全部数据。这类约束只问一次，不需要量化。

决策树上的每个节点都对应一条约束，而不是一个偏好。**把决策树当偏好清单用（「我想要更强 AI 能力 → 学 Databricks」）会失效，因为约束不匹配时，做法搬过去也不会产生同样的结果。**

### 7.6 各案例的失败面

案例对比里最有用的部分不是「它做对了什么」，而是「它为做对这件事付出了什么」。下面三条都是有公开痕迹可查的代价——**照搬一个案例而不照搬它的代价，是照搬失败最常见的方式**。

- **Snowflake 的代价：为了「不复制即可共享」，把存储做成了专有格式**
  - 它换到了什么：最强的跨组织共享体验——消费者直接读生产者的存储，不需要复制。
  - 什么条件下反噬：当客户的多引擎需求（Spark 上做 ML、Flink 上做流）超过纯 SQL 时，副本要么落回客户自己的存储、要么必须走出产品边界。
  - 公开痕迹：它在 2024 年推出对开放表格式的支持（[Snowflake 公开材料, 2024]），说明「专有统一」的代价已被自己承认。
  - 正确做法：如果分析注定是单引擎，这笔代价不必付；如果两三年内会出现第二个引擎，从一开始就让存储格式保持开放。

- **Databricks 的代价：为了「数据与 AI 一体化」，同时维护三条产品线**
  - 它换到了什么：最完整的能力面——客户从数据到模型不必换平台。
  - 什么条件下反噬：团队只需要一个 SQL 数仓时，这份完整度会变成学习成本与运维面；**功能的边际价值随实际使用比例下降而迅速衰减**。
  - 公开痕迹：SQL 引擎、Spark 运行时、模型生命周期与训练栈在公开材料中长期并列存在。
  - 正确做法：以「我实际会用到哪几件」而不是「它一共有多少件」来评估一体化平台。

- **模型公司（Anthropic / OpenAI）的代价：为了「不拥有客户数据」，把数据侧的价值让了出去**
  - 它换到了什么：最干净的合规叙事（数据不用于训练、企业版可隔离），因此更容易进入强合规客户。
  - 什么条件下反噬：模型能力被追平、价格战压缩毛利时，可依赖的差异化只剩模型能力、价格与协议生态位。
  - 公开痕迹：把接口做成开放协议并被竞争对手采纳（[OpenAI 公开公告, 2025]）——这既是影响力，也是「不掌握数据侧」的补偿动作。
  - 正确做法：站在模型侧，要把协议生态位当成核心资产经营；站在数据侧，不要把「接哪一家模型」写死在一处。

### 7.7 选型矩阵

| 你的处境 | 最该参考 | 最该避免照搬 | 理由 |
| --- | --- | --- | --- |
| 多引擎并存、副本漂移严重 | Microsoft 统一工作区 | 试图用一个引擎覆盖所有场景 | 统一存储层可行，统一引擎会在某类场景上全面落后 |
| 数据量是主要成本、团队无内核专家 | BigQuery 托管路线 | 自建 MPP 集群 | 托管把门槛降一个层级，自建的专家成本摊不平 |
| 有多云 / 跨组织数据交换需求 | Netflix 的表格式路线 | 把共享做成产品内能力 | 格式是跨边界唯一不需要重写数据的一层 |
| 数据是核心竞争力、要打通数据与模型 | Databricks 路线 | 把数据复制到模型侧 | 把模型搬到数据旁边，才能保留数据侧的差异化 |
| 差异化在模型与产品体验 | Anthropic 的协议路线 | 自建数据托管平台 | 托管数据会与云厂商和数据平台直接竞争 |
| 合规与权限是硬约束 | Microsoft 的统一身份与权限 | 每个引擎各配一套权限 | 多引擎下「谁能看什么」必须能一次性回答 |

上表的每一行都隐含一个**组合**，而不是一个单品选择。三种在实践中稳定成立的组合是：

1. **「开放列式格式 + 多引擎 + 统一权限」**
   - 职责边界：格式负责可迁移，各引擎负责自己擅长的计算模式，权限层负责合规。
   - 代价：权限层成为新的关键路径——它一旦不可用，所有引擎都读不了数据，因此权限服务的可用性要求高于任一引擎。
   - 适合：已经出现或即将出现第二种引擎的组织。
2. **「托管分析服务 + 对象存储 + 按用量计费」**
   - 职责边界：服务商负责容量、调优与弹性，用户只负责建表与写查询。
   - 代价：成本随使用量增长而增长，必须配用量监控与配额，否则账单会在无人察觉时翻倍。
   - 适合：团队里没有内核专家、而分析需求尚未释放的阶段。
3. **「自有引擎 + 开放格式 + 治理产品」**
   - 职责边界：引擎与治理由自己掌握，格式对外开放以避免锁定。
   - 代价：治理面与运行平台要同时维护，产品复杂度会传导到使用者的学习成本上。
   - 适合：数据本身是核心资产、且有能力长期投入的组织。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（结构性差异层面） |
| --- | --- | --- |
| 只有一种引擎、一个云 | 用托管形态，接受专有统一 | 专有统一胶水更少、性能更好 |
| 出现第二种引擎 | 优先统一存储格式，而不是统一引擎 | 格式层不动数据即可换引擎 |
| 成本主导项是数据量 | 用「统一存储 + 分层 + 按量计费」组合 | 让优化收益落在账单上，用户才有动力 |
| 能力会被第三方消费 | 把接口做成开放协议 | 收益函数随采用者数量增长 |
| 数据是核心资产 | 自建 + 开放格式，能力向内收 | 差异化在数据，不在引擎 |
| 团队规模不足以养内核专家 | 托管 + 自动优化 | 专家成本无法摊薄 |

> 本节小结：这 8 个案例讲的是五件不同的事，跨问题域排名排不出东西；但在它们共同回答的四条机制轴上，**唯一真正起决定作用的一条是「统一发生在哪一层」**——引擎、存储、规范还是接口。统一层次越低（接口 < 规范 < 存储 < 引擎），越不容易被锁定、越容易跨边界，但消除的重复也越少；层次越高，收益越直接，边界越硬。Databricks、Snowflake、Microsoft、Google 四家的路线差异，以及 Netflix 与两家模型公司的开放选择，都可以由这一条推出。**商业模型决定了它们愿意统一在哪一层，而你的处境决定了你该学哪一个。**
>
> 💡 **思考锚点**：先问一句「我的表定义现在由谁持有」——答案不在引擎里，就先统一格式层；已经在新引擎里，就不必为格式层再付一次迁移。再把它对到四层统一（引擎 / 存储 / 规范 / 接口）：你打算统一在哪一层，而这一层买到的可逆性值不值那份「重写期两条链路同时正确」的代价？
