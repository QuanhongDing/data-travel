## 4. 关键决策

§3 把这些公司还原成"被约束逼出来的范式"，回答的是**它们为什么长成这样**。本节回答另一个问题：**如果你要照搬其中一条，怎么把这条决策落到自己的组织与存量系统上** —— 按什么顺序拍板、每一步做到什么程度算数、手上应该多出什么、已有的仓库与报表怎么办、以及在什么条件下这个决策会失效。

本节把 §3 的八个范式收敛成五个需要拍的板：**统一层选在格式层还是引擎层（4.2 第 1 条）**、**跨组织共享用不用副本（第 2 条）**、**资金类状态用不用追加型账本（第 3 条）**、**合规把哪些数据划出可用集合（第 4 条）**、**模型怎么接工具（第 5 条）**。4.1 与 4.2 是两类读者共用的：从零起步的团队照着顺序走，存量改造的团队把每一步的"判据"当作补账的检查项读（第一步换成"给已有资产标不可逆项"）。4.3 给候选与选型判据，4.4 专门写给存量迁移，4.5 是可直接套用的模板。

先定一条纪律：本节所有的选型结论都必须能追溯到一个**约束**。说不出"我是在哪条约束下选它的"，等于把一个产品自带的假设当成了自己的需求——这是照搬案例最常见、也最难在半年内发现的失败方式。

### 4.1 落地步骤

**Step 1：约束盘点，把"不可逆项"标出来（【经验】1–2 周，随已有架构文档的完整度变化）**

把四条约束逐条写成明文：**存量栈**（从零建还是从既有生态长出）、**引擎数量**（现在几个、两三年内会变成几个）、**成本函数**（按容量买、按扫描量买、还是按 token 买）、**合规强度**（哪些数据不能用于训练、能不能跨边界）。然后在这张表上圈出**不可逆项**：分片键、账本的表结构、是否采用专有存储格式、共享边界、评测集与训练语料的隔离点——这几类东西改起来的代价与"重做一遍"同阶。

- **产物**：一张约束表（每格写"这条约束在我的环境里是否存在"）+ 不可逆项清单。
- **判据**：拿最近一次已经完成的技术选型复盘一遍：结论能不能反推出"当时哪条约束是决定性的"。推不出来的选型，说明当时比的是功能清单而不是约束。
- **为什么必须第一步、且不能与选型合并**：因为候选的价值完全由约束决定。同一个 Lakehouse，在"会出现第二引擎"的环境里是省下迁移成本，在"三年内只有一种计算形态"的环境里只是多买了一份治理面要自己补的复杂度。

**Step 2：候选收敛到 2–3 个，按约束淘汰而不是按功能打分（【经验】2–4 周）**

- 用 §3.3 的决策表把候选按"统一发生在哪一层"归类：格式层、引擎与存储层、账本与记录层、接口与协议层。
- 同时写一份**明确不用的能力清单**：这一列的条数，比候选总功能数更能预测上线后的实际使用比例。
- 淘汰理由必须写成"某条约束在我的环境里不成立"，而不是"它的功能少"。

- **产物**：候选对照表（每格写"在什么约束下选它"）+ 不用清单 + 淘汰记录。
- **判据**：表里每一行都能指向 Step 1 的一条约束；再抽一条淘汰记录，问"如果这条约束反过来，结论会不会变"——不会变说明那次淘汰没有依据。
- **为什么必须第二步**：候选收敛是唯一能在**采购与写代码之前**完成的动作。进了试点之后再换候选，代价就从"改一张表"变成"已写的代码 + 已培训的人 + 已迁的数据"。

**Step 3：可逆性分级，先做能退回来的部分（【经验】2–6 周试点，随存量规模变化）**

- 把 Step 1 的不可逆项排到最后再定；先做能回退的动作：只读镜像、旁路查询（同一个查询在两个平台上跑，比结果）、只读共享交换。
- 试点只回答事实问题：结果是否一致、延迟与账单落在哪个量级、兼容性缺口在哪。
- 每个动作都要有回退路径与回退时长。

- **产物**：可回退动作清单 + 试点结果（两个平台的差异清单，含"差异是口径还是实现"的判定）。
- **判据**：每个动作都能回答"如果明天不要了，怎么退、退多久、影响谁"；答不出的动作不许进试点。差异清单里每一条都要被判为"可解释"或"必须在迁移前解决"。
- **为什么必须第三步、且在迁移之前**：迁移是单向的。先用可回退的动作把事实测出来，再动不可逆项——顺序颠倒时，你会在已经复制完数据之后才发现口径差异。

**Step 4：存量迁移与双轨（【经验】6–24 个月，随存量规模与新旧口径的差异面变化）**

见 §4.4。这里只记它在本流程里的位置：它必须在不可逆项定案之后、在决策留痕之前完成主体部分——因为它会产出"这个决策的真实代价"，而这个代价是复审触发条件的一部分。

- **产物**：资产分类清单、业务键与代理键的映射、三级对账报表。
- **判据**：§4.4 的四条退出信号，缺一条就不退双轨。
- **为什么必须排在 Step 5 之前**：双轨期会产生大量"临时"做法，而判断"什么时候可以停"必须靠一组事先写死的判据，不能靠当时的感受。

**Step 5：决策留痕与复审触发条件（【经验】1–3 天，但它决定这个决策三年后还能不能被解释）**

- 写一份决策记录：约束、候选、淘汰理由、接受的代价、不可逆项、**复审触发条件**、责任人。
- 复审触发条件要写成可观测的事件，例如"出现第二种计算引擎""计费方式从按容量改为按扫描量""某类数据被要求不得跨边界""租户间数据量差距超过某个比例"——这些都能被监控，而"业务发展了"不能。

- **产物**：签字的决策记录（含触发条件与责任人）。
- **判据**：抽任意一条已签字的决策，能否独立回答两个问题——当时哪条约束是决定性的；这笔代价被记在了哪里。答不出的记录记的是结论，不是决策。
- **为什么必须最后**：因为依据里包含试点结果与迁移代价，这两样在 Step 3、Step 4 之前都还不存在。

**最常被跳过的是 Step 1 与 Step 5 的"复审触发条件"。** 两个都不产出系统，都进不了进度表。跳过 Step 1 的症状不会在选型当天出现，而是在两年后：约束变了（出现了第二种引擎、计费方式改了），但没人知道当初的结论建立在哪条约束上，于是按"再买个新平台"解决，重复付一次迁移成本。跳过触发条件的症状更晚：三年后没人能说清"当初为什么选它、什么情况下该换"，决策只能靠重新论证一遍——而重新论证的最常见结局是照着最新宣传语再选一次。

**同一个步骤表，两类读者的起手式不同：**

| 你的处境 | 第一步具体做什么 | 最该避免的起手式 |
| --- | --- | --- |
| 从零搭建（没有存量栈） | 从 Step 1 起走；约束表与候选对照表可以在一两周内做完，因为没有历史包袱 | 跳过 Step 1 直接按"功能最全"选平台——约束少不等于没有约束 |
| 存量改造（已有一套在用） | 先做 Step 1 的变体：给已有资产标出不可逆项；再对**最活跃的少数几张表**补登记，一周内见效 | 先规划一张三年后的目标架构图，两年内不产出任何可验证的动作 |

### 4.2 关键技术点

**统一层：格式层还是引擎与存储层**

- **做法**：先回答"统一发生在哪一层"，再选产品。格式层统一 = 表被定义为**数据文件 + 追加写的事务日志**，任何引擎实现"读日志"即可读；引擎与存储层统一 = 客户不直接寻址文件，由服务层管理存储、事务与优化；传统一体机形态 = 容量与计算绑定、按峰值预留。这三种的成本结构不同，不是新旧关系。
- **机制**：因为格式层把"表是什么"下沉成一份可被任意实现读取的协议，所以换引擎等于换一个读取实现，数据文件一个字节都不动；代价是**格式层只统一了"读"**——权限、血缘、审计仍留在各家自己的治理产品里，迁移那天要单独重建一遍映射。反过来，引擎层统一买到的是弹性与体验，代价是一旦跨出平台边界就要导出。
- **失效条件**：两种。其一，当写入频率高而压缩跟不上时，「任意引擎都能读」反转为「谁都读得慢」——快照规划的元数据成本随日志条目与文件数增长，最终超过扫描数据的成本。**症状**：瓶颈既不在计算也不在存储，而在"先搞清楚要读哪些文件"。**观测信号**：查询耗时中规划阶段的占比、小文件数、日志条目数的增速。其二，当初选了引擎层统一而两三年后真出现第二种计算需求（流处理、特征、向量检索）时，本轮决策整体失效：数据要么复制一份、要么停机重写，而这笔代价在选型那天被完整地记在了"以后再说"一栏。**档位**：【公开：Delta Lake 于 2019 年由 Databricks 开源；Iceberg 于 2018 年由 Netflix 开源、2020 年成为 Apache 顶级项目】；湖仓形态的定型时间按 2019–2020 年记【推算：以 2019 年 Delta Lake 开源为起点，湖仓一体的产品叙事集中在 2020 年前后，推导过程见本章 §7.1 的时间窗说明】。

**共享即读：跨组织交换用不用副本**

- **做法**：跨组织、跨云、数据市场三类场景，统一采用"共享读权限与元数据指向"，不导出副本；对不能直连的场景，用开放格式做兜底，把导出当作最后手段而不是默认路径。共享双方要各自确认：谁能读、读到的是不是生产者的当前数据、边界跨不跨厂商。
- **机制**：因为共享的是读权限与元数据指向而不是一份复制出来的数据，所以副本根本不产生，「哪一份是对的」这个问题在结构上不存在；代价是共享体验与厂商边界绑定——跨云能力取决于厂商，而一旦要跨出产品边界，仍然要导出。
- **失效条件**：当消费者需要对共享数据**加工与回写**时，只读共享不够用；当合规要求数据不得跨边界或必须本地化时，共享边界与监管边界冲突。两种情况下都会出现同一个症状：消费者侧悄悄复制一份，副本漂移与"哪份对"重新出现。**观测信号**：共享对象的消费者数量中，做了本地副本的比例；以及副本的同步作业是否在无人认领地运行。**档位**：【公开：Snowflake 数据共享与数据市场为官方产品能力，功能边界与计费口径以官方文档当前版本为准】+【经验】。

**资金与账务状态：追加型账本 + 对账**

- **做法**：账本只追加、不修改历史；纠错表示为一笔**反向分录**；金额以最小货币单位存整数（不用浮点）；写入用幂等键 + 唯一约束（重试不会重复入账）；借贷恒等写成一条能被 SQL 直接校验的不变量，并纳入例行校验；余额由重放或聚合得到，或由与账本保持一致的物化视图维护；账本与数据仓分成两层——**真值在应用侧，仓里的余额是派生值**。
- **机制**：因为"修改"被表示成"追加"，所以任意时点的余额都能由历史重放得到，审计对象是一份只增不改的记录；因为借贷恒等是可被查询直接校验的约束，所以错误会在对账时被机器抓住，而不是等报表被人质疑时才暴露。这条机制与 §3.2.3 的结构是同一件事，本节只讲它在工程上要求什么。
- **失效条件**：当有人为了"修一个数"直接对历史分录做 UPDATE 或 DELETE 时，「可重放」反转为不可追溯——余额仍然是那个数，但支撑它的分录已经被改写，"这个数怎么来的"再也答不出来。**症状**：对账能把差异暴露出来，但差异落在"金额对得上、依据说不清"这个最难处理的位置。**观测信号**：不变量校验是否每天运行且必须为零；分录表上是否给任何人授予了更新权限；"最近一次真实重放是什么时候"。**档位**：【公开：Stripe 的 API 文档中有专门的 Idempotency 章节，判定方法与字段语义以官方文档当前版本为准】；复式记账与只追加账本是记账领域的通行机制【经验】。

**合规把哪些数据划出可用集合**

- **做法**：训练侧按来源分层登记（公开语料、合成数据、用户反馈、红队与安全数据各自一档，默认不用于训练的要写死）；企业版提供数据隔离与本地化选项；访问控制用 RBAC 与 ABAC 两层叠加；静态与传输加密分开配置；所有操作留审计日志。落地的最小要求是：字段级登记 + 来源与许可 + 保留期，**三件都要能被一次性检索出来**。
- **机制**：因为合规把一部分数据从"可用集合"里**永久**划走，所以模型侧能做的只有接口（工具调用、协议），而不能托管客户数据——这不是能力不足，是约束决定的位置。因为分层登记与审计日志是可自证的前提，所以"这条数据能不能用、谁在什么时候用过"必须能被一次性回答，而不是靠翻三个系统的日志拼出来。
- **失效条件**：其一，当分层登记只做了一次、没有随数据源扩展维护时，新来源会以"未登记"状态进入管线，**症状**是审计时答不出某批数据的来源与许可，且这个缺口会随数据源数量线性增加。其二，当访问控制只在应用层做（依赖应用自己加条件）时，任何绕过应用的入口——直连、导出、共享、下游副本——都会失效，**症状**是同一个用户在两个入口看到的数据范围不同。**观测信号**：字段级 PII 标注覆盖率、训练语料中"来源未知"的占比、审计日志的缺写路径数。**档位**：【公开：数据使用与隐私相关的条款以各厂商官方文档当前版本为准】+【经验】。**注意**：合规条款会随版本变化，任何以条款为依据的架构结论都应在复审时重新核验，而不是一次性引用。

**工具调用与多智能体：模型怎么接外部数据**

- **做法**：把工具调用当作**数据侧的接口契约**来管：工具名、输入 schema、是否可写、Owner、审计字段逐项登记；读写工具分离、写操作单独授权；把每次调用记入日志以便回放；多智能体只在"任务可分解、且每一步的结果可被验证"时引入。演进脉络按能力分层看：基础模型 → 对话 → **Function Calling（工具调用标准）** → **Custom GPTs（低代码封装）** → **Agent SDK（编程式编排）** → **多智能体协同（Swarm 一类实验项目）**。
- **机制**：因为模型能做什么被工具 schema 固定，所以"能做什么"的边界由数据侧定义的接口决定，而不是由模型决定——这让权限与审计第一次能落在接口上，而不是散落在提示词里。
- **失效条件**：当工具 schema 频繁变动而调用方（提示词、编排代码）没有版本约束时，「能力扩展」反转为**静默失败**：模型会继续调用一个已经改名或改参数的工具，基于返回的错误信息继续推理，不报错、只是结果偏离。**症状**：成功率没掉，但需要人工复核的比例上升。**观测信号**：各工具的参数校验失败率、schema 版本与调用方版本是否对齐。**档位**：【公开：Function Calling 与 Custom GPTs 于 2023 年公开，多智能体实验项目与后续官方 SDK 于 2024 年起陆续公开，具体以各官方公告与官方仓库当前版本为准】。**评估实验性项目时先看它的自我定位**：若官方仓库明确标注为实验性、不保证维护，就不要把它放进关键路径——判定方法是读它的 README 定位段，而不是读新闻。

**成本可见性：让查询写法与账单的因果链可见**

- **做法**：把三件事做成例行可查，而不是靠治理推动——分区与列裁剪的实际效果、缓存（含提示词前缀缓存）命中率、每次关键操作的资源用量归因到团队。按用量计费的形态下，还要配用量配额与账单归因口径。
- **机制**：因为按用量计费时优化的收益**直接落在使用者身上**，所以不需要外部推动，使用者自己会看账单；而按容量计费时优化只体现为"更快"，不体现为"更省"，动力自然弱一个量级。这也是同一个技术动作（缓存、裁剪）在不同成本函数下紧迫性差很远的原因。
- **失效条件**：当计费方式从按容量改为按扫描量或按 token，而**写法与账单的因果链没有被监控**时，成本会在无人察觉时翻倍——因为没有任何一个时点需要有人做决策，每一笔支出当下都是合理的。**症状**：月度账单的增速与业务量增速脱节，但查不出是谁贡献的。**观测信号**：单位业务的资源用量（每次分析、每次请求）走势、查询扫描量与命中行数之比、缓存命中率。**档位**：【经验】；这条触发条件的特殊性在于——**它是唯一在规模完全不变时也会发生的一条**，触发它的是计费方式或财务口径的变化。

### 4.3 工具链与平台

选型判据写成"在什么约束下选它"。同一行里的候选不是竞争关系，它们在不同的约束下分别是最优解。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| **分析平台形态** | 传统数仓（Teradata、Oracle Exadata）；云数仓（Snowflake、BigQuery）；Lakehouse（Databricks） | 已有数据中心、有强隔离与固定 SLA 的监管要求、且短期内不会出现第二种计算引擎 → 传统形态仍可维持；分析单引擎、团队没有内核专家、需求波动大 → 云数仓；存量已在对象存储、未来会出现第二种引擎、且 ML/AI 要在同一份数据上做 → Lakehouse | 选云数仓而未来必然出现第二引擎：离开平台要导出；选 Lakehouse 而无第二引擎：自建与治理成本照付而格式开放的收益兑现不了 |
| **表格式与存储** | Apache Iceberg、Delta Lake | 判断只有一条：两三年内会不会出现第二种计算引擎。会，就必须用开放表格式；不会，格式开放的收益无法兑现 | 用引擎私有格式承载需要长期共存的数据：换引擎那天要复制或重写全部数据 |
| **跨组织共享** | 共享即读（Snowflake 数据共享与数据市场一类）；开放格式 + 导出兜底 | 交换边界在单一厂商内、消费者只需要读 → 共享即读；交换要跨出厂商、或消费者要加工回写 → 开放格式 + 明确的导出流程 | 默认用导出交换：副本数量与"哪一份对"同时增长；默认用共享而不留兜底：一旦跨出边界就无路可走 |
| **事务与账本** | PostgreSQL 一类关系库 + 自研追加型账本（幂等键、唯一约束、反向分录） | 只要状态是资金、账务、权益这类"必须能重放"的对象，就用追加型账本；普通业务状态不要照搬，重放与物化视图是额外的维护成本 | 用 UPDATE 维护余额：数对得上，依据说不清；对账差异落在最难处理的位置 |
| **合规与访问控制** | 字段级 PII 登记 + RBAC/ABAC + 静态与传输加密 + 审计日志 + 本地化部署选项 | 受监管、需要向客户或审计方自证的场景必须齐备；内部非敏感数据可以按分级放宽 | 只在应用层做过滤：任何绕过应用的入口都会失效，且失效不报错 |
| **Agent 与工具调用** | 平台内置的工具调用（Function Calling 一类）、官方 Agent SDK、多智能体编排框架（含实验性项目） | 工具边界稳定、需要审计 → 用平台内置工具调用并把 schema 登记为资产；要编程式编排 → 官方 SDK；多智能体只在任务可分解且每步可验证时引入 | 把实验性编排框架放进关键路径：它的接口与维护承诺随时可能变，而你已经把业务流程绑上去了 |

**决策依据仍然成立，但每条都要补一句判据。** 比对维度沿用这几项：核心定位（云数仓 / Lakehouse）、多模数据、ML 能力、AI 能力、数据共享、商业化成熟度——每一项都要落到"在我这里会不会成为约束"，而不是整体打分。四条常见的决策依据按下面这样补：

| 你的侧重 | 倾向的形态 | 必须补的判据（否则会误选） |
| --- | --- | --- |
| 强 ML / AI | Lakehouse（Databricks 一类） | 先确认"训练与推理是否真的要在同一份数据上做"——不是，则只是多买了一套平台 |
| 强数据共享 | 云数仓（Snowflake 一类） | 先确认共享边界会不会跨出该厂商——会跨，就要同时准备开放格式的兜底 |
| 强多模数据 | Lakehouse（Databricks 一类） | 先确认多模数据的量级是否值得为它承担"治理面自建"的长期成本 |
| 纯 SQL 数仓、单一引擎 | 云数仓（Snowflake、BigQuery 一类） | 先确认两三年内不会出现第二种计算引擎——会出现，格式层的选择要提前做 |

这一类里**最容易被误选的是"分析平台形态"**：评估表按功能覆盖度打分，Lakehouse 在"多模数据 / ML / AI"上天然领先，于是结论看起来不需要讨论。误选的后果不在当天：两三年后业务出现第二种计算需求或成本结构改变（从按容量计费转向按扫描量或按 token 计费）时，数据要么复制一份、要么停机重写，而权限与血缘要重建一遍。**替代判据是一条**：把"我未来 12 个月确定会用到哪几件能力"列出来，用这一列的数量决策，而不是用"平台一共有多少件"。

第二容易被误选的是**合规与访问控制**这一行——它常被当作"上线后再补"的项。但合规的特点是：**它划走的数据是补不回来的**。等到审计要求出现时，你需要的是"过去两年这条数据被谁用过"的完整记录，而这份记录只能从第一天就开始记。

### 4.4 存量迁移

存量迁移的难点从来不是"搬数据"，而是**真值与派生的边界在迁移期会短暂失效**：旧栈还在被读、新栈还不能全信。因此迁移的顺序，本质上是在决定"这段时间里谁说了算"。

**① 先做只读镜像与旁路查询，不动生产链路。** 第一步是把待迁移的数据以只读方式镜像到新栈，并把一部分**只读**分析负载切过去跑，与旧栈比对结果。这一步完全可回退：出问题就切回旧栈读，新栈留着不动。

- **判据**：同一个查询在两个栈上的结果差异清单，每一条都被判为"可解释"（精度、时区、空值语义、排序）或"必须解决"。**没有差异清单的迁移，等于没有验证过。**

**② 历史资产分三类处理，禁止全量返工。**

- **A 类｜活跃且被引用**：分阶段迁——先只读镜像与对账，再切读路径，最后才迁写入与调度。
- **B 类｜活跃但无人引用**：打标挂账，冻结新增下游，不迁。这类资产在存量仓里占比通常不低，把它们一起迁进来，等于把旧栈的混乱完整复制到新栈【经验：这类表往往要等到做一次独立的下游统计才会被发现】。
- **C 类｜已停更**：留在旧栈只读，登记退役责任人，不迁。
- **判据**：每张表都落在三类之一，且分类依据（下游数量、最近一次查询时间）可查。**账本类例外**：历史分录一律不重算、不"修正后再迁"——只追加搬迁并把不变量校验在新栈上重跑一遍。

合规类存量数据在迁移里有一个**不可逆**的特性：字段级 PII 登记、来源与许可、保留期这三件事，**补不回来**——你可以给存量数据今天补上"含 PII"的标注，但你补不出"过去两年它被谁访问过"。所以正确做法是从迁移第一天起就把字段级登记与访问日志一起接上，而不是等审计要求出现后再补。**判据**：上线后能否对任意一张表回答两个问题——它含不含 PII；谁在什么时候读过它。答不出，缺的不是标注，是日志。

**③ 双轨怎么维持，维持多久。** 双轨不是两套并行开发，而是**只在一个方向前进**：新需求一律落在新栈，旧栈只接受必要的数据修复。两栈之间用一张键映射打通（业务键 ↔ 代理键、或租户 ↔ 分片），让旧报表按老口径读到新数据。

- 双轨期最关键的动作是**对账**，三级都要跑：行数（同一天、同一实体数）、聚合（同一定义的核心指标）、抽样明细（抽若干单据逐字段比）。只有第一级过了就宣布成功，是这类迁移最常见的自欺。
- 双轨长度由**旧栈查询量的下降速度**决定，不由项目计划决定【经验：6–24 个月区间；旧报表退役越慢、新旧口径差异面越大，双轨越长】。
- 双轨期的成本要提前记账【推算：同一份数据在新旧两栈各存一份，存储与写入成本约翻一倍；若旧栈只保留最近 N 天热数据，冗余倍数降为 N 占全量历史的比例】。
- **跨组织共享与租户分片要单独对待**：共享关系在迁移期最容易出现"两边都以为是对方在维护"的副本；分片键一旦选定极难更改（§3.6），迁移不是重选分片键的时机——若确实要重选，把它当作一次独立项目，而不是迁移的附带动作。
- **双轨期必须有一条"改哪边"的规则**：同一个口径发现错误时，默认只改新栈，并通过三级对账验证旧报表是否需要同步；万一必须改旧栈，要记录原因与改动人。缺这条规则时，两栈会被不同的人各自修，差异只会以"对账时才发现"的方式出现。

**④ 什么信号说明可以退出双轨。** 四条同时满足：

1. 连续两个完整结算周期，三级对账零差异；
2. 旧栈查询量降到可忽略——能拿出具体数字与统计口径，不是"感觉没人用了"；
3. 调度系统里没有新作业依赖旧栈——看依赖图，不看口头承诺；
4. 旧栈的 Owner 提交退役清单，逐张签字。

**⑤ 迁移的成本由三块构成，最容易被漏的是第三块。** 一次性的搬迁与重写（最容易估）、双轨期的冗余（存储 + 计算 + 运维）、以及对账与口径回归的人力（最容易被漏）。第三块不产出任何新东西，却是唯一能证明迁移成功的动作。判断方法：把三级对账排进例行调度之后，看它每月占用多少人天——这个数乘以预计的双轨月数，就是对账成本的下限【推算：双轨期冗余 ≈ 同一份数据的存储与写入各一份（旧栈若只留最近 N 天，则冗余倍数降为 N 占全量历史的比例）；对账人力 ≈ 每月固定人天 × 双轨月数，两项都随旧栈的退役速度变化】。

**⑥ 模型侧资产的迁移与数据类不同，不能只做"镜像 + 对账"。** 语料、评测集与特征管线要满足两条：训练与打包管线**可重跑**（改了配比或去重规则就能整体重跑，而不是增量补丁），评测集与训练语料的隔离必须在管线里做到**物理隔离**。后一条不是迁移期的可选项：一旦泄漏，离线指标会被推高而真实泛化不变，这种错误不报错，只会让团队按错误的信号继续投入算力（机制见 §3.2.6）。本节的迁移要求只有一句：**隔离点要能指出在管线的哪一步做的，并且重跑之后仍然成立。**

**最典型的失败是按日期下线**：计划写着"六个月后切换"，到点就关。此时总还剩几张没人记得的报表、几个没人知道的定时脚本挂在旧表上；它们不会立刻报错，而是在下一个季度的口径核对里变成"这个数怎么和上季度对不上"。**判据**：退双轨这件事，要由对账报表和依赖图决定，不能由日历决定。

**怎么用**：第 4 段是这类文档里唯一不能省的一段——把代价写具体，三年后才有人能判断"这个代价现在还成立吗"。第 5 段里的每一条都要能被监控系统或财务口径测出来；写成"业务发展"或"需求变化"的触发条件等于没写。第 3 段的"回退代价"一栏如果填不出来，说明这个不可逆项还没有被真正评估过。

**模板三：迁移期三级对账（骨架，方言自调）**

```sql
-- 第 1 级：行数与实体数（同一天、同一实体）
SELECT 'user_cnt' AS metric, (SELECT count(DISTINCT user_id) FROM old.dim_user) AS old_v,
                             (SELECT count(DISTINCT user_id) FROM new.dim_user) AS new_v
UNION ALL
SELECT 'order_cnt', (SELECT count(*) FROM old.fact_order WHERE dt = :d),
                    (SELECT count(*) FROM new.fact_order  WHERE dt = :d);

-- 第 2 级：同一定义的核心指标（口径必须来自同一份定义，不是两段手写 SQL）
--   gmv_1d = SUM(order_amount_rmb) WHERE dt = :d AND order_status = 'PAID'

-- 第 3 级：抽样明细（抽 N 笔单据逐字段比，N 按单据金额分层抽）
SELECT * FROM old.fact_order WHERE order_id IN (:sample) MINUS
SELECT * FROM new.fact_order WHERE order_id IN (:sample);
```

**怎么用**：第 1 级会过而第 2 级不过，说明差异在口径而不是数据——去查定义，不要去查管道。第 3 级要**按金额分层抽样**（大额单据单独抽），因为随机抽样会漏掉金额极值处的转换错误。三级都要进例行调度，只在迁移当天手工跑过的对账等于没做。

```markdown
| 工具名 | 输入 schema（版本） | 读/写 | Owner | 权限范围 | 审计字段 | 失败时的降级路径 |
| --- | --- | --- | --- | --- | --- | --- |
| query_metric | v2（metric, dims, grain） | 读 | {具体到人} | 只读语义层已注册度量 | 提问者 / 调用时间 / 返回口径 | 返回"无此度量"，不猜 |

```

**怎么用**：写操作必须单独一行、单独授权，不要与读工具混在同一张授权里。schema 版本要与调用方（提示词、编排代码）的版本对齐后再改——表里"版本"这一列存在的意义就是让这次对齐可见。最后一列的降级路径要写成具体行为（"不猜""转人工"），写"记录日志"不算降级。

```markdown
| tmp_shop_rank | 表 | B｜活跃无人引用 | 下游 0；30 天内查询 3 次（均为本人） | 打标挂账，冻结新增下游 | {到人} | 连续两个季度零查询 |
| ods_legacy_log | 表 | C｜已停更 | 最近一次查询在 400 天前 | 留在旧栈只读 | {到人} | 保留期到期后归档 |
| fact_ledger_entry | 分录表 | 例外｜不重算 | 不变量校验依赖全量历史 | 原样搬迁 + 新栈重跑不变量 | {到人} | — |
```

**怎么用**：分类只有三类，不要发明第四类——多出来的类目会让"谁负责"变得模糊。"依据"这一列必须写成可复核的数字（下游数、最近查询时间），写"业务方说没用了"不算依据。表里示例行的数值只是示意，其中"下游几个算多""多少天算停更"要按你自己的资产分布定，并把这两个口径写进分类规则——否则不同的人会给出不同的分类。"退役条件"这一列是写给未来的人看的：它让 B 类资产不必每隔半年被重新论证一遍。

### 4.6 成本：这套东西的账单

本主题的账单有一个反直觉之处：**这些公司多花的钱，大半是因为约束，不是因为规模**。跨区副本、合规隔离、多引擎治理面，都是"约束逼出来的"（§3 的范式就是被约束逼出来的），不是规模自然而然带来的。照搬结论而不照搬约束，就会**只付成本、不拿收益**——这是本章反复警告的失败方式在账单上的样子。

三类里真正相关的是**云账单**与**人力**，硬件仍不构成约束（数据平台不吃裸机）。

**跨区 / 出网（增，随合规放大）**：【公开：AWS 的 EC2 数据传出（Data Transfer）计价页、Google Cloud 的 VPC 网络计价页，2024——两页均把出网流量（egress）与跨区传输单列为计价项；具体单价与计费口径以各自官方计价页当前版本为准】。数据本地化要求把同一份逻辑数据按地区存多份——【推算】若业务覆盖 R 个要求本地化的地区、每区各存一份，存储与写入即按 R 倍计；地区之间的聚合查询要跨区拉取，每次拉取计一次出网费。这是"全球化"最直接、也最容易被低估的一项：它不随用户数增长，而随**地区数**增长。

**多引擎 / 多区域的治理面（增）**：§3 的统一层决策一旦落在引擎层，两三年后出现第二种计算需求（流、特征、向量）时，代价是复制数据或停机重写（§4.2 第一条失效条件）。这项成本在选型当天被完整记进"以后再说"一栏——不是不会发生，只是被推到了账单看不见的地方。

**迁就案例规模的过度设计（增，纯浪费）**：为 3 亿用户设计的分片键（§2.2.1）、为多 BU 设计的隔离，落到一百万用户的环境里只留下复杂度。判据在 §4.1 Step 1：说不出"我在哪条约束下选它"，就是在替一个不属于你的规模付费。

按用量计费下"写法 ↔ 账单"的因果链如何做成可查，见 §4.2「成本可见性」；迁移期的冗余与对账人力三块，见 §4.4⑤。本节只点本主题**特有的成本形状**：它随**地区数**与**约束条数**增长，而不随用户数增长。

### 4.7 容灾与故障演练

本主题的容灾有一道别处没有的约束：**合规会限制你"能不能把数据复制到另一个区"**。跨地域容灾的标准做法是异地副本，但当数据是欧洲用户 PII 时，把副本放到 US 区本身就可能违规——于是容灾必须在**驻留边界之内**设计。这是本主题与通用容灾最大的差别：可用区不是唯一的天花板，法条也是。

| 失效模式 | 影响面 | 降级策略 | 恢复目标 |
| --- | --- | --- | --- |
| 单区故障（机房 / 可用区不可用） | 该区用户全量不可用，且**受限数据可能不允许切到别的区** | 在合规边界内做区内多可用区；跨区只同步**非受限**数据，受限数据接受更长 RTO 而不是违规复制 | RTO/RPO 按数据类型分档【经验：受限数据 RTO 高于非受限数据，随合规条款与本地副本形态变】 |
| 用户删除权（Right to be Forgotten） | 主库删了、备份与派生副本里还在，审计答不出"删干净了没" | 删除必须贯穿备份与派生：以用户 ID 可定位所有副本，并把"证明已删"做成可查询 | 删除 RTO【经验：随副本数与派生链长度变，天级到周级】 |
| 跨区共享的副本漂移 | 消费者侧悄悄复制一份，"哪份对"重新出现（§4.2 第 2 条） | 共享读权限与元数据指向、不导出；不能直连时用开放格式兜底 | 无固定目标，以副本同步作业是否在无人认领运行作为观测信号 |

演练演**合规性故障**而不是"拔网线"：① 抽一个用户 ID，走一遍"就地删除并证明删干净"（主库 + 备份 + 派生），记录从发起到拿出证据的时长；② 断掉一个区，验证受限数据**没有**被违规复制到边界外、同时非受限服务仍可用；③ 抽查一个共享对象，数它有多少消费者做了本地副本。

通用容灾形态与 RPO/RTO 分级见 [容灾与恢复](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)、故障注入方法论见 [混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)；本节只点本主题特有的那一层：**合规是容灾的硬边界**。

### 4.8 演进路线：0 → 1 → 100

> 每一阶段只写两件事：**变贵的是什么**、**先坏的是什么**。本章的演进主线（§3）是被约束逼出来的范式变迁，这里只讲"你要照搬时"的代价曲线。

**0 → 1（最小可用）**：单区、单引擎、无跨组织共享。先做的不是搭架构，而是 §4.1 Step 1 的约束盘点——把"两三年内会不会出现第二引擎""是否要求数据本地化""哪些数据不能用于训练"写成明文。变贵的是把这四条问清楚的一次性功夫；先坏的是跳过盘点直接按"功能最全"选平台，约束一变结论无从解释，只能整体重选。

**1 → 100（规模化）**：出现第二种计算需求、跨组织共享、或首个要求本地化的地区——此时才按 §3 的范式逐个引入统一层、共享读、账本。变贵的是多引擎治理面、跨区 / 出网账单（见 §4.6）与迁移双轨（§4.4）；先坏的是**按日历退双轨**——到点就关旧栈，剩下的报表在下一个季度变成"这个数怎么对不上"（§4.4 最典型失败）。这一阶段的顺序必须由对账报表与依赖图决定，不由时间轴决定。

**100 →（下一道坎）**：合规的边界从"数据放哪"扩展到"模型能不能托管它"——训练与推理把一部分数据划出可用集合，模型侧只能做到接口而不能托管客户数据（§4.2 合规一节）。变贵的是把字段级 PII 登记、来源许可、保留期，以及**访问日志**一起在迁移第一天接上——前三件补不回来（见 §4.4）；先坏的是删除权与审计：它们平时不暴露，只在第一次审计或第一次用户行使删除权时，让你答不出"删干净了没"。

### 4.9 自检清单

- [ ] 你现在这份选型结论，能不能指出"哪一条约束是决定性的"？指不出，说明当时比的是功能清单。
- [ ] 跨边界的那几个数据集属于哪一类资产，它们的权限规则现在写在哪里？换平台时会不会跟着丢？
- [ ] 如果出现第二种计算引擎，你的数据需要复制、重写，还是换一个读取实现就能读？现在能答出来吗？
- [ ] 共享给对方的数据，对方是直接读还是复制了一份？如果有副本，谁在维护它的同步？
- [ ] 资金 / 账务 / 权益类状态：余额是算出来的还是存下来的？有没有一条能被查询直接校验的不变量？
- [ ] 分录表上是否给任何人授予了 UPDATE / DELETE 权限？"最近一次真实重放是什么时候"能回答吗？
- [ ] 训练或模型侧用到的数据，能不能一次性回答"它从哪来、许可是什么、能不能用于训练"？
- [ ] 访问控制是否只在应用层做？列出所有绕过应用就能读到数据的入口，逐个确认它们受不受同一套规则约束。
- [ ] 每个工具调用的 schema 有版本吗？改 schema 时怎么确认调用方已经跟上？
- [ ] 多智能体或实验性编排框架，是否被放进了关键路径？它的官方定位是"实验性"还是"生产可用"？
- [ ] 存量表里能否随手点开一张就知道它属于 A / B / C 哪一类，依据是什么？
- [ ] 退双轨的四条信号里，哪几条现在是可测的？测不出来的那几条，由谁负责把它变成可测的？

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **§4.1 的 Step 1「约束盘点，并把不可逆项标出来」**——它不产出任何系统，却是唯一能让后面每一步都可被检验的环节。约束一旦写成明文，候选淘汰、试点判据、迁移分类、复审触发条件全部变成可核对的动作；反过来，约束没有写成明文时，4.2 的技术点、4.3 的候选表都只是知识的堆叠，读者会在自己环境里挑到"功能最全的那一个"，然后照搬了做法却没照搬它的代价。
>
> 💡 **思考锚点**：按 §4.4 把迁移成本拆三块，第三块——对账与口径回归的人力——的下限是「三级对账每月占用的人天 × 预计双轨月数」。把它算进你手上那份迁移预算后再问一句：你的双轨退出是按日历定的，还是按对账报表与依赖图定的？如果至今拿不出一张「每条差异都被判过可解释或必须解决」的差异清单，你又凭什么知道到点可以切？
