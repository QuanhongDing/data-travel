## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本章是海外案例章，而海外材料有一个结构性特点：**最容易被写成"前沿"的那些条目，恰恰是最不容易被第三方核验的那些**——厂商产品文档写的是"我们能做什么"，发布方工程博客写的是"我们为什么这么设计"，两者都不回答"别人在生产里用了多久、付了什么代价"。原 § 5 把 24 个条目并列成同一句式（「**RAG**：检索增强生成。」「**Databricks AI Platform**：数据 + 模型 + 应用。」），读者据此排路线图时无法判断哪一条今天能上生产、哪一条只是产品页上的一个模块名。本节对每个方向都要求：**判据必须是可核验的动作**（去哪份 release note / 哪份规范里核什么），而不是"它支持"。

第二个坑是**把"能力名"当成"产品特性名"**。同一件事在不同厂商那里的叫法与边界都不一样：把模型调用做成仓内函数（本文简称"仓内 AI 函数"）、把工具与上下文的定义做成协议（MCP 一类的开放协议）、把非文本输入直接交给模型（多模态输入），这三件事在原文里分别被记成了某个具体产品的名字。**产品名会换代，能力名不会**，所以本节按能力名展开，产品名只作为该能力的实例出现，并且每次都补一句"这个能力由哪些动作可以核验"。

第三个坑是**把发布时间当成成熟度**。模型厂商的发布节奏是季度级的，数据平台的发布节奏是年级的，两边的"已发布"含义完全不同：模型侧的一次发布通常指"接口可用"，数据侧的一次发布通常指"正式版本可用"。本节因此不看"谁先发"，只看三条判据。

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note（或版本化发布的规范）；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定、可预期 | 可以排进路线图 |
| **L2 可试点** | ① 或 ③ 基本成立，但 ② 拿不出；或接口/生态未稳，或仅有厂商自有案例 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 实验性项目（**"有公开论文、公开基准或开源实现，但没有正式产品条目"也归入这一形态**） | 记录，不要在架构里预留假设 |

三条判据的分工：① 回答"它是发布过的，还是演示过的"；② 回答"出问题时我能不能找到别人的经验，而不是厂商的承诺"；③ 回答"我明年会不会为它重写一遍"。**② 只有两种命运：满足，或降为 L2**——不存在"L1 的边界案例"这种写法，也不存在"把 L1 的适用范围缩小到某一层"的写法，那等于换了判据却不动名字。**同一组状态必须给出同一个级别**：② 不满足时，L2 与 L3 的分界只有两条——① 或 ③ 里至少有一条"基本成立"（① 有正式的产品条目或版本化发布的规范；③ 接口形态已趋同、不随版本重写），或者 ② 虽缺、但这件做法已有**厂商自有的运行案例**；两条都拿不出、只剩论文 / 公开基准 / 开源实现的，一律按 L3 判。**"①部分满足"不算"①基本成立"**：本节表里"知识图谱 + LLM"与"AI 评估指标与自动评估"两行的状态完全相同（①部分满足、③不满足、②不满足），级别因此也必须相同。

三条判据可以各用一个动作核验，不需要读完整篇文档：**① 的动作是"在发布说明里搜关键词，看条目写的是实验性 / 预览还是正式能力"；② 的动作是"去找一份不是由卖方、也不是由发起方自己写的运行记录"；③ 的动作是"看这个接口在过去两三年里有没有被迫重写过"**【经验：③ 的观察窗口，随领域的技术代际节奏变，越新的领域这一窗口越短】。三个动作里任何一个做不出来，说明这个方向还不到可评估的阶段——这句话对下面每一个 L3 都成立。找不出动作的方向不是"暂时不知道"，而是**证据形态本身还不存在**。

级别不是一次定终身。每次平台或模型版本升级后回填一次，规则只有两条：某个 L2 方向若出现第三方公开的运行记录就升 L1；某个 L2 方向若在你自己的场景里跑满一段观察期仍拿不到可比的数字（召回、失败率、单位成本），就降 L3 并停止投入——**长期停在"可试点"而无人敢上量，本身就是一条结论**【经验：观察期取 6–12 个月，随使用频次与数据量变；使用频次越低，需要的观察期越长】。

**本节对 §2.1 的 L1 判据做了如下修正**：判据 ① 在本主题按「已 GA 且有正式 release note，**或**以版本号发布的公开规范」取。理由是本节要评的方向里包含协议与规范（MCP 一类），它们不以产品形态发布、因此没有产品的 release note，而规范以版本号发布、版本记录本身可查，取证形态与 release note 等价；只认 release note 会把这一整类方向判成"没有正式发布"，与它们的可核验程度不符（判法见 §5.1 表与 §5.2.2 成熟度行，两处一致）。**修正只作用于 ① 的证据形态，②③ 的主体与适用范围一字未改**——本节无一行到 L1 与这条修正无关，缺的都是第②条。本主题最诱人放宽第②条的地方在于：本节的案例本身就是厂商与平台，很容易把"厂商自己的产品公告"或"某平台公开的采用者名单"读成第三方生产案例。但按判据读，产品公告证明的是**它被卖出去了或即将可用**，采用者名单证明的是**商务关系**，两者都不是"某非厂商组织公开过它在生产里的规模、目标与实测结果"这类带参数的材料。另一条纪律：**已经在生产里跑了多年的既有能力**（向量索引本体、工具调用的基本形态、追加型日志、开放表格式）不是 AI 方向，本节只在对照时提及。

按这套判据，本主题下的方向分成：

| 演进方向 | 级别 | 判据（①/②/③ 的具体状态） | 现在该做什么 |
| --- | :---: | --- | --- |
| 检索增强生成（RAG）主链路（Embedding + Vector DB + 生成） | **L2** | ①满足（向量检索与嵌入的查询接口多年不变、产品已 GA）；③满足（索引构建 / Top-K / 过滤条件形态趋同）；②不满足 | PoC：先建自建评测集（含召回与引用正确性），再谈上量 |
| 知识图谱 + LLM（图增强检索一类） | **L3** | ①部分满足（有公开论文与开源实现，无正式产品条目）；③不满足（实体与关系的表示各家用各自定义）；②不满足 | 记录；不要在 schema 里预留"通用实体-关系层" |
| 工具调用（Function Calling） | **L2** | ①满足（2023 年起为多家模型 API 的正式文档条目）；③满足（工具 schema 形态趋同）；②不满足 | 排进试点：把工具当"数据侧的接口契约"登记（名称 / 入参 / 可写性 / Owner / 审计） |
| 智能体编排（Agent / 官方 Agent SDK / LangChain·LlamaIndex 一类框架） | **L2** | ①满足（官方 SDK 于 2024–2025 年陆续正式发布）；③部分满足（编排接口随框架版本变动）；②不满足 | 试点，且只用在"任务可分解、每步可验证"的场景 |
| 多智能体协同（Multi-Agent） | **L3** | ①不满足（公开形态为实验性项目与论文）；③不满足；②不满足 | 记录；不要把它放进关键路径 |
| 工具与上下文协议（MCP 一类的接口层统一） | **L2** | ①满足（规范 2024 年公开并版本化）；③较好（协议可被第三方重新实现，SDK 可替换）；②不满足（公开采纳来自厂商公告与实现清单，不是生产用户的运行记录） | 试点：关键集成同时保留"协议实现 + 直连实现" |
| 数据与模型同平台的一体化（仓内 AI 函数 + 平台侧 AI 能力） | **L2** | ①满足（各厂商正式发布）；③需逐条核验（函数的执行位置与计价因产品而异）；②不满足 | PoC 前先答一个问题：训练与推理是否真要在同一份数据上做 |
| 多模态输入（图像 / 音频 / 视频直接进模型） | **L2** | ①满足（2024 年起为多家模型 API 的正式文档条目）；③满足（输入模态接口趋同）；②不满足 | 可以用，但必须把"原件消费记录"写进元数据 |
| 生成式内容作为数据资产（原清单里 DALL-E / Sora 属**输出侧**，与上行的输入侧是两个方向） | **L2** | ①满足（生成能力已以正式接口发布、有公开文档与发布说明）；③部分满足（"提示词 → 生成物"的接口形态随模型换代变动，跨厂商不统一）；②不满足（没有非厂商组织公开"生成物进入生产数据链路"的运行口径）。**① 是就"已正式发布"判的，不随模态变**：你要用的那一模态（图像 / 视频）标的是正式能力还是预览，须按该厂商 API 文档的生成章节与对应 release note 自核（文档位置与检索词见 §5.4 判定入口一类的图像 / 视频生成条目）——标 preview 的，那一模态的 ① 不成立 | PoC：只在需要合成语料时小范围用，并把"来源 = 生成"与生成所用的模型版本写进元数据；不要为"生成物即资产"预留 schema |
| AI 评估指标与自动评估（Auto-Evaluation） | **L3** | ①部分满足（有公开基准与评测方法，自动评估本身无产品条目）；③不满足（指标口径各评测各定义）；②不满足 | 记录；自建评测集并与语料物理隔离（这两件事不依赖该方向的成熟度）；不要把厂商榜单当验收 |
| 持续训练与反馈回灌（Continuous Training） | **L3** | ①不满足（无正式产品条目）；③不满足；②不满足 | 记录；先解决"评测能不能区分改好与改坏" |
| 按量计费的模型 API（按 Token / 按请求 / 混合计费） | **L2** | ①满足（计价口径与定价页公开）；③稳定（计费口径长期不变）；②不满足 | 把"单位业务用量"做成可查项，而不是年底谈价 |
| 数据与模型市场（Snowflake / Databricks Marketplace、Hugging Face 一类） | **L2** | ①满足（平台 GA 多年、上架与拉取接口稳定）；③稳定；②不满足（上架与拉取是分发行为，不是第三方生产运行记录） | 先在私有共享里用起来，不要等市场 |

> **本节没有任何一行达到 L1。** 缺的都是第②条：本主题可核验的公开材料只有三类——厂商产品文档（支撑 ①）、发布方与建设方的工程自述（即 L2 定义里的"厂商自有案例"）、论文与公开基准（证明方法可行）——没有一类是"非厂商组织公开的生产运行记录"。**L2 不等于"不能用"**：表里多行（检索、工具调用、编排、按量计费）在真实系统里天天在跑；L2 只表示**公开证据到不了 L1**。要警惕的是把 L2 当 L1 用，写成"所以可以按某个产品的形态定架构"。

给每个 L2 行预先写好升 L1 的条件，比年底重评一次更有效，条件都写成可观察的信号（§5.1 表里 9 个 L2 行逐行有对应：工具调用与协议一组覆盖两行，其余各组一行）：检索的升级条件是**出现第三方公开的、带语料规模与召回目标的运行口径**；工具调用与协议的升级条件是**非发起方组织公开其生产运行记录（含调用量、失败率与权限模型）**；智能体编排的升级条件是**编排接口在连续几个正式版本之间保持兼容，且出现非框架方组织公开的运行记录**；平台一体化的升级条件是**仓内函数的执行位置与计价口径被官方文档固定下来，且出现第三方在强合规场景的公开运行报告**；多模态输入的升级条件是**原件消费与版本复现的记录形态成为正式文档条目**；生成式内容的升级条件是**"生成物进入生产数据链路"出现非厂商公开的运行口径，且来源标注与再消费记录成为正式文档条目**；计费单位的升级条件是**缓存与批处理的计价口径跨厂商可比**；数据与模型市场的升级条件与 §5.6 第 4 条是同一条信号——**出现被多家非发起方正式产品实现的跨厂商共享协议，且跨组织交易口径可公开核验**。

**本节与主文件的关系**：主文件 §2 给的是海外公司的**挑战**（全球化、合规复杂、多业务、AI 工程化），本节回答的是"这些挑战现在有哪些可用的解法，以及它们的成熟度"。两者会给出不同结论——主文件 §2.2.3 把 AI 工程化记成一条挑战，本节判的是**可从外部核验的工程可用性**：挑战讲的是问题存在，成熟度讲的是解法可不可依赖。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向在评审时应被直接打回。四个方向覆盖本节 §5.1 表里 13 行中的 12 行（多智能体、持续训练与输出侧生成虽未各自单列成节，但在 §5.2.2、§5.2.4 与 §5.2.3 里各有独立评级与判据），**仅"数据与模型市场"未在 5.2 展开**，其落点见 §5.3 的共享接口行、§5.5 第 1 条与 §5.6 第 4 条。

#### 5.2.1 「找」的机制换了：把关键词匹配换成语义近邻

- **旧做法与它的卡点**：原 §5.1.1 的三条（RAG / 知识图谱 + LLM / Embedding + Vector DB）解的是同一个卡点：**能搜到的前提是你知道它叫什么**。关键词索引要求提问者与文档用同一批词，而"复购率"与"重复购买率"、"GBM"与"胶质母细胞瘤"在倒排表里是两个不相干的词；跨语言与跨模态更是直接失效。还有一条更硬的卡点写在主文件 §2.2.2（数据合规：数据本地化、用户删除权、血缘可追溯）里：这三件事都指向同一个动作——**在不把数据捞出来的前提下判断"这条数据是谁的、谁能看"**；如果检索侧不在召回时下推权限过滤，召回回来的就会是你没有权限看的内容，而此时它已经进了上下文。
- **AI 改变了什么机制**：**把"匹配"从词的相等换成向量空间里的近邻**（编码 + 向量索引 + 多路融合），这是第一条腿；**把关系外化成可遍历的边**（知识图谱 + LLM）是第二条腿——它不改变"相似"的定义，只是让"这个实体的上下游有哪些"从一次人工盘点变成一次图遍历。两条腿的机制不同，不该被写成一句话。
- **由此得到的**：**因为"相似"被定义在编码器学出来的空间里而不是词表里，所以跨写法、跨语言的召回可以只做一次索引**；因为图把关系外化成边，所以"改这个字段会影响谁"这类问题可以沿边走一遍，而不需要去读别人的 SQL（这与本章 §3.2.4 的"日志 + 派生视图"是两种不同的解耦手段：一个解耦读形态，一个解耦关系表达）。

```text
两条链路的误差位置不同（这是"该不该用检索增强"之外的第二个问题）
  文本/向量链：查询 ──编码──► 近邻检索 ──排序──► 送进上下文
      误差位置：分块边界与编码器版本（换一次就要重建索引）
  图增强链：  查询 ──实体识别──► 图上走 N 跳 ──► 子图送进上下文
      误差位置：实体识别的准确率与跳数（跳数越多，上下文越贵、越吵）
  ────────────────────────────────────────────────
  共同点：生成只负责"读"，不负责"找"——召回失败无法由生成补救
```

| 机制 | 匹配依据 | 召回上限由什么决定 | 换一次要付什么 |
| --- | --- | --- | --- |
| 稀疏匹配（倒排表 / 关键词） | 词是否出现、出现几次 | 提问者与文档的用词是否重合 | 维护同义词表；影响面小、可局部改 |
| 稠密检索（Embedding + 向量索引） | 向量空间里的距离 | 分块策略与编码器版本 | 重建全部索引（存储与写入按向量数量增长） |
| 图增强（实体 + 关系） | 图上能不能走到 | 实体识别准确率与跳数预算 | 维护实体与关系；跳数变大则上下文更贵更吵 |

- **由此付出的**：**其一，召回上限从"词表"转移到"分块策略 + 编码器版本"**——这两件事都不含关键词信号，改一次就要重建索引，索引重建不是零成本（存储与写入随分块与向量的数量线性增长）；**其二，评测缺位**——"检索得准不准"没有公开标准，只能自建评测集，而没有评测集时，两个方案谁更好只能靠体感，体感在多路召回场景里极不可靠；**其三，图增强的更新成本**——实体与关系要随数据变化维护，而维护质量直接决定跳数能不能压住，这条成本往往在上量后才显现。
- **证据与来源**：【公开】稠密检索取代稀疏匹配的公开依据是 Karpukhin et al., "Dense Passage Retrieval for Open-Domain Question Answering", EMNLP 2020；"RAG"这一形态与名称的公开来源是 Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", NeurIPS 2020；图增强检索的代表工作是 Edge et al., "From Local to Global: A Graph RAG Approach to Query-Focused Summarization", arXiv 2024（**研究形态，不等于产品可用**）。**本节不引用"召回率提升多少"这类数字**：它们强烈依赖语料集、分块与编码器配置，跨数据集的通用数字不可比。
- **成熟度**：**L2（检索增强生成主链路）**：①满足（查询接口多年不变、产品已 GA）、③满足（索引构建 / Top-K / 过滤条件形态趋同）、②不满足（无可核验的第三方非厂商生产案例）。**L3（知识图谱 + LLM）**：①部分满足（有公开论文与开源实现，无正式产品条目）、③不满足（实体与关系的表示各家用各自定义）、②不满足。

#### 5.2.2 「做」的机制换了：控制流从应用代码移到模型

- **旧做法与它的卡点**：原 §5.1.2 的 Function Calling / Agent / Multi-Agent 与原 §5.2.2 的 Agent SDK / MCP / LangChain·LlamaIndex 解的是同一件事：**"下一步做什么"过去必须写死在代码里**——每加一个数据源就要改一次编排代码，且"这次该调哪个工具"的判断只能由人做。主文件 §2.2.3 把这条记成"AI 工程化"挑战；本章 §4.2 把它落成一句更具体的话：**"能做什么"的边界由数据侧定义的接口决定，而不是由模型决定**。
- **AI 改变了什么机制**：**把"下一步做什么"从代码的控制流换成模型的采样输出，同时把"能做什么"固定在工具 schema 上**。判断是概率的、能力是确定的，两者被拆到了两个地方；协议（MCP 一类）是这条机制的第二段：它把工具与上下文的定义从"某家 SDK 的接口"提升为**可被第三方重新实现的协议**。

```text
工具调用把"判断"与"能力"拆到了两处
  能力边界（稳定、可登记）：工具名 / 入参 schema / 是否可写 / Owner / 审计字段
  判断（概率、不可登记）：调哪个工具、调几次、失败后怎么退、用什么预算
  ────────────────────────────────────────────────
  旧做法：两者都写在编排代码里 → 加一个数据源 = 改代码 + 一次完整回归
  新做法：能力写进 schema，判断交给模型 → 边际成本显著下降
          条件：新增数据源不再需要改编排代码，只登记一份 schema
          代价：回归测试不再覆盖"模型选了哪条路"，
                覆盖成本转移到评测集与线上复核比例
```

- **由此得到的**：**因为能力边界由工具 schema 固定，所以权限与审计第一次能落在接口上**——谁能调哪个工具、入参是什么、是否可写，都能逐项登记，而不是散落在提示词里（本章 §4.2 把"工具名 / 入参 schema / 是否可写 / Owner / 审计字段"列为登记项）；**因为协议可被第三方重新实现，所以"换一家"的迁移成本从改代码压到改配置**——这正是本章 §7.3 的判据：能被重新实现是生态的前提，SDK 不能。
- **由此付出的**：**其一，方差成为主要成本**——控制流由采样决定，同一个问题两次结果可能不同，"成功率"必须按重复运行的分布来量，而不是按一次演示；**其二，静默失败**——工具改名或改参数时，模型会基于错误信息继续推理，不报错、只是结果偏离，表现为"成功率没掉但人工复核比例上升"（本章 §4.2 的失效条件）；**其三，新的权限面**——非人主体第一次有了调用权限，如果权限模型里没有"非人主体"这一档，Agent 只能借用某个人的身份，审计便答不出"这条数据是被谁读的"。
- **证据与来源**：【公开】"推理与工具交替"的公开依据是 Yao et al., "ReAct: Synergizing Reasoning and Acting in Language Models", ICLR 2023；工具调用从提示工程变成模型能力的公开依据是 Schick et al., "Toolformer: Language Models Can Teach Themselves to Use Tools", NeurIPS 2023；工具调用自 2023 年起成为多家模型 API 的正式文档条目；协议侧：MCP（Model Context Protocol）规范由 Anthropic 于 2024 年 11 月公开开源，2025 年被 OpenAI 在其智能体开发套件（Agents SDK）中公开采纳（【公开：Anthropic 的 MCP 规范与版本记录, 2024；OpenAI 公开公告, 2025】，与本章 §3.2.5 引用同一事件）。**上述材料来自提出方与采纳方，不是第三方生产用户的运行记录**，故②不满足。
- **成熟度**：**L2（工具调用）**：①满足（2023 年起为多家模型 API 的正式文档条目）、③满足（工具 schema 形态趋同）、②不满足。**L2（工具与上下文协议）**：①满足（规范 2024 年公开并版本化）、③较好（协议可被第三方重新实现，SDK 可替换）、②不满足（公开采纳来自厂商公告与实现清单，不是生产用户的运行记录）。**L2（智能体编排）**：①满足（官方 SDK 于 2024–2025 年陆续正式发布）、③部分满足（编排接口随框架版本变动）、②不满足。**L3（多智能体协同）**：①不满足（公开形态为实验性项目与论文）、③不满足、②不满足。

这条方向的取舍可以用一句话判断：**它把"路径不确定"的部分交给模型，把"结果必须确定"的部分留在接口上**。因此凡是路径本身就确定的场景（每天固定跑一批报表、固定口径的对账），引入编排只会增加方差而不增加能力——**编排的价值与"下一步无法预先写死"的程度成正比**，与任务复杂度无关。"任务复杂"不是引入编排的理由，"每一步的结果可被验证"才是。协议侧同理：本节只把协议当**接口稳定性**的证据，不当**能力成熟度**的证据——一个协议被广泛实现，说明"换一家"变容易了，不说明"这件事已经有人做成过"。

#### 5.2.3 边界画在哪：多模态输入上移与"模型搬进数据平台"

- **旧做法与它的卡点**：原 §5.2.3 的输入侧两条（GPT-4o / Claude 3.5 Sonnet）、它的输出侧一条（DALL-E / Sora），与原 §5.2.1（Databricks AI Platform / Snowflake Cortex / Anthropic Claude API）看似两件事，卡点却是同一个：**边界画在"数据要出去"的那一侧**。非文本资产要进链路，过去必须在最上游做一次转换（OCR / ASR），转换产物成为唯一可计算形态、原件退回归档，于是误差发生在链路最上游且不可逆；而"数据平台用上模型"过去必须在平台外另起一套，把最敏感的数据复制到模型侧——本章 §7.2.3 把它写成"模型搬到数据旁边"与"数据搬到模型旁边"两条成本曲线。
- **AI 改变了什么机制**：**输入边界上移**（模型 API 直接接受图像 / 音频 / 视频，预处理从架构必经环节降为可选优化），加上**执行位置内移**（把模型调用做成仓内函数一类的平台能力，执行发生在数据所在的权限与网络边界内）。前者改的是模型侧接口，后者改的是数据侧位置；两者都不改索引结构。
- **由此得到的**：**因为模型能直接吃原件，所以原件从"预处理完就能丢的中间产物"变成可再次消费的资产**——对数据库层的直接推论是元数据里必须记"这件原件被哪个模型版本消费过"（本章 §5.3 把这条写成一条接口：原件引用 + 消费记录）；**因为能力可以搬进平台，所以强合规行业里"数据不外发"与"用上模型"可以同时成立**，这也解释了为什么数据平台侧的 AI 能力往往先在强合规行业落地（本章 §7.2.3）。

| 判断项 | 能力搬进来（仓内 AI 函数一类） | 接口接出去（模型 API + 工具协议） |
| --- | --- | --- |
| 数据动不动 | 不动：模型在数据所在的边界内执行 | 动：以提示词或工具入参出域 |
| 适用于谁 | 敏感数据不能外发的场景 | 通用场景，成本最低 |
| 能力更新节奏 | 跟随平台发布 | 跟随模型厂商发布（通常更快） |
| 退出成本 | 换平台 = 换函数写法与计价口径 | 换模型 = 重跑评估 + 重写提示词 |
| 谁负责失败 | 平台侧负责执行可用性 | 调用方负责预算、权限与越权 |

- **由此付出的**：**其一，成本函数换了形状**——从"每页一次预处理的固定成本"变成"每次调用都送原件的边际成本"，问答次数越多越贵【经验：随输入体量与调用次数变，长视频与高分辨率图尤其明显】；**其二，可复现性下降**——模型版本迭代会改变对同一原件的理解，同一个问题在不同版本上答案不同，所以"用哪个版本消费过"必须落进元数据；**其三，位置绑定**——把模型搬进平台等于加深对平台的依赖，而仓内函数的执行位置与计价口径**因产品而异、需逐条核验**（判定方法：在该产品的官方文档里查函数的执行位置与计价条目，而不是看首页有没有写 AI）。
- **证据与来源**：【公开】多模态输入自 2024 年起为多家模型 API 的正式文档条目（判定入口是各 API 文档中输入模态章节标注为 GA 还是 preview）；仓内 AI 函数是各平台的**公开文档能力**，各有具名条目可核：Snowflake 侧的 Cortex 函数 2023 年公布、2024 年陆续可用（【公开：Snowflake Cortex 函数的官方文档与发布说明, 2023–2024；请以官方文档当前版本为准】）；Databricks 侧的仓内函数以 SQL 语言参考中 "AI functions"（`ai_query` 一类）的形式列条目（【公开：Databricks SQL 语言参考 "AI functions", 2024 起；请以官方文档当前版本为准】）。以上均为厂商材料，②不满足。
- **成熟度**：**L2（多模态输入）**：①满足（2024 年起为多家模型 API 的正式文档条目）、③满足（输入模态接口趋同）、②不满足。**L2（数据与模型同平台的一体化）**：①满足（各厂商正式发布）、③需逐条核验（函数的执行位置与计价因产品而异）、②不满足。

**同一道边界的另一端是「生成」**（原 §5.2.3 的 DALL-E / Sora 属输出侧，机制与上面两条相反：不是把外部的原件读进来，而是生产出新的原件）。它改变的不是"原件怎么进来"，而是**原件的来源本身**——过去"原件"的语义是"某个业务过程客观留下的记录"，现在同一张表里会出现"由某个模型版本按提示词生成的记录"，两者在血缘、可复现性与责任归属上都不是一回事。**由此得到的**：合成语料可以在不触碰真实数据的前提下造出评测集与边界样本，这是它与数据侧唯一强相关的用途，也解释了它为什么常常先出现在评测环节、而不是生产链路。**由此付出的**：元数据要多出"来源 = 生成"一档，并记下生成所用的模型版本与提示词摘要，否则这条记录既无法复现也无法审计；更要紧的是它会反向污染评测——评测集与生产分布不再同源之后，离线指标会偏乐观且不报错，于是"这项能力能不能上量"这个判断会失去一个可用的证据来源。**证据与来源**：【公开】生成能力可经模型厂商的正式 API 调用，公开文档与发布说明俱在；某一生成模态标的是正式能力还是预览，按该厂商 API 文档的图像 / 视频生成章节与对应 release note 核（文档位置 + 检索词见本节 §5.4 判定入口一类的图像 / 视频生成条目，年份与命名以官方文档当前版本为准）。以上均为厂商材料，**②不满足**——没有非厂商组织公开"生成物进入生产数据链路"的运行口径。**成熟度**：**L2（生成式内容作为数据资产）**：①满足（生成能力已以正式接口发布、有公开文档与发布说明；模态级差异按 §5.4 的生成侧条目自核）、③部分满足（"提示词 → 生成物"的接口形态随模型换代变动、跨厂商不统一）、②不满足。本节因此只把它记为**一条元数据要求**（登记来源与生成所用的模型版本）与一个 PoC 入口，不当成可以排进路线图的核心能力。

两条路不是竞争关系，而是**约束的产物**，与本章 §3.1 的判法一致：因为强合规行业里最敏感的那部分数据几乎不可能被允许外发，所以"把模型搬到数据旁边"在那里不是优化选项而是唯一可行路径；因为通用场景里数据外发的合规成本很低，所以"把数据接出去"在那里最便宜、也最快拿到最新能力【经验：这条由强合规行业普遍不允许敏感数据外发这一行业实践推得，无单一公开数字】。实践上更常见的是**按数据分级走两条路**：敏感等级高的走仓内执行，其余走外部 API，并在元数据里记下"这条链路的执行位置"，否则同一条看板的两个指标会分别落在两个合规口径里而无人察觉。

#### 5.2.4 优化什么由指标决定：计费单位与评测指标

- **旧做法与它的卡点**：原 §5.3.1（按 Token / 按请求 / 混合计费）与原 §5.1.3（AI 评估指标 / Auto-Evaluation / Continuous Training）也共享同一个卡点：**"优化目标"不是一个可计量的量**。按容量计费时，优化只体现为"更快"、不体现为"更省"，使用者没有动力做，于是优化只能靠治理推（本章 §7.2.2 把它写成"计费单位就是这套系统里唯一被所有人认真优化的那个指标"）；评估侧同理，判断过去靠人工抽查，抽查无法随调用量线性扩展，于是"上线后变差"通常要等新数据分布出现才被发现。
- **AI 改变了什么机制**：**把优化目标从形容词换成一个可计量的单位**——按 token 计费把"上下文长度 × 调用次数"变成账单的自变量；评测指标把"好不好"变成一组可重复的测量。机制上改变的不是能力强弱，而是**激励的归属**：谁的账单与他的写法直接挂钩，谁自己就会优化；谁的评测能重复跑，谁才敢让模型自动迭代。
- **由此得到的**：**因为计费单位与写法之间的因果链可见，所以成本控制从"治理要求"变成"使用者自己的利益"**，不需要外部推动；**因为评测是可重复的测量，"持续训练 / 反馈回灌"第一次有了判据**——只有当评测能把"改好了"与"改坏了"区分开，回灌才不会把噪声灌进权重。这两条是同一个机制在两个面上的表现：**先有可计量的单位，才有可优化的系统**。
- **由此付出的**：**其一，Goodhart 效应**——凡是被当作目标来优化的度量就不再是好度量：账单可以靠把成本挪到别的科目（批量任务、缓存写入）而下降，评测分数可以靠泄漏与过拟合上升，两者都不报错；**其二，评测集与语料必须物理隔离**——否则离线指标被推高而真实泛化不变，团队会顺着错误的信号继续投入算力（本章 §3.2.6 的失效点）；**其三，计费口径本身会变**——缓存、批处理、上下文分档的计价规则各家不同且会调整，把单位成本写进架构假设前先确认口径，并按官方定价页当前版本复核。

四种计费方式对应四种成本函数形状，**它们决定的是"你努力的方向能不能变成钱"**：

| 计费依据 | 成本 ≈ | 用户的优化杠杆 | 平台被激励去优化什么 |
| --- | --- | --- | --- |
| 按容量（传统数仓 / 包年） | 固定 | 无（用量与账单解耦） | 把存储与并发做省，作为卖点 |
| 按扫描量 | f（查了什么，与查了多久无关） | 分区裁剪、列裁剪、减少无效扫描 | 减少扫描量（裁剪、下推、物化） |
| 按计算资源 × 时间 | f（用了多少资源 × 用了多久） | 缩短运行时间、提高并发复用 | 把优化做成默认行为（统计、自动整理） |
| 按 token（输入 + 输出） | f（输入长度 + 输出长度） | 压缩上下文、复用前缀、批处理 | 减少 token 消耗（缓存、批处理计价） |

- **证据与来源**：【公开】按 token 计费与缓存 / 批处理的计价结构见各模型厂商公开定价页（以当前版本为准）；Anthropic 于 2024 年推出 prompt caching 并公开其定价结构（【公开：Anthropic "Prompt caching" 文档与定价页, 2024；请以官方文档当前版本为准】）；OpenAI 于 2024 年推出 Batch API（【公开：OpenAI "Batch API" 文档与定价页, 2024；请以官方文档当前版本为准】）；检索增强生成的自动评测方法有公开论文【公开：Es et al., "RAGAS: Automated Evaluation of Retrieval Augmented Generation", arXiv 2023 起】。以上均属发布方材料，**②不满足**（没有第三方非厂商公开的、带口径与规模的运行记录）。
- **成熟度**：**L2（按量计费的模型 API）**：①满足（计价口径与定价页公开）、③稳定（计费口径长期不变）、②不满足。**L3（AI 评估指标与自动评估）**：①部分满足（有公开基准与评测方法，自动评估本身无产品条目）、③不满足（指标口径各评测各定义）、②不满足。**L3（持续训练与反馈回灌）**：①不满足（无正式产品条目）、③不满足、②不满足。

选型时真正要盯的不是单价，而是**这条成本函数的自变量是不是你能控制的**：如果自变量不在你手里（如包年容量下的用量），你无法通过努力降本，只能靠议价；此时平台侧的自动优化能力就变成了唯一可依赖的优化来源。评测侧的同一条推论是：**如果评测不能区分"改好了"与"改坏了"，那么"持续训练"就只是把线上的噪声固化进权重**。

### 5.3 与本主题既有栈的接口在哪

模型侧与数据侧不是"结合"关系，而是**交接物**关系：谁把什么交给谁、以什么形态穿过边界、失败时谁负责。下表按"谁把什么交给谁"来写；"现状"一列评的是**这个接口今天长什么样**，不是本节 §5.1 表里的方向评级。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 模型 API ↔ 数据平台 | 工具调用：以函数 schema 为契约，模型只拿到返回值，不直接读存储 | 数据侧；工具返回越权数据时没有自动兜底 | 已有能力延伸（需把 schema 登记为资产） |
| Agent ↔ 权限与审计 | 非人主体的身份与授权：谁能调哪个工具、读写分离、调用留痕 | 平台侧；权限模型没有"非人主体"档时，审计答不出"谁读的" | 需新建 |
| 检索 ↔ 数据源与权限 | 交接物 = Top-K + 元数据 + **权限过滤下推**（不是"先捞出来再过滤"） | 检索侧；**返回空优于返回越权或过期结果** | 已有能力的延伸 |
| 多模态原件 ↔ 对象存储与元数据 | 原件引用（不是原件字节）+ 消费记录（被哪个模型版本读过） | 存储侧负责原件持久性；消费记录缺失则无法复现 | 需新建字段 |
| 评测集 ↔ 训练 / 打包管线 | **物理隔离**：评测集与语料的目录不在同一处，重跑之后仍然成立 | 管线侧；泄漏不报错，只让离线指标虚高 | 工程纪律，非新能力（见本章 §3.2.6） |
| 计费单位 ↔ 成本可见性 | 统一签名：单位业务的用量（每次分析 / 每次请求的 token 与资源）跨边界可见 | 使用方；账单归因不细时优化无从下手 | 需新建 |
| 数据市场 ↔ 跨组织共享 | 共享读权限 + 元数据指向；跨出厂商边界用开放格式 + 导出兜底 | 共享方；消费者侧会悄悄复制一份，副本漂移随之出现 | 既有形态，边界由厂商定 |
| 协议 ↔ SDK | 协议可被第三方重新实现；关键集成同时保留"协议实现 + 直连实现" | 集成方；协议演进方向与你的需求分叉时，"等"变成真实成本 | 变化中 |
| 模型版本 ↔ 元数据 / 可复现 | 交接物 = 一次调用的三元组：哪个模型版本 + 读了哪份原件 + 花了多少钱 | 元数据侧；缺任一条，复盘与换代重跑都做不了 | 需新建 |
| 检索 ↔ 生成 | 交接物 = 候选集 + 每条的来源标识（引用）；上下文预算有上限 | 检索与排序侧；引用对不上原件时，生成侧无法自查 | 已有能力的延伸（引用正确性需自建评测） |
| 配额与限流 ↔ 统一入口 | 配额挂在取数入口上，人与机器同口径计量 | 入口侧管总量，调用方管自己的预算 | 已有能力的延伸 |

一句话概括：**AI 在本主题里没有新增调用关系，只改了两件交接物**——工具 schema（在模型与数据之间）和**非人主体的身份**（在平台与权限之间）。前者决定"能做什么"，后者决定"这件事出了事算谁的"；两者都还没有稳定到可以写进三年规划，但**它们都不依赖某个 AI 产品，今天就能定**——这是本节所有接口行里唯一的"现在就能做"。

表里最容易被推给别人的一行是"Agent ↔ 权限与审计"：数据侧会说"权限是平台的事"，平台侧会说"调用方自己控制工具范围"。**判据只有一个动作**：把一次 Agent 取数的完整审计日志拉出来，看它能不能回答"这次调用用的是谁的身份、读了哪些字段、有没有越权返回"。答不出来，缺口就在这道边界上，而不在任何一方的产品文档里。

### 5.4 公开进展与文献

分三类列。论文与第三方案例两类，每条给出会议或文档名 + 年份；判定入口一类，每条给出**文档名（或文档位置）+ 年份 + 检索词**（理由见该类开头）。**宁少勿假**。

**论文**

- Karpukhin et al., "Dense Passage Retrieval for Open-Domain Question Answering", EMNLP 2020——稠密检索取代稀疏匹配的公开依据（对应本节 §5.2.1）。
- Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", NeurIPS 2020——"RAG"形态与名称的来源。
- Yao et al., "ReAct: Synergizing Reasoning and Acting in Language Models", ICLR 2023——"推理与工具交替"的机制来源（对应本节 §5.2.2）。
- Schick et al., "Toolformer: Language Models Can Teach Themselves to Use Tools", NeurIPS 2023——工具调用从提示工程变为模型能力的公开依据。
- Edge et al., "From Local to Global: A Graph RAG Approach to Query-Focused Summarization", arXiv 2024——图增强检索的代表工作；本节把它当作"该研究方向存在"的证据，**不是**产品可用的证据（对应本节 §5.2.1 的 L3 定级）。
- Es et al., "RAGAS: Automated Evaluation of Retrieval Augmented Generation", arXiv 2023 起——检索增强生成的自动评测方法（对应本节 §5.2.4）。

**官方文档 / release note（判定入口）**

**这一类的用法与论文不同**：它们是"去哪儿核、核什么关键词"的入口，不是可以照抄的引用来源——每条给出的是**文档名（或可定位的文档位置）+ 年份 + 检索词**。判定动作本身是可核验的（按下述关键词能直接落到条目），但据此引用任何结论前都应按官方文档当前版本复核。

- **MCP 的规范与版本记录**（Anthropic 于 2024 年 11 月公开开源，规范以日期版本号发布）——**用途是核验协议条目**：规范是否有版本号、是否存在参考实现、客户端与服务器实现清单里有多少非提出方组织。原 §5.2.2 的那一条，判定入口就是这份规范，不要把产品页文案当能力事实。
- **各模型厂商面向开发者的 API 文档**中的工具调用与多模态输入两章（代表性的两份：OpenAI API 文档的 "Function calling" 章节，2023 年起；Anthropic API 文档的 "Tool use" 与 "Vision" 章节，2024 年起；其余厂商按各自文档目录里的同名章节核）——检索词是「工具调用 / tool use / function calling」与「多模态输入 / image input / vision」（正式能力自 2023–2024 年起陆续列为 GA，以文档当前版本为准）；用途是核验是 GA 还是 preview，这一条直接决定本节 §5.2.3 的评级成立与否。
- **模型厂商与框架方的官方仓库 README**（代表性的几份：OpenAI 的 Agents SDK 仓库，2025 年起；LangChain、LlamaIndex 的仓库，2024–2025 年陆续正式发布；另有若干标注为实验性的多智能体项目）——检索词是「README 定位段 / experimental / preview」；**用途是核验"实验性还是正式能力"**：标注实验性、不保证维护的，判定方法就是不放进关键路径。
- **各平台 SQL 语言参考里的仓内 AI 函数条目**（代表性的两条：Snowflake 侧的 Cortex 函数，2023 年公布、2024 年陆续可用；Databricks 侧语言参考里的 "AI functions"，2024 年起；年份与命名以官方文档当前版本为准）——检索词就是函数名（如 `ai_query` 一类，函数命名因平台而异）；看条目本身而不是首页有没有写 AI：函数在哪个执行边界内运行、是否单独计价、标注为正式还是预览。
- **各模型厂商的公开定价页**（代表性的两份：Anthropic 的 "Prompt caching" 文档与定价页，2024 年；OpenAI 的 "Batch API" 文档与定价页，2024 年）——检索词是「缓存 / caching」「批处理 / batch」「上下文分档」；用途是核验单位成本口径，任何以单价为依据的结论都应按当前版本复核，因为计费规则会调整。
- **各模型厂商 API 文档中的图像 / 视频生成章节，及其对应的 release note**（代表性的：OpenAI API 文档的图像生成（Images）章节，2022 年起陆续开放；视频生成一侧的接口命名与可用范围各家不同，按各自文档目录里的同名章节核；年份与命名以官方文档当前版本为准）——检索词是「图像生成 / image generation」「视频生成 / video generation」与「GA / preview / 正式能力」；**用途是核验某一生成模态标的是正式能力还是预览**：条目写正式能力的，该模态的 ① 才算成立；标 preview 的按 preview 判。原 §5.2.3 的 DALL-E / Sora 那一条属这一类，本节 §5.1 表「生成式内容作为数据资产」行与 §5.2.3 段末的定级，判定入口都是这一章。

**第三方生产案例**

- **本节未能给出**可核验的第三方（非厂商）公开生产案例。公开材料里能核到的是三类：① 厂商产品文档（能支撑判据①）；② 发布方与建设方的工程自述——本章 §3、§6、§7 整理的案例均属这一类，按判据正是 L2 定义所指的"厂商自有案例"；③ 论文与公开基准（证明方法可行）。**这个空白本身是结论**：它正是本节 §5.1 表里没有任何一行到达 L1 的直接原因。要填补这个空白，需要的不是更多产品页，而是"非厂商组织公开其在生产中的规模、目标与实测结果"这类带参数的材料。

**怎么用这份清单**：先判断你要核的是"能力"还是"位置"。能力侧看论文与 API 文档（更新快、可核验性高）；位置侧看平台文档与定价页（更新慢，但一条正式条目抵十篇评测博客）。

**如果第②条一直空着，你自己就是那类材料的来源。** 本节表里每一行的升级条件都写成了可观察信号，而其中有一半（召回与引用正确性、工具 schema 变更率、单位业务用量、失败与复核比例）只能由**使用方**产生，不能由卖方产生。做法是把这四个数按固定口径记下来、并允许外部复核：它不解决本节评级的问题，但解决一个更要紧的问题——**你自己的环境里，这些方向到底有没有兑现**。这也是面对任何一份"某产品支持某能力"的说法时唯一可用的自证动作：不看它说什么，看你自己量到什么。

### 5.5 被过度宣传的部分

**「数据市场会让数据变成可流通资产」** —— 实际是**共享的接口形态**（读权限 + 元数据指向）而不是所有权流动。为什么会这样：共享即读把消费者绑在厂商边界内，跨出边界仍要导出，而合规又把最值钱的那部分数据永久划出了可用集合（本章 §3.1 的第四条约束：合规把哪些数据划出可用集合，决定的是"能不能复用"，不是"愿不愿意共享"）。**它什么时候才会成真**：出现由非发起方在正式产品中实现的跨厂商共享协议，并伴随公开可核验的跨组织交易口径——不是一方市场上的商品条目数。

**「多智能体协同能解决复杂数据任务」** —— 实际是把控制流交给概率模型之后，再叠加一层概率模型之间的协商。为什么会这样：方差随参与者数量上升，而"每一步结果可被验证"这个前提在数据任务里很难满足——查询可以验证，语义判断不能（本章 §4.2 给出的引入条件正是这一条）。**它什么时候才会成真**：出现第三方公开的、带方差口径（重复运行的成功率分布与人工复核比例）的评测，而不是一次演示的录屏。

**「Embedding + 向量库就等于企业知识库」** —— 实际是换了"找"的机制，没有换"权限与口径"这两件事。为什么会这样：检索是一个排序问题，召回失败无法由生成补救；权限过滤如果没在检索侧下推，越权内容会先被召回、再被口头要求"不要引用"——这道防线不成立（本节 §5.3 接口表把它写成"返回空优于返回越权"）。**它什么时候才会成真**：跨编码器的分数可校准，且出现带语料规模与召回目标的第三方公开评测。

三条的共同结构：**被宣传的是"能力覆盖"，而决定能不能用的是"边界与成本"**。评审任何一条 AI 前沿方向时先问一句"它把边界画在了哪一侧、成本随什么增长"——把边界画在数据不出去的那一侧、成本随业务量而不是随调用次数增长的方案，通常活得更久。

### 5.6 未来 3–5 年：可证伪的预测

四条预测里，前两条问的是"厂商会不会按成本结构做选择"，后两条问的是"形态会不会变"——前者的命中率通常更高，因为成本约束比技术偏好稳定。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 模型侧与数据侧的相遇点会停在接口层（工具与上下文协议），而不是数据托管 | 模型厂商继续发布协议与参考实现、不提供客户数据托管；非提出方组织的协议实现进入正式产品文档 | 模型厂商开始把客户数据托管做成对外正式能力并作为核心卖点宣传 |
| 「成本可见性」会成为取数与推理系统的一等功能，而不只是治理要求 | 平台把"单位业务的资源用量"做成产品内可查指标；缓存与批处理的计价口径跨厂商可比 | 成本优化仍要回到人工议价与包年容量合同，用量与账单继续解耦 |
| 多智能体不会成为取数主路径，主路径是"单智能体 + 工具 + 步数上限" | 公开材料里的取数系统仍以单智能体编排为主，多智能体停留在实验与特定任务 | 出现第三方公开的、带方差口径的多智能体取数生产运行记录 |
| 数据市场的公开流通量不会成为数据资产化的主路径 | 市场目录条目继续增长，但跨组织交换仍以私有协议与私有共享为主 | 出现被多家非发起方正式产品实现的跨厂商共享协议，且跨组织交易口径可公开核验 |

写这四条时的共同约定：**信号必须是外部可观察的**（规范版本、官方文档条目、第三方公开运行记录），而不是"我觉得会"。凡写不出证伪信号的判断，本节不写——这也是本节不预测"AI 会不会成为数据架构默认选项"的原因：那句话永远正确，因而没有信息量。

四条预测里，第二条最容易被误读成"成本会自动下降"。它说的是**成本会变得可见**，而不是变便宜：可见之后你才知道该不该优化、该优化哪一段，而"要不要为这件事投入人力"仍然由你决定。本章 §3.6 的规模跃迁表里有一条判据与此同源——**成本可见性成为硬要求**这条跃迁在规模完全不变时也会发生，触发它的是计费方式或财务口径的变化，而不是数据量。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 要做企业问答 / 知识库 | 先建检索基线：分块策略、召回评测集、权限过滤下推；把索引当成可重建的派生态 | 观察编码器与索引形态是否稳定（是否出现跨编码器分数可校准的公开方法） | **不要先选框架**；不要为"任意模态互搜 / 统一向量空间"预留 schema；不要把向量库当成唯一检索路径 |
| 已有 Agent 在跑取数 | 把工具 schema 当接口契约登记（名称 / 入参 / 可写性 / Owner / 审计），读写分离，设步数上限与预算 | 观察工具 schema 的变更率与参数校验失败率——它们比成功率更早暴露问题 | 不要引入多智能体；不要把关键集成只做成某家 SDK 的直连实现（保留协议实现一条） |
| 在评估"数据平台要不要买 AI 能力" | 先答一个问题：训练与推理是否真要在同一份数据上做；再核验仓内函数在哪执行、如何计价 | 观察仓内函数的执行位置与计价口径是否被官方文档固定 | 不要为一个"一体化"叙事多买一套平台；不要把"支持 AI"当成选型主轴 |
| 准备做持续训练 / 反馈回灌 | 先把评测集建起来，并与训练语料做到**物理隔离**；先问"评测能不能区分改好与改坏" | 观察是否出现公开的评测协议与带口径的第三方评测 | 不要把厂商榜单当验收；不要在评测集与语料同处的情况下回灌 |
| 成本压力上来了（按量计费） | 把单位业务用量做成可查指标（每次请求的 token、每次分析的资源与扫描量），配上配额 | 观察账单增速与业务量增速是否脱节、缓存命中率是否稳定 | 不要用包年容量把用量与成本解耦之后再谈优化——那是把优化动力关掉 |
| 非文本原件要进链路 | 元数据登记三项：模态与来源、权限范围、被哪个模型版本消费过；检索侧保留 OCR 文本作为可审计产出 | 观察索引体积与单次直读成本，按月复算 | 不要一次性替换文本链路；不要把"原件不出域"当成默认事实 |
| 想做跨组织数据交换 | 先在私有共享里跑通"读权限 + 元数据指向"，并为跨出厂商边界准备开放格式兜底 | 观察是否出现被非发起方产品实现的跨厂商共享协议 | 不要把导出与导入当默认路径；不要在市场里上架还没做过权限分层的数据资产 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的（改 schema、加深绑定、关掉优化动力），而收益依赖一个尚未成立的假设**（协议已普及 / 评测口径已统一 / 跨厂商共享已可用）。等 §5.6 的信号出现再投入，损失的只是时间。

**如果你同时落进好几行**（这是常态），投入顺序按"确定性"排，而不是按"先进程度"排：先做**元数据与身份**（原件消费记录、非人主体、计费口径）——它们不依赖任何 AI 能力的成熟度，且是后面所有行的前提；再做**工具与索引的接口登记**——它们决定后面换模型、换编码器时要不要重写；最后才做**判断侧的能力引入**（更强的模型、更多的智能体）。顺序反了会出现一种很贵的局面：判断侧先上量，元数据与权限没跟上，于是每次效果波动都只能靠加人复核来兜。

**如果你只能做一件事**：把"判断"与"能力"分开记账。能力侧（工具 schema、权限、审计字段、计费口径）是确定性的，今天就能定；判断侧（模型选哪条路、评测能不能过）是概率的，只能靠重复运行来量。这两件事混在一张表里评审，结果一定是"演示很亮、上量就散"：

1. 工具与索引的接口变更，走变更流程与回归测试。
2. 模型的选择与提示词，走评测集与线上复核比例，不走回归测试。
3. 每条链路都要能回答"这次输出用了哪个模型版本、读了哪份原件、花了多少钱"。
4. 评测集与训练语料物理隔离，且重跑之后仍然隔离。

这四条不依赖任何新产品或新协议，今天就能落地。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**判断与能力被拆到了两个地方**——"能做什么"被固定在工具 schema、权限与计价口径这些确定性接口上，"下一步做什么"交给概率模型。因为这一点，本节表里排在最前面的不是任何一个 AI 产品，而是**那些确定性接口**（工具 schema、索引与元数据的形态、非人主体的身份、可计量的单位业务用量）；13 行方向里没有一行到达 L1，缺的都是同一条判据——**没有第三方非厂商公开的生产运行记录**，而这个空白本身就是海外案例材料的构成所决定的结论。它**没有**改变的是：数据平台的结构性选择（统一发生在哪一层、账本的真值与派生在哪、日志与视图谁派生谁，见本章 §3.1 与 §3.2）一条都没有变，AI 只是给这些老问题加了一个新的调用方。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是"判断"还是"能力"？** 改变"能力"的（工具 schema、协议的版本化、仓内执行位置）今天就能定；只改变"判断"的（更强的模型、更多的智能体），要等评测与方差口径。
>
> 最后一条可操作的建议：**把"这次输出用了哪个模型版本、读了哪份原件、花了多少钱"当成第一条 SLO**。它今天就能建，且它同时覆盖合规（谁读过）、复盘（哪个版本变了）与成本（钱花在哪）三件事——这条与本章 §7.2.2 的"计费单位就是被优化的那个指标"是同一个要求的两面。
