## 3. 架构演进（分案例）

### 3.1 先看约束：范式不是选择题，是约束的产物

**案例表把架构讲成了「按场景选一家」，但真实的技术选择是被约束推着走的。** 同一个「要把数据分析做起来」的诉求，在从零起步的公司和背着一堆存量表的公司那里，正确路径完全不同 —— 前者敢用专有存储换体验，后者连「把数据搬一次」的窗口都找不到（本章 §7.1 把这条讲成了「存量约束的差异极大」）。所以要读懂这些案例，先立约束，再看它选了哪种范式。

**第一条约束是「统一发生在哪一层」。** Databricks 把统一放在**格式层**（数据文件加事务日志，任何引擎都能读），Snowflake 把统一放在**引擎与存储层**（客户不直接寻址文件，由服务层管理）。前者买到可迁移，代价是治理面要自己补；后者买到性能与体验，代价是离开平台要导出。这不是先进与落后的差别，是两种成本结构。

**第二条约束是「成本函数长什么样」。** 卖容量的（数仓）、卖扫描量的（按查询计费）、卖 token 的（模型服务），优化动力落在完全不同的地方：卖容量的人有动力把你的存储做省，卖扫描量的人有动力让你少扫，卖 token 的人有动力让你少发 token。**同一个技术动作（比如缓存）在不同成本函数下的紧迫性差一个量级。**

**第三条约束是「事件有几个下游」。** LinkedIn 的一类事件有几十个下游，且下游的读形态各不相同（实时点查 / 离线批 / 特征）；这类系统不能靠同步调用串起来，只能靠追加型日志加派生视图。而一个下游只有一两个的内部系统，引入整套日志骨干是纯负担。

**第四条约束是「合规把哪些数据划出了可用集合」。** Anthropic 与 OpenAI 的资产是模型而不是数据，它们的合规叙事（数据不用于训练、企业版可隔离）越干净，能托管的数据就越少 —— 于是它们在数据侧只能做「定义接口」（MCP 这类协议），而不能做「托管数据」。这不是能力不足，是约束决定的位置（本章 §7.6 把它写成「为了不拥有客户数据，把数据侧的价值让了出去」）。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 存量栈（从零建 / 从既有生态长出） | 敢不敢用专有格式、能不能停机迁移 | 「专有格式是落后」——从零建的公司用专有格式换来的是体验，它没有要迁移的历史包袱 |
| 引擎数量（1 个 / 2–4 个） | 统一该放在格式层还是引擎层 | 「一个平台搞定所有场景」——多引擎是常态（本章 §7.4 按 2–4 个估算），统一引擎会在某类场景上全面落后 |
| 成本函数（按容量 / 按扫描 / 按 token） | 哪些优化会被自动推动、哪些必须靠规范 | 「优化要靠治理推动」——按用量计费时，优化的收益直接落在使用者身上，不需要治理推 |
| 事件下游数量与读形态 | 用同步调用还是追加日志 + 派生视图 | 「消息队列就是异步的 RPC」——把它当 RPC 用，会丢掉「可重放重建」这一唯一的衍生价值 |
| 合规强度（数据可否用于训练、能否跨边界） | 数据能不能复用、模型能不能搬 | 「数据越多模型越好」——合规把一部分数据从可用集合里永久划走，模型侧只能靠接口而非托管 |
| 商业模式（卖容量 / 卖平台 / 卖 token） | 谁的差异化能被长期守住 | 「估值高的路线更值得学」——跨问题域比估值，比出来的是问题域差异，不是做法差异 |
| 团队技能与运维能力 | 统一该自建还是交给托管 | 「自建更可控」——自建的收益要能摊平内核专家成本，摊不平就只会得到一个更贵、更慢的自建版 |

**表里「商业模式」与「团队技能」两行是本节最想提醒的：这些案例不在同一个问题域里。** Databricks 与 Snowflake 回答的是「用什么形态交付分析能力」，Netflix 回答的是「把内部解决的格式问题变成行业规范」，Anthropic 与 OpenAI 回答的是「模型怎么接外部数据与工具」。把它们的估值、客户数并列排名，排出来的是问题域之间的差异；本节因此按**机制**而非名次来讲每个范式 —— 每个范式先给约束，再给结构，最后给它在什么条件下失效。

### 3.2 模式逐个拆解（核心节）

下面 8 个范式按「它统一在哪一层」排列：从格式层（3.2.1）、引擎与存储层（3.2.2）、账本与记录层（3.2.3）、日志与派生层（3.2.4）、接口与协议层（3.2.5、3.2.6）、结构层（3.2.7）、数据结构本身（3.2.8）。每个范式严格包含六件事：被什么约束逼出来、结构、为什么有效、代价、失效点、真实使用。**判断一个范式是否适合你，第一问永远是「它统一的那一层，我能不能接受被它绑定」** —— 能接受则该层的约束恰好是你的优势，不能接受则它每一点体验优势都会在换方向时变成迁移成本。

#### 3.2.1 Databricks：开放表格式（Lakehouse 的统一层）

- **被什么约束逼出来**：数据已经在对象存储上（便宜、近乎无限），但对象存储没有事务与一致快照；同时客户不接受把数据锁进某一家引擎的内部元数据。
- **结构**：「表」不再定义在引擎内部，而是定义成**数据文件清单 + 事务日志**，日志本身也是对象存储上的普通文件。

  ```text
  Delta Lake 型表 = 开放列式数据文件 + 追加写的事务日志
    /table/_delta_log/00000000000000000000.json   ← 一次提交一条
    /table/_delta_log/00000000000000000001.json
    /table/part-0000-xxxxxxxx.parquet             ← 数据文件，只追加
    日志条目：{ add: [文件], remove: [文件], metaData: schema, commitInfo }
  → 读方只需实现一件事：按日志拼出某个版本的快照
  → 换引擎 = 换「读日志的实现」，数据文件一个字节都不动
  → 删除/更新 = 追加一条日志 + 写新文件（旧文件变墓碑，靠压缩回收）
  ```

- **为什么这样设计有效**：因为「表是什么」被下沉成一份可被任意实现读取的协议，所以 Spark / SQL 引擎 / 流式作业 / 训练任务可以在同一份文件上各自读取 —— 数据不搬家，多引擎共存的成本从「做一次集成工程」降到「实现一个协议」。
- **代价**：写入放大是结构性的（每次提交都要写日志，更新与删除留下墓碑与旧文件，必须靠定期压缩回收）；元数据操作本身会成为一个独立的成本项（快照规划要先读日志再列文件）；**表格式只统一了「读」**，权限、血缘与审计仍然留在各家自己的治理产品里。
- **失效点**：当写入频率高而压缩跟不上时，「任意引擎都能读」的优点会反转为「谁都读得慢」——因为快照规划阶段的元数据成本随日志条目与文件数增长，最终超过实际扫描数据的成本，此时瓶颈不在计算也不在存储，而在「先搞清楚要读哪些文件」这一步。
- **真实使用**：Delta Lake 于 2019 年由 Databricks 开源（【公开：Databricks 公开公告, 2019】）；Iceberg 于 2018 年由 Netflix 开源、2020 年成为 Apache 顶级项目（【公开：Apache Software Foundation, 2020】）。湖仓形态的定型时间本节按 2019–2020 年写（【推算】：以 2019 年 Delta Lake 开源为起点，湖仓一体的论文与产品叙事集中在 2020 年前后，推导过程见本章 §7.1 的时间窗说明）。判断某个平台是否真的统一在格式层，方法很直接：**看它的表能不能被一个不是它家产品的引擎直接读**（【经验】核验方法）。**同一范式在 Databricks 产品线上的其余部分**：Databricks SQL 是该格式层之上的 SQL 数仓入口、Databricks AI Functions 是把模型调用做成仓内函数，两者分别把这层统一延伸到查询侧与推理侧；MLflow（模型生命周期）、Feature Store（特征）、Dolly（开源模型）是把「不换平台」的思路延伸到模型侧的能力；MosaicML 收购发生在 2023 年（本书按公开公告的年份写，**不以「30 亿美元」「2024 年」这类常见转述为准**，金额与时间请以官方公告为准）；Unity Catalog 承担前述「表格式不统一治理」留下的那一层；「AI Platform」（2023 年起步、2024 年全面升级）与 2025 年的「Agent Platform」（全面 AI Native）延续的是同一条思路 —— 把「不换平台」的边界从数据侧推到模型与应用侧（【公开：Databricks 各次公开公告, 2019–2025】）。

#### 3.2.2 Snowflake：存算分离 + 共享即读

- **被什么约束逼出来**：存储的增长是持续而廉价的，计算的需求是脉冲式的；跨组织交换数据时，如果每个消费者都要一份副本，数据量乘以组织数就不可行。
- **结构**：三层各自独立扩展，客户不直接寻址文件；共享的也是「读权限与元数据指向」，而不是一份复制出来的数据。

  ```text
  存储层：对象存储上的列式文件（由服务层管理）
  计算层：虚拟仓库（0 → N 瞬时起停，按秒计费，仓与仓之间互不争抢）
  服务层：元数据、事务、优化器、访问控制
        │ 计算每次向存储层拉取所需列与分区（本地缓存 + 结果缓存）
  共享：消费者拿到「读权限 + 元数据指向」→ 读到的仍是生产者的当前数据
  → 不复制即可共享；换算引擎 = 数据要走出产品边界
  ```

- **为什么这样设计有效**：因为计算节点不持有数据、事务与元数据集中在服务层，所以计算可以按查询瞬时扩缩、多个使用方之间靠「各自的仓库」隔离而不是靠各自的数据副本 —— 隔离与扩缩这两个动作同时被简化了。
- **代价**：每次计算都要跨层取数，本地缓存与结果缓存因此从「优化项」变成「可用性前提」；成本与查询写法直接挂钩（仓库规模 × 运行秒数 + 扫描量），成本控制的责任被推给使用方；专有存储格式意味着一旦要跨出平台，必须导出。
- **失效点**：当工作负载变成「大量小点查 + 高并发」时，「弹性」的优点反转为固定开销劣势 —— 因为仓库启动与远端取数是按次摊不薄的固定成本，单次小查询的收益抵不过这两层开销，此时按常驻与按用量计费的直觉会被账单推翻。
- **真实使用**：2020 年 9 月上市，上市首日市值 700 亿美元量级（【公开：Snowflake IPO 上市首日行情, 2020-09】，本章 §7.4 同口径）；2024 年推出对开放表格式的支持（【公开：Snowflake 公开材料, 2024】）—— 本章 §7.6 把这条读成「专有统一的代价已被自己承认」。**其余能力都挂在同一套结构上**：Snowpark 是计算层上的多语言编程入口，「Data Cloud」是这套三层结构的对外称呼（2024 年「AI Data Cloud 战略」、2025 年「AI 全栈 + Agent Platform」，即同一个称呼向 AI 侧的延伸），Data Marketplace 是共享层的公开市场形态，Cortex 是仓内 AI 函数，Streamlit 是应用开发层，多云（三大云厂商）是「存储与计算解耦」带来的部署自由度；本节不再逐条展开，因为它们的机制都是 3.2.2 那三层（【公开：Snowflake 官方文档与历次公开材料，以官方当前版本为准】）。

#### 3.2.3 Stripe：追加型账本 + 对账（财务一致性）

- **被什么约束逼出来**：资金状态的每一次变化都要可审计、可复现；外部系统（银行、卡组织）随时可能异步对不平；重试与重复请求是常态，不是异常。
- **结构**：账本只追加不修改，「纠正一笔」被表示为「追加一笔反向分录」，且借贷恒等是一条数据库可校验的不变量。

  ```sql
  -- 追加型账本：不 UPDATE 历史，纠错靠反向分录
  CREATE TABLE ledger_entry (
    entry_id     BIGSERIAL PRIMARY KEY,
    txn_id       UUID        NOT NULL,   -- 一笔业务的两条分录共享它
    account_id   UUID        NOT NULL,
    direction    SMALLINT    NOT NULL,   -- +1 一方向 / -1 另一方向
    amount_minor BIGINT      NOT NULL,   -- 以最小货币单位存整数，不用浮点
    currency     CHAR(3)     NOT NULL,
    occurred_at  TIMESTAMPTZ NOT NULL,
    idem_key     TEXT        NOT NULL,
    CONSTRAINT one_side UNIQUE (txn_id, account_id, direction),
    CONSTRAINT one_idem UNIQUE (idem_key)     -- 重试不会重复入账
  );
  -- 不变量：SELECT sum(direction*amount_minor) FROM ledger_entry WHERE txn_id=? 恒为 0
  -- 余额靠重放/聚合得到，不靠 UPDATE 维护
  ```

- **为什么这样设计有效**：因为「修改」被表示成「追加」，所以任意时点的余额都能由历史重放得到，审计对象是一份只增不改的记录；因为借贷恒等是可被 SQL 直接校验的约束，所以错误会在对账时被机器抓住，而不是等报表被人质疑时才暴露。
- **代价**：存储与写入随分录数增长（一笔业务至少两条，还有调整与对账分录）；「当前余额」要么聚合要么维护物化视图，于是多出一层必须与账本保持一致性的派生数据；幂等键与唯一约束是必需品，重试、乱序、重复投递这三件事在资金链路上都不允许靠人工兜。
- **失效点**：当团队为了「修一个数」直接 UPDATE 历史分录时，「可重放」的优点反转为不可追溯 —— 因为余额仍然是那个数，但支撑它的分录已经被改写，「这个数怎么来的」再也答不出来；对账会把差异暴露在「金额对得上、依据说不清」这种最难处理的位置上。
- **真实使用**：幂等键是支付接口的公开标准做法，Stripe 的 API 文档中有专门的 Idempotency 章节（【公开：Stripe 官方 API 文档 Idempotency 章节，以官方文档当前版本为准】）；复式记账与只追加账本是记账领域的通行机制（【经验】），判断某个系统是否真的这么做的办法是看它的余额是算出来的还是存下来的。**数据栈共五项：业务库（Postgres + 自研）、数据仓库（自研 + Snowflake / BigQuery）、实时计算（Kafka + Flink）、BI（自研 + Looker）与 ML（自研平台）**。其中业务库承载账本本身（真值所在），其余四项都挂在账本的派生侧：它们读的是账本派生出来的副本，因此这一层可以整体重算，而重算不会反过来改写账本 —— 这条演进线是 2011–2015 年的「Ruby + Postgres 起步」、2016–2018 年的「数据栈系统化（Hive + Spark + Presto）」、2019–2022 年的「实时化（Flink + Kafka）」与 2023 年起的「AI Native」，其中 Hive + Spark + Presto 就是这批派生组件的前身。**产品线（Payments / Billing / Connect / Sigma / Tax / Atlas）与「所有能力 API 化、开发者文档优先」这两条**，在这里是同一条机制的两种表述：账本型结构只有被外部以幂等接口调用时才成立，而「API 化 + 文档优先」正是把幂等与重试约定暴露给调用方的方式（【经验】：这条因果是从上述接口约定推出的，产品清单以官方文档为准）。

#### 3.2.4 LinkedIn：追加型日志骨干 + 派生索引

- **被什么约束逼出来**：一类事件有几十个下游，下游的读形态互不相同（实时点查 / 离线批 / 图谱 / 特征）；若用同步调用串联，生产者会被所有消费者的可用性绑住。
- **结构**：日志是唯一事实来源、只追加；每个消费者维护自己的物化视图，视图坏了可以从日志重放重建。

  ```text
  业务库（Espresso / Oracle / MySQL）──CDC──► 日志（按 key 分区）
                                                  │
        ┌───────────────┬───────────────┬─────────┴──────────┐
        ▼               ▼               ▼                    ▼
   流处理（Samza）  实时 OLAP（Pinot）  离线仓（Hive/Spark）  特征/模型
  各自维护视图：新增消费者不动上游；视图可重放重建
  分区键决定顺序边界：同 key 内有序，跨 key 无序
  → 键选错 = 单分区热点；并发上限由分区数决定，不由机器数决定
  ```

- **为什么这样设计有效**：因为日志只追加且是唯一事实来源，所以新增一类消费者不需要改上游，派生视图可以在任意位点重放重建；因为每个消费者读自己维护的视图，所以下游故障不会反向传播 —— 用**读放大与存储冗余**换来了上下游的解耦。
- **代价**：端到端延迟是「生产 → 日志持久化 → 消费 → 派生写入」的累加，单跳同步调用的延迟优势被明确放弃；派生索引的存储与写入量随消费者数量倍增；可重放窗口由日志保留期决定，保留期一旦短于重建所需时间，「可重放」就只剩口号。
- **失效点**：当消费端把「位点已提交」当作「数据已处理」（先提交后处理，或把派生写入做成异步且不重试）时，「可重放」的优点反转为不可恢复 —— 因为丢失的不是日志本身而是「处理到哪」的记录，重放无法区分哪些派生数据是缺的，最终只能全量重建一次并承担重复写入的代价。
- **真实使用**：Kafka 于 2011 年由 LinkedIn 开源、2012 年起进入 Apache 项目体系（【公开：Apache Kafka 项目页与 Apache 软件基金会项目记录，2011 年开源、2012 年毕业为顶级项目】）；Samza、Pinot、Helix 与 Voldemort 亦出自 LinkedIn，各自的开源与毕业年份可按「项目名 + 官方站点」自行核验（【经验】）。此处需更正一处常见归属错误：**Apache Avro 属于 Apache Hadoop 生态项目，并非 LinkedIn 出品**（可按 Apache Avro 项目页核验）。LinkedIn 的会员规模在十亿量级（【公开：LinkedIn 官方公布的会员数, 2023】），2016 年由 Microsoft 完成收购（【公开：收购双方公告, 2016】）；2016–2020 这段是「被 Microsoft 收购后深度整合 Azure」—— 云平台层是与本节日志骨干平行的一条整合线，两者不是同一个统一层。**开源贡献里，Kafka / Samza / Pinot / Helix / Project Voldemort 都属这一范式的产物**（日志、流处理、实时 OLAP、集群协调、KV 存储各占一层）；消费这一日志的下游是 Profile、Feed、Recruiter、Sales Navigator 与 Learning，它们各自维护自己的派生视图，且读形态互不相同（Feed 要特征与近实时视图，图谱与 Recruiter / Sales Navigator 要关系检索视图，Learning 要行为统计视图），因此不能共用一份表；数据架构（业务库 Espresso / Oracle / MySQL，离线 Hadoop + Hive + Spark，实时 Kafka + Samza + Flink，图谱与自研 ML 平台）正对应上图日志右侧的那几个分支（【经验】：具体范围以各项目官方站点与 LinkedIn 工程材料为准）。

#### 3.2.5 Anthropic：训练数据分层 + 推理前缀复用

- **被什么约束逼出来**：训练侧的数据可得性被合规切走一块（用户数据默认不用于训练、企业版可隔离），推理侧的成本随上下文长度增长；两条边的约束方向相反 —— 一边想要更多数据，一边想要更少计算。
- **结构**：训练侧按来源分层登记，服务侧按「不变的前缀 / 可变的后缀」切分请求。

  ```text
  训练侧（离线，可回溯）             服务侧（在线，按 token 计费）
  ├ 公开语料（登记来源与许可）        ├ 前缀缓存：同一前缀只预填充一次
  ├ 合成数据（标注生成方式）          │   缓存键 = 前缀字节的精确匹配
  ├ 用户反馈（默认不入训练）          ├ 工具调用（外部能力不写进权重）
  └ 红队 / 安全数据（单独隔离）        └ 批处理 / 流式：延迟与吞吐的取舍
  ────────────────────────────────────────────────
  共同要求：每条数据、每次请求都要能回答「它从哪来、能不能用、算了多少钱」
  ```

- **为什么这样设计有效**：因为缓存键是提示词前缀的精确匹配，所以把稳定内容（系统提示、工具定义、长文档）放在前面、把易变内容放在后面，就能把「每次重算整段上下文」变成「只算增量」—— 成本与首字延迟沿同一个机制一起下降。
- **代价**：缓存有写入与读取两种计价、有存活窗口，缓存断点必须由调用方自己管理（把它当成平台的隐形优化会算错账）；训练侧的分层登记意味着同一批数据不能跨用途随意复用，去重与来源登记成为需要长期维护的资产，而不是一次性的清洗脚本。
- **失效点**：当前缀被易变内容污染（时间戳、随机 ID、每次不同的用户画像被放在最前面）时，前缀复用的优点直接归零 —— 因为前缀一变缓存键就变，请求退回全量预填充；这类失效不报错、不掉成功率，只体现在账单与首字延迟上，因此最难被监控发现。
- **真实使用**：MCP（Model Context Protocol）由 Anthropic 于 2024 年公开并开源，2025 年被另一家模型厂商采纳（【公开：OpenAI 公开公告, 2025】，本章 §7.2.4 引用同一事件）；提示词缓存是官方 API 的公开能力（【公开：Anthropic 官方文档，以当前版本为准】）。融资轮估值：2024 年约 184 亿美元、2025 年约 615 亿美元（【公开：各轮融资公开材料, 2024 / 2025】，与本章 §7.4 同口径）。**其余条目都服务于上面这两侧约束**：Constitutional AI 属训练侧（用成文原则生成与筛选安全训练数据，正是本范式训练侧分层里「红队 / 安全数据」那一层）；Claude 的模型家族（家族名是 Haiku / Sonnet / Opus；迭代路径是 2021–2022 年的 Claude 1.0 训练、2023 年的 Claude 2 与企业版、2024 年的 Claude 3 系列与 3.5 Sonnet、2025 年的 Claude 4 / 4.5 与多模态 Agent 能力）、三种交付形态（Claude.ai / Claude API / Claude Enterprise，即同一能力的对话产品、开发者接口与企业版，其中企业版正是「企业版可隔离」那条合规约束的产品化）与工具链路（Claude Code 把工具调用做成面向开发者的客户端形态，Computer Use 让模型直接操作外部界面）属服务侧 —— 本节把它们归入两侧而不是并列罗列，因为它们的约束是同一对（【经验】：归类依据为官方文档的功能描述，具体能力以当前版本为准）。

#### 3.2.6 OpenAI：离线打包管线 + 在线服务分档

- **被什么约束逼出来**：训练是「跑几天、失败即重来」的同步作业，集群规模在作业开始前就固定；推理是请求量大、延迟敏感、成本随 token 线性增长 —— 两条链路必须按不同的目标优化。
- **结构**：离线侧把样本预先打包成定长分片，在线侧按请求路由到不同档位的模型。

  ```text
  离线（吞吐优先）                          在线（延迟与成本优先）
  原始语料 → 清洗 → 去重 → 分词 → 打包分片     请求 → 路由 → 模型档位
       └ 分片定长 → 每步计算量恒定               ├ 小模型 / 大模型分流
  检查点（故障续跑）→ 评测集 → 人工评审          ├ 前缀缓存 / 批处理
  ────────────────────────────────────────────────
  关键顺序：去重与「评测集物理隔离」必须在打包之前完成
            打包之后再发现泄漏，代价是重跑整条管线
  ```

- **为什么这样设计有效**：因为样本被提前打包成定长分片，所以每个训练步的计算量恒定、并行效率不随样本长度抖动，故障续跑也与样本边界对齐；因为服务侧按请求路由到不同档位，所以成本与延迟能按场景分档，而不是让所有请求都付最大模型的代价。
- **代价**：清洗、去重、分词是与训练同量级的工程投入，且必须可重跑（改一次配比就要重新打包整个语料）；多档服务意味着多条部署与评测路径，需要长期维护「哪类请求该走哪档」的判据，判据本身也会过期。
- **失效点**：当评测集与训练语料没有做到物理隔离时，「高吞吐」的优点反转为虚假进展 —— 因为重复与泄漏样本会把离线指标推高而真实泛化不变，团队会顺着错误的信号继续投入算力，直到线上效果与离线指标脱节才被发现，此时已消耗的算力无法回收。
- **真实使用**：演进路径是 2015–2019 年的 GPT-1 / GPT-2、2020 年的 GPT-3、2022 年的 ChatGPT、2023 年的 GPT-4、2024 年的 GPT-4o 与 o1、2025 年的 o3 / o4 与 Agent SDK；推理模型（o 系列）自 2024 年起公开；智能体开发能力以开源实验项目 Swarm 与后续的官方 Agent SDK 两种形态并存（【公开：OpenAI 官方公告与官方仓库，以当前版本为准】）。2024 年融资轮的投后估值约 1570 亿美元（【公开：融资轮公开材料, 2024】，本章 §7.4 同口径）。判断某条训练管线是否真的做到「评测集隔离」，方法同样是可执行的：**去查评测集的物理位置，它是否与训练语料的打包目录不在同一处**（【经验】核验方法）。**模型与产品（GPT 系列、ChatGPT、OpenAI API、DALL-E、Sora、Whisper、Agent SDK / Swarm、Custom GPTs）是这条管线在不同模态与形态上的外延**：多模态产品（DALL-E / Sora / Whisper）只是把打包与分片的对象从文本拓展到其他模态，ChatGPT、OpenAI API 与 Custom GPTs 属在线侧的分档、路由与接入层，Agent SDK / Swarm 则是把在线侧的路由与工具调用单独工具化 —— 换句话说，它们不影响 3.2.6 的两条约束，只是把两侧各自复制了多份（【经验】：归类依据为官方公告的功能描述，以当前版本为准）。

#### 3.2.7 Slack / Notion：多租户分片 + 派生建模

- **被什么约束逼出来**：租户数量巨大而单租户数据不大，且租户之间不能互相影响；协作类产品的写入是高频细粒度操作，不是批式事实，在线库与分析库要回答的问题本来就不同。
- **结构**：在线侧按租户分片，分析侧从在线库派生一份独立的、为此重算过的结构。

  ```text
  Slack 式：分片键 = 租户
    应用 ──► 分片路由（keyspace / vindex 一层）──► MySQL 分片 1..N
    单租户读写只落一个分片；跨分片查询必须靠有索引的少数维度，否则退化成扇出
  Notion 式：在线库 → CDC → 仓 → 分层建模
    Postgres（行式，OLTP） ─CDC─► 对象存储 ─装载─► 仓（列式）
      └ 仓内分层转换（dbt 一类工程）：原始 → 清洗 → 维度 / 事实 → 指标
  关键：两层用两套表结构解决两个问题，不做「一份 schema 两头用」
  ```

- **为什么这样设计有效**：因为分片键就是租户，所以单租户的读写只落在一个分片上，租户间的资源干扰被物理隔离；因为仓内结构是对分析需求重新设计的，所以指标口径的演化不会反过来约束在线库的 schema —— **两个目标被拆到两套结构上，各自只付各自的代价**。
- **代价**：跨租户分析必须在仓里重做一遍（链路维护 + 新鲜度延迟 + 一次装载的可重跑性）；分片带来的跨片查询与再均衡是长期运维负担；同一份业务事实存在两个定义，口径不一致时没有任何机制会自动发现它。
- **失效点**：当租户之间数据量差距悬殊（少数超大租户）时，「按租户分片」的均匀性假设失效 —— 因为单个分片装不下一个大租户的数据，热点分片的分裂与迁移必须在线上完成，而迁移期的双写与一致性校验正是这类系统最容易出错的位置。
- **真实使用**：Slack 于 2021 年由 Salesforce 完成收购（【公开：收购双方公告, 2020–2021】），其在线业务库以 MySQL 分片为公开叙述的基础，分片中间件（Vitess 一类）是 SaaS 领域的通行做法（【经验】，具体实现请以官方工程材料为准）。Notion 在 2021 年融资轮中的估值约 100 亿美元（【公开：融资轮公开材料, 2021】），数据栈以「在线库 + 云数仓 + 转换工程」为常见组合（【经验】）。**数据栈与上图两层结构一一对应**：Slack 是 Vitess（MySQL 分片）+ Snowflake + Kafka + Flink，Notion 是 Postgres + dbt + Snowflake —— 第一项落在在线库一侧，云数仓与 dbt 是分析侧，Kafka + Flink 是两者之间的同步与派生链路。**AI 能力（Notion AI 与 Slack 的 AI 功能，其后端点名 OpenAI 与 Claude 两家）在这套结构里是仓外的一层**：它们以外部模型 API 的形式接入，因此不改变上面两条约束，只多出一条要求 —— 被送往外部模型的内容要先过一遍权限与合规判断（【经验】：产品侧通常不披露具体的模型路由，具体实现请以官方文档为准）。

#### 3.2.8 Figma：CRDT 协作模型与它的落仓代价

- **被什么约束逼出来**：多人同时编辑同一份文档，网络延迟与乱序不可消除，而所有人最终必须看到一致的结果；同时分析侧还要能回答「谁在什么时候改了什么」。
- **结构**：把「冲突合并」从运行时决策变成数据结构的性质；编辑操作可重放，落仓的是操作流与快照两条。

  ```text
  CRDT：合并规则写进数据类型本身，不依赖到达顺序
    客户端 A 的编辑 ─┐（带唯一 ID 与因果前提）
    客户端 B 的编辑 ─┴─► 服务端按数学规则合并，无需仲裁
      → 任意顺序到达、任意次数重放，收敛到同一结果
  落仓：操作日志 + 周期性快照 ──► 仓（用于分析、审计、复盘）
  成本结构：操作日志的体积随「编辑次数」增长，不随「文档数」增长
  ```

- **为什么这样设计有效**：因为合并规则不依赖到达顺序，所以服务端不必为并发编辑做仲裁，客户端可以离线继续编辑并在重连后安全合并 —— 这是「实时协作」能成立的前提；因为操作流可重放，分析侧能在事后重建「文档是怎么变成现在这样的」。
- **代价**：操作日志的写入量与体积远大于最终文档（存储成本随编辑次数增长）；日志与快照必须一起维护 —— 只留日志则重放太慢，只留快照则过程丢失；合并粒度决定并发上限，粒度越细元数据越多。
- **失效点**：当出现「回滚到某一历史版本」「按权限裁剪历史」「删除某个用户贡献的全部内容」这类诉求时，收敛性的优点反转为额外工程 —— 因为 CRDT 保证的是「合并后一致」，不是「状态可寻址」或「历史可裁剪」，任何按时间点取状态或按人裁剪历史的能力，都必须在日志与快照之上另建一层。
- **真实使用**：Adobe 与 Figma 的收购协议于 2022 年公布、2023 年 12 月终止（【公开：双方公告, 2022–2023】）；CRDT 与 OT 是协作编辑的两条主流技术路线：CRDT 的定义性文献是 Shapiro 等的《Conflict-free Replicated Data Types》（2011），公开的开源实现有 Yjs 与 Automerge，Figma 也用一篇工程博客（《How Figma's multiplayer technology works》, 2019）公开说明过自己在两条路线上的取舍；数据栈（业务库 Postgres + 自研 CRDT、协作层 CRDT + OT、分析侧 Snowflake）也分三层落在上图里：协作层产出操作流与快照，分析侧接住这批落仓数据（【公开：Shapiro 等《Conflict-free Replicated Data Types》, 2011；Yjs / Automerge 项目仓库；Figma 工程博客, 2019】——论文与仓库可按标题与项目名自行检索核验）。

### 3.3 模式选择决策表

| 约束组合 | 推荐范式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 存量在对象存储上、未来会出现第二个引擎 | 开放表格式（3.2.1） | 不用专有统一：一旦有第二引擎，要么复制一份要么重写数据 | 两三年内是否会出现第二种计算引擎 |
| 分析注定单引擎、团队没有内核专家 | 托管 / 存算分离（3.2.2） | 不用开放格式：没有第二引擎时，格式开放的收益兑现不了，自建成本却要照付 | 是否有长期自建引擎的人力 |
| 需要跨组织交换数据 | 共享即读（3.2.2）+ 格式中立兜底 | 不用「导出再导入」：副本一旦存在就要维护同步与「哪一份对」 | 交换边界是否跨出单一厂商 |
| 一类事件有几十个下游、读形态各异 | 追加型日志 + 派生索引（3.2.4） | 不用同步调用：生产者会被所有消费者的可用性绑住 | 下游数量与是否需要重放重建 |
| 资金 / 账务 / 权益类状态 | 追加型账本 + 对账（3.2.3） | 不用「UPDATE 改数」：余额算得出来，但依据再也说不清 | 余额是算出来的还是存下来的 |
| 训练与推理同时存在 | 离线打包 + 在线分档（3.2.6） | 不用一套流水线兼顾：吞吐优先与延迟优先的目标互相冲突 | 评测集是否与训练语料物理隔离 |
| 合规把部分数据划出可用集合、推理成本随上下文线性增长 | 训练数据分层 + 推理前缀复用（3.2.5） | 不用「先攒数据再说」：被合规划走的数据攒不回来，只能靠来源登记与接口解决 | 每条数据能否回答「从哪来、能不能用、算了多少钱」 |
| 多租户 SaaS、单租户数据量小 | 按租户分片 + 派生建模（3.2.7） | 不用单库多租户：租户间会互相影响，且分析会拖慢在线 | 租户间数据量是否悬殊 |
| 多人实时协作编辑 | CRDT / OT（3.2.8） | 不用「锁 + 顺序提交」：延迟与乱序不可消除，仲裁点会变成单点 | 是否需要历史可裁剪（要则另建一层） |

**本主题下最常被误选的一对，是「开放表格式」与「专有统一」。** 两者都被宣传成「一体化数据平台」，区别只在统一的位置：格式层（可迁移、治理要自己补）与引擎层（性能与体验更好、离开要导出）。误选的后果很具体：一个团队按「少一个引擎、少一份运维」选定了引擎层统一，两三年后业务上出现第二种计算需求（流处理、特征、向量检索），此时数据要么复制一份到自己的存储上（副本漂移与「哪一份对」的问题同时出现），要么停机重写 —— 而这笔代价在选型那天被完整地记在了「未来再说」一栏里。本章 §7.6 把它写成一句更短的话：照搬一个案例而不照搬它的代价，是照搬失败最常见的方式。

**这一对误选有一个极早的预警信号：盘点时把「今天的引擎数」当成了「三年后的引擎数」。** 引擎数量是这条决策里唯一真正起作用的变量，而它在选型当天几乎总是被低估 —— 因为第二种引擎的动因（流处理、特征、向量检索、跨组织交换）通常来自业务侧的新诉求，而选型会议上的讨论对象是当下的报表与作业。**可操作的判据是：把「未来三年可能出现的新计算形态」列一遍（不是猜技术，是猜需求），只要其中任何一条需要读同一份数据，就说明统一必须在格式层。**

### 3.4 组合模式：真实系统不会只用一种

**组合 A：开放表格式 + 多引擎 + 统一治理面（3.2.1 + 3.2.4 的实时派生）。** 格式层负责可迁移，各引擎负责自己擅长的计算模式，治理面（权限、血缘、审计）负责合规。职责边界是：**谁都不许把治理规则写进引擎**，否则第二个引擎一接入就有第二套权限。运维代价是治理面成为所有引擎的共同关键路径，它的可用性要求高于任一引擎；适合已经出现或即将出现第二种引擎的组织。

**组合 B：存算分离 + 共享即读 + 按用量计费（3.2.2 + 3.2.3 的对账）。** 由平台方承担容量、调优与弹性，使用方只负责建表与写查询；账务类数据在应用侧仍走追加型账本，平台侧只做副本与聚合。职责边界是：**账本的真值在应用侧，仓里的是派生值**，两者不一致时以账本为准。代价是用量与账单强相关，必须配配额与用量监控，否则成本会在无人察觉时翻倍；适合团队里没有内核专家、分析需求还在释放阶段的组织。

**组合 C：追加型日志 + 多形态派生 + 分层数据登记（3.2.4 + 3.2.5）。** 日志负责事实与重放，派生视图负责各自读形态，数据分层登记负责回答「这条数据能不能用」。职责边界是：**重放窗口与保留期必须由下游的重建时间倒推**，而不是由存储预算单独决定。代价是存储与写入的倍数放大（每个下游一份），以及一份必须长期维护的元数据（来源、口径、保留期）；适合事件型业务、下游形态多样、且对「可重放重建」有硬要求的系统。

三个组合的共同点是：**它们都把「最容易变的那一层」留在外面** —— 组合 A 把引擎留在外面，组合 B 把容量与调优留在平台侧，组合 C 把读形态留在各派生视图里。反过来，一旦把易变的东西放进被统一的那一层（把治理规则写进引擎、把业务口径写进平台、把读形态写进日志），下一次变化就必须整体迁移，而不是局部替换。这是判断一个组合会不会在两三年内变成负担的最快方法：**问自己「哪一层会先变」，再看它是否正好是被绑定的那一层。**

### 3.5 反模式与失效分析

下表把本节各范式在生产中最容易踩的失效收在一起 —— 但它**不与八个范式一一对应**：同一条失效常横跨几个范式（「把一体化平台当买一件产品」来自 3.2.1 与 3.2.2，「把数据复制到模型侧」与「提示词前缀被易变内容污染」来自 3.2.5），最后一条则是跨范式的选型方法失效；而账本（3.2.3）、离线打包（3.2.6）、按租户分片（3.2.7）与 CRDT（3.2.8）的失效形态已写在各自范式的「失效点」条里，不在下表重复。**判断一条反模式是否已经发生，靠的不是感受而是一个可查证的动作** —— 第二列给的就是这个动作（去数、去看、去问一个能被回答的问题），而不是「架构混乱」这类无法证伪的形容词。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 1. 把「一体化平台」当「买一件产品」 | 评估表里列的是功能清单，没有一列写「我实际会用到哪几件」 | 功能边际价值随实际使用比例迅速衰减，代价变成学习成本与运维面 | 一体化叙事在采购阶段最好表达，使用比例要到上线半年后才看得见 | 以「实际会用到的能力」而非「一共有多少件」评估；列一份明确不用的清单 |
| 2. 为跨组织共享把存储做成专有 | 消费者只能通过厂商入口读；跨边界需求靠定期导出 | 出现第二引擎时数据必须复制或重写，副本漂移同时出现 | 共享体验是当期收益，格式锁定的代价记在「以后」 | 需要跨边界的资产从一开始就用开放格式；先用「未来会不会有第二引擎」筛一遍 |
| 3. 把数据复制到模型侧 | 训练/推理链路依赖每日的数据同步作业 | 同步链路成为新增故障面，且「哪一份对」无人能答 | 模型侧最熟悉的是拉数据，而不是定义接口 | 把模型搬到数据旁边（读同一份存储），或让数据侧只暴露接口 |
| 4. 用一个引擎覆盖所有场景 | 每类新需求都在同一引擎里找近似解法 | 统一引擎会在某类场景上全面落后，且落后方向由引擎的架构决定，不是配置能补的 | 多引擎意味着多份运维，而运维成本在选型时最容易被低估 | 按场景各选一类引擎，用开放存储层与统一权限层把运维面收回来 |
| 5. 表格式只做「读」不做治理 | 换引擎很顺，但换完权限全丢、血缘断链 | 格式层只统一了数据可见性，治理规则仍绑在旧产品里，迁移的隐性成本在切换当天才出现 | 格式层的价值显性（能换引擎），治理的迁移成本隐性（要重建权限映射） | 权限与血缘放在独立于引擎的一层；迁移演练必须包含「权限是否还原」 |
| 6. 把追加型日志当异步 RPC 用 | 下游只有一个消费者、每次只读最新一条、从不重放 | 保留期被当成成本项砍到最短，可重放重建的能力名存实亡 | 消息队列的用法最容易被类比成 RPC，「重放」在无需求时看不出价值 | 保留期按「下游视图重建需要多久」倒推；把「上次真实重放是什么时候」当成可检查项 |
| 7. 提示词前缀被易变内容污染 | 缓存命中率低，账单与首字延迟回到基线 | 缓存键是前缀精确匹配，前缀一变即失效，整段上下文重新预填充 | 提示词由多人拼接，时间戳与随机 ID 常被放在最前面 | 固定结构：稳定内容在前、易变内容在后；把缓存命中率作为线上指标 |
| 8. 按估值 / 客户数横向排名选型 | 选型结论是「学估值最高的那家」 | 跨问题域排名比出来的是问题域差异，不是做法差异，照搬后约束不匹配，失效原因还会被误读成执行不力 | 排名最好懂，约束分析最费劲 | 先比约束（存量栈、引擎数、成本函数、合规强度），再比做法 |

**反模式 2 与反模式 5 是同一件事的两半，最危险的地方在于它们的暴露时间差。** 反模式 2 在共享体验最好的那年完全不痛，反模式 5 在换引擎很顺的那一刻也完全不痛 —— 两者的账单都开在「出现第二个引擎」那一天：数据要么复制、要么重写，而权限与血缘要重建一遍。判断方法不是问厂商「支不支持开放格式」，而是问自己两个可自查的问题：跨边界的那几个数据集属于哪一类资产？它们的权限规则现在写在哪里？

**反模式 6 在系统还很小时几乎不可能被发现。** 一个下游只有一个消费者、从不重放的日志，看起来和工作队列完全一样，于是保留期被压到最短、位点提交被放在处理之前 —— 直到某次下游视图写坏，需要按位点重建，团队才发现可重放的输入已经不在了。这时唯一的选择是全量重建，代价与事故规模同时放大。**判断标准很硬：保留期必须由「下游视图重建需要多久」倒推，而不是由「日志占多少存储」决定。**

**反模式 1 是唯一一条在采购阶段就注定发生的。** 它的成因是信息在时间上的错位：功能清单在选型当天就能列全，而「实际会用到哪几件」要等系统跑上半年才有数据；于是决策被功能覆盖度主导，而覆盖度的边际价值随实际使用比例迅速衰减。可操作的替代判据只有一条：**列出未来 12 个月确定会用的能力，用这一列的数量而不是总件数来决策。**

### 3.6 规模跃迁时模式何时该换

范式不是一劳永逸的。**规模、引擎数量或成本结构跨过某个阈值时，原来正确的范式会变成错的** —— 而且通常不是「变差」，是「变成账单或事故」。

换范式之所以要提前规划，是因为下面这些跃迁**没有一个能在发生当天完成**：格式要重写数据、分区键要重新设计、分片键几乎不可更改、账本的真值位置不能事后调整。因此表里最右一列（迁移的代价）才是这张表的重点 —— 它决定了你**现在**该为哪一个可能的跃迁预留余地。

| 跃迁 | 原范式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单引擎 → 2–4 个引擎 | 引擎层统一（专有存储） | 第二引擎要么读不了，要么只能靠复制 | 开放表格式 + 统一治理面（3.2.1） | 存量数据要重写成开放格式，权限与血缘要重建映射 |
| 每天几次批处理 → 分钟级时效 | 定时抽取 | 抽取周期成为时效地板，下游再多优化也压不下去 | 追加型日志 + 流式派生（3.2.4） | 分区键与顺序边界要重新设计，派生视图要全部重建一次 |
| 单租户 → 租户量级增长 | 单库多租户 | 单租户的慢查询影响其他租户，分析查询拖慢在线 | 按租户分片 + 派生仓（3.2.7） | 分片键一旦选定极难更改；跨租户分析要在仓里重做 |
| 单组织 → 跨组织交换数据 | 导出 / 导入 | 副本数量与「哪一份对」同时增长 | 共享即读 + 格式中立（3.2.2） | 访问控制要跨边界重建；跨出厂商时仍需导出兜底 |
| 按需查询 → 成本可见性成为硬要求 | 只管跑通查询 | 按扫描/按 token 计费时，写法直接等于账单 | 分区与列裁剪 + 缓存 + 用量配额（3.2.2 / 3.2.5） | 需要用量监控与口径统一的账单归因，否则优化无从下手 |
| 离线评测 → 线上持续变化 | 一次性打包的语料 | 配比与去重规则一变，整条管线要重跑 | 可重跑的打包管线 + 物理隔离评测集（3.2.6） | 管线要工程化（可重跑、可对比），短期看不出收益 |

**这张表里最容易被忽略的一条是「成本可见性成为硬要求」。** 前面五条跃迁都由规模或形态的变化触发，只有它在规模完全不变时也会发生 —— 触发它的是计费方式（从按容量变成按扫描量、按 token）或财务口径的收紧。此时需要换的不是架构，是**让查询写法与账单之间的因果链可见**：分区与列裁剪做到什么程度、缓存命中率是多少、每次请求的上下文多长。这些动作在小规模时收益太小、看不出差别，在按用量计费之后会直接决定单位成本；而它们通常不来自治理推动，只来自「用的人自己看得到账单」。

### 3.7 自检清单

1. 你现在的数据，**换引擎时需不需要重写数据本身**？需要即说明格式层没有对外开放。
2. 你的「一体化平台」里，**实际会用到的能力占几件**？列得出来吗？
3. 权限与血缘规则现在写在哪里 —— 引擎内、厂商产品内，还是独立的一层？换引擎时它们会不会跟着丢？
4. 每个追加型日志的**保留期是怎么定出来的**：按存储预算，还是按下游视图的重建时间？
5. 位点提交与派生写入的先后顺序是什么？**先提交后处理**的组合下，重放能否发现缺了哪些数据？
6. 资金 / 账务 / 权益类状态，余额是**算出来的还是存下来的**？有没有一条能被 SQL 直接校验的不变量？
7. 你的评测集与训练语料**是否物理隔离**？隔离是哪一步做到的（打包前还是打包后）？
8. 分片键选定后，**最大的那个租户占了多少**？它装得进一个分片吗？
9. 提示词的**前缀是否稳定**？把时间戳、随机 ID、每次不同的画像放在前面了吗？
10. 你评估一个平台时，用的是「它一共有多少件」还是「我实际会用到哪几件」？
11. 你最近一次跨组件的架构结论，是**比约束**得出的，还是**比估值/客户数**得出的？
12. 在你选定的组合里，**会先变的那一层**是否正好是被统一层绑定的那一层？如果是，迁移预案是什么？

### 3.8 小结

把前面八个范式压缩成一张表：左边一列写的是**你的约束**（不是你的偏好），右边一列写的是这条约束下**机制上成立**的选择。表里没有一行是「因为它先进」，因为范式本身没有先进与落后之分 —— 只有在给定约束下，某一层的统一成本是否值得付。

| 你的约束 | 建议范式 | 关键理由（机制层面） |
| --- | --- | --- |
| 存量在对象存储、会出现第二引擎 | 开放表格式（3.2.1） | 「表」被定义成文件清单 + 日志，换引擎不需要搬数据 |
| 单引擎、无内核专家、要弹性 | 存算分离 + 托管（3.2.2） | 计算不持有数据，所以能瞬时扩缩；代价是跨层取数成为固定开销 |
| 跨组织共享、不能复制 | 共享即读（3.2.2） | 共享的是读权限与元数据指向，副本根本不产生 |
| 资金与账务状态 | 追加型账本 + 对账（3.2.3） | 修改 = 追加反向分录，余额可重放，不变量可机器校验 |
| 一类事件有几十个下游 | 追加型日志 + 派生索引（3.2.4） | 唯一事实来源可重放，视图坏了能重建 |
| 合规把部分数据划出可用集合、推理成本随上下文增长 | 训练数据分层 + 推理前缀复用（3.2.5） | 被划走的数据攒不回来，只能靠来源登记与接口解决；缓存键是前缀精确匹配，稳定内容在前即可只算增量 |
| 训练与推理同时存在 | 离线打包 + 在线分档（3.2.6） | 两条链路的优化目标冲突，必须分开 |
| 多租户 SaaS | 按租户分片 + 派生建模（3.2.7） | 分片键即租户，租户间物理隔离；分析另建一套结构 |
| 多人实时协作 | CRDT / OT（3.2.8） | 合并规则写进数据类型，不依赖到达顺序 |

> 本节小结：本主题下**决定范式选择的唯一那条约束，是「统一发生在哪一层」——格式层、引擎层，还是接口层**。统一在格式层买到可迁移、代价是治理要自己补；统一在引擎层买到体验、代价是离开要导出；统一在接口层买到合规叙事的干净、代价是数据侧的差异化让出去。所有关于「学谁」的争论，都只在「统一层选在哪」给定之后才成立；顺序颠倒了，越努力越锁定。
>
> 💡 **思考锚点**：在你自己的栈里挑一次「统一」，按 §3.2 归到格式层（学 §3.2.1 的开放表格式）、引擎层（学 §3.2.2 的共享即读）还是接口层——明天要换掉它，导出与迁移的工作量落在哪一层？再看 §3.4：组合成立的前提是「谁都不许把治理规则写进引擎」——你的权限与血缘是绑在某个引擎上，还是已经独立成一层？
