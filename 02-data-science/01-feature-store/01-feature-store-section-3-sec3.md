## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

八个模式看起来是「离线优先 / 实时优先 / 混合 / FaaS / AI 原生 / 联邦 / 湖仓一体 / 边缘」的并列选项，好像按团队规模挑一个就行。真实的选型不是挑风格，而是被**约束**推着走：同样是「实时推荐」，在「事件量每秒十万、特征窗口 1 小时」与「事件量每秒一百、特征窗口 30 天」两种约束下，正确模式完全不同——前者的流状态量可控，后者只能靠批，因为 30 天窗口的累计状态在流里既不经济也难以重放。

八个模式的差异，归根到底只由**一个机制**决定：**特征值在什么时刻、由谁算出来，以及离线训练与在线推理凭什么保证拿到同一份值**。这条机制一旦定死，存储、调度、监控、回填的形态全都跟着定——一致性靠引擎保证（单一路径）还是靠测试守（双路径），就是本节所有模式分歧的总开关。

所以本节的组织方式是：先立六条约束（下表），再让每个模式自报被哪条约束逼出来，最后用「失效点」说明这条约束一旦改变，模式如何反转成负担。写不出约束的模式，往往只是别人方案的形状，抄过来会在规模跃迁时爆掉。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态 / 写入模式 | 特征是事件流的函数（追加写、留历史），还是属性维度的快照（覆盖写）——决定用流状态还是宽表 | 「特征就是一张宽表」：覆盖写抹掉历史，Point-in-Time 训练与回填同时失去依据 |
| 访问模式（点查 / 扫描 / 聚合） | 训练要按 `entity + event_time` 批量扫描与时间对齐，推理要按实体键单点取——两套形态 | 「一套存储同时服务训练和推理」：扫描型存储做不了毫秒点查，KV 做不了时间对齐扫描 |
| 变更频率与历史要求 | 特征定义多久改一次、是否要复现三个月前的模型——决定版本化与回填的工程量 | 「改个 SQL 直接上线」：定义一改历史模型不可复现，回填必须重跑全量 |
| 一致性要求 | 离线与在线是「同一份定义两条执行路径」还是「同一次计算的两次读取」——决定靠测试守还是靠引擎守 | 「两套代码结果差不多就行」：差一点，就是训练指标与上线效果的断崖 |
| 规模与成本约束 | 实体基数 × 特征数决定在线存储常驻成本；窗口长度决定流状态成本 | 「特征越多越好」：在线存储按实体基数常驻计费，宽表化的账单落在推理侧 |
| 团队技能与运维能力 | 流状态、批调度、在线 KV 三套引擎的运维面能否被现有团队承担 | 「上了 Flink 就是实时」：实时特征的主要成本是流状态运维与回填能力，不是引擎选型 |

### 3.2 模式逐个拆解（核心节）

以下 8 个模式，每个都给出结构示意（DDL 或关系图），并回答「被什么逼出来 / 为什么有效 / 代价 / 失效点 / 真实使用」。

#### 3.2.1 离线优先（Offline-First）

- **被什么约束逼出来**：模型天级更新、在线只需一份「最新快照」；团队只有批调度能力，没有流状态运维能力。
- **结构**：离线宽表持有历史（追加写 + `event_time`），物化任务把每个实体的最新一行搬到在线 KV。
- **为什么这样设计有效**：因为特征只有一条计算路径（批），所以离线与在线的一致性只取决于物化搬运是否忠实，而不是两份实现是否等价——一致性成本从「人守两套代码」转移成「守一条管道」。

```sql
-- 离线特征表：追加写、保留历史（Point-in-Time 的基础）
CREATE TABLE fs.user_click_7d (
  entity_id    STRING    NOT NULL,   -- 实体键（用户 / 商品 / 店铺）
  event_time   TIMESTAMP NOT NULL,   -- 特征对应的时间点（不是写入时间）
  click_cnt_7d BIGINT,
  gmv_30d      DECIMAL(18,2),
  dt           STRING    NOT NULL    -- 物理分区，仅用于裁剪扫描
) PARTITIONED BY (dt);

-- 训练取数：WHERE event_time <= label_time（用"当时能看到"的值）
-- 物化：按 entity_id 取最新一行 → 写在线 KV（TTL = 物化周期 + 余量）
```

- **代价**：特征的时间分辨率等于物化周期（小时级到天级），在线存储要按实体基数常驻（用户基数大时 KV 是笔固定账单）；回填必须重跑批任务。
- **失效点**：当在线侧要求秒级新鲜度时，「一致性可守」的优点反转成「永远滞后」的缺点——因为批调度周期就是特征的时间分辨率，模型看到的是上一个周期的世界。
- **真实使用**：Uber Michelangelo 的 Palette 是公开披露最早的生产级特征存储，服务其派单与 ETA 等场景【公开】（来源：Uber Engineering 官方博客 2017 年发布的平台介绍文章《Meet Michelangelo: Uber's Machine Learning Platform》——可在 Uber 官方工程博客按年份 2017 与关键词 Michelangelo 检索核验；与本书主文件 §1.4「2017：Uber 提出 Michelangelo Palette」同口径）；Feast 的离线存储 + `materialize` 流程是这一模式的标准化实现【公开】（来源：Feast 官方文档的离线存储（offline store）与 `materialize` 物化命令两条目，域名 docs.feast.dev；该文档随版本更新、无固定出版年份，开源时间线见本书主文件 §1.4，可按 "Feast materialize" 自行检索核验）。

#### 3.2.2 实时优先（Streaming-First）

- **被什么约束逼出来**：特征本身就是事件的函数（近 1 分钟点击、最近一笔交易），业务要求事件到特征秒级可用。
- **结构**：Flink / Kafka Streams 直接在流上维护 keyed state（窗口 / 累计），窗口结果写在线 KV，落湖侧供训练时间对齐。
- **为什么这样设计有效**：因为在线的读路径没有中间搬运环节、特征在事件到达后立刻更新，所以新鲜度等于流作业的延迟（秒级）；且离线可以复用同一份算子代码（流批同源），把「两套代码」问题压到最小。

```text
流式特征（同一份算子同时产出在线侧与训练侧）
  事件流 ──► Flink 作业（keyed by entity_id）
               ├─ 状态：滑动 / 滚动窗口、累计量（RocksDB state backend）
               ├─ 在线侧：窗口结果 upsert 到 Redis（毫秒读）
               └─ 落湖侧：窗口结果 append 到湖仓表（供训练时间对齐）
  ── 一致性来源：同一份算子代码 + 同一个 key + 同一套时间语义（事件时间 / 水位线）
  ── 关键上限：state TTL 决定"能重放多久的历史"
```

- **代价**：要承担流状态的存储与检查点成本（状态越大，checkpoint 越慢、恢复越久）；乱序事件与迟到数据的处理逻辑必须显式写；长窗口（30 天累计）的状态规模可能超过收益。
- **失效点**：当需要回填历史或重放三个月前的样本时，「秒级新鲜度」的优点反转成「历史不可重算」的缺点——因为流状态是按在线服务设计的、且受 TTL 限制，不是为可重放设计的。
- **真实使用**：Tecton 是主打实时特征视图与流式聚合的商业平台，本书主文件 §1.4 记为 2021 年商业化；它与 Uber Michelangelo 的承继关系、以及创始团队背景，本节不代为断言——**判断方法**：查 Tecton 官方文档中 feature view / streaming aggregation 一类条目最早出现在哪一版，再对照其官方关于公司与产品起源的公开介绍，看能否与 Uber Michelangelo 对应上【经验】。实时风控与实时推荐的流式特征是最主要的落点【经验】。

#### 3.2.3 混合架构（Hybrid）

- **被什么约束逼出来**：一个模型同时要吃两种时间常数的特征——用户长期偏好（天级、可回填）与本次会话行为（秒级、不可回填）。
- **结构**：定义层统一，执行层两条路径（批 + 流），训练时按 `event_time` 拼接，服务时按实体键合并。
- **为什么这样设计有效**：因为可以按特征的时间常数选择计算路径，所以长窗口特征不必挤进流状态、短窗口特征不必等批；代价是一条新的保真链——一致性不再由单一路径保证，必须由「双路径等价性校验」来守。

```text
混合架构：一个定义，两条路径，靠"等价性校验"缝合
  定义层（feature view）
      feature: user_click_7d | entity: user | ttl: 3d
      ├─ 批路径：Spark 按天算 → 湖仓表（可回填 / 可重放）
      └─ 流路径：Flink 按分钟增量 → 在线 KV（低延迟）
  校验层（这条链的命门）
      定时抽样比对「批路径结果」与「流路径结果」
      ├─ 差异率超阈值 → 告警（train-serving skew 的前哨）
      └─ 差异定位：按 entity 抽样 + 按 event_time 对齐
```

- **代价**：需要同时运维批、流、在线 KV 三套引擎；必须额外养一个一致性校验作业与漂移告警；定义层要做抽象，才能让同一份逻辑被两条路径翻译。
- **失效点**：当任何一个团队就地改写其中一条路径的实现（而不是改定义）时，「一致性由等价性校验守住」的优点反转成「测试没覆盖的静默偏差」——因为校验只比结果，不保证两份实现同源。
- **真实使用**：工业级大规模推荐的常见形态是混合架构【经验】；Feast 逐步补齐 on-demand 与流式两类 feature view 以支持双路径【公开】（来源：Feast 官方文档的 feature view 分类条目——On demand feature views 与 Stream feature views 两节，域名 docs.feast.dev；该文档随版本更新、无固定出版年份，具体到哪个版本支持哪些能力请以官方文档当前版本为准，可按 "Feast on demand feature views" / "Feast stream feature view" 自行检索核验）。

#### 3.2.4 Feature as a Service（FaaS）

- **被什么约束逼出来**：特征从「一个团队的脚本」变成「多个团队共享的服务」，于是需要契约、配额、权限与计量。
- **结构**：特征以 API 契约交付；`feature_service` 是一组 feature view 的命名快照，消费方只传实体键，不关心上游表结构。
- **为什么这样设计有效**：因为交付物是 API 而不是代码或表，所以特征可以按消费方限流、单独计费、按特征授权，且上游表结构变更不必穿透到所有调用方；代价是取数入口变成所有模型共享的关键路径。

```text
FaaS：特征以 API 契约交付（而不是以代码或表交付）
  消费方                               特征服务
  ──────────────────────────────       ───────────────────────────────
  get_online_features(       ────────►  feature_service: ranker_v3
      service="ranker_v3",                ├─ feature_views: [user_7d, item_30d]
      entity_ids=["u1","u2"])             ├─ entities: [user_id, item_id]
                                          ├─ SLA: p99 延迟 / 可用性承诺
  调用计量 / 配额 ◄─────────────────────  ├─ 配额: 按调用方的 QPS 上限
  审计（谁取过哪些特征） ◄───────────────  └─ ACL: 特征级（敏感特征单独授权）
```

- **代价**：特征服务成为在线推理的关键路径，它的延迟与可用性上限等于所有模型的延迟与可用性上限；契约治理（版本、弃用、配额谈判）是持续的组织成本，不是一次性工程。
- **失效点**：当特征服务的 SLA 没有被明确写进模型的上线条件时，「统一复用」的优点反转成「故障放大」的缺点——因为所有模型共享同一个取数入口，一次抖动会同时打穿全部线上模型。
- **真实使用**：Feast 的 Feature Server 与 Tecton 的 feature service 都是这一模式的标准化形态【公开】（来源：Feast 官方文档的 Feature Server 一节（docs.feast.dev）与 Tecton 官方文档的 Feature Services 一节（docs.tecton.ai）；两者都是随版本更新的产品文档、无固定出版年份，能力细节以官方文档当前版本为准，可按 "Feast feature server" / "Tecton feature service" 自行检索核验）；企业内以特征平台对多团队提供取数服务是主流做法【经验】。

#### 3.2.5 AI 原生（AI-Native）

- **被什么约束逼出来**：LLM / RAG 场景下「特征」变成 prompt 模板、embedding、检索结果与工具描述——非结构化、需要向量检索、且随索引变化。
- **结构**：把 prompt 版本、embedding 模型版本与索引快照绑定成一次推理的「输入快照」，与线上分布监控一起纳入平台管理。
- **为什么这样设计有效**：因为输入快照被整体版本化，所以一次推理可以复现、效果变化可以归因到「输入变了还是模型变了」；代价是索引与 embedding 的重建成本，以及按 token 计费的在线成本。

```text
AI 原生：把 Prompt / Embedding / 索引一起版本化
  一次推理的输入快照 =
      (prompt_template@v7, embed_model@v3, index_snapshot@2026-10-01)
  ┌──────────────────────────────────────────────────────────┐
  │ prompt_template@v7    文本模板（含变量占位，版本化）       │
  │ embed_model@v3        向量化模型 + 归一化参数              │
  │ index_snapshot@...    向量索引快照 ID（不是"当前索引"）    │
  │ retrieval_params@v2   召回条数 / 阈值 / 重排策略           │
  └──────────────────────────────────────────────────────────┘
  → 效果归因：输入快照变了，还是模型权重变了？
```

- **代价**：向量索引重建是重成本（换一次 embedding 模型要全量重算，且重算期间新旧索引并存）；非结构化特征没有 PSI 那样简单的漂移指标，监控要么靠抽样人工评估、要么靠 LLM 评测；上下文越长，单次调用成本越高。
- **失效点**：当索引内容被静默更新（重灌数据但快照 ID 未变）时，「可复现」的优点反转成「A/B 结果不可信」——因为版本化只覆盖被显式记录的元数据，索引里的向量内容不在其中。
- **真实使用**：Hopsworks 与 Tecton 的官方文档都有面向 embedding / 向量检索的特征能力条目【公开】（来源：Hopsworks 官方文档的 embedding 与相似度检索（similarity search）条目，域名 docs.hopsworks.ai；Tecton 官方文档中与 embedding / 向量特征相关的条目，域名 docs.tecton.ai；均为随版本更新的产品文档，无固定出版年份，具体支持范围以官方文档当前版本为准，可按 "Hopsworks similarity search" / "Tecton embedding" 自行检索核验）；RAG 工程里「prompt + 索引 + 模型」三者一起版本化是通行做法【经验】。

#### 3.2.6 联邦特征平台（Federated）

- **被什么约束逼出来**：数据不能出域（跨机构、跨法人、受监管子域），但模型需要多方特征。
- **结构**：各方本地计算与本地存储，只用统一契约交换特征值或聚合量；实体对齐表由双方各自持有。
- **为什么这样设计有效**：因为流转的是特征值而不是原始记录，所以合规边界由「数据放在哪」决定，不依赖访问控制的自觉；代价是「同一个人 / 同一时刻」的定义必须跨方对齐。

```text
联邦特征平台：只交换特征值，不搬原始记录
  A 域（本地存储 + 本地计算）          B 域（本地存储 + 本地计算）
     本地特征表 ──► 特征值 ─┐           本地特征表 ──► 特征值 ─┐
                            │                                │
      实体对齐（ID 映射，各方自持，不明文外传）               │
                            │                                │
                            └────► 统一特征契约（字段 + 语义 + 时间口径）◄──┘
                                              │
                              联合模型只消费契约内的特征值
  ── 风险点：契约统一了"字段"，不一定统一了"同一个人、同一时刻"
```

- **代价**：实体对齐与时间口径统一的协调成本（跨方评审、联调）；跨域调用带来延迟与失败处理复杂度；契约变更需要所有参与方同时升级。
- **失效点**：当各方的实体对齐口径或时间口径不一致时，「数据不出域还能建模」的优点反转成「特征错位」的缺点——模型学到的不是信号而是拼接噪声，且因为看不到对方原始数据，排查极其困难。
- **真实使用**：跨机构联合风控、联邦学习场景常用这一形态，主要动机是数据不出域而非性能【经验】。

#### 3.2.7 湖仓一体（Lakehouse Feature Store）

- **被什么约束逼出来**：企业已选定湖仓（Iceberg / Delta / Hudi）作为唯一存储底座，要求特征与业务数据同源、不引入第二套存储与第二套治理。
- **结构**：特征就是湖仓表（实体键 + `event_time` + 分区），在线侧由物化管道导出，训练直接用湖仓表的时间旅行取快照。
- **为什么这样设计有效**：因为特征与业务数据同表格式、同目录、同权限，所以血缘、权限、时间旅行可以直接复用湖仓能力，不必为特征重建一套治理；代价是湖仓表要同时承受扫描与高频 upsert 两类负载。

```sql
-- 特征就是湖仓表：与业务数据同格式、同目录、同权限、同血缘
CREATE TABLE lake.feature_user_behavior (
  entity_id  STRING,
  event_time TIMESTAMP,
  feat       MAP<STRING, DOUBLE>,  -- 稀疏特征放 map，避免宽表列爆炸
  dt         STRING
) USING iceberg
PARTITIONED BY (dt)
TBLPROPERTIES ('write.update.mode' = 'merge-on-read');

-- 训练：SELECT ... FOR SYSTEM_TIME AS OF <训练样本时刻>（直接复用时间旅行做对齐）
-- 在线：由物化管道导出到 KV —— 湖仓不承担毫秒点查，这条边界不能省
```

- **代价**：湖仓的点查能力弱于专用 KV，必须额外维护物化链路；频繁 upsert 会带来小文件与合并开销（copy-on-write 写放大、merge-on-read 读放大，两头都要权衡）；分区设计要同时满足训练扫描裁剪与在线导出。
- **失效点**：当团队把特征表设计成「高频覆盖写的最新快照表」时，「复用湖仓时间旅行做 Point-in-Time」的优点反转成「历史被抹掉」——因为覆盖写不保留版本，时间旅行无处可依。
- **真实使用**：Databricks Feature Store 建立在 Delta Lake 之上【公开】（来源：Databricks 官方文档的 Feature Store / Feature Engineering 一节，域名 docs.databricks.com，2020 年发布的产品文档、随产品版本更新；与本书主文件 §1.4「2020：Databricks 发布 Feature Store」同口径，可按 "Databricks feature store Delta Lake" 自行检索核验）；Hopsworks 是否以 Iceberg / Hudi 作为特征存储底层，本节不代为断言——**判断方法**：查其官方文档里有没有「外部特征组（external feature group）/ 表格式对接」一类条目，且该条目是否明确列出 Iceberg 或 Hudi 及对应版本【经验】。

#### 3.2.8 边缘特征（Edge Feature Store）

- **被什么约束逼出来**：推理发生在端侧（手机 / IoT），原始数据不宜出设备，网络不可靠且带宽有限。
- **结构**：慢特征（画像 / 偏好）由云端下发成「特征包」，快特征在本地算，端侧只上报聚合量。
- **为什么这样设计有效**：因为特征在本地算，原始数据不必离开设备、断网也能推理，所以隐私与可用性同时改善；代价是端侧算力与存储预算、以及两端特征定义的版本对齐问题。

```text
边缘特征：慢特征下发、快特征本地算、原始数据不出设备
  云端                                  设备端
  ────────────────────────────────      ─────────────────────────────────
  日级特征快照（画像 / 偏好）      ──►    本地特征包（带版本号 + 有效期）
  量化后的模型                     ──►    端侧推理（断网可用）
                                        ├─ 本地快特征：本次会话点击 / 位置
  聚合上报（仅在用户授权时）       ◄──    └─ 原始数据不出设备
  ── 特征定义有两份（云端 + 端侧），版本对齐依赖设备的联网行为
```

- **代价**：端侧有硬预算（模型与特征包大小、内存、电量），特征工程被迫做减法；特征定义在两端各有一份实现，需要版本协商与降级策略；云端无法直接回填端侧特征，历史样本只能来自上报的聚合量。
- **失效点**：当特征定义需要与云端同步更新、而设备长期不联网时，「本地计算保隐私」的优点反转成「两端分布漂移」的缺点——同一模型在联网设备与离线设备上表现不一致，因为版本对齐依赖设备行为而非平台。
- **真实使用**：手机端推荐、输入法候选、相机端侧模型普遍在设备本地算特征【经验】；联邦学习与端侧学习场景同属这一约束家族。

### 3.3 模式选择决策表

> 下表全部为**情景阈值**【经验：按区间判断，不是测量值】——「特征几十到几百个」「是否存在 > 7 天的窗口特征」这类规模档与门槛只回答「该往哪个方向选」，不回答「卡在第几个」；请代入自己的实际规模与预算。

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 小规模 ML 团队 / 特征几十到几百个 | 离线优先 + Feast（开源） | 实时优先要养流状态，此时运维成本远超收益 | 在线是否需要秒级新特征？否 → 离线优先 |
| 中大规模 + 强实时需求 | 混合架构 + Tecton（商业） | 纯离线满足不了新鲜度；纯实时回填不了长窗口 | 是否存在 > 7 天的窗口特征？是 → 必须混合 |
| 大数据 + 数仓 / 湖仓已统一 | 湖仓一体 + Hopsworks | 再建独立存储会让血缘与权限出现两套 | 特征表能否直接落在既有湖仓表格式上？ |
| 阿里云生态 | 阿里 FeatureDB / PAI 特征平台 | 跨云拼接会让在线取数多一跳 | 在线服务与训练是否都在同一云内？ |
| 字节生态 | ByteFS | 同上，生态内集成省掉大量适配 | 训练框架与存储是否同生态？ |
| 腾讯生态 | TI-EMS 特征平台 | 同上 | 同上 |
| 离线训练为主、天级更新 | 离线优先 | 引入流式只增加新鲜度、不改变业务指标 | 模型更新频率是天级吗？ |
| 实时推荐 / 实时风控 | 实时优先（Tecton + Flink） | 离线优先在风控场景会漏掉最新行为 | 事件到决策的预算是否在秒级？ |
| LLM / RAG 场景 | AI 原生（Tecton AI 相关能力 / Feast + 向量库） | 传统特征平台不管理 prompt / embedding / 索引版本 | 效果变化能否归因到输入快照？ |
| 多团队 / 跨部门共享 | FaaS | 共享表会让上游 schema 变更穿透所有消费方 | 是否需要按调用方配额与计费？ |
| 隐私敏感 / 数据不能出域 | 联邦特征平台 | 集中式平台要求原始数据汇聚 | 原始记录能否离开本域？ |
| 端侧推理 | 边缘特征 | 云端特征在断网与隐私约束下不可用 | 推理是否必须在设备上完成？ |
| 已有 Spark / K8s 技术栈 | 离线优先 / 混合 + 既有栈 | 换栈的成本通常高于模式收益 | 团队能否承担流状态运维？ |

表后补充：**最常被误选的一对是「离线优先」与「实时优先」**。误选实时优先的后果通常在半年后暴露【经验】——流状态与检查点成本随窗口长度增长，而真正要解决的业务问题（比如长周期用户偏好）本来就不需要秒级新鲜度；反向误选（该实时却选了离线优先）的后果则是模型永远落后一个物化周期，风控场景会直接表现为「当天新注册账号无特征可用」。

已有技术栈也会约束选型：若团队已在 Spark 上做批特征，Feast + Spark 是摩擦最小的起点；若平台已建在 K8s 上，Tecton + K8s 这类托管形态会省掉大量在线服务与物化的自研工作【经验】。这两条都属于「约束优先于偏好」——技术栈是约束，不是可以随手更换的选项。

### 3.4 组合模式：真实系统不会只用一种

> 三条组合标题里的「0 → 1 / 1 → 10 / 10 → 100」是团队与特征规模的相对档位【经验：按区间判断，不是精确门槛】——它标的是「这一档该不该引入下一套引擎」，不是容量规划值。

**组合 1：Feast + Flink + Redis（轻量级，适合 0 → 1）**

- 构成：Feast 定义与管理特征、Flink 做实时计算、Redis 做在线存储。
- 职责边界：Feast 管定义与物化编排，Flink 管新鲜度，Redis 管毫秒读取。
- 运维代价：多一套 Flink 作业与状态要运维，但特征定义与在线存储都是轻量件，可先上批路径再补流。
- 适合规模：单业务域、百级特征、约束以「尽快跑通一致性」为主。

**组合 2：Tecton + 实时引擎（企业级实时，适合 1 → 10）**

- 构成：Tecton 统一管理定义与实时视图，底层接入实时计算引擎，在线存储由平台托管。
- 职责边界：平台承担双路径等价性与物化，团队只维护特征逻辑；FaaS 形态提供取数契约。
- 运维代价：商业组件与在线服务的成本、以及特征服务成为关键路径的可用性风险。
- 适合规模：多算法团队共享特征、有秒级新鲜度要求、有明确 SLA 的场景。

**组合 3：Hopsworks + Iceberg + 向量库（AI 原生，适合 10 → 100）**

- 构成：Hopsworks 管理特征与模型，Iceberg 做湖仓底座，向量库承担 embedding 与检索。
- 职责边界：Iceberg 管历史与时间旅行，Hopsworks 管 AI 原生资产（含 prompt / embedding 版本），向量库管近邻检索。
- 运维代价：三套存储的运维面与一致性边界必须写清楚（谁负责哪一类特征），否则会出现「同一特征两处口径」。
- 适合规模：既跑传统模型又跑 LLM 应用、需要输入快照可复现的组织。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 离线 / 在线两套代码 | 同一特征存在 Spark SQL 与在线代码两份实现 | 两条路径各自翻译同一语义，偏差只在校验时暴露，训练指标与上线效果脱钩 | 平台缺失，算法团队先跑通离线再说 | 统一到一份特征定义 + 由平台生成 / 托管双路径 |
| 特征重复开发 | 不同模型里出现语义相同、命名不同的特征 | 语义分叉让「同名不同义」出现，模型效果无法跨团队归因 | 没有可发现的目录与复用流程 | 建 Feature Catalog + 复用评审 |
| 无 Point-in-Time 校验 | 训练指标异常高、上线即跌；样本含未来信息 | 训练用了 `event_time > label_time` 的值，泄露未来导致指标虚高 | 取数用「最新快照」而非时间对齐 | 取数强制 `event_time <= label_time`，并加样本审计 |
| 特征无版本管理 | 定义变更后无法复现三个月前的模型 | 定义与样本不再一一对应，回滚与复盘失去依据 | 特征定义被当作代码而非受管制品 | 定义进 Git + 语义化版本 + 与模型版本绑定 |
| 特征血缘断裂 | 上游表结构变更时说不清影响哪些特征与模型 | 变更影响面不可枚举，事故只能事后发现 | 血缘靠人工登记，登记后很快过期 | 由作业定义与查询日志自动解析血缘，定时校准 |
| 特征无监控 | 模型指标缓降但无人定位；特征分布已变 | 漂移不可见导致问题被归因到模型而不是数据 | 只监控模型指标、不监控输入分布 | 建 PSI / KS / 缺失率监控与阈值告警 |
| 敏感特征无访问控制 | 身份证号、手机号类特征对所有取数方可见 | 一次越权取数就是合规事故，且难以追溯 | 特征平台按「平台内可信」假设设计权限 | 特征级 ACL + 取数审计 + 敏感特征单独授权 |
| 特征回填困难 | 新特征上线时历史样本大面积缺失 | 新模型无法在历史样本上评估，只能拿线上流量试错 | 平台只支持「向前物化」不支持重算 | 支持 Backfill 的物化机制 + 定义可重放 |
| 实时特征过度使用 | 大量天级语义的特征被塞进流作业 | 流状态与检查点成本上升，而业务指标无变化 | 「实时」被当作目标而不是手段 | 按时间常数分级（离线 / 近实时 / 实时） |
| 向量特征与传统特征分裂 | 传统特征在特征平台、向量特征在向量库，两套元数据 | 特征发现与血缘被切成两半，AI 应用无法一次取全 | 向量库先于平台引入，各管一摊 | AI 原生平台统一管理，或至少统一目录与血缘 |

**最危险的三个反模式**：

**「离线 / 在线两套代码」** 在生产中的典型暴露方式是「离线指标很好看，上线效果平庸」，而且越是特征复杂的模型越严重——因为复杂特征里的每一个条件分支都是两条实现可能分歧的地方。它的排查成本极高：两套代码都「没错」，错的是它们不等价，只能靠抽样比对逐特征定位。

**「无 Point-in-Time 校验」** 的暴露方式更隐蔽：训练指标会因为「看到了未来」而偏高，团队往往先怀疑模型、再怀疑数据，最后才发现取数口径用了最新快照。它的修法必须在取数层强制时间对齐，而不是靠评审发现——因为「哪一列属于未来信息」在宽表里并不显然。

**「敏感特征无访问控制」** 的暴露方式是一次性、不可逆的：越权取数一旦发生，数据已被复制，事后审计只能定位责任、无法撤回暴露面，所以它必须作为准入条件前移到平台设计里。

### 3.6 规模跃迁时模式何时该换

> 本节正文与下表的规模档（特征数几百 → 数千、团队一个 → 十个）与跃迁阈值同样全部为**情景阈值**【经验：按区间判断，不是测量值】——只回答「跨过了哪个台阶」，不回答「跨在第几个」；请代入自己的实际规模。

模式不是一劳永逸的：**规模或访问模式跨过某个阈值时，原来正确的模式会变成错的**——离线优先在特征数几百、团队一个时是最省的选择，到特征数千、团队十个时就变成口径分叉的源头；边缘特征在设备型号单一、上线节奏可控时成立，到设备版本高度碎片化时就成了分布漂移的来源。判断该不该换，看的不是「量变大了」，而是**约束的形态是否变了**：新鲜度要求、回填要求、数据位置、一致性成本的承担方，任何一条改了，模式就该重新审一遍。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单团队 → 多算法团队（特征数百级 → 千级） | 离线优先，各自脚本 | 语义重复与口径分叉开始产生，找特征靠问人 | 离线优先 + Feature Catalog + 版本化 | 需要补登记流程与复用评审，短期拖慢上线 |
| 天级更新 → 秒级新鲜度 | 离线优先 | 物化周期成为新鲜度上限，风控类场景直接失效 | 混合架构（批 + 流双路径） | 新增流作业与状态运维，并要养一致性校验链 |
| 单卡/单机 → 多节点流式 | 实时优先（单作业） | 状态与 checkpoint 规模上升，恢复时间变长 | 实时优先 + 状态分区与检查点调优，或退回混合 | 必须重新设计 key 与窗口，历史不可直接迁移 |
| 集中式 → 数据不出域 | 集中特征平台 | 原始数据无法汇聚，平台取不到数 | 联邦特征平台 | 需要实体对齐与契约协同，建模能力受限 |
| 云端 → 端侧 | 云端在线特征 | 断网与隐私约束下云端特征不可用 | 边缘特征 | 端侧预算迫使特征做减法，两端版本需对齐 |
| 传统模型 → LLM / RAG 应用 | 传统特征平台 | prompt / embedding / 索引无人版本化，效果不可归因 | AI 原生 | 需要索引重建与评测链路，评测成本高于指标监控 |

### 3.7 自检清单

- [ ] 每个特征的取数是否强制 `event_time <= label_time`？任意样本能说清它用了哪个时刻的值吗？
- [ ] 同一个特征是否只有一份定义？如果存在离线与在线两份实现，有没有自动化等价性校验在跑？
- [ ] 在线特征的新鲜度上限是多少？这个数字是否能被业务方复述（而不是只有平台团队知道）？
- [ ] 每个特征的在线存储成本是否可算？即实体基数 × 特征数 × 副本数的量级能否给出？
- [ ] 特征定义变更后，历史模型能否复现？上一次定义的版本是否仍可取到？
- [ ] 上游数据源变更时，能否一键列出受影响的特征与模型？
- [ ] 有没有特征漂移监控（PSI / KS / 缺失率）？阈值告警触发后谁负责处置？
- [ ] 新增特征时能否对历史样本重算（回填）？回填的时长与资源上限是多少？
- [ ] 敏感特征是否在特征级做了访问控制与取数审计？最近一次越权尝试有没有被记录？
- [ ] AI 原生场景下，一次推理的「输入快照」（prompt / embedding / 索引）是否可完整还原？
- [ ] 流式特征的状态保留期（TTL）是否与「要支持多久的回填 / 重放」这一需求对齐？
- [ ] 特征服务是否定义了延迟与可用性 SLA，并且写进了模型的上线条件？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 天级更新、团队小 | 离线优先 | 单一路径让一致性由管道保证，而不是由两套代码的等价性保证 |
| 秒级新鲜度、单业务域 | 实时优先 | 特征在事件到达后就地更新，新鲜度等于流作业延迟 |
| 长短窗口特征并存 | 混合架构 | 按时间常数分流计算路径，用等价性校验补回一致性保障 |
| 多团队共享、需计量与权限 | FaaS | 以 API 契约交付才能独立限流、授权、计费，但入口即单点 |
| LLM / RAG、需可归因 | AI 原生 | 输入快照整体版本化才能把效果变化归因到输入而非只能归因到模型 |
| 数据不出域 | 联邦特征平台 | 流转特征值而非原始记录，合规边界由数据放置决定 |
| 湖仓已是唯一底座 | 湖仓一体 | 复用湖仓的血缘 / 权限 / 时间旅行，避免出现第二套治理 |
| 端侧推理、隐私优先 | 边缘特征 | 本地计算让原始数据不出设备，同时获得断网可用性 |

> 本节小结：决定这 8 个模式选择的是**唯一一条约束 —— 特征值必须在什么时刻、由谁算出来，离线与在线凭什么拿到同一份值**。这条约束定死后，存储形态、回填能力、一致性保障方式、失效点全都是它的推论。
>
> 💡 **思考锚点**：把你线上特征按时间常数分成离线 / 近实时 / 实时三档，分别数出各档的特征数——有几档是业务真正需要的？每多留一档就多养一条计算路径与一条一致性校验链；按你现在的特征数与团队规模，哪一档可以砍掉而不让任何离线 / 在线的值对不上？
