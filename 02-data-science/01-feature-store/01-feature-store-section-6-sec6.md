### 1.1 某头部电商"**100+ 模型特征复用**"4+ 年（2020-2024）

**背景（Why）**

该电商 2020 年面临**特征重复开发 + 训练推理不一致**：
- **100+ 模型**——每个算法团队**重复写同一份特征**（用户近 7 日点击、商品近 30 日 GMV）
- **训练 / 推理不一致**——离线用 Spark 算、线上用 Java 算，**同一特征两套实现，必然漂移**
- **上线周期长**——新模型从 0 到上线要 **6 周**，其中 **3 周在搞特征**

**触发点（What）**

2020 年该电商启动 Feature Store（[案例 2020]），目标四条：
- **特征复用率**——**30% → 70%+**
- **离线 / 在线一致性**——**90% → 99.9%**
- **ML 项目周期**——**-40%**
- **新模型上线**——**6 周 → 3 周**

**详细做法（How）**

该电商 Feature Store 的**5 大核心组件**：

1. **Iceberg 离线特征（核心创新）**
   - 关键设计：**特征以 Iceberg 表存储**，带 `event_time` 与 `partition`
   - 关键能力：**Point-in-Time 正确性**——用 `event_time <= 训练样本时间` 取特征，**杜绝特征穿越**
   - 关键数字：**特征穿越事故 -95%**
   - Point-in-Time 取数示意：
     ```sql
     -- 训练样本：label 时刻 t 的特征快照（严禁用到 t 之后的数据）
     SELECT s.user_id, s.label_ts,
            f.click_cnt_7d, f.gmv_30d
     FROM training_samples s
     JOIN feature_user_daily f
       ON f.user_id = s.user_id
      AND f.ds = date_sub(s.label_ts, 1)   -- 只用 t-1 及更早
     ```

2. **Redis 在线特征（核心）**
   - 关键设计：**Redis 存最新特征值**，`user_id → {feature: value, ts}`
   - 关键能力：**毫秒级在线读取**
   - 关键数字：**P99 < 5ms**

3. **Flink 实时特征（核心）**
   - 关键设计：**Flink 消费埋点流，实时更新 Redis**
   - 关键能力：**秒级特征新鲜度**
   - 关键数字：**特征延迟 < 10s**

4. **Feast 自研（核心）**
   - 关键设计：**特征定义 YAML 化**，一份定义生成离线 SQL + 在线 KV + Flink 作业
   - 关键能力：**定义与实现分离**，**从结构上消灭训练推理不一致**
   - 关键数字：**一致性 99.9%**
   - 定义示例：
     ```yaml
     feature_view: user_behavior
     entities: [user_id]
     ttl: 30d
     features:
       - name: click_cnt_7d
         dtype: int64
         offline: "SELECT user_id, ds, count(*) ... GROUP BY user_id, ds"
         online: {store: redis, ttl: 7d}
         streaming: {source: kafka://user_click, window: 7d}
     ```

5. **元数据（核心创新）**
   - 关键设计：**特征的 Owner / 血缘 / 使用方 / 质量分**统一登记
   - 关键能力：**特征可发现 + 可追责**
   - 关键数字：**找特征时间 -90%**

**该电商 Feature Store 关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **特征复用率** | 30% | 70%+ | **+133%** |
| **离线 / 在线一致性** | 90% | 99.9% | **+11%** |
| **ML 项目周期** | 100% | 60% | **-40%** |
| **特征穿越事故** | 基线 | -95% | **-95%** |
| **在线读取 P99** | 50ms | < 5ms | **-90%** |
| **找特征时间** | 基线 | -90% | **-90%** |
| **100+ 模型** | 各写各的 | 统一复用 | **统一** |

**具体数字（How much）**

- 团队规模：该电商特征平台团队 30+ 人
- 关键数字：**100+ 模型复用**；**一致性 99.9%**；**复用率 70%+**
- 业务影响：覆盖该电商 **100+ 模型**的推荐、搜索、广告

**失败教训**

- 早期「**同一特征三个团队各写一遍且结果不同**」——模型效果无法归因，倒逼**「统一 Feature Store + 定义即代码」**
- 「**只做在线不做 Point-in-Time**」——第一版特征表直接 join 最新分区，训练样本用到了未来数据，离线 AUC 0.85 而线上只有 0.65，倒逼**「补 Point-in-Time 正确性」**
- 「**特征定义与实现两套**」——YAML 只是文档、实际 SQL 另写，必然漂移，倒逼**「定义即代码，SQL 由定义生成」**
- 「**特征没有 Owner 与使用方登记**」——不知道谁在用、既不敢改也不敢下线，倒逼**「元数据统一登记 Owner / 血缘 / 使用方」**

### 1.2 某出行公司"**实时特征 端到端 50ms**"4+ 年（2020-2024）

**背景（Why）**

该出行公司 2020 年面临**实时供需匹配的特征瓶颈**：
- **实时供需匹配 / 实时定价**——**必须毫秒级特征**
- **特征算得慢**——原架构 **特征计算在请求链路里同步算**，一次要 **200ms**
- **高峰期劣化**——早晚高峰 **QPS 翻 5 倍，特征服务直接超时**

**触发点（What）**

2020 年该出行公司启动实时特征（[案例 2020]），目标：
- **端到端 < 50ms**（特征部分 < 20ms）
- **实时定价延迟**——**-60%**
- **订单匹配率**——**+10%**

**详细做法（How）**

该出行公司实时特征的**5 大核心组件**：

1. **Tecton 特征定义（核心创新）**
   - 关键设计：**声明式特征定义**，自动生成 Flink 作业与在线存储
   - 关键能力：**只写声明式定义，Flink 作业与在线存储由平台生成，不必手写流作业**
   - 关键数字：**特征开发周期 -70%**
   - 定义示意：
     ```python
     @batch_feature_view(entities=[driver, geo_cell], schedule="@every 5m")
     def driver_supply(ds): ...

     @stream_feature_view(entities=[geo_cell], schedule="@continuous")
     def live_demand(events): ...   # 近 5 分钟呼叫量

     @on_demand_feature_view(entities=[driver, geo_cell])
     def supply_demand_ratio(driver_supply, live_demand):
         return driver_supply / max(live_demand, 1)
     ```

2. **Flink 流式计算（核心）**
   - 关键设计：**窗口聚合在 Flink 侧完成**，请求链路只读不算
   - 关键能力：**请求链路与计算链路解耦**
   - 关键数字：**特征计算从请求链路移出，省 180ms**

3. **Redis 在线存储（核心）**
   - 关键设计：**分片 + 本地缓存 + 批量 MGET**，一次请求取 200 个特征
   - 关键能力：**批量取特征 < 20ms**
   - 关键数字：**P99 < 20ms**

4. **实时定价（核心）**
   - 关键设计：**供需比 / 拥堵指数 / 历史成交价**三类实时特征
   - 关键能力：**动态定价可解释**
   - 关键数字：**定价延迟 -60%**

5. **订单匹配（核心创新）**
   - 关键设计：**司机-订单匹配特征**（距离 / 方向 / 历史接单率）
   - 关键能力：**司机与订单两侧的距离、方向、历史接单率被同时建模**
   - 关键数字：**订单匹配率 +10%**

**该出行公司实时特征关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **端到端延迟** | 200ms | < 50ms | **-75%** |
| **特征部分延迟** | 180ms | < 20ms | **-89%** |
| **实时定价延迟** | 100% | 40% | **-60%** |
| **订单匹配率** | 基线 | +10% | **+10%** |
| **特征开发周期** | 基线 | -70% | **-70%** |
| **高峰 QPS 承载** | 1x | 5x | **+400%** |

**具体数字（How much）**

- 团队规模：该出行公司特征平台团队 20+ 人
- 关键数字：**< 50ms 端到端**；**订单匹配 +10%**；**峰值 5x QPS**
- 业务影响：覆盖该出行公司**全部订单**的匹配与定价

**失败教训**

- 早期「**特征在请求链路里同步计算**」——一次要 200ms、高峰直接超时，倒逼**「Flink 预计算 + 请求链路只读」**
- 「**只做 Redis 不做本地缓存**」——高频司机特征每次跨网络取、尾延迟卡在 60ms，倒逼**「加本地缓存 + 批量 MGET」**
- 「**特征 TTL 设置一刀切**」——司机位置特征 TTL 设成 30 分钟、用到过期位置导致派单错乱，倒逼**「按特征语义分别设 TTL（位置 30s）」**
- 「**每个特征都手写 Flink 作业**」——加一个特征要写一段流作业、开发周期以周计，倒逼**「改用声明式定义，自动生成作业与在线存储」**

### 1.3 某银行"**反欺诈特征 决策 < 30ms**"4+ 年（2020-2024）

**背景（Why）**

该银行 2020 年面临**毫秒级风控决策的特征工程复杂度**：
- **毫秒级风控**——转账决策必须 **< 30ms**
- **特征计算复杂**——**数百个特征**含滑动窗口、图特征、时序统计
- **监管可解释**——每个拒绝决策**必须给出特征依据**

**触发点（What）**

2020 年该银行启动反欺诈特征平台（[案例 2020]），目标：
- **决策延迟 < 30ms**
- **欺诈召回率**——**+20%**
- **特征数**——**100 → 数百**

**详细做法（How）**

该银行反欺诈特征的**5 大核心组件**：

1. **Flink 流式特征（核心创新）**
   - 关键设计：**滑动窗口 + 会话窗口**实时计算（近 1 分钟转账笔数、近 1 小时失败次数）
   - 关键能力：**近 1 分钟转账笔数、近 1 小时失败次数在交易发生时已经算好**
   - 关键数字：**特征延迟 < 500ms**
   - 窗口计算示意：
     ```sql
     -- 近 5 分钟同设备登录账户数（团伙信号）
     SELECT device_id,
            count(DISTINCT acct_no) AS login_acct_cnt_5m,
            HOP_END(ts, INTERVAL '1' MINUTE, INTERVAL '5' MINUTE) AS win_end
     FROM login_events
     GROUP BY HOP(ts, INTERVAL '1' MINUTE, INTERVAL '5' MINUTE), device_id;
     ```

2. **Redis 在线存储（核心）**
   - 关键设计：**分级存储**——热特征 Redis、冷特征磁盘 + 本地缓存
   - 关键能力：**数百特征批量取回**
   - 关键数字：**P99 < 15ms**

3. **自研 Feature Store（核心）**
   - 关键设计：**特征定义 + 血缘 + 可解释元数据**（每个特征有业务含义说明）
   - 关键能力：**每个特征带业务含义说明与血缘，拒绝决策能逐条给出依据**
   - 关键数字：**决策可解释率 100%**

4. **数百特征（核心）**
   - 关键设计：**统计特征 + 时序特征 + 关联特征（图）**三类
   - 关键能力：**覆盖团伙 / 盗刷 / 洗钱**
   - 关键数字：**特征数 100 → 数百**

5. **反欺诈集成（核心创新）**
   - 关键设计：**规则 + 模型双通道**，特征同时供两者消费
   - 关键能力：**规则可解释、模型可泛化**
   - 关键数字：**欺诈召回 +20%**、**误报 -40%**

**该银行反欺诈特征关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **风控决策延迟** | 200ms | < 30ms | **-85%** |
| **特征部分延迟** | 150ms | < 15ms | **-90%** |
| **欺诈召回率** | 基线 | +20% | **+20%** |
| **误报率** | 100% | 60% | **-40%** |
| **特征数** | 100 | 数百 | **+200%** |
| **决策可解释率** | 60% | 100% | **+67%** |
| **特征延迟** | 分钟级 | < 500ms | **-99%** |

**具体数字（How much）**

- 团队规模：该银行风控特征团队 30+ 人
- 关键数字：**< 30ms 决策**；**欺诈召回 +20%**；**可解释 100%**
- 业务影响：覆盖该银行**全部风控决策**

**失败教训**

- 早期「**数百特征在决策链路里同步计算**」——决策延迟压不到 30ms，倒逼**「预计算 + 在线只读」**
- 「**可解释性后补**」——模型先上线，监管要求解释时才发现特征没有业务含义标注、被迫回头补，倒逼**「特征定义时强制写业务含义」**
- 「**窗口边界没对齐**」——离线按自然小时、实时按滑动窗口，同一特征两个值不同，倒逼**「统一为滑动窗口 + 事件时间」**
- 「**热特征与冷特征用同一种存储**」——冷特征拖慢热特征读取，倒逼**「分级存储：热特征走 Redis、冷特征走磁盘 + 本地缓存」**

### 1.4 某短视频平台"**AI 原生 Feature Store**"3+ 年（2021-2024）

**背景（Why）**

该短视频 2021 年面临**传统特征与 LLM 特征两张皮**：
- **传统特征**——点击/时长/互动，在 Feature Store 里
- **LLM Embedding**——内容向量、用户向量，**散在向量库里**
- **Prompt 模板**——散在代码里，**改 prompt 要发版**
- **两套体系**——模型既要用传统特征又要用 embedding，**拼接靠手写胶水代码**

**触发点（What）**

2021 年该短视频启动**AI 原生 Feature Store**（[案例 2021]），目标：
- **传统 + LLM 统一**——一个 Feature Store 管三类资产
- **Prompt 版本化**——改 prompt 不发版
- **特征到模型一键接入**

**详细做法（How）**

该短视频 AI 原生 Feature Store 的**5 大核心组件**：

1. **传统特征（核心创新）**
   - 关键设计：**沿用原有 Feature Store**（离线 Iceberg + 在线 Redis）
   - 关键能力：**原有离线 Iceberg 与在线 Redis 照旧运行，新资产挂到同一注册中心**
   - 关键数字：**存量特征 100% 保留**

2. **LLM Embedding（核心）**
   - 关键设计：**embedding 作为「向量特征」纳入同一注册中心**，含模型版本 / 维度 / 距离度量
   - 关键能力：**embedding 可版本化、可回滚**
   - 关键数字：**embedding 版本可追溯 100%**
   - 注册示意：
     ```yaml
     feature: content_embedding
     type: vector
     dim: 1024
     model: bge-m3@v2.1        # 模型版本绑定
     distance: cosine
     store: {offline: iceberg://feat/content_emb, online: milvus://idx_content}
     consistency: "训练与推理必须用同一 model 版本"
     ```

3. **Prompt 模板（核心）**
   - 关键设计：**Prompt 作为「配置资产」注册**，支持版本 / A-B / 灰度
   - 关键能力：**改 prompt 不发版**
   - 关键数字：**Prompt 迭代周期 -80%**

4. **向量检索（核心）**
   - 关键设计：**Milvus + 离线 Iceberg 双写**，保证训练推理同源
   - 关键能力：**训练用离线向量、推理用在线向量，两侧来自同一次双写**
   - 关键数字：**召回一致率 99.5%**

5. **AI 集成（核心创新）**
   - 关键设计：**统一 SDK**——一次调用取「传统特征 + embedding + prompt」
   - 关键能力：**传统特征、embedding、prompt 一次调用取回，模型侧不必再拼三段代码**
   - 关键数字：**模型接入工时 -60%**

**该短视频 AI 原生 Feature Store 关键数字**（[案例 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **传统特征** | 100% | 100% | **保留** |
| **LLM Embedding 统一** | 未建设 | 已覆盖 | **新增能力** |
| **Prompt 版本化** | 未建设 | 已覆盖 | **新增能力** |
| **Prompt 迭代周期** | 基线 | -80% | **-80%** |
| **召回一致率** | 85% | 99.5% | **+17%** |
| **模型接入工时** | 基线 | -60% | **-60%** |
| **embedding 版本可追溯** | 0 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：该短视频 AI 平台团队 50+ 人
- 关键数字：**存量特征保留 100%**；**Prompt 迭代周期 -80%**；**召回一致率 99.5%**
- 业务影响：覆盖该短视频**全部推荐 / 搜索 / 生成**

**失败教训**

- 早期「**传统特征与 LLM 特征两套体系**」——模型接入要靠手写胶水代码，倒逼**「AI 原生 Feature Store 统一三类资产」**
- 「**embedding 不绑模型版本**」——换模型后旧向量与新向量混检、召回劣化 30%，倒逼**「embedding 必须绑定 model 版本」**
- 「**Prompt 存在代码里**」——改一个词就要走发布流程、迭代周期两周，倒逼**「Prompt 配置化 + 版本 + 灰度」**
- 「**向量库与离线特征各写一份**」——训练用离线向量、推理用在线向量、两边对不上，倒逼**「Milvus 与离线存储双写，保证同源」**

### 1.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**Feast 开源 Feature Store**」（**最简单**）——**10+ 特征**
- **必须一开始就做 Point-in-Time**——否则离线线上不一致无法回补
- 团队：**2-3 人**
- 验证标准：**离线 / 在线一致性 ≥ 99%**、**无特征穿越**

**1 → 10 阶段：6-12 个月**

- 扩展到「**100+ 特征 / 3+ 模型**」
- 引入「**Iceberg 离线 + Redis 在线**」**（**必须**）**——定义即代码生成两侧实现
- 引入「**元数据（Owner / 血缘 / 使用方）**」
- 团队：5-10 人
- 验证标准：**特征复用率 ≥ 60%**

**10 → 100 阶段：12-24 个月**

> - 真正的 ROI 来自「**复用 70% + 一致 99.9% + 决策 < 30ms**」——是**大厂核心 ML 基础设施的命脉**。
