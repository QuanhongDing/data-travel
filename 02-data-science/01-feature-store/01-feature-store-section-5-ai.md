## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本主题的清单里混着四种性质不同的东西：**既有机制**（离线 / 在线一致性、Point-in-Time 取数、物化、特征服务、漂移监控）、**把非结构化输入纳入治理**（Prompt 模板、Embedding、Tool 描述）、**交付形态的扩张**（FaaS、边缘、联邦）、以及**厂商的版本消息**。它们被并列成「演进方向」之后，最典型的一个误读是：把「平台能登记 prompt 了」当成「训练与推理的同源问题也解决了」——**登记与同源是两件事**。

特征平台还有一条别的主题没有的判据落点：它存在的理由**不是算得快，而是算得一致**。主文件 [§1.1](01-feature-store.md) 把「离线 / 在线一致性（Train-Serving Skew）」列为核心问题的第一条，「Point-in-Time 正确性」列为第五条；本章 [§3.1](01-feature-store-section-3-sec3.md) 进一步把八个模式的差异归结为**一条机制**——「特征值在什么时刻、由谁算出来，以及离线训练与在线推理凭什么保证拿到同一份值」。所以本节判一个新方向成不成熟，问的是两件事：**它有没有改变「谁在什么时刻算出这份值」**，以及**它能不能给出「同一份值」的证据**。

判一个方向能不能现在规划，本节用 L1 / L2 / L3 三级区分，判据是可核验的三条：

- **L1 生产可用**：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条全中才算，可以排进路线图。
- **L2 可试点**：已可用但接口 / 生态未稳，或只有厂商自有案例，或只在小规模被验证。可做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。记录，不要在架构里预留假设。

**判据声明（本节不对 L1 判据做任何修正；本表与 §5.2 的逐项评估完全一致）**：三条判据沿用到底，不替换、不放宽，也不为某一行另立说法。本主题下第②条是系统性不可得的，而且**非 AI 的既有机制行同样躲不开**：特征平台的运营细节（特征数、复用率、在线取数水位、一致性校验的差异率）属于企业内部数据，公开材料通常只到「某公司在做某类特征资产」，而这类材料绝大多数由产品方自己发布，正是 L2 定义所指的「仅有厂商自有案例」；既有机制那一侧能举出的也只是「多个彼此独立的项目各自实现了同一套机制」加上官方文档条目，同样给不出一个**可点名**的第三方（非厂商）生产案例。把「没有第三方公开案例」重写成「有公开的生产记录」「有可被第三方复核的机制性材料（论文 / 规范 / 官方文档）」，只是给同一条判据换措辞，读者按新措辞照样核验不了；**也不许借「这些行是非 AI 能力」把第②条换成别的标准**。本节的做法是：**够不到第②条的行一律判 L2，并在判据格里写明它卡在哪一条**。结果是**下表没有任何一行达到 L1**——包括那三条最像「既成事实」的非 AI 既有机制行（一致性、特征服务、漂移监控）；**也没有任何一个 AI 方向达到 L1**。读表时请把这一层看进去：**L2 不等于「不好」或「不能现在做」，只等于「公开证据到不了 L1」**。

四件最容易混的事，先在这里分开：

- **项目名 vs 能力名**：Feast 是**项目名**，`materialize`、Feature Server、Feature View 是**能力位**；「Feature Store」是能力名，不是任何一家的专属命名。各平台把「离线特征搬进在线存储」实现成什么接口，互不相同，不要张冠李戴。
- **已发布版本 vs 路线图**：判断某个能力能不能规划，只看一处——**该版本的 release note 或官方文档里有没有对应条目**；博客、生态伙伴转述、演示视频都不算。**版本号一律以官方发布页为准**（「Feast 0.40+」「Hopsworks 4.0」这类版本，本节不代为断言）。
- **论文里的原型 vs 产品里的实现**：判断某能力能不能开箱用，看官方文档里它有没有**配额、计费或 SLA** 三项中的至少一项，而不是看论文标题。
- **治理边界外扩 vs 机制变化**：把 Agent 的 Memory、Plan 或向量索引纳入平台管理，是**治理对象的外扩**；一致性机制、Point-in-Time 约束这些底层约束一条都没变。**外扩值得做，但不要写成架构升级**（本章 [§3.5](01-feature-store-section-3-sec3.md) 把「向量特征与传统特征分裂」列为反模式，说的正是外扩没做全的后果）。

本节有三件事不做：**不做产品选型**（同一能力在不同产品里的成熟度不同，选型看各产品官方文档与自家实测）；**不做性能断言**（取数延迟、召回率必须带条件：实体基数、特征数、召回目标、硬件）；**不做「未来蓝图」式描述**（写不出可观察信号的判断，都不写进 §5.6）。这三条边界决定了本节的结论会显得保守——**在一致性这类「错了才被发现」的问题上，保守才是准确的**。

读下面这张表时，先看第三列，再看第二列：**判据是可核验的，级别只是它的结论**。如果你不同意某个级别，正确的反驳方式是拿出「某条判据其实满足」的证据（点得开的页面与年份），而不是争辩「这个方向很重要」。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**？本主题的答案只有一条：**「特征」的边界从「结构化数值列」扩到「一次推理的非结构化输入快照（prompt / embedding / 索引）」**，于是版本化的对象从「列定义」变成「输入快照整体」。它改变的是**可复现性的对象与漂移指标的可得性**，没有改变主文件 [§1.1](01-feature-store.md) 的第一条与第五条核心问题：**同一份值、同一时刻**这两条约束不随输入形态改变，也不因模型变强而消失——这正是本节把「同一份值、同一时刻」相关的三条既有机制排在最前面、而把所有 AI 方向压在 L2 / L3 的原因。

**这三级排法直接决定路线图顺序**：

- **先做的三条就是上表前三行（那三条非 AI 的既有机制）**：Point-in-Time 与一致性机制 → 特征服务的 SLA 与契约 → 漂移监控与处置责任人。它们排在所有 AI 方向之前，因为**后面每一个 AI 宣称都要靠这三件事才能被复核**：没有时间对齐就没有「这份特征当时是什么值」这句话，没有 SLA 就没有「取数慢不慢」这句话，没有漂移监控就没有「效果变化是不是输入变了」这句话。注意它们的级别**仍是 L2**（第②条拿不出来）：动作可以今天就开始，但不要在评审材料里把它们写成「行业已普遍验证」的前提。
- **L2 做 PoC，并先测两个数**：**换 embedding 模型时的重算窗口**（见 §5.2.1 的推算）与**输入快照的可还原比例**（随机抽推理请求，看能不能还原 prompt / embedding 模型 / 索引快照三件）。这两个数拿不出来，L2 就停在原地。
- **L3 不排进排期**：Agent Feature Store 与 GraphRAG 图特征都属于「等信号」，它们的共同前提（治理对象界定清楚、图谱有 Owner 与质量口径）比选哪家平台重要得多。
- **回填机制**：每半年回填一次本行的级别；某个 L2 若一年内仍拿不到自己组织里的实测数字，降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。四个方向共用 §5.1 里的同一条机制（特征边界从数值列扩到输入快照），差别在**这条机制落在哪一层**——落在版本化对象上的是 §5.2.1，落在治理对象边界上的是 §5.2.2，落在数据放置上的是 §5.2.3，根本没落在 AI 上的是 §5.2.4。

| 方向 | AI 改变了什么机制 | 这条机制落在哪一层 |
| --- | --- | --- |
| §5.2.1 输入快照纳入治理 | 版本化对象从「列定义」换成「输入快照整体」 | **版本化对象**（可复现性的粒度变了） |
| §5.2.2 Agent 侧的特征化 | 治理对象从「训练 / 推理同源的值」换成「运行时状态」 | **治理对象的边界**（不是同一类资产） |
| §5.2.3 跨域特征与联邦 | 数据移动换成特征值 / 聚合量移动 | **数据放置**（合规边界由放置决定） |
| §5.2.4 交付形态与端侧 | 与 AI 无因果关系 | **交付与部署形态** |

读法建议：如果时间只够读一节，读 §5.2.1——它包含本主题里唯一一条**今天就可能让你少付一笔钱**的账（换 embedding 模型的全量重算窗口）；§5.2.2 的结论是「先做目录，别急着做平台」；§5.2.3 的失败点不在算法而在「同一个人、同一时刻」的定义；§5.2.4 的两条收益都真实，但**没有一条来自模型**。

#### 5.2.1 把「输入快照」纳入治理：LLM 特征与向量特征

- **旧做法与它的卡点**：旧平台的治理对象是「特征值」——一个实体键、一个时刻、一份数值。它成立的前提是**同一份定义能算出同一份值**。LLM / RAG 场景把这个前提打掉了：输入变成 prompt 模板、embedding、检索结果与索引快照，它们**非结构化、随索引变化、按 token 计费**，而且「同一份定义」不再意味着「同一次输入」。本章 [§3.2.5](01-feature-store-section-3-sec3.md) 把这层约束写成「LLM / RAG 场景下特征变成 prompt 模板、embedding、检索结果与工具描述」。
- **AI 改变了什么机制**：**版本化的对象从「列定义」换成「一次推理的输入快照整体」**——把 `(prompt_template@版本, embed_model@版本, index_snapshot@标识, retrieval_params@版本)` 作为一个不可分割的单元登记。机制的实质是**可复现性的粒度变了**：过去「复现一次推理」等于「拿到同一份特征值」，现在等于「还原整组输入与其版本」。
- **由此得到的**：因为输入快照被整体版本化，所以**效果变化第一次可以被归因到「输入变了还是模型变了」**——本章 [§3.2.5](01-feature-store-section-3-sec3.md) 把这写成这一模式的成立理由；过去 RAG 效果波动只能整体归因给「模型」或「运气」。

| 要登记什么 | 为什么要登记 | 不登记的后果 |
| --- | --- | --- |
| prompt 模板 + 版本 | 改一个词就会改变输出分布 | 改 prompt 要发版，或改完没人知道哪一版有效 |
| embedding 模型 + 维度 + 距离度量 | 换模型后旧向量与新向量不可比 | 新旧向量混检，召回悄悄劣化（本章 [§6 案例 1.4](01-feature-store-section-6-sec6.md) 把这条列为失败教训） |
| 索引快照标识（不是「当前索引」） | 索引内容会变，标识不变就无法复现 | A/B 结果不可信，且无法判断是输入变了还是模型变了 |
| 检索参数（召回条数 / 阈值 / 重排策略） | 同一索引下不同参数结果不同 | 复现时还原不出当时的检索行为 |

- **由此付出的**：**其一，重建成本是重成本**——【推算】换一次 embedding 模型的全量重算耗时 ≈（向量条数 × 单条编码耗时）÷ 并行度，且重算期间新旧索引并存，索引存储要付双份；这条链里每个量都要用自己的规模代入。**其二，漂移监控失去了简单指标**——结构化特征有 PSI / KS 这类单值度量，非结构化输入没有对应物，监控要么靠抽样人工评估、要么靠模型评测（本章 [§3.2.5](01-feature-store-section-3-sec3.md) 把它列为代价）。**其三，在线成本按 token 计费**，上下文越长单次调用越贵，这笔钱落在推理账单而不是存储账单上。**其四，版本登记不等于内容冻结**——若索引内容被静默重灌而快照标识没变，「可复现」这条优点会直接反转（本章 [§3.2.5](01-feature-store-section-3-sec3.md) 的失效点）。
- **证据与来源**：【公开】登记与检索侧有可核验的官方文档条目（判定入口：Hopsworks 官方文档的 embedding 与相似度检索条目、Tecton 官方文档中与 embedding / 向量特征相关的条目、Feast 官方文档的 on demand 与 stream feature view 两节；均为随版本更新的产品文档、无固定出版年份，具体支持范围以官方文档当前版本为准，可按「Hopsworks similarity search」「Feast on demand feature views」一类关键词自行检索核验）。【经验】「换 embedding 模型的重算窗口」与「输入快照可还原比例」这两组数，公开材料里没有通行口径——这正是它停在 L2 的直接原因。
- **成熟度**：**L2**。判据：① 相关产品有正式文档条目，但「prompt 与索引一起版本化」没有独立 release note；② 只有产品方材料；③ prompt 是配置资产，接口形态各家不同 → 做 PoC，不要作为核心依赖。
- **判定方法**：抽 10 次线上推理，看能不能还原出「prompt 版本 + embedding 模型版本 + 索引快照标识 + 检索参数」四件。缺任何一件，效果归因就只能靠猜。
- **什么时候值得做**：你已经能对传统特征说出「这一份值是哪个时刻算的」，并且开始遇到「改了 prompt 之后效果说不清」的问题时。
- **什么时候不值得做**：传统特征还没有 Point-in-Time 与版本管理时——**先把「同一份值」这件事做对，再去做「同一次快照」**。

#### 5.2.2 Agent 侧的特征化：治理对象变了，不是同一类资产

- **旧做法与它的卡点**：把 Tool 描述、Memory、Plan 散落在 Agent 代码与配置里，改一次要动代码、也没法横比。本章 [§3.5](01-feature-store-section-3-sec3.md) 的「向量特征与传统特征分裂」反模式，与 [§3.2.5](01-feature-store-section-3-sec3.md) 的 AI 原生模式要解决的问题同源：新资产散在两处，发现与血缘被切成两半。
- **AI 改变了什么机制**：**治理对象的边界外扩了，但对象本身不是同一类**。传统特征是「训练与推理必须同源的那个值」；Memory 与 Plan 是**运行时状态**（一次会话内产生、随会话变化、通常不参与离线训练）。把两者放进同一个注册中心，得到的是**目录层面的统一**，不是计算路径的统一——**这一条要老实说：它是治理边界的外扩，不是一致性机制的进步**。
- **由此得到的**：因为 Tool 描述与 prompt 被登记为可版本化资产，所以**Agent 的行为变更第一次可以像模型一样做灰度与回滚**（改的是配置资产，不必重新发布代码）——这是外扩带来的真实收益，也是它与「把配置写进代码」的区别。

| 资产 | 与传统特征的差别 | 该由谁保证什么 |
| --- | --- | --- |
| Tool 描述 / API 描述 | 影响的是「模型能不能选对工具」，不是特征分布 | 平台侧保证版本可回滚；调用方保证白名单 |
| Prompt 模板 | 变更影响输出分布，但没有分布指标可看 | 平台侧保证版本与灰度；效果由评测兜底 |
| Agent Memory | 运行时状态，随会话变化，一般不参与训练 | Agent 侧保证可清理与可追溯，平台只登记不承诺同源 |
| Plan / 中间产物 | 一次任务的临时状态，保留期短 | 调用方保证留痕，不进特征目录 |
| 图特征（实体关系图） | 依赖图谱质量与本体口径，更新节奏与特征表不同 | 图谱侧保证 Owner 与质量口径，否则不要作为特征源 |

- **由此付出的**：**其一，目录会被运行时状态污染**——把 Memory 这类高频变化对象登记进目录，会让「目录里有什么」失去稳定性，检索与复用反而变难；**其二，长期保留成本与合规成本**——Memory 可能含个人信息，保留期与访问控制要单独定（本书《数据血缘与影响面》[§ 5.1](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-5-ai.md) 把训练数据血缘判为 L2 的同一条理由也适用于此：采集面扩大，口径各家不同）；**其三，收益兑现依赖 Agent 侧的护栏先成立**，否则版本可回滚只是让错误回滚得更整齐。
- **证据与来源**：【公开】prompt 与工具描述作为配置资产的登记与灰度，在多个平台的官方文档里有条目（判定入口：各平台文档里 prompt 管理 / 工具注册相关一节）。【经验】「Agent 状态统一登记进特征目录」的公开生产材料以概念叙述为主——**判定方法**：查目标产品文档里 Memory 相关条目有没有写清**保留期、访问控制与删除接口**三项，有才是可治理的资产，没有就只是缓存。
- **成熟度**：**Agent 侧 L3；图特征 L3**。两侧的 L3 原因不同，分开写——**Agent 侧**：① 无独立 release note；② 无第三方机制级材料；③ 治理对象是运行时状态，与「训练 / 推理同源的值」不同类，接口无通行做法。**图特征**：① 无正式能力条目；**②核不到**；③ 图谱质量与 Owner、以及图特征与传统特征的融合口径都无通行做法（与 §5.1 表第 11 行同判） → 记录，不要在架构里预留假设。
- **判定方法**：问三个问题——这份资产**参与训练吗**？它**变更时有没有评测兜底**？它**保留多久、谁能读**？三问里「参与训练」答否，就不该按特征管理；后两问答不上来，就不该进目录。
- **什么时候值得做**：你有多个 Agent 在跑、且已经出现「改了 prompt 效果说不清」的问题时——此时先做的是**prompt 与工具描述的登记与灰度**，不是平台化改造。

#### 5.2.3 跨域特征与联邦：数据放置决定了合规边界

- **旧做法与它的卡点**：跨机构建模的旧路是**搬运**——把数据集中到一处再算。卡点在**合规**而不是算力：原始记录一旦出域，责任就被转移了，而很多行业的监管不允许。本章 [§3.2.6](01-feature-store-section-3-sec3.md) 把这条约束写成「数据不能出域（跨机构、跨法人、受监管子域），但模型需要多方特征」。
- **AI 改变了什么机制**：**把「原始记录移动」换成「特征值或聚合量移动」**。机制变化是真的：**合规边界由「数据放在哪」决定**，而不是由访问控制的自觉决定（本章 [§3.2.6](01-feature-store-section-3-sec3.md) 把这一条写成该模式的成立理由）。
- **由此得到的**：因为交换的是特征值而不是原始记录，所以**数据不出域与多方共建特征第一次能同时成立**——联合风控、联合营销这类场景第一次有了在合规边界内可做的技术形态。

```text
联邦特征平台的失败点：契约统一了「字段」，不一定统一了「同一个人、同一时刻」
   A 域                                  B 域
   特征表 ──► 特征值 ─┐                  特征表 ──► 特征值 ─┐
                      ├── 统一特征契约（字段 + 语义 + 时间口径）──┤
   实体对齐（ID 映射，各方自持）──────────┘
  ────────────────────────────────────────────────
   两类错位都会静默发生：
     · 实体错位：A 的 user_id 与 B 的 user_id 不是同一人
     · 时间错位：一边按自然日、一边按滑动窗口，同一特征两个值
   后果：模型学到的是拼接噪声，且因为看不到对方原始数据，
         排查极其困难（本章 §3.2.6 的失效点）
   → 所以第一件交付物不是平台，是这两份口径的书面约定与联调用例
```

- **由此付出的**：**其一，实体对齐与时间口径统一的协调成本**（跨方评审、联调）是长期成本，不是一次性工程；**其二，契约变更要所有参与方同时升级**，升级节奏受最慢的一方支配；**其三，跨域调用的延迟与失败处理复杂度**上升；**其四，「只交换特征值」不等于没有隐私风险**——中间量仍可能反推样本（Zhu, Liu, Han, "Deep Leakage from Gradients", NeurIPS 2019【公开】），隐私参数要单独评估。
- **证据与来源**：【公开】联邦平均（McMahan et al., AISTATS 2017）与梯度泄露反证（NeurIPS 2019）给出了原语与风险两侧的出处；本章 [§3.2.6](01-feature-store-section-3-sec3.md) 已把这一模式的代价与失效点写全。【经验】「联邦特征平台」的公开材料以方向叙述为主，**没有给出参与方数量 + 实体对齐口径 + 时间口径**这一组成对描述——这是它判 L2 的直接原因。
- **成熟度**：**L2**。判据：① 原语层有论文与多个独立实现；② 特征平台一侧只有方向叙述；③ 跨方契约与实体对齐口径无通行做法 → 做 PoC，不要作为核心依赖。
- **判定方法**：让对方给出两样东西——**实体对齐的判定用例**（怎么证明两边说的是同一个人）与**时间口径的对照表**（同一天的两个值能不能对上）。给不出来，方案就还停在纸面。
- **什么时候值得做**：监管明确要求原始记录不出域、参与方数量可枚举（个位数到十几个）时。
- **什么时候不值得做**：你的真实约束只是「不想把数据给别人看」——那该做的是访问控制与脱敏，不是联邦。

#### 5.2.4 交付形态与端侧：与 AI 无因果关系的两条

这两条都被写进了「AI 时代的特征平台演进」，但机制与 AI 无关：

| 方向 | 旧做法与它的卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据 / 成熟度 |
| --- | --- | --- | --- | --- | --- |
| Feature as a Service | 特征以代码或表交付，上游 schema 变更会穿透所有消费方 | **没有改变机制**：改的是交付物形态（API 契约）与随之而来的配额、授权、计量 | 特征可以按消费方限流、单独授权与计费，上游表结构变更不必穿透到调用方 | 特征服务成为所有模型共享的关键路径，一次抖动同时打穿全部线上模型；契约治理是持续的组织成本 | 判定入口：Feast 的 Feature Server 与 Tecton 的 feature service 官方文档条目；**第②条核不到**（无可点名的第三方非厂商生产案例） → **L2（非 AI 能力，工程底座；与 §5.1 表第 2 行同判）** |
| 边缘 Feature Store | 云端在线特征在断网与隐私约束下不可用 | **与 AI 无因果关系**：改的是部署位置（慢特征下发、快特征本地算） | 原始数据不出设备、断网也能推理，隐私与可用性同时改善 | 端侧有硬预算（特征包大小、内存、电量）；特征定义两端各一份，版本对齐依赖设备联网；云端无法直接回填端侧特征 | 判定入口：端侧推理是既有工程实践，无「边缘特征平台」的正式能力条目 → **L2** |

**这两条的共同读法**：收益都真实存在，但**没有一条来自模型**——一条来自交付物形态（API 与契约），一条来自部署位置。把它们写成「AI 时代的特征平台演进」，会让真正要做的三件事（Point-in-Time 取数、特征服务 SLA、漂移监控与处置）一件都排不进排期。

再看一层：§5.2.4 与 §5.2.1 的差别很明显——前者要**先有组织约定**（谁能调、配额多少、两端版本怎么对齐）才能兑现，后者**取决于你什么时候动手**（快照登记做不做、重算窗口算不算）。排期时应优先做取决于自己的那一类。

### 5.3 与本主题既有栈的接口在哪

特征平台与 AI 之间不是「结合」关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比「能不能用」更能决定它能不能落地。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 特征平台 ↔ 数据血缘与影响面（[数据血缘与影响面](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)） | 交接物 = 「特征 ↔ 上游字段」的边；**上游改了表结构，要能列出受影响的特征与模型** | 双方共用：特征侧漏采，整条链路就断，且断点在下游看不见 | L1（采集机制）/ L2（口径与采集面，与 [§ 5.3](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-5-ai.md) 的判定一致） |
| 特征平台 ↔ 数据目录（[数据目录](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 交接物 = Feature Catalog 的元数据（含义 / Owner / 版本 / 使用方）；**Feature Catalog 是数据目录的子集**（主文件 [§2.4](01-feature-store.md)） | 目录侧：登记不强制时，特征发现退化成问人 | L1（登记与检索机制）/ L2（特征的机器可读口径） |
| 特征平台 ↔ 向量湖与向量库（[向量湖](../../04-data-assetization/02-vector-lake/02-vector-lake.md)） | 交接物 = 向量特征的版本（embedding 模型 + 维度 + 距离度量）与**索引快照标识** | 双方共用：索引静默重灌而标识未变时，「可复现」不成立 | L1（索引与检索能力）/ L2（索引是否随快照版本化） |
| 特征平台 ↔ RAG 架构（[RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md)） | 交接物 = 一次检索的输入快照（query 处理 / 召回参数 / 重排策略 / 索引版本） | RAG 侧：只版本化 prompt、不版本化索引时，效果归因失效 | L2 |
| 特征平台 ↔ 模型管理与评估（[模型管理](../../01-modeling/11-model-management/11-model-management.md)、[模型评估](../../02-data-science/07-eval/07-eval.md)） | 交接物 = 模型版本与特征版本的绑定；**回滚模型必须能回到当时的特征定义** | 特征侧与模型侧共同：绑定缺失时回滚只能靠重跑 | L1（版本注册）/ L2（跨系统的绑定口径） |
| 特征平台 ↔ 湖仓与表格式（[湖仓一体](../../03-data-stack/03-lakehouse/03-lakehouse.md)） | 交接物 = 特征表所在表格式的**时间旅行快照**；训练按样本时刻取快照 | 湖仓侧：表被设计成覆盖写的最新快照表时，时间旅行无处可依 | L1（表格式与时间旅行）/ L2（特征表是否保留历史） |
| 特征平台 ↔ 流处理（[流式存储](../../03-data-stack/04-streaming-store/04-streaming-store.md)） | 交接物 = 流状态保留期（state TTL）与「要支持多久的回填 / 重放」这一需求的对齐 | 流侧：TTL 短于回填需求时，历史不可重算（本章 [§3.2.2](01-feature-store-section-3-sec3.md) 的失效点） | L1（流式计算能力）/ L2（TTL 与回填需求的显式对齐） |
| 特征平台 ↔ 数据质量（[数据质量](../../11-cross-cutting/01-data-quality/01-data-quality.md)） | 交接物 = 特征的校验规则与阈值，以及**漂移告警的处置责任人** | 质量侧：没有处置责任人的告警等于没有告警 | L1（校验与阈值机制）/ L2（特征级阈值的可比性） |
| 特征平台 ↔ 隐私计算（[隐私计算](../../11-cross-cutting/08-privacy-computing/08-privacy-computing.md)） | 交接物 = 参与方 / 协议 / 隐私参数 / 处理位置（见 §5.2.3）；**实体对齐表各方自持** | 协作方共同：一方不遵守协议，全局保证不成立 | L1（原语）/ L2（跨方口径约定） |

一句话概括：**AI 没有给特征平台新增任何一致性原语，只新增了一类需要版本化的输入**。这张表「现状」列用同一套 L1 / L2 字面，但**评的是这个接口本身，不是 §5.1 表里的演进方向**——这里的「L1」指该接口的机制已稳、可以直接排期，「L2」指机制可用但口径或责任还没统一；两者不要互相引用，否则同一个 L1 会在两处指两件事（例如漂移监控的采集接口已稳，但它作为演进方向因缺第②条判 L2）。特征场景下最常出问题的不是算力，而是「两边对同一个特征的理解不一样，谁也没错」。

由此得到三条约定。

**第一条约定：没有 `event_time` 的特征表，不算特征。** 覆盖写的最新快照表能服务在线推理，但训练与回填同时失去依据（本章 [§3.1](01-feature-store-section-3-sec3.md) 的约束表把这一条列为最容易被推翻的直觉）。

**第二条约定：先把「同一份值」做对，再谈「同一次快照」。** 两类一致性口径不同：结构化特征靠同一份定义与同一条加工链路保证；非结构化输入靠整组输入的版本标识保证。**混用口径是本节最容易犯的错**——用 PSI 去监控 prompt 版本，或用「特征定义版本」去代替「索引快照标识」。

**第三条约定：特征服务的 SLA 要写进模型的上线条件。** 否则一次取数抖动会同时打穿所有线上模型，而事后没人能说清这次抖动该由谁负责。

### 5.4 公开进展与文献

分三类列，三类的著录口径不同：**论文与著作**只列能给出标题 + 会议（或发表年）的条目；**官方文档与发布页**给的是**可点名的页面**——这类文档持续更新、没有固定出版年份，因此本类不给年份（主文件已记有发布时点的条目照记，如 Databricks 2020 年、Tecton 2021 年商业化）；**第三方生产案例**本节给不出可核验的条目，理由见该类第一条。三类都属判定入口，进页面即可核对，**宁少勿假**，具体版本与能力一律以页面当前内容为准。

**论文与著作（可核验）**

- Sculley et al., "Hidden Technical Debt in Machine Learning Systems", NeurIPS 2015——训练数据的依赖是隐性债务，也是「离线 / 在线两套代码」这类反模式的理论出处。
- Baylor et al., "TFX: A TensorFlow-Based Production-Scale Machine Learning Platform", KDD 2017——把「训练 / 服务一致性」写成平台性问题的公开文献之一（主文件 [§1.4](01-feature-store.md) 记为 2017 年 Google 发布 TFX）。
- McMahan et al., "Communication-Efficient Learning of Deep Networks from Decentralized Data", AISTATS 2017——联邦平均，§5.2.3 的原语出处。
- Zhu, Liu, Han, "Deep Leakage from Gradients", NeurIPS 2019——「只交换梯度不等于隐私」的反证，§5.2.3 代价一侧的依据。
- **五条学术条目本节不当作证据**（Feast + Milvus 集成论文、Hopsworks GenAI 论文、Vector / Federated / Streaming Feature Store）——它们给的是主题名而非可检索标题与作者。处理办法：**保留它们所指的方向**（向量特征工程化、联邦特征、流式特征），但只作方向，不作依据。

**官方文档与发布页（判定入口）**

- **Feast 官方文档**（docs.feast.dev）——核三件事：离线存储与 `materialize` 物化流程、Feature Server、以及 on demand / stream 两类 feature view。**判定方法：看文档里该能力标的是 GA 还是实验特性，再看它有没有配额或 SLA 说明**（「Feast 0.40+」一类版本号一律以发布页为准）。
- **Databricks Feature Store 文档**（docs.databricks.com，2020 年起的文档）——核「特征表落在 Delta Lake 上」这一条（主文件 [§1.4](01-feature-store.md) 记为 2020 年发布）。
- **Tecton 官方文档**（docs.tecton.ai）——核 feature service、流式聚合与 embedding 相关条目的当前状态；主文件 [§1.4](01-feature-store.md) 记为 2021 年商业化。
- **Hopsworks 官方文档**（docs.hopsworks.ai）——核 embedding 与相似度检索条目、以及是否提供表格式对接一类的条目。**判定方法：查文档里有没有「外部特征组 / 表格式对接」并明确列出 Iceberg 或 Hudi 及版本**（本章 [§3.2.7](01-feature-store-section-3-sec3.md) 已用同一条判定方法）。
- **Milvus 与主流向量库的官方文档**——核「索引快照能否版本化、重灌数据后快照标识是否变化」；判定入口与判据见本书《向量湖》[§ 5](../../04-data-assetization/02-vector-lake/02-vector-lake-section-5-ai.md)。
- **国内平台（阿里云 PAI 特征平台、字节 ByteFS、腾讯 TI-EMS）**——本节不一一代言其能力：**判定方法：查各平台官方文档里的能力条目与版本记录，不看发布会介绍页**。
- **怎么用这份清单**：要核「能力存不存在」看官方文档与发布条目（最快）；要核「接口稳不稳」看版本兼容说明与弃用策略（最稳）；要核「在我这里值不值得做」看 §5.2 每条的判定方法——**第三类问题没有任何公开材料能替你回答**。

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含机制细节（实体基数、特征数、在线取数水位、一致性校验差异率）的第三方「特征平台 + AI」生产案例。本章 [§6](01-feature-store-section-6-sec6.md) 的四个案例（某头部电商、某出行公司、某银行、某短视频平台）出处标注为「案例 + 年份区间」，划在自述一类——它们能支撑「Point-in-Time 取数」「实时特征移出请求链路」「embedding 绑定模型版本」「向量双写」这一层的做法，**不能充当 AI 方向的第②条**。§5.1 表第 13 行里列出的企业案例（含 Uber Michelangelo 这类有公开工程文章可查的）同理：文章可核，其中的量级数字属自述口径。**这个空白本身是结论**：它正是本节把所有 AI 方向判在 L2 / L3 的直接原因。
- 要补第②类证据，最实际的办法是自己造：把特征数、复用率、在线取数 P99、一致性校验差异率、回填时长留存成口径。这五组数在特征平台评审里的分量，超过任何厂商案例。
- 三类证据里**最容易造假的是「一致性提升到小数点后几位」**：只报数字而不给校验方法与基线，无法复核。**判定方法：只接受同时给出「校验方式（抽样比对还是全量比对）/ 比对频率 / 基线」三样的数字。**
- 本主题三类证据的分布是不均衡的：**第一类（官方文档与发布条目）很密**——物化、特征服务、feature view 分类、向量检索都有正式条目；**第二类（第三方案例）很稀**——特征平台的运营指标天然留在企业内部；**第三类（带口径的对照数据）几乎为零**——一致性差异率、重算窗口这类数，公开材料里没有可复算的口径。这个分布不是偶然：**它正是「平台型能力」的典型形态**——能力能被公开，运营数据不能。因此本主题的路线图应该照着「自证型」来定：先把口径定下来自己测，再拿结果去说服人。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：
1. **Point-in-Time**：抽 5 个训练样本，看能不能说清每个特征用的是哪个时刻的值。
2. **一致性**：把线上真实流量的一段特征快照拿回离线复算，看值是否相同。
3. **快照可还原**：抽 10 次线上推理，还原「prompt 版本 + embedding 模型版本 + 索引快照标识 + 检索参数」。
4. **重算窗口**：按 §5.2.1 的推算算一次换 embedding 模型的耗时与双份索引空间。
5. **服务 SLA**：问「特征服务抖一次，哪些模型会同时受影响、由谁负责处置」。
6. **血缘贯通**：问「上游表结构变更时，能否一键列出受影响的特征与模型」。

### 5.5 被过度宣传的部分

**「AI 原生 Feature Store = 传统 + LLM + 向量特征统一管理，一次解决」**——实际是：**统一的是目录，不是计算路径**。传统特征要求「同一份值」，非结构化输入要求「同一次快照」，两类一致性由不同机制保证：前者靠「同一份定义与同一条加工链路」（本章 [§3.2.1](01-feature-store-section-3-sec3.md) 的单一计算路径、[§3.2.2](01-feature-store-section-3-sec3.md) 的同源算子），后者靠「输入快照整体版本化」（本章 [§3.2.5](01-feature-store-section-3-sec3.md)）。**为什么会这样**：把「能登记在一起」当成了「能一致地算出来」，而登记只是元数据动作。**它什么时候才会成真**：换一次 embedding 模型后，平台能给出「新旧索引并存期的召回对照口径」与「受影响模型清单」，而不是让用户自己保证同源。**判定方法**：问「上一次 embedding 模型升级，怎么列出受影响的模型与训练样本」，答不上来就说明统一只发生在目录层。

**「向量特征 + 传统特征统一管理就等于混合检索能力」**——实际是：**混合检索是查询侧能力，统一管理解决的是治理侧问题**。向量库先于平台引入时，两套元数据会把特征发现与血缘切成两半（本章 [§3.5](01-feature-store-section-3-sec3.md) 的「向量特征与传统特征分裂」）。**为什么会这样**：把「同一个页面上能搜到两类资产」当成了「它们可以被同一条链路加工与追溯」。**它什么时候才会成真**：两类资产的元数据与血缘进同一张图，且向量特征也能回答「上游字段变了会影响谁」。**判定方法**：问「这张向量特征表的上游是哪张业务表、变更后影响哪些模型」——答不上来，两者的治理仍是分开的。

**「联邦特征平台让数据不出域，所以跨机构建模没有代价」**——实际是：**它解决的是数据放置问题，不解决「同一个人、同一时刻」的问题**。契约统一了字段，不等于统一了实体对齐与时间口径（本章 [§3.2.6](01-feature-store-section-3-sec3.md) 的失效点：模型学到的是拼接噪声，且因为看不到对方原始数据，排查极其困难）。**为什么会这样**：把合规约束的解法当成了建模质量的解法。**它什么时候才会成真**：公开材料给出**参与方数量 + 实体对齐判定用例 + 时间口径对照**这一组三件套。**判定方法**：让对方证明「两边说的是同一个人」——用具体用例证，不用组织结构图。

这三条的共性：**它们都把「某个环节变得更容易」当成了「整套机制已经成立」**——登记更容易、检索更容易、数据放置更容易。而本主题的判据始终只有一条：**你能不能指出这条宣称改变了「谁在什么时刻算出这份值」，并且证明它真的变了。** 没变的，就是目录或交付形态的改良。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| AI 原生的落点会先出现在**目录与注册中心**（prompt / embedding / 索引的版本登记与回滚），而不是计算路径的统一 | 平台发布条目里出现版本登记与回滚，但同源保证仍写成「由使用方负责」 | 出现「换 embedding 模型后训练与推理自动同源」的可核验机制说明，且不依赖使用方自觉 |
| 特征平台的验收指标会从**复用率**转向**可复现率** | 平台文档或评审材料里出现「任意一次推理的输入快照可还原」这一条，并给出抽样方法 | 行业仍把复用率与调用量当作唯一验收口径，且无人能回答「三个月前那次推理用了什么」 |
| 向量特征的治理会先收敛到**「绑定模型版本 + 索引快照标识」**，而不是先收敛到「统一特征平台」 | 向量库与特征平台的正式条目里出现索引快照标识与重建窗口的说明 | 出现跨平台统一「向量特征规范」并被多方独立实现 |
| 联邦特征平台会停在**强监管的垂直场景**（联合风控、医疗协作），不会成为跨企业特征共享的默认形态 | 公开材料同时给出参与方数量与实体对齐口径，且场景集中在受监管行业 | 出现多方参与、跨行业、并披露对齐口径与效果对照的公开生产案例 |

写这四条时的共同约定：**信号必须是外部可观察的**（正式功能条目、发布说明、带口径的公开案例），而不是「我觉得会」。**被检验得最快的是第三条**——下一批向量库与特征平台的发布说明里有没有「索引快照标识」，一两年内就能看到；**最慢的是第四条**——它是一种否定式预测，需要有人长期公开参与方规模与对齐口径。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已经有特征平台，但没人在意取数时刻 | 先给取数加 `event_time <= label_time` 的强制约束，并抽查 5 个样本 | 观察一致性校验差异率是否纳入定期报告 | 不要先接 LLM 特征——未来的问题会盖住现在的问题 |
| 业务方要求「把 Prompt 也管起来」 | 先做 prompt / 工具描述的登记与灰度回滚 | 观察改 prompt 是否还需要发版 | 不要把它说成「特征平台升级为 AI 原生」 |
| 准备换 embedding 模型 | 先算重算窗口与双份索引空间（§5.2.1 的推算） | 观察新旧索引并存期的召回对照是否可做 | 不要在旧向量与新向量混合检索的情况下直接切流 |
| 团队在推「Agent Feature Store」 | 先问三个问题：它参与训练吗？变更有没有评测兜底？保留多久、谁能读？ | 观察 Agent 侧的工具白名单与留痕是否先落地 | 不要把 Memory、Plan 这类运行时状态按特征管理 |
| 跨机构要联合建模 | 先写实体对齐判定用例与时间口径对照表 | 观察参与方与协议是否稳定 | 不要先搭联邦平台——口径没对齐时，平台只放大错位 |
| 多团队共享特征、要计量 | 先给特征服务定 SLA 并写进模型上线条件 | 观察一次抖动的影响面是否可枚举 | 不要在 SLA 未定义时把核心模型全部迁到共享取数入口 |
| 端侧要离线可用 | 先定特征包版本、有效期与降级策略 | 观察两端版本不一致时模型表现如何 | 不要指望云端回填端侧特征——历史样本只能来自上报 |
| 有人在推「用 LLM 自动生成特征」 | 先定生成结果的验收与抽样复核比例 | 观察「直接可用比例」是否上升 | 不要让无签字生成的特征直接进训练集 |
| 预算有限，只能做一件事 | 做 **Point-in-Time 取数 + 特征版本绑定**（它同时喂饱回填、评估与审计） | 观察历史模型能否复现 | 不要把预算先花在接向量库或买 AI 原生版本上 |
| 要给管理层一份判断 | 写成三行：特征数 / 一致性校验差异率 / 在线取数 P99 | 观察这三行能否被第三方按口径复核 | 不要用「我们上了 AI 原生特征平台」代替数字 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（重建索引、改计算路径、引入新的在线依赖），**而收益依赖一个尚未成立的假设**（生成即正确 / 统一登记即同源 / 数据不出域即无代价）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**「特征」的边界从结构化数值列扩到一次推理的非结构化输入快照**——于是版本化的对象从「列定义」变成「prompt 模板 + embedding 模型 + 索引快照 + 检索参数」这一整组，可复现性的粒度随之改变。它**没有**改变主文件 [§1.1](01-feature-store.md) 里的第一与第五条核心问题：**离线训练与在线推理要拿到同一份值、训练样本不能用到未来的信息**——这两条约束与输入形态无关，也不随模型变强而消失。
> 
> 判断本主题下任何新提法的快捷方式：**它改变的是「谁在什么时刻算出这份值」，还是只把新资产登记进了目录？** 前者改变可用性（上表最前那三条既有机制，以及 §5.2 里落在这条机制上的方向），后者先要付口径与验收的成本（本节判 L3 的那些）。第二条同样快的判断：**这件事能不能在没有任何 AI 的前提下先做完**——能做完的（Point-in-Time 取数、特征服务 SLA、漂移监控与处置），今天就该排进路线图。
> 
> 如果只能带走一句话：**先让「同一份值」成立，再让「同一次快照」成立**；顺序反过来，就是给一个连时间对齐都没做的平台，接上一类更难复现的资产。
>
