## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

「实时特征」一栏给 Feast 3 分、Tecton 5 分。这 2 分不是能力的绝对差距——**在你没有秒级新鲜度需求时，它的实际价值等于 0**。同一张表里，「工程门槛」一行又给出 Feast 3 分、自研 5 分，可门槛的权重取决于你有没有 2 个能常驻维护流状态的工程师，而这个前提表里没有。

打分表的根本问题是把「在某种约束下的价值」写成了「绝对能力」。约束一变，权重就反转：天级更新的离线训练团队里，实时能力是负资产（多一条常驻链路要运维、要有人懂它的语义）；实时风控团队里，同样的能力是准入门槛。**同一维度在不同约束下权重相反，这是打分表修不好的缺陷**，只能换成「先用判据筛掉不适用的族，再在族内比可比的少数几项」。

判据也不能太多。特征平台的选型分歧，最终几乎都能归到三个机制上：**谁拥有计算路径、时间语义在哪里被强制、以及取数发生在哪条链路**。下面 6 条判据就是把这三个机制问清楚，剩下的都是它们的推论。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 计算路径归属 | 离线与在线的加工由谁生成、由谁维护 | 决定一致性由机制保证还是由流程纪律保证，也决定出问题时有没有外部责任方 |
| 时间语义 | 特征表有没有 `event_time`，取数能否按 `label_time` 对齐 | 决定训练样本是否可能泄漏未来信息——这直接决定模型效果是否可信、能否复现 |
| 取数链路位置 | 特征值在事件发生时算好，还是请求到达时算 | 决定延迟量纲从「模型复杂度」变成「存储 QPS」，也决定你要不要常驻一条流链路 |
| 成本结构 | 特征数 × 物化频率、以及回填窗口有多长 | 决定这是运营支出问题还是一次性工程问题（回填常比日常物化更贵） |
| 资产类型覆盖 | 只覆盖结构化特征，还是也要管 embedding 与 prompt 快照 | 决定「统一」发生在目录层还是计算层——这两者的验收方式完全不同 |
| 部署与数据边界 | 托管 SaaS、私有化，还是跨机构联邦 | 决定锁定程度，以及哪些数据根本不允许进平台 |

> 六条判据的顺序不是随意的：前两条是**准入项**——不满足就谈不上选型；中间两条决定**成本结构**；后两条只在特定场景下才是否决项（要管 embedding、或数据不能出域）。

**判据分两步用**：前两条（计算路径归属、时间语义）是**准入筛**，筛掉的是「机制上做不到一致性」的方案，不是「不太好用」的方案——一个平台若无法把 `event_time` 做成特征表 schema 的必填项，它在准入这一关就出局，实时能力再强也补不回来。后四条（取数链路、成本结构、资产类型、部署边界）是**权重筛**，它们的取值通常只影响排序；但如上文所述，当「要管 embedding」或「数据不能出域」成立时，其中资产类型覆盖与部署边界两条会升级为否决项。

再举一个权重反转的例子：同一张表给「向量特征」打分，对做传统推荐 / 风控的团队而言，向量能力接近无用（他们的特征都是数值与类别）；对做 RAG 的团队而言，它决定平台能不能被选——**同一个能力在两边的权重分别是 0 与 1**，而这取决于你要解决什么问题，不取决于产品本身。

**分数唯一可以保留的形式是「机制依据 + 排序」**：若一定要排序，每一行都必须能写出「因为它的 X 机制，所以在 Y 条件下它排前面」。本章 §7.6 的矩阵就是这种形式——它回答的是「在你这个处境下首选谁」，不是「谁分高」。

**把它落到两个场景上看**：一个 2–3 人、天级更新、单业务域的团队，判据结果是「准入项通过（有 `event_time`）、权重项全指向离线优先」，此时实时能力与资产类型覆盖都不该进入评分；一个决策预算在几十毫秒级的实时风控团队，判据结果是「准入项通过、取数链路必须移出请求链路、部署边界要求私有化」，此时「开源」这一项与它几乎无关。**同样的候选在这两个场景里的排序几乎是反向的**——这正是打分表承载不了的那部分信息。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Feast | 开源特征框架 | 一份定义生成离线取数与在线物化两条路径 | 中小 ML 团队、愿意自接在线存储的团队 | 开源（LF AI & Data 托管项目） |
| Tecton | 商业托管特征平台 | 声明式定义由平台编译成批 / 流两条聚合链路 | 实时推荐 / 实时风控团队 | 商业 SaaS |
| Hopsworks | 开源 + 商业的 AI 平台 | 特征、模型与湖仓对接在同一平台上管理 | 既跑传统模型又跑 LLM 应用的组织 | 开源 + 商业版 |
| 阿里 FeatureDB / PAI 特征平台 | 云厂商托管 | 特征表与在线服务同在一个云生态内 | 阿里云用户 | 商业（云服务） |
| 字节 ByteFS | 云 / 内部托管 | 与字节的训练框架和存储同生态集成 | 字节生态 | 商业 / 内部平台 |
| 腾讯 TI-EMS | 云厂商托管 | 同上，生态内集成省掉适配 | 腾讯云用户 | 商业（云服务） |
| Databricks Feature Store | 湖仓内建 | 特征表就是 Delta 表，在线同步与血缘随表走 | 已在 Databricks 上跑 ML 的团队 | 商业（平台内置） |
| AWS SageMaker Feature Store | 云厂商托管 | 在线 / 离线双存储由托管服务维护 | AWS 全栈团队 | 商业（云服务） |
| GCP Vertex AI Feature Store | 云厂商托管 | 同上，与 Vertex 训练管线绑定 | GCP 全栈团队 | 商业（云服务） |
| Azure ML Feature Store | 云厂商托管 | 同上，与 Azure ML 管线绑定 | Azure 全栈团队 | 商业（云服务） |
| 自研 | 完全自建 | 计算路径与存储都是自己的，可做任何加工 | 有平台团队的大厂 | 自建 |

这 11 个候选其实是四个族：**A 开源框架族**（Feast、Hopsworks 开源版）、**B 云生态托管族**（Databricks、SageMaker、Vertex AI、Azure ML、阿里 PAI、ByteFS、TI-EMS）、**C 端到端商业平台族**（Tecton），以及**自研**。四族的差别不在功能清单，而在**谁拥有计算路径**：A 族与自研是「你拥有」，B / C 族是「平台拥有」。自研之所以单列而不并入 A 族，是因为 A 族至少给了你一份现成的定义生成器与物化编排，自研连这一层也要自己写，且一致性没有外部参照——本章后面几张按族列的表（紧接的这张、§7.3.1 的候选族表、§7.4 的族表）都按这四组列；§7.3.4 的责任划分表只分「托管 / 你拥有」两栏，是这四族的合并读法。这一条决定了后面所有代价的归属——一致性出问题找谁、平台表达不了的加工往哪放、迁移时要重写什么。**同族内部几乎没有需要比较的差异**（B 族是同一类托管能力在不同云 / 生态里各取一个名字：Databricks 之于自家湖仓、SageMaker 之于 AWS、Vertex AI 之于 GCP、Azure ML 之于 Azure，一家云一个），跨族才是真选择；先分族再选，能省掉一半比较。

| 族 | 谁拥有计算路径 | 一致性谁负责 | 能力上限由什么决定 | 迁移代价主要落在 |
| --- | --- | --- | --- | --- |
| A 开源框架 | 你 | 你 | 你的工程能力 | 换框架要重写定义与物化编排 |
| B 云生态托管 | 平台，且与该云存储绑定 | 平台（有 SLA） | 平台支持的源与定义语言 | 换云 = 重接存储与在线服务 |
| C 端到端商业平台 | 平台 | 平台（有 SLA） | 平台的定义语言与配额 | 退出即重写加工链路 |
| 自研 | 你 | 你，且无外部参照 | 只受你的工程能力限制 | 不迁移，但一致性验收要自建 |

**为什么相邻的 MLflow、模型注册、实验管理不在候选名单里**：它们管理的是模型与实验，不管理特征值的取数与一致性——一个特征定义改了两侧却不一致，MLflow 不会知道，也无法阻止。本章 [§2.4](01-feature-store.md) 已把这一边界写明：它们是协作关系，不是同类的替代选项。

**表里「许可 / 商业模式」一栏最容易过期**：开源项目改由基金会托管、商业产品改为按量计费、云厂商把能力并入既有平台，都会改动这一列。**判定方法是查项目或产品的官方发布页与定价页，不要以本章的表述为准。**

**同族内部的差异什么时候才需要比较**：只有当约束把你逼到族内只剩两三个选项时（例如已经定在同一云内、或已经要求私有化部署），才去比同族内的定价、配额与托管程度——这些差异的量级通常在同一个数量级内摆动；跨族的差异（谁拥有计算路径）才是可能差一个数量级的那一类。

### 7.3 机制差异：为什么它们表现不同（核心节）

§7.1 归纳的三条机制里，「谁拥有计算路径」只回答了谁该负责，本节把**一致性**从它里面单列出来作第四维——它回答的是「这个候选用什么拦住不一致」，对得上的不是一份 SLA 而是一份抽检脚本；判据表把这两者合在「计算路径归属」一行里，§7.3 必须分开讲。这 4 个机制不是并列清单，而是有依赖顺序的：`7.3.1`（一致性）与 `7.3.2`（时间语义）决定「结果可不可信」，`7.3.3`（取数链路）与 `7.3.4`（路径归属）决定「代价落在谁身上」。前两个机制不成立时，后两个只是在优化一个不可信的结果——这也是 §7.5 的决策树把节点 ① 给 `7.3.2` 的 `event_time`（准入项）、把节点 ② 给 `7.3.3` 的「事件到决策的预算是否在秒级以内」（成本量纲）的原因：先立住「结果可不可信」的前提，再决定要不要为新鲜度付一笔常驻成本。**`7.3.1`（一致性）在树里不占节点**，因为它不是二值问题——没有哪个候选是「完全没有一致性机制」，差别只在保证方式（定义生成还是平台内置）与覆盖范围（定义语言能表达的那部分），所以只能在方案选定之后用 §7.3.1 的抽检方法逐条验收；它约束的是「这个候选能不能留下」，而不是「走树时在哪一步分叉」。

#### 7.3.1 一致性机制：同一份定义生成两条路径，还是两份独立实现

- **机制是什么**：训练用的特征值与推理用的特征值是「同一份定义的两次执行」，还是「两份各自实现的代码」。前者的差异只可能来自时间边界与空值语义，后者的差异来自两份代码的任意一行。
- **各候选的实现差异**：

| 候选族 | 一致性的保证方式 | 一致性失效时谁负责 |
| --- | --- | --- |
| A 开源框架 | 定义（YAML / Python）生成离线 SQL 与在线物化，两条路径出自同一份定义 | 你（框架只提供生成器） |
| B 云生态托管 | 离线表与在线存储的同步是平台内置动作，特征表就是数仓表 | 平台（有 SLA 与工单） |
| C 端到端商业平台 | 声明式定义由平台编译成批 / 流两条聚合链路 | 平台（有 SLA 与工单） |
| 自研 | 完全取决于你的生成器与流程纪律 | 你，且没有外部参照 |

  **被压缩到的那类差异具体是什么**（都是可逐条写测试的）：

  | 差异来源 | 为什么它总会存在 | 验证方法 |
  | --- | --- | --- |
  | 窗口闭合边界 | 离线按自然日聚合、在线按事件时间滑动窗口，边界不同则值不同 | 同一实体取同一天，两侧各算一次比对 |
  | 时区与日期截断 | 离线用数仓时区、在线用请求时区 | 跨零点采样比对 |
  | 空值与除零 | 离线 SQL 的 NULL 语义与在线语言 / KV 写入的默认值不同 | 构造缺失样本比对 |
  | 迟到数据 | 离线重算会吸收迟到事件，在线侧当时已经算完并写出 | 注入迟到事件，看两侧是否都会更新 |

- **由此必然导出的性质**：因为定义只有一份、两条路径由它生成，所以不一致的来源被压缩到「时间边界与空值处理」这类**可枚举的差异**上，可以逐条写测试；代价是**定义语言成为能力上限**——凡是定义语言表达不了的加工（自定义算子、跨表复杂逻辑、请求级实时变换），就必须退回平台之外各写一份实现，而这一段立刻失去一致性保证。
- **公开证据**：把「训练 / 服务一致性」写成平台性问题的公开文献之一，是 TFX 论文（Baylor et al., "TFX: A TensorFlow-Based Production-Scale Machine Learning Platform", KDD 2017）【公开】；「训练数据的依赖是隐性债务」出自 Sculley et al., "Hidden Technical Debt in Machine Learning Systems", NeurIPS 2015【公开】。Feast 的 `materialize` 物化流程属官方文档条目，是判定入口（具体能力与版本以页面当前内容为准）。
- **失效条件**：当在线侧需要请求级实时变换时，两条路径不再等价——部分特征只能在线算，训练样本必须复现同一次请求上下文；此时一致性只覆盖了「平台定义语言能表达的那部分」。

  **怎么度量「定义语言覆盖不到的比例」**：把团队现有特征逐条过一遍，打三类标记——能用定义语言表达的、要写自定义算子的、必须在线实时算的。第二、三类的占比就是不一致风险的实际暴露面。这个比例在多数团队落在 **10%–30%**【经验：按特征条数统计，团队之间差异很大，请自行统计】，而它决定了托管方案「一致性可追责」这个收益的上限——比例越高，绕出去的部分越多，能追责的覆盖面越小。

#### 7.3.2 时间语义：Point-in-Time 是取数协议，不是平台功能

- **机制是什么**：每张特征表带 `event_time`，每个训练样本带 `label_time`，取数按 `event_time <= label_time` 取。它是一个**取数时的约束**，不是某个产品的开关。
- **各候选的实现差异**：任何平台都能实现它（约束写在取数 SQL 或 SDK 里），也都可以没实现（平台无法阻止你把最新分区 join 进训练样本）。差别只在于**平台是否把 `event_time` 变成特征表 schema 的必填项**：

| 平台的强制程度 | 表现 | 后果 |
| --- | --- | --- |
| 强制（时间列是必填字段） | 不填 `event_time` 就建不出特征表 | 协议由数据模型保证，换人也不丢 |
| 可选（提供时间列但可省略） | 新人图快，第一版特征表就没有时间列 | 协议靠自觉维持，随人员流动退化 |
| 无此概念（只当普通表管理） | 覆盖写的最新快照就是全部 | 训练与回填同时失去依据，只能靠外部流程补救 |

- **由此必然导出的性质**：因为 Point-in-Time 靠取数约束而非产品功能，所以它**不随采购预算增长**——换了最贵的平台，没有 `event_time` 的表照样泄漏未来信息，而离线指标还会因为没有时间轴而无法复现；反过来，代价是你要在数据模型上先付一次成本：每张特征表带 `event_time`、每个训练样本带 `label_time`、每个特征视图声明窗口语义。把它当成平台特性去采购，是这类项目最常见的误判。
- **公开证据**：本章 [§5.3](01-feature-store-section-5-ai.md) 把「没有 `event_time` 的特征表，不算特征」写成第一条约定；本章 [§6](01-feature-store-section-6-sec6.md) 的电商案例把这套协议落成一句 join 条件（`f.ds = date_sub(s.label_ts, 1)`；该案例出处标注为「案例 + 年份区间」，形如 `[案例 2020]` / `[案例 2020-2024]`，机构匿名，属自述口径）。**可自行核验的判定方法**：抽 5 个训练样本，看能否说清每个特征用的是哪个时刻的值——说不清就说明协议没有落地。
- **失效条件**：特征是静态属性时（用户注册渠道、内容类目），时间对齐退化为普通 join，约束不带来额外收益，只增加建模负担。

#### 7.3.3 取数链路位置：请求链路内计算，还是预计算后只读

- **机制是什么**：特征值在**事件发生时**算好并写入在线存储，还是等**请求到达时**在链路里算。
- **各候选的实现差异**：

| 形态 | 计算发生位置 | 新鲜度上限 | 你必须运维什么 |
| --- | --- | --- | --- |
| 纯离线（离线优先，本章 [§3.2.1](01-feature-store-section-3-sec3.md)） | 物化批作业 | 一个物化周期（多为天级） | 调度与物化 |
| 请求链路内计算 | 每次推理 | 实时 | 无额外常驻组件，但延迟随特征复杂度增长 |
| 预计算 + 在线只读（混合，本章 [§3.2.3](01-feature-store-section-3-sec3.md)） | 流作业与批作业 | 秒级 | 流作业、窗口状态、检查点 |
| 平台托管的取数接口（FaaS，本章 [§3.2.4](01-feature-store-section-3-sec3.md)） | 平台预计算，客户端只读 | 秒级 | 计费与配额面（按调用方计量） |

- **由此必然导出的性质**：因为把计算移出了请求链路，所以单次请求的延迟从「算一次特征」降为「读一次特征」，扩容维度从模型复杂度变成存储 QPS，高峰时不再因为某个特征算子慢而整体超时；代价是多了一条常驻流处理链路——**窗口状态、检查点、乱序与迟到数据的处理都成了你要长期负责的东西**，而状态规模随窗口长度和实体基数增长（见 §7.4 的推算）。
- **公开证据**：本章 [§6](01-feature-store-section-6-sec6.md) 的出行案例记录了「把特征计算从请求链路移出」这一动作（出处标注为「案例 + 年份区间」，机构匿名，属自述口径）——做法可迁移，其数字不能当作第三方对照数据。**可自行核验的判定方法**：看一次推理的执行计划里有没有特征算子的耗时，有则说明计算仍在链路内。
- **失效条件**：当事件到决策的预算在秒级以上时，这条链路的成本换不来业务收益；此时引入实时只增加了运维面，以及一条将来可能没人完全理解的链路。

  **判断计算是否已移出链路的三个问题**（不需要采购即可问）：一次推理的延迟预算里特征占多少？高峰时延迟是随 QPS 上升，还是随特征算子数上升？特征服务抖一次，同时受影响的是哪些模型？第三个问题答不出来，说明这条链路还没有明确的责任边界。

#### 7.3.4 计算路径归属：平台拥有，还是你拥有

- **机制是什么**：批 / 流加工与在线存储由平台提供并维护，还是由你的团队自建并维护。它决定**锁定发生在哪一层**、**成本的性质**（许可费还是人力）、以及**一致性问题的责任归属**。
- **各候选的实现差异**：B、C 族把计算路径收进平台，能力边界由平台的定义语言与支持的数据源划定；A 族与自研把计算路径交给你，能力边界只受你的工程能力限制，但也没有人为一致性背书。**把责任边界写清楚是选型动作的一部分**：

| 责任项 | 托管（B / C 族） | 你拥有（A 族 / 自研） |
| --- | --- | --- |
| 双路径等价性 | 平台（可写进 SLA） | 你的定义生成器与等价性测试 |
| 在线存储的可用性 | 平台 | 你 |
| 物化与回填的调度 | 平台 | 你 |
| 特征口径的正确性 | 你（平台不知道你的业务含义） | 你 |
| 特征定义的评审与下线 | 你 | 你 |
- **由此必然导出的性质**：因为平台拥有计算路径，所以一致性验收变成一份可追责的 SLA，出故障有单一责任方，团队可以把精力放回特征逻辑；代价是**平台表达不了的加工必须绕到平台之外，而绕出去的部分立刻失去一致性保证**。反过来，因为你拥有计算路径，所以任何加工都能做；代价是一致性没有外部责任人——「定义与实现两套」只能靠自己的流程与测试堵住，且这件事会随人员流动复发。
- **公开证据**：各平台的 `feature view` / `feature service` / `materialize` 一类官方文档条目是判定入口（是否有配额与 SLA 说明，以页面当前内容为准）；国内平台（阿里 PAI 特征平台、字节 ByteFS、腾讯 TI-EMS）同样以官方文档的能力条目为准，**不以发布会介绍页为准**（本章 [§5.4](01-feature-store-section-5-ai.md) 采用同一判定入口）。
- **失效条件**：当特征逻辑大量依赖定义语言覆盖不到的加工（跨源复杂变换、图特征、自定义算子）时，「托管」的收益会被反复绕行抵消——此时 A 族或自研反而更快。

  **锁定程度的判定**（按代价从小到大）：特征定义能否导出成与平台无关的形态？在线存储里写入的键值布局是否可读？在线取数的客户端能否被替换（是标准协议还是私有 SDK）？三个问题里答「否」的越多，退出代价越高——注意**锁定发生在在线取数这一层**，而不是在特征定义这一层，因为定义通常可以照抄，键值布局与私有协议不能。

  **托管还有一个容易被忽略的代价在版本节奏上**：平台的能力会随版本演进与弃用，你的定义与在线存储也跟着动。**判定方法**：查平台官方文档的版本兼容与弃用策略，看一次破坏性变更通常给多长的迁移期——这个期限就是你对上游节奏的被动程度，它与你的模型上线周期是否匹配，是托管选型里没人写进评分表、但每年都会遇到的一项。

### 7.4 成本结构对比（不是价格表，是成本函数）

特征平台的成本不是一个价格，而是一个随若干变量增长的函数：

```
成本 ≈ 平台许可 / 托管费
      + f(特征数 × 物化频率)             物化与回填的计算量
      + g(在线取数 QPS × 单请求特征数)     在线存储与网络
      + h(实体基数 × 窗口数 × 窗口长度)    流式状态与检查点
      + i(平台人力)                      自建时是工资，托管时残留在集成与排障
```

**用法**：不要去比不同方案的单位价格，而是把上面三项变量（特征数与物化频率、在线 QPS 与单请求特征数、实体基数与窗口数）代进自己的数，看哪一项在你的取值域里成为主导。**主导项决定的是「这个方案的账算得动算不动」，不是「这个方案好不好」**——同一个平台在高频物化场景里成本失控，在低频物化场景里可能最省。

**第一项 f：物化与回填是主导项，而回填常被漏算。** 设 1 000 个特征视图、每视图日均一次物化、每次扫 10 GB 源数据，则日扫描量 = 1 000 × 10 GB = **10 TB/天**【推算：推导链为「特征视图数 × 单视图日扫描量」，即 1 000 × 10 GB = 10 TB】；列存与分区裁剪通常能把这个量降一到两个量级，但量纲不变。真正被低估的是回填。**回填只重算被回填的那一条特征，扫描量与平台上已有多少个特征视图无关，只与它的历史窗口长度成正比**——新特征上线按历史窗口重算，2 年日粒度就是 730 次物化、每次扫的仍是它自己的那 10 GB，合计 730 × 10 GB = **7.3 TB 扫描**【推算：730 次 × 10 GB = 7 300 GB = 7.3 TB】。而这条特征未来一整年的日常物化是 365 × 10 GB = **3.65 TB**【推算：365 次 × 10 GB = 3 650 GB = 3.65 TB】——**一次回填的扫描量已经超过它一整年的日常物化**，差别只来自历史窗口（730 天）比未来一年（365 天）更长；这也是为什么回填常被漏算：它不在日常账单上，只在每次新特征上线时出现一次。

**第二项 g：在线取数本身不贵，为尾延迟付的冗余才贵。** 单请求取 200 个特征、每特征按 16 字节（值加编码开销）计约为 3.2 KB，1 000 QPS 时平均带宽 ≈ **3.2 MB/s**【推算：200 × 16 B = 3 200 B，1 000 × 3 200 B ≈ 3.2 MB/s】。平均量级很小，成本落在**尾延迟**上：为了让 P99 稳定，在线存储要多分片、多副本、加本地缓存，这部分容量是平均用量的数倍——倍数由你的延迟承诺决定，不由平均流量决定【经验】。

**第三项 h：流式状态随窗口长度增长，是实时路径的隐性常驻成本。** 设 1 亿活跃实体、每实体每窗口 64 字节状态、同时维护 5 个窗口，状态 ≈ 1 亿 × 64 B × 5 ≈ **32 GB**；计入检查点与副本，按 3–5 倍计约为 **96–160 GB** 常驻【推算：10^8 × 64 B × 5 = 3.2 × 10^10 B ≈ 32 GB；32 GB × 3–5 = 96–160 GB】。**窗口越长、实体越多，这笔常驻成本越大，且它不随查询量下降**——没有流量时它依然占着内存。

**第四项 i：人力与许可费的互换，是选型里最容易算错的一项。** 自建路径的起步规模，按本章 [§6](01-feature-store-section-6-sec6.md) 落地路径给出的 0 → 1 阶段是 2–3 人（属该章案例的自述口径，不是第三方对照数据），到生产规模是 10–30 人【经验】；托管路径把这笔人力换成许可与集成成本，但**没有消灭它**——上线后仍要有人负责定义评审、一致性抽检与回填排期。**多数团队在数十到数百个特征、单一业务域时，开源框架自建的总成本低于采购托管平台；当特征数上千且多团队共享时，一致性验收、配额管理与口径仲裁的人力开始超过许可费**【经验：按区间判断，请用自己的薪资深单价重算，不要照抄】。

**按族看，主导项与隐性成本不同**：

| 族 | 主导项 | 隐性成本（最容易漏算的那一项） |
| --- | --- | --- |
| A 开源框架 | f（物化与回填）+ i（人力） | 自建在线存储的尾延迟容量、流作业的语义维护 |
| B 云生态托管 | 平台费 + g（取数调用）+ 生态内存储费 | 迁出该云时的重接成本 |
| C 端到端商业平台 | 许可费 + 按调用量计的取数费 | 定义语言覆盖不到时的绕行成本 |
| 自研 | i（人力，10–30 人量级） | 一致性没有外部责任人，验收口径要自建 |

**成本重心会随阶段移动**：第 0 年由 i（搭建）与 f（首次回填）主导；稳定运行后由 f（日常物化）主导，走实时路径的组织再加一项 h；每次换 embedding 模型或调整口径，f 会再出现一次尖峰。**因此不要用「首年预算」做选型**——按三年看，回填与重算这类尖峰会重复出现两到三次，而许可费是平的【经验】。

**为什么存储本身很少成为主导项**：特征表的存储量 ≈ 实体基数 × 特征数 × 每值字节 × 保留天数。设 1 亿实体、1 000 个特征、每值按 16 字节计（未压缩），单日 ≈ 1 亿 × 1 000 × 16 B = **1.6 TB/天**，保留 90 天约 **144 TB**【推算：10^8 × 10^3 × 16 B = 1.6 × 10^12 B = 1.6 TB；1.6 TB × 90 = 144 TB】；列存压缩与稀疏（并非每个实体每天都有全部特征）通常还能再降一个量级【经验】。**按同一条特征把两笔账放在一起看**：它 90 天的存储 ≈ 1 亿 × 16 B × 90 = **144 GB**【推算：10^8 × 16 B = 1.6 GB/天；1.6 GB × 90 = 144 GB】，而它一次 2 年回填要扫 **7.3 TB**——**存储便宜、扫描贵，这是特征平台成本结构里最反直觉的一条**，也是「回填要不要全量重算」这个决定为什么值钱的原因。

**一致性抽检本身也有一笔可算的常驻成本。** 设每天抽 1 000 个样本、每个样本 1 000 个特征、离线与在线各取一次，则日取数次数 = 1 000 × 1 000 × 2 = 2 × 10^6 次；若单次取数折算 1 ms 的 CPU 时间，日合计约 2 000 秒，折合常驻算力 ≈ **0.023 vCPU**【推算：10^3 × 10^3 × 2 = 2 × 10^6 次；2 × 10^6 × 1 ms = 2 000 s；2 000 s ÷ 86 400 s ≈ 0.023】。量级很小——**这正是「一致性抽检应该默认做」的算术依据**，砍掉它省不下钱，却会失去唯一能提前发现双路径漂移的手段。

### 7.5 决策树（每个分支都要有阈值依据）

```
[特征平台需求]
  │
  ├─ ① 特征表是否带 event_time？
  │     否 → 先补 event_time 与 label_time 取数约束；换任何平台都一样（§7.3.2）
  │     是 ↓
  ├─ ② 事件到决策的预算是否在秒级以内？
  │     否 → 离线优先：新鲜度由物化周期决定即可，不引入常驻流链路
  │     是 ↓
  ├─ ③ 是否存在 > 7 天的窗口特征？
  │     是 → 定架构形态：混合（离线重算长窗口 + 流式维护短窗口） ↓
  │     否 → 定架构形态：纯流式路径 ↓
  ├─ ④ 常驻平台人力是否 ≥ 2–3 人？
  │     否 → 选托管形态（B / C 族），不要自建流链路
  │     是 ↓
  ├─ ⑤ 训练与在线取数是否在同一云 / 生态内？
  │     是 → 该生态的托管平台（Databricks / SageMaker / Vertex AI / Azure ML / 阿里 PAI / ByteFS / TI-EMS）→ 跳到 ⑦
  │     否 ↓
  ├─ ⑥ 共享特征数是数十到数百，还是上千且多团队共享？
  │     数十到数百 → 开源框架（Feast / Hopsworks）+ 自建在线存储 → ⑦
  │     上千且多团队 → 托管平台（FaaS 形态：按调用方配额与计费）→ ⑦
  └─ ⑦ 是否需要管理 prompt / embedding 的输入快照？
        是 → 在 ① / ② 的前提之上加版本绑定与索引快照标识，先做登记，不急于统一计算路径
        否 → 到此为止
```

**阈值依据**（与树上 7 个节点一一对应）：

- **① `event_time` 有 / 无**：来自本章 [§5.3](01-feature-store-section-5-ai.md) 的第一条约定「没有 `event_time` 的特征表，不算特征」。它是准入项而不是能力项，所以放在第一个节点，且没有「有但不多」的中间态。
- **② 秒级以内 / 秒级以上**：机制依据是取数链路的成本量纲（§7.3.3）——只有需求快于物化周期时，常驻流链路的成本才能被收益覆盖；本章 [§3.3](01-feature-store-section-3-sec3.md) 用同一口径把「模型更新频率是天级吗」列为离线优先与实时优先的分界。
- **③ 7 天窗口**：沿用本章 [§3.3](01-feature-store-section-3-sec3.md) 决策表的判据「是否存在 > 7 天的窗口特征？是 → 必须混合」。机制依据是流状态随窗口长度增长（§7.4 的 32 GB 推算），且长窗口的重算与回填必须由离线路径承担。
- **④ 2–3 人**：沿用本章 [§6](01-feature-store-section-6-sec6.md) 落地路径里 0 → 1 阶段的团队规模。低于这条线时，流作业的语义、状态与检查点没有长期负责人，链路会成为「没人敢改」的资产。
- **⑤ 同云 / 同生态**：沿用本章 [§3.3](01-feature-store-section-3-sec3.md) 决策表「阿里云生态 / 字节生态 / 腾讯生态」三行的判据「在线服务与训练是否都在同一云内」。机制依据是跨云会让每次在线取数多一跳，而在线取数处在请求关键路径上。正因为同云内再自建一套在线存储等于把生态已经提供的取数与存储重搭一遍，它的「是」分支直接给结论并跳到 ⑦，不再经过 ⑥。
- **⑥ 数十到数百 / 上千且多团队**：它是 ⑤「否」分支之后的下游节点——训练与在线取数不在同一云 / 生态内，意味着吃不到生态内集成，选择只能落在「自己搭」与「跨云可用的托管」之间。分界线来自 §7.4 第四项：自建与托管的分界由「一致性验收与配额管理的人力」决定，而这项人力随「共享特征数 × 消费团队数」增长，不随特征数本身线性增长。
- **⑦ prompt / embedding 快照**：判据取自本章 [§5.5](01-feature-store-section-5-ai.md)「统一的是目录，不是计算路径」。这一节点只要求先做登记与版本绑定，因为登记是可独立交付、可独立验收的动作，而计算路径的统一目前没有可核验的落地机制。

**两个边界情形要单独说**：一是特征数极少（几十个）且全部离线——此时真正的风险不是选型，而是特征表没有 `event_time`，换任何平台都救不了；二是已经上了实时链路，却说不清哪些模型在消费它——此时先补消费方清单，再谈换平台，否则迁移会把未知的影响面一起搬过去。

**两个常被问到、但树里没有的分支**：一是「要不要上 FaaS（特征即服务）」——它问的不是新鲜度而是「要不要按调用方计量与配额」，属于 ⑥ 的延伸；二是「要不要做特征发现与目录」——它与新鲜度、延迟都无关，任何规模都该做，所以不构成决策分支（本章 [§2.4](01-feature-store.md) 把 Feature Catalog 定义为 Data Catalog 的子集）。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单业务域、数十到数百特征、无秒级需求 | Feast + 既有批引擎 + 在线 KV | Hopsworks 开源版 | 引入流式只增加新鲜度，不改变业务指标 |
| 多算法团队共享特征、有秒级新鲜度与 SLA | Tecton（或等价的托管平台） | 自研声明式定义 + 流引擎 | 自研要自己承担双路径等价性，且没有外部责任方 |
| 特征表已在湖仓、要时间旅行与回溯 | Databricks Feature Store / Hopsworks + Iceberg | Feast + Iceberg | 再建一套独立特征存储，会让血缘与权限出现两套 |
| 训练与在线服务都在同一云内 | 该云的托管平台（SageMaker / Vertex AI / Azure ML / 阿里 PAI / ByteFS / TI-EMS） | 开源框架 + 该云存储 | 跨云拼接让在线取数多一跳 |
| 隐私敏感、原始数据不能出域 | 联邦特征平台（本章 [§3.2.6](01-feature-store-section-3-sec3.md)） | 各域自建 + 只交换聚合结果 | 集中式平台要求原始数据汇聚 |
| 端侧推理、断网可用 | 边缘特征（本章 [§3.2.8](01-feature-store-section-3-sec3.md)） | 云端特征 + 端侧缓存 | 云端特征在断网与隐私约束下不可用 |
| 既跑传统模型又跑 LLM 应用 | AI 原生平台 + 向量库 | 传统平台 + 独立向量库 | 两套体系会让效果变化无法归因到输入快照 |
| 已有 Spark / K8s 技术栈、不想换栈 | 开源框架 + 既有批引擎 | 自研一层声明式定义 | 换栈成本通常高于选型收益 |
| 需要按调用方计量与配额 | 支持按调用方计量的托管形态 | 自建网关 + 计量 | 共享一张表回答不了「谁在用、用多少」 |

**走树的方式**：从上往下，每个节点只回答一个问题，箭头「↓」指向必须继续往下走的那条分支。① 与 ② 的「否」给出的是前提性结论（先补 `event_time`、先走离线优先），④ 的「否」直接落在托管形态——这三处都是终点，不必把 7 个节点全走完。③ 是唯一的例外：它两条分支都要继续往下，因为它定的是架构形态，不决定选谁。节点 ①–④ 决定「要不要引入实时、要不要托管」，节点 ⑤–⑦ 只在 ④ 通过（确实有常驻平台人力）之后才有意义：⑤ 的「是」直接落到该生态的托管平台并跳到 ⑦，⑥ 只细化 ⑤ 的「否」分支——不在同一云、吃不到生态集成时，才轮到按共享特征数与团队数在「开源框架 + 自建在线存储」与「托管 FaaS」之间选；⑦ 是叠加项，落在哪个分支都要过一遍。

**5 个常见组合，各件承担什么、代价是什么**：

1. **Feast + Flink + Redis（轻量级）**——Feast 管定义与物化编排，Flink 管新鲜度，Redis 管毫秒读取。**运维代价**：多一套 Flink 作业与状态要运维；可先上批路径再补流，这也是它适合起步的原因。**适合规模**：单业务域、百级特征、优先跑通一致性。
2. **Tecton + 实时引擎（企业级实时）**——平台承担双路径等价性与物化，团队只维护特征逻辑。**运维代价**：商业组件与在线服务成本，且特征服务进入请求关键路径后，它的可用性风险会同时影响所有线上模型。**适合规模**：多算法团队共享特征、有秒级新鲜度要求与明确 SLA。
3. **Hopsworks + Iceberg + Milvus（AI 原生）**——Iceberg 管历史与时间旅行，Hopsworks 管 AI 原生资产（含 prompt / embedding 版本），Milvus 管近邻检索。**运维代价**：三套存储的运维面与一致性边界必须写清楚谁负责哪一类特征，否则会出现同一特征两处口径。**适合规模**：既跑传统模型又跑 LLM 应用、需要输入快照可复现的组织。
4. **阿里 PAI + MaxCompute + 实时计算（国产化）**——生态内集成省掉大量适配。**运维代价**：与生态绑定，跨云场景下在线取数多一跳；一旦离开生态，特征定义与在线存储的同步逻辑要重写。**适合规模**：训练与在线服务都在同一云内的团队。
5. **自研 + 开源（混合）**——核心平台自研、周边工具用开源。**运维代价**：一致性没有外部责任人，必须自建验收口径与抽检机制，否则「定义与实现两套」会随人员流动复发。**适合规模**：加工形态高度定制、托管平台的定义语言覆盖不了的核心链路。

**组合的边界怎么划**：判断一件东西该不该进组合，只问一个问题——**它的失效会不会破坏一致性**。会（例如另起一份特征定义、把在线存储换成第二套写入路径）就不能进；不会（只读的监控、离线评估、目录登记）就可以挂在旁边。按这条划线，上面 5 个组合里真正承担一致性的是第一件（定义与物化），其余各件分的是新鲜度、延迟、生态与资产类型。

**组合最常见的失败不是选错件，而是职责重叠**：两件都声称自己在管特征定义（框架里定义一份、平台里又定义一份），结果是两套物化路径并存，一致性保证互相抵消，比单用任何一个都差。**检查方法**：问「这份特征的定义以哪一份为准」——如果答案里出现「一般是 X，但 Y 场景用 Z」，说明已经重叠了。

**矩阵怎么读**：每一行的「首选」不是在说它更强，而是在说**它的失效点恰好不在你这条约束上**。例如「单业务域、数十到数百特征」一行不选流式，不是因为流式差，而是因为它的失效点（状态随窗口增长、语义没人维护）正好落在「团队只有 2–3 人」这条约束上。

### 7.7 选错的代价与迁移成本

**反模式：把「实时」当成默认选项。** 症状：业务只要求天级更新，架构里先引入了常驻流链路；**后果**：流状态与检查点成本随窗口长度增长、且不随流量下降（§7.4 第三项），半年后这条链路的语义只剩原作者懂，没人敢改【经验：随团队规模与人员流动率变，人越少来得越快】；**正确的做法**：先用「事件到决策的预算是否在秒级」筛一遍，不通过就走离线优先，把预算花在 Point-in-Time 与回填上。

**反模式：把一致性交给流程纪律。** 症状：特征定义写在 YAML 里当文档，离线 SQL 与在线代码另写一份；**后果**：差异只在线上暴露（离线复现不出），排障时两边都「看起来对」；**正确的做法**：让离线与在线从同一份定义生成，把定义语言覆盖不到的加工单独列出并逐条写等价性测试。

**反模式：先接向量库，再补时间语义。** 症状：embedding 先进平台，传统特征表仍然只有最新分区；**后果**：训练样本取不到「那一刻的向量」，回填无从下手，效果问题无法归因到输入快照；**正确的做法**：先做 `event_time` 与版本绑定，再引入向量资产——本章 [§5.5](01-feature-store-section-5-ai.md) 给的判定方法就是问「上一次 embedding 模型升级，怎么列出受影响的模型与训练样本」。

**这三条反模式的不对称之处在暴露时机**：把一致性交给流程纪律，问题是**缓慢累积**的（差异随人员流动一点点变多）；把实时当默认选项，问题是**半年后突然出现**的（链路没人敢改）；先接向量库，问题是**被要求复现时才出现**的（回填无从下手）。三条都处在「现在不痛、以后很贵」的位置，所以判断只能依据机制，不能依据当前体感。

**换成另一个要动什么**：

| 迁移方向 | 数据迁移 | 查询 / 定义改写 | 运维重建 | 团队再学习 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| 开源框架 → 托管平台 | 特征表落点变更，需按平台表结构重灌 | 定义语言不同，特征逻辑要重写一遍 | 在线存储与物化交给平台，自建链路下线 | 中（学平台定义语言与配额模型） | 平台表达不了的加工留在外部，重新变成双路径 |
| 托管平台 → 开源框架 | 需先确认历史快照能否导出，导出能力决定回填可行性 | 同上，反向重写一遍 | 需自建在线存储与物化编排 | 高（要补上平台原先兜住的一致性职责） | 一致性责任从 SLA 变成自己的测试覆盖 |
| 云生态 → 另一云生态 | 跨云搬运，量大时按 TB 级计 | 定义大体可保留，接口与 SDK 全换 | 在线服务重建 | 中 | 迁移期双跑，在线取数多一跳 |
| 自研 → 托管 | 特征表与在线存储都要重接 | 自定义算子多半无法平移 | 自建组件逐步下线 | 低到中 | 平台覆盖不了的自定义算子成为长期例外 |
| 离线优先 → 混合 | 特征值保持不变，但需补事件时间列与窗口语义 | 短窗口特征改用流定义，长窗口仍走批 | 新增流作业、状态与检查点运维 | 中到高（团队要懂事件时间与迟到数据） | 实时与离线两条路径的窗口边界不一致 |
| 同族内换平台（同云或同框架） | 定义与表结构基本可平移 | 改动集中在 SDK 与配置 | 基本不动 | 低 | 生态内的兼容性变更（配额、弃用） |
| 集中式 → 联邦特征平台 | 原始数据留在各域，但要在各域分别建特征管道 | 取数改为按域路由，实体对齐与时间口径需分别对齐 | 多一套跨域协调、加密与审计组件 | 高（联邦协议、配额与审计口径） | 口径没对齐时，模型学到的是拼接噪声 |

**三条反模式的共同点**：都是在判据还没坐下来时先做了技术动作——先引入流引擎、先接向量库、先把定义写成文档。**顺序反过来，三条就都不成立**：先定「谁拥有计算路径、时间语义在哪里被强制、取数在哪条链路上」，再决定引入什么。

**真要迁移时的通用顺序**（反过来做几乎一定返工）：先把历史快照的可导出性确认清楚 → 再把特征定义逐条标注为「可平移 / 需重写 / 平台无对应」→ 再双写并跑一致性抽检 → 最后切读、下线旧路径。**顺序的核心是「先保证能回退」**：一致性抽检没过就不切读，这样最坏情况只是多花一份存储，而不是线上模型同时吃到两套口径。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 还没有特征平台，特征表无 `event_time` | 先补 `event_time` 与 `label_time` 取数约束，再谈选型 | 这是准入项：不满足它，任何平台都挡不住未来信息泄漏 |
| 天级更新、单一业务域、团队 2–3 人 | 开源框架 + 既有批引擎 + 在线 KV | 实时链路的常驻成本换不来业务收益 |
| 有秒级需求、多团队共享、要 SLA | 托管平台（Tecton 或同云托管） | 一致性验收变成可追责的 SLA，团队精力回到特征逻辑 |
| 特征表已在湖仓、要回填与时间旅行 | 湖仓内建特征能力 + 开放表格式 | 再建独立存储会让血缘与权限出现两套 |
| 要管 prompt / embedding | 先做登记与版本绑定，暂不动计算路径 | 统一的是目录不是计算路径；登记可独立交付且可验收 |
| 原始数据不能出域 | 联邦特征平台，且先把实体对齐与时间口径对齐 | 平台只解决数据放置，不解决「同一个人、同一时刻」 |
| 只有一个人维护特征 | 托管形态 + 只做 Point-in-Time 与版本绑定 | 单点人力下，常驻流链路的语义风险无人分摊 |
| 要做回填，但历史快照没保留 | 先解决历史可达性，再谈新特征上线 | 回填能力由历史快照的保留策略决定，不由平台决定 |

> 本节小结：这一组候选里**唯一真正起决定作用的差异是「谁拥有计算路径」**——它决定一致性由机制还是纪律保证、平台表达不了的加工往哪放、离开时要重写什么。其余差异（实时能力、资产类型覆盖、生态）都是这条差异在具体场景下的投影，因此它们的分值会随约束反转，不适合写成固定分数。
>
> 三句话结论：**第一，准入项只有两条**——有没有 `event_time`、计算路径归谁；**第二，权重项随场景反转**，所以任何固定分数都会误导；**第三，「实时」与「向量」这两项能力只在两类场景里该进入评分**——事件到决策在秒级、以及要管输入快照；其余场景里它们的边际价值接近零，而成本是实打实的。
>
> 💡 **思考锚点**：先拿你手上最吃重的那张特征表过两条准入项——它有没有 `event_time`、计算路径归谁？第一条给不出，你在 7.5 决策树上走哪个分支都挡不住未来信息泄漏；两条都过了，再自问你的场景是否真落在「事件到决策秒级」「要管输入快照」这两类里——若不是，你在打分表里给「实时」「向量」打的分应该扣到多少？
