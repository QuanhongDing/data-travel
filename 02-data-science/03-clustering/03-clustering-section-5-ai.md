## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单在本主题上的第一个问题是没有时间维度。原 §5 把「LLM 直接做聚类决策」与「编码器 Embedding + 传统聚类」写成同一种句式，而后者今天已经是文本归类的通行做法（[§3 §3.2.6](03-clustering-section-3-sec3.md) 直接把它称为 LLM 时代主流），前者连「怎么算做对了」都还没有公认形态。两者都写「演进方向」，读者据此排路线图，多半会先去做那个没有验收标准的。

第二个问题是机制差异被抹平。本主题的「前沿」实际横跨三层，改动它们的东西完全不同：

1. **相似度从哪来**（人工特征与度量 / 编码器的训练目标）——这是唯一无法由算法补救的输入（[§7 §7.3.2](03-clustering-section-7-sec7.md)）。
2. **簇由谁切**（距离 / 密度 / 层次 / 图）——它决定算法会以什么形状失效（[§7 §7.3.1](03-clustering-section-7-sec7.md)）。
3. **簇由谁解释与验收**（人 / 模型命名 / 下游动作）——它决定结果能不能被消费（[§7 §7.3.4](03-clustering-section-7-sec7.md)）。

[§3 §3.1](03-clustering-section-3-sec3.md) 已经把四条约束写在前面：簇的定义假设、相似度是否可信、无监督评估证明不了正确性、规模与复杂度的硬上限。**第 2 层与第 3 层的后半段一条都没有被 AI 改动**——换更强的编码器不改变 K-Means 假设簇是围绕质心的球、也不改变 DBSCAN 假设簇是密度连通的一块；而验收仍然要靠一个真实的下游动作，几何指标还是证明不了分群在业务上真实存在。AI 真正改变的是两处：**第 1 层，相似度的定义权从人工特征工程转到编码器的训练目标**；**第 3 层的前半段，「这个簇是什么」的表达从人换成了模型**。这两处合起来足够重要，因为它们分别解释了零样本为什么可能（新领域不必先标注）与标签为什么终于能被业务读懂；但它们都不改变「算法只能在给定空间里分组」这条性质。

本节用 L1 / L2 / L3 三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期。
- **L2 可试点**：①③ 大体满足、② 不满足。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

**本主题对 §2.1 的 L1 判据 ① 做如下修正，理由是对象不同**：① 的原义是「已 GA 且有正式 release note」。本节评估的方向对象是**建模机制**而不是可以直接采购的产品能力——编码器聚类、主题发现、社区检测、联邦聚合这类方向没有「GA 产品」这一形态，它们的正式发布物就是论文与公开实现。因此 ① 在本节统一按「**同行评审的会议或期刊论文，或带版本化发布记录的公开实现**」核；本节没有一行是产品能力行，故这条修正全表适用；**判 ① 时看的是「该方向声称的对象本身」有没有论文或实现把它当对象**——原文件列在「学术进展」里的研究条目（流式聚类、对比聚类、LLM-as-Judge 等）论文即其载体，判 ① 满足；拿不出对象级文献或实现的能力声张（如本节「LLM 判同」与「Agent 驱动聚类」两行），判 ① 不满足。**② 与 ③ 按 §2.1 原文核，不做修正**——② 仍是本节全部方向的上限，也是没有任何一行达到 L1 的唯一原因。

判据 ② 在本主题格外难过，原因值得先说清：**聚类效果的公开材料天然是建设方自述**。分群口径与它带来的收益是平台最核心的商业数字，能拿出来讲的往往只有方向与框架；而本书 [§6](03-clustering-section-6-sec6.md) 的四家公司案例本身就是「某头部电商」「某股份制银行」这类匿名自述，按 §2.1 的定义正是 L2 所指的「仅有建设方自有案例」。**把建设方自述换一个名字，仍然是建设方自述**。原 §5.3 的企业落地条目（含具体公司名与「运营效率提升 5 倍」「召回率 +30%」一类百分比）在本节不转载：其中若干条把公司名与做法的对应关系剥离、只剩结论，读者无法复核，而这类清单最容易发生的错误就是把一家公司的做法记到另一家头上。**② 只有「满足」与「降为 L2」两种命运**：它不能被改写成「有公开的效果数字」，也不能靠「本节只评估相似度这一层」把适用范围缩小来绕过去。

还要说清 L2 在本节的含义：它标的是**证据缺口**，不是「不能用」。一行若 ①③ 干净而只缺 ②，缺的是「别人用过、并且公开说了代价」这类材料，不是能力本身；采不采用由读者按自己的风险偏好决定，判据不因这句说明而放宽。另有一条评级规则全节通用：**合并方向取最弱子项**——原 §5.4 趋势 7、8 的「自适应聚类」与「聚类 + 推荐融合」是若干方向的目标句之和（前者说的是参数自选、后者说的是把簇喂给推荐，两者都没有自己的机制与正式载体），本节把它们当叙事处理，不当作可以单独定级的能力。

**本节没有一行达到 L1。** 离得最近的是四行——编码器 Embedding 聚类、LLM 命名、多模态聚类、聚类作为 RAG 预处理：它们没有一条判据完全落空，差的只有 **②（第三方非厂商公开生产案例）**。这四行的差别在 ③：编码器聚类一行的接口多年不变（同一个距离度量、同一套参数）；RAG 预处理一行只算大体满足，因为它取决于检索侧的去重与分组是否被纳入流程；多模态与 LLM 命名两行同样只算大体满足——跨模态配比没有统一形态，命名结果不可复现。判断某条方向是不是 L1，不要看有多少供货方在同一年推出它，看第 ② 条的材料是不是**建设方之外的机构**给出的：单靠匿名案例与效果百分比，无论多少条，都还是 L2。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式载体能不能找到——是同行评审的论文或带版本记录的公开实现，还是只有博客与演示？找不到 → L3。
2. 建设方之外的证据能不能找到——有没有人公开讲过它在多大数据量上跑、相似度怎么定、代价是什么？找不到 → L2。
3. 相似度那一环明年会不会变——**换一次编码器，这个方案要不要整库重算？** 要重算 → 至多 L2。

第 3 句在本主题特有的失手方式，是把**编码器**当成常量。簇由某个编码器版本产出的向量定义，换一版编码器，全库向量就不再可比，而聚类不会报错——它只会给出一个自洽但不同的划分。判定方法是看这个项目的变更记录里有没有「按编码器版本重建向量与索引」这一条，**而不是看换模型之后轮廓系数涨了多少**。

### 5.2 演进方向逐条拆解（核心节）

下面四个小节按同一套结构写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**。只写收益不写代价的方向，评审时应直接打回——聚类里每一次能力提升，都对应一项成本结构的变化。

读这套结构时有两个约定。**第一，「机制」那一行必须落到一个可以被改动的对象上**——相似度由谁定义、簇由谁切、簇由谁表达。写成「效果更好了」的，都不算机制。**第二，「代价」那一行必须是真实存在的新成本项或新故障模式**，而不是「需要学习」这类永远成立的代价。

#### 5.2.1 编码器 Embedding + 传统聚类：把相似度的定义权外包出去

- **旧做法与它的卡点**：旧做法是人工特征 + 词袋 / TF-IDF + 距离度量。卡点有两处（[§7 §7.3.2](03-clustering-section-7-sec7.md)）：**相似度由人定义，且定义不可迁移**——换一批语料、换一种语言，特征工程要重做一遍；而度量一旦定错，任何算法都只能在错的空间里分组（[§3 §3.1](03-clustering-section-3-sec3.md) 第二条约束）。原方向 1 把「Embedding 主导聚类」列为演进，要补上的正是「主导了什么」这一层。
- **AI 改变了什么机制**：**把相似度的定义权从人工特征工程转到编码器的训练目标**。聚类算法的工作从「理解内容」退化成「在给定度量空间里分组」；算法族一寸没变，变的是它们输入的那个空间。
- **由此得到的**：**因为编码器把语义相似翻译成余弦距离小，所以零样本成为可能**——新领域不必先标注与训练就能拿到第一版分组（[§3 §3.2.6](03-clustering-section-3-sec3.md)）；**又因为相似度是一次性定义、长期复用的，所以它获得了资产的性质**——一旦被版本化，同一批语料在任何时候重跑都落到同一个空间里，跨期对比才有意义。代价是这份资产必须被登记，而登记的自觉通常来得比需求晚；这两条合起来，解释了它为什么是文本归类的默认起点。
- **由此付出的**：**其一，定义权交出去之后不可修正**——聚类只能放大编码器的训练目标，无法修正它：用通用语义模型区分工单紧急程度时，簇会按主题而不是按紧急度分开，而轮廓系数可能并不低（[§7 §7.3.2](03-clustering-section-7-sec7.md)）。**其二，换一次编码器就是换一次全库**——编码器版本等于向量空间版本，新旧向量混在一个索引里，查询不报错，结果只是「不那么准」；全库重算是一次性大成本，且它不会出现在任何一次调参实验的账上。**其三，多了一次降维的必需性**——向量维度在数百到数千之间【经验】，密度聚类前通常必须先降维（PCA / UMAP 到 10–50 维【经验】），而降维又引入一次近似（[§3 §3.2.6](03-clustering-section-3-sec3.md)）。**其四，入场费与簇数无关**——全库编码的算力与每对象一份向量的存储，是这条路必须先付的成本，做一簇还是做一百簇都要先付。
- **证据与来源**：【公开】Reimers & Gurevych，EMNLP 2019（Sentence-BERT）；Radford 等，ICML 2021（CLIP）；Campello 等，2013（HDBSCAN，公开实现带版本记录）；Johnson 等，2017（Faiss）。**② 不满足**：本节给不出建设方之外的机构公开的、含规模与代价的编码器聚类生产案例。
- **成熟度**：**L2**（与 5.1 表「编码器 Embedding + 传统聚类」行一致），判据：①③ 满足、**② 不满足**。

| 判断项 | 人工特征 + 词袋 | 编码器 Embedding |
| --- | --- | --- |
| 相似度由谁定义 | 人：选特征、定权重、定度量 | 编码器的训练目标 |
| 换语料 / 换语言 | 特征工程重做 | 换编码器，或直接复用多语版本 |
| 距离错在哪里 | 能定位到具体特征或量纲 | 只能靠下游任务评估反推 |
| 换版代价 | 重算特征 | 全库重算向量与索引 |
| 失效表现 | 结果无意义，且原因可见 | 结果体面，但按错维度分开 |

```text
编码器聚类链：每一环都产生一个必须登记的版本
  对象 ─► 编码器(版本 v) ─► 向量 ─► 归一化 ─► 降维(PCA / UMAP, 参数 p)
        ─► 聚类(随机种子 s, 参数 q) ─► 簇
  ────────────────────────────────────────────────
  纪律：编码器版本 = 向量空间版本，换版必须整库重算，不能新旧混用（正文见 §3 §3.2.6）
  性质：这条链上任何一环变了，历史标签与新标签就不再可比
  代价：聚类没有「报错」这一档，它只会给出一个自洽但不同的划分 ——
        所以「不可比」这件事没有监控能替你发现，只能靠登记
```

**厂商措辞的边界**：原 §5.3 给各托管 Embedding 列了维度、上下文长度与排名，本节不转述（理由见 5.5 第 3 条）。判定方法是去该模型的官方文档页找三件事——输出维度、单次输入的长度上限、批次上限；**不要按首页文案判断**。

#### 5.2.2 LLM 命名与簇描述：换的是「这个簇是什么」的表达环节

- **旧做法与它的卡点**：聚类的消费方是人和业务流程，需要「这个群是谁」的自然语言答案，而算法侧只能给出数字标签（[§7 §7.3.4](03-clustering-section-7-sec7.md)）。旧绕法是让分析师看代表样本、手工写名字，成本随簇数线性增长，而且写完就散落在文档里，下游读不到。
- **AI 改变了什么机制**：**把簇的表达环节从人换成了模型**——每簇取代表样本（离质心最近的前若干条）交给模型，产出候选簇名与一句话描述。归属判定不受影响：模型不参与「谁属于哪个簇」（[§3 §3.2.10](03-clustering-section-3-sec3.md)）。
- **由此得到的**：**因为自然语言描述正是运营、报表与标签体系需要的接口，所以簇被真正使用的门槛下降**；**又因为归属判定不经过模型，所以这条改动可以在不触碰簇稳定性的前提下独立上线与回滚**——这是本节少见的一处「收益与主链路解耦」的改动。
- **由此付出的**：**其一，不可复现**——同一簇两次描述可能不同，所以结果必须落成标签字典并由人签字，下游读字典而不现场调模型（[§3 §3.2.10](03-clustering-section-3-sec3.md)）；这一步不能省，因为它同时是口径的冻结动作。**其二，会把一次随机划分固定成组织事实**——标签一旦进入报表与考核就有惯性，而聚类的可复现性缺陷不会在报表里显示出来，错误因此不可见。**其三，成本随簇数与重跑次数增长**——每次命名都有 token 成本，且簇越不稳定越要频繁重命名，而重命名会让前后两期的分群不再可比。**其四，它可能给出与业务口径冲突的名字**，把「高退货率用户」说成「活跃用户」，所以 review 环节不是装饰。
- **证据与来源**：【公开】Grootendorst，2022（BERTopic 与 c-TF-IDF）；Angelov，2020（Top2Vec）；Blei 等，2003（LDA）。用大模型为簇命名是当前通行做法【经验】，可按关键词 LLM clustering labeling 自行检索核验。**② 不满足**。
- **成熟度**：**L2**（与 5.1 表「LLM 命名与簇描述」行一致），判据：① 满足、③ 大体满足（输入输出形态稳定，但提示版本不进登记）、**② 不满足**。

**判定方法（自己怎么核验）**：让两个没参与过本项目的人各自按同一批代表样本独立命名一次，比较两次结果的语义重合度；重合低说明簇本身不稳定，此时不该先把名称用进报表——先回去看相似度与参数，再谈命名。

#### 5.2.3 多模态聚类：把图像与文本放进同一个空间

- **旧做法与它的卡点**：图文混排的内容（商品、封面、短视频）要归组，旧做法是按模态分别处理——图像算视觉特征、文本算词袋，两套结果再靠人工规则对齐。卡点是**跨模态的相似度无法定义**：一张图和它的标题「像不像」，在任何单一模态的度量里都问不出来。
- **AI 改变了什么机制**：**把两种模态编码进同一个可比空间**——图像与文本各自编码后落进同一向量空间，距离可计算。换的是**特征侧的模态边界**，不是聚类算法。
- **由此得到的**：**因为同一批内容的两侧落在同一个空间里，所以「同一件东西的图与它的描述」由构造保证彼此接近，不需要人工规则去对齐**；**又因为编码器是零样本的，所以没有标注的新品类也能先分出来**——这是它在内容侧特征缺失场景（只有封面、没有类目标签）里的真实收益面。
- **由此付出的**：**其一，增益幅度必须自测**——从「能编码」到「在自有目录上分得比单模态好」中间隔着一次必须自测的对照；多模态编码器在通用基准上的排名不能替代这次对照。**其二，每多一路模态就多一路成本**——多一份编码算力、多一份向量存储、多一份编码器版本登记，且换版同样要全库重算。**其三，融合方式没有统一形态**——拼接、加权、对齐投影各有实现，而「配比」这个参数没有公认的取法，调参空间反而变大。**其四，弱模态被强模态淹没**——当文本信号本身很稀（短标题、水印词）时，聚类会退化成按图像分组，而这一退化不会体现在几何指标上。
- **证据与来源**：【公开】Radford 等，ICML 2021（CLIP，图文对比对齐）；同族的多模态编码工作可按关键词在论文库自行检索核验。**② 不满足**：本节给不出建设方之外的、含规模与代价的多模态聚类生产案例。
- **成熟度**：**L2**（与 5.1 表「多模态聚类」行一致），判据：① 满足、③ 大体满足（编码器接口稳定，但跨模态配比与融合方式无统一形态）、**② 不满足**。

#### 5.2.4 其余方向为什么停在这里

下面七条同样按六行结构写：它们停在低处不是因为看不到收益，而是因为判据过不去；逐条写全六行，是为了让「停在这里」这个判断能被复核，而不是留一句印象。

- **LLM 判同 · 旧做法与它的卡点**：「这两簇该不该合并」缺少客观指标，只能靠人肉看样本；人工判断的规模上不去、也不记录依据。
- **LLM 判同 · AI 改变了什么机制**：把「是否同群」的判定从人换成模型的一次比较——换的是**裁决策略**，不是簇的产生方式。
- **LLM 判同 · 由此得到的**：如果判定可靠，它能让合并与切分有可复核的输入，而不是只留下一个结论。
- **LLM 判同 · 由此付出的**：**它的调用量随样本数呈平方增长**——成对判定需要 N(N−1)/2 次比较，N=10⁴ 即约 5×10⁷ 次【推算：10⁴ × 9999 ÷ 2 ≈ 5×10⁷】，而每一次都会给出一个「是 / 否」，因此判定阈值与一致性口径必须先定义，这两样都没有标准形态。
- **LLM 判同 · 证据与来源**：没有把「由模型判定两簇是否同群」作为能力项的正式载体；**① 不满足、② 无**。
- **LLM 判同 · 成熟度**：**L3**（与 5.1 表「LLM 判同」行一致）：① 不满足、③ 不满足、② 无。

- **LLM 评估聚类质量 · 旧做法与它的卡点**：无监督评估只能用几何指标，而几何指标证明不了「这几个群业务上真实存在」；人肉抽检是唯一旧办法，且不可比。
- **LLM 评估聚类质量 · AI 改变了什么机制**：把「这组簇好不好」的判断从指标换成模型的一次整体评判——换的是**评价的表述方式**，不是评价的依据。
- **LLM 评估聚类质量 · 由此得到的**：它能产出一段可读的评述，帮助 reviewer 定位可疑的簇，省掉一部分通读样本的时间。
- **LLM 评估聚类质量 · 由此付出的**：**它给不出可复现的分数**，同一组簇在不同提示下评述不同，因此不能作为验收依据；把它当验收依据，等于把「业务上真实存在」这一判断换成一次不可复现的生成——而验收仍要落回一个真实的下游动作（[§7 §7.3.4](03-clustering-section-7-sec7.md)）。
- **LLM 评估聚类质量 · 证据与来源**：公开材料以用法记录与论文为主；按本节修正后的 ① 判**满足**（用模型评判质量这一类做法有同行评审出处，可按关键词 LLM-as-a-judge 自行检索核验）、**③ 不满足**（针对「一组簇的质量」的判据与阈值未定型）、**② 无**。
- **LLM 评估聚类质量 · 成熟度**：**L3**（与 5.1 表「LLM 评估聚类质量」行一致）：① 满足、③ 不满足、② 无。

- **Agent 驱动聚类 · 旧做法与它的卡点**：聚类任务的发起靠人发现「这里可以分群」，选算法、调参、评估、交付四步都由人串起来；卡点不是算力，是**没人发起**。
- **Agent 驱动聚类 · AI 改变了什么机制**：把「发起与串联」交给智能体——换的是**任务的提出者**，不是簇的定义方式。
- **Agent 驱动聚类 · 由此得到的**：如果验收动作可以被机器表达，那么「发现可聚类的地方 → 跑一版 → 交给人审批」这条链就能被批量触发，覆盖人不会主动去看的长尾数据。
- **Agent 驱动聚类 · 由此付出的**：**验收无法外包**——本节的所有方向最后都要落到一个真实的下游动作上，而「这个分群有没有用」只有业务方能回答；在验收标准写成机器可判之前，Agent 只能产出提案，而提案一多，复核就成了新的瓶颈（[§3 §3.2.10](03-clustering-section-3-sec3.md) 关于把随机划分固定成组织事实的那条失效点，在批量触发下会放大）。
- **Agent 驱动聚类 · 证据与来源**：没有面向「由智能体自主发起并验收聚类」这一能力项的正式载体；**① 不满足、② 无**。
- **Agent 驱动聚类 · 成熟度**：**L3**（与 5.1 表「Agent 驱动聚类」行一致）：① 不满足、③ 不满足、② 无。

- **聚类作为 RAG 预处理 · 旧做法与它的卡点**：建库侧的旧做法是逐条处理文档，分块之间高度重复、主题散乱，检索时返回一堆同质内容挤占上下文；而主题要靠人读出来。
- **聚类作为 RAG 预处理 · AI 改变了什么机制**：把「哪些内容讲的是同一件事」交给聚类在产品上表达——离线去重、主题发现、检索后分组三件事共用同一次编码与聚类。它改变的是**建库侧的整理方式**，不是在线检索路径。
- **聚类作为 RAG 预处理 · 由此得到的**：**因为同一主题的文档落在同一个簇里，所以去重与「按主题分组返回」都有了依据，不需要人工维护主题表**；主题一侧还顺带产出每簇关键词，使「这批内容在讲什么」变成可读的产物（[§3 §3.2.9](03-clustering-section-3-sec3.md)）。
- **聚类作为 RAG 预处理 · 由此付出的**：**其一，簇数不受控**——换一个 min_cluster_size 就换一批主题数，而下游报表的口径会跟着漂移，需要人工收敛到可用粒度。**其二，噪声是常态而非异常**——密度聚类会把一部分文档判为不属于任何簇，业务必须单独定义处置方式，不能把噪声静默混进某个簇。**其三，长文短文混排时「可解释」会反转**——c-TF-IDF 描述的是词分布而不是语义，长文档因词数多而主导关键词（[§7 §7.3.4](03-clustering-section-7-sec7.md)）。**其四，它必须留在离线侧**——把聚类放进在线检索的必经环节，等于给每次查询加一次全库结构的依赖。
- **聚类作为 RAG 预处理 · 证据与来源**：【公开】Grootendorst，2022（BERTopic 与 c-TF-IDF）；Angelov，2020（Top2Vec）。**② 不满足**。
- **聚类作为 RAG 预处理 · 成熟度**：**L2**（与 5.1 表「聚类作为 RAG 预处理」行一致）：① 满足、③ 大体满足、**② 不满足**。

- **GraphRAG 的社区检测 · 旧做法与它的卡点**：多跳关系的「为什么」靠人写规则链或展示层模板；图侧实体与内容侧主键之间没有既定的交接方式。
- **GraphRAG 的社区检测 · AI 改变了什么机制**：把「社区」从人工划分换成图算法在抽取出的关系图上自动切分，再由模型为每个社区写摘要——换的是**关系的抽取与分组方式**，不是检索本身的形态。
- **GraphRAG 的社区检测 · 由此得到的**：如果实体到主键的映射成立，同一张图可以分别充当召回通道、过滤条件或解释层，一份数据准备支持三种用法。
- **GraphRAG 的社区检测 · 由此付出的**：**抽取质量决定一切，而它不可控**——实体与关系由模型抽取，漏抽会直接变成看不见的链路缺失，而这类缺失不会报错，只会在回答质量上体现；且三种角色对数据与延迟的要求不同（召回要可检索、过滤要低延迟、解释要可回溯），接口未定意味着无论选哪一种都要重做一次数据准备。
- **GraphRAG 的社区检测 · 证据与来源**：【公开】Traag 等，2019（Leiden）；Microsoft GraphRAG（2024）是这类做法的公开实现之一，其社区检测环节采用 Leiden，公开实现带版本记录。**③ 不满足**（图与检索的交接形态未定）、**② 无**。
- **GraphRAG 的社区检测 · 成熟度**：**L3**（与 5.1 表「GraphRAG 的社区检测」行一致）：① 满足、③ 不满足、② 无。

- **联邦聚类 · 旧做法与它的卡点**：跨机构联合建模默认要把数据搬到一处，合规与工程成本都过不去；而它成立的前提是各方有共享的特征空间（[§3 §3.2.8](03-clustering-section-3-sec3.md) 失效点），这在多数跨机构场景本就不满足。
- **联邦聚类 · AI 改变了什么机制**：把「搬数据」换成「搬可加摘要」——各方本地算和与计数，只上传摘要或加密参数。
- **联邦聚类 · 由此得到的**：**在共享特征空间成立时**，它能不集中原始数据就算出全局质心，这是 K-Means 更新公式天然允许的，不需要为隐私额外牺牲表达力。
- **联邦聚类 · 由此付出的**：**联邦保留的是数值可加，不保留语义一致**——各方同名字段含义不同时，聚合出的全局质心落在任何一方都不描述的位置；而上传的摘要仍有反演风险，差分隐私的噪声随轮次累积并影响簇边界。代价是两笔：一笔在 ID 对齐，一笔在防御。
- **联邦聚类 · 证据与来源**：【公开】McMahan 等，AISTATS 2017（FedAvg）。**③ 不满足**（跨方 ID 对齐与接口无标准形态）、**② 无**。
- **联邦聚类 · 成熟度**：**L3**（与 5.1 表「联邦聚类」行一致）：① 满足、③ 不满足、② 无。

- **流式聚类、零样本表格聚类与对比聚类（合并为一条）· 旧做法与它的卡点**：三条要解的题不同——流式要解「数据持续到达而簇要跟着变」，零样本表格聚类要解「表格数据没有可信距离、又没有标签」，对比聚类要解「表示学习与聚类目标不一致」；共同卡点是它们各自的验收判据都还没有公认形态。
- **流式聚类、零样本表格聚类与对比聚类 · AI 改变了什么机制**：流式换的是「跑一次」这个前提（改成增量分配）；后两者换的是**表示的学习方式**（由对比目标或基础模型给出），不是归组方式。
- **流式聚类、零样本表格聚类与对比聚类 · 由此得到的**：流式让最新到达的数据不必等下一次全量重算；后两者让没有标签、没有可信人工特征的数据也能先分一版。
- **流式聚类、零样本表格聚类与对比聚类 · 由此付出的**：**「新旧标签是否可比」没有标准定义**——增量分配的簇编号会随分布漂移而漂移，上一期的「第 3 群」和这一期的「第 3 群」未必是同一群人，而这类漂移不会体现在任何指标上（[§7 §7.3.3](03-clustering-section-7-sec7.md) 失效条件）；后两条的代价是验收判据未定，拿不出「做对了」的定义，投入就变成一次无法验收的实验。
- **流式聚类、零样本表格聚类与对比聚类 · 证据与来源**：三条都是研究传统，公开材料就是同行评审论文与公开实现（增量聚类可按关键词 streaming clustering 检索，表格基础模型与对比聚类可按原条目给出的题名检索）；按本节修正后的 ① 判**满足**（这两类对象的正式载体本来就只有论文与实现）、**③ 不满足**（「新旧标签是否可比」与「做对了」的判据都没有公认定义）、**② 无**。
- **流式聚类、零样本表格聚类与对比聚类 · 成熟度**：**L3**（与 5.1 表「流式聚类」「零样本表格聚类与对比聚类」两行一致，按合并规则取最弱子项）：① 满足、③ 不满足、② 无。

把上面七条并排看，会发现它们停在低处的理由只有两类：**一类是验收判据还不成立**（判同、评估、Agent 驱动的验收，以及 5.2.4 最后一条里零样本表格聚类与对比聚类各自「做对了」的定义），**一类是前提条件不成立**（联邦需要共享特征空间、社区检测需要可靠的实体到主键映射、5.2.4 最后一条里流式需要新旧标签的可比性口径）。判据 ① 与 ③ 讲的是前一类（载体与接口有没有被定义下来），判据 ② 讲的是后一类——**能拿出「别人在生产里用过」的材料，本身就是前提条件成立的证据**。

### 5.3 与本主题既有栈的接口在哪

聚类不是独立系统：它的输入来自特征与编码两侧，输出交给标签字典、下游动作与检索侧。写清接口边界（谁调用谁、以什么形态穿过边界、失败时谁负责）比写「与 X 结合」有用。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 编码器 ↔ 特征与索引 | 交接物 = **编码器版本 + 向量维度**；换版即整库重算 | 拥有编码器的那一侧（谁换版本谁负责重算与重跑评估） | 需登记：多数项目不记录编码器版本 |
| 聚类产出 ↔ 标签字典 | 交接物 = 簇编号 + 簇名 + 版本（编码器 + 预处理链 + 聚类参数同属一个版本） | 数据科学侧；簇不稳时先采用名称等于把随机划分固定成事实 | 需新增：字典与签核环节 |
| 聚类产出 ↔ 下游动作（运营 / 风控 / 推荐） | 交接物 = 稳定的簇编号 + 可读名称；下游读字典，不现场调模型 | 下游业务侧；没有动作可验收时，指标无法说明分群有效 | 既有做法，验收环节常缺失 |
| 聚类 ↔ 向量检索 / 向量库 | 交接物 = Top-K 主键 + 分数 + **编码器版本**；索引可重建，主键不可丢 | 检索侧 | 既有技术 |
| 聚类 ↔ 主题发现（关键词与描述） | 交接物 = 每簇关键词与一句话描述；长文短文混排时它描述的是词分布而非语义 | 主题侧；应按长度分层处理 | 既有技术，混排语料下需分层 |
| 聚类 ↔ 图 / GraphRAG | 交接物 = 实体到主键的映射；检索不到合法主键即视为未命中 | 检索侧（返回无主键的实体等于制造幻觉） | 需自建：实体到主键的映射常被忽略 |
| 聚类 ↔ 跨机构联合（联邦） | 交接物 = 可加摘要（样本数 / 线性和 / 平方和）；前提是共享特征空间与 ID 对齐 | 各方共担；ID 对齐不成立时聚合结果没有意义 | 未定型 |
| 聚类 ↔ 流式链路 | 交接物 = 增量分配 + 「新旧标签是否可比」的口径；摘要会漂移，需周期性重建 | 流侧；漂移不会被离线指标捕捉 | 未定型 |

这张表的八行里，只有三行属于既有能力（向量检索的交接物、主题发现的关键词、下游动作的读字典方式），其余都要新建登记或新建口径。**失败归属必须在设计阶段写清**，否则会退化成扯皮：上线的分群和上一期对不上，是编码器换了版本、预处理链漏了一环、还是簇编号在增量分配里漂移了？三件事都能解释同一个现象，而它们分属三个环节。

其中有一处最容易漏：**「编码器版本」与「聚类参数版本」不是同一件事**。前者决定向量空间（换了编码器，旧向量与新向量不再可比，需要整库重算），后者决定切法（换了种子或 min_cluster_size，同一空间里的划分会变，但向量不必重算）。两者都要登记，但补救成本不在同一档【经验：相差约一到两个数量级，随语料规模、编码器是自建还是托管、索引是否需要重建而变】（换编码器要重跑全库编码与索引重建，换聚类参数只重跑分组、不动向量）——登记时把它们写成两个字段，比合成一个「模型版本」要好。

**判定这张表有没有被用起来**：每个季度核对两个数——本季有多少条分群产出能追到编码器版本，有多少条能追到标签字典的签核记录。两个数都是零，说明表还停在文档层面。

### 5.4 公开进展与文献

分三类列，只列能给出会议 / 文档名 + 年份的条目；**宁少勿假**。

**论文**

- Reimers & Gurevych，EMNLP 2019（Sentence-BERT）——把语义相似度变成可计算距离，是「编码器聚类」这条方向的方法来源，也是 5.2.1 判据 ① 的依据。
- Radford 等，ICML 2021（CLIP）——图文对比对齐，使两种模态落进同一个可比空间；5.2.3 判据 ① 的依据。
- Campello 等，2013（HDBSCAN）——密度聚类的自适应扩展，其公开实现带版本记录，是「接口跨多个主版本未变」这一条的核验入口。
- Grootendorst，2022（BERTopic 与 c-TF-IDF）；Angelov，2020（Top2Vec）——把「这一簇在讲什么」变成可读标签的做法，是 5.2.2 与 5.2.4 中主题发现一侧的依据。
- Traag 等，2019（Leiden）——社区检测的当前通用算法，GraphRAG 类做法在图上切分时的依据。
- McMahan 等，AISTATS 2017（FedAvg）——联邦方向的聚合方法出处。

**官方文档 / 版本化实现（判定入口）**

- **密度聚类与近邻检索的公开实现的版本记录**——核验「归一化 + 余弦 + 聚类参数是否跨多个主版本未变」这一条（5.2.1 的 ③）。具体入口是两份实现各自的 release notes：HDBSCAN（Campello 等，2013）的 `hdbscan` 包与 scikit-learn 的 `HDBSCAN` 估计器；近邻检索一侧看 Faiss（Johnson 等，2017）的 release notes。要看的是参数签名有没有变，不是版本号大小。
- **各托管 Embedding 服务的模型页与版本说明**——核验三件事：输出维度、单次输入长度上限、批次上限。这一类给到**文档名 + 页内小节**这一级，不写死 URL（链接会随版本失效）：用「产品名 + embeddings + API reference」检索，命中的就是该产品自己的 Embeddings 参考页或模型页——OpenAI 的 Embeddings 参考页（`text-embedding-3`，2024）、Cohere 的 Embed API 参考页（`embed-english-v3`，2024）、Google 的 Gemini API 文档 Embeddings 一节（Gemini Embedding，2024）、Anthropic 的 API 参考 Embeddings 一节（Claude Embeddings，2025）、Voyage AI 的 Embeddings 参考页（2024）、阿里 DashScope 的文本向量模型页（2024）、BGE 的模型卡（2024）、百度 ERNIE Embedding 的模型页（2024）与 Nomic Atlas 的嵌入模型页（2024）。其余同类服务按各自的文档页核验——其中 **HuggingFace 的托管推理端点**本身不发布模型、只托管第三方模型，入口是所托管模型各自的模型卡，核验项同上。**不要把对话模型的上下文长度记到嵌入模型上**；判定方法是打开该模型自己的文档页，而不是首页或模型对比页。
- **主题发现类工具的版本记录**（BERTopic 的 release notes 与文档，Grootendorst 2022；Top2Vec，Angelov 2020）——含 c-TF-IDF 相关参数与 `min_cluster_size` 的说明；核验簇数是否由结构决定、以及换一个参数会换一批主题数这一性质。

### 5.5 被过度宣传的部分

**「LLM 可以直接做聚类，取代传统算法」** —— 实际是：模型在簇上的作用主要落在表达与裁决（命名、评估、以及有限规模的判同），归属判定仍由算法负责。原因：成对判定要 N(N−1)/2 次比较，N=10⁴ 时约 5×10⁷ 次【推算：10⁴ × 9999 ÷ 2 ≈ 5×10⁷】，这条路径在规模上不成立；而「模型给出聚类中心」这类说法，本质是先降维再落到传统算法。**它什么时候才会成真**：出现公开的、把模型判定作为归属主路径并上量的架构——注意这说的是「谁属于哪个簇」，不是「这个簇叫什么」。

**「Embedding 聚类是零样本的，所以不需要治理」** —— 实际是：零样本省掉的是标注，不是治理。编码器版本、预处理链、聚类参数与簇名签核一件都没少，而它们不登记时错误不可见——聚类不会报错，只会给出一个自洽但不同的划分。原因：相似度是一次性定义、长期复用的资产，而资产的成本在项目早期看不出价值，等换人接手或换一批语料时才显形。**它什么时候才会成真**：变更记录里出现「编码器版本 + 预处理链 + 聚类参数」三个字段，并且重跑一次能复现同一批簇。

**「长上下文模型意味着 Embedding 也能吃长文本」** —— 实际是：嵌入模型的输入长度上限要单独查它自己的文档页；把对话模型的上下文长度记在嵌入能力上，是这类清单最典型的串行错误。原 §5.3 里「标称 200 万上下文 Embedding」这一类条目正是这种记法，本节不转载。原因：嵌入与生成是两种不同的服务形态，长度上限、维度、批次约束各自定义。**它什么时候才会成真**：在该嵌入模型的官方文档页上看到这个数字，并且该模型的批次与维度说明与之一致。

三条合起来看，被过度宣传的部分有同一个形状：**它们都把「某一环变好了」讲成了「整条链可以少一环」**。模型换掉的只是表达与裁决（归属仍在算法手里）、零样本换掉的只是标注（治理一件没少）、长上下文换掉的只是嵌入服务的另一项参数（与聚类目标无关）。识别方法因此很简单——**把宣传句里的动词换成「表达」「标注」「参数」，看它还成不成立**。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 编码器 Embedding 会成为文本 / 图像归类的默认起点，但「由模型决定谁属于哪个簇」不会成为主流 | 生产系统里归属判定仍是算法，模型只出现在命名与评述环节；工具链把编码与聚类拆成两个独立步骤 | 出现把模型判定作为归属主路径、并给出规模与代价口径的公开架构 |
| 编码器版本与预处理链会像特征口径一样进入分群产出的变更登记 | 分群的发布物或标签字典里出现「编码器版本 + 预处理链」字段；重跑可复现成为验收项 | 三年后仍只登记簇数与标签名；换编码器靠口头同步，跨期对比无法判断 |
| 聚类在 RAG 里的落点会停在离线建库侧，不进在线检索路径 | 公开的 RAG 架构里，在线链路仍是「编码 + 近邻检索」，聚类只出现在离线去重与主题发现 | 出现把聚类作为在线检索必经环节并上量的公开架构 |
| 主题发现会以「由结构决定簇数 + 人工收敛粒度」的方式落地，而不是由模型直接给 K | 实践中把 min_cluster_size 的业务含义写进流程文档；主题数在报表口径里被显式冻结 | 出现无需任何粒度设定、即可稳定产出可下线使用的主题体系的公开方案 |

四条都能被**公开文档与实际变更记录**证实或证伪，不需要内部数据：

- 第 1 条看工具链是否把编码与聚类拆开、以及公开架构里归属由谁判定，一到两年见分晓。
- 第 2 条看分群发布物的必填字段，一到两年。
- 第 3 条看公开 RAG 架构的在线链路里有没有聚类环节，两到三年。
- 第 4 条看实践文档里簇数是怎么被定下来的，一到三年。

最值得先盯第 2 条：它是唯一一条**不依赖任何新模型发布**就能观察到的信号，而且它一旦做不到，其余三条的结论都失去可比性——编码器换了而没人知道，任何跨期对比都不成立。

提醒一句：这四条问的都不是「哪个编码器会更强」，而是「**判断依据会不会出现在公开文档里**」。前者无法证伪，后者可以逐条核对。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有一批无标签文本要分群 | 先固定相似度：编码器选型 + 归一化 + 降维参数写进流水线，再谈算法（[§7 §7.3.2](03-clustering-section-7-sec7.md)） | 换一个随机种子后簇的稳定性；轮廓系数与业务 review 是否一致 | 不要在相似度还没定义清楚时调聚类参数；不要把标准化写在临时脚本里 |
| 分群结果要进报表与考核 | 先落标签字典：簇编号 + 名称 + 版本，由人签字（5.2.2） | 标签一进报表后，簇结构变了会不会有人知道 | 不要在簇本身不稳定时先采用名称；不要把一次划分当成分群体系 |
| 想用模型给簇命名 | 现在就用，取代表样本交给模型产出候选名，人工 review 后入库 | 两次独立命名的语义重合度 | 不要让模型参与「谁属于哪个簇」；不要把命名结果直接灌进下游而不签核 |
| 想把聚类接进 RAG | 只放离线建库侧：分块去重 + 主题发现（5.2.4） | 噪声文档（不属于任何簇的那部分）的处置方式是否被定义 | 不要在在线检索路径里加聚类环节；不要沿用默认 min_cluster_size 而不定义业务含义 |
| 数据是持续到达的 | 先定义「新旧标签是否可比」的口径，再考虑增量分配 | 簇编号漂移时有没有任何监控能发现 | 不要在标签可比性口径定下来之前把增量标签供下游使用 |
| 想上 Agent 驱动聚类 / 联邦聚类 | 先补前置：验收动作能否被机器表达、跨方 ID 是否对齐 | 提案量与人工复核量之比 | 不要在验收标准写成机器可判之前让它自动发起；不要为图 + 聚类预留 schema |

「明确不要做」这一列的共用逻辑只有一句：**本节真正变了的只有「相似度由谁定义」与「簇由谁表达」，簇怎么切与谁来验收一寸没动**。所以预算应当投在相似度的可重放、编码器版本登记与标签字典这三件确定性工程上；这三样没定下来之前，任何「AI 原生聚类」的采购都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先把相似度写成可重放的步骤**：标准化方式、编码器、归一化时机、降维参数。交给一个没参与过本项目的人按它重跑一遍，能复现同一批簇才算过。
2. **再定验收动作**：用簇标签驱动一个真实动作，看它是否比随机分组更有效。没有这一步，后面所有指标都只是几何一致性。
3. **然后登记版本**：编码器版本与聚类参数进变更记录。这一步决定跨期对比有没有意义。
4. **最后才谈 Agent 与联邦**：这两类都会改变发起者与责任归属，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新模型——可重放的预处理链、验收动作、版本登记、标签字典的签核，全是流程与工程。这也解释了本节为什么没有 L1：真正成熟的那部分（编码器 + 传统聚类）不需要被宣传，而需要被宣传的那部分，还没有成熟到能被建设方之外的人核验。

### 5.8 小结

> 本节小结：AI 在本主题上**只改了两处机制**——**相似度的定义权从人工特征工程转到编码器的训练目标**（于是零样本成为可能，新领域不必先标注就能拿到第一版分组），以及**「这个簇是什么」的表达从人换成了模型**（于是标签终于能被业务读懂）。它**没有改变**的是两件事：簇怎么切仍由算法族决定（换更强的编码器不改变 K-Means 假设簇是球、也不改变 DBSCAN 假设簇是密度连通的一块）、几何指标仍然证明不了分群在业务上真实存在（验收仍要落回一个真实的下游动作）；它同时换来一项新负担——**编码器版本等于向量空间版本**（换一次就要整库重算，而聚类不会报错，只会给出一个自洽但不同的划分）。本节没有一行达到 L1，离得最近的四行——编码器聚类、LLM 命名、多模态聚类、聚类作为 RAG 预处理——差的只有「第三方（非厂商）公开生产案例」这一条；所以现在该投的是可重放的预处理链、验收动作与版本登记，而不是「让 LLM 直接做聚类」。
