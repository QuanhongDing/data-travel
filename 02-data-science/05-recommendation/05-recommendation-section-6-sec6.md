## 6. 落地实践

### 6.1 某头部电商"**1 亿用户双塔+DeepFM+DIN**"6+ 年（2018-2024）

**背景（Why）**

该电商 2018 年面临**大规模推荐的极限约束**：
- **1 亿用户、10 万 SKU**——**协同过滤的矩阵分解训练不动亿级交互**
- **QPS 10 万+**——**推荐必须在 100ms 内完成召回 + 粗排 + 精排 + 重排**
- **长尾商品曝光不足**——协同过滤天然偏向热门，**90% 的 SKU 拿不到 1% 流量**
- **多目标**——CTR、CVR、GMV、收藏——**单一目标会失真**

**触发点（What）**

2018 年该电商启动推荐系统演进（[案例 2018]），目标：
- **CTR**——**+20%**
- **GMV**——**年增 30%+**
- **QPS**——**10 万+**、**延迟 < 100ms**
- **长尾商品**——**有曝光**

**详细做法（How）**

该电商推荐系统的**5 大核心组件**：

1. **双塔召回（核心创新）**
   - 关键设计：**User Tower + Item Tower 各出 embedding**，ANN 检索 Top-K
   - 关键能力：**十万级候选秒级召回**
   - 关键数字：**QPS 10 万+**、**召回率 95%+**
   - 结构示意：
     ```
     [user_tower]
       user_id + hist_seq + context
            ↓
        user_emb  ─────┐
                       │  inner product
        item_emb  ←────┤
     [item_tower]      │
       item_id + attr    ↓
                    Top-K 检索 (Faiss)
     ```

2. **DeepFM 粗排（核心）**
   - 关键设计：**FM 捕捉低阶交叉 + DNN 捕捉高阶**
   - 关键能力：**候选从 1000 缩到 100**
   - 关键数字：**CTR +10%**

3. **DIN 精排（核心）**
   - 关键设计：**Attention 加权用户历史行为**——点过 A 的人在 A 候选上 attention 高
   - 关键能力：**个性化精排——同一个用户对不同候选得到不同的历史行为加权表示**
   - 关键数字：**CTR +20%**
   - 关键示意：
     ```
     候选商品 A ──→ Attention (A vs 用户历史) → 加权用户表示
     候选商品 B ──→ Attention (B vs 用户历史) → 加权用户表示
     分别输入精排塔
     ```

4. **重排（多样性 + 业务规则）（核心）**
   - 关键设计：**打散同店 / 同品 / 同类**，防「点啥推啥」信息茧房
   - 关键能力：**生态健康 + 用户体验**
   - 关键数字：**用户停留 +8%**

5. **EasyRec 平台（核心创新）**
   - 关键设计：**统一推荐建模框架**——双塔 / FM / DIN 都能在同框架跑
   - 关键能力：**模型间可横向对比**——同一套框架下换模型只改配置，不再每个模型各写一套代码
   - 关键数字：**迭代效率 +50%**

**该电商推荐系统关键数字**（[案例 2018-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **CTR** | 基线 | +20% | **+20%** |
| **GMV** | 基线 | 年增 30%+ | **+30%** |
| **QPS** | 不可用 | 10 万+ | **∞** |
| **召回率** | 不可用 | 95%+ | **∞** |
| **延迟 P99** | — | < 100ms | **—** |
| **长尾曝光** | 基线 | +40% | **+40%** |
| **停留时长** | 基线 | +8% | **+8%** |
| **迭代效率** | 基线 | +50% | **+50%** |

**具体数字（How much）**

- 团队规模：该电商推荐算法团队 200+ 人
- 关键数字：**CTR +20% / GMV +30%**；**QPS 10 万+**；**1 亿用户 / 10 万 SKU**
- 业务影响：覆盖该电商**全部推荐位**

**失败教训**

- 早期「**只用协同过滤召回**」——长尾 SKU 无人看、新品拿不到曝光，倒逼**「双塔 embedding + ANN 召回」**
- 「**DIN 用平均池化历史行为**」——效果不如加权、兴趣被平均掉，倒逼**「加 Attention 按候选加权历史」**
- 「**重排只按分数排序**」——结果全是同店商品、用户觉得「越推越窄」，倒逼**「重排做打散 + 多样性 + 业务规则」**
- 「**多算法各自实现、迭代慢**」——每个模型一套代码、无法快速横向对比，倒逼**「统一推荐建模框架，迭代效率 +50%」**

### 6.2 某短视频平台"**5 亿 DAU + MMoE + SIM 长序列**"6+ 年（2018-2024）

**背景（Why）**

该短视频 2018 年面临**超大规模短视频推荐**：
- **日活 5 亿**——**用户历史序列长度 1000+**
- **短期 CTR 饱和**——只优化 7 日行为，**次日新视频曝光不足**
- **单一精排**——CTR 高但**完播率掉**、**长期留存掉**
- **长序列建模**——**Transformer 全量计算 O(N²) 不可行**

**触发点（What）**

2018 年该短视频启动**MMoE + SIM 长序列**（[案例 2018]），目标：
- **日均时长**——**+15%**
- **用户活跃**——**+10%**
- **次日留存**——**+5%**

**详细做法（How）**

该短视频推荐的**5 大核心组件**：

1. **双塔召回（核心创新）**
   - 关键设计：**用户侧 = 长序列 SIM 压缩**（不再全量 attention）
   - 关键能力：**亿级候选 + 长序列**
   - 关键数字：**召回率 95%+**、**QPS 10 万+**

2. **MMoE 多任务精排（核心）**
   - 关键设计：**点击 / 完播 / 点赞 / 关注 / 评论五任务 + 共享 Expert**
   - 关键能力：**多目标不打架——点击 / 完播 / 点赞 / 关注 / 评论五个目标共享 Expert，不各自抢特征**
   - 关键数字：**多任务 +8%**、**日均时长 +10%**
   - 结构示意：
     ```
     共享 Expert 层（4 个专家）
        ↓      ↓      ↓      ↓      ↓
      点击塔  完播塔  点赞塔 关注塔  评论塔
     ```

3. **SIM 长序列（核心）**
   - 关键设计：**从全量行为中用 GSU 检索 Top-K 相关 + 软搜索**——**O(N²) → O(K²)**
   - 关键能力：**长序列可建模——GSU 先检索 Top-K 相关行为（K≪N），把注意力计算从 O(N²) 降到 O(K²)**
   - 关键数字：**长序列提升 +5%**

4. **ByteRec 平台（核心）**
   - 关键设计：**字节自研推荐框架**——支持双塔 / MMoE / SIM / 多目标一站式
   - 关键能力：**千级模型并行——双塔 / MMoE / SIM 在同一个框架里并行迭代，不再各写一套代码**
   - 关键数字：**迭代效率 +60%**

5. **深度学习平台（核心创新）**
   - 关键设计：**训练 / 部署 / 监控 / A-B 一体**
   - 关键能力：**5 亿 DAU 实时响应**
   - 关键数字：**P99 < 200ms**

**该短视频推荐关键数字**（[案例 2018-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **日均时长** | 基线 | +15% | **+15%** |
| **用户活跃** | 基线 | +10% | **+10%** |
| **次日留存** | 基线 | +5% | **+5%** |
| **多任务** | 不可用 | +8% | **∞** |
| **长序列** | 不可用 | +5% | **∞** |
| **QPS** | 不可用 | 10 万+ | **∞** |
| **迭代效率** | 基线 | +60% | **+60%** |

**具体数字（How much）**

- 团队规模：该短视频推荐算法团队 500+ 人
- 关键数字：**日均时长 +15% / 活跃 +10%**；**5 亿 DAU**；**P99 < 200ms**
- 业务影响：覆盖该短视频**5 亿 DAU**

**失败教训**

- 早期「**只看 7 日行为**」——新视频曝光不足、兴趣表达偏窄，倒逼**「SIM 长序列建模」**
- 「**用全量 Transformer 处理长序列**」——O(N²) 在 N=1000 时训练不动，倒逼**「GSU 先检索 Top-K 再精算，把复杂度降到 O(K²)」**
- 「**只优化 CTR**」——CTR 上升但完播下降、长期留存受损，倒逼**「多任务 MMoE 让模型自己平衡多目标」**
- 「**训练与推理链路不一致**」——离线调好的模型上线效果打折，倒逼**「训练 / 部署 / 监控 / A-B 一体化平台」**

### 6.3 某新闻信息流"**秒级实时推荐**"5+ 年（2019-2024）

**背景（Why）**

该新闻 2019 年面临**实时新闻推荐**：
- **实时新闻**——「突发事件 30 分钟必须推给相关用户」，**离线推荐 4 小时延迟不可接受**
- **内容敏感**——**政治 / 灾难**类容错为 0，**推错代价大**
- **内容生命周期短**——新闻 **6 小时后失效**

**触发点（What）**

2019 年该新闻启动实时推荐（[案例 2019]），目标：
- **CTR**——**+12%**
- **用户留存**——**+8%**
- **延迟**——**分钟级**

**详细做法（How）**

该新闻实时推荐的**5 大核心组件**：

1. **双塔召回（实时）（核心创新）**
   - 关键设计：**用户塔定时更新**（5 分钟）+ **物品塔实时更新**（每条新闻入推流即更新）
   - 关键能力：**突发事件秒级进候选**
   - 关键数字：**物品新鲜度 < 1 分钟**

2. **DIN 精排（核心）**
   - 关键设计：**Attention 关注用户最近点击主题**——突发新闻命中相关用户
   - 关键能力：**实时个性化——attention 只看最近点击主题，突发新闻能立刻命中相关用户**
   - 关键数字：**CTR +12%**

3. **重排（多样性）（核心）**
   - 关键设计：**打散同类 / 同源 / 同观点**——防信息茧房
   - 关键能力：**生态健康——同类 / 同源 / 同观点被打散，避免越推越窄的信息茧房**
   - 关键数字：**用户停留 +10%**

4. **Flink 实时（核心）**
   - 关键设计：**用户行为流进 Flink → 实时更新用户 embedding**
   - 关键能力：**秒级个性化——行为流进 Flink 后用户 embedding 秒级刷新，兴趣不再按天更新**
   - 关键数字：**用户 embedding 延迟 < 1 分钟**

5. **Redis 在线（核心创新）**
   - 关键设计：**用户 embedding / 候选池双写 Redis**
   - 关键能力：**毫秒级在线读取**
   - 关键数字：**P99 < 50ms**

| **用户留存** | 基线 | +8% | **+8%** |
| **停留时长** | 基线 | +10% | **+10%** |
| **物品新鲜度** | 4 小时 | < 1 分钟 | **-99.6%** |

**具体数字（How much）**

- 「**用户 embedding 每日更新**」——热点发生时用户兴趣已经偏了，倒逼**「改 Flink 流式更新，秒级响应」**
- 「**突发新闻没有兜底**」——政治灾难类推错的代价极大，倒逼**「白名单 + 人工审核兜底」**
- 「**物品侧向量更新滞后**」——新发新闻要 4 小时才能进入召回，倒逼**「物品向量实时生成，新鲜度压到 1 分钟以内」**

### 6.4 某 LLM 推荐平台"**生成式推荐**"3+ 年（2021-2024）

**背景（Why）**

该电商 2021 年面临**生成式推荐（LLM 推荐）**：
- **LLM 助手**——用户**用自然语言描述需求**（「给妈买生日礼物，预算 500」）
- **传统推荐**——**只能从历史行为猜**，**对「无行为新需求」无能为力**
- **对话式推荐**——多轮交互，**模型要理解上下文**

**触发点（What）**

2021 年该电商启动**生成式推荐**（[案例 2021]），目标：
- **对话式推荐**——**用户转化率 +5%**
- **冷启动**——**新需求可推荐**
- **多轮上下文**——**自然语言理解**

**详细做法（How）**

该电商 LLM 推荐的**5 大核心组件**：

1. **LLM 对话式推荐（核心创新）**
   - 关键设计：**用户自然语言输入 → LLM 提取意图 → 检索 + 精排 → 自然语言回复**
   - 关键能力：**无历史也能推荐**
   - 关键数字：**对话推荐转化 +5%**
   - 流程示意：
     ```
     用户：给妈买生日礼物，预算 500
     ↓ LLM 意图提取
     意图：{ recipient: "妈妈", occasion: "生日", budget: 500, category: "礼物" }
     ↓ 检索 + 精排
     候选 50 条
     ↓ LLM 生成回复
     "为您推荐几款适合妈妈的生日礼物，都在 500 元以内：…"
     ```

2. **Prompt 模板（核心）**
   - 关键设计：**Prompt 版本化 + A-B + 灰度**
   - 关键能力：**改 prompt 不发版**
   - 关键数字：**Prompt 迭代周期 -80%**

3. **RAG 检索（核心）**
   - 关键设计：**用户 query → 商品 embedding 检索 Top-K → LLM 综合**
   - 关键能力：**真实库存 + LLM 综合**
   - 关键数字：**推荐准确率 +15%**

4. **多轮上下文（核心）**
   - 关键设计：**对话历史进 LLM context**——可追问「预算能不能到 800」
   - 关键能力：**真正对话式——对话历史进 context，用户可以连续追问而不必重述需求**
   - 关键数字：**多轮转化 +10%**

5. **生成式集成（核心创新）**
   - 关键设计：**LLM 与传统推荐融合**——LLM 决定「推荐什么 + 如何解释」，传统召回给候选
   - 关键能力：**对话 + 个性化兼备**
   - 关键数字：**整体转化 +8%**

**该电商 LLM 推荐关键数字**（[案例 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **对话式转化** | 基线 | +5% | **+5%** |
| **多轮转化** | 基线 | +10% | **+10%** |
| **整体转化** | 基线 | +8% | **+8%** |
| **推荐准确率** | 基线 | +15% | **+15%** |
| **Prompt 迭代** | 不可用 | -80% | **∞** |
| **RAG 检索** | 未建设 | 已覆盖 | **新增能力** |
| **LLM 对话式** | 未建设 | 已覆盖 | **新增能力** |

**具体数字（How much）**

- 团队规模：该电商 LLM 推荐团队 30+ 人
- 关键数字：**对话 +5% / 整体 +8%**；**Prompt 迭代周期 -80%**；**推荐准确率 +15%**
- 业务影响：覆盖该电商**LLM 助手**全部用户

**失败教训**

- 早期「**传统推荐只能从历史猜**」——面对「给妈买礼物」这类无历史的新需求无能为力，倒逼**「LLM 对话式推荐」**
- 「**让 LLM 自由发挥**」——模型编造出不存在的商品、用户点进去发现查无此物，倒逼**「改为三段式：LLM 提意图 → 真实库存检索 → LLM 解释」**
- 「**Prompt 写死在代码里**」——改一个词就要发版、迭代周期两周，倒逼**「Prompt 配置化 + 灰度」**
- 「**RAG 只做向量召回**」——语义相近但不符合硬约束（尺码、预算、库存）的商品被召回，倒逼**「向量召回 + 结构化过滤组合」**

**100 → 1000 阶段：12-24 个月**
