## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表最根本的问题，是把**取决于场景的结论**伪装成**绝对结论**。「冷启动」这一维在行为丰富的电商与新品驱动的平台权重相反；「长序列支持」在有专职平台团队时是资产，在没有算力预算时是负债。分数 3 与 4 之间没有任何机制说明，读的人只能按自己的直觉补权重，于是两个团队读同一张表得出相反的结论，还都觉得自己是照表办事。

第二类误导是**维度并列**：把机制不同的东西放在同一行比较。协同过滤与双塔都出现在「召回」语境下，但前者用共现计数定义相似度、不需要训练，后者把用户与 Item 编码进同一向量空间做内积、依赖负采样；它们在「大规模可扩展」一行上分数不同，真正来源却是「相似度是算出来的还是学出来的」——同一张表里，「矩阵分解」与「FM」的分差又来自另一条机制（分解评分矩阵 vs 显式建模特征二阶交叉）。维度名字一样，机制不一样，分数就没有可比性。

第三类误导是**把成熟度当先进度**。原打分表的「工业成熟度」一列上，协同过滤 / 矩阵分解 / FM / 双塔都是 5 分，DIN 4 分、LLM 推荐 3 分、生成式推荐 2 分——而这一列分数最低的后两列，恰恰是「AI 时代适配」一列得 5 分的两个。同表之内，越贴近当下热点的方案越在成熟度上显得像缺点；但对多数团队，成熟度高的方案意味着有版本化文档、有稳定接口、有别人踩过的坑，它才是正确起点。把「趋势」与「能不能上线」混在一列打分，路线图就会按论文发表日期来排。

更要紧的是，打分表完全绕开了本主题的三条硬约束（[§3 §3.1](05-recommendation-section-3-sec3.md)）：**候选集规模 × 请求延迟预算**、**反馈闭环**、**目标多元**。任何方案能不能用，第一问是它在这三条约束下还剩多少空间，而不是它在某个维度上打几分。典型例子：DIN 的注意力表达力确实强于 FM，但它必须在被召回的小集合上运行；把它当召回层方案用时，问题不在精度而在算不完——**它被排除的理由是预算，不是能力**。

第四类误导出在打分表的下游：它给出的结论最终要落成决策树，而打分表本身不含任何阈值依据。「行为数据大量」是多大量、「长序列」是多长、「LLM 可用」到什么程度算可用——这些词在树上是判断节点，在打分表上找不到对应物，于是阈值只能凭空定。本章的做法是让每一个阈值都能回溯到三类来源之一：**成本函数**（7.4 的推算）、**结构约束**（内积表达不了交叉、共现为零即无信号、前缀随码本漂移而失真）、**组织约束**（探索预算能否跨过考核周期）。读者可以据此逐节点复核，而不是接受一个数字。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 候选集与延迟预算 | 这套方案在千万级候选上还跑得动吗 | 单次请求能承受多少次模型推理；不满足这条的方案不是「弱」，是「上不了线」 |
| 信号来源 | 它依赖行为共现、内容语义，还是探索产生的标签 | 三种信号的获取前提不同：共现为零时依赖共现的方案是**退化**而不是变弱 |
| 落在漏斗的哪一层 | 它决定候选集里有什么，还是只在候选集内排序 | 级联不可逆——召回决定效果上限，精排只决定上限内的顺序 |
| 交叉表达力 | 它能否表达「用户 × 候选」的交叉特征 | 内积空间表达不了交叉，交叉只能推到精排，而精排看不到没被召回的 Item |
| 目标数与考核周期 | 收益何时兑现、成本何时发生 | 探索类的收益延后、成本当期；考核周期短于回报周期会系统性地杀掉它 |
| 版本与可复现性 | 换一次模型或编码器要重建什么 | 决定一次升级是「可估价的迁移」还是「一次事故」（向量作废、序列不可比） |

这张表不是打分表的替身：判据之间**没有权重**，因为它们并不同类。第一条与第三条是否决项——不满足就没有选型问题可言；第二、四、五条决定在满足前两条之后选哪一族；第六条决定的是「这次升级能不能赶在上线前做完」。把否决项与偏好项分开，是本章与打分表的根本区别。

### 7.2 候选方案全景

| 方案 | 定位（漏斗的哪一层） | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 协同过滤（UserCF / ItemCF） | 召回 | 用共现计数定义相似度，按相似邻居的兴趣加权 | 电商早期召回与跨域兜底【经验】 | 自研 / 开源框架内置模块 |
| 矩阵分解（MF / SVD / SVD++） | 召回与打分 | 把评分矩阵近似为 U·Vᵀ，相似度在隐向量空间算 | Netflix Prize 之后的经典基线【经验】 | 自研 / 开源 |
| FM / FFM / DeepFM / xDeepFM / AutoInt | 精排 | 隐向量内积显式建模二阶交叉，高阶交给 DNN 或自注意力 | 电商与广告精排主线【经验】 | 开源（DeepCTR 一类） |
| Wide & Deep / DeepCrossing / DCN | 精排 | 宽侧线性「记忆」与深侧 MLP「泛化」并行 | Google Play（Cheng 等，RecSys 2016）【公开】 | 自研 / 开源 |
| 双塔（Two-Tower / DSSM / YouTube DNN / MIND） | 召回 | 用户与 Item 各自独立编码，交互只在内积空间发生 | 千万级候选的召回事实标准（Covington 等，RecSys 2016）【公开】 | 自研 / 开源 |
| DIN / DIEN / SIM / ETA | 精排 | 用注意力按候选激活历史行为；序列长时只挑相关片段 | 阿里（Zhou 等，KDD 2018）【公开】 | 自研 / 开源 |
| SASRec / BERT4Rec | 精排 / 序列建模 | 对行为序列直接做自注意力 | Kang & McAuley, ICDM 2018；Sun 等，CIKM 2019【公开】 | 开源 |
| 多任务：MMoE / PLE / ESSM / AITM | 精排 | 专家层共享 + 每任务独立门控；或用乘法结构补偿样本偏差 | Ma 等，KDD 2018；Tang 等，RecSys 2020【公开】 | 自研 / 开源 |
| 图模型：NGCF / LightGCN / GraphRec / KGAT / RippleNet / MKR | 召回与精排 | 在用户—物品二部图上做多跳邻域聚合 | 学术与稀疏场景为主【经验】 | 开源 |
| 多模态：VBPR / MMGCN / CLIP4Rec | 召回与内容特征 | 用图文预训练编码器给零交互 Item 一个非退化向量 | He & McAuley, AAAI 2016；Radford 等，ICML 2021【公开】 | 开源 |
| Bandit 探索配额（ε-greedy / Thompson / LinUCB） | 重排或旁路 | 用一部分曝光换反事实标签 | 新闻与信息流（Li 等，WWW 2010）【公开】 | 自研 |
| 深度 RL（DQN / PPO） | 策略层 | 优化长期回报而非单次点击 | 论文与实验环境为主【经验】 | 自研 |
| LLM 推荐（Embedding 召回 / 理由生成 / 直接排序） | 召回与展示层 | 用预训练语言模型的语义先验替代共现信号 | P5（Geng 等，RecSys 2022）、GPT4Rec（Li 等，2023）、ChatRec（Gao 等，2023）【公开】 | 开源模型 + 自研链路 |
| 生成式推荐（TIGER / LC-Rec / CFGen / IDGenRec / P5） | 召回 | 把 Item 量化成语义 ID，召回变成自回归生成下一段 ID | Rajput 等，NeurIPS 2023【公开】 | 开源实现 + 自研（LC-Rec / CFGen 的出处可按模型或论文名自行检索核验） |
| 联邦推荐（FedAvg 类） | 召回 | 各方只上传模型更新，原始行为不出域 | McMahan 等，AISTATS 2017【公开】 | 自研 |

这十五行其实只分五族：**共现族**（协同过滤、矩阵分解）、**交叉与序列族**（FM 系列、Wide & Deep、DIN 系列、SASRec）、**双塔族**、**语义与生成族**（多模态、LLM 推荐、生成式推荐）、**约束补偿族**（多任务、图、Bandit、深度 RL、联邦）。同族内部换的是同一机制的不同实现，差异小；跨族换的是机制本身，差异大。先分族再选，能省掉一半比较。

还有一个容易被表结构掩盖的事实：**族与漏斗层不是一一对应**。共现族与双塔族主要落在召回层，交叉与序列族、多任务族主要落在精排层，Bandit 落在重排或旁路，LLM 推荐会同时出现在两个位置（Embedding 召回在召回层、理由生成在展示层）。所以「定位」这一列比任何一列分数都重要——**问错了层，再强的方案也是错的**。

这张表的作用是逼着「某某方案更强」这句话先落到一层：

| 漏斗层 | 本章落入该层的候选 | 这一层决定什么 | 判据侧重 |
| --- | --- | --- | --- |
| 召回 | 协同过滤、矩阵分解、双塔、多模态、LLM Embedding、生成式、联邦、图（作召回通道时） | 效果**上限**：候选集里有没有正确答案 | 候选从哪来（7.3.1）；在线代价是否与候选池规模解耦 |
| 粗排 | 轻量交叉模型（FM / 小 MLP） | 预算分配：从千级收到百级 | 单条推理成本 |
| 精排 | FM 系列、Wide & Deep、DIN / DIEN / SIM / SASRec、MMoE / PLE / ESSM | 上限**之内**的相对顺序 | 交叉表达力与序列长度（7.3.2、7.3.4） |
| 重排 | Bandit 配额、多样性 / 频控 / 业务硬规则 | 集合级性质与标签生产 | 目标数与考核周期（7.3.3） |
| 展示层 | LLM 理由生成、对话式推荐 | 信任与可解释，**不改变顺序** | 是否触碰效果指标 |

落到层之后，两个方案才可比：同层之间比的是「同样预算下谁的上限更高」，跨层之间根本不该比——精排层的任何改进都无法挽回召回层漏掉的 Item。

「典型使用者」一列要谨慎读：它标的是**该机制的公认出处或最早公开的工业实践**，不是「这些平台今天仍在用它」。多数平台不会公开当前生产链路的完整选型，所以本节只对机制归属下判断，不对任何具体产品当前的能力下断言。

### 7.3 机制差异：为什么它们表现不同（核心节）

下面四个小节按同一条结构写：机制是什么 → 各候选的实现差异 → 由此必然导出的性质 → 公开证据 → 失效条件。只写收益不写代价的对比，评审时应直接打回。

四个维度之间有优先级：**7.3.1 决定上限，7.3.2 决定成本，7.3.3 决定标签供给，7.3.4 决定一次请求内能装几个目标**。若只读一节，读 7.3.1——它是唯一一个「选错之后无法在别处补救」的维度：召回没让某个 Item 进候选集，后面三层再强也看不见它。

#### 7.3.1 候选从哪来：共现空间 / 语义空间 / 序列空间

- **机制是什么**：「相似」用什么判据定义——是共现计数、语义邻接，还是序列解码。这一条决定了候选集里**可能出现什么**，比任何排序层技巧都靠前。
- **它在各候选中的实现差异**：

  | 产生方式 | 相似判据 | 零交互 Item 能否进候选 | 换件的代价 |
  | --- | --- | --- | --- |
  | 共现族（ItemCF / MF） | 谁和谁一起被选过 | 不能，退化为热门兜底 | 重算相似度 / 重训分解 |
  | 双塔族 | 内积空间里的向量邻近 | 不能（ID 侧），能（内容侧） | 重训，重训后历史向量作废 |
  | 语义族（多模态 / LLM Embedding） | 编码器输出的内容邻接 | 能 | 换编码器要全库重编码 |
  | 生成族（TIGER 一类） | 语义 ID 的共享前缀 | 能（靠内容量化） | 码本可能整体漂移，需重建 |

- **由此必然导出的性质**：因为共现族的相似度来自「谁和谁一起被选过」，**所以**共现为零的 Item（新品、长尾、跨域）不是信号弱而是**没有信号**，它只能被热门兜底接住；**又因为**语义族把判据换成编码器输出的内容邻接，**所以**零交互 Item 第一次能拿到非随机候选，代价是语义邻近不等于「会被一起选」——它会稳定推出一批「看起来相关但没人买」的候选；**再因为**生成族把候选产生表述为受限解码下的序列生成（前缀树只允许在真实存在的 ID 前缀上扩展），**所以**「生成目录里不存在的 Item」在解码层面被排除，代价是码本必须跟得上目录变更，「共享前缀」的前提才成立。
- **公开证据**：【公开】TIGER（Rajput 等，NeurIPS 2023）给语义 ID + 生成式召回的机制；【公开】CLIP（Radford 等，ICML 2021）给图文对齐编码器；【公开】YouTube DNN（Covington 等，RecSys 2016）给「候选生成 + 排序」两阶段结构。三条都是**机制存在**的证据，不是「别人在生产里用过并公开了代价」的材料。
- **失效条件**：目录高频变动时语义 ID 的重训跟不上，旧码本与新 Item 语义错位，前缀不再代表语义；内容侧错标（标题党、类目错挂）会直接变成候选，而冷启动路径没有反馈纠正项；共现族在共现为零的样本上无解。

这三条通道在实践中不是互斥选项，而是**配额问题**：因为三者的失效样本集不重合（共现族在零交互上失效、语义族在「相关但不被选」上失效、生成族在目录频繁变动时失效），**所以**正确做法是并行接入并分配配额，而不是用一个替换另一个。判定方法是把请求按「哪条通道贡献了最终候选」分桶，看每条通道覆盖的是哪一类样本——若某条通道只覆盖最难的样本，它的贡献会被平均指标掩盖，也就永远拿不到加预算的依据。

#### 7.3.2 打分在哪里做：内积够不够用

- **机制是什么**：可扩展性来自「用户与候选是否被独立编码」。独立编码 → 向量可预计算、可建索引、候选池规模不进入在线算力，但交互只能在内积空间发生；联合编码（交叉特征）→ 表达力强，但推理次数等于送进模型的候选数。
- **它在各候选中的实现差异**：

  | 方案 | 用户与候选何时相遇 | 在线代价随什么增长 | 表达力边界 |
  | --- | --- | --- | --- |
  | 双塔 | 只在内积那一步 | 与候选池规模相关，与候选集大小无关 | 无法表达特征交叉 |
  | FM / DeepFM | 打分时逐条交叉 | 送进模型的候选数 × 单条推理成本 | 二阶显式 + 高阶隐式 |
  | DIN / SIM | 打分时按候选激活历史 | 同上，且随序列长度上升 | 序列内注意力，序列外仍受限 |
  | 生成式召回 | 解码时（候选尚未存在） | 与生成长度相关，逐 token 累加 | 候选产生方式变了，排序仍要另做 |

- **由此必然导出的性质**：因为双塔把交互限制在内积空间，**所以**它能把 Item 向量离线预计算并建索引，候选池扩大到千万级而在线代价基本不变；**也正因为**内积表达不了特征交叉，**所以**召回丢掉的表达力只能靠精排补，而精排永远看不到没被召回的 Item——这就是级联不可逆；**再因为**交叉与序列族每条候选都要过一次模型，**所以**它们的成本由「漏斗上游送进来多少条」决定，而不由 Item 总数决定。这条性质直接推出下一节 7.4 的成本函数，也是「DIN 到底有多强」这个问题必须先回答「它在多少条候选上跑」的原因。
- **公开证据**：【公开】Wide & Deep 的记忆与泛化并行结构（Cheng 等，RecSys 2016）；【公开】DIN 的注意力激活机制（Zhou 等，KDD 2018）；【公开】LightGCN 的邻域加权聚合（He 等，SIGIR 2020，属同一「用结构替代手工相似度」的思路）。
- **失效条件**：把精排直接放到候选全集上时，总代价退化成 O(候选全集 × 单条推理成本)，延迟预算被击穿；序列特征越长，单条推理越贵，长序列的收益会被算力预算反噬。

由此推出一个工程判断：**「在召回层加交叉能力」这条路基本走不通**——双塔的可扩展性恰恰来自它放弃了交叉，想两者兼得只能改候选的产生方式（生成式召回把交叉挪进序列模型的注意力），或者接受候选池缩小的代价。对多数团队，真实的选项只有两个：接受内积召回 + 强精排，或者把候选池规模降下来换表达力。

#### 7.3.3 标签从哪来：反馈闭环决定探索是否必需

- **机制是什么**：训练标签由推荐系统自己的曝光策略产生。只有被曝光的 Item 才有标签，没被曝光的 Item 永远没有反事实标签。这不是数据量问题，是**数据生成机制**问题。
- **它在各候选中的实现差异**：

  | 方案 | 标签来源 | 能否纠正流行度偏置 | 主要代价 |
  | --- | --- | --- | --- |
  | 监督模型（双塔 / FM / DIN） | 日志里的曝光与点击 | 不能，策略偏置会被原样学进去 | 探索的成本无人承担 |
  | Bandit 配额 | 策略分配的曝光 | 能，估计逐步无偏 | 短期指标下滑，且收益延后 |
  | 深度 RL | 长期奖励信号 | 理论上能 | 需要允许试错的环境，线上不具备 |
  | 语义 / 生成族 | 预训练编码器先验（不依赖本站标签） | 部分能（缓解而非消除） | 内容质量被放大，无反馈纠正 |

- **由此必然导出的性质**：因为只有被曝光的 Item 有标签，**所以**离线样本是被旧策略筛过的，**离线指标涨而在线不动是这条机制的必然结果，不是运气差**；因为 Bandit 把一部分曝光按策略分配出去，**所以**「热门越曝越热」的流行度偏置在机制上被削弱，**代价是探索的成本当期发生、收益延后兑现**——考核周期短于回报周期时，探索会在第一次指标下滑被砍掉；因为语义与生成族用的是预训练先验，**所以**它们不依赖本站标签就能给零交互 Item 候选，**但这也意味着它们无法自我纠正**：推错的人不会点，于是既拿不到正样本也拿不到有区分度的负样本，错误被持续放大。
- **公开证据**：【公开】上下文 Bandit 用于新闻推荐（Li 等，WWW 2010）；【公开】FedAvg 的聚合方法（McMahan 等，AISTATS 2017）属于「不共享原始数据时如何获得协同信号」的另一条路线。
- **失效条件**：长期奖励信号不可得时，深度 RL 没有可优化的目标，公开材料停在仿真与离线；反事实评估（IPS 一类）方差大，评估本身成为独立工程项。

这一条也是「离线评估为什么不可信」的完整答案：不是离线数据集不够大，而是**它的样本分布由旧策略决定**，且新策略能影响的那个区域（未被曝光的 Item）在离线数据里根本没有标签。所以离线指标能回答「在上次曝光的那批 Item 里排序对不对」，回答不了「有没有更好的 Item 从未被曝光」——后一个问题只能靠探索来回答，而探索的成本记账方式与模型迭代完全不同。

#### 7.3.4 一次请求内的目标数：多任务是共享专家，不是多加几个塔

- **机制是什么**：多任务的收益来自**专家被多任务共用**，而不是来自塔的数量；同时 CVR 这类目标的训练分布（点击样本）与推理分布（全曝光）不一致，样本选择偏差（SSB）是内生的。
- **它在各候选中的实现差异**：

  | 方案 | 任务间如何共享 | 怎么处理样本空间不一致 |
  | --- | --- | --- |
  | 单目标 + 人工加权 | 不共享 | 不处理，权重反复漂移 |
  | Shared-Bottom | 共享一整层底层 | 不处理 |
  | MMoE / PLE | 专家池 + 每任务独立门控 | 不处理 |
  | ESSM | 不共享 CVR 塔，改为乘法结构 | pCTCVR = pCTR × pCVR，在曝光全空间取监督 |
  | AITM | 逐层自适应信息迁移 | 迁移强度可学 |

- **由此必然导出的性质**：因为门控决定每个任务取哪些专家，**所以**任务间的梯度冲突被路由隔开，多目标能在一次请求内被平衡；**也因为收益依赖专家被共用**，**所以**当两个任务的用户行为几乎不相关时（例如「完播」与「下单」），门控会退化成各任务各用一组专家，多任务相对单任务不再有增益，而参数量、训练时长与调参成本全部保留。ESSM 的因果链不同：因为 pCTCVR = pCTR × pCVR 在曝光全空间上有标签，**所以** CVR 塔能从乘法结构里隐式拿到无偏梯度，而不需要点击样本的分布与曝光分布一致。
- **公开证据**：【公开】MMoE（Ma 等，KDD 2018）；【公开】PLE（Tang 等，RecSys 2020）；【公开】ESSM（Ma 等，SIGIR 2018）。
- **失效条件**：任务不相关时增益归零；损失权重成为新的超参，改权重等于改各任务的实际优化强度，而它通常不进版本登记。

补一条机制层面的判断：多任务不是「多加目标」的手段，而是「在目标冲突时给出一个可训练结构」的手段。若目标之间并不冲突（都单调受益于同一个中间量），多任务带来的只有参数量；若冲突且不相关，门控会退化成路由、增益归零。判定方法是看各任务的最优排序是否真的互相拉扯——两个任务的最优排序高度一致时，把它们做成多任务没有机制收益。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
推荐系统的总成本 ≈ 召回成本（与候选池规模相关）
                 + 精排成本（送进模型的候选数 × 单条推理成本，随序列长度上升）
                 + 特征与标签成本（随实时性要求与探索量上升）
                 + 维护成本（模型数 × 特征数 × 需登记项）
```

各族的**主导项**与**隐性成本**（这一节按**成本形态**重新分组，与 7.2 的机制分族不是同一套划分——成本函数的形状相同就可以合在一起算）：

- **共现族 / 双塔族**：主导项是索引与近邻检索——存储随「Item 数 × 维度」增长，检索随候选池规模增长而与候选集大小无关。隐性成本是负采样口径与训练数据管线；一次重训会让历史向量作废。
- **交叉与序列族（FM 系列 / DIN / SIM）**：主导项是**精排的推理次数**，即上游送进来多少条候选。隐性成本是序列长度——序列越长，单条推理越贵。这条成本函数是分层漏斗存在的经济理由，也解释了为什么「换更强的精排模型」经常比「把召回候选收窄一档」更贵。
- **多任务族**：在精排同层之上叠加参数量与训练成本；隐性成本是损失权重调参与样本空间处理（SSB）。
- **语义族**：主导项是编码器推理（离线批量建库 + 在线请求各一次）与 LLM 的 token 成本；隐性成本是**换编码器时的全库重编码**——同一件 Item 在不同编码器版本下有两个不可比的向量。
- **生成族**：主导项是逐 token 的自回归解码；它不随候选池扩大而涨，但常数比一次近邻查询大。隐性成本是码本维护，以及重训后历史行为序列与旧 ID 不再可比、训练数据有一次性作废的一段。
- **探索族（Bandit）**：没有模型成本，主导项是探索配额的**机会成本**（按定义要牺牲一部分曝光效率）。

汇总成一张可对照的形态表（不含任何价格，只标「随什么增长」）：

| 族 | 主导成本项 | 随什么增长 | 隐性成本 | 升级时作废什么 |
| --- | --- | --- | --- | --- |
| 共现族 | 相似度计算与存储 | 用户数 × Item 数（相似度矩阵可到平方级） | 离线重算作业 | 相似度表 |
| 双塔族 | 向量索引与近邻检索 | 候选池规模（与候选集大小无关） | 负采样口径与训练管线 | 全库向量 |
| 交叉 / 序列族 | 精排推理 | 送进模型的候选数 × 单条成本（序列越长越贵） | 序列特征挤压在线算力 | 模型与特征口径 |
| 多任务族 | 精排同层 + 参数量 | 任务数 × 专家数 | 损失权重调参与 SSB 处理 | 门控与权重记录 |
| 语义族 | 编码器推理（离线与在线各一次） | Item 数 × 编码器规模 | 换版期间的双索引维护 | 全库向量 |
| 生成族 | 自回归解码 | 生成长度（与候选池规模无关） | 码本维护与重训作业 | 语义 ID 与历史序列的可比性 |
| 探索族 | 探索配额的机会成本 | 探索比例 × 当期曝光价值 | 反事实评估设施 | 无需作废，但需考核约定 |

【推算】向量索引内存：某目录 100 万 Item、向量 128 维、float32 存储——向量本体 = 1e6 × 128 × 4 字节 ≈ **0.5 GB**；HNSW 一类图索引的邻居表，按每向量约 2×M 条边（取常用 M=16 即 32 条）、每条边一个 4 字节 ID、再乘 1.5 的层间冗余 ≈ **192 字节/向量**（这是按公开索引结构的量级估算，不是任何产品的实测参数，实际取决于索引参数与实现）——合计 ≈ **0.7 GB** 常驻内存。结论：这一量级单机可承载，**这条路线的成本瓶颈不在存储，而在「重训后全库向量作废」**。

【推算】分层漏斗的延迟量级：若把精排直接放到 100 万候选上，单条推理即使按 0.1 ms 计，单次请求需 1e6 × 0.1 ms = **100 秒**；把候选先收窄到 1000 条，同样单条成本下是 1000 × 0.1 ms = **0.1 秒**。两档差三个数量级。（0.1 ms 是用于标定量级关系的假设值，不是任何产品的实测值——它说明的是「候选数每降一个数量级，精排延迟降一个数量级」这条线性关系。）

【推算】换编码器的一次性成本：某目录 100 万 Item 要全库重编码。若重编码能力按每秒数十到数百条的量级【经验】估，1e6 条即约 2 × 10³–2 × 10⁴ 秒，合 **0.5–6 小时**的纯计算时间；但真正的代价不在这个时长，而在**迁移窗口内新旧向量不可混用**——混用会让近邻检索在两个不同的向量空间里比较，结果不可比。所以要么双写双索引（存储与索引成本按约 2 倍计），要么在窗口内接受召回质量下降，没有第三种便宜办法。这也解释了为什么生成族的码本重训与语义族的编码器换版，本质上都是同一类「一次性作废 + 双份维护」的成本。

把这张表并排看能得出一条通用结论：**只有召回层的成本与候选集大小无关**，所以架构上最划算的方向永远是「把候选收窄一档」，而不是「把模型换大一号」；而唯一能压低召回层常数成本的办法是换候选的产生方式——生成式的解码不随候选池规模增长，但它的常数比一次近邻查询大。这两句话是 7.5 里所有与成本有关节点的依据来源。

读这张成本表的方法，是对每个候选问三个问题：**它的成本随什么增长**（候选池规模 / 送进模型的候选数 / 序列长度 / 目录变更频率 / 实时性强度）、**哪一项是隐性成本**（不进预算表、由别处承担）、**一次升级会让什么作废**（向量、序列、码本、历史特征）。第三个问题最容易被漏掉，却在实际项目里造成最多返工。

### 7.5 决策树（每个分支都要有阈值依据）

```text
① [可用的行为共现有多少？]
   ├─ 稀疏（新平台 / 新业务域，交互量在起步量级）→ 内容 / 多模态向量召回 + 冷启动旁路 + 探索配额
   │        不要先上 DIN / Transformer
   └─ 有量 →
        ② [单次请求延迟预算是多少？]
           ├─ 200ms 以内 → 必须分层漏斗：召回 → 粗排 → 精排 → 重排
           │      └─ ③ [精排候选数能否收窄到千级？]
           │           ├─ 能 → 精排用交叉 / 序列模型（FM / DeepFM → DIN / SIM）
           │           └─ 不能 → 先修漏斗，不要换模型
           └─ 远大于 200ms（离线 / 近线场景）→ 可以牺牲漏斗层数换表达力
        ④ [要同时优化几个目标？]
           ├─ ≥2（CTR + CVR / GMV / 时长）→ MMoE / PLE；CVR 有样本选择偏差时用 ESSM
           └─ 1 个 → 单目标精排 + 重排规则
        ⑤ [行为序列长度量级？]
           ├─ 数十～数百条 → DIN / DIEN
           ├─ 数百～数千条 → SIM（只挑相关片段）
           └─ 更短 → 统计特征 + FM / DeepFM 足够
        ⑥ [需要「为什么推这个」吗？]
           ├─ 需要（展示层需求）→ LLM 理由生成，不参与排序
           └─ 不需要 / 是排序需求 → 精排输出直接进重排
        ⑦ [零交互 Item 占比高且内容侧有多模态吗？]
           ├─ 是 → 多模态编码 + 向量召回（先做自有 Golden Set 对照）
           └─ 否 → 单模态
        ⑧ [目录变更频率 vs 码本重建周期，哪个更快？]
           ├─ 码本重建能跟上目录变更 → 生成式召回可试点
           └─ 目录日更、码本重建跟不上 → 先不上，改用双塔 + 语义通道
```

**阈值依据**（与树上 ①–⑧ 一一对应）：

- **① 共现是否「有量」**：依据是「有效样本数必须撑得起参数量」这一统计约束，不是成本函数。本主题下的常见分界是十万级用户 / 万级 Item 的起步量级【经验】（[§3 §3.5](05-recommendation-section-3-sec3.md) 的反模式表：「一开始就用深度学习」的症状是十万用户 / 万级 Item 直接上 DIN / Transformer，后果是参数远多于有效样本、验证集波动大、线上不稳）。
- **② 200ms 延迟预算**：来自在线推荐 P99 通常被压在几十到几百毫秒量级这一工程惯例【经验】（[§3 §3.1](05-recommendation-section-3-sec3.md)）。取 200ms 作为「分层漏斗是必需项」的分界——它不是某个产品的限制，而是「用户划走之前必须返回」这条业务约束的量化形式。
- **③ 精排候选数收窄到千级**：来自 7.4 的【推算】算例（100 万候选 × 0.1 ms ≈ 100 秒 vs 1000 候选 ≈ 0.1 秒，差三个数量级）。判定动作是数一下精排实际收到的候选数，而不是看它离线 AUC 有多高。
- **④ 目标数 ≥ 2**：来自「目标多元」这条约束（[§3 §3.1](05-recommendation-section-3-sec3.md)）——能即时测量的只有点击，只优化可测量目标会损害不可测量目标。阈值定在 2，是因为单目标下多任务的机制收益（专家共享）没有可解的冲突。
- **⑤ 序列长度分档**：树上「数十～数百条 → DIN / DIEN、数百～数千条 → SIM」这一细分**是本文件补的**——[§3 §3.3](05-recommendation-section-3-sec3.md) 的模式选择决策表把「长序列行为（数百条）+ 算力足」列为对 DIN / DIEN / SIM 的**并列**档位，并未在三者之间再分档；本节按 7.4 的成本函数（序列越长单条精排推理越贵，而 SIM 只挑相关片段）把 SIM 划到更长的量级。分档的依据因此同时是「表达力够不够」与「预算够不够」。
- **⑥ 「需要解释」是展示层需求还是排序需求**：分界来自一处接口差异——理由生成不参与排序，所以它可以在不触碰效果指标的前提下独立上线与回滚；若需求实为「用解释改变顺序」，那它就落回精排层，不适用本节点。
- **⑦ 零交互 Item 占比高且内容侧有多模态**：这里不给百分比阈值，理由是多模态增益必须自测——编码器侧是成熟的（图文对齐自 ICML 2021 起有公开工作），但从「能编码」到「在你自己的目录上涨」隔着一次必须做的对照。判定动作是：用自有 Golden Set 比较「多模态通道 vs 单模态」在同一批零交互 Item 上的表现，通过才加预算。
- **⑧ 码本重建周期 vs 目录变更频率**：来自生成式的失效机制（[§3 §3.2.7](05-recommendation-section-3-sec3.md)）——「共享前缀」的前提是码本稳定，码本漂移后前缀不再代表语义。判定方法是先量出自己的码本重建周期，再与目录变更频率比；这个阈值不用数字表达，因为它取决于你的量化训练成本与目录更新节奏。

**怎么用这棵树**：从①往下逐节点走，每到一个节点**先取数、再判断**——取不到数的节点说明你的平台还没有把这件事度量出来，这时选哪个方案都不重要，先把度量补上。树上最常被跳过的是③，而它恰好是唯一一个能用「数一下精排实际收到多少条候选」当场验证的节点。

还要注意树上**没有**「换更强的模型」这个节点——它不是一个判断，而是一个不改变任何约束的动作：模型换强之后，延迟预算不变、反馈闭环不变、级联性质不变。它只能在③判定为「精排候选数已收窄」之后作为同层内的优化存在。把「换模型」写成决策树的一个分支，是把资源问题误当成技术问题。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 十万级用户 + 万级 Item（起步期） | ItemCF / FM-DeepFM 起步 | 双塔（Item 数继续增长后） | 不上 DIN / Transformer：有效样本养不起参数 |
| Item 千万级 + 延迟 200ms 以内 | 双塔召回 + DeepFM / DIN 精排 | 协同过滤作兜底通道 | 单个强模型全量排序算不完（7.4 的第二个【推算】：100 万候选 ≈ 100 秒 vs 1000 候选 ≈ 0.1 秒） |
| 新 Item 占比高 + 内容侧可用 | 内容 / 多模态向量召回 + 探索配额 | 语义 Embedding 并列通道 | 纯 ID 模型对零交互 Item 拿不到梯度信号（7.3.1） |
| 多目标（CTR + CVR + GMV） | MMoE / PLE | ESSM（CVR 有样本选择偏差时） | 单目标人工加权的权重不可解释且反复漂移（7.3.4） |
| 长序列（数百条以上） | SIM | DIN / DIEN | 只用统计特征会丢掉兴趣演化，而序列越长单条推理越贵（7.4） |
| 长尾分布明显 + 行为稀疏 | 双塔召回 + MMoE | 单塔 + 单目标 | 单塔容量被头部 Item 占满，长尾样本养不起独立参数 |
| 强上下文（新闻 / 短视频） | SASRec / BERT4Rec 类序列模型 | 流特征 + 近线更新 | 静态画像的更新慢于上下文变化 |
| 知识密集（医疗 / 教育） | 知识图谱 + KGAT 类图模型 | LightGCN | 纯协同在共现稀疏时没有信号（7.3.1） |
| 需要可解释 / 对话式 | LLM 理由生成（展示层） | ChatRec 类对话式 | 把 LLM 放主排序：token 成本与端到端延迟比向量检索高出若干数量级【经验】 |
| 目录相对稳定 + 有专职平台团队 | 生成式召回（试点） | 双塔 + 语义通道 | 目录日更时码本跟不上，前缀不再代表语义（7.3.1 失效条件） |
| 需要探索未知兴趣 | Bandit 配额 | 序列决策建模 | 纯利用会被流行度偏置锁死（7.3.3） |
| 跨机构 / 数据不出域 | 联邦推荐（先解决 ID 对齐） | 集中训练（不合规时不适用） | 各方实体不重叠时聚合的是互不相干的目标 |
| 有 LLM 与商品库的助手场景 | 三段式：LLM 提意图 → 真实库存检索 → LLM 解释 | — | 自由文本生成会输出目录里不存在的 Item（7.3.1） |

**常见组合**（每条给出职责边界与运维代价；组合的名字沿用既有做法，边界是本章补的）：

1. **双塔召回 + DIN 精排（工业默认）**。职责边界：双塔只负责「别漏」，主动放弃交叉特征换可扩展；DIN 在千级候选上负责顺序。运维代价：两套模型、两套特征、两套监控；召回与精排若用不同负采样口径，会出现「召回排名与精排排名系统性错位」，需要定期做一致性校验。
2. **MMoE + DIN（多任务 + 兴趣）**。职责边界：MMoE 在一次请求内平衡多目标，DIN 处理用户兴趣；两者都在精排层，不改变召回。运维代价：在组合 1 之上叠加损失权重调参，且权重变更通常不进登记（7.3.4 的失效条件）。
3. **LLM Embedding + 双塔（语义推荐）**。职责边界：LLM 编码器提供内容侧向量作为**并列召回通道**，双塔保留 ID 通道；两者并行而非互相替代。运维代价：多一层编码器版本依赖——离线批量编码与在线编码必须同属一个版本，否则同一件 Item 会有两个向量。
4. **生成式推荐 + 排序推荐（混合）**。职责边界：生成负责候选的产生方式，排序仍负责多目标、多样性与频控——这些要求写在集合层，不写在 ID 序列里。运维代价：码本维护 + 自回归解码延迟落在本来最便宜的召回层，是本章运维面最大的一种组合，建议只在有专职平台团队时采用。
5. **Bandit + 精排（探索-利用）**。职责边界：Bandit 分配探索曝光，精排保主流量；探索的目标是**产生标签**，不是提升当期点击。运维代价：需要反事实评估设施，以及一条写进考核的探索预算——后者是组织成本而非技术成本。
6. **协同过滤 + 内容推荐（冷启动）**。职责边界：行为少时用内容 Embedding 回答「像谁」，行为积累起来后交回协同通道；两者的切换判据是共现是否为零，而不是一个固定比例。运维代价：内容通道的效果必须能被单独度量，否则它只在最难的样本上出现，永远拿不到加预算的依据。

7. **流特征 + 近线更新 + 重精排（实时推荐）**。职责边界：流链路负责分钟级兴趣（行为发生到特征可用），近线更新负责让模型跟上，重精排负责表达力；三者的边界是「谁在什么时延内可见」。运维代价：批与流两套实现、两套测试，口径对齐是持续性成本；实时特征**不可回填**，出问题只能堵不能补。

这七条里只有两条跨了召回与精排（1、4）；组合 3 的两条通道（双塔 ID 通道与 LLM 编码器的内容通道）都在召回层——它跨的是**信号族**（行为共现与内容语义），不是漏斗层，因此要监控的是两侧编码器版本是否一致（组合 3 的运维代价），而不是召回与精排的排名错位；组合 5 跨的是重排与精排的分工，但两层消费的是同一批候选，同样不涉及召回与精排的级联错位；其余三条（2、6、7）不跨这条级联，可以独立上线与独立回滚。跨层的组合（1、4）要把「召回排名与精排排名系统性错位」当成一个长期监控项——两边若用不同的负采样口径，错位会稳定存在且不会报警。判断一个组合是否真的落地，看三样东西有没有登记：召回侧用的编码器版本、精排侧的特征口径、曝光日志里的策略版本。三样都没有，这个组合就还停在架构图上。

### 7.7 选错的代价与迁移成本

- **反模式：把强模型放在最贵的位置** —— 症状：有效样本只有十万级用户就上 DIN / Transformer，离线 AUC 确实更高；在线延迟超预算后被迫把强模型只跑在 Top-N 候选上。→ 后果：等于自己手搓了一个退化版漏斗，而两套模型、两套特征、两套监控的成本已经付了；真正的损失不是「不准」，而是**把延迟预算花在了最不该花的位置上**。→ 正确做法：先上双塔 + FM / DeepFM，等交互量与算力同时到位再换重精排（机制依据：7.3.2 的级联不可逆 + 7.4 的精排成本函数）。
- **反模式：把离线指标当上线依据** —— 症状：每一次离线模型迭代都在线无收益，团队逐渐失去对离线指标的信任，进而放弃迭代。→ 后果：迭代节奏停滞，而问题不在模型而在评估——离线样本由旧策略筛选，训练分布与线上暴露分布不一致。→ 正确做法：固定一份 Golden Set、在曝光日志里记下当时的策略版本、用 A/B 做验收（机制依据：7.3.3 的反馈闭环）。
- **反模式：内容通道当兜底规则而不是并列通道** —— 症状：内容向量只在 ID 通道召回到空时才被调用。→ 后果：冷启动拿到的是近乎随机的曝光，而且内容通道只在最难的样本上出现，它的效果无法被单独度量，永远得不到加预算的机会。→ 正确做法：并列接入主链路、按配额或加权合并，并用「新增 Item 曝光占比」这一项指标单独观察它（机制依据：7.3.1 的信号来源差异）。

这三条的共同结构是：**把「某一层的成本降了」误当成「整条链路可以少一层」**。判断一个选型决定是否成立，看它有没有同时给出自己新增的成本项——只讲收益的方案，成本一定落在别处（延迟、重编码窗口、运维面或考核周期），而它通常在事故之后才被发现。

**换成另一个要动什么**（工作量量级为【经验】档，只给区间不给精确值）：

| 迁移 | 数据迁移 | 服务 / 接口改写 | 运维重建 | 团队再学习 | 量级 |
| --- | --- | --- | --- | --- | --- |
| 协同过滤 → 双塔 | 共现相似度表 → 向量索引 | 召回接口从「查相似表」改「近邻检索」 | 新增向量索引与编码服务 | 负采样与向量检索调参 | 中，数月量级 |
| 双塔召回 → 生成式召回 | Item → 语义 ID 码本（一次量化训练） | 召回从近邻查询改受限解码 | 新增码本维护与重训流程 | 序列建模与受限解码 | 大，需专职平台团队 |
| 单目标精排 → 多任务 | 标签与样本空间对齐（CVR 只在点击样本上有标签） | 输出从单分改为多分（或乘法结构） | 门控与损失权重调参流程 | 多任务训练与 SSB 处理 | 中 |
| 离线特征 → 流特征 | **实时特征不可回填**，历史只能从上线日起累积 | 特征服务改为在线拼接 | 新增流作业 + 批流口径对齐测试 | 口径纪律（同名特征唯一一份定义） | 大 |
| 集中训练 → 联邦 | 需要 PSI / 公共 ID 体系做实体对齐 | 训练改为多轮聚合 | 通信与聚合设施 | 隐私与安全聚合 | 大 |
| 内容通道作兜底 → 内容通道并列 | 无需迁移既有向量 | 合并逻辑从「兜底分支」改「配额 / 加权」 | 新增内容通道的独立监控 | 内容侧质量治理（标题 / 类目） | 小到中 |
| 无版本登记 → 全链路版本登记 | 补登历史编码器版本（确定可比性的起点） | 无 | 发布流程加必填字段 | 无新增技能，需跨团队约定 | 小，但依赖约定 |
| 离线评估 → 在线 A/B + 反事实评估 | 需要曝光日志（含策略版本），只能从开启日起积累 | 无 | 新增实验平台与流量分配校验 | 反事实估计方法（IPS 一类） | 中 |
| 无探索 → 有探索配额 | 无需数据迁移 | 重排或旁路加策略分配 | 反事实评估设施 | **组织成本**：探索预算写进考核 | 技术小、组织大 |

### 7.8 小结

把本章压成一句话：**先确定候选从哪来，再确定它落在漏斗的哪一层，最后才是模型选择**。下面按处境给出落点。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 交互数据在起步量级 | ItemCF / FM-DeepFM 起步，先别上深度序列模型 | 有效样本撑不起参数量时，收益是离线幻觉、成本是线上不稳 |
| Item 千万级、延迟紧 | 双塔召回 + 轻精排 + 重排规则 | 内积独立编码把候选池规模移出在线算力；级联不可逆，召回决定上限 |
| 冷启动塌陷 | 内容 / 多模态向量作为**并列**通道 + 探索配额 | 共现为零时只有非共现信号可用；标签只能由探索产生 |
| 多目标互相打架 | MMoE / PLE；CVR 有 SSB 用 ESSM | 收益来自专家被共用；CVR 的无偏梯度来自曝光全空间的乘法结构 |
| 想用 LLM 提效果 | LLM 只挂意图解析与理由生成两处接口 | 理由生成不参与排序，可独立上线与回滚；主排序的推理次数等于候选数 |
| 目录日更、想上生成式 | 先量码本重建周期与解码延迟，再决定 | 「共享前缀」的前提是码本稳定，目录日更会先把这条前提打掉 |
| 有 LLM、但精排本来就正常 | 不换排序，先补 Golden Set 与版本登记 | 判断依据来自「可比性」，不来自模型的强弱 |

> 本节小结：本章所有候选的差异，最终都能归到两问——**候选从哪来**（共现 / 语义 / 序列）与**它落在漏斗的哪一层**。这两问之外，延迟预算与反馈闭环一寸未动：延迟预算决定了精排能看多少条候选（7.4 的三个数量级），反馈闭环决定了标签从哪来、探索是否必需（7.3.3）。打分表之所以误导，正是因为它把这两条不变的约束与「能力」混在同一列里比较。选型的第一动作不是挑模型，而是先去数三个数：精排实际收到多少条候选、延迟预算剩下多少、新增 Item 的曝光占比是多少。
