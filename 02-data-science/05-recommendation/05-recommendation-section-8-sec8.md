### Q1：推荐系统为什么要分层（召回 - 粗排 - 精排 - 重排）？每层的职责、候选规模、典型模型、延迟预算如何匹配？

**题型**：架构设计题（必考，难度 ★★★★☆）

**考察点**：候选规模递减 → 模型精度递增 → 算力成本递减的「漏斗模型」理解，以及对每层职责边界的把握。

#### 1. 概念定位
推荐系统的根本矛盾是 **亿级候选 vs 毫秒级延迟**。分层漏斗的本质是「精度 ↔ 算力」的分级交易：召回层用轻量模型把全量 1 亿 Item 缩到千级（召回率优先），粗排层用中型模型缩到百级（精度换速度），精排层用重型模型缩到十级（精度优先），重排层引入多样性与业务规则完成最终决定。从业务过程建模的视角看，每一次曝光 - 点击 - 转化都是一个 `recommendation.impressed` / `recommendation.clicked` / `recommendation.converted` 事件，漏斗只是把"在何时生成候选"这件事按计算代价切成四段。

#### 2. 核心原理
- **召回 Recall**：从亿级到千级，典型模型是 **双塔（Two-Tower）/ YouTube DNN / ItemCF / Swing / 多兴趣 MIND**，目标 Recall@1000 ≥ 95%。  
- **粗排 Pre-Ranking**：从千级到百级，典型模型是 **轻量 DeepFM / COLD / LR**，要求 P99 ≤ 10 ms。  
- **精排 Ranking**：从百级到十级，典型模型是 **DeepFM / DIN / DIEN / SIM / DCN-V2 / ESSM**，要求 P99 ≤ 40 ms。  
- **重排 Re-Ranking**：从十级到最终展示（通常 6-20 条），典型做法是 **MMR（Maximal Marginal Relevance）/ DPP / Listwise / 业务规则引擎**。  

候选规模逐层递减：召回层约 10⁵×（亿级 → 千级），粗排、精排各约 10×（千级 → 百级 → 十级）；每层模型容量、特征维度、延迟预算严格匹配。

#### 3. 工程实现
- **服务编排**：召回 → 粗排 → 精排 → 重排通常以 **gRPC / Thrift** 串联，每层独立部署、独立扩缩容；召回层常驻向量检索服务（Faiss / Milvus），粗排精排用 TF-Serving / Triton 推理，重排用规则引擎 + 轻量 DNN。  
- **延迟分配**：召回 20 ms + 粗排 10 ms + 精排 40 ms + 重排 5 ms + 业务规则 5 ms ≈ P99 80 ms。  
- **多路召回**：双塔（语义）+ ItemCF（行为）+ 热门（统计）+ Bandit（探索）四路并发，再做合并去重。  
- **回流闭环**：精排结果回流到推荐事实表（`recommendation_log`），下次训练做负样本与偏差修正。

#### 4. 行业实践
- **YouTube（Google）** 经典 DNN 双塔召回 + 精排两层。  
- **阿里淘宝** 是 **双塔 + DIN + 多任务精排 + 业务重排** 的四段式模板。  
- **字节抖音** 是 **双塔 / SIM 长序列 + MMoE 多任务精排**，日均时长有可观测提升（方向性表述，【经验】档：幅度依内容形态与用户结构而异）。  
- **京东 JDRec** 是 **DeepFM + 多路召回 + 规则重排**。  
- **美团** 到店 + 外卖用 **双塔 + DIN + 多样性重排**。  
- **Netflix** 的推荐链路是 **序列召回 + 个性化海报精排**。序列召回所用的具体模型本节无出处；学术界的代表方法是 **BERT4Rec**（Sun et al., 2019，双向 Transformer 序列推荐），Netflix 线上是否采用该方法本节无法核验，不作等同。

#### 5. 落地陷阱
- **层级越界**：粗排层引入重型 DIN（延迟爆炸）或召回层做了交叉特征（推理代价不可接受）。  
- **缺少重排**：精排 CTR 高但全页同质，信息茧房，次日留存下降。  
- **回流断裂**：精排结果没有回流到训练样本，模型迭代慢、效果停滞。  
- **延迟分配失衡**：精排给 100 ms 留给召回 5 ms，看起来快但召回率跌穿 90%。  
- **多路召回打架**：各路候选无去重策略，热门 Item 霸榜。

#### 6. 追问预测

- **「分层漏斗的层数是不是越多越好？」** 答：不是。每多一层就多一套模型、特征与监控口径，也多一次级联取舍；是否值得独立成层，判据是「这一层的候选规模 × 该层单条推理成本」相对总预算是否还划算。国内电商普遍采用「召回—粗排—精排—重排」四层属工程惯例【经验】，候选集不大时两层（召回 + 排序）反而更省——机制见 [§3 §3.2.1](05-recommendation-section-3-sec3.md)。
- **「召回率目标凭什么定在 95% 左右？为什么不设成 100%？」** 答：这是【经验】档的量级，不是标准值。定它的依据是级联不可逆——没进候选集的 Item 后面任何一层都救不回来，所以召回决定效果上限；但把目标推到 100% 意味着不设上限地放大候选集。【推算】候选数每翻一倍，精排单次推理次数翻一倍，延迟与算力近似线性增长——上限是被延迟预算卡住的，不是被理想值卡住的。
- **「延迟预算怎么分配？」** 答：按端到端可接受的总 P99 倒推：先扣掉网络传输与业务规则的开销，剩下的按各层算力消耗切，越贵的层给越小的候选集，而不是层间均分。本节正文给出的是一组示例分配（召回 / 粗排 / 精排 / 重排 / 业务规则各级别，【经验】档，非实测值），读者应按自己集群的算子实测延迟替换参数重算。
- **「上线后延迟忽高忽低，怎么定位到层？」** 答：按层埋 P50 / P99 分位，并让每层带上同一个请求 ID，先区分是整体抬升还是长尾抬升；再对每层的「入参候选数」做监控——候选数被上游放大（某一路召回超时后返回全量兜底）是常见的隐性原因，它不会写在任何一层的代码里。
- **「重排为什么不全用模型？」** 答：重排要解的是集合级目标（多样性、频控、业务硬约束），逐条打分的精排表达不了「两条都不错但放在一起不好」——这是重排必须独立存在的理由（[§4 §4.2](05-recommendation-section-4-sec4.md) 给了这条机制）。用 MMR / DPP 一类边际增益最大化的做法即可，不必换成模型，但规则必须显式化、可审计。

### Q2：双塔模型（Two-Tower）与 DeepFM 在召回 vs 精排定位上的本质差异是什么？为什么不能互换？

**题型**：模型机制对比题（高频，难度 ★★★★☆）

**考察点**：双塔"结构解耦 → 向量检索"的核心架构优势，与 DeepFM"特征交叉 → 精确打分"的目标冲突，进而理解召回与精排在训练 / 推理范式上的根本差异。

#### 1. 概念定位
双塔的本质是 **用户与物品独立建模 → 双方 Embedding 内积 → 向量检索 top-K**；DeepFM 的本质是 **FM 捕捉二阶交叉 + DNN 捕捉高阶非线性 → 单点打分**。前者面向 **检索范式（retrieval）**，后者面向 **打分范式（scoring）**。从业务过程的角度看，召回对应"把候选带进来"的事件语义（粗粒度），精排对应"决定展示顺序"的事件语义（细粒度），两者对实时性、特征丰富度、模型容量的要求完全不同。

#### 2. 核心原理
- **双塔模型**  
  用户塔 $u = f_u(x_u)$，物品塔 $v = f_v(x_v)$，相似度 $\hat y = \cos(u, v)$。训练用 softmax over negatives；推理时把物品 Embedding 离线预计算 + 索引到 Faiss / Milvus，线上只算用户 Embedding 然后做 ANN 检索。**关键限制**：用户与物品的特征交互必须发生在塔内，两塔之间只能通过最后的内积交互，因此 **无法建模"用户 - 物品"交叉特征**（如用户 - 物品类目共现）。

- **DeepFM**  
  $\hat y = \mathrm{FM}(x) + \mathrm{DNN}(x)$，FM 部分自动学习两两特征的内积交叉，DNN 部分学习高阶非线性。任意特征交互都可以在 forward 阶段就计算好，适合做 **点对点的精确打分**。但因为要把所有候选都过一遍完整模型，所以 **推理代价不可承受于亿级候选**。

#### 3. 工程实现
- **双塔召回**：用户特征（人口学 + 行为统计 + 上下文） → 用户塔 MLP → 64 维向量；物品特征（类目 + 品牌 + 文本 + 图像） → 物品塔 MLP → 64 维向量；离线把亿级物品 Embedding 索引到 Faiss IVFFlat / HNSW，线上一查 top-1000。  
- **DeepFM 精排**：把用户 - 物品 - 上下文 - 交叉特征全部 concat 喂入 FM + DNN，输出 0-1 之间的 CTR 预测。  
- **不可互换原因**：  
  - 把 DeepFM 做召回 = 亿次 DNN 推理，QPS 撑不住。  
  - 把双塔做精排 = 候选 Item 与用户没有交叉特征，用户性别 × 母婴类目的强信号学不到。

#### 4. 行业实践
- **YouTube（Google）** 召回层用 DNN 双塔（用户的 watch history + 人口学），精排层用 Wide & Deep / DeepFM。  
- **Meta DLRM** 是经典的"召回 + 精排"双塔 → 交叉网络范式。  
- **阿里 DIN** 精排侧把双塔做不到的用户 - 历史注意力补回来。  
- **Pinterest PinSage** 是图卷积版双塔，召回用 PinSage Embedding；重排侧只作方向性表述——图卷积结构可以延伸到重排，其学术代表方法是 **LightGCN**（He et al., SIGIR 2020）；Pinterest 生产系统是否采用该方法本节无法核验，不作等同。  
- **Amazon Item-to-Item** 是经典工业级双塔：用户表 → 物品 → 同类物品（i2i），召回极简但精排靠业务规则 + 业务经验。

#### 5. 落地陷阱
- **双塔冷启动塌陷**：新物品没有行为就没法训练物品塔，必须用内容 Embedding（BERT / CLIP）兜底。  
- **DeepFM 召回率塌陷**：把 DeepFM 当成"精排兜底"会导致精排候选全是热门 Item，召回层被穿透。  
- **负采样偏差**：双塔训练用 in-batch negative，热门物品作为负样本被过度打压。  
- **向量漂移**：用户塔与物品塔分别更新，导致 user-item 分布错位，需要周期性联合校准。

#### 6. 追问预测

- **「双塔能不能加特征交叉？」** 答：塔内可以自由加（用户塔内部对历史行为做自注意力、物品塔内部做属性交叉），塔间不行——两塔只在最后的内积处交互，所以「用户 × 物品」的显式交叉在结构上无法表达。这是双塔为可检索性付出的代价，补偿责任转移到精排；而精排永远看不到没被召回的 Item，所以这部分损失不可逆（机制见 [§3 §3.2.1](05-recommendation-section-3-sec3.md) 的失效点）。
- **「内积和余弦可以随便挑一个吗？」** 答：不可以。余弦把向量归一化到单位球面、丢掉模长，内积保留模长；模长在训练中会吸收热门程度一类信号，两者的打分尺度不同。要求是「训练时的相似度定义」与「索引里的距离算子」同源——离线按一种算子建索引、线上按另一种打分，是召回效果莫名下降的常见根因。
- **「负采样怎么定？」** 答：in-batch negative 的工程成本最低，但会把同一批内的热门物品当作负样本，产生流行度偏置；缓解办法是按热度做采样概率校正（把「物品被抽为负样本的概率」从打分或样本权重里折掉），或降低热门物品被采为负样本的概率。具体的负正比与校正强度按各站点的热度分布标定，本节不给出统一值【经验】。
- **「召回结果里全是热门物品，怎么查？」** 答：先看负采样与样本权重，再看物品向量的模长分布——若热门物品的模长显著偏大，就是内积口径下的热度放大。判据很直接：把打分换成余弦重跑一遍，热门占比是否回落；回落说明问题出在打分口径，不在模型本身。
- **「塔间能不能换掉内积、用更强的交互结构？」** 答：可以，但必须满足「物品向量不与用户侧特征耦合」这个前提，否则物品向量无法离线预计算，检索会退化成逐条打分，双塔的工程优势随之消失。这是双塔成立的条件，不是可调项。
- **「DeepFM 该选带 Field-aware 的版本吗？」** 答：FFM 的参数规模随 field 数呈平方级增长，在 field 多、样本稀疏时训练不稳；工业精排更多用 FM + DNN 结构（DeepFM、DCN 一类）。判据是 field 数量与每个 field 的平均样本量，而不是离线指标的单点高低。

### Q3：DIN / DIEN 为什么用注意力池化（attention pooling）替代 mean / max pooling？如何建模"用户兴趣随时间动态演化"？

**题型**：深度学习机制题（必考，难度 ★★★★★）

**考察点**：DIN 用候选 Item 触发的 Local Activation Unit 计算注意力权重；DIEN 用 GRU + 注意力抽取兴趣演化路径；理解为什么"不同候选需要不同兴趣表达"。

#### 1. 概念定位
DIN（阿里 2018）的核心洞察是 **用户兴趣是 multi-interest 的、且与候选 Item 相关**——给用户推泳衣应激活其历史中的泳衣 / 度假相关行为，推婴儿用品应激活其曾经的母婴浏览。传统的 mean / max pooling 把所有历史行为压缩成一个固定向量，忽略了 **"用户兴趣需要被候选 Item 唤醒"** 这一关键机制。DIEN（阿里 2019）进一步把兴趣表示为时序演化过程，引入 AUGRU（Attention-based GRU）追踪兴趣路径。

#### 2. 核心原理
- **DIN 注意力池化**  
  $$v_U(A) = \sum_{j \in H} a(e_j, e_A) e_j$$  
  其中 $a(\cdot)$ 是 Local Activation Unit，输入为 $[e_j, e_A, e_j - e_A, e_j \odot e_A]$（concat 四元组），输出注意力权重 $w_j$。它 **不归一化到 1**，允许兴趣激活"集中度"自然显现。

- **DIEN 兴趣演化**  
  三层结构：  
  1. **Behavior Layer**：原始行为序列 → Embedding。  
  2. **Interest Extractor Layer**：用 GRU 抽取每一时刻的兴趣状态 $h_t$。  
  3. **Interest Evolving Layer**：用 AUGRU（注意力更新 GRU）结合候选 Item 调节兴趣漂移方向，$\tilde h_t = (1 - \alpha_t) \tilde h_{t-1} + \alpha_t \tilde h_t'$。

- **SIM（Search-based Interest Model）**：长序列兴趣建模的代表，把 1000+ 行为序列通过 GSU（General Search Unit）粗筛到 50-100，再用本地注意力精排。

#### 3. 工程实现
- **LocalActivationUnit**：输入维度 $4 \times \text{embed\_dim}$（concat），MLP 输出 1 个注意力分数。  
- **训练技巧**：DIN 历史序列 padding 到 50-100，DIEN 训练时把兴趣状态序列一起传入 MLP。  
- **在线服务**：DIN 推理需要拉历史行为（Redis / 自研 KV），P99 控制在 30 ms 以内。  
- **长序列优化**：SIM / ETA 把 1000+ 行为压缩到 50-100，再做注意力，降低线上 KV 读取带宽。

#### 4. 行业实践
- **阿里 DIN / DIEN / SIM**：电商用户兴趣建模的标杆。  
- **字节抖音**：长视频 + 短视频混合序列用 DIEN 思想建模。  
- **京东**：DIN 用于"猜你喜欢"，CTR 有可观测提升（【经验】档：幅度依品类与曝光位而异，本节无法给出可溯源的统一数字）。  
- **美团**：DIN 用于外卖商家推荐，订单量有可观测提升（【经验】档：幅度随城市与商家结构而异，本节无法给出可溯源的统一数字）。  
- **Uber Eats**：DIN 变种用于用户 - 餐厅兴趣建模。  
- **快手**：DIN + 长序列视频兴趣建模。

#### 5. 落地陷阱
- **历史拉取代价**：DIN 需要实时拉取用户最近 50-100 行为，KV 命中率与带宽压力大。  
- **冷启动失活**：新用户行为 < 5 条，注意力分布几乎无意义，需降级到双塔或内容推荐。  
- **padding 噪声**：历史行为 padding 太多会让注意力被分散，必须做时间衰减或长度过滤。  
- **兴趣漂移**：兴趣演化要求分钟级更新，单纯离线训练无法捕捉实时变化。  
- **数据偏置**：只看到点击过的 Item，"曝光未点击"语义丢失。

#### 6. 追问预测

- **「DIN 的注意力为什么不归一化到 1？」** 答：因为权重和可以大于 1，模型才能区分「历史里有强相关行为」与「历史里没有强相关行为」两种情况——归一化会把两者压到同一尺度，等于丢掉「兴趣强度」这一维信息。代价是未归一化的分数不能再当概率解释；业务侧要的是排序而不是概率时，这个代价不构成问题。
- **「历史序列长度怎么定？」** 答：训练侧按分位数截断（覆盖大多数用户即可），服务侧按可拉取的 KV 带宽定上限；序列变长收益递减、带宽成本线性上升。具体长度属【经验】档，判据有两个：把长度再加一大截后离线指标是否还有显著变化，以及线上 P99 是否仍在预算内。
- **「DIEN 比 DIN 多出来的收益来自哪里？」** 答：来自兴趣的时序演化——AUGRU 用候选物品调节兴趣漂移方向，等价于把「同一用户在不同时间点对同类物品的偏好强度不同」纳入建模。如果业务里的兴趣本身变化慢（复购周期长、品类窄），这部分收益会相应变小。
- **「千级以上的长序列为什么不用全量注意力？」** 答：精确注意力的代价随序列长度增长，而线上要拉取的 KV 带宽是硬约束；两级结构先用与候选相关的粗筛把长序列压到几十条、再做精确注意力，就是用便宜的检索换掉大部分注意力开销。这是 SIM 的思路，代价是多一次粗筛与一条额外的截断判据。
- **「曝光未点击为什么不进历史序列？」** 答：因为日志通常只记点击，未点击的曝光没有行为记录，序列实际是「点击过什么」而不是「看过什么」，模型学不到「看过但不感兴趣」这个负向信号。留存时长、是否划走这类弱信号可以补一部分，前提是埋点里真的有——这是「数据偏置」这条陷阱的根治办法，而不是模型侧的调参。
- **「注意力权重能直接当推荐理由给业务吗？」** 答：能回答「哪个历史行为被激活了」，但不能当因果解释——权重是当前模型的打分贡献，不是用户心理。业务用它做定性排查（推荐理由是否合理）是合适的，用它做因果归因不是。

#### 7. 参考资料

- DIEN / AUGRU 的原文——本节正文已把 DIEN 记为阿里 2019 年提出；本主题 [§7 §7.2](05-recommendation-section-7-sec7.md) 把 DIN / DIEN / SIM / ETA 列为阿里同一族（Zhou 等，KDD 2018）【公开】，DIEN 单篇的会议名本节无法在离线环境核实，引用前请按方法名自行检索确认。

### Q4：MMoE 多任务学习如何缓解 CTR / CVR / GMV / 时长等多个目标的冲突？专家网络与门控如何设计？

**题型**：多任务架构题（高频，难度 ★★★★☆）

**考察点**：MMoE 用 K 个专家网络 + 每个任务独立门控，让任务共享底层表征但保留独立决策路径；以及 PLE / ESSM 等改进方案的差异。

#### 1. 概念定位
推荐系统的本质是 **多目标优化问题**——CTR（点击）、CVR（转化）、GMV（金额）、时长（停留）、留存（次日活跃）经常相互拉扯。Shared-Bottom 共享底座容易出现任务负迁移（一个任务涨另一个任务跌）。MMoE（Google，KDD 2018）提出 **Multi-gate Mixture-of-Experts**：用 K 个专家网络分别学不同表征，每个任务独立门控决定使用专家的权重，让相关任务共享、不相关任务独立。从业务过程看，CTR 是曝光 - 点击的转化率、CVR 是点击 - 购买的转化率、GMV 是购买事件度量，三个过程度量在同一张用户粒度事实表里天然耦合。

#### 2. 核心原理
- **Shared-Bottom**：所有任务共享一个 MLP 顶层 → 任务负迁移。  
- **MMoE**：  
  $$y_k = h_k \left( \sum_{i=1}^{K} g_i^{(k)}(x) \cdot f_i(x) \right)$$  
  - $f_i$ 是 K 个专家网络，每个独立 MLP。  
  - $g_i^{(k)}$ 是任务 k 的门控，softmax(K) 输出专家权重。  
  - $h_k$ 是任务塔（task tower），各自独立。  
- **PLE（Progressive Layered Extraction）**：分层多任务，下层专家有"任务专属 + 任务共享"两类，避免任务负迁移。  
- **ESSM（Entire Space Multi-task Model）**：解决 CVR 样本稀疏问题——用 CTCVR（全空间转化）作为主任务，CVR 拆成 CTCVR / CTR。  
- **AITM（Adaptive Information Transfer Multi-task）**：自适应信息迁移，让任务间按需共享信息。

#### 3. 工程实现
- **专家数量**：通常 K = 4-8，过少退化为 Shared-Bottom，过多训练不稳定。  
- **任务权重**：CTR : CVR : GMV 的权重配比没有普适值，需按业务优先级与各任务样本量设定（【经验】档：本节无法给出可溯源的统一比例，任何具体比例都应结合自身数据标定）；权重过小导致任务训练不充分。  
- **Loss 融合**：$\mathcal L = \sum_k w_k \mathcal L_k + \lambda \mathcal L_{\text{share}}$，或用 Uncertainty Weighting 自动调权。  
- **工程接口**：每个任务有自己的 AUC / GAUC 监控、独立训练 - early stop，但底层特征 + 专家共享。

#### 4. 行业实践
- **Google MMoE**：YouTube 视频推荐多任务（点击 + 完播 + 分享）。  
- **阿里 ESSM**：淘宝电商 GMV 推荐，CVR 样本稀疏问题缓解（方向性表述，【经验】档：缓解幅度随场景与样本分布而异）。  
- **PLE（Tang et al., RecSys 2020，腾讯）**：腾讯提出的分层多任务方案，MMoE 之后的代表性改进。  
- **字节 ByteRec**：信息流多任务（CTR + 点赞 + 评论 + 完播）。  
- **美团**：外卖推荐多任务（点击 + 下单 + 复购）。  
- **平安保险**：产品推荐多任务（CTR + 留资 + 投保）。

#### 5. 落地陷阱
- **任务负迁移**：专家数过少（K 趋近 1）时 MoE 结构会退化为 Shared-Bottom，负迁移重新出现 → 工程上 K 通常取 4 以上。注意：MMoE 与 OMoE 的差别在门控设计（每任务独立门控 vs 全局共享门控）而非 K 的取值。  
- **CVR 样本选择偏差**：点击 - 转化的样本与全空间分布不同，ESSM 必须做全空间建模。  
- **Pareto 前沿**：多任务优化本质上求 Pareto 最优，不可同时涨所有指标，需业务确定优先级。  
- **任务权重僵化**：固定权重不适应季节性 / 活动期，需动态调整。  
- **门控坍缩**：所有任务门控都选同一专家 → 退化为 Shared-Bottom，需加门控熵正则。

#### 6. 追问预测

- **「MMoE 与 Shared-Bottom 的差别是结构还是参数量？」** 答：差别在门控。MMoE 每个任务有独立门控，可以按需取不同专家；Shared-Bottom 只有一个共享底座，任务间的梯度冲突无处隔离。参数量增加是副产品而不是原因——判据是把门控换成全局共享（OMoE）后效果是否回落，回落才说明门控的独立性在起作用。
- **「专家数 K 怎么定？」** 答：K 通常落在个位数【经验】。太少会退化成共享底座，太多会让每个专家分到的有效样本变少、训练不稳；可先按「任务数的一到两倍」起手，再按验证集上各任务的指标调。具体取值必须按样本量标定，没有普适值。
- **「门控坍缩怎么判、怎么修？」** 答：监控门控输出的熵或各专家被选中的占比——熵持续走低说明所有任务在抢同一批专家。修法是给门控加熵正则，或按任务分层（PLE 的思路：把专家分成任务专属与任务共享两类）。
- **「任务权重怎么设？」** 答：没有普适比例【经验】。可以用 Uncertainty Weighting 一类做法自动调权，也可以按业务优先级设初值、再按各任务样本量折算；关键是把权重变更纳入版本记录——否则「模型变好」与「权重变了」这两件事无法区分，评审时说不清收益来自结构还是超参。
- **「CVR 的样本选择偏差除了 ESSM 还有什么办法？」** 答：两条路。一条是改结构，用全空间建模把监督信号挪到曝光空间（pCTCVR = pCTR × pCVR，CVR 塔从乘法结构里隐式拿梯度）；另一条是不改结构、用 IPS 一类加权校正单任务 CVR 的分布偏差。取舍是「多一个输出约束」对「加权带来的方差」。
- **「AITM 与 PLE 有什么区别？」** 答：PLE 在层间做专家隔离（任务专属 + 任务共享），AITM 用自适应注意力让任务之间按需迁移信息。两者都是对 MMoE 门控的改造，选型看任务是更需要严格隔离，还是需要在特定两个任务之间做强迁移。

### Q5：推荐系统的「冷启动」有哪些类型？新用户 / 新商品 / 新平台 / 新场景分别如何破局？

**题型**：场景工程题（必考，难度 ★★★★☆）

**考察点**：冷启动四类问题的本质——用户侧的"没有行为"、商品侧的"没有曝光"、平台侧的"全域无样本"、场景侧的"业务事件尚未建模"——各自的工程方案差异。

#### 1. 概念定位
冷启动（Cold Start）是推荐系统最经典的三大长尾挑战之一。从业务过程视角看，冷启动意味着"业务事件样本不足"——曝光 - 点击事件没有形成足以训练模型的样本量。需要根据"缺什么"对症下药。

#### 2. 核心原理（按四类冷启动分述）

| 冷启动类型 | 本质问题 | 核心解法 |
| --- | --- | --- |
| **新用户** | 没有历史行为，无法个性化 | 人口学特征 + 探索（Bandit）+ 内容匹配 |
| **新商品** | 没有曝光 / 点击，无法学 Embedding | 内容 Embedding（BERT / CLIP）+ 流量扶持 + Bandit |
| **新平台** | 全域无样本 | 跨域迁移 + 联邦学习 + 规则兜底 |
| **新场景**（如新功能） | 业务事件尚未建模 | Few-shot Learning + LLM Zero-shot + Prompt 推荐 |

#### 3. 工程实现
- **新用户冷启动**：  
  1. 注册时搜集人口学（年龄 / 性别 / 地域）+ 设备 + 入口来源。  
  2. 用 LinUCB / Thompson Sampling Bandit 做探索，β 越大越探索。  
  3. 利用「最近一次会话的实时行为」做短时个性化。  
- **新商品冷启动**：  
  1. 用 BERT / CLIP 提内容 Embedding，与相似商品做 ItemCF。  
  2. 流量侧「新商品池」保证每天曝光 ≥ 一定次数。  
  3. 用 Contextual Bandit 处理"边探索边利用"。  
- **新平台冷启动**：  
  1. 从外部 / 关联方迁移知识（跨域协同过滤）。  
  2. 用 LLM Embedding 做 Zero-shot 推荐（GPT4Rec / InstructRec）。  
  3. 规则兜底：热门 + 编辑精选。

#### 4. 行业实践
- **Spotify**：新歌冷启动把歌曲内容信号与歌单 / 艺人等协同信号**联合嵌入**做相似歌曲召回（本节无法核验 Spotify 采用的是否即 **EGES（Enhanced Graph Embedding with Side Information）** 这一具体方法；EGES 出自阿里 KDD 2018 论文，与本节引用场景并非同一体系）。  
- **Airbnb**：新房源冷启动用 **Listing Embedding（GraphSAGE 风格）**，用相似地域 / 价格 / 设施做邻居检索。  
- **LinkedIn**：新用户用 **人口学 + 简历 Embedding** 做职位推荐。  
- **Uber Eats**：新餐厅用 **菜品图像（CLIP）+ 类目 + 地理** 做菜品推荐。  
- **招行（理财）**：新用户用 **风险测评问卷 + 人口学** 做基金推荐。  
- **平安（保险）**：新用户用 **年龄 + 收入 + 资产等级** 做产品分层推荐。  
- **米哈游**：新角色 / 新活动用 **历史活动相似度 + LLM 推荐** 兜底。  
- **Shein**：新商品用 **图像 + 文本 Embedding** 做"相似商品"推荐。  
- **字节抖音**：新视频用 **多模态 Embedding + 流量池扶持**。

#### 5. 落地陷阱
- **冷启动流量倾倒**：新商品扶持成为"流量垃圾场"，CTR 极低拉低整体指标 → 必须做"扶持配额制"。  
- **Bandit 探索过激**：Thompson Sampling β 设置过大导致用户体验差，立刻流失。  
- **内容 Embedding 语义陷阱**：图像 Embedding 与点击行为分布不对齐，冷启动转化率明显低于正常水平（【经验】档：落差随品类与内容信号强度而异，本节无法给出可溯源的统一数字）。  
- **跨域迁移负迁移**：源域与目标域分布差异大，直接迁移反而拉低效果，需要 Domain Adaptation。  
- **LLM 推荐成本**：每天 1 亿次 LLM 推荐不可行，必须 LLM Embedding 预计算 + 轻量在线。

#### 6. 追问预测

- **「四类冷启动哪一类最难？」** 答：新平台。用户与商品冷启动都还有同站点内其他实体的信号可用（内容向量、人群先验、相似物品的受众），而新平台是全域零样本，只能靠跨域迁移或通用语义先验起步，且迁移本身带负迁移风险。机制见 [§3 §3.2.8](05-recommendation-section-3-sec3.md) 的三路兜底结构：前两路只能回答「像谁」，只有探索配额那一路能产生新标签。
- **「探索配额给多少？」** 答：没有普适比例【经验】。可按「短期指标可承受的下滑幅度」倒推——先定探索组能容忍的指标损耗上限，再换算成曝光占比。更关键的是把配额写进排期与考核：本主题 §3 的自检清单把这一条列为必查项，原因是探索的成本即时发生、收益延后兑现，只看当期考核就会系统性地杀掉探索。
- **「内容 Embedding 做冷启动为什么会失效？」** 答：内容语义与行为共现不同向。在标品、工具类、强价格导向的品类，内容相似会稳定指向「长得像但不该推」的物品。判据是「内容相似召回的候选，其点击表现与随机候选的差距是否稳定显著」——不显著就说明这条信号在该品类不可用，应退回协同信号或人群先验。
- **「为什么 LLM 推荐不能全量上线？」** 答：【推算】每次请求跑一次大模型推理，算力与延迟都随请求量线性增长，按日均请求量级换算的推理成本不可承受；所以通行做法是离线预计算 LLM Embedding + 在线轻量检索，LLM 只用在低频高价值的环节（冷启动期的新品描述解析、长尾查询改写）。这也解释了正文为什么把「LLM 推荐成本」单列成一条陷阱。
- **「新商品扶持会不会变成流量垃圾场？」** 答：会。判据是两个数的比值与趋势——扶持池 CTR 相对大盘 CTR 的比值，以及扶持后有多少新商品拿到了自然分发；如果后者长期接近零，说明流量投出去了却没有产出可用的共现信号，扶持就应改为按内容质量与类目稀缺度分配配额，而不是按上架时间平均撒。
- **「跨域迁移怎么避免负迁移？」** 答：先做分布对齐检查（源域与目标域的物品空间重叠度、共现结构是否同向），重叠度低时优先共享用户侧参数而不是物品侧参数；再做小流量实验而不是直接全量迁移。机制在 [§3 §3.2.10](05-recommendation-section-3-sec3.md)：聚合式协同的收益来自「同一实体在不同方有不同的侧面」，实体不重叠时没有侧面可拼。

### Q6：推荐系统如何做到离线 AUC 与在线 CTR / CVR / 留存等业务指标对齐？实时推荐与反馈闭环怎么设计？

**题型**：评估 / 闭环工程题（高频，难度 ★★★★★）

**考察点**：理解 GAUC / NDCG / Recall@K 离线指标的局限性，掌握在线 A/B 测试、Interleaving、反馈链路、流式特征的关键设计。

#### 1. 概念定位
推荐系统最常见的失败是 **「离线 AUC 0.85，上线 CTR 没动」**——离线指标与业务不对齐。根本原因是：①离线样本有偏差（曝光过的 ≠ 全量候选）；②离线优化目标是 LogLoss / AUC，与 GMV / 时长 / 留存业务目标不一致；③实时反馈链路断。从业务过程看，"曝光 → 点击 → 转化 → 复购 → 流失"构成一条完整的事件链（参考业务过程建模），评估必须覆盖 **业务过程的端到端延迟与质量**，而不是单点 AUC。

#### 2. 核心原理
- **离线指标体系**：  
  - **单点**：AUC / LogLoss / GAUC（分组 AUC，按用户聚合）/ Recall@K / NDCG@K。  
  - **排序**：NDCG / MAP / MRR（适合精排）。  
  - **业务**：CTR = 点击 / 曝光，CVR = 转化 / 点击，GMV / 时长 / 留存。  

- **在线评估**：  
  - **A/B 测试**：分桶均匀，金标准。  
  - **Interleaving**：把新旧模型结果交错展示，看用户偏好（更快、更敏感）。  
  - **Switchback**：时序交替分桶（适用于电商大促）。  

- **实时闭环**：  
  - 行为日志 → Kafka → Flink 实时特征 → 在线推理 → 用户反馈回流到特征库与训练样本。

#### 3. 工程实现
- **离线训练**：用次日样本训练当天模型，特征包含 7 / 14 / 30 天窗口统计。  
- **在线推理**：实时特征（用户最近 5 分钟行为）从 Redis 拉取，预训练 Embedding 从向量库拉取。  
- **反馈链路**：曝光 → 点击日志在 1 秒内回流到 Kafka，Flink 在 5 分钟内更新实时特征；次日精排训练消费全量回流日志。  
- **指标监控**：  
  - 离线：训练 AUC 监控、特征分布漂移（KS / PSI）。  
  - 在线：A/B 桶的 CTR / CVR / GMV / 时长 + P99 延迟 + QPS。  
- **纠偏方法**：IPS（Inverse Propensity Scoring）/ Doubly Robust 估计 / 探索流量兜底。

#### 4. 行业实践
- **Google YouTube**：A/B + Interleaving 双轨评估；分钟级流式特征。  
- **Netflix**：用 Interleaving 快速验证推荐策略，避免长时间 A/B 的延迟成本。  
- **Uber Eats**：Switchback 实验设计应对外卖高峰期的强时间相关性。  
- **阿里淘宝**：实时 Flink 特征 + 每小时级模型增量 + A/B 测试平台。  
- **字节 ByteRec**：分钟级实时训练 + 在线学习 FTRL。  
- **京东**：实时特征 + 全链路监控 + 业务指标对齐 dashboard。  
- **Spotify**：用流式 Flink 推实时播放特征 + 反馈闭环，强化学习推荐。  
- **Meta DLRM**：端到端 GPU 推理 + 分钟级反馈链路。

#### 5. 落地陷阱
- **离线 AUC 高但在线无效**：LogLoss 与业务不对齐，必须看 GAUC + 业务指标。  
- **A/B 测试样本不足**：未跑满周期就下结论，新模型上线反而损失 GMV。  
- **反馈延迟**：实时特征没接回流，模型用的是"昨天的数据"。  
- **特征穿越**：用未来特征训练（数据泄漏），离线 AUC 虚高。  
- **曝光偏差**：训练只用曝光过的 Item，导致模型对新候选打分偏低。  
- **数据漂移**：模型 3 个月没更新，输入分布已变化，效果断崖式下跌。  
- **业务指标波动**：大促 / 节假日与日常分布不同，必须分层评估。

#### 6. 追问预测

- **「离线 AUC 涨了、在线没动，第一步查什么？」** 答：先查训练与推理的特征口径是否同源同定义——口径分叉不会让离线指标变差，只会让在线不动，是最难发现的一类原因；再查离线样本与线上暴露分布是否一致（曝光偏差）。判据是「用线上请求时点的特征把离线评估重放一遍」：重放后 AUC 掉下来，就说明原来的离线数字不能用于决策。
- **「线上 A/B 跑多久才敢下结论？」** 答：要覆盖完整的业务周期（含周内与周末差异）并预先算好样本量，不能看到显著就停——提前停止会放大假阳性。另外首周数据受新奇效应影响会偏高，效果常在随后数周回落，所以「首周显著」不足以支持长期决策【经验】。
- **「IPS / 反事实评估能不能替代 A/B？」** 答：不能。反事实评估的可信度高度依赖曝光概率估计的质量与日志覆盖度（曝光日志必须记录当时的策略版本，否则连概率都估不出来）。工业上的通行组合是「反事实评估先筛掉明显更差的候选 + 小流量 A/B 做最终确认」【经验】。
- **「GAUC 和 AUC 差在哪里？」** 答：AUC 把所有曝光样本混在一起算，用户之间的可比性差异被抹平；GAUC 先按用户（或请求）分组算、再按曝光量加权，衡量的是「同一用户内部排序对不对」。推荐本质是同用户多候选之间的排序问题，所以分组口径更贴近业务——这也是「离线 AUC 高但在线无效」这条陷阱里点名要看 GAUC 的原因。
- **「实时特征为什么不可回填，口径对齐怎么做？」** 答：实时特征由请求时点的原始行为算出，事后无法重放当时状态，出问题只能堵不能补。【经验】做法是让同名特征在批流两侧共用同一份定义与同一套测试用例，把口径写进特征注册表而不是各自实现——本主题 §3 的自检清单把「同名特征能否追溯到唯一一份定义」列为必查项。
- **「大促期间指标波动大，A/B 怎么读？」** 答：分时段（活动期 / 平销期）分层评估，时间相关性强的场景改用 Switchback 一类时序交替设计；直接拿大促期间的日均做新旧对比，容易把时段效应当成模型效应——这正是正文把 Switchback 单列在「在线评估」里的理由。

#### 7. 参考资料

- He 等，2014《Practical Lessons from Predicting Clicks on Ads at Facebook》——离线 AUC 与在线效果不总同向的经典工程记录（本文件 Q2 参考资料已收该条，此处取它关于「线上线下相关性」的一面）。
