## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的第一个问题是没有时间维度：把「用一种生成模型直接产出候选 ID」（2023 年的会议论文）与「把语义 Embedding 接进召回」（今天多数平台已在做）写成同一种句式，读者据此排路线图，多半会先去做那个最写不出验收标准的。

第二个问题是机制差异被抹平。本主题的「推荐演进」实际横跨三层，改动它们的东西完全不同：

1. **候选从哪来**（召回的形式）：从「共现 ID 的近邻」扩展到「语义内容的近邻」，再到「直接生成 ID 序列」。
2. **一次请求内怎么排序**（粗排 / 精排 / 重排）：打分模型、多任务、集合级多样性约束。
3. **标签从哪来**（反馈闭环）：标签由推荐系统自己的曝光策略产生，没被曝光的 Item 永远没有反事实标签。

[§3 §3.1](05-recommendation-section-3-sec3.md) 已把三条硬约束写在前面：候选集规模 × 请求延迟预算、反馈闭环、目标多元。**第 2、3 层一条都不是 AI 能改的**——延迟预算是物理量，反馈闭环是数据生成机制；换更强的模型，漏斗的分层结构与离线评估的不可信性都原样保留。AI 真正改变的是第 1 层：候选的产生依据从「谁和谁一起被选过」扩到「这件东西讲的是什么」。这一点足够重要，因为它第一次让零交互 Item 拿到非随机的候选（主文件 §1.2 痛点 1）；但它不改变「召回决定效果上限、精排只决定上限内的相对顺序」这条级联性质（[§3 §3.2.1](05-recommendation-section-3-sec3.md) 的代价一段）。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期。
- **L2 可试点**：①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

**本主题对本书的 L1 判据 ① 做如下修正，理由是对象不同**：① 的原义是「已 GA 且有正式 release note」。本主题的多数方向对象是**建模机制**而不是可直接采购的产品能力——语义 ID 生成式召回、Bandit 分配、联邦聚合这类方向没有「GA 产品」这一形态，它们的正式发布物就是论文、算法与公开实现。因此 ① 按对象分两类核，全节统一适用：**产品能力类**（要落地就得先拿到某一项产品能力的方向：语义 Embedding 的通路、LLM 直接排序与对话式推荐、Agent 推荐）要求该能力项已 GA 且有 release note 或版本化文档；**建模机制类**（自己按公开方法实现的一条通道：生成式召回、多模态推荐、Bandit 探索配额、深度 RL 长期价值、知识图谱 / GraphRAG、联邦推荐、推荐基础模型）要求该机制有可核验的正式载体——同行评审的会议或期刊论文，或带版本化发布记录的公开实现。只有预印本、厂商演示或博客，或该方向赖以实现的关键环节（长期奖励信号、图与漏斗的交接形态、跨业务复用的验收判据）在公开材料里没有定义的，① 判不满足。**② 与 ③ 按本书 L1 判据（§5.1）原文核，不做修正**——② 仍是本节全部方向的上限，也是没有任何一行达到 L1 的唯一原因。

判据 ② 在本主题格外难过，原因值得先说清：**推荐效果的公开材料天然是建设方自述**。A/B 结果是平台最核心的商业数字，能拿出来讲的往往只有方向与口径，样本量、对照条件与统计口径都握在发布方手里；论文一侧则几乎全是离线数据集上的指标，与线上暴露分布隔着一层。所以本节的方向大多停在 L2 或 L3。**② 只有「满足」与「降为 L2」两种命运**：它不能改写成「有公开效果数字」（那等于把自述口径当证据），也不能靠「本节只评估某一层」把适用范围缩小来绕过去。

还要说清 L2 在本节的含义：它标的是**证据缺口**，不是「不建议用」。当一行的 ①③ 干净而只缺 ② 时，缺的是「别人用过、并且公开说了代价」这类材料，不是能力本身；采不采用由读者按自己的风险偏好决定，判据本身不因这句说明而放宽。

另有一条评级规则，全节通用：**合并方向取最弱子项**。本节把「Bandit 探索配额」与「深度强化学习长期价值」拆成两行而不是合成「强化学习推荐」一行，理由是它们的可规划性差一个量级：前者今天就能配预算，后者要先有可用于优化的长期奖励信号。

**本节没有一行达到 L1。** 离得最近的是四行——语义 Embedding 召回、生成式召回、多模态推荐、Bandit 探索配额：它们没有一条判据完全落空，差的只有 **②（第三方非厂商公开生产案例）**。四行的差别在 ③ 的稳定程度：语义 Embedding 一行的接口多年不变；Bandit 一行更简单，它连模型都不需要；生成式召回一行的 ③ 只能算大体满足，语义 ID 的码本与目录版本强绑定；多模态推荐一行同样只算大体满足，融合方式没有统一接口，多一路模态就多一路编码器版本。判断某条方向是不是 L1，不要看它由多少厂商支持，看第 ② 条的材料是不是**发布方之外的机构**给出的：单靠建设方自述与论文跑分，无论多少条，都还是 L2。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式发布载体能不能找到——产品能力类看 release note 或版本化文档，建模机制类看同行评审的论文或带版本化发布记录的公开实现？找不到 → L3。
2. 建设方之外的证据能不能找到？找不到 → L2。
3. 接口明年会不会变？会变 → 至多 L2。

第 3 句在本主题特有的失手方式，是把「编码器」当成常量：召回向量由某个编码器版本产出，换一版编码器，全库向量就不再可比。判定方法是看平台的变更记录里有没有「按编码器版本重建索引」这一条，而不是看换模型之后离线指标涨了多少。

本节与主文件 §1.4 的关系值得说一句：§1.4 沿时间线记录「发生了什么」（协同过滤、矩阵分解、深度学习、LLM 与生成式），本节回答的是「现在能不能用」。同一条时间线在两种写法下结论可能相反——§1.4 把 2023–2024 的生成式召回列为里程碑（研究意义），本节判的是工程可用性：它落在 L2，理由是码本与目录变更频率绑定，而不是因为它不重要。**里程碑讲的是研究意义，成熟度讲的是工程可用性**，把两者混起来，路线图就会按论文的发表日期来排。

三个常见误判，排路线图时最容易踩：

- **把「离线指标涨了」误当成「方向可用」**：离线样本是被旧策略筛过的（[§3 §3.1](05-recommendation-section-3-sec3.md) 第二条约束），离线涨而在线不动是这条约束的必然结果，不是运气差。
- **把「论文有实现」误当成「有生产案例」**：论文给的是机制与数据集指标，② 要的是别人在生产里用过并公开了代价。
- **把「生成式」误当成「端到端」**：生成式召回换掉的是候选的产生方式，不是漏斗；精排与重排仍要在生成结果之上做（5.2.2）。

### 5.2 演进方向逐条拆解（核心节）

下面四个小节都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向，评审时应直接打回——推荐系统的每一次能力提升，都对应一项成本结构的变化。

#### 5.2.1 语义 Embedding 接进召回通路：把「共现」换成「内容」

- **旧做法与它的卡点**：双塔与 ItemCF 的召回依据是行为共现。共现为零时——新上架 Item、长尾 Item、跨域场景——不是「信号少」，是**没有信号**（[§3 §3.2.8](05-recommendation-section-3-sec3.md) 的原话是「不是『少』，是『没有』」）。旧绕法是内容特征 + 按类目写死的规则兜底，规则覆盖不到的类目就退化成随机曝光。
- **AI 改变了什么机制**：**把「相似」的判据从行为共现换成编码器输出的语义邻接**。它改变的是冷启动的**信号来源**（内容本身成为可比较的表征），不是召回的结构——候选仍然从一次近邻检索里出来，漏斗一层没少。
- **由此得到的**：因为语义向量不依赖本站交互，**所以**共现为零的 Item 第一次能进入候选集，且候选可以自动生成、不必逐类目写规则；**又因为**编码与建索引是离线批量动作、检索代价与索引规模相关而与候选比较次数无关，**所以**候选池的扩大与在线延迟解耦——这两条合起来，是「内容通道」值得作为并列召回而不是兜底规则的原因。
- **由此付出的**：**其一，一致性成本**——离线批量编码与在线编码必须同属一个编码器版本，否则同一件 Item 会有两个向量；换编码器要全库重编码，这是选型时最容易被忽略的一次性大成本。**其二，语义邻近不等于「会被一起选」**——把语义向量当主召回，会推出一批「看起来相关但没人买」的候选，召回的可解释性与业务直觉同时下降。**其三，内容侧质量被放大**——标题党、错标类目会直接变成候选，而冷启动路径没有反馈纠正项（[§3 §3.2.8](05-recommendation-section-3-sec3.md) 的失效点）。**其四，多一层模型依赖**：编码器版本进不了模型登记，就没法回答「这批候选是谁算出来的」。
- **证据与来源**：【公开】图文对比对齐的机制与零样本能力有原始论文（Radford 等，"Learning Transferable Visual Models From Natural Language Supervision"，ICML 2021）；把内容向量用于冷启动召回在电商与内容平台属通行做法【经验】。**② 不满足**：本节给不出「建设方之外的机构公开的、含规模与代价的生产案例」这一材料。
- **成熟度**：**L2**（与 5.1 表「语义 Embedding 接进召回通路」行一致），判据：①③ 满足、② 不满足。

| 判断项 | 共现通道（ID 双塔 / ItemCF） | 内容通道（语义 Embedding） |
| --- | --- | --- |
| 依据 | 谁和谁一起被选过 | 这件东西讲的是什么 |
| 共现为零时 | 无信号，退化为热门 | 仍有非随机候选 |
| 换件代价 | 换模型要重训，重训后历史向量作废 | 换编码器要全库重编码 |
| 主要失效形态 | 长尾与新品拿不到曝光 | 相关但不动销；内容错标直接传导 |

```text
两条通道并行接进漏斗（内容是并列通道，不是兜底规则）
  请求 ──┬─► ID 通道：用户 ID / 物品 ID 双塔 ──► 近邻检索 ──► 候选 A
         └─► 内容通道：用户侧语义表示 / 物品内容向量 ──► 近邻检索 ──► 候选 B
                              │
                        合并（配额或加权，按场景配置）
                              │
                         粗排 → 精排 → 重排
  ────────────────────────────────────────────────
  没被改动的东西：漏斗层数、粗排与精排的模型、延迟预算的分配位置
  被改动的东西：候选的来源多了一路，以及「内容向量由哪个编码器版本产出」
               必须进变更登记（同一件物品换编码器后会有两个向量）
```

**怎么判断内容通道在你这里值不值**（三项都不需要新采购）：把新增 Item 的曝光占比单独看一周——ID 通道完全覆盖不到的那部分才是它的收益面；抽查内容通道召回的候选里「语义相近却从不动销」的占比，它决定你要不要加一层类目或价格约束；查同一条物品在主链路与内容链路的向量是否同源——离线批量编码与在线编码用了不同编码器版本，是这个方案最隐蔽也最常见的坏法。

#### 5.2.2 生成式召回：让检索与生成共用同一个序列空间

- **旧做法与它的卡点**：双塔把用户与 Item 各压成一个独立向量，交互只在内积空间发生——想表达特征交叉就得放弃可扩展性，而放弃可扩展性在千万级候选上不可接受（[§3 §3.2.1](05-recommendation-section-3-sec3.md) 失效点、[§3 §3.2.7](05-recommendation-section-3-sec3.md) 被什么约束逼出来）。
- **AI 改变了什么机制**：**把「检索」重新表述为「生成」**——Item 先被量化成语义 ID，召回变成自回归地生成下一段 ID。机制上换掉的是候选的产生方式（从近邻查询变成序列解码），不是漏斗层数。
- **由此得到的**：因为相似 Item 共享语义 ID 前缀、且前缀树把解码限制在真实存在的 ID 上，**所以**「生成目录里不存在的 Item」在解码层面就被排除，生成空间被约束成真实目录的子集（[§3 §3.2.7](05-recommendation-section-3-sec3.md) 的核心机制）；**又因为**召回与精排可以共用同一套序列模型与同一套 ID 表示，**所以**模型数量与特征口径的维护面缩小——这是它对平台团队而非对单个模型的价值。
- **由此付出的**：**其一，码本维护**——语义 ID 依赖一次量化训练，目录高频变动时旧码本与新 Item 的语义空间错位，「共享前缀」的前提不再成立（[§3 §3.2.7](05-recommendation-section-3-sec3.md) 失效点），而多数平台的目录是每天在变的。**其二，延迟落在最紧的一层**：自回归逐 token 展开，延迟高于一次向量检索，而召回层本来是整条链路里最便宜的一层，把最贵的算子放进去等于把预算用在最不该用的位置。**其三，重训的连带成本**：ID 一旦重训，历史行为序列与旧 ID 不再可比，训练数据有一次性作废的一段。
- **证据与来源**：【公开】TIGER（Rajput 等，NeurIPS 2023，篇名与页码以论文库当前版本为准）；【公开】把推荐重建为生成式序列建模的论文（Zhai 等，ICML 2024，篇名以论文库当前版本为准）；【公开】大规模线上报告以预印本形式公开（OneRec 一类，2025；作者、篇名与版本以论文库当前版本为准）。**② 不满足**。
- **成熟度**：**L2**（与 5.1 表「生成式召回」行一致），判据：① 满足、③ 大体满足、**② 不满足**，且 ③ 有一处不稳（码本与目录版本强绑定）。

| 判断项 | 双塔近邻召回 | 生成式召回（语义 ID） |
| --- | --- | --- |
| 候选的产生方式 | 一次近邻查询 | 逐 token 序列解码 |
| 相似性的载体 | 向量空间的内积 | 语义 ID 的共享前缀 |
| 输出合法性 | 天然合法（索引里只有真实 Item） | 靠前缀树与受限解码约束（[§3 §3.2.7](05-recommendation-section-3-sec3.md)） |
| 目录变动的影响 | 新增 Item 编入索引即可 | 码本可能整体漂移，需重建 |
| 延迟形态 | 常数级，与候选集规模无关 | 与生成长度相关，逐 token 累加 |

这条方向最容易被过度解读的一句话是「端到端取代漏斗」。它换掉的是候选的产生方式：**生成出来的候选仍要经过分数排序与集合级约束**，因为多目标、多样性、频控这些要求不写在 ID 序列里。

#### 5.2.3 LLM 直接排序与对话式推荐：换的是接口，不是排序

- **旧做法与它的卡点**：排序模型只吃特征，回答不了「为什么推这个」（主文件 §1.2 痛点 10）；「给妈买生日礼物、预算五百」这类**没有历史落点**的需求，在 ID 空间里无处安放——它不是冷启动，是**需求先于行为**。
- **AI 改变了什么机制**：**这一处是接口改良，不是架构变化**——把「自然语言 → 结构化条件」这一步从规则与词典换成了语言模型；真正变化的只有两处接口：主要入口的**意图解析**，与展示层的**理由生成**。排序仍由原精排层完成。
- **由此得到的**：因为自然语言请求可以被解析成结构化约束（受众 / 场合 / 预算 / 类目），**所以**「无历史的新需求」第一次能转成可执行的过滤与检索条件，而不是从历史行为里猜；**又因为**理由生成不参与排序，**所以**它可以在不触碰效果指标的前提下独立上线与回滚——这是本节少见的一处「收益与主链路解耦」的改动。
- **由此付出的**：**其一，成本与延迟**——单次生成的 token 成本与端到端延迟比向量检索高出若干数量级【经验】（[§3 §3.2.6](05-recommendation-section-3-sec3.md)），把 LLM 放进主排序等于把最贵的一步放在请求路径最热的位置。**其二，输出空间不受约束**——把 Item 空间交给自由文本生成，会输出目录里不存在的 Item（[§3 §3.2.6](05-recommendation-section-3-sec3.md) 失效点），必须用真实检索结果做约束，即「LLM 提意图 → 真实库存检索 → LLM 解释」三段式。**其三，新的隐性依赖**——提示词、目录描述、模型版本都成为模型外的依赖，换模型等于换了一整套「特征」，而它们通常不进版本登记。
- **证据与来源**：【公开】P5（Geng 等，RecSys 2022）、GPT4Rec（Li 等，2023）、ChatRec（Gao 等，2023）是这条方向的公开来源。**① 与 ② 均不满足**：「用 LLM 排序」是被使用的方法，不是被正式发布的能力项；截至本节写作时也拿不出发布方之外的生产案例。
- **成熟度**：**L3**（与 5.1 表「LLM 直接排序与对话式推荐」行一致）：① 不满足、② 无。可用的那部分（意图解析、理由生成）已按接口处理，落在 5.3 的表里。

```text
可用的三段式（每一段都留有确定性路径）
  ① 理解：自然语言请求 ──► 结构化条件（受众 / 场合 / 预算 / 类目）
        · 失败形态：条件解析错 → 后续全错，所以这一步要有回读确认
  ② 取候选：结构化过滤 + 向量检索 ──► 真实在售的 Item 集合
        · 关键约束：候选必须来自真实库存，硬约束（尺码、预算、库存）走过滤而不是走提示
  ③ 解释：候选 + 用户上下文 ──► 一句话理由（不改变顺序）
        · 失败形态：理由与候选不符 → 影响信任，但不影响排序指标
  ────────────────────────────────────────────────
  把「生成」限制在 ① 与 ③，中间那一步交给确定性检索——
  这是「LLM 输出目录里不存在的 Item」这条失效路线唯一的堵法
```

#### 5.2.4 其余方向为什么停在这里

下面 8 条同样按六行结构写：除末条「实时链路」外，它们停在低处不是因为看不到收益，而是因为判据过不去；把理由拆成六行，是为了让「停在这里」这个判断能被逐条复核，而不是留一句印象（末条「实时链路」是既有工程约束，不套 ①②③ 判据、也不判级，见该条）。

- **Agent 推荐 · 旧做法与它的卡点**：跨系统的动作选择靠人工规则与工单，「要不要调、调哪个」由人判断；既不能规模化，出错了也没有可归属的对象。
- **Agent 推荐 · AI 改变了什么机制**：把「动作选择」表述成一次推荐——工具与动作成为被排序的对象。换掉的是被推荐对象的类型，不是推荐系统本身。
- **Agent 推荐 · 由此得到的**：因为工具目录一旦可枚举就与 Item 目录同构，**所以**推荐侧不需要新机制，扩展成本落在平台侧（工具目录 + 权限 + 调用预算）而不是模型侧。
- **Agent 推荐 · 由此付出的**：**失败无法归属**——在工具调用审计与权限模型成立之前，向一个还没有权限模型的对象推荐动作，推错的后果没人接得住；且动作不可逆，推荐一个 Item 推错只损失一次曝光，推荐一个动作推错可能产生副作用。
- **Agent 推荐 · 证据与来源**：机制一侧的公开材料以论文与开源原型为主（AgentRec 一类，2024；具体篇目与出处请按该关键词在论文库自行检索核验）；**① 不满足**：没有面向「向 Agent 推荐工具」这一能力项的正式发布；**② 无**。
- **Agent 推荐 · 成熟度**：**L3**（与 5.1 表「Agent 推荐」行一致）：① 不满足、② 无。

- **Bandit 探索配额 · 旧做法与它的卡点**：只按当前最优策略分配曝光，新 Item 拿不到流量，反馈闭环自我锁死（[§3 §3.2.8](05-recommendation-section-3-sec3.md)）；真正的卡点不在算法而在**考核**——收益落在长期、成本落在当期。
- **Bandit 探索配额 · AI 改变了什么机制**：**用一部分曝光换标签**——把「按当前最优确定性分配」换成「按臂分配 + 小额均匀探索」。它不需要模型，也不会因为模型变强而变准。
- **Bandit 探索配额 · 由此得到的**：因为探索配额直接作用于反馈闭环（[§3 §3.2.8](05-recommendation-section-3-sec3.md) 三路兜底里的第三路），**所以**它是唯一能把「候选」变成「新标签」的机制，更深的模型替代不了它。
- **Bandit 探索配额 · 由此付出的**：**当期效率的确定性损失**——按定义要牺牲一部分曝光效率（[§3 §3.2.8](05-recommendation-section-3-sec3.md) 的代价一段）；而且它必须先有一条写进考核的预算，否则第一次指标下滑时就会被砍掉（[§3 §3.7](05-recommendation-section-3-sec3.md)）。
- **Bandit 探索配额 · 证据与来源**：【公开】探索-利用在推荐里的经典出处是 Li 等，WWW 2010（面向新闻推荐的上下文 Bandit）；**② 不满足**——本节给不出建设方之外、含规模与代价的生产案例。
- **Bandit 探索配额 · 成熟度**：**L2**（与 5.1 表「Bandit 探索配额」行一致）：①③ 满足、② 不满足。

- **深度 RL 长期价值 · 旧做法与它的卡点**：优化目标停在单次点击，留存与生态健康只能靠间接指标盯；要用策略优化处理它们，需要可用于优化的长期奖励信号与一个允许试错的环境，两样都不具备。
- **深度 RL 长期价值 · AI 改变了什么机制**：把「逐步贪心」换成「对长期累积回报做序列决策」——机制从单步打分变成策略优化。
- **深度 RL 长期价值 · 由此得到的**：**如果**长期奖励信号成立，频控、疲劳度与生态健康这些今天靠规则外挂的目标可以进入同一个优化过程，这是它相对 Bandit 的潜在增量。
- **深度 RL 长期价值 · 由此付出的**：**试错环境本身就是成本**——线上不允许低成本试错，仿真环境与线上分布的差距又无法自查，而离线评估本就不可信；策略一旦上线，故障形态从「一次排序错了」变成「整段策略持续走偏」。
- **深度 RL 长期价值 · 证据与来源**：公开材料以仿真或小规模环境为主，本节给不出可点名的线上生产报告；**① 不满足**——本方向赖以实现的关键环节（可用于优化的长期奖励信号）没有可核验的正式载体；**② 无**。
- **深度 RL 长期价值 · 成熟度**：**L3**（与 5.1 表「深度强化学习推荐」行一致）：① 不满足、② 无。

- **多模态推荐 · 旧做法与它的卡点**：内容侧信号靠人工标注与单模态字段，封面、视频帧、图文关系进不了模型；缺特征等于把一部分目录当成盲区，而人工补标一条 Item 的成本远高于它带来的边际收益。
- **多模态推荐 · AI 改变了什么机制**：把非结构化内容（图像 / 文本 / 视频）编码成可比较的表征并融合——换的是**特征侧**，不是排序侧。
- **多模态推荐 · 由此得到的**：因为编码器把封面与视频帧映射进同一语义空间，**所以**「字段缺失但内容可看」的那部分 Item 第一次能被纳入候选与排序，收益面正是内容侧特征缺失的场景。
- **多模态推荐 · 由此付出的**：**增益幅度必须自测**——从「能编码」到「在自有目录上涨」中间隔着一次必须自测的对照，缺的是评测协议与自有 Golden Set，不是能力；且多一路模态就多一路延迟、多一份编码器版本登记（换版同样要全库重编码）。
- **多模态推荐 · 证据与来源**：【公开】编码一侧的基础工作（Radford 等，ICML 2021，CLIP）、多模态推荐的两个代表工作（He & McAuley，AAAI 2016，VBPR；Wei 等，ACM MM 2019，MMGCN）；**② 不满足**。
- **多模态推荐 · 成熟度**：**L2**（与 5.1 表「多模态推荐」行一致）：① 满足、③ 大体满足、② 不满足。

- **知识图谱 / GraphRAG · 旧做法与它的卡点**：多跳的「为什么推荐」靠人工写的规则链或展示层模板，属性关系一变就要改代码；图的邻居与漏斗候选之间没有既定的交接方式。
- **知识图谱 / GraphRAG · AI 改变了什么机制**：把「多跳关系推理」从手写规则链换成在图与检索上生成的推理路径——换的是关系与解释的**产生方式**，不是候选的产生方式。
- **知识图谱 / GraphRAG · 由此得到的**：**如果**实体到 Item 主键的映射成立，同一张图可以分别充当召回通道、重排特征或解释层，一份数据准备支持三种用法——这是它相对纯文本解释的潜在优势。
- **知识图谱 / GraphRAG · 由此付出的**：**三种角色对数据与延迟的要求完全不同**（召回通道要可检索、重排特征要低延迟、解释层要可回溯），接口未定意味着无论选哪一种都要重做一次数据准备；此外检索侧一旦返回没有主键的实体，等于把幻觉直接送进解释。
- **知识图谱 / GraphRAG · 证据与来源**：代表工作是论文与开源原型（GraphRAG 一类；具体篇目与发布年份请按该名称在论文库与开源仓库自行检索核验）；**①③ 不满足**——本条的关键环节（图与漏斗的交接形态）在公开材料里没有定义。
- **知识图谱 / GraphRAG · 成熟度**：**L3**（与 5.1 表「知识图谱 / GraphRAG」行一致）：①③ 不满足。

- **联邦推荐 · 旧做法与它的卡点**：跨机构联合建模默认要把数据搬到一处，合规与工程成本都过不去；而它成立的前提——各方实体有重叠（[§3 §3.2.10](05-recommendation-section-3-sec3.md) 失效点）——在多数跨机构场景本就不满足。
- **联邦推荐 · AI 改变了什么机制**：把「搬数据」换成「搬更新」——各方在本地训练，只交换参数更新。
- **联邦推荐 · 由此得到的**：**在实体重叠成立时**，它能在不集中原始数据的前提下扩大协同信号的覆盖面，这是它唯一的机制性增量。
- **联邦推荐 · 由此付出的**：上传的更新仍有反演与成员推断风险，需要额外防御；且 ID 对齐不成立时，聚合出来的全局更新没有意义——两条叠加，先解决 ID 对齐再谈建模。
- **联邦推荐 · 证据与来源**：【公开】聚合方法的经典出处是 McMahan 等，AISTATS 2017（FedAvg），各联邦学习框架普遍内置这一聚合算法；**① 满足**；**③ 不满足**——跨机构 ID 对齐与接口没有标准形态；**② 无**。
- **联邦推荐 · 成熟度**：**L3**（与 5.1 表「联邦推荐」行一致）：① 满足、③ 不满足、② 无；且前提（各方实体重叠）在多数跨机构场景不成立。

- **推荐基础模型 · 旧做法与它的卡点**：每个业务各训一套模型、各维护一套特征口径，跨业务复用只能靠特征工程与召回复用；「一个模型跨业务通用」一直没有能验收的判据。
- **推荐基础模型 · AI 改变了什么机制**：把「一业务一模型」换成「预训练 + 适配」——换的是模型的复用单位，不是特征口径的复用方式。
- **推荐基础模型 · 由此得到的**：**如果**判据成立，它能把模型数量与特征口径的维护面收敛到一处（与 5.2.2 对平台团队的价值同源）。
- **推荐基础模型 · 由此付出的**：**判据本身要先立起来**——「同一份权重在不同业务上都不劣于各自专用模型」需要跨业务的对照条件与统一评测集，而各业务的指标定义与曝光分布并不一致；拿不出这个对照，投入会变成一次无法验收的基础设施建设。
- **推荐基础模型 · 证据与来源**：【公开】P5 一类工作给出了「把推荐表述为文本任务」的范式（Geng 等，RecSys 2022）；**① 不满足**——本方向的验收判据「同一份权重跨业务都不劣于专用模型」没有可核验的发布物；**② 无**。
- **推荐基础模型 · 成熟度**：**L3**（与 5.1 表「推荐基础模型」行一致）：① 不满足、② 无。

- **实时链路 · 旧做法与它的卡点**：批处理口径的特征按天或按小时更新，新行为要等下一批才进模型，热点事件的反馈跟不上。
- **实时链路 · AI 改变了什么机制**：**这条不是 AI 改的**——改它的是批流一体的工程栈，变的是特征的新鲜度，不是模型能力。
- **实时链路 · 由此得到的**：上一次曝光的结果能在下一次打分之前进入特征，「反馈 → 下一次打分」的时延被压进可行范围。
- **实时链路 · 由此付出的**：批流两套口径对齐是持续性成本，且实时特征不可回填——口径分叉不会被离线评估捕捉，只会静默掉线上指标（[§3 §3.2.9](05-recommendation-section-3-sec3.md)）。
- **实时链路 · 证据与来源**：不适用 ①②③ 判据——它不是待评估的能力项，而是既有工程约束（[§3 §3.2.9](05-recommendation-section-3-sec3.md)）。
- **实时链路 · 成熟度**：**不判级**（与 5.1 表的处理一致：本节把它按既有技术放在 5.3 的接口表里处理）。

把上面这几条里**停在低处**的并排看，会发现理由只有两类：**一类是接口还不成立**（知识图谱与漏斗的交接形态、Agent 工具目录与权限模型、联邦的 ID 对齐），**一类是前提条件不成立**（深度 RL 需要允许试错的线上环境、推荐基础模型需要跨业务的同一份权重、生成式召回需要目录相对稳定）。判据 ① 与 ③ 讲的是前一类（机制与接口有没有被定义下来），判据 ② 讲的是后一类——**能拿出「别人在生产里用过」的材料，本身就是前提条件成立的证据**。这也解释了为什么 ② 在本主题如此难过：它要求的不是更多厂商支持，而是有人愿意把代价讲出来。

### 5.3 与本主题既有栈的接口在哪

推荐系统不是独立系统：它的输入来自特征与内容两侧，输出交给展示与实验两侧。写清接口边界（谁调用谁、以什么形态穿过边界、失败时谁负责）比写「与 X 结合」有用。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 召回 ↔ 向量库 / 向量湖 | 交接物 = Top-K 的 item 主键 + 分数 + **编码器版本**；索引可重建，主键不可丢 | 召回侧（索引可重建）；Item 主键与目录的一致性由目录侧负责 | 既有技术 |
| 编码器 ↔ 特征与索引 | 以「编码器版本 + 向量维度」为接口；换版本等于全库重编码 | 拥有编码器的那一侧（谁换版本谁负责重编码与重跑评估） | 需登记：多数平台的编码器版本不进变更记录 |
| LLM ↔ 取数与检索（意图解析） | 以「结构化条件（受众 / 场合 / 预算 / 类目）」为接口；解析结果必须回读确认，不得静默降级为默认条件 | 请求理解侧（条件解析错，后续全错） | 可做：提示版本需入登记 |
| LLM ↔ 展示层（理由生成） | 以「排序结果 + 提示版本」为接口；LLM 只产出文本，不改变顺序 | 展示层（理由错不影响排序，但影响信任） | 可做，提示版本需入登记 |
| 生成式召回 ↔ 目录系统 | 以「语义 ID 码本版本」为接口；目录变更要能触发码本维护 | 召回侧（码本漂移的后果由召回承接） | 需自建：码本重建周期是这条链路的门槛 |
| 推荐 ↔ 知识库 / RAG 检索 | 以「检索到的实体必须回到 Item 主键」为接口；检索不到合法主键即视为未命中 | 检索侧（返回无主键的实体等于制造幻觉） | 需自建：实体到主键的映射常被忽略 |
| 推荐 ↔ Agent 平台 | 以「工具目录 + 权限范围 + 调用预算」为接口 | Agent 平台侧（推荐只管候选，权限与预算不在推荐侧） | 未定型：工具目录与权限模型尚未成为通用能力 |
| 推荐 ↔ 实验与评估平台 | 以「策略版本 + 曝光日志 + Golden Set」为接口；离线结论必须能追到策略版本 | 实验平台侧（SRM 一类由平台检测）；结论口径由业务侧定义 | 部分既有：曝光日志记策略版本的仍是少数 |
| 推荐 ↔ 特征链路（批 / 流） | 以「同名特征唯一一份定义」为接口；批流两套实现必须口径一致 | 特征侧（口径分叉不会被离线评估捕捉，只会静默掉线上指标） | 既有技术，口径对齐是持续成本 |

这张表里只有两行属于既有能力（特征链路的批流分层、向量检索承载大规模候选），其余都要新建登记或新建链路。**失败归属必须在设计阶段写清**，否则会退化成扯皮：线上指标掉了，是编码器换了、码本漂移了、还是流侧特征口径分叉了？三件事都能解释同一个现象，而它们分属三个团队。唯一能让争论停下的是把「编码器版本 + 码本版本 + 特征口径」登记成资产——也就是下面 5.7 里那条最不性感、却最省事的要求。

**判定这张表有没有被用起来**：每个季度核对两个数——本季有多少条召回变更有编码器版本记录，有多少条模型变更有特征口径记录。两个数都是零，说明表还停在文档层面。

还有一件容易漏的事：这张表的九行里，有三行的失败**最终会落到业务侧而不是算法侧**。编码器未登记导致候选不可复现，损失由上线后的用户体验承担；曝光日志没记策略版本导致无法做反事实评估，损失由长期的生态健康承担；特征口径分叉导致模型静默退化，损失由业务指标承担。把这三条写进接口表的用途不是分工好看，而是让争论在事故发生前就有归属。

### 5.4 公开进展与文献

**论文**

- Rajput 等，"Recommender Systems with Generative Retrieval"，NeurIPS 2023——语义 ID + 生成式召回的代表工作（TIGER）；本节把「生成式召回」判 L2 的 ① 依据。
- Zhai 等，ICML 2024——把推荐重建为生成式序列建模的论文（篇名以论文库当前版本为准），是理解「召回即生成」这条路线在工业侧走到哪一步的主要公开来源。
- Geng 等，RecSys 2022（P5）、Li 等，2023（GPT4Rec）、Gao 等，2023（ChatRec）——LLM 用于推荐的三条早期路线（把推荐表述为文本任务、生成列表、对话式）。
- Kang & McAuley，ICDM 2018（SASRec）、Sun 等，WWW 2019（BERT4Rec）、He 等，SIGIR 2020（LightGCN）——序列与图两条建模路线，仍是今天精排与召回的常用组件。
- Zhou 等，KDD 2018（DIN）、Ma 等，KDD 2018（MMoE）、Tang 等，RecSys 2020（PLE）——注意力兴趣建模与多任务，本主题精排层的基线；[§3 §3.2.2](05-recommendation-section-3-sec3.md) 已给结构。
- Li 等，WWW 2010（面向新闻推荐的上下文 Bandit）——探索-利用在推荐里的经典出处；McMahan 等，AISTATS 2017（FedAvg）——联邦方向的聚合方法出处。
- He & McAuley，AAAI 2016（VBPR）、Wei 等，ACM MM 2019（MMGCN）——多模态推荐的两个代表工作；Radford 等，ICML 2021（CLIP）——多模态编码的基础工作。

**官方 release note / 版本化文档**

- 向量检索与向量库项目的官方文档：`FAISS`、`Milvus`、`pgvector` 的文档里，「近似近邻索引类型（IVF / HNSW 一类）」「距离算子（L2 / 内积 / 余弦）」「元数据过滤」都是带版本沿革的条目，按各项目的文档与版本记录可核验这些接口分别从哪一版起进入 GA（**各产品的能力名与配置项名称不同，请以各自官方文档当前版本为准**）。用途是核验 5.2.1 的 **③**：这些接口是否跨多个主版本未变；该行 ① 的 GA 与版本化文档依据见 5.1 表——向量检索一侧即本节点名的这三个项目，编码服务一侧见下一条。
- 模型厂商的 Embedding 与结构化输出文档：以「Embedding」「structured output / JSON schema」两组关键词检索提供这两项能力的厂商官方 API 文档与版本说明，核验「语义召回」与「意图解析」两处接口是否已列为 GA 能力、自哪一版起提供。判断时看 API 参考与版本说明，**不要按首页文案判断**。**这一条只给关键词、不点名具体厂商与页面名**：读者按上述关键词定位到具体文档页与版本号之后，「语义召回」与「意图解析」两处接口的 GA 判定才算核到位。

**第三方生产案例**

本节**未能给出**可核验的、含规模与代价的第三方推荐系统生产案例。企业落地百分比（CTR / GMV / 转化 / 时长 / 留存各项提升）属建设方自述口径，本节不转载。**这个空白本身是结论**：它直接决定了本主题下没有任何方向可以排成 L1。

**引用纪律**：本主题最容易被误引的三类数字是「效果提升百分比」「离线 AUC 涨幅」「生成式召回的召回率」。可核验的做法是回到来源找三样东西——样本量、对照条件、统计口径；缺一个就不要引用这个数。

**怎么用这份清单**：先看你要核的是「信号从哪来」还是「候选怎么产生」。前者的证据看编码器与检索侧的技术报告和版本化文档（更新快、可核验性高）；后者的证据看会议论文与开源实现（更新慢，但一篇有实现的论文抵十篇公众号解读）。两类材料都不能替代判据 ②——它们证明的是机制存在，不是有人在生产里用它并承担了代价。

### 5.5 被过度宣传的部分

**「LLM 直接做推荐可以取代排序模型」**——实际是换了一处接口，不是换了排序。原因：把自然语言解析成结构化条件，与在千万级候选上打分，是两件成本函数不同的事；前者的输出体量固定，后者的推理次数等于候选数。**它什么时候才会成真**：生成式召回被正式发布为产品能力、并能在自有目录上给出带成本与延迟口径的对照结果——注意这说的是「生成候选」，不是「用 LLM 打分」。

**「生成式推荐 = 一个模型端到端取代漏斗」**——实际换掉的是候选的产生方式。原因：多目标、多样性、频控这些要求写在集合层，不写在 ID 序列里；漏斗分层的目的是把最贵的推理限制在小候选集上，这条预算约束不因模型变强而消失。**它什么时候才会成真**：语义 ID 的码本维护能跟上目录日更节奏，且自回归解码的延迟落进 P99 预算——两个条件同时可见于公开材料时再讨论。

**「有了语义 Embedding，协同信号就不需要了」**——实际是两条互补信号被说成了一条替代关系。原因：语义向量回答「这件东西像什么」，共现回答「谁和谁一起被选」；前者在共现为零时兜底，后者在前者分辨不出「相关但不被选」时兜底，两者失效的样本集不重合。**它什么时候才会成真**：内容侧特征（标题、类目、封面）在自有目录上完整且准确，且业务只需要「语义相似」而不需要「偏好排序」——这要求把「为什么不选」这件事从指标里去掉，多数业务做不到。

这三条有一个共同结构：**把「某一层的成本降了」说成「整条链路可以少几层」**。判断它们何时成真，看的是同一件事——**新一代方案有没有自己的成本与延迟口径，并且这个口径能与旧链路逐项对齐**。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 召回层的默认形态从「单一路径」变成「共现通道 + 内容通道并行」，内容通道不是兜底而是并列一等 | 开源推荐框架与云厂商推荐服务的文档里出现独立的「内容/语义向量召回」配置项；新平台的冷启动不再以 ID 模型为主链路 | 三年后主流开源框架的召回通道仍只有 ID 双塔与规则兜底，内容向量只作为离线补充 |
| 生成式召回会先在「目录相对稳定 + 有专职平台团队」的场景落地，而不是全面取代漏斗 | 公开论文与行业报告里出现带成本、延迟与目录变更频率口径的线上运行材料，且链路里仍保留精排层 | 生成式召回长期停留在离线评测与演示，公开材料始终只给效果不给成本与延迟 |
| 「LLM 做展示层理由生成」会成为标配，「LLM 做精排」仍是少数 | 推荐系统的变更记录里出现理由/解释与提示版本的登记条目；精排层仍然是特征模型 | 精排层被 LLM 整体替换并在多个平台被公开采用 |
| 编码器版本与特征口径会像模型版本一样进入变更登记 | 推荐平台的发布流程与目录里出现「编码器版本 + 码本版本 + 特征口径」字段 | 推荐系统仍只登记模型版本，编码器与码本版本不进任何登记，换编码器靠口头同步 |

四条都能被**公开文档与实际变更记录**证实或证伪，不需要内部数据：

- 第 1 条看开源框架与云服务文档的召回配置项，一到两年见分晓。
- 第 2 条看公开材料的字段（有没有成本与延迟），两到三年。
- 第 3 条看平台变更记录里出现的是「理由」还是「排序替换」，一到三年。
- 第 4 条看发布流程的必填字段，一到两年。

最值得先盯第 4 条：它是唯一一条**不依赖任何新产品发布**就能观察到的信号，而且它一旦做不到，其余三条的结论都失去可比性——编码器换了而没人知道，任何跨期对比都不成立。

提醒一句：这四条问的都不是「哪个模型会更强」，而是「**判断依据会不会出现在公开文档里**」。前者无法证伪，后者可以逐条核对。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有 ID 双塔，冷启动差 | 并列接一条内容/语义向量召回通道，用自有 Golden Set 与 ID 通道对照（5.2.1） | 内容通道在长尾与新 Item 上的曝光占比是否上升 | 不要用内容通道替换 ID 通道；不要在全量替换前先做全库重编码 |
| 目录日更、想上生成式召回 | 先量两个数：码本重建周期、自回归解码的 P99（5.2.2） | 公开材料里是否出现带成本与延迟口径的线上报告 | 不要为生成式召回预建码本基础设施；不要动召回层之外的链路 |
| 想用 LLM 做排序 | 先把 LLM 放在意图解析与理由生成两处接口上（5.2.3） | 输出合法性校验与提示版本登记是否成为平台能力 | 不要在主排序链路里放自由文本生成；不要把生成的 Item ID 直接送展示层 |
| 有 LLM 助手与商品库 | 走「LLM 提意图 → 真实库存检索 → LLM 解释」三段式，并给模型调用加预算上限 | 检索侧是否出现「实体必须回到主键」的强制校验 | 不要用向量召回单独承接硬约束（尺码、预算、库存）；不要省掉结构化过滤 |
| 想上 Agent 推荐 / 联邦推荐 | 先补前置：工具目录与权限模型、跨机构 ID 对齐 | 平台是否把「工具目录 + 权限 + 预算」做成一等能力 | 不要在没有权限与审计的前提下让 Agent 执行动作；不要为图 + 推荐预留 schema |
| 刚开始建推荐平台 | 先把三样登记成资产：编码器版本、码本版本、特征口径（5.3） | 有多少条召回变更能追到编码器版本 | 不要把建设方自述的效果数字写进选型结论 |

「明确不要做」这一列的共用逻辑只有一句：**本节真正变了的只有「候选从哪来」，延迟预算与反馈闭环一寸没动**。所以预算应当投在编码器版本管理、特征口径与自有评测集这三件确定性工程上；这三样没定下来之前，任何「AI 原生推荐」的采购都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先建对照**：自有 Golden Set + 曝光日志记策略版本。没有它，后面任何改动都无法判断变好还是变坏。
2. **再接一条通道**：内容/语义向量作为并列召回接入，与 ID 通道并行跑，只对照、不替换。
3. **然后定版本**：编码器版本、码本版本、特征口径进变更登记。这一步决定跨期对比有没有意义。
4. **最后才谈生成式与 Agent**：这两类都会改变链路的层数与责任归属，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新模型——对照集、版本登记、并列召回、探索预算，全是流程与工程。这也解释了本节为什么没有 L1：真正成熟的那部分（向量检索、Bandit 分配、批流特征分层）不需要被宣传，而需要被宣传的那部分，还没有成熟到能被建设方之外的人核验。

### 5.8 小结

> 本节小结：AI 在本主题上**只改了一条机制**——候选的产生依据从「行为共现」扩到「语义内容」，于是共现为零的 Item 第一次能拿到非随机候选，冷启动从「等标签」变成「先用内容顶住」。它**没有改变**的是三件事：标签仍然由推荐系统自己的曝光策略产生（所以离线评估依然不可信、探索配额依然必要）、延迟预算依然是分层的理由、召回依然决定效果上限而精排只决定上限内的顺序。本节没有一行达到 L1，离得最近的四行——语义 Embedding 召回、生成式召回、多模态推荐、Bandit 探索配额——差的只有「第三方（非厂商）公开生产案例」这一条；所以现在该投的是编码器版本管理、特征口径与自有评测集，而不是「端到端生成式推荐」。
>
> 💡 **思考锚点**：挑你们最近给推荐加的那条召回通道，翻曝光日志里记的策略版本与编码器版本——追得到它上线时用的是哪一版吗？§5.2.1 要求内容 / 语义通道与 ID 通道并行对照；若版本都没登记，你拿什么把「内容通道更好」和「只是特征口径变了」分开？
