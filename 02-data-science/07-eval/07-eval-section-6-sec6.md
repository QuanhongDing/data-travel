### 7.1 某头部电商"**A/B 测试 1000+ 实验**"6+ 年（2018-2024）

**背景（Why）**

该电商 2018 年面临**大规模并行 A/B 的统计学陷阱**：
- **日均 1000+ 实验**——多团队并行
- **SRM（Sample Ratio Mismatch）频发**——分流配比与设计不一致
- **多重比较**——1000 个实验同时跑，**假阳性必然出现**
- **方差大**——长尾实验观察周期太长

**触发点（What）**

2018 年该电商启动 A/B 测试平台（[案例 2018]），目标：
- **实验效率**——**+50%**
- **SRM 问题**——**-80%**
- **多重比较假阳性**——**控制住**

**详细做法（How）**

该电商 A/B 测试的**5 大核心组件**：

1. **流量分层（核心创新）**
   - 关键设计：**用户 hash 模 N 分桶**，多实验**层与层正交**
   - 关键能力：**千实验并行不打架**
   - 关键数字：**日 1000+ 实验**
   - 分层示意：
     ```
     100% 流量
     ├─ 第 1 层：UI 实验（每层 4 个流量分桶）
     ├─ 第 2 层：推荐实验
     ├─ 第 3 层：营销实验
     └─ ...
     用户按 (layer, hash(uid)) 取模进桶
     同一层内多实验分桶独立 → 互不干扰
     ```

2. **哈希分桶（核心）**
   - 关键设计：**hash(uid) % N**——**避免时间分桶不均**
   - 关键能力：**分流稳定**
   - 关键数字：**分流准确率 99.99%**

3. **SRM 检测（核心）**
   - 关键设计：**每 5 分钟 check 一次实际分流与设计比**，卡方检验
   - 关键能力：**自动发现 SRM**
   - 关键数字：**SRM 问题 -80%**
   - 检测示意：
     ```python
     observed = [bucket_a, bucket_b]   # 实际流量
     expected = [total * ratio_a, total * ratio_b]
     chi2 = (observed[0] - expected[0])**2 / expected[0] + ...
     p = 1 - chi2.cdf(chi2, df=1)
     if p < 0.001:  # 严重 SRM
         alert_and_pause_experiment()
     ```

4. **多重比较校正（核心）**
   - 关键设计：**Bonferroni / BH-FDR** 控制假阳性
   - 关键能力：**1000+ 实验可同时跑**
   - 关键数字：**假阳性控制 95%**

5. **CUPED（核心创新）**
   - 关键设计：**用实验前协变量矫正指标**——**方差降 30%**
   - 关键能力：**小差异也能检测**
   - 关键数字：**实验周期 -40%**

**该电商 A/B 测试关键数字**（[案例 2018-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **日均实验数** | 100 | 1000+ | **+900%** |
| **实验效率** | 基线 | +50% | **+50%** |
| **SRM 问题** | 100% | 20% | **-80%** |
| **多重比较** | 不可控 | 控制 95% | **+95%** |
| **实验周期** | 基线 | -40% | **-40%** |
| **流量分层** | 不可用 | 100% | **∞** |
| **CUPED 方差缩减** | 0 | 30% | **∞** |
| **假阳性** | 不可控 | 控制 | **—** |

**具体数字（How much）**

- 团队规模：该电商 A/B 测试平台团队 30+ 人
- 关键数字：**日 1000+ 实验**；**SRM -80%**；**周期 -40%**
- 业务影响：覆盖该电商**全部 A/B 实验**

**失败教训**

- 早期「**实验效率低**」——人工分析，**千实验根本跑不过来**，倒逼自动化
- **不做 SRM**——第一版流量分配有 bug，**10% 的实验分流不对**，结果全错；后**SRM 自动检测**
- **不做多重比较校正**——1000 个实验**必然有 50 个假阳性**，被业务方骂「实验没用」；后加 **BH-FDR**
- **不做 CUPED**——小差异需要海量用户才能检，**实验周期 2 个月**；CUPED 后**方差降 30%**

### 7.2 某短视频平台"**Interleaving 5x 灵敏度**"5+ 年（2019-2024）

**背景（Why）**

该短视频 2019 年面临**排序 A/B 太慢**：
- **搜索 / 推荐排序**——CTR 差异 1% 的微小改进，**传统 A/B 需千万用户**
- **排序微调**——**不能等几个月才上线**
- **需要更灵敏的实验方法**

**触发点（What）**

2019 年该短视频启动 **Interleaving**（[案例 2019]），目标：
- **实验周期**——**-70%**
- **灵敏度**——**+5 倍**
- **对排序微调**——**可快速验证**

**详细做法（How）**

该短视频 Interleaving 的**5 大核心组件**：

1. **Team Draft Interleaving（核心创新）**
   - 关键设计：**用户看到的列表是 A/B 交替插入**，**避免顺序偏置**
   - 关键能力：**两套排序在同一用户身上比较**
   - 关键数字：**灵敏度 +5 倍**
   - 关键示意：
     ```
     A 排序：[a1, a2, a3, a4, a5, a6, a7, a8]
     B 排序：[b1, b2, b3, b4, b5, b6, b7, b8]
     Interleaved: [a1, b1, a2, b2, a3, b3, a4, b4, ...]
     统计：用户在 A 上点击 / 在 B 上点击 → A 的胜率
     ```

2. **A/B 双层验证（核心）**
   - 关键设计：**Interleaving 出结果后，必须再用 A/B 验证**
   - 关键能力：**避免 Interleaving 偏置**
   - 关键数字：**与 A/B 吻合率 92%**

3. **自研 A/B 平台（核心）**
   - 关键设计：**Interleaving + A/B 双模式**
   - 关键能力：**场景选模式**
   - 关键数字：**覆盖 100+ 排序实验**

4. **排序实验（核心）**
   - 关键设计：**从「CTR +1%」到「CTR +0.1%」**都能检
   - 关键能力：**微调可量化**
   - 关键数字：**微调可检 5x**

5. **5x 灵敏度（核心创新）**
   - 关键设计：**Interleaving 共享用户方差**——**A/B 需 100 万用户，Interleaving 只需 20 万**
   - 关键能力：**同样样本量下 5x 灵敏**
   - 关键数字：**灵敏度 5x**、**周期 -70%**

**该短视频 Interleaving 关键数字**（[案例 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **实验周期** | 100% | 30% | **-70%** |
| **灵敏度** | 1x | 5x | **+5x** |
| **A/B 吻合** | — | 92% | **—** |
| **Team Draft** | 不可用 | 100% | **∞** |
| **A/B 双层验证** | 不可用 | 100% | **∞** |
| **覆盖排序实验** | — | 100+ | **—** |
| **所需用户** | 100 万 | 20 万 | **-80%** |
| **微调可检** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：该短视频 Interleaving 团队 20+ 人
- 关键数字：**周期 -70% / 灵敏度 5x**；**与 A/B 吻合 92%**；**100+ 排序实验**
- 业务影响：覆盖该短视频**全部搜索 / 推荐排序实验**

**失败教训**

- 早期「**A/B 慢**」——排序微调需千万用户，**几个月才能上线**，倒逼 Interleaving
- **Interleaving 不双层验证**——第一版只跑 Interleaving，**2% 场景结果失真**；后必须 **A/B 二次验证**
- **顺序偏置**——把 A 全部排在前面，**A 天然胜出**；Team Draft 均衡插入才消除

### 7.3 某 LLM 公司"**LLM 评估平台**"3+ 年（2021-2024）

**背景（Why）**

该 LLM 公司 2021 年面临**多版本 LLM 的快速评估**：
- **训练多个 LLM 版本**——周级发版
- **传统 A/B 太慢**——LLM 改动小、风险大，**不能直接上线**
- **能力维度多**——**推理 / 写作 / 代码 / 中文 / 指令跟随**，各维度都要评
- **人工评估贵**——千题 × 千模型 = 百万次评

**触发点（What）**

2021 年该 LLM 公司启动**评估平台**（[案例 2021]），目标：
- **评估周期**——**-60%**
- **LLM 选择效率**——**+3 倍**
- **能力维度**——**全覆盖**

**详细做法（How）**

该 LLM 评估的**5 大核心组件**：

1. **HELM 全面评估（核心创新）**
   - 关键设计：**多任务多维度**——分类 / 生成 / QA / 代码 / 推理
   - 关键能力：**一个平台评估全部能力**
   - 关键数字：**5 大任务 × 30 维度**
   - 关键示意：
     ```yaml
     # HELM-style 评估矩阵
     benchmarks:
       - name: truthful_qa       # 事实性
         samples: 817
       - name: mmlu               # 多任务语言理解
         samples: 14042
       - name: humaneval          # 代码
         samples: 164
       - name: gsm8k              # 推理
         samples: 1319
       - name: c-eval             # 中文
         samples: 13948
     # 一次跑出 5 任务 × 30 维度的完整画像
     ```

2. **AlpacaEval（核心）**
   - 关键设计：**自动评估**（用大模型判分）
   - 关键能力：**千题千模型可评**
   - 关键数字：**评估成本 -90%**

3. **LMSYS Arena（核心）**
   - 关键设计：**真实用户盲测**——Elo 排名
   - 关键能力：**真实偏好**
   - 关键数字：**覆盖 100+ 模型**

4. **AI-as-Judge（核心）**
   - 关键设计：**GPT-4 等做裁判**——与人类一致率 85%+
   - 关键能力：**大规模自动评**
   - 关键数字：**与人类一致率 85%**

5. **Human Eval（核心创新）**
   - 关键设计：**关键场景留人工评**，**AI 评 90% 场景**
   - 关键能力：**质量 vs 成本平衡**
   - 关键数字：**评估成本 -60%**

**该 LLM 评估关键数字**（[案例 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **评估周期** | 100% | 40% | **-60%** |
| **LLM 选择效率** | 1x | 3x | **+3x** |
| **评估成本** | 100% | 40% | **-60%** |
| **AI-judge 一致率** | — | 85% | **—** |
| **HELM 任务数** | 1 | 5+ | **+5x** |
| **LMSYS 覆盖模型** | 不可用 | 100+ | **∞** |
| **AI-as-Judge** | 不可用 | 100% | **∞** |
| **Human Eval** | 不可用 | 关键场景 | **∞** |

**具体数字（How much）**

- 团队规模：该 LLM 公司评估团队 30+ 人
- 关键数字：**评估周期 -60%**；**选择效率 3x**；**HELM 5 任务**
- 业务影响：覆盖该 LLM 公司**全部 LLM 版本**

**失败教训**

- 早期「**评估慢**」——人工评一周才有结果，倒逼 HELM + AlpacaEval
- **完全用 AI 评**——AI 评 100%，**关键维度偏差未发现**；正解是**「AI 评 90% + 关键场景人评」**
- **用单一榜单**——只看 Arena，**忽略了垂直能力**（代码 / 中文）；正解是**多任务多维度**
- **过拟合榜单**——为了榜单刷分，**真实能力下降**；正解是**榜单分 + 用户反馈**

### 7.4 某 Agent 公司"**Agent 评估**"3+ 年（2021-2024）

**背景（Why）**

该 Agent 公司 2021 年面临**Agent 评估的特殊性**：
- **Agent 任务**——Web / 代码 / 文件，**结果难用单一指标评**
- **多步决策**——**单步对不代表最终对**
- **环境多样性**——浏览器 / 终端 / API / 文件系统，**测试环境难建**
- **评估成本高**——跑一次真实 Web 任务要 5 分钟

### 7.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**A/B 测试**」（**最简单**）——**10+ 实验**
- 关键设计：**哈希分桶 + SRM 检测 + 多重比较**是底线
- 团队：**2-3 人**
- 验证标准：**SRM 自动检测**、**假阳性控制**

**1 → 10 阶段：6-12 个月**

- 扩展到「**100+ 实验**」
- 引入「**流量分层**」——千实验并行
- 引入「**CUPED 方差缩减**」——实验周期 -40%
- 团队：5-10 人
- 验证标准：**日 100+ 实验**、**SRM -50%**

**10 → 100 阶段：12-24 个月**

- 扩展到「**1000+ 实验**」
- 引入「**Interleaving 排序实验**」——周期 -70%
- 团队：10-30 人
- 验证标准：**日 1000+ 实验**、**排序周期 < 1 周**

**100 → 1000 阶段：12-24 个月**

- 引入「**HELM + AlpacaEval + AI-as-Judge**」——LLM 评估
- 引入「**Agent 模拟器 + Web/代码任务**」——Agent 评估
- 团队：30-100 人
- 验证标准：**LLM / Agent 选择效率 3x**、**评估成本 -60%**

| 「**Agent 模拟器**」 | 不可用 | 100% | **∞** |

**关键投资回报**：
- **直接节省**：「**实验周期 -70%**」——业务上线速度从「季度」到「周」
- **业务价值**：「**LLM / Agent 选择效率 3x**」——选对模型 / 选对 Agent 的速度直接决定竞争力
- **AI 时代关键**：「**AI-as-Judge + Interleaving**」——**AI 评 AI、Interleaving 双层验证**是 LLM / Agent 时代评估的范式

> **本节小结**：
> - 4 个真实案例（电商 / 短视频 / LLM / Agent）印证：**评估不是「**A/B 测试**」，是「**流量分层 + Interleaving + HELM + Agent 模拟器 + AI-as-Judge**」**5 件套**。
> - 关键时间线：6+ 年 / 5+ 年 / 3+ 年 / 3+ 年 —— **评估是 3+ 年长期工程**。
> - 选型第一原则：「**A/B 测试 + SRM + 多重比较**」（**最简单**）——**10+ 实验** → 「**流量分层 + CUPED**」（**必须**）→ 「**Interleaving + HELM**」（**生产**）→ 「**Agent 模拟器 + AI-as-Judge**」（**AI 时代**）。
> - 99% 的失败来自「**实验效率低 + SRM + 多重比较 + 评估慢**」——必须有 **流量分层 + SRM + BH-FDR + HELM**。
> - 真正的 ROI 来自「**实验 +50% / 周期 -70% / 灵敏度 5x / 评估 3x**」——是**大厂核心评估基础设施的命脉**。
