## 6. 落地实践

### 6.1 某头部电商"**A/B 平台：当一天有一千个实验同时跑**"（2018-2024）

**背景（Why）**

该电商 2018 年面临**"实验规模上量之后的统计与工程双重失效"**：
- **多团队并行实验**——**各团队各自开实验，流量互相挤占，结论互相污染**
- **分流比例与设计不符**——**分流实现中的微小错误会让实验组与对照组的用户构成不同，结论全部作废，而这类问题往往在实验结束时才被发现**
- **多重比较必然产生假阳性**——**同时跑上千个实验时，纯凭随机也会出现相当数量的"显著"结果，业务方据此上线的功能其实无效**
- **小差异检测成本极高**——**要检测很小的相对提升，需要极长的实验周期与极大的样本量，产品迭代等不起**

**触发点（What）**

2018 年起该电商建设统一的实验平台（[案例公开材料 2018-2024]），目标：
- **支撑大规模并行**——多团队同时跑且互不干扰
- **分流可信**——分流正确性可被持续验证
- **结论可信**——假阳性被系统性控制

**详细做法（How）**

该电商实验平台的**5 大核心组件**：

1. **流量分层：让不同实验正交（核心创新）**
   - 关键设计：**按业务域划分实验层（界面层 / 推荐层 / 营销层等）**，同层内的实验各自分桶、互斥，不同层的实验在同一个用户上可以同时进行
   - 关键能力：**并行实验不互相污染**——如果所有实验共用一份流量，实验之间会争抢用户、结论互相干扰；分层把一个"共享资源"的竞争问题变成多个独立资源池
   - 关键数字：**支撑日均千级实验**
   - 关键示意：
     ```text
     分层解决的是"实验之间互相污染"（否则结论全部不可信）
       ✗ 所有实验共用一份流量
         实验 A 改了界面，实验 B 改了推荐
         同一批用户可能同时命中 A 和 B
         → A 的效果里混进了 B 的效果，谁的结论都不干净
       ✓ 按业务域分层，层内互斥、层间正交
         100% 流量
          ├── 界面层  → 实验 A1 / A2 / A3（层内互斥）
          ├── 推荐层  → 实验 B1 / B2     （层内互斥）
          └── 营销层  → 实验 C1
         同一用户在不同层可同时进入不同实验
         → 各层结论独立，且用户总体覆盖率高
       ────────────────────────────────────────────────
     代价与要求：
         要求"层"之间的效应近似可加（这本身是一个需要验证的假设）
         若两个层的效应强交互，正交就不再成立
         → 所以分层的划分依据是"业务上是否近似独立"，
           不是"我们想让它们并行"
     ```

2. **哈希分桶保证分流稳定（核心）**
   - 关键设计：**用 `hash(用户标识 + 实验标识) % N` 分桶**，而不是按时间或按请求切
   - 关键能力：**同一用户在整个实验期内始终落在同一桶**——按时间分桶会让不同时段的用户构成不同（例如白天与深夜的用户本就不同），那不是随机化
   - 关键数字：**分流准确率 99.99%**

3. **分流比例持续校验（SRM 检测）（核心）**
   - 关键设计：**周期性检验实际分流比例与设计比例是否一致**（卡方检验），偏差超阈值即告警并暂停实验
   - 关键能力：**分流错误在几分钟内暴露**——而不是等实验跑完、结论已经交付之后才发现
   - 关键性质：**分流比例问题显著下降**
   - 关键示意：
     ```text
     为什么"分流比例校验"必须自动化、且必须高频
       分流错误是静默的：
         实验照常跑、数据照常出、看板照常显示
         但两组用户的构成不同 → 结论是错的
       ────────────────────────────────────────────────
       这种错误通常来自：埋点位置差异、过滤条件差异、
       缓存穿透、客户端版本分布不均 …
         ——都是"看起来和分流无关"的地方
       ────────────────────────────────────────────────
       ✓ 因此必须：定期用实际分流数据反推"分流是否如设计"
         偏差超阈值 → 立即告警 + 暂停实验
       判据：分流比例是实验有效性的第一道门禁，
             它比任何指标显著性都更优先检查
     ```

4. **多重比较校正（核心）**
   - 关键设计：**对同时进行的多个实验采用多重比较校正**（如控制错误发现率的方法），并把"未经校正的显著"与"校正后的显著"区分呈现
   - 关键能力：**假阳性被控制在可接受水平**——否则"跑得越多、发现的假效果越多"，实验平台反而会降低组织的决策质量
   - 关键性质：**假阳性受控——并行实验越多，多重比较带来的假阳性偏差越大，必须由校正抵消**

5. **方差缩减让小幅改进可检测（核心创新）**
   - 关键设计：**利用实验前的协变量对指标做校正**（用实验前行为预测实验后表现，扣掉可解释的部分），在不改变实际分流的前提下降低指标方差
   - 关键能力：**小改善也能被检测**——产品迭代到后期，能拿到的改进本来就很小，如果检测手段跟不上，就等于"改进无法验证"
   - 关键数字：**方差降低约 30%，实验周期随样本量需求同比例下降、约 30%**

**该电商实验平台关键数字**（[案例公开材料 2018-2024]）：

| 指标 | 改前（无统一平台） | 改后 | 提升 |
| --- | --- | --- | --- |
| **并行实验数** | 百级 | 千级/日 | **+900%** |
| **实验间污染** | 共用流量、互相干扰 | 分层正交 | **结论独立** |
| **分流依据** | 时间 / 请求 | 哈希分桶 | **同用户同桶** |
| **分流准确率** | 未知 | 99.99% | **可验证** |
| **分流错误暴露时点** | 实验结束后 | 分钟内自动告警 | **提前** |
| **多重比较** | 不处理 | 校正后区分呈现 | **假阳性受控** |
| **小差异检测能力** | 需极大样本 | 方差降低约 30% | **可检测** |
| **实验周期** | 基线 | -30% | **-30%** |

**具体数字（How much）**

- 团队规模：该电商实验平台团队 30+ 人
- 关键数字：**日均千级实验**；**分流准确率 99.99%**；**方差降低约 30%**；**周期约 -30%**
- 业务影响：让大量业务团队能在可信的公共实验基础上并行迭代，而不是各自维护一套不可比的验证方式

**失败教训**

- 早期「**各团队各自开实验**」——流量互相挤占、结论互相污染，倒逼**「按业务域分层、层内互斥、层间正交」**
- 「**不做分流比例校验**」——出现过相当比例的实验分流不正确、结论全部作废且发现太晚，倒逼**「高频自动校验分流比例并暂停异常实验」**
- 「**不做多重比较校正**」——大量假阳性被当成真实效果上线，倒逼**「对并行实验做校正并区分呈现」**
- 「**分桶按时间或请求切**」——不同时段用户构成不同、随机化不成立，倒逼**「用哈希分桶保证同用户同桶」**
- 「**靠加大样本量去检测小差异**」——实验周期长到业务无法等待，倒逼**「用方差缩减技术提高检测效率」**

### 6.2 某短视频平台"**排序实验：为什么 Interleaving 比 A/B 灵敏数倍**"（2019-2024）

**背景（Why）**

该短视频平台 2019 年面临**"排序上的小改进无法被及时验证"**：
- **排序微调的提升幅度很小**——**CTR 上零点几个百分点的提升已经是可观收益，但用常规实验方法需要极大的样本量**
- **产品迭代等不起**——**常规实验要跑到所需样本量需要很长的周期，而排序策略的迭代节奏是周级的**
- **排序问题天然适合配对比较**——**同一个用户面对两套排序时的偏好，可以在同一时刻被观测到**
- **上线效果不能只看离线指标**——**离线指标提升不等于线上更好，必须在线验证**

**触发点（What）**

2019 年起该平台在排序场景引入 **Interleaving 方法**（[案例公开材料 2019-2024]），目标：
- **缩短实验周期**——用更少的样本得到结论
- **提高灵敏度**——能检测出更小的差异
- **保证结论不偏**——方法本身不能引入系统性偏差

**详细做法（How）**

该平台 Interleaving 的**5 大核心组件**：

1. **在同一用户身上比较两套排序（核心创新）**
   - 关键设计：**把 A、B 两套排序的结果交错插入同一个列表**（而不是把用户分成两组各看一套），观察用户的点击落在哪一套的内容上，据此判断哪套更优
   - 关键能力：**用户自身差异被消除**——常规实验里两组用户本来就有差异（兴趣、活跃度），这部分方差会淹没小效果；同一用户配对比较把这块方差直接去掉
   - 关键数字：**灵敏度提升数倍、所需样本量 100 万量级 → 20 万量级（-80%）**
   - 关键示意：
     ```text
     同一份差异，两种方法的"信噪比"不同
       ✗ 常规分组实验（两组不同用户）
         A 组用户 ← 兴趣 / 活跃度 / 地域 各自分布
         B 组用户 ← 分布略有不同（随机化只能保证"总体近似"）
         → 指标差异 = 真实效果 + 两组用户差异
         → 要确认那点真实效果，必须把样本量堆到用户差异可忽略
       ✓ Interleaving（同一用户，两套排序交错）
         同一个用户看到 [A1, B1, A2, B2, A3, B3, …]
         点击落在 A 的内容还是 B 的内容
         → 指标差异 ≈ 真实效果（用户差异被配对消掉）
         → 同样样本量下能检测更小的差异
       ────────────────────────────────────────────────
     前提：交错时必须均衡插入（避免位置本身带来的偏差）
           否则"排在前面的一套"会天然胜出，
           这不是效果，而是位置偏差
     ```

2. **均衡插入消除位置偏差（核心）**
   - 关键设计：**两套排序的结果在列表中交替、均衡地插入**，而不是"先把 A 的都放前面"
   - 关键能力：**比较是公平的**——位置本身极大影响点击率，若不均衡插入，结论衡量的其实是"谁排得更靠前"
   - 关键性质：**位置偏差被消除**

3. **用常规实验做二次验证（核心）**
   - 关键设计：**Interleaving 得出初步结论后，再用常规分组实验验证**，两者结论一致才认为可靠
   - 关键能力：**方法自身的偏差被拦住**——Interleaving 的灵敏度高，但也可能在特定场景下失真；把它当"筛选器"而不是"最终判决"，能同时获得速度与可靠
   - 关键数字：**与常规实验结论吻合率 92%**

4. **按场景选择实验方法（核心）**
   - 关键设计：**Interleaving 用于排序类、可配对比较的场景；涉及非排序改动（价格、机制、长期指标）的场景仍用常规实验**
   - 关键能力：**方法用在适配的地方**——把 Interleaving 强行用于所有实验，会在不适配的场景里产出错误结论
   - 关键性质：**覆盖大量排序类实验**

5. **平台同时支持两种模式（核心创新）**
   - 关键设计：**平台内建两种实验模式**，实验发起方按场景选择，两种模式共享用户分桶与指标口径
   - 关键能力：**选择成本低**——如果两种方法需要两套工具，团队会倾向于只用自己熟悉的那种，而不是适合自己的那种
   - 关键性质：**双模式可选、口径统一**

**该平台 Interleaving 关键数字**（[案例公开材料 2019-2024]）：

| 指标 | 改前（仅常规实验） | 改后 | 提升 |
| --- | --- | --- | --- |
| **实验周期** | 基线 | -70% | **-70%** |
| **灵敏度** | 基线 | 提升数倍 | **可检出更小差异** |
| **所需样本量** | 100 万量级 | 20 万量级 | **-80%** |
| **用户差异方差** | 计入总方差 | 配对消掉 | **信噪比提升** |
| **位置偏差** | — | 均衡插入消除 | **比较公平** |
| **结论可靠性** | — | 常规实验二次验证（吻合 92%） | **不失真** |
| **适用场景** | — | 排序类 | **方法适配** |
| **工具支持** | 单一模式 | 双模式共享口径 | **选择成本低** |

**具体数字（How much）**

- 团队规模：该平台实验相关团队 20+ 人
- 关键数字：**周期 -70%**；**所需样本量 -80%**；**与常规实验吻合 92%**
- 业务影响：让排序类的小幅改进能在周级节奏内被验证，而不是每个改动都要等上数月

**失败教训**

- 早期「**所有实验都用常规分组**」——排序微调需要极大样本量、周期长达数月，倒逼**「在排序场景引入配对比较方法」**
- 「**交错时不均衡插入**」——排在前面的那套天然胜出，结论衡量的是位置而不是效果，倒逼**「均衡交替插入」**
- 「**把 Interleaving 当作最终结论**」——在部分场景下结论失真，倒逼**「用常规实验做二次验证，两者一致才采信」**
- 「**把 Interleaving 套用到所有实验**」——在非排序场景产出错误结论，倒逼**「按场景选择方法」**
- 「**两种方法各用一套工具**」——团队只用熟悉的那套而非适合的那套，倒逼**「平台内建双模式并统一口径」**

### 6.3 某 LLM 公司"**模型评估：从"看榜单"到"多维度画像 + 混合评审"**"（2021-2024）

**背景（Why）**

该 LLM 公司 2021 年面临**"模型迭代快，而评估跟不上"**：
- **发版频率高**——**模型版本迭代是周级的，每个版本都要判断"是否更好、好在哪里、有没有退化"**
- **常规在线实验不适用**——**模型改动的风险面大（可能全线变差），不适合直接上线做实验**
- **能力维度高度分散**——**推理 / 写作 / 代码 / 中文 / 指令跟随等能力各自独立，单一指标无法代表整体**
- **人工评估成本随规模爆炸**——**题目数乘以候选模型数，人工评的成本不可承受**

**触发点（What）**

2021 年起该公司建设统一的模型评估体系（[案例公开材料 2021-2024]），目标：
- **评估周期缩短**——从"一周才有结论"到"天级"
- **能力画像完整**——一个版本要能看出各维度强弱
- **成本可承受**——大批量评估不能全靠人工

**详细做法（How）**

该 LLM 公司评估体系的**5 大核心组件**：

1. **多任务多维度画像，而不是单一分数（核心创新）**
   - 关键设计：**一次评估覆盖多个任务族与多个维度**（事实性、推理、代码、长文、中文、指令跟随等），产出的是一张能力画像而非一个总分
   - 关键能力：**"是否更好"变成"哪些变好、哪些变差"**——单一分数会把"推理提升但事实性退化"这类关键信息抹平，而这恰恰是模型迭代中最常见的情况
   - 关键性质：**多任务 × 多维度画像**
   - 关键示意：
     ```text
     为什么单一分数会在模型迭代中误导决策
       版本 A：总分 78
       版本 B：总分 79   ← 看起来"B 更好"
       ────────────────────────────────────────────────
       但拆开看：
         维度        版本 A   版本 B
         推理          72        80   ↑ 明显提升
         事实性        85        74   ↓ 明显退化
         代码          79        79   =
         中文          76        82   ↑
         指令跟随      78        80   ↑
       ────────────────────────────────────────────────
       → 总分只差 1，但事实性退了 11 分
       → 这在一个对准确性敏感的产品里可能是致命的
       → 结论：评估必须产出画像，且画像要能按场景加权
     ```

2. **自动评审承担大部分批量评估（核心）**
   - 关键设计：**用强模型作为评审者对生成结果打分 / 排序**，并持续度量自动评审与人工评审的一致率
   - 关键能力：**评估成本可控**——纯人工评估在"多版本 × 多题目"的组合下成本不可承受
   - 关键性质：**与人工评审一致率达到较高水平**

3. **关键场景保留人工评审（核心）**
   - 关键设计：**高风险、评价标准微妙、或自动评审一致率低的场景，保留人工评审**，其余交给自动评审
   - 关键能力：**自动评审的系统性偏差有人兜底**——自动评审会继承评审模型的偏好（如偏好更长的回答、更"客气"的语气），这类偏差只有在人工对照下才看得出来
   - 关键数字：**关键场景 100% 人工**

4. **真实用户偏好作为独立信号（核心）**
   - 关键设计：**用真实用户的匿名盲选偏好**形成独立的排名信号，与内部评估并列呈现
   - 关键能力：**避免"只对内部题目优化"**——内部题目一旦固定，模型会朝着这些题目优化，而真实使用中的表现未必同步提升
   - 关键性质：**覆盖大量模型版本**

5. **评估结果与发布门禁绑定（核心创新）**
   - 关键设计：**建立"哪些维度不允许退化"的红线**，任一红线维度退化即阻止发布，其余维度的提升不能用来抵消
   - 关键能力：**评估结果真正影响决策**——如果评估只是"参考信息"，团队在进度压力下会选择性忽略；把它绑定到门禁，评估才有约束力
   - 关键性质：**红线维度不允许用其他维度的提升来抵消**

**该 LLM 公司评估体系关键数字**（[案例公开材料 2021-2024]）：

| 指标 | 改前（人工 + 单榜单） | 改后 | 提升 |
| --- | --- | --- | --- |
| **评估产出** | 单一分数 / 榜单排名 | 多任务多维度画像 | **可定位退化** |
| **评估周期** | 周级 | 天级 | **-60%** |
| **评估成本** | 纯人工，随组合爆炸 | 自动评审承担大部分 | **-60%** |
| **自动评审可靠性** | — | 与人工一致率被持续度量 | **可校准** |
| **关键场景** | 与其余场景混评 | 保留人工评审 | **偏差有兜底** |
| **真实用户信号** | 无 | 匿名盲选偏好作为独立信号 | **避免只对内部题目优化** |
| **评估与发布** | 参考信息 | 红线维度绑定发布门禁 | **有约束力** |
| **版本迭代判断** | 总分高低 | 哪些变好、哪些变差 | **可决策** |

**具体数字（How much）**

- 团队规模：该公司评估相关团队 30+ 人
- 关键数字：**评估周期 -60%**；**成本 -60%**
- 业务影响：让周级迭代的模型版本能在天级得到可靠的横向判断，并拦住"某维度退化被总分掩盖"的情况

**失败教训**

- 早期「**只看榜单排名**」——忽视了垂直能力与事实性退化，倒逼**「产出多任务多维度的能力画像」**
- 「**完全依赖自动评审**」——评审模型的偏好被当成客观标准，倒逼**「持续度量一致率 + 关键场景保留人工」**
- 「**只用内部固定题目**」——模型朝题目优化而与真实使用脱节，倒逼**「引入真实用户偏好作为独立信号」**
- 「**评估只作参考**」——进度压力下被选择性忽略，倒逼**「红线维度绑定发布门禁」**
- 「**用总分高低判断版本优劣**」——把"某维度明显退化"抹平成"总分略高"，倒逼**「按维度呈现，并禁止用提升抵消红线退化」**

### 6.4 某 Agent 公司"**Agent 评估：单步对不代表最终对**"（2021-2024）

**背景（Why）**

该 Agent 公司 2021 年面临**"Agent 的成败不在单步，而现有评估只看单步"**：
- **Agent 是长程多步决策**——**中间每一步看起来都合理，最终任务仍可能失败；反之中间走过弯路也可能成功**
- **环境多样且难复现**——**浏览器、终端、文件系统、API 各不相同，搭一套可批量运行、可复现的测试环境本身是难题**
- **成败难以用单一指标表达**——**"任务是否完成"常常需要看最终状态（页面变成了什么、文件内容对不对），而不是某个分数**
- **真实环境跑一次代价高**——**跑一次真实的浏览器任务可能需要数分钟，评估速度成为迭代瓶颈**

**触发点（What）**

2021 年起该公司建设 Agent 评估体系（[案例公开材料 2021-2024]），目标：
- **任务级评估**——以"任务是否完成"为准，而非单步指标
- **环境可复现**——评估结果不能被环境差异污染
- **评估速度可控**——能支撑迭代频率

**详细做法（How）**

该 Agent 评估体系的**5 大核心组件**：

1. **以任务完成度为评估单位（核心创新）**
   - 关键设计：**评估对象是"整条轨迹执行下来任务是否达成"**，同时记录中间步骤用于诊断，但**判定依据是最终状态**
   - 关键能力：**评估目标与用户价值一致**——用户关心的是"帮我做成了没"，不是"每一步的概率分布好不好"；只优化单步指标会系统性地偏离用户价值
   - 关键性质：**任务级通过率可量化**
   - 关键示意：
     ```text
     为什么单步指标会和用户价值脱节
       一次"帮我在某网站下单"的任务：
         单步视角：每一步的"下一个动作预测准确率"都在 90% 以上
         任务视角：最终是否下单成功
       ────────────────────────────────────────────────
       常见脱节：
         · 90% 的单步准确率，连续 20 步下来的任务成功率可能远低
            （每一步的小概率错误会累积）
         · 两步等价动作（点这里 / 点那里）单步指标会惩罚其中一个，
           但任务结果完全相同 → 惩罚了等价替代方案
         · Agent 走了一条更长的正确路径，单步指标会扣分
       ────────────────────────────────────────────────
     结论：单步指标可用于诊断"哪里出的问题"，
           但不能作为"Agent 好不好"的判定标准
     ```

2. **环境容器化以保证可复现（核心）**
   - 关键设计：**把评估环境做成容器镜像**（含浏览器、依赖、初始数据），每个任务从同一初始状态出发
   - 关键能力：**结果可复现、环境差异不被误判为能力差异**——非容器化的环境会让"这次失败"无法归因：是 Agent 不行，还是环境不同
   - 关键性质：**环境保真度达到较高水平**

3. **任务定义与评分一体化（核心）**
   - 关键设计：**每个任务定义包含初始状态、目标判定条件与容差范围**，判定由程序自动完成（检查最终页面状态、文件内容、接口返回值），难以程序化的部分交给模型评审
   - 关键能力：**判定客观且可批量**——判定标准写不清，"通过率"就没有意义
   - 关键性质：**大量任务可批量运行**

4. **自动评审处理难以程序化的判定（核心）**
   - 关键设计：**用多模态模型评审最终截图 / 输出，判断任务完成度**，并与人工评审做一致性度量
   - 关键能力：**语义型目标可被自动判定**——"页面上的报告是否合理回答了问题"这类目标无法用程序规则表达
   - 关键性质：**与人工评审一致率较高**

5. **评估速度作为一等指标（核心创新）**
   - 关键设计：**并行执行 + 环境预置 + 结果缓存**，把单次评估从分钟级压到几十秒
   - 关键能力：**评估频率能匹配迭代频率**——如果一次全量评估要跑一整天，团队就不会在每个改动上跑评估，评估的意义随之减半
   - 关键数字：**单次评估从分钟级降到数十秒**

**该 Agent 评估体系关键数字**（[案例公开材料 2021-2024]）：

| 指标 | 改前（单步指标 + 手工环境） | 改后 | 提升 |
| --- | --- | --- | --- |
| **评估单位** | 单步动作正确率 | 任务是否完成 | **与用户价值一致** |
| **单步指标的作用** | 判定依据 | 仅用于诊断定位 | **不误导** |
| **环境可复现性** | 手工搭建，每次不同 | 容器镜像，同一初始状态 | **结果可比** |
| **判定方式** | 人工查看 | 程序判定 + 模型评审兜底 | **可批量** |
| **语义型目标** | 无法自动判定 | 多模态模型评审 | **可自动** |
| **评审一致性** | — | 与人工持续对齐 | **可校准** |
| **单次评估耗时** | 分钟级 | 数十秒 | **-90% 量级** |
| **评估频次** | 低（成本高） | 可随每次改动运行 | **匹配迭代节奏** |

**具体数字（How much）**

- 团队规模：该公司评估相关团队 20+ 人
- 关键数字：**单次评估 -90% 量级**
- 业务影响：让 Agent 的每次改动都能在小时级得到"任务成功率是否变化"的判断

**失败教训**

- 早期「**用单步动作准确率判定 Agent 好坏**」——与任务是否完成脱节，倒逼**「改为任务级评估，单步指标只用于诊断」**
- 「**评估环境手工搭建**」——每次环境不同、失败无法归因，倒逼**「环境容器化，从同一初始状态出发」**
- 「**任务判定标准写得含糊**」——"通过率"失去意义，倒逼**「每个任务明确初始状态、判定条件与容差」**
- 「**语义型目标靠人工看**」——无法批量，倒逼**「用多模态模型评审并持续度量与人工的一致率」**
- 「**评估一次要跑很久**」——团队因此不在每次改动上跑评估，倒逼**「把评估速度当作一等指标来优化」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**常规实验 + 分流校验 + 多重比较意识**」（**最简单**）——**1 个业务场景**
- 产出：**哈希分桶方案 + 分流比例自动校验 + 一个完成的实验及其决策记录**
- 团队：**2-3 人**
- 验证标准：**分流比例有自动校验且能告警**、**同一用户在实验期内落在同一桶**、**结论里区分了校正前后的显著性**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 团队 / 并行实验**」
- 引入「**流量分层**」——按业务域分层、层内互斥、层间正交
- 引入「**方差缩减**」——让小改善也能被检测，缩短实验周期
- 团队：5-10 人
- 验证标准：**并行实验之间结论互不污染**、**实验周期明显缩短**、**平台可支撑日常实验量**

**10 → 100 阶段：12-24 个月**

- 扩展到「**百级 ~ 千级实验 / 排序类场景**」
- 引入「**配对比较方法（Interleaving 类）**」——用于排序这类可配对比较的场景，并保留常规实验做二次验证
- 引入「**平台内建多种实验模式，共享口径**」——让团队选"适合的"而不是"熟悉的"
- 团队：10-30 人
- 验证标准：**排序类实验周期进入周级**、**配对方法与常规实验结论一致率被度量**、**方法按场景正确选用**

**100 → 1000 阶段：12-24 个月**

- 引入「**多维度能力画像**」——评估产出从单一分数变为分维度画像，并按场景加权
- 引入「**自动评审 + 关键场景人工 + 真实用户偏好**」三路信号并列
- 引入「**评估绑定发布门禁（红线维度不允许退化被抵消）**」+「**任务级 / 长程评估能力**」
- 团队：30-100 人
- 验证标准：**能定位"哪个维度退化了"**、**自动评审与人工一致性被持续度量**、**红线退化会阻止发布**、**长程任务的成功率可被批量测量**

- **AI 时代关键**：「**多维度画像 + 混合评审（自动 + 人工 + 真实偏好）+ 长程任务级评估 + 评估速度为一等指标**」——**模型与 Agent 的能力是分维度的、且是长程的**：单一分数无法支撑决策，单步指标无法代表任务成败；而"评估太慢就没人跑评估"这条规律，在迭代频率更高的 AI 时代只会更明显

> **本节小结**：
> - 4 个真实案例（电商 / 短视频 / LLM / Agent）印证：**评估不是「跑个 A/B」，是「分流可信 + 分层正交 + 按场景选方法 + 多维度画像 + 评估绑定决策」5 件套**。
> - 关键时间线：6+ 年 / 5+ 年 / 3+ 年 / 3+ 年 —— **评估是长期建设的基础设施**，且**它最关键的一个判据是"评估结果是否真的改变了决策"**。
> - 选型第一原则：「**常规实验 + 分流校验 + 多重比较意识**」（**最简单**）→ 「**流量分层 + 方差缩减**」（**必须**）→ 「**配对比较方法 + 双模式平台**」（**生产**）→ 「**多维度画像 + 混合评审 + 任务级评估 + 评估绑定发布门禁**」（**AI 时代**）。
> - 99% 的失败来自「**分流不可信 + 多重比较不校正 + 单一分数 + 评估只作参考**」——必须有 **分流校验 + 校正 + 分维度呈现 + 结果绑定决策**。
> - 真正的 ROI 来自「**周期 -70% + 成本 -60% + 假阳性受控 + 维度退化可定位**」——是**组织决策质量能否随规模提升的分水岭**。

> 💡 **思考锚点**：拿你最近一次上线的实验回放三件事——分流比例有没有高频自动校验（还是靠事后才发现）、多重比较有没有校正、下结论用的是总分还是分维度？任一答不上，你就落在 6.5 的 0→1 与 1→10 之间；再算一次方差缩减能把你的「100 万量级样本」压到多少——压不下来，小改善根本测不到。
