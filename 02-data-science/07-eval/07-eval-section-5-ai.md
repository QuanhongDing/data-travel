## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是没有时间维度。本节要评估的方向里，「在线 A/B 与方差缩减」已经在多数实验平台上作为常规配置存在，而「过程奖励模型」「公平性与可解释性成为强制」还停在论文、监管文本与演示里；两者被写在同一个清单里，读者据此排路线图，多半会先做那个最写不出验收标准的。

第二个问题是机制差异被抹平成同一类词。本主题的「评估」实际横跨三层机制，改动它们的东西完全不同：

1. **判断由谁做出**：人、有标准答案的标签，还是模型代理（裁判）。
2. **实验单元与随机化**：把用户随机分组、比较组间差异——在线实验的全部合法性来自这一步。
3. **结论的获得方式**：从「相关」走到「因果」，靠的是设计（随机化、双重差分、工具变量），不是靠更大的模型。

本主题的既有卡点写在主文件 §1.2 里，共十条：离线与在线不对齐、实验周期长、小流量等不到显著、SRM、多重比较、新奇效应、长尾被平均掩盖、因果与相关混淆、LLM 评估不稳定、Agent 评估困难。这十条里，前八条属于上面第 2、3 层——**第 2、3 层一条都不是 AI 能解的**，它们是统计学与流程问题。后两条（LLM 评估不稳定、Agent 评估困难）属于第 1 层，正是 AI 真正改变的那一层：谁做出判断、做一次判断要多少钱；5.2.2 与 5.2.3 分别对着这两条。这一层的变化足够大，大到评估可以被放到流程的另一个位置上；但它不改变「因果只能由设计获得」这条。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 有正式、版本化的公开发布（合格材料按方向类型分两类，见下）；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期。
- **L2 可试点**：①③ 满足、② 不满足；③ 若有一处明确不稳（跨版本不可比一类），判据文本写成「①③ 大体满足」，级别不变；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

**本主题对 §2.1 的 L1 判据做了如下修正（只修 ① 的合格材料，声明后 5.1 表与 5.2 逐项按此判级）：① 的合格材料按方向类型分两类。** **方法 / 算法 / 指标 / 工具类**方向（CUPED 一类的方差缩减、Interleaving 与多臂老虎机、因果推断工业化、LLM-as-Judge 的裁判方法、多模态代理指标、检索增强评估的框架与指标）认**正式论文（已发表）+ 版本化实现或官方版本化文档**——这类方向的「正式发布」就是论文与随之稳定下来的实现，不存在也不需要「产品 GA」这种发布。**能力项 / 产品 / 基准类**方向（基准与公开排行榜、评估即服务、持续评估、过程评估、公平性评估）只认**已 GA + 正式 release note**，基准与题目集一类按**版本化题目集与跨版本维护**核——这类方向的落点是「有没有一项被正式发布、可被引用的东西」，论文与开源实现都不构成发布。理由是本节要评估的方向一半是方法、一半是能力项，同一把尺子会两头误判：把已正式发表、实现可复用的方法判成「无正式发布」，也会把只有论文的能力项判成「有发布」。归属按方向在 5.1 表里的落点定，不看括号里有没有一个方法名——推理过程评估问的是「过程评估这一能力有没有被正式发布」，按能力项类核；Interleaving、因果推断、裁判方法问的是「算法能不能按论文自己实现」，按方法类核。② 的「第三方（非厂商）公开生产案例」与 L1 / L2 / L3 的边界一字未动。

判据 ② 在本主题尤其难过，原因值得先说清：**效果评估的公开材料天然是自述**——做了实验的人写实验结论，做模型的人报自己的跑分，材料里的口径、样本量与对照条件都握在发布方手里。所以本主题的方向大多停在 L2 或 L3；这不是保守，是判据的必然结果。**② 只有「满足」与「降为 L2」两种命运**：既不能改成「有公开效果数据」（那等于把营销页当证据），也不能靠「本节只评估某一层」把适用范围缩小来绕过去。

还要说清 L2 在本节的含义：它标的是**证据缺口**，不是「不建议用」。当一行的 ①③ 干净而只缺 ② 时，缺的是「别人用过、并且公开说了代价」这类材料，不是能力本身；本节照判据如实标 L2，并把缺的是哪一条写在判据列里，采不采用由读者按自己的风险偏好决定，判据本身不因这句说明而放宽。

另有一条评级规则，全节通用：**合并方向取最弱子项**。本节把「LLM 评估」与「Agent 评估」分成两行而不是一行，理由是它们的可规划性差一个量级：前者今天就能接进流水线，后者要先有能重置的环境。

**本节没有一行达到 L1。** 十条 L2 全都卡在同一条上：**②（第三方非厂商公开生产案例）拿不出**。其中判据列写「①③ 满足」的有五行——在线 A/B 与方差缩减、Interleaving 与多臂老虎机、因果推断工业化、LLM 评估基准与公开排行榜、LLM-as-Judge 与偏差校正；写「①③ 大体满足」的另有五行（Agent 评估基准、检索增强应用评估、持续评估与漂移监控、多模态评估、评估即服务）——它们要么 ③ 有一处明确不稳，要么判定标准尚未形成共识，两种情形都落回 L2 的定义。Agent 评估基准最典型，也最容易被误读：同一基准换一个 harness 后成功率就不再可比，所以它不在「①③ 最干净」的那一组里——这与 5.2.3 的判据是同一条。判断某条方向是不是 L1，不要看它由多少厂商支持，看第 ② 条的材料是不是**发布方之外的机构**给出的：单靠厂商与建设方自述，无论多少条，都还是 L2。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它那一类的正式发布物能不能找到——方法类看正式论文与版本化实现，能力项、产品与基准类看 GA 与正式 release note？找不到 → L3。
2. 厂商之外的证据能不能找到？找不到 → L2。
3. 接口明年会不会变？会变 → 至多 L2。

第 3 句在本主题特有的失手方式，是把「题目集版本」当常量：公开基准的题目集会随版本更新，同一模型的分数因此**不能跨版本比较**。判定方法是看基准发布页有没有记录题目集版本与评测日期，而不是看榜上名次。

三个常见误判，排路线图时最容易踩：

- **把「有跑分」误当成「有评估」**：跑分是别人设计的题目，评估是你自己的业务分布与失效代价。
- **把「裁判一致度实验」误当成「裁判可靠」**：公开实验给出的一致度，是与某一批人类标注比较的结果；换一批标注者、换一个裁判版本，这个数字就变。
- **把「自动」误当成「省人」**：评估自动化省掉的是执行工时，不是判断责任——裁判偏差要人做锚点，评测集要人维护（5.5）。

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 实验这一层：AI 一寸都没动

- **旧做法与它的卡点**：实验的卡点不是模型，而是**样本量的物理下限**。要把给定大小的效应分辨出来，所需样本与效应量的平方成反比、与指标方差成正比（主文件 §2.2 的样本量公式）；流量却是给定的，于是小业务要么等上数周，要么把结论建立在噪声上。主文件 §1.2 的痛点 2（周期长）与痛点 3（流量不够）说的都是这一条。
- **AI 改变了什么机制**：没有。方差缩减、Interleaving、多臂老虎机背后都是统计与算法：CUPED 用预实验协变量做调整、Interleaving 用配对比较替代组间比较、bandit 用自适应分配替代固定分配。三者都不需要模型，也不因模型变强而变准。AI 在本层唯一站得住的位置是实验**之前**的假设与候选生成、实验**之后**的异常归因——这两件是接口改良，不是架构变化。
- **由此得到的**：因为 CUPED 减掉的是「实验前就能解释的那部分方差」，缩减比例只由协变量与指标的相关系数决定（`1-ρ²`，见主文件 §2.2），**所以**同样的流量能分辨更小的效应，等价于把实验周期按相近比例压下来；**又因为**随机化的合法性不来自任何模型，**所以**在线实验结论的可信度不会因为链路上多了一个 LLM 而改变——这一点值得明说，因为本节其余方向都做不到这么干净。
- **由此付出的**：协变量必须满足「与实验无关、且不受本次处理影响」，选错就把偏差引进来，而它不会以报错的形式出现——指标照常显著，只是数不对；Interleaving 衡量的是排序偏好，从偏好到业务指标（成交、留存）之间隔着一层未被验证的转换假设，因此它适合做筛选、不适合做上线判据；bandit 用「少看一部分用户」换效率，代价是因果解释变弱——结论依赖自适应分配策略本身，换一个探索比例就能得到不同结果。
- **证据与来源**：【公开】CUPED 的原始方法论文（Microsoft，WSDM 2013）；【公开】Interleaving 的配对比较方法（信息检索方向，2008 年前后发表于 CIKM / SIGIR / WSDM 系列会议；可按 "interleaving" 与 "retrieval evaluation" 组合检索核验具体篇目与年份）；【公开】各实验平台把流量分层、方差缩减、SRM 检测列为 GA 能力（能力名与配置项名称各平台不同，以各自官方文档当前版本为准，不要按产品名对号）。这几条只证明机制存在且接口稳定，不证明谁的实验因此快了多少——② 拿不到。
- **成熟度**：**L2**（与 5.1 表「在线 A/B 与方差缩减」行一致）。本节的「Interleaving 与多臂老虎机」行同为 **L2**，判据同上：①③ 满足、② 不满足。

| 手段 | 机制 | 失效条件 |
| --- | --- | --- |
| 流量分层 | 同一用户在不同实验层独立分流、互不干扰 | 同一层的实验共享流量，层划错了会互相污染 |
| CUPED | 用预实验协变量减掉可解释方差 | 协变量受本次处理影响，或与指标无关（缩不动） |
| Interleaving | 同一用户看两个排序，做配对比较 | 结论是排序偏好，不等于业务指标 |
| SRM 检测 | 比对实际分流比例与预期比例 | 只在实验开始时跑一次，跑完不看 |
| Bandit | 把流量自适应分配给表现好的组 | 收敛后回头看指标，得到的是选择偏差而非效应 |

**怎么判断 CUPED 的协变量合格**（三项都不需要新工具）：它必须在实验开始前就已确定；它不能是本次处理的结果；抽查它与目标指标的相关性——相关系数接近零的协变量缩不动方差，上了等于没上。三项里第二项最常被忽略，也最致命：拿实验期内的行为做协变量，等于把处理效应的一部分减掉了。

#### 5.2.2 裁判这一层：把「做出判断」从人手里接过来

- **旧做法与它的卡点**：摘要、对话、报告、生成 SQL 这类开放输出没有唯一正确答案，只能用相似度指标或人来判。相似度指标（BLEU / ROUGE / BERTScore 一类）衡量的是「像不像参考答案」，对「对不对」几乎没有约束；人工评审的问题是**边际成本**——一人一条要分钟级【经验】，于是评审只能抽小样本（百条量级【经验】），结论在项目结束时出一次，之后再没人跑。
- **AI 改变了什么机制**：把做出判断的承担者从人换成了模型代理。这是本节唯一一处真正的机制变化：它改的不是接口，是**判断的边际成本**，从人力分钟级降到一次模型调用【经验】。成本一变，评估能挂的位置就变了。
- **由此得到的**：因为单次判断的成本可以忽略，**所以**评估第一次能挂在每次提交（CI 门禁）与每次线上变更（回归监控）上，评测集也不必停在百条量级；**又因为**判分不再依赖人类专家的时间，**所以**原来因为「没人愿意评」而长期无数据的维度（格式遵循、长尾意图、拒答是否恰当）第一次有了数——评估的覆盖面因此从「一个主指标」扩到「一组行为约束」。
- **由此付出的**：裁判有系统性偏差，而且**不能用同一类裁判自证**（同族模型偏袒自己的输出）；裁判版本一升级，历史分数就不可比，于是评估结论必须与裁判版本一起归档，否则你得到的是一条折线而不是趋势；把待评内容送进裁判，等于多了一条数据出境边界，而这一步通常没有走过数据审批。
- **证据与来源**：【公开】MT-Bench 与 Chatbot Arena 的裁判方法论文（2023，含「强模型裁判与人类偏好一致性」的公开实验——一致度数字随裁判版本与题目集变化，本节不引用具体值）；【公开】HELM（Stanford，2022 年起发布，场景与题目集随版本更新）。② 不满足：能充当第三方生产案例的公开材料，本节给不出来源与统计口径。
- **成熟度**：**L2**（与 5.1 表「LLM-as-Judge 与偏差校正」「LLM 评估基准与公开排行榜」两行一致），判据同为 ①③ 满足、② 不满足。

裁判的四类偏差与各自的检测方法（都不需要内部数据就能做）：

| 偏差 | 表现 | 怎么测 |
| --- | --- | --- |
| 位置偏差 | 同样两条答案交换顺序，胜率翻转 | 把候选对调重跑一遍，看结论是否一致 |
| 长度偏好 | 更长答案胜率偏高 | 按答案长度分层看胜率，长度与得分是否同向 |
| 自我偏好 | 同族模型给自己的输出打分更松 | 换一个家族的裁判重跑同一批样本，看排名是否稳定 |
| 题目泄漏 | 裁判见过题目（训练数据覆盖） | 用新题与公开旧题分别跑，看分数差有多大 |

| 用法 | 什么时候可以 | 什么时候不行 |
| --- | --- | --- |
| 做筛选（从十个方案里挑两个） | 差异明显、样本量足够 | 差异接近噪声水平时，裁判的排序不可信 |
| 做回归门禁（这一版不许比上一版差） | 裁判版本与评测集都固定 | 中间换过裁判或换过题目集，比较就断了 |
| 做对外结论（发布用数字） | 有人工锚点标注可比 | 只有裁判分数，没有人类基线 |

**第一批评测集的建法**（不需要任何新采购）：

- 从**真实失败样本**里取样，不要从「应该会问什么」里编题：线上差评、被转人工的会话、用户换个说法重问了一遍的问题，是成本最低的题源。
- 每题写清**判定标准**，并把判不了的题先剔除——它会用裁判的方差吃掉全部信号。
- 第一批取百条量级【经验】，其中留二十条上下【经验】作人工锚点，裁判只在锚点上校准【经验】。
- 评测集与裁判一起打版本号并写进变更记录；改评测集时先把旧题重跑一遍，看旧结论是否还成立。

**八条评估维度落到哪里**——每条都要有落点，因为「落到哪一行、由谁判分」直接决定它能不能被自动化：

| 评估维度 | 落到本节的哪一行 | 判分主体 |
| --- | --- | --- |
| 准确性（事实性、推理能力） | LLM 评估基准与公开排行榜 / 自建评测集 | 有标准答案的标签；开放部分靠裁判 |
| 安全性（有害输出、偏见） | 公平性与可解释性评估（L3）+ 合规门禁 | 规则 + 分组指标 |
| 有用性（任务完成度） | Agent 评估基准（5.2.3）的完成判据 | 环境校验 |
| 流畅性（语言质量） | LLM-as-Judge 与偏差校正 | 裁判（需人工锚点） |
| 鲁棒性（对抗样本） | 自建对抗样本集，无对应产品行 | 标注 |
| 多语言能力 | 按语种分层抽样的自建评测集 | 标签 / 裁判 |
| 长上下文能力 | 按上下文长度分段的评测集 | 标签 / 裁判 |
| 多模态能力 | 多模态评估（L2） | 代理指标 + 裁判 |

八条里有四条主要靠裁判（流畅性、多语言、长上下文，以及准确性里没有标准答案的那部分），另外四条不靠裁判——安全性靠规则与分组指标，有用性靠环境校验，鲁棒性靠标注好的对抗样本，多模态靠代理指标。后四条不会因为裁判变强而自动获得，规划时不要把它们算进「评估自动化」的收益里；其中鲁棒性一条在本节连对应的产品行都没有，只能自建。

#### 5.2.3 Agent 评估：单元从「一个答案」变成「一条轨迹」

- **旧做法与它的卡点**：把单次输出打分当成能力结论。卡点在**评估单元选错了**：Agent 的一次执行是一条轨迹（思考 → 调工具 → 读结果 → 再调），同一模型同一任务跑两次，中间的工具调用次数与环境状态就可能不同，成功率本身是随机变量，而不是模型的属性。
- **AI 改变了什么机制**：改变了评估单元的粒度——从「输出」变成「轨迹 + 环境状态」。连带改变的是复现的定义：从「固定随机种子」变成「固定环境快照 + 记录每步动作与工具返回值」。
- **由此得到的**：因为环境可以被重置到同一初始状态，**所以**「同一任务采样多次」才成立，成功率才能被报成带区间的数而不是一个点；**又因为**轨迹里天然带着步数与调用次数，**所以**评估维度能从「对不对」扩到「多贵、几步、错在哪一类」——后三项比成功率更直接地决定它能不能上生产。
- **由此付出的**：环境维护成本前置——沙箱要能重置、依赖要冻结、外部服务要可控；这是基准从论文变成回归工具的真正门槛，也是多数团队做不下去的原因。轨迹级评估的方差极大，样本量不足时最容易给出过早结论。最后一个代价更隐蔽：基准里的工具权限是固定的，而生产事故多来自权限、超时与长尾接口，于是「基准分数高」与「生产可用」之间没有必然联系。
- **证据与来源**：【公开】WebArena（2023 年论文，Web 任务环境）、SWE-bench（ICLR 2024，代码修复任务）、AgentBench（ICLR 2024）、GAIA（Meta，2023–2024 年间发布，以论文库当前版本为准）、ToolBench（2023）、OSWorld（2024）、AndroidWorld（2024）的论文与公开榜单；【公开】SWE-bench Verified（2024）这类由发起方之外的机构做人工校验后发布的子集——它是**校验**，不是生产案例，不能充当判据 ②。
- **成熟度**：**L2**（与 5.1 表「Agent 评估基准」行一致），判据：①③ 大体满足，② 不满足，且 ③ 有一处不稳（换 harness 后成功率不可比）。

```text
Agent 评估的可复现性由三样东西决定（缺一样，两次跑就不同）
   环境快照   初始页面 / 数据库 / 文件系统状态，可重置到同一版本
   工具契约   每个工具的参数、返回值与超时，冻结在同一版本
   轨迹记录   每步的动作与观测落盘；失败样本保留原始轨迹

判定方法：同一模型、同一任务、同一环境，连跑 5 次以上【经验】
   结果全同   → 任务足够确定，单次结果可作参考
   结果不稳   → 报成功率必须带采样次数与区间，单次差值不作结论
   报不出方差 → 说明还没跑够，此时任何「A 比 B 强」都不可信
```

#### 5.2.4 因果推断工业化：把高维混杂交给 ML 拟合

- **旧做法与它的卡点**：不能随机化的场景（补贴、策略、广告投放、风控规则）只能看观察数据，办法是双重差分、倾向得分匹配、工具变量。卡点在**高维混杂**：混杂变量一多，人指定的回归形式就变成猜测，结论对设定高度敏感——换一个函数形式，效应量就换一个数。
- **AI 改变了什么机制**：把干扰函数的拟合从人指定的模型换成 ML（残差化 + 交叉拟合）。机制上做的是**交出建模自由度、用正交化换回无偏性**：先用 ML 把结果与处理分别对协变量回归，再拿残差做回归。
- **由此得到的**：因为正交化只要求干扰函数的收敛速度慢于目标参数（这正是该方法成立的弱条件），**所以**高维特征第一次能被整块放进模型，不必手工挑协变量；**又因为**协变量里的非线性关系被 ML 吸收掉，**所以**「看起来是相关、残差化后归零」的伪效应会显形——它的价值一半在估计效应，一半在证伪效应。
- **由此付出的**：交叉拟合的实现细节（样本如何分割、分几折）会影响结果，漏掉它结论会出现向下的偏误；工具从公式换成 ML 之后可解释性下降——业务方问「为什么是这个数」，你能给出的只有模型与协变量清单；最重要的一项代价是它不解决最关键的假设：「无未观测混杂」不可检验，工具再先进也不能把观察数据变成实验数据。
- **证据与来源**：【公开】Double / Debiased Machine Learning 的方法论文（Chernozhukov 等，2018，Econometrics Journal）；【公开】Causal Forest 与异质处理效应估计（Wager & Athey，2018，JASA）；【公开】合成控制法（Abadie 等，JASA 2010）；【公开】双重差分估计的标准误与序列相关问题（Bertrand / Duflo / Mullainathan，QJE 2004）与处理时点交错下的修正（Goodman-Bacon，Journal of Econometrics 2021）。② 不满足。
- **成熟度**：**L2**（与 5.1 表「因果推断工业化」行一致），判据：①③ 满足、② 不满足。

**把适用条件写进结论**——这一步不做，工具会把观察数据的结论包装得像实验结论：

| 结论里必须写 | 缺了会怎样 |
| --- | --- |
| 处理组与对照组的定义（谁算处理、从哪一刻算开始） | 同一份数据能被解释成两个不同的效应量 |
| 协变量清单与交叉拟合设置 | 换一组协变量就换一个数，且没人说得清为什么 |
| 「无未观测混杂」这一条不可检验 | 读者会把观察结论当成因果结论去用 |

这三项都是文字工作，成本很低，但它们是观察数据结论唯一能自证的部分。

**表中其余方向为什么停在这里**：

- **检索增强应用评估（L2）**：它把端到端拆成「检索质量」与「生成质量」两段，机制上让失败可定位到段——检索一段的常用指标是 Recall / Precision / NDCG，生成一段靠裁判或规则。可用，但有两处必须自己定：一是「忠实性」在不同框架里的定义不同（是否允许外部知识、是否只要求不矛盾），二是跨文档与多跳问题需要路径级标注——GraphRAG 一类报的检索准确率与推理准确率就属此列，没有路径级标注口径就复现不了，公开材料因此稀少。
- **持续评估与漂移监控（L2）**：机制是「把评估从一次性作业变成周期性任务」，可用部分（评估进 CI、漂移告警）接口已经稳定；「自动重训」不在此列——重训的触发条件本身是可争议的判定，把它自动化等于把判定交给阈值。
- **多模态评估（L2）**：CLIP Score / FID 一类是**代理指标**，用一个模型的特征距离代替人的判断。代理指标适合做回归门禁（这一版不许比上一版差），不适合做验收标准，因为它是可以被优化的；FID 一类还对样本量与预处理敏感，跨论文的数字不可比。
- **评估即服务（L2）**：机制是把评估基建外包，代价是评测集、裁判版本与结论都经过第三方——对内部业务而言，评测集本身就是敏感资产。
- **推理过程评估（L3）**：① 按能力项类核——论文与开源实现有，作为能力项的正式发布没有；更根本的是过程奖励要求**步骤级标注**，而公开的步骤级数据集规模远小于结果级，没有步骤标注，这一方向无法启动。
- **公平性与可解释性评估（L3）**：义务性文本证明的是「要求存在」，不证明「方法存在且可核验」。可做的是分组指标监测与数据侧的分层统计，不是「公平性达标」的结论。
- **AI 原生评估（L3）**：合并叙事，其子项（AI-as-Judge、评估即服务、持续评估、推理过程评估、公平性评估）在本表中分别是 L2 与 L3，按最弱子项取 L3；这个说法本身给不出判据，所以它不能当能力清单用。

### 5.3 与本主题既有栈的接口在哪

评估不是独立系统：它的输入分别来自建模、实验与应用三层，写清接口边界比写「与 X 结合」有用得多。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 建模侧 ↔ 离线评估 | 模型与特征以「版本号」穿过边界；评估记录的输入是版本，不是「当前线上模型」 | 建模侧（谁发版谁提供版本号与训练数据快照） | 需自建：多数团队的离线指标与模型版本没有强绑定 |
| 实验平台 ↔ 指标与埋点 | 以「分流键 + 事件流 + 指标定义」为接口 | 实验平台侧（SRM 由平台检测，不靠人眼看比例） | 平台侧已有能力；指标口径要靠指标层统一 |
| 应用 ↔ 裁判 | 以「待评内容 + 裁判提示 + 裁判模型版本」为接口 | 应用侧（谁引入裁判谁负责锚定与归档） | 需自建：裁判版本不进归档，历史分数就不可比 |
| Agent 运行环境 ↔ 评估 | 以「可重置的沙箱 + 工具契约版本」为接口 | 评估侧（谁报数谁保证环境可重置） | 需自建，且这是 Agent 评估真正的门槛 |
| 检索侧 ↔ 检索评估 | 以「查询集 + 相关性标注」为接口 | 检索侧（谁改检索谁跑回归） | 需自建：标注是人工成本，外包不掉 |
| 数据目录 / 血缘 ↔ 评测集与结论 | 以「评测集版本 + 裁判版本 + 结论发布记录」登记为资产条目 | 评估侧（谁发布结论谁登记版本） | 需自建：结论不登记，半年后没人说得清这个数是哪一版 |

表里只有半行属于既有能力（实验平台侧的 SRM 检测与指标口径统一），其余都要自建。**失败归属必须在设计阶段写清**，否则会退化成扯皮：线上指标变差了，是模型变了、裁判变了，还是评测集换了？三件事都能解释同一个现象，而它们分属三个团队。唯一能让争论停下的是把这三样登记成资产——这也正是「评估即服务」在本主题只能记 L2 的原因：外包出去的恰好是这三样。

**判定这张表有没有被用起来**：每个季度核对两个数——这一季有多少条结论能追到「模型版本 + 裁判版本 + 评测集版本」，有多少次方案改动是因为评估（而不是评估在上线后被用来解释）。两个数都是零，说明表还停在文档层面。

还有一件容易漏的事：「谁负责失败」那一列写的是**修复责任**，不是**损失归属**。按表，六行的修复责任分属建模侧一行、实验平台侧一行、应用侧一行、评估侧两行（Agent 运行环境、数据目录 / 血缘）、检索侧一行；但无论落在谁头上，损失最后都由业务承担——评测集过时导致结论不成立，资源按错的结论排了下去；裁判版本没归档导致趋势不可比，决策层拿着一条折线做判断；环境不可重置导致 Agent 结论不可信，代价落在上线后的用户身上。把这三条写进接口表的用途不是分工好看，而是让「谁来修」与「谁担损失」在事故发生前就分清。

**引用纪律**：本节最容易被误引的三类数字是「裁判与人类的一致度」「Agent 成功率」「实验提升幅度」——它们都随裁判版本、采样次数、题目集版本变化。可核验的做法是：回到原文找这三个条件，缺一个就不要引用这个数。关于 5.4 的著录口径：论文与方法类给到可检索的篇名或方法名 + 年份（已在会议或期刊发表的写上会议或期刊名），基准与工具类给到名称 + 年份（发布方能确定时一并给出），两类都可按篇名或方法名检索核验当前版本；**官方文档与 release note 一类只给能力名与文档位置，不给版本号**——这类文档持续更新，写死单一年份反而误导，请以官方文档当前版本为准。至于定位不到任何公开文档的工程做法，本节一律不列：列一个指不到论文的名字，比留一条空白更糟。

### 5.5 被过度宣传的部分

**「AI-as-Judge 让评估自动化了」**

- *实际是什么*：自动化的是判分的执行，不是判断的责任。裁判偏差、评测集选题、锚点样本标注，一样都没省掉。
- *为什么会这样*：裁判与被评对象同源，评估能力无法自证；一旦「谁对」完全交给模型，评估就失去了独立的证据基础。
- *什么时候它才会成真*：当评估结论能连裁判版本一起归档、且每次改动都有固定的人工锚点可比时——那时「自动化」指的是流程，而不是免责。

**「Agent 基准跑分说明 Agent 能上生产」**

- *实际是什么*：基准测的是封闭环境、固定工具权限下的成功率；生产里的失败多半来自权限、超时、长尾接口与成本失控。
- *为什么会这样*：基准为了可比必须冻结环境，而冻结环境就必然与生产脱节——两者是同一个设计目标的两面。
- *什么时候它才会成真*：当基准发布物里同时给出成本、步数与失败分类，而不只是一个成功率与排名（见 5.2.3 的判定方法）。

**「公开榜单排名可以当作选型依据」**

- *实际是什么*：榜单比的是榜单的题目集；题目集会被训练数据覆盖、会随版本更新，且与你的业务分布无关。
- *为什么会这样*：榜单的激励方向是排名而不是「预测你的场景」，发布方从名次里拿到的收益，与从你的业务里拿到的无关。
- *什么时候它才会成真*：当你的评测集能用同一份裁判协议跑出与业务指标一致的方向时——此时榜单只是外部参照，不是依据。

这三条有一个共同结构：把「执行成本降了」说成「判断可靠性升了」。判断它们何时成真，看的是同一件事——**评估结论里有没有独立于被评对象的那部分证据**。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 评估进入 CI 成为默认做法 | 产品发布说明或流水线模板把评估列为一等对象（有配置项与门禁语义），而不是外挂脚本 | 评估仍是上线前的一次性作业，CI 里只有单元测试与静态检查 |
| 裁判被当作「依赖」管理，版本进归档 | 评估报告里出现裁判模型与提示版本字段，且跨版本分数被明确标注不可比 | 分数继续跨裁判版本直接比较，换一版裁判就要重跑全部历史结论 |
| Agent 评估从「成功率」扩到「成本 / 步数 / 失败分类」 | 基准与内部评估的发布物里出现这三列 | 仍只报成功率与名次，成本靠事后算 |
| 因果推断从研究代码变成实验平台的常规配置项 | 商业实验平台文档把它写成配置与流程（先决条件、诊断项），而不是「联系团队」 | 仍是每个团队各自实现，结论依赖个人实现水平 |

四条都能被**公开文档**证实或证伪，不需要内部数据：

- 第 1 条看流水线模板与产品发布说明，一到两年见分晓。
- 第 2 条看评估报告的字段，一到两年。
- 第 3 条看基准的发布物，两到三年。
- 第 4 条看实验平台文档的能力清单，三到五年。

最值得先盯第 2 条：它是唯一一条**不依赖新产品发布**就能观察到的信号，而且它一旦做不到，其余三条的结论都会失去可比性。

提醒一句：这四条都不是「某产品会不会做」，而是「**判断依据会不会出现在公开文档里**」。前者无法证伪，后者可以逐条核对——这正是本节用成熟度分级换掉趋势清单的原因。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有 A/B 平台但周期长 | 先上流量分层与 CUPED，检查协变量是否会被处理影响（5.2.1） | 平台是否把方差缩减列为默认项 | 不要先上 bandit 换效率，它换掉的是因果解释 |
| 要做 LLM 应用评估 | 用 LLM-as-Judge 建首批评测集，同时固定裁判版本、留人工锚点（5.2.2） | 裁判版本管理是否进入你们的模型依赖清单 | 不要把公开榜单名次写进选型结论 |
| 要评估 Agent | 先解决环境可重置，再谈成功率；报数必须带采样次数与区间（5.2.3） | 基准是否开始披露成本与步数 | 不要用单次成功率的差值下结论 |
| 不能随机化（补贴 / 策略 / 风控） | 用 DML 一类方法估计，并把「无未观测混杂」写进结论的适用条件（5.2.4） | 实验平台是否把因果推断做成配置项 | 不要把观察数据的结论写成因果结论 |
| 有检索增强应用 | 拆开检索与生成两段各自评估，先固定「忠实性」的定义 | 评估框架之间的指标定义是否收敛 | 不要用相似度指标当正确性指标 |
| 刚开始建评估体系 | 先把三件事登记成资产：评测集版本、裁判版本、结论发布记录（5.3） | 有多少结论能追到这三个版本 | 不要把评估交给外部服务后就当结论可用 |

「明确不要做」那一列的共用逻辑只有一句：**本节真正变了的是「判断由谁做出」，实验的随机化与因果的合法性一寸没动**。所以预算应当投在评测集、裁判版本与实验设计这三件确定性工程上；在它们定下来之前，任何「AI 原生评估」的采购都不会带来可度量的收益。

如果只能排一个顺序，按这条走：

1. **先接位置**：把评估接到每次提交上（有评测集与裁判就能做），这一步不需要新采购。
2. **再定版本**：评测集版本、裁判版本、结论记录三样绑定归档；它决定后面所有比较有没有意义。
3. **然后解决环境**：Agent 评估只有在这一步做完之后才谈得上。
4. **最后才谈外包与自动化**：这两类都会改变数据边界与责任归属，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新模型——评测集、裁判归档、锚点标注、环境重置，全是流程与工程。这也解释了本节为什么没有 L1：真正成熟的那部分（随机化、方差缩减、分层）不需要被宣传，而需要被宣传的那部分，还没有成熟到能被第三方核验。

### 5.8 小结

> 本节小结：AI 在本主题上**只改了一条机制**——把「做出判断」从人手里部分交给了模型代理，判断的边际成本因此从人力分钟级降到一次调用【经验】，评估第一次可以挂在每一次提交上；它**没有改变**的是实验的随机化与因果识别：结论的合法性仍然来自实验设计与可辩护的假设，不来自模型。本节没有一行达到 L1，十条 L2 全都卡在「第三方（非厂商）公开生产案例」这一条上；其中 ③ 最稳的五条集中在实验与因果层（在线 A/B 与方差缩减、Interleaving 与多臂老虎机、因果推断工业化）与裁判、基准层（LLM-as-Judge 与偏差校正、LLM 评估基准与公开排行榜）。所以现在该投的是评测集、裁判版本与实验设计，而不是「AI 原生评估」。
>
> 💡 **思考锚点**：挑一条你们最近据它做过决策的评估结论，倒着追三样东西——评测集版本、裁判版本、结论发布记录。本节说判断的边际成本已降到一次调用、评估因此能挂在每次提交上，可这三样里若有一环先断，挂上去的评估就只会反复复制同一个错判；你最先断的是哪一样？
