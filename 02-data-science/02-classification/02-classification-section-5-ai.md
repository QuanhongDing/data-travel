## 5. 前沿演进（AI 时代）

> 原 § 5 共 171 行、列出 5 个演进方向、一批模型与工具名，以及 8 条趋势；本节重写为约 280 行的前沿评估，保留全部 5 个方向与 8 条趋势的去向，并为每个补上机制与可核验判据。

### 5.1 先分清三类「前沿」

同一份清单里藏着时间差。「LLM 当分类器」与「Agent 自动发现类目、自动标注、自动上线」被并列写在一起时，读者会以为它们只差一个工程成熟度：前者今天就能在一个只读场景里跑起来，代价是延迟与账单一目了然；后者目前为止，本节列不出一个可指名的、既不是模型发布方也不是项目承建方的第三方生产案例。按同一份清单排期，前者是一个能验收的试点，后者会变成一个没有人敢签收的项目。

本节给每个方向一个级别，级别由三条可核验判据决定，不由感觉决定：

- **L1 生产可用**：① 已 GA 且有正式 release note；② 有第三方（非厂商、非项目承建方）公开生产案例；③ 接口稳定。三条**全中**才算 L1 —— 可以排进路线图。
- **L2 可试点**：已可用但接口或生态未稳，或仅有厂商 / 建设方自有案例，或只在小规模被验证。可以做 PoC，**不要做核心依赖**。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录，**不要在架构里预留假设**。

这三条判据在本主题下**不做任何修正**，也不会在某个单元格里就地放宽。**第②条是最难满足的一条**：公开材料里「我们用 LLM 做了 X」的绝大多数是**建设方自述** —— 自己做项目、自己写文章，按定义落在 L2。本节对②的要求是：案例来自既不是模型发布方、也不是项目承建方的第三方。**第②条核不到就是 L2**，不存在「准 L1」「L1 的边界案例」这类说法。

**表里没有一行是 L1。** 最接近的是 5.2.1 与 5.2.2 对应的两条（LLM 作为分类器与打标机、免微调与轻量适配）：① 能给出可核验的落点 —— 模型的发布说明里有结构化输出与工具调用这类正式能力；而 ③ 两条都只算**部分** —— 前者的提示词、结构化输出与工具调用三种接口形态仍在并存演进，后者的 embedding 一换版本、下游分类头就要重建（轻适配产物还与基座版本绑定）；缺的还有 ②。按判据它们是 L2，本章不接受「人人都在用」代替「有一个能被指名的案例」。这一点值得停下来想一想：本主题下**门槛最低的两条恰好也是收益最直接的两条**（省掉标注与训练），而那些听起来更颠覆的方向（自动发现类目、自动上线）连第①条都还没有 —— 这说明在这一主题上，「能不能省掉一次训练」比「模型有多强」更接近可用的分界。

**L2 在实际排期上是什么意思**：可以做 PoC，可以把「不改变最终口径」的环节接上去（打标、候选、检索、路由），但不要把它写进对外承诺的能力清单。判据之外还有一条取材纪律 —— 每个方向都会给「读者可以怎么自己核验」，核验顺序固定：先查官方发布说明里有没有这条能力（这是①）；再查有没有**不是发布方**的人写过它在生产中的用法（这是②）；最后看接口有没有变过，一年内改过两次接口的方向，即使前两条满足也只能按 L2 排期。

本节的组织方式与本章 §3.1 一致：先立约束，再谈模式；只是这里的约束换成了**时间** —— 一个方向能不能排进路线图，前提不是它有多先进，而是它的证据能不能被别人按同一套判据复现。这也是本节把「趋势清单」重排为三档的全部理由：清单缺的不是条目，是时间维度。

读本节时守住四条命名与版本纪律：

- **区分产品名与能力名**：「让模型输出枚举标签」在不同平台上是不同名字的接口（结构化输出、工具调用、枚举约束一类），不要把它当成某个产品的专属概念。
- **区分已发布与路线图**：模型版本迭代快，能力边界以各家官方文档**当前版本**为准；本节不写版本号，只写可核验的区间表述。
- **区分「模型能分类」与「分类能上线」**：前者是一次调用，后者包含校准、阈值与成本矩阵（[§ 3 §3.5](02-classification-section-3-sec3.md) 的代价矩阵推导与「忽视校准」），以及冻结口径下的回归集（[§ 7 §7.3.4](02-classification-section-7-sec7.md) 的「标签口径的可冻结性：能不能回归评估」）——把前者当后者，是本主题最常见的高估。
- **区分生成式标签与可聚合的概率**：LLM 给的是枚举标签加置信度，专用分类器给的是可校准的概率；报表、阈值与代价矩阵只能建立在后者之上。

### 5.2 演进方向逐条拆解（核心节）

每个方向都按同一组问题写：旧方案卡在哪、AI 改变了哪个机制、由此得到什么、由此付出什么、有什么证据、成熟度几级。**机制一栏是本节的判别器**：只换了前端的，这里会直接写「这是接口改良，不是架构变化」。

四个方向按「离可用有多远」排：5.2.1 与 5.2.2 在前，因为它们的失败模式可枚举（标签口径漂了、embedding 换版本了），**改错的代价可控**；5.2.3 需要额外模态的数据与合规口径；5.2.4 涉及在线链路的位置决策，错了会同时影响成本与口径。这个顺序与 §3.1 的约束表一致 —— 先看约束，再谈模型。

#### 5.2.1 LLM 作为分类器与打标机

- **旧做法与它的卡点**：专用分类器每加一类都要标注、训练、发布，而标签空间可能按周变更（[§ 3 §3.2.4](02-classification-section-3-sec3.md) 的约束）。卡点很具体：一次训练-发布周期是周级到月级，**业务想加一个类目，要等一个迭代**；冷启动与长尾类目更是没有样本可标。
- **AI 改变了什么机制**：判决信息的载体从**标注样本**移到**预训练语料**（§3.1 的载体表）。接口也变了：从「输出一个可校准的概率」变成「输出一个受枚举约束的标签」。新增类目从「重新训练」变成「改枚举值与提示词」—— 这是**判决信息来源与接口形态的双重变化**，不是分类任务的重新定义。
- **由此得到的**：因为类别语义已在语料里，所以新类目上线周期从训练-发布周期压到一次提示词改动，长尾类目第一次有了可用的兜底；因为输出可以被约束在枚举内，所以它可以被聚合、被统计、被回归评估 —— 但这条成立的前提是**先有冻结的 Golden Set**（[§ 7 §7.3.4](02-classification-section-7-sec7.md)）。打标机路线把这条机制用在了正确的位置：LLM 只离线产标签，上线仍是可评估的小模型（§3.2.4）。
- **由此付出的**：
  - ① **口径难以冻结**：同一输入不同调用可能给出不同标签，而分类系统的长期可维护性恰恰取决于「同一输入稳定给同一标签」（§7.3.4）。没有 Golden Set 与越界拒答时，错例无法定位、无法回归。
  - ② **私有口径会退化**：类别边界由业务私有定义决定时，零样本退化成按类名字面猜（§3.2.4 的失效点）；此时必须补少样本示例与固定评测集，而不是换更大的模型。
  - ③ 单次调用的成本比本地分类器高三个量级以上、延迟高 1~2 个数量级【经验】（成本量级推导见 [§ 7 §7.3.3](02-classification-section-7-sec7.md)），因此进不了低延迟主路径；能进主路径的只有「打标机」这种把成本挪到离线的形态。
  - ④ **换版本等于换口径**：模型迭代会让标签分布整体漂移，一次版本升级要重跑整套回归集；这是持续成本，不是一次性成本。
  - ⑤ 混合架构的价值来自**流量的长尾分布**，长尾占比上升时成本与延迟同时上涨，而被判定为「长尾」的比例越走越高这件事不会自己暴露（§3.2.5 的失效点）。
  - ⑥ **评测集会被自己污染**：用 LLM 产出的标签去评测 LLM，容易形成自我确认的循环 —— 指标稳定上升，而它衡量的是「与上一次的自己有多像」。判定方法是让 Golden Set 里有相当一部分来自人工标注，且这部分单列统计。

**打标机为什么是本主题最常见的折中**：它把 LLM 放在离线侧，用 LLM 批量产标签，用这些标签训练一个可评估、低延迟、概率可校准的小模型上线（§3.2.4 的第三种形态）。这一步在机制上做的事是**把不确定的判决换成一次性的标注投入**：口径仍然要在人手里冻结一次，但冻结之后的每一次推理都回到确定性函数上，回归评估、阈值标定与成本核算全部重新成立。代价是它放弃了「新类目零样本可用」这个最大卖点 —— 类目一变，又要重新打标与重训，只是这一次的重训成本比人工标注低得多。

| 工程模式 | 模型承担什么 | 必须由谁承担 |
| --- | --- | --- |
| 纯提示（零样本） | 给出枚举内的标签与置信度 | 类目定义、Golden Set、越界拒答 |
| 少样本示例 | 从示例里对齐口径 | 示例本身的正确性与代表性 |
| 结构化输出 / 工具调用 | 保证输出落在枚举内、可解析 | schema 的版本管理与兼容 |
| 多次采样投票 | 降低单次波动 | 成本核算与「投票后仍不一致」的处置 |
| 离线打标 + 小模型上线（打标机） | 批量产标签、覆盖长尾 | 口径冻结一次、样本库治理、回流监控 |

- **判定方法**：
  - 判断一个「LLM 分类」方案能不能上：先问它的 Golden Set 在哪、口径版本谁签。答不上来，它现在只能做候选，不能做结论。
  - 判断该不该换模型版本：把当前版本与候选版本在同一份 Golden Set 上跑一遍，看**标签一致率**（而不是准确率）。一致率低说明口径会跟着版本漂。
  - 判断该不该走混合架构：先统计类目频次分布。头部集中的场景里，混合架构省下的钱抵不过多一条链路的复杂度。
  - 判断它是「架构变化」还是「接口改良」：看判决权是否被交出去。模型只把问题翻成枚举标签、口径仍由人冻结的，是接口改良；模型自己决定类目集合与边界的，才谈得上架构变化 —— 而后者在本节没有立足点。
- **证据与来源**：【公开】把分类输出约束到枚举的两条工业接口是结构化输出与工具调用（可按 OpenAI Function Calling、Anthropic Tool Use 一类官方文档名核验）；【公开】免提示词的少样本路线见 SetFit（Tunstall et al., "Efficient Few-Shot Learning Without Prompts", 2022，§3.2.4 已引用）；2024 年前后有若干对照评测 LLM 与专用分类器的公开工作，本节不点名转述（原清单里的「LLM-as-Classifier Benchmark」只有简称、没有可定位的论文标题），读者可按 "LLM as a classifier"、"LLM vs. fine-tuned classifier" 一类关键词自行检索核验。关于「LLM 分类准确率超过专用模型多少个百分点」的说法，本节不转述 —— 结论随评测集与口径定义变化。
- **成熟度**：**L2**（① 有；② 缺 —— 本节列不出既非模型发布方、也非承建方的第三方生产案例；③ 部分 —— 接口形态仍在并存演进）。升级到 L1 的条件是可观察的：出现一份由第三方发布、写清标签口径、Golden Set 构造方式与成本条件的生产材料。

#### 5.2.2 免微调与轻量适配：把「训练」换成「复用 + 轻适配」

- **旧做法与它的卡点**：想得到一个分类器，就要有标注、有训练、有上线；换一个业务域要重来一遍（§3.2.3 的深度学习特化需要足够标注量）。对中小数据量与高频迭代的场景，这套流程的固定成本压不下来。
- **AI 改变了什么机制**：判决信息的载体从**任务标注**移到**预训练表示**。三档复用的程度不同：embedding + 轻分类头复用表示、只训一层映射；LoRA / Adapter 类轻适配复用模型、只训少量参数；表格基础模型直接把「先验」装进模型，连训练环节都省掉（§3.3 已把它列为小样本表格任务的候选）。改变的是**每次迭代的边际成本**，不是分类问题的结构。
- **由此得到的**：因为分类头只学一个低维映射，所以迭代的边际成本从「一次训练 + 一次发布」降到「一次轻适配」；因为 embedding 可以预计算，所以推理延迟与调用量解耦，扩容靠缓存而不是靠加机器；因为表格基础模型把先验前移到模型里，所以百级以下样本的表格任务可以不训练直接出结果 —— 这一点在 §3.3 的决策表里已经作为小样本候选出现。
- **由此付出的**：
  - ① **embedding 版本是最容易被低估的依赖**：向量空间一换，历史样本、分类头与阈值全部要重建；这不是升级，是重做。
  - ② 收益上限由「预训练表示与你的域的距离」决定：域差大时它不如自建小模型，而这件事在投入前很难预测。
  - ③ 组件变多、可控性变少：embedding 服务、向量缓存、分类头服务各一份，出问题时先要定位是表示漂了还是头过拟合了。
  - ④ 表格基础模型有适用门槛（样本量、特征数、类别数），超出后要退回 GBDT；把它当默认值就是把约束丢掉了。
  - ⑤ 「小模型复兴」的论证通常来自特定评测集：同一个结论换到你的标签口径上不复现时，团队会误判为工程问题。

| 复用程度 | 复用的是什么 | 每次迭代的成本 | 主要代价 |
| --- | --- | --- | --- |
| embedding + 轻分类头 | 预训练表示 | 训一层映射 | 换 embedding 版本即重做 |
| LoRA / Adapter 轻适配 | 模型主体 | 训少量参数 | 适配器与基座版本绑定 |
| 表格基础模型（免训练） | 模型内的先验 | 一次前向 | 有适用规模门槛 |

- **判定方法**：
  - 判断该不该上 embedding + 分类头：先用同一份数据同时跑「该方案」与「GBDT 基线」，只有台面上更优且延迟可接受时才换。
  - 判断轻适配能不能替代全量微调：固定基座版本做一次对照实验；基座一换，之前的结论作废。
  - 判断表格基础模型适不适用：先看样本量与特征数是否落在它的适用区间，再看类别数；都超出就回 GBDT。
  - 判断方案是否可迁移：问一句「Embedding 服务哪天换了默认模型，我们要做哪些事」。答不上来就是把关键依赖放在了别人的默认值上。
  - 判断轻适配值不值得：先看「每一版模型要迭代几次」。只迭代一次的场景用全量微调或干脆用 GBDT；要反复迭代才有复用的优势。
- **什么时候它只是接口改良**：如果这套轻适配只是为了少写几行训练代码、而标签口径与评估方式都没变，那它是工程效率的改良，不是架构变化 —— 判断标准仍然是「判决信息的载体变了没有」。
- **证据与来源**：【公开】TabPFN（Hollmann et al., "TabPFN: A Transformer That Solves Small Tabular Classification Problems in a Second", ICLR 2023；§3.3 已引用）；【公开】SetFit（Tunstall et al., "Efficient Few-Shot Learning Without Prompts", 2022）；【公开】LoRA（Hu et al., "LoRA: Low-Rank Adaptation of Large Language Models", 2021）与 QLoRA（Dettmers et al., "QLoRA: Efficient Finetuning of Quantized LLMs", 2023）为公开发表方法（两篇均先以 arXiv 预印本公开，会议与卷期请按论文标题核验）。关于「成本降低 90%+」「参数量只有 10MB 级别」这类比例与规模，本节不转述 —— 它们强依赖基座、批量与硬件条件。
- **成熟度**：**L2**（① 有；② 缺；③ 部分 —— embedding 版本变化会让下游重建，轻适配产物与基座版本绑定）。

#### 5.2.3 多模态分类

- **旧做法与它的卡点**：图文不符的违规要文本模型与图像模型各判一次，两者冲突时**没有仲裁者**（[§ 6 §2.3](02-classification-section-6-sec6.md) 的短视频审核案例正是这个卡点）；而「图文是否一致」本身是判别信号，单模态模型结构上看不到它。
- **AI 改变了什么机制**：把两种模态投影到**同一表示空间**（对齐式双塔，可用类目名称充当文本端），或让一个模型同时看两种输入（融合式）。判决信息从「某个模态内部」移到「模态之间的一致性」—— 这是**判决信息来源的位移**，不是分类器的替换。
- **由此得到的**：因为对齐在预训练阶段完成，所以新类目可以只用类目名称作为文本端输入，不必为每个类目准备图像样本（§3.2.4 引用的图文对齐路线）；因为冲突可以被显式判定，所以「图说正常、文说违规」这类样本能被单独挑出来，交给更贵的路径或人工 —— §6 的案例用的正是这个机制：**只对分歧样本调用大模型**，把昂贵的容量留给真正难判的样本。
- **由此付出的**：
  - ① **类目名的写法变成超参**：文本侧描述换个说法，判决就可能变；「类目名怎么写」从此是需要维护的资产。
  - ② 融合式模型的单次成本与延迟比对齐式双塔高 1~2 个数量级【经验】，只能用在被挑出来的样本上，因此它的价值取决于分歧判定准不准。
  - ③ 模态缺失是常态（有文无图、有图无文），必须有降级路径，否则线上会出现「因为缺一个模态所以打不出标签」。
  - ④ 对齐的失败模式是「看起来都对」：在细粒度类目上它退化成粗粒度判断，而这一类错误在抽样里很难被发现。
  - ⑤ 合规面翻倍：同一份样本同时受图像与文本两套审核与删除要求约束，删除时要两处一起动。

| 路线 | 判决方式 | 适用 | 代价 |
| --- | --- | --- | --- |
| 对齐式双塔（零样本） | 两路各自编码后比相似度 | 类目语义为主、要求低延迟 | 类目名措辞影响大；细粒度判断弱 |
| 跨模态融合 | 一个模型同时看两路输入 | 需要判定跨模态矛盾、可接受更高单价 | 单价与延迟最高，只适合分歧样本 |

- **判定方法**：
  - 判断该不该上多模态：先看「单模态判定冲突」的样本占比。占比极低时，多模态是净成本。
  - 判断对齐式还是融合式：先看冲突样本量。量大且要低延迟用对齐式，量小且要求精度用融合式（只对分歧样本调用）。
  - 判断类目描述是否稳定：把类目名换一种写法重跑一遍，看标签一致率。一致率低说明这条链路还依赖措辞。
- **证据与来源**：【公开】图像-文本对齐支撑零样本分类（Radford et al., "Learning Transferable Visual Models From Natural Language Supervision"（CLIP）, ICML 2021）；【公开】跨模态融合路线（Alayrac et al., "Flamingo", NeurIPS 2022；OpenAI, "GPT-4V(ision) System Card", 2023）—— 与 §3.2.3 的引用一致；视觉骨干一类的定位见 5.4 的自行核验线索（提供表示或分割，不直接给分类口径）。本节不转述具体识别率或分歧样本比例。
- **成熟度**：**L2**（① 有；② 缺；③ 部分 —— 各家的图像 / 视频输入能力、限额与接口形态不同）。

#### 5.2.4 路由与检索增强：把类目定义和判决成本挪到运行时

这一节合并了原文件的两个方向（Agent 路由、RAG / GraphRAG 增强分类），因为它们的机制是同一件事：**判决所需的信息与判决本身的成本，从模型内部挪到了运行时链路上**。前者把「走哪条路」变成一个分类问题，后者把「类目怎么定义」变成一次检索。

- **旧做法与它的卡点**：类目定义写死在训练数据里，边界含糊时（「科技」与「AI」）只能靠标注者的一致性硬撑；判决成本写死在模型体积里，高频与长尾必须用同一个模型，任一端都会失分（§3.2.5 的约束）。
- **AI 改变了什么机制**：两处外置。**类目定义外置**成可检索、可版本化的描述与层次结构（本体或知识图谱是它的一个来源），判决时实时取回；**判决成本外置**成一条路由决策，按类目频次与置信度把请求分到成本不同的路径。机制变化落在**运行时链路**上，分类器本身没变。
- **由此得到的**：因为类目描述可以在运行时可取，所以新增类目、修正边界、调整层次都不必重训模型 —— 类目治理从数据工程问题变成内容维护问题；因为成本被路由外置，所以占比最高的主流流量留在便宜路径，只有长尾与大模型分歧样本付大模型单价。这两件事合起来，是本章说「LLM + 专用分类器 + 业务规则三位一体」时真正在指的结构（主文件 §1.3）。
- **由此付出的**：
  - ① 多了一条需要监控的路由链路与两套评估口径；两套模型的标签定义必须完全一致，否则回流样本会污染专用模型（§3.2.5）。
  - ② 路由阈值本身是需要持续调的超参，**它的漂移不会自己暴露** —— 长尾占比上升时，被判定为长尾的比例越走越高，成本与延迟同时上涨。
  - ③ 类目描述库成为新的真源：它与标签树、与报表口径三方不一致时，会出现「模型判对了、报表对不上」。
  - ④ 检索引入延迟与失败点：检索不到就退化成零样本，而这一次退化在指标上表现为「随机波动」。
  - ⑤ 层次一致性要保证：父类概率必须等于其子类概率之和（§3.2.6 的硬约束），而路由与检索都可能在链路中途破坏这条约束。
- **判定方法**：
  - 判断该不该做路由：先统计类目频次分布与长尾占比，再看长尾的绝对值。头部集中且长尾绝对值小，路由是净成本。
  - 判断类目描述库能不能当资产：能不能被第三方按版本复现（枚举值、判定边界、冲突时取哪个类）。写不出来就还是散落的约定。
  - 判断检索增强是否有效：把「检索不到」的样本单独统计一次。它们才是这条链路真正的错误来源。
  - 判断路由是否已经漂移：按月看「被判为长尾的比例」这一条曲线。它持续上升，说明阈值该重标了。
- **证据与来源**：【公开】主流检索与向量索引、Agent 框架的工具调用与路由，都是已发布的正式能力（可按各家官方文档里 retrieval / tool use / routing 一类条目、按当前版本核验）。把本体与知识图谱用作标签层次的定义来源，**本节不登记文献条目** —— 它对本文的意义在工程侧而不在文献侧：判据是类目描述能不能被第三方按版本复现（枚举值、判定边界、冲突时取哪个类），这一点在上面的判定方法里已给出。本节不代任何平台断言其路由或检索增强的具体效果。
- **成熟度**：**L2**（① 有；② 缺；③ 未稳 —— 路由判据与阈值、类目描述库的 schema 都没有通行约定）。

这一节的核心判断可以压成一句：**类目治理的位置变了**。过去它落在数据侧（标注与训练数据），现在它可以落在内容侧（可检索、可版本化的类目描述）；好处是改动成本低、可回滚，代价是它变成了需要长期有人维护的**内容资产** —— 没人维护的描述库，会比一份过期的训练数据更危险，因为它看起来是「新的」。

### 5.3 与本主题既有栈的接口在哪

判断标准是接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。凡是说不清失败归属的「与 X 结合」，在评审会上听起来完整，在事故复盘时提供不了任何信息。本主题尤其如此 —— 分类链路上的每一段都可以被替换，唯独边界上的**口径与代价定义**换不掉。

本主题有一处特别的接缝：**AI 改变的是判决信息的来源，没有改变决策的那一步**。阈值、代价矩阵、校准、口径冻结全在模型之外，而且全部是**必须由人给定**的输入 —— 业务不给代价矩阵，阈值就只能凭感觉调（§3.5 的「类别权重拍脑袋」）。表里最后一列的级别沿用 §5.1 的三条判据，评级对象是**接口**；凡与某个 5.2.x 方向对应的行，级别与该方向一致，并在「现状」列注明对应关系。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 特征平台 → 分类器 | 带时间戳的特征快照（Point-in-Time 对齐） | 特征定义的 Owner —— 取到「当前值」就是穿越（§3.5） | 既有栈（[§ 4 §4.2](02-classification-section-4-sec4.md)） |
| 专用分类器 → 在线决策 | 校准后的概率 + 阈值 | 校准与阈值的 Owner —— 未校准的概率会让自动处置比例整片偏移（§3.5） | 既有栈（§3.7 自检清单） |
| LLM 打标机 → 样本库 | 枚举内的标签 + 置信度 + 越界拒答 + Golden Set 版本 | 把 LLM 标签当真值写进样本库的人 —— 脏标签会以「下游效果波动」出现 | L2（对应 5.2.1） |
| 路由器 → 两条路径 | 路由信号（类目历史频次、专用模型置信度、特征缺失率、是否命中新类目） | 路由阈值的 Owner —— 阈值漂移不会自己报警（§3.2.5） | L2（对应 5.2.4） |
| 类目描述库 / 本体 → 判决 | 可检索、可版本化的类目描述与标签层次 | 标签体系 Owner —— 描述与报表口径不一致时，模型判对也算错 | L2（对应 5.2.4） |
| 分类输出 → 报表 / 考核 | 可聚合的类目概率分布（不是一段自然语言） | 发布口径的一方 —— 口径一天一个样时，跨类目报表无法发布（§3.3 第二常被误选的一对） | L2（对应 5.2.4） |
| 模型 → 评测与回流 | 冻结的 Golden Set + 口径版本 + 回归结果 | 口径冻结的 Owner —— 没有冻结口径就没有回归（§7.3.4） | 既有栈（§3.5 的「LLM 分类无评估」） |

```text
判决信息来源（本节各方向在改这一侧）      决策与治理（本节所有方向都没改这一侧）
  标注样本 ─────┐                        ┌── 校准（概率 → 真实频率）
  预训练语料 ───┼──► 分类器 / 打标机 ──► 概率或枚举 ──┼── 阈值（代价矩阵反推，§3.5）
  检索到的类目描述 ┤                        ├── 口径冻结与 Golden Set（§7.3.4）
  另一模态的表示 ──┘                        └── 回流样本治理
── 判据：上侧换了，下侧一样要人给；代价矩阵给不出时，阈值只能凭感觉调
```

边界上最难的两件事，恰好是本节所有方向都没有触及的部分：

- **代价矩阵**：漏检与误报各值多少钱，决定了阈值、类权重、以及「自动处置」的边界；业务不给这个数字时，团队只能在误报投诉与漏检事故之间来回摆动，最后把问题归因成「数据不可用」（§3.5 已把这条列为最常见的两阶段反模式）。它可以被写成一行公式：期望代价 ≈ 正类占比 × 漏检率 × 漏检代价 + 负类占比 × 误报率 × 误报代价（§3.5 的推算），代入之后就会发现「默认 0.5」只在两类各占一半、两种错误代价相等时才最优。
- **口径冻结**：同一份输入用同一个模型版本必须给出同一个标签，否则报表、考核与下游模型都建立在流沙上；而生成式输出在没有枚举约束与固定评测集时恰恰不满足这一条（§7.3.4）。

| 你要判断的事 | 现在能查清楚吗 | 查不清时先做什么 |
| --- | --- | --- |
| 漏检与误报各自的业务代价 | 多数情况下不能 | 先写代价区间与谁签字，再谈阈值 |
| 概率是不是校准过的 | 能（在独立校准集上算 Brier / LogLoss） | 未校准前不要用「按 0.9 自动处置」这类规则 |
| 口径能不能被第三方复现 | 能（写枚举值与冲突规则） | 写不出来就先别接进报表 |
| 换模型版本会不会改口径 | 能（同 Golden Set 跑标签一致率） | 一致率未知时，不要在版本升级时顺带改业务规则 |

### 5.4 公开进展与文献

只列可核验的条目，按「论文 / 官方发布说明 / 第三方生产案例」三类分开。给得出论文标题（或文档名）与年份的才写在这里，给不出的放在上文方向讨论里并标明级别；本节对论文条目一律不写效果数字。

**论文与公开实现**

- 【公开】TabPFN（Hollmann et al., "TabPFN: A Transformer That Solves Small Tabular Classification Problems in a Second", ICLR 2023）—— 小样本表格分类的免训练先验（§3.3 已引用）。
- 【公开】SetFit（Tunstall et al., "Efficient Few-Shot Learning Without Prompts", 2022）—— 免提示词的少样本分类路线（§3.2.4 已引用）。
- 【公开】LoRA（Hu et al., "LoRA: Low-Rank Adaptation of Large Language Models", 2021）与 QLoRA（Dettmers et al., "QLoRA: Efficient Finetuning of Quantized LLMs", 2023）为公开发表方法（两篇均先以 arXiv 预印本公开；会议与卷期请按论文标题核验）。
- 【公开】CLIP（Radford et al., "Learning Transferable Visual Models From Natural Language Supervision", ICML 2021）、Flamingo（Alayrac et al., NeurIPS 2022）、GPT-4V(ision) System Card（2023）—— 多模态分类的两条路线（§3.2.3 已引用）。
- 【公开】Focal Loss（Lin et al., ICCV 2017）与 SHAP（Lundberg & Lee, NeurIPS 2017）—— 分别对应不平衡场景与事后归因，§3.3 已引用；它们属既有栈，不是本节的新方向。

**官方发布说明（release note）与官方文档**

- 【公开】结构化输出与工具调用是各家模型的正式能力（可按 OpenAI Function Calling、Anthropic Tool Use 一类官方文档名核验；这两项在 2024 年前后从预览转为正式接口，具体版本与日期以各家官方文档当前版本为准）—— 本节只用它们支撑「输出可被约束到枚举」这一条事实依据，不比较实现差异。
- 多模态输入能力没有跨平台一致口径：单次请求能带几张图、多长时间的视频、按什么单位计费，各家不同。判断某个版本能不能用在你的链路上，看该版本官方文档里的限额条目，而不是产品页的能力列表。

**第三方生产案例**

- 本节对「LLM 与分类结合」这部分**没有可指名的第三方非发布方生产来源** —— 这正是 5.1 表里六个方向停在 L2、三个方向停在 L3 的原因。
- 可自行核验的入口有三处：各家官方发布说明（对应判据①）、公开评测与数据集上的复现结果（可验证但不等同生产）、以及既非发布方也非承建方的公司工程材料（对应判据②，也是当前最缺的一类）。
- 需要特别说明的是：**厂商与承建方公布的业务提升数字不进入本节的证据列**。不是因为它们不可信，而是因为它们几乎都缺三样东西 —— 标签口径的定义、评测集的构造方式、以及上线前的基线数字；缺了这三样，数字无法被第三方复核，也无法与别的方案对照。

**四条可自行核验的公开线索**

- 想知道某个「结构化输出 / 工具调用」能力处在什么状态：查官方文档里它是否被列为正式能力，以及输出约束的适用范围（是否支持枚举、是否支持必填字段）。
- 想知道某个分类方法在你的域上值不值得试：找它的公开实现与评测脚本，用**你自己的 Golden Set** 跑一遍，而不是用论文里的数据集。
- 想知道某个「LLM 替代分类器」的说法是否成立：看那句话的原始出处是产品页、论文还是第三方评测。三者能支撑的结论强度完全不同 —— 产品页支撑「能力存在」，论文支撑「方法成立」，只有第三方评测才支撑「在可比条件下更好」。
- 想知道某个视觉骨干能不能当分类器用：按模型名找到它的论文与官方实现，先看它的**输出形态**是什么（表示、分割，还是一组可枚举的类别）—— 提供表示或分割的骨干不直接给你分类口径，DINOv2、SAM 一类常被这样误读。

### 5.5 被过度宣传的部分

**「LLM 可以直接替代专用分类器」** —— 实际是分工被重新划线，不是替代。为什么会这样：分类器要做的事里，只有「给出标签」这一件被交给了模型，其余几件它给不了 —— 可校准的概率（阈值与代价矩阵要靠它）、可冻结的口径（报表与考核要靠它）、可预测的延迟与成本（主路径吞吐要靠它），而这些恰恰是主文件 §1.3 把专用分类器留在核心位置的理由。什么时候它才会成真：模型能稳定输出可校准的概率、同一输入在版本内给出同一标签，并且这两点被第三方在真实流量上核验过。顺带说清一件事：模型在输出里附带的「理由」**不属于**可解释分类的工具链 —— 它是自述，不是归因；后者在 §3.5 与 5.4 已有对应做法。

**「Agent 会自动发现类目、自动标注、自动训练部署」** —— 实际是「做」的成本下降、「判」的成本不变。为什么会这样：自动化的边界由「边界能否被程序判定」决定 —— 「这一类的样本该不该归到那一类」需要业务裁决，而裁决一旦错，整治成本要沿报表、考核与下游模型逐层传导。什么时候它才会成真：出现可被程序判定的类目边界（例如由标签树与冲突规则完全确定），且误判之后能自动回滚并重跑回归集。

**「自适应分类与小模型复兴能直接省钱」** —— 实际是先要有度量，才谈得上自适应。为什么会这样：按难度选推理深度，前提是能**稳定地估出难度与代价**；而分类任务的「难度」并不由输入长度或置信度决定，它由这个样本在标签边界上的位置决定 —— 没有边界度量，自适应就退化成按长度切分。什么时候它才会成真：出现可复核的难度度量，并且「简单样本走小模型」的判定误差被证明低于它省下的成本。

这三条的共同点是：**AI 把「给出一个标签」变便宜了，没有把「决定标签该长什么样、错了谁负责」变便宜**。所以判断一个「AI 分类」方案值不值得投，只需问一句 —— 它省掉的是「给标签」的成本，还是「定口径」的成本。省「给标签」的成本，收益立刻兑现；声称省「定口径」的成本，先让它证明口径被冻结在了哪里。

### 5.6 未来 3–5 年：可证伪的预测

写不出信号与反信号的预测不写。下表后两列是给自己留的检查项，不是修辞。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| LLM 在分类上的落地会集中在离线打标与长尾兜底，而不是主路径 | 公开材料里「打标机」与「分歧样本复核」的形态增多；主路径仍以小模型与被蒸馏模型为主 | 出现以 LLM 为在线主路径、并公开尾延迟与成本结构的生产案例 |
| 分类系统的分水岭会从「模型选型」退回到「标签口径的可冻结性」 | 公开讨论里 Golden Set、口径版本与回归评估成为上线前提的常态；口径变更要通知下游这件事被写进流程 | 继续以基准分数作为选型依据，而口径与回归集在公开材料里持续缺席 |
| 类目治理会从数据侧移到内容侧（可检索、可版本化的类目描述成为资产） | 出现把类目描述库按版本管理、并与报表口径对账的公开做法 | 类目边界继续写死在训练数据与代码里，改一次要重训一次 |
| 隐私保护分类在 3–5 年内仍以「合规驱动的点状试点」为主，不是通用能力 | 公开案例集中在金融、医疗等强合规场景，且多为单机构自述 | 出现跨机构、跨行业可复用的隐私分类通用方案与公开评测 |

四条预测里，第二条与第三条的「会证伪的信号」本质是同一件事：**只要口径与回归集继续缺席，本节关于「口径决定分水岭」与「类目治理位置迁移」的两条判断就不会被推翻，只会被绕过**。这也是为什么下面那张表的最后一列比前几列更值得记住。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 被要求「用 LLM 做分类」 | 先建 Golden Set 与越界拒答，从只读场景（打标、候选）起步 | 标签一致率（同口径换版本）与被判越界的比例 | 不要让 LLM 直接进低延迟主路径；不要在口径未冻结时把它接进报表 |
| 类目按周新增、重训追不上 | 把类目描述做成可版本化的资产，再决定哪部分走模型、哪部分走检索 | 类目新增到上线的时间，以及边界修正的成本 | 不要为一个还在变的类目体系做全量重训；不要用一次训练去锁住会变的口径 |
| 想省掉训练成本 | 先做 embedding + 轻分类头或轻适配，与 GBDT 基线在同一份数据上对照 | Embedding 服务是否换了默认模型，以及换时要动几处 | 不要把 embedding 版本当成透明依赖；不要在域差很大时指望零样本 |
| 内容形态是图文 / 音视频混合 | 先统计单模态判定冲突的样本占比，再决定是否上多模态 | 分歧判定的准确率，以及被挑出样本的绝对量 | 不要对全量样本调用大模型；不要在缺模态时没有降级路径 |
| 在做 Agent，需要意图路由 | 把路由信号显式记录（类目频次、置信度、缺特征率），便于事后定位 | 「被判为长尾的比例」这条曲线是否持续上升 | 不要把路由阈值当成一次性配置；不要让两套模型的标签定义各写一份 |
| 被合规要求做隐私保护分类 | 先做可行性验证：把对齐与划分这两步在受限条件下跑通 | 合规是否**硬性**要求数据不出域 | 不要在合规方案未定前先建数据链路；不要把联邦当成绕开合规的手段 |
| 被要求「提升分类精度」 | 先看现有方案的误差落在哪一层：口径、特征、阈值还是模型（§3.5 的反模式表按层给了修法） | 误差归因的分布是否变了（换模型常常改不了归因） | 不要用换模型去解决口径与阈值问题；不要在未校准的概率上调阈值 |
| 打算把 LLM 接进已有链路 | 先让它只做候选与打标，输出必须落到枚举并附置信度 | 人工复核的通过率，以及越界与拒答的比例 | 不要让它的输出绕过已有阈值与代价矩阵；不要让它直接改写类目体系 |

最后一列是这个表里唯一有长期价值的：前三列做的事一年后都能补，「不要做」的那几件做错了，要花一年拆掉。

同一件事换个说法：**这张表里没有一行是「选哪个模型」，全部是「先弄清哪一条约束」**。这不是巧合 —— 本章 §3.1 的约束表（标签信息量、决策模式、漂移频率、合规、成本、团队能力）在本节每个方向里都先于模型出现，而其中**最难被满足的一条是代价结构**：漏检与误报各值多少钱，只有业务能给，而阈值、类权重与评估口径全都从它推出来。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**判决信息的载体从「标注样本」移到了「预训练语料与运行时可取的类目描述」** —— 由此「加一个类目」从一次训练-发布变成一次提示词或描述改动，长尾与冷启动第一次有了可用的兜底。它**没有改变**的是**标签口径的可冻结性仍然决定一切**（[§ 7 §7.3.4](02-classification-section-7-sec7.md)）：阈值要从代价矩阵推、概率要校准、口径要冻结、错例要能回归 —— 这四件事一件都没有被自动化，它们仍然是人给的输入。本节没有方向达到 L1，门槛最低的两条恰好也是收益最直接的两条：能把「一次训练」省掉的方向，比声称能提升能力的方向更接近可用；而「业界都在用」与「能被判据核验」仍然是两件事，前者不能替后者。
