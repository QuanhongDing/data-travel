## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题是没有时间维度。「混合检索 + 精排」今天已经是多数检索引擎的默认能力项，而「反思 token 的专门训练」「用反馈自动优化检索」还停在论文与演示里；两者被写在同一个清单里，读者据此排路线图，多半会先做那个最写不出验收标准的。

第二个问题是机制差异被抹平成同一类词。本节要评估的方向实际横跨三层机制，改动它们的东西完全不同：

1. **索引里放什么**：文本块、页面图像，还是实体与关系——这一层决定了「什么形态的知识可以被检索到」。
2. **检索结果怎么变成上下文**：向量召回、关键词召回、融合、精排、压缩——这一层是排序问题。
3. **谁决定检索**：固定流水线，还是由模型在生成过程中决定再检一次——这一层是控制流问题。

本节方向里的「多模态 RAG」「GraphRAG」动的是第 1 层，「Hybrid RAG 三路召回」动的是第 2 层，「Self-RAG / CRAG / Agentic RAG」动的是第 3 层。三层的改动成本、失败模式与可验证方式完全不同，混在一句话里就没法评估——这是本节把它们分开逐条拆的原因（5.2）。

本主题的既有卡点写在主文件 §1.2 里：微调解决不了知识更新；再长的提示词也塞不下百万份文档；长上下文解决不了成本与精度；单一向量召回的召回率不足——相似度检索处理不了精确匹配、多跳推理与时效过滤。这几条卡点里，「召回率不足」已经被混合检索解掉了一大半，这恰好说明**检索这一层的机制是成熟的**，不需要 AI 来救。真正没被解决的是另外三件事：(a) 索引里的表示由模型生成——分块与嵌入都由模型决定，换一次模型就要重建索引；(b) 检索从「一次」变成「多轮」，控制流进入概率模型，失败不再可复现；(c) 检索的**可见性边界**——谁能检索到什么，在数据资产的语境里比精度更要命，而它是本节所有方向中最少被写进架构文档的一条。

本节用三级划分，三条判据必须可核验：

- **L1 生产可用**：三条全中才算。① 已 GA 且有正式 release note；② 有**第三方（非厂商）公开的生产案例**；③ 接口稳定、可预期。
- **L2 可试点**：①③ 大体满足、② 不满足；或能力可用而判定标准尚未形成共识。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图、论文、厂商演示或预览特性。记录即可，不要在架构里为它预留假设。

判据 ② 在本主题尤其难过，原因值得先说清：**RAG 的公开效果材料几乎都是产品方与建设方自述**，而且分数依赖一整套未被写出来的条件（分块策略、提示、裁判模型、采样次数、harness 版本），换一个 harness 就换一个排名。所以本主题的方向大多停在 L2 或 L3；这不是保守，是判据的必然结果。**② 只有「满足」与「降为 L2」两种命运**：既不能改成「有公开效果数据」（那等于把产品页当证据），也不能靠「本节只评估检索层」把适用范围缩小来绕过去。

还要说清 L2 在本节的含义：它标的是**证据缺口**，不是「不建议用」。本节几行的 ①③ 很干净、只缺 ②，缺的是「别人用过、并且公开说了代价」这类材料，不是能力本身；级别照判据如实标，采不采用由读者按自己的风险偏好决定，判据本身不因这句说明而放宽。

另有一条评级规则，全节通用：**合并方向取最弱子项**。本节把「混合检索」与「Agentic RAG」分成两行而不是一行，理由是它们的可规划性差一个量级：前者今天就能接进现有的检索链路，后者要先给控制流设上界。

**本节没有一行达到 L1。** ①③ 最干净的是两行——检索基础、混合检索与融合：它们的接口（查询、top-k、过滤条件）多年不变，卡点是同一条——**②（第三方非厂商公开生产案例）拿不出**。其余各行在 ① 或 ③ 上至少打了一处折扣——表里写着「大体满足」或「不满足」（② 不满足是全表共有的卡点，不能用来区分哪两行更干净）；同为第 1 层机制的多模态 RAG 恰恰是本表里 ③ 最不稳的一行，页面级编码的表示格式与索引结构还在各家自己定义，所以表里给它的 ③ 只是「大体满足」，不能与上两行并列。判断某条方向是不是 L1，不要看它被多少平台内置，看第 ② 条的材料是不是**发布方之外的机构**给出的：平台内置只证明它被卖出去了，不证明别人用了多久、付了什么代价。

给读者的核验动作——拿到任何一条方向，按顺序问三句：

1. 它的正式 release note / 论文 / 版本化文档能不能找到？找不到 → L3。
2. 厂商之外的证据能不能找到？找不到 → L2。
3. 接口明年会不会变？会变 → 至多 L2。

第 3 句在本主题特有的失手方式，是把「检索效果」当成与 harness 无关的属性：同一套向量模型与 reranker，换一种分块、换一种融合、换一个 top-k，端到端答案质量就会变。判定方法是固定一份查询集，只改一个变量重跑，看结论是否稳定。

三个常见误判，排路线图时最容易踩：

- **把论文里的原型当成产品里的实现**：反思标记、协同训练这类方法在论文里成立，靠的是专门训练；只抄提示词不训练，复现的是文本风格而不是机制。
- **把某次评测的分数当成自己场景的效果**：分数是「那套 harness + 那批题」下的结论，与你语料的分布、权限模型、更新频率无关。
- **把「索引里有」当成「检索得到」**：权限过滤、时效窗口、双索引不一致都会让内容躺在索引里却检索不到——这类问题不会报错，只会漏答（5.3）。

### 5.2 演进方向逐条拆解（核心节）

#### 5.2.1 混合召回与融合：把「找相似的」换成「组合多种证据的排序」

- **旧做法与它的卡点**：单路向量召回。卡点有两层：**相似度不等于正确性**——语义最近的片段未必是答案所在；以及**失败不可见**——正确文档根本没进 top-k 时，生成模型只会把错的线索讲得更流畅，而错误发生在检索侧，报错却出现在答案里。主文件 §1.2 把这一条列为「单一向量召回召回率不足」，并明确了它覆盖不了的三类查询：精确匹配、多跳、时效过滤。
- **AI 改变了什么机制**：改变的是**排序证据的来源**，而不是检索这件事本身。RRF 的机制很干净：把每个检索器输出的**名次**按 `1/(k+名次)` 相加，只用名次、不用分数——因此异构检索器（倒排、向量、图、结构化查询）不需要做分数归一化就能融合。查询侧则从「原样检索」变成「先改写或扩展再检索」，HyDE 用一段假设答案的向量去对齐文档向量。这两处合起来，是把「一次相似度比较」换成「多路证据 + 融合 + 精排」的决策链。
- **由此得到的**：因为融合只用名次，**所以**接入一个新检索器的成本从「调权重、做分数标定」降到「接一个排名列表」，而每接一路，能被覆盖的查询类型就多一类——精确关键词交给倒排、语义近似交给向量、关系交给图；**又因为**精排模型看的是「问题 + 片段」的整体，**所以**检索质量的上限从「召回集里有没有」推进到「召回集里的排第几」，端到端失败从「检索不到」（无解）变成「排序不高」（可改善）。这一段是本节唯一一条「多做一点就多拿一点」的确定性收益。
- **由此付出的**：延迟与成本按路数放大——每一路都是一次检索，精排又是额外的模型推理，所以要显式做延迟预算的取舍，而不是把召回一路加到检索不到为止；RRF 丢掉分数意味着**丢掉置信度**——一路以极高相似度命中和一路勉强挤进前十，融合后可能同权，需要另加规则才能区分；查询改写引入了一类新故障：改写把原问题里的实体改没了、或者把时间条件改掉了，而它发生在检索之前，出错时连"检索为什么没命中"都很难看出来，所以改写步的前后文本必须落盘。
- **证据与来源**：【公开】RRF 的原始论文（Cormack 等，SIGIR 2009，给出「只用名次融合」的机制与实验）；【公开】假设文档检索一类方法（2022–2023 年间，具体篇目以论文库当前版本为准）；【公开】主文件 §2.2 已给出 RRF 的融合公式与向量、BM25、混合相似度的形式，本节不重复推导。② 不满足：能充当第三方生产案例的材料要给出来源与统计口径，本节给不出。
- **成熟度**：**L2**（与 5.1 表「检索基础」「混合检索与融合」「查询改写与扩展」三行一致），判据同为 ①③ 满足或大体满足、② 不满足。

```text
召回失败无法由生成补救，排序不高可以（这两类必须分开看）
   问题 → 多路召回 ──┬─ 倒排：精确词 / ID / 型号 / 日期
                     ├─ 向量：语义近邻 / 跨措辞
                     └─ 图或结构化：关系 / 聚合
                          │  各自输出一个排名列表
                          ▼
                     RRF 融合（只用名次，不用分数）
                          ▼
                     精排（问题 + 片段一起过模型）
                          ▼
                     组装上下文 → 生成

判定方法：把「正确片段在第几路召回里、排第几位」记下来
   正确片段不在任何一路的 top-k 里 → 这是召回问题，换大模型、改提示都救不了
   正确片段在但排位靠后        → 这是排序问题，精排与融合能解决
```

**延迟预算怎么分**：多路召回与精排都是可以加的，但每一路都要占预算，所以要先把总预算定下来再决定加几路——常见做法是让召回路径并行、只在融合之后做一次精排【经验】，并让「加一路召回」变成一次有数据的取舍（加这一路让多少条查询从「不在召回集里」变成「在」），而不是默认越多越好。判定方法：把查询集按「原先是召回失败还是排序失败」分成两组，看新加的这一路主要改善哪一组。

#### 5.2.2 GraphRAG：把关系从向量里拿出来，代价记在建索引那一刻

- **旧做法与它的卡点**：多跳与汇总类问题（「这几份文件讲的战略有没有冲突」「A 与 B 之间是什么关系」）在纯向量检索里做不了。原因是结构性的：向量召回返回的是**单个片段**，而答案所需要的关系不在任何单个片段里；把这类问题交给生成模型，它只能在场内自己编关系——这正是「跨文档推理」失败的机制，而不是提示词没写好。
- **AI 改变了什么机制**：把「关系」从查询时算，挪到**建索引时**算。流程是：用模型从文本抽实体与关系 → 在图上做社区检测 → 逐社区生成摘要 → 查询时按问题类型走「按实体附近取证据」或「按社区摘要取全局视图」两条路（Local / Global Search）。机制上的改变是**把推理的一部分前置成索引结构**，边加数据边加结构，查询时只做遍历与检索。
- **由此得到的**：因为社区摘要在索引阶段就已经生成，**所以**「宏观问题」不再需要把大量原文塞进上下文，一次检索就能拿到摘要级证据——这是纯向量检索在结构上做不到的；因为关系以实体为节点存在图里，**所以**「沿关系走两跳」变成一次遍历查询，而不是让模型在文本里猜。一句话：它把「多跳」从模型能力问题变成数据结构问题，而数据结构问题是可以被工程解决的。
- **由此付出的**：成本前置且与语料量成正比——建图要完整跑一遍抽取、再做社区检测与逐社区摘要；语料更新后这些成本要重跑，不是「插入一个片段」那么简单，所以它天然适合**低频更新的语料**，高频更新的语料上它是一次次全量作业。第二项代价是抽取质量决定上限：漏掉实体，后面的遍历就不存在；抽错关系，错误会以「看起来合理的错误关系」进入答案，比检索不到更难发现。第三项是新增了要维护的东西（图存储、社区结构、摘要版本），在数据资产语境里，这份结构同样要有 owner 与版本，否则半年后没人说得清某条关系是从哪一版语料里抽出来的。
- **证据与来源**：【公开】Microsoft GraphRAG 开源项目（2024 年起发布，其文档给出从文本到社区摘要的完整流程与两种查询方式）；【公开】Leiden 社区检测算法（2019 年论文，是该流程里划分社区的常用方法）；【公开】LightRAG 与 HippoRAG（2024 年预印本，分别做轻量化与更接近「联想式记忆」的图结构）。② 不满足：可查到的效果材料以项目方与采用方自述为主。
- **成熟度**：**L2**（与 5.1 表「GraphRAG」行一致），判据：①③ 大体满足、② 不满足，且语料更新后的增量维护没有稳定方案。

| 你的问题类型 | 混合检索够不够 | 判断依据 |
| --- | --- | --- |
| 单点事实查询 | 够 | 答案落在某一个片段里 |
| 需要跨片段汇总 | 不够 | 答案不在任何单个片段里，也不在任何一句里 |
| 需要沿关系走两跳以上 | 不够 | 关系本身没有被索引，模型只能在场内猜 |
| 语料每天更新 | 慎重 | 建图与摘要是重跑形态，更新频率直接决定成本 |

#### 5.2.3 反思与智能体：把「要不要再检索一次」交给模型

- **旧做法与它的卡点**：固定流水线一次检索定生死。卡点在**判断发生在错误的时刻**：检索命中与否，只有在看到结果之后才好判断；而固定流水线在检索之前就决定了检索几次，于是「检索不到」这件事没有补救路径。把「检索不到就别答」写进提示词也没用——它是一条祈使句，不是控制流，模型照答不误。
- **AI 改变了什么机制**：改变的是**控制流**。Self-RAG 让模型在生成过程中输出反思标记，用它决定是否需要检索、检索到的内容是否被支持；CRAG 在检索之后加一个可信度判定，不可信就重检索或转向外部检索。两者相同的一点是：把「是否继续检索」这个分支交给一个概率模型在**看到中间结果之后**决定。Agentic RAG 则是把这个分支进一步扩成「调哪个工具、按什么顺序」，检索只是工具之一。
- **由此得到的**：因为「要不要再检一次」由模型在看到初步结果后决定，**所以**固定流水线里「一次没检到就答错」的那类问题第一次有了补救路径；**又因为**判定与生成在同一个循环里，**所以**「无证据不生成」这条约束第一次可以被写成可执行的控制流，而不是写在提示词里的祈使句。这是主文件 §2.3 把 Self-RAG / CRAG 与朴素 RAG 区分开的那一点，也是它值得被单列的原因。
- **由此付出的**：控制流交给概率模型之后，**延迟与成本不再有上界**——轮数由模型判断决定，而判断不是确定的，同一问题两次请求可能走不同轮数，尾部延迟会明显变长、成本按轮数放大；这一步必须显式设上界，不设就是把线上成本交给一个不可预测的控制器。第二项代价是可复现性下降：同一输入两次结果不同，生产排障需要把每一轮的检索与判定都落盘，否则复现不了。第三项更隐蔽：反思能力依赖模型是否被专门训练过这套标记——在通用模型上直接套提示词，得到的往往是「看起来在反思」的文本，而不是真的触发了重检索，此时你付出的是延迟，换来的只是措辞。
- **证据与来源**：【公开】Self-RAG（2023 年预印本、ICLR 2024；核心是反思标记 + 专门训练，缺了训练这一步复现不了论文效果）；【公开】CRAG（2024 年预印本；检索后可信任度判定 + 外部检索回退）；【公开】FLARE 一类主动检索（2023 年会议论文；按生成过程中的置信度决定何时检索）。这三条的②都不满足：生产采用材料以框架方与应用方自述为主。
- **成熟度**：**L2**（Agentic RAG 行，判据：①③ 大体满足、② 不满足）；**L3**（Self-RAG / CRAG 反思机制行，判据：① 不满足——反思标记依赖专门训练，在通用模型上不是可用的能力项；② 无）。两行不要合并使用：**给控制流加上界现在就能做，靠模型自己的反思换来更好的检索则是另一件事。**

```text
控制流交给模型之后，要先给它三个上界（不设上界＝把线上成本交给控制器）
   轮数上界      最多再检几次（常见 2–3 轮【经验】），到顶就按现有证据作答或明确说不知道
   预算上界      单次请求的 token 与工具调用上限，超了降级到单轮检索
   落盘要求      每轮的查询、命中片段、判定结果都要可查，否则复现不了线上问题

判定方法：同一问题连问 5 次【经验】，记录轮数与总耗时
   轮数波动大 → 成本不可预测，先设上界再谈效果
   轮数稳定而答案不同 → 瓶颈在生成侧而非检索侧
```

#### 5.2.4 多模态与长上下文：换掉的是「进索引的东西」

- **旧做法与它的卡点**：索引里放的是文本。扫描件、图表、双栏排版、视频、音频要么先做 OCR 与版面解析转成文本（版式信息在转换中丢失，且转换错误会一路上传到答案），要么根本不进索引。另一个卡点是长文档：分块把版面结构打散，「这张表和上面那段话是一组」这类信息在切完之后就不存在了。
- **AI 改变了什么机制**：改变的是**进入索引的表示**。多模态模型可以直接把一页 PDF 当图像编码成一组向量（页面级、按图像块做晚交互检索），跳过 OCR 与版面解析；同时长上下文的成本结构变了，把「整份文档进上下文」从不可行变成可选，于是检索的角色从「唯一入口」变成「成本分级里的一档」。两处改动都属于第 1 层机制——**索引里放什么**，而不是检索算法变了。
- **由此得到的**：因为页面图像可以直接进索引，**所以**扫描件、图表、双栏排版这类「解析器做不好」的文档第一次能被检索，而且检索单元与人类阅读的单元一致（一页），「答案在第几页」变得可回答；因为长上下文能装下一份文档，**所以**在「需要通读一份文件」的任务上，检索不再是必经之路，架构可以按「文档大小 × 更新频率」分档，而不是一律先切分再拼上下文。
- **由此付出的**：多模态索引的体积与成本按像素与页数增长，而不是按字符数——同一页 A4，文本切分通常出几个片段（常见 3–10 个【经验】），页面级图像编码的向量数则由页面像素与图像块边长决定，常见区间是从数十倍到上百倍不等【经验】；这个倍数不是常数，它随扫描分辨率与块大小变化，必须在定下这两项之后按自己的语料估算，再写进预算。检索侧的计算也更重（每个查询 token 要与大量图像块比较），这两项都要在预算里写清楚；把整份文档进上下文则把成本与延迟按 token 线性放大，而且「放进去」不等于「用得上」——长上下文里的中段信息利用并不稳定，所以长上下文替代的只是「一部分」检索场景；最后一项最容易漏：多模态索引与文本索引的**权限模型必须对齐**，否则会出现「原文无权访问、截图能搜到」这类漏洞，而它不会报错，只会安静地越权。
- **证据与来源**：【公开】ColPali（2024 年预印本，把 PDF 页面作为图像做多模态检索）；【公开】CLIP（Radford 等，ICML 2021，对比式图文预训练，是双塔图文嵌入的方法来源）；【公开】多模态嵌入模型的官方模型卡（本节具名的是 5.1 落点表里的 Qwen-VL 一类；模型卡给出输入形态与向量维度，命名与版本各家不同，请以模型卡当前版本为准）；【公开】长上下文能力以模型厂官方文档当前版本的窗口声明与计价为准（本节具名的是 5.1 落点表里的 Gemini 1.5 / Claude 3.5 一类，窗口数字随版本变化，不要引用二手材料里的数字）。② 不满足。
- **成熟度**：**L2**（与 5.1 表「多模态 RAG」与「长上下文与检索的组合」两行一致），判据同为 ①③ 大体满足、② 不满足。

**表中其余方向为什么停在这里**：

- **实时 / 流式 RAG（L2）**：机制是「把索引更新从批处理改成增量写入」（Kafka 一类消息队列 → 嵌入 → 向量库）。能力可用，但有两个坑：一是**删除**——文档撤回或权限回收时要从索引里删干净，向量库的删除语义与倒排不同，删不干净就是越权；二是**一致**——同一份内容在向量索引与倒排索引里更新不同步时，混合检索会把新旧两版一起召回，生成模型照着旧版答。判定方法很便宜：做一次「删除 + 立刻检索」，看它还在不在。
- **本地化 / 私有化 RAG（L2）**：机制是把嵌入、向量库与生成模型全部放在边界内。组件都有版本化发布，可用；代价是效果与运维的折中要自己承担——本地模型与托管模型在检索与生成上的差距在不同语种、不同任务上分布不均，只能自己按语料测。核验时要先分清合规要求的是「数据不出边界」还是「模型不拿你的数据训练」，两者的解法不同。
- **托管 RAG 平台（L2）**：机制是把「切分 + 嵌入 + 索引 + 检索」整段交给平台服务，自己只提交语料与查询。省掉的正是自建栈里最费人的那一段（索引形态、检索参数、扩容），代价是**核验能力同时被交出去**：内部分块与检索策略不公开，判据 ① 只剩产品文档、判据 ③ 随平台版本变，判据 ② 更无从核验——平台被多少团队采用，不构成「别人用了多久、付了什么代价」的证据。判定方法：把查询集与语料快照留在自己手里，同一份查询集在平台与自建栈上各跑一遍；若分块与检索参数两边都改不了，这个分数就只能用来比平台版本，不能用来比效果。
- **RAG 评估框架（L2）**：机制是把「检索相关性」与「生成忠实性」拆成可计算的指标。可用，但指标本身由裁判模型给出（5.1 已说明分数依赖一整套未被写出的条件，其中就包括裁判模型），所以框架的可靠性与裁判同源；另外「忠实性」在框架之间的定义不同（是否允许外部知识、是否只要求不矛盾），跨框架的分数量级不可比。
- **RAG 与微调协同（L3）**：RAFT / RA-DIT 一类做的是训练模型更好地使用检索结果，前提是先有一套稳定的检索与评测；而且它把「什么时候该忽略检索结果」写进了模型参数，改起来比改提示词贵得多。检索链路没稳定之前做它，等于把移动的目标固化进权重。
- **Self-improving RAG（L3）**：用反馈自动优化检索与提示。缺的不是方法而是**可靠的反馈信号**：点赞不等于正确，未反馈不等于满意；把噪声当奖励，系统会向「更容易被点赞」而不是「更正确」的方向漂。可做的第一步是把反馈信号与正确性对齐（人工标注一批，看信号与标注的一致度）。
- **合并叙事（L2）**：按最弱子项取 L2——「成为标配 / 工业化 / 标准化」是措辞，它指向的三行（Agentic RAG、GraphRAG、RAG 评估框架）都停在 L2。作为章节标题可以，作为能力清单会误导排期。

### 5.3 与本主题既有栈的接口在哪

RAG 不是自成一体的系统：上游接数据资产与预处理，下游接应用与智能体。下表写清谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 数据源 ↔ 索引构建 | 以「分块结果 + 元数据（来源、版本、密级）」契约穿过边界 | 索引侧（谁建索引谁保证可重建） | 需自建：分块策略与模型版本必须记进索引元数据 |
| 向量库 / 倒排 ↔ 检索层 | 以「查询 + top-k + 过滤条件」为接口 | 检索侧（召回失败由检索侧负责，不许推给生成） | 引擎侧已有能力；过滤条件能否下推要逐库验证 |
| 权限系统 ↔ 检索 | 过滤器必须在**检索侧**下推，不能生成后再裁剪 | 应用侧（越权是安全事故，不是效果问题） | 需自建，且是最容易被漏掉的一行 |
| 数据目录 / 血缘 ↔ 索引 | 以「语料快照 + 嵌入模型版本 + 分块策略」登记为资产条目 | 索引侧（谁更新索引谁登记版本） | 需自建：缺了它，「换模型 = 重建索引」的成本没人算得清 |
| 评估集 ↔ 检索与生成 | 以「查询集 + 相关性标注」为接口 | 评估侧（谁发布结论谁维护查询集） | 需自建：标注是人工成本，外包不掉 |
| 应用 / Agent ↔ 检索工具 | 以「工具 schema + 返回片段及其来源」为接口 | Agent 侧（谁编排谁负责轮数与降级） | 框架侧有形态，上界与降级策略要自建 |

表里只有半行属于既有能力（引擎侧的检索与过滤），其余都要自建。**失败归属必须在设计阶段写清**，否则会退化成扯皮：答错了，是没检索到、检索到但被权限过滤掉了、还是检索到了但生成没用上？三种原因的修法完全不同，而它们分属三个团队。这也是本节把「召回失败无法由生成补救」写成判定方法的原因（5.2.1）——没有这条划分，争论会一直停在「换个大模型试试」。

第三行值得单独说一句：**权限过滤放在检索侧与放在生成后，是两种系统**。放在生成后，被过滤掉的证据已经进入过模型的上下文，模型可能在答案里泄露它的存在（哪怕不泄露内容）；放在检索侧，越权的内容从未进入链路。这一行在数据资产化的语境里比精度重要，因为精度差是效果问题，越权是事故。

**判定这张表有没有被用起来**：每个季度核对三件事——有没有一次变更能追到「语料快照 + 嵌入模型版本 + 分块策略」，有没有一次「删除 / 权限回收」后立刻验证过检索侧不再返回，有没有一次端到端答错能定位到是召回、过滤还是生成的哪一段。三件都是零，说明表还停在文档层面。

### 5.5 被过度宣传的部分

**「GraphRAG 能做多跳，所以每个企业 RAG 都该带 KG」**

- *实际是什么*：它把推理的一部分前置成索引结构，只在「跨文档汇总与关系推理」这类问题上带来结构优势；单点事实查询看不出差别，而建图成本与语料更新频率成正比。
- *为什么会这样*：建图与摘要是重跑形态的作业，语料天天变时它变成一次次全量计算；而宣传材料通常只展示抽取质量好的小语料。
- *什么时候它才会成真*：当图索引支持增量更新与局部社区重算成为稳定能力时——那时高频语料上的成本才与「插一个片段」可比。

**「长上下文已经取代 RAG」**

- *实际是什么*：替换的只是「需要通读一份文件」这一类场景。成本按 token 线性放大，且长上下文里的中段信息利用并不稳定。
- *为什么会这样*：上下文窗口是容量限制，不是注意力保证；而检索的价值在于**选择**，选择这件事便宜且有效，与窗口大小无关。
- *什么时候它才会成真*：当「把整份语料塞进上下文」的单位成本与「检索几段」接近，且长上下文对中段信息的利用有稳定的公开判据时。

**「Agentic RAG 更聪明，所以一定更好」**

- *实际是什么*：它把控制流交给概率模型，换来「检索失败可补救」这一条好处，代价是延迟与成本没有上界、同一问题两次结果可能不同、线上排障需要逐轮落盘。
- *为什么会这样*：多轮的价值取决于「第一次没检到」的概率有多大；在混合检索 + 精排已经解决排序问题的场景里，这个概率本就不高，多轮只是多花成本。
- *什么时候它才会成真*：当轮数上界、降级策略与逐轮落盘成为框架的默认行为，且能证明「多轮比单轮多解决了一类问题」时。

这三条有一个共同结构：把「机制上可行」说成「指标上更好」。判断它们何时成真，看的是同一件事——**公开材料里有没有独立于实现方的、可复算的那部分证据**。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 混合检索 + 精排成为默认基线，「单路向量」被当成反模式 | 主流框架的默认模板改成混合召回加精排，文档里把单路向量标为简化示例 | 默认仍是单路向量 + top-k，精排被当成可选优化 |
| 过滤与权限成为检索接口的一等参数 | 向量库与检索框架文档把过滤条件与权限模型写进接口定义，并有下推的执行计划说明 | 仍靠应用层「生成后裁剪」，或把权限当业务规则写在提示里 |
| 多模态检索的默认单元从「文本块」转向「页面 / 图像」 | 主流索引方案把页面级多模态编码列为一等选项，并与文本块索引并列 | 仍以「先 OCR 转文本」为唯一路径，页面级编码停留在研究代码 |
| GraphRAG 的建图成本被增量机制解决 | 图索引出现正式的增量更新与局部社区重算能力，并被写进发布说明 | 仍是全量重跑形态，采用停留在小语料与低频更新场景 |

四条都能被**公开文档**证实或证伪，不需要内部数据：

- 第 1 条看框架的默认模板，一到两年见分晓。
- 第 2 条看检索接口的文档定义，一到两年。
- 第 3 条看索引方案的默认单元，两到三年。
- 第 4 条看图索引的发布说明里有没有增量机制，两到三年。

最值得先盯第 2 条：它是本节唯一一条**与效果无关、只与事故有关**的信号，一旦做不到，其余三条的收益都会被越权风险抵掉。

提醒一句：这四条都不是「某产品会不会做」，而是「**判断依据会不会出现在公开文档里**」。前者无法证伪，后者可以逐条核对——这正是本节用成熟度分级换掉趋势清单的原因。

这四条里还有一条共同的观察线索可以单独记下来：把每年的「默认模板」与「默认接口参数」抄一遍，比读任何趋势文章都更能说明哪条方向真的落地了。默认值不会撒谎——它只有在足够多的人按默认值跑起来之后才会改。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 刚开始做 RAG | 先把混合召回 + 精排 + 一份自己的查询集做出来（5.2.1） | 框架默认模板是否已经内置混合召回 | 不要先上 GraphRAG 或 Agentic，它们解决的是你还没遇到的问题 |
| 只有单路向量检索 | 加倒排与精排；把「正确片段在第几路、第几位」记下来 | 过滤条件下推在各库的实现是否一致 | 不要把「换更大的向量模型」当成提升召回的唯一起点 |
| 面向跨文档汇总类问题 | 先量语料规模与更新频率，再决定是否建图（5.2.2） | 图索引是否支持增量更新 | 不要在低频小语料上就上全量重跑式建图 |
| 文档含扫描件 / 图表 | 先试页面级多模态检索，并单独算索引体积（5.2.4） | 页面级编码是否成为默认单元 | 不要先投一条 OCR 流水线，它丢失的版式往往正是答案所在 |
| 数据有权限分级 | 把过滤放在检索侧下推，并做一次「删除后立刻检索」的验证（5.3） | 引擎是否提供可审计的下推执行计划 | 不要用生成后裁剪来兜权限 |
| 想用智能体接管检索 | 先设轮数、token 与工具调用上界，再谈效果（5.2.3） | 框架是否默认提供上界与逐轮落盘 | 不要把「多轮」当成质量保证，它同时是成本与不确定性的来源 |

「明确不要做」那一列的共用逻辑只有一句：**本节真正被 AI 改掉的是「索引里放什么表示」和「谁决定再检一次」；检索仍然是排序问题，召回失败仍然不能由生成补救**。所以预算应当投在召回路径、精排、权限下推与索引元数据这四件确定性工程上；在它们做完之前，任何「智能体化」都会先把成本放大，再把问题暴露在更难定位的地方。

如果只能排一个顺序，按这条走：

1. **先量召回**：按 5.2.1 的判定方法，把正确片段的位置记录下来——它决定后面所有投入该花在哪一段。
2. **再补排序与融合**：精排与融合是收益确定、代价可算的一步，且不需要改数据结构。
3. **然后定元数据**：语料快照、嵌入模型版本、分块策略登记成资产条目；它决定「换模型」是一次可估价的迁移还是一场事故。
4. **最后才谈图、多模态与智能体**：这三类都会改变索引形态或控制流，回滚成本高于前三步。

最后一条提醒：本节所有「现在就能做」的动作都不需要新模型——混合召回、精排、过滤下推、元数据登记，全是既有组件与流程。这也解释了本节为什么没有 L1：真正成熟的那部分（倒排、向量索引、精排）不需要被宣传，而需要被宣传的那部分，还没有成熟到能被第三方核验。

### 5.8 小结

> 本节小结：AI 在本主题上改了两条机制——**索引里放什么表示**（由模型生成的分块与嵌入、页面级多模态编码、抽取出来的实体关系）与**谁决定再检一次**（控制流交给概率模型）；它**没有改变**「检索是一个排序问题」这条：召回失败无法由生成补救，权限过滤如果没在检索侧下推，后面的所有环节都救不回来。本节没有一行达到 L1，①③ 最干净的两行都卡在「第三方（非厂商）公开生产案例」这一条上——所以现在该投的是召回路径、精排、过滤下推与索引元数据，而不是「Agentic RAG 化」。
