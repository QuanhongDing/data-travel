## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

决策表把设计讲成了「按场景特征选一个」：PoC 选 Naive、生产级选 Advanced、企业级平台选 Modular、高准确性选 Self-RAG / CRAG、复杂多跳选 Agentic、宏观问题选 GraphRAG。这些推荐本身没有误导，但它们把**四种不同性质的东西**排进了同一列格子——**管线的成熟度**（Naive → Advanced → Modular 是同一条单跳管线的三段形态）、**召回层的构成**（Hybrid RAG）、**控制流上的判定点**（Self-RAG / CRAG）、**证据的位置**（GraphRAG / Agentic）。前三族之间可以叠加，第四族是能力边界。一旦把「能力边界」与「工程复杂度」并排放进一张可加的表，两者的地位就被抹平了：前者决定系统的天花板，后者决定你维护得起什么。

真正决定选择的约束有六条，顺序不能颠倒。第一条是**回答所需的证据落在哪里**：如果证据落在某个片段里，那么「检索」这条路本身就是对的，剩下的只是取不取得到、排不排得前；如果证据跨多个片段、或需要沿关系走两跳，那么打分式检索在结构上就没有表达力，加大 top-k 只是把噪声一起取回来。这是能力边界而非性能权衡，所以它排在所有阈值之前。

第二条是**检索失败能不能在链路里被看见**。固定流水线的结构决定了它没有第二个判断点：检索发生在生成之前，而「有没有检到」只有看到结果之后才好判断。这条约束决定的不是「要不要更准」，而是「失败有没有补救路径」——它把 Self-RAG / CRAG 与前三族分开。第三条是**语料变更频率**：凡是要在索引阶段预计算结构的东西（实体关系、社区摘要），成本都随语料变更量重跑；语料天天变时，预计算结构从「一次投入」变成「一次次全量作业」。

第四条是**每次查询的预算与延迟敏感度**。精排的成本 ∝ 候选数 K 且与 QPS 相乘；反思与多轮检索的成本 ∝ 轮数，而轮数由模型判断决定、方差很大。两者都不是「多做一点就多拿一点」的项。第五条是**谁来维护**：同一套 RAG，在有检索平台团队的组织里能持续调优，在由应用团队顺带维护的组织里三个月后就没有人再跑评测——而检索质量下降不会报错，只会表现为「答得不太对」（[§5.3](05-rag-architecture-section-5-ai.md) 把这条写成了接口表里的一行）。第六条是**业务能不能接受拒答**：在不允许编造的场景里，「检索不到就不答」是唯一正确的降级；在内部助手这类场景里，拒答率过高会直接让工具失去使用价值。这条不写进任何技术选型表，却决定了流程约束能不能上线。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 证据落在哪里（单跳 / 跨片段 / 多跳） | 要不要改结构（GraphRAG）或改控制流（Agentic） | 「召回不够就加大 K、换更强的嵌入」——证据不在任何片段里时，这两件事都无效 |
| 检索失败能不能被看见 | 要不要加判定点（Self-RAG / CRAG） | 「把『不要编』写进提示词就够了」——祈使句不是控制流 |
| 语料变更频率 | 预计算式结构（图、社区摘要）能不能用 | 「建索引是一次性成本」——建图是重跑形态的作业 |
| 每次查询的预算与延迟敏感度 | 精排、反思、多轮能不能进高频在线 | 「多轮只是多花一点」——成本按轮数放大，且轮数方差很大 |
| 谁在维护这条链路 | Modular 的边界划在哪、默认值由谁负责 | 「模块化更先进」——没有第二个复用者时，抽象只有成本 |
| 业务能不能接受拒答 | 「无检索不生成」这类流程约束能否上线 | 「拒答是效果差」——在不允许编造的场景里，拒答是唯一正确的降级 |

读这张表要自上而下：第 1 行是**能力边界**（不满足时后面的讨论都无意义），第 2–4 行是**成本与补救路径的结构**，最后两行决定方案能不能活过第一年。

### 3.2 模式逐个拆解（核心节）

按「它改变的是管线上的哪一段」可分成四族：**管线成熟度**（3.2.1–3.2.3）、**召回构成**（3.2.4）、**控制流归谁**（3.2.5–3.2.6 与 3.2.8）、**证据位置**（3.2.7）。小节顺序按「它改变的是管线上的哪一段」排列：Hybrid 排在 3.2.4 与召回层相邻，Agentic 排在末位 3.2.8；Agentic 既属控制流族、又把取数范围扩到语料之外，因此控制流族被 3.2.7 隔成两段。真正的判据是 [§5.1](05-rag-architecture-section-5-ai.md) 的三层机制——**索引里放什么 → 查询怎么召回 → 控制流归谁**，同层内部多为替代，跨层之间多为叠加。

每个模式按六件事展开：被什么约束逼出来、结构、为什么这样设计有效、代价、失效点、真实使用，并在末尾附一条**核验方法**。**失效点最关键**：它回答「这个模式的优点在什么条件下反转成缺点」，而「缺点」只写到现象（召回率低、噪声大、无溯源），没有写它在什么条件下出现。

#### 3.2.1 Naive RAG（向量召回 + Prompt）

- **被什么约束逼出来**：需要一个能跑通的最小闭环，且证据确实落在单个片段里——先用最低成本验证「检索 + 生成」这条链路在你的语料上成不成立。
- **结构**：

```text
离线：文档 → 切分(chunk) → 嵌入 → 向量索引
在线：问题 → 嵌入 → 近似近邻 top-k → 拼 prompt → 生成

索引里每条记录只有「片段 + 向量」两项：
  { chunk_id, vector, text }
  ✗ 没有来源、版本、时间、密级、租户字段
  → 这些条件只能等检索回来之后再补，补不到就是过期或越权
链路上一共两个可调参数：切分粒度、top-k
```

- **为什么这样设计有效**：因为链路上只有一次相似度比较、没有第二个判断点，所以端到端行为完全由「切分粒度 + top-k」两个参数决定——这让它可以被低成本复现、低成本重建，也让一次语料更新只需重跑一遍嵌入。这正是它适合做验证基线的机制原因，而不是因为它「简单」。
- **代价**：切分粒度成了唯一的质量旋钮，而切分与嵌入模型是绑定的——**换任一项都要全量重建**；索引里没有元数据字段，意味着时效、密级、租户这些硬条件在结构上无处表达，只能事后裁剪（事后裁剪的越权风险见 3.5）；此外召回质量没有任何中间信号可观测。
- **失效点**：当**正确片段不在 top-k 里**时（跨措辞提问、ID 与型号、需要跨片段汇总），「链路最短、可复现」的优点反转成「失败不可见」——因为错误发生在检索侧，而错误的表现出现在生成侧：模型会把错的线索讲得更流畅。所以判据不是「答得对不对」，而是先分开统计「正确片段是否在召回集内」。
- **真实使用**：【公开】RAG 的原始论文（Lewis 等，NeurIPS 2020，检索器 + 生成器联合的架构）是这个模式的源头；【经验】它至今是多数团队的验证起点，也是 [§6 案例 6.2](05-rag-architecture-section-6-sec6.md) 里平台化之前的默认形态。
- **核验方法**：取 100 条真实问题（【经验】量级），逐条标注正确片段是否落在 top-k 内，算出 Recall@k。这个数不达标时，后面所有投入都是在错的方向上加钱。

#### 3.2.2 Advanced RAG（Pre-Retrieval + Post-Retrieval 优化）

- **被什么约束逼出来**：证据确实存在、也确实落在一个片段里，但「问题的表述」与「片段的表述」分布差得太远（口语化提问、指代、抽象概念），或者正确片段在召回集里但排位靠后。这两件事发生在管线的不同段，所以要用两段不同的手段。
- **结构**（召回前改查询、召回后改排序）：

```text
Pre-Retrieval（改查询，尚未检索）        Post-Retrieval（改候选集）
  · Query Rewrite  改写/扩写查询           · Rerank     交叉编码器对 (问题, 片段) 重排
  · HyDE           先假写答案再检索        · Compress   压到最小必要信息
  · Step-Back      先问更一般的问题        · 元数据过滤 时间/密级/租户（见下方 SQL）
  · 多查询扩展     一次改写成多个查询            · Lost-in-the-Middle 缓解
                                           证据置于上下文头尾、压掉中段冗余（位置效应）
        └── 改写发生在检索之前：改错了，连「为什么没命中」都看不出来 → 前后文本必须落盘
```

```sql
-- 元数据过滤：过滤发生在近邻搜索「之前」还是「之后」，决定召回是否被静默截断
SELECT id, chunk_text, embedding <=> $1 AS dist      -- pgvector 风格的距离算子
FROM   doc_chunks
WHERE  tenant_id = $2                                -- 硬条件：是否越权取决于它
  AND  updated_at >= now() - interval '90 days'      -- 时效条件
ORDER BY embedding <=> $1
LIMIT  20;
-- 对照测法：同一条查询跑「带过滤」与「不带过滤」两个版本，比返回条数与命中
-- 并用 EXPLAIN 确认过滤是否下推到索引扫描，而不是扫描之后再裁剪
```

- **为什么这样设计有效**：因为精排模型看的是「问题 + 片段」的整体而不是两个独立向量，所以它能对召回集里的顺序重新算一遍，端到端失败因此从「检索不到」（无解）变成「排序不高」（可改善）；又因为改写改变了查询在向量空间里的落点，它修的是「问法与写法不一致」这一类分布差，而这一类问题靠换更大的嵌入模型是修不掉的；又因为长上下文里的信息利用率随位置衰减——证据沉在上下文中段时最容易被忽略（【公开】Liu 等，2023 年论文《Lost in the Middle》），所以压缩与位置重排修的是另一类失败：证据已经检到、却没有被读进答案。
- **代价**：链路从 1 个模型变成 3–4 个模型（改写、嵌入、精排、生成），每一次升级都要重跑一轮回归；精排的前向次数 ∝ 候选数 K，与 QPS 相乘，所以 K 只能由延迟预算反推（常见取 50–100，【经验】），不能由效果倒推；改写引入一类新故障——把原问题里的实体或时间条件改掉了，而它发生在检索之前，出错时症状与「语料里没有」完全一样。
- **失效点**：当**召回集里根本没有正确片段**时，「精排把正确结果排上来」的优点反转成「把召回缺失掩盖得更深」——因为精排只能在已召回的集合里重排，同时它把明显不相关的结果排下去，于是「召回缺失」这条症状更难被看见。判据很直接：在看精排收益之前，先看 Recall 是否已经达标；Recall 高而 nDCG 低才是排序问题。
- **真实使用**：【公开】HyDE 一类方法（2022–2023 年预印本，具体篇目以论文库当前版本为准，本主题的机制说明见 [§5.2.1](05-rag-architecture-section-5-ai.md)）；【公开】把「混合检索 / RRF 检索器 / 过滤下推」写成正式文档条目的向量库与检索引擎——本节具名三家：Milvus 的多路向量检索与标量过滤、Elasticsearch 的 RRF 检索器、pgvector 的索引与过滤查询计划（三者的功能命名与引入年份互不相同，请按「产品名 + 该功能名」在各自官方文档及发布说明中核验条目与年份，并以当前版本为准）；【经验】它同时是多数生产 RAG 的起点形态。
- **核验方法**：把失败样本分成两组——「正确片段不在召回集里」与「在但排位靠后」。两组比例决定该修改写、该修精排，还是该改结构（见 3.2.7）。

#### 3.2.3 Modular RAG

- **被什么约束逼出来**：不止一个应用要用 RAG，且每个应用的调参经验无法迁移到下一个；同时组织希望「一次升级只影响一段」，而不是每次改动都要重跑一条端到端链路。其约束的实质是**复用次数**与**回归范围**。
- **结构**（模块之间以显式契约为界，而不是以函数调用为界）：

```text
模块边界与契约（谁调用谁、数据以什么形态穿过边界）
  [Query 理解] ──查询(改写后文本 + 过滤条件)──▶ [检索]
  [检索]       ──片段列表(id, text, score, 来源, 版本)──▶ [重排/压缩]
  [重排/压缩]  ──证据片段(带来源)──▶ [生成] ──答案 + 引用──▶ [评估]

关键设计：
  · 每个模块独立版本化、独立回滚；一次升级的回归范围 = 该模块的契约
  · 平台给经验默认值（切分粒度、top-k、是否开精排），业务方按需覆盖
  · 失败归属写进契约：召回失败由检索侧负责，不许推给生成
  → 收益来自复用次数：第三个接入方开始，默认值就是净收益
```

- **为什么这样设计有效**：因为模块之间以「查询 + 过滤条件」「片段 + 来源 + 版本」这样的显式契约为界，所以一次升级的回归范围可以被界定在某一段之内（换精排模型不必重跑检索）；也因为同一套模块被多个应用复用，调参经验从「每个应用各摸索一遍」变成一次投入——这是它相对「每个应用自建一遍」的实质差别，而不是架构上的讲究。
- **代价**：模块边界本身就是运维面——每个模块都要版本化、要有 Owner、要能单独回滚；契约一旦不兼容，所有接入方同时受影响；更隐蔽的一项是把「调参责任」显式化了：平台给默认值之后，业务方仍然要知道自己覆盖了什么，否则线上行为变化时无人说得清差异来自哪一层。
- **失效点**：当**接入方只有一两个、且平台与业务是同一批人**时，「一次做好、多处复用」的优点反转成「多了一层抽象与一套版本管理，却没有第二个复用者来分摊」——因为模块化的成本是固定发生的，收益随复用次数增长。判据是先数接入方：复用次数不超过两次时，先把单条链路做对，再抽模块。
- **真实使用**：【经验】字节的扣子 Coze 把知识库接入、分块、向量化、检索、重排、生成各做成可配置节点、由平台给默认值，是这一模式的样本（[§6 案例 6.2](05-rag-architecture-section-6-sec6.md) 记录了这条链路；该案例的出处在 §6 是区间式标注「字节扣子 Coze 公开材料 2020-2024」，不含可检索的标题与链接，因此本条按【经验】计；节点划分请按「扣子 Coze + 知识库 / 节点编排」核验其官方文档当前版本）；【公开】Modular RAG（GAIR Lab，2024 年预印本）把 RAG 拆成「索引 / 检索 / 重排 / 生成 / 反馈」五个可替换模块（同一划分见本章 §7 与主文件 §2.3），是本主题把方向归类时的一处参照；它与本章 [§5.1](05-rag-architecture-section-5-ai.md) 的三层机制划分（索引里放什么 / 检索结果怎么变成上下文 / 谁决定检索）层数与名称都不同——注意它是架构综述，不是能力清单。
- **核验方法**：数一次「换嵌入模型要重建几套索引、跑几轮回归」。若这个数等于应用数量，说明模块化只停在文档里。

#### 3.2.4 Hybrid RAG（三路召回 + RRF 融合）

- **被什么约束逼出来**：不同类型的问题需要不同的匹配方式——语义近似、精确 token（单号、型号、错误码）、关系。而单路召回的失败模式无法通过调参消除：一路漏「词面不同意思相同」，另一路漏「意思不同词面相近」，这两类错误来自不同原因。
- **结构**：

```text
[问题] ─┬─▶ [向量召回 Top-Kv]  ─┐
        ├─▶ [BM25 召回 Top-Kb] ─┼─▶ [RRF 融合] ─▶ [精排] ─▶ [组装上下文] ─▶ [生成]
        └─▶ [KG 遍历/社区摘要] ─┘
              score(d) = Σ_r 1 / (k + rank_r(d))，k 常取 60【公开】（Cormack 等，SIGIR 2009）
              → 融合只消费「名次」，不消费分数
                ⇒ BM25 分数无上界、余弦相似度挤在窄区间这个量纲问题被消掉
                ⇒ 代价是置信度也被丢掉：高相似度命中与勉强进前十可能同权
                ⇒ 想让某一路更重，应调该路的取数数量，而不是给公式加权
```

- **为什么这样设计有效**：因为 RRF 只吃名次不吃分数，所以异构检索器（倒排、向量、图）不需要做分数归一化就能融合，接入一个新检索器的成本从「调权重、做分数标定」降到「接一个排名列表」；而每接一路，能被覆盖的查询类型就多一类——精确关键词交给倒排、语义近似交给向量、关系交给图。融合的收益全部来自两路错误的**不相关**，这是它成立的唯一前提。
- **代价**：多一路就多一套「编码模型版本 + 索引版本 + 重建流程」的对应关系，任何一次模型升级都要跑多次重建与多次回归；丢掉置信度意味着 CRAG 一类的判定拿不到输入（见 3.2.6），需要另加规则才能区分「命中得很实」与「勉强挤进前十」；三路的语料必须同源同版本，否则融合的是两个不同快照的排名，结果不可解释。
- **失效点**：当**两路实际同源**时（共用同一个查询改写结果，或稀疏侧由稠密模型蒸馏而来），「错误不相关所以并集上限更高」的优点反转成「融合收益趋近零、成本照付」——因为两路漏的是同一批文档。判据是并集 Recall@K 相对较优单路的提升幅度：落在标注噪声量级之内（几百条问题的标注集上大致 3–5 个百分点，【经验】）即按高度重合处理。
- **真实使用**：【经验】企业知识中台与电商搜索栈的常见形态，与 [04-hybrid-search §3](../04-hybrid-search/04-hybrid-search-section-3-sec3.md) 同源（那一节给出双路/三路的结构与各自的失效分析）；【公开】RRF 的原始论文（Cormack、Clarke、Buettcher，SIGIR 2009，给出「只用名次融合」的机制与实验）。
- **核验方法**：同一问题集分别跑单路与双路，比较**漏召回集合的交并比**与**并集 Recall@K 的提升幅度**。交并比解释原因，提升幅度才决定加不加路。

#### 3.2.5 Self-RAG（生成中反思）

- **被什么约束逼出来**：固定流水线在检索**之前**就决定了检索几次，而「有没有检到」只有看到结果之后才好判断——于是「检索不到」这件事在结构上没有补救路径。把「检索不到就别答」写进提示词也没用：它是一条祈使句，不是控制流，模型照答不误。
- **结构**（把判定放进生成循环）：

```text
生成 ──▶ [Retrieve]?  需要检索吗        ── 否 ──▶ 继续生成
            │是
            ▼
        检索 Top-k ──▶ [IsRel]?  片段相关吗 ── 否 ──▶ 丢弃，换查询或放弃
            │是
            ▼
        生成 ──▶ [IsSup]?  有证据支持吗 ── 否 ──▶ 回到检索
            │是
            ▼
        [IsUse]?  对回答有用吗 ──▶ 输出

控制流归模型 ⇒ 必须同时给三个上界，否则把线上成本交给不可预测的控制器：
  轮数上界（常见 2–3 轮【经验】）· 单次预算上界 · 每轮检索与判定必须落盘
```

- **为什么这样设计有效**：因为判定发生在看到初步结果之后、且与生成在同一个循环里，所以「检索不够就再检一次」从一句请求变成一条可执行的控制流——这是固定流水线里没有补救路径的那类问题第一次有了补救路径。它换来的不是「更准的检索」，而是「失败可补救」这个性质。
- **代价**：控制流交给概率模型之后，延迟与成本不再有上界——轮数由模型判断决定、方差大，尾部延迟明显拉长；可复现性下降，同一问题两次请求可能走不同轮数，线上排障必须把每一轮的检索与判定都落盘；第三项代价最隐蔽：反思能力依赖模型是否被专门训练过这套标记，在通用模型上直接套提示词，得到的往往是「看起来在反思」的文本，付出延迟只换来措辞。
- **失效点**：当**把它放进高频在线路径**时，「按需检索」的优点反转成「成本与延迟不可预测」——因为方差乘以 QPS，容量与预算都要按最坏轮数准备，而长尾轨迹会打满下游检索集群。判定方法：同一问题连问 5 次（【经验】），记录轮数与总耗时；轮数波动大时，先设上界再谈效果。
- **真实使用**：【公开】Self-RAG（2023 年预印本、ICLR 2024；核心是反思标记 + 专门训练，缺了训练这一步复现不了论文效果，[§5.2.3](05-rag-architecture-section-5-ai.md) 对此有展开）；【公开】FLARE 一类主动检索（2023 年会议论文，按生成过程中的置信度决定何时检索）。两者都缺独立的第三方生产采用材料。
- **核验方法**：确认你所用的模型是否被专门训练过这套反思标记。若没有，你付出的是延迟，换来的是措辞——此时应退回到固定规则判定（3.2.6）。

#### 3.2.6 Corrective RAG（CRAG）

- **被什么约束逼出来**：检索一定会返回东西（top-k 永远填满），所以「检索到了」不等于「检索对了」。需要一个在**生成之前**的判定点，而且这个判定必须挂一个可执行的动作，否则判定等于没判。
- **结构**（判定 → 分流 → 动作）：

```text
[检索] ─▶ [可信度判定器]
              │
   高可信 ────┼──▶ 直接用（可选：分解再重组，去掉无关片段）
              │
   低可信 ────┼──▶ 丢弃这一轮检索结果 ──▶ 转外部检索 / 换查询重检
              │
   中可信 ────┴──▶ 两者并用（内部片段 + 外部结果 一起进上下文）

对应三档「高 / 中 / 低 → 直接用 / 精炼 / Web 兜底」
关键：每条分支都必须有动作；没有动作的判定只是展示

不允许编造的场景里，判定可以退化成一条业务规则：
  命中为空 或 命中分数 < 阈值 ──▶ 拒答 / 转人工（见 §6 案例 6.4「无检索不生成」）
```

- **为什么这样设计有效**：因为它把「检索结果可不可信」做成了一个显式的三态判定、且每条分支都有动作，所以检索失败从一个隐形事件变成一个被处理的事件；这也是它与「加大 K」的实质差别——加大 K 只会把更多噪声放进上下文，而判定点会把它挡在上下文之外。
- **代价**：判定器本身就是新的失效点——它是一个额外的模型或阈值，会误判；阈值是一个要随语料与模型版本长期校准的参数；而「转外部检索」引入一个不受控的依赖（延迟、成本、合规边界、来源可信度），等于把系统的一部分正确性交给链路之外的东西。
- **失效点**：当**判定器不可靠或阈值长期不校准**时，「不可信就重检索」的优点反转成「把正确答案丢掉、把噪声引进来」——因为三态判定是阈值化的，而检索质量是连续的，两个方向的误判代价并不对称（漏判会去编造，误判只是多花成本）。修法是分别统计两个方向的错误率，并与人工标注对齐；不能只统计一个总体的准确率。
- **真实使用**：【公开】CRAG（2024 年预印本，检索后可信任度判定 + 外部检索回退）；【经验】在不允许编造的场景里，判定点是不可省的，但判定不必由模型做——[§6 案例 6.4](05-rag-architecture-section-6-sec6.md) 的银行 RAG 客服把「检索结果为空或置信度不足」直接接到「无法回答 / 转人工」，用的就是流程约束而不是模型判断。
- **核验方法**：查两个数——判定器两个方向的错误率，以及阈值上一次被校准是什么时候。阈值从未被校准过的判定，实际上是一条固定规则。

#### 3.2.7 GraphRAG

- **被什么约束逼出来**：有一类问题的答案不落在任何单个片段里——跨文档对比、全局性归纳、沿关系走两跳。此时把问题交给生成模型，它只能在场内自己编关系，这正是「跨文档推理」失败的机制，而不是提示词没写好。
- **结构**（把推理的一部分挪到建索引阶段）：

```text
离线（重跑形态的作业，成本 ∝ 语料变更量）：
  语料 ──▶ LLM 抽取 (实体, 关系) ──▶ 实体对齐 ──▶ 社区检测 ──▶ 逐社区生成摘要

在线（查询时只做遍历与检索，不做推理）：
  实体链接 ──▶ Local Search   取回相连实体的描述与片段
  社区摘要 ──▶ Global Search  取回全局视图，回答「这几份文件讲的有没有冲突」

关键：索引阶段就把「关系」和「摘要」算好 ⇒ 在线不必把大量原文塞进上下文
      代价同源：每篇文档变更都要重抽 + 重对齐，可能触发社区重算
```

- **为什么这样设计有效**：因为它把「关系」从查询时算挪到建索引时算，所以「沿关系走两跳」从让模型在文本里猜变成一次图遍历——多跳由此从**模型能力问题**变成**数据结构问题**，而数据结构问题是可以被工程解决的；又因为社区摘要在索引阶段已经生成，宏观问题不再需要把大量原文塞进上下文。
- **代价**：【推算】设语料 100 万篇、平均 500 token/篇，则一次全量抽取的输入规模约为 100 万 × 500 = 5 亿 token（【推算】，推导链是「篇数 × 每篇 token 数」），社区摘要还要在这个结果上再跑一遍生成。这个量级的意义不在于绝对费用，而在于**建图必须被当成一条数据加工流水线来运维**（分区、重跑、版本、失败重试），而不是一个「建索引」步骤；抽取质量决定上限——漏掉实体，后面的遍历不存在；抽错关系，错误会以「看起来合理的错误关系」进入答案，比检索不到更难发现。
- **失效点**：当**语料高频变更、而多跳与汇总类问题占比低**时，「覆盖关系与跨文档推理」的优点反转成「图永远在重建」——因为每篇变更文档都要重抽与重对齐，成本随变更量线性增长，而收益只落在那部分问题上。判据：标注问题集中「需要跨文档汇总或多跳」的比例，与语料日变更比例放在一起读；多跳占比 ≲ 10–20%（【经验】）或语料每天大幅变更时，先别为全部语料建图。
- **真实使用**：【公开】Microsoft GraphRAG 开源项目（2024 年起发布，文档给出从文本到社区摘要的完整流程与 Local / Global 两种查询）；【公开】Leiden 社区检测算法（2019 年论文，是该流程里划分社区的常用方法）；【公开】LightRAG 与 HippoRAG（2024 年预印本，分别做轻量化与更接近联想式记忆的图结构）。可核到的效果材料以项目方与采用方自述为主。
- **核验方法**：统计一次建图流水线的输入 token 量与最近一次全量重建的耗时，再看它有没有失败重试与版本；把这两个数与「多跳问题占比」放在一起读，就能判断它是在提供能力还是在消耗团队。

#### 3.2.8 Agentic RAG

- **被什么约束逼出来**：问题形态跨度极大——有的落在一篇文档里，有的要跨系统取数（订单、库存、工单、文档各是一个源），而系统事先无法区分。固定管线只能取一个折中值：难问题上取数不足，易问题上取得过多。
- **结构**：

```text
[问题] ─▶ [Agent 规划] ─┬─▶ 调向量检索 / 调 KG / 调 SQL / 调 Web / 调工具 API
                        ▼
                    [判断证据够不够]
                        ├─ 不够 ─▶ 改写查询 / 换一路 / 换工具 ──▶ 回到规划
                        └─ 够了 ─▶ 整合 ─▶ 作答

与固定管线的差别：路数与顺序由「中间结果」决定，不由配置决定
  ⇒ 它是控制流的改变，不是又多了一路召回
  ⇒ 必须为每次调用配限流与超时：一次失控的规划会打满下游检索集群
  ⇒ 成本按「平均轮数 × QPS」增长，但方差大 → 容量按 P99 轮数准备
```

- **为什么这样设计有效**：因为轮数与路径由中间结果决定，所以它能在难问题上多花算力、在易问题上少花，而固定管线只能取一个折中值——这解释了它为什么只适合低频高价值的查询（复杂分析、跨源调查），而不是通用的在线入口。
- **代价**：成本与延迟的**方差**远大于固定管线（同一问题可能走 2 轮也可能走 8 轮），容量规划必须按 P99 轮数做而不是按均值；同一问题的检索轨迹不唯一，使离线评估不可复现，回归测试需要比固定管线更大的样本量才有统计意义；此外它把「检索该不该发生」也交给了模型，于是检索侧的指标（Recall@k）不再单独决定端到端结果，排障要先分清是没检索、检索了没用上，还是根本没决定检索。
- **失效点**：当**把高频在线 QPS 交给它**时，「灵活」的优点反转成「不可预测」——因为方差乘以 QPS 之后，成本与容量都要按最坏情况准备，长尾轨迹会打满下游。这正是每次调用必须配限流与超时的原因：Agent 不修改索引、只组合调用，一次失控的规划打的是整条链路。
- **真实使用**：【公开】OpenAI 把知识（文件检索）与能力（工具调用）在架构上解耦，让检索回到「工具之一」的位置；其对外形态是 Assistants API 的 File Search（把文件检索做成一个可调用的工具）与 GPTs 的知识挂载，年份落在 2023–2024 年间，具体命名与版本请以 OpenAI 官方文档当前版本为准（[§6 案例 6.3](05-rag-architecture-section-6-sec6.md) 即此案例）——这是 Agentic 形态成立的前提条件，而不是它本身的实现；【经验】它当前适合低频高价值的复杂查询入口。
- **核验方法**：取一批真实问题跑一遍，统计**轮数的 P99 与均值之比**。比值呈长尾时，只把它挂在低频入口上，不放进高频在线路径。

把 8 个模式的「换来的性质」与「性质反转的条件」并排放一次，失效点这一维就清楚了：

| 模式 | 它换来的性质 | 性质在什么条件下反转 |
| --- | --- | --- |
| Naive | 链路最短、可复现、可低成本重建 | 正确片段不在 top-k 里时，失败在生成侧才显形 |
| Advanced | 排序可改善、问法差异被抹平 | 召回集里没有正确片段时，精排把缺失掩盖得更深 |
| Modular | 一次升级只影响一段，默认值可复用 | 接入方不超过两个时，抽象只有成本 |
| Hybrid | 两路错误不相关 → 并集上限高于任一路 | 两路同源时，融合收益趋近零而成本照付 |
| Self-RAG | 检索失败有补救路径 | 放进高频在线时，方差乘以 QPS |
| CRAG | 检索失败被显式处理 | 阈值长期不校准时，两个方向的误判代价不对称 |
| GraphRAG | 多跳从模型能力问题变成数据结构问题 | 语料高频变更且多跳占比低时，图永远在重建 |
| Agentic | 按问题难度分配算力 | 放进高频路径时，容量要按 P99 轮数准备 |

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| PoC / 语料小而干净 / 证据落在单篇 | Naive RAG | 上 Advanced 的每一段都要人维护，此时没有可评估的东西 | 正确片段是否落在 top-k 内 |
| 生产级 / 单跳为主 / 专有名词多 | Advanced RAG + Hybrid（向量 + BM25 + RRF） | 只换更大的嵌入模型解决不了排序问题，也补不了另一类查询 | Recall 高而 nDCG 低 → 排序问题；两路漏召回是否高度重合 |
| 多业务线 / 多应用复用同一套 RAG | Modular RAG | 每个应用自建一遍，调参经验无法迁移 | 接入方数量是否会超过两个 |
| 高准确性 / 不允许编造 | CRAG（判定点 + 拒答/转人工） | 提示词里的「不要编」不是控制流；判定点不能省，但可以退化成业务规则 | 判定两个方向的错误率 + 阈值最近一次校准时间 |
| 需要在生成中动态决定是否再检索 | Self-RAG | 通用模型缺专门训练，复刻不了论文效果 | 模型是否被专门训练过这套反思标记 |
| 宏观问题 / 跨文档汇总 / 多跳 | GraphRAG | 加大 K 与更强的生成模型都补不回缺失的关系 | 多跳与汇总类问题占比 + 语料日变更比例 |
| 复杂多跳 + 跨系统取数 / 低 QPS | Agentic RAG | 固定管线的取数在两端都不合适 | 轮数 P99 与均值之比 |
| 实时性高 / 知识频繁更新 | CRAG 的外部检索回退（慎用） | 兜底依赖外部来源，延迟与合规边界不受控 | 外部来源是否在合规边界内、能否留痕 |
| 多模态 / 图文混排 | 混合召回 + 多模态嵌入 | 纯文本嵌入看不到版面与图表；双塔图文嵌入（【公开】CLIP，Radford 等，ICML 2021）在同模态内可用、跨模态细粒度弱 | 检索单元是「页」还是「字符」（见 [§5.2.4](05-rag-architecture-section-5-ai.md)） |
| 中文为主 / 跨语言语料 | 多功能嵌入（如 BGE-M3 一类）+ 精排 | 词法路要为每种语言单独维护分词与词干化，质量参差 | 语料里有几种语言；嵌入模型支持的语言以模型卡当前版本为准 |
| 召回够、排序不够 | 交叉编码器精排，K 取 50–100（【经验】） | 换嵌入模型：召回没坏，换模型解决不了排序 | Recall 达标而 nDCG 不达标 |

本主题下最常被误选的一对是**「Advanced RAG 与 GraphRAG」**，而误选的依据通常是「我们的问题越来越难，所以要把管线做强」——于是不断加大 K、换更大的嵌入模型、上更强的精排。这三种手段都在同一个前提里运作：**证据存在于某个片段里**。后果不是系统不工作，而是系统**看起来在改进**：单点事实类问题的指标确实在动，而跨文档汇总类的失败率不动；更糟的是精排会把不相关的结果排下去，让「召回缺失」更难被看见。正确的第一步不是升级管线，而是给问题集打标：先数一遍「需要跨文档汇总或多跳」占多少。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Advanced（管线）+ Hybrid（召回层）**。Advanced 是管线的成熟度，Hybrid 是召回层的构成，两者不是替代关系——[§7.6](05-rag-architecture-section-7-sec7.md) 的组合 4（向量 + BM25 + 知识图谱三路召回）写的就是这一对里的召回层那一半。职责边界很清楚：召回层只负责「把正确的证据放进候选池」，不判断「够不够回答」；判断属于生成层或 Agent。运维代价最低，但要盯住召回质量与生成质量**两个独立指标**的分解，否则会把生成的问题误判成召回的问题。适合全部规模的生产 RAG。

**组合二：Modular（平台）+ CRAG 判定点**。平台把「生成前的判定」做成一个可配置模块，业务方只管定阈值与兜底动作（拒答 / 转人工 / 走外部检索）。职责边界是：平台提供形态与默认值，业务方按场景风险定分级——[§6 案例 6.4](05-rag-architecture-section-6-sec6.md) 就是「命中为空或置信度不足即拒答」的形态。运维代价是判定阈值要随语料与模型版本重新校准，且这套校准要有 Owner。适合多业务线、有合规要求的组织。

**组合三：Hybrid（召回）+ GraphRAG / Agentic（控制流增强）**。向量与 BM25 负责「找到相关段落」，图负责「找到关系上相连但语义不相似的实体」，Agent 负责「决定这一次该调哪一路、调几次」。职责边界是：图不承担相似度排序，向量不承担多跳，Agent 不修改索引、只组合调用。运维代价是图需要更新流水线（抽取 + 对齐 + 摘要）、Agent 需要轨迹可观测与逐次限流。适合多跳占比可观、且查询频次低而价值高的语料。

三条组合有一个共同要求：**每个组件挂掉时系统降级成什么，必须能一句话说清。** 改写挂了降级为用原问题检索（质量下降但可用）；精排挂了降级为融合结果（顺序变差但可用）。最容易被忽略的是判定器：它故障时的默认行为决定了系统在最坏情况下是「答得少」还是「编得多」——不允许编造的场景里，默认必须是拒答。

组合还有一条否决线：**如果两件东西的正确性互为对方的输入，就不能组合。** 例如「用反思判定去决定要不要重新检索、再用重新检索的结果去修正判定」——这个环在任何一段抖动时都会变成「时好时坏、无法复现」的系统。组合能分担负载、能分担运维，唯独分担不了正确性。

### 3.5 反模式与失效分析

下表 10 条反模式。四列回答四个不同的问题：**怎么发现它、它按什么机制造成损失、团队为什么会写成这样、改什么。**

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 全部塞进 Prompt | 上下文长度顶到窗口上限，成本随文档库增长 | 注意力被摊薄、无法溯源，成本按 token 线性放大 | 把「模型没看过」误判为「模型看得不够多」 | 切分 + 检索，只放进被检索选中的片段 |
| Embedding 万能 | 换了更大的嵌入模型后指标几乎不动 | 嵌入只改变「候选集里有没有」，改变不了「候选集里的顺序」 | 把检索当成一个模型选型问题 | 先测召回上限，再决定是加路、精排还是改写 |
| Chunking 越细越好 | 召回条数变多但生成质量下降，答案常被切断 | 切分粒度决定「检索单元 = 证据单元」是否成立，切太细时答案不落在任何单元里 | 把「召回条数」当成召回质量的代理指标 | 按证据单元（段落 / 小节 / 页）切，并用「答案是否落在单个 chunk 内」评估 |
| 不用 Reranker | 融合后的 Top-10 里明显不相关的结果混在前面 | 粗排顺序直接决定喂给生成的证据质量，而这类失败在指标上表现为「答得不太对」而不是报错 | 精排是一次额外的在线成本，先省掉 | 只对 Top-50~100 做交叉编码器精排（【经验】） |
| 忽视元数据过滤 | 检索到过期、越权、跨租户的内容 | 过滤放在生成后时，被过滤的证据已经进入过模型上下文；放在检索侧则从未进入链路 | 把检索当纯语义问题，忽略时效与权限是硬条件 | 过滤在检索侧下推，不在生成后裁剪 |
| Prompt 模板过于复杂 | 提示词里堆满规则，模型仍不遵守 | 提示词是请求不是控制流，规则越多越难验证哪条在起作用 | 把控制流问题当成措辞问题 | 把硬约束做进流程（无检索不生成），提示词只留角色与输出格式 |
| 不评估 | 无法回答「这次改动有没有让效果变差」 | 检索质量下降不报错，只表现为「答得不太对」；没有固定问题集时，调参把噪声当收益 | 评测集建设成本高，且失败不报警 | 建固定问题集（查询 + 正确片段标注），把召回失败与排序失败分开统计；自动指标用 RAGAS / TruLens 一类框架，但「忠实性」在各框架里定义不同，跨框架分数不可比 |
| 盲目 GraphRAG | 为全部语料建了图，多跳问题却占比很低 | 建图是重跑形态的作业，语料一变更就重算，收益只落在少数问题上 | 把「能做多跳」当成「每个问题都该走多跳」 | 只对需要汇总 / 多跳的那部分问题建图 |
| LLM 当真理 | 用同一个模型既生成答案、又当裁判、又做反思判定 | 裁判与被测同源时错误高度相关，指标稳定而系统在退化，幻觉在闭环里传播 | 人工标注成本高，想用模型替代 | ground truth 必须独立于被测链路（人工标注 / 业务规则），或换族系交叉验证并抽样人工核 |
| 忽视成本 | 账单先于指标报警 | 精排成本 ∝ QPS × K，多轮检索成本 ∝ 轮数，两者的方差结构不同 | 只在离线指标上看效果 | 分级模型 + 缓存 + 抽样开精排 + 给控制流设上界 |

三个最危险的反模式值得单独说。**「Embedding 万能」与「不用 Reranker」是同一处误解的两面**：前者以为换嵌入能救排序，后者以为省掉精排影响不大——而**召回与排序是两个不可互相替代的阶段**（融合不能创造候选集里不存在的文档，精排只能在已召回的集合里重排），所以投入顺序必须是先修召回、再修排序。判据只有一条：把失败样本按这两个阶段分开数。

**「LLM 当真理」危险在它同时出现在两个位置**：离线评测里的裁判模型，与线上反思 / 判定。两处都是把「正确性」交给一个与被测对象同源的概率模型，于是系统会收敛到「自洽」而不是「正确」，而且指标不会报警——它会稳定地给出好看的分数。修法不是换个更贵的裁判，而是让 ground truth 回到链路之外。

**「忽视元数据过滤」危险在它伪装成召回问题**：用户真正的需求是「最新 + 我有权看 + 这个租户」，团队却在调融合权重与候选数；召回指标看起来在变好，业务指标不动，因为正确答案本来就在被过滤掉的那部分里。而在权限这一维上，它还会从效果问题升级为事故——被过滤的证据曾经进过模型的上下文，模型可能在答案里泄露它的存在。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| PoC → 生产 | Naive | 问题类型变多，单路召回的天花板暴露 | Advanced + Hybrid | 加改写与精排两段；固定问题集要重建 |
| 单跳 → 出现跨文档汇总 | Advanced | 答案不在任何单个片段里，加大 K 只是加噪声 | GraphRAG（或对少数问题走 Agentic） | 建图流水线（本表最重的一项） |
| 单应用 → 多应用 | Advanced | 每个应用各自调参，经验不可迁移 | Modular RAG | 平台团队 + 模块版本与 Owner |
| 允许编造 → 不允许编造 | Advanced | 提示词约束不是控制流 | CRAG 判定点 + 拒答 / 转人工 | 阈值校准与长期维护；业务侧要接受拒答率 |
| 单语 → 跨语言 | 中文嵌入 + 中文精排 | 词法路要为每种语言单独维护分词与词干化 | 多功能嵌入 + 精排 | 全量重建 + 分语言评测集 |
| 文本 → 图文混排 | 文本切分 + 文本嵌入 | 版面与图表在解析中丢失，检索单元与阅读单元不一致 | 页面级多模态检索（[§5.2.4](05-rag-architecture-section-5-ai.md)） | 索引体积按像素与页数增长（【经验】数十倍到上百倍，随分辨率与块大小变化）；权限模型要重新对齐 |
| 固定管线 → 加控制流 | Advanced | 想让「检索失败可补救」，但方差乘上 QPS 后成本不可控 | 控制流只放低频入口，或退化为固定规则判定 | 轨迹落盘、限流、按 P99 轮数备容量 |
| 全量精排 → 抽样精排 | 全量精排 | QPS × K 的前向次数超过单机可承担量级 | 只对头部流量开精排（例如 10%，【经验】） | 两套结果的对比与灰度；评测口径要能分解 |

跃迁表里有一条贯穿全部行的约束：**任何一次「换了嵌入模型或切分策略」的迁移都会让历史评测数据作废。** 分数分布变了、召回集变了，旧的阈值、旧的 K、旧的融合参数全部要重调，旧的问题标注还要重新确认「切分是否仍切在同一位置」。工程上的做法是把「问题集 + 切分版本 + 嵌入模型版本 + 检索参数」作为一组统一打版本号，迁移时整组替换；只换模型、不换评测集这种半换，是这类项目里最常见也最难察觉的质量回退来源。

还有一条与模型无关的迁移约束：**迁移必须先在离线问题集上完成可比性验证，再上线切流。** 因为检索质量没有硬性报错，「新方案更好」这件事只可能在固定问题集上被证明；一旦上线后才发现问题，你会同时失去旧的基线与判断依据。可操作的做法是把迁移拆成四段：离线问题集上新旧双跑并人工比对差异 → 小流量双跑看业务指标 → 切流 → 保留旧路一个周期做回退。

### 3.7 自检清单

- [ ] 失败样本有没有按「正确片段不在召回集里」与「在但排位靠后」分开统计？（混在一起统计等于什么都没测）
- [ ] 语料切片后，答案是否仍然落在单个 chunk 内？「答案被切断」与「答案跨 chunk 未拼上」是两类不同的修法。
- [ ] 索引里除了向量，是否还有来源、版本、时间、密级、租户字段？缺了它们，硬条件只能事后补。
- [ ] 权限过滤是在检索侧下推的，还是在生成后裁剪的？（后者意味着越权内容进过模型上下文）
- [ ] 改写步的前后文本有没有落盘？改写把实体或时间条件改没了时，这是唯一能看出来的证据。
- [ ] 关掉精排、关掉判定点、关掉图之后，系统还能不能返回答案？能返回的是增强项，不能返回的是路径项。
- [ ] 判定点故障时的默认行为是拒答还是放行？这个默认值决定最坏情况下系统是「答得少」还是「编得多」。
- [ ] 建图之前，有没有统计过「需要跨文档汇总 / 多跳」的问题占比与语料日变更比例？
- [ ] 控制流（反思 / 多轮 / Agent）有没有轮数上界、单次预算上界与逐轮落盘？同一问题连问 5 次（【经验】）的轮数波动有多大？
- [ ] 评测的 ground truth 是不是独立于被测链路？用被测模型当裁判，测的是自洽而不是正确。
- [ ] 「问题集 + 切分版本 + 嵌入模型版本 + 检索参数」有没有一起打版本号？换模型时是否整组替换？
- [ ] 多路召回的几路是否语料同源同版本？不同快照的排名融合，结果不可解释。

这 12 条里，第 1–2 条是**诊断项**（先看清问题在哪一段），第 3–5 条是**结构项**（决定方案的形状与安全边界），第 6–8 条是**能力边界项**（决定该不该加深结构），第 9–12 条是**运维项**（决定它能不能长期活下去）。诊断项性价比最高：它们大多只需要一两天标注（【经验】），却能一次性回答「该加路还是该改结构」。最容易被跳过的是第 1 条与第 7 条——前者决定后面所有投入的方向，后者决定部分组件故障时系统是少答还是乱答。

### 3.8 小结

把本节所有结论压成一句：**检索增强生成的每一个模式，都在回答同一个问题——「回答所需的证据，能不能用一次检索取回」。** 能取回时，剩下的全部选择都发生在「取不取得到、排不排得前、错了能不能补救」这三个工程变量上；取不回时，任何模型侧或参数侧的投入都无效，只能改结构（把关系预计算进索引）或改控制流（让模型多取几次）。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 只是验证链路 | Naive RAG | 链路最短、可复现，先拿到召回基线再谈优化 |
| 单跳为主、专有名词多 | Advanced + Hybrid（+ RRF） | 两路失败模式互补；精排只能重排已召回的集合 |
| 召回达标、排序不达标 | 交叉编码器精排，K 取 50–100（【经验】） | 精排成本 ∝ K，K 的上限由延迟预算反推 |
| 多业务线、多应用复用 | Modular RAG | 收益来自复用次数；接入方不超过两个时先别抽 |
| 不允许编造 | CRAG 判定点 + 拒答/转人工 | 把「不要编」从提示词请求变成流程上的硬约束 |
| 需要生成中动态决定再检索 | Self-RAG（并设轮数上界） | 反思标记依赖专门训练；通用模型上只得到措辞 |
| 跨文档汇总 / 多跳 | GraphRAG | 多跳是数据结构问题，加大 K 解决不了 |
| 跨系统取数、低频高价值 | Agentic RAG | 轮数由中间结果决定，代价是方差与可复现性 |
| 语料高频变更 | 不加预计算结构（不加图、少用晚交互） | 预计算结构的成本随变更量重跑 |
| 高频在线、延迟敏感 | 不上多轮控制流 | 方差乘以 QPS，容量要按 P99 准备 |

> 本节小结：本节 8 个模式之间，**真正决定选择的那一条约束是「回答所需的证据是否落在检索单元之内」**——它划出能力边界，边界之外（GraphRAG、Agentic）不是更好的选择，而是另一种能力。边界之内，二次筛选由两件事决定：**检索失败能不能被看见**（决定要不要加判定点与补救路径），以及**每次查询的预算买得起哪一段**（精排的成本 ∝ K × QPS，多轮的成本 ∝ 轮数且方差大）。融合算法、K 的取值与嵌入模型的选择，都是这条链条的下游结果；顺序反了，讨论就会永远停在「哪个模型在榜单上更靠前」。

> 💡 **思考锚点**：拿 §3.6 那条贯穿约束对账你的存量——「问题集 + 切分版本 + 嵌入模型版本 + 检索参数」现在是一组统一版本号，还是四个各走各的？回忆你最近一次换嵌入模型时，那批旧阈值、旧 K、旧融合参数里，有几个是在没做新旧双跑的情况下继续服役的？
