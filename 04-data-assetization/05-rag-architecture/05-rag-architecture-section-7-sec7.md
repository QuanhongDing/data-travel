## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表最根本的问题，是把**取决于场景的结论**伪装成**绝对结论**。「实时性」这一维在 RAG 与微调的对比里给 RAG 满分，但如果你的语料是季度更新的制度手册，「实时」就不是需求——为一个不存在的问题买单，比选错工具更常见。「知识更新」同理：它的权重取决于语料的变化频率，而不是取决于方案本身的能力高低。分数没有条件，读的人只能按自己的直觉补条件，于是同一张表被读出两个相反的结论。

第二类误导是**维度并列**。写在一起的「实施成本」在两个方案之间根本不是同一件事：微调的成本主要在训练与再训练，Prompt Engineering 的成本主要在提示维护，RAG 的成本主要在索引维护与检索调参——三个成本的**增长变量**不同，放在一列里比大小没有意义。「准确率」更不可比：RAG 的端到端质量依赖分块策略、top-k、reranker 版本与裁判模型，换一个 harness 就换一个排名（[§5 §5.1](05-rag-architecture-section-5-ai.md) 已把这一条写成判据 ② 难过关的原因）。

第三类误导是**把成熟度当先进度**。工业成熟度高在打分表里只值几分，读起来像缺点；但对多数团队，它意味着有版本化文档、有稳定接口、有别人踩过的坑。「倒排 + 向量 + 精排」不需要被宣传，恰恰因为它是默认值；而需要被宣传的那部分，还没有成熟到能被建设方之外的人核验（[§5 §5.5](05-rag-architecture-section-5-ai.md)）。

第四类误导出在打分表的下游：它给出的结论最终要落成决策树，而**打分表本身不含任何阈值依据**。打分表的决策树按向量库规模给出 10 万 / 1000 万 / 1 亿三档，这个分档是对的，但它没有说明这三档从哪来。本章的做法是让每个阈值回溯到三类来源之一：**成本函数**（7.4 的索引内存与建图调用次数推算）、**结构约束**（答案不在任何单个片段里、上下文窗口是容量限制而非注意力保证）、**组织约束**（评测集与语料快照能不能留在自己手里）。读者可以据此逐节点复核。

最后一层问题在于「适用规模」这一维常被写成「小 / 中 / 大」这样的标签，读者只能按直觉映射：语料 5 万份算中还是大？实际上决定规模可行性的是**索引的内存占用**与**语料更新频率**这两个可算量（7.4），而不是「方案本身能到多大」——同一个方案在 10 万条与 1 亿条向量下的部署形态完全不同，但它用的机制一步没变。把「能到多大」换成「内存占用随什么增长、更新一次要重跑什么」，这一维才成为判据。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 知识放在哪 | 参数里、索引里，还是每次请求的上下文里 | 三处的更新成本与可溯源性完全不同：改索引是分钟级作业、改参数是一次训练、改上下文是每次请求的成本 |
| 索引里放什么表示 | 文本块、页面图像，还是实体与关系 | 它决定「什么形态的知识可能被检索到」，也决定语料更新时要不要重跑一遍全量作业 |
| 这是排序问题还是控制流问题 | 一次相似度比较，还是由模型决定再检一次 | 前者的失败可复现、可定位；后者的失败不可复现，必须靠上界与落盘来兜 |
| 可见性边界 | 谁检索得到什么；过滤在检索侧还是在生成之后 | 生成后再裁剪时，被裁掉的内容已经进过模型上下文——这是事故，不是效果问题 |
| 证据可得性 | 结论能否被发布方之外的人核验 | 公开的效果分依赖一套未被写出的条件；不可核验的结论不该进选型会议 |
| 成本随什么增长 | 语料量、向量数、轮数，还是 token 数 | 决定谁是主导项、哪一项会在规模变大后失控 |

这张表与打分表的关键区别是**判据之间没有权重**：第三、四条是否决项，第一、二条决定架构形态，第五、六条决定这件事能不能被验收。把否决项与偏好项分开，选型才可复核。

### 7.2 候选方案全景

| 方案 | 知识放在哪 / 改的是哪一层 | 核心机制（一句话） | 典型形态与出处 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Fine-tuning | 参数 | 把知识或能力写进权重，推理时不再依赖外部检索 | 通用做法，无单一出处；与检索协同的方法见 RAFT / RA-DIT 一类论文【公开】 | 自研 / 各家训练平台 |
| Prompt Engineering | 上下文（每次请求） | 用提示把已有知识与任务格式交代清楚，不引入新知识 | 通用做法【经验】 | 无额外成本 |
| Naive RAG | 索引（一次召回） | 问题 → 向量召回 top-k → 拼进提示 → 生成 | Lewis 等，NeurIPS 2020（RAG 原论文）【公开】 | 自研 / 开源框架 |
| Advanced RAG | 索引 + 排序 | 在朴素流程上加查询改写、HyDE、融合与跨编码器精排 | 假设文档检索一类方法（2022–2023 年间）【公开】 | 自研 / 开源框架 |
| Modular RAG | 架构划分 | 把 RAG 拆成索引 / 检索 / 重排 / 生成 / 反馈五个可替换模块 | GAIR Lab，2024 年预印本（架构综述，不是能力清单）【公开】 | 无需采用，用作划分参照 |
| Self-RAG / CRAG（反思与纠错） | 控制流 | 生成中输出反思标记，或检索后做可信度判定并回退重检 | Self-RAG（2023 年预印本、ICLR 2024）；CRAG（2024 年预印本）；FLARE（2023 年会议论文）【公开】 | 开源实现（需专门训练才复现论文机制） |
| Hybrid RAG（向量 + BM25 + 图，RRF 融合） | 检索排序 | 多路检索各出名次，用 RRF 按名次相加融合，再做一次精排 | RRF（Cormack 等，SIGIR 2009）【公开】 | 引擎侧已有多数能力 |
| GraphRAG | 索引（建图） | 建索引时抽实体关系、做社区检测与摘要，查询时走 Local / Global 两条路 | Microsoft GraphRAG（2024 年起开源）；Leiden 社区检测（2019 年论文）；LightRAG / HippoRAG（2024 年预印本）【公开】 | 开源 |
| Agentic RAG | 控制流 | 由智能体决定查什么、何时查、如何组合；检索是其工具之一 | LangGraph / LlamaIndex Workflows 一类编排框架（2024 年前后）【公开】 | 框架开源 + 自建上界策略 |
| 长上下文（与检索组合） | 上下文（整份文档） | 把整份文档放进窗口，让检索从「唯一入口」变成「成本分级里的一档」 | 各模型厂官方文档的窗口声明与计价页（OpenAI / Anthropic / Google 等各家模型文档；数字随版本变更、无固定年份，请以官方文档当前版本为准）【公开】 | 按 token 计价 |
| 多模态 RAG | 索引（换表示） | 页面 / 图像直接编码进索引，跳过 OCR 与版面解析 | ColPali（2024 年预印本）；CLIP（Radford 等，ICML 2021）【公开】 | 开源 / 模型卡授权 |
| 实时 / 流式 RAG | 索引（增量写入） | 语料变更经消息队列增量写入索引，而不是批量重建 | 向量库官方文档里的增量写入 / upsert 接口（Milvus、Qdrant、Weaviate、Pinecone 一类均作为 GA 能力提供；接口名与版本以各产品官方文档当前版本为准）【公开】 | 引擎能力 |
| 托管 RAG 平台 | 索引 + 检索（整段托管） | 平台接管切分、嵌入、索引与检索，自己只提供语料与查询 | OpenAI Assistants File Search（2024）、Google Vertex AI Search（2024；产品线随后续版本并入 Vertex AI Agent Builder，命名与形态请以官方文档当前版本为准）、国内百炼 / 千帆 / 混元一类【公开】 | 商业 SaaS |
| 本地化 / 私有化 RAG | 全链路在边界内 | 嵌入、向量库与生成模型全部部署在合规边界之内 | Ollama + 本地向量库一类组合；各组件在各自仓库有版本化发布记录（版本随发布滚动、无固定年份，可按仓库 release 记录核验）【公开】 | 开源 |
| 向量索引与向量库（Chroma / FAISS / Milvus / Qdrant / Weaviate / Pinecone / Vespa / pgvector） | 索引的物理载体 | 用近邻索引（HNSW / IVF / PQ / DiskANN 一类）把 top-k 检索的代价与语料规模解耦 | 各产品官方文档与 release note（HNSW / IVF / PQ / DiskANN 一类索引在各产品中的名称、默认参数与版本不同，请以官方文档当前版本为准）【公开】 | 开源 / 商业 / 托管 |

这十五行分四组：**改「知识放在哪」**（Fine-tuning、Prompt Engineering、长上下文）、**检索层内的改良**（Naive、Advanced、Hybrid、多模态、实时、向量库）、**改索引结构或控制流**（GraphRAG、Self-RAG / CRAG、Agentic）、**改变部署与所有权**（托管 RAG 平台、本地化 / 私有化 RAG）。同组内部换的是同一机制的不同实现，差异小；跨组换的是机制本身，差异大——先分组再选，能省掉一半比较。（Modular RAG 不占一格：它是架构划分方式，不是一项能力，所以只作为分层参照保留。）

族与「三层机制」的对应关系（[§5 §5.1](05-rag-architecture-section-5-ai.md) 已给出这个分层）：

| 机制层 | 本章落入该层的候选 | 这一层决定什么 | 判据侧重 |
| --- | --- | --- | --- |
| 索引里放什么 | 文本块的嵌入、页面级多模态编码、抽取出来的实体与关系 | 什么形态的知识**可能**被检索到 | 索引形态（判据二）+ 更新成本（判据六） |
| 检索结果怎么变成上下文 | 向量召回、BM25、RRF 融合、跨编码器精排、查询改写 | 排序质量：召回集里的答案排第几 | 这是排序问题（判据三的前半） |
| 谁决定检索 | 固定流水线 vs 反思标记 / 可信度回退 / 智能体编排 | 控制流：检索几次、失败能否补救 | 控制流（判据三的后半）+ 可见性（判据四） |

跨层的改动不能互相替代：精排再强也救不回「答案不在任何单个片段里」的问题（那是索引层的），而索引层做对了也不代表权限过滤会自动正确（那是控制流与接口层的）。

表里还有一行需要单独说明：**向量索引与向量库不是「与 RAG 并列的方案」，而是所有 RAG 形态的物理载体**。把它列在表里，是因为选它的时候最容易犯的错是「按语料规模挑产品」——真正的判据只有三条：内存索引带不带得动（7.4 的推算）、过滤条件能不能在检索侧下推、删除语义是否可靠。三条过关之后，产品之间的差异远小于「分块策略 + 精排 + 自己的查询集」这三件自建工作的差异。

同族内部又怎么选？判据只有两条：**接口是否稳定**（能不能给出可核验的版本化文档）与**换一次要重建什么**（向量、图，还是什么都不用重建）。族内选型不值得开三次评审会——把它变成一张「接口稳定性 × 迁移成本」的清单，逐项打勾即可，因为族内差异通常小于自建工作的差异。

### 7.3 机制差异：为什么它们表现不同（核心节）

四个小节按同一结构写：机制是什么 → 各候选的实现差异 → 由此必然导出的性质 → 公开证据 → 失效条件。只写收益不写代价的对比，评审时应直接打回。

#### 7.3.1 知识放在哪：参数 / 索引 / 上下文

- **机制是什么**：知识有三种载体，它们的**更新成本**与**可溯源性**完全不同。改索引是一次可增量的作业（分钟到小时量级），改参数是一次训练（且旧知识只能靠再训练覆盖），改上下文是每次请求都要付的 token 成本。
- **实现差异**：

  | 载体 | 更新一次要做什么 | 能不能给出引用 | 失败时的定位点 |
  | --- | --- | --- | --- |
  | 参数（Fine-tuning） | 准备数据 + 重训 + 重新评测 | 不能（答案来自权重） | 只能定位到「模型记错了」 |
  | 索引（RAG） | 语料快照 + 重建或增量写入 | 能（引用到片段） | 可分成「召回不到」与「生成没用上」 |
  | 上下文（长上下文 / Prompt） | 每次请求重新投喂 | 能（就在提示里） | 可定位到「这段话没被用上」 |

- **由此必然导出的性质**：因为知识在索引里是可增量的，**所以**「知识更新」这件事的成本与语料规模的一小部分成正比，而不是与「重训一次」的固定成本成正比——这是 RAG 在知识频繁变动的场景里必然优于微调的机制原因；**又因为**回答的依据能引用到具体片段，**所以**审计与事故复盘有落点，而这一点是参数化知识给不了的（[§6 落地实践](05-rag-architecture-section-6-sec6.md) 里「无检索不生成」的约束正是把这条性质写成门禁）；**反过来**，因为长上下文把整份文档放进窗口，**所以**在「需要通读一份文件」的任务上检索不再是必经之路，代价是成本与延迟按 token 线性放大，而**「放进去」不等于「用得上」**——上下文窗口是容量限制，不是注意力保证。
- **公开证据**：【公开】RAG 的原始论文（Lewis 等，NeurIPS 2020）给出「检索器 + 生成器」的联合架构；【公开】各家模型厂的官方文档给出窗口声明与计价（窗口数字随版本变化，请以当前版本为准）；【公开】RAFT / RA-DIT 一类「让模型更好地使用检索结果」的方法停在论文与开源实现级，没有把「协同训练」作为能力项的正式发布。
- **失效条件**：当任务要的是**风格 / 格式 / 推理形式**而不是事实时，索引里没有可检索的东西，微调是唯一解；当语料每天都在变时，参数化的更新节奏跟不上，而全量重跑式索引结构同样跟不上（7.3.3）。

由这条机制还能推出一处常被忽略的差别：**三种载体的失败可见性不同**。参数化知识答错时，你只能看到「模型记错了」，没有可查的证据；索引化知识答错时，链路上至少有两个可定位的分界点（召回没检到 / 检到了但生成没用上）；上下文里的知识答错时，证据就在提示里，能直接看出「哪一段被忽略了」。所以选型时「能不能定位失败」应当与「答得准不准」分开评估——前者决定迭代速度，而迭代速度决定长期效果。

#### 7.3.2 检索是一个排序问题：单路相似度 vs 多路证据

- **机制是什么**：把「相似度最高的片段」换成「多路证据的融合排序」。RRF 的机制很干净：把每个检索器输出的**名次**按 1/(k+名次) 相加，只用名次、不用分数，因此异构检索器（倒排、向量、图、结构化查询）不需要做分数归一化就能融合。
- **实现差异**：

  | 方案 | 证据来源 | 融合方式 | 覆盖不了的查询类型 |
  | --- | --- | --- | --- |
  | Naive RAG（单路向量） | 语义近邻 | 无（直接取 top-k） | 精确匹配（型号 / ID / 日期）、多跳、时效过滤 |
  | Advanced RAG | 单路 + 改写 / HyDE | 无（仍是单路） | 改写失败时全线失守，且失败不易察觉 |
  | Hybrid RAG | 倒排 + 向量（+ 图 / 结构化） | RRF 按名次融合 + 跨编码器精排 | 答案不在任何单个片段里的汇总类问题 |
  | GraphRAG | 实体关系 + 社区摘要 | Local / Global 两条检索路径 | 建图成本与语料更新频率冲突的场景 |

- **由此必然导出的性质**：因为融合只用名次，**所以**接入一个新检索器的成本从「调权重、做分数标定」降到「接一个排名列表」，而每接一路，能被覆盖的查询类型就多一类（精确词交给倒排、语义近似交给向量、关系交给图）；**又因为**精排模型看的是「问题 + 片段」的整体，**所以**检索质量的上限从「召回集里有没有」推进到「召回集里排第几」——端到端失败由此分成两类：**召回失败（无解）与排序不高（可改善）**，而这两类必须分开看，否则所有讨论都会停在「换个大模型试试」。**代价是**延迟按路数放大（每一路都是一次检索，精排又是一次模型推理），且 RRF 丢掉分数意味着**丢掉置信度**：一路以极高相似度命中与一路勉强挤进前十，融合后可能同权。
- **公开证据**：【公开】RRF 的原始论文（Cormack 等，SIGIR 2009，给出「只用名次融合」的机制与实验）；【公开】主文件 §2.2 给出 RRF 的融合公式与向量 / BM25 / 混合相似度的形式；【公开】多家引擎把混合检索做成 GA 配置项并按版本发布文档（本节具名 Milvus 的多路向量检索与标量过滤、Elasticsearch 的 RRF 检索器、pgvector 的索引与过滤查询计划；命名与版本各产品不同，请以官方文档当前版本为准）。
- **失效条件**：当正确答案不在**任何一路**的 top-k 里时，融合与精排都无从补救；当查询改写把原问题里的实体或时间条件改没了时，出错位置在检索之前，排查成本高于排序问题。

这里还有一条容易漏掉的工程约束：**多路召回必须并行，不能串联**。因为每一路都是一次独立检索，串联会让延迟按路数线性叠加，而并行的代价只是 CPU 与内存占用。判定方法是看检索链路的延迟是否随路数增长——若增长了，说明实现是串联的，加第三路之前先把它改成并行。改写这一步同理：它发生在检索之前，所以它必须落盘（改写前后的文本都留），否则「检索为什么没命中」这个问题无法回答。

上面那套判定方法的价值在于它把「效果不好」拆成两个可执行的后续动作：**召回失败 → 改索引或改查询构造**（加一路召回、改分块、改改写策略），**排序不高 → 加精排或调融合**。没有这个拆分，「效果不好」只能变成一次没有方向的模型替换，而模型替换同时抬高延迟与成本，通常连问题在哪都还没确定。

#### 7.3.3 推理前置到索引期：GraphRAG 把多跳从能力问题变成结构问题

- **机制是什么**：把「关系」从查询时算，挪到**建索引时**算——用模型从文本抽实体与关系，在图上做社区检测，逐社区生成摘要；查询时按问题类型走「按实体附近取证据」（Local）或「按社区摘要取全局视图」（Global）。
- **实现差异**：

  | 方案 | 关系在什么时候被算出来 | 查询时的主要动作 | 更新语料的代价 |
  | --- | --- | --- | --- |
  | 向量 / Hybrid RAG | 不算关系，只算相似 | 一次近邻 / 融合检索 | 插入片段即可 |
  | GraphRAG | 建索引时抽取 + 社区检测 + 摘要 | 图遍历或读摘要 | 重跑抽取与摘要（重跑形态） |
  | LightRAG / HippoRAG 一类 | 建索引时（轻量化 / 联想式结构） | 图检索 + 向量检索结合 | 视实现：多为部分重建 |

- **由此必然导出的性质**：因为社区摘要在索引阶段就已经生成，**所以**跨文档汇总类问题不再需要把大量原文塞进上下文，一次检索就能拿到摘要级证据——这是纯向量检索在**结构上**做不到的（答案不在任何单个片段里，交给生成模型它只能在场内自己编关系）；因为关系以实体为节点存在图里，**所以**「沿关系走两跳」变成一次遍历查询，而不再靠模型在文本里猜。**一句话：它把多跳从模型能力问题变成数据结构问题，而数据结构问题可以被工程解决。** 代价同样明确：建图成本前置且与语料量成正比，**抽取质量决定上限**（漏掉实体，后面的遍历就不存在；抽错关系，错误会以「看起来合理的错误关系」进入答案，比检索不到更难发现），而且新增了图存储、社区结构与摘要版本三样要维护的东西。
- **公开证据**：【公开】Microsoft GraphRAG 开源项目（2024 年起发布，其文档给出从文本到社区摘要的完整流程与两种查询方式）；【公开】Leiden 社区检测算法（2019 年论文，是该流程里划分社区的常用方法）；【公开】LightRAG 与 HippoRAG（2024 年预印本，改的是建图与检索的具体做法，不改「多跳要靠结构」这条前提）。
- **失效条件**：语料高频更新时，建图与摘要是重跑形态的作业，成本随更新次数线性叠加——它天然适合**低频更新的语料**；单点事实查询看不出它相对混合检索的差别，此时建图只是纯支出。

这条机制给出一条可迁移的判据：**当一类问题的答案「不在任何单个片段里」时，检索层的所有排序技巧都无效，必须改索引结构**。反过来，当答案确实落在某个片段里时，建图不会带来结构优势——这就是同一套 GraphRAG 在两类语料上表现差异极大的原因，也是它不该被当成默认升级的原因。

#### 7.3.4 控制流归谁：把「要不要再检一次」交给概率模型

- **机制是什么**：固定流水线在检索**之前**就决定了检索几次，于是「检索不到」这件事没有补救路径；反思与智能体把「是否继续检索」这个分支交给模型，在**看到中间结果之后**决定。
- **实现差异**：

  | 方案 | 谁做决定 | 决定发生在什么时刻 | 失败可复现性 |
  | --- | --- | --- | --- |
  | 固定流水线 | 流水线定义 | 检索之前 | 可复现 |
  | Self-RAG | 模型输出的反思标记 | 生成过程中 | 依赖专门训练，通用模型上复现不了机制 |
  | CRAG | 检索后的可信度判定 | 检索之后 | 回退到外部检索在私有数据场景通常不可用 |
  | Agentic RAG | 智能体（编排层） | 每一轮之后 | 不可复现，必须逐轮落盘 |

- **由此必然导出的性质**：因为「要不要再检一次」由模型在看到初步结果后决定，**所以**固定流水线里「一次没检到就答错」的那类问题第一次有了补救路径；**又因为**判定与生成在同一个循环里，**所以**「无证据不生成」这条约束第一次可以被写成**可执行的控制流**，而不是写在提示词里的祈使句。**代价有三条**：其一，控制流交给概率模型之后，**延迟与成本不再有上界**——轮数由模型的判断决定，同一问题两次请求可能走不同轮数，尾部延迟明显变长；其二，可复现性下降，生产排障需要把每一轮的检索与判定都落盘，否则复现不了；其三，**反思能力依赖模型是否被专门训练过这套标记**，在通用模型上直接套提示词，得到的往往是「看起来在反思」的文本，此时付出的是延迟，换来的只是措辞。
- **公开证据**：【公开】Self-RAG（2023 年预印本、ICLR 2024，核心是反思标记 + 专门训练）；【公开】CRAG（2024 年预印本，可信度判定 + 外部检索回退）；【公开】FLARE 一类主动检索（2023 年会议论文，按生成过程中的置信度决定何时检索）；【公开】编排框架侧有版本化文档（LangGraph / LlamaIndex Workflows 一类，2024 年前后）。**这几条的生产采用材料以框架方与应用方自述为主**，判据 ② 在这些方向上不成立。
- **失效条件**：当混合检索 + 精排已经把排序问题解决时，「第一次没检到」的概率本就不高，多轮只是多花成本；当框架默认不提供轮数上界与逐轮落盘时，Agentic 化的收益无法被验收，而它的成本会先出现在延迟预算上。

补一条机制层面的判断：**反思与多轮解决的是「召回失败」，不是「排序不高」**。当失败原因是排序（正确片段在召回集里但排位靠后）时，精排与融合是更便宜也更确定的解法；只有当失败原因是「正确片段不在任何一路的 top-k 里」时，多轮才带来结构性收益。判定动作就是 7.3.2 给的那条：把正确片段在第几路、第几位记下来，按两类失败分组，看多轮改善的是哪一组。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
RAG 总成本 ≈ 索引成本（语料量 × 分块与嵌入；随语料更新频率反复发生）
           + 检索成本（每路召回的查询开销 + 精排的交叉推理）
           + 生成成本（输入 token × 输出 token × 轮数）
           + 结构化成本（建图 / 社区检测 / 摘要，只在 GraphRAG 一类上出现）
           + 评估与元数据成本（查询集标注、语料快照、分块策略与嵌入模型版本登记）
```

| 方案 | 主导成本项 | 随什么增长 | 隐性成本 | 升级时作废什么 |
| --- | --- | --- | --- | --- |
| 参数（Fine-tuning） | 训练作业 | 语料量 × 重训次数 | 评测与数据准备 | 上一版权重 |
| 上下文（长上下文 / Prompt） | 每次请求的 token | 文档大小 × 请求量 | 中段信息利用不稳定 | 无（但每次都要重付） |
| 单路向量 RAG | 索引与近邻检索 | 向量数 × 维度（见下方推算） | 分块与嵌入的参数选择无人记录 | 全库向量 |
| Hybrid / Advanced RAG | 多路召回 + 精排 | 路数 × 查询量 + 精排推理 | 精排服务的延迟占用 | 融合与精排配置 |
| GraphRAG | 建图与社区摘要 | 语料量 × 更新次数（重跑形态） | 抽取质量与摘要版本维护 | 图、社区结构、摘要 |
| Agentic RAG | 生成轮数 | 轮数（无上界，尾部按最大轮数走） | 逐轮落盘与排障 | 编排与提示版本 |
| Self-RAG / CRAG（反思与纠错） | 让论文机制可复现的专门训练 | 训练作业 + 判定与回退多出来的轮数 | 回退所用的外部检索在私有语料上通常不可用，判定阈值只能自测 | 训练出的标记模型与判定阈值 |
| 多模态 RAG | 页面级编码与索引 | 页数 × 页面像素（见下方推算） | 与文本索引的权限对齐 | 页面级向量 |
| 实时 / 流式 RAG | 增量写入吞吐 | 变更频率 | 删除语义与双索引一致性 | — |
| 托管 RAG 平台 | 平台侧的索引与检索 | 语料量（按平台计价） | 内部分块与检索参数不可调 | 迁移成本：换平台要重迁语料与索引 |
| 本地化 / 私有化 RAG | 常驻硬件 + 常驻运维人力 | 硬件按索引规格一次到位（不随查询量线性增长），人力是常驻项 | 与托管模型的效果差距按语种与任务分布不均，只能用自己的语料自测 | 本地权重与嵌入模型的版本组合 |

【推算】向量索引内存（**这正是把向量库规模分成三档的依据**）：按向量 1024 维、float32 存储——单条向量本体 = 1024 × 4 字节 = **4 KB**；HNSW 一类图索引的邻居表按每向量约 2×M 条边（取常用 M=16 即 32 条）、每条边一个 4 字节 ID = **128 字节**；层次化图索引在稀疏的上层另有邻居表，冗余系数取 **1–2 的中间量级**【经验】（本处取 ×1.5）≈ **192 字节**（按公开索引结构的量级估算，不是任何产品的实测参数，实际取决于索引参数与实现）。这一项只占单条向量估算的约二十分之一，系数在 1–2 之间取值只让三档估算浮动不到一成，不改变下面的分档归属。于是：

- **10 万条** → 1e5 × 4.29 KB ≈ **0.43 GB** → 单机内存即可，对应 Chroma / FAISS 一类轻量方案；
- **1000 万条** → 1e7 × 4.29 KB ≈ **43 GB** → 需要大内存单机或小集群，对应 Milvus / Qdrant / Weaviate 一类可分布式部署的方案；
- **1 亿条** → 1e8 × 4.29 KB ≈ **430 GB** → 单机常驻内存已不现实，需要分片，或改用落盘索引（DiskANN 一类），对应 Pinecone / Vespa / Milvus 集群一类形态。

三档的向量数是 10 万 → 1000 万（×100）→ 1 亿（×10），内存占用按同样的倍数走，因为内存占用与向量数**线性**相关——这一点与很多「规模上去后成本突然失控」的系统不同，向量索引的成本是好算的。**但页面级多模态索引会打破这条线性感**，见下一条推算。

【推算】页面级多模态索引的体积：一页 A4 按 150 DPI 计约 1240 × 1754 像素；若按 32 像素的图像块编码，(1240 ÷ 32) × (1754 ÷ 32) ≈ 39 × 55 ≈ **2100 个向量/页**；同一页按文本切分通常出 **3–10 个片段**【经验】。以 100 万页语料为例，取文本侧每片段 1024 维（4 KB）、页面侧每块 128 维（512 B）：文本侧 = 5e6 × 4 KB ≈ **20 GB**；页面侧 = 100 万 × 2100 × 512 B ≈ **1.07 TB**；比值 ≈ 1.07 TB ÷ 20 GB ≈ **54 倍**。这个倍数不是常数，它同时取决于扫描分辨率、图像块边长与两边的向量维度——**必须在定下这三项之后按自己的语料重算**（判定动作：先算索引体积，再决定要不要整库走页面级编码）。

【推算】GraphRAG 的建图调用量：100 万页语料按每页 5 个片段计 ≈ **500 万个片段**；实体关系抽取至少要对每个片段跑一次模型调用 ≈ **500 万次调用**（单位成本请按当时的模型计价换算，本节不给单价），其上还要加社区检测与逐社区摘要。结论不在这个绝对值，而在它的**形态**：语料每更新一轮，这些调用就再发生一次——所以它适合低频更新的语料，不适合日更语料。

【推算】多轮的延迟量级：若单轮检索（含精排）按**百毫秒量级**【经验】（本处取 100–300 ms）计，2–3 轮的检索段就是 **0.2–0.9 秒**（2 × 100 ms 到 3 × 300 ms），其上还要加每一轮的生成开销；固定流水线是一轮，延迟恒定。这不是说多轮一定慢到不可用——它说的是延迟的**形态**变了：从常数变成与轮数相关，而轮数由概率模型决定。判定方法很便宜：同一问题按**十次量级**【经验】取样（5–10 次），记录轮数与总耗时；轮数波动大就说明成本不可预测，先设上界再谈效果。

读这张成本表的方法，是对每个候选问三个问题：**它的成本随什么增长**、**哪一项是不进预算表的隐性成本**、**一次升级会让什么作废**。RAG 的隐性成本几乎全部落在第四项（评估与元数据）上——分块策略、嵌入模型版本、语料快照这三样如果不登记，「换一次嵌入模型」就从一次可估价的迁移变成一场事故。

【推算】长上下文与检索的 token 对比：一份 200 页文档按每页约 500 token 估 ≈ **10 万 token**【经验】；整份放进上下文意味着每次提问都要重付这 10 万 token；而检索 top-5 片段按每片段 500 token 估 ≈ **2500 token**，两者相差约 **40 倍**（100000 ÷ 2500）。倍数比绝对值重要：**「通读一份」与「问一句」是两种成本形态**——前者随文档大小线性增长且每次请求重付，后者随 top-k 增长而与语料总量无关。这就是长上下文减少的只是「一部分」检索场景在成本上的原因。

还有一项常被漏算的成本：**多路召回与精排都要占延迟预算**，所以「加一路」必须当成一次有数据的取舍——加这一路让多少条查询从「不在召回集里」变成「在」。判定动作是把查询集按「原先是召回失败还是排序失败」分成两组，看新加的这一路主要改善哪一组；若两组都没动，这一路只是多花成本。

### 7.5 决策树（每个分支都要有阈值依据）

```text
⓪ [需要让模型回答本组织的私有知识吗？]
   ├─ 不需要 → 直接用通用 LLM（本节的候选比较都不适用）
   └─ 需要 ↓
① [知识需要随业务实时更新吗？]
   ├─ 不需要，要的是风格 / 格式 / 表达方式 → Fine-tuning（记住：知识变了要重训）
   └─ 需要 →
        ② [这批知识能装进一次上下文吗？按「文档大小 × 更新频率」分档]
           ├─ 能，且任务是「通读一份文件」→ 长上下文；但仍保留检索做「选择」
           └─ 装不下 / 需要精准定位 → RAG ★
                ③ [你的问题属于哪一类？]
                   ├─ 单点事实 → 单路向量（Naive RAG）够用
                   ├─ 精确匹配 / 换措辞找不到 → Advanced RAG（改写 + 倒排与向量 + 精排）
                   ├─ 跨文档汇总 / 关系推理 → GraphRAG
                   └─ 复杂业务、多步 + 多工具 → Agentic RAG（必须设轮数上界）
                ④ [语料更新频率 vs 建索引形态的代价？]
                   ├─ 低频更新 → 可以承担全量重跑形态（建图 / 社区摘要可用）
                   └─ 日更 / 高频 → 走增量写入 + 混合检索，不上全量重跑式结构
                ⑤ [数据有权限分级吗？]
                   ├─ 有 → 过滤必须下推到检索侧；生成后裁剪不可接受
                   └─ 无 → 仍按最小必要做元数据过滤
                ⑥ [索引规模落在哪一档？]
                   ├─ 十万级向量 → Chroma / FAISS（单机）
                   ├─ 千万级向量 → Milvus / Qdrant / Weaviate（大内存单机或小集群）
                   └─ 亿级向量 → Pinecone / Vespa / Milvus 集群（分片或落盘索引）
                ⑦ [自建还是托管？]
                   ├─ 合规要求「数据不出边界」→ 本地化栈（嵌入 + 向量库 + 生成模型全部在边界内）
                   └─ 追求起步速度 → 托管平台，但查询集与语料快照必须留在自己手里
```

**阈值依据**（与树上 ⓪–⑦ 一一对应）：

- **⓪ 是否需要私有知识**：这一条不是阈值而是**前置开关**——问题只靠通用模型的世界知识与推理就能回答时，没有任何私有语料可以进索引，后面的索引与检索成本全是支出；判定动作是看答案是否必须引用本组织的语料或口径。
- **① 知识是否实时更新**：依据是三种知识载体的**更新成本形态**（7.3.1 的对照表）——改索引是可增量的作业，改参数是训练作业，两者相差的是一次作业与一次训练。分界不看语料规模，看语料的变化频率与任务的类型（事实问答 vs 风格 / 格式）。
- **② 能否装进一次上下文**：依据是「上下文窗口是容量限制，不是注意力保证」这一机制（7.3.1 的失效条件）——分档变量取「文档大小 × 更新频率」：单份、低频、需要通读的文档适合长上下文；多份、高频、需要精准定位的语料适合检索。这里不给 token 阈值，因为窗口数字随模型版本变化，应查各家官方文档当前版本，而不是引用二手材料里的数字。
- **③ 问题类型分档**：依据是「答案落在哪里」——落在某一个片段里（单点事实）、落在多路检索的交集里（精确匹配与近义表述）、**不在任何单个片段里**（跨文档汇总）、既不在片段里也不在一次检索里（多步与多工具）。因此这一节点不给数字阈值：它是一道**结构判断题**，判定动作是抽 30–50 条真实问题人工标一遍「答案在第几路、哪个片段」【经验】，而不是按语料规模猜。
- **④ 语料更新频率 vs 索引形态**：依据是建图与摘要是**重跑形态**的作业（7.4 的调用量推算：100 万页 ≈ 500 万次抽取调用，每更新一轮再发生一次）。分界取决于两个可量出的数：语料更新频率、一次全量建图的耗时与调用量——两者之比决定了结构化的成本是否可承受。
- **⑤ 有无权限分级**：依据是「过滤放在检索侧与放在生成之后是两种系统」（[§5 §5.3](05-rag-architecture-section-5-ai.md) 的接口第三行）——放在生成后，被过滤的证据已经进过模型上下文，模型可能在答案里泄露它的存在；放在检索侧，越权内容从未进入链路。这两者是两回事，不是同一条防线上的强弱之分。这条不是阈值，是开关：有分级就必须下推。
- **⑥ 索引规模三档**：依据是 7.4 的索引内存推算（10 万 ≈ 0.43 GB / 1000 万 ≈ 43 GB / 1 亿 ≈ 430 GB）——相邻档分别是 100 倍与 10 倍、跨全档 1000 倍，与向量数逐档同倍放大，而内存占用与向量数线性相关，所以分档点就是「单机内存带不带得动」这个物理边界。若走页面级多模态编码，同样内存能承载的页数会下降约 50 倍、约 1.7 个数量级（7.4 的 54 倍推算），三档要整体下移。
- **⑦ 自建还是托管**：依据是核验能力会随托管一起被交出去——托管平台的内部分块与检索策略不公开（[§5 §5.1](05-rag-architecture-section-5-ai.md) 的「托管 RAG 平台」行）。判定动作是先分清合规要求的是「数据不出边界」还是「模型不拿你的数据训练」，两者解法不同；再确认查询集与语料快照能留在自己手里。

**怎么用这棵树**：⓪与①是开题项——问题若不需要私有知识、或知识不需要随业务更新，后面几步都不必走；②与④是一对，共同决定「要不要索引」与「索引用什么形态」；③是结构判断题，判定动作是抽真实问题人工标注答案位置；⑥是唯一一个纯成本节点，算一次就有答案；⑤不是阈值而是开关，有权限分级就必须下推。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 单点事实问答、语料中等 | 混合检索（向量 + 倒排）+ 精排 | 单路向量（Naive） | 单路向量覆盖不了精确匹配与时效过滤（7.3.2） |
| 制度 / 手册类、季度更新 | 混合检索 + 精排，标准 RAG | 长上下文（单份文档通读） | 长上下文按「每次请求 × 整份文档」重付，而制度问答要的是在大批条款里精准定位、不是通读——逐次重付换不到定位能力（7.3.1） |
| 语料日更、要求秒级可见 | 增量写入 + 混合检索 | 批量重建索引（小时级延迟） | 批量重建以小时计的窗口里，撤回与改权重的文档仍会被召回，而重建期间新旧两版索引并存、召回结果无法解释（[§5 §5.1](05-rag-architecture-section-5-ai.md) 的流式文档更新行） |
| 跨文档汇总、关系推理 | GraphRAG | 混合检索 + 分治归并（按文档分别取证据，再由模型合并） | 分治归并要模型自己在没有结构的情况下拼关系，漏证据与编关系都不可核验（7.3.3） |
| 复杂业务、多步跨系统 | Agentic RAG（设轮数上界 + 逐轮落盘） | 固定流水线 + 明确说「不知道」 | 固定流水线在检索之前就定死了检索次数，「一次没检到」没有补救路径，只能直接答「不知道」（7.3.4） |
| 扫描件 / 图表 / 双栏排版 | 页面级多模态索引 | OCR 转文本后再检索 | OCR 丢失的版式往往正是答案所在；但索引体积按 7.4 的推算上涨 |
| 风格 / 格式 / 输出结构不达标 | Fine-tuning（配 RAG 供事实） | 提示工程 + 少样本 | 提示与少样本只约束这一次请求，风格漂移要每次重写提示去追，而漂移恰恰是这类任务的失败形态——要的是把风格写进权重（7.3.1 失效条件） |
| 合规要求数据不出边界 | 本地化栈 + 混合检索 | 托管平台（合规允许时） | 托管平台把语料与索引的存放边界交给平台，内部分块与检索策略不公开，「数据不出边界」这一条无从核验（7.1 判据五「证据可得性」） |
| 想最快跑起来 | 托管平台 + 自建查询集 | 开源框架自建 | 自建等于把切分、嵌入、索引参数与检索链路四段都自己定，起步时间花在四段都要给出取舍依据——「最快跑起来」要的正是把这四段交出去（7.4 的成本函数里，这四段都落在你自己的账上） |
| 语料含表格与结构化数据 | 聚合与筛选交给 SQL，说明性问答走检索 | 全走检索 | 聚合类问题的答案不在任何单个片段里，检索结构上做不到 |
| 多模态（图 / 视频 / 音频） | 按模态分别编码后统一做检索 | 先转写成文本再检索 | 转写会引入新的失败点，且视频问答需要时间戳索引而非普通向量索引 |
| 语料十万级以内、只有单机资源 | Chroma / FAISS 单机 + 混合检索 + 精排 | 托管平台 | 单机内存足够（7.4 推算约 0.43 GB），没有理由把核验能力交出去 |

**常见组合**（每条给出职责边界与运维代价）：

1. **RAG + Fine-tuning（RAFT 一类）**。职责边界：微调让模型学会「如何使用检索结果」的格式与模式，RAG 提供实时事实——**事实永远不进参数**。运维代价：两套版本（权重 + 索引）必须同时登记，改一个，另一个的评测结论就失效；而且它把「什么时候该忽略检索结果」写进了参数，改起来比改提示贵得多。
2. **RAG + 知识图谱（GraphRAG）**。职责边界：RAG 负责语义近邻，KG 负责关系与多跳；真正的边界在「关系从哪来」——抽取质量决定上限。运维代价：建图与摘要是重跑形态，语料更新时成本重付；图存储、社区结构、摘要版本三样都要有 owner。
3. **RAG + Agent（Agentic RAG）**。职责边界：Agent 决定查什么、何时查、如何组合，检索是它的工具之一；轮数上界、预算上界与逐轮落盘由编排侧负责。运维代价：延迟与成本失去上界，同一问题两次结果可能不同；线上排障依赖逐轮记录，缺了它无从下手。
4. **向量 + BM25 + 知识图谱（Hybrid RAG）**。职责边界：向量管语义近邻、BM25 管精确匹配、KG 管关系推理，RRF 只用名次融合，所以三路不需要做分数归一化。运维代价：延迟按路数放大；RRF 丢掉分数意味着**丢掉置信度**，一路以极高相似度命中与一路勉强进前十可能同权，需要另加规则区分。
5. **RAG + 长上下文（按内容分级投喂）**。职责边界：长上下文负责「能整份通读的文档」，RAG 负责「在大量语料里做选择」；分档变量是「文档大小 × 更新频率」。运维代价：token 成本按文档大小线性放大，且中段信息利用不稳定——所以它减少的只是**一部分**检索场景，不是全部。
6. **托管平台 + 自建评估与快照**。职责边界：平台管切分、嵌入、索引与检索，自己管查询集、语料快照与结论口径。运维代价：核验能力被交出去（内部分块与检索参数不可调），跨平台比较只能比版本、不能比效果。
7. **本地化栈 + 混合检索（合规场景）**。职责边界：嵌入、向量库与生成模型全部在合规边界内；检索侧仍要做过滤下推与删除验证。运维代价：与托管模型的效果差距在不同语种、不同任务上分布不均，只能按自己的语料测，运维人力留在自己这边。

这七条里有三条跨了机制层（2、3、5：分别动了索引层、控制流层、上下文层），四条留在检索层内（1、4、6、7 的检索部分）。跨层的组合要把「换一层会不会打掉另一层的前提」当成长期监控项——例如页面级多模态索引上线后，文本侧的权限模型是否覆盖了图像索引。

判断一个组合是否真的落地，看三样东西有没有登记：**语料快照**（索引用的是哪一版语料）、**嵌入模型与分块策略**（换一次要重建什么）、**每一路召回各自的失效记录**。三样都没有，这个组合就还停在架构图上。

### 7.7 选错的代价与迁移成本

- **反模式：先做检索效果，权限与删除语义最后补** —— 症状：过滤靠「生成后裁剪」，文档撤回或权限回收后索引里还留着。→ 后果：被裁掉的内容已经进过模型上下文，模型可能在答案里泄露它的存在；而「删不干净」不会报错，只会安静地越权。→ 正确做法：过滤在**检索侧**下推，并做一次「删除 + 立刻检索」的验证（机制依据：7.1 判据四「可见性边界」与 [§5 §5.3](05-rag-architecture-section-5-ai.md) 的接口第三行）。
- **反模式：把 GraphRAG 当企业 RAG 的默认升级** —— 症状：语料以单点事实查询为主，却先建图。→ 后果：建图、社区检测与摘要的成本前置，且随语料更新次数线性叠加（7.4 的 500 万次调用推算），而收益只出现在跨文档汇总类问题上。→ 正确做法：先统计问题类型分布（7.5 节点③的判定动作），再量语料更新频率与一次全量建图的耗时。
- **反模式：用一次评测的分数做选型依据** —— 症状：拿某次评测或某个榜单的端到端质量分比较两个方案。→ 后果：分数是「那套 harness + 那批题」下的结论，与你的语料分布、权限模型、更新频率无关（[§5 §5.1](05-rag-architecture-section-5-ai.md) 已把这一点写成判据 ② 难过关的原因）；据此选型等于用别人的题目考自己的系统。→ 正确做法：固定一份自己的查询集与语料快照，只改一个变量重跑。

这三条的共同结构是：**把「某一层变便宜了」误当成「整条链路可以少一层」**。判断一个选型决定是否成立，看它有没有同时给出自己新增的成本项与新增的失败模式——只讲收益的方案，代价一定落在别处（延迟、索引体积、权限或运维人力），而它通常在事故之后才被发现。

还有一类代价不出现在技术清单里，而出在**验收标准**上：跨层迁移（组合 2、3、5）引入的收益都无法用单一总体指标验收——GraphRAG 的收益出现在汇总类问题上，Agentic 的收益出现在原本召回失败的样本上。若不做分层验收（按问题类型分组看指标），这两类改动的收益会被平均指标吃掉，团队会在半年后得出「没什么用」的结论，而真实原因是没人按类型去看。

迁移顺序上有一条经验规则：**先动检索层，再动索引层，最后动控制流**。检索层的改动可回滚且不动数据结构；索引层的改动要做一次全量重建（7.4 的编码与建图推算就是它的价格标签）；控制流的改动会让延迟与成本失去上界，回滚成本最高。反过来做——先上 Agentic，再回头补精排——会让两件事的收益互相掩盖，最终无法归因到底是哪一步起了作用。

**换成另一个要动什么**（工作量量级为【经验】档，只给区间不给精确值）：

| 迁移 | 数据迁移 | 服务 / 接口改写 | 运维重建 | 团队再学习 | 量级 |
| --- | --- | --- | --- | --- | --- |
| Naive → Advanced RAG | 无需重建向量索引 | 检索链加改写、融合、精排三段 | 新增精排服务与延迟预算 | 融合与精排调参 | 小到中 |
| 文本块 → 页面级多模态索引 | 全库重新编码（一次批量作业） | 检索单元从片段改页面 | 索引体积与检索算力显著上升（7.4 的 54 倍量级） | 页面级编码与晚交互检索 | 中到大 |
| 单路向量 → 加 KG / GraphRAG | 需对全语料跑一遍抽取 + 社区摘要 | 查询侧分成 Local / Global 两条路 | 新增图存储、社区结构、摘要版本三样维护 | 抽取质量治理 | 大，且语料日更时是重跑形态 |
| 固定流水线 → Agentic（控制流交给模型） | 无需数据迁移 | 检索从固定节点改为工具，编排层接管 | 新增轮数上界、预算上界、逐轮落盘 | 概率控制流的排障方法 | 中，但排障成本长期存在 |
| 自建 → 托管平台 | 语料与索引迁移；查询集与快照必须留下 | 检索接口改为平台 SDK | 自建栈的运维能力部分闲置 | 平台的切分与检索参数不可调，只能适应 | 小到中 |
| 无元数据登记 → 全链路版本登记 | 补登分块策略与嵌入模型版本（确定可比性起点） | 无 | 索引构建流程加必填字段 | 无新增技能，需跨团队约定 | 小，但依赖约定 |
| 单路向量 → 多路并列召回 | 无需迁移既有向量 | 召回从一次检索改多路并行 + 融合 | 新增融合器与每一路的独立监控 | 融合只用名次、各路失效模式不同 | 小到中 |

### 7.8 小结

把本章压成一句话：**先确定知识放在哪，再确定索引里放什么，最后才谈用哪种检索**。这个顺序不能颠倒——检索层的改良收益最确定，但它救不回载体与索引层选错造成的问题。下面按处境给出落点。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 刚要做企业知识问答 | 混合检索 + 精排 + 一份自己的查询集 | 召回失败无法由生成补救，排序不高可以；先把自己那批题的答案位置量出来 |
| 语料日更、要求近实时 | 增量写入 + 混合检索，并先验证删除语义 | 删除与双索引一致性不解决，越权会安静发生 |
| 知识随业务频繁变动 | 走 RAG，不要靠微调更新知识 | 改索引是可增量作业，改参数是一次训练 |
| 任务是风格 / 格式不达标 | 微调（配 RAG 供事实） | 索引里没有「风格」这种可检索的东西 |
| 单份长文档通读 | 长上下文，保留检索做选择 | 窗口是容量限制不是注意力保证，中段信息利用不稳定 |
| 跨文档汇总 / 关系推理 | GraphRAG，且只在低频更新语料上 | 关系被前置成索引结构才有结构优势；建图是重跑形态 |
| 复杂多步、跨系统 | Agentic RAG + 轮数上界 + 逐轮落盘 | 控制流交给概率模型换来补救路径，代价是延迟与可复现性 |
| 数据有权限分级 | 过滤下推检索侧，做一次删除验证 | 生成后裁剪时越权内容已经进过模型上下文 |
| 索引规模已达亿级 | 分片或落盘索引，或换托管 | 1 亿条 1024 维常驻内存约 430 GB，超过单机内存边界 |
| 语料含大量表格与结构化数据 | 聚合类问题走 SQL，只有说明性问答走检索 | 答案不在任何单个片段里时，检索结构上做不到 |

> 本节小结：本章所有候选的差异，最终都能归到三问——**知识放在哪**（参数 / 索引 / 上下文）、**索引里放什么表示**（文本块 / 页面图像 / 实体关系）、**控制流归谁**（固定流水线 / 模型决定再检一次）。三问之外，两条性质一寸未动：**召回失败无法由生成补救**（所以「换个大模型」永远不是第一动作），以及**检索是一个排序问题**（所以精排与融合是收益最确定、代价最可算的一步）。打分表之所以误导，正是因为它把这三问压成一列分数，又用一套没有写出来的 harness 条件去支撑那些分数。
>
> 💡 **思考锚点**：按 7.7 的顺序「先检索层、再索引层、最后控制流」看你这条 RAG 链路的下一步落在哪一层：如果往索引层走（例如换成页面级多模态索引），先照 7.4 算一次全量重编码与 54 倍量级的索引体积——你的索引规模是不是已经逼近「1 亿条 1024 维常驻内存约 430 GB、超过单机内存边界」那道坎？
