### 6.1 阿里 OneService 数据服务 8+ 年演进（2016-2024）

**背景（Why）**

阿里 2016 年面临**数据消费困境**：
- **5 套数仓**——**重复 ETL**——**数据不一致**
- **业务方直接读数仓**——**数据库扛不住**
- **5 套不同 API**——**业务方不知用哪个**

**触发点（What）**

2016 年**阿里启动 OneService 项目**（来自 [《大数据之路 2017]）——**目标**：「**统一数据服务**」——**业务方一个 API 拿到所有数据**。

**详细做法（How）**

阿里 OneService 的**5 大核心组件**：

1. **统一查询服务**
   - 关键设计：**SQL-like 查询**——**自动路由到对应数仓**
   - 关键能力：**业务方无感知**——**底层 HBase / MySQL / Druid 自动选**
   - 关键代码：
     ```java
     // 阿里 OneService 统一查询
     public class OneServiceQuery {
         public QueryResult query(SQL sql) {
             // 1. 解析 SQL
             // 2. 路由到最优数仓
             String engine = router.route(sql);
             // 3. 执行
             return executor.execute(engine, sql);
         }
     }
     // 业务方只需要写 SQL，不需要知道底层
     ```

2. **统一 API 网关（核心创新）**
   - 关键设计：**TopLink**（**阿里自研**）——**HSF / Dubbo 风格 RPC**
   - 关键能力：**限流 / 鉴权 / 监控** — **「**所有数据消费**」**通过统一 API
   - 关键数字：**90%+ 数据消费走 OneService**

3. **统一数据服务（多种服务）**
   - **iSearch**（**搜索服务**）——**Elasticsearch 包装**
   - **iGraph**（**图查询**）——**图数据库包装**
   - **iRec**（**推荐服务**）——**算法服务包装**
   - 关键能力：**业务方调用**——**底层复杂**

4. **统一监控 + SLA**
   - 关键设计：**每个服务**——**SLO / SLI**——**实时监控**
   - 关键能力：**业务方**——**知道每个服务**——**可用性**

5. **API 网关（Kong）**
   - 关键设计：**Kong**（**开源**）——**API 网关**
   - 关键能力：**限流 / 鉴权 / 跨域**

**阿里 OneService 关键数字**（[阿里 2023 公开数据]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **数据消费效率** | 基线 | +10 倍 | **10 倍** |
| **API 调用量** | 100 万/天 | 10 亿+ / 天 | **1000 倍** |
| **指标一致性** | 60% | 95%+ | **35% 提升** |
| **数据库连接** | 10000+ | 2000+ | **80% 减少** |
| **业务接入时间** | 2 周 | 1 天 | **14 倍** |
| **服务覆盖** | 5 套 | 100+ 服务 | **20 倍** |

**具体数字（How much）**

- 团队规模：阿里 OneService 团队 50+ 人
- 关键数字（[2023 公开数据]）：
  - **10 亿+ API 调用/天**
  - **100+ 服务**——**业务覆盖全集团**
  - **95%+ 指标一致性**
- 业务影响：**支撑阿里 8 万亿 GMV + 100 万企业云用户**

**失败教训**

- 早期**直接读数仓**——倒逼**「**API 网关**」**
- **API 性能**——倒逼**「**缓存**」**
- **API 安全**——倒逼**「**鉴权 + 限流**」**

### 6.2 字节跳动 DataFinder 数据服务 4+ 年（2020-2024）

**背景（Why）**

字节 2020 年面临**数据服务**挑战：
- **抖音 / TikTok**——**多个数仓**——**业务方不知道用哪个**
- **API 不统一**——**业务方重复建设**
- **数据消费慢**——**业务方要等 ETL**

**触发点（What）**

2020 年**字节启动 DataFinder 项目**（[ArchSummit 2021]）——**目标**：「**统一数据服务**」——**OneService 风格**。

**详细做法（How）**

字节 DataFinder 的**5 大创新**：

1. **统一查询服务**
   - 关键设计：**SQL-like**——**跨 Hive / ClickHouse / Druid 联邦**
   - 关键能力：**业务方一站式**——**无感知**

2. **指标平台（OneMetric）**
   - 关键设计：**每个指标**——**Owner** + **定义** + **计算**
   - 关键能力：**10 万+ 指标**——**80% 业务方自助**

3. **实时数仓接入**
   - 关键设计：**Kafka → Flink → OneService**——**实时数据**
   - 关键能力：**秒级延迟**

4. **API 网关 + 限流**
   - 关键设计：**Kong + 自研限流**——**API 网关**
   - 关键能力：**限流 / 鉴权 / 监控**

5. **资产目录集成**
   - 关键设计：**DataFinder**——**字段血缘**——**找数据**
   - 关键能力：**业务方自助**——**「**找数据 + 用数据**」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选**Kong + Trino**（**最简单**）——**API 网关 + 联邦查询**
- 接入**核心 10-30 个数据消费方**
- 配置**基本鉴权 + 限流**
- 团队：2-3 人

**1 → 10 阶段：6-12 个月**

- 扩展到**100+ 服务**
- 引入**指标平台**（**OneMetric**）
- 引入**资产目录**（**OneAsset**）
- 团队：5-10 人

**10 → 100 阶段：12-24 个月**

- 扩展到**千+ 服务**
- 引入**实时数仓**（**Flink + Iceberg**）
- 引入**AI 数据助手**
- 团队：10-30 人

**100 → 1000 阶段：12-24 个月**

- 引入**Serverless**——**按 query 计费**
- 引入**跨云**——**多云数据服务**
- 团队：30-100 人

> **本节小结**：
> - 4 个真实案例（阿里 / 字节 / 腾讯 / 京东）印证：**OneService 不是「**装个 API 网关**」，是「**统一 API + 指标 + 资产 + 实时数仓**」**组合。
> - 关键时间线：阿里 8+ 年 / 字节 4+ 年 / 腾讯 3+ 年 / 京东 3+ 年 —— **数据服务是持续运营**。
> - 选型第一原则：**Kong + Trino**（**最简单**）——**API 网关 + 联邦查询** → **指标 + 资产**（**必须**）→ **实时数仓 + AI**（**AI 时代**）。
> - 99% 的失败来自「**直接读数仓 + 跨数仓不一致 + 业务方抵触**」——必须有**API 网关 + 统一指标 + 业务 Owner**。
> - 真正的 ROI 来自「**10-100 倍 API 调用 + 35% 指标一致性**」——是**大厂数据中台的核心保障**。
