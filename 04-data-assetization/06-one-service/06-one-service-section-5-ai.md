## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本主题的清单有一个特殊性：**"前沿"里混着三种不同层级的东西**——**接口形态**（Text-to-API、Function Calling、MCP）、**定义层**（语义层 / 指标定义驱动）、**运维自动化**（Agent 监听变更自动更新 API、自动排查、自动生成文档）。它们常被并列在同一组 bullet 里，但**判分标准完全不同**：接口形态可以查发布说明，定义层要看口径有没有人负责，运维自动化要看变更的影响面能不能枚举。混着读，读者会得出"这几个都差不多成熟"的错误结论。

本节用主文件 §2.2 的公式做统一判据：

```text
API = f(Table, Metric Definition, Dimension, Filter, Access Policy)
────────────────────────────────────────────────
问每个演进方向一句话：
  它改的是这五个入参里的哪一个，
  还是只改了"谁来填这些入参"？
────────────────────────────────────────────────
· Text-to-API     → 只改了"谁来填"（人 → 模型）
· 语义层 / 定义驱动 → 改的是 Metric Definition 的完备度与所有权
· Agent 自动化     → 试图改"谁来改契约"（这一步最危险）
· 实时服务        → 改的是 Table 这一侧的时效，与 AI 无关
```

第二个必须提前说清的陷阱是：**Text-to-API 类条目"能不能用"，取决于语义层与指标定义的完备度，而不是模型版本**。同一条"自然语言直接取数"，在演示现场成立（一个干净的小 schema）、在没有指标定义的生产仓里不成立。本章 §6.2 的字节案例给出了原因：真正让自助取数可控的，不是模型，而是**"服务引用指标定义、维度越界不可配置"**这条约束——它把"业务方自造口径"这条路径从流程上堵死了。

第三个陷阱是**把产品名当能力名**。Snowflake Cortex Analyst、Databricks Genie、dbt Semantic Layer、Cube、Hasura DDN、阿里 Quick BI + AI 都是**产品名**；它们指向的能力是"自然语言取数""指标定义即服务""自动生成 API"这三类。**本节不对任何产品是否支持某特性做断言**（这类断言在无法逐条核对发布说明时风险极高），只给判定方法：查三件事——**该能力在哪个版本进入正式可用（而不是预览）、它对外暴露的语义写在哪一节文档、有没有第三方（非厂商）生产案例**。

本节的分级判据是可核验的三条：**① 已 GA 且有正式发布说明；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条全中才算 **L1 生产可用**；只有厂商自有案例、或只在小范围被验证是 **L2 可试点**；只有路线图 / 论文 / 演示是 **L3 观望**。**本节不做判据修正**：本主题下没有一行能三条全中，因此没有 L1 行——最接近的一行（下表第 1 行，把治理与定义层作为 Agent 的取数入口）第①条给不出具名发布说明、第②条给不出第三方生产案例，按判据只能记 L2；它不叫"准 L1"，本节也不拿"机制在 AI 之前就存在"去替换判据（理由见 §5.4 第 7 条）。

> 本主题下**没有方向满足 L1 的三条判据**，最接近的是上表第一行：把 OneService 的治理与定义层作为 Agent 的唯一取数入口。它离 L1 只差证据、不差能力——统一入口、定义驱动、字段级权限、配额与计量这些机制在 §6 的四个案例里已经有 4 年以上的公开实践（年限按 §6 案例给出的起止年份推算【推算】：字节 2020-2024 为 4 年，阿里 2016-2024 为 8 年），AI 带来的唯一变化是**调用方从人变成了机器**，而机器比人更不能容忍模糊的契约（人看到报错会自己换写法，Agent 会原样重试）。但它卡在两条判据上：**第①条**要求"已 GA 且有正式发布说明"，本节写不出这些部件的 release note 名称与年份；**第②条**要求"第三方（非厂商）公开生产案例"，而 §6 的四个案例是实践方自述（阿里 OneService 还是厂商自有产品），讲的又是治理本身而不是 Agent 调用。**按本节采用的判据，第②条核不到就是 L2**——降级不是贬低，是准确；把它写成"L1 的边界案例"会让同一方向在其他章节评级不一致。上表除第 1 行以外的 8 行，不够格的原因可以归成三类：**契约侧的新东西还没有通行做法**（校验层放哪、权限语义怎么写、口径归哪一层、路由由谁决定）；**它们试图改的是"契约本身"而不是"谁来调用"**（自动改 API、自动生成物化策略）——这是最需要等证据的一类；以及**它根本不构成 AI 方向、或拿不出第三方验证**（实时 OneService 的瓶颈在物化时效与一致性语义，与 AI 无关，见 §5.2.4 的第二个方向；MCP 的规格可核验，但"生产规模被第三方验证"这一条核不到）。

读这张表时还要记住一件事：**"级别"一列说的是"能不能现在就规划"，不是"这件事重不重要"**。Text-to-API 与语义层的重要程度都很高，但它们的落地顺序排在"定义写全、治理做严"之后——因为一个没有指标定义、没有配额的服务层，接上自然语言调用的第一件事就是被一条大查询打垮，而且你无法回答"这个数字是哪个口径"。级别低不等于不用管，它只意味着**现在做会比晚一点做贵**。

### 5.2 演进方向逐条拆解（核心节）

下面四个小节按同一套结构写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**；其中 §5.2.4 一小节里有两个方向（Agent 自主维护、实时服务），第二个方向同样按这六行展开。只写收益不写代价的方向在评审时应被直接打回——本主题里每一次"门槛降低"，都会对应一项新的校验责任。四个小节各自改变了什么，先集中列一次：

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 自然语言取数 | 人机分工：谁写查询（人 → 模型） | **接口层**，`API = f(...)` 的五个入参一个没变 |
| §5.2.2 把服务交给 Agent | 调用方与调用节奏：人 → 机器；契约读者：人 → 机器 | **接口边界与治理落点**（真变化） |
| §5.2.3 语义层与定义驱动 | 把"定义完备度"从加分项变成硬上限 | **定义层**（AI 没有改变谁负责定义） |
| §5.2.4 Agent 自主维护与实时服务 | 候选变更的生成成本 → 近零；实时那一支与 AI 无关 | **只换了产出物**——变更本身的代价一分未降 |

读法建议：只有 §5.2.2 是可以照做的（治理与定义层已经存在，只需把它做严）；§5.2.1 与 §5.2.3 是同一件事的两半（门槛与上限）；**§5.2.4 是本节的反方**——它说明为什么"Agent 自主维护 OneService"这类说法在责任链上没有落点。

这六项里最容易被跳过、也最该被追问的是第四项（付出）。本主题的"付出"有两个固定形态：**把"谁填参数"从人换成模型，代价是"错的时候没人复核"**；**把"生成产物"交给模型，代价是"看起来专业的错误会被当成方案"**。两项都不在采购清单上，也不会出现在任何 demo 里。

#### 5.2.1 自然语言取数：换的是"谁写查询"，不是"数据怎么被算出来"

- **旧做法与它的卡点**：数据消费的门槛是"会写查询"——业务方要知道表在哪、字段叫什么、怎么 JOIN、指标口径是什么（主文件 §1.2 列了五个痛点，与数据消费直接相关的是前三个：找数难、懂数难、用数难）。卡点有三个：**供给被锁在少数熟手身上**（会写的人产能恒定，查询量增长不会让他们更快）；**发现缺口**（用户往往不知道要查的东西在哪个资产里，按 §2.4 的分工那是元数据目录的职责，服务层并不持有这份信息）；**口径分裂**（同一指标在不同接口里定义不同，§3.5 的「口径不统一」已把它列为反模式）。
- **AI 改变了什么机制**：改变了**人机分工**——把"把意图翻译成查询"这件事从人换成了模型。注意它改的是接口层的分工：§2.2 的五个入参（表 / 指标定义 / 维度 / 过滤 / 访问策略）一个没变，引擎侧更没变。
- **由此得到的**：**因为翻译被交给了统计模型，所以"写"的门槛下降、而"校验"的必要性上升**——人写错时会自己复核，模型写错时不会，于是链路上必须显式长出一个校验层：表与字段是否存在、维度是否在指标定义声明的范围内、权限是否满足、扫描量是否超阈值。§2.3 已把这条链路写成四步（schema 注入 / few-shot / 校验层 / 人在环），**这四步里只有"校验层"是本方向真正的工程量**，模型反而是最容易替换的部件。

```text
自然语言 → [模型生成？指标+维度+过滤] → [校验层] → [服务层执行]
                                          ↑ 本方向的工程重心
        ────────────────────────────────────────────────
        校验层必须回答的四问：
          ① 这个指标存在吗？（不存在 → 报错，不许编）
          ② 这些维度在指标定义里声明过吗？（越界 → 拒绝，§6.2 的约束）
          ③ 这个调用方有权看这些数据吗？（行 / 列 / 指标级，§2.3）
          ④ 扫描量与调用量在配额内吗？
        ────────────────────────────────────────────────
        判定方法：给模型一个不存在的指标名，
        看链路是"报错"，还是"编一个看起来合理的结果"
```

- **由此付出的**：**其一，正确性的归属模糊了**——结果错了，是模型的问题、指标定义的问题，还是源侧数据的问题？没有校验层，这个问题无法回答，复盘会停在"模型不太行"；**其二，多出一个与引擎无关的延迟与成本项**（一次模型调用），而它按调用方归账时往往没人认；**其三，没有指标定义时，上限由"命名是否自解释"决定**——模型只能靠表名与字段名猜口径；**其四，证据链变长**：自然语言、生成的调用、校验结果与实际执行的查询都得留，任何一环没留，复盘就做不成。
- **证据与来源**：【公开】厂商侧的代表是 Snowflake Cortex Analyst 与 Databricks Genie（原 §5.3 已列，均标注 2024），以及国内 BI 产品 + LLM 的形态（原 §5.3 点名阿里 Quick BI + AI）；**本节不对它们的能力做断言**，判定方法是查三件事（见 §5.1）。【公开】学术侧的公开评测集是 Spider（EMNLP, 2018）与 BIRD（2023）——**两者都是单库、schema 相对干净的设定**，不度量跨源联邦，也不度量"指标语义"；把单库成绩外推到"跨源 + 指标体系上自然语言取数"是常见误读。
- **成熟度**：**L2**。判据：单库、已有指标定义的范围内有产品化能力与公开评测，跨源与跨口径场景既无公开评测也无第三方生产案例；可以 PoC，不要作为核心依赖。
- **什么时候值得做**：已有一批口径明确、被反复查询的指标（§6.2 那种"定义即服务"的形态），且你愿意把校验层当成一个要长期维护的组件来做时。
- **什么时候不值得做**：指标定义还没统一、口径还在打架时——此时模型只会把口径分歧变成一个更快给出的错误答案；另外，若查询量本身很小、业务方找熟手问一句就能拿到数，引入它的收益也覆盖不了校验层的维护成本。

#### 5.2.2 把 OneService 交给 Agent：契约的读者从人变成了机器

- **旧做法与它的卡点**：§4.1 把 AI 集成放在最后一步（Step 8），把它当成"再加一层调用"。但治理面（鉴权、限流、计量、版本管理）是为人的节奏设计的：调用方是人时，"这条接口不该这么调"可以靠约定与常识兜住（§6.1 的教训正是"没有限流与配额时，单个应用的异常调用打挂上游"）。§3.5 的「忽视 AI 集成」已点明：只服务 BI、不服务 Agent，是一个反模式。
- **AI 改变了什么机制**：**调用方与调用节奏**（人 → 机器），以及**接口的读者**（人读文档 → 机器读工具描述与参数 schema）。机制上没变的是 §2.2 的五个入参——它们一个都没多。对 Agent 来说，**N 个数据源与 N 个指标收成了 1 个工具**。
- **由此得到的**：**因为 Agent 只看到"一个工具 + 一组参数"，所以原先由人承担的那些判断必须由服务层自己做掉**——这条调用能不能发、发多少、扫多少、超了怎么办。而这些部件（统一入口、定义驱动、字段级权限、配额、计量）**在 §6 的四个案例里已经跑了多年**：§6.1 阿里把"先搜后建 + 统一鉴权限流 + 只建在公共层之上"做成流程，§6.2 字节把"服务引用指标定义、维度越界不可配置"变成硬约束，§6.4 的做法被该章总结为**受约束自助 + 字段级鉴权**。**这就是本节最接近 L1 的一行**（它缺的是"Agent 调它"的第三方案例，不是能力）——要落地的机制早已存在，AI 带来的只是"必须把它做出来"的紧迫性。

| Agent 改变了这一侧 | Agent 没有改变这一侧 |
| --- | --- |
| 调用频率与并发形态（机器节奏，不是人的节奏） | 指标口径的定义权（仍在定义方与 Owner） |
| 审计对象（哪个 Agent、基于哪个会话、为回答什么问题） | 行 / 列 / 指标级权限的判定规则（§2.3） |
| 错误信息的消费方式（模型会重试，人不一定） | 变更的影响面（仍要靠目录与血缘枚举） |
| "一个工具"的接口形态（数据源数量被隐藏） | 数据本身怎么被算出来（引擎与建模，§2.2 的五个入参） |

值得注意的是，**"把自由度限定在已治理资产内"这件事在 AI 之前就已经被回答过**：§6.4 的零售企业案例给出的形态是"业务方只能在已发布的公共层表 / 已定义的指标之上构建服务，不允许直连原始表、不允许自写任意 SQL"，该章把它总结为**受约束自助 + 字段级鉴权**。Agent 调用只是把这个形态的**消费方**换了一次——**约束的形状没变，变的只是违反约束的人不会像人那样犹豫**。

- **由此付出的**：**其一，拒绝必须结构化**——只回"403"或"超时"时，模型会原样重试，把一次超量放大成持续负载；错误里要能区分超量、权限、语法；**其二，审计的对象变了**——按人审计在这条链路上失去解释力，要改记 Agent 身份、会话与目的；**其三，账要按调用方归集**——否则容量规划失去依据；**其四，工具描述本身成了契约**——描述写错，模型会稳定地调错接口，而且这种错误不报错、只给错结果。
- **证据与来源**：可核验的材料是本章 §6 的四个公司实践材料（阿里 2016-2024、字节 2020-2024、Netflix 2019-2024、某零售企业 2020-2024）——它们列在 §5.4 的"第三方生产案例"一类，但本节把证据等级记为"实践方自述"，**不当判据②要求的第三方（非厂商）生产案例使用**（理由见 §5.4 第 7 条）；工具形态见 §4.2 第 10–11 项（Function Calling / Text-to-API）与 §4.5 的示例 3。**MCP 单独说明**：该协议规格 2024 年公开、有版本与修订、有多家独立实现，但**"某平台支持 MCP、支持到什么程度"必须自行核验官方文档**，本节不给版本号、也不做能力断言；要判定，查它对外暴露的语义（工具描述 / 权限 / 会话）写在哪一节。
- **成熟度**：**治理入口 L2**（统一入口、定义驱动、鉴权 / 配额 / 计量在 AI 之前已生产可用，且有 4 年以上的公开实践；但"LLM / Agent 调服务层"缺第三方非厂商生产案例，见 §5.4 第 7 条）；**协议与工具生态 L2**（接口形态稳定但权限语义与调用方归因没有通行做法，生态仍在演进）。
- **什么时候值得做**：已有服务目录与统一网关、且准备承接机器调用方时——先把配额、字段级鉴权与结构化错误补齐。
- **什么时候不值得做**：服务层还没有统一入口（各业务线各写各的接口）时——把 Agent 接到这种状态上，只会让"口径分裂"从报表时代进入 Agent 时代。

#### 5.2.3 语义层与定义驱动：AI 把"定义完备度"从加分项变成硬上限

- **旧做法与它的卡点**：口径过去只存在于文档与人脑里——§2.1 的指标 / 派生指标 / 维度 / 标签，§2.3 的口径管理与指标血缘，都要靠人维护；卡点是**定义只有人读得懂**：口径争论靠开会，改口径靠发公告（§6.2 的教训：指标改了，接口里的 SQL 未必跟着改）。
- **AI 改变了什么机制**：**它没有改变"定义该由谁负责"，只是把定义的完备度变成了硬上限**。语义层（dbt Semantic Layer、Cube 一类）在这里的作用，是把口径从文档搬进可被程序读取的定义，让模型有 ground truth 可对齐——同一份定义既服务 BI，也服务模型。
- **由此得到的**：**因为服务"引用指标定义、维度越界不可配置"，所以模型生成的调用不可能自造口径**——§6.2 的那条约束正是"让 AI 自助但不产生新口径"的工程前提，也是该章给出的 AI 时代结论（**受约束自助 + 字段级鉴权 + 定义驱动**）里最容易被忽略的一半。反过来，没有语义层时，模型的每一次调用都在**重新发明口径**，而且发明得比人更自信。
- **由此付出的**：**其一，语义层成为新的单点**——定义错了，所有下游一致地错，而且错得更可信（数字对得上）；**其二，定义维护成本与"谁能改定义"的权限问题**变成关键路径，改一次口径的影响面要能被枚举（这正是 §6.2 的依赖血缘要解决的事）；**其三，定义与物理表之间的漂移若无人负责**，会以"两个系统数字对不上"的形态长期存在，且每次都要重新排查一遍；**其四，模型换代不会解决定义缺失**——这是本方向最常见的误判。
- **证据与来源**：可核验的材料是 §6.2 字节的指标定义驱动服务（2020-2024，公司公开材料，4+ 年）——同属实践方自述，**不构成判据②要求的第三方（非厂商）生产案例**（见 §5.4 第 7 条）；产品侧的 dbt Semantic Layer 与 Cube 有公开文档可核验（**本节不给版本号**，能力与发布节奏以各自官方文档为准）。**判定方法**：抽 20 个业务问题，看模型是否只在"已定义指标"的范围内作答——超出范围时它是**拒绝**，还是**编一个指标出来**；再抽 20 个已被定义的指标，看模型选的维度是否都在定义声明的维度表里。
- **成熟度**：**L2（与 LLM 的集成形态）**。判据：语义层本身是既有工程、可核验；但"LLM 通过语义层取数"这一集成形态缺第三方非厂商生产案例，且"口径归哪一层负责"没有通行做法；定义驱动服务这一工程机制本身是 §5.1 表第 1 行（本节最接近 L1 的一行）的组成部分，而该行同样因缺第②条证据只记 L2。
- **什么时候值得做**：口径争议已经在影响决策、且你愿意先投入把"指标定义 + 维度 + Owner"写全时——**先写定义，再谈集成**。
- **什么时候不值得做**：组织里还没有公认的口径 Owner 时——语义层会把"没有 Owner"这件事固化成一个看起来权威的单点。

#### 5.2.4 Agent 自主维护与实时服务：把"变更"交给模型，而变更的代价没降

- **旧做法与它的卡点**：§3.5 的反模式「无血缘」是——API 改了口径，不知道影响哪些调用方；§6.2 的依赖血缘与 §6.1 的"记录调用方清单"都是为这件事建的。而 Agent 自主变更会把这个问题放大：变更的影响面从"人记得的调用方"变成"没人枚举过的调用方"。
- **AI 改变了什么机制**：**只改变了"候选变更的生成成本"**——OpenAPI Schema、接口文档、迁移脚本、指标异常的第一批排查假设，这些产物从"要有人花时间写"变成"随手可生成"。**变更本身的代价（契约破坏、调用方迁移、口径变更的连锁影响）一分未降**；而"这个变更该不该发"是决策，不是生成。
- **由此得到的**：**因为生成变便宜，所以低风险产出第一次可以默认产出**——文档、Schema、异常排查线索、以及"这批指标里哪些没人调用了"这类清单。这也是原 §5.4 趋势 5「AI 增强指标治理」里唯一站得住的部分：它增强的是**发现与描述**，不是决策。
- **由此付出的**：**其一，"谁批准变更"没有答案**——Agent 改线上契约时，影响面必须能自动枚举，而这取决于目录与血缘的完备度（本节之外的基础设施，见 §4.1 Step 6 的元数据注册）；**其二，错误以"看起来专业的建议"形态出现**——一份语法正确、字段齐全的迁移脚本可能是错的，且不会自己报错；**其三，自动生成物化策略会直接动计算资源**（原方向 3 的后半段），成本落在数据平台账上、决定权却在模型侧；**其四，实时那一支的代价与 AI 无关**——"API 实时返回"的瓶颈在物化时效与一致性语义（跨源读的是各源各自的当前状态），把它挂 AI 名义会误导选型。
- **证据与来源**：**本节没有可核验的第三方生产案例**（"Agent 自主维护数据服务"这一形态）：**改线上契约**这一支因此只记 L3；**生成类产出**（文档、Schema、排查线索、调用清单）按判据中"仅有厂商自有案例"那一档记 L2。可核验的替代是 §3.5 反模式「无血缘」与 §4.1 Step 6 所描述的既有做法——变更影响面靠目录与血缘枚举，不靠模型。**判定方法**：拿一次真实的契约变更，让 Agent 列出受影响调用方，与目录/血缘给出的清单对照；**差异率就是这条路的当前上限**。
- **成熟度**：**L3（自动改线上契约、自动生成物化策略）/ L2（文档、Schema、排查线索、调用清单）**。判据：生成类产出风险低、可核验；改契约类无公开案例且责任链没有落点。
- **什么时候值得做**：当一个"建议产物 + 人审"的流程已经在跑，且影响面能被自动枚举时——把它接到变更评审的输入端。
- **什么时候不值得做**：影响面还靠人工回忆、或变更没有回滚与审计时——**不要让模型直接改线上契约**。

**同一节里的第二个方向：实时 OneService（原 §5.4 趋势 6）**——它与 AI 只有一层关系，按同样六行单独说清：

- **旧做法与它的卡点**：时效承诺靠"定时物化 + 批查询"：数据按小时或天级落进服务层可查的表，接口的响应时间与新鲜度都稳定，但新鲜度有下限；要求分钟级以内的场景（风控、库存、大促看板）只能另开一条实时链路，而两条链路的指标口径要再对齐一次。
- **AI 改变了什么机制**：**没有改变**。这一支是数据栈自身的实时化（流处理与湖仓时效）：按 §5.1 的公式，它改的是 Table 这一侧的时效，与"谁来填五个入参"无关——模型既不决定数据什么时候可查，也不决定一致性语义。
- **由此得到的**：**因为时效由物化与一致性语义决定，所以把它挂到 AI 名下不会让链路更快**（趋势清单里它与 AI 方向并列，容易读成"AI 让实时成为可能"）；它唯一与 AI 有关的落点是准入——机器调用方会把"偶尔可用"的链路当成"总是可用"，实时接口的配额与降级策略要比批接口更早定下来。
- **由此付出的**：**无界流直查破坏可解释性**：跨源读的是各源各自的当前状态，同一句提问在不同时刻给出不同口径的答案，这一点很难向业务解释（§5.6 第 4 条预测的证伪信号，正是"出现能说清一致性语义的 API 直查无界流案例"）；此外实时链路的成本与运维复杂度要另计一份。
- **证据与来源**：**本节没有 AI 角度的公开证据**，因此不按 L1 / L2 判定；可核验的替代是数据栈侧的实时化路线（流批一体入仓 + 服务层查询），口径与判定方法见 §5.1 表里"实时 OneService"那一行。
- **成熟度**：**L3**（针对"AI 驱动的实时服务"这一提法）。判据：本节给不出任何 AI 角度的公开证据；若按数据栈自身的实时化路线推进，它与本节的 AI 分级无关。

### 5.3 与本主题既有栈的接口在哪

OneService 与 AI 之间不是「结合」关系，而是**契约**关系：谁调用谁、数据以什么形态穿过边界、失败时谁负责。这张表比"AI 能做什么"更能决定它能不能落地。下表的"现状"指该接口形态在公开实践中的成熟度，不是某一家厂商的能力。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Agent / LLM → OneService | 工具调用：能力描述 + 指标 + 维度 + 过滤，返回结果集或**结构化错误** | 服务层准入负责拒绝；模型负责换参数或放弃 | 治理侧已生产可用；Agent 侧仅试点（缺第三方案例） |
| OneService → 指标平台 / 语义层 | 读指标定义（口径、可用维度、SLA、Owner），**服务引用定义而不是重写 SQL**（§6.2） | 定义侧；定义缺项则拒绝发布 | 生产 |
| OneService → 数据目录 | 服务注册：口径、Owner、上游表 / 指标、SLA、调用方清单（§6.1、§4.1 Step 6） | 目录侧；缺项不可提交 | 生产 |
| OneService → API 网关 | 鉴权、限流、计量、版本管理（与 [§ 07 数据 API 网关](../07-data-api-gateway/07-data-api-gateway.md) 的分工，主文件 §2.4） | 网关侧；拒绝即闭环 | 生产 |
| 检索层 ↔ OneService | 交接物 = "这个问题该走文档还是走指标"的路由判断 | 编排层；**路由错误应可观测**（否则用户只会看到"答得不对"） | 试点 |
| Agent → 变更流程 | 交接物 = 建议的 Schema / 迁移脚本 + 影响面清单 | 变更评审人；**模型不签字** | 观望 |

这张表里有三处值得单独点出：

1. **第一行是真边界变化**：服务层对上层不再暴露"连哪个库、用哪张表"，只暴露能力描述与参数。**它把数据源的数量从 Agent 的视野里隐藏了**——这既是它好用之处，也是它危险之处：隐藏得越干净，调用方越无法判断"这个结果是不是我要的口径"。
2. **第二行是 AI 时代最该加固的一条**：机器调用方不会像人那样"感觉数字不对"，所以服务与定义之间的绑定必须是引用关系（§6.2），而不是"生成时抄了一遍"。
3. **第六行是唯一还在观望的边界**：变更的批准权留在人手上，AI 只交建议——这与 §4.1 把 AI 集成放在最后一步是一致的。

把边界上的失败按类型拆开，责任归属就清楚了：

| 失败类型 | 落在哪一侧 | 对架构的直接影响 |
| --- | --- | --- |
| 生成失败（模型编了不存在的指标 / 越界维度） | 校验层（若存在）；否则落到服务层报错 | 校验层缺失时，错误以"结果为空"或"语法错误"暴露，调用方无法自助 |
| 口径失败（引用了一个不该用的指标） | 定义侧与 Owner | 数字可信但没有意义——比报错更难发现 |
| 准入失败（超配额、越权） | 服务层，且必须返回**结构化**错误 | 不结构化时，Agent 原样重试，负载被放大 |
| 契约变更失败（调用方未迁移） | 变更评审人 + 调用方清单 | 影响面不能枚举时，事故只能在下游失败时被发现 |
| 时效失败（实时承诺与物化延迟不符） | 服务层的时效承诺方 | 承诺写入接口文档却无人负责，会长期以"偶尔偏旧"的形态存在 |

这五行对应三种返工成本：第一、四行是**接口契约问题**，改动便宜但必须早做；第二行是**治理问题**（定义 Owner），越晚补越贵；第三、五行是**责任写没写清楚的问题**——它们没有技术解法。

由此得到两条约定。

**第一条约定：工具描述是契约的一部分，要版本化。**Agent 看到的是能力描述与参数枚举，描述变了调用方就可能失败——所以它必须像 API 契约一样有 Owner 与版本，变更要通知；这条约定在过去不存在，因为"接口文档"曾经只是给人看的辅助材料。

**第二条约定：变更的批准权留在人手上，AI 只交建议。**这不是保守，而是因为变更的影响面必须能被枚举（第六行），而枚举依赖的是目录与血缘的完备度，不是模型的推理能力。落到工程上就是一句话：**生成的 Schema 与迁移脚本进入评审流程的输入端，而不是发布流水线的输出端**。

最后补一句"现状"列的用法：**它是接口形态的成熟度，不是你的架构成熟度**。同一个"服务 → 数据目录"的接口，在已有目录的组织里是生产级，在没有目录、靠人问的地方只是纸面存在；同一个"服务 → 指标平台"的引用关系，在定义驱动生成的组织里是生产级，在"手写 SQL 再抄一遍定义"的组织里则根本不存在。**评估自己时，把这一列替换成你的实际形态，再决定要不要现在做**。

### 5.4 公开进展与文献

按「论文与公开评测 / 官方文档与发布说明 / 第三方生产案例」三类列出。宁少勿假：只列确有把握、读者可自行核验的条目。

**官方文档与发布说明（判定入口）**

6. 模型供应商的工具调用文档（原方向 2 列出的 OpenAI Function Calling 与 Anthropic Tool Use，各有自己的官方文档页）与你所用服务层自己的 OpenAPI / 工具描述文档——**判定方法**：查工具描述里的参数枚举是否与指标定义一致（不一致时模型会稳定地调错），以及拒绝错误是否区分超量 / 权限 / 语法；参数枚举与错误语义以各自官方文档的当前版本为准。

**第三方生产案例**

7. 本章 §6 的四个案例（阿里 OneService 2016-2024、字节指标定义驱动服务 2020-2024、Netflix 联邦查询层 2019-2024、某零售企业受约束自助 2020-2024）——**本节把它们的证据等级记为"实践方自述"，不当第三方证据使用**：书中给出的是公司名与年份区间，§6 对应处的挂载形式是方括号占位（`[阿里 OneData / OneService 公开材料 2016-2024]`、`[字节技术博客 2020-2024]`），没有文档标题、也没有链接，读者按它定位不到任何一份可读材料；而对阿里而言 OneService 是其自有产品，这类材料本身就属于厂商自有案例。**这正是 §5.1 表第 1 行记 L2 而不是 L1 的直接依据**：它们能证明的是**服务化与治理本身**有人在做、且做了多年，**不能证明"AI 取数"**有人在做——**专门针对"LLM / Agent 调 OneService"的第三方公开生产案例，本节给不出**。这个空缺本身是结论：它也是所有 AI 特有方向（Text-to-API、MCP 集成、Agent 自动运维）压在 L2 / L3 的直接原因。

**尚未核验的一类条目（保留方向，不当证据）**：原 §5.3 的 7 条条目（含协议与产品：Cortex Analyst、Genie、dbt Semantic Layer、Cube、MCP、Hasura DDN、Quick BI + AI），以及散落在原 §5.4 趋势里的"成为标配""标准化"这类总括判断，本节**统一处理为待核验**：它们指向的能力已经落在 §5.1 表里（自然语言取数、定义驱动、工具化集成），但"某产品是否在某版本支持某特性"只能逐条核对官方文档；而"成为标配"需要的是采用率证据，本主题这一类证据恰好空缺——**能被核验的是能力与机制，不能被核验的是"行业已经这么做了"**。

**怎么用这份清单**：要核"能力存不存在"看官方文档（最快）；要核"机制成不成立"看第一类（最慢但最稳）；要核"在我这里值不值得做"，只能靠 §5.2 给出的判定方法——**第三类问题没有任何公开材料能替你回答**。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购、也不需要内部资料）：

1. **自然语言取数**：给模型一个不存在的指标名，看它是报错还是编结果。
2. **维度越界**：让它按一个指标定义里没声明的维度拆分，看服务层是拒绝还是照做。
3. **工具描述**：把工具描述里的枚举改错一个值，看调用方是否稳定地调错——这是"描述即契约"的检验。
4. **拒绝可消费性**：发一条明显超量的调用，看返回是否结构化、Agent 能否据此换写法而不是重试。
5. **口径绑定**：改一次指标定义，看引用它的服务是否自动跟随（§6.2 要解决的正是这件事）。
6. **影响面**：拿一次真实契约变更，对照目录/血缘与人肉回忆给出的受影响调用方清单，看差异。
7. **配额与归因**：查能不能按调用方（哪个 Agent / 哪个应用）列出调用量与成本。

### 5.5 被过度宣传的部分

**「Text-to-API 会让业务方零门槛，不再需要写查询」**——实际是：它取代的是"写"这一步的人力，**没有取代口径**。按 §2.2 的公式，`API = f(Table, Metric Definition, Dimension, Filter, Access Policy)`，模型能填的是括号里的参数，括号里出现什么完全由定义层决定。原因：模型选对指标、选对维度的前提，是有人把口径写成了机器可读的定义；公开评测集又是单库、干净 schema 的设定，**跨源与跨口径的真实环境不在评测范围内**。**它什么时候才会成真**：出现跨源、含指标语义的公开评测集，并且有第三方在其中给出可复现的成绩；在那之前，正确的说法是"在已定义指标的范围内可用"，而不是"零门槛"。

**「把 API 注册成 MCP Tool，OneService 就成了 Agent 的通用数据源」**——实际是：注册只让能力**被看见**，不解决身份、配额、审计与错误语义这四件事，而它们恰恰是 OneService 存在的理由（§2.2 的 Access Policy、§6.1 的统一鉴权限流、§6.2 的定义约束）。原因：**"通用数据源"意味着任何 Agent 都能调**，而"谁能调哪些指标、调用量算谁的账、审计记到哪个会话"在这条路上没有通行做法；协议本身仍在演进，把架构假设压在某个版本上会付出迁移成本。**它什么时候才会成真**：出现公开的、含配额与审计设计（而不只是"接上了"）的跨供应商实践材料。

**「Agent 能自主维护数据服务：监听 schema 变更自动更新 API、自动生成 Schema 与文档、自动排查指标异常」**——实际是：**生成便宜，变更昂贵**。原因：文档、Schema、排查线索都是产物，错了重生成即可；而改线上契约会波及所有调用方，影响面必须能自动枚举——那依赖的是目录与字段级血缘的完备度（§3.5 反模式「无血缘」的解法），不是模型的推理能力；自动生成物化策略还会直接动计算资源。**它什么时候才会成真**：影响面能自动枚举 + 变更流程有自动验证与回滚 + 有人对契约签字，三者同时具备；在那之前，正确的落点是"生成建议 → 人审 → 变更"。

这三条的共性：**它们都把"产出变便宜"当成了"判断变准确"**。而本主题的判据落在两处硬约束上——**口径由定义层决定**（§5.2.3），**契约变更由人签字**（§5.3 第六行）。这两条不随模型换代而改变。

**怎么用这三条判断**：遇到一个"AI + 数据服务"的提案，按顺序问三件事——① 它降低的那项成本（写查询 / 生成文档 / 找影响面）落在 §2.2 公式的哪个入参上，还是只在公式外面；② 它改动的动作，是"谁来调用"，还是"契约本身"（后者要影响面枚举与签字）；③ 如果它的输出错了，谁会被叫去解释（答不出人，就说明还没有责任人）。三问之后仍站得住的，通常只有一条：**把定义写全、把治理做严，然后再放开给机器调**。

### 5.6 未来 3–5 年：可证伪的预测

预测必须写成「预测 + 会成真的信号 + 会证伪的信号」；写不出信号的预测不要写，因为它无法被检验，也就不带信息量。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 1. Agent 取数的默认形态是**经过受治理的服务层**（统一入口 + 定义驱动），而不是直连表或直写 SQL | Agent 平台把"数据服务 / 语义层"列为首选连接器；配额与字段级权限在服务层配置 | 公开生产案例里，直连单库 / 直写 SQL 的方案持续占多数 |
| 2. 自然语言取数的准确率提升主要来自**指标定义与语义层的完备度**，而不是模型版本 | 厂商发布与案例介绍强调定义 / 语义层 / schema 检索，模型版本是次要变量 | 无语义层的纯模型方案在同类评测上追平带语义层的方案 |
| 3. 契约变更仍由人签字，"Agent 自主改线上 API"在 3–5 年内停在建议层 | 工具把 Schema / 迁移脚本生成定位为"评审前产物"；变更门禁要求人工会签 | 出现公开的、生产规模的、Agent 自动改契约并有自动回滚与审计的案例 |
| 4. 实时 OneService 的落地形态是**先物化再由服务层查询**，而不是 API 直查无界流 | 公开案例反复出现"流批一体入仓 + 服务层查询"的组合 | 出现公开的、生产规模的 API 直查无界流案例，并说明其一致性语义 |

读这四条的方法：**它们的证伪信号都比成真信号更容易观测**。这不是巧合——本主题的特点是，新能力大多落在"接口层与治理层"，而**契约本身（口径归属、变更批准权、一致性语义）很少被真正放开**；因此预测的默认值是"落点变化、契约不变"。

每条预测背后的依据分别是：第 1 条依据的是"治理必须有一个落脚点"（§6.1–§6.4 的四个案例都是把治理收到一处）；第 2 条依据的是 §5.2.3 的机制（模型要选对指标，前提是定义存在）；第 3 条依据的是"变更的影响面必须能被枚举，而这依赖目录与血缘"（§3.5 反模式「无血缘」的解法在工具侧，不在模型侧）；第 4 条依据的是"无界输入的一致性语义难以向业务解释"。**四条里只有第 1 条是趋势判断，其余三条都是机制推论**——这也是判断本节是否可信的一个自检点：机制推论的比例越高，这份评估越不容易过期。

**被检验得最快的是第 1 条**：一年内就能看——Agent 生态里"经过服务层"与"直连库"两类连接器的公开采用情况。**最慢的是第 3 条**（否定式预测，需要有人长期跟踪变更流程），**最容易先被推翻的是第 4 条**（它只要一个反例就够）。**把预测按"被证伪后影响多大"排序，比按"可能性多大"排序更有用**：第 1 条若被证伪，"服务层"这一层的价值判断需要重写；第 4 条被证伪只说明实时引擎补上了自己的短板。

还可以用这四条做一次反向自检：**如果第 1、2 条同时被证伪**，意味着"定义与治理是前提"这个判断错了，本节 §5.2.3 与 §5.7 的行动顺序都要重排；**如果只有第 3 条被证伪**，那说明变更的可枚举性比预期更容易做到（例如字段级血缘普及到可自动枚举），此时"人签字"这一条的形态可以放宽、但责任归属不会消失。**四条里，第 2 条的观测成本最低**——只要看厂商发布材料里"这次升级提升了多少"讲的是模型还是定义，就能判断行业自己认为瓶颈在哪。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有 OneService / 指标平台，还没接 Agent | 先补字段级鉴权、配额与**结构化错误** | 拒绝率与单次调用扫描量的分布 | 不要在没人配配额时把服务层开放给 Agent |
| 业务方要求"自然语言取数" | 先在已有指标定义的范围内做，把校验层建起来 | 超出定义范围的提问占比、模型的"编造率" | 不要在没有指标定义、也没有校验层时对业务承诺准确率 |
| 正在选语义层 / 指标平台 | 先把口径、维度与 Owner 写全，定下"谁能改定义" | 定义变更的影响面能否自动列出 | 不要先买工具再补定义；不要把"能生成 SQL"当成"口径有人负责" |
| 想用 MCP / Function Calling 统一暴露 | 先定工具描述的所有权与版本策略 | 工具描述变更是否引发调用方失败 | 不要把架构假设压在某个协议版本上 |
| 想让 Agent 自动更新 API / Schema | 先把字段级血缘与调用方清单补齐 | 影响面能否自动枚举（与人工清单的差异率） | 不要让模型直接改线上契约；不要让自动生成的物化策略直接生效 |
| 想上实时服务 | 先按数据栈的实时化路线把物化与一致性做出来 | 时效承诺能否向业务解释清楚 | 不要为了"AI 实时"把无界流接进 API |
| 接口重复、复用率低 | 先把"先搜后建 + 服务注册（口径 / Owner / SLA / 调用方）"做出来 | 复用率与下线接口数 | 不要用 Text-to-API 掩盖"接口没有目录"这件事 |
| 业务方在讨论"全自助建服务" | 把自由度限定在已发布资产上（受约束自助 + 字段级鉴权） | 自助服务里越界配置的拦截次数 | 不要开放自写任意 SQL 与直连原始表 |

「明确不要做」这一列的共同逻辑：**这些动作都把"人原本要承担的判断"直接交给了模型或工具**——而在数据服务这个方向上，那些判断（这个口径对不对、这条调用该不该发、这个变更影响谁）恰恰是工程上唯一可靠的部分。按投入排序，行动顺序是三件：**先把治理与定义补齐（本节最接近 L1 的一行）→ 再把自然语言取数开在已定义范围内（L2）→ 最后才谈协议化与自动化（L2 / L3，等信号）**。

判断某件事该不该现在做，通用口径有两条：

- 它是否在**绕过你的服务层**？凡是在服务层之外新建一条取数通路（让 Agent 直连库、让业务方直连宽表）的方案，都会把口径与权限重新打散一次；正确动作是把它变成服务层的一次准入配置。
- 它是否在改**契约**？改契约的成本不在生成，而在"影响面能否枚举 + 谁签字"；答不上这两问的，先别做，等 §5.6 的信号。

如果只允许做一件事，做第一件：**把"被拒绝"变成一次可被机器理解的结果**。它同时解决两个问题——让 Agent 不至于把超量调用反复重发，也让服务层第一次有了可统计的拒绝率；而它是治理层里最便宜、见效最快的一环。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**"谁来调用数据服务、契约给谁看"**——调用方从人变成机器，接口的读者从读文档的人变成读工具描述的 Agent。于是原本靠常识与约定兜住的那些判断（这条调用该不该发、扫多少、超了怎么办），必须由服务层的字段级鉴权、配额与结构化错误来接管。它**没有改变**的是 §2.2 的公式本身：口径仍由指标定义决定（§5.2.3），契约变更仍由人签字、影响面仍要靠目录与血缘枚举（§5.2.4）。因此本主题下**没有任何方向满足 L1 的三条判据**，最接近 L1 的只有一件——**把 OneService 的治理与定义层做严，再让它承接机器调用方**（它缺的是第三方证据，不是能力）；自然语言取数、协议化集成、Agent 自动运维都还在可试点或观望区。
>
> 判断本主题下任何新提法的快捷方式：**它改的是 §2.2 五个入参里的哪一个，还是只改了谁来填？** 只改"谁来填"的，门槛会下降、校验责任会上升；声称能改"定义与契约"的，先问影响面能不能枚举、谁签字。
