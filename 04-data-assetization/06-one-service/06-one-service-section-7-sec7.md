## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表用九个维度、1–5 分排出一条「谁更强」的队列：数据语义统一、可治理、AI 友好、灵活性、性能、业务门槛、工程复杂度、实时性、成本。这张表里真正的信息量其实只有一句话——**灵活性越高的方案，语义统一越低；语义越统一的方案，工程复杂度越高**。这句话盖不满整张表：前半句（灵活性越高、语义统一越低）只在六行中的五行成立，第六行是例外——**Text-to-API 的灵活性是次高档（4）、语义统一却给了最高档（5）**，原因是它用另一种方式回避了语义散落：不生成口径，只填参数。其余六个维度（九个维度减去这句话点名的灵活性、语义统一、工程复杂度三个）都是这句话的投影。把它拆成九个整数之后，投影反而盖住了原话。

问题出在方向性上。用 5 分标一个方案「工程复杂度」高，到底是在说它差，还是在说它贵？同一列在两个场景里的读法相反：一个只有 5 个 API 的团队，上平台化的复杂度是纯浪费；一个有 300 个 API、30 个调用方、还要按部门计费的团队，不上平台化的复杂度是纯负债【经验】。**打分表把「取决于规模」的判断伪装成了「与规模无关」的判断。**

第二个问题是把不同层的东西排成一行。直接查 DB、数据集市场、数据 API 网关、OneService、联邦查询网关、Text-to-API 并不是六个竞争产品：**数据 API 网关是给已经存在的 API 加治理的**，它不生产语义；**联邦查询网关是给会写 SQL 的人提供受控入口的**，它不承诺口径；**OneService 是生产语义契约的**，它不管流量；**Text-to-API 是契约的填充方式**，它可以架在其中任何一层之上；**数据集市场是交付形态**，它甚至不是一条访问路径。把它们打分排序，会诱导读者去做「六选一」，而真实架构里它们通常是**分工与叠加**。真正的选型问题因此是：**在我的约束下，哪一层必须由我来建，哪一层可以不存在。**

第三个问题是门槛错位带来的顺序错误。这个主题里收益最容易被高估的恰恰是门槛最高的那一个：**Text-to-API 能不能用，取决于语义定义与指标定义的完备度，而不是模型版本**。在演示现场（一个干净的小 schema）成立，在没有指标定义的生产仓里不成立——模型会把「口径」当成一个可以自由发明的参数。所以「先上自然语言取数、后补定义」这个顺序，代价不是效果差，而是**错误的口径被记住并在组织里扩散**。

第四个问题是本主题特有的：**这些方案的失败模式不体现在性能上，而体现在责任归属上**。一个没有分层的服务层不会变慢，它只会让「这个数字是哪个口径、谁该为它负责」变得无法回答。因此下面的判据里，权重最高的不是性能，而是「口径归谁」。

还有一个反向的陷阱同样值得提前说清：**不要为了让判据好看而把「统一」本身当成目标**。把八种访问路径统一到一条，会同时统一掉它们的适用性——一次性排查、跨源探索、对外交付这几类需求本来就不该走同一扇门。判据的作用是**给每一类需求指定它该走的那条路**，而不是把所有需求赶到一条路上。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 口径归谁 | 同一个指标的口径由谁定义、由谁改、改错谁负责 | 这是本主题唯一无法用工程手段补救的维度：语义没有主体，任何服务层都只是缓存了一个没人负责的数字 |
| 可变性从哪来 | 消费方的自由度是「选参数」「写 SQL」还是「自然语言」 | 自由度决定校验责任的落点：自由度越高，越需要有东西替调用方兜住口径越界 |
| 治理挂在哪一层 | 限流 / 鉴权 / 计量 / 审计是否有物理落点 | 没挂上物理落点的治理规则会在第一次性能压力下被绕过，且不留痕迹 |
| 契约的读者是谁 | 调用方是工程师、业务人员，还是 Agent | 机器不像人会自己换写法，它对契约的模糊、字段的缺失与错误的语义是零容忍的 |
| 定义维护的规模成本 | 资产数与变更频率共同决定维护工作量 | 单次口径变更的改动面随「同一指标的实现份数」线性增长，这是本主题的主导成本项 |
| 迁移与锁定的代价 | 离开它要改什么：调用方、口径、权限配置 | 服务层的锁定不在数据上而在调用方上：接得越顺、调用方越多，换的代价越大 |

这六条里有一条最先起作用：**口径归谁**。它不像「性能」那样可以事后优化——如果指标定义的所有者不明确，那么无论上不上服务层，组织里都会并存多个版本的真相；服务层只是把它从「多个报表对不上」变成「一个 API 的结果和报表对不上」，后者更难排查。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 直接查 DB | 最原始的访问路径 | 给一个只读账号直连库表，口径与权限都在 SQL 里 | 小团队、临时排查 | 无额外成本 |
| 表透出型自动 API | 结构即接口 | 由库表结构自动生成 REST / GraphQL 接口（PostgREST、Hasura、PostGraphile、DreamFactory、Directus、Supabase） | 内部工具、CRUD 型应用 | 开源，许可请按各项目当前 LICENSE 核验 |
| 数据集市场 | 资产交付形态，不是访问路径 | 以「数据包 / 数据集」为单位订购与交付，含授权与结算 | 跨部门数据交易、对外数据合作 | 商业产品与自建均有 |
| 数据 API 网关 | 流量治理层 | 对已有 API 做鉴权、限流、配额、路由与可观测（Kong、Apache APISIX、Tyk、Envoy） | 已有一批 API、需要统一出入口 | 开源 + 商业版 |
| OneService | 语义契约生产层 | 把指标 / 标签 / 维度 / 宽表封装为有定义、有版本、有 Owner 的 API | 数据中台场景（阿里 OneService 为典型） | 商业产品 + 自建 |
| 指标平台 / 语义层 | 定义层（可独立于服务层） | 指标定义集中一处、由定义驱动计算与查询（dbt Semantic Layer、Cube、MetricFlow、Airbnb Minerva） | 指标口径混乱的组织 | 开源 + 商业版 |
| 联邦查询网关 | 受控 SQL 入口 | 跨源查询（Trino、Presto），用权限与配额约束 SQL 的边界 | 分析师、临时跨域分析 | 开源 |
| Text-to-API | 契约的填充方式 | 自然语言 → 已定义 API 的参数（Snowflake Cortex Analyst、Databricks Genie、国内 BI + LLM 的 AI 取数形态） | 业务自助、AI 助手 | 厂商增值能力 |

这八项分三族，**同族内部差异小、跨族差异大**——先分族再选，能省掉一半比较：**透出族**（直接查 DB、表透出型自动 API、联邦查询网关）不生产语义，把「结构」或「SQL」直接交给调用方，差异只在入口的受控程度；**定义族**（OneService、指标平台 / 语义层）把口径变成一等公民，差异只在「定义服务化到什么程度」（只定义 vs 定义即服务）；**治理与交付族**（数据 API 网关、数据集市场、Text-to-API）不改语义也不改数据，改的是「谁来调用、怎么交付、怎么填参数」。

跨族比较通常没有意义：一个组织几乎一定同时需要定义族与治理族。**族内比较才有信息量**：直接查 DB 与表透出型争的是「要不要有接口层」，OneService 与指标平台争的是「定义层与执行层要不要合成一体」。后者是一个真实的架构分岔——把定义层独立出来，可以让同一个定义同时驱动 BI、服务 API 与模型训练取数；合成一体则换来实现简单、性能可控，代价是定义只能被这一条路径复用。

还有一条容易被忽略的分界：**表透出型自动 API 这个名称暗示了「零成本」，但它的成本只是被推迟了**。自动生成的接口让接入变得极快，于是接口数量与调用方数量会一起快速增长；等到需要回答「这次口径变更影响哪些接口」时，你会发现影响面由物理表结构决定，而表结构不表达口径。这一类方案的运维代价不在建设期，在变更期。

### 7.3 机制差异：为什么它们表现不同（核心节）

八个方案看起来是八个选项，实际回答的是同一个问题的四个侧面：**语义定义放在哪一层、可变性由谁提供、治理挂在哪个物理落点、契约的读者是人还是机器**。下面四个机制维度各展开一次，每个维度都给出「由此必然导出的性质」「支撑它的公开材料」与「什么条件下这条性质失效」。

#### 7.3.1 语义定义放在哪一层：从「无定义」到「定义即服务」

**机制是什么**：一条数据访问路径的价值取决于「调用方需要自带多少知识」。知识越少落在调用方身上，可复用性与一致性越高；这些知识不可能消失，只能被搬到系统里——搬到哪一层，就是这条路径的形态。

| 方案 | 口径写在哪 | 调用方必须自带的知识 |
| --- | --- | --- |
| 直接查 DB | 调用方的 SQL 里 | 表结构、JOIN 关系、过滤条件、字段含义 |
| 表透出型自动 API | 仍然在调用方的查询条件里 | 表结构（接口是结构的一一映射） |
| 联邦查询网关 | 调用方的 SQL 里 | 各源的表结构与跨源 JOIN 规则 |
| OneService | 服务契约里（指标 / 标签 / 宽表定义） | 只需知道「要哪个指标、按什么维度切」 |
| 指标平台 / 语义层 | 定义文件 / 定义表里，可被多条路径复用 | 指标名与维度名 |
| Text-to-API | 不改变口径所在层，只改变**谁来填参数** | 无（但这正是风险所在） |

**由此必然导出的性质**：因为口径在「透出族」里写在调用方的 SQL 中，所以**同一指标的实现份数等于消费方的数量**——每多一个消费方就多一份实现，这份实现不会自动跟随任何上游变更。这是一个结构性结论，与工具好坏无关。反之，因为「定义族」把口径收敛到了一处，所以**一次口径变更的改动面从 N 处降到 1 处**；代价是这次改动从「某个报表改了」升级为「一次需要评审、需要兼容期、需要通知全部调用方的契约变更」，而且一处出错的影响面也放大到全部调用方。这是同一条机制的两个方向：收敛消灭了重复劳动，同时也消灭了故障的隔离性。

这条性质也解释了为什么「表透出型自动 API」常被误认为已经解决了服务化问题：它确实消灭了「每个调用方自己写连接与鉴权」这部分重复劳动，但**结构到接口的一一映射意味着口径仍然散落在调用方**。判定方法很直接：看这个 API 的接口清单是否与物理表一一对应；如果表改了字段名接口就得改，说明口径不在接口里，只在调用方的查询条件里。

由此还导出本主题最关键的一条推论：**服务层的可治理性上限，等于其定义的完备度**。定义只写了「指标名 + 描述」时，服务层能做的只有路由与限流；定义里有可执行表达式、维度约束、粒度与 Owner 时，它才能做口径校验、影响面分析与按语义计量。所以「先补定义、再谈服务」不是流程偏好，而是能力边界。

**公开证据**：这条分界的实践形态可参照阿里数据中台的方法论——OneData / OneService / OneID 在数据中台阶段被系统化提出，其中 OneService 的定位是「数据资产服务化」，即把口径收敛进服务契约；本节不重复年份，该路线的时间线与实践材料以本章 §6 为准（§6.1 记其起止年份），要核验可按「阿里 OneData OneService 数据中台」等关键词自行检索。这批材料在本章 §5.4 里被记为「实践方自述」——书里给到的只有公司名与年份区间，没有文档标题与链接，读者按它定位不到任何一份可读材料，因此本节沿用该口径、不按【公开】档引用。开源侧的定义层方案包括 dbt Semantic Layer、Cube、MetricFlow 与 Airbnb 开源的 Minerva【公开】（来源：dbt Labs 官方文档「About the dbt Semantic Layer」与「MetricFlow」，docs.getdbt.com；Cube 官方文档中 measures / dimensions / filters 的设计说明，docs.cube.dev；这些项目的能力、许可与版本以各自官方文档与仓库当前版本为准）。

**失效条件**：当「同一指标的不同口径是业务上真实需要」时（例如大促期间与平常的 GMV 定义确实不同），强行收敛成一个定义会把差异挤到调用方的过滤条件里，反而更难发现。此时正确做法不是取消定义层，而是在定义层显式支持**带命名与所有者的多个变体**，让差异可见。

#### 7.3.2 可变性从谁提供：选参、受控 SQL、自然语言

**机制是什么**：调用方总要能表达「我要哪一段」。区别在于这段表达被限制在什么自由度内，以及**越界的责任落在谁身上**。

**它在各候选中的实现差异**：

- **直接查 DB / 联邦查询网关**：自由度最高（完整 SQL），责任几乎全在调用方。联邦网关能做的是在外围加权限、配额与资源组。
- **表透出型 API**：自由度中（过滤、排序、分页、部分联表），越界表现为「能查到本不该看到的数据」，因此权限必须落在行级 / 列级规则上。
- **OneService / 指标平台**：自由度低（指标 + 维度 + 过滤 + 时间范围的组合）。超出组合范围的请求**在语义上不可表达**，这是它的核心特征。
- **Text-to-API**：自由度看似最高（自然语言），实际被语义层限死——它能填的只有已定义的参数。

**由此必然导出的性质**：因为 OneService 这类方案的参数空间本身就是白名单，所以**「越权取数」与「口径走样」在语义上不可表达**，不需要靠事后审计去发现；代价是它回答不了「组合之外的问题」，这类需求必须另开一条受控 SQL 路径，否则业务方会绕到别的系统里自建。反过来，因为联邦查询网关的自由度是完整的 SQL，所以它能回答任何问题；代价是它**无法承诺口径**——同一句 SQL 的两次调用结果可以完全合理却不一致，而且没有任何机制会告诉你这件事。

自由度还有一个容易被忽略的后果：**它决定了校验层必须放在哪里**。自由度低的方案里，校验发生在「参数是否在定义内」这一步，成本低且可自动化；自由度高的方案里，校验只能发生在「结果是否符合预期」这一步，而这需要有人知道预期是什么。这也是自然语言取数真正的难点所在——它不是把问题翻译成 API 调用，而是**把「不知道预期」这件事暴露了出来**。

**公开证据**：这条分界有两类可核验的公开形态。其一是**白名单式参数空间**：dbt Semantic Layer（含其指标定义引擎 MetricFlow）与 Cube 对外暴露的查询接口，入参被限定为「指标 + 维度 + 过滤 + 时间范围」这几类，超出范围在接口层即不可表达【公开】（来源：dbt Labs 官方文档「About the dbt Semantic Layer」与「MetricFlow」中查询接口的入参定义，docs.getdbt.com；Cube 官方文档中查询 API 的 measures / dimensions / filters 设计说明，docs.cube.dev；版本与命名以各项目当前文档为准）。其二是**受控 SQL 的兜底手段**：Trino 的资源组文档按用户组 / 队列约束并发与内存，并提供按执行时间或扫描量终止单条查询的查询级配置，即「完整 SQL 自由度必须由资源约束兜住」这条原则的工程落点【公开】（来源：Trino 官方文档 trino.io/docs 中资源组（Resource groups）与查询级资源限制（Query resource limits）两节；该项目 2020 年由 PrestoSQL 更名而来，配置项以当前版本文档为准）。生产形态可参照本章 §6.2 的字节案例（2020–2024）：服务只引用已定义的指标，维度越界在配置层不可表达；该案例同属本章 §5.4 记的「实践方自述」（只有公司名与年份区间、没有文档标题与链接），故此处按实践线索引用，不按【公开】档引用。判定方法：对白名单式接口发一条「组合之外」的请求，看它返回的是明确的「不可表达」，还是被静默降级成一次近似查询；对受控 SQL 通道，看能否对单条查询设出扫描量或执行时间的上限。

**失效条件**：当业务方的问题里有相当比例落在「已定义组合」之外时，白名单式方案会持续被绕开，最终退化成「名义上的统一入口 + 事实上到处直连」。判断这件事不需要调研，看直连库表的账号数是否在增长即可。

#### 7.3.3 治理挂在哪一层：有没有物理落点

**机制是什么**：限流、鉴权、计量、审计这些治理动作要生效，必须挂在一个**每个请求都会经过的物理落点**上。挂在哪一层，决定了你能治理什么、不能治理什么。

**它在各候选中的实现差异**：

| 方案 | 治理落点 | 能治什么 | 治不了什么 |
| --- | --- | --- | --- |
| 直接查 DB | 数据库账号 + 网络策略 | 库 / 表级访问 | 按调用方计量、按业务限流 |
| 数据 API 网关 | API 入口 | 鉴权、限流、配额、路由、可观测 | 请求背后的数据量（看不到语义） |
| OneService 服务层 | 语义入口 | 上述各项 + 按指标 / 维度的口径与范围约束 | 服务层之外的直连路径 |
| 联邦查询网关 | 查询引擎 | SQL 级资源约束、权限、资源组 | 口径一致性 |
| 数据集市场 | 交付流程 | 授权与结算 | 出厂副本之后的任何变更 |

**由此必然导出的性质**：因为数据 API 网关看不到语义，所以**它只能限「调用次数」，不能限「资源消耗」**——一次调用扫描 1 TB 与扫描 1 MB 在它眼里是同一条请求。因为服务层看得见语义，所以它能按「指标 × 维度组合 × 时间范围」设配额与成本预估；代价是它必须持有完整的指标与维度元数据，元数据不全时配额规则会失效得无声无息。这条差别在事后很难补：网关的配额配置已经存在，你要改的是服务层的语义信息，而那意味着定义要重做。

这条性质也解释了「为什么治理不能只在最外层做」：最外层的落点离请求最近，所以它对调用频次最敏感、对业务含义最迟钝。一个只有网关的系统，会在被一次大查询打满之后才发现——按次数配的额度对「贵查询」和「便宜查询」一视同仁。补上这一层的方式不是把网关做得更聪明，而是让服务层在转发前把「这条请求的工作量量级」交给网关。

**公开证据**：这条性质可在三类公开材料里对照。**限流只认请求、不认数据量**：Kong 与 Apache APISIX 的限流插件（rate-limiting / limit-count 一类）的限流维度是「单位时间内的请求数」，配置项里没有「本次调用扫描了多少数据」这一维度【公开】（来源：Kong 官方插件文档 developer.konghq.com 的 Rate Limiting 插件页；Apache APISIX 官方插件文档 apisix.apache.org 的 limit-count 插件页；配置项随版本演进，以各项目当前文档为准）。**资源消耗的约束点在引擎侧**：Trino 的资源组按队列 / 用户组限制并发与内存，并可对单条查询设扫描量或执行时间上限，说明「按消耗治理」必须挂到看得见执行的引擎，而不是挂在入口网关【公开】（来源：Trino 官方文档 trino.io/docs 中资源组与查询级资源限制章节；该项目 2020 年由 PrestoSQL 更名而来，配置项以当前版本文档为准）。**按语义计量**：阿里数据中台的方法论把「服务注册（口径 / Owner / SLA / 调用方）」列为服务化的必要条件，计量与授权因此落在语义入口而非网络入口——该材料同属本章 §5.4 记的「实践方自述」，故此处只记形态、不按【公开】档引用。判定方法只问两件事——你的限流规则能否区分「一次扫 1 TB 的调用」与「一次扫 1 MB 的调用」；你的指标定义指向的表被改名后，治理侧会不会给出任何告警（若照常放行且无人察觉，说明它校验的是定义文本而不是实际执行链路）。

**失效条件**：当服务层的元数据与实际表结构脱节时（指标定义指向已经被重命名或替换的表），治理规则会照常放行，因为它校验的是定义而不是实际执行。这类失效不报错，只能靠「定义与实际执行链路的一致性检查」发现。

#### 7.3.4 契约的读者是谁：人还是机器

**机制是什么**：同一个 API，工程师读文档、业务人员看界面、Agent 直接读 schema 与错误码。读者的容错能力完全不同，而**契约的完备度要求由容错能力最弱的那个读者决定**。

**它在各候选中的实现差异**：

- **直接查 DB**：读者几乎只有工程师。契约不完备时，人会问、会试、会自己绕。
- **表透出型 API / 联邦查询网关**：读者是工程师与分析工具。参数错误会报语法或类型错误，反馈是明确的。
- **OneService**：读者包括业务系统与 Agent。业务系统要求版本稳定，Agent 要求错误可结构化处理。
- **Text-to-API**：模型是中间读者。它不会问人，而会把「参数不存在」理解成「换一种说法再试」。

**由此必然导出的性质**：因为 Agent 不像人会自己换写法，所以**它会把契约的模糊放大成调用量的浪费**：字段缺失时人会说「这个接口查不了」，模型会连续重试并生成看似合理的替代参数——**因为没有结构化的拒绝语义，模型只能靠猜**。这条性质推出一个很具体的工程要求：把 OneService 开放给机器之前，先补齐四件事——① 每个指标的机器可读定义；② 明确的参数边界与枚举值；③ 结构化错误码（区分「不存在」「无权限」「参数越界」，而不是一律返回空集）；④ 按调用方身份的配额与可归因的调用记录。这四件都属于在 AI 之前就该存在的治理能力，AI 只是提高了它们的下限。

**公开证据**：把数据服务注册为模型工具这一形态，在多家的工具调用规范中都有对应实现，MCP 协议规格自 2024 年公开、按修订日期版本化、有多家独立实现【公开】（来源：MCP 项目公开规格 modelcontextprotocol.io，规格本身带修订日期，具体版本以该站点当前的修订号为准）。但**本节不对任何产品是否支持某项具体能力下断言**——判定方法是查三件事：该能力在哪个版本进入正式可用（而不是预览）、它对外暴露的语义写在文档哪一节、有没有第三方（非厂商）的生产案例。本章 §5 用同一套判据做过分级。

**失效条件**：当组织里还没有「机器可读的指标定义」时，把自然语言取数接在有定义的范围之外，得到的是「能演示、难审计」的系统。此时正确的顺序是先补定义、再开自然语言入口，而不是先调模型。

四个维度可以压成一句话的对照：

| 机制维度 | 它决定的问题 | 判据落在哪 |
| --- | --- | --- |
| 语义定义放在哪一层 | 改动面是 N 处还是 1 处 | 同一指标的实现份数；表改名是否需要改接口 |
| 可变性从谁提供 | 校验责任落在谁身上 | 参数是否只能取自白名单；超出范围时返回什么 |
| 治理挂在哪一层 | 能否按语义而非按路径治理 | 治理规则能否看到「这次调用要扫多少数据」 |
| 契约的读者是谁 | 契约完备度的下限 | 是否有机器可读定义与结构化错误码 |

本节的主结论是：**服务层的强弱不由它暴露了多少接口决定，而由它能否回答「这个数字的口径是什么、谁为它负责」决定。**

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本函数里，**调用量不是主导项**——主导项是**定义与契约的维护成本**，它在定义族上最明显（透出族对应的一项是消费方数量，治理族对应的是运维量）：

```text
总成本 ≈ 一次性建设（定义层 + 服务层 + 网关）
       + f(资产数 × 变更频率)      ← 定义维护成本（主导项）
       + g(调用量 × 单次扫描量)     ← 算力与缓存成本
       + h(契约数 × 调用方数)       ← 版本与兼容成本
       + 组织成本（口径所有权与评审）
```

各方案的主导项：

| 方案 | 主导成本项 | 隐性成本 | 随什么增长 |
| --- | --- | --- | --- |
| 直接查 DB | 无（近乎零建设） | 口径多份实现的返工 + 无法计量 | 消费方数量 |
| 表透出型自动 API | 一次性接入 | 权限规则与结构耦合，改表即改接口 | 表数量与表结构变更频率 |
| 数据集市场 | 交付与授权流程 | 数据出厂后无法回收，口径变更追不上 | 数据集数量与合规要求 |
| 数据 API 网关 | 网关运维 | 看不到语义，只能限次数不能限消耗 | API 数量与调用量 |
| OneService | 定义层建设 + 定义维护 | 元数据与实现脱节时治理规则静默失效 | 核心指标数 × 口径变更频率 |
| 指标平台 / 语义层 | 定义维护 | 定义与物理实现的一致性 | 指标数 × 变更频率 |
| 联邦查询网关 | 引擎与资源 | 无法承诺口径，查询成本不可预测 | 并发查询数与数据源数 |
| Text-to-API | 校验层建设 + 评测 | 口径越界与调用浪费 | 提问分布与定义覆盖度 |

几个量级上的特征（都写成成本函数里的哪一项主导，不给无来源的单价）：

- **透出族的成本随「消费方数量」增长**：因为实现的份数等于消费方数量，这一项是线性且没有规模效应的。它便宜在启动，贵在长期。
- **定义族的成本随「资产数 × 变更频率」增长**：这是本主题的主导项，也是唯一有规模效应的一项——定义收敛后，新增一个消费方不增加维护成本【经验】。
- **治理族的成本基本是固定项**：网关的运维量与调用量相关，但与「有多少个业务语义」无关。
- **Text-to-API 的成本随「问题分布与定义覆盖度的差」增长**：覆盖度以外的问题越多，校验与人工兜底的成本越高。

两个【推算】示例。**其一，改动面**：设某个 GMV 口径在 6 个下游里各有实现（BI 报表、两套应用接口、两处特征工程、一个对外数据包）。口径变更时需改动并验证 6 处（推导链：改动面 = 实现份数 = 消费方数量）；收敛到定义层后改动面降到 1 处，但这一处变更需要一次评审、一段兼容期与一次全量通知，因此**改动面下降与单次变更成本上升同时发生**——它们不是可选项之间的取舍，而是同一条机制的两个后果。**其二，缓存与物化**：设某指标 API 日均 10 万次调用（1e5）、每次直落明细扫描约 1 GB，则日扫描量 ≈ 1e5 × 1 GB = 1e5 GB ≈ 100 TB【推算】（推导链：扫描量 = 调用次数 × 单次扫描量，未计缓存命中与列剪裁的削减）；若这些调用命中物化结果（结果集在 GB 量级以内），扫描量可降到 GB 级。这两个数字的量级差异说明：**服务层真正省下的不是「接口开发」，而是把重复的明细扫描换成一次物化**——缓存命中率因此是这套架构最值得监控的一个比率。

成本函数还解释了本主题一个常见的误判：**把「接口数量」当成服务化成效的指标**。接口数量的增长既不明显降低定义维护成本（因为定义的份数没变），也不明显提高缓存命中率（因为调用是分散的），却会稳定地把「版本与兼容成本」推高。真正值得追踪的是三个比率：定义覆盖率（有多少消费走的是有定义的路径）、缓存命中率、以及口径变更的平均影响面。

### 7.5 决策树（每个分支都要有阈值依据）

```text
① 消费方是谁？
   ├─ 只有内部工程师、且是一次性临时需求 → 直接查 DB（受限只读账号 + 审计）
   └─ 有业务方 / 应用 / Agent 持续消费 → 继续
        │
② 消费对象是「有统一定义的指标 / 标签 / 宽表」，还是「任意明细 / 跨源数据」？
   ├─ 有统一定义 → OneService（或独立语义层 + 服务层）★
   └─ 任意明细 / 跨源 → 继续
        │
③ 业务方会不会写 SQL？
   ├─ 会 → 联邦查询网关（受控 SQL：权限 + 配额 + 资源组）
   └─ 不会 → 继续
        │
④ 需要的是「一组稳定的数据对象」，还是「随前端页面变化的接口形态」？
   ├─ 稳定对象 + 需要配额与计量 → 数据 API 网关（对已服务化的 API 做治理）
   └─ 随前端变化 → 表透出型自动 API / GraphQL（并接受结构耦合）
        │
⑤ 已定义指标是否覆盖这个问题？
   ├─ 覆盖 → Text-to-API（模型只填参数，不生成口径）
   └─ 不覆盖 → 先补定义；在此之前上自然语言取数＝让模型发明口径
        │
⑥ 交付形态是「一次性把数据包给出去」，还是「持续访问」？
   ├─ 一次性交付 → 数据集市场（授权 + 结算 + 出厂后不可回收）
   └─ 持续访问 → 回到 ②
```

树上六个判断节点读的都是**可核验的事实**（谁能自救、定义存不存在、调用方会不会写 SQL、接口是否跟随表结构、定义是否覆盖、要不要副本），没有一个是成熟度标签。

**阈值依据**：

- **① 消费方是谁**：来自「契约的读者是谁」这一判据。依据是容错能力的差别：工程师能自己发现并绕开契约缺陷，业务方与 Agent 不能。因此分界不在数据敏感度，而在**读者能否自救**——能自救时可以只给受限只读账号，不能自救时必须给契约。
- **② 是否有统一定义**：来自「口径归谁」这一判据。依据是机制：定义族的前提是「定义存在且有人负责」；定义不存在时，服务层只是把 SQL 挪了一个位置，语义统一度不会提升一分。判定方法：能否为当次要服务的数据列出定义清单并指明每个定义的所有者。
- **③ 会不会写 SQL**：来自「可变性从谁提供」这一判据。依据是责任落点：会写 SQL 的调用方承担口径责任，此时正确做法是给一条受控通道并加资源约束，而不是把它硬塞进白名单式 API（硬塞的结果是对方绕开系统去直连）。
- **④ 稳定对象 vs 随前端变化**：来自成本函数里「契约数 × 调用方数」这一项。依据是版本成本：接口数量与变动频率越高，版本与兼容成本越高。稳定对象可以走语义契约并配网关治理；随前端变化的接口形态则应接受结构耦合，并放弃「它也能当数据资产」的期待。
- **⑤ 定义覆盖度**：来自 §7.3.4 的机制与 Text-to-API 的成本项。依据是判定而非比例：逐个问题检查「它映射到的指标是否已在定义清单中」。覆盖度不足时，成本从「调用」转移到「人工兜底与口径纠纷」，且这部分成本不会出现在任何仪表盘上。
- **⑥ 交付形态**：来自本主题的机制边界——数据集市场不是访问路径。依据是「数据一旦出厂即不可回收」：这类交付必须一次性把口径、授权与版本写进交付物，因为之后你无法再通过接口去修正调用方手里的副本。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 内部工程师的临时排查 | 直接查 DB（受限只读账号） | 联邦查询网关 | 不上服务层：一次性需求，契约成本收不回来 |
| 有统一定义的指标 / 标签消费 | OneService（或独立语义层 + 服务层） | 指标平台 + 网关 | 不用表透出：结构即接口，口径仍散落在调用方 |
| 跨源明细分析、调用方会写 SQL | 联邦查询网关 | 数仓内预汇总后再服务化 | 不用白名单式 API：组合外的问题会被绕开 |
| 已有大量 API、需要统一出入口 | 数据 API 网关 | 服务网格 | 不指望网关解决口径：它看不到数据语义 |
| 前端驱动的多样接口形态 | 表透出型自动 API / GraphQL | 按页面定制聚合层 | 不用它承载数据资产：结构耦合会让口径无法收敛 |
| 业务方自助取数、不会写 SQL | Text-to-API（限定在已定义范围内） | 预置看板 + 参数化 | 不在定义之外开自然语言入口：等于让模型发明口径 |
| 对外数据合作、一次性交付数据包 | 数据集市场 | 受控 API + 计量 | 不用 API 交付：对端要的是副本，不是访问权 |
| 面向 Agent 的取数 | OneService + 网关（定义 + 鉴权 + 配额） | 单独为 Agent 开一个受控入口 | 不直接暴露联邦网关：Agent 不会自己控制查询成本 |
| 口径混乱、多个报表对不上 | 指标平台 / 语义层（先解决定义） | 人工对账 | 不先上服务层：定义没收敛时，服务层只是多一个版本的数字 |

这张矩阵的使用顺序应该**从下往上读**：先确认口径有没有主体，再确认契约的读者是谁，最后才看接口形态。从上往下读，会得到一个「接口很漂亮、数字对不上」的系统。

五条常见组合，重点是**职责边界与运维代价**：

1. **OneService + 数据 API 网关**：OneService 生产语义契约（指标 / 标签 / 宽表的定义与版本），网关负责鉴权、限流、配额、路由与可观测。边界——网关不解释语义，因此「按数据消耗限流」这类规则必须由服务层提供用量信息。运维代价——两条链路都要有 SLO，且排障时要先判断问题在语义层还是流量层。
2. **OneService + 数据目录**：服务层的每个 API 注册到目录，成为可发现、可检索、带 Owner 与血缘的资产。边界——目录负责「有什么、归谁、怎么用」，服务层负责「能不能调、调了算什么」。运维代价——API 的变更必须同步更新目录条目，否则目录会退化成一份过期的接口清单。
3. **OneService + 指标平台**：指标平台是 OneService 的核心组件（定义、计算、服务三段中的前两段）。边界——平台管口径与计算，服务层管契约与暴露；把两者合成一个系统是常见的简化，代价是定义无法被 BI 与模型训练等其他路径复用。运维代价——定义变更要同时触发计算任务与契约版本两个动作。
4. **OneService + RAG**：结构化数据（指标、标签、宽表）走服务层，文档与半结构化内容走检索层，由路由决定走哪条。边界——谁来决定「这个问题该走哪条」目前没有通行做法，通常靠问题分类或显式入口。运维代价——两条链路的口径与权限必须分别可审计，否则会出现「同一问题两种答案」。
5. **OneService + Agent**：把服务层的 API 注册为 Agent 的工具（含机器可读描述、参数 schema 与结构化错误），并给 Agent 一个独立身份与配额。边界——Agent 只填参数，不定义口径；「这条调用算谁的账」必须在服务层可归因。运维代价——需要为机器调用单独做配额与熔断，因为模型的重试行为会把一次错误放大成一批调用。

五条组合共同的前提是：**先有定义与所有者，再谈暴露方式**。组合里任何一件的职责边界只要留在某个人的记忆里，规模一旦扩大就会退化成「接口有一堆、口径说不清」。

### 7.7 选错的代价与迁移成本

**反模式一：表透出（把库表直接暴露成 API）。** 症状——接口清单与物理表一一对应，表改字段名接口就得改；调用方在使用接口时仍然要理解 JOIN 与过滤条件。后果——建设成本看起来很低，但**口径仍然散落在每一个调用方**，服务层没有带来任何语义收敛；等到需要回答「这个数字的口径是什么」时，答案取决于问的是谁写的查询。正确做法——接口的粒度按业务对象（指标 / 标签 / 宽表）设计，而不是按表设计；判定方法就是那条：表结构变更是否需要改接口。

**反模式二：先上自然语言取数，后补指标定义。** 症状——业务方在演示环境里用自然语言直接查到数，上线后开始出现「同一个问题两个答案」。后果——**错误口径会被记住并扩散**，且因为入口看起来是「自动的」，用户会默认它比报表更权威；纠正成本远高于一开始就不开这个入口。正确做法——先限定在已定义指标的范围内开放，并保证每个指标都能回答「口径是谁定的」；范围外的问题返回明确的「未定义」，而不是让模型猜。

**反模式三：把语义层做成一张字符串表。** 症状——指标定义只写「名称 + 描述 + 口径说明」，没有可执行的表达式、没有维度约束、没有所有者与版本。后果——定义无法驱动计算，只能作为文档存在，于是每个消费路径仍然各自实现一遍（改动面回到 N 处）。正确做法——定义必须包含可执行的表达式与维度 / 粒度约束，并且有 Owner、有版本、有变更流程。

**反模式四：无版本管理与无配额。** 症状——API 的 schema 改了就改，调用方在生产上才发现；没有调用配额，一次大查询把后端打满。后果——**服务层从「可治理的出口」变成「不可预测的风险源」**，而它的治理价值恰恰是它存在的理由。正确做法——契约版本化 + 兼容期；按调用方身份设配额，并对高消耗查询单独限速。

**反模式五：把数据集市场当作访问路径。** 症状——用「数据包」的方式满足所有取数需求，对端拿到副本后自行加工，口径与授权都脱离平台。后果——数据出厂后无法回收：口径变了追不上，权限撤销了也撤不回，出问题时无法定位是哪一个副本。正确做法——先判断需要的是「访问权」还是「副本」：需要实时口径的走服务层，确实需要交付副本的才走市场，并把口径与授权写进交付物。

这五条反模式有一个共同点：**它们的代价都不在接口层，而在「口径」这一层**——接口可以重写，错误的口径一旦被业务记住并写进汇报，纠正就不只是工程工作。

按后果归类，它们的暴露方式也不一样：

| 反模式 | 谁先发现 | 典型暴露形态 |
| --- | --- | --- |
| 表透出 | 下游调用方 | 表结构变更引发一串接口改动 |
| 先上自然语言取数 | 财务 / 管理层 | 同一问题两个答案，且都「看起来对」 |
| 语义层只有字符串 | 维护者 | 口径变更时找不到全部实现 |
| 无版本与无配额 | 值班工程师 | 上线后调用方崩溃，或后端被单次查询打满 |
| 市场当访问路径 | 合规 / 审计 | 副本已扩散，权限撤销无法生效 |

换成另一条路径要动什么（只标工作量量级）：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 直接查 DB → 服务层 | 无 | **高**：全部查询改写成 API 调用 | **中**：加服务层与网关 | **中**：从写 SQL 转为用定义 |
| 表透出 → OneService | 无 | **高**：接口按业务对象重新设计，调用方全部改 | **中** | **中高**：要理解指标 / 维度建模 |
| 散落 API → OneService | 无 | **中**：调用方改指向统一入口 | **中**：建设定义层与 API 目录 | **中高**：口径评审成为常态流程 |
| 联邦查询为主 → 定义驱动 | 无 | **中高**：把高频 SQL 沉淀为定义 | **中**：加指标平台 | **高**：从「自己能查」转为「先定义再查」 |
| 人工报表 → Text-to-API | 无 | 无 | **中高**：校验层、评测集、配额与归因 | **中**：需要维护定义覆盖度 |

表里可以看到一个共同点：**这些迁移都不动数据，代价集中在「查询改写」与「口径流程」两项上**——也就是说，它的成本主要落在业务方的习惯上，而不是落在工程上。这解释了为什么服务化改造经常在技术上完成、在组织上失败。也正因如此，成功率最高的做法通常不是「新建一个平台再号召大家来用」，而是**找一个高频、口径争议最大的指标先收敛**，让「改动面从 N 处降到 1 处」这件事被看见，再逐步扩面。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 只有内部工程师临时取数 | 直接查 DB（受限只读账号） | 契约与治理的成本在这一次性需求上收不回来 |
| 指标口径混乱、多个报表对不上 | 指标平台 / 语义层（先定口径） | 口径没有主体时，服务层只是多一个版本的数字 |
| 有统一定义的指标 / 标签要服务化 | OneService（+ 网关） | 参数空间是白名单，越权与口径走样在语义上不可表达 |
| 跨源明细分析、调用方会写 SQL | 联邦查询网关 | 完整 SQL 自由度必须由资源约束与权限兜底，而不是白名单 |
| 已有 API 要统一出入口与计量 | 数据 API 网关 | 治理规则必须挂在每个请求都经过的物理落点上 |
| 前端驱动的多样接口 | 表透出型自动 API / GraphQL | 接受结构耦合，放弃它承载数据资产的期待 |
| 业务方自助、不写 SQL | Text-to-API（限已定义范围） | 模型只应填参数，不应发明口径 |
| 对外一次性交付数据包 | 数据集市场 | 副本出厂后不可回收，口径与授权必须写进交付物 |
| 面向 Agent 的取数 | OneService + 收口 + 配额 | 机器零容忍模糊契约，会把契约漏洞放大成调用量 |

> 本节小结：本主题的对比中**唯一真正起决定作用的那条差异**是「口径由谁定义、定义放在哪一层」——它决定了改动面是随消费方线性增长的 N 处，还是收敛后的一处，也决定了治理规则能不能建立在语义上（而不是只建立在调用路径上）。其余所有差别（网关、市场、Text-to-API、产品形态）都能归因到这条差异上，也都是它的推论。
>
> 值得单独记住的一句：**服务层的价值不在于把数据变成接口，而在于让「这个数字的口径是什么」有一个可指认的答案。** 接口做得再漂亮，如果口径仍散落在每个调用方的查询条件里，那它只是给隐式约定加了一层美观的包装。
>
> 落到动作上，顺序只有三步：**先把定义与所有者补齐**（让口径有主体），**再把服务契约与治理挂上去**（让出口可计量、可审计），**最后才谈自然语言与 Agent**（让填参数这件事交给机器）。跳过第一步直接做第三步，得到的是「演示很好看、审计说不清」的系统。
>
> 💡 **思考锚点**：拿你口径争议最大的那个指标，按 §7.7 的迁移表量一次：从「直接查 DB」改成服务化后，调用方要改几处、改动面有没有从 N 处收到 1 处？若没收成 1 处，按本节小结的三步顺序，你缺的是第一步的「定义与所有者」，还是第二步的「契约与治理」？
