## 4. 工程实现

§3 回答的是「语义冻在哪一刻、六个模式各自被什么约束逼出来」；本节回答的是**同一条链路上更靠后的问题**：这八个 Step 谁先谁后、每一步做完手上应该多出什么、怎么在做的过程中就知道自己偏了、以及**存量那批已经在跑的接口怎么收拾**。§4.1 到 §4.3 面向从零搭建的团队（顺序与判据在这里），§4.4 面向在既有资产上改造的团队（先读它再回来看 §4.1）；§4.5 的模板与 §4.9 的自检清单两类读者都用得上——前者交付前照抄与自查，后者用来划存量与新增的边界；§4.10 收束全节。

文中的具体数值一律是**示意值**，不指向任何真实系统；即便如此，每一个数值仍标出档位——【公开】带来源与年份，【推算】写出推导链，【经验】给区间并写明它随什么变。

### 4.1 落地步骤

**Step 1：数据资产盘点（1–2 周【经验】，随资产数量变）**

1. 盘点四类资产：**表 / 指标 / 标签 / 维度**，逐个记 Owner、最近调用时间、调用方数量。
2. 按「访问频率 × 业务重要性」排出服务化优先级；把「有 Owner 但零调用」的资产单独列一栏。
3. 输出按优先级排序的清单，而不是按主题域分类的清单。

- **产物**：数据资产清单 + 服务化优先级（含零调用资产单列）。
- **判据**：抽 10 个已被消费的资产，逐个看有没有 Owner 与最近调用记录；没有调用记录的排到最后——它们通常不是没人要，而是没人找得到。
- **为什么必须第一步**：Step 2 的设计要落在这份优先级上，§6 的复用率也以它作基线。跳过盘点直接建服务，得到的是「按需求单建接口」，而那正是 §6 四个案例共同踩过的第一坑。

**Step 2：服务化设计（2–4 周【经验】，随要收窄的指标 / 维度白名单规模与调用方类型数量变）**

1. 选 API 模式：**指标 / 标签 / 宽表 / 联邦查询 / GraphQL / AI 增强**，与 [§3.2](06-one-service-section-3-sec3.md) 的六个模式一一对应（Text-to-API 是 AI 增强型的入口，见 Step 8，不是第七个模式）。选哪个由「语义冻结点」与调用方类型决定。
2. 设计 API Schema（REST / GraphQL），把参数空间写成白名单（指标 × 维度 × 过滤 × 时间范围）。
3. 设计权限模型（行 / 列 / 指标级）与版本管理策略（不兼容变更走新版本 + 兼容期）。

- **产物**：API 设计文档，含参数白名单、权限矩阵、版本策略。
- **判据**：接口路径与返回字段里**有没有出现物理表名或物理列名**——这是 §3.5「表透出」的判据，出现即说明语义层还不存在；再检查一次参数空间，超出白名单的请求是「被拒绝」还是「被尽力执行」。
- **为什么必须这一步、且必须在建平台之前**：§3.1 的四条约束里第一条是「语义冻结时刻」——参数空间一旦被调用方用起来，就再也不能自由收窄。把它放在 Step 3 之后，等于让定义层去适配已经发出去的接口。

**Step 3：指标 / 标签平台搭建（1–3 个月【经验】，随要收编的存量指标 / 标签数量与未决口径争议数变）**

1. 建指标平台（详见 [10-metric-platform](../10-metric-platform/10-metric-platform.md)）：指标定义表带版本、Owner、表达式、基础表、维度白名单与 SLA。
2. 建标签平台（用户 / 商品 / 内容画像）：正查走 KV 点查，反查（按标签圈人）走倒排或位图，两套结构分别建索引。
3. 统一指标 / 标签的定义、口径与 Owner，口径责任人具体到人而不是团队。

- **产物**：统一指标 / 标签库（定义表），可被程序读取。
- **判据**：抽 3 个指标各改一次口径，看它是**产生新版本还是原地覆盖**；再看每个指标的 Owner 能不能写成一个具体的人。两条都不满足时，Step 4 建出来的只会是一批各自内嵌 SQL 的接口。
- **为什么必须排在 API 平台之前**：§6.5 记的落地方向是「服务由定义生成（引用指标 / 公共层），不手写 SQL」——定义层不存在时，口径的份数等于接口的份数，日后收敛的代价按调用方数量计（§3.5「口径不统一」的机制）。

**Step 4：API 平台搭建（1–2 个月【经验】，随要收敛的取数路径数量与既有鉴权 / 计量体系的复杂度变）**

1. 选 API 网关（详见 [07-data-api-gateway](../07-data-api-gateway/07-data-api-gateway.md)）：鉴权、限流、配额、路由、计量、脱敏统一在这里生效。
2. 选 API 框架（FastAPI / Spring Boot / Go 一类），把契约生成到 OpenAPI，让接口可被机器读出来。
3. 打通认证 / 鉴权 / 限流 / 监控四件事，并给 Agent 预留独立身份与配额。

- **产物**：API 平台，即所有取数的**唯一出口**，治理规则挂在它上面。
- **判据**：把现存所有取数路径枚举一遍——导出任务、分析师直连、Agent 拿到的库凭证、离线脚本——看还剩几条不经过出口。这个数字就是治理的实际覆盖率。
- **为什么必须紧接着 Step 3**：§3.1 的第四约束写明，权限、计量、血缘、配额这四件事全部建立在「取数走同一个点」之上；出口一旦不止一条，服务层上的全部工作按直连路径的数量被稀释。

**Step 5：后端数据源对接（2–6 周【经验】，随数据源数量变）**

1. 对接数仓与湖仓（MySQL / Hive / ClickHouse / Iceberg），按访问模式选择存储与索引形态：点查走 KV，圈人走倒排 / 位图，聚合走预聚合。
2. 对接实时数据（Flink / Kafka Streams），并把批链路作为对账的裁决方。
3. 做查询优化（索引、物化、缓存），同时对**无范围条件的查询强制拒绝**，不降级执行。

- **产物**：可查询的数据后端，附一份「引擎 × 下推能力」的实测记录。
- **判据**：同一条查询在两个源上各跑一次，记录差异来源（谓词下推 / 投影下推 / 分片）；再提交一次不带时间或分区条件的查询，看它是否被拒绝。
- **为什么排在网关之后**：每接一个源，都要用同一个网关口径去验证鉴权、限流与计量是否照常生效。先接源后补网关，中间那段过渡期必然出现直连。

**Step 6：元数据注册（1–2 个月，与 Step 4 / 5 并行【经验】，随服务数量与注册项采集的自动化程度变）**

1. 把所有服务注册到数据目录（详见 [08-data-catalog](../08-data-catalog/08-data-catalog.md)）：Schema、血缘、Owner、文档、上游表 / 指标、SLA。
2. 同步采集**调用方清单与最后调用时间**——这是下线机制的输入。
3. 缺项不可提交：注册项与上线流程绑定，而不是上线后补录。

- **产物**：可发现的 API 目录 + 每个服务的调用方清单。
- **判据**：做一次下线演练——任选一个服务，只看目录能否列出它全部调用方与最后调用时间。列不出来，说明清单是人工猜的，不是自动采集的。
- **为什么必须与 Step 4 / 5 并行**：调用方清单只能在服务上线的那一刻同步采集，事后补录时，前面发生的调用已经没有记录；而 §6 的四个案例里「服务只增不减」是共同踩过的坑，修法就是这条清单。

**Step 7：评估与监控（持续，从 Step 4 起就位【经验】）**

1. 采集 QPS、延迟、错误率、缓存命中率、数据新鲜度与用户满意度。
2. 做监控大盘（Grafana + Prometheus 一类），指标全带**调用方维度**。
3. 对异常 QPS / 错误率 / 延迟告警，告警阈值按实测调整而不是拍脑袋。

- **产物**：可观测的 OneService 平台，含按调用方拆分的使用与成本视图。
- **判据**：试着回答「上一季度每个调用方用了多少资源、其中机器调用占多少」。答不出来，说明监控只覆盖了服务维度。
- **为什么它是持续项而不是一个阶段**：配额与容量规划都要按实测调整，而实测数据的积累从第一个服务上线时才开始。

**Step 8：AI 集成（在 Step 3–6 全部就位后再开【经验】）**

1. 把 API 注册为 Agent Tool（Function Calling）：工具描述 + 参数 schema + 结构化错误码。
2. 集成 Text-to-API（Snowflake Cortex Analyst 一类模式），模型只填参数，不生成并执行 SQL。
3. 收集模型调用的失败形态（误拒、编造行为、同参数重复调用），回流到契约与定义层的改进。

- **产物**：机器可读的契约（工具描述 + 参数边界 + 结构化错误），以及 Agent 的独立身份与配额。
- **判据**：构造两次调用——一次问一个不存在的指标、一次问一个无权限的指标——看返回的错误能不能被区分。两者都回同一个「查询失败」时，模型会把它当成可重试的错误持续重试。
- **为什么必须放在最后**：§3.2.6 的失效条件写明，模型没有能力区分「这个指标不存在」与「这个指标我没听说过」——定义层不完备时它会编出一个看起来合理的替代指标，而调用方拿到的答案在形态上与正确答案无法区分。把这一层开在定义与治理之前，等于把错误答案的产能放大。

**最常被跳过的是 Step 6**，因为它不影响任何一次调用成功。跳过后第一个出问题的时点是第一次口径变更：症状是没人能列出受影响的调用方，只能等业务方报错——而接口数量过百、调用方里出现 Agent 之后，Agent 不会报错，它只会改用另一个看起来合理的接口。

### 4.2 关键技术点

这十二条分三段排列：第 1–8 条是服务自身的契约、治理与引擎机制（API 设计规范、限流、鉴权、缓存、查询优化、权限模型、可观测、网关），第 9–11 条是面向机器读者的三种接口形态（GraphQL / Function Calling / Text-to-API），第 12 条收回到数据契约——把前面每一条服务级的机制升格为组织级、缺项不可发布的登记义务。这与 §3.2 的六个模式是两套切法：模式回答「语义冻在哪」，这里回答「冻住之后哪些机制必须跟着到位」。

**1. API 设计规范**（REST 命名、参数校验、错误码、版本管理）
- **做法**：路径按业务对象命名（`/api/v1/metric/gmv`）；参数空间是白名单；错误码区分「不存在 / 无权限 / 参数越界」；不兼容变更走新版本号并留兼容期。
- **机制**：因为契约一旦有调用方，物理结构就被固化成了对外承诺，所以把语义放在业务对象上、把物理表名挡在契约外，重构才不会变成跨团队迁移。
- **失效条件**：**当接口数量随字段组合而不是业务域增长时**，设计已经退化成 §3.5 的「表透出」——这条不会在监控上报警，第一次被点出来通常在变更评审会上：一个「加一列」的需求被排成一次跨部门发版，回归清单里躺着全部按列名取值的调用方，而会上没有人能回答「谁真的在意这一列」。

**2. 限流策略**（令牌桶、滑动窗口、配额管理）
- **做法**：按调用方身份分档配额，在网关侧执行；配额单位按访问模式选——点查按调用次数，扫描型按扫描量。
- **机制**：因为限流是唯一能在异常调用打到上游之前生效的手段，而它必须在所有调用都经过的点位上执行，所以它只能落在统一出口，不能下沉到各服务。
- **失效条件**：**当调用方从人换成机器时**，模型会原样重试，一次超量被放大成持续负载——症状是监控里几乎全是 200，而成本曲线呈台阶式上跳。

**3. 鉴权**（OAuth 2.0、JWT、API Key、RBAC）
- **做法**：鉴权在网关统一执行，服务不各自实现；身份区分人、应用与 Agent 三类。
- **机制**：因为每多一个自行实现鉴权的服务就多一处可能漏判的路径，所以收归一处不是为了省事，是为了让漏判在物理上不可能。
- **失效条件**：**当审计对象变成 Agent 时**，按人审计失去解释力——审计记录要能回答「哪个 Agent、基于哪次会话、为回答什么问题取走了这批数」，否则合规举证走不通。

**4. 缓存**（Redis 结果缓存、ClickHouse 物化、本地 Caffeine）
- **做法**：结果缓存的键必须包含身份 / 租户与口径版本；本地缓存只放与身份无关的维度字典一类数据。
- **机制**：因为命中缓存的响应绕过了权限计算与口径解析，所以缓存键少一个身份维度，就等于给越权开了一条最快的路径。
- **失效条件**：**当口径改了版本而后端缓存未失效时**，同一接口会返回两个口径的数——症状是调用方用相同参数拿到不同结果，且两边都能自证。

**5. 查询优化**（索引下推、覆盖索引、JOIN 优化、向量化执行）
- **做法**：把过滤与投影尽量下推到存储层；对无时间或分区条件的查询强制拒绝。
- **机制**：因为这一步的收益先落在资源账单与租户配额上、后落在任何延迟指标上（代价结构见 §3.2.4），所以它在工程上的形态是**把扫描量按调用方摊开**：摊开之后优化对象从「哪条查询慢」变成「哪个调用方在烧预算」，减少读取量这件事才有人替它排期，而不是等 P99 破线才被想起。
- **失效条件**：**当源端 Connector 不支持谓词下推时**，一条「临时分析」可能比当天全部报表还贵（§3.2.4 已述），而写这条查询的人在写的时候感知不到——症状是集群负载与业务量脱钩。

**6. 权限模型**（行级 Casbin / OPA、列级动态脱敏、指标级白名单）
- **做法**：权限条件**改写下推**进底层查询，脱敏在网关返回前统一生效；三层权限（行 / 列 / 指标）都落在服务层，不由各服务自行实现。
- **机制**：因为下推把「记得过滤」这件事从每个实现里收走、只留在服务层一处，所以权限用例的回归面不再随服务数量增长——新接口默认继承行级条件，漏判只可能来自新开出来的取数路径，而那正好是出口盘点要盯的对象（两种做法为什么不等价，见 §3.5「无权限管控」）。
- **失效条件**：**当出现汇总 / 聚合接口时**，它最容易被漏——这类缺陷在开发期的界面与用例上都看不出来，第一次被指出多半是合规抽查或数据外发前的复核：某人手上的总数大于他逐行能看见的记录之和，而两个接口都没有报错。

**7. 可观测**（Prometheus 指标、Jaeger 链路追踪、ELK 日志）
- **做法**：四类指标（QPS / 延迟 / 错误率 / 数据新鲜度）全部带调用方维度；服务视角与调用方视角各有一套视图。
- **机制**：因为容量规划与配额调整都需要「谁在用、用了多少」这个维度，而总量指标无法被拆回调用方，所以维度是这类系统的第一需求，采样精度排在它之后。
- **失效条件**：**当只能回答总量问题时**，故障只能等业务方反馈——症状是「这个接口的 P99 是多少、谁在调、扫了多少」三个问题一个都答不出来。

**8. API 网关**（Kong / APISIX / Tyk / Envoy，详见 [07-data-api-gateway](../07-data-api-gateway/07-data-api-gateway.md)）
- **做法**：网关只做流量治理与统一策略（鉴权 / 限流 / 路由 / 计量 / 脱敏），不承载业务语义；上游引擎差异在网关上按类型路由，对业务透明。
- **机制**：因为网关是无状态策略层，它能被独立扩缩容与升级；一旦把语义映射写进网关插件，网关升级就变成一次跨团队变更。
- **失效条件**：**当上游引擎种类增加时**，若语义留在网关，每接一个源都要改插件并回归全部调用方——症状是一次版本升级要协调所有业务方。

**9. GraphQL**（Hasura / Apollo GraphQL / PostGraphile / GraphQL Mesh）
- **做法**：只对外暴露一个端点，批量解析由网关侧持有整棵查询树、按层合并下发（DataLoader 一类机制；某个实现是不是只做到了「GraphQL 代理」，判据见 §3.2.5）；对查询深度与节点数设上限，并按复杂度计量。上线前做一次对照：同一条查询分别在关掉批量解析 / 打开批量解析下各记一次后端请求数，两个数写进上线检查单——两次没什么差距，说明这层还没生效。
- **机制**：因为这一层要防的是「一个客户端把整批后端拖慢」，而单条查询的合法性与它的总代价之间没有关系，所以上限只能在网关侧按调用方身份生效，并且要落进配额插件而不是业务代码——写在业务代码里，后来加字段的人不会知道还有个上限。
- **失效条件**：**当查询深度与并发上升时**，会出现无法定价的请求——暴露方式是账单与配额告警同时对不上：大盘 P99 看着正常，而少数调用方贡献了大部分扫描量，按调用方拆的那个视图通常是唯一能看见它的地方。

**10. Function Calling**（OpenAI Function Calling / Anthropic Tool Use / MCP）
- **做法**：每个服务注册为一个工具，含人可读的一句话描述与机器可读的参数 schema；错误一律结构化。协议某个特性是否支持、支持到什么程度，以该协议与各平台官方文档当前版本为准。
- **机制**：因为工具的读者从人变成了模型，而模型不像人会自己换写法，所以契约的每一点模糊都会被放大成调用量的浪费——描述写错，模型会稳定地调错接口，且这种错误不报错、只给错结果。
- **失效条件**：**当错误只回「403」或超时时**，模型会原样重试，把一次超量放大成持续负载；错误里必须能区分超量、权限与语法。

**11. Text-to-API**（Snowflake Cortex Analyst / Databricks Genie / 自研）
- **做法**：把已定义指标与维度白名单注入上下文，模型只产出候选参数包；校验层判定合法后转发给第 1 项的指标接口，不让模型直接生成并执行 SQL。厂商侧形态见 [§5 前沿演进](06-one-service-section-5-ai.md)，本节不对其能力做断言。
- **机制**：因为这一层的每次放量只动两个可回滚的旋钮——注入上下文的指标条数与校验层的拒绝阈值——所以调整它不必碰执行引擎，出事时改回配置即可；代价是这两个旋钮都要有人盯：判据不是「答对率」，而是误拒率与人工兜底比例，它们在指标数越过某个点之后通常先于任何准确率指标抬升（为什么限定在参数空间就够，见 §3.2.6）。
- **失效条件**：**当定义层不完备时**，「门槛降到零」会反转成「错误答案的产能被放大」（§3.2.6）；判定方法：拿一个不存在的指标问它，看它是拒绝还是给出一个合理替代。

**12. 数据契约**（Data Contract：Schema、SLA、Owner）
- **做法**：每个服务在目录里强制登记 Schema、SLA、Owner、上游表 / 指标与调用方清单，缺项不可发布。
- **机制**：因为变更影响面只能靠机器可读的契约与血缘自动枚举，而人记的清单在接口过百、调用方里出现 Agent 之后必然不完备，所以登记必须与上线流程绑定而不是事后补录。
- **失效条件**：**当登记变成上线前的最后一道橡皮图章时**，它会与实际实现脱节——症状是登记里的上游表已经改名而契约没动；判定方法：挑一个服务，把登记信息与实际执行计划对一遍。

### 4.3 工具链与平台

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| API 网关 | Kong / Apache APISIX / Tyk / Envoy + Istio | 判据是「改一次策略要不要动服务代码」：要动，说明治理没收归网关；已有服务网格时优先复用 Envoy 侧能力 | 每个服务各自实现鉴权限流，漏一处就是一条越权路径 |
| API 框架 | FastAPI / Spring Boot / Gin / Echo / Express / NestJS | 判据是团队既有语言栈 + 「契约能否生成 OpenAPI」：接口要能被机器读出来 | 文档与实现漂移，契约无法被 Agent 消费 |
| GraphQL 平台 | Hasura / Apollo GraphQL / PostGraphile / GraphQL Mesh | 判据是「有没有分层批量解析」+「能否设查询复杂度上限」，两条都不满足时它只是换了协议 | N+1 从客户端搬到网关，成本没降还多了一层 |
| 自动 API 生成 | PostgREST / DreamFactory / Directus / Supabase | 判据是「这套表结构是否就是对外的业务语义」：结构即契约，只适合内部工具与 CRUD 场景 | 用在对外场景即是 §3.5 的「表透出」，一次重构变跨团队迁移 |
| 指标 / 标签平台 | 阿里 OneService（商业）/ dbt Semantic Layer / Cube（Cube.js）/ MetricFlow（dbt Semantic Layer 的指标定义引擎）/ Transform（商业）/ Airbnb Minerva | 判据是「指标有没有独立于 SQL 的定义载体、改口径是产新版本还是原地覆盖、Owner 是否具体到人」 | 口径没有承担者，服务层只是缓存了一个没人负责的数字 |
| Text-to-API | Snowflake Cortex Analyst / Databricks Genie / 阿里 Quick BI + AI / 腾讯 BI + LLM | 判据是「超出已定义指标范围时它拒绝还是编造」+「参数是否受维度白名单约束」 | 直接开放 SQL 入口，等于把成本与口径都交给调用方 |
| 联邦查询（辅助入口） | Trino / Presto | 判据是「问题事先无法枚举」且「源端 Connector 支持谓词下推」，两条缺一即不划算 | 为临时问题另开一条直连路径，绕过全部治理 |

这张表里最容易被误选的是**自动 API 生成工具**：它以最少的工程量给出最多的接口，很容易被当成服务化的捷径。误选的后果不是慢，而是把物理表结构固化成对外契约——一旦有上百个调用方按列名取值，任何一次表重构都是跨团队迁移，而「口径」在这条路径上无处安放。修法很便宜：把它限定在内部工具与原型，对外服务一律按业务对象重新设计。

上表的产品名、许可与能力以各自官方文档与仓库当前说明为准；部分项目近年发生过更名与归属变化，**指标平台的归属尤其容易写错**，选型前请按项目官方仓库核一次（本主题的使用者判断只需要回答一个问题：指标定义是不是独立于 SQL 的、可版本化的对象）。

### 4.4 存量迁移

这一节写给**已经有一批在跑的取数接口、不能推倒重来**的团队。迁移的目标不是把存量接口变漂亮，而是让**新增的取数先走上受治理的路**——存量的价值在于它还在被调用，改造它的收益低于让它继续跑。

**① 立刻见效且可回退的动作**

两件事可当天开始：一是**把新服务先收到同一个网关后面**（存量接口暂不动）；二是**给现有服务在目录里补一条登记**（只登记，不改造）。回退成本都接近零——撤掉路由、删掉条目即可。反面动作也要同时禁掉：迁移期内不再批准任何绕过网关的新接口上线。

**② 历史资产怎么分类处理**

| 分类 | 判断方法 | 处理方式 |
| --- | --- | --- |
| 高频 + 口径已稳定 | 有稳定调用方、有 Owner、近一个季度无口径争议【经验：观察窗口随业务结算周期变，至少要覆盖一次完整结算】 | 纳入定义层（建议一批 5–10 个指标【经验：批次大小随定义层评审带宽与接口交付节奏变】），服务逐步改为引用定义生成 |
| 低频 / 无调用方 | 目录里查不到调用方或最后调用时间已超过一个季度【经验：窗口随调用方的业务周期变，定期报表类需跨过一次报表迭代】 | 挂账不返工，标记「待下线」；到期仍无调用再下线 |
| 直连路径 | 网关日志里看不到的取数（导出任务、分析师直连、Agent 拿到的库凭证） | 不强制切断：先让受约束通道比绕路更好用，再配合过渡配额与告警 |

分类的动作要落到数字：拿一份最近三个月的网关日志【经验：窗口随发布与结算节奏变，至少要覆盖一次版本切换】，把调用量前 20% 的服务划进第一类【经验：分位随服务总数变——服务只有几十个时，改用绝对调用量划线更稳】，其余按要求处理。**不要全部返工**——把低频接口改成定义驱动，收益覆盖不了改造与回归的成本。

**③ 双轨怎么维持、维持多久**

迁移期必然双轨：定义层与手写 SQL 并存，新老取数路径并行。维持的要诀是**两条路径都能对账**——挑 3–5 个核心指标【经验：个数随指标总数与对账人力变，优先挑高调用、口径稳定的那几个】，让两条路径各算一次并按周期比对，差异即口径分叉的早期信号。时长按「新增服务 100% 走定义生成」这个目标推算：一到两个季度【经验，随存量服务数量与团队的接口交付节奏变】。

**④ 什么信号说明可以退出双轨**

- 网关日志的调用覆盖率 = 100%：目录里已没有未登记的取数路径；
- 新增服务的平均交付周期降到当天量级，且新服务里没有手写 SQL；
- 对账指标连续两个周期在两条路径上算出一致结果【经验：周期长度随各指标自身的刷新节奏变——按天刷新的以天计，按周结算的以周计】。

三条同时成立时，可以关掉旧路径的写入权限。

**⑤ 代价与不可回退点**

代价有两块。其一，**收敛出口的工作量按存量调用方数量线性增长**：单个调用方需要改一处连接配置并做一次联调，单价按【经验】每个调用方 0.5–1 人日——区间随该调用方的取数复杂度、是否需要双方约定联调窗口、以及它是否嵌在定时任务链里而变（点查型偏下端，带离线脚本与上下游定时依赖的偏上端）；乘数不用推算，N 直接取网关日志里尚未覆盖的调用方数量，总量即 N × 0.5–1 人日【经验】。其二，双轨期间的维护面翻倍——两套实现都要监控、都要响应事故。

不可回退的是定义层：一旦服务开始引用定义生成，改一次口径的影响面从 N 处收敛到 1 处，同时也意味着**定义层出错的影响面是全局的**——所以定义层要配 Owner、版本与评审，这三样必须在第一步回填存量定义时补齐，而不是等到出事再补。

### 4.5 模板 / 示例

**示例 1：FastAPI + ClickHouse 指标 API**

```python
from fastapi import FastAPI, Depends, HTTPException, Query
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
import clickhouse_connect

app = FastAPI(title="OneService Metrics API")
security = HTTPBearer()

@app.get("/api/v1/metric/{metric_name}")
async def get_metric(
    metric_name: str,
    dim: list[str] = Query(default=[]),
    time_range: str = Query(...),
    filters: dict = Query(default={}),
    credentials: HTTPAuthorizationCredentials = Depends(security),
):
    user = verify_token(credentials.credentials)          # 1. 鉴权
    if not has_metric_permission(user, metric_name):      # 2. 指标级权限
        raise HTTPException(403, "no permission")
    metric_def = get_metric_definition(metric_name)       # 3. 读定义（不内嵌 SQL）
    sql = build_sql(metric_def, dim, time_range, filters, user.row_filter)  # 4. SQL 生成（由定义表驱动）
    client = clickhouse_connect.get_client(host="clickhouse", port=8123)
    result = client.query(sql)                            # 5. 执行
    return {"data": result.result_rows,
            "meta": {"metric": metric_name, "version": metric_def.version}}
```

**怎么用**：照抄的部分是顺序——鉴权 → 指标级权限 → 读定义 → 生成 SQL → 执行，五步不能换序（换序即绕过权限）。不要照抄的是 `build_sql` 的细节：它必须由定义表驱动，`user.row_filter` 必须**下推进 SQL**（第 6 项技术点），而不是在返回结果上过滤。

**示例 2：Hasura 自动 GraphQL**

```yaml
# Hasura 从 PostgreSQL 生成 GraphQL：权限声明在平台上，不在 SQL 里
tables:
  - name: orders
    select_permissions:
      - role: analyst
        filter:
          order_date: { _gte: "2025-01-01" }   # 行级过滤：改写下推
        columns: [order_id, order_amount, user_id]   # 列级：未列出的列取不到

```

```graphql
# 业务方查询：一次往返，不再串联两次接口
query {
  orders(where: {user: {city: {_eq: "Beijing"}}}, limit: 10) {
    order_id
    order_amount
    user { name }
  }
}
```

**怎么用**：这一段只演示「权限写在哪、下钻怎么下」，不示范生产配置——生产上还要加查询深度与节点数上限，否则这段示例本身就构成 §3.2.5 的失效条件（成本无法定价）。表名与列名出现在配置里是允许的，它们出现在**对外接口路径**里才叫「表透出」。

**示例 3：Function Calling 数据服务**

```python
from openai import OpenAI

client = OpenAI()

tools = [{
    "type": "function",
    "function": {
        "name": "get_metric",
        "description": "获取业务指标，如 GMV、DAU",
        "parameters": {
            "type": "object",
            "properties": {
                "metric_name": {"type": "string",
                                "enum": ["gmv", "dau", "conversion_rate"]},
                "time_range": {"type": "string"},
                "filters": {"type": "object"},
            },
            "required": ["metric_name", "time_range"],
        },
    },
}]

response = client.chat.completions.create(
    model="gpt-4o",  # 模型标识以平台官方文档当前版本为准
    messages=[{"role": "user", "content": "上个季度 GMV 是多少？"}],
    tools=tools,
)
if response.choices[0].finish_reason == "tool_calls":
    args = json.loads(response.choices[0].message.tool_calls[0].function.arguments)
    result = call_oneservice_api(args)   # 走示例 1 的入口，配额与审计照常生效
```

**怎么用**：照抄的是「工具描述 + 参数 enum 是契约的一部分」这一点——`enum` 里没有的指标，模型就取不到，这是把定义层接到模型侧的最短路径。不要照抄的是模型名与 SDK 版本：以各平台官方文档当前版本为准。`call_oneservice_api` 必须走服务层入口，不要让模型拿到数据库凭证——否则示例 1、2 里所有的鉴权与配额全部失效。

### 4.6 成本：这套东西的账单

OneService 把「取数」从分析师直连（临时算、用完就走）改成常驻 API（预计算 + 缓存 + 计量），成本结构因此从「查询时算」整体挪到「先付一笔物化与常驻的固定成本、再按调用摊薄」。它的单价判断不能用「一次查询多少钱」，要用「这条链路被调用多少次才摊得平」。

- **云账单（主项）：物化宽表与缓存。** 三类资产各自吃存储与刷新算力：预聚合指标表、物化缓存、宽表（§2.2、4.2 第 4 / 5 项）。【推算】物化成本 ≈ 物化粒度数 × 时间跨度 × 单行字节 × 每次全量重算成本 × 刷新频率；粒度与刷新频率取自实际下钻需求，不是越多越好——每加一个下钻维度都是一份新的物化。**为什么贵在这里**：直连取数按需付费，OneService 是先算好等人来取；命中率不足时，你为「可能被问到的组合」付了全量账单，而这些组合大多数从未被问过。
- **网关与计量链路的固定成本。** 鉴权、限流、计量、脱敏都收敛到统一出口（4.2 第 1 / 3 / 8 项），这几件事要求出口本身至少双实例——它是全量的单点，这笔钱买的是它不成为可用性单点（见 4.7）。
- **硬件：后端数仓资源按调用方摊开。** §3.2.4 与 4.2 第 5 项已述，这里的增量是**配额视图**：没有按调用方拆的监控，「哪个调用方在烧预算」答不出来，优化对象会一直停在哪条查询慢。
- **人力：收敛出口 + 定义层。** 收敛出口的工作量按存量调用方数量线性增长（4.4 ⑤：0.5–1 人日 / 调用方）；定义层是另一笔——它改一次口径影响全局（4.4 ⑤），必须配 Owner + 版本 + 评审，这三样是长期人力而不是一次性投入。
- 通用分账与单位成本指向 [§11 数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)。本主题特有的增量是上面第一条：先物化后取用的成本形态，与直连取数不是同一种账单。

### 4.7 容灾与故障演练

OneService 的可用性有一个真正的单点——**统一出口**。这是它与资产管理、流批一体最大的不同：那两类的失效是渐进退化，这里的网关挂了就是全量取数中断。所以容灾的第一位不是重放窗口，而是这个出口本身。

| 失效模式 | 影响面 | 降级策略 | 演练 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 统一网关不可用 | 全部取数中断（BI / 应用 / Agent 一起） | 多实例 + 多可用区；至少留一条只读旁路能直连后端 | 摘掉一个网关实例，量调用成功率与切换耗时 | 【经验】RTO 秒级到分钟级，随实例数与会话粘性 |
| 后端源不可用（某一数仓 / 缓存） | 该源相关的接口失败，其余正常 | 网关按源路由，失败接口快速失败并回结构化错误（不静默重试） | 拔掉一个源，看失败是否隔离在该源、错误码是否可区分 | 【经验】分钟级，取决于该源自身的恢复 |
| 缓存未随口径失效 | 不崩，返回旧口径的数值（静默错误） | 缓存键含口径版本（4.2 第 4 项），改口径即换键 | 改一次口径版本，用同参数再调，看返回新旧 | 靠部署纪律，无 RTO；发现时点是调用方报错 |
| 权限漏判（汇总接口） | 越权可见——合规事故而非可用性事故 | 权限改写下推（4.2 第 6 项），汇总路径单独复核 | 抽一个聚合接口，验证其总数 ≤ 逐行可见之和 | 靠复核发现，非 RTO 问题 |
| 定义层口径出错 | 全局影响面（N 处同时错），即 4.4 ⑤ 的不可回退点 | 定义层版本化 + 评审，出错即回滚版本 | 改一个核心指标口径，走一次「发现 → 回滚 → 对账」全流程 | 【经验】小时级（回滚 + 缓存失效 + 对账） |

**为什么这里要谈跨地域，而资产管理、流批一体两节不必谈**：统一出口是全量的，它挂掉时没有「另一条链路还活着」可依赖，所以网关做成跨可用区、必要时跨地域是划算的，通用形态见 [§12 灾备](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)。但本主题真正的长期风险不是节点存活，而是**定义层的全局性**与**缓存的静默性**——这两类都不触发可用性告警，要靠表中第 3、5 行的演练主动去找。通用故障注入方法见 [§12 混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)，本节只给本主题特有的失效面。

### 4.8 演进路线：0 → 1 → 100

- **0 → 1（最小可用）：一个出口 + 一批手写 API。** 把新服务先收到同一网关后面，存量接口只登记不改造（4.4 ①）。此阶段**变贵的是**网关与登记的人力（每接一个源都要按同一口径验鉴权与限流）；**先坏的是**出口覆盖率——只要还有直连路径，治理就被按直连数量稀释（4.1 Step 4）。
- **1 → 100（规模化）：定义层驱动 + 多源 + 物化缓存。** 触发信号是接口数超过定义条目数（见 §2.4 思考锚点）：口径的份数 = 接口的份数。此阶段**变贵的是**物化与缓存（见 4.6）——下钻维度越多，物化份数越多；**先坏的是变更影响面**——定义层成为不可回退点，改一次口径影响全局，而目录里的调用方清单若没自动采集（4.1 Step 6），连受影响的是谁都说不出。
- **100 →（下一道坎）：AI 原生服务化。** 触发条件是把 API 注册为 Agent Tool / 开 Text-to-API（§1.4 AI 原生阶段）。此阶段**变贵的是**错误答案的产能——定义层不完备时，模型会编出一个形态上无法与正确答案区分的替代指标（4.1 Step 8、§3.2.6）；**先坏的是审计与错误语义**——审计对象从人变成 Agent 后，按人审计失去解释力（4.2 第 3 项），错误若只回「查询失败」，模型会把它当可重试错误持续重试。这一步靠加接口解决不了，只能靠定义层完备 + 结构化错误 + Agent 独立配额三件事。

### 4.9 自检清单

下面只列**跑起来才能回答**的问题。「契约里有没有物理表名、指标有没有独立于 SQL 的定义载体与具体到人的 Owner、参数空间是不是白名单、权限是改写下推还是应用层后置过滤、缓存键有没有身份维度」这五问在设计阶段坐下来就能回答，逐条见 [§3.7 自检清单](06-one-service-section-3-sec3.md)，本节不复述。

- [ ] **抽样**：抽 10 个已发布的服务，看**线上实际生效的契约**——路径与返回字段里有没有出现物理表名或物理列名？
- [ ] **对账**：取迁移期选中的 3–5 个核心指标，在定义层与存量手写 SQL 两条路径上各算一次并按周期比对，这个周期里有没有出现过两套数？
- [ ] **出口**：把现存取数路径枚举一遍（导出任务、分析师直连、Agent 拿到的库凭证、离线脚本），减去目录里已登记的，还剩几条不经过统一出口？
- [ ] **拒绝测试**：提交一次不带时间或分区条件的查询，它被拒绝还是被降级执行？
- [ ] **权限复核**：抽一个汇总 / 聚合接口的输出数字，解释它为什么包含这一刻的所有行——解释不通，说明行级过滤没有下推到聚合路径。
- [ ] **缓存复核**：改一次口径版本，再用同一组参数调一次，返回的是新口径还是旧口径？
- [ ] **用量读出**：打开监控大盘，能否直接读出「上个季度每个调用方用了多少资源、其中机器调用占多少」，而不是靠翻日志估算？
- [ ] **下线演练**：任选一个服务，只看目录能否列出它全部调用方与最后调用时间。
- [ ] **错误可区分**：构造「指标不存在」与「无权限」两次调用，返回的错误能否被区分？
- [ ] **登记对账**：挑一个服务，把目录里登记的上游表 / 指标与实际执行计划对一遍，是否一致？

### 4.10 小结

> 本节小结：这条路径上**唯一决定成败的环节是定义层**（Step 3、§4.9 里指向 §3.7 的那组设计态核查，问的都是它）——网关、缓存、监控这些工程件都能在事后补齐，甚至换一套重做；而「口径有几份实现」这件事，一份就是一份，接口建得越多、调用方接得越深，收敛的代价越大。它的投入之所以优先于其余环节，是因为它同时决定三件事：自助取数会不会以口径分裂为代价、变更的影响面是一处还是 N 处、以及模型接入后是拒绝还是编造。
>
> 💡 **思考锚点**：数两个数——你对外接口的条数，和指标 / 标签定义表里的条目数。若前者大于后者（口径的份数 = 接口的份数），§4.10 说的"收敛代价按调用方数量计"这个乘数已经存在，而且它会随 Agent 接入继续变大。这时你缺的是 Step 4 的网关，还是 Step 3 那张带版本、Owner、表达式的定义表？
