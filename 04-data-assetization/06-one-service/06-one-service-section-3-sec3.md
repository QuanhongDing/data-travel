## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把设计讲成「按场景挑一个」，但服务化的模式分野不是「用指标还是用宽表」，而是**语义在哪一刻被冻结**。主文件 §2.2 把服务化的本质写成 `API = f(Table, Metric Definition, Dimension, Filter, Access Policy)`；括号里这五项，有的在建模期就写死（指标口径、宽表 JOIN），有的要等调用到达才由调用方填（维度、过滤），还有的可以整段交给模型去推断（要问什么、按什么切）。冻结得越早越贵——要预计算、要刷新、要有 Owner——但越可控：参数空间是白名单时，「越权取数」与「口径走样」在语义上不可表达。冻结得越晚越灵活，但每一次调用都要为「这个问题该怎么查」重付一次决策成本，而且没有机制能承诺两次调用得到同一个口径。

第二个约束是**调用方是谁**。BI 要的是稳定的字段名与口径；分析师要的是能表达「我看得见、但你没预想到」的问题；Agent 两者都不占——它既不像分析师那样判断成本，也不像 BI 那样尊重既有口径，而模型的重试会把契约里的每一点模糊放大成一批调用（本章 §7 记有这条性质：机器会把契约漏洞放大成调用量）。同一个数据资产，三类调用方的正确形态不同。

第三个约束是**刷新预算**。预计算型模式（指标 / 标签 / 宽表）的时效性上限由刷新周期决定，而刷新周期由「重算范围 × 数据量 ÷ 可用算力」决定。这条约束解释了为什么「T+1 的数仓宽表」无法靠 API 层优化承担实时业务：瓶颈不在接口，在重算链路。

第四个约束是**出口数量**。权限、计量、血缘、配额这四件事全部建立在「取数走同一个点」之上。每多一条直连路径（导出任务、分析师直连、Agent 拿到的库凭证），服务层上的全部工作就被稀释一次——这一条不是模式选择题，而是模式能否生效的前提。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 语义冻结时刻 | 走预计算型（指标 / 标签 / 宽表）还是运行时决定型（联邦 / GraphQL / Text-to-API） | 「给业务方一个自然语言入口就等于自助取数」——语义没冻结，模型填出的参数无处校验 |
| 访问模式（点查 / 扫描 / 聚合 / 圈人） | 存储与索引形态：点查要 KV，圈人要倒排或位图，聚合要预聚合 | 「有一张宽表就能应付所有问题」——同一张表同时服务点查与圈人时，必有一条退化 |
| 调用方（人 / BI / 分析师 / Agent） | 契约严格程度、错误语义、配额单位 | 「Agent 就是又一个 API 客户端」——人看到报错会换写法，模型会原样重试 |
| 变更频率与口径历史要求 | 定义是否需要版本化、旧版本是否继续在线 | 「口径改了直接改实现」——历史报表会在没有提示的情况下变形 |
| 刷新预算与时效要求 | T+1 / 小时级 / 分钟级，以及为此付出的算力与人力 | 「加个缓存就能实时」——缓存不能把 T+1 的管道变成分钟级 |
| 出口数量与治理前提 | 权限、计量、血缘是否有落脚点 | 「先建服务，治理以后补」——第二条出口出现后，补治理的代价按调用方数量计 |

### 3.2 模式逐个拆解（核心节）

这 6 个模式按「语义冻结时刻」从早到晚排列：指标 / 标签 / 宽表把语义冻在建模期；联邦查询与 GraphQL 把它留到调用时决定——前者交给调用方写的 SQL，后者只把「能取哪些字段」冻在 schema 里、由调用方在查询期选；AI 增强型把它交给模型在对话里推断。读的时候盯住同一个问题：**这次调用到达引擎时，还剩多少事要做？**

#### 3.2.1 指标驱动型（Metric-Driven）

**被什么约束逼出来**：同一个「GMV」在十张报表里有十种算法，每次口径分歧都要靠开会澄清——口径必须变成有 Owner、有版本、可被引用的对象，而不是散落在每个调用方自己的 SQL 里。

**结构**（口径是一张可版本化的定义表，API 是它的出口）：

```sql
-- 语义冻结点：口径 = 一条带 Owner 与版本的声明，而不是一段散落的 SQL
CREATE TABLE metric_definition (
  metric_id     VARCHAR(64)  NOT NULL,   -- gmv
  version       INT          NOT NULL,   -- 口径变更 = 新版本，老版本继续服务
  owner         VARCHAR(64)  NOT NULL,   -- 具体到人，不是团队
  expr          TEXT         NOT NULL,   -- SUM(order_amount)
  base_table    VARCHAR(128) NOT NULL,   -- dwd_trade_order
  filters       TEXT         NOT NULL,   -- status = 'PAID'
  dim_whitelist TEXT         NOT NULL,   -- 允许的维度：date / region / channel
  sla_freshness VARCHAR(32)  NOT NULL,
  PRIMARY KEY (metric_id, version)
);
-- 出口：GET /api/v1/metric/gmv?dim=date&time_range=last_7d
-- 参数空间 = dim_whitelist 的组合；组合之外的请求在语义上不可表达
```

**为什么这样设计有效**：因为口径被抽成一条带版本号的记录，所以「这个数字怎么算的」只有唯一答案，「换个团队问同一个指标」不会得到第二个答案；因为调用方的参数空间是维度白名单的笛卡尔积，所以越权聚合与口径走样不靠事后审计发现，而是根本表达不出来。主文件 §2.2 给出的 `派生指标 = 原子指标 × 维度 × 修饰词 × 时间周期` 就是这个白名单的生成规则。

**代价**：定义层是常驻成本——每个指标要有 Owner、有 SLA，口径变更要触发版本与影响面评估，服务层还要为「同一指标的历史版本」同时在线付费。更隐性的是定义与实现的脱节：定义里写的是 `SUM(order_amount)`，而底层表被改名、上游语义被悄悄改动时，服务层不会自动报错（本章 §7 把这类失效记为「元数据与实现脱节时治理规则静默失效」）。

**失效点**：当业务问题落在「已定义指标 + 已声明维度」的组合之外时，本模式的「口径统一」会反转成「无法回答」，因为**参数空间是白名单，组合外的问题不是慢，而是表达不出来**；团队的实际反应通常不是回去补定义，而是另开一条自建 SQL 路径，服务层的治理随之被绕过。

**真实使用**：阿里数据中台的 OneService 把指标 / 标签 / 维度 / 宽表统一封装为服务，是本模式的实践来源（定位见主文件 §1.1；起止年份与材料形态见本章 §6.1，属实践方自述，本书不按【公开】档引用）。开源侧的定义层方案可参照 dbt Semantic Layer 与 Cube 的 measures / dimensions 设计【公开】（来源：dbt Labs 官方文档「About the dbt Semantic Layer」，docs.getdbt.com；Cube 官方文档中 measures / dimensions / filters 的设计说明，docs.cube.dev；两处均为随版本迭代的官方文档、不落固定发布年份，发布时间可查各自的发布说明，能力、许可与版本以当前版本文档为准）。判断某平台是否真做了这一层：看它的指标是否有独立于 SQL 的定义载体，改口径时是产生新版本还是原地覆盖。

#### 3.2.2 标签驱动型（Tag-Driven）

**被什么约束逼出来**：推荐与营销要的不是「某个指标等于多少」，而是「这个人是谁」——一次请求就要拿到一个实体的全部画像，晚一步就来不及在投放请求里用上。

**结构**（点查走 KV，圈人走倒排，两套结构缺一不可）：

```text
标签服务的两套存取结构（正查 / 反查）
  正查：一次点查拿全量标签
    GET /api/v1/profile/user/10086
    ┌────────────────────────┬─────────────────────────────────┐
    │ row key                │ value                           │
    │ u:10086#tag:churn      │ {value: 0.82, ts: 2026-10-17}   │
    │ u:10086#tag:value_lvl  │ {value: "白金", ts: 2026-10-17}  │
    └────────────────────────┴─────────────────────────────────┘
    → 不 JOIN、不聚合，一次 IO 出结果

  反查：按标签圈人（tag=churn 的 user_id 集合）= 倒排 / 位图
    → 正查与反查是两个方向，必须分别建索引
    → 只有正查时，「圈人」会退化成全表扫
```

**为什么这样设计有效**：因为标签在建模期就被算成「实体 → 值」的键值对，所以调用路径上没有任何计算，延迟由一次 IO 决定而不是由数据量决定；因为标签带计算时间戳（`ts`），下游可以据此判断这条画像是否够新，而不是无条件信任——这是推荐链路里最容易出问题的地方。

**代价**：标签构建是独立于服务层的第二条生产链路（特征计算、回填、监控），标签越多、实体越细，存储按「实体数 × 标签数」放大；时效性由标签的计算周期决定，服务层再快也改不了它。反查索引还要额外维护一份与正查同源的副本，两者口径漂移后会出现「查得到这个人有 churn 标签、但按 churn 圈人圈不到他」。

**失效点**：当标签数量增长到数百、且每个标签的更新频率不同时，你最初换来的「一次点查拿全部画像」会反转成「一次点查拖着一个巨大的写放大」——因为**正查要求所有标签写在同一行**，任何一个标签更新都要重写整行；此时 KV 的单行写成为瓶颈，要么拆行（正查退化为多次读），要么放弃部分标签的实时性。

**真实使用**：【经验】标签服务是画像类产品的标配：实体服务走 KV / 宽表点查、圈人走位图或倒排，多数团队会把两者拆成两个服务，因为它们的容量模型完全不同。判断某个平台的标签服务属于本模式还是「宽表模式」：看圈人操作是在标签服务内完成，还是被转发到数仓跑一条大查询——后者意味着标签只是宽表的别名。

#### 3.2.3 宽表驱动型（Wide-Table-Driven）

**被什么约束逼出来**：高频报表里反复出现同一种查询形状——固定几张表 JOIN、固定几个维度、按时间聚合。让每一次 API 调用都现场 JOIN 一次，等于把同一份计算重复付钱。

**结构**（JOIN 在建模期付清，API 只做过滤）：

```sql
-- 宽表 = 把 JOIN 与常用聚合提前付清；语义冻结点在这里
CREATE TABLE dws_user_trade_1d (
  dt        DATE          NOT NULL,
  user_id   BIGINT        NOT NULL,
  city      VARCHAR(32),                -- 维度已展开
  is_new    BOOLEAN,                    -- 修饰词已展开
  order_cnt BIGINT,                     -- 预聚合列
  gmv       DECIMAL(20,2),              -- 预聚合列
  PRIMARY KEY (dt, user_id)
) PARTITION BY RANGE (dt);              -- 按天分区：重算只重算受影响的分区

-- 出口：GET /api/v1/wide_table/dws_user_trade_1d?dt=2026-10-17&city=beijing&limit=1000
-- API 层只剩 WHERE + LIMIT，没有 JOIN、没有 GROUP BY
```

**为什么这样设计有效**：因为 JOIN 与聚合被提前到刷新链路里付清，所以调用路径的代价与「表有多少行」弱相关、与「过滤后返回多少行」强相关，高频重复查询不会每次都重付一次计算；因为按天分区，所以补一天数据只需要重算一个分区，而不是整表重建。

**代价**：存储按「维度组合数 × 时间跨度」放大，每个组合都有一份独立数据与独立刷新任务；维度一改就要回刷历史分区（回刷窗口常常按天计【经验】）；宽表与上游之间的口径同步是持久负担——上游改了清洗逻辑，宽表不会自己知道，必须靠调度与校验发现。更关键的是它把「有哪些维度可用」变成了物理事实：没被展开进宽表的维度组合，调用方拿不到。

**失效点**：当维度数量上升、且每个维度的取值基数都很大时，「预 JOIN 换性能」会反转成「维度组合爆炸」——因为**宽表的数量随维度组合增长，而每张宽表都要有自己的刷新链路**，于是维护面从「一条管道」变成「N 条管道」，而其中大多数宽表的长尾查询量根本覆盖不住它的刷新成本。此时正确做法是砍掉长尾组合、把它们退回给联邦查询或现场聚合，而不是继续加宽表。

**真实使用**：某零售企业让业务方自助建服务、从「排队等接口」变成「当天可用」（本章 §6.4，属实践方自述）。判断一个「宽表驱动」的服务是不是真宽表：看接口背后的查询里有没有 JOIN——一次调用触发多次 JOIN，说明宽表只是叫法。

#### 3.2.4 联邦查询型（Federated）

**被什么约束逼出来**：数据分散在 MySQL / Hive / ES / 向量库多个引擎里，而「先搬到一处再查」的搬运链路本身要维护、还要面对第二份副本与源端不一致——于是把查询送到数据所在处。

**结构**（一个 SQL 入口，代价由「没被下推的那部分」决定）：

```text
联邦查询网关（Presto / Trino 形态）
  Catalog A(MySQL) ┐
  Catalog B(Hive)  ├─► Coordinator ─► 拆分 ─► 各源执行 ─► 汇总
  Catalog C(ES)    ┘         │
                             ├─ 源端能下推（过滤 / 投影 / 分片）
                             │    → 只传过滤后的结果集，便宜
                             └─ 源端只能整表吐
                                  → 联邦 = 最贵的一条路（把搬运摊在每次查询上）

  API 形态：POST /api/v1/query {sql: ...}（权限校验 + 配额 + 成本上限）
  关键：同一个「联邦查询」模式，因为 Connector 能力不同，
        在这两个源上的正确性判断完全相反（口径与
        [09-unified-query-gateway §3](../09-unified-query-gateway/09-unified-query-gateway-section-3-sec3.md) 一致）
```

**为什么这样设计有效**：因为不要求先搬运，所以新增一个数据源的成本只是加一个 Connector，而不是新建一条同步管道与一份副本；因为调用方写的是完整 SQL，所以「你没预想到的问题」也能被回答——这是本模式相对所有预计算模式的核心优势。

**代价**：性能不由你的系统决定，由源端 Connector 的下推能力决定，同一句 SQL 换个源可能差几个数量级；权限、配额与成本上限必须在查询入口做（本章 §7 已述 Trino 的资源组能按队列 / 用户组限制并发与内存、并对单条查询设扫描量或执行时间上限【公开】，来源：trino.io 官方文档的资源组与查询级资源限制章节，配置项以当前版本文档为准）；口径不承诺——同一句 SQL 两次调用可以都「合理」却不一致，而且没有机制提醒你。

**失效点**：当源端不能有效下推、而结果集又很大时，联邦的「灵活性最高」会反转成「成本最高的那条路」，因为**代价与未下推的数据量成正比，而不是与最终结果成正比**；此时一次「临时分析」的扫描量可能超过当天所有报表之和，而写出这条 SQL 的人在写的时候感知不到。

**真实使用**：Presto 由 Facebook 开源并用于跨数据源的交互式分析【公开】（论文《Presto: SQL on Everything》，ICDE 2019）；其分叉版本于 2020 年 12 月更名为 Trino【公开】（来源：trino.io 官方博客的更名公告，2020 年 12 月；公告标题与发布日期以该博客当前页面为准）。Netflix 用联邦查询层替代「每个前端一个接口」（本章 §6.3，属实践方自述）。判断某个「联邦」是真联邦还是数据搬运：看源端 Connector 是否实现了谓词下推——不支持下推时，它只是把 ETL 挪到了查询期。

#### 3.2.5 GraphQL 型

**被什么约束逼出来**：BI 与前端需要的字段组合千变万化，为每种组合开一个 REST 端点会得到几十个高度相似的接口；让前端自己串多次调用，又会产生 N+1 次后端请求。

**结构**（单端点 + 按查询树分层批量解析）：

```graphql
# 语义冻结点：schema 决定「哪些字段可取、能下钻几层」
type User {
  id: ID!
  name: String
  orders(first: Int, after: String): [Order!]!   # 按需下钻，不是固定返回结构
}
type Order { id: ID!  amount: Decimal  created_at: DateTime }

# 单端点：POST /graphql
#   { user(id: "123") { name orders { amount } } }
# 无网关（前端串行）：1 + N 次后端查询
# 有网关（按层批处理）：层1 user(id=123) → 1 次；层2 orders(user_id in [...]) → 1 次
# 关键：批量解析必须由网关承担——它看得见整棵查询树，
#       单个字段的解析器永远不知道自己会被调用多少次
```

**为什么这样设计有效**：因为返回字段由调用方在查询期决定、而 schema 已经把可取字段限定住，所以接口数量不再随需求组合爆炸，同时「能取什么」仍有明确边界；因为网关持有完整查询树，它可以把同一层的字段需求收集起来一次性下发，使「按需取字段」不退化成「按需打后端」。

**代价**：网关必须实现批量解析与去重，否则 N+1 只是从客户端搬到了网关；缓存键不再是 URL，而是「查询 AST + 变量 + 身份」的规范化形式，规范化算法本身要维护；权限从端点级下沉到字段级，要求权限模型在 schema 上有对应表达（同一个 `User` 类型下，`phone` 与 `name` 的可读范围可能不同）。

**失效点**：当查询深度与并发上升时，本模式的「按需字段」会反转成「请求成本无法定价」——因为**单次请求的成本由客户端决定、上限却由服务端承担**，一个深嵌套查询可以合法地触发大量后端扫描与多层批查询。此时不得不引入查询复杂度评分与深度 / 节点数上限来兜底，而阈值一旦设错，正常调用先被拦住。

**真实使用**：GraphQL 由 Facebook 于 2015 年开源，自 2018 年起由 GraphQL Foundation 托管【公开】（来源：GraphQL Foundation 的托管公告，2018 年；公告出处与发布日期可在 graphql.org 检索核验）。本章 §4.3 已列 Hasura / Apollo GraphQL / PostGraphile / GraphQL Mesh 等实现——它们的能力、许可与版本以各自官方文档当前版本为准。判断某服务是否只是「GraphQL 代理」：看它有没有批量解析（DataLoader 一类机制），没有就只是换了协议，N+1 原样存在。

#### 3.2.6 AI 增强型（AI-Augmented）

**被什么约束逼出来**：业务方既不会写 SQL、也说不全指标名，而「找数难、懂数难、用数难」这三件事不会因为把界面做得更漂亮而消失——需要把「自然语言 → 结构化取数调用」这一步交给模型。

**结构**（模型只填参数，不定义口径）：

```text
POST /api/v1/text2api {"question": "上个季度北京新用户 GMV"}
  ① Schema 注入：可用指标 = metric_definition 的机器可读定义（含 dim_whitelist）
  ② 模型产出候选调用（对应主文件 §2.2 的形式化）：
       {metric: "gmv", filter: {is_new: true, city: "beijing"},
        time_range: "last_quarter", dim: "date"}
  ③ 校验层：指标是否存在？维度是否在 dim_whitelist？过滤值域是否合法？
       通过 → 转发给 3.2.1 的指标 API（不直接生成并执行 SQL）
       不通过 → 返回结构化拒绝（不存在 / 无权限 / 参数越界），而不是返回空集
  ④ 置信度低于阈值 → 转人工确认
关键：模型能填出什么，完全由 ① 决定；② 只是填参数
```

**为什么这样设计有效**：因为模型只被允许填「已定义指标 + 已声明维度」这个白名单内的参数，所以它的幻觉被限制在参数层面，最坏结果是「选了错误的维度」，而不是「编出一个口径」；因为校验层把拒绝做成结构化错误，模型与 Agent 都能据此换参数重试，而不是把空集当成答案（本章 §7 把这一条列为把服务开放给机器之前必须补齐的四件事之一）。

**代价**：schema 注入的规模随指标数量增长，指标越多，上下文越挤、选错指标的基线概率越高；校验层是新增组件，必须跟着定义一起演进，否则会拦错或漏拦；这一层还引入了一个新的失败模式——**「看起来能用」**：在演示用的干净 schema 上成立，在没有指标定义的生产仓里不成立。校验层的正确性无法靠模型自身保证，必须靠「拒绝率、误拒率、人工兜底比例」这类指标持续观测。

**失效点**：当定义层不完备时，本模式的「门槛降到零」会反转成「错误答案的产能被放大」——因为**模型没有能力区分「这个指标不存在」与「这个指标我没听说过」**，在定义缺失处它会生成一个看似合理的替代指标或替代维度，而调用方（尤其是 Agent）拿到的回答在形态上与正确答案无法区分。公开评测也帮不上忙：Spider（EMNLP 2018）与 BIRD（2023）都是单库、schema 相对干净的设定，不度量跨源联邦，也不度量「指标定义是否完备」【公开】（本章 §5.2.1、§5.5 已述）——把单库成绩外推到真实环境是常见误读。

**真实使用**：厂商侧的代表是 Snowflake Cortex Analyst 与 Databricks Genie【公开】（本章 §5.2.1 已列，均标注 2024）；本节不对它们的能力做断言，判定方法是查三件事——是否只在已定义指标范围内作答、超出范围时是拒绝还是编造、参数是否受维度白名单约束。Agent 侧的工具协议可参照 MCP【公开】（Anthropic 于 2024 年公开，本章 §5.2.2 已述、§5.4 已列为公开材料；本节不给版本号，是否支持、支持到什么程度以官方文档为准）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 口径要统一、有 SLA、被 BI 与报表高频消费 | 指标驱动型 | 宽表驱动能出数但不承诺口径，同一问题会有第二种答案 | 是否出现过「同一个指标两个数」的争议 |
| 画像 / 推荐 / 营销，需要一次拿到实体全貌或按标签圈人 | 标签驱动型 | 指标驱动回答「多少人」，回答不了「这个人是谁」 | 是否存在「按标签圈人」这一访问模式 |
| 查询形状固定、重复率高、维度组合收敛 | 宽表驱动型 | 联邦查询会把每次重复查询的计算重付一遍 | 前 20 个查询形状覆盖了多少调用量 |
| 临时分析、跨域研究、问题事先无法枚举 | 联邦查询型 | 预计算型模式回答不了组合外的问题 | 源端 Connector 的下推能力 |
| 前端 / BI 字段组合多变、接口数量在爆炸 | GraphQL 型 | 为每种组合开 REST 端点，接口数随组合增长 | 接口数是否在随字段组合而非业务域增长 |
| 业务方自助取数、AI 助手入口 | AI 增强型（架在指标驱动之上） | 直接开放 SQL 入口，等于把成本与口径都交给调用方 | 定义层完备度：超出已定义指标时它拒绝还是编造 |
| 中台标准化、要同时覆盖「看数」与「找人」 | 指标 + 标签双驱动 | 只上一侧，另一侧需求会绕道自建 | 是否两类取数诉求同时存在且都高频 |
| 实时业务、时效要求进入分钟级 | 宽表 + 流计算 | 只靠 T+1 批宽表，再快的接口也是昨天的数 | 重算链路的最短周期能否压到业务要求内 |

最常被误选的一对是 **指标驱动型** 与 **联邦查询型**：两者都能「回答问题」，于是团队常以为「上了联邦查询就等于有了统一取数」。误选的实际后果不是报错，而是**口径重新分裂**——业务方在联邦入口用 SQL 算出的 GMV 与 BI 上的 GMV 不一致，两边都能自证，最后只能靠开会仲裁，而服务层的治理（配额、计量、血缘）在这条路径上完全没参与。这个问题的修复成本很高：要么把联邦入口的语义收窄成「只许查明细、不许算指标」，要么补一套口径校验，两条路都要动存量调用方。

### 3.4 组合模式：真实系统不会只用一种

**组合一：指标驱动 + 标签驱动（双驱动）**

- 组合构成：指标回答「多少」，标签回答「是谁」，共用同一套鉴权、配额与计量。
- 职责边界：指标层持有口径与版本，标签层持有实体与值的映射；两者都不持有对方的定义，交叉问题（「高价值用户的 GMV」）由一个更高层的编排接口拼装。
- 运维代价：两条生产链路的刷新周期不同，交叉结果的新鲜度取两者中较差的那个，接口必须暴露口径与数据时间，否则调用方会拿昨天的标签配今天的指标。
- 适合规模：中台标准化阶段——有稳定的报表消费，同时有画像 / 营销类消费。

**组合二：宽表驱动 + 流计算（实时业务）**

- 组合构成：批宽表承担历史与全量，流计算管道承担分钟级增量，API 抽象成「同一张逻辑表」。
- 职责边界：批链路保证完整性与可重算，流链路保证时效；对账由批链路负责，因为流链路的正确性最终要靠批来裁决。
- 运维代价：同一份口径要维护两套实现（批 SQL 与流 SQL），一旦两边写的过滤条件不一致，就会出现「实时数与离线数对不上」且很难发现——需要常驻的对账任务与差值告警。
- 适合规模：时效要求进入分钟级、且团队已有流计算运维能力的阶段。

**组合三：指标驱动 + AI 增强 + 校验层（AI 取数入口）**

- 组合构成：定义层（3.2.1）提供机器可读指标定义与维度白名单，Text-to-API 负责理解问题并填参数，校验层负责拒绝非法调用。
- 职责边界：模型不定义口径、不执行 SQL、不判断权限；它的输出只是一个「候选参数包」，能不能执行由校验层与定义层共同裁决。
- 运维代价：校验层与定义必须同步演进（新增维度要同时改两处）；需要为机器调用单独做配额与熔断，因为模型的重试会把一次错误放大成一批调用；还要有人持续看「拒绝率与人工兜底比例」。
- 适合规模：定义层已经完备、治理（字段级权限、配额、结构化错误）已经就位之后再开这一层。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **「表透出」** | 接口路径里带表名（`/api/v1/wide_table/ods_xxx`），返回字段与物理列一一对应 | 物理结构即接口契约，加一列要发版、改表名要改调用方；口径没有任何承担者 | 自动生成接口最省事，先跑通再补语义 | 接口按业务对象重设计（指标 / 标签 / 宽表），物理表名不出现在契约里 |
| **「口径不统一」** | 同一个指标名在两处返回不同的数，且两处都能自证 | 服务层的全部价值（统一口径）失效，调用方回到「每个报表自己算」 | 每个业务线各建一层服务，没有共同的定义载体 | 统一指标定义 + 版本管理，服务只引用定义不内嵌 SQL |
| **「过度灵活」** | 对外提供 SQL-like 或任意 GraphQL 深嵌套入口，无复杂度上限 | 成本与口径同时失控：一次调用可以合法地扫全库 | 灵活性需求被当成主要需求，边界被推给「用户自觉」 | 按白名单收窄参数空间；确实需要开放 SQL 时，加复杂度评分、配额与成本上限 |
| **「无权限管控」** | 只校验 token 有效性，不校验「能看哪些行 / 列 / 指标」 | 任意合法调用方可读全量数据；鉴权只回答「是不是人」，不回答「能看什么」 | 权限被当应用层责任，每个服务各自实现或干脆不实现 | 行级 / 列级 / 指标级三层权限落在服务层，改写下推而不是应用后置过滤 |
| **「无版本管理」** | 改 schema 后调用方直接报错；没有兼容期与弃用流程 | 契约不稳定，调用方只能靠人力追版本，Agent 会因字段缺失反复重试 | 版本管理没有即时收益，改一次现场修调用方更快 | API 版本化 + 兼容期 + 变更前先枚举受影响调用方（依赖字段级血缘） |
| **「过度依赖 OLTP」** | API 直连 MySQL 主库；报表查询与线上交易抢同一批连接 | 分析型查询占用 OLTP 连接与 IO，交易链路被拖慢 | 数据「本来就在这个库里」，省一次同步 | 读写分离或专用分析库；OLTP 库只做点查与事务 |
| **「无监控」** | 回答不了「这个接口的 P99 是多少、错误率多少、谁在调」 | 故障只能等业务方反馈；容量规划没有输入；配额无法按实测调整 | 监控被当成上线后的可选项 | QPS / 延迟 / 错误率 / 数据新鲜度四类指标 + 按调用方维度拆分 |
| **「忽视成本」** | 相同参数的高频查询每次都直达计算引擎，缓存命中率无从谈起 | 成本与调用量线性同增；一次异常调用就能打挂上游（本章 §6.1 记有这类教训） | 缓存失效复杂，先不做 | 结果缓存（键含身份维度）+ 物化 + 配额；以参数重复率评估收益 |
| **「无血缘」** | 改了口径，没人能列出受影响调用方 | 变更影响面靠人记，必然漏；契约变更变成掷骰子 | 血缘建设周期长，且不影响当前功能 | 定义 → SQL → 表字段全链路血缘；变更影响面必须可自动枚举 |
| **「忽视 AI 集成」** | Agent 只能用「抓页面 / 读导出文件」的方式取数 | 服务层的鉴权、配额、计量对 AI 调用全部失效，且不可审计 | 现有接口是给人设计的，AI 需求后到 | 把 API 注册为工具（机器可读描述 + 参数 schema + 结构化错误），并给 Agent 独立身份与配额 |

三个最危险的反模式值得单独展开。

**「表透出」**看起来只是「还没抽象」，实际后果是**把物理结构固化成对外契约**：一旦有上百个调用方按列名取值，任何一次表重构都变成跨团队迁移；更麻烦的是它让「口径」无处安放——同一个 `order_amount` 被十个调用方各自解释一次，服务层连「口径分歧」这件事都感知不到。它的判据很直接：**接口文档里出现物理列名了吗？出现了就说明语义层不存在。**

**「无权限管控」**的危险在于它「看起来有安全措施」：有网关、有鉴权、有 TLS，唯独没有「这个调用方能看哪些行」。最容易漏的是聚合接口——明细接口做了行级过滤，而返回总计的汇总接口忘了过滤条件，于是汇总数字里包含了他人的数据，且形态上完全看不出异常。修法的关键是**改写下推**：把权限条件注入到底层查询里，而不是在应用层对结果做后置过滤，因为后置过滤要求每一个实现都记得过滤，下推由服务层统一保证。

**「无血缘」**通常被排在最后修，因为它的收益不体现在功能上。但机制上它是**所有契约变更的前置条件**：改口径、改字段、下线接口，这三件事都需要先回答「影响谁」。在有人维护调用方清单的年代，这个问题靠人记；一旦接口数量过百、且调用方里出现了 Agent，人记的清单必然不完备——而 Agent 不会在变更后主动报错，它只会持续失败或改用一个看起来合理的替代接口。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的。下面这些阈值的共同点是：**触发它们的是一个形状上的变化（谁在调、问题长什么样、时效要求变没变），而不是单纯的量变**。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 指标数从数十 → 数百【经验：分界随团队规模与口径变更频率变，成本结构见本章 §7.4】 | 一个接口一个 SQL | 没有共同的定义载体，口径分歧开始以「每周一次会议」的速度产生 | 指标驱动（定义表 + 服务引用定义） | 存量接口逐个回填定义与 Owner；口径评审成为常态流程 |
| 问题从「已定义指标」→「事先没想到的问题」 | 指标驱动 | 参数空间是白名单，组合外的问题表达不出来，业务绕道自建 | 补一条受控的联邦查询路径（只查明细、不承诺口径） | 要为新路径单独配权限、配额与成本上限；两条路径的口径边界必须写清楚 |
| 调用方从人 → Agent | 面向人的 REST 契约 | 契约的模糊被放成调用量的浪费：缺字段时人会换写法，模型会原样重试 | 契约机器化：机器可读定义 + 参数边界 + 结构化错误 + 按身份配额 | 四件事都要补齐；还要为机器调用单独做熔断与额度模型 |
| 时效从 T+1 → 分钟级 | 批宽表 | 瓶颈在重算链路而非接口，加缓存与加机器都无效 | 批流一体（同口径两套实现 + 对账） | 流 SQL 与批 SQL 要双维护，对账与差值告警成为常驻工作 |
| 维度数量增长、长尾组合变多 | 宽表驱动 | 宽表数量随维度组合增长，每张都有自己的刷新链路，长尾覆盖不住成本 | 砍掉长尾组合，退回联邦查询或现场聚合 | 要能回答「哪些组合被真正查询过」，依赖服务层的访问日志 |
| 单业务域 → 多业务域 | 单层服务 | 各域口径开始冲突，一次定义变更的影响面跨域不可枚举 | 定义层共享 + 服务按域隔离 + 字段级血缘 | 跨域口径评审机制、血缘覆盖要跟上，否则门禁形同虚设 |
| 只有一条取数路径 → 出现第二条 | 任意模式 | 治理的全部前提（唯一出口）被打破，权限、计量、血缘同时失效 | 先收敛出口，再谈模式 | 存量直连调用方逐个迁移，期间要给过渡配额与告警 |

这张表里最容易误判的是「调用方从人 → Agent」这一行。它之所以被低估，是因为**流量曲线不会立刻变化**，变的只是错误形态：人遇到模糊契约会产生一次失败调用然后放弃，模型会产生一串看起来合理、实际上参数错的调用，而这些调用在监控里全部是 200。所以这个跃迁要盯的指标不是 QPS 与错误率，而是**「同参数重复调用率」与「返回空集 / 异常聚合值的比例」**。

### 3.7 自检清单

- [ ] 接口契约里出现物理表名或物理列名了吗？出现即说明语义层不存在。
- [ ] 同一个指标在服务层与任一报表 / 联邦入口上，是否算出过两个不同的数？
- [ ] 每个指标是否有独立于 SQL 的定义载体、版本号与具体到人的 Owner？改口径是产新版本还是原地覆盖？
- [ ] 调用参数空间是白名单（指标 + 维度 + 过滤 + 时间范围）还是自由语法？若是后者，有没有复杂度与成本上限？
- [ ] 一个合法调用方，能否通过某个聚合接口读到不属于它的行？汇总接口是否也做了行级过滤？
- [ ] 权限是「改写下推」还是「应用层后置过滤」？后者有几个实现路径漏了过滤？
- [ ] 是否存在第二条能拿到数据的路径（导出、分析师直连、Agent 拿到的库凭证）？有几条？
- [ ] 缓存键是否包含身份 / 租户维度？不带身份维度的缓存有没有准入白名单？
- [ ] 改动一个指标口径时，能否自动列出受影响的调用方与接口版本？如果不能，靠什么清单？
- [ ] 高频重复查询是否每次都直达计算引擎？参数重复率是多少，值不值得缓存？
- [ ] 服务层 API 是否已注册为工具（含机器可读描述、参数 schema、结构化错误码）？「这个指标不存在」与「无权限」能否被区分？
- [ ] 能否回答「上季度每个调用方用了多少资源、其中机器调用占多少」？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 口径必须统一、有 SLA、被高频消费 | 指标驱动型 | 语义冻在定义表里，越权与口径走样在参数空间上不可表达 |
| 要一次拿到实体画像、要按标签圈人 | 标签驱动型 | 点查零计算；但正查与反查是两套结构，缺一套就会退化 |
| 查询形状固定、重复率高 | 宽表驱动型 | JOIN 提前付清；代价是维度组合决定维护面 |
| 问题事先无法枚举、跨源 | 联邦查询型 | 灵活性最高；代价与未下推的数据量成正比，且不承诺口径 |
| 字段组合多变、接口数量爆炸 | GraphQL 型 | schema 限定可取范围，网关承担批量解析；须设复杂度上限 |
| 业务方自助、Agent 取数 | AI 增强型（架在定义层之上） | 模型只填参数；定义不完备时它会编，不是会拒 |
| 时效进入分钟级 | 宽表驱动 + 流计算 | 瓶颈在重算链路，批流双实现 + 对账是必付成本 |
| 要同时覆盖「看数」与「找人」 | 指标 + 标签双驱动 | 两类访问模式的索引形态不同，合成一张表必有一条退化 |

> 本节小结：本主题下决定模式选择的**唯一那条约束是「语义在哪一刻被冻结」**——冻得早（指标 / 标签 / 宽表）换来确定的性能与可表达边界，代价是预计算、刷新与维护面；冻得晚（联邦 / GraphQL / Text-to-API）换来表达力，代价是每次调用都要重付一次决策成本，而且没人能承诺口径一致。所有模式选择，本质是在这条时间轴上给自己找一个「性能、口径、灵活性三者都可运维」的位置，而不是挑一个更先进的技术形态。
>
> 💡 **思考锚点**：数一数你的服务层现在有几条能拿到同一份数据的路径（REST 接口、导出、分析师直连、Agent 拿到的库凭证各算一条）：若大于 1，你选「指标驱动」还是「联邦查询」已经不重要——按 §3.6「只有一条取数路径 → 出现第二条」那一行，治理的全部前提（唯一出口）已被打破，权限、计量、血缘同时失效。把出口收敛回一条之前，你打算先把哪个存量调用方迁走，过渡期配额给谁？
