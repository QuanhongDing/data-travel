## 3. 设计模式与范式

> 原 § 3 共 78 行，形式为「模式 + 优点 / 缺点 / 适用」条目 + 决策表 + 反模式清单，缺结构示意、机制解释与失效分析，重写为 336 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

指标平台的 6 个模式表面上像产品选型（用谁家的），但它们真正的差别只有一条主线：**口径定义的唯一载体长什么样，以及从定义到执行计划之间隔了几层**。同一个 GMV，定义可以是一段组合式 DSL、一个 YAML 文件、一段 JavaScript、一门专有建模语言，或平台自造的语法——载体形态决定了三件事：谁能改口径、改一次要动几处、谁能消费。

第一条约束是**定义是否有唯一载体**。只要同一个指标存在两份可执行的定义，两份就会分叉，而且分叉不会报错——它表现为两个报表给出两个数字，并且没人能证明哪个对。所以所有指标平台模式的第一目标是同一个：把定义收拢到一处。差别只在收拢到哪：仓库里的文件（dbt Semantic Layer）、平台自己的元数据库（OneMetric / 自研）、还是前端工程仓库（Cube.js）。

第二条是**计算发生的位置**。dbt Semantic Layer 与 LookML 把定义翻译成 SQL 下推到数据仓库执行，平台自己不存数；自研模式通常自己生成两条物理链路（离线批、实时流）并落自己的指标存储。这决定了新鲜度上限与运维面：下推模式的能力上限由底层模型决定，自研模式的上限由自己的代码生成器决定，代价是必须养一支长期团队。

第三条是**消费方是谁**——数据团队（会写 SQL、会发 PR）、业务方（只会点选与提问）、还是 Agent（只调 API）。dbt / LookML 服务机构化协作，Cube.js 服务产品化嵌入，AI 增强层服务自然语言入口。消费方不同，同一个定义层要暴露的接口就不同——这也是为什么 3.4 的组合里，AI 增强几乎总是叠在某个定义层之上，而不是替代它。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 定义的唯一载体（放在哪儿） | 谁能改口径、改动走什么流程 | 「先各写各的，之后再统一」——分叉不会报错，只会变成两个数字 |
| 计算发生的位置（下推 / 自生成） | 新鲜度上限与运维面的大小 | 「语义层顺便能把性能也解决了」——下推模式下性能由底层模型决定 |
| 指标类型（可加度量 / 比率 / 集合） | 定义语言的表达力够不够 | 「组合式定义能表达所有指标」——转化率、留存类往往表达不了 |
| 指标规模（千级 / 万级 / 十万级） | 消费端的检索方式 | 「把全量 schema 灌给 LLM 就行」——规模一大必须改成先召回再注入 |
| 消费方（数据团队 / 业务方 / Agent） | 接口形态与使用门槛 | 「业务方学一下就会用」——门槛超过等待容忍度，治理就被绕过 |
| 实时与离线是否都要（团队运维能力） | 是否需要定义驱动生成双链路 | 「先做离线，实时以后再说」——以后再补时两套口径已经分叉 |

把这 6 个模式放回上面这三条约束（再加上表里另列的三条次级约束——指标类型、指标规模、实时与离线是否都要）上看：OneMetric（3.2.1）解决的是定义的**形状**（组合式，可枚举）；dbt Semantic Layer（3.2.2）、Cube.js（3.2.3）、LookML（3.2.4）解决的是定义的**存放位置与消费形态**；AI 增强（3.2.5）不碰定义，只改入口；自研（3.2.6）则把定义一路延伸到执行计划的生成。**把不同层次的问题当成同一个单选题，是选型出错的典型形式。**

### 3.2 模式逐个拆解（核心节）

下面 6 个模式按「定义载体 → 消费入口 → 计算位置」排列：3.2.1–3.2.4 是四种定义载体（组合式 DSL、YAML 声明、JavaScript 定义、专有建模语言），3.2.5 是叠加在定义层之上的自然语言入口，3.2.6 是把定义延伸到执行计划生成的自研路径。

#### 3.2.1 阿里 OneMetric 模式（原子指标 × 修饰词 × 时间周期 × 维度）

- **被什么约束逼出来**：指标数量上万、由多个团队在同一个数仓里生产；口径必须能被**枚举式穷举**，否则「同一指标跨业务是否一致」这件事根本无法检查。
- **结构**：四个正交要素组合成派生指标。四要素各是一张可枚举的注册表，派生指标只是对它们的引用；定义是「组合」，不是「SQL 片段」，所以派生指标不产生新的计算逻辑。

```sql
-- OneMetric 式定义的物理形态：派生指标 = 原子指标 × 修饰词 × 时间周期 × 维度
-- 原子指标：不可再分，度量表达式只在这里出现一次
CREATE TABLE metric_atomic (
  atomic_id    VARCHAR(64) PRIMARY KEY,
  name         VARCHAR(128) NOT NULL,  -- order_paid_amount
  expr         VARCHAR(512) NOT NULL,  -- SUM(pay_amount)
  source_table VARCHAR(256) NOT NULL,  -- dwd_trade_order_pay_di
  grain        VARCHAR(64)  NOT NULL   -- order_id：粒度声明，防止跨粒度重复计数
);

CREATE TABLE metric_modifier (         -- 修饰词：可被任意派生指标复用
  modifier_id  VARCHAR(64) PRIMARY KEY,
  name         VARCHAR(128) NOT NULL,  -- new_user / app_channel
  condition    VARCHAR(512) NOT NULL   -- is_new_user = true
);

CREATE TABLE metric_time_grain (       -- 时间周期：day / week / month / quarter
  grain_code   VARCHAR(16) PRIMARY KEY
);

CREATE TABLE metric_derived (          -- 派生指标：不写 SQL，只引用四要素
  derived_id   VARCHAR(64) PRIMARY KEY,
  name         VARCHAR(128) NOT NULL,  -- new_user_paid_amount_1d
  atomic_id    VARCHAR(64) NOT NULL REFERENCES metric_atomic(atomic_id),
  modifier_ids VARCHAR(64)[] NOT NULL,
  grain_code   VARCHAR(16) NOT NULL REFERENCES metric_time_grain(grain_code),
  dimensions   VARCHAR(64)[] NOT NULL  -- [city, channel]
);
```

- **为什么这样设计有效**：因为所有派生指标都由同一份原子表达式组合出来，所以「口径一致性」在结构上就被保证——不存在两个团队各写一份 SUM 的机会；改一次原子表达式，所有派生指标同步改变，一致性由结构保证而不是靠评审发现。
- **代价**：① 表达力受限——漏斗、留存、跨层去重这类复合逻辑放不进四要素组合，只能破例写「非标指标」，一旦破例，口径治理就出现一个填不上的洞；② 强依赖数仓分层规范（DWD / DWS），规范不落地时组合式定义无处安放；③ 每个派生指标要人工登记组合，指标数量增长时登记工作量线性增长。
- **失效点**：当业务需要**比率型与集合型指标**（转化率 = 分子 / 分母、留存 = 两日用户集合的交集）时，四要素组合表达不了，这些指标会被放到平台之外实现——而它们恰恰是决策最依赖的那批。所以本模式的失效点是**指标类型**，不是规模：它擅长可加性度量，不擅长比率与集合；规模上去了它只会更慢，类型不匹配它直接失效。
- **真实使用**：阿里数据中台「原子指标 + 修饰词 + 时间周期 + 维度」的定义范式，公开记录见《大数据之路：阿里巴巴大数据实践》（2017）的数据模型设计部分；本书 [§ 4.3](10-metric-platform-section-4-sec4.md) 工具链清单与 [§ 6](10-metric-platform-section-6-sec6.md) 案例 10.1 记录了它在阿里 DataWorks 指标平台上的应用。【公开】（来源：《大数据之路：阿里巴巴大数据实践》，2017；产品侧应用另见本书 §4.3 / §6 案例 10.1 的书内记录）

#### 3.2.2 dbt Semantic Layer 模式（MetricFlow）

- **被什么约束逼出来**：分析逻辑已经以 dbt 模型的形式存在于数据仓库里，团队用 Git 协作；指标若另立门户（独立的 Web 配置台），就会立刻变成仓库之外的第二个真相。
- **结构**：指标是仓库里的一个文件，与模型同仓库、同 PR、同评审。

```yaml
# 指标定义即代码：与 dbt 模型放在同一仓库、走同一套 PR 流程
# 关键分工：聚合方式属于语义模型的 measure，不属于 metric
semantic_models:
  - name: orders
    model: ref('orders')
    defaults: { agg_time_dimension: order_date }
    entities:
      - { name: order, type: primary }
      - { name: user,  type: foreign }
    dimensions:
      - { name: order_date, type: time, type_params: { time_granularity: day } }
      - { name: status,     type: categorical }
      - { name: is_new_user, type: categorical }
    measures:                        # ← agg / expr 只写在这里
      - name: order_pay_amount
        agg: sum
        expr: pay_amount
      - name: order_cnt
        agg: count_distinct
        expr: order_id

metrics:
  - name: paid_amount                # 指标只引用 measure，自身不写 agg
    type: simple
    type_params: { measure: order_pay_amount }
    filter: "{{ Dimension('order__status') }} = 'paid'"

  - name: new_user_paid_amount
    type: derived
    type_params:
      expr: paid_amount
      metrics: [{ name: paid_amount }]
    filter: "{{ Dimension('order__is_new_user') }} = true"
# 口径变更 = 一次 diff；评审、历史、回滚全部复用工程流程
```

- **为什么这样设计有效**：因为定义以文件形式与数据模型放在同一仓库，所以「改口径」复用了已有的工程通道（PR 评审 + diff + 版本历史 + 回滚），治理成本被摊到既有流程上，不需要再建一套审批系统——**口径治理的落地成本，是这类模式能否推广的真正变量**。
- **代价**：① 语义层不物化数据，查询时才翻译成 SQL 下推仓库，性能完全由底层模型决定，语义层给不了性能；② 能力边界由 dbt 生态决定，生态外的数据源与引擎要自己接；③ 定义语言仍是「度量 + 过滤 + 聚合 + 维度」结构，表达力有限。
- **失效点**：当使用者从数据团队扩展到不熟悉仓库与 Git 的业务方时，PR 工作流反而成为门槛：改一个过滤条件要走评审、等合并，等待时间从分钟级变成天级，业务方于是绕开语义层自己写 SQL，口径重新分裂。所以它的失效点是**使用者的工程能力与等待容忍度**，不是数据规模；解法是在定义层之上再加服务化或自然语言入口（见 3.4 组合二）。
- **真实使用**：dbt Labs 的 Semantic Layer + MetricFlow，完整定义示例见本书 [§ 4.5](10-metric-platform-section-4-sec4.md) 例 1。【公开】（来源：dbt Labs 官方文档「About the dbt Semantic Layer」与「MetricFlow」（docs.getdbt.com，随 dbt 版本更新的产品文档）；dbt Semantic Layer 2022 年推出、MetricFlow 2022 年开源，时间线见本书 §1.4）

#### 3.2.3 Cube.js 模式

- **被什么约束逼出来**：指标要被**产品**消费——前端、嵌入式分析、多租户 SaaS，而不是被人写 SQL 消费；产品对延迟的要求由交互决定，不由分析习惯决定。
- **结构**：定义即 API 契约，预聚合也写在定义里（而不是藏在优化器黑盒里）。

```javascript
// 定义直接决定对外 API 契约：measures / dimensions 声明什么，就暴露什么
cube(`Orders`, {
  sql: `SELECT * FROM public.orders`,
  measures: {
    gmv: { sql: `amount`, type: `sum`,
           filters: [{ sql: `${CUBE}.status = 'paid'` }] }
  },
  dimensions: {
    city:      { sql: `city`,       type: `string` },
    orderDate: { sql: `order_date`, type: `time`   }
  },
  preAggregations: {              // ← 加速发生在物理层，定义层一行不改
    gmvByDayCity: {
      measures: [gmv],
      dimensions: [city],
      timeDimension: orderDate,
      granularity: `day`
    }
  }
});
```

- **为什么这样设计有效**：因为预聚合是定义的一部分而不是优化器的黑盒行为，所以「查询变快」与「口径不变」可以同时成立——加速只改变物理存储形态，不产生第二份口径。
- **代价**：① 预聚合是「用存储与新鲜度换延迟」，每个被物化的维度组合都要刷新，组合数增长会带来物化表数量的组合爆炸；② 定义用 JavaScript，与数据团队的 SQL / YAML 技能栈错位，通常是前端或全栈团队维护，治理责任容易模糊；③ 预聚合与缓存都引入「数据延迟」，必须显式告诉消费方读到的是哪个新鲜度，否则会反复出现「为什么两个接口的数字不一样」。
- **失效点**：当维度的可自由组合数增长时，预聚合策略反转成负担：因为预聚合的收益取决于命中率，而命中率取决于查询在维度组合上的集中度；维度越自由、下钻越随意，命中率越低，后台却在持续刷新大量没人查的组合。此时正确的动作是**关闭预聚合、把压力交回 OLAP 引擎**，而不是加更多预聚合。
- **真实使用**：Cube（Cube Dev 的开源指标 API 平台，原名 Cube.js），典型场景是被产品嵌入的自助分析与多租户报表；定义与预聚合的写法见官方文档「Data Modeling」「Pre-aggregations」（docs.cube.dev）与本书 [§ 4.5](10-metric-platform-section-4-sec4.md) 例 2。【公开】（来源：Cube 官方文档「Data Modeling」「Pre-aggregations」（docs.cube.dev）；该文档随产品版本更新、无固定出版年份，开源项目的时间线另见本书 §1.4）至于哪家企业真的在生产里这么用，本节不列具名名单——**判断方法**：看对方的指标接口是否由声明式 schema 生成、预聚合是否写在 schema 里而不是一张人工维护的物化表清单。【经验】

#### 3.2.4 LookML 模式

- **被什么约束逼出来**：企业已经在用某个商业 BI，要让业务方的自助探索（点维度、下钻、换过滤）直接落在受治理的语义模型上，而不是每人写一条 SQL。
- **结构**：度量、维度、视图与「探索路径」都由建模者在模型里预先声明，查询时由引擎翻译成 SQL。

```lookml
view: orders {
  sql_table_name: analytics.orders ;;
  dimension: order_date { type: date   sql: ${TABLE}.order_date ;; }
  dimension: city       { type: string sql: ${TABLE}.city ;; }
  measure: gmv {
    type: sum
    sql: ${TABLE}.amount ;;
    filters: [status: "paid"]      # 口径写死在度量里 → 用户无法绕过
  }
}
# 可下钻的 JOIN 路径由建模者预先声明 = 受治理的探索边界
explore: orders { label: "订单" }
```

- **为什么这样设计有效**：因为度量的过滤条件写死在度量定义里、可组合的 JOIN 路径由建模者预先声明，所以业务方的自助查询只在建模者授权的空间里自由组合——自由度是被**结构**限制的，而不是被制度或流程限制的。
- **代价**：① 引擎与定义语言绑定，迁移意味着语义模型作废重写（锁定锁住的是几百个度量与探索，不只是查询语句）；② 建模是专门技能，建模者成为所有新指标的排队点；③ 模型表达能力受 BI 引擎的查询能力限制，底层引擎更换时模型也要改。
- **失效点**：当业务需要的下钻路径超出预声明的探索范围时，业务方要么等建模者改模型，要么用 BI 自带的自定义 SQL 绕过——而后者一旦被使用，整层治理就形同不存在。所以以建模者为中心的模式，失效点是**建模带宽**：当模型改动的等待时间超过业务容忍度，治理就被绕过，而不是被遵守。
- **真实使用**：LookML 是 Looker（Google Cloud）的语义建模语言；Looker 于 2019 年被 Google 收购【公开】（来源：Google Cloud 官方博客 2019 年发布的 Looker 收购公告；公告标题与具体日期可在该博客按年份与产品名检索核验）。Looker 与 Gemini 结合的 AI 方向见本书 [§ 5](10-metric-platform-section-5-ai.md)。

#### 3.2.5 AI 增强模式（Text-to-Metric）

- **被什么约束逼出来**：消费指标的人远多于会写 SQL 或熟悉建模 DSL 的人；同时平台已经有机器可读的指标定义——没有定义就无从「增强」。
- **结构**：把指标 schema 注入 LLM，LLM 只输出结构化意图，计算永远由平台执行。

```text
Text-to-Metric：LLM 只做"意图映射"，不做计算

  问句："上个季度北京新用户 GMV"
        │
  ① 注入：指标 schema（名称 / 描述 / 维度 / 修饰词 / 时间粒度）+ 少量示例
        ▼
  ② LLM 输出结构化意图（不是 SQL）
     {"metric": "new_user_paid_amount",
      "filters": { "city": "Beijing" },
      "time_range": "2025-07-01/2025-09-30",
      "grain": "quarter"}
        ▼
  ③ 校验层：指标名必须存在于指标库；维度与取值必须在 schema 枚举内；
           时间范围必须能落到存在的分区 —— 不通过则拒绝或转人工
        ▼
  ④ 指标 API 计算并返回（计算永远在平台里，不在 LLM 里）

  ─────────────────────────────────────────────────────────────
  关键：把 LLM 的输出约束在"选择"而不是"生成"上
       → 幻觉的表现形式从"算错数"退化为"选错指标"，后者可被发现
```

- **为什么这样设计有效**：因为 LLM 只输出「指标 + 维度 + 过滤 + 时间范围」这个封闭集合里的选择项、而计算由平台执行，所以幻觉不可能变成错误数字——它只会变成「选错指标」或「被校验层拒绝」，两种都能被发现和纠正。这正是 Text-to-Metric 相对 Text-to-SQL 的核心机制优势：SQL 允许生成出语法正确但语义错误的查询，封闭选择集不允许。
- **代价**：① 效果上限等于指标库的描述质量——描述缺失时模型只能靠名字猜；② token 成本随「注入的候选指标数」与提问次数增长，指标上万时不可能全量注入，必须先做指标召回，而那是另一套需要维护的系统；③ 引入新的失败模式：置信度不可知，模型给出一个合理但错误的映射，且措辞自信。
- **失效点**：当指标规模增长到无法把全部 schema 注入 prompt 时，全量注入失效，必须改为「先召回候选指标再注入」；此时**召回率成为准确率的上限**——没被召回的指标，LLM 永远不可能选对，而用户从答案里看不出「其实有更合适的指标没被召回」。所以规模只是触发条件，真正失效的是**指标 schema 的可达性**（见 3.6 的「千级指标 → 万级指标」跃迁），不是模型能力；解法是把指标元数据质量与召回升到与模型同等重要的位置。
- **真实使用**：Snowflake Cortex Analyst 与 Databricks Genie 把自然语言入口做进云数仓【公开】（来源：Snowflake 官方文档的 Cortex Analyst 一节与 Databricks 官方文档的 Genie 一节（docs.snowflake.com / docs.databricks.com，2024 年发布的产品文档，随产品版本更新，页面标题以文档站当前版本为准））；国内阿里 Quick BI + 通义、腾讯 BI + LLM 方向相同（见 [§ 5](10-metric-platform-section-5-ai.md)）。需要说明的是，多数企业的现状是自然语言入口与既有 BI 并存，「全面替代」尚不是普遍事实。【经验】

#### 3.2.6 自研模式

- **被什么约束逼出来**：同一个指标要同时服务离线分析与在线实时（推荐、风控、投放），一套定义必须驱动两类完全不同的物理链路，而现成产品通常只覆盖其中一条。
- **结构**：定义驱动执行计划的生成——离线链路与实时链路都由同一份定义推出来。

```text
自研模式的核心不是"自己写"，而是"定义驱动执行计划的生成"

  指标定义（一次定义，业务方只定义、不写 SQL）
        │
  平台生成执行计划（DAG 由定义推导，不由人编写）
     ├─ 离线链路：批处理作业 → 数仓明细 / 聚合表 → 供分析查询
     └─ 实时链路：流处理作业 → KV / OLAP 指标存储 → 供在线读取
        │
  一致性校验：两条链路对同一时间窗口的结果定时对拍，
             偏差超阈值告警并阻断后续变更
        │
  统一服务层（指标 API）：分析侧与在线侧读同一个指标名

  ──────────────────────────────────────────────────────────
  边界：写 SQL 的自由度被收走了，换取"改口径不可能漏改"
```

- **为什么这样设计有效**：因为执行计划由定义生成而不是由人编写，所以「改口径要改 N 个下游」这件事在流程上不再存在——不存在需要人去记得改的第二处。这是自研真正买到的东西（不是「定制化」）：**把一致性从人的纪律变成结构的必然**。
- **代价**：① 维护成本持续且绑定引擎演进——每接一种计算引擎就要实现一套代码生成；② 迁移成本极高：定义、生成器、执行计划、指标存储全是自有，退出等于重写全部指标；③ 自造语言的文档与培训负担都在自己身上；④ 需要一支长期团队，这类团队规模普遍在数十人以上。【经验】
- **失效点**：当覆盖的计算引擎种类增加时，「定义驱动」的收益会被代码生成器的维护成本抵消：因为定义语言能表达的东西是所有目标引擎能力的**交集**，引擎越多，交集越小，可表达的指标类型越少，最终退化为「只在主干链路上有效」，长尾指标又回到手写 SQL——而长尾正是口径失控的高发区。
- **真实使用**：以下两条都是书内二手记录【经验】，不是一手出处，本节因此不断言其内部技术细节。字节：开源指标平台框架 OSCAR 的记录见 [§ 4.3](10-metric-platform-section-4-sec4.md) 工具链清单，字节自建平台的落地经过见 [§ 6](10-metric-platform-section-6-sec6.md) 案例 10.2（该案例里的平台名为 Bytemetric，与 §4.3 的 OSCAR 是否同一系统，本节不裁定）。美团：定义驱动的自研指标平台见 [§ 6](10-metric-platform-section-6-sec6.md) 案例 10.3。但这类模式的共同特征不依赖具体厂商——定义层只接受声明式定义、不向业务方暴露 SQL，执行计划由平台生成。**判断方法**：读者可检索这两家团队的公开分享或开源仓库，确认两件事——（a）指标定义是否只有声明式入口（不存在让业务方写 SQL 的旁路），（b）离线与实时链路是否由同一份定义生成；两条都为「是」才算真的落在本模式上，只有一条则更接近「声明式定义层 + 人工维护链路」并存的混合形态，而不是本模式的完整形态。【经验】

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 中大型企业 + 已有数仓分层规范 + 指标上万 | 阿里 OneMetric | 表达式式定义在万级指标下无法枚举与比对，一致性只能靠人工评审 | 是否存在可复用的**分层规范与原子度量池** |
| dbt 用户 / 数据团队 + 变换逻辑已在仓库里 | dbt Semantic Layer | 另立门户的配置台会立刻变成仓库之外的第二个真相 | 定义能否与数据模型**同仓库同流程** |
| 互联网产品 / 全栈团队 + 指标要嵌进产品 | Cube.js | YAML / 专有 DSL 的交付形态不适配前端消费与嵌入式多租户 | 消费方是**产品**还是人 |
| Looker 用户 + 业务方自助探索 | LookML | 换引擎意味着语义模型重写，只在既有投入已沉淀时才划算 | 语义模型是否已**绑定在该 BI 上** |
| AI 原生 / 业务自助 / 消费方不会写 SQL | AI 增强模式 | 定义没有唯一载体时，LLM 只会把「找不到」变成「找错」 | 指标元数据的**描述覆盖率**是否够 |
| 大型企业 / 定制化 / 实时与离线必须同源 | 自研 | 现成产品通常只覆盖离线或只覆盖实时，双链路同源要自己生成 | 是否有**长期维护代码生成器**的团队 |
| SaaS / 中小企业 / 没有平台团队 | 托管指标平台（Cube Cloud / Transform 一类） | 自研的门槛不在开发而在长期维护与迁移成本 | 是否愿意长期**承担平台成本** |

表里最常被误选的一对是**自研 vs dbt Semantic Layer**（或任何开源语义层）。中型团队常见的误判是「现成的不够用，不如自研」，但自研真正的门槛不是开发，而是长期维护代码生成器与未来的迁移成本。更糟的是自研的收益只在**覆盖率高**时成立：若平台只覆盖了主干指标，长尾仍在报表里手写 SQL，团队就付了平台成本却仍有两套口径——这比不建平台更差，因为它多了一层「我们已经统一了」的错觉。

### 3.4 组合模式：真实系统不会只用一种

**组合一：组合式定义（OneMetric）+ 生成器（自研或开源平台）**

- 构成：定义层用四要素组合（保证可枚举、可对比），执行层由平台按定义生成链路。
- 职责边界：定义层管「怎么组合」，生成器管「在哪算、怎么算」；业务方只碰前者。
- 运维代价：两层的表达能力互相牵制——生成器支持的引擎越多，定义语言能表达的东西越少。
- 适合规模：指标上万、有分层规范、离线为主并可延伸到实时的组织。【经验】

**组合二：dbt Semantic Layer（定义）+ 指标召回 + Text-to-Metric（消费）**

- 构成：定义在仓库里走 PR，消费端是自然语言；中间必须补一层「指标检索召回」，不能把全量 schema 直接灌给 LLM。
- 职责边界：仓库管定义与版本，召回层管「这次提问可能涉及哪几个指标」，LLM 只管在候选集内选择。
- 运维代价：多了一个必须随指标库增量更新的召回索引；召回率成为端到端准确率的上限，需要单独度量。
- 适合规模：指标千级到万级、消费方以业务方为主的 AI 原生场景。【经验】

**组合三：指标平台（定义与计算）+ 数据目录（指标血缘）+ Agent Tool（消费）**

- 构成：指标血缘（指标 → 表 → 字段 → 下游应用）注册进数据目录，指标 API 同时暴露给 BI 与 Agent。
- 职责边界：平台管口径与计算，目录管「这个指标从哪来、改了影响谁」，Agent 只调用不做解释性推理。
- 运维代价：两边需要统一的资产标识，否则「同一个指标」在两个系统里会各有一条记录。
- 适合规模：已有数据目录、指标需要与表级 / 字段级血缘打通的组织（见 [§ 7.3](10-metric-platform-section-7-sec7.md)）。【经验】

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 指标定义散落 | 同一个 GMV 在不同报表里数值不同，且无人能证明哪个对 | 争议只能靠职位而非证据裁决，决策前提不可靠 | 报表开发最直接的路径就是把 SQL 写在报表里，快且不需要协调 | 建立唯一载体（文件 / 平台）+ 发现分歧时以定义为准 |
| 无口径 Owner | 指标改了没人知道该通知谁，也没人签字 | 变更无人负责 → 变更随意 → 下游被动救火 | Owner 被当成行政字段，不绑任何流程 | 指标 Owner 具体到人，并挂在变更审批上 |
| 重复计算 | 同一指标在多个报表里有各自的物理实现 | 改一次口径要同步 N 份实现，漏改概率随 N 上升 | 复用成本高于重写成本时，每个团队都会重写 | 一次定义一次计算，消费方接 API 而不是接表 |
| 无血缘 | 指标改了，不知道会影响哪些报表与看板 | 变更风险在提交前不可见，只能在上线后由业务方反馈 | 指标血缘要跨定义层与 BI 层，采集比表血缘难 | 记录指标 → 表 → 字段 → 下游应用的血缘并纳入变更流程 |
| 过度细化 | 原子指标拆得极细，派生指标数量爆炸但复用率低 | 组合空间爆炸 → 检索与治理成本上升，用户找不到该用哪个 | 「拆得越细越灵活」是直觉，但组合复杂度是指数级的 | 按复用度收敛原子指标，公共指标下沉到公共层 |
| 无版本管理 | 定义被直接覆盖，历史数字变了却归因不了 | 无法区分「业务变了」还是「口径变了」，历史对比全部失效 | 平台没有把定义当成需要版本化的对象 | 定义版本化 + 变更留痕（变更人 / 时间 / 影响面） |
| 不与 AI 集成 | LLM 无法查询指标，只能猜表名或让用户手填参数 | 指标资产不被机器消费，在 Agent 场景里等于不存在 | 平台按「给人看的页面」设计，没有面向机器的接口与语义描述 | 指标 schema 机器可读 + 注册为 Agent Tool（Function Calling / MCP） |
| 忽视成本 | 高频实时计算账单失控，或看板打开要等很久 | 实时链路的成本随查询频次线性增长，且预算无人认领 | 「实时 = 先进」的直觉，没有为新鲜度分级付费的意识 | 按新鲜度分级（实时 / 分钟 / T+1），把成本与 SLA 一起定义 |

**「重复计算」**。它是其余反模式的物理载体：口径分裂之所以难以修复，不是因为没有制度，而是因为同一个口径有 N 份各自可执行的实现——制度管不住已经存在的 SQL。机制上，漏改概率随实现数量上升（N 份里改对 N-1 份，结果依然是错的，而且错得不明显），所以「重复计算」的代价不是浪费算力，而是**每一次变更都变成一次赌博**。修法的重点不是「要求大家复用」，而是让复用比重写更省事：一次定义 + 稳定的 API，比「去找谁的表能复用」更快。

**「无版本管理」**。它的暴露方式很隐蔽：数字突然变了，团队先怀疑数据、再怀疑业务，最后才想到是口径改过，而此时旧定义已经被覆盖、无法对比。机制上，指标是**时间序列的语义**——一旦定义可以无痕变更，所有跨期对比分析都失去基准，而跨期对比恰恰是经营分析最常用的动作。所以定义必须像代码一样版本化，并记录「谁在什么时候因为什么改了它」。

**「过度细化」**。它的暴露方式是**检索失效**：原子指标拆得极细，派生指标数量以组合方式膨胀，业务方在平台上搜「GMV」得到几十个近似条目，只能靠猜。机制上，原子指标的价值来自复用度，拆到无人复用的粒度后，每多拆一个都只增加组合空间而不增加复用；组合空间是乘法增长的，治理成本却要一件一件地付。修法是按复用度收敛原子指标，并让被多业务共用的指标自动下沉到公共层。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 报表硬编码 → 指标上千 | 报表里写死 SQL | 同一指标多份实现，改一次漏一次，报表间数字对不上 | 平台化定义（OneMetric / 语义层） | 需要先做指标盘点与原子指标收敛，否则只是把散落搬到平台里 |
| 数据团队自用 → 业务方自助 | dbt / YAML 定义 | 业务方走不了 PR 流程，等待时间超过容忍度就绕开 | 加服务化 / 自然语言入口 | 定义层之上要再养一层 API 与召回索引，并度量它的准确率 |
| 只做离线 → 离线实时同源 | 下推式语义层 | 实时链路另起一套实现，两套口径必然分叉 | 定义驱动生成双链路（自研） | 需要代码生成器与对拍校验，团队规模与维护成本上一个台阶 |
| 千级指标 → 万级指标 | 全量 schema 注入 LLM | schema 无法全部塞进 prompt，只能先召回再注入 | 指标检索召回层 + 注入 | 召回率成为准确率上限，需要单独建设与监控 |
| 单租户 → 多租户 SaaS | 单实例语义层 | 租户间指标命名与口径互相可见、互相污染 | 租户级命名空间 + 隔离的指标存储 | 定义、命名空间、API 三层都要加租户维度；越权必须在编译期挡住 |
| 稳态 → 口径频繁调整 | 无版本的定义 | 历史数字变了却归因不了，跨期对比失去基准 | 定义版本化 + 变更留痕 | 每次变更要记录影响面并通知下游，流程成本上升 |

这些跃迁的共同点是：**触发换模式的不止是「指标变多」，更是「定义载体的可达性」——业务方够不到定义、LLM 够不到 schema、实时链路够不到同源定义，三者都是可达性问题**。指标数量本身不会让模式失效，它只是让不可达这件事更贵。

### 3.7 自检清单

- [ ] 每个指标是否有一个**可执行定义的唯一出处**？出现第二份等价实现即视为口径分裂。
- [ ] 指标 Owner 是否**具体到人**？出现团队名即视为无主。
- [ ] 定义是否有版本历史？能否回答「这个指标上个月的定义是什么、谁改的、为什么改」。
- [ ] 是否存在比率型、集合型指标（转化率、留存、去重）？它们在四要素组合里能否表达？不能时是否有「非标指标」的登记出口？
- [ ] 指标血缘是否覆盖到「指标 → 表 → 字段 → 下游看板 / 应用」？只到表级时，改一个字段能不能列出受影响的指标？
- [ ] 消费方是接 API 还是接表？若大量下游直接读底层表，定义层等于不存在。
- [ ] 若使用预聚合，命中率是多少？有多少预聚合长期无人查询？
- [ ] 实时与离线两条链路是否做过定时对拍？对拍偏差超阈值时会不会阻断变更？
- [ ] LLM 查询指标时，输出是结构化意图还是 SQL？校验层是否会把不存在的指标名直接拒绝？
- [ ] 指标 schema 是否对 Agent 开放（Function Calling / MCP），并有可被检索的描述文本？
- [ ] 是否存在长期无人使用的僵尸指标？废弃机制是否真的执行过？
- [ ] 新指标从提出到可用要多久？若超过业务容忍度，业务方是否已经在报表里手写 SQL？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 指标上万 + 有数仓分层规范 | 阿里 OneMetric | 组合式定义让一致性可枚举、可检查；代价是比率 / 集合类指标表达不了 |
| 变换逻辑已在仓库、团队用 Git | dbt Semantic Layer | 口径变更复用工程流程，治理落地成本最低；代价是门槛挡住业务方 |
| 指标要嵌进产品、消费方是前端 | Cube.js | 定义即 API 契约，预聚合在物理层加速而不改动口径 |
| 已在商业 BI 上沉淀语义模型 | LookML | 用户在授权空间内自由组合，绕过成本高；代价是建模带宽与引擎锁定 |
| 消费方不会写 SQL、要自然语言 | AI 增强模式 | 封闭选择集让幻觉只能表现为「选错」；代价是召回率成为上限 |
| 离线与实时必须同源 | 自研 | 执行计划由定义生成，改口径不存在「漏改的第二处」；代价是长期团队与迁移成本 |

> 本节小结：指标平台的模式选择，最终由**「口径定义的唯一载体放在哪里、以及谁够得到它」**这一条约束决定——它同时决定了谁能改口径、变更走什么流程、消费方以什么形态接入；计算位置（下推 / 自生成）、消费入口（点选 / 自然语言）与指标粒度策略都是在这一条确定之后才展开的次级选择。任何让「第二份定义」得以存在的做法，无论效率多高，最终都会以两个无法对质的数字结账。
