## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表在「口径统一 / 复用度 / 血缘 / 服务化 / AI 集成 / 工程复杂度 / 实时性 / 业务门槛」八个维度上，给「报表硬编码 / BI 工具指标 / 指标平台 / AI 增强指标」四个候选打 1–5 分。问题不在分数高低，而在**这些数没有单位、也没有前提**：「工程复杂度 3 分」与「4 分」的差别，是多一个人、多一周，还是多一个必须常驻的服务？没有单位的分差不可复现，也无法在两家企业之间核对——同一套分数，20 人的公司与 2000 人的公司会得出相反结论。

更深一层的问题：**这些维度的权重会随规模反向变动**。核心指标几十个、消费端只有一个时，「工程复杂度」是主导项，BI 工具内建指标最划算；指标涨到几百个、消费端涨到十几个（看板、API、Agent）时，「口径统一」与「服务化」变成主导项，此时哪怕多养一层语义层也是省的。打分表把「你的规模」这个前提抹掉了，于是把**场景相关的结论**伪装成了**绝对结论**——而选型恰恰是「按场景挑」，不是「按总分挑」。

打分表还有一处层级混淆：它把「指标平台」与「AI 增强指标」并列成同一层的两个候选，但 AI 增强在机制上不是一种平台，而是**挂在指标 API 之上的一层召回与校验**（本章 §5.2.2）。没有可调用的指标接口，LLM 就没有「东西」可选，只能退回生成 SQL。把不同层的东西并列打分，会让人以为可以绕过指标平台直接跳到 AI 增强。

需要说明的是，打分表的八个维度本身并没有选错——它们恰好覆盖了选型时必须回答的问题。问题只在于「打分」这个动作替代了「回答」。**把每个维度还原成一个可核验的问题，它立刻变得可用**：

| 维度 | 换成可核验的问法 | 这个问题导向哪条机制 |
| --- | --- | --- |
| 口径统一 | 同一个指标在本企业目前有几个算法？变更时能不能列出受影响面？ | 7.3.2 口径的权威归属 |
| 复用度 | 一个口径改动要动几处？答案是 1 处还是 N 处？ | 7.3.1 定义与消费是否解耦 |
| 血缘 | 指标 → 表 → 字段的链路是自动采集还是人工登记？ | 7.3.2（登记的可持续性） |
| 服务化 | 业务方要一个新指标的取数，周期是几天还是几次点击？ | 7.3.1（消费路径是否独立） |
| AI 集成 | 指标描述的覆盖率是多少？召回率测过吗？ | 7.3.4 语义契约的机器可读性 |
| 工程复杂度 | 新增几个常驻服务？谁值班？升级窗口怎么排？ | 7.4 成本结构 |
| 实时性 | 新鲜度需求是 T+1、小时级还是分钟级？维度组合是固定还是长尾？ | 7.3.3 计算放在哪一侧 |
| 业务门槛 | 业务方能否自己找到并读懂指标，而不必问数据团队？ | 7.3.4（描述质量即准入门槛） |

所以本章的判据不是「给候选打分」，而是「先问清自己的约束，再看哪个候选的机制在约束下成立」。下面六条判据全部围绕这个顺序。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 能力边界 | 它**做不到**什么 | 报表硬编码做不到「口径变更影响哪些报表」，因为它根本没有独立的口径对象；语义层做不到表达任意加工逻辑，必须有回落路径 |
| 成本结构 | 成本随什么变量增长 | 语义层的成本由「指标数 × 维度组合数」主导，报表由「报表数」主导——增长变量不同，规模效应就反向 |
| 机制契合度 | 核心机制是否匹配你的数据形态与访问模式 | 预计算匹配「维度组合固定、查询高频」；运行时下推匹配「维度组合长尾、新鲜度要求高」 |
| 运维复杂度 | 要几个人、什么技能、多少常驻组件 | 语义层是常驻服务（需部署、监控、升级），BI 内建指标是既有工具的配置项 |
| 生态与锁定 | 离开它要付出什么 | 用 YAML / JavaScript 声明的口径可导出重写，写进 BI 工具私有模型的口径导出即丢失 |
| 演进风险 | 项目活跃度与路线图方向 | 定义层一旦停更，迁移成本由使用者承担。【公开】dbt Semantic Layer 2022 年推出，MetricFlow 由 Transform 于 2022 年开源、其后被 dbt Labs 收购并整合进该语义层（来源：dbt Labs 官方文档「About the dbt Semantic Layer」与「MetricFlow」，docs.getdbt.com；开源与收购的具体时间线以 dbt Labs 官方公告为准）；【经验】活跃度要看最近一年的发布与提交频率，不看路线图 |

### 7.2 候选方案全景

打分表对比的四个候选全部保留（报表硬编码 / BI 工具指标 / 指标平台 / AI 增强指标），并按本章 §4.3 的工具清单把「指标平台」与「AI 增强」展开为具名实现。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 报表硬编码（选型基线） | 指标定义与展现写在同一份 SQL 里 | 口径没有独立载体，改口径 = 改报表 | 指标数少、消费端单一 | 无许可成本，人力成本计 |
| BI 工具指标 | 口径建在 BI 工具的模型层内 | 定义是工具私有模型，消费必须经过该工具 | Looker（LookML）、QuickSight、Quick BI 用户 | 随席位 / 计算计费 |
| 开源语义层 / 指标平台 | 定义独立、以 API 对外 | 声明式定义 + 查询时编译成 SQL（headless BI） | dbt Semantic Layer + MetricFlow、Cube / Cube.js、Airbnb Minerva、字节 OSCAR | 开源为主，部分厂商提供托管版 |
| 商业 / 自研指标平台 | 组织级指标资产治理 | 定义层 + Owner / 口径审批 / 血缘 / SLA 一起上 | 阿里 DataWorks OneMetric、字节 DataFinder、腾讯 WeData、美团与网易严选自研、Transform、Alation Metric Studio | 商业授权或自研人力 |
| AI 增强指标（挂在上面某一层之上） | 自然语言取数与智能治理 | 把「找指标」变成可度量的召回问题 + 校验层 | Snowflake Cortex Analyst、Databricks Genie、AWS QuickSight Q、阿里 Quick BI + 通义、Looker + Gemini | 云厂商功能项或独立产品 |

**这些候选其实分三族**：第一族「定义与消费同处一地」（报表硬编码、BI 工具指标）；第二族「定义独立、消费分离」（开源语义层、商业 / 自研指标平台）；第三族是挂在第二族之上的检索与校验层（AI 增强）。**同族内部差异小、跨族差异大**——dbt Semantic Layer、Cube、Minerva 之间的差别主要在定义语言与下推实现，而族与族之间的差别是「口径到底是不是一个独立对象」。先分族再选，能省掉一半比较。

还有两个候选不在上表里，但每次选型都绕不开它们：

- **自助取数 / 直连明细 SQL**（BI 工具里的 ad-hoc 查询）。它不解决口径，但它决定了前三族的实际压力：**只要业务方能随意直连明细表写 SQL，任何口径治理都会被旁路**——因为绕过定义层永远比走定义层快。所以「允不允许直连明细、通过什么通道直连」是选型时必须一起回答的问题，而不是上线后补的权限配置。
- **用汇总层宽表承载口径**（把口径做进 DWD / DWS 或宽表，表名即口径）。它在很多团队里是事实上的现状。与独立语义层的差别是：**口径变更在这里表现为一次 ETL 变更而不是一次定义变更**，于是「改了口径」与「补了数据」在调度日志里长得一样，事后追溯时无法区分。它的成本低、上手快，代价是口径的可解释性随时间下降。

### 7.3 机制差异：为什么它们表现不同（核心节）

四个机制维度：定义与消费是否解耦（7.3.1）、口径的权威归属（7.3.2）、计算放在写入侧还是查询侧（7.3.3）、语义契约的机器可读性（7.3.4）。

先给四个候选在四条机制上定位一次，后面的展开都围着这张表：

| 机制维度 | 报表硬编码 | BI 工具指标 | 语义层 / 指标平台 | AI 增强 |
| --- | --- | --- | --- | --- |
| 定义与消费 | 同一处 | 同一工具内 | 解耦（多端消费） | 解耦，且多一个消费方 |
| 口径权威 | 无主 | 工具或数据团队 | 可到人的 Owner + 审批 | 同左（机器只出候选） |
| 计算位置 | 查询时，面向单张报表 | 查询时 + 工具缓层 | 预计算 / 下推 / 混合 | 不改执行，只改入口 |
| 机器可读契约 | 无 | 工具私有模型 | 有（YAML / JS 声明） | 有 + 召回层 + 校验层 |

#### 7.3.1 定义与消费是否解耦

**机制是什么**：口径是一个独立于展现层的声明对象，查询时由语义层编译成 SQL——定义一次，BI、API、LLM 多端消费。

**各候选的实现差异**：

| 候选 | 定义存在哪 | 消费路径 | 改口径要动什么 |
| --- | --- | --- | --- |
| 报表硬编码 | 报表 SQL 内部 | 只能看这张报表 | 找到所有写了同一口径的报表逐份改 |
| BI 工具指标 | 工具私有模型 | 必须经过该工具 | 改模型 + 重新发布受影响的看板 |
| 开源语义层 | 版本控制的 YAML / JS | REST / GraphQL / JDBC 接口 | 改定义文件 → 走 PR → 全消费端同时生效 |
| AI 增强 | 不新增定义层 | 自然语言 → 指标 API | 同上，另需同步召回索引 |

**由此必然导出的性质**：**因为定义与消费解耦，所以同一份口径能同时被看板、业务系统、Agent 消费，口径变更只需改一处，且「谁在什么时候把过滤条件从已支付改成已发货」在版本历史里可查；代价是多了一层编译——语义层的表达力弱于手写 SQL，窗口函数、递归、跨周期复杂运算这类加工往往表达不出来，只能先把中间结果物化成表、让语义层只做聚合。** 这一条代价在实践中非常具体：它意味着你可能需要一个额外的调度层来生产中间表，而这层调度不在语义层工具的职责范围内。

**公开证据**：【公开】dbt 的指标以 YAML 声明并区分 simple / derived / ratio / cumulative 等类型（来源：dbt Labs 官方文档「About the dbt Semantic Layer」与「MetricFlow」，docs.getdbt.com；dbt Semantic Layer 2022 年推出、MetricFlow 2022 年开源）；【公开】Cube 把 measure / dimension 声明为 schema、对外只暴露 API（来源：Cube 官方文档中 measures / dimensions / filters 的设计说明，docs.cube.dev；该文档随版本更新，没有单一发布年份，能力请按当前版本核对）；【公开】Airbnb 以「指标定义与查询分离」实现 Headless BI（来源：Airbnb 工程博客《Minerva: Building a Scalable Metrics Platform》，2020 年前后）；【经验】字节 OSCAR 的定位与定义形态在书内只有二手记录，且两处归属不一致（[§4.3 工具链清单](10-metric-platform-section-4-sec4.md) 把它记为字节的开源指标平台，[§6 案例 10.1](10-metric-platform-section-6-sec6.md) 记录的五要素则挂在阿里 OneMetric 名下，详见 7.3.2），故本节不把它当一手出处引用。**具体某版本支持哪些能力，请以官方文档当前版本为准**。

**失效条件**：消费端只有一个、指标数在几十个以内时，解耦的收益为负——你付出了编译层与定义登记流程，却只服务一张报表。这时「全面上语义层」是最常见的一次过度投资。

**判定方法**：挑出当前最痛的三个指标，逐个问「改它的口径要动几处、要找到几个人签字」。答案在三处以上，说明口径没有独立载体；答案稳定为一处且改动可回滚，解耦才算成立。

#### 7.3.2 口径的权威归属：定义归谁维护

**机制是什么**：谁有权修改口径，决定了口径冲突是「流程问题」还是「架构问题」。

**各候选的实现差异**：

| 归属模式 | 谁签字 | 谁来发现冲突 | 口径变更的传播 |
| --- | --- | --- | --- |
| 无主（报表硬编码的自然状态） | 没人 | 冲突发生后才被发现 | 靠通知，漏通知即分叉 |
| 数据团队集中（平台制） | 平台 | 平台在登记时发现 | 平台统一改，业务方排队等 |
| 业务方 Owner（OneMetric 一类） | 具体到人 | 评审与血缘比对 | 定义层改，下游自动跟随 |
| 机器产出候选（AI 增强治理） | 仍必须是人 | 机器列疑似重复清单 | 机器只出建议，不进定义层 |

**由此必然导出的性质**：**因为定义是版本化的声明对象，所以变更可以 diff、可以评审、可以回滚，口径从「谁记得」变成「谁签字」；代价是每个指标都要走登记流程，长尾指标的登记成本高于直接写一行 SQL——这个成本差正是「口径统一」在长尾上反复失败的原因。** 本章 §3.7 的判据「出现团队名即视为无主」同源：无主的东西不会有人为它的口径负责。

**公开证据**：【经验】「把口径写成结构化要素」这一形态在书内是有记录的——[§6 案例 10.1](10-metric-platform-section-6-sec6.md) 把「Owner / Statistic / Caliber / Attribute / Reference」五要素列为阿里 OneMetric 的核心组件，而 [§4.3](10-metric-platform-section-4-sec4.md) 又把 OSCAR 记为字节的开源指标平台；两处归属不一致，且都只是书内二手记录（§3.2.6 对同一线索的结论也是【经验】），故本节按【经验】而不按【公开】引用，也不裁定这五要素出自谁；其设计与归属可按厂商公开仓库与产品文档自行核对。【公开】同一脉络的另一条建模法——阿里 OneMetric 的「原子指标 + 修饰词 + 时间周期 + 维度」——有公开成书出处（来源：阿里巴巴数据技术团队《大数据之路：阿里巴巴大数据实践》，该书是该方法论的标准出处，见 [§ 8 参考来源](10-metric-platform-section-8-sec8.md)；出版信息可按书名核对），主文件 [§1.4 演进历程](10-metric-platform.md) 亦收录。【经验】Owner 制在实践中的可持续性随组织规模变化，无单一权威来源，故本节只给判定方法而不给覆盖率数值。

**失效条件**：登记与复核的人力是线性的，指标数量的增长常常不是。当指标过千、增长快于治理人数时，Owner 制会退化成「有 Owner 字段但没人真的管」——此时要压缩的是登记对象的范围（只强制治理核心指标），而不是加人。

**判定方法**：在指标库里随机抽 20 个指标，数一数有几个能追到一个具体的、还在职的人。低于半数时，Owner 制只是字段；高于八成时，制度才真的在运转。

#### 7.3.3 计算放在写入侧还是查询侧

**机制是什么**：把计算成本放在哪一侧——写入时算好（预计算 / 物化）还是查询时再算（下推到 OLAP / 数仓）。

**各候选的实现差异**：

| 计算位置 | 代表实现 | 查询延迟 | 新鲜度 | 能查的维度组合 |
| --- | --- | --- | --- | --- |
| 写入侧预计算 | 物化到 ClickHouse / Doris / StarRocks，或数仓物化视图 | 低且稳定 | 受物化调度约束 | 仅限被物化的组合 |
| 查询侧下推 | 语义层把聚合下推到底层引擎 | 随扫描量波动 | 受底层表约束 | 任意组合 |
| 混合 | 高频组合预计算 + 长尾下推 | 高频低、长尾波动 | 分层 | 常见的都有 |

**由此必然导出的性质**：**因为预计算把成本挪到写入侧，所以查询延迟低且可预测，代价是必须事先选定「指标 × 时间粒度 × 维度组合」的子集，没选中的组合退回全表扫描；因为运行时下推，所以任意维度组合可查、新鲜度只受底层表约束，代价是扫描量随并发用户数线性增长。** 这是两条相反方向的代价，选型时看你的读多还是写多、维度组合是固定还是长尾。

**量化示例（推算）**：一个 500 个指标的指标库，若为每个指标物化 30 个常用维度组合，每日新增物化任务约 1.5 万次【推算：500 × 30 = 15,000】；设每次物化平均扫描 1 GB，则每日扫描约 15 TB、每月约 450 TB【推算：15,000 × 1 GB/日 × 30 日 = 450 TB】。按扫描量计费 $5/TB 量级（各厂商与合约差异较大，请以当前价目为准）推算，仅物化一项每月约 $2.2k【推算：450 TB × $5/TB ≈ $2,250】。这个数本身不大，它说明的是：**预计算成本由「维度组合数」主导，而不是由「指标数」主导**——控制组合数比优化单条 SQL 有效得多。

**公开证据**：【公开】预计算在各引擎的官方文档里都是正式条目——ClickHouse 官方文档的 Materialized View 章节（clickhouse.com/docs）、Apache Doris 官方文档的物化视图与 ROLLUP 章节（doris.apache.org/docs）、StarRocks 官方文档的物化视图章节（docs.starrocks.io）；这三份都是随版本更新的产品文档，没有单一发布年份，语法与能力请按当前版本文档核对。【公开】按扫描量计费的定价结构只在按量计费的引擎上成立，可在其公开定价页核验（如 Google Cloud BigQuery 的按需查询定价页，按扫描字节数计费）；按资源计费的引擎是另一套成本函数——Snowflake 按虚拟仓库规格与运行时长计费、Amazon Redshift 按预置节点容量或 Serverless 容量单元计费，两者都不能按扫描 TB 折算；计费单位与单价请以各家定价页当前版本为准。价格还随区域、合约与版本变化，故本节按 $5/TB 量级给推算而不引用具体单价。

**失效条件**：维度基数极高（用户级标签、商品级维度）或口径频繁变更时，预计算的重算成本会把收益吃掉——每次口径变更都要重跑全部受影响组合。

**判定方法**：统计最近一个月的查询里，有多大比例命中了预计算表。命中比例高，说明组合选得准；大量长尾查询落到全表扫描时，往预计算里继续加组合通常不如把长尾交给查询侧下推。

#### 7.3.4 语义契约的机器可读性

**机制是什么**：LLM 能不能选对指标，取决于「提问 → 指标」这一步是否存在可检索、可校验的契约。

**各候选的实现差异**：

| 契约强度 | 形态 | 错误的形态 | 谁先发现错误 |
| --- | --- | --- | --- |
| 无契约 | LLM 直接生成 SQL | 语法正确、语义错误的查询，数字看着正常 | 只有懂口径的人 |
| 仅 schema 注入 | 全量指标 schema 进 prompt | 指标多时塞不进上下文，选错指标 | 使用方比对口径 |
| 召回 + 注入 + 校验层 | 先检索候选，再注入，输出被枚举校验 | 选错近似指标，或时间范围落不到分区 | 系统 / 口径回显 |
| 上述 + verified queries | 附带人工核验过的问答样例 | 显著减少选错 | 系统 |

**由此必然导出的性质**：**因为候选集被约束成「指标名 + 维度 + 枚举取值 + 时间范围」的封闭集合、且计算由平台执行，所以幻觉的表现形式从「算出一个错误的数」退化成「选错指标」或「被校验层拒绝」——两种都能被发现；代价是端到端准确率的上限等于召回率**，没被召回的指标模型永远选不对，而召回率取决于指标描述（一句话口径）的写作质量，那是 Owner 的人力工作，不是平台能生成的。

**公开证据**：【公开】Snowflake Cortex Analyst 以语义模型 YAML 为输入，其中包含 tables / dimensions / measures 与 verified queries 段（Snowflake 官方文档自 2024 年起可查）；【公开】Databricks Genie 的自然语言入口有 2024 年官方发布材料；【公开】自然语言到结构化查询的公开评测基准可按关键字自行检索（Spider、BIRD 等），它们测的是「给定 schema 下的执行准确率」——**换一套 schema 结论不可搬运**，这正是本章不引用任何「准确率 X%」宣传口径的原因。

**失效条件**：指标库没有结构化描述时，召回层与模型一起失效。本章 §5.2.4 把它写成一条硬判据：**机器辅助的成熟度不可能高于指标定义的完整度**。

**判定方法**：固定一组真实提问（必须包含长尾指标与近似指标），逐条记录「正确指标是否出现在前 K 个候选里」——这个数就是召回率。它必须与最终准确率分开监控，否则出错时判断不了该改检索还是该改模型。

### 7.4 成本结构对比（不是价格表，是成本函数）

四个候选的成本函数形式不同，主导项也不同：

```
报表硬编码      成本 ≈ 报表数 × 单报表开发人力 + 口径分叉的决策成本
BI 工具指标     成本 ≈ 席位许可 × 人数 + 模型维护人力 + 工具绑定的迁移成本
语义层/指标平台  成本 ≈ 常驻平台成本 + f(指标数) + g(维度组合数 × 物化频次) + h(查询并发) + 元数据维护人力
AI 增强        成本 ≈ 语义层全部成本 + 召回索引维护 + 评测集建设 + token(候选注入量 × 提问量)
```

| 候选 | 主导项 | 隐性成本（不体现在账单上） |
| --- | --- | --- |
| 报表硬编码 | 报表数 × 人力，线性 | 口径冲突：同一名字多个算法，决策时反复争论，无单一账单 |
| BI 工具指标 | 席位许可 × 人数 | 绑定：口径不可导出，换工具等于重写全部模型并重新对账 |
| 语义层 / 指标平台 | 维度组合数 × 物化频次（见 7.3.3 的推算） | 语义层表达力不足导致的「回落物化表」，这一层调度往往无人负责 |
| AI 增强 | token 与召回索引随指标库规模增长 | 评测集建设：没有可抄的公开基线，必须自建固定问题集 |

**两条推导链**：

- 维护面随指标数**线性**增长（登记 + 复核的人力），而口径冲突的期望面随指标数近似**平方**增长【推算：n 个指标两两可能冲突，组合数 n(n-1)/2 量级；冲突是否真的发生取决于命名与业务重叠度，故这是上界而非实际值】。两条曲线相交的位置，就是**「引入独立定义层是否划算」的分界**——量级在**几十到一两百个核心指标**之间【经验：多数团队在 50–200 个核心指标时，靠约定与评审还能维持口径一致，超过后口径协调成本开始超过工具成本；具体位置取决于团队的人均指标数与业务重叠度】。
- AI 增强的常驻成本可按候选注入量估算：每条候选指标描述注入 100–200 token【经验】，每次注入 50 条候选约 7,500 token【推算：50 × 150 = 7,500】；提问量上万次时这是一笔可测算的月度成本，且它与指标库规模同向增长。

**底层引擎换一个，成本函数的主项会换**：

| 底层 | 计费 / 成本变量 | 主导项 | 换引擎时语义层要改什么 |
| --- | --- | --- | --- |
| 云数仓（Snowflake / BigQuery / Redshift 一类） | 计算按用量（扫描量 / 仓库时长 / 预置容量，因引擎而异）、存储按容量 | 查询扫描量与并发 | 方言与函数差异，需逐条核对定义里的 SQL 片段 |
| 自建 OLAP（ClickHouse / Doris / StarRocks） | 固定集群成本为主 | 集群规格与常驻节点数 | 方言差异 + 需自行管理扩缩容与副本 |
| 混合（预计算入 OLAP、明细留数仓） | 两边之和 | 数据同步链路 | 需保证两侧口径一致，多一条一致性校验 |

这条表的意义是：**语义层把「定义」与「执行」分开之后，执行侧就是一个可替换的部件**——但替换的前提是你的定义里没有写死底层方言的特有函数。这也是一条真实的隐性成本：定义里嵌入的自定义 SQL 片段越多，换引擎的成本越高。

**怎么用这个成本函数**：不要先算总价，先问「我的成本随哪个变量增长得最快」。答案是维度组合数（7.3.3）、还是席位人数、还是报表数——这决定了你该优化的对象。在维度组合数主导的场景里，把预算花在减少物化组合上，比换一个更快的引擎收益大得多。

### 7.5 决策树（每个分支都要有阈值依据）

```
你要解决的是「口径」问题，还是「一张固定报表」？
  │
  ├─ 只要一张固定报表 → 报表 / BI 直连，不引入语义层
  │
  └─ 要统一口径 → 核心指标数（需要统一口径、被多方消费的指标）
        │
        ├─ < 50 且消费端只有 1 个 → BI 工具内建指标；需要嵌入式 API 时用 Cube.js
        │
        ├─ 50–500，1–3 个团队 → dbt Semantic Layer / Cube 一类语义层
        │        └─ 已经重度使用 dbt → dbt Semantic Layer；要把指标嵌进自有产品 → Cube
        │
        ├─ > 500，跨 BU，需要指标级血缘 + Owner + 审批 → 自研平台，或 OneMetric / DataFinder / WeData 一类平台
        │
        └─ 任一规模，要自然语言取数
               ├─ 指标定义结构完整（一句话口径 + 来源字段 + Owner）→ Cortex Analyst / Genie / Quick BI + 通义
               └─ 定义不完整 → 先补定义，不要先上 LLM
```

**阈值依据**：

- **「是不是口径问题」**：判据是「同一个名字在不同消费端是否已经算出不同的值」。只有出现分叉时才需要独立口径对象；未出现分叉时，语义层是纯成本（7.3.1 的失效条件）。
- **< 50**：来自 7.4 两条曲线的交点区间下沿（50–200，取更保守的一侧【经验】）。低于这个量级，登记与复核的人力成本高于口径冲突的期望损失。
- **消费端只有 1 个**：解耦的收益来自多端复用，单一消费端时编译层不产生任何复用价值（7.3.1）。
- **50–500 用语义层**：语义层的定义文件在这个量级仍可由 1–2 人维护，且不需要指标级审批流与血缘治理【经验：超过约 500 个核心指标后，跨团队的口径协调开始需要专职角色，此时「定义层 + Owner + 审批」的平台固定成本才被摊薄】。**「1–3 个团队」这个条件**的依据在 7.3.2：团队数少时口径冲突能在评审里当场发现，团队数多时冲突面增长快于评审带宽，需要的是平台化的审批与血缘，而不是更快的查询。
- **已经重度使用 dbt**：dbt Semantic Layer 的指标与 dbt 的模型、测试共用同一份 YAML 与 CI，复用既有工程的边际成本低于换栈（来源：dbt Labs 官方文档「About the dbt Semantic Layer」与「MetricFlow」，docs.getdbt.com；dbt Semantic Layer 2022 年推出，MetricFlow 由 Transform 于 2022 年开源、其后被 dbt Labs 收购并整合进该语义层）。
- **树上两处 Cube 落点（`< 50` 支的「需要嵌入式 API 时用 Cube.js」，与 dbt 支的「要把指标嵌进自有产品 → Cube」）**：这两处依据的不是规模阈值，而是**要一份对外的 API 契约，还是 BI 层里的一个展现对象**。嵌入式场景要把指标嵌进自有产品的界面与后端，需要的是稳定的接口、鉴权与配额边界，而 Cube 的机制正是把 measure / dimension 声明成 schema、对外只暴露 API（7.3.1 的公开证据）。所以「指标少 + 要嵌入」落在 Cube.js 的轻量用法，「已用 dbt + 要嵌入」落在 Cube 做指标服务；这也是 7.6 表格「API-first 定位与嵌入式场景更贴」那一行的依据。它不随 < 50 / 50–500 / > 500 三档移动——三档只决定要不要上语义层，这一条决定上哪一族的语义层。
- **> 500 且跨 BU**：到达这个规模后，真正的瓶颈不是查询性能而是**谁改口径谁通知谁**——需要 Owner 制度、审批流与指标级血缘，这些是语义层工具本身不提供的（7.3.2）。
- **指标定义结构完整**：来自 §5.2.4 的判据「机器辅助的成熟度不可能高于指标定义的完整度」。定义不完整时上 NL 入口，产出的是无人消化的召回清单与静默选错。

**把树走一遍（一个常见的选型场景）**：一个已用 dbt 约半年的团队，核心指标在一百多个的量级，业务方要求「能在对话里问数」。

1. 第一个问题：是口径问题吗？——是，同一个「活跃用户」在不同看板上已经算出不同的值。走「要统一口径」分支。
2. 核心指标落在一百多个：在 50–500 区间内，且消费端不止一个（看板、API、Agent、数据导出）。走语义层分支。
3. 已重度使用 dbt：选 dbt Semantic Layer，复用既有 YAML 与 CI，而不是换 Cube。
4. 业务方要对话问数：先查指标定义结构完整度——这些指标里有多少有一句话口径 + 来源字段 + Owner？若不足半数，**这一步的输出不是选一个 NL 产品，而是一份定义补全的排期**。
5. 定义补全后，再把 NL 入口作为一种消费端挂上去，并用固定问题集测召回率。

这个场景里最容易做错的，是把第 4 步跳过——它不产出任何可演示的东西，所以最容易被排在进度表末尾。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 小团队、指标几十个、只有一张看板 | BI 工具内建指标 | Cube.js 自建 API | 语义层的编译层收益覆盖不了定义登记成本 |
| 已重度使用 dbt、100–500 个指标 | dbt Semantic Layer | Cube | 换栈要重建已跑通的模型与测试 |
| 要把指标嵌进自有产品对外提供 | Cube | dbt Semantic Layer | API-first 定位与嵌入式场景更贴 |
| 万级指标、跨 BU、要指标级血缘与 Owner | 自研平台 / OneMetric / DataFinder / WeData | 语义层 + 数据目录 | 纯语义层不提供审批流与 Owner 制度 |
| 数据不能出云 / 需私有化 | 开源语义层 + ClickHouse / Doris / StarRocks | 云厂商 AI 增强 | 云厂商的 NL 入口绑定在其数据平台上 |
| 需要自然语言取数且定义已结构化 | Cortex Analyst / Genie / Quick BI + 通义 | 自建 Text-to-Metric | 自建要额外维护召回索引与评测集 |
| 业务方强烈要求直连明细做自助分析 | 语义层 + 受控直连通道 | 开放明细表权限 | 无口径层的直连会让治理被旁路（7.2） |
| 团队小、ETL 人力本就充足 | 汇总层宽表承载口径 | 轻量语义层 | 宽表口径无法区分「改口径」与「补数据」 |

**五条常见组合**（每条都要说清职责边界与运维代价）：

1. **指标平台 + OneService**：指标平台负责「定义与计算」，OneService 负责「统一的对外服务与鉴权」。边界是指标 API 由谁暴露——两边都做会出现两份 API 与两套配额。运维代价是两套服务的版本需要一起发。
2. **指标平台 + RAG**：指标段答「是多少」（走指标 API），文档段答「为什么」（走向量检索）。边界必须在答案里显式标注哪一半来自指标、哪一半来自文档，否则一次混合回答的错误无法归因。运维代价是文档段的时效性需要单独维护。
3. **指标平台 + Agent**：Agent 把指标 API 当工具调用。边界是 Agent 只做「选工具 + 组织答案」，不重算指标。运维代价是每个新指标都要确认它的描述是否足以被 Agent 选中。
4. **指标平台 + 数据目录**：目录负责「可发现」，指标平台负责「可计算」。边界是**指标定义只有一个权威副本**——把定义同时登记在两处，就制造了第二个口径来源。运维代价是两处的同步与归属字段对齐。
5. **指标平台 + 统一查询网关**：网关负责跨源路由与方言适配，指标平台负责定义与语义。边界是下推一致性——同一指标跨不同源必须得到同一口径的值，这需要在网关层做一致性校验。运维代价是多了一层查询改写，排障链路变长。

这五条组合有一个共同的失败形态：**边界不清时，两边都做或两边都不做**。前者的表现是同一份口径出现两个副本（目录里一份、平台里一份），后者的表现是「指标 API 有了，但没有鉴权、没有配额、没有 SLA」。**判定方法**：把每条组合画成一条链路，在每一个交接点上写清「谁负责、失败时谁收到告警」。写不出责任人的交接点，就是三个月后出问题的地方。

### 7.7 选错的代价与迁移成本

**反模式：先上 LLM，后补定义** —— 症状：PoC 用 20 个描述完整的核心指标跑得很好，上线后长尾提问的召回为空或选中近似指标。后果：出现静默失败（数字正常、口径不同，肉眼看不出来），业务方开始不信任任何自然语言取数结果。正确做法：先按 §5.2.4 的顺序补齐「一句话口径 + 来源字段 + Owner」，再开 NL 入口——定义完整度是这类能力的上限。

**反模式：把 BI 工具内建指标当语义层** —— 症状：口径写在工具的私有模型里，只有该工具能消费。后果：Agent 取数必须绕过 BI 工具、业务方把口径复制进自己的 SQL，口径重新分叉成两份。正确做法：要么接受「只有一个消费端」的定位，要么把口径挪到独立的定义层。

**反模式：把预计算当性能的默认解** —— 症状：为每个指标铺满维度组合。后果：物化任务与存储按组合数而非指标数增长（7.3.3 的推算），重算挤占底层引擎资源；口径一改，全部受影响组合重跑。正确做法：先量出前 20% 的高频组合做预计算，其余走查询侧下推。

**反模式：把指标平台建成第二个数据目录** —— 症状：指标定义登记在目录里，计算配置留在平台里，两边各存一份「口径」。后果：改口径时只改了一边，两边从此不一致，而**不一致比缺失更难发现**——搜索时两边都能搜到，读到哪份取决于入口。正确做法：定义只保留一个权威副本，另一处只存引用（编号或链接），并让引用在目标缺失时报错。

**换成另一个要动什么**：

| 从 → 到 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 报表硬编码 → 语义层 | 无（底层表不动） | 全部报表改为调指标 API | 新增语义层服务与部署 | 中：定义语言 + 口径登记流程 |
| BI 工具内建指标 → 独立语义层 | 无 | 私有模型重写为标准定义 | 新增语义层 + 看板改数据源 | 高：口径需重新对账 |
| 自研平台 → 开源语义层 | 无 | 指标定义逐条迁移并回归 | 替换服务 | 中：失去自有的审批流能力 |
| 语义层 → AI 增强 | 无 | 无（新增一层） | 新增召回索引与固定评测集 | 中：评测集建设与召回率监控 |

量级说明【经验】：前三行的主要工作量都在「查询改写 + 口径对账」上，与指标数量成正比；**没有真正「无痛」的一行**——只要口径曾经分叉过，换栈就必然包含一次人工对账，这是选型时最容易被低估的一块。

**什么时候不该换**：出现下面任意一条时，迁移的期望收益为负，先把现状治理好更划算。

- 口径还没有分叉，只是「担心以后会分叉」——此时迁移买到的是保险，不是收益。
- 指标数在几十个以内且消费端单一——换栈后仍要维护那套定义登记流程，纯增成本。
- 团队里没有人能长期负责定义层——语义层是常驻服务，没有主就会在一年内变成僵尸组件。
- 换栈的主要动机是「追新」而不是「某个具体指标算错了」——说不出当前的错误场景，就说不清新方案怎么消除它。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 指标几十个、单一消费端 | BI 内建指标或 Cube.js | 解耦在这时只有成本、没有复用收益 |
| 已用 dbt、指标上百 | dbt Semantic Layer | 与既有模型 / 测试 / CI 共用一份定义 |
| > 500 且跨 BU | 自研或商业化指标平台 | 瓶颈是权属与审批，不是计算 |
| 维度组合固定、查询高频 | 写入侧预计算 | 预计算成本由组合数主导，可控 |
| 维度组合长尾、要求新鲜 | 查询侧下推 + 少量预计算 | 下推保证任意组合可查 |
| 要自然语言取数 | 先补定义，再上召回 + 校验层 | 准确率上限 = 召回率，召回依赖描述 |
| 指标口径写在宽表里、追溯困难 | 抽出口径到独立定义层 | 宽表把「改口径」与「补数据」混成同一件事 |
| 业务方在直连明细表写 SQL | 收通道到指标 API 或受控直连 | 绕过定义层的路径永远更快，治理必被旁路 |
| 想换栈但没有具体的算错案例 | 先不换，先量化错在哪 | 说不出错误场景，就无法验证新方案消除了它 |

> 本节小结：这几个候选之间**唯一真正起决定作用的差异，是口径有没有成为一个独立于消费端存在的对象**。它一旦独立（有版本、有 Owner、有状态），复用、服务化、血缘、AI 取数都只是挂在它上面的能力；不独立时，后四样各自都要重造一份口径，而每一份都是一次新的分叉。其余差别——预计算还是下推、开源还是自研、要不要 AI——都是可逆的战术选择，只有这一条是结构性的。
>
> 💡 **思考锚点**：本节把「引入独立定义层是否划算」的分界落在**几十到一两百个核心指标**——它是维护面（随指标数线性）与口径冲突面（随指标数近似平方）两条曲线的交点。先数你自己的核心指标（需要统一口径、被多方消费的那些）有几个，再拿这个数去撞这条分界：落在 **50 以下**且消费端只有 1 个时，7.5 树为什么把你指向 BI 工具内建指标、此刻上语义层又为什么是纯成本？落在 **50–500 且消费端不止一个**时，你打算拿什么去为 7.4 的 `f(指标数)` 与 `g(维度组合数 × 物化频次)` 这两项付账？
