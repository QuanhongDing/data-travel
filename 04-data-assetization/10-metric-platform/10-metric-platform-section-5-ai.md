## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单在这门主题上最容易骗人的地方是**它看起来每一条都已经落地**：Cortex Analyst、Genie、Quick BI + 通义都有 2024 年的发布材料，dbt Semantic Layer 与 Cube 都有正式文档。缺的不是「有没有这个东西」，而是三件**可核验**的事：它在哪一份 release note 或公开规范里、有没有第三方（非厂商）的生产案例、接口一年内变过几次。「Text-to-Metric 主流化」今天已经有可用的商业产品与公开文档（下表 L2），而「LLM 自动推荐指标定义」连「怎么算做到了」都还没有公认口径（下表 L3）。本节按 L1 / L2 / L3 分级，三条判据全中才是 L1：① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定。L2 = 已可用但接口或生态未稳，或只有厂商自有案例；L3 = 仅路线图、论文或厂商演示。「感觉成熟」不算判据，因为它在评审会上无法被复核。判据里特意写「第三方（非厂商）」，是因为本主题的商业产品密度极高，而**产品页上的能力清单与「在你的指标库上能不能答对」是两件事**。

第二个坑是**能力名、协议名与产品名的混淆**。「Function Calling」「MCP」「Agent + 指标 API」被并列成三种技术选项，但前两者是同一个机制（工具调用）的两套协议实现，第三个是使用场景——三者不在同一个分类轴上。同类风险还有「语义层」这个词：它在 dbt Semantic Layer、Cube 的建模层、LookML 里指的**不是同一个东西**（有的是仓库里的定义文件、有的是 API 契约、有的是 BI 引擎的建模语言，见 [§3](10-metric-platform-section-3-sec3.md) 的四种定义载体）。**能力名与产品名混写，是本节写错的唯一高频原因**；拿不准时本节只写能力，并给出「去哪个文档的哪一节核」的判定方法，而不是断言某产品支持某特性。

第三个要说清的是本节结论的方向：**本主题里「最像 AI」的那几项，成熟度反而最低**。原因是它们的成败不取决于模型，而取决于 AI 之前就存在的两件基础设施——**指标定义的唯一载体**（§3.1 的第一条约束）与**指标描述的覆盖率**。模型只是把对这两件事的依赖暴露了出来：定义没有唯一载体时，自然语言入口不会让口径变统一，只会让「找不到」变成「找错」；描述缺失时，模型只能靠指标名字猜。所以在判级时，**凡是需要先补一套新基础设施才能成立的方向，都不算 L1**。

第四点是评级的落点必须说清：**下表里没有任何一条方向同时满足 L1 的三条**（表后一段逐行说明），最接近的是第 1 行「指标 API 作为 Agent 的唯一取数入口」。它能保证的是**「接口现在就能接」**——指标能被机器以稳定的契约取到；它**不**保证「Agent 自助问数能答对」，后者是 5.2.2 的另一件事。把这两件事混为一谈，是排路线图时最常见的踩空方式。

这一落点必须写明，因为它决定了第 1 行的级别：我们手上的是**指标服务化在生产中成立**的记录（Airbnb Minerva 的公开工程文章，2020 年前后；书内 [§6](10-metric-platform-section-6-sec6.md) 的 6.1–6.4，来源标注见该节），而**不是**「指标 API 已被第三方（非厂商）注册为机器入口并被公开验证」——后者本主题下没有第三方公开案例（5.4 的第三方生产案例一栏已注明），这也是 5.2.2 判 L2 的理由。而 Airbnb 是 Minerva 的建设方、§6 四个案例的公司也都是各自平台的建设方，全属「厂商自有案例」这一档；按 L2 的定义（「已可用……或仅有厂商自有案例」），第 1 行只能定 L2——不能因为「接口层的构件在 AI 之前就存在」就把它升到 L1，那等于换了第②条判据。5.1 与 5.2.1 的判据按此完全一致。

读表时还要注意一点：**「级别」说的是能不能现在就规划，不是这件事重不重要**。Text-to-Metric 与指标召回的重要程度很高，但它们的落地顺序排在指标元数据治理之后——因为一个没有唯一载体的指标库接上自然语言入口，第一件事就是把口径分裂放大（机制见 5.2.2）。级别低只意味着**现在做会比晚一点做贵**，不意味着不用管。

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 指标 API 作为 Agent 的唯一取数入口 | **L2** | ① 接口 = 既有的指标 API + 公开的 GA 工具调用规范（Anthropic 的 MCP 规范 2024 年 11 月公开发布；OpenAI 的 Function Calling 2023 年发布并成为正式功能）；② 指标服务化有公开生产记录，但**全部出自平台建设方自己**（Airbnb Minerva 的公开工程文章，2020 年前后；书内 [§6](10-metric-platform-section-6-sec6.md) 的 6.1–6.4，来源标注见该节）——没有第三方（非厂商）公开案例，按第②条即 L2；③ 新增的只是「调用方是机器」，接口形态与口径边界未变 | 做 PoC：先补指标目录的机器可读描述，把指标 API 注册为工具，再谈自然语言入口；不要把它当核心依赖排进路线图 |

| AI 增强指标治理：自动识别重复指标 / 自动推荐定义 / 自动异常检测 | **L3**（自动识别重复指标）/ **L3**（自动生成定义）/ **L2**（异常检测） | 异常检测的机制是统计基线而不是 LLM（§6 案例 6.2 的同期基线）；「自动识别重复指标」卡在「相似」没有客观标准、「自动生成 / 合并指标定义」的公开材料集中在厂商演示，且口径变更需要 Owner 签字（§3.7 判据） | 异常检测可排期；重复清单与定义草稿只进评审流程，不进定义层 |

> 表里**没有任何一条方向同时满足 L1 的三条判据**，最接近的是**第 1 行：把指标 API 注册为机器取数入口**——它的①③都成立（工具调用协议有公开 GA 文档、接口形态与口径边界未变），但它能拿出的生产记录全部出自平台建设方自己（Airbnb Minerva、§6 的 6.1–6.4），第②条要求的「第三方（非厂商）公开生产案例」本主题下一条也没有，所以只能到 L2。五个方向不够格的原因分四类，处置方式完全不同：**第 1 行是「材料都在建设方自己手里」**——不缺工程条件，缺的是证据强度，可以做 PoC，但不做核心依赖；**第 2、4 行是「缺效果证据」**（Text-to-Metric 的效果、自动治理的能力，公开材料都以厂商演示为主），这类只能做 PoC 并自建评测集，别拿厂商演示当验收标准；**第 3 行是「缺前提」**（召回层、指标描述、唯一载体），这类不是等它成熟，而是**你要先把前提补上**，补不齐之前，第 2、4 行连 PoC 都测不准；**第 5 行是「缺标准本身」**（各家定义格式互不兼容，「成为事实标准」是预测不是现状），处置是不为「标准」提前迁移，选定一处作为自用载体即可。

这三级怎么用：**L1 排进路线图；L2 只做 PoC，并把结论写成实测数字**（召回率、端到端准确率、每次提问的 token 成本）；**L3 不排期**，只在架构评审记录里留一条「如果它成真，我们要改哪里」。每轮评审后回填级别：某个 L2 方向若出现了厂商之外的公开生产案例与评测，就升 L1；某个 L3 方向若一年内仍只有演示，就继续留在 L3 并停止投入。**级别不是标签，是投入决策。**

### 5.2 演进方向逐条拆解（核心节）

下面四个**含新机制**的方向按机制重排（5.1 表第 5 行「指标语义层的标准化」是标准格局的预判、不含新机制，故不单列——它的处置就是上表后一段的「选定一处作为唯一载体、不为『标准』提前迁移」）。每条都写全「旧做法卡点 → 机制改变 → 得到 → 付出 → 证据 → 成熟度」六项——**只要有一项写不出来，这个方向就还没有资格进路线图**。六项里最容易被跳过、也最该被追问的是第四项（付出）：本主题的付出有一个共同形态，**把取数这件事从人身上搬到机器身上之后，"数字错了"这件事就没人兜底了**——人写错 SQL 会自己看一遍结果，Agent 取错数不会。

#### 5.2.1 指标 API 作为 Agent 的唯一取数入口：改的是调用方，不是服务化机制

- **旧做法与它的卡点**：「Function Calling / MCP / Agent + 指标 API」被并列成三种技术选项。真正的卡点在平台侧：**指标平台的对外形态通常是"给人看的页面"**，而不是给机器看的契约——没有指标名、没有维度枚举、没有错误语义，Agent 只能退回去猜表名写 SQL。这正是 [§3.5](10-metric-platform-section-3-sec3.md) 反模式「不与 AI 集成」的机制后果：**指标资产在 Agent 场景里等于不存在**。第二个卡点是实时指标：它常被当成一条新链路来建设，于是 Agent 有了两个取数入口（离线一个、实时一个），两条路径的口径与权限各管各的——这正是主文件 §1.2 痛点 1「同一个 GMV 5 个数」在 AI 时代的复现。
- **AI 改变了什么机制**：**只改变了调用方，没有改变服务化机制**。指标 API 是既有部件：定义侧是 [§3](10-metric-platform-section-3-sec3.md) 3.2.1–3.2.4 的四种定义载体，消费侧是 [§4.3](10-metric-platform-section-4-sec4.md) 工具链里列出的各家指标平台（开源 / 云厂商 / 商业 / 国内四组），它们本来就以查询接口对外服务；AI 带来的唯一新事实是「调用方是一个会持续提问、且不会看页面的程序」，以及「它能调的接口必须自带描述与错误语义」。实时与离线在这里也不是两个机制，而是**同一个 API 的两个新鲜度档位**。
- **由此得到的**：**因为指标定义本身是一个封闭集合**（原子指标 × 修饰词 × 时间周期 × 维度，或语义层的度量 + 维度 + 过滤），所以把它注册为工具**不需要新增任何 AI 专用能力**，Agent 与 BI 消费同一个 API、同一个口径，口径分裂在结构上无处发生；**因为工具调用失败是可观测的**（工具名不存在、参数不在枚举内、超时、越权），所以「取数出错」从「回答错误」退化为「调用失败」——前者要人去核对数字，后者是明确的错误码。实时指标要做的也只是**挂到同一个工具入口**，而不是再开一条消费路径。
- **由此付出的**：四条真实代价：**其一，指标变成对外契约后，改名与改维度就是破坏性变更**，必须有版本管理与变更通知（§3.5 的「无版本管理」在这里的后果被放大：受影响的从报表变成程序）；**其二，工具数量随指标数量增长**，把上万个指标各注册成一个工具会让模型的选择空间爆炸，必须收敛为「少数工具 + 指标名作为参数」，而这一收敛正是 5.2.3 要建的召回层；**其三，权限必须下沉到指标级**——Agent 调用时用的是谁的权限？指标 API 一旦被机器调用，越权读指标（薪资、风控、未脱敏明细）成为新的故障模式，且它不会像页面那样被肉眼看见；**其四，成本形态变了**：从「报表按刷新周期算一次」变成「每次提问都算一遍」，实时指标尤其如此（§3.5 反模式「忽视成本」）。
- **证据与来源**：工具调用协议有公开规范【公开】：Anthropic 的 Model Context Protocol 规范于 2024 年 11 月公开发布（本书 [§8](10-metric-platform-section-8-sec8.md) 的来源清单亦收录该规范）；OpenAI 的 Function Calling 于 2023 年发布并成为正式功能。指标服务化一侧的生产记录见 [§6](10-metric-platform-section-6-sec6.md) 的 6.1–6.4（阿里 OneMetric / 字节 Bytemetric / 美团定义驱动 ETL / 某 SaaS 多租户，都是「定义 → 计算 → 服务化」的生产系统）。**可自行核验的判定方法**：拿你平台的指标目录逐条问三个问题——（a）有没有机器可读的描述文本，（b）能不能只靠「指标名 + 枚举内的维度与时间范围」取数，（c）越权与超时的错误语义是否明确；三条都「是」，才算真的可以接给 Agent；任何一条为「否」，接上去之后 Agent 只会退化成猜表名。
- **成熟度**：**L2**。判据：① 接口 = 既有指标 API + 公开的 GA 工具调用规范（MCP 2024-11 / Function Calling 2023）；② 指标服务化有公开生产记录（Airbnb Minerva 的公开文章，2020 年前后；书内 [§6](10-metric-platform-section-6-sec6.md) 的 6.1–6.4，来源标注见该节），**但这些记录都出自平台建设方自己**，不满足第②条的「第三方（非厂商）公开生产案例」，按该条即 L2；③ AI 带来的变化只是调用方，接口形态未变。**L2 的含义是可以做 PoC 与灰度、不做核心依赖**：接口侧的前置（机器可读描述、注册为工具、错误语义）现在就能做，而「Agent 自助问数已被第三方公开验证」那一层见 5.2.2 的 L2。

```text
把「Agent 取数」收敛成一次封闭选择（而不是让它生成 SQL）

  提问："上个季度北京新用户 GMV 是多少"
        │
  ① 召回：先在指标索引里选出候选集（本例命中 3–5 个候选指标）
        ▼
  ② 选择：工具调用只允许两种形态
       · list_metrics(keyword)         → 返回候选指标名 + 描述
       · query_metric(name, dims, time, filters)
       └─ 参数取值必须落在枚举内（维度 / 时间粒度 / 修饰词）
        ▼
  ③ 执行：计算永远发生在平台里，工具只返回数值与口径版本号
        ▼
  ④ 失败：名字不存在 → 明确报错（不是猜一个最像的）；
           越权 → 拒绝并记录（不是返回空值）
  ────────────────────────────────────────────────
  关键：工具调用的价值不在"能查数"，在于它把失败变得可见——
        猜出来的表名与枚举外的维度，都不会静默通过
```

> 这张图里最容易被省掉的是第 ④ 步。**没有明确失败语义的工具，等于把「取错数」伪装成「取到数」**，而这正是 AI 取数最难排查的故障形态。

工具形态的选择本身就是一次架构决策，三条路各有适用规模：

| 工具形态 | 形态 | 适用规模 | 代价 |
| --- | --- | --- | --- |
| 每指标一个工具 | `get_gmv`、`get_dau` … 各注册一个 | 指标数十个 | 指标上千时模型选择空间爆炸；每新增一个指标都要改工具注册，发布节奏被指标治理拖住 |
| 少数工具 + 指标名参数（本节推荐） | `list_metrics(keyword)` + `query_metric(name, dims, time, filters)` | 千级到万级 | 指标名成为对外契约（改名即破坏性变更）；名字合法性必须在服务端校验 |
| 直接暴露查询语言 | `run_sql(statement)` | — | 机制上退回「让模型生成 SQL」，5.2.2 的「失败可被发现」优势全部消失 |

#### 5.2.2 Text-to-Metric：它买到的不是「会说人话」，是「失败可被发现」

- **旧做法与它的卡点**：Cortex Analyst（2024）、Genie（2024）、Quick BI + 通义、Looker + Gemini 的发布被并列，读起来像是同一件事的四个实现。它们的**卡点不在识别意图，而在候选集**：业务方的提问是开放的，平台的指标库是封闭的，两者之间隔着一次「这次提问可能涉及哪几个指标」的检索。这一步缺失时，模型要么硬猜指标名，要么退回生成 SQL——而 SQL 允许生成出**语法正确但语义错误**的查询（口径写对了一半、时间窗口差一天、维度取错一层），这类错误算出来的数字看上去完全正常。
- **AI 改变了什么机制**：**把人工判断换成统计判断，并且把输出从「生成」改成了「选择」**。传统取数的错误是「人理解错了口径」，排查靠问人；Text-to-Metric 的错误是「在候选集里选错了指标」，排查靠比对候选集。这是本节认为它是真机制变化、而不是换前端的原因——**换前端只改入口，而它改变了错误的分布与可发现性**。
- **由此得到的**：**因为 LLM 的输出被约束在「指标名 + 维度 + 过滤 + 时间范围」这个封闭集合内，而计算由平台执行，所以幻觉的表现形式从「算错数」退化为「选错指标」或「被校验层拒绝」，两种都能被发现和纠正**（[§3.2.5](10-metric-platform-section-3-sec3.md) 已把这个机制写透，本节不重复推导）。由此还导出一个工程结论：**校验层不是可选项**——指标名必须存在于指标库、维度与取值必须落在枚举内、时间范围必须能落到存在的分区，缺一即拒绝或转人工。
- **由此付出的**：三条代价：**其一，端到端准确率的上限是召回率**——没被召回的指标，模型永远不可能选对，而用户从答案里看不出「其实有更合适的指标没被召回」（§3.2.5 的失效点）；**其二，token 成本随候选集与提问次数增长**：按每条候选指标 100–200 token 的注入量【经验】，每次注入 50 条候选约 7500 token【推算：50 条 × 150 token/条 = 7500】，提问量上万次时这是一笔可测算的常驻成本，且它与指标库规模同向增长；**其三，置信度不可知**：模型给出一个合理但错误的映射，并且措辞自信——因此必须有「这条回答对应哪个指标、哪段定义」的回显，否则使用方无法自行核对。
- **证据与来源**：自然语言到结构化查询的公开评测基准可自行核验【公开】：Spider（Yu et al., EMNLP 2018）与 BIRD（Li et al., NeurIPS 2023 Datasets and Benchmarks）——两者测的都是「在给定 schema 上的执行准确率」，**换一套 schema 结论不可搬运**，这正是本节拒绝引用任何「准确率 X%」宣传口径的机制依据。产品侧【公开】：Snowflake Cortex Analyst 与 Databricks Genie 的自然语言入口有 2024 年官方发布材料（书内 §3.2.5 已按此口径记录），国内阿里 Quick BI + 通义、腾讯 BI + LLM 方向相同。**判定方法**：要用它之前，先在自己的指标库上建一组固定问题（含长尾指标与近似指标），测三个数——候选集命中率、最终选择正确率、被校验层拒绝的比例；三者里第一个数低，问题在召回而不在模型。
- **成熟度**：**L2**。判据：产品已发布，但公开材料以厂商自有案例与演示为主；它在本企业能不能用，取决于本企业的指标描述覆盖率与召回层质量，只能靠自建评测集验证。

这个方向的失败形态不是一种，而是五种，且**能被谁发现**差别很大——这一点决定了校验层该放在哪里：

| 失败形态 | 表现 | 谁最先发现 | 需要的前置能力 |
| --- | --- | --- | --- |
| 召回为空 | 回答「没有匹配的指标」 | 用户，立刻 | 空召回率监控（否则会被当成"指标库里真没有"） |
| 命中近似指标但选择错误 | 数字正常、口径不同，肉眼看不出来 | 只有懂口径的人 | 回答必须回显指标名与口径版本号 |
| 选对指标、参数越枚举 | 明确报错 | 系统 | 校验层对枚举取值的强制检查 |
| 时间范围落不到存在的分区 | 报错或返回空值 | 系统 | 分区可用性检查前置到校验层 |
| 混合问答中文档段给出过期解释 | 解释与数值互相矛盾 | 需要看时间戳才能发现 | 文档段必须带出处与时间，且与数值分开标注 |

表里只有第 2 行是「静默失败」，而它恰好是最常见的一类。**所以本节把「回答回显指标名与口径版本」当成 Text-to-Metric 的验收条件，而不是界面优化**——没有这一行，PoC 阶段的所有准确率结论都无法复核。

#### 5.2.3 指标召回与混合检索：「指标 + 向量库 / RAG / GraphRAG」不在同一个层次上

- **旧做法与它的卡点**：四条结合项被并列——指标 + RAG、指标 + 向量库、指标 + GraphRAG、指标 + Agent。问题是它们**不在同一个层次上**：第一条与第二条是同一个机制（用检索把候选集缩小），第三条是另一个机制（用图上的关系做多跳扩展），第四条根本不是检索而是调用（已归 5.2.1）。混写会让读者以为「上了 RAG 就能答对」，而卡点其实是：**提问到指标之间缺少一个索引，且这个索引必须随指标库增量更新**。
- **AI 改变了什么机制**：**把「找指标」从人脑的模糊记忆变成了可度量的召回问题**。AI 之前，找指标靠人搜；AI 之后，同一个动作变成程序做，于是第一次有了「召回率」这个可被监控的数——**这是本方向唯一的机制变化，也是它为什么值得单独建一层的理由**：召回率是端到端准确率的乘数因子，它可度量、可回归测试，而模型能力不可控。
- **由此得到的**：**因为召回层把「全量 schema 注入 prompt」换成了「先选候选再注入」，所以指标规模从千级涨到万级时，系统不会因为塞不进上下文而失效**；同时把「指标 + 文档混合查询」（『上个季度 GMV 为什么下降』）拆成了两段可分别验收的事——指标段答「是多少」（走 5.2.1 的工具调用），文档段答「为什么」（走向量检索），**答案里必须标明哪一半来自指标、哪一半来自文档**，否则一次混合回答的错误无法归因。
- **由此付出的**：**其一，多了一个必须长期维护的系统**：召回索引要随指标库增量更新，指标改名 / 废弃时索引必须同步，否则会出现「选得到但查不到」的悬空候选；**其二，召回率成为准确率上限之后，指标描述的写作质量变成关键路径上的人力工作**——描述是 Owner 写的，不是平台生成的，描述缺失时召回层与模型一起失效；**其三，混合检索会改变「什么算答对」**：文档段的召回上限同样存在，且文档的时效性差，容易给出过时的解释——因此混合回答需要分别标注来源与时间；**其四，图的维护成本是长期的**：GraphRAG 需要维护指标—维度—实体之间的关系边，这些边大多要靠解析与人工确认，且它们**是定义边不是因果边**。
- **证据与来源**：召回 + 注入的分工机制见 [§3.4](10-metric-platform-section-3-sec3.md) 组合二（本节的判据与之完全一致）；混合检索的组件级能力因产品与版本而异，**本节不断言某产品支持某检索形态**，判定方法是查你所用的检索 / 向量组件的 release note 里「混合检索（hybrid）」「过滤（filter）」「增量更新」分别是不是正式条目。**「指标 + GraphRAG」在指标场景下没有可核验的公开案例**，故归 L3。
- **成熟度**：召回层 **L2**（机制是既有检索技术、可立即实施，但召回率必须自建评测集度量，且没有公开的指标召回评测口径）；GraphRAG **L3**（概念与演示期）。

| 结合项 | 真实机制 | 该怎么验收 | 级别 |
| --- | --- | --- | --- |
| 指标 + RAG（指标 + 文档混合） | 两段检索：指标段选指标，文档段选段落 | 分别标注来源与时间；两段的命中率分开测 | L2 |
| 指标 + 向量库（向量召回 + 指标 API） | 检索索引把候选集缩小后再注入 | 召回率是端到端准确率的上限，需回归测试 | L2 |
| 指标 + GraphRAG（聚合 + 关系推理） | 图上的多跳扩展（定义边，不是因果边） | 先证明多跳能命中单跳命中不了的指标 | L3 |
| 指标 + Agent（工具调用） | 调用，不是检索 | 归 5.2.1 的三条判定方法 | L2 |

召回层本身的实现也是三选一，代价落在不同的地方，选错会让「召回率」这个数失去意义：

| 召回方式 | 机制 | 适用与代价 |
| --- | --- | --- |
| 关键词 / 别名检索 | 指标名、别名、同义词的倒排索引 | 便宜、延迟低；代价是命中率被命名质量锁死——叫 `mt_001` 的指标永远搜不到 |
| 向量检索 | 描述文本的语义相似 | 对口语化提问更宽容；代价是描述质量即上限，且要维护随指标库更新的向量索引 |
| 标签 / 分层过滤 | 先按主题域、分层、Owner 缩小范围再检索 | 与既有资产分类复用；代价是分类不准时直接漏召回，且分类维护本身是人力活 |

工程上通常是后两者叠加（先按域过滤、再语义检索）。**判定方法**：取一组真实提问，逐条记录「正确指标是否出现在前 K 个候选里」——这个数就是召回率，它必须与准确率分开监控，否则出错时无法判断该改检索还是该改模型。

#### 5.2.4 AI 增强指标治理：机器能产出候选，不能替口径签字

- **旧做法与它的卡点**：自动识别重复指标、自动推荐指标定义、自动异常检测被并列成同一行的三项，但它们的卡点各不相同，写在同一行会掩盖真正的难点：**重复指标识别**卡在「相似」没有客观标准（两个 GMV 差一个过滤条件算不算重复？答案取决于业务，不取决于文本相似度）；**定义推荐**卡在定义是组织契约，一份新定义意味着有人开始为它负责；**异常检测**其实不卡在 AI——[§6](10-metric-platform-section-6-sec6.md) 案例 6.2 的做法是**同期基线**（按「同星期几 + 同时段」的历史值做基线）而不是 LLM，因为基线的口径可解释、可复现。
- **AI 改变了什么机制**：**在三项里只对「异常检测」这一项改变了机制**（把固定阈值换成统计基线 + 序列模式识别），其余两项改变的是**候选产出的成本**：过去发现重复指标要靠人工盘点，现在可以先让机器把疑似重复的清单列出来。**候选产出成本下降不等于决策成本下降**——合并两个指标仍然要改一个人的口径、通知一批下游看板。
- **由此得到的**：**因为机器只做候选、人做裁决，所以这三项都可以在既有治理流程里落地而不改流程**：疑似重复清单进指标评审会、定义草稿进 PR 流程、异常候选进告警队列。反过来，**凡是把机器输出直接当结论的做法都会制造新的治理债**：自动合并掉两个「看起来一样」的指标，等于在没有 Owner 签字的情况下静默改变了口径（§3.7 的判据「出现团队名即视为无主」，同理适用于「出现机器判断即视为无主」）。
- **由此付出的**：**其一，候选清单本身要有人消化**——无人处理的疑似重复清单会变成新的技术债堆积点；**其二，异常检测的代价是误报**：阈值放宽会漏报，收紧会淹没告警，而这个平衡点只能由业务确认，不能由算法自选；**其三，自动生成的定义有幻觉风险**，而定义是下游所有数字的依据，错一步会沿血缘放大，因此必须经人工评审才能进定义层；**其四，用 LLM 解释异常会引入新的失败模式**：解释读起来很像真的，但可能把「季节性」说成「渠道结构变化」，让排查走错方向。
- **证据与来源**：同期基线异常检测有书内生产记录（[§6](10-metric-platform-section-6-sec6.md) 案例 6.2，字节 Bytemetric）；机制层面它属既有统计方法，无厂商专属来源可引。**「LLM 自动生成 / 合并指标定义」在公开渠道以厂商演示为主，本节未找到可核验的第三方生产案例**，故归 L3——**缺失也是一种证据**。
- **成熟度**：异常检测 **L2**（书内有生产记录、机制可解释，但误报率需自建基线度量）；自动识别重复指标 **L3**（判定「重复」的标准尚未形式化）；自动生成 / 合并定义 **L3**（口径决策需要人负责，且无第三方生产案例）。

这三项落到实施上有一个共同的顺序，顺序错了就会白做：**先给指标定义补齐结构化字段，再谈机器辅助**。原因是三项都依赖同一份输入——指标的「一句话业务口径 + 来源表字段 + 维度 + Owner」（[§6](10-metric-platform-section-6-sec6.md) 案例 6.1 里那份 Owner / Statistic / Caliber / Attribute / Reference 的五要素定义就是这个形态）。字段缺失时，重复识别的相似度无所依凭（只剩指标名可比）、异常检测的基线无处归属（不知道异常该通知谁）、定义推荐没有可参照的既有样本。**所以本节把这个顺序写成一条硬判据：机器辅助的成熟度不可能高于指标定义的完整度**——定义完整度不到，AI 增强治理的每一项都只会产出无人消化的清单。

### 5.3 与本主题既有栈的接口在哪

「指标平台 + AI」不是「结合」，而是**挂载**：新的消费方（LLM / Agent）挂到既有的哪一个接口上、什么形态的数据穿过边界、失败时谁负责。写成「与 AI 结合」会省掉三件必须回答的事，而这三件事恰好是 PoC 阶段最容易出问题的地方。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 指标定义层 ↔ 消费方（BI / 产品后端 / Agent） | 只暴露指标 API，不暴露底层表；请求 =「指标名 + 枚举内维度 + 时间范围 + 过滤」，响应 = 数值 + 口径版本号 | 平台方负责口径与数值；消费方负责「提问是否落在指标库范围内」 | 服务化是既有 GA 能力（§4.3 工具链、§6 案例 6.1–6.4）（L2） |
| 指标 schema ↔ Agent 的工具描述 | 机器可读描述（名称 / 一句话口径 / 维度枚举 / 时间粒度）；没有描述的指标不出现在工具清单里 | 指标 Owner 负责描述质量；平台负责「描述缺失就不注册」 | 需在既有平台补一层导出，工作量小（L2） |
| 指标召回层 ↔ 指标库 | 提问进来先召回候选指标，再注入 prompt；索引随指标库增量更新 | 召回层负责召回率；平台负责指标元数据质量 | 召回率是端到端准确率上限（§3.2.5），需单独建设与监控（L2） |
| 指标血缘 ↔ 数据目录（[Ch4 §08](../08-data-catalog/08-data-catalog.md)） | 指标 → 派生表 → 字段 → 下游看板 / 应用的血缘注册进目录，两侧用同一套资产标识 | 目录负责「改了影响谁」；平台负责「定义改没改、改成什么」 | 需要统一资产标识，否则同一指标在两边各有一条记录（§3.4 组合三）（L2） |
| 实时链路 ↔ 离线链路 | 同一份定义生成两条物理链路，定时对拍；偏差超阈值阻断后续变更 | 平台方；对拍失败时以离线为准还是暂停服务由业务定 | 自研模式具备，多数现成产品只覆盖一条链路（§3.2.6、§3.6）（L2） |
| 指标 API ↔ 数据 API 网关 / 统一查询网关（[Ch4 §07](../07-data-api-gateway/07-data-api-gateway.md)、[Ch4 §09](../09-unified-query-gateway/09-unified-query-gateway.md)） | 网关做准入、配额、审计；指标平台只做口径与计算，不自己实现限流 | 网关负责「谁能调、调多少」；平台负责「算得对不对」 | 需要网关侧新增「机器调用方」的配额模型——Agent 会持续提问，不是人点一下就停（L2） |
| 异常检测 ↔ 告警 | 检测产出「异常候选」而不是动作；基线口径与阈值由业务确认并留痕 | 业务方确认；平台只负责产出候选与解释 | 同期基线已在案例 6.2 落地；LLM 化的异常解释属 L3（L2） |

```text
一次 Agent 取数里，数据穿过边界的三段形态

  ① 提问 → 召回层
       交出去的东西：自然语言（未结构化）
       交回来的东西：候选指标清单（指标名 + 描述 + 口径版本）
       失败形态：召回为空 → 必须回答「没有匹配的指标」，不许拿最像的顶替

  ② 候选集 → 工具调用（平台）
       交出去的东西：指标名 + 枚举内维度 + 时间范围 + 过滤
       交回来的东西：数值 + 口径版本号 + 计算时间
       失败形态：名字不存在 / 参数越枚举 → 明确报错，不返回近似值

  ③ 文档段（混合问答时）→ 向量检索
       交出去的东西：问题文本 + 时间范围
       交回来的东西：段落 + 出处 + 文档时间
       失败形态：语料过期 → 标注时间，不许与 ② 的数值混成一句结论
  ────────────────────────────────────────────────
  注：三段边界的共同要求是「失败时返回什么」必须写进契约，
      留给实现去猜的那部分，在 PoC 之后就再也没人补
```

一句话概括这三条边界：**AI 没有新增调用关系，只新增了三种「必须会失败」的交接物**——召回候选集、口径版本号、文档出处与时间。取数体系做得好不好，看这三样东西在答错时是否齐全，而不看有没有接上大模型。

这三条边界还有一个共同的现状：**接口形态只需在既有接口上补字段与补校验，召回层是唯一需要新建的组件（见下段）**。这也解释了为什么本主题下五个方向没有一个够得上 L1——最接近的接口层（5.1 表第 1 行）缺的不是工程量，而是「第三方（非厂商）公开生产案例」这一条证据：把「谁调用谁、穿过边界的形态、失败时谁负责」写清楚可以在一个迭代内做完，但它买到的仍然只是「接口现在就能接」，不是「有人公开验证过这套问答能答对」。而它的收益不依赖任何 AI 组件先达标。

关于「失败时谁负责」再补一句：三条边界里有两条的责任方是平台内已有的角色（指标 Owner 负责描述、平台团队负责口径与计算），**只有召回层是本节建议新建的组件，也是唯一需要为它专门指定 Owner 的组件**。没有 Owner 的召回层会随指标库的增量更新悄悄退化，而它的退化没有任何报错——只表现为「答得越来越不对」。这是本节把召回率列为与准确率并列的监控项的原因。

### 5.4 公开进展与文献

分三类列，每条给出可核验的出处；**宁少勿假**，核不到的不列。

**论文与评测基准**

- Yu et al., "Spider: A Large-Scale Human-Labeled Dataset for Complex and Cross-Domain Semantic Parsing and Text-to-SQL Task", EMNLP 2018——自然语言到结构化查询的公开评测基准，说明了「准确率」是在给定 schema 上测出来的。
- Li et al., "BIRD: A Big Bench for Large-Scale Database-Grounded Text-to-SQL Evaluation", NeurIPS 2023（Datasets and Benchmarks）——更贴近真实库的基准（含脏数据与外部知识），是「演示用的干净 schema 上成立、真实库上下降」这一现象的公开依据，也是本节拒绝搬运厂商准确率数字的机制依据。

**官方规范与产品文档（可核验的判定入口）**

- Anthropic 的 Model Context Protocol 规范（2024 年 11 月公开发布）——工具调用协议的公开入口；书内 [§8](10-metric-platform-section-8-sec8.md) 的来源清单亦收录该规范与 Function Calling 文档。
- OpenAI 的 Function Calling 文档（2023 年发布）——工具调用的既有形态，与 MCP 是同一机制的两套协议实现。
- dbt Semantic Layer / MetricFlow 的官方文档与开源仓库（MetricFlow 由 Transform 开源、后被 dbt 收购，主文件 §1.4 记为 2022 年）——「指标定义即代码」的公开入口。
- Cube（前身 Cube.js）的官方文档与开源仓库——指标 API 形态的公开入口；核验入口 = 文档站与仓库里「指标定义格式 / 指标 API」的正式章节（本条只给仓库与文档站入口，不给年份与版本号，版本口径见下条说明）。
- 说明：OSCAR（字节指标平台）、dbt Semantic Layer 与 Cube 的版本号（「1.0+」「1.x」）**本节不复述具体版本**，改给判定入口：查对应项目的 release note / 仓库 tag，确认「指标 API 的对外形态」与「定义格式版本」是否为正式条目。

**第三方生产案例**

- Airbnb 工程团队关于 Minerva 的公开工程文章（2020 年前后；标题与出处见书内 [§8](10-metric-platform-section-8-sec8.md) 的来源清单）——**本节唯一一条来自本书之外的公开生产记录**：指标定义与查询分离的早期工程样本。但它是平台建设方自己发布的材料，属「建设方自述」而不是第三方对某款产品的评测，因此本节不据此判 L1。
- 本书 [§6](10-metric-platform-section-6-sec6.md) 的 6.1–6.4：阿里 OneMetric、字节 Bytemetric、美团定义驱动 ETL、某 SaaS 多租户指标平台——**公开材料记录的生产实践**（来源标注回该节核对）：它们记录的是「定义统一 → 计算 → 服务化」这件事在生产中成立。这些案例的公司同样都是各自平台的建设方，属于「建设方公开材料」这一档证据，不是第三方对某款产品的评测——按 L2 的定义（「已可用……或仅有厂商自有案例」），这一栏的证据只能支撑到 L2，本节据此把 5.1 表第 1 行定为 L2，且它的范围限于「指标服务化这个既有能力」，不是「Agent 拿指标 API 取数」这个新用法。
- 说明：本主题下**未找到**「企业把指标 API 交给 Agent 自助问答并公布端到端准确率」的第三方公开案例。这一栏的空白，正是 5.1 表第 1 行与 5.2.2 都判 L2 的依据。

**怎么用这份清单**：它不是「读论文就能上生产」的路径，而是一组**判定入口**。遇到任何「某产品支持自然语言查指标 / 指标自动治理」的说法，先判断它的出处类型——是评测基准（只说明有这种任务）、是官方文档里的正式条目（说明能力存在）、还是产品页与演示（说明有人做出来了）——三者的证据强度差一个量级，而这正是本节 L1 / L2 / L3 三条判据的来源。**清单短不是资料少，是合格证据少。**

最后补一句这份清单**刻意不列**的东西：本节没有收录任何「某产品自然语言取数准确率 X%」的数字。不是因为这些数字不存在，而是因为它们全部缺少本节要求的三项条件限定——**在哪套 schema 上测（Spider / BIRD 这类公开基准的 schema 与你的指标库不同）、候选集多大（全量注入与先召回后注入不是同一个问题）、错误如何判定（选错指标算不算错）**。缺少这三项限定的准确率，读起来像事实，实际不可复现，而本节的存在意义就是不再把它们当技术事实转述。

### 5.5 被过度宣传的部分

下面三条不是「唱反调」，而是把**被宣传的能力**与**公开证据支持的能力**分开写。判断标准固定：宣传句里有没有可核验的条件（指标规模、召回率、第三方案例）——没有的，就归入下面三条。

**「Text-to-Metric 让业务方不再需要数据团队」**——它替换的只是「提问到取数」这一段的路由，不是「指标从哪来」这件事。指标定义、Owner、口径评审、变更通知，一样都不会因为多了一个自然语言入口而消失；而且它的效果上限由本企业的指标描述覆盖率与召回率决定（[§3.2.5](10-metric-platform-section-3-sec3.md) 的失效点）。**为什么会这样**：LLM 只在候选集里做选择，候选集由平台的指标库决定——没有被定义、或没有描述的指标，模型不可能选对，而用户从答案里看不出这一点。**它什么时候才会成真**：出现厂商之外的、覆盖长尾指标的公开评测（含召回率与端到端准确率），而不是演示用的少数几个指标；在此之前，正确说法是「业务方自助取数的**覆盖面**变大了，**边界**仍由指标库决定」。

**「LLM 能自动生成 / 合并指标定义，指标治理可以自动化」**——机器能生成草稿，不能替口径签字。合并两个「看起来一样」的指标，意味着改变某位 Owner 的口径、并影响一批下游看板；这件事必须有人负责（§3.7 的判据「出现团队名即视为无主」，同理适用于「出现机器判断即视为无主」）。**为什么会这样**：口径是组织契约而不是文本相似度问题——两个 GMV 差一个过滤条件算不算重复，答案取决于业务，不取决于文本距离。**它什么时候才会成真**：自动生成的建议进入定义层的 PR / 评审流程、有公开案例说明「机器建议被 Owner 采纳并按流程发布」，并且能查到采纳率与推翻率这两个数。

**「指标 + GraphRAG 能做因果推理」**——图提供的是关系检索（把指标、维度、实体连起来），不是因果推断。**为什么会这样**：图里的边是**定义边**（同源、派生、同维度、同口径），不是因果边；「GMV 为什么下降」这类问题需要归因方法（结构分解、控制变量、对照实验），图只能给出**候选路径**，而候选路径的数量往往大于人能逐一验证的数量。**它什么时候才会成真**：出现把「指标归因」形式化为可评测任务、并公布评测结果与失败案例的公开工作；在此之前，GraphRAG 在指标场景的合理位置是 5.2.3 的召回增强，而不是结论生成。

这三条的共同结构是：**被宣传的能力都指向「结论」，而公开证据支持的能力都停在「候选」**。所以在评审任何 AI 指标方案时先问一句「它输出的是候选还是结论」——输出候选的可以试，输出结论的现在先不要接。

这一问还有一个附带用处：它把「AI 能不能用来做指标治理」变成一个**当场就能问出口的问题**——凡是答不出「这个结论由谁负责」的方案，无论模型多强，都不该进入定义层；而答得出「这是候选、由某人确认」的方案，通常不需要模型多强就能落地。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 指标 API 会成为 Agent 取数的默认入口，自然语言入口退化为它前面的一个前端 | 主流 Agent 框架或数据平台的工具目录里出现「指标平台」这一类；企业公开架构里「读指标」与「读表」被拆成两条权限路径 | 三年后主流做法仍是 Agent 直连数仓生成 SQL；指标平台在取数链路上被绕过（表现为没有指标 API 的调用日志） |
| 自然语言取数的瓶颈会从「模型能力」转到「指标元数据质量与召回」 | 公开分享里的失败复盘从「模型不懂业务」改成「没召回对的指标」；出现独立开源 / 独立售卖的指标召回组件 | 评测显示长尾指标无需检索即可被选中（召回率不再是准确率上限），或准确率不再随指标描述覆盖率变化 |
| 指标语义层不会出现单一「事实标准」，而是「一个交换格式 + 多种实现」 | 出现被多家产品实现的指标定义导入 / 导出格式（含维度、修饰词、时间粒度的互换）；迁移案例公开 | 某一家语义层被绝大多数 BI 与云厂商原生支持，且用户迁移不需要重写定义 |
| 实时指标 + Agent 的瓶颈会落在成本而不是能力 | 公开材料开始讨论「Agent 提问的查询 / 算力预算」，出现按提问计费或按调用方限流的指标 API 实践 | 实时指标的单次查询成本降到可忽略（例如预聚合物化让多数提问零重算），成本不再出现在架构讨论里 |

写这四条时的共同约定：**信号必须是外部可观察的**（出现在 release note / 官方文档 / 公开案例 / 评测报告里），而不是「我觉得会」。凡写不出证伪信号的判断，本节不写——它没有信息量。另外注意这四条里没有「AI 会取代指标平台」这一条：**指标定义的唯一载体、Owner、版本管理这些机制与 AI 无关，它们不会被替代，只会被调用得更多。**

这四条可以当作一份**按季度核对的观察清单**：它们都不依赖某家厂商的产品路线，而依赖**接口形态**与**证据类型**的变化——所以右两列的判据，读者可以自己去 release note、官方文档与公开案例里核对，不需要等本节更新。这也是它们与「未来 AI 原生」这类句子的区别：**后者永远正确，因而没有信息量；前者可以被证伪，因而能在评审会上当判据用。**

### 5.7 给架构师的行动建议

下表按「你的处境」分行而不是按技术分行：同一项技术在不同处境下的正确动作完全不同——已有指标平台的团队要做的是「把它接到工具上」，还没有唯一载体定义的团队要做的是「先别谈 AI」。

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有指标平台 / 语义层，指标已服务化 | 把指标目录的机器可读描述补齐（名称 + 一句话口径 + 维度枚举 + 时间粒度），注册为工具；把「无描述不注册」做成硬规则 | 观察工具调用日志里「名字不存在」「参数越枚举」两类错误的比例——这两个数是接口质量的直接度量 | **不要为自然语言入口单独建一套取数链路**；不要让 Agent 直接连底层表取数（那等于把口径交给模型猜） |
| 指标有定义但散落多处（报表里、BI 里、平台里各一份） | 先做指标盘点与原子指标收敛，确定唯一载体；把「同一指标的第二份可执行实现」列为待清理项（[§3.5](10-metric-platform-section-3-sec3.md)） | 观察是否存在「平台里改了、报表里没改」的分叉案例 | 不要在唯一载体确定之前接 Agent——**分叉不会报错，它只会变成两个都查得到的数字** |
| 想做 Text-to-Metric 试点 | 先建自建评测集（含长尾与近似指标各若干条），再建召回层；把「候选集命中率」作为第一个门槛 | 观察候选集命中率与最终选择正确率是否同步变化；不同步说明瓶颈在召回 | 不要用厂商演示的准确率当验收标准；不要在没有召回层时全量注入 schema（指标上千就塞不进去） |
| 已有大量 BI 报表、业务方自助需求强 | 先做「指标 API + 权限到指标级」，再谈自然语言入口；越权与超时的错误语义必须明确 | 观察越权访问尝试是否出现在审计日志里 | 不要把「业务方可以自己问数」等同于「不需要治理」——访问控制随消费方变成机器而变得更关键 |
| 离线指标已通，实时指标也在建 | 让实时与离线共用同一份定义、同一个工具入口；建立定时对拍与偏差阻断 | 观察两条链路的对拍偏差是否稳定收敛 | 不要为实时指标再开一条 Agent 消费路径；不要让两条链路各自维护口径 |
| 已有指标异常告警 | 先把基线口径（同期基线 / 季节性）写清并留痕，再考虑 LLM 解释异常 | 观察误报率与告警处理时长；引入 LLM 后这两个数是否变化 | 不要自动执行由异常触发的动作（改预算、调库存、停投）；不要让 LLM 的解释替代基线口径 |
| 受监管行业 / 财务口径（对外披露、审计） | 让每一次取数都带口径版本号与取数时间，并进入审计日志 | 观察审计方是否开始要求「这个数字是按哪一版口径算的」 | 不要允许自然语言入口在不留痕的情况下改变过滤条件（时间窗口、合并范围） |

「明确不要做」这一列的共同逻辑是：**这些动作的代价是确定的（新链路、新索引、新权限面），而它们的收益依赖一个尚未成立的前提**（指标描述已齐、召回率已达标、唯一载体已确定）。等到前提补齐或 5.6 里的信号出现再投入，损失的只是时间，不是钱。

**如果你只能做一件事**：把指标目录导出成一份机器可读清单，然后**逐条问三个问题**——有没有描述、能不能只靠「指标名 + 枚举参数」取数、越权和超时的错误语义是否明确。这份清单的长度与你答「是」的比例，同时决定了三件事：Text-to-Metric 准确率的上限（5.2.2）、召回层该覆盖什么（5.2.3）、以及现在能不能把指标交给 Agent（5.2.1）。**这件事不依赖任何 AI 组件，所以它什么时候做都不亏。**

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**取数的调用方从人变成了机器**——由此带来三个必须被工程化的后果：接口必须自带描述（否则机器只能猜）、失败必须显式（否则「取错数」伪装成「取到数」）、权限必须下沉到指标级（否则 Agent 的权限就是调用者的权限）。**它没有改变的是**：指标定义的唯一载体、口径评审与 Owner、版本与变更通知、离线与实时同源——这些是主文件 §2 与 [§3](10-metric-platform-section-3-sec3.md) 的那一套，AI 只是让它们的缺失更早暴露（描述缺失、召回缺失、载体分裂，都会在 Agent 取数时立刻显形）。
>
> 判断本主题下任何新提法的快捷方式：**它产出的是候选还是结论？** 产出候选的（召回、异常清单、定义草稿）现在就能接进既有流程；产出结论的（自动合并定义、自动归因、自动执行）要等它先找到「谁负责」。
>
> 落地顺序也只有一条主线，且不可逆：**先把指标定义收成唯一载体并补全机器可读描述 → 把指标 API 接到工具调用上 → 最后才是自然语言入口与召回层**。前置没做完时，后一步的收益会被自己的缺口吃掉：描述缺失时召回率上不去，载体分裂时 Agent 只会把两个数字一起带出来，而它不会告诉你哪个对。
>
> 三个可以立刻开始量的数：指标目录中**有机器可读描述的比例**（决定召回与选择的上限）、工具调用的**失败率**（名字不存在 / 参数越枚举 / 越权三类分列）、固定问题集上的**候选集命中率**（决定该改检索还是改模型）。这三个数都不依赖任何 AI 组件先达标，因此什么时候开始量都不亏。
>
> 💡 **思考锚点**：把你指标目录里「有机器可读描述」的比例算出来（名称 + 一句话口径 + 维度枚举 + 时间粒度四件是否齐），再想：按这个比例接 Agent 时，失败会落在「名字不存在」还是「参数越枚举」——若两类都高，说明瓶颈在接口描述而不在模型，你会先补目录还是先上召回层？
