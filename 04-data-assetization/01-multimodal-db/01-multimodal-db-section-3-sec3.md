## 3. 设计模式与范式

> 原 § 3 共 78 行、为「6 个模式条目 + 8 条反模式 + 7 行场景决策表」，缺少结构示意、机制解释与失效分析，重写为 303 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表读起来像一道选型题：要跨模态就统一向量空间、要灵活就模态专属 + 元数据、图省事就用多模态原生库、量大就上 Lakehouse + 向量库、要问答就套多模态 RAG、扫描件就用 ColPali。但它放进真实约束里会立刻散架：同样是「以文搜图」——如果这张图必须和结构化条件（品牌、时间、权限）一起筛，那么「统一向量空间」解决不了「过滤放在哪一步」，而这一步才是决定召回质量的地方。同一句需求，正确模式可能完全不同。

决定这些模式彼此不同的底层机制有三个：**模态的表示是否可比**（各模态编码器是否输出同一空间、同一维度，由主文件 §2.1 关键概念定义与 §2.2 形式化给出）、**原件在哪里**（进库、还是外置只留路径与摘要）、**过滤与近邻谁先发生**（条件参与检索，还是检索完再裁）。后两条主文件未展开，其判据来自本章 [§6 落地实践](01-multimodal-db-section-6-sec6.md) 里四个案例的失败教训。前一个决定跨模态检索在物理上是否可能，后两个决定它准不准、贵不贵。

所以本节先立约束、再谈模式。下表不是选型表，而是「本主题下最容易被约束推翻的直觉」清单。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 模态之间是否需要互相比较 | 是否共用一个向量空间（可比性从哪来） | 「统一向量空间一定更好」——它用单模态精度换取跨模态可比，主力模态会变差 |
| 预处理是否不可逆（OCR / ASR / 抽帧） | 全链路的信息保真上限 | 「先统一转文本最省事」——OCR 错一次，下游全部继承这个错误且无法回头 |
| 原件体积与合规要求 | 原件进库、外置留路径，还是只留摘要 | 「一行里什么都存最省事」——库体积与备份时间同时失控 |
| 过滤条件的选择性 | 过滤与近邻的先后顺序 | 「先检索再过滤」——Top-K 被条件裁空后结果为零 |
| 单次查询的成本预算 | 走 Embedding 检索，还是多模态 LLM 直接读 | 「大模型什么都能看」——成本随「页面数 × 提问数」增长 |
| 时序 / 结构敏感性（视频、点云、日志） | 是否必须保留时间与结构信息 | 「抽帧成图就够了」——帧序丢失后事件顺序不可恢复 |

还有一条容易被忽略的约束是**检索层与生成层的边界画在哪里**。多模态资产最终要被人或 LLM 消费，但把生成能力接进检索链路，会把「可测性」从两段变成一段——出了问题既不知道是没搜到，还是搜到了却被解释错。因此下文模式划分里，凡是涉及 LLM 的都只出现在链路末端，检索层始终保留一条可独立评估的出口。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 统一向量空间（CLIP / ImageBind 模式）

- **被什么约束逼出来**：业务要「以文搜图」「以图搜文」这类跨模态检索，而不同模态的原始表示根本不可比；若每种模态一套索引、一套分数，跨模态排序在应用层无从下手。
- **结构**：所有模态经各自的编码器投到同一个对齐空间，检索时不区分模态，只比向量。

```text
单一向量空间：跨模态可比，代价是所有模态共用同一组维度
  文本 ─┐
  图像 ─┼─► 同一个对齐空间 R^d ──► 最近邻检索（不比模态，只比向量）
  音频 ─┘
  ────────────────────────────────────────────────
  机制：训练时用成对数据（图-文）拉近匹配对、推远不匹配对
        → 被对齐的是"语义"，不是"模态"
  代价：所有模态被迫共用同一维度与容量
        某一模态的专有信息在投影进这个空间时被压掉
```

```python
# 双塔：两侧编码器各自独立，但输出维度与空间必须一致
v_text  = E_text("一只橘色的猫")      # d = 512 / 768 【公开】（CLIP 官方规格：ViT-B/32 输出 512 维、ViT-L/14 输出 768 维；主文件 §2.1 同）
v_image = E_image(load("cat.jpg"))    # 同一空间、同一维度
sim     = cosine(v_text, v_image)     # 以文搜图：直接比向量，无需额外映射
# 关键判据：换成两套维度不同、训练目标不同的编码器，cos 就没有意义
```

```text
换编码器的代价（为什么向量必须可重建）
  模型 A 的空间 ──► 模型 B 的空间：两个空间不可比
  拿旧查询向量与新文档向量算 cos → 数值没有意义
  所以换编码器 = 全量重算 + 检索质量从头建基线
  ────────────────────────────────────────────────
  这就是"必须存原件"的机制理由：
  没有原件，向量不可重建；向量不可重建，模型就换不动
```

- **为什么这样设计有效**：因为两侧编码器在同一批成对数据上被对齐、输出同维向量，所以「以文搜图」与「以图搜图」共用同一条检索链路，新增一种查询模态不需要新增一套索引；代价是这个可比性来自共享空间，任何模态的专有信息在投影进这个空间时都会损失。
- **代价**：统一空间的维度与编码器容量是共享资源，为图像调优会挤掉文本的区分度；换编码器意味着全量重算向量（新旧向量不可比），是一次全库重建；跨语言与跨域能力由训练数据分布决定，不是调参能补齐的。
- **失效点**：当业务以单模态检索为主、且该模态存在更强的专用编码器时，统一空间从「跨模态可比」反转成「精度拖累」，因为通用对齐空间为容纳多模态把每种表示压得比专用模型更粗；训练分布与业务领域相差越大（中文长尾商品、专业文档），反转越明显，此时应改为领域内微调或分模态编码。
- **真实使用**：CLIP 由 OpenAI 提出并公开 【公开】（Learning Transferable Visual Models From Natural Language Supervision，2021）；ImageBind 以图像为锚点把六种模态对齐到同一空间 【公开】（Meta，2023）。中文场景通常换用中文对齐模型或做领域微调 【经验】。

#### 3.2.2 模态专属存储 + 元数据关联（含「多模态 Embedding + 向量库」的低延迟形态）

- **被什么约束逼出来**：每种模态都有明显更适合它的工具（关键词检索、对象存储、向量索引、图遍历），且真实查询几乎总是「先按业务条件缩小范围，再按语义排序」——把两者放进同一个系统往往两边都不够好。
- **结构**：每种模态留在最合适的存储里，靠一个共同主键与元数据把它们关联；查询分「先筛后搜」两步。低延迟形态（实时推荐类）会把向量与少量热字段放进同一个在线向量库，把两步合成一跳。

```text
模态专属 + 元数据关联：关联键是唯一的契约
  元数据 / 关系库： item_id, brand, ts, acl      ← 先筛：缩小候选集
        │  item_id 是唯一关联键
        ├─ 向量库：   item_id, embedding(d)       ← 再搜：在候选集内做近邻
        ├─ 对象存储： s3://.../item_id/xxx.jpg    ← 取原件（不参与检索）
        └─ 文本索引： item_id, 标题 / 描述         ← 专有名词与编号命中

  查询路径：WHERE brand='Nike' → 候选 ID 集 → 向量近邻 → 回取原件
  ────────────────────────────────────────────────
  低延迟形态（实时推荐）：向量与热元数据同库
        → 少一跳；前提是元数据条件能作为过滤参与检索，而非事后裁剪
```

- **为什么这样设计有效**：因为每一段都用最适合该模态的引擎，召回与延迟可以分别调优、单独替换；代价是「关联键」成了唯一契约——跨系统拼装的正确性完全依赖 item_id 在四套系统里始终一致。
- **代价**：N 套系统意味着 N 套备份、监控、升级与权限，且跨系统写入无法共用同一事务，会出现「有向量没元数据」的孤儿记录；跨模态排序要在应用层完成，用不上任何引擎的联合优化。
- **失效点**：当「先筛」的候选集很大（筛出百万级 ID【经验】）时，第二步的向量检索从「候选集内近邻」退化成「全库近邻再求交集」，因为向量索引无法把一份百万级 ID 列表当作高效过滤条件；此时要么把条件下沉进向量库（带过滤的近似检索），要么改成同表混合查询。
- **真实使用**：这是最常见的起步形态 【经验】；Pinecone 等托管向量库把元数据过滤与命名空间做进平台，正是为了消掉「先检索后过滤」这一步 【公开】（Pinecone 官方文档的两项能力条目：Metadata Filtering 与 Namespaces，在 pinecone.io 文档站可自行检索；能力形态另见本章 [§1.3 Pinecone 案例](01-multimodal-db-section-6-sec6.md)）；某 SaaS 与某车企的收敛路径见 [§6 落地实践](01-multimodal-db-section-6-sec6.md)。

#### 3.2.3 多模态原生数据库（SurrealDB / Weaviate）

- **被什么约束逼出来**：团队规模小、模态种类还在增长，既运维不起 N 套系统，也不想自己维护跨系统的关联一致性；要的是「一个系统里就能完成一次多模态查询」。
- **结构**：一个系统内同时提供文档、图与向量的数据类型与索引，跨类型的条件写进同一条查询。

```sql
-- 多模态原生库的形态（示意语法）：同一存储里既是文档、又能向量检索
DEFINE TABLE item SCHEMAFULL;
DEFINE FIELD modality  ON item TYPE string;
DEFINE FIELD meta      ON item TYPE object;        -- 结构化属性，可直接参与过滤
DEFINE FIELD embedding ON item TYPE array<float>;  -- 向量，在同一条查询里参与近邻
DEFINE INDEX idx_vec  ON item FIELDS embedding HNSW DIMENSION 1024;
DEFINE INDEX idx_meta ON item FIELDS meta.brand;

SELECT id, file_path FROM item
WHERE modality = 'image' AND meta.brand = 'Nike'
ORDER BY vector::similarity::cosine(embedding, $qvec) DESC
LIMIT 10;
-- 关键：过滤与近邻由同一个执行器安排顺序，能先收缩范围再做近邻
```

- **为什么这样设计有效**：因为结构化条件与向量近邻由同一执行器统一安排执行顺序，过滤能真的缩小近邻搜索范围，而不是检索完再把结果裁掉；代价是这套一体化能力的成熟度与深度都低于各模态的专用系统。
- **代价**：生态小——采集、监控、备份、权限、方言与工具链都不如主流数据库或专用向量库，团队技能不易复用；扩展方式与容量上限由单一项目决定。另外要注意：原生支持图与文档不等于拥有跨模态语义空间，跨模态可比仍然只在「向量」这一条通道上成立。
- **失效点**：当规模跨过单机或单个中等集群，或需要为某个模态单独做精细调优（专门的版面检索、专门的图遍历）时，一体化从「少维护一套」反转成「哪一样都不够用」，因为一体化产品必须在多种能力之间做取舍，而专用系统不必。
- **真实使用**：Weaviate 提供模块化的多模态向量能力 【公开】（Weaviate 官方文档，源码仓库 weaviate/weaviate；文档站可自行检索 multi-modal / multi-vector 条目）；SurrealDB 提供文档 + 图 + 向量的多模型形态 【公开】（SurrealDB 官方文档，源码仓库 surrealdb/surrealdb；文档站可自行检索 data model 与 vector search 条目）；新项目与中小规模场景采用较多 【经验】。

#### 3.2.4 Lakehouse + 向量库

- **被什么约束逼出来**：多模态数据体量到了 PB 级，原件生成后基本不变，且要同时被训练、分析与在线检索三条链路消费；存储必须便宜、开放、可被多个引擎读。
- **结构**：原件与「可分析部分」放湖仓（开放表格式），向量与在线检索放向量库，两者靠主键与增量同步衔接。

```text
湖仓 + 向量库：湖是唯一事实源，向量库是可重建的派生物
  对象存储 / Iceberg
    ├─ 原件：图片 / 视频 / 音频（不可变，按分区组织）
    └─ 表：  path, meta, 摘要, 向量
             │  增量同步：新增 / 更新分区 → 向量化 → 写向量库
             ▼
  向量库：item_id, embedding, 少量热字段      ← 在线检索，毫秒级
             │
  训练 / 分析 ───────► 直接读湖（不经过向量库）
  ────────────────────────────────────────────────
  关键：向量库丢了可以重建；但重建期间在线检索不可用
```

```text
同步链路的两种形态（决定不一致以什么形式暴露）
  全量重建：定期整批重新向量化 → 幂等好做，但窗口期内检索读到的是旧数据
  增量追平：按分区 / 主键增量向量化 → 更新更及时，但漏一条就长期不一致
  ────────────────────────────────────────────────
  无论哪种，都必须能回答一个问题：
  "检索能命中、但原件已被删或已更新"的条目有多少
```

- **为什么这样设计有效**：因为向量与摘要都是可重建的派生物、只把在线检索压在向量库上，所以存储成本能压到对象存储的价格，同时保留毫秒级检索；代价是两套系统之间多出一条必须保持同步的链路。
- **代价**：同步延迟与一致性（向量库落后于湖时，会检索到已删除或已更新的条目）；向量化作业的算力成本与幂等设计；湖与向量库的权限必须对齐，否则「检索能查到、取原件被拒」；湖侧小文件合并与快照清理是常驻运维。
- **失效点**：当数据从「基本不变、新增为主」变成频繁更新（原件被反复替换、标注被频繁修正）时，这套结构从「存储便宜、可扩展」反转成「每改一次就要重算向量并追平两套系统」，因为同步链路的单位成本固定而更新频率上去了；此形态的前提本身就是「不可变」。
- **真实使用**：Iceberg / Delta 是开放表格式 【公开】（Apache Iceberg 项目仓库 apache/iceberg 与 Delta Lake 项目仓库 delta-io/delta 的官方文档与表格式规范，可自行核验）；Milvus / LanceDB 等常与该形态搭配 【公开】（Milvus 仓库 milvus-io/milvus、LanceDB 仓库 lancedb/lancedb 的官方文档，可自行核验）；阿里把原件放对象存储、可检索部分与向量放在仓库侧加工，属同族形态 【经验】（本章 [§1.4 阿里 PAI 案例](01-multimodal-db-section-6-sec6.md) 对该材料只标了「阿里 PAI 公开材料 2019-2024」这一方括号标记，没有标题、作者或链接，故此处不按【公开】采信；要按【公开】引用，需先补上可定位的原始出处。判断方法：看该形态是否把不可变原件留在对象存储、只把可检索部分与向量放在仓库侧加工）。

#### 3.2.5 多模态 RAG 模式

- **被什么约束逼出来**：业务要的是答案而不是候选列表；而多模态 LLM 无法直接消费企业全量语料——上下文窗口放不下，成本也不允许把原件全喂进去。
- **结构**：检索一小块 → 组装上下文 → 多模态 LLM 理解并生成 → 带引用返回。

```text
多模态 RAG：LLM 只看被检索出来的那一小块
  查询 ──► 检索（向量 + 结构化过滤）──► Top-K 资产（图 / 页 / 帧 / 文本）
                                              │ 组装上下文
                                              ▼
                                    多模态 LLM 理解 + 生成
                                              │
                                       答案 + 引用（回链原件）
  ────────────────────────────────────────────────
  成本位置：单次成本 ≈ O(Top-K 的图像 / 页面数)
            总成本随提问数线性增长
  不检索直接喂全量：成本不可行，且超出上下文窗口
```

- **为什么这样设计有效**：因为进入 LLM 的是检索后的少量上下文，生成成本与上下文规模成正比而非与语料规模成正比；代价是答案的质量上限被检索的召回与精度锁死——检索没找到的，LLM 补不出来，而且它会用流畅的语言把缺失掩盖掉。
- **代价**：每次提问都要付一次多模态推理成本（图像与页面按视觉 token 计价）；端到端延迟是检索加生成两段之和；评估变复杂，必须同时评检索的 Recall@K 与生成的正确性和引用是否对得上，端到端指标好看但检索层坏掉的情况很常见。
- **失效点**：当问题需要跨多个文档聚合（「这几份合同的差异是什么」）或需要开放式推理时，它从「端到端体验好」反转成「每问都差一点」，因为 Top-K 检索的前提是「答案集中在少数片段里」，而聚合类问题的答案分散在全库——此时应改成先结构化聚合再让 LLM 解释。
- **真实使用**：多模态 LLM（GPT-4V / Claude 3.5 Vision / Qwen-VL 一类）为公开产品 【公开】（各自的厂商模型文档与发布公告：OpenAI GPT-4V，2023；Anthropic Claude 3.5 Sonnet 的视觉能力，2024；阿里 Qwen-VL，2023 起开放权重）；「先 Embedding 检索、再把 Top-K 交给多模态 LLM」是当前通行做法 【经验】；完整链路与评估方法见 [§4.1](01-multimodal-db-section-4-sec4.md)。

#### 3.2.6 ColPali / 多模态文档检索模式

- **被什么约束逼出来**：复杂版式文档（扫描件、财报、表单）的信息在版面里而不在文本流里；OCR 一旦出错，后续所有环节都继承错误，而且这一步不可逆——原始版面信息在转文本时就丢了。
- **结构**：跳过 OCR，直接把页面当图像编码成多向量（每个 patch 一个向量），检索时做 late interaction 逐 token 匹配。

```text
ColPali 形态：页面 → 多向量，检索时逐 patch 匹配
  传统链路：PDF ─► OCR ─► 文本块 ─► 每块一个单向量
        ▲ 版面信息丢失；OCR 错 → 全链路错，且不可逆

  ColPali：PDF 页面 ─► 视觉编码器 ─► 每页 N 个 patch 向量（多向量）
    查询向量 ─┐
              ├─ late interaction：逐 patch 取最大相似度后再聚合
    页面向量 ─┘
  ────────────────────────────────────────────────
  保留版面（表格、印章、手写、图表、栏位关系）→ 不需要 OCR
  代价：向量数 = 页面数 × patch 数 → 索引体积与检索算量成倍放大
```

- **为什么这样设计有效**：因为检索直接在页面图像的多向量表示上做逐 patch 匹配，表格结构、印章、手写这些不在文本流里的信息被保留下来，OCR 错误不再成为不可逆的上游；代价是索引体积与检索算力按 patch 数成倍放大。
- **代价**：存储与内存显著高于单向量方案（每页存 N 个向量而不是 1 个）；检索要算 token 级匹配，延迟与算力都高于普通近邻；模型与链路较重，且它替代的是「OCR + 文本检索」这一段，不替代生成，也不替代结构化抽取。
- **失效点**：当查询依赖精确字符（合同编号、型号、金额逐位比对）时，纯视觉多向量检索反转成不如 OCR 加关键词，因为像素级表示对稀疏字符串的精确匹配天然弱于符号匹配；此时应改为稀疏与多向量混合检索，而不是二选一。
- **真实使用**：ColPali 于 2024 年提出（用视觉语言模型直接做文档检索，跳过 OCR），并已有开源实现与后续演进 【公开】（论文 *ColPali: Efficient Document Retrieval with Vision Language Models*，2024；开源实现仓库 illuin-tech/colpali，可自行核验）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 以图搜文 / 以文搜图，且跨模态是主需求 | 统一向量空间 | 不选分模态编码：各模态向量不在同一空间，跨模态排序无从下手 | 编码器是否输出同维同空间 |
| 多模态融合（电商商品、诊断数据），条件筛选强 | 模态专属 + 元数据关联 | 不选统一空间单打：条件筛选落不进向量检索，Top-K 会被裁空 | 过滤条件的选择性有多强 |
| 新项目、追求简单、团队小 | 多模态原生数据库 | 不选多套存储：组合出来的关联一致性没人维护 | 规模是否还在单系统能力内 |
| 超大规模、数据以新增为主 | Lakehouse + 向量库 | 不选全放库内：库体积、备份与成本同时失控 | 数据是否基本不可变 |
| 多模态问答 / 视频理解 | 多模态 RAG | 不选只给候选列表：业务要的是答案 | 检索层是否可独立评估 |
| 扫描 PDF / 复杂版式文档 | ColPali 一类多模态文档检索 | 不选 OCR + 文本检索：版面信息在转文本时已丢失且不可恢复 | 信息是否依赖版面而非文本流 |
| 实时多模态推荐 | 多模态 Embedding + 向量库（元数据参与检索） | 不选先检索后过滤：候选集被裁空，召回为零 | 是否要求毫秒级且条件必须参与检索 |
| 数据频繁更新、要求读到最新 | 条件与向量同表 / 同库（缩短同步链路） | 不选湖 + 异步向量库：向量库追不上更新，会检索到已删条目 | 更新频率是否高于同步周期 |
| 专有名词 / 编号类查询与语义查询并存 | 稀疏 + 稠密混合检索 | 不选纯稠密：型号、编号这类字符级区分在语义空间里被抹平 | 是否存在大量精确字符串检索 |
| 检索结果必须人工复核 | 结果附原件路径并按模态分组 | 不选只回相似度分数：复核要回到原件，缺路径等于把成本转给人 | 复核环节是否真实存在 |

本节最常被误选的一对，是**「统一向量空间」与「模态专属编码器」**。机制差别很直接：统一向量的可比性来自「所有模态共用一组维度与容量」，它买的是跨模态检索的可能性，付的是每种模态的表示精度。误选的实际暴露方式是：把全部模态压进一个通用对齐空间，上线后发现主力模态（通常是中文文本或专业图像）的检索质量还不如原来的专用方案，却因为「分数看起来正常、召回率没有基线」而长期查不出原因；反过来，在本该跨模态的场景里坚持各模态独立编码，结果是跨模态查询根本做不出来。

### 3.4 组合模式：真实系统不会只用一种

**组合一：湖仓（原件与批量加工）+ 向量库（在线检索）+ 关系库（条件与权限）**

- 构成：湖仓存原件与可分析表，向量库只承载在线近邻，关系库存元数据、权限与关联键；三者靠 item_id 与增量同步衔接。
- 职责边界：湖仓管「不可变的原件与可重建的派生物」，向量库管「毫秒级近邻」，关系库管「条件筛选与访问控制」，任何一方都不试图包办。
- 运维代价：三条同步链路、三套权限、三套备份；必须有「向量库与湖的差异可查」的指标，否则不一致是静默的。
- 适合规模：PB 级、以新增为主、同时要服务训练与在线检索的组织（本章 [§1.4 阿里案例](01-multimodal-db-section-6-sec6.md)）。

**组合二：统一向量空间（召回）+ 条件过滤（收敛）+ 多模态 LLM（生成）**

- 构成：统一空间负责跨模态召回，结构化条件把候选收敛到业务允许的集合，多模态 LLM 只对收敛后的 Top-K 做理解与生成。
- 职责边界：召回不负责精确、过滤不负责语义、生成不负责检索；三段各自可测（Recall@K / 过滤后候选量 / 端到端正确率）。
- 运维代价：三段要分别建评估集，端到端指标无法定位是哪一段坏了；上下文组装与引用回链是额外工程。
- 适合规模：多模态问答、文档助手这类端到端场景 【经验】（本章 §6 收录的四个案例都止于「检索 + 原件回链」，没有生成层，故此组合不给案例引用；检索段与生成段的划分方式见 [§4.1 落地步骤](01-multimodal-db-section-4-sec4.md)）。

**组合三：图像/视频原件外置 + 摘要与向量入库 + 检索结果直达原件**

- 构成：原件留在对象存储，库内只放可检索摘要（关键帧向量、统计特征、文本描述），结果返回原件路径供人工查看。
- 职责边界：存储管容量与成本，库管「可检索的那一部分」，前端负责把分数翻译成工程师能看的原件。
- 运维代价：摘要与原件的对应关系要可校验（摘要存在、原件被删是最常见的脏数据）；权限要在库与对象存储两侧同时生效。
- 适合规模：图像/视频占比高、检索后必须人工复核的场景 【经验】。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 为每个模态单独建库 | 一次跨模态查询要在 4~5 个系统之间拼装；同一条目在不同库里状态不一致 | 跨系统关联只能靠应用层拼装，一致性无事务保证，孤儿记录长期存在 | 每个模态各由一个团队选型，没人负责跨模态的那一步 | 统一关联键 + 同表/同库混合查询，或至少统一元数据与权限 |
| 忽视 OCR / ASR 质量 | 检索结果里出现明显错字；同一个实体在不同文档里被识别成不同字符串 | 上游错误不可逆地传播到向量、索引与答案，且下游无法分辨是检索问题还是提取问题 | 把 OCR/ASR 当「预处理小工具」，没有准确率基线与抽检 | 对 OCR/ASR 单独建准确率基线并持续抽检；关键字段保留人工复核 |
| 用单一 Embedding 模型 | 中文/专业领域查询效果差；检索换一个说法就找不到 | 一个通用对齐空间为容纳多模态压低了每种表示的精度，域外表现进一步下滑 | 「有一个能用的模型就先上线」，且没有召回率基线可对比 | 用真实数据集做召回率基准测试；按语言与领域选模型（中文图文可看 BGE-VL / Qwen-VL 一类）或做领域微调 |
| 不存原文件 | 检索命中后取不到原件；复核时无法判断对错 | 只有向量时结果不可复核，也无法重算向量（换编码器即全库作废） | 为了省存储只留向量，或先把向量当成了数据本身 | 原件外置对象存储 + 库内留路径与校验和，保证向量可重建 |
| 忽视模态对齐 | 不同模态向量维度不同，跨模态查询报维度错或结果随机 | 跨模态检索在物理上不成立，任何跨模态排序都是假的 | 各模态各自选模型，没人检查输出维度与空间是否一致 | 显式规定统一维度与坐标系；用成对样本做跨模态召回验证 |
| 过度依赖 LLM 多模态 | 用多模态 LLM 直接读全部页面；成本与延迟随页数线性上涨 | 成本按「页面数 × 提问数」增长，且延迟不可控，多数查询其实一次近邻就能满足 | 大模型效果惊艳，忽略了它只能处理被喂进去的那一小部分 | 先 Embedding 检索再让 LLM 处理 Top-K；为每类查询设成本上限 |
| 不处理时序 | 视频抽帧后顺序丢失，事件先后无法判断 | 时序是视频与点云的一等信息，丢掉之后「发生了什么」不可恢复 | 把视频当成"一堆图片"，按图像流水线处理 | 帧与时间戳一起存；顺序敏感场景保留时间轴或分段摘要 |
| 忽视存储成本 | 库体积与备份时间快速增长；相似度检索变慢但磁盘先满 | 大文件入库把存储与备份成本推到关系库不适配的量级，检索性能被同时拖累 | 先按"能跑通"实现，把压缩与归档留到以后 | 大文件外置 + 分级存储与归档策略 + 生命周期规则 |

**「用单一 Embedding 模型」是最隐蔽的一条，因为它不会报错、只会悄悄变差。** 生产里的暴露方式通常是：检索功能上线时抽测有效，几个月后【经验】业务反馈「搜不准」，但监控里延迟、成功率、索引健康全绿——因为质量从来没有基线可对比。判据很短：有没有一份固定查询集的 Recall@K 记录，以及这份记录最近一次更新是什么时候；没有基线的检索质量，等于不可观测。

**「忽视 OCR / ASR 质量」是最不可逆的一条。** 机制上，抽取错误会同时污染向量、文本索引与后续所有评估，而下游系统无法区分「模型没搜到」与「原文就没提取对」；更麻烦的是它不可回头——原始版面一旦丢弃，重跑已经没有输入。所以关键字段必须保留原件与校验和，OCR/ASR 必须有独立的准确率抽检。

**「为每个模态单独建库」不会以「慢」的形式暴露，而是以「对不上」的形式暴露。** 各模态的库各自可用，问题是它们对同一个条目的状态认知不同：向量库里有、元数据里没有，或者原件已删而索引还在。这类不一致没有事务可以挡，只能靠统一关联键、统一权限与一条可查的差异指标来收敛。

### 3.6 规模跃迁时模式何时该换

> 下表全部为**情景阈值**【经验：按区间判断，不是测量值】——它只回答「跨过了哪个台阶」，不回答「跨在第几个」；规模档位的量级推导见本章 [§ 7 与其他方法对比](01-multimodal-db-section-7-sec7.md) §7.5 决策树与 §7.4 的体积推导；请代入自己的实际规模。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单模态 → 多模态 | 单模态向量检索 | 每加一种模态就多一条检索链路与一套分数，跨模态排序拼不出来 | 统一向量空间，或统一元数据 + 关联键 | 统一空间要全库重算向量；统一元数据要新建关联键并回填历史数据 |
| 千万 → 亿级【经验】 | 单机向量索引 | 索引重建时间与内存撞上硬上限，召回率随规模悄悄下降 | 分布式或托管向量库（分片 + 在线扩缩） | 索引类型与参数要重调，必须重建召回率基准，扩容窗口要设计 |
| 只增不改 → 频繁更新 | 湖 + 异步向量库 | 同步落后于更新，检索到已删或已更新条目 | 条件与向量同表 / 同库，或 CDC 驱动的增量同步 | 写入路径变长、事务边界要重划，更新放大与延迟都要重新预算 |
| 纯检索 → 端到端问答 | 检索服务 | 业务要答案，团队各自在应用层拼 LLM，口径与引用各不相同 | 多模态 RAG（检索层与生成层分离且各自可测） | 评估从 Recall@K 扩展到端到端；成本模型从存储转向每问推理 |
| 内部单租户 → 多租户 SaaS | 单命名空间 | 租户之间可能越界，配额与成本无法归因 | 命名空间隔离 + 配额与计量 | 索引与配额规划成为常驻工作；跨租户的缓存不能复用 |
| 库内加工 → 数据不出侧 | 把原件导出到算力侧向量化 | 搬运成本与合规风险双高，且链路越长越难治理 | 在原侧加工（仓内 / 平台内向量化） | 加工能力受平台限制，模型与算子要跟着平台走 |

补一句判据：**当「新数据的向量化与索引更新」追不上「新数据的产生速度」时，就该换模式**——要么缩短同步链路，要么把检索层改成可增量更新的形态。另一条同样有效的判据是：**当过滤后的候选集大到向量索引无法把它当作过滤条件时，就该把条件搬进检索内部**，否则「先筛后搜」只是名义上的两步，实际退化成全库近邻加求交集。

### 3.7 自检清单

1. 有没有一份固定查询集与它的 Recall@K 记录？没有，则检索质量处于不可观测状态。
2. 跨模态检索的两侧编码器，输出维度与坐标空间是否显式规定过？没有规定，"跨模态"可能根本不成立。
3. 结构化条件是在检索前参与筛选，还是检索后裁剪？后者在条件选择性强时会把 Top-K 裁空。
4. 库里是否存了原始大文件？存了，则备份体积与检索性能是同一批问题的两个表现。
5. 每条向量能否重建（原件 + 编码器 + 版本是否都在）？不能，则换编码器等于数据作废。
6. 向量与元数据是否可能不一致（异步同步链路）？是，则必须有「差异条目数」这个指标。
7. OCR / ASR 是否有独立的准确率基线，关键字段是否保留人工复核路径？
8. 视频 / 点云的时序信息是否与向量一起保留？只留帧序不存时间戳，事件顺序不可恢复。
9. 是否存在用多模态 LLM 直接读全量页面的查询路径？存在，则成本与延迟不可控。
10. 相似度分数是否被当作绝对可信？换过编码器或索引参数后，旧分数与新分数不可比。
11. 检索结果是否附原件路径（而只给分数）？只给分数，复核环节会退化成人工翻库。
12. 是否设了分级存储与归档策略，并验证过实际生效？只写在文档里的策略不算生效。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 跨模态是主需求 | 统一向量空间 | 同维同空间才有可比性，跨模态排序才成立 |
| 条件筛选强、模态各异 | 模态专属 + 元数据关联 | 每段用最优引擎，条件与近邻分工；但关联键必须唯一 |
| 团队小、模态还在增 | 多模态原生数据库 | 过滤与近邻由同一执行器安排，少掉跨系统拼装 |
| PB 级、以新增为主 | Lakehouse + 向量库 | 湖是唯一事实源，向量是可重建派生物，存储便宜 |
| 要答案不要候选 | 多模态 RAG | 成本与上下文规模成正比，而非与语料规模成正比 |
| 扫描件 / 复杂版式 | ColPali 一类多模态文档检索 | 检索直接在页面上做，版面信息不必经过 OCR |
| 实时推荐、毫秒级 | 多模态 Embedding + 向量库 | 少一跳；前提是元数据条件能参与检索 |
| 频繁更新 | 条件与向量同表 / 同库 | 缩短同步链路，避免检索到已删条目 |

> 本节小结：本主题下决定模式选择的**唯一那条最前置的约束，是「模态之间的可比性从哪来」**——跨模态检索能不能做，取决于各模态有没有被投进同一组维度与坐标系；这一条不成立，其余选择全都失去意义。可比性成立之后，二次筛选由两件事决定：过滤条件的选择性（决定过滤与近邻谁先发生，也就是「先筛后搜」还是同表混合），以及原件是否不可变（决定能否用湖 + 可重建向量库这条便宜路线）。而多模态 LLM 始终是这条链路的下游消费者，把它放进上游，成本与不可解释性会一起失控。
