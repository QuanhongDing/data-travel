## 4. 工程实现

§3 讲的是「在你那组约束下该选哪种形态」，本节讲的是「选定之后怎么把它立起来，以及存量数据怎么办」。两者不重叠：一段话如果只是在复述统一向量空间或 ColPali 的机制，它属于 §3，本节只留引用。

本文件对两类读者的重心不同。**§4.1–§4.3 两边都成立**（步骤、机制与选型判据与起点无关）；**§4.4 只写给存量改造者**——维度的特别之处在于，多模态的存量改造常常不是「迁移数据」，而是「原件已经找不回来了」，分类规则与别的章节不同；**§4.5 的模板、§4.9 的自检清单与 §4.10 的小结**两边都能直接用。从零搭建的读者请重点看 §4.1 的 Step 1 与 §4.4 的第 ② 段：它们定的不是「今天能不能跑通」，而是「换编码器那一天有没有退路」【经验：换编码器的时点随模型迭代节奏与合规要求而变，通常在一两年之后，不是上线时】。

### 4.1 落地步骤

**Step 1：模态清点（1–2 周【经验：随模态种类与是否已有资产台账而变】）**

- 盘点企业数据模态（文本 / 图像 / 音频 / 视频 / 表格 / 3D），逐类标出体量级、增长率、以及**已有真实查询需求**。
- 对每一类记两件事：**预处理是否不可逆**（OCR / ASR / 抽帧属于不可逆），以及**原件是否必须保留**（合规、复核、以及换编码器时要重算）。
- **产物**：多模态资产清单（模态 × 体量级 × 预处理方式 × 原件去向 × 负责人）。
- **判据**：抽 3 个已经存在的查询需求，能在清单里指到对应的模态、预处理链路与原件位置。指不到，说明清单是按系统盘出来的，不是按数据盘出来的。
- **为什么必须这一步 / 为什么在这个位置**：它决定后面两步的边界。跳过它直接做编码器选型，会在上线后才发现「占比最大的那一类模态没有对应编码器」，或者「这一类的前处理已经把需要的信息丢掉了」。

**Step 2：预处理 Pipeline（2–6 周【经验：随模态种类与原件质量而变】）**

- 接 OCR（PaddleOCR / Tesseract）、ASR（Whisper / Paraformer）、抽帧（ffmpeg，1 帧/秒或关键帧【经验：起点参数，按场景调整】）、文档结构化（PyMuPDF / Unstructured）。
- 关键字段保留人工复核路径；预处理结果与**原件路径、校验和**一起落库。
- **产物**：结构化 + 文本化的多模态数据，以及每一类预处理器的准确率基线。
- **判据**：抽 30 份原件，人工核对 OCR / ASR 输出，得出这一批的实际准确率并记下来。没有这份记录，后面的检索质量问题无法归因到「没搜到」还是「没提取对」。
- **为什么必须这一步 / 为什么在这个位置**：预处理是不可逆的——版面信息在转文本时就丢了，之后无论换什么编码器都补不回来。它必须在编码器选型之前定下来。

**Step 3：Embedding 模型选型（2–4 周【经验：随候选模型数量与成对样本的获取难度而变】）**

- 按模态选候选：图文 CLIP / OpenCLIP / BGE-VL / Qwen-VL；音文 CLAP / Whisper Embedding；文档 ColPali / LayoutLMv3；视频 VideoCLIP / InternVideo。
- 显式规定**统一维度与坐标系**，并用成对样本做一次跨模态召回验证。
- **产物**：多模态向量库（含编码器名称与版本、维度记录）+ 召回率基线。
- **判据**：用同一份固定查询集在候选模型上各跑一遍 Recall@K，择优再上线。**换编码器意味着全库重算**，所以必须先比完再写第一批数据。
- **为什么必须这一步 / 为什么在这个位置**：编码器决定向量空间，向量空间一经采用就是一次全库重建的代价。放在存储架构之前，索引的维度与距离度量才有依据。

**Step 4：存储架构（2–4 周【经验：随是否已有对象存储与元数据库、以及关联键要跨几套系统对齐而变】）**

- 选向量库（Milvus / Qdrant / Weaviate / pgvector）；原文件存 OSS / S3（本地可用 MinIO 替代）；元数据存 PostgreSQL；决定用多模态原生数据库（SurrealDB / Weaviate）还是自建组合。
- 大文件一律外置，库内只留路径与摘要；把**关联键（item_id 一类）**当作跨系统契约写进设计文档。
- **产物**：可检索的多模态数据库 + 关联键定义 + 原件去向约定 + 向量与元数据的写入顺序。
- **判据**：入库 3 条数据后，能否只凭库内信息把原件取回来、并用记录的编码器重算出一致的向量。取不回或算不出的，说明「可重建」这条前提不成立。
- **为什么必须这一步 / 为什么在这个位置**：关联键是后面所有跨系统拼装的唯一契约，必须在写第一批数据之前定下来——它定晚了，历史数据的回填就是一次全量重跑。

**Step 5：检索 Pipeline（2–4 周【经验：随过滤条件的复杂度与精排是自建还是用现成组件而变】）**

- 打通跨模态检索（以文搜图 / 以图搜文 / 多模态混合）；元数据过滤（时间 / 来源 / 权限）必须**参与检索**而不是检索后裁剪；加一层精排（CLIP-ViT-L / 多模态 Reranker）。
- **产物**：Top-K 多模态结果，附原件路径并按模态分组。
- **判据**：构造一个条件选择性很强的查询（某品牌 + 某时间窗），确认 Top-K 不为空。空了就是过滤被放在了检索之后。
- **为什么必须这一步 / 为什么在这个位置**：过滤与近邻的先后顺序决定召回是否被裁空，而这一步的改动会同时影响索引参数选择，所以要在索引定型之前暴露出来。

**Step 6：多模态 RAG（2–6 周【经验：随查询类型数量与是否强制引用回链而变】）**

- 把检索结果喂给多模态 LLM（GPT-4V / Claude 3.5 / Qwen-VL 一类），生成答案 + 引用，引用要能回链到原件。
- 为每一类查询设成本上限，并让超限的请求被拒而不是被降级到静默失败。
- **产物**：多模态问答系统 + 引用回链 + 每类查询的成本上限。
- **判据**：抽查 10 个答案，统计其中几条的引用能回链到原件。不能回链的答案无法复核，等于把成本转给人。
- **为什么必须这一步 / 为什么在这个位置**：生成层依赖前面全部产物（检索质量、原件路径、成本模型）。它必须在检索层有一条可独立评估的出口之后再做，否则端到端指标一差，你分不清是没搜到还是被解释错。

**Step 7：评估与监控（1–2 周搭起【经验：随需要接入的评估块数与可复用的监控组件而变】，之后长期运行）**

- 多模态检索评估（Recall@K / mAP）、OCR / ASR 准确率评估、端到端问答效果，三块各自成表；把召回、索引健康、成本接进同一块大盘。
- **产物**：评估报告 + 监控大盘（召回 / 索引 / 成本三块）。
- **判据**：能说出召回率基线最近一次测量是什么时候、当时用的是哪份查询集。说不出，说明检索质量处于不可观测状态。
- **为什么必须这一步 / 为什么在这个位置**：它是唯一的「坏了会知道」机制。放在最后不是因为它最不重要，而是因为它要消费前面所有环节的输出。

最常被跳过的是 **Step 1 的「预处理是否不可逆」**与 **Step 3 的「召回率基线」**。前者跳过后不会有任何即时症状——症状要等到换编码器时集中爆发【经验：这个时点通常在一两年之后，随模型迭代节奏与合规要求而变】：没有原件，向量不可重建，全库作废。后者跳过后的症状是上线几个月内业务反馈「搜不准」，而监控里延迟、成功率、索引健康全绿——因为质量从来没有基线，所以没有一条曲线会动。

### 4.2 关键技术点

**多模态 Embedding（CLIP / ImageBind / Qwen-VL，统一向量空间）**

- **做法**：选定一组能输出同维同空间向量的编码器，文本与图像（音频、视频按需）共用；建立**编码器登记表**，逐条记下编码器名称、版本、输出维度、训练目标与它服务哪几个模态。
- **机制**：共享空间的收益与代价（机制见 [§ 3.2.1](01-multimodal-db-section-3-sec3.md)）只有在换一次编码器时才会变成账单，而账单大小由登记表决定——登记表全，换模型就是一次可排期、可按模态分批的重算；登记表只有一条总分，换模型就变成一次谁也不敢动的全库停工。CLIP 由 OpenAI 提出【公开】（*Learning Transferable Visual Models From Natural Language Supervision*，2021；ViT-B/32 输出 512 维、ViT-L/14 输出 768 维）；ImageBind 以图像为锚点把六种模态对齐到同一空间【公开】（Meta，2023）。
- **失效条件**：**当登记表由各团队各自维护、召回基线只留一条总分时**，某一模态的精度下滑会被总分掩盖——症状是**新增一个模态后总分不降反升，而主力模态的召回连续两次评估都在退**；因为基线没有按模态分列，你拿不出「这个模态该不该单独编码」的证据，只能凭感觉换模型。
- **档位**：【经验】——总分与按模态基线的偏离幅度随训练分布与业务领域的距离变化。

**OCR / ASR 工具链（PaddleOCR / Whisper）**

- **做法**：为关键字段指定 OCR / ASR 引擎，对关键字段保留人工复核路径，并把每次抽检的准确率记进基线。
- **机制**：因为预处理器是链路最上游的一环，换引擎、换版本、换参数都会让下游产物全部重算，所以这一步的验收物不是「跑通了一次」，而是**准确率基线 + 抽检节奏 + 一份能追责的复核记录**（不可逆与传播路径见 [§ 3.5](01-multimodal-db-section-3-sec3.md) 反模式表）。代价是复核环节持续消耗人力，且准确率会随文档版式与音频质量漂移。
- **失效条件**：当版式复杂（表格、印章、手写）或音频有口音 / 多说话人时准确率会显著下降——本节要盯的症状是**抽检记录里同一字段的准确率在不同批次之间掉档**，或关键字段的人工复核退回率突然升高；这两种信号比「检索结果里出现错字」出现得更早，也更容易定位到是哪一类原件在拖后腿。
- **档位**：【经验】——不要沿用别人的准确率数字，只能用你自己抽检出来的那一份。

**视频处理（ffmpeg 抽帧、关键帧检测、VideoCLIP / InternVideo）**

- **做法**：抽帧（1 帧/秒或关键帧【经验】），帧向量入向量库，同时把**时间戳**与帧序号一起存；顺序敏感的场景额外存时间轴或分段摘要。
- **机制**：因为视频的一等信息是「什么时候发生了什么」而不是「有哪些画面」，只把视频当一堆图片处理会丢掉顺序；代价是时间轴要跟着向量一起维护，索引结构与查询语法都要扩。
- **失效条件**：当查询依赖事件先后（某动作是否发生在其后）时，只存帧序不存时间戳会让事件顺序不可恢复——症状是**答案里的先后顺序颠倒，而检索分数完全正常**，这类错误在只看分数的监控上不可见。
- **档位**：【经验】。

**向量库（Milvus / Qdrant / Weaviate / pgvector）**

- **做法**：选型时先问一个问题——**过滤条件能不能作为检索的一部分参与**（带过滤的近似检索），再问规模档位。
- **机制**：因为「条件参与检索」是引擎能力而不是一个配置项，选型阶段不能只看功能列表，要看**实测**：把一条真实查询原样跑一遍，再加一个高选择性条件跑第二遍，两次的召回与 P99 一起看（顺序如何影响候选集见 [§ 3.2.2](01-multimodal-db-section-3-sec3.md)）。代价是带过滤的近似检索会牺牲一部分召回（过滤越强，可走的图越少）。
- **失效条件**：**当过滤条件的选择性降到索引无法把它当作高效过滤来用时**（触发量级见 [§ 3.2.2](01-multimodal-db-section-3-sec3.md)，且随索引类型、维度与内存预算变化，以你自己压测出来的数为准），「先筛后搜」会退化成全库近邻再求交集——本节要盯的症状是**同一条查询去掉过滤条件后延迟与召回双双恢复正常**；这个「加条件 / 去条件」的对照是判断过滤有没有真正参与检索最省事的做法，只看大盘上的平均延迟是看不出来的。
- **档位**：【经验】。

**对象存储（OSS / S3 / MinIO）**

- **做法**：大文件一律外置，库内只留路径与校验和；权限在库与对象存储两侧同时生效；生命周期规则要在设计时就把「原件不可删」这条排除掉。
- **机制**：因为向量的可重建性完全依赖原件——没有原件就无法重算向量，换编码器等于全库作废。代价是多一跳取件、多一套权限与一套校验。
- **失效条件**：当生命周期规则把原件归档或删除、而库内路径还在时，系统会进入「检索能命中、原件取不回」的状态——症状是**复核环节退化成人工翻库**；这也是最难在事后修复的一类不一致。
- **档位**：【经验】。

**多模态 LLM（GPT-4V / Claude 3.5 Vision / Qwen-VL / InternVL）**

- **做法**：只对检索后的 Top-K 调用，不整库喂；为每类查询设成本与延迟上限。
- **机制**：因为成本随「送进去的页面数 × 提问数」增长（成本结构见 [§ 3.2.5](01-multimodal-db-section-3-sec3.md)），这条在工程上的落点是**预算控制**而不是模型选型：先定每类查询允许送进多少页、单价上限多少，再在这些约束下挑模型。代价是答案质量的上限被检索的召回锁死。
- **失效条件**：**当问题需要跨多个文档聚合时**，Top-K 检索的前提不再成立（失效点见 [§ 3.2.5](01-multimodal-db-section-3-sec3.md)）——本节要盯的症状是**把 Top-K 调大之后正确率不动、账单却按比例上涨**；这说明缺的是聚合方式而不是检索条数，继续加 K 只是把成本推高。
- **档位**：【经验】。

**元数据管理（PostgreSQL + 数据目录）**

- **做法**：关联键唯一且全局一致；元数据与向量在同一事务或同一条写入路径里落库；把模态、来源、时间、权限、原件路径作为必备字段。
- **机制**：因为关联键是跨系统拼装的唯一契约，而跨系统写入没有共同事务，这条的工程形态只能是二选一——要么把元数据与向量放进同一条写入路径（同表 / 同库），要么接受异步并配一套可校验的补偿（取舍与代价见 [§ 3.2.2](01-multimodal-db-section-3-sec3.md)）。代价是元数据成为新的关键路径，它的变更要管版本。
- **失效条件**：**当元数据与向量分属两套系统、而写入路径没有补偿时**，不一致会偏向写入顺序的后半段【经验：偏向哪一侧随写入路径是「先元数据后向量」还是反过来而变】——本节要盯的症状是**差异条数只单向增长**：一直只有「有元数据没向量」，说明补偿逻辑补错了方向；两侧同时涨，说明该停下来查写入路径、而不是把对账频率调高。这类不一致没有事务可挡，它的正确性只能靠一条单独计算的差异条目数来观察。
- **档位**：【经验】。

**跨模态检索（统一向量空间 + 元数据过滤）**

- **做法**：显式规定统一维度与坐标系，用成对样本验证跨模态召回，再让元数据条件作为过滤参与检索。
- **机制**：因为跨模态排序成立的前提是两侧向量同坐标系，这条在工程上的落点是**写入期契约**：维度与坐标系写进关联键定义，写入路径上校验，谁引入新编码器谁负责跑一次跨模态召回验证（坐标系与可比性见 [§ 3.2.1](01-multimodal-db-section-3-sec3.md)）。代价是契约一旦变更就是全库重算。
- **失效条件**：**当新模态由另一个团队接入、而写入路径上没有维度 / 坐标系校验时**，错误会以「排序看起来合理但不可复现」的形式出现——同一条查询隔一天再跑，Top-K 的次序会变；这类问题不该靠肉眼比对答案去发现，判据是抽 3 条向量核对维度与坐标系，对不上就先补写入校验、再谈模型。
- **档位**：【经验】。

**多模态 Reranker（CLIP-ViT-L / 多模态 Cross-Encoder）**

- **做法**：对召回出的 Top-N 做一次精排，再返回 Top-K。
- **机制**：因为双塔检索两侧独立编码，查询与候选之间没有交互，相似度是近似的；精排让两者在同一模型里交互，排序质量上升。代价是延迟与算力——精排的计算量随 N 增长，且它天然是串行的最后一段。
- **失效条件**：当 Top-N 设得大或 QPS 高时，精排成为延迟瓶颈——症状是**P99 被精排段吃掉，而召回段很闲**（可在 Query Trace 上分开量）。此时该做的是调 N 或加缓存，而不是换向量库。
- **档位**：【经验】。

**多模态 RAG（ColPali / LayoutLMv3 / GPT-4V + RAG）**

- **做法**：检索层与生成层分离，各自有独立评估集（检索看 Recall@K，生成看正确率与引用是否对得上）。
- **机制**：因为把生成能力接进检索链路会把可测性从两段压缩成一段，出了问题既不知道是没搜到、还是搜到了却被解释错，所以这套做法的产物里最重要的不是链路本身，而是**两份互相独立、谁都改不了对方的评估集**。ColPali 一类方案的索引形态与适用边界见 [§ 3.2.6](01-multimodal-db-section-3-sec3.md)（论文 *ColPali: Efficient Document Retrieval with Vision Language Models*，2024【公开】）。
- **失效条件**：**当评估集只覆盖「答案在版面上」的那类问题、而线上还有相当比例的精确字符类查询时**——本节要盯的症状是**评估集上的指标持续达标，线上却总有一类查询被反复退回人工**；这时不要急着换模型，先把线上样本按查询类型（版面类 / 字符类）切成两组，看退回的是哪一组，再决定补稀疏召回还是补 OCR 通道（纯视觉多向量的边界见 [§ 3.2.6](01-multimodal-db-section-3-sec3.md)）。
- **档位**：【经验】。

### 4.3 工具链与平台

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 多模态原生数据库 | SurrealDB / Weaviate / TigerData 与 TigerGraph / Aerokog（待核，见下）/ SingleStore | 判据是「过滤与近邻能否由同一个执行器安排顺序」再加「团队能不能只运维一套系统」——团队三到五个人【经验：随模态种类与团队既有运维能力而变】的新项目才划算 | 一体化能力在每一维上都低于该维的专用系统：一旦某个模态需要精细调优（版面检索、图遍历），会发现哪一样都不够用 |
| 通用向量库 | Milvus / Qdrant / Weaviate / Pinecone / pgvector | 判据有两条：**过滤能否参与检索**，以及**规模档位**——单库能力内、元数据本来就在关系库 → pgvector 一类同库方案；需要分布式与在线扩缩 → 分布式向量库；不想自建分片 → Pinecone 一类托管 | 选到不支持带过滤近似检索的库，条件一加就得全库近邻再求交集；选到需要自建分片的库，扩容变成「重新索引 + 停机窗口」 |
| 文档数据库（多模态支持） | MongoDB Atlas / ArangoDB / Cosmos DB | 判据是「现有元数据是不是已经在这里」——把向量放到元数据已经在的地方，省掉一条关联链路；如果元数据本来就在关系库，为了向量再引一套文档库是净增负担 | 多一套系统就多一套备份、监控、权限与一条必须保持同步的链路，孤儿记录的概率随之上升 |
| 多模态 Embedding 服务 | OpenAI CLIP（`GPT-4V` 一类是视觉理解模型，不是嵌入端点；嵌入端点名与维度以厂商文档当前版本为准）/ 阿里通义 Qwen-VL / BGE-VL（BAAI）/ Jina CLIP / Cohere Embed v3 / Replicate | 判据有三个：**语言与领域**（中文长尾是否在训练分布里）、**能否本地部署**（数据能否出域）、**输出维度是否与检索层约定一致** | 通用对齐模型在域外表现会下滑，而它不会报错：症状是检索「看起来正常、实际搜不准」，没有按语言与领域分的召回基线时查不出来 |
| 多模态 RAG 工具 | ColPali / Unstructured.io / PaddleOCR + LangChain / GPT-4V + RAG / Qwen-VL + RAG | 判据是「答案是否长在版面里」：扫描件、财报、表单 → ColPali 一类跳过 OCR 的多向量方案；信息在文本流里就够 → OCR + 文本检索更省也更可控 | 在需要精确字符匹配的场景选纯视觉多向量，字符级命中弱于稀疏匹配；反过来在扫描件上用纯 OCR，版面信息在一次抽取里就不可逆地丢了 |

表里最容易被误选的是**把「多模态原生数据库」当作默认起点**——因为它宣传上「一个系统全包」。机制上的代价在于：一体化产品必须在多种能力之间做取舍，而每一种能力都有比它更深的专用系统。误选的暴露方式很典型：起步阶段非常顺利（模态少、规模小、过滤简单），等到要为某一个模态单独做精细调优、或者规模跨出单机能力时，才发现没有可替换的局部。**判定方法**：问一句「如果明年只把某一个模态的检索换掉，要动几套系统」——答案是一套里的大半，就说明这个选择把退路押上了。

另外三点说明：上表中 **Aerokog（待核）** 一项——引用前请以其官方站点与文档的当前版本为准，并按「有没有可查的第三方生产案例」这一条自行核验；核到之前，不建议把它当作主力存储的候选。**TigerData 与 TigerGraph 是两家不同的公司**，引用时不要合并成一个产品名，选型前先分别核对它们各自支持的模型类型。上表其余候选（BGE-VL / Jina CLIP / Cohere Embed v3 / Qwen-VL / Replicate 等）按同样的两条核验：官方文档当前版本 + 有没有可查的生产案例；**产品归类也别照抄厂商的营销话术**——同一个厂商的视觉理解模型与嵌入服务常常是两条不同的产品线，把前者的型号当成嵌入端点填进设计文档，会在联调时才发现调不通。

### 4.4 存量迁移

多模态的存量迁移与别的主题有一处根本不同：**别的主题迁移的是数据，这里迁移的常常是「已经找不回来的东西」**。向量是从原件算出来的派生物，原件丢了，向量就只能一直用旧编码器算，换模型的代价从「重建索引」变成「不可完成」。所以分类规则要从「原件还在不在」开始。

**① 先做立刻见效且可回退的那一步：同表试水，只写新增。** 在现有关系库上加一张表，把**元数据、向量、文件路径**放在同一张表里（形态参见 [§ 1.1 某 SaaS 案例](01-multimodal-db-section-6-sec6.md)），只对**新进来**的数据写入，现有读取路径一个字不改。回退方式就是删掉这张表。这一步在几周内就能给出一个真实的判断：新增数据的量级、向量化的耗时、以及同表混合查询的延迟到底能不能接受。

**② 历史资产按「原件还在不在」分四类：**

- **原件在、也从未编码**：正常排期批量编码。这类是主流，成本主要是算力与时间。
- **原件在、已有编码器产物**：保留旧向量继续服务，直到明确要换模型时整体重算。**不要为了换模型而换模型**——重算是一次全库作业。
- **OCR / ASR 产物在、原件已丢**：直接**打标挂账**。这类资产不可重建，必须登记「用哪个编码器、哪个维度、不可重算」，否则未来某次模型升级会把它变成一堆无法解释的旧向量。
- **大文件当年被塞进了库里**：先外置到对象存储、回填路径与校验和，再谈别的。备份体积与检索性能是同一批问题的两个表现。

挂账的每一条都要写清「为什么现在不处理」和「复审日期」，否则挂账会变成永久盲区。

**③ 双轨期要盯两个数，而不是一个。** 新旧两条检索路径并行时，除了一条一致性指标（同一查询在两条路径上的结果差异条数），还要单独盯 **孤儿记录数**——有向量没元数据、有元数据没向量。多模态的不一致几乎都以孤儿的形式出现，而不是以「查询报错」的形式出现；没有这个数，双轨期的正确性无法判断。双轨维持多久【经验：随写入频率与复核频率而变，以能覆盖一个完整的对账周期为下限】。

**④ 退出双轨的信号。** 三个同时满足：孤儿记录连续归零、新路径上的召回基线达到或超过旧路径（用同一份固定查询集测，而不是用感觉）、旧索引的读取量归零且旧编码器依赖已被移除。**只满足前两个就退出是常见错误**——旧索引还在、旧凭据还在，几个月后某个脚本会重新写回旧路径。

### 4.5 模板 / 示例

**模板 1：CLIP 图文检索**

```python
from transformers import CLIPProcessor, CLIPModel
from PIL import Image

model = CLIPModel.from_pretrained("openai/clip-vit-large-patch14")
processor = CLIPProcessor.from_pretrained("openai/clip-vit-large-patch14")

texts = ["a cat", "a dog", "a car"]
images = [Image.open(f"image_{i}.jpg") for i in range(10)]

outputs = model(**processor(text=texts, images=images, return_tensors="pt", padding=True))
probs = outputs.logits_per_image.softmax(dim=1)   # 图像-文本相似度
```

**怎么用**：这是**验证「统一向量空间成不成立」的最小脚本**——把同一批图文对跑一遍，看匹配对的分数是否稳定高于不匹配对。维度那一格（这里是 ViT-L/14 的 768 维）要与你写进元数据的记录一致；换模型请同时换模型名与维度两处。

**模板 2：多模态向量库（Milvus 一类）的 schema 与带过滤检索**

```python
from pymilvus import connections, Collection, FieldSchema, CollectionSchema, DataType

connections.connect(host="milvus", port=19530)
fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True),
    FieldSchema(name="text", dtype=DataType.VARCHAR, max_length=512),
    FieldSchema(name="image_path", dtype=DataType.VARCHAR, max_length=256),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=512),
    FieldSchema(name="modality", dtype=DataType.VARCHAR, max_length=16),
    FieldSchema(name="timestamp", dtype=DataType.INT64),
]
collection = Collection("multimodal", CollectionSchema(fields=fields, description="multimodal collection"))
collection.create_index("embedding", {"index_type": "IVF_FLAT", "metric_type": "IP", "params": {"nlist": 1024}})

# 以文搜图，且模态过滤作为检索条件参与，而不是检索后再裁
results = collection.search(
    data=[text_embedding],
    anns_field="embedding",
    param={"metric_type": "IP"},
    limit=5,
    expr='modality == "image"',
)
```

**怎么用**：填三格——`dim` 必须等于你选定的编码器输出维度；`metric_type` 必须与编码器的训练目标匹配（用错度量，排序就是错的）；`expr` 要放**选择性高的条件**，并用「条件加上后结果是否变空」检验它是否真的参与了检索。索引类型与参数是起点，不是结论，请随数据量级重调并留一次召回率记录。

**模板 3：多模态文档 RAG（ColPali 一类）**

```python
from byaldi import RAGRetrieval            # 具体类名以所用库的当前版本文档为准

rag = RAGRetrieval(model="vidore/colpali-v1.2")
rag.index(input_path="documents/", index_name="docs")
pages = rag.search(query="Q3 营收是多少？", k=5)     # 返回的是页面图像，不是文本块

# 把检索到的页面 + 问题交给多模态 LLM；引用要能回链到页面
from openai import OpenAI                  # 需要 openai-python >= 1.0 的客户端写法

client = OpenAI()
response = client.chat.completions.create(
    model="gpt-4o",                        # 换成你所在区域可用的视觉模型
    messages=[{"role": "user", "content": [
        {"type": "text", "text": "Q3 营收是多少？请基于以下页面回答，并给出页面编号。"},
        # 页面对象里取图像地址的字段名，以你所用的检索库文档为准
        *[{"type": "image_url", "image_url": {"url": p.image_url}} for p in pages],
    ]}],
)
print(response.choices[0].message.content)
```

**怎么用**：要照抄的是**检索单元是「页面」而不是「文本块」**这一条——它决定了索引体积与检索算量按 patch 数放大。库里返回的是图像，所以你的存储与前端必须能承接图像与页面编号，而不是只接字符串。模型名与接口名请以所用库当前版本的文档为准；生成侧按 `openai-python >= 1.0` 的客户端写法（`from openai import OpenAI` + `client.chat.completions.create`），早期那种模块级 `openai.ChatCompletion` 的写法在新版 SDK 里已经移除，照抄会直接报错。

**模板 4：视频 RAG（抽帧 + 编码）**

```python
import ffmpeg
from glob import glob

# 抽帧：1 帧/秒是起点参数【经验：随镜头切换频率与检索粒度而变】，按场景调；同时保留时间戳
ffmpeg.run(ffmpeg.output(ffmpeg.input("video.mp4"), "frame_%04d.jpg", vf="fps=1"))

video_embeddings = []
for i, path in enumerate(sorted(glob("frame_*.jpg"))):
    vec = encode_image(path)
    timestamp = float(i)          # 换成从抽帧元数据里读真实时间戳，不要用帧号推断
    video_embeddings.append({"frame": i, "path": path, "ts": timestamp, "vec": vec})

# 写入：字段顺序与模板 2 的 schema 一致（id / text / image_path / embedding / modality / timestamp）
collection.insert([[e["frame"], "", e["path"], e["vec"], "video", int(e["ts"])]
                   for e in video_embeddings])

# 检索返回 Top-K 帧 → 用 ts 拼回视频片段，而不是只返回帧号
results = collection.search(data=[text_embedding], anns_field="embedding",
                            param={"metric_type": "IP"}, limit=5,
                            expr='modality == "video"')
for hit in results[0]:
    print(hit.id, hit.entity.get("timestamp"))     # timestamp 与帧向量同存，才能拼回片段
```

**怎么用**：填两格——抽帧频率与时间戳来源；写入那一段的字段顺序要与模板 2 的 schema 对齐，顺序不一致会被库拒绝或写错列。**`timestamp` 一定不要用帧号乘出来的近似值**：变速视频、丢帧、合并片段都会让它偏移，而偏移后的时间轴在事件顺序类问题上会给出看起来合理但错误的答案。

**模板 5：同表承载元数据 + 向量 + 文件路径**

```sql
CREATE TABLE item (
  id        bigserial primary key,
  modality  text,            -- text / image / video
  meta      jsonb,           -- 结构化属性，可直接用于 WHERE / JOIN
  file_path text,            -- 指向对象存储的大文件，不存二进制
  embedding vector(1024)     -- 与选定编码器一致的维度
);
CREATE INDEX ON item USING hnsw (embedding vector_cosine_ops);

SELECT id, file_path FROM item
WHERE  modality = 'image' AND meta->>'brand' = 'Nike'
ORDER BY embedding <=> :qvec
LIMIT 10;
```

**怎么用**：填三格——`vector(1024)` 里的维度、`meta` 里实际要筛的键、以及索引类型与距离度量。**大文件那一格只填路径**，这是这张表能不能长期跑下去的关键；把二进制塞进来，备份体积与检索性能会同时失控。

### 4.6 成本：这套东西的账单

多模态的账不是按「行数」结的，是按「模态种类 × 每类流经的算力放大倍数」结的。三项成本里，与本主题真正相关的是这三项：

- **编码算力（一次性 + 增量）**：成本随「单位时间的编码次数」而非数据条数增长。**推算**：一小时视频按 §4.2 的起点帧率 1 帧/秒抽帧 = 3600 帧，每帧一次图像编码，即一小时视频 ≈ 3600 次编码；同等信息量的一批文本可能只有几千条短向量。这就是「这个主题贵在这里」的机制——视频与 PDF 把计费单位从「条」放大到「帧 / 页 / patch」【推算：编码次数 = 时长(秒) × 抽帧率】。GPU 单价与吞吐按你所选编码器实测，不要沿用别人的 QPS【经验】。
- **原件存储**：大文件外置到对象存储后，存量体积 ≈ Σ(原件码率 × 时长)，且只增不减（§4.4 要求原件不可删）。它比向量库本身贵得多，向量库只是它的索引【经验：原件体积通常是向量体积的数十倍以上，随模态与压缩率而变】。
- **生成（多模态 LLM）**：按「送进去的页面数 × 提问数」计费，只对 Top-K 调用；它是预算控制项而不是模型选型项（成本结构见 [§ 3.2.5](01-multimodal-db-section-3-sec3.md)）。

人力的大头在 §4.1 Step 2 的 OCR / ASR 人工复核——它是持续开销而非一次性投入。单位成本口径、FinOps 归因这类通用账法见 [Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节只标这个主题把成本放在哪一格。

### 4.7 容灾与故障演练

多模态这里的第一性问题不是「向量库能不能切到另一个可用区」——向量库自身可多副本，那是通用题（[Ch12 §07](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)）。本主题独有的失效形态是**「服务还在，向量却重算不出来」**：

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 索引损坏 / 需重建 | 全库检索不可用 | 读旧索引、降级到元数据精确检索 | 隔离环境用**原件 + 编码器登记表**重建一个小样本集合，验证能否还原 | RTO【经验：小时级至天级，随数据量级与重建并行度而变】 |
| 编码器权重不可得（内部服务停服 / 模型下线） | 该模态向量**不可重建** | 只能继续用旧向量服务 | 把每个在册编码器的权重 / 镜像与版本固定，定期做一次「离线可加载」验证 | 退化为不可重建，须已被 §4.4 挂账登记覆盖 |
| 原件被生命周期规则归档 / 删除 | 检索能命中、取件失败 | 触发回源取件 | 对「命中但取件失败」单设一条巡检 | RPO【经验：配合每日巡检，天级】 |

跨模态另有一条隐匿失效：**坐标系漂移**（某团队换了编码器版本却未更新登记表），症状是排序看似合理但隔日不可复现（判据见 §4.2「跨模态检索」）。它不适合用多云切换演练，只能用「固定查询集 + 逐条重算」暴露。演练的判据与 §4.9 第 2 条同一件事：**抽 3 条向量，用登记的编码器能不能重算出同一个向量**。

### 4.8 演进路线：0 → 1 → 100

这个主题的每一级坎都踩在同一个资源上——**重建能力**，只是每级变现的方式不同：

- **0 → 1（最小可用）**：现有关系库上加一张表，同表承载元数据 + 向量 + 文件路径，只写新增（§4.4 ①）。**便宜在**敢用一个现成编码器、不动存量；**先坏的是检索质量没有基线**——它不报错，只是几个月后业务说「搜不准」，而监控全绿。
- **1 → 100（规模化）**：向量库独立出来，原件外置对象存储，编码器登记表与按模态召回基线补齐。**变贵的是运维形态**——多一套备份 / 监控 / 权限与一条必须同步的写入链路，孤儿记录成了要长期盯的数（§4.4 ③）；**先坏的是换编码器那一天的窗口**：全库重算从「一个作业」变成「一次停工协商」。
- **100 →（下一道坎）**：跨编码器版本共存、视频 / 3D 的时序与分片、多模态原生库的整合。**变贵的是重建能力**——原件、编码器权重、维度登记三者只要有一处不一致，重建就从「重跑」变成「不可完成」，这也是 §4.6 那笔账里唯一无法用钱补回来的一项。

压测与容量规划、灰度回滚这类通用动作见 [Ch12 §04](../../12-architecture/04-capacity-planning/04-capacity-planning.md) 与 [Ch12 §09](../../12-architecture/09-gray-and-rollback/09-gray-and-rollback.md)，本节只说这个主题最早的坎落在哪一步。

### 4.9 自检清单

设计期的判定（维度与坐标系是否显式规定、结构化条件在检索前还是检索后、库里有没有存原始大文件、时序规格）以 [§ 3.7](01-multimodal-db-section-3-sec3.md) 的自检清单为准，本节不重复。下面 12 条只查另一件事：**上线之后，你手上有没有能证明它在运转的记录**——答不出记录的，一律按「不知道」处理。

1. 资产清单里占比最大的那一类模态，是否写清了预处理方式与原件去向？这份清单最近一次更新时间是什么时候？
2. 随机抽 3 条向量，能否从库内信息取回原件、并用记录的编码器重算出一致的向量？抽出的这 3 条里，跨模态两侧的维度与坐标系是否与检索层约定一致？两个问题有一个答不上，后面的问题都不用问了。
3. OCR / ASR 最近一次抽检是多少份原件、结果如何？关键字段的人工复核退回率有没有按月留下记录？
4. 条件选择性很强的查询（某品牌 + 某时间窗）返回的 Top-K 是否为空？把同一条查询去掉过滤条件再跑一遍，两次的召回与 P99 差多少？
5. 当前孤儿记录（有向量无元数据 / 有元数据无向量）有多少条？这个数是否有人定期看、有没有告警阈值？
6. 「检索能命中、但原件已删或已归档」的条目有多少？这个数能不能每天跑一次？
7. 视频 / 点云类结果的返回里带的是真实时间戳还是帧序号？抽 5 条结果回溯一次：这个时间戳是从抽帧元数据读出来的，还是用帧号推算的？
8. 多模态问答的答案是否带可回链的原件引用？抽 10 条能回链几条，回不了链的那几条属于哪一类问题？
9. 是否存在「用多模态 LLM 直接读全量页面」的查询路径？有，则列出并给出成本上限，并说明这套上限最近一个月有没有真的触发过——没触发过，它多半只是文档，不是闸门。
10. 存量挂账条目（原件已丢、不可重建）有没有写复审日期？翻一遍挂账清单，有没有已经超过复审日期还没处理的？
11. 双轨期结束了吗？孤儿记录连续归零、新路径召回基线不劣于旧路径、旧索引读取量为零，这三条各是什么时候达成的？只满足前两条的，写清退出还差什么、谁在盯。
12. 索引的类型、维度、距离度量与当前数据量级是否匹配？最近一次重调并留召回率记录是什么时候？分级存储与归档策略是否实际触发过（有可查的归档记录）——只写在文档里的策略不算生效。

### 4.10 小结

> 本节小结：整个落地过程中**唯一那个决定成败的环节，是 Step 1 与 Step 4 里那句「原件必须保留、关联键必须唯一」的判断**。它不用写代码、也不出现在任何性能指标上，但它决定了后面所有变更的成本形态：原件在、关联键唯一，则换编码器、换索引、换存储都是增量作业，最坏是从头重算一遍；原件丢了或关联键不唯一，则同一个动作变成不可完成——向量不可重建、跨系统条目对不上。其余每一步做错了都还能改，只有这一条错了没有第二次机会，所以它比选哪个向量库、用哪个多模态 LLM 都更值得先花时间。
>
> 💡 **思考锚点**：按 §4.9 第 2 条，从你库里随机抽 3 条向量，试着用当初记下的编码器把它重算回来——重算得到同一个向量吗？如果重算不回来，说明 §4.10 那两格「原件保留」与「关联键唯一」里有一格是空的；那等你哪天要换编码器，占比最大的那一类模态，能按增量重跑，还是只能整块作废？
