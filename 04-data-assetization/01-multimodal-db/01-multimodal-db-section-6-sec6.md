## 6. 落地实践

### 6.1 某 SaaS 创业"**用 PG + pgvector 把 5 套存储收成 1 套 4+ 年**"（2020-2024）

**背景（Why）**

该 SaaS 创业 2020 年面临**"每种模态各选一个库"带来的组合爆炸**：
- **文本走搜索引擎、图片走对象存储、向量走专用向量库、元数据走关系库**——**一次跨模态查询要在 4~5 个系统之间拼装**
- **跨模态筛选代价高**——**"找出品牌为 Nike 的商品图，按语义相似度排序"要先在关系库筛 ID、再去向量库检索、再回对象存储取文件**
- **数据一致性难保证**——**同一个条目的元数据与向量分属两库，写入失败会出现"有向量没元数据"的孤儿记录**
- **小团队运维不起**——**5 套存储意味着 5 套备份、监控、升级**

**触发点（What）**

2020 年该 SaaS 决定**用 PG + pgvector 把多模态收进一个库**（[案例 2020-2024]），目标：
- **一套存储承载元数据 + 向量 + 文件引用**——跨模态查询一条 SQL 完成
- **复用 PG 生态**——备份、事务、权限、驱动全部现成
- **小团队可运维**

**详细做法（How）**

该 SaaS 多模态架构的**5 大核心组件**：

1. **"元数据 + 向量 + 文件路径"同表（核心创新）**
   - 关键设计：**结构化属性（JSONB）、向量列、指向对象存储的文件路径放在同一张表**；大文件本身仍放对象存储，库里只存路径
   - 关键能力：**向量与结构化条件在同一条 SQL 里参与同一执行计划**，天然可 JOIN，免去跨系统拼装
   - 关键数字：**系统数 5 → 1、跨模态召回 80%+**
   - 关键示意：
     ```sql
     -- 一张表统一三种模态：元数据 + 向量 + 文件路径
     CREATE TABLE item (
       id        bigserial primary key,
       modality  text,            -- text / image / video
       meta      jsonb,           -- 结构化属性（可直接用于 WHERE / JOIN）
       file_path text,            -- 指向对象存储的大文件
       embedding vector(1024)     -- CLIP / BGE 统一向量空间
     );
     CREATE INDEX ON item USING hnsw (embedding vector_cosine_ops);

     -- 一条 SQL 同时约束模态、结构化条件与语义相似度
     SELECT id, file_path
     FROM   item
     WHERE  modality = 'image'
       AND  meta->>'brand' = 'Nike'
     ORDER BY embedding <=> :qvec
     LIMIT 10;
     -- 关键：向量索引与 JSONB 条件由同一个优化器安排执行顺序，
     --       既能用索引缩小范围，又能在缩小子集上做近邻检索
     ```

2. **大文件外置：库里只放路径（核心）**
   - 关键设计：**原始文件存对象存储，数据库只保留路径与元数据**
   - 关键能力：**避免把大对象塞进关系库导致的性能与备份灾难**——这是"用 PG 做多模态"能不能长期跑下去的关键取舍
   - 关键性质：**大文件不入库、备份体积可控**

3. **统一向量空间：让跨模态检索成立（核心）**
   - 关键设计：**文本与图片用同一套编码器映射到同一向量空间**（如 CLIP 风格的双塔），检索时不区分模态
   - 关键能力：**"用文字搜图"与"用图搜图"共用同一条检索链路**
   - 关键数字：**跨模态召回 80%+**

4. **向量索引参数按数据量调整（核心）**
   - 关键设计：**初期用较小的索引参数快速跑起来；数据量增长后再调整索引类型与参数，并在真实数据集上做召回率基准测试**
   - 关键能力：**索引参数与业务规模匹配**，避免"默认参数在小数据上够用、在百万级就崩"
   - 关键性质：**召回率可基准测试、参数可演进**

5. **复用 PG 生态降低运维负担（核心创新）**
   - 关键设计：**事务、备份、权限、连接池、驱动全部沿用 PG**，不引入新的运维对象
   - 关键能力：**小团队能用得起**——这是创业公司选型最关键的一条：不是"最先进"，而是"运维得动"
   - 关键数字：**运维系统数 1 套**

**该 SaaS 多模态关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **存储系统数** | 5 套（搜索 / 对象 / 向量 / 关系 …） | 1 套（PG + 对象存储） | **-80%** |
| **跨模态查询** | 4~5 个系统间拼装 | 一条 SQL | **-80% 复杂度** |
| **跨模态召回** | 无法做 | 80%+ | **∞** |
| **元数据与向量一致性** | 分属两库易产生孤儿记录 | 同表同事务 | **一致** |
| **大文件处理** | 曾尝试入库 | 对象存储 + 路径 | **备份体积可控** |
| **运维对象** | 5 套备份 / 监控 / 升级 | 1 套 PG | **-80%** |
| **业务自助率** | 依赖工程取数 | SQL 直查 | **80%+** |
| **团队规模** | — | 5-10 人即可支撑 | **小团队可行** |

**具体数字（How much）**

- 团队规模：该 SaaS 数据 / 后端团队 5-10 人
- 关键数字：**系统数 5 → 1**；**跨模态召回 80%+**；**一条 SQL 完成跨模态查询**；**运维 1 套**
- 业务影响：支撑该 SaaS 的多模态搜索、推荐与内容检索场景

**失败教训**

- 早期「**每种模态各选一个库**」——跨模态查询要在 5 个系统间拼装且数据一致性难保，倒逼**「元数据 + 向量 + 路径同表，跨模态一条 SQL」**
- 「**把原始大文件也存进数据库**」——库体积与备份时间迅速失控，倒逼**「大文件外置对象存储，库内只存路径」**
- 「**各模态用各自的编码器**」——不同向量空间无法比较，跨模态检索做不了，倒逼**「统一编码到同一向量空间」**
- 「**向量索引用默认参数**」——数据量涨到百万级后召回率明显下降却无人察觉，倒逼**「在真实数据集上做召回率基准测试并随规模调参」**

### 6.2 某车企"**多模态诊断库：把图片 / 雷达 / 日志 / 故障码收进一套可 JOIN 的存储 4+ 年**"（2020-2024）

**背景（Why）**

该车企 2020 年面临**"诊断一次故障要看五类数据"的现实**：
- **车辆数据天然多模态**——**摄像头图像、雷达点云、GPS 轨迹、控制器日志、故障码**
- **数据分散在 5 套系统**——**排查一个故障要人工在多个平台之间对齐时间戳与车辆标识**
- **故障诊断依赖跨模态关联**——**"这个故障码出现时，雷达在什么状态下、摄像头拍到了什么"——这类问题跨系统几乎答不出来**
- **相似故障难以检索**——**历史故障记录是文本，没有语义检索能力，"找相似的故障案例"只能靠关键词**

**触发点（What）**

2020 年该车企推进**多模态诊断库**（[案例 2020-2024]），目标：
- **多模态统一入库**——五类数据一套存储、可 JOIN
- **故障诊断跨模态**——按车辆 + 时间段关联全部模态
- **相似案例语义检索**——故障描述向量化后可检索

**详细做法（How）**

该车企多模态诊断库的**5 大核心组件**：

1. **以"车辆 + 时间窗"为主键关联所有模态（核心创新）**
   - 关键设计：**所有模态的数据都带统一的车辆标识与时间戳**，查询以"车辆 + 时间窗"为入口把相关模态一次取齐；结构化列与向量列放同一存储以便混合筛选
   - 关键能力：**"某车在某个时间窗内发生了什么"成为一条可执行的查询**，而不是跨五个平台人工对齐
   - 关键性质：**跨模态关联从人工对齐变为一次查询**
   - 关键示意：
     ```text
     诊断一次故障，五类模态按「车辆 + 时间窗」对齐
                        ┌─ 摄像头图像（关键帧 + 向量）
                        ├─ 雷达点云（摘要 + 向量）
       车辆 VIN + 时间窗 ─┼─ GPS 轨迹（结构化序列）
                        ├─ 控制器日志（结构化 + 文本）
                        └─ 故障码（结构化 + 描述向量）
     ────────────────────────────────────────────────
     一次诊断查询由三部分组成
       ① 精确筛选：WHERE vin = ? AND ts BETWEEN ? AND ? AND dtc = ?
       ② 语义检索：ORDER BY embedding <=> :相似故障描述向量
       ③ 关联取数：把命中的模态文件路径一并返回，供工程师查看
     -- 关键：多模态的价值不在"存得下"，而在"能按同一个键对齐"
     --       没有统一的车辆 + 时间维度，多模态就只是五堆数据
     ```

2. **大文件外置 + 摘要入库（核心）**
   - 关键设计：**原始点云与视频存对象存储；库内保存"可检索的摘要"**（关键帧向量、统计特征、文本描述）
   - 关键能力：**在库内做检索、到对象存储取原件**——检索性能与存储成本同时可控
   - 关键性质：**库内保留可检索摘要、原件外置**

3. **故障描述向量化与相似案例检索（核心）**
   - 关键设计：**历史故障的描述文本向量化**，新故障可按语义找相似历史案例
   - 关键能力：**"找类似故障"从关键词匹配升级为语义匹配**——工程师不必猜前人用了什么词描述
   - 关键性质：**相似案例可语义检索**

4. **时间序列与向量的混合查询（核心）**
   - 关键设计：**GPS 轨迹、日志这类时间序列以结构化方式存储**，与向量检索在同一查询中组合
   - 关键能力：**"在满足时间与状态条件的数据里找语义相似"**这一混合模式可执行
   - 关键性质：**混合查询可用**

5. **检索结果的工程化呈现（核心创新）**
   - 关键设计：**查询结果按模态分组返回，附带原件路径与可信度**，便于工程师按需查看
   - 关键能力：**工程可用性**——诊断场景下工程师最终要看的是原始图片与日志，而不是向量分数
   - 关键性质：**结果按模态组织、可直达原件**

**该车企多模态诊断库关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **模态数据位置** | 分散在 5 套系统 | 一套存储，可按车辆 + 时间窗关联 | **-80%** |
| **诊断数据对齐** | 人工跨平台对齐时间戳 | 一次查询取齐 | **∞** |
| **相似故障检索** | 关键词匹配 | 语义检索 | **显著提升** |
| **原始大文件** | 分散存储 | 对象存储 + 库内摘要 | **检索与成本兼顾** |
| **混合查询（条件 + 语义）** | 不支持 | 结构化条件与向量组合 | **∞** |
| **结果呈现** | 多平台分别查看 | 按模态分组 + 直达原件 | **可用性提升** |
| **故障排查人力** | 多人多平台协作 | 单人单查询起步 | **人力下降** |
| **数据规模** | PB 级分散 | PB 级统一 | **可管理** |

**具体数字（How much）**

- 团队规模：该车企数据平台 / 诊断团队 50+ 人
- 关键数字：**模态数据位置 5 套 → 1 套**；**车辆 + 时间窗一次取齐**；**相似故障语义检索**；**原件外置**
- 业务影响：支撑车辆故障诊断、质量分析与远程诊断，把跨平台人工对齐变成一次查询

**失败教训**

- 早期「**各模态各存一套系统**」——诊断时人工跨平台对齐时间戳，效率极低，倒逼**「统一车辆标识与时间戳，按车辆 + 时间窗关联」**
- 「**把点云等原始大文件入库**」——存储与检索性能双双恶化，倒逼**「原件外置 + 库内保留可检索摘要」**
- 「**相似故障靠关键词匹配**」——换个说法就搜不到，倒逼**「故障描述向量化 + 语义检索」**
- 「**只返回向量分数不返回原件**」——工程师仍要再去别处找图，倒逼**「结果按模态分组并附原件路径」**

### 6.3 Pinecone"**托管向量数据库：把分片、扩缩与召回率做成服务 4+ 年**"（2020-2024）

**背景（Why）**

Pinecone 2020 年面临**"自建向量检索的运维代价被严重低估"**：
- **向量规模增长快**——**从百万到十亿级，自建方案要重做索引、重分片、停机重建**
- **召回率需要持续调参**——**索引参数与数据分布强相关，业务方很难判断"当前召回率是多少"**
- **多租户与隔离**——**SaaS 场景下要给每个客户独立命名空间与配额**
- **混合筛选需求普遍**——**真实查询几乎都带结构化条件，"纯向量检索"很少见**

**触发点（What）**

2020 年起 Pinecone 推出**托管向量数据库**（[Pinecone 公开材料 2020-2024]），目标：
- **免运维扩缩**——分片与重建由平台负责
- **可观测的召回指标**——业务方能知道检索质量
- **多租户隔离**——SaaS 场景开箱可用

**详细做法（How）**

Pinecone 托管向量库的**5 大核心组件**：

1. **托管分片与在线扩缩（核心创新）**
   - 关键设计：**平台负责分片、副本与扩容**，业务侧只声明索引规格与容量预期；扩缩对读写无停机
   - 关键能力：**把"向量库扩容"从一次工程项目变成一次配置调整**——这是托管相对自建最核心的价值
   - 关键性质：**扩缩免停机、免人工分片**
   - 关键示意：
     ```text
     自建 vs 托管：扩容路径的差别
       ✗ 自建
         数据涨到 N 亿 → 需要增加分片 → 重新索引（耗时数小时~天）
                        → 期间写入受限或需要双写与新老切换
                        → 每次扩容都是一次高风险变更
       ✓ 托管
         声明索引规格与容量预期 → 平台在后台完成分片与副本调整
                                → 读写路径不变，业务无感
     ────────────────────────────────────────────────
     托管真正卖的不是"能存向量"，而是"不用自己处理下列问题"：
       · 分片与再平衡        · 索引参数随规模调整
       · 副本与可用性        · 多租户命名空间与配额
       · 备份与恢复          · 召回质量的观测口径
     -- 关键：向量检索的运维难度随规模非线性上升，
     --       这是"自建看起来可行、跑起来吃力"的常见原因
     ```

2. **结构化元数据过滤与命名空间隔离（核心）**
   - 关键设计：**向量附带元数据，检索时可同时对元数据做过滤**；**命名空间**用于把不同租户或业务的数据隔离开
   - 关键能力：**"带条件的向量检索"与"多租户隔离"成为平台内置能力**，而不是每个使用方各写一遍
   - 关键性质：**元数据过滤内置、租户命名空间隔离**

3. **召回质量可观测与调参建议（核心）**
   - 关键设计：**索引质量指标可查询**（如召回率近似值、索引统计），并给出参数建议
   - 关键能力：**"我们的检索质量到底如何"从无从得知变成可度量**——这是很多团队真正缺的东西
   - 关键性质：**索引质量可观测、参数有据可调**

4. **混合检索：稀疏与稠密并用（核心）**
   - 关键设计：**支持稀疏向量（关键词权重）与稠密向量（语义）并存储与检索**，用融合策略结合两者
   - 关键能力：**专有名词、型号、编号类查询靠稀疏命中，语义泛化靠稠密**——覆盖纯稠密检索的盲区
   - 关键性质：**稀疏 + 稠密可并存**

5. **多租户配额与计量（核心创新）**
   - 关键设计：**按租户 / 命名空间统计存储与查询量**，配额与计费挂钩
   - 关键能力：**SaaS 场景下的成本归因天然成立**，不必额外搭一套计量
   - 关键性质：**配额与计量内置**

**Pinecone 托管向量库关键数字**（[Pinecone 公开材料 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **扩缩方式** | 自建：重新索引，停机数小时~天 | 托管：后台完成，读写不停 | **免人工分片** |
| **运维负担** | 分片 / 副本 / 备份 / 修复自建 | 平台承担 | **-80%+** |
| **元数据过滤** | 自行实现（常退化为先检索后过滤） | 平台内置 | **∞** |
| **多租户隔离** | 自行实现命名空间 | 平台内置命名空间与配额 | **∞** |
| **召回质量** | 无从得知 | 索引质量可观测 | **可度量** |
| **检索类型** | 仅稠密向量 | 稀疏 + 稠密可并用 | **覆盖专有名词查询** |
| **容量规划** | 按经验预估 | 按声明规格扩缩 | **更可预期** |
| **计量计费** | 自行搭建 | 内置按租户计量 | **∞** |

**具体数字（How much）**

- 团队规模：Pinecone 工程团队数百人，服务大量企业客户
- 关键数字：**运维负担 -80%+**；**免停机扩缩**；**元数据过滤与命名空间内置**；**稀疏 + 稠密并用**；**召回质量可观测**
- 业务影响：让不具备向量检索运维能力的团队也能把语义检索用起来，并服务多租户 SaaS 场景

**失败教训**

- 早期「**让客户自建与运维**」——扩缩需重新索引并伴随风险窗口，客户运维吃力，倒逼**「托管分片与在线扩缩」**
- 「**只做纯向量检索**」——真实查询几乎都带结构化条件，倒逼**「元数据过滤内置，且参与检索而非事后裁剪」**
- 「**只支持稠密向量**」——型号、编号类专业词检索效果差，倒逼**「稀疏 + 稠密并用 + 融合策略」**
- 「**不提供检索质量指标**」——客户不知道召回率如何、该不该调参，倒逼**「索引质量可观测 + 参数建议」**

### 6.4 阿里"**PAI 多模态链路：把对象存储、数据仓库与多模态模型接成一条流水线 5+ 年**"（2019-2024）

**背景（Why）**

阿里 2019 年面临**多模态数据"存得住但用不起来"**：
- **图片 / 视频体量最大**——**天然适合对象存储，但对象存储没有"查"的能力**
- **多模态模型在算力平台上**——**模型能产出向量，但向量要有地方存与检索**
- **数据与算力割裂**——**训练时要先把 EB 级多模态数据导出到算力侧，网络成本与合规风险双高**
- **业务要的是结果**——**业务方要的是"能按语义检索到商品图"，而不是一堆中间产物**

**触发点（What）**

2019 年阿里推进**PAI 多模态链路（对象存储 + 数据仓库 + 多模态模型 + 检索）**（[阿里 PAI 公开材料 2019-2024]），目标：
- **数据不出仓**——多模态数据在仓库侧完成加工与向量化
- **一条流水线**——从原件到可检索向量无需人工搬运
- **上线到业务**——检索能力直接作为服务提供

**详细做法（How）**

阿里 PAI 多模态链路的**5 大核心组件**：

1. **"对象存储存原件 + 仓内加工与向量化"的分工（核心创新）**
   - 关键设计：**原始多模态文件放对象存储；元数据、摘要与向量进数据仓库**；向量化在仓库内由多模态模型函数直接完成（AI Function 形式）
   - 关键能力：**EB 级多模态数据不必导出到算力侧再导入回来**——省掉一轮搬运，也消除了数据出仓的合规风险
   - 关键性质：**数据不出仓、导出流量大幅下降**
   - 关键示意：
     ```text
     多模态流水线（原件在对象存储、可检索部分在仓库、加工在仓内）
       对象存储（图片 / 视频 / 音频原件，EB 级）
            │  ① 登记：路径 + 元数据 + 校验和
            ▼
       数据仓库（表：path / meta / 摘要 / 向量）
            │  ② 仓内向量化：AI Function 直接对图片/文本产出向量
            │     → 无需把原件导出到算力侧再导回
            ▼
       检索服务（向量 + 结构化条件同一执行计划）
            │  ③ 对外提供语义检索 API
            ▼
       业务应用（搜索 / 导购 / 审核）
     ────────────────────────────────────────────────
     关键：把"多模态模型"作为仓库内的一个函数能力，
           而不是一个需要搬运数据才能调用的外部服务
     -- 这一步决定了多模态链路的成本结构与合规可行性
     ```

2. **仓库内向量化（AI Function）（核心）**
   - 关键设计：**多模态模型以函数形式在仓库内可用**，一条 SQL 即可对整列图片 / 文本产出向量
   - 关键能力：**向量化从"离线批量作业"变成"SQL 的一部分"**，新数据入库即可向量化
   - 关键性质：**SQL 内完成向量化**

3. **向量与结构化元数据同表检索（核心）**
   - 关键设计：**向量列与元数据列同表**，检索时结构化条件与语义相似度在同一执行计划内组合
   - 关键能力：**"符合业务条件的多模态数据里找语义相近的"可一条查询完成**
   - 关键性质：**混合查询可用**

4. **权限与合规随链路一体（核心）**
   - 关键设计：**多模态原件与向量的访问都走仓库权限体系**，可审计、可追溯
   - 关键能力：**多模态数据不因"体量大、链路长"而脱离治理**——这是企业级多模态能上线的前提
   - 关键数字：**访问审计 100%**

5. **对外提供检索服务（核心创新）**
   - 关键设计：**检索能力封装为服务 API 对外提供**，业务方接入即用
   - 关键能力：**业务方不必理解向量与索引**，只关心"能不能搜到"
   - 关键性质：**服务化接入、多业务复用**

**阿里 PAI 多模态链路关键数字**（[阿里 PAI 公开材料 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **多模态数据流转** | 导出到算力侧再导回 | 仓内加工与向量化 | **导出流量大幅下降** |
| **向量化方式** | 离线批量作业 | SQL 内 AI Function | **新数据即时向量化** |
| **原件存储** | 分散 | 对象存储统一 + 仓内登记 | **统一管理** |
| **混合查询（条件 + 语义）** | 跨系统拼装 | 同一执行计划 | **∞** |
| **访问治理** | 链路长、易漏 | 全链路走仓库权限 | **审计 100%** |
| **业务接入** | 各自搭检索 | 检索服务化 | **多业务复用** |
| **数据规模** | PB | EB | **1000x** |
| **多模态类型** | 文本为主 | 文本 / 图片 / 视频 / 音频 | **多模态** |

**具体数字（How much）**

- 团队规模：阿里 PAI + MaxCompute 团队 500+ 人
- 关键数字：**EB 级多模态（数据规模 PB → EB，1000x）**；**数据不出仓**；**SQL 内向量化**；**混合查询**
- 业务影响：支撑阿里集团内商品图检索、内容审核、导购等多模态场景，并向云上客户输出

**失败教训**

- 早期「**把多模态原件导出到算力侧做向量化再导回**」——EB 级数据搬运成本极高且带来合规风险，倒逼**「仓内向量化（AI Function），数据不出仓」**
- 「**原件与向量分处两套系统**」——检索到向量后还要另去取原件，且权限不一致，倒逼**「对象存储存原件 + 仓库登记路径与向量，权限统一」**
- 「**只做纯向量检索**」——业务条件无法参与，倒逼**「向量与元数据同表，混合查询同一执行计划」**
- 「**检索能力只服务单个业务**」——重复建设，倒逼**「检索服务化，业务接入复用」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**关系库 + 向量扩展（同表）+ 对象存储存原件**」（**最简单**）——**百万级向量、1 个场景**

- 引入「**托管或平台化的分片与在线扩缩**」——扩容不再是高风险变更
- 引入「**命名空间 / 租户隔离 + 配额与计量**」
- 团队：10-30 人
- 验证标准：**扩容免停机**、**租户间零越界**、**专有名词查询靠稀疏命中**、**成本可按租户归因**

**100 → 1000 阶段：12-24 个月**

### 6.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**存储 / 检索系统数**」 | 5 套 | 1~2 套（库与对象存储合并计 1、拆开计 2，故为区间） | **-60~80%** |
| 「**跨模态查询复杂度**」 | 4~5 系统间拼装 | 一条 SQL / 一次查询 | **-80%** |
| 「**跨模态召回**」 | 无法做 | 80%+ | **∞** |
| 「**元数据与向量一致性**」 | 分库易产生孤儿记录 | 同表同事务 | **一致** |
| 「**扩容方式与风险**」 | 重新索引 + 停机窗口 | 在线扩缩 | **免停机** |
| 「**运维对象**」 | 备份 / 监控 / 升级各 5 套 | 1 套（或托管） | **-80%** |
| 「**大文件成本**」 | 曾尝试入库 | 对象存储 + 路径 | **备份体积可控** |
| 「**检索质量可观测性**」 | 无从得知 | 召回 / 索引指标可查 | **可度量** |
| 「**多模态数据导出流量**」 | 导出算力侧再导回 | 原侧加工 | **-90% 量级** |
| 「**检索能力复用**」 | 各业务自建 | 服务化复用 | **∞** |

**关键投资回报**：
- **直接节省**：「**系统数 -60~80% + 运维 -80% + 导出流量 -90%**」——**多模态架构最大的成本不在存储本身，而在"同一份数据在多套系统之间反复搬运与重复治理"**；把元数据、向量与文件路径收进一套可 JOIN 的存储，省下的是运维与工程人力
- **业务价值**：「**跨模态混合查询 + 相似案例语义检索**」——**多模态数据的价值不在"存了多少"，而在"能不能按同一个键把它对齐起来看"**：以车辆 + 时间窗或商品 + 条件为入口一次取齐多模态，才让"跨模态分析"从人工拼装变成可执行的查询
- **AI 时代关键**：「**统一向量空间 + 原侧加工（数据不出侧）+ 召回质量可观测**」——**这是多模态 AI 的三块地基**：统一向量空间让跨模态检索成立；原侧加工决定了 EB 级多模态数据能否在成本与合规约束下被用起来；可观测的召回质量则决定"检索效果退化"能不能被及时发现——否则 RAG 与多模态 Agent 的失效会是静默的

---

> **本节小结**：
> - 4 个真实案例（某 SaaS / 某车企 / Pinecone / 阿里）印证：**多模态数据库不是「再买一个向量库」，是「同表承载元数据与向量 + 大文件外置 + 统一向量空间 + 混合查询 + 在线扩缩与可观测召回」5 件套**。
> - 关键时间线：某 SaaS 4+ 年 / 某车企 4+ 年 / Pinecone 4+ 年 / 阿里 5+ 年 —— **多模态存储是 4+ 年长期工程**，且**成败取决于"能否在同一执行计划里同时满足结构化条件与语义相似"，而不是向量库本身的性能**。
> - 选型第一原则：「**关系库 + 向量扩展 + 对象存储**」（**最简单**）——**百万级、1 个场景** → 「**统一向量空间 + 召回基准测试**」（**必须**）→ 「**在线扩缩 + 多租户隔离 + 稀疏稠密并用**」（**生产**）→ 「**原侧加工 + 权限统一 + 检索服务化**」（**AI 时代**）。
> - 99% 的失败来自「**每模态各选一个库 + 大文件入库 + 向量空间不统一 + 只做纯稠密检索**」——必须有 **同表混合查询 + 大文件外置 + 统一编码 + 稀疏稠密并用**。
> - 真正的 ROI 来自「**系统数 -80% + 跨模态召回 80%+ + 扩容免停机 + 导出 -90%**」——是**多模态数据能否从"存得下"走到"查得动"的分水岭**。

> 💡 **思考锚点**：点一遍你现在为多模态数据养了几套存储 / 检索系统——若像本节案例那样是 5 套，收进 1~2 套能省哪几项运维？再挑一个你真实的分析入口（如「商品 + 某条件」），问它今天能不能用一条查询一次取齐元数据与向量、且不带出孤儿记录；做不到，你缺的是同表承载还是统一向量空间？
