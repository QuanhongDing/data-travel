## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单在这门主题上的问题比别的章节更严重，因为**这一节的关键词全是"支持"**：数据库"支持多模态"、向量库"支持 ColPali"、模型"支持六模态"——而"支持"在两个产品页里可能指完全不同的东西（能存、能算、能检索、能跨模态检索、能生成）。原文件把「ColPali（2024）—— 多模态文档检索，无需 OCR」「SurrealDB 2.x（2024）—— 多模态原生数据库」「ImageBind（Meta）开创六模态对齐」（均为原文件 §5.1 / §5.3 的原句）并列成同一种句式，读者据此排路线图时无法判断哪一条今天能上生产。本节对每个方向都要求：**判据必须是可核验的动作**（去哪一份 release note / 哪一篇论文里核什么），而不是"它支持"。

第二个坑是**把模型能力与存储能力混为一谈**。主文件 §2.4 已经区分过「多模态 Embedding vs 多模态 LLM」：Embedding 服务于"从大规模语料里找"，LLM 服务于"理解了再说"。这两件事的成本函数形状相反——索引的边际成本随查询次数被摊薄，直读的边际成本随每次调用线性增长。**2024 年之后的真实变化发生在"直读"这一侧（模型能直接吃图像/音频），而不是"索引"这一侧**；把两者混成一句"AI 让多模态数据库更重要了"，就会同时高估存储层的变化、低估接口层的变化。

第三个坑是**命名**。本主题的型号名混淆风险是全书最高的：`CLIP` 是模型族名而不是某个具体规格，各家视觉塔的规格命名（`ViT-L/14` 一类）以官方仓库为准；"CLIP-ViT-LG"这种写法在原文件的 §5.3 里出现过，本节保留该条目但**不把它当作可引用的型号名**——判定方法是去官方模型仓库看有没有这个标识，没有就按"CLIP 系列的某个较大规格"理解。同理，"支持多模态 + 向量 + 图"是一句产品定位描述，不是一条可核验的技术事实。

按这套判据，本主题下的方向分成三级：

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 多模态模型直接消费原始模态（Agent 多模态能力） | **L1** | 主流模型 API 的图像 / 音频输入是正式文档条目而非预览项；第三方在生产中使用；接口稳定 | 排进路线图：把"预处理"从必经环节降为可选优化 |
| 多模态 RAG 工业化 | **L2** | 各组件（检索、生成）都已可用，但"工业化"所需的部分——评测集与指标、索引成本模型——没有公开标准；生产案例以自建为主 | PoC：图文两条链路分开做，先建自建评测集 |
| 多模态文档检索免 OCR（ColPali 类） | **L2** | 论文与开源实现可核验（2024 年起）；但多向量 / late-interaction 索引在各向量库里的支持程度不一，需逐产品核验 | PoC：小规模先量"索引膨胀倍数"再决定上不上量 |
| 原生多模态数据库（向量 + 文档 + 图同一引擎） | **L2** | 产品存在且有正式版本发布；但"一个引擎同时管多模型"的规模边界需逐产品核验——判定方法是看索引组件能否独立扩缩 | 中小规模可试点；上亿级向量【经验：主流向量库公开文档给出的集群规模量级】仍按专用引擎设计 |
| 多模态 Embedding 标准化 / 跨模态统一向量空间 | **L3** | 六模态对齐的代表工作是 2023 年的研究原型；产品里真正生产的仍是"图文对齐 + 各模态各自编码 + 元数据关联" | 记录，不要在 schema 里预留"任意模态互搜" |
| 3D / 点云 / IMU / 传感器数据支持 | **L3** | 通用数据库里没有一等公民式的点云类型与索引；公开材料多为数据集与专用栈 | 用专用存储承载 + 用元数据挂钩，不在通用库里预留 |
| 行业多模态标准化（医疗 / 零售 / 安防） | **L3** | 无公开可核验的标准草案或第三方评测协议 | 不要预留，按自己的业务口径定义 |

> 本主题下唯一处在 L1 的方向是**第一行：多模态模型直接消费原始模态**——它改变的是接口边界（模型 API 直接接受图像 / 音频 / 视频），因此"能不能用"不构成问题。要注意的是，排在这一行的是**接口能力**，不是"统一向量空间"或"原生多模态数据库"：后两者的存储侧变化远小于宣传口径，这是本节与营销材料最大的分歧点。

三级的判据都可以被"一次动作"验证：**L1 的验证动作是"挂上去用一天"，L2 的验证动作是"把那两个数测出来"，L3 的验证动作是"去公开渠道找一份第三方评测或标准草案"**。找不到验证动作的方向，本身就说明它还不到可评估的阶段——这句话对下面每一个 L3 都成立。

**这三级的排法直接决定路线图的顺序**：

- **L1 先做**：把"模型可直读原件"用起来——它不要求改存储，只要求你**别再把原件当可丢弃的中间产物**。
- **L2 只做 PoC，并先把两个数测出来**：索引膨胀倍数（多向量索引 vs 单向量索引的存储比）与单次问答的原件直送成本。这两个数是"要不要上量"的判据。
- **L3 不排进排期**：统一向量空间、任意模态互搜、点云进通用库，都属于"等信号"而不是"抢跑"。

每次版本升级后回填一次级别：某个 L3 方向若出现第三方评测或标准草案就升 L2；某个 L2 方向若一年内仍拿不到实测数字，就降 L3 并停止投入。

本节与主文件 §1.4 的关系：§1.4 沿时间线记录"发生了什么"（CBIR、CLIP、ImageBind、多模态 RAG），本节回答的是"现在能不能用"。同一条时间线在两种写法下结论可能相反——§1.4 把「里程碑」这个标签给了 2021 年的 CLIP（研究意义），而 ImageBind 在 §1.4 只是一条普通时间线条目；本节判的是工程可用性：图文对齐（CLIP 一脉）落在 L1，六模态对齐（ImageBind）落在 L3。**里程碑讲的是研究意义，成熟度讲的是工程可用性**。

核验"支持多模态"这句话时，可用的动作只有三类，建议照做：

- **查 release note**：在对应产品 / 版本的官方发布说明里搜关键词，看条目写的是"实验性 / 预览"还是正式能力。
- **查模型仓库**：型号名（`CLIP` 的视觉塔规格一类）以官方仓库为准，不要在二手材料里认定型号。
- **自己测一次**：索引膨胀倍数、跨模态召回、单次直读成本，这三项自测出来的数比任何产品页可信。

本节不预测"多模态会不会成为默认"——这类判断永远正确，因而没有信息量。本节只回答两件事：**某个具体动作今天能不能做，以及做它要付出什么代价。**

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向在评审时应被直接打回——多模态的每一次能力提升，都对应一项成本结构的变化。

#### 5.2.1 原生多模态数据库：一个引擎管四种数据模型

- **旧做法与它的卡点**：主文件 §1.2 列的第一、三、四号痛点就是这条方向要解的题——文本用 ES、图像用 Milvus、向量单独存，**同一件资产要在三处对齐**（向量、原件、元数据）。成本不在存储费，而在"对齐"：任何一处漂移就产生"能检索到但取不到原件"或"取到的是上一版"。原清单说「SurrealDB、Weaviate 等原生支持多模态 + 向量 + 图的数据库崛起」，要补上的恰恰是"支持"到底指什么。
- **AI 改变了什么机制**：**把"跨系统对齐"换成了"引擎内 JOIN"**。把向量索引、文档/图模型、元数据放进同一个引擎、同一套查询语言、同一份备份单位，机制上改变的不是能力清单，而是**原子性与一致性发生的位置**——从应用层拼装下移到引擎内部。
- **由此得到的**：**因为一致性从"应用层拼装"变成"引擎内完成"，所以"检索到 + 拿到原件 + 权限与元数据过滤"可以在一条查询里成立，代价是引擎在每一个维度上都比专项引擎弱**；反过来说，如果你的场景只需要"向量 + 元数据过滤"（主文件 §2.3 的检索模式 1–5 大多如此），专项向量库加一个对象存储就已经够用，原生多模态带来的收益接近于零。

| 判断项 | 专项组合（向量库 + 对象存储 + 元数据库） | 原生多模态数据库 |
| --- | --- | --- |
| 一致性的位置 | 应用层拼装（要自己保证三处不漂移） | 引擎内（一条查询内完成） |
| 每个维度的能力上限 | 各自做到最好 | 受引擎整体架构约束 |
| 扩缩单位 | 各自独立扩缩 | 取决于索引组件能否独立扩缩（**需逐产品核验**） |
| 退出成本 | 换单个组件即可 | 换引擎等于换查询语言与数据模型 |
| 运维面 | 三套小系统（故障域小，但联调成本高） | 一套大系统（故障爆炸半径变大） |

核验"原生多模态"的四个动作（缺任意一项，就先按普通组合架构设计）：

- 查 release note 里**索引组件是否独立部署**（独立服务 / 独立扩缩配置）。
- 查**备份与恢复是否覆盖索引**：恢复主引擎能不能同时恢复索引。
- 查**多向量检索与元数据过滤能否组合**（页面级检索的实际用法就靠这个）。
- 用你自己的语料跑一次**导入 → 查询 → 变更**闭环，而不是看官方 demo。
- **由此付出的**：**其一，规模上限**——一个引擎同时承载向量索引与文档/图，它能否扛住大规模型向量取决于索引组件是否独立扩缩，多数"原生"产品的索引与主引擎同生共死；**其二，锁定**——把四种模型塞进一个小众查询语言，退出成本高于"换一个向量库"；**其三，故障爆炸半径**——主文件 §1.2 抱怨的是"多套系统难管"，而这里付出的是相反方向的代价：把三套系统合并成一套后，一次引擎故障同时带走检索、元数据与权限判断。
- **证据与来源**：产品存在且有正式版本发布，可自行核验——**判定方法是查对应产品的 release note 里"索引 / 向量"相关条目是否与主引擎解耦**（有独立的索引服务或独立的扩缩配置），而不是看首页写没写 multimodal。**本节不引用任何"支持多少模态 / 多大规模仍毫秒返回"的厂商性能声称**：这类数字普遍缺少条件限定（数据量、维度、召回率目标、硬件）。
- **成熟度**：**L2**。判据：产品已可用但接口与生态未稳（查询语言与数据模型仍在演进），且没有第三方公开的、含规模与指标的对比评测；小规模可用，不要作为核心依赖。

一句话总结这个方向的取舍：**它用"每个维度的能力上限"换"跨系统对齐的成本"**。只有当你的检索确实需要四种模型在同一处联动（向量 + 图 + 文档 + 元数据过滤）时，这笔交换才划算；否则专项组合更便宜，也更容易换掉其中一块。

#### 5.2.2 多模态 RAG 工业化：把"检索用什么模态"与"生成看什么模态"拆开

- **旧做法与它的卡点**：原清单把「GPT-4V + RAG / Claude 3.5 Vision + RAG / Qwen-VL + RAG」并列为一条方向。要补的卡点是主文件 §1.2 的第五号痛点（「LLM 无法直接消费图像 / 视频」）：过去的绕法是在预处理阶段把一切**文本化**（OCR / ASR），而文本化把版面与画面信息丢在链路最上游，**误差不可逆**——OCR 错一个数字，后面检索、生成、引用全都建立在错的文本上。这是"预处理在最上游"的架构决定的，不是模型能力问题。
- **AI 改变了什么机制**：**把一件耦合的事拆成两个独立决定**——「检索用什么模态」（Embedding 侧）与「生成看什么模态」（LLM 侧）。过去两者被"先文本化"绑在一起（文本检索、文本生成）；现在生成侧可以直接接收原件，检索侧可以多模态编码。
- **由此得到的**：**因为生成侧可以直接吃原件，所以"OCR 错了就全错"这个不可逆点被移到了可对照的位置**（原件与 OCR 文本可以同时进入上下文，让模型自查矛盾），并且**原件从"归档物"升级为"可再次消费的资产"**——对数据库层的直接推论是元数据里必须记"这件原件是否被模型消费过、用的哪个模型版本"。

| 对比项 | 文本化链路（OCR → 文本 → 检索 → 文本生成） | 图文链路（多模态检索 + 原件直送生成） |
| --- | --- | --- |
| 误差发生的位置 | 链路最上游，且不可逆 | 生成时可见，可与原件对照 |
| 成本形态 | 每页一次预处理 + 每次查询的检索成本 | 每次查询的检索成本 + 每次问答的原件直送成本 |
| 成本随什么增长 | 文档量（可预算） | 问答次数 × 输入体量（易失控） |
| 版面信息 | 在预处理中丢失 | 保留（检索与生成都以原件为准） |
| 评测方式 | 文本检索指标（Recall@K 一类） | 无公开标准，需自建（含引用正确性） |
| 主要风险 | OCR 错则全错 | 成本与延迟失控 |

- **由此付出的**：**其一，成本函数换了形状**——从"每页一次 OCR 的固定成本"变成"每次问答都送原件的边际成本"，问答次数越多越贵，这与"预处理一次、检索多次"的旧成本直觉相反，上量前必须按 QPS 重算；**其二，评测缺位**——多模态 RAG 的评测集与指标没有公开标准，只能自建（这也是 §5.1 把它判 L2 而不是 L1 的原因）；**其三，延迟**——图像与音频进入上下文会拉长首字延迟，对交互式应用是硬约束，且它不随模型升级自动消失。
- **证据与来源**：公开可核验的是模型能力本身——多模态模型有公开技术报告（例如 Qwen 系列的 VL 版本技术报告，arXiv 2024），可自行核验其输入模态与规格；**"工业化"没有可核验的标准**，第三方生产案例以自建为主，故不判 L1。
- **成熟度**：**L2**。判据：已可用但评测与成本模型未稳；判定方法是**先用自建评测集跑一遍"文本链路 vs 图文链路"的对照**，看原件直送带来的准确率提升是否值回它的成本增量——这个对照做不出来，就说明还不具备上生产的条件。

这条方向最容易被跳过的一步，恰恰是"先建评测集、再改链路"。多模态 RAG 的失败往往不是检索变差了，而是**没有人能说清它比原来好还是差**——旧链路的评测指标（文本 Recall@K 一类）测不了"答案有没有引用对原件"这件事，于是只能靠体感，而体感在跨模态场景里极不可靠。

#### 5.2.3 多模态文档检索免 OCR：用索引膨胀换预处理链路的缩短

- **旧做法与它的卡点**：文档类资产（报表、合同、发票、扫描件）的传统链路是 **OCR → 分块 → 文本 Embedding → 检索**。卡点在"版面"：表格、图表、印章、多栏排版经 OCR 后变成线性文本，语义丢失（"Q3 营收"与它对应的数字可能被分到两块）；而且 OCR 是最上游的不可逆误差源，OCR 的置信度通常也不进入检索链路。
- **AI 改变了什么机制**：**把检索单元从"文本块"换成"页面 / 图像块"**。原清单记的「ColPali（2024）—— 多模态文档检索，无需 OCR」在机制上做的正是这件事：页面当图像直接编码，并保留 **patch 级的多向量表示**（不是压成单一向量），检索时用 late-interaction 打分。

```text
两条链路，换的是"检索单元"，不是"要不要 OCR"（OCR 仍可作为并行产出）
  传统链路：  页面 ──OCR──► 文本块 ──► 文本向量（1 块 = 1 向量）──► 检索
              成本：每页一次 OCR；误差：不可逆（原件信息已丢弃）
  免 OCR 链路：页面 ──► 页面图像编码 ──► patch 级多向量（1 页 = N 个向量）──► 检索
              成本：索引与检索算力上升（N 决定倍数，需自行实测）
              收益：表格 / 图 / 版面的关系不必在预处理时显式重建
  ────────────────────────────────────────────────
  关键：这不是"OCR 死了"，而是"OCR 从必经环节变成可选产出物"——
        很多场景仍需要 OCR 文本（可搜索、可审计、可比对），
        变化在于它不再挡在检索链路的正中间
```

- **由此得到的**：**因为检索单元细化到页面 patch，所以版面对检索质量的影响大幅下降**——"表头与数字分家""跨栏串行"这类 OCR 病灶不再传导到检索；代价是**索引膨胀**：一页产生 N 个向量（N 由页面密度与模型 patch 配置决定），存储与检索成本相对单向量索引显著上升，且**这个倍数只能实测，没有通用数字**。
- **由此付出的**：**其一，索引膨胀与检索算力**——又一次"用钱换准确"，而且膨胀倍数与页面密度强相关，扫描件与纯文本页的差距可能很大；**其二，生态未稳**——单向量索引是多数向量库的一等公民，多向量 / late-interaction 的支持程度需逐产品核验（判定方法：看该库文档里是否有"多向量字段 / 多向量检索"的正式条目，以及它能否与元数据过滤组合使用）；**其三，与"原件不可变"耦合**——页面图像就是检索依据，原件一旦重排或重新导出，索引必须重建（这条与 §5.2.4 的"原件是资产"是同一件事的两面）。
- **证据与来源**：【公开】ColPali 论文（Faysse et al., arXiv 2024）可核验其机制与评测方式；**本节不给"检索质量提升百分之多少"或"索引膨胀多少倍"的数字**，因为两者都强烈依赖文档集与 patch 配置，任何跨数据集的通用数字都不可信。
- **成熟度**：**L2**。判据：论文与开源实现可核验、思路已被产品吸收，但索引侧的支持程度因向量库而异、且缺少第三方公开的上量案例；判定方法是**先在一批真实页面上量出索引膨胀倍数与检索延迟，再决定要不要全量**。

上量之前必须先测出三个数，否则"换链路"只是把一种不确定性换成了另一种：

- **索引膨胀倍数**：同一批页面，多向量索引的存储量与单向量索引的比值。
- **检索延迟**：在目标召回率下的 P99（多向量打分的算力开销高于单向量）。
- **重建触发频率**：原件重新导出 / 重排导致索引重建的频率——它决定这套方案的长期运维成本。

这三项测完之后通常会得到一个反直觉的结论：**多向量检索值得用在"检索质量要求高、文档量可控"的场景，不值得无条件全量替换文本链路**——它的成本随页面密度上升，而文本链路附带的产出（可搜索、可审计、可人工复核的文本）在多向量链路里不会自动获得。

#### 5.2.4 多模态模型直接消费原始模态：L1 的接口能力，与"统一向量空间"不是一回事

- **旧做法与它的卡点**：原清单有两组条目要在这里对齐：方向 5「Agent 直接处理图像 / 视频 / 音频，无需 Embedding 中介」，与方向 3「多模态 Embedding 标准化（ImageBind 六模态对齐）」。它们的卡点是同一个：**把"找"和"理解"混成了一句"多模态能力"**。主文件 §1.2 的第五号痛点（LLM 无法直接消费图像 / 视频）属于"理解"侧；主文件 §2.4 里"多模态 Embedding vs 多模态 LLM"的区分属于"找"侧。混为一谈会同时产生两种错误：拿 LLM 当检索器（贵、召回不稳），或拿 Embedding 当理解器（根本无法生成）。
- **AI 改变了什么机制**：**接口边界上移**——模型 API 直接接受图像 / 音频 / 视频，于是"预处理"从架构上的必经环节变成了可选的优化环节。注意这条机制的适用范围：它改的是**输入形态**，不是**索引结构**。
- **由此得到的**：**因为模型能直接吃原件，所以语料侧有两件事同时成立**：原件不再是"预处理完就能丢"的中间产物，而是可再次消费的资产（元数据要记模态、来源、权限、被哪个模型版本消费过）；同时"存原件"的价值上升而"预处理产物"的价值下降。**但"从大规模语料里找"这件事仍然只能靠索引完成**，因为两条路径的成本函数形状不同。

```text
同一种模态的两条消费路径（不要混用，也不要用一条替代另一条）
  路径 A（索引路径 / 回答「从大规模语料里找哪几条」）
     原件 → 各自的编码器（图 / 文 / 音频 / 视频帧）→ 向量索引 → Top-K
     特点：编码一次、查询多次，边际成本随查询次数被摊薄
     限制：召回上限由编码器与索引决定
  路径 B（直读路径 / 回答「理解了再说」）
     候选原件（来自路径 A 或人工指定）→ 多模态模型 → 答案 / 结构化结果
     特点：每次调用都付费，输入体量线性影响成本与延迟
     限制：不能作用于整个语料，只能作用于少量候选
  ────────────────────────────────────────────────
  2024 年之后的真实变化：路径 B 的**输入**不再要求先变成文本；
  而"统一向量空间、任意模态互搜"属于路径 A 的改造，它没有同等程度的变化
```

- **由此付出的**：**其一，成本与延迟随输入体量上升**，长视频与高分辨率图像尤其明显，因此路径 B 只能作用于已筛出的少量候选；**其二，可复现性下降**——模型版本迭代会改变对同一原件的理解，同一个问题在不同版本上答案不同，因此"用哪个版本消费过这件原件"必须落进元数据；**其三，锁定面转移**——从"存储格式"转到"模态接口"，换模型等于重跑评估与重写提示词。
- **证据与来源**：模型 API 的模态输入是否为正式条目可自行核验（判定方法：查该 API 文档中图像 / 音频 / 视频输入是标注为 GA 还是 preview）；图文对齐的基础工作有公开论文可核验【公开，Radford et al., "Learning Transferable Visual Models From Natural Language Supervision", ICML 2021】；六模态对齐的代表工作是公开论文【公开，Girdhar et al., "ImageBind: One Embedding Space To Bind Them All", CVPR 2023】，**它是研究原型，不等于产品中的"任意模态互搜"已经可用**。
- **成熟度**：**L1（仅指"模型直接消费原始模态"这一接口能力）**；**其"用统一向量空间替代各模态专用检索路径"的推论是 L3**。两件事必须分开定级——把 L1 的接口能力当成 L3 方向的证据，是本节最常见的误判。

元数据里至少要新增三项，否则"直读"这件事在上量后无法审计、也无法复现：

- **模态与来源**：这件原件是什么模态、原始出处（与主文件 §1.1 的"统一元数据"对齐）。
- **权限范围**：谁能把它送进模型——送进模型就等于出域。
- **消费记录**：被哪个模型版本、在什么时间消费过；模型换代后要能按这份记录重跑。

**支线：中文多模态模型与自托管路线**（原文件 §5.1 方向 1 里的 InternVL 条，与原文件 §5.3 里的 Qwen2-VL、InternVL2 条）

- **旧做法与它的卡点**：主文件 §2.3 的多模态 Embedding 表里，图文侧标「中文 SOTA」的是 BGE-VL、标「通用 SOTA」的是 CLIP（同一张表里 OpenCLIP 的「特点」列写的是「开源 CLIP」，定位是 CLIP 的替代实现）；而**可自托管的中文多模态 LLM 在过去没有一等选择**，理解侧只能走闭源 API。卡点有两个：**语种**——中文文档的字形与版面特征与英文语料差异大，英文系编码器在中文文档上召回是否够用不能靠推断，判定方法是拿自己的中文文档集跑一次召回对照；**合规**——原件不允许出域时，云端 API 这条路径直接关闭。
- **AI 改变了什么机制**：**把多模态模型从「只能租用的服务」变成「可下载的权重」**——中文多模态 LLM 以开放权重发布后，同一个「直读」接口能力可以在自有集群内落地。机制上改变的是**部署边界**（问题从「能不能理解」变成「在哪台机器上理解」），不是模型能力本身。
- **由此得到的**：**因为权重可自托管，所以「原件不出域」与「模型直读原件」可以同时成立**；对数据库层的推论是原件与索引可以整条链路留在同一合规边界内，元数据里的「消费记录」也因此有了本地可查的落点。
- **由此付出的**：**其一，运维面搬家**——推理集群、量化与批处理调优从供应商回到自己身上，成本从「按 token 线性付费」变成「按 GPU 小时付费」，后者在低利用率时通常更贵；**其二，版本跟随成本**——开放权重的迭代节奏快，换一个更强版本等于重跑评估、重建索引，这条与 5.2.4 正文的「可复现性下降」是同一个代价；**其三，许可与规格**——权重许可、上下文长度、支持的输入模态需逐个模型核验，不能按「开源即可任意用」假设。
- **证据与来源**：模型侧可自行核验——InternVL 系列与 Qwen 系列 VL 版本的技术报告、模型卡与仓库是公开的（arXiv，2023–2024）；**本节不写「某开源模型在某榜单上超过某闭源模型」**：这类排名随版本与评测口径变化，单次榜单不构成架构判据。
- **成熟度**：**L1（「模型可直读原件」这一能力在开放权重侧同样成立）/ L2（自托管成本与生态）**。判据：权重、模型卡与许可证公开可下载可核验，接口形态与闭源 API 一致；但自托管的推理成本与运维成熟度因团队而异，且缺第三方公开的含规模与成本对比的运行报告。

### 5.3 与本主题既有栈的接口在哪

多模态数据库与上下游不是"结合"关系，而是**交接物**关系：一次检索的结果以什么形态交给下一跳、失败时谁负责，比"支持哪些模态"更能决定系统能不能用。下表按"谁把什么交给谁"来写。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 多模态 DB → 混合检索（§04）/ RAG（§05） | 交接物 = Top-K + 元数据 + **原件引用**（不是原件字节） | 检索侧；**返回空优于返回越权或过期结果** | 既有技术（L1） |
| 多模态 DB ↔ 向量湖（§02）/ AI 原生 DB（§03） | 索引制品与原件分离存放：索引可重建，原件不可丢 | 索引重建方承担耗时；原件侧承担丢失 | 可做，但索引跨 Region 的语义要逐产品核验（L2） |
| 多模态 DB ↔ 数据目录（§08） | 资产登记补三项：模态、权限、**是否被模型消费过及模型版本** | 目录缺项则拒绝发布 | 需要新建字段（L2） |
| 多模态 DB ↔ 多模态模型 API | 原件直送（引用或字节），预处理从必经降为可选 | 模型不可用时回退到"路径 A + 文本化"链路 | 接口能力成熟（L1） |
| 检索 ↔ 预处理链路（Ch3 数据全栈） | OCR / ASR 产出从"链路必经"变为"并行产出 + 可对照" | 预处理侧；但错误不再不可逆 | 变化中（L2） |
| 多模态 DB ↔ Agent 平台（Ch5） | Agent 以工具形式调用检索，工具入参含模态与权限范围 | Agent 侧负责权限与预算；检索侧只管召回 | 可试点，注意预算失控（L2） |
| 多模态 DB ↔ 图 / GraphRAG | 多模态实体与关系（人 - 车 - 地点一类的视频图谱）作为另一套索引 | 图侧；与向量索引的一致性无自动保证 | 概念与自建阶段（L3），原清单条目保留但不判可用 |
| 多模态 DB ↔ 可观测（Ch11） | 新增指标穿过边界：检索命中率、原件取回失败率、单次问答的直读成本 | 平台侧提供通道；业务方定义"什么算异常" | 需要新建，不是既有指标的复用（L2） |
| 多模态 DB ↔ 合规与隐私 | 原件出域前的脱敏与最小化（人脸 / 证件 / 语音）作为**入库门禁** | 数据侧；违规出域没有自动兜底 | 需自建门禁（L2） |
| 多模态 DB ↔ 数据湖（Ch3 数据全栈） | 分层存放：湖存原件与预处理产物，库存索引与元数据 | 湖侧负责原件持久性；库侧负责索引可重建 | 既有技术（L1） |
| 多模态 DB ↔ 多 Region / 单元化（Ch12 §01、§02） | 索引与原件尽量同域部署，避免跨区域取原件 | 单元归属方；跨域取原件失败应降级而非重试打满 | 既有技术，关键是"索引与原件同域"（L1） |

一句话概括：**AI 没有新增调用关系，只改了两件交接物的形态**——原件引用（在检索结果里）和模型版本（在元数据里）。这两样东西决定了一次多模态检索能不能被审计、能不能在模型换代后复现。

这份清单里"第三方生产案例"一栏是空的，原因不是没人在用，而是**可核验的公开材料里没有含规模与指标的多模态数据库运行报告**——厂商案例、技术博客与客户证言都不能当证据用。把这个空白写出来比凑三条模糊案例更有用：它直接决定了本主题下没有任何存储侧方向可以排进路线图。

### 5.5 被过度宣传的部分

**「原生多模态数据库 = 一个引擎搞定一切」**——实际是"把向量索引与文档 / 图模型放进了同一个引擎与查询语言"，规模上的天花板由**索引组件能否独立扩缩**决定，而不是由"支持几种模态"决定。原因：多模型共处一个引擎时，扩缩单位被引擎架构绑住，向量索引这个最需要独立扩缩的部件往往跟着主引擎一起动。**它什么时候才会成真**：release note 里出现独立的索引服务与独立的扩缩配置条目，并且有第三方公开的、含数据规模与召回目标的运行报告——不是"毫秒级检索"这种无条件限定语的宣传。

**「多模态模型能直接读原件，所以不需要 Embedding 检索」**——实际是两条成本函数形状不同的路径被混成了一条。原因：索引是"编码一次、查询多次"，边际成本随查询次数被摊薄；直读是"每次调用都付费"，边际成本随输入体量线性增长。语料规模一大、查询次数一多，"全部直读"在成本上不可行。**它什么时候才会成真**：出现公开基准，证明在给定语料规模与查询次数下，全量直读在成本与延迟上优于"检索 + 直读"——这类基准必须带条件，否则不可比。

**「ColPali 免 OCR，所以 OCR 可以下线了」**——实际换来的收益是"版面对检索的干扰下降"，付出的代价是索引膨胀与生态未稳，而且 OCR 文本在很多场景是必要产出物（可搜索、可审计、可比对、可被人复核）。原因：检索单元从"文本块"细化到"页面 patch"，成本结构随之改变；这是一个工程权衡，不是一次能力替代。**它什么时候才会成真**：多向量 / late-interaction 成为主流向量库的一等索引类型，且文档密集行业出现第三方公开的上量案例（含索引成本对比）。

这三条的共同结构是：**被宣传的是"能力覆盖"，而决定能不能用的是"成本结构"**。所以评审任何多模态方案时先问一句"它的成本随什么增长"——随文档量增长的是可预算的，随问答次数增长的是会失控的。

### 5.6 未来 3–5 年：可证伪的预测

四条预测里，前两条问的是"工程界会不会按成本结构做选择"，后两条问的是"技术形态会不会变"——前者的命中率通常高于后者，因为成本约束比技术偏好稳定。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 多模态检索的默认形态会是"多向量 / late-interaction 索引 + 原件对象存储"，而不是"一切先文本化再单向量检索" | 主流向量库把多向量检索做成一等索引类型（release note 可见）；文档密集行业出现第三方公开的上量案例 | 三年后主流仍是"OCR → 文本块 → 单向量"，多向量索引停留在论文与试点 |
| 「原生多模态数据库」的竞争点会从"支持几种模态"转到"索引能否独立扩缩" | 产品路线图与 release note 出现索引组件独立扩缩 / 存算分离条目；对外口径跟着改 | 厂商仍在比模态数量与单机演示，架构文档里索引与主引擎仍不可分 |
| 3D / 点云在通用数据库里仍不会成为主流存储对象 | 通用库仍无点云一等类型；实践仍是专用栈承载 + 元数据挂钩（与今天一致） | 出现第三方公开的、用通用数据库承载点云检索并上量的生产案例（含规模） |
| 「多模态 Agent 普及」会以工具调用的形式发生，而不是 Agent 内置多模态索引 | Agent 平台的标准实践是"把检索当工具调用"，权限与预算在 Agent 侧 | 出现"Agent 自带向量索引 / 自带多模态存储"成为主流架构并被广泛采用 |

写这四条时的共同约定：**信号必须是外部可观察的**（release note 条目、第三方公开案例、架构文档），而不是"我觉得会"。凡写不出证伪信号的判断，本节不写。

其中第三条最容易被误读：它不是说 3D 不重要，而是说**通用数据库不会为它改动自己的类型系统与索引结构**——自动驾驶与机器人会继续走"专用栈承载点云 + 对象存储 + 元数据挂钩"这条路，而这条路今天就已能跑通，不需要等前沿。

### 5.7 给架构师的行动建议

下表按"你的处境"分行：同一项技术在不同处境下的正确动作不同——文档密集的团队该先量索引膨胀，而只有文本资产的团队最该做的是**先别引入多模态**。

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 只有文本，业务开始提"能不能搜图" | 先做"文本 + 图像两条独立链路 + 元数据关联"，不要先合并存储 | 观察图文混排文档的实际占比——它决定了要不要上多模态索引 | **不要为"统一向量空间 / 任意模态互搜"预留 schema**；不要一上来就换数据库 |
| 文档密集（合同 / 报表 / 发票） | 小规模试点页面级多向量检索；同时保留 OCR 作为并行产出物 | 观察向量库是否把多向量检索列为一等能力，以及它与元数据过滤能否组合 | 不要在没有对照评测的情况下宣布"免 OCR 上线"；不要把 OCR 直接下线 |
| 已有向量库并坚持单向量索引 | 先把"原件引用 + 模型版本"补进元数据；再评估是否引入第二套索引 | 测量"图像 / 页面检索"的真实需求量，而不是预估 | 不要为了追新做一次全量重建；不要让索引与原件版本脱钩 |
| 场景含 3D / 点云 / IMU | 用专用栈承载 + 用元数据挂钩到主库；在目录里登记模态与来源 | 观察通用库是否把点云列为一等类型（大概率不变） | 不要在通用数据库里预留点云字段类型；不要指望向量库解决点云的近邻查询 |
| 面向 C 端的多模态交互（拍照问答） | 走"路径 A 检索 + 路径 B 直读"的两段式，并对模型调用加预算上限 | 观察单次问答的原件直送成本与首字延迟，按月复算 | 不要把全量语料直读进上下文；不要用分辨率无关的方式估成本 |
| 已有 GraphRAG / 知识图谱，想接入多模态实体 | 把多模态实体作为图的节点与属性接入，而不是把向量塞进图库 | 观察图库是否提供"向量 + 图"联合查询的正式能力条目 | 不要指望图与向量索引自动保持一致（没有自动保证） |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的（改 schema、全量重建、成本模型失真），而收益依赖一个尚未成立的假设**（统一向量空间已可用 / 多向量索引已普及 / 通用库能管点云）。等 5.6 的信号出现再投入，损失的只是时间。

**如果你只能做一件事**：把"检索路径"与"直读路径"在架构图上分开画，并各写一个成本口径。多模态项目最常见的失败不是模型不够好，而是这两件事被当成一件做：

1. 检索路径的成本按**查询次数**估算（编码一次、查询多次）。
2. 直读路径的成本按**输入体量 × 调用次数**估算（每次都要付费）。
3. 两条路径之间要有明确的**候选数量上限**（直读只作用于 Top-K）。
4. 元数据要能回答"这张索引是用哪个编码器版本建的、这件原件被哪个模型版本读过"。

这四条不依赖任何新产品或新模型，今天就能落地。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**接口边界上移**——模型可以直接消费原始模态，于是"预处理"从架构必经环节变成可选优化环节，原件从归档物升级为可再次消费的资产。因为这一点，排进 L1 的是一个**接口能力**，而不是任何存储侧的产品：原生多模态数据库、多向量文档检索、跨模态统一空间都停在 L2 或 L3，判它们的不是"支持多少模态"，而是"索引能否独立扩缩、索引膨胀多少倍、跨模态检索有没有第三方评测"。它**没有**改变的是索引的基本职责——**从大规模语料里找**这件事仍然只能靠编码 + 索引完成，模型直读只能作用于已经筛出来的少量候选。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是"找"还是"理解"？** 改变"理解"的（直读原件）今天就能用；改变"找"的（统一向量空间、任意模态互搜）要等评测和索引生态。
>
> 最后一条可操作的建议：**把"原件可用性"当成多模态系统的首要 SLA**。索引可以重建、编码器可以更换、模型可以换代，原件丢了或版本对不上，前面所有能力都归零——这条与主文件 §1.1 的"统一存储 + 统一元数据"是同一个要求。
