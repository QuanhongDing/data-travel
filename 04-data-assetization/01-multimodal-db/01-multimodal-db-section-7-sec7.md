## 7. 与其他方法对比

> 原 § 7 共 48 行、为打分表 + 决策树 + 组合罗列，缺少机制解释与可溯源证据，重写为 ~300 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

打分表的第一处误导，是把**场景相关的结论**写成**绝对结论**。原表在「实时性」一列给「文本 + ES」5 分、「多模态原生 DB」4 分，这一分之差没有任何机制说明——两者都靠 ANN 近邻索引，真正的差别是索引驻留在哪、一次查询要跨几个系统。同样，「跨模态检索」给文本 + ES 打 1 分、给多模态原生 DB 打 5 分，掩盖了一个事实：多模态原生 DB 能做跨模态检索，靠的是它内部同样使用了**统一向量空间**，而不是「原生」这个属性本身——把同一套图文对齐编码器接到 ES 的向量字段上，跨模态这件事一样成立。

第二处误导是**维度方向不明**。「工业成熟度」给文本 + ES 5 分、多模态原生 DB 3 分，读起来像后者更差，但它真正要表达的是「生态与工具链的存量」——这是**可替换成本**，不是能力差异。把可替换成本和能力放进同一张表并排打分，读者无法分辨哪一列是在描述系统本身、哪一列是在描述你离开它的代价。

第三处误导是**同一维度在不同规模下权重相反**。「单一存储管理」对小团队是第一位，对已有成熟数据平台的组织几乎是末位——多一套存储的边际运维成本，在已经有二十套系统的地方接近于零。打分表给的是跨规模的平均数，而选型永远发生在某一个具体规模上。

第四处误导是**把「能不能做」混进「做得多好」**。「跨模态检索」给文本 + ES 打 1 分，读起来像「它做不到跨模态」；真正做不到的只是「在同一空间里排序」这一件事——换上统一空间的编码器、把向量写进向量字段，文本 + ES 同样能返回跨模态候选，它的强项仍然留在符号匹配那一侧。打分把「需要先换一件东西才能做」压缩成了「天生不会做」，代价是读者会整类跳过其实可用的方案。

所以本章的判据不写成「几分」，而写成三句话：**这个方案在机制上做不到什么**、**它的成本随什么变量增长**、**我离开它要付什么**。下面是具体化的 6 条。

判据之间**有先后**，不能平权相加。**可比性来源**是前置条件：它不成立时，跨模态排序在物理上做不出来，后面五条讨论的都是「一个不能做跨模态的系统有多好」，没有意义。**过滤与近邻的先后**是第二个前置条件：它决定一次查询是返回结果还是返回空集，而返回空集是唯一无法靠调参掩盖的失效。剩下的四条——原件可变性、表示保真度、稀疏覆盖、运维规模——是在前两条成立之后，用来在同类候选之间做取舍的。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 可比性来源 | 各模态是否被投进同一组维度与坐标系 | 跨模态排序只在同一空间里成立；分模态编码时跨模态查询在物理上做不出来，不是「效果差一点」 |
| 过滤与近邻的先后 | 结构化条件参与检索，还是检索后裁剪 | 条件选择性强时，后裁剪会把 Top-K 裁空，召回直接为零——表现为「查不到」，不是「慢」 |
| 原件的可变性 | 原件是否基本不变、只是持续新增 | 决定向量是「可重建的派生物」还是「必须与原件同事务」的一等数据，直接决定要不要同步链路 |
| 检索表示的保真度 | 信息在文本流里，还是在版面 / 时序里 | OCR 是不可逆的上游；版面信息一旦丢弃，重跑也没有输入 |
| 稀疏与稠密的覆盖 | 查询里有没有大量型号、编号、专名 | 稠密向量把字符级区分抹平，纯稠密会整体漏掉精确匹配类查询 |
| 运维与团队规模 | 有几个人能长期维护几套存储 | 多套存储的成本不在软件许可，在 N 套备份 / 权限 / 升级与跨系统对账 |

这 6 条分两类：前两条是**门槛项**——不满足时不是「差一点」，而是「这件事根本做不成」（跨模态排序做不出来、查询返回空集）；后四条是**权重项**——它们的相对重要性随规模与场景反转。把两类混进同一张表平均打分，正是打分表失真的根源：门槛项被平掉，权重项被当成常数。用表时按顺序读——先过门槛，再比权重。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 文本 + ES | 关键词为主、向量为辅的检索栈 | 倒排索引（BM25）+ 向量字段 kNN，稀疏与稠密同库 | 已有关键词检索栈、以文本为主的团队 | 开源 + 托管服务（Elastic） |
| 传统向量库（Milvus / Qdrant / pgvector） | 专用近邻检索 | 只索引向量与少量标量，专注 ANN 与索引参数调优 | 单模态语义检索、起步阶段 | 开源 / 托管，两种都有 |
| 多模态原生 DB（Weaviate / SurrealDB） | 一个系统内多模型 | 文档 + 图 + 向量在同一执行器内安排过滤与近邻 | 小团队新项目、模态种类还在增长 | 开源 + 托管 |
| Lakehouse + 向量库 | 超大不可变语料的在线检索 | 湖是唯一事实源，向量是可重建的派生物，增量同步 | PB 级、以新增为主、同时服务训练与在线 | 开源为主 |
| 模态专属 + 元数据关联 | 每段用最优引擎 | 统一关联键 + 先筛后搜（实时形态下沉为同库混合） | 条件筛选强的电商、车联网场景 | 组合式，无单一供应商 |
| 多模态 RAG | 端到端问答 | 检索 Top-K → 多模态 LLM 生成并回链原件 | 图文问答、视频理解、文档助手 | 组合式 |
| ColPali 一类多模态文档检索 | 复杂版式文档 | 页面当图像编码成多向量，late interaction 逐 patch 匹配，跳过 OCR | 扫描件、财报、表单 | 论文 + 开源实现（illuin-tech/colpali） |
| CLIP + Milvus | 图文跨模态检索基线 | 双塔统一空间 + ANN 近邻 | 图文检索起步、做可行性验证 | 开源 |
| 托管向量库（Pinecone 一类） | 把分片、扩缩与隔离做成服务 | 平台承担分片 / 副本 / 扩缩，元数据过滤与命名空间内置 | 不具备向量检索运维能力的团队、多租户 SaaS | 商业托管 |
| 仓内向量化（AI Function 形态） | 在事实源侧完成加工 | 多模态模型以函数形式在仓库内可用，数据不出仓 | EB 级多模态、合规要求高的组织 | 随平台 |

这 10 个候选其实只分三**族**：**通用检索栈加向量能力**（文本 + ES、pgvector 一类、传统向量库、托管向量库）、**一体化多模型**（多模态原生 DB）、**组合式**（模态专属 + 关联、Lakehouse + 向量库、多模态 RAG、ColPali、仓内向量化）。同族内部换件代价小（改索引参数、换索引类型），跨族切换要重做数据组织方式（重建关联键、全量重算向量）。**先分族再选，能省掉一半比较。**

族内的差别比读表产生的印象小得多，可以说清：

- **通用检索栈族内**：ES 强在倒排索引与聚合、强在已有的分析能力；pgvector 一类强在向量与事务 / 权限 / JOIN 同库；专用向量库强在索引参数与规模化的调优深度。**三者都不提供跨模态编码器**——能不能跨模态，由你选的编码器决定，不由数据库决定。原 § 7 决策树里「CLIP + Milvus」这一分支，正是这一族 + 一个统一空间编码器的组合。
- **一体化多模型族内**：Weaviate 偏向量优先的模块化能力，SurrealDB 偏文档 + 图 + 向量的多模型形态。两者都提供「一个系统内写完过滤与近邻」，**也都不提供跨模态语义空间**——把「原生支持文档与图」当成「原生支持跨模态」，是选型中最常见的误读。
- **组合式族内**：差别集中在**事实源是谁**。Lakehouse 形态以湖为唯一事实源、向量是可弃的派生物；模态专属 + 元数据关联形态以各模态系统各为事实源、靠关联键拼装；仓内向量化形态把事实源放在数据仓库，连加工都不离开它；多模态 RAG 与 ColPali 形态则把「检索结果」本身当作下一步的中间输入。事实源定不下来，一致性的责任就落不到具体某个组件上。

读「许可 / 商业模式」这一列时要注意，它衡量的不是成本高低，而是**成本从哪个口袋出去**：开源组合把成本放在集成与运维人力上，托管服务把它挪到账单上。两者在总拥有成本上未必谁更低——小团队的时间往往比账单贵，而人手充足的组织里，托管溢价会显得刺眼。这一列的作用是让你知道钱从哪来，不是替你算总账。

原 § 7 出现过的候选——文本 + ES / 文本向量库、传统向量库、多模态原生 DB（Weaviate / SurrealDB）、Lakehouse + 向量库、模态专属 + 元数据关联、CLIP + Milvus、ColPali 一类多模态文档检索——在上表中逐条保留，未做删减；其中「文本向量库」与「文本 + ES」在决策树里本是一体的两种取法，此处并列。

### 7.3 机制差异：为什么它们表现不同

以下 4 个机制维度，决定了候选之间的绝大多数可观察差异。前两个决定「一次查询能不能得到想要的结果」，后两个决定「这套结构能不能长期跑下去」——四者都不可通过调参绕开，只能在选型时选对。

#### 7.3.1 可比性从哪来：统一向量空间 vs 分模态编码

- **机制是什么**：训练时用成对数据把匹配对拉近、不匹配对推远，两侧编码器输出**同维同坐标系**的向量；检索时只比向量，不比模态。
- **在各候选中的实现差异**：

| 候选 | 向量空间 | 可见结果 |
| --- | --- | --- |
| CLIP / ImageBind 一类 | 单一对齐空间，所有模态共享维度与容量 | 跨模态排序成立，主力模态精度可能低于其专用编码器 |
| 分模态编码（各模态各一套模型） | 多个互不可比的空间 | 单模态检索各自最优，跨模态排序无从下手 |
| 多模态原生 DB | 本身不提供对齐空间，只提供多向量类型与索引 | 能不能跨模态取决于你喂进去的编码器，不取决于产品 |
| ColPali 一类 | 页面级多向量（每 patch 一个向量），非单向量 | 检索在页面上做，与文本空间不可直接混排 |

- **维度与容量是所有模态共享的一笔预算**：`d` 与编码器容量对每个模态都是同一个约束，为图像调大容量就会挤压文本的区分度，反之亦然。中文与专业领域常见的做法不是加大容量，而是做领域微调——微调改变的是分布对齐的方向，不是容量本身 【经验】。
- **由此必然导出的性质**：因为所有模态共用同一组维度与容量，所以「以文搜图」与「以图搜图」共用同一条检索链路、新增一种查询模态不需要新增一套索引；代价是这个可比性是从共享空间里**挤出来**的——任何模态的专有信息在投影进这个空间时都会被压掉，为容纳多模态，每种表示都比专用模型更粗。
- **公开证据**：CLIP 由 OpenAI 公开，ViT-B/32 输出 512 维、ViT-L/14 输出 768 维 【公开】（Learning Transferable Visual Models From Natural Language Supervision，2021）；ImageBind 以图像为锚点把六种模态对齐到同一空间 【公开】（Meta ImageBind，2023）；ColPali 于 2024 年提出并已有开源实现 【公开】（ColPali: Efficient Document Retrieval with Vision Language Models，2024；仓库 illuin-tech/colpali 可自行核验）。中文图文场景通常换用中文对齐模型或做领域微调 【经验】。
- **失效条件**：当业务以单模态检索为主、且该模态存在更强的专用编码器时，统一空间从「跨模态可比」反转为「精度拖累」——训练分布与业务领域相差越大（中文长尾商品、专业文档），反转越明显。
- **落地判据**：跨模态这件事是否成立，不取决于产品名，而取决于**两侧编码器输出维度与坐标系是否被显式规定过**。没有显式规定，「跨模态」在物理上就不成立，任何跨模态排序结果都是假的（本章 [§3.5](01-multimodal-db-section-3-sec3.md) 把这一条列为「忽视模态对齐」反模式的后果）。可用的验证方式很小：取一批成对样本（同一对象的图与文），看跨模态召回的命中顺序是否符合预期。

#### 7.3.2 过滤与近邻谁先发生

- **机制是什么**：ANN 索引一次查询能接受两类输入——查询向量本身，以及一批**可下推**的过滤条件。条件能否下推，决定它是「缩小搜索范围」还是「检索完再裁剪」。
- **在各候选中的实现差异**：

| 候选 | 条件与近邻的关系 | 暴露方式 |
| --- | --- | --- |
| 多模态原生 DB / ES / 同表混合查询 | 过滤与近邻由同一执行器（或优化器）安排顺序 | 条件真正缩小了近邻搜索范围 |
| 托管向量库的元数据过滤与命名空间 | 过滤作为检索接口的一部分传入 | 需要按官方文档确认过滤是下推还是后置 |
| 模态专属 + 元数据关联（先筛后搜） | 关系库筛出 ID 集 → 向量库在候选集内近邻 | 候选集一大就退化成全库近邻再加交集 |
| ES 同库（倒排 + 向量字段） | 向量字段上带过滤的近邻查询 | 语法都写得通，过滤是否真下推仍要看执行计划 |
| Lakehouse + 向量库 | 条件在应用层拼装，跨两个系统 | 两段各自正确，组合结果需要自行对账 |

- **由此必然导出的性质**：因为过滤能作为近邻搜索的**输入**下推，所以 Top-K 一定落在满足条件的子集里；反之若条件只在检索**之后**裁剪，因为 ANN 返回的是全库近邻的前 K 条，条件一强就把这 K 条整个裁空——用户看到的是「零结果」。硬化一下这条因果：这不是「慢一点」，是「查不到」，而且是随条件选择性升高而必然发生的。
- **公开证据**：把元数据过滤与命名空间做进检索接口、而不是留给应用层拼接，是托管向量库的常见能力形态 【经验】（可按 Pinecone 官方文档的 Metadata Filtering 与 Namespaces 两个条目自行核验，能力条目与命名以该文档当前版本为准）；多向量与多模型同样是开源多模型库的常见能力条目 【经验】（可按 Weaviate 官方文档的 multi-modal / multi-vector 条目、SurrealDB 官方文档的文档 + 图 + 向量多模型条目，以及源码仓库 weaviate/weaviate、surrealdb/surrealdb 的当前版本自行核验）；本章 [§1.3 Pinecone 案例](01-multimodal-db-section-6-sec6.md) 记录了同一机制在托管产品上的落地形态。
- **失效条件**：当过滤后候选集**仍有百万级**时，索引无法把这份 ID 列表当作高效的过滤条件，「先筛后搜」名义上两步、实际退化成全库近邻再加交集。注意 pgvector 一类扩展也支持在同一 SQL 里写 `WHERE` 与 `ORDER BY` 近邻，但过滤是否真的下推到索引、还是退化为后置过滤，取决于索引类型与查询计划——**必须在自己的数据上验证**，不能按语法像不像来判断。
- **怎么把选择性测出来**：在真实数据上跑两条查询——带条件与不带条件——对比各自返回的候选量上限与响应时间；再看 `EXPLAIN` 一类的执行计划里，过滤算子出现在近邻搜索之前还是之后。前者的结果与后者相差一个量级以上时，说明条件真的在下推。这一步通常半天以内就能做完，却能避免后面整轮方案误判 【经验】。

#### 7.3.3 原件是否可变：可重建的派生物 vs 唯一事实源

- **机制是什么**：向量是「原件 + 编码器 + 编码器版本」的确定函数。原件不变时，向量是可重建的**派生物**；原件频繁更新时，向量必须与原件同生命周期管理。
- **在各候选中的实现差异**：

| 候选 | 向量的地位 | 一致性由谁保证 |
| --- | --- | --- |
| Lakehouse + 向量库 | 派生物，库丢了可重算 | 增量同步链路 + 「差异条目数」指标 |
| 同表 / 同库（pgvector、多模态原生 DB） | 与元数据同事务的一等数据 | 数据库事务 |
| 原件外置对象存储 + 库内路径 | 库内只留可检索部分，原件是事实源 | 路径与校验和必须可校验 |

- **由此必然导出的性质**：因为换编码器会让新旧向量**互不可比**（两个空间不可比，`cos` 数值失去意义），所以只要原件与编码器版本都留着，向量库整个丢掉也只是重算一次，选型上就敢把它当「可弃的缓存」；反过来，只要原件被反复替换，因为同步链路的单位成本是固定的而后端更新频率上去了，「湖 + 异步向量库」就会**长期**检索到已删除或已更新的条目——这不是偶发故障，是结构性的。
- **公开证据**：换编码器即全库重算这一机制，本章 [§3.2.1](01-multimodal-db-section-3-sec3.md) 已用同一条推导给出，并在 [§3.5 反模式表](01-multimodal-db-section-3-sec3.md) 中列为「不存原文件」的后果；CLIP 的 512 / 768 维输出为公开规格 【公开】（OpenAI，2021）。
- **失效条件**：当数据以**原地更新**为主、且业务要求读到最新（下单即更新库存向量这类场景），这条便宜路线整体失效，必须缩短同步链路（同表 / 同库，或 CDC 驱动的增量同步）。
- **重建窗口是一个必须提前算的预算**：把「可重建」当成「随时能重建」是常见误判。重建要跑全量编码 + 重建索引，这段时间里在线检索要么不可用、要么用旧版本顶着。因此选型时要能回答两个问题：全量重算一次需要多少算力与多久，以及在这段时间里业务能不能接受检索结果滞后。【经验】多数团队的做法是保留上一版索引、新索引构建完成后原子切换，而不是就地重建。
- **派生物地位还带来一个附加能力：可审计的重算**。因为从原件到向量的每一步（编码器、版本、参数）都能被记录，所以「这个检索结果是用哪个模型、哪版数据算出来的」是可以回答的；原件一旦丢弃，这条链在第一步就断了，模型审计也就无从谈起。

#### 7.3.4 检索作用在什么表示上：文本流 / 页面多向量 / 稀疏 + 稠密

- **机制是什么**：检索的召回上限，由「被索引的那个表示里还剩多少信息」决定。索引的是 OCR 后的文本、页面图像，还是关键词倒排，决定了能召回什么。
- **在各候选中的实现差异**：

| 检索表示 | 保留了什么 | 丢了什么 | 典型候选 |
| --- | --- | --- | --- |
| OCR 后的文本流 | 可精确匹配的字符串 | 版面结构、印章、手写、图表关系（不可逆） | 文本 + ES、传统文本检索链路 |
| 页面多向量 | 版面与视觉信息 | 精确字符匹配能力 | ColPali 一类 |
| 稀疏（BM25 / 稀疏向量） | 字符级精确区分 | 语义泛化 | ES、支持稀疏 + 稠密的向量库 |
| 稠密单向量 | 语义泛化 | 型号、编号这类字符级区分被抹平 | CLIP + Milvus 一类 |
| 帧 + 时间戳（视频）/ 结构摘要（点云） | 事件顺序与结构一等信息 | ——（若不保留则顺序不可恢复） | 模态专属存储 + 摘要入库 |

- **由此必然导出的性质**：因为 ColPali 把页面当图像编码成每 patch 一个向量，所以表格栏位关系、印章、手写这些**不在文本流里**的信息被保留下来，OCR 错误不再成为不可逆的上游；代价是向量数 = 页面数 × patch 数，索引体积与检索算力按 patch 数成倍放大——它买的是保真，付的是体积。反向的因果同样成立：因为像素级表示对稀疏字符串的匹配天然弱于符号匹配，所以合同编号、金额逐位比对这类查询在纯视觉表示上会**系统性地漏**，此时该用稀疏与多向量混合，而不是二选一。第三条同源的因果是：因为视频抽帧只保留帧、不保留时间戳，所以「先后发生了什么」在索引里已经不存在，任何下游处理都补不回来——视频与点云必须把时间与结构当一等信息存，而不是当图像的附属字段。
- **公开证据**：ColPali 论文与开源实现 【公开】（ColPali: Efficient Document Retrieval with Vision Language Models，2024；仓库 illuin-tech/colpali 可自行核验）；稀疏 + 稠密并用、两条通道的分数融合后重排，是托管与开源向量库的常见能力形态 【经验】（可按 Pinecone 等向量库官方文档的 hybrid search / sparse-dense 条目自行核验，能力命名与范围以各自文档当前版本为准）；本章 [§3.2.6](01-multimodal-db-section-3-sec3.md) 对同一机制的完整拆解。
- **表示的选择还决定了错误能不能被定位**：OCR / ASR 出错时，「检索没找到」与「原文根本没提取对」在监控里长得几乎一样——成功率、延迟、索引健康全是绿的。所以为 OCR / ASR 单独建准确率基线不是可选项，它是把「检索问题」与「提取问题」分开的唯一手段（本章 [§3.5](01-multimodal-db-section-3-sec3.md) 把这一条列为最不可逆的一条反模式）。
- **失效条件**：当语料是干净的数字原生 PDF、且信息基本都在文本流里时，页面多向量方案付出的索引体积换不到相应的召回提升——此时 OCR + 文本检索反而是更省的形态。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ C_原件      随数据总量增长，单价最低（对象存储量级）
     + C_向量与索引 随「向量条数 × 维度 × 索引膨胀系数」，单价最高，通常必须常驻内存或高性能盘
     + C_向量化     随语料总量，一次性 + 每次换编码器再付一次全量
     + C_在线检索   随 QPS × 候选扫描量（过滤越弱，扫描量越大）
     + C_同步与治理 随系统套数增长，与数据量无关
```

比较成本前要先固定三个变量，否则「A 比 B 便宜」这个结论没有可比性：**数据总量**（决定 C_原件）、**向量条数与维度**（决定必须常驻的那部分）、**查询量与过滤选择性**（决定 C_在线检索的扫描量）。大量看似冲突的成本结论，其实是两次比较里这三个变量取了不同的值。

各候选的**主导项**完全不同：

| 候选 | 主导成本项 | 隐性成本 |
| --- | --- | --- |
| 文本 + ES / pgvector | C_在线检索 + 索引驻留 | 过滤未下推导致的扫描量放大 |
| 传统向量库（单机） | C_向量与索引 | 扩容时的重建窗口与召回基线重建 |
| 多模态原生 DB | C_向量与索引 | 生态窄带来的自建运维件（监控、备份、权限） |
| Lakehouse + 向量库 | C_同步与治理 + C_向量化 | 跨系统不一致的长期对账人力 |
| 模态专属 + 元数据关联 | C_同步与治理（随系统套数） | 关联键失配产生的孤儿记录 |
| 多模态 RAG | C_在线推理（随提问数） | 检索层与生成层各自的评估集建设 |
| ColPali 一类 | C_向量与索引（随 patch 数放大） | 为精确字符查询补一套稀疏通道 |

**隐性成本**有两处最常被漏算：换编码器触发的全量重算（一次性但很大），以及跨系统不一致的长期对账人力（不大但永久）。

【公开】对象存储标准层的公开定价约 $0.023/GB-月、归档层约 $0.004/GB-月（AWS S3 公开定价页，us-east-1，2024 年前后可核验；当前值请以云厂商定价页为准）。

【推算】1 亿条 1024 维向量的在线成本量级：

- float32 每维 4 字节 → 每条 1024 × 4 B = 4096 B ≈ 4 KB
- 1 亿条 → 4 KB × 1e8 ≈ **400 GB 原始向量**
- ANN 索引（如 HNSW）在向量之外还要存图连接结构，实测膨胀通常在原始向量的 1~2 倍量级 【经验】
- 所以「在线必须常驻」的是 **400 GB ~ 1 TB** 这个量级；原件可以放在上面那个约 $0.023/GB-月 的对象存储层，向量不行，它要参与每一次查询
- 按同一单价粗算，与**向量**同体积的那 400 GB 若放标准层约 $9.2/月（$0.023/GB-月 × 400 GB），一年约 $110——**这个数小到可以忽略，恰好反过来说明账单的决定项从来不是「静态体积放在哪个介质上」，而是「必须参与每次查询的那部分」放在什么介质上**
- **原件**的体积是另一笔独立的账，不在上面这个 400 GB 里：一条 1024 维 float32 向量约 4 KB，而一张图片、一段音视频原件的体积通常比它大一到三个数量级 【经验】。上面那个 $9.2/月只说明「向量自己占的静态体积」有多便宜，**没有回答原件存储这一笔**——原件要按原件体积重算，同单价下账单与体积成正比：体积大多少倍、账单就大多少倍，不能把向量体积代进原件的算式
- 若把向量量化到 int8：每条 1024 × 1 B = 1 KB，1 亿条 ≈ **100 GB**，推导与上面同源（位宽从 32 位降到 8 位，维度不变）；召回损失必须在自己的固定查询集上实测，不能按比例外推 【经验】
- 量化是控制 C_向量与索引 最直接的手段，它换来的是内存与账单、付出的是召回率，而召回损失与数据分布强相关，只能实测 【经验】

【推算】7.5 决策树里的「千万 / 亿」两个阈值，就是由上面这段推导定出来的：1,000 万条按同一推导约 **40 GB** 原始向量，单机单实例可以容纳；1 亿条约 **400 GB**，通常需要分片或托管。**这两个数字的来源是内存与索引体积的物理量级，不是经验拍数。**

【推算】换一次编码器的重建成本量级：语料条数 × 单条编码算力。以 1 亿条图文条目为例，编码要跑 1 亿次前向推理，再叠加一次全量索引构建与切换——这是一次按天计的专项动作，不是一次配置变更。所以「不存原件」的代价不是省了存储，是**换模型这条路被永久堵死**。推导链：条数 × 每条算力 = 总算力；该算力与你的编码器规模成正比、与你的语料规模成正比。【经验】多模态 RAG 的成本函数与上面完全不同：单次成本 ≈ 被喂进 LLM 的页面 / 图像数 × 每页单价，总成本随提问数线性增长，与语料规模无关。所以「用多模态 LLM 直接读全量页面」的路径不是「贵一点」，是「成本随使用量无上限增长」。

### 7.5 决策树（每个分支都要有阈值依据）

树的形状由判据的先后顺序决定：**先问可比性**（有没有非文本模态、跨模态是不是主需求），**再问一次查询能不能出结果**（版面信息在哪、过滤能不能下推），**最后才问规模与运维**。前三层是「做不做得到」，第四层才是「值不值得」。把规模问题放在前面，就会得到「先买一个能扛亿级的向量库，再发现过滤没下推」这类返工。

```
[数据里有非文本模态吗？]
 ├─ 否（只有文本）
 │   └─ [查询里有大量型号 / 编号 / 专名吗？]
 │        ├─ 是 → 文本 + ES（BM25 为主），语义需求叠加向量字段
 │        └─ 否 → 传统向量库 / pgvector；已在 ES 栈上就别引入第二套
 │
 └─ 是（多模态）
     ├─ [跨模态检索是主需求吗？]
     │    ├─ 否（模态各自检索，靠业务键关联）
     │    │   → 模态专属 + 元数据关联（统一关联键是唯一契约）
     │    └─ 是
     │        ├─ [信息依赖版面（扫描件 / 财报 / 表单）而非文本流吗？]
     │        │    ├─ 是 → ColPali 一类页面多向量检索（+ 稀疏检索兜精确字符）
     │        │    └─ 否
     │        │        ├─ [过滤后候选集占比 < 10% 吗（条件选择性强）？]
     │        │        │    ├─ 是 → 过滤必须参与检索：多模态原生 DB / 同表混合查询 / 支持过滤下推的向量库
     │        │        │    └─ 否 → 统一向量空间 + 向量库（CLIP + Milvus 或托管向量库）
     │        │        └─ [向量条数量级？]
     │        │             ├─ ≤ 千万   → 单机 / 单实例可容纳，多模态原生 DB 或 pgvector 足够
     │        │             ├─ 千万 ~ 亿 → 分布式或托管向量库（分片 + 在线扩缩），重建召回基线
     │        │             └─ > 亿     → 原件与可分析部分进湖仓，向量作为可重建派生物
     │        └─ [原件是否基本不变、以新增为主？]
     │             ├─ 是 → Lakehouse + 向量库（湖为唯一事实源）
     │             └─ 否（频繁更新）→ 条件与向量同表 / 同库，或 CDC 增量同步
     └─ [要的是候选还是答案？]
          ├─ 要候选 → 结果附原件路径并按模态分组（复核要回到原件）
          └─ 要答案 → 多模态 RAG（检索层与生成层分离，各自可测）
```

**阈值依据**（与树上每个判断节点一一对应）：

- **节点「有没有非文本模态」**：机制判据，不是按文件扩展名判断，而是按「关键查询所依赖的信息是否落在文本流里」判断。图片、音频、点云、视频一眼可辨；而扫描 PDF 的「非文本性」往往要等到业务想查表格栏位关系时才暴露。
- **节点「型号 / 编号 / 专名占比」**：判据是稀疏查询的比例。抽样一两百条真实查询，若其中有相当一部分是型号、单号、编号这类字符级匹配，纯稠密会系统性漏召回，必须保留 BM25 一类符号通道。【经验】
- **节点「跨模态是主需求吗」**：机制判据——标准是「有没有一类查询要求把不同模态的候选放进同一个排序里」。只要存在这样的查询，可比性来源就是第一位；不存在时，为跨模态付出的精度损失纯属白付。
- **节点「信息依赖版面吗」**：机制判据而非数值阈值——表格栏位关系、印章、手写、图表关系不在文本流中，OCR 后**不可恢复**，所以只要这类信息是关键查询的依据，就应直接选择页面表示，不给 OCR 留下不可逆的上游。
- **节点「过滤后候选集占比 < 10%」**：条件选择性决定下推的收益边界。占比很低时，下推能把近邻搜索范围缩小一个量级以上；占比接近一半时，下推与后裁剪的差别迅速缩小、不值得为它换技术栈 【经验】。该阈值的作用是提示「先验证选择性，再决定要不要换」，不是精确判据。
- **节点「向量条数量级」**：来自 7.4 的体积推导——1024 维 float32 每条约 4 KB，1,000 万条 ≈ 40 GB、1 亿条 ≈ 400 GB 原始向量，叠加 1~2 倍索引膨胀；40 GB 量级可单实例常驻，400 GB 量级通常必须分片或托管。依据是**内存与索引体积的物理量级**，不是使用习惯。
- **节点「原件是否基本不变」**：机制判据——标准是「更新间隔是否短于同步周期」。只要存在会被原地替换的原件，异步同步链路就会周期性地给出已失效结果。
- **节点「要候选还是要答案」**：机制判据——返回候选需要可解释的排序依据（业务方自己看），返回答案需要端到端正确率与引用回链。两者验收口径不同，混在一套评估里会导致双方都测不准。

用法上要强调一点：这棵树**不是一张一次走到底的清单，而是四个各自要回答的问题**——可比性、版面与过滤、规模、可变性。现实中团队常被规模问题先吸引（「我们数据量大」），再回头发现前两层根本没答；而前三层任何一层答错，后面的规模规划都建立在错误前提上。判断顺序反了，规模选得再对也没用。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 商品图文 + 强条件筛选（品牌 / 类目 / 价格带） | 同表混合查询（pgvector / 多模态原生 DB） | 支持过滤下推的托管向量库 | 先筛后搜在筛出百万级候选时退化成全库近邻加交集 |
| 扫描件 / 财报 / 复杂版式检索 | ColPali 一类页面多向量 | 页面多向量 + 稀疏混合 | 纯 OCR 文本链路丢版面且不可逆；纯视觉漏精确字符 |
| 团队 5 人以内、模态还在增加 【经验】 | 多模态原生 DB | pgvector | 组合式方案要求有人长期维护关联键与对账指标，小团队最缺的正是这个人 |
| PB 级图文视频、以新增为主 | Lakehouse + 向量库 | 湖 + 托管向量库 | 全放库内会让库体积、备份与成本同时失控 |
| 实时推荐、毫秒级、条件必须参与 | 向量与热字段同库 | 多模态原生 DB | 湖 + 异步向量库在更新频率高时检索到已删条目 |
| 图文 / 视频问答 | 多模态 RAG | 检索服务 + 应用层自拼 LLM | 只返回候选列表满足不了「要答案」的业务；而各业务自拼 LLM 会导致引用与口径不一致 |
| 专名 / 编号检索与语义检索并存 | 稀疏 + 稠密混合检索 | 稠密检索 + 前置精确匹配 | 支撑向量库默认只有稠密一条通道 |
| 只有图文、条件筛选弱、千万级以内 | CLIP + Milvus 一类 | 多模态原生 DB | 统一空间 + ANN 已经够用，一体化的生态与深度要额外付学习成本 |
| 已有 PB 级数据湖，只想补一层检索 | 湖仓内向量化 + 检索服务 | 另起一套独立向量库 | 数据出湖的搬运与权限成本，往往高于检索本身带来的收益 |
| 模态之间不需要互相比较、只按业务键拼装 | 模态专属 + 元数据关联 | 统一向量空间 | 为跨模态能力付了精度代价，而业务并不做跨模态排序 |

**4 个常见组合**（原 § 7 的组合清单逐条保留，并给出职责边界）：

1. **多模态 DB + RAG**：多模态 DB 只负责召回（Recall@K 可单独评估），RAG 负责组装上下文与生成（端到端正确率单独评估）。运维代价是两套评估集，且端到端指标好看时**依然可能检索层已经坏掉**——必须分开看。适合规模：业务要的是答案而不是候选列表，且检索层能独立建评估集。
2. **多模态 DB + 向量湖**：向量湖承担「可重建的大体量语料」，在线库承担「毫秒级近邻」。职责边界是「湖是事实源、库是可弃缓存」。运维代价是同步链路与「差异条目数」指标常驻。适合规模：PB 级、以新增为主、同时要服务训练、分析与在线检索三条链路。
3. **多模态 DB + Agent**：DB 负责把多模态内容变成 Agent 可调用的工具返回，Agent 负责编排。职责边界是 DB 不做推理、Agent 不直接扫库。运维代价是工具返回必须带原件路径与权限，否则 Agent 会绕开治理。适合规模：查询形态多变、无法预先枚举成固定检索接口的场景。
4. **多模态 DB + 数据目录**：目录负责「有哪些多模态资产、归谁、含不含 PII、可否访问」，DB 负责「怎么检索」。运维代价是多模态资产的元数据必须进入目录的强制登记入口，否则「能搜到但不敢用」。适合规模：资产规模大到没人能凭记忆说清有哪些多模态资产的组织。

选择组合的判据只有一条：**每个组件都要有一个「别人替不了它」的职责**。如果一个组件被拆掉之后系统仍然完整，说明它是冗余的；如果有两个组件都对同一条一致性负责，说明一致性实际上无人负责。

还有一条容易被低估的性质：组合的运维代价随组件数**超线性**增长——两个组件只产生一组不一致，四个组件之间是六组潜在的不一致，且每一组都需要一条自己的对账指标。所以「先拆成小件、按需组合」这条建议成立的前提是：**每加一个组件，你都能说清它消掉的是哪一条不一致**；说不清时，它带来的对账成本会超过它分摊掉的那部分工作。

### 7.7 选错的代价与迁移成本

**选错的代价可以事先归账。** 四类反模式的损失落在不同的账上：反模式一落在**质量账**（静默退化，发现时已没有可回溯的基线）；反模式二落在**重建账**（换一次编码器就是一次按天计的全量重算，且这条路会被永久堵死）；反模式三落在**返工账**（误诊为召回不足，于是加 Top-K、加重排、换模型，问题依然在）；反模式四落在**成本账**（单次成本随喂进 LLM 的页面数增长、总成本随提问数增长，与语料规模无关，因而随使用量无上限上升，且涨在账单上、不涨在任何技术指标上）。前三者的共同点是**都不会在压测里暴露**——压测测的是延迟与成功率，而这三件事伤的是召回与可维护性；反模式四恰好相反，它一定会在压测里暴露，只是那时暴露出来的已经是账单，而不是一个可以回滚的配置。

**反模式一：用统一向量空间硬扛单模态主力业务。** 症状是跨模态能用、但主力模态召回不如原来的专用方案，而监控全绿（延迟、成功率、索引健康都正常）。后果是检索质量**静默**退化——质量从来没有基线可对比，几个月后业务反馈「搜不准」时已无从定位。正确做法是在上线前建一份固定查询集的 Recall@K 记录，按主力模态与跨模态分别设置基线。

**反模式二：把向量库当事实源。** 症状是只存向量与摘要、不存原件，或原件被替换后向量未同步。后果有两重：检索命中却取不到原件，复核无从进行；换编码器时向量不可重建，等于全库作废。正确做法是原件外置对象存储并保留校验和，把向量明确定义为可重建的派生物。

**反模式三：先检索后过滤。** 症状是条件一多就返回零结果，团队的第一反应是「调大 Top-K」。后果是把问题从「条件没下推」误诊为「召回不够」，Top-K 调到上千后延迟上升、结果依然为空。正确做法是先把条件下的推能力验证清楚，再决定技术栈。

**反模式四：用多模态 LLM 直接读全量页面。** 症状是系统跑得通、效果也不错，直到用量上来。后果是成本按「页面数 × 提问数」增长而不是按语料规模增长——它与你的数据量无关，与你的使用量有关，因此没有上限也没有预警。正确做法是先做一次 Embedding 检索把范围收敛到 Top-K，再让多模态 LLM 处理这一小部分，并为每类查询设成本上限。

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 分模态编码 → 统一向量空间 | 全量重算向量（前提是原件与编码器版本齐备）· **高** | 分数合并逻辑重写 · 中 | 索引重建 · 中 | 低 |
| 统一向量空间 → 分模态编码 | 新增专用编码器与索引，旧空间可保留过渡 · 中 | 跨模态查询需改造或下线 · **高** | 多一套索引链路 · 中 | 中 |
| 先筛后搜 → 同表混合查询 | 候选逻辑改造，数据基本不动 · 低 | SQL / 查询计划重写 · 中 | 索引类型与参数重调 · 中 | 中 |
| 湖 + 异步向量库 → 同表 / 同库 | 向量并入事实源，事务边界重划 · **高** | 同步链路下线、读写路径变长 · 中 | 少一套同步、多一套事务约束 · 中 | 中 |
| 单机向量索引 → 分布式 / 托管 | 重建索引并回填 · **高**（含重建召回基线） | 基本不变 · 低 | 运维面缩小或转移 · 低 | 低 |

（工作量量级为【经验】档：**高** = 需要专项项目与全量数据动作，**中** = 需要一到两个迭代，**低** = 配置级调整。）

看这张表要抓住一条：**迁移成本的大头几乎总落在「数据侧」与「评估侧」，不在软件侧**。换一个向量库，装一遍通常是一两天的事；重建索引、重算向量、重建召回基线却是以周计的动作 【经验】。这也解释了一个常见现象——团队评估了半年方案，最后卡住的往往不是「选哪个」，而是发现**没有召回基线可用来判断迁移是否成功**。所以更稳的顺序是：先补评估集 → 再动数据 → 最后换组件。顺序反过来，就会在换完之后无法回答「现在到底比之前好还是差」。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 跨模态是主需求 | 统一向量空间 | 同维同空间才有可比性，跨模态排序才成立 |
| 条件筛选强、模态各异 | 模态专属 + 元数据关联，或同表混合查询 | 条件与近邻分工明确；但关联键必须唯一，且要验证条件下推 |
| 团队小、模态还在增 | 多模态原生 DB | 过滤与近邻由同一执行器安排，少掉跨系统拼装与对账 |
| PB 级、以新增为主 | Lakehouse + 向量库 | 湖是唯一事实源，向量是可重建派生物，存储便宜 |
| 要答案不要候选 | 多模态 RAG | 成本与上下文规模成正比，而非与语料规模成正比 |
| 扫描件 / 复杂版式 | ColPali 一类页面多向量 | 检索直接在页面上做，版面信息不必经过不可逆的 OCR |
| 实时推荐、毫秒级 | 向量与热字段同库 | 少一跳；前提是元数据条件能参与检索而非事后裁剪 |
| 频繁更新、要求读到最新 | 条件与向量同表 / 同库 | 缩短同步链路，避免检索到已删条目 |
| 专名 / 编号与语义并存 | 稀疏 + 稠密混合 | 稠密空间把字符级区分抹平，符号匹配通道不可省 |
| 结果必须人工复核 | 结果附原件路径并按模态分组 | 复核要回到原件，缺路径等于把成本转给人 |
| 只有文本、查询以符号匹配为主 | 文本 + ES | 倒排索引对精确字符串最强；为语义另起一套存储要额外付运维 |
| 模态间不需要互相比较 | 模态专属 + 元数据关联 | 为跨模态付了精度代价，而业务并不做跨模态排序 |
| 已有事实源（湖 / 主库），只想补一层检索 | 湖仓内向量化 / 同库向量字段 | 事实源只有一个，向量是可重建的派生层 |
| 视频 / 点云等时序与结构敏感场景 | 模态专属存储 + 摘要入库（保时间与结构） | 帧序或结构一旦丢失不可恢复，跨模态可比换不回事件顺序 |
| 多租户 SaaS，租户间必须隔离 | 命名空间隔离 + 配额与计量 | 越界与成本归因靠应用层自觉挡不住 |

顺带说清一个常见的误选方向：把「多模态」当成选型目标，而不是当成约束。多模态是**数据的属性**，不是**架构的优点**——只有当某类查询必须把不同模态的候选放进同一个排序里时，可比性才值得付精度代价。反过来，如果业务只需要「按图查图、按文查文、再用业务键拼起来」，最合适的架构看起来一点也不多模态：它就是几个各自最优的单模态系统，加一个可靠的关联键。

一句话的选型顺序：**先确认可比性，再确认过滤能不能下推，最后才谈规模与成本**——把顺序倒过来，规模选得再对也只能建立在一个做不出跨模态、或者答不出结果的系统上。

> 本节小结：这些候选之间，**唯一真正起决定作用的那一条差异，是「可比性从哪来」**——各模态有没有被投进同一组维度与坐标系。这一条不成立，跨模态排序在物理上就做不出来，其余所有比较都失去意义。可比性成立之后，二次筛选由两件事决定：**过滤条件的选择性**（决定过滤与近邻谁先发生，也就是同表混合还是先筛后搜），以及**原件是否不可变**（决定能否用「湖 + 可重建向量库」这条便宜路线）。多模态 LLM 始终是这条链路的下游消费者，把它放到上游，成本与不可解释性会一起失控。
