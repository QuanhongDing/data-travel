## 6. 落地实践

### 2.1 Databricks"**把向量索引建在 Lakehouse 表上：数据不出仓做 RAG 4+ 年**"（2020 年起）

**背景（Why）**

Databricks 2020 年面临**"AI 与数据平台分裂"带来的重复搬运**：
- **湖仓里有权威数据**——**但向量化与检索通常发生在 Python 侧，需要先把数据导出**
- **导出的副本脱离治理**——**湖仓上的权限、血缘、审计在导出后全部失效**
- **向量索引与源数据不同步**——**源数据更新后，索引里的向量仍是旧版本，RAG 检索到过期内容**
- **两套系统两套成本**——**湖仓存一份、向量库再存一份向量，EB 级下成本可观**

**触发点（What）**

2020 年 Databricks 提出 **Lakehouse**；此后推出的 **Vector Search 把向量索引建到湖仓表上**（[Databricks 公开材料 2020-2024]），目标：
- **数据不出仓**——向量化与检索都在湖仓内完成
- **索引与源数据自动同步**——源表更新即索引更新
- **EB 级可扩展**

**详细做法（How）**

Databricks Vector Search 的**5 大核心组件**：

1. **向量索引作为湖仓表的"派生视图"（核心创新）**
   - 关键设计：**向量索引声明在湖仓表之上**，由平台负责同步；源表发生变更时，索引增量更新，而不是让使用方手动重建
   - 关键能力：**"索引与源数据不一致"从需要人工维护的问题，变成平台保证的属性**
   - 关键示意：
     ```python
     # 向量索引声明在 Delta 表之上（由平台负责同步，而非手动重建）
     from databricks.vector_search import VectorSearchIndex

     index = VectorSearchIndex(
         delta_table='rag.docs',          # 源表：权威数据留在湖仓
         embedding_model='bge-large-en',  # 平台负责向量化
         index_type='HNSW',
     )

     # 检索：向量附近 + 结构化条件同时生效
     results = index.similarity_search(
         query='什么是数据中台',
         k=5,
         filters={'dept': 'platform'},    # 结构化过滤参与检索
     )
     ────────────────────────────────────────────────
     对照"数据出仓"的做法：
       湖仓表 ─导出─▶ Python 作业 ─向量化─▶ 专用向量库 ─▶ 检索
       问题① 导出副本脱离湖仓权限与血缘
       问题② 源表更新后索引不同步，检索到过期内容
       问题③ EB 级数据多存一份向量副本
     -- 关键：把索引定义为"表的派生结构"，让同步成为平台责任
     ```

2. **平台内向量化（核心）**
   - 关键设计：**向量化由平台按模型配置完成**，使用方不维护向量化作业
   - 关键能力：**换模型 / 加字段时重建索引由平台调度**，使用方不必自建调度

3. **结构化过滤与向量检索同计划（核心）**
   - 关键设计：**检索接口支持结构化过滤条件**，与向量近邻在同一执行计划中组合
   - 关键能力：**"带业务条件的语义检索"成为默认能力**，而不是让使用方先检索再过滤

4. **自动分片与水平扩展（核心）**
   - 关键设计：**索引分片由平台按数据量与查询负载自动管理**
   - 关键能力：**从百万到十亿级不需要重建索引的工程投入**
   - 关键性质：**分片随数据量与查询负载自动调整——从 PB 级到 EB 级的规模跨度由平台承担，不落到使用方**

5. **与治理一体：权限、血缘、审计沿用湖仓（核心创新）**
   - 关键设计：**索引继承源表的权限模型**，谁能在源表上看到哪些行，检索结果就受同样约束；血缘中记录"索引派生自哪张表"
   - 关键能力：**AI 检索不会成为治理的盲区**——这是企业级 RAG 能否通过合规评审的关键

**Databricks Vector Search 关键数字**（[Databricks 公开材料 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **向量化位置** | 导出后外部作业 | 湖仓内平台完成 | **数据不出仓** |
| **索引与源表同步** | 人工重建，易过期 | 平台自动同步 | **不一致消除** |
| **向量副本** | 湖仓一份 + 向量库一份 | 湖仓内一份索引 | **冗余下降** |
| **权限 / 血缘** | 导出后失效 | 索引继承源表权限 | **治理不断链** |
| **结构化过滤** | 先检索后过滤 | 参与同一执行计划 | **召回质量提升** |
| **扩展方式** | 手动重建索引 | 平台自动分片 | **免工程投入** |
| **数据规模** | PB | PB~EB | **1000x** |
| **企业客户** | 0 | 10000+ | **∞** |

**具体数字（How much）**

- 团队规模：Databricks 团队 5000+ 人
- 关键数字：**服务 10000+ 企业客户**；**数据规模 PB → EB 级**；**数据不出仓**；**索引自动同步**；**索引继承源表权限**
- 业务影响：让湖仓上的权威数据直接支撑 RAG 与语义检索，服务全球 10000+ 企业客户

**失败教训**

- 早期「**AI 侧独立做向量化与索引**」——数据要导出、副本脱离治理、索引与源表不同步，倒逼**「索引作为湖仓表的派生结构，平台负责同步」**
- 「**手工重建索引**」——源表更新后忘记重建，RAG 检索到过期内容，倒逼**「源变更驱动索引增量更新」**
- 「**只做纯向量检索**」——业务条件无法参与，倒逼**「结构化过滤与向量检索同一执行计划」**
- 「**索引独立于湖仓权限体系**」——检索结果突破了源表权限，倒逼**「索引继承源表权限，血缘记录派生关系」**

### 2.2 字节"**Iceberg + Milvus：湖上传权威数据、Milvus 上做在线检索 4+ 年**"（2020-2024）

**背景（Why）**

字节 2020 年面临**"向量数据的离线治理"与"在线检索性能"难以兼顾**：
- **6 亿+ 用户的内容检索**——**在线检索要求毫秒~十毫秒级，索引必须在内存 / SSD 上**
- **向量来源于湖上数据**——**内容与用户行为数据在湖仓，向量由这些数据派生**
- **多业务（抖音 / TikTok / 西瓜 / 今日头条）**——**各业务各建向量服务，重复建设**
- **索引重建频繁**——**模型升级、数据更新都要重建索引，重建期间的可用性需要保障**

**触发点（What）**

2020 年字节推进**Iceberg + Milvus 的向量湖架构**（[字节技术博客 2020-2024]），目标：
- **湖上存权威数据与向量**——可治理、可回溯
- **Milvus 做在线检索**——保证毫秒级
- **多业务复用同一套服务**

**详细做法（How）**

字节向量湖的**5 大核心组件**：

1. **"湖上权威 + 检索服务副本"的双层职责划分（核心创新）**
   - 关键设计：**湖上保存向量及其来源数据（权威、可回溯、受治理）；专用向量引擎只承载"服务用的索引"**，索引可从湖上随时重建
   - 关键能力：**治理归治理、性能归性能**——湖保证"向量从哪来、能否复现"，向量引擎保证"检索够快"
   - 关键数字：**6 亿+ 用户、在线检索毫秒级、湖上可回溯**
   - 关键示意：
     ```text
     向量湖的分层职责（权威在湖上，性能在服务层）
       湖仓（Iceberg）
         · 内容 / 行为原始数据
         · 派生出的向量（版本、模型标识、生成时间）
         · 全量可回溯、可重算、受权限与血缘治理
                    │
                    │ ① 按需构建 / 重建索引（模型升级、数据更新）
                    ▼
       向量检索引擎（Milvus）—— 只承载"服务用的索引"
         · 内存 / SSD 上做毫秒级近邻检索
         · 索引可随时从湖上重建，不承担"唯一数据源"职责
                    │
                    ▼
       在线检索服务（多业务共用）
     ────────────────────────────────────────────────
     关键分工：湖负责"可治理、可复现"，引擎负责"够快"
       若让向量引擎承担权威存储 → 不可回溯、模型升级后无法重算
       若让湖直接承担在线检索 → 延迟达不到交互要求
     ```

2. **向量的可追溯元数据（核心）**
   - 关键设计：**每条向量记录携带来源、embedding 模型版本与生成时间**
   - 关键能力：**"这批向量是用哪个模型生成的"可查**——模型升级时能精确定位需要重算的范围

3. **索引重建与在线切换（核心）**
   - 关键设计：**新索引在后台构建，构建完成后灰度切换**，重建期间旧索引继续服务
   - 关键能力：**"重建索引"不再需要停机窗口**——这是模型能持续迭代的前提

4. **多业务共用检索服务（核心）**
   - 关键设计：**检索服务按命名空间隔离多业务数据**，共用同一套引擎与运维
   - 关键能力：**4 业务共用一套，避免每个业务各建向量服务**
   - 关键数字：**4 业务统一**

5. **向量质量与效果回归（核心创新）**
   - 关键设计：**维护检索评测集**，模型或索引变更后跑回归，命中质量不达标不允许切换
   - 关键能力：**"换了模型检索变差"这类问题在切换前被发现**，而不是上线后由业务反馈

**字节向量湖关键数字**（[字节技术博客 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **向量权威存储** | 向量引擎内（不可回溯） | 湖上（可重算可复现） | **可治理** |
| **在线检索延迟** | 湖上直查不可用 | 引擎索引，毫秒级 | **交互可用** |
| **索引重建** | 停机窗口 | 后台构建 + 灰度切换 | **不停服** |
| **向量来源追溯** | 无记录 | 模型版本 + 生成时间 | **100%** |
| **业务覆盖** | 各业务各建 | 4 业务共用 | **∞** |
| **模型升级** | 全量重算且不可定位 | 按模型版本精确定位重算范围 | **成本可控** |
| **切换前验证** | 无 | 评测集回归门禁 | **∞** |
| **用户规模** | 亿级 | 6 亿+ | **∞** |

**具体数字（How much）**

- 团队规模：字节搜索 / 向量检索团队 200+ 人
- 关键数字：**6 亿+ 用户**；**4 业务统一**；**湖上权威 + 引擎加速**；**重建不停服**
- 业务影响：支撑抖音 / TikTok / 西瓜 / 今日头条的搜索、推荐与内容检索

**失败教训**

- 早期「**把向量引擎作为唯一数据源**」——模型升级后无法重算，索引也难追溯来源，倒逼**「湖上存权威向量 + 引擎只做服务副本」**
- 「**重建索引要停机**」——每次模型迭代都要承受可用性风险，倒逼**「后台构建 + 灰度切换」**
- 「**向量不带模型版本信息**」——模型升级时无法定位需要重算的范围，只能全量重算，倒逼**「向量携带模型版本与生成时间」**
- 「**各业务各建向量服务**」——重复建设且质量参差，倒逼**「多业务共用命名空间隔离的检索服务」**

### 2.3 阿里"**把向量能力放进数据仓库：10 亿商品向量与仓内模型函数 5+ 年**"（2019-2024）

**背景（Why）**

阿里 2019 年面临**"AI 与数据仓库之间反复搬运"的成本与合规问题**：
- **10 亿+ 商品**——**商品与行为数据的权威源在数据仓库，向量却要在外部生成**
- **导出成本与合规风险**——**为了做向量化把数据导出，网络成本高且副本脱离治理**
- **知识时效性**——**商品上下架、价格变动频繁，向量库若与仓库脱节就会检索到过期商品**
- **多业务重复建设**——**客服、搜索、导购各搭一套向量链路**

**触发点（What）**

2019 年阿里推进**仓内向量化与检索能力（模型函数 + 向量索引）**（[阿里 PAI / MaxCompute 公开材料 2019-2024]），目标：
- **数据不出仓**——向量化在仓库内完成
- **时效对齐**——向量随数据更新而更新
- **多业务复用**

**详细做法（How）**

阿里仓内向量能力的**5 大核心组件**：

1. **模型函数：把向量化做成 SQL 的一部分（核心创新）**
   - 关键设计：**多模态模型以函数形式在仓库内可用**，一条 SQL 即可对整列商品标题 / 图片产出向量；新数据入库即可向量化
   - 关键能力：**向量化从"离线批量作业"变成"查询的一部分"**，数据与向量天然同源同时效
   - 关键数字：**数据不出仓、10 亿+ 商品向量**
   - 关键示意：
     ```sql
     -- ① 仓内向量化：一条 SQL 对整列产出向量，无需导出
     CREATE TABLE item_vec AS
     SELECT item_id,
            embedding(title)  AS title_vec,     -- 文本向量函数
            embedding(image)  AS image_vec,     -- 图像向量函数（多模态）
            category, brand, status
     FROM   item_detail
     WHERE  ds = '2024-01-01';

     -- ② 检索：结构化条件与向量相似度在同一执行计划内组合
     SELECT item_id
     FROM   item_vec
     WHERE  category = '手机' AND status = 'on_sale'   -- 业务条件先缩小范围
     ORDER BY title_vec <=> :qvec                       -- 再在子集内做近邻
     LIMIT  20;
     -- 关键：导出模式要把商品数据搬到外部向量库，
     --       仓内模式让"向量化 + 检索"都发生在数据所在地
     ```

2. **向量与业务状态同源读取（核心）**
   - 关键设计：**上下架、价格这类高频变更字段不预置进向量**，检索时从仓库表实时关联
   - 关键能力：**避免"检索到的商品已经下架"**——语义相似与业务状态各走其道

3. **向量索引与分区裁剪协同（核心）**
   - 关键设计：**按时间 / 类目分区组织数据**，检索时先做分区与条件裁剪，再在缩小子集上做近邻
   - 关键能力：**10 亿级规模下检索仍可控**——不裁剪就在全量上做近邻，代价无法接受
   - 关键数字：**10 亿+ 可检索**

4. **多业务复用与统一检索服务（核心）**
   - 关键设计：**检索能力封装为服务**，客服、搜索、导购接入同一套
   - 关键能力：**避免每个场景各自搭一套向量链路**

5. **权限与治理一体（核心创新）**
   - 关键设计：**向量的访问走仓库权限体系**，行 / 列级权限对检索同样生效
   - 关键能力：**多模态与向量数据不脱离治理**——企业级场景上线的前提

**阿里仓内向量能力关键数字**（[阿里 PAI / MaxCompute 公开材料 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **向量化位置** | 导出到外部生成 | 仓库内模型函数 | **数据不出仓** |
| **向量时效** | 与仓库脱节 | 随数据更新同步 | **对齐** |
| **商品规模** | — | 10 亿+ 商品向量 | **可检索** |
| **业务状态（上下架 / 价格）** | 曾进向量导致过期 | 检索时实时关联 | **准确** |
| **检索执行** | 全量近邻 | 分区 / 条件裁剪 + 子集近邻 | **可控** |
| **多模态** | 文本 | 文本 + 图像 | **多模态** |
| **业务复用** | 各场景各搭 | 检索服务化 | **∞** |
| **访问治理** | 链路外失效 | 走仓库权限 | **审计 100%** |

**具体数字（How much）**

- 团队规模：阿里 PAI / 数据中台团队 100+ 人
- 关键数字：**10 亿+ 商品向量**；**数据不出仓**；**仓内向量化**；**多业务复用**
- 业务影响：支撑阿里集团内商品语义检索、导购、客服问答等场景，并作为云能力对外输出

**失败教训**

- 早期「**把商品数据导出到外部生成向量**」——导出成本高、副本脱离治理、向量与仓库脱节，倒逼**「仓内向量化（模型函数），数据不出仓」**
- 「**把上下架状态也预置进向量**」——检索到已下架商品，倒逼**「高频变更字段检索时实时关联」**
- 「**在全量数据上直接做近邻**」——10 亿级规模下检索代价不可接受，倒逼**「分区与条件裁剪后，在子集内做近邻」**
- 「**每个业务各搭向量链路**」——重复建设且治理口径不一，倒逼**「检索服务化 + 权限走仓库体系」**

### 2.4 Pinecone"**SaaS 向量湖：让 1000+ 企业不必自建向量基础设施 4+ 年**"（2020-2024）

**背景（Why）**

Pinecone 2020 年面临**"向量检索的规模化运维门槛"被普遍低估**：
- **1000+ 企业客户的向量规模跨度极大**——**从几十万到十亿级，同一套方案要能覆盖**
- **自建索引的运维复杂度**——**分片、副本、索引重建、扩容都随规模非线性上升**
- **多租户与计费**——**SaaS 场景要按租户隔离与计量**
- **RAG 落地门槛**——**企业希望"接上就能用"，而不是先搭一套向量基础设施**

**触发点（What）**

2020 年起 Pinecone 推出**SaaS 向量湖**（[Pinecone 公开材料 2020-2024]），目标：
- **1000+ 企业开箱可用**
- **免运维扩缩**
- **与 RAG 生态直连**

**详细做法（How）**

Pinecone SaaS 向量湖的**5 大核心组件**：

1. **"数据在客户侧、索引在服务侧"的托管形态（核心创新）**
   - 关键设计：**客户通过 API 写入向量与元数据，服务侧负责索引、分片、副本、扩缩**；客户不需要在自有环境里跑一套向量基础设施
   - 关键能力：**把"向量基础设施"从自建工程变成一个外部依赖**——这是中小企业能用上语义检索的关键
   - 关键数字：**1000+ 企业、免运维扩缩**
   - 关键示意：
     ```text
     SaaS 向量湖的职责边界（客户侧 vs 服务侧）
       客户侧（数据与应用）
         · 原始数据与业务逻辑（客户自己持有）
         · 调用 SDK / API 写入向量与元数据
         · 检索：调 API 取回结果
     ────────────────────────────────────────────────
       服务侧（Pinecone 承担）
         · 索引构建与参数调优（随规模自动调整）
         · 分片 / 副本 / 再平衡
         · 在线扩缩（免停机）
         · 命名空间隔离与配额计量
         · 稀疏 + 稠密检索与元数据过滤
         · 索引质量指标
     -- 关键：把"运维复杂度高"的部分整体外包，
     --       客户只保留"数据"与"应用"这两件他最该做的事
     ```

2. **命名空间隔离与配额计量（核心）**
   - 关键设计：**按租户 / 业务划分命名空间**，存储与查询量按命名空间统计
   - 关键能力：**多租户 SaaS 的隔离与计费天然成立**，客户不必自行搭一套计量

3. **元数据过滤 + 稀疏 / 稠密混合（核心）**
   - 关键设计：**检索支持元数据过滤**；稀疏向量（关键词）与稠密向量（语义）可并存并用
   - 关键能力：**专有名词、型号、编号类查询由稀疏命中，语义泛化由稠密覆盖**，两者结合才接近可用

4. **在线扩缩与索引重建免停机（核心）**
   - 关键设计：**扩容与索引参数调整在后台完成**，读写路径不中断
   - 关键能力：**"业务增长 → 需要扩容 → 承担停机风险"这条链路被切断**

5. **与 RAG 生态直连（核心创新）**
   - 关键设计：**提供与主流 RAG 框架的集成**，检索层可直接接入编排流程
   - 关键能力：**企业做 RAG 时不必自建检索层**，把精力放在数据准备与提示词设计上

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **企业客户** | 0 | 1000+ | **∞** |
| **向量基础设施** | 客户自建自运维 | 服务侧托管 | **免自建** |
| **扩缩** | 重新索引，需停机窗口 | 后台完成，读写不停 | **免停机** |
| **隔离与计量** | 客户自行实现 | 命名空间 + 配额内置 | **∞** |
| **检索类型** | 仅稠密 | 稀疏 + 稠密并用 | **覆盖专有名词查询** |
| **元数据过滤** | 事后过滤 | 参与检索 | **召回质量提升** |

**具体数字（How much）**

- 团队规模：Pinecone 工程团队数百人
- 关键数字：**1000+ 企业**；**免停机扩缩**；**稀疏稠密并用**；**命名空间隔离与计量**
- 业务影响：让 1000+ 家企业以服务方式获得向量检索能力，无需自建向量基础设施

**失败教训**

- 早期「**让客户自建向量基础设施**」——分片、扩容、重建都需要专业投入，多数团队做不出可用的版本，倒逼**「托管形态：客户只持有数据与应用」**
- 「**扩容需要重新索引**」——每次增长都伴随停机风险，倒逼**「后台在线扩缩」**
- 「**只做稠密向量检索**」——型号、编号类查询效果差，倒逼**「稀疏 + 稠密并用」**
- 「**多租户隔离与计量让客户自行实现**」——重复建设且易出错，倒逼**「命名空间与配额内置」**

### 2.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**湖仓表 + 托管向量索引 + 元数据过滤**」（**最简单**）——**百万级向量、1 个场景**
- 产出：**索引声明在源表之上 + 结构化过滤参与检索 + 检索评测基线**
- 团队：**2-3 人**
- 验证标准：**索引与源表自动同步**、**过滤条件参与检索而非事后裁剪**、**评测集上有命中率基线**

**1 → 10 阶段：6-12 个月**

- 扩展到「**千万级 / 多业务**」
- 引入「**向量携带模型版本与生成时间**」——模型升级可精确定位重算范围
- 引入「**索引重建不停服（后台构建 + 灰度切换）**」+「**稀疏 + 稠密并用**」
- 团队：5-10 人
- 验证标准：**模型升级可定位重算范围**、**重建不停服**、**专有名词查询命中改善**

**10 → 100 阶段：12-24 个月**

- 扩展到「**亿级 / 多租户 / 在线扩缩**」
- 引入「**双层职责划分：权威在湖上、索引在服务层可随时重建**」
- 引入「**命名空间隔离 + 配额与计量**」+「**在线扩缩免停机**」
- 团队：10-30 人
- 验证标准：**索引可从湖上重建（湖为唯一权威）**、**扩缩免停机**、**租户越界 0**、**成本可归因**

**100 → 1000 阶段：12-24 个月**

- 引入「**原侧向量化（数据不出侧）+ 高频变更字段检索时实时关联**」
- 引入「**分区 / 条件裁剪 + 子集近邻**」+「**权限与血缘一体（索引继承源权限）**」
- 引入「**切换前评测集回归门禁**」
- 团队：30-100 人
- 验证标准：**导出流量 -90% 量级**、**上下架 / 价格等状态检索时准确**、**检索权限与源表一致**、**模型 / 索引切换必过评测集**

### 2.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**向量化位置**」 | 导出到外部 | 原侧（仓内 / 平台内） | **导出流量 -90% 量级** |
| 「**索引与源数据同步**」 | 人工重建，常过期 | 变更驱动自动更新 | **不一致消除** |
| 「**向量副本**」 | 湖仓 + 向量库两份 | 权威一份 + 可重建索引 | **冗余下降** |
| 「**索引重建**」 | 需停机窗口 | 后台 + 灰度切换 | **不停服** |
| 「**向量可追溯**」 | 无记录 | 模型版本 + 生成时间 | **100%** |
| 「**结构化过滤**」 | 事后裁剪 | 参与检索计划 | **召回质量提升** |
| 「**检索类型**」 | 仅稠密 | 稀疏 + 稠密并用 | **专有名词命中改善** |
| 「**权限 / 血缘**」 | 导出后失效 | 继承源表 | **治理不断链** |
| 「**业务接入**」 | 各业务各建 | 服务化复用 | **∞** |
| 「**企业客户 / 覆盖规模**」 | 0 | 1000+ ~ 10000+ 企业 | **∞** |

**关键投资回报**：
- **直接节省**：「**导出流量 -90% + 向量副本下降 + 运维外包**」——**向量湖最大的成本是"同一份数据为向量化再搬一遍、再存一遍"**；把向量化搬到数据所在地、把运维复杂度整体外包，省下的是 EB 级数据的搬运开销与向量基础设施的运维人力
- **业务价值**：「**索引自动同步 + 重建不停服 + 检索服务化**」——**AI 检索能否持续可用的关键不是首次搭起来，而是"数据变了、模型换了之后还能不能跟上"**：自动同步与不停服重建决定了 RAG 不会因为数据更新而悄悄退化
- **AI 时代关键**：「**原侧向量化 + 索引继承源权限 + 向量携带模型版本**」——**这三条决定了 AI 检索能否进入企业生产环境**：原侧向量化解决成本与合规；权限继承保证 AI 不会成为数据泄露的新通道；模型版本可追溯则让"检索质量退化"与"模型升级重算范围"都变成可定位、可回归的工程问题

---

> **本节小结**：
> - 4 个真实案例（Databricks / 字节 / 阿里 / Pinecone）印证：**向量湖不是「再建一个向量库」，是「索引作为源表派生结构 + 原侧向量化 + 权威与检索分层 + 稀疏稠密并用 + 权限血缘一体」5 件套**。
> - 关键时间线：Databricks 4+ 年 / 字节 4+ 年 / 阿里 5+ 年 / Pinecone 4+ 年 —— **向量湖是 4+ 年长期工程**，且**核心矛盾是"治理与性能如何分工"，而不是"用哪个向量库"**。
> - 选型第一原则：「**湖仓表 + 托管索引 + 元数据过滤**」（**最简单**）——**百万级** → 「**模型版本可追溯 + 重建不停服 + 稀疏稠密并用**」（**必须**）→ 「**权威在湖 / 索引在服务层 + 多租户隔离与计量**」（**生产**）→ 「**原侧向量化 + 权限血缘一体 + 切换评测门禁**」（**AI 时代**）。
> - 99% 的失败来自「**数据导出做向量 + 索引与源表脱节 + 高频字段预置进向量 + 只做稠密检索**」——必须有 **原侧向量化 + 变更驱动同步 + 检索时实时关联 + 稀疏稠密并用**。
> - 真正的 ROI 来自「**导出 -90% + 重建不停服 + 权限血缘不断链 + 治理可审计**」——是**AI 检索能否从演示环境进入企业生产的分水岭**。

> 💡 **思考锚点**：本节的阶段表把第一档卡在「**百万级向量、1 个场景**」，而「**原侧向量化（导出 -90% 量级）**」要到 100→1000 阶段才引入——你的向量规模现在落在哪一档？如果还在百万级，该做的是 2.5 给的三件事（索引声明在源表之上、过滤参与检索、有评测基线）；此刻就上「权威在湖 / 索引在服务层」的双层职责与多租户配额计量，付出的是双份存储加一条同步链路的运维成本，而收益要等你真跨到亿级、多租户才兑现。
