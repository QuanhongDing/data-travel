## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

这一节的关键词是"湖"和"标配"，而这两个词都太容易把不同量级的事情压扁。原文件把「Pinecone Serverless（2024）」「LanceDB + Iceberg（2024）」「Trino / Presto 向量 Connector」排成同一句式，但它们改的根本不是同一层东西：前者改的是**成本函数的形式**，第二个改的是**治理与事务的归属**，第三个改的是**过滤在查询计划里的执行位置**。把这三件事并列成"演进方向"，读者据此排路线图时，会以为它们可以同时做、或者可以互相替代。

第二个坑是**产品名与能力名混淆**。DiskANN 是 Microsoft 的一条研究路线与随之开源的实现（论文 NeurIPS 2019；开源实现的创建与 release 时间可由其公开仓库页核验，本节不写年份），**不是一个通用的索引类型名**；各家引擎把"面向磁盘的索引"做成自己的实现，命名与参数都不一样。判定方法：**去该引擎的 release note 里找"面向磁盘 / SSD 的索引类型"这一条目**，找到再谈支持，而不是看到一篇博客提到 DiskANN 就认为"它支持 DiskANN"。同理，RaBitQ 是一篇量化论文的名字，产品里是否用它，要看该产品的官方文档，不能由论文反推。

第三个坑是**把"向量湖"当成一个产品类别**。[§7 §7.2](02-vector-lake-section-7-sec7.md) 已经把这件事说清楚了：同一个产品常常横跨两族，分族看的是**部署形态**而不是品牌——Milvus 的 standalone 与 distributed 分属不同族，pgvector 在单机 PostgreSQL 上是"索引与查询同机"，换成存算分离的云数据库后就已经部分落在"存储与计算分离"这一族。所以本节的判据统一是：**这套部署里，索引状态放在哪种介质上、由谁持有**，与产品选型无关。

第四个坑是**把"存得下"当成"查得动"**。向量湖解决的第一个问题是容量单价，而容量单价与查询延迟是两笔账：把向量从内存挪到对象存储，账单立刻好看，延迟分布却被推向对象存储的首字节延迟。本节给每个方向都标出"它换的是什么介质、付出的是什么尾延迟"，这是趋势清单里完全没有的一栏。

> 本主题下唯一处在 L1 的方向是表里的第一行：**索引状态从计算节点下移到 SSD 或对象存储**。这个 L1 是发给**机制**的，不是发给"向量湖"这个概念或任何一个产品的——它成立的条件是"图结构驻内存、向量本体驻磁盘"这一拆分真的发生了，而不是"数据量很大所以应该用向量湖"。把 L1 发给概念，是本节最常见的误判。

**这张表里 L2 最多，原因不是保守，而是这门主题的成熟形态就是"能力已交付、边界未定型"**。介质下移之所以能判 L1，靠的是"决定搜索路径的结构留在哪台机器上"这件事在实现之间高度一致——换一个引擎，你仍然能问出"图在哪、向量在哪、每次搜索读几次盘"，答案可比较。Serverless、Lakehouse + Vector、多模态、AI 运维都不满足这一条：它们的差异不在机制，而在**计费口径、格式规范与编码器**这些会随厂商推动而变的地方。对架构师的实际含义是：L2 的能力可以用，但**不要让它出现在不可替换的一侧**——把它放在"可以从湖全量重建"的缓存层、分析入口或派生视图之上，而不是放在"丢了就没法重建"的那一侧。

反过来，L2 也不是永久等下去的档位。给每个 L2 方向预先写好"升 L1 的条件"，比年底重新评审一次更有效：Serverless 的升级条件是**cache miss 的计费与延迟口径被公开**；Lakehouse + Vector 的升级条件是**索引随快照版本化**；多模态的升级条件是**跨编码器的分数可校准**；AI 运维的升级条件是**产品的自动动作有明确回滚路径**。这四条都是可观察的，不是感觉。

读这张表时有三个动作，顺序不能换：

1. **先定位介质**——你现在的索引状态在内存、SSD 还是对象存储？这一步决定了你在哪一族，而不是哪个产品更适合你。
2. **再算容量账与 IOPS 账**——容量账决定"装不装得下"，IOPS 账决定"查不查得动"；只算前者是 SSD 路线最常见的翻车点（§5.2.1）。
3. **最后才看功能清单**——过滤、更新、多模态这些都是在介质确定之后才需要精算的第二层问题（[§7 §7.5](02-vector-lake-section-7-sec7.md) 给出了阈值与推导）。

每次版本升级后回填一次级别：某个 L3 方向若出现第三方评测或标准草案就升 L2；某个 L2 方向若一年内仍拿不到实测数字，就降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向在评审时应被直接打回：本主题里每一次规模提升，都是拿延迟分布或召回率换来的。

读这张结构时有两个约定。**第一个，"机制"必须落到介质或执行位置上**——是"图与向量分居两种介质"，是"成本从按节点变成按请求"，还是"过滤从应用层移进索引扫描"。落不到这几件事上的，都只是评价。**第二个，"代价"必须是一个可以被观测的量**——尾延迟、IOPS、账单的不确定性、重建窗口。写成"需要投入学习"的，不算代价。

#### 5.2.1 索引状态从计算节点下移：本主题唯一的 L1

- **旧做法与它的卡点**：主文件 §1.2 的第一号痛点「向量库成本失控」说的就是这件事——向量全内存驻留，成本随向量数线性上升，规模一上来就"要么降精度、要么缩副本、要么砍数据"。卡点不在算法，而在**介质单价**：同一份 10 亿条 768 维 FP32 向量约 2.8 TiB【推算】（= 2,861 GiB；按 10⁹ × 768 × 4 B ≈ 3.07 × 10¹² B 计算，推导见 [§7 §7.5](02-vector-lake-section-7-sec7.md)），把它放进内存与放进对象存储，单价差约两个数量级（同节的介质单价梯子【推算】）。
- **AI 改变了什么机制**：**把"图结构"与"向量本体"拆到两种介质上**——内存只放邻居 ID（每节点几十到几百字节），向量本体落 SSD 或对象存储、按需懒加载。注意这**不是压缩**：压缩减少的是每向量的字节数，拆分改变的是每个字节住在哪种介质上；两者可以叠加，但解决的是不同的问题。
- **由此得到的**：**因为决定搜索路径的图结构驻在内存，所以单节点容量改由磁盘或对象存储决定，规模上限比"全内存"高出一个量级或更多**；**因为向量本体只在访问到某个节点时才读，所以随机读的次数与搜索跳数同阶，而不是与数据量同阶**——这正是十亿级能在单节点上成立的原因（机制来源见 [§5.4](#54-公开进展与文献) 的 DiskANN 与 SPANN 两条论文线）。

```text
"把向量放到 SSD 就够了"只算了一半的账
  容量账：10 亿 × 768 维 × 4 B ≈ 2.8 TiB 原始向量（推导见 §7 §7.5）
   IOPS 账：峰值 QPS × 每次搜索的随机读次数 ≤ 卷的 IOPS 上限
     · 前者来自业务（峰值查询量）
     · 后者来自引擎文档里的搜索流程描述（每一跳到底读几次）
     · 相除 = 需要的卷数与条带方式
  ────────────────────────────────────────────────
  关键：云上块存储的 IOPS 是按卷上限供给的，不随容量线性增长；
        容量账算完就认为"够用"，是 SSD 路线最常见的翻车点
```

三种驻留层级对应的可行规模，可以直接对照自己的现状（【推算】，前提是 768 维 FP32；推导链见 [§7 §7.5](02-vector-lake-section-7-sec7.md)，换成 1536 / 3072 维时按比例前移）：

| 驻留层级 | 代表机制 | 可行规模量级【推算】 |
| --- | --- | --- |
| 内存（全精度，或量化后的副本） | 单机图索引 | 百万 – 千万（量化把拐点右移：INT8 约 4×、PQ 约 8×【推算】，见 [§7 §7.5](02-vector-lake-section-7-sec7.md) 的"维度的杠杆"表） |
| 本地 SSD + 内存中的图结构 | 面向磁盘的图索引 | 十亿 |
| 对象存储 + 本地缓存与预热 | 存算分离的检索 | 十亿以上，成本按存储计，延迟由缓存命中率决定 |

需要强调的是，**量化与介质下移是两条正交的路**：量化在同一层级内压缩每向量的字节数，介质下移改变每字节住在哪。只做前者，你仍在内存里；只做后者，你仍在读全精度向量。两者叠加才是常规做法，但它们的收益各自都要用召回损失与 IOPS 预算来支付。

- **由此付出的**：**其一，瓶颈迁移而不是消失**——从"内存容量"变成"IOPS"，而 IOPS 是另一个需要单独规划的资源，且实例本地 NVMe 与网络块存储的能力差别很大，选错会让"存算分离"的弹性优势落空；**其二，尾延迟变差**——随机读的延迟比内存访问高两到三个数量级【经验】，P99 由"未命中率的倒数 × 单次随机 IO"主导，这不是调参能解决的；**其三，量化必须配精排**——为了进一步压缩而引入的量化会带来召回损失（[§7 §7.3.1](02-vector-lake-section-7-sec7.md) 给出量级，[§7 §7.7](02-vector-lake-section-7-sec7.md) 说明它会累积），要用更大的候选数与精排补回来，等于把省下的存储换成算力。
- **证据与来源**：【公开】DiskANN（NeurIPS 2019，目标为单节点十亿点）与 SPANN（NeurIPS 2021，SSD + 内存两级结构）给出了"图驻内存、向量落盘"这一分界的原始出处；RaBitQ（SIGMOD 2024）在量化误差界上给出新的理论上界；Milvus 2.x 把日志、对象存储与查询 / 索引节点拆成独立角色（官方文档，2022 起）是同一方向的产品化。**判定方法**：查该引擎 release note 里有没有"面向磁盘 / SSD 的索引类型"作为正式条目，以及它的参数是否包含内存与磁盘的分工——有，才是这条 L1 机制，否则只是"向量能落盘存着"。
- **失败条件**：当工作集能装进内存时，这条机制不带来任何容量收益却引入随机读延迟；当云上块存储的 IOPS 上限成为约束（单卷封顶）时，面向磁盘的索引会把吞吐锁死在 IOPS 上，此时必须改用实例本地 NVMe 或多卷条带——而后者又破坏了原本想要的"随时迁移"。**判定方法**：先用一个不装进内存的数据集跑一次，看 P99 是随未命中率上升而平稳劣化，还是出现台阶式跳变。
- **成熟度**：**L1**。判据：①正式 release note——多家独立引擎把"面向磁盘 / SSD 的索引类型"列为 GA 条目；②第三方（非发起方）生产案例——§5.4 所引 [§6](02-vector-lake-section-6-sec6.md) 的公司案例里，检索层索引落在内存 / SSD 上是有年份可查的；③索引类型与查询接口多年稳定。**降级条件**（说的是**级别**会不会掉，与上面那条"失败条件"是两件事）：判据②一旦不成立——某引擎把"面向磁盘的索引类型"从 GA 条目退回实验性 / 预览，或第三方生产案例被证伪——本方向即降回 L2，"图在内存 + 向量在磁盘"从路线图假设降为待核选项。

#### 5.2.2 Serverless 向量库：换的是成本函数的形式，不是价格

- **旧做法与它的卡点**：自建集群的成本由常驻节点决定——扩容要搬数据、缩容要还资源，而业务请求常常是尖峰型或长尾低频的（内部工具、每隔一段时间跑一次的分析）。卡点在于**固定成本摊不下去**：低 QPS 下每台机器都很闲，账单却照付（主文件 §1.2 的第一号痛点）。
- **AI 改变了什么机制**：**成本函数的形式变了**——从"按节点（固定成本）"变成"按存储 + 按请求（线性成本）"，同时扩缩容从"你的运维动作"变成"服务端的行为"。注意：没有一个字节的存储被省下来，改变的是**计费边界与控制权的归属**。
- **由此得到的**：**因为闲置不占用计算资源，所以尖峰型与低频负载的单位成本下降**；**因为状态的真源被放到对象存储、计算节点只是无状态缓存，所以扩缩容几乎是瞬时的**——代价被搬到了查询路径上，即每次冷启动或缓存未命中都要从对象存储拉数据。
- **由此付出的**：**其一，低频场景单位成本反而最高**——每次查询都近似一次冷启动，缓存命中率被请求间隔稀释，而"按量计费"会把这份代价一分不少地记在账上；**其二，成本不可预测**——它是"存储 × 单价 + 请求数 × 单价 + 索引拉取"的线性叠加，没有"最后一台机器被摊薄"的固定项，流量翻倍账单就翻倍；**其三，迁出成本高**——索引格式在各引擎之间不通用，换供应商的动作是"全量重灌并重建索引"，不是"拷文件"（[§7 §7.7](02-vector-lake-section-7-sec7.md)）。
- **证据与来源**：【公开】Pinecone 在 2024 年公布的 Serverless 架构明确采用存储与计算分离、索引与数据落在对象存储上，可作为机制核验入口；各家定价页可核验其计费维度（存储、请求、索引拉取分别怎么计）。**本节不给任何"单位请求成本降低多少"的数字**：它取决于请求形态、索引大小与缓存命中率，跨用户不可比。**判定方法**：先算交叉点——自建月度固定成本 C 除以 Serverless 单位查询成本 u，得到月查询量 Q*；算 u 时**必须把 cache miss 时的索引拉取算进去**，否则会把 Serverless 算便宜。

把两种成本函数写成并排的形式，它们随规模增长的方式就一目了然：

| 成本项 | 自建集群 | Serverless |
| --- | --- | --- |
| 随数据量增长 | 常驻内存与磁盘（阶梯式：装不下就换架构） | 存储（线性、单价低） |
| 随请求量增长 | 几乎不变（固定成本被摊薄） | 线性（请求单元 + 索引拉取） |
| 闲置时的成本 | 全额照付 | 接近零 |
| 可预测性 | 高（按节点报价） | 低（随请求形态波动） |

**读这张表只需要一句话：自建的成本由"你有多少数据"驱动，Serverless 的成本由"你被查了多少次"驱动。** 用数据量去判断该不该选 Serverless，方向就是错的。

- **成熟度**：**L2**。判据：产品已 GA 且有正式文档；但计费口径仍在演进、冷启动的延迟与费用口径不透明、缺第三方公开的跨产品对比。**升级条件**：产品公开 cache miss 的计费与延迟口径，且有第三方在同一负载下给出可复现的对比。

#### 5.2.3 Lakehouse + Vector：列进了表，索引还在表外

- **旧做法与它的卡点**：向量与结构化数据分家——向量在一个系统里、业务表在湖仓里，两者要 JOIN 就得把数据搬来搬去，而权限、血缘、生命周期这三件事要在两处各维护一遍（主文件 §1.2 的"数据孤岛"与"无统一元数据"两条痛点）。
- **AI 改变了什么机制**：**把向量变成湖表的一列**，于是变化的是**治理与事务的归属**——权限、时间旅行、快照、血缘落在表格式上，可以由已有机制统一提供。但要说清这里的关键区别：**变的是"列"，不是"索引"**。索引仍然由检索引擎自持，它是表外的旁挂件。
- **由此得到的**：**因为向量与结构化数据同源同权，所以权限与时间旅行可以直接复用表格式已有的机制，不必在应用层维护两套权限**；**因为检索成为湖仓查询的一部分，所以分析型负载（BI 探索、批处理做相似性聚合）不必把数据搬出湖**。这也解释了为什么它对应的原趋势是"向量作为湖仓一等公民"——一等公民说的是**数据治理**，不是检索性能。
- **由此付出的**：**其一，索引不随快照走**——时间旅行能回到旧数据，却回不到旧索引，索引的重建不受快照提交的保护（**判定方法**：查表格式规范里有没有向量索引条目、索引是否随快照版本化；两者都否，就说明索引是旁挂件）；**其二，可见性由提交节奏决定**——量级在分钟到天级【经验】，写在湖里、在检索侧立刻可查这件事不成立，把它用在实时 RAG 上，用户会稳定看到"刚上传的文档搜不到"（[§7 §7.3.3](02-vector-lake-section-7-sec7.md)）；**其三，在线交互式场景的延迟由对象存储首字节延迟支配**，除非常驻缓存——而常驻缓存会把"存算分离省下的钱"再花回去一部分。
- **证据与来源**：【公开】LanceDB 以 Lance 列式格式承载向量与标量并在对象存储上做版本化（2023 起）；Milvus 2.x 的角色拆分（2022 起）说明同一方向；Apache Iceberg / Delta 的**格式规范本身**就是判定"索引是否进入表格式"的入口——规范里没有索引条目，就说明索引由引擎自持。**本节不引用任何"湖上检索多少毫秒返回"的声称**：这类数字缺少数模、维度、召回目标与缓存状态这些条件。

"索引与表格式的关系"只有三种可能，判定入口都在格式规范里，不在产品首页：

| 关系 | 含义 | 判定方法 | 对你的影响 |
| --- | --- | --- | --- |
| 列进了表 | 向量作为普通列被快照与权限覆盖 | 格式规范里的列类型章节 | 可以直接用时间旅行与列级权限 |
| 索引是旁挂件 | 索引由检索引擎自持，不随快照走 | 规范里有无索引相关条目 | 重建不受快照保护，需自建重建脚本与时间上限 |
| 索引是表的一部分 | 索引随快照版本化、随提交原子切换 | 规范里索引条目的提交语义 | 目前只在少数格式与引擎的组合里出现，须逐对核验 |

- **失败条件**：当检索是分析型负载（BI 探索、批处理做相似性聚合）时，"可见性由快照提交节奏决定"就不是缺点，而"索引不随快照走"也影响有限；反过来，当检索是用户在页面上等待的在线请求时，这条路线基本不成立。**判定方法**：看发起检索的是谁——人通过 BI 工具探索，还是用户在等页面。
- **成熟度**：**L2**。判据：产品已 GA、可用于中小规模试点；但索引与表格式的耦合方式各产品不同、且没有第三方公开的上量评测；"一等公民"目前是治理层面的定位，不是格式层面的事实。

#### 5.2.4 融合查询、多模态与 AI 运维：三件要逐件问「改了哪一层」的事

- **旧做法与它的卡点**：这三个原方向要解的题分别是——查询要跨"向量 + 结构化 + 图"三套系统（原方向 3）；一份资产要按图像 / 音频 / 视频分别编码、分别存（原方向 4）；索引参数、召回下降与成本异常要靠资深工程师逐项排查（原方向 5）。它们的共同卡点是同一个：**同一件资产、同一个问题，被拆在了多处，而每一处都要单独维护一套判断**。
- **AI 改变了什么机制**：**三件事改的层完全不同**——融合查询改的是**执行位置**（过滤从应用层拼装移进索引扫描之内）；多模态"原生支持"改的是**编码侧**（存储层没有变化，向量就是等长的浮点数组）；AI 运维改的是**接口**（把规则与统计的结论换成自然语言解释）。**把这三件并列成"一体化"会掩盖一个事实：只有第一件是存储与查询层的机制变化，后两件不会改变你的架构。**

| 原方向 | 改变了哪一层 | 由此得到的 | 由此付出的 |
| --- | --- | --- | --- |
| 向量 + 结构化 + KG（向量 + SQL + Cypher；Trino / Presto Connector） | 执行位置：过滤下推到索引扫描之内 | 高选择性过滤下召回不再静默崩塌 | 连接器生态未稳；跨引擎的代价模型不共享，无法联合优化 |
| 多模态 Embedding 原生支持 | 编码侧：一套存储承载多种模态的向量 | 一种向量存储服务多个模态的检索 | 模态对齐错了不报错，只让分数不可比；多套编码器 = 多套版本管理 |
| AI 增强运维 | 接口：从指标面板换成自然语言解释 | 诊断知识的传递成本下降 | 决策仍由规则与统计做出；自动执行动作的风险与收益不对称 |

- **由此得到的**：**因为过滤下推到索引扫描之内，所以"先多取再筛"那条会静默崩塌的路径被消除**（原方向 3 里真正有价值的那一半）；**因为多模态的差异只在编码器里，所以"向量湖支持多模态"这句话的实际含义是"它能存任意维度的向量"**——这不是新能力，而是原来就成立的事被重新表述了一遍。
- **由此付出的**：**其一，连接器是新的故障点**——跨引擎查询多了一次序列化与网络跳转，且这条链路上没有共享的代价模型，优化只能各自为政；**其二，模态对齐没有校验**——不同编码器产生的向量在同一个索引里混合时，距离分数不可比，而查询不会报错，只会"不那么准"，这类失败只能靠元数据记录模型版本来发现；**其三，"AI 运维"的边界在它给的是建议还是动作**——给自动执行权限意味着把一次错误建议变成一个生产事故。
- **证据与来源**：【公开】Vespa 官方文档长期把"向量 + 标量过滤 + 文本相关性"描述为同一排序框架内的计算，是"过滤进入检索"这条机制的产品化证据；Trino / Presto 的向量连接器属较新的集成，须逐插件核验其是否把过滤下推（**判定方法**：构造命中率 0.1% 的查询，比较"先过滤后检索"与"先检索后过滤"两种实现的召回差）；索引参数的自动选择早于 LLM 存在，LLM 部分的证据只有产品文档条目，无第三方基准。
- **失败条件**：当查询里根本没有需要顺着关系走的检索、也没有跨引擎的过滤需求时，这三个方向的收益都趋近于零——此时它们只是采购清单上的三行。**判定方法**：统计生产查询里真正跨引擎的融合查询占比，以及真正需要模态互搜的请求占比；两个数都接近零，就说明这一节的三件事与你无关。
- **成熟度**：**L2（结构化融合、多模态编码）/ L3（跨模态 SQL 与图侧一体化、运维动作自动执行）**。判据：能查能用已可用；跨引擎统一优化与自动执行尚无公开证据。**一个通用判据**：问"这个能力失效时，我的系统是变慢还是变错"——变慢是接口问题，可以试；变错是架构问题，必须先把校验补上。

### 5.3 与本主题既有栈的接口在哪

向量湖与上下游不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。原 §5.2 的四条组合在下面按接口写清。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 向量化 ETL（Spark / Flink / Ray）→ 向量湖 | 交接物 = 分区级列式文件 + **嵌入模型版本** | ETL 侧；模型版本一变，整列向量必须重算 | 既有技术（L1） |
| 向量湖 → 检索服务（Milvus / Pinecone 等） | **湖是源、检索是缓存**；交接物 = 向量 + 主键 + 元数据列 | 检索侧；必须能从湖全量重建，重建脚本与时间上限写进运维手册 | 既有技术（L1） |
| 向量湖 ↔ 湖仓表格式（Iceberg / Delta / Hudi） | 向量是表的一列，索引是表外的旁挂件；快照版本化只覆盖数据 | 表格式管数据，索引重建方管索引 | 需逐格式核验（L2） |
| 向量湖 ↔ 数据目录（Ch4-08） | 资产登记补三项：模型版本、维度、量化方式 | 目录侧：缺项则拒绝发布 | 需新增元数据字段（L2） |
| 向量湖 → RAG（Ch4-05）/ Agent（Ch5） | 交接物 = Top-K + 元数据 + 分数；**分数必须带口径** | 检索侧；返回空优于返回不可比的分数 | 既有技术（L1） |
| 向量湖 ↔ 权限与治理（Ch11-02、Ch11-07） | 向量是"聚合泄露"的载体：字段级权限在向量上没有对应物，必须在返回路径做行级过滤 | 治理侧；过滤漏一次就是越权检索 | 需在返回路径重建（L2） |
| 向量湖 ↔ 统一查询网关（Ch4-09） | 向量检索作为一类算子下推；过滤与排序的分工要写清 | 网关侧 | 可试点（L2） |
| 向量湖 ↔ GraphRAG | 湖存 Embedding、KG 存关系，两者的 join 在应用层 | 应用层；两边没有自动一致性保证 | 概念与自建阶段（L3） |
| 向量湖 ↔ 湖仓元数据（Apache Gravitino 一类） | 元数据侧登记向量资产 | 项目侧；判定入口是该项目的成熟度状态页 | L3 |

```text
一条链路上的三种失败，各归各的负责人
  权威数据（湖表快照） ──ETL / 重建──► 向量索引（检索缓存） ──查询──► RAG / Agent
       │                                   │                        │
   快照提交失败                        索引构建失败              分数不可比
   → 数据没更新，旧快照仍可读      → 缓存过期或缺失，             → 结果"不那么准"，
                                      必须能从湖全量重建           不报错，只能靠元数据发现
  ────────────────────────────────────────────────
  关键：检索缓存的"可重建性"是这条链路的硬要求——
        没有重建脚本与时间上限，向量库就变成不可替代的有状态黑盒
```

一句话概括：**AI 没有在这张图上新增调用关系，只改了两件交接物的形态**——嵌入模型版本（进入元数据）和分数口径（进入检索结果）。这两样东西决定了向量湖里的一次检索能不能被审计、能不能在换模型后复现。

围绕这张图有三条接口纪律，评审时可以逐条念：

1. **谁产生分数，谁负责标注口径**——分数必须带上"由哪个模型、哪种距离度量、哪种量化方式产生"，否则两个批次的结果不可比，而不可比不会报错。
2. **谁的依赖更长，谁担风险**——湖表格式的演进速度远慢于向量引擎，把检索缓存做成"可以从湖重建"的一侧，就永远不会被引擎的版本节奏绑架。
3. **能在同一介质内完成的，不要跨系统完成**——每跨一次系统就多一个失败模式，而这类失败的模式是"不报错、只是不太准"。

### 5.4 公开进展与文献

分三类列，**宁少勿假**。**论文**与**第三方生产案例**两类只列能给出会议名 / 文档名 + 年份的条目；中间的**判定入口**一类是例外：它给的是"用哪份文档的哪一节自行核验"，这类文档持续更新，写死年份会过期，所以只给文档名与核验位置——**这是本节显式声明的例外，不是省略**。

判定入口的"时间切片"由版本号而不是年份决定：核验时以**你所用的那个版本**的 release note 为准，而不是以站点上的当前版本为准。

- Chen et al., "SPANN: Highly-efficient Billion-scale Approximate Nearest Neighborhood Search", NeurIPS 2021——另一条"SSD + 内存两级结构"的路线，说明"下移介质"有多种实现，不是单一产品的专利。
- Malkov & Yashunin, "Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs", arXiv 2016 / IEEE TPAMI 2020——HNSW 的原始工作，理解"图结构为什么必须驻留在低延迟介质上"的起点。
- Gao & Long, "RaBitQ: Quantizing High-Dimensional Vectors with a Theoretical Error Bound for Approximate Nearest Neighbor Search", SIGMOD 2024——量化误差界；本主题里"从论文到产品"的典型传导案例，**产品是否采用须查该产品的官方文档**。

**官方文档 / release note（判定入口）**

- Milvus 官方文档与其 release note / CHANGELOG——核验角色拆分（日志 / 对象存储 / 查询与索引节点）与"面向磁盘的索引"是否为正式索引类型；**具体版本与特性条目以对应 release note 为准**。
- Vespa 官方文档中的向量检索与排序（rank profile）章节——核验"向量 + 标量过滤 + 文本相关性在同一排序框架内"这一条。
- LanceDB / Lance 格式文档（格式规范与版本化两节）——核验列式格式如何承载向量与标量、以及在对象存储上的版本化行为。
- Pinecone 关于 Serverless 架构的公开材料（2024）——核验"存储与计算分离、索引落对象存储"。
- Apache 项目状态页（projects.apache.org 的项目状态）与 Gravitino 自身的 release 节奏——判定这类湖仓元数据项目能不能当依赖；孵化 / 毕业状态以状态页为准。

### 5.5 被过度宣传的部分

**「向量湖原生支持多模态」**——实际是什么：向量就是等长的浮点数组，任何引擎都能存，模态的差异全在编码器里，而编码器住在引擎外面。为什么：引擎的索引与存储路径里没有模态分支，模态信息只存在于元数据与编码器的输出维度里。**什么时候才会成真**：引擎的过滤路径能理解模态语义（例如按模态分区裁剪、不同编码器的分数可校准），而不只是"能存 1536 维，也能存 1024 维"。

**「十亿级向量，召回率 99%、成本可控」/「Serverless 按量付费所以更便宜」**——这两句是同一类毛病的两个版本：把"成本"当成一个可以脱离条件讨论的量。实际是什么：召回率是"索引参数 + 数据集 + 候选数"三者的函数，脱离这三者给一个百分比没有信息量；而两条路线上的"便宜"各有一个陷阱——自建侧，要 99% 召回就得加候选数与精排算力，要成本可控就得量化、就得接受召回损失；Serverless 侧，交叉点在**访问频次**上而不在数据量上，低频请求几乎每次都接近冷启动，等于每次都付索引拉取的钱，而自建集群的固定成本在低频下摊不下去——两个方向的代价同时存在，谁的绝对成本低完全取决于 QPS。为什么：本主题的所有优化都是在同一组约束下做取舍（[§7 §7.3.1](02-vector-lake-section-7-sec7.md)：这是一次瓶颈迁移，不是一次免费优化），不存在同时改善召回、延迟与成本的免费午餐；Serverless 的单位成本 u 里含 cache miss 的拉取，而大多数团队算这笔账时会把它漏掉（§5.2.2 的判定方法）。**什么时候才会成真**：出现第三方公开的运行报告，**同时**给出规模、维度、召回目标、延迟分位与硬件条件，且产品公开 cache miss 的计费与延迟口径——缺任何一项都不可比。

**「向量 + 结构化 + KG，一条 SQL 查完」**——实际是什么：向量与标量的融合在部分引擎里确实成立（[§5.2.4](#524-融合查询多模态与-ai-运维三件要逐件问改了哪一层的事) 的 Vespa 形态），但**图侧仍要靠应用层 join**——图查询与向量检索的代价模型不共享，跨引擎的统一优化没有公开证据。为什么：把两种索引放进同一个查询语言容易，让优化器同时理解两者的代价很难，而这正是"一体化"的价值所在。**什么时候才会成真**：出现第三方公开的、把跨引擎融合查询放进关键路径并上量的架构，且能给出与"分路查询 + 应用层合并"的对照数据。

三条合起来看，被过度宣传的部分有同一个形状：**它们都把"概念包了一层"讲成了"技术前进了一步"**。多模态是编码侧的事，被说成引擎能力；99% 召回与成本可控是三个互相拉扯的指标，被合成一句口号（Serverless 的"更便宜"是同一件事的计费版本）；跨模态 SQL 是查询语言层面的整合，被说成执行层面的统一。识别方法因此很简单——**把宣传句里的名词换成"介质"或"编码器"，看它还成不成立**：只有在换过之后仍然成立的说法，才是关于架构的。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| "向量湖"作为一个独立概念会淡出，被吸收成"索引驻留层级"这一常规架构选择 | 讨论从"要不要建向量湖"变成"索引放哪一层"；湖表格式与检索引擎的边界成为标准议题 | 三年后厂商仍在用"向量湖"做独立产品叙事，且客户按概念采购而不是按介质算账 |
| Serverless 会在低频长尾场景胜出，在高频稳态场景输给自建 | 第三方成本对比开始按"请求数 × 单价 vs 常驻节点成本"给出交叉点；产品公开 cache miss 的计费口径 | 出现"同一成本下 Serverless 在高 QPS 稳态也全面优于自建"的公开可复现对比 |
| 索引与湖表格式的耦合会加深，但不会在主流格式里成为一等公民 | 出现由表格式侧定义的索引描述（哪怕只覆盖部分引擎），并随快照版本化 | 三年后索引仍完全由引擎自持，格式规范里没有任何索引条目 |
| "跨模态统一 SQL"会长期停在演示层，生产用法是分路检索 + 应用层合并 | 生产实践仍以分路为主；相关标准无进展 | 出现第三方公开的、把跨引擎融合查询放进关键路径并上量的架构（含与分路方案的对照） |

写这四条时的共同约定：**信号必须是外部可观察的**（格式规范条目、产品文档的计费与配置章节、第三方公开案例），而不是"我觉得会"。凡写不出证伪信号的判断，本节不写。

四条里前两条是**架构选择**预测、后两条是**生态耦合**预测。它们每年可以按固定动作复评一次：

- 查一次你所用的表格式规范（Iceberg / Delta / Hudi）里有没有索引相关的条目——这是预测 1、3 的判定入口。
- 算一次 Serverless 的交叉点 Q*（用你自己的 QPS 与单价），与上一次比——这是预测 2 的判定入口。
- 统计一次生产查询里真正跨引擎的融合查询次数——如果始终是零，说明它只是演示能力，这是预测 4 的判定入口。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 向量在千万级以内，索引还装得进内存 | 留在全内存路线；把"索引大小 / 可用内存"这个比值做成监控指标 | 比值何时越过 1——它比任何容量告警都更早 | **不要因为"以后会长到十亿"提前上 SSD 或存算分离**；小规模用磁盘索引是纯亏 |
| 向量到亿级，索引开始装不下 | 先上量化把拐点右移，再考虑把向量本体下移介质 | IOPS 账：峰值 QPS × 每次搜索随机读次数是否会撞上卷的上限 | 不要只算容量账；不要用"多买几块盘"代替 IOPS 规划 |
| 请求是长尾低频（内部工具、周期性分析） | 算交叉点 Q*，再决定 Serverless 还是常驻集群 | cache miss 的计费与延迟口径是否被产品公开 | **不要在没算过 cache miss 的情况下选 Serverless**；不要用数据量而不是访问频次做判据 |
| 要求向量与结构化数据同源同权 | 用湖表承载向量列，把权限与血缘复用表格式机制 | 表格式规范里是否出现索引条目；索引是否随快照版本化 | **不要假设时间旅行能回到旧索引**；不要把湖上检索放进用户等待的在线路径 |
| 业务提出"多模态检索" | 按"多套编码器 + 一套向量存储"设计，并在元数据里记模态与模型版本 | 跨模态分数是否可比（拿一个已知正样本对验证） | **不要为"统一向量空间、任意模态互搜"预留 schema**；不要把模态当作索引能力来采购 |
| 已经建了一版向量索引，想换引擎 | 先把"能否从冷源全量重建"补上（重建脚本 + 时间上限） | 重建一次要多久、期间新增数据怎么补 | **不要在无法全量重建的前提下迁移**——索引格式不通用，那等于把数据押在一个黑盒里 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的（换介质、涨账单、迁移、改 schema），而收益依赖一个尚未在你自己的数据上验证过的假设**（规模会继续涨 / 请求会变高频 / 模态分数天然可比 / 表格式会接管索引）。等 §5.6 的信号出现再投入，损失的只是时间；提前投入损失的是迁移窗口和一条不可逆的架构选择。

这张表的六行不是互斥选项，而是同一支团队会依次遇到的处境。真正**不可逆**的决定只有一个：**索引状态放在哪种介质上**。它决定了容量上限、成本函数与弹性，一旦选定，后续所有优化都只是在这个层级内做取舍——量化是在同一介质内压缩，缓存是在层级之间做弥补，都不会把你从对象存储拉回内存。至于 Serverless、湖仓一体、多模态、AI 运维，都是在介质确定之后还可以替换的选项。**把不可逆的决定与可逆的决定分开排期，比把它们一起放进路线图更重要。**

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**索引状态的驻留层级发生拆分**——决定搜索路径的图结构留在内存，向量本体下移到 SSD 或对象存储，于是容量上限从"单机内存"变成"介质容量 + IOPS 预算"。因为这一点，排进 L1 的是"介质下移"这个机制，而不是"向量湖"这个概念：Serverless、Lakehouse + Vector、多模态 Embedding、AI 增强运维全部停在 L2，判它们的不是"能不能存得下"，而是"成本函数由什么驱动、索引是不是旁挂件、分数还可不可比"。
>
> 它**没有**改变的是检索的基本代价：**向量索引是有状态的结构，"装得下"与"查得动"是两笔账**——容量可以买到，IOPS 与尾延迟只能通过设计与缓存去换。
