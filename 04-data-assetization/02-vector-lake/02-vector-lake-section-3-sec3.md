## 3. 设计模式与范式

> 原 § 3 共 87 行，形式为「模式 + 优点 / 缺点 / 适用」条目 + 适用场景决策表 + 反模式清单，缺结构示意、机制解释与失效分析，重写为 ~330 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把向量湖的设计讲成了「按规模选一个」：千万级选内存、亿级选 SSD、十亿级选存算分离。但真实的选型几乎从不是选出来的，是被三条主约束推出来的：**索引结构驻留在哪一级存储介质、向量作为模型派生物如何失效与重建、标量条件在哪一层参与过滤**。这三条里任何一条不同，同样的向量数、同样的延迟目标，正确的模式就不同。

第一条是**索引驻留的介质**。ANN 检索不是顺序扫描，是随机访问：HNSW 的每一次贪心跳转都要取一个节点的邻居表，`ef` 越大跳得越多（[§ 2.2](02-vector-lake.md) 给了 HNSW、IVF、PQ 的形式化基础）。所以单次查询的延迟下限由「跳数 × 一次随机访问的介质延迟」决定，而不由向量总数决定。这条约束把「内存 / SSD / 对象存储」从成本选项变成了**性能天花板**——把它当成本题做，会在规模上去以后发现延迟模型整个不成立。

第二条是**向量是派生数据**。向量由 Embedding 模型生成，模型换一次（换版本、换维度、换归一化方式），存量向量的语义空间就变了，旧向量与新向量不可比。所以向量湖与普通数据湖最关键的区别不是「存的东西不一样」，而是**它多出一个会整体失效的版本维度**：「不分版本」「不分片」「无血缘」这几条反模式的根因都在这里（见 3.5）。

第三条是**标量条件的参与深度**。「最近 30 天、本租户、类目 = X、语义相似」这类查询里，标量条件不是优化，是正确性的一部分（权限、时效、合规）。ANN 索引的召回假设建立在「在整个空间里找最近邻」上，一旦过滤是后置的（先取 Top-K 再筛），过滤率一高，Top-K 就被筛空。所以「向量放在哪」这个问题，实际上同时在回答「过滤与 JOIN 在哪一层执行」。

下面这张表把前三条列在前面三行；后三行（写入模式、重建窗口与变更频率、规模与成本约束与团队运维能力）是由这三条派生出来的**次级约束**——它们不改变「索引放在哪一级介质」这条主线，但决定同一介质上的实现形态：段化还是原地插入、全量重建能否落在重建窗口内、容量与运维风险由自建还是托管承担。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 索引驻留的介质（内存 / SSD / 对象存储） | 单次查询的 I/O 次数与延迟下限 | 「能全内存就全内存」——超过单机内存预算后成本是阶跃的，不是缓升的 |
| 向量是模型派生物（带版本） | 是否需要版本化、可重建、可回滚 | 「向量入库一次就完事」——换 Embedding 模型等于存量向量作废 |
| 标量条件在哪一层参与过滤 | 召回率是否还成立（不只是快慢） | 「先检索再按条件筛」——后置过滤会把 Top-K 越筛越少，直到筛空 |
| 写入模式（批量构建 / 增量流式） | 索引是段化 + 定期合并，还是原地插入 | 「HNSW 支持动态插入就够了」——删除只能标记，空间要靠合并回收 |
| 重建窗口与变更频率 | 全量重嵌入能否在 SLA 内完成 | 「重建是运维的事」——重建窗口由 Embedding 吞吐决定，不由向量库决定 |
| 规模与成本约束、团队运维能力 | 自建 / 托管 / Serverless 的分界 | 「Serverless 零运维所以总是更省」——成本从容量变成调用量，持续高负载反而更贵 |

把这 6 个模式放回上面三条主约束（以及由它们派生的次级约束）上看，关系会清楚很多：内存向量库、SSD 向量库、存算分离向量湖回答的是第一条（索引放在哪一级介质）；Lakehouse + 向量列回答的是第三条（过滤与 JOIN 在表格式里做）；Serverless 向量 DB 回答的是「谁承担容量与运维风险」；联邦向量查询既不解决介质也不解决过滤，它解决的是「数据不能搬」这一组织现实。**把不同层次的问题当成同一个单选题，是向量库选型最常见的出错形式。**

### 3.2 模式逐个拆解（核心节）

下面 6 个模式按「索引驻留介质（3.2.1–3.2.3）→ 过滤与 JOIN 的位置（3.2.4）→ 运维与成本归属（3.2.5）→ 数据的物理位置是否可动（3.2.6）」排列。3.2.1–3.2.3 是同一条约束上的三个档位，不是三个互斥选项。

#### 3.2.1 内存向量库（HNSW 常驻内存）

- **被什么约束逼出来**：图遍历是随机访问，单次查询要跳几十到几百个节点，只有内存能给出每次跳转近似常数的时间；当向量规模在千万级以内、延迟要求毫秒级时，这是唯一能同时满足两者的结构。
- **结构**：向量本体与图结构（邻居表）都常驻内存，标量列与向量同表，扛不住时靠分片横向扩。

```sql
-- 内存向量库（pgvector 风格）：向量与标量同表，索引常驻内存
CREATE TABLE doc_chunk (
  chunk_id      BIGSERIAL PRIMARY KEY,
  doc_id        BIGINT      NOT NULL,
  tenant_id     TEXT        NOT NULL,        -- 标量过滤条件：权限在这里
  effective_at  TIMESTAMPTZ NOT NULL,        -- 标量过滤条件：时效在这里
  model_version TEXT        NOT NULL,        -- Embedding 版本：重建的依据
  embedding     vector(768) NOT NULL         -- FP32 768 维 = 3072 字节/行
);
CREATE INDEX doc_chunk_hnsw ON doc_chunk
  USING hnsw (embedding vector_cosine_ops)      -- m 与 ef 决定内存占用与召回
  WITH (m = 16, ef_construction = 64);

-- 内存账【推算】推导链：
--   向量本体 = 768 维 × 4 字节（FP32） = 3072 字节/向量
--   10^9 向量 × 3072 字节 = 3.072 × 10^12 字节 ≈ 3.07 TB —— 尚未计入图结构
--   图结构 ≈ 每节点 m 个 int32 邻居 + 层级指针，m=16 时再加几十字节/节点
-- → 结论：这个量级下问题是"单机装不下"，不是"慢一点"
```

- **为什么这样设计有效**：因为索引是内存里的一张邻居表、向量本身也常驻，所以一次查询的代价约等于「跳数 × 内存随机访问延迟」，与候选集总规模几乎无关——**这是「毫秒级 P99 + 接近暴力搜索的召回」能同时成立的唯一机制**，也是它至今仍是小规模默认选择的原因。
- **代价**：① 内存占用是向量本体 + 图结构两部分，前者恒定、后者随 `m` 线性增长，两者都随向量数线性增长；② 构建期内存放大——建图时的工作集大于最终索引，必须预留额外余量，否则在批量导入时 OOM；③ 进程重启意味着要么重建、要么从快照重新加载，冷启动时间随规模增长，**「毫秒级」这个卖点只在进程热着的时候成立**。
- **失效点**：当向量数超过单机内存预算时，「毫秒级延迟」反转成「根本装不进一台机器」，因为全内存方案的内存占用随向量数线性增长，而内存单价与 SSD、对象存储不在一个量级，容量增长无法靠单价下降消化。此时正确的动作是把索引下沉（3.2.2）或把持久层搬到对象存储（3.2.3），而不是加机器——加机器只解决容量，同时引入分片聚合与副本一致性这两项新成本。
- **真实使用**：HNSW 由 Malkov & Yashunin 提出（*Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs*，arXiv 2016 / IEEE TPAMI 2020）；FAISS 是应用最广的内存 ANN 库之一（Meta 开源，仓库 `facebookresearch/faiss`，配套 GPU 检索论文 2017 年预印本、2019 年期刊版）；pgvector 提供 HNSW 与 IVFFlat 两种索引（pgvector 仓库的 README 与索引参数说明）；Qdrant、Weaviate 在中小规模下同样把向量与图结构放内存（各自官方文档的索引与资源占用章节）。【公开】（来源：上述论文、仓库与官方文档；索引参数默认值以当前版本为准）

#### 3.2.2 SSD 向量库（DiskANN / Vamana）

- **被什么约束逼出来**：十亿级向量装不进内存，但 ANN 的随机访问又不能退化成顺序扫描全量——逼出了「内存只放导航信息，完整向量放 SSD，并把 SSD 访问组织成块读」。
- **结构**：导航结构（量化后的短码 + 邻居 id）常驻内存；完整向量与邻居记录按固定大小的块布局在 SSD 上，一次 I/O 取回一个节点及其邻居，而不是一次取回一个向量。

```text
SSD 向量库（DiskANN / Vamana 思路）：内存放导航，SSD 放向量，块读代替逐向量随机读

  内存（每向量几十～几百字节，而不是 3 KB）
  ┌──────────────────────────────────────────────────────┐
  │ 节点 i ： 量化短码(i) │ 邻居 id 列表(i) │ 是否已缓存标记 │
  └──────────────────────────────────────────────────────┘
        │ 图遍历在水面之上完成，候选集只在这里扩展
        ▼
  SSD（每个块 = 一个节点的完整向量 + 它的邻居向量，连续排布）
  ┌────────────────┬────────────────┬────────────────┐
  │ block(k)       │ block(k+1)     │ block(k+2)     │
  │ 节点 + 邻居向量 │ 节点 + 邻居向量 │ 节点 + 邻居向量 │
  └────────────────┴────────────────┴────────────────┘
        │ 需要精确距离时才读块；块内数据一次取回
        ▼
  延迟模型：查询时间 ≈ 跳数 × 一次块读延迟
            （不是「向量总数 × 一次随机读」）

  ──────────────────────────────────────────────────────────
  关键：内存里存的是「怎么走」（导航），不是「是什么」（原始向量）
        布局决定成败——同一节点的向量与邻居必须相邻
        才能拿顺序带宽去换随机 IOPS
```

- **为什么这样设计有效**：因为内存里只保存量化短码与邻居 id，单个节点的内存开销从「完整向量」降到「几十到几百字节」，同样内存能覆盖的向量数提高约一到两个数量级【推算：FP32 768 维的向量本体 = 3072 字节，而 DiskANN 类结构在内存中每节点只需量化短码 + m 个 int32 邻居 id；3072 ÷ 100 ≈ 30×，取更激进的量化码时比值更高】；因为 SSD 上按块布局把「一个节点及其邻居」放在相邻位置，一次 I/O 就取回扩展候选集所需的全部数据，所以查询代价由**跳数**决定而不是由向量总数决定——这两条合起来，才是「单机十亿级」这个组合能成立的原因。
- **代价**：① 延迟下限被 SSD 读延迟锁死，内存随机访问与 SSD 块读相差约两到三个数量级【推算：内存随机访问约百纳秒（10² ns 量级）、SSD 随机读约几十微秒（2～9 × 10⁴ ns 量级），两者之比在 200～900 倍之间，即 2.3～2.95 个数量级】，P99 从亚毫秒退到毫秒～十毫秒区间；② 写入路径复杂——新节点要重排块、图要定期重连，删除只能标记；③ SSD 的随机读 IOPS 成为新的稀缺资源，必须监控「每查询块读次数 × QPS」，否则会用容量换了 IOPS 却不自知。
- **失效点**：当并发上升或候选集变大（`ef` 调高、带大量过滤后再检索）时，「省内存」反转成「被 SSD IOPS 卡住」：因为每次查询的块读次数随 `ef` 与遍历深度增长，QPS 乘以每次查询块数一旦超过盘的能力，延迟不是线性上升而是雪崩式上升。此时只有三条路——把热集合拉回内存（冷热分层）、靠副本分摊读、降低 `ef` 并接受召回下降，三条都不免费。
- **真实使用**：DiskANN 由微软研究院提出（Subramanya et al., *DiskANN: Fast Accurate Billion-point Nearest Neighbor Search on a Single Node*, NeurIPS 2019），把图索引放到 SSD 上以支持单机十亿级检索；参考实现开源在 `microsoft/DiskANN` 仓库（仓库的创建与 release 时间可由其公开仓库页核验，本节不写年份）；Timescale 的 pgvectorscale 提供 StreamingDiskANN 索引（仓库 `timescale/pgvectorscale`，其 release 记录可核验）；Pinecone 的官方架构材料把持久层放在对象存储、索引与缓存放 SSD（**判定方法**：以该产品当前架构文档的表述为准，不以第三方转述为准）；Milvus 2.x 把 DISKANN 列为可选索引类型，即同一个存算分离集合上也可以对单集合启用 SSD 驻留索引（Milvus 官方文档的索引类型章节）。【公开】（来源：上述论文、仓库与官方文档）

#### 3.2.3 存算分离向量湖（对象存储 + 弹性计算）

- **被什么约束逼出来**：向量总量到 TB～百 TB 级后，索引构建（批量 ETL、换模型全量重嵌入）与在线检索的算力形态完全不同——前者吞吐敏感、可中断可重试，后者延迟敏感、必须常驻。把两者绑在同一批机器上，任何一边扩容都要为另一边付钱。
- **结构**：对象存储放段化索引、向量段与元数据（持久层）；计算层无状态、可弹性拉起（检索节点、构建节点、合并节点）；协调层持有集合 / 分区元数据与版本，增量写入经消息流承接。

```text
存算分离向量湖（Milvus 2.x 思路）

  写入：日志流（增量） ──► 建索引 ──► 生成新段 ──► 提交到对象存储
                                                   │
  协调层（集合 / 分区 / 段 / 版本 元数据）────────────┤
                                                   │
  计算层（无状态）：检索节点 / 构建节点 / 合并节点 ◄───┘
        │  缓存热段与热索引（命中率决定 P99）
        ▼
  对象存储（S3 / OSS）：已提交的段 + 索引文件 + 元数据

  ──────────────────────────────────────────────────────────
  关键 1：计算层不持有持久状态 → 扩容 = 多拉副本，缩容 = 杀副本
          成本随查询量走，而不是随「容量上限 × 时长」走
  关键 2：段（segment）是一次写入、多次读取的不可变单元
          → 删除靠标记 + 合并回收，空间不会立刻释放
  关键 3：在线检索与批量重建读同一份对象存储数据，互不搬家
```

- **为什么这样设计有效**：因为计算节点不持有持久状态，扩容只是拉起更多副本、缩容只是杀掉副本，**成本随查询量而非随时长与容量上限走**；因为索引以不可变段为单位提交到对象存储，所以「重建索引 / 换 Embedding 模型 / 新增一路标量过滤」这类批作业与在线检索可以同时读同一份数据。这是 [§ 2.3](02-vector-lake.md) 里「LSM 思想：内存 HNSW + 磁盘段 + 定期合并」在架构层最直接的对应物。
- **代价**：① 段化意味着「刚写入的向量」与「已合并的向量」走不同路径，删除只能标记、空间要等合并才回收，**写多读少的场景会攒下大量待合并段**；② 未命中缓存的查询要走一次对象存储（数十毫秒量级），缓存命中率因此成为 P99 的直接决定项，而不是一个可选的优化指标；③ 协调层 + 元数据服务是新的有状态组件，其可用性、一致性与元数据膨胀都要单独设计。
- **失效点**：当访问从「大量长尾集合」变成「少数高度倾斜的热点集合」时，「弹性」的收益被缓存命中率抹平：因为每次扩容拉起的副本都要先预热缓存，扩容收益滞后于扩容动作，而热点集合始终落在同一批分片上，此时要么做副本级热点隔离，要么为极少数集合保留常驻资源——长尾成本优势至此反转。判据可直接观测：**扩容后 P99 是否随副本数下降**，若不降，瓶颈就在缓存预热或热点分片，而不在算力。
- **真实使用**：Milvus 2.x 的「存算分离 + 消息流 + 段」架构是这一模式最完整的公开实现（Milvus 官方文档的架构章节）；Pinecone Serverless（2024 年公开发布，见该产品的官方发布材料）与 Weaviate 的 serverless / 多租户形态属同一思路（各自官方文档的云服务章节）。【公开】（来源：上述产品的官方文档与发布材料；版本与特性条目以当前文档为准）

#### 3.2.4 Lakehouse + 向量列

- **被什么约束逼出来**：检索很少只按相似度——「本租户、最近 30 天、类目 = X 且语义相似」里，标量条件是正确性的一部分。向量库若把标量过滤当成检索之后的过筛，过滤率高时 Top-K 会被筛空；反过来，向量若游离在湖仓之外，就得为每次 JOIN 搬一次数据。
- **结构**：向量作为湖仓表的一列与标量列共用一个快照，分区与排序键承担「会被一起过滤的条件」，ANN 索引作为随表版本演进的派生索引文件存在。

```sql
-- Lakehouse + 向量列（概念示意：Iceberg / Delta / Hudi / Lance 等变体）
CREATE TABLE doc_chunk (
  chunk_id      BIGINT      NOT NULL,
  tenant_id     STRING      NOT NULL,
  doc_date      DATE        NOT NULL,
  category      STRING      NOT NULL,
  model_version STRING      NOT NULL,           -- 版本是列，不是外部约定
  embedding     VECTOR(768) NOT NULL            -- 向量列：与标量列同一快照
)
PARTITIONED BY (doc_date, tenant_id)             -- 分区 = 一定会被过滤的条件
TBLPROPERTIES ('sort.columns' = 'category');     -- 物理聚集 = 提高裁剪效果

-- 快照：每次查询都指定一个表版本
--   → 向量与它对应的标量行来自同一版本，一致性由表格式保证
-- 派生索引文件（ANN 索引）：随表版本生成，写入提交后需增量构建 / 合并

-- 对照（为什么后置过滤会出事）：
--   先 ANN 取 Top-100 → 再筛 tenant / date / category
--   若过滤通过率仅百分之几，取回 100 条最终只剩几条【推算：100 × 通过率】
--   → 看起来是"召回差"，实际是过滤打穿了 ANN 的召回假设
```

- **为什么这样设计有效**：因为分区与排序把「会被一起过滤的条件」预先物化成分区与物理聚集，所以向量检索可以在**已被裁剪到与谓词相交的片段**上做，而不是在全量上取 Top-K 再筛——过滤从「检索之后」变成「检索之前」；因为向量与标量列在同一快照里，所以时间旅行下「这一行」与「它的向量」是同一个版本，一致性由表格式保证，不靠应用层对齐。
- **代价**：① ANN 索引不再是数据库的一等结构，而是「随表版本演进的派生文件」，必须自己解决索引与数据版本的对齐（写入提交后索引滞后，要靠增量索引 + 合并补齐）；② 点查延迟通常高于专用向量库，因为一次查询要同时付「文件裁剪 + 索引文件读取 + 向量计算」三段代价；③ 标量列的选择性与物理排序一旦不匹配查询模式（排序键是热度、查询按时间过滤），裁剪效果大打折扣。
- **失效点**：当查询的标量条件选择性很低（只过滤一个占比九成的类目）时，「先裁剪再检索」的优势消失，退化成「大范围扫描 + 向量计算」，此时同等规模的专用向量库会反超。所以判据不是「有没有向量列」，而是**你的谓词能不能把数据裁剪到一个很小的片段**——这条可以在上线前用一段 SQL 量出来：同一查询在裁剪与不裁剪下的扫描量之比。
- **真实使用**：Databricks Vector Search 建立在 Delta 表之上（Databricks 官方文档中 Vector Search 与 Delta 的集成章节）；LanceDB 使用自研的 Lance 列式格式，向量与标量同文件（LanceDB 官方文档与 Lance 格式规范）；Iceberg 侧存在把向量与向量索引纳入规范的社区提案（进展以 Apache Iceberg 仓库的规范讨论为准，撰写时尚未成为标准）。【公开】（来源：上述项目官方文档与规范讨论）

#### 3.2.5 Serverless 向量 DB

- **被什么约束逼出来**：需求的形态是「峰值不可预测 + 长尾集合多 + 团队没有向量库运维能力」。固定容量在长尾场景下必须为峰值付费，而长尾集合的平均利用率很低。
- **结构**：控制面（集合 / 索引元数据、权限、配额）与数据面（无状态查询节点 + 共享存储）分离，按查询与存储计费，空闲时可缩到零。

```text
Serverless 向量 DB：控制面 / 数据面分离 + 按用量计费

  控制面（集合定义、索引参数、权限、配额、凭据、用量账本）
        │
        ├── 数据面：无状态查询节点（按请求拉起，空闲回收）
        │        └── 共享存储：索引 + 向量（不随节点生命周期存在）
        └── 计量：读单位 / 写单位 / 存储量  →  账单

  ──────────────────────────────────────────────────────────
  关键 1：节点无状态 → 冷却后可缩到零
          长尾集合的边际成本 ≈ 它的实际使用量
  关键 2：可调空间收窄 → 索引参数、量化方式、数据落盘位置通常不可控
  关键 3：成本模型从「容量 × 时长」变成「调用量 + 存储量」
```

- **为什么这样设计有效**：因为查询节点不持有持久状态，实例可以真的缩到零，所以**成本结构从「按峰值容量 × 时长」变成「按实际调用 + 存储」**——对长尾集合（今天被查三次、下周被查两次）来说，这是从「为峰值常备资源」到「为使用付费」的换轨，而不是打折。
- **代价**：① 冷启动——缩到零之后的第一个查询要经历「拉起 + 加载索引 / 预热缓存」，P99 的尾部被拉长，且这个尾部取决于该集合的大小；② 可调空间被收窄，索引参数、量化方式、数据落盘位置通常不可控，遇到「必须自定义召回 / 成本」的场景没有出口；③ 多租户共享资源意味着噪声邻居：别人的负载会出现在你的 P99 里，而这条曲线你看不到，只能从自己的延迟分布反推。
- **失效点**：当负载从「间歇 / 长尾」变成「持续高 QPS」时，「按用量付费」反转成「比预留容量更贵」：因为 serverless 的单位查询价格里含了隔离、弹性与运维的溢价，而持续负载根本不需要弹性。这条可以算，不需要争论——把过去一段时间的调用量换算成服务商的计量单位得到账单，与同规格预留 / 自建方案的成本曲线对比，交点就是分界。【经验】多数团队的实际形态是「核心稳定负载走预留或自建，长尾与实验集合走 serverless」，而不是二选一（见 3.4）。
- **真实使用**：Pinecone Serverless（2024 年公开发布，见该产品的官方发布材料）；Weaviate 与 Qdrant 的托管云形态（各自官方文档的云服务与多租户章节）；以及各云厂商的托管向量检索服务，也都在把向量检索做成按用量计费的服务（各自产品的文档与当前定价页）。【公开】（来源：各服务商官方文档与发布材料；计费单位与价格以当前定价页为准）

#### 3.2.6 联邦向量查询

- **被什么约束逼出来**：向量不在一个系统里——历史向量在旧库、新向量在新库、图像向量在图库、标量数据在数仓；而跨组织的数据往往不能搬（合规、权责、成本），于是只能在查询层拼。
- **结构**：查询改写 → 各后端并行检索 → 全局归并（统一度量排序 + 按全局 id 去重）→ 回到各源补齐标量字段。

```text
联邦向量查询：fan-out + 归并（每个后端都要超取）

  查询 q（向量 + 标量谓词 + K）
        │
        ├──► 后端 A（旧向量库，度量 cosine，超取 K'）
        ├──► 后端 B（新向量库，度量 L2，    超取 K'）
        ├──► 后端 C（图库，    度量 IP，    超取 K'）
        └──► 后端 D（数仓向量列，度量 cosine，超取 K'）
                     │
              归并层：① 统一度量（必须先做，否则排序无意义）
                      ② 按全局 id 去重
                      ③ 取全局 Top-K
                     │
              延迟 = max(各后端延迟)，不是 avg

  ──────────────────────────────────────────────────────────
  为什么要超取 K' > K：
    下限在哪：若各后端与归并层用同一度量、且能精确返回前 K 名，
    K' = K 就够了——各后端前 K 名的并集必含全局 Top-K
    （全局第 r 名在它所在的那个后端里至多排前 r）
    超取的余量不来自这条下限，而来自两处，两处都只是降低漏召回的
    概率、不构成正确性保证：
      · 各后端多为 ANN 近似检索，recall@K 不饱和，真近邻会漏在后端 Top-K 之外
      · 各后端各带自己的度量（cosine / L2 / IP），统一发生在归并层，之后还要
        按全局 id 去重——后端按自身度量排出的前 K 名，未必是统一度量下的前 K 名
  代价：总候选数 ≈ M × K'（M = 后端数），计算量随后端数放大
```

- **为什么这样设计有效**：因为不需要搬迁数据，所以它能覆盖「有合规或组织阻力、数据不能搬」的场景——**这是它唯一不可替代的价值：跨组织的数据往往不能搬，但可以查**；其余优点（不改数据、各自演进）都是这条的副产品。
- **代价**：① 每个后端都要超取 K'，总候选数约为 M × K'，归并与精排的计算量随后端数放大【推算：各后端与归并层同度量口径、且精确返回前 K 名时，其并集必含全局 Top-K（全局第 r 名在它所在后端里至多排前 r），故 K' = K 即是正确性下限；K' > K 是为 ANN 近似召回（recall@K 不饱和）与归并层的度量统一、按全局 id 去重留的召回余量】；② 必须先把不同库的度量统一（cosine / L2 / IP 混用直接比距离是错的），归一化方式不一致会让排序失去意义；③ 去重依赖全局 id 体系，而这在多个历史系统里通常并不存在。
- **失效点**：当后端数量或单后端延迟上升时，「跨源可见」反转成「P99 由最慢分支决定」：因为 fan-out 会放大长尾——每个后端都有一条慢请求的尾巴，M 个后端里至少一个慢的概率随 M 上升，整体延迟被这条尾巴拖住。所以联邦向量查询适合「后端数为个位数、查询频率不高、可接受百毫秒级」的场景；一旦它变成主链路的高频查询，正确动作是把需要一起检索的向量**物理合并到一个索引**里（并接受搬迁成本），而不是继续优化归并层。
- **真实使用**：原 §3 为这个模式列的代表是「Trino / Presto + 向量 Connector」。本节对这条路径的判断是：SQL 引擎侧的向量连接器尚不是成熟的标准能力，各插件是否把过滤下推到索引扫描之内必须**逐个插件核验**——判定方法是构造命中率 0.1% 的查询，比较「先过滤后检索」与「先检索后过滤」两种实现的召回差（本章 [§ 5 前沿演进](02-vector-lake-section-5-ai.md) 把这条路径定级为 L2「可试点」：产品已在演进，但尚不构成既成事实）。【经验】实践中更常见的是在应用层做 fan-out（服务内并行调用多个向量服务再归并），或在统一查询网关里以自定义算子实现（见 [§ 4 工程实现](02-vector-lake-section-4-sec4.md)）。无论走哪条，都要先核验连接器当前版本的真实行为，不要把「有连接器」当成既成事实。

### 3.3 模式选择决策表

> 下表里的向量规模与延迟阈值都是情景阈值【经验】；其中 1000 万 / 1 亿 / 10 亿三条规模线的【推算】见 [§ 7.5](02-vector-lake-section-7-sec7.md)（768 维 FP32 口径：1000 万 ≈ 30.7 GB 向量本体 + 约 2.6 GB 图 ≈ 33 GB，单机 64 GB 内存可容纳；1 亿 ≈ 307 GB + 26 GB 图，INT8 量化后约 77 GB、PQ 后约 38 GB；10 亿 ≈ 2.8 TiB，全内存需 20–30 台 128 GiB 实例）。

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 千万级向量 + 毫秒级延迟【经验】 + 单机内存装得下 | 内存向量库 | SSD 方案在这个规模只是白白多付一层 I/O 延迟 | 单机内存是否**装得下向量本体 + 图结构 + 构建期余量** |
| 亿级 / 十亿级【经验】 + 成本敏感 + 内存装不下 | SSD 向量库（DiskANN） | 内存方案的容量缺口无法靠单价下降消化，成本是阶跃的 | 每查询块读次数 × QPS 是否**低于盘的随机读能力** |
| 十亿级以上【经验】 + 需要弹性 + 有运维能力 | 存算分离向量湖 | 固定集群要为峰值付费，且重建与在线检索互相抢资源 | 增量写入占比与**重建窗口是否落在 SLA 内** |
| 向量 + 强标量过滤 / 需要与结构化数据 JOIN | Lakehouse + 向量列 | 专用向量库做后置过滤会在高过滤率下打穿召回 | 谓词能否**把数据裁剪到很小的片段** |
| 峰值不可预测 / 长尾集合多 / 无运维团队 | Serverless 向量 DB | 预留容量要为峰值付费，而长尾利用率低 | 调用量 × 单价 与 预留容量的**成本曲线交点** |
| 数据不能搬（合规 / 跨组织）+ 查询频率低 | 联邦向量查询 | 物理合并最省事，但搬迁成本或合规不允许 | 后端数是否**个位数**、延迟目标是否**百毫秒级可接受**【经验】 |
| 实时流式更新 + 低延迟检索 | 内存向量库 + CDC（见 3.4） | 纯批量方案的新鲜度受重建周期限制，实时性无法保证 | 可接受的新鲜度上界 vs **重建周期** |
| 离线批量分析 / 全量重嵌入 | 存算分离向量湖 | 内存与 Serverless 的计价方式对批量吞吐极不友好 | 任务是否**可中断可重试**、是否按吞吐而非延迟计价 |

表里最常被误选的一对是**内存向量库 vs SSD 向量库**：团队通常按「延迟目标」选前者，因为全内存的延迟更好看。但机制上，内存方案的内存占用随向量数**线性**增长且单价台阶高，一旦越过单机内存预算，问题不是「贵一点」而是「装不下」；而那时数据模型、索引参数、召回目标都已经按内存方案调好，迁移成本远高于一开始就选 SSD 方案。正确的判据不是延迟目标，而是**先把「向量数 × 单向量字节数 + 图结构开销」算出来，与可用内存对一次账**（3.2.1 的注释给了这个算式）。

### 3.4 组合模式：真实系统不会只用一种

**组合一：存算分离向量湖 + 内存缓存层（冷热分层）**

- 构成：对象存储放全量段，SSD 存索引与温数据，内存缓存放热点集合的 HNSW 图；三层共用同一套 id 与版本。
- 职责边界：持久与重建交给对象存储层，延迟目标交给内存层，中间层承担长尾与预热。
- 运维代价：三层的预热与失效策略必须一起设计，否则会出现「同一集合在不同层召回不一致」；分层要监控命中率，否则会退化回一层。
- 适合规模：十亿级以上、访问高度倾斜（少数集合吃到多数流量）。【经验】

**组合二：CDC + 内存向量库（原决策表中的「实时流式」）**

- 构成：CDC 捕获源表变更 → Embedding Worker → 内存向量库增量插入；离线链路定期做全量重建与对账。
- 职责边界：CDC 链路只负责新鲜度，离线链路负责一致性与历史修正；两条链路必须共享 `model_version`。
- 运维代价：双链路的口径漂移是最常见故障源（在线插入与离线重建的向量来自不同模型版本）；HNSW 上的删除与更新只能标记，需要定期重建回收。
- 适合规模：千万级以内、新鲜度要求分钟级、写入 QPS 不高的场景。【经验】

**组合三：Lakehouse + 向量列 + 专用向量检索（各取所长）**

- 构成：湖仓存向量列与标量列（权威、可时间旅行、可与结构化数据 JOIN），专用向量库存同一批向量的检索索引（快），两者靠 id 与版本对齐。
- 职责边界：湖仓是真相源，向量库是派生索引；任何重建都以湖仓为准，向量库可随时丢弃。
- 运维代价：多一份派生副本要同步（写放大），必须能回答「索引落后真相源多少」，否则会出现「检索到的向量在湖仓已被删除」。
- 适合规模：既要复杂标量分析又要低延迟检索的中大型组织。【经验】

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 全内存堆规模 | 内存用量随向量数线性上涨，单机装不下时只能加副本 | 成本是阶跃的不是线性的，越往后越不可能靠优化挽回 | 全内存延迟最好看，PoC 阶段向量少、成本感知不到 | 先算内存账再选介质；超预算即下沉 SSD（3.2.2） |
| 无量化 | 存量向量以 FP32 为主，内存 / 盘用量与向量数同比例增长 | 存储与 I/O 都按原始精度付费；SSD 方案里直接决定装不装得下 | 量化会掉召回，而召回损失在上线前看不见 | SQ / PQ 起步，用召回评测兜底（档位与损失见 [§ 2.2](02-vector-lake.md)） |
| 不分片 | 单节点向量数持续增长，延迟缓慢劣化且无拐点告警 | 单节点容量上限与单点故障同时成为系统上限 | 早期分片增加复杂度，而规模增长是渐进的 | 按 id 或聚类分片 + 副本；把「单分片向量数」做成监控项 |
| 不分版本 | 换过 Embedding 模型，库里同时存在多版本向量且查询不区分 | 新旧向量不可比，召回静默下降——不报错，只是答得不准 | 版本被当成外部约定，而不是数据模型的一部分 | `model_version` 入表、入索引、入查询条件；支持按版本重建与回滚 |
| 无血缘 | 无法回答「这个向量由哪份原始数据、哪个模型、哪个版本产出」 | 出问题只能全量重建；合规上无法举证数据来源 | 向量被当成纯技术产物，而不是数据的派生物 | 向量与源记录 id、模型版本、生成时间一起落库，并纳入血缘 |
| 无成本监控 | 只监控 QPS 与延迟，账单出现时才追查 | 成本失控无法归因到集合 / 租户 / 查询类型 | 向量库的成本项分散在计算、存储、I/O 三处，不易看出 | 按集合 / 租户维度出成本报表，I/O 与存储分开计 |
| 忽视召回率评估 | 只测延迟不测 Recall@K，调参凭手感 | 延迟指标好看而答案质量静默下滑，且无法区分是模型问题还是索引问题 | 召回评测要构造标注集，一次性成本高 | 固定一批查询与标注结果，把 Recall@K 纳入发布门禁 |
| 盲目追求高精度 | 召回目标定到接近 100%，索引参数一路调高 | 延迟与成本为最后几个百分点付指数级代价 | 「召回越高越好」听起来没有反驳空间 | 按业务定召回目标，剩余交给精排（见 [§ 4](02-vector-lake-section-4-sec4.md)） |
| 无冷热分层 | 热集合与冷集合混在同一层，扩容只能整体扩 | 冷数据常占热介质，成本与延迟目标同时被拖累 | 分层需要先有访问统计，而访问统计往往没做 | 按访问频次分层、逐层下沉；分层规则写进运维手册 |
| 无多租户隔离 | 一个租户的批量任务让其他租户延迟抖动 | 邻居噪声无法归因，SLA 无法对单个租户承诺 | 早期租户少，共享资源看起来没有代价 | 配额 + 优先级 + 关键租户物理隔离（分片 / 独立实例） |

**「无量化」与「全内存堆规模」通常一起出现**，暴露方式也相同：不是报错，是账单。机制也一样——把召回率当成唯一目标，忽略存储与 I/O 也是检索的一等成本。上线时向量少，两种做法都看不出问题；规模上去以后想省内存只能补量化，而量化会掉召回，于是要重新评测、重新调参、重新验证下游效果：**这是一次返工，不是一次调优**。正确的顺序是反过来的——先定召回目标，再选量化档位，最后算内存账。

**「不分版本」是本节最隐蔽、也最容易被误判为模型问题的一条**。它不报错，不变慢，只是答案在变差：新旧向量在同一个索引里被比较，距离不再可比，召回下降被解读成「模型不行」或「数据质量差」，于是团队去调模型、补数据，而真正的原因是索引里混了两个语义空间。修法很直接也很重：`model_version` 必须是查询条件的一部分，且系统要能按版本重建与回滚。它的修法之所以重，是因为**它要求系统具备「按版本全量重嵌入」的吞吐能力**——而这正是存算分离（3.2.3）要解决的问题。

**「无冷热分层」的暴露方式是扩容收益递减**：团队按峰值扩容，延迟却没有按预期下降，于是继续扩容。机制在于冷数据一直占着热介质——扩容拉起的副本仍要先预热整个集合（含大量从不被访问的向量），预热时间随集合大小增长，而热点只占其中很小一部分。所以分层的价值不在「省存储」，而在**让扩容的收益与热点规模成正比，而不是与总量成正比**。

### 3.6 规模跃迁时模式何时该换

> 本表的跃迁阈值同为情景阈值【经验】；三条规模线（1000 万 / 1 亿 / 10 亿）的【推算】见 [§ 7.5](02-vector-lake-section-7-sec7.md)，口径一致（768 维 FP32）。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 百万级 → 千万级【经验】 | 单机内存向量库 | 单机内存先于延迟到达上限，构建期内存放大开始触发 OOM | 内存向量库 + 分片副本 | 引入分片聚合与副本一致性；查询变成 fan-out 取 Top-K 再归并 |
| 千万级 → 亿级【经验】 | 内存向量库 | **未量化时**向量本体 + 图结构超出单机内存预算，成本阶跃（量化到 INT8 / PQ 后 1 亿以内仍可留在单机内存，见 3.5「无量化」一行与 [§ 7.5](02-vector-lake-section-7-sec7.md)） | SSD 向量库（DiskANN） | 索引布局与写入路径重做；P99 从亚毫秒进入毫秒～十毫秒区间 |
| 亿级 → 十亿级【经验】 | 单集群 SSD | 重建与在线检索抢同一批机器，扩容要按峰值买 | 存算分离向量湖 | 引入对象存储与协调层；缓存命中率成为 P99 的决定项 |
| 批量更新 → 分钟级新鲜度【经验】 | 定期全量重建 | 重建周期是新鲜度的下限，而重建窗口随规模变长 | CDC + 增量段 + 定期合并 | 双链路（增量 / 全量）的口径漂移成为常态风险 |
| 单租户 → 多租户 | 共享集群 | 邻居噪声进入 SLA，无法对单租户承诺 | 配额 + 优先级 + 关键租户隔离 | 需要按租户的成本与用量账本，调度与限流要重做 |
| 固定负载 → 峰值不可预测 | 预留集群 | 为峰值常年付费，而长尾集合利用率低 | 核心预留 + 长尾 Serverless | 两套系统的 id / 版本 / 权限要能对齐；运维面翻倍 |

这些跃迁有一个共同点：**触发换模式的从来不是「向量数量」本身，而是「内存账算不过来」「重建窗口超过新鲜度要求」「过滤打穿召回」这三类结构性矛盾**。向量数量不会直接让模式失效——它让模式失效的方式，一定是通过上面某个具体机制。

因此判断该不该换模式，看的是三个可直接观测的量：**向量数 × 单向量字节数 与可用内存的比值**（逼近 1 时必须换介质）、**全量重建耗时与新鲜度要求的比值**（逼近 1 时必须改成增量段化）、**后置过滤的通过率**（低到某个水平就说明过滤位置错了，应该换到 3.2.4 那类预裁剪结构）。这三个量都能从现有监控与一段 SQL 里取到，不需要先做架构评审。

### 3.7 自检清单

- [ ] 每个向量是否带 `model_version`，且它是**查询条件的一部分**？不带版本，换模型后召回会静默下降。
- [ ] 是否算过内存账（向量数 × 单向量字节数 + 图结构开销 + 构建余量）与可用内存的比值？没算过就是靠感觉选介质。
- [ ] 是否量化？量化档位与它对应的召回损失是否有过评测，而不是照抄默认值？
- [ ] 标量过滤是**检索前**还是**检索后**执行？后置过滤时，过滤通过率是多少？
- [ ] 是否有固定的查询集与标注结果，把 Recall@K 纳入发布门禁？
- [ ] 单分片的向量数是否有上限与监控？超过上限时会告警，还是继续长大？
- [ ] 删除是物理删除还是标记删除？标记的向量什么时候被回收（合并周期）？
- [ ] 是否有冷热分层？分层依据是访问统计还是猜测？
- [ ] 是否按集合 / 租户出成本报表？计算、存储、I/O 三项能否分开看？
- [ ] 多租户场景下，单租户的批量任务会不会影响其他租户的 P99？
- [ ] 「这个向量由哪份数据、哪个模型、哪个版本产出」能否用一条查询回答？
- [ ] 是否定期做全量重建演练？重建耗时是否仍在 SLA 窗口内？

### 3.8 小结

> 本表阈值的档位沿用 3.3 / 3.6：向量规模与延迟为情景阈值【经验】，1000 万 / 1 亿 / 10 亿三条规模线的【推算】见 [§ 7.5](02-vector-lake-section-7-sec7.md)。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 向量数在单机内存内、要毫秒级【经验】 | 内存向量库 | 跳转代价 ≈ 跳数 × 内存随机访问；代价是内存线性增长且构建期需余量 |
| 十亿级【经验】、成本敏感、内存装不下 | SSD 向量库（DiskANN） | 内存只放导航、SSD 按块读；代价是 P99 被盘延迟与 IOPS 锁死 |
| 十亿级以上【经验】、需要弹性 | 存算分离向量湖 | 无状态计算 + 不可变段；代价是缓存命中率决定 P99、删除靠合并回收 |
| 强标量过滤 + 需要 JOIN | Lakehouse + 向量列 | 过滤前移成裁剪，向量与标量同快照；代价是索引随版本演进而非一等结构 |
| 峰值不可预测 / 无运维团队 | Serverless 向量 DB | 无状态节点可缩到零；代价是冷启动尾部与持续高负载时单价更高 |
| 数据不能搬（合规 / 跨组织） | 联邦向量查询 | 不搬数据也能查；代价是超取 M × K′ 与 P99 由最慢分支决定 |

> 本节小结：向量湖的模式选择，最终由**「索引结构驻留在哪一级存储介质」**这一条约束决定——它同时决定了延迟下限、成本曲线的形状与扩容收益的来源；版本化（换模型怎么办）与过滤位置（召回是否还成立）是在这条确定之后才展开的次级选择，而 Serverless 与联邦查询改变的分别是**谁承担容量风险**与**数据能不能搬**，不改变介质这条主线。
