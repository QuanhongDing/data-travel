## 7. 与其他方法对比

### 7.1 先立判据：为什么「性能 5 分 / 限流 2 分」这类表会误导

打分表把「能力」当成网关产品的固有属性。可在数据 API 网关里，绝大多数能力的上限不由产品决定，而由**网关能看见多少上下文**决定。Kong、APISIX、Envoy 都能实现令牌桶；差别不在算法，而在它们能否看见「这次请求扫描了 30 亿行」。看不见，就限不住慢查询；看不懂查询里的谓词，就做不了行级权限。于是同一款网关在「按请求数限流」这一格是满分，在「按资源量限流」这一格是零分——**分数取决于你让它看什么，而不是它是什么**。

打分表还把**场景相关的结论伪装成绝对结论**。部署复杂度在小规模时是第一判据，在万级 API 且对外多租户时权重趋近于零：此时约束已经换成「越权必须语法上不可达」，上线快一天没有任何意义。同理「AI 集成」这一格在 2024 年之前对任何网关都是伪命题——不是网关做不到，而是那时还没有合格的调用方（[§5.2.1](07-data-api-gateway-section-5-ai.md) 已论证：Agent 出现后，接口边界的形状才从「路径」变成「能力 + schema」）。

因此本章不用分数，用**能被证伪的判据**。判据的共同要求是：它必须指向某个机制，而不是某种印象。「性能」不是判据——它会被缓存、被后端、被跨区网络往返支配，与网关选型关系很弱；「网关能看见什么、策略在哪一层执行、限流计什么、账本主键是什么」才是判据。

打分表的第三个问题是**把不同族的候选放进同一张表逐格打分**。转发族与协议族在没有共同判据的维度上被强行比出高低，读者会据此得出「AI Gateway 的数据权限比 Envoy 强」这类结论，而真实关系是：Envoy 可以承载数据权限（如果有人在它的过滤器链里写改写器），AI Gateway 也可以只管 Token 计量（如果只把它当 LLM 出口）。**跨族比较只有在判据落到「执行单元能否承载判据」这一条上才有意义**。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 能力边界 | 它**看不见**什么（而不是它支持哪些插件） | 看不见查询语义，就限不住扫描量、做不了行级权限；这一条决定它在架构里是负载均衡器还是数据网关 |
| 成本结构 | 成本随什么增长：请求数、扫描量、常驻组件数，还是策略份数 | 数据网关的主导成本通常在后端计算（∝ 扫描量）而不在网关自身；判错主导项会在成本上放过一个数量级 |
| 机制契合度 | 它的执行单元（插件链 / 过滤器链 / Sidecar / 编译期改写）能否承载我的判据 | 执行单元承载不了判据时，能力只能靠「在别处再实现一遍」补，而多实现一份就是多一个漂移源 |
| 运维复杂度 | 常驻组件数、策略副本数、一次改动的回归范围 | 网关是所有流量的公共资源池，它的发布回归范围等于全站调用方；这一条决定团队敢不敢在白天发版 |
| 生态与锁定 | 策略定义在哪一层：绑产品（插件 DSL）、绑引擎（SQL 方言），还是绑资产 | 权限规则绑在引擎上，换引擎就要重建一套并必然漂移（[§6 阿里案例](07-data-api-gateway-section-6-sec6.md)）；绑在资产层才能一套规则多引擎复用 |
| 演进风险 | 项目活跃度 + 协议面是否在变（HTTP → 工具 / MCP、请求计量 → 资源计量） | 协议面变化会改变「网关该管什么」；选一个不能在不重启进程的情况下更新策略的产品，演进风险会直接落在可用性上 |

还有一条不属于判据、但决定判据是否成立的前提：**出口是否唯一**。§3.1 已论证，所有治理措施都建立在「访问经过同一个点」上；出口不收敛时，下面所有比较的收益按出口比例打折。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 反向代理（Nginx / HAProxy） | 通用入口转发 | 只看得懂 HTTP：路由、TLS、连接与请求级限流 | 入口尚未数据化、还没出现治理诉求的团队 | 开源 + 商业版，协议以各项目仓库为准 |
| ESB（企业服务总线，SOA 时代） | 服务编排与协议转换中枢 | 以中心化中介承载消息路由、格式转换与流程编排 | 2000 年代的企业集成项目与存量系统 | 厂商商业产品，授权方式各异 |
| Kong | 插件式 API 网关 | 基于 OpenResty 的插件链，策略以插件为单位装载 | 需要统一鉴权 / 限流 / 计量的 API 平台 | 核心开源（Apache-2.0 系）+ 商业版 |
| Apache APISIX | 云原生 API 网关 | 插件链 + 由 etcd 承载配置，策略动态下发 | 云原生且配置变更频繁的团队 | Apache-2.0 |
| Tyk | API 管理与网关 | Go 实现的网关 + 管理面（密钥、配额、开发者门户） | 需要自建 API 门户的团队 | 开源 + 商业版，协议以仓库为准 |
| Traefik | 云原生反向代理 | 从编排系统自动发现路由，配置跟随声明式定义 | 集群入口的默认选择 | MIT |
| Envoy | 高性能代理（数据面） | 过滤器链 + xDS 类动态配置，控制面与数据面分离 | 需要动态下发与统一东西向治理的平台 | Apache-2.0 |
| Istio | 服务网格（控制面） | 以控制面统管 Envoy 数据面，策略在网格内统一下发 | 微服务多、要统一 mTLS 与重试策略 | Apache-2.0 |
| Ambassador（基于 Envoy 的集群入站网关） | 南北向入口 | 把 Envoy 的过滤器链封装成声明式资源配置 | 集群上要自助发布 API 的团队 | 开源 + 商业版 |
| 自研数据网关 | 数据语义网关 | 在转发链里解析查询、改写谓词、编译期注入权限与租户约束 | 多引擎 + 多租户的数据平台（[§6](07-data-api-gateway-section-6-sec6.md) 的字节 / 阿里 / 美团 / 某 SaaS 都属这一族） | 自建 |
| AI Gateway（Kong AI 插件 / Portkey / Cloudflare AI Gateway） | LLM 调用的统一入口 | 在网关层做多模型路由、Token 计量、凭证托管与回退 | Agent / LLM 应用已进入生产的团队 | 开源与商业并存，以各产品文档为准 |
| MCP 网关 | Agent 工具入口 | 以「能力名 + 参数 schema + 权限范围」注册工具，统一鉴权与计量 | 把数据能力开放给 Agent 的团队 | 规范公开发布，以官方规范页为准 |
| GraphQL Gateway（Apollo / Hasura 等） | 字段级取数入口 | 由网关承担联邦解析与批量取数，接口数量不随字段组合增长 | BI / 前端字段组合多变的团队 | 开源 + 商业版 |

【公开】上述项目的公开时间线：Nginx 于 2004 年首次公开发布；Kong 于 2015 年开源并基于 OpenResty（主文件 §1.4 已述）；Apache APISIX 于 2019 年进入 Apache 孵化器、2020 年成为顶级项目；Envoy 由 Lyft 于 2016 年开源，Istio 于 2017 年发布；Model Context Protocol 由 Anthropic 于 2024 年公开开源，规范以带日期版本号发布。以上均可按各项目官方站点、代码仓库或规范页核验；**项目的版本、许可与功能清单持续演进，请以官方文档当前版本为准**。

这 13 个候选其实分 4 族：**转发族**（Nginx / HAProxy / Traefik）、**策略族**（Kong / APISIX / Tyk，加上自研数据网关）、**网格族**（Envoy / Istio / Ambassador——Ambassador 的数据面就是 Envoy）、**协议族**（AI Gateway / MCP 网关 / GraphQL Gateway）。ESB 是策略族的历史前身，今天更多以「厂商集线器」的形态存在于存量系统。分族依据只有三条：执行单元（转发 / 插件 / 过滤器链 / 协议适配）、配置生效方式（文件重载 / 动态下发）、能看见的上下文（HTTP / 查询 / 工具 schema）。同族内部差异小，跨族差异大——**先分族再选，能省掉一半比较**。

ESB 留在表里是为了一个具体判断：它的失效不是「性能不行」，而是**把编排逻辑放进了一个跨所有业务共享的中介**——中介里每加一条流程，所有接入方都要跟着回归。今天用「网关 + 服务内编排」替代它，并不是换了个更快的产品，而是把「谁负责这条流程」从共享中介挪回了业务侧。判定方法：如果你的网关里已经出现「如果指标 = GMV 则转 A 否则转 B」这类分支，你正在自建一个小型 ESB，而它的回归范围等于全站。

自研数据网关单列成族，是因为它和其他候选不是同一个选择维度：前 3 族是「买什么产品」，自研是「把多少数据语义搬进这层」。它与策略族共用代理骨架（很多自研网关直接以 Envoy 或 Nginx 作数据面、自己写控制面与改写器），差别全在控制面里那个改写器上。

读这张表的方式：**「核心机制」一列是唯一可比较的列**，其余四列只是定位辅助。同一个机制描述出现在多行时（例如 Kong 与 APISIX 都是插件链），说明它们在本文的判据体系里是同类，二者的差别（语言、配置存储、生态）应当用你团队的技能栈去决定，而不是继续在架构维度上比较——那属于选品，不属于选型。

### 7.3 机制差异：为什么它们表现不同（核心节）

下面 4 个机制维度回答同一件事：**这个差异由什么机制导致，因此必然导出什么性质，代价是什么**。读法建议：先看每个维度的「机制是什么」一句，再看「实现差异」表——表里的行是候选，列是同一件事的不同做法；如果某一列在你的场景里根本不存在（例如没有多租户），这一维度对你就没有区分力，可以直接跳过。

#### 7.3.1 治理点在哪一层：数据面能看见什么，策略就只能在哪一层生效

**机制是什么**：网关由**数据面**（转发并执行策略）与**控制面**（把策略下发到数据面）构成。一条策略能否被执行，前提是数据面上存在它所需要的判据。

**它在各候选中的实现差异**：

| 候选 | 执行单元 | 配置生效方式 | 数据面能看见的上下文 |
| --- | --- | --- | --- |
| 转发族（Nginx / HAProxy / Traefik） | 配置里的路由与上游定义 | 改文件 + 重载（Traefik 可跟随编排声明） | HTTP：路径、方法、头部、连接 |
| 策略族（Kong / APISIX / Tyk） | 插件链，**顺序即语义** | 控制面或 etcd 动态下发（以各项目文档为准） | HTTP + 插件自己解析出来的东西 |
| 网格族（Envoy / Istio / Ambassador） | 过滤器链 | xDS 类协议动态下发，控制面与数据面分离 | HTTP/gRPC + 连接级元数据 |
| 自研数据网关 | 编译期改写（查询改写器 + 约束注入器） | 随策略仓发布，能力可覆盖全局 | 查询语义：表、列、谓词、租户列 |

**由此必然导出的性质**：

- 因为转发族的判据只来自 HTTP 层，所以它可以被放在任意流量前面而不需要理解业务——**代价是它对「这次请求扫了 30 亿行」与「调用方只能看自己租户的行」完全无感**，这两件事只能下沉到每个数据服务里各实现一遍，而「多实现一份」的结局是策略漂移（§3.1）。
- 因为策略族把策略装成插件，所以新增一种治理能力不必改网关内核——**代价是插件顺序即语义**（缓存排在鉴权之前就是越权读缓存），且插件之间传递的上下文成为新的耦合面。
- 因为网格族把控制面与数据面分离、以 xDS 类协议动态下发，所以改一条路由不需要重启数据面进程——**代价是控制面自己成了必须高可用的新组件**，而它的配置错误会瞬间作用于整个网格，缺少「重载失败就保持旧配置」这层保护。
- 因为自研数据网关把改写器放在转发链之后，所以它能做到前 3 族做不到的两件事（按谓词与租户列改写、按扫描量分队列）——**代价是它同时继承了「策略集中在网关」的全部风险**：一次改写器缺陷影响全部 API，且这个缺陷不会以报错的形式出现，而是以「返回了不该返回的行」的形式出现。

**公开证据**：【公开】Envoy 由 Lyft 于 2016 年开源、Istio 于 2017 年发布，官方文档均以控制面与数据面分离为设计起点（可按各自官方文档核验）；【公开】Apache APISIX 于 2019 年进入 Apache 孵化器、2020 年成为顶级项目，其公开架构文档写明配置由 etcd 承载（可按 Apache 官方文档核验）。判定方法：查该产品是否提供「不重启数据面进程即可改策略」的接口，有则是动态下发，没有则每次改策略都在改可用性。

**失效条件**：当治理判据在 HTTP 层不可见时（扫描量、行级权限、Token 计量），转发族「便宜 + 通用」的优点全部反转为「无治理」；此时只装了几个通用插件的策略族并不比转发族更好，差别只在插件市场的规模。

**判定方法**：把你要执行的每一条策略写出来，逐条问「执行它需要看见什么」。只要有一条需要看见谓词或扫描量，这一族候选就必须升级到能改写查询的那一族——这一条判定的结果不受产品功能清单影响。

#### 7.3.2 限流计什么：请求数还是资源量

**机制是什么**：限流算法（令牌桶 / 滑动窗口 / 漏桶 / 固定窗口，主文件 §2.2）只决定**突发怎么被削平**；**计什么**由观测点决定。这两件事经常被混为一谈，结果是「限流做好了」与「资源被吃光」同时成立。

**它在各候选中的实现差异**：

| 观测点 | 表达的量 | 谁需要上报 | 挡得住什么 / 挡不住什么 |
| --- | --- | --- | --- |
| 请求计数（令牌桶等） | 请求个数 | 不需要 | 挡得住高频小请求；挡不住一个大请求 |
| 并发数 / 连接数 | 同时占用的资源单元 | 不需要 | 挡得住连接被打满；挡不住一个连接跑几十秒 |
| 返回行数 / 扫描量 | 资源消耗 | 数据服务或查询引擎必须上报 | 挡得住慢查询；完整性依赖每个后端都上报 |
| 执行前代价估算 | 预估消耗 | 网关需能解析查询 | 在执行之前就能拒绝；估算不准会误拒或漏拒 |
| 调用方总额度（配额） | 一段时间内的累计量 | 不需要（只记请求或资源） | 管得住月度总量；管不住小时级突发，且归因粒度取决于记账单位 |

**由此必然导出的性质**：因为令牌桶计的是请求个数，**所以它对「一个大请求」完全无效**——【推算】推导链是「单次请求的后端成本 ∝ 它处理的数据量」：同一个 API 上两次请求的请求数都是 1，但一次点查只读索引与少量数据页，一次无范围条件的查询要走全表。要把这条定性关系算成数，得先把两个前提写出来：被扫表 N 行、每行百字节量级（10^2 B），点查读取量 P 取 10^4–10^5 B（几十到上百 KB 的索引页加若干数据页），则两者读取量之比 ≈ N × 10^2 B ÷ P。按 10^7 行 ≈ 1 GB 的表代入得 **10^4–10^5**；按 [§3.1](07-data-api-gateway-section-3-sec3.md) 举的极端形态（单个请求扫 30 亿行 ≈ 3 × 10^11 B）代入同一个 P 得 **10^6–10^7**。本节下游引用（7.4、7.5 的阈值）取的是保守的那一端——GB 量级表、相差 4–5 个数量级，因为表越大这个比值只会更大、结论只会更强。写成单值则只对某一张具体的表成立，这就是「限流能力满分」在数据网关里失效的机制原因。

因为按扫描量限流要求执行统计从数据侧上报，所以计量的完整性依赖每个后端都上报——**代价是任何一个后端漏报就是一个不被限流的出口**，而这类出口不会出现在网关自己的访问日志里（§3.5「无网关直接暴露」的一种变体）。

因为「代价」是可以与「优先级」正交的第二个维度，所以把大查询放进独立受限队列（而不是压低它的优先级）能让在线查询有保底资源——**代价是多了一个队列状态机**：排队时长、超时拒绝、队列长度告警都得有人维护，而且这次请求的失败原因从「后端慢」变成「被网关拒绝」，排障路径外移了一层。

**公开证据**：四种限流算法属通用公开知识（[主文件 §2.2](07-data-api-gateway.md) 已列）；「按返回行数 / 扫描量限流」在数据平台属工程实践，无第三方可比口径，故本节不引用任何具体倍数【经验】。判定方法：构造一个返回行数是日常调用两个数量级以上的请求，看它在请求数未超限时是否被拦——拦不住，说明限流对象仍然是请求数。

**失效条件**：当查询都是点查、返回行数有明确上界时，按资源量限流带来的精度提升趋近于零，只剩下上报成本。

**配套的一步是舱壁**：限流决定「进不进得来」，舱壁（按 API / 租户划分并发上限）决定「进来之后能占多少」。只做前者时，一个已获准的慢查询仍可能占满连接池；两者一起配，资源事故才有上界。

#### 7.3.3 权限在哪一层执行：改写下推还是后置过滤

**机制是什么**：行级 / 列级权限只有两个可能的位置——**进查询**（改写成条件并随查询下推到引擎执行）或**出结果**（先取回再由网关裁剪）。

**它在各候选中的实现差异**：

| 位置 | 谁保证不漏 | 越权数据是否离开引擎 | 对网关的要求 |
| --- | --- | --- | --- |
| 应用层各自实现 | 每一个接口的实现者 | 会（先取回再过滤） | 无要求 |
| 网关后置过滤 | 网关这一处 | 会（全量取回后裁剪） | 能解析结果集 |
| 网关改写下推 | 改写器（强制注入，缺失即拒绝） | 不会 | 理解查询语义 + 租户列 + 引擎方言 |

**由此必然导出的性质**：因为改写下推把权限变成查询的一部分，**所以「忘了过滤」在结构上被消除**（前提是改写器强制注入、注入后仍缺条件即拒绝执行）——**代价是网关必须同时理解查询语义与后端引擎方言**，这份理解随引擎种类增长而维护，`引擎数 × 方言变更频率` 就是它的维护成本函数。

因为后置过滤只处理返回结果，**所以它对新后端的要求最低、接入最快**——**代价是它必须先取回全量再裁剪**：既浪费扫描（成本回到后端），又让越权数据已经出过一次引擎；更要命的是它只保护走这条路的调用，任何一个旁路出口（导出任务、直连、交给 Agent 的库凭证）都会让整套措施归零。

因为列级脱敏与行级权限共用同一个注入点（都是「在查询或结果上按身份做变换」），**所以把它们放在一起做最省事**——**代价是两种变换的失败模式被绑在一起**：脱敏是「该遮的没遮」，越权过滤是「该挡的没挡」，一旦注入器逻辑写错，两类事故会同时发生，而它们在监控上的表现完全不同（前者数据看着正常、后者数据看着偏少）。

**公开证据**：[§6](07-data-api-gateway-section-6-sec6.md) 里把权限做成「编译期注入 + 下推」的是三个案例，不是全部四个：字节以「权限与谓词条件下推」为五个核心组件之一，验收数字写的是「越权数据不出引擎」；阿里把行 / 列级权限编译成查询条件下推，并要求审计可逐条自证；某 SaaS 在编译期强制注入租户约束、注入后仍缺即拒绝执行，验收判据是「越界在语法上写不出来」（三例依次见 §6 的字节 / 阿里 / 某 SaaS 案例小节）。同节的第四个案例（美团）不在此列——它治的是「大查询挤死在线看板」，解法是「查询代价 × 业务优先级」双维分档、受限队列与无范围查询拒绝，全篇没有权限下推或越权不可达的表述；把它算进来，会让这条证据的支持面看起来比实际更宽。所以这里能主张的是「三条独立的生产实践同向」，不是「四个案例都如此」。这三例是工程实践记录，不是第三方 benchmark，不构成性能可比口径。

**失效条件**：单租户、无行级要求时，改写下推的收益为零而成本为正——此时正确做法是停在「鉴权（你是谁）+ 授权（有什么角色）」，不要为架构完整性提前引入改写器。

**判定方法**：用一条查询验证——「这个调用方上一次读到的是哪些行、依据哪条规则」。回答里若只有接口名而没有规则与范围，说明权限还在应用层，网关只是转发。

#### 7.3.4 账本主键：按请求记账还是按资源记账

**机制是什么**：计量单位决定了配额、容量模型与成本归因。账本主键换了，容量模型、配额模型与异常检测口径都要跟着换（[§5.2.2](07-data-api-gateway-section-5-ai.md)）。

**它在各候选中的实现差异**：转发族与策略族默认记请求数与状态码；数据网关记调用方 + API + 数据量；AI Gateway 记 Token 与模型；MCP 网关还要记「这个工具调用代表谁」。四者的差别不是加一个字段，而是换一本书。

**由此必然导出的性质**：因为按请求记账只需要请求元数据，**所以它可以在网关侧近乎零成本完成**——**代价是它无法回答「上季度每个调用方消耗了多少资源」**，而这正是数据网关成本分摊的唯一起点（§3.5「无计量」）。

因为按资源单位（返回行数 / 扫描量 / Token）记账能与后端成本对齐，**所以账单第一次能解释「为什么这个月贵了」**——**代价是网关必须读请求体与响应体**，于是它从「不需要理解内容的转发层」升级为能看见内容的高敏组件，加密、脱敏与留存边界都要重画。

因为调用方从人变成 Agent 后「请求数」与「资源消耗」不再成比例，**所以鉴权主体从 1 个变成 2 个**（谁发起 + 代表谁）——**代价是额度挂在人身上会带来新的博弈**：Agent 超额等于人超额，用户会拆小任务绕过配额，配额机制有变成业务阻碍的风险。

因为审计与计量共用同一份调用记录，**所以「按资源记账」天然带来更完整的审计**（每条记录里已经含了读了哪些字段、代理了谁）——**代价是审计日志本身升级为敏感资产**：它记录的是「谁在什么时候读走了哪些字段」，一份完整的审计库等于一张内网数据地图；同时留痕本身受数据留存与跨境规则约束，留得越全，合规审查越重。

**公开证据**：【经验】主流 LLM 服务在 API 响应中返回用量字段（请求侧与生成侧的 token 各计一个数）：这是各服务商接口层面的通行做法，没有单一权威来源，且各家字段名、计量范围与计费口径并不相同——请以你要接入的那家服务商的 API 参考页当前版本为准，在响应结构的用量字段里核对字段名与单位。【公开】Model Context Protocol 由 Anthropic 于 2024 年公开开源，规范以带日期版本号发布（可按 MCP 官方规范页核验版本与日期）。前者说明「用量已经是接口的一等字段」，后者说明「协议面正在扩展」，两者共同支撑「账本主键向资源单位迁移」这一方向——但单位归一与实时扣减都还没有稳定做法。

**失效条件**：调用方全是人、查询同质且资源消耗差异不大时，资源记账带来的归因精度不足以覆盖它新增的敏感面与故障点。

**这一维度与 7.3.2 的关系**：7.3.2 决定「拦不拦得住」，这一维度决定「账单对不对得上」。两者常被一起改，但它们可以分开落地——先按资源量限流（不动账本），再逐步把账本主键迁到资源单位，是多数团队更现实的两步走；反过来先改账本、限流仍按请求数，则会出现「账单准确但拦不住」的组合。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
总成本 ≈ C_数据面(∝ RPS × 单请求 CPU 开销)
       + C_后端计算(∝ 扫描量 + 返回行数)          ← 数据网关的真主导项
       + C_缓存(∝ 缓存容量 + 一致性维护)
       + C_审计与计量存储(∝ 调用数 × 单条大小 × 留存期)
       + C_运维(∝ 常驻组件数 × 策略副本数 + 一次改动的回归范围)
```

| 族 | 主导成本项 | 隐性成本（不在账单上） |
| --- | --- | --- |
| 转发族 | 数据面 CPU（低） | 每个服务各实现一遍鉴权 / 限流 / 脱敏的代码，随服务数线性增长；无治理导致的事故成本 |
| 策略族 | 插件链的 CPU 与调试成本 | 插件顺序与版本矩阵的维护；策略集中后一次误配影响全部 API |
| 网格族 | 常驻组件（每个工作负载一个数据面）+ 控制面集群 | 团队要能读懂动态配置语义，人力门槛；配置错误的爆炸半径等于全网格 |
| 协议族（AI Gateway / MCP / GraphQL） | 语义解析或模型调用成本（若做智能路由） | 账本分裂（两套计量单位）、工具清单与 API 清单不同步、GraphQL 深查询的成本无法定价 |
| 自研数据网关 | 改写器与权限规则的长期维护（∝ 引擎数 × 方言变更） | 策略集中带来的爆炸半径：一次改写器缺陷影响全部 API，且以「返回了不该返回的行」的形式静默出现 |

下面几条用来判断「钱花在哪」（每条的档位标注在其内）：

- **审计与计量存储**【推算】：按每天 1000 万次调用、每次审计记录 1 KB 推算 → 10 GB/天 → 300 GB/月；单价取公开的对象存储标准层价格 $0.023/GB-月【公开：AWS S3 定价页, 2024（标准层首 50 TB 档，us-east-1；https://aws.amazon.com/s3/pricing/）；价格随区域与时间变化，请以该页当前版本为准】，据此推算 ≈ **$7/月**；若需 90 天在线留存，则 900 GB ≈ **$21/月**。推导链：调用数 × 单条大小 × 留存天数 × 单价。若要对审计做全文索引或按字段检索，成本通常再上一个量级【经验】——这正是「审计覆盖 100%」在有合规要求的场景里要先算一次的原因。
- **后端计算才是主导项**【推算】：推导链是「单次请求的后端成本 ∝ 它处理的数据量」，而 §7.3.2 给出的两端（GB 量级表上的点查 vs 全表扫描，取该节保守的那一端）相差 4–5 个数量级——也就是说，一次无范围条件查询在后端账单上的分量，约等于 10^4–10^5 次点查。把它写成判据：**单次扫描的后端成本 × 这类查询的月频次 > 网关的月常驻成本**（常驻成本只由数据面副本规格、控制面与运维决定，与调用频次无关）。所以拦截的经济性是**频次驱动**的，而不是「拦一次就赚回网关一个月」：这类查询每天都出现时，按资源量限流 + 执行前拒绝是唯一能在后端账单上看到效果的动作；每月只出现几次时，为拦截而升级到能改写查询的那一族，所付的常驻成本反而高于它省下的后端成本。判定方法：先统计无范围条件查询的月频次，再与网关的月常驻成本比一次，别跳过这一步。
- **缓存不是免费的**【推算】：结果集缓存把「每次查询都付一次后端成本」换成「第一次付、之后命中」——**代价是一项恒定成本**（缓存容量与一致性维护），而收益 ∝ 参数重复率。推导链：收益 ≈ 参数重复率 r × 单次后端成本 c × 调用量 − 缓存容量成本；因此 r 低到一定程度时缓存为负收益，而 r 的临界值取决于 c（查询越贵，缓存越值）。判定方法：先统计调用的参数重复率，再决定要不要上缓存——不要反过来。
- **边缘层对冲的是往返成本**：跨区调用每多一次网络往返就多一份延迟（跨大洲往返通常在百毫秒量级【经验】；实际值随路径与运营商变化，需自行测量），边缘缓存与就近回退能消掉重复请求的这部分成本——**代价是缓存键必须含身份 / 租户维度**，键错了它就从成本优化变成越权通道，且不报错。
- **运维成本与流量的关系很弱**：网关的常驻人力大致与「策略份数 × 引擎数」同向，与 QPS 同向的程度低得多【经验】——这正是「按流量规模选网关」最常选错的原因：决定运维负担的是你有多少种策略、跨几个后端，而不是每秒多少请求。

【经验】多数单体或单团队场景在 API 数量数十、只有一个产品线时，用转发族或集中式策略族就已足够；跨到 3 个以上团队、100+ API 后，「策略各写一份」的维护成本会超过网关自身的部署成本。这个区间随组织形态变化，不要当成硬阈值使用。

成本函数里还有一类容易被忽略的**固定项**：多可用区部署、控制面高可用、证书与域名体系、灰度与回切能力。它们与流量无关，但有外部调用方或 SLA 承诺后就必然存在。判断方法：把成本表里的「随流量增长」各项都设为 0，剩下的那部分是否仍能接受——不能接受，说明这套方案的门槛在固定成本，而在规模上继续优化没有意义。

### 7.5 决策树（每个分支都要有阈值依据）

```
[① 所有数据访问是否已收敛到同一个入口？]
   │
   ├─ 否 → 先收敛出口（此阶段网关能力等于零），回到 ①
   │
   └─ 是 ↓

[② 调用方可枚举吗（内部账号 / 可实名）？]
   │
   ├─ 否（对外开放或客户自带账号）→ 边缘层（WAF + 限流）前置
   │
   └─ 是（内部可枚举）→ 不必前置边缘层，走网络层放行规则
   │
   ↓（② 的两条分支都进入 ③）

[③ 单请求资源消耗是否与请求数脱钩？]
   │
   ├─ 否（点查为主、返回行数有上界）→ 策略族，按 API / 调用方分档令牌桶
   │
   └─ 是（存在大结果集 / 扫描类查询）→ 必须补「按资源量限流 + 按代价分队列」
   │
   ↓（限流对象在这一步确定；两条分支都继续，④ 及之后与 ③ 的答案无关）

[④ 是否存在「同一张表不同调用方只能看到子集行」的需求？]
   │
   ├─ 否 → 权限止于鉴权 + 角色授权
   │
   └─ 是 → [⑤ 越权是否必须「语法上不可达」（涉对外客户 / 监管举证）？]
            │
            ├─ 否（内部、可人工复核）→ 自研数据网关：改写下推
            │
            └─ 是 → 自研数据网关：编译期强制注入 + 缺失即拒绝
   │
   ↓

[⑥ 调用方里有 Agent 吗（存在非人主体发起调用）？]
   │
   ├─ 否 → 账本主键 = 请求
   │
   └─ 是 → 账本主键 = 资源单位（行数 / 扫描量 / Token）+ 主体（代表谁）
            → 协议族（AI Gateway / MCP 网关）与传统网关融合，共用一本账
   │
   ↓

[⑦ 是否需要东西向（服务间）治理？]
   │
   ├─ 否 → 只做南北向：入站网关
   │
   └─ 是 → 网格族（Envoy / Istio）管东西向，入站仍由数据网关管南北向
```

**阈值依据**（与树上 ①–⑦ 一一对应）：

- **① 出口是否唯一**：这是前提条件而非成本判断。依据来自机制：所有治理措施都建立在「访问经过同一个点」上，每多一个出口，网关上的全部工作被稀释一次（§3.1）。判定方法：能否列出所有绕过网关直达后端的网络路径；有一条就说明还不该比较网关产品。
- **② 调用方可枚举**：边缘层的成本是固定的（常驻组件 + 规则维护 + 证书体系），只有当攻击面不可枚举时它的期望收益才为正；内部可枚举的调用方改用网络层放行规则的边际成本更低【经验】。判定方法：调用方是否都为你能逐一列举与吊销的内部账号。
- **③ 资源消耗是否与请求数脱钩**：来自 §7.3.2 的推导——后端起主导成本的是扫描量，而令牌桶约束的是请求数；两者相差一个数量级时按请求数配限流尚能约束总量，相差 4–5 个数量级（§7.3.2 的 GB 量级表一档）时它几乎没有约束力。判定方法：看单请求返回行数或扫描量的 P99 与中位数之比，而不是看 QPS 曲线。
- **④ 是否存在行级权限需求**：改写下推的维护成本 ≈ 引擎种类 × 方言变更频率（§7.3.3）；只有存在「同表不同行」的需求时，这份成本才有对价。判定方法：问业务「有没有哪两个调用方查同一张表但应看到不同行」，答不出就不需要。
- **⑤ 越权是否必须语法上不可达**：编译期强制注入的额外成本主要是流程成本（任何新接口都要过改写器）；在内部可人工复核的场景里，评审能覆盖大部分漏写；在对外多租户场景里一次漏写即数据泄露，其期望损失远高于流程成本【经验】。判定方法：是否存在外部客户或需要向监管逐条举证的场景。
- **⑥ 是否含 Agent 调用方**：账本主键从「请求」换成「资源单位 + 代表谁」，代价是网关要读内容、加密与脱敏边界要重画（§5.2.2）。只有当非人主体已进入生产、且其调用量与资源消耗明显不成比例时，这笔代价才值得付。判定方法：计量日志里能否区分「人调用」与「代表某人的工具调用」。
- **⑦ 是否需要东西向治理**：网格族的常驻成本 ∝ 工作负载数量（每个工作负载一个数据面），这项成本只在服务数量到了量级时成立；入站网关的常驻成本 ∝ 副本数，与业务规模无关。判定方法：是否已出现「每个服务各自实现重试 / 超时 / mTLS 且无法维持一致」的症状。

这 7 个节点不是并列的勾选项，而是有先后：①②③ 决定「要不要数据网关、以及要哪一族」，④⑤ 决定「权限放在哪一层」，⑥⑦ 决定「账本与东西向怎么接」。任一条答错，后面的选择都是在错误前提上做优化——最常见的误判是跳过 ① 直接讨论 ②③，结果买了一款功能齐全的网关，而它管不到真正花钱的那部分流量。

反向用法同样有用：**当有人主张「我们该上一个网关」时，用 ①–③ 去问**——出口数得清吗、调用方可枚举吗、单请求的资源消耗与请求数成比例吗。三问都不是，说明问题不在网关，而在访问路径本身失控；此时引入网关只是给失控的路径加了一层更贵的转发。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单产品线、数十 API、团队 2–3 人 | 集中式策略族（Kong / APISIX / Tyk） | 反向代理 + 服务内自实现 | 反向代理看不见数据语义，治理会散落到每个服务 |
| 对外开放、调用方不可枚举 | 边缘层（WAF + 限流）+ 数据网关 | 只上集中式网关 | 不可信流量进入共享资源池，一次爬取打满全部 API |
| 多引擎 + 多租户、要求越权不可达 | 自研数据网关（编译期注入 + 下推） | 策略族 + 应用层过滤 | 应用层过滤必然漏，且事后无法证明全覆盖 |
| 微服务多、语言栈杂、需东西向治理 | 网格族（Envoy / Istio）管东西向 | 把数据权限也塞进 Sidecar | Sidecar 看不到数据语义，权限实现会发散到 N 个服务 |
| 字段组合多变、接口数量按组合增长 | GraphQL Gateway | 继续扩 REST 端点 | 端点数量随组合而非业务域增长，治理对象失控 |
| Agent 与人共用同一批数据服务 | 传统网关 + AI Gateway / MCP 网关融合 | 让 Agent 直连数据 API | 两套入口 → 两本账，Agent 用量无法归因到人 |
| 只有一个后端引擎、权限止于角色 | 反向代理 + 服务内鉴权 | 过早引入改写器 | 改动本已可见，改写器只增加维护面而无新判据 |
| 已有集群内的服务网格，只缺数据治理 | 网格族管东西向 + 薄的数据网关层 | 把数据权限写进 Sidecar 配置 | 权限会发散到 N 个服务，且没有一处能回答「这个人能看到什么」 |

组合不是「都装上」，每一件都要有明确职责边界（下面 5 条组合要点，一项未删，补齐每条的分工与运维代价）：

- **网关 + OneService**：OneService 负责「数据语义 API」（口径、指标、维度），网关负责「流量治理」（鉴权限流、脱敏、计量）。职责边界是「谁定义口径、谁执行策略」；运维代价是两者要共用同一份资产与权限定义，否则 API 层的口径与数仓层会分叉。
- **网关 + 数据目录**：目录做元数据治理（有哪些资产、谁负责、是否含敏感字段），网关做运行时治理（谁在什么时候取走了哪些字段）。职责边界是「静态元数据 vs 运行时流量」；运维代价是两侧的字段标识必须能对齐，否则「目录说这张表有 PII」无法变成「网关拦下这次取数」。
- **网关 + Service Mesh**：网关管南北向（外部到数据），Mesh 管东西向（服务到服务）。职责边界是「是否来自外部、是否能看数据」；运维代价是两套策略体系并存，规则写错位置的表现是静默不生效。
- **网关 + AI Gateway**：传统 API 与 Agent 工具调用统一鉴权、计量、审计。职责边界是「协议面不同、账本一本」；运维代价是计量单位要在请求数 / 行数 / Token 之间归一，且工具清单要与 API 清单对齐（§5.2.1 的「两套清单」问题）。
- **网关 + WAF + CDN**：CDN 做边缘缓存与就近接入，WAF 拦已知攻击模式，网关做数据级策略。职责边界是「越靠外越看不懂数据语义」（§3.2.2 的「每层只用自己看得懂的上下文」）；运维代价是**边缘缓存键必须含身份 / 租户维度**，不含就是越权通道，且这类问题不报错。

这 5 条组合的共同点是：**每加一件，就多一处必须与别处对齐的状态**（边缘缓存键与身份维度、目录的字段标识与网关的字段标识、两套计量单位、两套策略体系的归属）。因此组合的代价不体现在部署上，而体现在**一致性校验**上——凡是没有自动校验的组合，半年后都会出现两套规则各自为正的情况。判定方法：能否用一条查询同时回答三件事——「这个字段在目录里的标注是什么」「这个调用方能不能读它」「上一次是谁读的」。答不出，说明组合还只是并列部署，不是组合。

### 7.7 选错的代价与迁移成本

**反模式：把网关当选型终点，而不是当收敛结果的副产品** —— 症状是先选一款网关产品，再回头想办法把所有访问塞进去，于是导出任务、直连查询、交给 Agent 的库凭证长期留在网关之外 → 后果是网关上的治理被按出口比例稀释，且**事后无法证明「所有访问都经过了网关」**（§3.5 第一条反模式） → 正确做法是先收敛出口（网络层只放行网关网段 + 存量调用方分批迁移），再比较产品。

**反模式：把数据权限做成后置过滤** —— 症状是网关或应用在结果集上裁剪行与列，权限规则散落在 N 个接口里 → 后果是越权数据已经出过引擎、全表扫描的成本已经付过，而聚合类接口（返回汇总数字的）最容易整条漏掉 → 正确做法是把权限编译成查询条件下推，并以「构造一个不含权限条件的查询」作为验收用例。

**反模式：用请求数限流去管一个扫描型负载** —— 症状是限流阈值配得很严、QPS 曲线也很平，但后端偶尔被单个查询打满 → 后果是容量模型失真，故障归因指向「后端不稳」而不是「某一次查询」 → 正确做法是补一层按返回行数 / 扫描量的限流，并把无范围条件的查询在执行前拒绝。

**反模式：为了「统一」把所有治理塞进网关，包括业务分支** —— 症状是网关配置里出现按指标名或按客户定制的分支，改业务要先发网关 → 后果是网关的发布回归范围扩到全站调用方，发布窗口越来越长，最后没人敢在白天发网关（§3.5「网关做业务逻辑」） → 正确做法是用「这条规则能否由不熟悉业务的平台同学解释清楚」作判据，不能就下沉回服务。

换成另一个方案要动什么（量级是相对比较，不是工期承诺）：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 转发族 → 策略族 | 无 | 无 | 中：把散落在各服务的鉴权 / 限流下线，策略集中到一处 | 低–中：插件配置与顺序语义 |
| 策略族 → 自研数据网关 | 无 | 有：所有查询要经过改写器，历史查询模板要回归 | 高：改写器与引擎方言绑定，需长期维护 | 高：要同时懂查询语义与权限模型 |
| 集中式 → 分层（边缘 + 数据） | 无 | 无 | 中–高：两处规则要能按同一请求 id 串联排障 | 中：要清楚每条规则该写在哪一层 |
| 请求数限流 → 资源量限流 | 无 | 无 | 中：需要后端按约定上报执行统计 | 低：理解「限流对象换了」 |
| 单租户 → 多租户编译期约束 | 视表结构而定（共享表需加租户列） | 有：历史靠应用层过滤的接口要逐一切换 | 高：越界校验成为发布链路的一环 | 中：租户模型与审计要求 |
| 传统网关 → 传统网关 + AI Gateway / MCP | 无 | 无 | 中：账本要能同时记请求数与资源单位 | 中–高：工具清单与 API 清单的对齐机制 |
| 转发族 → 网格族 | 无 | 无 | 高：引入控制面 + 每个工作负载一个数据面，两套策略体系要划界 | 中：动态配置语义与排障方式都变了 |
| 后置过滤 → 改写下推 | 无 | 有：历史查询模板要逐条回归 | 高：改写器必须覆盖全部引擎与方言 | 中–高：要同时理解查询语义与权限模型 |

这张表里最容易被低估的是「策略族 → 自研数据网关」的团队再学习一列：改写器要求同一个人既懂查询语义又懂权限模型，而这个组合的人力并不常见。多数团队的真实路径是先在某个数据服务里做改写、被复用到第三处时才把它抽出来做网关——反过来说，**如果一段改写逻辑至今没有第二次重复出现，它还不该进网关**。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 访问还没收敛到单一入口 | 先做出口收敛，别选产品 | 治理的收益与出口数量成反比；此时任何网关能力都被打折 |
| 调用方全是内部可枚举账号 | 集中式策略族 + 按 API 分档限流 | 判据都在 HTTP 层可见，转发/插件就够了 |
| 有扫描型查询与对外调用方 | 边缘层 + 按资源量限流 + 无范围查询拒绝 | 主导成本是扫描量，令牌桶管不住它 |
| 多租户 / 需要对外举证 | 编译期注入权限与租户约束并下推 | 「忘了过滤」被结构性消除，且审计可逐条自证 |
| 服务多、要东西向治理 | 网格族管东西向，数据网关管南北向 | 每层只用自己看得懂的上下文，别让 Sidecar 做数据权限 |
| Agent 已进入生产 | 融合网关：协议面两种、账本一本 | 账本主键不换，Agent 用量就无法归因到人 |
| 只有一个后端引擎、权限止于角色 | 反向代理或集中式策略族，权限停在身份层 | 判据都在 HTTP 层可见，改写器只增加维护面 |
| 有外部客户、且要逐条举证 | 编译期注入 + 全量审计 | 审计与隔离都在执行之前完成，事后补救无法作为依据 |

> 本节小结：这些候选之间唯一真正起决定作用的差异，是**网关在执行的时刻能看见多少上下文**——看得见查询语义，就能把权限编译进查询、把限流改成按扫描量计；看不见，就只能做转发与鉴权，其他一切能力都要下沉到每个数据服务里各写一遍。产品、语言、部署形态的差异都是这条差异的下游；而「出口是否唯一」是这条差异能否发挥作用的前提。
>
> 💡 **思考锚点**：先答一个前提——你的所有访问出口是不是已经收敛到唯一入口？没收敛，本节任何网关能力都要先按被绕过比例打折。再量第二层：你的限流是按请求数还是按扫描量配的——一个没有范围条件的查询打满后端时，你那根很平的 QPS 曲线看得出来吗？
