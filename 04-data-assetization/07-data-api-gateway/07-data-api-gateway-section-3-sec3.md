## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

网关的模式分野根本不是「集中还是分散」，而是**网关这一层能看见什么上下文**。通用 API 网关看见的是 HTTP：一次请求、一个响应、一个状态码。数据 API 网关要处理的却是「这次请求扫描了 30 亿行」「调用方只能看自己租户的行」「返回的 phone 字段必须脱敏」——这些判断**在 HTTP 层面根本不存在**。所以本主题下所有模式选择的第一个约束是：**你打算把多少数据语义搬进网关**。搬得越多，网关越像数据服务（能限流到行、能改写下推权限），也越贵、越难升级、越容易变成业务逻辑的垃圾场；搬得越少，网关越像负载均衡器，便宜通用，但数据治理只能下沉到每个 API 各自实现。

第二个约束是**故障域**。数据查询是长尾的：P50 可能几十毫秒，P99 可能几十秒（取决于扫描量与后端排队）【经验】。这决定了「一个慢查询拖垮整个网关」不是理论风险，而是默认结局——除非把线程/连接/并发从「按请求数」管到「按扫描量」管。集中式网关把这条约束放到最大：所有 API 共享同一个资源池，一个坏 API 的坏查询可以吃掉整个池子。

第三个约束是**策略的一致性 vs 演进的自由度**。所有策略集中在网关，意味着改一次限流规则影响全部 API（一致，但也意味着一次误配影响全部 API）；策略分散到每个服务，意味着每个团队按自己节奏演进（灵活，但半年后同一个用户在不同 API 上看到不同的数据范围）。这两种失败都是真实发生过的，模式选择本质是在这两种失败之间选一个你更能承受的。

第四个约束是**延迟预算**。它决定网关放在边缘前置还是直连后端、结果集缓存落在 CDN 还是网关本身——跨国链路补的那 100ms 网络往返，往往比任何网关内部优化都贵，而想缩短链路就得放弃一部分集中的治理点。

第五个约束是**调用方身份的复杂度**。当调用方是人（BI、报表）时，鉴权就是「你是谁 + 你有什么角色」；当调用方是 Agent 时，它还要回答「这个 Agent 代表谁、它的额度算在谁头上、它的每一次工具调用是否可审计」——身份从一个主语变成两个。

第六个约束是**合规与数据可见性**。脱敏放在网关还是留给应用、审计日志记到字段级还是调用级，取决于网关到底能看见哪些字段——看得见的字段越多，越能把合规收在网关这一层。

还有一个容易被漏掉的约束：**出口数量**。数据治理的所有措施都建立在「所有访问都经过同一个点」这个前提上。导出任务、直连查询、数据同步、Agent 拿到的数据库凭证——每多一个出口，网关上的全部工作就被稀释一次。这一条不是模式选择的问题，而是模式能否生效的前提：**先收敛出口，再谈模式**。

约束先立清楚，下面的模式才读得懂。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 网关能看见的上下文 | 是只做 QPS 限流，还是要按「扫描量 / 返回行数」限流、按行级列级改写下推 | 「网关不需要懂 SQL」——不懂 SQL 就限不住慢查询，也做不了行级权限 |
| 故障域与资源池 | 单池共享还是按 API / 租户隔离；是否需要并发舱壁 | 「限流做好就不会被拖垮」——限的是请求数，吃资源的是扫描量 |
| 策略一致性 vs 演进自由度 | 策略集中在网关，还是下沉到各服务 | 「集中在网关 = 更安全」——一次误配全站生效，与单点故障等价 |
| 延迟预算 | 边缘前置还是直连；缓存放在 CDN 还是网关 | 「链路越短越快」——跨国调用补 100ms 网络往返，比任何网关优化都贵 |
| 调用方身份（人 / 服务 / Agent） | 鉴权协议与计量单位（调用次数 / 行数 / Token） | 「Agent 就是一个 API 客户端」——它需要一个能被授权也能被追责的主体 |
| 合规与数据可见性 | 脱敏放在网关还是应用；审计日志的粒度 | 「应用层脱敏就够了」——只要有第二个出口，脱敏就等于没做 |

### 3.2 模式逐个拆解（核心节）

下面 6 个模式按「治理发生在哪一层」排序：集中式把一切收进一个进程，分层式按能看见的上下文切开，Sidecar 把治理搬进每个业务 Pod 的旁边，边缘式把一部分判断推到离用户最近的地方，AI Gateway 融合式改变的是计量单位与鉴权主体，GraphQL 式改变的是「一次请求」的边界。盯住同一个问题：**这个模式下，策略在哪里被执行**。

#### 3.2.1 集中式网关

**被什么约束逼出来**：API 数量还没到需要分域管理的规模，但「每个服务各自实现鉴权/限流」已经造成了实现不一致——需要一个唯一的策略执行点。

**结构**（一个入口，一条插件链）：

```text
                  ┌─────────────── 网关集群（无状态，可水平扩） ───────────────┐
调用方 ──► 入口 ──┤ ① 身份认证(API Key/JWT) ② 限流 ③ 结果集缓存              │──► 数据 API 服务池
                  │ ④ 超时/熔断 ⑤ 计量埋点 ⑥ 访问日志                        │
                  └──────────────────────────────────────────────────────────┘
   ▲ 所有策略只写一遍、只升一次级；插件顺序即处理顺序（缓存命中则不落后端）
```

**为什么这样设计有效**：因为策略只存在于网关这一个进程里，所以「同一个用户在不同 API 上被同等对待」是结构保证而不是流程约定；因为网关无状态，扩缩容只是加副本，不需要迁移任何业务数据。

**代价**：网关成为**所有流量的公共资源池**。一个 API 的慢查询占满连接/线程后，其他 API 一起变慢——故障从「某个 API 挂了」升级为「网关挂了」。此外，网关的插件链本身是一段必须被理解、被测试、被升级的代码：每加一个策略就加一层顺序依赖，插件顺序写错（例如缓存放在鉴权之前）会直接造成越权读缓存。

**失效点**：当后端出现「返回行数极大但请求数很小」的查询时，按 QPS 配的限流完全不起作用，因为**限流计的是请求而不是资源消耗**——一个请求可以扫 30 亿行、拖住一个连接几十秒。此时集中式网关的「策略统一」优点会反转成「风险统一」。

**真实使用**：【公开】Kong（2015 年开源）、Apache APISIX（2019 年开源）是这类网关的常见实现（主文件 §1.4 已述）。某个数据中台是否采用集中式，判断方法：看它对外是否只有一个 API 域名、以及限流配置是写在网关侧还是各服务侧。

#### 3.2.2 分层网关（边缘 / 内部 / 数据）

**被什么约束逼出来**：单一网关要同时照顾「抗 DDoS」「服务间路由」「数据权限」三类完全不同的判断，而这三类判断依赖的上下文各不相同——混在一起后，任何一次改动都要重新验证全部场景。

**结构**（按能看见的上下文切三层）：

```text
边缘网关（南北向入口）
  · 只做与业务无关的事：TLS 卸载 / WAF / 全局限流 / 身份初步校验
  · 不认识「表」「字段」「行」——它不解析数据语义
        │
内部网关（服务间与灰度）
  · 路由与灰度、服务发现、协议转换（HTTP → gRPC）、超时与重试
        │
数据网关（数据语义层，本主题重点）
  · 行级 / 列级权限：改写下推（把 WHERE tenant_id = ? 注入查询）而非只写 header
  · 按「返回行数 / 扫描字节数」限流与配额
  · 结果集缓存与物化视图命中
  · 数据脱敏：敏感字段在出网关前替换
关键：分层的依据不是「安全性递增」，而是每层只依赖自己能看懂的上下文
```

**为什么这样设计有效**：因为每一层只用它拿得到的上下文做判断，所以边缘层不需要理解 SQL、数据层不需要关心 TLS 与爬虫；一次「调整行级权限规则」的改动被限制在数据层，回归范围因此可控。

**代价**：链路变长（多一跳或多跳转发，每跳都有延迟与失败面），配置面增加（同一条策略要在正确的层落位，落错层的表现是「规则不生效」而不是报错），以及排障成本上升——一个请求要跨三层看日志才能还原它的完整处理路径。

**失效点**：当团队把「分层」当成「多买几套网关」时，层与层的职责会重新糊在一起（例如边缘网关被要求解析 JWT 里的租户并做行级过滤），此时分层的代价全部保留、收益全部消失，因为**层之所以有价值是因为每层只用自己看得懂的上下文，一旦跨层伸手，边界就不存在了**。

**真实使用**：主文件 §1.4 提到阿里 DataWorks、字节 DataFinder、腾讯 WeData 等数据中台内嵌网关能力，但**其内部是否采用三层分离未公开**，不要断言。判断方法：看该平台的对外 API 域名与内部服务域名是否分离、限流与权限配置是否分域管理。

#### 3.2.3 Sidecar 模式

**被什么约束逼出来**：微服务数量多、语言栈杂，把治理能力写进每个服务的代码意味着 N 次实现、N 套 SDK 版本——治理必须从业务进程里搬出来。

**结构**（治理能力随业务容器一起部署）：

```text
        Pod A                                  Pod B
┌──────────────────────┐              ┌──────────────────────┐
│  业务容器             │              │  业务容器             │
│      ↓ localhost     │              │      ↓ localhost     │
│  Sidecar 代理         │─── mTLS ───► │  Sidecar 代理         │
└──────────────────────┘              └──────────────────────┘
        ▲ 控制面统一下发：路由 / 超时 / 重试 / 熔断 / mTLS 证书
关键：业务代码零改动，治理能力随代理升级而升级；
      代价是代理只看得到 HTTP/gRPC 这一层——
      它不知道「这次查询返回了多少行」，也不知道「这个字段是不是手机号」
```

**为什么这样设计有效**：因为策略由控制面统一下发、由本地代理执行，所以「跨语言统一治理」不需要每个语言各写一套 SDK；因为代理与业务同生命周期，它的部署、扩缩、故障都与业务 Pod 一致，不需要单独运维一套集群。

**代价**：每个 Pod 多一个进程——内存与 CPU 开销按副本数放大，连接数多、配置复杂时更高（量级通常是每侧数十 MB 内存，实际随配置与连接数变化【经验】）；多一跳本地转发（延迟影响小但存在）；以及升级的耦合：代理版本与业务 Pod 的滚动升级绑定在一起，基础组件的版本管理变成平台问题。

**失效点**：当被要求「在 Sidecar 里做数据权限」时，Sidecar 会失效，因为它**只看到 HTTP 字节，看不到 SQL 语义与结果集**——行级权限需要改写查询、列级脱敏需要解析响应体，这两件事都要网关或数据服务理解数据语义才做得到。强行在 Sidecar 层做的结果是：每个服务各自实现一遍，回到 Sidecar 本来要解决的那个问题。

**真实使用**：【公开】Envoy 是 Istio 的数据面代理，治理策略由控制面下发（Istio 官方文档，Istio 2017 年开源）。主文件 §2.4 已明确边界：Sidecar 做东西向（服务间）流量治理，API 网关做南北向（入口）流量治理。

#### 3.2.4 边缘计算 + 网关

**被什么约束逼出来**：调用方与数据后端在地理上相隔很远，而数据 API 的延迟预算里**网络往返是最不可优化的那一段**——后端优化 5ms 抵不过跨国多出的 100ms 级往返【经验】。

**结构**（把一部分判断推到离用户最近的地方）：

```text
        用户 / Agent（分布在不同区域）
                  │
      ┌───────────┴────────────┐
      │  CDN / Edge Function    │ ← 凭证校验、参数校验、结果集缓存命中、静态聚合
      └───────────┬────────────┘
                  │ 只回源未命中的请求
      ┌───────────┴────────────┐
      │   数据 API 网关          │ ← 行级/列级权限、按数据量限流、计量、审计
      └───────────┬────────────┘
          数据后端（数仓 / 向量库 / 联邦查询）
关键：边缘只放「不需要数据语义就能判断的事」；
      凡是需要看 SQL、看结果集的判断，一律留在回源后的数据网关
```

**为什么这样设计有效**：因为缓存与校验的计算被搬到了离用户最近的位置，重复查询根本不产生回源流量，所以延迟与后端负载同时下降；因为边缘节点的判断不依赖数据语义，它可以在多区域同构部署而不需要同步任何业务元数据。

**代价**：治理能力被切成两处，规则要在两个地方各配一次（写错一处就是「边缘放过了本该拦住的请求」）；边缘节点数量多、发布链路长，配置变更的生效时间与一致性难保证；边缘侧可观测性通常弱于中心机房，一个请求被边缘拦下时，中心的日志里什么都看不到。

**失效点**：当缓存的内容与权限相关时，边缘缓存会反转成数据泄漏通道——因为边缘节点大多只按 URL/参数做缓存键，**不知道「同一 URL 换个租户就该换一份结果」**，一旦缓存键里漏了身份维度，A 租户的响应会被返回给 B 租户，而中心侧的权限检查根本没有被触发（请求没回源）。

**真实使用**：【公开】Cloudflare Workers 在 2018 年正式可用、AWS Lambda@Edge 于 2016 年发布（来源：两家厂商的公开公告）。判断某架构是否属于此模式：看其缓存键（cache key）里是否包含租户与身份维度——不含就属于此模式的风险区。

#### 3.2.5 API 网关 + AI Gateway 融合

**被什么约束逼出来**：同一个数据服务（例如「查某个指标」）现在既被人通过 BI 调、也被 Agent 通过工具调用调，如果分成两套网关，就会出现两套鉴权、两套计量、两套审计——而审计恰恰是 Agent 场景最不能省的。

**结构**（同一份策略，两种协议面；下例是形态示意，不是任何产品的配置格式）：

```yaml
# 示意：同一份路由/策略描述被两种入站协议复用
routes:
  - id: bi-query
    inbound: http              # 人 / BI 工具
    upstream: query-service
    policy: {auth: jwt, rate: {qps: 200}, mask: [phone, id_card]}
    meter:  {unit: rows}       # 计量单位 = 返回行数

  - id: agent-tool-call
    inbound: mcp               # Agent 经 MCP 调用数据工具
    upstream: semantic-api
    policy: {auth: agent-token, on_behalf_of: end-user, rate: {qps: 20}}
    meter:  {unit: tokens, audit: full}   # Token 计量 + 全量审计留痕
关键：计量单位从「请求数」变成「行数 / Token」；
      鉴权主体从「一个」变成「Agent + 它代表的人」两个
```

**为什么这样设计有效**：因为两种调用共享同一份策略与计量管道，所以「Agent 用了多少、代表谁用、读了什么」与人调用走的是同一套账本，口径不会分裂；因为鉴权模型里显式带上「代表谁」（on-behalf-of），Agent 越权可以被定位到具体的人与具体的一次工具调用。

**代价**：网关要同时理解两种协议与两种计量单位，插件链的分支变多（同一段代码要处理「行数配额」与「Token 配额」）；MCP 是较新的协议（【公开】Anthropic 于 2024 年开源，主文件 §1.4 已述 MCP 网关为 2024 年新形态），实现与治理经验都还在积累期，选它意味着接受一定的规范漂移风险。

**失效点**：当 Agent 的调用频率远高于人时，「统一计量」会反转成「配额体系失真」，因为按请求数给 Agent 配额没有意义（Agent 一次任务可能发起数百次工具调用），而按 Token/行数配额又需要一个能实时扣减的计数器——两者都没准备好时，实际结果是 **Agent 把额度吃光，人访问被限流**，且难以判断谁该为此负责。

**真实使用**：【公开】Model Context Protocol 由 Anthropic 在 2024 年提出并开源，用于让模型/Agent 以统一协议访问外部能力（含数据）来源。判断某网关是否真的做了融合：看它的计量日志里是否同时存在「请求数」与「行数/Token」两类单位，以及审计记录里是否带「代表谁」字段。

#### 3.2.6 GraphQL Gateway

**被什么约束逼出来**：前端/BI 需要的字段组合千变万化，为每种组合提供一个 REST 端点会得到几十个高度相似的接口；而让前端自己串多次调用，又会产生 N+1 次后端查询。

**结构**（网关把「按字段懒加载」重写成「按层批查询」）：

```text
无网关（前端串行，N+1）             有网关（按层批处理）
  query { user(1) }        → 1 次       query { user(1) { orders { amount } } }
  query { orders(1) }      → N 次            │
  …  (每个 user 一次)                        ├─ 层1: user(id=1)            → 1 次
                                             └─ 层2: orders(user_id in […]) → 1 次
  解析次数 = 1 + N                      解析次数 = 1 + 1
关键：批处理必须由网关承担（它知道整棵查询树）；
      单看某一个字段的解析器，永远不知道自己会被调用多少次
```

**为什么这样设计有效**：因为网关持有完整的查询树，它可以**先在 schema 层把同一层的所有字段需求收集起来，再一次性下发**，所以「按需取字段」不会退化成「按需打后端」；因为返回字段由客户端决定，接口数量不再随需求组合爆炸。

**代价**：网关必须理解 schema 并实现批处理与去重（否则 N+1 只是从客户端搬到了网关）；缓存变复杂——缓存键不再是 URL，而是「查询 AST + 变量 + 身份」的规范化形式（规范化算法本身要维护）；权限控制也从「端点级」下沉到「字段级」（哪个用户能看哪个字段），这要求权限模型在 schema 上有对应表达。

**失效点**：当查询深度与并发上升时，会被滥用成一个「客户端随意组合的取数引擎」——因为**单次请求的成本由客户端决定而上限由网关承担**，一个深嵌套查询可以合法地触发大量后端扫描与多层批查询。此时「避免过度查询」的优点反转成「无法为请求成本定价」，网关不得不引入查询复杂度评分与深度/节点数上限来兜底。

**真实使用**：【公开】GraphQL 由 Facebook 于 2015 年开源，2018 年起由 GraphQL Foundation 托管（GraphQL Foundation 官方公告）。判断某网关是否只是「GraphQL 代理」而非真正的 GraphQL Gateway：看它是否实现了批量解析（DataLoader 一类机制），没有就只是换了个协议、N+1 问题原样存在。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| API 数量少（数十）、团队小、要快速上线 | 集中式网关 | 分层会在还没有第二个业务域时先产生三层配置负担 | 是否有超过一个团队需要独立调整策略 |
| 多个业务域 / 多团队、各域有独立合规要求 | 分层网关（边缘 + 数据） | 集中式会让一次策略误配影响全部业务域 | 是否出现「某域的规则不能影响其他域」的诉求 |
| 云原生微服务、语言栈杂、需要东西向治理 | Sidecar（Service Mesh） | 用它做南北向入口治理会把业务入口也拖进平台升级节奏 | 治理对象是服务之间的调用，还是外部到数据的调用 |
| 全球分布式调用方、延迟预算紧、查询重复率高 | 边缘计算 + 网关 | 只靠中心网关，跨区往返吃掉全部优化空间 | 重复查询占比与调用方地理分布 |
| Agent 与人共用同一批数据服务 | API 网关 + AI Gateway 融合 | 两套网关会让 Agent 的用量与人的用量对不上账 | 是否出现「同一份数据被 Agent 高频调用」 |
| 前端/BI 字段组合多变、接口数量爆炸 | GraphQL Gateway | REST 端点会按组合数量线性增长 | 接口数量是否在随需求组合而非业务域增长 |
| 数据合规严格（个人信息、跨境） | 分层 + 数据脱敏（脱敏必须在数据网关执行） | 只在上层做脱敏，一旦有旁路出口即失效 | 是否存在第二个数据出口（导出、直连、Agent 直读） |
| 调用方是穷举不可控的公开 API | 边缘 + 集中式（WAF 在最前） | 只集中式容易被爬虫打满资源池 | 调用方是否可信、是否可枚举 |

最常被误选的一对是 **分层网关** 与 **Sidecar 模式**：因为 Service Mesh 也自称「网关」，团队会把数据治理（行级权限、脱敏、按行数限流）搬进 Sidecar。误选的实际后果不是立刻报错，而是**权限实现开始发散**——每个服务在自己的 Sidecar 侧配置里加一段规则，半年后同一个用户在 A API 上能看到全租户数据、在 B API 上只能看本部门，且没有任何一处能回答「这个人到底能看到什么」。这个问题的修复成本极高，因为要先把散落在 N 个服务里的权限语义重新收敛成一份定义。

### 3.4 组合模式：真实系统不会只用一种

**组合一：边缘网关（WAF + 缓存）+ 数据网关（行级权限 + 数据量限流）**

- 组合构成：边缘做与数据语义无关的判断，数据网关做需要看懂查询的判断。
- 职责边界：边缘决定「这个请求要不要到后端」，数据网关决定「这个请求能看到哪些行、哪些列」。
- 运维代价：规则要配两处，且边缘缓存键必须包含身份/租户维度，否则缓存会成为越权通道；两处的可观测日志需要能按同一个请求 id 串起来。
- 适合规模：调用方跨区域、重复查询占比高的场景，通常是「有外部或跨区调用方」之后。

**组合二：Sidecar（东西向）+ 集中式入站网关（南北向）**

- 组合构成：服务之间的调用由 Sidecar + 控制面治理，外部到数据的调用由入站网关治理。
- 职责边界：东西向关心「服务是否健康、能否重试、证书是否轮转」；南北向关心「谁在调、能不能调、能调多少数据」。
- 运维代价：两套策略体系并存，团队要清楚「这条规则该写在 Mesh 里还是网关里」——写错位置的表现是规则静默不生效。
- 适合规模：微服务数量多（需要统一 mTLS 与重试策略）且对外有数据服务出口时。

**组合三：API 网关 + AI Gateway 融合 + GraphQL 聚合（AI 原生数据中台）**

- 组合构成：HTTP 与 MCP 两种入站协议共享同一套鉴权/计量/审计；对外的字段级取数由 GraphQL 聚合承担。
- 职责边界：融合网关管「身份、额度、审计、脱敏」，GraphQL 层管「字段选择与批量取数」，两者都不承载业务计算。
- 运维代价：计量单位要在「请求数 / 行数 / Token」之间统一到同一账本；GraphQL 需要复杂度上限，否则一次深查询的成本无法定价。
- 适合规模：Agent 已进入生产（不只是实验）且与人共用同一批数据服务时。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **无网关直接暴露** | 用服务直连域名能拿到数据；网关的访问日志里没有这条链路 | 鉴权、限流、计量、审计四处全部绕过；事后无法回答「谁取过这份数据」 | 建库建表时可直连，等发现时已有大量存量调用方 | 强制唯一入口：网络层只放行网关网段 + 存量调用方分批迁移 |
| **单点网关** | 网关重启期间全站 API 不可用；扩容只能垂直加机器 | 资源池单点：任何策略误配、插件崩溃都是全站故障 | 「网关无状态所以不用做多活」——无状态解决不了单集群故障 | 多副本 + 多可用区 + 独立的控制面与数据面 |
| **网关做业务逻辑** | 网关里出现「如果指标=GMV 则……」这类分支；改业务要先发网关 | 网关部署频率被业务需求绑架，回归范围变成全站；策略与业务耦合后无法独立演进 | 网关离请求最近，把逻辑放这里「最省事」，短期确实省事 | 网关只做治理，业务逻辑下沉到服务；用「能否在不发版的情况下解释这条规则」作判据 |
| **无数据权限** | 网关只校验 token 有效性，不校验「这个用户能看哪些行/列」 | 任意合法用户可读全量数据；鉴权只解决了「是不是人」不解决「能看什么」 | 权限被当成应用的责任，每个服务各自实现或不实现 | 网关集中行级/列级权限（改写下推 + 字段脱敏），并把它作为默认能力 |
| **无熔断** | 一个后端变慢后，网关线程/连接被占满，连带其他 API 一起失败 | 故障沿共享资源池横向传播，从「一个 API 不可用」升级为「全站不可用」 | 熔断不写看不见问题，直到第一次雪崩 | 熔断 + 超时 + 降级三件套同时配，且超时必须小于上游超时之和 |
| **无限流** | 压测或异常调用方可以打满后端；事后查不到限制阈值是多少 | 无阈值即无容量模型：容量规划无法做，故障归因困难 | 限流会「伤害真实用户」，团队倾向先不加 | 先按调用方/API 分层限流，再按数据量（行数/扫描量）补一层 |
| **无计量** | 回答不了「上季度哪些调用方用了多少资源」 | 无法做成本分摊与容量规划；对外服务无法定价 | 计量数据量大，觉得「以后再补」——补的时候历史数据拿不回来 | 计量埋点在网关侧同步落（异步写出），单位至少含请求数与被扫描/返回量 |
| **忽视缓存** | 相同的重复查询直达数据库；后端负载与调用量同比例增长 | 每次请求都付一次后端成本，缓存敏感型场景（同参数重复查）成本线性放大 | 缓存失效策略复杂，先不做 | 结果集缓存（键含身份维度）+ 物化视图，命中率按参数重复率评估 |
| **无审计日志** | 出事后查不到「谁在什么时候读了哪些数据」 | 合规无法自证；事故无法定位到调用方；（AI 场景）Agent 的行为无法回溯 | 日志量被认为「没必要全留」 | 审计日志独立于访问日志：含调用方身份、代表谁、读了多少行、被脱敏字段 |
| **忽视 AI 安全** | Agent 的工具调用日志里只有「调用了某 API」，看不到参数与返回 | 提示注入导致的越权取数无法识别；敏感数据可能经 Agent 落到外部 | AI 场景是新增的，安全设计沿用「人调用」的假设 | Agent 调用纳入同一网关：强制脱敏、强制审计、额度与人在同一账本 |

三个最危险的反模式值得单独展开。

**网关做业务逻辑**之所以最容易被低估，是因为它每一次都是「合理的」。某个 API 需要在网关侧做一次字段映射、一次特殊路由、一次按指标的差异化限流——每一次都只加一个 if，每一次都比「回去改服务」快。代价不体现在发布那一刻，而体现在**部署耦合**：半年后网关的发布清单里躺着业务规则、协议转换、租户特例三类互不相干的东西，回归范围变成「全站所有调用方」，于是网关的发布窗口越来越长，最后没人敢在白天发网关。判据很简单：**这条规则能否由不熟悉业务的平台同学解释清楚？不能就说明它不该在网关里。**

**无数据权限**的危险在于它「看起来有安全措施」。网关有鉴权、有 WAF、有 TLS、有审计——唯独没有「行级 / 列级」这一层。于是一个有合法凭证的调用方可以按条件扫全表。更常见的是它被漏在**聚合接口**上：单个明细接口做了权限过滤，而汇总接口（返回总计、按维度汇总）忘了过滤条件，返回的数字里包含了他人的数据。修法的关键是把权限做成「改写下推」（把租户条件注入下推查询），而不是在应用层做后置过滤——后置过滤要求每个应用都记得过滤，而改写下推由网关统一保证。

**忽视 AI 安全**是新增且最容易被豁免的一条。理由通常是「Agent 是我们自己的」。但机制上没有这个区别：Agent 的输入来自用户与外部内容（提示注入的入口），它的输出会落到最终用户或外部系统，而它调用的工具正是数据 API 网关本身。所以「Agent 是我们自己的」只能说明它**更容易拿到高权限凭证**，不能说明它不会被诱导滥用这些凭证。可行的最小措施是把 Agent 纳入与人相同的路径：同一网关、同一脱敏、同一审计、额度挂在它代表的用户身上——这样即使被诱导，损失也是有界且可追溯的。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的。下面这些阈值的共同点是：**它们都不是「量大了要换」，而是「约束变了必须换」**。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 调用方从内部服务 → 外部客户 | 集中式网关 | 外部调用方不可枚举、不可信，攻击面进入共享资源池 | 边缘（WAF + 限流）+ 集中式数据网关 | 域名与证书体系重建、对外配额与计量上线、存量客户重新签约 |
| 单团队 → 多业务域 | 集中式网关 | 一次策略误配影响全部域；各域合规要求开始冲突 | 分层网关（按域隔离策略与配额） | 策略需要拆分并映射到正确层级，历史配置要逐条归位 |
| 服务数从数十 → 数百、语言栈变杂 | 集中式网关的 Sidecar 缺失 | 每个服务各自实现重试/超时/mTLS，一致性无法维持 | 引入 Sidecar（东西向）并保留入站网关（南北向） | 平台组件引入、代理版本管理、两套策略体系的边界约定 |
| QPS 限流够用 → 出现大结果集查询 | 按请求数限流 | 限流计的是请求而不是资源消耗，慢查询不吃请求额度 | 按「返回行数 / 扫描字节」限流 + 并发舱壁 | 需要能拿到查询的执行统计（与查询引擎/数据服务约定上报） |
| 人调用 → Agent 高频调用 | 请求数计量 | Agent 的调用量与资源消耗不成比例，配额失真 | 计量单位增加行数/Token，鉴权增加「代表谁」 | 计量账本改造、审计字段扩展、Agent 额度模型重新设计 |
| 单区 → 多区 / 全球化 | 中心网关 | 跨区网络往返成为延迟主要成分，且中心区故障影响全球 | 边缘计算 + 网关（边缘只做无语义判断） | 边缘缓存键必须含身份维度；两处规则一致性需要自动化校验 |
| 接口按业务域设计 → 接口按组合爆炸 | REST 端点 | 端点数量随字段组合而非业务域增长 | GraphQL Gateway（含批量解析） | schema 设计、字段级权限映射、查询复杂度上限与缓存键规范化 |

这张表里最容易误判的一行是「QPS 限流够用 → 出现大结果集查询」。它之所以容易被忽略，是因为**触发它的是一个查询形状的变化，而不是流量的变化**：调用方数量没变、QPS 曲线没变、错误率也正常，只是有人开始按「明细导出」的用法调那个原本设计成「看汇总」的接口。所以这个跃迁要盯的指标不是 QPS，而是**单次请求的执行耗时分布与返回行数的 P99**——它们先动，QPS 之后才会动。

### 3.7 自检清单

- [ ] 是否存在任何一条绕过网关能直达数据服务的网络路径？（有则其余检查都失去意义）
- [ ] 限流配的是「请求数」，还是也覆盖了「返回行数 / 扫描量」？慢查询能否在 QPS 未超限的情况下拖垮资源池？
- [ ] 一个合法调用方，能否通过某个聚合接口读到不属于它的行？汇总接口是否也做了行级过滤？
- [ ] 脱敏是「改写下推」还是「应用层后置过滤」？如果是后者，有几个出口没走这条过滤？
- [ ] 网关里是否存在需要理解业务才能解释的规则？如果有，它们由谁负责回归？
- [ ] 每个后端的超时、熔断、重试三者的数值关系是否自洽？（重试 × 超时是否超过入口超时）
- [ ] 计量日志能否回答「上季度每个调用方用了多少资源」？单位是请求数还是也含数据量？
- [ ] 审计日志里能否查到「某次 Agent 工具调用代表了谁、读了哪些字段」？
- [ ] 边缘缓存（若有）的缓存键是否包含身份/租户维度？不带身份维度的缓存是否有准入白名单？
- [ ] 同一套权限规则，是否在多个服务/Sidecar 里各写了一份？有多少处副本？
- [ ] 网关的发布是否需要业务方参与回归？如果是，业务逻辑已经渗进网关。
- [ ] 网关多副本是否跨可用区？控制面故障时数据面能否继续按既有策略运行？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| API 少、团队小、先跑通 | 集中式网关 | 单一策略执行点，一致性由结构保证；代价是共享资源池 |
| 多业务域、合规要求各异 | 分层网关（边缘 + 数据） | 每层只用自己看得懂的上下文，改动回归范围可控 |
| 微服务多、语言栈杂、需东西向治理 | Sidecar | 治理从业务代码里搬出来；但看不到数据语义，别让它做数据权限 |
| 调用方跨区、重复查询多 | 边缘计算 + 网关 | 无语义的判断前置；缓存键必须含身份维度 |
| Agent 与人共用数据服务 | API 网关 + AI Gateway 融合 | 计量单位与鉴权主体同时扩展，账本才不分裂 |
| 字段组合多变、接口爆炸 | GraphQL Gateway | 由网关承担批量解析，否则 N+1 只是换了发生位置 |

> 本节小结：本主题下决定模式选择的**唯一那条约束是「网关能看见多少数据语义」**——只看见 HTTP 就限不住慢查询、做不了行级权限；看得见 SQL 与结果集才有数据治理，但也就背上了业务耦合与回归范围的代价。所有模式选择，本质是在这条轴线上给自己找一个可运维的位置，而不是挑一个「更先进」的组件形态。
>
> 💡 **思考锚点**：翻一下你的网关限流配置——它计的是「请求数」，还是也覆盖了「返回行数 / 扫描字节」？找一个被设计成「看汇总」却被按「明细导出」调用的接口，它的返回行数 P99 是多少？这个数字，你在限流或告警里给它设过阈值吗？
