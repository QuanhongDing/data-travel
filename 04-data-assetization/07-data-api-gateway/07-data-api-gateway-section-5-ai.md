## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

网关这一层的成熟度**本来是查得到的**——它有版本号、有 release note、有插件清单，不像组织形态那样只能靠说服。但三类完全不同的东西混进了同一张清单：

- **已 GA 的组件**：Kong、Apache APISIX 等网关项目在 2024 年前后推出与 AI / LLM 相关的插件（具体版本与发布日期按各项目 release note 可查）。
- **刚出现的协议**：Model Context Protocol 由 Anthropic 于 2024 年公开并开源，其规范以带日期的修订版本发布（具体版本号与日期按 MCP 官方规范页可查）。
- **能力声称**：「边缘跑小模型做 query 重写」「按意图智能路由到不同后端」「网关防住提示注入」——这三条至今没有可核验的生产有效证据。

三类混排的后果不是「不够详细」，而是**读者会把「组件存在」当成「能力成立」**：看到「Kong 3.x + AI Plugin（2024）」，很容易顺势相信「提示注入防护」也已经有产品支持了。组件存在与能力成立之间，隔着一条本节要反复指出的界：**规则链能匹配语法，匹配不了语义。**

本节用 **L1 / L2 / L3** 三级划分，判据必须可核验，而不是「感觉成熟」：**① 已 GA 且有正式 release note**（能说出文档或版本页的名字，而不是「官网写了」）；**② 有第三方（非厂商）公开生产案例**（厂商自述的客户故事不算）；**③ 接口稳定**（可迁移、可替换，不随某一次模型或版本升级而变）。**三条全中才算 L1 生产可用**；已可用但接口或生态未稳、或只有厂商自有案例的记 **L2 可试点**；只有路线图、论文或厂商演示的记 **L3 观望**。

**本节不对这套判据做任何修正**——本主题的产出是软件组件，有版本、有 release note，三条判据都适用于它。结果如实说：**本主题下没有任何方向同时满足 L1 的三条，最高为 L2。** 卡点集中在第②条：本主题的公开生产材料绝大多数是**厂商自己的文档与客户案例**，按判据不构成「第三方（非厂商）公开生产案例」；而少数独立可核验的事实（协议规范、风险清单）属于第①类证据，它们能描述「威胁长什么样、接口怎么写」，不足以支撑一个组件级别的 L1 判定。**不写「准 L1」，也不为了好看放宽判据——L2 的定义本就覆盖「仅有厂商自有案例」这一情形。**

本主题真正的机制问题只有一个，而且 [§3.1](07-data-api-gateway-section-3-sec3.md) 已经给出：**网关能看见多少数据语义**。AI 在这条轴线上只动了两个量：

- **计量单位**：从「请求数」变成「资源单位」（返回行数 / 扫描量 / Token）——因为 Agent 的请求数与资源消耗不成比例。
- **鉴权主体的数量**：从一个变成两个（Agent + 它代表的人）——因为 Agent 需要一个「能被授权、也能被追责」的主体。

其余变化（换成哪个协议、用哪家网关、把判断放边缘还是中心）都是接口形态的替换，落不到这两条上。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | :---: | --- |
| MCP / AI Gateway：Agent 经统一协议访问数据 | L2 | 【公开】①协议规范公开、可核验（MCP 由 Anthropic 于 2024 年公开并开源，规范以带日期版本号修订）；②不满足——公开材料以厂商侧为主；③接口未稳（规范仍在修订，跨实现兼容要靠适配） | PoC：把工具清单与 API 清单对齐，并让每次调用能定位到「代表谁」 |
| Function Calling 把 API 注册为 Tool 统一治理 | L2 | ①接口公开可核验（各 LLM 服务的工具调用接口有公开文档）；②不满足（无第三方生产案例）；③工具的 schema 表达由各家自行定义，跨厂商不通用 | 先做一个只读工具的最小闭环，不要一次开放写入类能力 |
| Token 计量与用量归因（含 embedding 调用次数、RAG 检索次数） | L2 | ①用量字段是公开接口（主流 LLM 服务在 API 响应中返回 usage，读者可查任一服务商文档）；②不满足（无第三方生产案例）；③单位不统一——各家 usage 字段口径不同，且与「行数 / 扫描量」不可通约 | 现在就该做：让计量日志至少同时含两类单位 |
| 网关层输出过滤与全量调用审计 | L2 | ①脱敏与审计是既有网关能力，接口稳定；②不满足——但这一条的成效可被自己核验（能否还原一次完整工具调用）；③接口稳定 | 现在就该做：把 Agent 调用纳入与人相同的脱敏与审计路径 |
| 网关层检测并拦截 Prompt 注入 | L3 | ①无正式发布方可核验该能力的技术边界；②无第三方生产有效证据；③无稳定接口（检出率与漏检率都无法被外部复核） | 观望：把预算投到审计、脱敏与权限收窄上 |
| AI 增强路由（按复杂度选模型 / 按意图选后端 / 按预算降级） | L3 | ①无正式可核验的发布（只有厂商与演示材料）；②无第三方生产证据；③无稳定接口（无公开的准确率 / 路由正确率口径，事后不可复核） | 观望；先做基于 path / header 的静态多路复用 |
| 边缘 AI Gateway：边缘做 query 重写 | L3 | ①厂商产品存在（Cloudflare 的 AI Gateway / Workers AI 有公开文档）；②无第三方生产证据；③越过了 [§3.2.4](07-data-api-gateway-section-3-sec3.md) 的边界（边缘只应放不需要数据语义的判断） | 观望；边缘只放缓存、回退、凭证托管 |
| 边缘侧无语义判断（缓存 / 回退 / 重试 / 凭证托管）（「减少回源流量」那一半；这一组具体做法按 [§3.2.4](07-data-api-gateway-section-3-sec3.md) 的边界补出） | L2 | 【公开】①厂商公开文档与 release note 可核验（Cloudflare Workers 2018 年正式可用、AWS Lambda@Edge 2016 年发布）；②不满足（同上）；③接口稳定 | 可做，但缓存键必须含身份 / 租户维度 |
| RAG / 向量库 / GraphRAG / Multi-Model 经网关统一接入（四条） | L2 | ①鉴权与计量是既有网关能力；②不满足；③接口稳定，但计量单位各家不同 | 现在就该做：四条接入共用一套计量账本 |

> 表后说明：**本主题下没有任何方向够 L1，最高的一档是 L2**（共 6 个方向），其中真正代表本主题演进的是两块：「MCP / AI Gateway 统一入口」与「Token 计量」——它们都卡在第②条（第三方非厂商公开生产案例）。这个结论与读者可能有的直觉不同（毕竟 AI 网关产品已经很多），但请对照判据：**产品多不等于证据在**，而本节排路线图用的正是证据。按 L2 的行为指引，这两件事可以做 PoC，但**不要把核心取数链路的重构押在它们身上**；另外 3 个方向之所以是 L3，原因各不相同（拦注入原理上不可判定、智能路由失败静默、边缘语义预处理越界），表中已逐行写明。

本主题的证据结构为什么会是这样？因为网关是**基础设施组件**：它的成效只有在「有人把它接进生产、跑出问题、再写复盘」之后才会变成独立证据，而这个环节恰好最缺。于是本节能拿到的最强证据是**规范与风险清单**（它们描述威胁与接口），最弱的是**功能清单**（它只说明厂商实现了某个函数）。判断一个宣称值不值得信，用下面这个顺序追问即可：

| 遇到的宣称 | 该问的下一句 | 若答不出，它是什么级别 |
| --- | --- | --- |
| 「支持 MCP / 支持工具注册」 | 规范版本号与日期是什么？工具清单能不能与 API 清单对齐？ | L2（协议已可用，治理未验证） |
| 「支持 Token 计量」 | 计量日志里能不能看到行数 / 扫描量？能否归因到具体的人？ | L2（单位不全，归因缺失） |
| 「能防住提示注入」 | 检出率的测试集是什么、由谁定义的？误报怎么处理？ | L3（不可复核） |
| 「按意图智能路由」 | 路由错了会怎样被发现？事后能否复盘为什么走了这条？ | L3（失败不可见） |
| 「边缘预处理 query」 | 边缘缓存键含身份维度吗？与中心权限判断怎么分工？ | L3（越过 §3.2.4 的边界） |
| 「统一审计所有 LLM 调用」 | 审计里含不含工具返回内容？含的话它是否按敏感数据管？ | L2（能力可做，风险要自己兜） |

> 这张表的用法不是评判厂商，而是**判断自己能不能现在就依赖它**：答不出第二列的问题时，正确动作是「先自己做 PoC 并把答案问清楚」，而不是「因为大家都在用就先上」。

### 5.2 演进方向逐条拆解（核心节）

9 个方向按「AI 改了网关的哪一部分」归成 4 组：**入口（谁能调）**、**账本（算谁的、算什么）**、**安全（防什么）**、**路径（怎么走）**。四组都改了网关的行为，但落点不同：**只有账本那一组动到了资源模型**（容量、配额、成本归因都挂在它上面）；入口改的是接口边界的形状，安全改的是「不可信输入」的性质，路径改的是路由依据——后三者都不改变账本，因此不改变容量与配额模型。

| 本节方向 | 机制上它改了什么 | 评级 |
| --- | --- | --- |
| §5.2.1 统一入口 | 接口边界的形状（路径 → 能力 + schema） | L2 |
| §5.2.2 账本 | 账本主键（请求 → 资源单位；主体 1 → 2） | L2 |
| §5.2.3 安全 | 不可信输入的性质（语法畸形 → 语义合法） | 脱敏与审计 L2；拦注入 L3 |
| §5.2.4 路径 | 路由依据（请求元数据 → 请求内容） | 边缘无语义判断 L2；语义预处理与智能路由 L3 |

#### 5.2.1 Agent 统一入口：MCP / Tool 注册 / AI Gateway

- **旧做法与它的卡点**：Agent 访问数据的两条旧路都卡住。**发凭证**——给 Agent 一个数据库或 API 凭证，它能做任何事，而审计里看不出「是谁让它做的」；**各服务各做一套**——每个数据服务自己实现一个「工具接口」，于是出现了 N 套工具描述、N 套鉴权、N 套计量。卡点在于**「工具」这个概念在既有网关里没有位置**：网关路由的是路径，而 Agent 需要的是「能力名 + 参数 schema + 权限范围」。
- **AI 改变了什么机制**：**改变了接口边界的形状**——调用方从「预先知道 URL 与参数格式」变成「只声明能力与 schema，由协议负责发现与调用」。这是接口形态的变化，不是换了个协议名：**同一个数据服务，作为 API 存在和作为工具存在，对网关提出的要求不一样**。
- **由此得到的**：因为 Agent 不再需要为每个数据源写一份集成，所以「把一个数据能力开放给 Agent」的边际成本从「写一份适配」降到「注册一个带 schema 的工具」；也因为工具注册与鉴权挂在同一层，网关可以在一个点上回答「这个 Agent 能不能看见这个工具」——这正是 [§3.2.5](07-data-api-gateway-section-3-sec3.md) 融合模式里「同一份策略、两种协议面」的落点。
- **由此付出的**：
  - **① 规范在演进，接口未稳**：选它就要接受规范漂移，跨实现的兼容性不能靠一次测试保证，要靠版本管理。
  - **② 工具描述与返回内容成为新的攻击面**：工具返回的文本会进入模型上下文，等于把「数据」当「指令」喂给模型——§5.2.3 的注入问题正是从这里进来的。
  - **③ 会出现两套清单**：注册在网关的「工具清单」与网关外的「API 清单」不同步时，审计里会多出没有主人的入口，而这恰恰是 [§3.5](07-data-api-gateway-section-3-sec3.md) 把「无网关直接暴露」列为第一反模式的原因。
- **证据与来源**：【公开】Model Context Protocol 由 Anthropic 于 2024 年公开并开源，规范以带日期的版本号发布修订（读者可按 MCP 官方规范页核验具体版本与日期）；【公开】Kong、Apache APISIX、Envoy 等网关项目在 2024 年前后有与 AI / LLM 相关的插件或独立项目（读者可按各项目 release note 核验具体版本与发布日期）。本方向不满足第②条。
- **成熟度**：**L2** —— 接口已可用但生态未稳、且只有厂商侧材料；可做 PoC，不要做核心依赖。
- **判定方法**：查两件事——（1）工具清单与 API 清单能不能对得上（能否直接回答「哪些能力对 Agent 可见」）？（2）每一次 Agent 工具调用能否定位到「代表谁」？两条都答不出，说明你只是接了个协议，没有接入治理。

两套清单的关系是这个方向最容易出错的地方（示意，不是任何产品的配置格式）：

```text
        同一个数据能力的三种存在形态（必须能对齐）
  ┌────────────────────────────────────────────────────────┐
  │  ① HTTP API      路径 + 方法 + 参数      面向人 / BI     │
  │  ② 工具定义      能力名 + 参数 schema    面向 Agent      │
  │  ③ 权限条目      行级 / 列级范围          面向两者        │
  └────────────────────────────────────────────────────────┘
              │ 注册
              ▼
      网关（鉴权 / 计量 / 脱敏 / 审计 / 配额）
              │
      ┌───────┴────────┐
   工具调用          直接调用
   （代表某人）      （人自己）
      └───────┬────────┘
        同一本账、同一次审计
  ────────────────────────────────────────────────
  常见故障：②③ 各写一份且无人对齐
    → 审计里出现「可见但对不上任何人」的工具调用
    → 判据：能否用一条查询列出「对 Agent 可见的全部能力」并逐一指回 API
```

#### 5.2.2 账本变了：计量单位与鉴权主体

- **旧做法与它的卡点**：按请求数计量 + 单主体鉴权。卡点是**请求数不再代表消耗**：Agent 一次任务可能发起数十到数百次工具调用【经验】，其中任意一次都可能扫全表；同时「谁用了」在 Agent 场景下有两个答案。[§3.6](07-data-api-gateway-section-3-sec3.md) 已把这件事写成一条跃迁——「人调用 → Agent 高频调用」时，请求数计量会让配额失真，且失真的表现是**Agent 把额度吃光、人访问被限流**。
- **AI 改变了什么机制**：**改变了账本的主键**——计量单位从「请求」换成「资源单位」（返回行数 / 扫描量 / Token），鉴权主体从一个换成两个。这不是加一个字段，而是换一套记账协议：**账单的主键换了，容量模型、配额模型、异常检测的口径都要跟着换。**
- **由此得到的**：因为账本主键变了，「成本能归因到具体的人与具体的任务」才成立；也正因为归因成立，配额与降级才有意义——否则限制一个 Agent 等于同时限制它的全部用户，而那等于不能用。
- **由此付出的**：
  - **① 计量需要看内容**：按 Token 计量要求网关解析请求体与响应体，按行数计量要求查询侧上报执行统计。前者与「网关不该看内容」这条既有安全假设直接冲突——**内容一旦进了网关，加密与脱敏的边界就要重画，网关本身也升级为高敏组件。**
  - **② 实时扣减成为新的故障点**：计数器服务不可用时，是放行（超额）还是全拒（误伤）？两条都要有预案，而大多数网关今天还没有这个开关。
  - **③ 两种单位不可通约**：同一个后端既按行数又按 Token 计量时，账本里会出现两套单位，对账口径分裂；跨厂商的 usage 字段含义也不同，归一本身是一项要长期维护的工作。
- **证据与来源**：【公开】主流 LLM 服务在 API 响应中返回 usage（prompt / completion token）字段，这是可核验的公开接口（读者可查任一 LLM 服务商的 API 文档）；网关侧的 AI 插件与计量能力见 §5.2.1 的来源。本方向不满足第②条。
- **成熟度**：**L2** —— 计量接口可用，但单位归一与实时扣减都还没有稳定做法；可做 PoC，不要作为对外计费的唯一依据。
- **判定方法**：打开计量日志，看能不能回答两个问题——「上季度某个具体的人通过 Agent 用了多少资源」「这个数字里含不含被扫描的数据量」。答不出第二个，说明单位还停在请求数。

账本主键换了之后，同一个请求要在两条轴上被记账（示意）：

```text
  改前：账本主键 = 请求
    记录一条：{调用方, API, 时间, 状态码}
    能回答：调了多少次
    不能回答：这次请求花了多少资源、代表谁

  改后：账本主键 = 资源单位 + 代表谁
    记录一条：{调用方, 代表谁, 资源单位(行数/扫描量/Token), 时间, 工具名}
    能回答：谁通过哪个 Agent 花了多少资源
    新问题：单位不可通约（Token ↔ 行数无固定换算）
            → 因此必须两类都记，而不是二选一
  ────────────────────────────────────────────────
  判据：把任意一条 Agent 调用记录拿出来，
        能不能说出「它代表谁、它读了多少数据」
```

四种接入形态，落到账本上就是四行不同的记账规则：

| 接入形态 | 计量单位 | 鉴权主体 | 经网关后多出来的那一步 |
| --- | --- | --- | --- |
| API Gateway + RAG | 检索次数 + Token | 发起提问的人 | 检索与生成两段请求要在同一账本里对齐 |
| API Gateway + 向量库 | 检索次数 / 返回条数 | 代表的人 | 向量检索的返回量要能被查询侧上报 |
| API Gateway + GraphRAG | 图查询次数 + Token | 代表的人 | 图遍历成本与文本生成成本分属两个后端，需分别记账 |
| AI Gateway + Multi-Model | Token（各家口径不同）+ 请求数 | 代表的人 | 跨厂商 usage 字段归一 |

> 四行的共同点：**计量单位都不是「请求」**。这就是 §5.2.2 的全部结论——如果只改了一样东西，改的应该是账本的主键。

#### 5.2.3 AI 安全：能做的是哪三件，不能做的是哪一件

- **旧做法与它的卡点**：WAF 拦 SQL 注入、XSS 是「一个字符串模式」问题——畸形输入在语法上就可疑，规则链可以匹配。提示注入不是：**它是「数据里带指令」的问题，而数据与指令在同一个 token 流里，没有语法上的区分**。这是本方向最本质的卡点，也是它被过度宣传的根源。
- **AI 改变了什么机制**：网关要面对的「不可信输入」从**语法层面的畸形输入**变成**语义层面的合法指令**——输入在语法上完全合法，因此基于模式与规则链的检测**在原理上无法判定它是否恶意**。
- **由此得到的**：因为判定做不到，**有确定收益的只有三件不需要识别注入的事**：①把 Agent 的每一次工具调用记成完整审计（含参数与返回，[§3.5「忽视 AI 安全」反模式](07-data-api-gateway-section-3-sec3.md) 的修法）；②在网关统一做**输出侧**脱敏，把最坏情况的损失上界压下来；③把 Agent 的权限收窄到「它代表的人」的权限（§5.2.2 的第二个主体），让被诱导时的损失有界、且能追到具体的人与具体的一次调用。
- **由此付出的**：
  - **① 输出侧脱敏一定会漏**：脱敏规则是枚举的，敏感数据形态是开放的；漏掉的形态会被完整写进审计日志——**审计日志本身因此成了新的敏感资产**，需要按敏感数据的标准来管。
  - **② 全量留痕的存储与合规成本上升**：Agent 的调用频率比人高【经验，数十到数百次/任务量级】，日志量按同一倍数放大，而留痕本身又受数据留存与跨境规则的约束。
  - **③ 额度挂在人身上会带来新的博弈**：「Agent 超额」变成「这个人超额」，用户会为了避免被限流而不用 Agent，或者拆小任务绕开配额——这需要例外流程，否则治理工具会变成业务阻碍。
- **证据与来源**：【公开】OWASP 的 LLM 应用风险清单把提示注入列在首位（OWASP，2023 年首版并有后续更新版本；读者可按 OWASP 官网核验版本与年份）——它排第一**不是因为它最好防，而是因为它最没有通用解法**。网关层「拦注入」无公开可核验的生产有效证据。
- **成熟度**：分两半，与 §5.1 表的两行一致——**输出侧脱敏与全量审计 L2**（能力已可用，成效可由自己核验）；**网关层检测并拦截 Prompt 注入 L3**（只有厂商演示与论文，无第三方生产有效证据）。
- **判定方法**：不要问「能不能防住注入」（这个问题今天没有答案），改问三个能查的问题：（1）审计能否还原一次被诱导的完整调用链（含工具返回）？（2）Agent 凭证的权限是否**等于且不高于**它代表的人的权限？（3）输出侧脱敏规则覆盖哪些字段、谁在维护、上一次更新是什么时候？

三件可做的事，各自的产出与核验方式（**都不依赖「识别出注入」**）：

| 可做的事 | 机制上的作用 | 产出物 | 怎么核验它真的在工作 |
| --- | --- | --- | --- |
| 全量工具调用审计 | 把「最坏情况」变成可复盘的事实 | 结构化调用记录（参数 / 返回 / 主体） | 随机抽一次调用，能否还原完整链路 |
| 输出侧统一脱敏 | 压低最坏情况的损失上界 | 脱敏规则与命中记录 | 构造一个含敏感字段的返回，看它是否被替换 |
| 权限收窄到「代表谁」 | 让被诱导时的损失有界、可追责 | 权限映射（Agent 凭证 → 人的权限） | 用 Agent 凭证尝试读它代表的人读不到的行 |

> 三件都做不到时，「网关能防住提示注入」这句话在你的架构里没有任何支撑。

#### 5.2.4 路径变了？AI 增强路由与边缘 AI Gateway

- **旧做法与它的卡点**：路由按 path / header / method / 权重；边缘只做 TLS 卸载、WAF、缓存（[§3.2.2 分层网关](07-data-api-gateway-section-3-sec3.md)）。当调用方是 Agent、后端同时有 SQL、向量、图三条取数路径时，「这一次该走哪条」需要理解 query 本身——而这正是 path 级路由表达不了的。
- **AI 改变了什么机制**：**把路由依据从请求元数据换成请求内容**（用模型或分类器读 query 决定去向）；边缘侧同理，把一部分预处理从中心搬到离调用方更近的位置。
- **由此得到的**：因为路由可以基于语义，所以「同一个入口按意图分发到 SQL / 向量 / 图」在原理上可行；因为判断发生在离调用方更近的位置，重复请求可以不回源。本节把「提升首 token 延迟」作为一项收益声称来评估，结论是**不采纳**：首 token 何时到达由推理侧的排队与流式实现决定；边缘只做缓存与回退时，命中减少的是回源次数、生成仍发生在中心，未命中时边缘也不参与生成，所以两种情形下它都不改变首 token 的出现时刻。把延迟收益记在边缘侧，等于把推理侧的账记到边缘上。
- **由此付出的**：
  - **① 路由本身要花一次模型调用**：它把零成本的路由变成有成本、有延迟、且新增一个失败点的路由；**路由错了的表现是「后端调用成功但答案是错的」——这类故障不报错**，只能靠人工发现。
  - **② 可解释性下降**：事后无法复盘「为什么这次走了向量检索」，而这正是 [§3.5「无审计日志」](07-data-api-gateway-section-3-sec3.md) 在 AI 场景下的新形态。
  - **③ 边缘做语义判断越过了既有边界**：边缘只应放「不需要数据语义就能判断的事」（[§3.2.4](07-data-api-gateway-section-3-sec3.md)）；而 query 重写恰恰需要理解语义。更危险的是同一个失效点——**边缘缓存键一旦不含身份 / 租户维度，A 租户的响应会被返回给 B 租户，而中心的权限检查根本没有被触发（请求没回源）。**
- **证据与来源**：【公开】Cloudflare 的 AI Gateway 与 Workers AI 属厂商公开产品，2024 年前后公开、有公开文档与 release note（读者可按其开发者文档核验功能清单与发布记录）；【公开】Cloudflare Workers 于 2018 年正式可用、AWS Lambda@Edge 于 2016 年发布（来源：两家厂商的公开公告）。「边缘跑小模型做 query 重写」与「AI 增强路由」均无第三方生产证据。
- **成熟度**：分两半，与 §5.1 表的两行一致——**边缘侧无语义判断（缓存 / 回退 / 重试 / 凭证托管）L2**；**边缘语义预处理与 AI 增强路由 L3**。
- **判定方法**：查两处——（1）边缘缓存键里有没有身份 / 租户维度（不含就是越权风险，与是否用了 AI 无关）；（2）边缘的 AI 功能清单里有没有「query 重写」这类需要语义的能力，如果有，问它怎么保证不与中心的权限判断冲突。

中心与边缘该各放什么，判据仍然是 [§3.2.2](07-data-api-gateway-section-3-sec3.md) 那条「每层只用自己看得懂的上下文」：

| 判断 | 放边缘可行吗 | 理由 |
| --- | --- | --- |
| 凭证是否有效、参数是否合法 | 可行 | 不需要数据语义，且能拦截大量无效回源 |
| 结果集能否命中缓存 | 可行 | 但**缓存键必须含身份 / 租户维度** |
| 后端失败时的重试与回退 | 可行 | 无语义判断，且就近失败更快 |
| 这次 query 该走 SQL 还是向量 | **不可行** | 需要理解 query 语义，越过了边缘的能力边界 |
| query 重写（补全、改写、扩写） | **不可行** | 同上，而且改写错了不报错、只出错答案 |
| 行级 / 列级权限判定 | **不可行** | 需要改写查询或解析结果集（[§3.2.3](07-data-api-gateway-section-3-sec3.md) 已给出失效分析） |

> 这张表判为「不可行」的行里，「这次 query 该走 SQL 还是向量」与「query 重写」两行正是「边缘 AI Gateway」被放到 L3 的原因——它们不是做不出来，而是**做出来之后，失败是静默的**：答案错了但没有任何一处报错；「行级 / 列级权限判定」那一行是同一处越界风险的旁证，它的失效形态是越权取数，不是错答案。「AI 增强路由」的同类风险发生在中心侧，见上文「由此付出的」第 ① 条。

### 5.3 与本主题既有栈的接口在哪

不要写「网关与 AI 结合」这种空话。下表写清**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Agent ↔ 数据网关 | 工具注册（能力名 + 参数 schema + 权限范围），MCP 类协议承载 | 网关负责鉴权与过滤；Agent 侧负责它自己的提示 | L2（试点，接口在演进） |
| 网关 ↔ 计量账本 | 执行统计上报（返回行数 / 扫描量 / Token）+「代表谁」 | 查询侧负责上报准确；网关负责落账与扣减 | L2（单位归一未定） |
| 网关 ↔ 审计 | 全量工具调用留痕（参数 + 返回 + 主体） | 网关；脱敏漏检由脱敏规则维护方承担 | L2（可做，但要按敏感数据管日志） |
| 网关 ↔ RAG / 向量库 / 图库 | 检索与查询 API 经网关（鉴权 + 计量） | 网关负责治理；语义正确性归后端 | L2（接口稳定） |
| 网关 ↔ LLM 供应商 | 多模型统一接入与回退 | 网关 | L2（各家 usage 口径不同） |
| 网关 ↔ 边缘节点 | 无语义判断的前置（缓存 / 回退 / 凭证托管） | 边缘；缓存键含身份是前提 | L2（前提满足才可做） |
| 网关 ↔ 数据权限 | 行级 / 列级改写下推（[§3.2.2](07-data-api-gateway-section-3-sec3.md)） | 网关 | 已有能力，非 AI 新增 |
| 网关 ↔ 查询引擎 / 数据服务 | 执行统计上报（返回行数 / 扫描字节） | 查询侧上报准确；网关负责落账与限流 | 需约定（它是按数据量限流与计量共同的前提） |
| 网关 ↔ 数据目录 | 能力名与业务含义的元数据来源（工具描述从这里取） | 目录负责元数据正确；网关负责执行与过滤 | 可做（没有目录元数据，工具描述只能靠手写） |

这张表里有三行是「与 AI 无关，但决定 AI 能不能用」的：

- **数据权限**：如果行级 / 列级权限还停在应用层后置过滤，那么 Agent 拿到的每一条数据都可能越权——而这与用哪个协议无关。
- **查询引擎 ↔ 网关的执行统计上报**：按数据量限流、按行数计量、判断一次 Agent 调用到底花了多少资源，全部依赖它。没有这条上报，网关只看得见请求、看不见消耗，[§3.6](07-data-api-gateway-section-3-sec3.md) 那条「QPS 没变但单请求形状变了」的跃迁就永远无法被及时发现。
- **数据目录 ↔ 网关**：工具描述里的「能力名 + 业务含义」只能从元数据来；没有目录，工具描述就退回成手写字符串，而手写的描述会随数据变化而过期。

还要写清一个前提：**以上接口全部建立在「所有取数都经过同一个点」之上**（[§3.1](07-data-api-gateway-section-3-sec3.md) 的出口收敛）——多一个绕过网关的出口，Agent 侧的脱敏、计量与审计就同时失效。

### 5.5 被过度宣传的部分

**「网关能防住提示注入」** —— 实际是：网关能做的是**输出侧脱敏、全量审计、把权限收窄到「代表谁」**，这三件都不依赖识别注入；而「识别并拦截」在原理上做不到，因为数据与指令共享同一个 token 流，没有任何语法标记能把它们分开。为什么会这样：WAF 的成功建立在「畸形输入在语法上就可疑」之上，而注入的输入完全合法。什么时候它才会成真：当模型调用链上出现**可强制、可验证的权限边界**——例如工具调用必须携带由网关签发、且权限等同于发起人的能力令牌，使「被诱导」能造成的最坏损失有确定上界。**那是授权模型的进展，不是检测模型的进展**；判定信号是这类令牌成为协议的一部分，而不是某家网关宣称的检出率。

**「MCP 会成为数据消费的事实标准，像 LSP 之于编辑器」** —— 实际是：这个类比漏了两处要害。①**LSP 的两侧是同一个开发者的两套软件**（编辑器与语言工具链的作者利益一致），而数据工具的两侧是**彼此不信任的双方**（提供数据的团队与消费数据的 Agent 使用者）；②**LSP 不承载计量与配额，MCP 类协议要承载**（§5.2.2 的账本主键）。为什么会这样：只要协议要表达「谁代表谁、额度多少、读了哪些字段」，它的规范复杂度就远高于 LSP，稳定化需要的时间也更长。什么时候它才会成真：出现**由非发起方主导、带日期的兼容性测试套件**，且跨实现的兼容问题不再靠逐个适配解决——判定信号是「同时支持多个实现的第三方库」是否出现并有人维护。

**「Token 计量就是 AI 时代的数据 API 计费」** —— 实际是：数据 API 的成本主体是**扫描量与结果集**，不是 Token——一个 Agent 可以用很少的 Token 触发一次全表扫描，账单上却看不出这件事。为什么会这样：Token 计的是「对话成本」，坐在模型调用那一侧；网关要计的是「资源成本」，坐在查询执行那一侧，两者在不同的资源池上。什么时候它才会成真：当**同一次调用能同时拿到 Token 用量与执行统计（扫描字节 / 返回行数），并且二者之间建立了可公示的换算关系**时；判定信号是网关的计量日志里是否同时存在两类单位（§5.2.2 的判定方法）。

### 5.6 未来 3–5 年：可证伪的预测

每条都写成「预测 + 会成真的信号 + 会证伪的信号」。写不出信号的，不写。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| Agent 的数据调用会被要求「代表某个具体的人」，匿名或纯服务账号式的 Agent 凭证会被合规淘汰 | 审计或监管材料明确要求 Agent 调用可追溯到自然人；网关产品出现「on-behalf-of」为一等公民的配置项 | 3 年后主流架构仍以服务账号为主，且无因 Agent 越权导致的处罚或公开事故 |
| 网关的计量单位会从单一变成两类并存（成本单位 + 资源单位） | 网关产品的计量配置里出现两种单位与换算配置；计量日志默认带执行统计 | 产品只保留 Token 一种单位，并明确放弃行数 / 扫描量 |
| MCP 类协议会继续发生不带向后兼容的修订，跨实现兼容要靠适配层 | 规范页出现新的日期版本并标注不兼容；社区出现「协议版本兼容层」类项目 | 连续 24 个月只有向后兼容的增量修订 |
| 边缘侧不会承担语义判断 | 主流边缘平台的 AI 网关功能清单长期只有缓存 / 重试 / 回退 / 凭证托管，没有 query 重写 | 边缘出现可配置的 query 重写并被生产采用，且有公开案例证明它不与中心权限判断冲突 |

四条预测的共同点是**都能用一个可观测事实证伪**，不需要等到有人写复盘。这也是它们与「AI 网关会成为标配」这类句子的区别——后者按今天的趋势看永远正确，因而没有信息量。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 还没有网关（数据服务直连可用） | **先收敛出口**：网络层只放行网关网段，存量调用方分批迁移 | 是否仍存在绕过网关能取数的路径 | **不要**先上 AI 网关或 MCP——出口没收敛时，接协议只是多一个入口 |
| 网关已上线、限流按 QPS | 补一层按「返回行数 / 扫描量」的限流与配额；计量日志增加资源单位 | 单次请求耗时与返回行数的 P99 是否在动（它们先于 QPS 变化） | **不要**因为「还没出事」就跳过这一层：慢查询不吃 QPS 额度 |
| Agent 已进生产（不只是实验） | 把 Agent 纳入同一网关：强制脱敏、强制审计、额度挂到「它代表的人」 | 审计能否还原一次完整工具调用；有多少条调用定位不到主体 | **不要**给 Agent 独立的高权限凭证；不要为它单开一条绕过网关的链路 |
| 正在评估 AI 网关 / MCP 类协议 | 做一个只读工具的最小闭环，把「工具清单 ↔ API 清单」对齐 | 协议版本是否发生不带兼容的修订 | **不要**一次开放写入类或导出类能力；不要把它设为核心依赖 |
| 有跨区调用方、重复查询多 | 边缘只放缓存 / 回退 / 凭证托管，**缓存键必须含身份 / 租户维度** | 边缘侧是否开始承接需要语义的能力 | **不要**在边缘跑模型重写 query；不要用 AI 增强路由处理核心取数路径 |
| 被要求「网关要防住提示注入」 | 把预算转到三件可核验的事：输出侧脱敏、全量审计、权限等于代表的人 | 这三件是否覆盖了全部出口 | **不要**采购「检出率 XX%」的注入检测作为主要防线 |

**自检清单**（每条都对应上文一个机制，答「否」的地方就是本主题下你的真实风险）：

- [ ] 是否存在任何一条绕过网关能直达数据服务的网络路径？
- [ ] 计量日志能否同时回答「谁用的」与「用了多少资源」两个问题（单位含行数 / 扫描量吗）？
- [ ] 每一次 Agent 工具调用，能否定位到「它代表谁」？
- [ ] Agent 凭证的权限是否**等于且不高于**它代表的人的权限？
- [ ] 「对 Agent 可见的能力」这份清单，与网关外实际存在的 API 清单是否对得上？
- [ ] 审计日志里含不含原始返回内容？如果含，它是否按敏感数据来管（留存、访问、跨境）？
- [ ] 输出侧脱敏规则覆盖哪些字段？上一次更新是什么时候？谁维护？
- [ ] 限流除了请求数，是否覆盖了返回行数 / 扫描量？
- [ ] 边缘缓存（若有）的缓存键是否含身份 / 租户维度？
- [ ] 是否在用「检测并拦截注入」作为主要安全防线？如果不是它，替代的三件事是哪三件？
- [ ] 多模型接入时，各家 usage 字段的归一由谁负责、口径写在哪儿？
- [ ] 新增一个 Agent 取数能力时，需要改动的系统有几个（超过 2 个，说明统一入口没做成）？

### 5.8 小结

> 本节小结：本主题下真正改到资源模型上的机制只有一条——**网关的账本主键**从「请求数」变成「资源单位」（返回行数 / 扫描量 / Token）、鉴权主体从一个变成两个（Agent + 它代表的人）（§5.2.2）；另外三组改的是接口形状与判断依据，都不动账本：**入口**把「路径」换成「能力名 + 参数 schema」（§5.2.1），**安全**要面对的输入从语法畸形变成语义合法（§5.2.3），**路径**把路由依据从请求元数据换成请求内容（§5.2.4）——安全侧新增的也主要是「审计与脱敏必须覆盖到 Agent」这一条旧要求。而 [§3.1](07-data-api-gateway-section-3-sec3.md) 那条约束没有变：**网关能看见多少数据语义**，仍然决定了它能不能限住慢查询、能不能做行级权限——AI 没有让这条约束松动一分。所以本主题下最该做的事，仍然是前 AI 时代那两件：**先把出口收敛成一个点，再把计量单位与鉴权主体补上去。**
>
> 💡 **思考锚点**：翻一次你们的网关计量日志，看同一栏能不能同时读出「谁」（含 Agent 与它代表的人）和「用了多少资源」——单位是请求数，还是返回行数 / 扫描量？§5.2.2 说账本主键要从请求数换成资源单位；若还在按请求数记账，那些一次扫几亿行的慢查询靠什么限住？
