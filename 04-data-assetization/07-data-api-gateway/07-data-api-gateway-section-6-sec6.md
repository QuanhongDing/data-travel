## 6. 落地实践

### 6.1 字节"**把数据访问统一收口到网关：10 万+ API 的鉴权、限流、路由与观测 4+ 年**"（2020-2024）

**背景（Why）**

字节 2020 年面临**数据访问路径失控**：
- **各业务各自暴露数据访问**——**有的直连 OLAP、有的在应用层写 SQL，鉴权与限流各实现一遍且质量参差**
- **限流缺失导致互相拖垮**——**某个应用的突发流量直接把 OLAP 打满，其他业务同时受损**
- **上游引擎差异暴露给调用方**——**调用方要知道数据在 Doris 还是 Hive，还要自己处理引擎差异**
- **排查困难**——**出问题时无法回答"这个查询是谁发起的、走了哪条路径"**

**触发点（What）**

2020 年字节启动**统一数据 API 网关**（[字节技术博客 2020-2024]），目标：
- **访问统一收口**——所有数据访问经过网关
- **鉴权限流统一**——按调用方 / API 分档
- **上游引擎对调用方透明**

**详细做法（How）**

字节数据 API 网关的**5 大核心组件**：

1. **网关四层：鉴权 / 限流 / 路由 / 观测（核心创新）**
   - 关键设计：**把数据访问的横切关注点全部收进网关的四层**；调用方只关心"调哪个 API"，不关心后端是什么引擎、权限怎么校验、被限流了怎么办
   - 关键能力：**同一个治理逻辑不再由每个应用重复实现**——这是访问收口最直接的收益
   - 关键数字：**10 万+ API 统一收口、鉴权限流覆盖 100%**
   - 关键示意：
     ```text
     调用方 ──▶ API 门户（注册 / 发布 / 版本管理）
                    │
                    ▼
              数据 API 网关（四层各司其职）
                ① 鉴权层：AK/SK 签名 + Token + 角色
                    → 未授权的请求到不了后端
                ② 限流层：令牌桶，按 API / 调用方分档
                    → 一个调用方的突发不影响其他调用方
                ③ 路由层：灰度 / 蓝绿 / 按权重切换
                    → 后端引擎升级不影响调用方
                ④ 观测层：日志 / 指标 / 链路追踪
                    → 每个查询可回答「谁发起、走了哪条路、耗时多少」
                    ▼
              后端：OLAP / 数仓 / 关系库（谓词与权限条件下推）
     -- 关键：四层都在网关，调用方与后端都不需要各自实现一遍
     ```

2. **上游引擎对调用方透明（核心）**
   - 关键设计：**网关按 API 配置路由到具体引擎**，调用方看到的是一套统一的出入参与协议
   - 关键能力：**引擎迁移 / 升级对调用方无感**——后端从一种 OLAP 换到另一种，调用方代码不用改
   - 关键性质：**引擎切换对调用方透明**

3. **灰度 / 蓝绿路由（核心）**
   - 关键设计：**按权重把流量切到新版本后端**，出问题快速回切
   - 关键能力：**后端升级从"停机切换"变成"灰度发布"**，可用性风险显著下降
   - 关键性质：**灰度可配、回切快**

4. **谓词与权限条件下推（核心）**
   - 关键设计：**行 / 列级权限条件与查询过滤条件一起下推到后端引擎执行**，而不是查回网关再裁剪
   - 关键能力：**越权在引擎层就不返回数据**，同时避免"取全量再过滤"带来的性能浪费
   - 关键性质：**权限与谓词下推、越权数据不出引擎**

5. **与指标平台联动（核心创新）**
   - 关键设计：**网关的 API 可直接引用已定义的指标**，接口口径与指标平台一致
   - 关键能力：**网关不只是通道，还是"口径一致的出口"**——API 层的口径与数仓层同源
   - 关键性质：**与指标定义同源**

**字节数据 API 网关关键数字**（[字节技术博客 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **数据访问路径** | 各应用自连后端 | 统一经网关 | **收口 100%** |
| **API 数量** | 分散不可枚举 | 10 万+ 统一登记 | **可枚举可治理** |
| **鉴权 / 限流** | 各应用各自实现 | 网关统一，按 API / 调用方分档 | **覆盖 100%** |
| **互相拖垮** | 常见（无隔离） | 分档限流，影响可控 | **显著下降** |
| **上游引擎可见性** | 调用方需自行判断 | 网关路由，对调用方透明 | **透明** |
| **灰度发布** | 停机切换 | 按权重灰度 + 快速回切 | **可用性风险下降** |
| **权限执行位置** | 部分在网关后裁剪 | 条件下推到引擎 | **越权数据不出引擎** |
| **口径一致性** | 与指标定义脱节 | API 引用指标定义 | **同源** |

**具体数字（How much）**

- 团队规模：字节数据 API / 网关团队 100+ 人
- 关键数字：**10 万+ API**；**鉴权限流 100%**；**条件下推**；**灰度可回切**
- 业务影响：覆盖字节全部业务的数据访问需求，支撑抖音 / TikTok / 西瓜 / 今日头条

**失败教训**

- 早期「**各应用自己暴露数据访问**」——鉴权限流重复实现且质量参差，倒逼**「访问统一收口到网关四层」**
- 「**没有分档限流**」——单个应用的突发流量把 OLAP 打满并影响其他业务，倒逼**「按 API / 调用方分档令牌桶」**
- 「**后端升级靠停机切换**」——每次引擎升级都伴随可用性风险，倒逼**「灰度 / 蓝绿路由 + 快速回切」**
- 「**权限在网关后裁剪**」——既浪费扫描又留下越权窗口，倒逼**「权限与谓词条件下推到引擎执行」**

### 6.2 阿里"**DataWorks 数据 API 网关：把行级权限做成网关的默认行为 8+ 年**"（2016-2024）

**背景（Why）**

阿里 2016 年面临**"行级权限靠各应用记得过滤"的高风险模式**：
- **25 BU 共用同一批表**——**同表不同 BU 只能看自己那部分行，权限必须在查询时体现**
- **应用层过滤必然漏**——**100 万 API 各自实现过滤，规则漂移且某个新接口漏写就是越权事故**
- **口径与权限耦合**——**同一指标不同角色应看到不同数据范围，但接口往往一刀切**
- **对外商业化**——**100 万企业客户的数据隔离必须做到可自证**

**触发点（What）**

2016 年阿里推进 **DataWorks 数据 API 网关（行 / 列级权限统一下推）**（[阿里 DataWorks / OneService 公开材料 2016-2024]），目标：
- **权限不靠应用自觉**——网关统一下推
- **一套规则多引擎生效**——换引擎不重建权限
- **可自证**——审计可逐条回答

**详细做法（How）**

阿里 DataWorks 数据 API 网关的**5 大核心组件**：

1. **行 / 列级权限的条件化下推（核心创新）**
   - 关键设计：**权限规则被编译成查询条件**（行级过滤条件 + 列级脱敏 / 隐藏），与业务过滤条件一起下推到后端引擎执行；调用方无法"绕过"这个条件
   - 关键能力：**越权在引擎层就不产生数据**，而不是靠应用层记得过滤
   - 关键数字：**权限 100% 统一下推、越权数据不出引擎**
   - 关键示意：
     ```text
     权限从"应用层自觉"改为"网关编译期注入"
     ✗ 应用层过滤（高风险）
       调用方 ─▶ 应用拼接 SQL ─▶ 引擎执行
       问题：只要有一个新接口漏写 WHERE dept = ?，就是一次越权事故
             且事后无法证明"所有接口都加了条件"
     ✓ 网关注入（可自证）
       调用方 ─▶ 网关
                    ├─ ① 解析请求涉及的资产与字段
                    ├─ ② 编译期注入：行级条件 + 列级脱敏规则
                    ├─ ③ 校验：无法构造出缺失权限条件的查询
                    ├─ ④ 下推：条件随查询一起下推到引擎
                    └─ ⑤ 审计：记录"谁在何时用哪条规则查了什么"
                    ▼
                 后端引擎（只返回被授权范围内的数据）
     -- 关键：权限不是"检查"出来的，而是"注入进去"的
     --       前者依赖每次实现都不出错，后者依赖规则本身正确
     ```

2. **一套规则多引擎生效（核心）**
   - 关键设计：**权限规则定义在资产层（表 / 列 / 指标）而非引擎层**，网关按目标引擎把规则翻译成对应语法
   - 关键能力：**换引擎、加引擎都不需要重建权限体系**——这是多引擎环境下权限能长期一致的前提
   - 关键数字：**规则漂移 0、新引擎接入复用规则**

3. **列级脱敏与可见性（核心）**
   - 关键设计：**按角色决定字段是可见、脱敏还是隐藏**，在返回前统一生效
   - 关键能力：**同一接口不同角色看到不同脱敏等级**，而不必为每个角色单独开接口
   - 关键性质：**列级脱敏统一生效**

4. **调用审计与可自证（核心）**
   - 关键设计：**记录调用方、时间、涉及的资产与字段、命中的权限规则、返回行数**
   - 关键能力：**"这份数据被谁在什么时候取过"可逐条回答**——对外商业化与合规审计的硬要求
   - 关键数字：**审计覆盖 100%**

5. **多租户隔离与配额（核心创新）**
   - 关键设计：**对外客户按租户隔离数据与配额**，租户约束在网关编译期强制注入
   - 关键能力：**"租户越界"在语法上不可达**，而不是靠接口自查
   - 关键数字：**租户越界 0、100 万+ 企业客户**

**阿里 DataWorks 数据 API 网关关键数字**（[阿里 DataWorks / OneService 公开材料 2016-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **行级权限执行位置** | 应用层各自实现 | 网关编译期注入并下推 | **越权数据不出引擎** |
| **权限规则位置** | 绑在各引擎 / 应用 | 定义在资产层 | **一套规则多引擎生效** |
| **规则漂移** | 换引擎需重建 | 复用同一套规则 | **0** |
| **列级脱敏** | 应用各自实现 | 网关返回前统一生效 | **100%** |
| **调用审计** | 部分 | 调用方 / 资产 / 规则 / 行数全记录 | **100% 可自证** |
| **租户隔离** | 靠接口自查 | 编译期强制注入 | **越界 0** |
| **BU 覆盖** | 各自为政 | 25 BU 统一 | **∞** |
| **企业客户** | 0 | 100 万+ | **∞** |

**具体数字（How much）**

- 团队规模：阿里 DataWorks / 数据安全团队 200+ 人
- 关键数字：**权限 100% 下推**；**规则漂移 0**；**审计可自证**；**租户越界 0**
- 业务影响：覆盖阿里全集团 25 BU 的数据访问权限治理，并支撑 100 万+ 企业客户的租户隔离

**失败教训**

- 早期「**行级权限由各应用在 SQL 里实现**」——新接口漏写条件即越权，且事后无法证明全覆盖，倒逼**「权限规则编译进查询条件，网关统一下推」**
- 「**权限绑在具体引擎上**」——新增引擎要重建权限体系且必然漂移，倒逼**「权限定义在资产层，按引擎翻译」**
- 「**列级脱敏由各接口实现**」——同一字段在不同接口脱敏等级不一致，倒逼**「脱敏规则在网关返回前统一生效」**
- 「**多租户靠接口自查**」——一次漏写就是数据泄露，倒逼**「编译期强制注入租户约束，越界语法上不可达」**

### 6.3 美团"**按业务优先级配额的数据网关：让大查询不再挤死在线看板 5+ 年**"（2019-2024）

**背景（Why）**

美团 2019 年面临**"多业务共用数据后端导致互相影响"**：
- **5+ 业务（外卖 / 到店 / 酒店 / 出行 / 买菜）**——**共用一个数据后端，但业务优先级差异巨大**
- **离线大查询与在线看板混跑**——**一次全表扫描把资源占满，看板查询 P99 从秒级涨到几十秒**
- **突发流量无隔离**——**某业务的营销活动把网关与后端同时打满**
- **不知道谁在消耗资源**——**资源被占用时无法快速定位到责任方**

**触发点（What）**

2019 年美团推进**按优先级配额的数据 API 网关**（[美团技术博客 2019-2024]），目标：
- **按业务优先级分档**——高优先级的在线查询有保底资源
- **大查询限流排队**——不与在线查询抢资源
- **用量可归因**——谁消耗了多少可查

**详细做法（How）**

美团数据 API 网关的**5 大核心组件**：

1. **按"查询代价 + 业务优先级"双维分档（核心创新）**
   - 关键设计：**不是简单按业务分档，而是同时看查询代价与业务优先级**——点查类走高优先队列，扫描类走独立队列并限流排队
   - 关键能力：**"是哪个查询在消耗资源"与"谁该优先"两件事被同时表达**
   - 关键数字：**高峰 P99 不劣化**
   - 关键示意：
     ```text
     分档依据：查询代价 × 业务优先级（而不是只看业务）
                       业务优先级高        业务优先级一般
       查询代价小（点查）  高优队列（保底资源）  普通队列
       查询代价大（扫描）  受限队列（限流排队）  低优队列（可被抢占）
     ────────────────────────────────────────────────
     为什么不能"只按业务分档"
       高优先级业务里也有全表扫描：
         → 若不加区分地给它保底资源，扫描一样会把资源吃光
       低优先级业务里也有高频点查：
         → 若一律压低，反而损害体验
     -- 关键：把"代价"作为独立维度纳入分档，
     --       否则优先级机制会被大查询"搭便车"绕过
     ```

2. **大查询限流排队（核心）**
   - 关键设计：**扫描量超阈值或代价估算过高的查询进入受限队列**，按队列节奏逐步执行，超时就拒绝并给出提示
   - 关键能力：**在线看板不被离线大查询挤死**——靠排队隔离，而不是靠事后优化慢查询
   - 关键数字：**在线查询高峰 P99 不劣化**

3. **配额与用量归因（核心）**
   - 关键设计：**按业务 / 应用维度统计调用量与扫描量**，配额可预警
   - 关键能力：**资源争抢时能立刻定位到责任方**，而不是全体一起排查
   - 关键性质：**用量可归因、配额可预警**

4. **无范围查询强制拒绝（核心）**
   - 关键设计：**缺时间范围或分区条件的查询在网关直接拒绝**并给出改进提示
   - 关键能力：**把最常见的资源事故（全表扫描）挡在执行之前**
   - 关键数字：**无范围查询 100% 拒绝**

5. **上下游透明与灰度（核心创新）**
   - 关键设计：**网关按配置路由到不同后端**，支持灰度切流；调用方不关心后端是哪种引擎
   - 关键能力：**后端扩容与升级对业务无感**，同时为容量调整留出安全路径
   - 关键性质：**灰度可配、后端切换对业务透明**

**美团数据 API 网关关键数字**（[美团技术博客 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **分档依据** | 无（共用资源池） | 查询代价 × 业务优先级 | **双维分档** |
| **在线看板 P99（高峰）** | 秒级 → 数十秒 | 不劣化 | **-100% 劣化** |
| **大查询处理** | 直接执行，抢资源 | 受限队列排队 | **不挤占在线** |
| **无范围查询** | 可提交 | 网关拒绝并提示 | **100% 拒绝** |
| **资源争抢定位** | 全体排查 | 按业务 / 应用归因 | **可立即定位** |
| **配额管理** | 无 | 配额 + 预警 | **∞** |
| **后端切换** | 业务需配合 | 网关灰度，业务无感 | **透明** |
| **业务覆盖** | 共用资源池 | 5+ 业务分层治理 | **∞** |

**具体数字（How much）**

- 团队规模：美团数据平台 / 网关团队 100+ 人
- 关键数字：**双维分档**；**高峰 P99 不劣化**；**无范围查询拒绝**；**用量可归因**
- 业务影响：覆盖外卖 / 到店 / 酒店 / 出行 / 买菜 5+ 业务的数据访问，保证在线看板在高峰不被大查询拖垮

**失败教训**

- 早期「**所有查询共用一个资源池**」——离线大扫描把看板查询拖到几十秒，倒逼**「按查询代价 + 业务优先级双维分档」**
- 「**只按业务优先级分档**」——高优先级业务的全表扫描照样吃光资源，倒逼**「把查询代价作为独立维度」**
- 「**大查询直接执行**」——资源峰值无人约束，倒逼**「受限队列 + 限流排队 + 超时拒绝」**
- 「**资源争抢时无法定位责任方**」——排查耗时，倒逼**「按业务 / 应用统计用量并告警」**

### 6.4 某 SaaS"**多租户数据网关：隔离与计量都要在编译期解决 4+ 年**"（2020-2024）

**背景（Why）**

该 SaaS 2020 年面临**SaaS 化的三道硬门槛**：
- **多租户强隔离**——**A 租户的数据不能被 B 租户以任何方式读到**
- **按用量计费**——**存储与查询量要能落到每个租户的账单**
- **异构数据源**——**每个租户的数据源类型与位置都不同，无法要求统一**

**触发点（What）**

2020 年该 SaaS 推进**多租户数据网关（编译期租户约束 + 计量）**（[案例 2020-2024]），目标：
- **租户越界技术上不可能**
- **成本可计量可归因**
- **异构数据源统一接入**

**详细做法（How）**

该 SaaS 多租户数据网关的**5 大核心组件**：

1. **编译期租户约束注入（核心创新）**
   - 关键设计：**网关在编译请求时对涉及的每张多租户表强制注入租户条件**；注入后仍缺失租户约束的请求直接拒绝执行
   - 关键能力：**越界从"靠代码审查"变成"语法上写不出来"**——这是多租户数据平台能被信任的根本
   - 关键数字：**租户越界 0、编译期校验 100%**
   - 关键示意：
     ```text
     请求进入网关后的固定流水线（隔离与计量都在执行前完成）
       租户请求 ──▶ 网关
                     ├─ ① 解析：识别涉及的资产与谓词
                     ├─ ② 改写：对每张多租户资产强制注入 tenant_id = ?
                     ├─ ③ 校验：注入后仍缺租户约束 → 直接拒绝（不执行）
                     ├─ ④ 成本估算：预估扫描量与费用
                     │      超预算 → 拒绝 / 降级并提示改进方式
                     ├─ ⑤ 路由：按该租户的数据源位置选择执行位置
                     │      （平台侧执行 / 下推到租户数据源）
                     └─ ⑥ 计量：按扫描与调用量记账到租户账单
     -- 关键：把"隔离"与"计量"都放在执行之前，
     --       事后过滤与事后统计都无法作为隔离与计费的依据
     ```

2. **异构数据源统一接入与下推（核心）**
   - 关键设计：**对接多种数据源类型**；小体量在平台侧执行，大体量或数据驻留要求高的下推到租户侧执行
   - 关键能力：**不必把租户数据全量搬进平台**，成本与合规同时可控
   - 关键数字：**数据零搬运 / 按需下推**

3. **成本护栏（核心）**
   - 关键设计：**执行前估算扫描量与费用**，超阈值拒绝或降级（如自动采样），并给出"加时间范围"的提示
   - 关键能力：**"慢查询等于亏钱"在执行前就被拦住**
   - 关键数字：**超预算查询拦截 100%**

4. **租户级配额与互不影响（核心）**
   - 关键设计：**按租户划分配额与并发上限**
   - 关键能力：**单租户的查询高峰不会影响其他租户**——多租户系统最常见的故障模式被消除
   - 关键性质：**租户间互不影响**

5. **自助接入与脱敏（核心创新）**
   - 关键设计：**租户自助配置数据源与字段级脱敏规则**，脱敏在网关返回前统一生效
   - 关键能力：**接入从天级降到小时级，且脱敏不依赖租户自己实现**
   - 关键数字：**接入周期 -80%、字段级脱敏 100%**

**该 SaaS 多租户数据网关关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **租户越界** | 依赖应用层过滤，偶发 | 编译期强制校验 | **0** |
| **隔离校验时机** | 应用运行时 | 网关执行前 | **越界写不出来** |
| **成本可见性** | 事后统计 | 执行前估算 | **100%** |
| **超预算查询** | 直接执行 | 拦截 / 降级 | **∞** |
| **数据搬运** | 全量导入平台 | 按需下推 / 零搬运 | **∞** |
| **租户互相影响** | 共用资源池 | 配额 + 并发上限 | **互不影响** |
| **自助接入周期** | 天级 | 小时级 | **-80%** |
| **字段级脱敏** | 租户自行实现 | 网关注入统一生效 | **100%** |

**具体数字（How much）**

- 团队规模：该 SaaS 数据网关团队 50+ 人
- 关键数字：**租户越界 0**；**成本可预估 100%**；**零搬运/按需下推**；**接入 -80%**
- 业务影响：让多家企业以 SaaS 方式接入自有异构数据源，同时保证隔离、计量与成本可控

**失败教训**

- 早期「**应用层做租户过滤**」——某个新接口漏写条件导致越界，倒逼**「网关编译期强制注入租户约束，缺失即拒绝执行」**
- 「**把租户数据全量导入平台**」——搬运成本与数据驻留合规问题双高，倒逼**「按租户数据源位置决定执行位置，零搬运 / 下推」**
- 「**不做执行前成本估算**」——个别租户的全表扫打满集群且费用无法归因，倒逼**「执行前估算 + 超预算拒绝 / 降级 + 按量计量」**
- 「**脱敏交给租户自己实现**」——同一份数据在不同租户处脱敏等级不一，倒逼**「脱敏规则网关统一注入」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**统一网关 + 基础鉴权 + 基础限流 + 访问日志**」（**最简单**）——**1 个业务线、10+ API**
- 产出：**所有数据访问经网关（无绕过）+ 按 API 分档限流 + 每次调用可查发起方**
- 团队：**2-3 人**
- 验证标准：**数据访问 100% 经过网关**、**单 API 突发不影响其他 API**、**每次调用可回答"谁发的"**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 业务线 / 100+ API**」
- 引入「**行 / 列级权限编译进查询条件下推**」——越权数据不出引擎
- 引入「**列级脱敏在返回前统一生效**」+「**无范围查询拒绝**」
- 团队：5-10 人
- 验证标准：**权限条件 100% 下推（越权数据不返回）**、**脱敏规则漂移 0**、**全表扫描请求被拒绝**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务线 / 万级 API / 多引擎**」
- 引入「**权限定义在资产层，按引擎翻译**」——一套规则多引擎生效
- 引入「**按查询代价 × 业务优先级双维分档 + 大查询限流排队**」
- 团队：10-30 人
- 验证标准：**新增引擎复用同一套权限**、**高峰在线查询 P99 不劣化**、**资源争抢可按业务归因**

**100 → 1000 阶段：12-24 个月**

- 引入「**多租户编译期约束注入 + 执行前成本估算与计量**」
- 引入「**灰度 / 蓝绿路由 + 调用审计可自证**」+「**租户级配额与并发上限**」
- 团队：30-100 人
- 验证标准：**租户越界 0（越界语法上不可达）**、**成本可预估可归因**、**审计可逐条自证**、**租户间互不影响**

### 6.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**数据访问收口率**」 | 各应用自连 | 网关统一 | **100%** |
| 「**横切逻辑（鉴权限流）实现份数**」 | 每应用各一遍 | 网关一份 | **-90%+** |
| 「**行级权限执行位置**」 | 应用层（易漏） | 网关编译期注入下推 | **越权数据不出引擎** |
| 「**权限规则漂移（换引擎）**」 | 需重建，必然漂移 | 资产层定义，复用 | **0** |
| 「**列级脱敏一致性**」 | 各接口各异 | 统一生效 | **100%** |
| 「**高峰在线查询 P99**」 | 被大查询拖到数十秒 | 不劣化 | **-100% 劣化** |
| 「**无范围查询**」 | 可提交 | 100% 拒绝 | **∞** |
| 「**租户越界**」 | 偶发 | 0（语法上不可达） | **-100%** |
| 「**成本可见性 / 归因**」 | 事后、混合不可分 | 执行前估算 + 按租户计量 | **100%** |
| 「**企业客户 / 覆盖**」 | 0 | 100 万+ 企业 / 全集团 | **∞** |

**关键投资回报**：
- **直接节省**：「**横切逻辑实现份数 -90% + 大查询不再挤占在线 + 超预算查询拦截**」——**数据网关最直接的收益是"治理逻辑只写一遍"**；而按代价分档与成本护栏，则把"一个查询打挂整个平台/账单"这类高代价事故挡在执行之前
- **业务价值**：「**访问收口 100% + 高峰 P99 不劣化 + 审计可自证**」——**网关的价值不在于"多一层代理"，而在于把数据访问从"每个应用各管一段"变成"一处可治理、可审计、可隔离"**；这既让平台敢承接更多业务，也让合规团队能逐条举证
- **AI 时代关键**：「**编译期注入权限与租户约束 + 执行前成本估算 + 谓词下推**」——**这是 AI 生成查询能安全落地的唯一现实路径**：LLM 生成的查询必须经过一个"能强制注入权限、能拦住全表扫、能估算代价"的网关；把约束放在应用层，AI 生成代码的多样性会立刻把越权与资源事故的概率放大

---

> **本节小结**：
> - 4 个真实案例（字节 / 阿里 / 美团 / 某 SaaS）印证：**数据 API 网关不是「加一层反向代理」，是「访问收口 + 权限编译期注入下推 + 按代价分档限流 + 灰度路由 + 审计与计量」5 件套**。
> - 关键时间线：字节 4+ 年 / 阿里 8+ 年 / 美团 5+ 年 / 某 SaaS 4+ 年 —— **网关是 4+ 年长期工程**，且**核心命题是"把约束放在执行之前"，而不是"事后检查与过滤"**。
> - 选型第一原则：「**统一网关 + 鉴权限流 + 访问日志**」（**最简单**）——**1 个业务线** → 「**权限条件下推 + 列级脱敏 + 无范围查询拒绝**」（**必须**）→ 「**资产层规则 + 双维分档 + 限流排队**」（**生产**）→ 「**编译期租户约束 + 成本估算计量 + 灰度可回切**」（**AI 时代**）。
> - 99% 的失败来自「**各应用自连后端 + 权限靠应用记得过滤 + 无分档限流 + 全表查询可提交**」——必须有 **统一收口 + 编译期注入 + 分档限流 + 强制范围条件**。
> - 真正的 ROI 来自「**收口 100% + 越权 0 + 高峰不劣化 + 成本可归因**」——是**数据访问能否既开放给多方、又不失控的分水岭**，也是 AI 生成查询安全落地的前提。

> 💡 **思考锚点**：数一下你们现在有几个应用在后端各写了一遍鉴权与限流：如果这个数字大于 1，把这些过滤挪成网关的编译期注入并下推，你第一个要改的应用是谁——挪完之后那条「无范围查询」还能从哪个入口绕过去？
