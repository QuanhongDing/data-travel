## 4. 工程实现

[§ 3](08-data-catalog-section-3-sec3.md) 回答的是「集中式 / 联邦式 / 事件驱动 / 湖仓一体 / AI 增强 / 图谱式各自被哪条约束逼出来、代价与失效点在哪」。本节回答下一个问题：**这套东西按什么顺序装上去、每一步拿什么判断自己做对了、以及装的过程中已有的那几万张表怎么办。**

> **证据档位**：本节【公开】给出来源与年份；【推算】写出推导链；**沿用公开案例的数字一律按【经验】使用——只取量级、不取精确值**。产品能力、版本号与发布年份请以各产品官方文档当前版本为准，读者可按产品名 + 关键词自行检索核验。

本文件对两类读者的入口不同。**从零搭目录的人**（还没有权威元数据源）按 4.1 的 Step 1–4 顺着走，4.5 的示例 1、2 就是这一段的交付物。**在存量上改造的人**（已有 Atlas / DataWorks 一类的元数据库、已有几万张表在跑）从 4.4 读起，再回头补 4.1 的 Step 2 与 Step 6——存量改造的返工几乎全部来自这两步被跳过。

### 4.1 落地步骤

**Step 1：需求与边界（【经验】1–2 周，随要覆盖的源类型数与干系人数量变）**

- 明确目录覆盖范围：数仓 / 湖仓 / DB / API / 文档，逐类写下第一版覆盖到哪一层。
- 评估用户：业务 / 数据 / AI 三类，各写下他们明天就会问的第一个问题。
- 写一份「第一版不覆盖什么」，与覆盖清单同等对待。
- **产物**：目录需求说明书（覆盖清单 + 不覆盖清单 + 三类用户各自的第一个问题）。
- **判据**：拿那三个真实问题（如「上季度各省的销量在哪张表」「哪些表含手机号」「Agent 能调哪些 API」）去对覆盖清单，任一问题答不上来，说明范围漏了一类源或一类用户。
- **为什么必须这一步**：因为采集端与数据源一一耦合——每接一种源就要多写一个采集器、多一份长期维护成本（[§ 3](08-data-catalog-section-3-sec3.md) §3.2.1 代价①）。范围没定就开工，等于把采集器的数量放进不可控状态；而这一步几乎是全流程里唯一改动成本为零的步骤。

**Step 2：元数据模型设计（【经验】1–3 周，随资产类型数变）**

- 设计 Asset 模型（Table / Field / API / MLModel / Dashboard）、Lineage 模型、Tag / Owner / Classification 模型。
- 把关键约束落到写入时：URN 全局唯一、Owner 非空、密级非空、采集时间必填。
- 事件模型单独版本化（它是长期契约，改一次影响所有消费方）。
- **产物**：元数据 Schema（DDL + 事件 schema 版本号）。
- **判据**：让两个人各自回答「这张表归谁、什么密级、什么时候采的」，看答案是否能从库里直接查出来；再抽 3 条记录，看 `Owner` 写的是人名还是团队名。
- **为什么必须在这一位置**：因为一致性只能靠写入时约束保证，而约束上线后再补，历史数据必须补录——补录速度永远追不上变更速度（[§ 3](08-data-catalog-section-3-sec3.md) §3.2.1 结构块的对照注释〔「无人维护」的物理起点〕与 §3.5 的「无人维护」一行）。它也必须早于采集：采集器是往这个模型里灌数据的，模型变了采集端要一起改。

**Step 3：元数据采集（【经验】2–6 周，随源类型数线性变）**

- 数据库直连采集 schema 与统计信息；ETL 解析采集血缘；Query Log 采集使用模式；事件流采集元数据变更。
- 每类源登记「已接 / 未接 / 采集周期 / 上次成功时间」，未接的也要在册。
- **产物**：元数据库 + 采集覆盖表（含每类源的上次成功时间）。
- **判据**：抽 3 张核心表，看「上次采集成功时间」是否落在你声明的刷新周期内；再看新接一个源从开工到有数据用了几天。
- **为什么必须这一步、为什么在这里**：因为元数据的新鲜度是**正确性问题而不是性能问题**——过期三个月的元数据比没有元数据更危险，因为读者会信它（[§ 3](08-data-catalog-section-3-sec3.md) §3.1）。没有采集时间戳，目录里就没有任何东西能告诉你某张表是不是还活着。

**Step 4：业务元数据补充（【经验】持续进行，不设截止日）**

- 推动 Owner 填写业务文档（业务含义 / 口径 / 典型用法）。
- 用 LLM 基于字段名、类型、样例数据与查询模式自动生成字段说明草稿。
- 业务方评审 + 确认：**生成与确认是一对**，只有生成没有确认的描述不进默认展示。
- **产物**：业务元数据 + 每条描述的「机器生成 / 人工确认」状态标记。
- **判据**：取 20 条生成描述，交给一位不熟悉该表但懂业务的同学盲评（他手上有真实字段与样例、没有描述），统计其中「明显不准确」的比例；再抽 3 张表，看有没有确认人签名。
- **为什么在 Step 3 之后**：因为机器采得到「是什么」、采不到「为什么」（[§ 5](08-data-catalog-section-5-ai.md) §5.2.1），而业务含义正是把检索键从表名换成业务语言的前提；没有自动采集做底稿，让 Owner 从零写业务含义就是纯人工成本，做不完。

**Step 5：分类分级与权限（【经验】2–4 周，随字段数与被监管范围变）**

- 按敏感度分类分级（公开 / 内部 / 机密 / 高密，对齐主文件 §2.1 的口径）。
- 配置访问权限与脱敏规则，并让权限策略读取元数据上的密级而不是另建一份。
- **产物**：合规元数据（字段级密级 + 权限策略 + 脱敏规则）。
- **判据**：拿「哪些表含手机号 / 证件号」这个问题去查，看是秒级可得还是要去问人；再抽 3 条被标为机密的字段，看访问策略是否真绑在这个字段标记上，而不是绑在整张表名上。
- **为什么在这个位置**：因为权限要挂在元数据上才有单一来源（主文件 §2.4 的分工是「目录登记分类分级、安全执行权限控制」）；而密级要能覆盖到字段，就同时依赖 Step 3 的字段级采集与 Step 4 的业务判断。

**Step 6：血缘构建（【经验】4–8 周，随引擎种类与长尾作业数变）**

- 静态 SQL 解析生成字段级血缘（表级是中间产物，不是终点）。
- 无法静态解析的作业（动态 SQL、字符串拼表名、脚本任务）单独标记，用运行时采集兜底，不让它们成为看不见的依赖。
- 血缘可视化、影响面查询，并定时校准、记录每条边的更新时间。
- **产物**：血缘图（每条边带来源、job_id、更新时间）+ 盲区清单。
- **判据**：抽 3 个字段做一次「改它会影响谁」的查询，看结果有没有来源与时间；再数一次盲区清单有多少条，以及这个数这个月是升还是降。
- **为什么在 Step 4 之后**：因为影响面清单里要出现的不是表名，而是下游表、指标、看板与责任人——这需要业务元数据先把资产与人对上号。表级血缘挡不住字段改名引发的静默算错（[§ 3](08-data-catalog-section-3-sec3.md) §3.1 第三条约束）。

**Step 7：搜索与发现（【经验】2–4 周，随检索质量要求变）**

- 关键词搜索（倒排索引）、语义搜索（向量）、自然语言搜索（LLM 意图理解）三路并存，合并结果按质量分排序。
- 结果卡片上必须能一眼看到 Owner、密级、最后更新时间。
- **产物**：可发现的目录入口（搜索 / 浏览 / API 三个入口）。
- **判据**：用 3 个业务方真实问法（不是表名）去搜，看 Top-5 里有没有正确答案；再把一个「目录里确实不存在的资产」拿去问，看它是拒答还是给出一个最接近的错误答案。
- **为什么在 Step 6 之后**：因为召回质量的上限等于元数据的完备度；血缘与业务含义还没补齐时上自然语言检索，模型只能靠猜表名，错误率不会因为模型更强而下降（[§ 5](08-data-catalog-section-5-ai.md) §5.2.2）。

**Step 8：AI 增强（【经验】持续进行）**

- 集成 LLM 做自然语言问答；自动文档生成；基于访问模式的资产推荐。
- 每个回答都必须能给出所依据资产的指针，指不回去的答案不进生产。
- **产物**：AI 原生目录（问答入口 + 生成描述 + 推荐位）+ 一份评估集。
- **判据**：复用 Step 4 的盲评方法对生成描述再评一次；再抽 3 个问答结果，点开它给的资产指针看是不是 404。
- **为什么在 Step 7 之后**：因为 AI 增强改变的是「谁来检索」，不改变权威源；权威源没立住时接入模型，只是把猜表名的工作从人转给了模型。

**Step 9：治理集成（【经验】3–6 周，随要接的系统数变）**

- 与 OneService 打通（API 元数据同步）；与数据 API 网关打通（权限同步）；与可观测打通（使用模式分析）。
- 把事件流做成唯一写入口：新增一种消费方式（今天加门禁，明天加权限同步）不改采集端。
- **产物**：一体化数据治理平台接口清单（每个消费方订阅哪些元数据事件）。
- **判据**：新增一个消费方时，需要改采集端吗？答「要」说明写路径还没收敛成事件；再抽 3 个消费方，看它们读的是同一份权威元数据还是各自的一份副本。
- **为什么放在最后**：因为这一段的收益全部来自「元数据只采一次、被多处复用」（[§ 3](08-data-catalog-section-3-sec3.md) §3.2.3）；权威源没立住就挂消费方，挂上去的每一个都会自己维护一份副本，目录反而多出几份真相。

九步里**最常被跳过的是 Step 2**：产品自带一套元数据模型，团队于是直接从 Step 3 开始采集，「先跑起来再说」。**跳过后第一个出问题的时点，是目录里第一次出现同名表或无人认领的表**——因为没有 URN 唯一约束与 Owner 非空约束，冲突在写入时不会暴露，只能靠事后审计补录；而补录速度追不上变更速度，于是目录里开始长期存在「两张同名的表、一张没人知道是谁的」。这时候唯一的修法是停机补模型再重灌，代价是前面积累的全部采集历史。

### 4.2 关键技术点

**元数据采集（Hook 路线）**

- **做法**：把采集点挂在引擎内部——JDBC Hook（连接层）、Spark Listener（作业层）、Flink Hook、Airflow Plugin（调度层）、Presto Plugin（查询层）各覆盖一类入口，每条记录带采集时间。
- **机制**：因为元数据的产生位置就在这些引擎里，所以挂在引擎上的采集点拿到的是「实际执行过的」而不是「文档里写的」——采集的可信度来自它与执行路径同源，而不是来自解析得多聪明。
- **失效条件**：**当需要同时跟住的引擎大版本多于团队的升级能力时（【经验】：大致 3 个以上大版本并存），这条会坏在「Hook 与引擎版本绑定」上**——引擎升级、Hook 失效，元数据静默停止更新。症状：某一类资产的「上次成功时间」整体停在同一周。
- **档位**：【经验】。

**血缘解析（静态 SQL 解析 + 字段依赖分析）**

- **做法**：用 SQL 解析器（Calcite、sqlparse 一类）把作业 SQL 解成 AST，从 SELECT 与 INSERT 的目标列反推字段级依赖；跨语言血缘（Spark / Flink / Python 作业）由各自解析器产出后归一到同一模型。
- **机制**：因为字段依赖只由作业文本决定，所以解析产物能随作业变更自动更新——这是人工维护字段级血缘在规模上不可能做到的替代。
- **失效条件**：**当 SQL 由字符串拼接、动态表名或存储过程生成时，静态解析拿不到依赖，这条会坏在「解析成功但血缘为空」上**——它不报错。症状：覆盖率看着很高，但那个核心脚本任务的下游栏是空的。
- **档位**：【经验】。

**存储后端（属性归属性库、检索归倒排、关系归图、变更归事件流）**

- **做法**：MySQL 存资产属性（URN、Owner、密级、采集时间），Elasticsearch 做检索，Neo4j 一类的图存储承载血缘遍历，Kafka 承载元数据变更事件。
- **机制**：因为「一次查询遍历几跳」和「一次查询匹配几个词」是两种不可互换的访问模式，所以属性、关系与检索必须分存；全塞进关系库时，先崩的一定是跳数那一侧（机制差异见 [§ 7](08-data-catalog-section-7-sec7.md) §7.3.3）。
- **失效条件**：**当血缘查询要遍历的跳数超过图存储的预算时（【经验】：3 跳以上的下游展开在界面上通常已需要截断），这条会坏在「返回不完整但看起来完整」上**。症状：影响面查询返回的条数与实际下游数对不上，且界面上没有任何截断提示。
- **档位**：跳数为【经验】。

**搜索（倒排 + 向量 + LLM 意图理解）**

- **做法**：倒排索引接表名 / 字段名 / 标签的精确与分词匹配；向量检索接自然语言问法；LLM 负责把问句改写成检索条件并对候选重排；三路结果合并后按质量分排序。
- **机制**：因为检索键的宽窄决定谁来用目录——只按表名匹配时，用目录的只有写 SQL 的人（[§ 7](08-data-catalog-section-7-sec7.md) §7.3.4）——所以三路是覆盖不同的提问方式，不是「一个比一个先进」。
- **失效条件**：**当向量检索的相似度永远给得出一个 Top-1 时，这条会坏在「回答根本不存在的资产」上**。症状：问一个目录里没有的资产，系统给出一个最接近的错误答案而不是拒答——这类错误比搜不到更贵，因为它被当成了答案。
- **档位**：【经验】。

**分类分级（正则 + 字段名匹配 + LLM 判断 + 人工确认）**

- **做法**：先按字段名与类型的规则初筛，再用样例数据抽样验证，LLM 对模糊字段给判断与理由，最后由人确认；确认结果写回字段级密级。
- **机制**：因为密级必须落到字段级，而字段级人工标注的覆盖速度追不上新增字段的速度，所以「规则与模型出候选、人做确认」是唯一可持续的形态——模型的产出是候选，不是终值。
- **失效条件**：**当新增字段的速度超过确认队列的消化速度时，这条会坏在「标了但没人确认」上**。症状：合规报告里出现大量「待确认」字段，而对外声明的覆盖率是按已确认口径统计的，两个数对不上。
- **档位**：【经验】。

**自动文档（LLM 基于样例数据 + 表名 + 查询模式生成）**

- **做法**：把表名、字段名与类型、样例数据、常见查询模式一起喂给模型生成业务描述；生成结果经业务方确认后才进默认展示。
- **机制**：因为机器采得到「是什么」、采不到「为什么」，所以这项能力的正确产出是给 Owner 一份可改的草稿，而不是替 Owner 定稿；它的价值在于把 Owner 的写作成本从「从零写」降到「改一遍」。
- **失效条件**：**当生成的描述未经确认就进入默认展示时，这条会坏在「错误描述被当成权威」上**。症状：上游表与下游表上同时挂着两条互相矛盾的描述，而两个读它的人都以为自己看到的是定稿。
- **档位**：【经验】。

**自然语言搜索（LLM + 资产向量库 + Re-ranking）**

- **做法**：问句先做意图理解与改写 → 向量库召回 Top-K 资产 → LLM 重排 → 返回带来源指针的答案。
- **机制**：因为「召回交给向量、判断交给模型」，所以召回率与准确率可以分别评估、分别调参；把两者合成一步，失败时就无法定位是没召回到还是排错了。
- **失效条件**：**当向量库的更新落后于元数据变更时，这条会坏在「推荐已经不存在的资产」上**。症状：答案里的资产指针点开是空页。所以向量索引必须与元数据事件同源更新，而不是按天批量重建。
- **档位**：【经验】。

**权限集成（与 ABAC / RBAC 打通）**

- **做法**：目录侧登记密级与分类，权限侧执行策略；字段级密级作为 ABAC 的属性之一参与判定，RBAC 决定主体可访问的范围；权限变更与元数据变更走同一条事件流。
- **机制**：因为「目录登记、安全执行」是一个单一来源结构（主文件 §2.4），所以密级必须挂在元数据上被权限系统读取，而不是在权限系统里再维护一份——两份密级一定会分叉，而且分叉时不会有人发现。
- **失效条件**：**当密级口径在目录与权限两侧分别维护时，这条会坏在「目录说机密、权限放行」上**。症状：合规审计时发现某张被标为机密的表权限范围很宽，而两侧的记录都自认为正确。
- **档位**：【经验】。

**可视化（血缘图、资产地图、影响分析）**

- **做法**：血缘图按查询按需展开，不做全量渲染；资产地图按数据域 / 分层 / Owner 聚合；影响分析以变更单为入口，直接给出下游清单而不是一张图。
- **机制**：因为图的价值在于回答一个具体问题（「改这个字段影响谁」），所以渲染必须由查询驱动；全量血缘图在资产数上万之后既慢又没人看，它满足的是「我们血缘做出来了」这句话，不是使用需求。
- **失效条件**：**当血缘图的节点数超过界面一次能展示的量级时（【经验】：万级节点、3 跳以上），这条会坏在「静默截断」上**。症状：影响面清单条数少于实际下游数，界面没有任何提示，使用者据此判断「影响面不大」。
- **档位**：【经验】。

**资产评分（使用频次 + 关键性 + 质量 + 合规风险）**

- **做法**：按使用频次（访问 / 查询 / API 调用）、关键性（下游依赖数与被指标引用）、质量（完整性 / 准确性 / 时效性）、合规风险（PII 字段数与密级）四项加权，评分用于检索排序与治理优先级排序。
- **机制**：因为「值不值得治理」必须是一个可排序的数，否则治理顺序只能按谁喊得响来定；评分的作用是让无主与劣质资产在检索里自然沉底，而不是靠管理员手动隐藏。
- **失效条件**：**当评分权重长期不校准而业务结构已经迁移时，这条会坏在「前排全是旧热点」上**。症状：新上线的高价值资产在检索里排在长期无人使用的历史表之后。校准时点应绑在业务域调整上，而不是绑在固定周期上。
- **档位**：【经验】。

**这一类里最容易被误选的一条，是把「买到一个目录产品」当成「建成了数据目录」。** 判据只有一句：**上次两个部门对同一张表的业务含义有不同说法时，最后是谁定的、记录在哪。** 目录产品的安装解决的是「有没有一个统一入口」，而数据目录真正解决的是「真相放在哪、谁签字」（[§ 3](08-data-catalog-section-3-sec3.md) §3.1 的第一条约束）。误选的典型后果是：产品上线、采集也接上了、检索能用，但同一个指标在两张表里仍然有两套口径，团队于是把问题归因于「工具不好用」，再买一套工具。

### 4.4 存量迁移

**① 先做一件立刻见效、且随时可回退的事**

不要一上来就迁元数据库。第一件事是**只读采集 + 来源标注**：用只读账号把现有资产的 schema 采进新目录，消费方一个都不动，同时给现有每张表标上「此资产的登记人未知 / 已知为 X」。它不改任何业务逻辑、随时可撤销，但立刻产出两样东西：一份**无主资产清单**，和一份按引用面排出的处置优先级。第二件事是**同名冲突体检**：把新目录里 URN 会冲突的资产先列出来，冲突处置方案定完再谈迁移。这两件事做完，你才第一次拥有了「迁移是否安全」的判断依据。

**② 历史资产按处置成本与引用面分三档**

| 档 | 判据 | 处置 | 不要做什么 |
| --- | --- | --- | --- |
| 全部返工 | 被对外数字引用、或在多个看板重复出现、或已被 AI 取数引用 | 按统一模型重建登记，旧登记下线 | 不要「先照抄进新目录再慢慢改」——照抄出来的第二份登记会立刻成为新的分叉点 |
| 只改动的部分 | 仍在使用，但引用面只在一个团队内 | 不排独立窗口，改到它的时候顺手迁，迁完即登记 | 不要为它立项：协调成本高于收益 |
| 打标挂账 | 说不清谁在用，或访问日志显示长期无读 | 登记为「待定」+ 打开访问统计 + 设到期日，到期无人认领即下线 | 不要直接删（那是别人口径的依据），也不要无限挂账（挂账必须有到期日） |

**③ 双轨要维持多久、怎么维持**

迁移期的双轨指的是**采集侧双写**：同一个源既进旧元数据库也进新目录，逐表比对两边登记的属性（Owner / 密级 / 最后更新时间）。它的成本是同一件事有两份实现：两套采集任务、两套告警、每次新增一个源要在两侧各接一次。可执行的维持规则只有一条——**每次新接一个源，必须同时接两侧；任何一次「这次先接一边」的例外，都会让目标侧在切换前就落后**。维持时长随源类型数与被引用面变（【经验】：数周到数月量级，长尾源与自定义脚本任务决定上界），没有例外通道时它会收敛，有例外通道时它会一直续期。

**④ 什么信号说明可以退出双轨**

退出条件必须写在开工之前，写成「以哪一类源的哪张表、哪个字段为准」。可观察的信号有三个：**同名冲突连续若干个采集周期为零**、**Owner 非空率与密级非空率达到你声明的目标**、**消费方开始主动查新目录（而不是被通知去看）**。三个里满足两个即可安排旧元数据库下线；只满足第一个时不要下——那只说明新库「对得上」，还不说明它被信任。

**迁移期的三条护栏**：**护栏一，新需求一律进新目录**——迁移期最大的风险不是迁得慢，而是两边同时加东西；只要新资产的登记还允许落在旧库，完成日就会不断后移。**护栏二，批次按「重复面」排，不按「表数」排**——先处理被最多下游引用的那批核心表，收益立刻可见；从表数最多的业务域开刀，得到的只是一批孤岛换了地方。**护栏三，每一批都要有一个可下线的东西**——批次的验收标准不是「迁完了」，而是「旧侧的某个采集任务可以关掉了」；没有可关掉的东西，说明这一批只是在做双写。

### 4.5 模板 / 示例

**示例 1：采集一个关系库的元数据（DataHub ingestion recipe 形态）**

```yaml
# 采集：关系库 schema + 统计信息；写入：目录服务（REST）
source:
  type: mysql
  config:
    host_port: mysql:3306
    database: ecommerce
    username: datahub
    password: ${MYSQL_PASSWORD}      # 只用环境变量注入，不落配置文件

sink:
  type: datahub-rest
  config:
    server: http://datahub-gms:8080
    token: ${DATAHUB_TOKEN}

pipeline_name: mysql_ingestion
```

**怎么用**：填 `source.config` 里的连接信息与 `sink.config` 里的服务地址；两个凭据**必须走环境变量**，不要把口令写进 recipe（这份文件通常会被提交进代码库）。**不要照抄字段名**：`type`、`config` 的具体键随产品版本调整，以该产品官方 ingestion 文档当前版本为准。

**示例 2：采集编排（schema 与血缘按同一份配置拉取）**

```python
# 伪代码：按「一个源 = 一条采集管道」的形态接采集
# 注意：具体模块导入路径随元数据平台版本变化，请以你所用版本的官方采集文档为准
client = MetadataClient(host=CATALOG_HOST, auth_provider=..., secret_key=...)

pipeline = Pipeline(

```

**怎么用**：填三样——源连接、要采的范围（schema / 血缘 / 使用模式）、Owner 的来源字段。**`owner_field` 那一格不要照抄**：源系统里往往没有负责人字段，此时应改成「采集后进待认领队列」，而不是让采集器写一个默认团队名进去。

**示例 3：自然语言入口（LLM + 资产向量库 + 重排）**

```python
# 形态：问句 → 改写 → 向量召回 → 重排 → 带来源指针的答案
# 具体框架的导入路径与类名请以你所用版本的官方文档为准
import os
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.vectorstores import Milvus
from langchain.chains import RetrievalQA

embedding = OpenAIEmbeddings(api_key=os.environ["OPENAI_API_KEY"])
vectorstore = Milvus.from_documents(asset_docs, embedding,
                                   connection_args={"host": "milvus"})

qa = RetrievalQA.from_chain_type(
    llm=ChatOpenAI(model="<以你所用模型供应商的当前模型清单为准>", temperature=0),
    retriever=vectorstore.as_retriever(search_kwargs={"k": 5}),
    return_source_documents=True,      # 必须返回来源，答案要能指回资产
)

result = qa.invoke("找包含用户手机号的表")
print(result["result"])
# 期望输出形态：包含 phone / mobile / cellphone 的表：users、orders、customer_service
# 并附这些资产的 URN —— 指不回 URN 的答案不进生产
```

**怎么用**：填三格——向量库连接、`k`（召回条数）、重排模型。**`k` 不要照抄 5**：它应由评估集定，判据是「正确答案是否落在 Top-k 内」而不是「看起来够不够多」。向量库必须与元数据事件同源更新，否则会推荐已删除的资产。

**示例 4：自动文档生成（生成 + 确认）**

```python
# 形态：表名 + 字段 + 样例数据 → 生成业务描述草稿 → 人工确认 → 进默认展示
from sqlalchemy import create_engine, inspect, text
from langchain_openai import ChatOpenAI      # 具体包与类名以你所用模型供应商的当前文档为准

llm = ChatOpenAI(model="<以你所用模型供应商的当前模型清单为准>")   # 下面用它生成草稿，先定义再调用

engine = create_engine("postgresql+psycopg://user:pass@localhost/ecommerce")
inspector = inspect(engine)

for table_name in inspector.get_table_names():
    columns = inspector.get_columns(table_name)
    with engine.connect() as conn:                      # 2.0 起不再用 engine.execute
        sample = conn.execute(
            text(f'SELECT * FROM "{table_name}" LIMIT 5')
        ).fetchall()

    prompt = f"""
    表名：{table_name}
    字段：{[c['name'] for c in columns]}
    样例数据：{sample}
    请生成该表的业务描述（用途、字段含义、典型查询示例），并注明你不确定的部分：
    """
    draft = llm.invoke(prompt).content
    write_as_draft(table_name, draft, status="pending_review")   # 关键：写成草稿
```

**怎么用**：填四格——连接串、样例行数、模型标识、草稿状态字段。**模型标识那一格不要照抄**（以你所用供应商的当前模型清单为准）；**`status="pending_review"` 那一格不要省略**：它的存在决定了这条描述能不能进默认展示，也是「生成与确认是一对」在代码里的落点；跳过它，等于把模型的猜测直接放进了目录。

### 4.6 成本：这套东西的账单

数据目录的账单很少贵在存储，几乎全贵在**采集面的宽度**与**真相失效后的连带停机**。

- **人力（多数组织里最大的一项）**。成本随「源类型数 × 消费方数」增长，而不是随资产条数：每接一种数据源要维护一条采集管道，每加一个消费方（门禁、权限同步、通知）就可能要改采集端（4.3 的判据）。数据管家的编制与「需人工裁决的描述 / 密级条目」成正比——【经验】数百到数千资产的量级通常配个位数 steward，比例随元数据完备度变，完备度高时人少。
- **云账单（元数据本身很小，检索与图最贵）**。目录库存的是元数据，量级在 GB 级【推算：按表数 × 字段数 × 每字段行字节数估，万张表的量级仍是 GB 级，远小于它所登记的数据本身】；真正的成本在**检索索引（Elasticsearch 一类）与血缘图（Neo4j 一类）**，它们的开销随「字段数 × 关系边数」增长，而不是随数据行数，同一集群的费用由分片数与副本数决定。
- **为什么这个主题贵在这里**：它要买到的是「新增一种消费方式不必改采集端」这条性质——事件驱动架构与独立重放机制本身就是要付钱的东西。选一体化程度高、但模型固定的产品，省下的正是这笔钱，代价是元数据模型跟着产品走（4.3 的判据）。

**别用「元数据很小」推出「目录很便宜」**：账单大项是采集管道数、索引与图集群、治理侧的人工裁决工时，三者都与数据量无关。通用的成本口径（预留、Right-sizing、成本分摊）见 [§11 数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，这里只讲目录特有的那一块。

### 4.7 容灾与故障演练

数据目录的容灾对象不是数据（它在别的系统里），而是**「真相能不能被读到、读到的还是不是最新的」**。跨地域复制对它意义有限：一份目录的价值在唯一性，两份都能写的目录一旦互为备份，就制造了两个真相——这正是 §3.1 第一条约束要防的。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 采集器停摆（管道挂了但不报错） | 目录静默陈旧，消费方按旧 schema / Owner 决策 | 对外暴露「上次成功采集时间」；陈旧超阈值时检索结果打标 | 杀掉一个源的采集任务，看陈旧告警在声明刷新周期的几倍内触发 | 【经验】RTO 分钟级（重启采集），RPO = 刷新周期 |
| 检索索引（ES 一类）损坏 / 丢失 | 搜索与浏览不可用，目录库本身仍在 | 降级为按分类 / 标签浏览 + 按 URN 直查 | 从备份重建索引并记录耗时，核对重建前后条目数 | 【经验】RTO 小时级（随索引规模），RPO 取决于索引能否从库重放 |
| 血缘图查询超时 / 不可用 | 「影响面」查询失败，不影响目录登记 | 明示「血缘不可用」，禁止把空结果当成「无下游」返回 | 注入图库延迟，验证返回的是「不可用」而不是空集 | 【经验】RTO 分钟级 |
| 目录作为权限门禁的唯一源 | 目录挂 → 生产放行也挂 | 门禁侧缓存最近一次授权快照，目录不可达时按快照降级放行并告警 | 断开目录与门禁，验证放行是否走缓存、缓存过期后的行为 | 【经验】按门禁侧缓存过期时间定 |

**最该演练的是第一行而不是第四行**：采集器停摆不报错，是这类系统最安静的失效——结果永远「有」，只是错的。混沌演练的通用方法论见 [§12 混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)；本主题特有的判断是**多云复制反而不该做**（两个可写真相），所以这里没有跨地域切换方案。

### 4.8 演进路线：0 → 1 → 100

触发换阶段的从来不是资产条数本身，而是某个具体的结构性矛盾——采集窗口、权责错配、检索键不匹配（与 §3.6 同一判据）。

- **0 → 1（最小可用）**：一个源、一张资产表、一个搜索框，登记「表名 + Owner + 密级 + 采集时间」四项，且**这四项有写入时约束**（URN 唯一、Owner 非空、密级非空、采集时间必填）。变贵的是「先回答组织问题」——Owner 归谁、密级怎么定——不是技术。先坏的是**没有约束的模型**：这一步省下的约束，会在资产涨到万级时以「两个部门两张口径」的形式回来（4.4 的返工面）。
- **1 → 100（规模化）**：采集从「全量拉」换成「增量 + 事件驱动」，因为全量窗口会追平刷新周期，目录只能交付「上一次扫描的真相」（§3.6 第一行）；同时用血缘自动解析替代人工登记。变贵的是**采集管道数与索引 / 图集群**；先坏的是**采集窗口**——它吃掉大半个刷新周期时，任何检索优化都救不回新鲜度。
- **100 →（下一道坎）**：从「记得表名的人用的目录」变成「业务方自助的目录」，检索键从表名换成业务问法，成本模型从「资产数」变成「用户数」（§3.6 第四行，向量副本随元数据增量刷新）。再往后是多租户与跨 BU 联邦——触发点是「租户间元数据互相可见」或「中心团队无权替各域定义口径」，是权责问题而不是容量问题（§3.6 第二、六行）。与 §5.6 的预测一致：默认入口与验收标准都会先落到「元数据覆盖率」上。

三个阶段共用一个判据：先问「现在疼的是哪个结构性矛盾」，再决定要不要换模式；规模这个数字本身从不构成理由。

### 4.9 自检清单

1. 抽 3 张核心表，`Owner` 一栏写的是**人名**还是团队名？写团队名的有几张？库里有没有「Owner 非空」的约束？
2. 抽 3 条资产记录，**采集时间**是否落在你声明的刷新周期内？有没有哪一类资产的「上次成功时间」整体停在同一周？
3. 目录里现在有几组**同名冲突**？冲突是写入时被约束挡住的，还是靠事后审计发现的？
4. 取 20 条机器生成的业务描述，找一位不熟悉该表但懂业务的同学盲评，**「明显不准确」的比例是多少**？它进了默认展示吗？
5. 拿「哪些表含手机号 / 证件号」去查，**是秒级可得还是要去问人**？被标为机密的字段，权限策略是否绑在这个字段标记上？
6. 抽 3 个字段做「改它影响谁」的查询，结果里有没有**来源与更新时间**？返回的条数与实际下游数对得上吗？有没有截断提示？
7. 数一次**无法自动解析的作业（盲区）有多少条**，这个数这个月是升还是降？
8. 用 3 个业务方真实问法（不是表名）去搜，**Top-5 里有没有正确答案**？问一个不存在的资产，系统是拒答还是给一个最接近的错误答案？
9. 新增一个消费方（门禁 / 权限同步 / 通知）时，**需要改采集端吗**？目前有几个消费方在各自维护元数据副本？
10. 密级口径在目录与权限两侧是否只有一份？最近一次审计里有没有出现「目录说机密、权限放行」的条目？
11. 存量迁移的**退出条件**是否写在开工之前？同名冲突连续几个采集周期为零了？
12. 迁移期有没有「这次先接一边」的例外？最近一批迁移下线了旧侧的哪个采集任务？

### 4.10 小结

> 本节小结：整条落地链路里唯一那个决定成败的环节，是 **Step 2（元数据模型设计）**。它排在第二、只花几周、产出物是一份 Schema 而不是任何可见的功能——正因为它最像「没有产出的会议」，它最常被跳过；而它一旦被跳过，后面七步（Step 3–9）产出的全部登记都建在一个没有唯一性与必填约束的模型上，返工面等于整座目录。
>
> **因为一致性只能由写入时约束保证（URN 唯一、Owner 非空、密级非空、采集时间必填），所以这些约束必须在第一次采集之前就位；代价是它们会让第一版上线的速度变慢，且要求你先把「谁是 Owner、密级怎么定」这两件组织问题回答掉——而这恰恰是整件事里真正难的部分。** 判据只有一句：抽 3 条资产记录，能不能从库里直接查出「归谁、什么密级、什么时候采的」。
>
> 💡 **思考锚点**：抽 3 张核心表查一下 `Owner` 一栏——写的是人名还是团队名，库里有没有「Owner 非空」这类写入时约束？如果约束不在写入侧、同名冲突只能靠事后审计发现（4.9 第 1、3 条），那你的目录正处在 Step 2 被跳过之后的返工面上，这时再贵的采集与检索功能也补不回第一版的元数据模型。
>
