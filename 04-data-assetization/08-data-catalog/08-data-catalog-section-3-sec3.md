## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把设计讲成了「按场景选一个」——中小企业选集中式，大企业选联邦式，实时数据中台选事件驱动。但真实的目录选型几乎从不是选出来的，是被三条约束推出来的：**元数据的权威源放在哪、变更怎么传播、关系查询要做到多深**。这三条里任何一条不同，同样的表、同样的团队，正确的模式就不同。

第一条是**权威源**。元数据的真相可以放在一个中心平台（集中式），可以留在各业务域（联邦式），也可以跟着表格式走（湖仓一体目录）。这看起来是技术选型，实质是**治理组织形态的直接投影**：谁持有真相，谁就握有编辑权，也就要承担质量责任。所以「集中式还是联邦式」的真正问题不是性能，而是「谁是 Owner、谁签字」——把它当技术题做，多半会在推广阶段撞墙。

第二条是**变更的传播方式**：拉（定时全量采集）还是推（事件流）。它决定了目录新鲜度的上限——拉模式下新鲜度由「采集窗口 + 采集周期」决定，推模式下由「事件产生到索引更新」决定。多数团队把这当性能问题，其实它是**正确性问题**：过期三个月的元数据比没有元数据更危险，因为读者会信它（见 3.2.1 失效点〔拉模式陈旧〕与 3.5「无人维护」）。

第三条是**关系查询的深度**：只需要回答「这张表被谁用」，还是要回答「这个字段被哪些下游字段引用」。前者用关系库的递归 JOIN 通常扛得住，后者在规模上往往要换图存储。6 个模式里，集中式 / 联邦式 / 事件驱动 / 湖仓一体在回答前两条，AI 增强与图谱式在回答第三条与「谁来消费」——它们不是互斥选项，是分层叠加的，这正是 3.4 要谈组合的原因。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 元数据的权威源（谁持有真相） | 编辑权与质量责任落在谁头上 | 「目录就是一张表清单，存哪儿都一样」——存储位置直接决定了谁能改 |
| 变更的传播方式（全量拉 / 事件推） | 新鲜度的上限与故障域的大小 | 「每天扫一次就够了」——扫描窗口会随资产数增长追平刷新周期 |
| 资产是否集中在一种引擎 | 元数据能否「跟着表走」 | 「上了湖仓 catalog 就不需要数据目录」——它只照亮自己管的引擎 |
| 变更频率与血缘深度要求 | 关系存在关系库还是图存储 | 「表级血缘够用」——字段改名引发的往往是静默算错，而不是报错 |
| 规模与成本约束 | 单库索引还是分片 + 事件流 | 「资产多了加机器就行」——加机器改不了「每次都要全量」这件事 |
| 治理组织形态与团队技能 | 一个中心团队还是各域自治 | 「建好了大家自然会用」——目录不嵌进日常工作流就是死资产 |

把这 6 个模式放回上面这三条主线（以及表中所列的引擎集中度、规模与成本、治理组织形态这三条次级约束）上看，它们的关系会清楚很多：集中式是把权威源收在一个点上（换统一性，付采集耦合）；联邦式是把权威源留在各域（换自治，付跨域延迟）；事件驱动解决的是传播方式（换新鲜度，付重建成本）；湖仓一体解决的是权威源的位置（把真相交给表格式，换强一致，付覆盖范围）；AI 增强与图谱式则完全不碰权威源——它们分别改的是「谁来检索」和「关系存在哪」。**把不同层次的问题当成同一个单选题，是选型出错的典型形式。**

### 3.2 模式逐个拆解（核心节）

下面 6 个模式按「权威源 → 传播方式 → 关系与消费层」排列：集中式（3.2.1，权威源单点）、联邦式（3.2.2，权威源分散）、事件驱动式（3.2.3，改传播方式）、湖仓一体目录（3.2.4，权威源交给表格式）在回答前两条约束；AI 增强目录（3.2.5）与图谱式目录（3.2.6）是叠加在它们之上的消费层与关系层。

#### 3.2.1 集中式目录

- **被什么约束逼出来**：元数据源数量可控，且存在一个有权定义口径的中心团队——「需要一个权威判定点」是它唯一的立足点。
- **结构**：单一权威源，所有资产登记进同一张表，URN 全局唯一。

```sql
-- 集中式：单一权威源 + 写入时约束
CREATE TABLE catalog_asset (
  asset_id       BIGSERIAL PRIMARY KEY,
  urn            TEXT NOT NULL UNIQUE,   -- 全局唯一标识，冲突在写入时暴露
  asset_type     TEXT NOT NULL,          -- TABLE / FIELD / DASHBOARD / API
  qualified_name TEXT NOT NULL,          -- db.schema.table
  owner_user     TEXT NOT NULL,          -- 具体到人，不许写团队名
  classification TEXT NOT NULL,          -- 公开 / 内部 / 机密 / 高密（对齐主文件 §2.1 的分类分级口径）
  collected_at   TIMESTAMPTZ NOT NULL    -- 采集时间：新鲜度唯一的证据
);
CREATE TABLE catalog_edge (              -- 血缘边（演进起点通常是表级）
  source_urn  TEXT NOT NULL,
  target_urn  TEXT NOT NULL,
  field_level BOOLEAN NOT NULL DEFAULT FALSE,
  job_id      TEXT,
  updated_at  TIMESTAMPTZ NOT NULL
);

-- 对照：元数据散在各处、没有唯一约束时，"同名表"与"无主表"
--       没有任何机制能挡住，只能靠事后审计补录 —— 而补录的速度
--       永远追不上变更的速度（这是"无人维护"反模式的物理起点）
```

- **为什么这样设计有效**：因为 URN 全局唯一、Owner 与分类是 NOT NULL，所以「同名资产冲突」「资产无主」这类问题在**写入时就被数据库拒绝**——一致性由约束保证，而不是靠事后审计和补录。
- **代价**：① 采集端与数据源一一耦合，每接一种源要写一个采集器；② 全量采集耗时与资产数成正比，而刷新周期的要求是固定的，两条曲线必然相交；③ 中心团队成为所有元数据编辑的唯一通道，目录的演进速度等于这个团队的带宽。
- **失效点**：当**全量采集窗口 ≥ 刷新周期**时，「统一视图」反转成「视图常年落后」，因为拉模式的全量采集耗时随资产数线性增长，而新鲜度要求不随规模放宽，于是目录交付的是「上一次扫描时的真相」。正确的动作是把传播方式从拉改成推（3.2.3），不是加机器。
- **真实使用**：Apache Atlas（2015 年开源，主文件 §1.4）是 Hadoop 生态的集中式元数据服务；DataHub 由 LinkedIn 于 2019 年开源（主文件 §1.4），接入方式正是「每个源配一个 ingestion recipe、批量写入权威存储」（见 §4.3 工具链与 §4.5 例 1）；OpenMetadata（2021 年开源，主文件 §1.4）的采集框架文档自 2022 年起随项目公开，接入形态同为「每源一条采集管道」；阿里 DataWorks 数据目录对外是单一权威入口，靠「关键元数据缺项不能发布」把质量压在入口上（见 §6 案例 8.1）。【公开】（来源：主文件 §1.4 演进历程的年份条目；DataHub 的元数据事件与血缘章节、OpenMetadata 的采集框架文档（2022 年起公开）、Apache Atlas 的分类 / 血缘文档（2015 起）——三条均为可检索的项目文档名 + 起始年份）

#### 3.2.2 联邦式目录

- **被什么约束逼出来**：多业务线各有自己的口径所有权与合规边界，中央团队既无权、也没有足够信息替所有域定义元数据——自治不是偏好，是权责现实。
- **结构**：权威源留在各域，中央只有只读的联邦查询层。

```text
联邦式：真相在各域，中央只有查询层（不复制、不能改）

  域 A 目录            域 B 目录            域 C 目录
  owner = 域A          owner = 域B          owner = 域C
  （口径由域自定）      （口径由域自定）      （口径由域自定）
      │                   │                   │
      └──── 联邦查询层（fan-out，只读，不落库）────┘
                          │
                    统一检索入口（跨域）
                          │
              全局 URN 注册表（解决同名资产冲突）
                          │
        回答"全公司有多少张表"时：中央只能现场向所有域发问再汇总

  ──────────────────────────────────────────────────────────
  关键：中央不持有元数据副本 → 跨域口径变更不需要跨组织协调
  代价：全局盘点没有预聚合的答案，每次都要现场 fan-out，聚合层本身是新的单点
```

- **为什么这样设计有效**：因为每个域的元数据留在域内、中央不复制，所以「域内口径变更」不需要跨组织协调——自治性是结构直接给出的，不是靠流程或行政命令保证的。
- **代价**：① 跨域查询是 fan-out，整体延迟由最慢的域决定；② 中央没有副本，所有「全局问题」（全公司资产盘点、跨域影响面）都要现场聚合，聚合层成为新的单点；③ 全局唯一标识成为必需品——没有统一 URN，跨域检索会把两张同名表混成一个。
- **失效点**：当跨域查询覆盖的域数增加时，「跨域发现」的体验持续下降：因为 fan-out 的整体延迟由最慢的分支决定，域数越多、出现慢分支的概率越高。更关键的是，当「跨域影响面分析」从偶发需求变成高频需求（核心表被多个 BU 引用）时，只读查询层撑不住——影响面需要在索引或图里预先聚合，此时必须在中央补一份血缘副本，模式从纯联邦滑向「联邦 + 中心血缘聚合」。
- **真实使用**：Apache Gravitino 的项目文档把自身定位为「federated metadata lake」——元数据留在各自引擎，由它提供统一入口（§4.3 工具链记为「Gravitino（Apache 2024）」）。它同时支持「联邦代理外部 catalog」与「自己托管 catalog」两种能力，本节的用法是前者；后者属于 3.2.4 的湖仓一体目录，也是 §4.3 把它归入的类目。各云厂商的跨账号 / 跨项目 catalog 共享（AWS Lake Formation 的跨账号共享、Google Cloud Dataplex 的跨项目 catalog）属同一思路，区别只在共享的是元数据还是查询入口。【公开】（来源：Apache Gravitino 项目文档，Apache 2024，见 §4.3 工具链）【经验】（AWS / Google 的对应功能属方向性提示，本节不逐条核其发布年份，以各自产品文档的跨账号 / 跨项目共享章节为准）

#### 3.2.3 事件驱动式目录

- **被什么约束逼出来**：元数据每天有大量增量变更（新增表、字段、作业），且下游（CI 门禁、权限、通知）需要「变更发生即感知」——全量拉模式无法同时满足新鲜度与成本。
- **结构**：写路径只产生事件，读路径是各自消费事件构建的索引。

```text
事件驱动：写路径 = 事件流（唯一写入口），读路径 = 各自构建的索引

  采集器（DB / 调度 / 查询日志 / BI）
        │  统一元数据变更事件（实体 + 方面 + 变更类型）
        ▼
  Kafka（元数据变更 topic，可回放）
        │
   ┌────┴────┬──────────┬────────────┬──────────────┐
   ▼         ▼          ▼            ▼              ▼
搜索索引   血缘图      门禁 / CI    权限同步      下游通知
（倒排）  （图存储）  （阻塞式）    （策略）      （Webhook）

  ────────────────────────────────────────────────────────
  关键：事件日志是唯一写入口 → 新增一种消费方式不必改采集端
        可回放 → 任何索引都能从事件重建（但重建成本随时间增长）
        增量 → 新鲜度不再受"全量扫描窗口"限制，改受"消费者滞后期"限制
```

- **为什么这样设计有效**：因为写路径只产生一条事件日志、读路径各自消费，所以「新增一种消费方式」（今天加门禁，明天加权限同步）不需要改动采集端——采集端只需要发事件，消费端可以任意增加。要分清的是，这里持续下降的是**新增消费方**的成本，不是**新增数据源**的成本：每接一种新源仍要按源实现采集端，§4.2 的元数据采集技术点列出的 JDBC Hook / Spark Listener / Flink Hook 等就是这一层。
- **代价**：① 必须处理乱序与重复——同一资产的多个变更事件可能乱序到达，最终状态要按事件时间而非到达时间归并；② 事件 schema 成为长期契约，改一次影响所有消费者，所以元数据模型必须版本化；③ 故障域从「一个库」扩到「Kafka + 消费者组 + 多个索引」，任何一环滞后都会变成「目录里有这张表、其实已经删了」这类不一致。
- **失效点**：当事件量增长到**从零重放全部事件重建索引的耗时超过可接受窗口**时，「可回放」从卖点反转成运维负担：因为事件日志持续增长，而重建必须从头消费，恢复时间随日志长度增长。所以生产上必须配「定期全量快照 + 从快照增量重放」，而这套机制本身又需要维护——事件驱动不是免费的实时性，它把「采集慢」换成了「重建贵」。
- **真实使用**：LinkedIn 开源的 DataHub 是事件驱动元数据架构的代表（统一事件模型 + 消息流 + 图 / 索引存储），主文件 §1.4 记录其 2021 年的 2.0 版本即为「事件驱动的元数据架构」；其 Actions Framework 允许订阅元数据事件触发自定义动作。【公开】（来源：主文件 §1.4 演进历程（DataHub 2019 年开源、2021 年 2.0 事件驱动架构）；DataHub 的元数据事件模型与血缘章节（2020 年起随项目公开），同一条目也列在 [§ 5](08-data-catalog-section-5-ai.md) §5.4 的「官方文档 / release note」判定入口列表中）

#### 3.2.4 湖仓一体目录

- **被什么约束逼出来**：表的 schema 已经由表格式自描述并随写事务提交——目录若再单独采集一份，就必然出现「两份真相」，而两份真相一定会分叉。
- **结构**：表格式的事务日志是 schema 的权威源，catalog 只保存「名字 → 当前快照」的指针。

```sql
-- 湖仓一体：schema 随事务提交，目录退化为指针层（Iceberg 概念示意）
-- 真正的 schema / 分区 / 统计信息在 metadata.json 与 manifest 里，
-- 与数据写入在同一个事务中提交 → 目录没有"采集延迟"这个概念
CREATE TABLE lake_catalog.table_pointer (
  namespace          TEXT   NOT NULL,
  table_name         TEXT   NOT NULL,
  metadata_location  TEXT   NOT NULL,   -- 指向当前 metadata.json
  current_snapshot   BIGINT NOT NULL,   -- 当前快照 ID
  PRIMARY KEY (namespace, table_name)
);
-- 时间旅行、快照隔离、schema 演进由表格式承担，不由目录承担
-- 对照：采集式目录里，schema 是"抄"来的一份副本；
--       湖仓一体里，schema 是"表自己的"，抄这个动作根本不存在
```

- **为什么这样设计有效**：因为 schema 变更与数据写入提交在同一个事务里，所以「目录里显示的结构」与「数据真实的结构」在机制上不可能不一致——一致性由存储格式保证，而不是由采集流程的及时性保证。这是它相对集中式目录最本质的优势。
- **代价**：① 目录能力被绑定在特定表格式与引擎上，换引擎意味着重建映射；② 治理能力（细粒度权限、脱敏、审计）受引擎 API 限制，目录只能暴露引擎已经提供的东西；③ 它只覆盖湖仓内的资产——关系库、消息队列、BI 报表、指标仍是盲区，这些照样要靠采集。
- **失效点**：当企业的资产分布在多种引擎时，「一体化」的覆盖优势反转成「只照亮了一角」的局限：因为该目录的权威源只在它管的引擎内，湖外资产在检索结果里根本不存在，而业务方不会区分「目录里没有」和「公司没有」。此时必须回到采集式目录做统一层，湖仓 catalog 降级为其中一个数据源——这也是 3.4 里最常见的组合。
- **真实使用**：Databricks Unity Catalog（主文件 §1.4 记 2023 年）、Snowflake Horizon Catalog（主文件 §1.4 记 2024 年）、Apache Gravitino（§4.3 工具链记 Apache 2024）都属这一类——Gravitino 在这里用的是它「自己托管 catalog」的那一面，与 3.2.2 引它的那一面（联邦代理外部 catalog）并存不矛盾。它们同时是引擎的权限控制面，因此更常被当作「治理基座」而不是「发现入口」。【公开】（来源：主文件 §1.4 演进历程；Unity Catalog 的能力文档与开源公告（2024，[§ 5](08-data-catalog-section-5-ai.md) §5.4 的判定入口列表亦列此条）；Snowflake Horizon Catalog 的产品文档条目）

#### 3.2.5 AI 增强目录

- **被什么约束逼出来**：元数据已经采集齐了，但消费端有大量不懂表名、不懂 schema 的业务方——「检索键」的鸿沟（人用业务语言提问，目录按表名匹配）逼出了这一层。
- **结构**：在已有元数据之上加一层派生索引（向量 + 倒排），LLM 只在「已登记资产」的封闭集合里做选择与解释。

```text
AI 增强目录：把检索键从"表名"换成"业务语言"，LLM 只做选择不做生成

  元数据（表名 / 字段 / 业务描述 / Owner / 血缘 / 样例）
        │  切块 + 向量化（离线，随元数据变更增量刷新）
        ▼
  混合检索（向量 + 倒排 + 标签过滤）
        │  提问："上季度高价值用户的订单在哪张表"
        ▼
  候选集 Top-K ──► LLM 重排 + 生成解释
        │
        ▼
  返回：资产 + 口径 + Owner + 上下游（每句解释都要能指回一条元数据）

  ────────────────────────────────────────────────────────────
  硬约束：LLM 只能"选"已登记的资产，不能"造"一个不存在的表
  风险点：描述字段为空时，相似度会给出一个格式完整但语义无关的答案
  因此必须成对交付：低置信度拒答 + 每个结论挂一条可点的元数据依据
```

- **为什么这样设计有效**：因为生成的每一句话都必须能指回一条已登记的元数据，所以幻觉的表现形式被限制在「选错资产」而不是「编造资产」——检索层成了幻觉的防火墙，错误是**可发现**的（点开就能看到真实字段）。
- **代价**：① 向量索引是元数据的**派生副本**，必须随元数据变更增量刷新，否则会出现「搜索结果的描述与真实口径不符」；② 成本随**用户数**增长而非随资产数增长（每次提问都要付 token），这与传统目录「一次采集、多次查询」的成本模型完全不同；③ 效果上限由元数据质量决定：描述为空的资产，向量化只是把「没有信息」变成高维空间里的「没有信息」。
- **失效点**：当元数据的业务描述覆盖率不足时，「自然语言搜索」反转成「自信地返回错误资产」：因为相似度检索永远会给出 Top-1，它默认没有「查不到就拒答」的行为，用户看到的是一个格式完整、但语义不相干的答案。所以 AI 增强必须配两件事才安全——低置信度时明确拒答，以及答案里每一条都带可点击的元数据依据。**它是放大器，不是补课**：元数据质量差时，它放大的是错误。
- **真实使用**：Snowflake Cortex Analyst 与 Databricks Genie 在 2024 年把自然语言入口做进云数仓（该方向在 [§ 5](08-data-catalog-section-5-ai.md) 里按「机制 → 证据 → 成熟度」评为 L2，见其 §5.1 的「自然语言搜索」一行与 §5.2.2；产品级条目见 §5.4 的「官方文档 / release note（判定入口）」列表，其中 Unity Catalog、Apache Gravitino、Snowflake Horizon 与商业目录三家都在列）；商业目录 Alation AI、Atlan AI、Secoda AI 也在 2024 年推出目录侧的 AI 增强检索（§4.3 工具链「AI 增强目录工具」一节列有这三条并列年份）。需要说明的是，「某公司已全面切换到自然语言取数」这类断言目前缺乏依据——更普遍的状态是自然语言入口与关键词搜索并存。【公开】（来源：Databricks Data+AI Summit 2024 的 Genie 发布公告；Snowflake 2024 年的 Cortex Analyst 发布公告；§4.3 工具链的 AI 增强目录条目（Alation AI / Atlan AI / Secoda AI，均标 2024）；主文件 §1.4 把 2024 年记为「AI 增强数据目录」阶段）

#### 3.2.6 图谱式目录

- **被什么约束逼出来**：血缘本质是「关系」而不是「记录」——「改这个字段会影响谁」是多跳问题，在关系模型里要靠递归 JOIN 反复物化中间结果。
- **结构**：资产属性留在关系库，血缘与引用关系进图存储，二者靠同一个 URN 关联。

```sql
-- 图谱式：属性在关系库，关系在图存储，URN 是唯一的桥
CREATE TABLE asset_prop (              -- 关系库：属性
  urn        TEXT PRIMARY KEY,
  asset_type TEXT NOT NULL,
  owner_user TEXT,
  updated_at TIMESTAMPTZ NOT NULL
);

-- 图存储（Neo4j 风格，概念示意）：
--   (:Asset {urn, type})-[:DERIVES_FROM {job_id, field_level}]->(:Asset {urn})
-- 查询：字段 $urn 的全部下游（变长路径）
MATCH p = (f:Field {urn: $urn})-[:DERIVES_FROM*1..6]->(d)
RETURN d.urn, length(p) AS hops
ORDER BY hops
LIMIT $k;
-- 注意 LIMIT：它是"结果可能被截断"的显式声明，不是性能优化
-- 关系库里的等价写法需要递归 CTE 逐层物化中间结果，深度越大越贵
```

- **为什么这样设计有效**：因为边是存储的一等公民，所以「深度若干跳的下游」的查询代价与**访问到的节点数**相关，而不是与全图规模相关——关系库的递归 JOIN 通常要对每一层的中间结果反复物化，深度一深代价就失控；图存储直接沿指针走。这是它在血缘密集型场景胜出的机制原因。
- **代价**：① 双存储一致性：属性改了图里的节点也要改，两者必须由同一个事件流同步，否则出现「属性库里有、图里查不到」的幽灵资产；② 运维技能栈与关系库不同（备份、扩缩容、慢查询分析、冷热分层都要重新学）；③ 深度遍历自带爆炸风险——一个被广泛引用的核心字段，几跳之内可达节点数可能极大。
- **失效点**：当血缘图出现高扇出节点时（少数核心字段被大量下游引用），多跳遍历的结果集会爆炸，「毫秒级血缘」反转成「只能返回前 N 条并提示已截断」：因为结果规模由图的**局部密度**决定，而不由查询写法决定。此时必须给遍历加深度上限与结果上限，而加限流意味着影响面只能给出近似答案——**精确性与响应性在血缘查询里是对立的**，这一点必须在设计时就承认，不能靠调参解决。
- **真实使用**：Lyft 开源的 Amundsen 用 Neo4j 存血缘关系、Elasticsearch 做资产检索（主文件 §1.4 记其 2019 年开源，§4.3 记为「基于 Neo4j + ES」）；LinkedIn 的 DataHub 也提供图查询用于血缘遍历。用图存储承载血缘、用倒排索引承载检索，是这一模式的常见分工。【公开】（来源：主文件 §1.4 演进历程与 §4.3 工具链的 Amundsen 条目；DataHub 的元数据事件模型与血缘章节（2020 年起随项目公开，同列 [§ 5](08-data-catalog-section-5-ai.md) §5.4 的判定入口列表））

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| --- | --- | --- | --- |
| 单一治理边界 + 万级资产【经验，量级依据见 §7】 + 有中心团队 | 集中式 | 联邦式在这个规模只增加查询跳数，不带来任何自治收益 | 是否存在**有权定义口径的中心团队** |
| 多业务线 / 合规边界不同 / 跨 BU 依赖少 | 联邦式 | 集中式要求中心团队替所有域定义口径，权责不对等，推广必然停滞 | 各域是否**自己持有并解释**元数据 |
| 元数据日变更频繁 + 下游要实时感知（CI 门禁） | 事件驱动式 | 拉模式无法在成本可控下满足新鲜度，门禁拿到的是过期血缘 | 变更频率是否已让**全量采集窗口接近刷新周期** |
| 资产基本都在同一湖仓 / 引擎统一 | 湖仓一体 | 再建一套采集目录会引入第二份 schema 真相，两份必然分叉 | schema 是否**随写事务一起提交** |
| 消费方主要是业务方 / 不懂表名 | AI 增强目录 | 只改搜索框不改元数据质量，会把「找不到」变成「找错」 | 元数据的**业务描述覆盖率**是否够 |
| 血缘密集型 / 需要字段级多跳影响面 | 图谱式 | 关系库递归 JOIN 在深度与扇出上会失控 | 是否需要回答**「这个字段影响谁」**而非「这张表被谁用」 |
| 业务线自治 + 消费方是业务方（混合云 / 多地域） | 联邦式 + AI 增强 | 单用联邦式则业务方仍要懂表名；单用 AI 增强则各域没有权威定义可检索 | 自治需求与**检索体验**是否同时存在 |

表里最常被误选的一对是**集中式 vs 联邦式**：绝大多数多业务线企业会先建集中式目录，因为它在工程上更简单——一个平台、一张表、一次采集。但机制上，集中式的成立前提是「存在有权的中心团队」，而多 BU 组织里这个前提通常不成立：中心团队无法替域定义口径，域也就没有动力把资产登记进去。结果是登记率长期上不去，目录变成一份「部分真相」，业务方很快学会「搜不到就去问人」——目录的可信度一旦被这个习惯击穿，就再难挽回。这正是 3.5 里「只为合规而建」这条反模式的机制来源。

### 3.4 组合模式：真实系统不会只用一种

**组合一：事件驱动 + 图谱式（采集与关系分离）**

- 构成：事件流做写路径，图存储做血缘的多跳读模型，倒排索引做检索，属性仍留在关系库。
- 职责边界：事件流只管「发生了什么变更」，不做关系推理；图只回答影响面，不承担全量属性查询。
- 运维代价：三套存储 + 一个消费者组；必须保证「重放事件能重建图」，否则图与属性库会漂移。
- 适合规模：字段级血缘 + 十万级资产以上的组织。【经验】

**组合二：联邦式 + AI 增强（决策表中的「混合云 / 多地域」组合）**

- 构成：各域目录持有权威元数据，中央只建向量索引与检索层，不持有属性真相。
- 职责边界：AI 层只做召回与解释，不做元数据写入；口径判定权始终在各域。
- 运维代价：中央索引必须随各域元数据同步（又一个派生副本），同步滞后会让检索结果与域内实际不一致。
- 适合规模：多业务线 / 多地域，消费方以业务方为主。【经验】

**组合三：湖仓一体目录 + 采集式集中目录（湖内加湖外）**

- 构成：湖内资产的 schema 真相由表格式与引擎 catalog 承担；湖外资产（关系库、消息、BI、指标）由采集式目录覆盖；统一检索层把两边合成一个入口。
- 职责边界：谁管 schema 谁就是权威源，中央目录**不复制湖内 schema**，只存指针与跨域关系。
- 运维代价：需要两套 URN 的映射表，并要处理「同一个真实资产在两边各有一条记录」的合并规则。
- 适合规模：已上湖仓但资产仍分散在多引擎的组织。【经验】

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 只为合规而建 | 检索次数长期低位，只在审计季被打开 | 目录不产生日常价值 → 无人登记 → 元数据残缺 → 更没人用，进入负循环 | 立项动因是「监管要求」而不是「有人正在找数」 | 先让一个高频找数场景在目录里跑通，再谈覆盖 |
| 无人维护 | 字段与真实 schema 对不上，Owner 是已离职的人 | 读者按过期信息决策，目录从「参考」变「误导」，信任一次崩塌很难恢复 | 只定义了「谁建」，没定义「谁在什么时候必须更新」 | Owner 具体到人 + 元数据变更事件自动触发刷新 |
| 元数据不完整 | 搜到表但不知道能不能用、该怎么用 | 技术元数据只回答「有什么」，不回答「为什么用」→ 业务方仍需问人 | 采集器能自动拿到的只有 schema，业务含义没人愿意填 | 强制登记关键项 + LLM 生成初稿 + 人工只做确认 |
| 血缘断裂（只到表级） | 改字段名引发的下游错误，影响面清单只列到表 | 影响面不可精确判断 → 门禁要么漏要么过度阻断 | 表级血缘靠作业依赖就能推出来，字段级需要 SQL 解析 | SQL 解析生成字段级血缘 + 定时校准 |
| 无标签体系 | 只能靠表名关键词搜到东西 | 无法按业务域 / 分类 / 密级聚合，发现能力只覆盖「记得名字的人」 | 标签被当成「锦上添花」，没有纳入发布门禁 | 统一标签体系 + 关键标签缺项禁止发布 |
| 目录与治理脱节 | 目录里看得到，打开却要另找权限；质量无从判断 | 目录与权限 / 质量两套真相 → 要么越权使用，要么绕开目录走老路 | 目录与治理分属不同项目，各自把「能查到」当成交付 | 分类分级登记即策略来源，质量分回写目录并参与排序 |
| 过度依赖人工 | 上线三个月后，大比例业务描述已过期 | 人工维护的衰减速度远快于资产变更速度，覆盖率持续下降 | 「先人工补一版」是最快能演示的路径，于是被当成了终点 | 自动采集为主，人工只补业务含义，新鲜度可度量 |
| 忽视 AI 集成 | Agent 选表靠猜表名，或反复追问用户「表叫什么」 | 元数据不被机器消费 → AI 取数不可靠，目录在 AI 时代失去主入口地位 | 目录按「给人看的页面」设计，没有面向机器的接口契约 | 元数据以 API / MCP 等形式对 Agent 开放，并保留可追溯来源 |

**「只为合规而建」**。它的暴露方式不是报错，而是**沉默**：仪表盘上只有一个数字——检索次数，它长期趋近于零。团队往往到年底盘点时才发现，目录里登记的表只有全量的一个零头，而且这批表恰好是「本来就有人管」的那批。机制上，目录的价值来自「有人靠它完成工作」；没有日常消费者，采集就没有压力，元数据就没有质量，质量差又赶走消费者。这条反模式之所以比其余七条都危险，是因为**它是其余七条共同的成因**。

**「过度依赖人工」**。它的暴露方式是**时间**：上线时覆盖率很高、演示效果很好，三个月后开始下滑，一年后没人再相信目录里的描述。机制是明显的错配——资产的变更速度由业务节奏决定，而人工补录的速度由人的空闲时间决定，两条曲线不可能长期同步。正确做法不是「要求大家更勤快」，而是把机器能拿到的全部自动采集（schema、分区、血缘、访问统计），人工只保留机器拿不到的那一小部分（为什么建这张表、口径的业务含义），并用新鲜度指标把偏差暴露出来。

**「血缘断裂（只到表级）」**。它的暴露方式是**事故的形态**：任务不报错，数字悄悄变了。字段改名、类型变更、口径调整这三类最常见的事故，在表级血缘下只能得到「影响这张表」这种无用粒度，于是影响面清单要么漏（下游字段级引用看不见），要么过度阻断（把改字段名当成改全表），后者会让团队学会绕过门禁。修法的关键是粒度：字段级血缘是让门禁「严格但不过度」的前提；没有它，门禁最终一定会被绕过，而不是被遵守。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 千级 → 万级资产【经验，见 §7】 | 集中式（全量拉） | 全量采集窗口追平刷新周期，目录只交付「上一次扫描的真相」 | 增量采集 + 事件驱动 | 采集器从「写库」改成「发事件」，并新建索引消费者与重放机制 |
| 单团队 → 多 BU | 集中式 | 中心团队无权替各域定义口径，登记率停滞，目录成部分真相 | 联邦式 + 中央只读检索层 | 需要全局 URN 注册与跨域查询协议；从「改代码」变成「谈权责」 |
| 表级 → 字段级血缘 | 关系库递归 JOIN | 深度与扇出增加后，递归物化的代价失控 | 图谱式（属性与关系分存） | 引入第二套存储与一致性同步，运维技能栈重建 |
| 元数据齐备 → 业务方自助 | 传统关键词检索 | 业务方不知道表名，命中率低，目录只服务「记得名字的人」 | 加 AI 增强层（保留原检索入口） | 维护一个随元数据增量刷新的向量副本；成本模型从「资产数」变成「用户数」 |
| 湖内 → 全资产覆盖 | 湖仓一体目录 | 湖外资产在目录里不存在，业务方误以为公司没有这份数据 | 湖仓 catalog + 采集式统一层 | 两套 URN 的映射与合并规则，长期维护落在中央团队 |
| 单租户 → 多租户 | 单实例目录 | 租户间元数据互相可见，检索结果串味 | 多租户隔离 + 查询层强制注入租户过滤 | 索引分片与查询改写改造；越界校验放在编译期而非应用层 |

这些跃迁有一个共同点：**触发换模式的从来不是「数据量」本身，而是某个具体的结构性矛盾**。上表六行的成因各不相同——前三行是「采集窗口追平刷新周期」「权责错配」「查询粒度不够用」，后三行是「业务方不知道表名」（检索键不匹配）、「湖外资产在目录里不存在」（覆盖范围之外）、「租户间元数据互相可见」（隔离）。数据量大不会直接让模式失效——它让模式失效的方式，一定是通过某个具体的结构性矛盾，而不是「规模」这个数字本身。

因此判断该不该换模式，看的不是「表有多少张」，而是一组可以直接观测的量。最容易从监控里读到的是这三个：采集窗口占刷新周期的比例（若它已经吃掉大半个刷新周期，就必须改传播方式）、跨域查询 p99 中慢分支的贡献占比（占比高说明联邦的 fan-out 已成为瓶颈）、以及高频影响面查询里「结果被截断」的比例（占比高说明关系层需要换存储）。这三个量对应的是上表前三行那类矛盾——传播方式、跨域聚合、关系层的查询代价；后三行的成因（检索键、覆盖范围、隔离）读不出这样的现成指标，通常要靠检索日志的命中率统计、目录外资产清点与租户可见范围的抽查来判断。这些量都能从现有监控与日志里取到，不需要先做架构评审。

### 3.7 自检清单

- [ ] 每条资产的 Owner 是否**具体到人**？出现团队名即视为无主资产。
- [ ] 是否存在一条**可观测的新鲜度指标**（如「元数据最后采集时间」的分布）？没有就无从判断过期。变更的传播是拉还是推——若是拉，全量采集窗口当前占刷新周期的比例是多少？
- [ ] 采集是否以自动为主？业务描述以外若还有人工登记项，那一项是否会随时间衰减？
- [ ] 血缘是否做到**字段级**？只到表级时，改一个字段名能不能列出受影响的具体字段？
- [ ] 影响面分析挂在**变更流程**上（CI / 发布门禁），还是只挂在文档与展示页上？
- [ ] 是否有一个高频找数场景**真的在用**目录（而不是上线时演示过一次）？检索次数可查吗？
- [ ] 关键元数据（业务含义 / 分层域 / Owner / SLA / 密级）缺项时，资产能否发布？能发布就不叫门禁。
- [ ] 跨域检索的延迟 p99 是多少？其中慢分支贡献了多少？
- [ ] 目录是否向 Agent / LLM 提供机器可读的接口（API / MCP），还是只有给页面用的接口？
- [ ] 若使用图存储，是否有深度与结果上限？超出上限时是否明确告知「结果被截断」？
- [ ] 若上线了自然语言检索，低置信度时是否**会拒答**，还是永远返回一个 Top-1？
- [ ] 是否存在「同一个真实资产在目录里有两条记录」（例如湖仓 catalog 与采集目录各一条）？合并规则写下来了吗？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 单一治理边界、有中心团队 | 集中式 | 唯一约束把「无主 / 同名」挡在写入时；前提是中心团队真有权 |
| 多业务线、各域持口径 | 联邦式（+ 中央只读检索） | 自治由结构给出；代价是全局问题要现场聚合、fan-out 决定延迟 |
| 变更高频、下游要实时感知 | 事件驱动式 | 事件是唯一写入口，新增消费者不必改采集端；代价是重建成本随日志增长 |
| 资产集中在同一湖仓 | 湖仓一体 | schema 随事务提交，一致性由格式保证；代价是只照亮自己管的引擎 |
| 消费方是不懂表名的业务方 | AI 增强（叠在已有目录之上） | 检索层是幻觉的防火墙；但它放大元数据质量，不弥补质量 |
| 需要字段级多跳影响面 | 图谱式 | 遍历代价随访问节点数而非全图规模增长；代价是高扇出时结果爆炸 |

> 本节小结：数据目录的模式选择，最终由**「元数据的权威源放在谁手里」**这一条约束决定——它同时决定了编辑权、质量责任、跨域查询代价与治理推广的难度；传播方式（拉 / 推）、关系存储形态（关系库 / 图）与消费层形态（关键词搜索 / 自然语言）都是在这一条确定之后才展开的次级选择。
>
> 💡 **思考锚点**：在你现有目录的监控里取三个数——采集窗口占刷新周期的比例、跨域检索 p99 里慢分支的贡献占比、影响面查询「结果被截断」的比例；哪一个已经逼近或越过警戒？这三个数分别指向传播方式、联邦 fan-out 与关系层存储该不该换，而你现在的「权威源」假设撑不撑得住这次换？
