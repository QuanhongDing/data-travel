## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

五条趋势（「AI 原生目录」「自然语言即查询」「Agent 自动治理」「目录即数据基础设施」「行业目录标准化」）全部是方向判断，没有一条带时间与判据。而 §6 的四个案例（2016–2024）已经把另一件事说清楚了：**数据目录的骨架在 LLM 之前就定型了**——五元组强制登记、SQL 自动采集、字段级血缘、质量分排序、指标↔表↔字段三向关联，这五项不是一次成套落地的，而是随各自案例的工程时间线逐件长出来的——五元组强制登记、自动采集与字段级血缘见 §6 案例 8.1（阿里，2016–2024）与 8.2（LinkedIn，2016–2024），质量分排序与三向关联见 §6 案例 8.3（字节，2020–2024）；主文件 §1.4 的「大数据目录阶段（2015–2020）」记的是这一代目录工具本身（Atlas 2015 起、Amundsen 2017、DataHub 2019 年开源），并不代表上述五项机制都在这个窗口内成型；「事件驱动」是更晚的一层——主文件 §1.4 把事件驱动的元数据架构记在 2021 年的 DataHub 2.0。所以本节的第一件事是把**骨架**与**AI 加在骨架之上的那一层**分开：骨架可核验、已被生产使用；AI 那一层多数停在可试点，只有少数场景够格进路线图。

本节沿用三条可核验的判据，**三条全中才是 L1**：① 已 GA 且有正式 release note；② 有第三方（非厂商）公开的生产案例；③ 接口稳定。L2 = 已可用但接口或生态未稳，或只有厂商自有案例；L3 = 仅路线图、论文或厂商演示。**本主题的第②条有它自己的麻烦**：目录类 AI 能力的公开案例基本由厂商自己发布（商业目录的客户故事、云厂商的产品博客）。判据直接给出结论：这些就是 L2，不写成「准 L1」，也不在单格里悄悄放宽（若确需修正判据，只能按 §2.1 第 2 条在 5.1 正文显式声明，见下段）。

但本主题有一个别处没有的东西：**本目录 §6 的四个案例本身就是公开材料记录的生产实践**（阿里 / LinkedIn / 字节 / 某云厂，来源标注见该节）。**本主题对 §2.1 的 L1 判据做了如下修正：第②条在底座类机制上接受「运营方自行公开发布、并给出规模与来源标注的生产记录」作为生产案例证据。理由是评的是机制而不是产品——「SQL 解析 + 变更事件」这类底座不属于任何单一厂商，而 §6 的三个案例来自三家互不相关的组织（阿里 / LinkedIn / 字节），各自给出规模与口径，读者可回该节逐条核对。该修正只适用于底座类机制；AI 层的检索、生成与写操作仍按原第②条要求非厂商来源——这也是它们停在 L2 的原因。** 它们足以支撑骨架的 L1；至于 AI 那一层，§6 案例 8.4 记过「自然语言查询」组件与自助查找命中率，但那是该案例自己的口径——引用时必须带上口径，不能当成通用数字。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | :--- | --- |
| **元数据底座：自动采集 + 字段级血缘**（未单列，但它是 §6 四个案例的共同核心，也是其余方向的前置条件） | **L1** | ① 有正式公开文档条目：DataHub 的元数据事件与血缘章节（2019 年开源后随项目公开，主文件 §1.4）、OpenMetadata 的采集框架文档（2021 年开源后随项目公开，主文件 §1.4）；② 生产案例（按 5.1 声明的第②条修正：运营方自行发布、带规模与来源标注的生产记录）：§6 案例 8.1（阿里 30 万+ 表）、8.2（LinkedIn 十万级数据集）、8.3（字节 4 业务）分别记录了自动采集与字段级血缘的生产用法（来源标注见该节）；③ 接口稳定：「源实体 / 字段 → 目标实体 / 字段 + 作业 + 时间」这组表达十年未变 | 直接排进路线图；下面所有 AI 能力都接在它上面 |
| 自然语言搜索 | L2 | 产品已 GA 并有官方文档条目（见 5.4；年份以官方文档发布记录为准）；非厂商的、含口径与规模的公开效果数据缺失 | 在已有元数据上试点；低置信度必须拒答 |
| 资产问答 | L2 | 与自然语言搜索同源（都依赖元数据向量库），差别只在入口形态（对话框 vs API）；接口形态未定 | 与搜索同批试点，共用同一份依据 |
| 自动文档生成 | L2 | 方法已可用（主文件 §2.3 列了四种依据：样例数据 / 查询模式 / 血缘上下文 / LLM）；但生成描述的正确性无公开评测，发布前必须有人确认 | 生成后由 Owner 确认再发布，并打上生成标记 |
| AI 驱动的数据治理 | L2（规则 / 分类器级识别）→ L3（LLM 判定与自动发布） | PII 与重复资产的识别长期以规则 + 分类器落地，接口稳定；LLM 判定缺公开准确率与误判代价口径——而「把敏感字段判成公开」这类误判不可接受 | 敏感判定保留人工确认；LLM 只做候选生成 |
| Agent-driven 数据目录 | L3（写操作）/ L2（只读检索接口） | 写操作没有公开的审计与回滚案例；只读侧有正式规范可依（MCP，2024 年 11 月公开） | 只开只读；写元数据的权限不做 |

> 本主题下**唯一处在 L1 的方向是元数据底座（自动采集 + 字段级血缘）**——而它恰恰不是 AI 带来的：它的公开能力在 LLM 之前就存在（Apache Atlas 2015 年起即把「分类 + 血缘」作为公开能力），生产形态见 §6 案例 8.1（阿里，2016–2024）与 8.2（LinkedIn，2016–2024）——主文件 §1.4 的「大数据目录阶段（2015–2020）」指的是这批目录工具，不是五元组强制登记、质量分排序这些机制本身；AI 只是把它从「有更好」变成「必须有」。§6 案例 8.7 把它说成「Text2SQL 与 Agent 取数的成像条件」，本节把它展开成一条可判定的机制：**AI 只能选已登记的资产**——元数据覆盖率为零的地方，模型给出的是格式完整但没有依据的答案。

> 其余方向不够格的原因各不相同：自然语言搜索与资产问答卡在**第②条**（缺非厂商公开效果数据，也就无从判断「错到什么程度会出事」）；自动文档生成卡在**正确性无人确认**（生成便宜了，但没人能判断一句描述对不对）；AI 治理卡在**误判代价不对称**（漏判是事故、误判只是麻烦，两者不能用同一个阈值）；Agent 写元数据卡在**责任与回滚**。四个瓶颈不在一处，**成熟时间不会同步**——把它们打包成「AI 原生目录」一次采购，一定会被最慢的那件拖住。

**三级各自该怎么用**（这一步比定级本身更常被跳过）：

- **L1 排进路线图**：它不依赖任何未发布的版本，今天做与明年做只差一年收益。
- **L2 只做 PoC，并先测出一个数**：搜索测「自然语言入口相对关键词检索的命中增量」（5.2.2）、生成测「盲评准确率」（5.2.3）、治理测「漏判与误判两类数」（5.2.4）。测不出数就不上量。
- **L3 只登记，不做架构假设**：不要在权限模型、审计制度上预先为它留位置——留了位置就会有人往里填事。
- **回填机制**：任何方向一旦出现第三方公开的、含口径与规模的生产案例，升一级；一个 L2 方向一年内仍拿不到你自己语料上的实测数字，降为 L3 并停止投入。

两点要说明：**其一**，工具条目不逐个给能力判断——版本与年份以各自官方文档为准，本节只给「去哪里核验」；**其二**，Apache Gravitino 的归属与项目范围以官方文档为准。

还有一处结构性错位值得写明：**「目录即数据基础设施」不是方向，是接口约定**。它说的是目录要与湖仓 / AI 平台深度集成——这件事只能落在接口上（见 5.3；指标平台是本节按同一接口标准补列的结合点），不能落在「深度」这种形容词上。判断方法是看三件事有没有写死：谁调用谁、数据以什么形态穿过边界、失败时谁负责。写不出来的「深度集成」，在工程上等于没有集成。

**本节与 §3 的分工**：§3 的「AI 增强目录」（模式 5）回答「这一层怎么加进既有架构」，本节回答「加进去的每一件能力现在能不能用」。同一件能力在两节里的结论必须一致——§3.2.5 已给出「LLM 只做选择不做生成」这条硬约束，本节把它落成判据（5.2.2 的 L2 评级与拒答要求），而不是换个说法重讲一遍。

读表的两条纪律：**第一，级别是发给「机制」的，不是发给产品的**——同一款目录产品里，采集与血缘可能是 L1、AI 检索可能是 L2、Agent 写元数据可能是 L3；按产品名定级会把三者混成一档。**第二，级别只能靠证据变**——不靠「今年大家都在讲 AI 目录」升，也不靠「去年有人用错过」降，只靠 §5.4 里官方文档与生产案例这两类证据是否出现。把这条写成回填机制（见上文），比每次争论「它到底成熟没有」省事得多。

### 5.2 演进方向逐条拆解（核心节）

四个方向都按同一结构写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**。只写收益不写代价的方向应在评审时直接打回——本主题每一次能力提升，都对应一项成本或责任的转移，先集中列一次分类：

| 方向 | 机制上发生了什么变化 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 元数据底座 | 不是 AI 改变的：把「人补元数据」换成「机器解析 + 人只补语义」 | **成本结构**（维护成本不再随资产数线性增长） |
| §5.2.2 自然语言搜索与问答 | 检索键从「表名 / 字段名」换成「业务语言」，LLM 只做选择与解释 | **接口边界**（提问的形态变了，资产本身没变） |
| §5.2.3 自动文档生成 | 业务含义的产出来源从 Owner 换成模型 | **成本结构 + 责任**（产出变便宜，责任无人承接） |
| §5.2.4 AI 治理与 Agent 维护 | 治理从「周期性项目」换成「事件触发」，判定从规则换成统计判断 | **控制流 + 判定来源**（误判的代价不对称） |

有一类条目必须提前分出去：**「把目录的搜索框换成对话框」是接口改良，不是架构变化**。判断方法是问三句——元数据模型增加了字段吗？采集链路增加了来源吗？权限模型增加了判定点吗？三句都是「没有」，那它只是检索层的一个新前端，应该记入工具升级，而不是写进架构演进。本节把它判为 L2 而不是 L1，一半原因就在这里：**接口改良的风险低，但它也不解决覆盖率问题**。

#### 5.2.1 元数据底座：把「人补元数据」换成「机器解析 + 人只补语义」

- **旧做法与它的卡点**：元数据靠人工登记。§6 案例 8.1 的失败教训写得很直白——「元数据靠人工填，3 个月后就过期」；§6 案例 8.2 的形态是「PII 靠人工标注，标了 3 个月只覆盖 60%，而新增资产持续产生」。卡点不在意愿，而在**成本随资产数线性增长，而资产的增长速度更快**：人一忙就停，停了就开始过期。
- **AI 改变了什么机制**：这里要说清一件事——**这条机制不是 AI 改变的**。SQL 解析 + 元数据变更事件把「是什么」交给机器（schema、血缘、使用模式），把「为什么」留给人（业务含义、Owner、密级）——§6 案例 8.1 称之为「自动采集 + 人工补全」，§6 案例 8.2 称之为「统一事件模型 + 适配器」。它与 AI 的关系是**依赖**：LLM 要选表、生成 SQL、判断能不能读，全靠机器可读的元数据。
- **由此得到的**：因为元数据由解析与事件产生、而不是由人逐条登记，所以它的**覆盖率不会因人力波动而衰减**；也正因为如此，「改表前先查影响面」这种动作才能变成日常而不是一次大作业（同 Ch11 · 05 血缘与影响面 §6 的结论；该句出现在该节「血缘查询只查元数据索引与关系图、永远不去扫数据湖」的示意块里，说的是查询代价；同节组件 3「字段级血缘与影响面（核心）」把这条动作的性质写清了——**影响面精确到字段与下游责任人，而不是止于表级**）。

```text
    元数据质量的两种衰减曲线（横轴：时间，纵轴：覆盖率）
      人工登记：  ↗↗↗ 一次性冲刺（盘点）
                       ↘↘ ↘ 人一忙就停、新增持续累积
      ↓ 结果：覆盖率随时间单调下降，3 个月后不可信（§6 案例 8.1/8.2 的形态）
      自动采集：  ↗↗↗ 接入一次（解析器 + 事件流）
                    → → → 随资产增长自动覆盖（新增资产默认被采集）
      ↓ 结果：覆盖率由解析器覆盖面决定，不由人的空闲决定
    ────────────────────────────────────────────────
    关键：AI 层（搜索、问答、治理）的上限就是这条曲线的平台高度
          所以「先补底座、再上 AI」不是保守，是唯一能生效的顺序
```

- **由此付出的**：**其一，盲区被换了位置而不是消失**——动态 SQL、脚本任务、外部导入这些解析不到的部分会成为新的不可见依赖；盲区本身不可怕，「不知道有盲区」才可怕，所以必须把「未能解析」的作业单独列出并追踪补齐。**其二，血缘与解析器版本绑定**：解析器一升级，血缘图就会变，必须能区分「源真的变了」与「解析器变了」，否则每次升级都会触发一轮假告警。**其三，成本形态转移**：人力成本换成了「解析链路 + 事件流 + 索引」的运维成本，总量未必下降，但它**不再随资产数线性增长**——这才是这条机制真正的收益，而不是「不用人了」。
- **证据与来源**：【公开】DataHub 的元数据变更事件与血缘模型有公开文档（2019 年开源后随项目公开，主文件 §1.4）；OpenMetadata 的采集框架有公开文档（2021 年开源后随项目公开，主文件 §1.4）；更早的 Apache Atlas（2015 起）同样把「分类 + 血缘」作为公开能力。生产案例（按 5.1 声明的第②条修正）见本目录 §6 案例 8.1 / 8.2 / 8.3（来源标注见该节）。判定方法：在你的目录里抽 10 张被频繁引用的表，看上游血缘有没有「最后采集时间 + 解析器版本」这类条目——没有这类条目的部分，就是人工登记的，它会过期。
- **成熟度**：**L1**。判据：① 有正式公开文档条目；② 有公开可核对的生产记录（§6 三个案例各含自动采集与字段级血缘，均由运营方公开发布并带规模与来源标注，即 5.1 声明的第②条修正）；③ 接口稳定（源 / 目标实体与字段 + 作业 + 时间这组表达十年未变）。
- **什么时候可以只做表级**：资产在百级、单一业务域时，表级血缘足够；等到出现「改字段名导致下游悄悄算错」这类事故（§6 案例 8.3 的形态）再上字段级——字段级的成本在解析覆盖与存储，不在算法。
- **什么时候最值得做**：三个条件同时成立时收益最确定——资产过千、跨多个业务域、且「改上游不知道影响谁」已成为反复出现的抱怨。少于这个规模，表级血缘 + 具体 Owner 通常够用；强行上字段级，买到的是覆盖率数字，不是风险下降。
- **失效条件**：动态 SQL 与脚本任务不是加预算就能解析干净的。正确做法是**让盲区可见**：单列「未能解析」清单、按影响面排序补齐；只在完全静态的 SQL 语料上宣称「血缘 100%」，是把已知盲区写成了未知依赖。
- **上线前的最小验证**：抽 10 张关键表，看上游血缘有没有「最后采集时间 + 解析器版本」条目，并按有 / 无分两组，各自统计过去半年的事故次数——这一对比通常比任何覆盖率数字更能说服人。

#### 5.2.2 自然语言搜索与资产问答：把检索键从「表名」换成「业务语言」

- **旧做法与它的卡点**：检索键是表名与字段名，而业务方用的是业务语言——主文件 §1.2 把这条列成两个痛点（「找数难」「懂数难」），主文件 §2.3 的资产发现方法里，关键词、过滤、推荐都受同一个限制：**提问的人必须知道一张表叫什么**。后果就是 §1.2 的第一条痛点与 §6 案例 8.1 的起点：找数靠问熟人。
- **AI 改变了什么机制**：把检索键从「表名」换成「业务语言」——LLM 只在**已登记资产的封闭集合**里做选择与解释（§3.2.5 的机制描述：混合检索 + 重排 + 生成解释，不生成资产）。**它改变的是提问的形态，不是资产本身**：表还是那些表，描述为空的资产依然不可被正确理解。
- **由此得到的**：因为提问不再要求知道表名，所以「能不能找到数」第一次不取决于业务方是否受过目录培训——这是它相对关键词检索的真实增量，也是主文件 §1.2 那条「LLM 需要元数据」的具体落地。
- **由此付出的**：**其一，不可复现**——同一问题两次可能返回不同资产，「命中」没有稳定口径，离线评测无法固定（检索侧对「不可复现」有更完整的推导，见 Ch4 · 04 混合检索 §7.3.4「结构增强的代价」：那里说的是 **Agentic 检索**——轮数由中间结果决定、轨迹不唯一，故离线评估不可复现；固定的混合检索管线本身是确定性的，本节这条代价的来源是 LLM 的选择与解释，不是检索管线）。**其二，错误的形态变了而不是消失**——LLM 不会编出一张不存在的表，但会**选错资产并给出格式完整的解释**，错误从「查不到」变成「看着对」（§3.2.5 的失效点：相似度检索永远会给出 Top-1）。**其三，权限面扩大**——若检索语料包含用户无权访问的资产，模型的解释本身就是越权信息泄露；权限必须在召回前过滤，返回空优于返回越权内容。**其四，成本位置变了**——这项开销随**提问次数**增长，而采集成本随**资产数**增长，两者不是同一条曲线（§3.2.5 已把这条列为 AI 增强目录的代价）。
- **成本量级**（【经验】）：两个自变量都是经验假设，只能给区间——日提问量按 **200–5000 次**【经验】，单个资产块按 **300–1000 token**【经验】（表名 + 字段清单 + 业务描述 + 血缘摘要），候选资产固定取 5 个。取中值代入：1000 × 5 × 500 = **250 万 token/天**；区间下沿 200 × 5 × 300 = **30 万 token/天**，上沿 5000 × 5 × 1000 = **2500 万 token/天**。再乘你所用平台的单价即可得日成本。**要点不是这个数，而是它的自变量是提问次数**——用户越多越贵，而元数据采集是「一次采集、多次查询」。
- **证据与来源**：【公开】RAG 的公开出处是 Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", NeurIPS 2020；各家目录与数仓产品的自然语言入口有官方文档条目（§3.2.5 列了 Snowflake Cortex Analyst、Databricks Genie，以及商业目录 Alation / Atlan / Secoda 的 AI 增强检索；年份以官方文档发布记录为准，可自行核验）。本目录 §6 案例 8.4 记录了某云厂目录 SaaS 的「自然语言查询」组件与自助查找命中率（来源标注与口径见该节）。判定方法：取 50 个真实业务提问，先让人工用关键词 + 目录检索找一遍，再让自然语言入口找一遍——**后者超过前者才算 AI 带来的增量**，否则只是换了一个入口。
- **成熟度**：**L2**。判据：产品已 GA 且有官方文档条目，但效果高度依赖元数据覆盖率、无跨组织公开评测；试点即可，且必须把「低置信度拒答 + 每条结论能点回元数据」作为上线前置条件——这不是体验优化，是安全设施。
- **失效条件**：当业务描述覆盖率不足时，能力会反转——从「找不到」变成「自信地返回错误资产」。同时，如果检索需求集中在精确的字段名与编码（型号、编号、错误码），关键词与倒排反而更准；此时正确的动作是补元数据与修索引，而不是先上语义层。
- **上线前的最小验证**：同一批 50 个提问，让「关键词检索」与「自然语言入口」各跑一遍，统计两者命中集合的差异与并集；再挑 10 个只有自然语言入口能找到的，人工核对命中是否正确——这一组数决定它是增量还是干扰。
- **诚实的定位**：它解决的是**「不知道表名就找不到」**这一类失败，不解决「表本身不可信」（质量、时效、口径）这一类失败。后者要靠质量分、SLA 与 Owner（§6 案例 8.3 的质量分机制），把两类失败混在一起验收，会让自然语言入口背上一堆它无解的问题。

#### 5.2.3 自动文档生成：把「业务含义的产出」从 Owner 换成模型

- **旧做法与它的卡点**：业务含义（业务名、业务定义、使用说明）由 Owner 手写。卡点是**激励错位**：写文档不直接产出业绩、优先级永远排在最后，于是覆盖率长期上不去；而覆盖率低又直接锁死 5.2.2 的上限（描述为空的资产无法被正确理解）。
- **AI 改变了什么机制**：把业务含义的产出来源从 Owner 换成模型，依据是样例数据、查询模式与血缘上下文（主文件 §2.3 的「自动文档生成」列的四种依据）。机制上这是**产出成本的转移**：从「人的时间」换成「与产出场次无关的推理」；但**责任没有跟着转移**。
- **由此得到的**：因为产出成本大幅下降，覆盖率第一次可能从「能写多少」变成「能确认多少」——**瓶颈从生产移到了审核**。这才是它真实的机制意义：它把稀缺资源从「写」换成了「确认」，而确认的单位成本远低于编写。
- **由此付出的**：**其一，「看起来合理但错」是沉没成本**——读者无法判断一句描述对不对，只能相信；一个错描述会被下游反复引用，比空描述更坏，因为空描述至少会让人去问。**其二，必须打标记**——哪些描述是生成的、谁确认过、依据哪次数据，否则治理审计时无法区分人工与生成内容。**其三，会随 schema 变更静默过期**——生成描述绑定了当时的字段与样例，字段一改就要重生成；没有「生成时间 + 生成依据」时，它就是一条会静默过期的记录。**其四，责任错觉**——把「没人写」变成「无人负责地写」，问题只是从覆盖率转到了可信度。
- **证据与来源**：书内这条「成对动作」只有一半落在主文件——主文件 §2.3 的「自动文档生成」只列了四种生成依据（LLM / 样例数据 / 查询模式 / 血缘），**没有「确认」这一侧**；「业务方评审 + 确认」出现在本目录 §4.1 的 Step 4「业务元数据补充」（08-data-catalog-section-4-sec4.md），本节把它作为对自动生成的前置要求，而不是记成主文件 §2.3 已有的做法。判定入口（对外部材料同样适用）：看官方文档与工程实践里有没有「生成 + 确认」这一对，只有生成没有确认的，不要用。**本节不引用任何「覆盖率提升 X%」的数字**——这类数字既无来源也是口径依赖的。判定方法：取 20 条生成描述，交给一位不熟悉该表但懂业务的同学盲评（他手上有真实字段与样例、没有描述），统计其中「明显不准确」的比例；这个比例决定它能不能进入目录的默认展示。
- **成熟度**：**L2**。判据：方法与工具普遍可用，但正确性无公开评测、发布前必须有人确认；把它当成「提高覆盖率的候选生成器」，不要当成「已经写完的文档」。
- **什么时候值得做**：当「字段无人解释」是找数失败的主要形态、且这些资产**已经有 Owner**时，它把 Owner 从「写」解放到「改」，收益是真实的。
- **什么时候不值得做**：没有 Owner 的资产不要生成描述——生成只会把「没有信息」变成「看起来有信息」，且没有人会发现其中的错（这与 5.2.1 的失效条件是同一件事的两端）。
- **失效条件**：当资产本身正在剧烈变化（重构中的表、临时表、实验表）时，生成描述的生命周期可能只有几天——此时它产出的是**一份必须跟着重建的文档**，成本反而高于不写。判断方法是看这批表最近 90 天的 schema 变更次数；变更频繁的先别生成。
- **上线前的最小验证**：取 20 条生成描述做盲评（评审人能看到真实字段与样例、看不到表名），统计「明显不准确」的比例；再隔一个月复查同一批，看有多少条因为 schema 变更已经失效。

#### 5.2.4 AI 治理与 Agent 维护目录：把治理从「周期性项目」换成「事件触发」

- **旧做法与它的卡点**：分类分级、PII 标注、重复与冗余资产识别、治理建议，都是**周期性项目**——发起一次盘点、人过一遍、出报告，然后停下来，而新增资产继续累积。§6 案例 8.2 的失败教训是这条最干净的形态：「PII 靠人工标注，标了 3 个月只覆盖 60% 且新增持续产生」，倒逼出「自动扫描 + 发布门禁」。
- **AI 改变了什么机制**：把治理动作从「周期性项目」换成「事件触发」（新资产发布、schema 变更、访问模式变化即触发判定），并把判定来源从「规则」换成「统计判断」——PII 从字段名正则扩展成语义判断，重复资产从名称相似扩展成用途相似。**改变的是触发方式与判定来源，不是治理目标**：该标注的还是要标注，该门禁的还是要门禁。
- **由此得到的**：因为触发不再依赖「下一次盘点」，覆盖率第一次可能跟得上资产的增长速度——这正是 §6 案例 8.2 用自动扫描替代人工标注的机制原因。「Agent-driven 数据目录」（监听 schema 变更自动更新、自动分类分级、自动补全业务元数据）要拆成两类看：**变更同步类是自动化**（既定规则，不需要语义判断），**语义判定类才需要模型**——前者今天就该做，后者才是 L3。

```text
    治理的两条循环：项目式 vs 事件式
      项目式：  盘点 ──► 报告 ──► 整改 ──► 停  ──►（新增资产累积）──► 再盘点
                覆盖率呈锯齿形：每次冲刺升一截，之后持续下滑
      事件式：  新资产发布 / schema 变更 / 访问模式变化
                  │
                  ├─► 规则判定（正则、字段名、密级映射）→ 直接执行
                  ├─► 语义判定（模型出候选）→ 人工确认 → 执行
                  └─► 发布门禁（未标注密级的资产不允许发布）
                覆盖率由「触发是否被接上」决定，不由盘点节奏决定
    ────────────────────────────────────────────────
    关键：两类判定必须分开走——规则判定可以自动执行
          语义判定只能出候选，且**漏判必须为零**才可以自动发布
```

- **由此付出的**：**其一，误判的代价不对称**——把公开字段判成敏感只是多一道流程，把敏感字段判成公开是一次合规事故；所以阈值必须偏保守，而保守意味着更高的误报率和更多人工确认，**自动化率注定达不到宣传里的水平**。**其二，写操作需要审计与回滚**——Agent 改元数据（改描述、改标签、改 Owner）必须能回答「谁在什么时候改的、依据什么、怎么回滚」，否则目录会变成一份没人知道作者是谁的元数据。**其三，判定随模型版本漂移**——「这条分级是哪个版本判的」必须可查，否则历史决定无法复核（同 5.2.1 对解析器版本的结论）。**其四，组合敏感漏判**——资产的敏感度有时取决于字段**组合**（单个字段都不敏感，合起来能定位到人），逐字段判定会系统性漏掉这一类，只能靠数据集级的策略与人工抽检补。
- **证据与来源**：【公开】PII 与敏感数据的识别长期以规则 + 分类器方式在安全与目录产品中落地（各产品官方文档有对应条目，年份以官方文档为准）；开源侧如 Presidio 一类项目公开列出了支持的实体类型与置信度机制，可自行核验其覆盖面与可配置项。MCP（Model Context Protocol）由 Anthropic 于 2024 年 11 月公开发布、规范带版本日期【公开】，是 Agent 访问外部系统（含目录）的一类接口规范；同样带版本化规范的不止它一家（OpenAPI 一类接口规范同样版本化）。判定方法：看它有没有独立的规范文档 + 版本日期 + 变更记录，而不是看产品页上有没有「支持 MCP」这句话。对照方法：从目录里抽 200 个字段，做「只靠规则」与「规则 + 语义」的对照，分别统计**漏判（敏感判成不敏感）**与**误判**两类数；**只有漏判为 0 才允许自动发布分级**。本节不引用任何「识别准确率 X%」的数字——它随语料与定义变化，跨组织不可比。
- **成熟度**：**规则 / 分类器级识别为 L2，只读的 Agent 检索接口为 L2，写元数据的 Agent 为 L3**。判据：识别能力可用但发布前需人工确认；写操作没有公开的审计与回滚案例。
- **什么时候值得做**：资产数量已经大到人工盘点跟不上新增（这是本条唯一的触发条件），且你已经接受「语义判定只出候选、必须有人确认」这条流程约束。
- **什么时候不值得做**：资产在千级以内、或合规压力主要来自少数核心表时，周期盘点 + 人工确认仍然更省事；此时上自动扫描买到的是覆盖率数字，而不是真实的风险下降。
- **失效条件**：当资产的敏感度取决于字段**组合**时（单看每个字段都不敏感，合起来能定位到人），逐字段的判定会系统性漏判——这类只能靠数据集级策略与人工评审补上，自动化率注定不高。承认这一点，比把阈值调松去凑一个漂亮的覆盖率数字更重要。
- **上线前的最小验证**：抽 200 个字段做「只靠规则」与「规则 + 语义」的对照，分别统计漏判与误判；再挑 10 个「业务上敏感但名字无关」的字段（如个体标识类字段）单独检验——这一组是漏判最集中的地方。

### 5.3 与本主题既有栈的接口在哪

本节不写「与 AI 结合」这类空话，只写三件事：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 元数据采集 ↔ 数据源（JDBC / 查询日志 / 事件流） | 交接物 = 资产与血缘事件；**采集要能区分「源变了」与「采集器坏了」** | 采集侧；解析器版本要随血缘一起登记 | 既有技术（L1） |
| 目录 ↔ 检索层（倒排 + 向量） | 交接物 = 元数据的**派生索引**；必须随元数据变更增量刷新 | 索引侧；索引过期会出现「描述与真实口径不符」 | 既有技术（L1） |
| 检索 ↔ LLM（问答与解释） | 交接物 = Top-K 资产 + 分数 + 权限域；**LLM 只做选择与解释，不生成资产** | 检索侧管召回，权限侧管越权；**权限在召回前过滤** | 可试点（L2） |
| 生成描述 ↔ Owner 确认 | 交接物 = 候选描述 + 生成依据 + 待确认标记 | Owner；**未确认的生成描述不得进入默认展示** | 可试点（L2） |
| 目录 ↔ 指标平台（Ch4 · 10） | 交接物 = 指标定义 ↔ 表 ↔ 字段的三向关联（§6 案例 8.3 的机制） | 指标侧；口径只在一个地方定义 | 可试点（L2） |
| 目录 ↔ 血缘与影响面（Ch11 · 05） | 交接物 = 字段级血缘边；目录只消费，不生产 | 血缘侧；**血缘的盲区要显式标记** | 既有技术（L1） |
| 目录 ↔ 数据 API 网关 / 权限（Ch4 · 07） | 交接物 = 分类分级标签；**目录登记不等于执行** | 安全侧执行，目录只登记 | 既有技术（L1） |
| 目录 ↔ OneService / 统一查询网关（Ch4 · 06、Ch4 · 09） | 交接物 = 已注册的 API 与服务条目；目录负责被发现，网关负责被调用 | 网关侧管鉴权与限流，目录侧管可发现 | 既有技术（L1） |
| 目录 ↔ 向量湖 / 检索底座（Ch4 · 02） | 交接物 = 元数据向量与片段；**索引是元数据的派生副本** | 索引侧；重建与刷新都要有人负责 | 既有技术（L1，作为组件）/ 可试点（L2，作为方案） |
| 目录 ↔ Agent（MCP / OpenAPI） | 交接物 = 工具调用与返回值 + 调用者身份 + 预算 | 组织侧；**越权与误写不可归因于模型** | 只读 L2 / 写入 L3 |
| 目录 ↔ 知识图谱 / GraphRAG | 交接物 = 决策与引用关系抽取出的实体与关系；**抽取模型版本必须随图一起登记** | 图侧；抽取质量随模型版本漂移，需重跑与对齐 | 观望（L3） |

一句话概括：**AI 没有新增调用关系，只把「读目录的人」从数据团队换成了模型**。因此接口上多出来的只有三样东西——**权限域、依据（这条结论指回哪条元数据）、身份与审计**。三样缺一，AI 那一层就不能接。

三条最容易出错的约定，单独写清：

**第一，权限过滤必须在召回前。** 放在召回后（post-filter）的代价不只是少返回几条，而是把「存在这样一份文档」这一事实暴露给了无权者——在 LLM 这一层，模型会用自然语言把它描述出来，泄露从「元数据可见」升级为「内容可读」。判定方法很具体：用一个只对部分资产有权的账号提问，看回答里是否出现无权资产的名字或口径描述。

**第二，派生索引必须可重建、可过期。** AI 检索层是元数据的副本，元数据一改它就要跟；跟不上时出现的不是报错，而是「看起来合理但已经过期」的答案——这是 AI 层最隐蔽的失效形态。所以索引要记录「最后刷新时间与元数据版本」，并在超期时降级为关键词检索或明确拒答。

**第三，写操作必须审计，分类分级不允许自动发布。** 这条把 5.2.3 与 5.2.4 的结论合在一起：生成描述可以自动产出但不能自动生效，分级判定可以自动出候选但不能自动发布。理由是同一个——**这两类内容的错误不会当场暴露**，而没有当场暴露的错误需要一个人来负责。

三条约定的共同点：**它们都不是技术接口，而是责任接口**。本主题所有的失效最后都落在这一层——模型能选、能写、能解释，但不能负责。

再补一条失败责任的划法，因为它决定事故电话打给谁：**「找不到」与「找错」是两件性质不同的事，不能混在一个告警里。** 找不到是能力问题，可降级（退回关键词检索）、可告警；找错是事故，因为它会被当成依据使用，并且无法用「模型不准」解释。这条划法与检索层的约定一致——**应当把「返回空」和「返回错误资产」分成两条路径**，前者允许自动降级，后者必须人工介入并回溯是哪一次索引刷新带进来的。

**核验 §5.1 表里六个宣称的最小动作**（都不需要采购、不需要新版本、也不需要内部资料）：

1. **元数据底座**：抽 10 张关键表，看上游血缘有没有「最后采集时间 + 解析器版本」条目；没有的就是人工登记，会过期。
2. **自然语言搜索**：取 50 个真实业务提问，关键词检索与自然语言入口各找一遍，比对命中集合差异。
3. **覆盖率基线**：数一数字段业务描述覆盖率与字段级血缘覆盖率；前者直接是 5.2.2 的上限（描述为空的资产听不懂业务语言），后者决定 5.2.1 的血缘粒度停在表级还是到字段。
4. **拒答行为**：故意问一个目录里不存在的资产，看它是明确拒答，还是给出最相近的资产并配上一段看起来合理的解释。
5. **权限**：用一个只有部分资产权限的账号提问，检查回答里是否出现无权资产的名字或口径。
6. **Agent 写操作**：写下「它代谁执行、依据什么、怎么回滚」三句话；写不全就说明接口还没成立。

这六条动作的共同点：**它们用的都是你自己的元数据、你自己的提问样本和公开文档**。还要说清它们的归类方式：**这六条按能力分，与 §5.1 表的六行不是一一对应**——覆盖率基线、拒答、权限三条是跨方向的通用检查，而表里第 4 行（自动文档生成）与第 5 行（AI 驱动的数据治理）各有自己的核验动作，见 5.2.3 与 5.2.4 的「上线前的最小验证」。本节把方向判成 L1 / L2 / L3，依据的是 5.1 的三条判据，以及 5.2.1–5.2.4 各自写出的核验动作——能做出结论的，才有资格进路线图。

**三类证据的更新速度不同**：模型与产品条目最快（以年为单位），官方文档次之，生产案例最慢（以数年为单位）。**不要用其中一类的结论去推另一类**——拿今年的产品条目去论证「组织的元数据质量已经跟上」，是本主题最常见的一步跳空，而这一步恰恰是趋势清单的写法。

> 四类材料的用法不同：**论文**给机制（为什么这样设计有效），**官方文档**给接口形态与判定入口，**生产案例**给可用性证据，**厂商材料**只给线索。落到分级上，5.1 的三条判据各有对应的证据类——①（正式 release note）与 ③（接口稳定）靠官方文档，②（第三方非厂商的生产案例）靠生产案例——**三条都进判据**；论文解释机制但不单独给级别，厂商材料只给线索、不进判据（本主题的公开案例基本由厂商自己发布，把厂商材料当判据就会把 L2 写成 L1）。不做这个区分，本节就会退回成趋势清单。

**怎么用这份清单**（先看结论再看出处，能省一半时间）：要核「底座该不该现在做」→ 看第 1 条；要核「自然语言入口值不值得上」→ 看第 2、4、5 条；要核「Agent 能不能写元数据」→ 看第 6 条。三条核验都不需要采购。

### 5.5 被过度宣传的部分

**「AI 原生目录」**——实际是：目录的骨架（五元组强制登记 + 自动采集 + 字段级血缘 + 质量分排序 + 三向关联）在 §6 案例的时间线（2016–2024）里就定型了，与 LLM 无关；AI 加在**检索**与**描述**这两层。原因：把「多了一个入口」说成「目录重做」。**它什么时候才会成真**：当 AI 改变了「哪张表会被搜到、被谁搜到」的顺序与质量，并且能用同一个口径的数证明（找数时间、命中率），而不只是多了一个对话框。

**「自然语言即查询：业务方无需懂表结构」**——实际是：它把「懂表结构」换成了「元数据里有没有对应语义」；查询接口简化了，**数据本身没有变好**。原因：把接口改良当成数据质量提升。**它什么时候才会成真**：用同一批问题做前后对照，自然语言入口的命中率超过「关键词检索 + 人工」——这个对照做不做，比任何产品演示都更能决定要不要上。附一条常被略过的风险：它同时扩大了越权面——模型会用自然语言描述用户无权访问的资产。

**「Agent 自主维护目录」**——实际是：能自动做的是「有明确规则的更新」（schema 变更同步、按规则补标签），不能自动做的是「业务含义与 Owner」——而后者才是目录失效的主因（§6 案例 8.1 的失败教训是元数据靠人工填、3 个月后过期；8.2 是 PII 靠人工标注、3 个月覆盖 60%）。原因：**责任不能自动化**；把「没人写」变成「无人负责地写」，只是让问题更难追。**它什么时候才会成真**：出现公开的、含误判率与回滚机制的生产案例；在此之前，Agent 只开只读。

这三条的共性值得点明：**它们都把「接口变简单」说成了「资产变好」**，而本主题的瓶颈始终是元数据覆盖率与责任归属。反过来说，这三个方向不是不能做：它们都是元数据质量的**放大器**——质量好时放大收益，质量差时放大错误（§3.2.5 已给过同一结论）。先量覆盖率、再决定放不放大，是本节最省钱的一条习惯。

**厂商材料在这个主题里该怎么用**：客户故事、产品博客与榜单都可以当**线索**（它们告诉你这个方向有人在做），但不能当**证据**（它们不提供口径、失败率与适用条件）。把线索当证据的典型后果，是把「某厂商的目录已经全面 AI 化」当成自己可以照抄的方案；而可核验的事实通常是另一副样子——**自然语言入口与关键词检索并存**（§3.2.5 的说明），而不是替代。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 自然语言入口会成为目录的默认入口之一，但「命中率上限由元数据覆盖率决定」会被写进验收标准 | 采购与验收清单里出现「业务描述覆盖率、字段级血缘覆盖率」作为前置门槛；复盘时先看覆盖率再看模型 | 三年后评估仍只看功能清单，覆盖率无人度量；或出现「换了更大的模型就解决了」这类结论 |
| 自动生成的字段描述会成为默认项，但必然带「生成来源 + 确认人 + 生成时间」三个标记 | 目录产品的元数据模型里出现生成标记字段（官方文档条目可见）；治理政策明文要求未确认描述不得发布 | 三年后生成描述与人工描述在目录里无法区分、也没有制度区分它们 |
| Agent 对目录的写权限会先落在低风险字段（描述、标签），不会落在权限与分类分级 | 产品把写权限按字段类型分级；出现「分级判定必须人工确认」的公开制度或产品约束 | 出现公开案例允许 Agent 直接修改分类分级，且无审批与回滚 |
| 「行业目录标准」会先出现在监管驱动的行业，且规定的是「元数据必须机器可读 + 变更可追溯」，而不是「必须用 LLM」 | 出现公开的行业数据字典 / 元数据规范，且在条文里要求可追溯与机器可读 | 三年后行业标准仍停留在「要不要建目录」；或标准把技术选型写成合规要求 |

写这四条的约定：**信号必须是外部可观察的**（官方文档条目、产品约束、公开规范），不是「我觉得会」。**被检验得最快的是第二条**——只要厂商在元数据模型里加上生成标记，一年内就能看到；**最慢的是第四条**，标准发布以年计，本节对它不给时间预期。凡写不出证伪信号的判断，本节不写。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 元数据还没采齐、血缘靠人工登记 | 先做自动采集 + 字段级血缘 + 质量分（L1 底座） | 观察两个数：业务描述覆盖率、字段级血缘覆盖率 | 不要先上自然语言搜索——它会把覆盖率不足放大成错误答案 |
| 已有目录，业务方抱怨找不到数 | 先补业务描述与 Owner，再接语义检索 | 观察关键词与自然语言入口的命中对照 | 不要在没有拒答机制与权限前过滤时开放自然语言入口 |
| 想上自动文档生成 | 先确认资产是否已有 Owner；生成后由 Owner 确认再发布 | 观察生成描述的盲评准确率、以及过期后是否有人修 | 不要给无 Owner 的资产生成描述；不要让生成内容与人工内容在界面上无法区分 |
| PII / 分级合规压力大 | 规则 + 分类器先做到「漏判为零」，再谈自动发布 | 观察漏判与误判两类数（两者不能加总成一个「准确率」） | 不要让 Agent 自动发布分级；不要用跨组织不可比的识别率数字做验收 |
| 想接 Agent 取数 | 先只开只读：权限在召回前过滤、每条结论带来源与 Owner | 观察越权与「答案过期」两类问题 | 不要开放写元数据的权限；不要让 Agent 改口径与分级 |
| 湖仓一体 / 多源目录 | 先把资产标识与命名空间统一（一个资产一个稳定标识） | 观察跨源资产的重复登记率 | 不要在多源标识未统一前做跨源检索与影响面 |
| 指标与表口径脱节 | 先做「指标 ↔ 表 ↔ 字段」三向关联 | 观察同一指标是否仍有多份定义 | 不要让模型去猜口径；口径由人定义，机器只做一致性检查 |
| 新人多、数据团队被重复提问淹没 | 先把高频问题与答案配上 Owner，再谈检索与问答入口 | 观察重复提问占比、以及答案的更新时间是否有人维护 | 不要把「答疑量下降」当成「问题解决了」——它可能只是换成了没人核对的自动回答 |
| 正在选目录平台 | 把「元数据模型能否承载五元组 + 字段级血缘 + 生成标记」作为选型项 | 观察产品官方文档里这些条目是否为一等能力 | 不要为「AI 原生」这个标签支付溢价；不要在没定元数据模型前先定模型供应商 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（错误答案进决策、越权泄露、元数据被无人负责地改写），**而收益依赖一个尚未成立的假设**（覆盖率已经够高 / 模型能判断对错 / Agent 有可回滚的权限模型）。等 §5.6 的信号出现再投入，损失的只是时间。

另外注意顺序：表里第一行是其余各行的前提。**底座没做完就上 AI 层，会出现「AI 表现得还行、但没人知道它对不对」的状态**——这比明显不可用更危险，因为它会让人停止补元数据。判据很简单：**AI 的答案能不能点回一条已登记的元数据**；点不回去的答案，无论多流畅都只是文本。

最后一条通用习惯：**每当有人提议引入一个「AI 目录能力」，先问它接在哪个交接物上**（5.3 的表）。接不上的，说明它要解决的问题还没被定义清楚——此时该做的是补那份交接物（谁来写、谁确认、什么时候更新），而不是先买能力、再回头补流程。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**检索键从「表名」换成了「业务语言」**——LLM 在已登记资产的封闭集合里做选择与解释，于是「能不能找到数」第一次不取决于业务方是否受过目录培训。因为这一点，**唯一处在 L1 的方向是元数据底座（自动采集 + 字段级血缘），而它不是 AI 带来的**：它在 LLM 之前那一代目录平台工程里就成型了（工具起点见主文件 §1.4 的「大数据目录阶段（2015–2020）」：Atlas 2015 起、DataHub 2019 年开源；自动采集与字段级血缘的生产形态见 §6 案例 8.1、8.2，时间窗 2016–2024），AI 只是把它从「有更好」变成「必须有」——§6 案例 8.7 称它为 AI 取数的成像条件。它**没有**改变的是两件事：一是**模型只能选已登记的资产**，覆盖率不足的地方，它给出的是格式完整却没有依据的答案；二是**责任不在模型**——谁写的、谁确认的、什么时候更新的，这三样缺位时，AI 层只是把过期的口径更快地送到更多人面前。
>
> 判断本主题任何新提法的快捷方式：**它改变的是「提问的形态」（接口），还是「元数据的质量」（底座）？** 改接口的，先量覆盖率上限再决定放不放大；改底座的（采集、血缘、质量分、Owner），直接做——它是本节唯一 L1，也是其余所有方向的前置条件。
