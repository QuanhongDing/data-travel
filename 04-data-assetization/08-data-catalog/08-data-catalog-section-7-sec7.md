## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

第一，打分把「不可行」压扁成了「少几分」。打分表「数据发现」一列给元数据库 2 分、给数据目录 5 分，读起来像是「弱一点」；但在**百级表**的组织里（【经验】：单团队、单引擎的常见量级），元数据库加一层关键词索引就够用，两者差距是零；在**万级到十万级资产、多个 BU** 的组织里（【经验】），元数据库差的不再是 3 分，而是「业务方根本不会打开它」。**分数的含义随规模反转，而表里没有规模这一维。**

第二，同一张表里已经藏着自相矛盾，只是被打分掩盖了。打分表「血缘可视化」一列给知识图谱 5 分、与数据目录并列最高，而「易用性」一列给知识图谱 2 分、与元数据库并列最低。这两个分数并不冲突，它们指向同一件事：**图存储把多跳关系查询变得便宜，同时把运维与上手门槛抬得很高**——打分只是把一条机制的两面拆成了两行，读者看不到它们同源。（候选的定位与年份见主文件 §1.4。）

第三，真正决定成败的约束几乎从不落在打分表的维度上。数据目录的选择被三件事推着走：**元数据的权威源放在哪、变更怎么传播、关系查询要做到多深**（[§ 3 设计模式与范式](08-data-catalog-section-3-sec3.md) 的 §3.1 约束表）。这三件事在打分表里一行都没有，而它们一旦错位，其余维度全部拿满分也没有用。

第四，AI 增强层引入了一个与其他候选**形状不同**的成本函数：它的成本随**用户数**增长，而不是随资产数增长。打分表里「AI 集成 5 分」隐去了这件事，而它决定了小团队上线 AI 增强层的账单可能比采购传统目录更贵（见 7.4）。

第五，打分表的决策树把一个**组织问题**包装成了技术分支：「用户群体是数据团队还是全员」这一问，实质是「是否存在有权定义口径的中心团队」。这不是能靠选一个工具解决的问题——它决定了你走集中式还是联邦式，而两者的一致性来源完全不同（一个靠写入约束，一个靠各域自负其责）。

因此本章不排序，只做三件事：**把候选按「与元数据真相隔了几层副本」分族**（同族内部差异远小于跨族差异），**给每条机制写出「什么条件下优势成立、什么条件下失效」**，最后把决策落到几个可以从监控里直接取到的比值上。

**本章所有数字按三档标注**：【公开】（有公开来源，正文给出处与年份）、【推算】（由公开前提推导，正文写出推导链）、【经验】（行业普遍实践，只给区间与条件）。三者混用时，读者可按档位决定采信程度。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 权威源归属 | 元数据的真相由谁持有、谁有权改口径 | 决定登记率能否持续；权威源错位时目录长期停在「部分真相」，而「搜不到就去问人」这个习惯一旦形成就再难逆转（§3.3） |
| 新鲜度上限 | 变更从发生到可检索要多久，这个上限由什么决定 | 过期元数据比没有元数据更危险——读者会信它（§3.1） |
| 关系查询深度 | 要不要回答「这个字段被哪些下游字段引用」 | 决定关系层用关系库还是图存储；表级粒度让门禁只能整表判断，于是门禁被绕过而不是被遵守 |
| 检索键的宽窄 | 使用者用表名提问，还是用「上季度高价值用户」这类业务语言提问 | 决定要不要向量层；这一层把成本从「资产数」驱动改成「用户数」驱动 |
| 登记约束力 | 关键元数据缺项时，资产还能不能发布 | 决定元数据质量由「约束保证」还是「靠自觉」；后者在三个月后开始衰减 |
| 消费契约 | 主要消费者是人，还是流程与 Agent | 决定目录要不要提供机器可读接口，以及元数据能否被程序判定（AI 取数的前提） |

> 这 6 条的权重随规模移动（本节出现的规模量级均为【经验】：行业常见区间）：百级到千级资产时，**登记约束力**最先起作用（它决定最小可用目录能不能立住）；万级到十万级，**权威源归属与新鲜度**成为硬约束；出现业务方自助与 Agent 取数需求后，**检索键与消费契约**才进入前三。**关系查询深度**是个例外——只要你的变更流程里存在字段改名或口径调整，它就必须先验证，与规模无关。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 元数据库 | 引擎侧技术元数据的登记与查找 | 只有 schema / 分区 / 统计信息，没有业务语义与治理字段 | 数据团队自查、引擎内部 | Hive Metastore、各引擎自带 catalog，Apache-2.0 |
| BI 工具的语义层 | 报表侧的指标与数据集登记 | 元数据是被动产生的副产品，范围止于该 BI 工具内 | 分析师、报表使用者 | 各 BI 厂商自带，商业 |
| 集中式采集目录 | 单一权威源的资产登记与检索 | 从各源采集元数据抄进一个中央存储，用写入约束保证唯一与有主 | 有中心治理团队的组织 | Apache Atlas（2015 起）、DataHub（LinkedIn 2019 开源）、OpenMetadata（2021 起）、阿里 DataWorks 数据目录，Apache-2.0 / 部分商业托管 |
| 事件驱动式目录 | 以变更事件为唯一写入口的目录 | 写路径只发事件，读路径各自消费建索引，新鲜度不再受全量扫描窗口限制 | 元数据日变更频繁的组织 | DataHub 2.0（2021 记事件驱动元数据架构），Apache-2.0 |
| 联邦式目录 | 权威源留在各域的跨域检索层 | 中央只持有路由与身份映射、不复制明细，跨域查询 fan-out | 多业务线 / Data Mesh | Apache Gravitino（Apache 2024，federated metadata lake）、AWS Lake Formation 跨账号共享、Google Cloud Dataplex 跨项目 catalog，开源 / 云服务 |
| 湖仓一体目录 | 把 schema 的权威源交给表格式 | 目录退化为「名字 → 当前快照」的指针，schema 随写事务提交，没有「采集延迟」这个概念 | 资产集中在同一湖仓 | Databricks Unity Catalog（2023）、Snowflake Horizon Catalog（2024）、Apache Gravitino（托管面），商业 / 开源 |
| 图谱式目录 | 属性留关系库、关系进图存储 | 边是存储的一等公民，多跳下游的代价与访问到的节点数相关 | 血缘密集型组织 | Lyft Amundsen（2019，Neo4j + Elasticsearch）、DataHub 的图查询、自建图存储，Apache-2.0 / 自研 |
| AI 增强目录 | 在已有元数据之上加一层派生索引 | 向量 + 倒排做召回，LLM 只在已登记资产的封闭集合里做选择与解释 | 消费方以业务方为主 | Atlan AI、Secoda AI、Alation AI（2024 年前后推出目录侧 AI 增强检索），商业 |
| 数据契约 / 资产登记台账 | 以协议而非页面为核心的治理载体 | 契约（schema、口径、频率）是生产方与消费方的双边承诺，目录只是展示面 | 多团队 Data Mesh | 多为自建或随治理平台提供 |

> 表中年份除标注来源外，均可在主文件 §1.4 演进历程与 [§ 4 工程实现](08-data-catalog-section-4-sec4.md) 的 §4.3 工具链年份条目中直接核到；Amundsen 的「Neo4j + Elasticsearch」形态见 §4.3 工具链条目【公开】（来源：主文件 §1.4 与 §4.3 的年份记录；年份锚点——Atlas 2015 年条目、Amundsen 2019 年开源、DataHub 2019 年开源与 2021 年 2.0、OpenMetadata 2021 年、Unity Catalog 2023 年、Snowflake Horizon 与 AWS Glue Data Catalog 升级 2024 年、Gravitino 记于 §4.3 的 2024 年条目、Atlan AI / Secoda AI / Alation AI 2024 年）。

这 9 个候选分成**四族**。分族的依据不是品牌、也不是开源或闭源，而是**它和「真相」之间隔了几层副本**：

- **族一 · 真相本地（0 层副本）**：元数据库、BI 语义层、湖仓一体目录、数据契约 / 资产登记台账。schema 与口径的真相就在产生它的引擎、表格式或生产方手里——目录要么本身就是那份真相，要么只是指向它的指针。
- **族二 · 抄一份（1 层副本）**：集中式采集目录、事件驱动式目录、联邦式目录。三者差异只在「抄」的方式：全量拉、事件推、或者干脆不抄只路由。
- **族三 · 复制的是边而不是属性（1 层副本）**：图谱式目录。
- **族四 · 派生的派生（2 层副本）**：AI 增强目录。它的向量索引建立在族二或族三的元数据之上。

**先分族再选，能省掉一半比较**：同族内部的差异通常是运维形态与许可证，跨族差异才是机制差异。分族还直接给出一个可验证的判断——**每多一层副本，就多一条「两份真相分叉」的路径**。族一没有分叉的可能（不存在第二份），族二的分叉由采集及时性决定，族四的分叉由「元数据刷新」与「向量索引刷新」两条链路的时滞叠加而成。

每族的**典型失败方式**也不同，这比典型优势更有用：族一死于**覆盖范围**——它在自己管的引擎里无可挑剔，直到业务方问「为什么目录里没有订单库这张表」；族二死于**新鲜度**——全量采集窗口悄悄追平刷新周期，目录开始稳定交付「上一次扫描时的真相」；族三死于**扇出**——结果集随图的局部密度爆炸，深链路查询只能返回前 N 条；族四死于**元数据质量**——描述为空的资产被向量化成高维空间里的「没有信息」，检索结果从「找不到」变成「找错」。**知道自己这一族会怎么死，比知道别人的分数是多少更有价值。**

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 与真相隔了几层副本

**机制是什么**：元数据的真相产生在某个系统里（引擎的 catalog 表、表格式的 metadata 文件、域内的登记系统）。目录把这份真相复制、加工、再发布。副本层数决定了一致性上限，也决定了刷新责任落在谁头上。

**它在各候选中的实现差异**：

| 候选 | 真相在哪 | 目录持有的东西 | 刷新责任 | 不一致的表现 |
| --- | --- | --- | --- | --- |
| 元数据库 | 引擎 catalog 本身 | 就是真相（或与写入同一事务） | 引擎 | 无（若有，属引擎自身问题） |
| 湖仓一体目录 | 表格式的 metadata / manifest | 指针（名字 → 当前快照） | 写事务 | 无——schema 变更与数据提交在同一事务 |
| 集中式采集目录 | 各源系统 | 全量副本 | 采集器 + 采集周期 | 采集窗口内发生的变更看不见 |
| 事件驱动式目录 | 各源系统 + 事件日志 | 事件流 + 各自构建的索引 | 采集端发事件 + 消费端建索引 | 消费者滞后 |
| 联邦式目录 | 各域 | 路由 + 身份映射，不存明细 | 各域各自负责 | fan-out 拿不到全局快照，合并结果可能对应两个时刻 |
| 图谱式目录 | 属性在关系库、边在采集链路 | 属性副本 + 关系副本 | 由同一事件流双写同步 | 「属性库里有、图里查不到」的幽灵资产 |
| AI 增强目录 | 族二 / 族三的元数据 | 向量 + 倒排（派生索引） | 随元数据变更增量刷新 | 搜索结果的描述与真实口径不符 |

**由此必然导出的性质（因果句）**：因为是**湖仓一体目录把 schema 的权威源交给了表格式、而 schema 变更与数据写入提交在同一个事务里**，所以「目录里显示的结构」与「数据真实的结构」在机制上不可能不一致——它换来的一致性由**存储格式**保证，而不是由采集流程的及时性保证；代价是**覆盖范围被引擎边界钉死**：湖外的关系库、消息队列、BI 报表在这套目录里根本不存在，而业务方不会区分「目录里没有」和「公司没有」（§3.2.4 失效点）。反过来，因为**集中式采集目录持有的是抄来的一份副本**，所以它天然覆盖多引擎，代价是不一致的可能性随「采集窗口 / 刷新周期」这个比值上升（7.3.2）。

**为什么这条机制决定了推广成败**：副本层数越少，登记与刷新越不需要组织配合。族一的目录几乎不需要动员（引擎自己就产出了），族二要多接一个采集器，族四要有人持续维护业务描述与向量刷新任务。**「目录推不动」在多数组织里不是意愿问题，是副本层数问题。**

**公开证据**【公开】：表格式把 schema 与快照纳入同一份元数据、catalog 退化为指针，这一点可由 Apache Iceberg / Delta Lake 的项目文档中 metadata.json（或等价的事务日志）与 catalog 的职责描述核验；DataHub 的元数据事件模型与血缘章节（2020 年起随项目公开）描述了「统一事件模型 + 消息流 + 图 / 索引存储」这一形态；Apache Atlas 的分类与血缘文档（2015 年起）描述了集中式元数据服务形态。判定方法：查该目录是否持有 schema 的**副本**——它自己存了一份 schema 定义，就是采集式；只存指针，就是湖仓一体式。

**失效条件**：当资产的引擎集中度不高时（多引擎、多朵云、存量关系库占大头），族一的「零副本」优势反转为「只照亮了一角」；而当引擎集中度极高、治理要求只是「看清楚有什么」时，族二多出来的整套采集链路与它的一致性风险反而不划算——**这种情况下它比不做更危险，因为它会给出过期但看起来权威的答案。**

#### 7.3.2 变更怎么传播：拉的全量窗口 vs 推的事件流

**机制是什么**：目录的新鲜度上限由传播方式决定。拉模式下上限 = 采集窗口 + 采集周期；推模式下上限 = 事件产生到索引更新的时延。

**它在各候选中的实现差异**：

| 候选 | 默认传播方式 | 新鲜度上限由什么决定 | 规模增长时先坏在哪 |
| --- | --- | --- | --- |
| 元数据库 / 湖仓一体目录 | 无「传播」概念 | 写事务提交时刻 | 不适用 |
| 集中式采集目录 | 拉（定时全量或增量） | 采集窗口 + 采集周期 | 全量采集窗口随资产数线性增长，追平刷新周期 |
| 事件驱动式目录 | 推（变更事件） | 消费者滞后 | 消费者组积压；事件重建耗时随日志长度增长 |
| 联邦式目录 | 各域各自决定 | 最慢的域 | fan-out 延迟由最慢分支决定 |
| 图谱式目录 | 随采集链路（通常是推） | 边同步的时延 | 双写不一致的时间窗 |
| AI 增强目录 | 随元数据的增量刷新 | 向量索引刷新任务周期 | 刷新任务积压，检索结果的描述与实际口径漂移 |

**由此必然导出的性质（因果句）**：因为**拉模式的全量采集耗时与资产数成正比，而刷新周期的要求是固定的**，所以两条曲线必然相交——一旦采集窗口吃掉大半个刷新周期，目录交付的就不再是「当前状态」，而是「上一次扫描时的真相」；**此时正确的动作是把传播方式从拉改成推，不是加机器**，因为加机器改不了「每次都要全量」这件事。反过来，因为**推模式把「采集慢」换成了「重建贵」**，所以它买到的实时性是有账期的：事件日志持续增长，从零重放全部事件重建索引的耗时随时间增长，生产上必须配「定期全量快照 + 从快照增量重放」，而这套机制本身又要维护（§3.2.3 失效点）。

**这条机制决定「新鲜度」能不能被管理**：拉模式下它是一个可以直接测量的比值（采集窗口 / 刷新周期），推模式下它是消费者滞后（可监控）。两种模式下它都可度量，唯一不可度量的是「没人度量它」——所以 §3.7 的自检清单把它列在第二条。

**公开证据**【公开】：DataHub 的元数据事件模型与血缘章节（2020 年起随项目公开）描述了以消息流承载元数据变更事件、由下游消费者各自构建索引的写读分离形态；主文件 §1.4 记其 2021 年的 2.0 版本为「事件驱动的元数据架构」，§3.2.3 亦以此为代表。判定方法：查采集侧能否只发事件（是否存在独立的元数据变更事件 topic）而不直接写库——能，则推模式可用；不能，则新鲜度上限被采集周期锁死。

**失效条件**：当资产规模小、变更频率低时，推模式带来的额外组件（消息队列 + 消费者组 + 重放机制）是纯负担；此时全量拉更简单，且窗口远小于刷新周期，没有可观测的收益。

#### 7.3.3 关系存放：递归 JOIN vs 图存储

**机制是什么**：血缘是「关系」而不是「记录」。「这个字段影响谁」是多跳问题——在关系模型里要靠递归 CTE 逐层物化中间结果，在图模型里是沿指针走。

**它在各候选中的实现差异**：

| 候选 | 关系存在哪 | 多跳查询的代价与什么相关 | 深度一深会怎样 |
| --- | --- | --- | --- |
| 元数据库 / BI 语义层 | 多数不存血缘，或只有作业依赖推导的表级关系 | 不适用 | 无法回答字段级问题 |
| 集中式采集目录 | 关系库的行表 | 递归物化的中间结果规模 | 深度与扇出上升后代价失控 |
| 事件驱动式目录 | 血缘图（图存储或图模型） | 访问到的节点数 | 高扇出节点处结果集爆炸，需要截断 |
| 联邦式目录 | 各域各自的关系，中央只有跨域桥接边 | 路径穿越域的次数 | 每一跳都是一次分布式调用 |
| 图谱式目录 | 关系进图存储，属性留关系库 | 访问到的节点数（边是一等公民） | 结果规模由图的局部密度决定 |
| AI 增强目录 | 不改变关系存放，只是消费关系 | 同上（取决于其底座） | 同上 |

**由此必然导出的性质（因果句）**：因为**图存储把边当成存储的一等公民**，所以「深度若干跳的下游」的查询代价与**访问到的节点数**相关，而不是与全图规模相关——关系库的递归 CTE 要对每一层的中间结果反复物化，深度一深代价就失控。而**因为结果规模由查询点附近的局部密度决定**（少数核心字段被大量下游引用），所以「毫秒级血缘」在高扇出节点上会反转成「只能返回前 N 条并提示已截断」——**精确性与响应性在血缘查询里是对立的**，这一点必须在设计时就承认，不能靠调参解决（§3.2.6 失效点）。反过来，因为关系库在浅链路（1–2 跳）上完全够用且运维成本最低，所以**在只需要回答「这张表被谁用」时，引入图存储是纯亏**。

**这条机制决定了门禁是「被遵守」还是「被绕过」**：粒度不够的影响面清单要么漏（下游字段级引用看不见），要么过度阻断（把改字段名当成改全表）——后者会让团队学会申请豁免（§3.5）。所以字段级血缘不是「更细更好」，而是**门禁能成立的前提**。

**公开证据**【公开】：Lyft 开源的 Amundsen 用 Neo4j 存血缘关系、Elasticsearch 做资产检索（主文件 §1.4 记其 2019 年开源，§4.3 记为「基于 Neo4j + ES」），即「属性与关系分存」这一形态；DataHub 提供图查询用于血缘遍历（§3.2.6）。判定方法：用血缘图里扇出最大的那个字段跑一次 3 跳下游查询，看返回结果集大小与耗时——结果集超过界面能展示的数量级时，你已经在依赖截断，此时必须在接口上显式标注「已截断」。

**失效条件**：当血缘只做到表级、且组织规模在千级表以内时，关系库的递归 JOIN 足够，图存储的运维技能栈（备份、扩缩容、慢查询分析、冷热分层）是净成本。

#### 7.3.4 检索键的宽窄：表名匹配 vs 业务语言

**机制是什么**：人用业务语言提问，目录按表名与字段名匹配。这条鸿沟不是数据问题，是检索键的问题。AI 增强层做的事就是把检索键从「表名」换成「业务语言」，方法是在已有元数据之上建一层向量 + 倒排的派生索引，LLM 只在已登记资产的封闭集合里做选择与解释。

**它在各候选中的实现差异**：

| 候选 | 检索键 | 谁在用得到 | 成本随什么增长 |
| --- | --- | --- | --- |
| 元数据库 | 库名 / 表名 / 字段名 | 数据团队自己 | 资产数 |
| BI 语义层 | 报表与数据集名 | 分析师 | 报表数 |
| 集中式 / 事件驱动 / 联邦式目录 | 表名 + 标签 + 分类 + Owner | 记得名字或知道域的人 | 资产数 |
| 图谱式目录 | 上述之外增加「沿关系找」 | 做影响面分析的人 | 资产数 + 查询跳数 |
| AI 增强目录 | 业务语言（自然语言） | 不懂表名的业务方 | **用户数 × 提问频次** |

**由此必然导出的性质（因果句）**：因为**相似度检索永远会给出一个 Top-1、默认没有「查不到就拒答」的行为**，所以当元数据的业务描述覆盖率不足时，「自然语言搜索」反转成「自信地返回错误资产」——用户看到的是一个格式完整、但语义不相干的答案（§3.2.5 失效点）。因此这一层必须成对交付两件事：低置信度时明确拒答，以及答案里每一条都能指回一条可点击的元数据依据。**它是放大器，不是补课**：元数据质量差时，它放大的是错误。

第二层机制与成本有关：**因为每次提问都要付 token，AI 增强层的成本随「用户数 × 提问频次」增长**，而其余候选的成本随「资产数」增长。这是本章唯一一个成本函数形状与其余候选族不同的候选——这一条在 7.4 会展开。

**公开证据**【公开】：Databricks Genie（Data+AI Summit 2024 发布）与 Snowflake Cortex Analyst（2024）把自然语言入口做进云数仓；Alation AI、Atlan AI、Secoda AI 在 2024 年前后推出目录侧的 AI 增强检索（§3.2.5 与 §4.3 工具链均列有这三条及年份）。判定方法：拿一个「目录里确实不存在的资产」去提问，看它是拒答还是给出一个最接近的错误答案——后者说明它没有置信度闸门。

**失效条件**：当消费方全部是数据团队（知道自己要找的表名或字段名）时，关键词与标签检索的命中率已经够用，AI 增强层的收益趋近于零，而账单按提问次数照付。

### 7.4 成本结构对比（不是价格表，是成本函数）

各候选族的成本函数**形状不同**，这才是选型的核心。写成统一形式：

```
月成本 ≈ 存储(资产数 × 每资产元数据体积 + 边数 × 每边体积)
        + 采集与解析算力(源系统数 × 引擎数 × 采集频率 × 解析复杂度)
        + 检索服务(资产数 × 索引数) + 自然语言层(用户数 × 提问频次 × 单次成本)
        + 人力(常驻组件数 × 技能稀缺度 + 业务描述的补录与校正)
        + 治理澄清成本(口径歧义数 × 组织规模)
```

**先算掉最容易被高估的一项：存储**【推算】。以十万级资产为例（【经验】：中大型企业的常见量级），按主文件 §2.2 的元数据模型估算，每资产的技术 + 业务 + 管理元数据约 2–5 KB，取 4 KB → 10 万 × 4 KB ≈ **400 MB**；血缘按 100 万条边、每条约 200 B（按主文件 §2.2 的血缘模型字段清单估算）≈ **200 MB**。合计不到 1 GB。按对象存储标准层 **$0.023/GB-月**【公开】（[AWS S3 定价页, 2024]）推算，月成本 **不足 $0.03**【推算】。**结论：元数据的存储成本在任何规模下都不是主导项——目录的账单由采集解析算力与人力决定。** 这条推算的意义在于：凡是把「元数据存哪、存多重」当成主要成本项的方案比较，讨论的都是次要项。

**每一项的主导者不同**：

| 候选族 | 主导项 | 隐性项 | 资产数翻 10 倍时的行为 |
| --- | --- | --- | --- |
| 族一（元数据库 / BI 语义层 / 湖仓一体 / 契约台账） | 引擎或生产方的成本 | **覆盖范围**（湖外资产要另建一套） | 近似线性，且不需要新增人力 |
| 族二（集中式 / 事件驱动） | 采集与解析算力 | **全量采集窗口**（拉）或**事件重放耗时**（推） | 超线性：解析器数量随「源系统 × 引擎 × 版本」增长 |
| 族二（联邦式） | fan-out 的网络往返 | **对齐表的人工裁决** | 跨域查询延迟由最慢分支决定，域数越多越慢 |
| 族三（图谱式） | 图存储与多跳查询 | **双写一致性的维护** | 高扇出节点的结果集爆炸，需要截断 + 分页 |
| 族四（AI 增强） | 用户数与提问频次 | **向量索引的刷新任务** | 资产数翻 10 倍若不带来用户增长，成本几乎不变 |

**「用户数驱动」与「资产数驱动」的差别是本章最容易被算错的一笔账**：族二、族三的成本随资产数走，用户从 10 人涨到 100 人账单几乎不变；族四反过来——资产数翻倍而用户不变时成本不涨，用户数翻 10 倍时成本线性上涨。所以**「AI 增强目录会不会更贵」完全取决于你的用户基数与提问频次，而不是数据规模**；这正好解释了为什么它在小团队自助分析场景里可能比传统目录贵，而在大规模内部数据平台上反而摊得薄。

**检索服务的成本项也要拆开看**，它包含三个形状不同的部分：

| 成本项 | 随什么增长 | 谁会忽略它 |
| --- | --- | --- |
| 索引服务常驻成本 | 资产数 × 索引数（检索、血缘、向量各一份索引） | 只算存储的人——索引常驻内存，单价远高于存元数据的对象存储 |
| 向量索引的刷新成本 | 元数据变更量 × 变化资产的嵌入成本 | 把向量化当成「上线时跑一次」的人——描述一改，索引就要重算 |
| 自然语言层的调用成本 | 用户数 × 提问频次 | 用资产数去论证「AI 层很便宜」的人 |

**索引常驻是这三项里最被低估的一项**：因为一份检索索引、一份血缘索引、一份向量索引要同时常驻，索引数每加一层就是一次乘法；而它们的介质单价远高于元数据本体所在的对象存储——**元数据本体便宜，不代表承载它的索引也便宜**。

**采集与解析这项常被当成一次性投入，其实它按「源系统数 × 引擎数 × 版本数」计息**：每多接一种源、每多支持一个引擎版本，都要多维护一个解析器。它在启动期是 0，在两三年后通常是最大的人力开支项（§3.2.1 代价①）。判断方法：数一遍你当前维护着多少个采集器与多少个引擎版本分支——把这两个数相乘，就是这项成本的乘数。

### 7.5 决策树（每个分支都要有阈值依据）

```
[资产是否集中在一两个引擎、且该引擎自带 catalog？]
   │
   ├── 是 → 湖仓一体目录（Unity Catalog / Gravitino 托管面 / Snowflake Horizon）
   │        │
   │        └── [湖外还有关系库 / 消息 / BI / 指标资产吗？]
   │              ├── 有 → 湖内：湖仓 catalog 为权威源（不复制 schema）
   │              │         湖外：采集式目录覆盖；统一检索层合成一个入口
   │              └── 没有 → 止步于此
   │
   └── 否 → [是否存在有权定义口径的中心团队？]
            │
            ├── 是 → 集中式采集目录（DataHub / OpenMetadata / Atlas / DataWorks）
            │        │
            │        └── [全量采集窗口是否已占刷新周期的一半以上？]
            │              ├── 是 → 改推：元数据变更事件 + 增量消费
            │              └── 否 → 维持全量拉
            │
            └── 否 → 联邦式目录（权威源留在各域，中央只读检索层）

（以下两问对上述所有分支共用）

[是否需要回答「这个字段被哪些下游字段引用」？]
   ├── 是 → 叠加图谱式关系层（关系进图存储，属性留关系库）
   └── 否 → 关系库递归 JOIN 足够，不要引入第二套存储

[消费方里有不懂表名的业务方吗？]
   ├── 有 → 叠加 AI 增强目录（Atlan AI / Secoda AI / Alation AI）
   │        并硬性附带：低置信度拒答 + 每条答案可点回一条元数据
   └── 没有 → 关键词 + 标签检索足够，不要为 AI 层付费
```

**阈值依据**（树上每个判断节点在此各有一条，逐条对应）：

- **「资产是否集中在一两个引擎、且该引擎自带 catalog？」**：依据是 7.3.1 的副本机制。湖仓一体的优势来自「schema 随写事务提交、不存在第二份真相」，这个前提只在资产确实住在那个引擎里时成立。判定方法：统计「湖外资产数 / 全部资产数」，若湖外占比不可忽略，这条分支就不能单独走完。
- **「湖外还有关系库 / 消息 / BI / 指标资产吗？」**：依据是覆盖范围的边界效应。湖仓 catalog 只照亮它管的引擎，而业务方不会区分「目录里没有」与「公司没有」——所以这不是优化项，是必需的第二层。同时必须写下合并规则（同一个真实资产在两边各有一条记录怎么处理），否则检索结果会出现重复资产。
- **「全量采集窗口是否已占刷新周期的一半以上？」**：这条线的形式**不是资产数而是比值**，因为失效的机制是「采集耗时 ∝ 资产数，而刷新周期固定」这两条曲线的相交，而不是某个绝对规模（§3.2.1 失效点）。取「一半」作为余量是【经验】判断：窗口吃掉半个周期后，任何一次采集重试或源端慢查询都会让本轮采集跨过刷新时刻，新鲜度从「偶尔落后」变成「稳定落后」。这个比值的两个量都能从现有监控里取到，不需要先做容量评估。判定方法：把最近一周的采集耗时与刷新周期画在同一张图上，看两条线是否已经相接。
- **「是否存在有权定义口径的中心团队？」**：依据是集中式目录的成立前提。集中式目录的一致性由**写入约束**保证（URN 全局唯一、Owner 非空、分类分级非空——见 §3.2.1 的 DDL），但登记率由**权责**决定：中心团队若无权替各域定义口径，各域就没有动力把资产登记进去，登记率长期停在低位，目录变成一份「部分真相」。判定方法：问「谁有权裁决两个 BU 对同一个指标的两种口径」——答不出具体的人，就是不存在。
- **「是否需要回答『这个字段被哪些下游字段引用』？」**：依据是 7.3.3 的代价结构。这条判据不是关于规模的，是关于**问题的形态**：只要变更流程里有字段改名或口径调整，就必须先验证一次最大扇出字段的 3 跳查询，再决定关系层用关系库还是图存储。
- **「消费方里有不懂表名的业务方吗？」**：依据是检索键机制（7.3.4）。关键词检索只服务「记得名字的人」；当消费方主体是业务方时，命中率低的根因不是元数据少，而是检索键与提问方式不匹配。**反向条件同样重要**：消费方全部是数据团队时，AI 增强层没有可服务的鸿沟，却带来一个随用户数增长的账单项和一套需要持续刷新的派生索引——此时不引入它才是正确决策。

**上树之前先做的三项验证**（都比选型更重要）：

1. **量一次「采集窗口 / 刷新周期」**：这个比值决定你是拉还是推（对应 7.3.2）。
2. **跑一次最大扇出字段的 3 跳下游查询**：看结果集是否需要截断（对应 7.3.3）。
3. **若已上线自然语言入口，用目录里确实不存在的资产提一次问**：看它是拒答还是给出一个最接近的错误答案（对应 7.3.4）。

这三项里任意一项不满足业务要求，无论落在树的哪一档，都应该先换方向，而不是先调参数。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 资产集中在单一湖仓、治理要求是「看清有什么」 | 湖仓一体目录 | 采集式目录 | 采集式会引入第二份 schema 真相，两份必然分叉 |
| 资产分散在多引擎、有中心治理团队 | 集中式采集目录 | 湖仓 catalog + 采集目录双层 | 单靠湖仓 catalog 只覆盖湖内，业务方误以为公司没有 |
| 多业务线、中心团队无权定义口径 | 联邦式目录 | 集中式 + 强推登记 | 中心团队无权时登记率上不去，目录停在部分真相 |
| 元数据日变更频繁、CI 门禁要感知变更 | 事件驱动式目录 | 增量拉（缩短周期） | 周期缩短到某个点后，全量扫描窗口仍会追平周期 |
| 变更流程里有字段改名或口径调整 | 图谱式关系层 + 采集式目录 | 关系库递归 JOIN | 深度与扇出增加后，递归物化的代价失控 |
| 消费方以业务方为主、且有持续提问量 | AI 增强目录（叠加在已有目录之上） | 关键词 + 标签检索 | 没有向量层时业务方仍要懂表名，发现能力只覆盖记得名字的人 |
| 只有百级表、一个消费方 | 元数据库 + 轻量检索 | 任何完整目录平台 | 目录的固定成本（采集链路 + 人力）在这个规模收不回来 |
| 多团队 Data Mesh、口径争议频繁 | 数据契约 + 资产台账 | 纯目录平台 | 契约是双边承诺、目录只是展示面；只建展示面无法约束生产方 |

**常见组合**（「OneService」与「数据 API 网关」合并为一条、「RAG」与「Agent」合并为一条；另新增 2 条，共 5 条）：

1. **湖仓一体 catalog + 采集式目录（湖内湖外分工）**：构成——湖内资产的 schema 真相由表格式与引擎 catalog 承担，湖外资产（关系库、消息、BI、指标）由采集式目录覆盖，统一检索层把两边合成一个入口。职责边界——谁管 schema 谁就是权威源，中央目录**不复制湖内 schema**，只存指针与跨域关系。运维代价——需要两套 URN 的映射表与合并规则，长期维护落在中央团队。【经验】
2. **元数据变更事件流 + 图谱式关系层（采集与关系分离）**：构成——事件流做写路径，图存储做血缘的多跳读模型，倒排索引做检索，属性仍留在关系库。职责边界——事件流只管「发生了什么变更」，不做关系推理；图只回答影响面，不承担全量属性查询；两者必须共享同一个 URN。运维代价——三套存储 + 一个消费者组；必须保证「重放事件能重建图」，否则图与属性库会漂移出幽灵资产。【经验】
3. **目录 + 质量分 + 发布门禁**：构成——目录提供资产与 Owner，质量系统产出新鲜度 / 完整性 / 校验通过率，检索结果按质量排序；关键元数据缺项时禁止发布。职责边界——目录负责「有与没有」，质量负责「好不好」，门禁负责「能不能上」。运维代价——质量分必须回写到目录并参与排序，否则它只是一个没人看的看板；门禁若无字段级血缘支撑，会因过度阻断而被绕过（§3.5）。【经验】
4. **目录 + OneService + 数据 API 网关（从「可发现」到「可调用」）**：构成——OneService 提供统一数据服务，数据 API 网关负责鉴权、限流与配额，两者把目录里登记的分类分级当作授权依据。职责边界——目录是「可发现 + 可理解」的入口，OneService 是「能取到」的出口，网关是「谁可以取多少」的闸门；**分类分级只能有一个真源**，否则会出现「目录里标机密、网关放行」这种越权。运维代价——三者的资产清单与权限口径要同步，任何一处漏配都是越权。【经验】
5. **目录 + RAG + Agent（元数据成为机器可读的取数依据）**：构成——目录元数据向量化供 RAG 检索，目录以 API / MCP 形式向 Agent 暴露「有哪些资产、口径是什么、谁能读」。职责边界——目录提供机器可读的元数据及其来源；RAG / Agent 只做选择与解释，**不得指向目录里不存在的资产**。运维代价——向量索引是元数据的派生副本，必须随元数据变更增量刷新；且每个结论都要可点回一条元数据依据，否则幻觉会以「格式完整的错误答案」形式出现。【经验】

> 组合的第一原则是**让每一件做它机制上最擅长的事**：湖是权威源就别让目录再抄一份，图回答问题就别让它承担属性查询。第二原则是**组合数不超过团队的运维带宽**——上面 5 个组合里，每多一件就多一份 URN 对齐、多一处新鲜度告警、多一个「两套系统对同一个问题给出不同答案」的战场。凡是「两套系统都要能回答同一个问题」的组合，最终都会变成口径不一致的战场。

### 7.7 选错的代价与迁移成本

**反模式：把目录当「表清单」建** —— 症状：采集器把 schema、分区、统计信息抓全了，业务含义、Owner、SLA、密级没人填，上线三个月后描述大比例过期。后果：技术元数据只能回答「有什么」，回答不了「能不能用、该怎么用」，业务方仍然要问人，检索次数长期低位；而检索次数低 → 没有采集压力 → 元数据更差，进入负循环（§3.5 的「只为合规而建」与「过度依赖人工」）。正确的做法：**关键元数据（业务含义 / 分层域 / Owner / SLA / 密级）缺项时禁止发布**，把质量压在入口上；机器能拿到的（schema、分区、血缘、访问统计）全部自动采集，人工只补机器拿不到的那一小部分。

**反模式：先上 AI 增强层，再补元数据质量** —— 症状：演示效果很好，业务方开始使用后频繁被引到错误的资产上，而答案看起来完整可信。后果：相似度检索永远返回 Top-1，描述为空的资产被向量化成「高维空间里的没有信息」，于是「找不到」变成「找错」，而后者更难被发现（§3.2.5）。正确的做法：先让一个高频找数场景在目录里跑通（业务描述覆盖到位），再叠加向量层；且必须带低置信度拒答。

**反模式：用湖仓 catalog 当全公司目录** —— 症状：湖内资产一目了然，湖外的关系库、消息队列、BI 报表与指标在检索结果里根本不存在。后果：业务方不区分「目录里没有」与「公司没有」，于是继续走「问熟人」的老路，而这次他们还多了一个失败过的入口。正确的做法：湖仓 catalog 只做湖内权威源，湖外由采集式目录覆盖，统一检索层合成一个入口，并把重复记录的合并规则写下来。

**反模式：把血缘门禁挂在表级粒度** —— 症状：改一个字段名也被当成改全表，门禁频繁阻断，团队开始集中申请豁免。后果：门禁不是被遵守而是被绕过，血缘的投入无法转化为事故下降（§3.5「血缘断裂（只到表级）」）。正确的做法：用 SQL 解析生成字段级血缘并定时校准，让门禁「严格但不过度」。

| 迁移方向 | 元数据迁移 | 查询与接口改写 | 运维重建 | 团队再学习 | 量级（【经验】） |
| --- | --- | --- | --- | --- | --- |
| 元数据库 → 采集式目录 | 需重采（元数据库只有技术元数据） | 需改检索入口与 API | 新增采集链路与调度 | 中 | 月级 |
| 采集式目录 → 湖仓一体目录 | 湖内不再抄、改存指针，湖外保留 | 需合并两套入口 | 需维护 URN 映射表 | 中 | 月级 |
| 集中式 → 事件驱动 | 采集器从「写库」改成「发事件」 | 接口不变（读路径仍查索引） | 新建索引消费者与重放机制 | 高（要懂事件顺序与重放） | 月级 |
| 集中式 → 联邦式 | 明细留在各域，中央只建路由与对齐表 | 跨域查询从单库查询改成 fan-out | 需指定对齐仲裁者 | 高（从改代码变成谈权责） | 季级 |
| 关系库 → 图存储（关系层） | 边需重新导入 | 图查询语句重写 | 引入第二套存储与一致性同步 | 高 | 月级到季级 |
| 传统目录 → 叠加 AI 增强层 | 元数据不变，需切块与向量化 | 新增自然语言入口，保留原检索入口 | 需维护随元数据增量刷新的向量索引 | 低到中 | 周级到月级 |

> 注意「采集式目录 → 湖仓一体目录」这一行与直觉相反：它看起来是升级，实际的迁移动作是**删掉一份副本**（湖内不再采集 schema），代价是接受湖外资产必须另建一层。**目录迁移的主要工作量从来不在搬迁元数据，而在重新划定权威源与合并规则。**

### 7.8 小结

数据目录选型的特殊性在于：**它选的是「真相放在哪」，而不是「哪个产品更好用」**。所有候选的差异都可以收到一条上——它与元数据真相之间隔了几层副本。零副本（元数据库、湖仓一体目录）换来一致性与低运维，代价是覆盖范围被引擎边界钉死；一层副本（集中式 / 事件驱动 / 联邦式）换来多引擎覆盖，代价是不一致的可能性随「采集窗口 / 刷新周期」上升；两层副本（AI 增强层）换来业务语言检索，代价是多一条刷新链路与一个随用户数增长的账单。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 资产集中在单一湖仓、要求目录结构与真实表结构永不分叉 | 湖仓一体目录 | schema 随写事务提交，第二份真相根本不存在 |
| 湖外还有大量关系库 / 消息 / BI 资产 | 湖仓 catalog（湖内权威）+ 采集式目录（湖外）+ 统一检索层 | 湖仓 catalog 的权威源只在它管的引擎内，覆盖范围由引擎边界决定 |
| 有中心治理团队、多引擎、需要统一口径 | 集中式采集目录 | 写入约束（URN 唯一、Owner 非空）能挡住「同名资产冲突」与「无主资产」 |
| 元数据日变更频繁、门禁要感知变更 | 事件驱动式目录 | 新鲜度不再受全量扫描窗口限制，改受消费者滞后期限制 |
| 多业务线、中心团队无权定义口径 | 联邦式目录 | 权威源留在各域，域内口径变更不需要跨组织协调 |
| 变更流程里有字段改名或口径调整 | 叠加图谱式关系层 | 递归 CTE 逐层物化中间结果，深度与扇出一上来代价就失控 |
| 消费方以业务方为主且提问量持续 | 叠加 AI 增强层（保留原检索入口） | 检索键从表名换成业务语言，但必须配拒答与可点回的元数据依据 |
| 只有百级表、一个消费方 | 元数据库 + 轻量检索 | 目录的固定成本（采集链路 + 人力）在这个规模收不回来 |

> 本节小结：本章所有候选之间，**唯一真正起决定作用的差异是「元数据的权威源放在哪、目录与它之间隔了几层副本」**——它同时决定了覆盖范围（能不能看见全部资产）、一致性上限（会不会出现两份真相）、刷新责任（谁必须持续做事）与推广难度（要不要动员组织）。其余维度（检索体验、可视化、AI 能力）都是在确定了权威源之后才需要精算的第二层问题；先算这份账，再谈其他。
>
> 💡 **思考锚点**：量两个数再选型：一是你的目录与元数据真相之间隔了几层副本（零 / 一 / 两），二是「采集窗口 / 刷新周期」这个比值。第一个数决定你该不该换权威源，第二个数只决定你该拉还是推——你的第一个数现在是几，和 7.5 决策树给你的分支对得上吗？
