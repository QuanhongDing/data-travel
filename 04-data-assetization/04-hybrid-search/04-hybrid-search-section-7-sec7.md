## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

原文件给「语义匹配」列打了 `单一向量 = 5 / 单一 BM25 = 1`，又在「精确匹配」列打了 `单一向量 = 1 / 单一 BM25 = 5`，7 个维度行 × 5 个候选列逐格打完分，结论是「向量 + BM25 + Reranker ★」。这个结论本身是对的，但它**用分数掩盖了本节最重要的一个事实：这里的候选大多不是互斥选项，而是管线上的不同段**。「向量 + BM25」是召回层的做法，「Reranker」是排序层的做法，「KG」是控制流上的增强，「Late Interaction」既可以是召回也可以是排序。把它们排成一列逐格打分，等于问「发动机和后视镜哪个更重要」——**你最后一定是都要，问题只是先装哪个、以及哪个在你的场景里根本不值。**

第二个问题是**维度不可加**。打分表把「多跳推理」的 1 分与「延迟」的 5 分并排放在同一张表里（原表只罗列分数，既未给权重、也未真的做过加权求和——但把不同性质的维度放进同一张可加的表，本身就是打分表方法论的默认暗示：**分数既然能并排，就能相加**），而这两项不是可以折价的商品：一个每周出现几百次的跨文档汇总类问题，答不出来是**能力缺口**（补不了就是补不了）；而延迟从 100 ms 涨到 200 ms 是**体验权衡**（可以用缓存、可以异步、可以只对少数查询开）。把能力缺口和体验权衡放进同一个加权和，等于默许「用能力换延迟」。

第三个问题是**阈值凭空来**。原决策树写「召回率 > 90% → 单一向量检索」，但 90% 这个数没有来源，而且**Recall@K 是不可跨系统比较的指标**：它随 K、随语料切分粒度、随问题集难度变化，同一个系统在 K=10 与 K=100 上、在「答案落在一个 chunk 里」与「答案需要跨三个 chunk 拼」的问题上，Recall 能差出几十个百分点。用一个没有定义的 90% 做分支条件，等于把决策权还给直觉。本章的做法是：把阈值换成**可推导的量**（精排阶段的前向次数、问题的多跳占比、语料日变更比例），并在树下写出推导链。

第四个问题是**评估顺序被跳过**。原表把「召回率」和「工程复杂度」并列打分，但这两项在决策里的地位完全不同：召回是**上游约束**（它决定系统的天花板），复杂度是**下游成本**（它决定你维护得起什么）。因为融合不能创造候选集里不存在的文档、精排只能在已召回的集合里重排，所以「召回不够」是一个无论花多少钱在排序上都解决不了的问题。**投入顺序不能反：先修召回，再修排序。**

本章保留原文件的**候选清单**与决策顺序，但把每个结论换成可推导的因果链，并对所有数字标注档位：【公开】指有官方文档 / 论文 / 模型卡可引，注明来源与年份；【推算】指由公开前提推导，正文写出推导链；【经验】指行业普遍实践，只给区间与条件。凡是既无来源、又精确到有误导性的数字（例如「召回率提升 47%」），本章一律不写——检索指标的绝对值高度依赖问题集与切分方式，**跨系统引用一个百分比，比不引用更有害**。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 失败模式是否互补 | 两路的漏召回是否落在同一批查询上 | 融合的收益只来自错误**不相关**；两路同源时融合等于重复劳动（§7.3.1） |
| 交互深度 | query 与 doc 在什么时候相遇 | 决定它是能做召回还是只能做精排，以及成本随候选数怎么长（§7.3.2） |
| 融合的坐标系 | 融合发生在排名空间还是分数空间 | 分数不可比是常态，决定要不要引入归一化参数与其风险（§7.3.3） |
| 索引与存储放大 | 每篇文档要存几个向量、几个表示 | 决定规模上限与写入成本；晚交互的存储是双塔的一个数量级以上（§7.3.2） |
| 增量更新代价 | 语料变一条要重建多少东西 | 决定方案能否覆盖高频更新的语料；这是 KG 路线的真正门槛（§7.3.4） |
| 评估可分解性 | 出问题时能否定位到「哪一路漏的」 | 不可分解的方案无法调参，只能整体换掉，也无法做回归 |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者（【经验】） | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 单一稠密向量（双塔 + ANN） | 语义召回 | 每篇文档一个向量，用近似最近邻搜索取 Top-K | 通用 RAG 起步形态 | 模型开源（BGE / E5 等）+ 索引自建或托管 |
| 单一 BM25（倒排） | 词项精确召回 | 倒排表 + 词频饱和 + 文档长度归一化，无训练参数 | 搜索引擎、日志检索 | 开源（Lucene / Elasticsearch / OpenSearch） |
| 稠密 + 学习稀疏（SPLADE++） | 两路都用模型 | 稀疏表示走倒排、稠密走 ANN，稀疏侧学到词项扩展 | 检索质量优先的自建栈 | 开源模型 |

| + Cross-Encoder 精排 | 精排层 | query 与 doc 拼接后过一次模型，只对 Top-K 做 | 对准确率敏感的业务 | Cohere Rerank 等商业 + BGE-reranker 等开源 |
| + Late Interaction（ColBERTv2） | 晚交互做召回或精排 | 每 token 一个向量，MaxSim 求和；doc 侧可离线预计算 | 存储便宜、算力贵的场景 | 开源（ColBERT / ColBERTv2） |

### 7.3 机制差异：为什么它们表现不同

#### 7.3.1 两路的失败模式是否互补

**机制是什么**：BM25 的打分是「查询词项在文档中的加权出现」，稠密向量是「固定维度空间上的距离」。两者的失效方式来自完全不同的原因。

**实现差异**：

| 候选 | 打分的依据 | 典型漏召回 | 典型误召回 | 对词表外 token 的表现 |
| --- | --- | --- | --- | --- |
| 单一 BM25 | 词项出现次数 + IDF + 文档长度归一化 | 同义改写、跨语言、错别字、口语化提问 | 词面相同但语义无关（一词多义） | **精确**（型号、订单号、错误码原样匹配） |
| 单一稠密向量 | 训练目标下的向量距离 | 稀有 token 被「语义相近」吸收 | 语义相近但业务上必须区分（型号后缀、版本号、单位） | 差（未见过的 token 与相近 token 难以区分） |
| 学习稀疏（SPLADE++） | 模型预测的词项权重 + 扩展项 | 扩展项选错时引入噪声 | 扩展过度导致主题漂移 | 中（词表仍基于原始词表） |
| 密集 + BM25 融合 | 两路的排名 | 取决于两者共同的盲点 | 取决于两者共同的盲点 | 继承 BM25 的精确性 |

**由此必然导出的性质**：因为两路的错误来源不同——一路错在「词面不同、意思相同」，另一路错在「意思不同、词面相近」——所以它们的**召回并集上限高于任一单路**，这才是融合有效的原因。反过来说，**融合的收益完全来自错误的不相关性**：如果两路实际同源（例如两路用了同一个查询改写结果、或稀疏侧就是稠密模型蒸馏出来的），错误高度相关，融合的收益会接近零，而成本照付。

这条机制直接给出一个必须在动工前做的测量：**取同一个问题集，分别跑两路，画出两张「哪条文档被漏掉」的集合，并同时算两个量**——漏召回集合的**交并比 J**（诊断量：J 接近 1 说明两路漏的是同一批文档，即两路同源），以及**并集 Recall@K 相对较优单路的提升幅度**（决断量：它才是融合真正能拿到的上限）。交并比用来解释原因，开关要看提升幅度：提升落在标注噪声量级之内（几百条问题的标注集上大致是 3–5 个百分点，【经验】）就按「高度重合」处理——此时你的问题不在「路数不够」，而在「两路都不行」，该换的是嵌入模型或切分策略，不是加一路。这条判定标准为什么用噪声量级而不是一个行业常数，见 §7.5 阈值依据（第 2 层）。

**公开证据【公开】**：RRF 由 Cormack、Clarke 与 Buettcher 在 SIGIR 2009 的论文中提出，其做法就是用多路检索结果的排名倒数求和，并在 TREC 数据上展示多路融合优于单路——这是「多路融合有效」这个结论的原始公开依据，也是 RRF 成为默认算法的起点；BGE-M3 的论文（arXiv，2024）以「同一个模型同时产出稠密、稀疏、多向量三种表示」为目标，说明工业界已经把「多路表示」当成默认需求（可自行核验其论文与模型卡）。

**失效条件**：当查询集本身只有一个失败模式时（例如内部的商品 ID 查询、日志检索），加一路只有成本没有收益。判定方法就是上面那次测量（交并比 + 并集上限提升）——它比任何基准分数都可靠，因为它是**在你的数据、你的问题上**测出来的。

**这个测量怎么做才算可靠**（三个细节决定结论是否可信）：

1. **标注的粒度必须与切分粒度一致**。如果召回的判定是「含答案的那个 chunk 是否进了 Top-K」，那么切分变了这套标注就作废——所以标注集要按**文档**切分，评测时再映射到 chunk。否则你会把「切分优化」的收益误记到「融合」头上。
2. **K 要固定并同时报告并集上限**。单路的 Recall@10 与两路的 Recall@10 并不是可比的（两路的候选池是两路的并集），真正要看的是「两路并集的 Recall@K」能否达到你要的下限——它给出了融合的理论上限；如果这个上限都不达标，融合再调也没用。
3. **失败要分类**。把漏召回的样本分成「语义理解失败」「专有名词丢失」「答案跨 chunk 未拼上」「切分把答案切断了」四类，只有第一、二类与路数选择有关。**第三、四类占了多数时，你该去修切分策略（见 [§4 工程实现](04-hybrid-search-section-4-sec4.md)），而不是加检索路。**

这三步的代价是一两天的人工标注，换来的是「加路还是换模型」这个判断的证据——它是本节所有决策里投入产出比最高的一次测量。

#### 7.3.2 交互深度：表达能力与成本的位置

**机制是什么**：query 与 doc 在什么时候相遇，决定模型能表达多细的匹配，也决定成本随候选数怎么增长。

**实现差异**：

| 结构 | query 与 doc 何时相遇 | 表达能力 | 每篇文档存储 | 能否用于召回 |
| --- | --- | --- | --- | --- |
| 双塔（Bi-Encoder，稠密） | 永不相遇，各自编码后比距离 | 受单向量瓶颈限制 | 1 个向量 | **能**（doc 侧可预计算 + ANN） |
| 学习稀疏（SPLADE++） | 永不 | 词项级，弱于晚交互 | 稀疏词项表（通常很稀疏） | **能**（走倒排） |
| 晚交互（ColBERT / ColBERTv2） | 在 MaxSim 阶段逐 token 比 | 强于双塔、弱于交叉编码 | 每 token 一个向量 | **能**（doc 侧可离线预计算） |
| 交叉编码（Cross-Encoder Reranker） | 一开始就拼接进同一个模型 | 最强（非 LLM 类中） | 不存储（在线算） | **不能**（每对一次前向） |
| LLM-as-Reranker | 提示词里拼接 | 最强且可解释 | 不存储 | 不能（成本最高） |

**由此必然导出的性质**：因为交叉编码器必须对**每一个** (query, doc) 对做一次前向，所以它的成本 ∝ K（候选数），这就是它只能用在 Top-K 精排、且 K 必须被压到几十到几百量级的根本原因——不是模型慢，而是**它无法预计算**。因为晚交互在 doc 侧把 token 向量预计算好了，在线只需做 MaxSim 的点积，所以它比交叉编码便宜得多（可以在更大的候选集上跑），同时比双塔准。**它的代价是存储在文档侧**：每篇文档要存「token 数 × 每 token 维度」的向量，这正是它没有取代双塔的原因——**限制晚交互的不是准确率，而是存储与写入放大预算。**

**【推算】晚交互的存储放大**：设每篇文档平均 128 个 token（【经验】，中英混排技术文档的量级），晚交互每 token 128 维 fp16 = 256 B，则每篇约 32 KiB；双塔 1024 维 fp16 = 2 KiB。比值约 **16×**。ColBERTv2 论文报告通过残差压缩把晚交互的存储占用降低 6–10 倍（【公开】ColBERTv2，NAACL 2022）——把上述 16× 除以压缩倍数，压缩后仍约为双塔的 **1.6–2.7 倍**。这就是它「在存储便宜、算力贵的场景受欢迎，在文档量大且更新频繁的场景受限」的定量解释：压缩只把倍数从约 16 降到 2 上下，没把它降到 1。

**失效条件**：当语料更新频繁时，晚交互的每 token 向量要随文档重建，写入放大约同倍数；当文档平均长度远大于 128 token（长合同、长篇报告）时，放大还会更大。反过来，当你的精排已经在用交叉编码器、且它没有成为延迟瓶颈时，晚交互带来的收益不足以支撑一次全量重建。

#### 7.3.3 融合的坐标系：排名空间还是分数空间

**机制是什么**：多路结果合并时，用「排名」做输入，还是用「分数」做输入。

**实现差异**：

| 融合方式 | 输入 | 是否需要归一化 | 参数 | 主要风险 |
| --- | --- | --- | --- | --- |
| RRF（倒数排名融合） | 各路的排名 | 不需要 | 常数 k（论文取 60） | 不能表达「我更信某一路」 |
| 加权求和 | 各路的归一化分数 | **需要** | 权重 + 归一化方法 | 量级不可比时权重失效 |
| Borda / Condorcet 等排序投票 | 排名 | 不需要 | 无 | 在多路质量差异大时不如加权 |
| 交叉编码器精排 | query + doc 原文 | 不需要（同一模型出分） | 模型本身 | 成本 ∝ K |

**由此必然导出的性质**：因为 RRF 只消费排名，所以**不同检索器的分数尺度差异被完全消掉**——这是它成为默认融合算法的唯一原因，也是它「无参数」的真实含义。反过来，加权融合必须先归一化，而归一化需要知道分布：min-max 的极值对离群值敏感，而 BM25 的分数在实际语料上**没有上界**（【经验】：在 Lucene 系实现上，一条高频命中的文档轻易把分数拉到几十分；判定方法就是打印自己语料上的 BM25 分数分布）；z-score 假设近似正态，而 BM25 的分布是长尾。于是出现一个非常典型的失败：**因为 BM25 的分数跨度是几十、余弦相似度在实践中挤在很窄的区间（大约 0.6–0.95 量级，【经验】），所以未归一化的加权和实际上等于「BM25 的分数 + 一个近似恒定的偏置」**——稠密这一路的排序贡献被淹没，而调权重时会出现「权重怎么调都像没调」的现象。

这条的性质还有一个「反面」：因为 RRF 不表达「我更信任哪一路」，所以当某一路在你的语料上确实明显更强时（例如一个全是自然语言问答、几乎不含专有名词的语料，BM25 近乎无信号），等权融合会把弱路的噪声引进来。此时正确的做法不是放弃融合，而是在候选生成阶段就调整各路取数（强路多取、弱路少取），**在融合之前控制输入质量，而不是在融合公式里加权。**

**公开证据【公开】**：RRF 的公式与 k = 60 这个经验常数见 Cormack 等人的论文（SIGIR 2009）；Elasticsearch 与 OpenSearch 都把排名融合（RRF）作为内置的混合检索能力提供（Elasticsearch 官方文档 Reciprocal rank fusion 章节，2023；OpenSearch 官方文档 hybrid search / rank fusion 章节，2023，两份均可自行核验）。

**失效条件**：当两路的分数**本来就同尺度**时（例如两路都是同一个模型产出的余弦相似度），归一化问题不存在，加权融合与 RRF 的差别很小，此时可以按可解释性来选。判定方法：分别打印两路在 100 条真实查询上的分数分布，看量级与方差是否可比——**可比就用加权，不可比就用 RRF。**

**RRF 里的 k 到底在调什么**：RRF 的贡献是 `1 / (k + rank)`。因为 k 出现在分母的加数上、与 rank 量级可比时，所以它控制的是「排名差异被放大的程度」——k 越小，第 1 名与第 10 名的贡献差越大（更倚重单路的头部结果）；k 越大，各名次的贡献越平坦（更像「多路都提到就加分」的投票）。论文取 k = 60，其效果是让排名在同一量级范围内（前一百名左右）的差异被显著压缩，从而**降低任何单路头部噪声对最终排序的影响**。这解释了为什么 RRF 在「两路质量都不错但任一路都有噪声」时好用，也解释了它为什么在「某一路质量显著更强」时会吃亏（平坦化把强路的头部优势也抹掉了）——此时应当靠**各路取数数量**而不是改 k 来表达偏好（§7.3.1 的失败分类测量同样适用于这里）。

#### 7.3.4 结构增强的代价：KG 与 Agentic 贵在哪

**机制是什么**：KG 与 Agentic 改变的不是「匹配方式」，而是「检索的控制流」——前者把「文档集合上的打分」换成「关系图上的遍历」，后者把「固定管线」换成「多轮决策」。

**实现差异**：

| 方案 | 索引时做什么 | 在线时做什么 | 成本随什么增长 |
| --- | --- | --- | --- |
| 混合检索（族 1 + 族 2） | 编码 + 建索引（分摊后极低） | 固定的几次检索 + 融合 | 与查询 QPS 线性 |
| 交叉编码器精排（族 3） | 无 | K 次前向 | 与 QPS × K 线性 |
| KG / GraphRAG（族 4） | **LLM 抽取实体关系 + 社区摘要** | 关系遍历 + 摘要读取 | 建图 ∝ 语料 token 数；更新 ∝ 变更文档数 × 抽取 + 对齐 |
| Agentic（族 4） | 无 | 多轮 LLM 决策 + 多次检索 | 与「平均轮数 × QPS」线性，且方差大 |

**由此必然导出的性质**：因为建图依赖 LLM 抽取，所以它的成本 ∝ 语料 token 数 × 抽取模型单价；而因为每篇文档变更后通常要重新对齐实体（合并同义实体、拆分裂实体、更新社区摘要），所以它的**边际更新成本远高于向量索引的插入**。这两条合起来决定了 KG 路线的适用域：**高价值、低更新频率、且多跳问题占比高**的语料。判定方法很具体：在你的问题集上标注「需要跨文档汇总或多跳的比例」，并统计语料日变更比例；多跳占比 ≲ 10–20%（【经验】）或语料每天大幅变更时，先别建图——为 10% 的问题把 100% 的语料做成图，是把成本摊在了不需要它的部分上。

**【推算】建图的语料量级**：设语料 100 万篇、平均 500 token，则一次全量抽取要处理约 **5 亿 token** 的输入；社区摘要还要在此基础上再跑一遍生成。这个量级的意义不在于绝对费用，而在于**它意味着建图必须被当成一条数据加工流水线来运维**（有分区、有重跑、有版本、有失败重试），而不是一个「建索引」步骤。把流水线当索引做的团队，第一次语料大更新时就会发现它不可重现。

**Agentic 的代价在方差而不在均值**：因为 Agent 每一轮都要调用 LLM 决策，且轮数由中间结果决定，所以它的成本与延迟的**方差远大于固定管线**——同一个问题在不同时间可能走 2 轮也可能走 8 轮。同时，「同一问题的检索轨迹不唯一」使离线评估不可复现，回归测试需要比固定管线更大的样本量才有统计意义。它适合低频高价值查询（复杂分析、跨源调查），不适合把高频在线 QPS 交给它。

**公开证据【公开】**：微软的 GraphRAG 于 2024 年开源，其公开材料把「实体与关系抽取 + 社区摘要」作为回答全局性问题的机制（可自行核验其仓库文档中的索引构建流程与成本提示）；主文件 §1.4 记录的 Agentic Hybrid Search 属 2024 年的方向，其机制与代价可对照各家 Agent 框架文档中的「最大迭代轮数」与「成本追踪」章节。

**失效条件**：当问题集中为「找一篇具体文档」时，图与 Agent 都属于过度设计；当语料规模小到可以用「多取一些候选 + 一个强精排模型」解决时，结构增强的收益同样被覆盖。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
总成本 ≈ 一次性索引成本（语料 token 数 × 每 token 编码成本；图抽取与社区摘要为其大头）
        + 存储成本 Σ_路 (文档数 × 每文档表示大小该路)
        + 在线成本 每查询 [ 查询编码 + Σ_路 检索(候选数 × 单次访问成本)
                            + 融合(候选数) + 精排(候选数 K × 每对推理成本) ]
        + 调参与评估成本（标注集 + 每轮改动的回归测试）
        + 运维成本（路数越多，需要同步的模型与索引版本越多）
```

**各候选的主导项与隐性成本**：

- **单路召回（族 1）**：主导项是索引存储与在线 ANN 访问；隐性成本是**召回天花板**——它的失败不会报错，只会表现为「答得不对」，且很难归因。
- **多路融合（族 2）**：主导项几乎没有增加（BM25 这一路通常几乎免费——倒排索引往往已经在你用的 ES / OpenSearch 里），真正增加的是**融合逻辑的调参与评估成本**。这是全表里性价比最高的一项，也是它成为事实基线的机制原因。
- **精排（族 3）**：主导项是 **K × 每对推理成本**，随 K 线性增长；隐性成本是「精排把明显不相关的结果排下去了，掩盖了召回缺失」，让问题更难发现。
- **晚交互**：主导项是**存储与写入放大**（见 §7.3.2 的 16× 推算）；它的成本不在查询时，而在每次语料变更时。
- **KG / GraphRAG（族 4）**：主导项是**一次性抽取 + 常驻的更新对齐**；隐性成本是抽取质量随模型版本漂移（换抽取模型等于换图），以及实体对齐错误的排查成本。
- **Agentic（族 4）**：主导项是**平均轮数 × 每次决策成本**；隐性成本是方差——容量规划要按 P99 轮数做，而不是按平均。

注意两类成本的增长方式不同：族 1 / 族 2 / 族 3 的成本随**数据量与 QPS**增长（可以容量规划），族 4 的成本随**语料变更频率与问题形态**增长（不可直接外推）。所以「要不要上族 4」不是一个纯粹的性能问题，而是一个**你的语料有多稳定**的问题。

**【推算】精排的成本随 K 的线性关系**：设精排阶段对 K 个候选各做一次前向。批处理能把单位成本压下来（同一批的矩阵运算摊薄、GPU 利用率提高），但**前向次数仍 ∝ K**，所以把 K 从 100 提到 500，精排阶段的计算量约 5×。这就是「精排的 K 上限由延迟预算反推」的来源：不是模型选得不好，而是你只能买得起这么多次前向。降低 K 的正当方式是提高召回质量（让正确答案更靠前），而不是为了省延迟而砍掉正确的候选。

**【推算】路数增加带来的运维面（而非机器成本）**：每加一路表示，就要多维护一套「编码模型版本 + 索引版本 + 重建流程」的对应关系。若两路使用不同的编码模型，则任何一次模型升级都要做两次全量重建、跑两次回归、并重新校准融合参数——**多路召回的隐性成本在这里，不在机器账单上**。这也是 BGE-M3 这类「一个模型出三种表示」的方案真正的价值：它把三路表示的版本对齐问题合并成一次升级。

**【推算】融合阶段的成本可以忽略，但它的调参成本不可以**：融合本身只是一次候选合并与排序（对 K 个候选做 O(K log K) 的排序），相对检索与精排可以忽略。真正的时间花在**确定权重与阈值**上：每改一次融合方式，都要重跑标注集、重算指标、确认没有在另一类问题上变差。若一次融合调整的回归验证需要 0.5–2 人日（【经验】），则「试三种融合方案再选最好的」这件事本身就要花掉数人日——这就是为什么 RRF（无参数）值得作为默认：**它一次性省掉的是一个持续发生的调参循环，而不是一次计算。**

把上面几项放在一起看，成本函数里真正随规模变化的是三项：**存储**（晚交互与 KG 放大）、**在线算力**（精排的 K 与 Agent 的轮数）、**语料加工**（KG 的抽取与对齐）。而族 2（多路召回与融合）几乎是唯一一项「加得越多、边际成本越低」的：倒排索引通常已经在引擎里，融合的计算量可以忽略，它增加的主要是一次性的评估工作量。**这也解释了为什么「先上混合检索、再考虑精排与结构增强」是正确的默认顺序——它是唯一一条低风险、可回退、且不锁死后续选择的路径。**

### 7.5 决策树（每个分支都要有阈值依据）

```
第 0 层（硬约束，先行）：答案是否只落在一篇文档/一个 chunk 里？
├─ 否（需要跨文档汇总、多跳、全局性归纳）→ 单路 + 更大 K 无解；先解决「能不能召回」，上关系图或 Agent（族 4），并接受成本结构变化
└─ 是 → 继续
第 1 层（先量，不猜）：分别跑稠密单路与 BM25 单路的 Recall@K，并求出并集上限
├─ 并集上限已达你的要求 → 问题不在召回；别加路，去修切分与生成
└─ 并集上限不达标 → 继续
第 2 层：两路漏掉的文档是否高度重合？
├─ 高度重合 → 融合收益接近 0（§7.3.1）；换嵌入模型 / 换切分策略 / 换表示（晚交互）
└─ 不重合 → 上融合：RRF（无参数、不需归一化）优于未做归一化的加权和
第 3 层：召回够、排序不够（Recall 高而 nDCG 低）
├─ 高 QPS（精排的前向次数 = QPS × K 超过单机可承担量级）→ 不上精排；或只在抽样流量上开（如头部 10%）
├─ 延迟预算买不起 K × 单对推理 → 换晚交互（doc 侧可预计算）或蒸馏小模型
└─ 买得起 → 上交叉编码器精排，K 取 50–100
第 4 层：语料与问题形态决定要不要结构增强
├─ 多跳 / 汇总问题占比 ≳ 10–20%（【经验】）+ 语料更新低频 → KG / GraphRAG（族 4）
├─ 查询形态多样、需多轮试探、且 QPS 低 → Agentic（族 4）
└─ 以上都不成立 → 停在「稠密 + BM25 + 融合 + 精排」，不要为了完整性加路
第 5 层（上线前，无阈值 / 可用性判据）：关掉每个新增组件，系统还能不能返回答案？
├─ 能 → 增强项（精排、KG 路、Agent 的某一路）：必须写明它的降级形态——Reranker 挂了降级为融合结果
└─ 不能 → 路径项（召回、融合）：它必须做成高可用，不能当可选开关
```

**阈值依据**：

- **「答案是否只落在一篇文档里」**（第 0 层，无阈值）：这是能力边界判据而不是性能权衡，所以排在所有阈值之前。判定方法：从业务问题里抽 50 条，人工标注「答案需要几篇文档才能拼出来」；这一列的比例直接决定你属于哪一族。
- **「Recall@K 达标」**（第 1 层）：**没有可迁移的行业常数，只有反推。** 做法是在带标注的问题集上画 Recall@K 曲线，同时统计「召回命中时的回答正确率」与「未命中时的编造率」：如果答案唯一、且生成器在缺乏证据时不编造，则回答正确率的上界约等于 Recall@K，于是可接受的下限应当由「你能接受多少问题答不出」反推，而不是抄一个数字（主文件 §1.2 提到的「工业级 RAG 要求 Recall@10 > 90%」应作为参考量级使用）。另外必须固定 K 与切分粒度后再比较，否则这个数在系统之间不可比。
- **「两路漏掉的文档是否高度重合」**（第 2 层）：判定量是**并集 Recall@K 相对较优单路的提升幅度**，不是交并比本身。做法见 §7.3.1：先得到两路的漏召回集合，交并比 J 用于解释（J 趋近 1 表示两路漏的是同一批文档，融合收益趋近 0），而「算不算高度重合」由提升幅度决定——提升落在标注噪声量级之内（几百条问题的标注集上大致 3–5 个百分点，【经验】：同一条问题「算不算被召回」的人工判定本身就会在这个范围内波动）即判为高度重合。这条阈值取噪声量级而不是某个行业常数，作用是**防止把噪声当收益去加路**；反过来，只要提升明显超出该量级，J 是多少都不影响「上融合」这个结论。
- **「K = 50–100」**（第 3 层）：【经验】档，由延迟预算反推（§7.4）：精排阶段的前向次数 ∝ K，批处理只摊薄单位成本、不改变线性关系；K 取到几百时精排会成为端到端延迟的主导项。这条阈值的作用是给出一个起点，真正的上限要靠在你的硬件上压测「单对推理延迟 × K vs 端到端预算」。
- **「多跳问题占比 10–20%」**（第 4 层）：【经验】档。低于这个比例时，建图的固定成本（抽取 + 对齐 + 摘要 + 流水线运维）摊不到足够多的问题上；高于这个比例时，图带来的召回增益会反过来改善整体指标。判定方法见 §7.3.4。
- **「先量并集上限」**（第 1 层）：这不是阈值而是**顺序约束**。因为融合不能创造候选集里不存在的文档，所以「先上融合再看效果」的做法本质上是在为一个未被诊断的问题付钱；而一旦它「看起来有效」，你会失去继续诊断召回缺陷的动机。
- **「RRF 优于未归一化加权和」**（第 2 层）：由分数尺度不可比这一事实决定（§7.3.3），判定方法是打印两路分数分布对比量级与方差；可比时才考虑加权（为了可解释性）。
- **「语料更新低频」**（第 4 层）：不设固定数值，因为它与语料规模相乘才有意义——判定式是「每次大更新的重抽 token 量 × 抽取单价」是否落在可接受预算内，以及「更新期间图与语料的偏差是否可容忍」。
- **「Agentic 只用于低 QPS」**（第 4 层）：依据是方差而不是均值（推导见 §7.3.4）——轮数由中间结果决定，容量规划必须按 P99 轮数做，成本与延迟随 QPS 相乘且分布长尾。判定方法：取一批真实问题跑一遍，统计轮数的 P99 与均值之比；比值大（分布长尾）时只把它挂在低频高价值入口上，不放进高频在线路径。
- **「高 QPS 不上精排」**（第 3 层）：这条不是质量问题而是**成本结构**问题——精排阶段的前向次数 ∝ K，属于与 QPS 相乘的项。判定方法：把你实际的 QPS × K 代入，看精排服务的总前向次数（次/秒）是否超过单机能承担的量级；超过就必须缩 K、换更小的模型，或只在抽样流量上开精排（例如只对头部 10% 的查询精排）。
- **「Reranker 挂了降级为融合结果」**（第 5 层）：这是可用性约束——精排是一个可摘除的环节，而**召回与融合摘不掉**。判定方法是问「关掉这个组件，系统还能不能返回答案」，能返回的是增强项，不能返回的是路径项。

**这棵树刻意不覆盖的分支**（以及为什么）：

- **「要不要用查询改写 / HyDE / Step-Back」**：它们改变的是**查询侧的表示**，属于族 1 的增强而不是路数选择，收益强依赖查询与语料的语言分布，没有可迁移阈值。判定方法是 A/B 而非推理：同一问题集上跑改写前后，看**并集上限**是否被抬高——如果并集上限没动，改写只是把排序改了。
- **「要不要自己训练嵌入模型」**：这是「领域词表与语料分布是否严重偏离通用模型」的问题，与本节的路数选择正交。判定方法：看你的失败案例里，「语义相近但必须区分」与「同义改写」哪一类占多数，前者指向训练，后者指向融合。
- **「要不要严格按打分选路」**：本章不提供分数排序，因为族之间是叠加关系；只有在**同族内部**（例如两种精排模型之间）才存在真正的替代，那时的比较应当在你的标注集上做，而不是引用公开榜单。
- **「要不要上多向量库 / 多模态融合」**：它改的是**表示的类型**（文本、图像、结构化各一路），而不是本节讨论的「同一表示的多种匹配方式」。判定方法是问「跨模态的查询在你的问题集里占多少」——如果接近零，多模态索引只是采购清单上的一行。
- **「要不要把检索结果缓存」**：缓存是延迟优化，不改变召回能力；判定方法是看查询的重复率，而不是看延迟有多紧。重复率低时缓存命中低，收益会被「缓存失效与版本一致性」的成本吃掉。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 通用企业知识库问答 | 稠密 + BM25 + RRF + 交叉编码器精排 | 用学习稀疏替换 BM25 路 | 单路稠密在专有名词与型号上漏召回，且失败不报错 |
| 全是自然语言、几乎没有专有名词 | 稠密单路 + 精排 | 加 BM25 路 | BM25 在此语料上近无信号，等权融合引入噪声 |
| 内部系统检索（ID、错误码、单号） | BM25 为主 + 稠密做补充 | 稠密单路 | 精确 token 必须精确匹配，相似度会给出「长得像」的错误单号 |
| 需要跨文档汇总（对比、综述） | 图 / 社区摘要（族 4） | 更大的 K + 更强的生成模型 | 打分式检索在关系信息上无表达力，加大 K 只是加噪声 |
| 高频在线问答（高 QPS、低延迟） | 稠密 + BM25 + RRF（不上精排） | 小模型精排（K 取小） | 交叉编码器成本 ∝ K，高 QPS 下不可负担 |
| 精度优先、QPS 低 | 稠密 + BM25 + 晚交互 / 交叉编码器 | 直接用 LLM 排序 | 成本按候选数线性，只适合低频高价值查询 |
| 语料每天大幅变更 | 稠密 + BM25 + 融合 | 晚交互 / KG | 每 token 向量与图边都要随文档重建，更新成本是同倍数的 |
| 存储预算紧、算力相对充裕 | 稠密 + BM25 + 交叉编码器精排 | 晚交互 | 晚交互的每篇文档存储是双塔的十几倍（§7.3.2） |
| 需要可解释的召回（为什么召回它） | BM25 为主 + 学习稀疏 | 纯稠密 | 词项级证据可解释，向量距离不可解释 |
| 多模态 / 跨语言 | 稠密（多语言模型）+ BM25 | 单路稠密 | 跨语言时 BM25 在查询语言与文档语言不一致时几乎失效 |

**常见组合**（每条注明职责边界与运维代价）：

- **混合检索 + RAG**（原 §7 组合）：混合检索是 RAG 的**召回层**，只负责「把正确的证据放进候选池」，RAG 负责编排、生成与引用。边界是：召回层不判断「够不够回答」，那是生成层或 Agent 的事。运维代价最低，但要盯住「召回质量」与「生成质量」两个独立指标的分解。
- **混合检索 + 向量湖**（原 §7 组合，见 [Ch4-02](../02-vector-lake/02-vector-lake.md)）：向量路走向量湖承载十亿级语料（【经验】量级，与 Ch4-02 的自有规模表述一致），BM25 路留在搜索引擎上。边界是：两边的语料必须同源同版本，否则融合的是两个不同快照的排名。运维代价是**两条摄入管线要保证同版本**，这是这套组合最容易出错的地方。
- **混合检索 + GraphRAG**（原 §7 组合）：向量与 BM25 负责「找到相关段落」，图负责「找到关系上相连但语义不相似的实体」。边界是：图不承担相似度排序，向量不承担多跳。运维代价是图的更新流水线（抽取 + 对齐 + 摘要）。
- **混合检索 + Agent**（原 §7 组合）：检索作为 Agent 的一个工具，Agent 决定调哪一路、调几次。边界是：Agent 不修改索引，只组合调用；每次调用都必须有限流与超时，否则一次失控的规划会打满检索集群。运维代价是必须为 Agent 的轨迹做可观测（否则不可复现）。

上面 4 条是原文件的组合，它们的差别在**控制流落在哪一段**；下面两条不改变组合结构、只替换前 4 条的**实现形态**，但同样决定运维代价：

- **单模型三表示（BGE-M3）+ RRF**：一个编码器同时产出稠密、稀疏与多向量，三路直接进 RRF。边界是：三路共享同一个模型的偏置，**错误相关性高于异构两路**（§7.3.1），所以它省的是运维成本，不是质量上限。运维代价是模型替换等于三路一起换（这既是它的优点也是它的风险）。
- **ES / OpenSearch 内置混合管线**：倒排索引与向量索引在同一个引擎里，融合由内置的排名融合完成。边界是：引擎同时负责两路，资源是共享的（向量查询与倒排查询互相影响）。运维代价最低，且**BM25 这一路几乎是白拿的**——这也是它成为起步形态的原因。

组合的原则只有一条：**每加一件，都要说清它负责哪一段边界，以及它挂掉时系统降级成什么。** 「稠密 + BM25 + 精排」里精排挂了，系统降级为混合检索（质量下降但可用），兜底是「关掉精排」这个开关；「混合检索 + 图」里图挂了，多跳问题全失效，兜底只能是「降级为单跳检索并明确告知用户」。**如果一个组件挂掉后的降级形态说不清楚，它就不该上线。**

**组合的边界否决线与收益递减**：如果两件东西的**正确性依赖互为对方输入**，就不能组合。例如「用精排结果去决定要不要重新检索」——重新检索的正确性依赖精排的稳定性，而精排的稳定性又依赖召回的完整性，这个环在任何一段抖动时都会变成「时好时坏、无法复现」的系统。组合可以分担负载、分担运维，**不能用来分担正确性**。至于收益递减：每加一件的收益来自它覆盖的那部分边界，成本来自它的运维单元数与版本对齐面；当一件东西覆盖的边界小于「缝合它所需的代码与流程量」时，它就是负收益——最典型的判据是：**如果你需要写一段代码来保证 A 和 B 的表示版本一致，那先问 A 和 B 能不能用同一个模型（例如三表示单模型）来合并这个一致性问题。**

### 7.7 选错的代价与迁移成本

**反模式：先买最强的 Reranker，再修召回** —— 症状：Recall@100 只有一半左右时，预算全花在精排模型上 → 后果：精排只能在已召回的集合里重排，**天花板被召回集锁死**；更糟的是精排把明显不相关的结果排下去了，让召回缺失更难被发现 → 正确的做法：先测并集上限（§7.5 第 1 层），修完召回再谈精排。

**反模式：不对齐分数就加权融合** —— 症状：写成 `w1 × BM25 分数 + w2 × 余弦相似度` → 后果：量级差异使稠密路的排序贡献被淹没，表现为「权重怎么调都像没调」；团队随后误判为「稠密没用」并把这一路砍掉 → 正确的做法：先打印两路分数分布，不可比就用 RRF 或 rank 归一化（§7.3.3）。

**反模式：为一个本质是「过滤」的需求上多路召回** —— 症状：用户真正的需求是「最新 + 某租户 + 某类目」，团队却在调融合权重与候选数 → 后果：召回指标看起来变好，业务指标不动，因为正确答案本来就在被过滤掉的那部分里 → 正确的做法：先把可过滤条件做成前过滤（机制讨论见 [Ch4-03 §7.3.4](../03-ai-native-db/03-ai-native-db-section-7-sec7.md)），再考虑多路。

**反模式：为全部语料建知识图谱** —— 症状：语料天天变，图永远在重建，而多跳问题只占一小部分 → 后果：抽取、实体对齐与摘要重算成为常驻开销，团队被流水线绑住 → 正确的做法：先标注问题集的多跳占比与语料日变更比例，只把「高价值 + 低更新」的那部分语料做成图。

| 从 → 到 | 索引重建 | 查询 / 管线改写 | 运维新建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 稠密单路 → 稠密 + BM25 + 融合 | 无（倒排通常已有，或新建一次） | 查询 API 加一路 + 融合参数 | 无（若复用同一引擎） | 融合与分路评估方法 | 低 |
| + 交叉编码器精排 | 无 | 管线加一段（只对 Top-K） | 精排服务与其限流 | K 与延迟的权衡 | 低–中 |
| 稠密+BM25 → 晚交互 | 全量重建 doc 侧 token 向量（最大项） | 换索引实现与打分函数 | 存储扩容（十几倍量级） | 压缩与召回调优 | 高（主要落在存储与重建窗口） |
| → 学习稀疏（SPLADE++ / 三表示模型） | 全量重建稀疏表示 | 换编码器与索引 | 无 | 稀疏模型的训练 / 调优与词表 | 中–高 |
| → KG / GraphRAG | 图构建：抽取 + 实体对齐 + 社区摘要（最大项） | 新增图检索路并接入融合 | 抽取流水线（分区 / 重跑 / 版本） | 抽取质量评估与对齐排错 | 极高 |
| → Agentic | 索引不变 | 检索由 Agent 决定（轨迹不可复现） | 轨迹观测与成本追踪 | 轨迹评估与回归测试设计 | 高 |

关于迁移时机有一条容易被忽略的约束：**检索方案的迁移必须先在离线标注集上完成可比性验证，再上线切流。** 因为检索质量没有硬性报错，「新方案更好」这件事只可能在固定问题集上被证明；而一旦上线后再发现问题，你会同时失去旧的基线与判断依据。可操作的做法是把迁移拆成「离线双跑（新旧两套对同一问题集出结果，人工比对差异）→ 小流量双跑（新旧同跑，看业务指标）→ 切流 → 保留旧路一个周期做回退」四段。

还有一条约束来自本节反复出现的机制：**任何一次「换了编码模型」的迁移，都会让历史评测数据作废。** 因为分数分布变了、召回集变了，旧的阈值、旧的 K、旧的融合参数全部要重调，旧的问题集标注也要重新确认「切分是否还切在同一位置」。所以工程上值得做的一件事是：**把「问题集 + 切分版本 + 编码模型版本 + 融合参数」当成一个整体打版本号**，迁移时只换整组，不做半换。半换（只换模型不换评测集）是这类项目里最常见、也最难察觉的质量回退来源。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 通用知识库、专有名词多 | 稠密 + BM25 + RRF（+ 精排） | 两路失败模式互补，融合收益来自错误不相关 |
| 语料几乎全是自然语言 | 稠密单路 + 精排 | BM25 无信号时等权融合引入噪声 |
| ID / 单号 / 错误码查询 | BM25 为主 | 精确 token 必须精确匹配，相似度会给出错误单号 |
| 召回不达标 | 先测并集上限，再决定加路还是换模型 | 融合不能创造候选集中不存在的文档 |
| 召回够、排序不够 | 交叉编码器精排，K 取 50–100 | 精排成本 ∝ K，K 的上限由延迟预算反推 |
| 存储紧、算力宽裕 | 交叉编码器精排 | 晚交互的存储是双塔十几倍，精排不占存储 |
| 语料每天大幅变更 | 稠密 + BM25 + 融合 | 每 token 向量与图边都要随文档重建 |
| 需要跨文档汇总 / 多跳 | 关系图 / 社区摘要（族 4） | 打分式检索对关系信息无表达力 |
| 高频在线、延迟敏感 | 不上交叉编码器精排 | 前向次数 ∝ K，高 QPS 下不可负担 |
| 低频高价值复杂查询 | Agentic（族 4） | 多轮决策的方差只在高价值查询上划得来 |

回到本章 6 条判据里权重最高的两条：**失败模式是否互补**决定了「要不要加路、加哪一路」，**交互深度**决定了「哪一段能买、哪一段买不起」。这两条回答完，剩下的融合算法、模型选型、K 的取值才有讨论价值——顺序反了，讨论就会永远停在「哪个模型在榜单上更靠前」。

与原文件最大的方法论差别是：原文件给的是**结论**（「向量 + BM25 + Reranker ★」），本章给的是**推导**（为什么 Reranker 买不回召回、为什么晚交互的代价在存储而不在查询、为什么 KG 的门槛是更新频率而不是规模）。结论会随版本与本组织的语料过时，推导不会。

> 本节小结：这些候选之间唯一真正起决定作用的差异是**「召回与排序是两个不可互相替代的阶段」**——融合只能抬高召回并集的上限，精排只能在已召回的集合里重排，所以任何投入都必须先修召回、再修排序。其余维度（融合算法、模型选型、晚交互还是交叉编码器）都是这条差异的下游结果，而且大多是**叠加**而非二选一。
