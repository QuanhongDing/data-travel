## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

原文件的决策表把设计讲成了「按场景选一个」：中文 RAG 选「向量 + BM25 + BGE-reranker」，多语言选 BGE-M3，高精度选 ColBERT，企业知识中台与多跳选 KG。这七行推荐本身没有错，但它们掩盖了一个更基本的事实——**这些候选大多不是互斥选项，而是检索管线上的不同段**（[§7.2](04-hybrid-search-section-7-sec7.md)）：「向量 + BM25」是召回层，「Reranker」是排序层，「KG」是控制流上的增强，「Late Interaction」既可以是召回也可以是排序。把它们排成一列逐格选，等于问「发动机和后视镜选哪个」——最后一定是都要，问题只是先装哪个、哪个在你的场景里根本不值。

真正决定选择的约束有四条。第一条是**答案能不能落在一处**：如果答案需要跨文档汇总或多跳才能拼出来，那么打分式检索在关系信息上没有表达力，加大 K 只是加噪声，必须换成关系图或 Agent（[§7.5](04-hybrid-search-section-7-sec7.md) 第 0 层）——这是能力边界，不是性能权衡，所以它排在所有阈值之前。

第二条是**两路的失败模式是否互补**。融合的收益完全来自错误的不相关：一路错在「词面不同、意思相同」，另一路错在「意思不同、词面相近」，两者的召回并集上限才高于任一单路。如果两路实际同源，融合收益趋近于零而成本照付（[§7.3.1](04-hybrid-search-section-7-sec7.md)）。

第三条是**预算花在哪一段**。精排的成本随候选数 K 线性增长、且无法预计算；晚交互的成本落在每篇文档的存储与重建上；KG 的成本落在语料加工流水线上。三条曲线随不同变量增长，因此「哪一段买得起」不取决于哪一段更准，而取决于你的 QPS、语料变更频率与存储预算。

第四条是**评估能不能分解**：出问题时能否定位到「哪一路漏的」。不可分解的方案无法调参，只能整体换掉，也无法做回归——这决定了你能不能把系统长期维护下去。

这四条的顺序不能颠倒。第一条是**能力边界**（不满足时任何后续投入都买不回来），第二条与第三条决定**收益与成本的结构**，第四条决定方案能不能长期调优。原文件的决策表是「场景特征 / 推荐模式 / 理由」三列、7 行推荐，只给推荐、不给判据；一旦把「召回能力」与「工程复杂度」并排放进同一张可加的表，两者的地位就会被抹平：召回是**上游约束**，它决定系统的天花板；复杂度是**下游成本**，它决定你维护得起什么（[§7.1](04-hybrid-search-section-7-sec7.md) 讨论的正是这类表为什么会误导）。

顺序颠倒的典型后果是「先买最强的精排，再修召回」：精排只能在已召回的集合里重排，天花板被召回集锁死；更糟的是精排把明显不相关的结果排下去了，让召回缺失更难被发现（[§7.7](04-hybrid-search-section-7-sec7.md)）。

还有一条不写进任何技术选型表的约束：**谁在维护它**。同一个混合检索栈，在有专门检索团队的组织里能持续调优，在由应用团队顺带维护的组织里三个月后就没有人再跑评测——而检索质量下降不会报错，只会表现为「答得不太对」。这也是 3.7 的清单把诊断项排在最前、并在结构项里单列出「关掉增强项后系统还能不能返回答案」这一条的原因。

上面四条是判据层面的约束；把同一个问题拆成可逐行核对的清单，就是下面六行——前四行决定候选集与可行性，后两行决定这件事做不做得下去。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 答案是否落在一处（单跳 / 多跳） | 要不要结构增强（族 4） | 「加大 K 就能回答汇总类问题」——打分式检索对关系无表达力 |
| 两路失败模式是否互补 | 要不要加路、加哪一路 | 「模型榜单分高就够了」——榜单与你的语料盲区无关 |
| 语料变更频率 | 晚交互与 KG 能不能用 | 「晚交互只是更准」——它的代价在每次文档变更时的重建 |
| QPS 与延迟预算 | 精排能不能上、K 取多少 | 「精排是纯收益」——前向次数 ∝ K，高 QPS 下买不起 |
| 存储预算 | 每篇存几个表示 | 「多路只是多一次查询」——每路都要一份索引与存储 |
| 评估的可分解性 | 方案能不能长期调优 | 「端到端指标好就行」——不可分解的方案只能整体换掉 |

读这张表要自上而下：第一行是**能力边界**（不满足时后面的讨论都无意义），第 2–4 行是**收益与成本的结构**（错误互补性、语料变更频率、QPS 与延迟预算），最后两行（存储预算与可分解性）决定方案能不能活过第一年。

### 3.2 模式逐个拆解（核心节）

原文件列出的 6 个模式在下面 6 个小节里逐条保留、未做删减。按「它挂在管线的哪一段」可以分成三组：**召回层**（3.2.1 双路、3.2.2 三路）、**排序与表示层**（3.2.3 单模型三表示、3.2.4 晚交互）、**控制流与执行形态**（3.2.5 Agentic、3.2.6 结构化 + 向量）。这里的分组只用于组织阅读，真正的判断标准是 [§7.2](04-hybrid-search-section-7-sec7.md) 的分族：**同族内部多为替代，跨族之间多为叠加**——先分清「替代」还是「叠加」，能避免一半的伪决策（「向量 + BM25」与「Reranker」不是二选一，而是管线上的两段）。

每个模式按六件事展开：被什么约束逼出来、结构、为什么这样设计有效、代价、失效点、真实使用，每条末尾再各附一条**核验方法**。**失效点最关键**：它回答「这个模式的优点在什么条件下反转成缺点」，而这一条在原始的模式清单里完全缺失。

原文件 6 个模式在本文的落点：向量 + BM25 双路 → §3.2.1；三路（+ KG）→ §3.2.2；BGE-M3 多功能 Embedding → §3.2.3；Late Interaction 精排 → §3.2.4；Agentic Hybrid Search → §3.2.5；结构化 + 向量融合 → §3.2.6。原决策表的 7 行推荐同样逐条保留：「向量 + BM25 + BGE-reranker」落在 §3.2.1 的精排环节，「实时性高 → 不加 Rerank」落在 §3.3 与 §3.6 的判据里，「多语言 / 跨境 → BGE-M3 多功能」落在 §3.2.3 的 Multi-Linguality，以及 §3.3、§3.8 的判据里。

#### 3.2.1 向量 + BM25 双路召回（最经典）

- **被什么约束逼出来**：单路召回的失败模式无法消除——BM25 漏同义改写与口语化提问，稠密向量漏稀有 token（型号、单号、错误码），而这两类错误恰好来自不同原因。
- **结构**：

```text
[Query] ─┬─▶ [向量召回 Top-Kv]  ─▶ 排名列表 R_vec
         └─▶ [BM25 召回 Top-Kb] ─▶ 排名列表 R_lex
                    │
         [RRF 融合]  score(d) = Σ_r 1 / (k + rank_r(d))，k 常取 60【公开】（Cormack 等，SIGIR 2009）
                    │
              [精排：Cross-Encoder / Late Interaction]
                    │
                 [Top-K 给 LLM]
  两路都可预计算（doc 侧离线建 ANN 索引与倒排索引），在线只做两次取数 + 一次合并
  → 融合只消费「排名」，两路分数量纲不必对齐
  RRF 的 k 控制「排名差异被放大的程度」：k 越小越倚重单路头部结果，
       k 越大越接近「多路都提到就加分」的投票
  要表达「更信某一路」应调整各路的取数数量，而不是改 k 或在公式里加权
```

- **为什么这样设计有效**：因为 RRF 只吃排名、不吃分数，所以「BM25 分数在实际语料上没有上界、余弦相似度挤在很窄的区间」这个量纲问题被彻底消掉，融合不需要归一化方法、不需要权重参数（[§7.3.3](04-hybrid-search-section-7-sec7.md)）。这是它成为 2023 年后企业级 RAG 事实基线的原因；其原始依据是 Cormack、Clarke、Buettcher 在 SIGIR 2009 提出的倒数排名融合，该论文即取 k = 60【公开】。
- **代价**：多一路就多一套「编码模型版本 + 索引版本 + 重建流程」的对应关系，任何一次模型升级都要跑两次重建与两次回归（[§7.4](04-hybrid-search-section-7-sec7.md)）；此外两路候选必须同源同版本，否则融合的是两个不同快照的排名（[§7.6](04-hybrid-search-section-7-sec7.md) 组合二）。
- **失效点**：当**两路实际同源**时（两路共用同一个查询改写结果，或稀疏侧由稠密模型蒸馏而来），「错误不相关所以并集上限更高」这个优点反转成「融合收益趋近零、成本照付」——因为融合的收益完全来自错误的不相关，同源意味着两路漏的是同一批文档。判据是并集 Recall@K 相对较优单路的提升幅度，落在标注噪声量级之内（几百条问题的标注集上大致 3–5 个百分点，【经验】）即按高度重合处理。
- **真实使用**：【经验】中大型电商与内容平台的搜索栈把召回做成可插拔的多路（字面 / 语义 / 标签 / 规则），在统一融合层合并，这类形态已持续 4 年量级（2020–2024）：[§6 案例 4.1](04-hybrid-search-section-6-sec6.md)（某电商的 ES + 向量双路 + RRF 融合）与 [§6 案例 4.3](04-hybrid-search-section-6-sec6.md)（字节的双引擎多路召回）各是一个样本。两处案例的出处均为区间式标注，不含可检索的标题与链接，因此本条按【经验】计；要落到具体组件时，请按案例中的组件名（ES / Milvus / RRF / 可插拔召回）与年份自行核验。
- **核验方法**：取同一问题集分别跑两路，比较它们的漏召回集合，并同时算出**并集 Recall@K 相对较优单路的提升幅度**——交并比用来解释原因，提升幅度才是决定加不加路的量。这一步的代价是一两天人工标注，是本主题里投入产出比最高的一次测量。

#### 3.2.2 向量 + BM25 + KG 三路召回

- **被什么约束逼出来**：有一类问题的答案不落在任何单篇文档里——跨文档对比、全局性归纳、多跳关系；而打分式检索在关系信息上没有表达力，加大 K 只是把噪声一起取回来。
- **结构**（沿用原文件的路径示意，补出建图与查询两阶段）：

```text
[Query] → [向量] + [BM25] + [KG 关系遍历 / 社区摘要] → [RRF] → [精排]
  建图（离线）：语料 ─▶ LLM 抽取实体与关系 ─▶ 实体对齐 ─▶ 社区摘要
  查询（在线）：实体链接 ─▶ 图上遍历 ─▶ 取回相连实体的描述与摘要
  → 三路里只有两路是「打分」，第三路是「遍历」：
    它们的成本随不同变量增长（打分区随 QPS，遍历区随语料变更）
  增量更新：每篇文档变更 → 重抽 + 重对齐（成本 ∝ 变更文档数，而不是索引插入量）
```

- **为什么这样设计有效**：因为建图依赖 LLM 抽取、且每篇文档变更后通常要重新对齐实体并更新社区摘要，所以它覆盖的正是「语义相似但关系上不相连」的盲区——向量与 BM25 都只能找到「像」的文档，找不到「关系上相连」的实体。微软 GraphRAG 于 2024 年开源，其公开材料把实体与关系抽取 + 社区摘要作为回答全局性问题的机制【公开】。
- **代价**：【推算】设语料 100 万篇、平均 500 token，一次全量抽取要处理约 5 亿 token 的输入，社区摘要还要在此基础上再跑一遍生成——这个量级的意义不在于绝对费用，而在于**建图必须被当成一条数据加工流水线来运维**（分区、重跑、版本、失败重试），而不是一个「建索引」步骤。
- **失效点**：当**语料每天大幅变更、而多跳问题只占少数**时，「兼顾语义 + 精确 + 关系」的优点反转成「图永远在重建、团队被流水线绑住」——因为每篇变更文档都要重抽与重对齐，成本随变更量线性增长，而收益只落在那部分多跳问题上。
- **真实使用**：【公开】微软 GraphRAG（2024 年）把「实体与关系抽取 + 社区摘要」作为回答全局性问题的构件，是这一模式可核验的公开实现；【经验】企业知识中台里更常见的做法是**只对「需要跨文档汇总或多跳」的那部分问题建图**，而不是为全部语料建图。判定方法很具体：在问题集上标注「需要跨文档汇总或多跳」的比例，并统计语料日变更比例；多跳占比 ≲ 10–20%（【经验】）或语料每天大幅变更时，先别建图——为少数问题把全部语料做成图，是把成本摊在了不需要它的那部分上。
- **核验方法**：查一次建图流水线的输入 token 量与最近一次全量重建的耗时，再看它有没有失败重试与版本；把这两个数与「多跳问题占比」放在一起读，就能判断它现在是在提供能力还是在消耗团队。

#### 3.2.3 BGE-M3 多功能 Embedding

- **被什么约束逼出来**：两条约束。其一是**运维面**——想上多路，但不愿维护多个编码模型与多套索引版本，多路召回的隐性成本恰恰在这里（[§7.4](04-hybrid-search-section-7-sec7.md)）。其二是**语料跨语言**——语料含中文 + 跨境多语种时，词法路要在每种语言上分别维护分词与词干化、质量参差不齐，而多语言编码器可以用同一套权重覆盖多种语言（[主文件 §2.2](04-hybrid-search.md) 记 BGE-M3 的 Multi-Linguality 支持 100+ 语言【公开】，BGE-M3 论文与模型卡，2024）。
- **结构**：

```text
BGE-M3：一个 checkpoint，三种表示
   doc ──▶ [同一个编码器] ─┬─ dense   向量        → ANN 索引
                          ├─ sparse  词项权重     → 倒排索引
                          └─ colbert 多向量       → MaxSim 打分
   query ─▶ [同一个编码器] ─┘ → 三路结果 → RRF → 精排
  → 升级一次 = 三路一起换：
    版本对齐问题从「三条对应关系」压缩成「一次升级 + 一次回归」
  → 同一套权重还覆盖 100+ 语言【公开】（BGE-M3 论文与模型卡，2024）：跨语言语料上不必为每种语言维护一套词法分析
  代价与收益同源：三路共享同一个模型的偏置 → 错误相关性高于异构两路
```

- **为什么这样设计有效**：因为三路共享同一个编码器，所以一次模型升级只需要一次全量重建、一次回归；对照异构两路的做法（重建两次、回归两次、再重新校准融合参数），它把**版本对齐成本**这一项从乘法变成了加法。BAAI 的 BGE-M3 论文（arXiv，2024）以「同一模型同时产出稠密、稀疏、多向量三种表示」为目标【公开】（可自行核验其论文与模型卡）；[主文件 §1.4](04-hybrid-search.md) 把它记为 2024 年的进展。
- **代价**：三路共享同一个模型的偏置，**错误相关性高于异构两路**（[§7.3.1](04-hybrid-search-section-7-sec7.md)），所以它省的是运维成本、不是质量上限；同时「模型替换等于三路一起换」这件事本身是双向的——它既是优点也是风险源。
- **失效点**：当**你的瓶颈是质量而不是运维**时（专有名词与型号召回仍然差、标注集上并集上限提不上去），「单模型、单库、一次升级」的优点反转成「三路一起退化」——因为三路的错误同源，调这个模型会把三路同时推向同一个方向，而真正缺的是一路**不共享偏置**的召回。另有第二条反转：当**语料以低资源语言为主**时，「一套模型覆盖 100+ 语言【公开】，BGE-M3 论文与模型卡 2024」反转成「每种语言都只是勉强够用」——因为多语言模型的参数预算被摊到了上百种语言上，单语能力不及该语言的专用单语模型（【经验】；判据是在你的目标语言上跑一份单语小模型做对照）。
- **真实使用**：主文件 §2.3 的向量模型表把 BGE-M3 列为「多功能（dense / sparse / colbert）」的代表，主文件 §2.2 另记它的 Multi-Linguality（100+ 语言【公开】，BGE-M3 论文与模型卡，2024）与 Multi-Granularity（短句 - 长文档）；[§7.2](04-hybrid-search-section-7-sec7.md) 把它归入「想上多路但不想维护多个模型」的选型位置。【经验】由此它对应两类落地场景：**中文 + 跨境多语言语料**（原决策表把它列为「多语言 / 跨境」的推荐），以及**小团队要一个人维护三路**。判断方法：看它能否在同一进程中同时输出三种表示且三路共用一次编码——只是「同时支持三种检索」而需要三个模型的，不属这个模式。
- **核验方法**：做一次模型替换演练，数一数要重建的索引数与要跑的回归轮数：一次与三次的差别，就是这一节的收益。

#### 3.2.4 Late Interaction 精排

- **被什么约束逼出来**：交叉编码器精度最高但无法预计算，成本 ∝ K；双塔能预计算但受单向量瓶颈限制。需要一种「精度高于双塔、又能在 doc 侧预计算」的中间形态。
- **结构**（沿用原文件路径示意）：

```text
[Query] → [Bi-Encoder 召回 Top-100] → [ColBERT 精排 Top-10] → [LLM]
  ColBERT 打分：MaxSim —— 每个 query token 取与之最相似的 doc token，再求和
      score(q, d) = Σ_{qt ∈ q} max_{dt ∈ d} <q_emb(qt), d_emb(dt)>
  doc 侧每 token 一个向量、可离线预计算 → 在线只做点积
  存储对照（每篇）：双塔 = 1 个向量（维度 D）；晚交互 = token 数个向量、每个「每 token 维度」维
      → 晚交互每篇存储量 ≈ 每篇 token 数 × 每 token 维度 × 单元素字节
  两个量必须分开说：
      存储放大倍数 = 晚交互每篇存储量 ÷ 双塔每篇存储量（只由 token 数与每 token 维度决定）
      写入放大绝对量 = 晚交互每篇存储量 × 语料日变更篇数（随每日变更量增长，与倍数无关）
      重建量的放大倍数与存储放大倍数相同 —— 因为它们乘的是同一份每篇存储量
```

- **为什么这样设计有效**：因为 doc 侧的 token 向量可以离线算好、在线只做 MaxSim 点积，所以它比交叉编码器便宜得多（可以在更大的候选集上跑），同时比双塔准。**它的代价落在存储侧而不是查询侧**：约束晚交互的不是准确率，而是存储与写入放大预算（[§7.3.2](04-hybrid-search-section-7-sec7.md)）。
- **代价**：【推算】设每篇文档平均 128 个 token（【经验】，中英混排技术文档的量级），晚交互每 token 128 维 fp16 = 256 B，则每篇约 32 KiB；双塔 1024 维 fp16 = 2 KiB，比值约 **16×**。ColBERTv2 论文报告通过残差压缩把存储降低 6–10 倍（【公开】ColBERTv2，NAACL 2022），把 16× 除以压缩倍数后仍约为双塔的 **1.6–2.7 倍**——压缩只把倍数从约 16 降到 2 上下，没降到 1。
- **失效点**：当**文档平均长度远大于假设的 128 token，或语料每天大幅变更**时，「精度高且可预计算」的优点反转成「重建成本高于收益」——因为存储放大倍数随 token 数线性增长，而每篇文档变更都要重建它的全部 token 向量，**重建量的放大倍数与存储放大倍数相同**（相对双塔都是那个比值），于是每日变更量把这个倍数直接换算成可观的绝对写入量。
- **真实使用**：【经验】它在「存储便宜、算力贵」的场景受欢迎，在「文档量大且更新频繁」的场景受限（[§7.2](04-hybrid-search-section-7-sec7.md)）；主文件 §2.4 把它与混合检索的关系界定为「晚交互是精排的一种，混合检索包含晚交互」。
- **核验方法**：算一次写入放大的绝对量——先把每篇存储量算出来（每篇 token 数 × 每 token 维度 × 单元素字节），再乘以语料日变更篇数，然后与存储预算及每日重建窗口对比；同时确认你的精排是否已经是延迟瓶颈，若交叉编码器没有成为瓶颈，晚交互的收益支撑不起一次全量重建。

#### 3.2.5 Agentic Hybrid Search

- **被什么约束逼出来**：查询形态跨度极大，固定管线的取数在难问题上不足、在易问题上过多，而系统无法事先区分两者。
- **结构**（沿用原文件路径示意，补出控制流）：

```text
[Query] → [Agent] → [决定查向量 / BM25 / KG / Web] → [调用] → [判断够不够]
                                       ┌───────────────────────┘
                                       ├─ 不够 → 改写查询 / 换一路 → 再检索
                                       └─ 够了 → 整合 → 作答
  与固定管线的差别：路数与顺序由「中间结果」决定，不由配置决定
  → 它是控制流的改变，不是又多了一路召回
  成本与延迟按「平均轮数 × QPS」线性增长，但方差大 → 容量必须按 P99 轮数准备
  必须为每次检索调用配限流与超时（一次失控的规划会打满检索集群）
```

- **为什么这样设计有效**：因为轮数与路径由中间结果决定，所以它能在难问题上多花算力、在易问题上少花，而固定管线只能取一个折中值。这解释了它为什么只适合低频高价值的查询（复杂分析、跨源调查）。
- **代价**：成本与延迟的**方差**远大于固定管线——同一问题在不同时间可能走 2 轮也可能走 8 轮，容量规划必须按 P99 轮数做而不是按均值；并且「同一问题的检索轨迹不唯一」使离线评估不可复现，回归测试需要比固定管线更大的样本量才有统计意义（[§7.3.4](04-hybrid-search-section-7-sec7.md)）。
- **失效点**：当**把高频在线 QPS 交给它**时，「灵活」的优点反转成「不可预测」——因为方差乘以 QPS 之后，成本与容量都要按最坏情况准备，而长尾轨迹会打满下游检索集群。这正是 [§7.6](04-hybrid-search-section-7-sec7.md) 要求「每次调用必须有限流与超时」的原因：Agent 不修改索引、只组合调用，一次失控的规划会打满整条链路。
- **真实使用**：【经验】低频高价值的复杂查询入口；[主文件 §1.4](04-hybrid-search.md) 把 Agentic Hybrid Search 记为 2024 年的方向，[§7.2](04-hybrid-search-section-7-sec7.md) 把它归入「检索策略由 Agent 决定」这一族。
- **核验方法**：取一批真实问题跑一遍，统计**轮数的 P99 与均值之比**；比值大（分布长尾）时只把它挂在低频入口上，不放进高频在线路径。

#### 3.2.6 结构化 + 向量融合（PostgreSQL + pgvector）

- **被什么约束逼出来**：答案本来就落在一个可过滤的子集里（租户、类目、时间、库存），这些条件必须精确满足；而语料规模还没大到需要独立向量库的程度。
- **结构**：

```sql
-- 结构化条件与向量距离在同一条 SQL 里表达（先过滤、再近邻）
SELECT id, title, embedding <=> $1 AS dist
FROM   products
WHERE  category = 'phone'
  AND  in_stock = true
  AND  updated_at >= now() - interval '30 days'
ORDER BY embedding <=> $1
LIMIT  10;
-- 关键：过滤发生在近邻搜索「之前」还是「之后」，
-- 决定了召回是否被静默截断 —— 必须用 EXPLAIN 与实测召回确认
-- 对照测法：同一条查询跑「带过滤」与「不带过滤」两个版本，比返回条数与命中
-- 若必须先缩小范围再近邻，说明过滤条件需要重设计成与索引匹配的前过滤
```

- **为什么这样设计有效**：因为过滤条件与向量距离在同一个查询计划里表达，所以不必在应用层拼两次请求、也不必先把范围缩小再近似搜索；它把「结构化过滤」与「语义相似」的取舍收敛成一次查询计划的选择——这也是它在中小规模 AI 应用里成为默认形态的原因：在语料还没大到需要独立向量库之前，多引入一套系统换来的是两套数据的一致性问题，而不是检索能力。
- **代价**：过滤与近似搜索共存会互相拖累。向量索引扫描通常先取 Top-K、再套过滤条件，此时满足条件的候选可能凑不满 K 个，表现为**召回静默变少**（而不是报错）；要弄清实际行为，只能看执行计划与在标注集上实测的召回，不能靠推理。选择性高时过滤后命中率低，选择性低时过滤条件退化成一个常数条件。
- **失效点**：当**向量规模与 QPS 超过单库可承担的量级**时，「一个库、一条 SQL、事务与检索共享一致性」的优点反转成「两类负载互相挤占」——过滤查询、事务写入与 ANN 扫描共用同一份缓冲与同一批 CPU，向量检索的延迟尖峰会影响在线写入；拆成「专用向量库 + 结构化库」能解决挤占，但会立刻引入两套系统的一致性问题（两路数据必须同源同版本，[§7.6](04-hybrid-search-section-7-sec7.md) 组合的边界要求）。
- **真实使用**：【经验】中小规模 AI 应用、原型与内部系统；原文件把它列为「中小规模 AI 应用」的推荐模式，并指向 [03-ai-native-db](../03-ai-native-db/03-ai-native-db.md)。
- **核验方法**：对同一条查询分别跑「带过滤」与「不带过滤」两个版本，比较返回条数与命中情况；再用 EXPLAIN 确认过滤是在索引扫描之后还是之前生效。**两条命令就能回答「我的过滤有没有把召回截断」这个最容易被忽略的问题。**

把 6 个模式的「换来的性质」与「性质反转的条件」并排放一次，失效点这一维就清楚了：

| 模式 | 它换来的性质 | 性质在什么条件下反转 |
| --- | --- | --- |
| 向量 + BM25 + RRF | 两路错误不相关 → 并集上限高于任一单路 | 两路同源时，融合收益趋近零而成本照付 |
| + KG 三路 | 覆盖关系与多跳，补上打分式检索的盲区 | 语料高频变更且多跳占比低时，图永远在重建 |
| BGE-M3 三表示 | 一次升级对齐三路版本，运维成本从乘法变加法 | 瓶颈是质量而非运维时，三路一起退化 |
| Late Interaction | doc 侧可预计算 → 比交叉编码器便宜得多 | 文档变长或语料高频变更时，写入放大吃掉收益 |
| Agentic | 按问题难度分配算力，难问题多花、易问题少花 | 放进高频在线路径时，方差乘以 QPS |
| 结构化 + 向量 | 一条 SQL 表达过滤与近邻，无应用层拼装 | 规模与 QPS 超过单库时，两类负载互相挤占 |

这张表要反向读：先在自己的环境里找**哪个反转条件已经成立**，再回头看这个模式是否仍然合适。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 通用企业知识库、专有名词多 | 向量 + BM25 + RRF（+ 精排） | 单路稠密在型号与专有名词上漏召回，且失败不报错 | 两路漏召回是否高度重合（提升幅度是否超出标注噪声） |
| 语料几乎全是自然语言 | 稠密单路 + 精排 | BM25 在此语料上近无信号，等权融合把噪声引进来 | 打印 BM25 在你的语料上的分数分布 |
| ID / 单号 / 错误码查询 | BM25 为主 + 稠密补充 | 相似度会给出「长得像」的错误单号 | 查询里精确 token 的占比 |
| 需要跨文档汇总 / 多跳 | 关系图 / 社区摘要（KG 路） | 更大的 K + 更强的生成模型救不回来 | 多跳问题占比与语料日变更比例 |
| 存储预算紧、算力相对充裕 | 交叉编码器精排 | 晚交互的每篇存储是双塔的十几倍（未压缩 16×，压缩后约 2 倍） | 写入放大是否落在预算内 |
| 延迟预算买不起 K × 单对推理 | 晚交互或蒸馏小模型 | 交叉编码器成本 ∝ K 且无法预计算 | QPS × K 是否超过单机可承担量级 |
| 高频在线、延迟敏感 | 向量 + BM25（不上精排） | 精排属于与 QPS 相乘的项 | 关掉精排后系统能否降级可用 |
| 中小规模、要一个人维护 | PostgreSQL + pgvector | 独立向量库要重建一致性对齐 | 过滤是否把召回静默截断（跑两次对比） |
| 不想维护多个模型 | BGE-M3 单模型三表示 + RRF | 三个模型意味着三次重建与三次回归 | 一次升级要重建几套索引 |
| 语料跨语言（中文 + 跨境多语种） | BGE-M3 三表示（Multi-Linguality）+ RRF | 词法路要为每种语言单独维护分词与词干化，单语模型无法跨语料复用 | 语料里有几种语言、是否愿意分语言维护词法分析 |
| 复杂业务问题、低 QPS | Agentic Hybrid Search | 固定管线在难问题上取数不足 | 轮数 P99 与均值之比是否长尾 |
| 召回够、排序不够 | Cross-Encoder 精排（K 取 50–100，【经验】） | 换更大的嵌入模型——召回没坏，换模型解决不了排序 | Recall 高而 nDCG 低 |
| 语料每天大幅变更 | 稠密 + BM25 + 融合 | 晚交互与 KG 都要随文档重建 | 每篇变更触发多少重建量 |

本主题下最常被误选的一对是**「单一稠密向量」与「稠密 + BM25 融合」**，而误选的依据通常是「我们的嵌入模型在公开榜单上分很高」。榜单分数与你的语料盲区无关：融合的收益只来自两路错误的**不相关**，而这个量只能在你的问题集上测出来（[§7.3.1](04-hybrid-search-section-7-sec7.md)）。误选的后果不是系统不工作，而是系统**看起来在工作**——召回缺失不会报错，只会表现为「答得不对」，而且会被精排掩盖得更深。正确的第一步不是选模型，而是取几百条真实问题，量一次并集上限。

### 3.4 组合模式：真实系统不会只用一种

**组合一：混合检索 + RAG**。混合检索是 RAG 的**召回层**，只负责「把正确的证据放进候选池」；RAG 负责编排、生成与引用。职责边界很清楚：召回层不判断「够不够回答」，那是生成层或 Agent 的事。运维代价最低，但要盯住召回质量与生成质量两个独立指标的分解——否则会把生成的问题误判成召回的问题（[§7.6](04-hybrid-search-section-7-sec7.md)）。适合全部规模的 RAG，也是 [§6 案例 4.1](04-hybrid-search-section-6-sec6.md) 起步时的形态。

**组合二：混合检索 + 向量湖**（见 [02-vector-lake](../02-vector-lake/02-vector-lake.md)）。向量路走向量湖承载十亿级向量（【经验】量级，与 Ch4-02 的「十亿级向量」表述一致），BM25 路留在搜索引擎上。职责边界是「两路各管一种匹配方式，语料同源」。运维代价是**两条摄入管线必须保证同版本**——否则融合的是两个不同快照的排名，这是这套组合最容易出错、也最难发现的地方。适合语料规模已超出单引擎舒适区、且更新可控的组织。

**组合三：混合检索 + GraphRAG 或 Agent（控制流增强）**。向量与 BM25 负责「找到相关段落」，图负责「找到关系上相连但语义不相似的实体」，Agent 负责「决定这一次该调哪一路、调几次」。职责边界是：图不承担相似度排序，向量不承担多跳，Agent 不修改索引、只组合调用。运维代价是图需要更新流水线（抽取 + 对齐 + 摘要）、Agent 需要轨迹可观测与逐次限流（否则不可复现、一次失控的规划会打满检索集群）。适合多跳占比可观、且查询频次低而价值高的语料。

三条组合有一个共同要求：**每个组件挂掉时系统降级成什么，必须能一句话说清。** 「稠密 + BM25 + 精排」里精排挂了降级为融合结果（质量下降但可用）；「混合检索 + 图」里图挂了的多跳问题全失效，兜底只能是「降级为单跳检索并明确告知」。**说不清降级形态的组件，不该进这个组合**——这条判据比任何性能指标都更能筛掉伪需求。

组合还有一条否决线：**如果两件东西的正确性互为对方的输入，就不能组合。** 例如「用精排结果去决定要不要重新检索」——重新检索的正确性依赖精排的稳定性，而精排的稳定性又依赖召回的完整性，这个环在任何一段抖动时都会变成「时好时坏、无法复现」的系统。组合能分担负载、能分担运维，**唯独分担不了正确性**。

### 3.5 反模式与失效分析

下表 10 条对应原文件的 10 条反模式（其中「无 Query 理解」与「忽视 HyDE / Query Rewrite」说的是同一件事，这里保留两行以便逐条对照）。四列回答四个不同的问题：**怎么发现它、它按什么机制造成损失、团队为什么会写成这样、改什么。**

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 单一向量检索 | 型号、单号、错误码类查询命中率明显偏低，且失败不报错 | 词面不同与稀有 token 两类盲区无人覆盖，召回天花板被锁死 | 起步时只上了一种索引，加路需要动查询链路 | 加 BM25 路 + RRF（融合只消费排名，无需归一化） |
| 无 Reranker | 融合后的 Top-10 里明显不相关的结果混在前面 | 粗排顺序直接影响喂给 LLM 的证据质量，噪声随 K 增大 | 精排是一次额外的在线成本，先省掉 | 加 Cross-Encoder 精排，只对 Top-50~100 做 |
| 加权融合不标准化 | 权重怎么调都像没调，稠密路的贡献被淹没 | BM25 分数无上界而余弦相似度挤在窄区间，未归一化的加权和等于「BM25 分数 + 近似常量」 | 直觉上「两路各有重要性，加权最自然」 | 改用 RRF 或 rank 归一化，先打印两路分数分布 |
| 盲目调权重 | 每次调参都在同一批样例上「感觉好了一点」 | 没有固定评测集时，调参把噪声当收益，且无法回归 | 缺少标注集，只能用样例试 | 建固定问题集 + 冻结 K 与切分版本，再谈权重 |
| 无元数据过滤 | 检索到过期、越权、跨部门的内容 | 过滤缺失时正确答案本就在被过滤掉的那部分里，加路与调融合都无效 | 把检索当纯语义问题，忽略权限与时效是硬条件 | 做前过滤（元数据-aware），先缩小范围再近邻 |
| 过度精排 | 端到端延迟由精排阶段决定，K 被越调越大 | 前向次数 ∝ K，K 从 100 提到 500 即约 5× 计算量 | 用增大 K 来补救召回不足 | 提高召回质量让正确答案更靠前，而不是加大 K |
| 无 Query 理解 | 口语化、指代型问题检索失败，改写后同一问题却能命中 | 查询与语料的表示不在同一分布上，召回损失与路数无关 | 把检索当成「一模一样的字符串匹配」问题 | 加 Query Rewrite / 意图识别 |
| 忽视 HyDE / Query Rewrite | 短查询、抽象提问的召回明显低于长查询 | 短查询的语义信号不足，稠密与稀疏两路同时受损 | 与上一条同源，多数团队在检索链路之外解决 | 用 HyDE / Query Rewrite / Step-Back 抬高并集上限 |
| 无融合评测 | 无法回答「融合到底有没有比单路更好」 | 融合的收益只来自错误不相关，不评测等于不知道融合是否在重复劳动 | 评测集建设成本高，且检索失败不报错 | 建标注集，看并集 Recall@K / MRR / nDCG |
| 忽视成本 | 精排与 Agent 的费用随 QPS 增长，账单先于指标报警 | 精排成本 ∝ QPS × K，晚交互与 KG 的成本落在语料加工上 | 只在离线指标上看效果 | 缓存 + 路由 + 抽样开精排，把降级形态写进设计 |

三个最危险的反模式值得单独说。**「加权融合不标准化」危险在它是渐进的**：系统能跑，只是稠密这一路的排序贡献被一个近似常量淹没，团队随后会得出「稠密没用」的结论并把这一路砍掉——而真正的原因是融合坐标系选错，不是路没用。判定方法只有一条：分别打印两路在 100 条真实查询上的分数分布，比量级与方差。

**「无 Reranker」与「过度精排」是一对镜像反模式**，都源于对精排成本结构的误解：前者省掉了唯一能重排证据顺序的环节，后者用增大 K 来补救召回不足——而前者的问题补不回来，后者的问题用 K 补不上，因为**召回与排序是两个不可互相替代的阶段**（融合不能创造候选集里不存在的文档，精排只能在已召回的集合里重排）。所以投入顺序必须先修召回、再修排序。

**「无元数据过滤」危险在它伪装成召回问题**：用户真正的需求是「最新 + 某租户 + 某类目」，团队却在调融合权重与候选数；召回指标看起来变好，业务指标不动，因为正确答案本来就在被过滤掉的那部分里。修法是先把可过滤条件做成前过滤，再考虑多路。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 稠密单路 → 两路融合 | 单一稠密向量 | 专有名词与型号类查询的天花板暴露 | 稠密 + BM25 + RRF | 查询 API 加一路 + 融合参数（倒排通常已在引擎里，代价低） |
| 两路 → 加精排 | 稠密 + BM25 + RRF | 召回够、排序不够（Recall 高而 nDCG 低） | 加 Cross-Encoder 精排 | 新增精排服务与限流；K 与延迟的权衡 |
| 精排 → 晚交互 | Cross-Encoder 精排 | 延迟预算买不起 QPS × K 的前向次数 | Late Interaction（doc 侧预计算） | 全量重建 doc 侧 token 向量，存储放大十几倍量级 |
| BM25 → 学习稀疏 | 两路融合 | 词面匹配在改写类查询上持续漏召回 | 学习稀疏（SPLADE++）或三表示单模型 | 全量重建稀疏表示，换编码器与索引 |
| 两路 → 加 KG | 稠密 + BM25 + 融合 | 多跳与汇总类问题开始占可观比例 | 关系图 / 社区摘要（族 4） | 抽取 + 实体对齐 + 社区摘要流水线（最大项） |
| 固定管线 → Agentic | 固定多路管线 | 查询形态发散，固定取数在两端都不合适 | Agentic（低频入口） | 轨迹观测与成本追踪；回归测试样本量扩大 |
| 单库 → 双引擎 | PostgreSQL + pgvector | 事务写入、过滤查询与ANN扫描互相挤占，延迟尖峰影响在线写入 | 专用向量库 + 结构化库 | 两路数据必须同源同版本，一致性对齐成为常驻工作 |
| 全量精排 → 抽样精排 | 全量精排 | QPS × K 的前向次数超过单机可承担量级 | 只对头部流量开精排（例如 10%） | 需要两套结果的对比与灰度，评测口径要能分解 |

跃迁表里有一条贯穿全部行的约束：**任何一次「换了编码模型」的迁移都会让历史评测数据作废。** 分数分布变了、召回集变了，旧的阈值、旧的 K、旧的融合参数全部要重调，旧的问题集标注还要重新确认「切分是否还切在同一位置」。所以工程上的做法是把「问题集 + 切分版本 + 编码模型版本 + 融合参数」作为一个整体统一打版本号，迁移时整组替换；只换模型、不换评测集这种半换，是这类项目里最常见、也最难察觉的质量回退来源（[§7.7](04-hybrid-search-section-7-sec7.md)）。

还有一条与模型无关的迁移约束：**迁移必须先在离线标注集上完成可比性验证，再上线切流。** 因为检索质量没有硬性报错，「新方案更好」这件事只可能在固定问题集上被证明；一旦上线后再发现问题，你会同时失去旧的基线与判断依据。可操作的做法是把迁移拆成四段：先在离线问题集上新旧双跑并人工比对差异，再小流量双跑看业务指标，然后切流，最后保留旧路一个周期做回退。

### 3.7 自检清单

- [ ] 我有没有量过**两路并集的 Recall@K 上限**？如果这个上限都不达标，加路与调融合都无效。
- [ ] 标注的粒度与切分粒度是否一致？（切分变了，按 chunk 标的评测集就作废）
- [ ] K 是否固定并在比较时同时报告了并集上限？（两路的候选池是并集，单路指标不可直接比）
- [ ] 漏召回样本是否分过类？若「答案跨 chunk 未拼上」「切分把答案切断」占多数，该修的是切分策略而不是加路。
- [ ] 两路的分数分布有没有打印出来对比量级与方差？不可比时是否已改用 RRF 或 rank 归一化？
- [ ] 精排的 K 是由延迟预算反推的，还是为了补救召回不足而被一路调大？
- [ ] 关掉精排、关掉 KG 路、关掉 Agent 之后，系统还能不能返回答案？能返回的是增强项，不能返回的是路径项。
- [ ] 两条摄入管线（例如向量湖与搜索引擎）是否保证语料同版本？
- [ ] 多跳/汇总类问题的占比是多少？在 10–20%（【经验】）以下时，是否真的需要建图？
- [ ] 上手 Agentic 之前，是否已经统计过轮数的 P99 与均值之比，并配了限流与超时？
- [ ] 用结构化过滤 + 向量检索时，过滤是前过滤还是后过滤？有没有跑过「带过滤 / 不带过滤」的对照？
- [ ] 精排与 Agent 的成本是否随 QPS 增长到需要缓存、路由或抽样开关？

这 12 条里，第 1–4 条是**诊断项**（先看清问题在哪一段），第 5–7 条是**结构项**（决定方案的形状与降级形态），第 8–12 条是**运维项**（决定它能不能长期活下去）。诊断项的性价比最高：它们大多只需要一两天标注，却能一次性回答「该加路还是该换模型」。

最容易被跳过的是第 1 条与第 7 条：前者决定后面所有投入的方向（并集上限不达标时，加路与调融合都是白花钱），后者决定部分组件故障时系统是否还能提供服务。

### 3.8 小结

把本节所有结论压成一句：**召回与排序是两个不可互相替代的阶段——融合只能抬高召回并集的上限，精排只能在已召回的集合里重排，所以任何投入都必须先修召回、再修排序。**

本节 6 个模式之间没有「谁更先进」，只有「谁对应你现在的约束」：当答案回到「就在一篇文档里」时，KG 与 Agent 立刻变成过度设计；当语料从「稳定、低频查询」变成「每天变更、高频查询」时，晚交互与 KG 立刻从收益变成负担。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 通用知识库、专有名词多 | 稠密 + BM25 + RRF（+ 精排） | 两路失败模式互补，融合收益来自错误不相关 |
| 语料几乎全是自然语言 | 稠密单路 + 精排 | BM25 无信号时，等权融合把弱路噪声引进来 |
| ID / 单号 / 错误码查询 | BM25 为主 + 稠密补充 | 精确 token 必须精确匹配，相似度会给出错误单号 |
| 召回不达标 | 先测并集上限，再决定加路还是换模型 | 融合不能创造候选集中不存在的文档 |
| 召回够、排序不够 | Cross-Encoder 精排，K 取 50–100（【经验】） | 精排成本 ∝ K，K 的上限由延迟预算反推 |
| 存储紧、算力宽裕 | Cross-Encoder 精排 | 晚交互的存储是双塔的十几倍（未压缩 16×，压缩后约 2 倍） |
| 不想维护多个模型 | BGE-M3 三表示 + RRF | 三路共享一次编码，版本对齐成本从乘法变加法 |
| 语料跨语言（中文 + 跨境） | BGE-M3 三表示 + RRF | 一套权重覆盖 100+ 语言【公开】，省掉分语言维护的词法分析 |
| 需要跨文档汇总 / 多跳 | 关系图 / 社区摘要（KG 路） | 打分式检索对关系信息没有表达力 |
| 高频在线、延迟敏感 | 不上交叉编码器精排 | 前向次数 ∝ K，与 QPS 相乘 |
| 中小规模、结构条件刚性 | PostgreSQL + pgvector 前过滤 | 一条 SQL 表达过滤 + 近邻，但必须确认过滤没截断召回 |
| 低频高价值复杂查询 | Agentic Hybrid Search | 多轮决策的方差只在高价值查询上划得来 |

> 本节小结：本节 6 个模式之间，**真正决定选择的那一条约束是「答案是否落在一处」**——它划出了能力边界，边界之外的模式（KG、Agent）不是更好的选择，而是另一种能力。边界之内，二次筛选由两件事决定：**两路的失败模式是否互补**（决定要不要加路、加哪一路），以及**预算买得起管线的哪一段**（精排的成本 ∝ K、晚交互的成本在存储、KG 的成本在语料加工）。融合算法与 K 的取值是这条链条的下游结果，顺序反了，讨论就会永远停在「哪个模型在榜单上更靠前」。
