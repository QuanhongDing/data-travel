## 6. 落地实践

### 4.1 某电商"**ES + 向量双路召回与 RRF 融合 4+ 年**"（2020-2024）

**背景（Why）**

该电商 2020 年面临**"单一路召回都有明显盲区"**：
- **纯字面（BM25）的盲区**——**用户搜"能折叠的行李箱"，商品写的是"可压缩收纳箱"，字面对不上但语义一致**
- **纯向量的盲区**——**用户搜具体型号"X1000 Pro"，向量检索会把一堆相似型号召回，精确型号反而排在后面**
- **两路分数不可比**——**BM25 分数与余弦相似度量纲完全不同，直接加权需要不断调参且不稳定**
- **多模态需求**——**以图搜图、以文搜图与文本搜索并存**

**触发点（What）**

2020 年该电商推进**双路召回 + 排名融合 + 重排序**（[案例 2020-2024]），目标：
- **字面与语义互补**——覆盖两类盲区
- **融合方法稳定**——不依赖反复调权重
- **毫秒级**——检索链路可在线使用

**详细做法（How）**

该电商混合检索的**5 大核心组件**：

1. **双路召回 + RRF 融合（核心创新）**
   - 关键设计：**字面路径（BM25）与语义路径（向量近邻）各自独立召回排名列表，再用 RRF（倒数排名融合）合并**；RRF 只用"排名"不用"分数"
   - 关键能力：**免去两路分数量纲对齐的调参**——这是融合能稳定长期运行的关键；同时两路互补，一路漏掉的另一路可能召回
   - 关键数字：**召回率 90%+、融合稳定无需反复调权重**
   - 关键示意：
     ```text
     双路召回 + 排名融合（RRF 只看名次，不看分数）
       查询 q ─┬─▶ BM25（字面）  ─▶ 排名列表 R_lex
               └─▶ ANN（语义）   ─▶ 排名列表 R_vec
                                  │
         RRF：score(d) = Σ_i 1 / (k + rank_i(d))     k 常取 60
                                  │
                  融合后 Top-N ─▶ 重排序模型（交叉编码器）─▶ 最终结果
     ────────────────────────────────────────────────
     为什么用 RRF 而不是"加权求和"
       加权求和：BM25 分数 0~30、相似度 0~1，量纲不同
                 → 权重需要按数据分布反复调，换数据就要重调
       RRF      ：只依赖"排在第几"，量纲问题不存在
                 → 参数少、跨数据集更稳，是工程上更可靠的选择
     -- 关键：融合层要"对量纲不敏感"，否则会变成长期调参负担
     ```

2. **重排序（交叉编码器）（核心）**
   - 关键设计：**融合后的 Top-N 交给交叉编码器精排**，模型同时看查询与候选，判断相关性
   - 关键能力：**双路召回负责"别漏"，重排负责"排对"**——两阶段分工明确
   - 关键数字：**精排后 Top-10 命中显著提升、P99 < 200ms**

3. **多模态统一召回（核心）**
   - 关键设计：**文本与图片经各自编码映射到同一向量空间**，两条召回路径都支持多模态输入
   - 关键能力：**以文搜图、以图搜图共用同一套融合与重排链路**
   - 关键性质：**多模态统一链路**

4. **检索质量的分层评测（核心）**
   - 关键设计：**分阶段评测**——先看"目标条目是否被召回"（召回率），再看"是否排进前 N"（排序质量），最后看端到端点击
   - 关键能力：**"效果不好"能被拆解为"是召回漏了还是排序错了"**，避免盲目调参
   - 关键性质：**分阶段指标可定位问题**

5. **以"业务约束"参与召回（核心创新）**
   - 关键设计：**类目、库存状态、门店等硬性条件在召回阶段参与**，而不是在最终结果上剔除
   - 关键能力：**避免"先召回再剔除导致结果只剩几条"**——这是检索质量最容易被忽视的损失点
   - 关键性质：**硬条件参与召回、结果数量稳定**

**该电商混合检索关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **召回方式** | 单路（字面或向量） | 双路召回 + 融合 | **盲区互补** |
| **融合权重调参** | 需反复调 | RRF 只看排名 | **调参负担消除** |
| **召回率** | 70% 量级 | 90%+ | **+28%** |
| **排序质量** | 依赖单路分数 | 交叉编码器精排 | **显著提升** |
| **端到端 P99** | — | < 200ms | **在线可用** |
| **模态支持** | 文本 | 文本 / 图片统一链路 | **多模态** |
| **硬条件（类目 / 库存）** | 结果后剔除 | 参与召回 | **结果数量稳定** |
| **效果定位** | 只能看端到端 | 分层指标可拆解 | **可定位** |

**具体数字（How much）**

- 团队规模：该电商搜索团队 30+ 人
- 关键数字：**召回 90%+**；**P99 < 200ms**；**RRF 免调权**；**多模态统一**
- 业务影响：覆盖该电商的全部商品搜索与以图搜图场景

**失败教训**

- 早期「**只用字面或只用向量**」——型号类查询与描述类查询总有一类效果差，倒逼**「双路召回互补」**
- 「**直接把两路分数加权求和**」——量纲不同导致权重需按数据反复调，倒逼**「RRF 融合，只依赖排名」**
- 「**只在召回后剔除不符合条件的商品**」——结果被剔到只剩几条，倒逼**「业务硬条件参与召回阶段」**
- 「**只能看端到端效果**」——效果差时无法判断是召回漏了还是排序错了，倒逼**「分层评测：召回率 / 排序质量 / 端到端分开看」**

### 4.2 某 SaaS"**托管检索栈的混合方案：把 embedding 与检索都交给托管服务 4+ 年**"（2020-2024）

**背景（Why）**

该 SaaS 2020 年面临**"自建检索栈的运维成本超过收益"**：
- **团队规模小**——**没有专门的人维护检索集群、embedding 服务与索引重建**
- **多业务共用一套检索**——**各业务检索需求不同，自建难以兼顾**
- **数据在托管云服务里**——**再用一套自研检索，等于在云环境里再造一个孤岛**
- **模型更新快**——**embedding 模型迭代频繁，自建难以跟上**

**触发点（What）**

2020 年该 SaaS 推进**基于托管服务的混合检索（托管搜索引擎 + 托管向量化服务）**（[案例 2020-2024]），目标：
- **免运维**——检索与向量化都由托管服务提供
- **混合召回**——字面与语义同时可用
- **多业务共用**

**详细做法（How）**

该 SaaS 托管检索栈的**5 大核心组件**：

1. **"托管搜索引擎 + 托管向量化"的组合（核心创新）**
   - 关键设计：**搜索与检索由托管服务承担，embedding 由托管模型服务产出**；自有代码只负责融合策略与业务逻辑
   - 关键能力：**把"索引运维 + 模型部署"这两块最重的活外包**，小团队把精力放在业务效果上
   - 关键数字：**运维人力 -80%+、接入天级**
   - 关键示意：
     ```text
     托管检索栈的职责切分
       自有代码（薄）     业务逻辑 / 融合策略 / 重排调用 / 结果后处理
     ────────────────────────────────────────────────
       托管服务（厚）     搜索引擎：索引 / 分片 / 副本 / 扩缩
                         向量化服务：模型托管 / 版本管理 / 批量与在线推理
     ────────────────────────────────────────────────
     判断准则：
       与业务差异化强相关 → 自有（融合策略、评测、业务过滤）
       通用基础设施能力   → 托管（索引运维、模型部署）
     -- 关键：小团队最容易犯的错是"把通用基础设施也自建一遍"
     --       结果是把有限人力消耗在运维上，业务效果反而没人做
     ```

2. **混合召回与融合（核心）**
   - 关键设计：**字面召回由搜索引擎完成，语义召回由向量检索完成，两路在自有代码层融合**
   - 关键能力：**融合策略掌握在自己手里**（这是业务差异化），而底层能力托管
   - 关键性质：**两路召回可组合**

3. **模型版本与索引重建的托管（核心）**
   - 关键设计：**embedding 模型版本由服务侧管理**，换模型时按其重嵌入与重建流程切换
   - 关键能力：**模型迭代不必自建一套重嵌入流水线**
   - 关键性质：**重嵌入流程托管**

4. **多业务命名空间与配额（核心）**
   - 关键设计：**按业务划分命名空间**，各自配额，互不影响
   - 关键能力：**多业务共用一套托管检索**，而不必每业务各买一套
   - 关键性质：**多业务共用、互不影响**

5. **效果评测与融合参数自有（核心创新）**
   - 关键设计：**维护业务自己的评测集**，融合参数与重排策略按评测结果调整
   - 关键能力：**"效果好不好"由自己可度量**——托管不等于放弃对效果的掌控
   - 关键性质：**评测集自有、参数可迭代**

**该 SaaS 托管检索栈关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **检索栈运维** | 自建集群与索引运维 | 托管服务承担 | **-80%+ 人力** |
| **embedding 服务** | 自行部署与保活 | 托管模型服务 | **免部署** |
| **接入周期** | 周~月级 | 天级 | **-70%+** |
| **模型迭代** | 自建重嵌入流水线 | 按托管流程切换 | **成本大幅下降** |
| **召回方式** | 单路 | 字面 + 语义双路 | **盲区互补** |
| **融合策略归属** | — | 自有代码（差异化） | **可控** |
| **多业务** | 各自搭建 | 命名空间隔离共用 | **∞** |
| **效果评测** | 无 | 自有评测集 | **可迭代** |

**具体数字（How much）**

- 团队规模：该 SaaS 团队 10-20 人（无专职检索运维）
- 关键数字：**运维人力 -80%+**；**接入天级**；**双路召回**；**评测集自有**
- 业务影响：让小团队以托管方式获得可用的混合检索能力，覆盖多业务搜索需求

**失败教训**

- 早期「**自建检索集群与 embedding 服务**」——小团队把人力耗在运维上，业务效果无人迭代，倒逼**「索引与模型托管，自有代码只保留融合与业务逻辑」**
- 「**把融合策略也交给托管**」——不同业务的融合偏好无法表达，倒逼**「通用能力托管、差异化能力自有」**
- 「**没有自有评测集**」——换了模型或参数后无法判断效果变化，倒逼**「维护业务评测集，参数按评测迭代」**
- 「**多业务各买一套检索**」——成本与治理双重膨胀，倒逼**「命名空间隔离共用同一套」**

### 4.3 字节"**ES + Milvus 双引擎服务抖音搜索：把召回从"单路"扩到"多路" 4+ 年**"（2020-2024）

**背景（Why）**

字节 2020 年面临**搜索场景多样化带来的召回需求分化**：
- **6 亿+ 用户**——**查询意图跨度极大：既有精确的人名、话题名，也有模糊的"这种感觉的视频"**
- **多模态内容**——**视频标题、标签、字幕、封面图、音频都可能是检索依据**
- **多业务（抖音 / TikTok / 西瓜 / 今日头条）**——**各业务召回策略不同，重复建设**
- **单路召回不够用**——**字面召回精确但不会泛化；语义召回会泛化但不精确**

**触发点（What）**

2020 年字节推进**双引擎（搜索引擎 + 向量引擎）多路召回**（[字节技术博客 2020-2024]），目标：
- **多路召回统一**——不同业务按需组合召回路径
- **多模态可检索**——视频的多类信号统一进检索面
- **6 亿+ 用户规模可用**

**详细做法（How）**

字节双引擎多路召回的**5 大核心组件**：

1. **"多路召回 + 统一融合层"的架构（核心创新）**
   - 关键设计：**把召回拆成多条独立路径**（字面、语义、标签、规则等），每条路径独立召回排名列表，在统一融合层合并；业务方按场景选择启用哪些路径
   - 关键能力：**召回能力可组合、可演进**——新增一路召回不影响其他路，业务不必重写整个检索
   - 关键数字：**多路可组合、6 亿+ 用户规模**
   - 关键示意：
     ```text
     多路召回 + 统一融合（新增一路不影响其他路）
       查询 q ─┬─▶ 路径1 字面召回（标题 / 标签）   ─▶ R1
               ├─▶ 路径2 语义召回（多模态向量）    ─▶ R2
               ├─▶ 路径3 标签 / 话题倒排          ─▶ R3
               └─▶ 路径4 规则 / 热度加权          ─▶ R4
                                 │
                     统一融合层（排名融合）──▶ 精排 ─▶ 结果
     ────────────────────────────────────────────────
     架构收益：每条路径的迭代相互独立
       新增"音频相似"召回 → 只加一路，融合层与其余路径不动
       某一路效果变差 → 单独下线，不影响整体
     -- 关键：把"召回"设计成可插拔的多路，而不是一个大而全的单路
     ```

2. **多模态信号统一进检索面（核心）**
   - 关键设计：**标题、标签、字幕、封面图、音频各自编码后进入相应召回路径**
   - 关键能力：**"用一句话描述画面"与"用一张图找相似"都能命中**
   - 关键性质：**多模态多路召回**

3. **融合与精排分离（核心）**
   - 关键设计：**融合层只做排名合并（对量纲不敏感），精排单独用交叉编码器做相关性判断**
   - 关键能力：**"别漏"与"排对"的职责分开**，各自可独立优化
   - 关键性质：**两阶段职责清晰**

4. **业务可配置的召回策略（核心）**
   - 关键设计：**各业务选择启用哪些召回路径与权重**，策略以配置表达而非硬编码
   - 关键能力：**4 业务共用一套引擎，但召回策略各自可调**
   - 关键数字：**4 业务统一引擎、策略可配**

5. **分层评测与快速回滚（核心创新）**
   - 关键设计：**按路径分别评测召回贡献**（哪一路带来了命中），上线按灰度放量，效果不达标快速回滚
   - 关键能力：**"新增这一路到底有没有用"可量化**，避免无效路径长期占用资源
   - 关键性质：**路径贡献可量化、可回滚**

**字节双引擎多路召回关键数字**（[字节技术博客 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **召回结构** | 单路 | 多路 + 统一融合 | **可组合可扩展** |
| **新增召回能力** | 需改造整条链路 | 新增一路即可 | **迭代成本大幅下降** |
| **模态支持** | 文本为主 | 标题 / 标签 / 字幕 / 封面 / 音频 | **多模态多路** |
| **融合方式** | 分数加权（需调参） | 排名融合 | **量纲无关** |
| **精排** | 与召回混在一起 | 独立交叉编码器精排 | **职责分离** |
| **业务策略** | 硬编码 | 配置化（4 业务可调） | **∞** |
| **路径贡献** | 不可知 | 按路径评测贡献 | **可量化** |
| **用户规模** | 亿级 | 6 亿+ | **∞** |

**具体数字（How much）**

- 团队规模：字节搜索 / 检索团队 200+ 人
- 关键数字：**多路可插拔召回、多模态 5 类信号**；**4 业务统一引擎**；**6 亿+ 用户**
- 业务影响：支撑抖音 / TikTok / 西瓜 / 今日头条的搜索与内容检索

**失败教训**

- 早期「**召回只有一路**」——精确查询与模糊查询总有一类效果差，倒逼**「多路召回 + 统一融合」**
- 「**每加一种召回就改造整条链路**」——迭代成本高且容易引入回归，倒逼**「把召回设计为可插拔的多路」**
- 「**融合层用分数加权**」——量纲不同导致权重需反复调，倒逼**「排名融合，对量纲不敏感」**
- 「**不知道新增的召回路径有没有贡献**」——无效路径长期占资源，倒逼**「按路径评测贡献 + 灰度可回滚」**

### 4.4 阿里"**ES + 自研向量引擎：把商品检索从"关键词匹配"升级为"多路语义检索" 5+ 年**"（2019-2024）

**背景（Why）**

阿里 2019 年面临**10 亿级商品检索的精度与泛化两难**：
- **10 亿+ 商品**——**纯语义检索在全量上做近邻代价不可接受，必须先缩小范围**
- **业务条件刚性**——**类目、库存、门店、价格区间必须精确满足**
- **查询意图多样**——**品牌型号类查询要求精确，场景描述类查询要求泛化**
- **多场景复用**——**搜索、导购、客服问答都需要检索能力，重复建设**

**触发点（What）**

2019 年阿里推进**搜索引擎 + 自研向量引擎的多路检索**（[阿里公开材料 2019-2024]），目标：
- **精度与泛化兼得**——字面保精度、语义保泛化
- **10 亿级可用**——条件先缩小范围再近邻
- **多场景复用**——检索能力服务化

**详细做法（How）**

阿里多路商品检索的**5 大核心组件**：

1. **"业务条件缩小范围 + 多路语义检索"的执行结构（核心创新）**
   - 关键设计：**先用结构化条件（类目 / 门店 / 库存 / 价格）把候选集收缩到可处理规模，再在这个子集上做多路语义近邻检索**；字面召回与语义召回并行
   - 关键能力：**10 亿级规模下语义检索可用**，且业务硬条件不会被"先召回再剔除"损失掉
   - 关键数字：**10 亿+ 商品可检索、条件参与召回**
   - 关键示意：
     ```text
     执行结构：先收缩范围，再多路召回（顺序决定可行性）
       Step 1 结构化收缩：category=手机 AND shop=? AND status=在售 AND price∈[..]
              → 10 亿收敛到数万~数十万
       Step 2 多路召回（在收缩后的子集上并行）
              ├─ 字面召回（标题 / 品牌 / 型号的倒排）  ─▶ 保精度
              └─ 语义召回（向量近邻）                 ─▶ 保泛化
       Step 3 融合（排名融合）→ 精排 → 结果
     ────────────────────────────────────────────────
     为什么顺序不能反：
       若先在全量上做语义近邻 → 计算代价不可接受
       若先召回再按条件剔除 → 解码"符合条件的产品没进候选"的召回损失
     -- 关键：结构化收缩既是为了性能，也是为了召回质量
     ```

2. **自研向量引擎承担在线近邻（核心）**
   - 关键设计：**向量索引与近邻检索由自研引擎承担**，按业务条件分区组织
   - 关键能力：**大规模近邻检索的延迟与召回率可按业务调优**
   - 关键性质：**在线近邻检索可用**

3. **排名融合与精排（核心）**
   - 关键设计：**多路排名融合后交由精排模型打分**
   - 关键能力：**多路召回都"别漏"，精排负责"排对"**
   - 关键性质：**精排后相关性提升**

4. **检索服务化与多场景复用（核心）**
   - 关键设计：**检索能力封装为服务**，搜索、导购、客服按场景配置召回路径与精排策略
   - 关键能力：**新场景不必重建检索链路**
   - 关键性质：**多场景复用一套底座**

5. **多模态扩展（核心创新）**
   - 关键设计：**图片经编码进入同一语义空间**，以图搜图与以文搜图共用召回与融合链路
   - 关键能力：**多模态检索不必单独搭一套**
   - 关键性质：**多模态统一链路**

**阿里多路商品检索关键数字**（[阿里公开材料 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **检索方式** | 关键词匹配为主 | 字面 + 语义多路 | **精度与泛化兼得** |
| **商品规模** | 亿级（语义检索不可行） | 10 亿+ 可检索 | **∞** |
| **业务硬条件** | 结果后剔除 | 结构化收缩参与召回 | **召回损失消除** |
| **在线近邻延迟** | — | 自研引擎，可按业务调优 | **可用** |
| **融合方式** | 单路分数 | 排名融合 | **量纲无关** |
| **精排** | 与召回混合 | 独立精排模型 | **职责分离** |
| **场景复用** | 各场景自建 | 检索服务化 | **∞** |
| **模态支持** | 文本 | 文本 / 图片统一链路 | **多模态** |

**具体数字（How much）**

- 团队规模：阿里搜索 / 检索团队 200+ 人
- 关键数字：**10 亿+ 商品可检索**；**条件参与召回**；**多路融合 + 精排**；**多场景复用**
- 业务影响：覆盖淘宝 / 天猫的搜索、导购与客服问答场景，并向云上客户输出检索能力

**失败教训**

- 早期「**用关键词匹配做全部检索**」——场景描述类查询召回极差，倒逼**「引入语义召回形成多路」**
- 「**先在全量上做语义近邻**」——10 亿级下计算代价不可接受，倒逼**「先用业务条件收缩范围，再在子集内近邻」**
- 「**先召回再按业务条件剔除**」——符合条件的产品可能压根没进候选，倒逼**「业务条件参与召回阶段」**
- 「**每个场景各搭一套检索链路**」——重复建设且效果参差，倒逼**「检索服务化，按场景配置召回路径」**

### 4.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**单引擎托管 + 字面召回 + 语义召回 + 排名融合**」（**最简单**）——**1 个场景、百万级数据**
- 产出：**双路召回 + RRF 式排名融合 + 分层评测脚本（召回率 / 排序质量分开看）**
- 团队：**2-3 人**
- 验证标准：**两路都能独立召回**、**融合不依赖量纲调参**、**评测能区分"召回漏了"与"排序错了"**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 场景 / 千万级数据**」
- 引入「**业务硬条件参与召回（收缩后再近邻）**」——避免先召回后剔除的召回损失
- 引入「**交叉编码器精排**」——与召回职责分离
- 团队：5-10 人
- 验证标准：**条件参与召回后结果数量稳定**、**精排后 Top-N 命中提升**、**端到端 P99 < 200ms**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 场景 / 亿级 / 多模态**」
- 引入「**可插拔多路召回**」——新增一路不影响其他路
- 引入「**多模态统一向量空间**」+「**命名空间隔离的多业务共用**」
- 团队：10-30 人
- 验证标准：**新增召回路径无需改造整条链路**、**按路径可量化贡献**、**多业务隔离共用**

**100 → 1000 阶段：12-24 个月**

- 引入「**检索服务化：按场景配置召回路径与精排策略**」
- 引入「**托管基础设施（索引 / 模型）+ 自有融合与评测**」的分工
- 引入「**模型版本托管重建 + 灰度放量与快速回滚**」
- 团队：30-100 人
- 验证标准：**新场景接入不改底座**、**模型切换可灰度可回滚**、**效果回归可自动化**、**运维人力不随规模线性增长**

### 4.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**召回率**」 | 70% 量级（单路） | 90%+（双路互补） | **+28%** |
| 「**融合调参负担**」 | 需反复调权重 | 排名融合，量纲无关 | **显著降低** |
| 「**排序质量**」 | 单路分数排序 | 交叉编码器精排 | **显著提升** |
| 「**端到端延迟**」 | — | P99 < 200ms | **在线可用** |
| 「**硬条件导致的召回损失**」 | 结果后剔除，损失明显 | 条件参与召回 | **损失消除** |
| 「**新增召回能力成本**」 | 改造整条链路 | 新增一路即可 | **-80%+** |
| 「**模态支持**」 | 文本 | 文本 / 图片 / 音频统一链路 | **多模态** |
| 「**运维人力（小团队场景）**」 | 自建集群与模型服务 | 托管 | **-80%+** |
| 「**多业务 / 多场景复用**」 | 各自搭建 | 服务化 + 命名空间隔离 | **∞** |
| 「**效果问题可定位性**」 | 只有端到端指标 | 分层指标可拆解 | **可定位** |

**关键投资回报**：
- **直接节省**：「**融合调参负担消除 + 新增召回能力成本 -80% + 运维人力 -80%**」——**混合检索最贵的不是算力，而是"不断调权重"和"每加一种检索就改造整条链路"这两笔人力账**；用对量纲不敏感的排名融合、把召回做成可插拔多路，省下的是长期的工程迭代成本
- **业务价值**：「**召回 90%+ + 精排显著提升 + 硬条件不损失召回**」——**检索效果直接决定搜索、推荐、问答的用户体验**；而"业务条件下沉到召回阶段"这一点常被忽略，却是很多检索效果长期上不去的真实原因
- **AI 时代关键**：「**多路可插拔召回 + 排名融合 + 分层评测**」——**这是 RAG 检索质量的地基**：LLM 的表现高度依赖"给它的上下文对不对"，而上下文质量又取决于召回是否既不全漏也不全错；分层评测则让"RAG 效果差"能被拆解到"检索漏了"还是"排序错了"，而不是笼统归咎于模型

---

> **本节小结**：
> - 4 个真实案例（某电商 / 某 SaaS / 字节 / 阿里）印证：**混合检索不是「把 ES 和向量库接起来」，是「字面 + 语义双路召回 + 排名融合（非分数加权）+ 硬条件参与召回 + 精排分离 + 分层评测」5 件套**。
> - 关键时间线：某电商 4+ 年 / 某 SaaS 4+ 年 / 字节 4+ 年 / 阿里 5+ 年 —— **混合检索是 4+ 年持续调优的工程**，且**关键在于"结构设计"（多路可插拔、条件先收缩）而非某个模型的选择**。
> - 选型第一原则：「**单引擎 + 双路召回 + 排名融合**」（**最简单**）——**百万级** → 「**硬条件参与召回 + 精排分离**」（**必须**）→ 「**可插拔多路 + 多模态统一空间 + 多业务隔离**」（**生产**）→ 「**检索服务化 + 托管基础设施 + 灰度回滚与分层评测**」（**AI 时代**）。
> - 99% 的失败来自「**单路召回 + 分数加权融合 + 先召回后剔除 + 召回与精排混杂**」——必须有 **多路互补 + 排名融合 + 条件参与召回 + 职责分离**。
> - 真正的 ROI 来自「**召回 90%+ + 调参负担消除 + 新增路径 -80% + 效果可定位**」——是**搜索 / 推荐 / RAG 效果能否真正上台阶的分水岭**。

> 💡 **思考锚点**：把你检索链路里的硬条件（品类、时间、权限、库存）列出来，逐条看它是在**召回时参与**还是**召回后才剔除**——落在后者的每一条，都在让精排去处理一批本该根本不存在的候选。你打算先动哪一条？
