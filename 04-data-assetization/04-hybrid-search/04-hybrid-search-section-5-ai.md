## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本主题的清单有一个别的章节没有的麻烦：**它的关键词全是"内置"与"SOTA"**——"某引擎内置混合检索""某模型多功能 SOTA""某框架支持 Agent 决定检索策略"。而"内置"在两家产品的文档里可以指完全不同的东西：内置了融合**函数**、内置了融合**参数**、还是把两路召回合并进**一条查询语句**。原文件把「Vespa Hybrid Search（2024）—— 一体化混合检索」「Weaviate Hybrid Search（2024）—— 内置 RRF」「Cohere Rerank 3（2024）—— 多语言 Rerank SOTA」并列成同一种句式，读者据此排路线图时，无法判断"内置"背后到底有没有你需要的那一半。本节要求每个方向都给**可核验的判定动作**：去哪一份官方文档的哪一节里核什么。

第二个坑是**把"模型更强"与"融合有效"混为一谈**。本目录 §7.3.1 已经证明：融合的收益**完全来自两路错误的不相关性**——一路错在"词面不同、意思相同"（稠密向量），另一路错在"意思不同、词面相近"（BM25）。这是**数据性质，不是模型能力**。所以换一个更强的 Embedding 模型不会自动提高融合收益（两路仍可能同源），而多分一路也不总会提高（若两路本已高度重合，收益接近零而成本照付）。任何以"某某模型 SOTA"开头的趋势判断，都必须先落到这个测量上，否则它描述的是模型榜位，不是你的系统。

第三个坑是**版本与命名**。本节涉及大量"某版本起支持某能力"：检索引擎的排名融合、向量库的多向量字段、多功能 Embedding 的规格（维度、上下文长度、支持语言数）。**本节不写具体版本号**——判定方法是去对应产品的官方 release note 或模型卡确认该条目是否存在、是否为正式发布项，而不是参考博客与榜单截图。同样，`BGE-M3` 是**模型名**，"多功能 Embedding"是**能力名**：任何"某模型也能出三种向量"的说法，都要以它的模型卡里有没有 sparse / colbert 两路的输出接口为准。

第四个坑是**把"只换了前端"当成架构变化**。本节对每个方向都要问一句：**AI 到底改变了哪个机制**——是成本结构、是接口边界、是把人工判断换成统计判断，还是只换了个交互方式？本主题里至少有一条（Query Understanding 的一部分）在机制上是"把已有的改写动作搬到了在线"，它改变的是成本发生的位置，不是检索的原理；把它说成"AI 让检索变准了"，会让读者以为换了模型就能解决问题。回答这张表见 §5.2 的引子。

最后说明本节对"成熟度"的用法：**L1 不是"我觉得它成熟"，而是三条同时成立**——有正式发布的条目、有非厂商公开的生产证据、接口稳定。本主题下大量宣称卡在第二条：厂商自有案例与演示很多，第三方公开的、含规模与条件的生产报告很少。**把这个空白写出来，比用"业内已广泛采用"把它填上更有用**，因为读者要据此决定的是自己要不要排期。

按这套判据，本主题下的方向分成三级：

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 多路召回 + RRF 融合成为引擎内置能力（原 §5.4「融合算法标准化」） | **L1** | RRF 公式与 k=60 有原始论文可核验（SIGIR 2009）；主流检索引擎的官方文档有排名融合专章（2023 年前后）；本目录 §6 的四个案例都在生产用多路召回与融合（其中 3 个明写排名融合） | 直接排进路线图：以 RRF 为默认融合，不再自研融合公式 |
| 多功能 Embedding（BGE-M3 / NV-Embed 类：一个模型出 dense / sparse / colbert） | **L2** | 论文与模型卡公开可核验（2024 年前后）；但三路各自的边际召回贡献只能自测，无第三方公开的、含并集上限的对比 | PoC：在自建评测集上量三路各自的边际贡献，再看是否值回三份存储 |
| Late Interaction 工业化（ColBERTv2 / ColPali / SPLADE++） | **L2** | ColBERTv2 有公开的压缩方法与评测（NAACL 2022）；ColPali 有公开论文（arXiv 2024）；但多向量 / 晚交互在各向量库里是否为一等索引类型需逐产品核验 | 先量存储放大（§7.3.2 的方法），再决定是否上量 |
| Query Understanding 智能化（Query Rewrite / HyDE / Step-Back / Multi-Query） | **L2** | 方法有公开论文可核验（2022–2024）；但每查询一次 LLM 调用使成本与结果不可复现，且无公开协议规定"如何扣除改写引入的方差" | PoC：必须做"开 / 关改写"的同集对照 |

| 多模态混合检索（向量 + BM25 + OCR + ASR 融合） | **L2**（组件 L1 / 融合 L2–L3） | 各路组件分别可用；但"融合"要求跨模态分数可比，缺公开评测协议 | 分路建索引 + 元数据关联，不要先合并 |
| 图增强召回（GraphRAG / KG 作第三路） | **L2**（建图）/ **L3**（在线多跳） | GraphRAG 于 2024 年开源，公开材料写明索引构建流程与成本提示 | 只在高价值、低更新频率、多跳占比高的语料上试点 |

> 本主题下**唯一处在 L1 的方向是"多路召回 + RRF 融合"**——但它恰恰不是 AI 带来的：RRF 是 2009 年的排序投票方法，它今天能用是因为主流引擎把它做成了内置能力，而不是因为模型有进展。其余方向的"不够格"各有各的原因：多功能 Embedding 与晚交互卡在**存储与版本对齐**（不是准确率）；Query Understanding 卡在**不可复现与成本位置**；Agentic 卡在**方差**；多模态卡在**跨模态分数可比**；图增强卡在**更新成本**。下面逐条给出机制。

为什么本主题只有一个 L1，值得说清楚：**因为混合检索的骨架（多路召回 + 融合 + 精排）在 2023 年前后就已定型**，此后所有新提法都发生在三个局部——表示层（一个模型出多种向量）、查询层（在线理解）、控制层（多轮决策与图）。这三个局部都还没有出现"已有正式条目 + 有非厂商公开的生产证据 + 接口稳定"三条件同时成立的条目，所以它们停在 L2 与 L3。**这不是保守，而是本主题最容易踩的坑：把"榜上更强"当成"架构成熟"。**

**这三级的排法直接决定路线图的顺序**：

- **L1 先做**：把两路召回（稠密 + BM25）与 RRF 用起来。它是全表里唯一"加得越多、边际成本越低"的一项——倒排索引通常已经在你用的引擎里，融合的计算量可以忽略（§7.4）。
- **L2 只做 PoC，并先把两个数测出来**：一是**并集 Recall@K 相对较优单路的增量**（决定要不要加路），二是**存储与写入放大倍数**（决定要不要上多向量 / 晚交互）。这两个数是"要不要上量"的判据，不是选型偏好。
- **L3 不排进排期**：把在线高频 QPS 交给多轮 LLM 决策，属于"等信号"而不是"抢跑"。
- **先有基线再改造**：本主题所有方向最终都要回到同一组数上（Recall@K / MRR / nDCG，加上延迟与成本）。**换任何一层之前先用固定评测集出一份基线**——没有基线的改造，事后无法归因，也无法验证能不能回退。
- **回填机制**：每次版本升级后回填一次级别。某个 L3 方向若出现第三方公开的、含成本与规模的在线案例就升 L2；某个 L2 方向若一年内仍拿不到你自己语料上的实测数字，就降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向在评审时应被直接打回——本主题的每一次能力提升，都对应一项成本结构的变化。四个方向各自属于哪一类机制变化，先集中列一次：

| 方向 | AI 改变了什么机制 | 属于哪一类变化 |
| --- | --- | --- |
| §5.2.1 多功能 Embedding | 多套编码器 → 一次编码多路输出 | **成本结构**（运维与版本对齐的单位变了，存储没省） |
| §5.2.2 Late Interaction 工业化 | 匹配粒度下沉到 token，且 doc 侧仍可预计算 | **成本结构**（用存储与写入放大买匹配粒度） |
| §5.2.3 Query Understanding | 改写从索引期移到查询期 | **成本位置**（一次性成本 → 每次查询成本）+ 接口边界（查询串形态变了） |
| §5.2.4 Agentic 与图增强 | 固定控制流 → 由中间结果决定下一步 | **控制流**（不是匹配方式；查询侧成本与方差同时上升） |

#### 5.2.1 多功能 Embedding：把"多路的版本对齐"合并成一次编码

- **旧做法与它的卡点**：多路召回的每一步都要有匹配的表示——稠密用一套编码器、稀疏用另一套（BM25 的统计量，或 SPLADE 类的学习稀疏）、晚交互再一套。卡点不在准确率，而在**版本对齐**。本目录 §7.4 已经算过：若两路使用不同的编码模型，任何一次模型升级都要做两次全量重建、跑两次回归、并重新校准融合参数，而融合阶段的调参本身要花人日。路数越多，"哪一版编码器配哪一版索引"的对应关系越难维护，这是多路召回最容易被低估的成本项。
- **AI 改变了什么机制**：**把"多套编码器"换成"一次编码、多路输出"**。原清单记的「BGE-M3（BAAI 2024）—— 单模型同时输出 dense / sparse / colbert」与「NV-Embed（NVIDIA 2024）」在机制上做的正是这件事：一次前向产出三种可用的检索表示，于是三种表示天然共享同一个版本号与同一次升级窗口。
- **由此得到的**：**因为三路表示共用一次编码，所以"多路"的运维成本从"路数 × 升级次数"降到"一次升级"**，而多路召回的收益（错误互补）原样保留——这就是"简化架构"的真实含义：省的是版本对齐与运维面，不是索引存储。
- **由此付出的**：**其一，存储放大而不是缩小**——三份表示就是三份索引（稠密向量 + 稀疏词项表 + 多向量），与"用三套系统"相比省的是运维，不是容量；**其二，单点相关性上升**——三路同源于一个编码器后，"错误互补"的前提被削弱：若该模型对某类查询（例如纯型号检索）系统性偏弱，三路会一起偏弱，而旧方案里 BM25 的词面精确性本就是与模型无关的独立信号；**其三，换模型等于换三条路**——升级要全量重建三份索引，回退同样要重建三份。

| 判断项 | 三套系统各出一路 | 一个模型出三路 |
| --- | --- | --- |
| 版本对齐单位 | 每条路各自升级 | 一次升级（但三路同时变） |
| 错误相关性 | 低（BM25 与模型无关） | **高**（共享同一个编码器） |
| 索引存储 | 三份 | 三份（省的是运维，不是容量） |
| 回退成本 | 回退某一路即可 | 三条路一起重建 |
| 适合的场景 | 查询里含大量专有名词 / 型号 | 以自然语言查询为主、运维人力紧张 |

- **证据与来源**：【公开】BGE-M3 的技术报告（arXiv，2024）以"多语言 / 多功能 / 多粒度"为目标，可自行核验其模型卡里的三路输出接口；**本节不引用任何"召回率提升多少"的数字**——融合收益与语料、问题集强相关，跨数据集的通用数字不可比（判定方法见 §7.3.1 的交集测量）。NV-Embed 一类工作同样是公开论文，具体规格以各自模型卡为准。
- **成熟度**：**L2**。判据：模型与接口已可用，但三路表示在各引擎里的落地方式不同、生态未稳，且没有第三方公开的、含并集上限的对比；小规模可试点，先量"三路相对两路"的边际贡献，再决定是否承担三份索引的升级面。
- **什么时候值得做**：运维人力紧张（一次升级要牵动多条路）、且查询以自然语言为主时，把版本对齐的单位从"路数"降到"一次"是实打实的收益；这时可以接受"三路共享一个编码器"带来的相关性上升。
- **什么时候不值得做**：如果你的查询里专有名词密度高（型号、订单号、错误码），BM25 这一路的独立价值很大，把它换成"同一个模型产出的稀疏"是**用相关性换运维简化**，多数情况下不划算。判定方法是取 100 条真实查询，分别用 BM25 与学习稀疏执行，比较两条路的命中集合差异；差异很小时才说明换得动。

#### 5.2.2 Late Interaction 工业化：用存储放大换匹配粒度

- **旧做法与它的卡点**：精排的常规做法是交叉编码器——把 query 与 doc 拼接过一遍模型，准确，但要对**每一个候选**做一次前向，成本 ∝ K，所以只能作用在几十到几百的候选上（§7.3.2）。想在更大的候选集上做细粒度匹配，旧路线做不到：双塔的 doc 侧只有一个向量，词级信息在建索引时就已丢失。
- **AI 改变了什么机制**：**把匹配粒度下沉到 token，同时保留可预计算的 doc 侧表示**。晚交互（ColBERT / ColBERTv2）把每篇文档编码成"每 token 一个向量"，在线只做逐 token 的 MaxSim；ColPali 把同一机制移到页面图像上（patch 级多向量）；SPLADE++ 是更轻的中间路线——学习稀疏，用倒排就能承载。**三者共同点的机制意义是：把成本从"在线算力"搬到"存储与写入"这一侧。**

```text
    三条路线的成本落在哪里（同一次检索）
      双塔（稠密）：  doc 侧 1 个向量   → 存储最低；匹配最粗（词级信息被压掉）
      晚交互：        doc 侧 N 个向量   → 存储与写入放大（N 决定倍数）；匹配细
      交叉编码器：    doc 侧不存        → 存储为零；但每对一次前向，成本 ∝ K
    ────────────────────────────────────────────────
    关键：三条路线不是"谁更准"，而是"把成本放在存储上、还是放在在线算力上"
          晚交互的位置在中间：比双塔贵在存储，比交叉编码便宜在在线
          → 所以它扩张的边界由存储预算决定，而不是由准确率决定
```

- **由此得到的**：**因为 doc 侧向量可以离线预计算，所以细粒度匹配第一次可以用在召回阶段，而不只是精排阶段**——这扩大了"能承受多细匹配"的候选集规模，也是它在存储便宜、算力贵的场景受欢迎的原因。
- **由此付出的**：**其一，存储与写入放大**。§7.3.2 已给出推算：按每篇 128 token、每 token 128 维 fp16 计，晚交互每篇约 32 KiB、双塔约 2 KiB，比值约 **16×**【推算，推导链见 §7.3.2】；ColBERTv2 的论文报告残差压缩把占用降低 6–10 倍【公开，ColBERTv2, NAACL 2022】——**压缩后仍约为双塔的 1.6–2.7 倍**【推算，16 ÷（6–10）】，没有把它降到 1。**其二，更新成本**：每 token 向量要随文档重建，写入放大约同倍数，所以它不适合高频变更的语料。**其三，生态未稳**：单向量是多数向量库的一等公民，多向量字段能否与元数据过滤组合需逐产品核验（判定方法：看该库文档里是否有"多向量字段 / 多向量检索"的正式条目，而不是看首页文案）。
- **证据与来源**：【公开】ColBERTv2（Santhanam et al., NAACL 2022）给出晚交互与压缩方法；ColPali（Faysse et al., arXiv 2024）把该机制用于文档页面；SPLADE 系列（Formal et al., SIGIR 2021 及其后续工作）给出学习稀疏的训练目标。**本节不给"晚交互比双塔准多少"的通用数字**——它随语料与问题形态变化；判定方法是先在自己的语料上量存储放大与延迟增量，再看它是否买到你需要的召回。
- **成熟度**：**L2**。判据：论文与开源实现可核验、思路已被部分产品吸收，但索引侧支持程度因产品而异、缺少第三方公开的上量案例；它现在的位置是"精排的一个可选层"，不是双塔的替代品。
- **什么时候值得做**：语料相对稳定、存储单价低、且召回瓶颈明确落在"词级匹配不足"上时，它的性价比最高；此时晚交互可以用在召回阶段，而不是只当精排用。
- **什么时候不值得做**：语料更新频繁（每天都有大量文档重写）时，晚交互的写入放大会跟着放大，而它的收益（更细的匹配）在高频变更场景里会被新文档不断稀释——此时正确的顺序是先修**切分与召回的失败分类**（§7.3.1 第三步），再谈晚交互。

#### 5.2.3 Query Understanding 智能化：把"理解"从索引期搬到查询期

- **旧做法与它的卡点**：查询理解过去发生在**建索引时**——同义词表、词典扩展、规则改写，都固化成索引的一部分。卡点是它**对每个具体查询是盲的**：词表覆盖不到的说法（口语化提问、指代、隐含条件、错别字、跨语言）永远检索不到，而改一次要重建或重新验证整套规则。§7.3.1 列的四类漏召回里，"语义理解失败"与"专有名词丢失"正属于这一类。
- **AI 改变了什么机制**：**把改写从索引期移到查询期**——每次查询现场用 LLM 生成更适合检索的表述：Query Rewrite（改写）、HyDE（先假写一份答案再拿去检索）、Step-Back（先抽象到上一层再检索）、Multi-Query（一次生成多个查询再合并）。机制上改变的不是检索算法，而是**"理解"发生在链路里的位置**。

```text
    成本与确定性的位置，随"理解放在哪里"而移动
      索引期理解（旧）：词表 / 规则 → 一次性重建成本，每次查询为零
                         → 结果确定、可复现；覆盖不到词表外的说法
      查询期理解（新）：每次查询调用 LLM 改写 → 成本随 QPS 线性，且带随机性
                         → 覆盖广；但同一问题两次的结果可能不同
    ────────────────────────────────────────────────
    关键：这不是"理解变强了"，而是"理解的位置换了"——
          换来的是覆盖，付出的是可复现性与容量的可规划性
```

原清单列的四种做法，机制上都在改变"查询被替成了什么"，代价也各不相同：

| 方法 | 它把查询改成了什么 | 主要代价 |
| --- | --- | --- |
| Query Rewrite | 更适合检索的表述（补全指代、去掉冗余） | 被丢掉的约束不可恢复（否定、时间、型号） |
| HyDE | 一份"假答案"文本，用它的向量去检索 | 假答案若偏离事实，会把整次检索带偏 |
| Step-Back | 更抽象的上位问题 | 抽象过度会丢具体约束，适合"为什么"类而非"哪一条"类问题 |
| Multi-Query | 多个改写后的查询，各自检索后合并 | 调用与检索次数成倍增加，并额外引入一路融合所需的方差 |

- **由此得到的**：**因为改写可以针对每个查询现场生成，所以查询侧的表达不再被"索引里写了什么词"锁死**——词表外说法、指代、隐含条件第一次有机会被召回；而且它是纯查询侧改动，不需要动索引，可以独立上线、独立回退，这是它比"换编码器重建索引"更轻的原因。
- **由此付出的**：**其一，成本位置变了**——从"索引一次、查询零次"变成"每查询至少一次 LLM 调用"，高频 QPS 下这项会超过检索本身的开销，容量规划必须按 QPS × 改写次数算。**其二，可复现性下降**——改写带随机性，同一问题在不同时间走不同查询，于是离线评测不再可复现：召回指标的差异里混进了改写方差，**必须做"开 / 关改写"的同集对照才能把方差扣掉**（§7.3.4 对 Agentic 说的"检索轨迹不唯一使离线评估不可复现"是同一个问题，只是这里更轻）。**其三，改写是"有损翻译"**——它把原始意图压成一个模型认为更可检索的表述，一旦压错（丢掉否定、丢掉时间约束、把型号泛化掉），检索侧再准也救不回来；这就是为什么含型号 / 错误码 / ID 的查询不能只走改写后的路径。
- **证据与来源**：【公开】HyDE（Gao et al., arXiv 2022 / ACL 2023）与 Step-Back（Zheng et al., ICLR 2024）是公开方法，机制与评测方式可自行核验；**"多查询生成"是改写类做法的常见变体，本节不给某个具体产品的函数名或参数名**——这类能力在不同平台的命名与行为不同，判定方法是查你所用平台的官方文档里"查询改写 / 查询扩展"章节的有无与开关形态。
- **成熟度**：**L2**。判据：方法已可用、实现成本低，但成本随 QPS 线性且结果不可复现，评测协议没有公开标准；适合"查询频次低、单次价值高"的场景（分析、调研），不适合直接压在高频在线路径上。
- **什么时候值得做**：查询以自然语言、长句、含指代或隐含条件为主，且漏召回的失败分类显示"语义理解失败"占多数时——这正是改写要解的问题。
- **上线前的最小验证**：取 200 条真实查询，跑三组——只有改写、只有检索侧优化、两者都开——比较 Recall@K。如果"只有改写"这一组的提升不稳定（换一批查询就消失），说明你买到的是噪声；如果"两者都开"与"只有检索侧优化"没有差别，说明当前瓶颈不在查询侧，改写可以先不上。

#### 5.2.4 从固定管线到多轮决策：Agentic 与图增强

- **旧做法与它的卡点**：混合检索是一条**固定管线**——几路召回、融合、精排，路数与顺序在写代码时定好。卡点有两种：**（a）路由问题**——不同类型的问题需要不同的路（型号查询该重 BM25、指代问题该先改写、跨源调查该多轮），而固定管线只能对所有问题用同一套权重；**（b）多跳问题**——需要"先查 A、看到结果再决定查 B"的问题，一次检索拿不到。原清单的「Agentic Hybrid Search（LangGraph + 多工具 / AutoGen + 检索决策）」与「混合检索 + GraphRAG（KG 召回 + 向量召回 + BM25 召回三路）」分别针对这两条。
- **AI 改变了什么机制**：**把"固定控制流"换成"由中间结果决定下一步"**。Agentic 让模型自己选路与轮数；图增强把一次"相似度打分"换成一次"关系图遍历"，并把"跨文档汇总"从"靠检索拼"换成"靠社区摘要读"（GraphRAG 的公开机制是实体关系抽取 + 社区摘要）。**注意两者改变的都是控制流，不是匹配方式。**

| 方案 | 索引期做什么 | 在线做什么 | 成本随什么增长 | 主要风险 |
| --- | --- | --- | --- | --- |
| 固定管线（两路 + RRF + 精排） | 编码 + 建索引（分摊后极低） | 固定几次检索 + 融合 + K 次精排 | QPS 线性 | 路由错了只能靠调参，无法自纠 |
| Agentic 检索 | 无 | 多轮 LLM 决策 + 多次检索 | 平均轮数 × QPS，**方差大** | 容量要按 P99 轮数做；离线评测不可复现 |
| 图增强（KG / GraphRAG） | **LLM 抽取实体关系 + 社区摘要** | 关系遍历 + 摘要读取 | 建图 ∝ 语料 token 数；更新 ∝ 变更文档数 | 抽取质量随模型版本漂移；实体对齐要人排 |

- **由此得到的**：**因为控制流可以由中间结果决定，所以"该怎么搜"这件事不再需要事先写死**——路由错误的查询第一次有自我纠正的机会，多跳问题也有了一条不依赖超长上下文的路径。
- **由此付出的**：**其一，Agentic 的代价在方差而不在均值**——同一个问题可能走 2 轮也可能走 8 轮，成本与延迟要按 P99 轮数规划；同时"轨迹不唯一"使离线评估不可复现，回归测试需要比固定管线大得多的样本量才有统计意义（§7.3.4）。**其二，图增强的代价在更新不在查询**——建图依赖 LLM 抽取，成本 ∝ 语料 token 数；文档一变更通常要重新对齐实体（合并同义、拆分误合并）并更新社区摘要，边际更新成本远高于向量索引的插入；§7.3.4 给出的推算量级是"100 万篇 × 平均 500 token ≈ 5 亿 token 的抽取输入"【推算，推导链见 §7.3.4】，这意味着建图必须被当成一条有分区、有重跑、有版本的**数据加工流水线**来运维，而不是一个建索引步骤。**其三，抽取质量随模型版本漂移**——换抽取模型等于换一张图，"这张图是哪个模型抽的"必须进元数据，否则历史结论无法复核。
- **证据与来源**：【公开】微软 GraphRAG 于 2024 年开源，其公开材料写明"实体关系抽取 + 社区摘要"的索引构建流程与成本提示（判定方法：看其仓库文档里的索引流程与成本说明，而不是看演示效果）；Agentic 一侧可核验的材料是各家 Agent 框架文档里的"最大迭代轮数"与"成本追踪"章节——**这类章节的存在本身说明方差是已知问题**，但**本节未能给出任何第三方公开的、含轮数分布与 P99 成本的在线 QPS 生产案例**。
- **成熟度**：**Agentic 为 L3**（仅框架与演示，无第三方在线的、含成本的公开案例）；**图增强的建图为 L2、在线多跳为 L3**。判据：图增强在"高价值、低更新频率、多跳占比高"的语料上可试点——先用 §7.3.4 的判定方法量"需要多跳的问题占比"与"语料日变更比例"，多跳占比 ≲ 10–20%【经验】或语料每天大幅变更时，先别建图。
- **什么时候值得做**：问题集里"需要多跳 / 需要跨源拼"的比例高（量级参照 §7.3.4），且这类查询单次价值高、频次低——两者同时成立时，多轮决策的方差可以用人工兜住，收益才开始为正。
- **一个更便宜的替代动作**：路由问题不必等到 Agentic 才能解。先用**查询分类 + 各路取数调节**（把"这类问题该重哪一路"做成规则或小分类器，直接改各路返回的候选数）就能拿到大部分收益，成本是一次性标注；只有当"该走几步"本身依赖中间结果时，多轮决策才是必需的。这条替代路径的价值在于：它把 §5.6 第三条预测的判断依据，提前变成了一个今天就能做的对照实验。

### 5.3 与本主题既有栈的接口在哪

混合检索与上下游不是"结合"关系，而是**交接物**关系：一次检索以什么形态交给下一跳、失败时谁负责，比"支持哪些路"更能决定系统能不能用。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Query 理解（LLM）→ 多路召回 | 交接物 = 改写后的查询表述 / 多个查询；**原始查询不再往下传** | 改写侧；**改写丢掉的约束，检索侧救不回来** | 可试点（L2） |
| 多路召回 ↔ 向量库 / 向量湖（§02） | 交接物 = Top-K 的 doc id + 分数 + 元数据；索引与原件分离存放 | 索引侧（索引可重建）；原件侧管丢失 | 既有技术（L1） |
| 多路召回 ↔ BM25 引擎 | 交接物 = **排名**（RRF 只消费名次，不消费分数） | 融合侧；分数不可比的问题被 RRF 消掉 | 既有技术（L1） |
| 召回结果 → 精排 | 交接物 = K 个候选的原文；K 由延迟预算反推（成本 ∝ K） | 精排侧；K 砍太狠会掩盖召回缺失 | 既有技术（L1） |
| 元数据 / 权限过滤 ↔ 召回 | 过滤发生在**召回前还是召回后**，是一条显式设计决定 | 权限侧；**返回空优于返回越权或过期结果** | 需明确（L2） |
| 检索 → RAG（§05）/ Agent（Ch5） | 交接物 = Top-K + 分数 + 来源引用 + 预算与权限域 | Agent / RAG 侧管预算与越权；检索侧只管召回 | 可试点（L2） |
| 检索 ↔ 图增强 | 图与向量是两套索引，一致性无自动保证 | 图侧；**抽取模型版本必须随图一起登记** | 建图 L2 / 在线 L3 |

一句话概括：**AI 没有新增调用关系，只改了一件交接物的形态**——"查询"从用户原话变成了模型生成的检索表述。这一件东西同时决定了两件事：成本从索引期移到查询期（可规划性下降），以及"用户到底想要什么"不再有单一事实来源（出现争议时，**原始查询必须留档**，否则无法回答"当时问的是什么"）。

四条接口上最容易出错的约定，值得单独写：

**第一，权限过滤的位置。**放在召回后（post-filter）的代价是：Top-K 里被权限拒掉的文档会挤掉本可返回的文档，并且向调用方暴露了"存在这样一份文档"这一事实；放在召回前（pre-filter）的代价是：过滤条件会改变召回的分布，等于在每个权限域里各自做一次最近邻搜索，召回质量与用户权限强耦合——同一个问题，权限不同的人拿到不同答案。这不是"配一下就好"的事，判定方法很具体：在索引里打一个"权限域"字段，统计跨域召回中被拒的比例——**比例高说明 post-filter 已经在实质性地降低召回，此时要么改 pre-filter，要么让检索侧先按权限域分片。**

**第二，索引与原件分离。**检索结果交给下游的应当是**原件引用**而不是原件字节：索引是可重建的制品，原件是不可丢的资产。这条约定同时决定了失败时的责任归属——索引重建慢是检索侧的问题（可回退到旧索引），原件丢失是存储侧的问题（不可逆），两者不能混在同一个告警里，否则一次索引故障会把存储团队也拉进事故电话。

**第三，失败时谁负责。**检索侧对"召回为空"和"返回越权结果"的责任完全不同：前者是能力问题，可降级、可告警；后者是事故，且不能用"模型不准"解释。因此接口上要有一条硬约定：**检索服务宁返回空，也不返回调用方无权查看的内容**；上游（RAG / Agent）要能区分"空结果"与"调用失败"，并对用户给出不同措辞。这条约定在引入 LLM 改写与 Agent 多轮之后会更重要——调用链变长后，"是谁把越权内容带进来的"会变得难以定位。

**第四，预算与权限域要一起传。**Agent 与 RAG 是检索的调用方，它们需要知道"这次检索花了多少、还能再调几次"。把预算（最大路数 / 最大候选数 / 最大重试次数）与权限域一并写进接口入参，而不是让调用方事后从日志里统计，才是真正能约束多轮决策成本的做法——这也是 §5.2.4 说"Agentic 的成本方差要按 P99 规划"时，唯一可操作的抓手。

**论文**

- Gao et al., "Precise Zero-Shot Dense Retrieval without Relevance Labels"（HyDE），arXiv 2022 / ACL 2023；Zheng et al., "Take a Step Back: Evoking Reasoning via Abstraction in Large Language Models"（Step-Back），ICLR 2024——查询期理解的两条代表路线。
- Faysse et al., "ColPali: Efficient Document Retrieval with Vision Language Models", arXiv 2024——把晚交互从文本块移到页面图像，是"多模态混合检索"里唯一有公开机制论文的一路。
- Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", NeurIPS 2020——RAG 的原始出处，也是"混合检索是 RAG 召回层"这一定位的公开依据。

**官方文档 / release note（判定入口）**

- 主流检索引擎官方文档中的排名融合（RRF）专章（2023 年前后）——判据是它把排名融合作为一等查询能力提供，而不是只给示例代码。
- Weaviate 官方文档的《Hybrid search》章节与 Vespa 官方文档的《Hybrid Search》页（本目录主文件 §1 的时间线记 hybrid search 于 2020 年在两家出现）——用途是核验两件事：融合发生在引擎内还是调用方，以及"内置"的具体语义（融合函数、权重参数、还是单条查询语句）；多向量字段是否为一等索引类型，看同一份官方文档里有没有"多向量"的正式条目。**不要用首页文案作判据。**
- Cohere 的 Rerank 3 模型卡与官方《Rerank》API 文档（2024）——可以核验的是**接口形态与限额**（输入长度、候选数上限、计费单位），不是这类服务的效果数字；Jina Reranker 一类同类服务用同一方法核验其模型卡与 API 文档，年份以各自发布公告为准。
- Microsoft GraphRAG 开源仓库文档（2024）——含索引构建流程与成本提示，是判断建图属于"流水线"还是"建索引步骤"的依据。
- LangChain 文档的《MultiQueryRetriever》页（2023 年前后）——"一次生成多个改写查询、各自检索后合并"这一做法的公开文档化形态；核验的是该能力的开关形态与调用次数（一次查询变成几次检索），而不是它的效果数字。各 LLM 平台对"查询改写 / 查询扩展"的命名与开关形态不同，判定动作见 §5.2.3。

**第三方生产案例**

- 本目录 §6 的四个案例（某电商的 ES + 向量双路召回、某 SaaS 的托管检索栈、字节的 ES + Milvus 双引擎、阿里的 ES + 自研向量引擎）——本节把它们作为"多路召回 + 融合"在生产可用的证据。
- 说明：本节**未能给出**可核验的、含轮数分布与成本的 Agentic 检索第三方在线案例，也未能给出含并集上限的"多功能 Embedding 对比两路"实测。**这两个空白本身是结论**，不是省略。

**怎么用这份清单**：

- 要核"**融合**"（某引擎的混合检索到底做了什么）→ 看 §7.3.3 与引擎官方文档的排名融合专章。
- 要核"**表示**"（某模型能否同时出多种向量、规格如何）→ 看模型卡与向量库的多向量章节。
- 要核"**控制流**"（Agentic 的成本与轮数边界）→ 看 Agent 框架文档里的最大轮数与成本追踪章节。
- 三类证据的更新速度不同（模型卡最快、引擎文档次之、生产案例最慢），**不要用其中一类的结论去推另一类**。

**核验 §5.1 表里七条宣称的最小动作**（都不需要采购、不需要新版本、也不需要内部资料）：

1. **多路召回 + RRF**：打开引擎文档的排名融合章节，确认它消费的是排名而不是分数——这一条就决定了你要不要做分数归一化。
2. **多功能 Embedding**：打开模型卡，确认 sparse / colbert 两路是否都有输出接口；再打印三路各自单独检索的候选集合，看交集有多高。
3. **晚交互**：打印语料的 token 长度分布，按 §7.3.2 的推算式估一遍存储与写入放大；再查向量库文档里多向量是否为一等能力。
4. **查询理解**：跑"开 / 关改写"的同集对照，并把同一个问题重复问两次，看两条回答对应的召回结果是否一致。
5. **Agentic**：在框架文档里找"最大轮数"与成本追踪条目；把自己的问题集按"需要几步"分类，数一数真正需要多轮的比例。
6. **多模态**：图文分别建一条索引，先看图文混排文档在语料里的真实占比，再决定要不要合并。
7. **图增强**：标注"需要多跳的问题占比"与"语料日变更比例"，两个数有一个不达标就先别建图。

这七条动作的共同点：它们用的都是**你本地的语料、你自己的评测集和公开文档**。本节把方向判成 L1 / L2 / L3，依据就是这些动作能不能做出结论——做得出结论的，才有资格进路线图。

### 5.5 被过度宣传的部分

**「混合检索把召回率提升 30%+」**——实际是：融合的收益**完全来自两路错误的不相关性**，两路同源时收益接近零而成本照付（§7.3.1）。原因：这句话把"换了一个更强的编码器"带来的收益，记到了"融合"这个动作上；而真正属于融合的上限是**并集 Recall@K 相对较优单路的增量**。**它什么时候才会成真**：在你的数据上量出这个增量，且它超出标注噪声量级（几百条问题的标注集上大致 3–5 个百分点【经验】）——这个测量一两天的标注就能做完，比任何通用数字都可靠。

**「多功能模型 SOTA，所以不再需要 BM25 了」**——实际是：学习稀疏的"精确匹配"来自模型判断哪些 token 重要，而 BM25 的精确性来自"这个词在文档里字面存在"这一与模型无关的事实。对**训练分布外**的 token（新出现的型号名、错误码、内部编号），学习稀疏的权重不可预期，而词面命中不受影响。原因：把"稀疏表示"与"BM25"当成了同一个概念——它们都产出稀疏向量，但一个来自统计，一个来自模型。**它什么时候才会成真**：判定方法是取最近一个月新增的型号名 / 错误码做一组查询，量两条路各自的命中率；这个测量做不做，比模型榜单更能决定选型。

**「Agentic 检索是混合检索的下一站」**——实际是把固定管线换成多轮决策：换来的是路由灵活性，付出的是**方差与不可复现**——成本与延迟要按 P99 轮数规划，离线评估需要大得多的样本量（§7.3.4）。原因：它适合"低频、单次价值高"的查询（跨源调查、复杂分析），不适合把在线高频 QPS 交给它，而"下一站"这个说法暗示的是全面替代。**它什么时候才会成真**：出现第三方公开的、含轮数分布与 P99 成本的在线 QPS 生产报告，且这些数字与固定管线可比。

这三条的共性值得点明：**它们都把"某个局部变强"说成了"整体更优"**，而本主题的成本结构恰好是分层的——表示层的收益由存储与更新成本买单，控制层的收益由方差与可复现性买单，融合层的收益由两路互补性决定。任何不给这三项限定语的性能声称，都可以直接归入营销材料。反过来说，本节并不是说这三个方向不能做：**它们的收益是真的，只是收益的边界由上面那三项成本决定**——先把边界写清楚再投入，是本主题里最省钱的习惯。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 融合层会继续标准化：融合本身不再是讨论焦点，重心移到"各路取多少候选"与"漏召回失败分类" | 引擎把排名融合作为一等能力并成为默认推荐；公开讨论里"怎么调融合权重"的比重下降 | 三年后主流实践仍在自研融合公式与逐案调权重，官方能力只被当作示例 |
| 晚交互会成为"精排之上的一个可选层"，而不是双塔的替代品 | 向量库把多向量检索列为一等索引类型，并明确给出存储放大与更新成本；产品把它定位为可选层 | 出现第三方公开的、用晚交互替代双塔并上量的案例（含存储与写入放大实测） |
| Agentic 检索会停在低频高价值查询与离线任务，不进入在线高频路径 | Agent 框架文档里"最大轮数"与成本上限成为标配；公开案例集中在分析类查询 | 出现公开的、含 P99 成本的在线 QPS 生产案例，且成本与固定管线可比 |
| 多模态检索的默认形态会是"各路独立索引 + 元数据关联"，而不是"一次融合跨模态分数" | 跨模态检索出现公开的评测协议与指标定义；统一索引成为主流库的一等能力 | 三年后实践仍是"图文分开建索引、在应用层拼"，跨模态统一检索停留在产品演示 |

写这四条时的共同约定：**信号必须是外部可观察的**（官方文档条目、公开案例、评测协议），而不是"我觉得会"。凡写不出证伪信号的判断，本节不写。

**被检验得最快的是第三条。** 原因：Agentic 的成本方差已经写在框架文档里（最大轮数与成本追踪），所以只要有人把它放到在线 QPS 上跑，P99 成本就一定会被记录下来并公开——这是一个一年内就能看到结果的判断。**最慢的是第四条**：跨模态检索要出现公开的评测协议，需要的是评测社区而不是产品团队的动作，本节对它不给时间预期。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 只有 BM25 / ES，召回不够 | 加一路稠密向量 + RRF，先不动融合公式 | 观察加路后并集 Recall@K 的增量；若落在噪声内，问题在切分或编码器 | 不要在没做交集测量前加第三路；不要自研融合算法 |
| 已有向量库，想提升精度 | 先上交叉编码器精排，K 由延迟预算反推 | 观察精排是否掩盖了召回缺失（做漏召回样本的失败分类） | 不要用"调融合权重"替代"修切分与取数"；不要为省延迟把 K 砍到掩盖正确答案 |
| 查询里大量型号 / 错误码 / 内部编号 | 保留 BM25 这一路并当独立信号；改写只用于自然语言查询 | 抽样人工核对改写前后，看型号是否被泛化掉 | 不要让所有查询都先过 LLM 改写；不要用学习稀疏替换词面精确匹配 |
| 想上多功能 Embedding / 晚交互 | 先量两个数：三路表示的边际召回贡献、存储与写入放大倍数 | 观察向量库是否把多向量列为一等能力（release note） | 不要在没量存储放大前全量重建；不要为"一个模型全搞定"承担三份索引的升级面 |
| 在线高频 QPS，想引入 Agent 决策 | 把 Agentic 留给离线 / 低频高价值查询；路由问题先用分类 + 取数调节解决 | 观察 P99 轮数与成本方差；容量按 P99 做 | 不要把高频在线路径交给多轮 LLM 决策；不要按平均轮数做成本预算 |
| 语料含扫描件 / 图表 | 图文两条独立链路 + 元数据关联 | 观察图文混排文档的真实占比 | 不要先合并索引；不要在没有跨模态评测的情况下宣布"统一检索" |
| 跨语言 / 跨团队查询多（同一问题有中英多种问法） | 先量化多语言查询在总流量里的占比，再决定换多语言编码器还是加改写 | 观察跨语言查询的漏召回是否集中在"语义理解失败"这一类 | 不要用查询改写替代多语言编码能力；不要为个位数占比的查询改架构 |
| 想做图增强 / GraphRAG 试点 | 先量"需要多跳的问题占比"与"语料日变更比例" | 观察抽取模型换代时的重建代价与图质量漂移 | 不要在语料每天大幅变更时建图；不要把它当成一次建索引的动作 |
| 正在做面向多团队 / 多租户的检索服务 | 先把权限域与失败责任写进接口契约（召回前 / 后过滤、空结果语义） | 观察跨域召回被权限拒的比例，据此决定是否改 pre-filter | 不要在没定权限过滤位置前把跨域文档合并索引 |
| 刚把评测集跑通、准备做一次大改造 | 先固定评测集与 K，并记录所有路的候选数（改造前基线） | 观察改造后各类漏召回占比的变化，而不是只看总分 | 不要在基线与指标口径没固定时改造；不要用改造后的口径解释改造前的数据 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改 schema、全量重建、成本模型失真），**而收益依赖一个尚未成立的假设**（两路一定互补 / 多向量索引已普及 / Agent 能扛住在线 QPS）。等 §5.6 的信号出现再投入，损失的只是时间。

另外注意顺序：表里每一行的「现在就该做」都可以独立完成，**不需要等上一行做完**——把它们当成并行清单，比当成阶段计划更贴近实际。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**"理解"与"表示"的位置从索引期移到了查询期**——查询理解从建索引时的词表与规则，变成每次查询现场生成的表述；多种表示从一个模型的一次编码产出。因为这一点，**唯一处在 L1 的方向——多路召回 + RRF 融合——恰恰不是 AI 带来的**：RRF 是 2009 年的排序投票方法，它今天能用是因为引擎把它做成了内置能力。它**没有**改变的是两件事：一是**融合收益的上限由两路错误的互补性决定**（这是数据性质，换更强的模型不会改变它）；二是"从大规模语料里找"仍然只能靠索引完成，查询期理解与重排都作用在候选集之上。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是"怎么搜"（控制流与理解位置），还是"搜得准"（表示与融合）？** 改控制流的（Agentic、图增强）要按成本与方差谨慎对待；改表示与融合的，先去量你自己语料上的两路互补性与存储放大。两者的共同前提是同一件事：**先把两路的漏召回测出来**——这个测量是本节所有判断的地基，也是唯一一项不需要等任何新版本、今天就能做完的工作。
>
> 如果只能带走一句话：**先把两路的漏召回测出来，再决定是加一路、换表示，还是加控制流。** 顺序反了，就会用多轮 LLM 决策去解一个切分问题。
