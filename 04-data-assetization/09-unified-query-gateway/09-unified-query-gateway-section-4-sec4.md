## 4. 工程实现

§3 回答的是「在你那组约束下该选哪种网关形态」，本节回答的是「选定之后怎么把它立起来」。两者不重叠：一段话如果只是在复述联邦查询或某个模式的机制，它属于 §3，本节只保留指向它的引用。

本文件同时写给两类读者，但重心不同。**§4.1–§4.3 对两类读者都成立**——步骤、机制、选型判据与起点无关；**§4.4 只写给存量改造者**：组织里已经有几十条跨源脚本、几套引擎凭据和一批不能停的看板，要做的是把入口收拢过来，而不是另起一套；**§4.5 的模板、§4.6–§4.8 的成本 / 容灾 / 演进三节与 §4.9 的自检清单**两边都能直接套用。从零搭建的读者可以把 §4.4 当「以后会遇到的边界」先读一遍——绝大多数网关在第二年都会变成存量改造项目，因为存量是长出来的，不是设计出来的。

### 4.1 落地步骤

八步的顺序大体是依赖关系：每一步都在给后一步生产判据所需的输入，但严格程度不同。**Step 1–4 与 Step 8 是硬顺序**（源端能力 → 引擎 → 连接器 → 元数据 → AI 集成），换序意味着前一步的产物必须重做；**Step 5–7 是一个可并行推进的组合**——隔离要在加速之前（否则收益无法测量），可观测与这两步并行（见 Step 7 的标题）。换序或省步的代价，写在每一步的第三件里。

**Step 1：需求分析（1–2 周【经验：随数据源数量与是否有现成查询日志而变】）**

- 清点数据源数量与类型（关系库 / 湖表 / 消息 / OLAP / 向量 / 图），逐个源标注它「能否过滤、能否聚合、能否分批读」。
- 从查询日志里捞真实查询样本——尤其是最耗时的那批，而不是发问卷问业务方想要什么。
- 记下 SLA 目标（延迟、并发）与首个业务域，只写一个。
- **产物**：一份「源 × 下推能力」清单 + 一份真实查询样本集 + 一页 SLA 目标。
- **判据**：拿样本里最耗时的 20 条，逐条写出它落在哪几个源、哪一段必须跨网络。写不出来的那条，说明源清点不全或日志不干净。
- **为什么必须这一步 / 为什么在这个位置**：源端的下推能力决定了后面所有性能结论。跳过它直接选引擎，会在 Step 5/6 才发现「最贵的那类查询恰恰是业务的主力查询」，那时已经接完连接器、上线了部分报表，退回成本远高于现在。

**Step 2：引擎选型（1–2 周【经验：随候选引擎数量与是否需要现场跑通 POC 而变】）**

- 用 Step 1 的样本集，在 2–3 个候选上跑同一批 SQL，记录 `EXPLAIN` 里源侧分片有没有带上过滤条件。
- 评估团队既有技能、可投入的运维人力、是否需要可采购的支持 SLA。
- 软件采购或自研的边界要在这一步定，不能拖到接连接器时再谈。
- **产物**：一页技术选型 ADR（选哪个、为什么、被放弃的候选各因什么放弃）。
- **判据**：ADR 里必须有一段「本引擎在本组织的下推能力清单」，并附至少一条 `EXPLAIN` 证据。只写「性能好」「生态好」不算判据。
- **为什么必须这一步 / 为什么在这个位置**：引擎决定连接器写在哪里、校验层挂在哪一层、权限规则如何下发。顺序颠倒（先接连接器再换引擎）意味着连接器配置与权限映射要整体重做一遍。

**Step 3：Connector 配置（2–4 周【经验：随源数量与私有源比例而变】）**

- 逐源接入 Connector（Hive / MySQL / Elasticsearch / Milvus / Neo4j 等），配置认证、连接池、分片大小。
- 每接一个源，同时登记两件事：**该源支持哪些下推算子**，以及**谁负责这个连接器**。
- **产物**：可联邦查询的数据源清单 + 每源的连接器配置 + 一页下推能力登记表。
- **判据**：对每个源跑一条「带过滤 + LIMIT」的查询，`EXPLAIN` 里源侧分片必须带上该过滤条件与 LIMIT。没带上，就是没下推，登记表上这一格不能填「支持」。
- **为什么必须这一步 / 为什么在这个位置**：这是把 Step 1 的能力清单变成事实的一步，也是后面性能优化的唯一抓手。它必须在 Step 4 之前，因为元数据集成要用到的 Catalog 就是这里建出来的。

**Step 4：元数据集成（1–2 周【经验：随 Catalog 数量与源端元数据能否直接复用而变】）**

- 把 Connector 元数据注册到数据目录（见本章 §6 的第 1 个案例，在 §6 文件中编号为 [6.1 字节](09-unified-query-gateway-section-6-sec6.md) 对统一语义层的处理），配置统一 Catalog 与命名空间分层。
- 核对统计信息是否随元数据一起可用——CBO 的输入就是它。
- **产物**：统一的元数据视图——N 个 Catalog 呈现成一套 schema，业务不必知道表在哪个源。
- **判据**：随机抽 3 张表，在目录里能查到它的 Owner、分层与统计信息最后收集时间。查不到，说明目录与网关没打通。
- **为什么必须这一步 / 为什么在这个位置**：没有统一 Catalog，优化器只能退回规则优化，Step 5 的 CBO 就无从开启；而没有目录，Step 5 的权限规则也无处登记。它是优化与治理的共同前置。

**Step 5：查询优化（2–4 周【经验：随资源组的划分维度是否需要按租户重划而变】）**

- 启用 CBO，收集列级统计；按业务 / 租户划分资源组，设并发上限、单查询内存上限与查询超时。
- 配置 LIMIT 与配额，让大查询进独立队列而不是与交互查询抢同一份资源。
- **产物**：可治理的查询网关——资源组划分、配额表、超时与拒绝策略。
- **判据**：故意提交一条不设 LIMIT 的全表扫，它必须被拒或被限流；紧接着提交一条正常点查，确认它没有被那条大查询拖慢。两个动作都要做，只做前一个测不出隔离。
- **为什么必须这一步 / 为什么在这个位置**：Step 3 让查询「能跑」，这一步让查询「不互相伤害」。放在 Step 6 之前，是因为只有隔离就位，性能优化的收益才可测量——否则加速前后的差异会被邻居噪声淹没。

**Step 6：性能优化（2–6 周【经验：随高频查询形态的稳定程度而变】）**

- 对可枚举的高频聚合建物化视图（Iceberg + Trino 物化视图）与结果缓存，配刷新策略并开启查询重写。
- 逐源核对查询下推（predicate / projection / limit），用 `EXPLAIN` 验证而不是看文档。
- 调整向量化执行参数（Velox / Gluten 一类执行路径）。
- **产物**：加速层（物化视图清单 + 刷新策略 + 命中率指标）+ 下推核对结果。
- **判据**：同一条高频报表查询，加速生效前后的扫描量差异必须能在 Query Trace 里看到；看不到差异，说明重写没命中，加速层在静默失效。
- **为什么必须这一步 / 为什么在这个位置**：它是唯一「先有观测能力才能做对」的一步。放在 Step 7 之后也可以，但那时你已经在用猜测调优。

**Step 7：可观测（1–2 周【经验：随要接的指标数量与 trace 分段粒度而变】，与 Step 5/6 并行）**

- 打开 JMX 暴露引擎指标到 Prometheus，用 Grafana 出板；接入 Query Trace，把一次查询拆成规划 / 排队 / 源侧 / Exchange 分段；打开慢查询日志留样本。
- **产物**：一块能按分段看耗时的看板 + 慢查询清单。
- **判据**：随机挑一条慢查询，能在看板上指出它慢在哪一段。指不出来的那次 trace，等于没接。
- **为什么必须这一步 / 为什么在这个位置**：跨源慢查询的成因分布在四个互不相同的层，没有分段就只能猜。它与 Step 5/6 并行而不是之后，因为隔离与加速的每一次调整都需要它来判定有效。

**Step 8：AI 集成（2–4 周【经验：随校验规则的条数与 Agent 可访问的 Catalog 数量而变】）**

- 打通 LLM（Text-to-SQL）→ 校验层 → 网关的执行链路，生成与执行之间那道校验不可绕过。
- 把网关注册成 Agent Tool，工具描述里写清可用 Catalog、禁止的算子与成本上限。
- **产物**：一条 Agent 可调用的查询通路 + 一份校验规则清单（裁剪检查 / 权限与租户注入 / 成本估算）。
- **判据**：让 Agent 生成 20 条查询，统计其中几条触发了裁剪检查、几条被成本估算拒绝。一条都没触发，要么校验层没生效，要么 Agent 只被喂了简单问题——两者都要查。
- **为什么必须这一步 / 为什么在这个位置**：它放在最后，是因为校验层依赖前面全部产物（分区信息、权限规则、成本模型）；放在最前，只会做出一层拦不住任何东西的装饰。

最常被跳过的是 **Step 3 的下推能力登记**与 **Step 5 的资源隔离**——它们不产出新功能，只产出「前面看起来已经跑通的东西能不能在规模下站住」的证据。跳过后第一次出问题的时点很固定：上线后第一个大促或第一个高频看板接入时。症状不是报错，而是 P99 一起劣化，且没人能指出是哪条查询拖的——因为既没有下推登记表，也没有分段 trace。

### 4.2 关键技术点

**Trino 集群（Coordinator + Worker）**

- **做法**：Coordinator 只做解析、规划与调度，Worker 承担执行；两者分离部署，Worker 可独立扩缩。
- **机制**：因为规划是单点、执行是可并行的那一半，把两者压在同一个角色上会让「一个复杂查询的规划」与「一群查询的执行」争同一份资源；拆开之后执行侧能水平扩展，而规划侧只需高可用。代价是多一跳调度与一份需要独立运维的角色。
- **失效条件**：当并发查询数与单条查询的规划复杂度同时上升（Catalog 变多、SQL 嵌套变深）时，先成为瓶颈的是 Coordinator 而不是 Worker——症状是**排队时间上涨而 Worker 利用率不高**，在 Query Trace 上表现为「排队」段占比上升而「源侧」段不动。
- **档位**：【经验】——拆分收益随查询形态变化，没有通用阈值。

**Connector 生态**

- **做法**：新增数据源 = 新增一个 Connector 配置，不新增一条链路。接入前先查官方 Connector 清单里是否存在该源的连接器。
- **机制**：因为 Connector 用统一的 SPI 把「读什么、能下推什么」抽象掉，新增源的成本从「建一条 ETL 链路」降到「写一份配置」；代价是每个 Connector 的下推实现质量不一致，同一个引擎在不同源上的表现可以差一个量级【经验：量级差随该源 Connector 的下推实现完整度而变，没有通用倍数】。
- **失效条件**：当某个源只有社区连接器、或者需要自行实现引擎的 SPI 时，这条从「配置即接入」退化成一个长期维护项目——症状是**该源上的查询 `EXPLAIN` 里永远是整表读，而且没人能改**，这个源随后会成为绕开网关最多的那个源。
- **档位**：【公开：Trino 官方文档, Connectors, 2024】官方连接器在数十个量级且随版本增长，此处不给固定数字——判定方法是打开该文档当前版本的 Connector 清单，数一遍「本组织真正要接的源」有几项落在里面。

**CBO（statistics、cost-based join reordering）**

- **做法**：收集列级统计（行数、不同值数、必要的直方图），让优化器按代价挑 Join 顺序与分发方式。
- **机制**：因为 Join 顺序与分发方式的选择完全依赖基数估计，而基数估计只能从统计来；有统计时优化器能把大表与小表分开（小表广播、大表分区），没有统计时只能退回规则默认。代价是统计本身要定期收集与维护，是新接一个源之后必须补的一项工作。
- **失效条件**：当统计缺失或过期（新分区写入后没有重新收集）时，大表 JOIN 大表会退化成广播——症状是**单个 Worker 内存打满、查询失败，而集群其余节点空闲**；这类失败容易被误判为「内存不够」，实际是计划选错。
- **档位**：【经验】——统计的失效速度随分区写入频率变化。

**资源组（按业务 / 租户隔离）**

- **做法**：按业务或租户划分资源组，为每组设并发上限、单查询内存上限与队列；大查询进独立队列。
- **机制**：隔离之所以有效，是因为 Worker 的内存与队列是共享资源、故障半径由隔离粒度决定——机制的完整推演同 [§ 3.5](09-unified-query-gateway-section-3-sec3.md)「资源无隔离」，本节不重述。实施层补两句：**隔离要拦的是「代价差」，不是「组织边界」**；**代价**是资源在组之间无法完全弹性互借，整体利用率低于无隔离。
- **失效条件**：当资源组按「团队」而不是按「查询代价」划分时，隔离会失效——同一个组里仍然可以有一条大查询拖垮全场。症状是**资源组配置看上去齐全，但每次大促仍有整组超时**；判据是看被拖慢的那些查询是否与被拖慢者同组，同组即分组维度选错。
- **档位**：【经验】。

**查询下推（predicate / projection / limit）**

- **做法**：逐 Connector 核对谓词、投影、LIMIT、分区裁剪是否实现，用 `EXPLAIN` 验证源侧分片带没带上条件。
- **机制**：机制与代价同 [§ 3.2.1](09-unified-query-gateway-section-3-sec3.md)——下推之后网络里传的只是过滤后的结果集，代价随之与结果集成正比，而这个性质完全寄生在 Connector 的实现上。往下推一层，本节只留实施层的结论：**下推能力不是引擎的属性，是「引擎 × 源」这一对的属性**，所以它不是选型时查一次的结论，而是每接一个源要重查一次、并写进登记表的事实。
- **失效条件**：**当登记表上某个源没有填「负责人」、或某一格从「支持」被悄悄改成「整表读」而没人复审时**，这条就失效了——查询本身不报错，只是那一类查询悄悄退化。查询侧的症状（小表快、上线后变慢）见 [§ 3.5](09-unified-query-gateway-section-3-sec3.md)「无下推」，本节补的是组织侧信号：**绕开网关直连该源的凭据或脚本数量开始增长**——绕行是下推失效最早、也最诚实的指标。
- **档位**：【经验】。

**物化视图（Iceberg + Trino 物化视图）**

- **做法**：对可枚举的高频聚合建物化视图，配定时或增量刷新，开启查询重写让原 SQL 不改也能命中。
- **机制**：因为重写发生在规划期且对业务 SQL 透明，加速收益与业务迭代解耦；代价是刷新链路、一致性校验与副本存储都由你承担。
- **失效条件**：当查询形态长尾、不可枚举时，命中率趋零，维护成本反超收益——症状是**建了一堆物化视图，但没有人看命中率指标**；加速层失效是静默的（不命中只是变慢，不报错）。
- **档位**：【经验】。

**向量化执行（Velox / Gluten）**

- **做法**：启用列式批处理的执行路径，让算子按批处理而不是逐行，减少分支与虚调用开销。
- **机制**：因为行式逐行执行里 CPU 相当一部分花在分支判断与虚函数调用上，列式批处理把同一摊工作摊到一批行上把固定开销摊薄，所以同样核数下吞吐上升；代价是类型映射、内存布局与周边插件生态的兼容面变窄。
- **失效条件**：当查询本身由 IO 或网络主导（扫的是远端对象存储、结果要跨网络 Exchange）时，换执行引擎对端到端时间几乎没有影响——症状是**本地扫描基准快了很多，生产 P99 不动**。
- **档位**：【经验】。

**可观测（JMX + Prometheus + Query Trace）**

- **做法**：JMX 暴露引擎内部指标到 Prometheus，Grafana 出板；Query Trace 把一次查询拆成规划 / 排队 / 源侧 / Exchange 分段；慢查询日志留样本。
- **机制**：因为跨源慢查询的成因分布在四个互不相同的层，只有分段才能把「慢」定位到某一层，优化动作才可被验证。代价是分段本身有开销，且要维护采样策略。
- **失效条件**：当只接了基础指标（QPS、整体延迟、失败率）时，定位只能靠猜——症状是**优化动作与 P99 之间没有可复现的因果关系**，同一调整今天有效明天无效，团队随后放弃量化、改回凭经验。
- **档位**：【经验】。

**AI 集成（Text-to-SQL + Agent Tool）**

- **做法**：把网关注册成 Agent 工具（描述里写清可用 Catalog、禁止的算子、成本上限），LLM 生成的 SQL 必须过校验层再执行。
- **机制**：因为 LLM 生成的 SQL 不可信（可能全表扫、可能漏租户条件），而网关是唯一不可绕过的执行入口，所以「校验」这一职责只能落在网关上；代价是多一段与查询语义同步演进的组件，改查询语义要同时改校验。
- **失效条件**：当 Agent 走旁路（直连源库、或使用另一套不经过网关的凭据）时，校验层形同虚设——症状是**网关上只有人工查询的成本与审计指标，Agent 产生的扫描量在账上找不到**。
- **档位**：【经验】。

**安全（认证 / 授权 / 行级 / 列级权限）**

- **做法**：账号与角色收归网关统一管理；行级、列级权限随 SQL 一起下推到源侧执行；关键操作留审计记录。
- **机制**：因为「查回来再过滤」意味着越权数据已经离开源系统、进入了网关内存与日志，所以只有把条件下推到源侧执行，越权才在引擎层就不返回。代价是权限规则必须覆盖每一个 Connector，新接一个源就要重新验证一次。
- **失效条件**：当新增了一个源而权限规则没同步覆盖时，这个源就成了旁路——症状是**同一角色在两个源上有不同的可见范围，而审计里看不出来**，因为不一致发生在规则覆盖的缺口里。
- **档位**：【经验】。

### 4.4 存量迁移

**① 先做立刻见效且可回退的那一步：影子查询。** 不动任何现有路径，先把网关接上 1–2 个只读源，让同一条查询在原路径与网关各跑一遍，比对结果。业务仍读原路径，回退方式就是关掉网关。这一步买到的不是功能，而是一份**可回退的证据**：网关在这个组织的真实查询分布上到底成不成立、差异集中在哪一类查询上。选源的原则是挑「只读、无强一致要求、下游不是关键看板」的那两个。

**② 历史资产分三类处理，而不是全部返工。** 存量脚本与报表按迁移代价分：

- **立即迁**：简单跨源、无强一致要求、下游可容忍结果顺序变化的那批。
- **打标挂账**：涉及长事务、强一致读、或依赖某引擎特有算子的那批。挂账不等于不管——每条要写清「为什么现在不迁」和「复审日期」，否则挂账会变成永久旁路。
- **不迁**：对延迟极敏感的点查、以及已经有专用加速路径的高频查询。它们的正确去向是留在加速层，网关只做编排（见 [§ 3.4 组合模式](09-unified-query-gateway-section-3-sec3.md)）。

分类时必须同时盘一件事：**这些路径各自用的是什么凭据**。迁移期最大的漏洞不是查询迁不过去，而是旧凭据没被回收——只要旧凭据还在，旁路就一直存在。

**③ 双轨期必须能回答「哪份对」。** 两条路径并行时，要对每一个已迁移的关键查询维护两个指标：**同一查询在两条路径上的结果差异条数**，以及**仍在旧路径上的查询量占比**。没有第一个指标，双轨期的正确性完全靠运气；没有第二个指标，你不知道迁移到底推进了多少。数据写入侧如果还有双写，要额外回答「检索能命中、但源已删或已更新」的条目有多少。

**④ 退出双轨的信号。** 三个都要满足：差异条数在连续一个完整的业务周期内保持为零（周期长度【经验：以月度为下限，随写入频率与对账频率而变】）、旧路径查询量降到可忽略、旧凭据已回收且回收记录可查。**只满足前两个就退出是常见错误**——旧凭据还在，几个月后某个脚本会重新长回旧路径，而这时已经没人记得双轨期做过对账。

### 4.5 模板 / 示例

**模板 1：跨源 JOIN（三个源一条 SQL）**

```sql
SELECT u.user_id, u.name, h.page_views, h.last_visit
FROM   hive.ecommerce.users u
JOIN   mysql.analytics.user_events h ON u.user_id = h.user_id
WHERE  u.city = 'Beijing'
  AND  h.event_date >= DATE '2025-10-01'
ORDER BY h.page_views DESC
LIMIT 100;
```

**怎么用**：把它当 `EXPLAIN` 的测试用例——跑完后看源侧分片有没有带上 `city` 与 `event_date` 这两个条件。带上了，说明两个连接器的谓词下推都在；只带上一半，登记表上就按「半下推」记，别记「支持」。

**模板 2：向量检索（Milvus 一类向量库连接器）**

```sql
-- 前提：该向量库存在官方连接器，且支持距离算子下推（先核对官方清单）
SELECT p.product_id, p.name, p.price, v.distance
FROM   mysql.ecommerce.products p,
       milvus.product_embeddings v
WHERE  v.id = CAST(p.product_id AS BIGINT)
  AND  v.embedding <=> CAST(:qvec AS ARRAY<DOUBLE>) < 0.3
ORDER BY v.distance ASC
LIMIT 10;
```

**怎么用**：照抄语法结构，**不要照抄前提**。这段成立与否取决于目标引擎的官方连接器清单里有没有该向量库——先核对，再决定走连接器还是走「引擎外先召回、把候选集注入 SQL」（口径见 [§ 3.2.6](09-unified-query-gateway-section-3-sec3.md) 与 [§ 5 前沿演进](09-unified-query-gateway-section-5-ai.md)）。

**模板 3：物化视图 + 查询重写**

```sql
CREATE MATERIALIZED VIEW top_products AS
SELECT product_id, SUM(amount) AS total_amount
FROM   iceberg.sales.orders
WHERE  order_date >= DATE '2025-10-01'
GROUP BY product_id;

REFRESH MATERIALIZED VIEW top_products;   -- 刷新策略与频率按查询的时效要求定
SELECT * FROM top_products ORDER BY total_amount DESC LIMIT 10;
```

**怎么用**：只对「重复出现且形态稳定」的聚合建，建完立刻把**命中率**接进看板——重写不命中时不会报错，只会静默走回原表。刷新区间随业务可容忍的陈旧度定，不要照抄这里的日期。

**模板 4：LLM 生成 SQL → 校验 → 执行**

```python
from trino.dbapi import connect

conn = connect(host="trino", port=8080, user="agent", catalog="hive")
schema = """
Table: hive.ecommerce.orders
Columns: order_id (bigint), user_id (bigint), amount (double), order_date (date)
"""

generated_sql = llm_generate(schema, "上个季度北京用户订单总金额")  # 换成你的 LLM 调用

# 校验层：不可绕过。三条检查缺一不可
#   ① 分区/时间范围裁剪检查（没有时间条件即拒绝）
#   ② 权限 + 租户条件强制注入
#   ③ 执行前成本估算（超阈值拒绝或降级）
checked_sql = guard.validate_and_rewrite(generated_sql, user="agent")

cur = conn.cursor()
cur.execute(checked_sql)
for row in cur.fetchall():
    print(row)
```

**怎么用**：真正要照抄的是中间那三行注释——它们是 Agent 场景下网关新增的那一段。上面的 LLM 调用与连接参数都是占位，**换掉**；`guard` 是你自己的校验组件，书本给不了它的实现。

### 4.6 成本：这套东西的账单

联邦网关的账单形状和「买一个数据库」不同：它不省数据、只省搬动，所以花费不落在存储上，落在**没被下推掉的那部分行**上。**这个主题贵在它是一个常驻在每条查询关键路径上的协调层**——容量必须覆盖跨源并发峰值，而账单最大的一行往往不是引擎，是它没拦住的那部分网络流量与 Connector 的长期人力。

- **人力（最易被低估）**：大头是「让 N 个 Connector 的下推结论保持诚实」（见 §4.2 Connector 生态）。每接一个源就多一份「登记哪些算子 + 谁负责」的台账（§4.5 模板、§4.9 自检第 1 条）。当某源从「配置即接入」退化成长期维护项目时，贵的是这个项目，不是许可证。
- **云账单两笔**：引擎侧 = Coordinator / Worker 常驻算力（Coordinator 单点但必须高可用，见 §4.2）；源间流量 = 跨源 Exchange 按 GB 计费，与下推率直接挂钩。同一引擎在一个源上只传过滤后结果集、在另一个整表拉入，网络费相差一到两个量级【经验：随源表规模与过滤选择性而变，须用自己的 `EXPLAIN` 与扫描量实测，不引用外部倍数】。量级的出处是 §1.4 的演化本身：联邦查询把「不搬数据」当卖点，代价恰在此处兑现。
- **存储 / 硬件**：只在自建对象存储 + 物化视图（Iceberg 表格式，§4.5 模板 3）时才显著——MV 副本与刷新链路是「加速」换来的新增账单，不是网关本身的。

**为什么贵在这里**：因为一次未下推，网关就从「省一次搬动」翻成「多搬一次」，成本符号翻转。这也是 §4.3 表里「把商业治理层当性能方案」最贵的误选：账单加在外层（许可证），而贵在内层。

> 💡 **思考锚点**：把你最贵的那条跨源查询的扫描量，按「下推率 100%」与「下推率 0%」各算一遍网络 GB，再乘你的出口单价——两者之差，就是你继续投入下推登记的人力预算上限。

### 4.7 容灾与故障演练

这一层的「数据」很薄——网关自己不存业务数据，它的资产是配置（Connector、资源组、权限、MV 定义）与缓存。所以容灾不是「备份多少 TB」，而是「计划层的高可用 + 配置即代码 + 缓存可重建」。

- **失效模式 → 影响面**：① Coordinator 挂（规划单点）→ **全部新查询**不可规划，在途查询在 Worker 上跑完（§4.2）；② 单个源挂 → 只有跨该源的查询失败，本地查询不受影响；③ 统计过期触发广播 → 单个 Worker OOM、其余节点空闲（§4.2 CBO 失效条件）；④ 下推静默退化 → 不报错，只有 P99 悄悄劣化（§4.2 查询下推）。
- **降级策略**：Coordinator 双活 + 接入层摘除；源级熔断，让跨该源的查询快速失败而不是拖住线程池；资源组保证一条大查询炸开时不拖垮交互组（§4.2 资源组）。
- **演练方案**：① 主动 kill Coordinator，量「新查询被拒 → 恢复可规划」的时长；② 断一个源的网络，确认只有跨源查询失败、且是快速失败而非挂起；③ 灌一条会造成广播的大 JOIN，验证它被资源组或超时拦住，而不是压垮集群。
- **恢复目标**：RPO 由配置仓库的提交频率决定——配置即代码时 RPO 为一个提交（近 0）【经验】；MV / 结果缓存可重建，RPO 等于重建耗时，不必单独备份【经验】。Coordinator 故障的 RTO 取决于有无热备【经验：有热备为秒到分钟级，冷启为分钟级，随集群元数据量而变】。**本主题不做跨地域多活**：网关无状态、可重建，跨地域容灾的成本落在「多一套常驻 Coordinator + 跨域配置一致性」，而故障半径其实由**上游源**决定——源挂了，网关多活也救不回；要跨域保的是源，不是网关。

> 💡 **思考锚点**：你的 Coordinator 上次被主动杀过是什么时候？如果从没杀过，你的 RTO 是「猜」出来的。

### 4.8 演进路线：0 → 1 → 100

**0 → 1（最小可用）**：一台引擎 + 2–3 个只读源 + §4.4 的影子查询。目标不是功能，是「一条跨源 JOIN 能跑通、且下推可验证」。**变贵的是**：几乎不贵，成本是人和时间。**先坏的是**：Coordinator 无高可用，重启即全停——此时没人会怪它，因为还没上关键看板。

**1 → 100（规模化）**：接几十个源、按「查询代价」划资源组、建物化视图加速、接分段可观测、把校验层挂到 LLM 通道上。**变贵的三样**：Connector 人力台账、跨源网络流量、MV 副本与刷新算力。**先坏的三样**：Coordinator 规划瓶颈（排队涨而 Worker 不忙，§4.2）、统计过期引发的 Worker OOM、资源组按团队分导致隔离失效（§4.2 与 §4.5 模板 5）。

**100 →（下一道坎）**：跨云 / 跨地域联邦 + 向量 / 图源 + LLM 规模生成查询（对应 §1.4 的「AI 原生统一查询，2024+」）。**变贵的是**：跨域专线流量，与多地域 Coordinator 的一致性成本（跨地域要保的是**查询可达**这一面；据 §4.7，容灾侧不为此做多活）。**先坏的是**：成本与审计的覆盖面出现缺口——Agent 一旦走旁路，账上就找不到它产生的扫描量（§4.2 AI 集成失效条件、§4.9 自检第 7 条）。这道坎的判据不再是「能不能查」，而是「还查不查得全」。

> 💡 **思考锚点**：你现在的阶段，按上面三档对号——你是「先坏 Coordinator」还是「先坏旁路」？这决定你下一笔钱该花在 HA，还是花在凭据收口上。

### 4.9 自检清单

模式层面的自检（下推、CBO、隔离、加速、权限各自的通用判据）见 [§ 3.7 自检清单](09-unified-query-gateway-section-3-sec3.md)。下面这 11 条只问一件事：**这些动作在本组织里是不是真的做过、并且留下了可查的记录**——答「是」必须能当场打开那份表、那块看板或那条记录。

1. 打开 Step 3 的**下推能力登记表**：每个 Connector 的两格（支持哪些下推算子 / 谁负责）是否都填了？有空格，说明接入时只改了配置、没留下结论，出问题时找不到人问。
2. 打开 Step 2 的**选型 ADR**：里面有没有一段「本引擎在本组织的下推能力清单」，并附至少一条 `EXPLAIN` 证据？只写「性能好 / 生态好」的 ADR，等于选型没留下可复用的判据，下一个引擎换型要从头再来一遍。
3. 随机抽 3 张已在用的表，在统一目录里查它的 Owner、分层与统计信息最后收集时间——五分钟内能否查到？查不到，说明 Step 4 只做到了一半。
4. 打开资源组的配置文件：谁在什么时候最后一次改的？改动之后有没有重跑过那条「大查询被隔离」的演练？只改配置不演练，隔离失效不会被发现。
5. 打开加速层看板：物化视图 / 反射的命中率，最近一周有人看过吗？建了但没人看命中率，加速失效是静默的——不命中只会变慢，不会报错。
6. 取最近一条被投诉过的慢查询，能否在 trace 上指出它慢在「规划 / 排队 / 源侧 / Exchange」哪一段？指不出，说明 trace 接了但没接到可判定的粒度。
7. 打开 Agent 的校验记录：最近 20 条生成查询里，几条触发了裁剪检查、几条被成本估算拒绝？一条都没触发，要么校验层没生效，要么 Agent 只被喂了简单问题，两者都要查。
8. 迁移期对每个已迁的关键查询，是否同时维护着「两条路径结果差异条数」与「旧路径查询量占比」？少一个，双轨期的正确性或进度就是在赌。
9. 打标挂账的历史资产：每一条是否写明了「为什么现在不迁」与**复审日期**？没有复审日期的挂账会变成永久旁路。
10. 打开凭据清单：旧凭据是否已回收，回收记录可查？是否还有仍在服役、能绕过网关直连源库的凭据——有，则前面的所有控制都只覆盖了一部分流量。
11. 抽一条查询查它的成本账：执行前的扫描量估算，与事后归到具体人或租户的成本，两者是否对得上？对不上，配额与计量都调不准，也无法据此砍掉最贵的那个用法。

### 4.10 小结

> 本节小结：整个落地过程中**唯一那个决定成败的环节，是 Step 3 的「逐源核对下推能力并把结论登记下来」**。它比选引擎、比加 Worker、比买商业发行版都更值得投入，因为它决定的是「网络里到底传了多少行」——同一个引擎，在一个源上只传过滤后的结果集，在另一个源上整表拉进来，两者相差一到两个量级【经验：倍数随源表规模与过滤条件的选择性而变，应在自己的源上用 `EXPLAIN` 与扫描量实测，不要引用外部倍数】。其余每一步都建立在这份登记表之上：没有它，Step 5 的优化没有抓手、Step 6 的加速无法验证、§4.9 的第 1 条永远答不上来。
>
> 💡 **思考锚点**：数一下你手上有几个源：其中多少个你已经用 `EXPLAIN` 实测过下推能力、并把结论登记进了那份表？再看双轨期——「同一查询两条路径上的结果差异条数」和「仍在旧路径上的查询量占比」这两个数，你现在能同时取到吗？取不到的那一个，就是你退出双轨前在赌的那一半。
