## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表读起来像一道选型题：大规模跨源选 Trino、云上 Lakehouse 选 Dremio、强治理选 Denodo 或 Starburst、有私有源就基于 Calcite 自研、面向 Agent 就加向量与图 Connector。但把它放进真实约束里就会散架：同样是「跨源查询」——一个源端的 Connector 实现了谓词下推与分片，联邦查询立刻便宜（只传过滤后的结果集）；另一个源只能整表吐数据，同一句 SQL 就从「省掉搬运」变成「最贵的一条路」。同一场景，正确模式相反。

决定这件事的底层机制不是「哪个引擎更快」，而是三个位置的合力：**计算在哪里执行**（下推到源侧、拉进引擎、还是搬一份到加速层）、**能力由谁声明**（Connector 声明自己能下推什么）、以及**网关除了执行还承担什么**（统一入口、语义、权限、租户、成本）。前两个决定查询能不能跑得动，第三个决定这套入口能不能被多个团队安全共用。需要说明的是，这三项里只有前两项落在主文件 §2.1 的术语表内（查询下推、Connector / Catalog），第三项是本章对「网关形态」的界定——它不属于任何单个引擎，因此 §2.1 里没有对应词条。

这里还要区分一件事：联邦查询引擎解决的是「一条 SQL 怎么被拆到多个源上执行」，而统一查询网关解决的是「谁来当唯一入口、口径在哪定义、权限在哪生效、成本怎么归因、谁能生成 SQL」。前者是单机或单集群的能力问题，后者是**组织级入口**的问题——同一个引擎装进网关后，多出的是语义层、改写器、校验器与计量，这些都不是引擎自带的。本章讨论的模式是按「网关形态」分的，因此同一款引擎在不同组织里会落在不同模式上。

所以本节先立约束、再谈模式。下表不是选型表，而是「本主题下最容易被约束推翻的直觉」清单。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 源端能下推多少（Connector 能力） | 联邦查询是否划算，代价由没被下推的那部分数据决定 | 「装个 Trino 就能跨源」——没有下推的联邦比搬数据还慢 |
| 数据能否移动（体积 / 合规 / 主权） | 选联邦下推、虚拟视图，还是物理搬一份 | 「先同步到一处再查最省事」——第二份副本一出现，「哪份对」再无答案 |
| 查询形态是长尾即席还是可枚举固定 | 是否需要加速层（物化 / 缓存 / 反射） | 「一个入口服务所有查询」——固定的高频查询每次重扫重算 |
| 并发与延迟预算 | 资源隔离方式与引擎路由 | 「集群不够就加机器」——一条不设上限的大查询能把全体交互用户拖慢 |
| 权限 / 多租户 / 成本可归因 | 约束写在哪一层（改写器 + 编译期校验 vs 应用层自觉） | 「应用层过滤就行」——漏一处即是越界事故，且事后无法自证 |
| 是否面向 Agent / LLM | SQL 生成之后有没有一道不可绕过的校验 | 「Text2SQL 直接连库」——不可信 SQL 同时带来性能事故与泄露风险 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 Trino / Presto 联邦查询

- **被什么约束逼出来**：明细在湖上、维表在关系库、实时流在消息系统，全量搬到一处既慢又会造出第二份互不一致的副本；而源端大多具备过滤与聚合能力，缺的只是一个统一入口。
- **结构**：一次查询被拆成「源侧分片 + 引擎内合并」，能推多远由 Connector 声明决定；网关额外把多个 Catalog 暴露成一套命名空间。

```text
多 Catalog 单一入口（一句 SQL 里出现三个源）
  SELECT o.dt, c.city, count(*) FROM iceberg.dwd_order o
  JOIN   hive.dim_city c ON o.city_id = c.city_id
  WHERE  o.dt = DATE '2025-01-01' GROUP BY 1, 2;

  物理分解
    分片 1  iceberg.dwd_order → 分区剪裁 + 谓词下推，只读命中分区
    分片 2  hive.dim_city     → 投影下推，只取 city_id / city 两列
    引擎内   Exchange → HashJoin → 聚合（只有聚合结果回到客户端）
  ────────────────────────────────────────────────
  代价的固定位置：分片结果必须经 Exchange 进引擎
                  下推越多，进引擎的行数越少
```

```properties
# etc/catalog/hive.properties —— 下推能力写在 Connector 实现与配置里，不写在 SQL 里
connector.name=hive
hive.metastore.uri=thrift://metastore:9083   # 元数据与统计信息的唯一来源（CBO 的输入）
hive.max-split-size=128MB                    # 分片粒度：决定源侧并行度
```

网关在这套结构上再加两件事——入口与裁决：

```text
引擎之上，网关补齐的四件事（都不是引擎自带的）
  ① 命名空间：N 个 Catalog 呈现成一套 schema，业务不必知道表在哪
  ② 语义层：指标 / 维度只定义一次，查询走语义视图而非裸表
  ③ 权限下推：行级 / 列级条件随 SQL 一起下发到源侧执行（不是查回来再过滤）
  ④ 成本与配额：执行前估算扫描量，超阈值拒绝或排队
  ────────────────────────────────────────────────
  判据：把引擎换成另一款，这四件事仍然存在
        → 说明它们属于"网关形态"，不属于某个引擎
```

- **为什么这样设计有效**：因为谓词、投影与 LIMIT 被下推到源侧执行，网络里只传「过滤后的结果集」，所以查询代价与结果集成正比、而非与源表大小成正比；代价是这个性质完全寄生在 Connector 的下推实现上——SQL 写得再漂亮，推不动没有实现的算子。
- **代价**：无法下推的算子必然把数据拉进引擎，跨源 JOIN 是网络瓶颈的固定位置；规划阶段要向每个 Catalog 取元数据与统计，Catalog 一多，规划本身就成延迟来源；引擎侧必须有内存上限与磁盘溢写兜底，否则一条大查询直接失败。
- **失效点**：当查询从「过滤后的小结果跨源关联」变成「两张大表全量关联」或「按分钟重复的高频点查」时，联邦从「省掉搬运链路」反转成最贵的一条路，因为每一行都要跨网络进引擎，而这里既没有源端本地索引、也没有预聚合可用。
- **真实使用**：Presto 由 Facebook 开源并用于跨 Hive 等数据源的交互式分析 【公开】（Presto: SQL on Everything，ICDE 2019）；其分叉版本于 2020 年 12 月更名为 Trino 【公开】（来源形态：Trino 官网的更名公告，2020 年 12 月）——更名是一个时间点而不是一段演进期，核对时应以公告页的发布日期为准；字节 / 美团的大规模生产形态见 [§6 落地实践](09-unified-query-gateway-section-6-sec6.md)。

#### 3.2.2 Starburst Enterprise（商业 Trino 发行版）

- **被什么约束逼出来**：组织已经选定 Trino 作为入口，但受监管或有多租户要求，必须补齐认证、审计、细粒度权限、跨源治理与可采购的支持 SLA——靠自建把这些补起来，人力与时间成本高于许可证。
- **结构**：执行引擎与开源 Trino 同源（Coordinator + Worker），差别在于同一引擎外挂了一层「企业能力带」，治理能力不另建一条链路。

```text
同一执行引擎，两层能力带（买的是外层，不是内层）
  ┌──────────────────────────────────────────────┐
  │ 企业能力带：认证 / 授权 / 行级列级权限 / 审计   │
  │            跨源治理 / 受支持发行版与 SLA        │
  ├──────────────────────────────────────────────┤
  │ 执行引擎：Coordinator + Worker + Connector SPI │  ← 与开源 Trino 同源
  └──────────────────────────────────────────────┘
  关键：查询性能的上限由内层（Connector 下推能力）决定，
        外层补的是"能不能被企业安全地用"，不是"跑得更快"
```

- **为什么这样设计有效**：因为治理能力挂在同一个引擎与同一套 SQL 接口上，权限与审计不需要在每个源各配一遍，也不会因为多一条链路而多出一份口径；代价是这套能力与发行版绑定，能力边界与升级节奏交给厂商。
- **代价**：许可证成本与厂商绑定；版本节奏不由自己决定，安全补丁与引擎特性要跟随发行版；治理能力再全，也改变不了「下推没实现就慢」这一条——买不到下推。
- **失效点**：当瓶颈位于下推能力或数据分布（而非治理功能）时，商业发行版无法解决；把发行版当成性能方案，会在许可证落地后发现问题原封不动——因为增强的是外层，疼的是内层。
- **真实使用**：Starburst Enterprise 是 Trino 的商业发行版 【公开】（来源形态：Starburst 官方站点上列出的企业发行版与其支持的 Trino 版本线，2024 年核查）；有合规审计与采购要求的组织选择受支持发行版是常见做法 【经验】。**判定方法**：核对时看两处——该发行版对应的 Trino 上游版本线，以及厂商是否公开承诺安全补丁的支持周期；这两项决定了「买」到底买到了什么。

#### 3.2.3 Dremio 云原生 Lakehouse

- **被什么约束逼出来**：数据在对象存储的开放表格式上（Iceberg / Delta），没有本地索引与缓存，直查要扫；但业务方要亚秒交互，又不接受为每条查询人工建物化视图。
- **结构**：加速靠「反射」——把原表物化成一份带排序、分区与预聚合的副本，由优化器在查询时自动重写命中，用户 SQL 不改。

```text
反射（Reflection）：把"加速物"与"用户 SQL"解耦
  原始数据：  s3://lake/orders/*.parquet        ← 无索引，范围扫描
                    │  物化 + 排序 + 预聚合
                    ▼
  反射副本：  orders_by_city_day（列存 + 分区 + 聚合）
                    │  优化器在规划期做"查询重写"
                    ▼
  用户查询：  SELECT city, sum(amt) FROM orders WHERE dt='...' GROUP BY city
              → 计划被改写成读反射副本，SQL 一个字没改
  ────────────────────────────────────────────────
  关键：加速对业务透明 → 也能静默失效（重写没匹配上，悄悄走回原表）
```

```text
反射的两种形态（决定它能覆盖哪类查询）
  Raw reflection（原料反射）：原表的列子集 + 排序键 + 分区
        → 覆盖"同一张表上各种过滤 + 取列"的查询
  Aggregate reflection（聚合反射）：按维度预聚合后的结果集
        → 覆盖"固定维度组合"的看板与报表
  ────────────────────────────────────────────────
  优化器在规划期匹配：命中 → 改写计划；不命中 → 静默走原表
  所以必须单独观测"命中率"，否则加速层失效时没有任何信号
```

- **为什么这样设计有效**：因为加速物由优化器在规划期自动匹配重写，业务不需要知道加速层的存在，加速的收益与业务迭代解耦；代价是必须维护「反射副本与源的一致性 + 刷新策略 + 副本存储」这三样，它们都由你承担。
- **代价**：反射副本的存储与刷新作业是常驻成本；重写匹配失败时不报错、只是变慢，需要专门观测命中率；与 sourced-from-Arrow 生态的工具链和团队既有 Trino 技能不完全互通，切换有学习成本。
- **失效点**：当查询形态长尾、不可枚举时（每条查询都不一样），反射覆盖不到，加速层退化成「人工为每条查询建物化」，维护负担反超收益，因为反射的前提是「查询模式可被归纳成有限几种」。
- **真实使用**：Apache Arrow 项目于 2016 年启动，由 Wes McKinney 与 Jacques Nadeau 共同发起，官方定位是多方参与的开源项目，Dremio 是参与组织之一——把它写成「某一家公司主导」是归属夸大，这类项目的历史应看项目自身的治理文档而非厂商博客 【公开】（来源形态：Apache Arrow 项目官方站点的项目与治理说明，2016 年启动）；「云原生联邦 + 反射加速」是 Dremio 自身公开的产品形态 【公开】（来源形态：Dremio 官方文档中 Reflection 一节的产品说明，2024 年核查）。

#### 3.2.4 Denodo 数据虚拟化

- **被什么约束逼出来**：企业有大量异构源，且**数据不允许移动**（合规、数据主权、跨法人边界），业务方要的是一层稳定的「逻辑视图」，而不是一个 SQL 执行引擎。
- **结构**：虚拟层里定义视图、视图之间的关联、缓存策略，以及「这个查询去哪些源、怎么下推」的映射；视图可嵌套复用，源可以替换而视图名不变。

```sql
-- 虚拟层里的逻辑视图：源位置被隐藏，业务只依赖视图名
CREATE VIEW v_customer_360 AS
SELECT c.cust_id, c.name, o.last_order_amt, s.ticket_cnt
FROM   erp.customer      c          -- 源 A（关系库）
LEFT JOIN crm.orders     o ON ...   -- 源 B（另一套库）
LEFT JOIN svc.tickets    s ON ...;  -- 源 C（SaaS API）

-- 业务查询只写视图；换源时只改映射，不改业务 SQL
SELECT * FROM v_customer_360 WHERE cust_id = :id;
-- 代价：视图是否可下推，取决于虚拟层的映射与优化能力
--       嵌套视图 + 跨源 JOIN + 外层过滤，容易让过滤推不到最底层
```

- **为什么这样设计有效**：因为逻辑模型与物理位置解耦，业务依赖的是视图契约而不是表结构，换源、拆源、加源都不改业务；代价是这层逻辑视图成为唯一的解释层，它的元数据与语义必须被治理，否则视图本身会变成新的口径孤岛。
- **代价**：虚拟层自身的元数据、权限与性能调优面成为新的常驻工作；缓存要定义失效策略（否则读到过期数据且无人知晓）；商业授权成本；下推效果依赖映射质量，不透明时只能靠观测。
- **失效点**：当视图层层嵌套、外层过滤无法被拆解下推到最底层源时，虚拟化从「不搬数据」反转成「在中间层搬数据」，因为中间结果必须在虚拟层落地才能继续关联，此时既不省传输也不省内存。
- **真实使用**：Denodo 是商业化的企业级数据虚拟化平台 【公开】（来源形态：Denodo 官方站点上列出的数据虚拟化平台产品与其支持的源类型清单，2024 年核查）；用户集中在受监管行业与多源并存的大型企业 【经验】。

#### 3.2.5 Apache Calcite 自研

- **被什么约束逼出来**：私有协议、私有存储、私有权限模型（自研 KV、内部 API、内部消息系统），现成引擎的 Connector 表达不了；而组织已经标准化在 SQL 上，希望新增一个源的成本是「写一个适配器」而不是「建一条链路」。
- **结构**：Calcite 提供 SQL 解析 → 关系代数 → 优化规则 → 执行框架；适配器对每张表显式声明「我能下推什么」，规划器据此生成物理计划。

```java
// 自研网关的关键不在"能解析 SQL"，而在"每张表声明了能下推什么"
public interface AdapterCapability {
  boolean supportsFilter(List<RexNode> conds, TableRef t);   // 谓词下推
  boolean supportsProject(List<String> cols, TableRef t);    // 投影下推
  boolean supportsAggregate(AggCall agg, TableRef t);        // 聚合下推
  double  estimatedRowCount(TableRef t);                     // 统计信息 → CBO 的输入
}
// 没声明下推 = 引擎把整表拉进来再过滤；
// 没有统计信息 = 优化器退回规则优化，大表可能被当小表广播。
```

```text
同一句 SQL，两次规划（行数为示意值，只用来体现量级差异）
  无统计：TableA (未知)  ⋈ TableB (未知)  → 规则默认把左侧当小表广播
                                        → 真实左侧是大表，单点内存打满
  有统计：TableA (2.1 亿行) ⋈ TableB (800 行) → 选分区 Join，小表广播
  ────────────────────────────────────────────────
  自研的上限就写在这里：能生成几套候选计划、按什么代价模型挑
```

- **为什么这样设计有效**：因为「能下推什么」由适配器逐表显式声明，同一句 SQL 在不同源上能生成差异极大的物理计划，一个自研引擎因此能覆盖对外部引擎而言差异过大的一组源；代价是优化器规则、统计收集、执行器与运维全部由自研方长期承担。
- **代价**：这是一个常驻项目而不是一次交付——优化规则质量、统计新鲜度、执行器内存管理、连接器维护四件都要人；分叉风险高，早期决策（类型系统、时间语义）后期很难改。
- **失效点**：当自研停在「SQL 能跑通、结果对」而没有 CBO 与统计时，复杂查询的物理计划劣化（Join 顺序错、大表被广播），自研从「最贴合业务」反转成「最不可控」，因为此时没有任何外部力量能帮你兜住计划质量。
- **真实使用**：Apache Calcite 是 ASF 项目，被多个开源 SQL 引擎当作解析与优化层使用 【公开】（来源形态：Apache Calcite 官网对其「SQL 解析、校验与优化框架」的定位说明与采用者列表，2024 年核查）；云厂商与大型互联网公司基于它自研统一查询网关是常见形态 【经验】。

#### 3.2.6 AI 原生网关（Trino + 向量 Connector + KG Connector + LLM 优化）

- **被什么约束逼出来**：Agent 与 LLM 要在一条查询里同时拿到结构化条件、语义相似度与关系遍历；同时 LLM 生成的 SQL 不可信——可能全表扫、可能越权，网关必须成为唯一不可绕过的关卡。
- **结构**：向量与图被表达成 Connector 里的「表」，跨模态 JOIN 落在同一个执行计划里；生成与执行之间插一道校验层。

```text
生成 → 校验 → 执行 → 回灌（校验层是 Agent 场景新增的那一段）
  自然语言 ──► LLM 生成 SQL
                    │
              ┌─────▼──────────────────────────────┐
              │ 校验层（不可绕过）                   │
              │  ① 分区/时间范围裁剪检查（防全表扫）   │
              │  ② 权限 + 租户条件强制注入            │
              │  ③ 成本估算（超阈值拒绝或降级）        │
              └─────┬──────────────────────────────┘
                    ▼  执行
      mysql.products  JOIN  milvus.product_embeddings
                      JOIN  neo4j.product_graph
                    │  结果回灌 LLM 生成答案
                    ▼
  ────────────────────────────────────────────────
  关键：向量/图在这一层只是"能参与执行计划的表"，
        它们的检索质量仍由各自的索引与过滤策略决定
```

- **为什么这样设计有效**：因为向量与图被表达成参与统一执行计划的表，结构化过滤 + 语义近邻 + 关系遍历可以用一条 SQL 表达并把可下推的部分推到各自引擎，Agent 不必自己编排多次往返；代价是通用引擎里那一段向量检索的能力弱于专用向量库。
- **代价**：生态不成熟——向量 / 图 Connector 的下推能力、类型映射与稳定性都弱于关系型 Connector，而且**通用引擎并不保证自带向量库连接器**：**判定方法**——不要采信「支持某向量库联邦查询」的说法，去目标引擎的官方连接器清单里逐项核对是否存在该向量库的连接器（[Trino 官方文档, Connectors, 2024]），不存在就只能自行实现引擎的 SPI，或把向量检索留在引擎之外、以候选集形式注入（口径与 [§5 前沿演进](09-unified-query-gateway-section-5-ai.md) 5.2.2 一致）；校验层本身是新增组件，要跟着查询语义一起演进，否则会拦错或漏拦。
- **失效点**：当向量规模上升到千万级以上、或需要「先宽召回再重排再过滤」的精细链路时，Connector 化的向量检索反转成瓶颈，因为 ANN 索引参数、多向量（late interaction）与带过滤的近似检索都不是通用引擎的强项，此时向量检索该退回专用向量库，网关只做汇总。
- **真实使用**：这一方向目前更常见的落地形态是「引擎之外先召回、把候选集注入 SQL」，而不是把向量 / 图做成通用引擎里的一等 Connector；把多模态做成通用 Connector 尚无公开生产案例 【经验】。**判定方法**：不看功能清单与发布会页面，去目标引擎的官方连接器清单里核对是否存在该向量库的连接器，再追问「这条链路上有没有第三方生产案例、跑了多久」。LLM 优化查询计划与 Text-to-SQL 的形态见 [§5 前沿演进](09-unified-query-gateway-section-5-ai.md)。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 多源即席、源端可下推、结果集不大 | Trino / Presto 联邦 | 不选先搬数据：搬运链路要维护，第二份副本还会与源不一致 | 源端能否过滤 / 分批（看 Connector 能力） |
| 数据在对象存储 / Iceberg 上、查询形态可枚举 | Dremio 类反射加速（或联邦 + 物化） | 不选纯联邦：同一条聚合被反复重扫重算 | 同一类查询是否被按小时以上频率重复 |
| 数据不允许出域、源数量多而杂 | Denodo 类虚拟层 | 不选物理搬运：搬出去本身就不合规 | 能否拿到「数据不出域」的技术承诺 |
| 私有协议 / 私有权限模型、源长期自研 | Apache Calcite 自研 | 不选自建 ETL：每接一个源就多一条常驻链路 | 接入的源是否只有本组织用 |
| 受监管、要审计与可采购的支持 SLA | Starburst 类商业发行版 | 不选裸开源：治理能力要自己建，且要有人长期养 | 是否受监管、是否有采购与预算流程 |
| Agent 要一条 SQL 跨结构化 + 向量 + 图 | AI 原生网关（多 Connector + 校验层） | 不选应用层拼装：多次往返且无法统一权限 | 向量规模是否在 Connector 能力内 |
| 高频固定报表 / 高并发点查 | 下沉到 OLAP 或物化，网关只做编排 | 不选联邦直跑：搬运与重算成本被重复支付 | 查询模式是否稳定到可被建模 |
| 多租户 SaaS、按量计费 | 改写器 + 编译期租户校验 + 成本护栏 | 不选应用层过滤：漏一处即越界事故且无法自证 | 是否有跨租户泄露的不可接受风险 |

本节最常被误选的一对，是**把「商业治理层」当成「性能方案」**——查询慢就上 Starburst 或 Denodo。两者的机制差别很直接：商业发行版增强的是外层（认证、审计、细粒度权限、跨源治理、支持 SLA），而慢的根因几乎总在内层（Connector 没实现下推、统计缺失导致计划劣化、资源没隔离）。误选的实际后果是：许可证落地、审计与权限确实变好了，但 P99 一点没动，团队随后把责任归给「联邦查询这条路走不通」，而真正该做的是逐个 Connector 补下推并用 `EXPLAIN` 验证。

### 3.4 组合模式：真实系统不会只用一种

**组合一：联邦编排层 + 加速层（谁编排、谁做重活）**

- 构成：联邦引擎负责跨源拼接、口径统一与长尾即席查询；物化视图 / 反射副本承载可枚举的固定模式查询。
- 职责边界：联邦层不做重活（不承担被反复重复的大规模聚合），加速层不做长尾（不为一次性查询建模），两边以「查询模式是否稳定」划线。
- 运维代价：两套系统加一条刷新链路，多出的是「哪份对」的一致性校验与新鲜度指标；加速层要建模（分区、排序键、物化定义），建模决策是长期成本。
- 适合规模：已有稳定高频报表、同时存在长尾跨源即席需求的组织（本章 §6 的第 3 个案例，在 §6 文件中编号为 [6.3 美团](09-unified-query-gateway-section-6-sec6.md)）。

**组合二：单一入口 + 统一语义层 + 权限下推（口径与权限各只定义一次）**

- 构成：网关是唯一 SQL 入口；指标与维度注册在语义层，业务写语义视图而非裸表；行级 / 列级权限规则由网关统一下发到各引擎执行。
- 职责边界：语义层管「同一指标只有一份定义」，网关管「这条查询用谁的权限、在哪执行」，引擎管「怎么算」。
- 运维代价：语义层成为新的关键路径，改一次口径影响面大，必须有版本与影响面分析；权限规则要能覆盖所有 Connector，新接一个源就要验证一次。
- 适合规模：多业务共用一套数据、且已出现「同名字段两个口径」问题的组织（本章 §6 的第 2 个案例，在 §6 文件中编号为 [6.2 阿里](09-unified-query-gateway-section-6-sec6.md)）。

**组合三：网关 + 编译期租户约束 + 成本护栏（多租户 SaaS 化）**

- 构成：查询改写器强制注入租户条件，编译期校验缺约束即拒绝；执行前做成本估算，超预算拒绝或降级；按扫描量计量出账。
- 职责边界：改写与校验管「越界写不出来」，成本护栏管「亏钱跑不起来」，网关本身不存放客户数据。
- 运维代价：改写器与优化器耦合，SQL 方言或计划形态一变化就要同步改；成本估算不准会误拦正常查询或漏放大查询，需要持续用真实负载校准。
- 适合规模：一对多的对外服务形态（本章 §6 的第 4 个案例，在 §6 文件中编号为 [6.4 某 SaaS](09-unified-query-gateway-section-6-sec6.md)）。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 跨源 JOIN 当 ETL | 网关集群夜间跑大批量跨源 JOIN，与即席查询争抢同一资源池 | 逐行跨网络搬运且无源端索引，结果还不落地、无法被下游复用 | 把「一条 SQL 能写出来」当成「应该这么跑」 | 周期性、可枚举、结果要被复用的场景下沉为 ETL / 物化，落一份 |
| 无下推 | `EXPLAIN` 里源侧分片是「整表读」，没带上过滤条件 | 全量数据进引擎再过滤，传输量与内存压力随源表线性放大 | 先接通再优化，Connector 只实现了「能读」 | 逐源核对谓词 / 投影 / LIMIT / 分区下推，用 `EXPLAIN` 验证 |
| 小数据源过度查询 | 几百行的维表被高频 JOIN，每次都过一遍网络与连接 | 固定成本被反复支付，源端连接数被打满 | 把「统一入口」理解成「所有表都走联邦」 | 小维表用复制 / 缓存 / 物化固定在引擎侧 |
| 无 CBO（用 RBO） | 大表 JOIN 大表时工作节点内存打满或广播失败 | 错误基数估计把大表当小表广播，单点内存成为天花板 | 统计信息缺失，只能退回规则优化 | 收集列级统计，必要时显式指定 Join 分发方式 |
| 资源无隔离 | 一条大查询开始后，全体交互查询同时变慢 | 单查询占满工作节点内存与队列，故障半径等于整个集群 | 默认配置直接上线，没有按工作负载分组 | 资源组 / 队列 / 独立集群 + 查询超时 + 并发上限 |
| 无成本控制 | 联邦查询扫全表；集群利用率与查询笔数不成比例 | 扫描量在执行前不可见，成本无法归因到人或租户 | 先把查询跑通，成本留给「以后再说」 | 执行前成本估算 + LIMIT / 配额 + 按扫描量计量 |
| 无监控 | 跨源查询慢，但说不清慢在下推、网络还是源端 | 没有分段耗时，优化只能靠猜，性能回归无法验证 | 只接了基础指标，没做查询分段 trace | Query Trace（规划 / 排队 / 源侧 / Exchange 分段）+ 慢查询日志 |
| AI 安全失控 | Agent 生成的 SQL 直连网关，出现全表扫或越权返回 | 不可信 SQL 同时带来性能事故与泄露，且事后无法自证 | 把 LLM 当成「又一个客户端」，沿用原有权限模型 | 生成后强制过校验层：裁剪检查 + 权限与租户注入 + 成本估算 |

**「无下推」是这一节最危险的一条，因为它是「联邦查询就是慢」这一印象的真正来源。** 生产里的暴露方式很典型：一条跨源查询在测试环境（小表）跑得飞快，上线后源表增长到远超测试规模，查询时间随之线性上涨——而团队会先去调引擎参数、加 Worker，实际原因是 Connector 每次都把整表拉进来。判据只有一行：看 `EXPLAIN` 里源侧分片有没有带上过滤条件，没带就是没有下推。

**「资源无隔离」不会以「慢」的形式暴露，而是以「一起慢」的形式暴露。** 机制上，工作节点的内存与队列是共享资源，一条不设上限的大查询会把它们占满，故障半径等于整个集群；因此这条反模式的代价不是某个查询变慢，而是全部用户的可用性被一个查询绑定。真正要做的不是优化那条慢查询，而是让慢查询挤不到快查询。

**「AI 安全失控」的特殊性在于它同时是两种事故。** LLM 生成的 SQL 既可能因为漏了时间范围而做出全表扫描，也可能因为漏了租户或权限条件而返回不该返回的行；前者是性能事故，后者是数据泄露，且两者都无法靠「应用层记得过滤」来兜住。所以 Agent 场景下网关新增的那一段不是优化，而是控制：生成与执行之间必须有一道不可绕过的校验。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单源 → 跨源 | 应用直连单库 | 每加一个源就多一条 ETL 链路，副本还会不一致 | 联邦查询（统一 Catalog） | 建 Connector 与权限映射；查询能力受源端下推能力限制 |
| 3 个源 → 10+ 个源 | 直配 Catalog | 规划期要向每个 Catalog 取元数据与统计，规划本身成延迟来源；权限一套套配 | Catalog 分层 + 权限规则统一下发 | 元数据治理成为常驻工作，新接一个源必须同步验证权限 |
| 长尾即席 → 出现固定高频查询 | 联邦直跑 | 同一条聚合被反复重扫、重复跨网络搬运 | 下沉到物化 / 反射加速层，联邦层只做编排 | 重建刷新链路与一致性校验，「哪份对」的问题回归 |
| 人写 SQL → Agent 生成 SQL | 面向人的权限与配额模型 | 生成 SQL 不可信：全表扫与越权都可能在无人察觉时发生 | 生成后校验层（裁剪 / 权限 / 租户 / 成本） | 每条生成 SQL 多一次校验与规划开销，且要持续校准阈值 |
| 单租户 → 多租户 | 应用层过滤租户条件 | 一处漏写即越界，且事后无法自证合规 | 改写器 + 编译期租户校验 | 每条 SQL 多一次改写与校验；改写器与优化器需同步演进 |
| 不计量 → 按量计费 | 无成本约束 | 个别用户的全表扫直接等于亏钱，且费用无法归因 | 执行前成本估算 + 按扫描量计量 | 估算不准会误拦正常查询或漏放大查询，需用真实负载反复校准 |

补一句判据：**当「每次查询都要重新搬运或重算的那部分」占执行时间的主要部分时，就该换模式**——要么把下推做得更深，要么把结果提前算好，要么把这条查询挪到另一个不该搬家的层。

### 3.7 自检清单

1. 随机抽一条跨源慢查询，`EXPLAIN` 里源侧分片是否带上了过滤条件？没带即「无下推」。
2. 每个 Connector 是否有明确的「支持下推算子清单」？答不出，说明下推能力处于未知状态。
3. 关键表的列级统计最近一次收集是什么时候？从未收集，说明 CBO 一直在猜。
4. 是否存在被按分钟调度的查询跑在联邦层？存在即应下沉到加速层。
5. 交互查询与大批量跨源 JOIN 是否共用同一资源池？是，则故障半径等于整个集群。
6. 是否设置了单查询内存上限与查询超时？没有，则一条查询可以打满集群。
7. 慢查询能否分段看到「规划 / 排队 / 源侧 / Exchange」各占多少？不能，则优化只能靠猜。
8. 加速层（物化 / 反射）最近一次刷新是什么时候，命中率能否观测？命中率不可观测，则加速失效是静默的。
9. 权限与租户条件是在网关层强制注入并校验，还是靠应用自觉？后者在多租户下不可接受。
10. 每条查询在执行前是否可估算扫描量，成本能否归因到人或租户？
11. Agent 生成的 SQL 是否与人工 SQL 走同一道校验？不一致，则 AI 是一个旁路。
12. 是否有仍在服役的自研 Connector / 改写器只由一个人维护？是，就是单点风险。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 多源即席、源端可下推 | Trino / Presto 联邦 | 只传过滤后的结果集，代价与结果集成正比而非与源表成正比 |
| 数据在对象存储、查询形态可枚举 | Dremio 类反射加速 | 加速物由优化器自动重写命中，业务 SQL 不改即可加速 |
| 数据不允许出域 | Denodo 类虚拟层 | 逻辑视图与物理位置解耦，换源不改业务 |
| 私有协议 / 私有权限模型 | Apache Calcite 自研 | 下推能力逐表声明，一个引擎可覆盖差异极大的源；代价是常驻自研 |
| 受监管、要审计与支持 SLA | Starburst 类商业发行版 | 治理能力挂在同一引擎上，不引入第二条链路 |
| Agent 要跨结构化 + 向量 + 图 | AI 原生网关 + 校验层 | 一条执行计划完成三类取数；校验层拦住不可信 SQL |
| 高频固定查询 | 下沉物化 / 加速层 | 避免每次重复支付搬运与重算 |
| 多租户、按量计费 | 改写器 + 编译期校验 + 成本护栏 | 越界在语法上写不出来，超预算在执行前被拦住 |

> 本节小结：本主题下决定模式选择的**唯一那条最前置的约束，是「下推能力与数据能否移动」**——它决定数据要不要跨网络搬家，而搬家一旦发生，延迟、内存与一致性会同时被绑住。其余约束（治理要求、加速需求、租户隔离、AI 安全）都是在这个可选集合里做二次筛选：能下推的走联邦，不可枚举又高频的加加速层，不许移动的留在源侧用虚拟层，源太特殊的下推到自研适配器里，而面向 Agent 时，网关的第一职责从「执行」变成「校验」。
>
> 💡 **思考锚点**：抽你最近一条跨源慢查询，看 `EXPLAIN` 里源侧分片有没有带上过滤条件——若没带（§3.5 的「无下推」），你会不会正打算按 §3.3 的误选去上 Starburst / Denodo 一类商业治理层，而慢的根因其实在 Connector？再算一次：这条查询里「每次都要重新搬运或重算的那部分」占执行时间多少，够到 §3.6 的换模式线了吗？
