## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

统一查询网关的技术底座在 AI 之前就已定型：读时转换 + 逐源协商的下推，规划与调度集中在 coordinator，关系算子之外的东西（向量 top-k、图遍历）只能作为表函数注入（§7.3）。因此本节要问的不是「联邦查询会不会被 AI 取代」，而是三个更窄的问题：

- **AI 改变了谁发出查询**——从分析师点一下，变成 Agent 持续调用。这改变的是负载分布与治理落点，不是引擎能力；
- **AI 改变了查询怎么被写出来**——从人写 SQL，变成模型生成 SQL。这改变的是正确性由谁负责、校验层放在哪里；
- **AI 试图改变引擎的哪个内部环节**——优化、连接器、执行。这一层最容易出现"演示能跑、生产不能用"的条目。

趋势清单之所以会误导读者排路线图，是因为它没有时间维度：把「已 GA 且有人在生产用」的东西，和「路线图里的一句话」并列写在同一个 bullet 列表里，读者从中读不出「下周能不能开工」。这个主题还有第二个特有风险：**自然语言查询类条目，其"能不能用"取决于 schema 规模与语义层是否齐全，而演示现场通常只有一个干净的小 schema**——同一句「自然语言直接跨源查询」，在演示里成立、在没有语义层的生产仓里不成立。

本节用 L1 / L2 / L3 三级区分，判据取可核验的三条：**有正式 release note、有第三方（非厂商）公开生产案例、接口稳定**——三条全中才是 L1；只有厂商自有案例、或只在小规模被验证过是 L2；只有论文 / 路线图 / 演示是 L3。「感觉成熟」不算判据，因为它无法在评审会上被复核。判据里特意写了「第三方（非厂商）」，是因为本主题的商业产品密度特别高，而产品页上的能力清单与"在你的 schema 上能不能跑对"是两件事。

把这三条判据落到本主题上，会得到一个与直觉相反的结论：**这个主题里"最像 AI 的"那几项成熟度反而最低**。原因是它们的成败并不取决于模型，而取决于网关侧的两件基础设施——语义层（表、字段、口径的机器可读定义）与治理层（准入、配额、审计）。这两件事在 AI 之前就存在、也早就有生产案例（§6 的四个案例全是这两件事的工程）；模型只是把对它们的依赖暴露了出来：**没有语义层时，自然语言查询的上限由"表名起得好不好"决定**。所以在判级时，凡是需要新增基础设施才能成立的方向，都不能算 L1。

这里还要提醒一个本主题特有的读表方式：**表格里"级别"一列说的是"能不能现在就规划"，不是"这件事重不重要"**。Text-to-SQL 与向量联邦的重要程度很高，但它们的落地顺序排在网关治理之后——因为一个没有准入的网关，接上 Agent 的第一件事就是被一条大查询打垮（§7.3.3）。级别低不等于不用管，它只意味着**现在做会比晚一点做贵**。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| 网关作为 Agent 的唯一取数入口（准入 / 配额 / 审计） | L1 | 网关本身是 GA 部件、第三方生产案例充分；新增的只是"调用方是机器" | 可排进路线图：先把准入与配额做出来，再放开给 Agent |
| Text-to-SQL + 联邦查询（云端产品与自研两条路） | L2 | 单库场景已有产品化能力，跨源场景缺公开评测与第三方生产案例 | PoC：先在单源 + 已建语义层的范围内做 |
| 向量 / 知识图谱作为候选集注入联邦查询 | L2 | 可用表函数形态接入，但执行不能进关系优化器（§7.3.4） | PoC：把召回数量显式限死，再谈效果 |
| AI 增强查询优化：索引推荐 | L2 | 索引推荐是数据库领域的既有方向，加 LLM 只是换实现 | 只做建议，不接入自动变更 |
| AI 增强查询优化：Join 顺序 / 计划解释 | L3 | 无第三方评测；计划解释是界面改良，不改变计划质量 | 记录；不要为它改架构 |
| 多模态 Connector（图像 / 音视频等非结构化源进联邦） | L3 | 缺公开生产案例，也缺对应的算子与成本模型 | 记录；不要写进架构假设 |
| Agent 联邦查询（单 SQL 跨源取数） | L2 | 形态可用，但模型生成的 SQL 分布与人类不同（§7.3.3） | 先做配额与超时，再放开跨源 |
| 实时联邦查询（流式源 + 联邦 JOIN） | L3 | 对流式源做跨源 JOIN 无可核验的生产案例；联邦多为有界查询 | 观望；先把流式数据物化到湖仓再查 |
| Trino + RAG / 向量湖 / GraphRAG 的混合检索 | L2 | 与"向量作为候选集注入"是同一机制的不同叫法 | 按 5.2.2 的边界做，不要让网关承担跨模态 JOIN |
| 向量化执行与执行引擎整合（Velox / Gluten 一线） | L2 | 是引擎内部的性能路线，与联邦语义无关；生态仍在演进 | 关注即可，它不改变选型判据 |

表里唯一处在 L1 的方向是**「把网关作为 Agent 的唯一取数入口」**：它的机制（把 N 个数据源收成 1 个入口，再加准入、配额、审计）在 AI 之前就 GA，第三方生产案例充分（§6 的 9.1–9.4 四个案例都属于这一类）；AI 带来的唯一变化是调用方从人变成了机器。其余九个方向之所以不够格，原因可以归成两类：**跨源与跨模态的语义边界还没有被解决**（Text-to-SQL 的跨源正确性、向量 / 图 / 多模态进不了关系算子），以及**它们改变的是引擎内部实现而不是外部契约**（向量化执行）——后者可以关注，但不必等它。

对这两类原因，处置方式完全不同，值得分开说：

- **语义边界未解决**：这类方向的正确做法是"绕着走"——跨源自然语言查询先在单源做，多模态检索先用候选集注入做，实时需求先把数据物化到湖仓再查。绕行的代价是少了些自动化，收益是不必赌一个未定型的接口。
- **引擎内部实现**：这类方向的正确做法是"不参与选型"——向量化执行提升的是吞吐上限，不改变下推比例、不改变跨源语义、不改变治理能力。把它写进选型结论，等于用一个与判据无关的维度影响决策。

### 5.2 演进方向逐条拆解（核心节）

每条都写全「旧做法卡点 → 机制改变 → 得到 → 付出 → 证据 → 成熟度」六项，**只要有一项写不出来，就说明这个方向还没有资格被写进路线图**。

这六项里最容易被跳过、也最该被追问的是第四项（付出）。本主题的"付出"尤其容易写漏，因为它有一个共同形态：**把某件事从人身上搬到机器身上，代价就是"出错时没人兜底"**——人写错 SQL 会自己看一遍执行计划，模型写错 SQL 不会。

还有一个贯穿四条方向的判断尺度，值得先说在前面：**这些方向里，几乎没有一个改变了"数据怎么被算出来"**。改的是"谁来发起查询""谁写 SQL""谁来记住下推规则"，而这些都属于接口层与治理层。真正动到引擎语义边界的（向量进优化器、无界输入进关系计划）恰恰是成熟度最低的那两个。**接口层可以放心跟进，语义边界要等证据。**

四条方向读完后，如果只记一件事，记这个先后关系：**网关的治理能力是前置条件，模型能力是后置选项**。同一个模型能力，放在一个有准入、有配额、有语义层的网关上，是效率工具；放在一个没有这些的网关上，是一次放大事故半径的变更。

| 方向 | AI 改变的机制类型 | 一句话判断 |
| --- | :---: | --- |
| 5.2.1 Text-to-SQL + 联邦 | 改变了**人机分工**（谁写 SQL、谁负责正确性） | 接口层的变化，引擎的语义边界没动 |
| 5.2.2 AI 原生 Connector | 试图改变**引擎的表达力** | 关系算子边界没被突破，只多了"候选集注入" |
| 5.2.3 AI 增强查询优化 | 试图把**人的调优经验**换成统计建议 | 只有索引推荐是真机制，另两项是包装 |
| 5.2.4 Agent 与实时联邦 | 改变了**调用方与调用节奏**（人 → 机器） | 治理层的落点是真变化，联邦语义不是 |

#### 5.2.1 Text-to-SQL + 联邦查询：把"写 SQL"的归属换个位置

```text
自然语言 → [模型生成 SQL] → [校验：表/字段是否存在、权限、扫描量] → [联邦执行]
                                     ↑ 这一层是本方向真正的工程重心
                                 没有它，模型的一次幻觉就是一次生产事故
判定方法：给模型一个不存在的表名，看链路是"报错"还是"编一个结果"
```

- **旧做法与它的卡点**：联邦查询的使用门槛是"会写跨源 SQL"——用户要知道每个源的 catalog / schema 命名、知道哪张表在哪个源、知道哪些操作能下推。卡点有三个：
  - 卡点一（人力）：**跨源查询的写法高度依赖少数熟手**，而熟手的产能是恒定成本，查询量增长不会让它变快；
  - 卡点二（发现）：用户往往不知道"要查的东西在哪"，这在 §7.6 组合 1 里被列为数据目录的职责（目录负责"有哪些表、字段是什么、谁能读"），而网关并不持有这份信息；
  - 卡点三（方言）：多源意味着多方言，用户要么学多套方言，要么学一套并被网关的方言边界反复绊倒。
  - 这三个卡点合起来的效果是：**跨源查询的能力被锁在少数人身上**，而这少数人的时间恰好是团队里最贵也最不可扩展的部分。这也是本方向被反复提出的真正动因——不是"想用 AI"，而是"跨源查询的供给跟不上需求"。
- **AI 改变了什么机制**：改变了**人机分工**——把"把意图翻译成 SQL"这件事从人换成了模型。注意它改变的是接口层的分工，**引擎侧的机制一点没动**：下推能力仍然逐连接器协商，跨源 JOIN 仍然要回到网关侧完成（§7.3.1、§7.3.2）。
- **由此得到的**：因为翻译这一步被交给了统计模型，**所以"写 SQL"的门槛下降、但"校验 SQL"的必要性上升**——人写错时会自己复核，模型写错时不会，于是链路上必须显式长出一个校验层：表与字段是否存在、权限是否满足、扫描量是否超阈值。**这个校验层才是本方向真正的工程量**，模型本身反而是最容易替换的部件。
- **由此付出的**：代价有五个，而且都很具体。
  - 第一，**正确性的归属模糊了**：查询错了，是模型的问题、语义层的问题，还是源侧的问题？没有校验层，这个问题无法回答，事故复盘会停在"模型不太行"。
  - 第二，**多出一个不可控的延迟与成本项**：生成 SQL 是一次模型调用，"自然语言查询"的端到端延迟里有一大块与引擎无关。
  - 第三，**方言与语义层成为上限**：模型能写对的前提是它知道表与口径的含义，而这取决于目录与指标定义是否完备（§7.6 组合 1 的职责边界：口径与字段定义归目录侧，网关不持有这份定义，只能依赖它的完备度）——**没有语义层时，Text-to-SQL 的准确率上限由"命名是否自解释"决定**。
  - 第四，**成本结构变了**：一次查询从"引擎成本"变成"引擎成本 + 模型调用成本 + 校验成本"，而这三项由不同团队负责。若不把账单摆在同一张表上（§7.3.1 的成本归属问题），就会出现"查询自由了、账单没人认"的局面。
  - 第五，**它把"查询的可解释性"变薄了一层**：人写 SQL 时，SQL 本身就是意图的证据；模型写 SQL 时，SQL 只是模型对意图的一次猜测，真正的意图留在自然语言里。于是出问题时，你需要同时保存自然语言、生成的 SQL、校验结果与执行计划——**证据链比原来长，而这条链条上任何一环没留，复盘就做不成**。
- **证据与来源**：厂商侧的代表是 Snowflake Cortex Analyst 与 Databricks Genie（同目录 §4.3 已列），本节不对它们的能力做断言，只给判定方法：**查该产品文档里是否标注 GA、是否有第三方（非厂商）的生产案例、是否公开了它的评测口径与 schema 规模**。学术侧的公开评测集是 Spider（EMNLP, 2018）与 BIRD（2023）——**判定方法**：注意它们都是**单库、schema 相对干净**的设定，不测跨源联邦；把单库成绩直接外推到"跨源自然语言查询"是常见的误读。
- **成熟度**：L2——单库场景已有产品化能力与公开评测，跨源场景既没有公开评测也没有第三方生产案例。

#### 5.2.2 AI 原生 Connector：向量 / 知识图谱 / 多模态进联邦的边界

- **旧做法与它的卡点**：多模态检索在网关出现之前是"两个独立调用"——向量库取候选、关系库查明细，由应用在中间拼。卡点在于**拼装逻辑散在应用里**：召回数量、过滤顺序、超时与降级各写一遍，跨团队无法复用，也无法统一治理。
  - 这个卡点常被误判成"接口不统一"，其实它的本质是**治理缺失**：没有一处能回答"全局有谁在调向量库、召回数量分别是多少、谁的超时最长"。接口统一只是让这个问题暴露出来，并不会自动解决它。
- **AI 改变了什么机制**：它试图改变**引擎的表达力**——把"取最相似的 10 条""从 A 走 3 跳到 B"变成 SQL 里可以写出来的东西。但机制上必须说清楚：**SQL 的关系代数只有选择、投影、连接、聚合、集合运算，向量 top-k 与图遍历不在其中**（§7.3.4）。因此这一方向实际发生的是"把两类非关系操作封装成表函数，作为**输入**进入关系计划"，而不是"把向量相似度变成一个可以被优化器重排的普通谓词"。
- **由此得到的**：因为表函数的结果不能在关系计划里被重排，**所以"先过滤再召回"还是"先召回再过滤"这两条路径的成本会有数量级差异（【经验】，具体倍数取决于源侧过滤能下推多少、召回集合有多大），而选择权在写 SQL 的人（或生成 SQL 的模型）手里**——这意味着**召回数量必须被显式限制**（一个"全库 top-k"会把网关与向量库同时拖住），而且这个限制不能只靠使用者的自觉，必须由网关的准入规则强制。Trino + RAG / 向量湖 / GraphRAG 三项，本质都是这一条边界下的具体形态：**检索由向量侧负责召回、由关系侧负责 JOIN 与过滤，网关只做编排与治理**。
- **由此付出的**：代价有五点。
  - 第一，**跨源一致性从"两个关系源的时间差"升级为"不同索引的更新滞后差"**（§7.3.4）——刚写入的文档要等向量索引构建完成才可能被召回，而这一段滞后的语义在关系侧没有对应概念，也没法用 SQL 表达。
  - 第二，**代价模型不同源，优化器无法统一估算**，于是多模态查询的执行顺序往往靠人工写死；一旦没人负责，这条链路出问题时无法归因——"召回了多少条、花了多少时间、是谁决定的"必须有人答。
  - 第三，**它引入了新的失败模式**：向量库不可用时，是整体失败还是降级为纯关系查询？这个决定必须显式写在接口契约里，否则会以"结果偶尔变少"的形态长期潜伏。
  - 第四，**它把"向量库的运维问题"变成了"网关的可用性问题"**：在应用自行拼装的时代，向量库慢只影响那一个应用；接入网关之后，同一条链路上的所有使用者都被同一次抖动影响——这是接口统一必然带来的耦合代价。
  - 第五，**召回质量变成了一个需要被治理的指标**：召回数量、超时阈值、降级策略一旦集中到网关，就必须有人对"召回得好不好"负责；而在分散时代，这件事没人负责，也就没有人抱怨。
- **证据与来源**：**判定方法**——不要采信"支持某向量库联邦查询"的说法，去目标引擎的官方连接器列表里核对是否存在该向量库的连接器（Trino 的连接器清单是公开维护的，[Trino 官方文档, Connectors, 2024]）；若不存在，则需要自行实现引擎的 SPI，或把向量检索放在引擎之外、以候选集形式注入。多模态 Connector 目前看不到公开生产案例，按 L3 处理。
- **成熟度**：向量 / 图谱作为**候选集注入**属 L2（形态可用，但执行不可被优化器重排，需人工定序）；作为**一等关系算子**与**多模态 Connector** 属 L3。

#### 5.2.3 AI 增强查询优化：索引推荐、Join 顺序、计划解释

- **旧做法与它的卡点**：联邦查询的计划质量取决于两件事——优化器有没有正确的代价模型，以及它能不能看到真实的统计信息。卡点在于**后者经常不成立**：
  - 源侧统计信息缺失或过期（连接器拿不到行数、拿不到列的分布），于是 CBO 在错误的基数估计上做决策；
  - 网关侧的优化器并不理解源侧的算子代价（§7.3.2：只要下推成功，代价就由源库执行特征决定，而这不进入网关的成本模型）；
  - 结果是"同一条 SQL 写得不同、性能差出数量级（【经验】）"，而人往往只能靠经验试。
  - 还有一个容易被忽略的事实：**这条链路上的"优化"有两个决策点，而它们在两个地方**——网关侧的算子顺序与下推选择，源侧的索引与统计。任何只优化其中一处的方案，上限都被另一处锁住。
- **AI 改变了什么机制**：把**人的调优经验**换成统计建议。三条里只有一条是真的换了机制：
  - **索引推荐**：本质是"从查询日志里归纳出该建什么索引"，这在数据库领域是既有方向（各家都提供过索引顾问类能力），LLM 的加入改变的是建议的表达方式（自然语言、可解释），**不是可归纳性本身**；
  - **Join 顺序**：CBO 已经在做这件事，模型要做得更好，必须拥有比 CBO 更准的基数估计——**而基数估计的误差来自缺失的统计信息，不是来自算法不够聪明**。模型不能补上不存在的统计，它只能猜；
  - **自然语言查询计划解释**：这是**把执行计划翻译成人话**，是界面改良。它不改变计划质量，只改变人读懂计划的速度。
- **由此得到的**：因为跨源计划差的主因是"源侧统计信息缺失"，**所以引入模型不会改变优化质量的量级**，它改变的只是"人发现问题"的速度——计划解释让一个不熟悉联邦引擎的人也能看出"这条被全表扫了"。
  - 真要把计划质量提上去，动作仍然在源侧：补统计信息、让连接器能提供行数与列分布、把分区裁剪真正下推。这些是工程动作，不是模型动作。
  - 反过来说，**计划解释本身是有真实价值的**：跨源计划的可读性长期很差（一条 SQL 展开成十几层算子，【经验】，具体层数取决于下推比例与连接器的展开方式），能把它翻译成人话，等于把"只有专家能看懂的环节"变成"普通工程师能看懂的环节"。只是要把它定位成**诊断工具**，而不是**优化能力**。
- **由此付出的**：代价有三类。
  - **第一类是误信**：自然语言的解释读起来"很有道理"，但它可以错，而错了不会有人复核——一个错误的计划解释会把人引向错误的优化方向，比没有解释更糟。
  - 第二类是建议的落地风险：如果索引建议直接接入变更流程（自动建索引），那就把一次 DDL 变更的决定权交给了统计判断；正确的落点是**建议 → 人工评审 → 变更**，这与 5.3 接口表里「Agent / LLM → 网关」一行的分工同理：模型负责出建议，决定权留在确定性逻辑（准入层）手里。
  - 第三类更隐蔽：**它会把注意力从"数据布局"引开**。跨源查询慢的根因常常是数据放在了不适合该查询形态的地方（行存 vs 列存、有无分区裁剪），而这需要改数据布局；模型给出的"改一下 SQL 写法"的建议，只是让同一份布局跑得快一点。
- **证据与来源**：本节找不到本主题下"LLM 生成的执行计划在公开评测上稳定优于 CBO"的第三方证据，Join 顺序与计划解释按 L3 处理；索引推荐作为数据库领域的既有方向属 L2，但"LLM 版索引推荐"同样缺第三方对比评测。**判定方法**：要求对方给出"在哪个公开 benchmark、哪个版本、与哪个 CBO 对比、提升是多少"——给不出这四项的，按 L3 处理。
- **成熟度**：索引推荐 L2；Join 顺序 L3；计划解释 L3（它是接口改良，不是架构变化）。

#### 5.2.4 Agent 联邦查询与实时联邦查询：调用方从人变成机器

把 Agent 联邦查询与实时联邦查询合并进同一节，是因为它们在机制上是同一件事的两面：**查询的发起方从人变成了机器**——Agent 是"自动化的发起方"，实时联邦是"机器节奏的发起频率"。两者对网关的压力落在同一处：治理层（准入、配额、超时、审计），而不是引擎的查询能力。

- **旧做法与它的卡点**：网关的准入与配额是围绕人的节奏设计的——分析师一天发几十条查询，偶发的大查询靠人自己收敛。卡点有三个：
  - 并发形态变了：模型生成的 SQL 分布与人类分析师不同（更长、更爱全表扫描，§7.3.3 的失效条件），**"小规模不设配额"的经验不能迁移到开放给 Agent 的场景**；
  - 意外形态变了：人会察觉"这条查不动"，Agent 会在超时后重试，把一次大查询放大成持续的负载。
  - 第三个卡点是**语义层面的**：人提交一条跨源 SQL 时，通常心里知道"这两个源的数据可能对不齐"（§7.3.1：跨源读的是各源各自的当前状态，不构成全局一致快照）；Agent 没有这个直觉，它只会把结果当成事实。
- **AI 改变了什么机制**：改变了**调用方与调用节奏**。对 Agent 取数这一支，它还改变了一件事——**网关从"被人使用的工具"变成"被机器描述的工具"**：Agent 看到的不是 catalogs 与连接器的细节，而是一段能力描述加一个参数（SQL 文本）。这是接口边界的真实变化：**N 个数据源对 Agent 来说是 1 个工具**。
- **由此得到的**：因为 Agent 只会看到"一个工具"，**所以网关必须自己承担原本由人承担的那些判断**——这条查询能不能跑、跑多久、扫多少、要不要拒绝。这就是为什么本方向是本节唯一的 L1：**要落地的机制（准入、配额、超时、审计）在 AI 之前就已 GA**，AI 带来的只是"必须把它做出来"的紧迫性。
  - 判定它到底有没有做好的标准很直接：**把一条明显超量的 SQL 发给网关，看它是被拒绝，还是把整个集群拖慢**。
- **由此付出的**：代价有五个。
  - 第一，**拒绝语义必须成契约**：Agent 拿到"被拒绝"之后应当换写法或放弃，而这要求错误信息足够结构化（是超量、是权限、还是语法），否则模型只会原样重试。
  - 第二，**审计的对象变了**：从"谁查的"变成"哪个 Agent、基于哪个会话、为了回答什么问题查的"；传统的按人审计在这条链路上会失去解释力。
  - 第三是**实时联邦那一支自己的代价**：流式源是无界的，而联邦 JOIN 需要有界输入——把两者拼在一起，要么给流式侧加窗口（这时语义从"持续查询"退化为"按窗口的一次性查询"），要么让 JOIN 两端各自推进（这时"两个源的当前状态"变成了"两个源在各自水位线处的状态"，一致性语义更难解释）。**这正是实时联邦停在 L3 的原因：不是不能做，而是做出来之后你很难向业务解释它到底算的是什么。**
  - 第四，**网关从"被抱怨的对象"变成"要被解释的对象"**：过去查询慢是使用者自己的问题，接入 Agent 之后，配额拒绝会被记成"平台不让用"。这要求治理层把拒绝理由做成可自助查询的形态（谁的配额、还剩多少、怎么申请），否则技术上的正确决定会在组织上被反复推翻。
  - 第五，**"谁在为这条查询付费"变得不清楚**：Agent 的一次任务可能发出几十条查询，成本落在网关集群与各个源上；如果没有按调用方归集的账，容量规划就失去了依据。这不是 AI 带来的新问题，但 AI 把它从"年度盘点"变成了"每月都要看"。
- **证据与来源**：**判定方法**——实时联邦这一支，去目标引擎的连接器清单里核对是否存在该流式源的连接器，以及该连接器是否支持把流读成有界快照；若只支持无界扫描，则它不适合放进联邦 JOIN。Agent 取数这一支的证据形态是第三方案例而非论文（§6 的 9.1 字节案例即属此类）。
- **成熟度**：Agent 取网关作为唯一入口 L1（治理层已 GA、第三方生产案例充分）；Agent 直接写跨源 SQL 属 L2；实时联邦查询 L3。

把这两个方向合并还有一层工程上的好处：它们的失败可以用**同一套观测**解释——配额拒绝率、单查询扫描量分布、超时后的重试率。反过来说，如果一套指标只能解释其中一个方向的失败，说明治理层还没建到能覆盖另一方的程度。这也是 5.3 那张接口表要按"失败归属"而不是按"功能"来列的原因。

### 5.3 与本主题既有栈的接口在哪

不要写「与 X 结合」这类句子，要写清**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。下表的"现状"一列指的是该接口形态在公开实践中的成熟度，不是某一家厂商的能力。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Agent / LLM → 网关 | 工具调用：能力描述 + 一段 SQL，返回结果集或结构化错误 | 网关准入层负责拒绝；模型负责换写法或放弃 | 生产 |
| 网关 → 数据目录 | 元数据 API：表 / 字段 / 口径 / 血缘，供 schema 检索与校验 | 目录侧；网关可降级为仅表名匹配 | 生产（§6 案例） |
| 网关 → 向量库 / 图库 | 表函数返回**候选主键**，关系侧再做 JOIN 与过滤 | 编排层（应用）；非关系算子不参与关系优化 | 试点 |
| 网关 → 权限与策略 | 查询改写注入行 / 列过滤，编译期校验 | 网关；拒绝即闭环 | 生产 |
| 网关 → 物化视图 / 缓存 | 版本号进入缓存 key，命中即返回 | 应用负责失效 | 试点 |
| 流式源 → 网关 | 有界快照（按时间窗），而非持续查询 | 查询方必须给出窗口；给不出则拒绝 | 观望 |

这张表里有三处是真边界变化，值得单独点出：

1. **第一行**：网关对上层不再暴露"连接"与"方言"，只暴露一个能力与一段 SQL。这是本节唯一被 AI 实质改变的接口——**它把数据源的数量从 Agent 的视野里隐藏了**。
2. **第三行**：向量 / 图以候选集形态穿过边界，**且必须携带召回数量与耗时**，否则这条链路无法归因（5.2.2 的第二类代价）。
3. **第六行**：流式源必须以有界形态穿过边界，否则它把"无界输入"带进了关系计划，而关系计划没有表达无界的算子。

把边界上的失败按类型拆开，责任归属就清楚了：

| 失败类型 | 落在哪一侧 | 对架构的直接影响 |
| --- | --- | --- |
| 生成失败（模型写错表名 / 写错方言） | 校验层（若存在）；否则落到引擎报错 | 校验层缺失时，错误会以"引擎语法错误"的形态暴露，用户无法自助 |
| 准入失败（扫描量 / 并发超限） | 网关，且必须返回**结构化**错误 | 错误不结构化时，Agent 只会原样重试，负载被放大 |
| 下推失败（本该下推的算子没下推） | 引擎与连接器；表现为网关侧数据搬运 | 需要能看见"哪些算子没下推"，否则性能问题无法归因（§7.3.2） |
| 非关系算子失败（向量 / 图不可用） | 编排层（应用），且必须显式选择降级或失败 | 不显式选择，就会以"结果偶尔变少"的形态长期潜伏 |

这四行对应四种不同的返工成本：第二、四行是接口契约问题，改动便宜但要早做；第一行是校验层缺失，越晚补越贵；第三行是能力问题，只能靠补统计信息与换连接器解决——**它没有模型侧的解法**。

最后补一句关于"现状"一列该怎么用：**它是接口形态的成熟度，不是你的架构成熟度**。同一个"网关 → 权限与策略"的接口，在已经有统一权限体系的组织里是生产级，在没有权限体系、只能按库授权的地方就只是"纸面存在"。评估自己时，把这一列替换成你的实际形态，再决定要不要现在做。

**第三方生产案例**

本节对这一类做一句实话交代：**能公开找到的、专门针对"AI 负载下的联邦查询"的第三方案例仍然稀少**。可引用的是"既有网关体系承接了新业务"这一形态（§6 的四个案例都属于此类：字节的 Trino 联邦网关、阿里的 OneService、美团的统一网关、某 SaaS 的多租户网关）。这不影响 5.1 的判级——判 L1 用的是"该机制本身有没有第三方生产案例"，而不是"AI 特有用法有没有案例"；后者的数量在现阶段还不足以支撑任何判级，这也是本节把 AI 特有用法普遍压在 L2 / L3 的原因。

**需要读者自行核验的厂商进展**

本节列了 7 条（Trino 特定版本号的 Iceberg 物化视图与向量化执行、Starburst Galaxy、Dremio Sonar、Trino + Velox、Apache Gluten、Snowflake Cortex Analyst、Databricks Genie）。这些是**产品能力名与版本条目**，本节不替它们背书，只给判定方法：**查三件事——该能力在哪个版本进入 GA（而不是"预览"）、它对外暴露的语义写在哪一节、有没有第三方生产案例**。特别提醒版本号：Trino 采用按月发布、版本号连续的节奏，因此**"某版本支持某特性"必须以 release note 为准，而不是以博客文章里的年份为准**——年份相近的版本号可以相差几十个。三者缺一，按 L2 处理；只出现在发布会页面或路线图里的，按 L3 处理。

为什么本节宁可把这 7 条降格成"待核验"，也不直接引用？因为本主题是全书里**产品名与能力名最容易张冠李戴**的一类：一个能力常被记成某个产品的专属名（自然语言查询、向量化执行、湖仓物化视图各有多个产品在做），而版本号又变化极快。在无法逐条核对 release note 的前提下，把"某产品支持某特性"写成结论，风险远大于收益。**改写成"判定方法"之后，这句话对读者仍然有用——它把核验动作交给了最有能力做这件事的人。**

### 5.5 被过度宣传的部分

**说法 1：「自然语言查询会取代写 SQL」**

- **实际是什么**：它取代的是"把意图翻译成 SQL"这一步的**人力**，没有取代 SQL 本身——下推、方言边界、跨源 JOIN 的语义都还在原地（§7.3.1、§7.3.2）。而且公开评测集都是单库设定，跨源场景没有公开成绩。
- **为什么会这样**：瓶颈不在语言生成，在**schema 与语义层的完备度**——模型要选对表、选对口径，前提是有人把表与口径的含义写成了机器可读的形态（这正是 §7.6 组合 1 划给数据目录与指标平台的职责：目录负责"有哪些表、字段是什么、谁能读"，网关只负责按这些元数据执行）。没有这一层，模型只能靠表名的字面猜测。
- **什么时候它才会成真**：出现**跨源、多方言**的公开评测集，并且有第三方在其上给出可复现的成绩。在那之前，"能用"的边界应当写清楚：单源、或已有语义层覆盖的那部分源。
- **怎么用这条判断**：立项时把问题拆成两问——"我们的源里有几个已经有语义层"、"生成的 SQL 由谁校验"。这两个答案决定了这件事现在能不能做，而不是模型选哪个版本。
- 一句话概括这条：**它改变的是接口层的人机分工，不是引擎的语义边界**；因此它的成败由语义层与校验层决定，这两样都得你自己建。

**说法 2：「向量库与图库接进联邦 SQL，一条 SQL 就能搞定多模态检索」**

- **实际是什么**：向量 top-k 与图遍历不是关系算子，它们只能以表函数形态作为**输入**进入关系计划，执行不能被关系优化器重排（§7.3.4）。这意味着"一条 SQL"在工程上仍是"网关编排两次调用、向量侧负责召回、关系侧负责 JOIN 与过滤"。
- **为什么会这样**：关系代数的算子集合里没有"取最相似的 k 条"和"走 3 跳"；而要让优化器重排它们，必须同时给出代价模型与下推规则，这两样目前都不存在。
- **什么时候它才会成真**：某个主流引擎把向量召回写成**可被优化器重排的物理算子**，并在 release note 里给出它的代价模型与下推条件。判定方法：现在就去它的连接器与算子清单里查有没有这样一个算子——只有表函数与外部函数的，就还在这一档。
- **怎么用这条判断**：把"多模态检索"拆成"召回"与"关联"两段分别验收——召回段看召回率与延迟，关联段看 JOIN 结果正确性。两段混在一个"一条 SQL 搞定"的目标里，出问题时无法定位是哪一段坏了。

**说法 3：「LLM 会优化查询计划」**

- **实际是什么**：跨源计划差的主因是**源侧统计信息缺失或过期**，不是优化算法不够聪明（5.2.3）。模型补不上不存在的统计，它只能猜；而模型猜出来的基数估计并不比 CBO 的估算更准。
- **为什么会这样**：代价模型需要的是"这张表有多少行、这列有多少个不同值"，这是数据侧的事实；模型手里只有 SQL 文本与表名。
- **什么时候它才会成真**：出现"用同一批 SQL、同一个引擎版本、在公开数据上与 CBO 对比、且结果可复现"的第三方评测。在此之前，把 LLM 用在这条路径上的正确位置是**解释与建议**（计划解释、索引建议），而不是**替代优化器做决策**。
- **怎么用这条判断**：把"优化"这个动作按决策点分开——源侧的统计与索引归 DBA / 数据工程，网关侧的下推与算子顺序归平台团队。凡是宣称能同时改善两端的方案，追问它在哪一端有可测量的证据。

### 5.6 未来 3–5 年：可证伪的预测

预测必须写成「预测 + 会成真的信号 + 会证伪的信号」；写不出信号的预测不要写，因为它无法被检验，也就不带信息量。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 1. 到 2028 年，Agent 取数的默认形态是**经过网关**，而不是让 Agent 直连各个数据源 | 主流 Agent 框架 / 平台把"查询网关"列为首选数据连接器，权限与配额在网关侧配置 | Agent 生态里"直连单库"的连接器数量与使用量持续高于网关入口 |
| 2. 跨源自然语言查询的准确率提升，主要来自**语义层与 schema 检索**，而不是模型本身 | 厂商发布与案例介绍时强调语义层 / 指标定义 / schema 检索，模型版本是次要变量 | 无语义层的纯模型方案在跨源评测上追平带语义层的方案 |
| 3. 向量与图会固化为**引擎外的独立调用**（或表函数），不会变成联邦 SQL 里可被优化器重排的一等算子 | 主流引擎文档里向量以表函数 / 外部函数形态出现，且不在 CBO 的算子清单中 | 某主流引擎把向量召回写成可被优化器重排的物理算子，并公开其代价模型 |
| 4. 实时联邦的落地形态是**先物化到湖仓再由网关查询**，而不是网关对流式源直接做跨源 JOIN | 公开案例中反复出现"流批一体入湖 + 网关查询"的组合 | 出现公开的、生产规模的、对流式源做跨源 JOIN 的案例并说明其一致性语义 |

读这四条的方法：**它们的证伪信号都比成真信号更容易观测**。这不是巧合——本主题的特点是，新能力大多落在"接口层与治理层"，而**引擎的语义边界（关系算子集合、逐源协商的下推）很少被真正推开**；因此预测的默认值是"边界不变、落点变化"，第 3 条尤其如此。第 4 条是四条里最容易被推翻的一条，因为它只要一个反例就够——但恰恰也是它，缺公开案例的时间最长。

每条预测背后的依据分别是：第 1 条依据的是"治理必须有一个落脚点"——把配额与审计分散到每个数据源侧，成本随源数量线性增长，而收在一处是常数级的；第 2 条依据的是 5.2.1 的卡点三（模型要知道表与口径的含义）；第 3 条依据的是 §7.3.4 的算子边界，它没有随时间松动；第 4 条依据的是"无界输入进不了关系计划"这一条纯机制推论。**四条里只有第 1 条是趋势判断，其余三条都是机制推论**——这也是判断本节是否可信的一个自检点：预测里机制推论的比例越高，这份评估越不容易过期。

还可以用这四条做一次反向自检：如果两年后第 1 条与第 3 条同时被证伪，意味着"网关"这一层的价值判断需要重写；如果只有第 4 条被证伪，那只是流式引擎补上了自己的短板，本节的其余结论不受影响。**把预测按"被证伪后影响多大"排序，比按"可能性多大"排序更有用**，因为前者决定你要盯着哪一条看。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 网关刚上线、使用者是人 | 把扫描量上限、并发上限、超时做成显式配置（§7.3.3） | 是否有负载开始呈现"机器节奏" | 不要在没人配配额的情况下把网关开放给 Agent |
| 准备把网关接给 Agent | 先定义结构化错误（超量 / 权限 / 语法），再放开 | Agent 侧是否能正确消费这些错误 | 不要指望模型自己学会"这条查询不该发" |
| 想做自然语言查询 | 先在已有语义层的单源范围内做，把校验层建起来 | 跨源公开评测集是否出现 | 不要在没有语义层、也没有校验层时对业务承诺准确率 |
| 业务要求"一条 SQL 查向量 + 关系" | 用候选集注入形态，把召回数量写成准入规则 | 主流引擎是否给出向量算子的代价模型 | 不要让网关承担跨模态 JOIN 的语义责任 |
| 想做实时联邦 | 先把流式数据物化到湖仓，用有界查询覆盖绝大多数需求 | 流式连接器是否支持有界快照 | 不要把无界输入接进关系计划，也不要先承诺"实时"再解释语义 |
| 想上 AI 优化器 | 先补源侧统计信息（行数、列分布、分区裁剪） | 是否出现与 CBO 的公开对比评测 | 不要用自然语言解释替代对执行计划的核对 |

「明确不要做」这一列是本节的重点：上表要避免的动作有一个共同点——**它们都把"人原本要承担的判断"直接交给了模型**，而在跨源这个场景里，那些判断（这条查询该不该发、这个源能不能下推、召回多少条合适）恰恰是工程上唯一可靠的部分。

按投入排序，本主题的行动顺序也是三件：**先把治理层做出来**（准入、配额、超时，以及能被 Agent 消费的结构化错误）→ **再把语义层接通**（让网关能拿到表、字段、口径的机器可读定义，这是自然语言查询的前提）→ **最后才谈多模态与实时**。顺序反过来做，会先得到"很能演示、很难上线"的系统。

判断某件事该不该现在做，通用口径有两条：

- 它是否依赖一个**尚未稳定的接口**？是，就等到接口稳定再做——向量进优化器、多模态 Connector、实时联邦都属于此类。
- 它是否在修一个**现在并不存在的问题**？如果跨源查询量还很小、也没有 Agent 在用，那么先把配额与审计建起来只是提前支出复杂度。

如果只允许做一件事，做第一件：**把"被拒绝"变成一次可被机器理解的结果**。它同时解决两个问题——让 Agent 不至于把超量查询反复重发，也让平台侧第一次有了可统计的拒绝率；而它是网关治理里最便宜、见效最快的一环。

### 5.8 小结

> 本节小结：AI 在本主题下真正改变的**唯一那条机制**是「把 N 个数据源对上层收成 1 个入口」这件事的**归属**——以前靠人记住哪个表在哪个源、哪个操作能不能下推，现在由一个能力描述加一段 SQL 替代，于是原本由人承担的判断必须由网关的准入、配额、审计接管。它**没有改变**的是引擎的语义边界：下推仍逐连接器协商、跨源 JOIN 仍要回到网关侧、向量与图仍进不了关系算子集合。因此本主题下现在就能排进路线图的只有一件——把网关作为 Agent 的唯一取数入口并补齐治理层；其余（跨源 Text-to-SQL、向量进优化器、LLM 优化计划、实时联邦）都还在观望区。
