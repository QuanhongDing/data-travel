## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表用 1–5 分给「数据新鲜度 / 跨源 JOIN / 性能 / 存储成本 / 灵活性 / AI 集成 / 工程复杂度」打分，把 ETL 同步、数据复制、联邦查询、统一查询网关排成一列。这张表的问题不是数字不准，而是**每个维度的分数取决于场景，打分却把它写成了绝对结论**：

- 「性能 5 分」对 ETL 同步意味着「查询时不存在跨源 JOIN，因为已物化」；对联邦查询意味着「下推比例高时接近本地查询」。同一个 5 分，前提完全不同。
- 「存储成本」在 ETL 路线里是**一次性的副本成本**，在联邦路线里是**每次查询都要付的源库负载成本**。两者不是同一种成本，放进同一列打分，比出来的差值没有含义。
- 「AI 集成」在打分表里靠印象给分，没说清机制。真实原因是：**LLM 无法事先知道该同步哪些表**，所以它需要一个「能在查询时才知道要读哪里」的入口——这是**规划权归属**的问题，与接口数量无关。

更根本的一点：**打分把「多维权衡」压成「加权求和」，而工程选型里的关键条件大多是「一票否决」**。生产库不允许承接分析查询是一条硬约束，它不会因为「灵活性 4 分」而被抵消。所以本章先立判据，再谈分数。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 下推能力边界 | 我的查询里有多大比例能被下推到源侧执行 | 联邦路线的成本正比于「被搬到网关侧的行数」，下推比例直接决定它能不能用 |
| 成本随什么增长 | 成本随数据量 × 副本数增长，还是随查询次数 × 扫描量增长 | 前者的预算是确定的（可规划），后者随业务查询行为漂移（不可规划），决定了走资本支出还是运营支出 |
| 一致性模型 | 我能否接受跨源结果不是同一时刻的快照 | 联邦天然是「读时读多个源的当前状态」，若业务要求同刻一致，联邦在语义上做不到，不是调优问题 |
| 源侧影响 | 我的生产库能不能承接分析负载 | 下推把计算放到源侧是**必然结果**，不是可选项；源侧顶不住就必须先复制，路线会退化 |
| 语义表达力 | 向量、图、半结构化能否用关系算子表达 | 决定了「单 SQL 跨源 + 向量 + 图」是可用能力，还是只能在演示里跑的营销词 |
| 运维与人 | 谁维护 coordinator / 权限 / 审计，需要几个专职人 | 联邦集群是常驻服务，不是一次性项目；没有常驻人力时，它的故障恢复时间会超过业务容忍度 |

**同一个维度在不同规模下权重相反**，这是打分表最容易掩盖的一点：

| 维度 | 在「几个分析师、单一团队」时 | 在「多业务、上千查询人」时 |
| --- | --- | --- |
| 工程复杂度 | 权重最高：复杂度直接吃掉全部收益 | 权重下降：复杂度是固定成本，被规模摊薄 |
| 权限与审计 | 权重最低：谁查了什么心里有数 | 权重最高：没有审计就无法对监管与内部合规交代 |
| 灵活性（随时改口径） | 权重高：探索期需要快速试错 | 权重下降：口径必须固化，否则跨团队对不上账 |
| 新鲜度 | 常常不重要：T+1 够用 | 可能变成硬要求：实时看板驱动业务动作 |

所以本章只保留一种「排序」：**在给定处境下，按判据逐条排除**（7.5 决策树），而不是把六个候选压成一个总分。若某个候选在某条判据上不满足，它在该处境下直接出局，不参与加权。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 1. **ETL 同步** | 把多个源的数据抽取、转换后写入一个目标存储 | **写时转换**：在数据落地前完成 JOIN 与清洗，查询只读一份物化结果 | 传统数仓团队（Hive / Spark 批处理）、指标平台 | 自行开发或商业 ETL 工具，成本随数据量与调度频次增长 |
| 2. **数据复制（CDC）** | 把源库的变更持续同步到目标存储 | **写时转换 + 准实时**：用 binlog / WAL 捕获变更，延迟从小时级压到秒–分钟级 | 需要报表近实时的团队、湖仓入湖链路 | 开源（Debezium、Flink CDC）或云托管服务 |
| 3. **物化视图 / 预计算表** | 把高频查询的结果预先算好存下来 | **用存储换查询时间**：把「重复计算」变成「一次计算 + 多次读取」，含湖仓内的物化表 | 指标平台、BI 加速层 | 引擎内置能力（各数仓 / 湖仓均提供），成本随「物化的组合数」增长 |
| 4. **联邦查询引擎（裸用 Trino / Presto）** | 用一条 SQL 读多个源的当前数据，不搬数据 | **读时转换 + 下推**：优化器决定哪些算子留在源侧、哪些拉到引擎侧执行 | 数据平台团队（交互式分析、数据探索） | Trino / Presto 为 Apache 2.0 开源；Facebook 于 2013 年开源 Presto（[Facebook Engineering, 2013]），PrestoSQL 于 2020 年 12 月更名为 Trino（[Trino 官方公告, 2020]） |
| 5. **商业数据虚拟化平台（Denodo / Dremio）** | 在多个源之上建一层逻辑语义层，面向 BI 与自助分析 | **逻辑视图 + 缓存 + 下推**：把物理位置隐藏在一个可治理的语义层后面 | 大型企业的 BI / 报表体系、受监管行业 | 商业闭源（Denodo）；Dremio 提供社区版与商业版；Starburst 是 Trino 的商业发行版 |
| 6. **统一查询网关** | 在联邦引擎之上再叠一层统一入口：目录、权限、配额、审计、AI 接入 | **联邦 + 治理层**：把「能查通」升级为「谁能查、能查多少、查了什么有记录」 | 多业务集团的统一查询入口、Agent 取数入口 | 自建（基于 Trino / Calcite）为主，能力可产品化 |

这 6 个候选其实只有**三族**：**写时物化族**（1、2、3）、**读时联邦族**（4、5）、以及**作为治理外壳存在的网关**（6 跨了前两族）。同族内部差异小（ETL 与 CDC 只差延迟与实现方式；物化视图只是把「同步频次」换成了「刷新策略」），跨族差异才是根本的：**数据在写的时候被转换，还是在读的时候被转换**。先分族再选，能省掉一半比较。

按判据看三族的分野，比逐候选打分更清楚：

| 判据 | 写时物化族 | 读时联邦族 | 治理外壳（网关） |
| --- | --- | --- | --- |
| 下推能力边界 | 不适用：查询时没有跨源 JOIN | 决定性：下推比例 = 可用性 | 继承联邦族，另加准入过滤 |
| 成本随什么增长 | 数据量 × 副本数 | 查询次数 × 扫描量 | 前者 + 治理层人力 |
| 一致性模型 | 目标是同刻一致（一次转换、一次落库） | 只能是「各源当前状态」（7.3.1） | 继承联邦族，可用缓存做局部收敛 |
| 源侧影响 | 抽取窗口内的读压力 | 查询时的读 + 下推算子的执行压力 | 由准入与配额限制影响上限 |
| 语义表达力 | 关系算子（转换在 ETL 里做） | 关系算子 + 自定算子 | 不改变表达力，只做封装 |
| 运维与人 | 调度与数据质量体系 | 常驻集群 + 连接器排障 | 再叠加权限、配额、审计 |

**读这张表的方法**：如果第 1 行与第 2 行就让你出局（跨源 JOIN 无法下推、或查询次数不可预估），不要再看后面几行——后面的维度只是在胜出的族里挑实现。

### 7.3 机制差异：为什么它们表现不同（核心节）

本节用 4 个机制维度解释「为什么六个候选的表现不同」，每个维度都按同一套结构写：机制是什么 → 各候选的实现差异 → 必然导出的性质（因为 A，所以 B）→ 公开证据或判定方法 → 什么条件下该机制的优势消失。**读法建议**：如果时间只够读一节，读 7.3.1，它决定了族的选择；其余三节决定族内选谁。

#### 7.3.1 写时转换 vs 读时转换：成本被挪到了哪个时刻

**机制是什么**：一条跨源查询的代价，可以付在「数据落地的时刻」（写时转换），也可以付在「用户提交查询的时刻」（读时转换）。二者不是快慢之别，而是**代价被记在谁账上**的区别。

**它在各候选中的实现差异**：

| 候选 | 转换发生在 | 谁承担代价 | 查询侧付出什么 |
| --- | --- | --- | --- |
| ETL 同步 | 调度窗口内 | 数仓团队（计算 + 存储 + 调度运维） | 只读一份物化表，代价最低，但新鲜度差一个调度周期 |
| 数据复制（CDC） | 变更发生时 | 源库 + 复制链路 + 目标存储 | 同上，新鲜度好，但目标存储必须能承接变更流 |
| 物化视图 | 刷新策略触发时 | 数仓团队（存储 + 刷新计算） | 最快，但只对「被物化过的那个查询形态」快 |
| 联邦查询 / 网关 | 用户提交查询时 | 用查询的人 + 源库 + 网关集群 | 新鲜（读的是源的当前状态），代价是每次查都在重算 |

**由此必然导出的性质**：

- **因为 ETL 是写时转换，所以它的查询成本几乎与查询次数无关，而它的新鲜度上限被调度周期锁死**——想更实时只能缩短调度周期，于是「同步频次」成为成本函数的主导变量。
- **因为联邦是读时转换，所以它的新鲜度天然最好（读到的是源的当前状态），但每一次重复查询都要重新付一遍下推与汇聚的代价**——于是「同一查询的重复次数」成为成本函数的主导变量。这就是同一套数据上「物化视图」与「联邦」永远并存的原因：它们优化的是成本函数里不同的项。
- **因为联邦跨源读的是多个源各自的当前状态，所以跨源 JOIN 的结果不构成一个全局一致的快照**——A 源读到的是 T 时刻，B 源读到的是 T+ε。这不是 bug，是「不搬数据」的必然代价；对账类场景要求同刻一致时，只能先物化到一处再算。
- **因为写时转换的产物是一份可被反复读取的物化结果，所以它天然可复现**——同样的查询在今天和明天得到相同的答案（前提是没重跑）。反之，读时转换的答案是「查询那一刻各源状态的组合」，**同一个查询在不同时间跑出不同结果不是数据出错，而是机制使然**。因此凡是需要「数字可复算、可对账、可审计」的场景，物化是唯一能给出这个保证的路线。
- **因为两条路线的成本被记在不同人的账上，所以「哪条更便宜」在这两个团队之间永远吵不出结论**——ETL 团队看到的是自己的计算与存储账单，查询团队看到的是自己的等待时间，而源库 DBA 看到的是自己被占用的 IO。选型时要把三方账单摆在同一张表上，否则会得出「各自都很有理」的假结论。

**公开证据**：Trino 官方文档把「Pushdown」列为连接器能力的一部分，并明确说明能力由各连接器提供（[Trino 官方文档, Connector / Pushdown 章节, 2024]）——这正说明下推不是引擎的普遍保证，而是逐源协商的结果。Apache Calcite 官方定位为「SQL 解析、校验与优化的框架」，本身不存数据（[Apache Calcite 官网, 2024]），说明「联邦」在工程上就是「规划器 + 一堆适配器」：**判定方法**：当你听到「我们做了数据虚拟化」时，问一句「优化器是谁、连接器有几个、下推能力表在哪」，就能区分它是真联邦还是给 ETL 换了个名字。

**失效条件**：当一层数据的重复查询次数很低（例如探索型分析、一次性归因），写时转换的固定成本摊不掉，读时转换必然更划算；反之当同一查询形态被每天重复上千次，读时转换就变成了持续付费，物化更便宜。**判据的量化形式是「重复次数 × 单次读时代价」与「一次写时代价 + 存储持有成本」的比较**，重复次数是唯一需要估的变量，而它可以从查询日志里数出来。

#### 7.3.2 下推与汇聚：网络传输量由什么决定

**机制是什么**：联邦查询的传输量 ≈ 「无法下推的行数 × 行宽」。下推是逐算子协商的：过滤、投影、LIMIT 通常能下推，跨源 JOIN、跨源聚合通常不能完整下推。

**它在各候选中的实现差异**：

- **能在源侧完成的**：单源过滤、投影、LIMIT、部分聚合（取决于连接器的实现程度）。
- **必须回到网关侧完成的**：跨源 JOIN 的构建侧与探测侧、跨源 GROUP BY、需要多源数据的窗口函数。
- **向量与图**：向量 top-k 检索与多跳图遍历**不是关系算子**，标准 SQL 没有对应表达（见 7.3.4）。

**由此必然导出的性质**：

- **因为过滤条件能否下推决定网关侧要接收的行数，所以「同一条 SQL 写得不同」会有数量级的性能差异**——`WHERE dt='2026-10-01'` 能下推的分区裁剪，与在网关侧对全表做 `WHERE`，成本不在一个量级。这不是调优技巧，而是机制的必然。
- **因为跨源 JOIN 必须把两侧数据搬到网关侧的内存里做，所以网关的可用性上限由「最坏那一条 SQL 的扫描量」决定，而不是由平均查询决定**——这就是网关必须做查询准入（扫描量上限、并发上限、超时）的原因：没有准入，一条误写的 SQL 能影响所有人。
- **因为下推能力逐连接器协商，所以「换一个数据源」不是零成本**——新源的连接器若不支持下推，同一条 SQL 会突然从「秒级」变成「扫全量」。这也意味着**「联邦查询的性能」不是引擎的属性，而是「引擎 + 你恰好用到的那几个连接器」的属性**，把性能写进选型结论时必须带上数据源清单。
- **因为列存格式的表能只读需要的列、并且能用统计信息（分区、文件级 min/max）先裁掉不必要的数据，所以同为「不能下推」，列存源与行存源在网关侧收到的数据量可以差一个量级**——这解释了一个常见现象：把同一条 SQL 从 Hive 换到表格式（Iceberg 等）后，没改一个字符却快了很多。**判定方法**：不要采信「引擎升级带来提速」，先看是不是数据从行存换成了列存、或从无统计信息换成了有统计信息。
- **因为跨源聚合往往只能部分下推，所以「先 JOIN 再聚合」与「各自聚合再合并」两种写法在高基数场景下结果可能不同**——前者在网关侧对明细做聚合，后者在源侧预聚合。这不是性能问题，而是**语义问题**：去重类指标（UV 等）不能被拆到多个源各自算完再相加。**判定方法**：把指标按「可加 / 不可加」分类，不可加指标必须回到单一事实来源计算，不能靠联邦把两侧结果拼起来。

**公开证据**：Trino 官方文档按连接器逐项列出其所支持的谓词下推、聚合下推能力（[Trino 官方文档, Connector 章节, 2024]）——**判定方法**：选型前把你最重的 5 条 SQL 拿到目标连接器的能力表上逐算子核对，凡是标「不支持」的算子，都会变成网关侧的数据搬运。Trino 支持 worker 侧 spill（写磁盘），所以大 JOIN 不必然 OOM，但会退化为磁盘 IO（[Trino 官方文档, Memory Management / Spill, 2024]）。

**失效条件**：当业务查询以「多源全量明细关联」为主（数仓式的宽表构建），下推的比例会很低，此时联邦退化成「用分布式引擎做一次昂贵的 ETL」，直接物化更便宜。另一个失效条件是**源侧算子太慢**：即便下推成功，如果源库对下推的聚合执行得比网关侧还慢（例如源库是弱配置的 OLTP），下推反而更长——此时需要能显式关闭该类下推的开关，这是选型时要核验的一项能力。

#### 7.3.3 规划与调度集中在哪里：并发上限由谁决定

**机制是什么**：联邦引擎的规划、调度与资源分配发生在协调者角色上（Trino 的 coordinator），执行发生在 worker 上。协调者保存着每个查询的规划结果与调度状态，因此它是**并发状态的有界容器**。

**它在各候选中的实现差异**：

| 形态 | 规划与调度 | 并发上限的约束来自 |
| --- | --- | --- |
| 批处理 ETL | 调度器（Airflow / 自研）按时间触发 | 调度器与集群容量，与在线请求无关 |
| 复制链路 | 流式作业常驻 | 目标存储的写入吞吐 |
| 联邦引擎（Trino） | coordinator 规划 + 调度，worker 执行 | coordinator 的内存与队列、资源组的配额、worker 的可用内存 |
| 网关（联邦 + 治理层） | 同上，外加一层准入与配额 | 多一层准入反而提高了上限的可控性 |

**由此必然导出的性质**：

- **因为规划状态集中在协调者，所以并发上限是被显式配置出来的，不是被硬件自然给出来的**——Trino 提供 resource group 与并发上限这类旋钮，存在本身就说明「无序接收查询」会打垮协调者（[Trino 官方文档, Resource Groups, 2024]）。
- **因为联邦引擎为「交互式、低延迟」设计，所以它擅长的是「大量中小查询并行」，而不是「单条扫描 TB 级的离线作业」**——后者的资源形态（长时间占用大块内存与网络）会与前者争抢同一批 worker。这直接决定了两类负载必须分成不同的资源组或不同的集群。
- **因为网关多了一层准入，所以它把「不可控的并发」变成了「可配额的并发」**——这不是性能优化，而是**可用性工程**：一票否决型判据（第 6 条判据「运维与人」）在这里落地。
- **因为长查询与短查询共享同一批 worker，所以「有没有把两类负载分开」比「集群有多大」更能决定交互式查询的体感**——一条扫描量巨大的长查询会占住内存与网络，短查询即便下推完美也要排队。**因此资源组（或独立集群）不是运维细节，而是选型的必要条件**：评估一个联邦方案时，要问的第二个问题是「它如何隔离长短查询」，第一个是「它支不支持配额」。
- **因为规划状态在协调者上、执行状态在 worker 上，所以两类故障的恢复方式不同**：worker 挂掉可以通过重跑该分片恢复，协调者挂掉则意味着**所有在跑的查询一起失败**。这决定了网关的部署形态必须是「协调者可快速重建 + 查询可重试」，而不能是「协调者单点且不可重启」。

**公开证据**：Trino 官方文档把 Fault-tolerant execution 作为独立主题描述，用 exchange 管理器接管中间结果的持久化，让 worker 失败后查询可以继续（[Trino 官方文档, Fault-tolerant execution, 2024]）——**判定方法**：如果你的负载里有长查询且集群需要滚动升级，就去文档里核对这一能力是否已在你的版本中可用，而不是假设「分布式引擎天然容错」。同理，资源组与并发上限的存在本身就是「协调者是有界资源」的官方承认（[Trino 官方文档, Resource Groups, 2024]）。

**失效条件**：当并发很低（例如只有几十个分析师在用）时，协调者不是瓶颈，做配额与资源组的收益低于其复杂度——此时简单配置反而是对的，但**「小规模不设配额」的经验不能迁移到开放给 Agent 的场景**：LLM 生成的 SQL 分布与人类分析师完全不同（更长、更爱全表扫描），这是量变引起质变的典型位置。

#### 7.3.4 关系语义的边界：为什么向量与图进不了同一个 JOIN

**机制是什么**：SQL 的关系代数只有选择、投影、连接、聚合、集合运算这些算子。「取最相似的 10 条」「从 A 出发走 3 跳到 B」不在其中——它们需要自定义算子与对应索引。

**它在各候选中的实现差异**：

- **关系源**（MySQL / Hive / Iceberg / 对象存储上的表格式）：标准算子可表达，下推与优化成熟。
- **向量库**（Milvus / Pinecone 等）：核心操作是「按距离取 top-k」，需要向量索引支撑，不是关系算子。
- **图库**（Neo4j 等）：核心操作是「按边遍历」，需要邻接索引支撑，也不是关系算子。
- **网关的常见做法**：把这两类封装成表函数 / 自定义算子接入，使它们能作为**输入**进入关系计划，但它们的执行不能被关系优化器重排。

**由此必然导出的性质**：

- **因为向量 top-k 与图遍历不是关系算子，所以「单 SQL 跨源 + 向量 + 图」在工程上通常是「网关负责关系侧 JOIN，向量召回作为候选集注入」**——把向量检索当成一个能返回候选主键的表函数，再与关系表 JOIN。任何宣称能把向量相似度当普通谓词参与全局优化的说法，都应该要求对方给出执行计划来验证。
- **因为表函数的结果不能在关系计划里被重排，所以「先过滤再向量召回」还是「先召回再过滤」这两条路径的成本可能差一个量级**——召回数量必须被显式限制（否则一个「全库 top-k」会把网关和向量库同时拖住）。
- **因为向量与图各有自己的索引与一致性模型，所以它们加入联邦后，跨源一致性问题从「两个关系源的时间差」升级为「不同索引的更新滞后差」**——一个刚写入的文档可能需要等待其向量索引构建完成，才可能被召回。这是「读时转换」在多模态场景下的新形态。
- **因为向量检索的代价主要由「索引规模 × 召回数量」决定，而这与 SQL 里其他算子的代价模型不同源，所以优化器无法对它做统一的成本估算**——结果就是：多模态查询的执行计划往往要靠人工写死顺序，而不是靠 CBO 自动选出。**这直接影响选型的可运维性**：谁来为「召回了多少条、花了多少时间」负责？如果没人，这条链路在出问题时无法归因。

**公开证据**：Trino 的连接器清单是公开维护的（[Trino 官方文档, Connectors 列表, 2024]）。**判定方法**：不要采信「支持某向量库联邦查询」的说法，去目标引擎的官方连接器列表里核对是否存在该向量库的连接器；若不存在，则需要自行实现引擎的 SPI，或把向量检索放在引擎之外、以候选集的形式注入。

**失效条件**：当 AI 场景其实只需要「结构化检索 + 一个独立的向量召回服务」时，硬把向量塞进联邦 SQL 层只会增加一层不可解释的延迟；此时正确的做法是让 Agent 编排两次调用，而不是让网关做一次跨模态 JOIN。

### 7.4 成本结构对比（不是价格表，是成本函数）

六个候选的成本都可以写成同一个骨架，差别在于**哪一项是主导项**：

```
总成本 ≈ 固定成本(集群/人力) + f(数据量 × 副本数) + g(查询次数 × 扫描量) + h(元数据对象数/维护项数)
```

| 候选 | 主导项 | 隐性成本（常被漏算） |
| --- | --- | --- |
| ETL 同步 | **f(数据量 × 副本数) + 调度运维人力** | 口径变更时要重跑历史；血缘由人工维护时会过期 |
| 数据复制（CDC） | **f(目标副本) + 链路稳定性成本** | 源库日志读取的资源占用；schema 变更导致链路中断 |
| 物化视图 | **h(物化组合数) + 刷新计算** | 每多一个被物化的查询形态就多一份存储与刷新；组合爆炸 |
| 联邦查询（裸用） | **g(查询次数 × 扫描量) + 源库负载** | 源库被打爆后的「加只读副本」成本，等于绕回来又买了一份存储 |
| 商业数据虚拟化平台 | **许可费（固定）+ 语义层维护人力** | 语义层是资产也是负债：厂商语义与自建口径的绑定 |
| 统一查询网关 | **固定集群 + g(查询) + 治理层维护人力** | 准入、审计、目录都要人维护；没有配额机制时故障半径最大 |

**【推算】一个数量级示例（说明「免搬迁」省的是什么、付的是什么）**：

- 场景：10 TB 冷数据，用联邦直读对象存储上的表格式，不做副本。
  - 存储成本：10 TB = 10,240 GB，按对象存储标准层公开列表价 $0.023/GB-月推算，**约 $235/月 ≈ $2.8k/年**（[推算：以 AWS S3 标准层公开列表价 $0.023/GB-月为前提到 2024 年]）。
  - 同一份数据若做两份副本（源库 + 湖仓），存储推算翻倍至**约 $5.6k/年**——**绝对金额不大，说明「存储成本」通常不是选型的主导项**。
- 真正的主导项在别处：联邦每次全表扫描这 10 TB，按对象存储的扫描吞吐与网关侧汇聚推算，一次全扫是分钟到十几分钟量级；若这类查询每天发生上百次，代价从「存储费」变成「源库负载 + 网关集群规模 + 人的等待时间」（[推算：由传输量与并发次数推导，具体数值取决于带宽与集群规格]）。
- 因此**「免搬迁」省的从来不是存储费，而是「一致性维护 + 调度链路」的复杂度**；它换来的是「每次查询都要付」的运营成本（[经验]）。这也解释了为什么多数企业的稳态是混合：**热路径物化，长尾路径联邦**（[经验]）。

**把成本函数写成「需要估哪几个变量」更有用**——因为选型讨论最容易卡在「谁的方案更省钱」上，而分歧往往来自两边估的变量不同：

| 候选 | 要估的变量 | 变量的可观测性 |
| --- | --- | --- |
| ETL 同步 | 每日新增数据量、同步频次、目标副本数 | 高：数据量与表数量可从元数据里数出来 |
| 数据复制（CDC） | 变更速率（行/秒）、目标端写入吞吐 | 中：变更速率可以从源库指标看出，峰值最难估 |
| 物化视图 | 被物化的查询形态数、刷新频率、刷新扫描量 | 中：形态数随业务增长，容易在半年内翻倍 |
| 联邦查询 | 查询次数、单次扫描量、下推比例 | 低：查询次数可数，下推比例要跑一遍才知道 |
| 统一查询网关 | 上述 + 并发峰值 + 准入策略命中率 | 低：Agent 接入后查询分布会突变 |

**这张表解释了一个常见误判**：联邦路线的成本变量「可观测性最低」（下推比例无法事前算准），因此它的预算天然比 ETL 路线更容易超支；而 ETL 路线的变量「可观测性最高」，因此它的预算是可以用元数据直接算出来的。**选型时若你要的是「可承诺的成本」，写时物化族在机制上更有优势**——这不是因为它更便宜，而是因为它的输入变量可以被数出来（[经验]）。

### 7.5 决策树（每个分支都要有阈值依据）

```
需要跨源查询吗？
├─ 否 → 单源直查（不要为了「统一入口」引入联邦层）
└─ 是 → 查询形态是「过滤后结果集小」，还是「需要全量扫描 / 大 shuffle」？
        │
        ├─ 小结果集（下推比例高）→ 读时联邦族
        │     │
        │     ├─ 源库能承接分析负载？── 否 → 源侧加只读副本 / 准实时复制后再联邦
        │     │                        └─ 是 → 网关直连源库
        │     │
        │     └─ 是否需要统一权限 / 配额 / 审计 / AI 接入？
        │            ├─ 否 → 裸用联邦引擎（Trino / Presto）即可
        │            └─ 是 → 统一查询网关（联邦 + 治理层）
        │
        └─ 大扫描 / 大 shuffle / 高频重复 → 写时物化族
              │
              ├─ 可接受的延迟 ≥ 小时级 → ETL 同步（批量）
              ├─ 可接受延迟 秒–分钟级 → CDC 数据复制
              └─ 查询形态固定且重复度极高 → 物化视图 / 预计算表
```

**阈值依据**：

- **「过滤后结果集小」没有固定行数阈值，判断方法是「下推后网关侧要接收的行数能否放进少量 worker 的内存」**：因为跨源 JOIN 在网关侧执行（7.3.2），所以这条阈值直接来自机制，不来自经验数字。工程上的操作方法是把最重的 5 条 SQL 拿到连接器下推能力表上核对（7.3.2 判定方法），估算推送回网关侧的行数。
- **「源库能否承接分析负载」的判定阈值来自源库自身的容量规划**，可观察指标是源库在分析查询期间的 CPU / IO 等待与业务侧 P99：一旦出现业务侧抖动，就说明这条硬约束被触犯了，与数据量大小无关。
- **「是否需要治理层」的阈值来自组织结构，不来自技术规模**：只有当「查同一个数据的人分属多个团队、且有审计或配额要求」时，网关这一层的固定成本才摊得掉；单一团队几十人时，治理层的人力投入高于它带来的收益（[经验]）。
- **「≥ 小时级 → ETL，秒–分钟级 → CDC」的阈值来自 CDC 的实现机制**：CDC 的成本主体是变更日志解析与目标端写入，延迟越低压得越紧，对目标存储的写入吞吐要求越高；业务对延迟的容忍度若在小时级，付这份复杂度没有回报（[经验]）。
- **「物化视图」的门槛来自 h(物化组合数)**：因为每个被物化的查询形态都要独立刷新，所以只有当某个查询形态的重复次数足够高、摊得掉刷新成本时才划算（[推算：由「刷新成本 ÷ 单位查询节省成本 = 盈亏平衡重复次数」推导]）。
- **「单源直查」这条分支容易被跳过，但它是最常被违反的一条**：因为引入联邦层的动机往往是「统一入口」这种组织诉求，所以技术上本该直查的场景也被强制走联邦，多了一层网络往返与一个可故障点。**判定方法是问「这条查询的源是不是同一个」**——同源就直查，不需要任何阈值（[经验]）。
- **「先复制再联邦」这个分支的触发条件是源库的业务侧指标，不是数据量**：源库的容量规划里通常没有给分析负载留份额，因此只要分析查询让业务侧 P99 出现可观测的劣化，就必须先复制。这里的阈值是「有没有业务侧可观测劣化」这一布尔判断，不需要量化（[经验]）。
- **给 Agent 开放网关的阈值与给人开放不同，依据是查询分布的可预测性**：人类分析师的 SQL 有历史模式（可据查询日志预估扫描量分布），LLM 生成的 SQL 分布会随模型与提示词变化。**因此给 Agent 的配额不能沿用人类团队的配额**，必须按「单次扫描量上限 + 并发上限 + 超时」三条同时收紧，并把被拒绝的查询记录下来用于改进提示词（[经验]）。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 分析师的交互式跨源探索（结果集小、形态不定） | 联邦引擎（Trino / Presto） | 商业数据虚拟化平台 | ETL 无法覆盖「不知道要问什么」的探索型查询 |
| 业务系统的跨源取数（有权限与审计要求） | 统一查询网关 | 数据 API 网关 | 裸用联邦引擎没有配额与审计，故障半径大 |
| 指标报表（形态固定、重复度极高） | 物化视图 / 预计算表 | ETL 同步 | 联邦每天重复算同一个数字是纯浪费 |
| 近实时看板（分钟级延迟） | CDC 数据复制 + 本地查询 | 联邦直连生产库 | 直连生产库把 OLAP 负载压在 OLTP 上，一票否决 |
| 受监管行业的自助 BI（需统一语义与血缘） | 商业数据虚拟化平台 | 自建网关 + 目录 | 自建语义层的人力与合规举证成本更高 |
| Agent 取数入口（SQL 由 LLM 生成） | 统一查询网关（含配额与审计） | 数据 API 网关（预定义接口） | LLM 生成的 SQL 不可预知，预定义接口覆盖不全；但必须配额 |
| 归因分析 / 一次性探索（查询不重复） | 联邦引擎 | 无 | 物化一次性的查询没有回报，写时转换的成本摊不掉 |
| 对账与监管报表（要求同刻一致、可复算） | ETL 同步 / 物化表 | 物化视图 | 联邦的跨源结果不是同刻快照，也难逐次复算（7.3.1） |
| 跨模态检索（结构化 + 向量 + 图） | 网关（关系侧）+ 独立向量 / 图服务 | 全部塞进联邦 SQL | 向量 top-k 与图遍历不是关系算子，塞进 SQL 会得到不可优化的计划 |

**常见组合（每条说明职责边界与运维代价）**：

1. **统一查询网关 + 数据目录**：目录负责「有哪些表、字段是什么、谁能读」，网关负责「按这些元数据执行查询」。**职责边界**：目录不做查询执行，网关不做元数据管理。**运维代价**：两者需要同步（新建表在目录里可见、在网关里可查），同步失败会导致「目录里有、查不到」这类最难排查的问题，需要一条自动同步链路（[经验]）。
2. **统一查询网关 + 向量检索（RAG）**：网关负责关系侧的结构化过滤与 JOIN，向量召回负责语义候选，由上层编排把两者拼起来。**职责边界**：网关不做向量索引，向量库不做关系 JOIN（7.3.4）。**运维代价**：两套索引的更新滞后不同，需要把「新数据的可见延迟」写进 SLA。
3. **统一查询网关 + 数据 API 网关**：数据 API 网关是**流量治理层**（限流、鉴权、计量），统一查询网关是**查询执行层**。**职责边界**：把已定型的查询封装成 API 走前者；临时与探索型查询走后者。**运维代价**：两套入口意味着两套配额与审计，需要统一到同一个身份与计量体系，否则出现「走 A 入口没配额」的漏洞。
4. **统一查询网关 + Agent / Text-to-SQL**：网关提供「能被机器读懂的统一入口 + 配额 + 审计」。**职责边界**：Agent 负责选表与生成 SQL，网关负责拒绝越权与兜住成本。**运维代价**：LLM 生成的 SQL 质量不可预期，**没有配额与扫描量上限的网关不能直接开放给 Agent**——这一条的代价不是钱，是可用性（[经验]）。
5. **物化层 + 联邦层（组合而非二选一）**：把重复度高、扫描量大的形态物化成表格式的表，让联邦只读物化结果并与其他源做小结果集 JOIN。**职责边界**：物化层对「已知形态」负责，联邦层对「未知形态 + 跨源补齐」负责。**运维代价**：多了一条物化链路要维护（调度、重跑、数据质量），且需要判断「哪些形态值得物化」——判断依据就是 7.4 里的重复次数（[经验]）。

**组合的代价要算在一起，而不是各算各的**：上面 5 条组合里，控制面（目录、配额、审计、身份）常常被重复建两到三套，真正的运维负担来自**控制面不一致**，而不是查询引擎本身。**判定方法**：画出「谁定义权限、谁记录审计、谁执行配额」三个问题的答案，如果同一个问题有多个答案，那部分就是要先合并的地方（[经验]）。

### 7.7 选错的代价与迁移成本

**反模式：把联邦当数仓用** —— 症状：用联邦引擎跑 T+1 的大宽表构建，每天扫全湖、做大规模 shuffle → 后果：worker 内存与网络被长作业占满，交互式查询 P99 抖动，源库被全量扫描拖慢 → 正确的做法：高频大扫描的形态物化成表格式的表（读时转换改为写时转换），联邦只承担「跨源补齐」与探索型查询（对应 7.3.1 的因果）。

**反模式：为「免搬迁」直连生产库** —— 症状：把联邦引擎的 MySQL 连接器指向 OLTP 主库，全靠下推减少传输 → 后果：下推恰恰意味着**过滤与聚合在源库执行**，OLAP 负载直接压在业务库上，业务侧抖动与联邦查询量正相关 → 正确的做法：源侧只读副本或 CDC 复制后再查询，并把副本滞后纳入查询结果的说明（对应第 4 条判据「源侧影响」）。

**反模式：网关没有查询准入** —— 症状：网关开放给全公司甚至 Agent，没有扫描量上限、并发上限与超时 → 后果：一条误写的全表 JOIN 让整层不可用；给 Agent 开放时更严重，因为 SQL 由 LLM 生成、错误不可预测 → 正确的做法：把配额与准入当作网关的**核心功能而非可选功能**，先把扫描量与并发上限设死再开放（对应 7.3.3 的因果）。

**反模式：用「统一入口」掩盖语义不一致** —— 症状：多个源里都有「订单金额」，各源口径不同（含税/不含税、退款是否冲减），网关把它们的 JOIN 结果直接吐给业务 → 后果：**技术上查通了，数字上对不上**；用户开始不信任入口，退回各自的私有脚本，统一入口名存实亡 → 正确的做法：把口径定义放进元数据/指标层（见 [§6 落地实践](09-unified-query-gateway-section-6-sec6.md) 里案例对下推与口径的处理），网关的一个连接器视图对应一个**明确的口径**，而不是「一张表」；口径变更走与表结构变更同样的门禁（[经验]）。

**反模式：把「省了 ETL」当作省了成本** —— 症状：立项理由写「免去数据搬迁，节省存储与同步成本」 → 后果：上线的第二个月发现源库需要加只读副本、网关需要更大的集群与专职人力，总成本反而上升；此时已无法退回，因为业务已经依赖「随时可查全量」 → 正确的做法：立项时就按 7.4 的成本函数把「源侧副本 + 网关集群 + 治理人力」三项显式列出，并把下推比例作为上线后的观测指标（对应 7.4 的变量可观测性分析）。

**换成另一个要动什么**：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 | 总体量级 |
| --- | --- | --- | --- | --- | --- |
| ETL → 联邦 | 无需搬（关键是**不搬**） | 高：所有已固化在调度里的 JOIN 逻辑要重写为跨源 SQL | 中：新建联邦集群与准入策略 | 中：SQL 方言与下推能力差异 | 【经验】数月，瓶颈在查询改写而非部署 |
| 联邦 → ETL / 复制 | 高：需要把数据真正搬一份过来 | 中：跨源 JOIN 变成同源 JOIN，通常更简单 | 中：新增调度与同步链路 | 中：调度与数据质量体系 | 【经验】数月，瓶颈在数据搬迁与校验 |
| 裸用联邦 → 统一查询网关 | 无 | 低：SQL 不变 | 中：叠加权限、配额、审计、目录集成 | 中：治理流程 | 【经验】数周–数月，取决于治理体系成熟度 |
| 自建网关 → 商业虚拟化平台 | 无 | 中：语义层表达方式不同 | 高：语义层要重建（这是资产也是负债） | 高：需要有人成为该平台专家 | 【经验】数季度，且存在被平台语义绑定的长期成本 |
| 直连源库 → 加只读副本 | 中：副本本身是数据复制 | 无 | 中：副本生命周期与延迟监控 | 低 | 【经验】数周 |

**读这张表的方法：迁移成本最高的那一列，永远是「查询改写」或「语义层重建」，而不是部署**。因为 SQL 里沉淀的是业务理解（哪些口径、哪些去重方式、哪些时间语义），换引擎不会让这些理解自动跟着走。**因此选型时最该问的问题不是「另一个引擎性能如何」，而是「我的 SQL 里有多少条强依赖了当前引擎的方言与下推行为」**——这个数可以从查询日志里按「使用了非标准语法 / 依赖了特定下推」筛出来（[经验]）。

**另一个常被忽略的迁移成本是「人的迁移」**：一个团队对某个引擎的熟悉程度，体现在排障速度上（能否在十分钟内判断「这条查询慢是因为下推没生效还是因为数据倾斜」）。换引擎意味着这段经验归零，而它在迁移预算里常常不记账（[经验]）。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 查询形态不定、结果集小、要新鲜 | 联邦引擎（Trino / Presto） | 读时转换无需预知查询形态，下推比例高时成本可控 |
| 多团队共用一个入口，有权限 / 审计要求 | 统一查询网关 | 配额与准入把「不可控并发」变成「可配额并发」，故障半径可控 |
| 指标与报表形态固定、重复度极高 | 物化视图 / 预计算表 | 写时转换把重复计算变成一次计算，成本函数里 g(查询次数) 项被消掉 |
| 分钟级延迟 + 高频查询 | CDC 复制 + 本地查询 | 复制把新鲜度做到秒–分钟级，同时把查询移出源库 |
| 源库是 OLTP 且不允许分析负载 | 先复制，再查询 | 「源侧影响」是一票否决判据，联邦下推反而会加重源库负担 |
| 需要向量 / 图与结构化联合 | 网关做关系侧，向量与图以候选集注入 | 向量 top-k 与图遍历不是关系算子，无法参与全局优化 |
| 只有几十个分析师、单一团队 | 裸用联邦引擎，先别做治理层 | 治理层的固定人力成本在这个规模摊不掉 |
| 需要「可承诺的成本预算」 | 写时物化（ETL / 复制） | 它的输入变量（数据量、频次、副本数）可从元数据数出来，而联邦的下推比例事前不可观测 |
| 只有一条查询、源是同一个 | 直查，不引入任何中间层 | 联邦层在这里只增加一个网络往返与一个故障点，收益为零 |

**本节的三条元规则**（比任何一个具体结论都更耐用）：

1. **先判断「数据在写时转换还是读时转换」，再看引擎**。族选错了，换引擎救不回来：把联邦引擎换成更快的联邦引擎，解决不了「每天重复算同一个大宽表」的问题。
2. **把一票否决型判据放在最前面**。源库能不能承接分析负载、业务能不能接受非同一时刻的跨源结果——这两条不满足时，后面所有维度都不用比。
3. **只测你自己的 5 条 SQL**。所有关于「联邦快不快」的结论都依赖于目标源的连接器下推能力，而这件事只能用自己的查询验证（7.3.2 判定方法）。

> 本节小结：这 6 个候选之间**唯一真正起决定作用的差异是「数据在写的时候被转换，还是在读的时候被转换」**——它一次性决定了新鲜度上限、成本随什么增长、以及跨源一致性到底能不能给。第二位的差异是「下推能不能把数据留在源侧」，它决定了联邦路线是「逻辑访问」还是「一次昂贵的搬运」。

> 💡 **思考锚点**：先去查询日志里数一个数——你的 SQL 有多少条用了非标准语法、或强依赖当前引擎的特定下推行为？这就是本节说的「换引擎时要重写的量」，也是迁移成本最高的那一列。再按元规则 2 排序：源库能不能承接分析负载、业务能不能接受跨源非同一时刻，这两条一票否决判据你现在满足几条？
