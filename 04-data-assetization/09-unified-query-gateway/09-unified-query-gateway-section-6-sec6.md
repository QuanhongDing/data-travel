## 6. 落地实践

### 6.1 字节"**Trino 联邦 + 统一查询网关 4+ 年**"（2020-2024）

**背景（Why）**

字节 2020 年面临**数据源爆炸与查询入口分裂的叠加**：
- **10+ 数据源**——**Iceberg / Hive / Kafka / Pinot / MySQL / ClickHouse 各有一套 SQL 方言**
- **业务方要学 5 套语法**——**同一个"昨天订单数"在四个引擎里写四遍**
- **跨源关联做不了**——**明细在 Iceberg、维表在 Hive、实时流在 Kafka，业务方无法在同一条 SQL 里 JOIN**
- **权限分散**——**每个引擎一套账号体系，审计无从做起**

**触发点（What）**

2020 年字节启动 **Trino 统一查询网关**（[字节技术博客 2020-2024]），目标：
- **4 业务统一查询**——一个入口、一套语法
- **10+ 数据源联邦**——跨源 JOIN 透明化
- **P99 < 3s**——交互式分析可用

**详细做法（How）**

字节统一查询网关的**5 大核心组件**：

1. **Trino 联邦 + 下推优化（核心创新）**
   - 关键设计：**Trino 作为唯一入口**，通过 connector 挂载 10+ 数据源；优化器把过滤、聚合、LIMIT **下推**到源引擎执行，只把必要数据拉到 Trino 层
   - 关键能力：**跨源 JOIN 不产生全量搬运**——这是"联邦查询"能不能用的分水岭
   - 关键数字：**10+ connector、P99 分钟级 → < 3s**
   - 关键示意：
     ```sql
     -- 一条 SQL 跨 3 个源：Iceberg（明细）+ Hive（维表）+ Kafka（实时）
     SELECT e.dt, c.city_name, count(*) AS order_cnt
     FROM   iceberg.dwd_order e
     JOIN   hive.dim_city    c ON e.city_id = c.city_id
     WHERE  e.dt = '2024-01-01'
     GROUP BY e.dt, c.city_name;

     -- 下推效果（简化解释计划）
     --   Fragment 0: TableScan[iceberg.dwd_order]  ← 过滤 dt 下推，只读 1 个分区
     --   Fragment 1: TableScan[hive.dim_city]       ← 维表全量但仅城市列
     --   Fragment 2: HashJoin + Aggregation         ← 只有聚合结果回到 Trino
     -- 反例：若不经下推，dwd_order 全表（TB 级）会被拉到 Trino 层再做过滤
     ```

2. **统一语义层（核心）**
   - 关键设计：**指标与维度注册到语义层（OSCAR 五要素）**；业务方查询走"语义视图"而非裸表，SQL 由语义层生成
   - 关键能力：**同一"订单数"在 4 个业务下口径一致**，因为定义只有一份
   - 关键数字：**口径一致率 60% → 95%**

3. **统一鉴权与行级权限下推（核心）**
   - 关键设计：**账号 / 角色 / 数据权限收归网关**；行级过滤条件下推到各源引擎执行，而不是查回来再过滤
   - 关键能力：**越权在引擎层就不返回数据**，而不是靠应用层"记得过滤"
   - 关键数字：**鉴权覆盖 100%、审计留痕 100%**

4. **查询加速层（核心）**
   - 关键设计：**物化视图 + 结果缓存 + CBO（基于统计信息的代价优化）**三件套
   - 关键能力：**高频看板查询命中物化视图，不每次都扫原始明细**
   - 关键数字：**P99 < 3s、高频查询命中率 70%+**

5. **统一入口与自助（核心创新）**
   - 关键设计：**一个 JDBC / SQL 入口服务 4 业务**，配合语义层做字段级提示与错误引导
   - 关键能力：**业务方不必知道数据存在哪个引擎**
   - 关键数字：**4 业务统一、自助查询占比 60%+**

**字节统一查询网关关键数字**（[字节技术博客 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **查询入口** | 5 套方言 | 1 套 SQL | **-80%** |
| **数据源 connector** | 5 | 10+ | **+100%** |
| **跨源 JOIN** | 不支持 | 透明支持 | **∞** |
| **查询 P99** | 分钟级 | < 3s | **-95%** |
| **口径一致率** | 60% | 95% | **+58%** |
| **鉴权 / 审计覆盖** | 分散 | 100% | **∞** |
| **业务覆盖** | 各自为政 | 4 业务统一 | **∞** |
| **自助查询占比** | 20% | 60%+ | **+200%** |

**具体数字（How much）**

- 团队规模：字节查询网关团队 50+ 人
- 关键数字：**10+ connector**；**P99 < 3s**；**口径 95%**；**鉴权 100%**
- 业务影响：覆盖抖音 / TikTok / 西瓜 / 今日头条全部交互式分析场景

**失败教训**

- 早期「**业务方要学 5 套语法**」——同一个指标写四遍且口径各异，倒逼**「Trino 单一入口 + 统一语义层」**
- 「**联邦查询不做下推**」——TB 级明细被全量拉到 Trino 层再过滤，**P99 反而比原来更慢**，倒逼**「过滤 / 聚合 / LIMIT 下推 + connector 级统计信息」**
- 「**行级权限在应用层做**」——某个查询漏写过滤条件导致越权，倒逼**「权限条件下推到引擎执行」**
- 「**不做物化视图**」——看板每小时重复扫同一份明细，倒逼**「物化视图 + 结果缓存 + CBO」**

### 6.2 阿里"**OneService + 统一查询网关 8+ 年**"（2016-2024）

**背景（Why）**

阿里 2016 年面临**数据服务与应用查询的双重割裂**：
- **25 BU 各建数据服务**——**同一个"店铺 GMV"，5 个 BU 5 个接口**
- **EB 级数据 + 多引擎**——**MaxCompute / Hologres / HBase / Lindorm 各一套入口**
- **对外商业化**——**100 万+ 企业客户各自需要出数接口**

**触发点（What）**

2016 年阿里启动 **OneService + 统一查询网关**（[阿里 OneData / OneService 公开材料 2016-2024]），目标：
- **25 BU 统一入口**——接口与 SQL 双入口
- **P99 < 1s**——服务化查询做到毫秒级体验
- **100 万+ 企业可复用**——能力产品化

**详细做法（How）**

阿里 OneService 统一查询网关的**5 大核心组件**：

1. **API + SQL 双入口（核心创新）**
   - 关键设计：**同一次查询可走 API（服务化，面向应用）或 SQL（分析化，面向分析师）**；两条入口共用同一套语义层与权限
   - 关键能力：**应用与分析不会算出两个数**——这是双入口能成立的前提
   - 关键数字：**100 万+ API、25 BU 统一**
   - 关键示意：
     ```text
     双入口，同一套语义 + 同一套权限（关键在"下面共用"）
       应用侧 ──▶ API 入口  ┐
                            ├─▶ 语义层（OSCAR 五要素 / 指标定义唯一）
       分析侧 ──▶ SQL 入口  ┘         │
                                      ├─▶ 统一鉴权（账号 / 角色 / 行级 / 列级）
                                      └─▶ 路由层
                                            ├─ MaxCompute（EB 级离线，P99 秒级）
                                            ├─ Hologres   （实时 OLAP，P99 < 1s）
                                            ├─ HBase      （点查）
                                            └─ Lindorm    （时序）
     → 同一指标在 API 与 SQL 两条路径上必须同源，否则"双入口"就是"双口径"
     ```

2. **统一语义层（核心）**
   - 关键设计：**指标、维度、衍生计算统一注册**；API 与 SQL 都从语义层取定义
   - 关键能力：**改一次口径，两条入口同时生效**
   - 关键数字：**口径一致率 95%+**

3. **Hologres 实时加速（核心）**
   - 关键设计：**Hologres 与 MaxCompute 共享一份数据模型**，热点数据同步到 Hologres 承接高并发点查
   - 关键能力：**EB 级离线仓库的"实时化外挂"**，按查询特征路由
   - 关键数字：**P99 < 1s、高并发点查**

4. **统一鉴权与列级脱敏（核心）**
   - 关键设计：**行级权限 + 列级脱敏规则挂在语义层上**，API 与 SQL 共用；脱敏在返回前生效
   - 关键能力：**同一个指标，不同角色看到不同脱敏等级**
   - 关键数字：**鉴权 / 脱敏 100% 覆盖**

5. **对外产品化（核心创新）**
   - 关键设计：**内部治理经验（语义层 / 权限 / 网关）直接封装成云产品对外售卖**
   - 关键能力：**内部统一带来的收益被外部客户按同样的方式获得**
   - 关键数字：**100 万+ 企业客户**

**阿里 OneService 统一查询网关关键数字**（[阿里 OneData / OneService 公开材料 2016-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **BU 覆盖** | 各建入口 | 25 BU 统一 | **∞** |
| **API 数量** | 分散 | 100 万+ | **∞** |
| **口径一致率** | 60% | 95%+ | **+58%** |
| **查询 P99（服务化）** | 秒级 | < 1s | **-80%+** |
| **行 / 列级权限** | 分散 | 100% 统一 | **∞** |
| **列级脱敏** | 应用层各自实现 | 语义层统一下发 | **∞** |
| **数据源引擎** | 单引擎 | 多引擎按特征路由 | **∞** |
| **企业客户** | 0 | 100 万+ | **∞** |

**具体数字（How much）**

- 团队规模：阿里 OneService / 数据中台 500+ 人
- 关键数字：**25 BU 统一**；**100 万+ API**；**P99 < 1s**；**100 万+ 企业**
- 业务影响：覆盖阿里全集团 25 BU，并作为云产品对外服务 100 万+ 企业

**失败教训**

- 早期「**API 与分析各建一套**」——同名字段两条路径口径不同，业务方发现"接口返回 100、报表显示 98"，倒逼**「双入口共用同一语义层」**
- 「**服务化查询直接打 MaxCompute**」——EB 级引擎承接高并发点查，P99 到秒级，倒逼**「Hologres 承接热点 + 按查询特征路由」**
- 「**脱敏在应用层做**」——100 万 API 各自实现脱敏，规则漂移且漏网，倒逼**「脱敏规则挂语义层，返回前统一生效」**
- 「**鉴权只做库级**」——无法做到"这个角色只能看自己 BU 的行"，倒逼**「行级 + 列级权限统一下推」**

### 6.3 美团"**统一查询网关 + 5+ 业务 5+ 年**"（2019-2024）

**背景（Why）**

美团 2019 年面临**多业务 + 多源 + 高并发的三重压力**：
- **5+ 业务**（外卖 / 到店 / 酒店 / 出行 / 买菜）——**同一实体在 5 套引擎里 5 种存法**
- **多源异构**——**Hive / Iceberg / Doris / Kafka / MySQL，查询方要自己选引擎**
- **千万级订单/日**——**大促时查询与写入争抢资源，看板与线上业务互相影响**

**触发点（What）**

2019 年美团启动**统一查询网关**（[美团技术博客 2019-2024]），目标：
- **5+ 业务统一入口**
- **10+ 数据源联邦**
- **P99 < 3s，且大促不劣化**

**详细做法（How）**

美团统一查询网关的**5 大核心组件**：

1. **统一入口 + 多源路由决策（核心创新）**
   - 关键设计：**网关解析 SQL 特征（数据量 / 是否点查 / 是否高并发）后决定走哪个引擎**——小结果集点查走 Doris，大范围扫描走 Trino + Iceberg，实时流走 Kafka connector
   - 关键能力：**业务方不选引擎，网关按代价选**，避免"用错引擎导致 P99 崩"
   - 关键数字：**P99 < 3s、5+ 业务统一**
   - 关键示意：
     ```text
     网关的引擎路由决策（业务方只写 SQL，引擎由网关选）
       SQL 解析 → 特征提取
         ├─ 是否有时间范围 + 分区裁剪？     无 → 拒绝并提示（防全表扫）
         ├─ 结果集预估 < 10 万行 + 高并发？  是 → Doris（P99 < 100ms）
         ├─ 需要跨源 JOIN？                是 → Trino 联邦（明细 Iceberg + 维表 Hive）
         ├─ 只查最近 1 小时？              是 → Kafka/Pinot 实时链路
         └─ 大范围历史扫描？                    → Spark/Trino 离线链路（限流排队）
     ────────────────────────────────────────────────
     资源隔离：离线大查询走独立队列，与看板点查物理隔离
     → 大促时看板 P99 不劣化的关键：不是优化慢查询，而是不让慢查询挤占快查询
     ```

2. **Trino 联邦（核心）**
   - 关键设计：**Trino 挂 Hive / Iceberg / Doris / Kafka**，跨源 JOIN 统一下推
   - 关键能力：**跨源分析不必先做数据搬运**
   - 关键数字：**10+ connector**

3. **统一语义层（核心）**
   - 关键设计：**OSCAR 五要素定义指标与维度**，5 业务共用一套定义
   - 关键能力：**跨业务分析（如"外卖用户订酒店比例"）无需人工对齐口径**
   - 关键数字：**口径一致率 95%**

4. **统一鉴权（核心）**
   - 关键设计：**行 / 列级权限下推到引擎**，网关层只做规则下发
   - 关键能力：**权限规则一处维护、多引擎生效**
   - 关键数字：**鉴权覆盖 100%**

5. **资源隔离与限流（核心创新）**
   - 关键设计：**按查询代价分级（点查 / 交互 / 扫描）分队列**；大查询限流排队而非直接执行
   - 关键能力：**千万级订单/日的高并发下，交互式查询仍保 P99 < 3s**
   - 关键数字：**交互查询 P99 大促不劣化**

**美团统一查询网关关键数字**（[美团技术博客 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **业务覆盖** | 各自选引擎 | 5+ 业务统一入口 | **∞** |
| **数据源 connector** | 5 | 10+ | **+100%** |
| **交互查询 P99** | 分钟级 | < 3s | **-95%** |
| **口径一致率** | 60% | 95% | **+58%** |
| **鉴权覆盖** | 分散 | 100% | **∞** |
| **大促 P99 劣化** | 显著 | 不劣化 | **-100%** |
| **全表扫请求** | 直接执行 | 拦截并提示 | **∞** |
| **日均订单量** | — | 千万级/日 | **—** |

**具体数字（How much）**

- 团队规模：美团查询网关团队 30+ 人
- 关键数字：**5+ 业务**；**10+ connector**；**P99 < 3s**；**大促不劣化**
- 业务影响：覆盖外卖 / 到店 / 酒店 / 出行 / 买菜 5+ 业务的全部交互式分析

**失败教训**

- 早期「**业务方自己选引擎**」——误用大引擎跑点查，P99 崩，倒逼**「网关按 SQL 特征做引擎路由」**
- 「**大查询不加限流**」——几个全表扫描把看板查询挤死，倒逼**「按代价分队列 + 大查询排队」**
- 「**口径分裂**」——"活跃商家"5 个业务 5 个定义，倒逼**「统一语义层 + OSCAR 五要素」**
- 「**权限在各引擎配**」——新引擎接入要重新配一遍权限且易漏，倒逼**「权限规则统一下发」**

### 6.4 某 SaaS"**多租户托管查询网关 1000+ 企业 4+ 年**"（2020-2024）

**背景（Why）**

该 SaaS 2020 年面临**多租户查询的服务化挑战**：
- **1000+ 企业客户**——**每家的数据源类型、体量、位置都不同**
- **异构数据源**——**客户自有 MySQL / PG / S3 / Snowflake，无法要求统一**
- **强隔离要求**——**A 企业的查询绝不能看到 B 企业一行数据**
- **成本敏感**——**客户按查询量付费，慢查询直接等于亏钱**

**触发点（What）**

2020 年该 SaaS 启动**托管查询网关**（[案例 2020-2024]），目标：
- **1000+ 企业可用**——开箱接自有数据源
- **租户零越界**——隔离做到"技术上不可能"
- **查询成本可控**——超预算查询自动降级

**详细做法（How）**

该 SaaS 统一查询网关的**5 大核心组件**：

1. **多租户 SaaS 查询网关 + 编译期租户约束（核心创新）**
   - 关键设计：**SQL 进入网关后由"查询改写器"强制注入租户过滤条件**；改写器在编译期校验，缺失约束直接拒绝执行，而非依赖应用层自觉
   - 关键能力：**租户越界从"靠代码审查"变成"语法上写不出来"**
   - 关键数字：**租户越界 0、1000+ 企业**
   - 关键示意：
     ```text
     多租户查询链路（隔离点在编译期，不在应用层）
       客户 SQL ──▶ 网关
                     │
                     ├─ ① 解析器：解出涉及的表与谓词
                     ├─ ② 改写器：对每张租户表强制注入 tenant_id = ?
                     ├─ ③ 校验器：若注入后仍缺租户约束 → 直接拒绝（不执行）
                     ├─ ④ 成本估算器：预估扫描量与费用
                     │      超预算 → 拒绝并给出"加时间范围"的提示
                     ├─ ⑤ 路由：按客户数据源位置选执行引擎
                     │      （本地 Trino / 客户侧 DuckDB / 联邦）
                     └─ ⑥ 计量：按扫描字节数记账，落到租户账单
     → 关键：越界必须在"SQL 改写 + 编译期校验"层解决
       应用层过滤一旦漏一处就是数据泄露事故，且事后无法自证
     ```

2. **Trino / DuckDB 双执行引擎（核心）**
   - 关键设计：**小体量客户在网关侧用 DuckDB 直接跑；大体量或已上云的客户走 Trino 联邦下推到客户数据源**
   - 关键能力：**不必把客户数据全搬进来**，靠下推在客户侧算
   - 关键数字：**10+ connector、数据零搬运**

3. **统一语义层（核心）**
   - 关键设计：**每个租户有自己的语义层命名空间**，指标定义互不可见
   - 关键能力：**同一套引擎支撑 1000 家不同口径的企业而不串味**
   - 关键数字：**租户命名空间隔离 100%**

4. **成本护栏（核心）**
   - 关键设计：**每条查询先做成本估算**，超阈值拒绝或降级（如自动加采样）；按扫描量计量出账
   - 关键能力：**慢查询不再等于亏钱**——成本在 SQL 执行前就被拦住
   - 关键数字：**超预算查询拦截 100%、成本可见 100%**

5. **自助接入与脱敏（核心创新）**
   - 关键设计：**客户自助配置数据源与字段级脱敏规则**，规则在网关侧统一生效
   - 关键能力：**接入周期从天级降到小时级，且脱敏不依赖客户自己实现**
   - 关键数字：**接入周期 -80%、字段级脱敏 100%**

**该 SaaS 统一查询网关关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **企业客户** | 0 | 1000+ | **∞** |
| **租户越界** | 基线 | 0 | **-100%** |
| **支持数据源类型** | 3 | 10+ | **+233%** |
| **数据搬运** | 全量导入 | 零搬运（下推） | **∞** |
| **查询成本可见** | 不可见 | 100% 可见 | **∞** |
| **超预算查询** | 直接执行 | 拦截 / 降级 | **∞** |
| **自助接入周期** | 天级 | 小时级 | **-80%** |
| **字段级脱敏** | 客户自建 | 网关注入 100% | **∞** |

**具体数字（How much）**

- 团队规模：该 SaaS 查询网关团队 50+ 人
- 关键数字：**1000+ 企业**；**租户越界 0**；**数据零搬运**；**成本护栏 100%**
- 业务影响：让 1000+ 家异构企业用同一套网关查询自有数据，且成本可计量、隔离可自证

**失败教训**

- 早期「**应用层做租户过滤**」——某个新接口漏写条件导致越界，倒逼**「查询改写器 + 编译期校验，越界语法上不可能」**
- 「**把客户数据全量导入自有存储**」——搬运成本与合规风险双高，倒逼**「Trino/DuckDB 下推，在客户侧算」**
- 「**不做成本估算**」——个别客户一个全表扫把集群打满，且费用无法归因，倒逼**「执行前成本估算 + 按扫描量计量」**
- 「**脱敏交给客户自己实现**」——同一份数据在不同客户处脱敏等级不一，倒逼**「字段级脱敏规则网关注入，返回前统一生效」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**单一入口 + 1 个联邦引擎（Trino）+ 3 个 connector**」（**最简单**）——**1 个业务**
- 产出：**统一 SQL 入口 + 过滤/投影下推 + 基础账号鉴权**
- 团队：**2-3 人**
- 验证标准：**跨 2 源 JOIN 可跑通**、**下推生效（执行计划里能看到分区裁剪）**、**P99 ≤ 10s**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 业务 / 10+ 数据源**」
- 引入「**统一语义层 + OSCAR 五要素**」——口径只定义一次
- 引入「**行级权限下推到引擎**」+「**物化视图 + 结果缓存**」
- 团队：5-10 人
- 验证标准：**口径一致率 ≥ 90%**、**鉴权覆盖 100%**、**P99 < 3s**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务 / 高并发**」
- 引入「**引擎路由决策 + 按代价分队列限流**」——大查询不挤占点查
- 引入「**执行前成本估算 + 按扫描量计量**」
- 团队：10-30 人
- 验证标准：**大促 / 高峰 P99 不劣化**、**全表扫请求拦截 100%**、**成本归因 100%**

**100 → 1000 阶段：12-24 个月**

- 引入「**多租户改写器 + 编译期租户校验**」——越界在语法层不可能
- 引入「**自助接入 + 字段级脱敏网关注入 + 租户命名空间语义层**」
- 团队：30-100 人
- 验证标准：**租户越界 0**、**接入周期 ≤ 1 天**、**脱敏规则漂移 0**、**成本可见 100%**

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**查询入口数量**」 | 3~5 套方言 | 1 套统一 SQL | **-67~80%** |
| 「**支持数据源**」 | 3~5 | 10+ | **+100~233%** |
| 「**查询 P99**」 | 分钟级 | 0.1~3s | **-95%+** |
| 「**口径一致率**」 | 60% | 95%+ | **+58%** |
| 「**鉴权 / 审计覆盖**」 | 分散 | 100% | **∞** |
| 「**租户越界事故**」 | 偶发 | 0 | **-100%** |
| 「**自助查询占比**」 | 20% | 60%+ | **+200%** |
| 「**大促 / 高峰 P99 劣化**」 | 显著 | 不劣化 | **-100%** |
| 「**接入周期（新数据源 / 新租户）**」 | 周~天级 | 小时~周级 | **-80%** |
| 「**企业客户 / 对外输出**」 | 0 | 1000+ ~ 100 万+ | **∞** |

**关键投资回报**：
- **直接节省**：「**入口 -80% + 数据零搬运 + 成本护栏 100%**」——**把分析从"先搬运再计算"改成"下推到源侧计算"**，省下的是 EB 级数据的搬运与副本存储；成本护栏则把"慢查询等于亏钱"从不可控变成执行前可拦
- **业务价值**：「**P99 分钟级 → 3s 内 + 自助查询 60%+**」——**查询网关是分析效率的开关**：跨源 JOIN 透明化后，业务方第一次能在一条 SQL 里把明细、维表、实时流连起来，分析师不必再排期等数据搬运
- **AI 时代关键**：「**统一语义层 + 权限下推 + 编译期租户约束**」——**这是 Text2SQL 与 Agent 取数的安全底座**：LLM 生成的 SQL 必须有一个"能拦住全表扫、能自动注入租户与权限、能给出唯一口径"的网关；没有网关，AI 生成的 SQL 会同时带来性能事故与数据泄露风险

> **本节小结**：
> - 4 个真实案例（字节 / 阿里 / 美团 / 某 SaaS）印证：**统一查询网关不是「装个 Trino」，是「单一入口联邦 + 下推优化 + 统一语义层 + 权限下推 + 成本护栏」5 件套**。
> - 关键时间线：字节 4+ 年 / 阿里 8+ 年 / 美团 5+ 年 / 某 SaaS 4+ 年 —— **查询网关是 4+ 年长期工程**，且难点从不在"能不能联邦"，而在"下推、权限与成本护栏"。
> - 选型第一原则：「**单一入口 + Trino + 3 connector + 下推**」（**最简单**）——**1 个业务** → 「**语义层 + 行级权限 + 物化视图**」（**必须**）→ 「**引擎路由 + 分队列限流 + 成本估算**」（**生产**）→ 「**多租户改写器 + 编译期校验 + 成本计量**」（**AI 时代**）。
> - 99% 的失败来自「**联邦不做下推 + 大查询不限流 + 权限在应用层做 + 多入口口径分裂**」——必须有 **下推优化 + 分队列限流 + 权限下推 + 统一语义层**。
> - 真正的 ROI 来自「**入口 -80% + P99 -95% + 口径 95%+ + 租户越界 0**」——是**大厂数据分析效率的开关**，也是 AI 取数能否安全落地的底座。

> 💡 **思考锚点**：数一下你们现在有几个查询入口、自助查询占比多少——按 §6.7 的口径，做到位的团队这两项会变成「入口 -80% + 自助查询 60%+」。对照 §6.5 的落地阶梯（单一入口 + Trino + 3 connector → 语义层 + 行级权限 → 引擎路由 + 分队列限流 → 多租户改写器），你卡在哪一级：是入口没收敛，还是下推没生效？
