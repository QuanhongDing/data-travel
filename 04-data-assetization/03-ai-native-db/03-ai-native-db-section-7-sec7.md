## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

原文件给「结构化 + 向量融合」行打了 `关系数据库 = 1 / 专有向量库 = 2 / AI 原生 DB = 5`，又在「规模上限」行打了 `关系数据库 = 5 / AI 原生 DB = 3`。这两行本身没错，错在**它把与规模强相关的结论写成了绝对结论**。同一维度在不同场景下权重相反：当一个业务的向量只有几十万条、且向量写入必须和订单写入同时可见时，单库几乎是免费的优势——你已经在跑这个数据库，多一列、多一个索引而已，跨库 JOIN 与一致性缝合的成本则完全不用付。反过来，当向量到了十亿级、语料以离线方式生成、更新以天为单位时，「单库」意味着把十亿个向量和图结构压在少数几台机器的内存里，而这时一致性需求已经降到接近零——**同一张表在两个场景里应给出相反结论，打分表却只能给一个**。

第二个问题是**维度不可加**。打分表把「融合 5 分」和「规模 3 分」加权求和，但这两项不是可以相互折价的商品：融合能力不足是**功能缺失**（做不到就是做不到，没有折扣），规模不足是**成本问题**（可以用钱和架构换）。把两者放进同一个加权和，等于默许「用功能换规模」，而真实决策里功能是硬约束、规模是可改的。

第三个问题是**候选不同质**。原表里四列（四个候选方案）其实是三类东西：「关系数据库 + 应用层算距离」是一种**没有向量索引**的形态；「AI 原生数据库」与「关系数据库 + 向量扩展」在很多产品上根本是**同一个东西**（下文 §7.3.1 给出判定标准）；「向量湖」解决的是**驻留层级**问题，不是检索语义问题。把它们排成一列逐格打分，等于把锤子、电钻、以及「把工具都搬到一个更大的工作台上」放在一起评分。

第四个问题是**阈值凭空来**。原决策树写「< 100 万 → AI 原生 DB；> 1 亿 → 向量湖」，但这两个数没有推导。本章的做法是：把阈值还原成**可以自己算的算术**——`向量数 × 每向量字节数` 与 `可用于缓存的内存` 的比值。算出来是多少就是多少，你的机器和维度会给出你自己的阈值。

本章保留原文件的**候选清单**（§7.2 给出逐项落点，一个都没丢），但**改变了它的结论顺序**：原文件先看规模、再看是否需要与结构化数据 JOIN；本章把「一致性硬约束」提到第 0 层先行（§7.5），规模退到第 1 层，而「结构化条件与向量排序一起做」这条诉求落在第 2 层（过滤区分度）与第 1 层的「是否要与湖表同一份数据」分支上。顺序之所以要改：一致性做不到就是做不到（功能缺失，不可折价），规模不足是成本问题（可以用钱与架构换），两者不该并列。每个结论都换成可推导的因果链，并对所有数字标注档位：【公开】指有官方文档 / 论文 / Release Note 可引，注明来源与年份；【推算】指由公开前提推导，正文写出推导链；【经验】指行业普遍实践，只给区间与条件。凡是既无来源又精确到有误导性的数字（例如「延迟降低 47%」），本章一律不写。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 一致性边界 | 向量写入能不能与业务写入在同一个事务里提交、同一个删除里生效 | 不能同事务 ⇒ 必须双写或 CDC，检索到过期数据从异常变成常态（§7.3.3） |
| 索引的所有权 | 向量索引是数据库内核注册的索引访问方法，还是一个独立服务自持的结构 | 决定崩溃恢复归谁、故障域多大、索引重建有没有运维窗口（§7.3.1） |
| 驻留层级 | 索引在图遍历时读的是内存、本地盘还是对象存储 | 决定规模上限与成本函数的主项；层级之间的差是数量级，不是百分比（§7.3.2） |
| 融合查询的执行位置 | 结构化过滤是在索引扫描之内还是跨系统拼接 | 决定过滤区分度低时要不要过取，以及要不要维护两份元数据（§7.3.4） |
| 运维单元数 | 一次扩容、一次备份、一次升级要动几个系统、几套监控 | AI 应用团队通常没有独立的检索运维编制（§7.6 组合） |
| 演进与锁定 | 向量能力是「一个产品」还是「某个数据库的一个特性」 | 决定三五年后你是否还需要单独养一个检索系统（§7.7） |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者（【经验】） | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 关系数据库（无原生向量） | 已有 OLTP 里凑合做检索 | 向量以数组/BLOB 存放，距离在应用层算，没有 ANN 索引 | 存量系统、数据量很小的场景 | 商业 / 开源 |
| 关系数据库 + 向量扩展 | 在 OLTP 里加一列一号 | 向量索引作为扩展注册成数据库的索引访问方法，与标量索引共用 buffer 与 WAL | PostgreSQL + pgvector（云上 RDS / Aurora / Cloud SQL / AlloyDB 均已内置） | 扩展开源（pgvector 为 PostgreSQL 许可） |
| AI 原生数据库 | 向量是一等公民 | 类型、距离算子、优化器代价模型、索引结构全部内建，融合查询在优化器内规划 | Oracle 23ai / SingleStore / SurrealDB / TiDB Vector / TigerData | 商业 + 开源混合 |
| 专有向量库 | 独立检索服务 | 索引、payload、分片、量化全部由自己管理，设计目标只有检索 | Milvus / Qdrant / Weaviate / Vespa / Pinecone | 开源 + 商业托管 |
| 向量湖 | 对象存储上的十亿级检索 | 索引建在对象存储与本地缓存之上，存算分离，与湖表格式集成（见 [Ch4-02](../02-vector-lake/02-vector-lake.md) §2.3） | 多模态大规模检索 | 开源 + 云托管 |
| Serverless 向量库 | 按量付费的托管检索 | 索引与扩缩容对用户不可见，成本从「按节点」变成「按请求 + 按存储」 | Pinecone Serverless | 商业 SaaS |
| Lakehouse + Vector | 湖仓里的向量列 | 向量作为湖表的一列，检索下推到湖仓查询引擎 | Snowflake Cortex / Databricks Vector Search | 云厂商托管 |

这七个候选其实分三**族**：**族 1 通用数据库承载**（关系库、关系库 + 扩展、AI 原生 DB）——向量住在已经有事务、备份、权限的那套系统里；**族 2 独立检索服务**（专有向量库、Serverless）——检索被当成一类专门的负载单独供给资源；**族 3 湖上向量**（向量湖、Lakehouse + Vector）——向量住在对象存储上，检索靠缓存与下推。同族内部可以逐项替换（族 1 里从「加一列」换到「换数据库」常常只改索引参数；族 2 里自建换托管主要换的是运维模型），跨族替换要动的是数据放在哪、谁来保证一致性、以及团队要会什么。**先分族再选，能省掉一半比较。**

### 7.3 机制差异：为什么它们表现不同

#### 7.3.1 索引的所有权：向量索引是谁的数据结构

**机制是什么**：向量索引在系统里的身份——是数据库内核注册的一个索引访问方法（index access method），还是一个独立进程/集群自持的数据结构。它决定三件事：崩溃恢复靠谁、索引重建的运维成本归谁、以及这套资源是否与其他负载共享。

**实现差异**：

| 候选 | 索引身份 | 崩溃恢复靠谁 | 资源边界 |
| --- | --- | --- | --- |
| 关系数据库（无向量） | 无索引，顺序扫描 | 数据库 | 与 OLTP 完全共享（且全表扫会把 OLTP 拖慢） |
| 关系数据库 + 向量扩展 | 注册进优化器的索引访问方法 | 数据库自身的 WAL + checkpoint | 共享 buffer pool 与后台工作进程 |
| AI 原生数据库 | 内核内建索引结构 | 内核 | 共享，但优化器知道它的代价，可参与规划 |
| 专有向量库 | 自持的段式索引（内存段 + 落盘段 + 合并） | 自己的日志与快照机制 | 独立节点，独占内存与 CPU |
| 向量湖 | 对象存储上的索引文件 + 本地缓存 | 索引文件版本 + 缓存重建 | 检索与构建分离，可各自伸缩 |

**由此必然导出的性质**：因为向量扩展的索引是数据库的索引访问方法，索引更新写进**同一份 WAL**，所以「写入向量」与「写入业务行」天然同事务、同崩溃恢复语义——你不需要为向量索引单独设计一致性协议、副本协议与故障恢复流程，这是单库路线最大的一笔隐性收益。反过来，因为索引条目也要服从 MVCC（更新是「插入新版本 + 标记旧版本」而不是原地改），所以图结构里的死点要靠清理进程回收，**长期高频更新会让索引膨胀、召回与延迟一起退化**——这是「单库能扛住十亿向量」这类宣称在写入型负载下失效的第一个机制。

因为专有向量库把索引做成自己的段式结构，所以它能做索引访问方法做不了的事：删除不必立即回收、按段并行构建、按段独立量化、把冷段换到便宜存储上，代价是它必须自己实现崩溃恢复、自己的副本一致性、以及自己的「写入何时可见」语义——**从数据库借来的那部分能力，全部要自己重写一遍**。

**公开证据【公开】**：pgvector 官方 CHANGELOG 显示 0.5 版（2023）引入 HNSW 索引、0.7 版（2024）引入 halfvec / bit / sparsevec 类型、0.8 版（2024）引入 iterative index scan；PostgreSQL 官方文档对 MVCC 与 VACUUM 的描述解释了索引死点的来源。可自行核验这条判据：对一个 HNSW 索引反复 UPDATE 同一批行，观察索引大小增长，以及重建索引前后的召回与查询延迟差。

**失效条件**：当负载以插入为主、几乎不删不改时，MVCC 死点问题不出现，这条判据失效；当团队本来就在跑检索系统、有独立的检索运维能力时，「多一套系统」的边际成本远低于本章的默认假设。

**一个具体的对照：索引重建的运维形态**。索引膨胀到影响召回时，两条路线的处理方式不同：

- 族 1：重建是一次数据库内的索引构建，它会占用连接、IO 与 CPU，因此在生产库上通常要排到低峰窗口；好在不搬数据，重建期间数据仍在原表里，读路径只降级不中断。
- 族 2：重建是段合并（compaction），它可以后台持续进行、不必排窗口，但代价是常驻的 IO 与内存开销，且「合并追不上写入」时会积压——这是向量库运维里最常见的容量问题。
- 族 3：重建是「重新生成索引文件并写回对象存储」，它可以完全离线做、做完了原子切换，代价是重建期间新增的数据要走增量通道补上，切换逻辑要自己写。

这三条不是优劣，而是**同一件事在不同所有权模型下的三种形态**。你如果没有低峰窗口（7×24 的交易系统），族 2 与族 3 的「在线重建」形态就是真实优势；反过来，如果你没有人在半夜被叫醒去盯合并进度，族 1 的「排窗口」反而更省心。

#### 7.3.2 驻留层级：规模上限从哪来

**机制是什么**：ANN 图的搜索是**逐跳随机访问**——每跳读一个节点的邻居表，再跳到下一个节点。单跳的耗时完全由「被访问的数据在哪一层」决定：内存随机访问在几十纳秒量级，本地 NVMe SSD 的随机读在几十到上百微秒量级，对象存储的首字节延迟在毫秒量级且按请求计费（均为【经验】量级判断：内存与本地盘之间约 2–3 个数量级，本地盘与对象存储之间再差 1–2 个数量级；具体倍数取决于介质代次、队列深度与请求模式）。所以「规模上限」不是产品能力问题，而是**索引驻留在哪一层**的问题。

**实现差异与驻留算术**（以 1024 维向量为例）：

| 驻留层级 | 代表 | 每向量占用（推导见下） | 可行规模量级（【推算】） |
| --- | --- | --- | --- |
| 内存，fp32 原向量 + 图 | 单机 pgvector / HNSW | ≈ 4.2 KiB：向量 1024 × 4 B = 4 KiB，图链接 m=16 × 双向 × 4 B ≈ 128 B | 百万–千万 |
| 内存，半精度或标量量化 | pgvector halfvec（0.7+）、各向量库的 SQ / BQ | 半精度 ≈ 2.1 KiB；int8 标量量化 ≈ 1 KiB + 图 | 千万–亿 |
| 本地 SSD + 内存图 | DiskANN 系列（见 [Ch4-02](../02-vector-lake/02-vector-lake.md) §2.3） | 内存只放邻居 ID 列表（每个节点几十–几百个 ID，按 int32 每 ID 4 B 计约 0.2–2 KB），全精度向量懒加载 | 十亿 |
| 对象存储 | 向量湖 | 远端拉取 + 本地缓存与预热 | 十亿以上，成本按存储计 |

**由此必然导出的性质**：因为搜索是逐跳随机访问，所以真正决定延迟的是比值 `索引大小 / 可用于缓存的内存`。这个比值小于 1 时，单跳是内存访问，延迟由算法决定；大于 1 时，每一跳都有概率落盘，P99 由「未命中率的倒数 × 单次随机 IO」主导——**这是「规模上去之后延迟突然变差」的真正原因，也是调参无法解决的问题**。因为量化按 2×–32× 压缩每向量字节数（见 [Ch4-02](../02-vector-lake/02-vector-lake.md) §2.2 的压缩比表），所以它把内存墙按同样倍数往后推；代价是召回损失（同一张表给出从不到百分之一到百分之十量级的召回下降），必须用更大的候选数与精排补回来。**量化的收益与代价同源：不存在只赚不赔的压缩。**

**公开证据【公开】**：DiskANN / SPANN 的磁盘索引机制（内存图导航 + SSD 懒加载完整向量）见 [Ch4-02](../02-vector-lake/02-vector-lake.md) §2.2 的 DiskANN 说明与 §2.3 的 ANN 索引对比表；代表论文本节无法核验，读者可按算法名自行检索；pgvector 的 halfvec / bit 类型为 0.7 版引入（pgvector CHANGELOG，2024）；专有向量库普遍提供标量 / 乘积 / 二值量化选项（各家官方文档，可自行核验其「quantization」章节）。

**失效条件**：语料只有几十万到几百万时，量化带来的规模收益不存在，而它引入的召回损失真实存在——这是「小规模上量化是纯亏」的机制解释。反过来，只做插入、从不删除的场景里，索引膨胀的代价也不存在。

**构建期是第二个被低估的变量**。HNSW 的构建复杂度约为 O(N log N)（分层图的逐点插入，见 [Ch4-02](../02-vector-lake/02-vector-lake.md) §2.2 对 HNSW 复杂度的说明），也就是说索引构建是**计算密集且随数据规模超线性增长**的一次性工作。它引出三条推论，每一条都会改变选型：

- 因为构建要靠 CPU，所以「换嵌入模型」不是一个改配置的动作，而是「全量重新编码 + 全量重建索引」的一次大工程——**嵌入模型的迭代速度因此被索引构建代价锁住**，这是很多团队最终选择把嵌入版本与索引版本一起做版本管理的原因。
- 因为构建随规模超线性增长，所以「冷启动导入 10 亿向量」和「每天增量更新 1 万条」是两种完全不同的负载；把两者放在同一套集群上，冷启动会长时间占满资源，拖慢在线查询。
- 因为量化索引的重建更贵（需要重算码本），所以「先全精度跑起来，再上量化」这个顺序是对的，但反过来「先上量化省内存，等不够了再回全精度」几乎不可逆——码本一旦作为索引的一部分对外提供服务，回退就意味着一次全量重建。

**公开证据【公开】**：HNSW 的分层图插入过程与 O(log N) 搜索、O(N log N) 构建的复杂度见 [Ch4-02](../02-vector-lake/02-vector-lake.md) §2.2；pgvector 0.6 起支持并行索引构建（官方 CHANGELOG，2024），这类优化的存在本身就说明构建耗时是使用者真实的痛点。可自行核验：在你的数据上分别构建一半规模与全量规模的索引，记录耗时比值——如果显著超过 2 倍，说明构建成本在这个规模上尚未进入可接受的线性区间。

#### 7.3.3 一致性边界：能不能和业务写入同生共死

**机制是什么**：向量写入与业务写入是不是同一个事务、同一次删除。

**实现差异**：

| 候选 | 写入原子性 | 删除同步 | 一致性的实现者 |
| --- | --- | --- | --- |
| 关系数据库（无向量） | 同事务 | 同一次 DELETE | 数据库 |
| 关系数据库 + 向量扩展 | 同事务（同一 WAL 与提交序） | 同一次 DELETE（索引随 MVCC 清理） | 数据库 |
| AI 原生数据库 | 同事务 | 同一次 DELETE | 内核 |
| 专有向量库 / Serverless | 无（双写或 CDC） | 需要两处显式删除 | 应用代码 + 同步通道 |
| 向量湖 / Lakehouse + Vector | 按湖表的事务语义（取决于表格式与提交协议） | 按湖表删除语义 | 表格式 + 摄入管线 |

**由此必然导出的性质**：因为向量写入与业务行写入共享同一份日志与提交序，所以「下单后立即可被检索」是**默认行为**，而不是需要额外机制保障的目标。反过来，独立检索服务要么双写、要么 CDC：双写没有原子边界，失败必丢一边；CDC 有延迟，且乱序要求下游用幂等键与版本号吸收，「检索到过期数据」从异常变成常态。【推算】双写的整体成功率是两次独立写入相乘——若单系统写入成功率 99.99%，双写约 99.98%，即失败率约 0.02%；按日写入 100 万笔算，日均约 200 笔静默不一致，日写入到 1,000 万笔则约 2,000 笔（该推算只在两次写入的故障相互独立时成立；共享网络与共享发布时，故障相关，不一致的形态从「零散丢」变成「成片丢」）。

更隐蔽的是**删除**：合规要求「删除某个用户的数据」时，单库路线是一条 DELETE；双系统路线要在两处都删，而向量库里没有「这个向量对应哪条业务记录」的原生约束（除非 payload 里显式存了主键），删漏了不会有任何报错——**它只在合规审计或用户投诉时暴露**。

**公开证据【公开】**：PostgreSQL 官方文档中关于事务原子性与 MVCC 可见性的描述，是「同库即同事务」这一结论的依据；各家向量库文档都会说明其写入可见性模型（多数为最终一致或「写入后需刷新才可检索」），可自行核验你正在评估的产品在这一节是怎么写的。

**失效条件**：当检索语料是离线生成、更新以天为单位时（文档库、知识库、离线语料），实时性需求消失，这条判据的权重降到接近零——此时族 2 的规模与量化优势占主导。这是本节最重要的一处「同一维度在不同场景权重相反」。

**怎么验证这条判据（而不是听厂商说）**：写一个三步的小测试，半小时能跑完，结论比任何文档都可靠。

1. 在业务写入路径上埋一个「写入后立即检索」的探针，检索键就是刚落库的那条记录，连测 1000 次，统计未命中的比例。族 1 上这个比例应当为 0；族 2 上你会得到第一个真实的延迟分布。
2. 删一条业务记录，然后立刻用它的原始文本检索，看它还在不在结果里。这一步检验的是删除同步，也是最容易在下游表现为「合规问题」的一步。
3. 把同步通道（CDC 或中继）停掉 1 小时，再看业务侧是否有任何异常。如果答案是「没有任何异常」，说明你的检索结果本来就允许滞后——那么一致性判据对你不成立，可以放心选族 2 或族 3，把预算花在规模上。

这三步的意义在于：**一致性需求是一个可以被业务方确认的事实，而不是一个需要架构师替业务方猜的偏好。** 猜错的代价是两个方向都真实——过度要求一致性会让你在千万级就背上单库的内存墙，而忽视一致性会让你的检索结果在最需要正确的时刻（刚下单、刚改地址）是错的。

#### 7.3.4 融合查询的执行位置：过滤与向量谁先谁后

**机制是什么**：结构化过滤与向量排序这两件事，是在同一个执行器里做，还是在应用层拼起来；如果是同一个执行器，优化器先做哪一步。

**实现差异**：

| 候选 | 过滤在哪执行 | 过滤与向量扫描的先后 | 是否需要跨系统取数 |
| --- | --- | --- | --- |
| 关系数据库（无向量） | SQL 引擎 | 先过滤，再在结果集上算距离 | 无 |
| 关系数据库 + 向量扩展 | SQL 执行器 | 早期为后过滤；pgvector 0.8（2024）起支持迭代扫描 | 无 |
| AI 原生数据库 | 优化器代价模型 | 优化器可在「先过滤」与「先向量扫」之间选 | 无 |
| 专有向量库 | 库内标量过滤 / payload 过滤 | 前过滤需要自建标量索引；外部字段要先同步进 payload | 有（字段要冗余一份） |
| 向量湖 / Lakehouse + Vector | 湖仓查询引擎 | 谓词下推 + 索引下推 | 无（同一存储层） |

**由此必然导出的性质**：因为后过滤是「先按向量取 `ef_search` 个候选，再逐个过 WHERE」，所以期望命中行数 ≈ `ef_search × 选择率 p`，要拿到 K 行就需要 `ef_search ≳ K / p`。取 K = 10、p = 1%，则需要 `ef_search` 约 1000；而检索耗时随 `ef_search` 增长（【经验】，增长近似线性到超线性，取决于图质量与数据集）。**这意味着 SQL 里最自然的写法（先 WHERE 再 ORDER BY 距离）在高区分度过滤下代价极高**——而这恰恰是业务查询最常见的形态（按租户、按时间窗、按权限过滤）。

因为把过滤字段冗余进向量库的 payload 能让过滤在索引扫描之前发生，所以专有向量库在「过滤字段固定、可冗余」的场景下反而更快；代价是这些字段进入了两处数据源，需要同步与一致性保障——**性能问题的解法又把一致性问题请了回来**。

**公开证据【公开】**：pgvector 0.8 引入 iterative index scan，官方 CHANGELOG（2024）明确其目的之一是改善带 WHERE 的向量查询；Qdrant / Milvus / Weaviate 的文档都提供 filtered search 以及「先过滤 / 先向量」的策略选择，可自行核验。核对你自己的查询：对同一条 SQL 分别执行「带真实 WHERE」与「WHERE 恒真」两版，比较 `EXPLAIN (ANALYZE)` 返回的行数与耗时差。

**失效条件**：当过滤条件几乎不筛掉任何行（p 接近 1）时，前过滤与后过滤无差别，这条判据失效；当过滤字段本身就住在同一个库里（族 1 的常态）时，冗余与同步问题也不存在。

**跨系统版本的过取代价（【推算】）**：如果不把过滤字段冗余进向量库，应用层只能「先多取、再回业务库过滤」。设过滤选择率 p = 5%、希望最终保留 10 条，则必须从向量库过取约 10 / 0.05 = 200 条候选，再回业务库做一次 `WHERE id IN (...)` 的过滤。这条链的代价有两项：**向量库要返回的候选数放大了 20 倍**（网络传输与序列化随之放大），以及**业务库多了一次 200 个 ID 的随机回表查询**。当 p 降到 0.5% 时，过取量涨到 2000 条，这条路径基本不可用——而它的失败方式不是报错，而是「结果不足 K 条」或「延迟劣化到不可接受」。这也是为什么原表给「结构化 + 向量融合」的差距是 1 分对 5 分而不是 4 分对 5 分：**跨系统融合的代价随过滤区分度非线性放大，而库内融合不随 p 变化（优化器可以在两种顺序间选）。**

### 7.4 成本结构对比（不是价格表，是成本函数）

```
总成本 ≈ 已有数据库集群的边际成本（多一列 + 索引常驻内存）
        + f(向量数 × 维度 × 驻留层级)     ← 存储与内存，可容量规划
        + g(写入速率 × 索引更新代价)       ← 索引维护与膨胀回收
        + h(查询 QPS × 每查询访问的索引节点数)
        + 运维单元成本（备份 / 监控 / 值班 / 升级 / 权限）
```

**各候选的主导项与隐性成本**：

- **关系数据库 + 向量扩展**：主导项是内存（索引驻留）；隐性成本有两块——索引膨胀后的重建窗口，以及向量查询与 OLTP 争抢缓存导致的**在线事务 P99 抖动**（向量查询是内存密集的，它挤掉的正是业务最热的那批页）。
- **AI 原生数据库**：主导项同样是内存，但优化器与算子在库内，省掉应用层拼接与二次取数；隐性成本是产品成熟度与许可锁定。
- **专有向量库**：主导项是节点内存，成本随集群规模阶梯上升；隐性成本是第二套备份 / 监控 / 升级 / 权限体系，以及一致性缝合代码的长期维护。
- **Serverless 向量库**：**成本函数的形式变了**——从「按节点」变成「按存储 + 按请求」。它对低 QPS、尖峰型负载友好（没有闲置节点），对稳态高 QPS 显著更贵，因为单价随用量线性、没有「最后一台机器被摊薄」的固定成本。选它之前先算一遍峰值 QPS × 单价与自建节点成本的交叉点。
- **向量湖**：主导项是「对象存储（便宜）+ 检索节点缓存内存（贵）」；因为存算分离，扩容不需要搬数据，但每次查询的 P99 受远端读取支配，除非缓存命中率高。
- **Lakehouse + Vector**：主导项是湖仓计算资源的占用；它成立的前提是「向量检索是分析任务的一部分」，而不是高频在线请求。

注意两类成本的增长方式不同：主导项随数据量增长（可以容量规划），隐性成本随**运维单元数与故障次数**增长（不可预测）。所以真正要比的不是「哪个更便宜」，而是「哪一份隐性成本落在我的团队能力范围内」。

**【推算】单库路线的规模拐点**：以 1024 维 fp32 计算，每向量约 4.2 KiB（§7.3.2 推导），1,000 万向量约 42 GB；若一台机器能拿出 32–64 GB 给索引缓存（【经验】，要留给连接、排序、工作内存与 OS），拐点就落在千万级附近。换半精度或标量量化把每向量压到 1–2 KiB，同样的缓存预算下拐点右移到 2,000 万–6,000 万（32–64 GB ÷ 1–2 KiB 后取整）。**原决策树里「百万 / 1 亿」两个阈值的来源就是这条算术**：它不是行业常数，而是「每向量字节数 × 可用内存」算出来的；维度或量化方式一变，你的阈值就变。

**驻留层级的成本差**（单价档位见句内标注，折算结果为【推算】）：10 TB 向量若走对象存储，按 S3 标准层列表价 **$0.023/GB-月**【公开】（AWS S3 标准层定价页，2026 年查询，取前 50 TB 档，价格随区域变动，此处取量级）约需 **$240/月**量级【推算】；同样 10 TB 若要常驻内存（每向量 4.2 KiB ⇒ 约 26 亿向量），按云上内存型实例单 GB 月价在个位数美元量级【经验】（各云商与区域差异明显，取量级）折算，成本高两个数量级【推算】。**这就是向量湖存在的唯一理由**：把成本从内存换到存储，用延迟与召回支付差价——差价是否值得，取决于你的查询能否靠缓存吸收。

**【推算】向量查询对同库在线事务的干扰**：族 1 里向量查询与业务查询共享同一个 buffer pool。一次 ANN 搜索要按 `ef_search` 的规模访问索引节点，每个节点是一次随机页访问（PostgreSQL 页大小 8 KB）；取 `ef_search` = 100，单次查询就是约 100 次页访问、量级约 1 MB 的缓存足迹（100 × 8 KB ≈ 0.8 MB）。这个量与业务热集相比是大还是小，完全取决于**你的热集有多大**：热集是几百 MB 的库，向量查询会把热页挤出去；热集是几十 GB、缓存本来就装不全的库，向量查询的扰动可以忽略。判定方法：在压测里打开与关闭向量查询，对比业务查询的 P99 与 buffer 命中率。若差异可观测，正确的做法不是优化向量查询，而是**把向量查询搬到只读副本上**——这是族 1 最便宜的资源隔离手段，也是它相对族 2 的主要让步。

**【推算】索引构建的时间成本**：按 §7.3.2 的 O(N log N) 构建复杂度估算，若 100 万向量构建耗时 t，则 1000 万向量的构建耗时约为 t × 10 × (log 1000万 / log 100万) ≈ t × 12（【推算】，仅按复杂度关系外推，实际受并行度、内存带宽与磁盘影响，可能有数倍偏差）。这条外推的用途不是预测绝对值，而是提醒你：**「先上小规模验证，再扩到 10 倍」在索引构建上是 10 倍以上的时间成本**，因此扩容计划里必须给构建留出与数据量匹配的窗口，不能按线性外推排期。

### 7.5 决策树（每个分支都要有阈值依据）

```
第 0 层（硬约束，先行）：向量写入是否必须与业务写入同事务可见（写完即可检索、删除同步生效）？
├─ 是 → 只能在「数据已经住进去的那个库」里做向量（族 1）；不要引入独立检索系统
└─ 否 → 继续
第 1 层（选族）：`向量数 × 每向量字节数` 能否被单机缓存装下？
├─ 能（千万级以内，见 §7.4 算术）→ 族 1：关系库 + 向量扩展；若「原生」能力对你重要则换 AI 原生 DB
├─ 装不下但仍在亿级 → 族 2：专有向量库
│   ├─ 先量化（2×–32×）后能装下 → 单机形态：量化 + 精排补召回
│   └─ 量化后仍装不下 → 索引下移到本地 SSD（磁盘索引）并按需分片 → 集群形态
└─ 十亿级，或向量要与湖表同一份数据 → 族 3
    ├─ 发起检索的是在线等待的用户 → 向量湖：P99 靠缓存命中率与预热
    └─ 发起检索的是分析型负载（BI 工具探索 / 批处理相似性聚合）→ Lakehouse + Vector
第 2 层（过滤区分度）：WHERE 的选择率 p 是多少？
├─ p 高（筛不掉几行）→ 融合查询在哪执行都行；留在族 1 收益最大（少一套系统）
├─ p 低（1% 量级，如按租户 / 时间窗 / 权限过滤）→ 必须确认候选支持前过滤或迭代扫描，否则需 `ef_search ≳ K / p`
└─ 过滤字段来自业务表且会变 → 冗余进 payload 会引入同步问题，优先族 1 或族 3
第 3 层（团队与存量）：你有没有独立维护检索系统的编制？
├─ 没有 → 族 1，或族 2 的托管形态（Serverless），并接受单价随用量线性
└─ 已有检索栈且有人维护 → 复用该栈（向量作为它的一列）通常比新引入单库更快见效
```

**阈值依据**：

- **「同事务可见」**（第 0 层，无阈值）：这是正确性硬约束而非性能权衡，所以排在所有阈值之前（§7.3.3）。判定方法：写下两个具体操作——「写入后多久必须能被检索到」「删除用户数据时要删几个地方」，任一答案超过 1 就说明你不需要强制单库。
- **「千万级」**（第 1 层第 1 分支）：由 §7.4 的内存算术给出，不是任何产品宣称的上限。核对方法：`pg_relation_size('你的向量索引')` 与机器可用于文件缓存的内存对比；比值一旦超过 1，先用量化把拐点右移，而不是加机器。
- **「亿级」**（第 1 层第 2 分支）：同一个算术往下算——1 亿向量按每向量 4.2 KiB 是约 420 GB，int8 量化后仍有约 105 GB，**远超单机 32–64 GB 的缓存预算**，于是「每跳落盘」从偶发变成常态，「装不下」不再是调参能解决的问题：这一档要么靠磁盘索引把随机 IO 限制在可承受范围、要么靠分片——两者都是族 2 产品作为一等能力提供的，所以阈值落在族 2。它同时是族 2 与族 3 的分界：到十亿级，单节点本地 SSD 的容量与每跳 IO 预算也撑不住，才需要把驻留层再降到对象存储（见下一条）。
- **「量化 2×–32×」**（第 1 层第 2 分支的第一个子分支）：不是经验估计，而是编码长度的算术——fp32 到 fp16 是 2×，到 int8 是 4×，到 1 bit 是 32×（见 [Ch4-02](../02-vector-lake/02-vector-lake.md) §2.2 的压缩比表）。**量化把第 1 层的拐点按同一倍数右移，而不是把它取消**：以半精度与 int8 标量量化这两档（2×–4×）为例，每向量从约 4.2 KiB 压到 1–2 KiB 后，同样的 32–64 GB 缓存预算能装下的向量数从千万级变成 2,000 万–6,000 万（§7.4 的同一算术），这就是「千万级」那条阈值在半精度 / 标量量化下的对应值。注意压缩比与规模是两回事：1 亿向量的 fp32 索引约 420 GB、int8 后约 105 GB，仍远超这一预算——那个规模对应的是第 1 层第 2 分支的第二个子分支（换驻留层级），不是「拐点右移」的例子。
- **「十亿级」**（第 1 层第 3 分支）：来自「驻留层级必须下移到本地 SSD 或对象存储」这一条机制（§7.3.2），而不是某个产品的能力表；判定的实质是「索引是否还能主要驻留内存」。
- **「在线等待 vs 分析型负载」**（第 1 层第 3 分支的第二个子分支）：Lakehouse + Vector 的成立条件是「向量检索的调用方是分析型负载」而不是在线请求。判定方法：看发起检索的是谁——如果是人通过 BI 工具探索数据、或批处理任务在做相似性聚合，属于前者；如果是用户在页面上等待，属于后者。这条无需阈值，因为它问的是调用形态。
- **「p 高」**（第 2 层第 1 分支）：后过滤的过取倍数是 1/p（§7.3.4 的 `ef_search ≳ K / p`），p 接近 1 时这个倍数是 1，前过滤与后过滤不再有差别，融合执行位置因此不再是判据；此时剩下的判据只有运维单元数，所以在族 1 与已有栈之间选，不为融合能力换族。
- **「p < 1%」**（第 2 层第 2 分支）：由后过滤的期望命中式 `ef_search ≳ K / p` 反推（§7.3.4）：K = 10、p = 1% 时需要 `ef_search` 约 1000，此时检索耗时已远高于同规模前过滤。核对方法见 §7.3.4 的 `EXPLAIN (ANALYZE)` 对比。
- **「过滤字段来自业务表且会变」**（第 2 层第 3 分支）：这条判据问的是「数据源份数」而不是性能——过滤字段会变，意味着冗余进 payload 的那一份必须跟着变，同步与版本管理从一次性的转换工作变成常态运维（§7.3.4）。族 1 的过滤字段与向量同库、族 3 的同湖表，都不产生第二份数据源。判定方法：数一下改一个过滤字段要动几个系统，超过 1 个就不该冗余。
- **「有没有独立检索编制」**（第 3 层）：这是组织约束不是技术约束。多一套系统的边际成本，主要不是机器成本，而是「谁值班、谁升级、事故时谁被叫醒」——**一个没有检索值班人的团队引入第二套检索系统，等于把故障恢复的责任挂空**。

**一条不列入阈值依据的提醒（因为它不是阈值，而是执行顺序）**：后过滤与跨系统取数会让「按需过滤 + 向量排序」在 p 很小时性能坍塌（§7.3.4），而很多团队会把这种坍塌误判为「向量库不够强」并直接换族——**在没量出 p 之前换族，等于为一个未被诊断的问题付一次迁移成本**。它列在阈值依据之外，是因为树上没有一条阈值可以挂靠它，它是遍历顺序上的纪律：先定硬约束（第 0 层），再量出第 2 层的 p，最后才轮得到用第 1 层的规模去换族。

**这棵树刻意不覆盖的分支**（以及为什么）：

- **「要不要上 GPU 索引」**：GPU 只改变单位成本的常数项（每台机器的吞吐与构建速度），不改变「索引驻留层级」这个决定性变量。当瓶颈已经落在存储层级时，换 GPU 不解决问题。判定方法：先看 CPU 版的瓶颈是随机 IO 还是算力。
- **「要不要向量 + 图放进同一个产品」**：向量与图回答的是不同问题——向量检索擅长语义相似度但丢掉了符号关系，图擅长显式关系路径但对纯语义召回弱（见 [Ch1-07 图推理](../../01-modeling/07-graph-reasoning/07-graph-reasoning.md) §2.4「vs Embedding 检索（向量库）」）。判定方法是问「你的查询里有多少需要顺着关系走」，如果接近零，图能力只是采购清单上的一行。
- **「嵌入式向量库（进程内）要不要用」**：它适合单机、单副本、可整段重建的场景（本地工具、桌面应用、测试环境），判定方法是问「这个进程重启时索引能不能重建」，能重建就可以，不能就不行。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 商品 / 内容检索，百万级向量，要按类目价格过滤 | 关系库 + 向量扩展，或 AI 原生 DB | 专有向量库 | 专有库要冗余一份过滤字段，一致性缝合成本大于它省的算力 |
| 向量必须与订单写入同时可见 | 族 1（同事务） | 单库 + 精排服务 | 双写没有原子边界，删除漏一边不报错 |
| 千万–亿级、离线语料、更新以天计 | 专有向量库（配量化与磁盘索引） | 单库 + 半精度/量化 | 单库会撞内存墙，且量化后回召需要更多精排补偿 |
| 十亿级多模态、与湖表同一份数据 | 向量湖 / Lakehouse + Vector | 专有向量库分片 | 独立系统要再同步一份语料，湖上路线天然共用一份 |
| 尖峰型低 QPS（内部工具、Demo） | Serverless 向量库 | 单机 pgvector | 自建节点在闲置期是纯成本；但稳态高 QPS 时 Serverless 更贵 |
| 高频写入 + 高频删除（会话记忆、时效内容） | 族 1（MVCC 与清理成熟） | 专有向量库（看其删除回收机制） | 段式索引的删除回收与膨胀是长期运维项 |
| 分析任务里顺带做相似度（报表、探索） | Lakehouse + Vector | 把向量导出后离线算 | 在线检索引擎为高 QPS 优化，为低频分析付这份钱不值 |
| 已有 Milvus / ES 且有人维护 | 复用现有栈承载向量 | 迁到族 1 | 新建一套单库路线的迁移成本（向量回填 + SQL 改写）可能大于复用 |

**常见组合**（每条注明职责边界与运维代价）：

- **AI 原生 DB + RAG**（原 §7 组合）：单库承担「业务数据 + 向量 + 全文」的检索层，RAG 只负责编排与生成。边界是：数据库不负责切分与嵌入的版本管理，嵌入模型换了必须整列重算。运维代价最低，因为只有一套备份与监控。
- **AI 原生 DB + 向量湖**（原 §7 组合）：热数据（近 30 天、活跃租户）留在单库做实时检索，冷语料进向量湖做归档检索。边界是：**两边的向量必须用同一个嵌入模型**，否则分数不可比、结果无法合并。运维代价是多一套摄入管线与「哪些数据在哪一边」的明账。
- **AI 原生 DB + 数据 API 网关 / OneService**（原 §7 组合，见 [Ch4-06](../06-one-service/06-one-service.md)）：网关负责把 SQL 与向量查询包装成受权限约束的接口，数据库只管存与算。边界是权限判断只在网关，所以绕开网关的直连必须封死。运维代价是网关成为新增的可用性依赖。
- **AI 原生 DB + Agent**（原 §7 组合）：Agent 通过单库 API 完成检索与取数，避免 Agent 自己拼多源。边界是 Agent 产生的查询形态不可预测，必须限制返回规模与执行时间，否则一次错误查询能拖垮在线库。运维代价是必须为 Agent 单独设资源隔离或只读副本。
- **专有向量库 + CDC（而非双写）**：把同步收敛到一条有位点的通道上。边界是 CDC 只保证最终一致，业务侧要接受读己之写的缺口。运维代价是 CDC 集群与位点监控、以及幂等与乱序处理。
- **单库 + 量化 + 精排**：用半精度或标量量化把内存墙推远，用精排补回召回的损失。边界是量化只改变存储层级，不解决缓存命中问题。运维代价是重建索引的窗口变长（量化索引重建更贵）。

组合的原则只有一条：**每加一件，都要说清它负责哪一段边界，以及当它挂掉时谁来兜底。** 「单库 + CDC 同步出去的检索副本」里副本挂了，写入照常、检索降级到过期数据，兜底是延迟告警与位点重放；「网关 + 单库 + Agent」里网关挂了，Agent 全线不可用，兜底只能是网关自身的高可用——**这也是为什么能合并的边界尽量合并**。

**一条组合的边界否决线**：如果两件东西的「正确性依赖」互为对方的输入，就不能组合。例如「用向量库的检索结果去决定要不要删除业务库里的记录」——删除的正确性依赖检索的完整性，而检索的完整性又依赖同步通道的一致性，这个环在任何一路故障时都会变成静默的数据错误。组合可以用来分担负载、分担运维，**不能用来分担正确性**；正确性必须落在某一处并明确写在架构图上。

**组合的收益递减**：每加一件东西，收益来自它覆盖的那部分边界，成本来自它的运维单元数与一致性缝合。当一件东西覆盖的边界小于「缝合它所需要的代码量」时，它就是负收益。最典型的判据是：**如果你需要写一段代码来保证 A 和 B 是一致的，那么先问 A 和 B 能不能合并。** 大多数「AI 原生 DB + 向量湖」之外的组合，都能在合并之后少写这段代码，代价只是接受单库的规模上限——而规模上限是可以算出来的（§7.4），缝合代码的 bug 面是算不出来的。

### 7.7 选错的代价与迁移成本

**反模式：为百万级向量引入独立检索系统** —— 症状：只有两三百万条商品向量，却上了独立向量集群 → 后果：多一套备份、监控、升级与权限体系，外加一份同步与删除的缝补代码；而两三百万向量在单库路线的内存占用只有十几 GB 量级（§7.4 算术），根本不构成瓶颈 → 正确的做法：先在现有库上把「驻留比值」测出来，超过 1 再换族。

**反模式：把「向量检索变慢」当成配置问题** —— 症状：不断调 `ef_search`、`m`、`ef_construction`、分片数 → 后果：真正的瓶颈是索引已无法主要驻留（§7.3.2），调参只能在很小范围内挪动延迟，投入产出极低，且调低召回会让问题转移到下游 → 正确的做法：先量索引大小与缓存命中率，比值超过 1 就直接上量化或换驻留层级。

**反模式：用双写维持两套系统的同步** —— 症状：业务代码里同时写业务库与向量库，认为「反正失败了重试就行」 → 后果：双写成功率相乘、删除漏一边不报错（§7.3.3），不一致只在下游表现为「检索结果偶尔对不上」→ 正确的做法：要么留在单库，要么以 CDC / Outbox 为唯一同步通道（CDC / Outbox 属跨系统同步的「日志与事件型」机制，见 [Ch12-08 §7](../../12-architecture/08-data-consistency/08-data-consistency-section-7-sec7.md)；该章自己的「族 2」即此型，与本节的族 2「独立检索服务」不是同一义项）。

| 从 → 到 | 数据迁移 | 查询 / 接口改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 关系库（应用层算距离）→ 关系库 + 向量扩展 | 加列 + 回填全部向量（一次性，最大项） | SQL 小改（加距离算子与排序） | 低（同库，加索引与内存规划） | 索引参数与过滤先后策略 | 中 |
| 关系库 + 向量扩展 → 专有向量库 | 向量与 payload 全量导出，并补齐过滤字段 | 从 SQL 换成 SDK 查询语言 | 新增一套集群、备份、监控、权限 | 分片 / 量化 / 副本调优 | 高（主要落在运维与同步代码） |
| 专有向量库 → 向量湖 | 向量重写到湖表 + 索引重建（最大项） | 检索改为湖仓查询引擎语法 | 换成存算分离的运维模型 | 湖表格式与压缩整理 | 高 |
| 单机全精度 → 半精度 / 量化 | 向量重编码（一次性，可后台做） | 查询不变，但要重调 K 与精排强度 | 无（同库） | 召回损失的度量与补偿方法 | 低–中 |
| 双写 → CDC 单通道 | 对齐历史差异（挂账式补齐） | 业务代码删掉双写 | 加 CDC 集群与位点监控 | 幂等与乱序处理 | 中 |

关于迁移时机有一条容易被忽略的约束：**向量迁移不能只搬数据，还要搬「分数」**。如果迁移前后换了嵌入模型，那么历史向量与新向量不可比，必须整库重算；如果换了驻留层级或做了量化，那么召回分布会变，下游的精排与阈值都要重调。可操作的做法是把迁移拆成「先双读比对（新旧两路同时查，人工看差异）→ 再切读 → 最后切写」，每段之间留一个完整的业务周期——直接切写是最容易一次性暴露全部不一致的做法。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 向量要与业务写入同事务可见 | 族 1（已有库 + 向量扩展） | 同 WAL 同提交序，一致性免费 |
| 百万级、要按业务字段过滤 | 族 1 | 过滤在优化器内完成，不必冗余字段也不必跨系统 |
| 千万级、过滤区分度极低 | 专有向量库（前过滤）或量化 + 迭代扫描 | 后过滤需要 `ef_search ≳ K / p`，代价随 p 变小而放大 |
| 千万–亿级、离线语料 | 专有向量库 + 量化 / 磁盘索引 | 内存墙是唯一约束，量化把它按 2×–32× 推远 |
| 十亿级、与湖表数据同源 | 向量湖 / Lakehouse + Vector | 成本从内存换到存储，延迟用缓存与预热支付 |
| 尖峰型低 QPS | Serverless 向量库 | 成本函数从按节点变为按请求，闲置不付费 |
| 高频写入 + 高频删除 | 族 1 | 段式索引的删除回收与膨胀是长期运维项 |
| 团队没有检索值班编制 | 尽量合并边界，减少运维单元 | 多一套系统的真实成本是「谁被叫醒」 |

回到本章 6 条判据里权重最高的两条：**一致性边界**决定了候选集合（要求同事务可见的场景不允许引入独立检索系统），**驻留层级**决定了同一族内部的选择（能否驻留内存决定用全精度还是量化、留在单库还是换族）。这两条回答完，剩下的生态、许可、学习曲线才有讨论价值——顺序反了，讨论就永远停在偏好层面。

与原文件最大的方法论差别是：原文件给的是**结论**（「> 1 亿就用向量湖」），本章给的是**推导**（为什么阈值是内存算术的结果，以及它在你的维度与量化设置下应该是多少）。结论会随版本与本组织的技术栈过时，推导不会。

> 本节小结：这些候选之间唯一真正起决定作用的差异是**「向量索引住在哪、以及它和业务数据是不是同一份事务」**——前者（驻留层级）决定规模上限与成本函数的主项，后者（一致性边界）决定你能不能用最简单的方式写出正确的业务。其余维度（生态成熟度、SQL 友好、实时性）都是这两条的下游结果。
