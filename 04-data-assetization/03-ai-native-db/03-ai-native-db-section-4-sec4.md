## 4. 工程实现

本节只回答一个问题：**「向量住在哪里」这个决定（§3）之后，怎么真的把它建成一套能上线、能扩容、出问题能恢复的系统。** 术语沿用 §3：**索引体积 / 可用内存的比值**、**驻留层级**、**事实源与可重建的派生数据**、**预过滤 / 后过滤**——这些机制在 §3 已展开，本节不复述，只给步骤、判据、产物与迁移路径。

本文件同时服务两类读者，**第一步不同**。**从零搭建**（新业务、新库）从 4.1 的 Step 1 顺序走。**存量改造**（已经在 PostgreSQL 里跑着 pgvector，或已经上了独立向量服务，现在规模或一致性开始疼）先做 4.4 的第 ① 步——**先把比值量出来**——再回到 4.1 的 Step 3：Step 1–2 的结论在你这里通常已经由历史决定，真正缺的是量化、分区与恢复演练。

### 4.1 落地步骤

**Step 1：场景与规模评估（1–2 周）【经验，取决于能否拿到真实查询日志】**

1. 评估数据规模（百万 / 千万 / 亿），算「向量行数 × 维度 × 每维字节数」，并与机器可给索引缓存的内存做比值。
2. 评估查询模式：纯向量、标量过滤后向量、还是混合排序；是否还要多模态检索（文本之外的图像 / 音频模态）。记录过滤条件的**选择性**（命中比例 p）。
3. 评估 SLA：延迟（P50 / P95 / P99）与召回率（Recall@K）分开写，两者不是同一个指标。
4. 写下两个硬约束的答案：**写入后多久必须能被检索到**、**删除一条业务数据时要删几个地方**。

- **产物**：**AI 原生数据库需求说明书**——规模与维度、查询模式与过滤选择性、延迟与召回目标、上面两个硬约束的答案。
- **判据**：**算例必须落在纸上**：以 1024 维 fp32 为例，每向量 4 KiB（1024 × 4 字节），加上 HNSW 图链接（m = 16、双向、按 4 字节 id 计约 128 B）后约 4.2 KiB【推算，推导链：1024 维 × 4 字节/维 = 4096 字节，加图链接约 128 B，与 §7.4 引用的 §7.3.2 算式一致】；1000 万条即约 42 GB【推算，同上算术】。若可给索引缓存的内存是 32–64 GB【经验，需留给连接、排序、工作内存与 OS】，比值已接近 1——这个数决定后面所有步骤。比值答不上来，Step 1 没做完。
- **为什么必须这一步 / 为什么在这个位置**：**先算比值，再选产品**（§3.2.1 的判断方法与 §3.8 的三步顺序）。跳过这一步直接比产品，得到的典型状态是「性能评测很漂亮、上线几个月后内存先爆」，而那时换架构的成本远高于此刻多花的两周。

**Step 2：数据库选型（1–2 周）【经验，取决于候选数量与能否在两三个候选上跑通真实查询】**

1. 按 §3.3 决策表筛族：单库（pgvector）、云托管、多模型、传统 DB 厂商、分布式、嵌入式。
2. 同一族内再比产品，判据是团队熟悉度、生态、备份与权限能否沿用、是否接受托管方决定索引参数与升级窗口。
3. 至少验证一条：**把一条真实查询在两个候选上跑通并导出执行计划**，而不是看能力列表。

- **产物**：**选型 ADR**——沿用 4.5 模板 1 的「选型与索引登记表」：向量行数 × 维度、每向量字节数、索引体积实测、可用索引缓存内存、比值、写入后多久必须可检索、删除一条业务数据要动几处、退出条件；选了什么、否掉了什么、依据什么约束写在 ADR 正文里。
- **判据**：ADR 里能否写出「写入后多久可检索」与「删除要动几个地方」这两个答案；写不出，说明 Step 1 的硬约束没有传下来，选型只能靠偏好。
- **为什么必须这一步 / 为什么在这个位置**：一致性边界是**第 0 层硬约束**，「做不到就是做不到」（§7.5）。它在规模之前生效：规模不足是成本问题，可以用量化或加机器换；一致性缺失是功能缺失，事后只能用跨系统同步与补偿代码去缝。

**Step 3：Schema 设计（约 1 周）【经验，取决于是否已有分区与索引规范可沿用】**

1. 设计混合表：结构化列 + 向量列 + JSON 列同表；向量维度与 embedding 模型版本一起记录在表注释或元数据表中。
2. 设计索引：向量索引（HNSW / IVFFlat）+ 必要的标量索引，明确每个索引服务的查询形态。
3. 设计分区：按时间或类别分区，让分区裁剪把候选集压到一个分区内。
4. 明确 opclass 与距离算子的对应关系，避免「查询写法命不中索引」。

- **产物**：**Schema DDL**（含索引与分区定义）+ 一条「维度 / 模型版本 / 索引参数」的登记记录。
- **判据**：抽三条真实查询跑 `EXPLAIN (ANALYZE)`，确认计划里**出现向量索引扫描**（而不是全表扫描后排序），且 `ORDER BY` 的表达式与索引 opclass 严格对应；再确认建表语句里记下了维度与 embedding 模型版本——换模型时要知道哪些行需要重算。
- **为什么必须这一步 / 为什么在这个位置**：HNSW 与 IVFFlat 的召回 / 速度 / 内存权衡（§2.3 的表）在写 DDL 时就固定下来了，上线后改索引类型意味着一次全量重建。排在 Step 4 之前，因为向量列的类型与维度要先定，写入链路才有落点。

**Step 4：Embedding 集成（2–4 周）【经验，取决于离线回填量与限流策略】**

1. 集成 Embedding 服务（OpenAI / BGE / 通义等，例如 BGE-M3 是 1024 维、OpenAI `text-embedding-3-small` 是 1536 维，维度以各模型卡当前版本为准），把模型版本、维度、调用限额写进配置而不是散在代码里。
2. 建向量化 UDF 或写入侧封装（见 4.5 模板 4），把「文本 → 向量」固定成一条可复用的路径。
3. 离线回填与实时写入双链路分开，各自有幂等键与重试上限。
4. 给回填设速率上限，避免把 Embedding 服务打成瓶颈。

- **产物**：**可向量化写入的库**——一条离线回填脚本 + 一条实时写入路径 + 一张记录维度与模型版本的登记表。
- **判据**：抽 10 行数据，检查向量维度与登记表一致、且同一文本两次调用得到同一向量（幂等）；再用一次批量导入观察限流与重试是否按预期工作，而不是靠失败告警才发现。
- **为什么必须这一步 / 为什么在这个位置**：向量是**可重建的派生数据**（§3.4）——这条性质只有在「输入文本 + 模型版本 + 维度」三者都被记录下来时才成立。没记录，换模型时无法回答「哪些行要重算」，唯一选择是全量重跑。

**Step 5：融合查询实现（2–4 周）【经验，取决于过滤条件的组合数与是否需要改索引形态】**

1. 实现「标量过滤 + 向量排序」的单条 SQL，过滤条件与向量排序同一事务快照内完成。
2. 明确过滤与排序的先后：根据 Step 1 记下的选择性 p 选预过滤或后过滤（§7.3.4 的 `ef_search ≳ K / p`）。
3. 实现混合排序（RRF 或加权），并**把融合逻辑放在数据库侧或一个统一函数里**，不散落到多个服务。
4. 性能调优：先验证计划命中索引，再调 `ef_search`、`m`、`ef_construction` 一类参数。

- **产物**：**可用的 AI 查询接口**——含过滤 + 向量排序 + 混合排序，并附一份「在哪些选择性下验证过」的记录。
- **判据**：构造一个低选择性过滤（p 很小，按 §4 的选择性定义）的查询，检查返回行数**是否凑满 LIMIT**；凑不满说明过滤把候选集压小了，需要预过滤、迭代扫描或两级索引。同时抽一条混合排序查询，确认融合权重或 RRF 常数只在一处定义。
- **为什么必须这一步 / 为什么在这个位置**：它必须排在 Step 6 的压测之前——否则压测测的是「查询写法是否正确」，而不是系统能力；也必须在 Step 3 之后，因为策略选择依赖索引形态。

**Step 6：性能测试（1–3 周）【经验，取决于是否启用量化与能否拿到固定查询集】**

1. 召回率评估：以精确检索为基线算 Recall@K；启用量化（halfvec / bit）时必须做这一步的回归对比。
2. 延迟测试：P50 / P95 / P99 分开看，单独观察**延迟分布是否分裂**。
3. 并发测试：固定数据量、只增并发与分片数，看 P99 是否随分片数上升（分布式方案的必测项）。
4. 恢复测试：把索引重建耗时实测一次，并与 RTO 目标对比。

- **产物**：**性能基线**——召回率、延迟分位、并发曲线、索引重建耗时，四项都要有数。
- **判据**：**P99 与 P50 的差距是否稳定**；量化后召回下降是否在预期区间内；索引重建耗时是否小于 RTO。任何一项答不上来，基线不成立。
- **为什么必须这一步 / 为什么在这个位置**：这一步的两个产物（召回回归与重建耗时）是后面所有变更的对照物；没有基线，4.4 的迁移就没有退出判据，只靠「感觉变快了」。

**Step 7：上线与监控（持续）**

1. 灰度发布：按流量或按租户切分，先观察召回与延迟再放量。
2. 监控四件套：QPS / 延迟（分位）/ 召回率 / 错误率，另外**单独采集索引体积与缓存命中情况**。
3. 告警 + 自动扩容：延迟分位与召回下降都要有告警，扩容要区分「算力不够」与「索引已无法常驻内存」。
4. 把「写入后多久可检索」变成可观测指标（跨系统方案下即同步窗口）。

- **产物**：**生产级 AI 原生数据库**——含仪表盘、告警规则、扩容与回滚预案，以及一份「比值 / 召回 / 重建耗时」的定期核算清单。
- **判据**：仪表盘上能否直接看到「索引体积 / 可用内存」的比值与召回率趋势；做一次真实故障演练（例如临时禁止索引使用），确认回滚路径可执行。
- **为什么必须这一步 / 为什么在这个位置**：可观测是这一步唯一无法后补的事——平均延迟会掩盖 P99 分裂（见 4.2 第 10 条），等发现时通常已经在排查「查询写法」而不是「索引为什么不在内存里」。

**七步里最常被跳过的是 Step 1 的比值核算与 Step 6 的恢复测试。** 跳过比值核算的第一个症状出现在上线后 3–6 个月【经验】：QPS 没变、数据量翻倍，P50 看起来正常而 P99 高出一个数量级【经验】——团队会先怀疑查询写法，再怀疑参数，最后才发现索引根本没在内存里。跳过恢复测试的症状出现得更晚：真出事时业务表几十分钟恢复，向量索引重建按体积可能要数小时【经验】，而这个时间从未被写进 RTO。

### 4.2 关键技术点

**pgvector 安装与配置**

- **做法**：`CREATE EXTENSION IF NOT EXISTS vector;`；建表前先确认扩展版本（`\dx` 或 `SELECT extversion FROM pg_extension`），把版本要求写进部署检查项。
- **机制**：能力边界由扩展版本决定——HNSW 自 0.5.0（2023）起提供、`halfvec` 与 `bit` 自 0.7.0（2024）起提供、迭代扫描自 0.8.0（2024）起提供【公开，pgvector README / CHANGELOG，可按扩展名与版号自行核验】；发行版镜像与托管服务的版本往往滞后于上游。
- **失效条件**：**当扩展版本低于代码要求的版本时**（典型是镜像里的 0.4.x），这条会以建索引失败的形式坏掉。症状：`CREATE INDEX ... USING hnsw` 报「access method "hnsw" does not exist」，或 `halfvec` 类型无法识别；上线前用一条含 HNSW 与 halfvec 的冒烟 DDL 就能提前发现。
- **档位**：版本与年份为【公开】。

**HNSW 索引**

- **做法**：`CREATE INDEX ... USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);`；查询期用 `SET hnsw.ef_search` 控制召回 / 延迟，按召回回归结果定值而不是照抄默认值。
- **机制**：HNSW 是图索引，查询沿图逐跳扩展候选，`ef_search` 决定扩展多少个候选——所以召回与延迟由同一个旋钮控制，且查询过程是随机跳转，**命中率完全取决于索引是否常驻内存**（§3.2.1）。
- **失效条件**：**当索引体积超出可用缓存内存时**，这条会以「尾延迟随缓存命中率抖动」的形式坏掉，而不是报错。症状：P50 稳定、P99 高一个数量级【经验】；`pg_relation_size('你的向量索引')` 与可用于文件缓存的内存相比接近或超过 1。此时继续调 `m` / `ef_construction` 属于在掩盖结构问题。
- **档位**：默认值 16 / 64 与参数含义为【公开，pgvector 文档；默认值随版本变动，以 `\d <索引名>` 的实际输出为准】；「P99 高一个数量级」为【经验】。

**融合查询（过滤 + 向量排序）**

- **做法**：单条 SQL 内写 `WHERE` + `ORDER BY embedding <=> $1 LIMIT k`；先根据选择性 p 决定预过滤 / 后过滤，必要时用迭代扫描或标量 + 向量两级索引。
- **机制**：后过滤的期望命中倍数是 `ef_search ≳ K / p`（§7.3.4）——过滤越严格（p 越小），要维持 K 条结果就需要越多候选，成本线性放大；预过滤则把候选集先压小，但会让图索引在小区间里走不到足够邻域。
- **失效条件**：**当过滤选择性 p 很低（例如 p < 1%，§7.5 的量级判据）而仍用后过滤时**，这条会以「召回悄悄变少」的形式坏掉。症状：`WHERE` 加得越具体、返回条数越少，而应用层只检查「有没有结果」不检查「够不够 K 条」——这类错误不进监控，只进用户投诉。判别动作：对同一查询在高低选择性两端各跑一次，比对返回行数与 `EXPLAIN (ANALYZE)` 候选数。
- **档位**：`K / p` 关系为【推算，依据 §7.3.4 的推导】；「p < 1%」为量级判据【经验】。

**量化压缩（halfvec / bit）**

- **做法**：把列类型从 `vector(N)` 换成 `halfvec(N)`，或用 `bit` 做粗排 + 精确重排；换索引 opclass（`halfvec_cosine_ops` / `bit_hamming_ops` 一类）并重建索引。
- **机制**：压缩比是**编码长度的算术**，不是经验估计——fp32 → fp16 是 2×，→ int8 是 4×，→ 1 bit 是 32×（§7.5）。同样一份缓存预算能装下的向量数按同一倍数右移，拐点因此从千万级右移；**以半精度与 int8 标量量化这两档（2×–4×）为例**，每向量压到 1–2 KiB 后是 2000 万–6000 万【推算，依据 §7.4：32–64 GB ÷ 1–2 KiB/向量】。注意这个数**只对应 2×–4× 档**：压缩比与规模是两回事，1 亿向量的 fp32 索引约 420 GB、int8 后仍有约 105 GB，远超 32–64 GB 的预算（§7.5）——那一档要换的是驻留层级，不是把拐点再右移一次。
- **失效条件**：**当量化后没做召回回归、且量化用于精排阶段时**，这条会以「静默召回下降」的形式坏掉：延迟变好了，用户看到的答案变差了。症状：召回率没有基线可对照；正确做法是量化只做粗排、候选再用全精度重排（over-fetch + rerank），并且每次换量化方式都跑一次 Recall@K 对比。
- **档位**：压缩比为【推算，编码长度算术】；拐点右移后的量级为【推算，依据 §7.4 与 §7.5】。

**分区表**

- **做法**：按时间或类别分区（`PARTITION BY RANGE (created_at)` 或按类别），为每个分区单独建向量索引与标量索引；查询带上分区键。
- **机制**：分区裁剪把候选集限制在一个分区内，索引更小、更容易常驻内存——所以分区在本主题下的真实作用是**把比值压下来**，而不是管理方便。
- **失效条件**：**当查询不带分区键、或全局 top-k 需要跨所有分区归并时**，这条会以「分区越多越慢」的形式坏掉。症状：计划里出现对所有分区的扫描，延迟随分区数增长；此时分区只增加了管理面（预建分区、维护窗口），没有换来裁剪收益。
- **档位**：【经验】。分区粒度按数据保留周期与查询时间窗选，没有通用值。

**向量化 UDF（数据库内生成 Embedding）**

- **做法**：用 `plpython3u` 一类过程语言把「文本 → 向量」写成一个函数，必要时由 `BEFORE INSERT/UPDATE` 触发器调用（见 4.5 模板 4），但**默认推荐把调用放在写入侧应用或批处理里**，UDF 作为补充路径。
- **机制**：把 Embedding 调用放进事务，换来的是「写入成功即可被检索」这个单库性质；代价是**事务时长 = 外部 API 延迟**，而外部调用的抖动、限流与失败都会变成事务层面的问题（长事务、锁等待、回滚重试）。
- **失效条件**：**当批量导入或补数据量变大时**，这条会以「批量写入把库拖住」的形式坏掉。症状：导入期间大量锁等待与超时、连接池打满；缓解方式是批量走离线链路（先算好向量再写）、UDF 只服务单行实时写入，并给外部调用设超时与失败降级（写入空向量并由后台任务补齐，而不是让整个事务失败）。
- **档位**：【经验】。阈值取决于 API 延迟分布与并发写入量，不要照抄任何一个数字。

**混合排序（RRF / 加权）**

- **做法**：把向量排序与全文 / 关键词排序各自取排名，用 RRF（`1/(k + rank)`，k 常取 60 一类常数）或加权分数融合；融合逻辑写在一处（SQL 或数据库函数），参数进版本管理。
- **机制**：RRF 用的是**排名而不是原始分数**，所以两路检索分数不可比（余弦相似度 vs `ts_rank`）时仍然可以融合——这是它比加权分数更稳的原因，也是它在口径变更时更可控的原因。
- **失效条件**：**当融合逻辑散落在应用层多个服务时**，这条会以「口径变更要改多处」的形式坏掉：调一次权重需要同时发布多个服务，遗漏一处就出现同一问题两个答案。症状：不同入口对同一查询给出不同排序；判别动作是搜代码里 `1.0 / (60 +` 一类的融合表达式出现在几个地方。
- **档位**：k = 60 为常见取值【公开，Reciprocal Rank Fusion 原始论文，Cormack / Clarke / Buettcher，SIGIR 2009，题为《Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods》，可按该标题自行检索核验；具体常数以团队召回回归结果为准】。

**事务一致性**

- **做法**：让向量与业务行同表或同库同事务写入；确实跨系统时，只允许一条同步通道（CDC / Outbox 一类），并写下可接受的同步窗口。
- **机制**：同库同事务使「业务写入成功」与「向量可被检索」是**同一个提交点**，不需要同步窗口——这是单库方案唯一无法被跨系统方案替代的性质（§3.2.1）。
- **失效条件**：**当业务代码双写业务库与向量库、且删除路径只覆盖一边时**，这条会以「检索到已删除数据」的形式坏掉（§7.7 反模式三）。症状：删除后仍能召回、回滚后仍能召回；判别动作是写下「删除一个用户要动几个地方」，答案超过 1 处就需要补偿机制，而不是靠重试。
- **档位**：机制陈述，无数字。

**备份恢复（PITR + 跨区域复制）**

- **做法**：业务数据用 PITR（时间点恢复）+ 跨区域复制；向量索引按「是否可重建」分类：可作为派生数据的允许重建，但**重建耗时必须实测并计入 RTO**；关键场景保留向量列的独立备份。
- **机制**：恢复时间 = 恢复数据 + 重建索引，而重建时间随体积增长（构建复杂度约 O(N log N)，§7.3.2）——所以「索引可以重建」这句话只有在重建时间被量过之后才成立。
- **失效条件**：**当 RTO 里只算了数据恢复、没算索引重建时**，这条会以「演练时才发现」的形式坏掉。症状：业务表恢复几十分钟，索引重建要数小时【经验】，超时后只能降级为无向量检索。
- **档位**：【经验】。重建耗时按 §7.4 的复杂度关系外推，实际受并行度、内存带宽与磁盘影响。

**可观测（pg_stat_statements + Prometheus）**

- **做法**：`pg_stat_statements` 采集语句级统计，Prometheus 采集 QPS、延迟分位、连接池、缓存命中；另外单独采集**索引体积**、**数据量**与**召回率**（用固定查询集定期跑）。
- **机制**：索引是否常驻内存这件事**不会出现在查询日志里**——它表现为随机 I/O 命中率，所以必须单独算成比值并画成趋势线；平均延迟会把 P99 分裂抹平。
- **失效条件**：**当监控只覆盖 QPS 与平均延迟时**，这条会以「故障被发现得太晚」的形式坏掉。症状：延迟告警长期不响，直到用户投诉召回变差；判别动作是看仪表盘上有没有「索引体积 / 可用内存」与「召回率」两条曲线。
- **档位**：【经验】。

### 4.3 工具链与平台

选型的第一判据是**索引住在哪一层、谁维护它、以及它能不能导出**——不是功能清单长短。产品与版本更新频繁，请以各自官方文档当前版本为准。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 主路线（同库） | PostgreSQL + pgvector | 业务数据已在 PG、要求「写入即可检索」、索引体积 / 可用内存比值 < 1 | 跨库同步窗口与一致性补偿代码（§3.3 的误选对） |
| 托管 PG | Supabase / Neon | 是否接受托管方决定扩展版本与升级窗口；Neon 偏 Serverless 形态，Supabase 带 API 与应用层能力 | 自管备份、升级与扩展版本兼容 |
| 时序 + 向量 | TimescaleDB + pgvector / pgvectorscale | 按时间窗口过滤是否是查询常态；时序压缩与降采样是否为主需求（§3.3 表） | 用纯向量方案硬扛时序负载，压缩与降采样要自建 |
| 云厂商托管 | Snowflake Cortex Search / Databricks Vector Search / AWS Aurora + pgvector | 数据与索引是否必须留在同一云、同一区域；先区分「厂商自有向量服务」与「托管起来的 pgvector」两类（§3.2.2） | 跨云迁移要重建索引，出网流量随数据量计价 |
| 国内云 PG 兼容 | 阿里云 PolarDB / 腾讯云 CynosDB | 向量能力是否与云内既有权限、审计、备份体系同源；数据驻留与合规是否要求留在本地云 | 多开一套权限与审计模型，合规举证要另做 |
| 多模型原生 | SurrealDB / SingleStore / ArangoDB / Azure Cosmos DB | 同一实体的文档 / 图 / 向量 / 时序查询深度是否均衡——某一类占比低于一成【经验】时，复杂度很可能高于收益（§3.2.3） | 引擎研发资源被分摊，每一项都不到专用深度 |
| 传统 DB 厂商 | Oracle 23ai AI Vector Search / SQL Server + 向量 | 向量索引是否随既有备份、权限、审计自动纳管；DBA 与安全团队是否必须沿用原流程（§3.2.4） | 为不使用的企业特性付费，同时承担陌生引擎的排障成本 |
| 分布式 | TiDB Vector | 业务是否已跑在分布式 OLTP 上、向量与业务行是否要一起水平扩展；向量检索占查询比例是否低于一成 | 全局归并的乘法效应：完成时间由最慢分片决定，P99 随分片数上升 |
| 嵌入式 / 轻量 | DuckDB VSS / Chroma / SQLite + sqlite-vss / LanceDB Embedded | 是否存在第二个并发写者——有就越界；这类方案不得进入在线服务路径（§3.2.6） | 在 PoC 阶段好用、进在线服务后遇上不可并发写与不可跨机的硬约束 |

这一类里**最容易被误选的是「在只有两三百万向量时就上独立向量集群」**（§7.7 反模式一）：两三百万条 1024 维向量在单库路线的索引体积是十几 GB 量级【推算，3 × 10^6 × 4.2 KiB ≈ 12.6 GB】，根本不构成瓶颈，却换来了多一套备份、监控、升级、权限，以及一份同步与删除的缝补代码。反向的误选同样常见：把亿级向量放进单库，索引无法常驻内存、主库备份被拖住。**这两种误选是可以事前避免的**——先测比值，再决定要不要拆。

### 4.4 存量迁移

**① 先做只读、可回退、立刻见效的一件事：把比值量出来。** 在生产库上跑只读查询，得到索引体积（`pg_relation_size`）、数据量与机器可用于文件缓存的内存，算出比值并记下来。它不改变任何东西、零风险、当天可完成，而且是后面所有决策的输入。第二步同样可回退：**在一个只读副本或评估环境上把 HNSW 建起来，用固定查询集跑一次 Recall@K 基线**。有了这两个数，才谈得上改什么。

**② 历史资产分类处理，不要全部返工。** 存量系统里的「历史资产」有三类，各有各的处理方式：

- **全部返工**（仅限少数）：向量数据——**换 embedding 模型或换维度时，所有存量向量都必须重算**，这是不可打折的一类。判据是维度与模型版本是否变过；变了就必须整列重算，并把重算排进容量窗口（按 §7.4 的复杂度关系，重算量与构建量的量级同阶）。
- **只改动的部分**：新写入路径。新数据按新类型（例如 `halfvec`）与新索引参数走，历史行保持 `vector` 不动；**混合列类型在实践中会把查询与索引搞成两套**，所以更稳的做法是加一列新类型、后台回填、回填完成后再切换。
- **打标挂账**：历史行里「长期不被检索到」的那部分（冷数据、已下线业务的向量）不做返工，只打标并给一个「是否仍在索引内」的可查询口径。挂账不是不管——清单要能被查到，否则以后查不到结果时无法区分「没有这条数据」和「这条数据不在索引里」（§3.4 的表述）。

**③ 双轨怎么维持、维持多久。** 在「主库 + 独立向量层」的迁移里，双轨就是：业务库为**唯一事实源**，向量层为**可重建的派生索引**，同步只走一条通道（CDC / Outbox 一类），并把不一致窗口显式写下来当做 SLA 的一部分。迁移期的纪律有三条：一是**删除路径必须同时覆盖两处**，二是**重建演练在切换前做一次**（不是切换后），三是**读路径要有降级开关**（向量层不可用时退回标量检索或返回空并显式标注）。双轨按 1–2 个季度设【经验，随数据量与删除路径的改造难度变化】，判断依据不是时间，而是下面三个信号。

**④ 什么信号说明可以退出双轨。** 三个可核验的信号，全部满足再退：一是**「删除一个用户要动几个地方」的答案回到 1**（这说明事实源与派生数据的关系已经稳定，窗口内的不一致有明确补偿）；二是**索引重建耗时实测落在 RTO 之内**，且这条数来自演练而不是估计；三是**在高低两种过滤选择性下都凑得满 LIMIT**，召回率不低于迁移前基线。三个信号里任何一个不过，退出双轨只是把一次内存问题换成一次一致性事故。

### 4.5 模板 / 示例

**模板 1：选型与索引登记表（填在 ADR 里）**

```markdown
# ADR-{YYYY-MM-DD}: {引擎与索引选型}

| 项 | 值 |
| --- | --- |
| 向量行数 × 维度 | {N × D} |
| 每向量字节数 | {D × 4（fp32）/ × 2（fp16）/ ÷ 8（bit）} |
| 索引体积（实测） | {pg_relation_size 结果} |
| 可用索引缓存内存 | {GB，已扣除连接 / 排序 / OS} |
| 比值 | {体积 ÷ 内存，这是主要上限} |
| 写入后多久必须可检索 | {答案 1} |
| 删除一条业务数据要动几处 | {答案 2} |
| 退出条件（什么情况下重审） | {例如比值 > 1、召回基线下降} |
```

**怎么用**：前五行必须来自实测与算术，**不要填产品文档里的「推荐规模」**；后两行是硬约束，答不出来说明还没到选型这一步。这张表的价值不在于填完，而在于半年后你能对着它判断「是规模变了，还是当年的假设错了」。

**模板 2：pgvector 安装、建表与索引（含分区与量化）**

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE products (
  id BIGSERIAL PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  description TEXT,
  category VARCHAR(50),
  price INT,
  embedding vector(1024),        -- 例如 BGE-M3 的 1024 维；维度与模型版本要登记，换模型即需重算
  embedding_model VARCHAR(64),   -- 例如 {模型名与版本}
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 按时间分区（让分区裁剪把候选集压小，索引更易常驻内存）
CREATE TABLE products_partitioned (
  LIKE products INCLUDING ALL
) PARTITION BY RANGE (created_at);

CREATE TABLE products_2026_q1 PARTITION OF products_partitioned
  FOR VALUES FROM ('2026-01-01') TO ('2026-04-01');

-- 向量索引（opclass 必须与查询里的距离算子对应）
CREATE INDEX ON products USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- 标量索引（服务过滤条件，配合两级索引策略）
CREATE INDEX ON products (category);
CREATE INDEX ON products (price);

-- 量化：先加新列回填，再切换索引，便于回退
ALTER TABLE products ADD COLUMN embedding_h halfvec(1024);
UPDATE products SET embedding_h = embedding::halfvec(1024) WHERE embedding_h IS NULL;
CREATE INDEX ON products USING hnsw (embedding_h halfvec_cosine_ops);
```

**怎么用**：`{模型名与版本}` 那一格换成你的真实模型标识并保持更新；`m` / `ef_construction` 先用默认值跑基线，再按召回回归结果调。**量化那一段不要直接 `ALTER COLUMN TYPE` 覆盖原列**——加列回填可以回退，覆盖类型不可逆。

**模板 3：融合查询与混合排序（RRF）**

```sql
-- 标量过滤 + 向量排序（注意：<=> 余弦、<-> L2、<#> 负内积，按官方文档当前版本核对）
SELECT id, name, price, category
FROM products
WHERE category = 'phone'
  AND price BETWEEN 1000 AND 5000
ORDER BY embedding <=> $1
LIMIT 10;

-- 混合排序（RRF）：融合逻辑只写在一处
WITH semantic AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank
  FROM products WHERE category = 'phone'
),
keyword AS (
  SELECT id, ROW_NUMBER() OVER (
    ORDER BY ts_rank(to_tsvector('english', name || ' ' || description), query) DESC
  ) AS rank
  FROM products, to_tsquery('english', 'smartphone | camera') query
  WHERE category = 'phone'
)
SELECT p.id, p.name, p.price,
       (1.0 / (60 + s.rank)) + (1.0 / (60 + k.rank)) AS rrf_score
FROM semantic s JOIN keyword k USING (id) JOIN products p USING (id)
ORDER BY rrf_score DESC
LIMIT 10;
```

**怎么用**：第一条查询用来看**过滤选择性对返回条数的影响**——把 `category` 换成更严格的条件再跑一次，看是否还凑得满 10 条；第二条的 `60` 是 RRF 常数，改成别的值要进版本管理。两条都要用 `EXPLAIN (ANALYZE)` 确认走的是向量索引扫描而不是全表排序。

**模板 4：向量化写入（UDF + 触发器，离线优先）**

```sql
CREATE EXTENSION IF NOT EXISTS plpython3u;

CREATE OR REPLACE FUNCTION embed(text) RETURNS vector(1024)
LANGUAGE plpython3u AS $$
  # 生产实现：读配置的密钥与模型名、设超时、失败返回 NULL 而不是抛异常
  # 客户端调用形态以 openai-python 1.x 为例（模块级 openai.Embedding 在 1.0 之后已移除）；换用 BGE / 通义等其它 embedding 服务时按其客户端替换，并保持同一返回结构
  # 返回维度必须与 products.embedding 的向量列维度一致（本例 1024，对应 BGE-M3）
  from openai import OpenAI
  client = OpenAI()
  response = client.embeddings.create(input=text, model='{你的 embedding 模型，例如 BGE-M3}')
  return response.data[0].embedding
$$;

CREATE OR REPLACE FUNCTION auto_embed() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  NEW.embedding := embed(NEW.name || ' ' || COALESCE(NEW.description, ''));
  RETURN NEW;
END;
$$;

CREATE TRIGGER products_auto_embed
BEFORE INSERT OR UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION auto_embed();

-- 查询侧用法（每次查询都会调用一次外部服务，线上慎用）：SELECT name FROM products ORDER BY embedding <=> embed('{查询文本}') LIMIT 10;
```

**怎么用**：触发器路径适合**单行实时写入**；批量导入与历史回填走离线链路（先算好向量再 `COPY` 入库），否则外部 API 的延迟会变成事务时长与锁等待。函数里必须设超时并明确失败时写 NULL 还是写零向量——这个选择决定了后续有没有一个「待补齐」的后台任务。

**模板 5：SurrealDB 多模型查询**

```sql
-- 多模型：同一引擎里文档 + 向量 + 图
DEFINE TABLE products SCHEMAFULL;
DEFINE FIELD name ON products TYPE string;
DEFINE FIELD description ON products TYPE string;
DEFINE FIELD category ON products TYPE string;
DEFINE FIELD embedding ON products TYPE array<float>;
CREATE products:1 SET name = 'iPhone 15',
  description = 'High quality smartphone',
  category = 'phone',
  embedding = $embedding;

-- 向量检索
SELECT name, vector::distance::cosine(embedding, $embedding) AS dist
FROM products ORDER BY dist ASC LIMIT 10;

-- 图查询与多模型联合（同一查询里同时下推向量与图两类谓词，才是多模型的判据）
SELECT ->purchased_by->user.name AS buyers FROM products:1;
SELECT name, count(<-purchased_by) AS buyer_count,
       vector::similarity::cosine(embedding, $1) AS score
FROM products WHERE category = 'phone' ORDER BY score DESC LIMIT 10;
```

**怎么用**：这段用来验证「同一查询里能否同时下推向量与图两类谓词」——**这才是多模型库的判据**，靠应用层拼装两次查询不算。具体函数名与语法（`vector::distance::cosine` 一类）请以 SurrealDB 官方文档当前版本为准；若语法对不上，说明你评估的是另一个版本。

### 4.6 成本：这套东西的账单

三项里真正相关的是**内存 / 算力**与**Embedding API 账单**；人力集中在选型与回填。它的成本结构由 §4.1 Step 1 那一个比值决定——**向量索引必须常驻内存才不走随机 I/O，所以主成本是内存，不是 CPU**。

- **内存（主成本）**：以 §4.1 的算例，1000 万条 1024 维 fp32 约 42 GB，若缓存预算给 32–64 GB，比值已近 1【推算，沿用 §4.1 的 4.2 KiB/向量 与 32–64 GB 预算】。一台能装下这个索引的云主机按内存计价，落在「每月数百–数千美元」量级【经验，单价以你所选云厂商的实例定价页当前版本为准】。**这个主题贵在内存**，因为它把「数据规模」直接翻译成「常驻内存需求」，而内存的单价高出磁盘约两个数量级【经验】。
- **Embedding API**：按 token 计价【经验，单价以各模型厂商定价页当前版本为准】。离线回填是一次性的大头（全量文本 × 单条 token × 单价），实时写入是持续的小头。
- **人力**：集中在 Step 1 的比值核算与 Step 5–6 的查询实现与基线（各以「周」计，见 §4.1 各步的【经验】周期），不集中在运维——单库路线下没有多一套集群要养。
- **最便宜的一档是压缩**：halfvec 2×、int8 4×、bit 32× 是**编码长度的算术**（§2.2 表列 halfvec 2× 与 bit 32×，int8 4× 见 §7.5），换档比加机器便宜得多。所以别先扩算力，先算比值与压缩比。

通用的 FinOps 方法见 [11-cross-cutting/03 数据成本与 FinOps](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节只说它在本主题里为什么落在「内存」这一行。

### 4.7 容灾与故障演练

§4.2「备份恢复（PITR + 跨区域复制）」已给出这条机制的骨架，本节只补**演练视角**：什么先坏、怎么降级、恢复目标怎么定。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 向量索引被挤出内存（比值 > 1） | 尾延迟，P99 高一个数量级【经验】 | 降 `ef_search` / 缩小召回 / 加两级索引 | 压测中逐步灌数据把索引挤出内存，观察 P99 分裂点 | 不是「恢复」，是结构性扩容 |
| 索引损坏或需重建 | 向量检索不可用 | 退回标量检索，或返回空并显式标注 | Step 6 第 4 条：实测一次索引重建耗时 | 重建耗时 < RTO，否则 RTO 不成立 |
| 跨系统同步中断（拆库方案） | 向量与业务数据的不一致窗口拉大 | 读路径退回事实源（标量） | 切断 CDC / Outbox 通道，量窗口与补偿 | 同步窗口写进 SLA【经验】 |
| Embedding 服务不可用 | 写路径无法生成新向量 | 写入占位向量 + 后台补齐任务 | 停掉 Embedding 端点，看事务是否被拖住 | 恢复后补算，不阻塞业务写 |

**本主题的容灾有一个特殊性**：向量是**可重建的派生数据**（§3.4），所以 RPO 通常可以放松（重建出来即可），但 **RTO 反被重建耗时绑架**——「索引可以重建」这句话只有在重建时间被实测过之后才成立（§4.2 的失效条件）。因此这一节的恢复目标不是「数据不丢」，而是「**重建耗时落在 RTO 之内**」，这条要用演练的数字，不能用估计。通用容灾与真切换演练见 [Ch12 §07 容灾](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md)，混沌实验设计见 [Ch12 §06 混沌工程](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)。

### 4.8 演进路线：0 → 1 → 100

| 阶段 | 做什么 | 先坏的是什么 | 变贵的是什么 |
| --- | --- | --- | --- |
| 0 → 1 | PostgreSQL + pgvector 单库，向量与业务行同事务 | **过滤选择性**：p 极低时后过滤凑不满 LIMIT（4.2 融合查询） | 几乎没有新增成本——复用既有 PG 的备份、权限、监控 |
| 1 → 100 | 加分区、量化（halfvec / int8）、建召回回归基线 | **比值**：数据翻倍后索引被挤出内存，P50 正常而 P99 高一个数量级【经验】 | **内存**：为让索引常驻而扩容；此时量化比加机器便宜 |
| 100 → | 亿级向量：独立向量层 / 分布式 / 磁盘驻留索引 | **一致性**：拆库后「删除要动几处」「同步窗口」都回来了（§3.2.1 的单库性质消失） | **缝补代码与运维**：多一套备份、监控、同步与补偿——这是本主题唯一的跃迁代价（§3.6） |

**一条主线**：这个主题的演进**围绕「比值」旋转**——0→1 比值远小于 1，一切简单；1→100 比值逼近 1，先用内存扩、再用压缩换回空间；100→ 单库比值压不回 1，只能换驻留层级，代价从「内存」变成「一致性」。每个阶段的账单都由同一个数驱动，与你上的是哪个引擎无关。

### 4.9 自检清单

- [ ] 是否算过「向量行数 × 维度 × 每维字节数」，并与可用索引缓存内存做过比值判断？比值接近或超过 1 时，尾延迟不可控。
- [ ] `EXPLAIN (ANALYZE)` 中是否确实出现向量索引扫描，而不是全表扫描后排序？
- [ ] `ORDER BY` 的距离算子与索引 opclass 是否严格对应（例如 `vector_cosine_ops` 配余弦算子）？
- [ ] 带 `WHERE` 的向量查询，是否在低选择性条件下检查过「返回行数是否凑满 LIMIT」？
- [ ] 若启用量化（halfvec / bit），是否跑过召回率回归对比，并说明量化用于粗排还是精排？
- [ ] 向量写入与业务写入是否在同一事务？若跨系统，同步窗口大小是否写进了 SLA 并有补偿机制？
- [ ] 索引重建耗时是否实测并纳入 RTO，而不是按「它很快」来假设？
- [ ] 每个向量列是否记录了 embedding 模型与维度，且知道换模型时要重算哪些行？
- [ ] 混合排序（RRF / 加权）的融合逻辑是否只写在一处，参数是否进版本管理？
- [ ] 监控里能否直接看到「索引体积 / 可用内存」与「召回率」两条趋势，而不只有 QPS 与平均延迟？
- [ ] 若为多租户，租户过滤是编译期强制注入，还是靠应用层自觉？
- [ ] 若使用嵌入式方案，是否确认它不会进入在线服务路径（存在第二个并发写者即越界）？

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **Step 1 的比值核算——「向量行数 × 维度 × 每维字节数」除以「可用索引缓存内存」**。它比选哪个引擎更值得投入，因为它是唯一能事前算出来的量：比值小于 1，后面所有参数调优都有意义；接近或超过 1，调 `ef_search`、`m`、分片数都只是在掩盖一个结构问题（§3.2.1 的判断方法）。第二个必须提前回答的是「写入后多久必须可检索、删除要动几个地方」——它决定要不要拆库，而拆库的代价一旦付出，就只能靠同步窗口与补偿代码长期承担（§7.5 第 0 层）。其余步骤都在为这两个答案服务：Step 3–6 建立可对照的基线与召回回归，Step 7 让比值与召回率变成看得见的曲线。
>
> 💡 **思考锚点**：把你的向量库代进 Step 1 的比值算一次——向量行数 × 维度 × 每维字节数 ÷ 可用索引缓存内存等于多少？小于 1，后面调 ef_search / m 才有意义；接近或超过 1，先按 §3.2.1 把它降下来再谈调参。再补一个数：从写入到可检索的窗口，和你 SLA 里承诺的那条差多远？
