## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

AI 原生数据库的选型文章常常写成一张对照表：中小规模用 PostgreSQL + pgvector，云上用 Snowflake / Databricks，多模型用 SurrealDB，大企业用 Oracle 23ai，亿级以上上专用向量库。这张表的问题不在结论，而在它把设计讲成了「按场景挑一个」，读者读完仍然不知道自己的系统属于哪一格。

本主题的真正分水岭只有一条：**向量是不是和业务数据活在同一个事务里**。向量与业务行同库同事务，就能做到「写入即可被检索」，代价是向量体积直接压在主库上；向量被放到另一个系统里，检索规模可以做得很大，代价是必须自己承担同步窗口与一致性补偿。所有模式都是在这条线上的不同落点。

第二条约束是**数据形态的多元程度**：只查向量与标量，一套索引就够；还要同时查 JSON、图关系、时序，才轮到多模型库出场。第三条是**规模与成本**——向量存储是纯粹的体量问题，而体量决定索引能否常驻内存，索引是否常驻又直接决定检索尾延迟。这三条主线（以及下表所列的次级约束）决定了后面每个模式的代价落在哪里。

需要提前说明一个容易混淆的点：本节讲的「模式」是**向量住在哪里**，不是「用哪个产品」。同一个产品可以承载多种模式——PostgreSQL 既可以是模式一（业务与向量同库），也可以只是模式二的实现载体（Aurora 上的 pgvector）；DuckDB 既可以是模式六（本地评估），也可以出现在离线批处理链路里。**先确定住处，再选产品**，反过来会得到「产品选对了、数据放在错的地方」的结果。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态与模型数量（标量 / 向量 / JSON / 图 / 时序） | 是否需要多模型库，还是单模型 + 应用层拼装 | 「多模型一定要用多模型库」——四个模型里三个只占 1%【经验】时，统一带来的收益低于每项都不到专用深度的损失 |
| 向量与业务数据是否需强一致 | 单库事务还是跨系统异步同步 | 「最终一致够用了」——下单一秒内不能被检索，在推荐与风控里就是错的 |
| 规模（向量行数 × 维度） | 索引能否常驻内存，从而决定尾延迟与成本 | 「向量库只受算法限制」——先撞墙的通常是内存与 I/O，不是算法 |
| 查询模式（纯向量 / 标量过滤后向量 / 混合排序） | 索引类型与过滤策略（预过滤还是后过滤） | 「加了 HNSW 就一定快」——带 WHERE 的向量查询若先过滤，可能连 LIMIT 条都凑不齐 |
| 更新频率与历史要求 | 索引重建成本与增量嵌入能力 | 「索引建一次就行」——写入频繁时索引维护本身成为负载 |
| 团队技能与合规要求 | 选通用生态还是厂商绑定，选开源还是商业 | 「最新特性代表能力」——用团队不熟的引擎，省下的研发时间会在排障时还回去 |
| 备份恢复目标（RTO / RPO） | 索引是否必须独立备份，还是允许重建 | 「索引可以重建」——重建时间随体积增长，可能直接超出 RTO |

### 3.2 模式逐个拆解（核心节）

六个模式的区别可以先用一句话对齐：**向量住在哪里**。住业务库里（模式一、四），住云厂商的托管服务里（模式二——它内部还分两小类：厂商自有的向量服务，与把模式一整体托管到云上的 pgvector，见 3.2.2），住一个多模型引擎里（模式三），住分布式 KV 之上（模式五），住在进程内（模式六）。下面的结构块依次画出这五种住处，以及每种住处的代价。

每个模式都按同一组问题展开：**被什么约束逼出来 / 结构 / 为什么有效 / 代价 / 失效点 / 真实使用**。之所以把「失效点」单独列为一栏，是因为在这个主题下，模式的失效几乎总是同一类原因——**索引体积跨过某个阈值后，原本的部署形态与内存假设不再成立**。模式不会因为「不够先进」而失败，只会因为「规模变了但住处没变」而失败。

#### 3.2.1 PostgreSQL + pgvector（最主流）

- **被什么约束逼出来**：业务数据已经在 PostgreSQL 里，而「写入即可被检索」要求向量与业务行同库同事务——跨库做不到。
- **结构**：向量是普通列，索引是普通索引。

```sql
CREATE TABLE products (
  id        BIGINT PRIMARY KEY,
  name      TEXT,
  category  TEXT,
  price     INT,
  embedding halfvec(768)          -- 0.7+ 起支持 float16；旧版本用 vector(768)
);

CREATE INDEX ON products USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);   -- 默认值

-- 融合查询：标量过滤 + 向量排序，同一事务快照内完成
SELECT id, name FROM products
WHERE category = 'phone' AND price < 5000
ORDER BY embedding <=> $1
LIMIT 10;
```

- **为什么这样设计有效**：因为向量列与业务列在同一张表、同一个 MVCC 事务里，所以「业务写入成功」与「向量可被检索」是同一个提交点，不需要同步窗口——这是单库方案唯一无法被跨系统方案替代的性质。
- **代价**：向量体积进入主库（行数 × 维度 × 每维字节数【推算】：1 亿行 × 768 维 float32 = 3 072 字节/行 ≈ 307.2 GB；halfvec 减半 ≈ 153.6 GB；768 位二值化 ≈ 96 字节/行 ≈ 9.6 GB）。pgvector 的 HNSW 索引同时保存向量副本与图结构，m=16 时每元素最多 32 条链接、按 4 字节 id 约 128 字节，相对 3 072 字节/行约 4%【推算】，因此工程上常按向量体积的 1.0–1.5 倍估索引体积【经验】。备份、扩容、迁移都被这个体量放大。
- **失效点**：当索引体积超出可用内存时，「单库事务一致」的优点反转成「尾延迟随缓存命中率抖动」——因为 HNSW 查询沿图随机跳转，随机 I/O 的命中率完全取决于索引是否常驻内存。第二个失效点是带过滤的查询：`WHERE` 选择性高时，先用索引再过滤可能凑不满 `LIMIT`（pgvector 0.8.0 起提供迭代扫描来缓解【公开】pgvector 发布说明，2024，可自行核验）。
- **真实使用**：pgvector 自 0.1 起提供向量类型，0.5.0（2023）加入 HNSW，0.7.0（2024）加入 halfvec 与 bit 类型【公开】pgvector README / CHANGELOG；距离算子 `<->`（L2）、`<#>`（负内积）、`<=>`（余弦）语义以官方 README 为准。零运维门槛（无需额外系统）是它在中小规模 RAG 中成为默认选择的原因，而不是它性能最好。
- **判断方法**：把「索引体积 / 可用内存」算成一个数。小于 1 且有余量，这个模式成立；接近或超过 1，后面每一条参数调优都是在掩盖一个结构问题。

#### 3.2.2 云厂商 AI 原生 DB（Snowflake Cortex / Databricks Vector Search / Aurora + pgvector）

- **被什么约束逼出来**：团队不愿自建向量服务，而数据已经在云上数仓里——把向量能力做成托管服务，让索引与计算随用量伸缩。
- **结构**：向量索引托管在存算分离的云服务内，与应用通过云内网络访问。

```text
云厂商托管向量能力（存算分离 + 云内网络）
   应用 / Agent
        │  云内调用（鉴权走云 IAM）
        ▼
   [托管向量索引服务]──── 与数据所在的数仓 / 湖仓同区域
        │                     · 索引由厂商维护与重建
        │                     · 计算按用量弹性
        ▼
   [对象存储上的数据]（存算分离，数据留在云内）
   ────────────────────────────────────────────
   关键：索引与数据同区域 → 跨区流量为零；一旦跨云/混合部署，这条前提消失
```

- **为什么这样设计有效**：因为索引维护（重建、压缩、参数调优）被移到厂商侧，团队只保留「写入向量 + 查询」两条路径，所以小团队也能获得一套持续演进的向量检索能力。
- **代价**：绑定云厂商的托管实现，索引参数与能力边界由厂商发布节奏决定；向量数据体量大，跨云迁移与出网流量会按数据量线性计价【经验】。
- **失效点**：当业务需要跨云、混合部署或数据必须留在特定区域时，「零运维」的优点反转成「迁移与合规的双重约束」——因为托管索引的形态由厂商定义，你无法把它整体搬到另一朵云上。
- **真实使用**：Snowflake Cortex Search、Databricks Vector Search、Amazon Aurora PostgreSQL 的 pgvector 扩展【公开：来源形态 = 三份产品官方文档中与该功能同名的条目——Snowflake 文档的 Cortex Search、Databricks 文档的 Vector Search（两者自 2024 年起开放）、AWS 文档的 Aurora PostgreSQL 扩展列表中 pgvector 一项（2023 年起支持）；版本与区域可用性以各文档当前内容为准】。Aurora + pgvector 属于「模式一搬到云上」，与 Snowflake / Databricks 的「厂商自有向量服务」是两种不同形态，选型时要区分。
- **判断方法**：问「索引参数与重建策略由谁决定」。答「厂商」且无法导出索引本身，就属于本模式；能把索引定义与参数写进自己的迁移脚本，则更接近自建。

#### 3.2.3 多模型原生 DB（SurrealDB / SingleStore / TigerData）

- **被什么约束逼出来**：同一个业务实体需要同时被文档、图关系、向量与时序查询——跨库拼装要写 ETL 与补偿逻辑。
- **结构**：一个引擎内多种数据模型，同一实体可同时带边、带向量、带时间序列。

```text
多模型库里的一个实体（文档 + 图 + 向量 + 时序共存）
  user:1001
    ├── 文档字段：{name, tier, created_at}
    ├── 向量字段：profile_embedding: [0.12, -0.98, ...]
    ├── 图关系：follows → user:2044 / works_at → org:7
    └── 时序：活动量（activity_1d: 2026-10-01 → 12, 10-02 → 19, ...）
  ────────────────────────────────────────────
  一次查询可跨模型：向量相似 + 沿边走 2 跳 + 过滤时序窗口
  代价：每种模型的索引与执行器都由同一个引擎实现
```

- **为什么这样设计有效**：因为不同模型共享同一个存储与事务边界，「按向量找相似用户，再沿关系扩两跳」可以在一次查询里完成，不需要把中间结果导出到另一个系统。
- **代价**：同一引擎要实现四套索引与执行路径，深度通常不如各自的专用系统；生态规模与人才池远小于 PostgreSQL，出问题时可参考的资料也少。
- **失效点**：当四个模型的使用深度严重不均衡（例如 99% 是向量检索、图只占 1%【经验】，比例按自己的查询日志统计）时，「统一」的优点反转成「每一项都不到专用深度」——因为引擎的研发资源被分摊在多个模型上，而你的负载只用到其中一个。
- **真实使用**：SurrealDB 2.x（多模型原生，2024）、SingleStore（HTAP + 向量）、TigerData（TimescaleDB 团队，时序 + 向量，2024）【公开：来源形态 = 各项目官方文档中与该功能同名的条目——SurrealDB 文档的多模型与向量检索条目、SingleStore 文档的向量索引条目、TigerData 文档的时序 + 向量条目；版本细节以各项目文档当前内容为准】。判断某引擎是否真多模型：看它是否在同一查询计划里能同时下推两类模型的谓词，而不是靠应用层拼装两次查询。
- **判断方法**：统计各模型的**查询占比**。若某一类模型占比低于一成【经验】，它带来的复杂度（索引维护、升级风险、人力缺口）很可能高于收益。

#### 3.2.4 传统 DB 厂商拥抱 AI（Oracle 23ai / SQL Server / PostgreSQL + pgvector）

- **被什么约束逼出来**：大型企业已有数据库资产、审批流程与合规审计要求，不允许为向量单开一套系统。
- **结构**：向量是一等数据类型，距离计算是一等函数。

```sql
-- Oracle 23ai 风格：向量类型 + 距离函数 + 向量索引
CREATE TABLE docs (
  id        NUMBER PRIMARY KEY,
  body      CLOB,
  dept      VARCHAR2(32),
  embedding VECTOR(768, FLOAT32)
);
CREATE VECTOR INDEX docs_vec_idx ON docs (embedding)
  ORGANIZATION NEIGHBOR PARTITIONS
  DISTANCE COSINE;

SELECT id FROM docs
WHERE dept = 'RISK'
ORDER BY VECTOR_DISTANCE(embedding, :q, COSINE)
FETCH FIRST 10 ROWS ONLY;
```

- **为什么这样设计有效**：因为向量能力长在原有引擎里，权限模型、备份策略、审计日志、SQL 工具链全部沿用，DBA 与安全团队不需要学习第二套系统——这在大企业里的价值往往高于性能。
- **代价**：按核数与内存计价，而向量索引倾向常驻内存，因此成本随索引体积上升；向量能力通常绑定较新的大版本，升级路径受厂商发布节奏约束。
- **失效点**：当成本敏感或团队对该厂商生态不熟时，「合规与 IT 友好」的优点反转成「TCO 与学习成本的双重负担」——因为你在为不使用的企业特性付费，同时承担陌生引擎的排障成本。
- **真实使用**：Oracle Database 23ai 的 AI Vector Search【公开：Oracle 官方文档的 *Oracle AI Vector Search User's Guide*（23ai，2024）】；SQL Server 侧的向量数据类型与向量索引【公开：Microsoft 官方文档中与该功能同名的条目，随 SQL Server 2025 提供，支持范围以文档当前内容为准】；PostgreSQL 侧见 3.2.1 的 pgvector。判断方法：确认向量索引是否随既有备份 / 恢复 / 权限体系自动纳管——不纳管就失去了「沿用企业 IT 流程」这个主要收益。

#### 3.2.5 分布式 AI 原生 DB（TiDB Vector / CockroachDB + 向量扩展）

- **被什么约束逼出来**：向量检索要服务的业务本身已经跑在分布式 OLTP 上，要求向量与业务行一起水平扩展、一起进事务。
- **结构**：每分片各自持有局部向量索引，查询时各分片取候选再全局归并。

```text
分布式向量检索：局部索引 + 全局 top-k 归并
   查询（向量 q, LIMIT k）
        │
   ┌────┼────┬────────────┐
   分片1 分片2 分片3 …   分片N        ← 每片一份局部 HNSW / IVF 索引
   top-k top-k top-k     top-k
   └────┴────┴────────────┘
        │  归并候选 ≈ N × k 条【推算】
        ▼
   全局 top-k（回表取标量列 + 事务快照）
   ────────────────────────────────────────────
   关键：分片数越多，单次查询触及的分片越多，归并与网络成为固定开销
```

- **为什么这样设计有效**：因为分片是数据分布的边界，向量索引跟着数据走，写入与业务行一起落在同一个分布式事务里，「下单即可检索」在水平扩展后依然成立。
- **代价**：每次查询都要触及所有相关分片并归并，网络往返与尾延迟随分片数增长；向量索引在每个分片内独立维护，重建与再平衡都要按分片进行。
- **失效点**：当向量检索从「附带能力」变成主负载时，「水平扩展」的优点反转成「全局归并的乘法效应」——因为完成时间由最慢的分片决定，而触及的分片数随集群规模上升；纯向量场景下，专用向量库的单查询路径更短。
- **真实使用**：TiDB 在 Serverless 形态引入向量检索（2024，Beta）、CockroachDB 在 24.2 引入向量索引（2024，Preview）【公开：来源形态 = 两项目官方文档的向量检索条目与对应版本的发布说明；具体版本与状态以官方发布说明当前内容为准】。判断方法：压测时固定数据总量、只增加分片数，观察 P99 是否随分片数上升。

#### 3.2.6 嵌入式 / 客户端 AI 原生（DuckDB VSS / Chroma / SQLite + sqlite-vss）

- **被什么约束逼出来**：数据量小、无运维预算、且索引必须跟着应用走（本地工具、桌面应用、CI 与离线评估）。
- **结构**：索引是进程内对象，或本地文件。

```sql
-- DuckDB VSS 扩展（实验性）：进程内 HNSW 索引
INSTALL vss; LOAD vss;
CREATE TABLE docs (id BIGINT, body TEXT, emb FLOAT[768]);
CREATE INDEX docs_emb_idx ON docs USING HNSW (emb);
SELECT id FROM docs ORDER BY array_cosine_distance(emb, $1) LIMIT 10;
```

- **为什么这样设计有效**：因为索引与数据都在本地文件里，没有网络往返、没有服务进程，检索延迟的确定性来自「无跨进程通信」，也让它成为评估与迭代阶段最省事的方案。
- **代价**：单进程、单机。写入并发受限、无法跨机扩展、无高可用与在线重建能力；数据量上限由本机内存与磁盘决定。
- **失效点**：当它从 PoC 进入在线服务时，「零运维」的优点反转成「不可并发写 + 不可跨机」的硬约束——因为嵌入式引擎的并发模型是进程级独占，多写者要么排队要么损坏。
- **真实使用**：DuckDB 的 vss 扩展（HNSW 索引，实验性）、Chroma（嵌入式向量库，LangChain 生态常用）、SQLite 的向量扩展（sqlite-vss 及其后继实现）【公开：来源形态 = DuckDB 官方文档的 *Vector Similarity Search*（vss）扩展条目、Chroma 官方文档、sqlite-vss 仓库 README；扩展的实验性标注与支持范围以各项目当前文档为准，实验性能力不承诺稳定】。判断方法：看它是否需要「服务进程」——不需要，则它不具备在线扩容与高可用。
- **判断方法**：把「是否有多写者」作为第一道门。只要存在两个并发写进程（例如后台任务 + 前台服务），嵌入式方案就已经越界，与数据量无关。

六个模式的失效点读下来，会看到同一条机制最常被撞到：**代价不是由算法决定的，而是由索引体积与可用内存的比值决定的**。模式一到六，多数时候是在回答同一个问题——当这个比值不再安全时，向量搬到哪里去。理解了这一点，选型就可以从「对比功能列表」变成一次简单核算：先量体积，再量内存，剩下的选择会被约束自己推出来。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 向量 ≤ 千万级、业务已在 PG、要求写入即可检索 | PostgreSQL + pgvector | 不选专用向量库：跨库同步窗口会破坏强一致 | 索引体积是否小于可用内存（这是主要上限） |
| 数据已在云上数仓、团队不做索引运维 | 云厂商 AI 原生 DB | 不选自建：索引维护的人力成本高于托管溢价 | 是否接受数据与索引留在同一云、同一区域 |
| 同一实体需同时查文档 + 图 + 向量 | 多模型原生 DB | 不选「PG + 图库」拼装：跨库事务与补偿逻辑要自己写 | 四个模型的使用深度是否均衡 |
| 企业已有 Oracle / SQL Server / DB2 资产、合规审批重 | 传统 DB 厂商 + 向量能力（Oracle 23ai / SQL Server / DB2 一类） | 不选新引擎：安全团队与 DBA 流程要重做 | 向量索引是否随既有备份与权限体系纳管 |
| 分布式 OLTP + 附带向量检索 | 分布式 AI 原生 DB | 不选单机方案：业务行本身必须水平扩展 | 向量检索占总查询比例是否低于 1 成 |
| PoC / 本地工具 / 离线评估 | 嵌入式（DuckDB VSS / Chroma） | 不选云服务：无网络、无运维预算 | 是否需要多进程并发写（需要就别选它） |
| 时序 + 向量（监控、IoT、设备画像） | TigerData 一类时序 + 向量 | 不选纯向量库：时序压缩与降采样是主需求 | 按时间窗口过滤是否为查询常态 |
| 向量 ≥ 亿级或需独立的向量生命周期管理 | 专用向量库 / 向量湖 | 不选 AI 原生 DB：索引无法常驻内存，成本失控 | 索引体积 / 可用内存的比值是否已接近 1 |
| 写入高频、要求检索立即反映最新数据 | PostgreSQL + pgvector（同事务） | 不选跨系统同步：窗口内检索到旧数据在业务上不可解释 | 业务能否容忍「写入后 x 秒才可检索」的窗口 |
| 模型 / 框架更新频繁、需要低成本回放评估 | 嵌入式（DuckDB VSS / Chroma） | 不选线上服务：评估流量会污染生产指标 | 是否能在本地完整重建一份可比的索引 |

上表的规模判据都是量级阈值：其中「千万级」「亿级」两档，连同判定它们的「索引体积 / 可用内存比值是否接近 1」，都由「向量数 × 每向量字节数」与可用缓存内存的算术推出【推算】，推导与阈值依据见 [§7 与其他方法对比](03-ai-native-db-section-7-sec7.md) §7.4–§7.5；「占比低于一成」是查询占比的量级判断【经验】。

表下说明：本主题下**最常被误选**的是「就在 PostgreSQL 里加个 pgvector」与「直接上专用向量库」这一对。误选的方向取决于有没有算过内存：没算过内存的团队常把亿级向量放进 PG，结果是索引无法常驻、尾延迟随缓存命中率抖动、主库被大备份拖住；而另一侧，习惯性上专用向量库的团队先付出的却是跨库同步与一致性补偿的长期成本——**同步窗口每天都会出问题，而内存问题通常半年才撞一次**。

第二个常见误选是「混合排序」的层次问题：许多团队把向量检索与全文检索放在应用层各自查询后再合并，看起来灵活，实际上把排序融合的逻辑从数据库挪到了服务代码里——一旦排序口径改变，需要同时改多个服务。若两者的融合规则是业务语义（例如 RRF），它应当靠近数据，而不是散落在应用层【经验】。

Oracle 23ai 与 SQL Server 的向量能力见 3.2.4，PostgreSQL 侧见 3.2.1 与 3.2.4，DB2 侧的向量能力与对应版本请以 IBM 官方文档核验。

### 3.4 组合模式：真实系统不会只用一种

1. **业务库 + 向量库（事件同步）**：构成——PostgreSQL 承载业务事实与标量过滤，专用向量库承载大规模型召回。职责边界——业务库是唯一事实源，向量库是可重建的派生物。运维代价——需要一套同步与补偿机制，并明确可接受的检索延迟窗口。适合规模——向量亿级以上、且能接受「写入后可检索」存在秒级窗口（亿级阈值为【推算】，与 3.3 表同一判据，推导见 [§7 与其他方法对比](03-ai-native-db-section-7-sec7.md) §7.4–§7.5）。
2. **嵌入式索引 + 云端服务（开发与生产分离）**：构成——本地用 DuckDB / Chroma 做评估与回归，线上升级为托管向量服务。职责边界——同一份 embedding 的两套索引必须可从同一数据源重建。运维代价——两套环境的索引参数会漂移，需要把「索引参数」纳入版本管理。适合规模——算法迭代频繁、需要低成本回放的团队。
3. **多模型库 + 对象存储（热冷分层）**：构成——多模型库只装热数据（近线窗口内的向量与图），历史数据留在对象存储。职责边界——向量索引只覆盖热数据，冷数据按需回填。运维代价——需要一套「哪些数据在索引里」的可查询口径，否则查不到结果时无法区分「没有」和「不在索引里」。适合规模——总量大但近期活跃比例低的业务（内容、订单、日志画像）。

```text
业务库 + 向量库的分工（谁是可重建的派生物）
  写入路径：业务事务提交 ──► 事实源（业务库）
                      └──► 发向量变更事件 ──► 向量库（派生索引）
  读取路径：一次查询同时打两边 ──► 业务库出标量与权限，向量库出候选
  ────────────────────────────────────────────
  不一致窗口 = 事件投递 + 索引写入（可观测，可补偿）
  关键：事实源只有一处，向量库的任何丢失都可以重建
```

三种组合的共同前提是**明确「什么可以被重建」**：向量库里的向量、嵌入式索引、冷数据回填，都是可从事实源重建的派生物；而业务行、原始文本、原始文件是不可重建的事实源。把这条分清之前就做组合，一定会在某次数据不一致时不知道该以哪一边为准。**重建成本决定可用性上限**——你只能承诺「重建时间」以内的恢复目标。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 亿级向量用 pgvector | 索引体积接近或超过可用内存、延迟随缓存命中率抖动 | 随机跳转的查询命中率下降，P99 高出一个数量级【经验】，主库备份与扩容被拖住 | 选型时按「能不能存下」判断，而不是按「索引能不能常驻」判断 | 先算索引体积 / 可用内存的比值；超阈值时拆出向量层或量化（halfvec / bit） |
| 无索引（顺序扫描） | EXPLAIN 显示全表扫描、延迟随行数线性上升 | 每次查询都是 O(N) 距离计算，只有在数据极小或过滤后行数极少时才可接受 | 建表时未建索引，或建了索引但查询写法未命中 | 先确认计划里出现向量索引扫描，再谈调参（HNSW / IVF） |
| FP32 不压缩 | 索引与备份体积远超预期，内存账单先超预算 | 存储与内存按维度线性放大，成本先于性能成为瓶颈 | 默认类型是 float32，没人评估过精度损失是否可接受 | 用 halfvec（0.7+）或二值化做粗排 + 精确重排，用召回率回归验证损失 |
| SQL 写法低效 | 写了 `ORDER BY ... LIMIT` 但计划没走索引 | 排序不可下推到索引，退化为全量计算后排序 | 距离算子写错（用函数包裹列）或排序表达式与索引 opclass 不匹配 | 让 `ORDER BY` 的表达式与索引 opclass 严格对应，用 EXPLAIN 验证 |
| 融合查询无优化 | 加 `WHERE` 后返回行数少于 `LIMIT`，或过滤后召回明显下降 | 「先过滤后排序」在过滤选择性高时凑不满结果；「先排序后过滤」则浪费召回预算 | 把向量检索与标量过滤当成两个独立阶段，未意识到索引与过滤的交互 | 明确预过滤 / 后过滤策略，必要时用迭代扫描或两级索引（标量索引 + 向量索引） |
| 忽视事务一致性 | 业务写入成功后短时间内检索不到，或回滚后仍能检索到 | 向量与业务数据分属两个提交点，产生可见性窗口与脏召回 | 把向量当成「派生数据、可以稍后同步」，未评估业务对此窗口的容忍度 | 让向量与业务行落在同一事务；确实要跨库时，明确窗口大小并给出补偿机制 |
| 盲目追求新特性 | 团队看不懂执行计划与错误日志，排障全靠厂商工单 | 能力未转化为生产力，且把运维路径交给外部 | 用特性列表做选型，未评估团队对该引擎的熟悉度 | 先用团队熟悉的引擎跑通链路，再按真实瓶颈决定是否换引擎 |
| 忽视备份恢复 | 备份策略只覆盖业务表，向量索引从未验证过恢复 | 恢复时需重建索引（耗时随体积增长），RTO 不可控 | 向量索引被当成「可重建的临时结构」，没人把它纳入恢复演练 | 把索引重建时间纳入 RTO 测算，并定期演练；关键场景保留向量数据的独立备份 |

三个最危险的反模式在生产中的典型暴露方式：

- **亿级向量用 pgvector**：它的暴露不是报错，而是**延迟分布的分裂**——P50 看起来正常，P99 高出一个数量级【经验】；团队先怀疑查询写法，再怀疑参数，最后才意识到索引根本没在内存里。等到主库备份窗口被向量体积撑爆时，问题已经无法在数据库内解决。
- **融合查询无优化**：它的暴露方式是**召回悄悄变少**。`WHERE` 加得越具体，返回条数越少，而应用层通常只检查「有没有结果」不检查「够不够十条」。这类错误不会进监控，只会进用户投诉。
- **忽视备份恢复**：它的暴露方式是**恢复时才发现**。业务表恢复只要几十分钟，向量索引重建按体积可能要数小时【经验】，而这个时间从未被写进 RTO。演练一次就能发现，但多数团队直到真出事才演练。

上表中「无索引」「SQL 写法低效」「融合查询无优化」这三条属于同一族：**它们都在同一个查询路径上，且都以「延迟或召回悄悄变差」的形式出现**。它们的共性诊断方法是把一次真实查询拆成三段可观测的量——向量索引扫描返回了多少行、过滤掉了多少行、最终排序前有多少候选。三者中任意一段出现数量级异常，就能定位到具体哪一条。表中「FP32 不压缩」不在此列：它的代价先落在存储与内存账单上，上面这三段查询量对它不敏感。

而不收集索引体积、不检查召回、不做恢复演练这三类问题，成本不在查询延迟上，而在**某一天突然变成事故**：延迟尖刺、召回缺失、恢复超时。它们不适合用延迟监控发现，只适合用定期核算（体积 / 内存比值、召回回归、恢复演练）发现。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：向量行数、维度或写入频率跨过阈值时，原来正确的模式会变成错的。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 向量 10 万 → 100 万 | 无索引 / 顺序扫描 | 距离计算次数随行数线性增长，延迟进入秒级 | HNSW 或 IVF 索引 | 需要评估召回率损失与构建时间 |
| 向量 100 万 → 1000 万 | FP32 + 单库 | 索引体积与内存需求开始挤压主库 | halfvec / 二值化 + 粗排重排两段式 | 需要一次召回率回归，精度损失必须可量化 |
| 向量 1000 万 → 亿级 | 单库 pgvector | 索引无法常驻内存，P99 抖动、备份与扩容受限 | 向量层独立（专用向量库或向量湖），业务库保留事实数据 | 需要同步机制与一致性窗口定义，且向量变成可重建的派生数据 |
| 写入从批量到高频流式 | 全量重建索引 | 重建频率跟不上写入，检索结果滞后 | 增量写入 + 定期重建的混合策略 | 需要把「索引新鲜度」变成可观测指标 |
| 查询从纯向量到带强过滤 | 先排序后过滤 | 过滤后凑不满 `LIMIT`，或召回质量下降 | 预过滤 + 迭代扫描 / 两级索引 | 需要在不同选择性下分别验证召回与延迟 |
| 单机嵌入式 → 在线服务 | DuckDB / Chroma | 并发写与跨机访问都是硬约束 | 服务化方案（托管或自建） | 需要把索引与数据的生命周期从「进程内」迁移到「服务侧」 |
| 单库 → 多租户 | 每租户一套索引 | 租户数量使索引份数线性增长，内存被份数而非总量挤爆 | 共享索引 + 强制租户过滤（编译期校验，而非应用层过滤） | 需要改造过滤器与权限模型，并验证越界在技术上不可能 |

上表的规模取值（10 万 / 100 万 / 1000 万 / 亿级）与延迟量级是情景判据【经验】，用于说明「何时该换」，不是任何产品的性能上限；其中「1000 万 → 亿级」一档的亿级阈值不由情景判断给出，而与 3.3 表的「千万级 / 亿级」同源，由「向量数 × 每向量字节数」与可用缓存内存的算术推出，属【推算】，推导见 [§7 与其他方法对比](03-ai-native-db-section-7-sec7.md) §7.4–§7.5。

值得单独强调的一次跃迁是「**1000 万 → 亿级**」：它不只是换引擎，而是**数据所有权的改变**。在此之前，向量与业务数据同库，向量是业务行的一部分；跨过阈值之后，向量成为可重建的派生数据，必须回答三个新问题——同步窗口多大、重建要多久、重建期间检索降级到什么程度。答不出这三个问题就换引擎，等于把一次内存问题换成一次一致性事故。

还有一类跃迁容易被忽略：**查询形态的变化**。同一条链路，从「纯向量相似」变成「强过滤 + 相似」，同一个索引的可用性会下降——因为过滤把候选集压小后，图索引的邻域遍历可能走不到足够多的候选。这类跃迁不需要换引擎，但需要换查询策略（预过滤、迭代扫描、两级索引）并重新做一次选择性扫描，确认在高低选择性两端都能凑满 `LIMIT`。

### 3.7 自检清单

- [ ] 是否算过「向量行数 × 维度 × 每维字节数」，并与可用内存做过比值判断（比值接近或超过 1 时，尾延迟不可控）？
- [ ] 带 `WHERE` 的向量查询，返回行数是否检查过「是否凑满 LIMIT」？
- [ ] `EXPLAIN` 中是否确实出现向量索引扫描（而不是全表扫描后排序），且距离算子直接作用于向量列、`ORDER BY` 表达式与索引 opclass 严格对应？
- [ ] 量化（halfvec / bit）如果启用过，是否做过召回率回归对比？
- [ ] 向量写入与业务写入是否在同一事务？若跨系统，同步窗口大小是否被明确写出？
- [ ] 索引重建耗时是否纳入 RTO，并做过一次真实演练（而不是假设它很快）？
- [ ] 若使用多模型库，各类模型的查询深度是否均衡（避免为不到一成的用途付全部的复杂度【经验】）？
- [ ] 若使用分布式方案，是否做过「固定数据量、只增分片数」的 P99 压测？
- [ ] 若使用嵌入式方案，是否确认过它不会进入在线服务路径（并发写会直接失败）？
- [ ] 是否明确记录了「哪些向量索引属于可重建的派生物、哪些属于唯一事实源」，以及每条向量数据的维度与 embedding 模型版本（换模型时必须知道哪些数据要重算）？
- [ ] 混合排序（向量 + 全文，如 RRF 一类融合）的逻辑放在数据库侧还是散落在多个服务里？
- [ ] 若为多租户，租户过滤是在编译期强制注入，还是靠应用层自觉？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 向量 ≤ 千万级、要求写入即可检索 | PostgreSQL + pgvector | 同库同事务使「写入成功」与「可检索」是同一个提交点 |
| 数据已在云上、不做索引运维 | 云厂商 AI 原生 DB | 索引维护外移，代价是能力边界与数据位置由厂商定义 |
| 同一实体跨文档 / 图 / 向量 / 时序 | 多模型原生 DB | 共享存储与事务边界，避免跨库拼装与补偿逻辑 |
| 企业已有 DB 资产与合规流程 | 传统 DB 厂商 + 向量能力 | 权限、备份、审计沿用既有体系，省下流程重建成本 |
| 分布式 OLTP + 附带向量检索 | 分布式 AI 原生 DB | 索引随数据分片，向量与业务行一起水平扩展 |
| PoC / 本地 / 离线评估 | 嵌入式（DuckDB VSS / Chroma） | 无网络与服务进程，迭代成本最低，但不具备在线属性 |
| 向量 ≥ 亿级或需独立生命周期 | 专用向量库 / 向量湖 | 把索引从主库内存压力中解耦，代价是同步与一致性窗口 |
| 强过滤 + 向量相似并存 | 两级索引（标量 + 向量）或迭代扫描 | 索引与过滤的交互决定召回是否够，不能只调索引参数 |
| 写入高频且要求检索即时 | 同库同事务（模式一 / 四） | 一致性只能靠同一个提交点保证，派生索引必然有窗口 |

> 本节小结：本主题下**最先要算、也最常被撞到的那条约束**是「索引能不能常驻内存」——它同时决定延迟分布、成本结构和是否需要把向量拆出主库。而「向量与业务数据是否同一事务」决定了拆出去之后要付多少一致性代价。表中的规模阈值（千万级 / 亿级）与 3.3、3.6 两张表同源，属【推算】，依据见 [§7 与其他方法对比](03-ai-native-db-section-7-sec7.md) §7.5。
>
> 落到动作上顺序只有三步：**先算体积与内存的比值**（决定单库还是双库），**再确认向量是否需要独立生命周期**（决定是否让向量变成可重建的派生数据），**最后才比较具体产品**（HNSW / IVF 参数、量化方式、托管形态）。跳过第一步直接比产品，得到的往往是「性能评测很漂亮、上线几个月后内存先爆」的典型状态。
>
> 💡 **思考锚点**：用你当下的向量规模算一次「向量行数 × 维度 × 每维字节数」与可用内存的比值——它离 1 还有多远？若已接近或超过 1，你是否还把向量放在业务主库里？按「先算比值、再判独立生命周期、最后比产品」的顺序，你现在该做的是哪一步？
