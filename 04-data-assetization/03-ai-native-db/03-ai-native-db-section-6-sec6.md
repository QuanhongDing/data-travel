## 6. 落地实践

### 6.1 某电商"**把 AI 能力注册成 SQL 函数：数据不出仓做推理 4+ 年**"（2020-2024）

**背景（Why）**

该电商 2020 年面临**"AI 要用数据、数据不能出仓"的两难**：
- **模型在 Python 侧**——**情感分类、文本向量化、图像打标这些推理都需要数据，而数据在数据仓库里**
- **导出即失控**——**为了跑推理把评价文本、订单数据导出到 AI 集群，副本脱离仓库权限与审计**
- **合规压力**——**用户评论等信息属于敏感数据，导出后无法回答"这份副本被谁用过"**
- **业务方等不起**——**每次要一个新标签都要找 AI 团队排期做离线作业，迭代被卡住**

**触发点（What）**

2020 年该电商推进**AI Function in SQL**（[案例 2020-2024]），目标：
- **AI 在仓内执行**——数据不出仓
- **业务自助**——业务方写 SQL 即可调用 AI 能力
- **每次调用可审计**

**详细做法（How）**

该电商 AI in SQL 的**5 大核心组件**：

1. **把 AI 能力注册成 SQL 函数（核心创新）**
   - 关键设计：**向量化、分类、大模型调用等 AI 能力统一注册为 SQL 函数（UDF）**；业务方在 SELECT 里直接调用，推理在仓库侧执行
   - 关键能力：**"AI 能力"从需要跨系统协作的工程项目，变成 SQL 里的一次函数调用**——这是业务自助能成立的前提
   - 关键数字：**100+ AI 函数、数据出仓 0**
   - 关键示意：
     ```sql
     -- AI 能力注册为 SQL 函数，推理下推到仓库内执行
     CREATE FUNCTION embedding(text)             RETURNS vector AS 'ai.embed';
     CREATE FUNCTION classify(text, ARRAY<STRING>) RETURNS STRING AS 'ai.classify';
     CREATE FUNCTION caption(image_uri)          RETURNS STRING AS 'ai.caption';

     -- 业务方自助：一条 SQL 完成打标 + 向量化，数据不出仓
     SELECT order_id,
            classify(review_text, ARRAY['好评','差评','中性']) AS sentiment,
            embedding(review_text)                            AS review_vec
     FROM   reviews
     WHERE  dt = CURRENT_DATE;
     -- 关键：计算发生在数据所在地，导出流量为 0
     --       每次调用携带审计 ID，可回答"这条数据被哪个作业用哪个模型处理过"
     ```

2. **数据不出仓（核心）**
   - 关键设计：**推理的计算下推到仓库侧，数据不产生副本**
   - 关键能力：**敏感数据的使用全程在仓库权限体系内**，合规可自证
   - 关键数字：**导出流量 0、访问审计 100%**

3. **业务自助与 SQL 化（核心）**
   - 关键设计：**打标、向量化、摘要等能力全部通过 SQL 暴露**，业务方按需组合
   - 关键能力：**标签生产从"AI 团队排期"变成"分析师当天写一条 SQL"**
   - 关键数字：**AI 能力 100% SQL 化、业务自助**

4. **模型与函数版本可追溯（核心）**
   - 关键设计：**函数绑定模型版本，调用记录中保留"用了哪个版本的模型、什么时候"**
   - 关键能力：**模型升级后，历史标签可定位到生成它们的模型版本**——这在对比新旧模型效果、以及解释"为什么这批标签看起来不一样"时是必需的
   - 关键数字：**调用 100% 可追溯到模型版本**

5. **多模态函数（核心创新）**
   - 关键设计：**文本、图片、视频各自的能力统一以函数形式暴露**，接口形态一致
   - 关键能力：**多模态打标不必为每种模态搭一套不同的工程链路**
   - 关键性质：**多模态统一函数接口**

**该电商 AI in SQL 关键数字**（[案例 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **推理执行位置** | 导出后在 AI 集群 | 仓库内下推 | **数据不出仓** |
| **数据导出流量** | 全量导出 | 0 | **-100%** |
| **AI 能力接入方式** | 排期做离线作业 | SQL 函数调用 | **当天可用** |
| **AI 函数数量** | — | 100+ | **∞** |
| **调用审计** | 导出后不可追 | 每次调用带审计 ID | **100% 可查** |
| **模型版本可追溯** | 无记录 | 调用绑定模型版本 | **100%** |
| **业务自助率** | 依赖 AI 团队 | 分析师大面积自助 | **显著提升** |
| **模态支持** | 文本为主 | 文本 / 图片 / 视频 | **多模态** |

**具体数字（How much）**

- 团队规模：该电商 AI 平台 / 数据团队 50+ 人
- 关键数字：**导出 0**；**100+ AI 函数**；**调用 100% 可审计**；**业务自助**
- 业务影响：覆盖该电商的评价分析、商品打标、图像审核等 AI 场景

**失败教训**

- 早期「**为跑推理把数据导出到 AI 集群**」——副本脱离治理且无法回答"谁用过"，倒逼**「推理下推到仓库内，数据不出仓」**
- 「**每个 AI 需求由 AI 团队排期做离线作业**」——标签生产被供给卡死，倒逼**「AI 能力注册为 SQL 函数，业务自助调用」**
- 「**调用不记录模型版本**」——模型升级后新旧标签混用且无法解释差异，倒逼**「函数绑定模型版本，调用记录保留版本」**
- 「**每种模态各搭一套工程链路**」——文本、图片、视频的打标实现各不相同，倒逼**「统一以函数形式暴露，接口形态一致」**

### 6.2 Snowflake"**Cortex：把 AI 函数做成数仓的一等公民 3+ 年**"（2021-2024）

**背景（Why）**

Snowflake 2021 年面临**"客户要在数仓里做 AI，但基础设施不在数仓里"**：
- **客户数据都已在数仓**——**做文本分类、摘要、向量化却要出仓或自建服务**
- **自建推理服务的门槛**——**部署模型服务、管扩缩、算成本，对多数数据团队都是额外负担**
- **成本不可控**——**推理成本与查询成本分属两套账单，难以归因到具体业务**
- **治理一致性**——**AI 处理后的结果如果落在数仓外，权限与血缘就断链**

**触发点（What）**

2024 年前后 Snowflake 推出 **Cortex AI Functions**（[Snowflake 公开材料 2021-2024]），目标：
- **AI 函数作为数仓一等公民**——像内置函数一样调用
- **无需自建推理服务**——托管、免运维
- **成本与治理统一**——AI 调用的成本与权限落在原有体系内

**详细做法（How）**

Snowflake Cortex 的**5 大核心组件**：

1. **AI 函数与内置函数同等待遇（核心创新）**
   - 关键设计：**分类、情感、摘要、翻译、向量化、大模型补全等以 SQL 函数形式提供**，与 `SUM` / `SUBSTR` 这类内置函数在语法上无差别
   - 关键能力：**"要不要用 AI"从架构决策降级为一次函数选择**——这是 AI 在数据分析工作流里真正普及的前提
   - 关键性质：**函数化调用、免自建服务**
   - 关键示意：
     ```sql
     -- 概念示意：AI 函数与内置函数在语法上无差别
     SELECT review_id,
            SNOWFLAKE.CORTEX.SENTIMENT(review_text)   AS sentiment,
            SNOWFLAKE.CORTEX.SUMMARIZE(review_text)   AS summary,
            SNOWFLAKE.CORTEX.EMBED_TEXT_1024('model', review_text) AS vec
     FROM   reviews
     WHERE  dt = CURRENT_DATE;

     -- 结果直接落回表，权限与血缘沿用原体系
     CREATE TABLE review_enriched AS
     SELECT r.*, SNOWFLAKE.CORTEX.SUMMARIZE(r.review_text) AS summary
     FROM   reviews r;
     ────────────────────────────────────────────────
     对照"自建推理服务"：
       导出数据 ─▶ 部署模型服务 ─▶ 管扩缩与成本 ─▶ 结果写回数仓
       每一步都是额外的工程与治理工作
     -- 关键：把"AI 能力"当成数仓的一个内置能力，而不是一个外部系统
     ```

2. **托管推理：免运维（核心）**
   - 关键设计：**模型由平台托管，扩缩与可用性由平台负责**
   - 关键能力：**数据团队不必具备模型部署与运维能力就能用上 AI**
   - 关键数字：**免自建推理服务（部署与运维人力 -80%+）**

3. **成本与治理统一（核心）**
   - 关键设计：**AI 调用消耗计入同一套用量与账单口径**，权限沿用数仓角色体系
   - 关键能力：**"AI 花了多少钱"与"这些结果谁能看"都可以在原有体系内回答**
   - 关键性质：**成本与权限统一归类**

4. **向量化与检索的配套（核心）**
   - 关键设计：**提供文本向量化函数**，向量列存储在表中，可与结构化条件一起检索
   - 关键能力：**语义检索不必依赖外部向量库**，在数仓内即可完成
   - 关键性质：**仓内向量化与检索**

5. **模型选择与任务适配（核心创新）**
   - 关键设计：**按任务类型提供不同模型（通用 / 轻量 / 长文本等）**，并按任务选择
   - 关键能力：**"用哪个模型"从架构问题变成参数选择**，成本与质量可以按任务权衡
   - 关键性质：**按任务选模型**

**Snowflake Cortex 关键数字**（[Snowflake 公开材料 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **AI 能力使用方式** | 自建推理服务 | SQL 函数调用 | **免自建** |
| **数据出仓** | 需导出 | 不外流 | **-100%** |
| **部署与运维** | 自行部署、扩缩、保活 | 平台托管 | **-80%+ 人力** |
| **成本归因** | 两套账单难对应 | 与数仓用量统一口径 | **可归因** |
| **权限** | 结果落在仓外，权限断链 | 沿用数仓角色体系 | **治理不断链** |
| **向量化** | 外部向量库 | 仓内函数 + 向量列 | **∞** |
| **模型选择** | 架构级决策 | 按任务选参数 | **灵活权衡** |
| **客户规模** | 0 | 10000+ | **∞** |

**具体数字（How much）**

- 团队规模：Snowflake 工程团队数千人，服务 10000+ 客户
- 关键数字：**AI 函数化、免自建服务**；**数据不出仓**；**成本与权限统一**；**10000+ 客户**
- 业务影响：让不具备 AI 工程能力的数据团队直接在数仓内做文本理解与向量检索

**失败教训**

- 早期「**让客户自建推理服务**」——多数数据团队缺乏模型部署与运维能力，倒逼**「平台托管推理，AI 函数化」**
- 「**AI 调用与数仓用量两套账单**」——无法归因到业务，成本失控，倒逼**「统一用量口径与账单」**
- 「**AI 结果落在数仓外**」——权限与血缘断链，倒逼**「结果直接落表，沿用原权限体系」**
- 「**把模型选择做成架构决策**」——不同任务用了不合适的模型，倒逼**「按任务类型提供多档模型，选择参数化」**

### 6.3 Databricks"**把模型调用与向量化接进湖仓的 SQL 层 3+ 年**"（2021-2024）

**背景（Why）**

Databricks 2021 年面临**"数据工程与 ML 工程各有一套表达方式"**：
- **数据加工写在 SQL / DataFrame 里**——**模型调用却要切到 Python，两种表达方式来回切**
- **特征与推理结果分散**——**模型输出的标签、向量容易落在湖仓之外的临时位置，脱离血缘**
- **模型迭代影响下游**——**模型换版本后，下游表的语义其实变了，但血缘里看不出来**
- **成本混淆**——**模型调用成本与数据计算成本混在一起，无法按业务拆分**

**触发点（What）**

2021 年起 Databricks 推进**模型调用与向量化接入 SQL 层**（[Databricks 公开材料 2021-2024]），目标：
- **模型调用成为 SQL 的一部分**——不必切换到另一种表达方式
- **输出落表并进入血缘**——推理结果与其他表同等治理
- **模型版本进入血缘**——下游能知道"这张表是用哪版模型生成的"

**详细做法（How）**

Databricks AI 函数的**5 大核心组件**：

1. **模型调用作为 SQL 表达式（核心创新）**
   - 关键设计：**推理以 SQL 函数 / 表达式形式调用**，输入是表里的列，输出是新的列，整条链路仍是一句 SQL
   - 关键能力：**"数据处理 + 模型推理"在同一个执行计划里完成**，不再需要在数据与 ML 之间搬一次
   - 关键数字：**推理 100% 在 SQL 内完成**
   - 关键示意：
     ```sql
     -- 推理结果直接落表，与普通 ETL 无异
     CREATE OR REPLACE TABLE review_insights AS
     SELECT review_id,
            review_text,
            ai_classify(review_text, ARRAY('好评','差评','中性')) AS sentiment,
            ai_query('llm-endpoint', CONCAT('用一句话总结：', review_text)) AS summary,
            ai_embed('embedding-model', review_text) AS review_vec
     FROM   reviews
     WHERE  ds = CURRENT_DATE;

     -- 血缘里会记录：这张表由哪个模型 / 哪个 endpoint 生成
     -- 模型换版本 → 下游表的语义随之改变 → 血缘中可见
     ────────────────────────────────────────────────
     对照"数据与 ML 两套表达"：
       数据侧出表 ─▶ Python 作业读表 ─▶ 调模型 ─▶ 写回另一处
       问题：中间多了一次搬迁，输出位置不固定，血缘不完整
     -- 关键：让"调模型"看起来像"加一列"，治理才能自动跟上
     ```

2. **推理输出即表，进入统一血缘（核心）**
   - 关键设计：**推理结果写为普通表**，与其他表一样被血缘、权限、质量规则覆盖
   - 关键能力：**"这张表的上游是哪个模型"可查**——AI 产出的数据不再是治理盲区
   - 关键数字：**推理输出 100% 入血缘**

3. **模型版本与 endpoint 作为血缘节点（核心）**
   - 关键设计：**模型 / endpoint 作为血缘中的一类节点**，模型换版本时下游影响面可见
   - 关键能力：**"换模型会影响哪些下游表"从凭经验估计变成可查询**——这是模型迭代能被安全推进的关键
   - 关键性质：**模型影响力可查**

4. **向量列与结构化列同表（核心）**
   - 关键设计：**向量作为列存储**，与结构化列同表；向量索引建立在表之上
   - 关键能力：**语义检索与业务过滤在同一查询内组合**，不必另建一套检索系统
   - 关键性质：**向量与结构化同表**

5. **按业务归因的用量统计（核心创新）**
   - 关键设计：**模型调用与数据计算的用量按作业 / 业务维度统计**
   - 关键能力：**"这个业务在 AI 上花了多少"可以回答**——成本归因是 AI 大规模铺开的前置条件
   - 关键性质：**用量可按业务归因**

**Databricks AI 函数关键数字**（[Databricks 公开材料 2021-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **模型调用位置** | Python 作业中 | SQL 表达式内 | **同一执行计划** |
| **数据搬迁** | 数据侧 → ML 侧往返 | 无搬迁 | **-100%** |
| **推理输出治理** | 落临时位置，血缘不全 | 直接落表，完整血缘 | **∞** |
| **模型版本可见性** | 只在代码里 | 血缘中的节点 | **影响面可查** |
| **向量存储** | 外部向量库 | 表中向量列 | **同表可筛选** |
| **成本归因** | 混合不可分 | 按作业 / 业务统计 | **可归因** |
| **换模型的风险评估** | 凭经验 | 按血缘列下游 | **可量化** |
| **企业客户** | 0 | 10000+ | **∞** |

**具体数字（How much）**

- 团队规模：Databricks 团队 5000+ 人
- 关键数字：**推理在 SQL 内完成**；**输出入血缘**；**模型版本为血缘节点**；**10000+ 客户**
- 业务影响：让数据工程与 ML 工程共用一套表达与治理体系，服务全球 10000+ 企业

**失败教训**

- 早期「**数据加工在 SQL、模型调用在 Python**」——两种表达来回切且中间要搬数据，倒逼**「模型调用作为 SQL 表达式，同一执行计划内完成」**
- 「**推理输出落在湖仓之外的临时位置**」——脱离血缘与权限，倒逼**「推理结果落为普通表，纳入统一治理」**
- 「**模型换版本不影响血缘**」——下游语义已变但无人知道，倒逼**「模型 / endpoint 作为血缘节点，换模型前列下游影响面」**
- 「**模型调用成本与数据计算混在一起**」——无法归因到业务，倒逼**「按作业 / 业务维度统计用量」**

### 6.4 阿里"**MaxCompute AI UDF 与 PAI 链路：让 EB 级数据上的 AI 不出仓 5+ 年**"（2019-2024）

**背景（Why）**

阿里 2019 年面临**"EB 级数据做 AI 时搬运成本压倒一切"**：
- **数据权威源在 MaxCompute**——**AI 训练与推理在 PAI，两侧分离**
- **导出成本与合规风险**——**EB 级数据导出一次的网络与时间成本极高，副本也脱离治理**
- **特征与训练不同源**——**离线特征用 SQL 算、训练侧用 Python 重算，口径漂移**
- **多业务重复搬运**——**同一份数据被多个 AI 任务反复导出**

**触发点（What）**

2019 年阿里推进 **MaxCompute AI UDF 与 PAI 一体化（AI in 仓）**（[阿里 MaxCompute / PAI 公开材料 2019-2024]），目标：
- **数据不出仓**——推理与特征加工在仓库内完成
- **特征与训练同源**——同一份定义驱动两侧
- **合规可追**——访问全程在仓库权限体系内

**详细做法（How）**

阿里 AI in 仓的**5 大核心组件**：

1. **AI UDF 与训练直读（核心创新）**
   - 关键设计：**AI 能力以 UDF 形式在仓库内可用**；同时训练任务可直接以仓库表为数据源读取，不需要落中间文件
   - 关键能力：**"数据出仓"这一环被整体去掉**——推理在仓内、训练直读仓内数据
   - 关键数字：**导出流量 -90% 量级、EB 级数据可用**
   - 关键示意：
     ```sql
     -- ① 仓内推理：AI 能力以 UDF 形式调用
     SELECT user_id,
            embedding(tag_seq)          AS user_emb,    -- 序列向量化
            predict_risk(feature_cols)  AS risk_score   -- 模型推理
     FROM   dws_user_profile
     WHERE  ds = '2024-01-01';

     -- ② 训练直读（伪代码）：训练以仓库表为数据源，不落中间文件
     ds = MaxComputeTableReader(table='dws_user_profile', partition='ds=2024-01-01')
     model.fit(ds)
     ────────────────────────────────────────────────
     对照"导出再训练"：
       EB 级数据 ─导出─▶ 中间文件 ─▶ 训练集群读入 ─▶ 训练
       问题① 导出与存储的额外成本；② 副本脱离治理；③ 训练启动要等搬运
     -- 关键：让"训练读取仓库数据"成为一等能力，
     --       而不是把"导出"当成流水线上固定的一步
     ```

2. **特征与训练同源（核心）**
   - 关键设计：**特征工程在仓库内完成并落为特征表，训练直接消费特征表**
   - 关键能力：**训练侧不再用 Python 重算一遍特征**——离线线上口径漂移的根本原因被消除
   - 关键性质：**特征一致率显著提升**

3. **统一权限与审计（核心）**
   - 关键设计：**推理与训练的每一次数据读取都走仓库权限体系**
   - 关键能力：**"哪些数据被哪个作业用过"可逐条回答**——这是 AI 能在受监管行业落地的硬前提
   - 关键数字：**访问审计 100%**

4. **弹性算力挂载（核心）**
   - 关键设计：**算力集群直接挂载仓库**，按任务扩缩
   - 关键能力：**大规模训练不必先把数据搬过来才能开工**
   - 关键性质：**弹性扩缩、免搬运开工**

5. **成本按任务归因（核心创新）**
   - 关键设计：**按任务 / 团队统计存储与算力消耗**，计入业务预算
   - 关键能力：**AI 成本可见、可归属**——避免"训练费用无人认领"导致的预算失控
   - 关键数字：**成本可见 100%**

**阿里 AI in 仓关键数字**（[阿里 MaxCompute / PAI 公开材料 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **数据导出流量** | 全量导出到 AI 侧 | 推理与训练直读仓内 | **-90% 量级** |
| **训练启动耗时** | 小时级（先搬数据） | 直读，免搬运 | **显著缩短** |
| **特征与训练一致性** | 两侧各算一遍，常漂移 | 特征表为唯一来源 | **漂移消除** |
| **访问审计** | 导出后不可追 | 全程走仓库权限 | **100%** |
| **算力弹性** | 需先搬数据 | 集群直接挂载仓库 | **免搬运开工** |
| **成本归因** | 不可见 | 按任务 / 团队归因 | **100% 可见** |

| **向量化 / 推理** | 导出后执行 | 仓内 UDF | **数据不出仓** |

**具体数字（How much）**

- 团队规模：阿里 MaxCompute + PAI 团队 500+ 人
- 关键数字：**导出 -90% 量级**；**特征与训练同源**；**审计 100%**；**EB 级**
- 业务影响：支撑阿里集团内推荐、风控、内容理解等 AI 任务在 EB 级数据上不出仓完成

**失败教训**

- 早期「**训练前先导出 EB 级数据**」——网络与时间成本极高且带来合规风险，倒逼**「训练直读仓内数据 + 仓内 AI UDF」**
- 「**特征在仓库与训练侧各算一遍**」——口径漂移导致线下效果与线上不符，倒逼**「特征工程落表，训练直接消费特征表」**
- 「**数据导出后失去审计能力**」——无法回答"这份副本被谁用过"，倒逼**「推理与训练全程走仓库权限体系」**
- 「**AI 成本无归因**」——训练费用无人认领、预算失控，倒逼**「按任务 / 团队统计用量并计入业务预算」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**一两个 AI 函数 + 一条打标 SQL**」（**最简单**）——**1 个场景、单表**
- 产出：**函数注册规范 + 1 条仓内推理 SQL + 调用审计记录**
- 团队：**2-3 人**
- 验证标准：**推理在仓内完成、导出流量为 0**、**每次调用可追溯到作业与模型版本**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 场景 / 函数库成型**」
- 引入「**AI 能力统一注册为函数**」——业务方自助调用，不必排期
- 引入「**多模态函数接口统一**」+「**推理输出落表进血缘**」
- 团队：5-10 人
- 验证标准：**业务方可自助调用（不依赖 AI 团队排期）**、**推理结果 100% 入血缘**、**多模态接口形态一致**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 场景 / 特征与训练同源**」
- 引入「**特征工程落表，训练直读**」——消除两侧口径漂移
- 引入「**模型 / endpoint 作为血缘节点**」+「**换模型前列下游影响面**」
- 团队：10-30 人
- 验证标准：**特征一致率 ≥ 99%**、**换模型前可列出受影响的表和作业**、**向量与结构化条件同查询可用**

**100 → 1000 阶段：12-24 个月**

- 引入「**训练直读 + 算力挂载（免搬运开工）**」+「**全链路权限与审计**」
- 引入「**按业务 / 任务归因的用量统计**」+「**按任务类型选择模型档位**」
- 团队：30-100 人
- 验证标准：**导出流量 -90% 量级**、**访问审计 100%**、**AI 成本可按业务归因**、**EB 级数据上推理可用**

**关键投资回报**：
- **直接节省**：「**导出流量 -90~100% + 免自建推理服务**」——**EB 级数据做 AI 的最大成本项是"搬运"，其次是"自建并运维一套推理服务"**；把推理搬到数据所在地、把模型服务托管，省下的是网络与运维两笔大账
- **业务价值**：「**AI 能力接入从周级排期到当天自助 + 特征与训练同源**」——**AI 在数据平台内普及的瓶颈不是模型能力，而是"要个新标签要等排期"**；函数化与自助化把 AI 从"项目"变成"工具"，而特征同源则消除了最隐蔽的效果损失
- **AI 时代关键**：「**AI 能力函数化 + 模型版本进血缘 + 成本可归因**」——**这是 AI 从少数团队的项目走向组织级基础设施的三个条件**：函数化决定可用性，血缘决定"换模型敢不敢换"，成本归因决定预算能不能持续；缺任何一条，AI 都会在规模化时卡住

> **本节小结**：
> - 4 个真实案例（某电商 / Snowflake / Databricks / 阿里）印证：**AI 原生数据库不是「加个向量列」，是「AI 能力函数化 + 推理下推不出仓 + 输出入血缘 + 模型版本可追溯 + 用量可归因」5 件套**。
> - 关键时间线：某电商 4+ 年 / Snowflake 3+ 年 / Databricks 3+ 年 / 阿里 5+ 年 —— **AI 与数据平台融合是 3+ 年长期工程**，且**核心矛盾始终是"数据要在哪里被处理"，而不是"用哪个模型"**。
> - 选型第一原则：「**一两个 AI 函数 + 一条打标 SQL**」（**最简单**）——**1 个场景** → 「**能力函数化 + 输出入血缘**」（**必须**）→ 「**特征与训练同源 + 模型版本进血缘**」（**生产**）→ 「**训练直读 + 权限审计一体 + 成本归因**」（**AI 时代**）。
> - 99% 的失败来自「**导出到 AI 侧跑推理 + 排期式接入 + 输出脱离血缘 + 模型版本不可见**」——必须有 **推理下推 + 函数化自助 + 结果落表 + 版本留痕**。
> - 真正的 ROI 来自「**导出 -90% + 接入周级→当天 + 审计 100% + 成本可归因**」——是**AI 能否从少数团队的项目变成组织级基础设施的分水岭**。
