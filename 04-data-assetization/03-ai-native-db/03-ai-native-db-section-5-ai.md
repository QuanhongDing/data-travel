## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单在这门主题上的问题比其他章节更隐蔽，因为**这一节的每个条目看起来都已经是产品**：Cortex Analyst、Genie、Oracle 23ai、SurrealDB 2.x 都有落地页、都有正式发布。缺的不是「有没有这个东西」，而是三件**可核验**的事：它在哪一份 release note 里、有没有第三方在受限条件下用过、它的接口一年内变过几次。「AI 原生优化器」今天已经能进路线图，「多模态融合查询」连「怎么算做到了」都还没有公认标准。

第二个坑是**能力名与产品名混淆**，这是本节最容易写错的地方。同一个能力在不同平台的命名各不相同——"在 SQL 里调用模型"这一能力，在 Snowflake 是 Cortex 的函数族，在 Databricks 是 `ai_query` 一类函数，在 BigQuery 是与 ML 相关的一族函数，在阿里是 MaxCompute 的 AI UDF。**`ai_query` 是 Databricks 的函数名，不是通用术语**；把它写成"数据库都支持的 AI 函数"，就是张冠李戴。本节写到这类能力时只写能力（"在库内调用模型"），并给出判定方法：**去该平台的 SQL 函数参考里找"调用模型 / 生成向量"的正式条目**，找得到再谈支持。

第三个坑是**把"支持"当成"原生"**。本节把判据归纳成四件事：向量类型、距离算子、优化器代价模型、索引结构（这四条散见于主文件 §1.1 的"统一优化器"、§2.1 的概念定义与 §2.3 的距离算子表，**不是主文件某个小节的原话**）。产品只要有一个 `vector` 类型就能在首页写 AI-native，而后面三件事的工程量才是分水岭。因此本节给出一条可执行的判定顺序：先看索引是不是内核注册的索引访问方法（决定崩溃恢复归谁），再看优化器的代价模型文档里有没有向量检索的代价项（决定过滤与向量谁先执行），最后才看支持哪些数据类型。**顺序反了，就会把"加了一列"读成"换了一代"。**

第四个坑是**把老问题读成新问题**。主文件 §1.2 列的五条痛点——跨库 JOIN、一致性、事务边界、运维套数、学习成本——一条都没有消失，改变的是**它们各自的价格**：一致性仍然要付，而"同一份 WAL 与提交序换来的免费一致性"今天依然只有单库路线能白拿；同时"多运维一套系统"的价格在向量规模上去之后反而更贵（理由见 [§7 §7.4](03-ai-native-db-section-7-sec7.md) 的运维单元成本）。按这套判据分级：

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 向量进入通用数据库并参与优化器规划 | **L1** | pgvector CHANGELOG 有正式条目（0.5 HNSW 2023 / 0.7 halfvec·bit 2024 / 0.8 迭代索引扫描 2024）；主流托管数据库服务内置；距离算子与索引语法跨多个主版本未变 | 排进路线图：百万–千万级直接在做业务的库里加一列一索引 |
| 在库内调用模型：AI 函数与向量化 UDF | **L2** | 各平台都有正式 SQL 函数条目，但函数名、计价、权限与失败语义各家不同；"写入时自动向量化"在多数产品里不是默认行为 | PoC：只用在批量生成 + 离线回填，不进事务路径 |
| 自然语言查询：Cortex Analyst / Genie / 通义 + PolarDB | **L2** | 产品已发布；准确率结论由语义层与自有口径决定，公开基准测的是通用 schema | PoC：先建语义层与自建评测集，再谈接不接业务 |
| 多模态融合查询：SurrealDB 模式、多模型数据库 | **L2** | "同一引擎存多种模型"有产品可核验；"一条查询里跨模型由优化器统一规划"没有公开的第三方评测 | 中小规模可试点；不要把跨模型 JOIN 放进关键路径 |
| AI 增强的数据库运维 | **L2** | 产品有正式条目；自动执行配置变更仍以"建议 + 人工批准"为主 | 当解释与建议用，不给自动执行权限 |
| 数据库内的图 + 向量一体化 | **L3** | 两种索引共处一引擎可核验；跨模型的统一代价模型与跨索引一致性无公开证据 | 记录；图查询留在专用图引擎或应用层 |

这张表要按**机制**读，不要按**产品**读。同一个产品可以同时落在两行里：一个数据库既有原生向量列（第一行，L1），又提供库内调用模型的函数（第二行，L2），还可能顺带支持图与文档（第四行，L2）——**产品的能力清单是叠加的，而成熟度不能叠加**。判断一款产品能不能进你的关键路径，要看你实际依赖的那个机制落在哪一级。举例：如果你只用它的向量列加 WHERE 过滤，用到的就是 L1 的部分，可以放心排期；如果你依赖它"写入时自动向量化"，用到的就是 L2 的部分，必须先做 §5.2.2 里那条最小 SQL 的失败语义测试。

> 本主题下唯一处在 L1 的方向是表里的第一行：**向量成为通用数据库的一等公民，并且优化器知道它的代价**。这个 L1 是发给**机制**的，不是发给"AI 原生数据库"这个产品类别的——它成立的条件是索引由数据库内核持有、过滤与向量的先后由优化器决定，与产品首页写不写 AI-native 无关。把 L1 发给某一个产品，是本节最常见的误判。注意第二行（库内调用模型）与第一行经常被绑在一起宣传，但两者的成熟度差一级：前者改变的是**调用点位置**，后者改变的是**索引所有权**，而所有权是更难得到、也更难替换的那一个。

读这张表时有三个动作，它们的顺序不能换：

1. **先定位**——你手上正在评估的那个东西，对应表里的哪一行？如果它没有出现在方向表里，说明它是"发布"，不是"方向"，不必为它单独排期。
2. **再看判据能不能自己核验**——"有 release note 条目"可以核验，"更智能"不能。凡是判据落在后者身上的，本节一律降级。
3. **最后看它在你的依赖路径上的位置**——同一个 L2 能力放在离线回填任务里与放在在线写入路径上，风险完全不同；级别是能力的属性，风险是你的用法的属性。

每次版本升级后回填一次级别：某个 L3 方向若出现第三方评测或标准草案就升 L2；某个 L2 方向若一年内仍拿不到实测数字，就降 L3 并停止投入。

**这张表里 L2 最多，原因不是"保守"，而是这门主题的成熟形态就是"能力已交付、接口未定型"**。向量进入通用数据库之所以能判 L1，靠的是接口多年不变这一条——同一个距离算子、同一套索引语法，跨多个主版本还认得出。库内调用模型、自然语言查询、多模态共查这三件事都不满足这一条，它们不是做不到，而是**换一家产品就要换一次写法**。对架构师的实际含义是：L2 的能力可以用，但**不要让它出现在架构的接缝上**——把它放在可以替换的一侧（离线回填任务、分析入口、演示路径），而不是放在"业务写进去就必须立刻被检索到"的那条路径上。

反过来，L2 也不是"永久等下去"的档位。给每个 L2 方向预先写好"升 L1 的条件"，比年底重新评审一次更有效：库内调用模型的升级条件是**失败语义写进产品文档且可配置**；自然语言查询的升级条件是**在自己的口径上出现可复现的准确率数字**；多模态共查的升级条件是**索引组件可以独立扩缩**。这三条都是可观察的，不是感觉。

还有一条只在阅读顺序上有用的区分：**"产品发布"与"机制变化"不是同一类事**。这一串产品（Oracle 23ai / Snowflake Cortex Search / Databricks Vector Search / SurrealDB 2.x / TiDB Vector / pgvector 0.7+ / TigerData / SingleStore 8.0）属于前者——它说明这一年市场很热，不说明这一年架构变了。同一时间窗内真正改变机制的变化只有两处：**索引的所有权下移到数据库内核**（§5.2.1），以及**模型调用点从应用进程移进数据库执行器**（§5.2.2）。其余条目要么是这两处变化的实例，要么是接口层的包装。把"发布密度"当成"变化速度"，是趋势清单最典型的一种误导。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。只写收益不写代价的方向在评审时应被直接打回：本主题里每一次能力提升，都对应一项成本结构的变化。

读这张结构时有两个约定。**第一，"机制"那一行必须能落到一个可以被改动的对象上**——索引的所有权、调用点的位置、执行顺序的决定者。写成"更智能了""效率更高了"的，都不算机制，只能算评价。**第二，"代价"那一行必须是真实存在的新成本项或新故障模式**，而不是"需要学习"这类永远成立的代价。这两条同时满足，一个方向才值得写进路线图。

#### 5.2.1 向量进入通用数据库并参与优化器规划：本主题唯一的 L1

- **旧做法与它的卡点**：主文件 §1.2 的第一、二、四号痛点讲的是同一件事——业务表在一个库里、向量在另一个系统里，**跨库 JOIN 要靠 ETL 或应用层拼装**。本节要补上的正是"优化器到底做了什么"这一层。卡点不在能不能存向量，而在**过滤与向量谁先执行**：跨库形态下应用层只能"先多取再筛"，而它的代价随过滤区分度非线性放大。
- **AI 改变了什么机制**：**改变了索引的所有权**——向量索引从"另一个进程自持的数据结构"变成"数据库内核注册的索引访问方法"。这是所有权变更，不是功能增加。它同时改了三件事：崩溃恢复归数据库、索引更新写进同一份 WAL、优化器能看到向量扫描的代价并参与选择执行顺序。
- **由此得到的**：**因为索引更新与业务行更新共用同一份日志与提交序，所以"下单后立即可被检索"是默认行为而不是需要额外保障的目标**；**因为过滤在优化器内完成，所以不必把过滤字段冗余进第二个系统，也就不必写那段"保证两份数据一致"的缝补代码**——这条推论在 [§7 §7.3.4](03-ai-native-db-section-7-sec7.md) 有完整推导。

```text
同一句业务查询，两种执行位置（决定代价的是"过滤在哪一层执行"）
  单库路线（索引是内核的索引访问方法）
     SELECT ... FROM products
     WHERE category='phone' AND price<5000        ← 优化器可在"先过滤"与"先向量扫"之间选
     ORDER BY embedding <=> $1 LIMIT 10
  跨库路线（向量在独立系统）
     应用层：先向向量库要 ef_search 个候选 → 再拿 id 回业务库过滤
     期望命中 ≈ ef_search × 选择率 p  ⇒  要拿 K 行需 ef_search ≳ K / p
     p = 1%、K = 10 时 ef_search ≈ 1000（推导见 §7 §7.3.4）
  ────────────────────────────────────────────────
  关键：这不是"哪个引擎更强"，而是"过滤发生在哪一层"——
        库内融合的代价不随 p 变化，跨库融合的代价随 p 变小而非线性放大
```

- **由此付出的**：**其一，写放大型退化**——索引条目服从 MVCC，更新是"插入新版本 + 标记旧版本"，长期高频更新会让索引膨胀，召回与延迟一起退化（判定方法见 [§7 §7.3.1](03-ai-native-db-section-7-sec7.md)）；**其二，资源争抢**——向量查询与业务查询共享 buffer pool，它挤掉的正是业务最热的那批页，正确解法是把向量查询搬到只读副本，代价是副本上的数据新鲜度；**其三，规模上限被单机内存锁住**——主文件 §1.1 说适用规模是"百万–千万级"，这不是产品弱点，是"每向量字节数 × 可用内存"的算术结果，量化只能把它按 4×–32× 往后推（【推算】，编码长度的算术：fp32 到 int8 是 4×，到二值 32×，见 [§7 §7.4](03-ai-native-db-section-7-sec7.md)）。
- **证据与来源**：【公开】pgvector CHANGELOG 显示 0.5 版（2023）引入 HNSW、0.7 版（2024）引入 halfvec / bit / sparsevec、0.8 版（2024）引入迭代索引扫描；PostgreSQL 官方文档对 MVCC 与 VACUUM 的描述解释了索引死点的来源；Oracle 23ai 的 AI Vector Search 有官方发布说明可核验——**具体特性条目以该产品官方文档为准，本节不引用其性能声称**（这类声称普遍缺少数据量、维度、召回目标与硬件条件）。
- **判定方法（自己怎么核验）**：三步，半小时能跑完。**①** 对同一个 HNSW 索引反复 UPDATE 同一批行，观察索引大小增长与重建前后的召回差（核验 MVCC 死点是否存在）；**②** 对同一条 SQL 跑两次执行计划分析——一次带真实 WHERE、一次 WHERE 恒真，比较返回行数与耗时差（核验过滤与向量扫描的先后由谁决定）；**③** 在压测里开关向量查询，对比业务查询的 P99 与缓存命中率（核验资源争抢的真实程度）。三步都过关，这条 L1 方向才算在你的环境里成立。

这条 L1 的规模边界可以直接算出来，主文件 §1.1 写的"百万–千万级"就是这张表的结论（每向量占用与单机内存的算术，完整推导见 [§7 §7.4](03-ai-native-db-section-7-sec7.md)）：

| 维度 / 精度 | 每向量占用（含图结构开销）【推算】 | 单机可行规模量级【推算】 |
| --- | --- | --- |
| 768 维 FP32 | 约 3 KiB + 图结构 | 千万级 |
| 1536 / 3072 维 FP32 | 约 6 / 12 KiB + 图结构 | 千万级偏下（按维度等比缩小） |
| 768 维 INT8 / PQ 量化 | 约 0.8 / 0.4 KiB + 图结构 | 亿级（代价是召回损失，须精排补偿） |

**推导链**（每一格都能自己复算）：FP32 每维 4 B——768 维 = 3,072 B ≈ 3 KiB，1,536 / 3,072 维 = 6,144 / 12,288 B = 6 / 12 KiB；INT8 每维 1 B——768 B ≈ 0.8 KiB；PQ（乘积量化）按 4 bit/维（每 2 维 1 字节，相对 FP32 是 8 倍压缩）——768 ÷ 2 = 384 B ≈ 0.4 KiB。每维位宽或子向量数不同的实现，按「每维字节数 × 维度」这同一算式换算；「+ 图结构」是 HNSW 邻接表的常数开销（与维度无关、随连接度 m 变化），故只记作附加项。规模列是「可用内存 ÷ 每向量字节数」的量级结果，完整算术见 [§7 §7.4](03-ai-native-db-section-7-sec7.md)。

**这张表是"什么时候该换架构"的唯一依据**：看到任何不含维度与精度前提的向量规模阈值，都应先怀疑它。

顺带说明这条边界为什么不能被"多模型融合"绕过去：把图、文档、全文也放进同一个引擎，只会让同一台机器要装的东西更多，不会让向量索引变小。这也是本节把"多模态共查"判 L2 而把"向量 + 优化器"判 L1 的另一层理由——**它们对内存的需求方向相反**。

- **成熟度**：**L1**。判据：有正式 release note；接口稳定（距离算子与索引语法跨多个主版本未变）；生产使用广泛但公开材料以工程博客为主，**缺少带规模与召回条件的统一评测**——这一条按 L1 的最低标准判通过，同时提醒读者：没有统一评测，意味着任何性能数字都必须自己带条件复测。**降级条件**：如果用的是"向量放数组 / BLOB、距离在应用层算"的形态（没有 ANN 索引），这条不成立。

#### 5.2.2 在库内调用模型：把推理搬进 SQL 执行路径

- **旧做法与它的卡点**：旧做法是"数据出仓"——把文本导出到应用侧调模型 API 生成向量，再写回库。卡点有两处：数据出仓的合规与带宽成本；以及**嵌入模型与业务数据的版本漂移**（换一次模型就要重新触发一次全量导出与回填）。
- **AI 改变了什么机制**：**改变了接口边界**——模型调用从"应用层的一段代码"变成"SQL 里的一个函数"。注意这不是成本结构的变化（token 计费照付），而是**调用点位置的变化**：调用点从应用进程移进了数据库执行器。
- **由此得到的**：**因为调用点在执行器内，所以"批量生成向量并回填"不再是一个 ETL 任务，而是一条 `INSERT ... SELECT`**；**因为模型标识可以作为函数参数出现在 SQL 里，所以"这一列向量由哪个模型、哪个版本生成"有机会落进表定义与查询记录**——这是它能与血缘、数据目录（[Ch4-08](../08-data-catalog/08-data-catalog.md)）对接的前提。
- **由此付出的**：**其一，数据库的 SLA 被外部模型服务绑住**——模型服务变慢或限流，SQL 跟着变慢，而数据库侧的排队会把影响放大（判定方法：压测时人为让模型 API 返回限流响应，看连接池是否被打满）；**其二，长事务**——把模型调用放进事务路径会让事务变长，长事务与 MVCC 的相互作用是明确的故障源；**其三，"写入自动向量化"多数产品里不是默认行为**，需要显式建触发器或由应用侧调用，**把它当成默认能力来设计 schema，是本节最常见的一处误判**。
- **证据与来源**：【公开】各平台的 SQL 函数参考是唯一可靠入口——Snowflake 的 Cortex 函数族、Databricks 的 `ai_query`、BigQuery 的 ML 函数族、阿里 MaxCompute 的 AI UDF 都有正式文档条目（**命名各不相同，不要互相套用**）；本目录 [§6](03-ai-native-db-section-6-sec6.md) 给出了这一类能力在四家公司里的落地形态。**本节不给"调用延迟降低多少"这类数字**：它取决于模型服务、网络与批大小，跨环境不可比。

四个判据决定这条能力能不能进关键路径，它们都能在函数参考里查到：

| 判据 | 查什么 | 它决定了什么 |
| --- | --- | --- |
| 模型标识是否必须显式传入 | 函数签名的参数列表 | 决定"这一列向量由哪个模型生成"能否被记录，也就决定它能不能接入血缘与目录 |
| 调用是否允许出现在写事务内 | 事务与函数调用的说明章节 | 决定长事务风险与回滚语义是否存在 |
| 计费是否单列 | 定价页与用量视图 | 决定这部分成本能否归因到查询或团队，还是混进数据库账单 |
| 失败语义 | 错误码与 NULL 处理说明 | 决定坏数据是"报错可见"还是"静默写入"，这一条最容易在文档里缺失 |

- **判定方法（自己怎么核验）**：查该平台 SQL 函数参考里的三件事——函数是否要求显式传入模型标识、计费是否按 token 单列、**模型不可用时返回什么**。第三件事最重要：如果文档没有写明失败语义，就按"会静默写入坏数据"来设计，即在写路径之外加一道向量非空与维度的校验。
- **成熟度**：**L2**。判据：产品可用、接口已发布，但函数命名、计费口径、权限模型与失败语义各家不同，等于没有可移植的接口；公开案例以厂商自有为主。**判定方法**：写一条最小 SQL，在模型服务不可用时看它是报错、返回 NULL 还是静默写入空向量——答案决定了它能不能进关键路径。

#### 5.2.3 自然语言查询：主件是语义层，模型只是接口

- **旧做法与它的卡点**：旧做法是业务方提需求、分析师写 SQL。卡点不在 SQL 的语法，而在**口径**：同一句"上月活跃用户"，两个分析师能写出两种 SQL，而两种都语法正确。Cortex Analyst、Genie、通义 + PolarDB 面对的是同一个卡点，要区分的是"翻译"与"口径"两件事。
- **AI 改变了什么机制**：**把"从需求到查询"的翻译环节从人换成了统计模型**——但只换了翻译环节，没有换口径的来源。口径仍然来自指标定义与语义层（见 [Ch4-10 指标平台](../10-metric-platform/10-metric-platform.md) 与 [Ch1-10 指标体系](../../01-modeling/10-metric-system/10-metric-system.md)）。
- **由此得到的**：**因为口径来源没有变，所以自然语言查询的准确率上限由语义层的完备度决定，而不是由模型能力决定**。这解释了一个反复出现的现象：同一款产品在演示里表现很好、在自有 schema 上明显变差——演示用的是厂商准备好的语义模型。
- **由此付出的**：**其一，新增一层需要长期维护的资产**（语义层、指标定义、列的业务含义），它的维护成本不会因为有了 LLM 而消失，反而因为入口变多而变大；**其二，错误形态变了**——从"SQL 报错"变成"SQL 跑通了但口径是错的"，后者不会被任何监控发现，只在业务复盘时暴露；**其三，权限面扩大**——自然语言入口让不懂 schema 的人也能发起查询，行级与列级权限必须在这条新入口上重新验证一遍。
- **证据与来源**：【公开】跨域 Text2SQL 的公开基准（如 BIRD，arXiv 2023，NeurIPS Datasets and Benchmarks Track）给出的是通用 schema 上的执行准确率，其论文中表现最好的方案仍显著低于"无人审核直接对业务开放"的水平——**具体数字以论文表格为准，且它测的不是你的口径**；产品侧 Cortex Analyst、Databricks Genie、通义 + PolarDB 都有官方文档可核验其前置条件（多数要求先定义语义模型）。
- **判定方法（自己怎么核验）**：抽一百条生产查询日志里的真实问题，覆盖三档——单表聚合、多表 JOIN、含口径歧义的指标；让产品生成查询、人工只判"结果对不对"。**如果第二档与第三档的正确率明显低于第一档，说明瓶颈在语义层与 schema 表达，而不在模型**，此时换产品不会改善；反过来，如果三档都接近，说明你的语义层已经足够好，可以扩大入口范围。
- **成熟度**：**L2**。判据：产品已发布并已被使用，但准确率结论不可跨组织移植，评测必须自建。**判定方法**：从生产查询日志里抽一百条真实问题做成评测集，跑一遍看正确率——这个数字比任何公开基准都更有决策价值。

#### 5.2.4 多模态融合查询与 AI 增强运维：一件改存储，一件改接口

- **旧做法与它的卡点**：这两条方向要解的题不同——多模态融合查询要解的是"同一份资产被拆进向量库、文档库、图库、全文索引四套系统"；AI 增强运维要解的是"诊断知识在少数人脑子里"。前者的卡点是跨四种模型对齐，后者的卡点是经验无法传递。
- **AI 改变了什么机制**：**多模态融合查询改变的是存储侧归属**——把多种模型放进同一个引擎与查询语言，一致性从应用层拼装下移到引擎内（判定方法与 [Ch4-01 §5.2.1](../01-multimodal-db/01-multimodal-db-section-5-ai.md) 同源）；**AI 增强运维改变的主要是接口**——过去的自动调优、自动诊断靠规则与统计（阈值、回归、执行计划对比），现在多了一层自然语言解释与建议。**后者是接口改良，不是架构变化**，这一点必须说清楚：把规则引擎换成 LLM 来解释告警，不改变"决策由谁做"。
- **由此得到的**：**因为多种模型共处一个引擎，所以"检索到 + 拿到原件 + 权限与元数据过滤"可以在一条查询里成立**；**因为运维建议可以被自然语言解释，所以诊断知识的传递成本下降**——但决策本身仍由规则与统计做出，这决定了它今天能自动执行的范围，也决定了读者不该把"自动优化"当成已交付的能力。
- **由此付出的**：**其一，引擎在每个维度上都比专项引擎弱**，且扩缩单位被引擎架构绑住——"一个引擎同时管向量与图"能否扛住大规模，取决于索引组件能否独立扩缩（判定方法：看 release note 里有没有独立的索引服务或独立扩缩配置条目，而不是看首页写没写 multi-model）；**其二，故障爆炸半径变大**——一次引擎故障同时带走检索、元数据与权限判断，这是主文件 §1.2 抱怨"多套系统难管"的反方向代价；**其三，"AI 运维"的边界在于它给的是建议还是动作**——给自动执行权限意味着把一次错误建议变成一个生产事故，收益与代价完全不对称。
- **证据与来源**：多模型数据库的产品存在与版本发布可核验（SurrealDB 2.x 等，**具体版本与特性须查对应产品的 release note**）；"跨模型统一代价优化"没有公开的第三方评测，故其融合查询只判 L2。运维侧没有可核验的第三方基准、只有产品文档条目，故同样判 L2。

把两个方向放在同一节，是因为它们的判定方式完全一致——**问它改变的是"数据放在哪"还是"建议怎么被表达出来"**：

| 方向 | 改变的是 | 判定方法 | 级别 |
| --- | --- | --- | --- |
| 多模态融合查询 | 存储侧归属：从"跨系统对齐"变成"引擎内 JOIN" | 索引组件能否独立扩缩（release note 条目） | L2（存储）/ L3（统一代价） |
| AI 增强的数据库运维 | 接口：从"规则告警"变成"自然语言解释" | 产品文档里是"建议"还是"自动执行" | L2 |

- **判定方法（自己怎么核验）**：多模型侧——看 release note 里有没有独立的索引服务或独立扩缩配置条目；运维侧——看产品的"自动优化"给的是建议还是直接改配置，前者可以试，后者在没有回滚路径时不要开。还有一个更省事的问法：**这条能力如果明天完全失效，我的系统会退化成什么样？** 退化成"要人工调参"是接口问题，退化成"检索不可用"就是架构问题。
- **成熟度**：**L2（多模型存储与共查）/ L3（跨模型统一代价优化、运维动作自动执行）**。判据：能存能查已可用；跨模型规划与自动执行尚无公开证据。

### 5.3 与本主题既有栈的接口在哪

AI 原生数据库与上下游不是"结合"关系，而是**交接物**关系：一次查询的结果以什么形态交给下一跳、失败时谁负责，比"支持哪些数据类型"更能决定系统能不能用。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| AI 原生 DB → RAG / 混合检索（Ch4-04、Ch4-05） | 交接物 = 行 + 距离分数 + 过滤后的 Top-K；**不含**嵌入模型版本 | 检索侧；分数口径不一致时由检索侧兜底 | 既有技术（L1） |
| AI 原生 DB ↔ 向量湖（Ch4-02） | 同一批向量必须来自同一嵌入模型，否则分数不可比；跨库合并前先对齐模型版本 | 两边都算，靠版本号对齐；无自动保证 | 可做但需自建版本对账（L2） |
| AI 原生 DB ↔ 数据目录（Ch4-08） | 表定义要能表达"这一列的向量来自哪个模型的哪个版本" | 目录侧：缺项则拒绝发布 | 需新增元数据字段（L2） |
| AI 原生 DB ↔ Agent 平台（Ch5） | Agent 以工具形式调用单库，工具入参必须含返回规模上限与超时 | Agent 侧负责预算与权限；库侧负责资源隔离 | 可试点，须设只读副本（L2） |
| AI 原生 DB ↔ 图 / GraphRAG | 向量答"相似"、图答"关系路径"，两者的 join 在应用层；一致性无自动保证 | 应用层 | 概念与自建阶段（L3） |
| AI 原生 DB ↔ 模型服务（库内 AI 函数） | 一次 SQL 调用外部模型，数据库 SLA 被绑到外部服务上 | 数据库侧；回退策略必须显式定义 | 接口已发布，各平台语义不同（L2） |
| AI 原生 DB ↔ 语义层 / 指标平台（Ch4-10、Ch1-10） | 自然语言入口的口径来自语义层，不是模型的猜测 | 语义层侧；口径错的 SQL 不会报错 | 边界要先划清（L2） |

一句话概括：**AI 没有在这张图上新增调用关系，只改了两件交接物的形态**——距离分数（进入检索结果）和模型版本（进入元数据）。这两样东西决定了一次单库检索能不能被审计、能不能在换模型之后复现。

```text
一次融合查询的交接物（失败时谁负责，比"支持哪些类型"更决定可用性）
  请求 ──► AI 原生 DB
             ├── 执行：WHERE tenant=… AND category=…   ← 过滤在优化器内
             ├── 排序：ORDER BY embedding <=> $1       ← 索引是内核的访问方法
             └── 返回：行 + 距离分数 + Top-K            ← 交接物 ①：分数要带口径
                       （不含嵌入模型版本 —— 必须由元数据补上）
  元数据侧（目录 / 血缘）
             └── 登记：这一列向量来自哪个模型、哪个版本   ← 交接物 ②：模型版本
  ────────────────────────────────────────────────
  失败归属：
    数据库挂了        → 检索不可用（无降级路径）
    模型服务挂了      → 取决于库内 AI 函数的失败语义（L2，须先测）
    模型版本变了      → 分数不可比：旧向量与新向量混在一个索引里，
                        查询不报错、结果只是"不那么准" —— 这一类失败
                        只有把模型版本作为元数据记录下来才能被发现
```

围绕这张图，有三条接口纪律值得在评审时逐条念一遍：

1. **谁产生分数，谁负责口径**——检索侧返回的分数必须带"由哪个模型、哪种距离度量产生"，否则下游无法判断两次检索的结果能不能合并。
2. **谁的依赖更长，谁担风险**——库内 AI 函数把数据库的可用性挂到了模型服务上，这条依赖必须画在图上，而不是藏在一条 SQL 里。
3. **能在引擎内完成的，不要跨系统完成**——每跨一次系统，就多一个"两侧数据不一致"的故障模式；而这类故障通常不报错，只在业务复盘时暴露。

- 一批"发布"级产品的官方文档入口——**Snowflake Cortex Search、Databricks Vector Search、TiDB Vector、TigerData（TimescaleDB）、SingleStore 8.0**：这一类只用来核验"该产品是否提供该特性、叫什么名字、有没有版本号"，**本节不转述其版本细节、也不引用其性能与规模声称**（理由见 §5.1 关于"产品发布"与"机制变化"的区分——它们说明市场很热，不说明架构变了）。判定方法：在各自文档里找三条正式条目——向量类型、ANN 索引、距离函数；三条都能找到再谈可用，只找到第一条的就是 §5.1 说的"加了一列"。其中 TiDB Vector 主打的"分布式承载向量"这一机制本节未做论证——能否解除 §5.2.1 的单机内存上限，须查它的 release note 里有没有独立索引组件与扩缩条目。

**第三方生产案例**

- 本目录 [§6](03-ai-native-db-section-6-sec6.md) 的四家公司案例（某电商把 AI 能力注册成 SQL 函数、Snowflake Cortex、Databricks 把模型调用接进 SQL 层、阿里 MaxCompute AI UDF 与 PAI 链路）——用于核验"在库内做推理"的落地形态与代价，年份与团队规模的表述以该节的标注为准。**它们证明的是工程可行性，不是向量检索性能。**
- 说明：本节**未能给出**独立的、含规模与召回目标的第三方 AI 原生数据库评测。**这个空白本身是结论**，不是省略：它意味着关于"向量能力行不行"的判断，只能在自己的数据上做。

**怎么用这份清单**：核"向量能不能进我的库"看 pgvector CHANGELOG 与 PostgreSQL 文档（更新慢，但一条条目抵十篇博客）；核"AI 函数能不能进我的 SQL"看各平台函数参考（更新快，但语义各家不同）；核"自然语言查询准不准"只能自建评测集——没有任何公开材料能代替它。三类材料里，**只有第二类（官方 release note / 文档）可以据以改动架构**；第一类用于理解机制；第三类用于判断能不能扩大使用范围。

### 5.5 被过度宣传的部分

**「自然语言查询数据库，业务人员不再需要分析师」**——实际是什么：翻译环节被自动化了，口径与权限环节一件都没少，而且错误形态从"查询报错"变成"查询跑通但口径错了"。为什么：语义模型、指标定义、行列级权限这些前置工程才是准确率上限的来源，模型只负责把问题映射到已定义的口径上。**什么时候才会成真**：出现第三方公开的、在**某个具体组织的自有 schema 与口径**上（而不是厂商准备的演示语义层上）的结果，且能证明人工审核仍然拿掉了大量错误——在那之前，正确的定位是"取数加速器"，不是"分析师替代品"。

**「向量化 UDF 让数据库自动 Embedding，写入即可检索」**——实际是什么：多数产品里"写入自动向量化"需要显式建触发器或应用侧调用；而一旦这么做，模型调用就被放进了写路径，等于把外部服务的可用性与延迟包进了数据库的事务路径。为什么：把模型调用放进执行器改变的是**调用点**，没有改变"模型服务是外部依赖"这个事实。**什么时候才会成真**：模型服务与数据库处在同一故障域内，且产品文档明确写出降级语义（模型不可用时事务是回滚、留空还是写占位值）——这条语义写进写入一致性文档之前，"写入即可检索"只是一个演示路径。

**「AI 原生数据库 = 单库解决 80% 的 AI 场景」**——实际是什么：主文件 §1.1 自己给的上限是"中（百万–千万级）"，而这个上限是索引驻留内存的算术结果（推导见 [§7 §7.4](03-ai-native-db-section-7-sec7.md)）。为什么：向量索引是逐跳随机访问的图结构，规模上限由"索引大小 / 可用于缓存的内存"这个比值决定，量化把它按 4×–32× 往后推，但不能取消它。**什么时候才会成真**：单库路线能把索引下沉到磁盘或对象存储而查询路径不变——届时"单库解决 80%"的分界线才会从千万级向右移动。

三条合起来看，被过度宣传的部分有同一个形状：**它们都把"接口变好了"讲成了"架构变好了"**。自然语言查询改的是入口（口径仍要自己建）、自动向量化改的是调用点（依赖仍是外部的）、单库解决一切改的是运维面（规模上限仍由内存算术决定）。识别方法因此很简单——**把宣传句里的动词换成"接口"或"存储"，看它还成不成立**：换成"接口"仍成立的是接口改良，换成"存储"才成立的是架构变化。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| "向量作为一等类型"会在通用数据库里常态化，"AI 原生数据库"作为独立产品类别反而被稀释 | 主流商业与开源数据库都把向量类型与 ANN 索引列为正式特性（release note 可见）；产品叙事从"我是向量库"转向"我是有向量的数据库" | 向量能力长期集中在少数专有产品上，通用数据库仍只提供"能存不能查"的向量类型 |
| 库内 AI 函数会成为数仓标准能力，但**不会**统一成同一套 SQL 语义 | 各平台保留自己的函数名与计价模型，跨平台迁移仍需重写 SQL | 出现被多家接受的 SQL 标准草案（例如标准语法里出现调用模型的条目），且至少两个主要平台按同一语义实现 |
| 自然语言查询会以"语义层 + 检索 + 生成"的三段式落地，而不是"把问题直接丢给模型" | 产品文档把语义模型定义列为前置条件；第三方实践分享里语义层建设的占比明显上升 | 出现无需任何语义定义、直接对原始 schema 稳定达到可上线准确率的公开评测 |
| 多模态融合查询的价值会落在"减少跨系统对齐"，而不是"跨模型 JOIN" | 主流用法仍是"按一种模态检索 + 用元数据关联其他模态"，跨模型 JOIN 停留在演示 | 出现第三方公开的、把跨模型 JOIN 放进关键路径并上量的生产架构 |

写这四条时的共同约定：**信号必须是外部可观察的**（release note 条目、标准草案、第三方公开案例），而不是"我觉得会"。凡写不出证伪信号的判断，本节不写。

四条预测里，前两条是**产品形态**预测、后两条是**落地方式**预测，它们证伪起来的难度不同：产品形态的变化会在 release note 与官网叙事里显形，一年之内就能看见苗头；落地方式的变化要靠行业实践分享与招聘描述才能观察，周期更长，但一旦方向相反，代价也更大（走错了意味着多维护一层语义资产或多写一套同步代码）。因此**建议每年按固定动作复评一次**：

- 检索一次 pgvector CHANGELOG 与所用数据库的 release note，看向量相关条目是增加了还是停滞了（对应预测 1、2）。
- 用自建评测集（不是公开基准）重跑一次自然语言查询，看正确率是否跨过了可开放给业务的门槛（对应预测 3）。
- 统计一次跨模型 JOIN 在生产查询里出现的次数——如果始终是零，说明它只是演示功能（对应预测 4）。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有 PostgreSQL / MySQL，向量在百万级 | 直接在现有库加向量列与 ANN 索引，过滤写成普通 WHERE | 索引大小与可用于缓存的内存之比值是否超过 1 | **不要为"以后可能上亿"提前引入独立向量库**；小规模不要上量化（收益不存在、召回损失真实） |
| 向量写入必须与业务写入同时可见 | 留在单库——同事务同 WAL 的一致性在这里是免费的 | "写入后立即检索"探针的命中率是否为 100% | 不要用双写维持两套系统；不要指望 CDC 提供读己之写 |
| 业务方提出"自然语言取数" | 先建语义层与自建评测集，模型只当翻译层 | 自建评测集上的准确率变化，而不是产品演示 | **不要在语义层建好之前对业务开放入口**；不要跳过行级权限在新入口上的重新验证 |
| 想用库内 AI 函数生成向量 | 只用在批量生成与离线回填 | 模型服务限流时连接池与事务时长的变化 | **不要把模型调用放进在线写入的事务路径**；不要让失败静默写入空向量 |
| 已有独立向量库且运转良好 | 保持现状，把"模型版本"补进元数据与目录 | 多一套系统的真实人力成本（值班、升级、备份） | **不要为了"统一"做一次全量迁移**——迁移成本主要在运维与同步代码，不在搬数据 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的（改 schema、迁移、把外部依赖放进事务路径），而收益依赖一个尚未在你自己的数据上验证过的假设**（规模会涨到需要换架构 / 自然语言已经够准 / 自动向量化是默认行为）。等 5.6 的信号出现再投入，损失的只是时间。

这张表的五行不是互斥的选项，而是同一个团队在不同时间点会依次遇到的处境。真正需要提前决定的只有一件：**向量写在哪**。它在第一行就要定下来，因为后面每一行的代价都建立在它之上——写进已有库，后面所有的伸缩都只是索引与内存的调整；写进独立系统，后面每一次扩大使用范围都要再问一遍"两边的数据还对得上吗"。至于模型调用、自然语言入口、多模型共查，都是可以在同一个底座上后加的能力，做错了撤回来也不难——**把不可逆的决定和可逆的决定分开，比把它们一起排期更重要**。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**索引与执行的所有权下移**——向量索引从"另一个进程自持的结构"变成"数据库内核持有的索引访问方法"，于是过滤与向量的先后由优化器决定，向量写入与业务写入共享同一份日志与提交序。因为这一点，排进 L1 的是"向量 + 优化器规划"这一机制，而不是任何产品品类；在库内调用模型、自然语言查询、多模态融合都停在 L2，判它们的不是"支持不支持"，而是"模型调用失败时事务怎么走、准确率在自有口径上是多少、索引组件能不能独立扩缩"。
>
> 它**没有**改变的是索引的基本义务：**向量索引是有状态的，驻留层级决定规模上限**——单库能装下多少向量，仍然只由"每向量字节数 × 可用内存"决定。
>
> 💡 **思考锚点**：按 §5.7 第一行，算一次你库里的「索引大小 ÷ 可用于缓存的内存」——这个比值越过 1 了吗？如果没过，你却在为「以后可能上亿」提前引入独立向量库或上量化，那正落在本节「明确不要做」的第一格上；你为那一天设的触发条件是什么？
