## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本主题的清单里混着四类性质不同的东西：**断言供给**（用 LLM 写规则）、**执行动作**（Agent 自动修数）、**契约形态**（把质量要求写进数据契约）、**评估方法**（怎么知道训练数据与 RAG 输出好不好）。它们的差别很大：前两类动的是"谁写、谁执行"，契约动的是"质量要求放在链路的哪一环"，评估动的是"用什么度量效果"。把它们并列成"演进方向"，读者很容易把"换了一种方式写规则"当成"质量问题被解决了"。

数据质量还有一个别的主题没有的陷阱：**它的成熟度不能按"能检测出多少问题"判断**。检测能力与治理效果是两回事——误报多了等于没有告警（本章 [§1.2](01-data-quality.md) 把"告警噪声大、狼来了效应"列为痛点之一）。所以本主题的第②条判据（第三方生产案例）要以**可核验的口径**为准：误报率、MTTR、契约违约次数。这类数字公开材料里极少，且多数来自产品方自己——这正是本主题**全表封顶在 L2、没有一行够得上 L1** 的原因（含三条非 AI 的既有能力行，理由见下段）。

判一个方向能不能现在规划，本节用 L1 / L2 / L3 三级区分，判据是可核验的三条：

- **L1 生产可用**：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条全中才算，可以排进路线图。
- **L2 可试点**：已可用但接口 / 生态未稳，或只有厂商自有案例，或只在小规模被验证。可做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。记录，不要在架构里预留假设。

**判据声明（本节不对 L1 判据做任何修正）**：上面三级与三条判据沿用到底，不替换、不放宽。本主题有一处特别诱人放宽的地方，先把话说死：数据质量的效果证据形态是**误报率、MTTR、违约次数**，这些数字属于各组织的内部运营数据，公开材料里不会有；能公开的通常是产品方的功能演示，正是 §2.1 里 L2 定义所指的"仅有厂商自有案例"。于是连三条"既有能力"行也很难凑齐第②条——**但证据少不等于判据可以改**：把"没有第三方（非厂商）公开生产案例"重写成"有多家彼此独立的组织分别实现或部署过该能力，且有可被第三方复核的机制性材料"，只是把同一条判据换了个说法，而"**是谁实现了这个工具**"与"**是谁在生产里用了它**"是两件事——工具维护方恰恰是第②条要排除的那一方（它写的是自己的能力说明，不是别人的生产记录），读者按新措辞照样核验不了。本节的做法是：**够不到第②条的行一律降到 L2，并在判据格里写明它卡在哪一条**。结果是本主题最重要的一句话：**没有任何一个 AI 方向达到 L1，全表也没有一行达到 L1**——L2 不等于"不好"，也不等于"不能现在做"，只等于"公开证据到不了 L1"；真正需要警惕的是把 L2 当 L1 排进核心路线图。

四件最容易混的事，先在这里分开：

- **产品名 vs 能力名**：清单里的"Quality Copilot""Autonomous""智能数据质量"都是**产品功能位名**，不是能力名；对应的能力是"用自然语言生成断言""不配置规则、从历史基线学异常"。各平台把这些能力叫什么是各自的命名，不要张冠李戴。
- **已发布版本 vs 路线图**：判断某个能力能不能规划，只看一处——**该版本的发布说明或官方文档里有没有对应条目**（§5.4 给了本主题的判定入口）。
- **论文里的方法 vs 产品里的门禁**：用模型给 RAG 输出打分的做法有公开论文与开源实现（§5.4），但"把打分直接当发布门禁"是另一回事——打分器本身有已知偏差，需要先证明它与人工判定的一致率。
- **检测到 vs 修好了**：本章 [§1.1](01-data-quality.md) 把数据质量定义成"度量 → 规则 → 监控 → 告警 → 修复 → 复盘"的闭环；生成规则与检测异常只覆盖前四环，**MTTR 由后两环决定**。只做前半段，不会改变业务方体感。

本节有三件事不做，先说清楚：**不评检测算法的先进性**（LSTM 自编码器比 3-sigma 新，不等于它在你的数据上更有用——本章 [§2.3](01-data-quality.md) 列的算法各有适用分布）；**不评具体产品选型**（同一能力在不同产品里的成熟度不同，选型看各产品文档与自家实测，本章 [§7.5](01-data-quality-section-7-sec7.md) 的决策树与 [§7.6](01-data-quality-section-7-sec7.md) 的选型矩阵给了成套选择）；**不做"未来蓝图"式描述**（凡是写不出可观察信号的判断，都不写进 §5.6）。这三条边界决定了本节的结论会显得保守——**在一个效果只能靠误报率与 MTTR 衡量的主题上，保守才是准确的**。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**？本主题的答案只有一条：**断言的供给方式变了**——从"人预先写出断言"变成"从历史分布或自然语言里得到断言与信号"。它改变的是**覆盖长尾的成本**（从每张表都要写规则，变成接入一次即覆盖），没有改变**判定的语义**：系统报出来的仍然是"某个指标偏离了多少"或"某条断言失败"，而**"偏离"不等于"错误"**（本章 [§2.2](01-data-quality.md) 的漂移检测与 [§2.3](01-data-quality.md) 的异常检测算法都只回答"偏离"）。这是本节把 AI 方向判在 L2 / L3 的核心原因：它改变了断言的供给，没有改变判定。

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 规则即代码 + 断言进执行链路（进 CI / 进调度，失败即阻断） | **L2**（非 AI 能力） | ①③成立：dbt-core、Great Expectations、Soda Core 各有正式发布页与版本化文档（判定入口：各项目仓库的 release notes 与官方文档，可按「项目名 + release notes」检索核验）；断言 DSL 与执行接口由各版本化文档固定。**②核不到**——公开材料写的是"这个能力存在"，不是"某家非工具方的组织在自己的生产链路里怎么用它、结果如何" | 先把断言挂到必经环节上——规则再多，不阻断就不改变事故量 |
| 版本化数据契约与契约校验（Bitol / ODCS 一类 + 消费方侧校验） | **L2**（非 AI 能力） | ①③成立：契约标准有正式规范版本与公开版本历史（这类标准在 2020–2024 年间成型并进入基金会体系，判定入口是各规范仓库的发布页，版本号与日期以页面上的条目为准）；契约是版本化文本对象，兼容性策略须显式声明（本章 [§3.2.4](01-data-quality-section-3-sec3.md)）。**②核不到**——本节举不出"某家非标准方的组织公开给出自己的契约采纳范围与违约统计"这类材料 | 先让契约可机器校验，再谈它覆盖多少条质量阈值 |
| 资产级指标时序 + 基线告警（新鲜度 / 体量 / Schema 变更 / 空值率） | **L2**（非 AI 能力） | ①③成立：这套形态有多个彼此独立项目的正式文档条目——dbt 的 `source freshness`、Great Expectations 的 profiling 与 checkpoint、Soda 的 freshness / schema 指标，以及商业可观测产品的同类能力（能力名以各项目当前文档为准，可按「项目名 + freshness / volume 监控」检索核验）；指标口径已收敛为通用三件套（freshness / volume / schema）。**②核不到**——给出误报率、处置结论这类生产数字的公开材料都出自产品方自己 | 先把这四项跑起来——它覆盖长尾的边际成本最低 |
| LLM 辅助规则生成 | **L2** | ① 各平台该能力有正式文档条目，但**生成规则的验收标准无通行做法**（误报率怎么算、抽多少条复核）；② 只有厂商自有材料；③ 输出是人可读的规则文本，需人工转成可执行断言并经历史回放 | 只用于**起草**；上线前必须过"历史数据回放看误报率"这一关 |
| Agent 驱动的数据修复 | **L3** | 三条判据全不成立：无正式发布条目、无第三方材料；且该动作会**直接改数据**，公开材料里没有可核验的授权、回滚与追责机制 | 记录；先把"谁授权、怎么回滚、出事追谁"写清楚再谈 |
| 训练数据与 RAG 输出的自动评估（质量分门槛 / LLM 打分 / 数据集漂移检测） | **L2** | ① 评测框架有正式发布与论文，但"评测接口"演进快；**②核不到**——公开论文与多个独立实现不是第三方（非厂商）生产案例（判定入口见 §5.4），跨组织可比的评测口径也拿不出；③ 打分器与评测集的接口未稳 → 可做 PoC | 先建**固定评测集 + 回归基线**，再谈用分数做门禁 |
| 向量库数据质量（Embedding 一致性 / 向量分布漂移 / Metadata 完整性） | **L3** | 只有概念与产品方叙述；"向量分布漂移到什么程度会影响检索效果"没有公开对照材料 | 记录；先把向量元数据（来源 / 版本 / 更新时间）补齐 |
| GraphRAG 数据质量（三元组正确性 / 图谱覆盖率 / 时效性） | **L3** | 双重未知：抽取本身有错、验证方法无通行做法；叠加图谱层后无可核验落地材料 | 记录；不要在架构里预留 |
| 实时（流式）质量校验 | **L2** | ① 流处理引擎与流式校验能力有正式发布条目；② 生产材料以产品方与自述为主；③ **流式规则的语义没有通行约定**（事件时间、迟到数据、状态与回溯重算） | 先想清"迟到与重算"的语义，再选引擎 |
| 训练数据质量工具链专门化 | **L2** | ① 标注与数据整理类工具有正式发布条目；② 采用材料以产品方为主；③ "训练数据质量"作为一个门类的接口未收敛 | 先把"数据集版本 + 评测集版本"绑定，工具选型放后面 |
| 可观测性下沉为平台默认能力 | **L2** | ① 各平台文档里质量 / 可观测条目在增加（判定入口仍是**你所用平台**的文档）；**②核不到**——平台自有文档是厂商自己的能力说明，不是第三方（非厂商）生产案例；③ 不成立：是否默认包含随平台与版本变化 | 先用现有平台能力，不要为此换平台 |
| 联邦化 DQ（跨云跨域质量对齐 / 隐私计算 + DQ） | **L3** | 制度与技术双重未定：跨域阈值的可比性与责任划分无公开做法；隐私计算与 DQ 的结合只有方向叙述 | 记录；先统一阈值的**定义**而不是阈值 |
| 「Data Reliability」取代「Data Quality」 | **L3**（作为能力断言） | 这是**术语更替**而非新能力：判定入口是看它有没有带来新的检测或修复原语，而不是看它出现在多少篇文章标题里 | 观察；不要为术语重建一套体系 |

> 表里**没有任何一行达到 L1**，最高档是 L2：第 1–3 行是三条**既有能力**（规则即代码进执行链路、版本化契约与契约校验、资产级指标时序与基线告警），它们满足 ① 与 ③，卡住的都是第②条；AI 方向里到 L2 的是规则起草、训练与 RAG 的评估、实时校验、工具链专门化、可观测下沉。读表时请把这一层看进去：**L2 不等于"不好"，也不等于"不能现在做"，只等于"公开证据到不了 L1"**。其余方向卡住的原因各不相同：Agent 修复卡在"它要改数据"，而公开材料里没有可核验的授权与回滚机制；向量库与 GraphRAG 的质量卡在"没有可对照的效果口径"；联邦化 DQ 与"Data Reliability"根本不是技术能力问题——一个是制度，一个是术语。

**这三级排法直接决定投入顺序**：

- **先做的三条就是上表前三个"非 AI 能力"行（它们卡在证据、不卡在能力）**：把断言挂进必经环节（CI / 调度 / 发布）→ 把质量要求写进可机器校验的契约 → 把资产级指标（新鲜度 / 体量 / Schema / 空值率）跑起来。它们排在所有 AI 方向之前，因为**后面每一个 AI 宣称都要靠这三件事才能被验收**：没有断言链路就没有"自动生成的规则能生效"这句话，没有契约就没有"跨团队承诺可判定"这句话，没有资产级指标就没有"基线学习"的输入。
- **L2 做 PoC，并先测两个数**：生成规则的**历史回放误报率**与评测的**基线差**（同一模型、同一提示，在过滤前后或修复前后的差异）。这两个数拿不出来，L2 就停在原地。
- **L3 不排进排期**：Agent 修复、向量库质量、GraphRAG 质量、联邦化 DQ 都属于"等信号"，它们的共同前提（授权与回滚可定义、效果口径可对照、跨域阈值可比）比选哪家工具重要得多。
- **回填机制**：每季度回填一次级别；某个 L2 若一年内仍拿不到自己组织里的实测数字，降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。四个方向共用 §5.1 里的同一条机制（断言供给方式变了），差别在**它落在闭环的哪一环**——落到"规则"这一环的是 §5.2.1，落到"承诺放在哪里"的是 §5.2.2，落到"评估哪一类数据"的是 §5.2.3，落到"修复与其余方向"的是 §5.2.4。只写收益不写代价的方向，在评审时应被直接打回。

| 方向 | AI 改变了什么机制 | 这条机制落在闭环的哪一环 |
| --- | --- | --- |
| §5.2.1 LLM 辅助规则生成 | 断言从"人预先写"换成"生成 + 复核" | **规则**（供给成本降，误报成本不降） |
| §5.2.2 数据契约标准化 | 质量要求从"事后检测"前移到"边界承诺" | **承诺**（可判定性从数据侧移到协议侧） |
| §5.2.3 训练数据与 RAG 的评估 | 度量对象从"表与字段"扩展到"语料与输出" | **度量**（新增一类被测对象，判定语义未变） |
| §5.2.4 Agent 修复与其余方向 | 与 AI 弱相关或无因果关系 | **修复与制度**（MTTR 与采纳率，不由检测决定） |

读法建议：如果时间只够读一节，读 §5.2.2——它是本主题里**唯一一条能把责任写进协议**的变化，而且不需要 AI；§5.2.1 的收益要等你愿意把"历史回放 + 抽样复核"配齐时才兑现；§5.2.3 是新增的评测对象，先建评测集与基线比选工具重要；§5.2.4 的五条收益都真实，但**没有一条能靠检测能力换来**。

#### 5.2.1 LLM 辅助规则生成：把"写规则"的成本换成"审规则"的成本

- **旧做法与它的卡点**：业务方提需求 → 数据工程师把它翻译成 SQL / Python 断言。卡点有两处：**翻译有损耗**（业务说"金额字段必须大于 0"，落地成断言时可能漏掉"仅对已支付订单生效"这个前置条件），**供给有上限**（每张表、每个字段都要写，长尾表长期没有规则）。本章 [§3.2.5](01-data-quality-section-3-sec3.md) 已把这条卡点写成"断言写不出来、也写不全"。
- **AI 改变了什么机制**：**断言从"人预先写"换成"生成 + 复核"**。这是成本结构的改变：自然语言的语义对齐由模型一次性完成，人从"翻译者"变成"审核者"。**判断权没有转移**——一条规则会不会误报、该不该阻断发布，仍然要人（或历史数据）来判。
- **由此得到的**：因为生成成本下降，所以**长尾表第一次有可能被规则覆盖**——过去只能靠"接入一次即覆盖"的基线告警兜着，现在可以补显式断言。这条收益是真的，也是本方向唯一真实的新增能力。

| 生成对象 | 谁验收 | 上线前必须有什么 |
| --- | --- | --- |
| 字段级断言（非空 / 值域 / 枚举 / 正则） | 该表的 Owner | 历史数据回放得到的**误报率** |
| 跨表对账断言（上下游一致 / 流批一致） | 上下游两个团队 | 一致性的**判定窗口与容差**（差异多少算违约） |
| 异常解释与归因（为什么这次告警） | 当天 oncall | 归因结论能被打脸（下一次同类告警时能否复现） |
| 修复建议（回刷 / 回滚 / 补偿 / 源头修复） | 变更评审人 | 回滚路径与影响面（本章 [§2.3](01-data-quality.md) 的四种修复方法各对应不同风险） |

这张表的读法是**看第二列**：生成器可以把第一列填满，**第二列空着的规则不上线**。

- **由此付出的**：**其一，误报成本不降反升的风险**——规则数量上去了，若没有统一的误报治理，告警会更快淹没真正的问题（本章 [§1.2](01-data-quality.md) 的"狼来了"痛点会以更大规模出现）；**其二，新的一致性风险**——生成的口径来自自然语言，与数据字典、指标定义可能不一致，而**没人负责对齐时，两条口径会同时存在**；**其三，抽样复核是新的固定成本项**，规则越多越不能省；**其四，责任主体问题**——"这条规则是谁定的、误报为什么一直没修"，答案必须落到人。
- **证据与来源**：【公开】各数据质量平台的该能力有正式文档条目（判定入口：产品文档里该能力标的是 GA 还是预览、有没有"建议 / 草稿"的定位）。【经验】生成规则的验收标准（误报率怎么算、抽多少条复核）在公开材料里没有通行做法，必须自己定并留存口径。
- **成熟度**：**L2**。判据：① 有产品文档条目，但生成规则的验收标准无通行做法；② 只有厂商自有材料；③ 输出是人可读的规则文本，需人工转成可执行断言 → 可做 PoC，不要作为核心依赖。
- **判定方法**：抽一批生成规则，在**历史数据上回放**，统计两个数——误报率与漏报案例（事后才知道没报的）。**没有这两个数，规则就不该进生产门禁。**
- **什么时候值得做**：字段多、长尾表多，且你已经有"回放 → 复核 → 签字"的流程时。
- **什么时候不值得做**：告警治理本身还没做好时——增加规则只会让告警量更不可控。**先把误报压下去，再增加规则供给。**

#### 5.2.2 数据契约标准化：把质量要求从"事后检测"前移到"边界承诺"

- **旧做法与它的卡点**：质量靠事后检测——下游发现数据不对，再回溯上游。卡点在**责任与时机**：上游改了 Schema 或口径，下游要么静默算错、要么第二天失败才发现；而"谁承诺什么、违约怎么判"只存在于沟通记录里（本章 [§3.2.4](01-data-quality-section-3-sec3.md) 把这一条写成"下游对上游没有编辑权"）。
- **AI 改变了什么机制**：**机制与 AI 无关**——契约把质量要求从"数据侧的事后断言"前移到"协议侧的边界承诺"，schema、SLA、语义与 owner 同处一份版本化文件，生产方按它发布、消费方按它校验。**这一条要说清：它不是 AI 带来的变化，本节把它放在这里，是因为它是 AI 方向能不能落地的前置条件**（生成契约、Agent 取数，都要先有机器可读的契约形态）。
- **由此得到的**：因为质量要求被写成两侧可独立校验的对象，所以**违约变得可判定**——下游按 freshness 与 volume 阈值自查，生产方在同一份文件上被校验，责任不再靠事后对质界定（本章 [§3.2.4](01-data-quality-section-3-sec3.md)）。
- **由此付出的**：**其一，契约要版本化并维护兼容性**，Schema 变更从"改字段"变成"发版本 + 通知 + 等适配"；**其二，契约数量随消费方数量增长**，每接一个下游就多一份要长期维护的协议；**其三，它只管边界上的承诺，管不了边界内部**——上游内部多算了一步、少过滤了一批，契约不会发现（本章 [§3.2.4](01-data-quality-section-3-sec3.md) 的失效点）。**最容易失败的方式是把契约做成一堆没人维护的文档**。
- **证据与来源**：【公开】契约标准有正式规范版本与公开版本历史（年份区间：2020–2024 年间成型并进入基金会体系，判定入口是各规范仓库的发布页）；本章 [§3.2.4](01-data-quality-section-3-sec3.md) 给了契约的字段样例（schema / sla / change_policy）与"抽三份契约问上次因契约被拒的发布是哪一次"这一判定方法。【经验】契约数量到多少需要自动化兼容性判定，取决于团队带宽，没有通用阈值。
- **成熟度**：**L2（非 AI 能力）**。判据（按 §5.1 的三条）：① 契约标准有正式规范版本与公开版本历史，契约校验可以嵌进 CI；③ 契约本身是版本化文本对象，接口由规范固定；**②核不到**——本节举不出"某家非标准方的组织公开给出自己的契约采纳范围与违约统计"这类材料（§5.4）。**这一级说的是"公开证据还没到 L1"，不是说你的组织不该做这件事**——采纳进度属于你们自己的现状，不进级别。
- **判定方法**：抽三份契约，问"上次因为契约被拒的发布是哪一次"；答不出来的那份已经从协议退化成文档。再数一次"有多少份契约在 CI 里被自动校验"。
- **什么时候值得做**：上下游是两个团队、且下游对上游没有编辑权时——这是契约收益最大的场景。
- **什么时候不值得做**：团队内部同一条链路、发布同频时——先把断言与新鲜度校验做起来，比写契约更快见效。
- **落地的顺序（本节的推荐）**：先落**可机器判定**的部分——schema 约束（哪些字段必须存在、类型与必填性）、新鲜度承诺（什么时候前必须可用）、体量区间（相对近 7 日均值的上下限）；这些项下游可以独立校验，不需要双方就"质量好不好"达成一致。**后落需要谈判的部分**——质量阈值、违约处理与赔偿、口径语义的细节。顺序反了，契约会在第一轮谈判里卡住，或者写完之后没人执行。

#### 5.2.3 训练数据与 RAG 的评估：新增一类被测对象，判定语义没变

- **旧做法与它的卡点**：质量体系围绕"表与字段"建——非空率、值域、对账。卡点是**新对象的度量空白**：语料是不是覆盖了业务场景、检索回来的片段是不是支持答案、训练集分布有没有随线上数据漂移，这三件事**没有字段级的断言可写**（本章 [§2.2](01-data-quality.md) 的公式与 [§2.3](01-data-quality.md) 的算法都针对结构化字段）。
- **AI 改变了什么机制**：**度量对象扩展了，判定语义没有变**——多了一类被测对象（语料、检索结果、模型输出），但判定仍然是"偏离预期"而不是"错误"。用模型给输出打分（LLM-as-a-Judge）只是把"人写断言"换成"模型打分"，打分器本身有已知偏差，需要先证明它与人工判定的一致率（§5.4）。
- **由此得到的**：因为评测集与基线可以版本化，所以**"数据改动会不会让效果变差"第一次可以被回归验证**——这比"我觉得过滤后训练更好了"强得多：【推算】同一模型、同一提示，在语料过滤前后各跑一次固定评测集，取两个分数之差，这个差值就是"数据改动的可归因增益"；没有这个对照，任何"数据质量提升效果"的说法都无法归因。
- **由此付出的**：**其一，评测集本身要维护**——它会随业务变化而过期，且"用同一批题反复调"会让分数虚高（过拟合评测集）；**其二，在线打分当作门禁有风险**——打分器的偏差会以"看起来合理的分数"进入发布决策；**其三，训练数据与线上数据的分布差异要靠漂移检测兜**（本章 [§2.2](01-data-quality.md) 的 PSI / KS 一类方法与"PSI < 0.1 无漂移、0.1–0.25 轻度、> 0.25 严重"的阈值区间【经验】），但**漂移大不等于效果差、漂移小也不等于安全**——它只是前兆信号，不是结论；**其四，成本随"评测集规模 × 模型调用次数"增长**，回归越频繁越贵。

| 被测对象 | 可用的判定 | 代价 |
| --- | --- | --- |
| 训练语料 | 过滤前后的固定评测集对照、去重率、来源分布 | 评测集维护成本；对照要控制变量 |
| 线上分布 | PSI / KS 一类漂移指标（前兆信号） | 漂移与效果不是因果；要单独验证 |
| 检索结果 | 命中率 / 覆盖率 / 片段级权限过滤 | 召回提升会同时带来越权与噪声 |
| 模型输出 | 固定评测集 + 人工抽样一致性 | 打分器偏差；评测集过拟合 |

**向量库与 GraphRAG 的质量指标**：旧做法是"不测"——向量的元数据（来源、版本、更新时间）常常缺失，图谱的抽取结果没人验证（Milvus / Pinecone / Weaviate / Qdrant 都是这一层的存储侧，缺元数据不是某一家的问题）；卡点是**没有可对照的效果口径**（"向量分布漂移到什么程度会让检索效果变差"没有公认答案）。AI 扩大的是需要被测的语料规模，**没有给出判定方法**。由此得到的是低门槛动作（先把元数据补齐、把抽取结果抽样人工核对）；付出的是多维护一层元数据与抽样校验的人力；证据：无可核验的公开对照材料。**成熟度 L3**：三条判据全不成立（无正式条目、无可对照口径、接口未定义）。

- **证据与来源**：【公开】用模型给输出打分这件事有公开论文与开源实现（判定入口与文献见 §5.4：MT-Bench 一类的 judge 研究给出与人工的一致率与已知偏差；RAG 评测有公开的框架与论文；数据筛选有 NeurIPS 2024 的一类工作）。**"LLM / RAG 效果衰减 80% 来自数据质量问题"这一说法本节不作数字使用**——它没有条件限定（哪个模型、哪类任务、什么口径的"衰减"）；正确的替代是把它换成一个你自己的对照数（上面那条【推算】的差值）。【经验】数据集漂移的阈值要按自己的业务节奏定，公开材料里的经验区间只能当起点。
- **成熟度**：**L2（训练数据与 RAG 输出的评估）/ L3（向量库数据质量、GraphRAG 数据质量）**。判据：评测部分 ① 有正式发布与论文、③ 打分器与评测集接口未稳，**②核不到**——论文与独立实现不是第三方（非厂商）生产案例，跨组织可比的评测口径也拿不出，因此可做 PoC、不做核心依赖；**向量与图谱两项的判据是三条全不成立**，因此只做记录——上一段已分别说明。
- **判定方法**：先问"评测集在哪、谁维护、多久没更新"；再问"过滤前后各跑一次，差多少"；两个问题答不上来，"数据质量提升效果"就还只是一句话。
- **什么时候值得做**：你要做语料过滤、训练数据治理或 RAG 上线前的回归时——**先建评测集，再谈工具**。
- **什么时候不值得做**：把这些分数直接接成发布门禁时——**先让打分器与人工判定的一致率可被核验**，再谈门禁。

#### 5.2.4 Agent 修复，以及被 AI 带起来的其余方向

**Agent 驱动的数据修复**

- **旧做法与它的卡点**：从告警到修复跨 3–5 个团队，MTTR 长（本章 [§1.2](01-data-quality.md) 把"修复链路长"列为痛点）。卡点在**授权与责任**：回刷会重算数据、回滚会改变下游看到的值，这两件事都要有人负责。
- **AI 改变了什么机制**：**把"人定位 + 人执行"里的定位环节自动化**（查血缘 → 定位上游 → 给修复方案）。执行环节没有变——它仍然要落到回刷 / 回滚 / 补偿 / 源头修复这四种手段上（本章 [§2.3](01-data-quality.md)），而这四种手段的风险由影响面决定。
- **由此得到的**：因为定位与方案生成变快，所以**MTTR 的前半段被压缩**——但只有前半段。
- **由此付出的**：**其一，自动执行会改数据**，公开材料里没有可核验的授权、回滚与追责机制；**其二，错误归因会被放大**——Agent 按血缘定位上游，血缘若缺字段级精度就会定位错误（见 §5.3 与 [数据血缘与影响面](../05-lineage-and-impact/05-lineage-and-impact.md)）；**其三，闭环里"复盘"这一环无法自动化**——复盘的产出是新的断言与契约，那是人的判断。
- **证据与来源**：【经验】公开材料里能核到的是设想与演示形态（"接告警 → 查血缘 → 出方案"这一串步骤；LangChain Agent 与数据质量产品的组合实验），**没有**可核验的授权、回滚与追责机制条目——判定入口是"有没有把这三件事写成正式的功能条目"，而不是看演示视频。
- **成熟度**：**L3**。判据：① 无正式发布条目、② 无第三方材料、③ 它要改的是数据本身，接口面无从谈 → 记录，不要在架构里预留假设。
- **判定方法**：问三个问题——谁授权这次修复、回滚路径是什么、出错后追谁。三问答不上来，就只把它当"建议系统"用。
- **什么时候值得做**：定位环节慢、且你有沙箱可先验证修复方案时。
- **什么时候不值得做**：血缘精度不够或没有沙箱时——此时自动化只会更快地把错误扩散出去。

同组还有五条方向，它们都被写进了"AI 时代的数据质量"，但机制与 AI 弱相关或无因果关系：

| 方向 | 旧做法与卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据 / 成熟度 |
| --- | --- | --- | --- | --- | --- |
| 实时（流式）校验 | 离线校验 T+1 出结果，错误已扩散一整天 | **没有改变机制**：把校验位点前移，是工程编排的变化 | 问题在扩散前被发现（本章 [§6](01-data-quality-section-6-sec6.md) 的实时校验案例） | 迟到数据、重算与状态管理带来新的语义复杂度 | 引擎有正式条目（Flink 属这一类）、语义无通行约定 → **L2** |
| 训练数据质量工具链 | 标注与数据整理靠脚本拼 | **弱相关**：工具链是既有标注 / 版本化能力的产品化 | 数据集版本与评测集版本可绑定 | 多一条工具链要维护；"数据质量"门类的接口未收敛 | 判定入口：各工具的正式发布与文档（Hugging Face Argilla / Scale AI / Surya 属这一类） → **L2** |
| 可观测性下沉 | 可观测是独立产品，要单独采买与接入 | **无因果关系**：是平台的产品策略 | 接入成本下降 | 默认能力通常只覆盖通用三件套，业务级断言仍要自己写 | 判定入口：你所使用平台的文档 → **L2** |
| 联邦化 DQ | 跨域质量口径各自定义，不可比 | **无因果关系**：这是制度与责任问题 | 若口径统一，跨域对账第一次可判定 | 统一"阈值"不如统一"定义"；跨域责任划分无公开做法 | 无公开可核验落地材料 → **L3** |
| 「Data Reliability」取代「Data Quality」 | 质量工具与事故复盘脱节 | **无因果关系**：术语更替 | 质量指标进入事故复盘流程 | 若只是换名字，体系重建一遍而能力不变 | 判定入口：有没有新的检测或修复原语 → **L3（能力断言）** |

**这五条的共同读法**：收益都真实存在，但**没有一条来自"更聪明的检测"**——两条来自工程编排（位点前移、接入成本），两条来自制度与术语（跨域口径、命名更替），一条来自工具链形态。把它们写成"AI 时代的数据质量演进"，会让真正要做的三件事（把断言挂进必经环节、把承诺写进契约、把修复链路的授权写清楚）一件都排不进排期。

再补一句排序原则：这五条里只有"实时校验"的收益**取决于你什么时候把校验位点前移**，其余四条要么等外部条件（平台默认能力、跨域规则、工具链成熟），要么只是换个名字。排期时应优先做"取决于自己"的那一条，把它做成能力；其余四条做的是"跟进度"。

### 5.3 与本主题既有栈的接口在哪

数据质量与 AI 之间不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比"能不能用"更能决定它能不能落地。表里「现状」一列说的是**这个接口点自己的机制状态**（哪一半已具备、还缺哪一半）；它与 §5.1 对演进方向的 L1 / L2 / L3 定级不是同一把尺子，**不参与方向评级**。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 数据质量 ↔ 数据血缘（[../05-lineage-and-impact](../05-lineage-and-impact/05-lineage-and-impact.md)） | 交接物 = 字段级血缘与影响面；**没有它，异常只能定位到表，定位不到字段** | 血缘侧：血缘缺字段级精度时，归因会指错上游 | 采集机制已具备；字段级贯通率是缺口 |
| 数据质量 ↔ 数据目录与契约（[../../04-data-assetization/08](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 交接物 = 契约文件的存放、版本与 Owner；**契约要有个能被找到的家** | 目录侧：契约散落在各仓库时，违约无法被一致判定 | 登记与版本机制已具备；跨团队采纳是缺口 |
| 数据质量 ↔ 指标平台（[../../04-data-assetization/10](../../04-data-assetization/10-metric-platform/10-metric-platform.md)） | 交接物 = 口径定义与变更通知；**口径改了没说，规则校验的还是旧口径** | 指标侧：口径变更不通知时，质量校验会"全部通过而全部错" | 口径定义已具备；变更联动是缺口 |
| 数据质量 ↔ 调度与编排（[../../03-data-stack/12](../../03-data-stack/12-scheduler/12-scheduler.md)） | 交接物 = 校验位点（入仓 / 加工 / 出仓）与阻断策略；**校验必须挂在必经环节上** | 平台侧：校验挂在可绕过的环节上，等于没有校验 | 位点机制已具备；阻断策略的粒度是缺口 |
| 数据质量 ↔ 可观测（[../04-observability](../04-observability/04-observability.md)） | 交接物 = 指标与告警的归属（别让同一个问题报两次） | 两侧共同：告警重复会直接制造"狼来了"效应 | 归属未定：两侧可能各报一次 |
| 数据质量 ↔ 隐私计算（[../08-privacy-computing](../08-privacy-computing/08-privacy-computing.md)） | 交接物 = 脱敏后的字段质量（脱敏出错本身就是质量问题） | 安全侧：脱敏把手机号变成 null 时，质量规则要能发现 | 脱敏机制已具备；脱敏后校验口径是缺口 |
| 数据质量 ↔ 特征与训练数据（[../../02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md)） | 交接物 = 训练数据的质量门槛与版本；**离线特征与线上特征的分布差异是质量问题** | 特征侧与质量侧共同：两边的新鲜度承诺不同步时，问题在离线评测之后才暴露 | 特征存储已具备；门槛口径是缺口 |
| 数据质量 ↔ 表格式与湖仓（[../../03-data-stack/03](../../03-data-stack/03-lakehouse/03-lakehouse.md)） | 交接物 = Schema 变更事件与兼容性判定 | 平台侧：变更事件不落库时，"Schema 漂移"只能靠事后发现 | 表格式机制已具备；跨引擎的事件一致性是缺口 |

一句话概括：**AI 没有给数据质量新增任何判定语义，只改变了断言的供给方式**。由此得到三条约定。

**第一条约定：没有口径就没有质量结论。**"完整性 99.9%"必须写清是哪个字段、哪个窗口、哪条链路、算不算迟到数据；写不出来，这个数字在事故复盘里不能用，在跨团队对齐里更不能用。

**第二条约定：新规则先过历史回放再上线。**把新规则在历史数据上跑一遍，拿到误报率与漏报案例，再决定阈值与是否阻断——本章 [§6](01-data-quality-section-6-sec6.md) 的实时质量平台案例把"新规则上线前用历史数据回放统计误报率"写成一条必须做的事。

**第三条约定：任何会改数据的动作都要有授权与回滚路径。**回刷、回滚、补偿、源头修复（本章 [§2.3](01-data-quality.md)）四种手段的风险各不相同，自动执行前先把"谁授权、怎么回滚、出错追谁"写进流程——**这三件事写不出来时，自动化只会更快地把错误扩散出去。**

### 5.4 公开进展与文献

分三类列：论文与方法只列能给出标题或出处 + 年份的条目；文档一类给的是**可点名的项目 / 规范 / 产品 + 该看哪一页**，年份只给站得住的区间，**精确版本与日期一律不代填**（属判定入口，进页面即可核验，具体版本与日期以页面上的条目为准）；**宁少勿假**——写不出年份的条目，本节宁可只给入口，也不写一个读者查不到出处的日期。

**论文与方法（可核验）**

- ISO/IEC 25012——数据质量模型，把质量划分为多个特征；本章 [§1.1](01-data-quality.md) 记的是它的发布时间与"实务界收敛为六个维度"这一结论。**本行不代填它的发布年份**（§1.1 记的是 2006）：这类标准的正式版本号与发布年份以 ISO 官方目录页的当前条目为准，可按「ISO/IEC 25012」在该目录页自行核验；**若官方页记的是另一年，本行与本章 §1.1、全书时间线须一并订正**。
- 群体稳定性指数（PSI）与 KS 检验——漂移检测的两条经典方法：KS 统计量出自 1930 年代 Kolmogorov–Smirnov 的工作【公开】；PSI 是信用风险记分卡监控里的长期通行做法（判定入口：模型风险管理的公开材料，本节不代填其最早文献年份）。本章 [§2.2](01-data-quality.md) 给出公式；**阈值区间（< 0.1 / 0.1–0.25 / > 0.25）是经验值【经验】，不是普适标准**。
- "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena", NeurIPS 2023（Datasets & Benchmarks）——用模型做裁判的公开研究，给出了它与人工判定的一致率与已知偏差；**判定方法：用这类结果前，先看你自己的场景里一致率是多少**。
- "RAGAS: Automated Evaluation of Retrieval Augmented Generation"（EACL 2024 系统演示）——RAG 评测的公开方法，把答案相关性、忠实度等拆成可计算的指标。
- "DataComp-LM: In search of the next generation of training sets for language models", NeurIPS 2024——数据筛选与训练效果的关系；**"提升 10 倍"一类数字必须回到论文看它的条件限定（算力预算、数据量、模型规模）**，不能拿来当通用结论。
- **"2024 VLDB Holistic Data Quality 框架""2025 SIGMOD AI-Native Data Quality 论文集"这两条本节不当作证据**——它们给的是主题名而非可检索标题与作者。处理办法：**保留它们所指的方向**（把质量与可观测、血缘统一建模；LLM 介入质量体系的系统性研究），但不作为依据。

**官方 release note / 文档（判定入口）**

- **dbt-core、Great Expectations、Soda Core 的发布页与文档**（三个项目的公开版本记录在 2016–2020 年间陆续开始，具体发布日期以各项目仓库的发布页为准）——核"规则即代码、断言进执行链路"这条的①③；**"GE GA 1.0""2025-Q1" 一类版本与时点一律以各项目发布页为准，本节不给版本号。**

**怎么用这份清单**：要核"能力存不存在"看官方文档与发布说明（最快）；要核"它到底管不管用"看论文与公开评测的一致率（最稳）；要核"在我这里值不值得做"看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**，而它恰恰是唯一影响你决策的那类问题。

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含口径（误报率、MTTR、契约违约次数）的第三方"AI + 数据质量"生产案例。本章 [§6](01-data-quality-section-6-sec6.md) 的四个案例（阿里 / 字节 / 蚂蚁）出处标注为"机构名 + 年份区间"、无可检索文档名，划在自述一类——它们能支撑"校验位点前移 + 规则分类 + 血缘归因 + 三道闸门"这一层的做法，**不能充当 AI 方向的第②条**。**这个空白本身是结论**：它正是本节把所有 AI 方向判在 L2 / L3、并且全表没有一行达到 L1 的直接原因（第 1–3 行那三条既有能力卡的是同一条判据，只是它们卡在证据、不卡在能力）。
- 要补第②类证据，最实际的办法是自己造：把**误报率、MTTR、规则命中率、契约违约次数、审计通过率**做成可上报的口径。这五组数在质量平台评审里的分量，超过任何厂商案例。
- 三类证据里**最容易造假的是"异常检测准确率"**：只报准确率而不给召回与误报的成对数字，无法复核——一个把所有点都判异常的系统准确率也可以很高。**判定方法：只接受同时给出"误报率 + 召回率 + 评测窗口"三样的数字。**

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **断言有没有进必经环节**：数一次"有多少条断言挂在发布 / 调度这种绕不过去的环节上"。
2. **契约可校验比例**：随机抽 10 份契约，数"在 CI 里被自动校验"的比例。
3. **资产级指标覆盖**：数一次"有新鲜度与体量监控的资产占比"。
4. **规则质量**：抽 20 条最近上线的规则，问它们的回放误报率是多少。
5. **修复链路**：问一次"最近一次回刷是谁授权的、回滚路径是什么"。
6. **评测集**：问一次"训练 / RAG 的评测集在哪、多久更新一次、基线是多少"。

### 5.5 被过度宣传的部分

**「LLM 自动生成规则，规则维护成本归零」**——实际是：**降下来的是起草成本，没降的是误报治理与责任归属**。规则的数量上去了，误报的绝对量也会上去，而误报治理是人力活（本章 [§1.2](01-data-quality.md) 的"告警淹没真正问题"会被放大）。**为什么会这样**：把"写出来"当成"维护好"，忽略了规则的成本大头在调参与复盘，不在打字。**它什么时候才会成真**：生成规则默认带"历史回放误报率"与 Owner 签字位，且误报率可以横向比较。**判定方法**：问一句"新规则上线前的误报率是多少"——答不出来，它省下的就不是治理成本。

**「有了数据契约，质量问题就消失了」**——实际是：**契约只覆盖边界上的承诺，不覆盖边界内部**——上游内部多算一步、少过滤一批，契约发现不了；而契约若不嵌进 CI，连边界都守不住（本章 [§3.2.4](01-data-quality-section-3-sec3.md) 的失效点："契约式最怕的不是没有契约，是一堆没人维护的契约"）。**为什么会这样**：把"责任清晰"当成了"数据正确"，而这两件事的判定依据不同。**它什么时候才会成真**：契约默认进 CI、兼容性判定自动化，且数量被收敛到关键下游。**判定方法**：抽三份契约问"上次因为契约被拒的发布是哪一次"。

**「可观测性可以替代显式规则」**——实际是：**可观测式只有"偏离"，没有"错误"**——分布正常但语义错了（金额单位从元改成角、状态枚举换了一套）不会表现为分布异常（本章 [§3.2.5](01-data-quality-section-3-sec3.md) 的失效点）。而且基线模型对业务节奏没有先验，大促与节假日会持续产生误报。**为什么会这样**：把"覆盖长尾的手段"当成了"覆盖全部的手段"，而两者的成本结构正好相反：规则式覆盖长尾是线性的，可观测式接入一次即覆盖，但确定性要求高的场景仍必须回补显式断言。**它什么时候才会成真**：基线模型把业务日历作为先验、且误报告警的处置结论里"业务正常波动"的占比被压到可接受范围。**判定方法**：统计一段时间内基线告警的处置结论里"业务正常波动"的占比。

这三条的共性：**它们都把"某一环变容易了"当成了"整条链路成立了"**——生成器成立的是供给，契约成立的是边界承诺，可观测成立的是长尾覆盖。而本主题的判据始终只有一条：**事故量、MTTR、误报率有没有真的变好，而且这个变好能不能被第三方按口径复核。**

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| LLM 生成的规则会停在"起草 + 人工确认"这一档，不会直接成为生产门禁 | 产品文档把生成能力标为建议 / 草稿；门禁仍要求人确认与回放统计 | 出现把生成规则直接接进发布门禁、并公开误报率与漏报案例的实践 |
| 契约落地会先收敛到 **Schema 与新鲜度**，后收敛到质量阈值 | 契约模板里 schema / freshness 字段先被标准化；阈值部分长期留白 | 跨团队普遍采纳的契约里，复杂质量阈值先于 schema 约束成为必备项 |
| 训练与 RAG 的质量评估会收敛到"固定评测集 + 回归"，而不是"在线打分当门禁" | 公开实践里评测集与基线被版本化，回归进入 CI | 在线打分分数被直接当作发布门禁，且其与人工判定的一致率被公开验证 |
| 术语会换（"Data Reliability"），但新原语不会随之出现——真正变的是质量指标进入事故复盘流程 | 事故复盘模板里出现数据质量指标与 MTTR 分解 | 出现回答"错误"而不是"偏离"的新检测原语，并被跨组织采用 |

写这四条时的共同约定：**信号必须是外部可观察的**（正式条目、发布说明、带口径的公开材料），而不是"我觉得会"。**被检验得最快的是第一条**——产品文档里生成能力标的是"建议"还是"门禁"，一年内就能看到；**最慢的是第四条**——它是一种否定式预测，需要长期观察事故复盘模板与检测原语的变化。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有人要上"AI 自动生成质量规则" | 先建"历史回放 → 误报率 → 签字"的流程 | 观察生成规则里有多少条过了回放 | 不要在告警治理没做好时增加规则供给 |
| 告警太多、业务方开始屏蔽 | 先按影响面分级 + 同一根因只告一次 | 观察"业务正常波动"在处置结论里的占比 | 不要靠提高阈值来降噪——那会把真问题一起压掉 |
| 上下游是两个团队、口径总对不上 | 写契约：schema + 新鲜度 + 变更策略先落，阈值后补 | 观察契约有没有进 CI、被拒的发布有多少 | 不要一次把所有质量阈值都写进契约——先让契约活下来 |
| 上游改 Schema 下游总受伤 | 把兼容性判定（向后兼容 / 破坏性）自动化，挂到发布流程上 | 观察破坏性变更是否被前置拦截 | 不要靠"发通知"代替技术拦截——通知不是门禁 |
| 要治理训练数据 / RAG 语料 | 先建固定评测集与基线，再谈过滤策略 | 观察过滤前后的分数差是否稳定可复现 | 不要把在线打分直接当发布门禁 |
| 有人提"Agent 自动修数" | 先定义授权、回滚路径与追责 | 观察有没有沙箱验证这一环 | 不要在血缘精度不够时自动执行修复 |
| 团队要把"数据质量"改名成"数据可靠性" | 先问它有没有带来新的检测或修复原语 | 观察质量指标是否进入事故复盘模板 | 不要为术语重建一套体系 |
| 预算有限，只能做一件事 | 做"断言进必经环节"（位点 + 阻断） | 观察变更事故与 MTTR 的变化 | 不要把预算先花在 AI 规则生成或联邦化 DQ 上 |
| 要给管理层一份判断 | 写成三行：误报率 / MTTR / 契约违约次数 | 观察这三行能不能被第三方按口径复核 | 不要用"我们上了 AI 数据质量"这种描述代替数字 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改流程、动阈值、引入新工具链），**而收益依赖一个尚未成立的假设**（生成器懂业务语义 / 契约被人维护 / 基线模型懂业务节奏）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**断言的供给方式**——从"人预先写出断言"变成"从历史分布或自然语言里得到断言与信号"，于是覆盖长尾资产第一次在经济上可行。由此才有"自动生成规则""基线学习""自动归因"这些说法，也才有必要把评测集、口径定义、契约版本提到与检测算法同等的位置。它**没有**改变的是本章 [§1.1](01-data-quality.md) 的闭环本身：**度量 → 规则 → 监控 → 告警 → 修复 → 复盘这六环一环都没少**，也没有改变判定的语义——系统报出来的仍然是"偏离"，而"偏离"与"错误"之间的那段距离，只能靠口径定义与显式断言补上。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是"断言从哪来"，还是"判定意味着什么"？** 前者立刻改变覆盖成本（本节判在 L2 的那几条），后者才可能改变事故量（而本节里没有任何一个 AI 方向做到）。第二条同样快的判断：**这件事能不能在没有任何 AI 的前提下先做完**——能做完的（断言进必经环节、契约进 CI、资产级指标跑起来），今天就该排进路线图。
>
> 如果只能带走一句话：**先把判定语义写清楚（哪个字段、哪个窗口、多少算违约）并把断言挂到绕不过去的环节上，再谈用 AI 来生成断言**；顺序反过来，就是让系统更快地报出更多无法判定的信号。
>
