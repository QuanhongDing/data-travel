### 6.1 阿里电商"实时数据质量平台"5+ 年演进（2018-2024）

**背景（Why）**

阿里电商 2018 年**日均 10 万+ 实时任务**（订单 / 库存 / 支付），**数据质量事故频发**：
- **每月 5+ 次 P0 故障**——**GMV 报错**——**业务损失 100 万+**
- **事后 8 小时**才被发现——**MTTR 8 小时**
- **业务方投诉**——**「**这数据能信吗**」**

**触发点（What）**

2018 年**阿里启动数据质量平台**（[DAMA 中国 2019 演讲]），目标：
- **实时**质量监控——**5 分钟延迟**（**不是 8 小时**）
- **6 维度规则**——**完整性 / 准确性 / 时效性 / 一致性 / 唯一性 / 合理性**
- **自动归因**——**「**哪个表出错**」** 1 步到位

**详细做法（How）**

阿里 DQC 平台的**5 大核心组件**：

1. **6 维度规则引擎**
   - 关键代码（SQL DSL）：
     ```sql
     -- 数据完整性规则
     CREATE DQ_RULE rule_orders_completeness ON TABLE orders
     CHECK COUNT(*) > 0 EVERY 5 MINUTE
     FAIL_LEVEL P0
     ON_FAIL SEND_ALERT;

     -- 数据准确性规则（值域）
     CREATE DQ_RULE rule_orders_amount_range ON TABLE orders
     CHECK amount BETWEEN 0 AND 1000000 EVERY 5 MINUTE
     FAIL_LEVEL P1
     ON_FAIL SEND_ALERT;

     -- 数据一致性规则（跨表）
     CREATE DQ_RULE rule_order_user_consistency
     ON (
       SELECT user_id, COUNT(*) FROM orders GROUP BY user_id
     )
     COMPARE WITH (
       SELECT user_id, COUNT(*) FROM users GROUP BY user_id
     ) DIFF_TOLERANCE 0
     EVERY 10 MINUTE
     FAIL_LEVEL P0
     ON_FAIL SEND_ALERT;

     -- 数据时效性规则
     CREATE DQ_RULE rule_orders_freshness ON TABLE orders
     CHECK MAX(ingest_time) > NOW() - INTERVAL '10' MINUTE
     FAIL_LEVEL P1;
     ```

2. **流式规则执行（Flink 引擎）**
   - 关键设计：**Flink DataStream API**——**5 分钟滑动窗口**
   - 关键能力：**TB 级**规则执行——**毫秒级延迟**
   - 关键代码：
     ```java
     // Flink 流式规则执行
     DataStream<RowData> stream = env.addSource(new KafkaSource<>(...));
     stream.keyBy(RowData::getTableName)
           .window(TumblingEventTimeWindows.of(Time.minutes(5)))
           .process(new DQRulesProcessWindowFunction())
           .addSink(new AlertSink<>(dingTalk, sms, email));
     ```

3. **自动归因（血缘 + 历史 Pattern）**
   - 关键设计：**血缘 + 变更记录 + 异常 pattern**——**自动定位根因**
   - 关键能力：**1 步到位**——**「**哪个表出错 + 最近谁改了**」**
   - 关键代码：
     ```java
     // 自动归因
     public class DQRcaAnalyzer {
         public RCAResult analyze(RuleFailure failure) {
             // 1. 找上游血缘
             List<TableRef> upstreams = lineageService.getUpstreams(failure.table);
             // 2. 找最近变更
             List<ChangeRecord> changes = changeService.getRecentChanges(upstreams, 24h);
             // 3. 找异常 pattern
             List<Anomaly> anomalies = patternService.findAnomalies(failure);
             // 综合判断
             return new RCAResult(changes, anomalies);
         }
     }
     ```

4. **4 级告警（P0 / P1 / P2 / P3）**
   - **P0**——**业务损失 > 100 万**——**短信 + 钉钉 + 邮件 + oncall**
   - **P1**——**影响业务决策**——**钉钉 + 邮件**
   - **P2**——**影响 1 个业务**——**钉钉**
   - **P3**——**影响内部**——**邮件**

5. **200+ 业务表覆盖 + 30 万+ 规则**
   - 关键数字：阿里**30 万+ 规则**——**85% 覆盖率**

**阿里 DQC 关键数字**（[DAMA 2019]）：

| 年份 | 规则数 | 故障 P0/月 | MTTR | 业务投诉率 |
| --- | --- | --- | --- | --- |
| 2018 | 5 万 | 5+ | 8 小时 | 基线 |
| 2019 | 10 万 | 3 | 4 小时 | -30% |
| 2020 | 20 万 | 1 | 2 小时 | -50% |
| 2022 | 25 万 | 0-1 | 1.5 小时 | -60% |
| 2024 | **30 万** | **0-1** | **1.2 小时** | **-70%** |

**具体数字（How much）**

- 团队规模：阿里 DQC 团队 30+ 人
- 关键数字：
  - **30 万+ 规则**
  - **200+ 业务表**
  - **85% 覆盖率**
  - **MTTR 8 小时 → 1.2 小时**（**6.5 倍**）
- 业务影响：
  - 支撑**双 11 / 双 12**全链路
  - 服务**100+ 业务线**

**失败教训**

- 早期**规则误判**——**业务方投诉**——倒逼**「**人工确认**」**机制
- **大表规则执行慢**——倒逼**「**采样 + 增量**」**
- **告警风暴**——倒逼**「**告警聚合 + 抑制**」**
- **根因定位不准**——倒逼**「**ML 模型 + 历史 pattern**」**

### 6.2 字节跳动"统一 DQC"5+ 年演进（2019-2024）

**背景（Why）**

字节 2019 年**日增 800 亿事件**——**数据质量事故频发**：
- **每月 10+ 次 P0 故障**——**业务损失 1000 万+**
- **MTTR 4 小时**
- **业务方不信任数据**——**「**这数据能信吗**」**

**触发点（What）**

2019 年字节**启动统一 DQC 平台**（[ArchSummit 2021]），目标：
- **百万级规则**——**每天执行**
- **5 分钟延迟**实时监控
- **PB 级**数据覆盖

**详细做法（How）**

字节 DQC 平台**5 大创新**：

1. **SQL DSL 声明式规则**
   - 关键设计：业务方写 **SQL DSL**——**不写代码**
   - 关键代码：
     ```sql
     -- 业务方定义规则
     DEFINE DQ_RULE orders_completeness
     ON TABLE realtime.orders
     CHECK COUNT(*) > 0
     EVERY 5 MINUTE
     ALERT TO dingTalk ORDER_DEPT;

     DEFINE DQ_RULE orders_amount_anomaly
     ON TABLE realtime.orders
     CHECK
       NOT (AVG(amount) > 1.2 * (
         SELECT AVG(amount) FROM realtime.orders
         WHERE dt = DATE_SUB(CURRENT_DATE, 1)
       ))
     EVERY 1 HOUR
     ALERT TO dingTalk FINANCE_DEPT;
     ```

2. **流批一体（DQC 规则流 + 批执行）**
   - 关键设计：**Flink 实时执行 + Spark 批执行**——**覆盖流批场景**

3. **自研异常检测算法**
   - 关键设计：**Prophet + 孤立森林**——**自动异常**
   - 关键能力：**无需人工规则**——**ML 自动**
   - 关键数字：覆盖**30%+ 异常**——**0 人工配置**

4. **自动归因（血缘 + 变更 + 历史）**
   - 同阿里**（血缘 + 变更 + 历史 pattern）**

5. **告警智能抑制**
   - 关键设计：**同一根因**告警**自动聚类**——**1 个告警**（**不是 100 个**）
   - 关键代码：
     ```python
     # 告警聚类
     class AlertCluster:
         def cluster(self, alerts):
             # 1. 根因相似度
             # 2. 时间窗（5 分钟内）
             # 3. 血缘相关
             # 4. 合并为 1 个告警
             return clustered_alerts
     ```

**字节 DQC 关键数字**（[ArchSummit 2021]）：

| 场景 | 规则数 | 日均执行 | 失败率 | MTTR |
| --- | --- | --- | --- | --- |
| **实时任务** | 50 万+ | 千万级 | 0.5% | 30 分钟 |
| **批任务** | 30 万+ | 百万级 | 0.1% | 1 小时 |
| **AB 实验** | 10 万+ | 百万级 | 0% | 5 分钟 |
| **用户行为** | 20 万+ | 千万级 | < 0.1% | 10 分钟 |

**具体数字（How much）**

- 团队规模：字节 DQC 团队 30+ 人
- 关键数字：
  - **百万级规则**
  - **PB 级**数据
  - **日均千万级执行**
  - **MTTR 4 小时 → 30 分钟**（**8 倍**）
- 业务覆盖：抖音 / TikTok / 电商 / 广告

**失败教训**

- 早期**自研 SQL DSL 难用**——倒逼**「**标准 SQL 兼容**」**
- **异常检测 ML 模型误判**——倒逼**「**人工反馈**」**
- **告警风暴**——倒逼**「**告警聚类**」**

**触发点（What）**

**详细做法（How）**

滴滴 DQC 的**4 大创新**：

1. **Flink 实时规则执行**（同阿里）

2. **订单数据专属规则**（业务深度集成）
   - 关键代码：
     ```sql
     -- 订单金额异常
     CREATE DQ_RULE rule_order_amount_anomaly
     ON TABLE orders
     CHECK
       NOT (amount > 10000 AND order_type = 'normal')
     EVERY 1 MINUTE;

     -- 订单状态一致性（订单状态与支付状态）
     CREATE DQ_RULE rule_order_payment_consistency
     ON orders
     CHECK
       (status = 'paid' AND EXISTS (SELECT 1 FROM payments WHERE order_id = orders.order_id))
       OR (status != 'paid' AND NOT EXISTS (...))
     EVERY 5 MINUTE;
     ```

3. **告警自动分派（业务 Owner 体系）**
   - 关键设计：每个表有**业务 Owner**——**告警直接到 Owner**

4. **质量分数体系**
   - 关键设计：每个表有**质量分数**（**0-100**）——**质量趋势**
   - 关键能力：**「**质量分 < 80**」** → **告警**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选 **Apache Griffin / Deequ**（开源）或 **Deequ**（ML 自动）
- 接入**核心 50-100 个表**
- 配置**基本 6 维度规则**
- 团队：2-3 人

**1 → 10 阶段：6-12 个月**

- 扩展到**1000+ 表**
- 引入**Flink 实时规则执行**（5 分钟延迟）
- 引入**异常检测 ML**（Prophet / 孤立森林）
- 引入**自动归因**（血缘 + 变更 + 历史）
- 团队：5-10 人

**10 → 100 阶段：12-24 个月**

- 扩展到**10 万+ 表**
- 引入**业务 Owner 体系**
- 引入**质量分数 Dashboard**
- 引入**告警智能抑制**
- 团队：10-30 人

**100 → 1000 阶段：12-24 个月**

- 引入**AI 数据助手**（LLM 辅助）
- **商业化**（云服务）
- 团队：30-100 人
