## 7. 与其他方法对比

>
> 阅读顺序：先立判据（7.1）→ 候选分族（7.2）→ 机制差异（7.3，本节重心）→ 成本函数（7.4）→ 决策树与阈值依据（7.5）→ 场景矩阵与组合（7.6）→ 选错的代价（7.7）。

### 7.1 先立判据：为什么打分表会误导

打分表给每个工具打了六个维度的分，并附一列「总分」。逐行核验会发现：**十行里有五行的总分与同行六个分项之和不一致**——Great Expectations 一行的六个分项相加是 22，表上写 20；Apache Griffin 是 20 对 18；Deequ 是 22 对 20；Soda Core 是 23 对 21；dbt tests 是 19 对 18（其余五行闭合）。这不是吹毛求疵：按分项重算，Apache Griffin（20）高于 dbt tests（19），而表上两者并列 18——**一份用来排序的表，排序依据本身没有闭合**。这类出入说明它没有被数值核对过，而一张没有被数值核对过的表，它的分数不是测量结果，是排版结果。

比算术更实质的问题在列的构成上。「配置成本」这一列的**名字指向代价**（越低越好），但整张表共用同一套图例——「评分标准：1（差/低/无）→ 5（优/高/强）」，所以该列上写 5 实际是「配置最省事」的意思，自研 DQC 拿到 2 分（自研确实最费配置）正是这个读法。读者得先在心里把这一列的方向翻一次，它才与另外五列（自动化程度、大数据支持、实时支持、AI 能力、社区生态）可比；而总分把六列等权相加，「配置最简单」的 +5 与「AI 能力最强」的 +5 因此完全同权——**总分的排序由「哪一列恰好被凑成高分」决定，而不是由「谁更适合我」决定**。

即使把刻度统一，分数仍然会误导，因为**权重是场景决定的**。同一个「实时支持」维度，在「支付链路错一个数就赔付」的链路上是硬约束，在「行为日志少几条没人发现」的链路上几乎不构成约束——本章 §3.1 正是拿这两条链路的对照来论证「同一数据形态下正确模式完全不同」。而打分表把两种链路压进同一个「实时支持」列里，于是它的高分既不能证明该工具适合赔付型链路，也不能证明它不适合观测型链路。

还有一条隐藏得更深的缺陷：**这六列全是「工具属性」，没有一列是「我的约束」**。约束决定候选的上界，属性只在候选之间分配名次。所以本节的第一张表不是工具评分表，而是一组能淘汰候选的判据。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 断言在哪一层执行 | 校验是嵌在作业里阻断写出、落在已落地的数据上，还是只读元数据与日志 | 决定故障是被**拦住**还是被**发现**——这是本主题第一条分水岭（§3.2.3 的嵌入式与 §3.2.5 的可观测式，差别就在这一行） |
| 配置量的驱动量 | 每加一列要不要多写一条规则，还是接一次数据源就自动覆盖 | 决定成本函数的主项：随字段数增长的成本在万级表上必然失控，随数据源数增长的成本曲线平得多（7.4 给推算） |
| 规则式还是基线式 | 问题是你已知的（写得出断言），还是未知的（只能靠分布偏离提示） | 规则只能发现被写下来的问题；基线能发现没被写下来的，代价是误报与「解释不了为什么」，且冷启动期无法工作 |
| 谁承担修复责任 | 断言失败时，是生产者补数据，还是消费者等修复 | 契约把责任前移到边界，监控把责任留在下游——同一份断言挂在哪个环节，决定它是「阻断」还是「工单」 |
| 是否需要跨团队协商 | 校验对象是不是另一个团队产出的表 | 决定引入成本是「配几条规则」还是「谈一份协议」；契约的成本几乎全在协商上，而不在技术上 |
| 证据形态 | 你要的是「当前这份数据的判定」，还是「时序上的偏离」 | 决定你选断言引擎还是可观测性平台；两者输出不同形态的产物，不能互相代替（7.3.3） |

六条里最容易被跳过的是第二条与第六条。第二条不看，就会出现「用开源工具省下许可费、再用人力把规则补齐」的账（7.4 给出这条账的算法）；第六条不看，则会在「已经买了平台、却没有任何一条能举证的断言」上反复——平台产出的是异常事件，而业务方要的是「违反了哪条规则」的判定。

使用顺序建议是：先答 1、3（拦不拦得住、发现的是哪类问题），再答 2、5（成本曲线会不会反转、要不要跨团队谈），最后答 4、6（责任归属与证据形态）。

**关于排序**：本节不取消排序能力，只把排序的依据摆到明处——7.6 的矩阵每行都带「不选它的原因」列，7.8 的每行都带「关键理由（机制层面）」列。凡是要给出顺序的地方，都由相邻列给出机制依据；**给不出依据的顺序，就是把场景相关的结论写成了绝对结论**。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| Great Expectations | 声明式断言引擎 | 断言写成 Expectation 套件，对一批数据求值并产出可存档的校验结果 | 自建 DQ 平台的数据团队 | 开源（社区版）与商业版并存 |
| Soda Core / Soda Cloud | 配置化 DQ（YAML DSL） | 用 SodaCL 声明检查，扫描时只取所需指标 | 中小团队快速起步 | Soda Core 开源；Soda Cloud 为 SaaS（许可与运行方式以官方文档当前版本为准） |
| Apache Griffin | 平台化 DQ（独立服务） | 批流一体的度量作业 + 独立服务，校验对象是表与分区 | eBay 起源并进入 Apache 体系（主文件 §1.4 记为 2016） | Apache 许可 |
| Deequ | 库嵌入式约束验证 | Check 作为 Spark 作业内的算子执行，并可基于统计剖面自动提议约束 | Spark 数据湖团队 | Apache 许可（AWS 开源，主文件 §1.4 记为 2018） |
| dbt tests | 与模型同仓的断言 | 断言与模型同文件、同版本、同一次代码评审，随 `dbt test` 在同一条 CI 链路里跑 | 用 dbt 做转换的团队 | dbt-core 开源 |
| 自研 DQC | 贴身但自担维护 | 规则以 SQL / 代码形式落在自家调度里，与血缘、调度、SLA 天然同栈 | 有平台团队的大厂 | 无许可成本，有人力成本 |
| 流式规则引擎（Flink / Kafka Streams 一类） | 链路内实时校验 | 规则是流上的算子，对「刚写出的记录」求值 | 实时数仓团队 | 引擎开源 |
| 数据契约（DataHub Contract / Bitol ODCS 一类规范） | 边界上的承诺 | 契约是可版本化、可机器校验的对象，进 CI 与发布门禁 | 多团队 Data Mesh | 规范开放、实现多样（版本与规范状态以项目发布页当前版本为准） |
| Monte Carlo | 可观测性平台 | 靠仓库元数据、查询日志与历史基线做异常检测与字段级血缘 | 中大型数据平台 | 商业 SaaS |
| Bigeye | 可观测性平台 | 深度集成云数仓（Snowflake / Databricks 一类），度量在仓库内计算 | 云数仓用户 | 商业 SaaS |
| Anomalo | 自动异常检测 | 无配置基线学习，用统计与 ML 检测分布与关系异常 | 想减少规则维护的团队 | 商业 SaaS |
| Mona | AI-first DQ | 自动异常归因 + Copilot 式规则生成 | 有 AI 治理诉求的团队 | 商业 SaaS |
| 中国本土平台（阿里 DataWorks / 字节 DataFinder / Univocity） | 平台内置 DQ | 质量规则与调度、血缘、SLA 同在平台内，校验发生在自家计算引擎里 | 国内大厂与合规优先行业 | 商业 / 云平台服务 |
| Datafold | 数据差异与回归测试 | 用两版数据的 diff 做回归对比，而不是逐条写断言 | 做重构与迁移的团队 | 开源与商业并存（以官方文档为准） |

**这十四行分五族**（其中 Datafold 单成一族）：**断言引擎族**（Great Expectations、Soda Core / Soda Cloud、Deequ、Griffin、dbt tests、流式规则、自研 DQC），机制是「把一条可判定的断言在数据上求值」，产出是 pass/fail 与指标——Soda Core 与 Soda Cloud 是同一套 SodaCL 检查的两种执行形态（前者在自家环境跑、后者是 SaaS 托管），机制同族，差别只在运行方式与许可，流式规则同属这一族（求值的仍是人写下的断言），但它的账单结构独立，7.4 为它单列一行；**基线与统计族**（Monte Carlo、Bigeye、Anomalo、Mona），机制是「先学历史基线、再测偏离」，产出是异常事件；**协议族**（数据契约），机制是「把质量要求写成双方可签的对象并嵌进门禁」，产出是拒绝发布的理由；**平台内置族**（DataWorks、DataFinder、Univocity），机制是「规则引擎与调度、血缘、SLA 同栈」，产出是平台内的质量看板与工单；**差异回归族**（Datafold），机制是「对两版数据做 diff 并判定差异是否落在可接受范围内」，产出是差异报告与回归结论——它的求值单位不是「一条断言」而是「一次新旧比对」，因此不替代前四族，只服务迁移与重构期的等价性验证（7.6 矩阵把它放在这个位置上）。还有一类更早的形态把 ML 检测与数据质量放在一起（本章 §4.3 列的 Apache Hivemall 一类）——它的机制属于基线与统计族，只是工程化程度更低。**选型的第一刀是选族，不是选产品**：跨族的差别是机制差别，同族内部的差别多数是接口、许可与运维形态的差别。

族之间还有一条容易被忽略的分界：**引擎在哪里读数据、读什么**。断言引擎族、平台内置族与差异回归族要读数据（扫表、读分区统计或抽样、比对两版明细），成本里必然含一笔计算；基线与协议两族原则上不读全量**明细**（读元数据、查询日志、统计剖面与契约文本——7.3.1 表的「是否读全量数据」一栏给这一族写的正是「以元数据、日志、**统计**为主」），成本里主要是平台与权限，**算力只占次要一笔**。这条分界有一处例外必须点名：基线式里有一类形态把度量下推到客户自己的仓库内计算（表内 Bigeye 一行的「度量在仓库内计算」即属此类），那笔算力并未消失，只是从供应商的账单挪到了客户仓库的账单上，所以在选型时要按「谁来付这笔算力」重新归位。这条分界决定了 7.4 的成本函数里哪一项是主导项——**同一句「质量监控」，在不同族里的账单结构完全不同**。

表里最后一列（许可与商业模式）常被当成采购问题，其实它是机制问题：**你问的不是「贵不贵」，而是「计价口径与我的增长方式是否同向」**。若计价按资产数或用量走，而你的表数在涨，成本就随规模同向上升；若计价按数据源数走，规模增长几乎不额外计费。判断方法是把供应商公开的计价维度与 7.4 表中「增长方式」那一列并排看——**这两列一旦反向，采购就会变成长期成本陷阱**。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 断言在哪一层执行：写出前拦 / 写出后发现 / 不碰数据

**机制是什么**：校验位置只有三种——作业内（写出前，此时还要区分「记一条失败」还是「让这一步失败」）、数据落地后（按调度在已写好的表上跑）、不碰数据（只在元数据与查询日志上推断）。本章 §3.2.3 给出的判定标准很干脆：**只有让这一步失败，才算真正的嵌入式**；只是把 DQC 挪到作业里跑、失败仅记一条日志，位置其实没变。

**它在各候选中的实现差异**：

| 候选 | 校验发生在 | 失败时会发生什么 | 是否读全量数据 |
| --- | --- | --- | --- |
| Deequ / 业务代码内联断言 | 作业内（写入路径上） | 可让该步骤失败（按严重度配置） | 读（通常只读本次处理的数据） |
| dbt tests | 模型构建之后、下游依赖之前 | 让测试与后续依赖失败 | 读（对刚构建的模型执行查询） |
| Apache Griffin | 数据落地后 | 产生质量指标与告警，不回滚已写出的数据 | 读（批 / 流作业） |
| Great Expectations / Soda | 数据落地后（批次校验） | 生成结果与告警，可挂到调度上阻断下游 | 读（按批次取数） |
| Monte Carlo / Bigeye / Anomalo / Mona | 数据落地后，且以元数据与日志为主 | 产生异常事件与告警 | 以元数据、日志、统计为主 |
| 数据契约 | 发布前（CI / 门禁） | 拒绝发布 | 读契约与 schema，不读数据本身 |

**由此必然导出的性质**：因为断言落在写出前，所以坏数据进不了下游——**代价是这次写入必须失败或重跑，上游要为失败准备补偿路径**，且校验本身进入关键路径、其延迟会计入产出时间；因为断言落在落地后，所以校验不阻塞生产链路、可以跑全量，**代价是坏数据已经在下游跑了至少一个周期**（这正是 §1.2 痛点 5「修复链路长、MTTR 高」的机制成因：监控不改变责任归属，只加快发现）。不碰数据的元数据侧校验成本最低、完全不阻塞，**代价是它的判定只能基于「量的形状」，看不到「值的内容」**——一个手机号字段整体错位一格，行数与分布形状都不会变；本章 §3.2.5 把同一条代价写得更直接：**它只有「偏离」没有「错误」**，金额单位从元改成角、状态枚举换了一整套，分布可以完全正常，只有值级断言才能发现。

还有一条与位置相关的工程约束：**校验位置决定了它能看到什么**。作业内校验看到的是「本次处理的数据」，落地后校验看到的是「整张表的一个分区」，元数据侧只能看到「量的形状与 schema 的变更」。所以同一句「监控订单金额」，在三个位置上是三件不同的事——这也是 §4.2 把规则执行方式单列一节的原因：执行方式不是实现细节，它决定了断言的语义。

**公开证据**：Deequ 提供 Check 的两种严重度（Error 与 Warning），即「让这一步失败」与「记一条」的开关，可由其官方文档核验；dbt tests 与模型同仓同版本、随 `dbt test` 在同一条 CI 里执行，见 dbt 官方文档的测试章节（该形态在本章 §3.2.2 的代码示意里已给出；支持的测试类型与默认严重度以官方文档当前版本为准）【公开】。各产品「校验发生在写入前还是落地后」的判定方法是：查它的部署与执行文档里，**校验作业是挂在转换作业内部还是挂在转换之后的调度节点上**——挂在调度节点上的，无论名字叫什么，都是落地后校验。

**失效条件**：当写入路径不受你控制（外部系统直写、埋点直投）时，「写出前拦」在物理上做不到，只能退回落地后校验，并通过契约去改边界（7.3.4）。

#### 7.3.2 配置成本的驱动量：字段数 vs 数据源数

**机制是什么**：三种形态的成本随不同的量增长——断言式随**被断言的字段数**（要人写规则）、基线式随**接入的数据源与资产数**（接入后自动覆盖）、契约式随**跨团队边界数**（要协商）。

**它在各候选中的实现差异**：

| 形态 | 配置量随什么增长 | 首次覆盖的代价 | 新增一列的边际成本 | 新增一张表的边际成本 |
| --- | --- | --- | --- | --- |
| 断言引擎（GX / Soda / dbt tests / Deequ / Griffin） | 字段数 × 每字段规则数 | 高（要写规则） | 高（不补就是盲区） | 高 |
| 基线式可观测性（Monte Carlo / Anomalo / Bigeye / Mona） | 数据源与资产数 | 高（接数据源与权限） | 近零（自动纳入） | 近零 |
| 契约式 | 团队边界数 | 极高（协商） | 低（契约里改一行） | 低 |
| 平台内置（DataWorks / DataFinder / Univocity） | 表数（可套模板） | 中（同栈、可批量） | 中（模板复用） | 中 |

**由此必然导出的性质**：因为断言引擎的成本随字段数增长，所以**它的单位成本不随规模摊薄**——表从几百涨到上万，规则数与维护人力同比例上涨，而且这份成本不是一次性的，而是随每张表的生命周期持续产生；因为基线式的成本随数据源数增长，所以**它的单位成本随规模下降**——接完若干个数据源之后，新表默认被覆盖。这条差异直接给出一个反直觉结论：**在万级表规模上，「开源工具 + 自建平台」的总成本常高于商业可观测性，尽管后者有许可费**。

**一条量级推导**（【推算】）：设表数 T、每表需人工维护的规则数 r、每条规则的年维护工时 w。开源路线的年人力 ≈ T × r × w（推导链：逐表逐规则相加）。取 T = 10,000、r = 5、w = 0.5 人时/年（后两项属于【经验】假设），得 10,000 × 5 × 0.5 = **25,000 人时/年**；按每人年 1,700–2,000 工时（同属【经验】）折算为 **12–15 人年**（25,000 ÷ 2,000 ≈ 12.5，25,000 ÷ 1,700 ≈ 14.7）。这就是「配置债」——它不是一次性建设成本，而是随表的生命周期持续产生的年金。

**公开证据**：主文件 §1.4 把 Monte Carlo 在 2020 年的融资与 Data Observability 概念的成型记为同一年，该概念的市场定位正是「不靠人写规则」；本章 §4.3 把 Anomalo 记为「无需配置规则，纯 ML 检测」，把 dbt tests 记为「仅支持 dbt 模型」；本章 §3.2.5 把这条差异直接写成一句——**规则式覆盖长尾的成本是线性的，可观测式是接入一次即覆盖**【公开】（来源：主文件 §1.4 演进历程 2020 年条目；本章 §3.2.5 与 §4.3 工具链与平台表）。各产品「是否自动覆盖新表、按什么计价」请以其官方文档当前版本为准。

**失效条件**：当业务要求「必须精确阻断」时（支付链路），自动基线给不出可举证的判定——它能说「这次分布异常」，说不出「违反了哪条业务规则」；此时断言不可省。因此二者不是替代关系，而是 7.3.3 要讲的分工。

#### 7.3.3 规则式 vs 基线式：已知未知与未知未知

**机制是什么**：断言式检测的是「你写下来的约束被违反」，输出是判定；基线式检测的是「这次的窗口与历史窗口相比发生了偏离」，输出是提示。两者的判据来源不同——一个是人写下的业务规则，一个是从历史学出的分布。

**它在各候选中的实现差异**：

| | 规则 / 断言式 | 基线 / 统计式 |
| --- | --- | --- |
| 判据来源 | 业务约束（人写的） | 历史窗口（学出来的） |
| 能发现 | 已知问题 | 没被写下来的偏离（漂移、量变、分布位移） |
| 输出 | 通过 / 失败 + 具体违反项 | 异常事件 + 严重度 |
| 冷启动（新表 / 新分区） | 立即生效（不需要历史） | **结构上无法工作**（没有历史就没有基线） |
| 误报来源 | 阈值写得过松或过紧 | 业务本身的季节性、促销、结构变化 |
| 举证能力 | 能说「违反了哪条规则」 | 只能说「偏离了历史」 |
| 阈值方法 | 静态阈值、业务约束（§4.2 的四类里占两类） | 3-sigma、ML（§4.2 的另两类） |

**由此必然导出的性质**：因为基线式没有「规则」这个对象，所以它**在新表、新分区、新业务这些冷启动场景里结构上无法工作**——没有历史就没有基线，而这恰恰是质量事故最集中的时段（新链路刚上线、口径刚改）。反过来，因为断言式只能发现被写下来的问题，所以**它的覆盖率等于人的想象力**，而数据漂移的典型形态（业务变化引起的分布位移）根本写不出规则。两条代价合起来，工程上唯一可行的结构是：**关键链路用断言（冷启动可用、可举证），长尾与广覆盖用基线（自动、便宜），并把基线发现的事件回灌成新的断言**——这正是本章 §3.4 组合模式在本主题上的形态。

**公开证据**：本章 §3.2.5 把可观测式与规则式的差别写成两条——断言从哪来（人预先写死，还是从历史分布学出来）、报的是什么（哪条规则失败，还是哪个指标偏离了多少）；主文件 §2.4 用同一分界界定 DQ 与可观测性的关系（「规则 + 阈值」驱动 vs「指标 + 时序 + 异常检测」驱动，可观测性是 DQ 的超集）【公开】（来源：主文件 §2.4 与相邻概念的关系；本章 §3.2.5）。基线式的量化口径之一是分布稳定性指标：主文件 §2.2 给出 PSI 的常用档位（小于 0.1 视为无漂移、0.1–0.25 轻度、大于 0.25 严重），并自己标注为「阈值经验值」，本章 §5 对这组数字用的也是同一档位【经验】；这类档位只适用于分布稳定、口径不频繁变更的字段，用错对象时误报会掩盖真问题。

**失效条件**：在强季节性与高频促销的业务上，基线式的误报率会高到没人看（§1.2 痛点 4 的「狼来了」），此时要么按业务日历切分窗口，要么退回断言；反之在口径频繁变更的字段上，基线的「历史」本身就是几段不同语义拼起来的，此时基线也不能用。

#### 7.3.4 谁负责修：契约把责任放在边界，监控把责任留在下游

**机制是什么**：质量断言默认是消费者写的（下游发现上游坏了）；契约把同一份要求写进生产者的发布门禁，使上游无法发布不合规的 schema、口径或数据。

**它在各候选中的实现差异**：

| | 消费者侧监控（断言引擎 / 可观测性 / 平台内置） | 生产者侧契约（DataHub Contract / Bitol ODCS 一类） |
| --- | --- | --- |
| 谁提出要求 | 消费方 | 生产方与消费方协商后写进契约 |
| 生效时点 | 数据产出之后 | 发布之前（CI / 门禁） |
| 谁先发现问题 | 下游（往往已是事故） | 上游自己 |
| 修复成本 | 高（下游已被污染，要回刷） | 低（还没发布） |
| 引入成本 | 低（自己写规则即可） | 高（要协商、要改发布流程） |
| 覆盖范围 | 覆盖它扫到的每一张表 | 只覆盖边界上的承诺，不覆盖边界内部 |

**由此必然导出的性质**：因为契约把校验点放在**发布之前**，所以修复成本被压到最低——坏数据从未进入下游，不需要回刷，也不需要跨团队追责；**代价是这项能力不是技术动作而是组织动作**：要先谈成协议、再改造发布流程，因此它在「跨团队边界多」的组织里收益最大，在「同一团队自产自用」的场景里几乎无用武之地。反过来，消费者侧监控的引入成本极低（自己写规则就行），**代价是它永远在下游发现问题**——7.3.1 已说明这就是 §1.2 痛点 5 的机制成因：监控加快「发现」，但不改变「谁负责修」。还有一条边界必须写清：**契约只覆盖边界上的承诺，不覆盖边界内部的算错**——上游内部多算一步、少过滤一批，契约看不见；而契约若不嵌进 CI，连边界都守不住。

**公开证据**：主文件 §1.4 把 2023 年记为「数据契约成为业界共识」的一年，2021 年则是可观测性向可靠性概念延伸的年份；本章 §3.2.4 把契约式的结构与失效点写清，其中最关键的一句是「差别不在语法，而在谁签字、违约时谁负责」；本章 §5 在讨论 AI 时代的契约时也引用了同一条失效点——**契约式最怕的不是没有契约，是一堆没人维护的契约**【公开】（来源：主文件 §1.4 演进历程 2021 / 2023 年条目；本章 §3.2.4 与 §5）。契约规范（Bitol / ODCS 一类）的正式版本与兼容性约定，请以项目发布页当前版本为准。

**失效条件**：当契约数量超过维护能力、且没有版本与兼容性策略时，契约本身成为负债——每次 schema 变更都要同时改契约、改上游作业、改下游校验，而没人负责这项同步。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 规则配置与维护（表数 × 每表规则数 × 每规则维护工时 × 表生命周期）
      + 校验执行的计算（扫描量 × 执行频率）
      + 平台与许可（数据源数 / 表数 / 席位或用量）
      + 契约协商与门禁集成（跨团队边界数）
      + 误报处理（告警量 × 单条处置工时）
```

各族哪一项是主导项、哪一项是隐性成本：

| 族 | 主导项 | 隐性成本 | 增长方式 |
| --- | --- | --- | --- |
| 断言引擎族 | 规则配置与维护（人力） | 规则会随表结构漂移而失效，没人清理就变成噪声 | 随表数与字段数线性增长 |
| 基线式可观测性 | 平台许可（按数据源 / 资产 / 用量计价） | 事件处置人力；冷启动期的空窗 | 首次高、边际近零 |
| 协议族 | 协商与流程改造（组织成本） | 契约的版本维护与兼容性判定 | 随跨团队边界数增长 |
| 平台内置族 | 平台采购与迁移（一次性） | 与平台外工具链的对接成本 | 随平台内资产数增长 |
| 差异回归族 | 按次运行的比对计算（两版明细都要扫） | 主键与比对窗口没对齐时的返工；结论没人解读就只是报表 | 随比对次数与单次数据量增长 |
| 流式规则（断言引擎族中成本结构独立的一支） | 校验执行的计算与流作业运维 | 乱序、迟到数据带来的误报与漏报 | 随吞吐量与规则数增长 |

**三条量级推导**：

1. **配置债**（【推算】）。见 7.3.2：T = 10,000、r = 5、w = 0.5 人时/年 ⇒ 25,000 人时/年 ≈ 12–15 人年（推导链：表数 × 每表规则数 × 每规则年维护工时，再按 7.3.2 的【经验】系数（每人年 1,700–2,000 工时）折算）。这条推导也是本节的「成本曲线何时反转」判据：当商业平台年费低于这笔人力成本时，总成本曲线反转。

2. **校验执行的扫描量**（【推算】）。若每天对 100 张 1 TB 的表各跑一遍全表扫描，则每天扫描量 ≈ 100 TB（推导链：表数 × 单表大小 × 每天次数）。改成只读统计与元数据时，假设每表统计与元数据量级为 MB（该假设属于【经验】），则每天 ≈ 100 张 × 1 MB = 100 MB；两者相差 **10⁶ 倍**（100 TB ÷ 100 MB = 10⁶），即约六个数量级。这就是「不碰数据的校验」与「扫数据的校验」在账单上的实际距离——**它比任何功能对比都更能决定你在万级表上选哪一族**。

3. **误报的处置成本**（【推算】）。若每天产生 N 条告警、每条平均处置 m 分钟，年处置工时 ≈ 365 × N × m ÷ 60。取 N = 200、m = 15，得 365 × 200 × 15 ÷ 60 = **18,250 人时/年 ≈ 9–11 人年**（推导链：365 天 × 每日告警数 × 单条处置分钟 ÷ 60；18,250 ÷ 2,000 ≈ 9.1，18,250 ÷ 1,700 ≈ 10.7）。这条推导最关键的一点是：**误报与真报的处置成本是一样的**，所以处置工时中被浪费掉的比例就等于误报率——在告警总量不变的前提下，把误报率从 50% 降到 20%，无效处置工时减少六成（推导链：无效占比由 0.5 降到 0.2，无效工时按「告警量 × 误报率」计）。**在总成本上，降误报比增检出更直接。**

**一条经验判据**（【经验】）：多数团队在**核心表数十到数百张**的规模上自建规则最划算，因为此时断言的可举证性正是业务要的；进入**千表以上**之后，长尾资产的规则写不完、也维护不动，成本曲线开始由配置债主导，此时结构上应该变成「关键链路断言 + 长尾基线覆盖」。这条线是经验线而非定律，可自行核验的判据是：统计最近一个季度新增表数与被覆盖的新增规则数，若比值持续下降，说明配置债已在积累。

还有一项常被忽略的成本：**规则失效之后的清理成本**。表结构一变（字段改名、分区策略调整、上游口径改了），挂在旧字段上的断言不会自动消失——它要么开始失败（变成噪声），要么静默地对着一个不再被写入的字段求值（变成假安慰）。**断言库越大，这类僵尸规则的绝对数量越多**，而它们的存在会让覆盖率的数字看起来比实际更高。判断方法是随机抽 20 条规则，逐条问「它上次失败是因为真问题，还是因为这个字段已经变了」。

### 7.5 决策树（每个分支都要有阈值依据）

```
[我该选哪一族、哪一种？]
 ① 坏数据能否在下游造成不可逆后果（赔付、监管报送、模型已上线）？
    ├── 能 → 走「写出前阻断」：嵌入式断言，或契约 + 发布门禁
    └── 否 → 继续
 ② 校验对象是流（分钟级必须知道）还是已落地的批次？
    ├── 流 → 流式规则（Flink 一类）+ 指标告警
    └── 批 → 继续
 ③ 表数是否已经进入千级并继续增长？
    ├── 是 → 优先评估基线式覆盖长尾（配置债压不住时）
    └── 否 → 继续
 ④ 转换是否已经用 dbt（或同类代码化转换）？
    ├── 是 → 从 dbt tests 起手，断言与模型同仓同版本
    └── 否 → 继续
 ⑤ 计算是否落在 Spark（数据湖 / 湖仓）上？
    ├── 是 → Deequ（库嵌入式 + 约束自动提议）
    └── 否 → 继续
 ⑥ 是否要求批流一体、且要独立于作业的 DQ 服务？
    ├── 是 → Apache Griffin（平台化）
    └── 否 → 继续
 ⑦ 是否有平台团队能长期承担自研 DQC 的维护？
    ├── 是 → 自研 DQC（与调度、血缘、SLA 同栈）
    └── 否 → Great Expectations / Soda Core 起手
 ⑧ 校验对象是不是「你无权改的上游」产出的表？
    ├── 是 → 在断言之上的加契约层 + 门禁
    └── 否 → 契约的协商成本换不回收益
 ⑨ 审计方要求平台内一体交付与本地合规举证？
    └── 是 → 国内平台内置 DQ（DataWorks / DataFinder / Univocity 一类）
 ⑩ 长尾资产没人愿意写规则？
    └── 是 → 用基线式覆盖，并把发现的事件回灌成断言
```

这棵树由两组彼此独立的判断组成：**①–③ 选族**（按后果可逆性、时效与规模），**④–⑩ 选具体形态**（按现有技术栈、团队与边界）。两组不能互相替代——一个只用 dbt 的小团队，如果链路是赔付型的，仍要先解决 ① 的写出前阻断，而不是先从 ④ 挑工具。

**阈值依据**：

- **①「不可逆后果」**：判据是「这条链路上坏数据的修复成本是否显著高于重跑成本」，即**能否回刷**这个可判定问题，而不是金额阈值（本章 §3.1 正是用「赔付型」与「观测型」两类链路做对照）。能回刷的链路，事后发现是可接受的。
- **②「流 / 批」**：判据是业务对「最坏多久必须知道」的容忍度（分钟级还是天级），以及校验对象是流还是已落地的分区；计量的单位是新鲜度要求，不是数据量。
- **③「千级表」**：依据是 7.4 的配置债推导——规则数随表数线性增长、维护人力不随规模摊薄，因此存在一个「单位成本反转」的规模；这里给的是经验线【经验】，判断方法在 7.4 末给出（新增表数与被覆盖规则数的比值）。
- **④「已用 dbt」**：依据是 dbt tests 的机制前提——断言与模型同仓、同版本、同一次评审；没有这个前提，它的最大优势（跟着模型一起演进、不会过期）不存在。
- **⑤「Spark」**：依据是 Deequ 的实现形态——约束验证以库的形式跑在 Spark 作业里（主文件 §1.4 与本章 §4.3 都把它记为 Spark 侧工具）；计算引擎不是 Spark 时这条不成立。
- **⑥「批流一体 + 独立服务」**：依据是 Griffin 的公开定位——Spark 上的独立 DQ 平台、支持批流一体（本章 §3.2.1 与 §4.3）；当你要的是「独立于作业的校验服务」而不是「作业内的一行断言」时，它比库嵌入式更合适。
- **⑦「自研的前提」**：依据是自研 DQC 的机制优势来自「与调度、血缘、SLA 同栈」，这需要一支长期维护平台的团队，而不是一次项目投入；**没有这支团队，自研的规则库通常会在半年左右失去维护**【经验】——规则随表结构漂移而失效，而没有人清理。
- **⑧「跨团队边界」**：依据是 7.3.4——契约的作用位置是发布门禁，收益正比于「你无权改的上游」的数量；边界数是这类组织约束的代理量。
- **⑨「平台内一体交付」**：依据是交付形态与举证要求（平台内置 vs 独立工具），而不是能力高低；判据是「审计方要什么形态的证据、数据是否必须留在平台内」。
- **⑩「长尾」**：依据是 7.3.2 与 7.3.3——长尾资产的规则写不完（成本随字段数增长），只能用基线式自动覆盖，再把事件回灌成断言补进关键链路。

树里没有「预算」节点，这一点需要单独说明：把「预算是否超过 100 万/年」作为分叉，但没有给出这个数的来源。**预算不是一个筛选条件，而是规模效应在账面上的投影**——它由 7.4 的三条推导决定：你的表数决定配置债，你的扫描方式决定计算开销，你的告警量决定处置人力。把预算当作分叉节点，最常见的后果是**为省下许可费而选了一个机制上要持续投入人力的方案，两年左右发现人力成本反而更高**——许可费是一次性的账，配置债是按年滚的账，两者的形状不同，而立项时只看得到前者【经验】。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 传统数仓 / DWH | dbt tests + Soda Core | Great Expectations | 转换与断言不在同一仓时，断言会随模型演进而过期 |
| 实时数仓 | 流式规则（Flink 一类）/ Apache Griffin | 商业可观测性 | 只有落地后校验时，赔付型链路已经来不及拦 |
| 数据湖 / Iceberg 一类 | Deequ（Spark 侧）+ 可观测性平台 | 自研 DQC | 湖上的转换引擎与校验引擎不同栈时，规则迁移成本高 |
| AI 训练数据 | Anomalo / Mona（基线式为主） | Great Expectations + LLM 辅助起草 | 训练数据要的是「分布是否漂移」，这类问题写不成断言 |
| 多团队 Data Mesh | 数据契约（DataHub Contract / Bitol ODCS 一类） | 自研 + 门禁 | 没有契约时，跨团队问题只能靠下游监控发现 |
| 早期 0 → 1 | Soda Core + dbt tests | Great Expectations | 表结构与口径一天一变时，Expectation 套件要按数据集逐个装配、按字段逐条改写，维护成本落在最付不起的阶段 |
| 金融 / 强合规 | 自研 DQC + 契约门禁 | 商业可观测性做补充 | 只有监控时，举证不了「违反了哪条规则」，审计过不去 |
| 中国本土（合规优先） | 阿里 DataWorks / 字节 DataFinder | Univocity / 自研 | 数据不能出平台时，独立 SaaS 在交付形态上不成立 |
| 表数已上万、长尾无人维护 | 商业可观测性覆盖长尾 + 关键链路保留断言 | 继续扩自研规则 | 配置债已主导成本，再扩规则只会继续线性加人 |
| 迁移 / 重构期 | Datafold 一类 diff 回归 + 断言 | 手工比对 | 只靠断言无法验证「新旧两版结果是否等价」 |

矩阵的读法是：**先按「后果是否可逆」定阻断方式，再按「规模与技术栈」定形态**。每行「不选它的原因」都不是能力不足，而是**机制不落在收益点上**——判断矩阵用对了没有，只需回答一个问题：我的痛点是否出现在我准备引入的机制所作用的位置上。

**四个常见组合**（各说明职责边界与运维代价）：

1. **dbt tests + Soda + Monte Carlo**：dbt tests 管「模型产出是否符合断言」（开发期与 CI），Soda 管批处理的规则执行，Monte Carlo 管跨资产的异常与血缘。运维代价：三套东西的覆盖范围会重叠，必须明确「同一个字段的判定以谁为准」——否则会出现「Soda 说通过、平台说异常」而没人裁定的局面。
2. **Great Expectations + DataHub + 自研告警**：GX 做规则引擎，DataHub 提供血缘与元数据（血缘是质量问题的定位工具，见主文件 §1.3 与 §05 血缘章），自研告警对接钉钉 / 飞书一类渠道。运维代价：告警通道与规则库都靠自研维护；规则数与表数同步增长时，这套组合最先暴露 7.3.2 的配置债。
3. **Flink + Deequ + Prometheus**：Flink 做流处理，Deequ 做校验，Prometheus 采指标并告警。这里需要说明一处机制上的限制：**Deequ 的执行引擎是 Spark（本章 §4.3 记为「仅支持 Spark」），把校验放在 Flink 流的算子位置上并不成立**；可行形态是「流负责写入、批或微批侧跑 Deequ 校验」，真正作为流算子的规则要么写在 Flink SQL 里，要么用流引擎自己的算子。运维代价：两套执行形态并存，同一指标要在两处对齐口径，否则会出现「流侧说好、批侧说坏」。
4. **数据契约 + Monte Carlo + Soda**：契约定义 schema、SLA 与质量条款（边界上的承诺），Monte Carlo 监控契约里承诺的指标（如新鲜度与量级），Soda 下发规则执行。运维代价：三者要以契约为唯一真源，契约一改，下游监控与规则都要跟着改——**契约不嵌进 CI 时，这套组合退化为「一份没人维护的文档 + 两套各说各话的监控」**。

四个组合的共同点是**入口低门槛、关键链路强约束**：面向所有表的覆盖走自动或低成本路径，面向赔付型链路的判定走可举证的断言与门禁。反过来设计——全量强约束（规则写不完）或全量弱约束（关键链路没有判定）——是本主题最常见的形态错误。

### 7.7 选错的代价与迁移成本

**反模式：把「规则条数」当治理成果** —— 症状是规则数量被写进汇报，覆盖率的分母取「有规则的表数」 → 后果是规则集中在最好写的字段（非空、唯一、枚举），而真正出事故的跨表一致性、口径变更、值域漂移没人写；机制上这是把**可度量的量**当成了**要度量的量**，而可度量的量恰好是成本曲线最平缓的那一段 → 正确做法：在 §4.1 Step 6 列出的过程指标（覆盖率、执行成功率、告警响应时长、MTTR）之外，补一个结果指标——**被拦在发布之前的比例**。

**反模式：先买平台、后补断言** —— 症状是先签了可观测性平台，规则没人写、SLA 没人签 → 后果是平台只产出「分布异常」事件，而关键业务约束没人管；机制上基线式与断言式覆盖的是两类问题（7.3.3），且基线在新表冷启动期结构上无法工作 → 正确做法：先按 §4.1 的 Step 1–5 把关键链路的断言与 SLA 立起来，再用平台补长尾。

**反模式：把契约当文档** —— 症状是契约文件写了、也评审了，但不进 CI、不阻断发布 → 后果是与没有契约等价，还多出一份需要同步的文档；机制上契约的能力来自「挂在门禁上」这一位置（7.3.4），不挂在门禁上的契约只是一份声明 → 正确做法：契约必须可机器校验并接进发布流程；做不到时，诚实地退回消费者侧监控更好。

**反模式：阈值由个人凭经验拍** —— 症状是告警阈值由写规则的人拍定，之后没人回看 → 后果是误报把 oncall 训练成选择性忽略告警（§1.2 痛点 4 的「狼来了」）；机制上误报与真报的处置成本相同（7.4 第 3 条推算给出 9–11 人年量级），**误报吃掉的是本该用于真问题的处置能力** → 正确做法：阈值分两类管理——业务硬约束用静态阈值并可举证，波动型指标用历史窗口基线，且每月统计误报率并回看。

四个反模式的共同点是**它们都在机制层面改变了「成本随什么增长」**：规则条数替代了结果指标，平台替代了断言，文档替代了门禁，个人经验替代了阈值方法。评估一次 DQ 建设方案时，看的不是它列了多少能力，而是**它有没有让 7.4 表里「增长方式」那一列换项**。

**换成另一种形态要动什么**：

| 迁移方向 | 规则迁移 | 执行链路改造 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 开源断言工具 → 商业可观测性 | 断言可保留，转为关键链路 | 接入数据源与仓库元数据权限（中高） | 新增平台账号、权限与事件流程（中） | 从「写规则」转为「读事件并处置」（中高） |
| 明细级检查 → 统计类检查 | 大部分规则要改写为统计口径（中高） | 执行位置从数据侧移到元数据侧（中高） | 需要统计与元数据库的维护（中） | 统计口径与阈值方法（中） |
| 消费者侧监控 → 生产者侧契约 | 断言从「下游的规则」变成「双方签字的条款」（中） | 要进 CI 与发布门禁（高） | 新增契约 Owner 与版本流程（高） | 跨团队协商与兼容性策略（中高） |
| 批校验 → 流式校验 | 规则要按流语义重写（窗口、乱序、幂等）（高） | 校验进入流作业（高） | 流作业运维与背压处理（高） | 流处理语义（高） |
| 自研 DQC → 平台 / 工具 | 规则要按目标 DSL 重写（中高） | 与调度、血缘的耦合要拆开（中） | 自研的定制告警与看板要迁移（中） | 目标工具的 DSL 与 API（中） |

这张表最容易被低估的是「执行链路改造」与「规则迁移」两列：**校验位置一变，语法几乎都要重写**（明细检查改写为统计口径、批规则改写为流语义），而且改完之后要重新校准阈值——重校准这一步常被漏掉，表现为迁移后告警量暴涨。表里还有一条规律：**从「批」迁到「流」的代价明显高于反向迁移**，因为流的窗口与乱序语义要重新定义规则的正确含义，而反过来只需接受更高的延迟。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 赔付型链路（错一个数就有后果） | 嵌入式断言，或契约 + 门禁 | 只有写在写出之前，才谈得上「拦住」 |
| 观测型链路（少几条没人发现） | 落地后校验 + 基线式覆盖 | 不值得为它阻塞生产链路 |
| 要分钟级知道 | 流式规则（Flink 一类） | 批校验的周期决定了它最坏情况下的发现延迟 |
| 已经用 dbt 做转换 | dbt tests | 断言与模型同仓同版本，才会跟着演进不过期 |
| 计算在 Spark 上 | Deequ | 约束验证以库的形式跑在同一个引擎里，省一次数据搬运 |
| 有平台团队且规模上万表 | 关键链路断言 + 长尾自动覆盖 | 配置债随字段数线性增长，长尾写不完也维护不动 |
| 上游是你无权改的团队 | 加契约层 + 发布门禁 | 契约把校验点前移到发布之前，修复成本最低 |
| 审计要「违反了哪条规则」 | 断言式（可举证） | 基线只能说「偏离了历史」，举不出违规项 |
| 新表多、老历史短 | 断言为主 | 基线在新表冷启动期结构上无法工作 |
| 告警量已经压垮 oncall | 先降误报，再谈增检出 | 误报与真报的处置成本相同，降误报直接换回处置能力 |
| 数据不能出平台 | 平台内置 DQ（DataWorks / DataFinder 一类） | 交付形态决定可行性，与能力高低无关 |
| 迁移 / 重构期要验证等价性 | diff 回归 + 断言 | 断言回答「是否符合预期」，diff 回答「新旧是否等价」 |

> 本节小结：这些方案之间真正起决定作用的差别只有一条——**你的断言挂在链路的哪一环**。「挂在写出前」换来拦住坏数据，代价是阻塞关键路径与重跑补偿；「挂在落地后」换来不阻塞与可跑全量，代价是坏数据已在下游跑过一个周期；「挂在元数据上」成本最低、覆盖最广，代价是只看得到形状、看不到值。**「成本随什么量增长」不是与它并列的第二条差异，而是「选族」这同一次选择在账面上的投影**——读值的那一族成本随字段数走，读统计与元数据的那一族随数据源数走，读契约文本的那一族随跨团队边界数走；正因为位置与成本是同一个决定的正面与账面，7.1 把它拆成两条判据只是为了分别回答，而不是两个可自由组合的选择。**其余维度（AI 能力、社区规模、评分高低）都是这一条选择的下游后果。**
>
> 💡 **思考锚点**：把「挂在链路哪一环」这条判据套回你的存量断言上：如果它们大多还挂在「落地后」，从里面挑一条提到「写出前」，这条链路被阻塞时你拿什么去补偿重跑——这条链路值不值得为它付这份阻塞？
