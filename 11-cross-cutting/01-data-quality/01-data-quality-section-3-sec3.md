## 3. 设计模式与范式

> 原 § 3 共 111 行：5 个模式中有 4 个带结构示意（1 张流程草图、2 段 YAML、1 段 PySpark 代码），加一张 7 行场景决策表与 7 条反模式；机制、代价与失效点未展开，重写为 303 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

质量模式的对照表读起来像一道按场景的选择题：传统数仓选 dbt tests、实时数仓选流式规则、数据湖选契约、AI 数据选可观测——仿佛数据形态一确定，模式就唯一确定。但把两套「实时链路」放在一起看，这个表立刻失效：一套是订单支付这类「错一个数就赔付」的链路（必须在写出之前拦住），另一套是行为日志这类「少几条没人发现」的链路（事后抽样就够）。同一个「实时数仓」，正确模式完全不同。

差异的根子就在表中第一行**断言执行位置**上：**断言必须有一个执行位置，而这个位置决定了它能做什么、不能做什么**。断言执行在数据落地之后，它只能**判定**——发现坏数据时，坏数据已经在表里了；断言执行在数据写出之前（处理链路内或 CI 里），它才能**拦截**；断言执行在两个团队的组织边界上，它才谈得上**定责**。五个模式不是五种工具，是断言执行位置的五个落点。

表中第二行是**断言从哪里来**：人预先写死（中心化、声明式、嵌入式、契约式都属于这一类），还是从资产自身的历史分布里学出来（可观测式）。这一条决定了覆盖长尾的成本曲线：人写的断言，覆盖成本随表数线性增长；学出来的基线，接一次采集就能覆盖一张表。两条路线都在生产里存在，原因见 3.2.5 的失效点——学出来的基线知道「什么是往常」，不知道「什么是正确」。

表中第五行**变更频率与历史要求**管的是另一件事：**规则库的维护成本由谁承担**。规则是活的：业务变了、口径变了、上游改了字段，规则必须跟着变。规则放在平台里，维护成本落在数据平台团队；放在模型旁边，落在建模的人；写进契约里，落在生产方。所以选型时真正要问的不是「哪个模式更强」，而是**「规则长在谁家里，谁在什么时候必须更新它」**——3.5 的七条反模式里，多数成因都是这一条没回答清楚。

表中第三行**数据形态与写入模式**看似技术细节，实则直接决定断言能不能有落点：**批处理有「这一批结束了」这个时刻**，断言可以挂在这个时刻上；**流处理没有**——数据连续到达，所谓「分钟级校验」实际是「滚动窗口上的校验」，窗口边界是人设的。这决定了流式链路上不存在「全量检查完再放行」这个选项，只能做窗口内的部分校验。多数团队把它当性能问题来调（窗口调大调小），它其实是语义问题：窗口越小、越接近拦截，漏检的概率越高。

表中最后两行（规模与成本约束、团队技能与运维能力）是关于团队自身的：同样一套断言，自研平台的运维面包括调度、存储、告警通道、权限与版本升级，而声明式方案的运维面是一组跟着代码库走的文件。**不少质量项目不是因为选错模式失败，而是因为选了一个自己运维不起的模式**——它上线时可用，一年后因为没人维护而变成噪声源；「可观测式」那一档的成本（对误报的持续调优）属于同一类长期负担。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 断言执行位置（落地后 / 写出前 / 组织边界上） | 只能判定、能拦截、还是能定责 | 「质量平台建起来就都一样」——位置不同，能力边界完全不同 |
| 断言来源（人写死 / 从历史分布学） | 覆盖长尾的成本是随表数增长，还是接入一次即覆盖 | 「规则写全了就能覆盖」——长尾表的规则永远写不全 |
| 数据形态与写入模式（批 / 流 / 变更流） | 断言能否落在一个确定的批次边界上 | 「流式就是批式加个定时器」——流没有「这一批结束了」这个时刻 |
| 访问模式（事后对账 / 在线决策消费） | 检查周期的上限由谁决定 | 「把周期调短就行」——周期必须短于「数据产出到被消费」的间隔才有意义 |
| 变更频率与历史要求 | 规则库的维护负担，以及能否对历史回溯重算 | 「规则定一次管很久」——上游改一次字段，一批规则静默失效 |
| 规模与成本约束 | 全量校验还是抽样校验 | 「全量校验更安全」——全量校验的成本与数据量同阶 |
| 团队技能与运维能力 | 自研平台、声明式落地，还是买 SaaS | 「上平台比改代码省事」——平台的运维面比一组 YAML 大一个量级 |

这张表不是选型问卷，而是一组判据：每一行都能在你的环境里被验证（有没有中心团队、批次边界存不存在、规则维护工时占比多少）。凡是无法验证的行，写下的结论只是偏好。

把这五个模式放回上面三条主线上，它们的关系就清楚了：**中心化**把断言放在数据落地之后、由平台团队维护（换跨域复用，付滞后与带宽）；**声明式**把断言放到模型旁边、由建模的人维护（换搭上同一条评审通道，付「只覆盖被建模的那部分」）；**嵌入式**把断言推进到数据写出之前（换拦截能力，付关键路径耗时）；**契约式**把断言抬到组织边界上（换责任可判定，付版本与协调成本）；**可观测式**不写断言，改从分布里学（换长尾覆盖，付误报与调优）。**它们不是互斥选项，是断言在三个位置上的分层落点**，这正是 3.4 要谈组合的原因。

### 3.2 模式逐个拆解（核心节）

五个模式按「断言的执行位置」排列：中心化（3.2.1）与可观测式（3.2.5）都在数据落地之后，前者由人写断言、后者由机器学基线；声明式（3.2.2）把断言推到提交阶段；嵌入式（3.2.3）推到数据写出之前；契约式（3.2.4）推到组织边界上。同一个系统里它们通常同时存在。

读每个模式时请盯住六项：被什么约束逼出来（它为什么存在）、结构（长什么样）、机制（为什么有效）、代价（必然付出什么）、失效点（什么时候优点反转成缺点）、真实使用（谁在用）。前两项容易写，后四项才决定模式能不能用对——尤其失效点，它回答的是「在什么规模、什么变更频率下，这个模式会变成错的」。

每个模式下面还附了一条**判定方法**：一个可以在自己系统上跑一遍的检查动作，用来确认这个模式的收益是否还在。模式本身没有「好不好」，只有「在你当前的约束下成不成立」。

每个模式都配了一段结构示意，这不是装饰。质量模式之间的差别几乎都在结构里：规则对象引用不引用作业（3.2.1）、断言与模型在不在同一份文件（3.2.2）、断言在不在关键路径上（3.2.3）、契约里有没有版本字段（3.2.4）、断言是人写的还是从分布里学的（3.2.5）。把这五处结构看明白，用法与代价就都能推出来。

#### 3.2.1 DQC 中心化（Data Quality Center）

- **被什么约束逼出来**：一套质量规则需要服务几十上百张表，而各业务团队的作业代码互不相通——「把规则从作业里抽出来、集中登记与执行」是唯一能让规则跨域复用的结构。
- **结构**：规则是平台里的一等实体，与产出数据的作业之间没有任何引用关系；执行按调度周期扫描已经落地的数据。

```sql
-- 中心化 DQC：规则与作业解耦，规则对象不引用任何作业
CREATE TABLE dq_rule (
  rule_id      BIGSERIAL PRIMARY KEY,
  dataset_urn  TEXT NOT NULL,          -- 规则的作用对象：被检查的表
  rule_type    TEXT NOT NULL,          -- completeness / uniqueness / consistency / validity / timeliness
  target_field TEXT,                   -- 字段级规则才有值
  assertion    TEXT NOT NULL,          -- 机器可执行的断言表达式
  severity     TEXT NOT NULL,          -- P0 / P1 / P2 / P3（对齐 §4.2 的告警分级）
  owner_user   TEXT NOT NULL,          -- 具体到人，不许写团队名
  schedule     TEXT NOT NULL           -- 检查周期，独立于作业调度
);
CREATE TABLE dq_result (               -- 检查结果是时序指标，不是阻断信号
  rule_id    BIGINT      NOT NULL,
  checked_at TIMESTAMPTZ NOT NULL,
  passed     BOOLEAN     NOT NULL,
  observed   NUMERIC,                  -- 实际观测值，用于趋势与调阈值
  PRIMARY KEY (rule_id, checked_at)
);

-- 关键：这两张表里没有一条外键指向"写出这张表的作业"
--       规则执行发生在数据已经落库之后 → 结构上只能判定，不能拦截
```

- **为什么这样设计有效**：因为规则对象不引用任何作业，所以同一条规则模板可以套到任意多张表上，覆盖面的增长不依赖各业务团队改代码——「一次定义、多处执行」是中心化唯一但决定性的收益。
- **代价**：① 检查滞后于产出结构性地存在：数据已经写进表，检查才跑；② 平台成为所有规则变更的唯一通道，规则演进速度等于平台团队带宽；③ 规则与业务语义的对应关系没有强制校验点——规则写了没人维护，不会报错，只会静默失效。
- **失效点**：当**数据从产出到被消费的间隔短于检查周期**时，「统一管理」反转成「检查结果永远迟到」：因为断言的执行位置在数据落地之后，而下游消费发生在落地之后的几分钟内，检查跑完时坏数据已经被消费。此时正确的动作是把断言前移（3.2.3 的链路内门禁，或 3.2.4 的契约），而不是把周期调得更短——调短只让发现更早，不改变「数据已经产出」这个事实。
- **判定方法**：取一张核心表，把「数据可被消费的时刻」与「该表最近一次质量检查完成的时刻」并排列出最近 30 天，两者相减若持续为正且量级与消费间隔相当，说明中心化在这条链路上已经不够。
- **真实使用**：Apache Griffin 由 eBay 于 2016 年开源，定位即 Spark 上的独立 DQ 平台（主文件 §1.4）；§6 案例 1.5 的落地路径也把这一形态放在起点——0→1 阶段做的是「1 个业务、10+ 关键表」的关键表校验与告警分级，「产出即校验、延迟分钟级」的流式实时校验要到 1→10 阶段才引入，也就是说这一阶段的校验仍落在已经落地的数据上；§4.3 工具链把 Deequ、Griffin、Great Expectations 并列在「开源工具」一栏；国内商业化平台里，阿里 DataWorks 被 §7.2 选型表列在「中国本土」一行；至于「以表 + 分区为校验对象、按调度周期运行」这一具体产品行为，本节不引具体文档作据，请以 DataWorks 官方文档当前版本的「数据质量」章节为准，或按关键词「DataWorks 数据质量 分区」自行检索核验。【公开】（来源：主文件 §1.4 演进历程 2016 年条目；§4.3 工具链表；§6 案例 1.5 的落地路径；§7.2 选型决策表）

#### 3.2.2 声明式 DQ（Declarative DQ）

- **被什么约束逼出来**：数据模型本身是版本化、要被评审的产物——把断言写在模型旁边，规则就能搭上同一条代码评审与 CI 通道，而不必再建一套规则管理流程。
- **结构**：断言与模型定义同文件、同版本、同一次提交；执行的产物是「模型 + 断言」这一个可版本化对象。

```yaml
# 声明式：断言与模型同文件、同版本、同一次代码评审
# （dbt 的 schema 测试即此形态；§4.3 把 dbt tests 与 Soda Core 列在同一类）
models:
  - name: dwd_trade_order
    columns:
      - name: order_id
        tests: [not_null, unique]        # 断言与列定义同处，改列必然看到断言
      - name: order_status
        tests:
          - accepted_values:
              values: [CREATED, PAID, SHIPPED, CLOSED]
      - name: amount
        tests:
          - accepted_range:
              min_value: 0               # 与主文件 §1.1 的「有效性」维度对齐
```

- **为什么这样设计有效**：因为断言与模型在同一次提交里，所以「改了模型、忘了改断言」这类漂移在代码评审阶段就暴露；更进一步，断言可以以退出码的形式挂在 CI 上，规则就从「事后报表」变成「提交门禁」——这是它相对中心化最本质的差别：**判定发生在数据产出之前**。
- **代价**：① 它依赖模型被集中定义，散落的脚本作业接不进来，覆盖率天然只覆盖「被建模的那部分」；② 断言只能看到自己这一层，跨系统、跨表的对账仍要回到中心化平台；③ 断言数量随模型数量增长，CI 时间随断言数增长，这两条曲线迟早相交。
- **失效点**：当断言数量增长到 CI 时长不可接受时，「每次提交都验证」反转成「抽样验证或干脆跳过」：因为声明式的成本随断言数与数据量线性增长，而提交频率不变。此时只能按严重级别分组（P0 全跑、P2 抽样），而分组本身就是一次降级——声明式最容易在「覆盖得很全」之后，死于自己的全覆盖。
- **判定方法**：查 CI 里断言相关步骤的时长占整条流水线的比例；若它已经超过一半，或团队开始出现「按路径跳过断言」的提交，说明分组策略必须提上日程。
- **真实使用**：Great Expectations 于 2017 年开源、Soda Core 于 2019 年出现（主文件 §1.4），两者都以「断言写在数据定义旁边」为形态；§4.3 工具链把它们与 dbt tests 并列；§4.5 示例 2 给出 Soda 的 YAML 声明写法；§7.2 的选型表把「传统数仓 / DWH」首选定为 dbt tests + Soda。【公开】（来源：主文件 §1.4 演进历程 2017 / 2019 年条目；§4.3 工具链表；§4.5 示例 2；§7.2 选型决策表）

#### 3.2.3 嵌入式 DQ（Inline DQ）

- **被什么约束逼出来**：业务要求「不合格的数据不允许进入下游」——这个要求在语义上就排除了事后检查，断言必须成为处理链路本身的一个算子。
- **结构**：断言是作业里的一个步骤，位于数据流出（落库或发出）之前；失败时链路中断或改道隔离区。

```python
# 嵌入式：断言是作业里的一个算子（PySpark + Deequ 形态，见 §4.3 工具链）
from pydeequ.checks import Check, CheckLevel
from pydeequ.verification import VerificationSuite

check = (Check(spark, CheckLevel.Error, "order_gate")     # Error → 让这一步失败
         .isComplete("order_id")
         .isUnique("order_id")
         .isContainedIn("status", ["CREATED", "PAID", "SHIPPED", "CLOSED"]))

result = VerificationSuite(spark).onData(df).addCheck(check).run()

# 关键差别在 CheckLevel：它是"记一条失败"还是"让这一步失败"
#   只有后者才叫嵌入式——前者只是把 DQC 挪到作业里跑，位置没变
df_out = df if result.status == "Success" else quarantine(df)
```

- **为什么这样设计有效**：因为断言与数据流在同一进程、同一次执行里，所以「这一批没通过校验」与「这一批被写出」是同一个决策点，坏数据在下游根本不存在（或被隔离到 quarantine 表）。**拦截能力来自位置，不来自规则写得更好**。
- **代价**：① 检查进入关键路径，检查耗时直接加到作业时长上，检查越重、产出越晚；② 规则变更要发版，阈值改动走一次上线流程；③ 检查点越密，作业结构越碎，调度图与血缘都变复杂，排障时要多跳几层。
- **失效点**：当检查逻辑变重（全量去重、跨表比对、模型打分）时，「拦住坏数据」反转成「拖垮整条链路」：因为嵌入式检查在关键路径上同步执行，耗时与数据量同阶，而链路的端到端时延预算不变。正确的做法不是把检查调快，而是把它拆开——**轻量断言留在链路内当门禁，重量校验移到旁路做对账**（§4.2 把执行方式分为批处理、流式、嵌入式、按需四类，正是这个拆分的落点）。
- **判定方法**：把链路里每一条断言的耗时加起来，除以端到端时延预算；占比超过一个预先约定的上限（例如三成）时，就该把最重的那条移出关键路径。
- **真实使用**：Deequ 由 AWS 于 2018 年开源（主文件 §1.4），以 Spark 上的 Check / VerificationSuite 实现「规则作为作业的一部分」；§4.3 工具链把它记为「Spark 自动约束发现」；§4.2 把「嵌入式」单列为一类执行方式，用于强一致场景；阿里 2018 年起的实时数据质量平台把五类规则前移到分钟级链路内（§6 案例 1.1）。【公开】（来源：主文件 §1.4 演进历程 2018 年条目；§4.2 规则执行方式表；§4.3 工具链表；§6 案例 1.1）

#### 3.2.4 契约式 DQ（Contract-based DQ）

- **被什么约束逼出来**：质量责任落在两个不同团队之间，而下游对上游没有编辑权——「谁承诺什么、违约怎么判」必须写成一份双方都能机器校验的协议，否则质量要求只能停留在沟通记录里。
- **结构**：契约是一份版本化的可机读对象，schema、SLA、语义与 owner 同处一份文件，生产方按它发布、消费方按它校验。

```yaml
# 契约式：断言从"检查数据的规则"变成"两个团队之间的协议"
# 与 3.2.2 的差别不在语法，而在谁签字、违约时谁负责
contract: dwd_trade_order
version: 2.1.0                     # 版本号是契约的核心字段，不是装饰
owner: trade-platform              # 生产方（对齐主文件 §2.1 的数据契约定义）
consumers: [ads_gmv_daily, risk_feature_daily]
schema:                            # 结构承诺：新增列须向后兼容
  - {name: order_id,   type: string, pii: false, required: true}
  - {name: user_phone, type: string, pii: true,  required: false}
sla:                               # 服务承诺：可被下游自动校验
  freshness:    {by: "T+1 09:00", window: 1d}   # 对齐主文件 §2.1 的 SLA 定义
  completeness: 0.9995
  volume:       {min_ratio: 0.7, max_ratio: 1.3}  # 相对近 7 日均值
  availability: 0.999
change_policy: backward_compatible # 破坏性变更须提前通知并等待消费方适配
```

- **为什么这样设计有效**：因为质量要求被写成了两侧可独立校验的对象，违约变得可判定：下游按 freshness 与 volume 阈值自查，生产方在同一份文件上被校验，责任不再靠事后对质界定。**它把「质量」从一种期望变成一条可执行的边界**。
- **代价**：① 契约必须版本化并维护兼容性规则，schema 变更从「改字段」变成「发版本 + 通知 + 等适配」；② 契约数量随消费方数量增长，每接一个下游就多一份要长期维护的协议；③ 它只管边界上的承诺，管不了边界内部——上游内部多算了一步、少过滤了一批，契约不会发现。
- **失效点**：当契约数量超过团队能维护的带宽时，「责任清晰」反转成「契约僵尸」：因为契约若不嵌进 CI，就拦不住违约发布，而每份契约的手工评审成本固定，数量一多，评审必然退化成点确认。此时要么把兼容性判定自动化（schema 差异进 CI 自动判破坏性），要么把契约范围收缩到关键下游——契约式最怕的不是没有契约，是一堆没人维护的契约（这与 3.5 的「忽视 Schema 漂移」是同一条机制的两种表现）。
- **判定方法**：随机抽三份契约，问「上次因为契约被拒的发布是哪一次」；答不出来的那份，基本已经从协议退化成了文档。
- **真实使用**：主文件 §1.4 把 2023 年记为「数据契约成为业界共识」的一年；§7.2 的选型表把「多团队 Data Mesh」一行的首选指向「DataHub Contract + 自研」，备选正是 **Bitol**；此外商业侧也有把契约做进平台的产品（Bit.io、Monte Carlo 的数据契约能力、DataHub 的契约形态同属这一方向，可按各自产品文档的当前版本核验）。§4.1 的 Step 5 把「上游接入必须签 Data Contract」写进落地步骤。【公开】（来源：主文件 §1.4 演进历程 2023 年条目与 §2.1 概念表；§4.1 Step 5；§7.2 选型决策表）

#### 3.2.5 可观测式 DQ（Observability-driven DQ）

- **被什么约束逼出来**：断言写不出来、也写不全——数据量大、字段多、分布随业务节奏变，把「事前把断言写全」作为覆盖策略，成本上不成立。
- **结构**：不定义断言，从资产自身的指标时序里学基线，偏离基线才产出信号；信号带归因线索，但不直接对应某条规则。

```text
可观测式：断言来源从"人写死"换成"从自身历史学"（不落规则表，落基线）

  资产（表 / 字段）
      → 采集五类信号 → 时序库 → 基线模型 → 偏离判定 → 告警 + 归因
        freshness  多久没更新 / 更新间隔是否偏离
        volume     行数、分区数相对历史的比值
        schema     结构变更事件（增列 / 改类型 / 删列）
        quality    空值率、枚举分布、数值分位
        lineage    上下游是否也在异常（用于归因，不是判定）

  ─────────────────────────────────────────────────────────
  与中心化 DQC 的结构差别不在"有没有监控"，而在两处：
    ① 断言从哪来：DQC 是人预先写死的；可观测是从历史分布学出来的
    ② 报的是什么：DQC 报"哪条规则失败"；可观测报"哪个指标偏离了多少"
  成本随之转移：省下写规则的成本，换成对误报的持续调优
```

- **为什么这样设计有效**：因为判定依据是资产自己过去的表现，所以它不需要人预先知道「这张表的正常值域是多少」——覆盖长尾表的边际成本从「为它写规则」降到「把它接进来」。**规则式覆盖长尾的成本是线性的，可观测式是接入一次即覆盖**。
- **代价**：① 误报是结构性的：基线模型对业务节奏没有先验，大促、节假日、上游重刷都会被判成异常，每次误报都要有人来判断；② 它只有「偏离」没有「错误」——分布正常但语义错了（金额单位从元改成角、状态枚举换了一套）不会表现为分布异常；③ 时序与基线本身是新的存储与计算，成本随「字段数 × 指标数」增长。
- **失效点**：当业务的正常波动幅度不小于异常幅度时，「不写规则也能发现异常」反转成「信号淹没在噪声里」：因为基线的隐含假设是「历史分布代表正常」，而业务节奏让分布在正常状态下就大幅跳变，模型无法区分「这是大促」与「这是故障」。退一步说，即便误报率压下来，确定性要求高的场景仍然必须回补显式规则（关键字段值域、跨表对账）——**可观测式不是规则式的替代品，它的正确位置是覆盖长尾与兜住未知**。
- **判定方法**：统计一段时间内基线告警的处置结论里「业务正常波动」的占比；若该占比一直很高，说明基线需要引入业务日历作为先验，或该退回到显式规则。
- **真实使用**：主文件 §1.4 把 Data Observability 概念的成型记在 2020 年（Monte Carlo Data 当年融资，该概念随之被广泛引用）；Anomalo、Mona、Bigeye 在 2022 年前后以自动异常检测进入同一市场（主文件 §1.4）；§4.3 把 Monte Carlo 记为「自动字段级血缘 + ML 异常检测」，§4.5 示例 4 给出与血缘平台集成的写法；§7.2 的选型表把「AI 训练数据」一行的首选指向 Anomalo / Mona。【公开】（来源：主文件 §1.4 演进历程 2020 / 2022 年条目；§4.3 商业 SaaS 工具链表；§4.5 示例 4；§7.2 选型决策表）

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 传统数仓、模型集中定义、团队熟悉 SQL | 声明式（3.2.2）+ 中心化（3.2.1） | 只上中心化则规则与模型两条线各自演进，改模型时规则静默失效 | 数据模型是否**集中定义且被评审** |
| 实时链路、坏数据不得进入下游 | 嵌入式（3.2.3） | 中心化在这个场景只能事后发现，坏数据已被消费 | 端到端时延预算内**能否容下检查耗时** |
| 多团队 Data Mesh、上下游权责分离 | 契约式（3.2.4） | 中心化要求下游有权改上游的规则，权责不对等 | 是否有**可版本化、可双侧校验的协议载体** |
| 数据湖、消费方数量多且持续增加 | 契约式 + 可观测式 | 只做契约则每接一个消费方多一份维护负担 | 消费方数量与**契约维护带宽的比值** |
| AI 训练 / RAG、字段多、分布随时漂移 | 可观测式（3.2.5）+ 契约式（3.2.4） | 只写规则覆盖不到长尾、跟不上分布变化；只用可观测式则下游拿到的字段含义与 SLA 没有可校验的承诺 | 是否存在**值得预先枚举的关键断言** |
| 早期 0→1、表少且变更频繁 | 声明式（3.2.2）+ 可观测式（3.2.5） | 自研平台在这个阶段是纯负债，运维面远大于收益；只做声明式则没被建模的表处于盲区，接一层指标采集比写规则便宜 | 表数是否**还没到「记不住有哪些」的程度** |
| 金融 / 强合规、需可追溯可审计 | 中心化 + 契约式 + 嵌入式 | 单靠嵌入式看不到跨表对账，单靠中心化拦不住写入 | 是否要求**校验结论可逐条追溯** |
| 多源接入、Schema 频繁演进 | 契约式 + 中心化 | 只做中心化则 schema 变更到审计时才发现 | 变更是否**发生在组织边界上** |

表里最常被误选的一对是**中心化 DQC 与嵌入式 DQ**。多数团队会先上中心化：它看起来最像基础设施，一次建设、多表复用，立项也最好讲。但机制上，中心化的成立前提是「质量可以事后检查」——这在离线 T+1 链路里成立，在实时链路上不成立：数据从产出到被消费可能只有几分钟，检查跑完时坏数据已经进了下游。反过来，直接上嵌入式也不对：它把每张表的每一条规则都塞进作业，改一条阈值要走一次上线，规则数量一多就会被绕过。正确的关系是分层的——**需要在产出前拦住的断言放嵌入式，需要跨表对账与长期趋势的断言放中心化**；把两者当替代品二选一，得到的一定是「要么拦不住、要么改不动」。

第二容易被误选的是**契约式与中心化**。直觉是「先把中心平台建起来，以后再补契约」，但两种结构的责任归属完全不同：中心化把规则的所有权给了平台团队，契约把承诺的所有权留在生产方。在一个下游无权改上游规则的组织里，先建中心平台的典型结局是「平台上有规则、上游不认账」，质量争议重新回到沟通层面。契约式的落地顺序恰好相反——先有书面承诺与版本，平台只是执行与度量这些承诺的地方。

读这张表有一个固定顺序：**先问断言执行在哪一侧**（这一行决定候选范围），再问断言从哪里来（人写还是从分布学），最后才看工具与预算。跳过前两步直接比工具，得到的结论通常与本组织的约束无关——同一个工具在这两个位置上的能力差得很远。表里每一行的「关键判据」都写成了一句可以在环境里验证的问题，它才是这张表真正的用法；模式名只是结论。

### 3.4 组合模式：真实系统不会只用一种

**组合一：声明式 + 可观测式（写得出规则的用前者，写不出的用后者）**

- 构成点：核心模型旁挂声明式断言进 CI；长尾表与非核心资产只接指标采集与基线检测。
- 职责边界：声明式负责「已知的正常是什么」，可观测负责「我不知道正常是什么，但你不正常我会发现」。
- 运维代价：两套系统、两套告警、两套阈值，必须统一告警分级（§4.2 的 P0–P3 分级），否则同一个故障会报两次。
- 适合规模：模型化程度中等、有明确核心表的组织。【经验】

**组合二：嵌入式 + 中心化（链路内门禁 + 旁路对账）**

- 构成点：链路内只跑轻量断言（非空、唯一、枚举值域）做门禁；重量校验（跨表对账、历史趋势、全量去重）放旁路平台。
- 职责边界：嵌入式保证「坏数据不流出去」，中心化保证「流出去的数据对得上」。
- 运维代价：同一个字段的规则分散在两处，必须约定「哪一类断言放哪一侧」，否则会出现两处阈值不一致。
- 适合规模：实时链路 + 有对账要求的业务（交易、金融）。【经验】

**组合三：契约式 + 中心化 + 嵌入式（跨组织 + 组织内 + 链路内三层）**

- 构成点：契约定义团队之间的结构与 SLA 承诺；组织内部用中心化平台跑规则与趋势；关键链路用嵌入式门禁兜底。
- 职责边界：契约管边界，中心化管存量与横向对比，嵌入式管单条链路的即时门禁。
- 运维代价：三层都要维护，且要保证契约里的阈值与中心化平台里的规则不冲突——这一层成本是真实的，只有强合规场景才付得起。
- 适合规模：多团队、多地域、有审计要求的大型组织。【经验】

三条组合的差别只在一点：**轻量断言与重量校验各放在哪一侧**。所以选组合的顺序也是固定的——先按 3.3 定断言的执行位置，再定哪些断言属于轻量，最后才是选工具与买不买 SaaS。

组合的另一个约束来自告警通道：三套机制若各自发告警，同一份数据的问题会在三个群里同时出现。因此组合的落地前提是**告警分级与责任人的统一**——谁的规则触发、谁在多久内响应，必须在组合确定时就一并定下，否则组合带来的覆盖收益会被噪声抵消。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 规则过多导致告警风暴 | 告警量与规则数同阶，值班人开始批量屏蔽 | 真告警与噪声不可区分 → 屏蔽动作把真告警一起屏蔽 | 覆盖被当成 KPI，「多写一条规则」的成本为零而收益看起来为正 | 按严重级别分组 + 关键字段优先 + 抽样执行，先保证「报出来的都值得看」 |
| 只在生产环境监控 | 开发与预发没有断言，问题第一次出现在生产 | 缺陷在成本最高的位置被发现，回滚与回刷的代价最大 | 断言被视为「运维的事」，开发阶段没有它的执行入口 | 断言进 CI（开发跑关键断言）、预发跑全量、生产跑抽样 + 关键断言 |
| 硬编码阈值 | 阈值写在规则里，业务涨一倍后告警量同步涨一倍 | 阈值与分布脱钩 → 要么长期误报，要么长期漏报，且无人知道是哪一种 | 静态阈值最容易写、最容易评审，动态阈值的调参没有明确负责人 | 静态阈值只保留业务硬约束（金额 ≥ 0），趋势类改成相对基线的偏离判定 |
| 只监控不修复 | 告警有记录、有 owner，但没有 MTTR 统计，故障反复出现 | 发现能力不转化为修复能力，同一条规则反复触发，团队逐渐脱敏 | 项目验收标准是「规则上线数」，不是「故障闭环数」 | 每条 P0 规则绑定处置流程与 MTTR 统计，故障后回写规则库 |
| 把 DQ 当事后补救 | 规则库的增长总是跟着事故走，事故前没有任何断言 | 断言永远落后于问题形态，新类型的问题第一次仍然无人发现 | 「先出问题再加规则」是最自然的路径依赖 | 在接入环节就签契约（3.2.4），把质量要求前置到数据进来之前 |
| 用同一套规则套所有数据 | 日志表与订单表用同一个非空率阈值 | 阈值不是过严就是过松，业务方学会忽略告警 | 规则模板被当成「标准」，没有人按业务域重新定档 | 按业务域分级（核心交易 / 用户画像 / 日志 / AI 数据），各级各自定档 |
| 忽视 Schema 漂移 | 上游新增列、改类型、删列，下游任务某天突然产出空值 | 结构变更没有校验点 → 下游按旧假设解析，错误表现为静默的算错 | 结构变更被认为「不破坏兼容」，没人把它算作一次质量事件 | schema 变更纳入契约与评审，兼容性判定自动化并进 CI |

**「规则过多导致告警风暴」与「用同一套规则套所有数据」**。这两个反模式的暴露方式一个是**人的行为**、一个是**阈值的形状**：前者不是系统指标，而是值班群里开始出现「这个每天都报，别管」这类话；后者把各业务域的表按告警率排序，会看到某些域长期霸榜、某些域从不告警——同一组阈值不可能同时适配两类数据。机制上它们是同一枚硬币的两面：一个用低价值规则稀释信噪比，一个用错配的参数让告警失效——阈值是分布的参数，而不同业务域的分布本就不同（日志表允许缺失、交易表不允许），把一组参数套到两种分布上，必然在一边过松、另一边过严。其中「规则过多」更危险：**它破坏的不是某条规则，而是整条告警通道的可信度**，而一旦值班人形成屏蔽习惯，漏检率会一次性抬升且很难逆转。两者的修法也是同一条：不是继续加规则、也不是继续调优那个数，而是先按业务域分档（§4.1 的 P0–P3 分级就是这一层），再在每档内部各自定阈值、各自定抽样比例。

**「只监控不修复」**。它的暴露方式是**重复**：同一条规则在半年内触发了十几次，每次都有记录、都有人认领，但没人统计修复率。机制上的错配在于——发现能力由覆盖广度决定，修复能力由处置流程与 owner 明确度决定，两者由不同的人负责，于是「发现」这条线一路增长，「修复」这条线原地不动。判定方法很简单：把过去三个月每条 P0 规则的触发次数与对应修复次数列在一张表里，重复触发且无修复记录的那几条，就是这个反模式的证据。

**「忽视 Schema 漂移」**。它的暴露方式是**下游的表现形态**：任务不报错，但某些字段开始整列为空、或者数值突然差了一个量级。机制上，结构变更是一次「契约的静默修改」——上游加了一列或改了一个类型，下游按旧假设解析，多数引擎不会因此失败，只会给出错误结果。它之所以常被漏掉，是因为它既不出现在代码变更里（下游没改代码），也不出现在质量规则里（旧规则仍全部通过）。唯一可靠的对策是把结构变更本身当成一次质量事件：纳入契约版本、在 CI 里判定兼容性，并让下游在发布前就能拿到「上游将要改什么」的通知。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 百表 → 千表【经验，量级依据见 §6 案例 1.5「真实落地路径」的规模阶段】 | 人工维护的规则清单 | 维护成本随表数线性增长而人力不变，覆盖率开始下滑 | 声明式（搭上模型评审通道） | 需要先把散落的作业建模化，未建模的部分成为覆盖缺口 |
| 单团队 → 多团队 | 中心化 DQC | 中心团队无权替各域定义阈值，域内没有动力补规则 | 契约式 + 中央只读的度量层 | 从「写规则」变成「谈承诺」，并要维护契约版本与兼容性 |
| 离线 → 实时 | 中心化 DQC 的周期检查 | 检查周期追不上「产出到消费」的间隔 | 嵌入式门禁 + 旁路对账拆开 | 规则要按「能否进关键路径」重新分类，部分重量校验能力要放弃 |
| 规则式 → AI 训练 / RAG 数据 | 声明式断言 | 字段多、分布随时漂移，断言写不全也跟不上 | 可观测式 + 关键字段的显式断言 | 基线模型的误报要有人长期调，且必须接受「只有偏离没有错误」 |
| 单一数据源 → 多源接入 | 各源各自校验 | 同一份语义在不同源里定义不同，跨源对账没有共同口径 | 契约式 + 中心化的跨源一致性校验 | 要为跨源实体定义统一标识，这项工作的成本常常超过校验本身 |
| 人工消费 → Agent 消费 | 按人消费场景设计的断言 | 断言面向「人看报表」，而 Agent 取数需要的是「这条数据能不能用」的机器可读判定 | 契约 + 元数据上挂质量分，供检索时排序与拒答 | 质量结论要以机器可读形式回写到元数据，且要有拒答策略 |

这些跃迁有一个共同点：**触发换模式的从来不是「数据量」本身，而是某个具体的结构性矛盾**。上表前三行的成因是「维护成本线性增长」「权责错配」「检查周期追不上消费间隔」，后三行是「断言写不全」「跨源没有共同口径」「消费方从人变成机器」。数据量大不会直接让模式失效，它一定通过上面这几种矛盾之一起作用。

所以判断该不该换模式，看的不是「有多少张表」，而是几个能直接观测的量：规则维护工时占总工时的比例（接近饱和说明该从人工转向声明式）、P0 规则的重复触发率（高说明修复闭环缺失）、「数据产出到被消费」的间隔与检查周期的比值（比值小于 1 说明中心化在实时链路上不成立）、以及断言在长尾表上的覆盖分布（长尾全为空说明需要可观测式兜底）。这四个量都能从现有的调度、告警与规则库里算出来，不需要先做一轮架构评审。

这些量之所以能算出来，是因为它们都是既有系统已经产生的副产物：调度系统知道每张表什么时候产出，规则库知道每条规则什么时候跑完，告警系统知道每次触发与认领。换模式的判断因此不需要新建任何东西——**如果这四个量一个都取不到，那真正缺的不是模式，是度量**。

### 3.7 自检清单

- [ ] 每条规则是否有**具体到人的 owner**？写团队名即视为无人负责。
- [ ] 每条 P0 规则的阈值依据是什么？能否指出它来自业务约束、契约还是历史分布（三者都不是，就是硬编码）。
- [ ] 关键链路上的断言，执行位置在数据写出**之前**还是之后？之后的话，写出到消费的间隔是多少？
- [ ] 断言是否进了 CI？开发阶段能否拦住断言失败，还是只在生产发现？
- [ ] 规则库里的规则，有多少条已经三个月没触发过、也没人复核过？
- [ ] 是否存在**同一字段在两处阈值不一致**（嵌入式一处、平台一处）的情况？
- [ ] 告警分级是否与实际响应 SLA 一致？P0 的中位响应时长是多少？
- [ ] 每条 P0 规则最近三个月的触发次数与修复次数，能否列成一张对照表？
- [ ] MTTR / MTTD 是否在统计？没有这两个数，「只监控不修复」就无法被发现。
- [ ] Schema 变更是否有自动的兼容性判定，还是靠下游自己发现？
- [ ] 长尾表（无规则、低访问）是被可观测式覆盖了，还是根本没有被观测？
- [ ] 若接入了自然语言生成规则的能力，生成的规则是否经过复核？未复核的规则不得进 P0。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 需要跨表复用、可事后发现 | 中心化 DQC | 规则与作业解耦，覆盖增长不依赖各团队改代码；代价是只能判定、不能拦截 |
| 模型集中定义、有代码评审 | 声明式 DQ | 断言与模型同一次提交，漂移在评审阶段暴露；代价是只覆盖被建模的部分 |
| 坏数据不得进入下游 | 嵌入式 DQ | 断言与数据流同一执行，拦截与写出是同一个决策点；代价是耗时进关键路径 |
| 上下游权责分离 | 契约式 DQ | 承诺双侧可校验，违约可判定；代价是版本与协调成本随消费方增长 |
| 断言写不全、分布持续漂移 | 可观测式 DQ | 判定依据是资产自身的历史，长尾接入一次即覆盖；代价是结构性误报 |

> 本节小结：数据质量的模式选择，最终由**「断言执行在哪一侧——数据落地之后，还是写出之前」**这一条约束决定。它同时决定了能不能拦住坏数据、检查成本落在关键路径还是旁路、以及维护成本由谁承担；断言来源（人写死 / 从分布学）与协议形态（模型旁 / 契约里）都是在这一条确定之后才展开的次级选择。
