## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

把技术排成五条路线（横向联邦 / 纵向联邦 / MPC / TEE / 混合），并给了一张「场景 → 推荐模式」的对照表；本章 [§1.1](08-privacy-computing.md) 的「三大技术路线对比表」则按「原理 / 性能 / 安全性 / 适用场景」给同一批技术打分。两张表读下来最大的问题是：路线在表里看起来只是「性能 / 安全性」两列打分不同，读者于是按「哪个分高选哪个」决策。但真实的选型判据只有一个，而且它不在那两张表里——**明文允许在哪台机器上出现过**。

这条约束之所以是根约束，是因为它同时决定了另外三件事。第一，**信任锚**：信任的是密码学假设（MPC）、协议与参与方（FL）、还是硬件厂商与远程证明（TEE）——信任对象不同，能被攻破的方式就完全不同。第二，**代价落在哪里**：FL 的代价落在通信与收敛（明文在本方）；MPC 的代价落在通信轮数与电路深度（明文从不出现）；TEE 的代价落在攻击面与算子覆盖（明文在隔离区内出现）；DP 的代价落在效果损失（明文可以随便出现，被保护的是输出）。第三，**合规能不能被陈述**：能不能写出一组可被第三方复核的隐私参数。

所以选型的第一步不是问「哪个方案更强」，而是问「**这次协作里，我要保护的对象到底是什么**」——是原始记录不被对方看到，是模型不被反推，是查询出口不被反复试探，还是统计发布不能被推断到个体。保护对象不同，路线立刻分叉。

把这几条路线按保护对象重新归一次类，分工就清楚了：**保护原始记录不被对方看到**——横向联邦、纵向联邦、MPC 都能做到，差别在样本 / 特征的分拆方式与信任锚落在谁身上；**保护计算过程不被算力提供方看到**——只有 TEE 与 MPC 两条路；**保护计算结果不被推断到个体**——只有差分隐私这一类加噪机制，密码学路线对"结果本身泄露了什么"无能为力；**保护某类函数的可计算性**——同态加密（本章 [§2.2](08-privacy-computing.md) 的 PHE / FHE 之分）。

本章 [§1.1](08-privacy-computing.md) 与 [§2.1](08-privacy-computing.md) 把 DP 与 HE 归在「辅助技术」里是准确的：它们不单独构成一条协作路线，但少了它们，前面几条路线都会缺一块——FL 缺可陈述的隐私参数，MPC 缺对"结果本身"的保护。多数团队的做法是把它们按环节拼进同一条链路（3.2.5），而不是全程只走一条路线【经验】。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 明文允许出现的位置（威胁模型） | 决定路线归属：明文留在本方 → FL；明文从不出现 → MPC；明文在隔离区内出现 → TEE | 「TEE 性能好又安全，优先选 TEE」——数据进 enclave 已经算离开本方边界，合规判定口径不同 |
| 参与方数量与互信程度（半诚实 / 恶意） | 决定协议与安全模型：两三方可用 MPC；十方以上更适合联邦组织 | 「用最强的密码学协议总没错」——多参与方下 MPC 的组织与通信成本先崩，而不是安全性先崩 |
| 计算类型（求交 / 统计 / 训练 / 任意函数） | 决定是选专用协议还是通用运行时 | 「一个框架能覆盖所有场景」——专用协议的效率来自它在计算类型上做的假设 |
| 精度与可解释要求 | 决定能否用加噪类方案，以及是否能向监管解释 | 「差分隐私更轻，能上就上」——若业务要求精确计数，ε 再大也补不回精度 |
| 性能与网络预算（延迟 / 带宽 / 轮次） | 决定单次计算的可行上限，以及是否需要把高频查询换成别的路线 | 「开销大一点可以接受」——MPC 的成本主要在通信轮数上，跨机构网络的 RTT 决定了下限 |
| 合规可举证要求 | 决定要不要保留 ε、记账方式、协议出处与证明报告 | 「技术方案做对就行」——回答不了「凭什么保证」的方案，在审查面前等同于没有方案 |

还有一条边界值得先说清，否则后面五个模式都会被误用：**隐私计算与数据脱敏、与数据安全不是同一件事**。脱敏是**用可用性换隐私**——把明文改掉（掩码、泛化、加噪），改完信息就永久少了一部分；隐私计算是**在不减少可用信息的前提下控制可见面**——明文仍然完整参与计算，只是某几方看不到它。安全解决的是"数据会不会被不该拿到的人拿到"（访问控制、传输加密、审计），隐私计算解决的是"数据在被合法使用的过程中，对方能看到多少"。这三者可以叠加，但**任何一个都不能替代另一个**：把脱敏当成隐私计算，会得到一个"数字已经不能用但对方仍然拿到了名单"的方案。

最后一点前置约定：本节讨论的是**协作模式**，不是产品选型。同一个产品（FATE、SecretFlow、Occlum 等）可以承载几种不同的模式，同一个模式也可以由不同产品实现——所以判断"某个平台是不是隐私计算"，要看它在你的场景里承担了哪一环、那一环的明文位置与信任假设是什么，而不是看它的功能清单。

### 3.2 模式逐个拆解（核心节）

下面五节用同一套模板拆：**被什么约束逼出来 → 结构 → 为什么这样设计有效 → 代价 → 失效点 → 真实使用**。每节的「失效点」都只反转**它自己**的优点，不借用邻座的——这也是判断一个模式有没有被真正理解的办法：如果写不出它的失效条件，说明还没找到它的约束。第五节（混合）在结构上是对前四节的组合，因此它的失效点是"最弱环节"，而不是某一条具体的性能或精度性质。

#### 3.2.1 横向联邦学习（Horizontal FL）

- **被什么约束逼出来**：各方特征相同、样本不同，单方样本量不足以训练；同时样本（原始数据）不允许离开本方。
- **结构**：

```text
横向联邦：样本分拆，特征相同，只交换更新量
  参与方 A（本地样本）   参与方 B（本地样本）   参与方 C（本地样本）
        │                      │                      │
   本地多步训练            本地多步训练            本地多步训练
        │                      │                      │
        └──── 更新量（按样本量加权）───┬───────────────┘
                                      ▼
                              聚合（δ 服务端或协调方）
                                      │
                              下发新的全局参数
                                      │
                            ── 重复若干轮直到收敛 ──
  明文位置：始终在本方；跨域流动的只有更新量与参数
  常见加固：聚合前做梯度裁剪 + 差分隐私加噪（否则"只交换梯度"不等于隐私）
```

- **为什么这样设计有效**：因为一轮训练被拆成「本地多步 + 周期性交换更新量」，所以单轮通信量由**模型参数量**决定，而不由样本量决定——样本越多、本地步数越多，通信相对计算就越不占主导，这正是横向联邦能在设备侧跑起来的原因（本章 [§2.2](08-privacy-computing.md) 给出的聚合式 $w_{t+1}=\sum_k \frac{|D_k|}{|D|}w^k_{t+1}$ 就是这个机制）。
- **代价**：通信轮数与参数量成正比，参与方越多、每轮要同步的对象越多；且设备/机构会在轮次间掉线，聚合必须容忍部分参与，收敛性随之下降（FedProx、FedNova 这类算法就是在补这一项）。
- **失效点**：当各方的数据分布差异大（非 IID）时，「样本量扩大带来的收益」会反转成「聚合把分布差异平均掉」——因为按样本量加权的参数平均，落点不一定在任何一方自己的数据分布上；实践中表现为联合模型在某一方数据上的效果还不如只用自己数据训练。
- **真实使用**：联邦平均（FedAvg）由 Google 于 2016 年提出【公开，McMahan 等论文，可按标题 "Communication-Efficient Learning of Deep Networks from Decentralized Data" 自行检索】；Google 在 2017 年公开说明将其用于 Gboard 的输入预测【公开，判定入口是 Google Research 官方博客的联邦学习介绍文章】。FedML、FATE 是公开框架【经验】。判定方法：问对方对非 IID 做了什么处理、是否默认叠加差分隐私——只答"数据不动"的，等于没回答。
- **为什么"安全聚合"是这一型的必备件，而不是可选项**：协调方要完成加权平均，就必须看到各方的更新量；如果只有它一方的视图不受约束，那"数据不出域"只挡住了参与方之间的直接交换，**没有挡住协调方**。安全聚合把"协调方只看到总和、看不到任何单方更新"做成协议要求（本章 [§1.1](08-privacy-computing.md) 的术语表中，不经意传输正是这类协议的构件之一）。缺少这一环时，横向联邦的隐私边界实际由**协调方的运营规范**兜底，而不是由机制兜底——这又回到了 3.2.3 所批评的那一类失效。

#### 3.2.2 纵向联邦学习（Vertical FL）

- **被什么约束逼出来**：各方的**样本（用户）重叠**、特征互补，任何一方都不掌握完整特征集；同时不允许交换各自的样本 ID 名单。
- **结构**：

```text
纵向联邦：样本对齐 + 特征分拆，中间量以加密 / 份额形式交换
  机构 A（特征子集 A，含标签）        机构 B（特征子集 B）
        │                                   │
   ① 隐私集合求交（PSI）───── 只得到交集，不暴露各自独有样本 ─────
        │                                   │
   ② 各自持有交集样本上的一部分特征
        │                                   │
        └── 加密梯度 / 加密分裂点统计 ⇄ ────┘
                        │
                   联合模型（双方各持自己可用的部分）
  明文位置：始终在本方；跨域流动的是密文中间量
```

- **为什么这样设计有效**：因为样本对齐用隐私集合求交，只输出交集本身、不输出各自的独有样本，所以「找共同客户」这一步不额外泄露任何一方的用户名单——这一步最容易被忽略，却是整条链路上最先泄露的地方；训练侧把特征按持有方切分，中间量以同态加密或秘密分享形式交换，任何一方都拿不到对方的特征值。
- **代价**：每轮迭代都要做加密与跨机构通信，且**非线性运算在密文下极贵**——树模型要在密文上找分裂点，需用分位点 / 近似方法把比较次数压下来（SecureBoost 一类算法存在的理由就是这个）；此外交集的任何变化都会改变训练样本集，协作双方必须能接受样本面随对方数据变动。
- **失效点**：当样本交集小、特征增量也有限时，「特征互补」的收益会反转成「交集 + 通信 + 加密三项成本之和超过增益」——因为标签方本可以用自己的数据训练一个不差的基线，纵向联邦的净收益只在交集规模与特征增量都足够大时才成立；判断这一点只能靠在**自己的数据上做明文基线对照**。
- **真实使用**：微众银行 FATE（2018 起）【经验，本章 [§6](08-privacy-computing-section-6-sec6.md) 整理的材料自述】；蚂蚁摩斯（2019 起）【经验，同上】。算法侧本章 [§2.3](08-privacy-computing.md) 列出 SecureBoost 与纵向联邦逻辑回归；工程侧 SecretFlow 提供纵向拆分能力【公开，FATE 与 SecretFlow 的正式版本以各自官方发布页为准】。判定方法：要一组「交集规模 + 特征增量 + 相对明文基线的效果差」的对照数。
- **与它相邻的一型（联邦迁移学习 FTL）**：当各方的样本与特征**都不同**时，横向与纵向都不适用，需要联邦迁移学习——它假定双方存在一个可共享的表示层（本章 [§1.1](08-privacy-computing.md) 的术语表给出 FTL 的位置）。判据很简单：**如果说不清"共享的是哪一层表示"，所谓联合训练实质上只是把两边的模型平均了一次**，效果不会超过各自单独训练。
- **样本对齐这一步不能省**：把两边名单直接比对再取交集，结果看起来一样，但**求交过程本身已经把双方各自的独有用户名单交给了对方**——后续所有加密训练都在保护一个已经被泄露干净的交集。判定方法：问对方"交集是怎么算出来的"，能给出协议出处与安全假设的才算过关。

#### 3.2.3 安全多方计算（MPC）

- **被什么约束逼出来**：任何一方都不接受自己的明文出现在别人机器上，且参与方之间**不完全互信**（不是"关系好所以不会越界"，而是"越界了也没人知道"）。
- **结构**：

```text
秘密分享：把明文拆成份额，少数份额拼不出原文
  明文 s  →  随机多项式 f(x) = s + a₁x + … + aₜxᵗ
              │
    ┌─────────┼─────────┬─────────┐
   f(1)      f(2)      f(3)  …   f(n)      ← n 份份额，分给 n 方
    │         │         │         │
   各方只持有自己的份额，任何 < t+1 份都还原不出 s
   计算在份额上进行（加法免费、乘法需交互），阈值达标才还原结果
  ─────────────────────────────────────────────────
  安全性的来源：数学假设（信息论或计算假设），不是运营方的自觉
  【Shamir, "How to Share a Secret", CACM 1979】（本章 §5.4 给核验入口）
```

- **为什么这样设计有效**：因为明文被拆成任务方无法独立还原的份额，所以「某一家被攻破」不构成泄露——安全性由**协议与数学假设**保证，而不是靠合同约束参与方。这一性质是它与其他路线最本质的区别：它是唯一不依赖"信任某一台机器或某一家机构"的路线。
- **代价**：计算与通信随参与方数量、电路深度增长，且常用运算的代价极不均衡——加乘便宜，比较、除法、非线性激活昂贵，于是每个具体任务都要被翻译成"对密文友好的电路"，这个翻译过程本身就是主要工作量。
- **失效点**：当计算类型需要大量比较或非线性运算、或查询频次很高时，「密码学保证」会反转成「不可用」——因为成本主要花在**通信轮数**上而不是算力上，跨机构网络的往返延迟决定单次计算的下限；另一个更隐蔽的失效是安全模型选错：半诚实模型下的协议面对恶意参与方并不成立，而这一点在验收时通常不会被问到。
- **真实使用**：安全两方计算的起点是姚期智的百万富翁问题【公开，Yao, "Protocols for Secure Computations", FOCS 1982】；门限秘密分享【公开，Shamir, "How to Share a Secret", CACM 1979；本章 [§5.4](08-privacy-computing-section-5-ai.md) 给出该条的可核验出处与对 §1.4 记法的校正】。本章 [§2.3](08-privacy-computing.md) 列出 SPDZ / ABY / ABY3 / Yao GC 等公开协议。Cape Privacy、Privitar 属平台类产品：**判断它们是否真的走 MPC，看其文档里有没有给出所用协议的出处与安全假设**，只看官网的场景口号说明不了问题。公开材料里缺的是带口径（参与方数 / 数据量 / 硬件 / 网络条件）的开销数字，这一档证据最实际的补法是自己造：把你们的参与方数、协议、开销比与精度损失按同一基线测一遍并留存口径。
- **协议族与它们各自的代价**（本章 [§2.3](08-privacy-computing.md)）：ABY 把布尔电路、算术电路与混淆电路混在同一次计算里，按"哪种表示更便宜就用哪种"来压成本；ABY3 把参与方压到三方，用复制秘密分享换掉高开销的大规模协议；SPDZ 提供更强的安全模型（含恶意参与方）但要为此付出更高开销；Yao 混淆电路适合布尔比较，但电路规模一大就不可行。所以选协议时真正要问的是三件事——**参与方有几种可能作恶、是否容忍参与方中途退出、需要支持哪些运算**：这三件事的答案不同，同一句「我们用 MPC」会指向完全不同的开销与保证。
- **两个基础构件决定了你要付哪种代价**：秘密分享把每个运算都拆成份额上的运算——加法几乎免费、乘法需要交互，于是**乘法深度（而不是数据量）成为成本的主导项**；不经意传输（OT）解决"一方在不暴露自己选择的前提下拿到另一方的一条数据"，它是多数两方协议的通信主体（本章 [§1.1](08-privacy-computing.md) 与 [§2.1](08-privacy-computing.md) 都把 OT 列为 MPC 的关键组件）。落到工程上就是一条比"MPC 慢"有用得多的判据：**能用加法与比较表达的统计任务在 MPC 上很便宜，凡是需要反复相乘或非线性函数的任务都会很贵**。
- **MPC 与 DP 的边界**：MPC 约束的是"计算过程中谁看到了什么"，它对"结果发布之后被推断到个体"没有任何约束；因此凡是把统计结果对外发布的场景，MPC 之外还要再叠一层 DP（3.2.5 的第 ④ 环）。把两者混为一谈，是"MPC 万能"这条反模式的另一种形态——技术上每一条都成立，合起来却不构成对个体的保护。

#### 3.2.4 可信执行环境（TEE）

- **被什么约束逼出来**：数据必须离开本方边界才能算（例如使用第三方的模型或算力），但又不接受运营方能看到明文。
- **结构**：

```text
TEE：明文只在硬件隔离区内出现，进出隔离区都是密文
  数据方 ──加密上传──► 宿主（云 / 运营方：看不到明文）
                          │
                     ┌────▼────────────────────────┐
                     │  Enclave（硬件隔离区）        │
                     │   · 解密并计算                │
                     │   · 内存加密                  │
                     └────┬────────────────────────┘
                          │ 加密结果
                     ┌────▼────────────────────────┐
                     │ 远程证明（Attestation）：     │
                     │  把"运行的是什么镜像 /       │
                     │   是否 debug 模式"交给远端校验│
                     └─────────────────────────────┘
  ─────────────────────────────────────────────────
  信任锚：芯片厂商 + 固件 + 证明服务（信任没消失，只是换了对象）
  关键问题：证明覆盖到哪一层？（镜像 / 启动配置 / 整机 / 加速器）
```

- **为什么这样设计有效**：因为明文只在隔离区内解密、且远程证明能把"运行的是什么"交给远端独立校验，信任从「运营方的承诺」换成「可被远端验证的硬件声明」——这是 TEE 相对其他路线唯一不可替代的地方：它让"运营方不可信"这件事在架构上可被检验，而不是靠合同。
- **代价**：信任没有消失只是换了对象（芯片厂商、固件、证明服务，任何一环的漏洞都直接落在你的数据上）；生态上很多负载在隔离区内跑不了——系统调用、部分算子、加速器覆盖不全，于是"能跑"的边界要逐个算子去确认；侧信道与瞬态执行类攻击面是被持续公开的【公开，例如 2018 年公开的 Foreshadow 一类针对 SGX 的瞬态执行攻击】。
- **失效点**：当把「隔离」直接当成「合规结论」时，隔离成立会反转成合规不成立——因为合规还要回答目的限定、留存期限、责任划分与可举证，而 TEE 只回答「谁能看到明文」；更实际的失效是**证明覆盖不到的那一层**（宿主 OS、编排、外挂加速器）被攻破或配置失当（例如证明里显示的是 debug 模式而没人看），此时"硬件隔离"这句话仍然成立，但它保护的东西已经不在了。
- **真实使用**：微软 Azure 的机密计算文档（Confidential VM 与 Attestation 章节）与 Google Cloud 的 Confidential VM 文档【公开，年份区间 2020–2021：这两条产品线的机密 VM 与远程证明文档在此前后成形、此后随版本持续更新，同章 [§5.4](08-privacy-computing-section-5-ai.md) 为同一口径，具体 GA 日期以页面标注为准】；NVIDIA 的 Confidential Computing 文档（H100 一类 GPU）【公开，年份 2024：本章 [§1.4](08-privacy-computing.md) 把 H100 CC 的商用记为 2024 年，文档条目按版本更新；看文档里有没有明确的算子与库支持清单，而不是"支持机密推理"这句概述】；Intel SGX 与 Occlum，以及阿里云等云厂商的 enclave 类产品，属同一路线的不同工程形态【经验】。判定方法：跑一次远程证明，看证明里能否读出镜像哈希与是否 debug 模式——读不出，隔离的边界就无法验证。
- **形态选择同样由约束决定**（本章 [§2.3](08-privacy-computing.md) 的对照）：进程级隔离（Intel SGX 一类）保护面最窄，代价是要改造代码去适配受限的运行环境；虚拟机级加密（AMD SEV-SNP 一类）迁移成本低，代价是保护边界扩到整机、攻击面同步变大；GPU 侧的机密计算（NVIDIA H100 CC 一类）是为模型推理准备的，代价是绑定单一厂商与受限的算子集。判断依据是**你的负载能不能被搬进隔离区**，而不是哪种方案"更安全"——搬不进去的方案，安全性无从谈起。
- **为什么 TEE 常被放在链路中间而不是两端**：它保护的是"计算那一刻的明文可见性"，因此最适合承担聚合、匹配、推理这类**单点收口**环节；把它放在数据入口（要求各方向隔离区集中数据）会同时放大出域范围与攻击面。3.4 的组合 C 把它放在聚合器位置，正是这个理由。

#### 3.2.5 混合方案（Hybrid）

- **被什么约束逼出来**：真实任务里没有一个环节能被单一路线同时满足——求交要精确（不能用近似）、训练要能收敛（FL 的天然优势）、聚合方不该看到明文（TEE 或 MPC）、发布统计要防成员推断（DP）。
- **结构**：

```text
混合：把链路拆成环节，每环节用最合适的技术（代价由最重的一环决定）
  ① 隐私集合求交（PSI）        精确、轻量、只输出交集
        │
  ② 联合训练（FL 纵向 / 横向）  复用明文训练的高收敛性
        │
  ③ 聚合器（TEE / MPC）        收口"谁都不能看到明文"
        │
  ④ 结果发布（DP）             挡住成员推断与差分攻击
        │
        ▼
     可交付结果
  ⚠ 整条链路的强度 = 其中最弱的一环
     每一环都要写清它的隐私假设，以及它假设了谁不可信
```

- **为什么这样设计有效**：因为链路被拆成若干环节、每环节各用最合适的技术，所以总代价由**最重的那一环**决定，而不是"最重的一环 × 环节数"——这是组合能优于"全程上最重方案"的机制（本章 [§2.2](08-privacy-computing.md) 的差分隐私 (ε, δ) 定义就是第 ④ 环可陈述性的依据）。
- **代价**：组合带来的直接成本是**工程复杂度**：密钥与凭证要在环节之间传递，审计要跨环节拼接，排障要在一组异构日志里对齐时间线；每新增一种技术就多一组要长期维护的参数（ε 与记账方式、参与方数与协议版本、证明策略），且这些参数不能各自独立调优。
- **失效点**：当链路上任一环节的隐私假设被违反时，「组合出的强保证」会反转成「最弱环节的保证」——因为组合的安全性不是叠加而是取最小值；最常见的具体形态是求交环节泄露了名单（或用了非 PSI 的直接比对），那么后面三环做得再严谨，链路整体的保证也已经归零。
- **真实使用**：【经验】本章 [§6](08-privacy-computing-section-6-sec6.md) 整理的蚂蚁摩斯 2019–2024 材料自述「多路线按场景选型 + 同一任务内组合（隐私求交 → 联邦训练 → 差分隐私发布）」；框架层面 FATE 与 SecretFlow 提供 FL 与 MPC / TEE 的组合能力【公开，正式版本以各项目官方发布页为准】，本章 [§7.3](08-privacy-computing-section-7-sec7.md) 给出组合清单。判定方法：让对方画出链路并逐环标注隐私假设，**只要有一环写的是"靠合同约束"，那一环就是整条链路的短板**。
- **统一记账是组合方案里最容易漏的一环**：链路上每一处加噪都在消耗同一份隐私预算，若各环节各自设定 ε 而不做跨环节累计记账，最终实际的 ε 会远大于任何一个环节声明的值。训练侧的可行做法由 DP-SGD 给出（Abadi 等，"Deep Learning with Differential Privacy", CCS 2016【公开】），端侧上报侧的工程形态见本章 [§5.4](08-privacy-computing-section-5-ai.md) 列出的三家公开部署——**判断一个混合方案是否可复核，就看它给的是"每环节一个 ε"还是"全链路一个累计 ε"**。
- **组合方案最容易退化成"技术堆砌"**：判断标准是每一环有没有独立的作用域与假设——如果拿掉某一环之后，方案的隐私保证会**明确变弱一个可陈述的量**，这一环才有意义；拿掉之后说不清损失了什么，就说明它只是被写进架构图的名词。
- **链路上各环的顺序不是随意的**：求交必须在最前（否则后续每一步都建立在已经泄露的名单上），加噪必须在最后（中间环节的计算会把噪声放大或抵消），隔离收口在聚合那一步（它保护的就是聚合瞬间的明文）。顺序错位时每一环单独看都仍然正确，合起来却不成立——这也是混合方案最容易被评审放过的地方。

五条路线放在同一张表里对比，差别全部落在「明文位置 / 信任锚 / 代价落点」这三列上：

| 模式 | 明文出现在哪里 | 信任锚 | 代价落在哪里 | 可陈述的参数 |
| --- | --- | --- | --- | --- |
| 横向 FL（3.2.1） | 各方本地 | 协议 + 参与方 + 协调方（需安全聚合） | 通信轮数、掉线容忍、非 IID 收敛 | ε（叠加 DP 后才有） |
| 纵向 FL（3.2.2） | 各方本地 | PSI 协议 + 加密中间量 | 交集规模、密文上的非线性运算 | ε + 协议安全假设 |
| MPC（3.2.3） | 从不出现 | 数学假设（信息论 / 计算假设） | 参与方数 × 乘法深度 × 网络 RTT | 协议出处 + 安全模型 |
| TEE（3.2.4） | 隔离区内 | 芯片厂商 + 固件 + 证明服务 | 算子覆盖、证明范围、侧信道攻击面 | 证明报告（覆盖到哪一层） |
| 混合（3.2.5） | 逐环节不同 | 各环节信任锚的合集 | 由最重的一环决定 | 全链路累计 ε + 各环节假设 |

这张表的用法有一个提醒：**"可陈述的参数"一列拿不出东西的方案，在技术评审里往往能过，在合规评审里过不了**——因为它回答不了"凭什么保证"。选型时可以先按前三列（明文位置 / 信任锚 / 代价落点）筛出候选，再用最后一列做淘汰。

### 3.3 模式选择决策表

| 约束组合（场景） | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 跨设备 AI 训练（特征同、样本多、设备不可信） | 横向 FL（3.2.1） | MPC 在大量弱设备上组织不起通信；TEE 的成本落在每一台设备上 | 是否有可靠的更新量聚合与掉线容忍机制 |
| 跨机构联合建模（样本重叠、特征互补） | 纵向 FL（3.2.2） | 横向 FL 需要特征相同，用不上；TEE 会让样本离域 | 样本交集规模与特征增量是否都够大（需明文基线对照） |
| 金融联合风控（要精确 + 强解释性） | 纵向 FL + MPC（3.2.2 + 3.2.3） | 只用 DP 会损失精度，风控阈值对精度敏感 | 能否给出协议出处与安全假设（半诚实还是恶意） |
| 医疗联合研究（敏感度极高，性能可让步） | TEE + MPC（3.2.4 + 3.2.3） | 只用 TEE 时信任锚落在硬件厂商；只用 MPC 时非线性运算不可承受 | 证明覆盖到哪一层；参与方数量是否 ≤ 3【经验】 |
| 政务数据共享（跨部门、必须留在本方） | TEE（3.2.4） | MPC 在多方跨部门组织下协调成本高；FL 需要能收敛的训练目标 | 部门是否接受"明文进隔离区"这一口径 |
| AI 训练数据稀缺（要扩大样本或特征） | 横向 / 纵向 FL + DP（3.2.1 / 3.2.2 + 3.2.5） | 只做 FL 没有可陈述的隐私参数；只做 DP 解决不了数据不够 | 能否给出 ε 与记账方式这一对值 |
| 机密 LLM 推理（保护用户输入与模型权重） | TEE（3.2.4） | MPC 的任意计算代价在推理规模上不可承受；FL 不是推理形态 | 算子与库在机密模式下的支持清单 |
| 结果发布 / 统计上报（防推断到个体） | DP（3.2.5 的发布环节） | 任何密码学路线都不保护"结果本身" | 隐私预算是否按用途分档并有记账 |
| 黑名单 / 客户名单求交（只要交集，不要分数） | MPC 的专用求交（PSI，3.2.3） | 上 FL 是过度设计——这里不需要模型，只需要一次集合运算 | 求交结果是否只输出交集，而不是两边的差集 |
| 跨机构对账 / 联合统计（要求精确计数） | MPC（3.2.3） | DP 的近似在这里不可接受；TEE 会额外引入硬件信任锚 | 是否必须精确值；参与方能否接受密文往返的延迟 |

**最常被误选的一对是「TEE」与「FL」**：两者都以「性能接近明文」著称，于是经常被并排放在选型表上按性能挑。但它们的约束完全不同——**FL 的前提是数据不出域，TEE 的前提是数据出域但不被看到**。误选的实际后果不是性能问题而是**方案作废**：在数据不能出域的行业里，把数据送进第三方 enclave 本身就构成一次"数据出域"的合规事件，无论结果是否加密返回；而真正该选的 FL（或 MPC）此时还没被评估。反向的误选同样常见：明明只是要让第三方算力帮忙做一次推理，却为了"不出域"去做 MPC，结果是推理延迟高到业务不可接受。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：横向 FL + 差分隐私（端侧与跨机构训练）**

- 各自承担什么：FL 决定**数据放置**（原始数据留在设备/机构），DP 决定**可陈述的隐私强度**（ε 与记账方式）。
- 运维代价：多了一层"预算记账"要维护——每个用途的 ε 要分档、要累计、要做效果回归；不记账的 DP 等于没有 DP。
- 适合规模：参与方数量多（设备量级）、模型规模中等、有稳定聚合通道的场景。
- 失效边界：当隐私预算被累计耗尽、或分档设得过松时，"数据放置"这一半保护仍然成立，而"个体不可识别"那一半会先失效——两组保护对象的失效时点不同，必须分开监控。

**组合 B：纵向 FL + MPC（跨机构联合建模与统计）**

- 各自承担什么：MPC 承担**样本对齐与密文统计**（求交、加总、交叉表），纵向 FL 承担**模型训练**（把加密代价限制在中间量交换上）。
- 运维代价：两套协议栈要同时运维，排查一个问题要在两套日志里对齐时间线；且双方都要能接受查询模式被对方统计到（哪怕只是密文）。
- 适合规模：两三家机构之间、交集规模可控、业务要求精确计数的场景（联合风控是典型）。
- 失效边界：交集之外的信息仍然会被对方观察到——交集的**规模**、查询的次数分布、每次参与的时间点，这些都不在"样本名单不泄露"的保护范围内；对"我们有多少客户与对方重叠"本身就敏感的场景，这一层要单独评估。

**组合 C：FL + DP + TEE（聚合器收口）**

- 各自承担什么：FL 承担训练组织，DP 承担梯度与结果的可陈述保护，TEE 承担聚合环节的明文收口（聚合方在隔离区内完成加权平均）。
- 运维代价：三层依赖各自的技术栈与版本，且 TEE 的证明要进运维流程；收益是把"聚合方必须被信任"这个假设从链路里去掉——**信任锚从"某一家机构"变成"可验证的硬件声明 + 可陈述的隐私参数"**。
- 适合规模：参与方少但敏感度极高（金融、医疗）、且无法接受"由某一家担任协调方"的场景。
- 失效边界：一旦证明覆盖不到的那一层被攻破，链路会退回"FL + DP 但聚合由某一方托管"的形态——组合带来的那部分收益随之消失，而三层架构的运维成本仍然要付。

三种组合的共同点是：**它们都在把"某一方必须被信任"这个假设从链路里逐步拿掉**。组合 A 拿掉的是"协调方看到每一方更新量"，组合 B 拿掉的是"对方看到我的样本名单"，组合 C 拿掉的是"协调方看到聚合前的明文"。反过来说，如果一个"组合方案"里没有任何一环在减少信任假设，那它大概率只是把几个技术名词并排放进了架构图，而协作的信任基础仍然是合同与关系。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 盲目上 FL | 方案里说不出数据分布情况，也没评估过单方基线 | 非 IID 下联合模型不如单方训练，投入换不来效果；且没有 ε 可供合规陈述 | 把"数据不动"当成了目标本身 | 先证明单方数据不够、再证明多方真的能提升（以明文基线为准） |
| FL 模型效果等同于明文 | 立项材料直接沿用集中式训练的预期指标 | 效果差距在验收期才暴露；差距幅度取决于非 IID 程度与参与方数量，事前无法假设为零 | 把"参与方更多"等同于"数据更多、效果更好" | 立项即写明"联合训练效果需相对明文基线实测"，并预留效果回归环节 |
| MPC 万能 | 所有场景都上最重的密码学方案 | 通信轮数主导成本，落地卡在延迟上；项目停在第 0 步 | 把"安全性最高"当成了唯一判据 | 先判场景对精度与可解释性的真实要求，再按计算类型选路线 |
| TEE 万能 | 把"部署在 enclave 里"写进合规结论 | 信任只是换成硬件厂商与固件；证明覆盖不到的层成为信任缺口；数据出域的口径问题未解决 | 把"隔离"读成了"合规通过" | 逐层核对证明覆盖范围，并把"明文是否出域"单独论证一次 |
| 忽视差分隐私 | 方案中出现"我们只交换梯度，所以是隐私的" | 梯度与更新量本身就是泄漏面（成员推断与梯度反演均已公开）；没有参数就无法向第三方陈述保证 | FL 的"数据不出域"被误读成"个体不可识别" | FL 默认叠加 DP，并把 ε 与记账方式作为交付物；参照 DP-SGD 的记账做法 |
| 忽视性能瓶颈 | 只在函数级 benchmark 上验证，没有端到端与网络条件实测 | 上线后延迟超预期；跨机构网络的往返延迟把单次计算的下限锁死 | 实验室环境与生产网络条件脱节 | 端到端压测并公开条件：数据量 / 参与方数 / 硬件 / 网络 |

**最危险的三条，生产中的典型暴露方式：**

「TEE 万能」不会以技术故障出现，它以**一份被写进合同的技术说明**出现：某方在协作协议里声称"数据在可信执行环境中处理，故不构成数据出境"。它的危险在于这个论断在技术上是真的、在合规上是错的——合规判定的是明文接触面与责任主体，而 enclave 的运营方仍然是另一个主体。修法不是换技术，而是在方案里把"明文出现在哪台机器、由谁运营、证明覆盖到哪一层"单独列一节。

「FL 模型效果等同于明文」的典型暴露方式是**验收期的指标落差**：上线前的预估照搬集中式训练的基线，实际联合训练的效果在某一方数据上明显回落。它的成因是这个反模式同时踩了两个机制——非 IID 导致的聚合偏差，以及缺少 DP 时用"数据不出域"顶替"个体不可识别"。修法是把它拆成两件事分别验证：效果相对明文基线的差距，以及 ε 与效果损失这一对数字。

「忽视差分隐私」的典型暴露方式最隐蔽：**系统在技术验收里全部通过**，因为每一环都按设计工作；问题出现在合规或安全评审的一句提问上——"你们的隐私预算是多少、记账怎么做的"。答不出来时，前面所有的工程投入都无法被陈述为一项隐私保证。这条反模式的成本不在系统里，而在**举证环节**。

六条反模式有一条共性，值得单独记住：**它们都在把"某个技术环节成立"当成"整套隐私保证成立"**——FL 成立的是数据放置，MPC 成立的是计算过程的密文性，TEE 成立的是隔离，DP 成立的是输出分布的可量化。而一条真实的隐私保证要同时回答四件事：保护对象是什么、对谁保护、保证的强度参数是多少、以及**这套机制在什么条件下失效**。四问里缺任何一问，方案就退回到"靠说明与合同"，而此时它在技术评审里仍然可能全票通过。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 2–3 方 → 10+ 方【经验】 | MPC（两三方协议） | 通信与协调随参与方数量增长，组织成本先于安全性成为瓶颈 | 横向 FL（加 DP） | 需要重构任务编排与聚合逻辑；精度与可陈述性要重新建立 |
| 单次比对 → 高频查询 | MPC | 单次成本乘上查询次数后不可接受，成本主要由通信轮数决定 | TEE（有隔离需求时）或本地 DP（只需统计口径时） | 信任锚改变，需重新做合规论证；证明与审计流程要重做 |
| 精确统计 → 任意计算 | MPC 专用协议 | 每新增一种运算都要新电路，非线性运算代价高 | TEE（通用运行时） | 算子覆盖要逐个确认；牺牲的是"不依赖硬件厂商"这一性质 |
| 中小模型 → 大模型训练 | 全参数 FL | 通信量按参数量 × 轮次 × 参与方数增长【推算：三项相乘，任一项放大都会线性推高总通信量】 | 参数高效微调 + 少量参与方，或改用 TEE 内的集中训练 | 需要重新论证可行参与方数量；效果与收敛性要重新测 |
| 内部协作 → 对外举证 | 技术方案（口头承诺） | 审查方要的是可复核的参数与证明，不是架构图 | 保留 ε 与记账、协议出处、证明报告与全流程审计记录 | 需要把参数与日志纳入交付物，运维流程要支持导出与复核 |
| 单方合规 → 跨域数据要素流通 | 单机构内的技术方案 | 参与方数量、责任划分与用途限定都变成多方协商项 | 协作任务化 + 平台托管身份与密钥 + 全流程审计 | 组织与法务成本高于技术成本，落地周期以季度计【经验】 |
| 精确计数 → 要发布分布 / 曲线 | MPC（精确统计） | 精确不构成保护：发布分布会把推断风险放大，而密码学路线对此无能为力 | MPC 负责算准 + DP 负责发布（3.2.5 的第 ④ 环） | 精度与 ε 必须一起调，并补一轮效果回归 |
| 参与方固定 → 参与方动态进出 | 三方协议（ABY3 一类） | 三方协议把参与方集合当作稳定前提，成员流动会直接破坏协调结构 | 需要容忍掉线与动态参与的联邦组织（横向 FL + DP） | 收敛性与精度要重新测，轮次同步机制要重建 |
| 数据留在机构内 → 计算要跨云跨区 | TEE（单集群内的隔离与证明） | 跨地域部署会让"数据驻留"要求与"集中计算"要求互相打架 | 就近部署隔离环境 + 处理位置前移（端侧或本区先处理） | 运维复杂度与网络成本上升，证明链路要跨区打通 |
| 联合模型上线 → 模型可被查询 | FL / MPC（保护训练过程） | 训练阶段保护好了不等于推理阶段安全：模型本身是泄漏面 | 推理侧加 TEE 或对输出做限流与加噪 | 是否做过成员推断评测（参照 IEEE S&P 2017 一类已公开攻击） |
| 少量样本 → 海量样本 | 纵向 FL | 交集内样本量增长会让密文统计的成本随样本数上升，而特征侧收益并不随之增长 | 横向 FL（按样本分流）或 MPC 只承担聚合统计 | 建模方式要重构，特征侧的收益要重新评估 |

判据是统一的：**当"多加一个参与方"或"多加一次查询"带来的边际成本开始超过它带来的边际收益时，就该换路线**——MPC 的边际成本在参与方数与乘法深度上，FL 的边际成本在参数量与轮次上，TEE 的边际成本在算子覆盖与证明范围上。这个拐点通常不体现在单次 benchmark 里，而是体现在**上线三个月后的排障工单构成**上【经验】：如果工单集中在"延迟超预期"与"某一方数据分布不同导致效果回落"，说明约束已经变了，而路线还停在原地。

### 3.7 自检清单

- [ ] 能否用一句话说清这次协作里**明文允许出现在哪台机器上**？说不清，选型就没有起点。
- [ ] 被保护对象是否写明（原始记录 / 模型 / 查询出口 / 统计发布），且评测过模型本身的泄漏面（成员推断、梯度反演）？训练阶段的保护不等于推理阶段的安全。
- [ ] 若涉及差分隐私：是否给出了 ε 与记账方式，且预算按**全链路累计**而不是每个环节各自声明一个 ε？
- [ ] 若采用 FL：是否有明文集中式训练的基线用于对比效果？没有基线，"效果损失可接受"无法验证。
- [ ] 若采用 MPC：能否说清参与方数量、协议族与安全模型（半诚实 / 恶意、诚实多数 / 不诚实多数），并确认协议覆盖了"参与方作恶"与"参与方掉线"中的哪一种？
- [ ] 若采用 MPC：是否按"数据量 / 参与方数 / 硬件 / 网络条件"四要素实测过端到端开销，并把它写进验收条款？
- [ ] 若采用 TEE：是否跑过远程证明，并能从证明里读出镜像哈希与是否 debug 模式？
- [ ] 若采用 TEE：加密能力覆盖到哪一层（镜像 / 启动配置 / 整机 / 加速器）？覆盖不到的层就是信任缺口。
- [ ] 若采用 TEE：是否单独论证过"明文进入隔离区"在这一行业是否构成数据出域？
- [ ] 若采用混合方案：链路上有没有哪一环的保证写的是"靠合同约束"？有，那一环就是短板。
- [ ] 求交环节是否使用了隐私集合求交？用直接比对交集等于泄露了双方的独有名单。
- [ ] 上线后是否有能力回答"这次协作用了哪些数据、按什么逻辑、产出了什么"？答不出来，审计与争议都无法收场。

### 3.8 小结

把 3.2 的五条路线、3.3 的判据与 3.5 的失效条件收在一起，得到的其实不是一张选型表，而是**一组必须同时成立的约束**：保护对象（原始记录 / 模型 / 查询出口 / 统计发布）、明文位置、参与方数量与互信、计算类型、可陈述的参数。任何一条约束被漏掉，选出来的路线都会在某一个环节上退回"靠合同兜底"。

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 特征同、样本不足、设备不可信 | 横向 FL（+DP） | 单轮通信量由参数量决定而非样本量，样本越多越划算 |
| 样本重叠、特征互补、名单不能换 | 纵向 FL（PSI + 加密中间量） | 交集本身不含各方独有样本，特征分拆使任何一方看不到对方特征值 |
| 明文不许出现在任何他人机器上 | MPC | 安全性来自数学假设而非运营方自觉，单点被攻破不构成泄露 |
| 数据必须出去算，但不能被看到 | TEE | 信任换成可远端验证的硬件声明，是唯一能检验"运营方不可信"的路线 |
| 只有部分环节有强约束 | 混合（PSI → FL → TEE/MPC → DP） | 总代价由最重的一环决定，不是最重的一环乘以环节数 |
| 要能对审查方逐条陈述 | 任何路线 + 保留参数与证明 | 回答不了"凭什么保证"的方案，在审查面前等同于没有方案 |

> 本节小结：决定路线选择的**唯一那条约束是「明文允许在哪台机器上出现过」**——它同时定下信任锚（数学假设 / 协议与参与方 / 硬件与证明）、代价落在哪里（通信轮数 / 通信与收敛 / 算子覆盖 / 效果损失）以及合规能否被陈述。判断路线选对了没有，也只需看一件事：**你能不能用一组可被第三方复核的参数，说清这套方案保护了什么、又没保护什么**。
