## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表最致命的动作不是打分，是**求和**。把 8 个方案放在「性能 / 安全性 / 易用性 / 生态 / AI 集成」五列上各打 1–5 分再加总，得到的数字要先经过两次无意义的运算：五列不是同一个量纲，「性能」的 5 分与「安全性」的 5 分不能相加；同一列在不同方案上量的还可能不是同一件事——进程级隔离方案那一行的「性能」量的是「明文进隔离区后能跑多快」，同态加密库那一行的「性能」量的是「密文上一次乘法要付多少代价」，两个数相减得不到任何东西。于是「21 分 vs 16 分」这类差别，无法被还原成任何一个真实约束下的结论。

即使不求和，逐列看也会被误导，因为**权重随场景反转**。同一个「安全性」列：在金融联合风控里决定成败的是能不能给出协议出处与安全模型（半诚实还是恶意）；在政务数据共享里决定成败的是「明文能不能不出本方边界」——后者根本不是安全性强弱问题，而是路线归属问题。同一个「性能」列也反转：跨设备联邦的瓶颈是通信轮数，机密推理的瓶颈是关键算子能不能搬进隔离区，两者与「快不快」都只有间接关系。

第三个问题更隐蔽：**打分表会把「不该放在同一张表上比较的东西」放在一起**。这张表里既有协议（MPC、联邦学习的聚合方式）、有框架（FATE、SecretFlow）、有库（Microsoft SEAL 这类同态加密库）、也有硬件与云服务（SGX、SEV、H100 CC、机密 VM）。协议与框架不是同一层的东西——协议决定保证，框架决定工程形态；库不构成一条完整路线，它只是路线里的一个构件。把它们并列打分，等于把「选路线」和「选实现」压成一次决策，而这两次决策的判据完全不同：选路线看明文位置，选实现看工程形态与你团队的既有技能。

本章的做法是：不做排序，只立判据。判据一旦立住，多数场景里「选哪个」会被**一条约束**直接决定，而不是靠加权。这条根约束来自 [§3.1](08-privacy-computing-section-3-sec3.md)：**明文允许在哪台机器上出现过**。它同时定下信任锚（数学假设 / 协议与参与方 / 硬件与证明）、代价落在哪里（通信轮数 / 收敛 / 算子覆盖 / 效果损失），以及合规能不能被陈述。选型因此分两步：先按**保护对象**分叉（原始记录 / 计算过程 / 结果发布 / 某类函数的可计算性），再用**可陈述性**淘汰。在这两步里，「4 分还是 3 分」没有位置。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 明文位置 | 明文会不会出现在他人机器上，出现在哪一台 | 它是根约束：定路线归属（本方 / 从不出现 / 隔离区内），并决定「数据出域」这个合规口径成不成立 |
| 信任锚 | 信任的是数学假设、参与方协议，还是芯片厂商与证明服务 | 信任对象不同，能被攻破的方式就不同；也决定了你需要哪种可复核的证明物 |
| 代价承重项 | 成本主要花在通信轮数、乘法深度、算子覆盖，还是效果损失上 | 承重项决定了「规模涨一倍会怎样」；承重项选错，性能预估会整体作废 |
| 参与方结构 | 几方、样本不同还是特征不同、能否容忍掉线与作恶 | 样本/特征结构决定走横向还是纵向；参与方数量与是否动态进出决定协议族是否可行 |
| 可陈述的参数 | 能不能给出 ε、协议出处与安全模型、证明报告 | 审查方要的是可被第三方复核的参数，不是架构图；给不出参数的方案过得了技术评审、过不了合规评审 |
| 合规口径 | 「明文进隔离区」在你这一行算不算数据出域 | 同一份技术方案在有的行业可用、在有的行业作废；这一条能一票否决最贵的方案 |

前三条是技术判据，后三条是工程与合规判据。把它们按顺序问下去，能筛掉的方案通常在一半以上【经验】。这些判据怎么分工，可以对照 [§3.3](08-privacy-computing-section-3-sec3.md) 那张十条场景的决策表看清：**「明文位置」直接把路线定死的只有政务共享一行**（该行的判据写作「部门是否接受『明文进隔离区』这一口径」）；其余各行的判据都落在族内更细的层次上——跨设备 AI 训练看「是否有可靠的更新量聚合与掉线容忍机制」，跨机构联合建模看「样本交集规模与特征增量是否都够大」，机密 LLM 推理看「算子与库在机密模式下的支持清单」，跨机构对账看「是否必须精确值；参与方能否接受密文往返的延迟」。换句话说，**明文位置负责分族，族内选哪条路线仍要逐条问后面的判据**——这正是 7.2 先分族、再在同族里比的原因。

### 7.2 候选方案全景

对比对象要先分清两类：**路线**（决定明文位置与信任锚）和**承载它的产品与库**（决定工程形态）。同一路线可以由不同产品承载，同一产品也可以承载几种路线——所以「某个平台是不是隐私计算」取决于它在你的链路里承担了哪一环、那一环的明文位置与信任假设是什么，而不取决于它的功能清单。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 横向联邦（FL） | 协作路线 | 样本分拆、只交换更新量，单轮通信量由参数量决定 | 端侧输入预测、跨机构扩样本 | 协议，无产品许可 |
| 纵向联邦（FL） | 协作路线 | 隐私集合求交对齐样本 + 特征分拆，中间量以密文/份额交换 | 金融联合风控、联合营销 | 协议，无产品许可 |
| MPC | 协作路线 | 明文从不出现，安全性来自数学假设而非运营方自觉 | 联合统计、隐私求交、跨机构对账 | 协议，无产品许可 |
| TEE | 协作路线 | 明文只在硬件隔离区内出现，信任锚换成可远端验证的硬件声明 | 机密推理、政务共享、聚合收口 | 依赖硬件与证明服务 |
| DP | 辅助机制 | 对输出加噪，(ε, δ) 可陈述 | 统计发布、端侧遥测、训练加固 | 机制，无产品许可 |
| HE | 辅助机制 | 密文上可计算，代价落在每次乘法之后的重线性化 | 小规模、以可加性统计为主的运算 | 机制，无产品许可 |
| PSI | 辅助机制 | 只输出交集，不输出各自的独有样本 | 黑名单 / 客户名单求交 | 协议，无产品许可 |
| **FATE** | 联邦框架 | 把跨机构联邦的学习任务编排成可复用算法组件 | 银行 / 保险风控、医疗联合建模 | Apache-2.0（以仓库 LICENSE 为准） |
| **SecretFlow** | 混合框架 | 同一编排下把 FL / MPC / TEE 分派到不同环节 | 跨机构联合建模与统计 | Apache-2.0（以仓库 LICENSE 为准） |
| **PySyft** | 联邦学习库 | Python 内构造虚拟参与方与联邦数据布局 | 研究、教学、原型 | Apache-2.0（以仓库 LICENSE 为准） |
| **FedML** | 联邦学习库 | 面向论文复现的跨设备 / 跨机构训练脚手架 | 高校、算法实验 | Apache-2.0（以仓库 LICENSE 为准） |
| **Intel SGX** | 进程级 TEE | 用户态进程级 enclave，保护面最窄 | 需改造代码以适配受限运行环境的负载 | 硬件 + SDK / 云服务 |
| **AMD SEV / SEV-SNP** | 虚拟机级 TEE | 整机内存加密，既有虚拟机可直接搬入 | 机密 VM、迁移成本敏感的负载 | 硬件 + 云服务 |
| **NVIDIA H100 CC** | GPU 侧 TEE | 把模型推理侧纳入机密计算 | 机密 LLM 推理 | 硬件 + 云服务 |
| **Occlum** | SGX LibOS | 在隔离区内提供系统调用兼容层，使既有应用不必重写 | 把既有服务搬进 SGX | Apache-2.0（以仓库 LICENSE 为准） |
| **Azure Confidential VM** | 托管 TEE | 云上机密 VM + 远程证明 | 托管机密推理、跨云协作 | 商业云服务 |
| **Microsoft SEAL** | HE 库 | 提供 BFV / CKKS 一类同态方案 | 研究与原型 | MIT（以仓库 LICENSE 为准） |
| 边界对照：直接比对名单 / 明文集中训练 | 无保护基线 | 无防护；作为其他一切方案的效果与成本基线 | — | — |

许可与模式一栏按各仓库与产品页的常见标注写；这类项目近年发生过更名、收购与许可调整，写进长期路线图之前，请以仓库 LICENSE 与官方公告的当前版本为准。

这些候选其实只分**四族**：① 协作路线（横向 FL / 纵向 FL / MPC / TEE）；② 辅助机制（DP / HE / PSI）；③ 协作框架（FATE / SecretFlow / PySyft / FedML）；④ 隔离与密码学底座（SGX / SEV-SNP / H100 CC / Occlum / Azure Confidential VM / Microsoft SEAL）。**跨族差异大于同族差异**：先分族（明文位置决定进哪族），再在同族里挑工程形态，能省掉一半比较——因为同族内部差别主要在「谁来做运维与举证」，而不是「能不能保护」。

§7.1 里那张打分表的五列（性能 / 安全性 / 易用性 / 生态 / AI 集成）在本章各有落点：**性能** → 7.3.2 的代价承重项与 7.4 的成本函数；**安全性** → 7.3.1 的明文位置与信任锚，以及 7.3.4 的可陈述参数；**易用性 / 生态** → 7.3.3 的框架定位与许可模式，以及 7.7 的团队再学习成本。而 **AI 集成**没有独立落点：判据里没有这一列，因为机密推理、联邦 LLM 训练、端侧 DP 这些 AI 场景改变的是**负载形态**，不改变任何一条路线的明文位置、信任锚或可陈述参数（本章 [§5](08-privacy-computing-section-5-ai.md) 的结论与此一致）。

### 7.3 机制差异：为什么它们表现不同（核心节）

四个机制维度，每个都只回答一件事：这条性质是被**哪个机制**逼出来的，以及它必然带来哪一笔代价。

#### 7.3.1 明文位置与信任锚：路线分岔的唯一根约束

**机制是什么**：一条路线能提供什么保证，取决于它的明文出现在哪里，以及它把信任寄托在什么上。前者决定它挡得住哪种泄露，后者决定它会被哪种方式攻破。

**它在各候选中的实现差异**：

| 路线 | 明文出现在哪里 | 信任锚 | 代价落点 |
| --- | --- | --- | --- |
| 横向 FL | 各方本地 | 协议 + 参与方 + 协调方（需安全聚合） | 通信轮数、掉线容忍、非 IID 收敛 |
| 纵向 FL | 各方本地 | PSI 协议 + 加密中间量 | 交集规模、密文上的非线性运算 |
| MPC | 从不出现 | 数学假设（信息论 / 计算假设） | 参与方数 × 乘法深度 × 网络往返 |
| TEE | 隔离区内 | 芯片厂商 + 固件 + 证明服务 | 算子覆盖、证明范围、侧信道攻击面 |
| DP | 不受限（保护的是输出分布） | 机制本身可陈述 | 精度与效果损失 |

**由此必然导出的性质**：因为横向联邦跨域流动的只有更新量，所以单轮通信量由**模型参数量**决定而不由样本量决定——样本越多、本地步数越多，通信相对计算越不占主导，这是它能在设备侧跑起来的机制；代价是收敛依赖参与方在轮次间不中途退出，且数据分布非 IID 时「按样本量加权平均」的落点不一定在任何一方自己的分布上，表现为联合模型在某一方数据上还不如只用自己数据训练。因为 MPC 的明文从不出现、安全性来自数学假设而非运营方自觉，所以「某一家被攻破」不构成泄露，这是所有路线里唯一不依赖「信任某台机器或某家机构」的一支；代价是成本由参与方数与乘法深度主导，跨机构网络的往返延迟直接锁死单次计算的下限。因为 TEE 的信任锚是硬件声明加远程证明，所以「运营方不可信」这件事第一次可以在架构上被检验而不是靠合同；代价是信任没有消失只是换了对象——芯片、固件、证明服务任何一环的漏洞都直接落在你的数据上，且证明覆盖不到的那一层既不能被证明也不能被否认。

**公开证据**：安全两方计算的起点是 Yao, "Protocols for Secure Computations", FOCS 1982【公开】；门限秘密分享的出处是 Shamir, "How to Share a Secret", CACM 1979【公开】（注意 [§1.4](08-privacy-computing.md) 把这条记为 1986 年，可核验的出处是 1979 年的论文）。针对 SGX 的瞬态执行类攻击在 2018 年前后被公开（Foreshadow 一类）【公开】，它印证的不是「TEE 不可用」，而是「信任锚换了对象」这句判断。各家机密计算产品的能力与版本，以 Azure Confidential Computing 文档的 Confidential VM / Attestation 章节、各家 Confidential VM 文档、NVIDIA Confidential Computing 文档的当前版本为准。

**失效条件**：当业务所在行业把「明文进第三方 enclave」算作一次数据出域时，选 TEE 就不是性能取舍而是**方案作废**——无论结果是否加密返回，[§3.3](08-privacy-computing-section-3-sec3.md) 末尾把这一对误选（TEE 与 FL）单独点出来，理由正在这里：FL 的前提是数据不出域，TEE 的前提是数据出域但不被看到，两者在选型表上都能写「性能接近明文」，约束却相反。

#### 7.3.2 代价的承重项：各条路线的承重项各自随什么增长

**机制是什么**：每条路线的成本函数里都有一个**主导项**，选型要看那个主导项会不会随你的规模增长——而不同路线的主导项是不同的变量。

**它在各候选中的实现差异**：

| 路线 | 主导项（成本由它决定） | 隐性成本（最容易漏算的一项） | 什么时候边际成本反超收益 |
| --- | --- | --- | --- |
| 横向 FL | 参数量 × 轮次 × 参与方数（通信） | 掉线容忍与重跑、非 IID 的效果回归 | 参与方数量上去而各方数据分布差异大时 |
| 纵向 FL | 交集规模 + 密文上的非线性运算 | 明文基线对照（不做出不来收益判断） | 交集小、特征增量有限时 |
| MPC | 参与方数 × 乘法深度 × 网络往返 | 把业务逻辑翻译成「对密文友好的电路」的人力 | 需要大量比较或非线性运算、或查询频次高时 |
| TEE | 把负载搬进隔离区的改造量 + 证明链路运维 | 逐算子确认覆盖的验证工时 | 关键算子在机密模式下不可用时 |
| HE | 乘法次数（每次乘法后要重线性化，密文会膨胀） | 参数选择与安全级别的复核成本 | 需要深层乘法或大模型推理时 |
| DP | 精度与效果损失 | 全链路累计记账与效果回归 | 业务要求精确计数时 |

**由此必然导出的性质**：因为 MPC 的成本由乘法深度与轮数（而不是数据量）主导，所以**能用加法与比较表达的统计任务在 MPC 上很便宜，凡是需要反复相乘或非线性激活的任务都会很贵**——代价是每新增一种运算都要先做一次「电路翻译」，这份人力通常超过算力成本本身。因为 TEE 的成本落在「把负载搬进隔离区」的改造量与证明链路运维上，所以「性能接近明文」这句话只在**算子覆盖到的那部分负载**上成立；代价是关键算子一旦不可用，整段链路就退回明文处理，而这类退化不会出现在函数级 benchmark 里，只会出现在上线后的验收里。因为 DP 的成本落在精度而不是算力上，所以它可以叠加在任何路线之上而不显著改变性能；代价是精确计数场景下 ε 再大也补不回精度，这也是允许量判定与加噪机制天然对立的地方。

**公开证据**：Gentry, "Fully Homomorphic Encryption Using Ideal Lattices", STOC 2009【公开】证明的是同态加密的**可行性**，不是**可用性**——它的成本结构（乘法后的噪声增长与重线性化）正是上面「乘法次数主导」那一条的来源。DP 的 (ε, δ) 形式化定义见 Dwork, McSherry, Nissim, Smith, "Calibrating Noise to Sensitivity in Private Data Analysis", TCC 2006【公开】；DP-SGD 与隐私预算记账见 Abadi et al., "Deep Learning with Differential Privacy", CCS 2016【公开】。协议族的成本差异（ABY 混合三种表示、ABY3 压到三方、SPDZ 面向更强的安全模型）见 [§2.3](08-privacy-computing.md) 的协议表，其判断方法是看协议对应的参与方数与安全模型，而不是看「MPC 快不快」的概述。

**失效条件**：用无条件的性能声称做决策。**判定方法**：只接受同时给出**数据量 / 参与方数 / 硬件 / 网络条件**四项的口径；缺一项的「接近明文」「可接受」只当方向记录，不当证据。此外当计算类型从「求交 / 统计」变成「任意计算」时，专用协议的优势会消失——每新增一种运算都要新电路，此时该换的是路线（[§3.6](08-privacy-computing-section-3-sec3.md) 的规模跃迁表把这一条列为一次跃迁）。

#### 7.3.3 协作框架之间：差异不在功能清单，在「哪一环由谁保证明文位置」

**机制是什么**：框架不改变路线，它决定**协作怎么被组织起来**——参与方身份与密钥怎么发、任务怎么编排、失败怎么重跑。因此比较框架要比「它在你的链路里承担哪一环、那一环的明文位置与信任假设落在谁身上」。

**它在各候选中的实现差异**：

| 框架 | 最擅长承担的那一环 | 它把明文放在哪里 | 不该指望它做的事 |
| --- | --- | --- | --- |
| FATE | 纵向 / 横向联邦的任务编排与可复用算法组件 | 明文始终在各方本地 | 替你回答「这一行能不能让明文进隔离区」 |
| SecretFlow | 在同一任务内把 FL / MPC / TEE 分派到不同环节 | 逐环节不同（密文 / 份额 / 隔离区） | 让组合自动变强——链路强度取最弱一环 |
| PySyft | 在 Python 里构造虚拟参与方与联邦数据布局 | 各参与方本地（多为模拟环境） | 直接替代生产级协作运行时（身份、重试、审计） |
| FedML | 跨设备 / 跨机构训练的实验脚手架与结果复现 | 各设备 / 机构本地 | 把「实验跑通」当成「跨机构网络下可按 SLA 跑」 |

**由此必然导出的性质**：因为 FATE 的算法组件以「拆分后的中间量交换」为默认形态，所以它把密文面压到梯度与分裂点这一层，换来「训练能收敛、精度接近明文」——代价是当交集规模与特征增量不足时，这项收益会被求交与加密成本吃掉，而判断这一点只能靠在**自己的数据上做明文基线对照**。因为 SecretFlow 允许多条路线共存于同一编排下，所以总代价由**最重的那一环**决定而不是「最重的一环 × 环节数」；代价是每新增一种技术就多一组要长期维护的参数（ε 与记账方式、参与方数与协议版本、证明策略），且这些参数**不能各自独立调优**——链路上每一处加噪都在消耗同一份预算。因为 PySyft 与 FedML 的定位在「把机制做成可实验的原语」，所以它们最擅长验证想法；代价是身份、密钥轮换、失败重跑、审计这些协作必备件不在它们的能力范围内，从实验到生产要补的正是这一层。

**公开证据**：【公开】FATE 的正式版本条目可回溯到 2019 年的 1.0，SecretFlow 自 2021 年开源起持续发布正式版本（判定入口是两个项目的官方 Releases 页；FATE 仓库 FederatedAI/FATE，SecretFlow 仓库 secretflow/secretflow；具体版本号与日期以页面上的条目为准）。【经验】「某框架更适合生产」这类判断在公开材料里大多为项目自述；判定方法是看**发布说明里有没有独立条目**，而不是看官网的功能介绍页。工具定位另见 [§4.3](08-privacy-computing-section-4-sec4.md) 的工具链表。

**失效条件**：功能清单不能推出信任假设。**判定方法**：让对方画出链路并逐环标注隐私假设——**只要有一环写的是「靠合同约束」，那一环就是整条链路的短板**；反过来，如果拿掉某一环之后说不清「隐私保证弱了哪个可陈述的量」，这一环就只是被写进架构图的名词。

#### 7.3.4 可陈述性：为什么「能给参数」的机制压过「分高」的机制

**机制是什么**：合规与审查需要的可复核物是一组**参数与证明**，而不同路线的可陈述物形态完全不同。它决定了方案能不能被第三方检验，也决定了「技术上没错」和「合规上能过」是不是同一件事。

**它在各候选中的实现差异**：

| 路线 | 可陈述的参数 | 拿不出来的后果 | 判定方法 |
| --- | --- | --- | --- |
| 横向 FL | ε + 记账方式（叠加 DP 后才有） | 只剩「数据不出域」这一句话，而梯度与更新量本身就是泄漏面 | 问「你们的 ε 是多少、记账怎么做的」 |
| 纵向 FL | ε + 所用 PSI 协议的出处与安全假设 | 说不清交集是怎么算出来的 | 问「交集是怎么算出来的」 |
| MPC | 协议出处 + 安全模型（半诚实 / 恶意、诚实多数 / 不诚实多数） | 半诚实协议面对恶意参与方并不成立，而验收时通常不会被问到 | 问「参与方能不能中途退出、作恶怎么处理」 |
| TEE | 证明报告（覆盖到镜像 / 启动配置 / 整机 / 加速器） | 隔离成立而合规不成立；证明里是 debug 模式而没人看 | 跑一次远程证明，看能否读出镜像哈希与是否 debug 模式 |
| HE | 方案名（BFV / BGV / CKKS 一类）+ 参数集与安全级别 | 密文参数无法被第三方复核 | 要它的参数集与安全级别 |
| DP | (ε, δ) + 记账方式（**全链路累计**） | 各环节各自声明 ε，实际总消耗远大于任何一个声明值 | 要求给「全链路累计 ε」而不是「每环节一个 ε」 |

**由此必然导出的性质**：因为密码学路线约束的是「计算过程中谁看到了什么」，它对「结果发布之后被推断到个体」没有任何约束，所以**凡是把统计结果对外发布的场景，在任何密码学路线之外都必须再叠一层 DP**——代价是链路上多一组要跨环节累计、跨用途分档、并随查询次数增长而耗尽的参数，而这份记账一旦缺位，前面所有工程投入都无法被陈述为一项隐私保证。因为 TEE 可陈述物的上限就是「证明覆盖到哪一层」，所以它的可复核性有一个明确的天花板——代价是覆盖不到的层（宿主 OS、编排、外挂加速器）成为信任缺口，而这个缺口在方案里往往写成一句「已启用机密计算」就被跳过了。

**公开证据**：(ε, δ) 的定义与「ε 越小保护越强」来自 TCC 2006 那篇论文【公开】；「只交换梯度不等于隐私」有两条公开反证——成员推断（Shokri et al., IEEE S&P 2017）与梯度反演（Zhu, Liu, Han, "Deep Leakage from Gradients", NeurIPS 2019）【公开】；端侧加噪后再上报的工程形态有三家彼此独立且有公开机制材料的部署（Apple, "Learning with Privacy at Scale", Apple Machine Learning Journal 2017；Google, "RAPPOR", CCS 2014；Microsoft, "Collecting Telemetry Data Privately", NeurIPS 2017）【公开】。**但这三条不能外推**：它们保护的都是统计上报量，不涉及模型训练与检索出口。

**失效条件**：参数齐备但按环节分别声明。最典型的形态是架构图上每一环都标了 ε、却没有累计口径——这时的实际 ε 远大于任何一个环节声明的值，而评审最容易放过它，因为每一环单独看都正确。

### 7.4 成本结构对比（不是价格表，是成本函数）

隐私计算的花费几乎没有一项是「按量付费」的算力，绝大多数落在人力、改造量与效果损失上。把各条路线的成本函数写成同一个形式：

```
总成本 ≈ 固定协作成本（身份 / 密钥 / 任务编排 / 审计）
        + f(参与方数, 轮次, 乘法深度)         ← 横向/纵向 FL、MPC 的主战场
        + g(搬进隔离区的改造量, 证明链路运维)  ← TEE 的主战场
        + h(把业务逻辑翻译成该技术友好的形态)  ← MPC 的电路、TEE 的算子、FL 的特征对齐
        + i(精度与效果损失)                    ← DP 的主战场
        + j(参数与证明的维护与举证)            ← ε 记账、协议出处、证明报告
```

各候选的主导项与隐性成本：**横向 FL** 的主导项是 f 里的「参数量 × 轮次 × 参与方数」，隐性成本是掉线容忍与非 IID 的效果回归；**纵向 FL** 的主导项是交集规模与密文上的非线性运算，隐性成本是必须做一份明文基线，否则无法判断净收益；**MPC** 的主导项是「参与方数 × 乘法深度 × 网络往返」，隐性成本是 h（电路翻译）；**TEE** 的主导项是 g，隐性成本是逐算子确认覆盖的验证工时；**HE** 的主导项是乘法次数，隐性成本是参数与安全级别的复核；**DP** 的主导项是 i，隐性成本是 j。一句话读法：**这套体系的账单里最贵的一项通常是 h 与 j，而它们最难被写进预算**。

**三项【推算】，推导链写全**：

- **DP 预算不因「摊到每天」而变少**。若某用途每次查询消耗 ε_d，按顺序组合的保守上界是**线性累计**，则 N 次查询后累计约 N × ε_d。代入 ε_d = 0.1、N = 30：累计 ≈ **3.0**。结论方向是：把同一个用途的预算拆成「每天一点点」并不降低总消耗，它只是把一次越界换成三十次小步越界；要压低总消耗只能减少查询次数、或用子采样/批处理把单次消耗摊薄。这条算例的作用是提醒：**ε 必须按全链路、跨用途累计并与查询频次一起规划**，否则预算是台账上的装饰。
- **横向联邦的协调侧通信量随参与方数线性上升**。设单轮同步量为 S（由参数量决定）、轮数为 R、参与方数为 K，则协调侧收发的对象总量量级 ≈ S × R × K。K 从 3 增到 30（一个量级）而 S、R 不变时，协调侧要处理的对象数量级同步上升。这正是 [§3.6](08-privacy-computing-section-3-sec3.md) 记的「2–3 方 → 10+ 方」那次跃迁的算术解释【经验】：参与方数量上去时，先崩的是协调与组织，而不是安全性。
- **MPC 的延迟下限由往返次数决定，而不是由数据量决定**。若任务需要 D 次串行乘法、每次乘法需要交互轮次 r，跨机构网络往返为 RTT，则单次计算的延迟下限 ≈ D × r × RTT（并行可乘的乘法可摊薄系数，串行部分不能）。代入一个自造的算例：D = 10、r = 2、RTT = 20 ms ⇒ 下限 ≈ 10 × 2 × 20 ms = **0.4 s**。跨机构 RTT 常见在十几到几十毫秒量级【经验】。这条推导链要说明的是：**MPC 的成本随电路深度走，不随数据量走**——所以「先把数据变小」在这里不解决问题，「把电路变浅」才解决。

**隐性成本往往才是最贵的一项**：把一条业务逻辑翻译成对密文友好的电路、把一份既有服务搬进隔离区、把两侧特征对齐成可联合训练的形态——这三件事都没有公开报价，也不随数据量增长，但它们决定了项目能不能交付【经验】。评审时的判据是：**这份方案里，谁是 h 和 j 的负责人、他们要投入多少时间**。答不上来的方案，成本估算通常是漏了这两项的。

**一个反直觉但很有用的推论：这套体系的成本对「数据量」最不敏感**。横向联邦的单轮通信量由参数量决定而非样本量，MPC 由电路深度而非数据量决定，TEE 由算子覆盖而非数据量决定，DP 由 ε 与查询次数决定——**这四条路线之外**，下表「数据量」一栏唯一标高的候选是 HE（密文膨胀与乘法次数）；纵向 FL 那一栏标「中」，是因为它随**交集内的样本规模**走，而不随各方自己的数据总量走。所以规模估算时该盯的是下表另外四行的变量，而不是数据量：**参与方数**（横向 FL 与 MPC 都随它增长）、**串行深度 / 轮次**（MPC 的延迟下限，HE 与横向 FL 也随它增长）、**查询频次**（MPC / HE / DP 都随它消耗，DP 消耗的是隐私预算）、**效果损失**（DP 的主导项，横向 FL 在非 IID 下也随它回退）。在评审材料里看到「数据量涨十倍所以成本涨十倍」这类线性外推时，先问它指的是哪一条路线：对横向 FL、MPC、TEE、DP 这四条，这个外推通常不成立。

| 成本对哪个变量敏感 | 横向 FL | 纵向 FL | MPC | TEE | HE | DP |
| --- | :---: | :---: | :---: | :---: | :---: | :---: |
| 数据量 | 低 | 中（交集内样本） | 低 | 低 | **高** | 低 |
| 参与方数 | **高** | 中（通常两三方） | **高** | 低 | 低 | 低 |
| 串行深度 / 轮次 | **高** | 高 | **高** | 低 | **高** | 低 |
| 查询频次 | 低 | 中 | **高** | 中 | 高 | **高**（消耗预算） |
| 效果损失 | 中（非 IID） | 中 | 低（精确） | 低 | 低 | **高** |

### 7.5 决策树（每个分支都要有阈值依据）

```
N1 明文允许出现在他人机器上吗？
├── 不允许 ──────────────────────────────────► N2
└── 允许，但运营方不得看到明文 ──────────────► N4

N2 协作目标与各方结构？
├── 只要集合运算（求交 / 精确计数，不要模型） ──► PSI 或 MPC 专用协议
├── 特征相同、样本不同 ──► 横向 FL（默认叠加 DP）
├── 样本重叠、特征互补 ──► 纵向 FL（PSI 对齐 + 加密中间量）
└── 两者都不同 ──────────► N3

N3 能否说清「共享的是哪一层表示」？
├── 能 ──► 联邦迁移学习（FTL）
└── 不能 ──► 退回单方基线：此刻的「联合训练」实质只是把两边模型平均一次

N4 负载能搬进隔离区吗（关键算子是否全部覆盖）？
├── 是 ──► TEE（并单独论证「明文进隔离区」是否构成数据出域）
└── 否 ──► MPC

N5 结果要对外发布吗？
├── 要 ──► 在已选路线之上叠加 DP（(ε, δ) + 全链路累计记账）
└── 不要 ──► 按已选路线交付

N6 参与方数量与流动性？（横向 FL / 三方协议的分界）
├── 2–3 方且参与方集合稳定 ──► MPC 或三方协议可行
└── 10+ 方，或参与方会动态进出 ──► 横向 FL 的组织形态

N7 需要向审查方逐条陈述吗？
├── 需要 ──► 把 ε 与记账、协议出处与安全模型、证明报告列为交付物
└── 不需要 ──► 仍建议留存：举证要求通常在上线后才出现
```

**阈值依据**（与树上节点一一对应）：

- **N1**：依据是 [§3.1](08-privacy-computing-section-3-sec3.md) 的根约束「明文允许在哪台机器上出现过」——它同时决定信任锚、代价落点与合规可陈述性，是唯一一条不需要其他信息就能分叉的判据。
- **N2**：第一条分支依据的是**计算类型**（专用协议的效率来自它在计算类型上做的假设：只要一次求交的任务上联邦学习是过度设计）；后三条依据的是样本与特征的分拆方式——横向联邦要求特征同、样本不同（此时跨域流动的只有更新量），纵向联邦要求样本重叠、特征互补（此时先要 PSI 对齐）。这是路线的定义性差异，不是强弱差异。
- **N3**：判据是**能否指出共享的是哪一层表示**。这不是数量阈值而是存在性阈值：说不清共享层时，所谓联合训练在机制上退化为参数平均，效果不会超过各自单独训练。
- **N4**：阈值不是覆盖率百分比，而是**「关键算子是否全部覆盖」**——因为一个关键算子不可用就让整段链路退回明文，而这个退化在整体覆盖率上可能只体现为很小的比例。判定方法是逐个算子确认覆盖（[§3.2.4](08-privacy-computing-section-3-sec3.md) 把「能跑的边界要逐个算子去确认」列为 TEE 的代价，[§3.6](08-privacy-computing-section-3-sec3.md) 的规模跃迁表也把「算子覆盖要逐个确认」写成换路线的代价），并按 [§3.7](08-privacy-computing-section-3-sec3.md) 的 TEE 自检项核完另一半——跑过远程证明、能从证明里读出镜像哈希与是否 debug 模式；只写「支持机密推理」这句概述不算证据。
- **N5**：依据是密码学路线的边界——它约束「计算过程中谁看到了什么」，对「结果本身泄露了什么」无能为力。因此任何对外发布的统计量都需要加噪环节，而这一环的可陈述物是 (ε, δ) 与记账方式。
- **N6**：依据是规模跃迁的成本拐点【经验】：MPC 的成本随参与方数与轮次增长，参与方多且集合不稳定时，协调与通信先于安全性成为瓶颈（三方协议把「参与方集合稳定」当作前提，成员流动会直接破坏协调结构）。这是从「10+ 方时组织成本先崩」这条经验推出的分界，不是从安全性推出的。
- **N7**：依据是可陈述性一条对方案的要求：审查方要的是参数与证明，不是架构图。它不改变技术路线，只改变交付物清单——**因此放在树的最末端，作为一道不淘汰路线、只淘汰说法的闸门**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 跨设备 AI 训练（特征同、样本多、设备不可信） | 横向 FL（+DP） | 端侧先处理 + 只上传统计量 | MPC 在大量弱设备上组织不起通信；TEE 的成本摊到每一台设备上 |
| 跨机构联合风控（样本重叠、特征互补、要精确） | 纵向 FL + MPC | 纵向 FL + TEE 收口 | 只用 DP 会损失精度，风控阈值对精度敏感 |
| 政务数据共享（跨部门、数据必须留在本方） | FL 或 MPC | TEE（需先通过「明文是否出域」这一关） | 只把「部署在隔离区」写进方案，不能替代合规论证 |
| 医疗联合研究（敏感度极高、性能可让步） | MPC + TEE | 纵向 FL（交集足够大时） | 只用 TEE 时信任锚全落在硬件厂商；只用 MPC 时非线性运算不可承受 |
| 机密 LLM 推理（保护用户输入与模型权重） | TEE（GPU 侧机密计算） | 端侧先处理 + 只回传结果 | MPC 的任意计算代价在推理规模上不可承受；FL 不是推理形态 |
| 结果发布 / 统计上报（防推断到个体） | DP | 任意路线 + DP | 任何密码学路线都不保护「结果本身」 |
| 黑名单 / 客户名单求交（只要交集） | PSI | MPC 通用协议 | 上 FL 是过度设计——这里不需要模型 |
| 跨机构对账 / 联合统计（要求精确计数） | MPC | TEE（可接受硬件信任锚时） | DP 的近似在这里不可接受 |

**四个常见组合**（前三个来自本章 §6 案例，第四个是求交→统计→发布链路的组合）：

- **组合 1：FATE + SecretFlow + Occlum**。职责边界：FATE 承担纵向 / 横向联邦的训练组织与算法组件（明文留在各方本地）；SecretFlow 承担同一任务里的密文统计与混合编排（求交、加总、交叉表）；Occlum 作为隔离区内的系统调用兼容层，把不便重写的既有服务搬进 SGX。运维代价：三套技术栈并存，排障要在一组异构日志里对齐时间线；且 Occlum 只解决「能不能跑」，不解决「证明覆盖到哪一层」——后者仍要单独确认。
- **组合 2：SecretFlow + NVIDIA H100 CC + Azure Confidential VM**。职责边界：SecretFlow 组织协作与求交；H100 CC 承担 GPU 侧的机密计算（模型推理这一段）；Azure Confidential VM 提供托管隔离与远程证明。运维代价：**信任锚同时落在三个不同主体上**（开源项目、硬件厂商、云服务商），证明链路要跨三层拼接，任何一层的能力变更都会改变整体保证。
- **组合 3：FL + DP + TEE（聚合器收口）**。职责边界：FL 承担训练组织，DP 承担梯度与结果的可陈述保护，TEE 承担聚合环节的明文收口（聚合方在隔离区内完成加权平均）。运维代价：三层各有自己的版本与参数，且 TEE 的证明要进运维流程；收益是把「聚合方必须被信任」这个假设从链路里拿掉——**信任锚从「某一家机构」变成「可验证的硬件声明 + 可陈述的隐私参数」**。
- **组合 4：PSI + MPC 统计 + DP 发布**。职责边界：PSI 只输出交集、不泄露各自独有名单；MPC 在份额上完成精确统计；DP 在发布环节加噪。运维代价：顺序不能颠倒——求交必须在最前（否则后续每一步都建立在已经泄露的名单上），加噪必须在最后（中间环节的计算会放大或抵消噪声）；且三环共用一份预算，ε 要跨环节累计。

四个组合的共同点是：**它们都在把「某一方必须被信任」这个假设从链路里逐步拿掉**。组合 1 拿掉的是「模型训练要交换原始特征」，组合 2 拿掉的是「算力提供方能看到推理明文」，组合 3 拿掉的是「协调方能看到聚合前的明文」，组合 4 拿掉的是「求交必须互示名单」。反过来说，如果一个「组合方案」里没有任何一环在减少信任假设，那它大概率只是把几个技术名词并排放进了架构图。

| 组合 | 它拿掉的信任假设 | 失效边界（哪一环先崩） | 运维代价落在谁身上 |
| --- | --- | --- | --- |
| 1：FATE + SecretFlow + Occlum | 「训练必须交换原始特征」「既有服务不能搬进隔离区」 | 求交环节（若用直接比对，后续三环的保护对象已不存在） | 平台团队；三套技术栈的版本与兼容性 |
| 2：SecretFlow + H100 CC + Azure Confidential VM | 「算力提供方能看到推理明文」 | 证明链路的某一层（跨三层拼接时，低层的能力变更会直接改写整体保证） | 云与硬件侧；证明策略要跟着厂商版本走 |
| 3：FL + DP + TEE 聚合器 | 「协调方能看到聚合前明文」 | 隐私预算（预算耗尽时「个体不可识别」这一半先失效，而「数据不离域」这一半仍成立） | 算法团队；ε 记账与效果回归要长期维护 |
| 4：PSI + MPC 统计 + DP 发布 | 「求交必须互示名单」 | 环节顺序（加噪若放在中间，后续计算会放大或抵消噪声） | 多方共同；跨机构日志要能对齐时间线 |

读这张表的方法与 7.3.3 一致：**看每一环能不能说出「拿掉它之后，隐私保证弱了哪个可陈述的量」**。说不出的一环，删除它反而让方案更清楚。

### 7.7 选错的代价与迁移成本

**反模式：把「部署在 enclave 里」当合规结论** —— 症状：协作协议或立项材料里写「数据在可信执行环境中处理，故不构成数据出境」。后果：这句话在技术上是真的、在合规上是错的——合规判定的是明文接触面与责任主体，而隔离区的运营方仍然是另一个主体；它在合同签署之后才暴露，此时改方案的代价是重谈协作范围。正确的做法：把「明文出现在哪台机器、由谁运营、证明覆盖到哪一层」单独列一节，并把「数据是否出域」当成一个独立的论证项，而不是由「已启用机密计算」推出。

**反模式：用直接比对代替隐私集合求交** —— 症状：双方把各自的 ID 名单交给对方取交集，结果看起来一样。后果：求交过程本身已经把双方各自的独有用户名单交给了对方，后续所有加密训练都在保护一个**已经被泄露干净的交集**；而且交集规模、查询次数、每次参与的时间点这些元信息也不在「名单不泄露」的保护范围内。正确的做法：求交走 PSI，并要一组「协议出处 + 安全假设」的说明；对「我们有多少客户与对方重叠」本身就敏感的场景，这一层要单独评估。

**反模式：每个环节各声明一个 ε** —— 症状：架构图上每一环都标了 ε，看起来处处有保护。后果：链路上每一处加噪都在消耗同一份预算，各环节各自设定而不做跨环节累计时，最终实际的 ε 远大于任何一个环节声明的值，而方案在技术评审里仍然可以全票通过——它的代价不在系统里，在举证环节。正确的做法：全链路累计记账，按用途分档，并把 ε 与效果损失作为一对数字交付。

**反模式：把「性能接近明文」外推到未覆盖的负载** —— 症状：立项材料直接沿用「TEE 性能接近明文」的预期。后果：上线后才发现关键算子在机密模式下不可用，要么退回明文处理（保护面归零），要么改模型结构（效果与工期一起变）。正确的做法：逐个算子确认覆盖清单，把覆盖不到的部分显式写进方案，而不是等验收时暴露。

| 从 → 到 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| FL → MPC | 无（样本不出域） | 有：把聚合逻辑翻译成密文友好的电路 | 有：新增多参与方协议栈与网络条件要求 | 高：协议族、安全模型、电路写法 |
| MPC → TEE | 有：明文要进隔离区，合规口径与责任主体同时变 | 中：关键算子要逐个确认覆盖 | 有：证明链路与镜像管理进运维流程 | 中：隔离环境与证明报告的读法 |
| TEE → FL | 有：数据要回到各方本地，特征要重新对齐 | 有：训练组织方式整体重写 | 中：聚合逻辑与掉线容忍 | 中：非 IID 与收敛调优 |
| 任一路线之上加 DP | 无 | 有：噪声注入点与记账要嵌进流程 | 低：新增预算记账与效果回归 | 中：ε、记账方式与效果损失的关系 |
| PSI 换成直接比对（反向） | 无 | 低 | 低 | 低——但这是用「举证能力归零」换工程量，属于净亏 |
| 实验框架 → 生产协作 | 无 | 有：实验脚本要改成任务编排与失败重试 | 有：身份、密钥轮换、审计全流程 | 高：跨机构协作的运维与法务 |

这张表的读法与前面一致：**技术更换本身通常不是最贵的，最贵的是合规口径与责任主体的重谈**。MPC → TEE 那一行的数据迁移量级看起来只是「搬数据」，实际要动的是一次数据出域的论证；这也解释了为什么路线一旦上线，迁移成本主要由组织与法务而不是工程决定【经验】。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 特征相同、样本不足、设备不可信 | 横向 FL（+DP） | 单轮通信量由参数量决定而非样本量，样本越多越划算 |
| 样本重叠、特征互补、名单不能换 | 纵向 FL（PSI + 加密中间量） | 交集不含各方独有样本，特征分拆使任何一方看不到对方特征值 |
| 明文不许出现在任何他人机器上 | MPC | 安全性来自数学假设而非运营方自觉，单点被攻破不构成泄露 |
| 数据必须出去算，但不能被看到 | TEE | 信任换成可远端验证的硬件声明，是唯一能检验「运营方不可信」的路线 |
| 数据连他人隔离区都不能进 | 横向 / 纵向 FL | TEE 在这个口径下等同于数据出域，方案会在合规环节作废 |
| 只要交集或精确计数 | PSI / MPC 专用协议 | 不需要模型，一次集合运算即可；上 FL 是过度设计 |
| 要把统计结果对外发布 | 任意路线 + DP | 密码学路线对「结果本身泄露了什么」没有任何约束 |
| 参与方 10+ 或会动态进出 | 横向 FL（+DP） | MPC 的协调与通信先于安全性成为瓶颈，成本随参与方数增长 |
| 要能对审查方逐条陈述 | 任意路线 + 保留参数与证明 | 回答不了「凭什么保证」的方案，在审查面前等同于没有方案 |

> 本节小结：本主题的对比里**唯一真正起决定作用的差异是「明文允许在哪台机器上出现过」**——它把候选劈成几族（明文留本方 / 从不出现 / 仅隔离区内出现 / 只保护输出），并同时定下信任锚、代价落点与合规口径；其余各列（性能、生态、易用性）只在同族内部用来挑工程形态。第二重要的差异是**可陈述性**：能不能给出一组可被第三方复核的参数（ε 与记账、协议出处与安全模型、证明覆盖范围），决定了方案是「一项隐私保证」还是「一段靠合同兜底的说明」。
>
> 判断任何一提法是否值得投入，只需问两句：**它的明文位置落在哪一环，它给出的可陈述物是什么**——答不上来的一律停在记录里。反过来说，凡是拿打分表上的总分、或拿「接近明文的性能」来论证的方案，都应该先被要求补齐那两项。
>
> 💡 **思考锚点**：拿你现有协作方案的每一环列一遍，对照 7.7 的四条反模式逐条打勾——"把部署在 enclave 里当合规结论""每个环节各声明一个 ε"这两条，你的材料里中了几条？再逐环追问"明文出现在哪台机器、由谁运营、证明覆盖到哪一层"——哪一环答不出这一问，它在你自己的账上到底是先补的那一环，还是先删的那一环？
