## 3. 设计模式与范式

> 原 § 3 共 80 行（5 个模式条目 + 1 张场景决策表；模式 1–4 各带一个箭头流程块，但无 DDL / 关系图式的结构示意、无机制解释、无失效分析），重写为 ~305 行模式手册：原 5 个模式与其代表工具全部保留，原 6 条陷阱全部保留并补齐「症状 → 后果 → 成因 → 修法」。

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把审计与合规讲成「按场景选一个」：大型企业选集中式，金融选不可篡改，多云选合规即代码。但真实的模式选择是被约束推着走的。审计体系真正的约束不在「要不要审计」，而在**审计日志是一种性质特殊的数据**：它被要求不可修改，同时又必须遵守「保留期一到就删」「用户要求删除就得删」；它由系统的调用行为产生，而不是由业务行为产生，所以体量随调用量增长而不是随业务量增长；它自身常常含敏感信息（访问日志里的 SQL 原文、LLM 审计里的 prompt），所以它自己就是被审计的对象。

**约束一：证据效力与可删除性是对立的。** 合规要求同时包含「保留 N 年」与「最小化 + 删除权」。这些年限本身是可查的：SOX 要求会计师的审计工作底稿保留 7 年（2002 年法案），HIPAA 安全规则要求相关文档保留 6 年，PCI DSS 要求日志至少保留 12 个月且其中最近 3 个月可即时调取，而 GDPR 不定具体年限、只要求「不超过必要期限」【公开】（依赖文本：SOX——Pub. L. 107-204（2002 年法案），其下会计师审计工作底稿的 7 年保留要求见该法案授权的 SEC 规则；HIPAA 安全规则——45 CFR Part 164，文档保留 6 年；PCI DSS——PCI SSC 标准现行版本要求项 10.5.1；GDPR——Regulation (EU) 2016/679 第 5(1)(e) 条存储限制原则。具体条号与版本以各文本原文为准，读者可自行核验）。因为一份物理上不可删除的日志无法履行删除请求，所以任何模式选择之前必须先回答：**你要长期保留的是原文，还是哈希与事件元数据？** 答错这一条，后面的防篡改投入全部作废。

**约束二：不可篡改与完整性是两件事。** 主文件 §2.2 把审计完整性定义为 $\text{Completeness} = |L_{\text{logged}}| / |L_{\text{actual}}|$。不可篡改只对分子起作用，对分母毫无贡献。因为大多数团队先被「日志被改」的风险吓到，所以最贵的机制往往被装在一份本来就不完整的样本上——这是本主题下最典型的资源错配。

**约束三：日志的体量由调用量和保留期共同决定，而这两项都不可谈判。** 把它量化，量级大致如下【推算】：

- 一个日均 1000 万次查询的中台，每条访问日志记录主体、资源、耗时、结果行数等约 500 B，则日增约 5 GB（10⁷ × 500 B = 5 × 10⁹ B）；保留 1 年约 1.8 TB，若按 HIPAA 那类 6 年期限的文档保留口径，则约 11 TB（5 GB × 365 × 6）。
- 若把 SQL 原文（平均约 2 KB）一并落库，单条记录涨到约 2.5 KB，日增从约 5 GB 升到约 25 GB，一年即约 9 TB——**这就是「只存指纹不存原文」的收益来源，而不是安全洁癖**。
- 若做成逐行留痕：一次扫描 1 亿行的查询，按每行 100 B 计，单条查询就产生约 10 GB 审计数据（10⁸ × 100 B）——**因此行级审计在物理上只能记录「访问了哪个对象、多少行」，不能记录行内容**。这不是设计偏好，是量级决定的。

**约束四：谁被审计，决定了权限怎么切。** 审计系统要防的第一类对象不是外部攻击者，而是持有平台高权限的内部角色。因为这套系统同时是「运维工具」和「监督工具」，所以它必须把「写日志的权限」与「删日志的权限」分开；这条约束不满足，3.2.2 的不可篡改就只是纸面承诺。

**约束一到约束四会互相打架，所以优先级必须显式排。** 可删除性与不可篡改冲突（约束一 vs 约束二），成本约束又与举证要求冲突（约束三 vs 约束一）。实践中的排序是：**先保证完整性（分母），再切分可删与不可删，最后才谈不可篡改与自动化**——反过来做，只会得到一份保护得很好、但并不完整的日志。

下面换一个角度看同一批约束：上面四条回答的是「谁和谁冲突」，表里六行回答的是「每条约束决定了哪个设计选择」。两者是两种切法，不是同一套分类，所以数目不同——不要拿「四条」去数这张表，反过来也一样。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态与写入模式 | 日志是「只追加、不回改」的事件流，因此写入侧可以便宜、读取侧要按调查方式设计 | 「审计库也要支持行级更新」——审计记录一旦可改，链条立刻失去举证价值 |
| 访问模式（点查 / 范围扫描 / 关联调查） | 真实查询几乎都是「某人在某时间段做了什么」，因此时间分区 + 主体索引是基本盘 | 「先建全文检索」——调查靠的是时间和主体，不是关键词 |
| 保留期与历史要求 | 保留期决定存储分层与删除通道，是本主题中唯一「不可优化」的成本 | 「保留越久越安全」——保留越久，暴露面与删除义务也越久 |
| 一致性 / 完整性要求 | 采集覆盖率、时钟与序列、至少一次投递决定证据能不能用 | 「接入了就等于采到了」——采样丢弃与字段缺失不会报警 |
| 规模与成本约束 | 决定何时必须分层、何时必须抽样、何时该只留证据子集 | 「全量全字段留 7 年」在多数规模下不成立，必须先算量级 |
| 团队技能与运维能力 | 决定能不能自建 WORM、规则引擎与持续监控，还是先用云厂商原生能力 | 「自研更可控」——审计是长周期低频次系统，自研的成本收不回来 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 集中式审计日志（Centralized Audit Log）

- **被什么约束逼出来**：审计要回答的是跨系统的关联问题（「这个人在三天内从五个系统里导出了什么」），而分散日志只能在单系统内回答。
- **结构**：

```text
数据源 1 → 日志采集 → 中央审计日志 → 分析 / 告警
数据源 2 → 日志采集 → 中央审计日志 → 合规报告
数据源 3 → 日志采集 → 中央审计日志 → 监管报送
         （采集端必须能落盘缓冲并至少一次重投）
```

```sql
CREATE TABLE audit_event (
  event_id      BIGSERIAL,
  ts            TIMESTAMPTZ NOT NULL,
  actor         TEXT        NOT NULL,   -- 谁
  actor_type    TEXT        NOT NULL,   -- 人 / 服务账号 / Agent
  action        TEXT        NOT NULL,   -- DDL / DML / READ / EXPORT / LLM_CALL
  resource      TEXT        NOT NULL,   -- 库.表 / 对象前缀 / 模型
  resource_cls  TEXT        NOT NULL,   -- 密级：公开 / 内部 / 秘密 / 机密
  purpose       TEXT,                   -- 访问用途（合规要能说明「为什么读」）
  source_system TEXT        NOT NULL,   -- 采集来源，用于算覆盖率
  sql_hash      BYTEA,                  -- 只留指纹，不留原文
  sql_shape     TEXT,                   -- 归一化模板，用于按模式聚合
  rows_affected BIGINT,
  outcome       TEXT        NOT NULL,   -- OK / DENIED / ERROR
  session_id    TEXT,
  src_ip        INET
) PARTITION BY RANGE (ts);             -- 保留期 = 分区生命周期
```

- **为什么这样设计有效**：因为所有来源被强制成同一张 schema，跨系统的关联调查退化成一次带时间范围的聚合扫描；因为分区键就是时间、保留期就是「丢分区」，所以删数据是元数据操作而不是逐行删除——查询模式与保留策略同构，这是它能在长保留期下活下来的原因。
- **采集方式决定覆盖率的上限**（主文件 §2.3 的六类方法各有边界）：数据库审计插件只覆盖单库直连；应用埋点只覆盖自研系统；代理层只覆盖走代理的流量；引擎钩子（Hive Hook、Spark Listener）只覆盖该引擎；API 网关只覆盖接口调用；云厂商原生只覆盖本云资源。因为没有任何一种方法能覆盖全部路径，所以集中式的真实覆盖率等于「各种采集方式的并集能被证明覆盖的比例」——这个并集必须被显式度量，否则它会在半年内静默下降。
- **代价**：① 中央成为可用性单点，采集端必须自带落盘缓冲与重投，否则「审计不中断」只能靠人工补；② 写入吞吐按「最忙系统的峰值 × 接入系统数」增长，容量被上游行为决定；③ 必须处理时钟偏移与事件序列，否则跨系统关联的顺序是错的；④ 每接一个新源都是一次改造，长尾系统往往永远接不进来，覆盖率长期停在主干系统上。
- **失效点**：当出现「受监管数据不得跨区汇聚 / 不得出境」的约束时，集中式的优点（全局关联）会直接反转成缺点（部署本身违法），因为把多法域日志汇到一处的那一刻就产生了跨境传输。此时正确解是**区域内集中 + 上层只汇聚合指标或哈希**，而不是把同一个中央集群做物理切分。
- **自验方法**：随机挑一个真实调查问题（例如「上周谁导出了客户名单」），要求在不写新代码的前提下 30 分钟内跑通「从问题到结论」；跑不通说明覆盖率或字段有问题，而不是查询技巧的问题。
- **真实使用**：这一模式在云端由 AWS CloudTrail、Azure Monitor、Google Cloud Audit Logs、阿里云操作审计（ActionTrail）与阿里云审计服务等托管服务提供；大数据生态用 Apache Ranger Audit，自建路线以 ELK Stack 为代表（[§4 工程实现](07-audit-and-compliance-section-4-sec4.md) §4.3「审计日志工具」还列出 Splunk）。此处只作产品形态归类，不引具体版本或配额——某个产品当前是否提供某项能力，以该产品官方文档的当前版本为准，读者可自行核验。多数企业的实际形态是「云厂商原生审计 + 自建中央日志」两层并存【经验】。

#### 3.2.2 不可篡改日志（Immutable Audit Log）

- **被什么约束逼出来**：审计证据的价值取决于「能不能证明没被改过」，而日志系统的高权限账号（DBA、平台管理员、云账号持有者）恰恰是最有能力改日志的人——约束来自「被审计者与被信任者重叠」。
- **结构**：

```text
第 n 条记录: (ts, actor, action, resource, prev_hash, rec_hash)
rec_hash_n = H(记录内容 ‖ rec_hash_{n-1})
链上任意一条被改写 → 其后所有哈希对不上 → 校验即可发现
锚定: 定期把链头发布到链外的不可变位置，否则整条链可被重算
```

```sql
-- 追加写入 + 哈希链：任何改写都会破坏链
CREATE TABLE audit_worm (
  seq       BIGINT PRIMARY KEY,  -- 单调递增、无空洞
  payload   JSONB  NOT NULL,
  prev_hash BYTEA  NOT NULL,
  rec_hash  BYTEA  NOT NULL      -- = H(payload ‖ prev_hash)；payload 即上文的「记录内容」
);
CREATE RULE no_update AS ON UPDATE TO audit_worm DO INSTEAD NOTHING;
CREATE RULE no_delete AS ON DELETE TO audit_worm DO INSTEAD NOTHING;
```

- **为什么这样设计有效**：因为验证只需要「重算哈希 + 比对链头锚点」，任何写入后的修改都会留下可检出的痕迹，不可篡改从一句承诺变成一次可执行的校验；而当把同一约束下沉到存储层（对象存储的写一次读多次模式），拒绝删除由存储组件执行，就不再依赖应用层的自觉。
- **锚定为什么是必需项而不是加分项**：哈希链的验证前提是「链头可信」。如果攻击者能改写全部数据，他也能重算整条链并给出自洽的哈希——此时链看起来完全正常。所以必须定期把链头写进攻击者改不到的地方（另一套权限域、外部存储或第三方时间戳），校验时比对锚点。没有锚定的哈希链，安全性约等于「普通表 + 一个校验函数」。
- **把不可变的成本算清楚，取舍就不难做**【推算】：沿用 3.1 的例子，日增 5 GB 的日志若全量进入不可变存储，6 年期的累积量约 11 TB，而且**这 11 TB 在保留期内不可删除、不可回收**。所以要覆盖的只是需要举证的子集——先统计一年内真正被用于举证的条目数，再据此定义证据区的口径。
- **代价**：① 写放大——每条记录多一次哈希计算与一次不可变对象写入；② **空间不可回收**，保留期内的存储成本是硬成本，压缩归档化解不了；③ 与删除权、最小化义务直接冲突，必须靠「加密后销毁密钥」或把可删内容放到链外来解决；④ 校验本身需要运维——链断了要能第一时间知道，否则「不可篡改」会静默退化为「没人验证过的普通表」。
- **失效点**：当删除义务（删除权、留存期限最小化）覆盖到链上内容时，不可篡改的优点反转成违法风险，因为物理不可删除意味着请求无法履行；反过来，当「全量不可变」的存储成本超过举证收益时，它退化成全量烧钱。因此不可变只应覆盖**证据区**（需要举证的少数事件），而不是全部运营日志。
- **自验方法**：取一条一年前的记录，从链头出发校验一次，看能否在不依赖「数据库自身完整性」的前提下证明它未被修改；这同时验证了锚点是否还在。
- **真实使用**：Amazon S3 Object Lock 的合规模式、阿里云 OSS 的 WORM 策略，以及 Qumulo 这类企业级存储提供的写一次读多次能力，都在存储层实现不可删除保留（产品形态归类，各产品提供哪种保留模式、有何限制，以其官方文档的当前版本为准，读者可自行核验）。原清单里的区块链方案另有其适用边界——它是多个互不信任主体共享审计记录的解法；单一企业内部的举证用哈希链 + WORM 即可达到同等效果，区块链在此处的增量价值需要具体论证【经验】。另需区分：表格式的 time travel 提供的是版本可回溯，不等于防篡改，两者常被混用【经验】。

#### 3.2.3 合规即代码（Compliance-as-Code）

- **被什么约束逼出来**：GDPR、个保法、HIPAA、PCI DSS、等保 2.0 的要求大量重叠（「最小化」出现在多个框架里），逐框架人工检查的维护面随框架数线性增长；而检查所需的输入（访问日志、配置、密级标注）本身已经是结构化的。
- **结构**：

```rego
package compliance.pii_access

# 一条控制项 = 一个可执行判断，而不是一段文档
deny[msg] {
  input.event.action == "READ"
  input.event.resource_cls == "机密"
  not input.grant.approved
  msg := sprintf("未授权访问机密资源 %s（事件 %s）",
                 [input.event.resource, input.event.event_id])
}
```

```text
监管条款             控制项目标              可执行判断              证据
GDPR 最小化      →  只允许必要字段被读取  →  deny[read_pii_no_need]  →  规则命中记录
个保法 告知同意   →  处理前必须存在同意    →  deny[no_consent]       →  同意流水
PCI DSS 日志保留 →  日志至少 12 个月可调取 →  retention_check        →  保留策略快照
等保 2.0 审计    →  审计记录不可中断      →  采集覆盖率 ≥ 阈值        →  覆盖率日报
```

（上表中 PCI DSS 的保留年限为该项标准的要求，条号与最新版本以标准原文为准【公开】。）

- **为什么这样设计有效**：因为把条款翻译成「对同一份事件流的判断」，一份规则可以同时服务事前门禁（拒绝）、事中告警、事后举证三个环节——框架数的增长只增加规则条目，不再增加检查流程与证据格式，这是「重复建设」在机制层面的解法。
- **规则库的最小可用形态由消费点决定**：事前门禁（申请、发布、权限授予）、事中告警（3.2.4）、事后举证（导出控制项与命中记录）三处消费同一份规则。因此最小形态不是「一个判定服务」，而是「规则 + 测试用例 + 框架映射表 + 版本」四件套；缺掉测试用例，规则库会在第二次修改时失去可信度。
- **代价**：① 规则成为代码资产，需要版本管理、评审、回滚与测试，否则改错一条等于全公司放行；② 判断引擎只管判断不管执行，落地要为每个消费点接执行钩子（网关、采集器、发布流程）；③ 一致性维护的责任从「人的记忆」转移到「规则库」，必须有人对规则正确性负责，而这个角色在多数团队里是空缺的。
- **失效点**：当规则没有测试、或误报率高于团队处理能力时，「自动化合规」的收益反转成「系统性放行」——门禁被批量豁免或被关闭，而这两条路径都不产生「规则已失效」的告警。判据是可算的：统计每条规则的命中量与其中被人工推翻的比例，被推翻比例高的规则会先被忽略，再被删除。
- **自验方法**：把当前合规检查表里的任一条控制项交给没参与建设的人，他能否只靠规则文件复现出同样的判断？不能，说明这条控制项仍停留在文档阶段。
- **真实使用**：判断引擎一侧的代表是 Open Policy Agent（OPA，CNCF 毕业项目）；控制项编排一侧是 Vanta、Drata、Tugboat Logic 与 Skyflow 这类自动化平台；国内对应形态包括阿里云合规审计类产品与自研合规中台（工具归类，不引具体版本：OPA 的毕业项目状态可在 CNCF 毕业项目列表中自行核验，各产品能力以其官方文档的当前版本为准；[§2 核心原理](07-audit-and-compliance.md) §2.3「合规检查方法」表与 [§4 工程实现](07-audit-and-compliance-section-4-sec4.md) §4.3 列的是同一批工具）。要区分两类工具：判断引擎解决「规则怎么写、怎么判」，合规 SaaS 解决「控制项怎么编目、证据怎么收」——它们不是同一个问题的解【经验】。

#### 3.2.4 持续合规监控（Continuous Compliance）

- **被什么约束逼出来**：第三方审计与等保测评是周期性抽样，而违规是连续发生的；抽样只能证明「抽样那个时刻合规」，无法回答「这一年里有没有违规」。要把结论从「抽样合规」升级为「持续合规」，检查就必须从周期任务变成对流式事件的判断。
- **结构**：

```text
采集（审计事件流） → 规则判断（有状态、带窗口） → 分级路由
                                          ├─ 立即告警：机密资源越权、大批量导出
                                          ├─ 工单：配置漂移、密级缺失
                                          └─ 合规台账：无告警但需留存
                                          ↘ 自动修复：回滚配置 / 收权 / 断会话
```

```yaml
# 控制项要写三件事：判断条件、发现时限、关闭时限
control: high_sensitivity_bulk_export
framework_map: [GDPR-Art32, PIPL, 等保2.0-安全审计]
detection:  { window: 5m, threshold: { rows: 100000 } }
sla:        { detect: 5m, ticket: 30m, auto_fix: revoke_session }
evidence:   { retention: 12mo, immutable: true }
```

- **为什么这样设计有效**：因为判断对象从「某个时点的快照」换成「事件流上的窗口」，发现延迟从「下一次审计」缩短到分钟级，同类事件在扩散前就能被拦住；同时每条控制项自动产出证据记录，审计准备从「临时凑材料」变成「导出既有台账」——这是持续监控相对周期审计的核心收益。
- **为什么必须监控「关闭率」**：这类系统的健康度不在规则条数，而在「告警从产生到关闭的时长分布」。因为告警是它唯一的产出，所以无法从系统内部判断它是否仍然准确；一旦某条规则的命中绝大部分以「已知问题」关闭，它就已经退化成噪声源。把它当作 SLA 指标而不是日志指标来维护，是这类系统的运维要点。
- **代价**：① 告警量随「规则数 × 流量」增长，必须有分级与去重，否则团队被淹没；② 有状态判断需要窗口与状态存储，成本与并发主体数相关；③ 自动修复是高风险写操作，必须有预演与回滚路径——误封一个正常账号造成的业务损失，可能大于它本想防住的风险。
- **失效点**：当告警量超过团队处理能力时，持续监控的优点反转成「告警疲劳」——团队开始批量忽略，实际响应率趋近于零。机制上，监控的产出是告警而不是结论，所以必须监控「告警的关闭率与误报率」这两个二阶指标；误报率升高而长期未被修的规则，会被无意识地忽略，此时系统看起来仍在运行，实际已经失效。
- **自验方法**：拉出近三个月告警的关闭时长分布；若中位时长明显大于设定的关闭时限，或大量告警以「已知问题」结单，这套监控已经在退化，而不是「运行正常」。
- **真实使用**：AWS Audit Manager 与阿里云合规中心类产品提供持续合规评估，Datadog 提供合规监控；字节跳动合规中台属自研形态，没有对外产品文档，这里只把「自研中台」当作一类形态列出，不对其能力作断言——两类形态的核验路径不同：托管产品的能力边界在官方文档里可逐项核验，自研中台的边界只能从其公开技术分享或岗位描述里间接推断【经验】。持续监控是否真的有效，取决于告警分级与关闭流程，而不取决于规则条数【经验】。

#### 3.2.5 AI 时代合规审计（AI Compliance Audit）

- **被什么约束逼出来**：LLM 与 Agent 把「谁做了什么」改写成「谁让模型做了什么」——一次对话可能触发跨系统的数据读取，而模型输出无法事后重算（同一个 prompt 在下一个模型版本上结果不同）。审计对象因此从「人对系统的操作」扩展到「模型调用 + 工具调用 + 训练数据来源」三类。
- **结构**：

```json
{
  "call_id": "c_...",
  "ts": "2026-10-18T09:00:00Z",
  "actor": {"user_id": "u_123", "agent_id": "support_agent_v3"},
  "model": {"name": "...", "version": "..."},
  "prompt_hash": "...", "prompt_redacted": "...",
  "retrieved_doc_ids": ["doc_9", "doc_17"],
  "tool_calls": [{"tool": "run_sql", "resource": "dw.orders", "rows": 42}],
  "output_hash": "...",
  "sensitive_findings": ["PII: phone"],
  "policy_result": "allowed_with_redaction"
}
```

```text
训练 / 检索侧                        推理侧                              事后
训练数据来源与版本（血缘）      →  LLM 调用留痕（prompt / 输出 / 上下文）→  模型版本审计
模型版本与评估报告              →  工具调用留痕（读了哪些库表 / 接口）    →  输出合规检查
```

- **为什么这样设计有效**：因为「检索到的文档 ID」与「工具实际读写的资源」被一起留痕，Agent 的每一次外部动作都能还原成一条可举证的链路；因为 prompt 与输出按「哈希 + 脱敏副本」双份留存，既保住了内容审计能力，又不把原始敏感文本复制进审计库——这两点让它能同时满足「可举证」与「最小化」。
- **留痕体量也要先算**【推算】：一个日均 10 万次调用的应用，若每条留痕（元数据 + 上下文摘要）约 4 KB，则日增约 400 MB（10⁵ × 4 KB），一年约 146 GB（400 MB × 365）；若连完整 prompt 与输出一起存（平均约 20 KB），日增约 2 GB，一年约 730 GB。**同一个系统，留痕口径差 5 倍，而这 5 倍里装的正是最敏感的内容。**
- **三类留痕的成本量级差别很大**：模型调用留痕（每次调用一条）随调用量增长；工具调用留痕（每次外部动作一条）条数通常少一些，但每条更敏感；训练数据来源留痕（每个模型版本一条）数量极少却要求最严格，因为它决定「这个模型能不能上」。三者的保留期应当分开设定——把训练数据留痕当调用留痕来管，会为几千条记录付出整套不可变存储的成本。
- **代价**：① 留痕体量与调用量成正比，且单条记录比传统访问日志大一到两个数量级（含上下文时）；② 审计库自身成为新的敏感数据集合，需要自己的密级、访问控制、保留期与删除通道，等于把 3.1 的约束又套了一遍；③ 模型升级后旧输出不可复现，审计结论只能建立在留痕之上，不能靠重放验证。
- **失效点**：当留痕直接保存原始 prompt 与输出时，审计系统会变成最强的敏感数据暴露面——因为它集中、长期、且被要求「谁都不能改」。同时它与删除权冲突：用户要求删除对话，而审计记录按定义不可删。修法是把「可删的原文区」（短保留、加密、密钥可销毁）与「不可删的哈希与事件区」物理分开，而不是在同一张表上做取舍。
- **自验方法**：任取一次 Agent 会话，看能否只靠审计记录还原出「读了哪些表、调了哪些接口、依据哪几份文档回答」；缺任何一环，它就不是证据链，只是一份日志。
- **真实使用**：Langfuse、LangSmith、Arize Phoenix、Helicone 提供 LLM 调用留痕与评估，阿里云通义安全一类产品提供面向 AI 场景的合规能力（工具归类，不引具体版本：某产品是否覆盖某类留痕，以其官方文档的当前版本为准，读者可自行核验；[§4 工程实现](07-audit-and-compliance-section-4-sec4.md) §4.3「AI 时代合规工具」列的是同一批工具的清单，不是这些工具能构成合规证据链的证明）；欧盟 AI Act 在 2024 年通过并分阶段适用，其中对高风险系统的记录留存提出要求【公开】（欧盟 AI Act，2024 年通过；具体条款与适用期以法规原文为准）。需要提醒的是：LLM 可观测性工具提供的是「留痕能力」，不等于「合规证据链」——证据链还要求留存策略、不可篡改与访问控制三件套【经验】。

**五个模式其实管的是同一条事件的不同段落**，把它们放在一起看，边界就清楚了：

```text
一条审计事件的一生
产生 → [3.2.1] 采集并统一 schema（保证完整性）
     → [3.2.2] 进证据区、算哈希并锚定（保证不可篡改）
     → [3.2.3] 用同一份规则判断是否允许（定义态）
     → [3.2.4] 命中即分级告警并产出证据（运行态）
     → [3.2.5] 若来自模型，连同工具调用与检索一起留痕（AI 扩展）
     → 保留期满：原文区销毁，哈希与台账按策略留存
```

任何一段缺失都不会报错，但都会在某个时刻让整条链失效——这正是 3.5 那些反模式能长期共存的原因。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 多系统、需要跨系统关联调查 | 3.2.1 集中式 | 不要先上不可篡改：日志还没采全，防篡改保护的是不完整样本 | 采集覆盖率能否被度量 |
| 强监管举证，且内部高权限账号需被约束 | 3.2.1 + 3.2.2（仅证据区） | 不做全量不可变：空间不可回收且与删除义务冲突 | 保留期内是否要求「可证明未被修改」 |
| 多法域（GDPR / 个保法 / 跨境经营） | 区域集中 + 上层只汇聚合或哈希 | 不用全球单点集中 | 是否会发生跨境传输 |
| 多云架构（多朵云混用） | 3.2.3 合规即代码 | 不按云各建一套合规：规则会在云之间漂移，同一事实两份结论 | 同一控制项是否需要在两朵云上得到同一个结论 |
| 多框架并行（如 GDPR + 等保 + SOC 2） | 3.2.3 合规即代码 | 不逐框架建检查流程 | 同一控制项是否被 ≥2 个框架要求 |
| 违规代价高，且要持续证明 | 3.2.4 持续监控 | 不只依赖周期性第三方审计 | 违规从发生到被发现的可容忍延迟 |
| 需按固定口径对外报送 | 集中式 + 报送证据同源（3.2.1） | 不用「事后人工导出报告」 | 报送口径能否映射到内部字段 |
| 要把审计与业务数据关联调查 | 集中式 + 目录 / 血缘联动（3.4 组合三） | 不把审计库当独立数据岛 | 资源标识能否与数据目录统一 |
| AI / LLM / Agent 应用 | 3.2.5 AI 合规审计 | 不只看传统访问日志 | 模型是否会产生对外部系统的动作 |
| 早期 0→1 | 3.2.1 + 云厂商原生审计 | 不自研 WORM 与规则引擎 | 是否已有明确的适用框架与举证场景 |

表后要单独说清**最常被误选的一对**：「不可篡改」与「集中式（完整性）」被当成了同一件事，而多数团队先建了前者。误选的后果在机制上是确定的——$\text{Completeness} = |L_{\text{logged}}| / |L_{\text{actual}}|$ 里，不可篡改只对分子起作用，对分母毫无贡献。生产中的暴露方式很典型：上线一年后遇到第一起需要举证的争议，发现要查的时段或系统根本没接入、或采样时被丢弃、或已过保留期，此时链条再完美也无法补救，因为缺失的记录无法补造。

第二对容易被混的是「持续监控」与「合规即代码」：前者是运行态，后者是定义态。只有规则没有监控，等于把条款写进代码后再无动作；只有监控没有规则，则每个消费点各写各的判断，口径必然漂移。正确顺序是**先立规则库（定义态），再让监控与门禁去消费它**——反过来先铺监控，后面会发现每加一个消费点就要重写一次判断。

### 3.4 组合模式：真实系统不会只用一种

**组合一：区域集中 + 分层保留 + 证据区 WORM。** 构成是「集中式采集（3.2.1）→ 热存（近 90 天可查）→ 归档层 → 证据区（不可变，仅覆盖需举证的少数事件）」。职责边界：集中式负责采全（完整性），分层负责把不可谈判的成本摊开，WORM 只保护需要举证的那一小部分，而不是全量日志。运维代价是两套存储加一条归档校验链路——归档后必须能证明归档内容与源一致，否则归档等于丢弃；分区生命周期与保留期策略绑定，改保留期是一次数据迁移而不是改一个参数。适合的规模：多法域或强监管企业、日志日增量在 TB 级以内【经验】；超过这个量级要先把「必须举证的子集」压缩到可管理的比例。**何时不该用**：日志量还很小、又没有明确举证场景时，分层只会多出两条链路，先用单一热存更划算。

**组合二：合规即代码 + 持续监控 + 变更门禁。** 构成是「规则库（3.2.3）作为唯一判断来源 → 持续监控（3.2.4）消费它做事中告警 → 发布与权限流程消费同一份规则做事前阻断」。职责边界：规则库只回答「是否允许」，监控负责发现，门禁负责阻止；三者共用一份规则，避免出现「告警口径」与「门禁口径」不一致这种最难查的问题。运维代价是规则改动必须测试与灰度（一条规则错误会被所有消费方同时放大），以及紧急豁免必须留痕并设自动到期，否则豁免会慢慢变成新的默认路径。适合的规模：适用框架数 ≥2 且变更频繁的组织【经验】；规则在数十条以内时收益来自口径统一，上百条后收益主要来自可回归测试。**何时不该用**：只有一个框架、且一年只被审一次时，把条款改写成可执行规则库的维护成本会高于收益。

**组合三：集中审计 + 数据目录与血缘联动 + 保留期最小化。** 构成是「审计事件带统一资源标识 → 关联数据目录的密级与 Owner → 血缘给出这次访问会流向哪些下游」。职责边界：审计回答「谁在何时做了什么」，目录与血缘回答「这件事涉及什么数据、影响什么」；两者冲突时以目录为准，审计记录不改写。运维代价是强依赖元数据质量——密级标注不全时审计结论直接失真；跨系统资源标识需要统一命名规范，否则关联率上不去。适合的规模：资产规模上千、需要回答「含 PII 的表被谁访问过」的组织。**何时不该用**：元数据本身还没立起来时，先补目录与密级标注，再谈审计与目录的联动。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 日志收集了没人看（数据墓地） | 有采集无查询量；近三个月没有任何调查或告警源于日志；存储账单在涨而平均响应时间不变 | 审计能力名义存在、实际为零，成本照付；事故发生时第一次查日志，才发现字段不全或链路不通 | 项目以「接入完成」为验收标准，没有以「能回答一个问题」为验收标准 | 每条日志（每组采集）必须绑定一个具体问题，并配查询入口与告警 |
| 合规靠人写 | 季度报告靠 Excel 拼；同一控制项不同审计员结论不同；报告里的数字无法回溯到数据源 | 证据不可复现，审计结论可被推翻；人力随框架数线性增长 | 先有报告模板后有数据，模板变成人工填充的容器 | 报告字段必须先有可执行判断与数据源，报告只做导出 |
| 日志可被篡改 | 平台管理员或云账号拥有删改日志的权限；日志存储无校验；备份可被覆盖 | 审计价值归零——争议中无法证明记录未被修改，而内部违规者正是最有权限改日志的人 | 日志系统与运维系统共用同一套高权限，权限没有按「谁被审计」切分 | 哈希链或 WORM + 权限分离（写日志的账号不能删日志）+ 链头外部锚定 |
| 多套合规重复建设 | GDPR 与个保法各建一套检查流程；同一份事实被要求以不同格式交两次 | 维护面随框架数增长，口径分歧导致同一事实得出两份结论 | 按框架立项而不是按控制项立项 | 以控制项为唯一单位 + 框架映射表（一条控制项对多个条款） |
| 忽视 AI 合规 | 模型已上线但无调用留痕；训练数据来源不可追溯；模型版本变更无记录 | 无法回答「这次输出用了哪些数据」；高风险 AI 的记录留存要求无法满足 | AI 功能以 POC 方式上线，未纳入既有审计采集流程 | 把模型调用与工具调用并入同一审计事件流，先于合规要求落地 |
| 合规流于形式 | 合规只出现在季度评审的 PPT 里；业务方不知道自己的操作会触发哪条控制 | 控制项只在上报时存在，实际行为无约束，抽查即暴露 | 合规目标被定为「通过审计」而不是「约束行为」 | 把控制项嵌进业务流程（申请、发布、导出入口），让不合规在操作时被拦 |
| 审计数据与业务数据分离 | 想查「哪些客户数据被导出过」要先跑审计库再手工关联业务库；两边 ID 体系不同 | 调查周期从小时级拉长到天级，多数调查不了了之 | 审计库为满足合规而建，独立于数据目录与主数据，未统一资源标识 | 审计事件的资源标识与数据目录统一命名，把目录与血缘当作审计的导航层 |

**最危险的三条，在生产中这样暴露。** 第一是「数据墓地」：它的危险在于**成本与风险不对称**——账单可测量、会走审批，而「查不出事」不可测量，直到出现第一起争议。识别方法很直接：统计日志查询接口的调用量，以及其中被真正用于结案的次数。第二是「日志可被篡改」：它的暴露方式几乎总是内部违规，因为外部攻击者拿不到平台高权限；而它暴露的时刻恰好是审计唯一被需要的时刻，所以这条反模式不会提前报错，只会一次性作废全部投入。第三是「忽视 AI 合规」：这是本主题下增长最快的风险面——传统审计按「人对系统的操作」建模，而 Agent 的动作由模型发起，落到哪个系统、读了哪些表取决于运行时，没有留痕就等于没有发生过。

**这些反模式会互相掩盖，这一点比单条反模式更值得警惕。** 「没人看日志」会掩盖「日志可被篡改」——因为没人查，篡改就不会暴露；「合规靠人写」会掩盖「多套合规重复建设」——人力在被消耗，重复建设只表现为持续加班；「忽视 AI 合规」会藏在「合规流于形式」之下——AI 功能根本还不在检查表里。因此诊断顺序应当反过来：先查「有没有被真正使用过的日志」，再查「它是否可信」，最后才查「覆盖了多少条款」。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单系统 → 10+ 系统 | 数据库审计插件直存 | 调查要跨库手工拼，关联查询无法用一次 SQL 完成 | 集中式 + 统一 schema + 时间分区 | 采集端要补时钟同步、事件序列与至少一次投递 |
| 日志日增 GB → TB | 集中式单一热存 | 成本随保留期线性上涨，而查询集中在最近一段时间 | 热存 + 归档 + 证据区三层 | 归档一致性校验；保留期变更变成数据迁移 |
| 单法域 → 多法域 | 全局单点集中 | 汇聚那一刻就构成跨境传输 | 区域集中 + 上层只汇聚合或哈希 | 必须先定义「哪些字段允许跨区汇总」 |
| 抽查 → 持续 | 周期性人工检查 | 抽查只能证明抽样时刻合规 | 规则化持续监控 + 门禁 | 规则库要建测试、版本与豁免到期机制 |
| 内部举证 → 对外监管报送 | 事后人工导出报告 | 报送口径与时点固定，人工整理既难按时也无法自证 | 报送数据与审计证据同源 + 签名 + 报送留痕 | 需把监管口径映射到内部字段并建校验规则 |
| 集中建设 → 多团队自治 | 中心团队统一改规则与流程 | 业务方改动要排队，规则与业务节奏脱节 | 规则库开放，域内自建监控，中心只保底线控制项 | 需要先定义「哪些控制项不可下放」 |
| 人工复核 → AI 辅助分级 | 人工逐条看告警 | 告警量超过团队处理能力 | 规则 + 模型分级（模型判断本身也留痕） | 模型判断不能是黑箱，必须可解释、可回退 |
| 单模型 → 多 Agent | 调用级留痕 | Agent 的外部动作跨系统、跨会话 | 会话级 + 工具级留痕 + 保留期最小化 | 留痕体量与敏感面同时放大，需先分区再放量 |

**跃迁的共同规律**：审计系统的成本与风险都随「保留期 × 数据量」增长，而任何一次跃迁都不会让保留期变短，所以化解动作集中在两种相反的操作上。**一是按新维度切开**，八次里有三次：日志日增 GB → TB 时拆成「热存 + 归档 + 证据区」三层、单法域 → 多法域时把全局单点换成「区域集中 + 上层只汇聚合或哈希」、集中建设 → 多团队自治时把中心只保底线控制项与域内自建规则分开——切开降低的是单点上的成本与耦合。**二是反过来把分开的东西收回同一份事实**，有两次：单系统 → 10+ 系统时把各库各自为政的记录收进「集中式 + 统一 schema」，内部举证 → 对外监管报送时把报送数据与审计证据做成同源——这两次方向相反，是因为要解决的问题不同：切开算的是成本账，收回消的是同源冲突（同一笔业务在两个库里各记一份、报出去两份对不上，靠分层解决不了）。剩下三次换的不是分合，而是判断的来源与粒度：抽查 → 持续把检查从周期任务换成事件流上的判断，人工复核 → AI 辅助分级把判断主体从人换成规则与模型（它的瓶颈不在存储而在人力，所以换的是判断主体而不是分区方式），单模型 → 多 Agent 把留痕粒度从调用级换成会话级加工具级。三加二加三，正好是表里的八次。

### 3.7 自检清单

- [ ] 是否给出过「采集覆盖率」的具体数字（分母怎么来的也说得清），而不是只说「已接入」？
- [ ] 想要长期保留的到底是原文，还是哈希与事件元数据？审计记录里是否含原始 prompt、SQL 原文或证件号？若含，保留期多久、谁能读、与不可删的证据区是否已物理分开？
- [ ] 写日志的账号，是否有权限修改或删除日志？若有，则「不可篡改」这一条不成立。
- [ ] 保留期策略是否与分区 / 生命周期绑定，改保留期能否在两小时内完成而不搬数据？
- [ ] 链头是否锚定在链外的不可变位置？不锚定的话，谁能重算整条链？
- [ ] 有没有一条日志能回答「谁导出过大表」或「谁看过机密表」这样的具体问题（而不是「有日志」）？
- [ ] 每条控制项是否映射到 ≥1 个监管条款，且最近一次合规检查结论能链接回它依据的原始证据（而不是只有结论本身）？
- [ ] 告警是否分级？近三个月告警的关闭率与误报率分别是多少？
- [ ] 紧急豁免是否自动到期？现存豁免清单有多长？
- [ ] LLM 与 Agent 的调用、检索到的文档与工具调用，是否已进入同一审计事件流？
- [ ] 监管报送（EAST / 1104 一类）的数据与审计证据是否同源？出现差异能否当天定位？
- [ ] 删除权请求的履行路径上，是否碰到过不可删除的日志？当时是怎么处理的？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 多系统、要能跨系统调查 | 集中式（3.2.1） | 关联问题的答案只存在于统一 schema 里 |
| 需向监管举证且涉内部高权限 | 集中式 + 证据区不可篡改（3.2.2） | 举证要求「可证明未被修改」，而非「存了很多」 |
| 多框架、多法域、多云并行 | 合规即代码（3.2.3）+ 区域集中 | 控制项是唯一单位，条款数不再放大检查流程 |
| 违规代价高、要持续证明 | 持续监控（3.2.4）+ 告警分级 | 发现延迟决定损失量级，而非规则条数 |
| AI / Agent 已上生产 | AI 合规审计（3.2.5） | 模型动作不走人工路径，没留痕等于没发生 |

> 本节小结：决定审计与合规模式选择的唯一那条约束，是**「这份记录要长期可举证，而它自身又必须被删除、被最小化、被保护」**——保留期与不可篡改性之间的张力无法消除，只能通过分层（证据区不可变、原文区可删）来分配。谁先想清楚这句话，谁就不会把预算花在全量 WORM 上。
