## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

合规题材的清单比别处更容易出错，因为它同时混着三种东西：**已经生效的法规**（既成事实）、**已经可用的工程能力**（工具）、**被反复谈论但还落不了地的做法**（趋势）。三者写成同一列，读者会误以为「法规提到了」等于「我已经有对应的技术手段」。本节对每个方向标注 L1 / L2 / L3，判据只有三条且必须**同时成立**才算 L1：

1. **已 GA 且有正式 release note**（能说出文档或版本页的名字，而不是「已经支持了」）；
2. **有第三方（非厂商）公开生产案例**（厂商自述的客户故事不算）；
3. **接口稳定**（可迁移、可替换，不随某一次模型或法规版本变化）。

只满足其中一两条的一律是 L2（可试点）或 L3（观望）。L1 不是形容词：核不到第②条就是 L2，本节不写「准 L1」这类放宽，**也不对本主题的 L1 判据做任何修正**。

本主题的分层方式与别处不同：审计与合规本来就是一套覆盖**「事前预防 → 事中监控 → 事后追溯 → 监管报送」**的体系（见主文件 §1.1）。AI 的落点不在其中某一段，而是同时改了四样东西——**审计对象**（从「人对系统的操作」扩展到「模型调用 + 工具调用 + 训练数据来源」）、**判定发生的位置**（RAG 场景下从「数据入口一处」变成「输入、检索、输出、存储四处」）、**被审计内容的性质**（从确定性操作变成不可复现的生成）、以及**合规判定的输入**（从「人的陈述与人工整理的材料」换成「系统可复算的输出」）。四样东西的成熟度不同，不能用一句「AI 让合规更智能」概括。

本节也不用「合规科技」「AI 治理」这类大词作为分类依据：一个方向归到哪一节，只看它的**判定输入**是什么——输入是系统可复算的输出，归 5.2.4；输入是模型与工具调用记录，归 5.2.1；输入是文本片段与向量，归 5.2.2；输入是生成文本，归 5.2.3。分类标准与成熟度判据分开写，才不会出现「同一件事在两个方向里各说一遍」。

还有一条读法必须写在前面：**合规题材的年份与状态最不能猜**。因此本节的做法是：凡涉及法规状态与版本，只写可核验的区间，并给出读者自己查的判定方法——在标准或法规的官方发布渠道里查编号与实施日期；凡涉及工具能力，只写「哪一类工具、以哪家官方文档的当前版本为准」；凡给不出第三方（非厂商）公开生产案例出处的方向，一律标 L2 而不是 L1。

本节全篇的数字与事实按三档标注：**【公开】**给出来源与年份；**【推算】**写出完整推导链，读者可以复算到同一个数；**【经验】**只给量级与区间。「核不到」不构成本节下调任何**事实**档位的依据，也不构成上调的依据——它只影响**成熟度评级**。

本节与 [§ 3 设计模式与范式](07-audit-and-compliance-section-3-sec3.md) 的分工是明确的：§3 的 3.2.1–3.2.5 讲五种模式（集中式日志 / 不可篡改 / 合规即代码 / 持续合规 / AI 时代合规审计）各自被什么约束逼出来；本节只回答一个问题——**这些方向里，哪些现在可以花钱，哪些只能记录**。两者判的不是同一件事：§3 判「这个模式在你的约束下值不值」，本节判「这个方向现在有没有可核验的生产依据」；一个模式完全可能在你这儿值得用，同时在整个行业里还没有一个可指出的生产案例。

本节也不复述 [§ 6 落地实践](07-audit-and-compliance-section-6-sec6.md) 里的四个案例（等保 2.0 对照整改、密级分级驱动权限与脱敏、多法域合规、金融级审计），只在需要指出「哪一条做法在工程上怎么落地」时引用它们。**它们都是本书内部材料，不构成 5.1 第②条要求的「第三方（非厂商）公开生产案例」**（见 5.4）。**案例提供的是做法，本节提供的是级别**，两者不要互相代替。

表里**没有任何一个方向**满足 L1 的三判据，卡点绝大多数落在第②条上：**合规即代码 + 持续合规**（含它依赖的不可篡改留存）是最接近的一条——工具都有公开 release notes，接口（版本化策略文件 + CI 集成 + 对象存储 API）也不随模型版本变化，但本节给不出具名的第三方（非厂商）公开生产案例出处，所以按规则只能是 L2，本节不为它放宽判据。LLM 行为审计、RAG 各环节控制同样卡在第②条；输出水印与输出追溯则是第③条不成立——它们的校验接口要下游配合，现在还没有稳定契约。

这恰恰是本主题最重要的一个结论：本节最不「AI」的那一条，反而是工程依据最扎实的一条。真正能改变合规判定方式的是**把要求变成可复算的控制项**，而不是任何模型能力；而无 L1 也不等于「别做」——它意味着这个方向现在应当以 PoC 与单点落地的方式推进，同时由读者自己去核验「厂商之外有没有具名的公开生产记录」，核到了再把级别提上来。

还有一处容易被误读：**「法规已生效」不等于「对应的技术方向是 L1」**。法规生效是事实，它带来的是**要求**；而某个技术方向能不能立刻上，取决于有没有可核验的生产做法与稳定接口。把这两件事混在一起，就会出现「因为 AI Act 实施了，所以我们该上 AI 合规审计」这类推导错误。

### 5.2 演进方向逐条拆解（核心节）

4 个方向在这里一个不少，只是被重新安放：留痕类进 5.2.1，RAG 链路上的控制进 5.2.2，输出侧进 5.2.3，而把「合规做成可复算的东西」这一族（合规即代码、持续合规、跨框架映射、RegTech）放进 5.2.4。每个方向都给出同样六行结构，外加**判定方法**与**失效的早期信号**两条读者可自查的东西。

| 本节方向 | 改的是哪一样 | 级别 |
| --- | --- | :---: |
| 5.2.1 LLM / Agent 行为与模型侧留痕 | 审计对象 | L2 |
| 5.2.2 RAG 链路上的合规控制 | 判定发生的位置 | L2 |
| 5.2.3 AI 输出合规：检测、水印与追溯 | 被审计内容的性质 | L3（检测部分 L2） |
| 5.2.4 合规即代码与持续合规 | 合规判定的输入 | L2 |

#### 5.2.1 LLM / Agent 行为与模型侧留痕：审计对象换了

- **旧做法与它的卡点**：传统审计记的是「谁在什么时间对哪张表做了什么」，三类日志（操作审计、访问审计、数据审计，见主文件 §1.1）都假设**操作是确定的、可重放的**。LLM 与 Agent 打破了这个假设：一次对话可能触发跨系统的多次数据读取，而模型输出**无法事后重算**——同一个 prompt 在下一个模型版本上结果不同。于是「重放验证」这条传统审计的兜底手段失效了。
- **AI 改变了什么机制**：审计对象从「人的操作」扩展为「模型调用 + 工具调用 + 训练数据来源」三类，记录单位从「一次操作」变成「一次调用」。留痕从「记发生了什么」变成「记下唯一能证明发生过什么的东西」。
- **由此得到的**：因为「检索到的文档 ID」与「工具实际读写的资源」被一起留痕，Agent 的每一次外部动作都能还原成一条可举证的链路；因为 prompt 与输出按「哈希 + 脱敏副本」双份留存，系统能同时满足「可举证」与「最少留存原始敏感文本」这两个互相拉扯的要求。
- **由此付出的**：
  - 留痕体量与调用量成正比，且单条记录比传统访问日志大一到两个数量级（含上下文时）【经验：量级】。**量级【推算】**（两个输入按【经验】假设：日均 10 万次调用、每条留痕约 4 KB（元数据 + 上下文摘要））：日增约 400 MB（10⁵ × 4 KB），一年约 146 GB（400 MB × 365 天）；若连完整 prompt 与输出一起存（均值约 20 KB），日增约 2 GB，一年约 730 GB——同一个系统留痕口径差 5 倍，而这 5 倍里装的正是最敏感的内容。把日均调用量与单条体积换成你自己系统的值，按同一式子即可复算；
  - 审计库自身成为组织内最集中、最长期、且被要求「谁都不能改」的敏感数据集合，等于把访问控制与保留期的约束又套了一遍；
  - 模型升级后旧输出不可复现，审计结论只能建立在留痕之上，不能靠重放验证——这削弱了传统审计里「用系统复算一遍」的说服力；
  - 留痕与删除权冲突：用户要求删除对话，而审计记录按定义不可删。修法是把「可删的原文区」（短保留、加密、密钥可销毁）与「不可删的哈希与事件区」**物理分开**，而不是在同一张表上做取舍。
- **证据与来源**：
  - Langfuse、LangSmith、Arize Phoenix、Helicone 提供 LLM 调用留痕与评估，能力以各自官方文档为准【经验：工具归类；某产品是否覆盖某类留痕，以其官方文档当前版本为准】；
  - 模型与数据披露有公开方法：Model Cards（Mitchell 等，FAT* 2019）与 Datasheets for Datasets（Gebru 等，CACM 2021）【公开】；
  - 欧盟 AI Act 于 2024 年通过并分阶段适用，其中对高风险系统的记录留存提出要求（具体条款与适用期以法规原文为准）【公开：欧盟 AI Act，2024】。
  - **本节未核到「LLM 行为留痕构成合规证据链」的非厂商公开生产案例**，故不标 L1。
- **与既有栈的接口**：留痕记录必须与访问控制使用**同一份**密级与权限定义（见 5.3），否则会出现「审计里说被拒、访问日志里说通过了」这种对不上的状态；留痕库自身也要有密级，否则它会成为一个新的越权读取入口。
- **成熟度**：**L2**。判据：留痕工具可用且已有正式发布，但字段与接口未稳，且核不到非厂商生产案例。
- **判定方法（读者可自查）**：① 任取一次 Agent 会话，看能否**只靠审计记录**还原出「读了哪些表、调了哪些接口、依据哪几份文档回答」——缺任何一环，它就不是证据链，只是一份日志；② 看留痕里有没有原始 prompt 明文（有，就说明最小化没做到）；③ 看「已删除文档的 ID」是否仍出现在检索留痕里（见 5.2.2）。
- **示意（一条留痕要能支撑举证）**：

```json
{
  "call_id": "c_...",
  "ts": "...",
  "actor": {"user_id": "u_123", "agent_id": "support_agent_v3", "source_ip": "..."},
  "model": {"name": "...", "version": "..."},
  "prompt_hash": "...", "prompt_redacted": "...",
  "retrieved_doc_ids": ["doc_9", "doc_17"],
  "tool_calls": [{"tool": "run_sql", "resource": "dw.orders", "rows": 42}],
  "tokens": {"in": 0, "out": 0},
  "output_hash": "...",
  "sensitive_findings": ["PII: phone"],
  "policy_result": "allowed_with_redaction"
}
```

- **失效的早期信号**：留痕只记「调用发生过」，不记「读了哪些资源」；审计库里出现原始 prompt 明文；或者团队把「留痕了」等同于「能举证了」——两者的差别是前者只有日志，后者能还原链路。

#### 5.2.2 RAG 链路上的合规控制：判定位置从一个变成四个

- **旧做法与它的卡点**：传统做法把合规卡在**数据入口**——入库时脱敏、赋密级、绑权限，之后数据在仓库内部流动时不再逐次判定。RAG 打破了这个前提：同一条数据会被切块、embedding 化、在检索时重新进入上下文，**权限结论必须在四个位置各自成立**，任一处缺失就是泄露。更麻烦的是一个新出现的失效形态：**数据在源系统已删除，但向量索引里还在**，检索仍能把已删数据召回进上下文。
- **AI 改变了什么机制**：判定位置从「一处（入口）」变成「四处（输入、检索、输出、存储）」，判定对象从「表与字段」变成「文本片段与向量」——后者没有天然的权限边界，必须由 metadata 显式携带。
- **由此得到的**：因为向量可以携带 metadata（密级、来源、所有者），RBAC 过滤可以在**检索时下推为过滤条件**，而不必把全部候选取回再筛——这既省算力，也避免了「取回之后再删」这种会在日志里留下痕迹的做法。
- **由此付出的**：
  - 四处各有一套策略，策略一旦漂移就会出现**看起来合规**的漏洞：入口允许、检索漏判、输出漏检，同一份数据可能被三处给出三种结论；
  - 删除权与索引的冲突成本会长期存在：删除请求要同时在源、索引、缓存、留痕四处生效，每多一处就多一个可能漏掉的地方；
  - 过滤下推会同时降低召回：被过滤掉的不只有「不允许看的」，也可能有「检索本来需要的」，质量与合规在这里是直接冲突的；
  - 输出侧检测本质是事后判定，误报与漏检同时存在，而漏检率通常没有可核验的公开口径。
- **证据与来源**：DLP、RBAC 与内容检测都是长期存在的通用技术，其能力以各产品官方文档为准【经验：本节未核原文】；向量库的 metadata filter 属各家文档可核验的能力，但接口不统一，实现前先查目标引擎文档【经验】。**本节未核到「四位置联动在非厂商生产环境中的公开案例」**，故不标 L1。
- **与既有栈的接口**：检索端过滤策略必须与源系统的权限系统**同源**（同一份定义、同一套发布流程），否则两边的结论迟早不一致；这条同源要求与 5.2.4 讲的策略库，实际上是同一个东西。
- **成熟度**：**L2**。判据：四处的能力都各自可用，但「联动」这一层没有稳定接口，也没有第三方生产案例。
- **判定方法（读者可自查）**：① 在源系统删除一条已入库文档，观察 RAG 是否仍能召回（能召回，说明删除联动没做）；② 用一个只有低密级权限的账号，问一个只有高密级文档才能回答的问题，看是否被拒**且被记录**；③ 把输出侧检测的拦截记录与人工复核记录对照，算出本团队自己的漏检率。
- **失效的早期信号**：合规检查只看「输出里有没有敏感词」就下结论；删除请求只处理源数据、不处理索引；四处策略由不同团队各自维护。

| 位置 | 判定对象 | 典型失效形态 | 现状 |
| --- | --- | --- | --- |
| 输入端 | 文档与字段 | 敏感数据未经扫描直接入库 | 成熟技术，先做 |
| 检索端 | 向量与 metadata | 过滤未下推，或策略与源系统不同源 | 能力可用，接口不统一 |
| 输出端 | 生成文本 | 漏检；申诉时说不清判定依据 | 事后判定，口径需自定 |
| 存储端 | 索引与留痕 | 源已删、索引仍召回 | 需要专门的删除联动 |

四个位置里，唯一不能只靠工程补齐的是**输出端**：它的输入是模型生成的结果，判定天然是事后的，因此它必须与审计留痕联动才能事后解释——这也是 §3 把「AI 时代合规审计」单独列成一个模式的原因。

#### 5.2.3 AI 输出合规：检测、水印与输出追溯

- **旧做法与它的卡点**：内容合规靠**发布前审核**（人审 + 关键词表），它的前提是「内容由人写、数量有限、发布前有停顿」。AI 输出把这三条同时推翻：内容即时生成、每用户一份、没有发布停顿点。同时，「这句话是从哪来的」在生成场景下没有天然答案——不能像传统审计那样指向一条操作记录。
- **AI 改变了什么机制**：检测从「字面命中」变成「分类判定」（统计判断替代字面匹配）；追溯从「记录来源」变成「把溯源信息嵌进内容本身」（水印或来源元数据）。**检测部分只是模型替换，不是架构变化**；追溯部分才是新增的接口与流程。
- **由此得到的**：因为分类器看语义而不是字面，改个说法绕不过去，对已知类别的变体更鲁棒；因为来源元数据随内容一起走，输出被转发之后仍可被检验——**前提是接收方也支持校验**。
- **由此付出的**：
  - 分类判定同时带来误报与漏检，且判定依据不可解释（「为什么这句被判违规」说不清），申诉与人工复核成本上升；
  - 水印有模态限制，且可被有损处理、重写或截断破坏；它证明的是「由某模型生成」，**不证明「内容合规」**，这是最常见的误用；
  - 输出追溯要下游平台配合校验，单方实现等于自证；
  - 这一层的成本与调用量成正比（每次调用都要过一次检测），在大流量下不是可忽略项。
- **证据与来源**：水印方案真实存在（如 Google 2023 年公布的 SynthID 一类，覆盖模态与强度以官方文档为准）【公开：厂商 2023 年公布；具体能力以官方文档为准】；内容来源元数据方向有 C2PA 一类联盟与规范（联盟 2021 年成立，规范自 2022 年起发布，版本以官方规范为准）【公开】。**核不到非厂商公开生产案例**，故不标 L1。
- **与既有栈的接口**：输出侧检测的结果要进**审计留痕**（见 5.2.1），否则事后无法回答「这条输出当时被判成什么」；而水印与来源元数据属于内容侧，不改变审计库结构。
- **成熟度**：**L3**（检测部分为 **L2**）。为什么一个方向里有两个级别：检测替换的是分类器，接口仍是「文本进、标签出」，因此它满足接口稳定但缺漏检率口径；而水印与追溯改变的是内容自身的形态与下游的接收方式，接口稳定性这一条不成立。
- **判定方法（读者可自查）**：① 取一段输出，看能不能判断它出自哪份上传文档——不能，就说明只有日志、没有追溯；② 把带水印的内容做一次常规编辑或重排，再检验是否还能识别；③ 抽查检测的误报是否有复核记录，以及漏检率有没有被度量过。

| 输出侧动作 | 判定对象 | 可核验的做法 | 现状 |
| --- | --- | --- | --- |
| 敏感词与分类检测 | 生成文本 | 记录误报与漏检，保留人工复核 | 可用，口径需自定 |
| 输出水印 | 内容内嵌信号 | 编辑 / 重排后复检 | 可被破坏，证明力有限 |
| 输出追溯 | 来源元数据 | 下游平台强制校验 | 依赖下游配合 |

- **失效的早期信号**：合规材料里写「输出已做合规评估」却不给漏检率；水印只在自家平台可校验；申诉时拿不出当时的判定记录。

#### 5.2.4 合规即代码与持续合规：把合规判定的输入换掉

- **旧做法与它的卡点**：合规靠**周期性人工审计**：一年一次、控制项写在文档里、证据靠人整理成册。它卡在三处：多框架并行时同一控制项被反复检查；AI 应用加入后，控制项清单里出现「模型版本、训练数据来源」这类新项，人工流程接不住；最根本的是**控制项与证据之间没有可复算的链路**——审计结论停在「某某确认过了」。
- **AI 改变了什么机制**：这一段的主力其实不是模型，而是**把控制项变成代码**：判定输入从「人的陈述与人工整理的材料」换成「系统可复算的输出」。模型在这里只做辅助——生成候选控制项映射、起草解释、总结差异；**判定仍由策略引擎给出**。分清这两者，才不会把「合规即代码」误当成 AI 能力。
- **由此得到的**：因为控制项是版本化文件、证据可由系统查询得到，**同一控制项在多个框架下的结论可以只算一次**（映射层）；因为结论可复算，审计从「看材料」变成「跑检查」——这正是持续合规能成立的原因。
- **由此付出的**：
  - 可自动化的边界只覆盖**技术控制项**；组织、培训、合同、治理结构类仍要人工取证，把「合规即代码」当成全覆盖会漏掉这一半；
  - 策略库本身成为需要审计的资产：谁改了策略、什么时候改的、谁批的，必须自己先有留痕；
  - 过度自动化会让组织失去「这条控制为什么存在」的理解，策略被抄来抄去，最后没人敢删；
  - 模型生成的映射建议必须人工复核，否则错误会稳定地写进策略库并长期生效——这是「生成物进入控制回路」的典型风险。
- **证据与来源**：
  - 策略引擎（如 Open Policy Agent 一类）以 CNCF 项目形式维护并有公开 release notes，可按项目仓库与基金会项目页核验其版本与采用者名单【经验：类目可核验，本节只给核验入口，不转述具体版本号与发布年份】；
  - 对象存储的不可变保留（对象锁一类）为云厂商 GA 能力，有公开 release note，核验入口是厂商文档的当前版本【经验：类目可核验】；
  - 可映射的公开框架：欧盟 AI Act（2024 年通过并分阶段适用）、NIST AI RMF 1.0（2023 年 1 月）、ISO/IEC 42001:2023，以及本章 §6 案例 7.1 所用的等保 2.0（GB/T 22239-2019，2019 年 12 月 1 日实施）【公开：各标准与法规的发布信息，可自行核验】。
  - **本方向的第三方（非厂商）公开生产案例本节给不出具名出处**（见 5.4），第②条不成立，故只标 L2。
- **与既有栈的接口**：策略引擎只做**判定**，不做阻断执行；阻断由访问控制与发布流程负责（见 5.3）。把两者揉在一起，会出现「策略写对了但没生效，或生效了却查不到依据」。
- **成熟度**：**L2**。判据：①③ 成立——策略引擎与对象锁都是 GA 能力、有公开 release notes 与版本页（核验入口见上行与 5.1 表），接口是版本化策略文件与 CI 集成、不随模型版本变化；② 不成立——本节给不出具名的第三方（非厂商）公开生产案例。按 5.1 的规则，②不成立就是 L2，本节不为它改写判据。
- **判定方法（读者可自查）**：① 任取一条控制项，看能否在不找人的情况下跑出一条带时间戳的结论；② 看同一控制项在两个框架下的结论是否来自**同一次检查**；③ 看策略库本身有没有版本与评审记录。
- **示意（合规结论要能复算，而不是能表述）**：

```text
控制项 → 检查 → 证据（可复算的链路）
  control_id    : 一条控制项（版本化文件，可追溯到框架条款）
  check         : 一条可执行的检查（查询 / 策略），有输入与判定标准
  evidence      : 一次检查的产物（结论 + 时间戳 + 输入快照 ID）
  framework_map : 同一 control_id 到多个框架条款的映射（多对多）
→ 关键：证据不是材料，是"这条检查在那一天跑出来的结果"
```

- **失效的早期信号**：合规结论仍然来自「某某确认过了」的表格；同一控制项在两个框架的检查里给出不同结论；策略库没有版本记录。

### 5.3 与本主题既有栈的接口在哪

「与 X 结合」没有信息量，因为结合点从来不是功能，而是**边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 数据血缘（[§ 5 血缘与影响面](../05-lineage-and-impact/05-lineage-and-impact.md)） | 训练数据来源追溯复用字段级血缘的溯源查询：输入是资产 ID，输出是来源链路 | 血缘过期导致溯源结论错，由数据平台负责，须同时暴露血缘新鲜度 | 训练集与检索集常不在血缘图内，需要先登记 |
| 数据安全（[§ 2 数据安全](../02-data-security/02-data-security.md)） | 密级与权限策略在访问路径上执行，审计只记录结果、不改判定 | 阻断失败由访问控制侧负责，审计不承担阻断职责 | 同一份策略被两处消费，须保证同源 |
| 可观测性（[§ 4 可观测性 §5 前沿演进](../04-observability/04-observability-section-5-ai.md)） | 观测留痕与审计证据**共用采集点、分级存储**：观测区可采样，证据区不可改 | 采样策略与不可删要求冲突，责任在架构设计而不是工具 | 未分开的团队先分开存储，再谈模型留痕 |
| 隐私计算（[§ 8 隐私计算](../08-privacy-computing/08-privacy-computing.md)） | 数据可用不可见时，审计对象变成「计算任务与输出」，而不是原始数据 | 输出合规检查落在输出侧，由调用方负责 | 需要单独登记任务、参与方与输出 |
| 监管报送（见 [§ 4 工程实现](07-audit-and-compliance-section-4-sec4.md) §4.2 监管报送链路） | 报送数据由 ETL 产出并校验；审计要覆盖**报送口径的变更** | 口径变更未留痕，会导致报送结论不可解释 | 报送链路的变更审计通常缺失 |
| 数仓与调度（见 [§ 4 工程实现](07-audit-and-compliance-section-4-sec4.md) §4.2 统一审计事件采集） | DB 审计插件、引擎 Hook、网关采集三选一或并用 | 缺采集点即盲区，由平台负责 | DDL 类有日志，脚本类常缺 |

这张表要说的是**同一件事在两边被消费时谁说了算**。最典型的是密级与权限：访问控制用它做阻断、审计用它做记录，一旦两份定义不同源，就会出现「审计记录显示允许、访问控制实际拒绝」这类无法解释的差异——而审计的价值恰恰建立在「记录与事实一致」上。

监管报送那一行值得展开：报送的确定性部分（ETL、校验、接口对接）早已是成熟工程，真正容易被漏掉的是**口径变更的留痕**——报表口径改了、历史数据重跑过，若没有记录，事后无法解释「为什么上月与这月的同一指标不同」。这类问题不是 AI 带来的，但 AI 生成报表解释会放大它：解释可以写得很自洽，而事实需要记录。

LLM 留痕与审计证据的关系也值得单独说一句：两者的**完整性要求不同**。可观测性留痕可以采样、可以过期；审计证据不能采样，且保留期由监管决定。把它们放在同一张表上，两边都会受委屈：采样策略会让证据区丢证据，证据区的不可删会让观测区无法按容量回收。**这不是 AI 带来的新问题，但 AI 把它放大了**，因为一次 LLM 调用留痕的体积比访问日志大一到两个数量级【经验：量级】，其绝对体量见 5.2.1 的推算。

上面六个结合点里，有三类失败会反复出现，且它们的共同点是**都不报错**：

| 失败形态 | 表面现象 | 谁会先发现 | 修法 |
| --- | --- | --- | --- |
| 策略不同源 | 审计说允许、访问控制说拒绝，两边都拿得出依据 | 事后复盘的人 | 策略库单一来源，且变更本身留痕 |
| 留痕口径混用 | 复盘还原不出完整链路，但日志看起来是全的 | 事后复盘的人 | 观测区与证据区物理分开，保留期分别设定 |
| 索引未联动删除 | 已删除的数据仍被检索召回进上下文 | 用户投诉或抽查 | 删除请求覆盖源、索引、缓存与留痕四处 |

- 这不是「这类案例不存在」的证据，而是本节不给任何方向标 L1 的理由——把它反过来读也成立：**读者不必相信本节的评级，可以自己推上去**。判据是：能否在厂商之外的公开材料（项目采用者名单、基金会或行业公开报告、监管公开文件）里查到**具名的**生产使用；查得到，该方向才有资格谈 L1。

**法规与进展的读法**

「某年某月某法规生效 / 某厂商发布某能力」的条目，本节不再逐条复述，因为这类条目最容易出现两种错：**把预告写成既成事实**、**把产品名当成能力名**。判断一条进展是否成立，用两条判定方法即可：**法规类**——能否在标准或法规的官方发布渠道查到编号与实施日期；**产品类**——能否在非厂商的材料里查到它的生产使用。举一个具体的例子：**「等保 3.0」**这一提法，判定方法是查官方标准发布渠道里有没有对应的标准号与实施日期；查不到，就按现行有效的等保 2.0 标准做对照，不要把「3.0 已实施」当成规划前提。

### 5.5 被过度宣传的部分

**「LLM 可观测性工具 = AI 合规证据链」**

- 实际是什么：这些工具提供的是**留痕能力**，不是证据链。证据链还要求留存策略、不可篡改与访问控制三件套。
- 为什么会这样：证据链的定义是「能被第三方复核」，而留痕只是「有记录」；可采样、可修改、可删除的记录在审计场景下不能算证据。
- 什么时候它才会成真：同一套留痕能同时给出「完整性可度量 + 不可篡改 + 按保留期销毁」三件事，且可删原文区与不可删哈希区在物理上分开。

**「AI 辅助生成合规报告能替代合规工作」**

- 实际是什么：它生成的是**文档**，不产生**证据**。
- 为什么会这样：报告的可信度来自逐条可核验的控制项结论；模型写出来的是通顺的文本，而通顺与真实无关——最坏的情况是报告写得比实际合规程度更好看。
- 什么时候它才会成真：报告里每一条结论都指向一条可复算的检查结果（查询语句 + 快照或时间戳），人只做复核与签署。

**「输出水印能解决 AI 输出追溯」**

- 实际是什么：水印只能部分回答「这段内容是不是由某模型生成的」，回答不了「内容是否合规」「依据了哪些数据」。
- 为什么会这样：水印是嵌在内容里的信号，会被编辑、重排、截断破坏；而且它证明的是**生成来源**，不是**内容责任**。
- 什么时候它才会成真：来源元数据成为内容流转流程的默认环节，且下游平台**强制校验**——只要校验还是可选的，它就只能自证。

三条合起来是同一个模式：**留痕不等于证据，生成不等于判定，嵌入不等于追溯**。合规题材里最贵的错误，是把「我们做了某件事」当成「我们能证明某件事」。

### 5.6 未来 3-5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 可自动化的边界稳定在技术控制项上，不向组织与流程类扩张 | 主流合规平台公开的控制项清单里，可自动化项集中在技术类，且三年内占比变化不大 | 非厂商审计机构开始接受全自动生成的组织类证据 |
| 模型与数据披露格式被至少一个法域以可执行形式引用 | 监管指引中出现对**具体披露字段**的要求（而不是原则性要求） | 三年后披露仍停留在自愿模板与厂商自述 |
| LLM 调用留痕分化为「观测区 + 证据区」两套存储 | 主流工具同时提供可采样的留痕与不可变证据导出，且两者保留期可分别配置 | 三年后主流方案仍只有单一保留策略 |
| 跨框架映射成为合规平台的默认数据模型 | 平台公开的数据模型里控制项与框架是**多对多**关系 | 仍按框架各建一套检查流程，映射靠人工维护 |

这四条预测的共同点是：**证伪信号都是「三年后还是老样子」**，而不是「出现了相反的技术」。写「AI 会让合规更高效」永远不会错，因为它没有可观测的证伪条件。上面第一、四条的成本最低——只要去读一份公开的控制项清单或数据模型，不需要等法规落地。四条预测的检验时点也应当先定下来，否则三年后没人记得当初承诺过什么：建议第一、四条每年对一次表，第二、三条按法规与工具的公开节奏每两年检查一次。**没有检验时点的预测，等于没有预测。**

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 尚未建立集中审计日志 | 先把采集覆盖率与保留期定下来，并用「覆盖率可度量」作为验收 | 证据区与观测区是否被分开 | 不要先上 LLM 行为审计：日志还没采全，模型留痕只是更贵的日志 |
| 已有集中审计日志、强监管 | 把控制项做成可复算的检查（合规即代码），保留期与不可篡改先落地 | 可自动化的边界到底在哪一类控制项 | 不要把 AI 生成的合规结论直接提交监管 |
| 已经在跑 LLM / RAG 应用 | 做调用与工具调用留痕（含检索文档 ID）；留痕区与证据区**分开存储**、保留期分开设 | 跨工具的留痕字段是否收敛 | 不要用可观测性的采样配置当审计留存配置 |
| 出海或多法域经营 | 先建「控制项 ↔ 框架」的映射层，同一控制只检查一次 | AI 合规标准在各法域的落地范围 | 不要按法域各建一套流程，也不要用「等新标准发布」代替现在动工 |

把上表压成一条实施顺序：**先让日志覆盖得住 → 再让证据不可篡改且保留期达标 → 再把控制项变成可复算的检查 → 最后才谈模型与输出的留痕**。顺序反过来的典型后果是：花大力气做了 LLM 留痕，审计时却发现采不到脚本任务的变更、也拿不出不可篡改的存储，留痕反而成了一个新的敏感面。

这套顺序的成本也要按同样的口径估。**量级【推算】**（沿用 5.2.1 的两个【经验】假设：日均 10 万次调用、按 4 KB/条计）：日增 400 MB、年增 146 GB，保留 3 年约 438 GB（146 GB/年 × 3 年）；若连完整 prompt 与输出一起存（20 KB/条，日增 2 GB、年增 730 GB），3 年约 2.19 TB（730 GB/年 × 3 年）。差别不在总量级，而在**最敏感的那部分内容要不要长期留在库里**——这正是「可删原文区 + 不可删哈希区」必须分开的原因。

最后一条与工具无关：**谁有权改上游**。审计能发现违规、合规能判定违规，但**纠正**需要有人有权改动生产系统；如果审计报告落在一个没有改动权的团队手里，闭环就合不上。这条判据与 AI 无关，却是所有 AI 合规方向的前置条件。

### 5.8 小结

> 本节小结：AI 在本主题真正改变的唯一一条机制，是**审计对象从「确定的操作」变成「不可复现的生成」**——因为同一个 prompt 在不同模型版本上结果不同，「重放验证」这条传统审计的兜底手段失效了，所以审计结论只能建立在留痕之上；代价是留痕库成为组织里最集中、最长期、且不许改的敏感数据集合，并与删除权正面冲突。它没有改变的是：合规判定的可信度来自可复算的证据，而不是来自生成了多少文字——因此本节**没有一个方向满足 L1**，最接近的仍是把合规要求变成可复算的控制项（合规即代码与持续合规），它缺的只是「厂商之外具名的公开生产记录」这一条，而不是任何模型能力。
>
> 💡 **思考锚点**：把本节那两个【经验】输入——日均调用量与每条留痕体积——换成你自己系统的值，按同一式子算一遍年增存储；再决定你把「完整 prompt 与输出」还是只留「哈希 + 脱敏副本」写进留痕。这 5 倍差距里装的正是最敏感的内容，你的删除权方案扛得住哪一档？
