## 7. 与其他方法对比

> 原 § 7 共 58 行、为打分表 + 1 棵决策树 + 3 条组合，缺少机制解释与可溯源证据，重写为 ~330 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

打分表把「场景相关的结论」伪装成「绝对结论」。同一个维度在不同约束下权重是相反的：在「单一法域、一年被审一次、只有几十条控制项」的场景里，「多框架支持」几乎没有价值——你只有一个框架；同一套能力放到「跨境经营、同时受 GDPR 与个保法约束、每季度都有客户来要证据」的场景里，决定生死的就是这一列。打分表没有位置表达这个反转，它给出的名次与场景无关，而选型恰恰是场景相关的。

第二，被打分的对象分属三层，彼此不是同一个问题的解。原表里同时出现云厂商审计日志（AWS CloudTrail、Azure Monitor、阿里云操作审计）、合规自动化平台（Vanta、Drata）与数据库审计（阿里云数据库审计）——前者回答「谁在控制面做了什么」，中者回答「控制项有没有被编目、证据有没有被收集」，后者回答「谁碰了数据库里的行」。把这三层压进一张表比「审计完整性」，等于拿「看得见什么」去比「能不能编目」：这三层在原表该列上拿的都是高分（云厂商审计与数据库审计 5 分、合规自动化平台 4 分），但它们说的根本不是一件事，而读者会把它读成「三者可以互相替代」。

第三，成本被压成了一个数。审计合规的成本至少是四条互不相同的曲线：写入与存储（随调用量 × 保留期增长）、判断与维护（随控制项数 × 框架数增长）、举证（每次审计都要重新准备的工时）、运维承接（有没有人管规则库、不可变存储与告警关闭量）。这四条曲线在打分表里都可以是「5 分」，但当你的日增从 GB 走到 TB 时它们的行为完全不同——有的按比例涨、有的阶跃、有的几乎不动。审计是全栈里少见的「成本与风险都随保留期单调增长、而保留期几乎不可谈判」的系统，这一点打分表完全看不出来。

第四，原树的判断节点只用描述性判据（「是否需要多框架」「是否需要数据库审计」「是否需要 AI 合规」「是否需要 SIEM」），节点上没有阈值，因此它无法回答「到多少量级就必须换形态」。本章的树给每个节点配一条可推导的依据（见 7.5），阈值要么来自成本函数、要么来自公开的标准要求、要么来自组织结构约束。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 观测位置 | 这条路径上的动作由谁看见（云控制面 / 数据库协议层 / 引擎钩子 / 应用埋点 / 工具调用） | 覆盖率是各观测点「并集」的可证明比例，任何一层都不能单独回答另一层的问题 |
| 不可篡改的落点 | 防篡改由应用约定、哈希链，还是存储组件执行 | 它决定「不可篡改」是承诺还是约束；写日志与删日志同权时，前者等于不存在 |
| 判断的载体 | 控制项是人读的文档、编目好的资产，还是可执行规则 | 它决定「多一个框架」要多付多少维护面：按框架立项是线性，按控制项立项是加一行映射 |
| 留痕的粒度与依据 | 记不记「操作当时的权限依据」 | 审计问的是「当时是否合规」；用当前权限比对历史操作会给出错误结论 |
| 保留期与可删除性 | 长期保留的是原文，还是哈希与事件元数据 | 原文区与不可变区的要求相反（一个必须可删、一个必须不可删），只能物理分开 |
| 运维承接能力 | 有没有人维护规则库、WORM、告警关闭与豁免到期 | 审计是长周期低频次系统，没有人承接时自建的成本收不回来 |

> 这 6 条与 [§ 3 设计模式与范式](07-audit-and-compliance-section-3-sec3.md) 的约束表同源：那里用约束推导模式，这里用约束推导选型。

这些候选其实分七族，**先分族再选，能省掉一半比较**：

1. **云控制面审计**（CloudTrail、Azure Monitor、阿里云操作审计、GCP Audit Logs）：采的是管理面。族内差异主要在「数据访问事件是否单独开启、如何计费」。
2. **集中日志与 SIEM**（Splunk、ELK、Ranger Audit）：解决的是「把很多来源汇成一份可按主体与时间检索的事件流」。Ranger Audit 是它的一个特化来源，只覆盖 Hadoop 生态的执行点。
3. **协议层审计**（阿里云数据库审计、Imperva、以及 MySQL Audit Plugin / pgAudit / IBM Guardium 这一类库侧能力）：唯一能看见「语句级读了什么、改了哪些行」的一族。
4. **控制项编排 SaaS**（Vanta、Drata、Tugboat Logic、Secureframe）：强项是编目与证据收集，弱项是判断与阻断——它不是门禁。
5. **判断引擎与不可变存储**（OPA、S3 Object Lock / OSS WORM）：是零件不是平台，必须挂在某个消费点或存储层上才有意义。
6. **自研合规中台**（含密级驱动与四元留痕）：把控制项、证据、管控动作放在一套体系里，机制上最强、承接成本也最高。
7. **模型与工具调用留痕**（Langfuse、LangSmith、Arize Phoenix、Helicone，以及阿里云通义安全一类面向 AI 场景的合规能力）：采的不是「人对系统的操作」，而是模型的外部动作（读了哪些文档、调了哪些接口）——审计主体换了，留痕的粒度也换了一层。

七族之外，还有一种形态常被忽略、但在小规模下确实成立：**只做留存不做使用**（日志开着、谁也查不动）。它满足「有记录」的字面要求，但不满足任何举证场景；把它列出来是因为选型的第一步往往是**确认自己有没有举证场景**，而不是直接比较平台。

分族之后有一个立即可用的推论：**同族内部可以先用功能与许可筛，跨族之间只能用机制做选择**。第 4 族内部（Vanta 与 Drata、Tugboat Logic 与 Secureframe）差的是控制项库覆盖面、集成数量与定价模式，换一家的迁移成本主要是重新做一遍证据映射；而第 3 族与第 4 族之间不可互换——控制项 SaaS 采不到语句级访问，协议层审计也编不了控制项库。跨族的错误选择不会以「不好用」的形式暴露，而会以「查不出」的形式在第一次争议时才暴露。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 观测位置：谁在被观测，决定了覆盖率的上限

**机制是什么**：审计能看见什么，由「观测点在哪一层」决定，而不是由平台的功能列表决定。

**它在各候选中的实现差异**：

| 观测层 | 代表方案 | 看得见 | 看不见 |
| --- | --- | --- | --- |
| 云控制面（管理面 API） | CloudTrail、Azure Monitor、阿里云操作审计、GCP Audit Logs | 云资源的建改删、权限与密钥变更 | 数据面：谁读了哪张表、谁跑了什么语句 |
| 数据库协议层 | 阿里云数据库审计、Imperva、MySQL Audit Plugin、pgAudit、IBM Guardium | 到达数据库的语句、账号、来源、影响行数 | 不经数据库的路径：对象存储直读、API 导出、缓存命中 |
| 引擎钩子 | Apache Ranger Audit、Hive Hook、Spark Listener | 该引擎内的表 / 字段级访问 | 其他引擎与旁路脚本 |
| 应用埋点 / API 网关 | 自研审计 SDK、网关日志 | 业务语义（谁的会话、查了什么） | 未接入的系统；埋点遗漏不会报警 |
| 模型与工具调用留痕 | Langfuse、LangSmith、Arize Phoenix、Helicone、阿里云通义安全 | prompt / 输出 / 检索到的文档 / 工具调用 | 模型之外未留痕的外部副作用 |

```text
同一句"谁看了客户名单"，五个观测层各给出什么
  控制面日志     →  查不到（"读数据"不在管理事件里）→ 返回空集，不报错
  协议层审计     →  能答，但只覆盖走了数据库那部分
  引擎钩子       →  能答，但只覆盖装了钩子的那个引擎
  应用埋点       →  能答，且带业务语义，但只覆盖接入埋点的系统
  LLM 工具留痕   →  能答"哪个 Agent 调了哪张表"，前提是该工具已留痕
  ────────────────────────────────────────────────
  真实覆盖率 = 这五者的并集能被证明覆盖的比例
  并集不可见的那部分，就是审计永远答不出的问题
```

**由此必然导出的性质**：因为云控制面采的是管理面 API，所以它能覆盖云上所有资源的「建改删」，却完全看不见数据面的读——把控制面日志当作「谁看过这张表」的答案，会得到一个空集，而空集不会报警，它只是安静地回答「没有人」。因为每一层的盲区各不相同，所以真实覆盖率等于各观测点**并集的可证明覆盖比例**，这个并集必须被显式度量，否则它会在半年内静默下降（新系统未接入、埋点未同步、数据事件忘了开）。代价是：集中式审计的运维工作量按「接入系统数」增长，长尾系统往往永远接不进来。

**公开证据**：AWS CloudTrail 把事件分为管理事件与数据事件，数据事件需显式开启且单独计费；Apache Ranger 在其权限组件上产出访问审计。这两条是产品文档中的既有能力描述，可按「CloudTrail data events」「Ranger audit」两组关键词在各自官方文档的当前版本中自行核验——此处只作机制依据引用，具体默认开关、计费口径与版本差异以官方文档为准。

**失效条件**：当问题需要跨观测层关联（「某人先在控制台授权、再用该权限导出数据」）时，任何单层都不成立，必须有一个统一 schema 的集中层（见 [§ 3.2.1](07-audit-and-compliance-section-3-sec3.md)）；反过来，当日增量增长到必须分层时，跨层关联的成本从「多查一张表」变成「跨热存与归档层的联合查询」。

#### 7.3.2 不可篡改落在哪一层：应用约定 / 哈希链 + 锚定 / 存储组件

**机制是什么**：防篡改由谁执行，决定了「不可篡改」是一条承诺还是一条约束。

**它在各候选中的实现差异**：

| 落点 | 代表 | 谁能改这份记录 | 代价 |
| --- | --- | --- | --- |
| 应用层约定（只追加、不发 UPDATE） | 自研日志表 | 任何持有库权限的人 | 成本最低，等价于一句承诺 |
| 哈希链 + 链头锚定 | 自研 WORM 表 + 链外锚点 | 改写者必须同时改写链与外部锚点 | 每次写入多一次哈希与一次锚定 |
| 存储层 WORM / 对象锁 | Amazon S3 Object Lock、阿里云 OSS WORM、Qumulo 类企业存储 | 由存储组件拒绝覆盖与删除 | 保留期内空间不可回收，压缩也化解不了 |

**由此必然导出的性质**：因为在多数团队里，写日志的账号与运维系统的账号是同一套，所以应用层的「不可篡改」只对误删有效、对「有权限的故意改写」无效——这条约束不满足，7.5 树上的 N3 分支就只是纸面承诺。因为哈希链的验证前提是链头可信，所以没有锚定的哈希链，安全性约等于「普通表 + 一个校验函数」：能改写全部数据的人也就能重算整条链并给出自洽结果，链看起来完全正常。代价是分层带来的运维：校验本身要有人做，否则「不可篡改」会静默退化为「没人验证过的普通表」。

**公开证据**：Amazon S3 Object Lock 提供合规（Compliance）保留模式，在该模式下保留期内的对象连根账号也无法删除——可按 AWS 官方文档 Object Lock 一章的当前版本自行核验。至于「写一次读多次」是不是硬约束，取决于它由谁执行：对象存储的保留模式是存储组件的属性，应用层「只追加、不发 UPDATE」只是应用层的一条约定，这一区分属机制判断、不是某份文档的结论【经验】。表格式的 time travel 提供的是版本可回溯，不等于防篡改，两者常被混用【经验】。

**失效条件**：当删除义务覆盖到链上内容（数据主体删除权、留存最小化）时，物理不可删除从合规资产反转为违法风险——因为一份不可删除的日志无法履行删除请求。此时正确解是把「可删的原文区」与「不可删的哈希与事件区」物理分开，而不是在同一张表上做取舍。

#### 7.3.3 判断的载体：文档 / 编目 / 可执行规则 / 事件流上的窗口

**机制是什么**：合规判断写在哪里，决定了「多一个框架」和「多一次检查」各要付多少。

**它在各候选中的实现差异**：

| 载体 | 代表 | 新增一个框架要做什么 | 判断在什么时候发生 |
| --- | --- | --- | --- |
| 文档 + 人工检查 | 早期自研、Excel 台账 | 加一套检查表与一份报告模板 | 测评前（周期抽样） |
| 控制项编目 + 证据收集 | Vanta、Drata、Tugboat Logic、Secureframe | 在映射表里加一列 | 持续（自动收集证据） |
| 可执行规则（合规即代码） | OPA 类判断引擎 + 门禁挂钩 | 在控制项上挂一条新条款的映射 | 事前拒绝 / 事中告警 / 事后举证，三处同一份规则 |
| 事件流上的窗口判断 | 持续合规监控 | 复用同一份控制项，只调窗口与阈值 | 事中（分钟级） |

```text
"控制项"是跨框架唯一的可复用单位
  GDPR   最小化 / 同意 / 存储限制 / 访问权 …
  个保法  告知同意 / 最小必要 / 删除权 / 跨境 …
  PCI DSS 日志至少保留 12 个月且近 3 个月可即时调取 …
  等保2.0 审计记录不可中断 / 权限最小化 …
   ────────────────────────────────────────────────
  按框架立项：N 个框架 = N 套检查流程 + N 份证据格式
  按控制项立项：1 套控制项 + 1 张映射表，框架数只增加表里的行
```

（上表中各条为对应框架的要求；其中 PCI DSS 的保留口径与其在选型中的用法，见 7.4 末条与 7.5 的 N5 依据【公开】。）

**由此必然导出的性质**：因为「最小化」「同意记录」「日志保留」被多个框架同时要求，所以按控制项立项时新增框架只增加映射表里的行，而按框架立项会让维护面随框架数线性增长——这是「重复建设」在机制层面的唯一解法。因为一份规则要同时被事前门禁、事中告警、事后举证三处消费，所以口径天然统一，代价是改错一条规则会被三个消费点同时放大：规则从文档变成代码资产，就必须有版本、评审、测试与回滚，缺掉测试的那一天，规则库会在第二次修改时失去可信度。

**公开证据**：Open Policy Agent 是 CNCF 毕业项目，毕业状态与毕业公告的具体年份可按 CNCF 官网项目列表与博客的当前版本自行核验；欧盟 AI Act 于 2024 年通过并分阶段适用，对高风险系统的记录留存提出要求【公开】（Regulation (EU) 2024/1689；具体条款与适用时点以法规原文为准）。

**失效条件**：当规则没有测试用例、或误报率高于团队处理能力时，门禁会被批量豁免、监控会被批量忽略，而这两条路径都不产生「规则已失效」的告警——系统看起来仍在运行，实际已经失效。判据是可算的：统计每条规则的命中量与其中被人工推翻的比例。

#### 7.3.4 留痕粒度与主体：记「发生了什么」还是记「当时凭什么」

**机制是什么**：一条审计记录里有哪些字段，决定了事后能回答哪一类问题；缺一个字段，整类问题永久答不上来，而且无法补造。

**它在各候选中的实现差异**：

| 粒度 | 代表 | 能回答 | 答不上来 |
| --- | --- | --- | --- |
| 操作日志（谁、何时、做了什么） | 云原生审计、数据库审计 | 「谁动过这张表」 | 「他当时凭什么权限做这件事」 |
| 四元留痕（主体 / 当时权限依据 / 对象与动作 / 结果） | 蚂蚁金融级审计形态（见 [§ 6](07-audit-and-compliance-section-6-sec6.md)） | 「当时是否合规」可判定 | 细粒度用途需额外字段 |
| 带用途字段的事件 | [§ 3.2.1](07-audit-and-compliance-section-3-sec3.md) 的 `purpose` 字段 | 「为什么读」 | — |
| 模型与工具调用留痕 | Langfuse、LangSmith、Arize Phoenix、Helicone、阿里云通义安全 | 「这次回答读了哪些文档、调了哪些接口」 | 未留痕的外部副作用 |

**由此必然导出的性质**：因为审计问的永远是「当时是否合规」，所以用当前的权限表去比对历史操作会得出错误结论——权限后来被回收时，一次当时完全合法的访问会被判成越权；因此「当时的权限依据」必须与操作写在同一条记录里，而不是事后关联。因为 Agent 的外部动作由模型在运行时决定（读哪些表、调哪些接口取决于检索结果），所以按「人对系统的操作」建模的传统留痕在 AI 链路上会整段留空——留痕必须下沉到工具调用层，否则「谁让模型做了什么」这一类问题永远答不上来。代价是留痕体量随调用量增长，且单条记录比传统访问日志大一到两个数量级（含上下文时），审计库自身成为新的敏感数据集合。

**公开证据**：【公开】欧盟 AI Act 于 2024 年通过，对高风险 AI 系统的记录与可追溯性提出要求（具体条款以法规原文为准）；LLM 可观测性工具（Langfuse、LangSmith、Arize Phoenix、Helicone）提供调用级留痕能力——它提供的是「留痕能力」，不等于「合规证据链」，后者还要求留存策略、不可篡改与访问控制三件套【经验】。

**失效条件**：当留痕直接保存原始 prompt 与 SQL 原文时，审计库成为「集中、长期、被要求谁都不能改」的敏感数据暴露面，并与删除权直接冲突（用户要求删除对话，而这段对话已在证据区）。修法仍是物理分区，而不是在同一张表上做取舍。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
成本 ≈ 采集与写入(调用量 × 单条大小)
     + 存储(日增量 × 保留期，证据区不可回收)
     + 判断与人力(控制项数 × 框架数)
     + 举证(每次审计的准备工时)
```

| 方案家族 | 主导项 | 隐性成本 | 成本随什么增长 |
| --- | --- | --- | --- |
| 云控制面审计 | 事件量与数据事件开关 | 跨云统一 schema 与关联调查 | 调用量，线性 |
| 自建集中日志 / SIEM | 摄入量与留存许可 | 集群运维、索引调优、冷热分层 | 日摄入量，线性 |
| 协议层审计 | 实例数 / 语句流量 | 对数据库本身的性能影响与旁路部署 | 实例数与语句量 |
| 控制项编排 SaaS | 员工数 × 框架数订阅 | 控制项维护、豁免管理与审计配合工时 | 人头与框架数，阶跃 |
| 自研合规中台 | 常驻人力（不可摊薄） | 规则库测试、告警关闭、证据归档 | 几乎不随规模变，随控制项数增长 |
| 判断引擎 + 不可变存储 | 证据区的存储与写入 | 空间不可回收；链断要能被第一时间发现 | 证据区条目数 × 保留期 |
| LLM 留痕 | 调用量 × 留痕口径 | 审计库自身成为敏感数据集合 | 调用量，线性 |

**一个【推算】示例**（前提写全，读者可换成自己的数）：日均 1000 万次查询，每条访问日志（主体、资源、耗时、结果行数）约 500 B。

- 日增 = 10⁷ × 500 B = 5 GB/日；一年累积 ≈ 5 GB × 365 ≈ **1.8 TB**【推算】。
- 按对象存储标准层约 $0.02–0.03/GB-月的公开定价量级折算（主流云厂商的标准对象存储都在这个量级上；单价随区域与时间调整，可按你所用法域厂商的官方定价页当前版本自行核验）：满一年后的存量 1.8 TB，月存储成本 ≈ 1800 GB × $0.023 ≈ **$41/月**【推算】。
- 若连 SQL 原文（平均约 2 KB）一起落库，单条涨到约 2.5 KB，日增 ≈ 25 GB，一年后存量 ≈ 9 TB，月成本 ≈ 9000 GB × $0.023 ≈ **$207/月**【推算】——**同一个系统，存储差 5 倍，而这 5 倍里装的正是最敏感的内容**。
- 逐行留痕在量级上不成立：一次扫描 1 亿行的查询，按每行 100 B 计 ≈ 10 GB/次（10⁸ × 100 B = 10¹⁰ B）【推算】；若这类查询每天 100 次，日增即 1 TB。所以行级审计只能记「访问了哪个对象、多少行」，不能记行内容——这不是设计偏好，是量级决定的。
- 不可变区把成本从「可优化」变成「不可谈判」：同样 1.8 TB/年若全量进 WORM，保留期内不可删除、不可回收；而 PCI DSS 要求日志至少保留 12 个月、其中最近 3 个月可即时调取【公开】（PCI SSC 标准现行版本要求项 10.5.1，条号与版本以标准原文为准）。

**怎么判断你的主导项**：先把「日增 × 保留期」算出来，再决定留什么（原文 / 指纹 / 哈希）。若这个量级已超过你愿意长期支付的水平，第一个该砍的不是保留期（它通常不可谈判，或被标准写死），而是**单条记录的字段**——这也是「只存指纹不存原文」的收益来源，而不是安全洁癖。

```text
审计成本的两条曲线（主导项在什么规模上易手）
  年成本
    ▲
    │   存储与写入曲线：随「日增 × 保留期」线性上行
    │             ╱      （证据区部分不可回收，压缩化解不了）
    │          ╱
    │       ╱  ───────────  判断与人力曲线：随「控制项数 × 框架数」
    │    ╱                    阶跃上行，与日志量几乎无关
    │ ╱
    └────────────────────────────────────────► 日志量
  小规模：人力（规则维护、举证准备、告警关闭）是大头
          → 此处的第一笔投入应买「工具与人」，不是买「不可变存储」
  大规模：存储与不可变区是大头
          → 此处的第一笔优化是「单条留什么」，而不是「留多久」
```

两条曲线的形状决定了两个常见误判：在小规模上先买最贵的不可变存储，等于把预算花在一条还没成为主导项的成本上；在大规模上继续靠加人维护规则与举证材料，等于用一条阶跃曲线去追一条线性曲线——**人力不会因为你多招人就变得可扩展，而存储会因为你少存一个字段就下降**。

### 7.5 决策树（每个分支都要有阈值依据）

```
N1  你要用这份记录回答什么问题？
    ├── 只是运维排障 → 云厂商原生审计 + 集中日志检索（先别买合规自动化、先别建 WORM）
    └── 要向监管 / 客户举证 → 继续 N2

N2  举证以「控制项编目 + 证据收集」为主（首次 SOC 2 / ISO 27001 认证）？
    ├── 是 → 合规自动化平台（Vanta / Drata / Tugboat Logic / Secureframe）+ 云原生审计
    └── 否 → 继续 N3

N3  举证要回答「当时是否合规」，且内部高权限账号需被约束？
    └── 是 → 四元留痕（主体 / 当时权限依据 / 对象与动作 / 结果）+ 独立不可篡改存储

N4–N12 是叠加在 N3 之上的并列检查项，不是 N3 之后的多选一：
命中哪一项就按那一项落地，不命中就跳过、继续看下一项。

N4  留痕对象是否包含模型与 Agent 的工具调用？
    ├── 是 → 调用级 + 工具级留痕进同一事件流
    │        （Langfuse / LangSmith / Arize Phoenix / Helicone / 阿里云通义安全）
    └── 否 → 跳过，看 N5

N5  日增 ≥ 数百 GB，或法定保留期 ≥ 12 个月？
    ├── 是 → 分层：热存（近 90 天）+ 归档 + 证据区（不可变，只覆盖需举证的子集）
    └── 否 → 单层存储 + 四元留痕 + 哈希链 + 链头锚定

N6  留痕单条 ≥ 1 KB 且日均 ≥ 10⁵ 条？
    └── 命中 → 先做时间分区与保留期策略再放量（否则改保留期会变成搬数据）

N7  需要回答「谁动了数据库里的数据」？
    ├── N8 直连数据库（协议层可见）
    │       → 数据库审计（阿里云数据库审计 / Imperva / pgAudit / MySQL Audit Plugin）
    └── N9 只经应用与自研通道（协议层看不到）
            → 应用埋点 + 引擎钩子（Ranger Audit / Hive Hook）+ 统一 schema 集中

N10 适用框架 ≥ 2 且变更频繁？
    ├── N11 数据会跨境汇聚
    │       → 区域集中 + 上层只汇聚合或哈希 + 受限数据阻断（不做全球单点）
    └── N12 单法域
            → 合规即代码（OPA 类）+ 门禁与监控共用同一份规则
```

**阈值依据**（与树上的 N1–N12 一一对应）：

- **N1**：依据 7.3.1 与 [§ 3.1](07-audit-and-compliance-section-3-sec3.md) 的约束二——不可篡改只对 $\text{Completeness}$ 的分子起作用，对分母毫无贡献；没有举证场景时先建 WORM，保护的是本来就不完整的样本，这是本主题下最典型的资源错配。
- **N2**：依据 7.2 的分族——控制项编排 SaaS 的机制强项是「编目 + 收证据」，不是判断与阻断；用错层会得出「买了工具就等于合规」，而门禁与阻断仍要做在 7.3.3 的规则层。
- **N3**：依据 [§ 3.1](07-audit-and-compliance-section-3-sec3.md) 的约束四——审计要防的第一类对象是持有平台高权限的内部角色，因此「写日志的权限」与「删日志的权限」必须分开，这条不满足则 N5 的不可变区只是纸面承诺。
- **N4**：依据 7.3.4——Agent 的外部动作由模型在运行时决定，按「人对系统的操作」建模的留痕在这条链路上整段留空，且事后无法补造。
- **N5**：「数百 GB / 12 个月」两条依据分别如下。(a) 日增阈值来自 7.4 的成本函数，但**不能**用「热存与归档的单价比值」来推——那个比值由单价差决定，与日增量无关，日增 5 GB 与日增 500 GB 的倍率完全相同。随量变化的是**绝对节省额**：分层带来的节省 ≈（标准层单价 − 归档层单价）× 存量，它随存量线性放大，而分层管道（生命周期规则、归档回取、双路径查询）的工程与运维成本近似固定，因此交点落在绝对支出进入千美元级月成本的区间。按 7.4 的同一单价外推：日增 5 GB 时一年后存量约 1.8 TB、标准层月成本约 $41【推算】——这个量级上单层存储的支出摊不平一条分层管道；日增 500 GB 时一年累积约 1.8×10² TB、年内平均存量约 9×10¹ TB，标准层月成本约 $2×10³ 量级【推算】——此处的绝对支出才足以让一次分层改造在可接受周期内回收。注意 7.4 只给出标准层单价、未给归档层单价，故上文的量级推导只依赖标准层单价，具体能省多少请按你所用云厂商当前的归档层定价自行核验。(b) PCI DSS 对日志至少保留 12 个月、近 3 个月可即时调取的要求【公开】（PCI SSC 标准现行版本要求项 10.5.1，条号与版本以标准原文为准）。树上的「热存近 90 天」来自访问模式：调查与告警几乎都集中在近期数据上【经验】，分层比例应据此设定，而不是按存储单价随手切。
- **N6**：这一节点标记的是**不可逆点**，不是成本阈值——依据 7.7：留痕粒度与范围不可回溯，保留期一旦绑定分区生命周期，改保留期就是一次数据迁移而非改一个参数。之所以定在「单条 ≥ 1 KB 且日均 ≥ 10⁵ 条」，是因为两个条件同时成立时表有了两个特征：单条到 KB 级意味着记录里已包含原文或上下文（字段结构将长期承重），日均 10⁵ 条意味着写入路径已在稳定承载生产流量、结构变更要走完整迁移流程。按 7.4 的算法，这一量级本身只有 10⁵ × 1 KB = 100 MB/日、约 36.5 GB/年【推算】，存储成本远未构成压力——正因如此，此处要提前定的是**分区与保留期的绑定方式**，而不是省存储；若把量级读成成本阈值，会得出「这么小不用管」的反向结论。
- **N7**：依据 7.3.1 的观测层表——数据库内发生的事只有协议层或引擎钩子看得见，控制面日志在这类问题上返回空集且不报警。
- **N8 / N9**：同样依据 7.3.1——协议层唯一看不见的是不经数据库的路径（对象存储直读、API 导出、缓存命中），因此「只经应用与自研通道」的组织必须用埋点与钩子覆盖，而不是买协议层产品。
- **N10**：「框架 ≥ 2」来自 7.3.3 与 [§ 3.4](07-audit-and-compliance-section-3-sec3.md) 组合二【经验】——只有一个框架、且一年只被审一次时，把条款改写成可执行规则库的维护成本高于收益；框架数与变更频率同时上升后，收益才来自口径统一与可回归测试。
- **N11**：依据跨境传输的法律性质——把多法域日志汇到一处的那一刻就产生了跨境传输；GDPR 对向第三国传输设有条件限制【公开】（Regulation (EU) 2016/679 第 44–46 条，条号与版本以法规原文为准）。
- **N12**：依据 [§ 3.3](07-audit-and-compliance-section-3-sec3.md) 中「先立规则库（定义态），再让监控与门禁消费它」的顺序——反过来先铺监控，每加一个消费点就要重写一次判断。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| AWS 上的组织、以云资源操作留痕为主 | CloudTrail（按需开数据事件）+ Audit Manager | 自建 ELK | 不选自建：采集适配与跨云统一 schema 的固定成本先落地，而你还只有一朵云 |
| 阿里云上的组织、需对齐本土监管口径 | 阿里云操作审计 + 阿里云合规中心 | 自研合规中台 | 不选纯自研：控制项与报告的编目工作量要在没有工具时先扛一遍 |
| 多朵云混用、同一控制项要得出同一个结论 | 合规即代码（OPA 类）+ 各云原生审计做采集 | 按云各建一套检查流程 | 不选逐云立项：规则会在云之间漂移，同一事实得出两份结论 |
| 首次做 SOC 2 / ISO 27001 认证 | Vanta / Drata / Secureframe | Tugboat Logic | 不选它：与首选同属第 4 族，差别只在控制项库覆盖面、集成数量与定价模式，不在判断机制；它只在你的框架或地域恰被它覆盖得更全时才轮到，而同族换家还要重做一遍证据映射（见 7.2） |
| 强监管行业、要回答「当时是否合规」 | 自研合规中台（四元留痕含权限依据）+ 独立不可篡改存储 | 商用审计平台 + 自建留痕 | 不选只记操作：权限后来被回收时，历史操作无法判定当时是否合规 |
| 需要语句级的数据访问审计 | 阿里云数据库审计 / Imperva（或库侧 pgAudit、MySQL Audit Plugin） | 应用埋点 | 不选只做埋点：绕过应用的直连、脚本与导出会整体漏掉 |
| 大规模日志检索与 SIEM 告警 | Splunk | ELK Stack | 不选无 SIEM 的纯检索：关联规则与告警编排要另外建设 |
| 有 LLM / Agent 生产流量 | 调用级 + 工具级留痕进同一审计事件流（Langfuse / LangSmith / Helicone 一类 + 阿里云通义安全一类的 AI 合规能力） | 只留访问日志 | 不选只留访问日志：模型读了哪些文档、调了哪些接口会整段留空 |

**常见组合（职责边界与运维代价）**：

1. **云原生审计 + 集中日志（两层并存）**：云厂商原生负责「管理面无遗漏」，集中日志负责「跨源检索与长保留」。边界是「采集归云、关联归自己」。代价是两套 schema 要映射，且资源标识不统一时关联率上不去——绝大多数企业的实际形态就是这个两层并存【经验】。
2. **合规自动化 SaaS + 自建证据源**：SaaS 负责控制项编目、证据工作流与合规状态看板；自建侧负责产生可核验的原始证据（扫描报告、覆盖率日报、告警关闭时长）。代价是证据必须**同源**：报告里的数字要能回指到原始记录，否则报告本身站不住。
3. **数据库审计 + 集中审计 + 数据目录联动**：数据库审计补上语句级视角，集中审计做统一 schema，数据目录提供密级与 Owner。边界是「审计答谁做了什么、目录答这件事涉及什么」。代价是强依赖元数据质量——密级标注不全时审计结论直接失真（见 [§ 6](07-audit-and-compliance-section-6-sec6.md) 阿里密级分级案例）。
4. **合规即代码 + 持续监控 + 变更门禁**：规则库是唯一判断来源，监控消费它做事中告警，发布与权限流程消费同一份规则做事前阻断。代价是规则改动必须测试与灰度，且紧急豁免要自动到期，否则豁免会慢慢变成新的默认路径。

组合的运维代价可以归到一句：**每多接一层，就多一次「同一事实在两处是否还对得上」的校验**；对不上的地方（通常是资源标识与密级标注）就是审计结论失真的起点。

### 7.7 选错的代价与迁移成本

**反模式：先用不可篡改，后补完整性** —— 症状：日志还没采全就上了 WORM 与哈希链，采集覆盖率没有度量 → 后果：不可篡改只保护了分子（被记录的样本），分母（本该记录却漏掉的）一动不动；等第一起需要举证的争议出现时，发现要查的时段或系统根本没接入，而缺失的记录无法补造 → 正确做法：先度量覆盖率与字段完整性，再把证据区（需举证的少数事件）做成不可变，而不是把全部运营日志做成不可变。

**反模式：把 SIEM 搜索量当成审计能力** —— 症状：以日志平台接入了多少源、每天查多少次为验收标准，但没有任何一条日志能回答「谁导出过大表」→ 后果：审计能力名义存在、实际为零，成本照付；事故发生时第一次真正查日志，才发现字段不全或链路不通 → 正确做法：每条采集绑定一个具体问题（含查询入口与告警），并以「能否在不写新代码的前提下 30 分钟内从问题跑到结论」做验收——这条时限是操作口径【经验】，可由团队按自己事故复盘的实测时长校准，不是任何法规的要求。

**反模式：用当前权限判断历史操作** —— 症状：审计时拿现在的权限表去比对三个月前的访问记录 → 后果：权限已被回收的合法访问被判成越权，权限事后扩大的越权访问被判成合规——两个方向都会错，且错得没有告警 → 正确做法：留痕里写入「操作当时的权限依据」（命中的角色、策略或临时审批单），把判断建立在当时的依据上。

**换成另一个要动什么**：

| 迁移方向 | 数据迁移 | 查询与规则改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 云原生审计 → 自建集中日志 | 历史日志导入（常按保留期只导一部分） | 检索语法与告警规则重写 | 采集端、索引、冷热分层与保留策略 | 检索与调优技能 | 中–大 |
| 手工文档合规 → 合规即代码 | 控制项与条款映射表导入 | 检查表改写成规则 + 测试用例 | 判断引擎、门禁挂钩、豁免到期机制 | 规则语言与评审流程 | 大（间隙期双轨） |
| 单法域 → 多法域 | 不需要搬日志，需重新划分域 | 控制项扩成「控制 × 法域」矩阵 | 区域集中部署 + 跨境阻断 | 隐私工程与法务协同 | 大，且不可逆（部署形态定了就难收回） |
| 只留操作日志 → 四元留痕 | 历史记录无法补齐（只能前向生效） | 采集器与 schema 改写 | 独立不可篡改存储 + 断链监测 | 采集端改造与联调 | 中，但**历史时段永久缺失** |
| 传统日志 → 含 AI 留痕 | 无历史可迁 | 事件模型扩展（模型、检索文档、工具调用） | 与既有事件流合并、保留期分区 | 模型侧与平台侧协同 | 中–大 |

- 上表量级为【经验】：迁移的主要成本不是工具替换，而是「控制项要重新表述一遍」与「留痕字段一旦确定就无法为历史时段补齐」——后者要在迁移计划里显式写成风险项。
- 一条不可逆的边界：**留痕粒度与范围不可回溯**。加字段只能从当天生效；因此「权限依据」「purpose」「工具调用」这三类字段应当在第一次建设时就写进 schema，而不是等到被审计问到再加。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 只有运维排障需求 | 云原生审计 + 集中检索 | 没有举证场景时，WORM 与合规自动化的收益为零，成本却是常驻的 |
| 多系统、要能跨系统调查 | 集中式（含统一 schema 与覆盖率度量） | 关联问题的答案只存在于统一 schema 里，分散日志答不了 |
| 首次做认证、以编目与证据为主 | 控制项编排 SaaS + 云原生审计 | 它的机制强项是组织控制项与收证据，不以判断与阻断为目标 |
| 强监管、要回答「当时是否合规」 | 四元留痕（含当时权限依据）+ 证据区不可变 | 举证要求「可证明未被修改」且判定依据必须是当时的 |
| 多法域、会跨境汇聚 | 区域集中 + 上层只汇聚合或哈希 | 汇聚那一刻即构成跨境传输，集中式的优点会反转为违法风险 |
| 多框架、变更频繁 | 合规即代码 + 监控与门禁共用规则 | 控制项是唯一可复用单位，框架数只增加映射行数 |
| 日增 GB→TB、保留期长 | 热存 + 归档 + 证据区三层 | 保留期不可谈判，唯一可优化的是「单条留什么」而不是「留多久」 |
| 有 LLM / Agent 生产流量 | 调用级 + 工具级留痕进同一事件流 | 模型动作不走人工路径，没留痕等于没发生 |

> 本节小结：这一主题下真正起决定作用的差异只有一条——**你要长期保存的到底是「原文」，还是「哈希与事件元数据」**。它同时决定了不可篡改该落在哪一层（存储组件还是应用约定）、成本是线性还是不可回收、以及删除权能不能被履行；观测位置、判断载体与留痕粒度都在这条差异之下派生。
