## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

**第一，总分把形状完全不同的成本函数压成了一个数。** 打分表给「自研（Prometheus + DataHub）」与 DataHub 各 24 分（可逐格复核）。这两个 24 分意味着「等价」，但它们的成本根本不是同一形状的：DataHub 一侧的成本随**被管理的资产数**增长（采集器、索引、事件量），自研一侧的成本随**你愿意长期养几个人**增长。这恰好掩盖了本章最需要算的那笔账（7.4）。

**第二，六个维度问的全是「能力有多强」，没有一列问「你防的是哪一类失效」。** 这六个维度是配置成本 / 自动化程度 / 大数据支持 / 实时支持 / AI 能力 / 社区生态。但在本主题里，第一个该问的问题是**你要覆盖的是已经想到的失效，还是没想到的偏移**——前者只有规则写得出，后者只有基线学得到，而结构变更两类都看不见，只能靠事件（[§ 3 设计模式与范式](04-observability-section-3-sec3.md) §3.1）。

**第三，打分表配套的决策树，第一问是没有推导的阈值，而且问错了对象。** 第一问「预算充足（> 100 万/年）？」既没有出处、也没有算法；更重要的是，**该问的不是「预算有多少」，而是「订阅年费」与「自建一支队伍的年成本」这两个数谁大**——前者随被监控资产数分档，后者随常驻人数走，两者相交的位置在每个组织里都不同（7.4 给出推导与代入方式）。

**第四，「配置成本」这一列把两件相反的事合在了一起。** 打分表给商业 SaaS 的配置成本 5 分、给自研 2 分。SaaS 的「配置成本低」不是因为它更简单，而是因为**基线由厂商在跨客户数据上学**（冷启动近零），代价是**每轮采集查询算在你自己的仓库账上**，且它要求你的表与公开同类表同构；自研的「配置成本高」换来的是覆盖长尾数据源与定制口径的能力。这 3 分差的是**控制权与账单位置**，不是便利程度。

**第五，打分表把不在同一层次上的东西放进了一张表。** DataHub 是元数据与血缘的载体（结构事件与依赖关系的真相源），Monte Carlo 的判定输入是数值指标。两者不是竞品而是互补的两层。**打分表要求所有候选可比，于是它把一个「分层问题」压成了一个「排序问题」。**

因此本章不排序，只做三件事：**按「正常这个参照物从哪里来」分族**（同族内部差异远小于跨族差异），**给每条机制写清优势成立的条件与失效条件**，最后把决策落到几个能从现有监控、账单与值班记录里直接取到的量上。

**本章所有数字按三档标注**：【公开】（有可定位的**外部**出处——官方文档 / 论文 / 工程博客 / Release Note——并注明来源与年份；**凡条目本身不含年份主张的**——规范、产品的长期能力、通用统计方法——正文会说明这一点，并请以官方文档当前版本为准）、【推算】（由公开前提推导，正文写出推导链，区间两端都必须能从链上得到）、【经验】（行业普遍实践，或本书内部小节给出的结构判断；只给区间与条件，不给精确值）。**本书内部小节一律按【经验】使用，不占【公开】档**——它给的是本书自己的结构判断与核验入口，不能充当外部来源。

**本章采用的 6 条判据**（与 §3.1 的约束表同一组轴，此处改从选型角度提问）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 「正常」的来源 | 参照物是人写下的期望、自己历史的基线，还是结构事件的有无 | 决定它能覆盖哪一类失效：规则覆盖已知，基线覆盖未知，事件覆盖结构变化——三者不可互替 |
| 采集是否读数据内容 | 采集成本随行数增长，还是随表数增长 | 决定「覆盖全量资产」这个要求能不能实现，也决定能不能看见「值错」而不只是「没产出」 |
| 判定单元与 MTTD 下界 | 判定单元是表 + 批次、分区 + 窗口，还是字段 | 判定单元越粗，发现越晚；单元越小，噪声下限越高——两者是同一个参数的两面 |
| 手上已有多少历史基线 | 新表接入当天能报出什么 | 没有基线时只有规则可用，且它恰好看不见漂移这类新问题 |
| 误报成本记在谁账上 | 阈值最终会被谁、往哪个方向调 | 采集查询跑在自己的仓库上、告警半夜叫醒自己的人——阈值最终是值班表问题 |
| 处置链的风险量级 | 自动化能开到哪一步 | 判定错是噪声，归因错是指错方向，处置错是改坏生产——三条链不能捆成一个开关 |

> 这 6 条的权重随处境移动（本节出现的规模量级均为【经验】：行业常见区间）：百级表、单团队时，**「正常」的来源**最先起作用（先有可见性再谈检测）；万级表、多源之后，**采集是否读数据内容**成为硬约束；跨团队消费、告警量超过处理能力之后，**误报成本与处置链风险**才进入前三。**判定单元**是个例外——只要链路上存在实时环节，它就要先确认，与规模无关。

| 自研（Prometheus + 时序统计 + Grafana 一类） | 指标 + 时序 + 阈值/基线 | 「正常」= 自己历史窗口里的均值与方差 | 有平台工程能力的团队 | 开源 + 自建 |
| 自研（Prometheus + DataHub + AIOps） | 指标 + 元数据 + 归因与处置 | 在前两族之上再加一条归因链与一条处置链 | 大型互联网平台 | 开源 + 自建 |

| 系统可观测性厂商的 AI 能力（Datadog / New Relic 一类） | 从系统侧向数据侧延伸 | 复用既有 APM 的采集与检测栈，再向上补数据侧判定 | 已有成熟 APM 体系的组织 | 商业 |

> 表中产品的沿革见主文件 §1.4 与 [§ 3 设计模式与范式](04-observability-section-3-sec3.md) §3.2 的各模式「真实使用」条目；本条只取「这些产品长期存在、其能力以各家官方文档当前版本为准」这一判断，不在此处断言具体版本号与发布日期。

这 14 个候选分成**五族**。分族的依据不是品牌、也不是开源或闭源，而是**「正常」这个参照物从哪里来**：

- **族一 · 规则式（正常 = 人写下的期望）**：Great Expectations、Soda、dbt tests、Apache Griffin。它是唯一「上线当天就生效、判定精确、误报低」的一族，代价是**覆盖率的上限恰好等于你写下的规则条数**。
- **族二 · 基线式（正常 = 从历史学出来的）**：自研（Prometheus + 时序统计）、Monte Carlo、Bigeye、Anomalo、Mona，以及数仓自带与 APM 厂商延伸过来的能力。同族内部真正的分界是**基线在哪里学、采集算谁的账**：自己学就要自己养采集与检测工程；厂商跨客户学则冷启动近零，但每轮采集查询记在你的数仓账上（§3.2.1 / §3.2.2 有这两条路径的结构）。
- **族三 · 事件式（正常 = 结构事件没有发生）**：DataHub、OpenLineage。判定输入不是值而是事件，所以覆盖全量资产的边际成本与数据体积无关，代价是**事件流之外的世界对它不可见**。
- **族四 · 流式（正常 = 分区 + 窗口的位点）**：Flink + Prometheus 一类的流式判定（属自研族的流式形态）。批量里「批次产出完成」这个可对齐的时点，在实时链路里不存在。
- **族五 · 归因与处置式（在前几族之上再走一步）**：AIOps、Datadog / New Relic 的 AI 能力、Mona 的解释能力，以及用语言模型做异常解释的一类做法。**它消费前几族的输出，不替代任何一族**——同一份指标，判定链可以换模型，输入却换不了。

**先分族再选，能省掉一半比较**：族一内部比的是规则的覆盖面与维护成本，族二内部比的是基线来源与账单位置，族三内部比的是事件契约与解析器覆盖。跨族之间才出现真正的机制差异（7.3.1）。**每族的典型失败方式也不同，这比典型优势更有用**：族一死于**覆盖率**——面板是绿的，因为那里根本没有规则；族二死于**同构性与账单位置**——表「每张都长得不一样」时报的都不是要紧的，且暂停订阅也退不回已发生的采集开销；族三死于**假绿**——「没有事件」被读成「没有异常」；族四死于**「队列不堵但用户已在等」**——过程量正常而端到端延迟在累积；族五死于**错误的自信心**——一段表述完整的归因被当成结论，团队顺着它排查的时间比没有它更长（§3.2.5）。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 「正常」从哪里来：期望、基线、事件

**机制是什么**：任何检测都在拿观测值与一个「正常」比较。这个参照物的来源只有三种：**人写下的期望**（规则）、**从历史推断的分布**（基线）、**某个事件有没有发生**（事件）；流式场景下还有它们的变体——**过程量的位点是否越界**。来源决定了它天然能看见什么、天然看不见什么。

**它在各候选中的实现差异**：

| 参照物来源 | 候选 | 上线当天能报什么 | 覆盖面随什么扩展 | 结构上看不见什么 |
| --- | --- | --- | --- | --- |
| 人写下的期望 | Great Expectations、Soda、dbt tests、Apache Griffin | 立刻能报（规则已定义） | **随规则条数扩展，而规则要人写** | 你没写下的那类失效（分布漂移、未知异常） |
| 从历史推断的分布 | Monte Carlo、Bigeye、Anomalo、Mona、自研时序统计、数仓自带 | 要等历史（新表头几周只有规则可用） | 随数据自己扩展 | 「你从没见过的正常」——基线把大促波动也学进去 |
| 事件的有无 | DataHub、OpenLineage | 立刻能报（事件一产生即判定） | 随接入的采集源扩展 | 值错、分布漂移（事件说不了值的事） |
| 过程量的位点 | Flink + Prometheus 一类 | 有就报（无批次时点可等） | 随接入的分区与窗口扩展 | 下游用户等了多久、批侧产出是否完整 |

**由此必然导出的性质（因果句）**：因为**规则式的「正常」是人写下的期望**，所以它上线当天就精确、误报低，代价是**它能覆盖的失效恰好等于你已经想到的那些**——覆盖率的上限是规则条数，而规则条数要人写、要随口径变化返工，于是「面板全绿」既可能是数据健康，也可能是这里根本没有规则（7.7 的第一条反模式）。反过来，因为**基线式的「正常」是从历史推断的**，所以覆盖面随数据自己扩展，代价是它**要求「历史能代表未来」**：基线里包含大促的波动，阈值就会跟着波动走，一旦节律本身变化，固定的倍数阈值立刻失去含义（§3.2.1 失效点）。而因为**事件式的判定输入是事件而不是值**，它能在不读数据内容的前提下覆盖全量资产——这是它唯一的、也是决定性的优势，代价是「**没有事件**」会被读成「**没有异常**」：脚本直接改表、外部导入、人工 DDL 都不产生事件，面板是绿的，但绿是假绿。

**三类参照物看不见的失效互不相同**，这正是「规则与指标并存」的机制依据：**用规则守住已知的底线，用指标发现未知的偏移，用事件盯住结构的变化**（§3.1）。把三者中的任意两个互相当成替代品，都会留下一整类看不见的故障。

**证据与来源**：系统可观测性的采集范式（metrics / logs / traces）与 SLI / SLO / 错误预算的原始记述，出自 Google 公开的 SRE 系列材料（2016 年起），判定入口是其中的 SLO 章节（本书 [§ 6 落地实践](04-observability-section-6-sec6.md) 的 Google SRE 案例引用的正是它）【公开：Google SRE 系列公开材料，2016 年起】；血缘事件契约可核 OpenLineage 项目文档：主文件 §1.4 把其 1.0 记在 2023 年，而 [§ 5 血缘与影响面](../05-lineage-and-impact/05-lineage-and-impact.md) 把它记在 2024-01，本书两处相差一年，本节不代为裁定具体日期，请以该项目官方 Release Note 为准【经验：只取「存在统一的血缘事件契约」这一结构判断，不取其年份与版本号】。**「元数据事件作为判定输入」这一形态**取自 [§ 3 设计模式与范式](04-observability-section-3-sec3.md) §3.2.3——它给出元数据事件表与血缘表的结构示意，并说明该形态只取「存在以元数据事件为驱动的开源元数据平台」这一结构判断、不取建设时间线【经验：只取上述结构判断，不取年份；某个项目是否以元数据事件为**唯一**驱动、以及各项目的开源年份，以各家官方文档为准】。统计阈值方法（3-sigma、IQR、孤立森林、KS 检验）的形式化见主文件 §2.2，属通用统计方法，本身不含年份主张【经验：方法名可直接检索】。

**失效条件**：当你既没有历史、也不愿意写规则、还没有可接入的事件源时（例如刚接入一批外部导入的表），这三种参照物一种都不成立——此时唯一的动作是先把资产与责任人登记起来（可见性优先于统计），而不是先买检测能力（§3.3 的判断）。

#### 7.3.2 采集是否读数据内容：成本形状与检出下界

**机制是什么**：采集分两种——只读**产出元信息**（最大更新时间、行数、分区数），或者**读数据内容**（空值率、唯一率、值域、分位数、直方图）。前者决定「有没有按时产出」，后者才能看见「值对不对」。这条分界线是本主题里成本函数形状的唯一来源。

**它在各采集方式上的实现差异**：

| 采集方式 | 成本随什么增长 | 能看见什么 | 看不见什么 |
| --- | --- | --- | --- |
| 只读产出元信息 | 表数 × 采集频率 | 新鲜度、体积、有无产出 | 值错、分布漂移（行数正常但值全错） |
| 读数据内容（全量） | **总行数 × 列数 × 频率** | 值错、分布、取值域、关系完整性 | 结构变更本身（要另接事件） |
| 读数据内容（抽样） | 总行数 × 采样率 × 列数 × 频率 | 同上，但检出能力有下界（见下） | 低于检出下界的污染 |
| 流式过程量 | 分区数 × 窗口数 | 延迟累积、堵塞、反压 | 批侧产出完整性、下游消费 |
| 元数据 / 血缘事件 | 事件数（与数据体积无关） | 结构变更、依赖变化、Owner 变化 | 值错、分布漂移 |

**由此必然导出的性质（因果句）**：因为**「读内容」的采集成本随行数走，而「读产出元信息」的成本随表数走**，所以在 PB 级资产上「全量字段级采集」不可能持续——**唯一现实的交易是把读内容的采集限定在关键字段，其余交给结构事件与分布摘要**（§3.3）。这条推算也解释了为什么「覆盖全量资产」与「覆盖全量字段」经常被混为一谈：前者只读元信息、成本随表数线性增长，后者要扫内容、成本随行数增长，两者不是一个量级。

**抽样能覆盖的失效有一个可算的下界**【推算】。设表有 N 行、采样率 s，则样本量 n = s × N；若表内污染比例为 r，样本里的期望污染数 λ = n × r。以 N = 1 亿行、s = 1% 为例，样本量 n = 10⁶ 行：

- 要让样本中的期望污染数达到 10（足以稳定判定），需要 r ≥ 10 / 10⁶ = 10⁻⁵，即表内至少约 10³ 行被污染（10⁻⁵ × 10⁸ = 10³）；
- 若污染比例降到百万分之一（10⁻⁶），样本中的期望污染数只有 1，而泊松分布下 λ = 1 时「本轮一条都没看到」的概率约为 e⁻¹ ≈ 37%；
- 若降到千万分之一（10⁻⁷），期望污染数为 0.1，**九成以上的轮次什么都看不到**（P(0) = e^(−0.1) ≈ 90%）。

**结论：采样式监控的覆盖能力有一个由采样率与表规模共同决定的检出下界，低于它就变成「污染真的存在、而面板是绿的」。** 这条下界是可算的，所以「要不要提高采样率」是一道成本题，不是偏好题。

**证据与来源**【经验】：本书 §3.2.1 给出「只读产出元信息」的采集结构（成本 ∝ 表数而非行数），§3.2.3 给出「判定不读值」的事件结构，§3.2.4 给出流式过程量的观测点；三者均可在该节自行核到，本节不重复其结构。这三条是本书自己的结构判断而非外部出处，故按【经验】使用。抽样检出下界所用的是比例与泊松分布的基本性质（通用统计方法，不含年份主张），推导链已写在正文，读者可按自己的表规模与采样率代入复算。

**失效条件**：当表规模小、或污染是「整批错」而不是「少数行错」时，抽样完全够用——**抽样损害的是低比例污染的检出能力，而不是一般意义上的准确性**。判断方法：问「这次故障会影响的行占比是多少」，占比越低，采样越不可靠。

**失效的早期信号**：没人能说出当前采样率是多少；或者有人用「我们监控了所有表」来回答「这张表的值会不会出错」——前者说的是元信息覆盖，后者问的是内容覆盖。

#### 7.3.3 判定单元：越早发现与噪声下限是同一个参数

**机制是什么**：判定必须等输入存在之后才能发生。**判定单元**（表 + 批次、分区 + 时间窗口、字段 + 值分布）决定了这个「最早能判出来的时刻」，也就决定了 MTTD 的下界——它不由算法决定，由结构决定。

**它在各类判定单元上的实现差异**：

| 判定单元 | 最早能判出的时刻 | 噪声下限由什么决定 | 典型误报形态 |
| --- | --- | --- | --- |
| 表 + 批次（T+1） | 下一批产出之后（小时到天） | 产出节律的方差 | 大促 / 节假日的正常波动被报成故障 |
| 表 + 小时 | 每小时结束时 | 同上，但窗口更短，每轮样本更少 | 短时抖动 |
| 分区 + 时间窗口（流式） | 窗口内（分钟级） | **窗口越小，单位时间判定次数越多，噪声下限越高** | 流量毛刺、上游重放 |
| 字段 + 值分布 | 取决于内容采集频率 | 抽样误差（即 7.3.2 的检出下界） | 长尾取值被当成异常 |

**由此必然导出的性质（因果句）**：因为**判定必须等到它的输入存在**，所以 MTTD 的下界与判定单元同构——表 + 批次的下界是一个批次（小时到天），分区 + 窗口的下界是一个窗口（分钟）。**代价是判定单元变小并不能单向地"更灵敏"**：单元越小，单位时间内的判定次数越多，噪声下限同时抬高，调到某个点之后值班开始把这类告警一眼关掉（§3.2.1 的失效的早期信号）。**「采得越密越灵敏」是一个只看到一半的直觉**：窗口大小是同时控制 MTTD 与噪声的同一个旋钮。

**这条机制在批量与实时之间划出硬边界**：实时链路里没有「批次产出完成」这个可对齐的时点，按「表 + 天」采指标的做法连判定单元都找不到，只能把单元换成分区 + 窗口（§3.2.4）；而反过来，把一个 T+1 的批任务硬套分区级判定，只会产生一堆在批次产出之前就已经判定完毕的噪声。

**证据与来源**【经验】：本书 §3.1 的约束表把「判定单元」列为决定 MTTD 下界与噪声下限的那一条约束，§3.2.4 给出流式判定单元（分区 + 窗口）的结构与它的失效点；判定入口是各节自己的结构示意与失效条件。这一条全部来自本书内部小节，本节不为它补外部数字，也不把它计入【公开】档。

**失效条件**：当业务的「坏」不以分钟计（例如日报、月度对账）时，把判定单元压到窗口级只会增加噪声与采集开销，不会更快发现真正的问题——**判定单元应当与「业务什么时候会因此受损」对齐，而不是与采集能力对齐**。

**失效的早期信号**：值班开始出现「这条告警每逢整点就来，看一眼就关」的行为；或团队把窗口调小之后误报变多，而处理方式是把阈值往上调（这等于用噪声换灵敏度，两边都在损失）。

#### 7.3.4 告警收敛与归因：血缘在不在链路上

**机制是什么**：一个上游故障会在它的每一个下游各产生一条告警。**有没有血缘、血缘做到什么粒度，决定这些告警是收敛成一条根因，还是变成 N 个同时叫醒 N 个人的警报。**

**它在各血缘状态下的实现差异**：

| 血缘状态 | 告警形态 | 定位方式 | 误报成本 | 归因输出 |
| --- | --- | --- | --- | --- |
| 无血缘 | 扇出 N 条 | 逐个排查（先查依赖再查数据） | N 倍人工分诊 | 只能靠人 |
| 表级血缘 | 收敛到表 | 沿表逐层排除 | 略降 | 表级候选根因 |
| 字段级血缘 | 收敛到字段 | 递归下游 + 责任定位 | 显著下降（前提是覆盖可信） | 字段级候选根因 |
| 血缘过期 | 收敛到**过去的拓扑** | 越走越偏 | **比没有血缘更贵** | 方向看似合理的错误答案 |

**由此必然导出的性质（因果句）**：因为**告警条数随血缘图的扇出放大，而人的处理能力近似常数**，所以没有血缘时「告警数量超过处理能力」是必然结果——**这不是配置问题，是拓扑问题**（§3.5 把「只看指标不看血缘」与「指标过多导致告警疲劳」列为两条反模式，机制上它们是同一条）。【推算】以一个扇出 20 的核心字段、每天 3 次根因故障为例：无血缘时每天产生约 20 × 3 = 60 条告警，有血缘并收敛后是 3 条；按每条分诊 3–5 分钟【经验：代入自己团队的值】计，差值 ≈ 57 × 4 ≈ **228 分钟 ≈ 3.8 人时/天**。**这个数字是上界**：§3.2.5 已指出，被抑制掉的往往是本来就一眼能看出的那一类，实际节省低于它——把它当成收益上限，而不是承诺。

反过来，因为**归因链的输出形态是「一个带解释的结论」**，它的可信度会超过它实际携带的信息量：血缘过期时，归因不会降级成「不知道」，而是给出一个方向看似合理的错误答案，团队顺着它排查的时间比没有它更长。**「错误的自信心比没有结论更贵」不是修辞，它是归因链的输入（血缘新鲜度）必须被当成一等指标的理由。**

**证据与来源**【经验】：本书 §3.2.5 给出 AIOps 三条链（判定 / 归因 / 处置）的风险分级与「错误归因比没有结论更贵」的判断；[§ 5 前沿演进](04-observability-section-5-ai.md) §5.3 给出归因链对血缘的硬依赖（字段级下游查询是归因的硬前置），§5.4 说明该方向缺少非厂商的公开生产案例。**本章沿用这两处的判断；它们都是本书内部小节，故按【经验】使用，不另引外部数字。**

**失效条件**：当依赖关系还在「能画在一张纸上」的规模（单团队、十几张表）时，人工定位比建图更快——此时血缘链路的采集器与图存储是净成本。

**失效的早期信号**：值班先看归因给出的解释、再决定查不查原始指标（§3.2.5）；或修复之后没人回头核对当初的归因对不对——归因正确率从未被度量过。

### 7.4 成本结构对比（不是价格表，是成本函数）

各候选族的成本函数**形状不同**。写成统一形式：

```
月成本 ≈ 采集查询算力(表数 × 频率 × 是否读内容：读内容则 ∝ 总行数 × 列数 × 频率)
        + 基线与检测算力(序列数 × 模型复杂度)
        + 存储(时序序列数 × 保留窗口 + 元数据事件数 × 保留窗口 + 采样快照)
        + 告警与值班(告警条数 ÷ 收敛率 × 每条分诊时间 + oncall 排班)
        + 订阅费(按被监控资产数或用量分档)
        + 处置成本(回刷的算力 + 下游重算)
```

**每一项的主导者不同**：

| 候选族 | 主导项 | 隐性项（最容易漏算） | 资产数翻 10 倍时的行为 |
| --- | --- | --- | --- |
| 族一（规则式） | 写规则与维护规则的人力 | **规则失效后的返工**（口径改了规则不改，面板继续绿） | 线性；但覆盖范围不随资产数扩展，只随规则数扩展 |
| 族二 · 自建 | 采集查询算力 + 时序基数 | 检测逻辑的训练与调参是一条常驻工程线 | 近似线性（表数），读内容的部分超线性（行数） |
| 族二 · SaaS | 订阅费 + **采集查询落在自己仓库的算力** | 跨客户基线的同构前提 | 超线性（订阅通常按资产数分档，采集算力记在自己账上） |
| 族三（事件式） | 采集器覆盖（每源一个解析器 / 事件契约） | 事件表随变更次数无界增长，需要自己的保留与归档策略 | 线性于事件数，与数据体积无关——这是它最便宜的地方 |
| 族四（流式） | 时序基数的内存与窗口计算 | 观测链路自身的容量与降级（峰值时它不能先崩） | 线性于分区数 × 窗口数，与表数无关 |
| 族五（归因与处置） | 模型维护 + 误报分诊 | 归因正确率从未被度量 | 取决于前几族的输出，本身不随资产数增长 |

**「自建还是订阅」的分界不是某个固定预算，而是两个数的比较**【推算】。自建侧：可观测平台通常需要 **2–4 人**长期维护（采集器、检测、告警路由、值班工具，各自都要有人负责），按【经验】一线城市资深工程师全成本 **60–120 万元/年/人**代入，得年成本约 **120–480 万元**（2 × 60 = 120，4 × 120 = 480）。订阅侧：报价通常按被监控资产数或用量分档【经验：具体口径以各家官方页为准】。**所以正确的分界是「订阅年费」与「自建团队年成本」谁大，而不是「预算是否超过某个数」**——后者随人数走、前者随资产数走，两者相交的位置在各个组织里都不同：资产数少时订阅摊薄了软件研发，资产数多、长尾数据源多时自建更划算（因为 SaaS 的自动覆盖上限受同构比例约束，长尾部分要人工补规则，补规则的人力又是自建侧的那笔成本）。

**两个最容易被漏算的项**：

- **采集查询记在谁的账上**。SaaS 的探针每轮都要对你的数仓发一次真实查询，这笔计算钱记在你的账单上；采集者与被打扰者是两拨人，所以它常常直到 DBA 投诉慢查询榜才被发现（§3.5 反模式 3）。**判定方法：把采集查询单独打上标签，看它占你数仓算力的比例。**
- **索引与序列的常驻开销**。时序库的开销主要随**活跃序列数**增长（资产数 × 指标数），而不是随数据总量增长；元数据侧同理。**判定方法：算一遍「资产数 × 每资产指标数」，再查你所用时序库文档里的基数上限并用一次压测确认——不要用存储单价去估它。**

**规则式还有一个反直觉的成本特征**：它的成本在「写完规则」之后才真正开始。口径变了规则要改、上游结构变了规则要改、规则多了没人删，而**规则集的维护成本随「资产数 × 变更频率」同时增长，覆盖范围却不随之增长**——这是它与基线式最本质的成本差异：基线式的维护成本主要在采集工程（一次建设、随源扩展），规则式的维护成本在内容（持续投入、只覆盖写下的部分）。

### 7.5 决策树（每个分支都要有阈值依据）

```
[你要防的是"已知失效"还是"未知偏移"？]
   │
   ├─ 已知失效（口径、非空、唯一、值域、引用完整性）
   │     └─ 规则式（Great Expectations / Soda / dbt tests / Apache Griffin）
   │           └─ [规则的执行要读数据内容吗？]
   │                 读 → 只对关键字段开；其余交给结构事件与分布摘要（7.3.2 的下界）
   │
   └─ 未知偏移（分布漂移、体积突变、新鲜度异常、结构变更）
         │
         ├─ [有可用的历史基线吗？]
         │     ├─ 没有 / 不想养采集工程 → 基线式 SaaS（Monte Carlo / Bigeye / Anomalo / Mona）
         │     │        └─ [核心表与公开同类表同构的比例高吗？]
         │     │              低 → 自动覆盖上限低，必须补人工规则（规则式与它并存）
         │     └─ 有 → 自建指标 + 时序 + 异常检测（Prometheus 一类 + 统计阈值）
         │            └─ [要求覆盖"全量资产"吗？]
         │                 是 → 叠加事件式（DataHub + OpenLineage）：它不读内容也覆盖全量
         │                 否 → 关键资产的指标即可
         │
         └─ [链路里有"批次产出完成"这个可对齐的时点吗？]
              没有 → 判定单元换成"分区 + 窗口"（Flink + Prometheus 一类），
                     并把 SLO 从 lag 改成端到端时间（7.3.3）

[要不要开归因链与处置链？]
   ├─ 归因 → 可开；前置条件：血缘可信、新鲜度可度量、归因正确率被度量（7.3.4）
   └─ 处置 → 先有回滚条件、幂等要求与变更审批；三者缺一不开（§3.2.5 的三条链）
```

**阈值依据**（树上每个判断节点在此各有一条，逐条对应）：

- **「你要防的是已知失效还是未知偏移？」**：依据 7.3.1 的判定输入差异——规则覆盖你已经想到的失效，基线覆盖你没想到的偏移，事件覆盖结构变化。**这不是规模阈值而是性质阈值**；判定方法：把最近三次数据事故列出来，看它们有没有被当时已有的规则覆盖——一次都没有，说明缺的是基线而不是更多规则。
- **「规则的执行要读数据内容吗？」**：依据 7.3.2 的成本形状与检出下界。判定方法：为每条规则写下它的执行频率与它扫过的行数，把「读内容」的规则限制在关键字段上；污染比例低于检出下界的那类失效，只能靠提高采样率或改用全量断言。
- **「有可用的历史基线吗？」**：依据 §3.2.1 的冷启动约束——新表在攒够历史之前只有规则可用。判定方法：问「最近新增的一张表，接入当天能报出什么」；答「什么都报不出」时，先上规则，不要先上 SaaS。
- **「核心表与公开同类表同构的比例高吗？」**：依据 §3.2.2 的跨客户基线前提。【推算】它是一次自查分类而不是测量值：把核心表按「有标准主键 / 时间分区 / 常见结构」与「结构特殊、口径在本团队脑子里」分成两类，**第一类的占比就是自动基线能覆盖的上限**，第二类必须靠人工规则补。
- **「要求覆盖全量资产吗？」**：依据 7.3.2——不读内容的采集成本随表数走，读内容的随行数走。因此「全量」这个要求本身就排除了「靠读内容实现它」这条路，只能靠事件式与元信息式。
- **「链路里有『批次产出完成』这个时点吗？」**：依据 7.3.3 的判定单元。判定方法：看现在的 SLO 是用 `consumer lag` 表达，还是用「用户从发起到拿到结果」的端到端时间表达——前者说明判定单元还没换过来（§3.2.4 的失效点）。
- **「血缘可信、新鲜度可度量吗？」**：依据 7.3.4——血缘过期时归因给出的不是「不知道」，而是一个方向看似合理的错误答案。判定方法：血缘有没有最后更新时间、最近一次拓扑变化是否被记录、归因正确率有没有被度量过（三个里有一个答不上，就先只开判定链）。
- **「有没有回滚条件？」**：依据 §3.2.5 的三条链风险量级——判定错是噪声，归因错是指错方向，处置错是改坏生产。**处置链的前置是幂等 + 回滚条件 + 变更审批，三者缺一就不开自动处置**。

> 上树之前先做三项验证（都比选工具更重要）：① **把采集查询单独打标签，看它占你数仓算力多少**——这项成本记在别人账上（7.4）；② **算一遍「资产数 × 每资产指标数」并核对时序库的基数上限**——序列基数是这一族最先撞上的墙；③ **拿最近三次数据事故，看它们各自是被「规则」「指标」还是「业务方电话」发现的**——如果不是规则也不是指标发现的，缺的是可见性，不是检测能力（§3.3 的判据）。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 表数百级、有稳定批次节律 | 规则式（Great Expectations / Soda / dbt tests）+ 指标时序 | 直接上 SaaS | 这个规模下 SaaS 的采集账单换不来额外信息，且新表本来就没有基线可学 |
| 表数万级、Schema 变更频繁 | 事件式（DataHub + OpenLineage）+ 指标时序 | 纯指标式 | 结构变更不体现在行数与新鲜度上，纯指标看不见它 |
| 实时链路、没有「批次产出完成」的时点 | 分区 + 窗口判定（Flink + Prometheus 一类） | 把批侧判定周期缩短 | 判定单元不存在时，缩短周期只是在做更频繁的错误判定 |
| 没有历史基线、也不想养采集工程 | 基线式 SaaS（Monte Carlo / Bigeye / Anomalo / Mona） | 自建 + 规则起步 | 自建在冷启动期用不上（没有基线），而它的人力成本是 2–4 人量级（7.4） |
| AI 训练数据、要盯分布漂移 | 基线式（数仓自带或 SaaS）+ 规则守住底线 | 纯规则 | 漂移是分布层面的问题，规则写不出「多偏算偏」 |
| 多业务线 / 跨域资产 | 事件式（结构与血缘统一）+ 域内各自的指标 | 全量统一采集指标 | 跨域能共享的通常只有结构事件与血缘这类轻量元数据，指标留在域内 |
| 告警量已超过处理能力 | 先补血缘（表级 → 字段级）再谈 AIOps | 先上归因链 | 没有依赖图时归因链的输出不可检验，错误的自信心比没有结论更贵 |
| 合规要求「哪些表含敏感字段、谁能访问」 | 事件式 + 规则（确定的事实） | 纯统计检测 | 合规要的是确定的事实，不是「看起来正常」 |

**常见组合**：

1. **Monte Carlo + DataHub + PagerDuty**：构成——SaaS 侧做指标检测与异常判定，DataHub 提供元数据与血缘用于排影响面，PagerDuty 把告警路由到 oncall。职责边界——判定归 SaaS，**影响面与责任人归元数据平台**，路由与升级归值班系统；判定结果不得反过来改写血缘。运维代价——两套资产标识必须对齐（否则告警收敛不到同一张表上）；PagerDuty 一侧要有明确的排班与升级策略，没有 oncall 的告警只是通知（§3.5 反模式 6）。【经验】
2. **Prometheus + Grafana + Great Expectations**：构成——Prometheus 采指标与时序，Grafana 做可视化与阈值告警，Great Expectations 在批处理管线里跑逐列断言。职责边界——Prometheus 回答「有没有按时产出、量对不对」，GE 回答「值对不对」；**两者必须共用同一套资产标识**，否则同一张表在两张面板上会给出两个结论。运维代价——两条采集链路、两套存储，且采集查询要单独限流，避免与业务查询抢资源（§3.5 反模式 3）。【经验】
3. **Mona + Snowflake + Anthropic**：构成——Mona 做质量监控与异常解释，Snowflake 既是被观测的数仓也是采集查询的执行地，Anthropic 一类模型服务把异常翻译成自然语言说明。职责边界——模型只做**解释与建议**，不做判定也不做处置；判定仍是指标与阈值，处置仍是人或受控的自动化。运维代价——每条解释都要能点回一条原始指标或规则，否则它会以「格式完整的错误结论」出现；用模型解释异常本身的调用成本随提问量增长。【经验】
4. **自研（Prometheus + OpenLineage + AIOps）**：构成——Prometheus 出指标，OpenLineage 出作业运行的事件与血缘，AIOps 在其上做异常检测与归因。职责边界——OpenLineage 只提供事件契约，血缘的可信度由采集覆盖与新鲜度决定；AIOps 的归因链**只在血缘可信时开启**。运维代价——三条链要分别启用、分别度量失败率；处置链在具备回滚条件与幂等要求之前不开（§3.2.5）。【经验】
5. **规则式 + 采样读内容 + 分区级流式（新增）**：构成——关键字段走规则与全量断言（精确、上线即生效），其余字段走低采样率的内容采集（看分布与趋势），实时链路走分区 + 窗口判定。职责边界——三者覆盖的失效类型互不重叠：已知规则、未知偏移、过程量异常；**冲突时以规则为准**（[§ 5 前沿演进](04-observability-section-5-ai.md) §5.3 的判定）。运维代价——每个数据源要维护两到三条采集路径，且各自的采样率与窗口都要有人设定并定期复核，否则会出现「规则说没问题、采样说分布漂了」这种没人裁的争议。【经验】

> 组合的第一原则是**让每一件做它机制上最擅长的事**：规则守已知底线，基线发现未知偏移，事件盯结构变化，血缘负责收敛，值班负责闭环。第二原则是**组合数不超过团队的运维带宽**——上面 5 条里每多一件，就多一处「同一张表在两张面板上给出两个结论」的战场。凡是「两个系统都要能回答同一个问题」的组合，最终都会变成口径不一致的战场。
>
> 「判定 / 影响面 / 路由」这个三分本身也是有机制依据的：判定只依赖指标与历史，影响面只依赖血缘，路由只依赖值班表——三者之中任何一个失效，另外两个仍然工作；把它们塞进同一个平台，一次故障就会同时带走三件事。

### 7.7 选错的代价与迁移成本

**反模式：用规则覆盖率冒充观测覆盖率** —— 症状：面板全绿，团队宣称「已覆盖全量资产」，而覆盖率指标的分子与分母都是「已写规则的字段数」。后果：没写规则的地方一律是绿的，**你没想到的失效恰好全部落在那里**（7.3.1）；等业务方打电话时故障已经发生数小时。正确的做法：把「规则覆盖率」与「资产发现覆盖率」拆成两个指标分别看——前者衡量你写下了多少期望，后者衡量你知道有多少资产；并且只对前者许下承诺。

**反模式：先开归因链与处置链，再补血缘** —— 症状：异常检测上线后直接叠加自动归因与自动处置，血缘还没建或已经过期。后果：归因给出方向看似合理的错误答案（7.3.4），处置在没有回滚条件的情况下改坏生产——**判定错只是浪费注意力，处置错不可逆**（§3.2.5 的三条链）。正确的做法：判定链可以先上，归因链以血缘可信为前置，处置链以幂等 + 回滚条件 + 变更审批为前置；三条链分别度量失败率。

**反模式：用 `consumer lag` 表达 SLO** —— 症状：实时链路的 SLO 定义在队列长度上，「队列不堵」被视为正常。后果：慢但不堵时端到端延迟已在累积而无人报警——用户等的时间由排队 + 处理 + 重试 + 下游共同决定，其中最慢的一段常常不在这条链路上（§3.2.4 的失效点）。正确的做法：SLO 用「用户从发起到拿到结果」的端到端时间表达，过程量只用于定位与预警，不用来定义故障。

**反模式：靠调阈值压误报** —— 症状：告警一来就调松阈值，从 3σ 调到 5σ，面板安静了。后果：阈值与数据在同一时刻失效，而失效本身不产生告警——**静默漏报比误报更贵**（§3.5 反模式 2）。正确的做法：把误报率作为被度量的指标，按节律建模（工作日 / 周末 / 大促）而不是拉大倍数；对确实无法建模的指标改用人写规则作为底线。

| 迁移方向 | 规则与配置迁移 | 查询与接口改写 | 运维重建 | 团队再学习 | 量级（【经验】） |
| --- | --- | --- | --- | --- | --- |
| 规则式 → 基线式 SaaS | 规则保留（作为底线），另接采集探针 | 告警入口从自有系统改为厂商侧 | 需开通采集权限与网络出网 | 中 | 周到月级 |
| 自建指标 → SaaS | 历史基线需重建（SaaS 侧重新学习） | 看板与告警路由需重建 | 采集查询从自建链路换成厂商探针 | 中 | 月级 |
| 批量判定 → 分区 + 窗口 | 判定逻辑需按窗口重写 | SLO 口径从 lag 换成端到端时间 | 需引入流式观测链路并做峰值降级 | 高（判定单元变了） | 月级到季级 |
| 无血缘 → 表级血缘 | 无需迁移 | 告警模板需带上上游与下游 | 需接入解析器或事件采集 | 中 | 月级 |
| 表级血缘 → 字段级血缘 | 无需迁移 | 影响面查询与门禁需按字段改写 | 需维护 SQL 解析器与定时校准 | 高 | 月级到季级 |
| 只开判定链 → 加归因链 | 无需迁移 | 需接血缘接口并暴露新鲜度 | 需度量归因正确率并有人对结果负责 | 高（从装工具变成定责） | 季级 |
| 观测区与证据区混用 → 分开存储 | 留痕需分流 | 查询需区分观测与取证两类入口 | 需两套保留策略与访问控制 | 中 | 月级 |

> 注意「批量判定 → 分区 + 窗口」这一行：它不是把采集频率调高，而是**换掉判定单元并连带改掉 SLO 的表达方式**——判定单元变了，判定结果的含义也变了，两者必须同时改，否则会出现「所有指标都正常而用户一直在等」的状态。**本主题迁移的主要工作量从来不在采集器上，而在重新定义「什么算正常」以及谁为这个定义负责。**

### 7.8 小结

数据可观测性选型的特殊性在于：**它选的不是「哪个工具更准」，而是「『正常』这个参照物从哪里来、以及为它付账的是谁」**。所有候选的差异都可以收到一条上——**参照物是人写下的期望、从历史学出的基线，还是事件的有无**。规则式（Great Expectations / Soda / dbt tests / Griffin）换来上线当天精确、误差可控，代价是覆盖率的上限就是你写下的规则数；基线式（自研时序统计与 Monte Carlo / Bigeye / Anomalo / Mona 一类）换来覆盖面随数据自己扩展，代价是它需要历史、且要求你的表与它所学的分布同构，同时采集查询记在你的仓库账上；事件式（DataHub / OpenLineage）换来「不读内容也覆盖全量资产」，代价是「没有事件」被读成「没有异常」；流式（分区 + 窗口）换来分钟级的 MTTD，代价是噪声下限随窗口缩小而抬高；归因与处置式（AIOps、APM 厂商的 AI 能力、用模型做解释）换来「从告警到根因」的那一跳，代价是它对血缘的依赖与「错误的自信心比没有结论更贵」。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 表数百级、有稳定批次节律 | 规则式 + 指标时序 | 规则上线即生效；这个规模下 SaaS 的采集账单换不来额外信息 |
| 表数万级、结构变更频繁 | 事件式 + 指标时序 | 结构变更不体现在值与行数上，只有事件看得见 |
| 没有历史基线、不想养采集工程 | 基线式 SaaS | 基线由厂商跨客户学，冷启动近零；代价是采集查询记在自己账上 |
| 核心表结构特殊、口径在本团队脑子里 | 规则式为主，SaaS 只作补充 | 跨客户基线的覆盖上限受同构比例约束，特殊结构只能人工写规则 |
| 要求覆盖全量资产 | 元信息 + 事件式（不读内容） | 读内容的成本随行数走，全量读内容在 PB 级不可能持续 |
| 污染比例低于采样检出下界 r < 10 / (s × N)（如 N = 1 亿行、s = 1% 时 r < 10⁻⁵） | 全量断言或提高采样率 | 采样检出下界由采样率与表规模共同决定，低于下界就是「面板绿而污染存在」 |
| 实时链路、SLO 还在用 lag 表达 | 分区 + 窗口判定 + 端到端 SLO | 判定单元不存在时，任何检测都判在错误的对象上 |
| 告警量已超过处理能力 | 先补血缘（表级 → 字段级）收敛告警 | 告警条数随扇出放大而人的处理能力是常数，这是拓扑问题不是配置问题 |
| 想开自动归因 / 自动处置 | 血缘可信 + 正确率可度量 → 才开归因；幂等 + 回滚条件 → 才开处置 | 判定错是噪声，归因错是指错方向，处置错是改坏生产，三条链风险量级不同 |

> 本节小结：本章所有候选之间，**唯一真正起决定作用的差异是「『正常』这个参照物从哪里来」**——它同时决定了能覆盖哪一类失效（已知 / 未知 / 结构）、能覆盖多大比例的资产（规则数 / 历史 / 事件数）、误报由谁付账（写规则的人 / 值班的人 / 你的数仓账单），以及整条链上能自动化到哪一步（判定可以外包，归因要有人核对，处置要先有回滚条件）。其余维度（自动化程度、AI 能力、界面体验）都是在确定了参照物来源与账单位置之后才需要精算的第二层问题；先算这份账，再谈工具。
>
> 💡 **思考锚点**：本节给抽样检出下界一个可算的式子——N = 1 亿行、采样率 1% 时样本量 n = 10⁶，污染比例降到百万分之一（10⁻⁶），样本里的期望污染数只有 1，一轮什么都没看到的概率约 37%。把你的表规模与**当前采样率**代进去算一次：你的 λ 落在哪一档？它决定了「面板绿」到底是数据健康，还是你既没写规则、历史又不够时长、事件源也没接上时留下的那一整类盲区。
>
