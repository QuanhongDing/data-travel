## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

一份没有时间维度的清单，最危险的地方不是它写错了，而是它把「已经有人在生产里跑」和「路线图里的条目」并列在同一列里——读者据此排路线图，会把预算押在明年才可能出现的东西上。本节对每个方向标注 L1 / L2 / L3，判据只有三条且必须**同时成立**才算 L1：

1. **已 GA 且有正式 release note**（能说出文档或版本页的名字，而不是「官网写了」）；
2. **有第三方（非厂商）公开生产案例**（厂商自述的客户故事不算）；
3. **接口稳定**（可迁移、可替换，不随某一次模型或版本升级而变）。

**三条全中才算 L1 生产可用**，可以排进路线图；**已可用、但接口或生态未稳，或只有厂商自有案例（含只在小范围被验证）的，记 L2 可试点**，可以做 PoC、不要做核心依赖；**只有路线图、论文或厂商演示的记 L3 观望**，记录即可、不要在架构里预留假设。L1 不是形容词：核不到第②条就是 L2，本节不写「准 L1」「L1 的边界案例」这类放宽，**也不对本主题的 L1 判据做任何修正**——若某方向确实需要不同判据，那是本节判错了方向，不是判据需要改。

本主题还有一层别人没有的分层方法：AI 在可观测性里的全部落点，都落在三条链上——**判定链（该不该报）、归因链（源在哪）、处置链（要不要动手）**（见 [§ 3 设计模式与范式](04-observability-section-3-sec3.md) §3.2.5）。三条链的错误代价差一个量级：判定链错了只是多一条告警，归因链错了会把排查引向错误方向，处置链错了就是改坏生产。因此本节对它们的评级天然不同，不能用一句「AIOps 成熟了」概括；同一份原始清单里的「AIOps 全面接管」在本节被拆成判定链 L2、处置链 L3 两个级别，正是这个原因。

还有一条取材纪律必须写在前面：本节不把厂商公告与产品页当作技术事实，凡涉及「某产品是否支持某特性」的说法，一律改写成读者可自行核验的判定方法（按官方文档或 release note 的名称检索即可）。因此**凡是给不出「非厂商公开生产案例」的方向，本节一律标 L2 而不是 L1**——给不出来源既不是「不存在」的证据，也不是「是真的」的证据。对每个方向，本节给出读者可以自己执行的判定方法（在 5.2 各方向末尾），而不是替读者下结论。凡涉及工具能力的地方，本节只写「哪一类工具、能力以谁家文档为准」，不写「某产品支持某特性」；凡涉及版本，只写可核验的年份区间。

本节全篇的数字与事实按三档标注：**【公开】**给出来源与年份，读者可自行核验；**【推算】**写出完整推导链，读者可以复算到同一个数；**【经验】**只给量级与区间，用于那些本节无法核到公开出处的判断。需要强调的是：「核不到」不构成本节下调任何**事实**档位的依据，也不构成上调的依据——它只影响**成熟度评级**，因为 L1 的第②条要求的是一个能被指出来的第三方来源，而不是一个「大概存在」的印象。

本节与 [§ 3 设计模式与范式](04-observability-section-3-sec3.md) 的分工是明确的：§3 讲五种模式各自受什么约束、代价落在谁头上；本节只回答一个问题——**这些方向里，哪些现在可以花钱，哪些只能记录**。因此本节不重复模式结构，只在必要处指回 §3。

最后说明本节与原 §5 的关系：原 §5 的四个方向与七条趋势，在本节都有落点——或被归入 5.2 的四个方向，或被移入 5.5「被过度宣传的部分」，或在 5.1 的表里被逐条合并评级；原 §5.2 点名的五个 LLM 可观测性工具里，Langfuse、LangSmith、Arize Phoenix、Helicone 保留在 5.2.2 的证据行里，Datadog LLM Observability 保留在 5.2.4 的证据行里；原 §5.3 工业条目里点到的产品名（Monte Carlo、Anomalo、Mona）保留在 5.2.1 的证据行里。**唯一没有逐条复述的是原 §5.3 的条目本身**——三条学术引用（2024 VLDB 时序异常检测、2024 SIGMOD LLM 驱动根因分析、2025 ICDE AIOps for Data Engineering）与那批「某年某月某厂商发布某能力」的条目（收购、GA、某云推出某能力）都没有逐条搬过来：前者只有会议与年份、没有论文标题，后者是**厂商发布**而不是方向，本节按 5.4 末段的取材纪律只保留可核验的方法与规范，原因见 5.4。被合并的是评级，不是方向本身——例如原清单同一段里的「自动异常检测」与「自动归因」，在本节是同一方向下的两种能力：级别相同（L2），代价不同（一个浪费注意力，一个带偏排查方向）。

### 5.2 演进方向逐条拆解（核心节）

原 §5 的 4 个方向在这里一个不少，只是被重新安放到三条链上（第 4 个「LLM 应用自身的可观测性」对应原 §5.2）。以下每个方向都给出同样六行结构，外加两条读者可以自己执行的东西：**判定方法**（怎么核这个方向到底能不能用）与**失效的早期信号**（出了问题最早会从哪里看出来）。

| 本节方向 | 落在哪条链 | 对应原 §5 条目 | 级别 |
| --- | --- | --- | :---: |
| 5.2.1 ML 异常检测与告警收敛 | 判定链 + 归因链 | 原 5.1-1、5.4-1 | L2 |
| 5.2.2 自然语言查询 / Runbook / Postmortem | 只读的接口层 | 原 5.1-2、5.1-4、5.4-7 | L2 |
| 5.2.3 Agent 修复与预测性告警 | 处置链 | 原 5.1-1、5.1-3、5.4-1、5.4-5、5.4-6 | L3 |
| 5.2.4 LLM / RAG 应用自身的可观测性 | 对 AI 应用做判定 | 原 5.2 | L2 |

为什么把「读者能不能自己判」写进正文：AI 时代的可观测性材料里，绝大多数结论来自厂商页与演示，它们描述的是能力上限而不是生产现实。本节三条自查方法的共同点是**不需要任何外部数据**，只要你自己平台上的记录：告警台账、留痕库、自动处置的执行日志。

#### 5.2.1 判定链：ML 异常检测与告警收敛

- **旧做法与它的卡点**：3-sigma 与硬编码阈值。它卡在两处，且都不是算法问题——
  - **规则覆盖**：人工写规则只能覆盖少数关键字段，剩余字段没有「期望」可比；
  - **节律**：大促、活动日、上新会让「偏离历史窗口」反转成「正常波动全被报成故障」。
  - 两处的共同瓶颈是人：写规则的人和半夜被叫醒的人是同一批。
- **AI 改变了什么机制**：把「人写下期望」换成「从历史推断期望」，并把判定输出从布尔值换成连续分——于是「报得多 / 报得准」变成一个可以按运营节奏调节的旋钮，而不是只能开或关。
- **由此得到的**：因为采集只问「最大更新时间、行数」这类产出元信息、判定只用同一序列的历史窗口，单表采集代价与表的体积无关，覆盖全量资产的成本随**表数**而不是行数增长——这是「全量字段监控」在人工规则路线下做不到、在指标路线下做得到的原因。
- **由此付出的**：
  - 阈值成了藏在配置里的新硬编码，换模型或换历史窗口它就失效，而它不在文档里；
  - 这套判定**看不见「行数正常但值全错」**，要补这一层必须加读内容的采集，成本随行数走；
  - 误报的钱记在值班表上——阈值最终由「谁在半夜被叫醒」决定，而不是由算法决定；
  - 归因链的输入是血缘，血缘不全时它会给出**表述完整、方向错误**的候选根因。
- **证据与来源**：
  - 原 §5.3 工业条目里点到的 Monte Carlo、Anomalo、Mona，以及主文件 [04-observability.md](04-observability.md) 另点名的 Bigeye，均为真实存在的商业产品，具体能力与计费以各家官方文档为准【经验：产品存在性以原 §5.3 与主文件所列为准，本节未逐家核原文】；
  - 3-sigma、IQR、孤立森林属通用统计与机器学习方法，不归属任何厂商、也不对应某个版本年份，本节不把它们与任何产品线绑定【经验：方法名可直接检索，本节不在此列举各自的原始文献与年份】；
  - SLO 与错误预算这一承载面有公开的原始记述（Google 公开的 SRE 系列材料，2016 年起）；但该材料出自本领域厂商自身的实践，属自述而不是第三方案例，故这一行只能记 L2【公开：Google SRE 系列，2016 年起】。
  - **本节未核到「ML 异常检测在非厂商生产环境中的公开效果度量」**，故不标 L1。
- **与既有栈的接口**：判定链消费两样东西——指标时序（轮询得来）与结构事件（事件推送得来）。两者的时间轴不同，合并判定前必须先把时间戳口径对齐，否则会出现「事件已经在路上、指标还没采」的半状态误报。
- **成熟度**：**L2**。判据：产品已可用，但效果口径（误报率、分诊时间）无公开可核验来源，接口随模型替换而变。
- **判定方法（读者可自查）**：① 取最近 20 条该链路发出的告警，人肉标一遍真伪，得到本团队自己的误报率；② 把最大的一次误报日期与业务高峰日期对齐，看它是否正好落在节律上；③ 看阈值写在配置里还是写在文档里——只在配置里，说明它已经是一个隐形的硬编码。

| 判定单元 | 最早能发现的时点（MTTD 下界） | 噪声下界 | 采集成本随什么增长 |
| --- | --- | --- | --- |
| 表 + 批次 | 下一批产出之后 | 低 | 表数 |
| 分区 + 时间窗口 | 窗口内（分钟级） | 高 | 分区数 × 窗口数 |
| 字段 + 分布 | 读一次内容之后 | 中 | 行数 |

这里要拆掉一个常见的过度承诺：**「数据可观测性平台接上就有基线」**。基线实际来自「你的表与公开同类表的相似度」，不是凭空长出来的——跨表学习的强项是同类表之间的共性统计，而定制业务表的个性恰恰在共性之外；这类表接上后通常先安静几周，然后被调松到不再告警。它要成真，前提是自动基线只用来兜住标准表、定制表明确交给人工规则，且两者在同一个告警路由里被区分对待。

- **失效的早期信号**：值班开始出现「这条告警每周都来，看一眼就关」的行为；或者团队把阈值从 3σ 调到 5σ，而不是去改基线模型。

#### 5.2.2 LLM 辅助运维：自然语言查询、Runbook 与 Postmortem

- **旧做法与它的卡点**：oncall 查历史故障靠人翻文档与群记录，新人上手靠口头交接。卡点是**检索**而不是判断——答案大多已经写在 Runbook 与 Postmortem 里（这两者加上血缘，就是本主题事实上的可观测性知识库），只是没人找得到、找不全，而且写这些文档的人早就轮岗了。
- **AI 改变了什么机制**：把「人跨多个系统检索并拼装上下文」换成「一次检索 + 一次生成」（RAG 的典型形态）。**这是接口边界的改变，不是判定机制的改变**：判定仍然来自既有指标与规则，LLM 只把结果翻译成人话。
- **由此得到的**：因为生成层不参与判定，它可以整体失效而不影响告警链路——这使它成为本节里风险最低、可以先上的一类能力；也正因如此，它的收益上限被限死在「省检索时间」上，不要按「提升可靠性」立项。
- **由此付出的**：
  - 生成内容不是证据——同一个问题在下一个模型版本上答案不同，事故定性不能建立在它上面；
  - 检索库本身会过期：检索层判断的是相关性而不是新鲜度，三个月没人更新的 Runbook 会被稳定地检索出来并当作答案，而且它比没有答案更危险；
  - Postmortem 与故障上下文含生产拓扑、表名、事故细节，送进第三方 LLM 是新开的数据出口，必须单独评估；
  - 模型与供应商的替换成本落在 prompt 及其周边工程上，这部分不会随模型换代而消失；
  - 面向业务方（不值班的分析与运营）的自助问答把**解释权**从数据团队手里分出去：同一张表会出现第二套口径解释，而业务方拿到的答案没有资产 Owner 背书——把它当成「替代 oncall 的手段」立项，是这类项目最常见的失败方式。
- **证据与来源**：
  - Langfuse、LangSmith、Arize Phoenix、Helicone 为真实存在的 LLM 调用留痕与评估工具，能力以各自官方文档为准【经验：工具存在性以官方文档为准，本节未核原文】；
  - 用模型给生成质量打分这一做法有公开论文支撑：MT-Bench 与 Chatbot Arena 的 LLM-as-a-judge 方法（Zheng 等，NeurIPS 2023）【公开】。
  - **核不到这四类能力在非厂商生产环境中的公开效果**，故不标 L1。
- **与既有栈的接口**：输入是告警正文与血缘上下文（只读），输出是文本草稿——整个链路上没有任何写接口。这条边界本身就是它的安全来源；一旦给它加写入权限，它就掉进 5.2.3 的 L3 区间。
- **成熟度**：**L2**。判据：能力已可用（工具存在、接口是文本），但缺第三方生产案例；本节建议的准入条件是「每个回答都附带它引用到的 Runbook / Postmortem 条目 ID」。
- **判定方法（读者可自查）**：① 随便问一个已经有标准答案的历史故障，看它引用的条目是不是最新的那一版；② 把 Runbook 库的「最后更新时间」分布拉出来，超过一个季度没更新的条目占比就是这套能力的失效比例；③ 检查日志里有没有把完整 prompt 与事故上下文出到外部端点——有，就先补脱敏。

| 生成物 | 谁读它 | 出错的代价 | 本节建议的门槛 |
| --- | --- | --- | --- |
| Runbook 草稿 | oncall | 照错步骤操作，故障被扩大 | 人工确认后入库，标注生成时间与引用条目 |
| Postmortem 草稿 | 团队与管理层 | 事故定性偏差，复盘失真 | 只作初稿，结论段必须人工改写 |
| 异常解释 | 值班 | 排查方向被带偏 | 必须附所引用的指标与查询语句 |
| 自助查询回答 | 业务方（不值班的分析与运营） | 把生成的解释当成数据事实引用，绕过资产 Owner | 只读；只答「表 / 指标 / 资产是什么」，不答「能不能改」；不替代 oncall |

- **失效的早期信号**：团队开始直接抄它的答案而不点开引用来源；或者同一个问题一周内问三次得到三个不同答案，却没人当回事。

#### 5.2.3 处置链：Agent 修复、变更影响评估与预测性告警

- **旧做法与它的卡点**：回刷、回滚、重启、上游修复全靠人，夜间响应慢；变更影响面靠人去血缘系统里查。卡点是**权限与时间**：能改生产的人不在线，在线的人没有权限。
- **AI 改变了什么机制**：把「人判断 + 人执行」换成「模型建议 + 自动执行」——真正被改变的不是判断精度，而是**生产写权限的边界**。这是三条链里唯一不可逆的一步。
- **由此得到的**：因为最常见的几类故障（任务失败、批次未产出、上游迟迟不出数）的修复动作恰好是幂等且可枚举的（重跑、回滚、重启），这一窄区间里的动作可以在有自动回滚条件的前提下被自动化。
- **由此付出的**：
  - 判定错只是误报，处置错是改坏生产，两者不能共用一个开关；
  - 自动化的前置条件是幂等、回滚条件与变更审批，缺一个就变成「自动制造事故」；
  - 预测性告警一旦假阳性，消耗的是团队对整套告警的信任，而信任不容易挣回来；
  - 「错误的自信心比没有结论更贵」——一段自然语言的根因解释会被当成结论，团队顺着它排查的时间比没有它更长。
- **证据与来源**：**无公开可核验的非厂商生产案例**，公开材料以厂商演示与产品页为主，属 L3。判定方法：找一份**非厂商**发布的、含自动处置动作清单与回滚条件的生产复盘；找不到就不要把它写进架构假设。
- **与既有栈的接口**：它必须调用变更审批与回滚机制，而不是绕过它们——接口是「提交一次待审批的变更」而不是「直接改生产」。这两种接口形态对应完全不同的风险量级，选哪一种决定了这套东西是可试点的 L3 还是不可用。
- **成熟度**：**L3**（预测性可观测性、自适应修复同此）。唯一窄例外见 5.7 表中「万级表，指标与字段级血缘已可查」那一行的「明确不要做」：那一格写的是『不要把自动修复接到任何有对外 SLA 的链路上』，它的反面——**无对外 SLA 的链路**——才是这一窄区间可以试点的范围，且仍要带上自动回滚条件。
- **示意（三条链不能共用一个开关）**：

```text
① 判定链：指标/事件 → 检测 → 异常分 → 阈值 → 是否告警   错 = 报错告警（可容忍）
② 归因链：异常 + 血缘图 → 反向遍历 / 概率排序 → 候选根因   错 = 指错方向（昂贵）
③ 处置链：候选根因 → 建议动作 → 执行 → 校验 → 回滚条件     错 = 改坏生产（不可逆）
→ 可以外包：①；必须自己核对：②；没有回滚条件就不要开：③
```

- **判定方法（读者可自查）**：① 把候选自动动作逐条问一句「这个动作有没有幂等的回滚方式」，答不出来的动作就不该进自动化清单；② 看自动化的执行记录里有没有「已回滚」字段——没有这个字段，说明回滚条件只是口头约定；③ 用一次演练去验证：人为制造一次误判，看自动处置会不会真的动生产。
- **失效的早期信号**：自动处置的执行记录只有成功与失败两种状态，没有「已回滚」；或者团队开始跳过评审直接采纳 Agent 给出的变更评估结论。

#### 5.2.4 让 LLM / RAG 应用自己可观测：调用留痕、漂移与检索质量

- **旧做法与它的卡点**：传统 APM 的 trace 到不了「这次回答依据哪几份文档」，数据可观测性的五支柱也不覆盖「模型输出质量」。卡点是**判定对象不存在**：既有指标体系里没有「一次生成调用」这个单位，所以五大支柱的异常检测表里根本没有它对应的那一行。
- **AI 改变了什么机制**：把可观测对象从「表 + 批次」扩展到「一次调用 + 一个检索集」，判定单元里第一次出现 prompt、上下文文档 ID、token 与成本。这是**判定单元的扩展**，不是新算法的胜利。
- **由此得到的**：因为每次调用自带成本计量与上下文标识，成本与质量第一次可以按调用方、按租户归因——这让它是本节里唯一能立刻算出回报的部分（成本账本来就在）。
- **由此付出的**：
  - 留痕体量随调用量线性增长，单条比访问日志大一到两个数量级。**量级【推算】**：日均 10 万次调用、每条留痕约 4 KB（元数据 + 上下文摘要），则日增约 400 MB（10⁵ × 4 KB），一年约 146 GB（400 MB × 365 天）；若连完整 prompt 与输出一起存（均值约 20 KB），日增约 2 GB，一年约 730 GB——同一个系统留痕口径差 5 倍，而这 5 倍里装的正是最敏感的内容；
  - 留痕库自身成为新的敏感数据集合，需要自己的密级、访问控制与保留期；
  - 接口尚未稳定（见证据行），跨工具迁移要写适配器；
  - embedding 漂移与检索质量**没有统一的阈值口径**，「漂移多少算异常」目前只能自己定，而且要同时盯训练与推理两侧的特征定义是否一致。
- **证据与来源**：
  - OpenTelemetry 语义约定中已加入 `gen_ai.*` 一组属性（来源：OpenTelemetry Semantic Conventions 仓库，2024 年前后加入），该组属性在其仓库中被标注为实验性，**状态请以仓库当前版本为准**——这正是本节把它判为 L2 而不是 L1 的直接原因【公开：OpenTelemetry Semantic Conventions，2024 年前后】；
  - 检索质量评估已有公开方法（RAGAS 一类，arXiv 2023，会议收录情况以论文页为准）【经验：只取「该方向有公开可核验的方法」这一判断，不取具体指标值】；
  - 工具侧 Langfuse、LangSmith、Arize Phoenix、Helicone、Datadog LLM Observability 均为真实产品，能力以官方文档为准【经验】。
- **与既有栈的接口**：留痕库与审计证据区共用采集点但**分级存储**（见 5.3 与 [§ 7 审计与合规 §5 前沿演进](../07-audit-and-compliance/07-audit-and-compliance-section-5-ai.md)）；成本标签必须与数仓成本的标签口径一致，否则同一个租户在两张账单上对不上。
- **成熟度**：**L2**。判据：工具可用、成本归因已硬，但语义约定尚未稳定、跨工具无稳定契约，且核不到非厂商公开生产案例。
- **判定方法（读者可自查）**：① 拿一条真实的差评回答，看能否只靠留痕还原「读了哪些文档、用了哪个模型版本、花了多少 token」；② 把留痕库的存储策略与审计证据区的策略对照，两者的保留期是否已经分开；③ 抽查有没有把原始 prompt 与输出整体入库——那是本节里最大的一个敏感面。

| 判定项 | 判定输入 | 需要读数据内容吗 | 阈值口径现状 |
| --- | --- | --- | --- |
| 调用成本 | token 计数 | 否 | 直接计量，无需阈值 |
| Prompt / Response 内容监控 | 按采样取得的原始输入输出 | 是（读的是整套留痕里最敏感的内容） | 无统一口径；敏感词与 PII 需自定词表，判定结果按调用方归因 |
| 调用时延 | 起止时间戳 | 否 | 可做分位数，口径自定 |
| 检索质量 | 检索结果与标注 / 评审 | 是（读内容） | 无统一阈值 |
| Embedding 漂移 | 向量分布摘要 | 是（读向量） | 无统一阈值 |

- **失效的早期信号**：团队只看总 token 成本而说不清「哪一类调用贵」；或者漂移指标上线后从没有人据此改过检索策略。

### 5.3 与本主题既有栈的接口在哪

「与 X 结合」这句话没有信息量，因为结合点从来不是功能，而是**边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 血缘与元数据（[§ 5 血缘与影响面](../05-lineage-and-impact/05-lineage-and-impact.md)） | 归因链调用字段级下游查询 API，输入是资产 ID，输出是候选根因列表 | 血缘过期导致的**方向错误**由数据平台负责，因此必须同时暴露血缘新鲜度 | 字段级血缘是归因链的硬前置；没有它就只开判定链 |
| 数据质量规则（[§ 1 数据质量](../01-data-quality/01-data-quality.md)） | 规则输出「已知失效」的布尔判定，可观测性输出「未知偏移」的连续分，两者在告警路由层合并 | 冲突时以规则为准，由规则 Owner 负责 | 并存，不互相替代：规则守已知底线，指标发现未知偏移 |
| 告警与 oncall（见 [§ 4 工程实现](04-observability-section-4-sec4.md) §4.2 告警分级与路由） | AI 只允许在分级**之前**插入收敛与抑制，不允许改分级结果 | 抑制必须可回放：AI 抑制掉一条 P0，由平台负责 | 收敛可试点；自动静音不要开 |
| 成本与 FinOps（[§ 3 数据成本](../03-data-cost-finops/03-data-cost-finops.md)） | LLM 调用的 token 成本以调用方 / 租户为标签写入成本归因 | 成本错配由平台负责，口径须与数仓成本同一套标签 | 调用级成本可直接采到，是本主题里最成熟的一块 |
| 审计与合规（[§ 7 审计与合规 §5 前沿演进](../07-audit-and-compliance/07-audit-and-compliance-section-5-ai.md)） | 可观测性留痕与审计证据**共用采集点、分级存储**：观测区可采样可过期，证据区要求完整且不可篡改 | 把采样率当完整性是常见错误，责任在架构设计而不是工具 | 未分开的团队，先分开存储再谈 AI |
| 流式链路（见 [§ 3 设计模式与范式](04-observability-section-3-sec3.md) §3.2.4） | 判定单元是分区 + 时间窗口，AIOps 的判定链要在这层单独实现 | 窗口级误报由值班负责，故窗口大小是运维决策不是算法参数 | 端到端时间尚未成为统一 SLO 时，先补分段埋点 |

这张表要说的是**失败责任落在哪一侧**。判定链与归因链的分界最容易被忽略：异常检测报错一条只会浪费注意力，而归因结论错会把整个排查方向带偏，因此归因链的输入（血缘）必须由数据平台保证新鲜度，而不能当作「反正是 AI 算的」。

同理，LLM 可观测性留痕与审计证据虽然共用采集点，但两者的完整性要求不同：一个可以采样，一个不可以——把它们放在同一张表上，两边都会受委屈：采样策略会让证据区丢证据，证据区的不可删会让观测区无法按容量回收。这一条不是 AI 带来的新问题，但 AI 把它的量级放大了，因为一次 LLM 调用留痕的体积是访问日志的一到两个数量级（见 5.2.4 的推算）。

上面六个结合点里，有三类失败会反复出现，它们的共同点是**都不报错**：

| 失败形态 | 表面现象 | 谁会先发现 | 修法 |
| --- | --- | --- | --- |
| 血缘过期 | 归因给出的是过去的拓扑，方向看似合理 | 排查越走越偏的值班 | 把血缘新鲜度做成与血缘覆盖率同级的指标 |
| 规则与指标冲突 | 同一张表在两张面板上得到两个结论 | 业务方 | 冲突时以规则为准，并把冲突次数记成治理指标 |
| 留痕口径混用 | 复盘时还原不出完整链路，但日志看起来是全的 | 事后复盘的人 | 观测区与证据区物理分开，保留期分别设定 |

多域（多云、Data Mesh）场景下还有一条边界要单独说：各域之间可以共享的往往只有**结构事件与血缘**这类轻量元数据，而指标与时序通常留在域内。把「统一采集全量指标」当作跨域可观测性的前提，是这类项目最常见的立项错误——它会把一个元数据对接问题变成一个跨组织的资源谈判问题。

最后一条边界不属于任何单一系统，却决定上面每一个接口能不能工作：**告警的接收者是否对数据的产出负责**。如果告警落在一个没人负责的群里，检测再准、归因再对也合不上环——因为「修」这个动作需要有人有权改上游。这条判据与 AI 无关，但它是所有 AI 方向的前置条件。

- 本节**未列出**「AI 可观测性能力」在非厂商生产环境中的公开案例。读者找不到这类案例，不等于案例不存在——但它正是本节不给这些方向标 L1 的理由：第②条要的是一个能被指出来的第三方来源，而不是一个「大概存在」的印象。读者可用一条判定方法自查：能否找到非厂商发布的、给出误报率或分诊时间口径的生产复盘；能找到，对应方向的级别就应当由读者自己上调。

**工业进展的读法**

原 §5.3 列出的条目——三条学术引用与那批「某年某月某厂商发布某能力」的发布——本节不再逐条复述。学术那三条只有会议与年份、没有论文标题，读者无从定位到唯一文献，按「宁少勿假」的取材纪律不收录；厂商发布那一批则有两个系统性的坑：一是**把路线图写成既成事实**（预览特性与 GA 在同一条时间线上看起来没有区别）；二是**把厂商发布当成第三方采用**（发布是能力存在的证据，不是生产可用的证据）。要判断一条工业进展是否值得跟进，用一条判据即可：**它有没有独立于厂商的、可复算的效果口径**。

### 5.5 被过度宣传的部分

**「Agent 自动修复让 oncall 下班」**

- 实际是什么：能自动化的只有判定链，处置链仍然需要人点头。
- 为什么会这样：判定错是噪声，处置错是不可逆的生产变更，两者风险量级差一个数量级；因此自动化必须先有幂等、回滚条件与变更审批三件套，而这三件套的建设成本通常高于自动修复本身的收益。
- 什么时候它才会成真：当「回滚条件」成为自动处置的默认前置项（而不是选配），且非厂商的事故公开复盘里出现带自动回滚的处置记录。

**「统一可观测性平台：Metrics + Logs + Traces + Data + AI 五合一」**

- 实际是什么：统一的是门户与账单，不是判定。
- 为什么会这样：五种模式的**判定输入不是同一种东西**（例如数值指标 / 表与字段的分布统计 / 元数据事件 / 分区窗口 / 一次调用），每一种在结构上看不见别人的盲区；把面板放在一起，不会让它们互相看见。
- 什么时候它才会成真：出现跨输入的公共判定层——例如结构事件、调用留痕与指标统一到同一个资产与事件 schema 上，而不是同一个 UI 上。

**「自然语言成为可观测性的主交互界面」**

- 实际是什么：接口改良，不是架构变化。
- 为什么会这样：NL 界面把「确定性查询」换成「统计生成」，同一个问题两次问可能得到两个答案，而运维决策要的是可复现的数字。
- 什么时候它才会成真：生成层给出的每个结论都附带它执行过的查询语句与结果快照 ID，使结论可以被复算——这条与可靠性无关，纯粹是接口设计问题，因此它反而是最可能先成真的一条。

三条合起来是同一个模式：**厂商描述的是能力上限，而架构师要决定的是失效下限**。上面每一条的「实际是什么」都在回答同一个问题——它失效时，谁在半夜被叫醒、代价由谁承担。

### 5.6 未来 3-5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 调用留痕的字段收敛到一个跨工具的公共语义约定 | `gen_ai.*` 一类属性组在语义约定中从实验性转为稳定，且至少两家不同生态的采集后端按同一属性名接收 | 三年后各厂商仍各用私有字段名，互转只能靠适配器 |
| 自动处置停在「带回滚条件的幂等动作」这一窄区间，不进入口径修复类变更 | 公开的生产复盘里，自动处置清单清一色是重跑 / 重启 / 回滚，且都附自动回滚条件 | 出现无需人工确认的口径变更自动化，并被非厂商生产环境公开采用 |
| 数据可观测性与 LLM 应用可观测性合并到同一份元数据模型 | 主流元数据系统的公开 schema 里出现「检索集 / 模型版本」作为一等实体，与表字段在同一张图里 | 三年后两者仍是两条独立产品线，交叉引用靠人工配置 |
| 价值叙事从「检出率」转向「告警条数与分诊时间」 | 厂商公开材料的案例指标变成可复算的告警条数下降与分诊时间下降 | 仍以「检出更多异常」为卖点，且不给误报口径 |

这四条预测有一个共同点：**它们的证伪信号都是「三年后还是老样子」**，而不是「出现了相反的技术」。写「AI 会让可观测性更智能」永远不会错，因为它没有可观测的证伪条件；上面每一条都能在一年后拿公开材料对一次表。第一条与第三条的检验成本最低——只要去读一份公开的语义约定仓库或元数据 schema，不需要任何采购。

四条预测的检验时点也应当先定下来，否则三年后没人记得当初承诺过什么：第一条与第三条一年即可对表（看仓库状态与 schema），第二条与第四条需要等到有足够多的公开复盘与厂商材料，建议按两年为一轮检查。**没有检验时点的预测，等于没有预测。**

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 表数百级，资产与血缘尚未登记 | 先把元数据登记与核心表的 SLO / 错误预算立起来——这是判定与归因的输入 | 留痕采集对生产库的开销是否可接受 | 不要先买 LLM 可观测性或接自动修复：没有资产图，二者都无处落地 |
| 万级表，指标与字段级血缘已可查 | 上 ML 检测 + 血缘收敛，并把误报率与分诊时间作为验收指标 | `gen_ai.*` 一类语义约定是否转稳 | 不要把自动修复接到任何有对外 SLA 的链路上 |
| 已经在跑 LLM / RAG 应用 | 做调用级留痕与成本归因；留痕区与审计证据区**分开存储**、保留期分开设 | 检索质量评估的指标定义是否收敛 | 不要用 LLM 生成的解释作为根因结论或事故定性依据 |
| 强监管行业，同时有 AI 应用 | 先让证据链三件套（留存策略、不可篡改、访问控制）成立，再谈模型留痕 | AI 生成内容的合规判定口径 | 不要把可观测性的采样配置直接当作审计留存配置 |
| 多云 / 多域（域数多、无统一采集） | 先让各域共享**结构事件与血缘**这类轻量元数据，而不是统一采集数据内容 | 域间事件 schema 是否收敛到同一套 | 不要为了统一面板去做跨域的全量指标采集 |

把上表压成一条实施顺序，就是：**先让资产与 SLO 可见 → 再让检测可度量（误报率、分诊时间）→ 再让归因可信（血缘新鲜度）→ 最后才谈处置自动化**。跳过中间任何一步，后面的能力都会给出「看起来完整、方向错误」的结论，而这类结论比没有结论贵。

这套顺序的收益也要按同样的口径估，不要按厂商给的比例估。**量级【推算】**：告警收敛带来的节省 ≈ 被自动合并或抑制掉的告警条数 × 每条的人工分诊时间。推导链是：设一天产生 A 条告警、其中可被血缘收敛掉的占 p、每条分诊与确认耗时 t 分钟，则释放的人工约为 A × p × t 分钟/天。注意两个常见的算错方式：一是只算 A 而忽略 p（被收敛掉的往往是本来就一眼能看出的那类，p 通常远小于 1）；二是把 t 取成抢修时间（分诊时间通常是分钟级，不是小时级）。A、p、t 请代入自己平台的值。

### 5.8 小结

> 本节小结：AI 在本主题真正改变的唯一一条机制，是把**期望的来源**从「人写下的规则」换成「从历史与结构事件中推断」，从而使覆盖全量资产的成本从随**行数**增长变成随**表数**增长——这是判定链能规模化的根据，也是本节唯一一条能站住的因果链；它的代价是阈值从文档搬进了配置，且这套判定仍然看不见「行数正常但值全错」。它还没有改变的是另外两件事：判定输入的类型决定了每个模式仍有它结构上看不见的故障，以及处置链一旦出错就无法回滚；因此「自动修复」在本节里始终是 L3。
