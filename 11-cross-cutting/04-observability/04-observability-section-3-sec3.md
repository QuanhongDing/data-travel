## 3. 设计模式与范式

> **证据档位**：本节【公开】均给出来源类型与年份；【推算】给出推导链；**凡本节无法核到公开出处的规模数字，一律按【经验】使用——只取量级、不取精确值**，并给出可自行核验的方向。**因此本节标【公开】的条目必须能指出可定位的出处（文档 / 公告 / 产品页的名称，或版本年份）；只能写"官方文档可自行核验"而给不出可定位出处的，改标【经验】，不标【公开】；对本身不含年份主张的条目（如通用统计方法），给出其所属类别即可。**本节未核到可引用的公开出处，因此"核不到"不构成"不存在"的证据，也不构成"是真的"的证据。

### 3.1 先看约束：决定模式的是"你的正常基线从哪来"

五种模式排在一起，读起来像是五条技术路线：自建、买 SaaS、挂元数据、做流式、上 AI。但它们在结构上回答的是同一个问题的五个分支——**"正常"这个参照物从哪来，以及每一轮为拿到它要付多少采集成本**。模式 1 的基线来自你自己极少数几张表的历史时序统计；模式 2 的基线来自厂商在大量同类表上学出来的分布；模式 3 干脆不求值，它把"正常"定义成"结构事件没有发生"；模式 4 把判定单元从"表 + 批次"压到"分区 + 窗口"；模式 5 把判定权交给模型，但**模型要吃的输入仍然是前四种产出的东西**——所以模式 5 不替代任何模式，它只消费它们的输出。

这条约束之所以是决定性的，是因为它同时锁死三件事。第一，**能不能覆盖全量资产**：采集要不要读数据内容，决定了成本随"表的行数"增长还是随"表的数量"增长——前者在 PB 级表上不可能全量，后者在万级表上仍然可行。第二，**故障最早在什么时候能被判出来**：判定单元越粗（表 + 天），MTTD 的下界就越长，因为它必须等到批次产出之后才有输入。第三，**误报由谁付账**：采集查询跑在你的数仓上就消耗你的资源，告警半夜叫醒的是你的人——所以"阈值定在哪"最终不是算法问题，而是值班表问题。

还有一层区分必须先讲清楚：这五种模式的**判定输入不是同一种东西**。模式 1、2 的输入是数值指标，所以它们看不见"行数正常但值全错"；模式 3 的输入是元数据事件，所以它们看不见"值错了但结构没变"；模式 4 的输入是流的分区位点，所以它看不见"下游用户等了多久"。**每个模式都有一类它结构上无法看见的故障**——这正是 3.4 说的"都用"不是贪心，而是覆盖不同盲区。

判断一份可观测性方案是否成立，本节用三条可核验的尺子：**采集是否读数据内容**（成本随什么增长）、**判定单元是什么**（MTTD 的下界在哪）、**误报的成本记在谁账上**（阈值最终会被调到多松）。三条都答不出的方案，通常是买了一堆工具而没有定义过"正常"。

最后一条容易混淆的地方值得单独说明：**"可观测性"与"数据质量规则"不是同一个东西，也不能互相替代**。质量规则是你写下的、已知的期望（"这个字段不能为空"），它覆盖的是你已经想到的失效；可观测性是从历史推断的、未写下的期望，它覆盖的是你没想到的失效。前者在上线当天就生效、判定精确、误报低；后者需要历史、判定模糊、但覆盖面随数据自己扩展。所以真实系统里两者并存——**用规则守住已知的底线，用指标发现未知的偏移**，本节 3.2.1 与 3.2.3 讲的正是后者的两条实现路径。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 采集是否读数据内容 | 覆盖全量资产是否负担得起；能看见"值错"还是只能看见"没产出" | 「要覆盖全量字段」——读内容的采集成本随行数走，不随表数走 |
| 判定单元（表+批次 / 分区+窗口 / 字段） | MTTD 的下界，以及噪声的下限 | 「采得越密越灵敏」——单元越小，噪声下限越高，两者同源 |
| 手上已有多少历史基线 | 冷启动期能不能告警、擅长哪类异常 | 「接上就有基线」——新表头几周只有规则可用，没有基线可学 |
| 误报成本落在谁的账上 | 阈值会被谁、往哪个方向调 | 「阈值交给算法定」——它最终由"谁被半夜叫醒"决定 |
| 血缘是否可信 | 告警能不能收敛成"一个根因" | 「有告警就够了」——没有血缘时，N 个下游会同时叫醒 N 个人 |
| 处置链的风险量级 | 自动化能开到哪一步 | 「AI 自动修复」——判定错是误报，处置错是改坏生产 |

### 3.2 模式逐个拆解（核心节）

5 个模式一个不少，只是被安置到了它们各自所属的约束位置上。每个模式都给出可落地的结构示意（DDL 或关系图），而不是只有工具名——**因为模式的本质是结构，工具只是这个结构的一种实现**。对照如下：

| 模式 | 本节归属 | 被什么约束逼出来 | 主要代价 |
| --- | --- | --- | --- |
| 模式 1 指标 + 时序 + 异常检测 | 3.2.1 | 表按批次产出、有历史节律，但表多到不能逐张写规则 | 看不见值错；基线含节律时误报 |
| 模式 2 数据可观测性 SaaS | 3.2.2 | 没有历史基线、也不想养采集工程 | 采集查询跑在自己的资源上；基线未必迁移 |
| 模式 3 元数据驱动可观测性 | 3.2.3 | 想覆盖全量资产，但扫数据付不起 | 不产生事件的变化对它是不可见的 |
| 模式 4 流式可观测性 | 3.2.4 | 没有"批次产出完成"这个时点可对齐 | 指标滚动、不保留可回查的历史视图 |
| 模式 5 AI 驱动可观测性（AIOps for Data） | 3.2.5 | 告警产出速度超过人的处理速度 | 阈值成了新的隐藏硬编码；错误归因比没有结论更贵 |

#### 3.2.1 指标 + 时序 + 异常检测（Metrics + TSDB + Anomaly）

- **被什么约束逼出来**：数据是分批产出的，批次之间有稳定节律，所以"上一批什么时候出来、出了多少行"本身就是可观测量；但表多到不能逐张写规则，也不可能为每张表读一遍全量数据。
- **结构**：

```sql
-- 指标时序表：只装"产出事实"，不装数据内容（TSDB 的概念模型）
CREATE TABLE data_metric_series (
  metric_name   TEXT        NOT NULL,  -- freshness_seconds / row_count / null_rate
  asset_id      TEXT        NOT NULL,  -- db.table 或 db.table.column
  labels        JSONB,                 -- owner / domain / tier：用于聚合与告警路由
  ts            TIMESTAMPTZ NOT NULL,
  value         DOUBLE PRECISION NOT NULL,
  PRIMARY KEY (metric_name, asset_id, ts)
);
-- 异常检测 = 在 (metric_name, asset_id) 这条序列上做窗口统计，
-- 而不是去读数据：3-sigma 判 |x_t − μ| > 3σ
-- → 采集成本 ∝ 表数，不 ∝ 行数；这也是它能覆盖全量资产的前提
```

- **机制**：因为采集只问"最大更新时间是什么、行数是多少"这类产出元信息，所以单表采集代价与表的体积无关，覆盖全量资产的成本只随表数线性增长；因为判定用的是同一序列的历史窗口，所以不需要人写"什么算异常"，只要产出节律稳定，μ/σ 会自动跟着数据走。
- **代价**：这套结构的输入里**没有数据内容**，所以它对"行数正常、值全错"完全无感——要看见空值率、值域、分布，必须另加一层读内容的采集，而那层成本随行数走。此外时序库按时间递增写入、按标签索引查询，标签基数（`asset_id` 数量）一大，内存与索引开销按基数增长，所以"全量字段级指标"通常要付热存与冷存两套账。
- **失效点**：当产出节律本身不稳定（大促、活动日、上新、节假日）时，**「偏离历史窗口即异常」会反转成「正常波动全被报成故障」**——因为 μ/σ 是从一段本身就含节律的历史里算出来的，而 3-sigma 假设的是"平稳"。机制上，节律=方差不恒定，方差一变，固定的倍数阈值就失去含义。判据：把最大的一次误报和真实故障的日期对齐，看它是不是正好落在业务高峰上。
- **失效的早期信号**：值班开始出现"这条告警每周都来，看一眼就关"的行为；或团队把阈值从 3σ 调到 5σ 而不是去改基线模型。
- **量级**：采集成本约等于"表数 × 每轮一次轻聚合查询"【推算：设 N 张表、每轮每表一次 `MAX(update_time)`/`COUNT(*)` 级别的查询、每天 T 轮，则日查询数 ≈ N × T；它不随每张表的行数变化——这正是"行数敏感"的自建校验做不到全量的原因。N 与 T 请代入自己平台的值】
- **真实使用**：Prometheus 是这一结构最常被引用的实现，由 SoundCloud 发起、后成为 CNCF 项目，Thanos 常与它配对做长期存储与跨集群查询；两者的沿革与能力可在项目官方文档与 CNCF 项目页自行核验，本节不逐一给出时点与版本【经验：只取"该项目是 CNCF 项目、可自行核验沿革"这一判断，不取精确年份】。引用时有一个**年份口径**上的常见误植值得提醒：项目的**内部立项年份**与**首次开源年份**不是同一年，两者相隔数年级【经验：量级表达】，把立项年份写成「某年开源」，读者按项目仓库的发布标签是核不到的——要给时点时，请以项目仓库的首个发布标签与 CNCF 项目页的加入/毕业记录为准，不要拿文档里「项目始于」的年份代替。3-sigma 与 IQR 是通用统计方法，不属于任何厂商专有技术，也不对应某个年份或厂商版本【公开：统计学教科书中的通用方法】。

#### 3.2.2 数据可观测性 SaaS

- **被什么约束逼出来**：团队既没有积累过指标历史（所以没有基线可学），也不想自建采集、检测、告警这一整套工程；而数据恰好落在云数仓里，以只读查询为接口的采集是可行的。
- **结构**：

```text
多租户可观测性 SaaS：判定与基线在厂商侧，客户侧只留探针
  客户数仓 / 对象存储
      │  ① 只读统计查询：行数 / 空值率 / 最大更新时间 / 直方图
      ▼
  客户 VPC 内的采集探针  ── 只上报指标，不上报原始数据 ──►  厂商网关
                                                            │
                       ┌────────────────────────────────────┤
                       ▼                                    ▼
               基线学习（按表按列自动建，客户不写规则）   多租户隔离与计费
                       │
                       ▼
               异常评分 → 按血缘排影响面 → 告警推到客户 IM
  ────────────────────────────────────────────────────────────
  关键：客户不写规则，基线由厂商在"跨客户同类表"的分布上学
        冷启动因此接近 0；代价是每轮采集查询算在客户的数仓账上
```

- **机制**：因为基线是跨客户在同类表上学出来的，所以新接入一张表不需要等它自己攒够历史——这直接消掉了模式 3.2.1 最难的那段冷启动期；因为判定与存储都在厂商侧，客户侧的能力上限不再由自己的工程团队规模决定。
- **代价**：每轮采集都是一次真实查询，**这笔计算钱记在你的仓库账单上**，且探针必须真的连得到数据（权限、网络、跨区域出网都要开通）；基线跨客户迁移的前提是"你的表和别人的表同类"，这个前提对定制业务表通常不成立；此外元数据与指标出到第三方，合规评审是必过的一关。
- **失效点**：当你的表"每张都长得不一样"（宽表里 200 列各有用意【经验：量级举例，不是测量值——代入自己最宽那张表的列数即可】、口径全在本团队脑子里）时，**「无需配置自动生效」会反转成「报的都不是要紧的、要紧的报不出来」**——因为这套结构的强项是同类表之间的共性统计，而你的问题恰恰是单表的个性。此时团队的处理方式通常是调松敏感度，于是它退化成"什么都不报"，订阅它的预算却不退。
- **失效的早期信号**：接入后两周内没收到过任何告警；或收到的告警全是"表没更新"这一类最简单的问题，而团队真正的痛点（口径、分布）一次都没被提到。
- **量级**：厂商侧能力的边界可以用一个式子估：能自动覆盖的比例 ≈ 你的表里"与公开同类表结构近似"的那部分占比【推算：不是一个测量值，而是一个自查比例——把核心表按"是否有标准同行/主键/时间分区"分类，第一类的占比就是自动基线能覆盖的上限，第二类必须靠人工规则补】
- **真实使用**："data observability" 这一提法由 Monte Carlo Data 在 2019–2020 年推向市场，Gartner 于 2022 年将其列入 Hype Cycle for Data and Analytics（沿用本书主文件 §1.4 的记述；本节未核到 Gartner 原文，故按**【经验】量级**使用）工具——Monte Carlo、Bigeye、Anomalo、Mona、Soda Cloud——均为真实存在的商业产品，具体能力与计费方式请以各家官方文档为准【经验：能力与计费口径以各家官方文档为准，本节未核原文，故不按公开档处理】。

#### 3.2.3 元数据驱动可观测性（Metadata-driven Observability）

- **被什么约束逼出来**：你希望覆盖**全量**资产，但扫数据内容的成本你付不起；同时相当一部分真实事故根本不体现在值上——上游改了字段类型、依赖的作业没跑、口径被换了、Owner 离职，这些在数据里是"看不出来"的。
- **结构**：

```sql
-- 元数据事件表：装"结构与依赖的事实"，不装值
CREATE TABLE metadata_event (
  event_id     TEXT PRIMARY KEY,
  asset_id     TEXT NOT NULL,       -- db.table
  field_path   TEXT,                -- 字段级事件时为 db.table.column
  event_type   TEXT NOT NULL,       -- schema_change / job_deployed / owner_change
                                    -- / partition_added / sla_changed
  before_value JSONB,               -- 变更前定义（类型 / 约束 / 口径）
  after_value  JSONB,
  emitted_by   TEXT NOT NULL,       -- 采集来源：SQL 解析 / 调度器钩子 / 人工登记
  produced_at  TIMESTAMPTZ NOT NULL
);
-- 判定不读值：只需要"事件是否发生、发生在谁身上、会传到谁"
-- 血缘表（asset_id → downstream asset_id）负责把单点事件放大成影响面
```

- **机制**：因为判定的输入是事件而不是值，覆盖全量资产的边际成本只与"事件产生的频率"有关，而与数据体积完全无关——这就是它能做到"不扫数据却覆盖所有表"的原因；因为事件是变更的前后对照（`before_value` / `after_value`），"上游改了"这条信息在改动发生的那一刻就成立，不必等下游下一批产出失败才发现，MTTD 从"一个批次"缩短到"一次事件"。
- **代价**：需要每个数据源都有一个能产生可信事件的采集点（SQL 解析器、调度器钩子、DDL 监听），新引擎接不进来就是新的盲区；事件表本身会随变更次数无界增长，需要自己的保留与归档策略；字段级事件的粒度取决于解析器能力，CTE、动态 SQL、脚本任务往往解析不全，**解析不出来的部分会以"没有事件"的形式被静默漏掉**。
- **失效点**：当上游改了却没产生事件（脚本直接改表结构、外部导入、人工 DDL）时，**「没有事件」会被读成「没有异常」**——面板是绿的，但绿是假绿。因为这套模式的全部输入就是事件流，事件流之外的世界对它结构上不可见。判据很硬：把最近三次数据事故拿出来，看它们发生的**那一刻**有没有对应的事件；只要有一次没有，覆盖度就低于你面板上显示的数。
- **失效的早期信号**：覆盖率指标的分子是"采集器上报的资产数"、分母也是"采集器知道的资产数"——一个只在它自己知道的世界里算出来的覆盖率；或有人开始用"手工登记"补事件。
- **真实使用**：DataHub、Apache Atlas、Unity Catalog 均为真实存在的元数据系统，其中 DataHub 是"以元数据事件驱动采集与血缘"这一结构的真实实现之一（Metadata Change Event 是它公开设计中的一环）。**本节不引用它的建设时间线，也不把任何年份写成既成事实**——本书主文件与 [§ 6 落地实践](04-observability-section-6-sec6.md) 都只把 DataHub 当工具名列出（§6 的四个案例是 Google SRE、字节、阿里、腾讯，不含 DataHub），本节没有可引的"记述"（本节未核对 LinkedIn Engineering 原文）【经验：只取"存在以元数据事件为驱动的开源元数据平台"这一结构判断，不取年份】。至于"某个系统是否以元数据事件作为**唯一**驱动"、以及各项目的开源年份，请以其官方文档为准，本节无法逐一核验。

#### 3.2.4 流式可观测性（Streaming Observability）

- **被什么约束逼出来**：在实时链路里，数据没有"批次产出完成"这个时点可对齐——它一产生就被消费，所以按"表 + 天"采指标的做法在这里连判定单元都找不到。
- **结构**：

```text
观测点必须落在"流动"上（没有产出时点可对齐）
   Kafka topic ──► Flink job ──► 在线 KV ──► 在线服务
      │               │              │            │
      │               │              │            └ 端到端：用户实际等了多久
      │               │              └ 读延迟 / 缺失率 / 热点分布
      │               ├ checkpoint 时长与失败次数（恢复能力的唯一证据）
      │               ├ watermark 滞后 = 处理时间 − 事件时间
      │               └ 反压（backpressure）占比
      └ consumer lag（分区级：生产 offset − 已提交 offset）
  ────────────────────────────────────────────────────────────
  判定单元是"分区 + 时间窗口"，不是"表 + 批次"
  → 窗口越小越早发现，同时噪声下限越高：两者是同一个参数的两面
```

- **机制**：因为判定单元被压到分区与窗口这一级，同一个坏数据可以在几分钟内被看见【经验：量级，实际值取决于窗口大小】，而批量模式必须等下一个产出周期；因为指标是"队列长度、滞后、反压"这类**过程量**，它能在结果变坏（用户投诉）之前就给出信号。Flink + Prometheus 指标导出器、Kafka 健康监控、Ververica Platform、Confluent Control Center、Pravega 监控，都是围绕这组过程量构建的【经验：能力存在性以各项目官方文档为准，本节未核原文，故不按公开档处理】。Flink 官方提供 Prometheus metrics reporter 属长期存在的能力，可在官方文档自行核验（本节未核原文）【经验】。
- **代价**：过程量随时间滚动，默认**不保留"历史某天此刻"的完整视图**，事后复盘要另存一份快照，否则事故过去就查不回来；窗口越小，单位时间内的判定次数越多，噪声与存储同时上升；此外这层指标本身运行在要观测的那条链路上，峰值时监控和被监控者抢资源，必须单独做容量与降级设计（见 [§ 6 落地实践](04-observability-section-6-sec6.md) 的峰值案例）。
- **失效点**：当链路出现"慢但不堵"——lag 长期非零但稳定、反压不高、任务不报错——时，**「队列不堵即正常」会反转成「端到端延迟已在累积而无人报警」**，因为这套监控看的是队列长度，而用户等的时间由"排队 + 处理 + 重试 + 下游"共同决定，其中最慢的一段常常不在这条链路上。
- **失效的早期信号**：SLO 用 `consumer lag` 表达，而不是用"用户从发起到拿到结果"的端到端时间；或复盘时发现"当时所有流指标都是绿的"。
- **量级**：把端到端拆成分段指标后，定位成本按段数而非链路长度变化【推算：定位工作量 ≈ 依次排除的段数，而不是整条链路的组件数；前提是每一段都有独立可观测的耗时，否则只能整条重放——这正是"分段埋点"值钱的地方】
- **真实使用**：Ververica Platform、Confluent Control Center、Pravega 监控均为真实存在的流平台运维产品，其监控能力（消费组 lag、作业指标导出）可在各自官方文档自行核验（本节未核原文）【经验：不按公开档处理】；Flink 官方提供 Prometheus 指标导出器同样属长期存在的能力，可在官方文档自行核验（本节未核原文）【经验】。判断一套流式监控是否合格有一条便宜的试法：**把链路中任意一个组件停掉，看监控能不能在窗口级别指出是哪一段，而不是整条链路一起变红。**

#### 3.2.5 AI 驱动可观测性（AIOps for Data）

- **被什么约束逼出来**：告警的产生速度超过了人能处理的速度，且"该不该报"本身需要判断——误报也是成本，于是需要一个能连续调节"报得多 / 报得准"的旋钮，而不是只能开或关。
- **结构**：

```text
AIOps 的三条链：可分别启用、分别失败，风险量级完全不同
  ① 判定链：指标/事件 → 检测模型 → 异常分（连续值）→ 阈值 → 是否告警
  ② 归因链：异常 + 血缘图 → 反向遍历 / 概率排序 → 候选根因 Top-K
  ③ 处置链：候选根因 → 建议动作 →（Agent）执行 → 校验 → 回滚条件
  ────────────────────────────────────────────────────────────
  ① 错了 = 报错告警（可容忍，代价是注意力）
  ② 错了 = 指错方向（昂贵：错误的自信心比没有结论更贵）
  ③ 错了 = 改坏生产（不可逆，必须先有回滚条件才允许开启）
  → 三条链绝不能捆成一个"自动"开关
```

- **机制**：因为判定链的输出是连续分而不是布尔值，它可以表达"报得多 vs 报得准"的取舍并在运营节奏上调整（大促期收紧、平峰放开），这是手写规则做不到的；因为归因链在血缘图上做反向遍历与概率排序（图遍历、PageRank 变体、贝叶斯网络、随机游走都是主文件 §2.3 列出的方法），"哪个上游最可能是源头"从靠经验猜变成可排序的候选列表。
- **代价**：①的阈值成了新的、看不见的硬编码——换模型、换历史窗口它就失效，而它藏在配置里、不在文档里；②的输入是血缘，血缘不全时它会给出一个**表述完整但方向错误**的结论；③需要把生产写权限交给自动化，必须先有回滚条件、幂等要求和变更审批。此外模型的训练与调参本身是一条新增的工程线，需要有人长期负责，否则半年后就没人敢改它。
- **失效点**：当归因链的血缘覆盖不全时，**「自动给出根因」会反转成「把排查引向错误方向」**——一条阈值告警只会说"哪里不对"，而一段自然语言的归因解释会被当成结论，团队顺着它排查的时间比没有它更长。机制上，模型的输出形式（解释）赋予了它超过其信息量的可信度。
- **失效的早期信号**：值班先看 AI 给的解释、再决定查不查原始指标；或修复后没人回头核对当初的归因对不对——归因正确率从未被度量过。
- **量级**：这套结构带来的节省集中在①上，而它的上限由"人一晚上能处理多少条告警"决定【推算：节省 ≈ 被自动合并/抑制掉的告警条数 × 每条的人工分诊时间；被抑制的条数由血缘的收敛能力决定，分诊时间请代入自己团队的值——两者相乘才是收益，只算条数会高估它，因为被抑制的往往是本来就一眼能看出的那类】
- **真实使用**：Mona（AI Quality Copilot）、Datadog AI、New Relic AI、Anomalo Autonomous 均为真实存在的产品与能力，其中 Datadog / New Relic 的 AI 可观测性还覆盖 LLM 应用自身的链路（Langfuse / LangSmith / Arize Phoenix 属同类）【经验：产品与能力的存在性以厂商公开文档与产品页为准，本节未核对具体版本与推出年份，故不按公开档处理】。把它们用在哪条链上，本节给一条判据：**判定链可以外包给工具，归因链必须自己核对，处置链在你有回滚条件之前不要开。**

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 传统企业数仓，表数百级，有批次节律 | 3.2.1 + 3.2.3 | 不先上 SaaS：数仓规模下的采集账单换不来额外信息；不先上 AIOps：没有基线就没东西可学 | 每张表是否有稳定的产出时间 |
| 数据湖 / Lakehouse，表数万级、Schema 变更频繁 | 3.2.3 + 3.2.1 | 不用纯指标：结构变更不会体现在行数与新鲜度上 | 最近三次事故里有无结构变更类 |
| 实时数仓 / 流处理 | 3.2.4（+3.2.1 对批侧） | 不用表 + 天的判定单元：单元不存在 | 是否已经用端到端时间而非 lag 表达 SLO |
| AI 训练数据，需要分布漂移与归因 | 3.2.2 + 3.2.5 | 不用纯规则：漂移是分布层面的，规则写不出"多偏算偏" | 训练/推理两侧是否有同一份特征定义 |
| 多云 / Data Mesh，跨域资产 | 3.2.3 + 3.2.2 | 不用单点自建全量：域数多时，统一采集的协调成本高于收益 | 各域是否愿意共享元数据事件 |
| 大型互联网，告警量已超过处理能力 | 3.2.1 + 3.2.3 + 3.2.5 | 不用先上 AIOps：没有血缘时归因链给不出可信结果 | 血缘覆盖是否可度量、误报率是否在度量 |
| 早期 0→1，百级表 | 3.2.1（Prometheus 一类）+ 最小 3.2.3 | 不用 SaaS：预算应先花在把资产登记起来（可见性优先于统计） | 每张核心表是否已有人负责 |
| 合规审计要求"哪些表含敏感字段、谁能访问" | 3.2.3（事件 + 标注）+ 规则 | 不用纯统计检测：合规要的是确定的事实，不是"看起来正常" | 能否一次性列出全部敏感字段及其访问者 |
| 已有大量历史告警但没人整理 | 先做 3.2.3 的依赖关系，再上 3.2.5 | 不用直接上 AIOps：没有依赖图时归因链的输出不可检验 | 告警模板里是否已带上游/下游 |

表里最常被误选的一对是**「先买数据可观测性 SaaS」与「先把资产与血缘登记起来」**。误选的后果不是没效果，而是效果错位：SaaS 接上后告警确实来了，来的却全是"表没更新"这类模式 3.2.1 就能回答的问题；而团队真正的痛——上游改了字段、这张表归谁、口径是谁定的——一条都没被回答，因为这些问题的输入是元数据与血缘，而它们的采集被推迟了。判据很简单：**最近一次数据事故，是靠什么发现的？** 如果是业务方打电话发现的，缺的不是检测能力，是可见性。

另有两对值得单独一提。**「按平均节律设阈值」与「按节律建模」**：前者当期零成本、见效快，后者要把节律（工作日/周末/大促）显式建模再判定；只按当期视角决策时，前者一定会被选——直到第一次大促。**「全量字段采集」与「关键字段 + 结构事件」**：读内容的采集成本随行数走，全量字段在 PB 级表上不可能持续，而"值错"恰恰只会出现在少数字段上——把字段级采集限定在关键字段、其余交给结构事件与分布摘要，是成本与覆盖之间唯一现实的交易。

最后一条判据与工具无关，但决定了这些模式能不能长期成立：**告警的接收者是否对数据的产出负责**。如果发出的告警落在一个没有人负责的群里，那么无论上游的检测多准，闭环都无法合上——因为"修"这个动作需要有人有权改上游。这表面上是路由配置问题，实际上是一个归属问题。

### 3.4 组合模式：真实系统不会只用一种

**组合一：指标时序（3.2.1）+ 结构事件（3.2.3）——覆盖"值"与"结构"两类盲区**

- 组合构成：3.2.1 负责产出类事实（新鲜度、行数），3.2.3 负责结构性事实（Schema、Owner、依赖、作业部署）。
- 职责边界：3.2.1 判"数据有没有按时来、量对不对"，3.2.3 判"该来的东西有没有被改、改动会传到谁"——两者互不越界，谁也不负责回答对方的问题。
- 运维代价：两条采集链路、两套存储（时序库 + 元数据库），且必须共用同一套资产标识（`asset_id`），否则告警无法收敛到一张表上；合并键一旦对不上，两个系统的数据会各说各话。
- 适合规模：表数百级起步即有收益；表到万级时，两者共用标识这件事从"方便"变成"必须"【经验：按区间判断】。
- 什么时候不该用：只有几十张表、且变更频率接近零时，结构事件的价值不足以支撑第二条链路。

**组合二：血缘（3.2.3 的关系表）+ 归因（3.2.5）——把 N 个告警收敛成 1 个根因**

- 组合构成：血缘提供"谁传给谁"，归因链在其上做反向遍历或概率排序，输出候选根因列表。
- 职责边界：血缘只负责描述关系、不对"是不是根因"下判断；归因只负责排序，不负责通知下游——通知范围由血缘算出的影响面决定。
- 运维代价：血缘必须可度量、可回溯，且它的新鲜度要单独监控；血缘一旦过期，归因链的错误会被它的表达形式放大。
- 适合规模：依赖关系跨越团队边界（且已无法靠熟人记住）时必需【经验】。
- 什么时候不该用：单团队、依赖关系可以画在一张纸上时，人工定位比建图更快。

**组合三：流式过程量（3.2.4）+ 端到端 SLO——把"队列不堵"与"用户没等"对齐**

- 组合构成：3.2.4 提供分段过程量（lag、反压、watermark 滞后），端到端 SLI/SLO 提供"用户实际等了多久"的判据；前者负责定位，后者负责判定。
- 职责边界：SLO 决定"算不算故障"与错误预算的消耗，过程量只用于定位与预警——不能反过来用 lag 定义故障。
- 运维代价：端到端埋点要穿过所有组件，且观测链路本身要单独做容量与降级（峰值时它不能先崩）；错误预算一旦公布就需要一套**定期评审**——预算耗尽后冻结功能性变更，需要一个"有人有权做这个决定"的场合，而 [§ 6 落地实践](04-observability-section-6-sec6.md) 的 Google SRE 案例只讲到「预算耗尽即冻结功能性变更」这一层，评审的周期与主持人在公开材料里没有通例，要按自己的组织补上【经验：评审节奏无公开通例，按组织自定】。
- 适合规模：链路跨超过一个团队、且"慢"已经成为一个投诉类别时【经验】。
- 依赖关系：组合三依赖组合一（没有基线就没有"正常"），而组合二依赖 3.2.3；倒过来不成立——先做 AIOps 再补血缘，等于让模型在空白图上做归因。

### 3.5 反模式与失效分析

下表把它们从"错误做法"改写成"症状 → 机制后果 → 成因 → 修法"。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（团队为什么会这样写） | 修法 |
| --- | --- | --- | --- | --- |
| **指标过多导致告警疲劳** | 指标数远超资产数；同一根因半夜叫醒多个人 | 注意力成为瓶颈资源，真实故障混在噪声里被一起忽略；值班开始按经验跳过某些告警 | 采集能力先于"什么算异常"被建设——先有了指标，再想判定 | 分级（P0–P3）+ 按血缘聚合同根因 + 抑制规则，并把"误报率"变成被度量的指标 |
| **硬编码阈值** | 阈值写死在配置里；业务量级变化后误报或漏报 | 阈值与数据在同一时刻失效，而失效本身不产生告警——静默漏报比误报更贵 | 静态阈值当下就能上线，动态基线需要历史与调参 | 关键指标用历史基线/EWMA/STL；保留静态阈值作为"底线规则"而非主判据 |
| **采集过频打垮生产** | 采集 SQL 出现在慢查询榜；DBA 收到来自监控的投诉 | 监控与被监控者争抢同一批资源，峰值时采集本身成为故障源 | 采集者与被打扰者是两拨人——成本记在别人账上 | 错峰、抽样、只对关键字段读内容、把采集负载纳入容量规划；采集查询与业务查询走不同队列/只读副本 |
| **忽视 Schema 漂移** | 上游加字段后下游静默算错或直接失败；指标上没有任何信号 | 结构变更在指标层不可见，"值还正常"的错觉会持续到下游产出错误结果 | 指标采集只看值、不看结构，而结构变更的采集点不在数据侧 | 3.2.3 的结构事件 + 契约（Schema Registry / 兼容性检查）+ 变更进发布门禁 |
| **只看指标不看血缘** | 告警里说不清"这张表是谁的下游/谁的上游" | 定位从"一天"变成"先查依赖关系再查数据"【经验：量级，按自己最近一次事故的时间线代入】；告警无法收敛，N 个下游= N 个告警 | 血缘的建设成本高于指标，于是它一直被排在后面 | 指标与血缘共用同一套 `asset_id`；告警模板里强制带上上游与下游 |
| **告警无 oncall** | 告警发到群里，没人对应；处理时长无人统计 | 告警退化成"通知"，SLO 与错误预算无法成立，因为没有对结果负责的人 | 组织没有值班制度时，工具上的路由只能指向一个群 | 告警 + oncall 排班 + Runbook + MTTD/MTTR 度量，四件一起；没有 Runbook 的告警不该开 |
| **忽视数据漂移** | 只监控硬指标（行数、空值），分布变化无信号 | 模型在"数据看起来正常"的绿面板下持续衰减，MTTD 实际是"直到业务方投诉" | 分布指标要读内容、要建模，成本高于计数类指标 | PSI / KS / 孤立森林上关键特征列；把"漂移"接到模型效果监控上 |

最危险的两条是**硬编码阈值**与**采集过频打垮生产**，因为它们都不在"故障"这条线上暴露，而在"信任"与"成本"这两条线上暴露。

硬编码阈值的暴露方式是"静默"：阈值定死之后，它在数据量量级变化的那一刻开始就错了，但"阈值错了"这件事本身没有告警——你只会看到误报变多或告警变少，而后者通常被解释为"最近质量不错"。它的修法是结构性的：主判据必须来自基线，阈值退居为兜底规则，且**兜底规则被触发时必须单独记一笔**，否则你永远不知道哪条规则已经失效。

采集过频的暴露方式是"账"：它不会让任何人受伤，只会让采集 SQL 出现在慢查询榜上，而这份成本的承担者（DBA、业务方）和收益获得者（监控团队）不是同一批人。识别它的办法很直接：把采集查询的资源消耗单独列出来，看它在峰值时占了多少——如果答不出来，说明采集还没有被当成一个需要容量规划的生产负载。

**只看指标不看血缘**是第三条值得单独展开的，它的危险在于把问题推迟到了最贵的时刻：平时一切正常，等到事故发生的那个晚上，你才发现需要先花几小时建立依赖关系才能开始排查。它的判定不依赖任何工具：**把最近一次事故的时间线画出来，其中"定位"占了多长时间。**

### 3.6 规模跃迁时模式何时该换

> 下表全部为**情景阈值**【经验：按区间判断，不是测量值】——它只回答"跨过了哪个台阶"，不回答"跨在第几个"；请代入自己的实际规模。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 表从百级到万级 | 关键表人工写规则 | 规则只覆盖少数表，其余无监控；写规则的人力赶不上建表速度 | 全量指标采集 + 结构事件驱动 | 需要一支平台团队；采集的存储与查询账单按表数增长 |
| 从有批次节律到有强季节性 | 3-sigma 静态窗口 | 节律=方差不恒定，固定倍数阈值失去含义 | 按周期分解（STL）或按日/周/大促分别建基线 | 需要标注业务日历；模型维护成为一条长期工程线 |
| 资产从千级到万级、字段级覆盖 | 只采表级指标 | 表级信号无法回答"哪个字段错了"，排查要靠人肉抽样 | 字段级指标 + 字段级血缘 | 指标基数与索引开销按字段数上升；热存/冷存要分层 |
| 从批到实时链路 | 表 + 天的判定单元 | 判定单元不存在，事故要等下游投诉 | 分区 + 窗口的过程量 + 端到端 SLO | 事后复盘视图要另存；观测链路本身要做峰值容量 |
| 告警量超过人的处理速度 | 全量告警 + 人工分诊 | 注意力被耗尽，真实告警被跳过 | 分级 + 同根因合并 + 归因候选排序 | 需要可信的血缘与误报率度量，否则排序不可信 |
| 从单域到多域 / 多租户 | 中心化采集全部数据 | 协调成本与权限评审成本高于收益 | 域内自治采集 + 事件/指标标准统一 | 需要统一资产标识与事件格式，否则跨域无法收敛 |
| 从"上报指标"到"自动处置" | 人工按 Runbook 处置 | 处置延迟成为 MTTR 的主要部分 | 只对幂等、可回滚的动作用 Agent 自动执行 | 需要写权限、回滚条件与幂等保证；误处置不可逆 |
| 从"检测"到"预测"（容量与成本） | 事后阈值告警 | 资源耗尽类故障发生后才知道 | 趋势外推 + 容量预测纳入观测 | 预测误差会转化成误报，需要与阈值告警分开统计 |

最容易被低估的是第一行。表只有几百张时，"关键表人工写规则"是当时最合理的做法——准确、可控、不需要平台；而它的成本随表数线性上升、收益却固定，所以在某个点上会突然变成瓶颈，而这个点不会有任何告警。判断阈值不需要精确数字：**当"新建一张表"不再自动带来"它被监控"，靠人工写规则就已经跟不上了。**

这些跃迁有一个共同形态：**原模式没有变坏，是它依赖的前提变了**。静态阈值依赖"方差不随时段变化"，表级信号依赖"表足够少、人能抽样"，全量告警依赖"告警量小于人的处理能力"——每条前提都随规模失效，且失效时是静默的。所以这张表的用法不是等疼了再查，而是定期核对自己当前依赖的那条前提还在不在。

第二容易被低估的是"从批到实时"那一行。它不像表数增长那样是渐变的，而是**一次性发生的**：只要有一条链路改成实时，那套"表 + 天"的判定单元当场失效，而同一批人往往还在用批的思路（等下一批出来再看）理解实时链路。迁移代价里最容易被忽略的不是技术，而是**事后复盘能力的下降**——批模式下"重跑一遍昨天"是常规操作，实时模式下要重建当时的视图，必须提前把快照存下来，这件事没有任何告警提醒你去做。

还要区分两种"该换"：一种是**规模跨过阈值**（表数、告警量、字段数），它缓慢发生、可以排期；另一种是**访问模式改变**（批改流、单域改多域、人看改 Agent 看），它一次性发生、且会让原有的判定单元与判据同时失效。前者的迁移可以分阶段，后者必须先停下来说清"新的判定单元是什么"，否则会得到一个"用旧判据观测新链路"的系统——面板齐全，结论全错。

### 3.7 自检清单

- [ ] 采集查询是否读数据内容？读的那部分成本随表的行数走还是随表数走？答不出就没做过容量规划。
- [ ] 是否存在"阈值写死在配置里、且没有历史基线兜底"的 P0 告警？每一条都记一次触发原因，看它是不是已经失效。
- [ ] 最近一次数据事故是被谁发现的？若是业务方打电话发现的，说明缺的是可见性而不是检测算法。
- [ ] 每张核心表是否都有 Owner，且 Owner 是具体的人而不是团队？
- [ ] 血缘的覆盖率分母，是"系统知道的资产数"还是"实际存在的资产数"？前者是自证循环。
- [ ] 告警模板里是否强制带出上游与下游？若没有，同根因告警就无法收敛，值班会被 N 次叫醒。
- [ ] 是否度量"误报率"与"MTTD"？只度量告警条数的团队，最终会把阈值调松到什么都不报。
- [ ] 流式链路的 SLO，是用 consumer lag 表达的，还是用"用户等了多久"表达的？前者是滞后指标。
- [ ] 关键特征列是否监控分布漂移（PSI / KS）？只监控行数与空值率的，看不到模型衰减。
- [ ] AI 归因给出的结论，是否有"事后核对正确率"的记录？没有记录就等于没有验证过。
- [ ] 观测链路自身是否做过峰值容量与降级设计？峰值时它先崩的话，等于没有观测。
- [ ] 自动处置动作是否有回滚条件与幂等保证？没有这两条就不该开放写权限。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 表多、有批次节律、不想写规则 | 3.2.1 指标 + 时序 + 自动基线 | 采集成本只随表数增长，所以能覆盖全量资产 |
| 没有历史基线、数据在云数仓 | 3.2.2 SaaS + 探针 | 基线跨客户学习使冷启动接近零，代价是采集跑在你的账上 |
| Schema 频繁变更、跨团队依赖 | 3.2.3 元数据驱动 | 判定输入是事件不是值，边际成本与数据体积无关 |
| 实时链路、没有产出时点 | 3.2.4 流式过程量 + 端到端 SLO | 判定单元压到分区+窗口，MTTD 从"一批"缩到"几分钟"【经验：量级】 |
| 告警量超过人的处理速度 | 3.2.5 AIOps（分链启用） | 连续异常分可调取舍；但归因与处置的风险量级不同，不能捆在一起 |
| 误报成本落在值班身上 | 先做血缘与聚合，再谈算法 | 没有血缘时任何模型都只能放大 N 个下游告警 |

> 本节小结：本主题下决定其余所有选择的那条约束，是**"正常"这个参照物从哪来、每轮为拿到它要付多少采集成本**。指标时序模式把成本压在表数上、元数据模式把成本压在事件频率上、SaaS 模式把成本转移到你的仓库账单上、流式模式把成本压在窗口大小上、AIOps 把钱压在模型的长期维护上——五种模式的差别，本质是**这笔成本记在谁账上、以及它随什么增长**。所以选型不该从"哪家工具好"开始，而该从"我们能持续负担哪一种采集成本"开始；能回答这一句，3.3 的表才有意义。
>
> 另需提醒：本节列的每条模式都有一类它**结构上看不见**的故障（指标看不见值错、事件看不见未产生事件的变化、流看不见端到端体验、SaaS 看不见单表个性、AIOps 看不见血缘之外的因果）。所以"覆盖度"的正确表述不是"我监控了多少张表"，而是"我漏掉的那类故障，是我自己知道的吗"。
