### 4.1 Google SRE"**从 SRE Book 到全球可用性工程体系**"20+ 年（2003-2024）

**背景（Why）**

Google 2003 年面临**大规模分布式系统的可靠性危机**：
- **百万级服务器**——传统运维**已经失效**（不可能雇 100 万 ops）
- **故障常态**——硬件 / 软件 / 网络故障是常态，**不能靠避免**
- **业务 SLO**——**用户能容忍的停机时间是固定的**（99.99% = 52.6 分钟/年）

**触发点（What）**

2003 年 Google 启动 **SRE 体系**（[Google SRE Book 2016]），目标：
- **可用性 99.99%+**
- **故障自愈**
- **运维自动化**

**详细做法（How）**

Google SRE 的**5 大核心组件**：

1. **SLO / Error Budget（核心创新）**
   - 关键设计：**99.9% SLO → 0.1% Error Budget**（可消费）
   - 关键能力：**用预算管可靠性与发布速度**
   - 关键数字：**SLO 99.99%+**
   - 关键示意：
     ```
     服务可用性 SLO: 99.99%  →  Error Budget: 0.01% / 月 ≈ 4.3 分钟
     决策: Error Budget 没用完 → 可以冒险发新功能
            Error Budget 用完了 → 停止新功能发布，集中做可靠性
     ```

2. **错误预算 + 发布联动（核心）**
   - 关键设计：**SLO 破了 → 冻结发布 → 全员做 SRE**
   - 关键能力：**发布速度 vs 稳定性自动平衡**
   - 关键数字：**发布冻结触发率 100%**

3. **Borg / Kubernetes（核心）**
   - 关键设计：**自研容器编排 + 自动扩缩 + 故障转移**
   - 关键能力：**百万级服务器编排**
   - 关键数字：**百万级**

4. **监控三支柱（核心）**
   - 关键设计：**白盒（Prometheus）+ 黑盒（Blackbox）+ 日志（ELK）**
   - 关键能力：**全维度监控**
   - 关键数字：**P99 < 5s**

5. **On-call 轮值（核心创新）**
   - 关键设计：**SRE 工程师 7×24 轮值 + SLO 报表**
   - 关键能力：**人少办大事**
   - 关键数字：**SRE 团队占比 < 10%**

**Google SRE 关键数字**（[Google SRE Book 2016-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **SLO** | 不可用 | 99.99%+ | **∞** |
| **Error Budget** | 不可用 | 100% | **∞** |
| **发布冻结** | 不可用 | 100% 触发 | **∞** |
| **P99 告警** | 不可用 | < 5s | **∞** |
| **百万级** | 不可用 | 100% | **∞** |
| **SRE 团队占比** | 不可用 | < 10% | **∞** |
| **Borg** | 不可用 | 100% | **∞** |
| **故障自愈** | 不可用 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：Google SRE 团队 1000+ 人
- 关键数字：**SLO 99.99%+**；**SRE Book 行业圣经**；**百万级服务器**
- 业务影响：覆盖**Google 全产品**

**失败教训**

- 早期「**故障人工处理**」——百万级服务器人工救不了，倒逼 SRE 体系
- **SLO 没设**——可靠性无法量化，**后设 SLO + Error Budget**
- **过度自动化**——全自动化后**工程师失去技能**，**后保留人参与**

> **本节小结**：
> - 4 个真实案例（Google / 字节 / 阿里 / 腾讯）印证：**SRE 不是「**值班救火**」，是「**SLO + Error Budget + APM + Chaos + 自愈**」**5 件套**。
> - 关键时间线：Google 20+ 年 / 字节 4+ 年 / 阿里 10+ 年 / 腾讯 8+ 年 —— **SRE 是 4+ 年长期工程**。
> - 选型第一原则：「**Prometheus + SLO + Error Budget 起步**」（**最简单**）——**10+ 服务** → 「**APM + On-call**」（**必须**）→ 「**Chaos + 容器化**」（**生产**）→ 「**大促抗住 + 跨 BU 统一**」（**AI 时代**）。
> - 99% 的失败来自「**故障人工处理 + SLO 没设 + 过度自动化**」——必须有 **SRE + SLO + APM + Chaos**。
> - 真正的 ROI 来自「**SLO 99.99%+ + 故障 1 分钟定位 + MTTR -50%**」——是**大厂核心 SRE 基础设施的命脉**。
