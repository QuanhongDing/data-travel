## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把跨域血缘讲成「按场景选一个」：多团队选联邦、多云选跨云、实时流选端到端、要开放选 API 网关、AI 时代选智能补全。但真实的模式选择被一条约束推着走：**血缘的对象身份不掌握在血缘系统手里**。主文件 §2.2 把联邦血缘定义成有向图集合的并 $G_{\text{federated}} = \bigcup_i G_i$，并在跨域边上加桥接关系 $\text{bridge}(u,v)$。这条式子的全部难点都在那个「并」上——$G_A$ 里的 `prod.orders` 与 $G_B$ 里的 `orders` 是不是同一个实体，没有任何系统能自己判断。所以**跨域血缘的第一性问题是身份对齐，不是存储或查询**；所有模式只是对「谁来对齐、在哪一层对齐、对齐错了怎么办」的三种不同回答。

第二条约束：**血缘是采集出来的，不是登记出来的**。主文件 §2.3 列了五类采集方法（OpenLineage 事件、联邦 Hook、ETL 工具 API、桥接同步、LLM 补全），它们的共同点是都只能看到自己视角的那一段。所以覆盖率天然小于 100%，而且缺口不是随机的——动态 SQL、脚本任务、手工导数这三类永远最难采。因为缺口是系统性的，所以任何「我的血缘是完整的」这个假设，都会在下一次变更事故里破产；正确的做法是把缺口**度量出来并标注为已知盲区**，而不是把覆盖率当作一个能冲到 100% 的指标。

第三条约束：**血缘是时间的函数，不是一张静态图**。Schema 演进了、任务重写了、口径改了，血缘就变了。主文件 §1.1 的术语表把「血缘时序」（血缘随时间的演化）与「血缘版本」（血缘快照）并列为两条独立术语，§2.1 的关键概念表沿用其中的「血缘版本（Lineage Version）」，原因就在这里：事故复盘要回答的往往不是「现在的影响面是什么」，而是「这次改动发生的那一刻，影响面是什么」。因为血缘随时间变化，所以任何只保留当前状态的设计都无法支撑复盘——它只能给出一个事后重建的图，而事后重建的图会被后续变更污染。

第四条约束：**跨域查询的代价由最慢的参与方决定**。联邦的承诺是「不搬数据」，代价是每次查询都要发起跨系统调用。这条约束在后面 3.2.1 会反复出现，因为它决定了联邦模式的能力上限。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据形态与写入模式（采集产生，不是登记产生） | 覆盖率是采出来的，缺口集中在动态 SQL / 脚本 / 手工导数三类 | 「接入了就等于采到了」——解析失败不报警，缺口静默存在 |
| 访问模式（正向、反向、路径、影响面） | 反向（上游溯源）与递归下游是两种代价很不同的查询，前者通常便宜得多 | 「血缘查询就是查一张图」——深链路递归会爆炸，必须有深度上限与截断 |
| 变更频率与历史要求 | 血缘时序决定要不要版本化，以及要不要保留「当时的图」 | 「存当前状态就够了」——复盘需要的是历史时刻的血缘，不是今天的 |
| 一致性 / 身份要求 | URN 命名与对齐策略决定跨域能不能连起来，这是本主题唯一不可绕过的地基 | 「先建联邦层，URN 以后再统一」——URN 不对齐时联邦层只会把两套身份并列展示 |
| 规模与成本约束 | 决定联邦 / 集中 / 混合三种拓扑，以及是否要物化高频路径 | 「先集中所有血缘再谈跨域」——组织上往往拿不到各域的采集授权 |
| 团队技能与运维能力 | 决定能不能自建图存储与桥接服务，还是先用开源栈 | 「自研图数据库更可控」——血缘是长期低改动系统，自研维护成本难收回 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 联邦血缘存储（Federated Lineage）

- **被什么约束逼出来**：没有任何单一系统能装下全组织的血缘；而在 Data Mesh / 多团队结构下，把血缘集中到一处意味着各域要交出采集权与命名权——这在组织上不可行。
- **结构**：

```text
   域 A 血缘服务          域 B 血缘服务          域 C 血缘服务
   (自采、自存、自查)      (自采、自存、自查)      (自采、自存、自查)
        │                      │                      │
        └──────────┬───────────┴──────────┬───────────┘
                   ▼                      ▼
             联邦层（只存三样东西）
             · 路由表：某实体的明细在哪个域
             · ID 对齐表：域内 ID ↔ 全局 URN
             · 桥接边：跨域的那几条 bridge(u, v)
                   │
                   ▼
             统一查询入口 → 按路由下发 → 各域返回片段 → 合并
     ────────────────────────────────────────────────────
     关键：联邦层不存血缘明细，只存"去哪找"和"谁等于谁"
```

```sql
-- 联邦层的两张核心表：对齐表是唯一的真相来源
CREATE TABLE entity_alignment (
  global_urn   TEXT NOT NULL,          -- 全局身份（主文件 §2.2 的 URN 形式）
  domain       TEXT NOT NULL,          -- 该实体的明细在哪个域
  local_id     TEXT NOT NULL,          -- 域内标识
  confidence   TEXT NOT NULL,          -- exact / inferred / manual（谁判定的）
  decided_by   TEXT NOT NULL,          -- 对齐由人还是规则决定，必须留痕
  PRIMARY KEY (global_urn, domain)
);

CREATE TABLE bridge_edge (               -- 跨域边，数量应当很少
  src_urn      TEXT NOT NULL,
  dst_urn      TEXT NOT NULL,
  evidence     TEXT NOT NULL,          -- 依据：同名字段 / 人工确认 / 作业配置
  valid_from   TIMESTAMPTZ NOT NULL,   -- 桥接也有时序，不是永久事实
  PRIMARY KEY (src_urn, dst_urn, valid_from)
);
```

- **为什么这样设计有效**：因为联邦层只持有路由、对齐与桥接，不持有明细，所以新增一个域只需登记映射关系，而不需要把历史血缘搬过来——这是它能在多团队结构下活下来的原因；反过来，因为明细始终留在域内，各域对自己血缘的准确性与访问控制负责，责任边界与组织边界重合。
- **代价**：① 每次跨域查询退化成多次远端调用（一个「从 X 到 Y 的完整路径」查询要按域分段执行后再拼接），延迟由最慢的域决定；② 联邦层拿不到全局一致性快照——两个域的采集时间不同，合并出来的路径可能对应两个不同的时刻；③ 对齐表成为新的单点与热点，且它同时是**唯一能被人工引入错误的地方**；④ 各域的血缘质量不再统一，统一视图的质量等于最差域的质量。
- **失效点**：当跨域桥接边的占比上升（域间依赖变密）或查询变成深链路时，联邦的优点「不搬数据」会反转成缺点「每一跳都是一次分布式调用」，因为路径在域间反复穿越，调用次数随跳数增长而不是随域数增长。此时正确的修法是把高频跨域子图**物化**成一张只读的合并图，而不是继续优化联邦层的查询计划。
- **自验方法**：问「新增一个域，要不要把它的历史血缘搬进中央？」——要搬，说明做的是集中式而不是联邦式，那么它同时继承了集中式的合规问题（见 3.2.4）。
- **真实使用**：主文件 §2.3「联邦血缘存储」表列出四条路线（Neo4j + 联邦层、DataHub + GraphQL Federation、JanusGraph 跨集群、自研图数据库 + 联邦），这四条都是方案形态而非某个产品的一手使用记录。三个产品候选分两类：Databricks Lakehouse Federation 与阿里云 DataWorks 跨云，可在主文件 §1.4 的 2024 年条目核到【公开】（来源：主文件 §1.4「跨云联邦化阶段（2023–2025）」的 2024 年条目：Databricks Lakehouse Federation；阿里云 DataWorks 跨云）；AWS Glue Data Catalog 的跨账户共享，本节未附可定位的官方文档条目（无标题、无年份、无链接），故只按产品形态作方向性候选【经验】——可按 AWS Glue 官方文档当前版本中「跨账户访问」相关内容自行核验。

#### 3.2.2 端到端血缘（End-to-End Lineage）

- **被什么约束逼出来**：故障与合规问题的对象是「一条链路」，不是一张表。上游 MySQL 改了类型、下游 Flink 作业挂了——只在数仓视角里看不到 MySQL，链路的第一跳就断了。
- **结构**：

```text
   MySQL ─► Kafka ─► Flink ─► Iceberg ─► 数仓内表 ─► BI / RAG
     │        │        │         │           │
     └────────┴────────┴─────────┴───────────┘
                 各环节各自的采集器
      （解析器 / 调度钩子 / 订阅元数据 / 查询日志）
                        │
                        ▼
           OpenLineage 规范事件（统一 schema）
                        │
                        ▼
          统一血缘存储（OpenLineage + DataHub / Marquez）
     ────────────────────────────────────────────────
     关键：采集点必须覆盖链路的每一跳
           任何一跳没有采集器，端到端就在这里断开且不报警
```

```sql
-- 边的结构：每条边都要说清"用什么作业、在什么时间、动了哪些字段"
CREATE TABLE lineage_edge (
  src_urn      TEXT NOT NULL,          -- 上游实体或字段
  dst_urn      TEXT NOT NULL,          -- 下游实体或字段
  granularity  TEXT NOT NULL,          -- table / column
  job_urn      TEXT,                   -- 产生这条边的那次作业
  transform    TEXT,                   -- 字段级变换形态（直接映射 / 聚合 / 条件）
  produced_at  TIMESTAMPTZ NOT NULL,   -- 边也是有时间戳的，支撑时序查询
  source_sys   TEXT NOT NULL,          -- 哪个采集器产出的，用于算覆盖率
  collector    TEXT NOT NULL           -- parser / hook / runtime，决定可信度
);
```

- **为什么这样设计有效**：因为每条边都携带「作业 + 字段变换 + 时间」，查询可以沿边递归，把「这个字段最终影响哪些指标」算出来，而不是只回答「这张表被谁用」；因为边由各引擎的采集器产出而非人工登记，它随作业变更自动更新，不会像人工登记那样在几次人员与流程变动后就静默失效【经验】（人工登记的血缘通常在数个月内失去可信度，具体周期随团队流程稳定性而异）。
- **代价**：① 采集面等于「系统数 × 引擎数 × 版本数」，每接一个引擎要写一个解析器；② 事件流要处理顺序、去重与至少一次投递，否则同一条边会重复计入影响面；③ 跨系统时钟偏移会让合并出来的链路顺序是错的；④ 一条链路的可信度等于**最弱那一跳**，只要有一跳靠人工登记，整条链路的时效性就退回到人工登记的时效性。
- **失效点**：当链路中间出现无法解析的节点（动态 SQL、脚本、手工导数）时，「链路可见」的优点反转成「确定的错误信心」——查询会返回一条看起来完整的路径，而实际上中间少了一段；更糟的是它不会报错，因为系统不知道那里有个节点。判据：统计 `collector = manual` 与解析失败的边占比，并在查询结果里把这些位置显式标出来。
- **真实使用**：OpenLineage 是跨工具的 lineage 规范，Marquez 是其参考实现、DataHub 同时提供采集与消费端能力【公开】（来源形态：OpenLineage 项目官方文档，以及 Marquez、DataHub 两个项目的官方文档——Marquez 在自身文档中自述为 OpenLineage 的参考实现；年份锚点见主文件 §1.4 的 2020–2023 年条目「OpenLineage 1.0；跨工具血缘互通起步」，本节未附文档标题与链接，两项目的版本与接口以当前文档为准，可按项目名核验）。多数团队的真实形态是「主干引擎自动采集 + 长尾手工补登记」【经验】。

#### 3.2.3 血缘 API 网关（Lineage API Gateway）

- **被什么约束逼出来**：血缘的消费者不止一个——目录、质量、权限、发布门禁、Agent 都要它。每多一个消费者就多一份 SQL 解析、一套口径；而血缘本身是**读多写少、查询形态集中**的服务，正好适合被统一收口。
- **结构**：

```text
  消费方：目录 / 质量 / 权限 / CI 门禁 / Agent / 人工查询
                    │
                    ▼
        ┌───────────────────────────────┐
        │   血缘 API 网关                │
        │  · 鉴权（谁能看哪个域的血缘）    │
        │  · 限流（防止一次深链路拖垮存储） │
        │  · 缓存（热点实体与常用路径）    │
        │  · 查询改写（下发到联邦或直查）   │
        │  · 结果标注（新鲜度 / 可信度）    │
        └───────────────────────────────┘
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   联邦血缘层              直连图存储
```

```graphql
# 网关对外只承诺一件事：任何一条血缘都带得出处与新鲜度
query {
  entity(urn: "urn:li:dataset:(hive,prod.orders,PROD)") {
    upstream(depth: 2, granularity: COLUMN) {
      edges {
        from to
        collector        # parser / hook / runtime / manual
        lastUpdated      # 没有这个字段，调用方就无法判断可信度
      }
    }
  }
}
```

- **为什么这样设计有效**：因为所有消费方走同一份接口，SQL 解析与身份对齐只做一次，避免「目录、质量、权限各解析一份、各自得出不同下游」这种最难排查的口径分歧；因为网关是唯一入口，鉴权、限流与缓存都只需实现一遍，深链路查询的爆炸半径被限流挡住。
- **代价**：① 网关成为可用性单点，它挂了所有消费方一起挂——而门禁依赖它意味着发布流程也被它绑住；② 接口一旦被多消费方使用就成为契约，加字段容易、改语义昂贵；③ 缓存引入「新鲜度」这个新变量，缓存的 TTL 直接决定调用方看到的血缘有多旧；④ 每个消费方的延迟要求不同（门禁要准、Agent 要快），一个接口要同时满足会退化成为最苛刻的消费方设计。
- **失效点**：当缓存 TTL 长于血缘采集周期时，优点「血缘随时可查」反转成「稳定地给出过期答案」，因为缓存命中意味着返回旧图而不是重新采集的结果。而过期的血缘比没有血缘更危险——它给出的是一个确定的、错误的答案，调用方不会去怀疑它。判据很简单：血缘查询的返回值里是否带 `lastUpdated`，以及它是否随缓存一起被冻结。
- **自验方法**：统计网关的调用方数量与调用量分布；若只有一个消费方在用，说明它还没有成为基础设施，此时引入网关只增加了一跳延迟。
- **真实使用**：主文件 §2.1 把「血缘 API 网关」与「血缘即服务（LaaS）」列为服务化形态；DataHub 对外暴露 GraphQL 接口、OpenLineage 对外暴露规范事件接口，两者都可编程访问【公开】（来源形态：DataHub 项目的 GraphQL API 文档与 OpenLineage 项目的规范文档；年份锚点见主文件 §1.4——DataHub 记于 2018–2020 年条目、OpenLineage 1.0 记于 2020–2023 年条目；本节未附文档链接与版本号，接口字段以两项目当前版本为准，可按项目名核验）。「自研 API Gateway + GraphQL Federation」是否值得做，取决于消费方数量与是否已存在联邦层【经验】。

#### 3.2.4 跨云血缘（Cross-Cloud Lineage）

- **被什么约束逼出来**：数据与计算分散在多朵云或自建机房，同时受数据出境与合规约束——**不能把明细血缘汇到一处**。于是「统一视图」必须在物理上避开「统一存储」。
- **结构**：

```text
   AWS 域                 Azure 域               自建机房
   血缘服务 A             血缘服务 B             血缘服务 C
   （明细留本地）          （明细留本地）          （明细留本地）
      │                      │                      │
      │  只上送：URN + 边 + 时间戳 + 采集器类型       │
      │  （元数据，不含任何数据内容与 SQL 原文）      │
      └──────────┬───────────┴──────────┬───────────┘
                 ▼                      ▼
            跨云汇聚层（只存骨架图，不存明细）
                 │
                 ▼
        统一视图 / 跨云影响面（明细按需回源查询）
     ────────────────────────────────────────────────────
     关键：跨越云边界的只有"谁指向谁"，不是"数据本身"
```

```sql
-- 汇聚层能存什么、不能存什么，由合规决定，应当写进 schema 里
CREATE TABLE cross_cloud_skeleton (
  urn          TEXT NOT NULL,       -- 允许：实体身份
  cloud        TEXT NOT NULL,       -- 允许：所在云/地域
  region       TEXT NOT NULL,       -- 允许：地域（决定是否跨境）
  edge_to      TEXT,                -- 允许：骨架边
  edge_kind    TEXT,                -- 允许：table / column（不含表达式）
  collected_at TIMESTAMPTZ NOT NULL,
  -- 禁止：sql_text、sample_rows、owner 的姓名与联系方式等可识别信息
  CHECK (region IS NOT NULL)
);
```

- **为什么这样设计有效**：因为明细查询在数据所在云完成，向上只汇「身份 + 边 + 时间」这类不含数据内容的元数据，跨云视图的构建不触发数据跨域传输——这让「统一视图」与「数据不出境」这对看似冲突的要求可以同时满足。代价是把一部分查询能力搬到了回源环节。
- **代价**：① 每个云各建一套采集与服务，运维面按云数倍增；② URN 命名必须跨云统一，而两朵云上的同名表默认不是同一个实体；③ 跨云路径查询要串行经过多次网络跳，交互式查询体验受制于跨云链路；④ 回源查询要求各云同时在线，任何一朵云不可用都会让跨云影响面不完整——而「不完整的影响面」在变更决策里和「没有影响面」一样危险。
- **失效点**：当同一条链路在两朵云里被赋予两个 URN（或跨云延迟超过交互式查询的容忍）时，优点「统一视图」反转成「看起来统一、实际不一致」——用户在两个入口查到不同的下游列表，且没有任何机制告诉他对齐是可疑的。修法是把 URN 对齐做成**有仲裁者的注册表**（谁命名、谁裁决冲突、冲突未裁决时如何展示），而不是靠命名规范的自然收敛。
- **真实使用**：主文件 §1.4 把 2023–2025 列为「跨云联邦化阶段」，其 2024 年条目记录 Databricks Lakehouse Federation 与阿里云 DataWorks 跨云【公开】（来源：主文件 §1.4 该阶段条目，可在本仓库直接核到）。Atlan、Collibra、阿里云 DataWorks 跨云属于这类产品形态，但本节未附各家可定位的发布材料（无标题、年份、链接），故只作方向性提示【经验】（判断方法：看它能否给出跨云的端到端路径，而不是看它能否同时列出两朵云上的资产）。要区分「跨云目录」与「跨云血缘」：前者能同时列出两朵云上的资产，不等于能算出跨云的端到端路径【经验】。

#### 3.2.5 AI 驱动血缘（AI-Augmented Lineage）

- **被什么约束逼出来**：采集缺口是系统性的（动态 SQL、脚本、外部导入），而人工补齐的维护成本随资产数线性增长、且登记出来的血缘会在数个月内失去可信度【经验】（区间随团队流程稳定性而异）。缺口因此需要一种**成本不随资产数线性增长**的补全手段。
- **结构**：

```json
{
  "edge_id": "e_7f31...",
  "src_urn": "urn:li:dataset:(hive,prod.orders,PROD)",
  "dst_urn": "urn:li:dataset:(hive,dws.trade_1d,PROD)",
  "granularity": "column",
  "column_map": [{"from": "amount", "to": "gmv", "transform": "sum"}],
  "origin": "llm_inferred",
  "evidence": {
    "kind": "job_script",                 // 依据来自哪段文本
    "ref": "job:etl_trade_daily.py@sha256:...",
    "excerpt_hash": "..."                 // 只留指纹，不留原文
  },
  "confidence": 0.0,                      // 由谁校准、校准样本多少，必须说明
  "verified_by": null,                    // null 表示尚未被任何证据确认
  "usable_in_gate": false                 // 未验证的边不得参与门禁判定
}
```

```text
  候选边生成            证据绑定              分级入库
  非结构化输入          能不能指到一段         · verified   → 可参与影响面与门禁
  （脚本 / 文档 /      可复现的文本或           · corroborated → 可展示，标注来源
    对话 / 工单）       配置上？                · inferred   → 只作排查线索，不进门禁
      │                    │                        │
      ▼                    ▼                        ▼
  LLM 生成候选 ────► 有证据才保留 ──────────► 按等级分表存放
                    无证据的只留提示
```

- **同族的三条能力，落点不同**：「自动识别跨域关系 / 自然语言查询血缘 / 智能补全缺失血缘」。**自动识别**（候选边生成）与**智能补全**（分级入库）产出边，共用同一套证据绑定与等级判定——上面的 JSON 就是补出来的那条边的形态；**自然语言查询血缘**消费边而不产出边，它把「某个字段的下游是谁、这次改动动了什么」从图查询语言翻译成自然语言入口。它对证据分级的要求反而更高：回答必须带出处与置信等级，否则提问者分不清答的是解析得到的边还是模型推断的边，也就无法判断这个答案能不能拿去改流程。
- **为什么这样设计有效**：因为 LLM 能吃进解析器覆盖不到的非结构化输入（脚本正文、变更工单、指标文档），它恰好补在主文件 §2.3 那五类采集方法的盲区上；而只要每条边强制携带证据引用与置信度、并且**按等级决定它能不能参与判定**，补全带来的假边就不会污染真实结论。
- **代价**：① 推理成本随资产数与变更频率增长，且需要定期重跑（否则补出来的边同样会过期）；② 每条候选边都需要证据与判定留痕，存储与审核成本随边数增长；③ 引入一种新的失败模式——**假边**，它比缺边更难发现，因为缺边会让查询报「无上游」，假边会让查询报出一个合理但错误的上游；④ 需要一个「谁来确认」的流程，而这个流程若没人负责，`verified_by` 会永远是 null。
- **失效点**：当 AI 补全的边没有与可验证证据绑定、也没有在下游（影响面分析、发布门禁）区分对待时，优点「补全缺口」反转成「污染图谱」——门禁会把模型猜出来的边当成事实去阻断或放行。此时团队对血缘的信任崩塌方式很典型：一次误拦截之后，所有人开始绕过门禁，而绕过比不建门禁更糟。修法是**门禁只信解析得到的边**，AI 边仅用于展示与排查线索，并在等级提升前必须有人工或运行时证据确认。
- **自验方法**：从图谱里随机抽 10 条 AI 产生的边，要求给出它们的证据引用；答不出证据的边占比就是这套补全的不可信比例。
- **真实使用**：主文件 §1.4 把「AI 驱动血缘补全」记入 2024 年、「LLM-as-a-Lineage」记入 2025 年，即 2024+ 演进阶段【公开】（来源：主文件 §1.4「AI 时代（2024+）」条目，可在本仓库直接核到）。Atlan AI、Collibra AI、阿里云 DataWorks 智能血缘属于产品宣称的 AI 辅助能力，本节未附各家可定位的发布材料（无标题、年份、链接），故只作方向性提示【经验】。判断方法：要求演示「这条边是怎么得出来的、证据在哪里」——答不出证据来源的输出是推荐，不是血缘【经验】。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 多团队 / Data Mesh，各域要保留采集与命名自主权 | 3.2.1 联邦血缘 | 不用集中式：拿不到各域的采集授权，集中只会得到一份过期的副本 | 新增域时是否需要搬迁历史血缘 |
| 单一法人主体、强合规、需要全局一致视图 | 集中式采集 + 3.2.3 网关 | 不用纯联邦：无全局快照，跨域查询延迟不可控 | 是否存在禁止汇聚的合规约束（若存在则回到 3.2.4） |
| 多云 / 自建混合，受数据出境约束 | 3.2.4 跨云血缘（骨架汇聚 + 明细回源） | 不用全局单点集中：汇聚那一刻就构成跨境传输 | 是否有字段必须留在境内 |
| 实时流 + 批流一体，链路跨引擎 | 3.2.2 端到端血缘 | 不用单域血缘：链路的第一跳就看不见 | 链路上每一跳是否都有采集器 |
| 多个消费方（目录 / 质量 / 权限 / CI / Agent） | 3.2.3 API 网关 | 不让各消费方各自解析：口径必然漂移 | 消费方数量是否 ≥2 且是否会增加 |
| 存在大量脚本 / 动态 SQL / 手工导数 | 3.2.2 自动采集 + 运行时兜底 + 3.2.5 分级补全 | 不用纯静态解析：这些恰恰是解析不到的那部分 | 解析失败的边占比是否被度量 |
| AI 时代：Agent 取数与模型审计 | 3.2.3 网关 + 3.2.5 分级补全 | 不只看可视化：Agent 要的是可编程、带新鲜度的接口 | 血缘返回值是否带出处与 lastUpdated |
| 早期 0→1（单域、百级表【经验】） | 3.2.2 的自动采集子集 + 开源栈 | 不上联邦与跨云：这两层的成本只有在多域/多云时才收得回来 | 是否真的存在第二个需要对齐的域 |

表后要单独说清**最常被误选的一对**：「联邦」与「集中」被当成按组织规模二选一的选项，而多数团队实际做的是「集中式采集 + 联邦式展示」【经验】——采集集中（所以拿到了全局一致性），展示联邦（所以各域看不到别人的明细）。误选的后果在机制上是确定的：如果先去建联邦层，URN 对齐就成了必须提前完成的前置工作，而对齐是**唯一需要人来裁决的环节**，它一旦拖延，联邦层就只能把两套身份并列展示，此时看起来有统一入口、实际没有统一实体，跨域路径查询永远查不出结果——而系统不会报错，它会返回空。

第二对容易被混的是「API 网关」与「可视化」：前者是服务能力，后者是消费形态之一。只做可视化而没有 API，血缘就只能被人工查阅，无法进 CI 门禁，也就无法在变更发生前产生任何约束力；反之只做 API 而没有任何嵌入流程的消费方，血缘会退化成「一个没人调的接口」（见 3.5）。

### 3.4 组合模式：真实系统不会只用一种

**组合一：自动采集（端到端）+ 统一存储 + 网关对外。** 构成是「各引擎采集器（3.2.2）→ 统一血缘存储（OpenLineage 模型）→ API 网关（3.2.3）→ 消费方」。职责边界：采集层只管「采得全不全」，存储层只管「身份对不对」，网关只管「谁能看、多快看到、看到的是不是旧的」；三者分开后，覆盖率、对齐率、新鲜度是三个可以独立度量的指标。运维代价是三套组件的版本协同，以及网关缓存策略与采集周期必须一起调（缓存 TTL 超过采集周期就会稳定返回旧图）。适合的规模：单主体、表规模千级到十万级、消费方 ≥2 的组织【经验】；只有百级表且只有一个消费方时，网关这一跳可以直接省掉。

**组合二：联邦层 + URN 对齐注册表 + 高频路径物化。** 构成是「各域血缘服务（3.2.1）→ 联邦层路由 → 对齐注册表 → 把最常查的跨域子图物化成本地只读图」。职责边界：联邦层负责「去哪找」，注册表负责「谁等于谁」（唯一允许人工介入的地方），物化子图负责「把最贵的那几条查询变便宜」。运维代价是物化子图必然滞后于源域，因此它必须带一个「物化时间」并在结果里显示，否则它会变成第二个失真源。适合的规模：域数 ≥5、跨域桥接边数量在千级以内【经验】；桥接边到十万级时，物化子图的维护成本会超过联邦查询本身，此时应当反过来考虑局部集中。

**组合三：跨云骨架汇聚 + 域内明细 + 回源查询。** 构成是「各云内完整血缘（3.2.4）→ 只上送 URN/边/时间/地域 → 跨云骨架图 → 跨云路径查询按需回源」。职责边界：骨架层回答「跨云链路存不存在」，域内服务回答「这条链路的具体字段映射是什么」；冲突时以域内为准，骨架层永远不被当作明细源。运维代价是回源链路要处理部分可用（一朵云不可用时返回的是「不完整」而非「无下游」，两者必须在接口上区分）。适合的规模：多朵云或公有云 + 自建机房并用，且存在明确的数据出境约束。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 血缘采集永远不全 | 解析失败的作业无人统计；动态 SQL 与脚本任务不在图里；覆盖率靠抽样估计而非分母可查 | 影响面永远是下界，变更决策建立在错误的安全感上；缺口不报警，只在事故里暴露 | 解析失败被当作个别问题逐条处理，而不是被当作一个必须持续度量的比率 | 把「解析失败率」与「manual 边占比」做成指标；对无法解析的作业用运行时采集兜底 |
| 联邦血缘变成信息孤岛 | 联邦层能列出多个域，但跨域路径查询返回空；同一张表在两个域里有两条身份 | 「统一入口」只统一了界面，没统一实体，跨域影响面恒为空且不报错 | 先建了联邦层，URN 对齐被排在其后，而对齐需要业务裁决、没人愿意负责 | 建 URN 对齐注册表并指定仲裁者；对齐未完成时在接口上显式标为「未对齐」而非静默并入 |
| 血缘 API 没人用 | 接口调用量集中在建设期，之后趋平；没有任何流程依赖它；变更照样靠发通知 | 血缘退化成参考资料，不产生约束力；投入的采集成本无法转化为事故下降 | 项目以「接口上线」为验收标准，没有以「某条流程依赖它」为验收标准 | 把影响面查询嵌进数据申请与变更流程（发布门禁），让不用它就走不下去 |
| 可视化漂亮但查询慢 | 点开一个深链路要等数十秒；图渲染完成但用户已经不看了 | 用户放弃深链路查询，只查一跳，血缘能力退化成表级邻接表 | 图存储只按可视化需要建模（存节点与边），没有为「按实体反查 + 按时间过滤」建索引 | 为高频查询路径建索引或物化：反向查询按目标实体建索引，深链路设深度上限并分页 |
| 忽视血缘时序 | 只有当前状态，没有历史版本；复盘时无法回答「当时的影响面」 | 事故复盘失去依据，只能事后重建图，而重建的图已被后续变更污染 | 时序被当作「以后再说」的增强项，而它恰恰是复盘场景的必要条件 | 边带 valid_from / produced_at；对关键变更保留血缘快照；区分「当前图」与「时刻图」 |
| 假边污染（AI 补全未验证） | 图谱里存在来源不明的边；门禁误拦截后团队开始申请豁免 | 错误的血缘比缺失的血缘更危险——缺失会报「无上游」，错误会给出一个合理的错误答案 | 补全结果被直接并入主图，没有区分「解析得到」与「模型推断」 | 边必须带 origin 与 evidence；未验证的边只能作排查线索，不得参与门禁判定 |
| URN 不对齐（同一实体多条身份） | 同一个表在两条路径里显示为两个节点；下游列表少于预期 | 跨域图被切成互不相连的碎片，端到端路径永远断在身份边界上 | 各系统自带命名习惯，URN 规范被当成文档而不是被当成约束来执行 | 把 URN 生成收口到注册表；接入时强制映射；定期跑一致性检查找出重复身份 |

**最危险的三条，在生产中这样暴露。** 第一是「血缘采集永远不全」：它的危险在于**缺口与信心方向相反**——采得越多的团队越相信血缘，而缺口恰恰集中在最不规范的、也最可能是关键链路的长尾作业上（脚本、临时任务、手工导数）。它的暴露方式几乎总是「变更后下游静默算错」而不是报错。识别方法很直接：统计 `collector = manual` 的边占比与解析失败率，而不是统计总边数。第二是「假边污染」：这是本主题下新增最快的风险面，因为 LLM 补全的产量远高于人工登记，而它产生错误的速度也远高于人工——一套没有证据分级机制的补全，可以在几周内把主图的可信度拉到无法用于门禁的程度，而团队通常在第一次误拦截之后才发现。第三是「URN 不对齐」：它的危险在于**沉默**——关联不上时查询返回空结果，用户会把这理解为「没有下游」，而不是「没对齐」；一次变更决策因此可能建立在一个空的、但看起来正常的答案上。

**这些反模式会互相掩盖。** 「API 没人用」会掩盖「URN 不对齐」——因为没人跨域查询，碎片化就不会暴露；「采集永远不全」会掩盖「假边污染」——反正真边也不全，假边被当成补充；「忽视血缘时序」会掩盖前三条——没有历史版本，就无法事后判断某个错误结论是「当时就错了」还是「后来漂移的」。因此诊断顺序应当是反过来的：先查「有没有被真实流程依赖」（有没有用），再查「身份对不对」（对齐率），最后才查「覆盖了多少」（覆盖率）。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单域 → 2 个域 | 单域血缘（一张图走天下） | 跨域的那几条边没有归属，两边都不采 | 联邦层（路由 + 对齐表） | 必须先做 URN 对齐，这是唯一需要人裁决的环节，无法自动化绕过 |
| 域数 2 → 10+【经验】 | 联邦层直查 | 每个查询串行经过多个域，延迟随跳数增长 | 联邦 + 高频跨域子图物化 | 物化子图必然滞后，需要携带并展示物化时间 |
| 边数 → 十万级【经验】 | 单机图存储 + 内存遍历 | 深链路递归的中间结果集超过内存 | 分布式图存储 + 查询深度上限 + 分页 | 拆图会削弱「一次遍历拿全路径」的能力，需要按实体分片并接受跨片查询更贵 |
| 血缘从「有人查」→「门禁依赖」 | 最终一致、有缓存的血缘服务 | 门禁要求确定性与低延迟，缓存返回旧图会误判 | 门禁读路径与展示读路径分离 | 门禁路径要保证新鲜度，代价是它拿不到缓存带来的低延迟 |
| 单云 → 多云 | 集中式汇聚 | 汇聚那一刻构成跨境传输 | 跨云骨架汇聚 + 明细回源（3.2.4） | 要重新定义「什么元数据允许跨云」，并接受部分可用时返回不完整结果 |
| 静态图 → 时序图 | 只存当前状态 | 复盘要的是当时的影响面 | 边带时间戳 + 关键时刻快照 | 存储量随时间增长，需要为快照设保留期与压缩策略 |
| 人工补登记 → AI 补全 | 人登记、全量入图 | 登记会过期，而补全产量远高于人工 | 分级入库（verified / corroborated / inferred） | 需要建证据绑定与等级判定，并让门禁只信高等级边 |
| 一个消费方 → 多消费方 | 各消费方各自解析 SQL | 同一实体得出不同下游，口径漂移 | API 网关（3.2.3）+ 统一血缘模型 | 接口成为契约，改语义要协调所有消费方 |

**跃迁的共同规律**：八次跃迁里有六次是「把原来混在一起的东西分开」——域内与跨域分开、单机图拆成按实体分片的分布式图、门禁读路径与展示读路径分开、骨架与明细分开、当前图与时刻图分开、真边与推断边分级。方向相反的是另外两次：「域数 2 → 10+」把分散在各域的跨域子图**物化**回一张只读图，这是「合」；「一个消费方 → 多个消费方」把各家自己解析的口径收口到一个网关，这也是「合」。原因是血缘系统的成本与风险都由「边的数量 × 需要回溯的时间长度」决定，而任何一次规模跃迁都不会让这个乘积变小，所以只能靠分区与分级化解；至于该分还是该合，取决于当时的瓶颈是存储与跳数（→ 分）还是口径一致性（→ 合）。

### 3.7 自检清单

- [ ] 有没有一个可查的**分母**来算采集覆盖率（自动解析成功的作业数 / 全部作业数），而不是靠抽样估计？
- [ ] 解析失败的作业是否被单独列出并纳入待办？还是它们只是「没出现在图里」？
- [ ] URN 由谁生成？两个域里的同名表，是否有一条明确规则判定它们是不是同一个实体？
- [ ] 存在一个「对齐仲裁者」吗？对齐冲突时谁来裁决，裁决结果记录在哪里？
- [ ] 血缘查询的返回值里，是否带 `lastUpdated` 与采集器类型（parser / hook / runtime / manual）？网关缓存 TTL 是否小于血缘采集周期——若不是，调用方看到的最旧血缘是多久以前的？
- [ ] 是否存在任何一条流程（发布门禁、数据申请、CI）**依赖**血缘查询才能走完？如果没有，它现在只是参考资料。
- [ ] 图谱里有没有「模型推断但无证据」的边？任一 AI 补全的边能否指出它依据的那段文本（脚本、配置、工单），以及它能否参与影响面与门禁判定？
- [ ] 深链路查询（≥3 跳）是否有深度上限与分页？一次查询的最坏结果集有多大？
- [ ] 是否保留过任何「时刻快照」？能否回答「三个月前那次变更当时的影响面是什么」？
- [ ] 是否存在无法解析的作业类型（动态 SQL、脚本、手工导数）？它们是被标记为已知盲区，还是根本不在视野里？
- [ ] 跨云（或跨域）路径查询在某一跳不可用时，返回的是「不完整」还是「无下游」？两者是否在接口上区分？
- [ ] 上一次变更事故里，血缘给出的下游清单是否覆盖了全部实际受影响的下游？差额为什么存在？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 单主体、消费方多、要能进流程 | 自动采集（3.2.2）+ API 网关（3.2.3） | 口径只解析一次，才有唯一答案可被流程依赖 |
| 多域自治、组织上拿不到集中授权 | 联邦血缘（3.2.1）+ 对齐注册表 | 不搬数据即可互通，但互通的前提是身份对齐先成立 |
| 链路上有大量非解析型作业 | 端到端（3.2.2）+ 运行时兜底 + 分级补全（3.2.5） | 缺口是系统性的，只能靠第二采集路径覆盖而非靠人工填 |
| 多云 / 数据出境约束 | 跨云血缘（3.2.4，骨架汇聚 + 明细回源） | 统一视图必须避开统一存储，否则部署本身违法 |
| 要支撑 Agent 取数与模型审计 | 网关（3.2.3）+ 字段级边（3.2.2）+ 时序图（3.6「静态图 → 时序图」） | 机器消费要求可编程、带出处、可回溯到当时状态 |

> 本节小结：决定跨域血缘模式选择的唯一那条约束，是**「实体的身份不掌握在血缘系统手里」**——所有模式差异都可以还原为「谁来做身份对齐、在什么粒度上对齐、对不齐时系统如何表现」。存储选图还是选关系表、网关用 GraphQL 还是 REST、补全用不用 LLM，都是这条约束的下游问题；先把对齐做出来，其余是工程细节。
>
> 💡 **思考锚点**：用 §3.7 的清单量你现有血缘图的两个可算量——采集覆盖率的「分母」（自动解析成功的作业数 ÷ 全部作业数）你答得出来吗，一条 ≥3 跳查询的最坏结果集有没有深度上限与分页？若分母答不出、深度又没上限，卡住你的是采集没覆盖全，还是深链路查询没有护栏？
