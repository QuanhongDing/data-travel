## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本章（迁移版血缘）的三条既有约束分写在三处：**血缘是采集出来的，不是登记出来的**、采集缺口是系统性的（动态 SQL、脚本任务、手工导数三类永远最难采）见 §3.1 的第二条约束；一条链路的可信度等于**最弱那一跳**见 §3.2.2 的代价④；联邦化的成立条件是「中央只存路由、对齐与桥接，明细留在各域」见 §3.2.1 的结构与「为什么这样设计有效」。前两条在 §7.3.2、第三条在 §7.3.3 另有机制层面的重述。

本节要判的不是「AI 能不能接进血缘」，而是**新增的边与新增的消费者会不会撞上这三条**。例如把模型推断出来的边当成事实送进发布门禁，撞上的就是第二条——门禁一旦误拦截一次，团队会开始集中申请豁免，而绕过比不建门禁更糟。

判断哪一条今天能进方案，要先分清两类东西：一类是**既有能力**（自动采集、字段级血缘、受影响面查询、API 化），它们不是 AI 带来的，本节只在需要对照时提及；另一类是**AI 时代新增的方向**，本节对它们逐个定级。

本节用 L1 / L2 / L3 三级划分，判据必须可核验，而不是「感觉成熟」：

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note（规范类项目按其版本化发布物计）；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口 / 生态未稳，或**仅有厂商或项目发起方自有案例**，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

**本节不对 L1 判据做任何修正**，也不缩小它的适用范围。本主题最诱人放宽的地方正是第②条：血缘领域有一批公开仓库、有跨工具规范、有项目发起方的工程文章，很容易把「有公开的机制性材料」当成「有第三方生产案例」。但项目发起方自己的工程文章按判据读就是**建设方自述**，正是 L2 的定义；把判据改写成「可被第三方复核」之后，读者按新措辞照样核验不了。

写法上还有四件容易混的事，先在这里分开：

- **产品名 vs 能力名**：「AI 推断血缘」「自然语言查血缘」是**能力名**，不是某个产品的专属功能；同一能力在不同厂商材料里挂在不同的产品名下。判定方法：按**产品全名 + 该能力的输入输出**去核对，而不是按能力名归类。
- **规范 vs 产品**：OpenLineage 是**跨工具的事件规范**，Marquez 是它的参考实现，DataHub 同时提供采集与消费端能力（§3.2.2）。三者的版本节奏与承诺不同，不能把「规范有版本」读成「某产品已 GA 某能力」。
- **单域 vs 跨域**：单域内的自动采集与字段级血缘是已建成能力；跨域、跨云是另一套语义（对齐表、桥接边、远端调用），不能拿单域内的覆盖率去推算跨域结论。
- **论文原型 vs 产品实现**：论文里演示的是**方法可行性**，产品里的实现受采集器、方言与作业类型的约束。判定方法：看该实现有没有把「解析失败」与「无法解析」显式暴露出来。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**——改变了成本结构、改变了接口边界、把人工判断换成统计判断，还是只换了个前端？本主题的答案很集中：**没有一条改变了可达性的性质**。真正落在机制上的只有一条——**边际成本的位置从人的注意力挪到了算力**：AI 补全改变的是**补全成本的增长形状**，自然语言入口改变的是**入口的词汇责任**。跨云、时序、API 化与 AI 没有因果关系，它们是既有工程取舍的延伸；Agent 探索与图谱推理则只换了前端。

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| LLM 辅助血缘补全（依据为代码注释 / 数据采样 / 业务文档 / 血缘模式） | **L2** | ① 形态已在书内 §3.2.5 定义（候选边 + 证据绑定 + 分级入库）；**②核不到**（产品侧只有厂商材料，见 §4.3）；③ 置信度与判定分级无通行约定 | 先把边的 `origin` / `evidence` / `usable_in_gate` 三个字段定下来 |
| 自然语言查询血缘 | **L2** | ① 形态见 §3.2.3（血缘 API 网关之上的消费者）；**②核不到**；③ 各家的问答权限与出处格式不统一 | 可做 PoC：入口必须复用同一套权限与 URN |
| 血缘文档 / 注释向量化检索 | **L2** | ① 向量检索是通用成熟能力；**②核不到**（本主题没有第三方生产案例可指）；③ 文档与图谱的边界没有约定 | 只把它当**线索**，不得作为影响面结论 |
| RAG 接入血缘 | **L2** | 同上一行：问答层消费边而不产出边；回答必须区分「确定无上游」与「这一段没采到」 | 与上两行合并交付，不要另建一份血缘 |
| Agent 驱动的血缘探索 | **L3** | ① 仅方向，无正式条目；③ 无接口约定；②不适用 —— 「哪个节点算根因」没有可核验的判据，结论也无法指回具体的边 | 记录；不要让它直接驱动变更流程 |
| 图谱推理 | **L3** | ① 仅论文与演示（见 5.4）；③ 无接口约定；②不适用 —— 可达性查询用图遍历更准也更便宜 | 记录；不要为此改图模型（见 5.5） |
| 训练数据血缘与模型侧追溯 | **L2** | ① 链路打通到模型特征是书内 §9.2、§9.5 的既有做法；**②核不到**；③ 特征 / 标注 / 导出的采集方式各家不同 | 把特征接进同一张图，不要另起一套 |
| 跨云与联邦血缘（Databricks Lakehouse Federation、Unity Catalog 跨云、阿里云 DataWorks 跨云） | **L2** | ① 形态见 §3.2.1、§3.2.4，跨云条目见主文件 §1.4 的 2024 年条目；**②核不到**；③ 对齐与桥接的接口无标准 | 先做全局标识与对齐表，再谈跨云 |
| 血缘 API 网关标准化 / 血缘即服务 | **L2** | ① 网关形态见 §3.2.3，规范侧有版本化发布物（OpenLineage）；**②核不到**；③ API 形态（REST / GraphQL）无共识 | 按 §3.2.3 的边界做，接口先对内 |
| 血缘时序与版本管理（VLDB 方向） | **L2** | ① 边带时间戳是 §3.2.2 边结构的既有字段；**②核不到**；③ 版本语义（快照 / 有效期）各实现不同 | 先把 `produced_at` 与校准时间写进边 |
| 血缘与 AI 治理融合 | **L2** | ①②③ 同第 7 行（**②核不到**）；机制上与该行同源（模型侧追溯）；制度侧要求见 5.4 | 与第 7 行合并推进，不单独立项 |

> 表里**没有任何一行达到 L1**：第 5、6 两行是 L3（只有方向、没有可核验条目，卡在①），其余 9 行则同时卡在②与③。这不是保守，而是本主题公开材料的构成决定的——可核验的材料只有**项目与规范文档**（属建设方一侧）与**厂商产品材料**两类，其余则是论文。按判据①它们大多成立，②与③则都不成立；所以**最高评级是 L2**，且 11 行里有 9 行停在 L2。**L2 不等于「不好」，只等于「公开证据到不了 L1」**——要警惕的是把 L2 当 L1 写进「所以我们可以让门禁信任模型推断的边」这类结论。

有两行的定级值得单独解释：

- **LLM 补全为什么不是 L3**：它不是路线图，也不能是纯演示——书内 §3.2.5 已经给出它的边结构与分级规则，且它补的正好是解析器的系统性盲区。但它也到不了 L1：**判据②核不到**，而且它的失败模式（假边）需要靠抽检度量，而不是靠功能清单。因此 L2，且必须限定在「展示与排查线索」这一侧。
- **OpenLineage 相关的行为什么仍是 L2**：规范有版本化发布（判据①成立），但判据②要求的是**第三方非厂商的生产案例**；经常被引用的落地案例里，项目发起方自己的工程文章属建设方自述。规范可以排进方案，前提是你自己按 §7.3.2 的方法度量了 `collector = manual` 与解析失败的比例。

### 5.2 演进方向逐条拆解（核心节）

下面把 5.1 表的 11 个方向按机制聚成 4 组，逐组给出六段拆解（旧做法与卡点 / 机制改变 / 由此得到 / 由此付出 / 证据 / 成熟度），级别与 5.1 表逐行一致。

落点映射：第 1 行 → 5.2.1；第 2、3、4 行 → 5.2.2；第 8、10 行 → 5.2.3；第 7、11 行 → 5.2.4；第 9 行（网关标准化 / 血缘即服务）不进 5.2，落在 5.3 的网关接口边界与 5.7；第 5、6 行（Agent 探索与图谱推理）机制尚未定型，放在 5.5 处理。

先给一张机制对照，便于建立整体感：

| 方向（5.1 表行号） | AI 改变的一句话机制 | 级别 |
| --- | --- | --- |
| 1 | 补全成本的增长形状变了（不再随资产数线性），边的可信度没变 | L2 |
| 2、3、4 | 把「问题到查询条件」的翻译交给模型，节点定位与边遍历仍是确定性的 | L2 |
| 7、11 | 把 AI 侧的可追溯并到同一张图上，追溯路径变短 | L2 |
| 8、10 | 未改变机制：统一的位置从存储层挪到身份层，是工程取舍不是 AI 带来的 | L2 |
| 9 | 未改变机制：统一的位置从存储层挪到**接口层**（网关收敛的是入口、权限与新鲜度，不是身份），同样是工程取舍 | L2 |
| 5、6 | 只换了入口的形态，未改变可达性查询的性质（见 5.5） | L3 |

#### 5.2.1 LLM 辅助血缘补全：把「覆盖率」换成「覆盖率 + 可信边占比」

- **旧做法与它的卡点**：采集缺口是系统性的——动态 SQL、脚本任务、手工导数这三类永远最难解析（§7.3.2），而人工补齐的维护成本随资产数线性增长，登记出来的血缘在几次人员与流程变动后就失去可信度【经验】。
  - 缺口不是随机的：它集中在长尾系统与临时作业上，而这些恰恰可能是关键链路的一环。
- **AI 改变了什么机制**：补全从「解析」扩成「推断 + 证据绑定」——模型吃进解析器覆盖不到的非结构化输入（脚本正文、变更工单、指标文档），产出候选边。
  - 它改变的是**补全成本的增长形状**（不再随资产数线性增长），而不是边的可信度；这一点是整节的关键区分。
- **由此得到的**：因为候选边与证据、置信度一起入库，并按 verified / corroborated / inferred 分级，缺口可以被补到「已知且被标注」的程度，而门禁仍然只信解析与运行时得到的边（§3.2.5 的 `usable_in_gate`）。
  - 于是「补全缺口」与「守住可信度」不再互相绑架：缺边报「无上游」（可从告警发现），假边报一个合理但错误的上游（最难发现）——两者被分表存放，前者的存在不再成为后者的借口。
- **由此付出的**：
  - ① **假边**这种失败模式比缺边更难发现，而它一旦进入判定（门禁、估值、审计）就会直接制造错误结论；
  - ② 推理成本随资产数与变更频率增长，且要定期重跑，否则补出来的边同样会过期；
  - ③ 需要一条「谁来确认」的流程，没人负责时 `verified_by` 永远是 null，分级形同虚设；
  - ④ 可信边占比只能用抽样度量：抽 10 条要求给出证据引用，答不出的比例就是不可信比例。
- **证据与来源**：【公开】边分级（verified / corroborated / inferred）与候选边 JSON 的字段（`origin` / `evidence` / `confidence` / `usable_in_gate`）见 §3.2.5，主文件 §1.4 把「AI 驱动血缘补全」记入 2024 年条目；而「四类依据」（代码注释 / 数据采样 / 业务文档 / 血缘模式）书内没有与它对得上的机制定义，只能按**待核验的能力声称**读。**判据②核不到**：产品侧的 AI 辅助能力（§4.3 列出的 Atlan AI、Collibra AI、阿里云 DataWorks 智能血缘）属厂商材料，本节不附可定位的发布条目。
  - 判定方法：要求演示「这条边是怎么得出来的、证据在哪里」——答不出证据来源的输出是推荐，不是血缘。
- **成熟度**：**L2（可试点）**——可补缺口、可做排查线索，但不得作为门禁与影响面判定的依据。

```sql
-- 覆盖率与可信度是两个指标，必须分开看（只看覆盖率会掩盖假边）
SELECT collector,
       COUNT(*)                                            AS edges,
       ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 1)  AS pct
FROM   lineage_edge
GROUP  BY collector;        -- parser / hook / runtime / manual / llm_inferred

SELECT origin, COUNT(*) AS n,
       COUNT(evidence_ref) AS with_evidence,   -- 带证据的比例
       COUNT(verified_by)  AS verified         -- 有人确认过的比例
FROM   lineage_edge
WHERE  collector IN ('manual', 'llm_inferred')
GROUP  BY origin;
-- 判据：门禁只读 usable_in_gate = true 的边；
-- 这个字段只能由 parser / runtime / 人工确认置真，模型推断不能自己置真
```

#### 5.2.2 自然语言入口：把图查询语言的门槛挪到模型侧

- **旧做法与它的卡点**：血缘的消费者只有少数会写图查询或调用 API 的人。
  - 业务方与 oncall 有真问题（「这张表今天为什么没数据」「谁改过这个字段」），但进不了入口；跨域之后，问题还要跨系统拼出来（§1.2 的「血缘难查询」）。
- **AI 改变了什么机制**：把「自然语言问题 → 查询条件」这一步交给模型，检索层用向量 + 倒排找候选节点与文档片段，回答的最后一步再回到图上做**确定性遍历**。
  - 它改变的是**入口的词汇责任**，不是边的生产：节点定位与可达性仍由图决定。文档向量化在这个结构里只承担「找候选」，不承担结论。
- **由此得到的**：因为答案的最后一步是图遍历，所以它能带出处（哪条边、哪个作业、什么时间），这与纯文档问答的区别在于**可核验性**；因为入口变低了，「从现象到上游」这一步第一次不需要人代查。
  - 对 oncall 而言，这直接缩短故障定位的第一跳：先问「这些异常指标的上游共同点是谁」，比先想「该用哪个工具查」快得多。
- **由此付出的**：
  - ① 问答层必须复用同一套权限与 URN，否则它成为绕过密级过滤的旁路（§3.2.3 的网关之上不能再开一个不受约束的入口）；
  - ② 回答必须区分「确定无上游」与「这一段没采到」（§7.3.3）——把不完整答成「无」，比不回答更危险，因为变更决策会把「不知道」当成「没有」；
  - ③ 文档片段会过期：注释与真实作业不一致时，它会给出一个「有依据的错误答案」；
  - ④ 成本随提问量增长，而 oncall 高峰正是最需要它的时候。
- **证据与来源**：【公开】消费者边界与网关形态见 §3.2.3；边结构与 `produced_at` 见 §3.2.2。产品侧（Atlan AI、Collibra AI、阿里云 DataWorks 智能血缘）为**厂商材料**，见 §4.3。**判据②核不到**。
  - 判定方法：分别问一个「已确认无上游」的字段与一个「本就没采集到」的字段，看两次回答是否不同。
- **成熟度**：**L2（可试点）**——可以试，前提是入口复用同一套权限，且回答能区分「无」与「未知」。

```text
影响面回答必须能落进三个状态之一（否则「不知道」会被读成「没有」）

  问题：改了 dwd_order.amount，会波及谁？
  ────────────────────────────────────────────────
  ① 有下游      → 返回节点与路径，每条边带 source_sys 与 collector
  ② 确定无下游   → 该节点在图中存在，且下游遍历确实为空
  ③ 不完整      → 链路上存在未采集 / 解析失败的段（盲区），必须显式标注
                  · 不能说成「无下游」
                  · 变更决策应把 ③ 读成「先补采，再决定」
  ────────────────────────────────────────────────
  判据：统计返回 ③ 的比例；它就是这个组织当前的血缘盲区占比
```

#### 5.2.3 跨云与联邦：把「统一」从存储层挪到身份层

- **旧做法与它的卡点**：没有任何单一系统装得下全组织的血缘；而把明细集中到一处，意味着各域要交出采集权与命名权，在跨云场景里还可能直接触碰数据出境约束——这不是成本问题而是合法性问题（§7.3.3）。
- **AI 改变了什么机制**：这个方向**没有 AI 带来的机制变化**，它是既有工程取舍的延伸：联邦层只存三样东西（路由 / 身份对齐 / 桥接边），明细留在各域；跨云再收一层，跨越云边界的只有「谁指向谁」，明细查询回到数据所在的云完成。
  - 换句话说，统一发生的位置从**存储层**挪到了**身份层**。本节把它列进来，是因为它决定了 AI 入口能问到哪里——模型能看到的图边界，就是这个边界。
  - 跨云版本再把「统一」收窄一层：跨越云边界的只有身份与边（§3.2.4）。
- **由此得到的**：因为只要登记映射、不必搬历史血缘，所以新增一个域或一朵云的边际成本与已有规模无关；因为明细不搬家，「统一视图」与「数据不出境」可以同时成立。
  - 又因为每条边都带 `produced_at`，血缘时序与版本管理在这套结构里第一次是**同一个字段的性质**（边的有效期），而不是另做一套快照机制。
- **由此付出的**：
  - ① 每次跨域查询退化成多次远端调用，延迟由最慢的域决定；
  - ② 拿不到全局一致性快照——两个域的采集时间不同，合并出的路径可能对应两个不同的时刻；
  - ③ 对齐表成为新的单点与热点，也是唯一能被人为引入错误的地方；
  - ④ 任一云不可用时跨云影响面不完整，接口上必须把「不完整」与「无下游」分开。
- **证据与来源**：【公开】联邦与跨云的形态见 §3.2.1、§3.2.4；Databricks Lakehouse Federation 与阿里云 DataWorks 跨云记在主文件 §1.4 的 2024 年条目；OpenLineage 是跨工具的事件规范、Marquez 是参考实现（§3.2.2），**不写死版本号，以项目当前文档为准**。**判据②核不到**：经常被引用的落地材料里，项目发起方自述占多数。
  - 判定方法：数一次典型跨域查询实际发起的远端调用次数；再用「某一跳不可用」做一次故障演练，看返回的是「不完整」还是「无下游」。
- **成熟度**：**L2（可试点）**——形态清楚、边界清楚，但没有可核验的第三方生产案例；先做标识与对齐，再谈跨云。

#### 5.2.4 训练数据血缘：把 AI 侧的可追溯并到生产血缘上

- **旧做法与它的卡点**：模型出问题时，「训练数据来自哪条链路、中间经过哪些口径变换」通常答不出来。
  - 常见形态是训练数据被导出到对象存储后再用，而这最后一跳（导出）不在图里——于是所有下游追溯都断在这里；常与血缘并列出现的「可信度评估」与「漂移检测」，其实不是血缘的能力。
- **AI 改变了什么机制**：把特征与训练用的表接进**同一张图**（§9.2、§9.5 的做法里「链路打通到最终消费」本来就包含模型特征），并补上「数据来源与治理记录」这类文档。
  - 它改变的是**追溯路径的长度**（从「另找一份清单」变成「沿边走到导出点」）；治理条款本身不产生血缘。
- **由此得到的**：因为模型特征是图中的节点，所以「改这个特征会影响哪些线上模型」从人工问答变成查询结果；因为来源记录被写进技术文档，训练数据的来源与用途第一次有了可核验的载体。
  - 这也让 5.1 表第 11 行（血缘与 AI 治理融合）有了具体落点：融合发生在**同一份边与同一份来源记录**上，而不是两套系统互相导入。
  - 标注与人工审核产生的边同样是新来源：它们不来自 SQL 解析，必须带来源标记，否则会被当成解析结果参与判定。
- **由此付出的**：
  - ① 训练侧引入新的边来源（导出作业、特征工程、标注），覆盖率的分母继续变大；
  - ② 「导出到对象存储」这一跳必须显式建模，否则追溯会静默断开；
  - ③ **漂移检测不是血缘的能力**：血缘回答「输入变了会波及谁」，而「输入分布变了」要靠统计监控，混用会得出错误结论；
  - ④ 合规文档与血缘是两份材料，靠人同步必然分叉——可行的做法是让文档生成在图上，而不是并排维护。
- **证据与来源**：【公开】链路打通到最终消费（含模型特征）见 §9.2 与 §9.5 的落地路径；文档化与来源审计的公开工作见 5.4。**判据②核不到**。
  - 判定方法：从线上模型反查它的特征与训练表，看能不能一路走回源头表而不在「导出」这一跳断开。
- **成熟度**：**L2（可试点）**——做法清楚、可核验的部分是「同一张图」这个前提，但要自己度量导出跳的覆盖。

### 5.3 与本主题既有栈的接口在哪

不写「与 X 结合」这种话，写清接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| §3.2.5 候选边分级 | AI 层写 `origin = llm_inferred` 的候选边，必须携带 `evidence` 与 `confidence`；判定侧只读 `usable_in_gate = true` | 把未验证的边放进判定的那一次配置变更 | 需要一次字段补齐；`confidence` 的校准样本与判定人要写清 |
| §3.2.2 边结构（采集器与时间） | AI 补全只补 `collector = manual` 的缺口，不覆盖 parser / runtime 产出的边 | 用模型掩盖解析器的缺陷，由引入方负责 | 先有 `collector` 与 `produced_at` 两列再谈补全 |
| §3.2.3 血缘 API 网关 | 自然语言入口与 Agent 都是网关之上的消费者，必须复用同一套权限与 URN | 问答层绕开权限过滤，由问答层负责 | 不要为问答单独建一份血缘 |
| 影响面与门禁 | 影响面查询必须区分「不完整」「无下游」「有下游」三态；推断边不得参与阻断 | 把不确定当确定的那次判定 | 见 §7.3.3 的接口要求 |
| §3.2.1 联邦层（对齐表） | 跨域只上送身份、边与时间；明细按需回源 | 对齐表引入的错误由维护对齐表的一方负责 | 跨云骨架按主文件 §1.4 的 2024 年条目推进 |
| 模型特征与训练侧 | 特征作为图中的节点接入，与生产边共用同一套 URN 与时间语义 | 特征产出方（导出一跳有没有被建模） | 见 §9.2 的四段链路 |

| 审计与合规 | 审计要的是「来源链路 + 变更历史」，因此推断边必须带 `origin` 才排除得掉 | 把推断边当审计依据 = 审计结论无效 | 见 §9.2 的审计追溯与 §3.2.5 的分级 |

这张表里最容易被写反的是第 1 行与第 3 行：AI 补全**产出**边，问答与 Agent **消费**边，两者的证据要求完全不同——消费侧对证据分级的要求反而更高，因为提问者分不清答的是解析得到的边还是模型推断的边（§3.2.5）。

### 5.4 公开进展与文献

按类型列出（方法类论文 / 规范与项目文档 / 文档化与来源审计 / 法规 / 厂商与项目材料 / 方向线索），每条给出核验入口；括号里是核验方式，不是能力断言。

按 5.1 的三条判据，其中「第三方（非厂商）生产案例」这一类在本主题下**为空**——这就是 5.1 表里没有 L1 行的原因。这类材料的缺失本身就是结论：经常被引用的落地材料里，项目发起方的工程文章占多数，而它们按判据读是建设方自述。

- **方法类论文**：Edge 等《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》（arXiv，2024）——面向**语料级全局摘要**的问答方法。核验方式：读它的任务定义，看它的目标问题是不是「一整个语料在讲什么」，而不是「A 到 B 有没有路径」。
- **规范与项目文档**：OpenLineage 规范与 Marquez 参考实现、DataHub 的图模型与血缘 API（§3.2.2、§9.1）。核验方式：看项目文档里「已集成的作业类型」清单与「解析不了怎么办」这两处；版本号以项目当前文档为准。
- **数据集文档化与来源审计**：Gebru 等《Datasheets for Datasets》（2018）与 Mitchell 等《Model Cards for Model Reporting》（FAT\* 2019）给出了「资产必须带机器可读说明」的字段清单；对公开语料数据集的来源与许可做大规模审计、并给出数据集卡片的一类公开项目（Data Provenance Initiative，2023 年起）是它的工程化版本。核验方式：看它记录的是来源与许可，还是血缘边——**它是审计结果，不是血缘图**。
- **法规侧**：欧盟《人工智能法案》（2024 年生效，其中高风险系统的义务按法案自身的时间表分阶段适用）——它对数据治理与技术文档提出要求，是训练数据可追溯的制度驱动。核验方式：读法案原文的适用时间条款与数据治理相关条款，不要读二手转述的阶段表。
- **厂商与项目材料**：Atlan AI、Collibra AI、阿里云 DataWorks 智能血缘一类能力（§4.3 已列产品名）。核验方式：在官方文档里找「血缘查询接口是否返回边的来源与置信度」——只返回一段自然语言描述的，应当归到界面，而不是查询能力。
- **方向线索（不指名单篇）**：「跨域血缘联邦」「血缘时序与版本管理」「AI 驱动血缘」这三个方向在数据管理会议（SIGMOD / VLDB / ICDE）上有连续议程；现有线索只到「会议 + 年份」这一粒度，不足以定位到单篇，因此按方向记录。核验方法：按会议论文集检索 `lineage` / `provenance` / `federated metadata`，按篇名与年份核对。

上面六类材料给出的大多是**你无法在自家庭里复现的东西**，所以本节把它们与 5.2 的机制拆解分开列：机制拆解是给判断用的，材料是给核验用的。核验的第一原则仍然是那句——**能不能指回具体的边与作业**。

### 5.5 被过度宣传的部分

**「Agent 会自己探索血缘图，直接给出根因结论」**

→ 实际是什么：把图查询封成工具调用，让模型决定查什么——这是**接口改良，不是架构变化**（5.2.2 已经说明入口层可以交给模型）。
→ 为什么会这样：根因定位是沿边的一跳或多跳检索，图遍历在确定性上更强、成本更低；模型真正有增益的只有「自然语言 → 查询条件」这一段。
→ 什么时候才会成真：当「哪个节点算根因」本身有可核验的判据（例如明确的失败点与时间窗口规则），且结论必须指回具体的边；在那之前，它的输出只能当排查线索。

**「把血缘接进 GraphRAG，就能推理出影响面」**

→ 实际是什么：GraphRAG 的强项是**语料级全局摘要**（「整体上发生了什么」），而影响面是**结构化可达性**查询（「改了 A 会波及谁」），两者机制不同。
→ 为什么会这样：可达性有确定答案，用它去问只会把确定性换成语义相似——而影响面一旦不确定，门禁与变更决策就失去了依据。
→ 什么时候才会成真：当边集合本身不完整、需要「猜一个可能相关的下游」做排查线索时，模型推断才有位置；而那时的输出必须标为 `inferred`，且不得进门禁。

**「LLM 自动补全血缘，覆盖率能冲到接近全量」**

→ 实际是什么：补出来的是**候选边**，覆盖率上升的同时假边率也在上升（5.2.1）。
→ 为什么会这样：缺口是系统性的（动态 SQL、脚本、手工导数三类最难解析），而模型只能从它读得到的文本里推——读不到的东西仍然读不到；「冲覆盖率」与「保可信度」是两条线，只有把边分级、把判定与展示分开，两条线才不互相绑架。
→ 什么时候才会成真：当每条候选边绑定可复现证据、按等级存放、只有前两级能进流程时；判据很简单——**抽 10 条要看得到证据**。

三条被过度宣传的说法有一个共同结构：**它们都把「能生成」当成了「能被判定」**。生成候选边、生成回答、生成关系都可以自动化；而「这条边能不能进流程」必须由可核验的证据与明确的判定人决定。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 一、跨云联邦按「骨架只上送身份与边、明细回源」成形，且不完整结果被显式返回 | 跨云产品文档里出现「明细留在各云、查询回源」的架构说明，且查询结果区分「不完整」与「无下游」 | 跨云仍需把明细汇聚到一处；某云不可用时静默返回不完整影响面 |
| 二、血缘新鲜度进 SLA，与监控告警同级，时序与版本合并为一件事 | 查询结果带 `produced_at` 与最后校准时间，出现过期血缘的告警 | 血缘只在构建时采一次，没有时间戳语义，版本靠另做快照 |
| 三、AI 补全的边进入图但不进流程，门禁显式排除推断边 | 图里出现 `origin` 与 `confidence` 字段，门禁配置里显式排除 `inferred` | 门禁把推断边当事实用；出现一次误拦截后团队开始集中申请豁免 |
| 四、血缘查询标准化为「工具 + API」，而不是按 LaaS 定价 | Agent 侧通过工具调用（而非页面）取影响面，返回里区分三态 | 仍是各家自己的页面；跨系统调用每次都要重写解析器 |

四条预测的信号都落在**接口形态与字段**上（有没有 `produced_at`、有没有 `usable_in_gate`、返回几态），而不是落在「有没有 AI 功能」。这是血缘这个主题的特殊之处：它的可信度由边的来源与分级决定，功能清单看不出来。

第三条预测值得单独说：它最可能的失败方式不是「门禁被绕过」，而是**没人再维护分级**——当 `verified_by` 长期为空、`usable_in_gate` 被批量置真时，图看起来更完整了，判定却回到了「凭经验」。

第四条预测的检验方式最直接：看 Agent 取影响面时拿到的是一段话，还是一个带三态的返回体。前者是页面能力的移植，后者才是可编程的查询服务——而只有后者能进变更流程。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 血缘只在主干系统自动采集 | 度量解析失败率与 `collector = manual` 的边占比（§7.3.2） | 候选边是否带证据与置信等级 | 先上 LLM 补全——缺口没量之前，补全是净成本 |
| 打算做 LLM 补全试点 | 先把边的 `origin` / `evidence` / `usable_in_gate` 三个字段定下来（§3.2.5） | 证据引用是否可复现、抽检是否过得去 | 让推断边进发布门禁与影响面结论 |
| oncall 反复问「为什么延迟 / 谁改的」 | 先把影响面与溯源做成可编程查询（§3.2.3） | 问答层是否复用同一套权限与 URN | 为问答单独建一份血缘；把文档检索的答案当影响面 |
| 跨云或跨域 | 先做全局标识与对齐表（§3.2.1） | 不完整结果是否被显式返回 | 把明细全量汇聚到一处（合规与延迟双输） |
| 模型与训练数据要被审计 | 把特征与训练用表接进同一张图（§9.2） | 导出一跳有没有被建模；来源记录怎么生成 | 另起一套与生产血缘不连通的「模型血缘」 |
| 已有厂商的智能血缘演示 | 用抽检 10 条边要证据的方法验收（5.2.1） | 它的边有没有来源标记与分级 | 把演示当生产能力；把能力名当成某产品的专属功能 |
| 想知道要不要上 GraphRAG | 什么都不用改：先把边与时间戳做实 | 出现的是摘要类需求还是可达性需求 | 用语义相似替换图遍历去回答影响面 |
| 已有问答入口，但回答不带出处 | 要求每条结论指回边与作业（§3.2.2 的边结构） | 回答是否区分三态 | 把自然语言回答直接当成影响面结论 |
| 想按「血缘即服务」采购或自建 | 先按 §3.2.3 的网关边界定接口 | 对外是否真有可编程 API 与三态返回 | 为 LaaS 单独立项：它是形态名，不是一条产品线 |

第 7 行（想知道要不要上 GraphRAG）值得单独说：本主题里真正需要预留的只有两样东西——**每条边的来源标记**与**每条边的时间戳**。它们不花钱、不用等任何新技术，并且是上面所有方向（补全、问答、跨云、审计）的共同前提。

### 5.8 小结

> 本节小结：血缘方向上 AI 真正改变的是**唯一一条机制**——它把「补全缺口」与「翻译问题」这两件事的边际成本从人的注意力上挪开（推断候选边代替人工登记、自然语言代替图查询语言），但**没有改变可达性查询的性质**：谁指向谁、影响面有多大，仍然由图遍历与边的来源决定。
>
> 因此 AI 带给血缘的不是更强的结论，而是更明确的**分级需求**：推断边可以展示、可以当排查线索，但判定（门禁、影响面、审计）只应相信解析与运行时得到的边；而跨云、时序、API 化这些方向与 AI 没有因果关系，它们是既有工程取舍的延伸。
>
