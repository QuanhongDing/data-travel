## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

第一，打分表把六个候选排成一个总分序列（25 / 24 / 23 / 23 / 21 / 15），但总分只对**同一个维度的最大值**敏感，而这条链路下不同候选的维度根本不是同一回事。「Atlan 5 分」与「自研（OpenLineage + Neo4j）5 分」在「跨域血缘」这一列并列，可前者是产品里已经做好的跨云连接，后者是**你要自己把两套 URN 对齐出来**才可能有的跨域能力——同分不同工，而后者的对齐工程通常以季度计【经验】（机制见 7.3.1，量级见 7.7 迁移成本表「单域自建 → 联邦层」一行）。**分数相同不代表代价相同，而选型选的从来是代价。**

第二，打分表里最像「客观指标」的两列——「端到端」与「API 化」——恰恰是最不该并列的。端到端是一条**链路上每一跳都有采集器**的结果（§3.2.2），它是覆盖率的函数；API 化是**同一份血缘被多个消费方复用**的结果（§3.2.3），它是消费方数量的函数。一个候选可以在两端都拿满分，却在你的链路上断在第一跳——因为那条链路上有个作业类型它解析不了。**打分表没有「你的链路」这一维。**

第三，阈值凭空来。常见的决策树里「预算充足（> 100 万/年）→ Atlan / Collibra」这条分支，把采购预算当成了技术分界。真实的机制分界在**自建的持续人力成本**上：自建栈的成本大头不是第一次搭建，而是采集器与引擎版本的长期跟进，加上 URN 对齐这个唯一必须由人来裁决的环节（§3.2.1 与 §3.6）。7.4 会把这条线重新推导一遍——它不是一条采购线，是一条「自己养人 vs 付年费」的交叉线。

第四，也是最重要的一条：这一章的候选**没有统一的比较对象**。血缘的「好」有两种完全不同的含义——**采得全**（覆盖了多少边、覆盖得多准）与**用得上**（有没有流程依赖它、能不能被 Agent 与门禁调用）。商业治理平台通常在「用得上」这一侧强，开源组装栈在「采得全」这一侧强，而这两侧的开销投在不同的地方。打分表把它们混成一列，于是「谁更好」这个问题本身就没有答案。

**本章所有数字按三档标注**：【公开】（有公开来源，正文给出处与年份）、【推算】（由公开前提推导，正文写出推导链）、【经验】（行业普遍实践，只给区间与条件）。三者混用时，读者可按档位决定采信程度。

**本章的引用约定**：文中不带文件名的「§1.x / §2.x」指本章主文件 [09-data-lineage.md](09-data-lineage.md)；「§3.x」指同目录的独立文件 [§ 3 设计模式与范式](09-data-lineage-section-3-sec3.md)——§3 的正文全部在该独立文件内，主文件只有 §0 / §1 / §2。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 身份对齐能力 | URN 由谁生成，两个域里的同名表凭什么被判定为同一个实体 | 这是本主题唯一不可绕过的地基：对不齐时跨域路径查询返回空，而用户会把它读成「没有下游」（§3.2.1 与 §3.5） |
| 边的来源与等级 | 这条边是解析器、运行时、人工登记还是模型推断出来的 | 决定它能不能参与门禁判定；把推断的边当事实会换来一次误拦截，而误拦截之后团队会绕过门禁（§3.2.5） |
| 部署与合规边界 | 明细血缘能不能离开它所在的云 / 域 | 决定你走中心汇聚、联邦路由还是跨云骨架；这一条常被合规直接钉死，不由技术偏好选择 |
| 查询代价结构 | 一次典型查询有多少跳、扇出多大、结果集会不会必须截断 | 决定深链路查询能不能作为日常动作；一跳查询与三跳递归是两种完全不同的代价 |
| 消费契约 | 消费者是人、是流程（CI / 发布门禁），还是 Agent | 决定要不要 API 化、要不要带 `lastUpdated` 与采集器类型；只给人看的血缘进不了任何流程 |
| 运维与锁定 | 离开它要重灌多少边、重写多少查询、重建多少对齐 | 血缘是长期低改动系统，锁定成本主要体现在 URN 与边的模型上，而不在数据量上 |

> 这 6 条的权重随阶段移动：单域起步时，**边的来源**最先起作用（它决定影响面能不能被信任）；出现第二个域时，**身份对齐**立刻跃升为第一位；有多云或出境约束时，**部署与合规边界**会直接排除掉整族候选；要支撑 Agent 与模型审计时，**消费契约**才进入前三。**查询代价结构**是个例外——只要你的血缘图里存在高扇出节点，它就必须先验证，与阶段无关。

这 9 个候选分成**三族**。分族的依据不是品牌或开源闭源，而是**三件事由谁决定：身份（URN）由谁生成、边由谁产出、明细放在哪**。

- **族一 · 平台自带（三者同源）**：Apache Atlas、DataHub、Unity Catalog。身份由平台自己的命名体系下发，边由平台的采集端或引擎产出，明细存在平台里。差别只在「采集端覆盖了哪些引擎」与「引擎是否在写路径上直接产边」。
- **族二 · 商业治理 SaaS（三者绑在一起，但可拆）**：Atlan、Collibra、阿里云 DataWorks。身份仍由平台连接器映射而来，边来自连接器 + 引擎钩子 + （近年加入的）模型补全，明细存在厂商侧。它们的强项是把「用得上」做完整——治理工作流、审批、AI 入口。
- **族三 · 开放规范 + 自组装（三者可以各自替换）**：OpenLineage + Marquez、自研（OpenLineage + Neo4j + GraphQL Gateway）、血缘 API 网关。规范只约束边的表达，身份、存储、查询、门禁全部由你决定——**自由度的代价是这几件事全部由你负责**。

**先分族再选，能省掉一半比较**：同族内部通常只是覆盖的引擎清单与许可证差异，跨族差异才是机制差异。而分族直接给出了一个可判定的问题——**你要买的到底是「产边」还是「用边」**。族三给你产边的能力但不给你用边的界面，族二给你用边的界面但产边的覆盖面取决于它的连接器清单，族一的产边覆盖面取决于它自己的采集端。**先回答这个问题，再看任何功能对比表。**

要提醒一点：**同一个产品常常横跨两族，分族看的是它承担的角色而不是品牌**。DataHub 在族一里是「平台」，但它也常被当作族三里的「存储与查询件」接在 OpenLineage 事件之后；阿里云 DataWorks 的调度面既是族一的产边组件，其治理与 AI 入口又具备族二的形态；Unity Catalog 在湖仓内是族一，一旦跨出引擎边界，跨云那部分就要靠族三的骨架层补。**选型时问的应该是「我这条链路上，身份、边、明细各自由谁负责」，而不是「我买了哪个产品」。**

每族的**典型失败方式**也不同：族一死于**覆盖**——平台采集端不支持的引擎，在那套血缘里根本不存在，且不报警；族二死于**对齐**——连接器把两朵云上的同名表并列展示，看起来统一、实际是两个实体；族三死于**没人用**——边采得很全、接口也建好了，但没有任何流程依赖它，两年后团队换了一批人，这套系统变成一个没人敢动的黑盒（§3.5 的「血缘 API 没人用」）。**知道自己这一族会怎么死，比知道别人的总分是多少更有价值。**

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 身份由谁生成：URN 收口 vs 各系统自带命名

**机制是什么**：主文件 §2.2 把联邦血缘定义成有向图集合的并 $G_{\text{federated}} = \bigcup_i G_i$，并在跨域边上加桥接关系 $\text{bridge}(u,v)$。这条式子的全部难点都在那个「并」上——$G_A$ 里的 `prod.orders` 与 $G_B$ 里的 `orders` 是不是同一个实体，没有任何系统能自己判断；URN 形式（如 `urn:li:dataset:(platform,name,env)`）只在**同一个命名域内**唯一。

**它在各候选中的实现差异**：

| 候选 | URN 由谁生成 | 同名表如何判定为同一实体 | 冲突由谁裁决 |
| --- | --- | --- | --- |
| Apache Atlas / DataHub / Unity Catalog | 平台自己的命名体系 | 平台内的类型与限定名天然唯一；跨平台要靠映射 | 平台（或没人） |
| Atlan / Collibra / 阿里云 DataWorks | 连接器把源系统命名映射进平台 | 映射规则由连接器配置决定 | 平台侧配置，冲突常表现为重复资产 |
| OpenLineage + Marquez | 规范只规定事件里的命名空间与名字 | 命名空间隔离，跨工具对齐要靠使用方自己 | 没人——规范不裁决 |
| 自研（+ 对齐注册表） | 由你收口到注册表 | 全局 URN 注册表 + 置信等级（exact / inferred / manual） | 你指定的对齐仲裁者 |

**由此必然导出的性质（因果句）**：因为**联邦层能回答「去哪找」，不能回答「谁等于谁」**，所以先建联邦层、把 URN 对齐留到以后，跨域路径查询会**恒为空且不报错**——用户看到的是一条正常的空结果，会把它读成「没有下游」，于是变更决策建立在一个空的但看起来正常的答案上（§3.5「URN 不对齐」）。因此**身份对齐必须先于联邦层成立**，而它是整条链路上**唯一需要人来裁决的环节**：规则可以自动化执行，但「这两个是不是同一个东西」在存在歧义时只能由人拍板。这决定了跨域血缘不是一个可以「先上线再治理」的项目。

**公开证据**【公开】：URN 的形式与联邦层的组成（路由表 / ID 对齐表 / 桥接边）见主文件 §2.2 的形式化与 §3.2.1 的结构图与两张 DDL；「OpenLineage 是跨工具的 lineage 规范、Marquez 是其参考实现」见 §3.2.2 并可由 OpenLineage 与 Marquez 两个项目的官方文档核验（年份锚点：OpenLineage 1.0 记于主文件 §1.4 的 2020–2023 年条目）。判定方法：问「新增一个域，要不要把它的历史血缘搬进中央？」，以及「两个域的同名表，规则写在哪、谁签字」——第二个问题答不出人和文档，对齐就还没有成立。

**失效条件**：当你的实体本来就是单域命名、且不存在同名歧义时（单团队、单引擎、命名规范严格），URN 对齐不产生额外成本，此时把对齐做成一套注册表反而是过度设计。**但在多域结构下它不是可选层**——跳过它的代价不是「对齐晚一点」，而是「跨域能力永远为假」。

#### 7.3.2 边由谁产出：解析器 / 运行时 / 人工 / 模型推断

**机制是什么**：血缘是**采集**出来的，不是登记出来的。主文件 §2.3 列了五类采集方法（OpenLineage 事件、联邦 Hook、ETL 工具 API、桥接同步、LLM 补全），它们的共同点是都只能看到自己视角的那一段。因此覆盖率先天小于 100%，而缺口不是随机的。

**它在各候选中的实现差异**：

| 候选 | 边的主要来源 | 对解析不了的作业怎么办 | 产出的边能不能直接进流程 |
| --- | --- | --- | --- |
| Apache Atlas | 作业与表的登记关系推导为主 | 多数依赖人工补登记 | 取决于登记质量 |
| DataHub | 采集端（解析器 / 钩子 / 查询日志）+ 统一事件模型 | 靠新增采集器，长尾覆盖慢 | 解析类边可进流程，需自带来源标记 |
| Unity Catalog | 引擎在读写时直接产生 | 引擎外的链路不产生边 | 可信度高，但范围被引擎边界限定 |
| 阿里云 DataWorks | 调度作业定义即来源；另有智能血缘做 LLM 补全 | 智能补全产出候选边 | 需分级：补全的边不宜直接进门禁 |
| Atlan / Collibra | 连接器 + 各工具 API | 取决于连接器清单 | 取决于采集器产出的来源标记 |
| OpenLineage + Marquez | 事件为主（各集成按规范发事件） | 没有集成的作业就不发事件 | 可进流程，但要自己区分来源 |
| 自研 | 由你决定（通常解析 + 运行时兜底） | 运行时采集兜底 | 由你在模型里区分可信度 |

**由此必然导出的性质（因果句）**：因为**缺口是系统性的**（动态 SQL、脚本任务、手工导数这三类永远最难采），所以「覆盖率冲到 100%」不是一条可达的路线；正确的做法是把缺口**度量出来并标注为已知盲区**，指标是「解析失败率」与「`collector = manual` 的边占比」，而不是总边数。而因为**一条链路的可信度等于最弱那一跳**，所以只要链路上有一跳靠人工登记，整条链路的时效性就退回到人工登记的时效性——**端到端不是「主干采到了」就成立的**。这条机制也解释了 LLM 补全为什么会成为这几年的主流方向：它是唯一成本不随资产数线性增长、又能吃进非结构化输入（脚本正文、变更工单）的补全手段；但它引入了一种新的失败模式——**假边**，缺失的边会让查询报「无上游」，假边会让查询报出一个**合理但错误**的上游，后者更难发现（§3.2.5 失效点）。

**这条机制决定门禁能不能成立**：门禁只应相信解析得到或运行时采集到的边；人工登记与模型推断的边只能作展示与排查线索。原因不是保守，而是**门禁被误拦截一次之后，团队会开始集中申请豁免，而绕过比不建门禁更糟**。

**公开证据**【公开】：五类采集方法与「OpenLineage 事件 / 联邦 Hook / ETL 工具 API / 桥接同步 / LLM 补全」的划分见主文件 §2.3；边的采集器类型与来源标记（parser / hook / runtime / manual）以及 AI 补全边的分级（verified / corroborated / inferred）见 §3.2.2 与 §3.2.5 的边结构（年份锚点：主文件 §1.4 把「AI 驱动血缘补全」记入 2024 年）。判定方法：从图谱里随机抽 10 条边，要求给出它们的证据引用——答不出证据的边占比，就是这套采集的不可信比例。

**失效条件**：当资产只在一个引擎里、且作业全部是同一种 SQL 方言时，解析器的覆盖率可以很高，运行时兜底与 LLM 补全都是净成本。**缺口的存在与否要先测量，不要先预防。**

#### 7.3.3 明细放在哪：中心汇聚 / 联邦路由 / 跨云骨架

**机制是什么**：血缘明细（边集合 + 字段映射 + 作业信息）放在哪个物理位置，决定了三件事：跨域查询要发多少次远端调用、能不能拿到全局一致性快照、以及**合规上是不是允许**。

**它在各候选中的实现差异**：

| 候选 | 明细存在哪 | 跨域查询的形态 | 全局一致性快照 |
| --- | --- | --- | --- |
| 平台自带（Atlas / DataHub / Unity Catalog） | 平台侧集中 | 单库查询（若各域都接入了同一平台） | 有（各域采集时间不同，仍非同一时刻） |
| 商业治理 SaaS | 厂商侧集中 | 单库查询 | 有，但依赖连接器的采集节奏 |
| OpenLineage + Marquez / 自研集中 | 你自己的一处 | 单库查询 | 取决采集节奏 |
| 联邦（自研 + 对齐表） | 留在各域 | fan-out，延迟由最慢的域决定 | 没有——合并结果可能对应两个时刻 |
| 跨云骨架 + 回源 | 明细留各云，只上送 URN / 边 / 时间 / 地域 | 骨架回答「链路存不存在」，明细按需回源 | 没有，且任一朵云不可用即返回不完整 |

**由此必然导出的性质（因果句）**：因为**中心汇聚把明细挪到了一处**，所以它能给出全局一致视图与低延迟查询，代价是**汇聚那一刻本身就构成一次跨域（乃至跨境）传输**——在有数据出境约束的场景里，这不是成本问题而是合法性问题，于是整族候选被直接排除。反过来，因为**联邦把明细留在各域、中央只存路由与对齐**，所以新增一个域只需登记映射、不必搬历史血缘，代价是**每一次跨域查询都退化成多次远端调用**，延迟由最慢的域决定，而且**联邦层拿不到全局快照**：两个域的采集时间不同，合并出来的路径可能对应两个不同的时刻。

**跨云骨架是第三条路，它的机制是把「统一」从存储层挪到身份层**：跨越云边界的只有「谁指向谁」，不是数据本身，明细查询回到数据所在的云完成（§3.2.4）。它换来的是「统一视图」与「数据不出境」可以同时成立，代价是把一部分查询能力搬到了回源环节——**任何一朵云不可用，跨云影响面就是不完整的，而「不完整的影响面」在变更决策里和「没有影响面」一样危险**。所以接口上必须把「不完整」与「无下游」区分开。

**公开证据**【公开】：联邦与跨云的形态见主文件 §1.4 的 2023–2025 年「跨云联邦化阶段」条目与 §3.2.1、§3.2.4 的结构图；其中 Databricks Lakehouse Federation 与阿里云 DataWorks 跨云记在该阶段的 2024 年条目。判定方法：拿一次典型的跨域查询，数它实际发起的远端调用次数，并用「某一跳不可用」做一次故障演练——看返回的是「不完整」还是「无下游」。

**失效条件**：当域数很少（2–3 个）【经验】且跨域查询是偶发需求时，联邦的远端调用代价可以接受，此时先做联邦、暂不物化是合理的。而当跨域桥接边涨到很大规模时，物化子图的维护成本会超过联邦查询本身，此时应当反过来考虑局部集中（§3.4 的组合二）。

#### 7.3.4 对外接口形态：可视化页面 vs 可编程 API

**机制是什么**：血缘有两种存在方式——被人看，和被程序调用。前者需要布局算法与交互，后者需要稳定的查询契约与**可信度元数据**（这条边是谁采的、什么时候采的）。

**它在各候选中的实现差异**：

| 候选 | 对外形态 | 是否带来源与新鲜度 | 能否被门禁 / Agent 消费 |
| --- | --- | --- | --- |
| Apache Atlas | Web 界面 + REST API | 有基本元数据 | 可以，但需自建门禁侧逻辑 |
| DataHub | GraphQL API + 界面 | 事件模型天然带时间与来源 | 可以，§3.2.3 以其 GraphQL 为例 |
| Unity Catalog | 以引擎内接口与 SQL 为主 | 与引擎事务绑定 | 可以，但在引擎边界内 |
| 阿里云 DataWorks / Atlan / Collibra | 控制台 + API；另提供自然语言入口 | 取决于产品 | 可以，通常需按厂商 API 契约来写 |
| OpenLineage + Marquez | 规范的 HTTP API + 界面 | 事件带运行 ID 与时间 | 可以，契约由规范定义 |
| 血缘 API 网关（自建 / GraphQL Federation） | 唯一入口，鉴权 + 限流 + 缓存 + 结果标注 | 由你在契约里强制（`collector` / `lastUpdated`） | 最能被多消费方复用 |

**由此必然导出的性质（因果句）**：因为**所有消费方走同一份接口，SQL 解析与身份对齐只做一次**，所以目录、质量、权限、门禁不会各自解析出一份不同的下游——这是「口径漂移」这类最难排查的问题在结构层被消除的方式；反过来，**因为网关是唯一入口，它一旦挂掉，所有消费方一起挂，而门禁依赖它意味着发布流程也被它绑住**（§3.2.3 代价①）。第二层后果来自缓存：**因为缓存命中意味着返回旧图而不是重新采集的结果**，所以当缓存 TTL 长于采集周期时，优点「血缘随时可查」反转为「稳定地给出过期答案」——而过期的血缘比没有血缘更危险，因为它给出的是一个确定的、错误的答案。判据很直接：查询返回值里有没有 `lastUpdated`，以及它是否随缓存一起被冻结。

**公开证据**【公开】：主文件 §2.1 把「血缘 API 网关」与「血缘即服务（LaaS）」列为服务化形态；DataHub 对外暴露 GraphQL 接口、OpenLineage 对外暴露规范事件接口，两者都可编程访问（§3.2.3 的调用形态与自验方法；年份锚点——DataHub 记于主文件 §1.4 的 2018–2020 年条目、OpenLineage 1.0 记于 2020–2023 年条目）。判定方法：统计网关的调用方数量与调用量分布——若只有一个消费方在用，它还没有成为基础设施，此时引入网关只增加了一跳延迟。

**失效条件**：当消费方只有一个（例如只有一个自研的血缘界面）时，网关是一层纯开销；此时直接查存储更简单，也更少一个可用性单点。**网关的价值随消费方数量增长，与数据规模无关。**

### 7.4 成本结构对比（不是价格表，是成本函数）

三族候选的成本函数**形状不同**，这才是选型的核心。写成统一形式：

```
年成本 ≈ 采集(源系统数 × 引擎数 × 版本数 × 采集频率 × 解析复杂度)
        + 存储(边数 × 每边体积 × 保留时长，含时序快照)
        + 查询(跳数 × 扇出 × 并发) + 人力(拓扑层数 × 技能稀缺度 + 对齐裁决工时)
        + 商业年费或社区支持成本
```

**先算掉最容易被高估的一项：存储**【推算】。以 1000 万条边为例（【经验】：十万级表的组织常见的边量级），按 §3.2.2 的 `lineage_edge` 字段清单（源 / 目标 URN、粒度、作业 URN、变换、时间戳、来源系统、采集器）估算，每条边约 200 B → 1000 万 × 200 B ≈ **2 GB**。按对象存储标准层 **$0.023/GB-月**【公开】（[AWS S3 定价页, 2024]）推算，月成本约 **$0.05**【推算】。即使为复盘保留 12 个月快照（存储 ×12，约 24 GB），月成本仍不足 **$0.6**【推算】。**结论：血缘的存储成本在常见规模下不是主导项——它的账单由采集器数量与查询形态决定。** 凡是把「图数据库贵不贵」当成主要成本项的方案比较，比的都是次要项。

**每一项的主导者不同**：

| 候选族 | 主导项 | 隐性项 | 边数翻 10 倍时的行为 |
| --- | --- | --- | --- |
| 族一（平台自带） | 平台本身的部署与升级成本 | **未覆盖引擎的采集端缺失**（只能等平台支持或自研适配） | 近似线性，人力不变；但未覆盖的引擎永远不会被覆盖 |
| 族二（商业治理 SaaS） | 商业年费 | **连接器的对齐配置与冲突处理工时** | 线性（多按资产数或用量计费） |
| 族三（开放规范 + 自组装） | 采集器与引擎版本的跟进人力 | **URN 对齐的裁决工时** + 图存储运维 | 采集器数量随「源系统 × 引擎 × 版本」增长，是超线性项 |
| （跨云拓扑，可叠加在任一族上） | 每云各一套采集与服务的运维面 | **回源链路的部分可用**（一朵云不可用即返回不完整） | 运维面按云数倍增，与边数无关 |

**「采集器数量」这一项常被当成一次性投入，其实它按「源系统 × 引擎 × 版本」计息**：每多接一种源、每多支持一个引擎版本，都要多维护一个解析器路径。它在启动期是 0，在两三年后通常是最大的人力开支项。判定方法：数一遍你当前维护着多少个采集器与多少个引擎版本分支，把两个数相乘——那就是这项成本的乘数。

**「预算 100 万/年」这条线该怎么读**【推算】：自建栈的持续维护若需要 2–3 名工程师专职（【经验】：一线城市资深数据平台工程师的全成本量级处于数十万元/年），其年度人力成本即进入数十万到百万元级；再加上图存储与对齐裁决的边际投入，自建的隐性成本通常已在同一量级。所以这条线的实质是**「自己养人 vs 付年费」的交叉点**，而不是一条采购预算门槛：商业方案在**你的采集缺口很小、而治理编排需求很大**时更划算；反过来，当你的缺口集中在商业产品覆盖不到的长尾引擎时，付年费买到的界面解决不了产边问题。

**查询这一项按「跳数 × 扇出」计息，而不是按边数**：一次一跳的邻接查询与一次三跳的递归影响面，代价可以差几个量级；而高扇出节点处的结果集必须截断——**截断意味着影响面只能给出近似答案**，这一点必须在 SLA 里写清楚，不能靠调参解决（§3.5「可视化漂亮但查询慢」与 §3.6「边数 → 十万级」跃迁：深链路递归的中间结果集超过内存，对应的措施是查询深度上限与分页——一旦分页，单次返回的影响面就只能是近似值）。

**把三族的成本放在同一张账单上，形状是这样的**：

| 成本项 | 族一（平台自带） | 族二（商业 SaaS） | 族三（规范 + 自组装） |
| --- | --- | --- | --- |
| 采集跟进（源 × 引擎 × 版本） | 平台承担，但你等它支持 | 连接器清单决定，缺的只能提需求 | **你承担，且是长期最大项** |
| 存储与查询 | 随平台规模 | 多按资产数或用量计费 | 你自己运维，常见规模下便宜 |
| 身份对齐 | 平台内部天然成立；跨平台仍需守住 | 连接器映射，冲突处理在你 | **你承担，且是唯一必须人做的** |
| 治理编排（审批 / 合规举证） | 弱，需自建 | **强，是它的主要卖点** | 弱，需自建 |

> 这张表最有用的一行是最后一行：**族二的年费主要买的不是血缘本身，而是治理编排**。如果你的组织已经有成熟的审批与合规流程，这一项买回来是重复的；如果没有，自建它的成本往往比血缘本体更高。判定方法：把「审批、合规举证、跨云视图、AI 入口」这四项里你真正需要的有几项数出来——少于两项时，族二的年费很难摊平。

### 7.5 决策树（每个分支都要有阈值依据）

```
[是否存在第二个需要对齐的域？]
   │
   ├── 否（单域、单团队）→ 解析器自动采集 + 影响面查询
   │        │
   │        └── [消费方是否 ≥ 2 个（目录 / 质量 / 权限 / CI / Agent）？]【经验】
   │              ├── 是 → 再加血缘 API 网关，让口径只解析一次
   │              └── 否 → 止步：网关这一跳只增加延迟与一个单点
   │
   └── 是 → [明细血缘能不能离开它所在的云 / 域？]
            │
            ├── 不能 → 跨云骨架汇聚 + 明细回源
            │          （跨越云边界的只有 URN / 边 / 时间 / 地域）
            │
            └── 能 → [组织上能不能把采集权收到一处？]
                     │
                     ├── 能 → 集中式采集 + 联邦式展示（多数团队的实际形态）
                     │
                     └── 不能 → 联邦血缘（路由表 + ID 对齐表 + 桥接边）
                                │
                                └── [域数 ≥ 5 且跨域桥接边在千级以内？]【经验】
                                      └── 是 → 把最高频的跨域子图物化成本地只读图

（以下两问对所有分支共用）

[变更要不要在提交前被拦住？]
   ├── 要 → 门禁只信解析得到或运行时采集到的边；
   │        人工登记的边与模型推断的边只能作排查线索
   └── 不要 → 血缘只作参考，不必为它建门禁（但要承认它不产生约束力）

[商业方案的年费，是否低于自建的持续人力成本？]
   ├── 是 → 商业治理平台（Atlan / Collibra / 阿里云 DataWorks）
   └── 否 → 开源栈自建（DataHub / OpenLineage + Marquez / 自研图存储 + 网关）
```

**阈值依据**（树上每个判断节点在此各有一条，逐条对应）：

- **「是否存在第二个需要对齐的域？」**：依据是 7.3.1 的身份机制。单域时 URN 天然唯一，对齐不产生成本；一旦出现第二个域，「谁等于谁」就成了必须先完成的前置工作，而它是**唯一需要人裁决**的环节。判定方法：如果新域的实体与现有域的实体不存在同名或语义重叠，这条分支可以按「否」走；只要存在一个需要判断「是不是同一个东西」的场景，就必须按「是」走。
- **「消费方是否 ≥ 2 个？」**【经验】阈值：依据是 7.3.4。网关的成本是固定的一层，收益是「口径只解析一次」；一个消费方时这笔收益为零，两个及以上时它随消费方数增长。判定方法：列出所有会调用血缘的系统（目录、质量、权限、CI、Agent、人工查询），同一个系统内部的多个页面算一个。
- **「明细血缘能不能离开它所在的云 / 域？」**：这是**合规判据，不是技术判据**，取值由法务与监管要求决定，不由架构师偏好决定。它一旦为「不能」，中心汇聚与商业 SaaS 的默认形态都被排除，只剩骨架汇聚 + 回源（§3.2.4）。判定方法：问「这条边里有没有任何字段属于禁止出境 / 禁止出域的范围」——边的 URN 可能含表名与字段名，这在某些行业里已属受控信息。
- **「组织上能不能把采集权收到一处？」**：依据是 §3.3 的判断——把血缘集中到一处意味着各域要交出采集权与命名权，这在多团队结构下常常在组织上不可行。判定方法：注意这里问的是**采集权**，不是视图；多数团队的真实形态是「采集集中 + 展示联邦」，因为采集集中拿到的是全局一致性，展示联邦避免各域看到别人的明细。
- **「域数 ≥ 5 且跨域桥接边在千级以内？」**【经验】阈值：两个量都取自 §3.4 的组合适用性判断（该处「域数 ≥5、跨域桥接边数量在千级以内」即标注为【经验】）。域数决定的是 fan-out 的跳数与「出现慢分支的概率」（域越多，整体延迟由最慢分支决定的效应越明显）；桥接边数量决定的是**物化子图的维护成本是否可承受**——桥接边到十万级时，物化子图的维护成本会超过联邦查询本身，此时物化的方向就是错的。两个量都能从现有运维数据里取到。
- **「变更要不要在提交前被拦住？」**：依据是 7.3.2 的分级机制。门禁的唯一价值是「让改动变成一件可以事先算清代价的事」；而它一旦误拦截，团队会开始集中申请豁免，**绕过比不建门禁更糟**。所以这条判据的反面不是「要不要准」，而是「你的边里有多少比例是可验证来源」——若 `manual` 与模型推断的边占比很高，先别建门禁，先去补采集。
- **「商业方案的年费，是否低于自建的持续人力成本？」**：依据是 7.4 的推导——自建的隐性成本主要是「采集器 × 引擎版本」的持续跟进与 URN 对齐的裁决工时，量级在数十万到百万元/年【推算】（推导链见 7.4）。这条线要按自己的两项数据来算，而不是按一个孤立的数字：**你的采集缺口有多大**（缺口大 → 商业产品的界面帮不上，自建更合算）、**你的治理编排需求有多重**（审批、合规举证、跨云视图多 → 商业产品更合算）。

**上树之前先做的三项验证**（都比选型更重要）：

1. **统计解析失败率与 `manual` 边占比**：这是决定「门禁能不能建」的唯一数据（对应 7.3.2）。
2. **抽 10 条 AI 补全的边，要求给出证据引用**：这是决定「补全能不能用」的抽样检验（对应 7.3.2）。
3. **拿一次典型的跨域查询，数远端调用次数，并演练「某一跳不可用」**：看返回的是「不完整」还是「无下游」（对应 7.3.3）。

这三项里任意一项不满足要求，无论落在树的哪一档，都应该先换方向，而不是先调参数。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单域、单团队、只需改表前看下游 | 解析器自动采集 + 影响面查询（开源栈起步） | 商业治理平台 | 商业产品的固定成本在这个规模收不回来 |
| 单主体、消费方 ≥ 2【经验】、要能进 CI 门禁 | 自动采集 + 血缘 API 网关（GraphQL 或 REST） | 各消费方各自解析 SQL | 各自解析必然得出不同下游，口径漂移最难排查 |
| 多业务域自治、组织上拿不到集中采集授权 | 联邦血缘（路由 + ID 对齐表 + 桥接边） | 集中式 + 强推登记 | 拿不到授权时集中只会得到一份过期的副本 |
| 多云或自建混合、存在数据出境约束 | 跨云骨架汇聚 + 明细回源 | 中心汇聚 | 汇聚那一刻即构成跨境传输 |
| 资产集中在同一湖仓、引擎在读写时能自动产边 | Unity Catalog 一类的湖仓一体目录 | 独立血缘平台 | 独立平台要多采一份边，且引擎外链路本来就不需要它 |
| 消费方以业务与治理团队为主、需要审批与合规举证 | 商业治理平台（Atlan / Collibra / 阿里云 DataWorks） | 开源栈 + 自建工作流 | 治理编排不是血缘的核心能力，自建要额外投入一大块 |
| 链路上有大量脚本 / 动态 SQL / 手工导数 | 自动采集 + 运行时兜底 + 分级补全 | 纯静态解析 | 这些恰恰是解析不到的那部分，纯静态解析会留下静默缺口 |
| 要支撑 Agent 取数与模型审计 | 字段级边 + 网关 + 时序图（边带时间戳与快照） | 只做可视化 | Agent 要的是可编程、带出处、可回溯到当时状态的接口 |

**常见组合**：

1. **Atlan + DataHub + OpenLineage**：构成——Atlan 承担跨云检索与 AI 入口，DataHub 承担血缘存储与 API，OpenLineage 承担统一的边表达规范。职责边界——OpenLineage 只管「边怎么表达」，DataHub 只管「边存在哪、怎么查」，Atlan 只管「谁在看、怎么解释」；**三者之中必须指定一个权威源**。运维代价——Atlan 的图与 DataHub 的图是两份副本，二者之间的同步是新增的一致性边界，任何一次同步滞后都会表现为「两个入口查出不同的下游」。【经验】
2. **阿里云 DataWorks + 智能血缘 + 通义千问**：构成——DataWorks 承担血缘与调度，智能血缘用 LLM 补全解析不到的长尾，通义千问提供自然语言入口。职责边界——**调度是采集的第一入口**（作业定义即血缘来源），智能血缘只产出「候选边」，自然语言入口只消费不产出。运维代价——补全的边必须分级入库（§3.2.5 的 verified / corroborated / inferred），未验证的边不得参与门禁；自然语言入口的每个结论都要能指回一条边，否则提问者分不清答案来自解析还是推断。【经验】
3. **OpenLineage + Neo4j + GraphQL Gateway（自研）**：构成——OpenLineage 做采集规范，Neo4j 做图存储，GraphQL Gateway 做统一查询入口。职责边界——图只管多跳遍历与影响面，属性与对齐留在关系库；网关只管鉴权、限流、缓存与结果标注。运维代价——你同时承担采集器跟进、图存储运维与 URN 对齐三件事；其中只有对齐是必须由人做的，另外两件都可以从开源社区获得，但跟进的责任仍然在你。【经验】
4. **OpenLineage + DataHub / Marquez**：构成——OpenLineage 定义事件，DataHub 或 Marquez 二选一承担存储与查询：前者带目录与图查询、生态更宽，后者是规范的参考实现、更轻。职责边界——规范负责「跨工具互通」，实现负责「存与查」；**不要把两份实现同时接在同一条链路上**，否则又是两份副本。运维代价——多一个组件版本要跟；规范演进时必须确认实现已跟进，否则会出现「事件发了但边没入图」。【经验】
5. **跨云骨架 + 域内明细 + 回源查询**：构成——各云内保留完整血缘，向上只送 URN / 边 / 时间 / 地域组成骨架图；跨云路径查询按需回源。职责边界——骨架层回答「跨云链路存不存在」，域内服务回答「这条链路的具体字段映射是什么」；冲突时以域内为准，骨架层永远不被当作明细源。运维代价——回源链路要处理部分可用，接口上必须区分「不完整」与「无下游」；且骨架能存什么、不能存什么应当写进 schema 的约束里，而不是靠约定。【经验】

> 组合的第一原则是**让每一件做它机制上最擅长的事**：规范管表达就别让它管存储，图管遍历就别让它管对齐（对齐需要人的裁决，而图不会裁决）。第二原则是**组合数不超过团队的运维带宽**——上面 5 个组合里，每多一件就多一份 URN 对齐、多一处新鲜度告警、多一个「两套系统对同一个问题给出不同答案」的战场。**组合最容易出错的不是选错件，而是没指定权威源。**

### 7.7 选错的代价与迁移成本

**反模式：把「接入了」当成「采到了」** —— 症状：接入了十个数据源，覆盖率却从不统计；解析失败的作业只是「没出现在图里」，没有告警也没有待办。后果：影响面永远是下界，而缺口恰恰集中在最不规范、也最可能是关键链路的长尾作业上（脚本、临时任务、手工导数），于是变更决策建立在一个错误的安全感上；缺口不报警，只在事故里暴露（§3.5「血缘采集永远不全」）。正确的做法：把「解析失败率」与 `manual` 边占比做成可查的指标，并用运行时采集为解析不了的作业兜底——**宁可多采一层，也不留不可见依赖**。

**反模式：先建联邦层，URN 对齐留到以后** —— 症状：联邦层能列出多个域，但跨域路径查询返回空；同一张表在两个域里显示为两个节点。后果：统一入口只统一了界面、没统一实体，跨域影响面恒为空**且不报错**——用户会把这读成「没有下游」。正确的做法：先建 URN 对齐注册表并指定仲裁者；对齐未完成时在接口上显式标为「未对齐」，而不是静默并入。

**反模式：血缘只挂在可视化页面上** —— 症状：界面很漂亮，但没有任何流程依赖它；变更照样靠发通知等人反馈。后果：血缘退化成参考资料，采集投入无法转化为事故下降——**血缘的价值取决于它挂在哪个环节上：放在文档里没人看，放在发布门禁上每次变更都必须正面回答影响面**（§3.2.3 与 §6 的案例）。正确的做法：把影响面查询嵌进数据申请与变更流程，让不用它就走不下去。

**反模式：把模型推断的边直接并入主图** —— 症状：图谱里存在来源不明的边；有过一次门禁误拦截之后，团队开始集中申请豁免。后果：错误的血缘比缺失的血缘更危险——缺失会报「无上游」，错误会给出一个合理的错误答案；而一次误拦截就足以让门禁失去信任。正确的做法：边必须带 `origin` 与证据引用，未验证的边只能作排查线索，**不得参与门禁判定**。

| 迁移方向 | 边数据迁移 | 查询与接口改写 | 运维重建 | 团队再学习 | 量级（【经验】） |
| --- | --- | --- | --- | --- | --- |
| 单域自建 → 联邦层 | 明细不必搬，但必须先做 URN 对齐 | 跨域查询从单库查询改成 fan-out | 新增路由表与对齐注册表 | 高（对齐是唯一要人裁决的环节） | 季级 |
| 可视化工具 → API 网关 | 边不用迁 | 需定义契约（含 `collector` / `lastUpdated`） | 新增一层入口与缓存策略 | 中 | 周级到月级 |
| 自研图存储 → 商业平台 | 边需重灌并重新对齐身份 | 需改写成厂商 API 的查询形态 | 自建运维大幅减少 | 中 | 月级 |
| 中心汇聚 → 跨云骨架 | 明细退回各云，只上送骨架 | 跨云查询改为回源 | 要重新定义「什么元数据允许跨云」 | 高 | 季级 |
| 无时序 → 有时序（边带时间戳 + 快照） | 需回填或从当前图开始积累 | 查询增加「按时刻」维度 | 需设快照保留期与压缩策略 | 中 | 月级 |

> 注意「自研图存储 → 商业平台」这一行与直觉相反：它看起来是把技术换成产品，实际的主要工作量在**重新对齐身份**——边可以重灌，但「谁等于谁」的裁决结论未必能整体搬过去。**血缘迁移的成本从来不在边数上，在身份与来源这两样元数据上。**

### 7.8 小结

血缘选型的特殊性在于：**它选的是「谁来替你产边、谁来裁决身份」，而不是「谁的可视化更好看」**。所有候选的差异都可以收到一条上——**它是替你产边，还是替你展示边**。产边的能力来自解析器、引擎钩子与运行时采集，覆盖率与可信度由此决定；展示的能力来自图、API 与界面。商业治理平台通常强在「用得上」（跨云视图、治理编排、AI 入口），开源组装栈强在「采得全」（你能为任何长尾写采集器），而这两侧的投入落在完全不同的地方。**买之前先回答一个问题：你的缺口在产边，还是在用边。**

而在多域结构下，还有一条更硬的前提不可绕过：**身份对齐必须先于一切**——因为跨域查询在对不齐时返回的是空结果，而不是错误（§3.5「URN 不对齐」与 §3.3 表后段落；§3.8 小结把同一条约束表述为「对不齐时系统如何表现」）。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 单域、百级到千级表【经验】、只要改表前看下游 | 解析器自动采集 + 影响面查询（开源栈起步） | 边由采集产出而非人工登记，才不会在几个月后过期 |
| 单主体、消费方 ≥ 2【经验】、要进 CI 门禁 | 自动采集 + 血缘 API 网关 | 口径只解析一次，才有唯一答案可被流程依赖 |
| 多域自治、拿不到集中采集授权 | 联邦血缘（路由 + 对齐表 + 桥接边） | 不搬数据即可互通，但前提是身份对齐先成立 |
| 多云 / 数据出境约束 | 跨云骨架汇聚 + 明细回源 | 统一视图必须避开统一存储，否则部署本身不合法 |
| 链路上有大量非解析型作业 | 运行时兜底 + 分级补全（未验证边不进门禁） | 缺口是系统性的，只能靠第二采集路径覆盖而非靠人工填 |
| 要支撑 Agent 取数与模型审计 | 字段级边 + 网关 + 时序图 | 机器消费要求可编程、带出处、可回溯到当时状态 |
| 消费方以治理与合规团队为主 | 商业治理平台（Atlan / Collibra / 阿里云 DataWorks） | 治理编排与合规举证不是血缘的核心能力，自建要额外投入一大块 |
| 有平台团队、且需要自定义对齐规则 | 自研（OpenLineage + 图存储 + 网关） | 身份与对齐规则必须可编程，现成产品改不动这一层 |

> 本节小结：本章所有候选之间，**唯一真正起决定作用的差异是「这块血缘的边是谁产出的、身份是谁生成的」**——前者决定它能不能被信任到进流程，后者决定它能不能跨域连起来。其余维度（可视化体验、AI 入口、接口风格）都是在确定了这两件事之后才需要精算的第二层问题；而对齐又必须先于其余一切，因为它出问题时不报错，只返回空。
>
> 💡 **思考锚点**：查两个数——你们血缘图的「解析失败率」，以及 `manual` 边占比；若解析失败率从没统计过，按 §7.7 它只会在事故里暴露，那你现在做变更决策依赖的影响面，究竟是上界还是下界？那些解析不出来的脚本、临时任务，你是用运行时兜底，还是就让它留在图外？
