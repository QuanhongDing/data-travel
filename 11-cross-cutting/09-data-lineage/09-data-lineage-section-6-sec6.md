## 6. 落地实践

### 9.1 LinkedIn"**把血缘构建成事件驱动、多源可扩展的图 8+ 年**"（2016-2024）

**背景（Why）**

LinkedIn 2016 年面临**"血缘信息散落在各类系统里，无法拼成一张图"**：
- **血缘生成点分散**——**批量 SQL、流式作业、调度依赖、BI 报表各自知道自己那一小段关系**
- **没有统一表示**——**不同系统用不同结构描述依赖，拼不起来**
- **全量重算不可行**——**EB 级数据下，不可能定期整体扫描所有作业重建血缘**
- **消费方多样**——**目录、质量、权限、审计都要用血缘，但各要各的格式**

**触发点（What）**

2016 年起 LinkedIn 推进 **DataHub 血缘体系**（[LinkedIn Engineering 2016-2024]），目标：
- **事件驱动增量构建**——不整体重算
- **多源可扩展**——新增数据源只需接适配器
- **统一表示**——一份血缘被多方消费

**详细做法（How）**

DataHub 血缘构建的**5 大核心组件**：

1. **事件驱动 + 增量更新（核心创新）**
   - 关键设计：**血缘的每一次变化以"变更事件"形式发布并追加到事件流**，由下游构建索引与关系图；而不是周期性全量重建
   - 关键能力：**血缘构建的代价与"变化量"成正比，而不是与"总规模"成正比**——这是 EB 级场景下血缘能保持实时的结构性原因
   - 关键性质：**增量更新、变更近实时可见、可回放重建**
   - 关键示意：
     ```text
     事件驱动的血缘构建（对比"周期性全量重建"）
       ✗ 周期性全量重建
         每天扫全部作业 → 重算整张图
         问题：EB 级下耗时极长；两次重建之间血缘是"旧"的
       ✓ 事件驱动增量
         作业变更 / 新增 / 下线  →  生成血缘变更事件
                                      │
                                 追加到事件流（可回放）
                                      │
                    ┌─────────────────┴─────────────────┐
                    ▼                                   ▼
              关系图更新（血缘）                  检索索引更新（发现）
     ────────────────────────────────────────────────
     关键：事件流可回放 → 出现问题可用同一份事件流重建图
           → 图的构建本身变成可复现的，而不是"每天算一次的黑盒"
     ```

2. **统一图模型（核心）**
   - 关键设计：**所有实体（数据集 / 字段 / 作业 / 看板 / 服务）与关系（派生 / 依赖 / 消费）统一到一种图模型**，屏蔽来源系统差异
   - 关键能力：**跨系统血缘可拼接**——"从数据源到看板"的完整链路第一次成为一条可遍历的路径
   - 关键性质：**多类实体统一建模、跨系统链路可遍历**

3. **适配器与采集面扩展（核心）**
   - 关键设计：**SQL 解析器、调度钩子、BI 工具集成、服务消费登记各作为一种采集来源**；每种来源以适配器形式接入
   - 关键能力：**长尾来源的覆盖成本可控**——血缘最常见的失败是"只覆盖主干数据管道，BI 与服务消费那一端是断的"
   - 关键性质：**新增来源接入周期显著缩短**

4. **读写分离支撑查询（核心）**
   - 关键设计：**图构建（写）与研究查询（读）分离**，查询走独立的索引与图服务
   - 关键能力：**血缘查询在 EB 级下仍为毫秒级**——这是血缘能作为日常工具而非批量报告的前提
   - 关键性质：**查询毫秒级**

5. **开放接口与多方消费（核心创新）**
   - 关键设计：**血缘以 API 与事件形式对外提供**，被目录、质量、权限、审计等多个系统消费
   - 关键能力：**一次采集多处复用**——避免每个工具各自解析 SQL、各建一份图
   - 关键性质：**多系统共用一份血缘**

**DataHub 血缘构建关键数字**（[LinkedIn Engineering 2016-2024]）：

| 指标 | 改前（周期性全量重建） | 改后 | 提升 |
| --- | --- | --- | --- |
| **构建方式** | 周期性全量扫描 | 事件驱动增量 | **代价与变化量成正比** |
| **血缘新鲜度** | 两次重建之间为旧 | 变更近实时可见 | **∞** |
| **可回放重建** | 不可复现 | 事件流可回放重建图 | **可复现** |
| **实体类型** | 以表为主 | 数据集 / 字段 / 作业 / 看板 / 服务 | **跨系统可拼** |
| **来源扩展** | 每源写一套逻辑 | 适配器机制 | **接入周期缩短** |
| **查询性能** | 批量报告 | 读写分离，查询毫秒级 | **日常可用** |
| **血缘复用** | 一工具一份 | 开放 API 多方共用 | **重复采集消除** |
| **可管理规模** | 千级表 | 十万级数据集 | **∞** |

**具体数字（How much）**

- 团队规模：LinkedIn 元数据 / 数据治理团队 50+ 人
- 关键性质：**事件驱动增量**；**统一图模型**；**查询毫秒级**；**开放 API 多方复用**
- 业务影响：让 EB 级规模下的血缘保持新鲜且可被多系统复用，并成为行业广泛采用的元数据与血缘基础设施

**失败教训**

- 早期「**周期性全量重建血缘**」——EB 级下耗时极长且两次之间血缘已过时，倒逼**「事件驱动增量构建 + 可回放重建」**
- 「**各来源系统各自表示依赖**」——拼不成完整链路，倒逼**「统一图模型，屏蔽来源差异」**
- 「**只覆盖主干数据管道**」——BI 与服务消费那一端断裂，倒逼**「适配器机制扩展采集面」**
- 「**血缘只给一个工具用**」——各工具重复解析、口径不一，倒逼**「开放 API，多系统共用一份血缘」**

### 9.2 阿里"**跨系统血缘打通：把计算、调度、BI 与服务拼成一张图 10+ 年**"（2014-2024）

**背景（Why）**

阿里 2014 年面临**"血缘断在系统边界上"**：
- **30 万+ 表、25 BU**——**数据链路横跨计算引擎、调度平台、BI 工具与数据服务，任何一段缺失都会让链路断掉**
- **断链即无法评估**——**"这张表最终影响了哪些看板"因为 BI 那一端没接上而答不出**
- **多引擎方言各异**——**不同计算引擎的 SQL 方言不同，解析逻辑不能通用**
- **合规审计需要完整链路**——**"这份看板数据的来源是什么"必须能一路追到源头**

**触发点（What）**

2014 年阿里推进**跨系统血缘打通**（[阿里公开材料 2014-2024]），目标：
- **一张图覆盖全链**——从数据源到看板与服务
- **多引擎方言可解析**——统一到同一表达式模型
- **审计可追到底**——链路完整可举证

**详细做法（How）**

阿里跨系统血缘的**5 大核心组件**：

1. **"链路不断在系统边界"是核心目标（核心创新）**
   - 关键设计：**把数据链路上每一类系统都接入血缘采集**——计算引擎（批量 / 流式）、调度平台（作业依赖）、BI 工具（看板与数据集）、数据服务（接口与调用方）；任意一类缺失都会让链路在该处断开
   - 关键能力：**"从源头到最终消费"是完整可遍历的路径**——这决定了血缘能否回答业务真正关心的问题
   - 关键数字：**30 万+ 表全链覆盖、审计可追到源头**
   - 关键示意：
     ```text
     完整链路的四段（任一缺失则链路断裂）
       ① 数据接入          外部源 → 贴源层
       ② 计算与加工        批量 SQL / 流式作业 / 脚本
       ③ 调度与依赖        作业之间的先后与依赖关系
       ④ 最终消费          BI 看板 / 报表 / 数据服务接口 / 模型特征
     ────────────────────────────────────────────────
     常见的"断链"位置：
       断在 ③ → 知道表关系，但不知道"谁先跑谁"
       断在 ④ → 知道表被谁加工，但不知道"最终影响了哪个看板"
     ────────────────────────────────────────────────
     为什么必须打通 ④：
       业务与审计真正关心的是"这个数最终用在了哪"
       只有表级链路的血缘，回答不了这个问题
     ```

2. **多引擎方言统一解析（核心）**
   - 关键设计：**不同计算引擎的 SQL 方言先解析成统一的表达式模型**（字段级映射 + 运算关系），再由统一模型生成血缘
   - 关键能力：**新增引擎只需补一个解析器**，血缘逻辑不重复实现
   - 关键性质：**多引擎统一解析、新增引擎可扩展**

3. **调度依赖与数据依赖合并（核心）**
   - 关键设计：**调度依赖（作业先后）与数据依赖（读写关系）合并到同一张图**，并区分两者
   - 关键能力：**"这个作业慢，会连带影响哪些下游"这类问题可回答**——纯数据依赖答不出时序传导
   - 关键性质：**调度与数据依赖可区分**

4. **链路溯源与合规举证（核心）**
   - 关键设计：**从任一节点可向上溯源到源头、向下展开到最终消费**，并记录变更历史
   - 关键能力：**审计"这份数据的来源是什么、经过哪些加工"可逐条展开**
   - 关键性质：**双向溯源、审计可举证**

5. **采集优先自动化（核心创新）**
   - 关键设计：**以解析与钩子自动采集为主**，人工登记用于补充无法自动获取的部分（如业务语义、外部系统）
   - 关键能力：**血缘不会因无人登记而大面积空缺**——人工登记的血缘通常在数周后开始过期
   - 关键性质：**自动采集为主 + 人工补充**

**阿里跨系统血缘关键数字**（[阿里公开材料 2014-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **链路覆盖** | 仅计算层 | 接入 / 计算 / 调度 / 消费四段 | **链路不断** |
| **能回答"最终影响了哪个看板"** | 不能 | 可向下展开到看板与服务 | **∞** |
| **引擎方言** | 各引擎各自解析 | 统一表达式模型 | **可扩展** |
| **调度与数据依赖** | 分离或缺失 | 合并到同一图并区分 | **可分析时序传导** |
| **溯源能力** | 单向 / 部分 | 双向（上游溯源 / 下游展开） | **可举证** |
| **变更历史** | 部分 | 完整记录 | **可追溯** |
| **采集方式** | 人工登记为主 | 自动为主 + 人工补充 | **不会大面积空缺** |
| **资产规模** | — | 30 万+ 表 / 25 BU | **∞** |

**具体数字（How much）**

- 团队规模：阿里数据治理 / 平台团队数百人
- 关键数字：**30 万+ 表 / 25 BU 全链四段覆盖**；**多引擎统一解析**；**双向溯源**；**审计可举证**
- 业务影响：覆盖阿里全集团 25 BU 的 30 万+ 表，把血缘从"表级关系"扩展为"从源头到消费"的完整链路

**失败教训**

- 早期「**只采集计算层血缘**」——BI 与服务消费那一端断裂，"最终影响了哪个看板"答不出，倒逼**「把接入 / 计算 / 调度 / 消费四段都接入」**
- 「**各引擎各自实现解析**」——新增引擎要重做一遍且口径不一，倒逼**「统一表达式模型，引擎只提供解析器」**
- 「**只看数据依赖忽略调度依赖**」——回答不了"作业延迟会连带影响谁"，倒逼**「调度与数据依赖合并到同一图并区分」**
- 「**血缘靠人工登记**」——数周后开始过期、覆盖持续下降，倒逼**「自动采集为主，人工只做补充」**

### 9.3 字节"**字段级血缘的解析工程：把动态 SQL 与脚本也纳入图 4+ 年**"（2020-2024）

**背景（Why）**

字节 2020 年面临**"字段级血缘的解析难点集中在'解析不出来'的那部分"**：
- **静态解析覆盖主干**——**标准 SQL 里的字段映射可以解析出来**
- **但最难的是解析不出来的**——**动态拼接 SQL、脚本任务、外部导入，这些往往是关键链路的一环**
- **实时链路血缘缺失**——**流式作业的字段级血缘在早期工具链里覆盖不足**
- **血缘图不完整就等于不可信**——**只要存在已知盲区，使用方就无法据此下判断**

**触发点（What）**

2020 年字节推进**字段级血缘的解析工程（含实时链路与兜底采集）**（[字节技术博客 2020-2024]），目标：
- **字段级解析**——逐字段映射关系
- **动态 / 脚本站点兜底**——运行时采集补齐静态解析的盲区
- **实时链路纳入**——流式作业血缘同样进图

**详细做法（How）**

字节字段级血缘解析的**5 大核心组件**：

1. **静态解析 + 运行时兜底的双层采集（核心创新）**
   - 关键设计：**静态解析负责主干（标准 SQL、调度定义、作业模板）**；**对无法静态解析的部分在运行时采集实际读写对象**（记录作业真正读了哪些表与字段、写了哪些）
   - 关键能力：**盲区不再是"看不见的依赖"**——动态 SQL 这类最难的场景也能被覆盖，血缘图的完整性有保障
   - 关键性质：**字段级覆盖、动态 SQL 盲区被兜底覆盖**
   - 关键示意：
     ```text
     两层采集：静态为主，运行时兜底（覆盖动态与脚本）
       ┌── 静态解析（覆盖主干，成本低、可提前）────────────┐
       │  · 标准 SQL（含 CTE / 子查询 / 窗口 / 表达式）      │
       │  · 调度与作业模板                                  │
       │  · 建表语句与 Schema 变更                            │
       └────────────────────────────────────────────────────┘
                         │ 解析不出的部分
                         ▼
       ┌── 运行时采集（覆盖动态与脚本，作为兜底）──────────┐
       │  · 动态拼接 SQL：记录最终执行语句                   │
       │  · 脚本任务：记录实际读写的表与字段                 │
       │  · 外部导入 / 导出：登记来源与去向                  │
       └────────────────────────────────────────────────────┘
     ────────────────────────────────────────────────
     关键：静态能解析的用静态（可提前、成本低）
           静态解析不出的用运行时兜底（事后但真实）
           两者合并 → 图上不再有"未知区域"
     ```

2. **实时链路血缘（核心）**
   - 关键设计：**流式作业的输入输出（topic ↔ 表 ↔ 下游作业）纳入同一张血缘图**，与批量链路拼接
   - 关键能力：**"实时链路 + 离线链路"组成完整图**——只覆盖批量会导致实时那一侧的字段级关系缺失
   - 关键性质：**实时与批量链路合并成一张图**

3. **血缘盲区的显式标记（核心）**
   - 关键设计：**无法采集到的部分不静默略过，而是显式标记为"未知"**，并统计盲区比例、给出补齐优先级
   - 关键能力：**使用方知道"哪里不知道"**——盲区不可怕，"不知道自己有盲区"才可怕
   - 关键性质：**盲区可见、比例可统计**

4. **图的新鲜度与校准（核心）**
   - 关键设计：**定期对比图的当前状态与重新解析的结果**，发现漂移即更新；记录每个节点与边的最后更新时间
   - 关键能力：**血缘不会静默过期**——过期血缘会给出错误的安全感，比没有血缘更危险
   - 关键性质：**新鲜度可查、漂移可发现**

5. **字段级图的查询能力（核心创新）**
   - 关键设计：**支持"某字段的下游字段全集"与"某字段的上游来源"的双向查询**，并支持路径展开
   - 关键能力：**字段级的问题能被字段级地回答**——只到表级的图，回答不了"改这个字段会影响哪些字段"
   - 关键性质：**字段级双向查询**

**字节字段级血缘解析关键数字**（[字节技术博客 2020-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **血缘粒度** | 表级 | 字段级（含表达式与聚合） | **字段级可查** |
| **动态 SQL / 脚本** | 未覆盖（不可见依赖） | 运行时采集兜底 | **盲区被覆盖** |
| **实时链路** | 多为空白 | 纳入同一张图 | **流批链路合并** |
| **盲区处理** | 静默略过 | 显式标记 + 统计比例 + 补齐优先级 | **盲区可见** |
| **新鲜度** | 不可知 | 定期校准 + 记录更新时间 | **过期可发现** |
| **查询能力** | 表级上下游 | 字段级双向 + 路径展开 | **可回答字段级问题** |
| **业务覆盖** | 单个业务 | 4 业务统一 | **∞** |
| **可管理规模** | 千级表 | 万级表 / 千万级字段关系 | **∞** |

**具体数字（How much）**

- 团队规模：字节数据治理 / 平台团队 50+ 人
- 关键数字：**4 业务统一**；**字段级解析**；**运行时兜底**；**实时链路纳入**；**盲区显式标记**
- 业务影响：让字段级血缘覆盖到动态与实时场景，成为变更评估与问题定位的可靠依据

**失败教训**

- 早期「**只做静态解析**」——动态 SQL 与脚本成为不可见依赖，倒逼**「运行时采集兜底，记录实际读写对象」**
- 「**只覆盖批量链路**」——实时那一侧字段级关系缺失，倒逼**「流式作业纳入同一张图」**
- 「**解析不出就静默略过**」——使用方误以为图的覆盖是完整的，倒逼**「显式标记未知区域 + 统计盲区比例」**
- 「**图建完不校准**」——依赖关系早已变化但图还是旧的，倒逼**「定期校准 + 记录节点与边的新鲜度」**

### 9.4 滴滴"**血缘图的服务化：把图变成可被多方调用的查询能力 5+ 年**"（2019-2024）

**背景（Why）**

滴滴 2019 年面临**"有图但用不上"**：
- **十万级表、多类数据源**——**血缘图建起来了，但只有少数人能查**
- **查询需求多样**——**上游溯源、下游影响、路径分析、按标签筛选，各团队要的不同**
- **图查询性能压力**——**多团队同时查同一张图，直接查图数据库会互相拖累**
- **成果不可复用**——**各团队自己写脚本查图，重复实现且口径不一**

**触发点（What）**

2019 年滴滴推进**血缘图服务化**（[滴滴公开材料 2019-2024]），目标：
- **查询能力服务化**——统一的查询接口而非直接查库
- **常见查询模板化**——上游溯源 / 下游影响 / 路径分析开箱可用
- **性能与隔离**——多团队并发查询互不影响

**详细做法（How）**

滴滴血缘服务化的**5 大核心组件**：

1. **"查询能力"而非"数据库"对外提供（核心创新）**
   - 关键设计：**对外提供的是查询接口与查询模板**（上游溯源 / 下游影响 / 两点间路径 / 按标签筛选），而不是让使用方直连图数据库写查询
   - 关键能力：**使用门槛降低且查询可控**——直连图库意味着使用方要懂图查询语言、且可能写出拖垮集群的查询
   - 关键性质：**查询模板开箱、使用方无需懂图查询**
   - 关键示意：
     ```text
     服务化：把"图数据库"包装成"查询能力"
       ✗ 直接开放图数据库
         各团队写自己的图查询 → 门槛高、口径不一、
         个别低效查询会拖垮集群
       ✓ 查询能力服务化
         上游溯源  ──▶ 给定节点，返回完整上游来源链路
         下游影响  ──▶ 给定节点，返回下游全集（可限定深度/类型）
         两点路径  ──▶ 返回从一个资产到另一个资产的链路
         标签筛选  ──▶ 如"含个人信息的字段及其下游"
                    │
             统一服务层：限流 / 缓存 / 查询代价控制
                    │
                    ▼
                 血缘图存储
     ────────────────────────────────────────────────
     关键：把"怎么查图"这件事收进服务层
           使用方只表达"我要什么"，不表达"怎么算"
     ```

2. **查询模板与参数化（核心）**
   - 关键设计：**常见问题做成参数化模板**（指定深度、限定实体类型、排除临时表等）
   - 关键能力：**同一类问题全公司口径一致**——而不是每个团队各写一版"下游影响"，得到略有差异的结果
   - 关键性质：**查询口径统一**

3. **查询代价控制与缓存（核心）**
   - 关键设计：**对深层递归查询设深度与规模上限**；高频查询结果缓存；按使用方限流
   - 关键能力：**图服务在多团队并发下不被单个查询拖垮**——血缘图的递归查询天然昂贵，不设限迟早出事
   - 关键性质：**并发查询互不影响**

4. **多点写入的图一致性（核心）**
   - 关键设计：**多来源写入同一张图时保证关系不冲突**（如同一依赖被两个来源以不同方式描述），冲突以优先级或合并规则处理
   - 关键能力：**图在多种采集来源并存时保持一致**，而不是出现互相矛盾的两条边
   - 关键性质：**多源写入一致**

5. **与消费方系统集成（核心创新）**
   - 关键设计：**目录、质量、权限、变更评估等系统通过服务接口取用血缘**，而不是各自建图
   - 关键能力：**血缘只存在于一处**——多系统各自建图必然导致结果不一致与维护重复
   - 关键性质：**多系统共用一份图**

**滴滴血缘服务化关键数字**（[滴滴公开材料 2019-2024]）：

| 指标 | 改前（开放图数据库） | 改后 | 提升 |
| --- | --- | --- | --- |
| **使用方式** | 使用方直连图库写查询 | 查询接口 + 模板 | **门槛降低** |
| **常见查询** | 各自实现 | 上游溯源 / 下游影响 / 路径 / 标签筛选 | **口径统一** |
| **查询结果一致性** | 各团队略有差异 | 同一模板同一口径 | **一致** |
| **低效查询风险** | 可能拖垮集群 | 深度与规模上限 + 限流 + 缓存 | **并发互不影响** |
| **多源写入冲突** | 可能出现矛盾边 | 优先级 / 合并规则 | **图内一致** |
| **消费方集成** | 各系统各自建图 | 统一服务接口 | **只存在一份图** |
| **可管理规模** | 千级表 | 十万级表 | **∞** |
| **新团队接入** | 需学图查询 | 直接用模板 | **周期缩短** |

**具体数字（How much）**

- 团队规模：滴滴数据治理 / 平台团队 50+ 人
- 关键性质：**查询服务化**；**模板口径统一**；**代价控制与缓存**；**多系统共用一份图**
- 业务影响：让十万级表的血缘图成为全公司可直接调用的能力，支撑变更评估、问题定位与合规追溯

**失败教训**

- 早期「**直接开放图数据库给各团队查**」——门槛高、口径不一，个别低效查询拖垮集群，倒逼**「查询能力服务化 + 参数化模板」**
- 「**下游影响查询各自实现**」——不同团队得到略有差异的结果，倒逼**「统一模板，口径一致」**
- 「**递归查询不设上限**」——深层查询把图服务打满，倒逼**「深度/规模上限 + 限流 + 高频缓存」**
- 「**各消费方各自建图**」——结果不一致且重复维护，倒逼**「统一服务接口，全公司只存在一份图」**

### 9.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**标准 SQL 静态解析 + 表级血缘图 + 上下游查询**」（**最简单**）——**1 个业务域、百级表**
- 产出：**静态解析器 + 统一图模型（实体与关系）+ 上下游双向查询**
- 团队：**2-3 人**
- 验证标准：**标准 SQL 的表级上下游可自动生成**、**无上游 / 无下游的孤立节点可识别**、**图可被查询接口访问（而非直连库）**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 业务域 / 千级表 / 字段级**」
- 引入「**字段级解析（含表达式、聚合、条件分支）**」——逐字段映射
- 引入「**调度依赖与数据依赖合并**」——可分析时序传导
- 团队：5-10 人
- 验证标准：**字段级双向查询可用**、**调度与数据依赖可区分**、**图有新鲜度记录**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 业务域 / 万级表 / 多引擎多链路**」
- 引入「**多引擎方言统一解析 + 运行时兜底采集（动态 SQL / 脚本）**」
- 引入「**离线与实时链路合并到同一张图**」+「**盲区显式标记与比例统计**」
- 团队：10-30 人
- 验证标准：**动态与脚本类依赖可见**、**流批链路完整拼通**、**盲区可见且比例下降**

**100 → 1000 阶段：12-24 个月**

- 引入「**查询能力服务化（模板 + 代价控制 + 缓存 + 限流）**」
- 引入「**链路打通到最终消费（BI / 服务接口 / 模型特征）**」+「**多源写入一致性规则**」
- 引入「**多系统共用一份图（目录 / 质量 / 权限 / 审计通过接口取用）**」
- 团队：30-100 人
- 验证标准：**能回答"最终影响了哪个看板 / 服务"**、**并发查询互不影响**、**全公司只存在一份血缘图**、**审计可一路溯源到源头**

### 9.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**血缘构建方式**」 | 周期全量重建 | 事件驱动增量 | **代价与变化量成正比** |
| 「**血缘新鲜度**」 | 两次重建之间为旧 | 变更近实时可见 | **∞** |
| 「**链路完整度**」 | 仅计算层 | 接入 / 计算 / 调度 / 消费全段 | **链路不断** |
| 「**血缘粒度**」 | 表级 | 字段级（含表达式与聚合） | **字段级可查** |
| 「**动态 / 脚本依赖**」 | 不可见 | 运行时兜底覆盖 | **盲区消除** |
| 「**实时链路血缘**」 | 空白 | 与批量合并成一张图 | **∞** |
| 「**盲区可知性**」 | 不可知 | 显式标记 + 比例统计 | **可见** |
| 「**查询方式**」 | 直连图库 | 服务化 + 模板 | **门槛降低、口径统一** |
| 「**并发查询**」 | 单个查询可拖垮集群 | 上限 + 限流 + 缓存 | **互不影响** |
| 「**血缘复用**」 | 各系统各自建图 | 全公司一份图 | **重复消除** |

**关键投资回报**：
- **直接节省**：「**构建代价与变化量成正比 + 全公司只维护一份图**」——**血缘最大的持续性成本是"不断重算整张图"与"每个系统各建一份"**；事件驱动增量与统一服务化分别消掉这两项
- **业务价值**：「**链路完整（含最终消费）+ 字段级 + 查询服务化**」——**血缘的价值取决于它能不能回答业务真正问的问题**："改了它会怎样""这个数最终用在哪"；只到表级、只到计算层的图，回答不了其中任何一个
- **AI 时代关键**：「**字段级双向血缘 + 盲区显式标记 + 服务化查询接口**」——**这是 AI 取数与模型可解释的前提**：LLM 要判断"这个字段能不能用、用了会波及什么"，需要一个能按字段遍历、且明确告知"哪些区域未知"的血缘服务；把图包装成查询接口，则是让 Agent 能用上它（而不是要求 Agent 会写图查询语言）的工程前提

---

> **本节小结**：
> - 4 个真实案例（LinkedIn / 阿里 / 字节 / 滴滴）印证：**数据血缘不是「画一张依赖图」，是「事件驱动增量构建 + 统一图模型 + 四段链路打通 + 静态解析与运行时兜底 + 查询服务化」5 件套**。
> - 关键时间线：LinkedIn 8+ 年 / 阿里 10+ 年 / 字节 4+ 年 / 滴滴 5+ 年 —— **血缘体系是 4+ 年长期工程**，且**三个最常见的断点是：动态与脚本没兜底、实时链路没纳入、BI 与服务那一端没接上**。
> - 选型第一原则：「**标准 SQL 静态解析 + 表级图 + 上下游查询**」（**最简单**）——**1 个业务域** → 「**字段级 + 调度依赖合并 + 新鲜度**」（**必须**）→ 「**多引擎解析 + 运行时兜底 + 流批合并 + 盲区标记**」（**生产**）→ 「**查询服务化 + 链路打通到消费 + 全公司一份图**」（**AI 时代**）。
> - 99% 的失败来自「**周期全量重建 + 只覆盖计算层 + 动态脚本不兜底 + 直连图库给使用方**」——必须有 **增量构建 + 全链打通 + 运行时兜底 + 服务化查询**。
> - 真正的 ROI 来自「**链路不断 + 字段级可查 + 盲区可见 + 并发互不影响**」——是**血缘能否从"关系图"变成"可依赖的基础设施"的分水岭**。
