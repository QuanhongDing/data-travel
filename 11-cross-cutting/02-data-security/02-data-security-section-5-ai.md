## 5. 前沿演进（AI 时代）

> 原 § 5 共 108 行、为方向清单（5 条方向 + 3 条 RAG 挑战 + 6 层解决措施 + 3 条 GraphRAG 要点 + 3 条学术条目 + 7 条工业条目 + 7 条趋势），其列出的条目在本节 5.1 表与各处落点里逐条保留并重新归类，重写为约 290 行的机制与成熟度评估。

### 5.1 先分清三类「前沿」

主文件把数据安全定义成「四道防线 + 一道审计」：分类分级 → 访问控制 → 脱敏加密 → 网关防护，加全链路审计（主文件 §1.1）。四道防线共享同一个前提，[§ 3.1](02-data-security-section-3-sec3.md) 把它压成一句话——**安全的强度 = 检查点的位置 × 检查点不可绕过的程度**；而检查点放在哪一层，是以「访问是一个可授权的事件——以表、以文件、以目录为单位被授予或拒绝」为前提选出来的。本节要判的不是「AI 能不能接进这套体系」，而是 **AI 把出口的形态改掉之后，这四道防线各自还剩多少效力**。

这个改动在 §3 的每一节里都已经显形：[§ 3.2.3](02-data-security-section-3-sec3.md) 说自然语言取数让 SQL 由模型生成、网关必须把默认行为改成「不可解析即拒绝」；§3.2.4 说训练语料是「一次授权、长期留存」的用途，脱敏必须在入库那一刻完成；§3.2.5 说模型权重与提示词成了与数据同等重要的资产；§3.2.6 说访问决策的输入多了「用途」这一维，而用途由调用方自己声明。四处的结论指向同一件事：**出口从「可打包授权的对象」变成了「按次发生的动作」**。

本节用 L1 / L2 / L3 三级区分，判据必须可核验，而不是「感觉成熟」：

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口 / 生态未稳，或**仅有厂商与建设方自有案例**，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

**本节不对 L1 判据做任何修正，也不缩小它的适用范围。** 本主题有一条特有陷阱：**法规文本不能充当第②条**。法规只证明「义务存在」，不证明「有人真的在做」；把「某法规要求了 X」读成「X 已是可用能力」，是这一节最容易犯的错。第二条纪律：**已经在生产里跑了很多年的既有能力**（分类分级、加密、审计、脱敏、网关）不是 AI 方向，本节只在对照时提及。

还有四件容易混的事，先在这里分开：

- **产品名 vs 能力名**：「AI DLP」「机密 LLM 推理」「RAG 数据隔离」都是**能力名**，不是某个产品的专属功能；同一能力在不同厂商材料里挂在不同的产品名下（[§ 4](02-data-security-section-4-sec4.md) §4.3 的「AI 时代新工具」一栏列的就是**产品与公司名**，六项里只有「机密 LLM 推理」写的是能力名；另两个能力名在这一章里写作「AI 输入 DLP」与「RAG 数据隔离」，见 §4.1 的「AI 时代加固」一步）。判定方法：按**产品全名 + 该能力的输入输出**核对，而不是按能力名归类。
- **数据水印 vs LLM 输出水印**：前者是把归属信息埋入外发数据、用于事后追溯，是**既有能力**（见 [§6](02-data-security-section-6-sec6.md) 案例里的「脱敏 + 隐式水印」）；后者是判断一段文本是否由某个模型生成，可被改写破坏、且有模态与长度限制。**在这两者之间，本节只判后者为 L3**（本节判 L3 的方向不止这一处，完整清单见 §5.1 表）。
- **多租户隔离 vs 密级过滤**：向量库的 namespace / 多租户解决的是**索引之间**的隔离；同一索引内不同密级的内容该怎么被过滤，是另一件事，两者不能互相替代。
- **产品能力 vs 部署事实**：判断取数出口是否真的受控，不看产品清单，看**能不能列出「没有经过任何检查点的取数路径」**（§3.2.3 的上线前验收动作）。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**——改变了成本函数、改变了接口边界、把人工判断换成统计判断，还是只换了个前端？本主题的答案集中在**一条**：**保护对象的粒度与出口的形态变了**——从「数据集被拷贝」变成「一次对话、一次工具调用、一次检索返回」，敏感物的单位从字节变成了**片段与一次调用**。所有四道防线都建立在「访问可授权」这个前提上，而按次发生的出口让「授权」这个动作失去了着力点——**能对一张表授权，很难对『第 3 次查询返回的第 5 个片段』授权**。其余方向要么是这条机制的直接后果（DLP、出口审计），要么只是把既有能力套到新对象上（分类分级、加密、脱敏），要么与 AI 没有因果关系（零信任、左移、隐私计算落地）。

| 演进方向（含原 §5 条目去向） | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| AI DLP：输入端扫描与实时拦截（原方向 1 输入端） | **L2** | ① 通用 DLP 与云安全服务有正式产品条目（判定入口：看官方文档里是 GA 还是 Preview）；**②核不到**——AI 场景下没有可指认的非厂商生产案例；③ 判定口径（什么算敏感、一次会话算一次还是多次）无公开标准 | 先做输入端拦截并把漏检与误报当成验收指标；**它不能替代路径收口** |

| 隐私计算大规模落地（原趋势 6） | **L3** | ① 原语层有正式条目（见 [§ 8 隐私计算](../08-privacy-computing/08-privacy-computing.md)）；② 不适用（本主题不评估它）；③ 在「AI 数据安全」这个口径下，缺少可复核的规模与开销口径 | 归 [§ 8 隐私计算](../08-privacy-computing/08-privacy-computing.md) 评估，本节不重复定级 |

> 表里**没有任何一行达到 L1**，原因不在技术，而在公开材料的构成：可核验的是**厂商产品材料**、**法规文本**与**论文**三类，其中没有一条可指认的第三方（非厂商）公开生产案例；法规文本更是只证明义务存在。表里工程依据最扎实的一行是**机密 LLM 推理**——底层隔离的正式条目与文档都能点到（§3.2.5），卡住的正是第②条：端到端机密推理的算子覆盖与证明粒度没有通行做法。**L2 不等于「不好」，只等于「公开证据到不了 L1」**。

**本节与原 §5 的对应关系**（保证原文件列出的条目一个不丢，只换位置与定级；「行」指 §5.1 表）：原 §5.1 的五个方向——方向 1 的四件事按表内行号顺序拆成第 1–4 行（**输入端** → 第 1 行 / **审计端** → 第 2 行 / **输出端敏感词检测** → 第 3 行 / **输出端水印** → 第 4 行），方向 2 → 第 5 行，方向 3 拆成第 6、7 行（建议 / 生效），方向 4 → 第 8 行，方向 5 → 第 12 行；原方向 3 的「代表探索」（OpenAI Moderation API + 自研分类、Collibra AI、Atlan AI）与原方向 4 的「代表实践」（Pinecone Namespace + RBAC、Milvus 多租户、Weaviate Multi-Tenancy、阿里云百炼 + 私有知识库）分别落在第 6 行与第 8、9 行的判定入口，两处都只作**方向指认**（§5.2.3、§5.2.4），其能力与版本以各家官方文档为准；原 §5.2 的三条 RAG 挑战（输入文档含敏感 / Embedding 记住敏感数据 / 向量库是新资产）分别落在第 8、10、9 行，六层解决措施落在 §5.2.3 的六层表，三条 GraphRAG 要点落在第 11 行；原 §5.3 的三条学术条目与七条工业条目，本节不逐条复述，统一按 §5.4 的判定入口处理——**其中三条学术条目所指的三个方向，§5.4 逐条给出落点**；原 §5.4 的七条趋势分别落在第 5、12、13、14、15 行，其中「AI DLP 成为企业标配」（原趋势 2）移入 §5.5 第一条——**它是对未来的断言，不是一项能力**。

**这三级的排法直接决定落地顺序**：

- **先做的三件事都不在表里**，因为它们是主文件 §1.1 的既有防线，却又是后面每一个方向的评估前提：**字段级分类分级**（主文件 §2.1）→ **把取数路径收口到网关**（§3.2.3）→ **全链路审计留痕**（主文件 §1.1 的第五层）。没有这三件事，「AI DLP 拦住了什么」无从判定，「机密推理保护了什么」无从核对。
- **L2 做 PoC，并先测两个数**：出口路径里**没经过检查点的比例**，以及内容检测的**漏检率**。这两个数拿不出来，L2 就停在原地，与选哪家产品无关。
- **L3 不排进排期**：输出水印、向量反演、GraphRAG 的隐私层、分类分级自动生效都属于「等信号」。它们的共同前提是**判定标准先存在**——现在我们连「水印被破坏」都证明不了。
- **回填机制**：每次安全项目复盘时回填一次级别；某个 L2 若一年内仍拿不到自己组织里的实测量，降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面把方向分成四组：**前三组按同一套结构逐条写**（旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度），**第四组用一张表覆盖同一套要素**，因为那一族的共同点恰恰是「机制没变」。四组共用 §5.1 里的那一条机制（保护对象的粒度与出口形态），差别在**它落在哪一层**。

| 方向 | AI 改变了什么机制 | 这条变化落在哪一层 |
| --- | --- | --- |
| §5.2.1 AI DLP 与出口审计 | 出口从「对象」变成「动作」，管控从一次授权变成按次判定 | **接口边界**（检查点必须从「入口一处」铺到「输入、检索、输出、存储四处」） |
| §5.2.2 机密 LLM 推理 | 信任锚从「信任运营方」换成「可远程验证的硬件声明」 | **信任假设**（可验证替代了承诺；新增的被保护对象是 prompt 与权重） |
| §5.2.3 RAG 与向量库 | 泄漏面从「数据集被拷走」变成「检索接口被反复询问」 | **数据资产边界**（向量库是新的资产副本，且它的粒度与源数据不一致） |
| §5.2.4 分类分级、治理与监管 | 大多没有改变机制 | **既有能力的延伸与制度侧**（分类分级、加密、脱敏、零信任都不是 AI 造的） |

读法建议：如果时间只够读一节，读 §5.2.3——它是本节里唯一一条**新增的、且今天就存在于你系统里**的风险（检索接口是数据出口），而且它的第一道控制（密级过滤放在召回前）今天就能做。§5.2.2 的收益要等你愿意把信任假设写进合规材料时才兑现。

只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次「管控更严了」，都对应一处新的误拦、新的性能开销或新的运维面。这也是为什么 §5.2.1 的三行都停在 L2 而不是更高：**它们的判定输入是内容，而内容判定天生带漏检与误报**，这两者的代价一个在明处（业务投诉）、一个在暗处（静默流出）。

#### 5.2.1 AI DLP 与出口审计（原方向 1）

- **旧做法与它的卡点**：出口管控靠网关与网络边界——所有取数经过网关的 SQL 改写与审计（§3.2.3）。卡点是**出口不再经过这张网关**：员工把内部数据贴进外部模型的输入框，这条路径上没有 SQL、没有表名、没有可改写的语句。§3.5 的反模式清单把这种情况写成「数据流出后脱离全部检查点，且留下的是无法撤回的自然语言片段」。
- **AI 改变了什么机制**：**管控判定的输入从「结构化访问请求」变成了「自然语言内容」**——判定从「你有没有权限查这张表」（确定、可执行）变成「这段话里有没有敏感信息」（统计、有漏检与误报）。检查点也因为出口的形态而必须**从一处铺到四处**（输入、检索、输出、存储），这是 [§ 7 审计与合规](../07-audit-and-compliance/07-audit-and-compliance-section-5-ai.md) 里「判定发生的位置从『数据入口一处』变成『输入、检索、输出、存储四处』」这一条在安全侧的对应物。
- **由此得到的**：**因为判定可以作用于内容而不只是对象，那些「不经过网关」的出口第一次有了检查点**——包括输入粘贴、API 调用、RAG 检索返回、以及 Agent 的工具调用。这条收益不依赖任何新密码学，只需要把检查点放在模型调用的必经之路上（企业模型网关 / 统一 egress）。

```text
       同一个数据出口问题，两种管控位置（差别在判定输入是什么）
       ────────────────────────────────────────────────
       旧位置（判定输入 = 访问请求）
         数据源 ──► 网关（我看得懂 SQL）──► 使用方
         盲区：输入框、外部 API、检索返回、工具调用
       ────────────────────────────────────────────────
       新位置（判定输入 = 内容，且铺到四处）
         输入侧 ── 扫描 / 拦截（拦在请求发出之前）
         检索侧 ── 密级过滤（放在召回之前，不是返回之后）
         输出侧 ── 内容检测 / 留痕（判定 + 记录，不承诺「证明」）
         存储侧 ── 与源数据同一套密级与审计
       ────────────────────────────────────────────────
       判定方法：列出取数路径清单，逐条标注「经过哪个检查点」
                 ——标不出来的那条，就是当前的实际出口
```

- **由此付出的**：**其一，误拦与漏检同时存在，而两者的代价不对称**——误拦会让业务方去找绕过方式（一旦绕过成为习惯，真正危险的路径也一起出去了），漏检则是静默的；所以默认行为必须写明（「不可判定即拒绝」还是「不可判定即放行」），这个选择本身就是一条策略。**其二，检测挂在在线路径上，就要按峰值流量做容量规划**——它和 §3.2.3 的网关一样，成为新的单点与新的延迟来源。**其三，审计留痕会与留存期、目的限定、员工隐私发生冲突**：把 prompt 与输出全量留存，本身就是一份新的敏感数据资产（检索结果里可能含个人敏感信息），必须与主文件 §2.1 的分类分级同标准管理。
- **证据与来源**：【公开】通用 DLP 与内容检测是成熟的既有能力（判定入口：看各家官方文档里该能力标的是 GA 还是 Preview，以及**它的判定输入是内容还是对象**）；§3.5 的反模式与修复方向可在书内逐行核对。**【本节未能核到】AI 场景下第三方（非厂商）公开生产案例**，也未能核到可复核的漏检率与误报率口径——**任何不带条件（语料类型、判定阈值、抽检口径）的检出率声称都不可复核**；原清单点名的 Nightfall AI、Harmonic Security、Microsoft Purview AI Hub、阿里云 AI 数据安全等，本节只作为方向指认，其能力与版本以各家官方文档为准。
- **成熟度**：**L2**。判据：① 能力有正式产品条目；**②核不到**；③ AI 场景的判定口径（什么算敏感、一次会话算一次还是多次）无公开标准 → 可做 PoC，不要做核心依赖。表内三行（输入端、审计端、输出端内容检测）同此判据；**输出水印另判 L3**，理由见 §5.5。
- **判定方法**：列出全部取数路径（BI 直连、离线同步、导出脚本、运维跳板机、第三方接口、AI 取数接口、员工自接的外部模型），逐条标注经过哪个检查点；再抽两周日志数一次「同一段敏感内容被不同请求拼出来」的次数。
- **什么时候值得做**：已经收口了网关与凭据、且内部已有可用的替代工具（自建问答、内部模型）时——**给不出替代品，拦截只会催生绕过**。
- **什么时候不值得做**：取数路径清单还列不出来时——它只会成为一份「已统一管控」的错觉。

#### 5.2.2 机密 LLM 推理（原方向 2；原趋势 1）

- **旧做法与它的卡点**：让外部模型处理受监管数据，旧路只有两条——不出来（私有部署，自己承担全部运维与算力），或签合同（把信任交给服务方）。卡点是**信任不可验证**：你能拿到的只有「我们不会看」这句承诺，而合规要回答的是「谁在什么条件下能看到明文」（主文件 §1.2 把这一点写成「AI 时代放大风险」）。
- **AI 改变了什么机制**：**信任锚的落点变了**——从「信任组织」换成「信任硬件 + 可远程验证的声明」。§3.2.5 给出这条机制的完整形态：TEE 生成证明（度量值 = 哪段代码 + 哪个版本 + 是否调试模式），调用方校验通过后才把数据密钥释放给 enclave。**模型再强也不会让运营方变得可信，能改变这点的只有证明。**
- **由此得到的**：**因为存在可远程验证的执行环境声明，所以「数据出域但计算过程隔离」第一次可以写进合规与采购材料**——不是「我们保证不看」，而是「设备签名的证明说这台机器跑的是这个镜像」。同一机制还能覆盖另外两样 AI 特有的资产：**模型权重**（模型方不必把权重交给调用方）与**提示词与上下文**（调用方不必把明文交给模型方），这是 §3.2.5 里「模型权重与提示词成为与数据同等重要的资产」这一条的技术回应。

| 要保护什么 | 掩护手段 | 掩护不了的 |
| --- | --- | --- |
| 用户输入（prompt / 上下文） | 推理在 enclave 内 + 不落盘不记日志 | 输入被模型记住并复述——这是模型行为问题，不是隔离问题（§5.4） |
| 模型权重 | 权重只在 enclave 内解密 | 权重被推理过程间接推断（输出可用于蒸馏） |
| 推理过程与中间态 | 显存加密 + 证明度量覆盖运行时 | 侧信道与微架构类攻击（见「由此付出的」第一条） |
| 训练语料 | 不在本行的范围内 | **TEE 完全不管训练阶段**——语料的脱敏必须在入库那一刻完成（§3.2.4） |

- **由此付出的**：**其一，信任只是转移，不是消失**——威胁模型从「服务方违规」换成「厂商固件与微架构的漏洞、以及密钥管理」，而这类攻击是被持续公开的；正确说法是「从信运营方变成信硬件厂商 + 证明流程」。**其二，性能与可移植性有代价**：enclave 内的算子覆盖、显存加密的带宽影响、系统调用穿越不可信边界的开销都会改变吞吐，**具体幅度必须以你自己负载的基准为准**——本节不给数字，因为公开的性能声称几乎都缺条件限定（数据量、序列长度、批次、硬件）。**其三，调试与可观测性变差**：不能随意 attach profiler，线上排障方式要重做。**其四，合规口径并未自动认可**：技术隔离回答的是「谁能看到明文」，回答不了目的限定、留存期限与可举证；把证明当成合规结论，是本主题最容易踩的一处越位。
- **证据与来源**：【公开】底层隔离有可点名的公开文档：Intel SGX 的开发者文档与 SDK 说明、AMD SEV-SNP 的架构文档、Arm CCA 的架构规范、NVIDIA H100 的机密计算模式说明、CNCF 的 Confidential Containers 项目，四家硬件厂商彼此独立（§3.2.5 给出完整判定入口与核验方式，本章不重复列出；这些文档随版本与代际更新、无固定出版年份，**请以官方文档当前版本为准**）。**【本节未能核到】「因为用了机密推理，某机构的合规结论因此改变」的第三方可核验材料**；原清单点名 Azure Confidential AI、AWS Nitro Enclaves、阿里云灵积机密版、蚂蚁摩斯等，本节只作为方向指认，其发布时点与能力一律以官方发布说明为准。
- **成熟度**：**L2**。判据：①③ 在底层隔离层成立（正式条目、证明接口稳定）；**②核不到**——端到端机密推理（算子覆盖、证明粒度、编排方式）无通行做法 → 做 PoC，不要作为核心依赖，也不要拿它当合规结论。
- **判定方法**：用厂商的证明工具跑一次，看证明里能不能读出「镜像哈希 / 启动配置 / 是否 debug 模式」；读不出来，说明隔离边界比你想象的小。再测一次开销比（enclave 内外同负载的耗时与吞吐之比），这个数决定它能不能进你的在线链路。
- **什么时候值得做**：确实需要把受监管数据交给外部模型、或需要把模型交给外部调用方，且能接受「专用实例 + 专用密钥 + 单租户」的形态时。
- **什么时候不值得做**：数据本来就允许出域、只需要约定不留存时——先做**合同与访问审计**更划算；先上 TEE 会把运维复杂度提上去，而合规问题一个也没解决。

#### 5.2.3 RAG 数据隔离与向量库（原方向 4；原 §5.2 的 3 条挑战与 6 层措施）

- **旧做法与它的卡点**：把语料放进检索库，靠「只让有权限的人查」来控制。卡点是**出口的性质变了**：top-k 检索是被反复调用的预言机——多查几次、换着措辞问，可以把不该看的内容一片片拼出来；而检索结果一旦进了外部模型的上下文，数据就已经出域了。传统权限控制假设「数据以文件或表为单位被访问」，检索却是**以片段为单位、按查询节奏**被访问的。
- **AI 改变了什么机制**：**数据资产边界多了一份粒度不同的副本**——向量库里存的是切片的向量与元数据，它与源数据不是一一对应的：源文档删了、向量还在（这是原 §5.2 的挑战 2 与 3）；密级是字段级的、而切片是跨字段的。于是「同一份数据有两份密级不同的存在」成为常态，而**两份里更弱的那一份决定实际风险**。
- **由此得到的**：**因为出口是「查询」而不是「文件」，访问控制第一次必须是「预算 + 审计」型的**——限次、限范围、逐次留痕，而不是一次授权长期有效。这条结论今天就能落，且不依赖任何新加密技术：**先把密级过滤放在召回前**，再谈别的——[§ 8 隐私计算](../08-privacy-computing/08-privacy-computing-section-5-ai.md) 在「RAG + 隐私计算」一行给出的落地顺序与此一致：**先做出口审计与查询预算，再谈密文检索**。

| 层面（原 §5.2 的六层措施） | 落到今天能做的是什么 | 它属于哪一级 |
| --- | --- | --- |
| 文档层（接入前 DLP + 分类分级） | 复用主文件 §2.1 的六类与字段级打标，接入即登记 | L2（既有能力 + 人工确认） |
| Embedding 层（敏感字段用专属模型） | 分库 / 分索引按密级拆开，而不是靠一个模型「更安全」 | L2（架构决定，不是产品特性） |
| 向量库层（多租户隔离 + 加密 + 访问控制） | 把向量库纳入同一套密级与审计；**它不是未登记的副本** | L2（能力以各家文档为准） |
| 检索层（RBAC / ABAC 过滤 + 掩码） | **过滤放在召回前**；策略与源系统同源，不另建一套 | L2（今天就该做） |
| 生成层（输出 DLP + 审计日志） | 见 §5.2.1；输出侧判定 + 留痕 | L2 |
| 使用层（TEE 推理 + 不可下载） | 见 §5.2.2 | L2（底层）/ L3（端到端） |

- **由此付出的**：**其一，过滤放在召回前会改变检索质量**——召回集合变小、排序结果的分布变化，效果下降会以「模型答错、且答得很自信」的形式出现，比传统系统里「查不到」更难归因。**其二，切片把「字段级密级」这条既有能力打薄了**：一份文档里既有可公开段落又有敏感段落时，切片边界与密级边界不一致，必须在接入期重新切一遍。**其三，删除权在向量库里是工程问题而不是承诺问题**：删除必须同时覆盖原文档、切片、向量、索引与缓存，任一处漏掉就等于没删（原 §5.2 的挑战 2、3）。**其四，向量反演与「embedding 里还剩多少原文」没有可复核的口径**——本节不给结论，只说不要把它当已经解决的问题。
- **证据与来源**：【公开：检索层的权限过滤与向量库多租户 / 加密能力是既有能力，具体以各家官方文档为准（判定入口：看官方文档里 metadata filter 与多租户能力标的是 GA 还是 Preview）】；[§ 3.2.4](02-data-security-section-3-sec3.md) 给出「脱敏规则只能有一份，并与密级绑定」的既有结构，可直接复用到语料入库。原清单点名的代表实践（Pinecone Namespace + RBAC、Milvus 多租户、Weaviate Multi-Tenancy、阿里云百炼 + 私有知识库）本节只作为**方向指认**——多租户与过滤能力在各家产品里的命名与开放程度各不相同，其能力与版本以各家官方文档为准，判定入口是官方文档里该能力标的是 GA 还是 Preview。**【本节未能核到】「向量库删除后残留在向量侧的敏感信息比例」的可复核第三方材料**，也未能核到 RAG 数据隔离的第三方（非厂商）公开生产案例；GraphRAG 侧只有论文与演示，故本组判 L3 的两行（Embedding 残留与向量反演、GraphRAG）不给判定入口之外的任何断言。
- **成熟度**：**L2**（隔离与检索层权限、向量库纳入既有密级体系）；**L3**（Embedding 残留与向量反演、GraphRAG 数据安全——前者无可复核口径，后者只有论文与演示，①②③ 均不成立）。
- **判定方法**：数两周的检索日志——**同一条敏感内容被不同查询「拼」出来的次数**，以及被权限拒绝的次数；再做一次删除演练：删一份含敏感信息的源文档，逐处确认原文档、切片、向量、索引、缓存是否都消失。
- **什么时候值得做**：检索库里混着不同密级的内容、且有外部模型参与时。**先做出口审计与密级过滤**，这两件事的成本远低于任何隐私计算方案。
- **什么时候不值得做**：在检索粒度的权限控制都还没做之前谈密文检索或向量加密——那等于给一个还在漏的桶换更好的盖子。

```text
   本节只有两处「事后无法补救」的位置（其余都能补，这两处不能）
   ────────────────────────────────────────────────
   ① 召回前 —— 权限过滤
       放在召回后：敏感片段已经进了内存、日志、可能已经进了模型上下文
       放在召回前：不该出的片段从未被取出 → 事后不必补救
   ② 入库前 —— 语料脱敏
       入库后再脱敏：语料库已建成，「事后再删」既没有可行性也没有证据链
       入库时就脱敏：一次授权、长期留存这件事才成立
   ────────────────────────────────────────────────
   判定方法：把这两处的当前行为写下来（过滤在召回前还是后？
             语料是入库前脱敏还是事后补？）——写不出来就是没做
```

#### 5.2.4 分类分级、治理与监管，以及被写进「AI 时代」但机制没变的那一族（原方向 3、5；原趋势 3、4、5、6、7）

分类分级自动化这一条先补齐要素里的**旧做法与它的卡点**：旧做法是字段级密级由人评审一次、写进元数据（主文件 §2.1 的六类）；卡点不在判得准不准，而在**覆盖面**——字段多、新字段持续产生，人工评审只能覆盖被点名的那一批，没被点到的字段在后续四道防线上全是空白（§5.3 接口表第一行）。**AI 改变的机制**是**把「一次判定」变成「持续判定」**，由此得到的是覆盖率，由此付出的是「一个每天都可能改写的结论被下游全量依赖」——这两句的展开见本小节末段；**证据与级别**见 §5.1 表第 6、7 行与 §5.4 核验清单第 6 条。

这一条还要单独说清一件事：原方向 3 的三步是「识别 / 打标 / **建议**策略」，而它经常被读成「自动打标并自动改权限」。**从「建议」到「生效」是一次级别跃迁**：建议错了只是多一次人工复核，生效错了是把该拦的放过去或者把不该拦的拦住，而**错标的责任在现有组织里无处落地**。因此本节把它拆成两行：**建议是 L2**（① 分类分级本身是既有能力、模型只换识别方式；**②核不到**；③ 「建议」到「生效」之间没有可核验的置信度约定），**自动生效是 L3**（① 无正式条目；② 不适用——「模型标的密级够不够准到能直接改权限」没有可复核的口径；③ 无接口约定：谁为错标导致的越权负责）。两行的「现在该做什么」都是同一句话：**生效动作保留人工审批。**

原方向 3 点名的「代表探索」（OpenAI Moderation API + 自研分类、Collibra AI、Atlan AI）本节只作为**方向指认**：它们的识别对象（PII / 机密 / 内容安全是三类不同判定）、置信度输出与发布时点一律以各自官方文档为准；判定入口是 §5.4 核验清单的第 6 条（抽 50 个字段算误标率）。本节不对它们是否支持「自动生效」作任何断言——按上面的拆分，那是另一行、另一个级别。

其余五条方向用一张表覆盖同一套要素（旧做法与卡点 / AI 改变了什么机制 / 由此得到 / 由此付出 / 证据与成熟度）：

| 方向 | 旧做法与它的卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据与成熟度 |
| --- | --- | --- | --- | --- | --- |
| AI 治理与安全监管（原方向 5） | 义务散在多部法规里，安全团队靠人工对照 | **与 AI 无因果关系**：它改的是义务清单与举证方式（法规文本可核验，见 §5.4） | 「要交什么材料、留什么记录」第一次有明确清单 | 法规只证明义务存在，不证明技术手段可用；把「法规要求了」当成「能力已具备」是本主题最常见的越位 | ① 法规文本可核验；**②核不到**（法规不充当②）；③ 监管口径与报送字段仍在演进 → **L2（义务）/ L3（平台化）** |
| 数据安全合规自动化（原趋势 3） | 合规报告与监管报送靠人工整理 | **既有能力的延伸**：报送自动化是成熟 ETL 工程，AI 只加解释与映射建议 | 报告从「人工整理数天」变成「从留痕里生成」 | 生成物不是证据——每条结论必须能指回一条审计记录，否则它只是看起来合规 | ① 报送自动化是既有能力；**②核不到**；③ 报送字段随口径变化 → **L2** |
| 零信任架构普及（原趋势 4） | 纵深防御把「网段」当身份，边界消失后失效 | **与 AI 无因果关系**，且**不是 AI 方向**（§3.2.2 的既有模式） | 服务间调用按可验证身份逐次判定，不依赖网络位置 | 要求全部服务具备可验证身份，改造面大于收益；策略系统不可用时必须明确「拒绝还是放行」 | ① 形态见 §3.2.2；**②核不到**；③ 组织与流程约定，无长期接口 → **L2** |
| 数据安全左移（原趋势 7） | 安全评审排在需求池末尾，问题在上线后暴露 | **与 AI 无因果关系**：它是流程与准入约定的前移 | 分类分级与策略在设计与 CI 阶段就登记 | 前移的收益依赖「准入真的卡得住」；卡不住的左移只是多一道签字 | ① 形态见 §3.2.6（策略即代码可在 CI 里跑）；**②核不到**；③ 流程约定 → **L2** |
| 隐私计算大规模落地（原趋势 6） | 跨机构协作受合规边界限制 | **机制正交**：隐私计算防「被看见」，数据安全防「被拿走」（主文件 §2.4） | 跨机构协作可以「数据可用不可见」 | 它的规模与开销口径不属于本主题；把两项技术混写成「AI 数据安全」会让两边都排不进排期 | 本主题**不评估**；归 [§ 8 隐私计算](../08-privacy-computing/08-privacy-computing.md) → **L3**（在本主题口径下） |

**读这张表的方式是看「AI 改变了什么机制」这一列**：五行里没有一行是模型带来的变化——两条是流程约定（零信任、左移），两条是制度与报送（监管、合规自动化），一条与 AI 正交（隐私计算）。它们与 AI 方向放在同一张排期表里竞逐资源，是本节最常见的一次排序错误。

**分类分级自动化这一条还有一层容易被忽略的代价**：它把「密级」这件事从**一次判定**变成了**持续判定**。字段级密级过去由人评审一次、写进元数据；模型每天扫描一遍，就可能每天改一次结论，而下游的脱敏规则、访问策略、审计口径全都挂在这个结论上。由此得到一条操作纪律：**模型给出的密级只能作为「待确认」的候选，进入人工确认队列**——这与 [§ 5 血缘与影响分析](../05-lineage-and-impact/05-lineage-and-impact-section-5-ai.md) 对「LLM 推断出的边」的处理是同一条纪律：**统计判断可以扩大覆盖面，但它的输出在进入控制路径之前必须有人签字。**

### 5.3 与本主题既有栈的接口在哪

数据安全与 AI 之间不是「结合」关系，而是**交接物**关系：谁把什么交给谁、数据以什么形态穿过边界、失败时谁负责。**下表「现状」一列沿用同一套三级定义，但评的是这个接口本身，不是 §5.1 表里的演进方向**：按 ①/②/③ 逐条核，这一列的②全都核不到——安全侧与各平台之间的交接物是双方内部的事，不会有可指认的第三方（非厂商）公开生产案例，因此**整列没有一行到 L1**；括号里写的是这条接口当前最常出问题的地方。**唯一一行在 §5.1 表里已有级别的是最后的隐私计算，两处按同一级别写。**

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 安全 ↔ 数据目录（[../../04-data-assetization/08](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 交接物 = 字段级密级与 PII 标注；六类分级（主文件 §2.1）必须先落到字段上 | 目录侧；标注缺失时，后面四道防线全部失准（脱敏不知道脱哪些、审计不知道查什么） | L2（字段级标注的覆盖率与维护责任常无人认领） |
| 安全 ↔ 血缘（[../05-lineage-and-impact](../05-lineage-and-impact/05-lineage-and-impact.md)） | 交接物 = 字段级密级 → 血缘边；「敏感数据流过哪些下游」由血缘回答 | 安全侧定级；定级缺失时血缘只能画出链路，不能回答它是否越界 | L2（跨系统标注口径一致性） |
| 安全 ↔ RAG / 向量库（[../../04-data-assetization/05](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md)） | 交接物 = 策略决策 + 密级过滤；过滤必须发生在召回前 | 应用侧；过滤放在召回后等于没做——敏感片段已经进了内存与日志 | L2（检索粒度的权限过滤无通行做法） |
| 安全 ↔ 模型服务与 AI 网关（[../../04-data-assetization/07](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway.md)） | 交接物 = 内容分类结果 + 拦截动作 + 用途声明（§3.2.6 说决策输入多了「用途」这一维） | 安全侧定口径、平台侧执行；**不可判定时的默认行为由安全侧写死** | L2（口径与默认行为都无共识） |
| 安全 ↔ 特征平台与训练链路（[../../02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md)） | 交接物 = 语料入库前的脱敏与授权记录（§3.2.4：训练语料是一次授权、长期留存） | 平台侧；**入库那一刻没脱干净，事后没有可行的补法** | L2（入库期门禁的落地） |
| 安全 ↔ 调度与作业（[../../03-data-stack/12](../../03-data-stack/12-scheduler/12-scheduler-section-3-sec3.md)） | 交接物 = 脱敏任务的编排与令牌库的访问凭据 | 平台侧；脱敏作业失败却继续产出，是静默的漏点 | L2（失败即停的默认值不统一） |
| 安全 ↔ 审计与合规（[../07-audit-and-compliance](../07-audit-and-compliance/07-audit-and-compliance.md)） | 交接物 = 可复算的留痕（谁 / 何时 / 调了哪个模型 / 带了哪些数据 / 用途） | 双方联合；**留痕字段定不下来，合规自动化就无从生成** | L2（字段未成约定） |
| 安全 ↔ 可观测（[../04-observability](../04-observability/04-observability.md)） | 交接物 = 异常访问模式（异常导出、异常调用频率）作为安全事件源 | 可观测侧；只看业务指标不看访问画像，异常出口不会被发现 | L2（访问画像的口径各家不同） |
| 安全 ↔ 隐私计算（[../08-privacy-computing](../08-privacy-computing/08-privacy-computing.md)） | 交接物 = 密级分级结果 + 脱敏规则；隐私计算侧负责「看不到明文」，安全侧负责「谁能看」 | 安全侧定级、隐私计算侧实现；定级错了，后面所有技术选择都白做 | **L3**（与 §5.1 表第 15 行「隐私计算大规模落地」同一级别、同一理由：本节**不评估**隐私计算本身；作为交接物，它卡在**②核不到**——没有可指认的第三方公开生产案例，也缺可复核的规模与开销口径。本节不为它另立判据） |

一句话概括：**AI 没有让数据安全多出一道防线，它把出口从「对象」改成了「动作」**——由此得到三条约定。

**第一条约定：默认行为必须写死。**内容检测不可判定、SQL 不可解析、用途未声明这三种情况，必须有人明确规定是拒绝还是放行（§3 的两节各给了一条：**[§ 3.2.3](02-data-security-section-3-sec3.md) 给的是「不可解析即拒绝」**，管的是第三类；**[§ 3.2.2](02-data-security-section-3-sec3.md) 给的是「策略服务不可用时，系统是拒绝访问还是放行」必须写成明文规定并由业务签署**，管的是「判定组件本身不可用」这一类）。**没有默认值的安全控制，会在第一次误拦后被改成放行，然后永远停在放行。** §3.1 把这条的另一半也说了：「密级」与「用途」的定义权不在平台团队手里——**写不下来的组织，后面所有检查点都会退化成按最高级一刀切，而一刀切在业务侧的结果通常是绕过。**

**第二条约定：密级过滤放在召回前，脱敏放在入库前。**这两处是本节里仅有的两个「事后无法补救」的位置：检索返回之后再过滤，敏感片段已经进了内存与日志；语料入库之后再脱敏，语料库已经建成，事后再删既没有可行性，也没有可举证的证据链（§3.2.4）。

**第三条约定：留痕字段先定，再谈自动化。**「谁 / 何时 / 调了哪个模型 / 带了哪些数据 / 用途是什么」这五项定不下来，合规自动化与 AI 治理平台化都无从落地——它们生成的只能是看起来像证据的东西。

### 5.4 公开进展与文献

分三类列：论文与第三方案例只列能给出标题 / 出处 + 年份的条目；文档与法规一类给的是**可点名的条目 + 判定入口**（进官方渠道即可核验，具体版本与生效日期一律以官方发布为准）。**宁少勿假**。

**论文（可核验）**

- Sweeney, "k-anonymity: A Model for Protecting Privacy", 2002——准标识符组合可以唯一指向个人，是「字段级脱敏不足以支撑外发」这一结论的形式化依据。
- Dwork, "Differential Privacy", ICALP 2006（其噪声标定版本见 TCC 2006 的 *Calibrating Noise to Sensitivity in Private Data Analysis*）——把隐私保证写成可陈述的参数 ε，是「没有参数就不叫隐私保证」这条约定的理论来源。
- NIST, *De-Identification of Personal Information*（NISTIR 8053），NIST，2015——去标识化实务指南。
- Shokri et al., "Membership Inference Attacks Against Machine Learning Models", IEEE S&P 2017——模型本身是泄漏面：成员推断攻击说明「不在输出里出现」不等于「没有被记住」。
- Carlini et al., "Extracting Training Data from Large Language Models", USENIX Security 2021——**大模型可以从训练数据中逐字复现内容**；这是 §5.2.2 表格里「输入被模型记住并复述——这是模型行为问题，不是隔离问题」那一条的依据。
- **原 §5.3 所列的三条学术条目本节无法核验其标题与作者**：**2024 S&P（Oakland）的机密 LLM 推理安全分析**、**2024 USENIX Security 的差分隐私用于 LLM 训练**、**2025 NDSS 的 AI Agent 数据安全威胁模型**——原文给的是会议名 + 主题名，不是可检索的标题与作者，因此**不作证据**。处理办法：**保留它们所指的三个方向，并逐条给出落点**——① 「机密 LLM 推理的安全分析」→ §5.1 表第 5 行与 §5.2.2 的「由此付出的」第一条（威胁模型从「服务方违规」换成「厂商固件与微架构漏洞、密钥管理」）；② 「差分隐私用于 LLM 训练」→ §5.1 表第 15 行「隐私计算」，归 [§ 8 隐私计算](../08-privacy-computing/08-privacy-computing-section-5-ai.md) 评估（差分隐私的形式化与 DP-SGD 的论文入口在 §8 的 §5.2.2 与 §5.4，本节不重复定级）；③ 「AI Agent 数据安全威胁模型」→ §5.1 表第 1–4 行与 §5.2.1（Agent 的工具调用是不经网关的新出口）。**三条方向都有落点，它们的时点没有。**

**官方文档 / 法规（判定入口）**

- **欧盟《人工智能法案》（Regulation (EU) 2024/1689）**（【公开】欧盟官方公报，2024 年）——核验「数据与记录保存、风险管理、透明度」这几类义务分别落在哪些条款、分阶段适用的时间点各是什么；**判定方法：以欧盟官方公报与官方发布渠道的文本为准，不要以转述文章为准**。
- **各厂商的机密计算产品文档**——可点名的入口见 [§ 3.2.5](02-data-security-section-3-sec3.md)（Intel SGX / AMD SEV-SNP / Arm CCA / NVIDIA H100 CC / CNCF Confidential Containers / 各云厂商的机密 VM 与远程证明文档，均在那一节逐条给出域名与核验方式，本节不重复列出）。核验三件事：能力是否 GA、远程证明里测量的是什么、是否支持在证明里写到你的密钥。
- **策略引擎与访问控制标准**——Open Policy Agent 的 Policy Language / Rego 文档、OASIS 的 XACML 3.0 标准（§3.2.6 给出判定入口）。核验「策略能不能被单测、能不能追到一条真实被拒的请求日志」。
- **中国的等保与数据安全相关标准**——**本节不给版本号与生效年份**：请以国家标准与主管部门发布的正式文本与目录为准，按标准编号自行检索核验；同理，**美国的 AI 行政令一类文件的编号与现行状态（含是否已被后续行政令撤销或替代）**也请以美国政府官方发布渠道为准，本节不做裁定。
- [§ 4](02-data-security-section-4-sec4.md) §4.3 的工具链表与 [§ 7 审计与合规](../07-audit-and-compliance/07-audit-and-compliance.md)（本书章节而非外部文献，故不标年份）。

**第三方生产案例**

- **本节未能给出**可核验的第三方（非厂商）公开生产案例。公开材料里能核到的是三类：① 厂商产品材料（能力与版本以各家官方文档为准）；② 法规文本（**只证明义务存在，不构成第②条**）；③ 论文（证明机制，不证明落地）。本书 [§6](02-data-security-section-6-sec6.md) 整理的四个案例（某银行 / 阿里 / 字节 / 某云厂）是**建设方自述**，其出处标注为「机构名 + 年份区间」，按判据同样不构成第②条。**这个空白本身是结论**：它正是 §5.1 表里没有任何一行到 L1 的直接原因。
- 原 §5.3 的七条工业条目（Purview + AI Hub、Azure OpenAI 机密推理、Google 机密 VM + Gemini、阿里云 AI 治理产品、蚂蚁隐私计算框架升级、欧盟 AI Act 实施细则、中国等保相关进展）**本节不逐条复述**，理由有二：一是它们的精确时点最容易被写成既成事实；二是它们指向的能力已分别落在 §5.1 表的第 1–3、5、12、15 行与 §5.3 的接口表里——**被合并的是复述，不是条目**。判定入口统一为：各家官方发布说明与法规官方文本。
- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——把出口路径清单（几条不经检查点）、内容检测的漏检率与误报率、向量库删除演练的结果、证明里能读出的字段这四组数算出来并留存口径。这四组数在安全评审里的分量，超过任何厂商案例。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **AI DLP**：让一个非平台团队的人列一遍他能想到的取数路径，逐条标注经过哪个检查点。
2. **审计留痕**：试着从留痕里回答一次「上周谁把客户名单发给了外部模型」——答不出来就是字段没定全。
3. **输出内容检测**：自己造 20 条含敏感信息的输出，数漏了几条、误拦了几条。
4. **输出水印**：把带水印的文本改写、截断、翻译一遍，再看还能不能校验出来。
5. **机密推理**：跑一次远程证明，看能不能读出镜像哈希、启动配置与是否 debug 模式。
6. **分类分级自动化**：抽 50 个字段看模型标的密级与人工标注是否一致，算出误标率。
7. **RAG 隔离**：做一次删除演练，逐处确认原文档、切片、向量、索引、缓存是否都消失。
8. **合规自动化**：抽一条生成出来的合规结论，看它能不能指回一条审计记录。

**怎么用这份清单**：要核「能力存不存在」看官方文档（最快）；要核「保证成不成立」看论文与标准；要核「在我这里该不该做」看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。

### 5.5 被过度宣传的部分

**「内容侧的检测与校验做到位，出口就管住了」**——被这么说的是两件事：「AI DLP 成为企业标配，数据出口就管住了」与「LLM 输出水印能证明内容合规」。**实际是**：DLP 的判定输入是**内容**，它有漏检也有误报；而出口的真正可控点是**网络与凭据**——§3.2.3 的失效点说得很清楚，检查点的覆盖面不取决于产品能力，而取决于「所有路径都被强制经过它」这个事实。水印同理：它证明的是「这段文本来自哪个模型」，不是「这段文本该不该被输出」，而且可被改写破坏、有模态与长度限制。**为什么会这样**：能买、能演示、能写进产品材料的是**判定环节本身**（检测规则、水印算法），而决定管控是否成立的另外两件事——把出口路径收干净、把默认行为写死——都是组织与流程工作，没有产品能替你做完；水印还多一层命名上的混淆，它与**数据水印**（把归属信息埋入外发数据、用于事后追溯，是既有能力，见 [§6](02-data-security-section-6-sec6.md)）共用一个词，前者不可靠却被当作后者使用。于是最常见的结局是检测装了一堆、绕过的路径一条没少。**它什么时候才会成真**：当「没有经过检查点的取数路径」这份清单为空且有责任人、且水印校验有稳定契约并被下游真的配合校验时。**判定方法**：让一个非平台团队的人列一遍他能想到的取数路径，逐条对照是否经过检查点；再把带水印的文本改写、截断、翻译一遍，看还能不能校验出来。

**「用了机密计算就过了合规」**——实际是：TEE 把信任从运营方转移到硬件厂商与固件，**信任没有消失只是换了对象**；而且它只覆盖「使用中」这一段——训练语料的脱敏、留存期限、目的限定、删除权，它一条都不管。**为什么会这样**：隔离回答的是「谁能看到明文」，合规要回答的是「数据是什么、为什么留、留多久、怎么删」。**它什么时候才会成真**：远程证明成为可被第三方独立复核的审计物，且监管口径明确承认它。**判定方法**：把证明拿给合规同事，让他试着只凭它回答「这批数据留存多久、怎么删」。

**「向量库有多租户能力，RAG 数据就隔离了」**——实际是：多租户解决的是**索引之间**的隔离，不解决同一索引内不同密级内容的过滤，也不解决「检索返回的内容进了外部模型上下文就已经出域」。**为什么会这样**：多租户隔离有产品功能条目可买、也能在演示里跑给别人看；密级过滤要靠你自己把策略接进召回路径，没有产品能替你做完。原清单其实把两层分开写了（「向量库层：多租户隔离 + 加密 + 访问控制」与「检索层：RBAC / ABAC 过滤 + 敏感字段掩码」），但能被写进产品材料的只有前一层——于是「隔离」被读成风险已被覆盖，而后一层（真正的泄密口）反而没有预算。**它什么时候才会成真**：密级过滤放在召回前、出口按次审计、删除演练能逐处对齐。**判定方法**：做一次删除演练，逐处确认原文档、切片、向量、索引、缓存是否都消失。

这三条，连同 §5.1 表里判 L3 的另外几行（分类分级结果自动驱动权限变更、Embedding 残留与向量反演、GraphRAG 数据安全，以及第 12 行里判 L3 的「平台化」半条、本节不评估的隐私计算那一行），共性是：**它们都把「某个技术环节成立」当成了「整条管控成立」**——DLP 成立的是内容识别，TEE 成立的是隔离，多租户成立的是边界，水印成立的是文本来源；而数据安全的判据始终只有一条：**你能不能列出全部出口，并说清每一处由谁负责拒绝。**

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| AI 数据安全的落点会从「内容识别」转到「路径收口」（谁能调哪个模型、走哪个网关、留什么日志） | 产品与方案材料把「出口路径清单 / 统一 egress」列为主功能，而不是把检测率列为主卖点 | 主流方案的验收指标仍是检出率与准确率，且没有任何产品把路径收口作为独立功能 |
| 机密推理会先在「受监管行业 + 单一模型 + 单租户」落地，公共多租户服务不是主战场 | 公开案例都带「专用实例 / 自有密钥 / 单租户」限定，证明与审计流程被写进采购条件 | 公共多租户服务把机密推理作为默认形态，且价格无溢价、不要求专用实例 |
| RAG 的安全控制会先做成「密级过滤 + 出口审计」，密文检索与向量加密仍停留在研究 | 检索服务把「召回前过滤」「查询预算」「逐次留痕」做成正式功能条目 | 密文 ANN 检索出现可核验的生产部署，含召回率与硬件条件 |
| 分类分级自动化会停在「辅助 + 人工确认」，不会自动驱动权限变更 | 产品把「建议」与「生效」分成两步，且生效动作需要人工审批 | 出现自动打标直接改权限并公开宣称默认开启的产品 |

写这四条时的共同约定：**信号必须是外部可观察的**（正式功能条目、发布说明、带口径的公开案例），而不是「我觉得会」。**被检验得最快的是第四条**——产品里「建议」与「生效」是不是两步，一个版本的发布说明就能看到。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 想上 AI DLP | 先列全取数路径清单并挂责任人，再上检测 | 观察漏检率与误报率是否被你自己量出来 | 不要在取数路径还收不住时先买检测；不要用 DLP 替代凭据收口 |
| 数据要交给外部模型 | 先做合同与访问审计；确需隔离再评估机密推理 | 观察远程证明能覆盖到哪一层、开销比是多少 | 不要把 TEE 当合规结论；不要在无专用实例时宣称机密 |
| 要建 RAG 知识库 | 密级过滤放在召回前，策略与源系统同源；把向量库纳入同一套密级 | 观察同一条内容被拼凑出来的次数 | 不要在过滤粒度都没做时先上密文检索；不要另建一套权限 |
| 要上分类分级自动化 | 只做辅助 + 人工确认，把误标率当验收指标 | 观察产品是否把「建议」与「生效」分成两步 | 不要自动驱动权限变更；不要用模型的判定替代字段级打标 |
| 训练语料要入库 | 脱敏与授权记录在入库那一刻完成 | 观察语料库的删除演练能否逐处对齐 | 不要先入库再补脱敏——建成之后既没有可行性也没有证据链 |
| 要留 LLM 交互审计 | 先定留痕字段（谁 / 何时 / 哪个模型 / 带了什么 / 用途） | 观察监管与内审要求的字段是否变化 | 不要把 prompt 与输出全量留存而不按密级管理——那是新的敏感数据资产 |
| 要做合规自动化 | 先把审计与留痕做全，再谈自动生成 | 观察生成物的每条结论能否指回一条记录 | 不要用生成的报告替代留痕；不要在义务清单还没登记时先上平台 |
| 有人提议 GraphRAG / 向量加密 | 先问它要防的是「索引越界」还是「片段被拼出来」 | 观察有没有带口径的生产部署与性能数据 | 不要为尚未定义清楚的风险改图模型或索引结构 |
| 预算有限，只能做一件事 | 抽一次出口路径盘点 + 一次向量库删除演练 | 观察两次盘点之间缺口是否收窄 | 不要一上来先补 AI 能力——缺口在哪都还不知道 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改权限模型、扩采集面、引入新的在线检查点），**而收益依赖一个尚未成立的假设**（检测够准 / 证明能覆盖全部层 / 多租户等于隔离）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的机制只有**一条**——**保护对象的粒度与出口的形态变了**：敏感物的单位从「数据集」变成「一次对话 / 一次工具调用 / 一次检索返回」。四道防线（分类分级、访问控制、脱敏加密、网关防护）的前提都是「访问可授权」，而按次发生的出口让「授权」失去着力点，于是每道防线都要额外长出「预算 + 审计」这一层。它**没有**改变的是技术体系本身：加密、脱敏、分类分级、最小权限一条都不作废（主文件 §1.1 的四道防线仍是主干），**AI 也没有产生新的信任锚**——能证明「看不到明文」的仍然只有密码学、硬件与合同。
>
> 判断本主题下任何新提法的快捷方式：**它是在管出口，还是在管对象？** 管出口的（DLP、出口审计、检索层过滤）要立刻回答「不可判定时默认拒绝还是放行」；管对象的（分类分级、加密、脱敏）要立刻回答「它在新出口上还生效吗」。第二条判断同样快：**这条控制事后能不能补？** 不能补的只有两处——召回前的密级过滤与入库前的脱敏。
>
> 如果只能带走一句话：**先把出口列全、把默认行为写死、把留痕字段定下来，再谈用不用 AI 去加固**——这三件事做完，本节表里所有 L2 都变得可评估；这三件事没做完，L2 与 L3 的差别只体现在产品演示里。
>
