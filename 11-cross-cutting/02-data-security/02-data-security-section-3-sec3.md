## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

场景表把安全讲成「按场景挑一个模式」。但同一个「云原生 / 微服务」，落在三个团队手里会得到三套不同答案：一个只上了 mTLS，一个上了策略引擎，一个把敏感字段搬进了 TEE。差异不在场景，在**检查点被放在了哪一层**。

这个主题的全部机制可以压成两句话。第一句：**安全的强度 = 检查点的位置 × 检查点不可绕过的程度**。而检查点能不能看见明文，直接锁死了你只能选哪一类机制——落盘加密（TDE、磁盘加密）只能防「拿到介质」，传输加密（TLS/mTLS）只能防「链路上被截」，一旦明文进了某个进程，剩下的唯一约束手段是「控制谁能让这个进程干活」。所以「加密了就安全」这句直觉，在数据被有权者正常读出并转手的那一刻就已经失效。

第二句：**每加一个检查点，就把这个检查点自己的可用性乘进了业务的关键路径**。n 个串联检查点的可用性上界是各点可用性之积：两个各自 99.9% 的串联组件给出 99.8%【推算，推导链：0.999 × 0.999 = 0.998001，即 99.8001%】。这解释了为什么「多加一层总更安全」在本主题里是不成立的——尤其当这一层被放进每次请求的路径上时（见 3.2.2 的失效点）。

由这两句话可推出本节的组织方式：**模式选择的实质是「把那个不得不存在的检查点放在哪一层」**。放得越靠近数据与身份（网关、策略引擎、TEE），覆盖越广、绕过越难，代价是它离业务越远、部署越重、可用性风险越集中；放得越靠近使用侧，越透明，代价是覆盖面等于「所有路径都被强制经过它」这件组织事实，而不是产品能力。

还有一条约束写在技术之外，却决定了这个主题的落地顺序：**密级与用途的定义权不在平台团队手里**。同一份数据算「一般」还是「个人敏感信息」，由业务与法务定义；平台只负责让这个定义可执行。所以安全体系的正确起手式不是采购某种网关或 TEE，而是先让业务把「密级」与「用途」这两个词写下来——写不下来的组织，后面所有检查点都会退化成「按最高级一刀切」，而一刀切在业务侧的结果通常是绕过。

因此本节的使用顺序是：先看 3.1 的约束表确定「检查点必须放在哪一层」，再看 3.2 里对应模式的结构、代价与失效点，最后才到 3.3 的决策表选型。反过来（先选产品再找理由）的团队，通常会得到一份写满产品名的安全架构，而它回答不了 3.5 里两个最朴素的问题：现在还谁有权读这张表，数据是从哪条路出去的。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据处于哪个环节（静态 / 传输 / 使用中） | 检查点能否看到明文，从而决定可选的机制类别（加密 / 网关 / TEE） | 「加密了就安全」——TDE 与 TLS 都不约束「有权访问的人拿它做什么」 |
| 身份的可验证性（有无可信身份源、能否持续验证） | 零信任是否可实施，以及权限撤销的时延 | 「内网就是可信的」——边界消失后，网络位置不再携带任何身份信息 |
| 使用方式的确定性（同一份数据被谁、以什么方式使用） | 策略能否写死为角色/属性，脱敏能否提前做 | 「先开放、以后再收紧」——策略粒度由使用方式的确定性决定，开放后无法事后补 |
| 数据形态（能否令牌化、是否被用作连接键或聚合维度） | 脱敏方法的选择，以及脱敏后这份数据还能不能参与计算 | 「脱敏是格式问题」——脱敏会改变取值分布，作连接键或聚合维度时结论会错 |
| 合规与举证要求（能否回答「谁在何时看了什么」） | 审计粒度与保留期，以及审计是否进入关键路径 | 「日志留 30 天够了」——保留期要覆盖「发现泄露所需时间」，不是「排查所需时间」 |
| 团队与运维能力 | 检查点的数量、策略引擎以何种方式被采用 | 「多一层总更安全」——每一层都在关键路径上，可用性要相乘 |

### 3.2 模式逐个拆解（核心节）

以下 6 个模式覆盖既有的全部 5 个模式（纵深防御、零信任、数据安全网关、脱敏即服务、机密计算），并补上第 6 个 —— **策略即代码 / 集中式策略引擎**。它不是新发明，而是前 5 个模式共同依赖的那一环：「策略从哪里来、谁对它负责」（主文件 §2.3 的「访问控制方法」列出 PBAC 一项，XACML 则出现在 §2.2 的 ABAC 形式化里，两者不在同一分节；§7.5 的决策树也把策略引擎作为首选项）。

六者不是并列的产品选项，而是「检查点位置」这条轴上的六个刻度：3.2.1 把检查点摊成多层，3.2.2 把它绑到每一次请求，3.2.3 把它放在数据源前面，3.2.4 把它做成可复用的规则与令牌，3.2.5 把它放进硬件，3.2.6 把它抽成可测试的策略函数。每个模式请先读「被什么约束逼出来」，再读失效点——**失效点决定它在你这里能不能用**。

#### 3.2.1 纵深防御（Defense in Depth）

- **被什么约束逼出来**：任何单一层都有被绕过的可能，且**不同层的失效原因通常互不相关**（配置错误、代码漏洞、凭据泄露、内部人滥用）；约束是「必须假设每一层都会失效」。
- **结构**：

```text
                        请求
  ① 边界     WAF / API 网关        拦已知攻击模式、限流
  ② 身份     IAM / SSO / MFA       回答「你是谁」
  ③ 应用     服务内鉴权 / 租户过滤  回答「这次能不能做」
  ④ 数据     库/表/列授权 + 脱敏    回答「能看到哪些行与列」
  ⑤ 审计     不可改写日志           回答「事后能不能还原」
  ────────────────────────────────────────────────
  串联关系：每层独立失效 → 穿透概率约为各层穿透概率之积
  前提：各层的失效原因互不相关（这一点在 3.1 表的「身份的可验证性」一行上最常被破坏）
  反过来说：只要有两层共用同一个身份源或同一套凭据，
            乘积关系就退化成「取最弱的那一层」
```

- **为什么这样设计有效**：因为各层失效原因不相关时，穿透概率近似为各层穿透概率之积【推算，推导链：单层被独立绕过的概率记为 p，n 层串联后被绕过的概率约 pⁿ；p = 0.2、n = 4 → 0.2⁴ ≈ 0.0016】，所以深度本身带来数量级上的下降；又因为各层关注不同问题（边界看模式、身份看主体、数据看字段），它们不会同时被同一个错误绕过。
- **代价**：策略要在多处保持一致（同一件事在 WAF、服务鉴权、数据库授权里各写一遍，任何一处改动都要同步，否则出现策略漂移）；每层增加延迟；每层都需要有人维护与评审。
- **失效点**：当**各层共用同一个身份源、同一套密钥或同一份策略存储**时，优点（多层独立）会反转成缺点（一次身份或密钥泄露等于同时穿透全部层），因为「深度」的前提正是各层失效原因不相关，而共享组件把这个前提取消了。典型表现是：五层画得很漂亮，实则是一个身份系统 + 四道形同虚设的检查。
- **真实使用**：NIST SP 800-53 把访问控制、审计与问责、加密等要求分置不同控制族并要求重叠覆盖【公开，NIST SP 800-53 Rev.5，2020；控制族划分以当期修订版为准】；等保 2.0 以「一个中心、三重防护」（安全管理中心 + 安全通信网络 / 安全区域边界 / 安全计算环境）表达同类思路【公开，GB/T 22239-2019《信息安全技术网络安全等级保护基本要求》，措辞以标准原文为准】。
- **AI 时代新增的约束**：Agent 取数把「人偶尔读一次」变成「机器批量反复读」，于是「高敏字段访问次数」这类阈值要么全量报警、要么全部沉默。多层防护仍成立，但每一层的阈值必须按**取数主体**（人 / 服务 / Agent）分别标定，不能共用一套。
- **上线前必须验证的一件事**：画一张共享依赖图——把所有防线共用的身份源、密钥、策略存储、日志通道列出来；如果其中某个组件一旦失守会同时影响三层以上，那么你的纵深防御实际只有一层。

#### 3.2.2 零信任（Zero Trust）

- **被什么约束逼出来**：网络位置不再能作为信任依据（云、远程办公、服务间调用、第三方接入），「内网」这个边界在物理上已经不存在；约束是「身份必须成为唯一的访问依据，且每次访问都要重新判断」。
- **结构**：

```text
        控制平面                        数据平面
  ┌──────────────────┐            ┌──────────────────┐
  │ 策略引擎 PE       │◄── 属性 ──│ 策略执行点 PEP    │
  │ 策略管理器 PA     │── 决策 ──►│ （网关/代理/SDK） │
  └──────────────────┘            └──────────────────┘
        ▲                                  ▲
   身份源 / 设备状态 / 资源属性      工作负载身份（SPIFFE ID）
   持续评估（风险分、行为异常）       + 微隔离：服务间默认拒绝
  ────────────────────────────────────────────────
  撤销权限的生效时延 = 单次请求验证间隔（而不是会话存活期）
```

- **为什么这样设计有效**：因为每一次访问都要经过策略决策点，所以权限的**生效与失效都是「下一次请求」级别的**——撤销一个账号的访问权，不必等它的会话过期，也不必等它重新登录；又因为工作负载带着可验证身份（而不是「来自某网段」），微隔离可以默认拒绝，而不是默认放行。它把「信任」从网络拓扑里移到了身份与属性上，而身份与属性是可撤销、可审计的。
- **代价**：每个请求多一次策略决策（或校验一个短期凭证）；身份与策略系统进入关键路径，成为新的单点；微隔离要求全部服务具备可验证的工作负载身份与 mTLS，这是一次跨团队的改造，而不是一次产品采购。
- **失效点**：当**策略系统的可用性低于业务的可用性要求**时，优点（持续验证）反转成缺点（策略系统一抖，全站访问被拒，运维被迫加「降级放行」开关，于是策略在故障期间等于不存在），因为零信任把一个平时不参与请求路径的组件放进了每次请求的关键路径上。判断标准很直接：问「策略服务不可用时，系统是拒绝访问还是放行」——答「放行」的零信任，只在它不出问题的时候存在。
- **真实使用**：NIST SP 800-207《Zero Trust Architecture》给出 PE/PA/PEP 与控制平面 / 数据平面的参考架构【公开，NIST SP 800-207，2020】；Google 自 2014 年起公开描述 BeyondCorp —— 不依赖内网边界的访问模型【公开，Google BeyondCorp 系列论文（;login: 2014 起），细节以原文为准】；工作负载身份的公开规范与实现是 SPIFFE/SPIRE【公开】（来源：SPIFFE 规范与其实现 SPIRE 的官方仓库，域名 spiffe.io 与 github.com/spiffe；规范与实现随版本演进、无固定出版年份，项目状态以当期页面为准，可按 "SPIFFE ID" / "SPIRE" 自行检索核验）；Istio 以 SPIFFE 身份为服务间认证的基础【公开】（来源：Istio 官方文档 Security 一节的 Authentication Policy / PeerAuthentication 条目，域名 istio.io；随版本更新、无固定出版年份，可按 "Istio authentication policy" 自行检索核验）；面向用户侧接入的零信任产品（ZTNA）有 Okta、Cloudflare Access、Zscaler 等，其公开产品文档描述的正是「按身份与设备状态放行，而不是按网段放行」【公开】（来源：三家厂商各自的官方产品文档条目，域名 okta.com / cloudflare.com / zscaler.com；均为随版本更新的在线文档、无固定出版年份，可按 "Cloudflare Access" / "Zscaler Zero Trust Exchange" 自行检索核验）。
- **AI 时代新增的约束**：非人身份（服务、任务、Agent、模型）的数量超过人之后，身份治理的主要工作量从「给人发权限」变成「给机器发可过期、可轮换、范围最小的凭据」；机器身份的泄露不会自带「行为反常」这个信号。
- **上线前必须验证的一件事**：在预发环境里让策略决策服务返回超时，观察业务请求是被拒绝还是被放行；把这个观察结果写成明文规定并由业务签署，而不是留作运维的经验。

#### 3.2.3 数据安全网关（Data Security Gateway）

- **被什么约束逼出来**：使用方已经用 JDBC/ODBC/SQL 直连数据源，不可能要求所有使用方改代码；而数据源自带的权限模型太粗（多是库/表级，表达不了「按角色脱敏」与「按租户过滤行」）；约束是「检查点必须放在数据源前面，且对使用方透明」。
- **结构**：

```sql
-- 网关对 SQL 的透明改写（使用方提交的是左，实际执行的是右）
-- 使用方:  SELECT user_phone FROM prod.orders WHERE city='HZ';
-- 改写后:
SELECT CONCAT('***', SUBSTR(user_phone, 8, 4)) AS user_phone   -- 列掩码
FROM   prod.orders
WHERE  city = 'HZ'
  AND  tenant_id = 'T-1024'                                    -- 强制行过滤
  AND  region IN (SELECT region FROM acl_user_region            -- 行级条件
                  WHERE principal = 'alice@corp');
-- 同一条链路上并存四件事：行过滤 / 列掩码 / 限流 / 审计留痕
```

- **为什么这样设计有效**：因为网关看到的是 SQL 文本与结果集，所以它能把「行级过滤、列级脱敏、流量控制、审计留痕」四件事做成对使用方透明的改写——**使用方拿到的仍然「是一张表」，但内容是经过策略裁剪的**。这让安全策略的上线不再依赖业务改代码，也就绕开了「安全改动排不进业务需求池」这个组织瓶颈。
- **代价**：所有 SQL 都必须能被网关解析与改写（存储过程、UDF、动态拼接 SQL、批量导入是天然盲区）；网关在关键路径上，吞吐与延迟成为新的容量约束，需要按峰值 QPS 单独做容量规划；改写后若结果与直连不一致，使用方会想办法绕开网关。
- **失效点**：当**存在绕过网关的直连路径**（备份工具、报表引擎、运维跳板机、数据同步链路、BI 本地抽取）时，优点（统一策略入口）反转成缺点（策略只覆盖了一部分路径，却给出「已统一管控」的错觉），因为网关的覆盖面不取决于产品能力，而取决于「所有路径都被强制经过它」这件网络与凭据管理上的事实。修法不是在网关里加功能，而是把直连凭据收掉、把网络可达性掐断。
- **真实使用**：Apache Ranger 提供行过滤（row filter）与列掩码（data masking）这类策略类型【公开】（来源：Apache Ranger 官方文档的授权策略类型条目——Row Level Filter 与 Data Masking，域名 ranger.apache.org；该文档随版本更新、无固定出版年份，特性以官方文档当前版本为准，可按 "Apache Ranger row level filter" / "Apache Ranger data masking" 自行检索核验）；Oracle Data Redaction 提供查询期脱敏【公开】（来源：Oracle Database 官方文档 Advanced Security Guide 的 Data Redaction 一章，域名 docs.oracle.com；随数据库版本更新、无固定出版年份，可按 "Oracle Data Redaction" 自行检索核验）；阿里云 DAS（数据库自治服务）提供数据库审计与安全管控能力【公开】（来源：阿里云 DAS 产品文档，域名 help.aliyun.com；随产品版本更新、无固定出版年份，可按 "阿里云 DAS 数据库自治服务" 自行检索核验）；字节跳动的 DataGPT 安全网关被本目录 [§ 4 工程实现](02-data-security-section-4-sec4.md) 的实现清单列为自研网关示例（可逐行核对）。可自行核验的判据：**能不能列出「没有经过网关的取数路径」**——列不出来的，就没有统一入口。
- **AI 时代新增的约束**：自然语言取数（Text2SQL）让 SQL 由模型生成，网关仍是最后一道可控点，但模型会生成网关解析不了的复杂 SQL。默认行为必须写成「不可解析即拒绝」，否则盲区会随模型能力一起扩大。
- **上线前必须验证的一件事**：以「非平台团队」的视角列一份取数路径清单（BI 直连、离线同步、导出脚本、运维跳板机、第三方接口、AI 取数接口），逐条确认是否经过网关；这份清单要有责任人，因为组织一变动它就会失效。

#### 3.2.4 数据脱敏即服务（Masking-as-a-Service）

- **被什么约束逼出来**：同一份敏感数据要在多种用途下被使用（生产查询、测试库、BI 看板、外发分析、AI 训练语料），每种用途需要的保真度不同；而「每个环境各写一套脱敏脚本」必然导致口径漂移与漏点；约束是「脱敏规则只能有一份，并且要与密级绑定」。
- **结构**：

```sql
-- ① 规则只有一份：密级 × 用途 → 脱敏方法（方法取值来自主文件 §2.3 的 8 种：替换/掩码/哈希/加密/泛化/扰动/合成/令牌化）
CREATE TABLE mask_rule (
  level          TEXT NOT NULL,      -- 公开/内部/一般/重要/个人一般信息/个人敏感信息（主文件 §2.1）
  purpose        TEXT NOT NULL,      -- analytics / testing / external / training
  column_pattern TEXT NOT NULL,      -- 如 ^1[3-9]\d{9}$
  method         TEXT NOT NULL,      -- replace/mask/hash/encrypt/generalize/perturb/synthesize/tokenize
  reversible     BOOLEAN NOT NULL,   -- 是否可逆（决定要不要令牌库）
  PRIMARY KEY (level, purpose, column_pattern)
);

-- ② 可逆方法必须配一个独立的、被隔离保护的映射库
CREATE TABLE token_vault (
  token      TEXT PRIMARY KEY,       -- 对外流通的标识
  ciphertext BYTEA NOT NULL,         -- 明文只在解密后出现在内存中
  kek_id     TEXT NOT NULL           -- KMS 里的主密钥版本（支持轮转）
);
-- 关键的隔离要求：token_vault 的读取权限与生产查询权限分离，且访问全量审计
```

- **为什么这样设计有效**：因为规则被抽成一张「密级 × 用途 → 方法」的表，所以**新增一个使用环境只是加一行规则，而不是加一套脚本**；又因为令牌化把明文集中到唯一的映射库里，攻击面从「N 个系统里各存一份明文」收敛成「1 个系统里存全部明文」——这既是它的价值，也是它必须被独立加固的原因。哈希与掩码则相反：它们不可逆，因此不需要映射库，代价是永久失去可关联性。
- **三种投递形态共用一张规则表**：**静态脱敏**（批量生成测试库，改的是存量，做一次用很久）、**动态脱敏**（查询期实时改写，改的是每一次查询，规则只在查询路径上生效）、**API 脱敏**（返回值脱敏，面向前端与第三方调用，改的是输出）。三者唯一的区别是「改写发生在什么时候」，因此它们必须读同一份规则，否则又回到口径漂移。
- **代价**：令牌库成为全组织最高价值的单体资产（要独立加密、独立权限、独立审计、独立备份，且密钥用 KMS/HSM 管理、支持轮转）；动态脱敏在查询路径上增加改写开销；脱敏后的数据要重新验证可用性（分布是否仍能支撑模型训练与统计）。
- **失效点**：当**脱敏字段被用作连接键或聚合维度**时，优点（保护）反转成缺点（结论错误），因为掩码与哈希破坏了取值分布与唯一性——对掩码后的手机号做用户去重会把大量用户合并，对哈希值做求和得到的数是完全无意义的。第二个失效面是「字段级脱敏被当成外发的充分条件」：单个字段都不敏感，但准标识符的组合会唯一指向个人（如邮编 + 生日 + 性别），这正是 k-匿名要处理的问题。
- **真实使用**：k-匿名由 Sweeney 形式化提出【公开，Sweeney, «k-anonymity: a model for protecting privacy», 2002】；NIST 公布过去标识化实务指南【公开，NISTIR 8053《De-Identification of Personal Information》，NIST，2015；可按编号自行检索核验】；差分隐私以隐私预算 ε 形式化【公开，Dwork, «Differential Privacy», 2006】；Apple 公开说明其在系统中使用了本地差分隐私【公开，Apple 平台安全白皮书相关章节，2016 年起，机制以当期白皮书为准】；联邦学习由 Google 研究者提出【公开，McMahan 等, «Communication-Efficient Learning of Deep Networks from Decentralized Data», 2016】；支付卡行业把令牌化作为缩小持卡数据范围的手段【公开】（来源：PCI SSC 的令牌化指引文档《PCI DSS Tokenization Guidelines》（2011）及其后发布的《Tokenization Product Security Guidelines》，域名 pcisecuritystandards.org；版本以 PCI SSC 官网当期发布为准，可按 "PCI SSC tokenization guidelines" 自行检索核验）；Immuta、Privacera、Collibra 等被本章 §7.2 列为脱敏与策略方向的选项（来源：本目录 [§ 7 与其他方法对比](02-data-security-section-7-sec7.md) 的 §7.2 对比表，可逐行核对）；各云厂商也提供数据脱敏与数据安全中心一类服务，如阿里云数据安全中心 DSC、华为云数据安全中心、AWS Macie、Google Cloud Sensitive Data Protection【公开】（来源：四者的官方产品文档，域名分别为 help.aliyun.com / huaweicloud.com / docs.aws.amazon.com / cloud.google.com；均为随版本更新的在线文档、无固定出版年份，可按 "<产品名> documentation" 与 "data security / sensitive data protection" 自行检索核验）。
- **AI 时代新增的约束**：训练语料是「一次授权、长期留存」的用途，脱敏必须在语料入库那一刻完成——语料库建成之后，事后再删既没有可行性，也没有可举证的证据链。
- **上线前必须验证的一件事**：用脱敏后的数据跑一遍**真实的**分析作业与模型训练，对比脱敏前的结论；如果结果不可比，是脱敏方法选错了（保真度不足），而不是作业写错了。

#### 3.2.5 机密计算（Confidential Computing）

- **被什么约束逼出来**：数据在「使用中」必然是明文，而所有软件层策略都默认操作系统与虚拟机管理程序可信；当计算发生在别人的机器上，或当攻击者已经拿到宿主机权限时，约束变成「连云厂商与宿主机管理员也不能看见明文」——这条约束是软件层无法满足的。
- **结构**：

```text
  ① 调用方发起计算请求（数据与代码均需在可信边界内解密）
  ② TEE 生成远程证明（attestation）：度量值 = 哪段代码 + 哪个版本 + 是否调试模式
  ③ 调用方校验度量值 → 通过后才把数据密钥释放给 TEE（密钥由 KMS 下发）
  ④ TEE 内解密 → 计算 → 加密输出；宿主机只能看到密文与访问模式
  ────────────────────────────────────────────────
  信任锚点从「账号/权限」移到「硬件 + 代码度量」
  隔离边界：Intel SGX（进程级 enclave）/ AMD SEV-SNP（虚拟机级）
            / ARM CCA（架构级）/ GPU TEE（如 NVIDIA H100 的 CC 模式）
```

- **为什么这样设计有效**：因为证明把「我在哪台机器上运行的是哪段代码」变成一个**可验证的断言**，所以密钥的释放条件可以写成「只给通过验证的那段代码」，而不是「只给权限正确的那个账号」——信任的对象从「人」变成了「代码与硬件」。这在「数据要交给别人算」的场景里是唯一能覆盖使用中状态的机制。
- **代价**：enclave 内可用内存受限、系统调用要穿越不可信边界（性能损失）；调试与可观测性变差（不能随意 attach profiler，线上排障方式要重做）；生态适配成本高（中间件、JVM、数据库都要适配）；还有长期的密钥管理与证明策略维护成本。
- **失效点**：当**侧信道攻击可行**（缓存时序、推测执行一类）时，优点（硬件隔离）反转成缺点（被保护的数据仍可被推断），因为 TEE 保证的是「读不到别人的内存」，而不是「从访存模式里推不出内容」。第二个失效面在配置上：如果证明策略只校验「这是 SGX/SEV」而不校验「是哪段代码、哪个版本、是否禁用调试」，那么等于把密钥发给任意代码——**证明的价值全部落在策略写了什么条件上**。
- **真实使用**：Intel SGX 有公开的开发者文档与规格说明【公开】（来源：Intel 官方开发者站点的 Software Guard Extensions / Intel SGX SDK 文档条目，域名 intel.com；随代际与 SDK 版本更新、无固定出版年份，代际能力以当期文档为准，可按 "Intel SGX SDK developer reference" 自行检索核验）；AMD SEV-SNP 有公开架构文档【公开】（来源：AMD 官方的 SEV-SNP 架构说明文档，域名 amd.com；随处理器代际更新、无固定出版年份，可按 "AMD SEV-SNP white paper" 自行检索核验）；ARM CCA 有公开架构规范【公开】（来源：Arm 官方的 Confidential Compute Architecture 规范条目，域名 developer.arm.com；规范仍在版本迭代中、无固定出版年份，可按 "Arm CCA specification" 自行检索核验）；NVIDIA H100 提供 Confidential Computing 模式【公开】（来源：NVIDIA 官方的 H100 Tensor Core GPU 架构文档与机密计算说明，域名 nvidia.com；随产品代际更新、无固定出版年份，可按 "NVIDIA H100 confidential computing" 自行检索核验）；容器场景有 CNCF 的 Confidential Containers 项目【公开】（来源：CNCF 的 Confidential Containers（CoCo）项目页与其 GitHub 仓库，域名 cncf.io / github.com/confidential-containers；项目持续演进、无固定出版年份，可按 "Confidential Containers CNCF" 自行检索核验）；Azure、Google Cloud、阿里云均有公开的机密计算产品【公开】（来源：Azure Confidential Computing 文档（learn.microsoft.com）、Google Cloud Confidential Computing 文档（cloud.google.com）、阿里云加密计算实例与机密计算相关产品文档（help.aliyun.com）；均为随版本更新的在线文档、无固定出版年份，可按 "<云厂商> confidential computing" 自行检索核验）；蚂蚁摩斯这类隐私计算平台把 TEE 作为多种技术后端之一【公开】（来源：该平台的公开产品介绍与官方技术分享，属随产品迭代更新的材料、无固定出版年份，可按 "蚂蚁摩斯隐私计算产品介绍" 与 "隐私计算可信执行环境 TEE" 自行检索核验；本目录 [§ 5 前沿演进](02-data-security-section-5-ai.md) 亦把蚂蚁摩斯列入机密计算的代表产品）。
- **AI 时代新增的约束**：模型权重与提示词成为与数据同等重要的资产，它们同样需要在 TEE 内被保护（权重被拖走就是资产损失）；同时推理的批处理会在同一 enclave 内跨请求共享内存，隔离边界要按「同一批次里能不能混入他人数据」重新确认。
- **上线前必须验证的一件事**：故意用一段**未经认证的代码**去申请密钥，确认它被拒绝。证明策略若只校验「这是 SGX/SEV」而不校验「哪段代码、哪个版本、是否禁用调试」，机密计算就等于把密钥发给任意程序。

#### 3.2.6 策略即代码 / 集中式策略引擎（PBAC）

- **被什么约束逼出来**：同一件事（「分析师可以看本部门、脱敏后的手机号」）要在多个引擎上生效（Hive、Spark、Presto、对象存储、自研服务、AI 取数接口），而每个引擎自带的 ACL 表达能力不同、改一处要改 N 处；约束是「策略必须是可版本化、可测试、可被多个执行点复用的一等产物」。
- **结构**：

```text
 策略仓库（版本控制 + Code Review + 单测）
       │  下发 / 拉取
       ▼
 决策服务 PDP（无状态，可水平扩展）
       ▲   策略输入（属性）
       │
 ┌─────┴─────────────────────────────────────────────┐
 │ 执行点 PEP：Hive 插件 / Spark 插件 / 网关 / API 中间件 │
 │ 决策输出：allow | deny | mask(column, method)       │
 └───────────────────────────────────────────────────┘
 决策输入的形状（属性基，对应主文件 §2.2 的 ABAC 形式化）：
   { "principal": {"dept":"risk","roles":["analyst"]},
     "resource":  {"level":"个人敏感信息","owner":"privacy-team"},
     "action":    "read",
     "env":       {"hour":14,"network":"office","device":"managed"} }
```

- **为什么这样设计有效**：因为决策被抽成「输入属性 → 输出允许/拒绝/脱敏动作」的函数，所以**策略第一次变得可以单元测试**——「风险部的分析师在工作网内读个人敏感信息字段应被脱敏」这条要求可以写成用例，在 CI 里跑；又因为同一条策略在所有执行点被复用，它不会随引擎不同而行为漂移。这解决了纵深防御那条「策略漂移」的代价。
- **代价**：每次决策一次调用（或用本地缓存 + 失效策略，于是产生「策略生效延迟」）；策略语言与调试方式要学（这个学习成本落在安全团队与平台团队）；策略仓库本身成为关键资产，它的发布要走变更评审而不是热改。
- **失效点**：当**执行点没有强制能力**时（某个引擎只能按库/表授权，表达不了行级条件；某个导出链路根本不经过任何执行点），优点（统一策略）反转成缺点（策略写了但不生效，并且看起来像已生效），因为「策略即代码」只解决表达与分发，不解决执行点的强制力——**一份在测试环境全绿的策略，可以在生产里从未被执行过一次**。
- **真实使用**：Open Policy Agent（OPA）提供通用策略引擎与 Rego 语言【公开】（来源：OPA 官方文档的 Policy Language / Rego 条目，域名 openpolicyagent.org；随版本更新、无固定出版年份，可按 "OPA Rego policy language" 自行检索核验，项目在 CNCF 下的状态以 CNCF 官方项目页为准）；XACML 是 OASIS 发布的访问控制策略标准【公开】（来源：OASIS 标准《eXtensible Access Control Markup Language (XACML) Version 3.0》，域名 docs.oasis-open.org；版本与状态以 OASIS 官网当期发布为准，可按 "OASIS XACML 3.0" 自行检索核验）；Cerbos、Immuta 等也在本章 §7.2 的工具对比表中被列为策略与脱敏方向的选项（来源：本目录 [§ 7 与其他方法对比](02-data-security-section-7-sec7.md) 的 §7.2 对比表与 §7.6 组合示例，可逐行核对；产品能力细节以其官方文档当前版本为准，域名 docs.cerbos.dev / immuta.com）。可自行核验的判据：**从策略仓库里挑一条策略，追它到执行点，再追到一条真实被拒的请求日志**——断在哪一环，哪一环就是当前的安全边界。
- **AI 时代新增的约束**：决策输入多了「用途」这一维（这次取数是回答问题、还是进入训练语料），而用途必须由调用方声明；这个声明本身要能被审计与追责，否则它可以被随手写成「查询」。
- **上线前必须验证的一件事**：在每个执行点上做一次**负向测试**——用测试账号、测试字段去访问「明明该被拒」的资源，确认它真的被拒且留下日志；把「策略未生效」的执行点列成盲区清单并挂上责任人。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 传统企业内部系统：使用方直连库、改造意愿低、审计是主要诉求 | 3.2.1 纵深防御 + 3.2.3 网关 | 零信任要求全部服务具备可验证身份，改造面大于收益 | 能否收掉全部直连凭据 |
| 云原生 / 微服务：服务间调用密集、边界已消失 | 3.2.2 零信任 + 工作负载身份 + 微隔离 | 纵深防御把「网段」当身份，边界消失后它退化成若干互不相干的检查 | 策略系统不可用时是拒绝还是放行 |
| 多团队 / Data Mesh：各域自治、策略必须一致 | 3.2.6 策略即代码 + 3.2.4 脱敏即服务 | 各域自建 ACL 必然漂移，事后无法回答「这条规则在几个引擎上生效」 | 策略能否被单测与 Code Review |
| AI 训练 / RAG：语料要离开自有机房或交给多方计算 | 3.2.5 机密计算 + 3.2.4 令牌化 | 网关与脱敏只覆盖「取数」环节，覆盖不了模型训练与推理进程内部的明文 | 证明策略是否校验了代码版本与调试位 |
| 金融 / 强合规：需举证、需事后还原 | 3.2.3 + 3.2.1 + 3.2.4，叠加审计留痕 | 单靠网关可知「谁查了什么」，但无法回答「数据外发之后去了哪」 | 审计保留期是否覆盖「发现泄露所需时间」 |
| 跨境数据：数据本地化约束 + 境内境外都要用 | 分区部署（数据本地化）+ 令牌化（跨境只传 token） | 机密计算解决的是「谁能看」，解决不了「数据根本不许出境」这条硬约束 | 跨境链路上传的是明文还是令牌 |
| 同一份数据要同时供 BI 与 Agent 取数 | 分类分级 + 3.2.3 网关（面向人）+ 3.2.6 策略引擎（面向机器） | 只上一套面向人的权限体系，Agent 会以服务身份绕过它 | 面向机器的取数接口是否有独立的授权与审计 |

上表「跨境数据」这一行还要单独补一句：**「监管报送」不是架构模式，而是流程要求**——它可以复用 3.2.3 与 3.2.6 产生的审计与策略证据，但没有哪一种部署结构能替代它。

读这张表的正确顺序是从「关键判据」一列倒着读：先量出「取数路径是否唯一」「策略系统不可用时是拒绝还是放行」「脱敏字段是否参与计算」，再去找匹配行。另外提醒一句：**推荐模式一列不是排他的**——同一家公司完全可以对交易库用网关、对算法团队用令牌化沙箱、对云上算力用机密计算，按数据类与路径分级本身就是正确做法；用统一模式覆盖全部数据才是反模式（见 3.5 的「只防外不防内」）。

表中最常被误选的一对是 **3.2.1 纵深防御与 3.2.2 零信任**。两者的画法很像（都是一串检查点），所以团队常把「WAF + SSO + 服务鉴权 + 库授权」当成零信任，也常在完全没有工作负载身份的情况下宣布自己上了零信任。误选的后果是具体的：把纵深防御当零信任的团队，会保留长生命周期的内网凭据与网段放行，**一次凭据泄露即穿透全部层**，而且事后审计只能证明「有人用合法凭据读了」；反过来，在没有策略系统可用性余量的情况下硬上零信任的团队，会在第一次策略服务抖动时被迫打开降级放行开关，此后这个开关再也不会被关掉。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：分类分级（元数据）+ 网关 / 脱敏即服务（执行点）** = 主文件 §2.1 的分类分级 + 3.2.3 / 3.2.4。职责边界：分级回答「这块数据是什么密级」（策略的输入），网关与脱敏服务回答「按密级该怎么处理」（策略的执行）。缺任何一个都会失效——有分级无执行点 = 打了标签没人用（本目录 [§ 6 落地实践](02-data-security-section-6-sec6.md) 记录的阿里案例把这一条写成失败教训「等级只打不管」，转引本仓库 §6 案例，2016–2024）；有执行点无分级 = 策略靠人工维护一张表，数月后即过期【经验，人工维护的策略清单通常在季度量级失效】。运维代价：分级的元数据成为关键资产，它的过期会让策略静默失效；适合任何已经有元数据目录的组织。

**组合 B：零信任（身份）+ 策略引擎（授权）** = 3.2.2 + 3.2.6。职责边界：零信任提供「每次请求都能拿到可验证身份」这一前提，策略引擎提供「拿到身份之后判断什么」。运维代价必须事先算清：两个组件都进了请求路径，**可用性上界相乘**——两个 99.9% 给出 99.8%【推算，推导链：0.999 × 0.999 = 0.998001 ≈ 99.8%】，跨三个 Region 的多活部署也改不了这个乘法。适合服务数量多、身份种类多（人 + 服务 + Agent）的规模。

**组合 C：机密计算（使用中）+ 令牌化（落地态）+ KMS（密钥）** = 3.2.5 + 3.2.4 + 主文件 §2.3 的密钥管理。职责边界：令牌化管「数据静止与流通时长什么样」，KMS 管「密钥谁能拿到」，机密计算管「计算时明文在哪」。三者合起来才覆盖数据的三种状态，缺一个就有明文暴露面。运维代价最高：证明策略、密钥轮转、enclave 内程序的发布流程，三套都要单独维护；适合「数据必须离开自有可控机房」的规模（多云、外部算力、联合建模）。**这类组合的前置条件是数据已经令牌化**——否则 TEE 保护的只是「一份已经没必要外发的明文」。

三条组合之间有一条硬性顺序：**先有规则（组合 A 的分级），再有身份（组合 B），最后才谈硬件级隔离（组合 C）**。从机密计算起步的团队常会发现自己把一份「本来就不该外发」的明文保护得很好——TEE 回答的是「交给别人算时看不看得见」，不回答「该不该交出去」。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 过度授权（研发 / 业务方持有 DBA 权限） | 权限清单里出现「生产库读写 + 无到期时间」的账号 | 任何一次凭据泄露都直接等于数据泄露，其余防线只记录不阻断 | 排障与取数都要权限，走审批太慢，于是默认给大 | 最小权限 + 按需授权（JIT，用完即收）+ 特权操作双人复核 |
| 明文落盘（备份、日志、测试环境） | 扫描备份与日志目录能直接命中原值 | 拖走一份备份即等价于拿走生产库，且不经任何检查点 | 加密影响恢复与查询，被当成「以后再说」的事 | 全链路加密（TDE + 备份加密）+ 日志脱敏 + 测试库脱敏 |
| 统一密码（共用 root / 业务账号） | 多人知道同一个高权密码；密码在多个系统的配置文件里 | 无法归因到人，审计链条从第一跳就断了；轮换一次要改几十处 | 共享账号最省事，且历史系统不支持个人账号 | IAM + SSO + MFA，服务用可轮转凭据而不是静态密码 |
| 权限永不回收（离职、调岗不回收） | 权限清单里存在已离职账号或不存在的项目 | 授权集合只增不减，多年累积后「有权的人」远多于「需要的人」 | 回收没有触发源（HR 系统与权限系统未打通） | 把入转调离做成权限变更的自动触发源，并定期做权限复核 |
| 安全与业务对立（安全被当成阻碍部门） | 业务绕过流程取数；安全需求排期永远最后 | 绕过路径成为事实上的主路径，策略只覆盖合规的那条路 | 安全只提要求、不提供可用工具，业务只能用绕过来完成目标 | 把安全做成自助能力（脱敏 API、沙箱），让合规的路径比违规的更快 |
| 只防外不防内 | 有边界防护与入侵检测，但没有内部人行为基线；威胁模型里没有「已授权主体的异常行为」这一项 | 内部人的少量高敏查询淹没在正常流量里，不触发任何告警；而内部人与第三方滥用是泄露事件的主要成因之一（具体占比随统计口径差异很大，请以 Verizon DBIR 一类年度报告的当期版本为准） | 威胁模型只画了「外部攻击者」，把内部默认成可信 | 内外并重 + UEBA（用户与实体行为分析），对高敏字段的访问单独设阈值 |
| 忽视 AI 工具（员工把内部数据喂给外部 LLM） | 出口流量里出现外部模型 API；RAG 库未继承数据权限 | 数据流出后脱离全部检查点，且留下的是无法撤回的自然语言片段 | AI 工具由个人自行接入，平台侧既不知道也不拦 | AI DLP（输入端拦截 + 输出端内容检测 + 审计）+ 给可用的内部替代品 |

其中五条最危险（「过度授权」与「权限永不回收」机制同源，并作一段），值得单独展开：

**「过度授权」与「权限永不回收」是同一个病。** 它们的合计效果是**授权集合单调递增**：新权限不断被加上，旧权限从不被减掉。典型暴露方式不是一次大事故，而是审计时的两个问题同时答不上来——「现在有多少账号能读这张表」与「其中多少个是还在岗、还需要的」。机制上的原因是一次授权是「加一个元组」，而回收是「判断这个元组是否还需要」，后者需要业务判断，因此永远排在确认性工作之后。修法必须把回收变成**自动触发**（入转调离事件驱动）而不是定期运动。

**「忽视 AI 工具」是唯一一类检查点位置在组织之外的失效。** 数据被贴进外部模型之后，落盘加密、网关、脱敏、审计四道防线全部不适用——它没有经过你的任何路径。它的典型暴露方式是出口流量里出现外部模型域名，而此时已经发生。可自行核验的判据有两个：**出口是否有对外部模型 API 的可见性**，以及**给不给得出一个「公司批准的内部替代品」**——第二问答不上来的团队，拦截只会把行为推向更隐蔽的通道。

**「统一密码」是审计链条上的第一处断点。** 它看起来只是运维便利，机制上的后果却无法用别的手段补：所有记录都指向同一个主体，「谁做的」这个问题永久无解，后续的 UEBA、告警、追溯全部失去投递对象。典型暴露方式是排查一次异常导出时，日志只显示 `app_rw` 这个账号——而它被十几个服务和若干人使用。修法不是换更长的密码，而是把「服务用可轮转的短期凭据、人用个人账号」变成硬性前提。

**「明文落盘」的隐蔽性来自「备份不算数据」。** 团队默认把备份、日志、测试库当成运维产物，而不是受管数据。但机制上它们包含全量原值，且通常权限更松（同一个服务账号可读全部备份）、审计更弱（很少有人审计备份读取）。所以它的修复顺序应该是：先扫描定位（有哪些地方存了原值），再加密与脱敏，最后才谈保留期。

还有一类失效不落在上表任何一行，后果却相同：**检查点存在、日志存在，但没有人看**。它的判据是「最近一次由审计日志主动发现（而不是由业务或外部反馈）的安全问题发生在什么时候」——答不出时间点的组织，审计目前只具备举证能力，尚不具备发现能力，而这两件事靠的是两套不同的东西：前者靠留存的完整性，后者靠有人对异常负责。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 1 个业务 → 多业务共享数据 | 表级分级 + 各业务自觉 | 同一份数据在不同业务里被标成不同密级，共享时无从判断，只能按最高级管控、业务用不了 | 统一分级 + 字段级打标（3.2.4 的规则表以密级为键） | 重新盘一遍字段并逐字段签字；跨业务的密级冲突要有人裁 |
| 单库 → 多引擎异构（数仓 / 湖 / 对象存储 / 消息） | 数据源自带 ACL | 同一件事要在 N 个引擎各写一遍，改一处漏 N 处，出现策略漂移 | 3.2.6 策略即代码 + 各引擎执行点 | 策略语言学习成本；执行点覆盖率要一项项补齐，且必须能列出盲区 |
| 只用自己机房 → 多云 / 外部算力 | 网关 + 脱敏 | 网关只拦得住「取数」，拦不住「把数据交给外部进程计算」 | 3.2.5 机密计算 + 令牌化 + 远程证明 | enclave 内程序要重写与重新发布；证明策略要有人持续维护 |
| 数据只给人用 → 也给模型用 | 面向人的权限体系 | Agent 与 LLM 以「服务身份」成批取数，一条授权等于一次全量导出 | 令牌化 + 面向机器的最小权限 + 取数行为审计 | 取数接口要能表达「允许用于训练」这类用途属性（进入 3.2.6 的决策输入） |
| 合规从「无」→「需举证」 | 事后口头说明 | 监管问「半年前谁看过这批数据」，答不出就是不合规 | 审计粒度到字段 + 保留期覆盖发现延迟 | 存储成本上升；审计链路自身要防篡改（只可追加） |
| 只防外 → 也要防内 | 边界防护为主 | 内部人的高敏访问与正常查询在同一分布里，不触发告警 | UEBA 行为基线 + 高敏字段单列阈值 | 需要先有「什么算正常」的基线期，基线期内的漏报要业务承担 |
| 单机房 → 多地部署 | 机房内互信 | 跨地区调用让「网段即身份」彻底失效，同时审计数据本身也变成跨境数据 | 零信任 + 分区审计 | 地区间的密级定义与法务审批要事先对齐 |
| 有目录 → 无目录（或目录停更） | 分级靠人工台账 | 人工台账通常在季度量级失效【经验】，台账一过期，策略的输入就失效，检查点会按错误的密级执行 | 分级落到元数据目录的字段级标签，并纳入目录的强制登记项 | 打标工作量与字段级 Owner 任命；目录与策略要双向同步 |

一句话总结这一节：**模式不是被「数据量」推动升级的，是被三个约束的变化推动的——检查点能不能看到明文、身份能不能被持续验证、以及这条路是不是唯一的取数路径。** 第三条最容易被忽略，而它恰恰决定网关、策略引擎、脱敏服务这些「统一入口」类模式到底成不成立。

上表里最反直觉的一行是「数据只给人用 → 也给模型用」：它看起来只是多了一个使用方，实际是**授权模型从「按人」变成了「按批」**——一条授予 Agent 的授权，等价于一次可重复执行的全量导出。所以这一跃迁里的正确动作不是收紧 Agent 的权限范围，而是先改掉可取数据的形态（令牌化、聚合层、受控视图），让「批量拉走原始明文」在结构上不成立。

### 3.7 自检清单

- [ ] 能否列出**全部**取数路径，并指出每条路径上有哪些检查点？列不出的路径，就是当前的绕过面。
- [ ] 是否存在位于关键路径上的安全组件？它不可用时系统是拒绝访问还是放行？这个行为是否明确写下来并由业务签署？
- [ ] 策略系统中任一组件不可用时的**可用性上界**是否算过（各串联组件可用性相乘），是否与业务 SLO 相容？
- [ ] 分级是否落到**字段级**？同一张表里的公开字段与敏感字段是否被分别管控（而不是整表按最高级）？
- [ ] 是否存在必须由两人同时在场才能完成的特权操作（高敏导出、密钥操作）？
- [ ] 是否有**单一账号能同时读到明文与删除备份**？有则说明凭据隔离没做。
- [ ] 审计的粒度是否到「谁 / 何时 / 读了哪些字段 / 结果多少行」，且存储只可追加、不可由生产凭据改写？
- [ ] 审计保留期是否长于「最慢一类泄露被发现的延迟」？给出天数与依据。
- [ ] 脱敏字段是否被用作连接键或聚合维度？若是，是否验证过脱敏后的结论仍然正确？
- [ ] 令牌库（若存在）的读取权限是否与生产查询权限**分离**，且所有访问被审计？
- [ ] 制度上是否有一个已批准的 AI 工具与数据出口清单，且出口对外部模型 API 有可见性？
- [ ] 权限回收是否由入转调离事件**自动触发**，而不是靠定期运动？最近一次复核的时间与结论是什么？

这 12 条里，第 1、2、12 条是「决定其余各条是否还有意义」的三条：路径不唯一，检查点就只是装饰；策略不可用时的行为没有定义，一次可用性事故就会自己把策略关掉；回收不自动，授权集合就只会单调增长。其余各条都能在半年内补齐，这三条拖不得。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 使用方直连、改造意愿低、要的是审计 | 纵深防御 + 数据安全网关 | 网关在数据源前看到 SQL 与结果集，脱敏与行过滤可对使用方透明 |
| 边界消失、服务间调用密集、权限要能即时撤销 | 零信任 + 工作负载身份 | 每次访问经策略决策点，撤销时延从「会话存活期」降到「单次请求间隔」 |
| 多引擎异构、策略必须一致且可测 | 策略即代码 | 决策成为纯函数 → 可单测、可评审；同一条策略在所有执行点行为一致 |
| 同数据多用途（生产/测试/外发/训练） | 脱敏即服务（含令牌化） | 规则一份、用途多份；令牌化把明文收敛到唯一映射库，攻击面由 N 收敛到 1 |
| 数据需离开自有可控机房 | 机密计算 + 远程证明 | 信任锚点由「账号」移到「硬件 + 代码度量」，覆盖唯一的明文状态——使用中 |
| 合规要能举证 | 全链路审计（粒度到字段 + 只可追加） | 举证能力靠可调取的记录，不靠架构图；保留期由发现延迟决定 |
| 无法确定取数路径是否唯一 | 先收敛路径（收凭据、掐网络），再选模式 | 统一入口类模式的覆盖面取决于组织事实，不取决于产品能力 |
| 数据要交给模型或外部算力使用 | 令牌化在先进语料/委托计算之前完成 | 语料一旦入库，「事后删」在可行性与举证上都最弱；先改形态再谈隔离 |
| 取数主体从人变成人 + Agent | 授权粒度从「按表」下移到「按用途 + 频次」 | 一条机器授权等价于一次可重复执行的全量导出，权限的表达力必须跟上 |
| 密级定义尚未由业务签署 | 先定密级与用途，任何模式都排在其后 | 检查点按错误的密级执行，比没有检查点更危险（它会给出合规的错觉） |

> 本节小结：本主题下决定模式选择的**唯一那条约束**是——**你能不能让所有取数路径都必须穿过同一个检查点**。穿得过，纵深防御、网关、策略引擎、脱敏服务才能从「展示用」变成「控制手段」；穿不过，再多层防护也只是给合规的那条路加了门，而数据会从没门的路上流走。第二个约束（身份能否被持续验证）决定撤销权限要多久才生效，第三个（明文能不能离开你的硬件）决定要不要动用机密计算——它们都在第一条之下做微调。
>
> 💡 **思考锚点**：数一下你的取数路径上串联了几个检查点——§3.1 给的公式是 n 个 99.9% 的检查点串起来只剩 99.8%，多一层就在关键路径上再乘一次可用性：你最后那个检查点（脱敏 / 审计 / 网关）是放在每次请求路径上，还是旁路？再按 §3.5 问一句——最近一次由审计日志主动发现、而不是由业务反馈的安全问题，发生在什么时候？
