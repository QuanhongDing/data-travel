## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把「配置成本 4 分」「ABAC 支持 5 分」这类格子加起来求总分，得到 21、25、26 这样的数——但这个求和在量纲上不成立：各列量的是不同东西（人力、能力、增速），相加等于暗设「省一天配置时间」与「不支持行级过滤」可以互相折算。真实决策里这两件事不可折算：一个不支持行级过滤的产品，无论多好配置，在你需要「客户级行级隔离」的场景里根本不在候选集内。【经验】

更根本的问题是候选们不在同一层。Ranger 是数据引擎侧的授权服务，OPA 与 Cerbos 是通用策略引擎，AWS IAM / 阿里云 RAM / LDAP / Keycloak 管的是身份与资源级授权，Vault 与 HSM 管的是密钥，Nightfall 与 Microsoft Purview 管的是出口内容，机密计算管的是使用中的明文。把它们的分数求和来排名，等于问「刹车和方向盘哪个更好」。真正该问的是：**我的检查点缺了哪一层，以及这一层的覆盖面由什么决定**。

同一维度在不同规模下权重还会反向。以「配置成本」为例：10 张表时逐字段配策略最省事；1000 张表时逐字段配置的人力按对象数线性增长，此时唯一可行的是把策略从「逐字段」改成「按标签」——成本函数换了形状，排序也就反了（推导见 7.4）。打分表恰恰把这个形状变化抹掉了。

另一种决策树是另一个方向的简化：它的判断节点全部压在「场景」上（是否需要细粒度 ABAC / 是否大数据场景 / 是否云原生），最后一支的「否」通向「传统 IAM（LDAP / Active Directory）」。这条分支的机制含义值得单独点出来——它建议一个既无细粒度需求、又不在大数据场景、也不在云原生的组织，用目录服务来管数据权限。但目录服务在结构上表达不了任何数据对象（见 7.3.3 的粒度表），它只能回答「你是谁、你在哪个组」。于是这条分支的实际效果是：组织以为自己在「用最小代价起步」，实际上是把「谁在哪个组」当成了「谁能读哪张表的哪些行」——这个映射要么由下游应用各自硬编码，要么根本不存在。正确的替代不是在场景上加深判断，而是补一条与场景无关的前置问题：**我有没有权力收掉直连凭据与网络可达性**（见 7.5 的节点①）。

这也是本章把「判据」放在候选清单之前的原因：场景决定的是「优先级排序」，而判据决定的是「谁进候选集」。把两者倒过来，得到的选型结果看起来合理、实际上不可用。

**本章采用的 6 条判据**：

| 判据 | 问的问题（本主题化） | 为什么它决定了选型 |
| --- | --- | --- |
| 能力边界 | 它做不到什么——具体到「能不能表达行级过滤、列级脱敏、标签驱动策略」 | 打分表问「能做什么」，而安全选型中被否决的永远是「它做不到的那一条恰好是你的合规硬要求」 |
| 成本结构 | 成本随什么变量增长（授权对象数 / 策略条数 / 出口通道数 / 密钥数 × 轮转频率） | 线性成本在百级资产上可以忽略，在万级资产上直接决定方案能不能运维下去 |
| 机制契合度 | 它的检查点放在链路的哪一层，能不能看到明文 | 看不到明文的检查点结构上只能做介质保护，无法约束「有权者读到之后做什么」（[§3.1](02-data-security-section-3-sec3.md)） |
| 运维复杂度 | 要不要改造成千个作业、要不要为每个数据源各写一次接入、要不要新增常驻组件 | 安全产品的失败多数不是能力不足，而是没有被全量接入——没接入的那部分等于没有产品 |
| 生态与锁定 | 离开它要付什么：策略要重写、作业要改、直连凭据要重发 | 策略是长在某套半成品语法上的资产，迁移成本通常高于多年许可费 |
| 演进风险 | 项目由谁维护、能力是被平台方收编还是被冻结 | 授权组件一换要同时动到全部数据作业，选错一次的代价按年度计 |

判据的顺序不是随意的：**能力边界先否决**（它做不到的那一条恰好是你的合规硬要求时，其余判据都无从谈起），**机制契合度紧随其后**（检查点看不到明文的方案，能力边界再宽也解决不了你的问题），**成本结构决定能不能规模化**，其余三条在它们都过关后用于排序。

### 7.2 候选方案全景

| 族 | 方案 | 定位（检查点在哪一层） | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- | --- |
| A 身份 | LDAP / Active Directory | 认证与目录 | 回答「你是谁、你在哪个组」，不回答「你能读哪些行」 | 有存量目录的企业内网 | 多为既有基础设施 |
| A 身份 | Keycloak | 身份联邦与 SSO | 以 OIDC / SAML 做身份联合，把「你是谁」标准化 | 需要统一登录与联合身份的组织 | 开源 |
| A 身份 | AWS IAM / Azure RBAC / 阿里云 RAM | 云资源级授权 | 以身份为授体、以云资源 API 为对象，在 API 层执行 | 云上原生工作负载 | 随云平台 |
| A 身份 | 华为云 IAM | 云资源级授权 | 同族机制，覆盖面限于该云自身的资源 API | 该云上的工作负载 | 随云平台 |
| B 数据授权 | Apache Ranger | 引擎侧授权服务 | 插件向集中式 Admin 取策略，在引擎编译期注入行过滤与列掩码 | Hive / Spark / HDFS 为主的集群 | Apache 开源 |
| B 数据授权 | Apache Sentry | 早期 Hadoop 授权服务 | 基于角色的库 / 表 / 列级授权，绑定 Hadoop 组；无行过滤与列掩码 | 存量 Hive 集群 | Apache 开源（维护状态以官方项目页为准） |
| B 数据授权 | AWS Lake Formation | 云上湖权限 | 在 Glue Data Catalog 上集中定义表 / 列 / 行权限，由查询引擎强制执行 | 该云上的数据湖 | 随云平台 |
| B 数据授权 | Unity Catalog | 湖仓统一治理 | 跨工作区的三级命名空间 + 集中授权 + 行过滤与列掩码函数 | 该湖仓平台上的组织 | 随平台（商业） |
| C 策略引擎 | Open Policy Agent | 通用策略引擎 | 声明式策略 + 进程内求值，决策不依赖网络往返 | K8s 与微服务的统一授权 | CNCF 项目、开源 |
| C 策略引擎 | Cerbos | 应用侧授权服务 | 策略即配置，独立 PDP 服务，应用通过 SDK 调用 | 应用层细粒度授权 | 开源 + 商业版 |
| C 策略引擎 | 自研 PDP / 自研网关 | 自定层 | 把策略写进自己的服务、网关或 SDK，行为完全可控 | 有平台团队的组织 | 自建 |
| D 控制平面 | Immuta | 商业数据安全控制平面 | 策略与数据源解耦，行级策略与动态脱敏在查询期下发到各引擎 | 多云、多引擎的强合规组织 | 商业订阅 |
| D 控制平面 | Privacera | 商业大数据安全平台 | 以 Ranger 机制为基础的策略管理与脱敏企业化 | 存量 Hadoop 生态的合规改造 | 商业订阅 |
| D 控制平面 | Collibra | 治理与目录侧 | 以目录与密级标注为中心，策略由标注驱动——定义「什么算敏感」 | 需要跨系统密级口径的组织 | 商业订阅 |
| E 密钥 | HashiCorp Vault | 密钥与凭据管理 | 集中签发短期凭据并自动轮转，把长期密钥从代码里拿掉 | 多云、多集群的组织 | 开源 + 商业版 |
| E 密钥 | HSM | 硬件密钥保护 | 密钥不出硬件边界，加解密在硬件内完成 | 金融、强合规 | 硬件采购 + 托管服务 |
| F 出口与使用中 | Nightfall | AI DLP | 对流出内容做分类器扫描，判定「这段文本里有没有敏感信息」 | 接入外部 LLM 的组织 | 商业订阅 |
| F 出口与使用中 | Microsoft Purview | 分类 + 数据地图 + DLP | 分类器自动打标，策略由标注驱动，覆盖其生态内的出口 | 该生态为主的合规组织 | 随平台（商业） |
| F 出口与使用中 | 阿里云 DAS 审计 / 通义安全 | 数据库审计 + AI 侧安全 | 记录数据库操作并对 AI 侧数据流做管控 | 该云上的组织 | 随云平台 |
| F 出口与使用中 | 机密计算（SGX / SEV-SNP / CC GPU） | 使用中保护 | 硬件隔离 + 远程证明，信任锚点从账号移到代码度量 | 受监管行业、单租户场景 | 机型溢价 |

这张表最重要的信息不是某一行，而是最左列：**A / B / C / D 是四种「谁来写策略、谁在什么时候执行」的答案，E 管密钥，F 管出口与使用中**。同族内部差异通常小到可以互换（例如 A 族之间比的是身份源覆盖率），跨族差异大到不可比（B 族与 F 族解决的根本不是同一件事）。**先分族、再定位缺失的那一层，能省掉一半以上的比较工作**；反过来，按总分排序会在跨族之间做无效对比。

需要单独说明 D 族的 Collibra：它不在执行路径上，它是判据一侧——它产出「这个字段是个人敏感信息」这个事实，而执行要靠 B / C / F。把定义侧与执行侧混为一谈，是 7.7 反模式③的来源。

还有两点读表时要留意。**第一，E 族与 F 族不是「可选项」**：E 族管的是「密钥谁能拿到」，F 族管的是「明文在谁的边界里出现」；这两件事没有任何 B / C / D 族产品能替代。授权做得再好，密钥躺在配置文件里、明文被有权者复制走，前面的检查点等于没有。**第二，同一族内部的产品差异通常可以用一条判据问干净**：A 族问「身份源能不能覆盖你的全部取数主体（含服务与 Agent）」；B 族问「它管不管得住你实际用的引擎」；C 族问「策略能不能被单测、能不能追到一条真实被拒的请求」；D 族问「离开它，策略能不能导出成你自己的格式」。这四条问完，同族内通常只剩一到两个候选。

### 7.3 机制差异：为什么它们表现不同（核心节）

四个机制维度决定了本节所有候选的行为差异。每个维度都请先读「因为……所以……代价是……」，再看失效条件——**失效条件决定它在你这里能不能用**。

#### 7.3.1 检查点看到的是明文还是密文

**机制是什么**：检查点能做什么，首先取决于它出现的位置上数据处于哪种形态（静态 / 传输 / 使用中）。静态检查点只能保护介质，传输检查点只能保护链路，只有处在「明文已进入某个进程」之后的检查点，才可能约束「谁能让这个进程干活」。

**各候选的实现差异**：

| 候选 | 检查点位置 | 能看到明文吗 |
| --- | :---: | :---: |
| 磁盘 / TDE 加密 | 静态 | 否 |
| TLS / mTLS | 传输 | 否 |
| 引擎侧授权（Ranger / Sentry / Lake Formation / Unity Catalog） | 使用中（查询期） | 是（可改写 SQL 与结果） |
| 数据安全网关 | 使用中（查询期，数据源之前） | 是 |
| 策略引擎（OPA / Cerbos） | 使用中（应用调用前） | 否——它只看到属性与动作，看不到数据 |
| DLP（Nightfall / Purview） | 出口 | 是（只看内容） |
| 机密计算 | 使用中（硬件内） | 是（但在受隔离的边界内） |

**由此必然导出的性质**：因为引擎侧授权与网关处在明文已被读出的环节，所以它们能改写行与列、能做动态脱敏；而正因为它们看到明文，它们的实现必须嵌入每个引擎的查询路径（Ranger 靠引擎插件，网关靠 SQL 改写）——代价是**所有没走这条路径的访问都不受它们约束**：备份工具、报表直连、运维跳板机、数据同步链路都是天然盲区。反过来，因为 OPA / Cerbos 只看到属性与动作、不接触数据，所以它们的部署对数据引擎零改造，代价是它们表达不了「这一列对分析师脱敏」——那需要能改写结果集的检查点。

**公开证据**：Apache Ranger 的行级过滤与数据脱敏是官方文档中并列的两类策略类型（来源：Apache Ranger 官方文档的 Row Level Filter / Data Masking 条目，可按 "Apache Ranger row level filter" 检索核验，版本与措辞以官方文档当前版本为准）【公开】；同一机制的商业等价物见湖仓平台的行访问策略与列掩码文档（可按 "row access policy" / "column masking" 检索核验）【公开】；「使用中」这一段的独立机制在 NIST 的机密计算相关材料与各芯片厂商的隔离技术文档中给出（可按 "confidential computing" 与具体技术名检索核验）【公开】。

**失效条件**：当存在绕过该检查点的直连路径时，机制契合度这一条直接归零——覆盖面不再取决于产品能力，而取决于「所有路径都被强制经过它」这件网络与凭据事实（[§3.2.3 失效点](02-data-security-section-3-sec3.md)）。判定方法只有一句：**能不能列出不经过它的取数路径**——列不出来的就没有统一入口。

**AI 时代新增的约束**：自然语言取数（Text2SQL）让 SQL 由模型生成，能改写 SQL 的检查点仍是最后一道可控点，但模型会生成检查点解析不了的复杂语句。因此这类检查点的默认行为必须写成「不可解析即拒绝」而不是「解析失败则放行」，否则盲区会随模型能力一起扩大。

#### 7.3.2 决策在执行点本地做还是集中做

**机制是什么**：授权决策要么在执行点本地用已加载的策略求值（本地决策），要么发一次请求到集中的策略服务（远程决策）。这个选择同时决定了延迟、可用性风险与撤销时延。

**各候选的实现差异**：

| 候选 | 决策在本地还是集中 | 可自行核验的公开入口（按关键词检索官方文档） |
| --- | --- | --- |
| Apache Ranger | 本地——各引擎插件从 Admin 拉取并缓存策略，在插件内求值 | Apache Ranger 官方文档中关于策略缓存与插件策略刷新周期的条目（关键词 `Apache Ranger policy cache` / `policy refresh interval`）【公开】 |
| Open Policy Agent | 本地——进程内库或 sidecar / daemon 形态，策略与数据预先加载后求值 | OPA 官方文档「Integrating OPA」一节逐条列出 Go library、sidecar 等集成形态（关键词 `Open Policy Agent integration Go library sidecar`）【公开】 |
| Cerbos | 集中——典型形态是应用经 SDK 调用独立 PDP 服务，每次决策一次网络往返 | Cerbos 官方文档中关于 PDP（Policy Decision Point）架构的章节（关键词 `Cerbos PDP architecture`）【公开】 |
| 云 IAM / RAM | 集中——由平台侧的策略评估服务裁决，对使用者不可见 | AWS IAM 官方文档的 Policy evaluation logic 章节；阿里云 RAM 的权限策略与授权文档（关键词 `IAM policy evaluation logic` / `RAM 权限策略`）【公开】 |
| Keycloak | 只在认证期介入——签发 token，不做每次数据访问的裁决 | Keycloak 官方文档的 Server Administration / Authorization Services 章节（关键词 `Keycloak authorization services`）【公开】 |

**由此必然导出的性质**：因为决策在本地求值，所以单次授权判断不引入网络往返、也不把策略服务的可用性乘进业务的可用性；代价是**撤销权限的生效时延等于策略分发时延**，不是零——一条被改掉的策略要等各执行点拉到新版本才生效，而这个窗口在批量分发时可能达到分钟级。反过来，集中裁决的撤销是立即的，代价是策略服务进入每次请求的关键路径：两个各自 99.9% 的串联组件给出 99.8%（推导链：0.999 × 0.999 = 0.998001）【推算】。

**公开证据**：零信任的参考架构把策略决策点与策略执行点显式分开，并给出控制平面 / 数据平面的划分（来源：NIST SP 800-207，2020）【公开】；纵深防御与访问控制、审计等要求被分置不同控制族并要求重叠覆盖（来源：NIST SP 800-53 Rev.5，2020；控制族划分以当期修订版为准）【公开】；国内对应思路见「一个中心、三重防护」（来源：GB/T 22239-2019，措辞以标准原文为准）【公开】。

**失效条件**：当策略服务的可用性低于业务可用性要求时，运维会被迫加「降级放行」开关，策略在故障期间等于不存在。判断标准很直接：问「策略服务不可用时，系统是拒绝访问还是放行」——答「放行」的方案，只在它不出问题的时候存在。

**AI 时代新增的约束**：取数主体从「人偶尔读一次」变成「Agent 批量反复读」之后，非人身份的数量会超过人。此时授权的主要工作量从「给人发权限」变成「给机器发可过期、可轮换、范围最小的凭据」；而机器身份的滥用不会自带「行为反常」这个信号——没有作息、没有历史基线，基于「凌晨三点下载」这类规则的异常检测在机器主体上直接失效。

#### 7.3.3 策略的表达粒度：RBAC / ABAC / 标签驱动

**机制是什么**：策略的表达能力由「授体与对象的粒度」决定：授体可以是个体、角色、属性组合或工作负载身份；对象可以是库、表、列、行或标签。

**各候选的实现差异**：

| 候选 | 授体粒度 | 对象粒度 | 表达能力 |
| --- | --- | --- | --- |
| LDAP / AD | 用户 / 组 | 无（不表达数据对象） | 只到「你是谁」 |
| Keycloak | 用户 / 组 / 客户端 | 无（凭 claims 传递给下游） | 只到身份与声明 |
| 云 IAM / RAM | 身份 / 角色 / 资源策略 | 云资源 | 资源级，通常不表达行 |
| Sentry | 角色（绑 Hadoop 组） | 库 / 表 / 列 | 无行级、无列脱敏 |
| Ranger | 用户 / 组 / 角色 | 库 / 表 / 列 / 行 + 标签 | 行过滤 + 列掩码 + 标签策略 |
| Lake Formation / Unity Catalog | 身份 / 组 | 表 / 列 / 行 | 与所在平台引擎绑定 |
| OPA / Cerbos | 任意属性（用户 / 资源 / 环境 / 动作） | 任意（由策略自定义） | 表达力上限等于策略语言的表达力 |
| Collibra | 不适用（定义侧） | 字段的密级标注 | 只产出标注，不执行 |

**由此必然导出的性质**：因为 Ranger 的行过滤与列掩码是在**引擎编译期注入 SQL 表达式**实现的，所以策略对使用方透明——不用改业务代码就能上线，代价是「被注入的必须是这个引擎能解析的 SQL」，存储过程、UDF、动态拼接 SQL 与批量导入成为天然盲区。因为 Sentry 的授权对象止于库 / 表 / 列，所以行级隔离只能靠「每个用户一个视图」实现，视图数随用户数线性增长，代价是这项成本随组织变大而失控——这正是它在本主题里只能作为存量方案的原因。因为标签驱动策略把「哪些字段是 PII」与「谁能读 PII」拆成两件事，所以一条策略能覆盖全部同类字段，代价是标签本身必须被维护：标签漏标时策略静默失效，而不会有任何报错。

**公开证据**：基于属性的访问控制有形式化标准（来源：OASIS 的 XACML 3.0 标准，版本与发布日期以 OASIS 官方发布为准，可按 "XACML 3.0" 检索核验）【公开】；通用策略引擎的策略可被单元测试与版本管理，其策略语言文档与社区生态见 Open Policy Agent 官方文档（可按 "Open Policy Agent policy language" 检索核验）【公开】；标签驱动策略在数据引擎侧的体现见 [§8.6 §5.4](02-data-security-section-8-5-4-ranger-与-sentry-对比与选型.md) 中标签策略与 PII 字段自动脱敏的机制说明（本仓库内可逐行核对）。

**失效条件**：当标签覆盖不全时（新表未打标、字段新增未同步），标签驱动策略的覆盖面会随资产生长而下降，而下降是静默的——这比「策略写漏了」更难发现，因为漏的是标签而不是规则。判定方法：抽样 50 个字段，看机器标注的密级与人工标注是否一致，算出误标率【经验】。

**推论：粒度不是越细越好**。粒度越细，策略条数越多、评审人次越多、漂移概率越高——这是 7.4 里 f 项的来源。工程上稳定的组合通常是「标签定粒度 + 表达式定条件」：用标签把字段归成有限几类（如 PII / SPI / PHI），用条件表达式处理环境与时间这类会变的条件，而不是为每个字段各写一条策略。判据是：**一条新字段进系统时，需要人工新增策略条数吗**——需要，说明粒度选细了。

#### 7.3.4 覆盖面取决于产品能力，还是取决于「路径都被收口」

**机制是什么**：一款授权产品宣称的覆盖面，与它实际生效的覆盖面是两件事。前者是能力，后者是「所有访问路径都被强制经过它」这一事实的函数。

**各候选的实现差异**：Ranger 的实际覆盖面 = 装了插件的引擎集合；Lake Formation / Unity Catalog 的实际覆盖面 = 走该目录的引擎集合；网关的实际覆盖面 = 没有绕过它的路径集合；OPA / Cerbos 的实际覆盖面 = 所有调用方都接了 SDK 或 sidecar；DLP 的实际覆盖面 = 所有出口通道都被串联了检测。

**由此必然导出的性质**：因为覆盖面是一个**组织事实**（谁持有直连凭据、哪些网段可达数据源），而不是产品特性，所以「再买一款产品」通常不改变覆盖面，只增加一个同样只覆盖一部分路径的检查点——代价是两份不完整的覆盖面叠加后，团队会误以为已经统一管控。要真正改变覆盖面，要做的动作是收掉直连凭据、掐断网络可达性，这两件事都落在组织与流程上，而不是采购单上。这就是为什么安全项目里最容易做的是「往上加检测」，最难做的是「把旁路关掉」。

**公开证据**：本书 [§5.5](02-data-security-section-5-ai.md) 把「AI DLP 成为标配，出口就管住了」列为被过度宣传的一项，给出的判定方法是让一个非平台团队的人列一遍他能想到的取数路径、逐条对照是否经过检查点（本仓库内可逐行核对）；[§3.2.1](02-data-security-section-3-sec3.md) 给出了纵深防御的前提——各层失效原因互不相关，一旦共享身份源或密钥，「深度」就退化为取最弱的一层。

**失效条件**：当团队把「采购完成」当成「管控完成」时，这个机制就会反向伤人：检查点数量增加了，但每条旁路仍在，而风险感知反而下降。可操作的复核动作是一张共享依赖图——把所有防线共用的身份源、密钥、策略存储、日志通道列出来；若某个组件失守会同时影响三层以上，你的纵深防御实际上只有一层。

**AI 时代新增的约束**：RAG 与向量库给覆盖面加了一类新旁路——「检索返回的片段进入外部模型上下文」这一步，既不是数据库访问也不是文件下载，很多存量检查点根本不在这条路径上。判定方法不是问产品支不支持，而是做一次删除演练：删掉一份源文档，逐处确认原文档、切片、向量、索引与缓存是否都消失——删不干净的地方，就是覆盖面之外的地方。

### 7.4 成本结构对比（不是价格表，是成本函数）

本主题的成本不是一个数，而是几个不同形状的函数之和：

```
总成本 ≈ 身份与目录基础设施（固定）
        + f(授权对象数：表数 × 每表策略条数)          ← 策略编写与评审
        + g(决策次数 × 单次决策成本)                  ← 本地求值 vs 远程裁决
        + h(数据源连接器数 × 接入工作量)              ← 每接一个新源各写一次
        + i(出口通道数 × 检测量)                      ← DLP 与审计
        + j(密钥数 × 轮转频率) + 硬件固定成本          ← KMS / HSM
        + 可用性损失（串联检查点可用性之积）
```

**哪个候选的主导项是什么**：

| 候选族 | 主导成本项 | 隐性成本（常被漏算的那一项） |
| --- | --- | --- |
| 引擎侧授权（Ranger / 湖仓目录） | f：策略对象数 | 插件覆盖不到的长尾引擎要自建接入，成本计入自研而非许可 |
| 通用策略引擎（OPA / Cerbos） | g + h：每次决策与每个调用方接入 | 策略数据的分发与版本管理是一套新的运维面 |
| 云 IAM / RAM | 固定项 + 调用量 | 每新增一个数据源都要把它接进同一身份模型，跨引擎的字段级语义仍要另做 |
| 商业控制平面（Immuta / Privacera / Collibra） | 年度订阅（按数据源或数据量计） | 策略仍然要落在每个引擎上执行，引擎侧改造不会因为买了控制平面而消失 |
| DLP（Nightfall / Purview） | i：出口通道数与检测量 | 漏检与误报的运营成本（人工复核队列） |
| 密钥（Vault / HSM） | j + 硬件固定成本 | 轮转一旦自动化失败会同时影响多系统，需要演练 |
| 机密计算 | 硬件固定成本（机型溢价） | 适配与证明集成的人力，且它只覆盖「使用中」一段 |

【推算】授权对象数是线性成本项，这一条决定了策略形态。设核心资产 1000 张表、每表平均 5 条字段级策略、每条策略人工确认 3 分钟（这三个数是假设值，请替换成你自己口径下的真实值），则一次全量确认 = 1000 × 5 × 3 ÷ 60 ≈ 250 人时；一年重审两次 ≈ 500 人时。若表数增长 10 倍而人力不变，单条策略的确认预算下降一个数量级，此时唯一可行的是把策略从「逐字段」改写为「按标签」——这是标签驱动策略的机制动因，不是产品偏好。

【推算】把决策服务放进每次请求路径的代价可以量化（可用性数值为假设值，请替换成你自己口径下的真实值）：设业务服务自身可用性 99.9%，则它自己一年就有 0.001 × 8760 ≈ 8.76 小时不可用，这是**基线**；再串入一个同为 99.9% 的策略服务后，组合可用性上界为 0.999 × 0.999 = 0.998001，年不可用为 (1 − 0.998001) × 8760 ≈ 17.51 小时——**这 17.5 小时是串联后的总不可用，不是增量**。把决策服务放进请求路径真正**额外**增加的，是 17.51 − 8.76 ≈ 8.75 小时/年（等价推导链：新增的不可用比例 1 − 0.999 = 0.001 被乘进基线，即 0.001 × 0.999 × 8760 ≈ 8.75），也就是让服务的年不可用时长翻倍。反过来，本地求值不引入这 8.75 小时，但把撤销时延换成了策略分发周期。

【经验】本主题的成本排序在百级资产与万级资产上会反向：百级资产时，人力成本可忽略、许可与接入周期主导；万级资产时，f 与 h 两项的线性增长超过一切许可费。因此「哪家更便宜」这个问法在跨规模时没有稳定答案。

还有两项成本常被漏算，而它们往往才是实际主导项。**第一是评审渠道成本**：策略生效前要有人确认「这条策略是否符合业务本意」，这条评审渠道的吞吐量是固定的（能评审的人就那几个），于是策略上线速度有上限，与产品无关。**第二是误拦的运营成本**：任何把检查点放进关键路径的方案都会拦错，误拦需要一条人工申诉与放行的通道；这条通道不建，使用方就会去建旁路——旁路一旦建成，7.3.4 的覆盖面结论立即生效。把这两项写进成本函数，得到的结论与只比许可费时常常相反。

```
总成本 ≈ 许可 / 建设成本
        + 评审渠道成本（策略条数 ÷ 评审吞吐）
        + 误拦运营成本（拦截次数 × 单次申诉成本）     ← 最容易被漏算
        + 旁路带来的风险敞口（不在账面上，但决定前面几项是否白花）
```

### 7.5 决策树（每个分支都要有阈值依据）

```
① 你的数据访问是否已经全部经过某一组可控入口？
├─ 否（存在 BI 直连 / 备份工具 / 跳板机 / 同步链路等多条旁路）
│    └─ 先收口：收掉直连凭据 + 掐断网络可达性
│       └─ 此时选任何策略引擎都不成立（见 7.7 反模式②）
└─ 是
   ② 你的首要控制目标是「授权」，还是「数据怎么出去」？
   ├─ 授权 → 跳到 ③
   └─ 出口 / 使用中 →
        ├─ 要求「连云厂商与运维管理员也看不到明文」→ 机密计算（TEE）+ 密钥托管在 KMS/HSM
        └─ 只要求「出口可见、可拦、可审」      → DLP（Nightfall / Microsoft Purview）+ 出口审计
           └─ 二者不互斥：受监管行业通常是「TEE 管一段 + DLP 管一段」
      ③ 你的数据平面是否以 Hadoop 系引擎（Hive / Spark / HDFS）为主？
      ├─ 是 →
      │    ├─ 需要行级隔离或列脱敏 → Apache Ranger（行过滤 + 列掩码 + 标签策略）
      │    └─ 只需要到列级、且要求极简接入 → Apache Sentry
      │         └─ 但要做行级隔离时，Sentry 只能靠「每用户一个视图」（见 7.3.3 失效条件）
      └─ 否 →
          ④ 授权决策是否要覆盖多个非 Hadoop 系统（K8s、微服务、自研 API）？
          ├─ 是 →
          │    ├─ 要求决策能在进程内求值、策略能被单测 → Open Policy Agent
          │    └─ 接受独立 PDP 服务、每次调用走一次网络 → Cerbos
          └─ 否 →
              ⑤ 你的表与权限是否天然挂在一个统一目录下（同一云 / 同一湖仓）？
              ├─ 是 → 目录原生授权（AWS Lake Formation / Unity Catalog）
              └─ 否 → 跨引擎控制平面（Immuta / Privacera）+ 目录侧定义密级（Collibra）
                 ⑥ 是否存在必须由你回答「什么算敏感」的跨系统密级口径？
                 ├─ 是 → 引入 Collibra 一类治理侧组件，只负责定义与标注，不承担执行
                 └─ 否 → 密级定义先写在数据标准里，等第一个跨系统分歧出现再上系统
```

**阈值依据**（与树上节点一一对应）：

- **① 路径是否已收口**：依据来自 7.3.4——覆盖面是组织事实而非产品能力；可操作判据是「让一个非平台团队的人列出他能想到的取数路径，逐条对照是否经过检查点」，清单非空则该节点判否。
- **② 目标是授权还是出口**：依据是两类机制的判定输入不同——授权约束「谁能读」，其输入是身份与属性；出口约束「读到的内容能不能离开」，其输入是内容。一份已被授权读取的数据被有权者导出，授权层在结构上无法阻止（[§3.1](02-data-security-section-3-sec3.md)）。
- **② → TEE 或 DLP 的分支**：依据是信任锚点位置。TEE 把信任从账号移到硬件与代码度量，因此连运营方也被排除在明文之外；DLP 的判定输入是内容，它不阻止已授权的读取，只标记外流。要求里出现「运营方也不能看」时前者是唯一的，出现「要留证与拦截」时后者是唯一的。
- **③ 是否以 Hadoop 系引擎为主**：依据是 Ranger 与 Sentry 的能力通过**引擎插件在查询编译期改写**实现，插件的存在与否就是能力边界；非 Hadoop 引擎要么无插件、要么需自建接入。
- **③ → Sentry 的分支**：依据来自 7.3.3——Sentry 的授权对象止于库 / 表 / 列，行级隔离须「每个用户一个视图」，视图数随用户数线性增长；只要你的要求里出现行级隔离或列脱敏，它就出局，与它多好配置无关。
- **④ 是否覆盖非 Hadoop 系统**：依据来自成本函数——策略引擎的成本随**策略对象数**增长，价值随**决策点数量**增长；决策点分散在 K8s 与微服务中时，集中策略的固定成本才被摊薄（7.4 的 f 项与 g 项）。
- **④ → OPA 或 Cerbos 的分支**：依据是决策位置。OPA 支持进程内求值，不引入网络往返，因此也不把策略服务的可用性乘进业务；Cerbos 的典型形态是独立 PDP，每调用一次走一次网络，撤销是立即的但可用性要相乘（7.3.2 的 0.998001 推算）。
- **⑤ 是否挂在统一目录下**：依据来自 7.3.4——目录原生授权的覆盖面 = 走该目录的引擎集合；有引擎绕过目录直读对象存储时，该授权对该引擎失效。多云多引擎时，需要的是一层在目录之外的策略控制面。
- **⑥ 是否需要跨系统密级口径**：依据是 Collibra 一类组件不在执行路径上，它的产出是「这个字段是个人敏感信息」这一事实（标签），执行仍要落在 B / C / F 族；没有跨系统分歧时，把密级先写进数据标准比先上系统便宜。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| Hadoop 生态为主 | Apache Ranger | Apache Sentry | 不选 Sentry：授权对象止于库 / 表 / 列，行级隔离要靠「每用户一个视图」，成本随用户数线性增长 |
| 云原生 / K8s | Open Policy Agent + Istio | Cerbos | 不选 Cerbos 作为首选：独立 PDP 使每次调用多一次网络，撤销快但可用性要相乘 |
| 数据湖 / Lakehouse | Unity Catalog / Lake Formation | Privacera | 不选 Privacera 作为首选：它要改造存量引擎侧接入，新平台则可由目录原生授权直接覆盖 |
| 多云数据 | Immuta | 自研 + Ranger | 不选自研 + Ranger：Ranger 的能力绑定引擎插件，多云下要为每朵云各建一套插件接入 |
| AI / LLM 出口 | AI DLP（Nightfall） + 机密计算 | Microsoft Purview | 不选 Purview 作为首选：它的覆盖面绑在其生态内的通道，跨生态出口需另接检测 |
| 中国本土合规 | 阿里云 RAM + DAS 审计 | 华为云 IAM | 二者同为云内资源级授权，覆盖面限于各云自身资源；跨云与自建集群需另加检查点 |
| 金融 / 强合规 | Immuta + 自研 + HSM | Privacera + HSM | 不选纯自研：策略语法与执行点都要自建，评审与举证能力也要自建，成本落在人力而非许可 |
| 什么都要但预算有限 | 先做「路径收口 + 引擎侧列级授权」 | — | 不先上 DLP：检测的覆盖面取决于通道是否串联，通道没收口时检测只是增加误报队列 |

**常见组合 1：Ranger + HSM + Vault**

- **职责边界**：Ranger 负责「谁能读表 / 列 / 行」并在引擎编译期改写；Vault 负责签发短期凭据并轮转；HSM 负责让根密钥不出硬件边界。三者边界清晰：**授权不问密钥、密钥不问授权**。
- **运维代价**：三个组件各有一次高可用设计，且 Vault 与 HSM 一旦不可用会导致全量作业无法取数（比授权服务不可用更严重，因为它是取数的前提）。轮转演练必须定期做，且要覆盖「轮转中途失败」的分支。

**常见组合 2：Open Policy Agent + Cerbos + Keycloak**

- **职责边界**：Keycloak 做身份联邦与 SSO，回答「你是谁」；OPA 承担通用策略决策（K8s 准入、服务间授权）；Cerbos 承担应用内细粒度授权。三者共用同一份身份声明，但不共用策略存储。
- **运维代价**：策略被拆到两个引擎里，同一件事可能在两处各写一遍，策略漂移是这份组合的主要风险；需要明确「哪类决策归谁」，否则会出现两处都能改、都以为自己说了算。

**常见组合 3：Unity Catalog + Immuta + Nightfall**

- **职责边界**：Unity Catalog 提供湖仓内的目录与原生授权（表 / 列 / 行）；Immuta 提供跨引擎的策略控制面与动态脱敏；Nightfall 管出口内容检测。三层分别对应「目录内」「跨引擎」「出口」。
- **运维代价**：三层都要接入同一份密级标注，标注一旦不同步，会出现「目录内脱敏、出口没脱敏」的缝隙；且三层的许可都是订阅制，成本随数据源与席位增长。

**常见组合 4：阿里云 RAM + DAS 审计 + 通义安全**

- **职责边界**：RAM 做云内统一身份与资源授权；DAS 审计记录数据库侧操作，供事后追溯；通义安全承担 AI 侧数据安全的管控。
- **运维代价**：审计日志的保留期要覆盖「发现泄露所需时间」而不是「排查所需时间」，这直接决定存储成本；三者都绑定在同一云生态内，跨云或自建集群需要另外的检查点。

四组组合有一个共性代价，值得单独说：**每多一层，就多一份「密级定义」的同步义务**。组合 3 里的三层都要消费同一份标签，组合 4 里的审计与管控都要消费同一份身份；这些共享输入没有同步机制时，缝隙会出现在「某一层还不知道标注已经改了」的那个窗口里，而窗口期的访问是合规的、事后却无法解释。因此在选组合之前，先回答一个与产品无关的问题：**密级与身份这两份共享输入，由谁维护、以什么频率同步、同步失败时各层的行为是拒绝还是放行**。这个问题的答案，比组合里选哪个产品更能决定事故率。

### 7.7 选错的代价与迁移成本

**反模式①：把打分表的第一名当成选型结果** —— 症状是选型材料里只有一列总分、没有一行「它做不到什么」；后果是上线后才发现缺的正是行级隔离或标签驱动这类被合规硬要求的能力，而补它意味着换掉整个策略层；正确做法是把 6 条判据里的「能力边界」放在第一位：先列出你必须满足的、可判定的能力项（行级过滤？列掩码？跨引擎？使用中加密？），再用其余判据在过关者之间排序。【经验】

**反模式②：用网关做授权，却没收回直连凭据** —— 症状是网关上策略齐全、报表团队仍持有一份直连账号，另有一台跳板机可达数据源；后果是策略只覆盖了一部分路径，却给出「已统一管控」的错觉，事故发生时追责链断裂；正确做法是把「收掉直连凭据 + 掐断网络可达性」写成有责任人与验收日期的任务，而不是在网关里继续加功能（7.3.4）。【经验】

**反模式③：把定义侧当成执行侧** —— 症状是买了治理与目录产品（如 Collibra 一类），在目录里完成了密级标注，就认为数据已被保护；后果是标注只回答了「什么算敏感」，没有任何检查点在查询期执行它，标注与实际访问脱钩；正确做法是让定义侧产出机器可读的标签，并确认标签被 B / C / F 族的某个执行点消费（7.3.3 的标签驱动策略就是这条链路的执行端）。【经验】

**反模式④：把 DLP 当作出口管控的全部** —— 症状是接入外部模型的通道上挂了内容检测，就认为 AI 泄密已被管住；后果是漏检与误报同时存在，而真正的可控点（网络与凭据）没有动；正确做法是先回答「有多少条不经检查点的出口」，再谈检测率（[§5.5](02-data-security-section-5-ai.md)）。【经验】

**换成另一个要动什么**：

| 迁移方向 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 | 量级判断 |
| --- | --- | --- | --- | --- | --- |
| 引擎侧授权 A → 引擎侧授权 B（如 Sentry → Ranger） | 不动数据 | 一般不动 SQL；行级隔离需从视图改为策略注入 | 换策略存储与分发，插件重装 | 策略语法与标签模型 | 中等——策略要按新模型重写一遍 |
| 引擎侧授权 → 通用策略引擎（Ranger → OPA） | 不动数据 | 不适用——OPA 不改写 SQL，它管的是调用方 | 决策点从引擎移到应用；要接 SDK / sidecar | 策略语言与单测方式 | 大——覆盖面从「引擎内」变成「调用方是否接入」，是组织任务 |
| 本地决策 → 集中决策（或反向） | 不动数据 | 不动 | 撤销时延与可用性风险位置互换；降级策略要重新定义 | 值班与故障处置流程 | 中等——机制简单，但故障语义变化影响面大 |
| 自建 → 商业控制平面 | 不动数据 | 一般不动 | 新增控制平面与连接器，引擎侧改造仍在 | 产品模型与策略迁移 | 中到大——引入订阅成本与新的运维面 |
| 单引擎 → 跨云多云 | 可能需复制或联邦 | 视引擎差异而定 | 每朵云各建一套检查点与身份映射 | 多套产品的策略模型 | 大——通常无法一次性完成，按数据域分批 |

判断量级的通用口径是：**动数据 > 动查询 > 动运维 > 动培训**；而本主题里最贵的一次迁移通常不是动数据，而是「从引擎侧授权换成应用侧策略」——它把覆盖面从「引擎能力」变成「所有调用方是否接入」这件组织事实。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 存在多条不经检查点的取数路径 | 先收口路径，再选产品 | 覆盖面是组织事实；产品升级不改变旁路的存在（7.3.4） |
| Hadoop 系为主、需要行级或列级控制 | Apache Ranger | 编译期注入 SQL 表达式，策略对使用方透明；代价是插件之外无覆盖 |
| 只要库 / 表 / 列级、且存量系统极简 | Apache Sentry（存量维持） | 授权模型浅因而接入成本低；代价是行级隔离只能靠逐用户视图 |
| 决策点分散在 K8s 与微服务 | Open Policy Agent | 进程内求值不引入网络往返与可用性乘积；代价是撤销时延等于策略分发周期 |
| 单一云、单一湖仓 | 目录原生授权（Lake Formation / Unity Catalog） | 权限定义挂在目录层，多引擎读同一表时权限一致；代价是绕过目录的直读不受约束 |
| 多云多引擎、强合规 | Immuta / Privacera + 目录侧定义密级 | 策略与数据源解耦，能跨引擎下发；代价是引擎侧改造与订阅成本都还在 |
| 必须回答「运营方也不能看明文」 | 机密计算 + 密钥托管在 KMS / HSM | 信任锚点从账号移到硬件与代码度量；代价是只覆盖「使用中」一段 |
| 担心数据经外部模型外流 | 先收口出口通道，再加 DLP 检测 | DLP 的输入是内容，它不阻止已授权读取，只标记外流 |
| 需要事后追责与举证 | 审计留痕 + 血缘 | 审的是「谁在何时读了什么」，其粒度决定事故能否被还原 |

> 本节小结：本主题的候选不是一堆可互换的产品，而是**检查点在不同链路层上的六个族**；**唯一真正起决定作用的差异是「覆盖面由产品能力决定，还是由『所有路径都被强制经过它』这件事决定」**——前者能买到，后者只能靠收凭据与断可达性换来。Ranger 的行过滤、Lake Formation 的行权限、Immuta 的跨引擎策略，机制上都很强，但只要有一条直连路径存在，它们的实际覆盖面都是零。因此正确的顺序永远是：先收口，再分层，最后才谈选哪一款。
>
> 💡 **思考锚点**：把决策服务放进每次请求路径前先算一笔账：你的业务服务可用性乘上策略服务可用性等于多少？按 7.4 那条推算，它会让年不可用从 8.76 小时变成约 17.5 小时——你更愿意付这笔，还是改成进程内本地求值、改付策略分发周期的撤销时延？
