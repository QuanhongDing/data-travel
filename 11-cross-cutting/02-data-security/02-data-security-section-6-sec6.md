## 6. 落地实践

### 2.1 某银行"**等保 2.0 三级 + 全链路加密 5+ 年**"（2019-2024）

**背景（Why）**

该银行 2019 年面临**监管与泄露双重压力**：
- **10 亿+ 账户**——**数据即资产**
- **等保 2.0 三级**——**强制合规**
- **泄露代价**——**罚款 + 声誉**

**触发点（What）**

2019 年该银行启动**等保 2.0 + 全链路加密**（[案例 2019]），目标：
- **等保三级通过**
- **加密覆盖率 100%**
- **泄露事件 0**

**详细做法（How）**

该银行数据安全的**5 大核心组件**：

1. **数据分类分级（核心创新）**
   - 关键设计：**公开 / 内部 / 秘密 / 机密四级，字段级打标**
   - 关键能力：**不同级别自动匹配不同的加密 / 访问 / 审计措施，安全强度与使用便利各归其位**
   - 关键数字：**100% 打标**
   - 关键示意：
     ```
     数据分级 → 控制措施矩阵
     ┌────────┬──────────┬──────────┬──────────┐
     │ 级别   │ 加密     │ 访问控制 │ 审计     │
     ├────────┼──────────┼──────────┼──────────┤
     │ 公开   │ 不要求   │ 全员     │ 不要求   │
     │ 内部   │ 传输加密 │ 部门级   │ 常规日志 │
     │ 秘密   │ 存储加密 │ 最小权限 │ 全量审计 │
     │ 机密   │ 全链路+   │ 双人授权 │ 全量+告警│
     │        │ 字段级    │          │          │
     └────────┴──────────┴──────────┴──────────┘
     ```

2. **最小权限 + 双人授权（核心）**
   - 关键设计：**机密级数据需双人授权**
   - 关键能力：**单人无法独立取走机密数据，作恶从个人行为升级为必须串通第二人**
   - 关键数字：**0 越权**

3. **全链路加密（核心）**
   - 关键设计：**传输 TLS + 存储 AES-256 + 字段级加密**
   - 关键能力：**即使拖库也不可用**
   - 关键数字：**100% 加密**

4. **全量审计（核心）**
   - 关键设计：**每条访问可追溯 + 保留 6 个月以上**
   - 关键能力：**监管问询时能逐条还原「谁在何时看了什么」，不必现场翻库补记录**
   - 关键数字：**100% 可查**

5. **UEBA 异常检测（核心创新）**
   - 关键设计：**用户行为基线 + 异常告警**
   - 关键能力：**内鬼的少量高敏查询不再淹没在正常流量里，异常由基线比对自动浮出**
   - 关键数字：**告警 < 5 分钟**

**该银行数据安全关键数字**（[案例 2019-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**等保合规**」** | 未通过 | 三级通过 | **∞** |
| **「**加密覆盖**」** | 40% | 100% | **+150%** |
| **「**字段级打标**」** | 20% | 100% | **+400%** |
| **「**越权事件**」** | 5 次/年 | 0 | **-100%** |
| **「**审计可查**」** | 60% | 100% | **+67%** |
| **「**UEBA 告警**」** | 不可用 | < 5 分钟 | **∞** |
| **「**泄露事件**」** | 基线 | 0 | **-100%** |
| **「**审计日志保留**」** | 30 天 | 180 天+ | **+500%** |

**具体数字（How much）**

- 团队规模：该银行安全团队 50+ 人
- 关键数字：**加密覆盖 40% → 100%**；**越权事件 5 次/年 → 0**；**审计日志保留 30 天 → 180 天+**（[案例 2019-2024]，见本节上表）
- 业务影响：覆盖该银行**10 亿+ 账户全部数据**

**失败教训**

- 早期「**分级只到表**」——整表按最高级别管控、业务根本用不了，倒逼**「字段级打标」**
- 「**只做传输加密**」——备份文件被拖走后仍可读，倒逼**「存储加密 + 字段级加密」**
- 「**审计日志只留 30 天**」——监管要追溯半年前的操作、答不出，倒逼**「保留 180 天以上」**
- 「**只看访问量不看行为模式**」——内鬼的少量高敏查询淹没在正常流量里、无人发现，倒逼**「UEBA 行为基线 + 异常告警」**

### 2.2 阿里"**数据安全 4 级分级 + 100 万企业 8+ 年**"（2016-2024）

**背景（Why）**

阿里 2016 年面临**25 BU + 100 万企业客户的安全**：
- **EB 级数据**——**30 万+ 表**
- **25 BU 共享**——**既要安全又要共享**
- **100 万企业**——**对外必须合规**

**触发点（What）**

2016 年阿里启动**数据安全 4 级分级**（[阿里 2016]），目标：
- **100% 字段级分级**
- **25 BU 安全共享**
- **对外 100 万企业合规**

**详细做法（How）**

阿里数据安全的**5 大核心组件**：

1. **4 级分级 + 字段级打标（核心创新）**
   - 关键设计：**公开 / 内部 / 秘密 / 机密，落到字段**
   - 关键能力：**同一张表里公开字段与机密字段各按自身密级管控，不为少数敏感字段牺牲整表可用性**
   - 关键数字：**100% 字段级**
   - 关键示意：
     ```sql
     -- 字段级密级标注（元数据）
     ALTER TABLE dwd_user ADD COLUMNS (
       phone STRING COMMENT '手机号'
         WITH ('security.level'='机密', 'security.tag'='PII'),
       city  STRING COMMENT '城市'
         WITH ('security.level'='内部')
     );
     -- 查询时解析密级 → 自动注入脱敏 / 权限校验
     ```

2. **ABAC 访问控制（核心）**
   - 关键设计：**属性基访问控制（部门/项目/密级/时段）**
   - 关键能力：**比 RBAC 更细**
   - 关键数字：**0 越权**

3. **自动脱敏（核心）**
   - 关键设计：**按密级自动脱敏（掩码 / 哈希 / 泛化）**
   - 关键能力：**使用侧拿到的是脱敏后仍可计算的数据，原始标识不出安全域**
   - 关键数字：**100% 自动**

4. **全链路审计（核心）**
   - 关键设计：**谁 / 何时 / 查了哪个字段 / 结果多少行**
   - 关键能力：**审计记录精确到字段与结果行数，事后能复盘一次查询究竟取走了什么**
   - 关键数字：**100% 可查**

5. **安全共享（核心创新）**
   - 关键设计：**数据可用不可得（沙箱 + 脱敏 + 水印）**
   - 关键能力：**安全与共享兼得**
   - 关键数字：**25 BU 共享**

**阿里数据安全关键数字**（[阿里 2016-2024]）：

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**字段级分级**」** | 20% | 100% | **+400%** |
| **「**越权事件**」** | 基线 | 0 | **-100%** |
| **「**自动脱敏**」** | 未建设 | 已覆盖 | **新增能力** |
| **「**审计可查**」** | 60% | 100% | **+67%** |
| **「**25 BU 共享**」** | 未建设 | 已覆盖 | **新增能力** |
| **「**企业客户**」** | 0 | 100 万+ | **∞** |
| **「**数据水印**」** | 未建设 | 已覆盖 | **新增能力** |
| **「**合规审计通过**」** | 弱 | 100% | **∞** |

**具体数字（How much）**

- 团队规模：阿里数据安全团队 100+ 人
- 关键数字：**字段级 100%**；**越权 0**；**100 万企业**
- 业务影响：覆盖**阿里全集团 + 100 万企业**

**失败教训**

- 早期「**表级分级**」——一张表里既有公开也有机密字段，整表按机密管、业务用不了，倒逼**「字段级打标」**
- 「**RBAC 不够用**」——同一角色在不同场景下应有不同权限，倒逼**「引入 ABAC 按属性判断」**
- 「**共享等于交付原始数据**」——数据给出之后就失控、无法追溯，倒逼**「沙箱 + 脱敏 + 水印」**
- 「**等级只打不管**」——打完标没人用、访问控制没跟上，倒逼**「让等级自动驱动权限与脱敏策略」**

### 2.3 字节"**数据安全 + 多业务合规 5+ 年**"（2019-2024）

**背景（Why）**

字节 2019 年面临**多业务 + 全球合规**：
- **4 业务**——**抖音 / TikTok / 西瓜 / 今日头条**
- **全球合规**——**GDPR / CCPA / 国内等保**
- **数据出境**——**红线**

**触发点（What）**

2019 年字节启动**数据安全 + 多业务合规**（[字节 2019]），目标：
- **4 业务统一分级**
- **GDPR / 等保双合规**
- **数据零违规出境**

**详细做法（How）**

字节数据安全的**5 大核心组件**：

1. **统一分级（核心创新）**
   - 关键设计：**4 业务统一 4 级 + 字段级**
   - 关键能力：**同一份数据在抖音与头条是同一密级，跨业务共享不必再逐次对齐口径**
   - 关键数字：**4 业务统一**
   - 关键示意：
     ```
     数据域隔离（合规分区）
     ┌─────────────────┬─────────────────┐
     │  国内域（CN）    │  海外域（INTL）  │
     │  等保 / 个保法   │  GDPR / CCPA     │
     ├─────────────────┼─────────────────┤
     │  不得流出 →      │  不得流入 ←      │
     └─────────────────┴─────────────────┘
     跨域访问需法务 + 安全双审批
     ```

2. **GDPR / 等保双合规（核心）**
   - 关键设计：**分区部署 + 同意管理**
   - 关键能力：**一套体系同时满足 GDPR 与国内等保两套要求，不必按法域各建一套**
   - 关键数字：**100% 合规**

3. **数据出境管控（核心）**
   - 关键设计：**出境白名单 + 双审批**
   - 关键能力：**不在白名单内的数据在链路上就出不去，违规由机制拦截而非事后审计发现**
   - 关键数字：**0 违规**

4. **脱敏 + 水印（核心）**
   - 关键设计：**按用途脱敏 + 隐式水印**
   - 关键能力：**数据外泄后可反查发放对象与时间，追责不再无据**
   - 关键数字：**100% 水印**

5. **全量审计（核心创新）**
   - 关键设计：**字段级访问审计**
   - 关键能力：**一次越权尝试能还原到具体字段与操作人，而不是只留一条「某人登录过」**
   - 关键数字：**100% 可查**

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| **「**4 业务统一分级**」** | 未建设 | 已覆盖 | **新增能力** |
| **「**GDPR 合规**」** | 弱 | 100% | **∞** |
| **「**等保合规**」** | 弱 | 100% | **∞** |
| **「**出境违规**」** | 基线 | 0 | **-100%** |
| **「**脱敏覆盖**」** | 40% | 100% | **+150%** |

| **「**审计可查**」** | 60% | 100% | **+67%** |

**具体数字（How much）**

- 团队规模：字节数据安全团队 100+ 人
- 关键数字：**4 业务统一**；**双合规 100%**；**出境 0 违规**
- 业务影响：覆盖**字节全部业务 + 全球**

**失败教训**

- 早期「**各业务各自分级**」——同一份数据在抖音是秘密、在头条是内部，跨业务共享时无从判断，倒逼**「4 业务统一分级」**
- 「**国内外数据想打通**」——触碰 data residency 红线被迫返工，倒逼**「设计之初就分区」**
- 「**共享无水印**」——数据泄露后无法定位来源、追责无据，倒逼**「隐式水印」**
- 「**用户同意状态不参与访问判断**」——拿到数据后才发现没有合法依据，倒逼**「把同意管理做成访问的前置条件」**

### 2.4 某云厂"**多租户安全隔离 + 100 万企业 8+ 年**"（2016-2024）

**背景（Why）**

该云厂 2016 年面临**多租户安全**：
- **100 万+ 企业**——**租户间必须强隔离**
- **合规资质**——**等保 / SOC2 / ISO27001**
- **客户审计**——**随时可能来查**

**触发点（What）**

2016 年该云厂启动**多租户安全隔离**（[案例 2016]），目标：
- **租户间 0 越界**
- **资质全通过**
- **客户审计 100% 通过**

**详细做法（How）**

该云厂数据安全的**5 大核心组件**：

1. **三层隔离（核心创新）**
   - 关键设计：**逻辑隔离（默认）→ 物理隔离（高敏）→ 专有云（金融）**
   - 关键能力：**按客户等级分层**
   - 关键数字：**3 层**
   - 关键示意：
     ```
     逻辑隔离（共享集群 + 租户 ID 强约束）
       → 99% 客户
     物理隔离（独立数据库实例 + 独立密钥）
       → 大型 / 敏感客户
     专有云（独立机房 + 独立运维）

     ```

2. **租户密钥隔离（核心）**
   - 关键设计：**每租户独立 KMS 密钥**
   - 关键能力：**单个租户密钥泄露不波及其他租户，爆炸半径被限制在一个租户内**
   - 关键数字：**100% 独立**

3. **强约束防越界（核心）**
   - 关键设计：**查询强制注入租户过滤，编译器层校验**
   - 关键能力：**技术上不可能越界**
   - 关键数字：**0 越界**

4. **合规资质（核心）**
   - 关键设计：**等保 2.0 / SOC2 / ISO27001 / PCI-DSS**
   - 关键能力：**资质覆盖国内外主流监管框架，To B 客户准入不再卡在「资质不全」上**
   - 关键数字：**10+ 资质**

5. **审计与取证（核心创新）**
   - 关键设计：**全量操作审计 + 一键取证**
   - 关键能力：**客户审计随时过**
   - 关键数字：**100% 通过**
