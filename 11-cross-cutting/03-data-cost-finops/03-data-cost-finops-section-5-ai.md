## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单最根本的毛病是**没有时间维度**。本节的三级判据必须可核验，**判据有三条**：**①** 该能力有**正式 release note 或官方文档条目**（不是博客、不是发布会 PPT）；**②** 有**第三方（非厂商）的公开生产案例**（建设方自述、产品页演示、白皮书里的示意都不算）；**③** **接口稳定**（不因版本升级改写调用方）。三条全中才是 L1，缺任一条就往下判。

| 级别 | 判据（三条全中） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 正式 release note / 官方文档条目 ② 第三方（非厂商）公开生产案例 ③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用，但接口或生态未稳，或只有建设方自有案例，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

成本主题还有一个其它主题没有的坑：**这一节的「前沿」几乎都不是新机制，而是新计费单元**。主文件 §2.2 把月度总成本写成存储、计算、查询、网络、运维五项之和，而 §7.3.3 指出账单真正对哪个变量积分决定了哪根杠杆按下去有收益。GPU 负载带来的不是第六项成本，而是**一个新的计费单元（GPU·小时，或按秒）**，以及随之而来的一整套分母问题。因此判断一个方向值不值得投入，第一个问题不是「它先不先进」，而是：**它改变的是成本函数里的哪个变量——单价、用量、利用率的分母，还是归因粒度？** 只改了账单展示方式的，是接口改良，不是成本结构变化。

第三个要先说清楚的写法差异：本节对以既成事实语气写下的**全部九条厂商进展与学术进展**（按时间排列）采取了**降档或改写为判定入口**的处理——「2024 NSDI Karpenter 论文」「2024 VLDB Lakehouse 查询成本优化」「2024-03 Snowflake Adaptive Compute」「2024-06 Databricks Serverless SQL（无服务器查询）」「2024-09 Karpenter 1.0 GA，支持 GPU」「2024-12 阿里云成本大脑」「2025-Q1 AWS Compute Savings Plans for ML」「2025-Q2 字节开源 CloudEon」「2025 SOSP Serverless GPU 调度」。**这不是断言它们不成立，而是本节给不出可供读者复核的正式出处**；在给不出出处的情况下，正确的写法是给出**查哪一版 release note / 哪一份官方定价页可以自行核验**，而不是把结论写成语态完成的事实。同一个产品名在不同时期可能指不同能力（例如主文件 §1.4 记的是 2022 年的「Adaptive Warehousing」，与「Adaptive Compute」并非同一处命名），**请以各产品官方文档的当前版本为准**。

本节把方向按「它们改变成本函数里的哪个变量」重新归类——改单价与容量的（池化、可回收容量）合成一个方向，Serverless 因计费单元不同在 5.1 单列一行，改单位请求成本的（量化、蒸馏、批处理、缓存）合成一个方向，改归因粒度的（编排与作业级归因）合成一个方向，改输入上下文的（RAG 及其缓存与路由）合成一个方向；而**成本预测与自适应降本不改变上面任何一个变量**——它们既不改归因粒度，也不改单价、用量或利用率的分母，卡点是「谁有权拦下一笔支出」，因此只能收在归因那一节里作反面（见 5.2.3、5.5）；碳排放与能耗、边缘计算降本、成本可见性实时化、统一 FinOps 平台这类提法则不各自构成一个独立变量——碳排放放在 5.3 的接口表里，统一 FinOps 平台里的跨云与 Serverless 计价部分放在 5.7，边缘计算降本在 5.1 的表里保留为一条单独的降档行，成本可见性实时化写进 5.2.3 的机制讨论。**合并的判据是机制，不是名称**——两个名字不同但改变同一个变量的条目，放在一起才能看出它们在争抢同一笔预算。

按这三条判据，本主题下的方向分布如下。表里的判据栏写的是**读者自己去核的动作**，不是结论：

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| GPU 资源池化与时分复用（统一池 / MIG·MPS 切分 / 队列共享） | **L2** | ① 云方 GPU 实例与 K8s 设备插件的 GA 文档齐备；③ 接口稳定；② 卡在缺非厂商的公开利用率实测——**池化的收益高度取决于作业形态**，没有第三方可复核的口径 | 做 PoC：先小池化一个团队，把「池化前后同一批作业的完成时长」量出来再谈扩大 |

> **本主题下没有任何方向进入 L1**，包括看上去最「成熟」的推理优化与作业级归因。判据①与③多数满足，卡住的是②：本节给不出**非厂商的、可被读者复核的公开生产案例**——注意这不是说它不存在，而是说本节给出的指向不足以让读者复算，按 5.1 的判据只能判 L2。**离 L1 最近的是「训练任务使用可回收容量 + 结束即释放」与「推理单位成本的四类杠杆」**：两者都不需要新原理，唯一缺的是把收益量到数字上；把「池化前 / 池化后同一批作业的完成时长与 GPU·小时」「量化前后同一评估集的质量差与吞吐差」这两组数公开写出来，是这两条**能被第三方复核**的前提——**自测记录本身不是第②条要的第三方（非厂商）公开生产案例**，它回答的是另一个问题：这两条方向的可核验收益到底存不存在。**本节宁可全部标 L2，也不为了让表格好看而放宽第②条**——成本决策直接对应预算，虚高的成熟度评级在这里比在别处更贵。

**主表只列「演进方向」；不占主表级别格的条目，去向与级别在这里交代**：「Serverless 推理」（Modal、Replicate、Anyscale Endpoints 等；另见 §5.7「已在用 Serverless 推理 / 托管推理」一行）与「AI 工作负载编排」（Ray、KubeFlow、Metaflow、SageMaker、PAI、字节 MLP；纳管的四类对象与其引擎——训练 TensorFlow / PyTorch、推理 Triton / vLLM / TGI、数据处理 Spark + GPU、Notebook Jupyter）已在主表各占一行（均 L2），后者的拆解见 §5.2.3；其余逐条落点——**可持续计算**（碳排放与能耗进入成本因子）放在 §5.3 的接口表（「碳排放 / 能耗 ↔ 成本因子」一行，L3）；**统一 FinOps 平台**（跨云 + 跨工作负载）拆在 §5.3 与 §5.7（「多云 / 多账号」一行，L2）；**成本可见性实时化**（T+1 月度账单 → T+1 小时看板）写进 §5.2.3 的机制讨论（L2）；**「GPU 池化普及」「AI-Native FinOps」等提法**收在 §5.5（第一条、第二条，L3）；**「Serverless 成为默认」**落在 §5.7（L2，它是容量来源的一种选择，不是默认）。

**这三级的排法直接决定预算的顺序**：L2 的行要立项做 PoC，并且**立项时就把验收数字写进方案**（否则 PoC 会退化成一次演示）；L3 的行不要排期，只在架构评审记录里留一条「如果它成真，我们要改哪里」。级别不是标签，是投入决策——与 §3.2.6 的预算护栏同一条逻辑：**控制点要放在花钱之前**。

**级别要定期回填**：某个 L2 方向如果出现了非厂商的公开生产案例，就升 L1；某个 L3 方向如果一年后还只有产品页与发布稿，就继续保持 L3 并停止投入。回填的动作是**每次架构评审顺手做一次**，而不是每年做一次大盘点——成本的判据会随产品版本与定价变化，一年一评的结果是评审当天用的还是去年的印象。这也是本节把判据写成「读者自己去核的动作」而不是「结论」的原因：结论会过期，动作不会。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向都按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。六个字段缺一不可。只写「得到」不写「付出」的方向应当被直接打回，因为成本领域里没有不付代价的降本。

#### 5.2.1 GPU 资源池化与可中断容量：把「独占算力」改成「按队列共享 + 可回收」

- **旧做法与它的卡点**：这一族是「每团队独占 GPU 集群 → 利用率低；统一 GPU 池 + 动态分配 → 利用率高」，工具点名 Karpenter + GPU Operator、NVIDIA GPU Operator、Run:ai、Determined AI、阿里云 PAI 灵骏、字节 Velo。卡点不在「能不能池化」，而在**GPU 的稀缺性让「共享」与「隔离」直接冲突**：CPU 时代的池化默认「一次分配、按时归还」，而 GPU 上跑的训练作业一旦被抢占，没有 checkpoint 就等于从头再来；推理服务则对显存有硬性下限，切得太碎会直接 OOM。主文件 §2.2 的成本模型里 $U_j$ 是利用率，**GPU 的 $U_j$ 与 CPU 的 $U_j$ 不是同一个东西**——它的分母（一张卡的算力与显存）不可再分且不可超卖。
- **AI 改变了什么机制**：**它把「按容量采购」变成了「按队列共享 + 按可中断性分级」**。真正的新事实不是池化本身，而是**负载被按「中断一次要付多少重算」重新分成两类**——**可中断的（有检查点的训练、可重跑的离线批推理）**与**不可中断或重算代价过高的（没有检查点的长单步训练、在线推理）**，而这两类在同一张卡池上的正确处置方式完全相反：前者应尽量往可回收容量里塞，后者要么走按需 / 预留，要么保证最小副本并接受冷启动代价。
- **由此得到的**：**因为有检查点的训练是批式负载、且检查点让中断的代价可被限定为「退回上一个检查点」而不是「全部重算」，所以这一类训练可以整体搬到可回收容量上（没有检查点的长单步训练不能，它只能走按需或预留，见下表），把省下的钱按 §3.2.4 的采购组合逻辑重新分配**；**因为 MIG 把一张卡的算力和显存切成固定档位，所以多个低负载任务可以共享一张卡**——它改变的是成本核算的**分母**。落到工程上就是两条默认策略：任务结束即释放（不挂在人身上）、推理服务设最小副本数并接受冷启动代价（[§3.5](03-data-cost-finops-section-3-sec3.md) 把「忽略 GPU 成本」列为反模式，其修法正是流程性的）。
- **由此付出的**：三条真实代价：**其一，池化把「资源独占」换成「排队与抢占」，交付时间的方差变大**——池化提高了平均利用率，也提高了「我的任务什么时候能跑完」的不确定性，这一点必须写进 SLA 而不是藏进调度器；**其二，可回收容量的中断通知窗口只有分钟级**，这点时间只够优雅退出与保存检查点，不足以把任务搬到别处重跑，所以它只能承接「可中断且能续跑」的负载；**其三，切分共享引入新的故障模式与新的计价口径**：显存被邻居占满时的 OOM 与整卡独占时的 OOM 不是同一回事，排查路径完全不同，而账单上仍是一张卡的钱——如果归因只做到实例级，你会看到「这张卡很忙」却说不清忙在哪个作业上。
- **证据与来源**：按秒/按小时计费与可回收容量的官方口径可核验：**Spot 类实例的中断通知窗口是云方正式文档条目**（【公开】AWS EC2 用户指南 · Spot 实例中断通知，该口径自 2015 年前后在多版本文档中一致；请以当前版本为准）；**MIG 的可用切分档位以厂商的 MIG 用户指南 profile 表为准**——A100 一代存在把一张卡切成 7 份的档位，但可用档位与显存切分随卡型与驱动版本不同（【公开】NVIDIA MIG 用户指南，请以官方文档当前版本为准）。**GPU 池化后的利用率提升幅度本节不给数字**：它取决于作业形态与共享比例，任何脱离「池化前后的同一批作业完成时长」的利用率声称都无法复核，故本方向判 L2。
- **成熟度**：**L2**。判据：① 与 ③ 成立（弹性伸缩与设备插件的接口稳定），② 缺非厂商可复核的公开实测；**判定方法是自己在账号里做一次对照实验**——同一批作业在独占与共享两种形态下各跑一遍，比完成时长与 GPU·小时，而不是比控制台里的利用率数字。

| 负载类型 | 正确的容量来源 | 中断的代价 | 谁定义可中断性 |
| --- | --- | --- | --- |
| 训练（有 checkpoint） | 可回收容量为主，按需兜底排队 | 退回上一个检查点 | 算法/训练负责人（检查点间隔是他们的决定） |
| 训练（无 checkpoint / 长单步） | 按需或预留 | 全部重算 | 同上，且这一条决定了它进不进池 |
| 离线特征回填 / 批推理 | 可回收容量 | 可重跑 | 数据负责人 |
| 在线推理 | 预留 + 最小副本；突发部分才走按需 | 请求失败或排队 | 业务方（哪些请求允许降级到小模型，由业务按请求类型定） |

表里的「谁定义可中断性」一列是本节最容易被跳过的一列，也是最容易出事的一列：**平台只能执行承诺，不能代替业务做承诺**。把「这个任务可中断」写成平台默认值，等于让调度器替业务判断「这次中断的代价可以接受」——而调度器不知道这批数据是不是当天要交付、这个请求是不是监管留痕的一部分。

关于切分共享还有一处常见的混淆要分清：**MIG 与 MPS 解决的不是同一个问题**。MIG 是在硬件层面把一张卡划成若干个带独立显存边界的实例，隔离强、粒度粗（档位是固定的几张表）；MPS 是把多个进程的 CUDA 上下文合并到同一张卡上共享执行，隔离弱、粒度细，适合**互相信任、都跑不满却都占显存**的推理进程。判断你的场景该用哪个，问一句「**这些负载之间互相算得清账、也互相赔得起吗**」：赔不起就用 MIG，赔得起才考虑 MPS——这不是性能选择，是故障隔离与归因粒度的选择。

```text
        账面「在用份数」由 1 变成 7【推算：7 ÷ 1 = 7】
        但整卡的算力与显存并未增加 —— 变化的是分母，不是产出
  ────────────────────────────────────────────────
  用法：情形 A 的数是「可以真省下来的钱」，情形 B 的数只是
        「同一笔钱换了个记法」。要降本，先找 A 那一类；
        要展示成果，B 那一类会让报表很好看（见 5.5 第一条）
```

#### 5.2.2 推理单位成本的四类杠杆：量化、蒸馏、批处理、缓存

- **旧做法与它的卡点**：Serverless 推理、模型量化（FP16 / INT8 / INT4）、模型蒸馏、动态批处理、KV Cache 复用（其中 Serverless 推理本质上是**容量来源**问题，已在 5.1 的表里单列一行、并在 5.7 里收口，本节只评估余下四条）。卡点是：**这四条的收益函数完全不同，却被并列成同一张清单**。量化改的是**每 token 的计算/显存成本**，蒸馏改的是**模型本身**（并因此改变输出质量），批处理改的是**同一份算力服务多少并发请求**，缓存改的是**重复请求被消掉的比率**。把它们当成同质的「优化手段」，最常见的后果是**只做了最容易做的那一条（量化），然后宣布推理成本已优化**，而真正的成本大头（低命中率下的重复 prefill、单请求串行）从未被触碰。
- **AI 改变了什么机制**：**这四条杠杆里有三条是既有的通用机制搬到了生成式负载上**——量化在传统机器学习里就是模型压缩（把权重从高精度降到低精度，这次只是搬到了 LLM 权重上），蒸馏在传统机器学习里同样属于模型压缩（换一个更小的模型，而不是压同一个模型的位宽），批处理在传统在线服务里叫合并请求；**真正因生成式负载而多出一层新做法的，只有缓存这一条**：生成式推理把一次请求拆成 prefill（读输入）与 decode（逐 token 生成）两段，而这两段的成本结构截然不同——prefill 可被共享前缀整段消掉（这正是 KV / 前缀缓存能生效的原因），decode 则与输出长度成正比、几乎无法复用，于是缓存除了原有的「缓存整个请求的结果」这一层，又多出「缓存输入里反复出现的那段前缀」这一层。**这条「两段可分别优化」的性质，是生成式负载区别于传统推理的真正新事实，也是四条杠杆里唯一一条生效方式被它改写过的。**
- **由此得到的**：**因为 prefill 的成本只取决于输入、且同一前缀在多次请求中重复出现，所以前缀缓存把「重复读同一个系统提示与知识片段」的成本从每次请求付一次变成命中一次付一次，节省比例约等于共享前缀在输入中的占比【推算：省下的 = 命中前缀 token 数 ÷ 总输入 token 数】；因为 decode 与输出长度成正比，所以压缩输出长度（更严格的格式约束、更短的默认回答）对成本的杠杆与压低输入同等重要，而这一点在「优化 prompt」的讨论里常被忽略。** 同理，**因为量化把每个权重的比特数降下来，所以权重体积按位宽线性缩小——FP16 换 INT8 是减半，换 4 bit 是降到四分之一**（【推算：16 ÷ 8 = 2，16 ÷ 4 = 4】），这直接降低了显存占用，从而影响「一张卡能装几个实例 / 多长上下文」——**注意它影响的是容量与并发，未必等价于单位请求成本下降**，后者还要看它是否真的提升了吞吐。
- **由此付出的**：三条代价：**其一，量化与蒸馏都会改变输出分布**——质量损失在通用基准上往往看不出来，却会在你自己的评估集上显现，尤其是长尾、格式严格、需要精确数字的任务；**其二，批处理把延迟换吞吐**，动态批处理会引入排队的尾延迟，而尾延迟在交互式场景里本身就是成本（用户等不及就重试，重试就是双倍成本）；**其三，缓存引入一致性责任**——前缀缓存与响应缓存都必须在「上下文变了」时失效，失效做错的表现是**用户看到过期答案**，这类问题的排查成本远高于它省下的算力费。
- **证据与来源**：机制侧有公开论文可核验：PagedAttention 把 KV 缓存的分页管理与请求调度写成了可复现的系统设计（【公开】Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention", SOSP 2023）；量化侧的后训练量化方法有公开论文（【公开】Frantar et al., "GPTQ: Accurate Post-Training Quantization for Generative Pre-trained Transformers", ICLR 2023）。**「量化后速度快 2–3 倍」「蒸馏成本降 10 倍」「KV Cache 省 50%+ 算力」这三类数字本节不引用**：它们没有条件（模型规模、批大小、硬件、输出长度、质量约束），无法复核。可用性判据是**你自己的评估集**：同一组输入跑优化前后，比质量差与 tokens/秒，两个数一起看。
- **成熟度**：**L2**。判据：① 公开论文与开源实现齐备、③ 推理引擎接口稳定，② 缺非厂商可复核的生产案例（各家流量形态差异太大，别人的收益换不到你身上）；**并且这里有一条硬性提醒——任何一项优化在没有评估集之前不要上线**，否则省下的钱可能小于质量下降带来的业务损失，而后者往往不进成本账单。

| 杠杆 | 它改变成本函数里的哪一项 | 必须一起观测的反向指标 | 判定它是否值得做的动作 |
| --- | --- | --- | --- |
| 量化（INT8 / INT4） | 每 token 的显存与算力需求 | 评估集上的质量差 | 同一评估集跑前后对比；质量不可接受的档位直接弃用 |
| 蒸馏 | 换成更小的模型 | 输出分布的变化（能否被业务接受） | 按请求类型分级：哪些请求允许走小模型、哪些必须走主模型 |
| 连续/动态批处理 | 同一份算力服务的并发数 | 尾延迟（P95 / P99） | 压测出「批大小 vs 尾延迟」曲线，取业务可接受的最优点 |
| 前缀 / 响应缓存 | 重复输入被消掉的比率 | 缓存命中率与失效正确性 | 先测命中率；命中率低于阈值时，缓存的运维成本会超过它省的钱 |

**做这四条的顺序比做哪一条更重要**：先测**成本项占比**（哪一段是大头），再测**缓存命中率**（重复请求占多少），然后才是**批处理**（尾延迟吃不吃得下），最后才是**量化与蒸馏**（要动权重或换模型，回退成本最高、质量风险也最大）。反过来做——先量化、再想缓存——会出现一个很常见的局面：权重体积小了一半、显存宽裕了，但请求里绝大部分输入 token 仍要每次重算，账单几乎没动，而团队已经宣布「推理优化完成」，后续真正的杠杆反而没人再提。**这条顺序的判据不是「哪条技术更先进」，而是「哪一条的回退成本最低」。**

这四条杠杆还有一个共同点值得单独说：**它们全部作用在「单位成本」上，而账单还取决于「量」**。推理请求量翻倍时，把单位成本压掉三成只能抵消一部分增长——**降本与控量是两个独立的杠杆，本节只讨论前者**；后者属于业务与产品决策（限流、降低调用频率、把对话式交互改成一次性任务），不在工程可控范围内，但评审时必须有人明确说出来，否则「优化完成、账单仍在涨」的局面会被误读为工程没做好。

#### 5.2.3 编排与作业级归因：先把账拆到作业，再谈自动降本

- **旧做法与它的卡点**：用 K8s 统一管理训练、推理、数据处理、Notebook（工具点名 Ray、KubeFlow、Metaflow、SageMaker、PAI、字节 MLP）与成本预测、AI 自适应降本。卡点正是主文件 §1.2 里的「算不清」：**成本治理在 CPU 时代已经能拆到作业与频次（§6 的字节案例把归因做到了「作业 × 调度频次」），而 GPU 负载目前多数只做到实例级**——一张卡被多个作业轮流用，账单上只有一行「这台实例跑了 720 小时」，于是「哪个作业贵」这个问题在 GPU 上重新变成了未解问题。**AI 新引入的不是编排能力，而是编排对象换了以后归因链断了一节。**
- **AI 改变了什么机制**：**它把「资源被谁用」这个问题的难度从「作业级」抬回「作业 × 卡 × 时段级」**。因为一张卡可以在同一小时内先后服务多个作业、也可以被切分成多份同时服务多个作业，**归因的最小单位从「实例小时」变成了「GPU·小时 × 作业」**，而后者要求调度器把「谁在这段时段持有这几份算力」记录下来——这是编排层新增的一件必须显式做的事，不会自动发生。
- **由此得到的**：**因为归因粒度决定了优化动作能不能落到具体的人身上（§6 阿里案例的第一条经验就是「从平台总账拆到业务分账」），所以在 GPU 上补上作业级归因，是让后续所有降本动作可执行的前置条件**——没有它，「把结余写进 OKR」这条最有效的机制在 GPU 上根本挂不上去。落地上不必等平台：先按「作业名 / 队列 / 团队 / 用途」四类标签把 GPU 负载登记起来，把标签缺失的用量在看板上单列成「未分配」，**仅仅是让未分配项可见，通常就能消掉一批无人认领的用量**。
- **由此付出的**：**其一，归因标签是新增的常驻人力**——[§7.4](03-data-cost-finops-section-7-sec7.md) 已按量级估过：单个计费口径下的规则维护与月度对账大致占用一名工程师每年的一到三成【经验】，叠加资源类型带来的增量后量级在 1 人年上下【推算：3 个计费口径 × (0.1~0.3) = 0.3~0.9 人年，再加资源类型带来的增量，量级落在 1 人年；推导见该节】，且这份人力不随成本规模缩小；GPU 是新增的第 N 类资源，它会让这份人力再上一档。**其二，「成本预测」与「自适应降本」把控制权交给了模型，而模型的误判在这种场景下没有便宜的兜底**：预测偏低导致预算不够，预测偏高导致过度预留；这两类错误的代价不对称，而公开渠道里没有可核验的预测误差评测。**其三，自动缩放对 GPU 的收益是有上限的**：缩容到零省的是闲置费，代价是冷启动与权重加载——这条下限由 5.2.1 的队列与制品加载时间决定，不因调度器更聪明而消失。
- **证据与来源**：机制侧属既有工程（标签归因与预算护栏见 [§3.2.1 与 §3.2.6](03-data-cost-finops-section-3-sec3.md)，成本函数对哪个变量积分见 [§7.3.3](03-data-cost-finops-section-7-sec7.md)）；云方成本与用量明细接口是 GA 的正式能力（【公开】各云的成本管理 API 文档，如 AWS Cost Explorer / Cost and Usage Report，请以官方文档当前版本为准）。**「LLM 预测月度成本」与「AI 自适应降本」两条没有公开可核验的第三方评测**，故判 L3；编排组件（Ray、KubeFlow、Metaflow、SageMaker、PAI 等）都是 GA 产品，**但「某个组件是否支持把 GPU 时长按作业切分归因」因产品与版本而异，本节不做断言**——判定方法是查它文档里有没有「按作业/按命名空间的加速器时长指标」，而不是看它有没有 GPU 调度能力。
- **成熟度**：**作业级归因 L2**（机制现成、②缺公开案例）；**成本预测与 AI 自适应降本 L3**（只有产品页与发布稿）。两者的差别正是 5.1 判据的用处：前者你可以今天就开始做并拿到可复核的数，后者的收益要先依赖一个未被验证的假设。

判断「编排层有没有真的把归因做出来」，有一个不依赖任何产品文档的检验动作：**随便挑一个作业，问「它上个月花了多少 GPU·小时」**。答案来自控制台里某个总数字、需要人工估算，或者干脆答不上来，说明归因链断在编排层；答案来自一条按作业聚合的记录、且这条记录能被人拿来跟自己的用量核对，才说明它接上了。**这个检验动作之所以有效，是因为它绕开了「支持按作业归因」这类能力描述——能力描述无法区分「能查到」与「能被用来对账」。**

还有一条要在这里收口：**「成本可见性实时化（T+1 月度账单 → T+1 小时看板）」**。它必须拆成两件事看——**小时级明细是云方计费接口既有的能力**，属能力可用性问题；而**按作业归因是自建的工作**，属责任归属问题，本节整段讨论的都是它。把看板从月频改到小时频，**改变的不是成本函数，而是发现异常的时点**：它把「月底对账才知道超支」提前到「当天就能看到」，所以值得做；但它的收益上限是「少花在已经发生的事上」，把它算进降本收益表就是虚报。判定方法很直接：**这套看板能不能在花钱之前拦住任何一笔支出**——拦不住的，它是可见性建设，不是降本。（5.5 结尾说的「把能力上线当成成本下降」，最常见的形态正是这一条。）

#### 5.2.4 RAG 链路的成本结构：四个成本项必须分开计量

- **旧做法与它的卡点**：RAG 成本写成「存储（向量库）20% + 嵌入 10% + 检索 10% + LLM 推理 60%」四段比例，并给出五条优化（向量库分层、Embedding 缓存、检索结果缓存、LLM 推理缓存、RAG 路由）。卡点有两个：**这组比例没有条件**（模型、上下文长度、缓存命中率、批处理、语料规模都会改变它，脱离条件的比例无法复核，本节不作为事实引用）；**更重要的是四个成本项的可优化空间完全不对称**——生成段通常是大头，而它的大小由「检索回来多少上下文」和「输出多长」决定，也就是说，**RAG 的成本结构主要由检索质量决定：召回不准，就会靠塞更多上下文来补救，成本转嫁给生成段**。
- **AI 改变了什么机制**：**它把一个「存储成本问题」重新表述成「上下文预算问题」**。传统检索的成本主要落在存储与索引；RAG 里多了一层放大器——**每一条被检索出来的片段都会在生成时变成输入 token，并在每次请求里重复付费**（除非前缀缓存命中）。于是「检索到几条、每条多长」从一个召回率参数变成了**成本参数**。GraphRAG 这类多跳检索同样落在这个框架里：它换的是检索段的实现方式，代价是索引构建与维护的额外算力。
- **由此得到的**：**因为生成成本随输入上下文线性增长，所以在固定评估集上把「Top-K 从 N 降到 N/2 而答案质量不变」这件事，收益会直接体现在账单上，且不需要换模型【推算：输入 token 减半 → 输入段成本按比例下降，输出段不变】**；**因为嵌入与检索结果都可缓存，所以命中率的提升等价于这两段成本的按比例下降【推算：省下的比例 ≈ 命中率】**。这两条合起来给出一条 RAG 降本的顺序：**先把计量建起来（四个成本项各自多少），再动缓存与 Top-K，最后才谈换更小的模型**——顺序反了，你会用一个质量下降换一个比重不大的成本项。
- **由此付出的**：**其一，降低 Top-K 与压缩上下文会损失召回**，这类质量损失不会立刻报错，表现为「偶尔答得不对」，因此在没有评估集的组织里它会被长期忽略，直到业务侧投诉；**其二，三级缓存各自引入失效问题**：Embedding 缓存对同文本是安全的（确定性函数），检索结果缓存与响应缓存在权限或语料更新后会返回过期内容——**RAG 的缓存失效做错，等于一个越权数据泄漏面**，这比算力浪费严重得多；**其三，多供应商路由（简单 query 走小模型）把质量分档引入产品**，同一问题的答案会随路由结果而不同，这一点必须与 5.2.2 的档位表用同一套口径定义。
- **证据与来源**：四个成本项的分解方式与缓存分层都是既有工程做法（分层的存储语义与生命周期规则见 [§3.2.2](03-data-cost-finops-section-3-sec3.md)——向量库分层是这套语义在索引制品上的一次应用）；各向量库对「分层存储 / 快照 / 跨集群复制」的支持粒度因产品与版本而异，**判定方法是查你所用产品的 release note 里这几项分别是哪个能力、一致性口径是同步还是异步**。20% / 10% / 10% / 60% 比例**本节不引用为事实**——它缺条件限定，读者要得到自己的比例，方法是按上面四项分别取当期单价乘用量。本方向判 L2。
- **成熟度**：**L2**。判据：① 构成机制均有 GA 实现、③ 接口取决于所选组件；② 缺非厂商公开的 RAG 全链路成本数据。**在拿到自己的四个成本项之前，「RAG 成本优化」不是一个可以立项的工程**。

```text
四个成本项必须分开计量（否则优化会打到比重小的那一段上）
  ① 向量存储   = 索引体积 × GB-月单价 × 副本数
  ② 嵌入       = 新增/回填文本的 token 数 × 嵌入单价
  ③ 检索       = 查询次数 × 每次查询开销（含过滤、重排）
  ④ 生成       = (输入 token 数 + 输出 token 数) × 模型单价
                 └─ 输入 token 数 ≈ Top-K × 每片段长度 × 重复请求次数
                    （重复请求若命中前缀缓存则不重付）
  ────────────────────────────────────────────────
  关键：② 只在写入与回填时发生，是一次性/低频的；
        ③④ 随请求量线性增长，是月账单的主干。
        因此"省钱"的动作几乎都落在 ③④ 的分母上：
        检索几条、每条多长、输出多长、重复请求能不能命中缓存。
        —— 只优化 ① 与 ②，账单曲线不会有明显变化
```

### 5.3 与本主题既有栈的接口在哪

「AI 时代的 FinOps」不是与既有 FinOps 体系「结合」，而是**给既有的成本治理闭环补一个新的资源类型**。判断接得对不对，看三件事：**谁调用谁、数据以什么形态穿过边界、失败时谁负责**。下表里每一行的「现状」都对应 5.1 的某个级别，二者必须一致。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| GPU 负载 ↔ 计费单元（[§7.3.3](03-data-cost-finops-section-7-sec7.md)） | 账单对 **GPU·小时（或按秒）** 积分；归因粒度必须是「作业 × 卡 × 时段」，不是实例小时 | 平台方提供用量明细；作业 Owner 认领用量 | 云方计费接口 GA，可直接接（L2：归因粒度要自建） |
| GPU 负载 ↔ 标签归因与 Showback（[§3.2.1](03-data-cost-finops-section-3-sec3.md)） | 标签规范扩展到 GPU（作业 / 队列 / 团队 / 用途）；标签缺失记为「未分配」并在看板单列 | 平台方保证标签体系可用；Owner 保证打标 | 可立即做，是后续一切动作的前置（L2） |
| 训练 / 推理 ↔ 预算护栏（[§3.2.6](03-data-cost-finops-section-3-sec3.md)） | 提交前估算「GPU·小时 × 单价 × 频次」，超预算阻断或走审批；护栏只阻断，不代写预算 | 提交者；审批通道的责任人 | 机制可复用，**缺的是 GPU·小时估算器**（L2） |
| 闲置与释放 ↔ 弹性计算与生命周期策略（[§3.2.3](03-data-cost-finops-section-3-sec3.md)） | 训练结束即释放挂到流程与调度器钩子上；推理设最小副本并接受冷启动 | 平台方提供默认策略；业务方定义可中断性 | 可立即做，是本主题收益最确定的一项（L2） |
| 向量索引与模型权重 ↔ 分层存储（[§3.2.2](03-data-cost-finops-section-3-sec3.md)） | 索引与权重按访问频率分层；同时必须记录**重建耗时**——它是「能不能只留一份」的判据 | 制品 Owner 负责可重建与版本可追溯；恢复方承担重建耗时 | 可做，但「能不能只留一份」要先实测（L2） |
| GPU 承载 ↔ 采购组合（[§3.2.4](03-data-cost-finops-section-3-sec3.md)） | 承诺折扣只买**稳态底座**，突发与训练走按需 / 可回收容量 | 采购方；业务方承诺负载形态与可中断性 | 可做，前置条件是有 3–6 个月的用量历史【经验】 |
| 成本指标 ↔ 可观测（[Ch11 §04 可观测性](../04-observability/04-observability.md)） | 新增业务指标穿过边界：GPU·小时/千次请求、每万 token 成本、闲置占比、未分配占比 | 平台方提供指标通道；业务方认领阈值 | **需要新建，不是既有指标的复用**（L2） |
| 降本动作 ↔ OkR / 考核（[§ 6 落地实践](03-data-cost-finops-section-6-sec6.md)） | 把「单位产出成本」「利用率」「闲置占比」写进业务方 OKR | 业务方自己；平台方只提供数据 | 机制已被验证有效，但**先要有可信的归因数据**（L2） |
| 碳排放 / 能耗 ↔ 成本因子 | 目前多数云方把能耗放在独立报表里，未与账单合并计费 | 尚无清晰责任人 | 不要为了它改架构（L3） |

```text
成本控制的三个位置，以及 GPU 该放在哪（沿用 §3.2.6 的护栏逻辑；三个位置与 §7.3.2 同名）
  ✗ 事后账单：跑完才知道花了多少 → 钱已花掉，只能"下次注意"
  △ 事前提醒：提交时给出估算与阈值对比，但只提醒不阻断 → 拦不住这一笔，
        只留下记录供事后追责；它买到的是"发现得更早"，不是"少花了"
  ✓ 事前阻断：提交时给出 GPU·小时估算并与预算比对
        ├─ 在预算内         → 直接执行
        ├─ 超预算但有理由   → 走审批（提高额度需说明用途与时限）
        └─ 超预算且可优化   → 拒绝并给出具体建议
  ────────────────────────────────────────────────
  GPU 与 CPU 的差别在"估算器怎么写"：
    CPU 作业：估算 = 扫描量 × 单价 × 频次
    GPU 作业：估算 = 卡数 × 预计时长 × 单价 × 频次
              ↑ 预计时长的方差远大于扫描量，所以栅栏要留
                缓冲，并且必须允许"排队等便宜容量"这条出路
  关键：护栏的价值不在拦住几次，而在让每次提交都必须
        正面回答"这次要花多少 GPU·小时"
```

表里这九行有一个共同的失败形态：**接口接上了，责任人没接上**。归因 API 通了、看板有了、护栏也拦了，但如果「未分配」用量没有明确归属，被拦下的作业会在某个审批通道里被批量放行——**护栏拦的是人，不是资源**。所以每接一条边界的正确顺序是：先写明这条边的失败由谁负责，再谈接入方式；把负责方写成团队名而不是具体 Owner 的，等于没写，因为团队不会收到告警。

另一条容易被忽略的边界是**「可中断性」这个字段本身**：它不属于平台，也不属于调度器，它是业务方对一件事情的承诺——这批流量能不能排队、这次训练能不能退回检查点。上表**第四行**现在就能动手，前提正是这份承诺已经被显式写下来（写在哪不重要，写下来才重要）；**第一行**的前置是作业 Owner 认领用量的承诺；**第六行**（采购组合）同样依赖「业务方承诺负载形态与可中断性」，但它有自己的前置条件——**3–6 个月的用量历史【经验】**，没有这段历史就定不出承诺折扣的基数，这两个条件不能互相替代。**没有这些承诺，池化与可回收容量带来的收益会在第一次抢占事故后被全部收回**，因为团队会要求把独占资源还回来——这也是 [§3.5](03-data-cost-finops-section-3-sec3.md) 那类反模式的典型收场：一次误伤否掉整套治理动作。

**第三方生产案例**

- 说明：本方向下，本节**未列出**符合 5.1 判据②的公开案例——这与 5.1 表里没有任何一行进入 L1 是同一件事。**证据的缺口本身是本节结论的一部分**：成本类前沿方向如果连第三方可复核的实测都拿不出来，那么「能不能现在就用」这个问题只能由你自己的对照实验回答（5.7 给了三个必须先量的数）。

**这条缺口怎么补**：本节不给「暂时缺证据就先放着」的结论，因为成本方向与容灾、血缘那类方向不同：**它的收益可以在一个季度内被自己的账单验证**——判断要不要追加投入，不必等第三方；但**能不能标 L1 是另一回事，判据②并不因此松动（见本段末）**。补法的固定形状是：选定一批作业或一段流量 → 记录优化前的 GPU·小时与产出指标（完成时长 / 质量分 / tokens 每秒）→ 只做一项改动 → 再记录一次 → 把两组数写进评审材料。**这一份材料是两样东西：本次决策的依据、下一项优化的基线。**换言之，本主题的成熟度评级里，「第三方案例」这一条**不会**因为你自己做了一次对照实验就被满足——**自己的对照实验属于建设方自述，按 5.1 的定义不计入第②条**；它回答的是这个方向在你的负载上究竟有没有收益、值不值得追加投入。但前提是它必须被记录下来，否则连这个问题也答不了，只能停在「我们感觉省了不少」。

**这份清单的用法**：它不是「读完就能上生产」的路径，而是一组**判定入口**。遇到任何「某平台支持 GPU 成本治理」的说法，先问它的证据属于上面哪一类——是论文里的机制、是官方文档里的正式条目、还是产品页上的一句能力描述；三者对应的成熟度差一个量级，而这正是 5.1 里 L1 / L2 / L3 的区分依据。清单刻意很短：**清单短不是资料少，是合格证据少。**

### 5.5 被过度宣传的部分

下面三条不是唱反调，而是把**被宣传的能力**与**公开证据支持的能力**分开写。判断标准固定：宣传句里有没有可核验的条件（数据规模、口径定义、成本结构与质量指标的对照）——没有的，就归入下面三条。

**「GPU 池化把利用率从 20–30% 提到 70%+」**——实际变化的是**分母**，不是产出。原因：场上的「利用率」至少有三种口径——显存占用、SM 活跃度、以及「卡被某个作业持有」的时长占比；池化最容易提升的是第三种，因为共享让「持有」不再要求「真在用」。把一个 5% 负载的作业和七个同样的作业塞进一张卡，持有率与账面利用率都会很好看，而**算力总产出没变、账单也没变**。真要看池化有没有省钱，只有一个口径：**同一批作业，池化前后的完成时长与 GPU·小时**。**它什么时候才能被当作成果**：当云方或平台方公开给出「按作业 × GPU·小时」的用量明细，并且你拿它算出的节省额与本季度账单的下降额对得上——在此之前，利用率是从报表里可以任意打扮的量。

**「AI 自动降本 / LLM 预测成本，就能把钱省下来」**——实际卡住的不是预测精度，而是**权限与责任**。原因：§6 的两个案例（阿里把成本写进业务 OKR、字节把预算做成硬约束）说明能真正省钱的动作只有两类——**有人认领这笔钱**，以及**花出去之前被拦住一次**；「推荐一个优化项」既不改变认领关系，也不改变放行条件，所以它多半会变成一份没人执行的建议清单。**它什么时候才会成真**：出现把预测结论绑定到**无副作用的动作**上的产品（例如自动降冷、自动缩短保留期、自动把可中断作业转入便宜容量），并且公开给误判率——只给「预计可省 X%」而不给误判代价的，不算。

**「量化 / 蒸馏 / 缓存能让推理成本降 N 倍」**——实际是**四类杠杆被合并成了一个数字**，而这个数字没有分母也没有质量约束。原因：量化改的是权重体积（影响并发与容量），蒸馏改的是模型（影响输出分布），批处理与缓存改的是重复请求的比率；四者的收益彼此不叠加、且各自都有反向指标（评估集质量差、尾延迟、缓存失效正确性）。**它什么时候才会成真**：当报告者同时给出「评估集上的质量差」与「tokens/秒」，并说明流量形态与硬件——**只有收益没有质量数据的优化报告，在成本评审里应当被直接退回**。

这三条的共同结构是：**被宣传的都是「省下了多少」，而可核验的都是「在什么条件下、付出了什么」**。评审任何 AI 降本方案时先问一句：**这个数字的分母是什么？** 分母说不清的，先按 0 计。

还有一类说法本节没有单列，但同样要提防：**把「能力上线」当成「成本下降」**。「平台支持 GPU 池化」「工具支持成本归因」描述的是能力的可用性，不是你的账单会怎样变化——两者的距离由 5.7 的对照实验来填。**判断口径很简单：任何降本声称，如果没有同时给出「改动前」与「改动后」两组可比的数字，它就还停留在能力描述阶段。**

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 通用 FinOps 工具会在三年内补上「按作业 × 加速器时长」的归因能力，GPU 成本不再需要自建看板 | 主流第三方 FinOps 平台的产品文档里出现加速器/作业级归因条目，并有非厂商客户的公开使用说明 | 三年后 GPU 归因仍需自建，通用平台仍以实例与服务为中心 |
| 「GPU 利用率」这个指标会从成本报表里被淘汰，取而代之的是「每千次请求的 GPU·小时」这类产出分母 | 云方或平台方的成本看板默认提供产出分母类指标；行业文章开始讨论利用率口径的定义分歧 | 利用率仍是唯一口径，且不同产品对它的定义继续不一致 |
| 成本预测类 AI 能力的定位会从「省钱」降级为「预算偏差预警」，不再被当作降本手段 | 产品宣传从「预计可省 X%」转为「预算偏差预警与归因」；公开材料开始给出误判率 | 出现以「AI 自动降本」命名、并被第三方生产案例验证的独立品类 |
| 训练侧的可中断化会成为默认设置（检查点 + 可回收容量），无检查点的长训练变成需要解释的例外 | 主流训练框架与托管平台的默认模板自带检查点与抢占处理；招聘与评审里开始把「能不能被抢占」当默认假设 | 数年后仍普遍出现「训练中断即从头再来」的案例，可回收容量只用于非关键任务 |

写这四条时的共同约定：**信号必须是外部可观察的**（出现在产品文档、release note、公开案例里），而不是「我觉得会」。凡写不出证伪信号的判断，本节不写——它没有信息量。

**这四条的用法不是「等」，是「留痕」**：把上面每一行的「会成真的信号」抄进你所在团队的架构评审模板，每次评审时用一句「本季度是否观察到」过一遍。做这件事的成本接近零，收益是**当信号真的出现时，你手里有一条已经讨论过半年、写清了要改哪里的记录**——而不是从零开始立项。反过来，如果某条预测连续四个季度都只有「证伪信号」出现，那就把它从观察清单里划掉，别再为它预留设计——**可证伪的预测之所以有信息量，正是因为它允许被删掉。**

### 5.7 给架构师的行动建议

下表按「你的处境」分行，而不是按技术分行：同一项技术在已有 FinOps 体系与刚起步的团队里，正确动作完全相反——前者要接管道，后者要先建口径。

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有 FinOps 体系、还没管 GPU | 把 GPU·小时接进现有的标签归因与 Showback；标签缺失记为「未分配」并单列 | 观察「未分配」占比是否随季度下降——它降不下去说明治理没落地 | **不要新建一套并行的 GPU 成本体系**；不要把「利用率」当验收指标 |
| 训练为主、成本增长最快 | 训练结束即释放挂到流程上；把可中断性写进作业模板并配检查点 | 观察闲置 GPU·小时占总量的比例 | 不要把「训练结束即释放」挂在人身上；不要承诺没有实测支撑的池化收益 |
| 推理为主、成本与流量同涨 | 先建四个成本项的计量，再谈优化；同时建一个质量评估集 | 观察缓存命中率、尾延迟、每千次请求的 GPU·小时 | 不要在没有评估集时上线量化或蒸馏；不要用降质换比重很小的成本项 |
| 自建 RAG | 把「输入 token 数」当成成本参数来管：调 Top-K 与片段长度要看账单 | 观察检索段与生成段成本占比的变化 | 不要让检索结果缓存与响应缓存在权限变更后继续命中 |
| 预算吃紧、要立刻见效 | 只做两件：作业级归因 + 结束即释放（含推理最小副本） | 观察下一次月度对账的偏差是否收敛 | 不要先上成本预测与自动降本；不要在归因之前谈 OkR 考核 |
| 多云 / 多账号 | 统一标签规范与计费口径对照表（口径数每翻一倍，人力近似翻倍） | 观察口径数是否在增加、对账人力是否同步增长 | 不要在没有口径对照表之前做跨云聚合报表 |
| 已在用 Serverless 推理 / 托管推理 | 把计价口径写进容量决策：按请求还是按秒、闲置是否计费、冷启动算谁的 | 观察「冷启动触发的请求占比」与「缩容到零省下的钱」谁更大 | 不要把稳态高并发放进缩容到零的形态；不要用按请求计价的档位承接长输出任务 |

**为什么表里没有「你的技术栈是什么」这一列**：本节所有行落在同一套动作上——可见、归因、可中断性分级、控制点前移。栈不同只影响「谁来提供这几个接口」，不影响「要不要有这几个接口」。这也解释了为什么本主题下 AI 特色能力全都排在后面：**它们提供的是新的展示与建议，而不是新的因果链。**

「明确不要做」这一列的共同逻辑是：**这些动作的代价是确定的（人力、复杂度、质量风险），收益却依赖一个尚未成立的假设**（利用率好看就等于省钱 / 模型能替你做成本决策 / 优化项总会被执行）。等到 5.6 里的信号出现再投入，损失的只是时间。

**如果你只能做一件事**：在下一个季度做一次对照实验，量三个数。成本主题的最大特点是**它的结论必须来自你自己的账单**——别人写下的百分比换到你的流量形态上都不成立：

1. **闲置 GPU·小时占比**——训练结束未释放与推理低谷期常驻各占多少（5.2.1）。
2. **同一批作业在共享与独占两种形态下的完成时长**——它同时是池化收益的唯一可信口径（5.2.1、5.5）。
3. **四个成本项各自多少**：向量存储、嵌入、检索、生成，以及其中输入 token 与输出 token 的占比（5.2.4）。

这三个数不依赖任何厂商承诺，也不需要新工具——**它们是决定某个 L2 方向值不值得追加投入的证据；要升到 L1，仍须出现第三方（非厂商）的公开生产案例**。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**计费单元与归因粒度**——GPU 让账单从「容量 × 时长」变成了「加速器 × 时长 × 作业」，让利用率的分母变得可以被重新定义，也让「谁的作业贵」这个问题重新需要答案。它**没有**改变的是成本治理的因果链：先可见、再归因、再在花钱之前设控制点（§3.2.6 的护栏）、最后才谈优化建议——这条链在 GPU 上一步都省不掉，只是每一步的工程量更大。因此本节把「作业级归因 + 结束即释放」排在所有 AI 特色能力之前，把「成本预测 / 自动降本」排到最后。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是单价、用量、利用率的分母，还是归因粒度？** 只改账单展示的（新看板、新报表）不改变成本；改归因粒度的（作业级、GPU·小时）现在就能做；声称能自动做决策的（预测、自适应降本）现在还不成立。
