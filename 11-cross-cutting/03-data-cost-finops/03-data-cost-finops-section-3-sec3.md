## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式清单读起来像一道菜单：多团队共享就选标签归因，数据量大就选分层存储，峰谷明显就选弹性伸缩。但同一句话在两个团队身上常常给出相反答案：同样"数据量大"，按**容量 × 时长**计费的平台（对象存储、常驻集群）该做的是把数据搬到更便宜的层，按**扫描字节**计费的平台该做的是让查询少扫——前者"少存"才降本，后者存多少几乎不进账单，"少扫"才降本。

真正做决定的是约束。成本治理里有六条反复出现：**计费单元**（成本对哪个变量积分）、**控制点位置**（能不能在花钱之前介入）、**负载可中断性**（省下的钱会不会被重跑吃掉）、**归因粒度**（账能不能拆到"能改变用量的人"）、**承诺与弹性的先后顺序**、**组织是否愿意让成本成为硬约束**。任一条不同，同一场景的正确模式就翻转。

所以本节先立约束、再谈模式。下表不是选型表，而是"最容易被约束推翻的直觉"清单——当你觉得某个模式"显然更省"时，先回去看是哪条约束在替你说话。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 计费单元（容量×时长 / 扫描字节 / 作业×频次 / GPU 小时） | 哪个杠杆按下去有收益 | 「降本就是省存储」——按扫描字节计费时，存得再多也不进账单，扫得多才进 |
| 控制点位置（事后账单 / 提交前 / 调度时） | 能挽回多少支出 | 「先看这个月账单」——账单描述已发生的事，只能影响下一个周期 |
| 负载可中断性 | Spot / 抢占式能不能用 | 「折扣越大越该用」——把可回收容量用在基线上，重跑会把折扣吃掉 |
| 归因粒度（账单行 / 资源 / 作业 / 表） | 优化动作能否落到人 | 「拆到团队就够了」——团队只能砍预算，改不了 SQL 与调度频次 |
| 优化动作的顺序（先缩占用量，后谈单价） | 会不会把优化空间锁死 | 「先谈折扣见效最快」——先承诺等于按现状封定规模，此后的缩容变成违约 |
| 组织是否让成本成为硬约束（告警 / 审批 / 预算） | 前五条能否落地 | 「有了看板就会省」——不进预算的成本，在用量决策里不是变量 |

还有一条不写在表里、但决定所有模式能否落地的约束：**优化动作的收益归谁、成本归谁**。平台团队做了冷热分层，省下的是业务方的存储账、付出的是自己的人力与一次数据迁移风险；业务方改了调度频次，省下的是部门的预算、付出的是产出时效。当收益与代价落在不同人身上时，任何一个模式都不会被主动执行——这也是为什么成本治理里"归因"必须先于"优化"：归因不解决"该不该做"，它解决"做完算谁的"。

因此下面的模式拆解统一按六个问题走：**被什么约束逼出来 → 结构长什么样 → 为什么结构有效 → 必然的代价 → 什么条件下优点反转成缺点 → 谁在真实使用**。其中"失效点"是本节最重要的部分：成本模式的失效大多不报错，它只是让账单在几个月后悄悄回到原来的水平。

### 3.2 模式逐个拆解（核心节）

下面 6 个模式覆盖原文件列出的全部 5 个模式（标签归因、分层存储、弹性计算、采购组合、Showback / Chargeback），并补入一个**预算护栏**：原清单里没有它的独立条目，但本仓库 [§7 对比](03-data-cost-finops-section-7-sec7.md) 把"控制点位置"单列为六条判据之一，并以 7.3.2 一整节论证"控制点越靠前，可挽回的支出越多"——而控制点的最前端正是提交路径。这 6 个模式按作用面对半分：**分层、弹性、采购三者改变的是用量或单价（账单上的数字），归因、Showback / Chargeback、预算护栏三者改变的是信息与约束**。后三者不动账单上的任何一个数字，但它们决定前三个有没有人执行。

#### 3.2.1 标签驱动的成本归因（Tag-Driven Allocation）

- **被什么约束逼出来**：共享资源池只有一个付款人，而"谁在花钱"的信息不在账单里——账单的维度是资源、服务与账号，问责单位却是团队、项目与作业。
- **结构**：归因 = 账单行 × 时间点有效的标签；未打标签的部分必须落到一个显式的"未归因"账户，而不是按比例平摊。

```sql
-- ① 资源的标签历史（用生效时间而不是当前值，才能回答"上个月的账该算给谁"）
CREATE TABLE resource_tag (
  resource_id  VARCHAR(128) NOT NULL,
  tag_key      VARCHAR(64)  NOT NULL,   -- team / project / env / owner
  tag_value    VARCHAR(128) NOT NULL,
  source       VARCHAR(16)  NOT NULL,   -- created / inherited / backfilled / default
  effective_at TIMESTAMPTZ  NOT NULL,
  PRIMARY KEY (resource_id, tag_key, effective_at)
);

-- ② 账单行（计费口径的最小单位：一行 = 一个资源在一个计费单元上的用量）
CREATE TABLE cost_line (
  bill_period DATE          NOT NULL,
  resource_id VARCHAR(128)  NOT NULL,
  charge_type VARCHAR(32)   NOT NULL,   -- storage / compute / scan / network / gpu
  usage_qty   NUMERIC(18,4),            -- GB-月 / vCPU-小时 / 扫描字节
  usage_unit  VARCHAR(16),
  amount      NUMERIC(18,4) NOT NULL
);

-- ③ 归因视图：任何一行都必须有归属，包括那个叫 unallocated 的归属
-- 注意：标签表的主键含 effective_at，一个资源天然有多条 team 历史版本，
-- 必须取"bill_period 之前有效的那一条"，否则同一笔账单会被连出多行、
-- 被 SUM 重复计入，视图合计 ≠ cost_line 合计
CREATE VIEW cost_attributed AS
SELECT l.bill_period, COALESCE(t.tag_value, 'unallocated') AS team,
       l.charge_type, SUM(l.amount) AS amount
FROM   cost_line l
LEFT   JOIN resource_tag t
       ON t.resource_id = l.resource_id
      AND t.tag_key = 'team'
      AND t.effective_at = (
            SELECT MAX(t2.effective_at) FROM resource_tag t2
            WHERE t2.resource_id  = l.resource_id
              AND t2.tag_key      = 'team'
              AND t2.effective_at <= l.bill_period
          )
GROUP  BY 1, 2, 3;
```

- **为什么这样设计有效**：因为账单行的维度只有资源，而问责单位是人所在的团队，所以必须插入一层"资源 → 问责单位"的映射；把这层映射的缺口显式暴露成 `unallocated` 一行，未归因的成本才会自己浮到台面上被处理，而不是消失在平摊里。
- **代价**：标签覆盖率是一份长期人力，新增资源不打标账立刻失真；标签是资源生命周期的横切面，改名、转组、项目合并都要靠 `effective_at` 回溯而不是改当前值；账单行与标签两套数据要做月度对账，否则两边永远对不上。
- **失效点**：当未打标签的比例持续偏高、而团队又把 `unallocated` 平摊掉时，标签归因从"可问责"反转成"越归因越失真"，因为平摊让每个团队的账看起来都合理，真正的大头反而不再有人追问——归因的正确性由最小的那个覆盖率决定，而不是由标签表建得多漂亮决定。
- **真实使用**：主流云的成本管理入口都支持按标签 / 资源组 / 项目分组出账【公开】（AWS Cost Explorer、Azure Cost Management、阿里云费用中心各自的成本管理文档；三者均为随版本迭代的官方文档、不落固定发布年份，可按「Cost Explorer 按标签分组」检索核验，以官方文档当前版本为准）；把归因粒度从"团队"继续推到"作业 + 调度频次"的做法，见 [§6 字节案例](03-data-cost-finops-section-6-sec6.md)。

#### 3.2.2 分层存储（Tiered Storage）

- **被什么约束逼出来**：对象存储按"容量 × 存放时长"计费，同时数据访问频率极度倾斜——绝大多数分区在写入后的头几天被读，之后只被偶尔回看，而查询性能要求只对热数据成立。
- **结构**：分层只能在分区 / 文件这一层做，且必须写成会自动执行的规则，而不是靠人定期搬。

```text
访问频率
  ▲
  │  热  ── 本地盘 / SSD / 缓存层      单价最高，延迟最低，容量小
  │  温  ── 标准对象存储（近 N 天分区）  单价中，首次读有毫秒级额外延迟
  │  冷  ── 低频访问类存储（低访问分区） 单价低，通常有最小计费时长
  │  档  ── 归档类存储（合规留存）       单价最低，取回按次计费且非即时
  └──────────────────────────────────▶ 数据年龄 / 最后访问时间
判定输入：最后访问时间 + 分区粒度 + 历史查询日志统计
落地形态：对象存储生命周期规则 / 表格式的冷热迁移（分区级重写）
关键：行级分层无意义——列存的一次扫描就是整列，按行搬不会减少扫描量
```

- **为什么这样设计有效**：因为列存与分区让同一时间段的数据共享访问特征，所以可以把整段分区一起搬到更便宜的层级，而绝大多数查询（按时间过滤的增量计算）根本不会碰它们；代价是每降一层都要用"取回延迟 + 取回费用"换单价。
- **代价**：取回费用与被读延迟（冷层取回不是即时的）；跨层查询要改引擎配置或 SQL 提示；部分档位有最小计费时长，转进去没几天又取回会双付；分层规则本身需要有人按访问统计复核。
- **失效点**：当访问模式从"按时间回看"变成"随机点查历史明细"时，分层从"降本"反转成"净增成本"，因为每次查询都要触发一次取回，取回费与延迟被计入每一次查询，而延迟还会顺带抬高下游任务的重试率。
- **真实使用**：对象存储的生命周期规则支持按天数自动转换存储类【公开】（AWS S3 用户指南的 Lifecycle 说明；属随版本迭代的官方文档、不落固定发布年份，具体档位、最小计费时长与取回定价以官方文档当前版本为准）；湖仓表格式（Iceberg / Delta Lake）做冷热迁移走的是"分区级重写 + 底层对象存储生命周期"这两步：表格式负责数据文件与清单文件的**位置与版本**，介质分层由重写配合对象存储生命周期承担【公开】（Iceberg 表规范把快照、清单文件与数据文件作为不同层级的元数据对象管理；可按「Iceberg table spec snapshots」检索核验，规范随项目版本迭代、以官方当前版本为准）。**快照过期是另一条独立过程**——它作用于快照这一层的版本引用与保留期，而不是文件所在的存储类【推算】（由表规范的元数据分层推出：快照引用清单文件、清单文件引用数据文件，过期动作落在引用关系上，不改变任何文件的存储类）；本仓 [§03-data-stack/05 冷热分层 §7](../../03-data-stack/05-cold-hot-tiering/05-cold-hot-tiering-section-7-sec7.md) 已把"分层只改介质位置、版本回收只由保留期策略决定"列为一对不可合并的动作。原文件列出的阿里云 OSS 归档、S3 + Lifecycle 属同一族手段。冷热分层后的实际账单降幅随访问分布而变，多数团队落在"存储账单明显下降"这一量级，具体比例应按自家账单实测【经验】。

#### 3.2.3 弹性计算（Elastic Compute）

- **被什么约束逼出来**：负载峰谷比大（批处理在夜间、在线服务在白天、大促在少数几天），而按峰值采购意味着全年为几乎用不到的容量付费。
- **结构**：伸缩策略必须同时带上界、下界与冷却窗口——没有上界的弹性等于没有预算。

```text
指标 / 队列深度 ──▶ 决策器 ──▶ 调整目标容量
  · 定时：已知峰谷（22:00 缩、09:00 扩）
  · 指标：CPU / 队列积压 / 待调度任务数
  · 混合：定时兜基线，指标接突发
必须显式写入的四个边界：
  minCapacity          下界——保护 SLO，低于它不加价只降级
  maxCapacity          上界——保护预算，弹性不能无上限
  stabilizationWindow  冷却窗口——抑制抖动
  drainBeforeShrink    缩容前排空——在跑的任务先跑完 / 打标为可中断
```

- **为什么这样设计有效**：因为成本是"容量 × 时长"的积分而不是峰值乘以周期，所以把容量沿时间轴贴合负载就能直接减少积分面积；代价是容量变化本身不是免费的，每一次扩缩都要付冷启动、任务重排与调度收敛的代价。
- **代价**：弹性依赖精确的负载指标（指标滞后于负载时，扩缩总是慢半拍）；缩容会打断在跑的任务，需要排空协议；有状态负载与需要数据本地性的负载不能简单缩到零；伸缩策略的调参本身是持续运维面。
- **失效点**：当负载抖动频繁或伸缩指标滞后时，弹性从"贴合需求"反转成"以更大振幅震荡"，因为每次缩容都可能杀掉正在跑的任务、继而触发重跑，而重跑又推高队列长度、触发扩容——节省被自己制造的振荡吃掉，成本反而高于固定的保守容量。
- **真实使用**：Karpenter 项目在 2024 年发布 1.0 GA，其调度目标包含"以更经济的实例类型满足容量需求"【公开】（来源：Karpenter 项目 Releases 页的 v1.0.0 条目，2024；可按「Karpenter v1.0.0 release」检索核验，版本与行为以该 Release Note 为准）。Kubernetes 的 Horizontal Pod Autoscaler 提供按指标伸缩的原生机制【公开】（Kubernetes 官方文档的 Horizontal Pod Autoscaler 章节；随版本迭代、不落固定发布年份，可按「Horizontal Pod Autoscaler」检索核验，以官方文档当前版本为准）；原文件列出的 YARN Capacity Scheduler、AWS ASG、阿里云 ESS 属同一族。数仓侧的"自动暂停 / 恢复"与"多集群"是弹性在仓库维度上的对应物【公开】（Snowflake 虚拟仓库的 auto-suspend / multi-cluster 文档；同为随版本迭代的官方文档、以当前版本为准，可按「Snowflake warehouse auto-suspend」检索核验）。

#### 3.2.4 采购组合：按需 / 承诺折扣 / 可回收容量

- **被什么约束逼出来**：同一份算力有三种买法，折扣的来源不同——承诺折扣买的是云厂商的确定性（因此要求你提前锁定用量与年限），可回收容量买的是别人暂时不用的空闲（因此可以随时被收回）。
- **结构**：三层的划分依据是"能不能重跑"，不是"重不重要"；承诺的量按可预测基线封顶。

```text
负载分桶（按「可中断性 × 稳定性」）
  ① 基线、不可中断（常驻服务、在线数仓）
        └─▶ 承诺折扣覆盖（预留实例 / 节省计划，1 年或 3 年承诺；
                            期限与折扣档位以各云定价页当前版本为准）
  ② 可中断、可重跑（批处理、ETL、训练、回刷）
        └─▶ 可回收容量（Spot / 抢占式）+ 检查点 + 重试
  ③ 突发与不确定（新业务、峰值溢出、探索性实验）
        └─▶ 按需兜底（贵但灵活，且不受承诺约束）

承诺量的定法：按「可预测基线用量」封顶，而不是按当前总用量
  └─ 因为承诺按锁定的用量计费，缩容不退款——多签的部分是纯亏
```

- **为什么这样设计有效**：因为折扣的来源决定了它的适用面——承诺折扣换的是"你承诺用、我给你低价"，可回收容量换的是"你容忍被收走、我给你低价"，所以可重跑负载用可回收容量、不可中断负载用承诺，两者的收益不会互相抵消；代价是把不确定性分别转移给了自己（承诺买多了亏）和任务（Spot 被收回要重跑）。
- **代价**：承诺利用率要持续管理（买了用不完就是净亏，且改不了）；Spot 需要中断处理（检查点、重试上限、多实例类型池、容量池分散）；三桶混跑要求调度器支持按桶打标与配额隔离；跨桶迁移（负载画像变了）需要重新定承诺。
- **失效点**：当业务增长高度不确定时，承诺折扣从"省钱"反转成"锁定成本"，因为承诺按锁定量计费而不按实际使用计，业务缩量后省下的那部分照样要付，承诺越长约得越死；反向的失效同样存在——当负载不可中断时，Spot 折扣反转成净增成本，重跑与重试的代价超过折扣差额。
- **真实使用**：云厂商普遍提供按需、承诺折扣与可回收容量三类购买方式【公开】（AWS 的 On-Demand / Reserved Instances 与 Savings Plans / Spot 各自的官方文档；属随版本迭代的产品文档、不落固定发布年份，可按「AWS Savings Plans 文档」检索核验，以官方文档当前版本为准），原文件列出的 Azure 节省计划、阿里云节省计划属同一族。折扣幅度随容量池与实例类型波动：可回收容量相对按需常见区间在 60–90%【经验】，承诺折扣通常落在同一区间的下半段【经验】，与 [§7 对比](03-data-cost-finops-section-7-sec7.md) 的口径一致。

#### 3.2.5 Showback / Chargeback（从可见到可扣款）

- **被什么约束逼出来**：成本可见性本身不产生激励——工程团队既不控制预算也不被扣款时，"省下来不归我、花出去不找我"，用量决策里就没有成本这一项。
- **结构**：分账视图是两级模式的共同底座，区别只在于它是否接到财务的预算上。

```text
阶段一 Showback：账单 → 分账视图 → 团队可见（不扣款）
阶段二 Chargeback：分账视图 → 分摊规则 → 计入部门预算（硬约束）

分账视图的最小字段：
  问责单位 | 期间 | 成本类别 | 用量 | 单价 | 已归因 / 未归因 | 环比变化 | 主要贡献作业
分摊规则的第一原则：谁能改变用量，谁就承担这一行
  可控项（作业选型、调度频次、SQL、实例规格）→ 直接归属
  不可控项（共享集群、公共组件、平台自用）→ 显式列为公共成本，单独立账
```

- **为什么这样设计有效**：因为预算是一种能被组织真正执行的硬约束，而看板不是——只有当成本进入一个被人问责的预算科目时，用量决策才会把成本当成变量；代价是分摊规则本身会成为组织议题，且没有一套规则能让所有团队都满意。
- **代价**：分摊规则的制定与维护要长期有人对账（共享集群、跨团队依赖、平台自用资源怎么摊）；Chargeback 会引出"把资源挪到别人账上"的博弈；口径一旦变更，历史环比就断了。
- **失效点**：当分摊规则退化成"按用量比例平摊"而不是"谁可控谁承担"时，Showback / Chargeback 从"激励优化"反转成"激励占用"，因为团队发现自己少用也要付同样的钱之后，理性选择是尽量多占——平摊把可控与不可控混在一行，而这一行恰恰是团队唯一能看见的成本。
- **真实使用**：FinOps 的三阶段（Inform / Optimize / Operate）作为公开框架由 FinOps Foundation 维护【公开】（来源：FinOps Foundation 官网的 FinOps Framework，基金会 2019 年成立、2020 年起发布框架；以官网当前版本为准）；原文件列出的 Apptio、Cloudability、Vantage 及自研 FinOps 平台以账单归一、分摊与预算为核心能力【公开】（各产品官方文档；属随版本迭代的产品文档、不落固定发布年份，可按产品名检索核验，以官方文档当前版本为准）。多数团队的实际路径是先做多年 Showback，再对少数可控大户上 Chargeback【经验】。

#### 3.2.6 预算护栏：把控制点放在花钱之前

- **被什么约束逼出来**：事后账单只能影响下一个周期，而一笔支出的量级在**提交那一刻**就已基本决定（作业 × 频次 × 输入规模 × 单价）；纠错成本最低的时刻就在提交路径上。
- **结构**：把成本估算与阈值判断插进作业提交路径，并让估算结果落库供月度对账。

```text
作业提交 ──▶ ① 成本估算（输入规模 × 调度频次 × 单价 → 预估月度成本）
         ──▶ ② 与基线和预算比较
               · 低于基线            → 放行
               · 超基线但可解释      → 放行 + 记录（进入重复作业清单）
               · 超预算阈值 / 高风险 → 阻断，要求：降频次 / 缩输入 / 走审批
         ──▶ ③ 落库（作业 × 频次 × 预估 × 实际），供月度对账与基线校准

关键：估算必须计入调度频次
      单次跑 1 分钟的作业与每分钟跑一次的作业，单次成本相同，
      月度成本相差三个数量级【推算】（1 天 1 次 vs 1 分钟 1 次，比值 1440 ≈ 10³）
      只算单次成本会让最大的那部分完全隐形
```

- **为什么这样设计有效**：因为成本的绝大部分由"作业 × 频次 × 输入规模"在提交时决定，所以在这里拦截能挽回的支出最多，而且此时还有替代方案（改频次、增量计算、缩输入）；代价是把成本判断塞进研发流程，必然带来摩擦，护栏的成败取决于它是否比业务节奏更快。
- **代价**：估算模型要长期维护（单价、压缩比、扫描量估算都有误差，必须用实际值回校）；审批通道要有明确 SLA；误拦会阻碍正常迭代，而误放又会让阈值形同虚设；这套逻辑要覆盖所有提交路径，漏掉一条就有旁路。
- **失效点**：当阈值过紧或审批慢于业务节奏时，护栏从"控制增长"反转成"被绕过"，因为团队会改走不经过这条路径的提交方式（改名、拆小、换入口），而预算约束随即失效——机制上与血缘门禁同源：粒度不够或响应太慢的门禁，最终都不会被认真对待。
- **真实使用**：云原生预算与告警（如 AWS Budgets 一类）属于事后到准实时的控制点：它的预算配置在告警阈值之外还可挂"动作"，能在实际或预测支出越线时对符合条件的资源执行动作（停止实例、附加策略一类），因此不只是"发一封通知"；但它仍然**不是提交前阻断**——动作作用在已经存在的资源上，改不了这一笔提交本身【公开】（各云预算功能的官方文档；随版本迭代、不落固定发布年份，可按「AWS Budgets actions」检索核验，可执行动作集合与触发行为以官方文档当前版本为准，本章 [§7.3.2](03-data-cost-finops-section-7-sec7.md) 已单列这一控制点）；把估算放进提交路径、超预算即阻断或要求审批的做法，见 [§6 字节案例](03-data-cost-finops-section-6-sec6.md) 与 [§6 阿里案例](03-data-cost-finops-section-6-sec6.md)。

把这 6 个模式放在一起看，会出现一个反直觉的排序：**能立刻改变账单数字的是三个用量 / 单价模式（分层、弹性、采购），决定这些钱能不能持续省下来的是另外三个信息与约束模式（归因、Showback / Chargeback、预算护栏）**。前三者的共同弱点是收益与代价落在不同人身上——分层省下的是使用方的存储账，付出的是平台团队的人力与一次数据迁移风险——因此它们需要归因把成本落到能改变用量的人身上；而这条链本身是有阶段的：归因让成本可问责，Showback / Chargeback 把它接进预算（从"看得见"走到"扣得到"），预算护栏把它挡在花钱之前。这也是成本治理比大多数技术优化更依赖组织设计的原因。

### 3.3 模式选择决策表

下表的每一行都是一组约束到模式的映射，读法与常见选型表不同：**先读第一列，确认你确实落在这组约束里，再读第二列**——如果约束判断错了，推荐模式会连同理由一起失效。

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 共享资源池、多团队、问责单位是团队 | 标签归因 + Showback | 不用 Chargeback 起步：分摊规则未定型时，硬扣款会先引发争议而不是优化 | 标签覆盖率与未归因占比是否已知 |
| 存量大、访问按时间衰减、按容量计费 | 分层存储 + 生命周期规则 | 不用压缩 / Compaction 当主线：它们改善的是扫描量与文件数，改不了"冷数据仍按热价存放" | 是否有稳定的最后访问时间与访问日志 |
| 峰谷比大、可重跑任务占比高 | 弹性计算 + 可回收容量 | 不用承诺折扣覆盖弹性部分：承诺锁量，而弹性部分的用量本来就是不确定的 | 负载里可中断比例有多高 |
| 稳态与突发混合、业务可预测 | 承诺折扣覆盖基线 + 按需兜底 | 不用全按需：稳态走按需等于长期支付弹性溢价 | 是否存在可预测的基线用量 |
| 预算需要成为硬约束、能改提交路径 | 预算护栏 + Chargeback | 不用只有看板：不进预算的成本不会进入用量决策 | 提交路径是否可控、审批 SLA 能否跟上 |
| 按扫描字节计费（BigQuery 一类） | 分区裁剪 + 列裁剪 + 结果缓存 + 物化视图 | 不用弹性伸缩当主手段：扫描计费与集群规模无关，缩容不减少扫描量 | 每次查询的"扫描量 / 返回行数"比值 |
| 早期 0→1、用量不可预测 | 标签归因 + 按需 | 不用承诺折扣：此时锁定的每一个量都可能是错的 | 业务周期是否已稳定 |
| 多云 / 多账号、各云计费口径不一致 | 账单归一 + 标签归因 + Showback | 不用单云原生账单直接汇总：各云的计费单元与账号结构不同，汇总数对不上，"跨云归一"实际发生在标签与分摊这一层 | 每朵云的计费单元与账号结构是否已归一 |
| GPU 训练为主 | 弹性 + 可回收容量 + 强制释放策略 | 不用固定常驻：训练是批式负载，闲时的占用量是纯浪费 | 任务结束后资源是否自动释放 |

本节最常被误选的一对，是把**弹性伸缩**与**承诺折扣**当成同一类"降本手段"并用错顺序。二者的机制完全不同：弹性改的是**占用量**（把时间轴上的容量贴合负载），承诺折扣改的是**单价**（用确定性换价格）。先谈折扣，等于按当前规模把用量锁进合同，之后每一次缩容都变成对自己不利；先做占用量优化、再对剩下的稳定基线去谈折扣，才可能叠加。顺序颠倒的实际后果在组织上很常见：工程团队先上了弹性与可回收容量，财务随后按"现状用量"签了年度承诺，两边都做了局部最优，合起来却把优化空间锁死了。

第二常被误选的一对，是把**分层存储**与**查询裁剪**当成可以互相替代的降本手段。分层改的是数据的存放位置（单价），裁剪改的是每次查询触及的数据量（用量）；按容量计费的平台上，分层是主线而裁剪收益有限；按扫描字节计费的平台上，裁剪是主线而分层几乎不进账单。误把分层当主线的典型后果是：存储账单确实降了，总成本却没动，因为大头在查询上；而且冷层的取回费用还会让查询账单略微上升，进一步迷惑判断。

### 3.4 组合模式：真实系统不会只用一种

**组合一：标签归因 + 分账视图 + 预算护栏（治理闭环）**

- 构成：标签归因回答"谁花的"，分账视图回答"和上个月比如何"，预算护栏回答"下一笔能不能花"。
- 职责边界：归因层只做映射与对账，不做优化判断；分账视图只呈现事实与未归因缺口；护栏只管阈值与流程，具体怎么改由提交方决定。
- 运维代价：标签治理是长期人力；分账口径变更要走版本管理；护栏的估算模型要按实际值回校，否则会因误差被质疑而失去权威。
- 适合规模：从多团队共用一套平台起就该有，不等成本出问题再建。

**组合二：分层存储 + Compaction + 生命周期规则（存储侧）**

- 构成：分层把冷数据移到低价层，Compaction 把小文件合并成大文件（提升压缩率、降低元数据与打开开销），生命周期规则负责让两者自动发生。
- 职责边界：分层管"放在哪一层"，Compaction 管"文件的形态"，生命周期管"什么时候做"；三者都不能决定数据该不该留。
- 运维代价：Compaction 本身消耗计算（是"用算力换存储与查询"的交换，必须在计算单价低时跑）；分层策略要按访问统计复核，规则一旦写错会批量误迁移。
- 适合规模：分区数进入万级、小文件开始影响查询时必做。

**组合三：弹性 + 可回收容量 + 承诺封顶基线（计算侧）**

- 构成：弹性负责容量随时间贴合负载，可回收容量覆盖可重跑部分，承诺折扣覆盖缩放不动的常驻基线。
- 职责边界：调度器负责按"可中断性"打标与选池；任务侧负责提供检查点与重试上限；采购侧只对基线签量。
- 运维代价：中断处理与重试逻辑是常驻工程；承诺利用率要按季度复核；三桶混跑要求配额与优先级隔离，否则可回收实例被回收时会连累在线任务。
- 适合规模：批处理与训练占比高、且团队有能力改造任务以容忍中断。

三条组合共享一个前提：**归因层先于优化层上线**。没有归因，组合二不知道热数据的热度分布该从谁的历史查询里统计，组合三不知道基线用量该由谁认领，组合一更无从谈"未归因占比"。多数团队把顺序做反——先做看起来最"工程"的冷热分层与弹性，几个月后才发现省下来的钱没有人在乎，因为没有一行账落到能改变用量的人身上。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 为了降本降 SLA | 降本动作上线后，查询变慢 / 任务超时开始出现，且没人事先说清哪些指标不可退化 | 降本省下的是确定的小钱，违约与重跑付出的是不确定的大钱，成本与风险被拆到两个指标上分别优化 | 降本有明确 KPI，SLA 退化是分散的、事后的、无人认领的 | 降本前先圈定 SLA 边界（哪些指标是硬线），把违约成本写进同一份评估 |
| 只盯存储、忽视查询 | 优化清单全是存储项，而查询账单持续上涨；没人说得清自家成本在三类上的实际构成 | 优化打在计费权重小的那一项上，投入产出比极低——而"哪一项权重大"完全由计费单元决定 | 存储账单最直观、最好理解；查询成本被分散到各个业务方的 SQL 里，没有单一责任人 | 先按计费单元拆自家账单结构，再决定第一件做什么；按扫描计费时优先裁剪与缓存 |
| 全员共享大集群、无归因 | 问任何团队"你们用了多少"都答不出，且所有人都觉得自己"用得不多" | 无归因 → 无激励 → 无优化，平台层承担全部成本却无法推动任何一个使用方改行为 | 建平台时以"资源池越大越省事"为目标，归因被当成后续优化项 | 归因层与资源池同步上线；未归因部分单独立账并对全员可见 |
| 用 Spot 做基线负载 | 常驻服务与有状态任务被调度到可回收实例上；中断告警频繁 | 回收触发重跑与重排，节省被重跑成本吃掉，甚至因反复重试造成净增成本与稳定性事故 | 折扣幅度最显眼，而"负载是否可中断"需要逐个任务判断，成本高 | 按可中断性给负载分类，可回收容量只承载可重试任务，基线用承诺覆盖 |
| 频繁扩容 / 缩容 | 容量曲线呈高频锯齿；缩容后紧跟一次重跑或失败告警 | 每次缩容都可能打断在跑的任务，重跑又推高队列长度并触发扩容，成本在振荡中高于保守容量 | 伸缩策略只看当前指标，没有冷却窗口与排空协议；把"响应快"当成优点 | 加冷却窗口、缩容前排水、按队列长度而非瞬时 CPU 决策 |
| 忽略 GPU 成本 | 训练任务结束后 GPU 仍被占用；推理服务在低峰期仍按峰值常驻 | GPU 小时单价高，闲置的每一小时都按最高单价计费，且它挤占的是稀缺容量而非可替代容量 | 训练完成即视为"任务结束"，资源释放挂在人身上而不是流程上 | 训练结束强制释放 / 自动伸缩；推理服务设最小副本并接受冷启动代价 |

**用 Spot 做基线负载**是最危险的一条，因为它在财务上表现为"当月省了钱"，出事时才表现为稳定性事故。它暴露的典型方式是：月底账单一度很好看，随后某个凌晨可回收容量集中收回，常驻服务同时重启，下游任务重试打满队列——此时要付出的不只是重跑成本，还有一次事故复盘。机制上，只要折扣来自"可被收回"这个属性，就不能把它用在不可中断的负载上，无论折扣多诱人。

**为了降本降 SLA** 的隐蔽性在于它从不以"事故"的形式出现，只以"慢慢变慢"的形式出现：查询从秒级变到十秒级、任务从按时产出变到偶尔超时。等它被当成问题时，已经没人记得是哪次降本动作造成的。

**只盯存储、忽视查询**则让优化在错误的权重上做功。它有个信号很好辨认：优化清单里没有一条需要改动业务的 SQL 或调度频次——而这类改动恰好是按扫描计费平台的成本大头。

**全员共享大集群、无归因**是一条"沉默的反模式"：它在任何监控指标上都不产生异常，只在预算评审时表现为"平台成本与业务增长无关地同步上涨"。它的暴露方式通常是某次财务问"这笔钱是谁花的"，而平台团队只能给出总量。修法不是补一张看板，而是与资源池同步上线归因层——晚了两年再补，最麻烦的部分不是建表，而是回填这两年里"哪个资源属于哪个团队"的历史真相，而这部分信息往往已经不存在了。

**忽略 GPU 成本**的独特之处在于它同时是成本问题与容量问题。GPU 闲置付出的不只是钱：它占用的是稀缺的加速卡池，而这块池子往往同时支撑训练与推理。因此这条反模式的修法必须是流程性的（任务结束即释放、按需拉起），把释放责任挂在人身上等于默认它不会发生——人总会去开下一个会。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单团队自用 → 多团队共享平台 | 总量看板 | 没有人对构成总量的任何一部分负责 | 标签归因 + Showback | 标签规范、历史回填、月度对账流程 |
| 归因到团队 → 归因到作业 | 团队级分账 | 团队只能砍预算，改不动具体作业的频次与 SQL | 作业 × 频次级归因 + 预算护栏 | 要接调度系统与查询日志，两套口径要对齐 |
| 数据量千级分区 → 百万级分区 | 人工定期清理 / 手工搬冷数据 | 人工动作的周期跟不上数据增长，冷数据长期按热价存放 | 生命周期规则 + Compaction 调度 | 规则错一次会批量误迁移，必须先在影子分区验证 |
| 全部按需 → 承诺折扣覆盖基线 | 纯按需采购 | 稳态部分的弹性溢价长期支付，且业务已可预测 | 承诺折扣 + 按需兜底 | 承诺按量计费不退款，需按可预测基线封顶 |
| 计算成本占主导 → 查询成本占主导 | 弹性与采购优化 | 计费单元变了，降集群规模不再减少账单 | 分区裁剪 + 列裁剪 + 结果缓存 + 物化视图 | 要改业务 SQL 与数仓物化策略，跨团队推动 |
| CPU 负载为主 → GPU 负载并重 | 通用实例采购与伸缩 | GPU 小时的单价与稀缺性完全不同，闲置的代价远高于通用算力【经验】 | 弹性 + 可回收容量 + 结束强制释放 | 要改造训练任务的检查点与断点续跑 |
| 单云 → 多云 / 多账号 | 单云原生账单 | 口径不统一，汇总数对不上，无法比较 | 账单归一 + 分摊规则引擎 | 每多一个口径就多一套标签规范与长期对账人力 |

一条经验判据：**当"未归因占比"开始上升、或"优化清单里再也找不到能改动业务行为的条目"时，就该换模式了**——前者说明归因层落后于资源增长，后者说明优化已经打在了错误的计费单元上。

还有一条更隐蔽的跃迁：**计费单元本身会变**。同一个平台从自建集群（按容量 × 时长）迁到按扫描计费的托管数仓，或从 CPU 集群扩到 GPU 集群，都会让原先最有收益的那套动作突然失效——不是执行得不好，而是成本函数换了变量。识别它的方法是固定的：每次平台形态变化后重问一次"账单是对哪个变量积分"，并把三到六条最贵的成本项按新的计费单元重新排序。

### 3.7 自检清单

1. 账单里"未归因"部分的占比是多少？它是否被平摊进各团队？若是，归因失真且不会自愈。
2. 每个资源是否带有能落到"能改变用量的人"的标签？新增资源不打标时，会被拒绝还是自动进入未归因账户？
3. 分层是否写成了生命周期规则（而不是靠人定期搬）？规则里是否考虑了最小计费时长与取回成本？
4. 上一次有人因为成本改了作业，是哪一个作业、改了什么？答不出，说明成本还没进入决策。
5. 弹性伸缩是否同时有下界（保护 SLO）与上界（保护预算）？冷却窗口与缩容排空协议存在吗？
6. 承诺折扣覆盖的量是按"可预测基线"算的，还是按当前总用量算的？承诺利用率是多少？
7. 可回收容量承载的负载里，真正可重试的比例是多少？检查点与重试上限是否落地？
8. 你有多少作业属于"每天扫描 TB 级、返回几百行"？按扫描计费时，这就是第一优先级。
9. 你所在平台的计费单元是什么？据此，"第一件该做的事"是哪一件？
10. GPU 在训练结束后是否自动释放？推理服务在低峰期的实际利用率是多少？
11. 僵尸资源（无下游的表、无调用的作业、长期空转的集群）是否有定期识别与回收流程，且回收前有通知、缓冲期与可撤回？
12. 本轮降本动作涉及的所有指标里，哪些是不可退化的硬线？这条线写在哪个文档上、由谁认？

这份清单可以按"能不能立刻拿到答案"分成两组：1、2、3、6、9 是当天就能查的（去看一眼账单与配置），4、5、7、8、10、11、12 需要一个周期才能回答（要看历史行为与流程）。第二组答不上来不代表做错了，只说明成本治理还停在"知道花了多少"这一步，尚未走到"改变量"。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 多团队共享资源池、成本需要被问责 | 标签归因 + 分账视图 | 账单只有资源维度，问责单位是人，中间必须有一层映射且缺口要可见 |
| 存量大、访问按时间衰减 | 分层存储 + 生命周期规则 | 列存与分区让同时段数据共享访问特征，可整段搬层而不影响多数查询 |
| 峰谷比大、可重跑比例高 | 弹性 + 可回收容量 | 成本是容量对时间的积分，不是峰值乘以周期 |
| 业务可预测、存在稳定基线 | 承诺折扣覆盖基线 + 按需兜底 | 折扣买的是云的确定性，只能用在提前确定的量上 |
| 预算必须成为硬约束 | Chargeback + 预算护栏 | 只有进预算的成本才会进入用量决策；控制点越靠前，可挽回的支出越多 |
| 计费单元是扫描字节 | 分区 / 列裁剪 + 结果缓存 + 物化视图 | 扫描计费与集群规模无关，缩小集群不会减少扫描量 |
| 负载以 GPU 为主 | 弹性 + 强制释放 | GPU 小时的闲置代价远高于通用实例，且挤占稀缺容量 |

> 本节小结：本主题下决定模式选择的**唯一那条最前置的约束，是计费单元**——成本函数对哪个变量积分（容量 × 时长、扫描字节、作业 × 频次、GPU 小时），它一确定，哪些杠杆按下去有收益、哪些按下去不响就已经定死；其余约束（控制点位置、可中断性、归因粒度）都是在给定计费单元之后做的二次筛选。也因此，成本治理的第一步永远是把自家账单拆到计费单元这一层，而不是先挑一个模板搬过来。
