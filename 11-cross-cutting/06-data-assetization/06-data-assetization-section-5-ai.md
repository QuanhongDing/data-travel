## 5. 前沿演进（AI 时代）

> 原 § 5 共 97 行、为方向清单（AI 目录 / 要素市场化 / RAG 融合 / Agent 消费 / 向量库 / GraphRAG / 六条趋势），其列出的方向在本节 5.1 表与「原条目去向对照」里逐条保留并重新归类，重写为约 300 行的机制与成熟度评估。

### 5.1 先分清三类「前沿」

趋势清单的根本问题是**没有时间维度**。同一个列表里，「已 GA 且有人在生产里用」「只在厂商材料里出现过」「写在政策文本里」被并列成同一年的三条趋势，读者据此排路线图就会踩空。

资产化这一主题尤其明显：入表是**制度**，AI 描述是**产品能力**，Agent 自助消费是**方向**——三者性质不同，却常被写进同一张「2025 趋势」表。判断哪一条今天能进架构，要先回到本主题的既有约束（§3.1）：三条是「登记与责任的强制性」「价值能否归因」「交付是否必须经过契约」，另加一条不同层级的「定义权落在谁头上」。

§3.1 的约束表里还有两行直接对应当今：**消费方是人 / 应用 / Agent**（决定元数据是否必须机器可读），以及**合规与政策约束（分类分级 / 入表）**（决定哪些项必须登记、估值是否要能被外部认可）。本节 5.2 的四组方向，正是从这两行与前面三条约束里长出来的。

本节要判的不是「AI 能不能接进目录」，而是**新增的生成者与消费者会不会撞上这四条约束**——例如让模型直接写业务含义列，撞上的就是第一条（登记的责任主体被抹掉）。

本节用 L1 / L2 / L3 三级划分，判据必须可核验，而不是「感觉成熟」：

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口 / 生态未稳，或**仅有厂商自有案例**，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

有一条硬规则要先说清：**判据②核不到就是 L2**，不为任何一行放宽判据，也不缩小判据的适用范围。表中 L2 行里出现「仅有厂商材料」「本节不指名案例」这类描述，那是 L2 的定义本身，不是对某一行额外开的口子。

**本节不对 L1 判据做任何修正**——本主题最诱人放宽的地方正是第②条：目录厂商都发布过 AI 助手、智能检索、智能盘点的公开材料，很容易把「有厂商产品文档」当成「有第三方生产案例」。但产品文档出自**产品提供方本身**，按判据读就是「厂商自有案例」，正是 L2 的定义；把判据改写成「有公开的机制性材料」之后，读者按新措辞照样核验不了。

所以本主题的读法要反过来：级别不是用来决定「买哪一家」，而是用来决定**先做哪件事**。5.1 表里 L2 共五行，分属两族：**AI 能力侧三行**（补全 / 语义索引 / 自然语言入口，第 1–3 行）与**制度侧两行**（入表 / 交易所，第 6、7 行）。能力侧现在就能推进的只有两件事——把关键项做成写入约束（登记那一半），以及把「草稿 / 已确认」分成两态之后再引入 AI 补全（补全那一半）；语义索引与自然语言入口（第 2、3 行）要先等描述覆盖率上来（5.2.2）。制度侧两行同样是「现在就该做」，但动作是**准备输入**而不是引入新能力：入表先把成本归集到资产粒度，交易先定契约与计量（5.7 第 4、5 行）。其余六行（第 4、5、8、9、10、11 行，均为 L3）只记录、先观察 5.6 的信号。

写法上还有四件容易混的事，先在这里分开：

- **产品名 vs 能力名**：「AI 资产盘点」「智能取数」是**能力名**，不是某个产品的专属名——同一个能力在不同材料里挂在不同的产品名下（§7.2 已就缩写「DAS」澄清过一次）。判定方法：按**产品全名**在厂商产品目录里检索，不要按能力名或缩写归类。
- **制度 vs 产品**：入表是会计处理制度，不是产品能力。把「制度生效」读成「能力已就绪」是本主题最常见的混淆（§3.2.2、§7.7）。
- **已 GA vs 预览 / 演示**：不要把演示里的「自然语言一键取数」写成已发布能力。判定方法：找该产品官方文档里的功能条目与发布说明；找不到就以厂商材料计，按判据①不成立处理。
- **单组织 vs 跨组织**：本组织内的目录、估值、计价是已建成能力；跨组织联邦与交易是另一套语义，不能拿本组织内的覆盖率数字去推算跨组织结论。

#### 5.2.1 AI 补全登记：把「从零写」变成「改草稿」

- **旧做法与它的卡点**：目录的关键项（业务含义 / 域 / Owner / SLA / 密级）由产出方人工填写。
  - 登记的成本落在产出方、收益落在消费方，所以没有强制机制时，新资产的登记率随时间下降（§3.2.1、§7.7 第一条反模式）。
  - 卡点不是「没人会写」，而是**登记成本的承担者与收益者不是同一方**，而成本随资产数线性增长。
- **AI 改变了什么机制**：把「从零写一段业务含义」变成「改一段草稿」——模型从 schema、作业 SQL、样例数据、变更工单里生成候选描述与候选标签，人只做确认或否决。
  - 它降低的是**单个资产的边际登记成本**，并没有改变成本与收益的归属结构。
- **由此得到的**：因为边际成本下降，覆盖率不再完全由人工投入决定，资产规模越大越划算。
  - 又因为产出物是「描述」和「标签」这一层，目录第一次有了能随 schema 自动跟进的部分——而那恰好是人工最容易过期的那部分（§3.2.1 的代价③：Schema 有采集器自动跟上，业务含义没有）。
  - 同一机制也解释了「推荐相关数据产品」「识别潜在使用方」这类条目的来源：它们不是发现新资产，而是在**已登记的资产之间**算相似度。
  - 密级这一项要单独小心：模型可以从样例数据里嗅出个人信息，但它给出的密级只是候选，必须由数据所有者确认——密级错了不是数据质量问题，是合规问题。
- **由此付出的**：
  - ① 新的失败模式——**看起来对的空**：空描述会让人去问，错误描述会被直接采信，而后者还会被向量化放大（§3.2.6）；
  - ② 需要一条「谁确认」的流程，没人负责时确认率会掉到很低，草稿层永久停在草稿；
  - ③ 描述的准确性没有自动指标可证，只能用抽样：随机抽 10 条，要求它指回一段可复现的依据（作业 SQL / 样例 / 工单），抽不到证据的比例就是不可信比例。
- **证据与来源**：【公开】产品侧，各目录厂商的公开材料中都有 AI 助手 / 智能描述 / 智能检索一类能力（§4.3、§7.2 已列），满足判据①的形态；**判据②核不到**（本节未附第三方非厂商公开生产案例）；判据③不满足（置信度与确认语义各家不同）。
  - 判定方法：让厂商演示一条错误的候选描述，看它的系统里「确认」与「否决」是不是两个有记录的状态。
- **成熟度**：**L2（可试点）**——仅有厂商自有材料、接口未统一。可以拿它产草稿，不要让它直接写业务含义列。

```sql
-- 草稿与确认必须分列存放，否则「AI 写的」会被当成「Owner 确认的」
ALTER TABLE asset ADD COLUMN business_def_draft TEXT;   -- AI 生成，允许为空
ALTER TABLE asset ADD COLUMN draft_source  TEXT;        -- 依据类型：job_sql / sample / ticket
ALTER TABLE asset ADD COLUMN draft_evidence TEXT;       -- 证据指纹（可复现，不留原文）
ALTER TABLE asset ADD COLUMN confirmed_by  TEXT;        -- NULL = 尚未确认
-- business_def 仍是 NOT NULL：只有 confirmed_by 非空时才允许写入
-- 两个指标分开看：描述覆盖率 = business_def 非空占比；确认率 = confirmed_by 非空占比
```

#### 5.2.2 自然语言入口：把词汇表的责任从命名者挪到提问者

- **旧做法与它的卡点**：目录检索是关键词与精确匹配，业务方不知道表名就搜不到（§7.7 第六条反模式：检索不排序时，使用者会退回「问熟人」——精确匹配是同一失效的另一个变体：它把责任推给提问者的用词）。
  - 卡点是**词汇表由资产命名者提供**：准确的检索要求提问者先猜出命名者的用词，而命名者的用词又随团队与年代漂移。
- **AI 改变了什么机制**：检索从字符串匹配换成「向量相似 + 倒排 + 标签 / 密级过滤」的混合检索，再由 LLM 重排并生成解释。
  - 它改变的是接口边界的**词汇责任**——提问者用自然语言，「问题到已登记元数据」这一步交给检索层。这一层在书里对应 §3.2.6 的「AI 增强的资产层」。
- **由此得到的**：因为匹配从相等变成相似，所以「必须知道它叫什么」这个前提被去掉，目录对不熟悉命名规范的人第一次可用。
  - 因为生成被限制在检索到的元数据上（§3.2.6 硬约束 1：模型只能「选」，不能「造」），错误形式被限制在「选错」——而选错是可发现的，点开原条目就能看到真实口径与 Owner。
- **由此付出的**：
  - ① 索引是元数据的派生副本，必须随元数据变更增量刷新，否则会出现「检索结果的描述与真实口径不符」；
  - ② 成本随**调用量**增长而不是随资产数增长，与目录「一次采集、多次查询」的成本模型完全不同；
  - ③ 相似度检索没有「查不到」这个行为，Top-K 永远返回东西——所以必须显式造出拒答分支，而阈值过松它就退化成「每次都给一个看起来对的答案」；
  - ④ 描述为空的资产被向量化，只是把「没有信息」变成高维空间里的「没有信息」。
- **证据与来源**：【公开】产品侧同上（§4.3、§7.2）；机制上的三条硬约束（只能选不能造 / 低置信度拒答 / 每个结论挂可点的元数据依据）见 §3.2.6。**判据②核不到**、③ 未统一。
  - 判定方法：只问两个问题——它会不会拒答？答案里的口径能不能点回元数据？
- **成熟度**：**L2（可试点）**——可以试，但拒答与依据必须成对交付，缺一个就退回「规模化地给出错误口径」。

#### 5.2.3 Agent 作为消费方：换掉的是发起者，不是权限模型

- **旧做法与它的卡点**：申请、授权、计费都是给人设计的——表单、审批流、按人或按团队计费。
  - 程序发起消费时走不完这套流程；更根本的是「谁为一次自动消费负责」没有主体。
- **AI 改变了什么机制**：把消费的**发起方**从人换成程序。真正需要变的是把凭据、用途、密级写进同一套元数据，而不是把界面换成人机对话。
  - 只换界面的，是**接口改良，不是架构变化**——这是本方向上最需要说清的一句。
- **由此得到的**：因为消费方能带用途、且用途可被校验，所以「按用途授权」第一次可执行：同一个人在不同用途下可以拿到不同粒度（风控可用、营销不可用），这在只有「角色」一维的权限模型里表达不出来。
  - 又因为消费记录与资产条目共用同一标识（URN），「这个资产被谁在用」可以从消费侧反算——而这正是估值里最难拿到的输入（§3.2.2 的收益归因缺的就是它）。
  - 落地上 Agent 更可能先落在「读」而不是「写」：读可以按用途授权并在执行前拦截；写（自助订阅、回写目录、改口径）会直接改动资产，责任更难落到具体主体。
- **由此付出的**：
  - ① **审计主体缺位**：Agent 以谁的名义取数、出错时责任落到哪个主体，是组织问题不是技术问题；把权限收口到一个「万能服务账号」会同时放大越权半径；
  - ② 使用反馈回写目录会引入噪声——按调用次数自动上调「价值」的机制会把批量轮询也计成价值（§3.2.2 代价②：指标成为目标后失效）；
  - ③ 供应商 / 框架锁定：取数能力依赖某个平台的 API 形态与凭据模型。
- **证据与来源**：主文件 §1.4 把「AI Agent 驱动的数据资产自服务」记入 2025 年，属**方向性记录**；本节未附第三方生产案例，也未见公开材料描述「Agent 走完申请—授权—计费全流程」的生产形态。
  - 判定方法：让 Agent 取一次受密级管控的数据，看拦截发生在**执行前**，还是只出现在事后的审计报表里。
- **成熟度**：**L3（观望）**——仅方向与演示，权限与审计主体未定；现在不要在架构里假设 Agent 能走完授权流程。

```text
把「谁能读、为什么读」变成数据，而不是流程约定

  principal   = agent:trade-assistant@v3      -- 消费主体（带版本，便于把责任追到一次变更）
  on_behalf   = user:<发起人>                  -- Agent 没有资历，必须有人背书
  purpose     = 具体用途（决定粒度与是否允许落盘）
  asset_id    → 密级 + 用途白名单               -- 执行前校验，不通过则显式拒绝
  grant_until = 期限                            -- 到期续签要重新声明用途
  ────────────────────────────────────────────────
  三条硬约束：
  · 拦截点必须在执行前（事后审计只能止损，不能防泄漏）
  · 拒绝要显式返回，不能返回空集（空集会被调用方读成「没有数据」）
  · 每次调用写一行消费记录：principal + on_behalf + purpose + asset_id + 行数
    → 这一列是估值时唯一可用的「被谁在用」的原始输入
```

#### 5.2.4 数据要素市场化：入表改变的是成本归集对象，不是价值度量

- **旧做法与它的卡点**：数据在报表上没有科目，投入只能作为费用发生；对外交易缺少合规与计量依据。
  - 卡点是**缺少一个可辨认的对象**——成本归集不到资产粒度，任何一版估值都没有输入。
- **AI 改变了什么机制**：制度把符合条件的「数据资源」纳入会计处理（按存货或无形资产），改变的是**成本归集的对象**，而不是价值的度量。
  - 这一点必须写清楚：它不产生「数据值多少钱」这个数。两者的分工见下表。
- **由此得到的**：因为归集对象第一次被定义，成本法估值第一次有了统一口径的输入（§3.2.2 的 `asset_cost` 表）。
  - 又因为确认要过「可辨认、可计量、可控制」这类条件，资产化里最容易被跳过的一步——Owner 具体到人、边界可描述——被财务口径反过来强制了一次；这与 §3.2.1 的「关键项 NOT NULL」是同一件事的两种说法。
- **由此付出的**：
  - ① 入表把治理缺口暴露成财务问题：确认条件不满足时，最先响的是财务而不是数据团队；
  - ② 一旦入表，资产就要面对**减值**——数据会贬值，减值是新增的财务风险，也是第一次有人认真问「这份数据还在被用吗」；
  - ③ 交易侧：交易所形态解决的是「这笔交易合不合规、算不算数」，不解决「数据怎么递过去」（§7.2），把挂牌当成分发渠道会落空；
  - ④ 作价入股（5.1 表第 8 行，单独定级为 L3）更远一层，它需要一套双方都接受的计量方法，而这个方法目前没有公开可核验的样本。
- **证据与来源**：【公开】财政部《企业数据资源相关会计处理暂行规定》，2023 年发布、2024 年 1 月 1 日起施行（§3.2.2、§7.7 已引）；交易所形态见 §7.2 的候选表，属「规则与审查」类主体。**判据②核不到**：本节不指名第三方按该规定在定期报告中列示数据资源的具体案例。
  - 判定方法：读规定原文的适用范围与施行日期条款（而不是转述材料里的阶段表），再看一份最近的上市公司定期报告里「数据资源」科目与附注是否披露确认条件与计量方法。
- **成熟度**：**L2（可试点）**——制度已生效且可核验，但确认判定依个案、第三方列示案例本节不指名。可以先把成本归集与口径准备做掉，不要把入表写进价值论证。

| 维度 | 会计口径（入表） | 资产化估值 |
| --- | --- | --- |
| 回答的问题 | 这类资源按存货还是无形资产处理 | 这份数据对我们值多少 |
| 输入 | 取得成本、可辨认性、可控制性 | 成本 / 收益 / 市场可比，加上归因基线 |
| 谁来负责 | 财务与审计 | 数据团队与业务方共同归因 |
| 有减值吗 | 有，且是常规流程 | 无此概念，但收益归因失败等价于减值 |

这张表也是本方向上最容易出错的接口：两者共用成本归集，所以团队很容易把「入表完成」当成「估值完成」，然后在下一轮预算讨论里仍然答不出归因（§7.7 第四条反模式）。

### 5.3 与本主题既有栈的接口在哪

不写「与 X 结合」这种话，写清接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| §3.2.1 资产目录（登记表） | AI 层只写 `business_def_draft` / `draft_evidence` 两列，`business_def` 仍由确认动作写入 | 描述错误由确认者承担；两态混在一列时责任直接消失 | 需要一次加列；已做成 NOT NULL 的字段不动 |
| §3.2.2 估值与 ROI | AI 不产出估值数字，只做成本归集的对象对齐与口径抽取；`method` / `assumption` 仍由人落库 | 估值失真由提交估值的人承担，不能归因到模型 | 已有 `asset_cost` + `asset_valuation` 两表即可对接 |
| §3.2.6 AI 增强的资产层（向量索引） | 索引由元数据变更事件驱动增量刷新；检索结果必须能指回已登记的元数据条目 | 索引陈旧算检索服务的问题，不算元数据的问题 | 必须与「拒答 + 依据」成对交付 |
| 权限与密级 | 检索入口与 Agent 运行时在**执行前**注入密级与用途过滤，拒绝显式返回 | 过滤缺失由入口 / 运行时负责，不得用「没显示」解释 | 取决于 `asset_grant` 有没有 `purpose` 列 |
| 血缘（Ch11 §05 / §09） | 影响面查询的产出是估值里「复用度」的输入；AI 推断出的边不得参与估值与门禁 | 复用度算错由采集方承担（盲区有没有被标记） | 见 [§ 05 血缘前沿](../05-lineage-and-impact/05-lineage-and-impact-section-5-ai.md) |
| 指标与口径资产（§6.2） | 估值按「被引用次数」算，引用关系由口径定义提供，不由调用日志提供 | 口径变更未做影响面评估由定义方负责 | 已有「指标 ↔ 表 ↔ 字段」三向关联的团队可直接接；注意本章 §6.2 给的是「引用而非复制、按引用方与消费量计量」，三向关联这一层在 [Ch4 §08 案例 8.3](../../04-data-assetization/08-data-catalog/08-data-catalog-section-6-sec6.md) |
| 落地路径（§6.5） | AI 补全属于 0→1 阶段的登记层；Agent 消费属于 100→1000 阶段的交付层 | 越阶段引入由引入方负责 | 两处都不要提前：登记层没做好时，消费层拿不到可信元数据 |

这张表里最容易被写反的是最后一行：补全属于登记层（0→1），Agent 消费属于交付层（100→1000）。顺序写反的代价很具体——在元数据还允许缺项的组织里引入 Agent 消费，Agent 只会更快地拿到没人负责的资产；而错误一旦从「人问人」变成「模型直出」，纠错链路就消失了，因为答案格式完整、看起来可信（§3.2.6 失效点）。

### 5.4 公开进展与文献

按类型列出（学术与知识体系 / 官方文件 / 方向线索 / 厂商材料 / 项目文档），每条给出核验入口；括号里是核验方式，不是能力断言。

按 5.1 的判据②，**「第三方（非厂商）生产案例」在本主题下为空**——这就是 5.1 表里没有 L1 行的原因。这类材料的缺失本身就是结论：它意味着任何一家的 AI 资产能力，现在都还没有「别人在生产里用它跑过」这层公开证据。

- **学术与知识体系**：DAMA-DMBOK 2.0（2017）把「数据作为资产」与估值方法列为数据管理知识领域（§3.2.2 已引）；Gebru 等《Datasheets for Datasets》（2018）与 Mitchell 等《Model Cards for Model Reporting》（FAT\* 2019）是「资产必须带机器可读说明」这条要求的学术源头，其字段清单可以直接对照目录的登记项。

- **方向线索（不指名单篇）**：「数据资产估值算法」「目录与 AI 集成」「AI 驱动数据治理」这三个方向在数据管理会议（SIGMOD / VLDB / ICDE）上有连续议程；清单里给的是会议 + 年份的组合，不足以定位到单篇，因此按方向记录。核验方法：按会议论文集检索 `data valuation` / `data catalog` / `data governance`，按篇名与年份核对。
- **厂商材料**：Atlan AI、Collibra AI、DataHub + LLM、Unity Catalog + AI、阿里云侧的 AI 智能盘点（§4.3 以「阿里云 DAS 智能盘点」列项；按 §7.2 的澄清，「DAS」这一缩写通常指数据库自治服务，核对时请按**产品全名**确认该能力挂在哪个产品名下，不要按缩写归类）——§4.3 把它们收在「2024-2025 新工具」一节，年份区间即取自此；Snowflake Marketplace 与 Databricks Marketplace 的升级、交易所侧的产品扩容同属这一类，年份以各自官网的更新日志 / 版本说明页为准（本节不指名具体 release note 名称）。**它们都不是判据②意义上的生产案例**。核验方法：在官方文档里找「元数据 API」与「拒答 / 置信度」两处定义（§7.2 已把「元数据 API 是否公开、是否覆盖业务含义与 Owner」列为选型核验项），而不是看演示视频。
- **一个可复用的公开判定方法**：任何一家的 AI 资产能力，先看三件事——关键项能不能缺项发布、答案能不能点回元数据、被拒绝的检索会不会显式说「不知道」。三件都成立，才配得上「可用于生产的资产层」这个说法；三件都答不出，它现在只是检索前端。
- **项目级文档（能力侧的一手材料）**：目录项目与平台（DataHub、Unity Catalog 一类，产品名见 §4.3）的官方文档里有元数据检索接口的条目——具体入口是该项目的 API 文档（DataHub 的搜索 / GraphQL 接口、Unity Catalog 的元数据 API），两个项目对 AI 的集成窗口同为 2024–2025（§4.3）。核验：看该文档是否同时给出「按业务含义检索」与「返回依据」两类接口——只给搜索框、不给接口的，应当归到界面而不是资产层；接口条目随版本变化，请以官方文档当前版本为准。

前三类材料（学术与知识体系、官方文件、方向线索）给出的是可与本书正文互相印证的一手条目；后两类（厂商材料、项目文档）必须带着**产品全名**去核对，这也是本节把它们分开列的原因。带着能力名去核对，几乎必然会把某家的产品名当成整个能力的名字。

### 5.5 被过度宣传的部分

**「AI 一键盘点，自动把资产目录建起来」**

→ 实际是什么：模型只能生成候选描述与候选标签，它读不到没被登记的东西。
→ 为什么会这样：资产的存在性与责任边界必须由某个系统强制记录，而模型只能读元数据里已有的内容（§3.2.6 硬约束 1）；「盘点」这个词暗示的「发现」与它实际做的「描述」是两件事。
→ 什么时候才会成真：当关键项是写入约束（缺项不能发布）、且存在一条「谁确认」的流程时，AI 才真的把覆盖率推上去；否则它只是把「没人填」变成「没人看」。

**「Agent 自主申请、订阅并使用数据」**

→ 实际是什么：把消费的发起者从人换成程序，需要的是凭据、用途、密级进入同一套元数据（5.2.3），而不是更好的对话界面。
→ 为什么会这样：权限与审计的主体是人，Agent 没有可追责的主体；只换界面属于接口改良，不动权限模型。
→ 什么时候才会成真：当凭据能按用途签发、每次消费能落回一个可追责主体，且执行前拦截成为默认路径。

**「把资产目录做成知识图谱（GraphRAG），让 AI 推理出资产价值」**

→ 实际是什么：图谱承载的是已登记的关系（表 → 字段 → 口径 → 使用方 → 血缘），它能回答「结构上相关」，不能回答「值多少」。
→ 为什么会这样：价值是归因问题，需要基线与对照；图里只有边，没有基线与对照。
→ 什么时候才会成真：当图里带上使用记录、被引用次数与归因基线，且估值仍由方法 + 假设落库产出（§3.2.2）——那时图的作用是为估值提供输入，而不是替代估值。

三条被过度宣传的说法有一个共同结构：**它们都把「生成」当成了「负责」**。生成描述、生成申请、生成关联，都可以自动化；而确认、授权、归因这三件事必须落到一个具体的人和一份可反驳的记录上。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 一、入表从个别试点变成有明确披露口径的常规科目，交易所侧出现可复用的交付与计量约定 | 连续两个报告期出现按该规定列示数据资源的公司，且附注写明确认条件与计量方法；交易所侧出现标准化交付与计量条款 | 长期停留在个别案例；挂牌数量与实际交付量持续不匹配（挂牌被当宣传用） |
| 二、「描述覆盖率 + 确认率」成为目录的运维指标，AI 补全被固定在草稿层 | 目录里出现「候选」与「已确认」两种状态与对应指标；资产治理与 AI 治理合并到同一份元数据上 | AI 只在演示里生成描述，生产里仍以人工填写为唯一来源；或候选描述被直接当作已确认使用 |
| 三、估值从「一个数」变成「一组可反驳的论证」，并出现资产减值评估流程 | 估值记录里 `method` 与 `assumption` 落库并被引用；出现按会计口径做的减值评估 | 仪表盘上只有数字没有方法与假设；被追问归因时仍答不出基线 |
| 四、跨组织数据流通先落到「身份与用途协议」，而不是落到「数据搬运」 | 出现全局标识级身份对齐 + 用途限定的互认材料，且能在一次真实跨组织查询里执行 | 跨组织交付仍是整表导出 + 线下合同，没有可编程的身份对齐 |

四条预测的信号都落在**有没有产生新的记录**（列示、确认率、假设、对齐表），而不是落在「有没有新功能」。功能演示是最容易伪造的信号，这一点在资产化方向上尤其适用：演示里的自然语言取数只需要一份精心准备的元数据。

第三条预测带一个前置条件：它要求估值记录先成为某次评审的输入——§3.2.2 的 `attribution` 字段必须真的被写下来。若估值只是季度汇报里的一个数字，它永远不会变成「一组论证」，因为没有人需要反驳它。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 资产数不到百级、目录还没建 | 把关键项设成写入约束并挂发布流程（§3.2.1） | AI 补全工具是否支持「草稿 / 已确认」两态 | 先买一个 AI 目录前端——元数据可空时它只会放大空 |
| 目录已有，但描述覆盖率在掉 | 先量覆盖率与确认率，把 AI 补全限定在草稿层（5.2.1） | 拒答行为与置信度接口是否成对 | 让模型直接写业务含义列 |
| 消费方开始是应用或 Agent | 把凭据与用途写进 `asset_grant`，执行前拦截（§3.2.6） | 能否按用途签发凭据（而不是角色） | 给 Agent 一个万能服务账号 |
| 被要求做数据资产入表 | 先把成本归集到资产粒度（§3.2.2） | 减值与确认条件的处理口径 | 把入表当价值证明（§7.7） |
| 想对外交易或挂牌 | 先定契约与计量，再谈渠道（§3.2.5、§7.2） | 交易所侧有没有真实交付机制 | 把挂牌当成渠道 |
| 想为 GraphRAG 或联邦预留设计 | 什么都不用预留：先把标识（URN）与关键项做实 | 跨组织身份对齐是否出现可执行样本 | 为「未来的图谱」改元数据模型 |
| 被问「AI 能不能给数据资产估值」 | 先把成本归集做到资产粒度（§3.2.2） | 有没有出现带方法与假设的估值记录 | 让模型生成估值数字——它没有基线期，只会产出一个不可反驳的修辞 |
| 已有 AI 检索入口，但没人用 | 量一次命中率与拒答率，再看描述覆盖率（5.2.1） | 命中率是否随覆盖率一起涨 | 继续优化界面：问题多半在元数据，不在前端 |

第 6 行（想为 GraphRAG 或联邦预留设计）值得单独说：本主题里真正需要预留的只有两样东西——**全局唯一标识**与**关键项的非空约束**。它们不花钱、不用等任何新技术，并且是上面所有方向（补全、检索、Agent 消费、估值、跨组织对齐）的共同前提。

### 5.8 小结

> 本节小结：资产化方向上 AI 真正改变的是**唯一一条机制**——它把「登记」和「找到」这两件事的边际成本从人的注意力上挪开（草稿代替从零写、相似度代替精确匹配），但**没有挪开责任与归因**：描述由谁确认、数据被谁因何使用、这份数据值多少，仍然要由人写下方法、假设与责任主体。
>
> 所以现在能推进的是 L2 那五行：制度侧的入表与交易所先把成本归集与契约计量准备做掉（第 6、7 行），AI 能力侧从第 1 行的草稿态补全起步，第 2、3 行的语义索引与自然语言入口要先有描述覆盖率打底；L3 的六行（Agent 自助消费、图谱推理、盘点标配、估值可视化、作价入股、跨组织联邦）在证据到齐之前不应进入架构假设。而入表这一方向的价值不在于给数据标价，而在于它第一次强制了成本归集与责任到人。
>
