## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

资产化工具的评分表尤其容易失真，因为**「资产目录」这一列几乎全是满分，而它恰恰不区分任何东西**。原表的五个维度（资产目录 / 估值能力 / 市场化 / AI 集成 / 合规适配）里，第一列八个候选全部是 5 分——一个所有选项都拿满分的维度不携带任何信息，真正在比的是另外四列。更麻烦的是"估值能力 3 分"与"估值能力 4 分"的差别从未被定义：是指它内置了收益法模型，还是指它能把成本归集到资产粒度？这两件事对选型的影响完全不同，对分数的影响却相同。

第二个问题是**维度之间不可相加**。资产化是一条「盘点 → 估值 → 治理 → 产品化 → 市场化」的链条（见 [§ 1.1](06-data-assetization.md)），每一段解决的是不同的约束：目录解决"有什么、归谁管"，估值解决"值多少"，市场解决"拿得到、可计量"。把各段分数相加再排序，等于假设"一个更擅长估值的工具"可以补偿"一个交付契约能力弱的工具"——而在真实链条里，后者的缺失会让前者的输出没有落点：**估出来的价值没有交付路径去兑现**。

第三个问题是**打分掩盖了「资格判定发生在什么时候」这个真正的分水岭**。目录类产品都能登记资产、都能展示 Owner 与 SLA；差别在于**关键项缺失的资产能不能被发布**。[§ 3.2.1](06-data-assetization-section-3-sec3.md) 给出的判据很具体：缺业务含义、缺 Owner、缺 SLA 的资产，是被写入约束在创建时拒绝，还是靠事后审计抽样发现。前者是全量且即时的，后者是抽样且滞后的——**同样的功能清单，两种机制下的目录可信度差一个量级**，而这在评分表里找不到对应的一行。

第四个问题是**决策树问的是"你要不要这个能力"，而真问题往往是"你的组织有没有条件用这个能力"**。原 § 7 的决策树以"是否需要数据市场 / 是否需要企业级合规 + 估值 / 是否需要 AI 集成"分叉，这三问都默认"需要就能用上"。但资产化的四条约束里，有两条是**能力的前置条件而不是能力本身**：登记必须被机制强制，定义权必须有归属。一个既没有有权定义口径的中心团队、也没把登记挂进发布流程的组织，无论选哪个目录产品，半年后都会得到一份覆盖率持续衰减的清单。

第五个问题是**把"估值"和"入表"混为一谈**。会计口径与资产估值是两条线：会计规定解决的是"这类资源按存货还是无形资产处理"，估值解决的是"它对我们的业务值多少"。混在一起之后，团队会以为完成入表就等于证明了数据团队的价值，而在下一轮预算讨论里，被问的还是那个老问题——**这份数据带来了什么，能不能归因**。这两件事都必须回答，但它们不能用同一个数字回答。

还有一层更隐蔽的问题：**排序会诱导"一次选对"的期待**。资产化不是一次采购，而是一条按顺序建起来的链——先有可信的登记，才有复用；先有复用与计量的记录，才谈得上估值；先有可交付的契约，才谈得上市场。链条上任何一环缺失，都会让后面各环的投入变成沉没成本。所以本章 7.5 的决策树按"前置条件是否成立"分叉，而不是按"你需要哪些功能"分叉；7.8 的小结也按处境给建议，而不是按分数给排名。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 资格判定时机 | 关键项缺失的资产能不能发布？靠写入约束、发布门禁，还是事后审计？ | 目录的可信度上限由此决定：审计是抽样滞后的，约束是全量即时的 |
| 定义权归属 | 口径与实体的定义权收归中心，还是留在域内？ | 决定跨域指标可比是"结构保证"还是"人工对齐"，也决定需求吞吐的上限 |
| 归因可行性 | 资产的收益能不能归因到具体消费（有基线期、有对照）？ | 不能归因时估值只能退回成本法；方法越有想象力，越依赖不可验证的假设 |
| 交付是否契约化 | 授权、配额、SLA、计量是否挂在同一个入口上？ | 目录只解决"知道有"，契约才解决"拿得到"；没有契约，资产只是一个被登记的名字 |
| 机器可读性 | 元数据能否被应用与 Agent 直接消费、能否自服务？ | 消费方从人变成机器后，"能搜到"不等于"能被消费"——Agent 只能读元数据 |
| 合规与举证 | 需要向谁举证（监管 / 客户 / 会计）？ | 决定哪些项必须登记、估值是否需要外部认可；会计规定解决处理方式，不解决价值高低 |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| **DataHub** | 开源元数据平台（目录 + 字段级血缘） | 事件驱动采集 + 读写分离，血缘查询只查元数据索引与关系图 | LinkedIn 开源，社区广泛采用 | 开源（具体许可请以项目仓库为准） |
| **Apache Atlas** | Hadoop 生态元数据与治理 | 类型系统 + 分类（classification）驱动 | Hive / Hadoop 生态 | 开源 |
| **Unity Catalog** | Lakehouse 统一资产与权限 | 资产与授权在同一命名空间内统一管理，跨引擎共享 | Databricks 生态 | 随平台提供 |
| **Alation** | 商业数据目录 | 以查询日志与协作行为驱动资产画像 | 中大型企业 | 商业 |
| **Collibra** | 企业级治理平台 | 合规与工作流优先：资产必须走流程与角色审批 | 强监管企业 | 商业 |
| **Atlan** | 现代数据目录 | 协作 + AI 助手，把资产管理做成工作流 | 数据团队中等规模、协作密集 | 商业 |
| **阿里云 DataWorks** | 数据资产目录 + 建模发布流程 | 资产登记挂在建模与发布流程上，关键项缺项不能发布 | 阿里云数据中台用户 | 商业（云服务） |
| **阿里数据中台** | 把口径与实体的定义权收归一点 | OneModel（统一建模）+ OneID（统一实体）+ OneService（统一服务） | 阿里及国内跟进的企业 | 方法论 + 云产品 |
| **字节 DataFinder** | 字节内部数据资产入口 | 内部数据平台的资产发现与消费入口 | 字节内部 | 内部自研 |
| **字节 Bytemetric（指标资产）** | 指标即资产 | 指标定义是唯一资产，消费方引用而不复制 | 字节内部（4 业务统一【经验】，出处见 [§ 6.2](06-data-assetization-section-6-sec6.md)） | 内部自研 |
| **华为 / 京东 / 腾讯数据中台** | 中台形态的其它实现 | 同一约束下的不同实现，定义权同样收归中心 | 各企业 / 各云 | 商业 + 内部 |
| **数据网格（Data Mesh）** | 模式（不是产品） | 数据产品的 Owner 就是产出它的域；中央只提供自助平台、全局标准与联邦治理 | 多域、域内有数据工程能力 | 方法论 |
| **Snowflake Marketplace** | 数据交付 / 交易 | 交付以共享形式发生、数据不搬动，按使用与订阅计量 | Snowflake 生态 | 商业（按使用计量） |
| **Databricks Marketplace / AWS Data Exchange / Azure Data Share** | 数据交付 / 交易 | 在各自云内提供订阅式数据交付与计量 | 对应云的用户 | 商业 |
| **阿里云数据市场 / 上海数据交易所 / 贵阳大数据交易所** | 数据流通 / 交易场所 | 以挂牌、合规审查与交易规则为核心 | 国内数据要素市场参与者 | 平台 / 交易所 |
| **AI 增强能力（Atlan AI / Collibra AI / DataHub + LLM / Unity Catalog + AI / 阿里云侧的 AI 盘点与智能检索能力一类）** | 目录之上的消费入口 | 用自然语言与人机协作降低"找到并理解资产"的门槛 | 已上目录、元数据较完整的团队 | 随各自主产品提供 |
| **DaaS / 数据 API（自建交付接口）** | 交付接口 | 把资产封装成可编程访问的接口，配额与鉴权在网关 | 已有 API 网关体系的组织 | 自建 |

**关于「阿里云 DAS」的一处澄清**：原 § 7 的组合把 DAS 列为"资产盘点 + 估值"组件；在阿里云产品体系中，DAS 这个缩写通常指**数据库自治服务**，与数据资产目录不是同一类能力。阿里云侧确实存在 AI 驱动的资产盘点与智能检索能力，但它在不同材料里被挂在不同的产品名下——所以上表**只按能力形态列它，不按缩写归类**（这也是选型表里唯一一处故意不写产品缩写的单元格）。核验方法与产品无关：在厂商产品目录里按**产品全名**而不是缩写检索，看其产品介绍是否包含"元数据 / 资产盘点"这一类关键词，再决定把它放进目录族还是自治运维族；"缩写同名、能力不同"在跨云选型里很常见，核对产品全名比核对缩写可靠【经验】。

这些候选其实只有**四族**，外加一个不是产品而是组织的**模式**：**目录族**（DataHub / Apache Atlas / Alation / Collibra / Atlan / Unity Catalog / 字节 DataFinder，解决"有什么、归谁管"）、**定义权族**（阿里数据中台 / 阿里云 DataWorks / 华为 / 京东 / 腾讯，以及它的反面数据网格，解决"口径谁说了算"）、**交付与市场族**（Snowflake Marketplace / Databricks Marketplace / AWS Data Exchange / Azure Data Share / 阿里云数据市场 / 上海数据交易所 / 贵阳大数据交易所，解决"拿得到、可计量"）、**指标资产族**（字节 Bytemetric 形态，解决"定义能不能被引用"）。同族内部差异小——目录族的差别主要在合规流程与协作方式，而不是"能不能发现资产"；跨族差异是机制性的。**先分族再选，能省掉一半比较**。

**市场平台与交易所有一条机制上的区别**：平台市场（Snowflake Marketplace / Databricks Marketplace / AWS Data Exchange / Azure Data Share / 阿里云数据市场）把交付放在自家平台内，数据不搬动、计量按使用发生，因此交付的边际成本近似为零，代价是消费方必须在该平台上；交易所形态（上海数据交易所 / 贵阳大数据交易所）做的是交易规则、挂牌与合规审查，交付方式由参与方另行约定，它解决的是"这笔交易合不合规、算不算数"，而不是"怎么把数据递过去"【经验】。把两者混为一谈，会出现"上了交易所就等于有了分发渠道"这类误解——**核验方法与产品无关**：问一句"签完之后数据怎么到消费方手里"，答案里有没有具体的交付机制，就分得清是哪一类。

**一个必须分清的区别：候选里有一个不是产品**。数据网格（Data Mesh）是组织与架构模式，不是可以采购的东西——把它与 DataHub、Collibra 并列打分，是最常见的分类错误。它对选型的影响方式是：**先决定定义权放哪，再决定用什么目录来承载这个决定**。反过来，如果先买目录再争论"到底要不要统一口径"，目录就会变成争论的战场，而不是资产的入口。

**「AI 集成」这一维度要落到机制上看**：各家的 AI 能力（Atlan AI、Collibra AI、DataHub + LLM、Unity Catalog + AI、阿里云侧的 AI 盘点能力）本质上都作用在**同一件事**上——把机器可读的元数据变成人和 Agent 都能消费的入口。所以判据不是"有没有 AI 按钮"，而是**它的元数据是否完整、是否可被 API 消费**；元数据不完整的目录加一个 LLM，只会更快地给出更自信的错误答案。用户也可以按"该产品的元数据 API 是否公开、是否覆盖业务含义与 Owner"自行核验。

**许可与锁定的分层**：目录族的开源项（DataHub / Apache Atlas）没有许可成本，锁定来自适配器与内部约定；商业目录（Alation / Collibra / Atlan）的锁定主要来自**元数据的业务含义**——那部分是人工沉淀的，换工具时带不走；定义权族（中台 / 数据网格）几乎没有许可成本，锁定来自组织习惯与建模资产；交付与市场族（Snowflake Marketplace / AWS Data Exchange 一类）的锁定最强，因为交付发生在对方的平台内、消费方也长在对方生态里。**选型语言**：想保留迁移自由，就把人工沉淀尽量放在可导出的元数据里（业务含义、Owner、SLA 都是可导出的字段），而不是放在某个工具专有的评论、标签或工作流状态里。

### 7.3 机制差异：为什么它们表现不同

资产化的四条约束（登记与责任的强制性、价值能否归因、交付是否必须经过契约、定义权落在谁头上）分别对映四个机制。**四个机制的先后顺序有意义**：先有可信的登记（7.3.1），才谈得上定义权放在哪（7.3.2）；先有定义权归属，才谈得上交付与计量（7.3.3）；而估值（7.3.4）是这四者之上最容易被过度工程化的一层——它依赖前三者提供的事实。

**7.1 的六条判据与这四个机制的对应关系**：资格判定时机 → 7.3.1；定义权归属 → 7.3.2；交付是否契约化、合规与举证 → 7.3.3；归因可行性 → 7.3.4；机器可读性 → 7.3.1 与 7.3.3 的交叉（登记项是否完整、能否被 API 消费）。

**这四个机制也解释了"功能表对比"为什么没有用**：同样叫"资产目录"的产品，在 7.3.1 上的差别是**它能不能让一次发布失败**，在 7.3.2 上的差别是**它背后有没有一个有权裁决口径的团队**（多数产品不含这一项，因为这是组织的事），在 7.3.3 上的差别是**授权与计量在不在它的边界内**。功能表把这三件事一并写成"支持资产目录"，于是最重要的差异被抹平了。

#### 7.3.1 资格判定发生在什么时候：写入约束 / 发布门禁 / 事后审计

- **机制是什么**：一份资产"算不算资产"由谁、在什么时刻判定——创建时的写入约束、发布流程上的门禁，还是事后审计的抽样。
- **各候选的实现差异**：

| 判定方式 | 谁在用 | 判定范围 | 失败的样子 |
| --- | --- | --- | --- |
| 写入约束（关键项 NOT NULL，缺项不能创建） | 目录注册表（[§ 3.2.1](06-data-assetization-section-3-sec3.md) 的 asset 表形态）、阿里云 DataWorks 的发布流程 | 全量、即时 | 字段列表过长导致登记成本高，产出方抗拒 |
| 发布门禁（CI / 发布流程检查关键项） | 指标资产（字节 Bytemetric 形态）、数据网格的契约发布 | 全量、即时 | 门禁过严会被绕过（走例外通道） |
| 事后审计（抽样检查覆盖率） | 多数目录类产品的默认落地方式 | 抽样、滞后 | 覆盖率随时间衰减，Owner 失联、口径过期 |

- **由此必然导出的性质**：因为写入约束是**全量且即时**的，所以"无主资产""用途不明的资产"在创建时就被拒绝——责任由约束保证，而不是靠事后补录；**代价是登记成本落在产出方、收益落在消费方**，所以强制登记的字段列表必须短，字段越多、绕过动机越强。反过来，因为事后审计是**抽样且滞后**的，所以它的结论永远落后于资产的实际状态；**代价是覆盖率会单调衰减**，最终目录里剩下的是一份"曾经登记过什么"的历史记录。
- **公开证据**：本仓 [§ 3.2.1](06-data-assetization-section-3-sec3.md) 给出了把关键项做成 `NOT NULL` 与把登记挂上发布流程的具体结构；把"关键项缺项的资产不能发布"作为目录落地判据的表述，也见 [§ 6.1](06-data-assetization-section-6-sec6.md) 归纳的阿里资产准入五条件（有业务含义、有 Owner、有 SLA、有下游使用者、有口径定义）【经验】。
- **失效条件**：当"资产"的边界没有收紧（把中间表、临时表也当资产登记）时，强制登记会把成本推高到不可承受——十万量级的表如果全部登记为资产，维护负担会按资产数线性增长（量级见 §7.4），于是团队必然去找例外通道，约束随即失效。**先收紧资产准入，再收紧登记约束**，顺序不能反。
- **选型落点**：判断一个目录产品是否真的能承担资产化，可核验的不是"它支持多少个数据源"，而是**它能不能让"缺 Owner 的资产"发布失败**；如果产品本身只是登记簿，那么门禁必须由你自己的发布流程承担——此时选的是一个注册表，不是一套治理能力。
- **进一步看：登记项要短到什么程度**。既然登记成本由产出方承担，字段列表就应当只有一个最小集合：**业务含义、Owner（具体到人）、SLA、密级，加一个全局唯一标识**。其余项都应由采集或计算得到——字段与分区由 SQL 解析、血缘由作业解析、质量分由规则计算、成本由账单归集。这样划分的理由不是省事，而是分工：**机器擅长回答"是什么"，人只擅长回答"为什么"**【经验】。把"是什么"的项也交给人填，等于让最贵的一环去做最机械的事。
- **进一步看：为什么"资产准入"要先于"登记约束"**。如果什么表都算资产，强制登记就等于要求全公司为每一张中间表写业务含义——约束越严，绕过动机越强，最后团队会去申请例外，约束名存实亡。所以正确的顺序是**先给"资产"设门槛（有业务含义、有 Owner、有 SLA、有下游使用、有口径定义），再把门槛做成强制项**：前者把资产数量收敛到可维护的规模，后者保证收敛之后的每一项都可问责。这两步的顺序颠倒，是目录类项目最常见的失败路径。
- **一个常见误判**：把"元数据采集覆盖率"当成资产化的进展。采集覆盖率衡量的是**机器读到了什么**（字段、分区、血缘），资产化要的是**人认可了什么**（业务含义、责任、承诺）。前者可以靠采集器在一周内推到很高，后者要在每一次发布上收一次税。用采集覆盖率汇报进展，会让项目在数字上成功、在效果上失败——**这两类指标经常同时出现在同一张周报里，而只有后者与资产化目标同向**。

#### 7.3.2 定义权落在哪：收归一点（中台）还是下推到域（Mesh）

- **机制是什么**：口径与实体的定义权放在哪一层。这是资产化里唯一一条**不可能两全**的约束：收归一点保证可比，下推到域保证贴合。
- **各候选的实现差异**：阿里数据中台（OneModel / OneID / OneService）与华为 / 京东 / 腾讯的中台形态，把定义权收归中心，供给路径是"中心建设 → 业务消费"；数据网格把定义权下推到域，数据产品的 Owner 就是产出它的域，中央只提供自助平台、全局标准与联邦计算治理；目录族**不决定定义权**——它可以是任何一种架构的目录层，这一点经常被误读为"上了目录就等于统一了口径"。
- **由此必然导出的性质**：因为定义权收敛到一个点，所以跨业务指标在**定义上**就可比——不是靠"事后对口径"对齐，而是根本只有一份定义；**代价是需求吞吐等于中心团队的产能**，而业务需求是并行产生的。反过来，因为数据产品的 Owner 就是产出它的域，所以业务语义不需要跨组织翻译；**代价是自助平台能力是硬前提**，域内没有数据工程能力时，"域自治"会反转成分布式烟囱，比中台更差——中台至少保证了一份口径，退化后的网格连口径都没有。
- **公开证据**：本仓 [§ 3.2.3 / § 3.2.4](06-data-assetization-section-3-sec3.md) 对这两种相反解法各自给出了结构、代价与失效点，并指出判断是否真做中台的可核验标准是"是否存在一个有权定义口径的中心团队 + 一份被多个业务共用的模型"；数据中台这一方法论与阿里在 2010 年代中期的对外输出密切相关（业界常引用的时间点是 2015 年前后），但"谁于何时首次提出"在不同材料里表述不一、本书不指向单一出处，因此这里只把年份当作量级参考而非定论【经验】；数据网格作为一种架构方法论由 Zhamak Dehghani 在 2019 年前后提出【公开】（来源：其公开文章与著作；具体年份与表述请自行核验）。
- **失效条件**：中台的失效条件不是规模而是**需求同质性**——当中心团队的交付吞吐低于业务需求产生的速度时，业务方的理性选择是绕开中台自建，"中台 + 域内烟囱"并存、两套口径重新分叉，而成本是双份的；网格的失效条件是**域内自助能力**，判断方法是"一个业务域的团队，能否不依赖中央团队独立交付一个数据产品"。
- **选型落点**：这一条不能靠比较产品功能来决断，要先量三个数：同一主题数据被重复建设的次数、跨业务口径冲突的频次、中心团队当前的排队时长。前两个数支撑"该不该集中"，第三个数决定"集中能不能撑住"。
- **进一步看：中台与网格之间还有一段中间地带**。这两者不是非此即彼：实际组织里常见的第三种形态是**联邦式目录 + 中心只做标准**——中心不持有数据、不定义每个业务口径，但定义"指标必须怎么写、实体怎么标识、契约里必须有哪些项"这类互操作标准，各域按标准自行建设。它比网格轻（不需要中央模型），比中台灵活（不承担需求队列），**代价是跨域指标的可比性从"结构保证"降级为"标准保证"**：标准能被遵守到什么程度，取决于审计与激励，而不是取决于只有一份定义。判断该取哪一档，看你能接受哪一种代价——中心贵还是口径不齐贵。
- **进一步看：这一条为什么是组织问题而不是技术问题**。定义权收归中心，意味着业务侧失去"自己定义活跃用户"的权限——这是一次真实的权力转移，不是一次技术上线。因此中台项目失败的原因很少是"模型建不起来"，而是**没有人有权在组织层面裁决口径**；反过来说，判断一家公司是否真的在做中台，可核验的不是"有没有中台产品"，而是"当两个业务对同一个指标有分歧时，谁的话算数"。

- **进一步看：两种解法的收益都是"时机相关"的**。中台的收益随业务相似度上升——业务越像，统一模型越能覆盖；网格的收益随域数与域内能力上升——域越多、越专业，下推的收益越大。所以同一家公司在不同阶段的最优解可以不同：**创业期集中（快），多业务期联邦（能容纳差异）**，而这不矛盾，只是约束变了。反过来说，最危险的是**在一个约束已经变化的组织里沿用旧答案**：业务早已异构却还在往中心加需求，或者域内根本没人建管道却先分了所有权。

#### 7.3.3 交付是否契约化：目录解决"知道"，市场与网关解决"拿到 + 计量"

- **机制是什么**：资产的"被发现"与"被交付"是不是同一个入口。目录是读模型，交付是接口——中间隔着授权、配额、SLA 与计量。
- **各候选的实现差异**：目录族只解决发现（搜到表、看到 Owner 与 SLA）；市场族（Snowflake Marketplace / Databricks Marketplace / AWS Data Exchange / Azure Data Share / 阿里云数据市场）与交易所形态（上海数据交易所 / 贵阳大数据交易所）把交付做成可订阅、可计量的契约；数据网格把接口与 SLA 写进数据产品本身（`interface_ref` + `sla` + `version`，见 [§ 3.2.4](06-data-assetization-section-3-sec3.md)）；指标资产则把交付做成"引用"——消费方读同一份结果，不重算。
- **由此必然导出的性质**：因为市场把交付做成了可计量契约，所以复用可以产生价格与结算；**代价是每一条被交付的资产都要有人维护契约与 SLA**，而契约过期比数据过期更贵——过期的数据只是旧，过期的契约会让消费方按错的承诺做规划。因为指标资产的成立前提是"消费方只能引用、不能本地重写"，所以口径改一处、所有引用方同步生效；**代价是失去灵活性**，某个消费方想改一处口径就必须推动上游改资产定义，而这会引发一轮影响面评估。
- **公开证据**：本仓 [§ 6.2](06-data-assetization-section-6-sec6.md) 把"复制 SQL"与"引用指标资产"的差别描述为资产能否存在的问题，并指出消费方一旦能在本地重写，资产立即退回为代码片段【经验】；市场族的交付形态与计量方式在各平台的官方文档里有完整说明，且该结论不依赖任何具体版本的费率数字——只需核对两条形态特征：**交付是否在平台内完成**（数据不搬动、以共享形式授权）与**计量是否按使用或订阅发生**【经验】。核验方法：任取一个平台市场，按其产品全名检索官方文档中的"数据共享 / 数据交换 + 计费方式"章节，看交付与计量是否都在该产品边界内。
- **失效条件**：当组织内部没有可比交易、也没有人愿意为交付背书时，"内部市场"会退化成内部计费的样子——有一条计量规则，但价格不由供需决定；此时市场的收益（定价与结算）不成立，退回目录 + 内部 SLA 反而更实在。
- **选型落点**：判断要不要上市场族，问一个具体问题：**这份资产有没有一个愿意为它的 SLA 签字的人**？没有签字方，就不是数据产品；有签字方但没有计量，就只能做内部结算而不能对外变现。目录 + 契约 + 计量三者中少任何一项，"市场化"这个名字都不成立。
- **进一步看：计量为什么能把复用从"要求"变成"收益"**。在没有计量时，复用只能靠治理要求推动——省下的是别人的人力，成本是产出方多维护一个接口；一旦把消费量计入资产的账（谁引用了、用了多少次），复用的收益就落到了产出方自己身上：多一个消费方带来的边际成本近似为零（大家读同一份结果），而重复建设的成本是每个消费方各自再付一遍【推算：若每个消费方独立实现同一份指标的成本为 C，N 个消费方各自实现的总成本为 N × C；引用同一份资产的总成本 ≈ C + N × s（s 为单个消费方的接入成本），当 N ≥ 2 且 s ≪ C 时引用更省】。这条推导就是"指标即资产"在成本上成立的原因。

**为什么授权与计量必须与资产标识同源**：如果申请在 A 系统、授权在 B 系统、计量在 C 系统，那么每一处都要各自维护一份"资产 → 谁可以用"的映射，这三份映射会各自漂移；一旦漂移，"谁在用这份数据"就没有单一答案，而它恰好是合规举证与成本分摊共同依赖的那个答案。把三者绑到同一个资产标识（URN 一类）上，是把三份映射压成一份的最小代价。**这也是"上目录"与"资产化"的分界**：目录只需要一份可检索的清单，资产化需要一份所有流程都能引用的标识。

#### 7.3.4 估值是否可被反驳：方法与假设落库 vs 一个数

- **机制是什么**：一个估值数字是否附带"它是怎么算出来的"。三大方法（成本法 / 收益法 / 市场法，见 [§ 2.2](06-data-assetization.md)）成立的前提完全不同：成本法只要求成本可归集；收益法要求收益可归因、折现假设可辩护；市场法要求存在可比交易。
- **各候选的实现差异**：多数目录产品把估值当"一个字段"（填一个数），少数治理平台把估值做成带方法与审批的流程（Collibra 一类以流程与角色为核心）；[§ 3.2.2](06-data-assetization-section-3-sec3.md) 给出的结构是把方法（cost / income / market）、假设（折现率、收益期、可比交易）与归因依据都落库，并允许"未归因"成为一个合法状态。
- **由此必然导出的性质**：因为方法与假设被强制记录，所以读者能判断两个数字是否可比——**成本法与收益法给出的量级可以差出数倍，混在一张表里比较会得出完全相反的结论**；**代价是估值从此带着一堆需要维护的假设**，折现率与收益期没有任何一个能由数据本身验证。反过来，如果估值只是一个字段，**代价是它无法被反驳**：不可反驳的数字在预算会上无往不利，因为它不需要为任何前提负责。
- **公开证据**：DAMA-DMBOK 2.0（2017）把数据估值与"数据作为资产"列入数据管理知识领域；成本法 / 收益法 / 市场法来自无形资产评估的既有方法体系；财政部《企业数据资源相关会计处理暂行规定》自 2024 年 1 月 1 日起施行，规定了符合条件的数据资源如何按存货或无形资产处理——它规定的是会计处理方式，不是"数据值多少钱"【公开】（来源：DAMA-DMBOK 2.0、财政部规定；年份与条文请以官方发布为准）。
- **失效条件**：当收益无法归因（没有基线期、没有对照、收益与数据投入之间有多个同时变化的中介变量）时，收益法估值会反转成"把业务增长的一部分记到数据头上"；此时唯一诚实的做法是退回成本法，并把"尚未归因的收益"列为清单而不是金额。
- **选型落点**：**先能做成本归集，再谈估值方法**。成本归集到资产粒度是成本法唯一的输入，也是 ROI 公式的分母；如果连"这份资产一年花了多少（含人力分摊）"都取不到，那么任何估值方法产出的都是叙事而不是数字。
- **进一步看：ROI 公式里最脆弱的不是分子而是分母**。[§ 2.2](06-data-assetization.md) 的 ROI 模型是**带折现**的形式 `ROI = (Σ_t B_t/(1+r)^t − Σ_t C_t/(1+r)^t) / (Σ_t C_t/(1+r)^t)`（`B_t` / `C_t` 为第 t 期收益与成本，`r` 为折现率）；当折现率取 `r = 0` 时，它退化为不带折现的 `ROI = (ΣB − ΣC) / ΣC`——[§ 3.2.2](06-data-assetization-section-3-sec3.md) 的 SQL 注释里用的正是这个简化式，因为那里要强调的是"只有当 B 可归因时这个比才有含义"，而不是折现本身。**两个式子的分母要求相同**：ΣC 要能归集到资产粒度（存储 + 计算 + 人力分摊，见 [§ 3.2.2](06-data-assetization-section-3-sec3.md) 的 `asset_cost` 结构），分子 ΣB 要能被归因。多数组织的实际情况是：**分母勉强能取到（账单 + 人力分摊），分子取不到（收益与数据投入之间有多个同时变化的中介变量）**。此时唯一诚实的做法是把 ROI 写成"成本已知、收益未归因"，而不是给它一个看起来精确的分母与一个编出来的分子——**一个不可反驳的 ROI 数字，在预算会上无往不利，也因此在下一个周期里最先被质疑**。
- **进一步看：估值为什么最容易被过度工具化**。估值的三个方法里，成本法的输入是成本（可由账单与人力分摊得到），收益法与市场法的输入是假设（折现率、收益期、可比交易）。工具能做的只有后者——把假设填进公式、把数字算得漂漂亮亮；而**能算得漂亮恰恰是它危险的地方**：一个带小数点的估值会让人忘记它的输入是猜的，而一个成本法算出来的"不好看"的数字反而更接近可信。所以选型时对"估值功能"的正确期待是：**它应当强迫你填写方法与假设，而不是替你隐藏它们**。

### 7.4 成本结构对比（不是价格表，是成本函数）

资产化的年成本可以写成：

```
年成本 ≈ 平台订阅或许可          （商业治理平台；开源方案此项近似为零）
       + 元数据存储与检索        （随资产数缓增，通常不是主导项）
       + 登记与口径维护人力 × 资产数
       + 契约与 SLA 维护 × 被交付的资产数
       + 估值与评审            × 每年评审次数
```

**这条式子的主导项是人力，不是许可**。这与可观测性、成本治理那几章不同——那几章里用量是主导项；资产化里用量（元数据存储、检索）几乎可以忽略，真正随资产数线性增长的是一份**由人承担的维护契约**：业务含义要随口径变化更新、Owner 要随组织调整改派、SLA 要随上游变更复核。

| 候选族 | 主导项 | 隐性成本 | 成本函数形状 |
| --- | --- | --- | --- |
| 目录族（DataHub / Atlas / Alation / Collibra / Atlan / Unity Catalog） | 许可 + 采集与接入人力 | 元数据过期（业务含义失效而无人更新）；实体对齐与去重 | 固定 + 随资产数缓增 |
| 定义权族（中台 / 网格） | 中心团队产能（中台）或域内工程能力（网格） | 中台的排队成本与双份建设；网格的自助平台建设与标准维护 | 中台近似固定产能上限；网格随域数增长 |
| 交付与市场族 | 契约与计量运维 | 契约过期、授权漏配；跨组织合规审查 | 随被交付资产数线性 |
| 指标资产族 | 指标平台 + 口径评审 | 引用统计必须可靠，否则下线决策没有依据 | 随指标数与引用方数增长 |

**【推算】档的数量级示例（推导链写明）**：

- 资产维护人力：若一名全职数据治理工程师一年可稳定维护 200–500 个资产【经验】（业务含义与口径维护 + Owner 责任确认 + SLA 复核），则 1 万个资产需要约 20–50 人年【推算：10000 ÷ 500 = 20；10000 ÷ 200 = 50】。
- 不设准入标准的代价：若把十万量级的表全部登记为资产【经验】（大型集团的表数量通常在十万上下），按上一条的人均维护量推算需要 200–500 人年【推算：100000 ÷ 500 = 200；100000 ÷ 200 = 500】——这远超任何组织的数据治理编制。所以"资产准入标准"不是洁癖，而是成本函数的必然要求：**资产数量必须先收敛到可维护的规模，才谈得上估值与复用**。
- 契约成本：被交付的资产要有人维护 SLA 与授权，这份人力与"被交付资产数"线性相关，而与总资产数无关。行业里可观察到的量级是，一名工程师可同时维护几十到两百条契约【经验】；据此，200 条契约约需 1–4 人【推算：200 ÷ 200 = 1；200 ÷ 50 = 4】。因此"把更多资产变成契约化交付"的边际成本是一份稳定的人力增量。

**各族在这条式子上的形态**：

```
目录族：  年成本 ≈ 许可（或 0）+ 采集接入人力 + 登记与口径维护人力 × 资产数
定义权族：年成本 ≈ 0（工具）   + 中心团队编制（中台） 或 域内工程能力（网格）
交付族：  年成本 ≈ 0（工具）   + 契约与计量运维 × 被交付资产数 + 合规审查
指标族：  年成本 ≈ 平台成本     + 口径评审人力 × 指标数 + 引用统计与下线成本
```

**隐性成本里最贵的一项是元数据的过期**：Schema 有采集器自动跟上，业务含义没有——它由人写入、随业务变化而过期，而它恰好是资产化里最有价值的那部分（决定这份数据能不能被信任使用）。这一项没有出现在上面的式子里：**它不产生账单，却会让所有基于它的决策（复用、估值、授权）建立在过期信息上**。这也是"元数据新鲜度"必须与"覆盖率"一起度量的原因——只报覆盖率的周报会把这一项完整地藏起来。

**一个容易被忽略的对比**：目录族的许可费在整条函数里通常不是主导项，**但换工具的代价很大**——元数据本身要重新采集与灌入，历史的口径、Owner、SLA 记录要与新工具的模型对齐。这解释了一个现象：很多团队明知手上的目录不够用也不换，因为换的成本落在"重新登记一遍"上，而重新登记一遍正是资产化里最贵的那件事。

**成本函数里的另一项回报：复用**。资产化的收益不是"省下许可费"，而是**同一个资产被第 N 个消费方使用时不再重复建设**。把这一项写进成本函数，形状是这样的：重复建设路线下，同一份主题数据的成本随消费方数量线性上升（每个团队各自采一遍、算一遍、维护一遍）；资产化路线下，第一次建设的成本不变，之后每多一个消费方只增加接入成本。**这解释了为什么"复用率"是资产化最核心的指标**：它不是治理口号，而是这条函数里唯一能把"随 N 线性增长"改写成"近似常量 + 缓增"的杠杆。反过来也成立——**如果消费方数量根本不会增长（同质需求只有一两个），资产化的收益不成立**，此时建目录、做估值的投入回报很低。

**成本函数怎么用：三个常见误判**

1. **把许可费当成主成本**。报价单上的数字是这条函数里最容易比较、也最不重要的一项；真正决定成败的是"维护人力能不能摊开"。一个更贵的目录如果能让登记项更短、采集更自动，总成本反而更低。
2. **把"登记完成"当成"资产可用"**。登记只解决"知道有"；资产能不能被用，取决于消费路径（申请、授权、交付）是否接在同一个标识上。只做登记时，函数的收益项（复用）不会发生，而成本项（维护人力）照样在涨。
3. **把复用率直接当考核指标下发**。复用率是重要指标，但一旦成为目标，就会出现"把消费方拉进来凑数"这类动作；真正该问的是**被复用的资产是否仍在维护、口径是否仍被认可**。指标成为目标后失效这一条在资产化里尤其明显，因为资产的价值本来就难以度量。【经验】

### 7.5 决策树（每个分支都要有阈值依据）

```
① 关键项缺失的资产，今天能不能被挡住？
├─ 挡不住（工具只是登记簿，发布不受它约束）→ 先把发布门禁接上：
│    DataHub / Apache Atlas / Unity Catalog 一类可直接承载注册表；
│    门禁挂在你自己的 CI / 发布流程上（结构见 § 3.2.1）
└─ 能挡住 → 继续
   │
② 口径与实体的定义权交给谁？
   ├─ 有足够同质、可复用的共性需求，且存在一个有权定义口径的中心团队 → 集中式：
   │     阿里数据中台（OneModel / OneID / OneService）/ 阿里云 DataWorks /
   │     华为 / 京东 / 腾讯数据中台形态
   └─ 域内具备数据工程能力与自助平台 → 联邦式：数据网格（Data Mesh）
         └─ 若"一个域能否不依赖中央团队独立交付一个数据产品"答不上来 → 不下推所有权，先建平台
         │
③ 交付要不要经过契约与计量？
      ├─ 只在组织内、只需解决"知道有" → 目录族：
      │     DataHub / Apache Atlas / Alation / Collibra / Atlan / Unity Catalog / 字节 DataFinder
      └─ 要跨组织交付、要按量计费或对外变现 → 市场 / 交易所形态：
            Snowflake Marketplace / Databricks Marketplace / AWS Data Exchange / Azure Data Share /
            阿里云数据市场 / 上海数据交易所 / 贵阳大数据交易所
```

**阈值依据**：

- **①「挡得住 / 挡不住」**：依据来自资格判定机制（§7.3.1），这是一条二分的能力边界，可自行核验——拿一张缺 Owner 的表走一遍发布流程，看它能不能上线。之所以把它放在第一个节点，是因为后面两个节点的选择都以"登记可信"为前提：一份覆盖率会衰减的清单，无论把定义权放在哪、无论接不接市场，都不可用。
- **②「中心 / 域」**：判据不是公司规模，而是两个可核验的条件——需求是否足够同质（同一批实体与口径被多个域重复建设），以及"一个域能否不依赖中央团队独立交付一个数据产品"。两个条件都用你自己的组织事实回答，不需要任何外部数字。这条依据来自 §3.2.3 / §3.2.4 的失效点：中台在需求异构时反转成排队，网格在自助能力不足时反转成分布式烟囱。
- **③「内部知道 / 跨组织交付」**：阈值是"交付对象是不是你能用行政手段协调的同一个组织"。在组织内部，授权与配额可以靠流程解决；跨组织时必须有契约与计量，因为此时信任不能靠内部流程替代，而这一点无法用金额衡量。依据来自交付契约机制（§7.3.3）。

**这棵树的使用方式**：把三个问题依次问一遍，**任何一问答不上来，就停在那里补前置条件，不要跳到下一问去比较产品**。资产化项目的失败大多是"跳步"：在登记不可信的情况下争论定义权，在没有定义权的情况下上市场，在没有消费路径的情况下做估值——每一步都在用后一环的复杂度掩盖前一环的缺失。

**为什么树上不放金额阈值**：资产化的成本函数以人力为主导项，而人力成本在组织之间的差异极大，任何"预算超过多少才该上某类工具"的阈值都会立刻失真；更重要的是，这条链上的每一步都有一条**可核验的前置条件**（能不能挡住、能不能独立交付、有没有人签 SLA），它们比金额更能决定成败。

**三个节点分别对应 7.1 判据表中的第 1、2、4 条**：① 对应"资格判定时机"，② 对应"定义权归属"，③ 对应"交付是否契约化"。其余三条判据（归因可行性、机器可读性、合规与举证）不进决策树，它们更像是**在已选定的族内做取舍的筛子**：同样是目录族，需要向监管举证的组织会把流程与角色权限放在第一位（Collibra 一类），以 Agent 为消费方的组织会把元数据的 API 完备度放在第一位（Unity Catalog / DataHub 一类）。

**树上没有"要不要买商业产品"这一问，是因为它由前三个节点派生**：需要向监管举证的组织会选流程与角色优先的商业平台（见 §7.6 矩阵第二行），只需要注册表与发布门禁的组织用开源目录即可。**先立判据、后选产品**，采购决策自然落在树的末端而不是开端——这也是本章不提供打分表的原因之一。

**无论选哪一族，有三件事必须先做**：① **收紧资产准入**（先定义什么算资产，否则登记约束会被滥用与绕过）；② **把登记挂进发布流程**（否则覆盖率随时间衰减）；③ **让消费路径回到资产标识**（否则目录只解决"知道有"，人还是要换系统走流程）。这三件事都与选哪个产品无关，也正是"买了工具却没有资产化"这个结果最常见的三个断点。

### 7.6 选型矩阵与组合

| 你的处境 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 资产数到千级、多数表说不清用途 | DataHub / Apache Atlas 一类做注册表 + 把登记挂进发布流程 | 商业目录 | 没有发布门禁时，花钱买功能只是把一份会衰减的清单换个界面 |
| 强监管、需要向监管或客户举证 | Collibra（流程与角色优先）+ DataHub 或 Unity Catalog 做技术血缘 | Alation / Atlan | 监管举证要的是流程留痕与角色审批，不是更漂亮的检索 |
| 多域、域内有数据工程能力 | 数据网格（Data Mesh）+ 目录族做跨域发现 | 集中式中台 | 自助能力不足时网格会退化成分布式烟囱，比中台更差 |
| 多业务重复建设同一批实体、口径冲突频繁 | 集中式（阿里数据中台 / DataWorks / 华为 / 京东 / 腾讯形态） | 数据网格 | 需求异构时中心的排队会逼业务绕开自建，成本变双份 |
| 需要对外变现 / 跨组织交付 | Snowflake Marketplace / AWS Data Exchange / 阿里云数据市场一类 | 内部 DaaS | 没有契约与计量的交付既无法定价，也无法持续 |
| 指标口径散落、同一指标多个实现 | 指标即资产（字节 Bytemetric 形态：引用而非复制） | 目录 + 文档规范 | 允许消费方本地重写时，资产立即退回为代码片段 |
| 消费方开始是应用与 Agent | 元数据机器可读（Unity Catalog / DataHub 的 API 一类） | 以人工检索为主的目录 | Agent 没有资历可问，只能读元数据；"能搜到"不等于"能被消费" |
| 数据资产要入表、要计入会计科目 | 先把成本归集到资产粒度，再谈估值方法 | 直接上收益法估值 | 会计规定解决的是处理方式而不是价值高低；没有成本归集就没有成本法 |
| 已有目录但没人用 | 先查消费路径是否接回目录（申请、授权、计费是否在目录里） | 换工具 | 目录的价值是覆盖率 × 使用率；换工具不改变"多一次跳转就流失一部分人"这条负循环 |
| 资产条目只增不减、检索结果越来越脏 | 用引用与消费记录驱动下线（引用统计 + 最后被消费时间） | 靠人工评审清理 | 只增不减的目录会让命中率下降，使用者最终回到"问熟人" |
| 数据已经在云上、但交付靠人工导文件 | 先建可寻址的交付接口（DaaS / 网关方式） | 直接上市场族 | 没有计量与授权的交付无法定价；先有交付机制，市场才有意义 |
| 只有一两个消费方、同质需求很少 | 先别做资产化，把这两条链路维护好 | 全面铺开目录与估值 | 资产化的收益来自"第 N 个消费方"，N 很小时收益不成立 |

**常见组合 4 条**（原 § 7.3 的三条保留，各自补上职责边界与运维代价）：

1. **阿里数据中台 + 阿里云 DataWorks + 阿里云 DAS** —— 职责边界：中台给定义权与业务化能力（统一建模 / 统一实体 / 统一服务），DataWorks 给技术平台与发布流程，DAS 在原组合里承担"资产盘点 + 估值"（见 §7.2 的澄清：DAS 通常指数据库自治服务，采购前请按官方产品定义核验它是否承担资产盘点，以及由哪个产品承担估值）。运维代价：三者绑定同一云生态，离开要重做建模与流程；定义权集中后，中心团队的产能成为所有数据需求的队列，排队一旦过长，业务就会绕开自建。
2. **Collibra + Snowflake Marketplace + DataHub** —— 职责边界：Collibra 管合规与流程（谁能访问、需要什么审批），Snowflake Marketplace 管交付与计量，DataHub 管技术血缘与影响面。运维代价：同一个资产在三处有三份描述，需要固定的同步机制；一旦不同步，"合规清单"与"技术血缘"会互相打脸。
3. **Atlan + Unity Catalog + Snowflake** —— 职责边界：Unity Catalog 提供湖仓侧的资产与授权命名空间，Snowflake 提供数仓侧的消费入口，Atlan 做跨两侧的目录与协作。运维代价：跨两套权限模型，授权仍要在各自平台落地，Atlan 层看到的权限是投影而不是事实——查权限时要回到源头平台确认。
4. **指标资产 + 目录族 + 发布门禁**（补充分组）—— 职责边界：指标平台把定义做成唯一资产（消费方引用而不复制），目录族负责发现与复用引导，发布门禁负责"缺项不发"。运维代价：指标被引用之后，下线要给出影响面评估与迁移方案；引用统计必须可靠，否则"哪些资产该退场"的判断没有依据。

**这四条组合的共同代价**：它们都得面对同一件事——**同一个资产在多个系统里有多份描述**（目录一份、血缘一份、权限一份、指标定义一份）。这份重复不是设计缺陷，而是分工的必然结果；代价是必须有固定的对齐机制（谁负责、多久对一次），否则最先出问题的一定是"缺 Owner 的表在 A 系统里有 Owner、在 B 系统里没有"这类不一致。

**组合的规模前提**：四条组合都至少需要一个人负责"资产标识对齐"这件长期工作。团队规模太小时这份人力摊不开，规模大时又必须有专职角色。判断能不能上组合，可以看一个具体信号——**今天关于资产的争议是"这份数据归谁管"（登记问题）还是"这份数据算不算资产"（准入问题）**：如果是前者，说明准入已经收敛，可以上组合；如果是后者，先回去收紧资产准入，组合只会把争议放大到更多系统里。

**四条组合里有一个共同的选择要先做**：**要不要把"授权"收进同一套标识**。收进来，目录就成为消费的入口，资产化链条完整；不收，目录就停在"知道有"这一格，交付回到各自的系统。这个选择与产品无关，它取决于你愿不愿意让资产的所有权人承担授权责任——**授权落到资产 Owner 身上，是资产化真正开始的地方**。

### 7.7 选错的代价与迁移成本

**反模式：先建目录，指望大家自然登记** —— 症状：买了工具、开了账号、发了通知，半年后覆盖率停在低位。后果：因为**登记的成本落在产出方、收益落在消费方**，所以没有强制机制时，新资产的登记率会随时间下降，而目录的价值是"覆盖率 × 使用率"的乘积——用的人少，产出方就更没有登记压力，形成负循环。正确的做法：把关键项做成写入约束或发布门禁（缺项不能发布），并让消费路径（申请、授权、计费）回到目录里，打破负循环。

**反模式：先上数据网格，但域内没有自助能力** —— 症状：为了摆脱中心团队排队，把所有权下推到各域。后果：因为每个域都在用各自的方式建管道、定口径，而中央已经没有统一模型可以对齐，所以结果比集中式中台更糟——中台至少保证一份口径，退化后的网格连口径都没有，而成本（重复建设 + 跨域对不上）是即时的。正确的做法：**先让平台能自治，再让组织自治**；判据是"一个业务域能否不依赖中央团队独立交付一个数据产品"。

**反模式：把估值精确到元，但收益无法归因** —— 症状：要求每个资产给出精确的年度价值。后果：因为折现模型对输入假设极度敏感（折现率、收益期、增长率各改一点，估值能差出数倍），而这些假设没有一个能被数据本身验证，所以精度越高，结论越像真的、越难被反驳——最终估值变成争取预算的修辞。正确的做法：把方法与假设落库（`method` / `assumption` / `attribution`），并让"未归因"成为一个可以写下来的合法状态。

**反模式：把"入表"当成价值证明** —— 症状：把数据资产列入资产负债表，并把它当作数据团队价值的证据。后果：因为会计规定解决的是**处理方式**（按存货或无形资产如何处理），不是价值高低，所以入表不会告诉你这份数据值多少；把合规动作当成估值结论，会让团队在下一轮预算讨论中失去论证能力。正确的做法：入表是财务口径的工作，估值是资产化的另一条线，两者共用成本归集，但不互相替代。

**反模式：把目录当成交付** —— 症状：业务方在目录里确认了资产存在，然后被指向另一套系统走申请流程，几天后再被指向第三套系统配置权限。后果：因为**目录是读模型、交付是接口**，每多一次跳转就流失一部分人；用的人少，产出方更没有登记压力，回到第一条反模式的负循环。正确的做法：让授权、配额、计量与该资产的条目使用同一个标识（URN 一类），跳转至少不要跨越系统。

**反模式：资产目录只增不减** —— 症状：目录上线几年，条目数翻了几倍，没有一次退场；检索结果里混着早已无人使用的表与过时指标。后果：因为使用者是按**命中率**建立信任的，所以只要前几页出现不再维护的资产，他们就会退回"问熟人"这条老路；而检索不排序、不下线，恰恰会让劣质资产占据同样的曝光。正确的做法：用引用统计与最后被消费时间驱动下线，让"退场"成为常规流程而不是一次运动；指标类资产尤其需要，因为指标一旦被引用，下线要附带影响面评估与迁移方案。

**什么时候不值得迁移**：如果当前目录的问题是覆盖率低而不是能力不足，换工具不会改善——覆盖率低是登记没有被强制的结果，而任何工具的登记都需要同一套强制机制。可核验的判断方法：先看关键项缺失的资产今天能不能发布；答案如果是"能"，该做的是把门禁接上，而不是换产品。反过来，当产品在**能力边界**上确实做不到时（例如元数据 API 不公开、无法承载字段级血缘、多租户隔离满足不了合规要求），迁移才是必要的。

**换成另一个要动什么**（工作量量级为【经验】）：

| 迁移 | 数据迁移 | 查询 / 引用改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 开源目录 → 商业治理平台 | 中：元数据要全量导出并重新灌入 | 无 | 中：采集器与工作流配置 | 中：从"自助查找"转向"流程与角色" |
| 目录 → 集中式中台 | 中：主题数据要重建成统一模型 | 中：按表引用的下游要改到服务 / 指标 | 高：建模、实体解析、服务化都要建 | 高：业务要接受定义权上收 |
| 集中式中台 → 数据网格 | 高：所有权与接口要逐个域迁移 | 高：下游要改为按数据产品的接口与契约消费 | 高：自助平台能力要先补齐 | 高：治理方式从审批转向标准 + 审计 |
| 内部目录 → 对外开放 / 市场 | 中：要挑出可对外的资产子集并脱敏 | 中：消费方从内部流程改为契约访问 | 中：计量、授权、审计要补齐 | 中：定价与合同能力 |
| 平台内置资产（DataWorks / DataFinder 一类）→ 自建目录 | 中：元数据要全量导出并保持增量同步 | 无 | 高：采集、存储、检索、血缘全自建 | 中：要读懂平台的元数据模型 |

**这张表里最容易低估的一格是"目录 → 集中式中台"的团队再学习**：技术侧的建模与服务化可以靠工程投入解决，但定义权上收是一次真实的权力转移——业务侧失去"自己定义活跃用户"的权限。这项迁移失败的原因，通常不是技术建不起来，而是没有人在组织层面决定"口径由谁定"。

**迁移成本里最不能靠计划消除的一项是"人的记忆"**：口径的来龙去脉、某个字段为什么这么定义、哪张表看起来没人用其实被一个脚本在跑——这些通常只存在于少数人的经验里，而不在任何一份元数据中。一次迁移会把它们一次性清零。所以迁移前真正该做的准备不是"导出元数据"，而是**把关键资产的口径与依赖关系先写成可读的元数据**；如果这一步做不完，迁移后必然要重新踩一遍当年的坑，而这次没有人记得当时的判断依据。【经验】

**往深走与往回退的不对称**：往资产化更深处走（加门禁、上契约、做计量）每一步都能立刻看到效果——找数变快、事故变少、口径冲突减少；而退回来（拆掉门禁、放弃计量、取消口径评审）都要付出可见代价：门禁一旦撤销，团队会认为"以后也没人管"，再想收紧要多花一倍的说服成本；口径评审一旦停止，几套定义会在几个月内重新分叉。**所以资产化里"能撤的动作"要尽量往后放**：先做可回退的（准入标准、登记项、检索），再做难回退的（发布门禁、口径裁决权、对外契约）。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 不知道有什么数据、也说不清归谁管 | 先做注册表 + 发布门禁，字段列表尽量短 | 资格判定必须是全量即时的；字段越多，绕过动机越强 |
| 目录建起来了但覆盖率在掉 | 把消费路径（申请、授权、计费）接回目录 | 目录的价值是覆盖率 × 使用率，负循环只能靠接通消费路径打破 |
| 多业务口径冲突频发 | 集中式（定义权收归一点），并量中心的排队时长 | 跨业务可比来自"只有一份定义"，不来自事后对齐；代价是吞吐受中心产能限制 |
| 多域、且域内有数据工程能力 | 数据网格；先验证域能否独立交付数据产品 | 域自治的补贴来自"解释权与生产责任同在一处"；自助能力不足则退化成烟囱 |
| 要对外变现或跨组织交付 | 市场 / 交易所形态，必须有契约与计量 | 没有 SLA 签字方与计量规则，市场化只是一次内部计费 |
| 被要求给出资产估值 | 先做到成本归集到资产粒度，再谈方法 | 成本法是唯一不需要不可验证假设的方法；方法与假设必须落库 |
| 被要求数据资产入表 | 按会计规定处理，不把它当价值证明 | 会计规定解决处理方式，不解决价值高低 |
| 消费方开始是应用与 Agent | 元数据必须完整且可 API 消费 | Agent 没有资历可问，只能读元数据；不完整的元数据 + LLM 只会更快地给出更自信的错误 |
| 有多个业务域、但没人有权裁决口径 | 先立口径裁决权（或退回各域自定、不承诺跨域可比） | 目录不产生定义权；没有裁决权时，跨域可比性无法靠工具获得 |
| 目录里资产很多、但新增资产没人登记 | 把登记挂进发布流程（缺项不能发布） | 覆盖率衰减是机制问题不是工具问题；换产品会重来一遍同样的衰减 |

**回到 7.1 的六条判据**：如果只打算用一条来筛，用"**资格判定时机**"——它是唯一一条能单独把"买过目录"和"做过资产化"分开的判据；其余五条（定义权、归因、契约、机器可读、合规举证）都建立在"登记可信"这个前提之上，前提不成立时它们只是在不同的错误基线上做比较。

**最后一句话留给顺序**：如果只能记住一件事，记住资产化的推荐顺序——**先收紧准入（什么算资产）→ 再强制登记（缺项不能发布）→ 再接通消费路径（知道有就能申请到）→ 再谈复用与计量 → 最后才谈估值与市场化**。顺序颠倒的代价是逐级放大的：没有准入就强制登记会逼出例外通道，没有登记就做估值会算出一堆不可比的数字，没有契约就谈市场化只能得到一次内部计费。

> 本节小结：这些方案之间**唯一真正起决定作用的差异**，不是功能清单的多少，而是**「资格判定发生在什么时候」**——关键项缺失的资产能不能被发布。这一条决定目录是"一份可信的登记"还是"一份会衰减的历史记录"；而定义权归属（中台 / 网格）、交付契约（目录 / 市场）、估值方法（是否落库）都是在"登记可信"这个前提之上才有意义的选择。
