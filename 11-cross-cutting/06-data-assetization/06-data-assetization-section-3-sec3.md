## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

模式表把资产化讲成了「按组织形态选一个」：传统企业选中台，多团队选 Mesh，要变现就上数据市场。但真实的选型几乎从不是选出来的，是被三条约束推出来的：**资产的存在性与责任边界有没有被强制记录、价值能不能归因到具体的消费、交付是否必须经过契约与授权**。这三条里任何一条不同，同样的公司、同样的数据量，正确的模式就不同。

第一条是**登记与责任的强制性**。资产化的一切都始于「有什么、归谁管」。这条约束的特点是它必须被机制强制——只靠倡议，覆盖率一定随时间衰减，因为登记是新增动作，而收益归他人、成本归自己。所以目录类模式的核心不是「能不能搜」，而是**关键项缺项时资产能不能发布**；判据非常具体：缺业务含义、缺 Owner、缺 SLA 的资产，是能上线，还是被打回。

第二条是**价值能不能归因**。估值只有三条路（成本法 / 收益法 / 市场法，公式见 [§2.2](06-data-assetization.md)），它们成立的前提完全不同：成本法只要求成本可归集；收益法要求收益可归因、折现假设可辩护；市场法要求存在可比交易。方法越有想象力，越依赖不可验证的假设。所以「能不能归因」决定了估值是**决策工具**还是**数字游戏**——这条约束是资产化里最容易被跳过、也最容易反噬的一条。

第三条是**交付是否必须经过契约**。「知道有什么」与「拿得到」之间隔着一整套契约：SLA、配额、授权、用途限定、计量。目录是读模型，交付是接口。这条约束决定了资产是不是「产品」——没有契约，资产只是一个被登记的名字，消费方仍要去找上游团队要数据。

在以上三条**之外**，还有一条不同层级的约束：**所有权与口径定义权落在谁头上**。前三条规定资产化「做不做、模式挂在资产链的哪一段」，这一条规定它「长成集中式还是联邦式、谁能签 SLA」——数据中台与 Data Mesh 就是它的两种相反解法，而这是本节最容易选错的一处。它是 3.8 小结的主轴，也在 3.2.3 / 3.2.4 的失效点里互为正反面。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 资产登记是否被强制（缺项能否发布） | 目录的覆盖率与责任是否可落地 | 「先建目录，大家自然会登记」——登记的成本落在产出方、收益落在消费方 |
| 价值能否归因到具体消费 | 估值是决策工具还是数字游戏 | 「估值要精确到元」——不能归因时，精度调得越高，结论越像真的 |
| 交付是否必须经过契约与授权 | 资产是「被登记的名字」还是「产品」 | 「有了目录就等于有了数据服务」——目录只解决知道，不解决拿到 |
| **所有权与口径定义权落在谁头上**（前三条之外的第四条，决定最终形态，见 3.8） | 集中式还是联邦式；谁能签 SLA | 「口径可以事后对齐」——两套定义并存时，对齐是靠人肉，且会反复 |
| 消费方是人 / 应用 / Agent | 元数据是否必须机器可读、可否自服务 | 「目录的读者是人」——Agent 没有资历，只能读元数据 |
| 合规与政策约束（分类分级 / 入表） | 哪些项必须登记、估值是否要能被外部认可 | 「入表就是给数据定价」——会计规定解决的是处理方式，不是价值高低 |

把这 6 个模式放回这些约束上看，关系会清楚很多：资产目录回答的是第一条（登记与责任）；数据中台与 Data Mesh 回答的是第四条，且互为相反解法（定义权收归一点 / 留在域内）；估值与 ROI 回答的是第二条；数据市场回答的是第三条；AI 增强资产层回答的是第五条（消费方从人变成机器）。**它们不是六个互斥选项，而是同一套资产在「登记 → 计量 → 交付 → 消费」四段上的不同挂点**——把它们当单选题做，就会出现「上了 Mesh 又想要统一口径」这类无解争论。

### 3.2 模式逐个拆解（核心节）

下面 6 个模式按「登记与责任（3.2.1）→ 计量（3.2.2）→ 定义权归属（3.2.3、3.2.4）→ 交付（3.2.5）→ 消费（3.2.6）」排列。3.2.3 与 3.2.4 是**同一约束（定义权放哪）的两种相反解法**，它们的失效点恰好互为正反面。

**关于具名实践的一处取舍**：下面各模式的「真实使用」只列可核验的公开主体。若干具名厂商实践——字节 / 华为 / 京东的数据中台、Netflix 的 Data Mesh、阿里云数据市场、阿里《数据资产入表实践》——缺少可核验的公开来源，因此不再把它们当作事实断言列出（模式 1 的产品名单仍列出）。**这不等于它们没做**：核验方法写在各模式的「真实使用」里，读者可以按它自行判断任何一家公司。

#### 3.2.1 数据资产目录（登记与发现）

- **被什么约束逼出来**：资产的存在性与责任边界没有被任何系统强制记录——典型症状是资产数一旦到千级，能说清用途的往往不足十分之一，且多数资产没有落到具体人的 Owner【经验】。这是资产化的起点约束：先能枚举，才谈估值与交付。
- **结构**：单一资产注册表，关键项（业务含义 / 域 / Owner / SLA / 密级）为 `NOT NULL`，并挂在发布流程上；消费侧的授权记录单独成表，因为「知道有」与「拿得到」是两件事。

```sql
-- 数据资产目录：关键项缺一不可，否则不能发布（写入时约束，不是事后审计）
CREATE TABLE asset (
  asset_id       BIGSERIAL PRIMARY KEY,
  urn            TEXT NOT NULL UNIQUE,      -- 全局唯一标识：跨系统可寻址
  asset_type     TEXT NOT NULL,             -- TABLE / FIELD / METRIC / MODEL / API
  business_def   TEXT NOT NULL,             -- 业务含义：这张表回答什么业务问题
  domain         TEXT NOT NULL,             -- 分层 + 域
  owner_user     TEXT NOT NULL,             -- 具体到人；写团队名视为无主
  sla            TEXT NOT NULL,             -- 更新频率 + 产出时间
  classification TEXT NOT NULL,             -- 公开 / 内部 / 秘密 / 机密
  updated_at     TIMESTAMPTZ NOT NULL
);
CREATE TABLE asset_grant (                  -- 发现之后能不能拿到，取决于这张表
  asset_id    BIGINT NOT NULL,
  consumer    TEXT   NOT NULL,              -- 消费方：团队 / 应用 / Agent
  purpose     TEXT   NOT NULL,              -- 用途：合规与计费的依据
  granted_at  TIMESTAMPTZ NOT NULL
);
-- 对照：目录若只登记、不承载授权
--   → "知道有"与"拿得到"之间就多了一次跳转
--   → 跳转处的流失，最终会把人赶回"问熟人"的老路（见 3.5 信息孤岛）
```

- **为什么这样设计有效**：因为关键项是 `NOT NULL` 且挂在发布流程上，所以「无主资产」「用途不明的资产」在**创建时就被拒绝**——责任由写入约束保证，而不是靠事后审计补录。这是目录能在规模上维持可信度的唯一机制：**审计是抽样且滞后的，约束是全量且即时的**。
- **代价**：① 强制登记的字段越多，登记成本越高，而登记成本由产出方承担、收益由消费方获得——所以字段列表必须短；② 目录只解决「知道有」，不解决「拿得到」，授权、审批、计费若在别处，目录就只是路上的一站；③ 元数据本身会过期：Schema 有采集器自动跟上，业务含义没有，而它恰好是最有价值的那部分。
- **失效点**：当目录不与消费路径集成（申请、授权、计费都不在目录里）时，「统一清单」反转成「信息孤岛」：因为读者在目录里确认资产存在后仍要换一套系统走流程，多一次跳转就流失一部分人，而目录的价值是「覆盖率 × 使用率」的乘积——用的人少，产出方就没有登记压力，覆盖更差，用的人更少。这条负循环一旦形成，只能靠把消费路径接回目录来打破。
- **真实使用**：DataHub、Apache Atlas、Unity Catalog、Alation、Collibra、Atlan 是公开的目录类产品（用途与形态见 [§7.1](06-data-assetization-section-7-sec7.md)）；阿里云侧有 DataWorks 的数据资产目录能力与数据资源目录类产品（注：缩写「DAS」在阿里云产品体系中通常指数据库自治服务，与资产目录不是同一类能力，选型时请按官方产品定义核验，不要按缩写归类）。需要说明的是：**判断一家公司是否真的在做资产目录，可核验的不是「有没有买工具」，而是「缺 Owner 的资产能不能上线」**。【公开】（来源：上述产品官方文档；具体年份与能力边界可自行核验）

#### 3.2.2 数据估值与 ROI 模型

- **被什么约束逼出来**：数据投入走预算制、收益无法归因到具体决策——没有共同口径，数据投入就只能靠「感觉」来砍或保，而感觉在预算收紧时总是偏向砍。
- **结构**：成本侧落到资产粒度，收益侧明确标注归因依据，估值记录必须包含「方法」与「假设」两列；三者缺一，数字就不可比。

```sql
-- 成本侧（成本法唯一的输入，必须细到资产，否则无从谈起）
CREATE TABLE asset_cost (
  asset_id BIGINT NOT NULL,
  period   DATE   NOT NULL,
  storage  NUMERIC NOT NULL,
  compute  NUMERIC NOT NULL,
  people   NUMERIC NOT NULL,        -- 人力分摊：最常被忽略、通常也是最大的一块
  PRIMARY KEY (asset_id, period)
);

-- 估值侧：方法与假设必须落库
CREATE TABLE asset_valuation (
  asset_id    BIGINT  NOT NULL,
  as_of       DATE    NOT NULL,
  method      TEXT    NOT NULL,     -- cost / income / market
  value       NUMERIC NOT NULL,
  assumption  JSONB   NOT NULL,     -- 折现率 / 收益期 / 可比交易 —— 必须可见
  attribution TEXT    NOT NULL,     -- 归因依据：基线期 / 对照 / 显式写"未归因"
  PRIMARY KEY (asset_id, as_of, method)
);
-- ROI = (ΣB - ΣC) / ΣC：只有当 B 可归因时，这个比才有含义；
-- method 不落库时，成本法的数与收益法的数会被放在同一张表里比较 —— 量级可差数倍
```

- **为什么这样设计有效**：因为「方法」与「假设」被强制记录为一列，所以读者能判断一个数字是「成本法」还是「收益法」——两种方法给出的量级可以差很多倍，混在一起比较会得出完全相反的结论。**把方法显性化，是把估值从「一个数」变成「一组可反驳的论证」的最小机制**；也让「未归因」成为一个可以写下来的合法状态，而不是被迫填一个编出来的数。
- **代价**：① 成本归集与收益归因本身是持续成本——每个资产要有成本归属与使用记录，这些记录要随组织调整不断重算；② 估值一旦进入考核，就会被优化：资产被包装成「高价值」来争取预算，这正是指标成为目标后失效的过程；③ 收益法的输入（折现率、收益期、增长率）没有一个能由数据本身验证，所以它天然依赖治理与评审，而不是依赖计算。
- **失效点**：当收益无法归因（没有基线期、没有对照、收益与数据投入之间有多个同时变化的中介变量）时，「收益法估值」反转成「把业务增长的一部分记到数据头上」：因为折现模型对输入假设极度敏感——折现率、收益期、增长率各改一点，估值能差出数倍，而这些假设没有一个能被数据本身验证。此时唯一诚实的做法是退回成本法，并把「尚未归因的收益」列为清单而不是金额。
- **真实使用**：DAMA-DMBOK 2.0（2017）把数据估值与「数据作为资产」列入数据管理知识领域；成本法 / 收益法 / 市场法来自无形资产评估的既有方法体系；中国财政部《企业数据资源相关会计处理暂行规定》自 2024 年 1 月 1 日起施行，规定了符合条件的数据资源如何按存货或无形资产处理——**它规定的是会计处理方式，不是「数据值多少钱」**，这两件事在项目里经常被混为一谈。IDC 的《Data Age 2025》系列报告常被引用来说明数据规模的增长，但它是规模预测，不是估值方法。【公开】（来源：DAMA-DMBOK 2.0、财政部规定、IDC 公开报告；年份与条文可自行核验）

#### 3.2.3 数据中台（把定义权收归一点）

- **被什么约束逼出来**：多个业务在同一批实体（用户 / 商品 / 交易）上重复建设主题数据，且口径各异——同一个「活跃用户」在不同部门指不同的人，横向无法对比，纵向无法复用。
- **结构**：一层建模 + 一套实体标识 + 一类服务接口，供给路径收敛为「中心建设 → 业务消费」。

```text
数据中台：把口径与实体的定义权收归一个点（供给路径收敛）

   业务 A      业务 B      业务 C
     │            │            │     需求都走这一条路径
     └────────────┼────────────┘
                  ▼
        ┌───────────────────────────┐
        │  OneModel    统一建模       │  定义权：口径在这里定
        │  OneID       统一实体       │  实体解析：同一个人只有一个 id
        │  OneService  统一服务       │  供给接口：复用在这里发生
        └───────────────────────────┘
                  │
        统一数据底座（接入 → 公共层 → 应用层）
  ────────────────────────────────────────────────────────
  关键：跨业务指标可比，不是因为「事后对过口径」
        而是因为只有一份定义 —— 对齐成本被结构消除
  代价：需求吞吐 = 中心团队产能；业务越异构，「统一」越难容纳特例
```

- **为什么这样设计有效**：因为口径与实体的定义权收敛到一个点，跨业务指标在**定义上**就可比——不是靠「对完口径」对齐，而是根本只有一份定义；因为服务是复用的，单个消费方分摊到的建设成本随消费方数量下降【推算：若每个域独立建设同一份主题数据的成本为 C，N 个域各自建设总成本 = N × C；中心化一次建设 + N 次适配的代价 ≈ C + N × s（s 为单次服务适配成本），当 N ≥ 2 且 s ≪ C 时中心化更省】。这就是「复用」的机制来源，也是它唯一的成立条件。
- **代价**：① 中心团队成为所有数据需求的队列——需求吞吐等于中心团队产能，而业务需求是并行产生的，两者增速天然不匹配；② 中心模型越统一，越难容纳某个业务的特例：「统一」与「贴合」是对立的，而特例往往出现在最关键的业务上；③ 组织上要付权力重排的代价——口径定义权从业务收归中心，这是一次真实的权力转移，不是技术项目。
- **失效点**：当中心团队的交付吞吐低于业务需求产生的速度时，「复用」反转成「排队」：业务方的理性选择是绕开中台自建，于是出现「中台 + 域内烟囱」并存、两套口径重新分叉，而成本是双份的。机制在于**收益与成本的时间错配**：复用的收益发生在第 N 个消费方，成本（排队、说服中心、适配）发生在第 1 个——当需求方看不到第 N 个消费方时，它必然选择自建。所以中台成立的前提是需求足够同质且有规模；判断该不该建，可以先量三个数：同类主题数据的重复建设次数、跨业务口径冲突的频次、以及中心团队当前的排队时长。
- **真实使用**：阿里自 2010 年代中期起提出并对外输出「数据中台」，其方法论（一层建模、统一实体、统一服务）落在阿里云相关产品的公开材料中；此后国内多家企业跟进，这一模式也因此成为国内主流。**判断一家公司是否真的在做中台，可核验的是「是否存在一个有权定义口径的中心团队 + 一份被多个业务共用的模型」**，而不是有没有一个叫中台的平台。【公开】（来源：阿里云公开材料与产品文档；具体年份与表述可自行核验）

#### 3.2.4 数据网格（Data Mesh：把定义权下推到域）

- **被什么约束逼出来**：中心团队不可能同时理解所有业务域的业务语义；而「全公司一份模型」的边际收益随域数增加递减、协调成本递增——于是把所有权下推到域，中央改为提供能力与标准。
- **结构**：每个域的数据产品是一个有 Owner、有接口、有 SLA、有质量断言、有版本的可寻址单元；中央不持有数据，只提供自助平台、全局标准与联邦计算治理。

```sql
-- Data Mesh：数据产品是「可寻址的一等单元」，不是「某张表」
CREATE TABLE data_product (
  product_id      TEXT PRIMARY KEY,        -- 全局可寻址：下游按产品消费，不按表名
  domain          TEXT NOT NULL,           -- 所有权：产出它的域
  owner_user      TEXT NOT NULL,
  interface_ref   TEXT NOT NULL,           -- 接口：表 / API / 流，含 schema 版本
  sla             TEXT NOT NULL,           -- 可承诺的交付时间与可用性
  quality_assert  JSONB NOT NULL,          -- 质量断言：下游按断言消费，不按实现
  version         TEXT NOT NULL,           -- 破坏性变更在契约层暴露
  discoverable    BOOLEAN NOT NULL DEFAULT TRUE
);
-- 中央不持有数据，只持有三样东西：
--   ① 自助平台（域能自己建管道、自己运维）
--   ② 全局标准（互操作：标识、契约格式、分类分级口径）
--   ③ 联邦计算治理策略（跨域使用时的策略执行点）
```

- **为什么这样设计有效**：因为数据产品的 Owner 就是产出它的域，所以业务语义不需要跨组织翻译——**解释权与生产责任落在同一个团队**，这是它相对中台最本质的差别；因为接口（schema 版本 + SLA + 质量断言）是发布契约的一部分，下游按契约消费而不是按当前实现消费，破坏性变更会在契约层暴露，而不是在下游任务失败时才暴露。
- **代价**：① 平台自助能力是硬前提——域要自己建管道、自己运维、自己承担 SLO，平台不够自助时，每个域各自造轮子；② 全局一致性变弱：跨域指标要由联邦治理兜底，否则「每个域一个口径」；③ 治理方式要从「审批」改成「标准 + 审计」，这是一套不同的技能与组织习惯。
- **失效点**：当自助平台能力不足（域内没有数据工程能力或没有自助工具）时，「域自治」反转成「分布式烟囱」：因为每个域都在用各自的方式建管道、定口径，而中央又没有统一模型可以对齐，结果比集中式中台更糟——中台至少保证了一份口径，退化后的 Mesh 连口径都没有。所以它的成立顺序不能颠倒：**先让平台能自治，再让组织自治**；判据是「一个业务域的团队，能否不依赖中央团队独立交付一个数据产品」，答不上来就不该下推所有权。
- **真实使用**：Data Mesh 由 ThoughtWorks 的 Zhamak Dehghani 公开提出（martinfowler.com 系列文章，2019 年前后；专著由 O'Reilly 于 2022 年出版）；公开材料中被引用较多的实践者包括 Zalando、Intuit 等。【公开】（来源：martinfowler.com 与 O'Reilly；具体年份可自行核验）需要提醒的是：**不要把「某公司已全面 Data Mesh 化」当成事实**——公开材料通常只能证明它在某个业务域做了数据产品化；判断方法是看它有没有可寻址的数据产品目录与域内 Owner 制【经验】。

#### 3.2.5 数据市场（把交付变成契约）

- **被什么约束逼出来**：消费方要自助取数，供给方要能被计量与被激励——这需要「上架 + 订阅 + 计量」三件套。没有它，供给方没有反馈（不知道谁在用、用了多少），消费方也没有可依赖的承诺。
- **结构**：上架项绑定供给主体与承诺，消费必须经过订阅授权，用量被计量并回流到账本。

```sql
-- 数据市场 = 上架项 + 订阅 + 计量（目录是读模型，市场是带契约的接口）
CREATE TABLE listing (
  listing_id    TEXT PRIMARY KEY,
  asset_id      BIGINT NOT NULL,
  provider      TEXT NOT NULL,        -- 供给主体：没有主体，就没有人能签 SLA
  sla           TEXT NOT NULL,
  price_model   TEXT NOT NULL,        -- free / showback / chargeback
  quota         TEXT NOT NULL,        -- 配额：市场与「有权限就能读」的区别在此
  purpose_limit TEXT NOT NULL         -- 用途限定：合规要求，不是可选项
);
CREATE TABLE subscription (
  listing_id TEXT NOT NULL,
  consumer   TEXT NOT NULL,
  granted_at TIMESTAMPTZ NOT NULL,
  expires_at TIMESTAMPTZ,
  PRIMARY KEY (listing_id, consumer)
);
CREATE TABLE metering (               -- 没有它，「市场化」退化成「多一层审批」
  listing_id TEXT   NOT NULL,
  consumer   TEXT   NOT NULL,
  period     DATE   NOT NULL,
  calls      BIGINT NOT NULL,
  rows_out   BIGINT NOT NULL
);
```

- **为什么这样设计有效**：因为访问路径必须经过订阅与计量，所以「谁在用、用了多少」变成可观测的——供给方得到反馈（哪些资产真的有人用），成本可以被回摊到消费方（showback 或 chargeback）。**这是市场与目录最本质的区别：目录是读模型，市场是带契约、可计量、可追责的接口**；契约存在的前提是有个主体能签它，这也是 3.1 里「所有权」那条约束在此处的投影。
- **代价**：① 契约与计量本身要维护：每个上架项都要有 SLA、版本、定价、授权策略，这些元数据的维护量与资产数同阶；② 一旦引入计费口径，申请数据这件事的成本会上升，短期内会抑制消费——所以多数组织先做 showback（只展示用量与成本），确认价值后再做 chargeback（真扣预算）；③ 对外分发还要额外承担合规成本（分类分级、出境限制、用途限定、审计留痕）。
- **失效点**：当计量只用于展示、不进入任何决策（预算、配额、优先级）时，「市场化」反转成「多一层审批」：消费方为一次取数多付了流程成本，却得不到任何配额或优先级上的回报，于是绕过市场直接找上游团队要数据，上架率与调用量同时下滑。机制是：**市场的价值来自「走市场比绕过市场更省事」**，一旦它比绕过更麻烦，它的存在只会增加摩擦。判据是可量化的：绕过市场的取数占比是否在上升。
- **真实使用**：Snowflake Marketplace、Databricks Marketplace、AWS Data Exchange 是公开的商业化数据交易平台；上海数据交易所 2021 年成立，属于数据要素场内流通的尝试。【公开】（来源：各平台官方站点与公开报道；成立时间与运营状态可自行核验）组织内部的「市场」形态则普遍更轻——多数是「目录 + 申请审批 + 用量展示」，做到真正按用量扣预算的是少数【经验】。

#### 3.2.6 AI 增强的资产层（把元数据做成机器可消费的）

- **被什么约束逼出来**：消费方从人扩展到 LLM 与 Agent——取数入口从「人查目录」变成「模型选表、生成 SQL」，而模型没有资历：**它只能读到元数据里写了的东西**。原决策表里的「AI 目录」正是这一层。
- **结构**：在已登记的元数据之上加一层派生索引（向量 + 倒排），LLM 只做选择与解释，不做生成；每个回答都要能指回一条已登记的元数据。

```text
AI 增强的资产层：元数据 → 机器可读索引 → 模型选择（模型只能"选"，不能"造"）

  已登记元数据：业务含义 / 口径 / Owner / SLA / 密级 / 血缘 / 样例 / 质量分
        │  切块 + 向量化（离线，随元数据变更增量刷新）
        ▼
  混合检索（向量 + 倒排 + 标签 / 密级过滤）
        │  提问："上季度高价值用户的订单口径在哪"
        ▼
  候选集 Top-K ──► LLM 重排 + 生成解释
        │
        ├─ 置信度不足 ──► 拒答（必须有这个分支，且要真的触发）
        ▼
  Agent / Analyst：资产 + 口径 + Owner + 上下游
        │
        ▼
  权限与合规校验（不是可选步骤：密级与用途限定必须在执行前拦）

  ────────────────────────────────────────────────────────
  硬约束 1：模型只能"选"已登记资产，不能"造"一个不存在的表
  硬约束 2：低置信度必须拒答 —— 相似度检索永远会给一个 Top-1
  硬约束 3：每个结论都要挂一条可点的元数据依据（否则错误不可发现）
```

- **为什么这样设计有效**：因为每一句输出都必须能指回一条已登记的元数据，所以错误的表现形式被限制在「选错」而不是「编造」——而「选错」是**可发现**的（点开就能看到真实字段与口径）。这是资产层在 AI 时代不可替代的部分：模型取数的能力上限，被元数据的覆盖率与准确率直接锁死，而这恰好就是 3.2.1 那条「强制登记」约束在新消费方下的延伸。
- **代价**：① 向量索引是元数据的派生副本，必须随元数据变更增量刷新，否则会出现「检索结果的描述与真实口径不符」；② 成本随**调用量**增长而不是随资产数增长，与目录「一次采集、多次查询」的成本模型完全不同；③ 效果上限由元数据质量决定：描述为空的资产，向量化只是把「没有信息」变成高维空间里的「没有信息」。
- **失效点**：当元数据的业务描述覆盖率不足时，「智能取数」反转成「规模化地给出错误口径」：因为相似度检索永远会返回一个 Top-1，它没有「查不到」这个行为，而错误一旦从「人问人」变成「模型直出 SQL」，纠错链路就消失了——没人再核对口径，因为答案格式完整、看起来可信。所以这一层必须成对交付：**低置信度拒答 + 每个结论挂可点的元数据依据**；它是放大器，不是补课，元数据质量差时它放大的是错误。
- **真实使用**：主要目录厂商都在公开材料中推出了 AI 检索与助手能力（Collibra、Alation、Atlan 等），云数仓侧也出现了面向自然语言的取数入口（见 [§5](06-data-assetization-section-5-ai.md)）。**判断方法**：不要看演示，看两件事——「它会不会拒答」以及「答案里的口径能否点回元数据」；公开材料通常不支持「某公司已全面用自然语言替代人工取数」这类断言，更普遍的状态是并存与灰度【经验】。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 传统大型企业 + 强合规 + 有中心治理团队 | 资产目录 + 数据中台 | 联邦式在这个组织形态下会放大口径冲突，而中央本来就有定义权 | 是否存在**有权定义口径的中心团队** |
| 多业务 / 多团队 + 域内有数据工程能力 | Data Mesh | 中台会成为所有需求的队列，异构业务的特例接不进来 | 一个域能否**不依赖中央**独立交付数据产品 |
| 多业务但平台能力不足 | 先补平台，再谈 Mesh | 直接下推所有权会得到分布式烟囱，比中台更糟 | 自助平台是否已能让域**自己建、自己运维** |
| 早期 0→1 创业 | 轻量资产目录 | 中台与 Mesh 的组织成本远超收益；估值没有归因基础 | 资产数是否已到**人工列举不可行**的规模 |
| 金融 / 强合规 | 资产目录 + 分类分级（中台可选） | 市场与联邦分发会放大合规面 | 关键项缺项时资产**能否发布** |
| 跨境 / 跨云 | 联邦式 + 数据市场（轻量契约） | 集中式在数据不能出境时无法成立 | 数据**能否物理集中** |
| 已有稳定内部消费 + 想对外变现 | 数据市场（先 showback） | 直接上目录解决不了「谁在用、用多少」 | 上架项是否有**能签 SLA 的主体** |
| AI 时代 / 消费方是 Agent | 目录 + AI 增强资产层 | 只做目录则 Agent 只能猜表名；只做 AI 则没有权威元数据可选 | 元数据的**业务描述覆盖率**与拒答行为 |

表里最常被误选的一对是**数据中台 vs Data Mesh**：多数团队按「组织是否分权」来选，但真正的判据是**平台能力是否先于所有权下推到位**。机制上，Mesh 把「语义解释」的成本从中央转移到了域，这要求域内有数据工程能力与自助平台；能力不到位时，转移过去的不只是责任，还有一堆各造各的轮子——而这正是中台当初要解决的问题。所以误选 Mesh 的实际后果通常不是「更敏捷」，而是**先退化一遍烟囱，再回来补中台**，代价是双份的建设与一次口径重对齐。

### 3.4 组合模式：真实系统不会只用一种

**组合一：中台（供给）+ 资产目录（发现）+ 数据市场 / API（交付）**

- 构成：中台负责统一建模与统一服务，目录负责五元组登记与检索，市场 / API 网关负责契约、授权与计量。
- 职责边界：中台管「怎么产出」，目录管「有什么」，市场管「怎么拿到」；三者共用同一套 urn 与 Owner。
- 运维代价：三段之间任何一处脱节（目录里看得到、网关里没上架、中台里没有该模型）都会让消费方回到问人的老路；三份元数据要能对齐。
- 适合规模：有中心治理能力、消费方以业务人员为主的中大型企业。【经验】

**组合二：Data Mesh（域所有权）+ 中心只读资产目录（联邦发现）+ 联邦计算治理**

- 构成：各域持有数据产品与契约，中央只建只读的联邦检索层与策略执行点，不持有数据副本。
- 职责边界：域对口径与质量负责，中央对「可发现」与「跨域使用策略」负责，且不替域定义口径。
- 运维代价：跨域查询是 fan-out，延迟由最慢的域决定；全局问题（全公司有多少资产）只能现场聚合；标识体系不统一时跨域发现会串味。
- 适合规模：多业务线、各域有数据工程能力、中央不掌握业务语义的组织。【经验】

**组合三：资产目录 + 估值 / ROI + 成本（让 ROI 真的可算的最小闭环）**

- 构成：目录提供资产清单与 Owner，成本系统提供按资产的成本归属，用量记录提供消费方与调用量，估值只在这三者齐备后才产出数字。
- 职责边界：目录不负责算钱，成本系统不负责口径，估值只在「成本可归集 + 用量可观测」时才有意义。
- 运维代价：成本要从存储 / 计算 / 人力三个来源归集到资产粒度，而人力分摊口径每次组织调整都要重算。
- 适合规模：数据投入已大到需要向管理层解释的规模（通常是有独立数据预算的组织）。【经验】

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 为了估值而估值 | 估值报告只出现在汇报里，从不进入投资决策 | 数字与决策脱钩后，估值只会被用来争取预算，反向污染后续所有估值 | 立项要「量化价值」，而量化本身比用它做决策容易得多 | 先定一个要回答的决策问题，再决定估到多细 |
| 资产目录变信息孤岛 | 目录能搜到，但申请 / 授权 / 计费在另一套系统 | 多一次跳转即流失一部分人 → 使用率低 → 无人维护 → 覆盖更差 | 目录与治理 / 消费各自立项，各自把「能查到」当成交付 | 把申请、授权、计费接回目录；用绕过率衡量集成度 |
| 过度产品化 | 上架了一堆「数据产品」，消费方仍在问人要表 | 产品无人消费 → 上架项不维护 → 契约过期 → 更没人敢用 | 产品化的动因是「要显得有产出」，不是「有人要消费」 | 需求驱动：先有消费方与用途，再上架 |
| 数据中台变数据烟囱 | 中台在跑，业务侧同时还有一套自建的同主题数据 | 复用收益消失而两套成本都在 → 口径再次分叉，横向不可比 | 中心交付吞吐低于需求产生速度，业务理性绕行 | 提高中心吞吐或缩小统一范围；先量排队时长与重复建设次数 |
| 忽视数据成本 | ROI 只算收益，成本项里没有存储、计算与人力 | 估值系统性偏高 → 投入决策错误 → 资源持续流向低效资产 | 收益容易讲故事，成本要跨系统归集，后者难得多 | 成本先归集到资产粒度（见 3.2.2 的 `asset_cost`） |
| Owner 写团队名 | 出事时找不到人，只能找到团队 | 责任无法落到人，问题在团队内部被反复转手 | 团队名比人名好填，且不会被离职打断 | Owner 具体到人，写团队名视为无主资产，禁止发布 |
| 估值方法不落库 | 一张估值表里混着成本法与收益法的数，无人能分辨 | 量级不同的数字被直接比较，得出相反结论 | 估值由不同人在不同时间用不同方法算出，表结构没留痕 | `method` 与 `assumption` 必须落库，缺一不出报告 |

**「为了估值而估值」是本节最危险的一条，因为它会污染后续所有判断**。它的暴露方式不是错误，而是**沉默的缺席**：估值报告每季度都有，但没有任何一次投资决策引用过它，也没有一次因为估值低而下线某个资产。机制上，估值一旦与决策脱钩，它唯一的下游用途就是「向管理层争取预算」——于是被估的对象会逐渐向「容易讲高价值」的方向漂移，整张表的分布被优化过，此后再想用它做减法已经不可能了。修法是把顺序倒过来：**先问「这个估值要帮我们决定什么」，答不出来就先别估。**

**「资产目录变信息孤岛」是最常见的一条**，因为它的成因往往是组织性的：目录与治理、消费分属不同项目，各自考核各自的交付。暴露方式是**绕过率**——问一圈业务方，有多少人拿到数据是靠问人而不是走目录。机制在于目录的价值是「覆盖率 × 使用率」的乘积，两个因子会互相喂养或互相拖垮：用的人少，产出方就没有登记压力，覆盖更差，于是更没人用。**打破这条负循环的支点是消费路径，不是元数据质量**：把申请 / 授权 / 计费接回目录，让它成为唯一的取数入口，覆盖率才有动力上去。

**「数据中台变数据烟囱」的暴露方式是成本翻倍而口径分叉**：中台在跑，业务侧同时还有一套自建的同主题数据。它通常不是技术失败，而是**排队问题**：业务需求是并行产生的，中心产能是串行的，当排队时长超过业务能接受的范围时，绕行是理性选择，而不是纪律问题。所以修法有两个方向，且必须选一个——提高中心的吞吐（加人、缩范围、把自助能力下沉），或缩小「统一」的范围（只统一真正需要跨域可比的那部分口径，其余交给域）。两边都不做，只会得到双份成本与两套口径。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 人工能列举 → 千级资产 | 无目录 / 文档登记 | 资产量超过人力可维护的范围，找数靠问人，重复建设开始出现 | 轻量资产目录（五元组 + 自动采集） | 登记成为新增动作，必须同时把申请入口接进来 |
| 单业务 → 多业务 | 轻量目录 + 各自建设 | 同一实体多份主题数据，口径冲突让横向对比失效 | 数据中台（或统一建模范围） | 定义权从业务收归中心，是一次权力重排而非技术改造 |
| 中心排队 → 业务绕行 | 数据中台 | 中心交付吞吐低于需求产生速度，绕行成为理性选择 | 提高吞吐 / 缩小统一范围，或转为域自治 | 转 Mesh 需先补自助平台，否则得到分布式烟囱 |
| 只有登记 → 要按用量分配资源 | 资产目录 | 用量与成本不可见，资源只能按预算均分 | 目录 + 计量 + showback | 引入用量账本与按资产的成本归集 |
| showback → chargeback | 用量展示 | 成本不进预算，消费方没有优化动机 | 按用量占预算（先小范围试点） | 定价与配额规则要能解释、能申诉，否则会被绕过 |
| 内部消费 → 对外 / 跨境分发 | 内部目录与授权 | 分类分级、出境限制、用途限定成为硬约束 | 数据市场 + 用途限定授权 + 审计留痕 | 合规评审与留痕成本，且上架项需要能签 SLA 的主体 |
| 人消费 → Agent 消费 | 目录（给人看） | 模型没有资历，只能读元数据；无元数据的资产等于不存在 | 目录 + AI 增强资产层 | 维护派生索引、拒答策略与可追溯依据；成本随调用量增长 |

这些跃迁有一个共同点：**触发换模式的从来不是「数据量」本身，而是「登记覆盖追不上产出速度」「收益无法归因」「消费路径比绕过更麻烦」这三类结构性矛盾**。数据量大不会直接让模式失效——它让模式失效的方式，一定通过上述某个具体机制。

因此判断该不该换模式，看的是三个可直接观测的量：**关键项（Owner / 业务含义 / SLA）的覆盖率与其衰减速度**（覆盖在降就说明登记没被机制强制）、**能归因的收益占估值的比例**（比例低说明估值只能退回成本法）、以及**绕过率**（拿到数据靠问人的比例，上升说明交付路径比绕过更麻烦）。这三个量都能从现有系统里取到，不需要先做架构评审。

### 3.7 自检清单

- [ ] 关键项（业务含义 / 域 / Owner / SLA / 密级）缺项时，资产**能否发布**？能发布就不叫约束，只叫建议。
- [ ] Owner 是否**具体到人**？出现团队名即视为无主资产。
- [ ] 目录里的资产能不能**直接申请与授权**？还是必须跳到另一个系统？跳转处的绕行率是多少？
- [ ] 成本的归集粒度是不是**资产级**？人力分摊口径写下来了吗（还是只在某人的表格里）？
- [ ] ROI 里的收益是否有**归因依据**（基线期 / 对照 / 显式写「未归因」）？
- [ ] 每一个估值数字是否标了**方法**与**假设**？不标就会与另一种方法的数字被直接比较。
- [ ] 数据产品的 Owner 与它所在业务域的 Owner 是否是**同一个团队**？不一致则语义翻译成本仍在。
- [ ] 跨业务的同名指标（如活跃用户）是否**只有一份定义**？还是靠定期对口径维持一致？
- [ ] 上架项是否都有能签 SLA 的**供给主体**？没有主体的上架项无法追责。
- [ ] 计量是否进入了某个决策（预算 / 配额 / 优先级）？只展示不决策的计量会被绕过。
- [ ] 消费路径能否支撑 **Agent**（元数据机器可读、低置信度拒答、结论可追溯）？还是只有给人看的页面？
- [ ] 若做 AI 取数入口，「查不到就拒答」这个分支是否**真的会被触发**？从不拒答等于从不承认不知道。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 有中心治理权、需跨业务可比 | 资产目录 + 数据中台 | 只有一份定义，横向可比由结构保证；代价是中心成为需求队列 |
| 多业务、域内有工程能力 | Data Mesh | 解释权与生产责任同域，语义不需翻译；代价是全局一致性要靠联邦治理兜 |
| 收益不可归因 | 只用成本法 + 列「未归因收益」 | 收益法的假设无法被数据验证，宁缺勿假；代价是数字偏保守 |
| 消费方要自助、资源要分配 | 目录 + 计量（先 showback） | 用量可见才能回摊成本；代价是契约与计量的维护量随资产数增长 |
| 要对外 / 跨境分发 | 数据市场 + 用途限定授权 | 契约与留痕让分发可追责；代价是合规与上架成本，且需能签 SLA 的主体 |
| 消费方是 Agent | 目录 + AI 增强资产层 | 模型只能读元数据，错误可发现依赖「可点回依据」；代价是派生索引与调用量成本 |

> 本节小结：数据资产化的模式选择，先由**「登记与责任的强制性」**立住前提（缺项即不能发布，见 3.1 表第一条）——前提不成立时，后面所有选择都落在错误基线上；前提成立之后，**「资产的所有权与口径定义权落在谁头上」**（3.1 表中前三条之外的第四条）决定它长成集中式还是联邦式——登记（谁签字）、估值（成本与收益归到谁账上）、契约（谁能承诺 SLA）、计量（谁来付账）四件事都随这一条的形态取舍落位；而「收益能否归因」与「消费是否经过契约」在形态确定之后才展开，是估值段与交付段各自的次级选择，它们分别决定估值是决策工具还是数字游戏、资产是可发现的名字还是可交付的产品。
>
> 💡 **思考锚点**：§3.6 给了三个能从现有系统直接取到的量——关键项（Owner / 业务含义 / SLA）的覆盖率及其衰减速度、能归因的收益占估值的比例、绕过率。挑你自己的资产盘点一次，这三个数里哪个最先变差？若「拿到数据靠问人」的比例在升，按 §3.5 的机制你会先修消费入口（把申请 / 授权 / 计费接回目录），还是先补元数据质量——这两条修的是同一件事吗？
