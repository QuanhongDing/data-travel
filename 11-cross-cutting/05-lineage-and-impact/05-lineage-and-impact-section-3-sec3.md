## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

「血缘用什么方案」看起来是一道选型题，实际不是。血缘系统有三个互相挤压的指标：**覆盖率**（多少条依赖被记录）、**新鲜度**（记录落后于真实依赖多久）、**粒度**（精确到表还是精确到字段）。同一份人力预算下，拉高任一项都会压低另外两项，模式选择本质上是在这组约束下找一个可行解，而不是找一个最优解。

再看采集入口。主文件 §1.1 把血缘拆成三要素——数据资产、流转关系、元数据；其中「流转关系」这类边的来源只有三类：**作业定义**（静态读 SQL 与配置）、**运行时事件**（作业真正跑的时候引擎吐出的读写实体）、**人的登记**（文档、口径说明、口头约定）。所有采集模式都只是这三类的不同配比：静态解析覆盖面广但被语法限制，运行时事件准确但要求作业至少跑过一遍，人工登记能补语义但一定会过期。**「血缘采集不全」与「血缘不更新」这两条反模式的根，就在这三类入口各自的边界上。**

粒度这条约束决定了图的规模。主文件 §2.2 给出形式化：血缘是有向无环图 $G=(V,E)$，节点 $v = (\text{type}, \text{identifier}, \text{metadata})$，$\text{type} \in \{\text{table}, \text{column}, \text{job}, \text{report}, \text{model}\}$。把节点类型从 `table` 换成 `column`，V 和 E 不是「多一点」，而是换了一个量级——见下表与 3.2.1 的量级估算。**这也是「只有表级血缘」这条反模式长期存在的真实原因：不是团队不知道字段级更准，而是字段级的边数决定了它的存储、遍历与校准成本都更高。**

还有一条常被忽略的约束：**血缘要为谁服务**。给人看的血缘只要「查得到、看得懂」，给程序用的血缘要「字段稳定、语义可机读、延迟可预期」；两者的验收标准不同，混在一起做，往往得到一个"图很漂亮但 API 不够稳"的系统。后面五个模式在这一点上的差别，比它们在采集方式上的差别更能决定成败。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 作业形态（静态 SQL / 动态拼接 / 脚本） | 采集入口用静态解析还是运行时事件 | 「解析 SQL 就够了」——拼接表名与脚本作业解析不出来，而这恰是关键链路 |
| 访问模式（点查影响面 / 全图遍历 / 聚合统计） | 存储与索引选型 | 「上图形数据库」——影响面是浅层 BFS、目录检索是全文匹配，两者对存储的要求相反 |
| 变更频率与血缘新鲜度要求 | 批量采集还是事件流采集 | 「采集一次就够」——作业每周都在变，静态快照半年后就是错的 |
| 一致性要求（能否容忍血缘滞后） | 采集与消费之间是否需要事务边界 | 「血缘必须实时」——多数决策（变更评审）只需要分钟级，为此付出的代价常被高估 |
| 规模与成本（表数 × 字段数 → 边数） | 是否做字段级、是否做跨域联邦 | 「粒度越细越好」——字段级边的量级差会让存储与校准成本同步跳档 |
| 团队技能与运维能力 | 自建还是采用规范 + 后端 | 「选 OpenLineage 就选完了」——它是规范不是产品，存储、UI、门禁仍要自己选 |

读这张表的方式是**从上往下找当前真正收紧的那一条**，而不是六条都要满足：早期团队通常只被「作业形态」一条约束住，等到要上门禁时「规模与成本」和「变更频率」才会同时收紧。**约束是会变的，所以模式也要跟着换——这正是 3.6 存在的理由。**

### 3.2 模式逐个拆解

先横向看三类采集入口的取舍——下面五个模式都是这张表的某一种配比。**读这张表时要注意一列：**「边的可信度」不是实现质量，而是**这条边能不能被复核**——静态解析的边可以拿 SQL 原文对照，运行时采集的边有执行记录，人工登记的边只剩登记者当时的理解。**能否复核，直接决定了这条边可不可以进审计与门禁**，这也是 3.2.5 把「LLM 推断边混入解析边」列为失效点的同一个理由。

| 采集入口 | 覆盖什么样的边 | 新鲜度 | 边的可信度 | 主要成本 | 典型缺口 |
| --- | --- | --- | --- | --- | --- |
| 作业定义（静态解析） | 代码里写出来的表 / 字段依赖 | 跟随代码变更，实时性取决于何时重跑 | 高：边可从 SQL 原文复核 | 各方言解析器的长期维护 | 动态 SQL、拼接表名、脚本 |
| 运行时事件（Hook / Listener） | 真实执行过的读写依赖 | 高：作业跑完即得 | 高：记录的是实际发生的读写 | 作业进程内集成 + 采集端可用性 | 长期不调度的作业、未接入的引擎 |
| 人工登记 | 语义层依赖（口径、业务含义） | 低：登记即开始过期 | 中：依赖登记者当时的理解 | 持续的运营人力 | 规模一大必然失守 |

#### 3.2.1 SQL 解析自动采集

- **被什么约束逼出来**：作业以 SQL 表达、数量大到人工登记不可行——血缘必须从「人填」变成「程序读」。
- **结构**：`SQL → Parser → AST → 依赖提取 → 血缘存储`，提取出的边带变换说明与时间戳。

```sql
-- 输入：一条典型数仓加工 SQL
INSERT INTO dws_trade_1d
SELECT o.shop_id, SUM(o.amount) AS gmv, COUNT(DISTINCT o.buyer_id) AS buyer_cnt
FROM   dwd_order o JOIN dim_shop s ON o.shop_id = s.shop_id
WHERE  o.dt = '${bizdate}'  GROUP BY o.shop_id;

-- 解析输出
-- 节点：dwd_order、dim_shop、dws_trade_1d
-- 表级边：dwd_order → dws_trade_1d；dim_shop → dws_trade_1d
-- 字段级边（每条边带 transformation）：
--   dwd_order.shop_id  → dws_trade_1d.shop_id    [直接映射]
--   dwd_order.amount   → dws_trade_1d.gmv         [SUM]
--   dwd_order.buyer_id → dws_trade_1d.buyer_cnt   [COUNT(DISTINCT)]
-- 静态解析的盲区：${bizdate} 之类的变量、拼接出来的表名、UDF、动态 SQL
```

- **为什么这样设计有效**：因为边是从**作业定义**而不是从数据本身推导的，所以采集成本只与「有多少条 SQL」相关、与数据量无关——扫的是文本、不扫数据行，这是它常被放在第一条采集路线上的机制原因【经验】。主文件 §2.3 把「SQL 解析」列为六种采集方法之首，并标明其边界是「准确但受 SQL 复杂度限制」。
- **代价**：解析器要按方言各维护一份（Hive / Spark SQL / Trino / Flink SQL / PostgreSQL 语法并不通用）；SQL 越复杂（CTE、窗口函数、多层子查询、UDF）越容易只给出近似边；引擎版本升级要重新回归解析结果。**这是一条持续的维护线，不是一次性投入。**
- **失效点**：当作业形态从「静态 SQL」转向「脚本 + 拼接表名」时，SQL 解析的**「覆盖面广」会反转成「漏掉的恰好是最关键的边」**，因为解析器看不见的边正是那些没人写进版本库、只存在于某人脚本里的依赖（反模式 1 的机制根源）。
- **真实使用**：Apache Spark SQL Lineage、sqlfluff、Apache Calcite、Cube.js 的 Cube Lineage（本仓 [§ 4 工程实现](05-lineage-and-impact-section-4-sec4.md) §4.3 工具链已列此项）与阿里开源的 SQLFlow 都是这条路线；SQLFlow 的仓库地址由 §4 子文件 §4.2「字段血缘采集（SQLFlow）」给出（github.com/alibaba/sqlflow），版本与发布日期请按该仓库的 release 记录自行核验。字段级边数与表级边数的量级差可按下面自行估算。
- **这条路线容易误列的系统**：Apache Atlas 常被顺手算作「SQL 解析采集」的一员，但它的来源注（主文件 §1.4 记 2015 年开源）只支撑「何时开源」，支撑不了「靠 SQL 解析采血缘」；本仓给它的归属是——§4 子文件 §4.3 的选型表把它定位为「Hadoop 生态元数据、强分类分级」，[§ 8-11-2 数据血缘基础](05-lineage-and-impact-section-8-11-2-数据血缘基础.md) 与 [§ 8-2-3 数据接入的治理与质量保障](05-lineage-and-impact-section-8-2-3-数据接入的治理与质量保障.md) 都把它列为 **Hook 路线**的代表实现（Apache Atlas 的 Hive Hook），本节 3.2.3 的结构图又把它画在 OpenLineage 的**后端**一侧。判断一个系统属于哪条采路，看它读的是**作业定义文本**（SQL 解析）、**执行期事件**（Hook）还是**已经产生的事件**（OpenLineage 后端），而不是看它有没有挂「血缘」的名号。
- **落地上的分层选择**：同一条 SQL 解析路线内部还有一层选择——先做表级还是直接做字段级。表级解析只需处理 `FROM` / `JOIN` / `INSERT` 的目标与被引用表；字段级解析还要处理表达式、聚合、条件分支、`SELECT *` 展开与 CTE 的作用域，实现难度与回归面都更高。多数团队的真实路径是「表级先上线、字段级等到有门禁需求再做」【经验】。

```text
【经验】字段级相对表级放大多少（前提 c 为经验取值）
  设一张表平均 c 个字段——数仓表的宽窄差异很大，这里按【经验】取 c 在 10～50 之间，
  下文用中值 c ≈ 20 演示；两表之间的表级边恒为 1 条。
  字段级边的理论区间是 [c, c²]（每个目标字段可引用任意来源字段，
  实际取到哪一端取决于 JOIN 形态与是否逐字段透传）。
  取 c ≈ 20：字段级边约为表级边的 20～400 倍；c 在 10～50 之间变动时，
  该倍数整体落在 10～2500 倍之间（低端随 c 线性、高端随 c² 走）——
  量级结论不因 c 的具体取值而翻转。
  → 结论不是"字段级更准"，而是"字段级的存储、遍历与校准成本同步跳档"，
    所以它必须等到有明确的变更门禁需求时再上（见 3.6）。
```

#### 3.2.2 Hook / Listener 实时采集

- **被什么约束逼出来**：静态解析拿不到的边（动态 SQL、脚本任务、跨引擎读写），却需要相对实时地反映到影响面上。
- **结构**：把采集点从「读作业定义」移到「作业执行的引擎内部」。

```text
引擎执行平面（依赖在此真实发生）
  Hive  ──► Hive Hook（编译期 / 执行期钩子）
  Spark ──► Spark Listener（作业起止与读写事件）
  Flink ──► Metric Reporter / 作业监听
                 │  运行时实际读写的实体
                 ▼
            血缘事件缓冲（队列，异步投递）
                 ▼
   血缘存储（与解析结果合并、去重、按时间版本化）
```

- **为什么这样设计有效**：因为事件产生在作业真正读写的那一刻，它记录的是**实际发生的依赖**，能覆盖动态表名、跨引擎读写和临时中间表——这是对「采集不全」最直接的补丁，也是静态解析做不到的部分。
- **代价**：每个引擎的 Hook 是一份独立的集成与运维面（插件版本冲突、采集失败要单独监控）；钩子跑在作业进程内，必须做成异步投递才不会拖慢作业；**它只覆盖「跑过的作业」**，长期不调度的任务照样没有边。
- **失效点**：当作业对延时的敏感度高于血缘的实时性收益时，Hook 的**「实时性好」会反转成「采集本身成为作业的故障源」**，因为钩子在作业进程内执行，采集端阻塞或异常会向上传播——实战中最常见的形态是钩子抛错导致任务失败，团队于是整体关掉钩子，血缘退回到人工登记。
- **真实使用**：Hive Hooks（【公开】来源：主文件 §1.4 演进历程，记 2012 年 Apache Hive Hooks 机制实现粗粒度血缘）、Spark Listener（【公开】来源：主文件 §1.4 记 LinkedIn DataHub 2019 年开源，其 Spark Lineage Listener 即引擎侧监听器的代表实现，见 §4.3 工具链的 DataHub 条目）、Flink Metric Reporter（接口定义见 Apache Flink 官方文档的 Metrics / Metric Reporter 章节，请按当前版本文档核验）——三者都是引擎自带的扩展点；这一路线在中国大陆主流数仓平台的采集中普遍作为兜底层【经验】。
- **与静态解析的合并规则**：两路采集的边入库时必须带来源，并规定同一条边两路结论不一致时的仲裁顺序（通常以运行时采集为准，因为它记录的是实际读写；静态解析负责补齐尚未运行的作业）。**没有这条规则的团队，会在第一次两端不一致时选择删掉其中一路，而不是建立仲裁。**【经验】

#### 3.2.3 OpenLineage 统一规范

- **被什么约束逼出来**：链路横跨多种引擎与调度工具（Spark / Airflow / dbt / Flink），每接一个源就重写一套采集与存储适配，边际成本降不下来，长尾数据源永远排不上队。
- **结构**：各引擎侧只做一件事——把本地信息翻译成同一种事件；存储与查询是另一侧的事。

```text
   采集侧（只产事件）                        消费侧（只读事件）
  Spark Listener  ┐
  Airflow Provider ├─► OpenLineage 事件 ─► 后端（Marquez / DataHub /
  dbt / Flink     ┘   (job / run /         Atlas / 自研）
                       dataset / facet)          │
                                                 ▼
                              血缘图 / 影响分析 / 变更门禁 / 审计
```

```json
{
  "eventType": "COMPLETE",
  "job":     { "namespace": "warehouse", "name": "etl_orders_daily" },
  "run":     { "runId": "..." },
  "inputs":  [ { "namespace": "lake", "name": "dwd_order" } ],
  "outputs": [ { "namespace": "warehouse", "name": "dws_trade_1d",
                 "facets": { "schema": {}, "columnLineage": {} } } ]
}
```

- **为什么这样设计有效**：因为规范把**采集与存储解耦**，新增一个数据源的成本从「写一套采集 + 改一次存储」降到「写一个适配器」，长尾数据源的边际成本第一次低于它的收益——这正是「忽视跨域血缘」与「每个源各写一套解析」的正面解。
- **代价**：规范只定义事件，不提供存储、UI、影响分析与门禁，选了它仍然要选一个后端，并承担后端与规范之间的版本兼容与语义对齐；规范覆盖不到的引擎仍要自己补适配器。**它降低的是接入成本，不是运营成本。**
- **失效点**：当组织把「已采用 OpenLineage」当成「血缘问题已解决」时，**「标准统一」会反转成「事件采到了却没人消费」**，因为规范解决的是边的产生，不解决边的使用（查询、门禁、审计）——事件堆在队列里，影响面照样靠问人，这是反模式 4「血缘是孤岛」在标准时代的新形态。
- **真实使用**：OpenLineage 由 LF AI & Data 孵化、Marquez 为其参考实现（【公开】主文件 §1.4 记载该项目 2021 年启动并进入 LF AI & Data 孵化）；主文件 §2.3 把它与 SQL 解析、日志解析、Hook、ETL 工具 API、LLM 补全并列为六种采集方法。
- **版本提示**：事件字段与 facet 定义随规范版本演进（如字段级映射的 facet 名称与结构在多版本间调整过），接入前请以项目仓库当前版本文档为准。

#### 3.2.4 联邦化血缘

- **被什么约束逼出来**：组织被云账号 / BU / 子公司切成多个治理域，域内数据不允许整体复制到中心，但合规举证与变更评审又需要跨域的完整链路。
- **结构**：跨域只交换**边**，不交换数据。

```text
      域 A                域 B                域 C
 本地血缘存储 ──┐     本地血缘存储 ──┐   本地血缘存储 ──┐
 （数据不出域）  │    （数据不出域）  │  （数据不出域）  │
               ▼                    ▼                 ▼
        Federation API（只交换边标识与关系，不搬数据行）
                          │
                  统一血缘图谱（跨域可达）
                          │
          跨域影响面 / 合规举证 / 跨 BU 变更评审
```

- **为什么这样设计有效**：因为交换的是关系的元数据而不是数据行，「数据不出域」这条硬约束与「我要看到完整链路」这个需求可以同时成立——权限边界和计算边界没有被打破，链路的可达性却补上了。
- **代价**：跨域没有全局事务，边只能**分域异步汇聚**，跨域影响面天然是最终一致的；实体标识必须跨域对齐（同名表、改过名的表、不同平台上的同名表）；每加一个域都要谈一次接口与权限，治理成本随域数增长。**它是「不搬数据」的必然代价，不是实现缺陷。**
- **失效点**：当域数增长而标识对齐规则没有统一时，联邦的**「跨域链路完整」会反转成「看起来完整、实际错接」**，因为不同域的同名实体被合并成同一个节点，影响面查询给出的是**错误的下游清单**——在变更评审里，查不到比查错更安全，查错会直接导致该拦的没拦住。
- **真实使用**：Databricks Lakehouse Federation（【公开】来源：主文件 §1.4 演进历程，记 2024 年 Databricks 推出 Lakehouse Federation，血缘跨云联邦化）与 Unity Catalog 的跨云能力（主文件 §1.4 有其条目，2021 年发布【公开：Data+AI Summit 2021 发布公告】；§4.3 工具链把它列为「Databricks Lakehouse 血缘」）都属这条路线；AWS Glue Data Catalog 的跨账户共享、阿里云 DataWorks 的联邦血缘是同一路线上的另两个实例——这两条本节未核到对应功能的发布日期，故不标注年份，其能力与限制请按 AWS Glue 与阿里云 DataWorks 产品文档中的「跨账户 / 跨账号共享」章节核验。
- **落地前先做的三件事**：① 定跨域实体标识（用「平台 + 库 + 表 + 字段」的全限定名，而不是裸表名）；② 定冲突消解规则（同名但不同实体时如何区分，改过名的实体如何沿历史合并）；③ 定汇聚延迟的可接受区间并在查询结果上显式标注「跨域部分可能滞后」。**这三件事在接入第二个域之前就要做完，接入后再补，成本是重做整个标识体系。**【经验】

#### 3.2.5 LLM 辅助血缘

- **被什么约束逼出来**：静态解析与运行时事件都覆盖不到的那部分——脚本里的隐式依赖、口径文档、注释、工单——但变更评审必须对它们有判断。
- **结构**：输入是非结构化文本，输出是**带置信度的候选边**，且必须经过确认才入库。

```text
  输入（非结构化）                         候选边处理
  · 脚本 / Shell / Python 作业 ─┐
  · 调度 DAG 与 ETL 配置注释    ├─► LLM / 规则抽取 ─► 带置信度的候选边
  · 口径文档、指标说明、工单    ─┘                          │
                                                            ▼
                                    人工确认队列（低置信度不自动入库）
                                                            │
                                                            ▼
                        血缘存储（边标注来源 = 解析 / 运行时 / 人工 / LLM 推断）
```

- **为什么这样设计有效**：因为它读的是**人写的文本**，而前面几种模式读的是代码或事件，所以它能补上「代码里根本没有写下来」的依赖，并且承载自然语言入口（「订单表的数据从哪来」），这正是本章 [§ 5 子文件](05-lineage-and-impact-section-5-ai.md) §5.2 讨论的「血缘图谱 → GraphRAG → 自然语言查询」的落地前提。
- **代价**：LLM 给出的边**没有可复核的推导路径**，必须带置信度与来源标注并进入人工确认；库里的「LLM 推断边」与「解析得到边」必须可区分，否则审计时说不清某条依赖是否可靠；模型与提示词一变，已入库的边会发生漂移，需要重跑比对。
- **失效点**：当 LLM 推断的边与解析得到的边**不加区分地混在一起**时，**「补齐长尾覆盖」会反转成「用高置信度的外观掩盖低置信度的内容」**，因为下游的门禁与审计把模型猜测当成事实使用——一条被误解的表名映射就能误导整场变更评审，覆盖率上升而可信度反而下降。
- **真实使用**：阿里云 DataWorks 智能血缘、Atlan AI、Collibra AI 均在这一方向。DataWorks 智能血缘的推出时间在本书内有两条并不一致的记录：主文件 §1.4 把它列在 2025 年的「AI 驱动血缘」条目下，[§ 5 子文件](05-lineage-and-impact-section-5-ai.md) §5.3 记为 2024-12 GA——引用这两个年份中的任何一个前，请以产品发布公告为准。Atlan AI 与 Collibra AI 由 §4.3 工具链的「AI 时代新工具（2024-2025）」一节列出，其具体发布公告的日期请按各家产品的 release note 自行核验。主文件 §2.3 把 LLM 补全列为六种采集方法中「新兴、准确率待提升」的一种；落地时以「候选边 + 人工确认 + 来源标注」为默认形态【经验】。

**五个模式的「代价 → 失效点」对照**（这张表是选型的速查，不是结论）：

| 模式 | 它买到的东西 | 它必然付出的代价 | 代价开始反噬的信号 |
| --- | --- | --- | --- |
| SQL 解析 | 成本与数据量无关的广覆盖 | 各方言解析器的长期维护 | 影响面与实跑结果对不上，缺口集中在脚本作业 |
| Hook / Listener | 真实发生的依赖、准实时 | 作业进程内的集成与可用性风险 | 采集端异常开始导致作业失败 |
| OpenLineage | 新增数据源的成本可摊薄 | 只产边不管用，仍需自选后端 | 事件采到了，但没人接进任何流程 |
| 联邦化 | 不搬数据也能看见跨域链路 | 最终一致的汇聚 + 跨域标识对齐 | 跨域影响面出现"看起来对但查错"的下游 |
| LLM 辅助 | 补上文本里的隐式依赖 | 边不可复核，需人工确认与来源区分 | 模型猜测被当成事实进了门禁 |

注意这张表的最后一列全部是**信号**而不是**故障**：代价反噬时系统都还在正常运行，只是开始悄悄产生错误结论。这也解释了为什么本节把「失效点」单独列一栏——它描述的不是崩溃，而是**优点在某个条件下变成缺点的那一刻**。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 作业以静态 SQL 为主、百表级、单域 | SQL 解析（3.2.1） | 不必先上 Hook：集成面大，而静态 SQL 已覆盖主干 | 抽 20 条最复杂作业，解析器能给出字段级边的条数占比 |
| 需要变更门禁、且改动常精确到一个字段 | SQL 解析 + 字段级粒度（3.2.1） | 不要只做表级：表级门禁会把「改字段」当「改全表」拦，拦久了必被绕过 | 变更里「只动单个字段」的比例 |
| 跨引擎、需准实时、作业频繁上线 | Hook / Listener（3.2.2）+ OpenLineage（3.2.3） | 不要只上 Hook 不上规范：接第三个引擎时你要把采集重写一遍 | 新增一个数据源的接入工时 |
| 多云 / 多 BU / 数据不得出域 | 联邦化（3.2.4） | 不要选中心化统一存储：合规边界不允许数据集中 | 是否存在「数据不得出域」的硬约束 |
| 长尾脚本与文档里的隐式依赖要补 | LLM 辅助（3.2.5），且必须进人工确认 | 不要用 LLM 替代解析：LLM 边不可复核，不能进审计 | 是否有「来源标注 + 置信度 + 人工确认」的流程 |
| 已有多套消费方但只有一份人工登记 | SQL 解析 + 运行时采集（3.2.1 + 3.2.2） | 不要先扩消费方：消费方越多，口径分叉越快 | 当前有几个系统在各自维护血缘副本 |

**最常被误选的一对是「联邦化」与「中心化统一血缘」**，且误选方向几乎总是提前上联邦：团队一听到「我们有多个 BU」，就直接把血缘做成联邦式，结果是每个域各建一份存储、各定一套标识规则，跨域查询要先对齐实例再对齐命名；等到真的需要一条完整链路时，发现**骨架有了、语义没统一**——这时候再回头做中心化，要拆掉的不是技术栈而是已经固化的域内习惯。判据只有一条：**是否真的存在「数据不得出域」的硬约束**；如果只是「域之间不方便」，中心化 + 权限控制远比联邦省事。

**第二常被误选的一对是「LLM 辅助」与「运行时采集」**，方向通常是**用 LLM 去补那些其实 Hook 就能采到的边**。判据是：这条缺失的依赖在作业执行时是否真实发生过？如果发生过（动态 SQL、脚本读写、临时表），运行时采集给出的是**事实**，LLM 给出的是**推测**；只有对「从未被执行、也无法被观察到」的依赖（口径文档、已废止脚本、口头约定），LLM 才不可替代。把可观察的依赖交给推测去补，等于用一个更贵、更不可复核的手段替换一个更便宜、更可信的手段。

### 3.4 组合模式：真实系统不会只用一种

**组合 1：SQL 解析 + Hook 运行时采集 + OpenLineage 事件**

- **职责边界**：解析负责「代码里写得出来」的边（主干批量作业），Hook 负责「只有跑起来才知道」的边（动态 SQL、脚本、跨引擎读写），OpenLineage 负责把两者统一成同一种事件交给后端。
- **运维代价**：三套采集点都要监控与版本跟踪；关键是**去重与冲突消解规则**——同一张表被两种方式采到、结论不一致时以谁为准，这条规则必须在录入时就定好，否则血缘会自相矛盾。
- **适合规模**：表数量进入千级以上、作业引擎多于两种、且已经有变更门禁诉求的组织。

**组合 2：血缘存储 + 影响面门禁 + 质量 / 安全 / 成本联动**

- **职责边界**：存储提供图与 API；门禁（CI / 发布流程）消费影响面做阻断；质量、安全、成本各自把血缘当作定位工具（异常定位上游、敏感数据找流转路径、成本归因到链路）。
- **运维代价**：血缘必须**只采集一次、被多处复用**，否则每个系统各自解析 SQL、各自维护一份图，口径立刻分叉；这要求血缘先有稳定的开放 API，而这一步常被跳过。
- **适合规模**：已有独立质量 / 安全 / 成本平台的团队；这是「血缘是底座」这句口号的工程含义。

**组合 3：联邦化 + LLM 辅助补全**

- **职责边界**：联邦解决「跨域能不能看见」，LLM 辅助解决「域内长尾能不能补齐」——一个管广度、一个管角落。
- **运维代价**：两者都会引入**低可信度的边**（联邦的分域异步汇聚、LLM 的推断边），必须都可标注来源，才不至于污染影响面查询；人工确认队列要有人真的看，否则它会退化成「挂着的待办」。
- **适合规模**：多法人 / 多云的集团型组织，且已有专人负责元数据运营。

**三个组合共享同一个前提**：**血缘只采集一次**。三条组合里的每一条，只要有两个消费方各自解析一遍 SQL，组合就会从「分工」退化成「三份互相矛盾的事实」。所以上线顺序应当是**先有唯一采集源与开放 API，再谈组合**；反过来先铺开消费方、再统一采集，代价是逐家回迁，而回迁时被推翻的往往是已经写进流程的口径。

### 3.5 反模式与失效分析

六条反模式不是六个彼此独立的错误：**采集不全、只做表级、不更新、忽视跨域**这四条都是同一件事的不同侧面——采集入口有边界，而边界没有被度量；剩下两条（**血缘是孤岛**、**可视化很漂亮但不可查询**）是同一件事的另一面——边采到了，但没有被任何流程消费。下表把每条写成可观测的症状、机制层面的后果、团队会写成这样的成因，以及对应的修法。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| **血缘采集不全** | 影响面查询的结果，与「跑一遍下游任务试试」得到的结果对不上；每次事故都能找到一条不在图里的边 | 图是**部分图**，基于它做的门禁会放行本该拦住的高风险变更，而人被"系统显示没影响"说服 | 只采主干（SQL 作业），脚本与动态 SQL 天然落在所有解析器的盲区里 | 静态解析 + 运行时兜底；**把无法解析的场景单独标记为已知盲区并度量其占比**，让缺口可见 |
| **血缘不更新** | 图的最后更新时间远早于作业的最后变更时间；下游失败时图里显示「无依赖」 | 过期的血缘比没有血缘更危险——它给出**错误的信心**，让人跳过人工核对 | 采集做成一次性作业而非定时任务；或采集失败无人监控，静默停止 | 定时校准 + 记录每次采集时间与差异；把「血缘新鲜度」当成一个可监控指标 |
| **只有表级血缘，没有字段级** | 只能回答「这张表被谁用」，回答不了「这个字段被哪些下游字段引用」 | 门禁只能按整表一刀切，拦得太粗 → 被绕过；或放得太松 → 静默算错（值域错但作业不报错） | 字段级边的量级高出 20～400 倍【经验，按 3.2.1 的 c ≈ 20 推导】，起步阶段性价比低，于是永久停在表级 | 按「是否要变更门禁」决定是否上字段级；上之前先算边数量级与校准成本 |
| **血缘是孤岛** | 血缘有 UI、有 API，但质量平台、权限平台、CI 里看不到它 | 每个消费方各自解析一遍 SQL，口径分叉；血缘价值止步于「查得到」 | 血缘先作为独立项目立起来，集成是"下一步"的待办，然后没有下一步 | 血缘开放 API 被多系统共用；把「被几个系统消费」当作血缘项目的验收指标 |
| **忽视跨域血缘** | 跨 BU 的链路在图上断成两截，靠人工补充说明 | 跨域变更的影响面**系统性低估**，而这类变更恰恰影响面最大 | 每个域有能力自建，但没人有权限做跨域统一 | 先在标识规则上统一（同名表、改名历史），再谈联邦化；跨域影响面明确标注"可能不完整" |
| **可视化很漂亮但不可查询** | 图能画出来、能截图汇报，但 CI 流程里调不到它 | 血缘无法进入自动化环节，只能靠人看图，价值上限由人的注意力决定 | 项目以"给管理层看"为目标验收，API 与门禁不在验收清单里 | API 优先、UI 次之：先保证「影响面可以被程序查询」，再谈可视化 |

**最危险的三条**：

**「血缘不更新」**在生产中的典型暴露方式是**静默放行**。作业改了三周，血缘还是旧的，于是某次变更的影响面分析里少了一整条下游链路——门禁显示通过，团队按流程签了字，事故发生后的复盘会上一查，责任落在「血缘系统给了错误结论」上，而系统本身没有任何异常告警。它的危险在于**没有任何一个环节会失败**：采集没报错、查询没报错、门禁没报错。

**「只有表级血缘」**的暴露方式是**门禁被绕过**。表级影响面把「改一个字段名」和「重写整张表」算成同一件事，于是大量低风险变更被拦；被拦三次以后，团队学会走特批通道，特批通道一开，真正危险的变更也一起进去了。粒度不足不是精度问题，是**流程可信度**问题。

**「血缘是孤岛」**的暴露方式是**口径分叉**。质量平台自己解析一遍 SQL、权限平台再解析一遍、CI 再解析一遍，三份图的 SQL 方言支持范围不同、更新节奏不同，于是同一个字段在三处有三条不同的下游清单。此时谁对谁错无法裁决，最后的做法是退回人工判断——血缘系统在这一刻实际上已经下线了。

**三条的共同点是：出问题时没有任何一个组件报错。**判断自己是否已经踩上，只需要做一个动作——**抽一次真实变更，把「影响面查询给出的下游清单」与「实际被这次变更影响的资产」逐条对齐**。对不上的部分落在哪一类（没采到 / 采旧了 / 粒度不够 / 口径不同），就对应本节表里的哪一行修法。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 百表 → 万表 | 人工登记 + Excel | 登记速度追不上建表速度，登记即过期 | SQL 解析自动采集 | 需要先统一作业书写规范，否则解析率上不去 |
| 解析率卡在瓶颈 | 只做解析、不管盲区 | 补不动的那部分长期不可见，覆盖率数字很好看 | 运行时采集兜底 + 盲区显式标注 | 采集点进入作业进程，需异步投递并独立监控 |
| 单引擎 → 多引擎 | 单一引擎的 Hook 或解析器 | 每加一个引擎就要重写采集，长尾永远补不上 | OpenLineage 统一事件 + 适配器 | 要接受「规范只管产生边、不管使用边」，仍需选后端 |
| 无门禁 → 有门禁 | 表级血缘 | 表级门禁误拦率高，被走特批绕过 | 字段级血缘 + 递归影响面 | 字段级边数量级上升，存储与校准成本同步上升 |
| 单域 → 多 BU / 多云 | 中心化统一存储 | 数据或权限不允许集中 | 联邦化 + 跨域标识对齐 | 跨域影响面变成最终一致，且要先统一命名规则，否则错接 |
| 批为主 → 流批混合 | 定时批量采集 | 流作业的血缘在下一个采集周期前是错的 | Hook / Listener 事件流采集 | 采集点进入作业进程，必须异步投递并单独监控 |
| 血缘「查得到」→ 血缘「拦得住」 | 血缘只作为查询/展示 | 没人主动查，改动照样引发下游失败 | 影响面进入 CI / 发布门禁 | 需要先有字段级精度，否则门禁会被绕过 |
| 单团队 → 多团队消费 | 血缘只服务一个平台 | 每个消费方各自解析一遍 SQL，口径立刻分叉 | 开放 API 作为唯一入口 | 需要先定义稳定的实体标识与事件契约，改契约要背着所有消费方 |

**判据不是「规模多大」，而是「这条约束有没有变」**：从「够用」到「不够用」的那一刻，通常不是表变多了，而是**某个下游动作开始依赖血缘的准确性**（门禁用它拦人、审计用它举证），此时精度不够就从"体验问题"变成了"正确性问题"。

跃迁里最容易拖延的一步是「血缘只作为查询/展示」→「进入门禁」，因为它不是技术升级而是**组织授权**：让一个系统去阻断他人的发布，需要有人承担误拦的后果。技术上的前置条件只有一个——**门禁的精度必须高于人工判断的精度**，否则它会稳定地制造误拦，而误拦会稳定地催生特批通道，最后门禁形同虚设。

表里 8 条跃迁中成本最高的是「单域 → 多 BU / 多云」：它要动的不是采集，而是**命名**——表名、库名、平台名一旦被固化成跨域标识，后续所有历史边都要重挂一次。

### 3.7 自检清单

下面每一条都设计成**可以用一次抽样直接验证**的问题，而不是「是否有血缘体系」这类口号式提问。答不出具体数字或近期样本的，就当作「否」。

- [ ] 血缘的**最后采集时间**是否可见，并与作业的最后变更时间做过比对？（只记录"有没有"而不记录"什么时候"，等于埋了反模式 2）
- [ ] 图里是否能列出**已知盲区**（解析不了的脚本、动态 SQL、外部导入）及其占比，而不是假装全图完整？
- [ ] 影响面查询的结果，是否与服务/作业里真实存在的依赖抽样核对过？核对样本最近一次是什么时候？
- [ ] 每条边是否带**来源标注**（静态解析 / 运行时采集 / 人工登记 / LLM 推断）？
- [ ] 血缘是否被**两个以上系统**通过 API 消费（质量、权限、成本、CI 中任意两个），而不是只有一个 UI？
- [ ] 变更流程里是否存在一个环节，会因为影响面超阈值而**真的阻断**发布？最近一个月真的拦下过吗？
- [ ] 门禁的阻断粒度是表还是字段？如果按表拦，误拦率是否已经导致团队走特批通道？
- [ ] 如果引入 LLM 补全：低置信度的边是否进人工确认队列，队列里是否有近期处理记录？
- [ ] 跨域链路上是否标注了「可能不完整」？跨域实体的命名对齐规则写在哪里、由谁维护？
- [ ] 血缘项目是否有**角色明确的所有者**（不是「某个平台团队顺便管」）？
- [ ] 有没有一个指标能回答「血缘今天比上个月更可信了吗」？（覆盖、新鲜度、被消费次数三者至少覆盖两个）
- [ ] 是否存在「改了作业但血缘没变」的静默路径？它被监控到了吗？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 单域、静态 SQL 为主、百表级 | SQL 解析自动采集 | 边从文本推导，成本与数据量无关，是最低成本的起点 |
| 多引擎、要准实时 | Hook / Listener + OpenLineage | 运行时的边只有引擎自己知道；统一事件让新增源不再重写采集 |
| 要变更门禁 | 字段级粒度 + 递归影响面 | 门禁的可信度取决于粒度，粒度不够的门禁必然被绕过 |
| 多云 / 多 BU / 数据不出域 | 联邦化 | 只交换边不搬数据，合规边界与链路可达性可以同时成立 |
| 长尾脚本与文档依赖 | LLM 辅助 + 人工确认 | 文本里的依赖只能从文本里读，但必须可标注、可复核 |
| 多域但无出域硬约束 | 中心化存储 + 权限隔离 | 联邦化会提前引入「最终一致 + 标识对齐」两项长期成本 |

表里每一行的「关键理由」都可以还原成一句话：**这个模式把成本放在了哪一侧**。SQL 解析把成本放在解析器维护上，Hook 把成本放在作业进程的可用性上，OpenLineage 把成本放在后端的自选上，联邦把成本放在跨域标识对齐上，LLM 把成本放在人工确认上——**没有零成本的模式，只有你能长期承担的那一种**。

选型的提问顺序建议固定为三步：**先说清这条边要拿来干什么（查得到还是拦得住），再确认它在执行时是否可被观察到（能观察到就别用推测去补），最后才在成本的几种形态里挑一个你能扛住的。**

> 本节小结：本主题下决定模式选择的**唯一那条约束是「血缘的边要拿来干什么用」**——只是「查得到」，静态解析加查询 API 足够；一旦要「拦得住」（门禁、审计、跨域举证），精度、新鲜度与来源可追溯就同时变成硬要求，模式也就必须整体换档。所以先回答用途，再选采集方式；顺序颠倒，就会得到一张很漂亮但没人敢信的血缘图。
>
> 💡 **思考锚点**：拿你们最近一次真实变更做一遍 §3.5 结尾那个动作——把「影响面查询给出的下游清单」与「实际被这次变更影响的资产」逐条对齐。对不上的那些边落在 §3.6 表里哪一类：没采到、采旧了，还是粒度不够（表级把「改字段名」与「重写整表」算成同一件事，于是被特批绕过）？若答案是「粒度不够」，你现在的门禁实际拦下过发布吗，还是已经形同虚设？
