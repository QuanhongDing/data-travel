## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

主文件把血缘定义成一张有向无环图（主文件 §2.2），把影响分析定义成沿反向边做 BFS / DFS、把根因分析定义成在候选上游集合上按重要度打分（主文件 §2.3）。这三件事在 AI 之前就已定型，AI 一步也没有改动它们。所以本节要判的不是「AI 能不能接进血缘」，而是 **AI 新增的那两样东西——新的边生产者与新的消费入口——会不会撞上本章既有的那几条约束**。

本章的既有约束写在 [§ 3](05-lineage-and-impact-section-3-sec3.md)：边的来源只有三类——作业定义（静态解析）、运行时事件、人的登记，而人工登记一定会过期（§3.1），采集缺口是系统性的、脚本与动态 SQL 永远落在解析器盲区（§3.5），一条链路的可信度等于**最弱那一跳**——只要有一跳靠人工登记，整条链路的时效性就退回到人工登记的时效性（这条结论的出处是 [09 数据血缘 §3](../09-data-lineage/09-data-lineage-section-3-sec3.md) §3.2.2 的「代价」④，本章 §3.1「人工登记一定会过期」是它的另一面），而血缘的价值取决于**它挂在哪个环节上**——挂在文档里没人看，挂在 CI / 发布门禁上才每次变更都必须正面回答影响面（§3.2.3、[§ 7](05-lineage-and-impact-section-7-sec7.md) §7.3.4）。把模型推断出来的边当成事实送进阻断路径，撞上的正是「最弱那一跳」这一条。

本节用 L1 / L2 / L3 三级区分，判据必须可核验，而不是「感觉成熟」：

| 级别 | 判据（三条全中才算 L1） | 读者该怎么做 |
| --- | --- | --- |
| **L1 生产可用** | ① 已 GA 且有正式 release note（规范类项目按其版本化发布物计）；② 有**第三方（非厂商）**公开生产案例；③ 接口稳定 | 可以排进路线图 |
| **L2 可试点** | 已可用但接口 / 生态未稳，或**仅有厂商与建设方自有案例**，或只在小规模被验证 | 可以做 PoC，不要做核心依赖 |
| **L3 观望** | 仅路线图 / 论文 / 厂商演示 / 预览特性 | 记录，不要在架构里预留假设 |

**本节不对 L1 判据做任何修正，也不缩小它的适用范围。** 本主题最诱人放宽的正是第②条：血缘领域有一批公开仓库、有跨工具规范、有建设方的工程文章，很容易把「有公开的机制性材料」读成「有第三方生产案例」。但建设方自己的工程文章按判据读就是**建设方自述**，正是 L2 的定义；把判据改写成「可被第三方复核」之后，读者按新措辞照样核验不了。另有一条纪律：**已经在生产里跑了多年的既有能力**（自动采集、影响面查询、字段级血缘、开放 API）不是 AI 方向，本节只在对照时提及，不为它们占用评级。

还有四件容易混的事，先在这里分开：

- **产品名 vs 能力名**：「自然语言查血缘」「LLM 补全血缘」是**能力名**，不是某个产品的专属功能；同一能力在不同厂商材料里挂在不同的产品名下（[§ 4](05-lineage-and-impact-section-4-sec4.md) §4.3 把它们一并列在「AI 时代新工具（2024-2025）」）。判定方法：按**产品全名 + 该能力的输入与输出**核对，而不是按能力名归类。
- **规范 vs 产品**：OpenLineage 是**跨工具的事件规范**，Marquez 是它的参考实现，DataHub 既提供引擎侧采集器（§3.2.2 的 Spark Listener 一类），也作为规范事件的消费后端被列在 §3.2.3。规范有版本，不等于某个产品 GA 了某个能力。
- **论文原型 vs 产品实现**：论文演示的是**方法可行性**，产品实现要受采集器、SQL 方言与作业类型的约束（§3.2.1）。判定方法：看该实现有没有把「解析失败」与「无法解析」显式暴露出来。
- **单域 vs 跨域**：单域内的自动采集与字段级血缘是已建成能力；跨域是另一套语义（对齐表、桥接边、汇聚延迟），不能拿单域覆盖率推算跨域结论（§3.2.4）。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**——改变了成本函数、改变了接口边界、把人工判断换成统计判断，还是只换了个前端？本主题的答案集中在**两条**：**第一条**是边的生产者多了一种，从「确定性解析器」扩到「统计推断器」，它改变的是**补全成本的增长形状**（边际成本从「每接一个源写一套解析」挪到「算力 + 人工确认」）；**第二条**是入口的**词汇责任发生了转移**，从「你必须知道表名与 SQL」挪到「系统必须把口语映射到实体」。**没有一条改变了可达性的性质**：影响面查询仍然是图遍历，边的可信度仍然取决于它的来源，链路可信度仍然等于最弱那一跳。

**这三级的排法直接决定路线图的顺序**：

- **先做的三件事不在表里**，因为它们是 AI 之前的既有能力，却又是后面每一个方向的评估前提：把解析缺口度量出来（§3.5 的抽检动作）→ 给边标来源（§3.2.5）→ 把影响面挂进门禁（§3.2.3）。没有这三件事，「模型补的边准不准」无从判定，「入口答得对不对」无从核对。
- **L2 做 PoC，并先测两个数**：解析失败率（缺口有多大）与假边率（模型补得准不准）。这两个数拿不出来，L2 就停在原地，与选哪家产品无关。
- **L3 不排进排期**：Agent 自动执行、GraphRAG 推理、可信度与漂移检测都属于「等信号」。它们有一个共同前提——**读路径与写路径的门槛必须分开定**，而这个约定比选哪套技术重要得多。
- **回填机制**：每次血缘项目复盘时回填一次级别；某个 L2 若一年内仍拿不到自己组织里的实测量（缺口比例或假边率），降 L3 并停止投入。

**原条目去向对照**：原 §5.3 的三条学术条目给的是主题名而非可检索的标题与作者，不能作为证据，本节保留它们所指的三个方向（跨工具统一规范 / 字段级自动采集 / AI 驱动补全），并在 §5.4 给出判定入口。原 §5.3 的七条工业条目里，时点最需要小心的一条是 OpenLineage 1.0 GA——本节不给年份，只给判定入口（项目发布页，看规范版本号与对应 release note）。其余六条按能力落点各自归位：Atlan AI、阿里云 DataWorks 智能血缘 → 上表第 1 行；Collibra AI、DataHub + LLM 集成 → 上表第 2 行（[§ 4](05-lineage-and-impact-section-4-sec4.md) §4.3 把这两条的能力记为「AI 辅助血缘补全」与「自动补全血缘」，与原方向 1 把它们并列在自然语言入口下并不一致，本节按 §4.3 的能力口径归到补全侧，不复述原清单的分组）；Databricks Lakehouse Federation、Unity Catalog 跨云联邦血缘 → 上表第 9 行。原 §5.4 的六条趋势落在上表第 13、9、2、12、11、10 行，一条不丢。

### 5.2 演进方向逐条拆解（核心节）

下面把方向分成四组：**前三组按同一套结构逐条写**（旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度），**第四组用一张表覆盖同一套要素**，因为那一族的共同点恰恰是「机制没变」。四组共用 §5.1 里的两条机制（边的生产者、入口的词汇责任），差别在**它落在哪一层**。

| 方向 | AI 改变了什么机制 | 这条变化落在哪一层 |
| --- | --- | --- |
| §5.2.1 自然语言入口与问答消费 | 入口的词汇责任从人挪到系统 | **接口边界**（消费方从数据工程师扩到业务与 oncall，但只读） |
| §5.2.2 LLM 辅助补全 | 边的生产者从确定性解析器扩到统计推断器 | **成本函数与边的可信度**（长尾补全的边际成本下降，代价是图里出现两种可信度的边） |
| §5.2.3 Agent 驱动的变更管理 | 血缘从「读」进入「写」 | **执行边界**（本主题里唯一会产生写操作的方向） |
| §5.2.4 机制没变的那一族 | 大多没有改变机制 | **前端与既有能力的延伸**（换前端 / 接一条边 / 与 AI 无因果关系） |

读法建议：如果时间只够读一节，读 §5.2.2——它是本主题里唯一**已经在你的系统里发生**的变化（边的来源多了一种），而它带来的问题（两种可信度的边混在同一张图里）不需要任何新产品就能验证。§5.2.1 的收益要等你把实体标识与权限统一之后才兑现。

只写收益不写代价的方向，在评审时应被直接打回——本主题里每一次「血缘更容易用了」，都对应一处新的判断成本：**模型补的边要人去确认，入口答出的结论要人去分辨，Agent 生成的修复要人去背书**。这也是为什么 §5.2.3 的级别低于 §5.2.1 与 §5.2.2：不是它的技术更难，而是它的错误落在写路径上。

#### 5.2.1 自然语言入口与问答消费（原方向 1、4；原 §5.2 第 2 条）

- **旧做法与它的卡点**：血缘的消费方式只有两种——人打开图看，或程序调 API 查。卡点是**入口的词汇由提问者承担**：要查「订单表的数据从哪来」，提问的人必须先知道表名、库名、分层命名规范；业务方与 oncall 恰恰不知道这些，于是血缘的消费方长期只剩数据工程师，而最需要它当场给出答案的排障场景反而用不上。
- **AI 改变了什么机制**：**词汇责任从人转移到系统**——提问者用人话，系统负责映射到实体与边。这不是「多了一个搜索框」，而是**入口的解析责任换了承担方**：过去解析失败表现为「搜不到表」，人自己会换个词再试；现在解析错误表现为「一条读起来很像真的链路」，而提问者没有能力判断它是编的。§3.2.5 把这条机制写成「LLM 读的是人写的文本，因此能补上代码里根本没写下来的依赖，并承载自然语言入口」。
- **由此得到的**：**因为系统承担了把口语映射到实体的责任，血缘第一次可以对「不知道表名的人」交付**——这意味着消费方从数据团队扩到业务、oncall 与新人，而这三类人恰好占据了排障与理解数据的大多数提问。这条收益不需要新建任何血缘存储，只需要在图与 API 之上加一层。

```text
       同一个问题的两种失败（差别在于谁来承担词汇责任）
       ────────────────────────────────────────────────
       旧入口（人承担词汇责任）
         提问: "订单表的数据从哪来"
         系统: 搜不到 "订单表"（真名是 dwd_trade_order）
         人的反应: 换个词再试 → 最终去问熟人   ← 失败是可见的
       ────────────────────────────────────────────────
       NL 入口（系统承担词汇责任）
         提问: "订单表的数据从哪来"
         系统: 映射到 dwd_trade_order → 返回一条链路
         人的反应: 直接采信            ← 失败不可见
       判定方法: 抽 20 个真实提问，逐条核对返回的实体是不是提问者指的那个
                 对不上却"有答案"的比例，就是这一层的实际错误率
```

- **由此付出的**：**其一，幻觉在血缘里不是「答错」，而是「给出一条不存在的边」**——它与真边在同一张图里、同一种展示样式，读者无法分辨，而下游的门禁若消费它，拦错的代价直接落在变更流程上。**其二，权限与实体标识必须先在**：问答层把「哪张表」变成了模型输出，如果入口不复用同一套权限与全限定名，就会出现「问到的表其实没权限看」或「同名实体被合并成一个」——后者正是 §3.2.4 里跨域查错的那类错误在单域内的版本。**其三，「查不到」与「没有上游」必须分开答**：模型倾向于把检索空结果答成「该表没有上游」，而这在血缘里是最危险的一种错误——它把「没采到」说成了「不存在」。
- **证据与来源**：【公开：本书 §3.2.5 给出「候选边 + 人工确认 + 来源标注」的结构、§3.2.3 给出可被 API 消费的边界，均可逐行核对】；产品侧的代表见 [§ 4](05-lineage-and-impact-section-4-sec4.md) §4.3 的「AI 时代新工具（2024-2025）」一栏，其具体能力与版本以各家官方文档当前版本为准。**【本节未能核到】第三方（非厂商）公开生产案例**——即「某非厂商组织公开过它的 NL 血缘入口的提问量与错误率」这类带口径的材料；原清单点名的 Atlan AI、Collibra AI、阿里云 DataWorks 智能血缘，本节只作为方向指认，其发布时点一律以官方发布说明为准。
- **成熟度**：**L2**。判据：① 核不到（形态在书内可核验、产品侧有厂商条目，但无可点名的正式发布物）；**②核不到**；③ 各家的问答权限模型与出处格式不统一 → 可做 PoC，不要做核心依赖。
- **同一套机制的另一半：文档与变更记录的向量化检索（原 §5.2 第 2 条）**——把 Postmortem、Runbook、变更记录接进向量库，是「给人看」的消费入口里最便宜的一种。它的级别与第 1 行一字不差地一致：**L2**，① 核不到（向量检索是既有通用能力，本方向没有自己的正式发布物）；**②核不到**；③ 文档与图谱的边界（哪条结论可以引到边）没有约定。**它只能当线索**：检索到的一段文字不能直接当作影响面结论，因为它不指向具体的边——这正是「线索」与「事实」在本主题里的分界。
- **判定方法**：抽 20 个真实提问，逐条核对返回实体是否就是提问者指的那一个；再试一次「问一张确定没有上游的表」与「问一张确实没采到血缘的表」，看两者是否被答成同一句。
- **什么时候值得做**：提问者里已经有大量「不知道表名」的人（业务、oncall、新人），且实体标识与权限已经统一时——这类人占排障与理解数据提问的大多数，收益直接兑现。
- **什么时候不值得做**：实体标识与权限还没统一时——此时 NL 入口只会把「同名合并」与「越权展示」这两个问题放大给人看。

#### 5.2.2 LLM 辅助血缘补全（原方向 2；原趋势 3）

- **旧做法与它的卡点**：三路采集各管一段——SQL 解析管「代码里写得出来的边」、Hook / Listener 管「跑起来才知道的边」、人工登记管剩下的（§3.2.1、§3.2.2）。卡点是**剩下那一小段的边际成本不下降**：脚本里的隐式依赖、口径文档里的引用、工单里的口头约定，每补一条都要一个懂业务的人读一遍，而**人读文本的成本不随数据规模摊薄**。于是覆盖率曲线在长尾处变得极平——即 §3.5 里「采集不全」那条反模式。
- **AI 改变了什么机制**：**补全的边际成本从「人的注意力」挪到「算力 + 人工确认」**——这正是本主题里唯一一条真正落在成本函数上的机制变化。输出的形态也变了：不再是「一条边」，而是**带置信度与证据的候选边**，且必须经确认才入库（§3.2.5 已把这条定成默认形态）。
- **由此得到的**：**因为模型读的是人写的文本，所以「代码里根本没写下来」的那类依赖第一次有了被记录的可能**——这是解析器与运行时采集结构性到不了的地方。它的价值不在覆盖率数字，而在**把长尾缺口从「不可见的空白」变成「一条待确认的候选」**：过去你不知道缺什么，现在你知道缺的是哪几条、由谁去确认。

| 边的来源 | 它证明什么 | 它证明不了什么 | 能进阻断路径吗 |
| --- | --- | --- | --- |
| SQL 解析 | 作业定义里确实这么写了 | 实际运行是否走了这条分支 | 可以（可复算、可复核） |
| 运行时采集 | 这次执行真的读了写这些对象 | 没跑过的作业有什么依赖 | 可以（是事实记录） |
| 人工登记 | 有人这么认为 | 是否仍然成立、何时过期 | 慎用（会静默过期） |
| **LLM 推断** | 文本里有这样的表述 | 这个表述是否指向那条边 | **不要**（无可复核的推导路径） |

- **由此付出的**：**其一，图里从此有两种可信度的边，而下游消费方看不出来**——除非边的**来源标注与验证状态**先定下来：§3.2.5 要求入库的边标出「解析 / 运行时 / 人工 / LLM 推断」并让 LLM 推断边与解析边可区分，字段一级的形态（`origin` / `evidence` / `usable_in_gate`）在 [09 数据血缘 §3](../09-data-lineage/09-data-lineage-section-3-sec3.md) §3.2.5 的候选边结构里给出（§3.2.5 的失效点写的就是这一条：不加区分地混在一起，等于用高置信度的外观掩盖低置信度的内容）。**其二，模型与提示词一变，已入库的边会漂移**，需要重跑比对，这本身就是一项长期运维成本。**其三，人工确认队列会退化**：没有人真的看它，它就变成一排挂着的待办，而「已确认」这个标记会失去意义。
- **证据与来源**：【公开：本书 §3.2.5 的「代价」与「失效点」两段，可逐行核对；主文件 §2.3 把 LLM 补全列为六种采集方法里「新兴、准确率待提升」的一种】。**【本节未能核到】可复核的准确率口径**（可复算的推导路径 / 对不同文本类型的召回差异 / 假边率），也未能核到第三方（非厂商）公开生产案例；正因如此，本节不给任何准确率数字——**任何不带条件（文本类型、提示词、抽检口径）的准确率声称都不可复核**。
- **成熟度**：**L2**。判据：① 核不到（形态已在书内定义，但无可点名的产品发布物）；**②核不到**；③ 置信度分级与入库约定无通行做法 → 可做 PoC，且必须限定在「展示与排查线索」这一侧。
- **判定方法**：抽 50 条模型给出的候选边，请懂业务的人逐条判真假，算出假边率；再抽 20 条「解析失败」的作业，看模型能不能补上其中几条可确认的边。**前者决定它能不能给人看，后者决定它值不值得做。**
- **什么时候值得做**：解析与运行时采集的缺口已经被度量出来（你确切知道缺的是哪一类），且你能接受「先给人看、不进阻断路径」这个定位。
- **什么时候不值得做**：缺口还没度量、或你想用它替代解析。前者会让投入没有靶子；后者是 §3.3 已经给出判据的反例——**可观察到的依赖交给推测去补，等于用一个更贵、更不可复核的手段替换一个更便宜、更可信的手段**。

#### 5.2.3 Agent 驱动的变更管理（原方向 3）

- **旧做法与它的卡点**：变更的影响面靠人去看门禁给出的清单，修复方案靠人写（[§6](05-lineage-and-impact-section-6-sec6.md) 整理的发布门禁流程：影响面超阈值或涉及关键资产则阻断发布，要求补充迁移方案与通知记录）。卡点不是「看不到」，而是**看到之后的动作全部由人承担**：一张被大量下游引用的表，改字段名之后的兼容修复是一批重复劳动。
- **AI 改变了什么机制**：**血缘的定义域从「读」扩到「写」**——这是原方向 3 与前两条的根本区别：前两条产出的是**给人看的信息**，这一条产出的是**对生产环境的写操作**。机制上，它把「影响面分析」从流程的一个输入，变成了行动的一个输入。
- **由此得到的**：**因为给出候选修复所需的全部信息（影响面 + 变换逻辑 + 下游字段）恰好都在血缘与作业定义里，所以「生成兼容修复的候选」是一个有依据的任务**——它可能把一批重复劳动压低到一次评审。注意这里得到的是**候选**，不是执行。
- **由此付出的**：**其一，置信度的门槛在写路径上比读路径高得多【经验】**——读路径上一条错边只是让人多看一眼，写路径上一条错边会改坏生产数据，而 §5.2.2 已经说明边的可信度是分档的。**其二，自动执行需要一个读路径上不存在的东西：回滚语义**——变更已经写下去、下游已经被影响之后，「自动修回来」要求系统知道改前状态、知道哪些下游已经基于新版本产出了数据；这套语义今天没有通行做法。**其三，责任划分会先于技术成熟**——自动执行的每一步都要有人负责，而这条链上今天的责任人是人。
- **证据与来源**：**【无公开可核验来源】**——本节未能核到任何一条可点名的正式条目或带口径的第三方材料描述「Agent 自主执行兼容修复」在生产中运行。原方向 3 的四步（接收变更通知 / 评估影响 / 推荐修复 / 自动执行）里，**前两步的能力已由 [§6](05-lineage-and-impact-section-6-sec6.md) 的发布门禁流程覆盖**（§3.7 的自检清单也把「门禁是否真的阻断过发布」列成必答项），本节判 L3 的是后两步，尤其是第四步。
- **成熟度**：**L3**。判据：① 无正式条目；③ 写操作接口与回滚语义无约定；② 不适用（修复是否正确本身要求影响面可信）→ 记录即可，不要在架构里预留「Agent 会自己把变更做完」这个假设。
- **判定方法**：问它「这次改动改坏了谁负责、怎么回滚」，再问「哪些下游已经基于新版本产出了数据」。**这两个问题答不出来，写路径就不能开**——它们不是实施细节，是权限本身。
- **什么时候值得做**：影响面已经精确到字段、修复动作是机械重复的那一类（改字段名之后的引用同步），且执行环节由人确认。
- **什么时候不值得做**：影响面还停在表级、或回滚语义说不清时——这两条任一不成立，让 Agent 写生产就是在用一个概率性的输入触发一个确定性的动作。

```text
   同一条边，在两条路径上的门槛不同（这是本方向判 L3 的全部理由）
   ────────────────────────────────────────────────
   读路径（提醒人）
       一条可能错的边 → 人再看一眼 → 代价：几分钟
   写路径（改生产）
       同一条可能错的边 → 自动改字段 → 代价：下游静默算错，
                                         且改动已经落盘
   ────────────────────────────────────────────────
   结论：把「生成候选修复」与「执行修复」分成两件事审批，
         而不是同一条流水线上的两个步骤
```

#### 5.2.4 被写进「AI 时代」但机制没变的那一族（原方向 5；原 §5.2 第 1、3 条；原趋势 1、2、4、5、6）

这一族有八个方向，它们的共同点是：**收益真实存在，但没有一条的收益来自模型能力**。它们要么只是换了前端（GraphRAG），要么是**把一类新边接进同一张图**（训练数据血缘——八行里唯一一条机制的延伸），要么与 AI 没有因果关系（字段级血缘、跨云联邦、开放 API、跨工具规范、AI 治理融合、血缘数据产品）。把它们一起写成「AI 时代的血缘演进」，会让真正要做的三件事——**统一实体标识、给边标来源、把血缘挂进门禁**——一件都排不进排期。

| 方向 | 旧做法与它的卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据与成熟度 |

| 血缘与 AI 治理融合（原趋势 4） | 模型侧追溯与数据侧血缘各写一套材料 | **与 AI 无因果关系**，但被 AI 的合规压力加速 | 一份材料同时回答「数据从哪来」与「模型用了什么」 | 治理还要回答数据来源、标注、模型行为，血缘一条都答不了；把它当治理结论是越位 | ①②③ 同「训练数据血缘追溯」行 → **L2** |
| 跨工具规范统一（原趋势 1；原工业条目 OpenLineage 1.0 GA） | 每接一个引擎就要重写一套采集与存储适配，长尾数据源永远排不上队（§3.2.3） | **与 AI 无因果关系**：它降低的是新增数据源的**接入**成本，不改变边的产生方式 | 采集与存储解耦，长尾数据源的边际接入成本第一次低于它的收益 | 规范只定义事件，不提供存储、UI、影响面与门禁，选了它仍要选后端；后端与规范之间的版本兼容与语义对齐要自己扛（§3.2.3 的代价） | ① 规范有版本化发布物：主文件 §1.4 记 2021 年启动、2022 年 Marquez 成为参考实现、2023 年 1.0 GA；**②核不到**；③ 事件字段与 facet 随版本演进 → **L2** |

**读这张表的方式是看「AI 改变了什么机制」这一列**：八行里只有「训练数据血缘追溯」是真正的延伸（把新的一类边接进同一张图），其余七行要么只换前端、要么与 AI 无因果关系。**这解释了为什么它们都停在 L2 / L3**——判据②核不到只是表层，深层原因是**它们的好处不来自模型能力，所以也不会因为模型变强而变得可核验**。

顺带说清一件常被省略的事：这八行里的**跨云联邦、字段级血缘、开放 API、跨工具规范**四条不是「以后要做」，而是「现在就该做」——它们与 AI 无关，却是 §5.1 表里所有 L2 方向变得可评估的前提。把这四件事与 AI 方向放在同一张排期表里竞逐资源，是本主题最常见的一次排序错误。

### 5.3 与本主题既有栈的接口在哪

血缘与 AI 之间不是「结合」关系，而是**交接物**关系：谁把什么交给谁、数据以什么形态穿过边界、失败时谁负责。这张表比「能不能用」更能决定它能不能落地。**下表「现状」一列用同一套 L1 / L2 判据，但评的是这个接口本身，不是 §5.1 表里的演进方向**——两者不要互相引用，否则同一个 L1 会在两处指两件事。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 血缘 ↔ 数据目录（[../../04-data-assetization/08](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 交接物 = 实体标识（全限定名）+ Owner；血缘图里的节点必须能被目录解析成同一个资产 | 目录侧；标识不统一时，问答入口会把两个同名实体合成一个，影响面直接给错 | L2（跨系统标识对齐无通行做法） |
| 血缘 ↔ 数据安全（[../02-data-security](../02-data-security/02-data-security.md)） | 交接物 = 字段级敏感标注 → 边；「敏感数据流过哪些下游」由血缘回答 | 安全侧定级；定级缺失时，血缘只能画出链路而不能回答它是否越界 | L2（① 核不到：字段级标注是两侧共用的同一份元数据，但这是两侧的内部约定，没有可点名的正式发布物；**②核不到**，没有可指认的第三方（非厂商）公开生产案例；③ 两侧的定级字段与对齐口径无通行做法） |
| 血缘 ↔ 调度与引擎（[../../03-data-stack/12](../../03-data-stack/12-scheduler/12-scheduler-section-3-sec3.md)、§3.2.2） | 交接物 = 运行时事件（作业实际读写）；采集端挂在作业进程内 | 平台侧；采集端异常会影响作业本身，这是 Hook 路线的固有代价 | L2（集成面大、可用性风险在作业侧） |
| 血缘 ↔ CI / 发布门禁（§3.2.3、[§6](05-lineage-and-impact-section-6-sec6.md)） | 交接物 = 影响面查询结果（下游清单 + 关键资产标记） | **血缘侧**；给错清单会放行本该拦住的变更，而门禁不会报错 | L2（门禁形态成熟，但边的来源分档未成约定） |
| 血缘 ↔ 可观测与根因分析（[../04-observability](../04-observability/04-observability.md)） | 交接物 = 异常节点的候选上游集合 + 打分依据 | 可观测侧；只看业务指标不看链路，会把「上游变更」误判成「数据质量问题」 | L2（打分方法无通行做法） |
| 血缘 ↔ 特征平台与模型服务（[../../02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md)） | 交接物 = 「特征 ↔ 上游字段」的边；模型侧只声明用了哪些特征 | 双方共用；特征侧漏采就整条链路断，且断点在下游看不见 | L2（口径与采集面各家不同） |
| 血缘 ↔ RAG / Agent 应用（[../../04-data-assetization/05](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md)） | 交接物 = 只读查询 API + 权限上下文；应用侧不能绕过权限读边 | 应用侧；回答必须区分「确定无上游」与「没采到」，否则错在应用而不在血缘 | L2（问答层的出处格式无共识） |
| 血缘 ↔ 审计与合规（[../07-audit-and-compliance](../07-audit-and-compliance/07-audit-and-compliance.md)） | 交接物 = 可复算的来源链路 + 边的时间戳与来源标记 | 合规与平台联合；**边不带来源标记时，「这条依赖是否可靠」无法举证** | L2（材料形态可定，跨系统互认无做法） |

一句话概括：**AI 没有给血缘新增任何一条边，它新增的是「边的来源多了一种」与「入口的词汇责任换了承担方」**。由此得到三条约定。

**第一条约定：边必须带来源，且来源要能决定它能不能进阻断路径。**（§3.2.5 要求库里的「LLM 推断边」与「解析得到边」必须可区分；到字段一级，卡住这件事的三个字段——`origin` / `evidence` / `usable_in_gate`——其候选边结构见 [09 数据血缘 §3](../09-data-lineage/09-data-lineage-section-3-sec3.md) §3.2.5）这条约定今天是可选的，一年后会变成必需的——因为图上会出现模型推断的边，而门禁必须知道自己在信什么。

**第二条约定：入口必须复用同一套实体标识与权限。** 自然语言入口不产生新的权限模型，它只是把已有权限模型暴露给更多人；任何一处绕过，都会把「查不到」变成「查错了」。

**第三条约定：先度量缺口，再谈补法。** §3.5 给的动作最省事：抽一次真实变更，把影响面清单与实际受影响的资产逐条对齐，对不上的部分落在哪一类（没采到 / 采旧了 / 粒度不够 / 口径不同）——**这个比例决定了你该上 LLM 补全、还是该先修解析器。**

```text
   AI 新增的两样东西，落在不同的边界上，谁也不能替谁兜底
   ────────────────────────────────────────────────
   新边生产者（LLM 推断） ──► 落在「边的可信度」这条边界上
       必须回答：这条边凭什么进图？能不能进阻断路径？
   新消费入口（NL / RAG） ──► 落在「实体标识与权限」这条边界上
       必须回答：它凭什么不把原图的错误放大给更多人？
   ────────────────────────────────────────────────
   两者都没有改变：影响面查询仍是图遍历，
                   链路可信度仍等于最弱的那一跳
                   （09 数据血缘 §3.2.2 的「代价」④）
   判定方法：任意一条结论，先问它来自哪一类边，再问它经过了
             几层消费——两层都答不出，这条结论就只能当线索
```

### 5.4 公开进展与文献

分三类列：论文与第三方生产案例只列能给出标题 / 出处 + 年份的条目；官方文档一类给的是可点名的页面或发布说明（属判定入口，进页面即可核验，具体版本与日期一律以页面上的条目为准）。**宁少勿假**。

**论文（可核验；这一节的作用是说明「问题」比「工具」老得多）**

- Buneman, Khanna, Tan, "Why and Where: A Characterization of Data Provenance", ICDT 2001——把「为什么有这个结果」与「这个值从哪来」分开，是影响分析与溯源两条用途分野的源头。
- Green, Karvounarakis, Tannen, "Provenance Semirings", PODS 2007——用半环统一描述血缘的传播，是「血缘可以从变换规则推导出来」这一工程直觉的形式化基础。
- Cheney, Chiticariu, Tan, "Provenance in Databases: Why, How, and Where", Foundations and Trends in Databases, 2009——血缘的系统性综述；**它成立时 LLM 尚不存在**，可作为「字段级血缘为什么难」的历史依据。
- Sculley et al., "Hidden Technical Debt in Machine Learning Systems", NeurIPS 2015——训练数据的依赖是隐性债务；这解释了为什么「训练数据血缘追溯」是既有诉求，而不是 AI 时代的新问题。
- **原 §5.3 所列三条学术条目（2024 SIGMOD 统一血缘规范、2024 VLDB 字段级血缘自动采集算法、2025 ICDE AI 驱动血缘补全）本节无法核验**：它们给的是主题名而非可检索的标题与作者。处理办法：**保留它们所指的三个方向**（跨工具规范 / 字段级自动采集 / AI 驱动补全），但不把它们当证据；本节也未能给出针对「LLM 生成候选边」的可核验论文标题。

**官方 release note / 文档（判定入口）**

- **OpenLineage 的项目发布页与规范文档**（LF AI & Data 孵化，Marquez 为参考实现）——核验「规范有哪些版本、事件与 facet 的字段长什么样」。年份：主文件 §1.4 记 2021 年项目启动并进入孵化、2022 年 Marquez 成为参考实现、2023 年 1.0 GA；**原 §5.3 另记 2024-01 GA，两条记录不一致，判定入口是项目发布页本身**。判定方法：看规范仓库里有没有该字段的正式条目，而不是看某篇介绍文章。
- **DataHub 的官方文档**（血缘、影响面分析、列级血缘相关页面）——核验「字段级血缘与影响面查询」是否都是正式能力。年份：主文件 §1.4 记 2019 年正式开源；具体能力以官方文档当前版本为准。
- **Apache Atlas 官方文档**——核验「分类分级与血缘」在 Hadoop 生态里的既有形态。年份：主文件 §1.4 记 2015 年开源。
- **各产品的 AI 能力官方文档（Atlan / Collibra / 阿里云 DataWorks 智能血缘 / DataHub 与 LLM 集成一类）**——判定方法：看官方文档里该能力是 GA 还是 Preview，以及**它产出的是「一条边」还是「一条带置信度与出处的候选边」**；前者要追问推导路径，后者才有可用的形态。原清单里「某年某月 GA」的精确时点，本节一律不给，以各家发布说明为准。
- [§ 4](05-lineage-and-impact-section-4-sec4.md) §4.3 的工具链表（本书章节而非外部文献，故不标年份）——核验各工具的定位与「2024-2025 新工具」的分类。

**第三方生产案例**

- **本节未能给出**可核验的第三方（非厂商）公开生产案例。公开材料里能核到的是两类：① 规范与项目的官方文档（属标准组织与建设方一侧）；② 建设方的工程自述——[§6](05-lineage-and-impact-section-6-sec6.md) 整理的 LinkedIn / 阿里 / 字节 / 滴滴四个案例，其出处标注为「机构名 + 年份区间」，没有可检索的文档名，因此按判据属**建设方自述**，不构成第②条。**这个空白本身是结论**：它正是 §5.1 表里没有任何一行到 L1 的直接原因。
- 对要做技术评审的人：**本主题第②类证据最实际的补法是自己造**——把你自己的解析失败率、**来源标为「人工登记」的边占比**、字段级边的数量级、门禁误报率算出来并留存口径。这四组数里，解析失败率、字段级边的数量级与门禁误报率在 §3.5 的修法与 §3.7 的自检清单里各有对应的提问；**「人工登记」边占比没有现成提问**——§3.7 只问「每条边是否带来源标注」，占比要自己从标注里算。这几组数在血缘评审里的分量超过任何厂商案例。
- 三类证据里**最容易造假的是「覆盖率」**：只报一个覆盖率数字而不说分母是哪些作业、解析失败是否计入分母，无法复核。**判定方法**：只接受同时给出「作业总量 / 解析成功率 / 明确标记为盲区的比例」三者的覆盖率。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **自然语言入口**：用 20 个真实提问核对返回实体，并问一次「一张确定没有上游的表」与「一张确实没采到血缘的表」，看回答是否一样。
2. **LLM 补全**：抽 50 条模型给出的候选边，算出假边率。
3. **Agent 变更管理**：问一句「它改坏了谁负责、怎么回滚」——答不出来就不具备写路径的资格。
4. **向量化检索**：查一次「这条边是哪份文档支持它成立的」，追不出出处的只能当线索。
5. **跨云联邦**：问一次「两个域的同名表怎么区分」，没有全限定名与冲突消解规则的，跨域影响面不可信。
6. **字段级血缘**：抽一次真实变更，把影响面清单与实际受影响的资产逐条对齐（§3.5）。

**怎么用这份清单**：要核「能力存不存在」看官方文档与发布说明（最快）；要核「这条边可不可信」看它的来源与推导路径（最慢但最稳）；要核「在我这里值不值得做」看 §5.2 每条给出的判定方法——**第三类问题没有任何公开材料能替你回答**。三类证据之外还有一种最没用、却最常见的形式：把「某平台支持 X」写进方案而不写判定入口——它既不能被复核，也不能被证伪。

### 5.5 被过度宣传的部分

**「自然语言查血缘让业务方自助」**——实际是：问答层**只消费边、不产出边**，它把「没采到」答成「没有上游」，而提问的人没有能力分辨。**为什么会这样**：入口把词汇责任从人挪到了系统，但图本身的缺口一条也没补上；自助的门槛从「会不会写 SQL」降到了「会不会提问」，**而判断答案真假的门槛反而升高了**。**它什么时候才会成真**：回答能区分「确定无上游」与「这一段没采到」，且每条结论都能指回具体的边与出处。**判定方法**：抽 20 个真实提问，数其中有多少条的答案能追到一条边。

**「GraphRAG 让血缘可以推理」**——实际是：可达性查询（谁是谁的下游、影响面有多大）是**图遍历问题**，主文件 §2.2 给出 BFS / DFS 就够了，LLM 推理给出的「可能的链路」既更慢也更不准。**为什么会这样**：图谱推理擅长的是把**非结构化文本**与图上的实体连起来（「这条链路为什么断」这类问题需要读工单与文档），不擅长精确的集合运算。**它什么时候才会成真**：当问题从「谁是谁的下游」变成「这段文字说的依赖对应图上的哪条边」，且答案必须能指回边。**判定方法**：拿一个影响面问题分别用图遍历和模型各答一次，对不上就以图遍历为准——**在血缘里，「查不到」比「查错了」安全**。

**「Agent 自动修好兼容性问题」**——实际是：修复的判定依赖影响面精度（§5.2.2 已经说明边是分档的），而执行依赖回滚语义，这两样今天都没有通行做法。**为什么会这样**：读路径上可以容忍的置信度，在写路径上不可容忍——**同一条边，用来提醒人时够用，用来改生产时不够**。**它什么时候才会成真**：出现「生成候选修复」被正式产品化，且执行环节始终保留人工确认与回滚路径。**判定方法**：问它「改坏了怎么退」。

这三条的共性：**它们都把「信息更易得」当成了「判断更可靠」**——NL 入口让信息更易得，GraphRAG 让解释更易得，Agent 让动作更易得；而血缘领域的稀缺资源从来不是信息，**是「这条边可不可信」这个判断**。

### 5.6 未来 3–5 年：可证伪的预测

这一节写了**五条**，比常规的三到四条多一条，理由是 §5.2 里三处最需要外部信号的位置各要至少一条可证伪的线，少一条就会有一组方向只有评级没有信号：入口（第 1 条）与推断边（第 2 条）对应 §5.2.1、§5.2.2；§5.2.4 那一族里与 AI 无因果关系、却决定前两条能不能被核验的三件事——跨域标识（第 3 条）、字段级精度（第 4 条）、来源标记（第 5 条）——各占一条。§5.2.3 不单列：它要的两个问题（改坏了谁负责、怎么回滚）今天没有可核验的外部材料，只留下 §5.7 的观察项。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 自然语言入口会先在**只读、低风险**场景落地（查口径、找负责人、排障线索），不会先用进变更审批 | 官方文档里出现「确定无上游 / 未采到」的区分项，以及「答案指向具体边」的出处格式 | 产品把两者合并答成「无依赖」，或把问答结果直接作为门禁输入对外宣称 |
| 模型推断的边**不会**进入阻断路径，只会进入「线索」路径 | 门禁或血缘存储出现「只信某几类来源的边」这一配置项 | 某产品默认把推断边计入阻断阈值，并公开说明这样做 |
| 跨云联邦血缘的标准化会先落在**实体标识与桥接语义**上，而不是先落在统一的查询接口上 | 规范侧出现标识 / 桥接的版本化条目（§3.2.4 的三件事被写进规范） | 先出现一个被多平台采用的跨域统一查询 API 标准，而标识规则仍各家一套 |
| 字段级血缘的普及由**门禁精度**驱动，而不是由 AI 取数驱动 | 公开材料把上字段级的动机写成「门禁误拦率高 / 被绕过」 | 公开材料把动机统一写成「AI 取数需要」，而门禁侧没有任何配套 |
| 「边的来源标记」会在三年内成为血缘存储的默认字段，而不是可选的扩展 | 规范或主流平台把来源标记做成默认字段，并出现「只消费某一类来源」的查询或门禁参数 | 来源标记仍是可选扩展，且没有任何消费方按它做过滤 |

写这五条时的共同约定：**信号必须是外部可观察的**（正式功能条目、发布说明、带口径的公开案例），而不是「我觉得会」。**被检验得最快的是第一条**——问答产品的下一个版本里有没有那个区分项，一年内就能看到；**最慢的是第三条**——跨域标准的形成周期通常以年计；最后一条是**本节唯一一条关于「本主题自己的工程约定」的预测**，它的信号落在你身边：规范与平台的下一个版本里，来源是不是默认字段。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有血缘图，但没人用 | 把影响面查询接进 CI / 发布门禁（§3.2.3） | 观察门禁的误拦率与豁免申请量 | 不要先做问答入口——图不可信时，入口只会把错误放大 |
| 想上自然语言查血缘 | 先统一实体标识与权限，再上入口；回答必须能指回边 | 观察官方文档里有没有「未采到」与「确定无上游」的区分 | 不要把问答结果直接喂给门禁；不要让它绕过权限 |
| 想用 LLM 补长尾 | 先定边的来源字段与人工确认队列 | 观察假边率是否被你自己量出来 | 不要用 LLM 去补 Hook 就能采到的边（§3.3 的判据） |
| 想让 Agent 处理变更 | 只做「生成候选修复」，执行仍走人工 | 观察有没有产品把执行环节做成有回滚语义的正式条目 | 不要让 Agent 直接改生产；不要在无回滚语义时开写权限 |
| 想接 GraphRAG | 先用图遍历把常见影响面查询做进百毫秒量级（十万级节点、单次浅层 BFS、不含跨域汇聚段）【经验】 | 观察图检索与图遍历两条路线的公开对比材料 | 不要为 GraphRAG 改图模型；不要用推理代替遍历算影响面 |
| 要为模型训练做数据溯源 | 把特征与导出接进同一张图 | 观察特征侧采集面是否被纳入血缘范围 | 不要另起一套「模型血缘」；不要把血缘当可信度证明 |
| 有人提议把问答结果接进审批流 | 先要求它区分「确定无上游」与「未采到」，并给出出处 | 观察有没有产品把这两者分开答、并支持「只信某几类来源」 | 不要用问答结论代替门禁的影响面查询——门禁要的是可复算的清单 |
| 多云 / 多 BU 要看跨域链路 | 先定全限定名与冲突消解规则，再谈联邦 | 观察规范侧是否出现标识 / 桥接的条目 | 不要在标识不统一前先上联邦——错接比查不到更危险 |
| 要给审计一份来源链路 | 边带时间戳 + 来源标记，链路可逐条复算 | 观察审计材料是否需要「边的来源」这一栏 | 不要用「我们做了血缘治理」这种描述代替可复算的链路 |
| 预算有限，只能做一件事 | 抽一次真实变更，把影响面清单与实际影响逐条对齐（§3.5） | 观察对不上的部分落在哪一类（没采到 / 采旧了 / 粒度不够 / 口径不同） | 不要一上来先补 AI 能力——缺口在哪都还不知道 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改权限模型、扩采集面、引入新的运维面），**而收益依赖一个尚未成立的假设**（图已经可信 / 入口不会被误读 / 模型推断的边够准）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的机制只有**一条**——**边的生产者从确定性解析器扩展到了统计推断器**（并顺带把入口的词汇责任从人挪给了系统）。由此才有「两种可信度的边共存于同一张图」这个新问题，也才有必要把「边的来源标记」从事后补的字段变成设计的一部分。它**没有**改变的是血缘的算法与性质：影响面查询仍是沿反向边的遍历（主文件 §2.2），链路可信度仍等于最弱那一跳（[09 数据血缘 §3](../09-data-lineage/09-data-lineage-section-3-sec3.md) §3.2.2 的「代价」④），**边的可信度仍只取决于它的来源**。
>
> 判断本主题下任何新提法的快捷方式：**它是在生产边，还是在消费边？** 生产边的（LLM 补全）要立刻回答「这条边凭什么可信、能不能进门禁」；消费边的（自然语言入口、RAG、GraphRAG）要立刻回答「它凭什么不放大原图的错误」。第二条判断同样快：**它需要的是图遍历还是文本理解？** 需要图遍历的，别交给模型。
>
> 如果只能带走一句话：**先把实体标识、边的来源标记、血缘在门禁上的挂点这三件事做完，再谈用不用模型**——这三件事做完，本节表里所有 L2 都变得可评估；这三件事没做完，L2 与 L3 的差别只体现在演示视频里。
>
