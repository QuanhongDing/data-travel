### 6.1 LinkedIn：DataHub 起源与 4 年演进（2019-2023）

**背景（Why）**

LinkedIn 在 2019 年面临**全公司数据治理问题**：
- **5000+ 数据资产**（含 Hive / Spark / Presto / Kafka / MySQL）
- **跨团队数据共享**——**「**我不知道谁在用我的数据**」**
- **故障定位**——「**今天 X 表错了，影响哪些下游？**」**没人能答**
- **GDPR 合规**——「**PII 字段在哪？哪些下游在用它？**」**手工数周**

原有方案（2019 前）：
- **手工 Excel 维护血缘**——**完全过期**
- **自研的轻量级血缘**——**只覆盖表级**，不覆盖字段级
- **第三方商业产品（如 Collibra / Alation）**——**贵 + 不灵活**

**触发点（What）**

2019 年 LinkedIn 启动 **DataHub** 项目，目标：
- **字段级血缘**（不只是表级）
- **实时**血缘（Schema 变更秒级反映）
- **开放**（开源 + 多引擎支持）
- **联邦**（跨 region / 跨公司）

**详细做法（How）**

DataHub 的**核心设计**（来自 [DataHub 2020 GitHub] 与 [DataHub 2023 架构升级]）：

1. **事件驱动的元数据采集**
   - 关键设计：**Schema 变更即事件**——发到 Kafka → DataHub 消费
   - 关键能力：HIVE / Spark / Presto / MySQL 都有 **Metadata Change Event** (MCE)
   - 关键代码：
     ```java
     // DataHub 核心：MCP（Metadata Change Proposal）
     public class MetadataChangeProposal {
       public MetadataChangeProposal addAspect(Aspect aspect) {
         this.aspects.add(aspect);
         return this;
       }
     }

     // 提交到 Kafka
     producer.send(new ProducerRecord<>("MetadataChangeEvent", aspect));
     ```
   - 关键收益：**Schema 变更秒级反映**（不是 T+1）

2. **字段级血缘（核心创新）**
   - 关键设计：**列级 lineage graph**（不是表级）
   - 关键能力：通过 SQL 解析器 / Spark 监听器 / DataHub 客户端**自动提取**字段级别血缘
   - 关键代码：SQL 解析
     ```python
     # DataHub SQL 解析器
     from datahub.sql_parsing.sqlglot_lineage import SqlParsingResult

     sql = """
       SELECT o.order_id, u.user_name
       FROM orders o JOIN users u ON o.user_id = u.user_id
     """
     result = SqlParsingResult(...)
     # 输出：order_id ← orders.order_id, user_name ← users.user_name
     ```

3. **联邦（Federation）**
   - 关键设计：多个 DataHub 实例可**互相查询血缘**——**跨 region / 跨公司**
   - 关键代码：基于 **GraphQL** + **gRPC**

4. **实时影响分析**
   - 关键设计：给定表/字段 → 实时计算**下游所有依赖**
   - 关键场景：「**如果我改 orders.user_id，下游哪些表会出问题？**」

5. **搜索 + 资产目录**
   - 关键设计：**全文搜索** + **结构化过滤**（按 owner / tag / domain）
   - 关键工具：**Elasticsearch** 后端
   - 关键数字：LinkedIn 内部**10 万+ 资产**可搜索

**DataHub 版本演进**：

| 版本 | 关键特性 |
| --- | --- |
| 0.1 (2019) | 内部 PoC，表级血缘 |
| 0.5 (2020) | 字段级血缘 + 联邦 |
| 0.8 (2021) | **开源（GitHub）** |
| 0.9 (2022) | Datahub Actions（变更联动） |
| 0.10 (2023) | **实时元数据**（秒级） + AI 助手 |
| 0.12+ (2024) | LLM 辅助血缘补全 + Schema 解读 |

**具体数字（How much）**

- 团队规模：核心贡献者 5-10 人（LinkedIn 团队）
- 关键数字（[DataHub 2023 公开演讲]）：
  - LinkedIn 内部**10 万+ 数据资产**
  - **字段血缘覆盖率 80%+**
  - **故障定位时间下降 70%**
  - 跨团队数据共享效率提升 50%
- 行业影响：到 2024 年，**GitHub 9k+ stars**
  - 80+ 公司用 DataHub（Shopify / Expedia / Coursera 等）
  - LinkedIn / Uber / Airbnb / Slack / Pinterest 等深度使用

**失败教训**

- 第 1 阶段**Schema 解析器太慢**——1 个大 SQL 解析 30 秒——倒逼**增量解析 + 缓存**
- 早期**字段血缘覆盖率 30%**（漏解析）——倒逼**多源解析**（SQL + Spark 监听 + 业务元数据）
- 一次**Kafka consumer lag**导致**元数据延迟 1 小时**——倒逼**Kafka 监控 + 报警**
- **元数据 API 限流**——下游订阅多时**接口扛不住**——倒逼**GraphQL + 分页 + 缓存**

### 6.2 Uber：Databook 5 年演进（2018-2023）

**背景（Why）**

Uber 在 2018 年**500+ 数据科学家**、**日增 200+ 数据表**、**10000+ 数据资产**。原数据资产管理：
- **Confluence / Wiki**——手工维护
- **自研轻量级血缘**——覆盖 30% 资产
- **痛点**：
  - 「**找不到数据**」——每次新数据科学家入职花**2 周**才能熟悉
  - 「**信任数据**」——**不知道这个表谁负责 + 质量如何**
  - 「**影响分析**」——**改一个表不知道影响谁**

**触发点（What）**

2018 年 Uber 启动 **Databook** 项目，2019 年开源（[GitHub uber/databook]），目标：
- **统一的「**数据 + 业务 + 治理**」入口**
- **字段级血缘**
- **影响分析**

**详细做法（How）**

Databook 的**核心设计**（公开演讲 [Strata 2020] 与 [QCon 2022]）：

1. **元数据三层模型**
   - **L1 物理层**：表 / 字段 / Schema / 血缘（来自 Hive Metastore / Spark 监听）
   - **L2 业务层**：业务术语 / 业务域 / Owner / SLA
   - **L3 治理层**：分类分级 / 合规 / 生命周期
   - 关键能力：**L1 → L2 → L3 自动关联**（字段名 = 业务术语）

2. **字段血缘 + 业务血缘**
   - 关键设计：**字段血缘图 + 业务血缘图**（两份图，对应业务实体的流转）
   - 关键代码：血缘合并
     ```python
     # Databook 设计：血缘图合并
     class LineageMerger:
         def merge(self, table_lineage, business_lineage):
             # 1. 字段血缘：A.field1 ← B.field2
             # 2. 业务血缘：业务实体 X ← 字段 Y
             # 3. 合并：字段血统链 + 业务血统链
             return UnifiedLineageGraph(...)
     ```

3. **影响分析**
   - 关键设计：给定变更 → **自动分析影响范围**（下游表 + 下游业务）
   - 关键场景：
     - 「**改 orders.user_id**」→ 「**影响 5 张表 + 2 个业务域**」
     - 「**下线 ads.dau_3metric**」→ 「**影响广告实时大屏 + 风控召回**」

4. **数据质量集成**
   - 关键设计：每个表有**质量评分**（完整性 / 准确性 / 时效性）
   - 关键数字：Databook 显示**质量趋势**——7 天 / 30 天质量变化

**具体数字（How much）**

- 团队规模：Databook 团队 15+ 人
- 关键数字（[Strata 2020]）：
  - Uber 内部**10000+ 数据资产**
  - **字段血缘覆盖率 85%**
  - 新数据科学家**入职第 1 天**就能用 Databook 找数据
  - **故障定位时间下降 60%**
- 业务覆盖：Uber **100% 数据团队**用 Databook

**失败教训**

- 早期**Schema 解析器覆盖 30%**——倒逼**多源解析 + 业务元数据融合**
- 一次**元数据 API OOM**（Hive Metastore 一次返回 100 万字段）——倒逼**分页 + 流式**
- **业务 Owner 标注不准确**——**30% 字段标错**——倒逼**自动推断 + 人工确认**
- **影响分析慢**——1 次完整分析 10 分钟——倒逼**增量分析 + 缓存**

### 6.3 Airbnb：Data Portal + 资产目录（2018-2023）

**背景（Why）**

Airbnb 2018 年**5000+ 数据资产**、**200+ 数据科学家**。原方案：
- **内部 Wiki**——手工维护
- **自研简单目录**——只覆盖 50% 资产

**触发点**

2018 年 Airbnb 启动 **Data Portal** 项目，**核心目标**：
- **「**Airbnb 的数据在哪里**」**——唯一入口
- **Owner / 文档 / 血缘**——一张卡片
- **新数据科学家 onboarding**——**1 天搞定**

**详细做法（How）**

Data Portal 的**核心设计**（公开演讲 [Airbnb OpenAir 2019]）：

1. **资产卡片（核心）**
   - 关键设计：每个表 / 字段 = **一张卡片**——含**Owner / 文档 / 血缘 / 质量 / SLA / Tags**
   - 关键能力：点击字段看所有**上下文**（不是孤立信息）

2. **搜索 + 发现**
   - 关键设计：基于 **Elasticsearch** 全文搜索
   - 关键能力：「**搜索 revenue → 列出所有 revenue 相关的表**」

3. **血缘**
   - 关键设计：基于**自研轻量级血缘** + 集成 Apache Atlas
   - 关键能力：**表级 + 字段级**血缘

4. **数据质量集成**
   - 关键设计：每个表有**质量评分** + **SLA**
   - 关键能力：表卡片上显示**「**这个表多准 / 多新**」**

**具体数字（How much）**

- 团队规模：Data Portal 团队 8 人
- 关键数字（[Airbnb OpenAir 2019]）：
  - **5000+ 数据资产**
  - **字段血缘覆盖率 70%**
  - 新数据科学家**1 天**找到 80% 需要的表（之前**2 周**）
  - 跨团队数据共享**提升 40%**

**失败教训**

- 早期**Owner 标注不准确**——倒逼**自动推断 + 定期审计**
- **字段血缘覆盖 30%**（漏解析）——倒逼**多源解析 + Schema 注册制**
- **数据质量评分被「**刷分**」**——倒逼**ML 异常检测 + 人工抽查**

### 6.4 字节跳动：Dataleap 数据治理（2020-2024）

**背景（Why）**

字节 2020 年**百万级数据资产**、**500+ 数据工程师**、**5 万+ 业务表**。原方案：
- **自研轻量级血缘**（基于 Spark 监听）
- **痛点**：
  - 「**改一个字段**」需要**手动评估**影响范围
  - 「**找字段归属 Owner**」需要**发群问**——平均**半天**
  - 「**判断字段是否含 PII**」——**人工审核**——**GDPR 风险**

**触发点（What）**

2020 年字节启动 **Dataleap** 项目（[ArchSummit 2022]），目标：
- **全公司数据治理**（不只是技术）
- **Owner 体系**（业务 Owner + 数据 Owner + 平台 Owner）
- **影响分析自动化**（5 秒出结果）
- **PII 自动识别**（ML 辅助）

**详细做法（How）**

Dataleap 的**5 大创新**：

1. **字段级血缘 + 影响分析（核心）**
   - 关键设计：基于 **Spark 监听 + Flink SQL 解析**——**字段级血缘覆盖 90%+**
   - 关键能力：「**改 orders.user_id**」→ **5 秒出影响范围**

2. **Owner 体系（治理基础）**
   - 关键设计：每张表有 3 类 Owner：
     - **业务 Owner**（产品经理）——**对数据语义负责**
     - **数据 Owner**（数据工程师）——**对数据质量负责**
     - **平台 Owner**（平台团队）——**对数据基础设施负责**
   - 关键能力：3 类 Owner 自动**认领**——**新表创建 24 小时内必须认领**

3. **PII 自动识别（GDPR / 个保法）**
   - 关键设计：基于 **ML 模型 + 命名规范**——**PII 字段识别准确率 95%**
   - 关键能力：自动打 PII 标签 + 自动应用访问限制
   - 关键工具：基于 BERT 的字段识别

4. **变更管理联动**
   - 关键设计：字段变更 → 自动通知**所有下游 Owner**
   - 关键能力：「**改了 orders.user_id**」→ **自动通知 5 个下游 Owner**
   - 关键效果：**变更管理时间从 1 天降到 10 分钟**

5. **PII 数据追踪（GDPR / 个保法要求）**
   - 关键设计：每个 PII 字段有**完整流向图**——「**这个身份证号在 5 张表里流转**」
   - 关键能力：GDPR 数据删除请求 → 自动定位 + 自动删除

**具体数字（How much）**

- 团队规模：Dataleap 团队 30+ 人
- 关键数字（[ArchSummit 2022]）：
  - **50000+ 数据资产**
  - **字段血缘覆盖率 90%**
  - **Owner 覆盖率 100%**
  - **变更管理时间从 1 天降到 10 分钟**
  - **GDPR 数据删除定位从 1 周降到 1 小时**

**失败教训**

- 早期**Spark 监听器 OOM**——一次大表血缘采集**让 Spark Driver 挂了**——倒逼**Spark 端血缘与查询端隔离**
- **Owner 认领率 30%**——**业务方不认**——倒逼**「**新表创建不认领不让上线**」**机制
- **PII 误报**——**正常字段（如 user_id）被识别为 PII**——倒逼**ML 模型 + 人工二次确认**
- 一次**字段血缘循环**（A→B→C→A）——**影响分析死循环**——倒逼**循环检测 + 截断**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选**LinkedIn DataHub**（开源）或 **Apache Atlas**（Hadoop 生态）
- 接入**核心 100-500 个表**
- 关键产出：1 个 metadata 平台 + 字段血缘
- 团队：3-5 人

- 扩展到**5000+ 表**
- 引入**字段血缘 + 业务血缘**融合
- 引入**Owner 体系**
- 引入**变更管理联动**
- 团队：10-20 人

**10 → 100 阶段：12-24 个月**

- 扩展到**10000+ 表**
- 引入**AI 辅助**（LLM 补全血缘 / PII 识别）
- 引入**影响分析自动化**
- 引入**PII 数据追踪**（GDPR / 个保法）
- 团队：20-50 人

**100 → 1000 阶段：12-24 个月**

- 跨云血缘联邦
- 跨公司血缘共享（Data Mesh 场景）
- **元数据即数据**（Metadata as Code）
- 团队：50-100 人
