## 7. 与其他方法对比

> 原 § 7 共 58 行、为 1 张 6 维度 1–5 分的打分表（含总分列）+ 1 棵决策树 + 3 条组合，缺少机制解释与可溯源证据，重写为 ~300 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

打分表在这一主题上失效得比在其他主题更彻底。原来那张表给「表级血缘 / 字段血缘 / 自动采集 / 实时性 / AI 集成 / 社区生态」各打 1–5 分再求总分——这意味着**「AI 集成」上的 1 分与「表级血缘」上的 1 分在决策里等价**，而实际上前者是一年内可能用不到的能力，后者是能不能用的底线。总分把「某维度一票否决的能力」和「加分项」混成了同一个尺度，于是排序会稳定地把「功能面广的产品」排在「覆盖边界清楚的产品」前面。

第二，同一维度在不同约束下权重相反，甚至**方向相反**。「实时性」在排障高频、变更频繁的团队里是加分项；但在以 T+1 批处理为主、对作业延迟极度敏感的平台上，「实时采集」可能反过来是风险项——采集钩子跑在作业进程内，采集端异常会向上传播，实战中最常见的形态是钩子抛错导致任务失败，团队于是整体关掉钩子，血缘退回人工登记（§3.2.2 的失效点）。这个反转在打分表里完全看不到。

第三，阈值没有来处。原决策树的最后一个节点写「预算充足（> 100 万/年）」，但没说这个数字是怎么来的——它是人力成本、软件订阅费，还是两者之和？不同来处意味着完全不同的可调整空间。本章把这类节点改写成**可以用推导或可观测指标替换**的形式：7.5 的 T5 会给出「100 万/年量级对应的是大约几名常驻工程师的全成本」，读者可以据此换算到自己团队的人数与薪酬水平。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 采集入口的覆盖边界 | 它采**不到**哪些边 | 一条采不到的边就是一次不可预见的变更事故；覆盖面决定影响面可不可信，而不是功能多不多 |
| 边的可信度与可复核性 | 每条边能不能拿 SQL 原文或执行记录复核 | 不可复核的边进不了审计与门禁——审计要能举证，门禁要被绕过就得有据可查 |
| 成本随什么增长 | 随表数、字段数、引擎种类，还是资产数增长 | 字段级边是表级边的 20–400 倍量级【经验：按 §3.2.1 的 c ≈ 20 估算，c 本身取经验区间 10–50】，成本函数决定你在哪个规模才付得起 |
| 血缘挂在哪个环节 | 谁在消费它：展示页 / 目录 / 发布门禁 / CI / 开放 API | 同一份采集能力挂在不同环节，价值差一个量级：放在文档里没人看，挂在门禁上每次变更都得正面回答 |
| 元数据模型是否开放 | 离开它要重写什么 | 私有模型把血缘锁死在单一工具里，目录、质量、权限各自重复解析一份（重复采集的根源） |
| 项目活跃度与路线图 | 停更了怎么办 | 停更项目的迁移不是换 UI，是重建整条采集链路（§4.3 已把两个停更项目单独标出） |

> 这 6 条不并列：**覆盖边界与边的可信度**是能不能用的底线（这两条不满足，后面四条没有意义）；**成本与挂在哪个环节**决定它能不能长期活下去；**模型开放度与活跃度**决定你要不要为将来准备一次迁移。

用这六条的顺序，可以避免一种最常见的错误：**先被功能列表吸引，再倒推需求**。血缘产品的功能列表高度相似（目录、搜索、字段级血缘、敏感数据标注、影响面查询、自然语言问询），差别几乎全在采集入口、可信度与消费位置上。所以正确的问法是「我的作业形态是什么、我的引擎有几个、我要把血缘挂在哪里」，而不是「哪个产品功能更多」——前一组问题的答案会把候选缩到两三个，后一组问题永远给不出排序依据。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| DataHub | 一体化开源元数据平台（出自 LinkedIn） | 统一事件模型采集 + 读路径走独立索引与关系图，血缘与目录同一份元数据 | 自建元数据平台的中大型团队 | Apache 开源（自托管，部署较重） |
| Apache Atlas | Hadoop 生态的元数据与治理 | 引擎 Hook（Hive Hook 一类）采集 + 强分类分级 | Hive / Hadoop 存量平台 | Apache 开源 |
| OpenLineage / Marquez | 采集规范 + 参考后端 | 规范只定义「作业 / 运行 / 数据集 / facet」事件，存储与查询交给后端 | 跨引擎、多调度工具的团队 | 开源（规范由 LF AI & Data 孵化） |
| Unity Catalog | Lakehouse 平台自带的元数据与血缘 | 血缘内建于平台管辖范围内，与 catalog 权限同一套对象模型 | 已在一个平台上集中建仓的团队 | 商业 / 随平台提供 |
| Collibra | 企业级数据治理套件 | 治理流程（政策、术语、审批）为骨架，血缘是其中的一个视图 | 金融、受监管行业 | 商业 |
| Atlan | 现代数据目录 + 血缘协作 | 面向协作的资产页 + 跨云的联邦视图 | 多云、多团队协作的现代数据栈 | 商业 SaaS |
| 阿里云 DataWorks（血缘） | 调度、血缘、治理一体化 | 血缘与调度同源，天然拿到任务级与字段级关系 | 阿里云上的中国本土团队 | 商业（云上服务） |
| 自研（OpenLineage + 自研存储） | 规范做采集、存储与门禁自建 | 用规范消除接入成本，把差异化放在影响分析与门禁上 | 规模大、有平台团队的头部公司 | 自研（长期人力投入） |

可以增补的同类候选（§4.3 已列，按活跃度分两类）：**仍在演进**的 OpenMetadata（易部署）、Datafold（数据测试 + 血缘 Diff 强）、Alation、Informatica、字节 DataFinder；**已停更**的 Metacat（Netflix）与 Amundsen（Lyft）——停更这两个是本章「演进风险」判据最直接的经验依据，选用前请按各自仓库的最近提交与 release 记录核验。

选型时容易被忽略的是**它们多数不是同一层的东西**：DataHub、Atlas、Unity Catalog 是「平台」（自带采集与存储），OpenLineage 是「规范」（不是产品），Marquez 是「后端」（规范的一个实现），Collibra、Atlan、Alation 是「治理套件」（血缘只是其中一个视图）。把它们放在同一张表里比较功能是失真的——**正确的做法是先确定每一层由谁承担，再逐层选**：规范层选 OpenLineage 或平台私有模型；后端层选自建 / Marquez / 平台自带；消费层选目录、门禁、审计分别用什么。

这些候选分成三族，跨族差异远大于族内差异：

- **规范族**：先定事件规范（OpenLineage），再选后端（Marquez / DataHub / Atlas / Unity Catalog / 自研）。族内差别几乎只在后端，采集侧相同。
- **一体化平台族**：采集、存储、UI、门禁出自一家（DataHub、Unity Catalog、DataWorks、商业套件）。上手快，但采集入口受平台自身的扩展点限制。
- **接入兜底族**：为长尾场景补采集（Hook / Listener、脚本类的运行时采集、人工登记）。**它不是一个可选的产品，而是任何一族的必配**——因为下游消费者从来不只在主干系统里。

**分族看的是你的部署方式，不是产品本身**：DataHub 与 Unity Catalog 都可以同时扮演「平台」与「规范后端」两种角色——DataHub 自带采集与存储时是一体化平台，把它的元数据与血缘模型当作规范事件的下游后端时又属于规范族；自研同理，既可以是「规范 + 后端」的解耦形态，也可以是采集、存储、UI 全自建的闭环形态。这正是 7.3.2 那张表里同一个候选会落在两行的原因：**读那张表时问的是「这一项在你的部署里承担哪一层」，而不是给产品归一次类了事**。

分族之后，每个候选只需要问两个问题就够了：

1. **它的采集入口覆盖你的作业形态吗？** 判断方法是查它的连接器 / 适配器清单，看你实际在用的那几个引擎与调度工具是否在列；不在列的部分，就是你要自己补的行数（这直接决定 7.4 成本函数的第一项）。
2. **它的血缘能被你想挂的那个环节消费吗？** 如果目标是门禁，就要确认它有 CI 可调用的接口（事件或 API），而不是只有页面；如果目标是审计，就要确认每条边带得出可复核的依据（解析出的 SQL 原文或执行记录）。

这两个问题答完之后，剩下真正需要比的东西已经很少：许可与费用、模型开放度、以及项目活跃度。**把候选按这两问过一遍，通常只会剩两三个**，此时再谈功能细节才有意义。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 采集入口决定了覆盖面与边的可信度

**机制是什么**：血缘的边从哪来——读作业定义文本、读执行期事件，还是由人填写。

| 采集入口 | 覆盖什么样的边 | 新鲜度 | 边的可信度 | 典型缺口 |
| --- | --- | --- | --- | --- |
| 作业定义（静态解析） | 代码里写出来的表 / 字段依赖 | 跟随代码变更 | 高：边可从 SQL 原文复核 | 动态 SQL、拼接表名、脚本任务 |
| 运行时事件（Hook / Listener） | 真实执行过的读写依赖 | 作业跑完即得 | 高：记录的是实际发生的读写 | 长期不调度的作业、未接入的引擎 |
| 人工登记 | 语义层依赖（口径、业务含义） | 低：登记即开始过期 | 中：依赖登记者当时的理解 | 规模一大必然失守 |

**由此必然导出的性质**：因为静态解析读的是**文本**而不是数据，所以它的采集成本只与「有多少条 SQL」相关、与数据量无关；代价是解析器要按方言各维护一份，且它看不见的边恰好是那些没人写进版本库、只存在于某人脚本里的依赖（§3.2.1 的失效点）。反过来，因为 Hook 记录的是**实际发生的读写**，所以它能覆盖动态表名与跨引擎读写；代价是钩子跑在作业进程内，采集端阻塞或异常会向上传播。两条路线的缺口集合不同，**所以它们的关系是互备而不是二选一**。

**公开证据**：主文件 §1.4 记 2012 年 Apache Hive Hooks 机制实现粗粒度血缘（[主文件 §1.4, 2012]）【公开】——该年份可按 Apache Hive 关于 Hooks 扩展点的历代文档与发布记录自行核验；本仓把 Apache Atlas 归为 Hook 路线的代表实现（§3.2.1 对该路线归属的说明），因为它的采集依赖引擎侧钩子而不是 SQL 文本解析。按引擎提供的扩展点类型判断一个系统属于哪条路线，比看它有没有挂「血缘」名号更可靠。

**失效条件**：当作业对延迟的敏感度高于血缘实时性的收益时，「实时性好」会反转为「采集本身成为作业的故障源」。此时正确的动作是把钩子做成异步投递并给采集端单独限流与降级开关，而不是整体关掉它——关掉之后血缘的覆盖会掉到人工登记那一档。

**两条路线在入库时必须带来源，并规定仲裁顺序**。因为解析出的边与运行时采集的边在语义上并不总是等价（解析面对的是「写了什么」，运行时面对的是「实际读了什么」，两者在有动态表名的作业里会不一致），所以合并规则必须事先写下来，通常是「以运行时采集为准，静态解析负责补齐尚未运行的作业」。缺少这条规则的团队，会在第一次遇到两端不一致时选择删掉其中一路——**删掉的那一路往往正是覆盖长尾作业的那一路**，于是血缘看起来更干净了，实际覆盖更窄了。

**采集入口还会决定一件组织上的事：谁负责接长尾源**。规范路线把「接一个新源」的成本降到一个适配器，但适配器由谁写仍然是一个组织问题——由平台团队统一写，长尾源会排队；由各业务域自己写，边进入平台时的质量参差。可行的一种分工是：平台团队维护**适配器模板与验收标准**（什么样的事件算合格、字段血缘必须采到哪一层），业务域负责各自源的具体实现，平台只做验收与合并——这样长尾源的边际成本被分摊，而质量的下限由平台守住。

#### 7.3.2 采集与存储是否解耦

**机制是什么**：采集侧与存储/查询侧是不是同一件东西；换个数据源时，要改的是「一个适配器」还是「一整条链路」。

| 形态 | 代表 | 新增一个数据源要做什么 | 消费侧（门禁 / 目录 / 审计）怎么拿血缘 |
| --- | --- | --- | --- |
| 解耦（规范 + 后端） | OpenLineage + Marquez / DataHub / Atlas / 自研 | 写一个适配器，产出同一种事件 | 读事件或调后端 API，规范变了后端跟着升 |
| 一体化（自带采集与存储） | DataHub 平台、Unity Catalog、DataWorks、商业套件 | 用平台提供的连接器，未覆盖的源要等平台支持或自建插件 | 用平台的 UI 与 API，数据模型由平台定义 |
| 自研闭环 | 自研解析 + 自研存储 + 自研 UI | 每种源都要自己写解析与入库 | 自建门禁与审计，一切自己负责 |

**由此必然导出的性质**：因为规范把「边的产生」与「边的使用」分开，所以新增数据源的边际成本从「写一套采集 + 改一次存储」降到「写一个适配器」，长尾数据源第一次变得值得接入——这是「每个源各写一套解析」的正面解（§3.2.3）。代价是规范只定义事件、不提供存储、UI、影响分析与门禁：**选了它仍然要选一个后端，并承担后端与规范之间的版本兼容与语义对齐；它降低的是接入成本，不是运营成本**。

**公开证据**：主文件 §1.4 记 OpenLineage 于 2021 年启动并进入 LF AI & Data 孵化、Marquez 为其参考实现（[主文件 §1.4, 2021-2022]）【公开】——该项目的启动年份与孵化方可在 LF AI & Data 的 OpenLineage 项目页自行核验；§3.2.3 给出了该规范的事件结构（job / run / dataset / facet）与「采集侧只产事件、消费侧只读事件」的分层图。事件字段与 facet 定义随规范版本演进，接入前请以项目仓库当前版本文档为准。

**失效条件**：当组织把「已采用 OpenLineage」当成「血缘问题已解决」时，「标准统一」会反转成「事件采到了却没人消费」——事件堆在队列里，影响面照样靠问人。规范解决的是边的产生，不解决边的使用（查询、门禁、审计），这是 7.7 反模式一的起点。

解耦还有一个容易被忽略的代价：**语义对齐**。规范定义了事件的字段结构，但没有定义你的组织里「一个数据集」指什么——同一张物理表在三个引擎里可能对应三个不同的命名空间，同一个字段在 Hive 与 Trino 里可能有不同的类型表示。这些差异不会在接入时暴露，而是在第一次做跨引擎影响分析时全部冒出来（表现为「明明有边却连不上」）。所以任何走规范路线的团队，都要在接入期就确定一套资产标识规则（命名空间 + 表 + 字段的稳定 ID），并把它当成规范之外的第一号自建物——**规范给了你统一的语法，没给你统一的词汇表**。

#### 7.3.3 粒度与存储模型决定了影响面精度和成本档位

**机制是什么**：血缘的节点是表还是字段，边存在关系表里还是图里。

- **表级边**：一对表之间恒为 1 条边，解析只需处理 `FROM` / `JOIN` / `INSERT` 的目标与被引用表，入库与遍历都便宜。
- **字段级边**：每个目标字段可引用任意来源字段，解析还要处理表达式、聚合、条件分支、`SELECT *` 展开与 CTE 作用域，边的条数量级跳档。
- **图存储**：血缘天然是有向图，影响分析是反向遍历、根因分析是带评分的反向游走（主文件 §2.2、§2.3）；用关系表模拟图遍历时，多跳查询会退化成多次自连接。

**由此必然导出的性质**：因为字段级血缘的边数是按字段组合展开的，所以在同样的表规模下，**字段级的存储、遍历与校准成本会同步跳档**，而收益是「改一个字段」与「改整张表」能被区别对待——门禁由此可以精确到字段，而不是按整表一刀切（§6 的字节案例正是这个机制）。这也解释了为什么多数团队的真实路径是「表级先上线、字段级等有门禁需求再做」。

【经验：沿用 §3.2.1 的量级估算，前提 c（每表字段数）本身取经验值，区间 10–50，下文用中值 c ≈ 20 演示】一张表平均 c 个字段时，字段级边约为表级边的 **20–400 倍**（低端随 c 线性、高端随 c² 走；c 取到区间两端时该倍数整体落在 10–2500 倍之间）。落到规模上，若一个平台有 10 万张表、平均每表 5 条表级入边（同为一个量级假设），则表级边约 **50 万条**；按 20–400 倍放大，字段级边约 **1000 万到 2 亿条**量级。这个区间的两端都能从「c 的取值 + 边数公式」推出，量级结论不随 c 的具体取值翻转：**字段级不是「更准一点」，而是另一个成本档位**。

**公开证据**：字段级血缘这项能力在公开材料里是可以按名字直接核验的——Spark SQL 的血缘、Databricks 的 Column Lineage、Cube.js 的 Cube Lineage 与阿里开源的 SQLFlow 都提供字段级依赖的产出（可按「<产品名> column lineage」在各自官方文档与仓库中检索，版本与发布时间请以各自 release 记录为准）。本仓对采集方法与工具的标注同样可逐条回查：主文件 §2.3 把「SQL 解析」列为六种采集方法之首并标明其边界是「准确但受 SQL 复杂度限制」；§4.3 的开源工具表里只有 DataHub 被明确标注字段血缘（「优势」列写「字段血缘 + 强大 UI」），而 Atlas 在同一张表里标注的强项是分类分级，Cube.js 字段血缘则列在其中的 2024-2025 新工具清单里——这几条是本书对工具的定位，不是逐年可核的版本事实。Unity Catalog、Atlan 等产品在 §4.3 并未被标注为字段血缘，它们的字段级覆盖程度请以其各自官方文档的当前版本核验。

粒度确定之后，还有一件必须配套的机制：**定时重采与比对**。因为血缘的准确性不取决于采得多细，而取决于**它是否还等于当前的依赖**——只要上游改过一次 SQL、加过一次 JOIN，上一轮采到的边就已经过期。所以任何粒度的方案都要能回答两个数：**覆盖率**（有多少作业 / 表被采过）与**新鲜度**（最近一次采集是什么时候）。这两个数构成了血缘平台自身的可观测性——**一个连自己是否过期都答不上来的血缘平台，无法为别人的数据可信度背书**。判定方法：随便挑一条边，看它有没有最后采集时间；没有时间戳的边，在审计场景里等于不存在。

**失效条件**：当变更风险集中在**表级**（整表重建、分区切换、调度依赖变更）而字段很少被单独改动时，字段级血缘的收益接近于零，此时为它付出的存储与校准成本纯属浪费。

粒度之外还有一层选择：**边存在哪里**。如果边存在普通关系表里，多跳查询会退化成多次自连接，第 3 跳之后性能与可读性一起崩塌。所以规模上来之后，图存储或专门的图遍历索引不是「更高端的方案」，而是「多跳查询能不能用」的分界线。判断方法：拿「三跳下游」这个查询（表 → 下游表 → 引用它的指标 → 引用该指标的看板，或字段级的等价链路）在你的方案上跑一次，看它的耗时随跳数的增长曲线——拐点出现在第几跳，就是你的方案实际能支撑的深度。

#### 7.3.4 血缘挂在哪个环节，决定了它有没有用

**机制是什么**：同一份血缘数据，被放在文档里、放在目录展示页上、挂在发布门禁或 CI 上，还是以开放 API 被多个系统消费——四种位置对应四种完全不同的组织行为。

| 挂载位置 | 谁在消费 | 组织行为有什么变化 | 常见结局 |
| --- | --- | --- | --- |
| 文档 / 汇报材料 | 写文档的人 | 无变化 | 一次性的，之后就过期 |
| 目录展示页 | 想查的人（自愿） | 想查的人查得更快 | 有效，但改的人不看 |
| 发布门禁 / CI | 变更流程本身（强制） | 改动前必须正面处理影响面 | 需要粒度够细，否则会被绕过 |
| 开放 API 多系统消费 | 目录、质量、权限、审计、CI | 血缘只采集一次、被多处复用 | 复用消除重复解析，但要求模型稳定 |

**由此必然导出的性质**：因为门禁会把「影响面」变成变更流程的一个必填项，所以血缘第一次从「参考资料」变成了控制手段；代价是**粒度不够的门禁会因为总在拦而被绕过**——按整表判断时，改一个字段名也会被当成「改全表」处理，阻断次数一多，团队会申请豁免通道，门禁形同失效（§6 阿里案例给的正是这条）。所以「字段级粒度」不是为了好看，而是门禁能长期活下来的前提。

**公开证据**：主文件 §1.4 记 Databricks 于 2024 年推出 Lakehouse Federation、阿里云 DataWorks 于 2025 年推出 LLM 辅助的「智能血缘」（[主文件 §1.4, 2024-2025]）【公开】——两项能力的发布时间可按 Databricks 与阿里云 DataWorks 的官方发布记录与产品文档自行核验；§3.2.3 的失效点指出「事件采到了却没人消费」是规范时代的孤岛形态。判断一个平台的血缘是否真的被消费，看它的 API 调用方有几个，而不是看它有没有血缘页面。

**失效条件**：当变更频率极低、且故障代价可控时，强制门禁的组织成本会超过它省下的事故成本——此时把血缘留在目录展示层、靠评审纪律约束反而是更合理的配置。

这四个位置之间有顺序，而且这个顺序不能跳：**先覆盖、再展示、再门禁、最后才谈复用**。跳过「覆盖」直接上「门禁」的团队，会得到一个总在拦却说不清依据的门禁（因为采不到的边不在名单里，被拦的变更往往不是真正危险的变更）；跳过「展示」直接上「门禁」的团队，则会在被阻断时缺少一条自助查证的路，于是所有人第一反应是找平台团队问。判定的方法很朴素：**门禁阻断一次之后，被阻断的人能不能自己在五分钟内查清「到底影响谁」**——能，说明展示层已经就绪；不能，说明还差一步。

### 7.4 成本结构对比（不是价格表，是成本函数）

血缘平台的成本函数与数据平台不同，它的自变量不是数据量：

```
成本 ≈ 解析器与适配器的长期维护        （∝ 方言数 × 引擎数 × 作业类型的组合）
     + 边的存储与遍历                  （∝ 边数：字段级是表级的 20–400 倍量级【经验】）
     + 常驻服务的固定成本               （事件流 + 索引 + 图存储 + 采集端可用性运维）
     + 人力                            （平台团队 N 人 + 各业务域的接口人）
     + 漏掉的边所对应的期望事故成本      （∝ 年变更次数 × 单次事故的恢复代价）
```

各候选的**主导项**与**隐性成本**：

| 候选 | 主导项 | 隐性成本 |
| --- | --- | --- |
| DataHub 自托管 | 常驻组件（事件流、索引、图存储）的运维人力 | 部署与升级成本；组件版本兼容要持续跟（§4.3 记为「部署复杂」） |
| Apache Atlas | 与 Hadoop 生态的集成与 Hook 维护 | 社区相对小（§4.3），生态演进跟不上时迁移成本高 |
| OpenLineage / Marquez | 适配器的持续开发 | 规范与后端的版本对齐；UI 与分析能力要另配（§4.3 记为「UI 较弱」） |
| Unity Catalog | 平台侧随用量计费 | 边界在平台管辖范围内：平台外的引擎与自建库要另找采集 |
| Collibra / Atlan | 订阅费（按资产 / 席位计价，需询价） | 数据模型与流程被工具定义，离开时导出与重建的成本高 |
| DataWorks 血缘 | 云上服务费 | 血缘与调度同源，好处是准，代价是脱离该平台的部分要自己接 |
| 自研 | 人力（这是唯一的主导项） | 平台能力的每一次扩展都要自己写，且要承担人员的流失风险 |

【推算：自建 vs 商用的对照，以资深工程师全成本 40–80 万元/人年为推导前提（行业普遍实践，无单一权威来源）】一支能长期维护血缘平台（采集适配器、后端、门禁集成、各域接口）的队伍，按 3–5 人常驻计：**3 × 40 = 120 万元/年** 到 **5 × 80 = 400 万元/年**，即 **120–400 万元/年**量级。这条推算的用途不是给出报价，而是把 7.1 里那个没有来处的「100 万/年」还原成它实际测的东西：**约 1–3 名常驻工程师的全成本**（100 万 ÷ 40 万元/人年 = 2.5 人，100 万 ÷ 80 万元/人年 = 1.25 人，区间两端都由这条推导链得到）。也就是说，那个阈值真正在问的是「你有没有一支愿意长期养血缘的团队」，而不是「你的预算够不够」——预算可以一次性批，人力不行，这正是血缘项目大量停在半路的原因。**但 1–3 人低于本段前半按最小队伍估的 3–5 人量级**，所以 7.5 的 T5 用「3–5 人」而不是「100 万元/年」作阈值：能拨出这支队伍，才算真的养得起。

【经验】成本函数里最容易被低估的是**第一项（解析器与适配器的维护）**，因为它看起来是一次性开发。实际上它是随引擎版本走的：被解析的 SQL 方言会随引擎升级而变化，作业里新出现的写法（CTE、窗口函数、UDF、动态表名）都会让解析结果从「精确边」退化成「近似边」，而每一次退化都可能让一条门禁失效。多数平台在第二年才开始为这件事单独排人力，而那通常已经晚了一个版本周期。

【推算：漏边成本的量级，以「一次事故的代价 = 发现 + 定位 + 重跑修复」三段为推导前提】一次未预期的跨团队变更事故，代价大致由三段构成：**发现延迟**（下游在下一个调度周期才失败，按小时到天计）、**定位时间**（无血缘时靠人逐个下游问，按人日计）、**重跑与修复**（按人日计）。取一次合计 **3 人日**（发现当天 + 定位 1 人日 + 修复 1 人日）：若一年发生 **5 次**，合计 15 人日，按 8 小时/人日折约 **120 人时**——相当于一个人大半个月的全部工时（一个人月按 21 人日 ≈ 168 人时计）。这条推算的用途不是精确估值，而是揭示成本函数最后一项的性质：**它随事故次数增长，而事故次数随变更次数增长**，与数据量无关。所以「变更越频繁、下游越多」的组织，血缘的价值增长得越快，这跟「数据量越大越需要血缘」的直觉正好相反。

### 7.5 决策树（每个分支都要有阈值依据）

用这棵树的顺序是**从 T1 往下依次问**，但只有 T1 是「命中分支就出树」的筛选题：它答「三个都是『否』」时到此为止；一旦答「至少一个『是』」，就要**依次回答 T2–T7 六个问题，六个都要答完**。这六问是**彼此正交**的，各自只决定方案的一个组成部分——T2 决定采集走哪条路线、T3 决定后端与目录用谁、T4 决定血缘挂在哪个环节、T5 决定自建还是商用、T6 决定要不要加一层联邦视图、T7 决定要不要叠加 LLM——所以它们各自的分支都不构成「终点」，也与你在其它几问选了哪一支无关。树里为消除歧义，把 T2–T7 画成**同一层上的连续节点**，而不是上一问某个分支的子节点。把六问的结论拼起来，才是你的方案。树上每个带编号的节点，都在树后有且仅有一条对应解释，并给出**在你自己的环境里怎么重算这个阈值**的方法。

```
T1 有没有一个必须系统化回答「这次改动会破坏谁」的场景？（近期是否发生过跨团队变更事故？
   是否有对外承诺 SLA 的下游？是否有审计要求能追溯来源链路？）
├── 三个都是「否」→ 先不要上平台：调度 DAG + 代码评审 + 一份人工维护的关键资产清单（到此为止）
└── 至少一个「是」→ 继续：依次回答 T2–T7 六个问题（六问正交，每问都要答完）
    │
    ※ T2–T7 都挂在 T1 的「是」这一支下、互为同一层，不是上一问某个分支的子节点；
      每一问的每个分支只决定方案的组成部分之一，答完都继续往下问。

    T2 作业以静态 SQL / dbt 模型为主吗？【决定采集路线】
    ├── 是 → OpenLineage + 后端（Marquez / DataHub），走「作业定义 + 运行时事件」双路
    └── 否（脚本、动态 SQL、跨引擎读写占比高）→ 必须补运行时采集（Hook / Listener）
            或脚本类运行时兜底，否则盲区恰好落在最关键的边上
    │
    T3 数据集中在一个平台 / 一个云账号内吗？【决定后端与目录】
    ├── 是 → 平台的 catalog 血缘（Unity Catalog 一类），血缘与权限同一套对象模型
    └── 否 → DataHub 为主；Hadoop 存量重、且需要强分类分级时用 Atlas 的 Hook 路线
    │
    T4 变更门禁要卡在代码评审阶段吗？【决定血缘挂在哪个环节】
    ├── 是 → 血缘必须能被 CI 调用（事件 / 开放 API）；规范化路线天然满足，
    │        一体化平台要确认它有没有 CI 可用的接口
    └── 否 → 目录 + 展示 + 影响面查询即可，先把覆盖面做起来
    │
    T5 有没有一支愿意长期维护血缘平台的常驻人力（约 3–5 人及以上）？【决定自建还是商用】
    ├── 有 → 自研（OpenLineage + 自研存储）或 DataHub 自托管
    └── 没有 → 商业服务（Collibra / Atlan）或云上服务（DataWorks 血缘）
    │
    T6 需要跨云 / 跨账号的联邦视图吗？【决定要不要加一层联邦】
    ├── 是 → Atlan / Unity Catalog 的跨 workspace 联邦 / DataWorks 跨云联邦
    └── 否 → 单域部署
    │
    T7 需要 LLM 辅助（补全血缘、自然语言问询）吗？【决定要不要叠加 LLM】
    ├── 是 → DataHub + LLM、DataWorks 智能血缘（通义千问）、Atlan AI / Collibra AI
    └── 否 → 先不做，等采集与门禁跑通再说
```

**阈值依据**（与树上 T1–T7 一一对应）：

- **T1「三个都是否」**：依据是**没有强制消费方时血缘不会有人维护**（7.3.4 的机制）。判定方法不用估算收益，用三个可查的事实：近一年是否发生过跨团队变更事故、是否有关键资产对外承诺 SLA、是否有审计要求回答来源链路——三者皆无时，血缘的每一份投入都对应不到一个会催它的角色。
- **T2「静态 SQL 为主」**：依据是 7.3.1 的两条路线缺口互补。判定方法很直接：抽样统计作业里「拼接表名 / 动态 SQL / 脚本任务」的占比，同时统计这些作业涉及的表中有多少在核心链路上——**占比低但涉及核心链路时，仍然必须补运行时采集**，因为缺口的价值不由缺口的大小决定。
- **T3「集中在一个平台内」**：依据是**血缘是平台模型的一部分还是库外的元数据**。平台自带的血缘在平台管辖范围内几乎零成本、且与权限同一套对象模型；一旦越出管辖范围（自建库、别的云、第三方 SaaS），它就必须靠外部采集补，此时一体化平台反而变成第二个孤岛。
- **T4「门禁卡在 CI」**：依据是门禁需要**变更流程可直接调用的接口**（事件或 API），而不是人可访问的页面。判定方法：问「CI 里能不能在不打开 UI 的前提下拿到某张表的下游列表」，能做到的才算支持门禁。
- **T5「3–5 人及以上」**：依据来自 7.4 的成本函数推算——自建与自托管的成本几乎全部是人力，而一支能覆盖采集适配器、后端、门禁集成、各域接口的最小队伍是 3–5 人，按 40–80 万元/人年计约 120–400 万元/年【推算，推导链见 7.4】。判定方法：看你现有的平台团队能否在不砍掉其他项目的前提下，拨出这样一支 3–5 人的队伍长期做这件事；拨不出就说明阈值不满足，与预算数字无关。
- **T6「跨云 / 跨账号」**：依据是**联邦的分界线在元数据而不在数据**（联邦只交换边与资产标识，不搬数据）。判定方法：盘点你的资产是否分布在两个以上互不可见的账号或云，且合规上不允许把元数据整体归集到一处。
- **T7「LLM 辅助」**：依据是 LLM 在这条链路上目前的位置——它是**补全与问询的入口，不是边的来源**：由模型推断出的边不可从原文复核，因此只能作为「待确认的候选边」进入，不能直接并入解析边参与门禁（7.3.1 的可信度判据）。判定方法：问「这条模型推断的边出问题时，我拿什么复核它」；答不上来就先不要把它接进门禁。

**这棵树里排在最前面、也最容易被跳过的其实是 T1**。它的作用不是筛选产品，而是**判断现在该不该开始**：血缘平台的失败模式高度集中——在没有强制消费方的情况下启动，于是没人用、没人维护、半年后停更，最后组织得到「血缘没什么用」的结论。反过来说，只要 T1 命中其中任意一项（发生过跨团队变更事故、有关键资产对外承诺、有审计要求），血缘就自动获得了一个会持续催它的角色，项目才有可能活过第二年。所以 T1 答「否」时的建议不是「再等等看」，而是「先去做那件让你将来不得不上血缘的事」——例如把关键资产的 SLA 明确下来、把变更流程写成书面规则——**这些动作本身就是血缘的入场券**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 单团队起步、只想先看清依赖 | OpenLineage + Marquez | 表级血缘 + 调度 DAG 导出 | 直接上商业套件时，流程成本远大于当时的收益 |
| 已有 Hadoop 存量、需要强分类分级 | Apache Atlas | DataHub | 以 SQL 解析为主的路线在这里拿不到 Hook 才有的执行期依赖 |
| 多引擎、多调度工具、要进 CI | OpenLineage + DataHub / 自研后端 | Marquez | 一体化平台的 CI 接口与血缘粒度要逐个确认，不到位时门禁会被绕过 |
| 已在一个 Lakehouse 平台上集中建仓 | Unity Catalog | DataHub 补平台外资产 | 它的血缘边界就是平台的管辖边界，越出范围后仍需外部采集 |
| 受监管行业、治理流程是主线 | Collibra | Alation / Informatica | 以血缘为切入点的工具在这里要补大量政策与审批流程 |
| 多云多账号、团队协作强 | Atlan | DataHub + 自建联邦 | 单域平台在多云下会变成多个互不可见的孤岛 |
| 阿里云上的中国本土团队 | DataWorks 血缘 | 自建 OpenLineage 路线 | 血缘与调度同源是优势，脱离该平台的部分要自己接 |
| 规模大、有平台团队、门禁是核心诉求 | 自研（OpenLineage + 自研存储） | DataHub 深度定制 | 商业套件的数据模型由厂商定义，门禁逻辑难按自己的流程改 |

**矩阵里最容易被误选的一对，是「一体化平台自带血缘」与「规范 + 后端」**。两者的差别不在功能，而在**边界的归属**：一体化平台的血缘边界等于它管辖的资产范围，范围内的成本极低、准确度极高（因为它与权限、调度同一套模型），越出范围就要外部采集；规范路线则相反，范围外照样能接，但范围内的人需要自己把后端的查询、UI 与门禁做出来。误选的后果通常是「范围内很好用、范围外看不见」，而看不见的那部分恰好是自建库、脚本任务与第三方 SaaS——正是变更事故的高发区。所以这一对的选择只应该由一个问题决定：**你的资产有多少比例落在某一个平台的管辖范围内？**接近全量时选一体化，明显不是全量时选规范路线，并把平台自带血缘当成其中的一个后端。

**常见组合及其职责边界**（组合的价值在于**边界清楚**，不在于件数多）：

- **组合一：DataHub + OpenLineage + Marquez**。OpenLineage 负责「把各引擎的信息翻译成同一种事件」，Marquez 负责事件存储与查询，DataHub 负责元数据模型、目录展现与血缘可视化。边界是：**采集侧的差异全部收敛到适配器，消费侧只认事件**。运维代价：三件常驻组件（事件流、Marquez、DataHub）要一起升级，规范版本与后端版本必须对齐。
- **组合二：Unity Catalog + Atlan + DataHub**。Unity Catalog 提供平台内血缘与权限，Atlan 提供跨云联邦与协作视图，DataHub 作为开源补充覆盖平台外资产。边界是：**每个域以自己的一体化平台为事实来源，联邦层只做拼装**。运维代价：同一份资产可能在两处存在描述，需要一套资产标识对齐规则，否则跨云影响面会出现重复与遗漏。
- **组合三：DataWorks + 智能血缘 + 通义千问**。DataWorks 提供血缘与调度（同源，任务级关系天然准确），智能血缘用 LLM 补全解析不到的边，通义千问提供自然语言问询入口。边界是：**LLM 只产出「待确认的候选边」，进入门禁前必须经过人工或规则确认**。运维代价：模型推断的边需要一条独立的复核队列，否则不可复核的边会污染审计结论。
- **组合四：自研（OpenLineage + 自研存储 + 自建门禁）**。用规范消除接入成本，把差异化投在影响分析与门禁上。边界是：**规范负责边的产生，自研部分负责边的使用**。运维代价：后端、UI、门禁、审计全部自建，人力是唯一且不可压缩的成本项（7.4 的第一项）。

这四条组合有一条共同的纪律：**每引入一件，就要能回答「这条边出问题时拿什么复核」**。答不上来的件，无论它带来多少功能，都不能接进审计与门禁——因为门禁的每一次阻断都要能被解释，解释不了的门禁会在第三次被阻断时失去权威。

### 7.7 选错的代价与迁移成本

**反模式：把「已采用 OpenLineage」当成血缘问题已解决** —— 症状是各引擎的适配器都接上了、事件也在流，但影响面查询照样靠人问；后果是规范统一了这个「标准已经落地」的印象，反而让「建后端、接门禁、做审计」这些真正的工作推迟了；正确做法是把规范落地与「消费侧建成」分开定义验收标准，前者看适配器数量，后者看「CI 里能不能拿到下游列表」这件事是否已经跑通（7.5 的 T4）。

**反模式：门禁按表级一刀切** —— 症状是任何人改一个字段名也要走一次影响面审批，阻断记录里大量是「实际上没人受影响」；后果是团队申请豁免通道，门禁形同失效，而豁免名单一旦出现就会一直存在；正确做法是先补到字段级粒度（7.3.3），让门禁能区分「改字段」与「改全表」，把严格度集中在真正高影响的变更上。

**反模式：把人工登记当作血缘的主要来源** —— 症状是上线时有覆盖、数月之后依赖早已变化而血缘还是旧的【经验】，且没有任何指标能发现这件事；后果是过期血缘比没有血缘更危险——它会给出错误的信心，让变更评审基于一份早已失效的下游名单放行；正确做法是以自动采集（解析 + 运行时）为主、人工只做补充与校正，并给每条边记录**最后更新时间**，把「新鲜度」做成可查询的指标（§6 的案例把这条列为四家共同踩过的坑）。

**换成另一个要动什么**：

| 迁移 | 数据迁移 | 查询改写 | 运维重建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| DataHub → 平台自带（Unity Catalog 一类） | 血缘与元数据重新采集，不是导出导入【经验：量级为月】 | 下游影响面查询改用新平台 API【经验：量级为周】 | 停掉自托管组件，接入平台侧权限【经验：量级为周】 | 平台的对象模型与权限模型【经验：量级为月】 |
| Atlas → DataHub | 元数据模型映射（分类分级条目要逐条确认）【经验：量级为月】 | 采集从 Hook 路线切到解析 + 事件路线，缺口集合会变【经验：量级为月】 | 新建事件流与索引，旧平台并行跑一段【经验：量级为月】 | 从「Hook 思维」切到「事件 + 解析双路」【经验：量级为月】 |
| 商业套件 → 开源自建 | 资产与血缘导出后重建，模型要重新映射【经验：量级为月】 | 通过开放 API 重新对接目录、质量、权限【经验：量级为月】 | 常驻组件从「厂商运维」变成「自己运维」【经验：量级为季】 | 缓存、事件流、图存储三套组件的运维技能【经验：量级为季】 |
| 自研 → 规范 + 现成后端 | 边的存储模型对齐规范（字段级 facet 是重点）【经验：量级为月】 | 采集侧改为产事件，自研的解析器逐步退役【经验：量级为月】 | 后端可替换，但要保留自建的门禁与审计接口【经验：量级为周】 | 团队从「造轮子」切到「接规范 + 做差异化」【经验：量级为月】 |

这四行里最贵的一列同样不是「数据迁移」而是**「团队再学习」**：血缘这个主题没有数据要搬，最贵的动作是**采集路线的更换会让缺口集合改变**——原来靠 Hook 采到的边，切到解析路线后可能采不到了，而团队往往在上线之后才发现。所以迁移方案里必须包含一次**缺口比对**：新旧两套采集并行跑一段时间，逐条比对两边边的差集，确认每一条消失的边都是「本来就不该有」还是「新路线采不到」。

缺口比对可以按三步做，每步都不需要停掉任何一侧：

1. **并行采集**：新旧两套同时采一段时间（覆盖一个完整的调度周期，含月末与季末这类特殊批次）。
2. **比对差集并归类**：把差集分成「新路线多出来的边」「旧路线独有的边」「两边都有但方向或粒度不同」三类；第二类是最危险的，它必须逐条给出解释。
3. **给第二类定去向**：要么补一个适配器 / 兜底采集把它重新覆盖，要么在方案文档里明确登记为「已知盲区」并在影响面查询里显式标注——**已知盲区可以接受，静默丢失不行**。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 还没发生过变更事故、无对外 SLA | 先不上平台，用调度 DAG + 评审 | 没有强制消费方时血缘不会被维护，投入找不到催它的角色 |
| 有一个业务域、百级表 | OpenLineage + Marquez，表级血缘起步 | 采集与存储解耦，新增数据源的边际成本只有一个适配器 |
| 需要进 CI 门禁 | 字段级血缘 + 开放 API，先确认 CI 能拿到下游 | 粒度不够的门禁会被绕过，门禁失效比没有门禁更糟 |
| Hadoop 存量重、要分类分级 | Apache Atlas（Hook 路线） | 执行期依赖与分类分级是它被本仓定位的两项强项 |
| 已集中在一个平台建仓 | Unity Catalog，平台外资产另配采集 | 血缘边界等于平台管辖边界，越界就要外部采集 |
| 多云多账号 | Atlan 或自建联邦层 | 联邦交换的是元数据与计划，不是数据 |
| 受监管行业 | Collibra / Alation，血缘作为治理的一环 | 那里的主线是政策与审批流程，血缘是其中的证据链 |
| 有平台团队、门禁是核心 | 自研（OpenLineage + 自研存储） | 门禁逻辑要按自己的流程改，商业模型改不动 |

上面八行可以压缩成两句话：**先确认有没有强制消费方（T1），再确认采集入口能不能覆盖你的作业形态（T2、T3）**；前者决定要不要做，后者决定做哪条路线。费用、UI、AI 能力都在其后——它们是同一族内可以换的部分，换一次的成本是一个季度（7.7 的迁移表），而不是一次架构重来。

五个最容易被忽略、但会在半年后显形的检查项：

- **每条边能不能回答「它是什么时候采到的」？** 没有这个时间戳，就分不清「依赖真的变了」与「血缘过期了」，而过期的血缘比没有血缘更危险（7.7 反模式三）。
- **采不到的边有没有被显式登记？** 盲区不可怕，静默丢失才可怕——已知盲区要能在影响面查询里被看见。
- **门禁阻断一次之后，被阻断的人能不能自己查清影响面？** 不能的话，门禁的压力会全部回流到平台团队，最终以「加白名单」收场（7.3.4）。
- **采集路线的缺口是不是写成了一份可查的清单？** 没有这份清单，下一次有人加一个新引擎时，会默认它已经被覆盖。
- **这套血缘被几个系统消费？** 只有一个（它自己的 UI）时，说明它还没有成为基础设施，只是又一个页面。

还有一个跨所有候选的提醒：**血缘是元数据的一个子集，不是独立的基础设施**。主文件 §2.1 的概念表把「血缘是元数据的子集」直接写在一行里，§1.1 给出的是三要素（数据资产、流转关系、元数据）与术语表；把它与质量、安全、成本并列为横切能力的是 §1.3 的「与其他横切能力的关系」——正是因为它的边要被这几件事同时消费，影响分析、根因定位、敏感数据流转、成本归因才都要读同一份图。所以选型时还有一个隐藏的判据没写进 7.1 的六条：**你选的方案，能不能被目录、质量、权限这几个系统以同样的方式读一次**。只能被自己读的血缘，会让每个下游系统各自再解析一份——那正是「重复采集」的来源，也是血缘平台最容易被悄悄绕开的原因。

第一次选型前值得先量出的三件事：

- **你的作业形态分布**：静态 SQL / dbt 模型、脚本与动态 SQL、外部导入各占多少（决定要不要补运行时采集）。
- **你的资产分布**：有多少比例落在某一个平台的管辖范围内（决定一体化还是规范路线，见 7.6 矩阵表后的第一段）。
- **你能拨出的常驻人力**：不是预算，是**接下来 12 个月里每周都会出现在这条链路上的那几个人**（决定 T5 的答案，而 T5 是自建与商用之间唯一的分界线）。

> 本节小结：这些候选之间**唯一真正起决定作用的差异是「边的采集入口与它被挂在哪个环节」**——采集入口决定影响面可不可信（采不到的边就是不可预见的变更事故），挂载环节决定它会不会被用（放在文档里没人看，挂在门禁上每次变更都必须正面回答）。其余差异（实时性、AI 集成、可视化、社区规模）都在下游，都是可以后期补的，而这两条补不上时，血缘平台会安静地变成一份没人维护的图。
