# 横切主题（Cross-cutting Lines）

> **一句话定位**：把"治理 / 观测 / 计量 / 演进"这 4 条横切线讲清楚，它们是数据架构师在所有 4 能力域都必须具备的"通用能力"。

> 本文是 data-travel 项目 [序章](../README.md) 的子章节（02-cross-cutting-lines），覆盖 **R3 数据建模** 能力领域中「跨域通用能力」的展开。

---

## 1. 概念与定位

### 1.1 是什么

**横切主题（Cross-cutting Lines）** 在数据架构语境下，特指**贯穿所有 4 能力域（基础 / AI 平台 / AI 应用 / 横切与软技能）都必须具备的通用能力**。它们不专属于某个能力域，但每个域都依赖它们。

> 注：在 [README](../../README.md) 中，"横线"与"能力域"并列为本书的二维结构。本章专门展开 4 条横线。

### 1.2 为什么需要

- **业务驱动力**：没有横切线 → 治理碎片化、监控缺失、成本失控、演进困难。
- **典型痛点**：某模块"性能很好但没有观测"，或"能上线但难以演进"——根因都是横切能力缺位。
- **AI 时代新诉求**：Agent 平台对横切能力要求更高——AI 决策必须可治理、可观测、可计量。

### 1.3 在 AI 时代数据架构中的位置

```
       4 横线（本章）
              ↓ 渗透到
       4 能力域（基础 / AI 平台 / AI 应用 / 横切与软技能）
              ↓ 落实在

```

### 1.4 演进历程

- **传统阶段（1990s–2010s）**：以 ITIL / COBIT 为主，4 横线雏形出现但未成体系。
- **大数据阶段（2010s–2020）**：Netflix SRE 推动可观测性；FinOps 推动可计量。
- **AI 原生阶段（2020+）**：Agent 决策的可解释性 → 推动可治理升级；模型监控 → 推动可观测升级。

## 2. 核心原理

### 2.1 关键概念定义

| 概念 | 定义 | 一句话解释 |
| --- | --- | --- |
| **横切关注点（Cross-cutting Concern）** | 跨多个模块共同需要的能力 | 横切 = 横向贯穿 |
| **可治理（Governable）** | 行为可被规则约束、可被审计 | AI Agent 决策可被白盒化 |
| **可观测（Observable）** | 内部状态可被外部测量 | SLO / Trace / Metric / Log |
| **可计量（Measurable / Cost-aware）** | 资源消耗可被量化、可被归因 | FinOps / Token 计费 |
| **可演进（Evolvable）** | 系统可平滑升级、可回滚 | API 兼容 / 灰度 / 抽象稳定 |
| **可重复（Reproducible）** | 同样输入产生同样输出 | 实验可重跑 / 结果可对齐 |
| **可观测性三大支柱** | Metrics / Logs / Traces | SRE 标准 |
| **技术债（Tech Debt）** | 为短期收益做的长期妥协 | 见 [Ch13.06](../13-decision/06-tech-debt/06-tech-debt.md) |
| **SLO** | Service Level Objective | 服务质量目标 |

### 2.2 数学 / 形式化基础

可治理性可被形式化为**规则覆盖率 R(c)**：
```
R(c) = (可被规则约束的决策数) / (总决策数) ∈ [0, 1]
```
R = 1 表示完全可治理；R = 0 表示完全黑盒。

可计量性可被形式化为**资源归因精度 A(r)**：
```
A(r) = 1 - H(r)/H_max
其中 H(r) = 资源消耗分布的熵，A(r) ∈ [0, 1]
```

### 2.3 关键算法 / 框架

- **可治理**：OPA (Open Policy Agent) / Apache Ranger / 数据分类分级
- **可观测**：OpenTelemetry / Prometheus / Grafana / Jaeger
- **可计量**：FinOps 基金会 / Kubecost / Cloudability
- **可演进**：Semantic Versioning / 蓝绿发布 / 灰度 / Feature Flag

### 2.4 与相邻概念的关系

| 相邻概念 | 与横切线的关系 |
| --- | --- |
| 4 能力域 | 横切线横穿 4 域 |

## 3. 设计模式与范式

### 3.1 主要模式

- **「治理嵌入平台」**：在数据平台层做治理，而非事后审计。
- **「观测左移」**：开发时就埋点，而非上线后补。
- **「成本可视化 + 归因」**：成本不只是账单，而是工程指标。
- **「演进 4 件套」**：版本化 / 抽象稳定 / 灰度 / 可回滚。

### 3.2 适用场景决策表

| 场景 | 推荐模式 |
| --- | --- |
| 创业期（0→1） | 治理先放后做，观测和计量必须从第一天起 |
| 成长期（1→10） | 治理补齐 + 成本精细化 |
| 规模期（10→100） | 演进能力是核心，灰度 / 抽象 / 兼容性是命脉 |
| 平台期 | 横切能力直接决定企业级竞争力 |

### 3.3 反模式与陷阱

- **「治理大而全」**：一次性引入完整治理平台 → 业务方抵触 → 落地失败。
- **「观测指标爆炸」**：1000+ 指标无人看 → 真正故障时找不到关键信号。
- **「成本大锅饭」**：按 BU 算总账 → 没人关心单次调用的成本。
- **「演进无版本」**：接口随意改 → 上下游适配成本爆炸。

## 4. 工程实现

### 4.1 落地步骤

1. **可治理**：先做最小治理（资源 Owner + 分类分级），再做完整治理（血缘 + 影响分析）。
2. **可观测**：从 Golden Signals（延迟 / 流量 / 错误 / 饱和度）开始，再扩到 4 个黄金指标 + 业务指标。
3. **可计量**：从「按服务计费」开始，再做「按调用计费」+「按业务价值计费」。
4. **可演进**：从 API 版本化开始，再做灰度 / 可回滚 / 抽象稳定。

### 4.2 关键技术点

- **数据血缘自动采集**：Apache Atlas / DataHub / LinkedIn 模式。
- **多维度 SLO**：可用性 SLO / 延迟 SLO / 正确性 SLO / 业务 SLO。
- **成本归因**：按服务 → 按调用 → 按业务 3 层归因。
- **抽象稳定性**：API 的「输入 / 输出 / 语义」稳定是核心。

### 4.3 工具链与平台

- 可治理：Apache Ranger / OPA / OpenMetadata
- 可观测：Prometheus / Grafana / Jaeger / OpenTelemetry
- 可计量：Kubecost / CloudHealth / Apache CloudStack
- 可演进：ArgoCD / Spinnaker / LaunchDarkly

### 4.4 代码 / 配置示例

```yaml
# observability.yaml — 4 横线的基础配置
governance:
  tool: apache-ranger
  policies: 3  # Owner / 分类分级 / 访问控制
  coverage: 0.85  # R(c) = 85%

observability:
  metrics: prometheus
  logs: loki
  traces: jaeger
  slos:
    availability: 99.95
    latency_p99_ms: 200

finops:
  tool: kubecost
  allocation: [service, team, business-line]
  monthly_budget_alert: 1.2  # 超出预算 20% 告警

evolution:
  versioning: semver
  canary: 10%  # 灰度 10%
  rollback: automatic-on-slo-breach
```

## 5. 前沿演进（AI 时代）

### 5.1 LLM / Agent 时代的演进方向

- **可治理 → AI 决策白盒化**：Agent 决策必须可解释、可审计、可回滚。
- **可观测 → 模型监控**：token 成本 / 延迟 / 准确率 / 幻觉率 / 安全违规率。
- **可计量 → Token 经济**：从「服务器计费」到「Token / 推理步 / Tool 调用」多维计费。
- **可演进 → Prompt 版本化**：Prompt 即代码，需要版本管理 / 灰度 / 回滚。

### 5.2 与 RAG / 向量库 / GraphRAG 的结合

- 治理：Agent 输出的事实性校验（防幻觉）。
- 观测：RAG 检索质量（召回率 / 准确率）作为新 SLO。
- 计量：向量库存储 / Embedding 调用成本。
- 演进：Embedding 模型升级的灰度策略。

### 5.3 学术与工业最新进展（2024-2025）

- **OPA + Rego + Gatekeeper**：K8s 时代事实标准的策略引擎。
- **OpenLLMetry**：OpenTelemetry 的 LLM 扩展。
- **Token 经济学 / FinOps for AI**：2024 Gartner Top Strategic Tech Trend。

### 5.4 未来 3-5 年趋势

- Agent 决策的可解释性成为监管刚需（EU AI Act、中国生成式 AI 管理办法）。
- 计量从「Token」到「Tool 调用 + 推理步 + 数据使用」综合成本。
- 演进从「API 版本化」到「模型版本化 + Prompt 版本化 + 数据版本化」三位一体。

## 6. 落地实践

### 6.1 真实案例

- **Netflix SRE**：可观测性 + 故障演练的全球标杆；4 个 Golden Signals 来源。
- **Google SRE Book**：定义 SLO / Error Budget / 故障复盘，是行业事实标准。
- **Uber 计费体系**：从「按服务」到「按行程 / 按城市 / 按业务」多维归因。
- **阿里 SRE / 字节 SRE**：国内大厂 SRE 实践 + 混沌工程。
- **蚂蚁 / 微众 / 平安 / 招行**：金融级可治理 + 监管报送。

### 6.2 踩坑与经验

- 观测指标定下后 3 个月内要持续 review，删掉没人看的指标。
- 成本归因要按「业务线」而非「资源」才有意义。
- 治理不要「一次性完美」，要「小步快跑 + 持续治理」。
- 演进路径必须有"向前兼容 + 向后兼容"策略，不能让"升级"成为高风险操作。

### 6.3 落地路径

- 0→1：先做可观测（最便宜），再做可计量（成本压力），再补可治理。
- 1→10：补齐 4 横线，引入 Apache Ranger / OpenTelemetry 等成熟方案。
- 10→100：自研横切能力平台，把治理 / 观测 / 计量 / 演进做成产品。

### 6.4 ROI 评估

- 可观测：故障定位时间从小时级降到分钟级，节省 70%。
- 可治理：合规审计成本降低 50%，数据事故减少 60%。
- 可计量：云资源浪费减少 20-40%。
- 可演进：版本升级导致的故障减少 50%。

## 7. 与其他方法对比

### 7.1 对比维度

| 维度 | 横切 4 线 | ITIL | COBIT | DevOps 三大支柱 |
| --- | --- | --- | --- | --- |
| 范围 | 数据 + AI 全栈 | IT 服务管理 | 信息技术治理 | 研发运维一体化 |

### 7.2 决策树

- 通用 IT 服务管理 → ITIL
- 治理 + 合规 → COBIT
- AI 时代数据 + Agent 平台 → 横切 4 线（本书方案）
- 研发效能 → DevOps 三大支柱

### 7.3 组合使用

- **ITIL + 横切 4 线**：IT 服务管理 + 数据 / AI 横切能力。
- **COBIT + 横切 4 线**：治理合规 + 技术横切能力。
- **DevOps + 横切 4 线**：研发效能 + 数据 / AI 横切能力。

### 8.2 分主题展开

#### 序.1 4 条横线（治理 / 观测 / 计量 / 演进）哪一条最容易被忽视？为什么？

**1. 考察点**：对横切线的整体理解 + 实际落地经验。

**2. 参考答案框架**
- 多数团队忽视「演进」→ 升级爆炸 / 技术债滚雪球。
- 多数 AI 团队忽视「可治理」→ Agent 黑盒决策无法审计。
- 不同行业侧重不同：金融重视治理，电商重视计量。

**3. 常见陷阱**：把「可观测」误认为「横切能力全部」。

**4. 追问预测**：4 横线如何排序实施？

**5. 参考资料**：Ch11 横切工程 / Ch13 技术债 / Netflix SRE / Google SRE Book。

---

#### 序.2 AI Agent 决策如何实现「可治理」？具体到技术层怎么做？

**1. 考察点**：是否理解 AI 时代治理的新形态。

**2. 参考答案框架**
- **白盒化**：决策日志（prompt / 检索结果 / 工具调用 / 输出）全留痕。
- **审计**：决策可回放、可解释。
- **白名单 / 黑名单**：危险操作必须人工审批。

**3. 常见陷阱**：把治理当成"事后日志"，不是"事中拦截"。

**4. 追问预测**：如果 Agent 调用了一个危险 API，如何撤销？

**5. 参考资料**：Ch8 AI 治理 / EU AI Act / OWASP Top 10 for LLM。

---

#### 序.3 如何在 AI 时代做「可计量」？Token 经济学和传统 FinOps 有什么差异？

**1. 考察点**：对 AI 计费模式的理解。

**2. 参考答案框架**
- 传统：按 CPU/内存/存储计费。
- AI：按 Token / Tool 调用 / 推理步 / Embedding / 向量存储 多维计费。
- 关键：按「业务价值」归因（每 1 元 token 换多少 GMV / 用户 / 收入）。

**3. 常见陷阱**：只看「总 token 花费」，不看「单位业务价值」。

**4. 追问预测**：如何定价 Agent 服务？

**5. 参考资料**：Ch11 数据成本 / 字节豆包计费 / OpenAI 定价 / Anthropic 定价。
