## 1. 概念与定位

### 1.1 是什么

**术语表（Glossary）** 是项目的「跨章节词典」：收录全书中反复出现、读者可能不熟悉、需要统一理解的核心术语。AI 时代项目尤其要扩充「智能体 / RAG / 向量数据库 / MCP / 等保」等新兴术语。

### 1.2 为什么需要

- **跨章节统一口径**：避免「数据湖」在不同章节指不同事物。
- **降低阅读门槛**：对不熟悉 LLM / Agent 的传统数据架构师，术语表是「词典」。
- **跨角色沟通**：架构师 / 工程师 / 产品 / 业务对同一术语的理解对齐。

### 1.3 在 AI 时代数据架构中的位置

```
       4 能力域（Ch1-Ch15）
              ↓ 引用
       术语表（本章，集中定义）
              ↓ 支撑
       跨角色 / 跨章节沟通
```

### 1.4 演进历程

- **传统数据术语**：ETL / ODS / DWD / DWS / ADS / SCD。
- **大数据术语**：Hadoop / Spark / Flink / Kafka / Iceberg。
- **AI 时代新增术语**：LLM / RAG / Agent / Vector DB / Embedding / MCP / Prompt / Token / Hallucination。

## 3. 设计与落地

### 3.1 使用方式

- **遇到不懂的术语**：在术语表搜索（Ctrl+F）。
- **跨章节同义**：每个术语在本书中含义一致，参见"本表"。

### 3.2 增补原则

- 新增术语必须出现在至少 1 个章节中。
- 缩写第一次出现时给出全称。
- AI 时代新增术语优先扩充（智能体 / RAG / MCP / 等保）。

**哪些登记进本表、哪些留在章节里**——上面三条是原则，下面这张表把它变成可照着判的场景（判据全部取自本文件与本章 README 的既有约定）：

| 场景 | 处置 | 依据 |
| --- | --- | --- |
| 同一术语跨章节反复出现 | **登记进本表**，并在章节内直接引用 | §3.3 反模式「每章重复定义」：定义在术语表，章节内直接引用 |
| 只在某一章内出现一次 | **留在该章正文**，不进本表 | 上面第 1 条原则的反面；README「术语表」一节只收跨章复用者 |
| 两章对同一术语的口径不一致 | **以本表为准**，回改那两章 | §4.1「跨章节新增术语时，先在本表登记」 |
| 与已有词条同义（只是换了个说法） | **合并进已有词条**，不新增行 | §6.3 的「1→10」阶段（定期 review 合并） |
| 含义模糊、给不出单一定义（「数据中台」「数字化转型」一类） | **不收录** | §3.3 反模式「使用模糊术语」 |
| 术语已被淘汰或改名 | **定期 review 时删除或改写**，并保留一次改名记录 | §4.1「每半年 review 一次，删除过时的、补充新的」 |

**这张表的读法**：不确定该不该收时，先问「它会不会在第二个章节里出现」——会的就登记，只在一处出现的留在原地。**把单章术语收进来，是本表最常见的膨胀方式**。

### 3.3 反模式

- **每章重复定义**：定义在术语表，章节内直接引用。
- **使用模糊术语**：「数据中台」「数字化转型」等含义不清的词，避免使用。

## 4. 工程实现

### 4.1 维护方式

- 在 `00-introduction/04-glossary/04-glossary.md` 集中维护。
- 跨章节新增术语时，先在本表登记。
- 每半年 review 一次，删除过时的、补充新的。

### 4.2 引用规范

```markdown
- 首次出现：完整中英文 + 缩写（如 "RAG（Retrieval-Augmented Generation）"）
- 后续出现：只用缩写
- 跨章节引用：「参见 [00/04 术语表](../04-glossary/04-glossary.md)」
```

### 4.3 检索

- 术语集中在本章正文（`00-introduction/04-glossary/04-glossary.md`），可直接全文搜索。
- Obsidian / VSCode 等编辑器的全文搜索。

### 4.4 代码 / 配置示例

本表的权威源是 [序章 README 的术语表](../README.md)（四列：术语 / 英文 / 简述 / 首次出现章节）。把它重编码成一张可机器校验的登记表，是为了让 §3.2 的三条增补原则变成**能跑出来的检查**——列名与人名就是校验入口：

```yaml
# glossary_registry.yaml — 术语登记表（节选自 README「术语表」一节，全文以该表为准）
# 校验规则（对应 §3.2，可写成 CI 检查）：
#   R1 owner 必须非空          → 未登记的术语等于没人负责
#   R2 first_chapter 必须解析得到真实章节 → 违反「必须出现在至少 1 个章节中」
#   R3 同名 term 不得出现两行   → 违反「跨章口径以本表为准」
terms:
  - term: 检索增强生成
    en: Retrieval-Augmented Generation (RAG)
    zh: 通过外部知识检索增强 LLM 生成质量的架构
    first_chapter: [Ch4]
    owner: Ch4 维护者
    review_due: "+6m"          # 对应 §4.1 的半年 review
  - term: 多模型编排
    en: Multi-Model Orchestration
    zh: 统一接入多模型，按成本/延迟/能力路由与组合
    first_chapter: [Ch6]
    owner: Ch6 维护者
    review_due: "+6m"
  - term: 语义层
    en: Semantic Layer
    zh: 指标定义与查询消费分离的一层；口径收敛为可被多消费端取用的对象
    first_chapter: [Ch1, Ch4]
    owner: Ch1 维护者
    review_due: "+6m"
```

**为什么用这份结构而不是再写一张表**：README 那张表是给人读的，登记表是给检查用的——`owner` 让「谁负责」成为必填项，`first_chapter` 让「出现在至少一个章节」成为可解析的引用（R2），`review_due` 让半年 review 有到期日而不是靠记忆。**三列里任何一列留空，§3.2 的原则就退化成一句口号。**

| 章节 | 与术语表的关系 |

| 00/01 能力地图 | 术语表是「通用语言」层 |
| 00/02 横切主题 | 横线名（治理 / 观测 / 计量 / 演进）是术语 |

| 99 趋势 | 未来新增术语来源 |

**这张表回答的是「本表在本章里是什么位置」，不回答「什么时候不该用它」**：本章之外，最常被拿来替代或升级术语表的相邻方法是本体建模、知识图谱与图数据推理（三条词条见[序章 README 的术语表](../README.md)）。下面三节照本章其它主题的同一槽位，把取舍边界与升级触发点补齐——**判据重编码自 Ch1「本体建模」§3（模式选择决策表与组合模式）与 §5.7（行动建议），以及 Ch4「混合检索」§3.2.2（多跳占比与语料变更的建图判据）；本节不引入新判据，逐条给出出处**。

### 7.1 对比维度

| 维度 | 术语表（本表） | 本体建模（RDF / OWL） | 知识图谱 | 图数据推理 |
| --- | --- | --- | --- | --- |
| 语义层次 | 词汇层：只统一「用哪个词」 | **schema / TBox**：类、属性与公理 | **instances / ABox**：实体-关系-属性三元组 | 在断言层上做路径、多跳与子图推断 |
| 机器能据此做什么 | 搜得到、口径一致；**无权拒绝坏数据** | 推出概念层的隐含事实（类型归属、子类包含）；违反约束的数据可被 SHACL 直接拒绝 | 查到实体间关系；**没有 schema 时只是一堆 RDF 节点** | 推出未显式存储的边，成本随遍历深度上升 |
| 标识与同一性 | 词条名（中英文 + 缩写），无全局标识 | 每个概念钉到公开 IRI；跨源同一性用等价公理（如 `owl:sameAs`）表达 | 节点由 IRI 标识 | 结论挂在被遍历的节点与边上，节点标识一变即失效 |
| 判错之后怎么回退 | 改一行词条，按 §4.2 重新指向引用方 | 撤一条公理，重新推理 | 删节点 / 边并重建索引 | 重跑推理 |
| 维护成本的主要项 | 每季度 0.5 人日量级【经验】（§6.4） | profile 选择 + 推理机 + SHACL 形状，三份资产 | 抽取、对齐、摘要的更新流水线 | 推理 profile 与实例规模共同决定 |

**这张表怎么读**：从第一列往右，每换一列问的都是同一个问题——**你要求机器替你判断到什么程度**。只要求「词一致」就停在第一列；要求「这条数据不合法、得挡住它」才进第二列（SHACL 拒收，本体在这一列推出的是概念层的类型归属与子类包含）；要求「实体间的关系查得到」才进第三列；要回答「未显式存储的边」才到第四列（多跳遍历，成本随深度上升）。表达力每上调一档，就必然用一档推理开销与运维面去换（同一条判据在[本体建模的六种模式](../../01-modeling/05-ontology-modeling/05-ontology-modeling-section-3-sec3.md)里已被展开成选型规则）。

### 7.2 决策树

- 只要求「同一术语在全书一个意思」→ **就用本表**，不建本体、不建图：本表的消费者是人，§4.4 的登记表已经是它的机器可校验形态。
- 已有数据字典或 Excel 词表，想让它跨团队、跨机器也用得上 → 先给每个概念钉一个公开 IRI（**术语表用 SKOS 表达，来源用命名图记录**），再谈推理；明确**不要自建顶层本体**，也不要以「以后要推理」为由推迟把术语登记起来（[本体建模 §5.7 的行动建议](../../01-modeling/05-ontology-modeling/05-ontology-modeling-section-5-ai.md)）。
- 需求从「找得到」升级为「校验得住」（要能拒绝坏数据）→ 才升到本体：SKOS 词表没有任何公理，这一步的触发点就是有人开始要求「这条数据不合法，得挡住」。
- 要回答「A 和 B 隔着几跳有什么关系」→ 才建图，**对照项是本表**：没走到这一步就沿用本表 + SKOS 词表（§7.3 第 1 条），不为「以后可能要多跳」提前建图；判定方法是先量「需要多跳的问题占比」与「语料日变更比例」，**语料每天大幅变更时先别建图**（同一判据见[混合检索](../../04-data-assetization/04-hybrid-search/04-hybrid-search-section-3-sec3.md)）。
- 已经在用一份 SKOS 词表 / 数据字典 / 数据目录的术语条目 → **不要用它替代本表**：词表是本表的机器消费形态，口径仍以本表为准（§7.3 第 1 条：词表改了而本表没改，就是 §3.3 的「每章重复定义」在术语资产内部重演）；两边不一致时改词表，不改章节里对本表的引用。

### 7.3 组合使用

- **术语表 + SKOS 词表**：本表的「术语 / 全称 / 简释」三列就是受控词表的人读形态，机器消费时用 SKOS 的 `broader` / `narrower` / `related` 表达层级与相关关系。两者**共用同一批词条**——词表改了而本表没改，就是 §3.3 的「每章重复定义」在术语资产内部重演。
- **术语表 + 本体 + SHACL**：三层职责不重叠——**SKOS 管「用哪个词」，OWL 管「什么关系成立」，SHACL 管「什么数据能进」**（[轻量化入口 + 强约束内核](../../01-modeling/05-ontology-modeling/05-ontology-modeling-section-3-sec3.md)）。本表是本体「自底向上」路线的起点：概念体系从业务术语表归纳而来，而不是先定顶层类再往下套。
- **术语表 + 知识图谱（§6.3 的「10→100」）**：术语图谱化就是把词条与词条之间的层级、相关关系落成一张可遍历的图（§5.4 的「自动化术语图谱」），把 §5.2 的「术语表向量化做 RAG」从「像」的召回补成「关系上相连」的召回——只靠向量，召回的是「像」的段落，召回不了「关系上相连」的实体（GraphRAG 的公开机制是「实体与关系抽取 + 社区摘要」【公开】，见[混合检索](../../04-data-assetization/04-hybrid-search/04-hybrid-search-section-3-sec3.md)）。本表在这一步仍是命名源：图上的节点类型名与关系名要能在本表查到，否则 §7.2 第 1 条「同一术语在全书一个意思」在图这一步就断了。

> 💡 **思考锚点**：翻你自己那份术语表，数出「只在一章出现过一次」的条目有几个——本节的增补原则要求「新增术语必须出现在至少 1 个章节中」、踩坑经验要求「只收跨章节反复出现的」；这些单次词条只在推高每季度 0.5 人日的维护成本，却分不到那 30% 的跨角色沟通收益，你会先砍哪一批？

### 8.2 分主题展开

#### 序.1 解释 Lakehouse / Lake House / Data Lake / Data Lakehouse 四个概念的关系。

**1. 考察点**：对数据架构核心术语的精确理解。

**2. 参考答案框架**
- **Data Lake**：原始数据湖（Hudi / Iceberg / Delta 之前的方案）。
- **Lake House / Data Lakehouse**：湖仓一体，融 OLAP 能力的数据湖。
- 关系：Lakehouse 是 Lake 的演进，统一了"存储 + 分析"两层。

**3. 常见陷阱**：把所有 lake 概念混为一谈。

**4. 追问预测**：Lakehouse 是否会被 Data Mesh 取代？

**5. 参考资料**：Ch1 / Ch3 湖仓一体章节 / Iceberg 官方文档。

---

#### 序.2 解释 RAG / Fine-tuning / Prompt Engineering 三者的关系与适用场景。

**1. 考察点**：对 AI 时代核心术语的精确理解。

**2. 参考答案框架**
- **Prompt Engineering**：用 prompt 调教模型，无需改模型。
- **RAG**：检索增强，模型不变，扩展上下文。
- **Fine-tuning**：微调模型权重。
- 选择：轻 → 重；成本低 → 高；可解释 → 不可解释。

**3. 常见陷阱**：以为 RAG 能替代所有 Fine-tuning。

**4. 追问预测**：何时该用 RAG，何时该 Fine-tuning？

**5. 参考资料**：Ch4 数据资产化 / Ch5 智能体平台 / Anthropic / OpenAI 文档。
