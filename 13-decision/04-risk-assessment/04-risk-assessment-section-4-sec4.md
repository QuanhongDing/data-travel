## 4. 工程实现

§3 回答的是「有哪几种方法、各自被什么约束逼出来、代价与失效点在哪」；本节回答另一个问题：**在一个已经有若干在跑的系统、若干次历史事故、若干条没人认领的隐患的组织里，按什么顺序把这套东西装进去，每一步做完手上应该多出什么，以及怎么知道某一步其实没做成。**

组织方式：§4.1 给七个步骤与每步的判据；§4.2 给机制与失效条件；§4.3 给工具选型判据；**§4.4 是本节的重心**——存量改造；§4.5 给可直接套用的模板；§4.6 给自检清单。

**本文件主要写给存量改造的读者**，因为这是本主题下绝大多数人真实的处境：不是「从零建一套风险管理体系」，而是「已经有系统在跑、已经有事故发生过，要让评估从一次性活动变成机制」。从零搭建的读者可以把 §4.1 的 Step 1–3 当作最小集先启动，其余步骤按组织规模逐步补，模板直接取 §4.5。两类读者在 §4.4 会合——差别只在于存量读者的「历史条目」需要先做一次分类与挂账。

### 4.1 落地步骤

**Step 1：识别范围与边界（【经验】1–2 天，随评估对象数量变化）**

- 写清评估对象是哪一个（一个系统 / 一个项目 / 一次决策），不要写「我们的数据平台」；范围写得越像口号，后面越无法收敛。
- 写清时间范围（未来 3 个月 / 1 年 / 3 年），因为它决定哪些风险进清单：3 个月的窗口里，供应商更换这类风险不会兑现。
- 划定边界维度（技术 / 业务 / 合规 / 声誉），并明确**哪几维本次不做**。
- **产物**：一页纸的评估范围说明，含对象、时间窗、覆盖维度、**显式排除的维度**。
- **判据**：把这一页拿给没参与的人看，他能否说出「这次评估不回答什么问题」。说不出排除项的，说明边界没划，后面必然出现「这也该算风险」的争论。
- **为什么必须这一步、为什么在最前**：评估的产出量由范围决定；范围不封口时，条目数会持续增长且无法宣布结束，最终评估会在「还没列完」的状态下被放弃。

**Step 2：建立风险分类法（【经验】1–3 天，随对象类型数与分类维度数变化）**

- 按类型分类（技术 / 业务 / 合规 / 安全 / 运营 / 财务 / 声誉 / 战略），每一类给出**可识别的判据**，而不是只有一个类名。
- 按层次分类（组件 / 子系统 / 系统 / 系统之系统），用于控制 FMEA 的粒度——枚举到哪一层由它决定。
- 按时间分类（实施期 / 上线期 / 运行期），用于把风险分配到对应的执行环节。
- **产物**：一份分类表，每个类别带一句判据与一个正例、一个反例。
- **判据**：拿最近一年的 10 起事故去套这张表——落在表外的比例是多少？超过三成【经验】说明分类与你的现实不符，先改表再继续。
- **为什么必须这一步、为什么在识别之前**：分类法是条目能跨轮次累积的唯一机制。省掉它，第二轮评估无法把新条目与旧条目合并，归档复用失效，同一类风险会年复一年被重新发现、重新讨论。

**Step 3：风险识别（多源）（【经验】1–2 周，随参与人数与历史资产量变化）**

- 多源并用，不要只靠一种：头脑风暴（5–10 人、1–2 小时【经验】，人多于 10 人时发言集中度反而上升）、历史事故复盘（Postmortem 库）、行业基准清单（OWASP Top 10、CWE、STRIDE 六类威胁）、架构评审与合规 Checklist、AI 辅助（把系统描述与历史风险库给模型，让它补未识别项）。
- 每一源都要留下**原始记录**（谁提的、依据是什么），否则后续定级时无法追溯。
- 对每一源单独统计「新增了多少条」，用于判断哪一源在你的组织里是有效的。
- **产物**：一份候选风险池，每条带来源标记；以及一张「各来源新增条目数」统计。
- **判据**：抽查 5 条候选，问「这是从哪一源来的、依据是什么」。答不出来的条目要么补依据，要么移入「待观察」而不是直接进评估。
- **为什么必须这一步、为什么在分类法之后**：分类法是识别的检索索引——没有它，头脑风暴的产出取决于在场的人当天想起了什么，覆盖度随人选波动。

**Step 4：风险分析（量化 + 定性）（【经验】1–2 周，随条目数与是否需要蒙特卡洛模拟变化）**

- 先做半定量定级：概率 1–5，影响 1–5 且**按维度分列**（技术 / 业务 / 合规 / 声誉）。
- 需要跨条目排序时走 P × I 的**档位映射**（见 §4.5 模板 2），不写成乘积分数；为什么序数不能相乘见 [§3.2.4](04-risk-assessment-section-3-sec3.md)，这里只落流程动作——工作表里不留乘积列，评审判级时看到乘积即打回。
- 对组件可枚举的系统做 FMEA 并算 RPN（Severity × Occurrence × Detection，各 1–10）；对顶层后果明确的关键链路做 FTA，产出最小割集。**RPN 的三连乘不违反上一条**：它是 FMEA 方法自身定义好的排序键，产物只有一个用途——在同一张工作表内排出先后；`P × I` 没有这样一个被方法定义过的排序键，写成乘积就成了一道没人定义过的自定义分数。两者的共同纪律是：**都只用于排序，都不跨系统做绝对比较**。
- 只在**有可辩护的先验**时才上 Monte Carlo 或贝叶斯推理；没有先验时它们输出的是伪精确。
- **产物**：一张带 P、I、影响面、依据来源的定级表。
- **判据**：抽 3 行问「这个 P 是排出来的还是测出来的」；答不出依据来源的行不是评估结果。另外看档位分布——某一档占比超过一半即为同分泛滥，排序失效。
- **为什么必须这一步、为什么必须在识别之后**：定级是**排序动作**，它的输入必须是已经收敛的条目集。条目还在增长时定级会反复重做，而重复劳动会让参与者退出。

**Step 5：风险应对（【经验】2–5 天，随处置条目数与是否需要跨部门协调变化）**

- 四象限分流：避免（Avoid，改设计绕开）/ 转移（Transfer，保险、外包、多供应商）/ 缓解（Mitigate，加控制）/ 接受（Accept，**显式记录理由**）。
- 每条分配具体到人的 Owner、截止日期与预算；写团队名等于没有 Owner。
- 按性质再分流一次：可日常改造的进改造计划；高影响低概率的转为**预案与演练**，不要塞进日常改造（手段与风险性质不匹配、成本极高）。
- **产物**：一张带处置策略、Owner、截止日期、预算的处置表，以及一份「显式接受」清单。
- **判据**：抽 5 条问 Owner 本人「这条你打算做什么、什么时候做完」。答不上来或答成「我们一起推」的，说明这条没有 Owner。
- **为什么必须这一步、为什么在定级之后**：处置资源是有限的，没有定级的处置表会按提出者的职级而不是按风险量级分配预算。

**Step 6：风险监控（持续）**

- 为每条进入「缓解」的风险写 KRI（Key Risk Indicator），并把它接到已有监控上（Grafana + Prometheus 一类），阈值触发告警。
- 设两级复评：常规季度评审 + 重大变更时的即时评审（架构改造、供应商更换、监管口径变化）。
- 监控对象是**风险的驱动量**而不是风险本身：磁盘增长速率可监控，「磁盘写满」不可监控。
- **产物**：KRI 与风险条目的对应表，以及一份复评日历。
- **判据**：任取一条已缓解的风险，问「它的 KRI 今天读数是几、告警规则在哪」。答不出来的那一条实际上没有被监控，只是被处理过。
- **为什么必须这一步、为什么在处置之后**：处置动作的效果会随系统变更衰减（三个月前生效的熔断今天可能已被一次配置变更改掉），监控是唯一能发现这种衰减的机制。

**Step 7：复盘与持续改进（持续）**

- 每次事故后更新登记册：新风险入库、已发生的条目补充实测数据（用真实频率替换当初的序数猜测）。
- 季度 / 半年做一次方法自身的复盘：哪一源识别率在下降、哪一类总在同分泛滥、哪一步总被跳过。
- 把上一年清单作为下一年评估的**输入**，做增量而不是从零开始。
- **产物**：更新后的登记册 + 一份「方法自身的问题清单」。
- **判据**：对比连续两轮的条目产生方式——本轮有多少条是从上一轮清单里增量更新的？如果接近零，说明每轮都在从零开始，归档没起作用。
- **为什么必须这一步、为什么在最后**：实测数据只能来自事故与运行，它是对序数打分唯一的校准来源；没有它，第二年仍会得到同样一批「中风险」。

**最常被跳过的是 Step 2（分类法）。** 原因是它没有直接产出「一条风险」，看起来像准备工作。它的缺席不会在第一次评估暴露——第一次评估甚至会更顺（不用为分类争论）。症状在**第二次评估时**出现：新条目与旧条目无法合并，同一类风险被重新发现一次，参与者发现自己去年写的东西今年又写了一遍。第二个受害者是 Step 7 的归档复用，因为归档的键就是分类。

### 4.2 关键技术点

**固定分类穷举（让覆盖不随人波动）**

- **做法**：对已知对象类型选一套固定分类逐项排查——安全威胁用 STRIDE 六类，应用漏洞用 OWASP Top 10 与 CWE，架构评审用组织自己的 Checklist；每一类必须逐项过一遍并把「不适用」的理由写下来。
- **机制**：本节装进组织的是「分类变成评审表里的固定行、理由变成必填栏」这一步——每一项分类占一行，连「不适用」也要填一句理由。此后漏项不再以「没人想到」的形态存在，而是以某一行的空栏、或一栏敷衍理由的形态留在评审当场，主持人当场就能反问；逐行覆盖本身为什么有效见 [§3.2.1](04-risk-assessment-section-3-sec3.md)。代价落在评审带宽上：行数随分类粒度增长，一旦超过一轮能认真讨论的条数，必填栏反过来会逼出敷衍的填写。
- **失效条件**：**当分类条目数远超一轮评审能认真讨论的条数时**，逐项排查会反转成逐项抄写。观测信号：抽一个已归档季度的 FMEA 工作表，看 S / O / D 三列的取值分布是不是接近一个常数，同时看「不适用」的理由栏是不是空的——两件事同时出现即可判定。产出这样一张表比留白更危险：留白会让人继续排查，填满的表会让人以为排查已经做过。
- **档位**：【公开】STRIDE 六类威胁通常归于微软 Kohnfelder & Garg 1999 年的工作（可按微软官方威胁建模文档核验）；【公开】OWASP Top 10 for LLM Applications 首版发布于 2023 年，其 2025 版发布于 2024-11（版本名与发布年份不一致，引用时需同时写清，可按 OWASP 官方项目页核验）。

**条目状态机与「验证后关闭」**

- **做法**：登记册每条含稳定 ID、影响面、触发条件、Owner（具体到人）、处置策略、**验证方式**、状态（open / treating / verified / closed / accepted）与最后评审时间；把「关闭必须带非空验证方式」写成结构约束（见 §3.2.5 的 DDL），而不是流程约定。
- **机制**：因为约束挂在登记册这个**载具**上而不是挂在评审流程上，所以纪律对新加入的成员是可继承的——后来的人不必理解设计理由，也一样会被挡住。代价在另一头：它只能保证「这一格有值」，**复核那一环必须由组织另行承接**，否则形式合规的条目会一路关到年底。
- **失效条件**：**当关闭动作没有第二个人复核时**（提交人自己就能把条目推到 closed），条目会以「已通知相关方」这类字样穿过约束，形成形式闭环。它没有运行期信号——不会告警、不会报错，唯一可预期的发现时点是下一次事故的责任追溯。所以要在流程里写死两件事：关闭前由非提交人核对「验证方式里有没有一个可重放的动作」；核对落空时把条目退回 treating，而不是当场补一句理由。
- **档位**：【经验】判定动作沿用 §3.2.5 的「能不能重放」一问，本节新增的是执行配置：每轮由非提交人复核，抽查比例取已关闭条目的两成上下【经验：随合规压力与历史落空率调整】。

**序数纪律：P 与 I 不做乘法**

- **做法**：用档位映射表（§4.5 模板 2）承载 P 与 I，把每一档「代表什么」写进流程文件（I = 3 对应哪一档用户量或资金量）。序数纪律本身（为什么不写 `P × I`）见 [§3.2.4](04-risk-assessment-section-3-sec3.md)。**这条约束的只是 1–5 档的序数打分**；写成 `P × I` 的那一类走的是真实概率——`EMV = P × I`（主文件 §2.2）用的是 0–1 的概率与货币化影响，量纲不同，两者不要排进同一张表，也不要用前者的纪律去否定后者。
- **机制**：因为档位边界是一次写死、逐轮复用的配置，所以「本轮的 P=4 与上季度的 P=4 指同一件事」由配置保证，而不是由参与者的记忆保证——跨轮次可比是这条唯一的产出。反过来，边界若留在各团队自己的说明里，第二轮的分档会悄悄漂移，而漂移不报任何错。
- **失效条件**：**当某一档的占比连续两轮超过一半时**，排序的输入已经退化成常数，处置预算会按条数摊开。它是本主题里少数几个不用等事故就能发现的失效，但要有人主动去看：把最近一轮的档位分布与过去两个季度实际投入处置人力最多的条目并排摆一次，两列的前几名对不上，即已失效。此时的正确动作是换定级人——把定级权交给承担损失的一方（[§3.5](04-risk-assessment-section-3-sec3.md)「过度风险厌恶」一行给的就是这个修法），本节补充的是它必须发生的时间：在下一次季度复评之前，否则新的分布会带着旧口径固化下来。档位再细分而不换定级人，分布仍会压在同一档上。
- **档位**：【经验】判定动作：导出最近一轮的 P、I 两列看取值分布，占比最高的一档占多少，再查工作表里有没有乘积列。两个动作都要拿**最新一轮**的导出做——用上一轮的会把已经修好的失效重新报一次。

**影响面量纲统一**

- **做法**：每条风险必须写出影响面，且量纲在同一组织内统一（影响多少用户 / 哪条链路 / 哪个口径 / 多少资金），而不是「影响较大」。
- **机制**：因为定级的两个维度里 P 是序数、不可测，所以「可比较」这件事只能由 I 承载；量纲统一后，I 才有跨条目可比性，排序才立得住。代价是填表工作量上升，且部分风险确实说不出量纲（此时应显式写「量纲未知」而不是编一个）。
- **失效条件**：**当影响面只写技术维度时**（可用性、延迟），量纲之外的那部分不会以「缺失」的形态出现，而是以「有值」的形态出现——表上每一格都填得满满的，被漏掉的那一维却没有一列能容纳它。症状：技术团队评出的「中风险」在业务侧造成重大损失，而评估表毫无预警。修法是让业务方进到定级环节（理由见 [§3.5](04-risk-assessment-section-3-sec3.md)「单一视角」一行），而不是把技术列做得更细。
- **档位**：【经验】

**KRI 与阈值触发**

- **做法**：为每类风险选一个**可采集的驱动量**（磁盘增长速率、变更频率、依赖方数量、未修漏洞数），设两级阈值（预警 / 行动），接到已有监控与告警通道上。
- **机制**：因为监控的是驱动量而不是结果事件，所以它能在风险兑现**之前**给出信号——「磁盘写满」不可监控，但它的增长速率可以。代价是每个 KRI 都要有人负责校准阈值，阈值定得松等于没有告警、定得紧等于告警疲劳。
- **失效条件**：**当 KRI 与条目没有对应关系时**（监控一堆指标但说不清对应哪条风险），告警会被忽略。症状：事故发生后回看监控，指标早就异常过，但没人知道那条曲线该由谁看。
- **档位**：【经验】判定方法：任取一条已缓解风险，问它的 KRI 读数与告警规则在哪。

**前移：以数据流图为输入的威胁建模**

- **做法**：在**设计阶段**而不是实现之后，用数据流图（数据从哪来、经谁处理、落到哪、谁能读）作为输入跑一遍固定分类排查；产出进入登记册并绑定到该设计的评审门禁。
- **机制**：因为发现时机决定了修复成本——设计期改一张架构图与上线后改一条数据链路，代价相差数量级——所以前移本身就是收益，与用哪种方法无关。代价是设计期信息不全，部分条目只能给出「待定」并需要有后续触发点，否则「待定」会永远趴在清单里。
- **失效条件**：**当设计期输入还是口述而不是图时**，前移退化成一次没有输入可查的评审会。症状：评审结论无法复现（第二次评审得出不同结论），且事后没人能说清当初排查过什么。修法：把「有没有数据流图」当成进入评审的前置条件。
- **档位**：【经验】

**风险按性质分流 + 显式接受**

- **做法**：把条目分成「可日常改造」与「高影响低概率、只能做预案与演练」两条路；对不处置的条目走显式接受（Accept），写明理由、批准人与复评日期。
- **机制**：因为处置手段必须与风险性质匹配——把区域级故障塞进日常改造，成本极高且几乎无法验证——所以分流决定了预算花得值不值。而显式接受解决的是另一个问题：「未处理」与「决定不做」在清单上必须可区分，否则复盘时分不清是遗漏还是决策。代价是接受清单需要有人定期复核，否则它会变成忽略的遮羞布。
- **失效条件**：**当接受清单没有复评日期时**，被接受的风险会永久沉默。症状：事故复盘时发现该风险三年前就被识别过、也被「接受」过，但没有任何人记得这个决定。
- **档位**：【经验】

### 4.3 工具链与平台

判据一列写的是**你能在自家组织里当场核对的约束**（有没有人能填、能不能接上现有流程、结论给谁看），不是成熟度标签。产品名仅在确定存在时列出；能力与版本命名以官方文档当前版本为准。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| FMEA 工作表 | Isograph FMEA / ReliaSoft / 鱼骨图（Ishikawa）工具 / 通用表格（Jira、Confluence 模板） | 判据是「团队能不能在一轮评审里认真过完的行数」——行数超出讨论带宽时，换工具没有用，该收窄枚举范围 | 直接上重型可靠性工程套件：填表成本上升，条目反而变少且更少被真正讨论 |
| FTA 逻辑树 | Isograph FaultTree+ / OpenFTA / 通用绘图工具 | 判据是「有没有明确且唯一的顶层事件」——没有它，先做枚举（FMEA）打底 | 用绘图工具硬画逻辑门：图能画出来，但「哪些叶子组合足以导致顶层事件」算不出来 |
| Bowtie 图 | BowTieXP / 通用绘图工具 | 判据是「要不要向非技术方解释控制今天还在不在」——要，则必须逐道屏障写 Owner 与检测手段 | 用纯因果图代替：预防与缓解两笔预算分不开，屏障是否真在拦也问不出来 |
| 风险登记册（载具） | ServiceNow GRC / Archer（原 RSA Archer）/ Riskonnect / SAP GRC / LogicGate Risk Cloud / Jira Risk Register 插件 / Confluence Risk Register 模板 | 判据是「关闭是否需要验证方式、状态机能不能自定义」——不能，则该载具承接不了闭环，只能当清单 | 先买 GRC 平台再定条目结构：平台固化了一套不适配的状态机，团队为迁就工具而改流程 |
| 热力图与可视化 | Tableau / Power BI | 判据是「输出给谁看」——给管理层看趋势用固定看板，给自己排序用表格 | 只有看板没有条目表：颜色好看但无法回答「谁在什么时候把它关掉」 |
| KRI 监控 | Grafana + Prometheus（或等价时序库 + 告警） | 判据是「KRI 能不能接到已有告警通道」——接不上就会产生第二个没人看的面板 | 单独建一套告警：值班只看一个通道，另一套里的异常等于没发生 |
| 概率与依赖推理 | @RISK / Oracle Crystal Ball / Python（numpy、scipy、pymc3）/ pgmpy / pybnlearn / R（mc2d、triangle） | 判据是「有没有可辩护的先验」——没有先验时，这些库只会把假设输出成两位小数 | 没有先验时上蒙特卡洛：结论看起来精确，输入是编的，读者无法从输出反推 |
| 混沌工程 | Chaos Monkey（Netflix）/ Gremlin / ChaosBlade（阿里）/ LitmusChaos（CNCF）/ Chaos Mesh（PingCAP）/ Azure Chaos Studio | 判据是「动作是否可回滚、爆炸半径能否界定」——涉及写数据、对外发送、删除的场景不适用 | 用评审替代实验：护栏静默失效发现不了，因为评审只能看配置不能看实况 |
| AI/ML 风险与公平性评估 | IBM AI Fairness 360 / Google Model Card Toolkit / Hugging Face Evaluate / Arize AI / WhyLabs / Microsoft Responsible AI Dashboard | 判据是「有没有先写出可接受的输出区间与度量口径」——没有口径时，工具产出的图无法判定 | 直接上工具做分数：指标有了但没有判定标准，出一批图之后没人知道该不该上线 |
| 数据与 AI 风险的统一治理 | Microsoft Purview / Databricks Unity Catalog | 判据是「你和数据资产是否已在同一个 catalog 里」——已在此生态内才选它，跨生态会因为元数据不同源而失效 | 单独建一套风险台账：与资产的真实变更脱节，台账三个月后过期 |
| 合规与风险自动化 | Vanta / Drata | 判据是「合规举证是不是主要痛点」——是，则它省的是证据收集时间而不是分析时间 | 把它当风险评估工具用：它给的是合规状态，不是风险排序 |
| 开发者体验与风险指标 | Atlassian Compass | 判据是「服务是否已在 Atlassian 生态里登记」——不是，则先解决服务登记再谈指标 | 服务未登记就上指标：指标口径与实际系统对不上，只能当参考 |
| AI 风险框架 | NIST AI RMF 及其生成式 AI 专题文件，以及 NIST 官方页面上配套的映射/说明材料 | 判据是「是否需要对外举证」——要，则选流程型框架（可写进制度、可被审计引用、不绑定厂商） | 用厂商自带的评估清单替代框架：术语随厂商版本变，跨年度的结论无法比较 |
| LLM 辅助识别 | 通用大模型 API + 自建提示模板（把系统描述与历史风险库作为输入） | 判据是「产出是否有人逐条复核」——没有复核环节时，它产出的是看起来合理的新风险，无法进入定级 | 把模型输出直接灌进登记册：条目膨胀、无法归因来源，登记册的可信度被稀释 |

这一类里**最容易被误选的是「风险登记册」这一格**：团队先采购一套 GRC 平台，再回头设计条目结构。误选的后果不是钱花了，而是**流程为迁就工具而改**——平台固化的状态机里没有「验证方式」这一列，于是团队把闭环要求降级成流程约定，而这正是 §3.5 里「走过场」反模式的起点。第二常见的误选是把合规自动化工具（Vanta / Drata 一类）当风险评估工具用：它们解决的是「证据收集」，不是「该先修什么」。

### 4.4 存量迁移

存量改造的起点不是一张空白清单，而是：一批在跑的系统、一堆历史事故报告、若干份没人再打开的风险评估文档。这一节的核心是**先拿收益、再分类挂账、最后才谈统一**。

**第一件事：只读回溯，先看清自己的存量（【经验】1–2 周，随事故报告数量与可回溯的时间跨度变化）**

把最近 12 个月【经验，按你的事故量调整】的事故报告按 Step 2 的分类法回溯套一遍。这件事不需要改任何系统、不需要任何人配合，产物是三个数：**落在分类外的比例**、**同类事故重复出现的次数**、**事故是否早已被某份文档识别过**。

这三个数决定了后面的投入方向：分类外比例高，说明分类法要先改；同类事故重复出现，说明缺的不是识别而是闭环；早已被识别过的比例高，说明文档不缺、缺挂载点。

**第二件事：存量系统分三类，分别处理**

| 存量类型 | 判据（怎么认出来） | 处理方式 |
| --- | --- | --- |
| 核心链路 | 有 SLA、影响资金或大量用户、下游不可改 | 完整 FMEA + 关键链路 FTA；进入发布门禁（变更前自动跑影响分析） |
| 一般系统 | 有 Owner、有监控、无对外 SLA | 只挂 KRI 与应急预案，**不做完整枚举**；但必须显式写出「本系统未做完整枚举」 |
| 无人认领 / 未知 | 找不出 Owner，或接管人说不清它做什么 | 进「盲区清单」打标挂账，由架构评审周期性地消化；不要为了填满清单先给它编一个 Owner |

**历史条目怎么处理**：把旧评估文档里的条目一次性导入登记册，但只保留两类——仍然 open 且可行动的，以及被显式接受但**没有复评日期**的（这类要重新补日期或重新决策）。已经处理且当初没有留验证方式的条目，按「未验证」重新打开；**一次性补验证方式**比让它们以「已完成」的状态继续存在更便宜——因为复盘时分辨「真做了」与「写了做了」的成本，远高于此刻重跑一次验证。

**第三件事：双轨怎么维持、维持多久**

双轨不是「新旧两套评估方法」，而是**新旧两种承接方式并行**：

- 新评估一律进登记册（条目 + 状态机 + 验证关闭），旧文档转为只读归档；
- 登记册是唯一权威，文档只读——**因为双轨期最大的风险不是流程不统一，而是同一件事有两个出处**，一旦两处不一致，实操中会习惯性地引用对自己有利的那一份；
- 维持期按【经验】给两到三个评估周期，随复评频率变化：复评越稀，双轨拖得越久，而拖得越久，旧文档被习惯性引用的次数越多。

**第四件事：什么信号说明可以退出双轨**

两个信号同时成立即可退出：① 连续两个评估周期内，新发生的事故都落在已有条目或已有分类里；② 关闭条目的平均停留时长在下降（不是条目数在下降——条目数下降可能只是因为没人往上写）。只满足第二条时会退得太早：分类还没收敛，下一轮事故又会落在表外。

Kafka Broker,磁盘满,生产停滞,8,日志未清理,4,3,96,监控告警+自动扩容+日志TTL,@张三

**怎么用**：一行是一条**失效模式**，不是一行一个组件。S / O / D 三列是评审人给出的序数判断（各 1–10），不是实测值——它能排序，不能被证伪，所以这张表是**教学示例**，分值不要照抄，要按你自家系统的历史频率重打。RPN 列由三者相乘得出，仅用于排序，不要拿去做跨系统的绝对比较。

**模板 2：概率影响矩阵（5×5）**

| | I=1 | I=2 | I=3 | I=4 | I=5 |
| --- | --- | --- | --- | --- | --- |
| P=5 | 中 | 高 | 高 | **极高** | **极高** |
| P=4 | 中 | 中 | 高 | 高 | **极高** |
| P=3 | 低 | 中 | 中 | 高 | 高 |
| P=2 | 低 | 低 | 中 | 中 | 高 |
| P=1 | 极低 | 低 | 低 | 中 | 中 |

**怎么用**：把 I 的 1–5 各自代表什么写死在流程文件里（例如按受影响用户量或资金量分档），否则两个团队的「P=4」会差一个量级。取到的值是**档位**，不是分数——不要写作 `P × I`。

**模板 3：故障树（FTA）**

```text
[数据平台宕机] — Top Event
    │
    ├── OR ──→ [Kafka 不可用]
    │              ├── OR ──→ [Broker 进程崩溃]
    │              │              └── AND ──→ [内存溢出] × [无健康检查]
    │              └── OR ──→ [ZooKeeper 脑裂]
    │
    ├── OR ──→ [数据库不可用]
    │              ├── OR ──→ [主库宕机]
    │              └── OR ──→ [主从延迟过大]
    │
    └── OR ──→ [网络分区]
                   ├── OR ──→ [专线故障]
                   └── OR ──→ [DNS 污染]
```

**怎么用**：先写清顶层事件，再往下推——顶层事件含糊时，这棵树会推成一堆并列的担心。**产出不是这张图，是最小割集**（哪些叶子的组合足以导致顶层事件）；画完不割集，等于只得到一张好看的图。每个叶子必须是可观测事件，不可观测的叶子只能是假设，不能进割集。

**模板 4：Bowtie 分析**

```text
Threats                        Top Event                  Consequences
[数据中心火灾]──→[预防]──→│                          ├──→[缓解]──→[业务损失]
[网络攻击]──────→[防火墙]→│[数据平台宕机]            ├──→[缓解]──→[客户投诉]
[人为误操作]───→[审批]──→│                          ├──→[缓解]──→[声誉损害]
                                                       └──→[缓解]──→[合规处罚]
```

**怎么用**：这张图的元素是自然语言级的，不承载概率——**不要拿它排序**。它的用法是逐道屏障追问「谁负责、怎么测」，图上每道屏障都必须落到一个 Owner 与一个检测手段上，落不到的那道等于画在图上。

**模板 5：蒙特卡洛模拟（Python）**

```python
import numpy as np

# 分布参数必须来自你自己的历史事故频率与损失记录，不要照抄
rng = np.random.default_rng(42)

# 每季度故障次数（泊松），每次故障影响金额（对数正态）
faults_per_quarter = rng.poisson(lam=2, size=10_000)
impact_per_fault = rng.lognormal(mean=2.0, sigma=1.0, size=10_000)

# 年度总影响 = 4 个季度 × 单次影响
annual_impact = faults_per_quarter * 4 * impact_per_fault

for p in (50, 90, 99):
    print(f"年度总影响 P{p}: {np.percentile(annual_impact, p):.2f}")
```

**怎么用**：`lam` 与 `lognormal` 的两个参数必须换成你自家的历史数据（或用三点估计转成的分布）；**没换之前，这段代码输出的是演示值，不是评估结论**。结论用 P50 / P90 这类分位表达而不是单一期望值——不可逆决策看的是尾部。

**模板 6：AI RMF 评估表**

| 类别 | 问题 | 评分 | 风险等级 | 缓解 |
| --- | --- | --- | --- | --- |
| Valid and Reliable | 模型准确率 / 稳健性 | 4/5 | 中 | 持续监控 |
| Safe | 输出是否有害 | 5/5 | 低 | 内容审核 |

| Privacy-Enhanced | 数据隐私 | 4/5 | 低 | 差分隐私 |
| Fair with Harmful Bias Managed | 公平性 | 3/5 | 高 | 偏见检测 + 缓解 |

**怎么用**：类别名取自 NIST AI RMF 的七项可信 AI 特性【公开】（NIST AI 100-1，2023-01 发布；其生成式 AI 专题文件 NIST AI 600-1 于 2024-07 另发——两份不是同一年，引用时要分别写清），**请以 NIST 官方页面当前发布的清单核验类别名**，不要按二手材料转抄。评分是评审人给出的示例值，必须配上「多少分算可上线」的口径，否则这张表只产出图不产出决策。表里两处最容易串：SHAP / LIME 给的是**归因**——只能回答「哪些输入影响了这一次输出」，回答不了「谁对这次决策负责」；后者靠上一行的决策日志与责任人登记，两行不要互相顶替。

**模板 7：AI 辅助风险识别（Python）**

```python
import anthropic
import os

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

def identify_risks(system_description: str, prior_risks: list[str]) -> str:
    """基于系统描述 + 历史风险，让模型推荐候选风险（需人工逐条复核）。"""
    prompt = f"""你是一名资深数据架构师，专注风险评估。

## 系统描述
{system_description}

## 历史风险（来自登记册）
{chr(10).join(f"- {r}" for r in prior_risks)}

请基于 FMEA 与 Bowtie 两种方法，推荐 10 条**尚未识别**的风险。
每条包含：风险描述、概率(1-5)、影响(1-5)、影响面（哪条链路 / 多少用户）、
应对策略、Owner 建议、以及你判断它的依据（引用上面哪一段描述）。
无法从输入判断的，写「依据不足」而不是给一个分值。
按 P 与 I 映射到的档位降序排列（映射规则见 §4.5 模板 2；不要输出乘积）。输出 Markdown 表格。"""

    msg = client.messages.create(
        model=os.environ.get("RISK_MODEL", "claude-sonnet-4-5"),
        max_tokens=3000,
        messages=[{"role": "user", "content": prompt}],
    )
    return msg.content[0].text
```

**怎么用**：这段代码的产物是**候选池**，不是登记册条目——它的输出必须经人工逐条复核后才入册，且每条要补上「依据」。提示里要求「依据不足就写依据不足」是刻意的：**不给模型留出编造确定性的口子**。模型名与 SDK 接口随版本变化，请按你所装 SDK 的官方文档核验。

### 4.6 自检清单

- [ ] 抽 5 条风险条目，问「这个 P 是排出来的还是测出来的」——答不出依据来源的有几条？再看档位分布：占比最高的一档占多少？超过一半【经验】说明排序输入已退化成常数。
- [ ] 「显式接受」的条目有没有一条有复评日期？一条都没有说明接受等于遗忘。
- [ ] 上一年的事故有多少落在「核心链路 / 一般系统 / 盲区清单」这三类之外？落在表外的比例是多少？本轮的条目里又有多少是从上一轮清单增量更新的（接近零说明归档没起作用）？
- [ ] 设计态的判定不在本节重复：影响面写法、owner 是否具体到人、同源风险是否合并、FMEA 的 detection 空行、FTA 叶子是否可观测、Bowtie 屏障有无 Owner、有没有出现乘积写法——照 [§3.7](04-risk-assessment-section-3-sec3.md) 的清单过一遍即可，本节只留下面这些必须动过系统才有答案的项。
- [ ] Step 顺序：翻出最近一轮的归档，看分类表（Step 2）的版本时间是否**早于**候选风险池（Step 3）的产生时间。分类表若是事后补的，第一批条目就是按旧类目归的档，第二轮合并时会对不上号。
- [ ] 存量分类：抽 3 个被定为「一般系统」的对象，它们的评估记录里有没有写明「本系统未做完整枚举」？没写明的，后续会被当成已完整评估的系统引用。
- [ ] 盲区清单：清单里有多少条已经挂满两个架构评审周期还找不到 Owner？挂账超过两个周期的逐条重新决策（补 Owner / 显式接受 / 关闭）【经验：周期数随架构评审频率调整】。
- [ ] 双轨退出：连续两个评估周期内新发生的事故，是否都落在已有条目或已有分类里？同时看关闭条目的平均停留时长有没有下降——只满足后者会退得太早。
- [ ] KRI：任取一条已缓解的风险，问它的 KRI 今天读数是多少、告警规则配在哪、最近一次触发是什么时候。答不出来的那一条实际上只是被处理过。
- [ ] 数据流图：最近一次设计阶段的威胁建模，能不能当场翻出作为输入的那张数据流图？翻不出的，这次评审的结论不可复现。
- [ ] 挂载点：最近一次评估的结论挂在哪个执行环节（发布门禁 / 变更流程 / 值班交接）？再抽一次真实变更，看门禁有没有真的拦下过东西——一次都没拦过，说明挂载点只是名义上的。

### 4.7 小结

> 本节小结：整套流程里唯一决定成败的环节是**结论的挂载点——条目是否「验证通过才允许关闭」**。因为识别、定级、可视化这些环节的质量差异，最多让结论好一点或差一点；而挂载点决定的是这份评估**会不会被执行**：只写进文档的结论，除了写它的人没人会再翻开；进了登记册状态机的结论，每一轮复评都要交代它推进到了哪一步；挂上发布门禁的结论，改一次代码就得先正面回答碰不碰它。这也是为什么 §4.2 里那些看起来最"技术"的条目（状态机、序数纪律、影响面量纲）都指向同一件事：把评估的产出变成**可被追问、可被判定的东西**。
>
> 存量改造的读者请把注意力放在 §4.4 的「只读回溯」上——用三个数（分类外比例、同类事故重复次数、早被识别过的比例）决定投入方向，比先买工具再设计流程便宜一个数量级。
>
