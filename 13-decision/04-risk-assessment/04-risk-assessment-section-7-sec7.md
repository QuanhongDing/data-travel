## 7. 与其他方法对比

### 7.1 先立判据：为什么「系统化 5 分 / 复杂度 3 分」这类表会误导

打分表把「方法能产出什么」与「方法在哪个环节生效」混为一谈。FMEA 的系统化程度在任何场景都是满分，但在「大促前两周、已进入封板」这个时间窗内它的可用性接近零：它的产出是一份清单，而封板期没有执行入口。反过来，一个只写了 20 条的 Checklist 如果挂在发布流程上，它对当期事故的约束力可能强于一份 300 条的 FMEA 表。**分数衡量的是方法本身的完备性，而决定效果的往往是它挂在哪里。**

打分表的第二个问题更隐蔽：它把**可证伪性差异**压成了同一个刻度。FMEA 的 S/O/D 是序数打分——两轮评审给出不同分值，无法判定谁对；分级放量给出的是实测值——换一次实验就能复现或推翻。把这两类东西放进「量化程度」这同一列来比高低，等于抹掉了它们唯一的实质差别：**一个能在预算会上被追问，一个不能。**

第三个问题在 AI 时代变得致命：打分表假设所有方法面对的是同一类对象。FMEA 的严重度、故障树的顶层事件、P×I 里的「影响」，全都围绕**系统可用性**定义——组件坏了、链路断了。而模型没有「坏」这个状态，它只是输出分布漂移（[§5.2.1](04-risk-assessment-section-5-ai.md)）。于是「系统化 5 分」的方法在 AI 系统上可能一列都填不满。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 枚举机制 | 它靠什么保证「不漏」：固定分类逐项排查、从顶层事件反推，还是靠人临场想 | 覆盖是否随参与者经验波动，决定了结论能不能被复核；固定分类的边界就是方法的边界 |
| 数字来源 | 分值是主观排序、分布假设，还是实测 | 决定这个数字能否用于排序、预算与举证；序数打分在条目全体同分时会整体失效 |
| 挂载点 | 产出的东西挂在哪：文档、条目状态机，还是变更门禁 | 决定它是一次性活动还是持续机制；同一份分析挂错位置，效果差一个量级 |
| 人力成本 | 一轮要多少人时、多久复评一次 | 决定方法能否存活：成本高于收益的方法会退化成照模板填，而填表比不做更糟（给出错误的信心） |
| 可举证性 | 能否逐条回答「排查了什么、缓解了什么、残留风险是什么」 | 决定它能否用于对外合规与客户审计，也决定了事故复盘能否落到具体条目 |
| 与被评估对象的匹配 | 它的前提（动作可回滚、状态是二值的、组件可枚举）在你的系统上是否成立 | 前提不成立时方法论整体失效——用「组件是否会坏」去问一个输出分布问题，问不出答案 |

判据之外还有一条前提，它不属于选型范畴但决定选型是否有效：**这个方法必须至少挂在一个执行环节上**。挂不上执行环节的分析，无论多完备，都只产出「我们知道自己挡不住」。

最后要说清本章的比较对象：这 19 个候选里只有少数是「产品」，其余是**做法与组织机制**——打分表最容易犯的错，正是把它们当成同一类东西来比强弱。它们真正的差异在于信息如何被结构化、数字如何产生、结论挂在哪个环节；这几件事都不随组织规模自动变好，但都会随「有没有一个执行环节」而立刻改变效果。

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型场景 | 出处 / 定位 |
| --- | --- | --- | --- | --- |
| 临时评估 | 基线做法 | 靠参与者记忆与直觉列举，无固定分类 | 一次性讨论、无历史事故可参考 | 无正式出处，作为对照基线 |
| Checklist（核对清单） | 最低成本的结构化 | 固定条目逐项打勾，不分析原因 | 上线前核查、合规逐项确认 | 通用工程实践 |
| FMEA | 组件级正向枚举 | 逐组件列失效模式 → 影响 / 原因 / 检测 → 排序 | 硬件、基础设施、中等规模系统 | 通常归于军方与航天工程 |
| FTA（故障树） | 顶层事件反向演绎 | 从「不希望事件」反推，用 AND / OR 门连接底层原因 | 关键系统可靠性、事故根因分析 | 通常归于 1960 年代贝尔实验室的工作 |
| Bowtie（领结分析） | 双向屏障建模 | 核心事件居中，左侧威胁 × 预防屏障，右侧后果 × 缓解屏障 | 安全 / 环境 / 运营的跨团队沟通 | 通常归于 1970 年代末油气行业 |
| HAZOP | 引导词驱动的偏差分析 | 用固定引导词对工艺参数逐项问「偏离会怎样」 | 流程工业、连续生产系统 | 通常归于 1960 年代化工行业 |
| P-I Matrix（概率影响矩阵） | 二维半定量定级 | 把 P × I 映射到红黄绿，用于汇报与分档 | 项目组合管理、季度回顾 | 通用风险管理实践 |
| Risk Register + Heatmap | **载具**而非分析方法 | 条目化 + 状态机 + 热力图，让风险可跟踪可复用 | 组织级持续治理 | 通用风险管理实践 |
| Bayesian Network | 条件概率推理 | 用条件概率建模风险之间的依赖，并随证据更新 | 复杂依赖系统（金融、AI 安全） | 通用概率方法 |
| Monte Carlo Simulation | 分布传播 | 对输入分布采样，输出 P50 / P90 等分位 | 工期、成本、容量规划 | 通常归于 1940 年代曼哈顿计划的工作 |
| Markov Chain | 状态转移建模 | 用状态之间的转移概率描述长期风险 | 可修复系统的可靠性建模 | 通用概率方法 |
| Scenario Analysis + Stress Test | 场景构造 | 构造基线 / 乐观 / 悲观 / 黑天鹅场景并评估系统表现 | 战略决策、容量规划 | 通用实践 |
| Chaos Engineering | 主动注入验证 | 在生产或类生产环境注入故障，验证护栏是否真的生效 | 分布式系统的韧性验证 | 与 Netflix 的公开实践相关 |
| 分级放量实测（灰度即风险度量） | **把变更本身当实验** | 按 1% → 10% → 50% → 100% 逐级放量，每级记录影响面指标的变化幅度，得到「每 1% 流量的单位风险」 | 变更密集、风险等级靠主观判断的系统 | 见 [§6](04-risk-assessment-section-6-sec6.md) 记录的字节变更风险度量实践 |
| CRQ / FAIR | 货币化量化 | 把频率与损失分布相乘，输出年化损失分布 | 安全预算与投入排序 | 网络安全量化领域 |
| Real Options Analysis | 决策灵活性估值 | 把「可推迟 / 可放弃」当作期权来估值 | 战略投资与架构演进节奏 | 金融方法移植 |
| Resilience Engineering | 能力评估 | 评估系统的吸收 / 恢复 / 适应能力，而非单点失效 | 业务连续性、关键系统 | 安全科学领域 |
| AI RMF | 面向 AI 系统的框架 | 以 Govern / Map / Measure / Manage 四个功能把 AI 风险纳入流程 | AI 系统治理与合规 | 机构发布的公开框架 |
| LLM 辅助 FMEA / AI 风险监测 | 用模型改写「识别」与「定级」环节 | 生成候选失效模式 + 基于异常的监测 | 条目规模大、人力受限的场景 | 厂商与论文材料为主 |

这 19 个候选分 5 族：**枚举族**（临时评估 / Checklist / FMEA / HAZOP / LLM 辅助 FMEA·AI 风险监测）、**演绎族**（FTA / Bowtie）、**量化族**（P-I Matrix / Monte Carlo / Bayesian / Markov / CRQ·FAIR / Real Options）、**验证族**（Scenario Analysis + Stress Test / Chaos Engineering / 分级放量实测 / Resilience Engineering）、**载具族**（Risk Register + Heatmap / AI RMF）。分族依据不是「强弱」，而是**它们各自回答的问题**：枚举族回答「可能出什么事」（临时评估是其中最弱的一档——它同样在「枚举」，但靠人临场想，没有固定分类），演绎族回答「什么组合会致命」，量化族回答「多大概率、多少钱」，验证族回答「护栏今天还在不在、每放一级流量的实际影响是多少」，载具族回答「结论挂到哪、谁来跟」。AI 风险监测这类做法跨在两族之间：它既生成候选条目（枚举），也持续观察异常（验证），本章按「它主要产出什么」归入枚举族。

分族最重要的推论是：**载具族与其余四族正交**。任何分析方法都可以挂进 Risk Register，也都可以不挂——挂与不挂的差别，比在枚举族内部换一种方法大得多。[§6](04-risk-assessment-section-6-sec6.md) 的四个案例里，真正拉开差距的不是用了 FMEA 还是故障树，而是条目化、验证后关闭与显式接受这三件载具层面的事。

读这张表的方式：**「核心机制」一列是唯一可比较的列**，其余列只是定位辅助。同一个机制描述出现在多行时（例如 FMEA 与 HAZOP 都是固定分类逐项排查），说明它们在本文的判据体系里是同类，二者的差别应当用你所在行业的既有规范去决定（流程工业有 HAZOP 的现成引导词与班组习惯），而不是继续在方法论维度上比较——那属于选品，不属于选型。

### 7.3 机制差异：为什么它们表现不同（核心节）

下面 4 个机制维度回答同一件事：**这个差异由什么机制导致，因此必然导出什么性质，代价是什么**。这四个维度里有三个（枚举、数字来源、挂载点）在多个候选上是叠加的：一套可行方法通常是「枚举打底 + 量化补数字 + 载具承接」，而不是二选一；第四个（屏障）只在需要向跨团队解释控制时才被单独用到。

#### 7.3.1 枚举机制：靠什么保证「不漏」

**机制是什么**：保证不漏只有三种机制——**固定分类逐项排查**（FMEA 的失效模式清单、HAZOP 的引导词、按固定类别的威胁清单）、**从顶层事件反推**（FTA 的逻辑门）、以及**靠人临场想**（临时评估）。

**它在各候选中的实现差异**：

| 机制 | 代表方法 | 覆盖由什么决定 | 结构性漏掉的形态 |
| --- | --- | --- | --- |
| 固定分类逐项排查 | Checklist / FMEA / HAZOP / 固定类别威胁清单 | 分类的宽度 × 排查的彻底程度 | 分类边界之外的失效模式一律漏掉 |
| 从顶层事件反推 | FTA / Bowtie | 顶层事件定义得对不对 + 建树者的系统理解 | 未被设想为「顶层事件」的那类后果 |
| 靠人临场想 | 临时评估 | 在座者的经验集合 | 在场所有人都不曾经历过的那类失效 |

**由此必然导出的性质**：因为固定分类把「想不想得到」换成「有没有逐项过一遍」，**所以覆盖不随参与者经验波动**——**代价是分类的边界就是方法的边界**，且成本随分类宽度线性上升（成本 ∝ 组件数 × 每组件耗时）。这也是「一次评审能认真讨论的条目数」成为硬约束的原因：分类越细，越容易退化成照模板填。

因为 FTA 从「不希望事件」反推并用 AND / OR 门连接，**所以它能表达「两个原因同时成立才导致故障」这类组合关系**，而正向清单式的方法表达不了——**代价是树必须由理解系统结构的人构造**，构造质量不可批量复制，换一个人重建会得到结构不同的树，两轮结论无法直接比较。

因为正向枚举以「组件」为单位组织，**所以它天然覆盖「每个组件会怎么坏」，也天然不覆盖「组件之间的交互会怎么坏」**——而后者正是分布式系统里发生频率最高、复盘最难的一类失效。要补上它，得向反推型方法（或向实战验证族）购买。

**公开证据**：【公开】FMEA 的做法通常归于美国军方 1949 年发布的 MIL-P-1629 文件，后发展为 MIL-STD-1629 系列（可按文件编号自行检索核验）；【公开】跨信任边界排查威胁的固定分类方法，通常归于微软 1999 年前后的工作，其公开安全文档以数据流图 + 固定类别为排查输入（可按 Microsoft 官方安全文档核验）。此处一律写「通常归于」——这类方法的归属年份在不同资料间存在出入，拿不准就不要写死。

**失效条件**：当组件数远超「一轮能认真过的条目数」时，固定分类的人力成本会把方法本身压垮；此时正确的做法不是换更细的分类，而是先把分类收窄到最贵的那几类组件，其余靠运行监控兜住。

**判定方法**：把上一年的事故逐起对照分类表——如果事故都落在分类表已覆盖的格子里，说明分类够用，缺的是闭环；如果有一半落在表外，说明该换机制（补分类或改用反推），而不是把现有的格子填得更细。

#### 7.3.2 数字从哪来：序数打分、分布假设，还是实测

**机制是什么**：FMEA 的 S / O / D、P-I 矩阵的 P 与 I，取值来自人的判断（序数）；Monte Carlo 与贝叶斯网络的输入是概率分布；分级放量、混沌注入这类做法产出的是**实测值**。这三类数字的可证伪性完全不同，而它们的名字常常长得一样（都叫「概率」或「风险等级」）。

**它在各候选中的实现差异**：

| 数字来源 | 需要的前置 | 输出形态 | 能否被证伪 |
| --- | --- | --- | --- |
| 序数打分 | 只要有人（专家即可） | 可排序的名次 | 不能：两轮评审给出不同分值，无法判定谁对 |
| 频率 / 分布假设 | 历史频率或可辩护的分布假设 | P50 / P90、年化损失分布 | 部分：假设错则结论错，且错得看不出来 |
| 实测（放量 / 注入） | 动作可放量、可回滚，且有观测口径 | 单位风险（每 1% 流量对应的指标波动） | 能：换一次实验即可复现或推翻 |

**由此必然导出的性质**：因为序数打分只要求比较、不要求测量，**所以它能在几乎任何场景下产出「可排序」的结果**——**代价是它无法被证伪**，而且当所有条目被赋成同一个值时排序立刻失效；这正是 [§6](04-risk-assessment-section-6-sec6.md) 里反复出现的「清单上全是高风险」。

因为 Monte Carlo 把输入写成分布、输出写成分位数，**所以它能回答「超期概率是多少」这类真正用于决策的问题**——**代价是输出精度不高于输入假设的精度**：一个没有依据的三角分布会产出一个看起来很专业的 P90，而它和小数点一起给人虚假的确定感。

因为分级放量产出的是实测的单位风险，**所以它能跨变更同台比较**（不同变更的「每 1% 流量影响多少」是可比的）——**代价是它必须真的放量**，对不可逆动作（写数据、对外发送、删除）无法使用，而这类动作在自动执行系统里只会越来越多。

**公开证据**：【公开】NIST AI RMF 1.0（NIST AI 100-1，2023-01）与其生成式 AI 专题文件 NIST AI 600-1（2024-07）把 Measure 单列为一项功能，公开文本要求先写清度量口径再谈管理（可按 NIST 官方发布页核验）；【公开】OWASP Top 10 for LLM Applications 首版发布于 2023 年，其后续版本于 2024-11 发布（可按 OWASP 官网核验）——它把提示注入列在首位，原因不是它最好防，而是它最缺通用解法。判定方法：拿到一张风险表后，逐行问「这个数字是排出来的还是测出来的」；答不出依据来源的行，不是评估结果，只是一段文字。

**失效条件**：在没有任何历史频率可估的场景（模型漂移、0→1 项目、供应商变更）里，频率类量化退化为「看起来精确的假设」；此时更诚实的写法是给出触发条件与可接受区间，而不是一个分值。

#### 7.3.3 屏障与两侧：Bowtie 建模的是控制，不是原因

**机制是什么**：FTA 建模**原因**（什么组合会导致顶层事件），Bowtie 建模**控制**（哪些屏障在阻止它、哪些屏障在止损）。两者常被当成同一种图，差别在建模对象，而这个差别决定了产出交给谁。

**它在各候选中的实现差异**：

| 方法 | 建模对象 | 图上的主要元素 | 产出交给谁 |
| --- | --- | --- | --- |
| FTA | 原因 | 逻辑门 + 底层事件 | 分析与评审（找根因） |
| Bowtie | 控制 | 威胁 / 预防屏障 / 核心事件 / 缓解屏障 / 后果 | 跨团队沟通与运营（查屏障） |
| FMEA | 组件失效 | 组件 × 影响 × 原因 × 检测 | 工程改进清单（逐条修） |

**由此必然导出的性质**：因为 Bowtie 把预防与缓解分成两侧，**所以「投在预防上的钱」与「投在止损上的钱」第一次可以被分开讨论**——**代价是它对中间事件的分解粒度不足**，复杂系统的级联仍要靠 FTA 补，这也是两者在实践里成对出现的原因。

因为 Bowtie 的元素（威胁、屏障、后果）是自然语言级的，**所以它天然是跨团队沟通格式**——**代价是它为了可读性放弃了量化能力**：图上不承载概率计算，硬要拿它排序只能得出伪精确的结论。判定方法：看这张图有没有数值列；有数值列而没有来源，就说明它被当成了量化工具。

因为屏障是可以枚举、可以指派责任人的（每道屏障有 Owner、有检测手段），**所以 Bowtie 的输出是一份「这套控制今天是否还在」的检查清单**——**代价是屏障清单会随分析轮次膨胀**，无人维护的屏障清单会反过来提供虚假的安全感：图上有屏障，实际上没人测过它。

**公开证据**：Bowtie 的行业起源通常归于 1970 年代末油气行业（壳牌等）的使用，并在 1988 年 Piper Alpha 事故后获得更广泛采用【公开：可按关键词 bowtie analysis 的公开历史材料自行检索核验；本节不引用任何「降低了多少事故率」式的效果数字，这类数字在不同材料里的口径互不可比】。

**失效条件**：当失效路径不是一个核心事件而是多点并发（部分失败、级联超时、依赖抖动）时，单中心图会让读者以为存在单一故障点，把注意力放错位置。

**判定方法**：数一数图上的屏障里，有多少道有明确的检测手段与负责人。只有名字没有检测手段的屏障，在事故当天是不会起作用的——它的存在只影响这张图好不好看。

#### 7.3.4 挂载点：产出挂在文档、条目，还是门禁上

**机制是什么**：同一份分析结论，挂在文档里等于没人看；挂进条目状态机等于可跟踪；挂在发布门禁上等于每次变更都必须正面回答。挂载点不改变分析质量，但决定分析有没有效果。

**它在各候选中的实现差异**：

| 挂载点 | 什么时候被读到 | 典型失效方式 | 需要的额外东西 |
| --- | --- | --- | --- |
| 文档 / 汇报材料 | 评审会上 | 会后无人跟进，同一风险反复出现 | 无（也正因如此最省事） |
| 条目状态机（Risk Register） | 每次评估与跟踪时 | 条目长期停在「处理中」，没人关闭 | Owner、状态定义、关闭前的验证方式 |
| 变更门禁（CI / 发布流程） | 每次变更时 | 粒度不够导致过度阻断，最终被例外流程绕过 | 影响面能自动算、阈值有依据 |

**由此必然导出的性质**：因为门禁在执行路径上，**所以它不依赖「人主动去看」**——**代价是门禁的误判直接落到交付速度上**：只做表级影响面的门禁会把「改一个字段」当成「改整张表」来处理，阻断过多之后团队会走例外流程，门禁形同不存在。

因为 Risk Register 把风险变成有状态的条目，**所以「改完就算解决」这类失效可以被看见**（没有验证方式就无法关闭条目）——**代价是它要求有人维护状态**：一个没有 Owner 的登记册会退化成一张过期列表，而过期的风险条目比没有条目更危险，因为它给出错误的信心。

因为 AI RMF 用四个功能（Govern / Map / Measure / Manage）定义流程，**所以它适合挂到组织流程上，且不绑定任何厂商**——**代价是它不提供检测手段**：把它整套搬进一个没有强合规要求的组织，管理成本可能高于它带来的风险下降；可行的最小用法是先落 Map 与 Measure（写清场景与度量口径），随合规要求再补其余两格。

**公开证据**：【公开】NIST AI RMF 1.0（NIST AI 100-1，2023-01）与 NIST AI 600-1（2024-07）；【公开】ISO/IEC 23894:2023（AI 风险管理指南，2023 年发布）。两者都是公开的正式发布文本，术语与功能划分跨版本稳定（可按各发布机构页面核验）。ISO 31000 的现行版本号与发布年份请以 ISO 官方网站为准——不同资料对其版本沿革的记述并不一致。

**失效条件**：当判据无法被自动判定时（例如「这个设计好不好」），门禁无法实现，只能退回评审；此时载具选择退化为条目化的登记册，效果取决于条目质量而非流程强度。

**判定方法**：随机抽一条已关闭的风险条目，问三个问题——它当时的验证方式是什么、验证结果记录在哪里、如果今天重放验证它还会通过吗。三问答不全，说明关闭动作是「改完即关」而不是「验证后关」。

### 7.4 成本结构对比（不是价格表，是成本函数）

```
单轮评估成本 ≈ 人力单价 × [ 组件数 × 每组件耗时（枚举）
                          + 专家时数（建树 / 建模 / 场景构造）
                          + 采样次数 × 单次模型评估（量化）
                          + 注入实验的期望损失（验证） ]
             + 持续跟踪成本（∝ 未闭环条目数 × 复评频率）
```

| 族 | 主导成本项 | 隐性成本（不在工时表上） |
| --- | --- | --- |
| 枚举族 | 组件数 × 每组件耗时（纯人力） | 分类的维护成本：系统变了而分类没变——过期的分类比没有分类更危险 |
| 演绎族 | 专家时数（建树 / 建模，门槛高） | 换人重建得到不同的树，两轮结论不可比；知识集中在个人身上 |
| 量化族 | 取得数据与可辩护假设的成本 | 伪精确：没有依据的分布会产出看起来很专业的 P90，并在预算会上被当真 |
| 验证族 | 注入实验的期望损失 + 环境成本 | 在生产注入可能引发真实事故；演练环境与生产不一致会使结论不可迁移 |
| 载具族 | 条目维护（∝ 未闭环条目数） | 形式主义填表成本；无 Owner 的条目给出错误信心 |

两项【推算】示例，用来判断「钱花在哪」：

- **FMEA 的人力**【推算】：按 [§3.2.1](04-risk-assessment-section-3-sec3.md) 给出的「每个组件 30–60 分钟」、100 个组件推算 = **50–100 人时/轮**（单个分析者）；若两人交叉复核则 100–200 人时/轮；按每季度复评一轮推算，年化约 **400–800 人时**。推导链：组件数 × 单组件耗时 × 复核人数 × 轮次。这条推算的用途不是预算，而是判断方法的适用规模：组件数再涨一个量级时，年化人力会进入「需要专职团队」的区间。
- **验证的期望损失**【推算】：混沌注入的期望损失 ≈ 注入频次 × 单次故障的业务损失 × 未被护栏兜住的概率。这是**结构式而非数值式**——三个因子都要用你自己系统的数据填；如果一个都填不出来，说明演练的爆炸半径与停机预算都还没有定义，此时先不要在生产做注入。

【经验】当一轮评估的条目数超过几十条后，跟踪成本会超过分析成本：催办、复核、验证、关闭的人力开始超过识别本身。这正是「条目必须有 Owner 与验证方式」的经济学理由——不是因为管理学要求，而是因为**没有关闭机制的条目会永久占用跟踪成本**。

评估频率本身也是一项成本变量：复评越勤，单轮可投入的深度越浅；越稀，条目过期的概率越高。可行的做法是按风险性质分层——会影响业务的条目按季度复评，其余按年度，并在结构变化（架构改造、供应商更换、监管变化）时触发一次增量复评，而不是整体加密频率。

### 7.5 决策树（我该用哪一套）

```
[① 被评估对象是「二值状态」还是「连续分布」？]
   │
   ├─ 连续分布（模型输出、生成质量） → AI RMF 打底（先只落 Map + Measure）
   │                                   + 分布监控与可接受区间
   │
   └─ 二值状态 → [② 失效路径是否需要表达「多因同时成立」？]
                  │
                  ├─ 需要 → FTA（建树）+ Bowtie（把屏障讲给跨团队听）
                  │
                  └─ 不需要 → FMEA / Checklist（固定分类逐项排查）
                              │
                  [③ 是否需要可比较的数字（用于排序、预算、容量）？]
                              │
                              ├─ 不需要（只需分出先后） → P-I Matrix + Risk Register
                              │
                              └─ 需要 → [④ 数字能否由实测产出？]
                                          │
                                          ├─ 能放量且可回滚 → 分级放量实测（灰度即风险度量）
                                          │
                                          ├─ 不能放量但可注入故障 → Chaos Engineering / Stress Test
                                          │      （产出是「哪里会穿」与护栏清单，不是精确数值）
                                          │
                                          └─ 两者都不能（不可逆动作 / 无实验环境）
                                                 → Monte Carlo / Bayesian，且必须显式写出分布假设
                              │
                  [⑤ 结论要挂在哪个环节？]
                              │
                              ├─ 汇报与分档 → P-I Matrix + Heatmap
                              ├─ 持续跟踪 → Risk Register（条目 + Owner + 状态机）
                              └─ 变更门禁 → 影响面分析进 CI / 发布流程（超阈值阻断）
                              │
                  [⑥ 是否需要对外举证？]
                              │
                              ├─ 需要 → 固定分类 + 逐条记录（可追溯「排查了什么、残留什么」）
                              └─ 不需要 → 轻量条目即可，优先保证条目被关闭
```

**阈值依据**（与树上 ①–⑥ 一一对应）：

- **① 二值状态还是连续分布**：依据来自机制——旧方法的严重度与「影响」都定义在可用性上，而模型类故障的表现是输出分布漂移、没有「坏」这个状态（[§5.2.1](04-risk-assessment-section-5-ai.md)）。判定方法：能否写出「什么样的输出算不可接受」的可接受区间；写不出，说明对象是分布而不是开关。
- **② 是否需要表达「多因同时成立」**：依据来自 §7.3.1——正向清单以组件为单位组织，天然表达不了组合关系，而组合失效在分布式系统里最常见。判定方法：过去一年的事故里，有多少起需要两个以上原因同时成立才发生；这个比例明显高于零，就需要一张树。
- **③ 是否需要可比较的数字**：依据来自 §7.3.2——序数打分能排序但不可证伪，频率与实测能用于预算与容量。判定方法：这个数字的下游用途是「决定先做哪个」（序数够用）还是「决定拨多少钱 / 买多少容量」（需要频率或实测）。
- **④ 数字能否由实测产出**：依据来自动作的可逆性——可放量与可回滚是实测的前提；不可逆动作（写数据、对外发送、删除）没有回滚窗口，用实验去测它等于把风险当成成本。判定方法：问「如果这一级放量真的失败了，能不能在受控时间内回到上一级」；答不出「怎么回」，就落到分布假设分支，并显式写出假设。
- **⑤ 结论挂在哪个环节**：依据来自 §7.3.4——挂载点决定效果量级，而门禁需要「可自动判定的判据 + 有依据的阈值」，条目需要「Owner + 验证方式」，两者所需的前置不同。判定方法：这个结论下一次会在什么时刻被自动读到；答不出时刻，说明它挂在文档上。
- **⑥ 是否需要对外举证**：依据来自可举证性这条判据——逐条记录的成本（保留排查与缓解痕迹）只有在需要向监管或客户举证时才有对价。判定方法：是否有人（外部或内部审计）会要求你证明「这个系统做过风险评估」。

这 6 个节点不是并列的勾选项，而是有先后：① 决定用哪一类方法体系，② 在枚举族与演绎族之间分流，③④ 决定数字的来源，⑤⑥ 决定结论挂到哪、留多少痕迹。任一条答错，后面的选择都在错误前提上优化——最常见的误判是跳过 ③④ 直接讨论「FMEA 还是故障树」，结果换了一套更精细的分析格式，而产出的数字仍然不可证伪。

反向用法同样有用：**当有人主张「我们该上一套风险评估体系」时，用 ⑤⑥ 去问**——这份结论下一次会在什么时刻被自动读到？谁会要求你出示它？两个问题都答不出，说明当前缺的不是方法，而是一个执行环节；此时应当先找到环节（例如把它接进发布流程或季度复盘），再选方法。

### 7.6 选型矩阵与组合

| 你的处境 | 最该用 | 最该避免 | 理由 |
| --- | --- | --- | --- |
| 单系统 / 单组件、组件可枚举 | FMEA（固定分类）+ Risk Register | 直接上故障树 | 组合失效还不是主要形态，建树成本换不回首轮收益 |
| 关键基础设施、依赖链复杂 | FTA + Bowtie | 只用 FMEA | 正向清单表达不了「多因同时成立」，也讲不清屏障 |
| 高层汇报、项目组合排序 | P-I Matrix + Risk Register | 把矩阵分值当测量值 | 序数打分可排序但不可证伪，当成测量值会误导预算决策 |
| 变更密集、风险等级靠主观判断 | 分级放量实测 + 统一影响面量纲 | 继续用「高 / 中 / 低」定级 | 分散度高的地方需要可比较的量，而不是形容词 |
| 验证护栏是否真的生效 | Chaos Engineering / Stress Test | 用纸面分析替代演练 | 纸面推不出「护栏今天还在不在」 |
| AI / ML 系统 | AI RMF（先落 Map + Measure）+ 分布监控 | 直接套用 FMEA 的严重度定义 | 对象是输出分布，不是「组件是否会坏」 |
| 需要对外合规举证 | 固定分类穷举 + 逐条记录 | 只留结论不留痕迹 | 举证要的是「排查过程与残留风险」，不是一份评级 |
| 条目多、人力受限 | LLM 辅助召回 + 专家定级 | 把定级交给模型 | 召回可以高召回低精确；定级要能说出依据来源 |
| 高影响低概率风险（区域级故障、供应商消失） | 转为预案与演练，并显式记录「已接受」 | 混进日常改造清单 | 手段要与风险性质匹配：用日常改造去应对区域级故障，成本极高且不解决 |
| 评估结论无人跟进 | 先补 Owner 与验证方式，再谈方法升级 | 先换一套更精细的方法 | 缺的是关闭机制而不是分析机制；换方法不会带来闭环 |

组合不是「都装上」，每一件都要有明确职责边界（下面 6 条组合要点，一项未删，补齐每条的分工与运维代价）：

- **FMEA + Risk Register**：FMEA 负责识别（组件 × 失效模式 × 原因 × 检测），Register 负责跟踪（Owner、状态、验证方式）。职责边界是「发现」与「关闭」分属两个动作；运维代价是两边的字段必须能对齐，否则识别出的条目会在登记册里丢掉。
- **FTA + Bowtie**：FTA 分析根因链（回答「怎么来的」），Bowtie 做可视化与沟通（回答「哪道屏障在挡、谁负责」）。职责边界是「分析格式」与「沟通格式」；运维代价是同一套事实要维护两张图，改了其一忘了其二就会出现图与事实不符。
- **Risk Register + AI RMF**：Register 管传统风险（按组件与链路组织），AI RMF 管 AI 系统风险（按 Govern / Map / Measure / Manage 组织）。职责边界是「对象不同、账本一本」；运维代价是两套定级口径要能并列，否则 AI 风险要么被低估、要么把传统风险的排序挤乱。
- **P-I Matrix + Chaos Engineering**：矩阵做纸面分档（决定先排哪个），混沌工程做实战验证（决定护栏是否真的在）。职责边界是「先验排序」与「实测证伪」；运维代价是注入实验必须定义爆炸半径与停机预算，否则验证动作本身成为最大风险源。
- **Risk + 知识图谱（KG）**：把风险、威胁、控制、组件建成关系图，用于级联路径与相似条目召回。职责边界是「检索与遍历」而不是「判定」；运维代价是语料治理——过期条目被检索到的概率更高，必须给条目加「最后复核时间」这类字段。
- **AI 辅助 + 专家 review**：模型负责召回（生成候选失效模式、按历史事故聚类），专家负责定级与残留风险接受。职责边界是「穷举」与「签字」；运维代价是要拦住幻觉条目入库——一条听起来合理却不存在的失效模式，一旦带上 Owner 就成为一条有人负责的假风险，清理成本高于生成成本。

这 6 条组合的共同点是：**每加一件，就多一处必须与别处对齐的口径**（识别格式与跟踪字段、分析图与沟通图、两套定级口径、纸面分档与实测值、图谱条目与登记册条目、模型召回与专家定级）。组合的代价不体现在启动上，而体现在**口径漂移**上——凡是没有对齐校验的组合，半年后都会出现两套结论各自为正的情况。

### 7.7 选错的代价与迁移成本

**反模式：把评估做成文档交付物** —— 症状是每次评估产出一份报告，条目没有 Owner 与验证方式，也没有状态机 → 后果是同一条风险年年被重新发现、重新讨论，跟踪成本永久占用而风险序列不变 → 正确做法是条目化（描述 / 影响面 / 触发条件 / 优先级 / 责任人 / 状态 / 验证方式），并以「验证通过才关闭」作为唯一的关闭条件。

**反模式：把序数打分当成测量值** —— 症状是风险表上每行都有 P 与 I 的精确分值，却没人能说出分值来源；或者所有条目的分值趋于一致（清单上全是高风险） → 后果是资源分配回到「谁推得动先做谁」，而评估本身成为形式 → 正确做法是给每条打分标注依据来源（历史事故频率 / 受影响链路 / 实测数据），标注不出来的行一律降级为「未定级」，并优先补齐可实测的那几类。

**反模式：在实现之后才做威胁 / 风险评审** —— 症状是评审结论里出现「架构级缺陷，改动成本高，本期接受」这类条目反复出现 → 后果是发现得越晚，可选项越少，最后只剩下「接受」这一种应对 → 正确做法是把评审输入前移到设计期的图（数据流、依赖、信任边界），此时修复成本最低，而不是等代码写完再对着实现做排查。

**反模式：把「没做」与「决定不做」混在一起** —— 症状是清单上留着一批无人处理的条目，既没说接受也没说排期 → 后果是复核时无法区分「遗漏」与「有意识地接受」，于是每轮评估都要把同一批条目重新讨论一遍 → 正确做法是把风险接受显式化（记录接受了哪几条、理由是什么、在什么条件下需要重评），未记录的一律视为遗漏。

换成另一套方法要动什么（量级是相对比较，不是工期承诺）：

| 迁移方向 | 已有资产能否复用 | 需要重做的工作 | 团队再学习 |
| --- | --- | --- | --- |
| 临时评估 → Checklist / FMEA | 会上讨论过的条目可直接转成条目 | 建立固定分类与模板（含责任人与验证方式） | 低 |
| FMEA → FTA + Bowtie | 组件与失效模式清单可复用为树的底层事件 | 从顶层事件重新建树，并补屏障与责任人 | 中–高：逻辑门与屏障建模 |
| 序数打分 → 分级放量实测 | 历史分值序列不可复用（口径不同） | 统一影响面量纲、设计对照实验、定义安全边界 | 中：实验设计与因果判断 |
| 文档式 → Risk Register | 既有结论可整体迁移为条目（这是最大价值） | 补齐「触发条件」与「验证方式」两列，指派 Owner | 低 |
| Register → 变更门禁 | 条目与影响面字段可复用 | 把影响面接到 CI / 发布链路，并定阈值与例外流程 | 中–高：阈值依据与误判处理 |
| 传统 FMEA → 纳入 AI 系统 | 条目结构可复用，定义方式不可复用 | 严重度改为「影响 × 静默期」，补可接受区间与分布监控 | 高：从二值状态转向分布思维 |
| 单点评估 → 定期复评 + 归档复用 | 上一轮条目可整体复用（这是省时最多的一步） | 建立复评节奏与条目状态复核，把本年清单作为下一年输入 | 低–中：习惯从「每年重来」改为「增量」 |

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 刚开始做风险评估 | Checklist / FMEA + Risk Register | 先用固定分类把覆盖稳住，再用条目状态机把闭环补上 |
| 依赖链复杂、组合失效多 | FTA + Bowtie | 只有反推型方法能表达「多因同时成立」，只有屏障图能讲清控制 |
| 需要为「先修哪个」排序 | P-I Matrix + 风险等级 × 业务影响 | 排序要的是可比较的量与显式的影响面，不是技术复杂度 |
| 要对预算或容量给出数字 | 分级放量实测；不可逆动作则用分布假设并显式标注 | 实测可证伪，假设不可证伪——两者不能用同一种写法呈现 |
| 要验证护栏是否真的生效 | Chaos Engineering / Stress Test | 纸面分析无法回答「屏障今天还在不在」 |
| 被评估对象是 AI 系统 | AI RMF（先落 Map + Measure）+ 固定分类补长尾 | 对象是输出分布，前提从可回滚变成了事前约束 |
| 条目多、人力受限 | LLM 辅助召回 + 专家定级 | 召回允许高召回低精确；定级必须能说出依据来源 |
| 有高影响低概率风险 | 转为预案与演练，并显式记录接受 | 手段与风险性质要匹配；这类风险用日常改造去应对既不经济也不现实 |
| 评估做过就以为已解决 | 定期复评 + 状态跟踪 | 架构变了，旧结论不会自动失效；不跟踪等于默认已解决 |

> 本节小结：这些方法之间唯一真正起决定作用的差异，是**它的结论挂在哪个环节、以及它的数字能否被证伪**——同一套 FMEA 放在文档里与放在发布门禁上，效果差一个量级；一串序数打分与一组实测值，在预算会上是完全不同的两类证据。方法本身的完备性（枚举得多全、图建得多细）只在这两件事成立之后才开始重要；而在 AI 系统上，还要先确认前提是否成立：被评估对象是二值状态，还是一段需要划出可接受区间的输出分布。
