## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

「硬件用 FMEA、安全事故用 FTA、高层汇报用 P-I 矩阵」这类对照表把设计讲成了按场景挑一个。但真实的选择是被约束推着走的：被评估对象是不是可枚举的二值状态、数字从哪里来、评估离不可逆时点还有多远、结论挂在哪，任一条不同，同一场景的正确方法就不同。FMEA 在组件可枚举的系统上完备度是满分，但在「模型输出分布漂移」这个对象上一列都填不满——不是它写得不细，是它的前提不成立。

第二条约束比第一条更容易被忽略：**方法本身的完备性与它的实际效果不是一回事**。同一份分析，挂在文档上等于没人看，挂进条目状态机等于可跟踪，挂在发布门禁上等于每次变更都必须正面回答影响面。挂载点不改变分析质量，但它决定分析有没有效果，而它的影响量级大于在枚举族内部换一种方法。

第三条约束是时间的不可逆性。评估做在封板之后、改造窗口之外时，它产出的是预案而不是改造——此时继续追问「风险识别得全不全」是问错了问题，该问的是「这套预案触发时由谁执行」。

所以本节的组织方式是：先给约束表，再逐个模式写清它被什么逼出来、结构长什么样、代价是什么、在什么条件下优点反转成缺点。**读法提醒**：上面那一段只展开表里最常被忽略的三条，不是全部六条，且正文的编号与表的行序并不对应——正文的「第二条」（挂载点）是表第 4 行，「第三条」（时间窗）是表第 3 行，其余三条只在表里。**读法建议**：不要在模式之间比强弱，只问「我这条约束成立吗」。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 对象是否可枚举、是否二值 | 决定能不能用「逐组件失效模式」这套枚举机制 | 「所有系统都能做 FMEA」——对象从二值状态变成连续分布时，整张表填不满 |
| 数字来源（序数 / 分布假设 / 实测） | 决定结论能否被追问、能否跨条目排序 | 「打完分就能排序」——同分泛滥时排序输入退化成常数 |
| 时间窗（评估离不可逆时点多远） | 决定产出是改造方案还是应急预案 | 「评估越全越好」——封板期一份再全的清单也没有执行入口 |
| 挂载点（文档 / 条目 / 门禁） | 决定它是一次性活动还是持续机制 | 「方法比挂载点重要」——挂错位置，同一份分析的效力差一个量级 |
| 是否需要对外举证 | 决定要不要载具、要不要留残留风险记录 | 「内部评估不用留痕」——客户审计与事故复盘都要逐条回答 |
| 人力与复评频率 | 决定方法能否存活 | 「分类越细越安全」——成本高于收益的方法会退化成照模板填，而填表给的错误信心比不做更贵 |

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 FMEA（失效模式与影响分析）

- **被什么约束逼出来**：对象可拆成有限个组件，且每个组件的失效是可命名的二值状态（坏了 / 没坏）——此时「逐组件正向枚举」是唯一能保证不漏的机制。
- **结构**：一张以「组件 × 失效模式」为单位的工作表，行是失效模式，列是影响 / 原因 / 检测 / 应对。

```text
FMEA 工作表（行 = 一条失效模式，不是一行一个组件）
  组件          失效模式     影响(S)  原因(O)  检测(D)  应对
  ───────────  ──────────  ─────  ─────  ─────  ──────────────────
  消息队列       磁盘写满       高      中      中     容量告警 + 自动扩容
  存储节点       心跳停止       中      低      低     多副本 + 自动摘除
  外部模型 API   服务降级       高      中      中     多供应商 + 降级策略
  ────────────────────────────────────────────────────────────
  关键：S / O / D 三项取值来自人的判断（序数），不是实测值
        所以它能排序，但不能被证伪
  关键：以「组件」为单位组织 → 天然覆盖「每个组件会怎么坏」
        天然不覆盖「组件之间的交互会怎么坏」
```

- **为什么这样设计有效**：因为把「想不想得到」换成了「有没有逐行过一遍」，所以覆盖不随参与者的经验波动，结论可复核。
- **代价**：成本 ∝ 组件数 × 每组件耗时【经验：每个组件 30–60 分钟量级】，最贵的一环是「检测方法」这一列——它要求写清「怎么发现它发生了」，而这通常要真的接一遍监控；另一个必然代价是它与组件边界绑定，跨组件交互失效要另买机制。
- **失效点**：当组件数远超「一轮评审能认真讨论的条目数」时，「系统化、覆盖全」会反转成「照模板填」，因为填表可以交付、思考不能交付，而填出来的表会给出错误的信心——一份没人真正过过的 S/O/D 表，比没有表更危险。
- **真实使用**：【公开】FMEA 的做法通常归于美国军方 1949 年发布的 MIL-P-1629 文件，后发展为 MIL-STD-1629 系列（可按文件编号自行检索核验）；【公开】把威胁按固定分类逐项排查的做法，通常归于微软 Kohnfelder & Garg 于 1999 年提出的 STRIDE 六类威胁（可按微软官方威胁建模文档核验）；【经验】数据平台团队一般只对最贵的几类组件（存储、消息、外部模型 API）做完整 FMEA，其余靠运行监控兜底。

#### 3.2.2 FTA（故障树分析）

- **被什么约束逼出来**：顶层后果已知且唯一，要回答的是「哪几件底层事件同时成立才会导致它」——正向枚举回答不了这种组合关系。
- **结构**：从顶层事件向下演绎的逻辑门树，叶子是可观测的底层事件。

```text
FTA：从「不希望事件」反推（门 = AND / OR）
  [核心链路不可用]                    顶层事件，先定义清楚
        │
        ├─ OR ─ [主库不可用]
        │          ├─ AND ─ [主库故障] + [切换失败]     ← 同时成立才致命
        │          └─ AND ─ [故障] + [备库未同步到位]
        │
        └─ OR ─ [上游依赖不可用]
                   ├─ AND ─ [DNS 解析失败] + [客户端未缓存]
                   └─ AND ─ [限流阈值过低] + [重试风暴]
  ────────────────────────────────────────────────
  关键：门语义让「两个原因同时成立」可表达，正向清单表达不了
  关键：最小割集（哪些叶子的组合足以导致顶层事件）才是产出
        它直接告诉你：要打断哪一条组合，收益最大
```

- **为什么这样设计有效**：因为用 AND / OR 表达组合，所以「单独一个组件坏不致命、两个同时坏才致命」这类结构可以被算出来，也才能算出最小割集去指导加固投入。
- **代价**：树必须由理解系统结构的人构造，构造质量不可批量复制；换一个人重建会得到结构不同的树，两轮结论无法直接比较；树深增加时，维护成本与评审成本同步上升。
- **失效点**：当失效形态不是「组合导致二值故障」，而是部分失败、级联超时、输出分布漂移时，FTA 的精确性会反转成误导，因为它的顶层事件与门语义都假设结果是二值的——用一个二值模型去问分布问题，会得出一个看起来精确的错误答案。
- **真实使用**：【公开】FTA 的方法通常归于 1960 年代贝尔实验室的工作（可按关键词 fault tree analysis 的公开历史材料自行检索核验）；【经验】SRE 团队手写事故 RCA 时，实质在做简化版 FTA——把「根因」写成一条链而不是一棵树，代价是漏掉组合型根因。

#### 3.2.3 Bowtie（领结分析）

- **被什么约束逼出来**：需要向跨团队（含非技术方）说明「这套控制今天还在不在」，并且需要把「投在预防上的钱」与「投在止损上的钱」分开讨论。
- **结构**：核心事件居中，左侧是威胁与预防屏障，右侧是后果与缓解屏障，每道屏障可指派负责人。

```text
Bowtie：建模的是「控制」，不是「原因」
  威胁                    预防屏障        核心事件        缓解屏障              后果
  ────────────────  ────────────────  ────────────  ────────────────  ────────────
  上游口径变更   →  [变更门禁]      ┐                 ┌ [下游通知]     → 指标口径错乱
  依赖服务抖动   →  [熔断 / 限流]   ├→ 核心链路      ├ [降级开关]     → 用户可见失败
  容量不足       →  [容量告警]      ┘   不可用        └ [回滚预案]     → 资金损失
  ────────────────────────────────────────────────────────────────────────────
  关键：左侧屏障防「发生」，右侧屏障防「后果扩大」——两笔预算第一次可分开谈
  关键：每道屏障必须有 Owner 与检测手段，否则它在事故当天不起作用
```

- **为什么这样设计有效**：因为预防与缓解分居两侧，所以「这道屏障是真的在拦，还是只是画在图上」可以被逐道追问，而单侧的因果图问不出这个问题。
- **代价**：元素是自然语言级的，图上不承载概率计算，硬要拿它排序只能得出伪精确结论；对中间事件的分解粒度不足，复杂级联仍要靠 FTA 补；屏障清单会随分析轮次膨胀，且需要持续维护。
- **失效点**：当屏障只有名字没有检测手段时，「直观、可跨团队沟通」反转成虚假安全感，因为事故当天这些屏障不起作用，而图外的人相信它们在。判定方法：数一数图上的屏障里有多少道写清了「怎么测、谁负责」。
- **真实使用**：【公开】Bowtie 的行业起源通常归于 1970 年代末油气行业的使用，并在 1988 年 Piper Alpha 事故后获得更广泛采用（可按关键词 bowtie analysis 的公开历史材料自行检索核验；本节不引用「降低了多少事故率」式数字，这类数字在不同材料里口径互不可比）；【经验】数据平台上常见于「核心链路单点」评审，典型产出是降级开关与回滚预案各一道。

#### 3.2.4 P-I Matrix（概率影响矩阵）

- **被什么约束逼出来**：需要在有限时间内给一批风险排出先后，且没有足够历史频率做真实概率估计——此时只要求比较、不要求测量的序数打分是唯一可行输入。
- **结构**：P 与 I 各分 5 档，映射到「极低 / 低 / 中 / 高 / 极高」五档，档位边界要写死在流程文件里。

```text
P-I Matrix（5×5，值 = 档位而非分数）
            I=1(极小)  I=2(较小)  I=3(中)   I=4(较大)  I=5(极大)
  P=5(极可能)  中        高        高        极高       极高
  P=4(较可能)  中        中        高        高         极高
  P=3(可能)    低        中        中        高         高
  P=2(不太可能) 低        低        中        中         高
  P=1(极不可能) 极低      低        低        中         中
  ────────────────────────────────────────────────
  关键：P 与 I 都是序数（比大小，不做除法）
        不要写「P=4 × I=5 = 20 分」——这个乘法在数学上没有意义
  关键：必须先写死档位边界，否则两个团队的「P=4」差一个量级
```

- **为什么这样设计有效**：因为只要求比较而不要求测量，所以它几乎在任何场景下都能产出可排序的结果，且汇报成本极低——这是它作为对齐工具的价值来源。
- **代价**：序数取值在同分泛滥时排序失效；只有两个维度，忽略时间窗与相关性——由同一根因触发的多个风险会在同一时刻一起发生，而逐行独立的评分表看不见这件事。
- **失效点**：当条目被赋成同一个值（「清单上全是高风险」）时，「简洁、可汇报」反转成「不可决策」，因为排序的输入已经退化成常数，此时真正缺的不是更细的档位，而是一次能区分这些条目的实测或影响面数据。
- **真实使用**：【经验】项目组合管理与季度风险回顾；判定方法：抽三行问「这是排出来的还是测出来的」，答不出依据来源的行不是评估结果，只是一段文字。

#### 3.2.5 Risk Register + Heatmap（风险登记册与热力图）

- **被什么约束逼出来**：评估会反复发生，所以结论必须能跨轮次累积——它解决的不是「怎么识别」，而是「结论存在哪、谁跟、什么时候算关」。
- **结构**：一张带状态机的条目表，状态迁移由「验证方式」约束。

```sql
-- 风险登记册：载具（不产生分析，只承接分析）
CREATE TABLE risk_register (
  risk_id        TEXT PRIMARY KEY,           -- 稳定 ID，跨轮次不变
  description    TEXT NOT NULL,              -- 一句话说清「什么会出问题」
  impact_scope   TEXT NOT NULL,              -- 影响哪条链路 / 多少用户
  trigger_cond   TEXT NOT NULL,              -- 什么条件下触发
  probability    SMALLINT,                   -- 序数；NULL 表示尚未定级
  impact         SMALLINT,                   -- 序数
  owner          TEXT NOT NULL,              -- 具体到人，不是团队
  treatment      TEXT NOT NULL,              -- avoid / transfer / mitigate / accept
  verify_method  TEXT NOT NULL,              -- 怎么证明已处理；无此项则不可关闭
  state          TEXT NOT NULL,              -- open / treating / verified / closed / accepted
  last_review_at TIMESTAMPTZ,                -- TIMESTAMPTZ，不是 TIMESTAMP
  CONSTRAINT no_close_without_verify
    CHECK (state <> 'closed' OR length(btrim(verify_method)) > 3)
);
-- 关键：NOT NULL 保证 verify_method 有值，CHECK 再挡住空串与纯空白
--       两级叠加，才让「什么都不填就关闭」在结构上不可能
--       但这两级只保证「写了」，不保证「写的是真的」：
--       「已通知相关方」照样通过，挡它要靠关闭前的评审抽查
--       去掉这两级，登记册会退化成一张过期列表
```

- **为什么这样设计有效**：因为条目带状态且关闭需要验证方式，「改完即认为解决」这类失效会被结构挡住（没有验证方法就无法迁移到 closed），事故复盘也能落到具体条目。
- **代价**：它要求有人持续维护状态——状态是靠人推的，没有 Owner 的登记册一样会腐坏；同时条目化会鼓励「条数增长」，把已经接受的残留风险继续留在 open 状态，看起来像未完成工作。
- **失效点**：当条目长期停在「处理中」而无人关闭时，「可跟踪」反转成形式主义，因为可跟踪的假象掩盖了没有闭环这件事；此时该做的是给停留超过约定时长的条目强制做一次三选一——修、显式接受、或关掉。
- **真实使用**：见 [§6](04-risk-assessment-section-6-sec6.md) 记录的阿里双 11 风险清单化实践（条目必含影响面、触发条件、责任人、验证方式；验证通过才关闭）；【经验】组织级持续治理场景；判定方法：随机抽一条已关闭条目，问它的验证方式是什么、验证结果记录在哪、今天重放还会通过吗——三问答不全，说明是「改完即关」。

#### 3.2.6 Bayesian Network（贝叶斯网络风险推理）

- **被什么约束逼出来**：风险之间不独立（上游控制失效会抬高下游触发概率），并且证据会陆续到达，结论必须能随证据更新——`P × I` 的乘法假设独立性，解决不了这个约束。
- **结构**：有向无环图 + 每个节点的条件概率表（CPT），新证据到达时做后验更新。

```text
贝叶斯网络：把「独立性假设」换成显式依赖
   [代码变更频率] ──► [缺陷引入率] ──┐
                                     ├──► [线上故障] ──► [资金损失]
   [监控覆盖率] ─────► [MTTD 长短] ──┘
                                     ▲
   [值班人力] ────────────────────────┘
  ────────────────────────────────────────────────
  证据到达前的先验：   P(资金损失) = 待估
  观测到「监控覆盖率下降」后：重算后验，得到下降幅度
  ────────────────────────────────────────────────
  关键：图上每一条箭头都是一句必须能被辩护的假设
        箭头画错，运算会把错误假设输出成两位小数
```

- **为什么这样设计有效**：因为依赖被显式建模，所以可以回答「把监控覆盖率提上去，资金损失概率降多少」这类干预问题，而逐行独立打分表结构上回答不了。
- **代价**：需要先验概率与条件概率表，而这两样恰恰是最缺的——有向图的结构学习与参数标定都要数据或专家标定成本；结论对结构敏感，换个团队画箭头会得到不同的数。
- **失效点**：当先验是编出来的时，「能建模依赖」反转成伪精确，因为有向图与后验运算把一个假设包装成了带小数位的结果，读者无法从输出反推输入的可靠性。判定方法：逐条问「这条箭头或这个条件概率的依据是什么」，答不出的箭头要标成待校准而不是直接进模型。
- **真实使用**：贝叶斯网络作为公开概率方法，其系统化表述一般归于 Judea Pearl 在 1980 年代的工作（可按关键词 Bayesian network 的公开文献自行检索核验）；【经验】金融量化与安全量化场景用它做依赖推理，而不是用它替代频率估计。

#### 3.2.7 Scenario Analysis + Stress Test（场景分析与压力测试）

- **被什么约束逼出来**：未来分布未知、历史数据里没有目标事件，但容量与预算这类不可逆决策必须给一个区间——构造场景是唯一绕开「历史里没发生过」的机制。
- **结构**：一张场景矩阵，每行是一个被构造出来的世界，而不是一个被采样出来的点。

```text
场景矩阵（场景是构造的，不是采样的）
  场景        触发条件                     影响面            预案
  ─────────  ─────────────────────────  ──────────────  ──────────────────
  基线         常态流量                     正常               —
  乐观         增长超预期                   容量提前打满       扩容窗口前移
  悲观         核心依赖降级                 部分链路不可用      降级 + 限流
  黑天鹅       历史未出现过的组合失效        全链路              人工接管预案
  ────────────────────────────────────────────────────────────────
  关键：场景之间不互斥、不完备
        所以不能给场景权重再求和（那不是概率，是把主观性乘一遍）
  关键：产出是「每个场景下的表现与预案」，不是「一个综合风险分」
```

- **为什么这样设计有效**：因为场景是构造的，所以它能覆盖到历史数据里完全不存在的事件（黑天鹅），这一点频率类方法结构上做不到。
- **代价**：场景构造主观，谁定场景谁就定了结论的范围；场景数增加时评审成本线性上升，且「黑天鹅」这一格永远无法证明已经列全。
- **失效点**：当场景被当成概率来加权求和时，「覆盖极端」反转成伪量化，因为权重是人给的，求和只是把主观性乘了一遍又输出成分数；判据是看产出里有没有出现「综合风险分」这种把场景压成一个数的写法。
- **真实使用**：见 [§6](04-risk-assessment-section-6-sec6.md) 记录的大促容量与压测联动实践（压测暴露的问题直接进入风险清单）；【经验】容量规划、预算评审与战略决策是主要适用场景，用量级区间（P50 / P90）表达结论而不是单一值。

#### 3.2.8 Chaos Engineering（混沌工程）

- **被什么约束逼出来**：护栏会随变更悄悄失效——三个月前验过的熔断今天可能已经因为一次配置变更不再生效，而静态分析与评审都发现不了这一点。
- **结构**：一次受控实验：先写稳态假设，再注入，再观测，最后对比假设是否仍成立，全程带终止开关。

```text
混沌实验的结构（缺任何一段就变成制造事故）
  ① 稳态假设     「在这个指标口径下，系统当前是正常的」
        │          —— 没有稳态假设就没有可证伪的对象
  ② 爆炸半径     最小注入集 + 隔离域 + 限流
        │          —— 这一段决定这次注入是实验还是事故
  ③ 注入         在网络 / 依赖 / 资源三个层面之一制造真实故障
        │
  ④ 观测         与稳态假设逐项对比（指标、日志、告警是否按预期触发）
        │
  ⑤ 结论与回滚   假设被推翻 → 这是一个待修条目；终止开关始终可用
  ────────────────────────────────────────────────
  关键：结论来自生产实况，所以它能被证伪——重跑一次即可复现或推翻
        这是它与序数打分最本质的差别
```

- **为什么这样设计有效**：因为产出是实测值而不是判断值，所以「护栏今天还在不在」变成一个可以被追问、可以被复现的问题，而不是一句形容词。
- **代价**：需要建设爆炸半径控制（终止开关、限流、最小注入集、排除不可逆动作），这套控制本身的工程量往往大于实验本身；对写数据、对外发送、删除这类不可逆动作不可用。
- **失效点**：当爆炸半径失控或注入落在隔离域之外时，「暴露隐藏风险」反转成制造真实事故，因为对用户而言，注入的故障与真实故障是同一件事——判定方法：实验前逐条确认终止开关由谁按、注入域是否覆盖了所有写路径。
- **真实使用**：【公开】与 Netflix 于 2011 年公开的 Chaos Monkey / Simian Army 实践相关（可按 Netflix 技术博客核验）；【经验】国内团队常见的最小可用形态是「演练 + 分级放量」，即用真实流量的小比例来验证护栏，而不是专门的注入工具。

#### 3.2.9 AI RMF（AI 风险管理框架）

- **被什么约束逼出来**：AI 系统的风险对象不是「坏掉的组件」，而是输出的分布漂移与治理责任——3.2.1 那种「组件会不会坏」的问法在它身上一列都填不满。约束变了，方法也得换。
- **结构**：四个功能构成的循环，把 AI 风险纳入组织流程，而不是给一套检测工具。

```text
AI RMF 的四功能循环（流程与工具分离）
  Govern   ── 定责任、定政策、定风险容忍度          （组织层）
     │
  Map      ── 写清场景：系统做什么、影响谁、边界在哪  （先写场景，不是先写防护）
     │
  Measure  ── 先写度量口径，再谈检测；口径本身要可复核
     │
  Manage   ── 按度量结果做处置：缓解 / 接受 / 停止
     │
     └────────► 回到 Govern 更新政策
  ────────────────────────────────────────────────
  关键：四个功能里，Map 与 Measure 是主入口
        跳过它们直接进 Manage，等于在没有度量口径的情况下谈处置
```

- **为什么这样设计有效**：因为它是流程而不是厂商方案，所以能直接写进组织流程文件、被审计引用，且不绑定任何供应商；而「先写场景再谈检测」这一条，正好补上了「输出区间」这类新对象缺的记录方式。
- **代价**：它不提供任何检测手段——检测要靠你在 Measure 里自己定义口径并实现；整套搬进一个没有强合规要求的组织时，管理成本可能高于它带来的风险下降，而四个功能里的 Govern 与 Manage 若没有合规压力推动，会退化成会议材料。
- **失效点**：当组织没有强合规要求、也没有人真的填 Map 与 Measure 时，「不绑定厂商、术语跨版本稳定」反转成只产出文档，因为框架能保证的只是「流程齐全」，不能保证「有人按流程做事」。可行的最小用法是先只落 Map 与 Measure 两格（写清场景与度量口径），随合规要求再补另两格。
- **真实使用**：【公开】NIST AI RMF 1.0（NIST AI 100-1，2023-01 发布）与其生成式 AI 专题文件 NIST AI 600-1（2024-07 另发）——**这两份不是同一年发布的**，把 1.0 记成「2024 正式版」是本主题最常见的引用错误，判定方法是看 NIST 文档页上的发布日期；【公开】ISO/IEC 23894:2023（AI 风险管理指南，2023）给方法，ISO/IEC 42001:2023（AI 管理体系要求，2023）给可审计的管理体系，前者是工具箱、后者是制度（均可按发布机构页面核验）；【公开】OWASP Top 10 for LLM Applications 首版发布于 2023 年，其 2025 版发布于 2024-11（版本名与发布年份不一致，引用时需同时写清）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 对象可枚举、失效是二值、要覆盖全 | FMEA（3.2.1） | 不选 FTA：此阶段还没有明确的顶层事件，反推型方法无处可推 | 组件清单能不能列全 |
| 顶层后果已知、要找致命组合 | FTA（3.2.2） | 不选 FMEA：正向枚举结构上覆盖不到组件交互失效 | 能否说清最小割集 |
| 要向跨团队解释控制是否还在 | Bowtie（3.2.3） | 不选 FTA：FTA 建模原因，产出交给分析者；要交出去的是屏障清单 | 图上有多少道屏障有检测手段与 Owner |
| 只有有限时间、要排出先后 | P-I Matrix（3.2.4） | 不选贝叶斯网络：没有先验与标注时，贝叶斯只会把假设包装成小数 | 条目的 P 与 I 是否出现同分泛滥 |
| 评估要反复发生、结论要累积 | Risk Register + Heatmap（3.2.5） | 不选 P-I Matrix：定级方法不承接状态，没有关闭条件 | 关闭前是否必须有验证方式 |
| 风险之间有依赖、证据陆续到达 | Bayesian Network（3.2.6） | 不选 `P × I` 乘法：乘法假设独立，会系统性算错联动风险 | 每条箭头能否给出依据 |
| 不可逆决策、历史里没有目标事件 | Scenario Analysis + Stress Test（3.2.7） | 不选 Monte Carlo：没有可辩护的分布假设时，采样只会输出伪精确的 P90 | 场景是否被当成概率加权 |
| 护栏可能已静默失效、且动作可回滚 | Chaos Engineering（3.2.8） | 不选真实事故复盘：复盘只能发现已经暴露的问题 | 终止开关与爆炸半径是否就位 |
| 被评估对象是模型、且需对外举证 | AI RMF + FMEA（3.2.9、3.2.1） | 不选纯 FMEA：模型没有「坏」这个状态，只有输出分布漂移 | Map 与 Measure 是否有人真的在填 |

表里最常被误选的一对是 **FTA 与 FMEA 互相替代**。团队在「还不知道会出什么事」的阶段直接上 FTA，于是不得不先凭空假定一批顶层事件，这一步一旦靠记忆完成，方法就退化成临时评估——只是长得更像图。反过来，在已经明确「有一类后果必须避免」的关键链路上继续用 FMEA，会得到一份很长的组件清单，却始终说不出「哪两个原因同时成立才致命」。判断顺序应该是：**先问有没有明确的顶层事件，有则 FTA，没有则 FMEA 打底**。

### 3.4 组合模式：真实系统不会只用一种

**组合一：FMEA 打底 + RPN 定级 + Risk Register 承接（最通用的三件套）**。FMEA 负责把候选失效模式枚举出来（覆盖），RPN 负责在条目之间排序（定序），Register 负责状态、Owner 与关闭条件（闭环）。职责边界很干净：枚举与定级都是「分析」，Register 是「载具」，后者换掉不影响前两者。运维代价是要有人维护状态机，且 FMEA 要按季度或按架构变更重跑。适合规模：单业务线到多团队共享平台，凡是「评估要持续做」的组织都适用。

**组合二：FTA + Bowtie（关键链路的因果与控制分离）**。FTA 回答「哪几件同时坏才致命」（原因侧），Bowtie 把结论翻译成「左侧预防屏障、右侧缓解屏障」并逐道指派 Owner（控制侧）。职责边界是：FTA 的产出交给分析与评审，Bowtie 的产出交给运营与跨团队沟通。运维代价是两份图要同步更新，屏障变动时因果图往往不同步。适合规模：只有明确 Top Event 的核心链路，通常是少数几条，不追求覆盖全部系统。

**组合三：分级放量实测 + Chaos Engineering + Register（把测量结果落成条目）**。分级放量负责在真实流量上测出「每放 1% 流量对应的指标波动」，Chaos Engineering 负责验证「护栏今天是否仍生效」，两者产出都是实测值；Register 负责把这些实测结论落成带 Owner 与验证方式的条目。职责边界是：前两者产生数字，后者承接数字。运维代价最高——需要爆炸半径控制、可回滚的发布流程与观测口径统一。适合规模：变更密集、发布频率高到人工评估跟不上的系统，也是三级组合里唯一能把「风险有多大」变成可比较数字的一条路。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「风险评估 = 走过场」 | 归档文件里 S/O/D 三项在所有行上取值几乎相同 | 表被生产出来但没有一次真实讨论，且它给出的是错误的信心而不是空白 | 评估被当成交付物而不是决策输入，填表可交付、思考不能交付 | 每条必须 Owner + 评审 + 行动，关闭需验证 |
| 「过度风险厌恶」 | 所有条目都是「高」，资源按条数分配 | 定序输入退化成常数，排序失效；同时把改造预算挪去处置低影响项 | 定级者是执行方而非承担损失方，抬高定级不影响自己成本 | 显式接受低风险是可选项，写进流程 |
| 「风险遗忘」 | 登记册里 last_review_at 是一年前 | 条目成为过期列表，而过期条目比没有条目更危险 | 评估被当成项目阶段而不是持续过程 | 评估是持续过程，设复评周期与提醒 |
| 「单一视角」 | 表里只有技术列（可用性、延迟），没有业务、合规、声誉列 | 影响面估计系统性偏低，因为它只看得见可观测的那一维 | 评估由技术团队单独发起，业务方不在场 | 多维度评估，业务侧参与定级 |
| 「忽视未知未知」 | 所有条目都是历史事故的复述 | 对未发生过的组合失效完全无预案，事故当天只能临时决策 | 历史事故是最省力的输入，而构造场景要花力气 | 建立韧性机制（场景分析、降级、人工接管） |
| 「P × I 盲目套用」 | 出现「P=4 × I=5 = 20 分」式乘法，或对强相关风险逐行独立评分 | 把序数当比率，且默认独立——由同一根因触发的风险会被系统性低估 | 乘法比序数比较看起来更「量化」，也更好汇报 | 用半定量 + 专家判断，相关风险合并成一个条目 |
| 「风险登记册无跟进」 | 列出上百条，多数条目 owner 为空或写的是团队名 | 无人推进，状态机永远停在 open，载具退化成清单 | 登记册由平台团队维护，但处置权在业务团队 | 每条必须 Owner（具体到人）+ 截止日期 |
| 「缺乏量化」 | 全部条目都是「中 / 高 / 极高」三档 | 无法优先级排序，等于没有评估 | 没有实测数据可用，就退回形容词 | 强制给出影响面（多少用户 / 哪条链路）与触发条件，至少有一个可核查的量 |

三条最危险的展开：

**「走过场」在生产中的暴露方式**：它不会以「我们没做评估」的形式暴露，而是以「评估做了、事故还是发生了」的形式暴露。典型的暴露点是复盘时发现某条已关闭的风险在事故中再次出现——去查那条条目会发现它当初的关闭依据是「已通知相关方」，而不是任何验证结果。这也是为什么 Register 的结构里要让关闭路径强制携带一个非空白的验证方式（`verify_method NOT NULL` 加一条 `length(btrim(verify_method)) > 3` 的 `CHECK`）：**结构能挡住「不填就关」，挡不住「敷衍地填」**——「已通知相关方」这类字样同样能通过这两级约束，它只能靠关闭前的评审抽查兜住。

**「P × I 盲目套用」在生产中的暴露方式**：它在联动风险上暴露。多个风险由同一根因（同一个外部依赖、同一段共享代码、同一次配置下发）触发时，逐行独立评分会把它们各自定成「中」，而它们实际上会在同一分钟一起发生。暴露点通常是事故的时间线——复盘时看到多个「中风险」在同一时刻同时兑现，而评估表毫无预警。

**「过度风险厌恶」在生产中的暴露方式**：它以上线的等待时间暴露，而不是以事故暴露。团队把每一条都定成「高」之后，处置资源被摊薄到所有条目上，真正的高影响项反而得不到优先处理；同时门禁因为总在拦而被全组织走例外流程。此时该修的不是档位定义，而是把定级权交给承担损失的一方。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 一次性评估 → 持续治理 | 单份 FMEA 文档 | 文档没有状态，同一风险每年重现，无法回答「处理到哪一步」 | FMEA + Risk Register | 要有人维护状态机与复评周期，且要定义关闭条件 |
| 组件数十个 → 数千个 | 逐组件完整 FMEA | 成本 ∝ 组件数，评审时间超出可支配人力，退化成填表 | 收窄到最贵的几类组件 + 运行监控兜底 + FTA 补交互失效 | 要接受「覆盖不再完整」，并明确列出未覆盖范围 |
| 变更周级 → 日级千次 | 人工评审 + 序数定级 | 评审带宽成为瓶颈，且序数打分无法跨变更比较 | 分级放量实测 + 门禁自动判定 | 要建设可回滚发布、统一观测口径与爆炸半径控制 |
| 新增模型 / LLM 组件 | 组件失效 FMEA | 模型没有「坏」这个状态，只有输出分布漂移，表填不满 | AI RMF 的 Map 与 Measure 两格 | 要先把「可接受输出区间」写出来，这是一项新工作 |
| 内部评估 → 需对外举证 | 条目状态机 | 客户审计与监管要求逐条回答「排查了什么、残留风险是什么」 | 在 Register 上加审计留痕与政策引用 | 每次评估要留下可复核的记录，评估成本上升 |

### 3.7 自检清单

- [ ] 每条风险的「影响面」写的是具体链路或具体口径，而不是「影响较大」这类形容词？
- [ ] 登记册里有没有任意一条条目的 owner 写的是团队名而不是人？
- [ ] 已关闭的条目中，有多少条能当场说出它的验证方式是什么？答不出的条数占比是多少？
- [ ] P 与 I 有没有出现「同分泛滥」（某一档占比超过一半）？如果有，排序还成立吗？
- [ ] 表里有没有出现 `P × I = 分数` 这类乘法？出现即违反序数纪律。
- [ ] 由同一根因触发的风险，是否被合并成一个条目而不是拆成多行？
- [ ] FMEA 表里「检测方法」这一列有没有空行？空行意味着这条失效模式不会有告警。
- [ ] FTA 树的每个叶子是否都是可观测事件？不可观测的叶子只能是假设，不能进割集。
- [ ] Bowtie 图上的每道屏障是否都有 Owner 与检测手段？
- [ ] 混沌实验是否逐项确认了终止开关、爆炸半径与不可逆动作的排除？
- [ ] 最新的评估结论是否挂在某个执行环节上（门禁、发布流程、值班交接），还是只存在于文档里？
- [ ] 上一年的事故是否都落在已有分类的格子里？落在表外的比例是多少？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 组件可枚举、失效二值、要覆盖全 | FMEA | 把「想不想得到」换成「逐行过一遍」，覆盖不随经验波动 |
| 顶层后果已知、要找致命组合 | FTA | 逻辑门能表达「两个原因同时成立」，割集直接指向加固点 |
| 必须向跨团队解释控制是否还在 | Bowtie | 预防与缓解分侧，两笔预算可分开谈，屏障可逐道指派 |
| 时间有限、只要排出先后 | P-I Matrix | 序数打分只要求比较，几乎任何场景都能出结果 |
| 评估要持续、结论要累积 | Risk Register + Heatmap | 状态机 + 关闭需验证，把「改完即解决」挡在结构外 |
| 风险有依赖、证据陆续到达 | Bayesian Network | 显式建模依赖，能回答干预问题 |
| 不可逆决策、历史无同类事件 | Scenario Analysis + Stress Test | 场景是构造的，可覆盖历史里不存在的事件 |
| 护栏可能已静默失效、动作可回滚 | Chaos Engineering | 产出实测值，可被证伪、可复现 |
| 对象是模型、需对外举证 | AI RMF + FMEA | 先写场景与度量口径，再谈检测与处置 |

> 本节小结：决定模式选择的唯一那条约束是**「被评估对象的失效是不是一个可枚举的二值状态」**——是，则枚举与逻辑门有效；不是（输出分布、漂移、存量指标波动），则整套「组件会不会坏」的问法失效，必须换成先写场景与度量口径。而在这条约束之外，真正拉开效果差距的不是选哪一种分析方法，而是**结论挂在哪个执行环节上**：挂在文档上等于没人看，挂进条目状态机等于可跟踪，挂在门禁上等于每次变更都要正面回答。
