## 3. 设计模式与范式

> 原 § 3 共 138 行：列出 10 个模式（其中 4 个带结构示意）与 9 条反模式，另有 7 行适用场景决策表；本节保留全部 10 个模式与 9 条反模式，为每个模式补上约束、结构、机制、代价与失效点，重写为 ~360 行模式手册。

### 3.1 先看约束：模式不是选择题，是约束的产物

原文件的决策表把设计讲成了「按场景挑一个方法」：识别用 Map、量化用 SQALE、优先级用 Backlog + ROI、节奏用 Sprint + Budget、重构用 Strangler Fig、AI 应用用 AI Tech Debt 治理、质量用 Quality Gates。这些推荐本身没有误导，但它们把**四种不同性质的东西**排进了同一列格子——**让债可见**（象限、Backlog、地图、燃烧图）、**给债一条通道**（预算、Sprint）、**偿还手段**（绞杀者、抽象分支）、**防新增**（质量门禁、AI 债治理）。前三者可以叠加，第四者是另一根轴。真正决定选择的约束有六条。

第一条是**这笔债的利息落在谁身上**。如果付息的人就是还债的人（同一团队、边界清晰），那么该团队自己能感知到痛，日常通道就够了；如果根因在一个团队、成本由多个团队承担，那么出资方与受益方不是同一方——单靠该团队没有动力，必须靠组织机制（固定预算、集中窗口、债主制）介入。这一条排在所有方法之前，因为它决定了「靠自觉能不能解决」。

第二条是**债务的类型**。五形态的分法（代码债、架构债、数据债、基础设施债、AI 债，见 [§1.1](06-tech-debt.md)）不是分类学，而是**手段可行性**的判据：代码债能在一次提交里顺手还，架构债不能切成碎片（替换存储格式、替换消息机制都要一次协调好的切换窗口），数据债与 AI 债没有现成的 lint 规则。类型选错，手段必然选错。

第三条是**度量口径是本金还是利息**。本金是「修好要多少人时」，利息是「每次变更多花多少时间」；选用哪一种，决定了榜单把哪一类债排到前面——按本金排序会系统性偏向「容易修的东西」，「没有 Owner 的宽表」这类算不出工时的债权重接近零，而真正的痛几乎全部来自利息（本主题的机制展开见 [§7.3.1](06-tech-debt-section-7-sec7.md)）。

第四条是**排期通道**：与需求竞争同一个池子，还是有一条固定且受保护的工时。这条决定还债会不会真的发生，而不是决定它值不值得做。第五条是**旧账有没有主**：没有具体到人的 Owner，债在被排期之前就已经无人认领——[§ 6.1](06-tech-debt-section-6-sec6.md) 的公开做法把「债主」与「时间预算」并列为三件套之一，原因就在这里。第六条是**产债速率与偿还速率的关系**：偿还再快也追不上新增速度时，先要修的是产债来源（门禁、评审、Owner 缺失），而不是加大偿还预算。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 利息落在谁身上（本团队 / 跨团队） | 靠自觉能不能解决，要不要组织机制 | 「先列清单再慢慢还」——跨团队债的瓶颈是协调，不是工时 |
| 债务类型（代码 / 架构 / 数据 / AI） | 哪种偿还手段可用 | 「重构能解决一切」——重构降利息，完不成架构级本金偿还 |
| 度量口径（本金 / 利息） | 榜单把哪一类债排到前面 | 「扫描报告第一屏就是最该还的」——按本金排序会把高利息热点排到中后段 |
| 排期通道（同池竞争 / 固定受保护） | 还债会不会真的发生 | 「等不忙了再还」——需求收益是当期的，债的收益是延迟的 |
| 旧账有没有主 | 债是被处理还是被搁置 | 「列出来自然有人管」——无 Owner 的条目会一直停在清单上 |
| 产债速率 vs 偿还速率 | 治理动作该先修哪一端 | 「加大偿还预算就能追上」——产债速率更高时，任何预算都会被淹没 |

读这张表要自上而下：第 1–2 行决定**这件事能不能靠单团队解决、以及它属于哪一类**，第 3–4 行决定**它会不会被排上、会不会被排对**，最后两行决定**它能不能长期被控制住**。

### 3.2 模式逐个拆解（核心节）

原文件列出的 10 个模式在下面 10 个小节里逐条保留、未做删减，顺序与原文件一致。按「它在治理链路上承担哪一段」可分成四族：**让债可见**（3.2.1–3.2.3、3.2.10）、**给债通道**（3.2.4–3.2.5）、**偿还手段**（3.2.6–3.2.7）、**防新增与 AI 债**（3.2.8–3.2.9）。分组只用于组织阅读，判据仍是 [§7.3](06-tech-debt-section-7-sec7.md) 的四条机制维度：**度量口径 → 偿还通道 → 可分批性 → 识别来源**。

每个模式按六件事展开：被什么约束逼出来、结构、为什么这样设计有效、代价、失效点、真实使用，并在末尾附一条**核验方法**。**失效点最关键**：它回答「这个模式的优点在什么条件下反转成缺点」，而原稿只有两个模式（绞杀者、抽象分支）标了一行「适用」，全部模式都没有写失效条件。

#### 3.2.1 技术债象限（Martin Fowler）

- **被什么约束逼出来**：团队分不清「哪些债是知情的权衡、哪些是无意的错误、哪些是明知故犯」，于是同一套处理方式被套到所有债上——该登记的没登记，该复盘的被问责，该问责的被当成正常代价。
- **结构**：

```text
                 Prudent（谨慎）                Reckless（鲁莽）
 Deliberate   「我们现在做 MVP，后续偿还」      「没时间设计，先写代码」
 （刻意）      + 有还债计划                    + 无还债计划
              → 该被登记 + 排期               → 该被问责 + 加门禁

 Inadvertent  「当时不知道更好的方案」          「不知道有这回事」
 （无意）      → 该被复盘 + 培训               → 该被识别 + 补能力

象限回答的是「这笔债该怎么处理」，不是「先处理哪个」
→ 它不产生优先级，只产生动作类型
```

- **为什么这样设计有效**：因为两个维度是正交的，所以「这笔债该不该被容忍」与「它该不该被登记」变成了两个独立问题——刻意且谨慎的债需要的是登记与排期，无意产生的债需要的是复盘与识别能力。这解释了它为什么是治理的起点：它先解决「记录什么」，而大多数团队的问题恰恰在于**只记录那些明显是错误的东西**，把刻意妥协的那一类留在了口头。
- **代价**：它是定性分类，产出的是「该怎么处理」而不是「先处理哪个」；每一笔债的归类都要人来判断，无法用工具批量打标；而且归类会随时间变化——今天「无意」的债，团队学会之后仍然是历史债，格子却变了。
- **失效点**：当**团队把它当成优先级工具**时（先做「鲁莽」那一格，因为它看起来最该还），「分清了债的性质」的优点反转成「按错误类型排队而不是按代价排队」——因为象限里不包含「这笔债的利息有多高」这一维，同一格里的两笔债，利息可能相差一个量级。修法是用变更热度补一层排序，把它接回 3.2.3。
- **真实使用**：【公开】Martin Fowler《TechnicalDebtQuadrant》（martinfowler.com；该文以常青文章形式维护，引用其年份请以站点当前版本为准，本章 [§7.3.4](06-tech-debt-section-7-sec7.md) 采用同一口径）；【公开】Ward Cunningham 于 1992 年（OOPSLA）提出技术债隐喻，其原始语境是「为快速交付做出的、需要被记住的妥协」——债的原生要求是被登记，而不是被自动发现。
- **核验方法**：翻你手上的债清单，看有没有一条属于「刻意 + 谨慎」那一格。一条都没有，说明清单只记了事故，没记妥协。

#### 3.2.2 技术债 Backlog

- **被什么约束逼出来**：债务分布在代码、架构、数据、基础设施、AI 五个层面，不集中登记就没人说得清「我们欠了多少」——而说不清的事，不可能被排进任何计划。
- **结构**（每条债的字段即它的可用性上限）：

```text
DEBT-<ID>
  描述 / 位置 ：哪一段代码、架构、数据或 AI 资产
  本金        ：一次性修复的估算人时（容易估 ⇒ 清单会偏向好修的东西）
  利息        ：每次变更多花的时间 × 变更频次（难估，但决定痛感）
  Owner       ：具体到人，不是团队                    ← 最常被漏掉的两个字段
  通道        ：持续（受保护的工时）/ 项目（有起止的窗口）←
  状态        ：登记 / 已排期 / 已偿还 / 已作废（作废必须写原因）
```

- **为什么这样设计有效**：因为每条债被拆成「本金 + 利息」两项，它才第一次能和需求放进同一个排期池里比较；而把「通道」写成必填字段，是因为它决定了这条债会走哪条路——持续通道靠固定工时保证会发生，项目通道靠一次立项保证有起止。这两个字段的缺失正是清单失效的直接原因。
- **代价**：登记本身是纯成本，收益要等到下一次排期才出现；清单越积越厚时信噪比下降，重要条目被埋在历史条目里；而且它的字段天然是本金口径（工时可估），因此会系统性偏向容易修的条目——真正贵的架构债在清单上往往只有一行字。
- **失效点**：当**清单既没有 Owner 也没有独立通道**时，「把债集中登记」的优点反转成「坟场」——因为条目与需求竞争同一个排期池，而需求的收益是当期的、债的收益是延迟的，同池竞争的结果总是需求先做。判定方法很便宜：翻过去四个季度的排期记录，数一数「技术债」条目实际被完成的次数。
- **真实使用**：【经验】这是多数团队唯一有的机制，也是多数团队唯一失效的机制；【公开】Cunningham 1992 的原始语境把它定位为「需要被记住的妥协」（见 [§7.3.4](06-tech-debt-section-7-sec7.md)），所以「登记」不是流程负担，而是这个概念的原生要求。
- **核验方法**：随机抽 10 条，看有几条同时填了 Owner 与通道。这两项的空缺率，就是这份清单的实际可用率。

#### 3.2.3 技术债地图（Tech Debt Map）

- **被什么约束逼出来**：清单能回答「有哪些债」，不能回答「债在哪」；而治理动作是按模块、按 Owner 下达的，不是按条目下达的。
- **结构**（两张坐标轴比一张金额表更有用：变更热度来自版本历史，复杂度来自静态分析）：

```text
            高变更热度（利息正在被支付）
                 │   营销系统 ●     ← 先还：本金小、每天都在付息
  ───────────────┼───────────────  复杂度 →
                 │   订单系统 ●  用户系统 ●
            低变更热度（本金大、利息低）
                 → 现在不动它反而是对的（但要登记，避免在错误的时间点一次性踩爆）

读法：色块深浅说明「问题有多密」，两个轴说明「它值不值得现在动」
```

- **为什么这样设计有效**：因为它把「债有多少」换成了「债分布在哪些模块、这些模块还会不会被改」，所以治理动作第一次有了可以下达的对象；又因为变更热度被乘了进来，排在前面的是「每天都在被改的复杂文件」，而不是「八年没人动的三千行旧模块」——前者的本金小、利息每天都在付，后者的本金大、利息接近零。这是它与按本金排序的扫描榜单最实质的区别。
- **代价**：地图要两张输入（静态分析 + 版本历史），缺任一张就退化；变更热度在提交习惯不规范时失真——大量批量提交、force push、把多个改动静默合并，会让热度排序接近随机（[§7.3.4](06-tech-debt-section-7-sec7.md) 的失效条件）；此外地图不包含本金估计，所以它不能单独回答「这笔债要花多少」。
- **失效点**：当**团队把地图当作结论**时（按色块深浅直接排优先级），「说明了债在哪」的优点反转成「按位置排序而不是按代价排序」——因为地图不含修复成本与收益，色块深只说明问题密度。第二条反转在同一维上：当**代码库很新、变更分布均匀**时，热度这一维的区分度下降到接近零，地图退化成按复杂度排序，而复杂度最高的往往正是那些稳定、少改的模块。
- **真实使用**：【公开】「变更热度 × 复杂度」的定位方法由 Adam Tornhill 在《Your Code as a Crime Scene》（2015）中系统化（本章 [§7.3.1](06-tech-debt-section-7-sec7.md) 的公开证据口径）；【经验】它是把静态扫描结果接回利息口径的最低成本做法。
- **核验方法**：取扫描报表前 20 条，逐条标「这段代码在过去 6 个月被改过几次」。若多数是 0 次，你手上是本金榜而不是利息榜。

#### 3.2.4 技术债预算（Tech Debt Budget）

- **被什么约束逼出来**：还债容量必须有上界——既防止「无限还债」挤占交付，也防止「无限产债」被默许。它要回答的是「我们允许欠多少」，而不是「先还哪一笔」。
- **结构**：

```text
期初额度（组织级 / 团队级）
   │
   ├─ 每笔新功能上线前评估「本次新增多少债」
   ├─ 累计额度未超 ──▶ 放行
   └─ 累计额度已超 ──▶ 先还一笔等额债，再上新功能

关键：它约束的是「产债速率」，不是「偿还速率」
      额度只能保证「不会无限新增」，不能保证「旧的会被偿还」
```

- **为什么这样设计有效**：因为额度把「产债速率」变成了一次可被拒绝的显式条件，所以「先上新功能、债以后再补」这条默认路径第一次有了成本——每笔新功能在放行前都必须先回答「本次新增多少债」，答不上或超额就得先还一笔等额债。它与 3.2.5 的分工也由此划出：预算管住分母（新增速率），Sprint 提供分子（偿还窗口）。
- **代价**：额度需要一个度量口径（钱或人时），而债务的度量本身不可靠——各类公开报告里「多少时间花在技术债上」的百分比口径差异很大（是否含维护、是否含会议），只能作量级信号，不能当精确值（[§7.4](06-tech-debt-section-7-sec7.md) 对此有专门说明）。口径不可比而额度被当成精确数字时，讨论会从「该不该还」滑向「这个数算得对不对」。
- **失效点**：当**预算只约束新增、不配偿还通道**时，「债务总额有上界」的优点反转成「额度成了汇报口径」——因为额度内该还的债仍然排在需求后面，曲线好看而利息照付。判据：看预算执行记录里，「因超额被要求先还债」实际发生过几次；一次都没有，说明它只是一张表。
- **真实使用**：【经验】额度本身是组织内部约定，不跨组织可比（[§7.4](06-tech-debt-section-7-sec7.md) 明确各类量化档位属工具默认值与团队习惯的常见取值，不是行业标准）。可核验的做法是查你自己的额度定义文件，确认 Y 轴口径是本金还是利息。
- **核验方法**：把额度除以「单位修复人时」，看它换算出的可偿还量级是否与团队规模对得上；对不上说明额度没有任何行为约束力。

#### 3.2.5 技术债 Sprint（还债 Sprint）

- **被什么约束逼出来**：日常排期里还债永远排在需求后面，而有一类债（跨团队接口调整、需要多个团队同时投入的改动）在分散状态下根本排不动——需要一个有起止、能批量协调的窗口。
- **结构**：

```text
每季度 1 个还债 Sprint（容量常见在 10–20% 之间，【经验】）
  输入：从 Backlog 按优先级选债单
       优先选「利息高 且 这段代码还会被改」的条目
  输出：可度量的收益（不是「做了几件事」，而是某个指标动了）
风险：Sprint 与需求竞争同一个排期池 ⇒ 需求一紧，它先被让出
```

- **为什么这样设计有效**：因为它把还债变成一个**项目通道**（有起止、有产出物），跨团队协调成本可以在窗口内一次性摊平——分散偿还最难解决的从来不是工时，而是「需要多个团队同时投入」这件事。也正因为它是项目通道，它的容量与需求共享同一个池子，这条性质是它的机制，不是执行问题。
- **代价**：偿还是脉冲式的——集中清一批之后，产债机制未变，债务会以相近速率重新累积；它还会给出一个隐性许可：其他时间可以不还债。这两项合起来，正是「还债运动」反复发生的原因（不是团队不努力，而是通道设计使它必然反复）。
- **失效点**：当**需求压力上升**时，「集中还债」的优点反转成「每季度第一个被让出的东西」——因为它与需求同池竞争，且收益是延迟的、不可见的。判据很直接：连续四个季度里，这个 Sprint 被完整执行了几次。
- **真实使用**：与之相对的是**持续通道**——【公开】Google 的公开材料描述了以固定时间预算 + 模块 Owner（债主）为核心的机制，其目标是「维持可控」而非「清零」（[Google 公开材料 2009-2024]，以官方材料的当前版本为准；整理见 [§ 6.1](06-tech-debt-section-6-sec6.md)）；【公开】阿里把「集中还债月 + 债主制」作为跨团队债的窗口（[阿里公开材料 2019-2024]，以官方材料的当前版本为准；见 [§ 6.4](06-tech-debt-section-6-sec6.md)）——前者是持续通道，后者是项目通道，两者的失败模式互补。
- **核验方法**：数两部分——Sprint 曾被让出几次，以及它清理的债在下一个季度里有多少重新出现在清单上。

#### 3.2.6 Strangler Fig Pattern（绞杀者模式）

- **被什么约束逼出来**：架构级债务无法切成碎片偿还，而一次性重写又不可行——旧系统在重写期间继续接需求，目标不断移动，重写永远追不上（Netscape 的重写是被公开引用的经典案例：Joel Spolsky 在 2000 年的文章中把它作为「不要重写」的论据【公开】，本章 [§7.3.3](06-tech-debt-section-7-sec7.md) 采用同一归属）。
- **结构**：

```text
[旧系统] ◀── [路由层] ──▶ [新系统]
                 │
     按流量 / 按调用方分批切换，每批走完整三段：
       ① 并行验证：新旧同时产出 + 对数，差异超阈值即阻断
       ② 灰度切换：切一部分流量 / 一部分调用方
       ③ 观察 + 回退：出问题只回退该批，不影响其他批

成本结构：双跑期成本 = 并存时长 ×（并行运维 + 一致性核对）
          与批次数无关 —— 分批降的是单次风险，抬的是总成本
```

- **为什么这样设计有效**：因为新旧实现长期并存、切换按流量或调用方分批判推进，所以每一批都能独立验证、独立回退，单批失败的影响面被限制在那部分流量上。这解释了一个反直觉的推论：**分批降低的是单次风险，抬高的是总成本**——两者是同一机制的两面，不是可以各自优化的两个指标。
- **代价**：【推算】设两张实现并存 6 个月（26 周），每周 0.5 人维护旧实现 + 0.25 人做一致性核对，则 26 × 0.75 ≈ 20 人周，按每月 4.33 周折算约 4.6 人月（【推算】，推导链是「并存周数 × 每周并行成本」，系数按你团队实际情况替换）。把同一系数用到季度尺度：13 × 0.75 ≈ 10 人周 ≈ 2.3 人月——**并存时间每延长一个季度，就多付约 2.3 人月**，这是「绞杀式替换要尽快把旧实现下线，而不是留着做备份」的定量理由。
- **失效点**：当**被替换的部分是强一致边界**（同一笔事务跨新旧两套实现）时，「分批可控、单批可回退」的优点反转成「核对成本高到不可接受」——因为并存期内每一笔跨边界的事务都要双写双读并对账，两边不一致时无法判定以哪一边为准。此时的修法不是硬撑，而是改成「先迁读路径、再迁写路径」，或者干脆把该边界收进一套新实现；若替换动机是合规或安全（旧实现不允许继续运行），双跑期本身就是违规的，只能走冻结窗口一次性切换。
- **真实使用**：【公开】绞杀者模式由 Martin Fowler 命名（martinfowler.com，2004；本章 [§7.3.3](06-tech-debt-section-7-sec7.md) 的归属口径），其原始动机正是「让替换过程可分批、可随时停下」；【公开】本章 [§ 6.2](06-tech-debt-section-6-sec6.md) 记录的 React Fiber 重构把「新旧实现并行 + 逐步切换」作为核心做法（[React 官方公开材料 2017-2024]，以官方材料的当前版本为准），与本模式同属「新旧并存」这一族，差别在切换粒度（按组件 vs 按流量 / 调用方）。
- **核验方法**：问两个问题——新旧实现能否同时存在（数据格式与协议是否允许双写双读），切换能否按流量或调用方分批。两个都能，绞杀是默认选项；有一个不能，走 3.2.7 或冻结窗口。

#### 3.2.7 Branch by Abstraction（抽象分支）

- **被什么约束逼出来**：新旧的切换点无法按流量分批——调用方太多、协议不允许双跑、或者这是同一进程内的组件替换（例如 ORM、序列化格式），根本没有「一部分流量」这回事。此时需要一个**单一的、可控的切换点**。
- **结构**：

```text
[旧实现] ──▶ [抽象层] ──▶ [新实现]
                 ▲
                 └── 切换点收敛到一处：一次切换、一次记录、可整体回退

与绞杀者的差别：
  并存期内多维护「一层抽象」（接口 + 适配器 + 双实现）
  切换是一次性的 ⇒ 风险集中，但没有长期双跑的一致性核对成本
  抽象层在切换完成后必须被删掉 —— 留下它就变成新的债
```

- **为什么这样设计有效**：因为切换点被收敛到一处，所以任何时刻只有一次切换动作、一份切换记录，避免了「一半调用方走新路径、一半走旧路径」的长期混乱——这种混乱的代价不是性能，而是**没人说得清线上跑的是哪一套**。它换来的性质是「切换可整体回退」，而代价是这一次不能分批。
- **代价**：并存期内要维护一层抽象（接口、适配器、两套实现并存），这层抽象在切换完成后必须被删除，而它经常被留下成为新的技术债；抽象层一旦设计错（抽象漏出实现细节），两边的实现会互相耦合，重构变成搬砖。
- **失效点**：当**抽象层泄漏了旧实现的细节**时，「切换点收敛到一处」的优点反转成「新实现被旧实现的形状锁死」——因为抽象层一旦暴露旧实现特有的语义（空值处理、事务边界、异常类型、超时语义），新实现就必须模仿旧实现才能兼容，于是替换退化成搬家。判据：看抽象层的接口里有没有出现只有旧实现才有的概念；有，就先修抽象，再谈切换。
- **真实使用**：【公开】Branch by Abstraction 与绞杀者同属 Martin Fowler 命名的替换手法家族（martinfowler.com 该模式页面；本章 [§7.3.3](06-tech-debt-section-7-sec7.md) 把两者列为「新旧并存」下的两种切换粒度）；【经验】它在进程内组件替换上比绞杀者更常见，因为这类替换本来就没有流量可以分批。
- **核验方法**：查抽象层的接口签名。若签名里出现了旧实现专有的概念，说明这层抽象是为了兼容而写、不是为了替换而写。

#### 3.2.8 Code Quality Gates（质量门禁）

- **被什么约束逼出来**：偿还再快也追不上新增速度时，必须先降低**产债速率**；而产债速率恰好是少数能被机器判定的东西——它的判定需要「同一输入同一结论」这个性质。
- **结构**（门禁项的类型是通用的，阈值必须来自你自己的存量基线）：

```text
门禁项（阈值必须从你的存量基线推出来，不要照搬任何默认值）
  测试覆盖率      低于团队基线 ──▶ 禁止合并
  圈复杂度        超过团队基线 ──▶ 禁止合并
  代码重复率      超过团队基线 ──▶ 禁止合并
  债务比率        SonarSource 口径的 Technical Debt Ratio（阈值以你的 Quality Gate 配置为准）

关键设计：门禁只拦「新增」，不还「旧账」
          误报率决定它能否长期存活 —— 误报多到一定程度，团队会学会绕过它
          判定依据必须是规则（同一输入同一结论），不能是概率模型的输出
```

- **为什么这样设计有效**：因为门禁的输入只有代码本身、不含使用频次，所以它能拦住「新写出来的复杂函数」，却完全看不见「这座模块每天被改多少次」——它管的是产债速率，与利息无关。这条性质同时解释了它为什么必须与「还旧账」的机制配套：**它能证明数量在降，不能证明痛感在降**。
- **代价**：门禁的可信度取决于误报率，而误报处理是持续的隐性成本——误报多到一定程度，团队会绕过它，此时它从机制退化成形式；它天然偏向「容易测的东西」（可自动计算的规则命中项），对「没有 Owner」「指标口径不一致」「无血缘」这类算不出修复工时的债近乎失明（[§7.3.1](06-tech-debt-section-7-sec7.md)）。
- **失效点**：当**把概率模型的输出直接当门禁判定**时，「拦住新增」的优点反转成「时拦时不拦」——因为门禁需要的是确定性判定，而概率生成器不具备这个性质，于是团队对它的信任会随着一致性下降而崩塌；这也是 LLM 辅助审查只能进候选池、不能单独作为判定依据的机制原因（[§7.3.4](06-tech-debt-section-7-sec7.md)）。第二条反转：当**基线被一次大重构抬高**之后，旧代码与新代码用同一条阈值，门禁会从「拦新增」变成「挡所有提交」。
- **真实使用**：【公开】SonarSource 官方文档把 Technical Debt 定义为修复成本、把 Technical Debt Ratio 定义为债务与开发成本的比值（本章 [§7.3.1](06-tech-debt-section-7-sec7.md) 的公开证据口径）；【经验】门禁的阈值属工具默认值与团队习惯的常见取值，不是行业标准——判定方法是查你自己的 Quality Gate 配置里那次判定用的具体门槛，并追问「这个门槛是谁定的、依据是什么」。
- **核验方法**：统计上一次误报（被判违规但人工判定不该拦）的比例，以及有没有观察到绕行记录。绕行记录比误报率本身更能说明门禁是否还有效。

#### 3.2.9 AI Tech Debt 治理

- **被什么约束逼出来**：AI 应用的债不在代码结构里，而在提示词、模型、数据与智能体行为上——静态规则看不见它们，且这类债的利息形态不同：**不是代码变慢，而是效果静默退化**（[§7.4](06-tech-debt-section-7-sec7.md) 族 5 的隐性成本）。
- **结构**（AI 债的偿还动作是「能回滚」，而回滚的前提是「版本可定位」）：

```text
每个 AI 资产要能被回答的四个问题（缺一个就无法回滚）
  提示词：哪一版、谁改的、改动前后的评估结果是什么
  模型　：哪个版本、训练 / 微调数据来自哪条链路、评测集是哪一版
  评估　：ground truth 从哪来、是否独立于被测链路
  轨迹　：这次调用用了什么工具、每轮的判定结果是什么
关键：版本可定位 + 评估独立 + 轨迹可查 —— 三件事缺任何一件，退化都无法被发现，更无法回滚
```

| AI 债 | 检测 | 治理 |
| --- | --- | --- |
| 提示词硬编码 | 代码扫描 / 评审 | Prompt Registry（版本可定位、变更留痕） |
| 模型无版本 | 元数据缺失检查 | Model Registry（版本 + 数据链路 + 评测集版本） |
| 模型无监控 | 漂移检测 | 线上监控（效果与成本的常态化观测） |
| 模型无评估 | 评估缺失检查 | Eval Pipeline（独立 ground truth + 发布前回归） |
| 智能体无审计 | 日志缺失检查 | 轨迹落盘（每一轮的调用与判定可查） |
| 数据漂移 | 分布检测 | 数据漂移监控 + 重新评估触发条件 |

- **为什么这样设计有效**：因为这类债的利息表现为「效果静默退化」，所以治理动作的核心不是重构，而是**让每一次变更可回滚、可回归**——版本可定位决定能不能退回去，评估独立决定退化能不能被看见。这两件事都成立时，「模型升级」才从一次赌博变成一次可验证的变更。
- **代价**：常设投入（评估集维护、监控、轨迹存储与留存），且评估集的人工标注成本外包不掉；更麻烦的是它的收益在很长一段时间内不可见——不退化的时候，这些投入看起来全是浪费。
- **失效点**：当**评估集的 ground truth 由被测链路自己产出**时（用同一个模型当裁判、把线上点赞当标注），「评估能发现退化」的优点反转成「评估在自我确认」——因为裁判与被测同源时错误高度相关，指标会稳定地给出好看的分数，而系统在退化。修法是把 ground truth 移出链路（人工标注 / 业务规则），或至少换族系交叉验证并抽样人工核；LLM 的输出只能进候选池，不能单独作为判定（[§7.3.4](06-tech-debt-section-7-sec7.md)）。
- **真实使用**：【经验】AI 债目前没有成熟的标准化量化方法，治理以「版本可定位 + 评估独立 + 轨迹可查」三件事为主；这类债在 Fowler 象限里多落在「无意」一侧，因此更依赖登记与评审，而不是自动发现（[§7.3.4](06-tech-debt-section-7-sec7.md) 对识别来源的口径）。
- **核验方法**：挑一条最近改过的提示词，问「它的上一版在哪、改动前后的评估分数各是多少」。答不出来，说明这条债连登记都没做到。

#### 3.2.10 Tech Debt Burndown（燃烧图）

- **被什么约束逼出来**：治理机制有没有效果，需要一条随时间变化的曲线——否则「我们在还债」只是一句声明，无法回答「债是被对冲了，还是只增不减」。
- **结构**：

```text
债务
 │ ●
 │   ●●
 │       ●●●              Y 轴口径必须冻结：
 │            ●●●●        本金口径与利息口径会给出相反的趋势
 │                 ●●●●●   （多写测试会让「修复工时」上升，而利息在下降）
 └──────────────────────▶ 时间
    Q1    Q2    Q3

曲线健康 ≠ 债被还掉：改分类、拆条目、直接关闭，都会让曲线变好看而利息不变
```

- **为什么这样设计有效**：因为它是一条趋势线，所以它度量的是**机制的效果**（债在被对冲还是只增不减），而不是单笔债务的优先级——它天然适合回答「我们的治理机制有没有用」，不适合回答「本周做什么」。把它放在制度那一层读，它的价值才成立。
- **代价**：曲线要成立，必须先冻结 Y 轴口径——本金口径与利息口径会给出相反的趋势，口径一改历史曲线全部作废，所以它要求治理层先做一次口径决策，而这次决策本身就容易拖成政治问题；此外图本身不产生任何动作。
- **失效点**：当**只有指标没有动作**时，「展示债务趋势」的优点反转成「汇报工具」——因为曲线下降可以由「把条目关掉」而不是「把债还掉」造成：结转头寸、改分类口径、把一个债拆成三个再关掉两个，都会让曲线变好看。判据是抽查最近一次曲线下降所对应的那批条目，看它们是被修复了，还是被重新归类或关闭。
- **真实使用**：【经验】它是治理层的沟通工具，取值频率通常是季度而非迭代；与 [§ 6.1](06-tech-debt-section-6-sec6.md) 的固定时间预算配套使用时，它回答的是「预算有没有花在利息上」，而不是「预算花了多少」。
- **核验方法**：抽样一次下降，逐个核对条目终态是「已偿还」还是「已关闭 / 已重新归类」。抽查 10 条就足以判断这条曲线是证据还是装饰。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 利息落在单团队内、边界清晰 | Backlog + 顺手重构 | 集中还债月对这类债是过度机制，跨团队协调成本白付 | 修好之后受益方是不是就是出资方 |
| 利息跨团队 / 出资方 ≠ 受益方 | 固定时间预算（受保护）+ 债主制 | 分散偿还解决不了协调成本，加大预算也没用 | 这笔债是否需要多个团队同时投入 |
| 不知道债在哪 | 地图（变更热度 × 复杂度） | 按本金排序的扫描榜会把高利息热点排到中后段 | 报表前 20 条里有多少在过去 6 个月被改过 |
| 想先降低新增速率 | 质量门禁 | 门禁只拦新增，不还旧账；单靠它债务总量不会降 | 误报率与绕行记录 |
| 代码级债、持续降利息 | 重构（每次提交顺手做） | 它完不成架构级本金偿还 | 这笔债能不能在一次提交里完成 |
| 架构级债、要替换核心机制 | 绞杀者模式 | 一次性重写会让旧系统在重写期间继续接需求，目标不断移动 | 新旧能否并存 + 切换能否按流量 / 调用方分批 |
| 新旧不能并存 / 切换点必须收敛 | 抽象分支 | 绞杀要求长期双跑，强一致边界下核对成本不可接受 | 抽象层有没有泄漏旧实现的语义 |
| 要向业务方解释为什么该还 | 利息口径（翻译成业务成本） | 本金口径说的是工程师的工作量，业务方无法判断 | 这笔债过去一个季度多花了多少次改动 |
| AI 应用的债 | 版本可定位 + 评估独立 + 轨迹可查 | 静态规则看不见语义类债；LLM 判定不稳定，不能当门禁 | 模型 / 提示词升级后能否回到上一版并复跑同一套评估 |
| 跨团队、平时没有窗口 | 集中还债月（项目通道） | 日常通道追不上累积速度 | 是否存在需要多团队同时改动的依赖 |

本主题下最常被误选的一对是**「还债 Sprint」与「固定时间预算 + 债主制」**，误选的依据通常是「Sprint 更有执行力、有交付物、能汇报」。但项目通道的容量与需求共享同一个排期池，而收益是延迟的、不可见的——于是需求一紧它先被让出，下一个季度重新累积，再开一次 Sprint。后果不是「债务没降」，而是**以为在治理，实际在复利**：每次组建 Sprint 的组织成本照付，利息却按变更频次持续累积（[§7.3.2](06-tech-debt-section-7-sec7.md) 把这条写成「还债运动总是反复发生」的机制原因）。正确的第一步不是加一个 Sprint，而是先判断这笔债的利息落在谁身上：落在本团队，Backlog 加顺手重构就够；跨团队，才需要组织机制，且这条机制要有 Owner 与保护工时。

### 3.4 组合模式：真实系统不会只用一种

**组合一：象限 + Backlog + 地图**。三件事分工明确：象限回答「这笔债该不该被记录、该被怎么处理」，Backlog 回答「记在哪、谁负责、走哪条通道」，地图回答「先做哪个」。职责边界同样清楚：象限不产生优先级，Backlog 单独存在必然变坟场，地图不产生本金估计。运维代价是前两者靠人维护（登记与盘点成为常设工作）、第三个靠工具跑（版本历史 + 静态分析）。适合任何规模，是起步阶段性价比最高的一组。

**组合二：固定时间预算 + 债主制 + 质量门禁**。预算保证「还债会发生」，债主保证「还对了地方」，门禁降低「新增的速度」——[§7.3.2](06-tech-debt-section-7-sec7.md) 把这组列为公开材料里出现的做法（【公开】Google 以固定时间预算 + 模块 Owner（债主）为核心，目标是「维持可控」而非「清零」，[Google 公开材料 2009-2024]，以官方材料的当前版本为准，见 [§ 6.1](06-tech-debt-section-6-sec6.md)）。职责边界：门禁只拦新的、不还旧的；预算只保证容量、不保证方向。运维代价是固定工时支出（确定性成本）加误报处理成本。适合规模大到「靠自觉」不可行的组织；【经验】团队在 3–5 人量级时，固定比例工时形不成并行，此时更有效的是把顺手重构并进每次改动。

**组合三：绞杀者 + 抽象分支 + 迁移顺序约束**。第三件不是模式，而是一条必须写进方案的顺序约束：先按流量分批（绞杀），遇到无法双跑的强一致边界就改用抽象分支（单切换点），并且在边界内部遵循「先迁读路径、再迁写路径」。职责边界是：绞杀负责把风险切小，抽象分支负责在切不动的地方把切换点收敛到一处，顺序约束负责让两者衔接处不留半新半旧的状态。运维代价是双跑期成本随并存时长线性累积（【推算】每延长一个季度约多付 2.3 人月，见 3.2.6）。适合既有架构级替换、又有强一致事务的系统。

三条组合有一个共同要求：**每一件机制被拿掉时，系统回到什么状态，必须能一句话说清。** 债主离职 → 债回落到团队，等于重新回到无人负责；预算被需求挤占 → 回到「有空再还」；门禁误报率高到被绕过 → 回到无门禁，还多了一层形式。说不清降级形态的机制不该上线——因为它的失效不会报警，只会安静地退回治理之前的状态。

### 3.5 反模式与失效分析

下表 9 条对应原文件的 9 条反模式。四列回答四个不同的问题：**怎么发现它、它按什么机制造成损失、团队为什么会写成这样、改什么。**

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 看不见技术债 | 问「我们欠了多少债」，没有人能回答 | 利息按变更频次复利，且事后无法还原「哪一步开始变慢」 | 只按功能排期，质量没有入口 | 地图 + 定期盘点，用变更热度排序 |
| 无限拖延 | 连续四个季度，债条目总是最后被延期的那几条 | 通道与需求同池，需求收益当期、债收益延迟 ⇒ 必然先做需求 | 没有独立通道，只有意愿 | 固定且受保护的工时预算（持续通道） |
| 过度还债 | 一段时间内功能交付停滞，业务方开始绕过流程 | 把「债务清零」当成目标而不是手段，ROI 变为负 | 把清零当政绩，缺 ROI 口径 | 预算 + 按 ROI 排序，只还「利息高且还会被改」的债 |
| 不知情技术债 | 只有口头的「这块很乱」，没有清单条目 | 排期时债无法摆上桌，等于默认接受持续付息 | 登记是纯成本，收益要等下一轮才出现 | 强制录入，至少覆盖跨团队债与架构级债 |
| 业务方不理解 | 预算审批会上被问「为什么不能先做功能」 | 持续通道批不下来，组织机制缺一块 | 用本金口径（工时）跟业务沟通 | 翻译成利息：这笔债过去一个季度多花了多少次改动 |
| 沉没成本陷阱 | 为一个已经不值得的旧模块持续还债 | ROI 为负的偿还，资源被锁在低收益位置 | 已经投入了，不愿承认 | 按「利息 ÷ 本金 × 这段代码还会不会被改」评估 |
| AI 债忽视 | 模型 / 提示词改了，但没人跑回归 | 效果静默退化，且版本不可定位、无法回滚 | AI 债不在代码扫描的视野里，没有现成 lint 规则 | Prompt / Model Registry + Eval Pipeline + 轨迹落盘 + 漂移监控 |
| 不量化 | 所有债都是「高 / 中 / 低」，无法排序 | 优先级退化成拍脑袋，高利息热点排不到前面 | 量化成本高、口径难统一 | 两口径并用：本金用修复人时，利息用变更热度 × 复杂度 |
| 无 Owner | 清单上有一批条目半年没有人动过 | 债没有「谁该处理」的答案，就谁都不处理 | 登记时只填描述不填人 | 每条必须有具体到人的 Owner，并定义 Owner 变更时的转移规则 |

四类最危险的反模式值得单独说。**「无限拖延」与「过度还债」是一对镜像**，都不是执行力问题：前者是通道设计问题（还债与需求共享同一个池子），后者是目标设定问题（把「清零」当成目标）。公开材料把这类机制的目标写成「维持可控」，正是因为清零在经济上不成立——债务本金与利息的比较才是判据，而这条判据只有在「这段代码还会不会被改」这个量被算进去之后才有意义。

**「不量化」危险在它会被一种看起来更专业的做法替换掉**：改用工具的债务比率与修复工时。这类口径度量的是**本金**，因此系统性偏向容易修的东西——能自动识别、能算出工时的条目排在榜单前面，而「没有 Owner 的宽表」「口径不一致的指标表」因为算不出修复工时，权重接近零；团队随后会得出「扫描出来的东西都不重要」的结论，而真实原因是口径选错了。**「AI 债忽视」危险在它的利息形态不同**：代码债的利息是「改得慢」，AI 债的利息是「效果静默退化」——后者不报错、不阻塞提交、不在任何代码扫描的视野里，只有在有独立 ground truth 的评估集上才会显形，所以它比其他任何一类债都更依赖登记与评估，而不是依赖工具自动发现。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单团队 → 多团队共用同一块资产 | Backlog（团队内） | 出资方与受益方不是同一方，该团队没有动力还 | 固定时间预算 + 债主制 | 需要有人维护债主清单与预算执行记录 |
| 口头 → 有清单、能排序 | 无 / Backlog | 排期时债摆不上桌；全是「高 / 中 / 低」无法排序 | Backlog + 地图 + 双口径量化 | 登记与盘点成为常设工作；要跑版本历史并定义复杂度口径 |
| 偿还追不上新增 | 分散偿还 | 偿还速率低于产债速率，清单只增不减 | 质量门禁（先降产债速率），再谈偿还 | 误报处理成为常设成本 |
| 代码债 → 架构债 | 重构 | 重构改不了架构机制，本金偿还不了 | 绞杀者 / 抽象分支 | 双跑期成本随并存时长累积（每季约 2.3 人月【推算】） |
| 门禁 → 门禁 + 候选池 | 仅规则门禁 | 语义类债规则写不出来，而 LLM 输出又不稳定 | 规则做判定、LLM 只进候选池 | 复核时间成为常设成本 |
| 无 AI → 有 AI 应用 | 门禁 + Backlog | AI 债没有 lint 规则，利息表现为效果静默退化 | Prompt / Model Registry + Eval Pipeline + 轨迹落盘 | 评估集与监控成为常设投入 |
| 集中还债月 → 常态化 | 集中还债月 | 脉冲式偿还之后，债务以相近速率重新累积 | 持续通道 + 门禁 | 需要把固定比例写进排期制度并提供保护 |

跃迁表里有两条贯穿全部行的约束。其一是**任何一次「换度量口径」的迁移都会让历史曲线作废**：燃烧图的 Y 轴从本金换成利息、或从修复工时换成变更热度，前后两个点就不再可比，团队因此失去「机制有没有效果」的唯一长期证据——工程上的做法是把「口径定义 + 统计范围 + 复杂度算法版本」作为一个整体冻结并打版本号，换口径时整组替换并保留一段新旧双轨期。其二是**迁移必须先在存量数据上算一遍，再改制度**：因为治理机制的收益不报错，「新机制更好」只能在你自己的数字上被证明，可操作的做法是先按新口径把历史数据重算一遍（通常只需一次版本历史扫描），再决定是否改通道、改阈值。

### 3.7 自检清单

- [ ] 问「我们欠了多少债」，能不能给出一个数，并说清它的口径是本金还是利息？答不出＝债不在任何清单里。
- [ ] 清单上每一条是否都有具体到人的 Owner 与所属通道（持续 / 项目）？
- [ ] 过去四个季度里，「技术债」条目实际被完成的次数是多少？（数出来，不靠印象）
- [ ] 最近一次曲线下降所对应的条目，是真的被修复了，还是被重新归类 / 关闭了？
- [ ] 扫描报表前 20 条里，有多少在过去 6 个月被改过？多数是 0 次 → 这是本金榜，不是利息榜。
- [ ] 这笔债的出资方与受益方是不是同一个团队？不是 → 分散偿还解决不了它，需要组织机制。
- [ ] 这笔债能不能在一次提交里完成？能 → 走重构，不必立项；不能 → 走新旧并存的分批替换。
- [ ] 要替换的东西，新旧实现能否并存、切换能否按流量或调用方分批？有一个不能，就要准备单点切换与回退预案。
- [ ] 门禁的判定依据是「同一输入同一结论」的规则，还是概率模型的输出？后者不能单独作为判定。
- [ ] 门禁的误报率是多少？有没有观察到绕行记录？
- [ ] 模型 / 提示词升级后，能不能回到上一版并复跑同一套评估？
- [ ] 评估集的 ground truth 是人工标注 / 业务规则，还是被测链路自己产出的？

这 12 条里，第 1–5 条是**可见性项**（决定债能不能被排上），第 6–7 条是**归属与手段项**（决定谁来还、用哪种手段），第 8–10 条是**替换与门禁项**（决定风险能不能被控住），第 11–12 条是**AI 债项**（决定退化能不能被发现）。可见性项性价比最高：它们大多只需要翻一次排期记录或跑一次历史扫描，却能一次性回答「我们到底在治理还是在复利」。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 债在单团队内、边界清晰 | Backlog + 顺手重构 | 利息与偿还都由同一方承担，日常通道足够 |
| 出资方 ≠ 受益方 | 固定时间预算（受保护）+ 债主制 | 跨团队债的瓶颈是协调成本，不是工时 |
| 不知道债在哪 | 地图（变更热度 × 复杂度） | 乘了变更频次之后，高利息热点才排得上来 |
| 债列了但没人做 | 给每条补 Owner 与通道 | 与需求同池竞争的条目，没有主就一定输 |
| 新增快到追不上 | 质量门禁（先降产债速率） | 门禁只拦新增、不还旧账，但要配还旧账的机制 |
| 代码级债、持续降利息 | 重构 | 它完不成架构级本金偿还 |
| 架构级债、要换核心机制 | 绞杀者 / 抽象分支 | 新旧并存 + 分批切换，把单次风险切小 |
| 强一致边界不能双跑 | 抽象分支 + 先读后写的迁移顺序 | 单切换点，避免半新半旧的长期状态 |
| 要向业务方解释 | 利息口径 | 本金口径说的是工程师工作量，业务方判断不了 |
| 有 AI 应用 | 版本可定位 + 评估独立 + 轨迹可查 | AI 债的利息是效果静默退化，只有独立评估能看见 |

> 本节小结：本节 10 个模式之间没有「谁更先进」，只有「谁对应你现在的约束」——**决定这一切的唯一那条约束是「利息落在谁身上」**，它划出「日常通道够不够」这条边界；边界之内，二次筛选由**债务类型决定手段可行性**（能不能切碎）与**度量口径决定榜单偏向**（本金还是利息）这两件事决定。Sprint 与预算的取舍、绞杀与重写的取舍、门禁与重构的取舍，都是这条链条的下游结果；顺序反了，讨论就会永远停在「这个季度有没有时间还债」。
