## 7. 与其他方法对比

> 原 § 7 共 48 行、为打分表 + 决策树，缺少机制解释与可溯源证据，重写为 ~320 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

原文件把「不管理 / Tech Debt Map / SQALE / Strangler Fig / AI 辅助」五者按 6 个维度打了 1–5 分，其中「不管理」在团队接受度上拿 5 分（因为没人反对），「AI 辅助」在识别能力与 AI 友好度上各拿 5 分，于是 AI 辅助排序最高。问题不在分数，而在这张表把**作用于不同环节的东西放进了同一排**：Tech Debt Map 与 SQALE 解决「债务在哪、有多重」（识别与量化），Strangler Fig 解决「怎么把旧实现换掉」（偿还手段），不管理是一个默认状态，AI 辅助是一台加速器。识别得再准也不能替你还债——原表算出的排序因此无法执行。

第二个问题是**维度不可加**，且在技术债这个主题上格外严重：「团队接受度」不是一种收益，它是一类约束。不管理拿 5 分的意思是「没有任何人反对」，而它同时意味着「没有任何人负责」——在技术债里，无人负责正是债务持续累积的直接原因（§6.1 的 Google 案例把这个因果写得很清楚：债务没有归属，于是谁都不还）。把「接受度高」当成加分项，等于把危害当资产计入总分。

第三个问题是**度量本身是估算**，而打分表掩盖了这一点。修一个重复代码块所花的人时是可测的；「因为耦合严重，每次改需求多花两天」是估算——它取决于改的是什么需求、谁在改、当时的上下文。因此本主题上所有量化方法（SQALE、债务/开发成本比率、利息模型）的输入都是**同一批不可靠的估算**。这带来一个硬结论：这些方法能用来**排序**（哪笔债在同类里更贵），不能用来**比较绝对值**（「我们欠了 380 万」这种数字的精度低于它的说服力，还会引来「那我们把它加进预算表里」的错误用法）。

第四个问题是**阈值凭空来**。原决策树写「大型遗留 → Strangler Fig / Branch by Abstraction」「小型遗留 → 直接重构」，但没有定义大小。真正决定偿还手段的不是代码量，而是两件可观测的事实：**新旧实现能否并存**（数据格式与协议是否允许双写双读）、以及**切换能否按流量或按调用方分批**。一个 30 万行的单体只要接口边界清晰就能分批绞杀，一个 3 千行的核心链路如果协议必须一次性切换，也只能停机冻结——「大 / 小」这个变量在这两种情形里给出的答案恰好相反。本章的做法是：决策树的每个节点只问可观测的事实（这笔债是利息还是本金、新旧能否并存、有没有 Owner），阈值一律在树下给出推导链。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 利息 / 本金 | 这笔债是每天付息（拖慢变更），还是一次性本金（架构替换） | 决定走持续通道还是项目通道——两者不能互相替代 |
| 变更热度 | 这段代码每个迭代被改动几次 | 决定先还哪笔：不热的代码即使本金很大，利息也接近 0 |
| 归属 | 这笔债有没有具体 Owner | 无主债务不会被还；这一条先于任何工具选型 |
| 可分批性 | 新旧能否并存、切换能否按批推进 | 决定偿还手段：能分批走绞杀，不能分批只能冻结切换 |
| 度量口径 | 度量的是修复成本（本金）还是持续损失（利息） | 决定排序结果系统性偏向哪一类债务 |
| 可验证性 | 还完之后能否证明「债确实减少了」 | 决定下一笔还债预算能不能获批 |

这些候选分五**族**：**族 1 策略型**（不管理 / Tech Debt Backlog）决定「记不记」；**族 2 度量与定位型**（四象限 / Map / SQALE / 热点分析 / Budget / Burndown）决定「哪笔先还」；**族 3 偿还手段型**（重构 / 绞杀者 / 抽象分支 / 一次性重写）决定「怎么还」；**族 4 组织机制型**（质量门禁 / 还债 Sprint / 时间预算 + 债主制）决定「谁还、什么时候还」；**族 5 AI 债**（Prompt / 模型 / Agent 债的治理）是债的**形态**变了，不是新方法。AI 辅助不属于任何一族——它改变的是「谁生成候选与草案」。

**族 2 与族 4 必须配对**，这是本主题与一般选型最大的不同：只买族 2 的工具（扫描器、仪表盘、比率报表）而不建族 4 的机制（Owner、受保护的工时、门禁），结果一定是**台账变成坟场**——条目越积越多、优先级每月重排、实际偿还量接近零。原文件把它们列成两个可比较的选项，掩盖了这层依赖。

### 7.3 机制差异：为什么它们表现不同

#### 7.3.1 度量口径：修复成本（本金）还是持续损失（利息）

**机制是什么**：技术债的量化方法几乎都建立在「成本」这个词上，但成本有两种：一次性偿还的**本金**（修复需要多少工时）与持续付出的**利息**（因为这段代码难改，每次变更多花多少时间）。选哪种口径，决定了排序结果系统性偏向哪一类债务。

**实现差异**：

| 候选 | 计量单位 | 偏向暴露的债 | 对哪些债近乎失明 |
| --- | --- | --- | --- |
| SQALE / Tech Debt Ratio | 修复人时（本金），按问题类型加权 | 重复代码、高复杂度函数、缺测试的可测问题 | 无 Owner、口径不一致、无血缘等没有「修复工时」的债 |
| Tech Debt Quadrant | 定性分类（刻意 / 无意 × 鲁莽 / 谨慎） | 需要沟通与复盘才能看清的决策类债 | 不产生优先级，纯排序 |
| 热点分析（热度 × 复杂度） | 变更次数 × 复杂度（利息代理量） | 每天都在被改的复杂文件 | 长期不动但一旦要改就很痛的高本金模块 |
| 债务本金 / 利息（§2.1 口径） | 本金 + 利息分开估 | 两者都可表达 | 利息估值本身是估算，精度取决于改动记录 |
| Tech Debt Budget / Burndown | 趋势（债务随时间的增减） | 机制是否有效（债有没有被对冲） | 单笔债务的优先级 |

**由此必然导出的性质**：因为 SQALE 的计量单位是**修复工时**，所以它度量的是本金而不是利息，因而**系统性偏向「容易修的东西」**：能自动识别、能算出工时的规则命中项会排在榜单前面，而「没有 Owner 的宽表」和「口径不一致的指标表」因为算不出修复工时，在这类工具里权重接近零。因为技术债真正的痛几乎全部来自利息（每天拖慢交付），所以按本金排序的榜单会把**利息最高、最容易改**的热点文件排到中后段——这是「扫描报告第一屏的东西总是没人觉得重要」的机制原因，不是团队不重视治理。反过来，因为热点分析把「变更频次」乘进排序，所以它天然优先暴露「利息正在被支付」的位置，代价是它完全看不见那些「现在不动、一旦要动就是大工程」的高本金模块——**两类方法看到的是两种债务，不是同一张清单的两个视角**。

把两种口径放在一起，就得到本主题的 ROI 定义：**ROI = 单位时间被省下的利息 ÷ 一次性修复本金**（主文件 §2.2 给的是同一条式子的年度化写法）。这个定义直接解释了「按本金排序」错在哪：榜单只优化分母（挑修复人时小的先做），而分子的变化取决于**这段代码还会不会被改**——同一笔债放在高频变更模块里与放在三年不动的模块里，分母相同、分子差一个量级，ROI 因此相差一个量级。所以「这笔债值不值得还」在本主题里不是一个可以只算一边的问题（下一节 §7.4 给出这两个量的输入项）。

**公开证据【公开】**：SQALE 方法由 Jean-Louis Letouzey 于 2012 年在技术债管理国际研讨会（MTD, 2012）上系统提出，SonarSource 官方文档把 Technical Debt 定义为修复成本、把 Technical Debt Ratio 定义为债务与开发成本的比值（SonarSource 官方文档）；「变更热度 × 复杂度」的定位方法由 Adam Tornhill 在《Your Code as a Crime Scene》（2015）中系统化。判定方法：打开你手上的扫描报表，看它是否对「缺少 Owner」「指标口径不一致」这类条目给出工时——如果一张清单上全是可自动计算工时的条目，那就是本金口径，需要用变更热度补一层利息排序。

**失效条件**：当代码库本身很新、变更分布均匀时，热点分析的区分度下降（所有文件的变更次数差不多），此时它退化成按复杂度排序；当团队没有可靠的版本历史（大量改动绕过评审直接提交、或最近才迁移到版本控制）时，热度数据不可用，只能退回静态规则口径。

#### 7.3.2 偿还通道：持续对冲 vs 项目制一次性

**机制是什么**：还债的**通道**决定它能否真的发生。通道有两种：常设的持续通道（有固定、被保护的工时）与项目通道（专门的迭代或立项，有起止时间）。

**实现差异**：

| 候选 | 通道 | 谁决定优先级 | 失败模式 |
| --- | --- | --- | --- |
| 不管理 | 无 | 无人 | 「有空再还」，一年下来「有空」从不出现 |
| Tech Debt Backlog | 与需求同一个排期通道 | 产品 / 项目经理 | 债务条目永远排在需求后面，清单只增不减 |
| Tech Debt Sprint | 项目通道（有起止） | 有排期权的角色 | 冲一次就完，之后快速重新累积 |
| 集中还债月 | 项目通道（批量） | 管理层 | 平时累积、集中清理，形成「债务脉冲」 |
| 时间预算 + 债主制 | 持续通道（比例固定且被保护） | 债主（模块 Owner） | 若无债主与清单，预算被浪费在顺手的地方 |
| Quality Gates | 防新增（与偿还无关） | 门禁规则 | 只拦新的，旧的继续累积 |
| Burndown / Budget | 度量通道效果 | 治理层 | 只有指标没有动作时，曲线会成为汇报工具 |

**由此必然导出的性质**：因为项目通道的容量是有限的、且**与需求竞争同一个排期池**，所以「还债 Sprint」的成功与否取决于当期需求压力——需求一紧，Sprint 首先被让出，债务随即回到累积状态；这也是「还债运动」总是反复发生的原因（不是团队不努力，而是通道设计使它必然反复）。因为持续通道把还债设为**与需求并行的固定预算**（Google 的公开做法是划出固定比例且不允许需求随意挤占，见 §6.1），所以它把失败模式从「不还」变成「还错地方」——后者的代价小得多，且可以用清单与 Owner 修正。反过来，因为**架构级债务无法切成碎片**（替换存储格式、替换消息中间件都要一次协调好的切换窗口），所以它必须走项目通道，靠 20% 时间慢慢磨会得到「一半新一半旧、且两边都在改」的最差状态。**通道按债务类型分配，而不是按团队习惯分配**。

**公开证据【公开】**：Google 的公开材料描述了以固定时间预算 + 模块 Owner（债主）为核心的还债机制，明确的目标是「维持可控」而非「清零」（[Google 公开材料 2009-2024]，整理见 §6.1）；Meta 的 Fiber 重构是「不停业务前提下完成架构级偿还」的公开案例（[Meta 公开材料 2017-2024]，见 §6.2）；字节的跨业务渐进迁移则展示了项目通道如何被拆成可分批、可回退的批次（[字节公开材料 2019-2024]，见 §6.3）。可自行核验：翻你们过去四个季度的排期记录，数一数「技术债」条目实际被完成的次数——如果它总是排在每季度最后被延期的那几条里，说明通道设计有问题，不是执行力问题。

**失效条件**：持续通道在团队规模很小（3–5 人）时会失效——固定比例工时在少量人手上无法形成「并行」，此时更有用的做法是**在每次改动里顺手做小重构**（把还债并入需求的能力），而不是划出一个独立预算。另外，若债务累积速度长期高于偿还速度（除了补充原来需求还在持续产债），任何通道都会被淹没：这时该先修**产债来源**（门禁、评审、Owner 缺失），而不是加大偿还预算。

#### 7.3.3 偿还动作的可分批性与可回退性

**机制是什么**：四种偿还手段（原地重构 / 绞杀式替换 / 抽象分支 / 一次性重写）的差异不在「激进程度」，而在两个机制变量：**新旧实现能否并存**，以及**切换能否按批推进**。这两个变量共同决定了单次切换的风险与双跑期的成本。

**实现差异**：

| 候选 | 新旧是否并存 | 切换粒度 | 可回退性 | 双跑期成本 |
| --- | --- | --- | --- | --- |
| Refactoring（原地重构） | 不是替换，是持续修改 | 每次提交 | 每次提交可回退 | 无 |
| Strangler Fig | 并存（长窗口） | 按流量 / 按调用方分批判 | 每批可独立回退 | 高（并存期内两套运维 + 一致性核对） |
| Branch by Abstraction | 并存（切换点集中） | 一次性切换，但切换点只有一处 | 切换点可回退 | 中（并存期内维护一层抽象） |
| 一次性重写 | 不并存 | 一次性整体切换 | 切换后不可回退（只能回滚整个系统） | 无（但风险集中在一次切换） |

**由此必然导出的性质**：因为绞杀式替换的切换点是按批推进的，所以每一批都能独立验证、独立回退，单批失败的影响面被限制在那部分流量上；但正因为它要求新旧长期并存，双跑期的运维成本与一致性核对成本会持续整个迁移窗口——**分批降低的是单次风险，抬高的是总成本**，两者是同一机制的两面。因为一次性重写把切换点压缩成一次，所以它省掉了双跑期，却把全部风险放进同一次切换，并且引入一个更常见的杀手：**旧系统在重写期间继续接需求**——目标不断移动，重写永远追不上，最终既没有新系统也没有可维护的旧系统（Netscape 的重写是公开的经典案例：Joel Spolsky 在 2000 年的文章中把它作为「不要重写」的论据【公开】）。因为原地重构的切换粒度是每次提交，所以它的风险最低但上限也最低：它能持续降低利息，却**无法完成架构级的本金偿还**——这类债需要一次「新旧并存 + 分批切换」的项目，重构帮不上。

**公开证据【公开】**：绞杀者模式由 Martin Fowler 命名（martinfowler.com, 2004），其原始动机正是「让替换过程可分批、可随时停下」；Branch by Abstraction 是同一家族的模式，做法是把切换点收敛到一处抽象层，从而避免「一半调用方走新路径、一半走旧路径」的长期混乱（来源：martinfowler.com 该模式页面）。判定方法：问自己两个问题——新旧实现能否同时存在（数据格式与协议是否允许双写双读），以及切换能否按流量或调用方分批。两个都「能」，绞杀是默认选项；有一个「不能」，就要走抽象分支或一次性切换，并提前准备好回退预案与冻结窗口。

**失效条件**：当被替换的部分是**强一致边界**（同一笔事务跨新旧两套实现）时，并存期的核对成本会高到不可接受，此时绞杀式替换应改为「先迁移读路径、再迁移写路径」，或者干脆把该边界收进一套新实现；如果替换的动机是合规或安全（旧实现不能被继续运行），那么双跑期本身就是违规的，只能走冻结窗口一次性切换。

#### 7.3.4 识别来源：静态规则、变更热度，还是模式生成

**机制是什么**：识别手段决定了「找到的是哪一类债」——这是决定治理动作的第一步，也是 AI 辅助唯一能实质改变的一步。

**实现差异**：

| 识别来源 | 输入 | 找到的债 | 输出稳定性 | 能否直接进门禁 |
| --- | --- | --- | --- | --- |
| 静态规则（Quality Gates 类） | 代码本身 | 规则定义的代码结构问题 | 高（同一输入同一结论） | 能（阈值可配） |
| 变更热度 | 版本历史 + 复杂度 | 每天在被改的复杂代码（利息型） | 高 | 不建议（排序不是判定） |
| 人工盘点 / 债主登记 | 人的判断 | 工具看不见的债：口径、Owner、数据债 | 中（取决于人） | 不能 |
| AI 辅助（LLM 识别） | 代码 + 上下文 + 自然语言描述 | 静态规则写不出的语义类问题（命名误导、注释与行为不符、Prompt 硬编码） | 低（同一输入可能给出不同结论） | 不能（只能进候选池） |
| AI 辅助（AI Code Review） | 变更 diff | 新引入的问题 | 中 | 能（作为门禁的一部分，不单独作为判定） |

**由此必然导出的性质**：因为静态规则的输入只有代码、不含使用频次，所以它会把一座八年没人改过的三千行旧模块排在**每天都被改的热点文件**前面——前者本金大、利息接近零，后者本金小、每天都在付息。因为热点分析把变更次数乘了进去，所以它优先暴露「利息正在被支付」的位置，这正是 §7.3.1 所说的口径互补关系的来源。因为 LLM 是基于上下文的**概率生成器**而不是判定规则，所以它能覆盖静态规则写不出的语义问题（这一点在 AI 应用的债上尤其重要：Prompt 硬编码、模型没有评估、Agent 没有监控，这些都没有现成 lint 规则），但它的输出不稳定——同一段代码问两次可能得到不同结论，因此它只能进候选池，**不能作为门禁的判定依据**；门禁需要的是「同一输入同一结论」这个性质，而这恰是概率生成器不具备的。

**公开证据【公开】**：Cunningham 在 1992 年的 OOPSLA 经验报告里提出技术债隐喻（OOPSLA, 1992），其原始语境正是「为快速交付而做出的、需要被记住的妥协」——即债需要**被登记**，而不是被自动发现；Fowler 后来用四象限区分刻意与无意（martinfowler.com 的《TechnicalDebtQuadrant》一文；该文的确切发布年份未能回查核对，故此处不写死年份），指出无意产生的债往往连当事人自己都不知道存在。判定方法：取你扫描报表里排名前 20 的条目，逐条标「这段代码在过去 6 个月被改过几次」——如果多数是 0 次，说明你拿到的是本金榜而不是利息榜。

**失效条件**：当代码库缺少可读的语义线索（脚手架生成、宏密集、领域缩写严重）时，LLM 的语义识别质量下降；当团队的提交习惯不规范（大量批量提交、force push、把多个改动静默合并）时，变更热度失真，此时热度排序与随机排序无异——先修提交习惯，再谈热点分析。

**四条机制维度的对照速查**（每行给出机制依据，而不是打分）：

| 候选 | 度量口径 | 偿还通道 | 可分批性 | 识别来源 | 由机制导出的最短结论 |
| --- | --- | --- | --- | --- | --- |
| 不管理 | 无 | 无 | — | 无 | 原型期合理；增长期是「赌债务累积速度低于扩张速度」 |
| Tech Debt Quadrant | 定性分类 | 无（沟通用） | — | 人工 | 解决「这笔债该不该被记录」，不产生优先级 |
| Tech Debt Backlog | 无（条目） | 与需求同池竞争 | — | 人工 / 扫描导入 | 单独存在必然变成坟场，需配 Owner 与通道 |

### 7.4 成本结构对比（不是价格表，是成本函数）

技术债没有「单价」可比：同一笔债在不同团队里的利息差一个量级（取决于这套代码被改多频繁），同一套工具在不同组织里的落地成本也差一个量级（取决于有没有 Owner 机制）。可比较的是**成本函数的形式**。

```
总成本 ≈ 识别成本（扫描 / 盘点，接近固定）
        + 利息 = 债务规模 × 利息率 × 时间 × 变更频次
        + 本金 = 一次性修复人时（阶跃式）
        + 双跑期成本 = f(并存时长) × (并行运维 + 一致性核对)
        + 常设机制成本 = 受保护的工时预算 + 门禁误报处理
        + 决策错误成本（本金付了但利息没降）
```

这个成本函数同时就是 §7.3.1 那条 ROI 式的输入：分子是利息项（债务规模 × 利息率 × 时间 × 变更频次），分母是本金项（一次性修复人时）。三项里只有**变更频次**是可实测的，利息率是【经验】比例常数——把变更频次这一项拿掉，ROI 就退化成「谁好修谁先修」，这正是本金口径榜单的失败机制。

**各族的成本主导项与隐性成本**：

- **族 1（策略型）**：主导项是 0（不记就没成本）；隐性成本是利息按变更频次复利，且事后无法还原「哪一步开始变慢」。
- **族 2（度量与定位）**：主导项是工具与报表维护；隐性成本是**度量口径决定了榜单偏向**（按本金排序会让高利息热点排在后面），以及清单越积越厚带来的信噪比下降。
- **族 3（偿还手段）**：主导项是本金；隐性成本是双跑期（绞杀 / 抽象分支）或一次切换的失败风险（重写）。
- **族 4（组织机制）**：主导项是受保护的工时预算（这是**确定性支出**）；隐性成本是门禁误报带来的绕行行为——门禁的可信度取决于误报率，误报多到一定程度，团队会学会绕过它，此时它从机制退化成形式。
- **族 5（AI 债）**：主导项是评估与监控的常设投入；隐性成本是「模型版本升级后没有回归集」——这类债的利息不是代码变慢，而是**效果静默退化**。
- **AI 辅助（跨族）**：主导项是草案复核时间；隐性成本是把复核省掉的那部分（见 §7.7 反模式）。

**【推算】持续通道的规模**：设团队 8 人、把 20% 时间划给还债（与 §6.1 的公开实践同量级），按每年 50 个有效工作周推算：8 × 20% × 50 = 80 人周/年，约合 18–20 人月/年。这个数字的用途不是「预算本身」，而是**对照物**：任何要求占用这笔工时的需求，都是在和「每年减少约 20 人月的持续拖累」竞争——把这个量级摆到桌上，讨论才会从「有没有时间」变成「哪一件更值」。

**【推算】热点分析的上限收益**：若某仓库的变更高度集中在少数文件（多数组件都如此，但集中度必须自测），那么把还债资源投向变更频次排名前 10–20% 的文件，能覆盖相当比例的「每天都在付息」的位置。**不要照搬任何一个百分比**：判定方法是用你的版本历史跑一次「变更次数 × 复杂度」，看前 10% 的文件覆盖了全部变更的多少比例——你自己跑出来的那个数，才是这次排序的依据。

**【推算】双跑期成本**：设两张实现（旧策略引擎 + 新策略引擎）并存 6 个月（26 周），期间每周 0.5 人维护旧实现 + 0.25 人做一致性核对，则约 26 × 0.75 ≈ 20 人周，按每月 4.33 周折算约 4.6 人月（【推算】，系数按你团队实际情况替换）。推导链是「并存周数 × 每周并行成本」；把同一个系数用到季度尺度上：13 × 0.75 ≈ 10 人周 ≈ 2.3 人月，也就是**并存时间每延长一个季度，就多付约 2.3 人月的成本**——这是「绞杀式替换要尽快把旧实现下线，而不是『留着做备份』」的定量理由。

**【经验】关于量化档位**：主文件 §2.2 引用的债务比率档位（如 20% 以上被判为高风险）与利息率常量，都属于**工具默认值与团队习惯的常见取值，不是行业标准**。SonarQube 一类工具的门槛是可配置项，判定方法是查你自己的 Quality Gate 配置里那次判定用的具体门槛，并追问「这个门槛是谁定的、依据是什么」。同样地，各类调查报告给出的「开发者有多少时间花在技术债上」的百分比，口径差异很大（是否含维护、是否含会议），不应当作可比较的精确值；本章因此只用它们作量级信号，不给具体百分比。

### 7.5 决策树（每个分支都要有阈值依据）

```
第 0 问（硬约束，先问）：这笔债是否已经造成不可接受的业务风险？
│    （数据算错、安全暴露、合规违规、资金链路受影响）
├─ 是 → 立即偿还；它不属于「优先级排序」问题
└─ 否 ↓
第 1 问：这笔债是「利息型」还是「本金型」？
│    （利息 ≈ 债务规模 × 利息率 × 变更频次；把「每迭代被改动的次数排名」与「修复人时」都列出来做交叉）
├─ 高频变更 + 高复杂度（利息型：变更频次显著大于 0，每天都在付息）
│    └─ 走持续通道：划出 10–20% 的受保护工时 + 债主制 + 原地重构（第 3 问立 Owner 是前提）
└─ 一次性架构替换（本金型，如换存储格式 / 换消息中间件）
     └─ 走项目通道 ↓
第 2 问：新旧实现能否并存？
├─ 能 → 能否按流量或按调用方分批切换？
│        ├─ 能 → 第 2b 问：并存期能否压在一个季度以内？
│        │        ├─ 能 → Strangler Fig（按批推进，每批独立回退）
│        │        └─ 不能 → 先把批次拆小、给每批写下线日期；拆不动则改用 Branch by Abstraction
│        └─ 不能（切换点只有一处）→ Branch by Abstraction
└─ 不能（强一致边界 / 合规要求旧实现必须停）→ 冻结改动窗口 + 一次性切换 + 回退预案
     ↓
第 3 问：这笔债有具体 Owner 吗？（在任何工具选型之前问）
├─ 无 → 先立债主制；无主债务不会被还，与用什么工具无关
└─ 有 ↓
第 4 问：债的形态是哪一类？
├─ 代码 / 架构 / 数据 / 基础设施债 → 按上面选定的族 3 手段执行
└─ AI 债（Prompt 硬编码 / 模型无评估 / Agent 无监控）→ 独立清单 + 版本化 + 回归评估集
     ↓
第 5 问（并行，非替代）：是否用 AI 加速识别与重构？
└─ 生成候选池与重构草案；优先级由人定；AI Code Review 只作为门禁的一部分
     ↓
第 6 问（只在需要对外汇报债务水平时才问）：要不要把它做成一个数字？
└─ 要 → 用「债务 / 开发成本」比率做**本项目**的趋势指标（纵向），不做跨项目排名、不进财务报表；
        折算成金额的货币化模型不在本章覆盖（见下方「刻意不覆盖的分支」）
```

**阈值依据**（按树的顺序，逐一对应树上的判断节点）：

- **「不可接受的业务风险」（第 0 问）**：无阈值，是硬约束。判定标准是「如果这件事明天被审计或客户发现，是否需要立即停机处理」——若是，它就不该和「代码有点乱」排在同一个清单里。
- **「高频变更」（第 1 问的利息型分支）**：取版本历史里变更次数排名**前 10–20%** 的文件（【经验】档）。这条阈值刻意不给固定分位，因为集中度因仓库而异；可操作的做法是跑一次 churn × complexity 排序，取排序曲线的拐点（还能明显高于平均的那一段）作为阈值，并记录这个阈值是怎么选的，便于下次复用。
- **「利息率」（第 1 问判定式里的常量，主文件 §2.2）**：【经验】档。它没有单一权威来源，用途仅限于同量级比较；判定式里真正有区分度的是**变更频次**（可实测），利息率只是一个把利息折算成工时或金额的比例常数。用它算出来的金额不应进入财务报表——如果某个模型要求你输入一个精确的利息率才能运行，那这个模型输出的是说服力而不是信息。
- **「时间预算 10–20%」（第 1 问的持续通道分支）**：【经验】档，与 §6.1 引用的公开实践（20% 时间）同量级。比例应与**债务累积速度**匹配：如果累积长期快于偿还，先修产债来源（门禁、评审、Owner 缺失），而不是继续加大预算——加大预算去追一个持续扩大的缺口，是典型的通道误用。
- **「新旧能否并存」（第 2 问）**：无阈值，是机制约束——它由数据格式与协议决定（能否双写双读），不是可以被优先级调整的量。
- **「并存期 ≤ 一个季度」（第 2b 问）**：由 §7.4 的双跑期成本推算反推（每周 0.75 人的并存成本 × 13 周 ≈ 10 人周 ≈ 2.3 人月），并结合一个组织事实：并存期需要覆盖至少一个完整的对账 / 发布周期（【经验】），否则核对不出问题。两者相交把量级定在「一个季度」附近。
- **「债务 / 开发成本」（第 6 问）**：【经验】档，工具默认值与团队习惯的常见取值（主文件 §2.2 记的 20% 一档即属此类），不是行业标准。它只适合用作**趋势指标**（同一项目纵向对比），不适合跨项目横向排名。

第 3、4、5 问是机制约束与形态判定，没有可调阈值，因此不给依据——它们只能被满足，不能被调参。

**这棵树刻意不覆盖的分支**（以及为什么）：

- **「要不要把技术债清零」**：不覆盖，因为答案是否定的——公开实践的目标是维持可控而不是清零（§6.1）；把它设成目标会导向一次性运动式还款，随后快速重新累积。
- **「要不要给技术债做货币化模型」**：多数组织缺少可靠输入（利息是估算、折现率是自由参数），估出来的数字精度低于它的说服力，反而抬高沟通成本。只有当组织已经在用货币化语言做决策（例如已在上线 TCO 报表）时，它才值得做。
- **「用什么工具扫」**：工具差异远小于口径差异。先决定你要的是本金榜还是利息榜（§7.3.1），再选工具；反过来做，会让工具的口径替你决定优先级。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因（机制层面） |
| --- | --- | --- | --- |
| 高频变更的复杂文件（利息型） | 热点分析定位 + 原地重构 | SQALE 榜单 | SQALE 按本金排序，会把这类排在后面 |
| 一次性架构替换（本金型） | Strangler Fig | Branch by Abstraction | 20% 时间慢慢磨会得到「一半新一半旧且两边都在改」 |
| 需替换的部分不能按流量分批 | Branch by Abstraction | 一次性重写 | 重写省双跑期但要求旧系统冻结改动，通常做不到 |
| 强一致边界或合规要求旧实现停机 | 冻结窗口 + 一次性切换 + 回退预案 | 绞杀式（若能先拆读路径） | 双跑期本身就是违规或不可核对 |
| 缺少 Owner 的宽表 / 口径不一致 | 先立债主制 | 任何扫描工具 | 无主债务不会被还，工具只会让清单更长 |
| 新债持续产生（还没开始还） | Quality Gates | 加大还债预算 | 偿还追不上新增时，预算会被缺口吞掉 |
| 多团队、长期累积 | 时间预算 + 债主制（持续通道） | 集中还债月 | 项目通道与需求争排期，需求一紧先被让出 |
| 债务形态是 Prompt / 模型 / Agent 债 | AI Tech Debt 治理（版本化 + 评估 + 监控） | 传统扫描工具 | 这类债没有现成 lint 规则，扫描器看不见 |
| 想让还债进度可见 | Burndown + Debt Budget | 单次扫描报告 | 没有趋势指标时，治理效果无法被验证也无法重复获批 |
| 探索期、要快速找债在哪 | LLM 生成候选池 + 人定优先级 | 无 | 直接采信 LLM 结论＝吸收一个不稳定输出 |
| 小团队（3–5 人） | 把还债并入每次需求的小重构 | 独立还债 Sprint | 人手不足时无法形成并行通道，固定预算会被挤掉 |

**常见组合**（每条注明职责边界与维护代价）：

- **热点分析 + SQALE 类扫描 + 原地重构（定位 × 排序 × 执行）**：热点分析负责「先改哪里」（热度 × 复杂度＝利息代理），SQALE 类扫描给出本金与规则命中，重构负责「改完不退功能」。职责边界：三者都只看得到存量代码里的债，且排序口径需要定期复核（§7.3.1）——如果榜单上全是可自动计算工时的条目，说明它是本金榜，不能直接当优先级。维护代价是每月跑一次热度排序、对齐两套数据源的口径（按文件还是按模块），并确认榜单没有漏掉「现在不动但一动就是大工程」的本金型债。
- **Strangler Fig + 上线校验（可回退批次）**：绞杀负责分批切换，校验负责每批的验证与回退条件。职责边界是「旧实现什么时候下线」必须在开工前写进计划——没有下线日期的绞杀会变成长期双跑（并按 §7.4 每季度多付约 2.3 人月）。维护代价是双跑期的并行运维与一致性核对。
- **时间预算 + 债主制 + Tech Debt Backlog + Quality Gates**：四件各管一段——时间预算保证「会发生」，债主制保证「有人负责」，Backlog 保证「还的是清单上的东西而不是顺手的东西」，门禁保证「新增被拦住」。缺一即退化：缺预算则永不发生，缺 Owner 则还错地方，缺清单则进度不可见，缺门禁则偿还追不上新增。维护代价是每季度重排一次优先级、接受「不可能全部做完」，以及持续处理门禁误报——误报率一旦高到团队开始绕行，就该调阈值而不是加严。
- **AI 辅助 + 人定优先级**：LLM 负责生成候选池与重构草案，人负责优先级与验收。职责边界是 AI 输出必须带「草案」标记，且不做门禁判定（因为概率生成器给不出「同一输入同一结论」）。维护代价是复核时间，这部分不能省。

组合的原则只有一条：**每一件都要说清它负责哪个环节（记 / 定位 / 还 / 防新增 / 验证），以及它在无人值守时会不会退化成形式**。

### 7.7 选错的代价与迁移成本

**反模式：只建清单不建 Owner 与通道** —— 症状：引入扫描工具、建了漂亮的技术债看板，条目每周增加 → 后果：看板变成坟场，团队对「技术债」这个词产生免疫，真正的严重债也被一并忽略 → 正确的做法：先把每笔债挂到具体 Owner，再给它一个通道（持续预算或项目批次）；清单只在这两件事之后才有意义。

**反模式：按本金排序还债** —— 症状：拿扫描报表的工时排序直接当优先级，先改重复代码最多的旧模块 → 后果：投入了人月，交付速度没有任何可观测改善（因为那部分代码本来就没人改），下一次预算申请被驳回 → 正确的做法：把变更热度乘进优先级（§7.3.4），先还「每天在付息」的债，本金型债按项目单独排期。

**反模式：把重写当还债** —— 症状：遇到难改的遗留系统就立项重写，同时旧系统继续接需求 → 后果：目标不断移动，重写永远追不上，双份维护拖垮团队（Netscape 是公开的经典案例，Joel Spolsky, 2000）→ 正确的做法：能并存就走绞杀式分批替换，不能并存先冻结改动窗口并给出明确的下线日期；把「旧系统停止接需求」当作重写的前置条件而不是假设。

**反模式：把 AI 识别结果直接排进 Sprint** —— 症状：让模型扫一遍代码给出债的清单，按它的顺序开工 → 后果：输出不稳定（同一段代码两次得到不同结论），团队把时间花在模型随机指出的位置，真实热点依然没动 → 正确的做法：AI 只进候选池，优先级由「热度 × 本金」决定，且它不参与门禁判定。

**反模式：用「不管理」当策略** —— 症状：明确表示不管技术债、先跑业务 → 后果：在原型期这是理性的（速度优先、代码可能被丢弃），但如果系统已经承载核心业务，这个选择就是**在赌债务累积速度低于业务扩张速度**——赌赢的前提是团队一直招得到人并且能承受变更变慢 → 正确的做法：如果选择不管理，把它作为一次显式决策记录（写明前提与复查时间），而不是默认状态。

| 从 → 到 | 债务与代码 | 度量口径 | 组织与角色 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 不管理 → Tech Debt Map / Backlog | 首次盘点（存量债登记） | 从无到有（先本金口径即可） | 需要一个维护清单的人 | 债务分类与登记 | 低（1–2 周） |
| Backlog → 加 Owner 与通道 | 每笔债补 Owner | 不变 | 需要有排期权的人认可预算 | 债主制、持续通道概念 | 中（1–2 个月，组织阻力为主） |
| 本金口径 → 加利息口径（热点分析） | 需要可用的版本历史 | 热度 × 复杂度排序 | 不变 | 读热度曲线与拐点 | 低（数天） |
| 一次性重写 → Strangler Fig | 需要新旧并存的适配层 | 不变 | 需要明确下线责任人 | 分批切换与回退流程 | 高（数月，双跑期持续付出） |
| 人工盘点 → AI 辅助识别 | 需要一份带理由的基线清单 | 不变（AI 只进候选池） | 需要复核流程 | 稳定性自检（同段代码复问） | 低（数天，复核成本长期存在） |
| 传统债清单 → 加 AI 债清单 | Prompt / 模型 / Agent 资产盘点 | 新增评估与监控指标 | 需要模型负责人角色 | 评估集与漂移监测 | 中（1–2 个月） |

有一条容易被忽略的顺序约束：**先把「谁还」这件事确定，再考虑「怎么量化」**。无主债务的清单化只会让问题更可见，而不会更可解决；反过来，有了 Owner 之后，一个粗糙的本金 × 热度排序就能立刻产生动作——这也是本主题里唯一一个「组织机制优先于工具」的结论。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 已造成业务风险（数据 / 安全 / 合规） | 立即偿还 | 这是硬约束，不进优先级排序 |
| 高频变更 + 高复杂度 | 热点分析 + 原地重构，走持续通道 | 利息按变更频次计，马上还就马上省 |
| 一次性架构替换 | 项目通道 + Strangler Fig | 重构无法完成本金偿还；绞杀可按批回退 |
| 切换点无法按流量拆 | Branch by Abstraction | 把切换点收敛到一处，避免长期双路径 |
| 新债还在持续产生 | 先上 Quality Gates | 偿还追不上新增时，预算会被缺口吞掉 |
| 没有 Owner | 先立债主制，再谈工具 | 无主债务不会被还，与工具无关 |
| 团队只有 3–5 人 | 把还债并入每次需求的小重构 | 人少时无法形成并行通道，独立预算会被挤掉 |
| 债的形态是 Prompt / 模型 / Agent | 独立清单 + 版本化 + 评估集 | 这类债的利息是效果静默退化，不是代码变慢 |

回到本章 6 条判据里权重最高的两条：**利息 / 本金**决定了走哪条通道（持续对冲还是项目批次），**变更热度**决定了两笔同样「看起来严重」的债谁该先还。这两条回答完，度量口径、可分批性、可验证性才有讨论价值。**归属**这一条则排在所有工具之前：没有 Owner 的技术债清单不会因为更好的扫描器而变短。

> 本节小结：这些方法之间唯一真正起决定作用的差异是**「度量的是本金还是利息，以及偿还走的是与需求并行的持续通道还是与需求争排期的项目通道」**——它同时决定优先级偏向哪类债、还债能否持续发生、以及投入之后能否被验证。工具、扫描器、仪表盘都是这条差异的下游结果。
