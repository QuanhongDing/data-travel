## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

技术债这一节的清单化倾向比别处更严重，因为「债」这个词天然吸引一张清单：AI 辅助识别、AI Tech Debt 标准化、AI Code Review、AI 重构助手、Prompt Registry、Model Registry、Agent Observability、AI Debt-as-Code、Tech Debt Graph——九个条目排在一起，看起来是一套完整的能力矩阵。问题在于它们**作用在不同的环节上**：识别（哪笔债存在）、度量（哪笔更贵）、偿还（怎么还）、通道（谁在什么时候还）。把它们并列，读者会以为九条都得做，实际上一半是工具、一半是机制，而只有机制决定债会不会减少。

本节用 L1/L2/L3 三级，级差由三条**可核验**的事实决定：有没有正式 release note、有没有第三方（非厂商）公开生产案例、接口是否稳定。

- **L1 生产可用**：已 GA 且文档公开、有第三方公开生产案例、接口稳定。可以排进路线图。
- **L2 可试点**：可用但接口或生态未稳，或只有厂商自有案例，或只在小规模被验证。可以做 PoC，不要做核心依赖。
- **L3 观望**：只有路线图、论文、厂商演示或预览特性。记录，不要在架构里预留假设。

判断成熟度时最常见的错法是**数产品**：「有三四家厂商都在做 Agent 可观测性，所以它成熟了」。产品数量说明的是市场预期，不是接口稳定性——决定能不能排进路线图的是「有没有正式 release note、有没有第三方生产案例、接口稳不稳」。在本主题上这个错法尤其贵：AI 债治理相关的产品在 2024-2025 年集中出现，每家的字段定义都不同，选错一家等于把可复现性的定义交给了一个可能两年后不存在的供应商。

判断一个方向是否值得投入，先看它有没有碰到本主题的既有卡点（§1.2、§2.2）。技术债的卡点也不是「没有工具」，而是四件事：

- **看不见**：不知道债在哪里、有多少（所以才有 Backlog / Map 这类定位工具）；
- **算不清**：本金与利息都只能估（§2.2 的量化公式输入全是估算），所以排序可靠、总额不可比；
- **没人还**：债没有 Owner、没有专属工时，于是「等有时间就还」永远不兑现；
- **说不服**：业务方看不懂技术语言，还债排期在与需求的竞争里永远输。

一个方向只有在**改变上述四条之一的机制**时才值得投入。这条判据会立刻淘汰一批条目：「AI Debt-as-Code」如果只是把债单从 Jira 搬到 YAML 文件里，它改变的是登记格式，不是需要机制；而「退役一个模块的债」真正卡住的地方，从来不是登记格式。

本主题还有一处特有的混淆：**债的形态与治理手段是两回事**。「AI 债」是形态——与代码债、架构债、数据债、基础设施债并列的第五种（§1.1）；而 Prompt Registry、Model Registry、Agent Observability 是手段。把形态与手段并列在同一张清单里，会让人以为「登记了 Prompt 就不欠 AI 债了」；实际登记只是让债可见，与代码债要写台账是同一件事，不是什么新机制。

还有一层自指关系必须说清：**本主题里 AI 同时是治理手段与新债的来源**。用 LLM 写代码会引入新的债（生成但未被理解的代码、没有版本的调用、没有评估的行为），而用来治理这些债的工具往往也是 AI。因此下面每条评估都要额外交代一句：它是在治理债，还是在制造债——两个方向都真实存在，混在一起谈会得出「AI 既治债又欠债」这种无法行动的结论。

本节所有数字按三档标注：**【公开】**（带来源 + 年份）、**【推算】**（写出推导链）、**【经验】**（用区间）。本主题的量化方法（SQALE、债务/开发成本比率、利息模型）输入全部是估算，因此本节不出现「某组织债务下降 X%」这类精确数字——那类数字不可核验，也不可迁移。

表前给一条通用判定方法：任何一项「AI 治理技术债」的能力，问它**改变了哪一步的边际成本**。识别、度量、偿还、通道这四步里，如果它只改变了第一步（让债更容易被发现），那么它还债总量不会变化——因为还债的约束是工时与 Owner，不是发现能力。这条判据贯穿本节。

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 债务识别与度量（SQALE 类量化、变更热度 × 复杂度定位） | **L1** | 方法有公开论文、工具文档公开、大量组织在用、不依赖 AI | 现在就做——先有台账，再谈 AI 提高覆盖率 |
| 偿还通道（受保护的固定工时 + 模块 Owner / 债主制） | **L1** | 有公开的长期实践材料（见 §6.1），失败模式已知 | 现在就做——它是唯一能让债真的减少的机制 |
| 偿还手段（原地重构 / 绞杀者 / 抽象分支 / 一次性重写） | **L1** | 模式命名与方法公开、可分批性判据明确 | 现在就做，按「能否分批」而非「工程量大小」选择 |
| AI 辅助识别（LLM 读代码与配置产出候选债单、AI Code Review） | L2 | 有厂商官方发布说明；无第三方公开的准确率/漏报率；结论不确定 | 作为候选池生成器，不做门禁、不进考核指标 |
| AI 辅助修复（LLM 重构助手） | L2 / L3 | 局部且可被测试判定的修复属 L2；架构级修复无自动判定标准，属 L3 | 只在「有测试兜底 + 改动可分批」的场景试点 |
| AI 债治理（Prompt 版本化、Model Registry、Agent 可观测性） | L2 | 模型版本管理侧成熟度高；Prompt 与 Agent 侧仅厂商文档与自有案例 | 先做版本与 trace 字段，再谈评估体系 |
| 技术债图谱（债 + 模块 + Owner 建图、GraphRAG 跨模块推理） | L3 | 无第三方公开生产案例；且其前提「债已被登记」与债的隐性特征冲突 | 记录，不在架构里预留假设 |
| 质量门禁 AI 化（用模型判定替代静态阈值） | L3 | 无第三方公开的误报率与申诉机制；可解释性低于阈值 | 保留阈值门禁，AI 建议只输出文本 |
| 合规债与可持续性债（AI 合规、碳排 / ESG 债） | L3 | 无统一定义、无可执行度量；合规约束的「偿还」语义本身不成立 | 写成约束与检查项，不要写成债单 |

表后一句话说明级别分布：**本主题的 L1 方向有三个——识别与度量、偿还通道、偿还手段，三个都既不新，也不含 AI**。之所以是三个而不是一个，是因为它们分属债的因果链上三个不可互相替代的环节（先有账、再有通道、再选手段），任何一条缺位，另外两条都不产生效果。这不是保守，而是本主题的因果结构决定的——「发现债」与「减少债」之间没有必然联系。原清单里的九个条目，绝大部分落在「发现」这一侧；而 §6.1 的公开案例显示，真正让债减少的是通道（受保护的工时 + 明确的 Owner），那是组织机制，不是模型能力。

归并的依据值得说明：原清单里「AI 辅助识别」「AI Code Review」「AI 重构助手」三条，看起来是三个投入项，实际上共用同一套前提（全量读得懂代码）、同一批代价（结论不确定、噪声、锁定）。分三条写，读者会以为可以先做识别、再做评审、最后做重构；而机制上它们是一件事的三个面——识别产出的候选，只能靠评审消化，只能靠重构偿还，三者中任何一个缺位，另外两个都不会产生效果（这正是 5.2.1 里那个「候选淹没团队」的失败形态）。

#### 5.2.1 AI 辅助识别与 AI Code Review：把抽样变成全量

- **旧做法与它的卡点**：债的识别靠三件事——扫描器的静态规则（重复代码、圈复杂度、覆盖率）、版本历史统计（变更热度 × 复杂度，§7.3.1）和人的回忆。卡点在**覆盖率上限**：静态规则只覆盖它能形式化的那几类问题，而人读代码的速度决定了抽查比例。【推算】人工抽查的覆盖率量级：假设一个季度按 13 周计，投入 2 人 × 每周 4 小时【经验参数】，共 104 人时【推算：2 × 4 × 13 = 104】；按每个文件 10 分钟【经验】约可看 624 个文件【推算：104 × 60 ÷ 10 = 624】；若仓库有 2 万个文件，覆盖率约 3%【推算：624 ÷ 20000 ≈ 3.1%】。也就是说「我们做了债务盘点」这句话，在多数组织里的真实含义是「看了 3%」——未看到的 97% 不是没有债，是不在视野里。
- **AI 改变了什么机制**：把识别从「按规则抽样」变成「对全量产物做一次批量语义判定」。落在机制上是**识别边际成本的变化**：LLM 能读懂的不是「重复率」这类可计算指标，而是注释、命名、异常处理、拼接 SQL、硬编码配置这些**语义上可疑但没有阈值**的形态。这是静态规则长期覆盖不到的部分。
- **由此得到的**：因为识别不再要求先有阈值，所以「阈值以下的债」第一次能被列出来——例如「这个函数没错，但它和隔壁那个函数在语义上重复」。这类债过去只有靠人读懂才看得见，因此从不出现在台账里，也不出现在任何报表里。
- **由此付出的**：
  - **与债的性质判定正交**：Fowler 四象限（刻意 / 无意 × 谨慎 / 鲁莽，§2.1、§3.1）判的是「这笔债该不该还」，判据是意图——是否知情、是否有还债计划。意图不在代码里，LLM 读得到代码，读不到意图。因此 AI 只能把候选池做大，不能给出优先级；把两者混在一起，会得到「AI 说这里有债，但它其实是当年刻意的、有计划的妥协」这类无效条目。
  - **低置信度的密度问题**：候选多了之后，团队的行为是「全部不看」。候选池的边际价值随密度下降，这是识别类能力最常见的失败方式——不是识别不准，是识别的结果没人消化。
  - **新的锁定与漂移**：判定行为随模型换代变化，而债务台账本应跨年可比较。如果台账口径年年变，趋势线的意义就消失了。
- **证据与来源**：厂商官方发布说明层面（代码质量工具的 AI 修复/建议功能、代码托管平台的自动代码审查功能，2024 年前后陆续公开；核验入口见 §5.3 末段）。**无第三方公开的漏报率与误报率对照数据**——凡是给出「准确率 X%」的说法，先看标注集与判定标准是否公开。【公开】与「自动识别债」最接近的学术线是自我承认技术债（SATD）研究：Potdar & Shihab 发表于 ICSME 2014 的探索性研究（《An Exploratory Study on Self-Admitted Technical Debt》，会议：IEEE ICSME 2014）从代码注释里的 TODO / FIXME 一类标记中识别开发者自认的债，并给出分类方法。它恰好说明了边界——**能自动识别的，是已被写下来的债**；没被写下来的，正是最危险的那部分。
- **判定方法**：拿台账里 50 条真实债（含已还的）做一次回放，看识别能力找回多少、误报多少，再看误报里有多少其实是「刻意谨慎的债」——后者不该被算作误报，它暴露的是判据不足。这个区分比准确率本身更有用。
- **成熟度**：**L2**（有官方说明、无第三方生产量化证据、结论不确定）。

识别方式不同，看到的是不同的债；这张表说明为什么必须与既有台账并存，而不是替换它：

| 识别方式 | 能看到什么 | 看不到什么 | 级别 |
| --- | --- | --- | --- |
| 静态规则（重复率 / 复杂度 / 覆盖率） | 可计算、可比较的债；适合做趋势 | 语义重复、缺注释、可疑但无阈值的问题 | L1 |
| 变更热度 × 复杂度（§7.3.1） | 每天都在被改、利息正在支付的位置 | 不动则已、一动就是大工程的高本金模块 | L1 |
| 自我承认债（注释标记，2014 年起） | 开发者已经写下来的、有意留下的债 | 没人写下来的债（最危险的部分） | L2 |
| LLM 语义判定 | 无阈值的语义可疑项；长尾形态 | 意图（是否刻意、是否有还债计划）；高本金但安静的模块 | L2 |

**失效条件**：当代码库本身已有一套被严格执行的静态门禁时，LLM 识别的增量价值会下降——能被规则卡住的债大都已经被卡住了，剩下的多是「刻意欠下的、且已被记录」的债，而这类债不需要再被发现。反过来，当代码库没有门禁、也没有台账时，LLM 识别出来的候选会瞬间淹没团队，此时它的净效果是负的：它把「不知道有债」换成「知道有债但还不起」，后者对团队信心的伤害更大。判断自己处在哪一种情形，看一个指标就够——过去一个季度里，台账上被标记为已偿还的条目有多少条。

#### 5.2.2 AI 债的形态：Prompt、模型与 Agent

- **旧做法与它的卡点**：AI 应用上线时，「债」这件事没有对应的登记方式。代码债可以算修复工时；而一个硬编码在代码里的 Prompt、一个没有版本记录的模型调用、一条没有 trace 的 Agent 执行路径，**没有「修复工时」这个量**。卡点就在这里：既有的量化口径（§2.2）对它们近乎失明，所以这类债既不进 Backlog，也不进报表，直到出事。
- **AI 改变了什么机制**：AI 应用引入了一类新的债——其成本不是「代码写得差」，而是**不可复现**。三类子形态是同一机制的三处表现：Prompt 硬编码 → 输入不可复现；模型未记录版本 → 环境不可复现；Agent 无 trace → 执行路径不可复现。因此这类债的「本金」定义与代码债不同：不是修复工时，而是**重建可复现性所需的工件**（版本字段、评估集、trace 字段）。原清单里 Prompt Registry / Model Registry / Agent Observability 三条，本质上是同一件事的三个工件。
- **由此得到的**：因为「可复现性」可以被具体化为字段（版本号、评估结果、trace_id），所以 AI 债第一次有了可落地的检查项——不是「这个 Prompt 写得好不好」，而是「这条调用链能不能被重放」。这使得它比代码债更容易自动化检测：字段缺没缺是确定的，代码结构好不好是不确定的。
- **由此付出的**：
  - **三类债不可加总**：Prompt 债的度量是「有多少次调用没带版本」，模型债是「有多少次推理没进评估」，Agent 债是「有多少条链路不可归因」。单位不同，加总成一个「AI 债总量」没有意义，反而会制造一个可被优化（打补丁式填字段）的指标。
  - **工件本身会腐化**：登记了版本但拉不到对应的模型、评估集半年没更新、trace 存了但没人看——这类「形式合规」的债比没有登记更贵，因为它消耗了团队对台账的信任。
  - **兼容性代价**：把版本号与 trace 打点接进推理路径，会给延迟与复杂度加一层持续的负担，且这层负担在低流量期看起来完全没必要——于是最容易被在赶方案时省掉。
  - **它不解决老问题**：AI 债治理做得好，不会让代码债、架构债少一分。把它当成「技术债治理终于有解了」的信号，会把预算从真正需要的地方（通道与人）挪到一个新维度上——而新维度的债，总量远小于旧维度。
- **证据与来源**：模型版本管理侧的公开文档与生态成熟度都较高（开源模型注册表与实验跟踪工具的官方文档可查，长期在产）；Prompt 版本管理与 Agent 可观测性侧，多为厂商产品文档与自有案例。【公开】可核验的标准化入口是可观测性语义约定：OpenTelemetry 的 GenAI 语义约定（2024-2025，公开规范，处于 development 状态）规定了模型调用与 Agent 执行应记录的属性。**判定方法**：查你所用 SDK 是否默认按该约定打点、以及该约定是否已从 development 提升为 stable——规范状态比任何产品宣传更能说明这件事成熟到哪一步。
- **成熟度**：**L2**（模型版本管理侧接近 L1；Prompt 版本化与 Agent 可观测性侧停在 L2，判定依据是标准化状态而非产品数量）。

三类子形态共享同一机制，因此修复动作也可以归并成同一张对照：

```text
AI 债的三种子形态，共同机制是「不可复现」

  子形态          不可复现的是什么      恢复可复现需要什么工件
  ─────────────  ───────────────────  ──────────────────────────
  Prompt 硬编码    输入（问的是什么）     Prompt 版本 + 变量快照
  模型未记录版本    环境（答的是谁）       模型版本 + 参数 + 时间
  Agent 无 trace   路径（怎么走到这的）    trace + 工具调用序列

  → 所以「AI 债」的本金不是修复工时，而是补工件
  → 所以字段缺没缺可自动检查，写得好不好不能

  反面用法：给三类债算一个加权总分 → 单位不同，加总无意义
```

**与既有量化口径的关系**：代码债的量化（§2.2 的 SQALE 与债务比率）对本方向几乎没有迁移价值——它度量的是「修复要花多少人时」，而 AI 债要度量的是「缺多少工件」。这不是精度差异，是维度差异：一个用补丁就能「修好」的函数，和一个没有版本记录的模型调用，前者能算人时，后者算不出来，因为「补一个版本字段」的成本与「这段代码为什么这么写」完全无关。把 AI 债硬塞进既有比率，结果一定是它被系统性低估——因为缺字段这类问题在「修复工时」口径下权重最低。

#### 5.2.3 技术债图谱：把债从清单变成图（含 RAG / 向量库 / GraphRAG）

- **旧做法与它的卡点**：债单是平的。一条债记着模块、Owner、优先级，但没有记录**债与债之间的关系**：A 债没还，导致 B 债的利息更高；两个模块的债其实是同一个根因；某条债一旦偿还，另外三条自动消失。卡点是：**排序按单条债做，而偿还往往发生在根因上**——所以「还了很多条，问题没少」是常见结果。
- **AI 改变了什么机制**：把债单从「表」变成「图」——债、模块、Owner、影响范围建成实体与关系，再叠一层语义检索（向量化债描述、相似债单召回）与多跳推理（GraphRAG 一类方法，2024 年公开）。落在机制上是**从「查一条」变成「看一片」**，以及**从结构化匹配变成语义近似匹配**。
- **由此得到的**：因为关系被显式化，所以「这批债的根因是不是同一个」第一次可以被系统回答，而不是靠一位资深工程师的记忆；因为检索变成语义近似，所以沟通场景受益明显——把「这堆技术术语」翻译成「业务影响」需要的历史案例，可以按语义召回而不是按标签匹配；而 §4.1 第 7 步把「向业务方解释债务」列为独立一步，说明它需要的正是这类可检索的历史材料。
- **由此付出的**：
  - **图会放大已登记的债，淹没未登记的债**：图谱的节点来自已登记的条目，而技术债最危险的部分恰恰是**没被登记的那些**（隐性债）。建图之后，团队的时间会自然流向图上显眼的大节点，违背了「提高债的可见性」这个初衷——这是本方向最需要警惕的副作用，也是它停在 L3 的主要理由。
  - **债描述是自然语言，语义近似会把语义上相似但性质不同的债混在一起**：一条「刻意谨慎的债」和一条「无意鲁莽的债」措辞可以很像，而它们该不该还的答案相反。语义检索在这里与 5.2.1 的四象限问题撞车。
  - **多一层需要维护的真相**：债单更新后图必须同步，否则图给出的是过期结论。这一类「第二份真相」的成本在本项目的其他主题里反复出现过，其代价从来不是首次建设，而是长期同步。
- **证据与来源**：图检索方法侧有公开论文与开源实现——微软研究院 2024 年公开的 GraphRAG 方法，论文《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》（Microsoft Research，2024，arXiv 预印本；标题与年份可由 arXiv 检索核验），并附对应开源仓库；把「实体 + 关系」建成图来做治理，在元数据与血缘领域已有多年的公开实践。**但「技术债图谱」本身没有第三方公开生产案例**——公开材料里见得到「血缘图」「元数据图」，见不到把债单建成图并给出收益数字的案例。判定方法：在公开材料里找「债」与「图」同时出现且带规模数字的段落；找不到就说明它还是原型阶段。
- **成熟度**：**L3**（无第三方公开生产案例，且前提假设与债的隐性特征冲突）。

**两种用法必须分开评价**：这个方向实际上被用在了两件不同的事上，且它们的成熟度相差很大。**其一是沟通**——把债单向量化后，按语义召回历史案例与相似债单，用来向业务方解释「我们为什么要还这笔债」。这一用法依赖的是「组织里有可检索的历史材料」，成本低、失败代价小，属 L2 可用。**其二是识别与推理**——用多跳推理发现「这几笔债的根因是不是同一个」。这一用法要求图覆盖的债本身是完整的，而债的完整性正是本主题最难的部分，属 L3 观望。原清单把它们并列在同一方向名下、未区分成熟度：前者今天就可以做，后者今天做就是把时间花在图的结构上，而不是花在账上。

#### 5.2.4 门禁 AI 化、合规债与可持续性债

- **旧做法与它的卡点**：质量门禁用静态阈值——覆盖率、重复率、复杂度、债务比率（§4.1）。卡点有两个：一是阈值是**静态的**，代码库变化后阈值要么太松（放行恶化）要么太紧（处处阻断）；二是阈值只能覆盖「可计算的东西」，覆盖不到的准入门槛只能靠人的评审判断，而人评审的深度不稳定。
- **AI 改变了什么机制**：把「按阈值判定」换成「按模型判定」。落在机制上是**判定权的转移**：从可解释的规则转到不可解释的分数。这是本方向最关键的一句话——它不是让门禁变准，而是让门禁变成统计判断。
- **由此得到的**：因为模型可以判定「这段改动是否引入了可读性/一致性上的退化」这类没有阈值的性质，所以理论上准入门槛可以覆盖到过去只能靠人的那一段，且判断标准可以随代码库风格自适应。
- **由此付出的**：
  - **可申诉性下降**：阈值可以被解释（「覆盖率 79% < 80%」），模型分数不能被解释。当门禁拒绝一个人时，他无法知道怎样才算通过——结果是绕过而不是改进。
  - **概率性判定获得确定性权力**：误报时没有人能证明它是误报，漏报时没有人知道发生过。这与 §4.1 的「CI 强制门禁」设计前提冲突，后者默认门禁结论是确定的。
  - **合规债与可持续性债的「偿还」语义不成立**：合规要求（AI 应用的数据来源、可解释性、留痕）的解释权在监管方，不在团队；碳排放之类的度量同样依赖外部口径。把这类约束登记为「债单」，意味着假设它能被一次性还清，而它实际是**持续满足型约束**。写进 Backlog 的后果是：它永远无法被标记为「已偿还」，于是 Backlog 里出现一批永不关闭的条目，稀释了 Backlog 的可信度。
- **证据与来源**：代码质量工具的 AI 修复与建议功能有厂商官方发布说明（2024 年前后；核验入口见 §5.3 末段）；合规治理框架侧有公开可查的框架文档（【公开】NIST《AI Risk Management Framework》1.0，2023，含 Govern / Map / Measure / Manage 四个功能），但**该框架不定义技术债度量，也不把「AI 债」列为独立条目**——把它当作「AI 债已标准化」的证据是误读。可持续性技术债目前没有统一的、可执行的度量口径，公开材料停留在概念层面。
- **成熟度**：**L3**（门禁 AI 化无第三方公开的误报率与申诉机制；合规债与可持续性债无可执行度量）。

**一条与本主题定义冲突的推论**：技术债的定义是「用未来的成本换今天的收益」（§1.1），隐含前提是**当初有得选**。合规要求与碳排约束不属于这一类——它们不是「今天省下的成本」，而是「外部强加的、必须持续满足的条件」。把它们叫「债」在修辞上说得通（都是持续性负担），在工程上会误导：债可以还清，约束不能；把约束放进 Backlog，会得到一批永远关不掉的条目，进而让 Backlog 的完成率失去意义。正确的落点是检查项与门禁：每次变更都要过，而不是排期去还。

### 5.3 与本主题既有栈的接口在哪

不写「与 AI 结合」这类空话，写清接口边界：谁调用谁、数据以什么形态穿过边界、失败时谁负责。三条原则先立在前面。

**第一，AI 建议必须挂在「不改变流水线结果」的位置。** 代码质量门禁的绕过路径很短——改一行配置即可。一旦把概率性判定设成阻断，团队遇到误报时的第一反应是调整门禁，而调整门禁的权限通常在下游团队手里。把 AI 放在门禁之后、只输出文本，避开的正是这条退化路径。

**第二，债单的字段必须与「谁能还」对齐。** 一条债必须能回答三件事：本金多少、利息多少、Owner 是谁。三缺一，它就会变成台账里的僵尸条目。AI 识别的产出默认缺 Owner（模型不知道谁负责），所以入库前必须补人——这一步不能自动化。

**第三，不可偿还的约束不要写成债。** 合规、碳排这类持续满足型约束应写成检查项与约束，而不是 Backlog 条目，否则 Backlog 会出现永远关闭不掉的项。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| AI 识别 ↔ 债台账（Backlog 系统） | 扫描结果 → 候选债单（含位置、类型、建议动作），入库前必须补 Owner 与本金估算 | 误报由台账 Owner 筛掉；漏报由台账覆盖度负责（即团队） | L2：候选池，不进考核 |
| AI Code Review ↔ PR 流程 | PR 事件触发 → 评论与建议；不改变流水线结论 | 建议被忽略无后果；但若误报率高，责任在采纳它的人（配置者） | L2 |
| AI 重构助手 ↔ 版本控制 | 生成补丁 → 人审 → 合并；**不得批量自动合并** | 合并后的行为变化由提交者负责（模型不承担） | L2（局部且有测试）/ L3（架构级） |
| Prompt / 模型版本 ↔ 推理路径 | 运行时可读的版本号 + 请求级记录，写入 trace | 版本缺失 → 故障不可复现，责任在应用 Owner；登记平台只负责存取 | L2 |
| Agent 可观测性 ↔ 追踪后端 | 按可观测性语义约定（如 OpenTelemetry GenAI 语义约定，2024-2025 公开规范）打点，写入追踪后端 | 字段缺失导致无法归因，责任在应用 Owner；规范未稳定由生态负责 | L2（规范尚在 development） |
| 质量门禁 ↔ CI | 静态阈值（L1）与模型建议（L2）分开挂：阈值阻断、建议只输出文本 | 阻断误判由门禁配置方负责；建议误判由提出建议的人负责 | 阈值 L1 / AI 门禁 L3 |
| 债图谱 ↔ 台账与血缘系统 | 台账条目 + 血缘关系 → 图；图只读，不回写台账 | 图过期由图谱平台负责（维护成本持续存在） | L3 |

表里能看出一条规律：**越靠近「产出物」的接口越成熟，越靠近「判定」的接口越不成熟**。登记版本、写 trace、存债单都是产出物，接口形态简单（写一个字段、存一条记录），今天就能做；而「这次改动该不该被拦」「这笔债该不该先还」是判定，接口形态复杂（要能解释、要能申诉），今天都停在 L2/L3。这不是技术问题，是权责问题——把一个判定交给模型，就必须同时决定「谁来承担它的错」，而在公开材料里，没有任何组织公开过这套权责设计。

```text
四条环节与 AI 的位置（越靠上游，AI 越成熟；越靠下游，AI 越不该介入）

  ① 识别     哪笔债存在          AI 提高覆盖率（L2：候选池，不是结论）
  ② 度量     哪笔更贵            AI 无优势（本金/利息都是估算，§2.2）
  ③ 偿还     怎么还              AI 只在可被测试判定的场景有效（L2）
  ④ 通道     谁在什么时候还       AI 无关（受保护工时 + 模块 Owner，§6.1）

  关键：①②③④ 是一条链，链的产出由最下游决定
        → 只在上游加 AI，链的产出不变（台账变长，偿还量不变）
        → AI 与治理的边界，恰好在「判定」与「产出物」之间
```

**落地的第一个动作是核验，而不是选型。**前面表与图给的都是抽象边界；落到一个具体组织，要先核清**已经在用**的那两个工具：**其一**，已在用的代码质量工具，其 AI 建议 / 修复功能有没有正式发布说明——核验入口是该产品官方文档站的 release note / changelog 页，要核的是支持哪些语言、给出的是建议还是自动改动、是否默认开启；**其二**，已在用的代码托管平台，其自动代码审查功能在你的套餐与版本里是否已可用——核验入口是该平台官方文档站的功能页与 changelog，要核的是默认触发条件与会不会阻断合并。两条都不写产品名与版本号——要核验的对象是你账号里的那个工具，通用产品清单对不上你的套餐与版本；两条都核不到落点时，这项能力在你那里就还停在 L3，不要按厂商演示排期。

### 5.4 公开进展与文献

**一、论文 / 方法（公开可查）**

- Ward Cunningham 1992 年在 OOPSLA 上提出技术债隐喻（经验报告）——这是本节所有量化讨论的起点：债是「用未来成本换今天收益」的选择。
- Martin Fowler 撰文《TechnicalDebtQuadrant》（martinfowler.com，公开文章）提出技术债四象限（刻意 / 无意 × 谨慎 / 鲁莽）——本节反复用它说明「AI 识别与债的性质判定正交」：象限判的是意图，而意图不在代码里。**该文的确切发布年份未能回查核对**，与主文件 §1.4 同口径，故不写死年份。
- Jean-Louis Letouzey 2012 年在技术债管理研讨会（MTD）上系统提出的 SQALE 方法——把每类问题的修复成本加权求和，得到修复成本口径的债务量。
- 自我承认技术债（SATD）研究线：Potdar & Shihab 的《An Exploratory Study on Self-Admitted Technical Debt》（会议：IEEE ICSME 2014）提出从代码注释中检测与分类开发者自认的债（TODO / FIXME 一类标记）。它是「自动识别债」在 LLM 之前最接近的形态，也划出了边界——能被自动识别的，是已经被写下来的债。
- 微软研究院 2024 年公开的 GraphRAG 方法与开源实现——论文《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》（Microsoft Research，2024，arXiv 预印本），用于评估「债 + 模块 + Owner 建图后多跳推理」的可行性上限；注意它是通用检索方法，不是技术债治理方法。
- 研究线入口（对应原清单「2024：AI Tech Debt 成为 IEEE / ACM 研究热点」）：IEEE / ACM 系的软件维护与演进会议长期收录技术债研究（上条 SATD 研究即发表于 ICSME 2014）。「2024 年成为热点」这类判断无法核验，故降档为可核验的入口——查 ICSE / ICSME 近两年 proceedings 中以 AI 债为题材的论文与专题名；本次未能回查，不写死结论。

**一条关于口径的提醒（无法核验，故不署文献）**：主文件 §2.2 的利息模型（年度利息 = 本金 × 利息率）里，「年利息率约 25%」是**【经验】量级**——本次未能回查到给出该数值的原始出版物，故此处不署文献。引用时写「量级」而非精确值：把一个估算常数写成精确数字，会让整张 ROI 表看起来比它实际可靠。

**二、官方文档、规范与框架（自行核验）**

- SonarSource 官方文档站的度量定义页（Technical Debt 与 Technical Debt Ratio 两条；该页随产品版本滚动更新，无法钉到某一年份，故本节不写死年份）：债务按**修复成本**计量、比率按债务/开发成本计算。核验要点：主文件 §2.2 给出的分档（<5% 优秀 … >20% 糟糕）属**经验分档**，文档定义的是算法而非分档，引用时不要把经验分档说成厂商标准。
- OpenTelemetry GenAI 语义约定（公开规范，2024-2025）：核验其状态是 development 还是 stable——**这是判断 Agent 可观测性成熟度最可靠的单一指标**，比任何产品数量都可靠。
- NIST《AI Risk Management Framework》1.0（2023，公开框架文档）：用于合规治理的框架参照。它**不**定义技术债度量，也不把 AI 债列为独立条目。

**三、第三方生产案例**

- 本主题的公开生产案例集中在「偿还通道与偿还手段」上（见 §6.1–§6.4，Google、Meta、字节、阿里的公开材料：受保护的固定工时 + 模块 Owner、不停业务的架构级替换、可分批可回退的渐进迁移、集中还债月）。
- **其中没有一条是「AI 自动识别并自动偿还技术债」的公开生产案例。** 这句空白是本节最重要的证据：该方向尚未跨过 L2，把「AI 自动还债」排进路线的组织找不到可对标先例。
- 可自行核验：在公开材料里找「债」与「AI」同时出现且带前后对比数字的段落。找不到，就说明现有证据只支持「AI 提高了识别的覆盖率」，不支持任何更进一步的结论。
- 另有一类常被当作证据的东西要排除：**工具厂商发布的「客户案例」**。判断它是不是第三方证据，看三点——案例里有没有给出方法（怎么量的）、有没有给出基线（改前是什么）、有没有让客户署名。三点缺一，它就只是产品页。

宁少勿假。本节只列方法 / 规范层面的公开材料与核验入口，不列任何「某产品支持某 AI 特性」的断言：在无法当场核验版本的条件下，正确的做法是把核验动作交给读者——上列每条都给了可核验的落点。

为什么本节不直接列「某平台的技术债 Backlog 产品」「某工具的 AI 修复功能」这类条目？因为它们的可核验信息只有产品页与厂商博客，而本节要回答的问题不是「市面上有什么」，而是「哪些能力现在能排进路线图」。产品名会变、功能会下线、版本会分叉；而上面列的方法、规范与框架是稳定的参照物。读者用它们判断自己手上的工具处在哪一级，比抄一份会过期的工具清单更有用。原清单里的「代码质量工具的 AI 建议 / 修复功能」「代码托管平台的自动代码审查功能」两条同理：本节不给它们留条目，而是改写为「怎么核验你自己已在用的那个工具」的两条自查，见 §5.3 末段。

### 5.5 被过度宣传的部分

以下三条是本节与营销材料的差别所在。每条按「实际是什么 → 为什么会这样 → 什么时候才会成真 → 判定方法」写，最后一栏是给读者的自检动作。

**一、「LLM 自动还债：识别 + 重构 + 测试一条龙」**

- **实际是什么**：可以自动完成闭环的，只有那些**正确性可被测试判定**的债——重复代码合并、类型补全、死代码清理、依赖升级带来的机械改写。架构级债（耦合、边界混乱、数据模型问题）不能被自动还。
- **为什么会这样**：「还债」需要知道改完是什么样才算对。前一类债的「对」可写成测试；后一类债的「对」是设计判断，没有可自动判定的标准。去问一个正在被重构的系统「怎样算改好了」，答案通常是「没有以前那么难受」——这不是一个可执行的验收标准。
- **什么时候它才会成真**：当架构约束本身变成**可执行的东西**（依赖规则可检查、契约测试可跑、模块边界可验证）时，一部分架构债会降级为「可判定」。§6.3 的公开案例已经示范了这一步：把「新链路算得对不对」变成每日自动对数、差异超阈值即阻断，正确性由对数结果证明，而不是由设计者判断（§6.5 把「每日对数 / 并行验证作为迁移正确性判据」列为最高一段的门槛）。
- **判定方法**：问「改完之后跑什么来证明它更好」。答得出，就是可自动化的债；答不出，就是在赌模型的理解与你一致。

**二、「AI 债有统一度量标准，可以算出一个总额」**

- **实际是什么**：三类子形态的计量单位不同（Prompt 债数「多少次调用没带版本」，模型债数「多少次推理没进评估」，Agent 债数「多少条链路不可归因」），加总无意义。
- **为什么会这样**：代码债的量化方法（SQALE 一类，2012 起）能成立的前提是「所有问题的修复都能折算成人时」。AI 债的本金不是修复工时，而是**补工件**——补版本字段、补评估集、补 trace。工件之间没有共同的折算汇率。
- **什么时候它才会成真**：当「可复现性」被标准化为强制字段（例如追踪语义约定成为 stable 并被 SDK 默认开启）时，「哪些调用不可复现」会成为一个可比的数字。即便如此，可比的是**可复现性覆盖率**这个单一维度，而不是一个笼统的「AI 债总额」。
- **判定方法**：问对方那个总额的数单位是什么。答不出单位的，是四个不同维度的数被乘上了拍脑袋的权重。

**三、「AI Code Review 会降低技术债」**

- **实际是什么**：它首先增加的是**审查带宽**——低置信度建议会占用评审者最稀缺的资源。团队面对大量建议的稳定行为是全部忽略，于是建议越多、单条价值越低。
- **为什么会这样**：评审的价值来自「被认真读过的意见」，而注意力是零和的。把建议量提高一个数量级，不会让被认真读的意见同比例增加。
- **什么时候它才会成真**：当建议**自带可执行的验证**（改完能跑什么来证明它更好）时——此时建议不再消耗判断力，而是消耗一次执行。可验证的建议是唯一能规模化消化的一类。
- **判定方法**：统计过去一个迭代里 AI 建议的**采纳率**与其中**被事后回滚的比例**。前者低说明噪声高，后者高说明它引入了新债——这两个数字比任何准确率宣传都直接，而且你们自己的仓库里就有。

### 5.6 未来 3–5 年：可证伪的预测

写不出「会成真 / 会证伪」两种信号的说法，本节一律不写。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 债务度量会从「总量」转向「产债速率」（新增债务 / 合并） | 门禁与仪表盘产品把「本次改动新增了多少债务」作为一等指标；公开案例开始报速率而不是总量 | 两年内产品仍只报总量与趋势线，没有按改动归因的增量 |
| 「可复现性」字段（版本、评估、追踪标识）会成为 AI 应用的强制项 | 追踪语义约定从 development 提升为 stable，且主流 SDK 默认按约定打点；代码评审里出现「这条链路能不能重放」作为拒绝理由 | 规范长期停留 development，或各厂商各自定义字段、互不兼容 |
| AI 自动修复会先在高重复度、可验证场景被接纳（依赖升级、框架迁移、机械改写），不会先在架构级 | 公开案例集中在 major 升级与框架迁移，且给出「改了多少处、测试通过率如何」的可核验数字 | 公开案例集中在架构重写，或所有案例都只讲「提速 X%」而无验收口径 |
| 可持续性 / ESG 技术债不会进入工程预算 | 出现跨组织、可执行、可比较的度量口径，并被写进架构评审的必过项 | 两年内它仍只出现在 ESG 报告的定性章节里，没有工程侧的可执行定义 |

这四条的共同特征是：**信号都出现在产品行为或公开案例里，而不是出现在展望文章中**。第二条尤其值得单独看——它其实是「AI 债」这件事会不会变成一门可管理工程的唯一分水岭。因为三类子形态的唯一共同点是「不可复现」，所以只要可复现性被标准化，AI 债就会从概念变成字段；反之，它永远只能停留在讨论里。

第一条预测（度量从总量转向速率）之所以值得单独下注，是因为它有一条现成的机制解释：总量是一个**不可执行的数**。它既不能归因到团队，也不能归因到改动，因此只能用于汇报。而速率可以归因——「这次合并新增了两条债」是一件有人认领的事。§6.1 的公开做法（固定工时 + 模块 Owner）能长期维持，靠的正是把债归因到人；总量口径与这套机制不相容，这是它迟早会被替换的结构性原因，而不是风向问题。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 3–10 人小团队 | 每次改动顺手做小重构；用 Fowler 四象限标注刻意欠下的债（§3.1） | 债务是否已高到需要独立通道 | 不要引入债务量化工具与 AI 识别——人少时「顺手还」比任何机制都有效 |
| 30–100 人、已有 CI | 建 Backlog（含本金 / 利息 / Owner 三字段）+ 门禁固定阈值 | AI 识别在你们自己台账上的找回率与误报构成 | 不要把 LLM 审查设成阻断，也不要把它计入考核指标 |
| 有 AI 应用已在生产 | 给推理路径补版本号与追踪标识；评估集纳入发布流程 | 追踪语义约定的状态（development → stable） | 不要给 AI 债算加权总分——三类单位不同，加总只会产生一个可被填字段刷的指标 |
| 有遗留系统正在替换 | 按「能否分批」选偿还手段（绞杀者 / 抽象分支），见 §7.3.3 | AI 重构助手在升级迁移场景的可用性 | 不要批量合并 LLM 生成的补丁——架构级改动无自动验收标准 |
| 要向管理层汇报债务 | 把利息翻成业务成本（§4.1 第 7 步），用 §6 的公开案例做对标 | 管理层是否开始问「新增了多少」而不只是「还剩多少」 | 不要报一个精确的债务总额——输入全是估算，精度低于它的说服力，还会引来「把它写进预算表」的错误用法 |

「明确不要做」这一列的共同点是：**它们都会制造「看起来在治理」的假象**。给 AI 债算总分、报精确总额、批量合并生成的补丁，这三件事都会产出可展示的成果（一个数字、一张表、一批提交），但不会让任何一笔债真的减少——而它们消耗的信任，会让下一次真正需要投入的偿还计划更难获批。

投入顺序也由上述机制决定，且顺序不可颠倒：**先补通道（④），再挑偿还手段（③），然后才谈度量（②），最后才是 AI 识别（①）**。这个顺序与直觉相反——直觉是从「先搞清楚我们欠了什么」开始。但机制上，识别只有在「有人会去还」的前提下才产生价值；先做识别而后建通道的团队，几乎都会走上同一条路：台账越来越长（因为 AI 让发现更容易）、还债越来越少（因为没有专属工时），最后台账被弃用，团队对债务问题的讨论变回凭印象。

### 5.8 小结

> 本节小结：AI 在本主题上真正改变的**唯一一条机制**是「债务识别的边际成本」——从靠静态规则与人的抽查（覆盖率有上限，【推算】量级见 5.2.1）变成对全量产物做一次批量语义判定。它没有改变的是**偿还的约束**：还债需要的是通道（受保护的工时与人）与 Owner，而不是发现能力。**AI 让债更可见，但不会让债更少**；在没有偿还通道的团队里，识别能力提高的直接后果是台账变长、优先级每月重排、实际偿还量不变。三个 L1 方向（识别与度量、偿还通道、偿还手段）全部不含 AI，这不是巧合，而是因果：它们是「债会减少」这条因果链上的环节，而 AI 目前只作用在这条链的最上游。
>
> 一条可用的自检：如果你的债务计划里「发现了多少条」在涨、而「还掉了多少条」没变，那么缺的是通道，不是工具——此时加任何 AI 都会让这个差距更大。
