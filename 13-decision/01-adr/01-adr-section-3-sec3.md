## 3. 设计模式与范式

> 原 § 3 共 133 行：6 个模板模式（其中前 3 个各带一段模板示意）、1 张「团队规模 → 推荐模式」表、10 条反模式提示。后 3 个模式与全部 10 条反模式都是要点式短句，没有结构示意、成本机制与失效条件。本节重写为约 330 行的模式手册，原 6 个模式名与 10 条反模式名全部保留。

### 3.1 先看约束：模式不是选择题，是约束的产物

原表把六个模板排成一条「团队规模 → 推荐模式」的阶梯（5–10 人用 Nygard、10–50 人用 MADR、200+ 人用 Y-statement + Living 等）。阶梯本身不算错，但它把**规模**当成了唯一的自变量，读者于是容易得出「人多了就换重模板」这种没有前提的结论。真正决定模板形态的，是**写下这条决策的人和将来要读它的人之间隔着多远**——时间距离（三个月后还是三年后）与组织距离（还能不能当面问到当时拍板的人）。这两段距离只要变长，记录就必须自己携带更多信息：约束（Context）、被否掉的选项（Options）、以及判断自己是否已过期的状态（Status）。

这条距离约束之所以是根约束，是因为它同时决定了另外三件事。第一，**字段深度**：能不能当面问到人，决定 Options 是「必须写」还是「可以不写」——只有当读者再也问不到当时的人时，被否掉的选项才有独立价值。第二，**载体**：读者越远，记录越不能依赖人脑、聊天记录与 wiki 条目这些会静默过期的载体，「与代码同库、可 diff、可被评审与门禁校验」于是从偏好变成必需（本章 [§7.3.2](01-adr-section-7-sec7.md)）。第三，**可判断性**：读者越远，「这条决策现在还成立吗」越不能靠回忆回答，只能靠 status 字段与 supersede 链（本章 [§7.3.3](01-adr-section-7-sec7.md)）。

还有一件常被忽略的事：**ADR 的价值不来自「写了」，而来自「将来有人要基于它做判断」**。所以选模板前该问的不是「写多重」，而是「谁会读它、他读完要决定什么」。同一份记录，服务对象是三个月后同团队的自己，还是两年后另一个团队的新人，模板形态完全不同。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 决策的重做成本（可逆性） | 决定值不值得写，以及模板最轻能轻到什么程度 | 「所有决策都该写 ADR」——恢复成本低于记录成本约一个数量级时，写是净损失【经验：这条「一个数量级」是保守止损线，不是精确盈亏平衡点，与本章 [§7.5](01-adr-section-7-sec7.md) 同口径】 |
| 决策的失效半径（波及几个团队 / 接口 / 数据契约） | 决定字段深度：半径越大，被否掉的选项与决策驱动越必须留下 | 「写一句结论就够了」——跨团队时结论本身没有信息量，因为读者不知道约束是什么 |
| 读者与拍板人的距离（时间 + 组织） | 决定要不要写 Considered Options 与 Decision Drivers | 「口头讲一遍就行」——接口类决策的读者是三个月后另一个团队的人 |
| 决策的预期寿命 | 决定要不要带监测指标与回滚条件（Living 模式） | 「写一次管终身」——寿命长于一次组织调整的决策，不写回滚条件就无法判断它是否仍成立 |
| 库的规模（条数） | 决定分类与检索入口是否成为必需 | 「按编号排目录就够」——上百条之后，回答「我们为什么不用 X」要读接近全量【经验，与本章 [§7.5](01-adr-section-7-sec7.md) 的检索阈值同口径】 |
| 组织是否已有代码评审习惯 | 决定 ADR 能否与实现同库并真正进入流程 | 「装上模板就有了 ADR 制度」——与代码同库的价值依赖评审环节，没有评审时它等同于 wiki 条目 |

这六条的共同点是：**每一条都在给你一个可观测的问题（重做要多久、谁会读、库有多大、有没有评审环），而不是一个偏好**。写得出来，模板就能选；写不出来，选什么模板都只是在挑排版。

### 3.2 模式逐个拆解（核心节）

六节用同一套模板拆：**被什么约束逼出来 → 结构 → 为什么这样设计有效 → 代价 → 失效点 → 真实使用**。每节的失效点只反转**它自己**的优点，不借用邻座的——写不出失效条件，说明还没找到这个模式的约束。

#### 3.2.1 Nygard 经典模板（最轻量）

- **被什么约束逼出来**：决策发生在单团队内、三个月内就可能被重新讨论，读者还能当面问到当时拍板的人；此时记录的任务只是「别再重开一轮」。
- **结构**：

```markdown
# {编号}. {标题}

## Status
{Proposed / Accepted / Deprecated / Superseded by ADR-XXXX}

## Context
{决策的上下文 / 约束 / 业务背景}

## Decision
{我们决定做什么}

## Consequences
{正面 + 负面影响}
```

- **为什么这样设计有效**：因为模板只要求四段、Decision 只要求一句话，所以撰写成本被压到分钟级（【经验】10–20 分钟量级，与本章 [§7.4](01-adr-section-7-sec7.md) 同一口径；四段式不含选项调研，量级低在这里）——门槛低到「决策当场顺手写」是可实现的，记录才会真的发生。
- **代价**：四段里没有 Options 与 Decision Drivers 的槽位，被否掉的方案与当时的约束不会进正文；也**没有 Owner 字段**——「谁拍板」只能靠 Context 里的叙述，出问题时无处可查。这两笔成本买的是撰写速度。
- **失效点**：当决策半径跨出团队时，「结论 + 后果」这套内容的优点会反转成「外部读者无法复现判断」——因为读者没有参与过当时的约束，缺 Options 意味着他既无法判断自己的场景是否适用，也不知道该不该 supersede；表现为同一个选型在新团队被重开一轮，而重开一版的成本（重新调研 + 重新说服）高于当初把 Options 写下来的成本。
- **真实使用**：【公开】本章主文件 [§1.1](01-adr.md) 记录 ADR 概念由 Michael Nygard 在 2011 年的《Documenting Architecture Decisions》中系统化；其 Status 的四个取值（Proposed / Accepted / Deprecated / Superseded by ADR-XXXX）定义在主文件 [§2.1](01-adr.md) 的关键概念表；【公开】本章主文件 [§1.4](01-adr.md) 记录 ThoughtWorks 技术雷达 2014 年收录 ADR 实践（Trial）；【经验】本章 [§6 案例 1.1](01-adr-section-6-sec6.md) 按该案例的自述，把这家组织推行这套做法的时间上溯到 2005 年、延续 15+ 年（该案例的出处是区间式公开材料，具体年份可按 §6 正文核对）——它与本条前面的 2011 年并不冲突：2005 年是组织内部「把决策推理留下来」的做法，2011 年才是它被公开命名与模板化的时点。判定方法：翻出你们最近一条「因为没人记得当时怎么想的而重开讨论」的决策，它当初值不值得写一段 Options。

#### 3.2.2 MADR（Markdown Any Decision Records）

- **被什么约束逼出来**：决策跨团队、跨年，读者问不到拍板人，也无法从结论反推约束；同时组织需要对库做横向对比与统计。
- **结构**：

```markdown
# {编号}. {标题}

- Status: {Accepted}
- Date: {YYYY-MM-DD}
- Deciders: {团队 / 决策者}
- Consulted: {被咨询的专家}
- Informed: {被通知的相关方}

## Context and Problem Statement
{问题描述 + 业务 / 技术驱动}

## Decision Drivers
- {驱动 1}
- {驱动 2}

## Considered Options
1. {选项 A}
2. {选项 B}
3. {选项 C}

## Decision Outcome
**Chosen option: "{选项 X}"**, because {理由}.

**Consequences**
- Good: {正面}
- Bad: {负面}
- Neutral: {中性}

**Confirmation**
{如何验证决策正确——指标 / 评审 / 复盘}
```

- **为什么这样设计有效**：因为 Decision Drivers 与 Considered Options 被字段化，所以「当初为什么没选 X」从一句需要当事人回忆的话，变成一次阅读即可复现的判断；因为 Deciders / Consulted / Informed 也被字段化，所以「谁拍板、谁被咨询过」第一次变成可核对的数据，而不是叙述。
- **代价**：选项调研从「可省略」变成「必做」——撰写成本从四段式的 10–20 分钟升到 30–60 分钟【经验，本章 [§7.4](01-adr-section-7-sec7.md) 同一口径】，多出来的部分几乎全部花在找齐选项与对账上，而不是写；另外字段齐全的文档自带权威语气，模板一旦僵化，把「探索性决策」硬塞进来就会产出一批字段齐全但内容不可信的 ADR。
- **失效点**：当 Options 段里没有一个是「当时真的有人倾向的选项」时，「可追溯」会反转成「给错误结论背书」——因为它看起来是一份完整的比较，检索器与后人都以更高置信度采信它（本章 [§7.3.4](01-adr-section-7-sec7.md) 对「填了 status 却没人维护」的机制分析同源）；表现为后续讨论不再追问约束，而是直接引用当年那份陪衬式的比较。
- **真实使用**：【公开】本章主文件 [§1.4](01-adr.md) 记录 MADR 于 2017 年发布；其字段结构即上方 3.2.1 的 Nygard 四段式之上再加 Decision Drivers、Considered Options 与 Confirmation 段（字段逐条见上方结构块）；【公开】MADR 官方模板与 `docs/adr/` + 编号文件名的目录约定可在公开仓库核验（可按 adr-tools、MADR 官方仓库检索），具体字段请以官方模板当前版本为准。判定方法：随机抽 5 条 ADR，看 Options 段里有没有一条是「当时真的有人倾向」的。

#### 3.2.3 Y-statement（单句决策）

- **被什么约束逼出来**：库已经大到人翻不动、或需要跨条聚合与机器处理（检索、统计、决策图谱），而整篇阅读无法规模化。
- **结构**：

```text
In the context of {上下文},
facing {关切 / 约束},
we decided for {选项},
to achieve {目标},
accepting {代价 / 后果}.

────────────────────────────────────────────
五个槽位 = 五个可被抽取的字段：
  context / concern / option / goal / consequence
→ 抽取后的用途：
  · 按 option 聚合「我们有多少条决策选了这个技术」
  · 按 consequence 找出「代价已不可接受」的候选 supersede 对象
  · 按 context 做多跳问答：「我们为什么不用 X」
────────────────────────────────────────────
注意：槽位装不下取舍过程，所以它必须配主文档，而不是取代主文档
```

- **为什么这样设计有效**：因为决策被压成一句带固定槽位的结构化陈述，所以它可以被抽取入图、跨条聚合、按字段过滤——回答一个历史问题的成本从「人读接近全量」降到一次查询；这正是它在「库大了、人读不动」之后才出现的机制原因。
- **代价**：表达力受限是结构性的——一句话装不下多轮权衡、被否掉的选项细节与失效条件；因此它必然依赖主文档，两份材料之间一旦失去双向链接，单句就成了「有出处但不完整」的引用，比自由文本更容易被当成完整结论。
- **失效点**：当组织把它当**唯一**记录时，「可聚合」的优点会反转成「后人无法判断该不该 supersede」——因为约束与代价被压成短语之后，判断「这个前提今天还成立吗」所需的上下文已经不在记录里了；表现为状态链看起来完整，但没人能说清某条是为什么、以及它在什么条件下失效。
- **真实使用**：【公开】句式定义见本章主文件 [§2.1](01-adr.md)，其流行时间本章主文件 [§1.4](01-adr.md) 记为 2018 年前后——出处口径与本章 [§7.3.4](01-adr-section-7-sec7.md) 一致；本章 [§7.3.4](01-adr-section-7-sec7.md) 把它作为「单句结构化」一档，与字段化模板并列。【经验】社区材料常把这一句式追溯到 Olaf Zimmermann 关于架构决策文档化的写作，但该说法的标题与年份在不同材料中并不一致，因此本节不把它当【公开】出处引用；需要写明出处时，请按「Y-Statement」「Zimmermann」检索其官方页面，以页面上标注的标题与年份为准。判定方法：看库里能不能一次查出「所有选了同一技术的决策」，以及这些单句背后有没有可点的正文。

#### 3.2.4 Lightweight ADR + Decision Matrix（结论与依据分载）

- **被什么约束逼出来**：团队要保留极简模板的速度，但关键决策需要可复算的量化依据；而 ADR 按约定不可变，评估过程却要反复争论——两种需求不能装在同一份载体里。
- **结构**：

```text
Lightweight ADR + Decision Matrix：把「结论」与「依据」拆成两份载体
  ADR 正文（极简、不可变）              评估矩阵（可反复更新、独立成文）
  ┌────────────────────────────┐       ┌───────────────────────────────────┐
  │ #0012 湖仓表格式选型         │       │ 准则     权重   A(Iceberg) B(Delta) │
  │ Status: Accepted            │──引用─▶│ 迁移成本  0.4      3         2      │
  │ Context: …（3 行）           │       │ 引擎适配  0.3      4         4      │
  │ Decision: 选 A               │       │ 团队熟悉  0.3      2         4      │
  │ Consequences: 好 / 坏（必写） │       │ 加权合计           3.0       3.2    │
  └────────────────────────────┘       └───────────────────────────────────┘
  权威划分：ADR 正文记「结论 + 代价」，矩阵记「依据与权重」
  约定：矩阵更新不改 ADR 正文；若结论因此改变，必须写新 ADR 并 supersede 旧的
  （以上准则、权重、评分与合计均为占位示意：用于说明两份载体的分工，不是对任何真实选型的评估结果）
```

- **为什么这样设计有效**：因为权重与评分被移出不可变的正文，评估过程可以在评审中被反复争论而不破坏「一度 Accepted 就不再修改」的约定——两份载体的生命周期不同，分开之后各自都能保持干净。
- **代价**：两处维护必然带来漂移风险，必须事先约定谁是权威（通常 ADR 记结论、矩阵记依据），并约定矩阵改动要不要回写 ADR；此外模板约定本身就是团队共识成本，不是写一次就自动生效的。
- **失效点**：当矩阵的分被当成结论时（「加权算出来 B 更高所以选 B」），量化的优点会反转成**责任的转移**——因为权重是人定的、且形式感会让人不再追问权重从哪来，于是决定权偷偷从人手里移到了表格上（本章 [§7.1](01-adr-section-7-sec7.md) 对打分表的批评在这里同样成立）。
- **真实使用**：【经验】中小团队常见做法是「ADR 正文一页 + 独立评估矩阵」；判定方法：看矩阵的权重是谁定的、有没有在 ADR 里被引用、以及结论与矩阵不一致时以哪份为准。

#### 3.2.5 Pattern-based ADR（按模式分类）

- **被什么约束逼出来**：库上百条，按编号排的目录已经无法回答「我们为什么不用 X」；同时新人的入口需要按主题，而不是按时间。
- **结构**：

```text
Pattern-based ADR：按主题分类的目录与索引
  docs/adr/
    README.md          ← ADL 索引：编号 / 标题 / 状态 / 主题 / Decision Owner
    data/              0001-… 0014-…   数据契约、口径、存储选型
    platform/          0007-… 0021-…   平台与基础设施
    security/          0011-…          权限、加密、合规
  ────────────────────────────────────────────────
  分类规则本身要写进 README，否则下一个人会按自己的直觉再分一次：
    · 一条决策横跨两个主题 → 只放一个主目录，另一个目录的索引里写一行链接
    · 分类维度选「提问者会怎么问」，而不是「技术栈怎么分」
  ────────────────────────────────────────────────
  规模判断：几十条以内，编号目录足够；
            上百条之后，检索入口的收益才开始超过分类与字段的维护成本【经验】
```

- **为什么这样设计有效**：因为分类把检索从「全文扫描」变成「先定位主题再读少数几条」，所以人读成本不再随库规模线性上升；一条决策归到一个主题下，后来者只需要读这一类的几条，而不是全库。
- **代价**：分类必须在写入时决定，而分类维度是不可预知的——一条决策常常横跨两个主题，写的人要额外做一次判断；分类本身也会成为争议（数据域怎么划、平台边界在哪），而且改分类意味着改所有人的链接。
- **失效点**：当分类维度与提问维度不一致时（读者问的是「跨数据域的权限怎么定」，而目录按技术栈分），「易检索」的优点会反转成新的检索障碍——因为分类只对「已经知道该看哪一类」的人有效，对不知道该看哪类的人等于没有入口；表现为新人仍然靠问人，而库的使用者永远是同一批老人。
- **真实使用**：【公开】`docs/adr/` + 编号文件名的目录约定与 adr-tools 一类自动化脚本可在公开仓库核验（可按 adr-tools、MADR 官方仓库检索，与本章 [§7.3.2](01-adr-section-7-sec7.md) 同源）；【经验】按主题分子目录（`adr/data/`、`adr/platform/`）在上百条规模时才划算（与本节结构块里的规模判断同一口径）；本章 [§6 案例 1.3](01-adr-section-6-sec6.md) 记录多业务统一结构后可按主题与状态集中检索的做法。

#### 3.2.6 Living ADR（持续演进的 ADR）

- **被什么约束逼出来**：决策寿命长于一次组织调整周期（基础设施迁移、合规框架一类），「这条决策现在是否仍成立」必须可判，而决策时的静态记录回答不了这个问题。
- **结构**：

```markdown
# 0031. 迁移到湖仓表格式 Iceberg

- Status: Accepted
- Date: 2024-03-11
- Owner: 数据平台组 / 张（Decision Owner —— 不是撰写人）
- Review-by: 2025-03-11，或迁移完成度 > 90%

## Context / Decision Drivers / Considered Options
（同 MADR，决策时刻写定后不再改）

## Decision Outcome
选定 Iceberg。

## Consequences
- Good: 与现有查询引擎的适配路径清晰
- Bad: 写入链路需重写；过渡期双写带来一致性维护成本

## 回滚条件（Living 模式的额外字段）
- 触发回滚的情形：迁移 6 个月后完成度仍 < 50%，或双写一致性工单持续上升

## 监测指标
- 迁移完成度（已迁移表数 / 总表数）
- 双写一致性告警数（周）
- 读取侧 P95 延迟（迁移前基线 vs 当前）

## 实施进展（唯一允许被追加的段落）
- 2024-05-02：写入链路改造完成 3/12 条
（以上为示意记录：日期、门槛值与进度均为占位示例，落地时按真实约束填写）
```

- **为什么这样设计有效**：因为回滚条件与监测指标被写进同一条记录，「该不该 supersede」从一个需要重新开会的判断题变成一次核对；不可变的是决策内容与后果，可变的是实施进展与复审结论——把这两类内容在模板里分开，两者才不打架。
- **代价**：维护成本高，且必须有人负责回写——它把 ADR 从「决策时刻的归档」变成「持续维护的活文档」，条目越多，这笔固定成本越大；同时它把 ADR 与 RFC / Design Doc 的边界重新拉近，团队需要更清楚地约定哪部分归谁。
- **失效点**：当决策寿命其实很短（一次迭代内就会被推翻）时，Living 的成本会反转成纯负担——因为「实施进展」每次都要回写，而这条决策三个月后已经没人再看；表现为该字段长期空白，读者从此不再相信任何一条记录里的状态（这与 3.5 的「文档僵尸」是同一机制的两端）。
- **真实使用**：【经验】长生命周期决策（基础设施迁移、合规框架、数据契约的级换代）的常见做法；本章 [§7.5](01-adr-section-7-sec7.md) 给出一条判定：寿命超过一次组织调整周期的决策才值得带上回滚条件。判定方法：看记录里有没有写死复审时点，以及最近一次复审是什么时候。

### 3.3 模式选择决策表

原表按「团队规模 + 决策风险」给五行推荐。规模这一维可以保留，但它只是「读者距离」的粗糙代理——同样的 50 人，如果彼此独立、各有明确汇报线，跨团队决策依然很少，用不上 MADR。下表把原五行改写成约束组合，另补一行原表没有覆盖的约束（决策理由是商业敏感信息），并给每一行补上「为什么不选另一个」与判据。

有一件事要先交代：下表的行与「推荐模式」**不再逐行对应**——「（原：…）」只标出该行约束组合承自原表的哪一行，推荐模式本身已按约束重组，差别集中在两处。其一，原表第 4 行（200+ 人 / 高）推荐「Y-statement + Living ADR」，本表把 Living 移到了战略级那一行，因为 Living 的回写成本要靠长寿命才摊得平（见 3.2.6 的失效点），该行只留下「统一结构 + Y-statement」这对面向聚合的组合。其二，原表第 5 行（任何规模 / 战略级）推荐「Pattern-based + Decision Matrix」，本表没有把它当成一个整体挂靠「战略」这个风险标签，而是拆到「按主题检索」与「量化依据」两条约束下：前者即 3.2.5 的 Pattern-based 分类，后者的矩阵一半落在 3.2.4（Lightweight ADR + Decision Matrix）。六个模式名都在 3.2 与 3.8 中逐个交代，只是不再与「规模 / 风险」一一绑死。

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 单团队、决策可逆、读者就是自己（原：5–10 人 / 低风险） | Nygard 四段式 | 完整 MADR 的选项调研成本高于决策本身的价值 | 重做这一次决策要几个人日 |
| 跨团队或跨年、约束复杂（原：10–50 人 / 中风险） | MADR（含 Decision Drivers 与 Considered Options） | 轻量模板缺 Options，后人无法质疑结论，只能重开一轮 | 读者还能不能当面问到拍板人 |
| 库上百条、需要按主题与状态检索（原：50–200 人 / 中高风险） | MADR + Pattern-based 分类 | 单层编号目录在上百条时不可检索；只加标签不解决「不知道看哪类」 | 回答一个历史问题平均要读几篇 |
| 需要组织级聚合、统计与图谱（原：200+ 人 / 高风险） | 统一结构的字段化模板 + Y-statement（可聚合） | 自由文本无法做组织级统计，跨 BU 重复讨论无法被结构性地发现 | 有没有「按技术选择聚合所有决策」这类查询需求 |
| 战略级 / 不可逆 / 需对外举证（原：任何规模 / 战略级） | MADR 全字段 + ADL 索引 + RFC 收敛 + Living（回滚条件与监测指标） | 轻量模板缺 Decision Owner 与确认记录，无法作为举证材料 | 这份记录会不会被审计或客户引用 |
| 决策理由是商业敏感信息 | 私有库 + 权限与 ADL 一致 | 公开库会把未公开的取舍暴露出去 | 问答入口的权限是否宽于库本身 |

本主题下**最常被误选的一对是 Nygard 四段式与 MADR**，而且误选方向几乎总是低估字段：团队在 10 人时选了四段式，到 50 人、跨三个团队时才发现每条记录都读不出「当时否掉了什么」，于是同一个选型被重开第二轮——第二轮的代价（重新调研、重新说服、可能选反）远超当初写下 Options 的成本。反方向的误选（小团队直接上全字段 MADR）也确实存在，但它的代价是显性且即时的（每条 30–60 分钟【经验】），团队会自己纠回来；**隐性的那一种才会长期留在库里**。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：RFC + ADR（拍板前后各一段）**

- 各自承担什么：RFC 负责「拍板前把异议与约束暴露出来」，ADR 负责「拍板后把结论与取舍固化」，边界是时间点（本章 [§7.3.1](01-adr-section-7-sec7.md)）。
- 运维代价：决策周期被反馈窗口拉长；且必须有人负责把 RFC 的结论准确搬进 ADR——搬错一次，后续所有引用都错。
- 适合规模：跨团队、涉及接口与数据契约的决策。
- 失效边界：RFC 讨论完即冻结，后续变更不会自动回写；若没人做这一步，库里的 ADR 会与 RFC 的最终结论不一致。

**组合 B：ADR + 设计文档（为什么 vs 怎么设计）**

- 各自承担什么：ADR 记决策与后果（decision log），设计文档记实现方案（blueprint），边界是「变了的是理由还是方案」（本章主文件 [§2.4](01-adr.md)）。
- 运维代价：两份文档极易漂移，必须在设计文档里显式回链 ADR 编号，并在 ADR 被 supersede 时回头检查引用它的设计文档。
- 适合规模：实现周期长于一个季度、或实现方案会被反复调整的系统。
- 失效边界：设计文档就地编辑时，理由会被顺手改写，历史因此丢失——这是「无 consequence」与「伪 ADR」两个反模式的共同入口。

**组合 C：ADR + 架构评审 / CI 门禁（产物挂在必经环节上）**

- 各自承担什么：评审是流程，ADR 是产物，同一个环节的两端；CI 负责结构检查（Options 是否 ≥ 2 项、Consequences 是否含负面代价、Status 是否合法）。
- 运维代价：评审会不开就不产出 ADR，产量会被会议节奏限制；结构检查的门槛要按风险分级，否则会催生「为过检查而写」的填充式 ADR。
- 适合规模：多个团队共用一套决策库、需要横向对比的组织（本章 [§6 案例 1.3](01-adr-section-6-sec6.md) 的做法）。
- 失效边界：ADR 编号若不写进评审的退出条件，「开完会没写 ADR」就会是常态——**把 ADR 当成写作任务，只要有人写就能完成；把它当成流程节点，则要「不写就过不去」**，两者的差别不在模板好坏。

### 3.5 反模式与失效分析

原文件的 10 条反模式全部保留，补上「症状 / 后果 / 成因 / 修法」四段。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「伪 ADR」（当成设计文档） | 记录越写越长，含表结构、接口签名与部署拓扑 | 篇幅与不可变约定冲突：设计必然要改，而记录按约定不该改，于是要么破坏不可变（历史丢失），要么把设计留在错误的载体里 | 把「写清楚」当成目标，没区分 decision log 与 blueprint | 记录只写决策与后果，设计进设计文档并双向链接 |
| 「文档僵尸」 | `docs/adr/` 里最近一条是两年前，改代码的人从没打开过 | 库看起来什么都写了，实际给出的是过期结论——比根本没有记录更难发现，因为它带着权威语气 | 把记录当成写作任务，而不是任何一个环节的必经节点 | 把编号接进评审退出条件与 CI；没有人引用的记录视为未完成 |
| 「过度工程化」 | 50 人团队要求每条记录走 4 周评审 | 团队改用「先在群里说一声」代替流程，记录既没变多也没变准——被绕开的流程比没有流程更糟 | 模板与风险不匹配，评审成本高于决策本身的价值 | 按风险分级：低风险用轻量模板免评审，高风险才走完整流程 |
| 「事后追溯」 | 决策执行完再写，Consequences 只写正面，Options 写成「我们的方案 + 一个明显更差的陪衬」 | 后人读到的是辩护词；上下文变化时无法判断该不该 supersede，于是要么沿用错误结论，要么重开一轮 | 把记录当汇报材料，而不是决策的输入 | 记录在决策之前起草；Options 里至少有一个是「当时真的有人倾向的」选项 |
| 「无人 review」 | 记录只躺在作者的分支里，没有 PR，没有人提过异议 | 决策过程无法成为对齐工具；错误在实现期才暴露，而那时改的成本已经翻倍 | 流程没有把记录纳入评审 | PR 化 + Reviewer 制度，评审退出条件里含「引用对应编号」 |
| 「永不 supersede」 | 明知决策过时也不更新，检索出来的还是旧结论 | supersede 链断裂，检索器与后人以更高置信度采信过期结论（本章 [§7.3.4](01-adr-section-7-sec7.md)） | 直接改实现比写新记录便宜，且没人检查链的完整性 | 把 supersede 写进变更流程；抽 10 条 Accepted 核对实现是否仍一致 |
| 「决策 owner 缺失」 | 每条记录有撰写人，但没有 Decision Owner | 出问题时无人响应，也无法判断该找谁复核；Owner 字段长期为空 | 模板里有 Author 没有 Owner——四段式与 Y-statement 本身都没有这个槽位 | 模板加 owner 字段，且必须落在有权决定的人身上 |
| 「混用术语」 | 同一份材料里，「用 ADR 描述设计」「用 RFC 记已拍板的结论」因人而异 | 读者无法判断一份材料是提案、决策还是蓝图，权威不清，检索时按错误的前提命中 | 组织没有定义三者的边界与产生顺序 | 在库的 README 里写下定义与流转（本章主文件 [§2.4](01-adr.md)） |
| 「缺乏索引」 | 几百条躺在目录里，README 按编号排序 | 回答一个历史问题要人读接近全量；库存在但使用率接近零——「写了」与「能用」之间隔着一次检索设计 | 把「写了」当成「能用」，跳过检索设计 | 先补状态链与主题分类，再谈检索入口与问答 |
| 「无 consequence」 | Consequences 只有好处，或写成「性能更优、维护更简单」这类形容词 | 后人不知道约束边界，无法判断自己的场景是否适用；记录沦为宣传稿 | 记录被当成争取支持的文档 | Consequences 必须写负面代价，并写成机制：成本落在哪里、在什么条件下反转 |

**最危险的三条，在生产中的典型暴露方式：**

「伪 ADR」不会以「文档太长」这种形式暴露，它以**一次重构事故**暴露：半年后有人按记录里的表结构调整了实现，而记录本身因为「不可变」被冻结在旧设计上——错的一方是读者，因为他把 decision log 读成了 spec。修法不是把记录写短，而是在模板里就把「设计不写在这里」说清楚，并让设计文档回链编号。

「无 consequence」的暴露方式是**验收期的争议**：有人问「当初说这个方案更简单，那过渡期的双写成本谁承担」，而记录里只有好处。这条反模式的成本不在系统里，而在**没人能复盘**——决策错了也说不清错在哪一步，于是下一个团队会把同样的取舍再走一遍。

「永不 supersede」最隐蔽：系统在功能上全部正常，问题出在**新人对现状的理解**上。他读到一条 Accepted 的记录，按它推理，得出与今天实现相反的结论，然后把这份矛盾带进评审。此时组织里没有人能立刻说清「哪条是现行的」，因为链断在最不显眼的地方——**它不是记录缺失，而是记录之间失去了关系**。

这 10 条有一条共性：**它们都在把「有一份文档」当成「有一个决策流程」**。文档只要有人写就能存在；流程要求它在某个环节上必须被引用、必须被更新、必须有人负责。选型时判断一套 ADR 实践能不能落地，看的就是这一条。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单团队 → 跨团队（2+ 团队共享接口或数据契约） | Nygard 四段式 | 读者问不到拍板人，四段里没有 Options，同一选型被重开 | MADR + RFC 收敛 | 历史记录需人工回溯补 Options；决策周期被反馈窗口拉长 |
| 库从几十条 → 上百条 | 按编号排的目录 | 回答一个历史问题要人读接近全量【经验】 | 按主题分类 + status / owner / supersedes 字段 | 分类要回溯补，且分类维度本身会成为争议 |
| 决策寿命从「一次迭代」→「跨组织调整」 | 静态 MADR | 「这条决策现在还成立吗」没有依据 | Living（回滚条件 + 监测指标 + 复审时点） | 记录从归档变成持续维护，需要固定人力回写 |
| 单团队浏览 → 组织级聚合与统计 | 自由文本 / 轻量模板 | 无法按状态与主题做统计，跨 BU 重复讨论无法被发现 | 统一结构 + Y-statement（可聚合） | 表达力下降，必须配主文档；结构不统一则无法对比 |
| 人读 → 检索器 / AI 读 | 自由文本 | 检索器分不清过期与现行，会用更流畅的语气把过期结论答出来 | 先补 status / supersedes 字段，再上检索入口 | 补字段按条计、不可自动；补不齐就是补不齐 |
| 内部记录 → 对外举证（合规、客户审计） | 轻量记录 | 缺 Decision Owner 与确认记录，无法作为举证材料 | MADR 全字段 + ADL 索引 + 评审记录 | 评审与确认记录要纳入交付物，流程要能导出 |
| 「先拍板后补写」→「先写再拍板」 | 事后补写 | 补写的 Consequences 只留正面，Options 变成陪衬 | 记录前移到评审之前，作为评审材料（本章 [§6 案例 1.2](01-adr-section-6-sec6.md)） | 要改评审的入口条件：没有记录不允许上会 |
| 单业务 → 多业务并行 | 各业务自定义模板 | 结构不同则无法横向对比与集中检索，并行团队方向撞车到实施阶段才发现 | 统一结构 + 自动结构检查（本章 [§6 案例 1.3](01-adr-section-6-sec6.md)） | 需放弃自定义，并为历史条目补结构 |

判据是统一的：**当「多一个读者 / 多一条记录 / 多一个团队」带来的边际成本开始超过它带来的边际收益时，就该换形态**。这个拐点通常不体现在书写体验上，而体现在**回答一个历史问题的耗时**与**重复讨论的次数**上【经验】：如果新人反复问同一批「为什么」，说明 Options 缺字段；如果检索出来的结论一半已过期，说明状态链断了。

### 3.7 自检清单

- [ ] 库里每一条记录，能不能回答「谁拍板（Decision Owner）」？答不出的是记录，不是决策。
- [ ] Options 段里有没有一个是「当时真的有人倾向的」选项？全是陪衬即为「事后追溯」。
- [ ] Consequences 里有没有写明负面代价，且写成机制（成本落在哪、在什么条件下反转）？只有形容词的等于没写。
- [ ] 随机抽 10 条 Accepted，它们描述的方案还是当前实现吗？对不上的条数就是状态链的断口数。
- [ ] 近三个月的代码 PR 里，有没有任何一条引用过 ADR 编号？没有，说明记录还没进入流程。
- [ ] 记录是否与代码同库、可被 diff 与评审？放在独立文档库的，问一句「谁负责更新」。
- [ ] 回答一个历史问题（如「我们为什么不用 X」）要读几篇？读接近全量，说明缺索引与主题分类。
- [ ] 有没有一条记录把设计细节写进了正文（表结构、接口签名、部署拓扑）？有，就是「伪 ADR」。
- [ ] 库的 README 里，ADR / RFC / Design Doc 三者的边界与产生顺序写清楚了吗？
- [ ] 决策被推翻时，新记录有没有把旧的标记为 Superseded 并互相链接？还是直接改了实现？
- [ ] 有没有明确「什么决策必须写」的触发条件（跨团队、难回滚、引入新依赖、违反直觉、成本显著）？没有触发条件，库会先变成流水账、再变成空库。
- [ ] 长生命周期决策有没有写回滚条件与复审时点？没有，半年后没人能判断它是否仍成立。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 单团队、决策可逆、读者是自己 | Nygard 四段式 | 恢复成本低于记录成本时，字段越多越是浪费 |
| 跨团队、涉及接口与数据契约 | MADR（Options 必写） | 读者问不到人，只能靠记录复现当时的约束 |
| 库上百条、按主题找决策 | MADR + Pattern-based 分类 | 人读成本随库线性上升，分类把它变成先定位再读 |
| 需要组织级统计与聚合 | 统一结构 + Y-statement | 只有带固定槽位的短句能被抽取、聚合、跨条关联 |
| 需要量化依据但保留极简正文 | Lightweight ADR + Decision Matrix | 把结论与依据分载，不可变约定与可争论过程才不打架 |
| 决策寿命跨组织调整、要能判断是否仍成立 | Living ADR（回滚条件 + 监测指标 + 复审时点） | 可判断性来自写死的触发条件，不来自事后回忆 |
| 要对外举证 / 客户审计 | MADR 全字段 + ADL 索引 + 评审记录 | 举证要的是可引用的序号化记录，不是一篇好文档 |
| 有库但没人引用 | 把编号接进评审退出条件与 CI | 不被引用的记录等于不存在，问题在流程不在模板 |

> 本节小结：决定这六个模板该选哪一个的**唯一那条约束，是「记录要服务的未来读者与当时拍板的人之间隔着多远」**——时间距离决定要不要写 Options，组织距离决定载体能不能是 wiki 与聊天记录，而库的规模只是「距离变远、读者变多」之后才出现的第二层结果。判断选对了没有，也只需看一件事：**一个没参与过这次决策的人，能不能只靠这条记录，判断它今天是否仍然成立**。
