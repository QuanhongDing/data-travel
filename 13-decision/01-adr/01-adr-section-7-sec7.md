## 7. 与其他方法对比

> 原 § 7 共 47 行、为打分表 + 决策树 + 组合罗列，缺少机制解释与可溯源证据，重写为 ~300 行对比与选型工程。

### 7.1 先立判据：为什么打分表会误导

原表在「可追溯性 / 讨论过程 / 决策速度 / 文档成本 / AI 友好度 / 跨团队可用 / 风险可控」七个维度上，给「临时讨论 / 设计文档 / RFC / ADR / AI 辅助 ADR」五个候选打 1–5 分。这些维度问得并不错，问题在于**分数替代了论证**：「讨论过程」这一栏 ADR 拿 3 分、RFC 拿 5 分，但 3 与 5 之间差的是什么？是多一轮评审、多两周时间，还是多一个必须有人主持的会议？没有单位的分差无法复现，也无法在两个组织之间核对。

更要命的是**这些维度的权重由组织形态决定，而不是由文档形态决定**。在 8 人、一个会议室能坐下所有人的团队里，「决策速度」是主导项，临时讨论 + 群里同步一条消息就够了，写 ADR 是净成本；在 200 人、决策要跨 4 个部门才能落地的组织里，「可追溯性」与「跨团队可用」变成主导项，此时哪怕每条决策写满一页 MADR 也是省的——因为一次「我们当初为什么没选 X」的重复争论，成本远高于文档本身。打分表把「你的组织形态」这个前提抹掉了，于是把**场景相关的结论**伪装成了**绝对结论**。

原表还有一处层级混淆：它把「ADR」与「AI 辅助 ADR」并列成同一层的两个候选。但 AI 辅助在机制上不是一种记录形式，而是**挂在某种记录形式之上的一层起草与检索**（本章 §5.2.1、§5.2.2）。没有状态字段、没有可检索的语料，AI 辅助就没有输入，只能生成一份排版漂亮但无历史可依的文档。把不同层的东西并列打分，会让人以为可以跳过模板与流程直接上 AI。

**候选之间还有一处常被忽略的不对称**：临时讨论不产生文档，「不写」这件事本身没有显式产物，于是它的成本从不出现在对比表里。本章把它当作一个正式候选保留（原表也保留了它），因为**在很多团队里它才是事实上的默认选项**，而选型的真正问题往往不是「选哪个模板」，而是「这件事值不值得留下记录」。

**把每个维度还原成一个可核验的问题，打分表立刻变得可用**——因为这些问题问的是「你的组织现在是什么样」，而不是「哪个候选更先进」：

| 原维度 | 换成可核验的问法 | 这个问题导向哪条机制 |
| --- | --- | --- |
| 可追溯性 | 三个月前那个决定，现在能不能找到是谁拍的板、当时否掉了什么？ | 7.3.2 载体与权威 |
| 讨论过程 | 反对意见是在拍板前被记录，还是只在走廊里说过？ | 7.3.1 时间位置 |
| 决策速度 | 从提出到落地要过几道会？其中几道会真的改变结论？ | 7.4 成本结构 |
| 文档成本 | 写一条要几分钟？评审一条要几个人几分钟？ | 7.4 成本结构 |
| AI 友好度 | 库里有多少条带了 status / owner / supersedes？ | 7.3.4 机器可读性 |
| 跨团队可用 | 别的团队想复用这个决策，找得到吗？找得到之后信得过吗？ | 7.3.2 + 7.3.4 |
| 风险可控 | 决策错了以后，多久能发现、靠什么发现？ | 7.3.3 变更语义 |

**本章采用的 6 条判据**（全部针对组织与决策机制，不针对文档模板好坏）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 能力边界 | 它**做不到**什么 | 临时讨论做不到「三个月后回答为什么当初这么选」，因为它没有载体；ADR 做不到描述完整实现方案，它是 decision log 不是 spec |
| 变更语义 | 决策被推翻后，旧记录怎么办 | 就地编辑的文档会静默改写历史；不可变 + supersede 会在链上留下痕迹，代价是读一个主题要读多份 |
| 载体与权威 | 决策的权威落在谁手里 | 落在人脑里则随人流失；落在代码仓库里则能被 diff、被评审、被 CI 校验，但要求写的人会用 git |
| 同步成本 | 拉一个新团队进来要付多少 | 决策半径每增加一个团队，知情成本上升；RFC 是唯一把「对齐」显式摊到决策前的机制 |
| 检索成本 | 库变大后，回答一个历史问题要读多少篇 | 人读目录的成本随 ADL 规模增长，超过阈值后「有没有记录」和「能不能查到」是两回事 |
| 演进风险 | 模板与流程会不会成为负担 | 流程成本高于决策本身时，团队会绕开流程——被绕开的流程比没有流程更糟 |

### 7.2 候选方案全景

原表对比的五个候选全部保留（临时讨论 / 设计文档 / RFC / ADR / AI 辅助 ADR），并按本章 §3.1 的模板谱系把 ADR 展开为具名形态。

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 成本形态 |
| --- | --- | --- | --- | --- |
| 临时讨论 | 事实上的默认选项 | 决策留在在场人的记忆与聊天记录里 | 小团队、低风险决策 | 无显式成本，代价滞后发生 |
| 设计文档（Design Doc） | 决策后、实现前的蓝图 | 描述「怎么设计」，决策理由夹在正文里 | 工程主导的组织 | 按页数计的人力 |
| RFC（Request For Comments） | 决策**前**的收敛机制 | 提案 + 反馈窗口 + 逐版修订 | 大型开源项目、跨团队技术委员会 | 参与者人数 × 反馈窗口时长 |
| ADR（Nygard / MADR 等） | 决策时刻的归档单元 | 一条决策一份不可变文档 + 状态字段 | Nygard 四段式、MADR、Y-statement | 按条计的人力 + 评审人力 |
| AI 辅助 ADR | 挂在 ADR 之上的起草与检索层 | 草拟、查重、候选 supersede 检测 | 见本章 §5.2 展开的四个方向 | token + 语料与索引维护 |

**这些候选其实分三族**：第一族「不落文档」（临时讨论）；第二族「落文档但决策理由不是主角」（设计文档——主角是设计；RFC——主角是提案与讨论过程）；第三族「决策本身是主角」（ADR 及其变体）。**同族内部差异小、跨族差异大**：Nygard 四段式、MADR、Y-statement 之间的差别主要是字段多少与是否可解析，而族与族之间的差别是「这份文档的首要服务对象是谁」——是设计者、讨论者，还是三个月后要重新判断的同一个人。先分族再选，比较量减半。

还有两个候选不在原表里，但它们在实际组织里经常是 ADR 的替代品，忽略它们会让选型结论失真：

- **代码本身与提交信息**。当决策直接落成代码时，「为什么」常常被塞进 commit message 或 PR 描述。它的问题不是没写，而是**与代码同生命周期**：代码重构掉，理由也一起消失；而 ADR 的价值恰恰是在代码已经不在了的时候还能读到。
- **知识库条目（Confluence / wiki 一类）**。它看起来比 ADR 更容易写，代价是既没有状态字段也没有版本语义——**过期条目不会被标记，只会被继续引用**（见 7.3.3）。

需要强调的是，**这七个候选在同一个组织里通常是并存的，问题不是「选一个」，而是划清各自的适用面**：低风险决策走临时讨论，跨团队提案走 RFC，决策结论进 ADR，实现方案进设计文档。真正的选型失败不是「选了错的那一个」，而是**其中某一个被当成了万能容器**——用 ADR 承载设计方案，或用 RFC 承载已经拍板的结论，都会让整个体系产生的信息量下降。

### 7.3 机制差异：为什么它们表现不同（核心节）

四个机制维度：文档挂在决策流程的哪一段（7.3.1）、决策的载体与权威（7.3.2）、变更语义（7.3.3）、机器可读性（7.3.4）。

先给五个候选在四条机制上定位一次：

| 机制维度 | 临时讨论 | 设计文档 | RFC | ADR | AI 辅助 ADR |
| --- | --- | --- | --- | --- | --- |
| 时间位置 | 决策当场 | 决策后、实现前 | 决策前 | 决策时刻 | 不改位置，改起草与检索成本 |
| 载体 / 权威 | 人脑 + 聊天记录 | 文档系统 | 评论流 + 讨论记录 | 与代码同库的 Markdown | 不新增载体 |
| 变更语义 | 无记录可变更 | 就地编辑 | 新 RFC 覆盖 | 不可变 + supersede | 出建议，不改状态 |
| 机器可读性 | 无 | 低（自由文本为主） | 低-中（有提案结构） | 中-高（状态 + 字段） | 高（依赖字段完整度） |

#### 7.3.1 文档挂在决策流程的哪一段

**机制是什么**：这份文档是在决策**之前**、**当下**还是**之后**产生的——位置决定了它能影响什么。

**各候选的差异**：

| 候选 | 位置 | 在决策中起什么作用 | 时延代价 |
| --- | --- | --- | --- |
| 临时讨论 | 决策当场 | 收敛在场人的意见 | 几乎为零 |
| RFC | 决策之前 | 把异议与约束在拍板前暴露出来 | 反馈窗口有多长，决策就慢多久 |
| ADR | 决策时刻 | 固定结论与取舍，供未来质疑 | 撰写与评审的人力 |
| 设计文档 | 决策之后 | 指导实现，不参与选择 | 不参与决策，故不能减少返工 |
| AI 辅助 ADR | 与 ADR 相同 | 降低起草与查找成本 | 语料维护 |

**由此必然导出的性质**：**因为 RFC 是「提案 + 反馈窗口」，所以它天然把延迟写进了流程——反馈窗口多长，决策就慢多久，换来的是约束在拍板前被暴露；因为 ADR 是归档，所以它几乎不消耗决策周期，但也无法在决策前暴露异议。代价是这两者不能互相替代：想用 ADR 达到「对齐」的效果是做不到的，想用 RFC 达到「可追溯」的效果也不够——RFC 讨论完就冻结，后续决策的变更不会自动回写到 RFC 上。** 组织里最常见的错配，正是用其中一种去代替另一种。

**公开证据**：【公开】本章主文件 §1.1 记录 ADR 概念由 Michael Nygard 在 2011 年的《Documenting Architecture Decisions》中系统化；【公开】本章主文件 §2.1 记录其 Status 的取值为 Proposed / Accepted / Deprecated / Superseded by ADR-XXXX；【公开】本章主文件 §1.4 记录 MADR 于 2017 年发布，其字段结构见本章 §3.1 模式 2（在 Nygard 四段之上增加 Decision Drivers、Considered Options 与 Confirmation 段）。**具体模板字段请以 MADR 官方模板与所用工具的当前版本为准，本节不对第三方产品的流程细节作断言。**

**失效条件**：决策频率高、单个决策影响面小时，在决策前加一层反馈窗口是纯延迟——此时真正的瓶颈不是「对齐不够」，而是「决策太多，每一个都不值得对齐」。

**判定方法**：翻一次上季度的会议记录，看有多少条决策是「会开完了才第一次有人提出反对」。这个比例高，说明该上 RFC；如果是「提案挂了两个月没人回」，那问题不在流程位置，而在没人被指定为决策者。

#### 7.3.2 决策的载体与权威

**机制是什么**：决策最终权威地存在于哪一个载体上，决定它会不会随人流失、能不能被评审与校验。

**各候选的差异**：

| 载体 | 权威归谁 | 可被谁校验 | 人离开后还剩什么 |
| --- | --- | --- | --- |
| 人脑 + 聊天记录 | 在场的人 | 无 | 搜索结果里留几个断片 |
| wiki / 知识库 | 最后编辑的人 | 读者 | 一条状态不明、可能是过期结论的条目 |
| RFC 评论流 | 提案人与决策者 | 读过整条讨论的人 | 一份冻结的讨论记录 |
| ADR（与代码同库） | Decision Owner | 任何人，含 CI 与门禁 | 一份可 diff、可双向链接的决策记录 |

**由此必然导出的性质**：**因为 ADR 与代码同库，所以决策可以被 diff、被 PR review、被 CI 校验（例如「改了某模块必须引用对应 ADR 编号」这类门禁才可行），代价是它继承了代码仓库的门槛——写 ADR 的人要会用 git 与 Markdown，这在非工程团队是真实障碍，于是「谁写」这个问题会决定 ADR 库覆盖的是哪一类决策。** 一个只有工程团队在写的 ADR 库，必然缺失那些在业务会议上口头拍板的架构决定，而那往往才是最难追溯的部分。

**公开证据**：【公开】本章主文件 §1.4 记录 ThoughtWorks 技术雷达 2014 年收录 ADR 实践（Trial）；【公开】`docs/adr/` + 编号文件名的目录约定与 adr-tools 一类自动化脚本可在公开仓库中核验（可按 adr-tools、MADR 官方仓库检索）。**本节不断言某产品在某版本支持某项功能。**

**失效条件**：当写了没人看时，与代码同库的优势消失——它与代码一起被 clone，也一起被忽略。这正是 7.3.4 要解决的问题。

**判定方法**：在代码评审记录里检索 ADR 编号。若近三个月的 PR 里没有任何一条引用过 ADR，说明决策记录与工程实践之间还没有建立连接——载体再对，也还是没进入流程。

#### 7.3.3 变更语义：不可变 + supersede vs 就地编辑

**机制是什么**：决策被推翻之后，旧记录怎么处理——是改写它，还是保留它并由新记录接管。

**各候选的差异**：

| 候选 | 变更方式 | 读者怎么知道它过时了 | 留下的痕迹 |
| --- | --- | --- | --- |
| 临时讨论 | 无记录 | 无法知道 | 无 |
| wiki 条目 | 就地编辑 | 靠人发现内容与现状不符 | 编辑历史（极少有人看）|
| 设计文档 | 就地编辑或另起新版 | 靠标题里的版本号 | 多份并存，权威不清 |
| RFC | 新提案覆盖，旧提案冻结 | 靠状态标注 | 讨论过程完整保留 |
| ADR | 原文件不改，写新 ADR 并把旧标记 Superseded by ADR-XXXX | 状态字段直接可读 | 决策族谱 |

**由此必然导出的性质**：**因为 ADR 不可变且用显式关系字段连接新旧记录，所以「为什么变了」本身就是可读内容，检索时也能靠状态字段把过期结论过滤掉；代价是读一个主题要沿链读多份文档，而且这条链一旦断掉——有人直接改了实现却没写新 ADR——就会出现「实现与记录不一致」的静默腐坏，它比「根本没有记录」更难发现，因为库里看起来什么都写了。** 这也是为什么 supersede 必须与代码评审挂钩（本章 §3.3 反模式 6「永不 supersede」）：链的完整性靠约定维持不住。

**公开证据**：【公开】Superseded 是 Nygard 2011 模板 Status 段的合法取值（本章主文件 §2.1 记录其取值为 Proposed / Accepted / Deprecated / Superseded by ADR-XXXX）；【公开】MADR 用 status 的取值（如 `Superseded by ADR-0123`）表达同一语义，其模板字段里没有独立的 supersede 关系字段（字段清单见本章 §3.1 模式 2，本章 §5.4 对 MADR 的判断与此一致）。**在检索场景下这条差别会被放大**：没有状态链的库，检索器会把过期决策以更高的置信度答出来——本章 §5.2.2 的原话是「没人读的过期 ADR 是无害的，被检索出来的过期 ADR 是误导」，原因是它带着「据我们所记录」的权威语气。

**失效条件**：决策的变更频率高于撰写与评审能承受的频率时，supersede 链会断裂。此时更安全的做法不是放弃记录，而是换更轻的形态（Y-statement 一句式），**因为「轻而完整」比「重而断链」可用**。

**判定方法**：随机抽 10 条状态为 Accepted 的 ADR，核对它们描述的方案是否还是当前实现。对不上的条数就是链的断口数——**断口不需要精确统计，只要发现存在，就说明 supersede 没有接进变更流程**。

#### 7.3.4 机器可读性：字段化到什么程度才值得

**机制是什么**：AI 与检索器的可用性，取决于状态与关系字段是否显式——显式的字段让判断降级为核对。

**各候选的差异**：

| 形态 | 可被机器利用的字段 | 能支撑什么 | 填写成本 |
| --- | --- | --- | --- |
| 自由文本 | 无 | 全文检索 | 最低 |
| 字段化模板（MADR 类） | status / date / deciders / consulted / informed | 过滤、统计、按状态排除过期 | 中 |
| 单句结构化（Y-statement） | context / concern / option / goal / consequence | 抽取入图、跨 ADR 关联 | 低（但表达力受限）|
| 上述 + 关系字段 | supersedes / superseded-by | 决策族谱，supersede 检测从判断降级为核对 | 低（但要求有人维护）|

**由此必然导出的性质**：**因为状态链与关系字段是显式的，所以「哪条决策已被取代」这个问题从需要判断变成可以直接核对，检索器不必靠文本相似度去猜；代价是模板会僵化——把「探索性决策」「一次会议产出多条决策」这类形态硬塞进模板，会产出一批字段齐全但内容不可信的 ADR，而填了 status 却没人真的维护它，比不填更危险（因为它会带着权威语气被检索出来）。**

**公开证据**：【公开】Y-statement 句式见本章 §2.1 的定义，其流行时间本章主文件 §1.4 记为 2018 年前后；【公开】向量检索与长上下文问答均为已 GA 的组件，各厂商正式文档可核验；【公开】Microsoft Research 于 2024 年发布 GraphRAG（arXiv 预印本，可按标题检索核验），说明「把文档拆成实体关系再做全局问答」在研究上成立。**「ADR 语料问答」在公开渠道以厂商演示与个人实践为主，本节未见可核验的第三方生产案例**——本章 §5.1 因此对这一方向采用**降级口径**，即原判据第二条（第三方生产案例）不可得时启用的替代判据：**失败可回退 + 不引入新的决策权威**，落到选型上就是：可以小规模自建验证，不要在关键决策链上依赖它。

**失效条件**：ADL 只有几十条时，字段化的收益低于填写成本——此时全文检索就够了，强制模板反而会让人放弃记录。

**判定方法**：统计库里带全部关键字段（status / owner / date / supersedes）的条目占比。这个占比同时是「检索器能不能用」和「AI 辅助有没有输入」的同一个前提，所以它值得作为一个可长期观察的指标，而不是一次性检查项。

### 7.4 成本结构对比（不是价格表，是成本函数）

五类候选的成本函数形式不同，主导项也不同：

```
临时讨论        成本 ≈ 0 + 重做决策的期望损失（滞后发生，不被计入）
设计文档        成本 ≈ 文档数 × 页数人力
RFC             成本 ≈ 参与者人数 × 反馈窗口时长 + 提案人修订人力
ADR             成本 ≈ 决策条数 × (撰写人力 + 评审人数 × 评审时长) + ADL 检索与维护
AI 辅助 ADR     成本 ≈ ADR 全部成本 + 语料与索引维护 + token(语料规模 × 查询次数)
```

| 候选 | 主导项 | 隐性成本（不体现在账单上） |
| --- | --- | --- |
| 临时讨论 | 零显式成本 | 决策重做：重开会 + 重新调研 + 重新说服，分散在几个月里，组织感觉不到 |
| 设计文档 | 页数 × 人力 | 决策理由夹在正文里，改设计时顺手被改写，历史因此丢失 |
| RFC | 参与人数 × 反馈窗口 | 大范围 RFC 会拖慢一切，包括那些不值得被讨论的决策 |
| ADR | 决策条数 × (撰写 + 评审) | 评审人力才是真瓶颈：它随组织规模增长，而撰写不随 |
| AI 辅助 ADR | token 与索引维护 | 语料治理（改了要重索引）+ 权限同步（ADR 正文常含未公开的缺陷与供应商结论） |

**两条推导链**：

- **轻量模板 vs 完整模板的撰写成本**【经验】：Nygard 四段式与 Y-statement 通常在 0.5–1 人时量级；完整 MADR 把撰写本身记为 30–60 分钟（本章 §3.1 的估计），多出来的是 Considered Options 的调研与对账——**而选项调研才是真正花时间的那一步**，模板只是让它变得必须做。
- **记录成本在组织产能里的占比**【推算】：设 40 人团队每季度做 10 个中大型决策，每个决策的 RFC 讨论 + ADR 撰写 + 评审合计 1–3 人日，则每季度消耗 10–30 人日【推算：10 × 1 至 10 × 3】；按每人每季度约 60 个工作日估算，团队季度产能约 2,400 人日【推算：40 × 60】，占比 0.4%–1.3%【推算：10/2400 至 30/2400】。这个比例说明：**记录本身的成本从来不是瓶颈**，瓶颈是评审参与者的时间——它等于「评审人数 × 每场时长 × 决策数」，随组织规模增长得比撰写快。

**成本随什么增长，决定了你该优化什么**：如果瓶颈是「会议太多」，要压缩的是必须走 RFC 的决策范围，而不是把模板改短；如果瓶颈是「找不到历史决策」，要补的是检索入口与状态字段，而不是写得更详细；如果瓶颈是「写了没人看」，问题既不在模板也不在检索，而在于这个组织还没有一个必须引用 ADR 的环节（详见 7.7 的反模式）。

| 观察到的症状 | 真正的主导项 | 该动的地方 |
| --- | --- | --- |
| 会议排满、决策仍在等 | RFC 的反馈窗口 × 决策数 | 缩小必须走 RFC 的决策范围，而不是缩短评审时长 |
| 每条 ADR 都写得很好，但没人引用 | 缺一个强制引用的环节 | 把 ADR 编号接进评审退出条件与 CI |
| 库很大，问题照样答不上来 | 检索成本随 ADL 规模增长 | 补状态链与主题分类，再上检索入口 |
| 撰写负担已经很重 | 评审人数 × 时长（不是撰写本身） | 按风险分级，低风险决策免评审 |

这条表的用法与 7.4 的成本函数一致：**先定位主导项，再决定优化对象**——把预算花在非主导项上，是治理工作里最常见的一种浪费。

### 7.5 决策树（每个分支都要有阈值依据）

```
你要做一个架构决策
  │
  ├─ 这个决策可逆吗？（恢复成本是否远低于记录成本）
  │     └─ 可逆且影响面小 → 临时讨论 + 群组同步留一条消息；不写 ADR
  │
  └─ 不可逆或影响面大 → 看决策半径
        │
        ├─ 单团队、不影响对外接口与数据契约 → ADR（Nygard 四段式 / MADR 轻量版）
        │
        ├─ 跨团队（两个及以上团队的接口、数据契约或平台依赖）→ RFC 收敛 → ADR 归档
        │
        ├─ 战略级 / 涉及外部承诺 / 需合规举证 → RFC + 多轮评审 + ADR（Living 模式：含回滚条件与监测指标）
        │
        └─ 历史库已过检索阈值（人翻目录不可行）→ ADR 标准化（status / owner / supersedes 字段齐全）
               └─ 在此之上再挂 AI 辅助起草、检索问答、候选 supersede 检测与决策图谱（KG / Decision Intelligence）
```

**阈值依据**（与树上的判断节点一一对应）：

- **「可逆吗」**：判据是比较恢复成本与记录成本。记录成本在 0.5–1 人时量级（7.4），恢复成本是重做决策的人日量级；**当恢复成本低于记录成本约一个数量级时，写 ADR 是负收益**【经验：这条「一个数量级」的写法给的是一个保守的止损线，不是精确盈亏平衡点】。
- **「决策半径」这个中间判断**：不可逆或影响面大的决策，接下来要看它波及几个团队——**「两个及以上」就是这里的阈值**，因为从两个团队开始，「对方知不知道我选了什么」不再能靠走廊沟通保证，而它一旦失守，失效模式就从「选错」升级为「选错且互不知情」。
- **「单团队、不影响对外接口」**：只要决策的失效范围还在一个团队的代码边界内，口头对齐就能完成闭环——此时 ADR 的作用是归档，不是对齐。一旦跨到别的团队的接口或数据契约上，就得靠文档消除信息差（机制依据见 7.3.2 的载体与权威）。
- **「战略级 / 涉及外部承诺 / 需合规举证」**：到达这一档时，文档从「最佳实践」变成「举证材料」——本章 §6 案例 1.4 记录 AWS Well-Architected 评审把架构评审结构化成「支柱 × 问题清单」，其产出正是可被外部审计引用的一类材料；序号化、可引用的记录是这套做法能被复用的前提。
- **「Living 模式」**：长生命周期决策（基础设施迁移一类）需要在决策时写下回滚条件与监测指标，否则「这条决策现在是否仍然成立」这个判断没有依据（本章 §3.1 模式 6）。**判据是决策的预期寿命**：寿命超过一次组织调整周期的决策，才值得带上回滚条件。
- **「检索阈值」**：这是【经验】区间——几十条以内，按编号或主题排的目录足够人读；上百条之后，回答「我们为什么不用 X」需要人读接近全量，检索入口的收益才开始超过字段化模板的填写成本。**判据不是条数本身，而是「回答一个历史问题平均要读几篇」**，条数只是它的代理指标。
- **最末一支「在此之上再挂 AI 辅助起草、检索问答、候选 supersede 检测与决策图谱」**：它不是与前几个分支并列的独立选项，而是挂在字段化 ADL 之上的一层增强，所以它排在「检索阈值」之下而不是旁边。判据是状态与关系字段的完整度（7.3.4 的判定方法）：字段不齐时先补字段，再谈检索问答与 supersede 检测，否则这一层会以更高的置信度把过期结论答出来（§5.2.2）。

**把树走一遍（一次真实的选型路径）**：某公司数据平台组 60 人、跨 3 个团队，正在决定「湖仓表格式用 Iceberg 还是 Delta」。

1. 可逆吗？——表格式一旦选定，迁移要重写全部写入链路与消费者的读路径，恢复成本远高于记录成本，走「不可逆」分支。
2. 决策半径？——写入链路归平台组，读取归分析与算法两个团队，跨团队成立，走「RFC 收敛 → ADR 归档」。
3. 于是产出两份东西：RFC 承载方案对比与反馈窗口内的意见，ADR 承载最终结论与后果；**RFC 里被否掉的那个选项要留在 ADR 的 Considered Options 里**，否则半年后会有人重新提一遍。
4. 这条决策的寿命是多长？——表格式是基础设施级选择，寿命超过一次组织调整，因此按 Living 模式补上回滚条件（哪些场景下会重新评估）与监测指标（迁移完成度、双写一致性）。
5. 是否够「战略级 / 需外部举证」？——不需要，故不加多轮评审，避免把流程做到超过决策本身的价值。

这个例子里最容易做错的是第 3 步的后半句：**只写选中的方案，不写被否掉的选项**。它的代价不会立刻显现，而是在下一次有人重新提出同一选项时才暴露——那时没人说得清当初为什么否掉它，只能再比一轮。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 5–10 人、单系统、决策可逆 | Nygard 四段式轻量 ADR | 临时讨论 + 群组同步 | 完整 MADR 的选项调研成本高于决策本身的价值 |
| 10–50 人、长期决策 | MADR + Decision Matrix | Nygard 轻量 | 轻量模板缺 Considered Options，后人无法质疑结论 |
| 50–200 人、跨团队 | MADR + 按主题分类（`adr/data/`、`adr/platform/`） | ADR + 标签 | 单层目录在数百条时不可检索 |
| 200+ 人、组织级治理 | Y-statement（可聚合） + Living ADR | 按主题分类 + Decision Matrix | 自由文本无法做组织级聚合与统计 |
| 需要 AI 辅助 | 字段化模板（status / owner / date / supersedes）+ 检索入口 | 自由文本 + 人工维护索引 | 没有状态链的库，检索器答得越流畅误导越深（§5.2.2） |
| 强合规、需对外举证 | MADR 全字段 + ADL 索引 + 评审记录 | 轻量 ADR | 轻量模板缺 Decision Owner 与确认记录 |
| 决策理由是商业敏感信息 | 私有库 + 权限与 ADL 一致 | 公开库 | 问答入口若权限宽于 ADL，就成了绕过权限的旁路（§5.2.2） |

**六条常见组合**（原表列的六条全部保留，每条说清职责边界与运维代价）：

1. **ADR + RFC**：RFC 负责「拍板前把异议与约束暴露出来」，ADR 负责「拍板后把结论与取舍固化」。边界是时间点，两个都要有，但不能互相顶替。运维代价：决策周期被反馈窗口拉长，且需要有人负责把 RFC 的结论准确搬进 ADR——搬错一次，后续所有引用都错。
2. **ADR + 设计文档**：ADR 记「为什么」，设计文档记「怎么设计」（decision log vs blueprint，本章 §2.4）。边界是「变了的是理由还是方案」。运维代价：两份文档极易漂移，必须在设计文档里显式回链 ADR 编号，并在 ADR 被 supersede 时检查引用它的设计文档。
3. **ADR + KG（决策图谱）**：把 Y-statement 与 supersede 关系抽成图，支持「我们为什么不用 X」这类多跳问题。边界是图只承载结构与关系，不承载判断。运维代价：关系边要人工确认，图的可用性完全取决于状态链的完整度——链断了，图会给出看似有据的错误路径。
4. **ADR + AI 助手**：LLM 起草与评审、查重、候选 supersede 检测（起草与评审降的是排版成本，不是上下文成本，见 §5.2.1；查重与 supersede 检测把「读」的成本从 O(N) 人读降到 O(1) 检索，是另一条机制，见 §5.2.2）。边界是 AI 只出建议，不改状态、不替人签字。运维代价：语料与索引维护 + 权限同步，且 ADL 里未公开的缺陷描述会成为泄露面。
5. **ADR + 架构评审**：评审是流程，ADR 是产物——同一个环节的两端。边界是 ADR 编号必须写进评审的退出条件，否则「开完会没写 ADR」是常态。运维代价：评审会不开就不产出 ADR，所以 ADR 的产量会被会议节奏限制。
6. **ADR + 技术债**：技术债的偿还与不偿还都是决策，写进 ADR 才能让「为什么现在不做」与「什么时候做」同时留痕。边界是 ADR 记决策，技术债清单记状态。运维代价：两处维护容易口径不一致，需要约定哪个是权威（通常以 ADR 为权威，清单只存引用）。

### 7.7 选错的代价与迁移成本

**反模式：事后补 ADR（叙事合理化）** —— 症状：决策执行完再写，Consequences 只写正面，Considered Options 写成「我们的方案 + 一个明显更差的陪衬」。后果：后人读到的是辩护词而不是决策依据；上下文变化时无法判断该不该 supersede，于是要么继续沿用错误结论，要么重开一轮讨论。正确做法：ADR 在决策**之前**起草（本章 §3.3 反模式 4），并确保 Options 段里至少有一个是「当时真的有人倾向的」选项。

**反模式：用 ADR 当设计文档** —— 症状：ADR 长到十几页，含表结构、接口签名与部署拓扑。后果：篇幅与不可变约定冲突——设计必然要改，而 ADR 按约定不该改，于是要么破坏不可变（历史丢失），要么把设计留在错误的载体里（ADR 是 log，不是 spec，本章 §3.3 反模式 1）。正确做法：ADR 只写决策与后果，设计与实现细节放设计文档，双向链接。

**反模式：有库无检索，只按编号排目录** —— 症状：几百条 ADR 躺在 `docs/adr/` 里，README 按编号排序。后果：回答一个历史问题要人读接近全量（7.3.4 的失效条件），库存在但使用率接近零——**「写了」和「能用」之间隔着一次检索设计**。正确做法：补状态链与主题分类，再谈检索入口。

**反模式：流程重到被绕开** —— 症状：50 人团队要求每条 ADR 走 4 周评审（本章 §3.3 反模式 3）。后果：团队开始用「先在群里说一声」代替流程，于是记录既没多、也没准。正确做法：按风险分级——低风险决策用轻量模板免评审，高风险决策才走完整流程。

四个反模式有一个共同的根源：**把 ADR 当成一种写作任务，而不是一个流程节点**。写作任务只要「有人写」就能完成，流程节点则需要「不写就过不去」——两者的差别不在模板好坏，而在于它有没有挂在某个必须经过的环节上（评审的退出条件、CI 门禁、PR 模板）。选型时判断能不能落地的，就是这一条。

**换成另一个要动什么**：

| 从 → 到 | 历史记录迁移 | 流程改写 | 工具 / 基建 | 团队再学习 |
| --- | --- | --- | --- | --- |
| 临时讨论 → ADR | 无历史可迁（这正是它的代价） | 需要定义「什么决策必须写 ADR」 | `docs/adr/` + 模板 + PR 流程 | 低-中：四段式与状态约定 |
| 设计文档 → ADR | 需从历史文档里人工回溯抽决策 | 设计文档保留 blueprint 职责，理由回链 ADR | 双向链接约定 | 中：先要划清两者边界 |
| RFC → ADR（并入） | RFC 归档为已接受，ADR 引用其编号 | 把结论从评论区搬进 ADR 正文 | 同一仓库即可 | 低：同为仓库内文档 |
| 无状态链 → 字段化 ADL | 需人工补 status / owner / supersedes（按条计，不可自动） | 明确 supersede 的触发与审批 | 加索引与检索入口 | 中：要接受「补不齐就是补不齐」 |

量级说明【经验】：四行的主要成本都在**人工回溯与对账**，与历史条数成正比；第三行最轻（结论已在同一仓库里，只是换个位置），第一行最轻也最重——没有历史要迁，但也意味着组织过去所有决策的理由都已经不可恢复。

**什么时候不该引入 ADR**：出现下面任意一条时，先解决它，再谈模板与流程。

- 决策权本身不清：谁拍板都要现问——此时 ADR 能记录结论，但记录不了「该由谁决定」，写出来的 Owner 字段会长期是空的。
- 团队还没有代码评审习惯：ADR 与代码同库的价值依赖评审环节，没有评审时它等同于 wiki 条目。
- 决策量远大于团队消化能力：每个季度几十条中大型决策的团队，正确动作是减少决策数，而不是提高记录效率。
- 引入的动机是「别人都有」：说不出当前哪一次决策因为没记录而重做，就无法验证引入后的收益。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 小团队、决策可逆 | 临时讨论 + 一条群消息 | 记录成本高于恢复成本 |
| 单团队、影响一处代码 | Nygard 四段式 ADR | 决策半径小，归档即可 |
| 跨团队、涉及接口与数据契约 | RFC → ADR | 知情成本只能靠文档消除 |
| 战略级、不可逆、要对外举证 | RFC + 多轮评审 + Living ADR | 需要回滚条件与可引用记录 |
| 库已上百条、查不动 | 先补状态链与主题分类，再上检索 | 状态链是检索可用的前提 |
| 想用 AI 起草 / 检索 | 先字段化，再上 AI | 没有字段与语料，AI 没有输入 |
| 有 ADR 库但没人引用 | 把 ADR 编号接进评审退出条件与 CI | 不被引用的记录等于不存在 |
| 决策权本来就不清 | 先明确 Decision Owner，再谈记录 | 记录能固化结论，不能产生决策权 |
| 团队还没有代码评审习惯 | 先用 wiki + 状态字段起步 | 与代码同库的价值依赖评审环节 |

> 本节小结：这几个候选之间**唯一真正起决定作用的差异，是决策有没有被当成一个有编号、有状态、有作者的独立对象**。它一旦成立，supersede、检索、图谱、AI 辅助都只是挂在它上面的能力；不成立时，再多的文档也只是文本——设计文档会随设计改掉，wiki 条目会过期而不自知，聊天记录会随人流失。其余差别（用哪个模板、要不要 AI、评审几轮）都是可以随组织成熟度调整的战术选择，只有这一条是结构性的。
