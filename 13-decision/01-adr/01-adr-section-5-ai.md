## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

趋势清单的根本问题不是列错了，而是**没有时间维度**。同一份清单里，「已经有第三方在生产里用」和「某个厂商演示里跑过一次」被并列成两条同级条目，读者据此排路线图时会把后者当成前者。ADR 这个主题尤其容易踩这个坑，因为 ADR 是典型的**低频、高价值、无即时反馈**的工件：写它的成本由作者在当下承担，收益归未来某个可能根本不会来的读者。这类工件的成熟度不能靠「功能存不存在」判断，只能靠「有没有人在真实组织里用它走完了完整的一轮」。

第二层判断是**机制**：AI 在一个方向里到底改变了什么。本节对每个方向只问一句「AI 改变了哪个机制」——是改变了成本函数、改变了接口边界、把人工判断换成了统计判断，还是只是换了个前端。最后一种情况要老实说清楚：那是接口改良，不是架构变化。

第三层是**反方**。一份只讲「AI 会让 X 更好」的清单永远正确，因而没有信息量；本节把被过度宣传的部分单列（§5.5），并且每条都写出「它要成真需要什么前置条件」。

这三层缺失在 ADR 这个主题上尤其致命，因为 ADR 的产出物有两个特殊性质：

- **它的错误不会当场暴露**。选错一个数据库，一个月内就会报错；写错一条 Context，三年后才会有人基于错误结论做决定，而且那时写的人可能已经离职。
- **它一经接受就不可修改**。所以它比代码更需要「写之前想清楚」，而不是「先写一版再迭代」——用 AI 提高产量在这种工件上，收益与风险的方向是相反的。

分级判据用三条，且三条必须同时成立才算 L1：

- **已 GA 且有正式 release note**——不是产品页的功能列表，是版本发布说明。
- **有第三方（非厂商）公开的生产案例**——厂商自己的案例不算，它证明的是功能存在，不是功能可用。
- **接口稳定**——能被别的系统依赖；如果接口还在预览期，你的集成本身就是风险。

这里有一处例外必须先写清楚，否则本节的分级会自相矛盾：**ADR 这个语料在公开范围内没有任何第三方生产案例**（见 §5.4「未能核验」）。严格按上面三条执行，本节将没有任何方向够 L1，「唯一处在 L1 的方向」这句话也就无从写起。所以本节对 L1 采用**降级口径**，并把它限到最窄：

- **替代判据（仅在第二条判据于公开范围内不可得时启用）**：该方向**失败可回退**——最坏情况下读者能按引用退回原文核对，错误不残留；且**不引入新的决策权威**——不写状态、不写正文、不产生需要人问责的新结论。两条必须同时成立，且级别栏必须标注「降级口径」，不得与按三条判据判出的 L1 混同。
- **替代判据不适用于任何写入方向**：凡是要改 Status、改正文、新增结论的方向，即使它「失败也能撤销」，也一律按三条原判据判，判不出来就是 L2。原因是决策记录的失败与代码的失败不同——代码回滚就干净了，被引用过的错误结论不会因为回滚而消失。

由此得到三级，读者该做的事完全不同：

- **L1 生产可用**：可以排进路线图，按正常工程标准做取舍。
- **L2 可试点**：可以做 PoC，**不要做核心依赖**；PoC 的目标是拿到你自己的数据，不是验证厂商的宣称。
- **L3 观望**：只记录，**不要在架构里为它预留假设**——预留假设的成本（接口层的抽象、字段的占位）往往比将来重构还贵。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| ADR 库的只读检索问答（ADR + RAG / 向量库） | L1（降级口径） | 第一、三条判据成立：检索与长上下文组件均有正式文档与稳定接口；第二条（第三方案例）不可得，故启用替代判据——只读、不产生新的决策权威、答错可回退到读原文 | 现在就做：给 ADL 加一条「只读、必须回链到 ADR 编号」的问答入口 |
| AI 起草（AI-drafted ADR） | L2 | 生成 MADR 草稿是通用能力，但「你组织的标准模板是什么、Context 该包含什么」没有外部共识，素材也不在模型手里 | PoC：只把会议记录改写成模板骨架，Status 一律 Proposed |
| AI 评审（AI Review） | L2 | 「字段齐不齐」可判定、可进 CI；「认知偏差检测」不可判定，只能算提示 | 先进 CI 门禁，且只做可复算的规则（必填字段、选项数下限） |
| AI supersede 检测 | L2 | 语义相似检索是成熟组件，但「相似」与「取代」是两个关系，判定规则要由组织给 | 只输出建议清单，不自动改 Status |
| AI 决策助手（Decision Copilot） | L3 | 检索增强的「推荐选项」未取得第三方生产案例，价值未被独立验证 | 记录；不要接进决策流程 |
| Decision Intelligence 平台 | L3 | 以厂商路线图与分析师叙事为主；前置条件（决策后果结构化回填）通常不成立 | 记录；先把 ADR 的 Outcome 字段填上有内容的东西 |
| Agent-driven ADR（Agent 自动生成 / 更新） | L3（能力 L2、治理 L3） | 让 Agent 往仓库追加 Markdown 是 L2 能力；让它改状态是授权问题，不是技术问题 | 可以做，但把产物限定为 Status=Proposed 的草稿 |
| 联邦 ADR（跨组织共享决策库） | L3 | 无格式标准、无激励结构、无隐私边界；公开可检索的只有个人与公司博客级分享 | 记录 |
| ADR + GraphRAG / 决策图谱 | L3 | GraphRAG 是 2024 年的研究原型加开源实现；组织级 ADL 只有几百到几千节点，远小于它被验证的场景 | 记录；先把编号与 supersede 链写对，收益更大 |
| 可执行的 ADR（Decision as Code） | L3 | 成熟形态是「策略 / 约束即代码」，ADR 侧没有公认的形态与工具 | 记录 |
| 决策模拟（用 Agent 模拟决策后果） | L3 | 模型里没有你的系统状态与依赖结构，产出的是叙事而不是推演 | 记录 |

表里**唯一处在 L1 的是「ADR 库的只读检索问答」**，且它是按上面的**降级口径**判的：组件侧（向量检索、长上下文问答）都有正式文档与稳定接口，方向本身**不产生任何新的决策权威**——最坏情况是答得不好，读者退回去读原文，错误不残留。它缺的正是原判据的第二条：本节未能取得可引用的第三方案例，替代判据只补上「可回退 + 不引入新权威」，**补不上「别人已经这么做成了」**。所以这一行应当读作「可以排进路线图，但它是三条原判据里缺一条的 L1」；要把它补成完整的 L1，最省的办法是在自己的 ADL 上做一次两小时的内部验证，而不是去找别人的案例。

其余方向不够格的共性原因有两条：它们要么要动**状态字段与授权**（supersede 检测、Agent 写入），要么要动**语料之外的东西**（决策后果、系统模型）。这两类都不是「组件成不成熟」能解决的问题，等多久也不会自己变成 L1。

还有一条使用提醒：**级别不是永久标签**。它跟着 release note 走，一个方向可能因为接口冻结而从 L2 升到 L1，也可能因为维护者退出而从 L1 掉下来。合理的做法是每半年重核一次（看 release note 与第三方案例），而不是在架构文档里写死一次判断。

读这一节时，建议按三种角色各取一部分：

- **如果你要写路线图**：只看 §5.1 的级别列与 §5.7 的行动表——它们回答「现在能不能投」。
- **如果你要向评审解释为什么不做某个方向**：看 §5.2 的「由此付出的」与 §5.5——它们给出可核验的反对理由，而不是「我觉得不成熟」。
- **如果你要自己验证**：看 §5.4 的判定方法与 §5.6 的信号列——它们给出三年内可观测的证据。

### 5.2 演进方向逐条拆解（核心节）

下面 4 个方向按「**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**」6 项逐条拆解。读的时候注意两点：**机制那一项**是判断整条方向真假的锚——如果一句话说不清 AI 改变了哪个机制，这个方向大概率只是换了个前端；**代价那一项**是本节区别于趋势清单的地方——只讲收益的条目在真实的架构评审里过不了关，因为评审要回答的从来不是「有没有好处」，而是「好处值不值这些代价」。

#### 5.2.1 AI 起草与 AI 评审：降的是排版成本，不是上下文成本

- **旧做法与它的卡点**：ADR 的卡点从来不是「不会写模板」——MADR 这类模板是公开的、免费的、五分钟能背下来。团队不写 ADR，是因为写 Context 需要把散在群聊、评审会、PR 评论里三个月的约束重新收集成一段话，而这段采集没有产出物归属：写的人当下付成本，读的人是未来某个陌生人。所以卡点在**上下文的生产**，不在排版。评审的卡点同理：审查者不缺模板，缺的是「这条 Consequences 是不是真的」的判断依据。
- **AI 改变了什么机制**：它改变了文档**边际生产成本的分布**——把「从零到一份格式正确的 MADR」从小时级压到分钟级，但没有改变「上下文从哪来」。模型能补的是**推断**（「既然选了 Iceberg，大概是冲着 schema evolution 去的」），不能补的是**事实**（「当时是因为另一个方案在某版本上没有某个功能」）。
- **由此得到的**：因为模板成本降到近零，所以「每一条认真决策都留一份 ADR」第一次在成本上可行——门槛从「值不值得写」变成「值不值得开一次会」。这会把 ADR 的**覆盖密度**提上去（过去只有重大决策才有 ADR），而覆盖密度是 ADL 能被检索的前提：一个只有十篇文档的语料库，检索再准也没用。评审侧拿到的是另一层收益——字段完整性这类可判定的检查终于能自动化，「选项少于两个」这种低级问题不必再靠人提醒。
- **由此付出的**：三条代价，都落在「不可变」这条规则上。
  - **推断被写成事实**：模型生成的 Consequences 段会用确定语气写「我们接受 X 风险」，而 X 是它推断的；一旦被 Decision Owner 接受，这条推断就随着「Accepted 不可变」永久留进决策族谱，后人引用它时无从分辨。
  - **格式正确掩盖内容空洞**：评审者看到结构完整、措辞笃定的 MADR，会降低追问 Context 的次数——而 Context 恰恰是这份文档唯一不可替代的部分。
  - **数量上升稀释信噪比**：ADR 从「半年十条」变成「一周十条」后，人工通读不再可能，消费只能依赖检索，而检索质量又回到「状态字段准不准」这件事上（见 5.2.2）。

「AI 评审」这一支的边界可以靠一张表划清：**可判定的**进 CI，**不可判定的**只做提示。

| 检查项 | 是否可判定 | 该放在哪 |
| --- | :---: | --- |
| 必填字段是否齐全（状态、日期、owner、后果段） | 可判定 | CI 门禁，阻断合并 |
| 选项数是否 ≥ 2 且至少一个不是明显陪衬 | 半可判定（数量可判定，陪衬需人判） | CI 给警告 + 评审人确认 |
| 每条 Consequences 是否有对应的事实来源 | 不可判定 | 评审清单上的问题，由签字人回答 |
| 这条决策是否与已有 ADR 的假设冲突 | 可检索、需人判断 | 提示 + Decision Owner 裁定 |

- **证据与来源**：
  - 【公开】MADR 模板与 Nygard 2011 年原文均可在其公开项目页核验。
  - 【经验】AI 起草节省的是排版与骨架时间，不是撰写总时间；本节未取得可引用的第三方量化数据，故不给百分比（任何「节省 N% 撰写时间」的说法若无来源，应视为营销）。
- **成熟度**：L2。判据：生成草稿的能力已 GA，但「你组织该用哪种模板、Context 该包含什么」没有外部标准可依，且错误代价落在不可变的 Accepted 记录上——一处错误会被长期引用，不像代码那样能被下一次提交改掉。

#### 5.2.2 检索问答与 supersede 检测：使用方式从「读」变成「查」

- **旧做法与它的卡点**：ADL 的可用性随 ADR 数量**下降**。N 条 ADR 时，回答「我们为什么不用 X」需要人读 N 篇，其中大部分与问题无关；编号与目录是给「已经知道要找什么」的人用的。于是 ADL 的典型命运是被写一次、被引用零次。卡点不是没有记录，而是**检索成本随规模线性上升**。
- **AI 改变了什么机制**：把「读」的成本从 O(N) 人读降到 O(1) 检索（向量检索加长上下文）。这是**接口边界**的改变：ADR 的消费者从「人」扩展到「人 + 检索器」，载荷字段也随之改变——过去重要的是标题写得好（便于人翻目录），现在重要的是状态写得准（便于机器过滤）。
- **由此得到的**：因为检索器直接读原文而不是读摘要，所以「ADR 写得长、写得糙、中英文混杂」不再致命——长尾的、非结构化的决策记录第一次可以被用起来。而且因为输出的是问题级答案而不是文档列表，ADR 的价值从「归档」变成「可查询的组织记忆」。这是本节唯一够 L1 的原因。

```text
最小可检索字段（缺一不可）——「状态链」是检索能不能用的前提
  ---
  id: ADR-0031
  status: Accepted | Superseded by ADR-0047 | Deprecated | Proposed
  supersedes: [ADR-0007]     # 关系显式写出来，不靠相似度猜
  date: <决策日期>            # 与「最后编辑日期」不是一回事
  owner: <Decision Owner>    # 拍板的人，不是写 ADR 的人
  context: <在什么条件下这条决策的上下文会变，可为空>
  ---
  → 关系字段显式化后，supersede 检测从「判断」降级为「核对」
  → 没有状态链的 ADL，检索器答得越流畅，误导越深
```

- **由此付出的**：三条代价，且第一条是「比现状更坏」的那种。
  - **过期结论会被以更高置信度回答**：检索器不知道 ADR-0007 已被 ADR-0031 supersede（除非状态链在），它会把两篇都读进来，合成一个自洽但过时的答案。没人读的过期 ADR 是无害的，**被检索出来的过期 ADR 是误导**——因为它带着「据我们所记录」的权威语气。
  - **相似度不等于取代关系**：新 ADR 可能只是补充同一决策的另一个侧面（同族关系），也可能只是措辞相近。用相似度阈值去切，会把决策族谱切碎；而族谱一旦碎了，就再也拼不回来（因为旧 ADR 不可改）。
  - **新增成本项**：语料与索引的维护（ADR 改了要重索引，否则检索到的是旧版本）、访问控制（ADR 正文里常写着未公开的系统缺陷与供应商谈判结论，问答入口的权限必须与 ADL 一致，否则它成了绕过权限的旁路）。
- **证据与来源**：
  - 【公开】向量检索与长上下文问答均为 GA 组件，各厂商正式文档可核验。
  - 【公开】Microsoft Research 2024 年发布 GraphRAG（arXiv 预印本，可按标题检索核验），说明「把文档拆成实体关系再做全局问答」在研究上成立。
  - 【经验】本节未取得「ADR 语料问答」的第三方生产案例；该方向的 L1 判定因此按 §5.1 的降级口径给出，第二条判据由读者自行小规模验证替代。
- **成熟度**：检索问答 L1（降级口径，见 §5.1）；supersede 检测 L2（输出建议、不做状态变更）。两者的差别不在技术难度，而在**是否触碰权威**。

#### 5.2.3 决策助手与 Decision Intelligence：改变的是候选集，不是判断

- **旧做法与它的卡点**：ADR 的 Considered Options 段通常质量最差——不是写的人偷懒，而是「想不出第三个选项」是人的常态：人对自己见过的方案有强先验，对没见过的方案没有搜索路径。于是大量 ADR 的 Options 段写着「我们的方案」加一个明显更差的陪衬，决策因此**不可质疑**——没有真选项，就没有真取舍。
- **AI 改变了什么机制**：模型把「列候选」从记忆任务变成采样任务，它给出的是**训练语料里的方案分布**。这是机制上的改变：候选集的来源从「在场人的经验」变成「语料里的频次」。

候选其实有三个来源，各自的偏差方向不同，把它们混在一起谈，就会得出「AI 让候选更全」这种半对的结论：

| 候选来源 | 覆盖什么 | 系统性缺什么 |
| --- | --- | --- |
| 在场人的经验 | 与在场人做过的系统高度相关，细节可当场追问 | 没见过的方案完全缺席；受会议室里谁级别最高影响 |
| 语料频次（模型采样） | 热门方案与流行组合稳定出现 | 冷门但恰好贴合你硬约束的方案；最近半年才出现的东西 |
| 内部实践（自己系统的历史） | 与你的约束最贴合，且带真实代价数据 | 需要有人去挖；不主动挖就会被前两者挤掉 |

可行的组合是三者都取：模型扩列负责广度，人工补尾部负责偏门，内部实践负责「你的约束」这一层。

- **由此得到的**：因为人要靠回忆、模型只要采样，所以 Options 段的**广度**不再受限于会议室里坐着谁——「我们没听说过 X」第一次有了补救办法。对跨域决策尤其有用：选数据平台时顺带考虑向量库与 Agent 框架的依赖，这种横跨三个门类的候选清单，过去要靠恰好有一位跨域经验的人在场。
- **由此付出的**：分布性偏差是结构性的，调提示词修不掉。
  - **热门坍缩**：语料里高频的方案（Kafka、Postgres、Iceberg）会被稳定列出，而恰好贴合你那条硬约束（「必须在两地三中心下保持单写者」）的冷门方案不会出现。模型给的是「平均意义上的好」，不是「你的约束下的好」。
  - **陪衬被生成出来**：为凑满表格而生的、没有真实支持者的选项，在评审里被轻易否决——矩阵看起来做了比较，实际只比较了一个。
  - **候选一多矩阵就变成负担**：20 个候选 × 12 个维度的矩阵没人填，最后又回落成「选两个填完」。
  - **Decision Intelligence 还有一层额外前提**：它主张把 ADR、实验数据、业务指标融合成建议，而融合的前提是决策的**后果被结构化回填**。在 Outcome 普遍还是一次性自由文本时，这种「建议」退化成了把三份各自不可信的数据放进同一个界面。
- **证据与来源**：
  - 无独立可核验的第三方生产案例；厂商侧材料不作为技术事实（「支持决策智能」这类表述没有可证伪的判据）。
  - 【公开】Gartner 2022 年战略技术趋势清单包含 Decision Intelligence（Gartner 官网当年清单可核验）；若某份清单把它记为 2024 / 2025 年的新趋势，应以当年清单原文为准。
- **成熟度**：L3。判据：无第三方生产案例，且其前置条件（Outcome 结构化回填）在多数组织尚不成立。可单独拆出的最小用法是 L2：**只用模型扩候选，然后人工补尾部**（见 §5.7）。

#### 5.2.4 Agent 写入与决策图谱：把「人写人读」改成「机器写机器读」

- **旧做法与它的卡点**：ADR 的生命周期里有三件事靠人手动做，且都可以被忘掉：写新 ADR、把旧 ADR 标 Superseded、把失效的 Context 标出来。忘掉的后果**不可见**——没人会因为「忘了 supersede」报错，只会让后人读到过期结论。这类「缺失型」维护任务在人力预算里永远排不上：它没有截止日期，出事的时刻在三年后，而且不会指向具体某个人。
- **AI 改变了什么机制**：Agent 可以把这三件事从「需要人记得」变成「由事件触发」（PR 合并、依赖升级、云区域变更）。机制上改变的是**触发源**：从人的记忆变成系统事件。GraphRAG 补的是另一半——把引用 / supersede / 同族关系建成图后，「这条决策的前后脉络」变成一次多跳遍历，而不是一次全文搜索。
- **由此得到的**：因为触发源变成事件，所以决策记录的维护第一次可以做到与代码变更同频，supersede 这条链不容易断；因为多跳遍历能一次性回答「当时为什么不用 X、后来因为什么改成了 Y」，后人复盘一条决策的完整演变不再需要人工拼线索——这两件事合起来，把 ADL 从「静止的档案」推向「跟着系统一起变化的记录」。
- **由此付出的**：四条代价。
  - **权威稀释**：ADR 的力量来自「这是 Decision Owner 签的字」。Agent 自动追加的记录没有可问责的主体；一旦它改动了 Status，决策族谱就失去可问责性，事后无法判断「这条 Superseded 是谁批的」。
  - **不可变被破坏**：如果 Agent 能改已有 ADR 的正文，§1.1 列为第一条本质特征的「不可变（Immutable）——Accepted 后不再修改，要改就写新 ADR 去 supersede」就不再成立，决策记录退化成事件日志——记录变多了，可信度反而下降了。
  - **双源不一致**：图谱是派生物，若有人通过 API 只改图谱，Markdown 源与图谱就分叉。不一致时以谁为准必须事先写死，否则争议会出现在最不该出争议的地方（复盘时）。
  - **规模不匹配**：组织级 ADL 通常几百到几千个节点，而 GraphRAG 被公开验证的场景是从一堆文档抽实体关系做全局摘要。技术上可行，很可能不划算——把 supersede 链写对的收益更大，成本更低。

```text
Agent 写入 ADR 的权限边界（按 ADR 的不可变规则推导，不是按模型能力推导）
  允许：新建文件，Status=Proposed，署名 = agent:<id> + 触发事件
  允许：在 PR 评论里贴「可能相关 / 可能 supersede」的候选清单
  禁止：修改 Status=Accepted 的 ADR 正文
  禁止：把 Status 置为 Superseded —— 必须有人会签，否则族谱不可问责
  → 结论：能力到位不等于授权到位；这条边界是授权问题，不是模型问题
```

- **证据与来源**：
  - 【公开】Microsoft Research GraphRAG（2024，arXiv 预印本，可按标题核验）。
  - 【公开】MADR 等模板本身不含强制的 supersede 关系字段（模板可在线核验），所以自动 supersede 缺的不是模型能力，而是关系数据。
  - 【经验】Agent 写 Markdown 是成熟能力；Agent 获得「改已接受决策」的授权，在任何组织都需要新的治理规则——这类规则通常诞生于一次事故之后，而不是提前写出来。
- **成熟度**：Agent 追加草稿 L2；Agent 改状态、决策图谱、联邦 ADR 均 L3。

把 4 个方向压成一张速查表，差别一眼可见：

| 方向 | AI 改变的机制 | 主要代价 | 级别 |
| --- | --- | --- | --- |
| 起草与评审 | 把「从零到一份合规 MADR」的边际成本压到分钟级 | 推断被写成事实，且不可变规则让它长期留存 | L2 |
| 检索问答与 supersede 检测 | 把「读」从 O(N) 人读降到 O(1) 检索 | 过期结论被以更高置信度回答；访问控制旁路 | L1（降级口径；检测 L2） |
| 决策助手与 Decision Intelligence | 候选集来源从人的经验变成语料频次 | 热门坍缩、陪衬选项；需 Outcome 结构化回填 | L3 |
| Agent 写入与决策图谱 | 维护触发源从人的记忆变成系统事件 | 权威稀释、不可变被破坏、双源不一致 | L2（草稿）/ L3 |

这张表也是本节的一条判别捷径：**凡是「改变的机制」一栏写不出成本函数或接口边界、只能写成「更智能」的方向，级别都在 L3**——因为无法描述机制，就无法判断它什么时候会成熟。

### 5.3 与本主题既有栈的接口在哪

「ADR + AI」的落地差别不在模型选型，而在**接口切在哪**。三个必答问题：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 检索问答（ADR + RAG） | 只读：读 `docs/adr/*.md`（git 为唯一真源），输出「答案 + 引用的 ADR 编号」 | 答错由提问者按引用回退到原文核对；索引过期由平台侧负责 | L1（降级口径，见 §5.1） |
| AI 起草 | 写 PR：产出 Status=Proposed 的 MADR 草稿文件 | Context 段的事实错误由签字的 Decision Owner 负责 | L2 |
| AI 评审 | CI job：对 PR 中新增 / 修改的 ADR 跑规则（必填字段、选项数下限、必须含后果段） | 误报由 ADR 作者走豁免流程 | L2 |
| supersede 建议 | PR 评论 / Lint 报告：列出「可能相关」的旧 ADR，不改任何字段 | 漏报与误报都由 Decision Owner 在评审时判断 | L2 |
| Agent 自动追加 | 事件触发写新文件（Proposed）；不得改 Accepted | 冲突由 git 历史与 CODEOWNERS 兜底 | L3 |
| 决策图谱 | 派生物：从 ADR 抽三元组（引用 / supersede / 同族），与 Markdown 单向同步 | 不一致时以 Markdown 为准，图谱仅用于导航 | L3 |

上表可以收成一条硬规则：**权威必须留在 Markdown 加 git**，AI 的产物只能出现在 Proposed 侧或只读侧。理由是 ADR 的四条性质（不可变、可追溯、可讨论、可被未来质疑）中有三条建立在 git 的历史与署名上——谁在什么时候把状态改成了什么，是有据可查的。凡是让 AI 写 Accepted 记录、或直接改状态字段的设计，都是拿便利换掉了 ADR 唯一的资产：可问责。

失败责任也必须沿这条线切：

- **检索错了**（答非所问、引用了过期 ADR）是**平台侧**的问题——语料新鲜度与状态过滤是它的职责。
- **草稿里的事实错了**是**签字人**的问题——他签字，就为 Context 段的每一句负责，「是模型写的」不构成免责。
- **状态错了**说明**授权链设计错了**——因为按上表，没有任何自动化环节被允许改状态。

最后一点关于数据形态：穿过边界的应当是**文本 + 显式关系字段**，而不是「一个向量库副本」。向量库可以有，但它是可重建的派生物；一旦它成了唯一真源，撤回一条错误结论就得靠删向量，而删错一个向量比改一个 Markdown 文件难发现得多。

三种最常见的接口误配，都是把便利放在了权威之上：

- **把索引副本当成真源**——写入只发生在向量库里，Markdown 落后；等到要审计「这条结论是哪来的」时，源已经不可信。
- **让答案没有引用**——回答流畅但指不回 ADR 编号，读者无法核实，错误也就无法追溯（这正是检索问答必须「回链」的原因）。
- **让 AI 直接改 Status**——省掉一次会签，代价是族谱里出现无人负责的状态变更，而这类变更正是复盘时最需要解释清楚的。

- **每个数字必须能指回来源与年份**；指不回去的，要么删掉，要么降级为【经验】区间，并说明这是经验值。

### 5.5 被过度宣传的部分

**说法：「AI 自动维护 ADR —— Agent 监测决策后果，发现过时自动提议 supersede」**

- **实际能做的**：提示语义相关的旧 ADR，列出「可能相关」的清单。
- **做不到的**：判定取代。原因是三点：supersede 是**授权行为**，效力来自某个 Decision Owner 的签字，而模型输出没有可问责的主体；**相似不等于取代**——同一主题下的两份 ADR 常是同族补充关系，用相似度阈值切会把族谱切碎；「监测决策后果」要求 Outcome 字段有可观测的回填，这件事多数组织没做。
- **什么时候才会成真**：当决策后果被结构化成字段（指标、实验结论、复盘结论）回填到 ADR，并且组织把「谁能改 Status」写成可执行的授权规则时。那时它做的是**核对**，不是判断——这才是这件事真实的样子。
- **怎么核验**：拿任何一个号称能自动 supersede 的工具，问一句「把 Status 改成 Superseded 的那次提交是谁署名的」。答不上来、或答「工具自己」，这条就还没成真。

**说法：「Decision Intelligence 平台把 ADR、实验数据、业务指标融合，给出决策建议」**

- **实际是什么**：一个 BI / 实验平台加一个自然语言前端。
- **为什么会这样**：融合三种数据**不产生新信息**，只产生一个新界面。建议需要的是因果估计（「这个动作会带来什么后果」），而 ADR 是事后记录、实验只覆盖被实验过的动作、业务指标里没有反事实。三者拼起来，缺的恰好是决策最需要的那一块。
- **什么时候才会成真**：当组织能系统性回填「被否决的方案后来发生了什么」——例如对小流量保留影子运行、对关键决策记录几个可观测代理指标。这目前只在少数有平台能力的组织里零星存在，而且它是组织能力问题，买不来。
- **怎么核验**：拿你自己的一条真实决策去测——看它能不能说出「当年被否决的那个选项，后来在别处发生了什么」。说不出，就说明它融合的只是三份结果数据，不是决策依据。

**说法：「用 Agent 模拟决策后果（决策模拟）」**

- **实际是什么**：模型生成一段「这类决策通常的后果」的叙事。
- **为什么会这样**：模型里没有你的系统状态与依赖结构，它采样的是训练分布中「相似决策的常见结局」——也就是**别人是怎么做的**，而不是**你这么做会怎样**。把它当模拟器用，得到的是措辞专业的解释，却会被读成事前预测。
- **什么时候才会成真**：当模型调用的不是自己的先验，而是真实的系统模型（容量模型、成本模型、依赖图、影子流量）时。那时它做的是「把仿真结果讲成人话」——这是这一支里唯一有实际机制增益的位置，也是唯一值得现在投入的形态。
- **怎么核验**：问它模拟用的系统状态从哪来。如果答案里没有你自己系统的模型、参数与观测数据，它给的就是叙事——无论措辞多像一份评估报告。

### 5.6 未来 3–5 年：可证伪的预测

写不出证伪信号的预测不要写。下表每条都给出两侧信号。

这四条的共同特点是**都能在三年内被观测**：前两条看模板与日志，后两条看「有没有出现反例」。写给架构师的判断标准很简单——如果一个说法三年后既不会因为某件事被确认，也不会因为某件事被推翻，那它就不是判断，只是一句场面话。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| ADR 会被拆成两份工件：给机器读的关系字段（编号 / 状态 / supersede / owner）与给人读的叙事正文 | 公开的 ADR 模板项目在文档里给出推荐的关系字段 schema，或被广泛采用的 ADL 普遍带 lint 规则检查这些字段 | 三年后主流模板仍只有标题加状态，「关系靠正文里的自然语言描述」 |
| 「查 ADR」会成为 ADL 的主要消费方式，超过人逐篇翻目录 | ADL 的访问日志里检索入口（MCP / API）的调用量超过页面浏览，且 ADR 的平均被引次数上升 | ADL 总访问量仍很低且集中在少数几篇——说明它依然是「写一次没人读」 |
| 自动 supersede 会长期停在「建议」层，拿不到自动改状态的权限 | 主流 ADR 工具与模板的**默认配置**里没有任何自动状态变更；每次状态变化都留下人的签字 | 出现被多组织采用、**默认开启**自动标记 Superseded 的工具，且有第三方生产案例 |
| 「联邦 ADR / 跨组织决策库」不会以共享库的形态出现，而会以厂商参考架构与公开复盘文章的形态存在 | 出现跨公司、有规模、可检索、可持续更新的公开 ADR 语料（非个人仓库），并被引用 | 三年后公开可检索的 ADR 仍主要来自个人与公司博客，没有共享语料层 |

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 已有 50 条以上 ADR | 给每条补状态链与 owner 字段并跑一次 lint；加一个只读问答入口，答案必须回链到 ADR 编号 | 问答命中率与误答类型；ADR 的被引次数是否上升 | 不要自动改 Status；不要用相似度自动生成 supersede 关系 |
| ADL 刚起步（不到 50 条） | 先解决「写不写」：用 AI 起草骨架，Context 段由 Decision Owner 逐句核对后签字 | 覆盖密度（每月新增有效 ADR）与空洞率 | 不要在语料还不成型时上决策图谱——图里没有东西可遍历 |
| 想用模型补 Options 段 | 让模型扩候选，然后**人工补尾部**：去问两个利益不同的团队「你们会怎么选」 | 候选是否真的变多；是否出现明显的凑数选项 | 不要把生成的选项直接当成矩阵的分母 |
| 只有一个人在维护 ADR | 把 supersede 与 Context 失效变成事件触发的提醒（PR 合并、依赖升级、云区域变更） | 是否有第二个人在处理 ADR 的 PR | 不要建 Decision Intelligence 平台；先让 Outcome 字段有内容 |
| 在评估「AI 决策助手」类产品 | 要它讲清四件事：读什么语料、状态链怎么过滤、答错时引用能否回链、谁对答案负责 | 产品是否开始公开检索与过滤机制（而不是只放演示） | 四项拿不到时不要把它接进决策流程 |
| 决策记录被纳入合规 / 审计要求 | 把「谁在何时把状态改成了什么」做成可导出的记录（git 历史本身就是） | 审计是否会问「这条结论当时的依据是什么」——答不上来就说明 Context 段太空 | 不要为此新建一套「合规 ADR 库」：两套记录必然分叉，且分叉点永远在最不该出错的地方 |
| 决策反复被跨团队重提 | 在 ADL 上开一个只读问答入口，让提问的人先看到历史结论 | 重提次数是否下降；重提时是否有人引用 ADR 编号 | 不要用 AI 生成一份「决策摘要」代替原文档——摘要是派生物，它丢掉的恰好是判断依据 |

这张表的「明确不要做」一列不是保守，而是**机会成本**：这些动作都要占用平台侧的人力，而它们换来的东西在当下都能用更便宜的方式拿到。等 §5.6 的信号出现再投入，比现在投入更划算——尤其当你的 ADL 还没到五十条时。

### 5.8 小结

> 本节小结：ADR 这个主题下，AI 真正改变的**唯一一条机制**是「读」的成本——它把 ADL 从需要人来翻的档案，变成可以按问题去查的语料，这也是本节唯一处在 L1 的方向（只读检索问答，按 §5.1 的降级口径判定）。它**没有**改变的是「上下文从哪来」与「谁有权改状态」：前者是人的事实，后者是组织的授权，两者都不是模型能力问题。所以 AI 时代的 ADR 工程，重点不在让模型把 ADR 写得更漂亮，而在把状态链、owner、supersede 关系这些**机器能过滤、人能问责**的字段补全——没有这些字段，检索器答得越流畅，过期结论误导得越深。
>
> 💡 **思考锚点**：数一下你 ADL 里有多少条 ADR，其中多少条写了 owner 与 supersede 关系字段——§5.7 说 50 条以上才值得先补字段再上检索，你现在在哪一侧？再拿一条真实决策去测你手上的问答工具：它答错了，你能顺着答案回链到 ADR 编号、并找到那次把 Status 改成 Superseded 的署名人吗？
