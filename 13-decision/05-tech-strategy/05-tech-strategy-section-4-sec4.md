## 4. 工程实现

[§ 3](05-tech-strategy-section-3-sec3.md) 已经把十二个战略工具各自「被什么约束逼出来、为什么有效、代价与失效点」讲完，本节不复述模式本身，只讲装进组织时多出来的那部分：**谁在什么时点交什么、怎么判对错、旧资产怎么办**。组织方式是按落地的九步顺序（4.1）、八条关键技术点及各自的失效条件（4.2）、工具选型判据（4.3）、存量技术栈的迁移（4.4）、可直接套用的模板（4.5）、自检清单（4.6）与小结（4.7）。

**本文件面向两种读者，分节给不同的人**：从零搭战略的人先看 4.1 的 Step 1–3 与 4.5 的模板；在存量上改造的人（已有在跑的技术栈、已有一批说不清为什么被选中的组件）先看 4.4，再回头补 4.1 的 Step 2 与 Step 8——前者是全流程最常被跳过的一步（原因见 4.1 末段）。文中工期一律给区间并标【经验】，它随组织人数、是否有独立技术预算、是否需要跨 BU 对齐三件事变化；方法类事实标【公开】并给出可自行检索核验的关键词。

### 4.1 落地步骤

**Step 1：业务对齐（1–3 周【经验】，跨 BU 越多越长）**

- 取业务 3–5 年规划的**原文档**（不是转述稿），标出其中与数据、实时、算法相关的三到五条承诺。
- 每条承诺翻成一句「技术要具备什么能力，这条承诺才成立」，写进 Alignment Matrix 的中间列。
- **产物**：技术战略 Alignment Matrix（业务承诺 × 所需技术能力 × 现有能力差距，一页）。
- **判据**：拿矩阵逐条问业务负责人「这几条里哪一条我理解错了」。能改掉至少一条，说明你取的是原文；一条都改不动，多半抄的是自己的旧认知。
- **为什么必须这一步 / 为什么在这个位置**：它是后面全部取舍的锚点。省掉它，Step 6 分资源时没有可比口径，只能按「哪个团队声音大」分；换序（先盘点再对齐）会让盘点退化成漫无目的的技术清点。

**Step 2：技术现状盘点（2–6 周【经验】，随组件数与是否有实时资产台账变）**

- 盘现有系统与能力（组件、版本、Owner）、技术债与风险、优势与劣势（SWOT）。
- 每条技术债额外写一句「不还它，明年会以什么形式变贵」（返工、故障、招人溢价）——这句话决定它在 Step 6 占多少预算。
- **产物**：技术现状报告 + 一张「组件 × 是否有 Owner × 最后复核时点」清单。
- **判据**：抽三个关键组件，能否说出它的 Owner、它当初为什么被选、上次复核在什么时候。答不出的组件就是「无人负责的存量」，直接进 4.4 的挂账清单。
- **为什么必须这一步 / 为什么在这个位置**：它是全流程最常被跳过的一步（见本节末段）。没有它，Step 4 无法区分「要新建的能力」与「已有但无人维护的能力」，路线图会退化成一串新建项目。

**Step 3：技术愿景（1–2 周【经验】）**

- 写 3–5 年后技术要长成什么样，1–2 页；配一张可视化（Wardley Map 适合这里，它自带演化轴，模板见 4.5）。
- 愿景里每句话都要能落到一个可判定的状态（「同一口径只有一份定义」而不是「数据驱动」）。
- **产物**：技术愿景文档 1–2 页 + 一张价值链图。
- **判据**：把愿景给一位没参与讨论的工程师看，他能否说出「三年后我们要停掉现在哪个做法」。说不出，说明写的是形容词。
- **为什么必须这一步 / 为什么在这个位置**：愿景是 Step 5 排环位的依据来源之一。没有它，雷达只能按外部热度排——那正是 § 3.1 的第二条约束（判断依据来自外部信号）。

**Step 4：技术路线图（2–4 周【经验】）**

- 分 H1（0–12 月）/ H2（12–36 月）/ H3（36–60 月），每阶段给关键能力 + 关键项目 + 关键资源。
- 每个项目带**复核时点**与**退出条件**（§ 3.2.11 的转向判定卡结构），否则三年不变的规划会变成承诺。
- **产物**：技术路线图（季度视图与年度视图两张粒度）。
- **判据**：随机抽三个项目，问「它在哪一层的钱里、验收口径是什么」。三个都答得出，才不是愿望清单。
- **为什么必须这一步 / 为什么在这个位置**：路线图是把 Step 3 的愿景与 Step 6 的预算接起来的唯一一层。省掉它，预算无从按层归属，H3 类投入会被季度预算吃掉（§ 3.1 的第一条约束）。

**Step 5：技术雷达（每期 2–4 周【经验】，随条目数变）**

- 对每条相关技术给环位（Adopt / Trial / Assess / Hold）与期号，移动环位时在同一行写下理由与决定人。
- 环位语义事先公布：Hold = 不推荐新项目采用，**不是禁令**。
- **产物**：技术雷达（象限 + 环位 + 期号 + 移动理由）。
- **判据**：让一位新人不问你、只查雷达，能否说出「某技术能不能上生产、它什么时候被移过环位」。查得到，才算判断依据被沉淀。
- **为什么必须这一步 / 为什么在这个位置**：雷达要排在路线图之后，因为环位高低需与路线图的能力需求对齐；若先雷达后路线图，路线图会被雷达上最热的技术牵着走。

**Step 6：技术投资组合（1–2 周【经验】）**

- 按 H1 / H2 / H3 分配人与钱。70/20/10 是该框架最常被引述的配比，实际取值随行业与业务成熟度差异很大【经验】。
- 写清每一层预算的**归属人**与**不可挪用条款**——这是这一步唯一真正产生效果的动作。
- **产物**：投资组合表（层 × 预算 × 项目 × 验收口径 × 归属人）。
- **判据**：调上两个季度的实际支出，看 H3 那一栏是否真的没被挪走。账上写着「不可挪用」而实际被挪过，说明条款没落地。
- **为什么必须这一步 / 为什么在这个位置**：§ 3.2.3 已说明三层模型有效的原因是「把 H3 移出当期比较范围」，而这个效果只能由预算归属实现，画布本身做不到。

**Step 7：战略沟通（1–2 周【经验】）**

- 对三类听众各出一版：老板要成本 / 收入 / 风险口径，业务方要业务影响，团队要愿景 + OKR。
- 每版都给**取舍理由**而非只给结论（§ 3.2.12），否则公开的部分会被读成确定承诺。
- **产物**：三版沟通材料 + 会议纪要（含当场答不上来的问题清单）。
- **判据**：汇报后回收的问题里，有没有出现「这跟我们的约束有什么关系」。没有，多半只讲了行业趋势没讲自身约束。
- **为什么必须这一步 / 为什么在这个位置**：沟通是把战略换成资源与执行的动作，不是收尾动作；它排在投资组合之后，因为老板真正追问的是钱怎么分。

**Step 8：执行跟踪（按季度常态运转）**

- OKR 跟踪（季度）、路线图评审（季度 / 半年）、战略调整（年度），三种节奏分开。
- 跟踪同时看结果指标与**投入指标**：H3 是否还在、技术债偿还项是否被新功能挤走。
- **产物**：跟踪报告（含口径变更记录——季度中途改过口径的 KR 必须留痕）。
- **判据**：季度末只回答两件事——达成与否、口径有没有被改过（§ 3.2.9 的复盘规则）。多答即说明跟踪变成了汇报。
- **为什么必须这一步 / 为什么在这个位置**：没有跟踪，战略的失败信号只能等到年度复盘；而那时 H3 已被挪走两个季度，损失不可逆。

**Step 9：复盘（半年 / 年度）**

- 识别战略失误并修正；先区分「执行不力」与「前提被证伪」，两者对应完全不同的动作。
- 更新技术战略文档，并把本次复盘的判断依据留档（当时已知什么、不知道什么）。
- **产物**：复盘纪要 + 更新后的技术战略 + 一份「改了什么、为什么改」的变更记录。
- **判据**：纪要里有没有至少一条「我们当时假设 X，X 被证伪了」。全是执行层面的复盘，说明战略本身从未被检验。
- **为什么必须这一步 / 为什么在这个位置**：复盘排在最后，但结论必须回灌到 Step 1；否则下一轮对齐用的仍是旧假设。
最常被跳过的是 **Step 2（技术现状盘点）**，因为它不产出可汇报的东西。跳过后第一个出问题的时点是 Step 6：分预算时无法区分「新建能力」与「已有但无人维护的能力」，同一笔钱被两个项目各要一遍。第二个时点是第一次关键人离职——没有「Owner × 复核时点」清单，那些大家都以为有人在管的组件会在这位关键人走后的 3–6 个月内相继暴露为无人维护状态【经验：随组件间耦合度与运维自动化覆盖程度变，耦合越紧、自动化越少则暴露越早】。

### 4.2 关键技术点

**1. 战略雷达的可追溯性（Tech Radar 工具：ThoughtWorks 开源雷达生成器、自建）**

- **做法**：每条条目带象限 + 环位 + 期号，环位移动时当场写下移动理由与决定人。
- **机制**：落地时真正起作用的是三处留痕——条目的期号、环位移动时必填的理由字段、以及决定人署名。三者齐全，一次选型争议的解决动作从「重开评审会」变成「打开那条记录的变更历史」，判断依据不再需要当事人到场。
- **失效条件**：**当维护节奏掉到一年一期以下时，这条会退化成过期归档**——环位停留在上一轮判断，期中出现的技术没有期号可查；症状是季度评审上被问到某技术的环位，答复是「我去问当时评估的人」，而那个人的记忆正是这套记录要替代的东西。
- **档位**：【经验】

**2. 成熟度定位与时间表的分离（Hype Cycle 工具：Gartner 订阅、公开报告）**

- **做法**：用曲线定位技术所处阶段，把「什么时候投产」交给内部证据（试点数据、依赖可得性），不写「低谷之后两年就该上」。
- **机制**：落地时起作用的是这条判据的存放位置——「什么时候投产」被做成立项表单的必填栏，只能填自家试点数据、依赖可得性这类内部证据；热度再高也填不进这一栏，判断于是发生在预算被占之前，而不是发生在曲线的读法争论里（模式层理由见 §3.2.1）。
- **失效条件**：**当规划文档出现「预计 20XX 年进入生产成熟期」这类时间断言时，这条退化成时间表**；症状是同一份材料既引用曲线、又给不出自家试点数据。
- **档位**：【公开：Gartner Hype Cycle 方法页当前版本，可按「Gartner Hype Cycle methodology」检索核验】

**3. 演化阶段决定自研采购边界（Wardley Maps：OnlineMapping.io、Miro）**

- **做法**：对少数关键组件画「价值链位置 × 演化阶段（Genesis → Custom → Product → Commodity）」，按位置定策略，并写下下次重画时间。
- **机制**：落地时起作用的是「下次重画时间」被写进图本身并与复核日程绑定——阶段判定一旦过期，会在评审日程上暴露，而不是等到某次选型争论里才暴露（模式层理由见 §3.2.4）。
- **失效条件**：**当组件数量与参与团队数超出维护能力时（平台型团队同时推进十几个组件是典型值【经验】），这条退化成墙上的过时归档**；症状是同一个组件在两个团队的图上处于不同阶段，且没人说得清哪个是当下判断。
- **档位**：【经验】

**4. 战略画布的门槛项与权重（AI 战略画布：自建 / 模板）**

- **做法**：按数据 / 算法 / 算力 / 治理 / 人才五维评估（示意权重 0.30 / 0.25 / 0.20 / 0.15 / 0.10），但**先判门槛**：数据可获得性与合规可用性不达标时，其余维度得分不计。
- **机制**：落地时起作用的是门槛判定的执行位置与签字人——门槛项写进立项表单、由数据 Owner 与合规两个角色分别签字，而不是留在评估会的讨论里。放在表单里，一次「数据不可用」会在预算被占之前发生；放在讨论里，它只是会上的一个意见。
- **失效条件**：**当门槛判定由吃这份数据的团队自评、且没有第二方签字时，这条反转成走过场**——自评者倾向于把「再谈谈就能拿到」算作可获得；症状是立项材料里门槛项全部勾选达标，而项目进入实施后的第一个季度仍在等数据授权。
- **档位**：【经验】（五维权重是示意赋值，不是实证结论）

**5. 决策记录作为资产（决策智能平台 DI，详见 [§ 01 ADR](../01-adr/01-adr.md)）**

- **做法**：一次决策一条记录：决策问题 → 当时可选方案 → 采用依据 → 谁在何时决定 → 执行 → 结果 → 复盘标注，并记下「当时不知道什么」。
- **机制**：落地层的机制是留痕的位置与时点——记录与代码评审同一入口提交，复盘时按决策日期检索而不是按人名翻邮件；其中「当时不知道什么」一栏必须在决策当天填写，补填时人已经知道结果，那一栏就写不出来了。
- **失效条件**：**当记录被允许事后补填、或与变更审批绑成同一张表单时，这条反转成走过场**——填的人已知结果，会把依据顺手写成结果的前因；症状是抽三份记录，「当时可选方案」一栏都只剩一个选项。
- **档位**：【经验】

**6. KR 的口径冻结（OKR 工具：Workboard、Asana、Lattice、飞书 OKR）**

- **做法**：KR 只写可度量的结果、不写动作；口径在周期开始前冻结并版本化，中途修改必须留痕。
- **机制**：落地层的机制是冻结动作本身——口径定义单独成文并带版本号，周期开始那一刻打上 tag，中途修改要留下改前改后与批准人。有了这条时间戳，「这个 KR 为什么没达成」才有可对照的基准，而不是各人凭印象回忆。
- **失效条件**：**当口径定义的维护权落在被考核团队手上、且修改不需要第二方批准时，这条反转成月末对表**——数字没动，测法动了；症状是定义文档没有版本号，或有版本号却在季度中途被改过而无人说得清是谁批的。
- **档位**：【公开：OKR 方法源自 Intel 实践并由 John Doerr《Measure What Matters》(2018) 系统介绍】

**7. 战略 Dashboard 的指标回流（Grafana、Tableau）**

- **做法**：把路线图项目与已上线的技术指标绑在一起看，而不只看业务结果指标；投入项（H3 项目数、技术债偿还额）与结果项同屏。
- **机制**：因为投入项与结果项同屏，季度评审不需要靠人回忆「我们今年投了什么」，H3 被挤占会在图上直接可见。
- **失效条件**：**当 Dashboard 只有结果指标、或指标口径由被考核方自行定义时，这条反转成「数据支持结论」**；症状是所有看板都在变好，而技术债与 H3 却在同期被砍。
- **档位**：【经验】

**8. 沟通材料的对象分化（PowerPoint / Keynote、Notion）**

- **做法**：同一份战略出三版口径（老板：成本 / 收入 / 风险；业务方：业务影响；团队：愿景 + OKR），并保留被否方案的取舍理由。
- **机制**：因为技术语言被换成各听众的决策语言，战略在资源竞争时才不会被优先砍掉——砍掉它的理由通常不是「不对」，而是「听不懂」。
- **失效条件**：**当三版材料的结论互不一致（向老板承诺的时间点比向团队承诺的早）时，这条反转成「多头承诺」**；症状是团队按自己那版的节奏走，管理层按另一版验收。
- **档位**：【经验】

### 4.3 工具链与平台

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| 成熟度参考 | Gartner Hype Cycle for Emerging Technologies（订阅）、公开报告 | 需要外部行业坐标时用；但要接受横轴无刻度、只能作定位不能作时间表 | 没有外部输入时，战略只能由内部既有认知推导，容易漏掉整类技术 |
| 组织级雷达 | ThoughtWorks Tech Radar（开源）、Zalando Tech Radar、Spotify Tech Radar、开源雷达生成器、自建 | 需要「结论带期号、可追溯、能公开」时用公开雷达；内网合规不允许公开时自建同一套环位语义 | 只靠会议纪要沉淀选型结论，新人无法查到某技术当初为何被搁置 |
| 战略画布 / 共创 | Miro、FigJam、Mural、Whiteboard 类工具 | 需要多人同时改一张图、且要留版本时用；一两人的战略规划用文档即可 | 共创环节缺失，战略在评审会上第一次露面，落地时被按最低合规标准执行 |
| 价值链图 | OnlineMapping.io、Miro | 需要按演化阶段判自研 / 采购边界时用；只做一次沟通则用通用画布 | 用「重不重要」代替「在哪个演化阶段」，把商品化组件当差异化自研 |
| 战略文档承载 | Notion、Confluence | 需要「结论 + 理由 + 复核时点」长期可检索时用；一页纸愿景用文档即可 | 决策记录散落在汇报 PPT 里，复盘时找不到当时的取舍理由 |
| OKR / Balanced Scorecard | Workboard、Lattice、Asana、飞书 OKR、钉钉 OKR、Perdoo、Gtmhub | 只要季度抓手时用 OKR 平台；要让慢收益项（技术债、架构健康）沿因果链落位时，先在候选工具里确认它能不能把一条指标挂到某个视角（如「内部流程」）下的因果链上——挂不上的，这一步另配一张表，工具照旧用 | 换一套系统不解决口径可中途修改的问题，只增加迁移成本 |
| 战略度量 | OKR 平台内置 Dashboard、Grafana + 自建指标、Tableau、Power BI | 需要投入项与结果项同屏时自建；只做汇报级展示用现成 BI | 只看结果指标，H3 与技术债被挤占在图上不可见 |
| AI 战略与风险 | AI Strategy Canvas（自建 / 模板）、NIST AI RMF | 有持续 AI 投入且有合规要求时，用 RMF 一类框架承载风险口径；只做方向规划用自建画布 | 风险口径缺失，AI 投入在第一轮合规审查时被迫重来 |
| AI 治理合规 | Vanta、Drata、OneTrust | 需要「流程持续运行」的证明（记录、责任人、复评周期）时上工具；否则先建流程 | 合规举证靠人工整理，审计期成本高且口径不一致 |
| 战略汇报 | PowerPoint、Keynote、Pitch.com | 面向董事会 / 老板用传统演示工具（可离线、可留档）；讲故事型汇报用 Pitch 一类 | 用文档代替汇报，老板拿不到他要的成本与风险口径 |
| AI 辅助战略草稿 | 通用大模型厂商的企业版助手（Anthropic、OpenAI、Google 均有企业版产品形态，功能与配额以各家官方文档当前版本为准） | 只用于生成**草稿与反例**，不用于定稿；有数据出域限制时选可私有部署的方案 | 把模型输出直接当战略，等于把「判断依据」外包给一个不含你自身约束的来源 |
**这一类里最容易被误选的是「成熟度参考」与「组织级雷达」的互换使用**：用 Hype Cycle 决定投不投，用 Tech Radar 判断技术成不成熟（§ 3.3 已指出这是最常被误选的一对）。典型后果不在选型环节显形，而在第一次立项评审和第一次季度预算盘点时才显形：立项材料里「投产时点」填的是曲线上的阶段名，「自家试点数据」一栏空着；到季度评审，这个项目以「业界已经成熟」为由申请追加预算，答辩现场拿不出一条内部数据反驳它。反向误选——把自家雷达的环位当成成熟度结论——更隐蔽：一个尚未被评估的技术因「我们还在 Assess」被静默推迟，推迟记录里没有签字人，也就不会有人在下次评审时把它翻出来。表格里刻意保留各家公开雷达与商业闭源参考两类，是因为它们回答的是不同问题：一个回答「我们这个组织采不采」，一个回答「业界此刻怎么定位」。

### 4.4 存量迁移

**① 先做哪一件：只加一份台账，不动任何流程（1–2 周【经验】）**

不要从「重新制定战略」开始，那会让所有已有投入瞬间变成待审对象。第一步只做一件事：把**已经在生产上的技术**列成一张台账，三列——组件、Owner（具体到人）、下次复核时点。这一步可随时回退（台账不进任何审批流），却立刻产生两个效果：谁在负责变得可见；复核时点一列会暴露出大量空白，为 ② 的分类提供依据。

**② 历史资产怎么分类：分档处理，不做全量返工**

| 存量类型 | 判断依据（怎么识别） | 处理方式 | 不处理的后果 |
| --- | --- | --- | --- |
| 关键且在维护 | 有 Owner、有活跃变更、下游依赖多 | 补决策记录（为什么选它、退出成本、规模拐点）与复核时点 | 下次争议时无法为它辩护，容易被「业界都在换」带走 |
| 在用但无人负责 | 台账里 Owner 或复核时点为空 | **打标挂账**：标为「存量挂账」，列入季度观察，不要求立即补文档 | 组件在关键人离职后同时进入无人维护状态 |
| 已评估未采用 | 曾在选型会上讨论过但没有结论 | 把结论与理由回写到雷达（哪怕结论是 Assess） | 同一技术被不同团队重复评估，结论互相矛盾 |
| 已下线 / 僵尸资产 | 无上游也无下游、长期无访问 | 由血缘式依赖分析识别后进入下线流程，不在本战略范围内 | 占用预算与注意力，且让台账失去可信度 |

**不做「全部返工」的理由是成本结构**：给每一条存量补完整决策记录的成本与新建一条记录相同，而存量数量通常是新建数量的数十倍【经验】。可行的做法是只对「关键且在维护」这一档强制补记录，其余各档打标挂账——挂账本身是合法的终态，它把「不知道」变成「已知的不知道」，这已经足以避免关键人离职时的集体失守。

**③ 双轨怎么维持、维持多久**

新项目从迁移开始就按新流程走：立项时给环位、结项前写决策记录、上线时登记复核时点。存量按季度分批补，每批只补「关键且在维护」那一档。双轨期通常维持 **2–4 个季度**【经验】，它随存量组件数与是否跨 BU 变化；跨 BU 组织因为要各 BU 认领，周期更长。

双轨期必须显式定义两条线的**接口**：新流程产生的结论（环位、决策记录）对存量组件同样有约束力，但存量组件不因「没走新流程」而被阻塞发布。若没有这条规则，双轨会退化成「新项目被卡、老项目照旧」，团队会主动把工作往老流程里塞。

**④ 什么信号说明可以退出双轨**

三个可检查的信号同时成立才退出：新立项项目 100% 在立项时带环位；关键组件（台账里「关键且在维护」那一档）的 Owner 与复核时点覆盖率连续两个季度为 100%，即该档里查不到一条 Owner 为空、或复核时点已过期而未补的项（这一覆盖率要求随存量组件数与可投入人力变，组件多时先只把这一档收紧到 100%、其余档按季度收敛【经验】）；**抽查通过**——随机点三名新人，让他们只查公开材料回答「某技术能不能用、为什么」，三人全对。第三个信号最关键：它直接检验「判断依据是否已从人脑迁到文档」，而这正是整套机制存在的理由。任一信号未达标就延长双轨，不要用「制度已发布」代替它。

### 4.5 模板 / 示例

**模板 1：Hype Cycle × Tech Radar 整合表**

| 技术 | 阶段 | 雷达分类 | 战略建议 |
| --- | --- | --- | --- |
| LLM | Slope of Enlightenment | Trial | 试用 + 评估 |
| Agent 框架 | Trough of Disillusionment | Trial | 试点项目 |
| RAG | Plateau of Productivity | Adopt | 大规模采纳 |
| Vector DB | Plateau of Productivity | Adopt | 大规模采纳 |
| Knowledge Graph | Slope of Enlightenment | Trial | 关键项目 |
| Quantum Computing | Innovation Trigger | Assess | 长期关注 |

**怎么用**：填「战略建议」一列时，必须写出内部依据（试点结果、依赖可得性），而不是把阶段名翻译成动作。「阶段」一列的取值随官方当年发布版本变化，请以官方当前版本为准；「雷达分类」用你自家雷达的期号口径。

**模板 2：Three Horizons 投资组合**

| Horizon | 占比 | 项目 |
| --- | --- | --- |
| H1（核心业务） | 70%【经验】 | 数据湖稳定性 + 实时数仓 + 数据治理 |
| H2（新兴业务） | 20%【经验】 | RAG + Agent 平台 + 多模型路由 |
| H3（未来业务） | 10%【经验】 | AGI 储备 + 量子计算关注 + 边缘 AI |

**怎么用**：占比是引述值不是目标值，按自身业务成熟度重定；真正必须填的是表格之外的两列——**预算归属人**与**毕业条件**（H2 进 H1 的条件）。

**模板 3：Wardley Map（智能体平台价值链）**

```text
        高价值 / 高可见性
            │
        LLM 编排（自研 - Custom）
            │
        Agent 框架（自研 - Custom）
            │
 ───────────┼─────────── 中价值 / 中可见性
            │
        RAG 检索（自研 + 采购 - Product）
            │
        向量库（采购 - Commodity）
            │
 ───────────┼─────────── 低价值 / 低可见性
            │
        LLM API（采购 - Commodity）
        监控（采购 - Commodity）
```

**怎么用**：横轴按 Genesis → Custom → Product → Commodity 四段判位置，判据是「市场上有没有多个可替换供应商、还有没有人靠它做差异化」。这张图有保质期，图上必须标注下次重画时间；照抄组件名没有意义，要照抄的是判断方法。

**模板 4：Core-Edge-Spot + TCO**

| 能力 | 类别 | 战略 | 资源 |
| --- | --- | --- | --- |
| Agent 编排 | Core | 自研 | 5 人 × 3 年【经验】 |
| 领域 RAG | Core | 自研 | 3 人 × 2 年【经验】 |
| 向量库 | Edge | 采购 | 1 人 × 1 年【经验】 |
| LLM API | Edge | 采购 | 0.5 人 × 1 年【经验】 |
| 监控 | Edge | 采购 | 1 人 × 1 年【经验】 |
| 行业 AI 试点 | Spot | 合作 | 1 人 × 1 年【经验】 |

**怎么用**：类别一列按「客户是否可感知差异」判，不按技术先进程度判；资源列的人年随团队规模与既有基础设施差异极大，只作量级参考。采购项必须补一列「规模拐点」——用量到多少时成本排序会反转。

**模板 5：技术战略 OKR（下列阈值均为示意值【经验】，须按自家基线重设）**

```text
O1：成为 AI 智能体平台领导者
  KR1：客户满意度 ≥ 4.5/5
  KR2：API 可用性 ≥ 99.99%
  KR3：AI 应用上线周期 ≤ 2 周
  KR4：覆盖 Top 10 行业

O2：构建可治理的数据基础
  KR1：数据质量覆盖率 ≥ 95%
  KR2：数据资产化率 ≥ 80%
  KR3：合规事件 ≤ 0
  KR4：技术债利息 < 1000 万 / 年
```

**怎么用**：KR 的**阈值**要按自家基线定，不要照抄——四条里最容易出错的是「技术债利息」这类需要口径定义的项，填之前先写清利息怎么算、由谁测。上线周期这类 KR 尤其要在周期开始前冻结口径。

**模板 6：AI Strategy Canvas**

```text
维度：数据 / 算法 / 算力 / 治理 / 人才
权重：0.30 / 0.25 / 0.20 / 0.15 / 0.10（示意赋值）

数据：
  - 数据资产化（5/5）
  - 数据质量（4/5）
  - 数据治理（3/5）→ 改进
算法：
  - LLM 选型（5/5）
  - 领域微调（3/5）→ 改进
  - Agent 编排（4/5）
算力：
  - GPU 资源（4/5）
  - 边缘 AI（2/5）→ 改进
治理：
  - 合规流程与举证（3/5）→ 改进
  - 数据授权与审计留痕（3/5）
人才：
  - AI 科学家（3/5）→ 招聘
  - AI 工程师（4/5）

门槛判定（先于打分）：数据可获得性 / 合规可用性不达标 → 其余维度不计
```

**怎么用**：**门槛行不要照抄成分数**，它是布尔判定；权重列照抄会误导，五维权重是示意值。每个「→ 改进」项要补一句「补它要多久」。

**模板 7：技术战略汇报提纲（PPT 大纲）**

```text
1. 业务背景（1 页）——业务战略 / 业务挑战 / 技术机会
2. 技术愿景（1 页）——3-5 年愿景 / 与业务对齐
3. 技术现状（2 页）——现有能力 / 技术债 / 优势与劣势
4. 技术路线图（3 页）——H1（0-12 月）/ H2（12-36 月）/ H3（36-60 月）
5. 技术投资组合（2 页）——资源分配 / ROI 预估
6. 风险与缓解（1 页）——技术风险 / 业务风险 / 缓解策略
7. 团队建设（1 页）——人才招聘 / 培训计划
8. 总结（1 页）——Key Takeaways / 决策请求
```

**怎么用**：面向老板的一版把第 5、6 页提到第 3 页之前，把第 7 页合并进第 5 页——老板的耐心在第 4 页之前用完。第 8 页的「决策请求」必须写清今天要批什么（预算、编制、还是授权范围），否则会开成信息同步会。

**模板 8：AI 辅助战略规划（Python / Claude）**

```python
import anthropic

client = anthropic.Anthropic()
def draft_tech_strategy(context: dict) -> str:
    """基于业务战略 + 技术现状，让模型起草技术战略草稿（草稿必须由人改写）。"""
    fields = "\n".join(f"## {k}\n{v}" for k, v in context.items())
    prompt = f"""你是一名资深 CTO，请基于以下信息起草 3-5 年技术战略草稿。
{fields}

请输出 Markdown 报告，包含：技术愿景 / Three Horizons 投资组合 /
核心与边缘能力（Build-Buy-Partner）/ 分阶段路线图 / AI Strategy Canvas /
风险与缓解 / 团队建设 / ROI 预估。

另外单列一节：「上述结论里，哪几条是你在信息不足时猜的」。
"""
    msg = client.messages.create(
        model="claude-opus-5-5",   # 模型 ID 以官方文档当前版本为准，照抄旧 ID 会直接报错
        max_tokens=8000,
        messages=[{"role": "user", "content": prompt}],
    )
    return "".join(block.text for block in msg.content if block.type == "text")

print(draft_tech_strategy({
    "business_strategy": "成为 AI 智能体平台领导者，覆盖金融 / 制造 / 零售行业",
    "tech_current_state": "已有数据湖 + 实时数仓 + 早期 Agent 平台",
    "key_challenges": "模型成本失控、合规风险、人才缺口、竞品压力",
    "budget": "技术投入 <上限> / 年，团队 <人数> 人",
}))
```

**怎么用**：最后那节「哪几条是猜的」是必填项，它的作用是逼出模型的信息缺口，而不是让它自我评价。`business_strategy` 等四个字段必须填自家真实约束；预算与人数照抄示例值会得到一份对任何公司都成立、因而对贵公司无用的战略。

### 4.7 小结

> 本节小结：技术战略落地全程里唯一决定成败的环节是 **Step 6 的预算归属条款**——不是愿景写得好不好，也不是雷达画得多细。因为本主题下最根本的那条约束（§ 3.1 已论证它是两条里更根本的一条）是：**规划周期长于考核周期时，H3 类投入必然被季度压力吃掉**，而只有「这笔钱属于谁、能不能被别的层挪用」这一件事写在纸上，才能把 H3 移出当期的比较范围。其余环节——对齐、盘点、路线图、雷达、沟通、跟踪——都是为这一步提供输入或检验它的执行结果；它们做得好会提高战略的质量，做不好也只是质量差，而这一步没做，战略会在第一次季度盘点时被安静地撤掉。

> 💡 **思考锚点**：本节把成败压在 Step 6 的预算归属条款上——规划周期长于考核周期时，H3 类投入必然被季度压力吃掉。那么在你的战略里，究竟是哪一条白纸黑字的归属条款把 H3 移出了当期比较范围？翻遍全文指不出这一条的话，它靠什么扛过第一次季度盘点？
