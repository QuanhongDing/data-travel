### 8.8 §19.3 Lambda 架构与实时数据处理

> 本主题是「技术路线图制定」场景下的架构题：在实时计算需求变化下重新审视 Lambda / Kappa，考察架构选型、资源规划、迁移决策。面试官通常结合"万节点集群 + 3-5 年路线图"的背景提问。

#### §19.3.1 随着实时计算需求的增长，纯粹的 Lambda 或 Kappa 架构都可能面临新的挑战。请探讨在 AI 时代，数据架构可能的演进方向，并举例说明。

**1. 考察点**

- 是否理解"纯粹的 Lambda / Kappa 都有局限"。
- 能否说清 AI 时代数据架构的演进：湖仓一体、Data + AI 融合、Agent 化。
- 是否知道工业实践：Databricks / 阿里 / 字节。
- 加分项：能给"数据架构为 AI 服务"的具体设计。

**2. 参考答案框架**

**第一层：纯 Lambda / Kappa 的新挑战。**

- **Lambda**：双链路维护成本在 AI 时代更高（特征工程要双份）。
- **Kappa**：状态后端限制 + 不适合大规模历史训练数据。
- **共同挑战**：① AI 需要海量原始数据（结构化 + 非结构化），两者都不擅长；② AI 应用对延迟要求多样（在线推理 ms 级、离线批训练小时级）；③ 数据要支持向量检索 / 多模态。

**第二层：演进方向一——湖仓一体 + 多模态。** 用 Iceberg / Hudi / Paimon 做统一存储，同时存结构化数据 + 非结构化数据（文本 / 图片 / 音视频）+ 向量。为 AI 提供统一的训练数据源。代表：Databricks Lakehouse。

**第三层：演进方向二——Data + AI 融合平台。** 数据和 AI 不再是两个团队两个平台，而是统一平台：数据管道 → 特征 → 训练 → 推理 → 反馈全链路。代表：阿里 PAI + MaxCompute、Databricks。

**第四层：演进方向三——流批一体的实时 AI。** Flink 流处理 + 在线推理 + 在线学习，实现"数据即到即训即推"。代表：字节推荐系统、Uber Michelangelo。

**第五层：演进方向四——Agent 化的数据架构。** AI Agent 作为数据消费者和生产者的新入口：Agent 通过自然语言查询数据、Agent 自动生成数据管道、Agent 做数据治理。代表：Snowflake Cortex / Databricks Assistant / 各厂商的 Data Agent。

**第六层：具体例子。** 阿里的"数据 + AI"演进：MaxCompute（批） + 实时计算 Flink（流） + Paimon（湖仓） + PAI（ML） + 通义千问（LLM），构成完整的 Data for AI 与 AI for Data 闭环。

**3. 常见陷阱**

- **认为某个架构是终点** —— 数据架构持续演进。
- **忽视 AI 对架构的新需求**（向量 / 多模态 / 低延迟推理）。
- **只讲架构不讲业务价值**。

**4. 追问预测**

- **「AI 时代还需要数据湖吗？」** 答：更需要。AI 训练需要海量原始数据，数据湖是唯一能存全量 + 多类型的方案。
- **「向量数据库会取代传统数据库吗？」** 答：不会，是补充。向量库做相似检索，关系库做事务。

**5. 参考资料**

- Databricks Lakehouse 论文与官方文档——湖仓 + AI。
- 阿里 PAI + MaxCompute 公开技术分享——Data + AI 融合。
- 字节推荐系统公开分享——实时 AI 架构。
- Snowflake Cortex / Databricks Assistant 官方文档——AI 化的数据平台。
- Zhamak Dehghani《Data Mesh》——数据架构演进的另一种视角。

#### §19.3.2 在一个大规模数据平台中，为什么 Lambda 架构中的批处理层和速度层通常会使用不同的存储系统？请说明各自的技术选型理由。

**1. 考察点**

- 是否理解"存储选型由访问模式决定"。
- 能否说清批处理层（HDFS / 湖表）与速度层（OLAP / KV）的技术差异。
- 是否知道新趋势：湖仓一体让两层共享存储。
- 加分项：能给出具体的选型对照。

**2. 参考答案框架**

**第一层：访问模式驱动存储选型。**

- **批处理层**：存储全量历史（TB 到 PB 级）、顺序扫描为主、写少读多、延迟容忍高。
- **速度层**：存储近期结果（GB 到 TB 级）、随机点查 / 范围查、写频高、延迟敏感（ms 级）。

**第二层：批处理层的存储选型。**

- **HDFS**：适合大规模顺序扫描；成本低（本地盘）；但点查性能差。
- **湖表（Iceberg / Hudi）**：在对象存储上提供 ACID + 时间旅行；多引擎共享。
- **选型理由**：存全量历史 + 支持重算 + 成本可控。

**第三层：速度层的存储选型。**

- **KV 存储（HBase / Cassandra）**：高并发点查；适合"按用户 ID 查实时特征"。
- **OLAP（Druid / ClickHouse / Doris）**：高并发聚合查询；适合实时看板。
- **选型理由**：低延迟查询 + 高写入吞吐。

**第四层：为什么不用同一套存储。**

- **性能需求冲突**：批处理要"高吞吐顺序扫描"，速度层要"低延迟随机查询"，一套存储难以兼顾。
- **成本模型冲突**：批处理层数据量大要廉价存储；速度层要高性能存储（贵）。
- **一致性需求不同**：批处理层要强一致（重算正确）；速度层可接受最终一致。

**第五层：新趋势——共享存储。** 湖仓一体让批处理层与速度层共享 Iceberg / Hudi：

- 批处理读写全量分区；速度层写增量 / 读近期。
- 湖表提供 ACID + 时间旅行，兼顾两者。
- 但仍需 OLAP 层做高并发查询（湖表点查性能不足）。
- 实际形态：湖表（明细）+ OLAP（聚合看板）双层。

**第六层：工业实践。**

- **LinkedIn** 批处理层用 HDFS + 速度层用 Espresso / Venice。
- **Uber** 批处理层用 HDFS + 速度层用 Hudi + Pinot。
- **阿里** 批处理层用 MaxCompute + 速度层用 Hologres / Doris。
- **字节** 批处理层用 HDFS + 速度层用 ClickHouse / ByteHouse。

**3. 常见陷阱**

- **不区分访问模式** —— 存储选型的根本依据。
- **认为"湖仓一体后不需 OLAP"** —— 高并发查询仍需 OLAP。
- **忽视成本模型差异**。

**4. 追问预测**

- **「湖仓一体后速度层还需要 KV 存储吗？」** 答：需要。湖表点查（按主键）性能不如 HBase；实时特征查询仍用 KV。
- **「怎么选 OLAP？」** 答：高并发点查 Doris / StarRocks；宽表分析 ClickHouse；高吞吐摄入 Druid。

**5. 参考资料**

- Apache HBase / Cassandra / Druid / ClickHouse 官方文档——KV 与 OLAP 选型。
- Apache Iceberg / Hudi 官方文档——湖表存储。
- LinkedIn / Uber / 阿里 / 字节关于存算选型的公开分享。
- 阿里《大数据之路》——批流存储选型。

#### §19.3.3 请简要解释 Lambda 架构和 Kappa 架构的核心思想，并说明它们各自的主要优缺点。

**1. 考察点**

- 是否理解两者核心思想的差异（双链路 vs 单链路）。
- 能否客观列出各自优缺点。
- 是否知道适用场景。
- 加分项：能说清现代融合趋势。

**2. 参考答案框架**

**第一层：Lambda 核心思想。** 用"批处理层（保正确性）+ 速度层（保低延迟）+ 服务层（合并查询）"三部分，解决"历史准确"与"实时新鲜"不可兼得的矛盾。核心是"批处理层的输出是真相，速度层的输出会被覆盖"。

**第二层：Kappa 核心思想。** 只保留流处理单链路，历史重处理通过"重放 Kafka 消息"实现。核心是"一套代码处理所有数据"。

**第三层：Lambda 优缺点。**

- **优点**：批处理层可重算、可修正历史；适合大规模长周期聚合；准确性有保障。
- **缺点**：双份代码（口径易漂移）；双份存储（成本高）；双份运维；服务层合并复杂。

**第四层：Kappa 优缺点。**

- **优点**：一套代码（口径统一）；运维简单；时效统一（秒/分钟级）。
- **缺点**：Kafka 长期存储成本高；状态后端容量有限；复杂计算（跨流 join）难；依赖消息队列可靠性。

**第五层：适用场景。**

- **Lambda**：大规模长周期聚合、复杂历史重算、严格准确性场景（金融计费）。
- **Kappa**：数据量中等、时效优先、逻辑相对简单、流处理能力强的团队。

**第六层：现代融合。** 湖仓一体 + 流批一体让两者融合：核心实时链路用 Kappa，长周期用批处理，共享湖表。这是头部企业的实际选择。

**3. 常见陷阱**

- **只说优点不说缺点**。
- **绝对化某个架构**。
- **忽视现代融合**。

**4. 追问预测**

- **「初创公司选哪个？」** 答：数据量小 + 团队小，用 Kappa（或直接用 Serverless 流处理）；规模上来后再优化。
- **「大厂为什么还用 Lambda？」** 答：历史包袱 + 大规模场景 Kappa 不成熟 + 准确性要求高。

**5. 参考资料**

- Nathan Marz《Big Data》——Lambda 原始定义。
- Jay Kreps《Questioning the Lambda Architecture》——Kappa 原始定义。
- LinkedIn / Uber / Netflix 关于两者取舍的公开分享。
- 阿里《大数据之路》。

#### §19.3.4 在规划一个万节点级别的 Lambda 架构集群时，你会如何设计批处理层和速度层的资源隔离与协同机制？

**1. 考察点**

- 是否理解万节点下批流资源隔离的必要性。
- 能否设计：队列隔离 + 优先级 + 共享存储 + 统一调度。
- 是否知道工业实践：YARN 队列 / K8s namespace。
- 加分项：能给具体的资源配比与隔离级别。

**2. 参考答案框架**

**第一层：资源隔离的必要性。** 批处理层吃资源峰值（大 ETL），速度层 24×7 常驻且延迟敏感。不隔离会导致：批作业挤死流作业（SLA 违约）、流作业拖慢批作业、故障互相波及。

**第二层：隔离级别。**

- **物理隔离（最强）**：批流用不同集群（不同机房 / 不同 K8s 集群）。适合核心业务。成本高（资源冗余）。
- **逻辑隔离（常用）**：同一集群不同队列 / namespace。批用 YARN 队列 A、流用 K8s namespace B。资源可弹性共享。
- **标签隔离**：用 YARN node-labels / K8s nodeSelector 把某些节点专门给流处理。

**第三层：队列设计。**

- **批处理队列**：P0（核心 ETL）、P1（重要 ETL）、P2（Ad-hoc / 试验）；配 `maximum-capacity` 上限。
- **速度层队列**：流作业独立队列，配保底资源（guaranteed）+ 抢占禁止。
- **优先级**：P0 批作业与流作业都可抢占 P2。

**第四层：协同机制。**

- **共享存储**：批流写同一湖表（Iceberg / Hudi），批写全量分区、流写增量。
- **统一调度**：Airflow / DolphinScheduler 统一编排批流作业；流作业用长驻应用调度。
- **统一监控**：Prometheus + Grafana 统一监控批流。
- **口径统一**：共享 UDF 库。
- **对账机制**：每日批流结果对账。

**第五层：资源配比经验。**

- 按业务重要性分配：核心业务流作业保底 40% 资源；批作业用剩余弹性。
- 流作业用预留资源（云上 RI / 包年），批作业用弹性（Spot）。
- 高峰期（大促）动态调整配比。

**第六层：工业实践。**

- **阿里** 用 YARN 队列 + Fuxi 调度做批流隔离（Quota 管理）。
- **字节** 用 K8s namespace + ResourceQuota 做隔离。
- **Uber** 用 YARN 队列 + Spark on K8s 做混合。
- **LinkedIn** 用多集群 + 队列隔离。

**3. 常见陷阱**

- **不做隔离** —— 批流互相干扰。
- **只做逻辑隔离不做优先级** —— 关键时刻流作业仍可能被挤。
- **忽视共享存储设计** —— 批流数据不一致。

**4. 追问预测**

- **「物理隔离成本太高怎么办？」** 答：用逻辑隔离 + 弹性资源；核心业务物理隔离，非核心逻辑隔离。
- **「流作业被抢占怎么防？」** 答：流作业队列设 `yarn.scheduler.capacity.<queue>.disable-preemption` 或最高优先级。

**5. 参考资料**

- Apache YARN 官方文档——队列与抢占。
- Kubernetes 官方文档——ResourceQuota、PriorityClass、nodeSelector。
- 阿里 MaxCompute / Fuxi 调度公开分享——批流隔离。
- 字节 / Uber 关于 K8s 大数据工作负载的公开分享。

#### §19.3.5 假设现有 Lambda 架构的维护成本过高，团队希望向 Kappa 架构迁移。请描述一个分阶段迁移方案，并说明每个阶段的风险控制点。

**1. 考察点**

- 是否理解迁移是"工程 + 组织"双重工程。
- 能否设计分阶段方案：能力建设 → 试点 → 灰度 → 全量。
- 是否知道每个阶段的风险控制。
- 加分项：能给"退出标准"与"回滚预案"。

**2. 参考答案框架**

**第零阶段：评估与准备（1-2 月）。**

- **评估收益**：明确迁移的动机（成本？时效？口径？），量化目标。
- **能力盘点**：团队 Flink / Kafka 能力是否具备。
- **风险识别**：哪些链路绝对不能迁（金融计费、长周期聚合）。
- **风险控制**：不过度承诺；先做好团队培训。

**第一阶段：能力建设（1-2 月）。**

- 搭建 Kafka 集群（长期存储）+ Flink 集群（K8s）。
- 建立流处理的监控 / 告警 / 运维体系。
- 团队培训（Flink SQL / 状态管理 / 调优）。
- **风险控制**：能力没建好不迁移；用小项目练手。

**第二阶段：试点迁移（2-3 月）。**

- 选 1-2 个非核心链路做试点（如日志处理）。
- Kappa 与 Lambda 双轨运行，结果对账。
- 积累经验 + 完善工具。
- **风险控制**：试点失败不影响核心业务；对账零差异才继续。

**第三阶段：灰度迁移（3-6 月）。**

- 按业务优先级逐个迁移链路。
- 影子运行 + 灰度流量（10% → 50% → 100%）。
- 每日对账。
- **风险控制**：保留回滚能力；下游依赖分析清楚。

**第四阶段：全量迁移与下线（6-12 月）。**

- 核心链路迁移（除绝对不适用的）。
- 批处理链路逐步下线。
- **风险控制**：下线前确认"Kappa 稳定 N 周 + 对账零差异 + 无下游依赖"。

**第五阶段：复盘与优化（持续）。**

- 复盘迁移收益（成本 / 时效 / 稳定性）。
- 优化 Flink 作业（资源 / 状态）。
- 建立长期运维规范。

**3. 常见陷阱**

- **大爆炸式迁移** —— 一次性替换，风险极高。
- **不考虑团队能力** —— 硬上 Kappa 必失败。
- **没有退出标准** —— 何时下线批处理链路不清晰。
- **忽视对账** —— 双轨期无对账等于裸奔。

**4. 追问预测**

- **「迁移中途发现成本反而更高怎么办？」** 答：暂停迁移，分析根因（Kafka 存储 + Flink 常态运行成本）；评估是否值得继续。
- **「团队不配合怎么办？」** 答：从架构收益（减少口径 bug）入手，用试点项目的成功说服。

**5. 参考资料**

- LinkedIn / Uber / Netflix 关于架构迁移的公开实践。
- Martin Fowler 关于 Strangler Fig 模式的文章。
- 阿里"去 IOE"渐进迁移案例。
- Apache Flink / Kafka 官方文档——迁移相关的运维指南。
