### 8.9 §19.5 大数据技术趋势与演进方向

> 本主题是「技术路线图」的核心考察点：湖仓一体、流批一体、万节点 3-5 年路线图、未来技术趋势、AI for Data。面试官考察的是资深架构师的"前瞻判断力 + 落地规划力"。

#### §19.5.1 请谈谈你对数据湖仓一体化（Lakehouse）架构的理解，并说明它相比传统数据仓库和数据湖的优势。

**1. 考察点**

- 是否理解 Lakehouse 的核心：**用表格式层在数据湖上补齐数仓能力**。
- 能否对比三种架构（数仓 / 数据湖 / Lakehouse）。
- 是否知道工业实践：Databricks / Netflix / Uber。
- 加分项：能说清"表格式层"的关键作用。

**2. 参考答案框架**

**第一层：三者的定义对比。**

| 维度 | 数据仓库 | 数据湖 | Lakehouse |
| --- | --- | --- | --- |
| Schema | on-Write | on-Read | on-Read + 治理 |
| ACID | 有 | 无（早期） | 有（表格式层） |
| 数据 | 结构化 | 多类型 | 多类型 |
| 存储 | 专用（贵） | 对象存储（廉） | 对象存储（廉） |
| 引擎 | 紧耦合 MPP | 多引擎 | 多引擎 |
| 用户 | BI / 分析师 | 数据科学家 | 两者 |

**第二层：Lakehouse 的核心机制。** 用**表格式层（Iceberg / Hudi / Delta Lake）**在对象存储上提供：

- **ACID 事务**：并发读写安全。
- **Schema 演进**：add / rename / drop column。
- **时间旅行**：查询历史快照。
- **增量读**：只读变更。
- **元数据管理**：避免"数据沼泽"。

**第三层：相比数据仓库的优势。**

- **成本更低**：对象存储比专用存储便宜。
- **开放性**：不被单一厂商锁定。
- **多类型数据**：支持结构化 + 半结构 + 非结构化。
- **AI 支持**：为 ML 提供海量原始数据。

**第四层：相比数据湖的优势。**

- **ACID**：补上了数据湖缺失的事务能力。
- **治理**：元数据 / 权限 / 血缘。
- **查询性能**：统计信息 + 索引 + 列存。
- **统一**：一份数据同时服务 BI + ML + 流处理。

**第五层：工业实践。**

- **Databricks** 是 Lakehouse 的提出者（Delta Lake）。
- **Netflix** 是 Iceberg 最大生产用户。
- **Uber** 是 Hudi 主要贡献者。
- **阿里** 用 Paimon 做湖仓一体。
- **Snowflake** 从数仓向湖仓演进（Iceberg Tables）。

**3. 常见陷阱**

- **认为 Lakehouse = 数据湖 + 数仓简单叠加** —— 关键在表格式层。
- **忽视治理** —— Lakehouse 的治理和存储能力同等重要。
- **不提开放表格式** —— 这是 Lakehouse 的核心。

**4. 追问预测**

- **「Lakehouse 能替代数仓吗？」** 答：新建场景可以；存量专有数仓迁移成本高。
- **「Iceberg / Hudi / Delta 怎么选？」** 答：Iceberg 跨引擎、Hudi CDC、Delta Databricks 生态。

#### §19.5.2 在当前技术背景下，流批一体架构为何成为重要趋势？请结合具体技术（如 Flink、Spark）说明其实现方式与优势。

**1. 考察点**

- 是否理解流批一体的驱动力：消除双链路成本、统一口径。
- 能否说清实现方式：统一 API + 统一引擎 + 统一存储。
- 是否知道工业实践。
- 加分项：能结合 Flink / Spark 的实现细节。

**2. 参考答案框架**

**第一层：为什么成为趋势。**

- **成本**：双链路维护成本高（两套代码 / 存储 / 运维）。
- **口径**：批流口径漂移是数据事故的头号来源。
- **实时化**：业务对时效要求提高，批的"T+1"不够。
- **技术成熟**：Flink / Spark 的流处理能力足够强，能承接批的负载。

**第二层：Flink 的实现。**

- **统一 API**：Table API / SQL 同时支持批（有界）与流（无界）。
- **统一 Runtime**：批模式（Blocking shuffle）+ 流模式（Pipelined shuffle）。
- **统一状态**：checkpoint 与状态后端批流共用。
- **上游下游统一**：Kafka / Iceberg / Hudi 既是批的 Source 也是流的 Source。

**第三层：Spark 的实现。**

- **Structured Streaming**：把流当作"无界的表"，与批 DataFrame / SQL 统一 API。
- **微批（Micro-batch）**：默认按小批次处理（100ms-分钟级）。
- **连续处理模式（Continuous Processing）**：低延迟模式（ms 级，实验性）。
- **统一 Source/Sink**：Kafka / Delta 批流共用。

**第四层：优势。**

- **一套代码**：消除批流口径漂移。
- **一套运维**：降低运维成本。
- **统一存储**：Lakehouse 让批流共享一份数据。
- **时效提升**：从 T+1 提升到秒/分钟级。

**第五层：工业实践。**

- **阿里** Flink + Paimon 是流批一体的代表。
- **字节** Flink on K8s 承接抖音实时数据。
- **Databricks** Spark + Delta 是批流一体的另一路径。
- **Netflix** Flink + Iceberg 流批协同。

**3. 常见陷阱**

- **认为流批一体 = 用流替代批** —— 是统一抽象。
- **忽视状态后端限制**。
- **只说 API 不说存储**。

**4. 追问预测**

- **「Flink 和 Spark 谁更适合流批一体？」** 答：Flink 强在流、Spark 强在批与 ML；现代架构常两者共存。
- **「流批一体怎么保证结果一致？」** 答：同一算子 + 同时间语义 + 相同状态恢复。

#### §19.5.3 在制定一个万节点级别大数据集群的未来 3-5 年技术路线图时，除了技术选型，还需要考虑哪些关键因素？请系统阐述你的规划框架。

**1. 考察点**

- 是否具备"资深架构师级"的系统性规划能力。
- 能否覆盖技术之外的因素：成本 / 组织 / 合规 / 业务 / 风险。
- 是否知道工业实践与技术趋势。
- 加分项：能给分阶段的路线图框架。

**2. 参考答案框架**

**第一层：规划的五个维度。**

1. **技术选型**：引擎 / 存储 / 调度 / 表格式。
2. **成本（FinOps）**：单位成本、投资组合（H1/H2/H3）、ROI。
3. **组织与人才**：团队能力、招聘、培训、组织架构。
4. **合规与安全**：数据安全法 / 个保法 / GDPR / 行业监管。
5. **业务对齐**：技术路线必须服务业务战略。

**第二层：技术选型维度。** 从"存算分离 + 湖仓一体 + 流批一体"三个主线规划：

- 存储：从 HDFS 迁移到对象存储 + Iceberg / Hudi / Paimon。
- 计算：从 MapReduce / Hive 演进到 Spark + Flink + Trino。
- 调度：从 Cron / Azkaban 演进到 Airflow / DolphinScheduler / K8s。
- 表格式：从 Hive Table 演进到 Iceberg / Hudi。

**第三层：成本维度。** Three Horizons 投资组合（70/20/10）：

- H1（核心）：现有平台稳定性 + 成本优化。
- H2（新兴）：湖仓一体 + 流批一体 + 实时能力。
- H3（未来）：AI 集成 + 新范式探索。
- 单位成本（per query / per TB）作为核心 KPI。

**第四层：组织维度。**

- **能力建设**：现有团队技能盘点 + 缺口识别 + 招聘 / 培训计划。
- **组织架构**：平台团队（基础设施）+ 数据团队（业务）+ 治理团队（合规）。
- **协作机制**：跨团队评审、共建、知识共享。

**第五层：合规模度。**

- **数据安全法 / 个保法**：数据分类分级、跨境传输、删除能力。
- **行业监管**：金融 / 医疗 / 电信的行业要求。
- **审计能力**：全链路审计日志。
- **合规预算**：合规团队 + 工具投入。

**第六层：业务对齐维度。**

- **业务战略映射**：技术路线必须回答"支撑哪些业务目标"。

#### §19.5.4 随着数据规模和复杂度的增长，你认为未来 3-5 年大数据平台在计算引擎、存储、调度三个层面会有哪些演进？

**1. 考察点**

- 是否对大数据技术演进有前瞻判断。
- 能否分层预测：计算引擎 / 存储 / 调度。
- 是否能结合趋势（云原生 / AI / 湖仓）。
- 加分项：能给"预测的依据"而非空谈。

**2. 参考答案框架**

**第一层：计算引擎的演进。**

- **流批一体成熟**：Flink / Spark 统一批流；新引擎（如 RisingWave / Materialize）探索"流式数据库"。
- **云原生弹性**：从"集群内调度"到"集群间弹性"（Spark on K8s / 无服务器）。
- **向量化 + 编译执行**：Velox / Photon / DataFusion 等向量化执行引擎成为标配。
- **AI 融合**：SQL + LLM（Text-to-SQL）；AI 优化器（自学习查询优化）。
- **异构计算**：GPU / DPU 加速数据处理。

**第二层：存储的演进。**

- **湖仓一体成为标准**：Iceberg / Hudi / Paimon 成为事实标准存储格式。
- **存算分离**：对象存储 + 表格式层成为主流。
- **多模态统一**：结构化 + 非结构化 + 向量统一存储（如 Lance / Iceberg 的向量扩展）。
- **格式统一**：Iceberg v3 引入删除文件、变长类型、向量支持。
- **零拷贝共享**：跨引擎 / 跨云共享数据（Snowflake Data Sharing / Delta Sharing）。

**第三层：调度的演进。**

- **声明式调度**：从"配置依赖"到"声明期望状态"（类似 K8s 的 Operator 模式）。
- **数据驱动调度**：从"时间依赖"到"数据就绪依赖"。
- **AI 优化调度**：AI 预测作业运行时长 + 动态调整优先级。
- **统一编排**：批 + 流 + ML pipeline 统一编排（Airflow 3.0 / Dagster / Prefect）。
- **Serverless 调度**：无需管理集群。

**第四层：贯穿三条线的趋势。**

- **云原生**：所有层面向 K8s 迁移。
- **AI 化**：AI 增强（优化器 / 调度 / 运维）+ 服务 AI（Data for AI）。
- **开放化**：开放表格式 / 开放标准（OpenLineage / Open Table Format）。
- **FinOps 化**：成本成为一等公民。

**第五层：工业实践与信号。**

- **Databricks Photon** 是向量化执行引擎的工业标杆。
- **Snowflake** 的存储 + 计算分离是演进方向。
- **阿里 Paimon** 是流批一体存储的新探索（2024 捐给 Apache）。
- **Uber / Netflix** 的增量处理实践指向"存储层统一"。
- **LangChain / LlamaIndex** 指向"AI 与数据平台融合"。

**3. 常见陷阱**

- **空谈趋势不说依据** —— 面试官要听"为什么这么判断"。
- **只讲一个层面** —— 计算 / 存储 / 调度要全覆盖。
- **忽视 AI 的影响** —— AI 是最大的变量。

**4. 追问预测**

- **「Hadoop 会消失吗？」** 答：HDFS + YARN 会逐步被对象存储 + K8s 替代，但 Hive SQL 生态会长期存在。

#### §19.5.5 AI for Data（或 Data for AI）是当前的热点，请讨论大数据平台如何更好地与 AI 融合，并说明技术架构上的关键设计。

**1. 考察点**

- 是否理解 AI 与数据平台的双向融合（Data for AI / AI for Data）。
- 能否说清架构设计：向量存储、特征平台、模型服务、Agent。
- 是否知道工业实践。
- 加分项：能给完整的融合架构。

**2. 参考答案框架**

**第一层：双向融合。**

- **Data for AI**：数据平台为 AI 提供训练数据 / 特征 / 样本。
- **AI for Data**：AI 增强数据平台（智能 ETL、自然语言查询、数据治理、数据质量）。

**第二层：Data for AI 的架构设计。**

- **统一存储**：湖仓一体存结构化 + 非结构化 + 向量。
- **特征平台**：Feature Store 统一离线/在线特征（Feast / Tecton / 阿里 FeatureStore）。
- **样本管理**：训练样本的版本管理 + 时序正确性（point-in-time）。
- **数据质量**：训练数据的质量校验（分布 / 缺失 / 异常）。
- **向量存储**：向量数据库（Milvus / Qdrant / pgvector）支持相似检索。

**第三层：AI for Data 的架构设计。**

- **自然语言查询（Text-to-SQL）**：LLM 把自然语言转 SQL；结合 Schema / 血缘做 RAG。
- **智能 ETL**：AI 生成数据管道 / 自动补全 / 优化。
- **数据治理**：AI 识别敏感数据 / 推断血缘 / 推荐数据质量规则。
- **智能运维**：AI 预测作业失败 / 优化资源调度。
- **Data Agent**：Agent 作为数据的新入口，自主查询 / 分析 / 生成报告。

**第四层：关键设计要点。**

- **元数据即上下文**：AI 需要 Schema / 血缘 / 业务语义作为上下文（RAG 的检索源）。
- **向量化存储**：数据 + 元数据向量化，支持语义检索。
- **模型服务分离**：AI 能力通过模型服务（LLM API / 自建）提供，不耦合到数据平台。
- **权限与合规**：AI 访问数据必须有权限控制 + 审计（防数据泄露）。
- **可解释性**：AI 生成的 SQL / 结论要可追溯。

**第五层：工业实践。**

- **Databricks** 的 Lakehouse + MLflow + Assistant（AI 生成 SQL）。
- **Snowflake** 的 Cortex（内置 LLM）+ Document AI。
- **阿里** 的 PAI + DataWorks Copilot + 通义千问。
- **字节** 的 DataLeap + 智能数据助手。
- **Microsoft Fabric** 的 Copilot。

**3. 常见陷阱**

- **只讲 Data for AI 不讲 AI for Data** —— 双向融合。
- **忽视元数据 / 上下文** —— AI 没有上下文做不好。
- **忽视权限合规** —— AI 访问敏感数据的风险。

**4. 追问预测**

- **「Text-to-SQL 准确率怎么提升？」** 答：RAG 检索 Schema + Few-shot 示例 + 校验（执行前 dry-run）。
- **「AI 生成的数据管道可靠吗？」** 答：AI 生成 + 人工审核 + 自动化测试；不建议全自动上生产。
