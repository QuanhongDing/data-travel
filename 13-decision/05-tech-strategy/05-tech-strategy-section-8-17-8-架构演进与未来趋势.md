### 8.7 §17.8 架构演进与未来趋势

> 本主题考察「新一代统一数据架构」：AI 与大数据融合、存算分离、湖仓一体、实时数仓、批流一体、数据湖与数仓的本质差异。面试官从概念辨析切入，逐层下钻到架构落地与选型取舍。

#### §17.8.1 请探讨 AI 与大数据平台融合的趋势，并分析在批流一体架构中集成机器学习能力的架构设计与挑战。

**1. 考察点**

- 是否理解"AI + 大数据"的融合形态：数据供 AI、AI 增强数据、平台化 AI。
- 能否说清批流一体架构中集成 ML 的设计：特征、训练、推理。
- 是否知道工业实践：Databricks Lakehouse + MLflow、阿里 PAI、字节。
- 加分项：能给"Data for AI + AI for Data"的双向闭环。

**2. 参考答案框架**

**第一层：融合的三个层次。**

- **Data for AI（数据服务于 AI）**：大数据平台为 AI 提供训练数据、特征、样本。
- **AI for Data（AI 增强数据）**：AI 用于数据治理（质量检测、血缘推断、智能 ETL、自然语言查询）。
- **Platform AI（平台化的 AI）**：统一的湖仓 + ML 平台（如 Databricks）。

**第二层：批流一体中集成 ML 的架构设计。**

- **特征工程层**：流处理（Flink）产出实时特征，批处理（Spark）产出历史特征，Feature Store 统一管理（保证训练-服务一致）。
- **训练层**：批处理用历史特征训练模型（Spark ML / PyTorch）；在线学习用流处理增量更新。
- **推理层**：流处理调用模型服务（TF Serving / Triton）做实时推理。
- **反馈层**：推理结果 + 业务反馈回到训练数据，形成闭环。

**第三层：架构形态。**

- **Unified Lakehouse**：Iceberg / Delta 做统一存储；Spark（批）+ Flink（流）做计算；MLflow 做模型管理。
- **Feature Store 集成**：Flink 实时特征写入 Feature Store；Spark 训练读取。
- **模型服务集成**：流处理通过 gRPC 调用模型服务。
- **Pipeline 编排**：ML pipeline（数据 → 特征 → 训练 → 评估 → 部署）用 Airflow / Kubeflow 编排。

**第四层：挑战。**

- **数据一致性**：训练数据与推理特征必须一致（Training-Serving Skew）。
- **延迟**：模型推理延迟影响流处理端到端延迟。
- **资源隔离**：训练（GPU 密集型）与流处理（延迟敏感）资源冲突。
- **版本管理**：模型、特征、数据的版本必须可追溯（实验可复现）。
- **数据漂移**：线上数据分布变化导致模型失效，需要监控。
- **算力成本**：GPU 训练 + 推理成本高。

**第五层：工业实践。**

- **Databricks** 的 Lakehouse + MLflow + Feature Store 是"湖仓 + ML"的标杆。
- **阿里** 的 PAI（机器学习平台）+ MaxCompute 提供 Data for AI 的完整链路。
- **字节跳动** 的推荐系统是"实时特征 + 在线训练"的典范。
- **Uber** 的 Michelangelo 平台支撑了 Uber 的所有 ML 应用。
- **Meta** 的 FB Learner Flow 是内部的 ML 平台。

**3. 常见陷阱**

- **把 ML 当"分析工具"** —— ML 是平台能力，不是报表的补充。
- **忽视特征一致性** —— 训练/推理漂移让模型失效。
- **不做资源隔离** —— 训练作业拖垮流处理。

**4. 追问预测**

- **「Feature Store 是必需的吗？」** 答：多模型共享特征时必需；单模型可以不用，但容易出现训练-服务偏差。
- **「LLM 怎么集成到批流一体？」** 答：LLM 推理延迟高，用于离线批处理 / 异步任务；实时用轻量模型。

#### §17.8.2 在构建云原生数据平台时，存算分离架构带来了哪些好处？请结合具体技术（如 S3、Iceberg、Kubernetes）说明，并分析其挑战。

**1. 考察点**

- 是否理解存算分离的本质：**存储与计算独立伸缩**。
- 能否说出好处：弹性、成本、多引擎共享。
- 是否知道挑战：网络带宽、数据本地性、一致性。
- 加分项：能结合 Snowflake / Databricks / 阿里谈工业实践。

**2. 参考答案框架**

**第一层：存算分离的定义。** 把数据存储（对象存储 S3 / OSS）与计算资源（无状态计算节点）解耦，计算节点按需启停，共享同一份存储。

**第二层：核心好处。**

- **独立伸缩**：存储与计算按各自需求伸缩；不再"为了存数据而养集群"。
- **弹性计算**：计算节点按需启停（K8s + Spot 实例），成本显著下降（幅度取决于负载的间断性与 Spot / 预留实例的配比，随业务形态差异很大，不宜引用单一区间，此处按【经验】档处理）。
- **多引擎共享**：同一份数据可以被 Spark / Flink / Trino / Presto 同时读取（配合 Iceberg）。
- **成本优化**：对象存储单价远低于本地 HDD/SSD（价差随厂商、规格与计费口径而异，不宜引用单一比值，此处按【经验】档处理）。
- **容灾简单**：数据在对象存储，天然多副本；计算节点故障不影响数据。
- **无状态化**：计算节点无状态，故障恢复快。

**第三层：具体技术。**

- **存储层**：AWS S3 / 阿里 OSS / GCP GCS（对象存储）。
- **表格式层**：Iceberg / Hudi / Delta Lake（提供 ACID + Schema 演进 + 时间旅行）。
- **计算层**：Kubernetes 编排 Spark / Flink；无状态 + 弹性。
- **缓存层**：Alluxio / JuiceFS 做对象存储前的缓存，缓解网络延迟。

**第四层：挑战。**

- **网络带宽**：计算节点每次读取都要走网络；对象存储的吞吐成为瓶颈。缓解：缓存层 + 数据本地性优化。
- **延迟**：对象存储的 first-byte 延迟高于本地 HDD；对延迟敏感场景（交互式查询）不友好。
- **一致性**：对象存储的最终一致（部分厂商已实现强一致）曾导致数据可见性问题。
- **元数据压力**：海量小文件在对象存储上的元数据操作慢；需要 compaction。
- **成本模型变化**：从"固定集群成本"变为"按使用计费"，成本可预测性下降。
- **安全**：对象存储的访问控制（IAM / Bucket Policy）需要重新设计。

**第五层：工业实践。**

- **Snowflake** 是存算分离的开创者——存储在三方云对象存储，计算独立伸缩。
- **Databricks** 的 Lakehouse = 存算分离 + Delta Lake + Spark。
- **阿里 MaxCompute** 从 2019 年起向存算分离演进（存储用 ECS + 对象存储）。
- **AWS EMR + S3** 是 AWS 上的存算分离标准组合。
- **Google BigQuery** 是完全 Serverless 的存算分离数仓。

**3. 常见陷阱**

- **忽视网络带宽瓶颈** —— 存算分离在超大 shuffle 场景下网络成瓶颈。
- **认为"存算分离必然省钱"** —— 高频访问场景下网络 + 对象存储 API 成本可能更高。
- **不做缓存层** —— 直接读对象存储延迟高。

**4. 追问预测**

- **「存算分离后 shuffle 怎么办？」** 答：shuffle 数据仍本地/近端存储（如 EMR 的本地盘），或改用 remote shuffle service（如 Apache Celeborn / Uber Spark-RSS）把 shuffle 数据落远端存储。
- **「对象存储一致性够吗？」** 答：S3 已实现强一致（2020 后）；但元数据操作仍慢，需要 compaction。

#### §17.8.3 随着数据治理和成本控制日益重要，在数据湖仓一体架构下，如何设计有效的数据治理与成本控制体系？

**1. 考察点**

- 是否理解"治理"与"成本"是湖仓一体的两大治理命题。
- 能否分层设计：元数据 / 血缘 / 质量 / 权限 / 成本。
- 是否知道湖仓特有的治理挑战：多引擎、多副本、Schema 演进。
- 加分项：能结合 Databricks Unity Catalog / 阿里 DataWorks 谈落地。

**2. 参考答案框架**

**第一层：数据治理的五个维度。**

- **元数据治理**：统一的 Catalog（表 / 列 / 分区 / 统计信息）。
- **血缘治理**：数据从源到消费的全链路血缘。
- **质量治理**：数据质量规则 + 监控 + 告警。
- **权限治理**：细粒度访问控制 + 动态脱敏。
- **成本治理**：资源归因 + 存储分层 + 计算优化。

**第二层：湖仓一体的治理挑战。**

- **多引擎**：同一份数据被 Spark / Flink / Trino 读取，权限要跨引擎统一。
- **多副本**：湖表 + 缓存 + OLAP 副本，一致性难保证。
- **Schema 演进**：湖表的 Schema 演进（add / rename / drop）比传统数仓复杂。
- **小文件**：湖表的小文件治理（compaction）。
- **成本模型**：对象存储 + 计算分离，成本归因复杂。

**第三层：治理体系设计。**

- **统一 Catalog**：Databricks Unity Catalog / 阿里 DataWorks / Iceberg REST Catalog——一份元数据 + 一份权限。
- **血缘采集**：通过 SQL Parser + Hook 采集血缘；Atlas / DataHub / OpenLineage。
- **质量卡点**：关键节点插 DQC 校验（行数 / 空值 / 枚举），异常阻断下游。
- **权限中心**：Ranger / Unity Catalog 做表 / 列 / 行级授权 + 脱敏。
- **成本中心**：把资源消耗按作业 / 业务线归因；Databricks 的 Tagging + 阿里 DataWorks 成本中心。

**第四层：成本控制手段。**

- **存储分层**：热（本地/SSD）→ 温（对象存储标准）→ 冷（归档）；参考 §4.5.7。
- **计算优化**：AQE + 动态资源分配 + 增量计算替代全量。
- **小文件治理**：compaction 减少文件数，降低元数据成本。
- **查询优化**：列裁剪 / 分区裁剪 / 物化视图。
- **弹性计算**：Spot 实例 + 按需伸缩。
- **成本看板**：每团队 / 每作业的成本可见。

**第五层：工业实践。**

- **Databricks Unity Catalog** 是湖仓治理的一体化标杆（元数据 + 权限 + 血缘 + 审计）。
- **阿里 DataWorks** + **MaxCompute** 是国内最完整的湖仓治理体系。
- **Snowflake** 的治理（Access Control + Masking + Cost Monitoring）是云数仓标杆。
- **Netflix** 的 Metaflow + 数据治理实践。

**3. 常见陷阱**

- **治理与成本分开做** —— 两者必须联动（如成本提示某个表该 compaction）。
- **只管元数据不管血缘** —— 没有血缘，治理无从下手。
- **成本不做归因** —— 没有靶子。

**4. 追问预测**

- **「湖仓血缘怎么采集？」** 答：SQL Parser 解析 + 引擎 Hook + OpenLineage 标准；Iceberg 的 snapshot 也能提供部分血缘。
- **「成本怎么降到最低？」** 答：存储分层 + 增量计算 + 弹性资源 + 小文件治理，四管齐下。

#### §17.8.4 实时数仓的构建对数据处理链路提出了更高要求，请描述一个典型的实时数仓技术架构，并说明各层的核心组件与设计要点。

**1. 考察点**

- 是否理解实时数仓的分层（ODS → DWD → DWS → ADS）。
- 能否说清每层的核心组件：Kafka / Flink / OLAP。
- 是否知道关键设计：一致性、回溯、维表 join。
- 加分项：能给"流式数仓 + OLAP"的完整技术栈。

**2. 参考答案框架**

**第一层：实时数仓的分层。**

- **ODS（实时采集层）**：CDC（Debezium / Flink CDC）采集业务库 + 日志采集（Filebeat）→ Kafka。
- **DWD（实时明细层）**：Flink 做清洗 / 规范化 / 维表关联 → 写 Kafka 或湖表。
- **DWS（实时汇总层）**：Flink 窗口聚合（分钟级）→ 写 OLAP（Doris / ClickHouse）。
- **ADS（实时应用层）**：面向看板 / API / 风控的在线服务。

**第二层：核心组件。**

- **采集**：Flink CDC / Debezium（CDC）+ Filebeat / Flume（日志）+ Canal（MySQL）。
- **传输**：Kafka（消息队列，缓冲 + 削峰）。
- **计算**：Flink（流处理，状态 + 窗口）。
- **存储**：Doris / ClickHouse / StarRocks（OLAP，高并发查询）+ Iceberg / Paimon（湖表，存明细）。
- **服务**：统一的查询网关 + 缓存。

**第三层：设计要点。**

- **一致性**：exactly-once 语义（Flink checkpoint + Kafka 事务）；维表 join 的一致性（temporal join + 版本）。
- **回溯能力**：Kafka 保留近期历史 + 湖表保留全量；重算用 offset 重置或湖表重放。
- **维表关联**：实时维表用 `Lookup Join`（查外部存储，如 HBase / Redis）；历史维表用 `Temporal Join`（带时间版本）。
- **迟到数据**：watermark + 允许迟到 + 侧输出。
- **OLAP 选型**：高并发点查（Doris / StarRocks）、宽表分析（ClickHouse）、高吞吐写入（Druid）。
- **数据分层存储**：热数据在 OLAP、全量明细在湖表。

**第四层：典型技术栈。**

- **阿里实时数仓**：Flink + Hologres / MaxCompute + DataWorks。
- **字节实时数仓**：Flink + ClickHouse / Doris + ByteHouse。
- **美团实时数仓**：Flink + Doris + Kafka。
- **腾讯实时数仓**：Flink + ClickHouse + TDSQL。

**第五层：挑战。**

- **资源成本**：流处理 24×7 运行，成本高于批处理。
- **状态管理**：维表 + 状态后端容量。
- **运维复杂度**：Kafka / Flink / OLAP 三套系统协同。
- **数据一致性**：批流结果对账。

**3. 常见陷阱**

- **只讲 Flink 不讲 OLAP** —— 实时数仓的查询层同样关键。
- **忽视维表关联** —— 实时维表 join 是一致性难点。
- **不做回溯设计** —— 业务逻辑变更无法重算历史。

**4. 追问预测**

- **「维表更新了怎么办？」** 答：用 Flink 的 temporal join（带版本）；或用广播状态（broadcast state）实时更新维表。
- **「怎么保证端到端 exactly-once？」** 答：Flink checkpoint + Kafka 事务 + 幂等 sink；sink 侧用主键 upsert。

#### §17.8.5 请解释批流一体架构（如 Apache Flink 或 Spark Structured Streaming）相比传统 Lambda 架构的优势，并说明其关键技术支撑。

**1. 考察点**

- 是否理解批流一体与 Lambda 的根本差异（统一 vs 双链路）。
- 能否说清关键技术支撑：统一 API、统一引擎、统一存储。
- 是否知道局限与适用场景。
- 加分项：能结合 Flink / Spark 的实现细节。

**2. 参考答案框架**

**第一层：与 Lambda 的根本差异。**

| 维度 | Lambda | 批流一体 |
| --- | --- | --- |
| 抽象 | 批 / 流两套 | 批 = 有界流（统一） |
| 代码 | 两套 | 一套 |
| 一致性 | 需合并批流结果 | 天然统一 |
| 存储 | 双存储 | 可共享湖表 |

**第二层：关键优势。**

- **消除口径漂移**：一套代码保证批流结果一致。
- **降低运维成本**：一套调度、一套监控。
- **简化架构**：没有服务层的合并逻辑。
- **统一存储**：Lakehouse 让批流共享一份数据。

**第三层：关键技术支撑。**

- **统一 API**：Flink Table API / SQL、Spark Structured Streaming、Beam——同一份代码支持批流。
- **统一执行引擎**：Flink Runtime 统一处理（批模式 + 流模式）；Spark 的微批（micro-batch）。
- **事件时间 + Watermark**：统一的时间语义，处理乱序数据。
- **统一状态管理**：批流都用 checkpoint + 状态后端。
- **统一 Sink/Source**：Kafka / Iceberg / Hudi 既是批的 Source 也是流的 Source。

**第四层：局限。**

- **超大规模长周期聚合**：流处理状态后端有限。
- **成熟度差异**：Flink 批模式不如 Spark；Spark 流模式延迟不如 Flink。
- **迁移成本**：现有 Lambda 系统迁移到批流一体需要重构。

**第五层：工业实践。**

- **阿里** Flink + Paimon——流批一体的代表。
- **字节** Flink on K8s——大规模流批一体。
- **Netflix** Flink + Iceberg——流批协同。
- **Databricks** Spark + Delta——Painless 批流一体。

**3. 常见陷阱**

- **认为批流一体就是 Flink** —— Spark 也支持批流一体。
- **忽视局限** —— 超大规模长周期聚合不适合。
- **只说 API 不说存储** —— 真正的批流一体需要存储层统一。

**4. 追问预测**

- **「Flink 批模式 vs Spark 批处理？」** 答：Flink 批模式在中小 batch 上够用，但超大规模批仍 Spark 更成熟；实践中常两者共存。
- **「批流一体怎么保证一致性？」** 答：同一算子 + 同时间语义 + 状态恢复。

#### §17.8.6 请阐述你对数据湖与数据仓库核心区别的理解，并说明为什么数据湖仓一体架构会成为趋势。

**1. 考察点**

- 是否理解数据湖（Schema-on-Read）与数仓（Schema-on-Write）的本质差异。
- 能否说清各自的优势与局限。
- 是否知道湖仓一体的核心主张与工业实践。
- 加分项：能说清"湖仓一体不是简单叠加，而是用表格式层统一"。

**2. 参考答案框架**

**第一层：数据湖 vs 数据仓库的核心区别。**

| 维度 | 数据湖 | 数据仓库 |
| --- | --- | --- |
| Schema | Schema-on-Read | Schema-on-Write |
| 数据类型 | 结构化 / 半结构化 / 非结构化 | 主要结构化 |
| 存储 | 对象存储（廉价） | 专用存储（较贵） |
| 计算 | 多引擎（Spark / Flink） | 紧耦合（MPP） |
| 事务 | 弱（早期） | 强（ACID） |
| 用户 | 数据科学家 / 工程师 | BI / 分析师 |
| 典型代表 | Hadoop / S3 + Spark | Teradata / Snowflake / Redshift |

**第二层：数据湖的优劣。**

- **优势**：存全量原始数据、支持多类型数据、存储廉价、灵活 Schema。
- **劣势**：无 ACID（早期）、无一致性保证、元数据混乱（"数据沼泽"）、查询性能差。

**第三层：数据仓库的优劣。**

- **优势**：ACID、强一致、查询性能好、业务友好。
- **劣势**：只支持结构化数据、存储贵、Schema 变更难、封闭。

**第四层：湖仓一体的核心主张。** 用**表格式层（Table Format）**在数据湖之上补齐数仓能力：

- **ACID 事务**：Iceberg / Hudi / Delta 提供。
- **Schema 演进**：add / rename / drop column。
- **时间旅行**：查询历史快照。
- **多引擎**：Spark / Flink / Trino 共享同一份数据。
- **元数据**：统一的 Catalog（避免"数据沼泽"）。

**第五层：为什么成为趋势。**

- **成本**：对象存储远低于专用数仓存储。
- **开放性**：不被单一厂商锁定（vs 专有数仓）。
- **统一性**：一份数据支持 BI + ML + 流处理。
- **能力补齐**：表格式层补上了数仓的 ACID / 一致性。
- **AI 需求**：ML 需要原始数据 + 多类型数据，湖仓天然适合。

**第六层：工业实践。**

- **Databricks** 是 Lakehouse 概念的提出者（Delta Lake）。
- **Netflix** 是 Iceberg 的最大生产用户。
- **Uber** 是 Hudi 主要贡献者。
- **阿里** 用 Paimon 做湖仓一体。
- **Snowflake** 从数仓向湖仓演进（Iceberg Tables）。

**3. 常见陷阱**

- **认为湖仓一体 = 数据湖 + 数仓** —— 本质是用表格式层统一。
- **认为数据湖是"升级版数仓"** —— 两者定位不同，湖仓一体是融合。
- **忽视表格式层的作用** —— 它是湖仓一体的核心。

**4. 追问预测**

- **「湖仓一体能替代传统数仓吗？」** 答：对新建场景可以；存量专有数仓迁移成本高，需评估。
- **「三种表格式怎么选？」** 答：Iceberg（跨引擎 / 读多）、Hudi（CDC / upsert）、Delta（Databricks 生态）。
