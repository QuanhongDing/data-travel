## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把 Hype Cycle / Tech Radar / Three Horizons / Wardley / OKR 放在同一张 1–5 分的表里，比「战略高度 / 落地性 / 沟通性 / 投资组合 / 适用规模 / AI 友好度」六个维度。这个做法有两个结构性错误。

**错误一：这五件不是同一层的产出。** Hype Cycle 的产出是一张期望曲线——它改变的是**你怎么看**；Three Horizons 的产出是一组资源比例——它改变的是**钱怎么分**；OKR 的产出是一组能被追问的结果——它改变的是**你必须做成什么**。给它们打分，等价于给「温度计 / 空调 / 手术」打分：它们不是备选项，是不同层的动作，且必须串起来用。打分表给 Hype Cycle「战略高度 5 分」、给 OKR「落地性 5 分」，其实是在说两件不同的事，而打分表把它们伪装成同一把尺子上的两个刻度。

**错误二：同一维度的权重在不同规模下会反转。** 「沟通性」在 200 人的组织里权重很低（谁写谁讲，共识在会议桌边就形成了），在 20000 人的组织里权重接近全部（战略落不了地几乎总是因为没翻译成别人能复述的话）——这两个规模断言属组织行为的经验判断，没有单一可引的权威来源【经验】。打分表给 OKR 与 Tech Radar 都打了「沟通性 5 分」，隐含假设是一个「需要跨部门对齐」的组织；而在 8 人的初创团队里，正确答案是「什么都别写，白板上画一次就够」【经验】。

打分表输出的是**排名**，而技术战略要的是「**在我这些约束下，下一步产出哪份东西，为什么不是另一份**」。更具体地说，本章要回答三个可被验证的问题：**(1) 这个框架的输出会改变哪一项决定？(2) 它占用的产能在这个团队规模下值不值？(3) 它失效的条件是什么？** 一个不能回答「什么时候不该用它」的选型建议，本质上还是打分表。

**本章采用的 6 条判据**（每条针对技术战略主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 输出层 | 它的产出改变的是**认知**、**资源分配**、**行为承诺**还是**合规约束**（加速族不改这四层中的任何一层，只降低其他框架的产出成本） | 只有挂上预算、考核或审计的产出才会真正改变组织；认知层的产出再多，也不会自动变成一分投入 |
| 时间常数 | 它多久刷新一次？你要管的对象变化有多快 | 刷新慢于对象变化 → 文档从指南变成误导；刷新快于对象变化 → 两次刷新间没有新信息，刷新是纯损耗 |
| 可回答的问题域 | 它答的是「成熟了吗」「该投多少」「该自建吗」还是「做成了吗」 | 这四个问题在机制上没有交集；用错框架等于拿温度计量体重，量得再准也没用 |
| 约束力来源 | 谁必须遵守它的输出？不遵守的代价是什么 | 没有代价的框架只能靠说服，而说服成本随组织规模上升而不是下降 |
| 产能占用 | 它每年吃掉多少人天？随团队规模怎么变 | 框架成本与人头挂钩、与预算无关，所以小团队里它反而更贵 |
| 失效条件 | 什么情况下它的输出会反向误导 | 一个不说「何时别信我」的框架，会在它失效的那一刻被当成权威 |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 业务对齐 | 认知：先确认投入能挂到哪个业务结果 | 用业务结果反推技术必要性，而不是用技术热度推业务必要性 | 需要向业务方要预算的团队 | 方法论 |
| Hype Cycle（Gartner） | 认知：判断技术的**期望位置** | 横轴时间、纵轴期望，5 阶段曲线（Innovation Trigger → Peak → Trough → Slope → Plateau） | 需要向管理层解释技术热度的组织 | 商业订阅 |
| Tech Radar（ThoughtWorks） | 承诺：判断**采纳动作** | Adopt / Trial / Assess / Hold 四环 + 固定周期刷新 | 有平台团队的工程组织 | 公开发布（官网免费阅读） |
| TRL（NASA） | 认知：判断**工程成熟度** | 1–9 级刻度，从概念验证到运行环境验证 | 航天、国防、硬件与基础设施 | 公开方法论 |
| Wardley Maps | 认知：判断**依赖方向 × 演化阶段** | 把能力放在「演化阶段 × 依赖方向」二维图上 | 需要决定自建 / 采购的组织 | 公开书籍与文章 |
| Three Horizons（McKinsey） | 分配：决定**钱分给谁** | 按回报时间把投入分成 H1 / H2 / H3 三层 | 有独立预算的企业 | 咨询方法论 |
| Core-Edge-Spot（Gartner） | 分配：决定**谁投入多少** | 把技术能力分成核心 / 边缘 / 机会三类 | 大型企业 IT | 商业方法论 |
| Balanced Scorecard | 分配 + 度量：四视角平衡 | 财务 / 客户 / 内部流程 / 学习成长四个视角同时设指标 | 传统大型企业 | 公开方法论 |
| 路线图（Roadmap） | 分配 + 时间：决定**什么时候做** | 里程碑 + 阶段产出 + 依赖排序 | 全部 | 无许可 |
| OKR | 承诺：决定**必须做成什么** | 公开目标 + 可量化关键结果 + 周期复盘 | 互联网与平台组织 | 公开方法论 |
| Build-Buy-Partner | 承诺：决定**谁来做** | 三选项 + 判据（差异化 / 成本 / 速度） | 全部 | 方法论 |
| AI Strategy Canvas | 认知：AI 能力缺口清单 | 画布式结构化提问，把缺口暴露在纸面上 | 要做 AI 战略的组织 | 方法论 |
| NIST AI RMF | 约束：AI 风险必须被治理 | Govern / Map / Measure / Manage 四功能 + 风险分级 | 受监管行业、AI 平台团队 | 公开（NIST 1.0，2023） |
| AI 战略 Copilot（AI 辅助） | 加速：降低产出成本 | LLM 汇总公开信息 + 生成结构化草稿 | 已在用 AI 工具的团队 | 商业 / 自建 |
| 结构化竞争分析（SWOT / Porter's Five Forces） | 认知：外部态势输入 | 结构化提问清单，强制覆盖容易被忽略的维度 | 全部 | 公开方法论 |

这 15 项其实分**五族**：**认知族**（业务对齐、Hype Cycle、TRL、Wardley、结构化竞争分析、AI Strategy Canvas）、**分配族**（Three Horizons、Core-Edge-Spot、Balanced Scorecard、路线图）、**承诺族**（Tech Radar、OKR、Build-Buy-Partner）、**约束族**（NIST AI RMF）、**加速族**（AI 战略 Copilot）。分族的依据是**产出挂在哪个环节**（7.1 的「输出层」判据），不是「看起来像不像」：AI Strategy Canvas 的产出是一张能力缺口清单，它只进入讨论、不产生任何强制项，因此归认知族，归到约束族会让人误以为它像 RMF 一样有约束力；适用法规是**外部输入而不是可选的框架**，它由 RMF 落成控制项，所以约束族里可选的框架只有一个（RMF），「每族只留一个」这条原则在约束族里就落在它身上。

**先分族再选，能省掉一半比较**：你不需要比较 Hype Cycle 和 OKR——它们不是一个位置上的两个候选人。真正需要比较的只有同族内部：「认知族里我用 Hype Cycle 还是 Wardley」，取决于我要回答的是**期望问题**还是**依赖问题**。决策树把「业务驱动 → 业务对齐」「需要可视化 → Wardley」「AI 战略 → Canvas + RMF」并列成互斥分支，其实这三条可以同时成立且不冲突：前两条是认知族内部两个不同问题（期望 vs 依赖），第三条里的 Canvas 也在认知族、RMF 在约束族，三者并不争抢同一份产出。

下表只列机制，不列「某框架是否适用于你的行业」这类静态断言——框架的适用性取决于你的组织约束，不属于可外部检索的事实。凡涉及具体方法的能力边界，请用下面三种判定方法自行核验：

- **它的输出是否被引用过**：找出最近一年该框架的输出物（雷达页、路线图、OKR 文档），看是否有一项决定能追溯到它。
- **它的判据是否可判定**：把它的每一条判据代进你自己的一个真实决策，看能否得出明确结论；得不出结论的判据是形容词，不是判据。
- **它的刷新是否真的发生**：看最新一期与上一期的差异条目。没有差异，说明这个框架在你的组织里已经变成仪式。

### 7.3 机制差异：为什么它们表现不同（核心节）

五族之间的表现差异可以完整归因到四个机制维度。选这四个，是因为它们分别对应选型时必须先回答的四个问题：**输出落在哪一层（7.3.1）· 刷新周期与对象周期是否同阶（7.3.2）· 维度数够不够回答你要问的问题（7.3.3）· 度量会不会被组织反向优化（7.3.4）**。每个维度给出「机制 → 因果 → 公开证据 → 失效条件 → 自验方法」。

#### 7.3.1 输出层：认知 / 分配 / 承诺 / 约束 —— 为什么「更准的框架」不一定更有用

**机制是什么**：每个框架的输出物会落到组织的一个具体环节上；落在哪个环节，决定了它能否改变资源与行为。认知层的输出只进入讨论，分配层的输出进入预算，承诺层的输出进入复盘与考核，约束层的输出进入合规审计。

**各候选的实现差异**：

| 候选 | 输出物 | 挂在哪个环节 | 不遵守的代价 |
| --- | --- | --- | --- |
| Hype Cycle / Wardley / TRL | 一张图或一个刻度 | 汇报材料、讨论会 | 无 |
| Three Horizons / Core-Edge-Spot | 一组资源比例 | 预算文档 | 预算被砍或拿不到 |
| 路线图 | 一份带时间的技术计划 | 项目排期与立项 | 排期被追问 |
| OKR | 一组可验证的结果 | 周期复盘 / 述职 | 复盘时被逐条追问 |
| Tech Radar | 四环标签 | 技术选型提案的默认答案 | 提案要额外举证 |
| NIST AI RMF / 适用法规 | 必须实现的控制项 | 合规审计 | 审计与法律后果 |

**由此必然导出的性质**：**因为** Hype Cycle 的输出没有挂任何代价，**所以**它的准确性提高一分，也不会自动带来一分投入——它改变的是「讨论的起点」，不是「资源的去向」；**反过来**，**因为** Three Horizons 输出的是一个可以直接写进预算文档的数（资源比例），**所以**它天然会改变分配，即使它的分析远比 Hype Cycle 粗糙。这就解释了一个反复出现的现场现象：**组织里被引用最多的框架，往往不是最准的那个，而是产出最容易被塞进某个流程的那个**。也因此，把认知族框架的结论直接当立项理由（「曲线正在上升」）必然失败——它缺的不是论据，是**挂点**。

**公开证据**：OKR 这套「公开目标 + 可验证关键结果」的机制来自 Intel 的目标管理实践，由 John Doerr 于 1999 年引入 Google 并在《Measure What Matters》（2018）中系统公开【公开，John Doerr 2018】；其公开设计规范里明确把 OKR 与绩效评估**分开**，正是因为它要进入的是复盘环节而不是薪酬环节。NIST AI RMF 1.0 于 2023 年发布，以 Govern / Map / Measure / Manage 四个功能组织风险管理【公开，NIST AI RMF 1.0，2023】；欧盟《人工智能法案》（Regulation (EU) 2024/1689）以不可接受 / 高 / 有限 / 极小四档风险分级对应不同义务【公开，2024 年生效】。这两者的输出之所以能被组织执行，是因为它们挂在**审计**上，而不是挂在「建议」上。

**失效条件**：当执行者手里没有分配权时（只能执行不能规划），分配族框架的输出会被架空成一份「没人看的附件」；当约束族框架与业务目标冲突且无人执法时，它退化为一份文档——**合规文档不是约束，审计才有约束**。

**自验方法**：找出该框架最近一次输出，用一句话回答「这个输出改变了哪一项具体决定（哪个立项被否、哪笔预算被调、哪个排期被改）」。如果答案只能写成「让大家对某项技术更有共识」，那它停留在认知层，不要指望它推动投入。

#### 7.3.2 时间常数匹配：刷新周期必须与被管理对象的变化周期同阶

**机制是什么**：每个框架有一个刷新周期，被管理的对象（技术采纳判断、战略方向、期望热度）各有一个变化周期。框架的有效窗口由两者中较短的那个决定。

**各候选的实现差异**：

| 候选 | 刷新周期 | 相匹配的被管理对象 | 错配的后果 |
| --- | --- | --- | --- |
| Tech Radar | 半年一期【公开，ThoughtWorks 自 2010 年起每半年发布一期】 | 技术采纳判断 | 写进 3 年路线图 → 一期未过就过期 |
| Hype Cycle | 年度更新【公开，Gartner Hype Cycle 系列报告 2024 年版】 | 技术期望位置 | 用它跟踪季度级的技术变化 → 永远滞后 |
| 路线图 | 年度主题 + 季度里程碑 | 战略方向与预算周期 | 做到月度粒度 → 每月重写，无人遵守 |
| Three Horizons | 年度（跟随预算） | 资源配比 | 按季度重分层 → 分层失去意义 |
| OKR | 季度（常见实践【经验】） | 团队交付节奏 | 年度 OKR → 中途无法纠偏；周度 OKR → 变成任务清单 |

**由此必然导出的性质**：**因为**框架的价值等于「刷新周期内的信息有效窗口」，**所以**当刷新周期长于对象的变化周期时，窗口内发生的任何真实变化都会把文档从「指南」变成「误导」，而且**误导比没有更危险**——过期的路线图会让人以为已经决策过了，从而跳过重新判断；**反之**，当刷新周期短于对象变化周期时，两次刷新之间没有新信息，刷新成本是纯损耗，且高频刷新会训练出「随便填」的习惯，让这个框架更快失效。这解释了一条反直觉的实践：**Tech Radar 的「Hold 环」比「Adopt 环」更需要解释**——每一次环位变动都是一个新的判断，而判断的密度必须与对象的变化密度匹配，否则环位会被当成永久标签。

**公开证据**：ThoughtWorks Technology Radar 自 2010 年起每半年发布一期，官网提供 2010 年至今的历年各期索引【公开，ThoughtWorks Technology Radar 2010 年至今历年各期】，这个周期本身是设计决策：短于半年的采纳变化由「Assess / Trial 环内新出现的条目」承接，长于半年的方向问题交给路线图。Gartner 的 Hype Cycle 为年度更新，每年按技术领域出多个分册【公开，Gartner Hype Cycle 系列报告 2024 年版】，其公开定位是给出**跨技术的相对期望位置**，而不是给出采纳时点——这一点读者可自行核验：在任一期的曲线上，用「当前采纳率」排序与用「期望值」排序会得到不同的顺序。

**失效条件**：当组织的变化速度被治理流程锁死（年度规划一旦批准就无法调整），再快的框架也不会加快决策——**此时瓶颈在审批流程，不在框架**，换框架是白花钱。

**自验方法**：取该框架最近两期输出，统计「发生变化的条目占比」。接近 0 → 刷新太快或没人认真填；出现「上一期标 Hold、这一期标 Adopt」却没有任何原因说明 → 刷新太慢，环位已经跟不上技术变化。

#### 7.3.3 维度数决定可回答的问题：为什么 Hype Cycle 永远答不了「要不要自研」

**机制是什么**：一个框架能回答的问题上限，由它的坐标轴数量与轴的定义决定。加一个维度不是「更全面」，而是**打开一个新问题域**。

**各候选的实现差异**：

| 候选 | 维度 | 能回答 | 机制上答不了 |
| --- | --- | --- | --- |
| Hype Cycle | 一维（时间 → 期望值） | 这项技术现在热度如何 | 采纳率、依赖关系 |
| TRL | 一维（工程成熟度 1–9） | 能不能进运行环境 | 生态与人才供给 |
| Tech Radar | 一维（采纳动作四环） | 该试还是该停 | 该投多少资源 |
| Wardley Maps | 二维（演化阶段 × 依赖方向） | 该自建还是该买、改这里会牵动谁 | 该投多少钱（需叠加预算） |
| Three Horizons | 一维（回报时间三层） | 钱分给谁 | 某项技术到底成不成熟 |
| OKR | 一维（结果承诺） | 做成了没有 | 做法对不对 |

**由此必然导出的性质**：**因为** Hype Cycle 的纵轴是**期望值**而不是**采纳率**，**所以**它必然在 Trough（低谷）区给出与真实采纳方向相反的信号——一项技术的期望崩塌，与它正在成为默认选择，是两件同时可能发生的事；采纳率服从另一条曲线（Rogers 的扩散曲线，1962），而高峰与低谷是期望的产物。这就是「低谷区恰好是采购窗口」这一悖论的机制来源，而不是民间经验。**又因为**自建 / 采购的判据需要**依赖方向**与**演化阶段**两个维度同时在场，**所以** Hype Cycle（只有期望这一个维度）在原理上无法替代 Wardley：你得先知道这个能力处在商品化阶段、且被多个差异化能力依赖，才能推出「必须采购」；只有期望值的信息，推不出这一步。

**公开证据**：Everett Rogers 的扩散曲线给出采纳率随时间的分布形状（《Diffusion of Innovations》1962）【公开，1962】；Geoffrey Moore 指出早期采用者与早期大众之间存在鸿沟（《Crossing the Chasm》1991）【公开，1991】——这两条与 Hype Cycle 的「低谷」常被混为一谈，但它们描述的是**采纳率**这一不同变量。Wardley 的演化轴四阶段（Genesis / Custom-built / Product / Commodity）由其作者在公开文章与《Wardley Maps》（2016）中系统化【公开，2016】。NASA 的 TRL 1–9 是又一条独立的成熟度刻度，面向「能不能在运行环境验证」，与采纳率也不是同一个量【公开，NASA 技术成熟度白皮书，1995】——**TRL 高不蕴含采纳率高**，科研与国防项目里「TRL 9 但生态极小」的情况很常见【经验】。

**失效条件**：当自建 / 采购决策不在你手里（例如全部基础设施由集团或云厂商统一提供）时，Wardley 的边际价值大幅下降；当技术选择不构成差异化（所有同行用同一套商品化组件）时，二维图退化成一维清单，此时用清单更省事。

**自验方法**：拿你现在用来做决策的那张框架输出，试着在上面回答一个**另一个问题**（例如拿 Hype Cycle 回答「这个组件该买还是自研」）。如果答案必须靠框架以外的信息补齐，说明这个问题超出了该框架的维度——此时加判断力没有用，要换工具。

#### 7.3.4 度量即行为：战略度量会被组织反向优化

**机制是什么**：一旦某个量进入考核或资源分配，组织就会向这个量优化。度量不只是描述，它是激励。这条机制在本主题里比其他维度更重要，因为技术战略的落地几乎完全靠度量驱动（见 [§6 落地实践](05-tech-strategy-section-6-sec6.md) 的阿里与 Netflix 案例）。

**各候选的实现差异**：

| 度量 | 团队最容易做到的最优化动作 | 与战略目标的关系 |
| --- | --- | --- |
| 中台吞吐量 / 接需求数 | 多接需求、少做抽象 | **相反**：规模上去了，复用率没动 |
| 复用率 / 口径一致性 | 推动别人用你的标准件、修口径 | 一致 |
| 技术雷达「纳入条目数」 | 每条技术都给出环位 | 无关：产出量不等于决策量 |
| OKR 关键结果（若挂考核） | 把关键结果写得保守可达 | **相反**：目标从牵引变成承诺 |
| 单位成本 / 每 token 成本 | 压缩单位消耗、批处理、降冗余 | 一致（但需同时看可用性） |

**由此必然导出的性质**：**因为**「中台吞吐量」这类指标可以靠**多接需求**直接拉高，**所以**当中台团队的 KPI 定在吞吐量上时，他们的最优策略必然是接需求而不是提复用，这与战略目标（能力复用）方向正好相反——**度量选错不是执行偏差，是理性响应**；**并且因为**这种响应是理性的，**所以**靠「加强宣贯」「开会强调复用」无法纠正它，只能改度量。这正是 [§6](05-tech-strategy-section-6-sec6.md) 阿里案例里「KPI 从吞吐量改为复用率与一致性」那一步的机制解释【公开，阿里 OneData 公开材料 2016–2024】。同一机制在 Netflix 的自建判据上也成立（见 [§6 落地实践](05-tech-strategy-section-6-sec6.md) 的 Netflix 案例）：把「是否直接决定用户为什么选 Netflix」作为唯一判据，等于给自建行为设了一个**无法靠堆工作量满足**的门槛【公开，Netflix Tech Blog 2014–2024】。

**公开证据**：「当一个度量成为目标，它就不再是一个好的度量」这一命题常被归于 Goodhart，其广为流传的措辞出自 Marilyn Strathern 1997 年对该命题的转述【公开，Strathern 1997】。OKR 的公开规范刻意区分「目标」（定性、有野心）与「关键结果」（定量、可验证），并把 OKR 与绩效评估解耦【公开，John Doerr 2018】——其设计动机与上述机制一致：**降低「把度量直接当考核」带来的扭曲**。

**失效条件**：当组织小到所有人都能看到最终结果时（约 10 人以下，此阈值与 7.4 的规模交叉点同源【经验】），度量的扭曲空间很小，此时建立度量体系的成本高于它的收益；当业务处于剧烈探索期、还没有稳定的成果指标时，任何被写下来的度量都会锁定一个错误方向——此时应该退回到认知族框架（重做判断），而不是加强度量。

**自验方法**：对每一条战略度量问一句：「如果团队只做这个指标的最优化，最省力的动作是什么？」若那个动作不是你希望看到的行为，这条度量会被反向优化。把这个问题写成度量上线前的必填项，比事后纠偏便宜得多。

### 7.4 成本结构对比（不是价格表，是成本函数）

这些候选的成本**随什么变量增长**：

```
框架总成本 ≈ 一次性引入（培训 + 模板 + 首个案例）
           + f(刷新频率 × 参与人数)      ← 参与项随人头线性，维护项近似常数
           + g(作用域重叠的框架对数)      ← 超线性，冲突时要仲裁
           + 隐性成本（汇报仪式化、术语分裂）
```

**主导项与隐性成本**：

| 候选族 | 主导项 | 隐性成本 |
| --- | --- | --- |
| 认知族 | 一次性绘制 / 解读的人力 | 图的维护成本随能力数量增长；**一张过期的图比不画更危险**，因为它给出错误的信心 |
| 分配族 | 年度分层的讨论与预算流程 | H3 在预算博弈中永远先被砍（H1 的收益更确定）；分层因此退化为「H1 加 H2」 |
| 承诺族 | 周期复盘的全员时间 | 目标膨胀，或反向的保守倾向（取决于是否挂考核） |
| 约束族 | 控制项实现与举证 | **合规惰性**：把「已合规」当成「已安全」，停止继续找风险 |
| 加速族 | 工具与提示词维护 | 生成内容的**不可溯源断言**——一旦进了战略文档，追溯成本高于重写成本 |

**为什么把「隐性成本」单列**：显性成本（会议时间、订阅费、培训）在日程表和账单上可见，于是被高估；隐性成本（图的维护、冲突仲裁、合规惰性）不出现在任何预算行里，于是被系统性低估。两者的相对量级随组织规模反转——**因为**显性成本随人头近似线性增长（且含一条不随规模缩小的维护底线），**而**作用域重叠带来的仲裁成本随「重叠框架对数」增长（有 n 个作用域重叠的框架，就有 O(n²) 对潜在的结论冲突要调停），**所以**小团队里主导项是「全员参与的那几个半天加上那条缩不下去的维护底线」，大组织里主导项是「两个框架给出相反答案时谁来定」——后者是 O(n²)，前者是线性加常数，**两者是不同的增长模式**，这正是下面 7.5 第一条阈值（先消除重叠、再谈数量）的来源：同一族里只留一个，重叠对数归零，框架数量的上限才由 `f(刷新频率 × 参与人数)` 这一项单独决定。

**【推算】数量级示例**（推导链完整给出，参数可替换重算）：

- 参数：每人年有效产能 220 人天，团队人数记作 N【推算，假设】。单个主动框架的年成本由**两项、两种增长模式**构成，这一点后面 7.5 的所有阈值都依赖它：
  - **参与项** = 全员按季度复盘 0.5 天 × 4 次 = 2 人天/人 × N → **随人头线性增长**；
  - **维护项** = 2 人各 20 天 = 40 人天 → **与人头弱相关**，是一条缩不下去的底线。
  - 于是 `单框架年成本 ≈ 2N + 40（人天）`。
- N = 50：140 人天 ≈ 团队年产能 11 000 人天的 **1.3%**；3 个 ≈ 3.8%；4 个 ≈ 5.1%。
- N = 20：80 人天 ≈ 4 400 人天的 **1.8%**；3 个 ≈ 5.5%。
- N = 10：60 人天 ≈ 2 200 人天的 **2.7%**；2 个 ≈ 5.5%。以上均【推算】。
- 若把「框架开销 ≤ 团队产能 5%」设为自己能接受的上限【经验】，按上式反推得到**随规模下降的上限**：**50 人 ≤ 3 个**（5% 产能 550 人天 ÷ 140 = 3.9，第 4 个即 5.1% 越界）；**20 人 ≤ 2 个**（5% 产能 220 人天 = 1.0 人年，÷ 80 = 2.75，第 3 个即 5.5% 越界）；**10 人 ≤ 1 个**（5% 产能 110 人天 ÷ 60 = 1.8，第 2 个即 5.5% 越界）。**上限随团队变小而下降**，原因就在维护项那 40 人天不随规模缩小——这正是「小团队里框架反而更贵」的算术来源【推算】。
- 反向的对照：不建任何框架不是零成本，它的成本函数是「决策次数 × 每次重建判据的成本 + 跨人维护共享判据的成本」。后一项有两块：**人头**带来的共享上下文维护成本（需要维持的关系数随人头超线性增长，这也是团队会自然分裂的机制【经验】），以及**人员流动**带来的重对齐成本（每次新人加入，口头共识都要重新对齐一次，故流动率越高、交叉点越低）。框架侧是 `2N + 40`（线性 + 常数），共识侧是超线性，两条曲线必然相交：按上式参数，10 人处框架要 60 人天/年、20 人处要 80 人天/年，而共识成本在这两个规模之间追上并越过这两条水平线，因此交叉点落在 **10–20 人**，且随流动率整体上移或下移【经验】。

**不同处境下的主导项不同，所以优先级不是固定的**：

| 你的处境 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| < 10 人、单一目标 | 框架那条缩不下去的维护底线（40 人天）vs 口头共识成本 | 一个框架都不要，或只留一份最小路线图 |
| 10–50 人、有年度规划 | 参与项（线性项）+ 维护底线 | 按 `2N + 40` 反推上限（50 人 ≤ 3、20 人 ≤ 2、10 人 ≤ 1），且每族只留一个 |
| 需要决定自建 / 采购 | 二维图的一次性绘制与维护 | Wardley（认知族里唯一能答这个问题的） |
| AI 战略且有监管约束 | 约束族的控制项与举证成本 | 先满足约束底线（RMF / 适用法规），再谈战略增量 |
| 框架数已越过 5% 上界（50 人团队第 4 个即越界） | 冲突仲裁（超线性项） | 先退役一个**近一年没有改变过任何决定**的框架 |
| 战略文档产出太慢 | 撰写与汇总人力 | 加速族（AI Copilot 做草稿），但数字必须回到原始来源 |

### 7.5 决策树（每个分支都要有阈值依据）

```
这次要产出什么？（按输出层定位，而不是按「哪个框架更好」）
├─ 要产出「投入方向」——钱和人往哪走
│    → Three Horizons（分配层）+ 路线图（时间层）
│      · 只有一个团队、只有一份预算 → 省掉分层，路线图本身就是分配
│      · 分层时必须同时给 H3 一份独立预算，否则它会被 H1 吃掉
│      · 路线图的粒度：主题按年度复核、里程碑按季度落（见阈值依据 9）
├─ 要产出「某技术该不该做」
│    ├─ 判断成熟度 / 风险 → TRL（能否进运行环境）+ Hype Cycle（期望位置）
│    │    ⚠ 二者都不回答「采纳率」，不要用它们做采购时点决策
│    ├─ 判断自建还是采购 → Wardley Maps（依赖方向 × 演化阶段）
│    │    判据：处在 Product / Commodity 且被多个差异化能力依赖 → 采购
│    └─ 判断该不该试 → Tech Radar（Assess / Trial 环），且必须有退出条件
├─ 要产出「团队必须做成什么」
│    → OKR。且必须与绩效评估解耦，否则度量必被反向优化（7.3.4）
├─ 要产出「AI 战略」且存在监管约束
│    → AI Strategy Canvas（能力缺口）+ NIST AI RMF / 适用法规（约束层）
│      · 合规强制 ≠ 战略：先满足底线，再谈增量
│      · 每个风险项要绑一个可度量指标，否则退化成合规清单
├─ 只是要把产出做得更快
│    → AI 战略 Copilot（加速层）。产出必须有人署名复核
└─ 约束检查（先过这一关，不过就别往下走）
     ├─ 团队 < 10 人？ → 最多 1 个框架；别分层、别做雷达
     ├─ 主动框架已达 3 个？ → 第 4 个会越过 5% 产能上界，先合并或退役一个，再增加
     ├─ 同族里有两个框架？ → 先删掉一个（重叠必然产生结论冲突）
     └─ 你无法改变预算或考核？ → 分配族 / 承诺族都会被架空，先解决授权
```

**阈值依据**（与树上每个判断节点一一对应；树上只在「路线图的粒度」一处标了编号批注「见阈值依据 9」，其余节点按其在树中的位置对应到下列条目）：

1. **「同族里有两个框架 → 先删掉一个」（7.5 的第一条阈值）**：由 7.4 的成本函数推出——作用域重叠的框架数 n 带来 O(n²) 对潜在结论冲突，而这一项不出现在任何预算行里。同族内的两个框架**变量与判据相同**（例如 OKR 与 Tech Radar 都在问「该承诺什么」），因此它们的结论冲突率最高、仲裁价值最低。可自验：同族两个框架若从未给出过相反结论，说明其中一个的输出根本没人读【推算，见 7.4】。
2. **「主动框架 ≤ 3」（50 人团队）**：由 7.4 的产能推算给出，不是行业惯例——单个主动框架约 `2N + 40` 人天/年，N = 50 时约 140 人天，3 个约占团队年产能 3.8%，第 4 个 5.1% 即越过「≤ 5% 产能」的上界，故上限取 3。换团队规模必须重算，且**上限随团队变小而下降**（20 人 ≤ 2、10 人 ≤ 1）【推算】。
3. **「团队 < 10 人 → 最多 1 个框架」**：由口头共识与框架的成本交叉点推出。框架侧是 `2N + 40`（线性 + 一条不随规模缩小的维护底线），共识侧随人头超线性增长、并因人员流动而整体上移（每次新人加入都要重新对齐），两条曲线在 **10–20 人**相交。10 人处框架需 60 人天/年，而 5% 产能只有 110 人天，即只装得下 1 个；再往上加就重演「框架比共识更贵」【经验，交叉点随流动率移动】。
4. **「Hype Cycle 与 TRL 都不回答采纳率」**：由变量定义推出，不依赖任何来源——Hype Cycle 的纵轴是期望，TRL 是工程成熟度，采纳率是第三个独立变量（Rogers 1962【公开】）。三者高相关但可分离，「TRL 9 而采纳率极低」在科研与国防项目中常见【经验】。
5. **「处在 Product / Commodity 且被多个差异化能力依赖 → 采购」**：由 Wardley 演化轴的定义推出，不需要外部数据——进入 Product / Commodity 阶段说明市场上已有多个供应商，自建不再产生差异；「被多个差异化能力依赖」意味着自研失败会同时拖垮多条产品线。两个条件缺一不可：只满足前者只是「可以买」，只满足后者只是「必须可靠」【经验】。
6. **「Tech Radar 的 Assess / Trial 必须有退出条件」**：由 7.3.2 的时间常数推出——Radar 半年一期【公开，ThoughtWorks 自 2010 年起每半年发布一期】，而「试」这个动作若不写清退出条件，下一期会以「已试过」为由被默认沿用，环位就从判断退化成标签。可自验：翻出上一期标 Trial 的条目，看有几条写明了「什么结果就放弃」【经验】。
7. **「OKR 必须与绩效评估解耦」**：由 7.3.4 的机制推出（Strathern 1997【公开】）——度量一旦直接进入考核，被优化的是度量而不是目标。可自验：检查关键结果是否被写成「保守可达」的形态。
8. **「每个 AI 风险项要绑一个可度量指标」+「合规底线先于战略增量」**：由 7.3.4 的机制叠加约束族的特性推出——约束族的自然终点是「已合规」这个二元状态，二元状态一旦达成，跟踪就停止（合规惰性）；绑一个可度量指标，是把它从二元状态变成一条持续被观察的曲线。而底线先于增量，是因为约束族挂在审计上、分配族挂在预算上，两者是**不同的挂点**，审计通不过时预算讨论没有意义【经验】。
9. **「路线图用『年度主题 + 季度里程碑』」**：由 7.3.2 的时间常数匹配推出。路线图要管的对象是**战略方向**，它的有效窗口是年度（跟着预算周期走，即 7.3.2 表中路线图那一行）；里程碑要起检查点作用就得短于主题复核周期，但又不能短到月度——7.3.2 表已把「做到月度粒度 → 每月重写，无人遵守」列为路线图的错配后果，季度落在两者之间【经验】。**这条阈值的依据不是「技术采纳判断的窗口」**：技术采纳判断的有效窗口是**半年级**，与 Tech Radar 的刷新同阶（7.3.2 表把「半年一期」与「技术采纳判断」列为相匹配【公开，ThoughtWorks Technology Radar 自 2010 年起每半年发布一期】）；把某一期的环位写进超过半年的路线图条目，一期未过它就会过期。
10. **「H3 必须有独立预算」**：由分配博弈推出，不需要外部数据——H1 的收益确定性高于 H3，因此在同一预算池里排队时 H3 必输，与 H3 的技术价值无关。给 H3 一个不受 H1 竞争的池子，是唯一能绕过这个博弈的做法【经验】。
11. **「只有一个团队、只有一份预算 → 省掉分层」**：由 Three Horizons 的机制推出——分层的产出是「资源比例」，而比例要能改变行为，前提是有多个预算池可供分配；只有一个池子时，比例写在文档里也不会改变任何一笔钱的实际去向，反而多一层需要对齐的口径【经验】。
12. **「加速族产出必须有人署名复核」**：由证据纪律推出——LLM 生成的技术趋势汇总无法自带来源，而战略文档里每条断言都要能追溯到原始出处。署名把「谁核验过」变成一个可追责的对象，是阻止不可溯源断言进入下游决策的唯一机制【经验】。
13. **「你无法改变预算或考核 → 先解决授权」**：由 7.3.1 的输出层机制推出——分配族挂在预算上、承诺族挂在复盘与考核上，两者都要求执行者手上有相应的分配权或评估权。没有这个权限时，这两族框架的产出会退化成一份没人看的附件，此时增加框架数量不会改善结果【经验】。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 只有一个年度技术预算要分 | Three Horizons + 路线图 | 按团队申请分 | 按申请分：会系统性偏向 H1（保护已有系统），H3 永远拿不到钱 |
| 会上要统一「这个技术值不值得跟」 | Tech Radar（给动作） | Hype Cycle | 单用 Hype Cycle：只给期望位置，不给动作，会后仍然没有结论 |
| 要决定某组件自研还是买 | Wardley Maps | Build-Buy-Partner 清单 | 只用三选项清单：缺少依赖方向，会漏掉「买来的组件被谁依赖」 |
| 要向老板汇报技术价值 | 路线图 + OKR（挂业务指标） | Hype Cycle 图 | 只讲曲线：老板听到的是「这技术很热」，不是「业务获得了什么」 |
| AI 战略要落地且有监管 | AI Strategy Canvas + NIST AI RMF | 只做 Canvas | 只做 Canvas：能力缺口画得很全，但没有约束力，不改变任何预算 |
| 技术决策反复扯皮、没有判据 | Wardley + 结构化竞争分析 | 多开会 | 开会次数不产生判据，只产生疲劳；判据要从机制里来 |
| 战略文档产出太慢 | AI Copilot 做草稿 + 人核验 | 招人写 | 招聘周期以月计，且招到的人未必懂本组织的机制；AI 的瓶颈在核验不在生成 |

**常见组合与其运维代价**：

1. **Three Horizons（分配）+ 路线图（时间）+ OKR（承诺）**：三者分别回答「钱分给谁 / 什么时候做 / 做成了什么」。边界是 **OKR 不重复写路线图里程碑，路线图不写成 OKR 式结果**。运维代价：三个产出物每年要**对齐一次**，否则会出现「路线图上的项目不在任何 OKR 里」的分裂——这类分裂本身就是一个信号，说明分层与目标脱节了。
2. **Tech Radar（采纳动作）+ Wardley Maps（自建 / 采购）**：Radar 给「试不试」，Wardley 给「自己建还是买」。运维代价：Radar 的环位是**组织级**的，Wardley 的结论是**业务级**的——同一项技术在不同业务下可能一个该 Adopt 一个该 Hold（因为依赖结构不同）。组合使用时必须写清这两个层级，否则会被人当成矛盾，进而否掉整套方法。
3. **Hype Cycle（期望位置）+ Tech Radar（动作）**：机制上成立，因为二者变量不同（期望 vs 动作），不冲突。运维代价：Hype Cycle 是商业订阅内容，其曲线图通常不可对外转发，对外沟通只能引用结论不能引用图；而 Radar 是公开发布的，可自由引用。
4. **AI Strategy Canvas（认知族：能力缺口）+ NIST AI RMF（约束族：必须被治理的风险项）**：两者分属不同族，因此这个组合不违反「每族只留一个」——Canvas 产出「我们缺哪些能力」（进入讨论），RMF 产出「哪些风险必须被管住」（进入审计）。运维代价：约束族的成本结构是「文档 + 举证」，容易停在「已合规」而不是「已安全」；组合使用时必须为每个风险项绑一个可度量的技术指标（见阈值依据 8），否则它永远不会被验证。

**组合的共同原则**：**每族只留一个**（消除作用域重叠）→ **每个框架必须有一个「它的输出改变过某个决定」的实例**（没有实例的框架是仪式）→ **每年退役一个不再改变任何决定的框架**（框架套数会自然膨胀，退役机制是唯一的刹车）。**加速族（AI 战略 Copilot）可以叠在上面任何一个组合上**——用它对公开信息做汇总与草稿、人负责判断，它不与任何族争占位，但它带着本章最容易被违反的一条纪律：**LLM 生成的技术趋势汇总不能作为【公开】档证据**，它会把「某技术已成熟」「某公司已全面采用」这类没有出处的断言写得非常流畅，而一旦被追问来源，整份战略的可信度归零。一个有效组合的标志不是「产出物齐备」，而是「上一个季度里，有某个决定可以被指认是由哪份产出推动的」。

### 7.7 选错的代价与迁移成本

**反模式：用打分表代替判据** —— 症状：评审会上比较「A 4 分 vs B 3 分」，却没人能说出这 1 分的机制差异是什么 → 后果：结论随打分人更换而翻转；换一个场景（规模翻倍、或预算被砍）原结论立刻失效，而且**无法预判何时失效** → **正确做法**：为每个候选写出**失效条件**（本章 7.3 每个机制小节末尾都有），选型结论必须能回答「什么条件下我会换」。

**反模式：把认知族框架当分配工具** —— 症状：Hype Cycle 上处在 Slope 的技术「因为曲线向上」被立项 → 后果：立项没有对应预算池与路线图位置，下一轮预算评审被整体砍掉（因为它没绑任何业务结果） → **正确做法**：认知族的结论必须先翻译成「替代哪个现有投入」，才有资格进入分配。

**反模式：把战略度量直接当 KPI** —— 症状：OKR 的关键结果被当考核指标，团队开始写保守目标 → 后果：组织优化的是度量而不是目标（阿里中台把 KPI 定成吞吐量后，团队忙接需求、复用率不动，见 [§6](05-tech-strategy-section-6-sec6.md)） → **正确做法**：OKR 与绩效评估解耦，或改用无法靠堆量改善的度量（复用率、口径一致性）。

**反模式：同时维护 6 个框架** —— 症状：每个框架都有年度仪式，但没人说得出上个季度哪个决定由哪份产出改变 → 后果：框架开销达团队年产能 **7.6%**（50 人团队，按 7.4 的 `2N + 40` 计：140 人天/框架 × 6 ÷ 11 000 人天）【推算，见 7.4】，且两个框架给出相反结论时无人仲裁 → **正确做法**：每族只留一个，每年退役一个。

**反模式：用 AI 生成的技术趋势汇总做证据** —— 症状：战略文档里出现「某技术已成熟」「某公司已全面采用」这类无出处断言 → 后果：被追问来源时整份战略的可信度归零，并且错误断言会被下游决策继承 → **正确做法**：AI 只做汇总与草稿，所有数字回到原始来源并标注年份。

**反模式的代价量级**（沿用 7.4 的参数估，不引入外部系数）：

| 反模式 | 代价的量级 | 推导依据 |
| --- | --- | --- |
| 用打分表代替判据 | 一次误判换一次返工；结论不可迁移到下一个场景 | 结论依赖打分数值，而数值无机制支撑 → 换场景需重打分【经验】 |
| 认知族当分配工具 | 立项在下一轮预算评审被整体砍掉，前 1–2 个季度的人力沉没 | 无预算池、无结果绑定的立项在分配博弈中优先级最低【经验】 |
| 度量直接当 KPI | 战略目标被系统性反向优化（越努力越偏） | 度量可被堆量动作直接拉高，这是理性响应（7.3.4）【推算，机制推导】 |
| 维护 6 个框架 | 约团队年产能 7.6% 的开销（50 人团队），冲突仲裁另计 | 140 人天/框架 × 6 ÷ 11 000 人天，即 7.4 的 `2N + 40` 取 N = 50【推算，见 7.4】 |
| AI 汇总当证据 | 一次来源追问即可让整份战略失去可信度 | 不可溯源断言无法被核验，且会污染依赖它的下游判断【经验】 |

**换成另一条路线要动什么**：

| 迁移方向 | 历史数据迁移 | 产出与口径改写 | 流程重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 从「无框架」转向「路线图 + OKR」 | 无 | 有（目标与里程碑从零写） | 季度复盘节奏 | 关键结果设计、里程碑拆解 | 1–2 人月 |
| 从「堆 KPI」转向「OKR 与绩效解耦」 | 无 | 大（考核口径与激励要一起改） | 述职与评估流程 | 关键结果设计、复盘方法 | 3–6 人月 |
| 从「按 Hype Cycle 选型」转向「Tech Radar 动作」 | 无 | 中（选型提案格式） | 半年度雷达评审 | 四环判据、提案写法、退出条件 | 1–2 人月 |
| 从「三选项清单」转向「Wardley 图」 | 无 | 中（能力清单要重画成图） | 图与路线图的同步节奏 | 演化阶段判据、读依赖箭头 | 2–4 人月 |
| 从「只做合规文档」转向「RMF 风险分级 + 度量」 | 部分（历史风险项要重分级） | 中（控制项与指标绑定） | 风险项跟踪与定期复核 | NIST 四功能的落地方式 | 3–6 人月 |
| 从「人工写战略」转向「AI 草稿 + 人核验」 | 无 | 中（提示词与核验清单） | 核验责任与署名 | 溯源纪律、事实核查 | 1–2 人月 |

> 量级按「一个熟悉业务、3–5 人的小组」估算【经验】；其中「从堆 KPI 转向 OKR 解耦」之所以量级最高，是因为它动的是**激励**——激励是最难改、也最容易反弹的东西。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| < 10 人、目标单一 | 一份最小路线图即可 | 框架成本含一条不随规模缩小的维护底线（`2N + 40`，10 人处仍要 60 人天/年【推算，见 7.4】），小团队分摊不掉它，而口头共识在这个规模上更便宜 |
| 要分钱 | Three Horizons + 路线图，且给 H3 独立预算 | 分配族是唯一挂预算的产出；同一池子里 H3 必输 |
| 要判断技术该不该做 | 先分清问的是「期望 / 成熟度」还是「自建采购」 | 维度数决定能回答的问题，一维答不了二维问题 |
| 要决定自建还是买 | Wardley Maps（依赖方向 × 演化阶段） | 商品化 + 被差异化能力依赖 → 采购，判据能从图上读出 |
| 要团队必须做成什么 | OKR，且与绩效评估解耦 | 度量进入考核必被反向优化（Goodhart / Strathern 1997） |
| 技术决策反复扯皮 | 先立判据与失效条件，再选框架 | 无判据的讨论只会重复消耗会议时间 |
| 有 AI 监管约束 | 先满足 RMF / 法规底线，再谈战略增量 | 约束族挂在审计上才有约束力；合规文档不是约束 |
| 框架数已超过 3 个（50 人团队第 4 个即越过 5% 上界） | 每族留一个 + 每年退役一个 | 溢出成本来自作用域重叠，重叠对数随 n² 增长 |
| 战略文档产出慢 | AI 做草稿，人做核验与署名 | 瓶颈在核验不在生成；不可溯源断言会污染决策 |
| 任何框架落地后 | 给它记一个「改变过的决定」 | 不能指认产出的框架，已经退化为仪式 |

> 本节小结：这些框架之间**唯一真正起决定作用的差异**不是「准不准」，而是**它的产出挂在哪一层**——认知层的产出只进入讨论，分配层的产出进入预算，承诺层的产出进入复盘，约束层的产出进入审计。同族框架可以互换（选一个即可），跨族框架不可互换（必须串联）。因此技术战略的选型顺序不是「哪个分数高」，而是：**先定位要产出什么（分配 / 承诺 / 约束 / 认知）→ 在该族里选一个 → 给它一个挂点（预算、复盘、审计，或至少一个被它改变的决定）**；没有挂点的框架，无论多准，都不会改变组织。
