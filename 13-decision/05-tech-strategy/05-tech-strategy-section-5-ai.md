## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

本主题的趋势清单有一个别的主题没有的困难：**它列出的东西大多不是技术**。

「AI 战略成为核心」「AI 战略 Copilot」「战略敏捷性」这类条目既没有版本号也没有接口，无法用「有没有 release note」来判断成熟度；它们更接近主张，而主张是没法「GA」的。

所以本节的第一步是先把口号换成可核验的判断。「每个公司都需要 AI 战略」这句话本身**不可证伪**——它在任何情况下都成立，因此没有信息量。

把它拆开，只剩一句可操作的话：**AI 相关的合规与治理要求已经变成硬约束，而硬约束必须进入技术战略**。这一句是有证据的（见 5.2.4）。其余部分属于修辞。

第二步是把「成熟度」做成可核验的判据。判据三条，全中才算 L1：

- **① 已 GA 且有正式发布文本**：标准、法规、release note 都算，发布会与博客不算。
- **② 有第三方（非厂商）的公开采用 / 审计记录**：厂商自述不算。
- **③ 接口稳定**：术语、条款、字段在多个版本间不变。

只满足 ①、或只有厂商自有案例的记 **L2**；只有路线图 / 论文 / 演示 / 预览的记 **L3**。动作口径固定：**按 L1 排路线图，按 L2 做 PoC，按 L3 只做记录、不在架构里预留假设。**

本主题的判据还要做一处替代，否则整节无法定级：**「第三方生产案例」在战略领域几乎不可能获得**——没有组织会公开自己的技术战略全文。

因此本节用「**是否有第三方审计或认证生态**」替代「是否有第三方生产案例」。理由是：战略类实践唯一能被外部核验的形态就是审计与认证；一个实践若既无法被审计、也没有外部标准引用它，它就不可验证，不能作为 L1。

本主题下**唯一处在 L1 的方向是「AI 治理战略的合规底座」**。

它够格的原因不是「AI 让战略变强了」，而是——AI 治理有正式标准文本（ISO/IEC 42001:2023，可认证）、有生效法规（EU AI Act，2024-08 生效），以及一个可以被查证的审计与认证生态。这三样共同构成「第三方可核验」。

其余方向分别停在 L2（基础模型战略、Agent 战略）与 L3（决策资产化、战略文档的 AI 化生产）：它们的机制都清楚，但**要么是接口未稳（模型抽象层、Agent 权限模型），要么是收益无法被外部核验（战略文档检索、Copilot）**。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| **① 基础模型战略**（Foundation Model 战略：选型 + 自研 / 采购 / 微调） | **L2** | 模型生命周期管理已有公开的供应商文档可依据，但**抽象层与路由层的接口语义未稳**（工具调用、结构化输出各家定义不同）；无公开可比的迁移成本口径 | 把「模型生命周期」写进路线图与 ADR，别只写「选用某模型」 |
| **② Agent 战略**（Agent 自主决策、AI-First Strategy 的落地形态） | **L2** | 平台能力可用，但验收标准与自主度分级没有第三方标准；§ 6 的 AI 投入案例用的是「场景分批 + 止损线」，不是 Agent 治理框架 | 先定义「自主度分级 + 审计留痕」两栏，再谈规模化 |
| **③ 决策资产化**（Decision Intelligence、战略 + 向量库 / RAG / KG / GraphRAG、战略图谱 Strategy Graph） | **L3** | 组件 GA，但「决策 / 战略知识库」没有第三方生产案例，也没有可审计的产出形态；本质是索引形态的改良 | 只做战略文档的检索（复盘时召回历史假设），不要建组织级战略图谱 |
| **④ AI 治理战略与战略文档的 AI 化生产**（AI 战略成为核心、AI Governance 战略、AI 宪法、AI Strategy Canvas、AI 战略 Copilot） | **L1**（仅治理底座） | 治理底座有正式标准与生效法规，且有可查证的认证 / 审计生态（ISO/IEC 42001:2023；EU AI Act 2024-08 生效）；Canvas / 宪法 / Copilot 三项无第三方核验路径，单列为 **L3** | 把治理底座按「管理体系」立项；Canvas 与 Copilot 只当写作工具，不写进战略方法 |

> 四个方向合起来覆盖了全部 27 个条目：AI 战略成为核心 / AI Strategy Canvas / AI Governance 战略 / AI-First Strategy / Decision Intelligence / AI 宪法（Constitutional AI）/ AI 战略 Copilot / Foundation Model 战略 / Agent 战略；战略 + RAG / 向量库 / KG / GraphRAG 四种结合；以及 Gartner / ThoughtWorks / NIST 等进展条目（见 5.4）与 7 条未来趋势（见 5.6）。
>
> 合并原则是**机制同源**：③的四项都是「换索引形态」，④的两半都是「把 AI 相关的承诺变成组织流程」。按机制归类而不是按热词归类，是为了让同一个方向里的东西有相同的成熟度理由。

### 5.2 演进方向逐条拆解（核心节）

每个方向都按同一套结构写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**，另加**判定方法**与**反方观点**两行。

结构之所以固定，是为了让「代价」无法被省略。只写机制与收益的方向，最后都会退回成趋势清单——**一个说不出代价的方向，不值得排进路线图**。

#### 5.2.1 ①基础模型战略：把「选型」变成「可替换性工程」（L2）

- **旧做法与它的卡点**：既有选型框架（TRL、Wardley Map、Core-Edge-Spot、Build-Buy-Partner）共享一个隐含假设——**技术一旦选定，迁移成本随时间单调上升，所以「选对了就锁定」是理性策略**。技术债、平台化、护城河这些概念都建立在「锁定是要付钱的一次性成本」之上。
- **旧做法的第二个卡点**：模型不满足这个假设。供应商会按自己发布的时间表**退役模型版本**，接口语义（工具调用、结构化输出、上下文长度处理）也会随版本变动。于是「锁定」不再只是成本问题，而是**可用性问题——被锁定的东西会自己消失**。
- **AI 改变了什么机制**：把「**一次性选型**」换成「**持续的可替换性工程**」——战略的产物从「选择结果」变成「替换能力」。
- **由此得到的**：因为存在「供应商主动下线」这个机制，所以**抽象层 + 可替换性测试 + 迁移演练**从「架构洁癖」升级为可用性要求；也正因为如此，「模型生命周期」这一栏必须进路线图，与「交付里程碑」并列。
- **由此付出的**：
  - **① 抽象层会磨平能力差异**：为了让替换可行，必须只用各家都支持的公共子集，能力上限被最弱的一层拉平；越强的模型特性越用不上。
  - **② 抽象层本身是新的技术债**：它有自己的 bug、自己的延迟、自己的版本兼容矩阵；把复杂度从「调用处」搬到了「中间层」，总量没有减少。
  - **③ 演练通过不等于迁移能过**：迁移演练跑的是「接口是否对得上」，而真实迁移的失败点通常在行为差异（同一提示词换模型后输出风格与拒绝边界都变），这部分无法靠接口测试覆盖。
- **判定方法**：判断一个团队有没有真的做基础模型战略，看它能不能回答三个问题——**当前用了哪些模型版本**、**它们各自的退役时间表**、**上次迁移演练是什么时候**。三个都答不出，说明战略仍停留在「选型」阶段。
- **反方观点**：也存在「**刻意不做抽象层**」的合理主张——在只用一个供应商、且场景对模型能力极度敏感时，抽象层带来的能力损失可能大于锁定风险。此时正确的做法是**把替换成本写进 ADR 的 Consequences 并显式接受**，而不是假装它不存在。
- **证据与来源**：主流模型供应商均发布模型生命周期 / 退役（deprecation）文档，这是可自行核验的事实【公开：查供应商文档中的 model lifecycle / deprecation 页】。**本节不引用任何具体模型版本号与退役日期**——这类信息变动频繁，引用即过期。
- **成熟度**：**L2**（判据：有公开文档可依据，但抽象层与路由层接口未统一，且没有公开可比的迁移成本口径）。

| 既有框架 | 它回答的问题 | 用在模型上缺什么 |
| --- | --- | --- |
| TRL 1–9 | 技术成熟到哪一步 | 分不清「模型能力成熟」与「这个模型版本还能用多久」 |
| Wardley Map | 自研还是采购 | 不区分「采购」与「采购 + 保留切走的能力」 |
| Core-Edge-Spot | 投入类别 | 没有生命周期维度，Spot 的退出成本被系统性低估 |
| Three Horizons | 资源如何分配 | H2 试点若依赖会退役的版本，试点结论会随时间过期 |
| Build-Buy-Partner | 三选项 | 缺第四选项：**Buy + Abstraction（采购，但保留替换能力）** |

#### 5.2.2 ②Agent 战略：交付物从「代码」变成「行为」（L2）

- **旧做法与它的卡点**：技术战略的验收单位是**交付物**——系统、项目、里程碑，每个单位都有一个明确的「完成」定义（功能验收、上线、SLO 达标）。路线图之所以能分期，靠的就是这个定义。
- **旧做法的第二个卡点**：Agent 的产出没有「完成」这个状态，只有「**在一定比例的场景下做对**」。于是路线图无法再用「上线 / 交付」来分期，而「AI-First」这类承诺也就无法转成可考核的 KR——这是它最常见的落地失败形态：口号写进了战略，却写不出季度目标。
- **AI 改变了什么机制**：把**验收单位从「交付物」换成「行为分布」**——战略必须回答的问题从「什么时候交付」变成「它能自主做到哪一步、做错了能不能查」。
- **由此得到的**：因为验收单位变了，所以技术战略必须新增两栏——**自主度分级**（Agent 被允许自主执行哪些动作，及每级的审批要求）与**审计留痕**（每个决策能否回溯到输入数据与依据）。这两栏不依赖任何外部标准，今天就能写进战略文档与架构评审清单。
- **由此付出的**：
  - **① 与既有技术债口径不兼容**：技术债的计量单位是代码与架构，而 Agent 的问题单位是行为（误答率、越权率、不可追溯率）；两本账不能相加，只能单列。
  - **② 组织能力缺口**：能写「行为验收标准」的人远少于能写「功能验收标准」的人，这类标准还依赖对业务边界的判断，不是技术团队能独立产出的。
  - **③ 自主度一旦开放就难以回收**：用户与业务方会在高自主度上建立流程依赖，之后降低自主度会变成一次业务变更，而不是一次配置调整——这使「先开权限再收紧」的策略代价极高。
- **判定方法**：判断一个 Agent 战略是否可执行，看它有没有写出**每级自主度对应的审批要求**，以及**一次错误决策的回溯路径**（从输出回到数据与依据）。写不出这两样，战略里就只有场景清单，没有控制面。
- **反方观点**：也有主张「**先放开、用事故倒逼治理**」的路径，在内部工具等低风险场景确实可行。但这条路径的适用条件必须写明：**动作可逆、影响面限于内部、有明确的回滚方式**；一旦涉及对外发送或资金动作，先放开就不再是一个可选项。
- **证据与来源**：本主题 § 6 的 AI 投入案例用的控制手段是「**场景分批 + 6 个月一评 + 三年止损线**」，而不是自主度分级【经验：数字取自本主题 § 6 的案例，该案例在 § 6 中标注为 `[案例 2021-2024]`，属书内案例叙述，**无外部可核验出处**，故不按【公开】档引用；如需外部核验，需另找公开材料】。这说明「用投入节奏控制 AI 风险」是当前有案例支撑的做法，「用自主度分级控制」尚无第三方案例支撑。
- **成熟度**：**L2**（判据：平台能力可用，但自主度分级与行为验收标准没有第三方标准可依，也没有可审计的产出形态）。

```text
Agent 战略的两个轴（都不能用「上线」来分期）
    自主度 ────────────────────────────────►
    只读查询 → 草稿生成 → 内部写入 → 对外发送 → 资金 / 删除动作
      │            │           │            │             │
      │            │           │            │             └─ 必须有确认点，且幂等
      │            │           │            └─ 必须有留痕与撤回方式
      │            │           └─ 必须权限最小集
      │            └─ 必须可人工改写后提交
      └─ 只需记录
    可审计性 ──────────────────────────────►
    无留痕 → 有日志 → 可回溯到输入数据 → 可回溯到依据与版本
判据：「先放开再收紧」的代价随组织流程依赖上升，
      所以自主度只能按轴逐级开放，不能按项目一次性开放。
```

#### 5.2.3 ③决策资产化：Decision Intelligence 与战略知识的检索化（L3）

- **旧做法与它的卡点**：战略讨论依赖「谁在场、谁记得」。上一轮战略的前提假设、当时的备选方案与放弃理由，散落在文档、表格与会议纪要里；三年后复盘时，能说清的只有结论，说不出结论依赖的假设。
- **旧做法的第二个卡点**：正因为依据不可召回，战略复盘很容易退化成「结果好就是决策对、结果差就是决策错」，而这恰好把运气当成了能力——这是战略无法积累经验的根本原因。
- **AI 改变了什么机制**：改变的是**索引形态**——把战略文档变成可检索语料，把战略 / 路线图 / 技术 / 团队建成可遍历的图（战略 + 向量库 / RAG / KG / GraphRAG 四种结合方式都在改这一件事）。
  需要说清楚的是：**这是接口改良，不是架构变化**。决策的责任归属、资源分配的权力、承诺与放弃的选择，一件都没有变。
- **由此得到的**：因为历史依据可被召回，所以战略复盘第一次可以对着「当年写的假设」逐条核对，而不是对着印象争论——这是本方向目前**唯一确定的收益**。
- **由此付出的**：
  - **① 召回的是「已写下的」内容**：战略失败的原因通常不在文档里，而在没人写下来的假设里；检索化会让人误以为「文档齐了就等于想清楚了」。
  - **② 战略文档是政治性文本**：向量化会把措辞的强度当成证据的强度，一段为汇报而写的乐观表述会在检索结果里与真实数据并列出现。
  - **③ 新的基础设施就有新的 Owner 问题**：战略知识库一旦成为复盘入口，谁来维护它、谁能看到全组织的战略假设，都会变成需要治理的问题（与被检索内容的敏感情形类似）。
- **判定方法**：判断一个「决策智能 / 战略图谱」方案是否值得投，看它有没有回答**「产出物是什么」**与**「谁用它做哪一个具体动作」**。答不出这两问，它就只能产出示意图——而示意图无法进入任何一个决策环节。
- **反方观点**：更便宜且有案例支撑的替代方案是**在 ADR 里把「备选方案 + 放弃理由 + 关键假设」写成强制字段**（本主题 § 1.3 已把 ADR 与战略的关系写明）。结构化记录解决的是同一个问题，成本远低于建图。
- **证据与来源**：Decision Intelligence 被 Gartner 列入顶级战略技术趋势（**Gartner 趋势清单，2022 年那一期**【公开，具体年份以 Gartner 当年原文为准】）。把这条趋势记成 2024/2025 年的新条目是本主题的常见混淆——**「Gartner 趋势」不是一条可以脱离年份引用的证据**。该方向**没有可核验的第三方生产案例**，因此判 L3。
- **成熟度**：**L3**（判据：组件 GA 但产出物与使用者都无法被外部核验；战略图谱与 GraphRAG 在此场景只有概念验证）。

| 结合方式 | 它改变什么 | 可核验的收益 | 级别 |
| --- | --- | --- | --- |
| 战略 + 向量库 | 战略文档可按语义检索 | 复盘时能找到当年的原话与口径 | L3 |
| 战略 + RAG | 评审时自动带出历史战略与类似案例 | 不同版本战略的表述一致性 | L3 |
| 战略 + KG | 战略 / 路线图 / 技术 / 团队建成关系图 | 无（无法被外部核验） | L3 |
| 战略 + GraphRAG | 跨域「战略推理」 | 无（结论数量大且无法排序） | L3 |

#### 5.2.4 ④AI 治理战略与战略文档的 AI 化生产（L1 底座 / L3 其余）

本方向内部有两半，成熟度不同，必须分开说——这正是 5.1 表格第 ④ 行判据列里那句「**Canvas / 宪法 / Copilot 三项无第三方核验路径，单列为 L3**」所指的分裂：同一个方向编号下，治理底座够 L1，其余三项只到 L3。

**先看治理底座这一半（L1）**

- **旧做法与它的卡点**：技术战略通常把合规放在「风险」章节用一句话带过（「确保符合相关法规」），因为传统合规的检查对象是**具体系统**，可以在项目验收时逐条核对。
- **AI 改变了什么机制**：治理对象从「某个系统是否合规」变成「**组织的流程是否持续合规**」——要求落在管理体系上，而不是落在一个交付物上。
- **由此得到的**：因为认证与审计的对象是流程，所以「做一次评估」不够，必须能证明**流程持续运行**（有记录、有责任人、有复评周期）。这与本主题 § 4 的 Step 8「执行跟踪」是同一个形状，因此可以复用既有的跟踪机制，不需要再造一套。
- **由此付出的**：
  - **① 管理成本是持续性的**：认证需要维持、标准版本会更新，它不像项目预算那样有终点。
  - **② 流程化会诱导「为审计而记录」**：当记录本身成为要求时，会出现与决策无关的文书；判定它是否变质的方法很直接——看这些记录有没有被用来改变过任何一个决定。
  - **③ 合规范围界定本身就是难点**：把哪些系统纳入治理范围，会直接改变成本量级，而这个界定往往需要法务与技术共同判断，不能由技术一方拍板。
- **判定方法**：判断 AI 治理战略是否真的立项，看三件事——**治理范围清单**（哪些系统在内）、**责任人**（具体到人）、**复评周期**。三样齐了才算管理体系；只有一份政策文件属于 L3。
- **证据与来源**：ISO/IEC 42001:2023（AI 管理体系要求，2023，可认证）【公开】；ISO/IEC 23894:2023（AI 风险管理指南，2023）【公开】；NIST AI RMF 1.0（NIST AI 100-1，2023-01）【公开】；EU AI Act（2024-08 生效，义务分阶段适用，**具体适用日期以官方时间表为准**）【公开】；中国《生成式人工智能服务管理暂行办法》（2023-08 施行）【公开】。
- **成熟度**：**L1**（判据：有正式标准文本 + 有可查证的认证与审计生态 + 条款与术语稳定）。

**再看战略文档的 AI 化生产这一半（L3）**

- **旧做法与它的卡点**：战略的产出是一份文档，而文档撰写确实耗人力——尤其是在把同一套战略翻译成对老板、对业务、对团队三种版本时。
- **AI 改变了什么机制**：只把「**写文档**」这一步自动化了。战略的输入（业务约束、资源上限）与输出（承诺与放弃）都没有变——**这是接口改良，不是架构变化**。
- **由此得到的**：因为翻译与排版成本下降，所以**同一份战略的不同版本之间更容易保持一致**（口径统一、术语统一），这是它唯一确定的收益。
- **由此付出的**：
  - **① 产出变多而决策没有变快**：文档生成变便宜后，组织容易用「更多战略文档」替代「更清楚的取舍」，反而增加了对齐成本。
  - **② 生成文本会掩盖假设的空缺**：一段通顺的战略文字会让人以为假设已经想清楚，而实际上模型只是把常识填了进去。
  - **③ 命名混淆带来的实际风险**：**Constitutional AI 是 Anthropic 于 2022 年公开的一种模型训练方法**（用一组书面原则让模型自我批评与修正），它**不是**组织治理制度【公开：Anthropic 2022 年公开的 Constitutional AI 论文】。
    把两者混为一谈会导致一个具体错误——以为写一份「AI 章程」就等于模型安全了。组织治理章程与模型训练方法是两件事，必须分别命名、分别审计。
- **判定方法**：判断战略 Copilot / Canvas 一类工具是否值得进流程，看它的输出**有没有改变过一次资源配置决定**。若只改变了文档的产出速度，它就是写作工具，不应写进战略方法章节。
- **反方观点**：对 Canvas 一类结构化模板，也存在「模板即价值」的合理主张——它强迫填写者显式回答原本会被跳过的问题（维度、权重、现状评分）。这个收益是真实的，但**它与是否用 AI 无关**；模板的价值来自填空题本身。
- **证据与来源**：AI Strategy Canvas 与战略 Copilot 类产品**没有可核验的第三方生产案例**，也没有外部标准引用它们，因此按 5.1 的替代判据只能记 **L3**。**StrategyGPT / BoardGPT** 一类名称属于此类应用的自称，没有产品级可核验证据——本节保留「战略文档的 AI 辅助生产」这个问题本身，不保留这些名称作为方向。
- **成熟度**：**L3**（判据：产出物无法被外部核验、无第三方审计接受路径；按 5.1 的动作口径（L3 只做记录、不在架构里预留假设），**这一半不做 PoC、不排路线图**，与 5.1 表格第 ④ 行「Canvas 与 Copilot 只当写作工具，不写进战略方法」一致）。

### 5.3 与本主题既有栈的接口在哪

这四个方向不该新建体系。它们必须挂在技术战略既有的五要素（**愿景 / 路线图 / 投资组合 / 雷达 / 沟通**）与既有的下游决策（ADR、选型、自研采购、技术债、架构评审）上。

下面只写**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 模型生命周期 → 路线图 | 路线图新增「模型 / 供应商生命周期」一列，退役时间是里程碑的一种 | 技术战略 Owner（规划口径） | 可做：供应商有公开的生命周期文档，见 5.2.1 |
| 模型可替换性 → ADR（§ 01） | ADR 的 Consequences 必须写明「替换成本」与「上一次演练时间」 | 决策人 | 可做：纯字段要求，不改流程 |
| Agent 自主度 → 技术雷达（§ 3.1 模式 2） | 雷达新增第 5 环「自主度分级」，与 Adopt / Trial / Assess / Hold 平行 | 平台团队 | 可试点：环的定义需先统一，否则各团队各说一套 |
| Agent 行为 → 技术债（§ 06） | 技术债预算单列「行为质量债」，单位是行为验收项，不与代码债相加 | 技术债 Owner | 需改造：计量单位与既有债池不兼容 |
| AI 治理范围 → 架构评审（§ 07） | 评审清单增加一栏「本系统是否落在治理范围内」，超范围需法务会签 | 评审主持人 | 可做：标准与法规范围界定清楚，缺的是范围清单 |
| 治理底座 → 投资组合（§ 2.2） | 在 H1 中单列「合规底座」，**不与其他 H1 项目竞争同一预算池** | 技术战略 Owner | 可做：与 § 6 的「两本账分开审批」同一机制 |
| 战略文档 → 检索 | 战略与复盘文档进入检索语料，召回结果只作复盘输入 | 战略 Owner | 可做：不改任何决策流程 |
| 可判定约束 → 策略即代码 | 只有**可判定**的约束（如「新服务必须落在指定区域」）写成策略并在 CI 校验 | 平台团队 | 可试点：OPA 类工具已长期可用，但多数战略约束不可判定 |
| AI 战略 KR → OKR（§ 2.3） | KR 必须落在可度量项上；「AI 优先」这类不可度量表述不得作为 KR | 战略 Owner | 明确：这是准入条件，不是建议 |
| 治理底座 → § 6 的「场景分批 + 止损线」 | 治理底座**不设止损线**（它是维持性成本），与场景投入的止损机制分开 | 技术战略 Owner | 明确：把合规放进场景止损池，会导致试点受挫时治理一起被砍 |

四条边界规则，写在这里以免含混：

- **预算分层优先于方法论**：§ 6 的 AI 投入案例已经把机制写清楚了——**基础设施按「能力卡位」审批，场景按 ROI 考核，两本账分开**。
  这一条的优先级高于任何 AI 战略框架：框架解决的是「怎么写」，两本账解决的是「钱从哪来」。
- **失败归属不变**：AI 战略失误的归属仍是**做出该承诺的人**，不是模型供应商；战略的载体是承诺与放弃，这两件事无法外包。
- **不与既有要素并行**：AI 战略不另建一套战略文档。
  若愿景、路线图、投资组合、雷达各自出现一份「AI 版」，就会出现两套口径；正确做法是在既有五要素里各加一栏，而不是加五份文件。
- **不可核验的产出不进战略**：任何无法被审计、也无法被外部标准引用的产出（战略图谱、Copilot 生成的战略稿）只能作为内部工作底稿。
  把它写进战略正文，等于把不可验证的东西放进了承诺。

**可自行核验的两个自查动作（不需要任何外部资料）**

- **两本账自查**：把当前预算表按 § 6 的「战略层 / 业务层」两栏重排一次，看基础设施投入是否正在被 ROI 标准否决。
  这是判断「有没有 AI 战略」最快的动作：如果基础设施与场景在同一张预算表里竞争，那么战略实际还没有立项。
- **战略产出自查**：把过去 12 个月的「战略产出」（文档、雷达、路线图、评审结论）列出来，逐条问「**它改变了哪一个资源配置决定**」。
  答不出的条目，无论技术多新、热度多高，都还没有进入战略——它们只是记录。

### 5.4 公开进展与文献

**标准、法规与官方文本（可直接引用，但必须带版本与年份）**

- **ISO/IEC 42001:2023**（AI 管理体系要求，2023，**可认证**）与 **ISO/IEC 23894:2023**（AI 风险管理指南，2023）。前者是本主题唯一「可被第三方审计」的锚点，也是把 AI 治理战略从口号变成立项的唯一路径。
- **NIST AI RMF 1.0**（NIST AI 100-1，2023-01 发布）与生成式 AI 专题文件（NIST AI 600-1，2024-07 发布）。**这两份不是同一年发布的**——把 1.0 记成「2024 正式版」是本主题最常见的引用错误。
- **EU AI Act**（2024-08 生效，义务分阶段适用）与中国《生成式人工智能服务管理暂行办法》（2023-08 施行）。**判定方法**：涉及具体条款适用日期一律查官方时间表，不引用二手总结——分阶段生效的法规，二手总结几乎必然会漏掉批次差异。

**成熟度对照物与市场研究（必须带年份引用）**

- **ThoughtWorks Technology Radar**：每半年一期、公开可查，四环为 Adopt / Trial / Assess / Hold（本主题 § 3.1 已列为方法之一）；**2024 年发布了第 28 期**（以 ThoughtWorks 站点当期公告为准）【公开】。它是本主题少见的「可以直接读到原文」的第三方成熟度证据——**判定方法就是去读当期原文，而不是读二手总结**。
- **Gartner 的两类产出**：① 顶级战略技术趋势清单（Decision Intelligence 出现在 **2022 年那一期**）【公开，以 Gartner 当年原文为准】；② 自 2023 年起另有生成式 AI 专题 Hype Cycle【公开，版本以 Gartner 文件为准】。
  这两类是**关注度**证据，不是**成熟度**证据——它们的用途是解释「为什么大家都在谈」，不能用来判断「现在能不能上生产」。
- **战略方法论部分（1980–2000 年代，属长期稳定项）**：Porter《Competitive Strategy》(1980)、Christensen《The Innovator's Dilemma》(1997)、McKinsey 的 Three Horizons（《The Alchemy of Growth》，1999）、Moore《Crossing the Chasm》(1991)、Wardley Map（Simon Wardley 提出）、NASA 的 TRL 1–9。
  列它们的用意是：**本主题的方法论骨架在 AI 之前就已经定型**，AI 时代新增的是「评估对象」，不是「战略方法」。

**论文与公开方法**

- **Constitutional AI**：Anthropic 于 2022 年公开的一种模型训练方法（用一组书面原则让模型自我批评与修正）【公开】。它属于模型训练，不属于组织治理——两者必须分开命名。
- **AI-First 类主张**：没有可核验的方法论文本，只有公司对外表述。本节因此只把它当作一种**投入姿态**（见 § 6 的案例），不当作可引用的战略方法。

**第三方生产案例：本主题的特殊缺口**

- 本主题 § 6 的四个案例（阿里数据中台 / Netflix 自建 vs 采买 / 字节流批路线切换 / 某大厂 AI 投入）中，**只有 1 个直接涉及 AI 方向**，而它的内容是投入节奏与组织安排（战略分层、场景分批、止损线、人才与算力双投入），**不是 AI 战略方法的验证**。
- 因此本节把除治理底座外的所有 AI 战略方向判为 L2/L3。这与 5.1 的替代判据一致：**拿不到生产案例时，就看有没有审计与认证生态。**
- 一个可检验的推论：如果两年后本主题出现了新的 L1 方向，它最可能来自**合规（治理底座）向上下游的扩展**（例如 AI 供应链与模型采购的审计要求），而不是来自「更好的战略工具」。

### 5.5 被过度宣传的部分

本节的标准是：一个说法如果**在公开材料里只有主张、没有失败条件**，就算被过度宣传。三条各写「实际是什么 → 为什么会这样 → 什么时候它才会成真」。

**「AI-First 战略：把 AI 作为公司的核心战略」**

- 实际是什么：能公开引用的「AI-First」只有公司对外表述；对多数组织，它无法转成可考核的季度 KR。
- 为什么会这样：它的成功标准不可度量——「AI 优先」既不是覆盖率也不是收入，任何结果都能被解释为「正在路上」。§ 6 的案例给出的可行替代是**两本账 + 场景分批 + 止损线**，那是投入纪律，不是「AI 优先」。
- 什么时候它才会成真：出现可度量的「AI 优先度」口径，例如「核心流程中有多少比例由模型参与且**可审计**」——注意「可审计」是必要条件，否则度量会被生成量灌水。

**「用 AI 宪法（Constitutional AI）约束 AI 战略」**

- 实际是什么：Constitutional AI 是 2022 年公开的**模型训练方法**，它约束的是模型的输出行为，不是组织的战略选择。
- 为什么会这样：两个不同的东西共用了「宪法」这个词。混淆的直接后果是**把「写一份章程」误当成「模型已经安全」**，从而跳过真正的控制手段（权限、幂等、评测）。
- 什么时候它才会成真：组织治理章程与模型训练方法被分别命名、分别审计；届时「AI 治理」会同时有制度记录与技术证据两条线，而现在是其中一条被当成了另一条。

**「战略 Copilot / StrategyGPT / BoardGPT：AI 辅助战略规划」**

- 实际是什么：改变的是战略文档的产出速度与一致性，**输入（业务约束、资源上限）与输出（承诺与放弃）都没有变**。
- 为什么会这样：战略的瓶颈从来不是写作，而是资源分配与取舍决策——这两件事需要承担后果的人拍板，无法委托。
- 什么时候它才会成真：当工具能对既有战略的假设做出**可追溯的反驳**（引用历史数据指出某个假设已被证伪），而不是生成一份新的通顺文本时，它才进入了决策环节。

### 5.6 未来 3–5 年：可证伪的预测

7 条趋势（AI-First Strategy / Decision Intelligence 平台化 / AI Constitutional Governance / 战略敏捷性 / AI 战略 Copilot / 战略图谱 Strategy Graph / 可持续性战略）全部保留，按「信号是否相同」合并为 4 条。

合并判据与前一节相同：同一条趋势的两半若会同时成真、也会同时被证伪，它们就是同一个预测。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| **AI 承诺进入组织制度并被外部审计**（原 AI-First Strategy + AI Constitutional Governance） | 出现由认可机构发布的公开 AI 治理认证名录；组织制度文件里出现**可审计**的 AI 承诺条款（有责任人、有复评周期） | AI 相关承诺只出现在对外传播材料与内部宣导中，不进制度与审计；「AI 宪法」停留在文档层面 |
| **决策依据成为可复用资产**（原 Decision Intelligence 平台化 + 战略图谱 Strategy Graph） | 出现跨组织的决策 / 战略数据模型或开放规范；战略复盘默认引用历史决策记录与当时的假设，而不是从零讨论 | 决策记录仍以文档归档、不复用；复盘仍以「谁的判断对」为主 |
| **战略刷新周期缩短到季度**（原战略敏捷性 + AI 战略 Copilot） | 出现以季度为单位公开更新战略的组织与案例；AI 辅助的战略复盘成为常规环节，且有公开的复盘模板 / 口径 | 战略仍按年度或三年期修订，调整以换词为主；Copilot 的产出从未改变过资源配置 |
| **可持续性成为技术约束而非报告项**（原可持续性战略） | 技术选型表出现能耗 / 碳排约束列；容量规划与能耗规划合并为同一份文档；数据中心能耗成为选型的一等输入 | 能耗与碳排只出现在 ESG 报告与财务口径中，不进技术选型与架构评审 |

四条预测的**共同证伪点**是同一件事：如果 AI 相关的战略产出始终无法被外部核验（既无认证也无审计），那么上面任何一条都不会成真。

这不是技术问题，是**核验标准**问题——这也是本节用「是否有审计与认证生态」替代「是否有第三方生产案例」的原因：**战略领域能被外部看到的，只有审计。**

**怎么用这张表**

- 每条预测都给了「会成真」与「会证伪」两列。**只有两列都能在公开材料里被观察到时，这条预测才有信息量**；否则它只是一句立场。
- 观察对象是「信号有没有出现」，不是「趋势对不对」。本节不含任何「哪种战略工具会胜出」的判断，只判断「哪些条件成立时它会进入制度」。
- 若三年后发现某条预测的证据方向相反，正确动作是**改判它的级别**（L2 与 L3 互换），而不是修改预测的措辞——改措辞等于把预测变成永远正确的句子，那正是本节要避免的东西。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 战略里写了「选用某大模型」 | 补一栏「模型 / 供应商生命周期」，含退役时间与上次迁移演练时间 | 抽象层与路由层的接口语义是否出现事实标准 | **不要**把「与某供应商深度绑定」当作战略优势写进路线图 |
| 被要求写「AI-First 战略」 | 先把它翻译成两本账：基础设施按能力卡位审批、场景按 ROI 考核 | 是否出现可度量且可审计的「AI 优先度」口径 | **不要**把不可度量的「AI 优先」写成 KR |
| 要给 Agent 定范围 | 先定自主度分级与每级的审批要求，再定场景清单 | Agent 权限模型与行为验收标准是否出现第三方标准 | **不要**一次性开放高自主度后再收紧（回收代价极高） |
| 要立项「决策智能 / 战略图谱」 | 先做最小版本：ADR 强制填写「备选方案 + 放弃理由 + 关键假设」 | 是否出现第三方公开的决策 / 战略数据模型 | **不要**建组织级战略图谱（L3，且无外部核验路径） |
| 被要求做 AI 治理合规 | 按 ISO/IEC 42001 立项管理体系；先出**治理范围清单 + 责任人 + 复评周期** | EU AI Act 与国内办法的适用细则出台情况 | **不要**用一份「AI 章程」替代控制手段（权限 / 幂等 / 评测） |
| 有人推荐用 Copilot 写战略 | 允许它做版本翻译与口径统一，设一人负责事实核对 | 工具输出是否开始改变资源配置决定 | **不要**把 Copilot 生成的口径直接写进对外承诺 |
| 路线图里排了 RAG / KG 相关的战略能力 | 先只在复盘环节做战略文档检索 | 检索结果是否真的被用于修正过假设 | **不要**把「战略 + GraphRAG」当作战略方法（那是索引改良） |

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是——**供应商可以按自己的时间表让某个能力消失**。既有战略方法（TRL、Wardley、Three Horizons、Build-Buy-Partner）都默认「选定即锁定、迁移成本随时间上升」，于是战略的产物可以是一次选择；这条机制把前提改成了「被选中的东西会自己消失」，于是战略的产物必须变成**可替换性**——抽象层、生命周期栏位、迁移演练，以及与 Agent 配套的自主度分级与审计留痕。
>
> 它**还没有改变**的是：战略的本质——资源分配与承诺和放弃。谁来做取舍、谁能承担后果，这是组织问题；AI 治理底座之所以是本主题唯一的 L1，恰恰因为它有外部标准与审计生态，而不是因为它更聪明。
>
> 因此把任何 AI 战略方向写进路线图之前，先过 5.1 的判据：**有正式文本吗、有第三方核验路径吗、接口稳定吗**。三问过不了，它就只是修辞。
>
> 💡 **思考锚点**：拿你路线图里正在押的一个 AI 方向，过一遍 5.1 的三问（有正式文本吗、有第三方核验路径吗、接口稳定吗）。再补本节真正的那条机制：如果明天供应商按自己的时间表下线这个能力，你写下的「可替换性」——抽象层、生命周期栏位、迁移演练——里哪一项是纸面的、哪一项真的演练过？没演练过的那项第一次触发时，你付的是迁移成本还是停机？
