## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

「战略规划用 Hype Cycle + Three Horizons，团队选型用 Tech Radar」——这张对应表把一个更硬的问题遮住了：**你的规划周期与考核周期是否一致**，以及**你的判断依据来自内部证据还是外部信号**。规划周期长于考核周期（例如三年战略、季度考核），H3 类投入就必然被季度压力吃掉，此时换任何画布都无效；判断依据来自外部信号（友商动作、媒体热度），再精细的坐标轴也只是把跟风包装成方法论。这两条约束不解决，工具之间的差别只是话术差别。

两条里更根本的是前一条：周期不对齐时，就算判断依据全部来自内部证据（数据基础、团队技能、成本线都量清楚了），结论也落不了地——长于考核周期的投入会在第一次季度盘点被抽调。反过来，周期对齐（预算写死、验收口径分开）之后，第二条才开始起决定作用。

主文件 §1.2 的业务痛点与 §3.5 列出的反模式，成因也都在约束层：战略无法落地，是因为「3-5 年愿景」与「季度可交付」之间没有翻译机制；老板不买账，是因为战略没有换算成成本与收入；团队失方向，是因为目标没有被拆成可验收的动作；盲目跟风，是因为判断依据不是自身约束；忽视技术债，是因为还债的收益落在下一个考核周期；战略锁死，是因为规划周期被当成承诺期限；一言堂战略，是因为战略的生产过程没有外部输入。本节对每个工具都问同一句话：**它解决的是哪一条约束，又在什么条件下失效**。

还有一条容易忽略的约束：**战略工具的产出必须是可被反驳的**。一张不能证明「什么情况下这个判断是错的」的图，就不是分析，而是立场表达。所以下面对每个模式都要求写出失效条件——写不出失效条件的战略工具，用起来都像护身符。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 规划周期 vs 考核周期 | H2 / H3 投入能否活过一次考核 | 「战略要长期主义」——考核周期短于回报周期时，长期投入会被季度压力吃掉 |
| 判断依据（内部证据 / 外部信号） | 采纳节奏由自身约束决定还是被外部带动 | 「跟随业界最佳实践」——外部信号不含你的数据基础与团队技能 |
| 差异化位置 | 自研 / 采购 / 合作的边界 | 「核心能力必须自研」——是否核心取决于对客户是否可感知，而非技术是否先进 |
| 资源可替换性 | 投资组合是加法（可调比例）还是门槛（缺一即无效） | 「补齐短板」——数据与治理是门槛项，不是可被算法得分补偿的加法项 |
| 决策可复盘性 | 战略能否被证伪、能否归因 | 「结果好就是战略对」——没有决策当时依据的记录，只能事后合理化 |
| 组织范围与人数 | 战略靠会议传播还是靠门禁与平台落地 | 「全员对齐」——战略落到执行要走门禁，会议对齐只覆盖到场的人 |

### 3.2 模式逐个拆解（核心节）

以下 12 个工具按同一顺序给出五件事：**被什么约束逼出来 → 结构 → 为什么有效 → 代价 → 失效点**，再加一条真实使用。战略工具的差别不在名字，而在它把「不确定性」放在哪条坐标轴上——看清这一点，才不会拿定位工具去做投资决策。

#### 3.2.1 Hype Cycle：把「期望」与「成熟度」拆成两条独立的轴

- **被什么约束逼出来**：技术关注度由媒体与厂商驱动，热度峰值与可用性峰值不同步，而投资决策必须按可用性而不是按热度来做。
- **结构**：
```text
期望值
  ▲        ╱╲  Peak of Inflated Expectations
  │      ╱    ╲
  │    ╱        ╲__  Trough of Disillusionment
  │  ╱ Innovation      ╲__  Slope of Enlightenment
  │ Trigger                ╲________ Plateau of Productivity
  └──────────────────────────────────────────► 时间（横轴无刻度）
  读法：位置 = 期望值判断，不是时间预测
  每条曲线的形状由「可观测证据」而非日期决定
```
- **为什么有效**：因为坐标系把「被谈论的程度」与「能交付的程度」显式分开，所以「现在热度高」不再等于「现在该投」，这条判断从直觉变成了图上的一次定位。
- **代价**：曲线是事后拟合的，横轴没有刻度，每年重画；把一个具体技术放在哪一点上依赖判断而非数据，因此不同分析者会给出不同位置。
- **失效点**：当拿它当时间表用（「我们处在低谷，所以两年后会好」）时，「期望与成熟度解耦」反转成「预测幻觉」，因为横轴没有刻度，位置本身不携带到达下一阶段的时间信息。
- **真实使用**：该模型由 Gartner 提出并自 1990 年代中期起按年发布，常被用于年度技术盘点（【公开：Gartner 官方 Hype Cycle 方法页当前版本，可按「Gartner Hype Cycle methodology」检索核验】）；落到具体技术的定位请以官方当年发布的版本为准。

#### 3.2.2 Tech Radar：给组织级选型一个可追溯的环位

- **被什么约束逼出来**：同一组织内各团队重复评估同一技术，结论不一致，且没人说得清「这个技术当初为什么被搁置」。
- **结构**：
```text
四个环（结论强度递减）：Adopt → Trial → Assess → Hold
四个象限：技术 / 语言与框架 / 工具 / 平台
每条目 = 象限 + 环位 + 一期期号（例如 2024 年第 2 期）
环位语义（关键）：
  Adopt  = 可用于生产
  Trial  = 值得在可控范围内试用
  Assess = 值得调研，尚不推荐投产
  Hold   = 不推荐新项目采用（不是禁止）
条目移动 = 结论变更，须留下变更理由
```
- **为什么有效**：因为每个条目同时带环位与期号，所以「能不能用」变成一个带时间戳的组织判断，新同事可以直接查到结论与它被移动的时点，而不必重新评估一遍。
- **代价**：环位需要跨团队共识，每期评审有固定组织成本；雷达只覆盖被评估过的技术，长尾技术没有环位，而「没被列上」在实践中会被误读成「不能用」。
- **失效点**：当环位被当成审批门槛（Hold 视作禁令）时，「降低选型分歧」反转成「抑制合理试验」，因为 Hold 的语义是「不推荐新项目采用」而非禁止，被当禁令后团队转为私下使用，组织反而失去了可见性。
- **真实使用**：ThoughtWorks Technology Radar 自 2010 年起每半年公开发布一期（【公开：ThoughtWorks 官方站点；Adopt / Trial / Assess / Hold 四环的当前定义以官方最新一期为准】）；许多组织沿用同一套环位语义做内部雷达（【经验】）。

#### 3.2.3 McKinsey Three Horizons：给不同回报周期的投入各自上锁

- **被什么约束逼出来**：维护类与探索类投入竞争同一批人，而探索的回报周期长于考核周期，若不给它独立预算，它在每次资源紧张时第一个被抽调。
- **结构**：
```text
H1 核心业务   → 维护 + 优化     资源占比（业界最常引述）70%
H2 新兴业务   → 拓展 + 试点                    20%
H3 未来业务   → 探索 + 储备                    10%
每层必须显式回答：
  · 预算归属（谁的钱，能不能被别的层挪用）
  · 验收口径（H3 不用当期收入验收）
  · 毕业条件（H2 进入 H1 / H3 进入 H2 的条件）
```
- **为什么有效**：因为三层被显式命名并各自绑定预算与验收口径，所以 H3 的投入不会在同一张季度预算表里与 H1 直接竞争——它被移出了当期回报的比较范围。
- **代价**：分层管理成本（三套口径、三次汇报）；H3 项目通常无法在考核周期内证明价值，需要长期政治资本支撑；层间资源调动会持续引发争议。
- **失效点**：当考核周期短于 H3 的回报周期且预算归属没有写死时，「面向未来的储备」反转成「随时可被抽调的人力池」，因为预算的名义归属只要不绑定「不可挪用」，在季度压力下就必然被挪。
- **真实使用**：三层面模型由 McKinsey 在《The Alchemy of Growth》中提出（【公开：McKinsey《The Alchemy of Growth》, 1999】）；70/20/10 是该框架最常见的引述配比，实际取值随行业与业务成熟度差异很大（【经验】）。

#### 3.2.4 Wardley Maps：把「该自研还是该采购」交给演化阶段决定

- **被什么约束逼出来**：同一个组织里，不同组件处在完全不同的演化阶段，用同一套策略对待全部组件必然错——把商品化组件当差异化自研是浪费，把差异化组件当商品采购是自弃。
- **结构**：
```text
纵轴：价值链位置（离用户需求的远近）
横轴：演化阶段 Genesis → Custom → Product → Commodity
                Genesis   Custom    Product   Commodity
  用户可见性高  ┌───────────────────────────────────┐
    · 差异化能力 │ 自研/试验  自研     混合     采购   │
    · 支撑能力   │ 试验       自研/开源 采购     采购   │
  用户可见性低  └───────────────────────────────────┘
读法：位置决定策略；随演化推进，同一组件要向右移动策略
```
- **为什么有效**：因为每个组件在图上同时有「价值链位置」与「演化阶段」两个坐标，所以策略由组件所处阶段决定，而不是由「它重不重要」这类无法执行的判断决定。
- **代价**：画图需要业务与技术共同参与（价值链位置是业务判断，演化阶段是技术判断）；图有保质期，演化推进会让结论过期；不重画就无法用于沟通。
- **失效点**：当把图当静态归档（画一次贴墙）时，「按阶段选择策略」反转成「按过时地图执行」，因为不同组件在演化轴上的移动速度不同，一次成图无法保留这个速度差。
- **真实使用**：该方法由 Simon Wardley 公开（【公开：Simon Wardley《Wardley Maps》，作者公开在线书稿，2010 年代中期起连载，以当前版本为准】）；常用于自研与采购的边界讨论（【经验】）。

#### 3.2.5 Core-Edge-Spot：用「客户是否可感知」划分投入等级

- **被什么约束逼出来**：预算有限，必须区分「构成客户可感知差异的能力」与「必要但不产生差异的能力」，否则重复造轮子会持续发生。
- **结构**：
```text
Core（差异化核心）  判定问题：客户能感知到它的差异吗？
                    → 自研 + 持续投入，按产品而非项目管
Edge（必要但不差异化）判定问题：它坏掉会影响业务吗？会 → 但差异感知为零
                    → 采购 / 复用 / 优化成本，不追先进
Spot（暂时性机会）  判定问题：这个价值窗口会持续多久？
                    → 试验 + 预设退出条件，不建长期团队
每个能力必须落在三类之一，且写明判定依据与复核时间
```
- **为什么有效**：因为分类的判据是「客户是否可感知」而不是「技术是否先进」，所以「我们也可以自研一个」这类投入冲动会在分类环节被拦下——它先要回答客户是否感知得到。
- **代价**：分类是判断题，边界案例多（一个能力可能今天是 Edge、明年是 Core）；被划为 Edge 的团队会感到价值被否定，这是组织成本而非技术成本。
- **失效点**：当分类由技术团队自评时，「聚焦差异化」反转成「一切皆核心」，因为自称核心能带来预算与编制的正当性，而外部的业务方通常不会主动反对内部团队的自评。
- **真实使用**：核心 / 边缘 / 机会这三类分法在技术采购与治理材料中广泛出现（【经验】，可按「核心能力边缘能力机会能力自研采购」等关键词自行检索核验）；具体归类与命名各家不同，关键是判据是否写出来。

#### 3.2.6 Build-Buy-Partner：把时间窗与退出成本放进同一个决策

- **被什么约束逼出来**：自研受招聘与学习曲线的硬约束，采购受供应商路线与锁定成本的硬约束，合作受协调成本的硬约束——三条路各有各的成本结构，不能只比第一年的报价。
- **结构**：
```text
选项      前期成本   长期成本       主要风险          适合的时间窗
Build     高         随规模摊薄     招聘与学习曲线     能力要长期持有
Buy       低         随用量线性上涨 供应商路线与锁定   能力已商品化
Partner   中         协调与对齐成本 依赖方优先级       能力需快速起步
决策必须同时写清：
  · 决策时点与复核时点     · 退出成本（迁移到另一选项要付什么）
  · 规模拐点（用量到多少时，成本排序会反转）
```
- **为什么有效**：因为决策被要求同时给出退出成本与规模拐点，所以「采购便宜」这类只比当年报价的结论会被迫延伸到它失效的规模点上，比较口径从价格改成总成本。
- **代价**：总拥有成本估算本身很难，且会随时间变化；锁定成本通常在数年后才显现，此时决策者往往已经换人。
- **失效点**：当只比较第一年报价时，「快速且低成本」反转成「长期成本最高」，因为订阅与许可成本随用量线性上涨，而自研成本会被规模摊薄——两条成本曲线的交点通常不在第一年。
- **真实使用**：自研 / 采购 / 合作三分法是技术战略与采购决策的通用结构（【经验】）；多数公开组织把决策理由与复核时点写进架构决策记录，以便后续回溯。

#### 3.2.7 AI Strategy Canvas：把数据与治理放在与算法同级的位置

- **被什么约束逼出来**：AI 能力由多块共同决定，而项目失败常被单一归因于「模型不行」，导致数据与治理的欠账被长期忽略。
- **结构**：
```text
五个维度（示意权重，非实证赋值）：
  数据 0.30 | 算法 0.25 | 算力 0.20 | 治理 0.15 | 人才 0.10
使用方式（关键）：
  ① 先做门槛判定：数据可获得性与合规可用性是否达标
     └─ 不达标 → 其余维度得分不计（门槛项，不可补偿）
  ② 门槛达标后，再按权重评估资源投放
  ③ 每个维度写清「当下缺什么、补它要多久」
```
- **为什么有效**：因为数据与治理被列为与算法同级的维度并前置为门槛判定，所以「模型效果不行」不再能单独归因到算法，数据可得性与合规可用性会被先检查一遍。
- **代价**：权重是示意赋值（原框架给的是 0.30 / 0.25 / 0.20 / 0.15 / 0.10），不同组织差异极大，照抄会误导（【经验】）；门槛判定需要业务与法务参与，判断周期比模型试验长。
- **失效点**：当把画布当评分卡给各部门打分时，「补齐短板」反转成「平均用力」，因为数据与治理是门槛项而不是可替换的加法项——算法分再高也不能把不可用的数据补偿成可用。
- **真实使用**：AI 战略画布类工具在咨询与厂商材料中形态各异（【经验】，可按「AI 战略画布 / AI Strategy Canvas」自行检索核验）；更稳的做法是自建维度并明确写出门槛项与权重理由。

#### 3.2.8 Decision Intelligence Strategy：把决策本身记成可复盘的资产

- **被什么约束逼出来**：决策质量与数据质量、模型质量不是同一件事；同样一份报表在两次决策中可能被用出相反结论，而组织无法从结果好坏中分辨是判断错了还是运气差。
- **结构**：
```text
决策图谱（Decision Graph，一次决策一条记录）
  决策问题 → 当时可选方案 → 采用依据（数据 / 规则 / 模型）
      → 决定（谁、何时） → 执行 → 结果 → 复盘标注
关键字段：当时已知什么、不知道什么、依据的置信度
用途：同类决策可检索、可对比、可归因；模型可被要求解释输入

同一条主线上的另外三个子项：
  决策 KPI      —— 度量「依据是否齐备、决策是否及时」，不只看结果好坏
  决策 ROI 评估 —— 把「延迟决策」的成本与「已做决策」的差额放在一起比
  AI 辅助决策   —— 模型给候选与置信度，署名与责任仍落在人
```
- **为什么有效**：因为决策被当作一等资产记录（含当时依据与未知项），所以复盘能区分「依据不足」与「判断偏差」，改进方向从「换个模型」变成「补哪类输入」。
- **代价**：记录成本落在做决定的那一刻，而那正是人最忙的时候；决策日志需要存储与检索系统，否则等于没有记录。
- **失效点**：当只记录结果而不记录当时依据时，「可复盘」反转成「事后合理化」，因为人只能凭结果反推理由，而结果的好坏会污染对当时判断的评价。
- **真实使用**：决策智能被 Gartner 列为战略性技术趋势之一（【公开：Gartner《Top Strategic Technology Trends 2022》含 Decision Intelligence，可按报告标题检索核验】）；落地形态通常是决策日志 + 指标回流（【经验】）。

#### 3.2.9 OKR + Tech Strategy：用可度量的结果把愿景翻译成季度动作

- **被什么约束逼出来**：技术愿景的时间尺度（3-5 年）与组织的考核尺度（季度）不一致，中间缺一层翻译，愿景就停在 PPT 上。
- **结构**：
```text
O（Objective，定性、少而稳）：例如「让数据可被自助取用」
  KR1（结果，可度量）：自助取数占比达标（按查询量口径定义）
  KR2（结果，可度量）：从提问到取到数的中位耗时下降到设定线
  Init（动作，非目标）：建指标目录 / 补字段注释
对齐规则：上层 O ← 下层 O 的支撑关系；KR 只写结果不写动作
复盘规则：季度末只回答两件事——达成与否、口径有没有被改过
```
- **为什么有效**：因为 KR 必须写成可度量的结果，抽象的「云原生化」被迫翻译成「有多少服务在什么口径下完成了什么」，愿景因此获得一个季度尺度的验收面。
- **代价**：可度量的 KR 倾向于选容易测的（覆盖率、吞吐），把难测的（可演化性、架构健康）挤出目标集；每季度对齐本身也有会议成本。
- **失效点**：当 KR 与个人绩效直接绑定时，「对齐」反转成「指标博弈」，因为达标的最省力路径不是完成工作，而是挑选好做的工作或修改口径。
- **真实使用**：OKR 方法源自 Intel 的实践并由《Measure What Matters》系统介绍（【公开：John Doerr《Measure What Matters》, 2018】）；技术组织普遍用它承载战略对齐（【经验】），成败多取决于口径是否被冻结。

#### 3.2.10 Balanced Scorecard：用因果链把技术债这类慢收益项落位

- **被什么约束逼出来**：只看财务指标会持续挤压内部流程与能力建设，而这些正是未来财务指标的来源，但它们的收益不在当期体现。
- **结构**：
```text
学习与成长（人才 / 工具能力 / 技术债偿还）
      ↓ 因果链（先验假设，需按年验证）
内部流程（架构健康 / 交付周期 / 质量）
      ↓
客户与业务（满意度 / 可用性承诺达成率）
      ↓
财务（成本 / 收入 / ROI）
四视角各自设指标，但必须写明上一层的哪一项由下一层哪一项驱动
```
- **为什么有效**：因为四个视角被要求串成因果链而不是并列打分，技术债这类「今天花钱、明年省钱」的投入才有一个非财务的落点，不至于每年都被财务视角淘汰。
- **代价**：四套指标带来采集成本与口径冲突；因果链是先验假设，验证周期以年计，中间地带容易被当成无效投入砍掉。
- **失效点**：当四象限各自独立打分而不连线时，「平衡」反转成「四份互相竞争的 KPI」，因为失去因果链后，每个视角都会最大化自己的指标，而内部流程视角最没有话语权。
- **真实使用**：平衡计分卡由 Kaplan 与 Norton 提出（【公开：Kaplan & Norton, "The Balanced Scorecard—Measures That Drive Performance", Harvard Business Review, 1992】）；技术组织常在「内部流程」视角下承载架构健康与技术债指标（【经验】）。

#### 3.2.11 Strategic Pivot：给转向预设触发条件与退出标准

- **被什么约束逼出来**：外部条件（业务模式、技术代际、市场）变化快于既定规划，继续执行只会加深沉没成本，但转向又极易被情绪与外部噪音触发。
- **结构**：
```text
转向判定卡（在转向之前先写好，而不是事后解释）
  触发信号（必须可观测）：
    · 业务侧：核心指标连续多个周期偏离规划假设
    · 技术侧：原路线的关键前提被证伪（例如依赖的能力不可得）
    · 成本侧：单位成本曲线不再随规模下降
  判定问题：这些信号指向的是执行不力，还是前提不成立？
  退出标准：旧路线停止投入的条件、已投入资产的处置方式
  决策记录：转向前后的依据必须留档，供后续复盘
```
- **为什么有效**：因为触发条件与退出标准被预先约定，转向决策就不再依赖某次情绪化的会议——判断依据是事先写好的可观测信号，而不是当下的热度。
- **代价**：转向会打断已积累的能力与人员（技能与信任的损失不在账面上）；频繁转向会让组织对下一份路线图不再投入，转向的说服成本随次数递增。
- **失效点**：当转向只因友商动作被触发时，「及时调整」反转成「跟风摆钟」，因为友商的约束（数据基础、团队技能、成本结构）与你不同，外部动作不含任何指向你的信息。
- **真实使用**：把「转向」作为受条件约束的决策来管理，源自精益创业的实践总结（【公开：Eric Ries《The Lean Startup》, 2011】）；企业技术战略沿用其判定结构（【经验】）。

#### 3.2.12 Open Strategy：用公开换取执行者的认同

- **被什么约束逼出来**：战略的效果取决于执行者是否认同，而认同需要信息；信息只在会议室里流动时，执行者只收到结论，收不到判断依据。
- **结构**：
```text
公开面（对外/对内全量可见）  私有面（限范围）
  · 技术雷达与该环位的理由      · 未定案的候选技术
  · 架构决策记录（含被否方案）  · 供应商谈判与价格
  · 开源出去的组件与规范        · 组织与编制安排
分界线规则：结论公开 + 依据公开；过程性信息可延后公开
公开粒度三档：全公开 / 内部公开（全员可见） / 仅结论公开
```
- **为什么有效**：因为公开的部分会被外部读者审阅，战略里的空洞与自相矛盾会提前暴露；同时执行者拿到的是依据而非结论，可以在自己的约束下重新推导。
- **代价**：公开承诺会限定后续选择空间（战略不能悄悄改，改要解释）；公开内容需要维护，过期的公开材料比不公开更有害。
- **失效点**：当只公开结论而不公开取舍理由时，「透明换取认同」反转成「承诺被过度解读」，因为外部读者只能按字面理解，会把试探性的选择读成确定承诺，之后的调整被当作失信。
- **真实使用**：多家组织将技术雷达与架构决策记录对外公开（【公开：ThoughtWorks Technology Radar 长期公开发布，可按官方站点核验】）；内部全量公开决策记录是更常见的形态（【经验】）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 年度技术盘点、判断该不该投产 | Hype Cycle | Tech Radar 只给组织内的采纳结论，不解释所处阶段 | 你要回答的是「成熟度」还是「我们采不采」 |
| 组织级选型一致性、跨团队复用 | Tech Radar | Hype Cycle 的横轴无刻度，无法作为审批依据 | 是否有定期评审机制维护环位与期号 |
| 同一环位内几个候选方案要排序 | Tech Radar + Decision Matrix | 雷达只回答「能不能用」，同为 Adopt 的两个候选它不排序 | 权重与判据能否在比较之前写下并留档 |
| 长回报周期投入被季度挤掉 | Three Horizons | OKR 以季度为周期，天然看不见 H3 | 预算归属能否写死为不可挪用 |
| 自研与采购边界争不清 | Wardley Maps | Core-Edge-Spot 只说该不该投，不说演化阶段 | 能否画出价值链并判断各组件所处阶段 |
| 预算受限、需快速划分投入等级 | Core-Edge-Spot | Wardley Maps 的绘图成本高于一次分类 | 判据能否写成「客户是否可感知」 |
| 采购 / 自研 / 合作三选一 | Build-Buy-Partner | 只比报价会在规模增长后反转，必须比总成本 | 能否给出规模拐点与退出成本 |
| AI 能力规划 | AI Strategy Canvas（+ 门槛判定） | 通用 OKR 会把数据与治理降级为任务项 | 数据可得性与合规可用性是否先判 |
| 决策质量要可归因 | Decision Intelligence Strategy | 只记结果无法区分运气与判断 | 决策当时的依据能否被记录并检索 |
| 战略对齐与度量 | OKR + Balanced Scorecard | 只有 OKR 会漏掉慢收益项，只有计分卡会缺季度抓手 | 口径是否冻结、因果链是否连线 |
| 外部条件发生实质变化 | Strategic Pivot（带触发条件） | 无触发条件的转向会退化为跟风 | 触发信号是否可观测量且指向自身约束 |
| 需要执行者认同与外部输入 | Open Strategy | 只发结论拿不到依据层面的反馈 | 公开面能否包含取舍理由 |

本主题下**最常被误选的一对**是「用 Hype Cycle 决定投不投」与「用 Tech Radar 决定成不成熟」。前者把一张没有时间刻度的定位图当时间表，于是出现「我们在低谷期，明年就该上了」这类推断；后者把组织内的采纳结论当成熟度评价，于是「我们还没 Adopt」被读成「技术不成熟」。两者共同的后果是**把判断依据从自身约束换成了图上的位置**，而位置一旦被当作事实，战略就失去了被证伪的能力。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Three Horizons + OKR + Tech Radar（多数技术组织的默认组合）**
- 职责边界：Three Horizons 管资源分层（谁的钱、按什么周期验收）；OKR 管季度翻译（愿景 → 可度量结果）；Tech Radar 管选型结论（环位 + 期号）。
- 运维代价：三套机制各自的维护成本——季度对齐会议、雷达评审会、分层预算盘点（【经验】）；口径不统一时三者会互相打架。
- 适合规模：有独立技术预算、几十人以上的组织【经验】。

**组合二：Wardley Maps + Build-Buy-Partner + ADR（能力边界决策）**
- 职责边界：地图给出各组件所处演化阶段；三选项决策给出该阶段的策略；决策记录把当时的阶段判断与退出成本留档。
- 运维代价：地图需定期重画（演化会移动），三者都要人去维护，只适合对少数关键组件做，不适合全量铺开。
- 适合规模：平台型团队、需要在自研与采购之间反复取舍的组织【经验】。

**组合三：AI Strategy Canvas + Decision Intelligence + 门槛清单（AI 战略落地）**
- 职责边界：画布定维度与门槛（数据与治理先行）；决策记录管「用 AI 做的决定」如何复盘；门槛清单在项目入口处拦截数据不可用的方案。
- 运维代价：门槛判定需要业务与法务参与（周期长），决策日志需要系统支撑；两者都属基础设施投入，短期看不到产出。
- 适合规模：有持续 AI 投入、且已出现「模型效果争议」的组织【经验】。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「战略无法落地」 | 战略文档里没有一个可验收的结果，全是方向词 | 无验收面即无反馈，战略与执行各走各路 | 战略被写成愿景陈述，缺少翻译层 | 每个方向配 2-3 个可度量结果 + 责任层 |
| 「老板不买账」 | 汇报材料讲架构演进图，不讲成本与业务影响 | 资源竞争时技术项被优先砍掉 | 技术战略用技术语言表达价值 | 用成本、收入、风险三类口径重写结论 |
| 「团队失方向」 | 团队说不出自己的季度目标与上层战略的关系 | 执行层动作与战略无关，资源被内耗 | 战略只传到管理层，没有拆成团队级目标 | 战略拆到团队级 OKR 并公开对齐关系 |
| 「盲目跟风」 | 技术栈在一年内经历两次整体替换，理由都是「业界都在用」 | 每次替换都清空既有积累，团队学习成本反复支付 | 判断依据是外部信号而非自身约束 | 采纳前先写「我们的约束是什么」，用雷达 + 试点门禁约束节奏 |
| 「忽视技术债」 | 预算里没有偿还项，或偿还项每次都被新功能挤走 | 交付周期与故障率同步上升，后期返工吞掉新功能产能 | 还债收益落在下个考核周期，不进入当期目标 | 技术债进 Three Horizons 的 H1 预算，并设固定比例上限 |
| 「战略锁死」 | 路线图三年不变，且改一次要走审批 | 外部条件变了而战略不变，执行层自行偏离 | 规划周期被当成承诺期限 | 设半年复核点，写明「什么条件下改」 |
| 「一言堂战略」 | 战略由一人拍板，团队在评审会上第一次看到 | 执行层缺乏认同，落地时以最低合规标准执行 | 战略生产过程没有外部输入，缺少异议通道 | 跨团队共建 + 事前征求意见并留档处理结果 |
| 「战略 vs 执行割裂」 | 战略会与执行会由不同人开且结论不通气 | 反馈无法回灌，战略越来越脱离现实 | 战略被定义为年度动作，不是持续过程 | 战略必须 Review 反馈：季度回看假设是否成立 |
| 「形式主义战略」 | 战略文档没有 Owner，也没有跟踪项 | 没有人对战略负责，等于没有战略 | 战略被当作汇报交付物而非管理动作 | 每项战略动作带 Owner + 复核时点 |

三个最危险的条目在生产中这样暴露：

- **「盲目跟风」**：典型形态是「友商全 AI，我们必须 follow」。它的问题不在跟随本身，而在于**判断依据被替换成了外部动作**——友商的数据基础与团队技能与你不共享，它的动作里没有关于你的信息。识别信号是：决策材料里能引用的全是外部报道，没有一条自身约束的量化描述。
- **「忽视技术债」**：它不表现为某次事故，而表现为**产能的持续下降**：同样的需求耗时逐年上升，新功能被返工吞掉的比重上升。因为债务的成本以「交付速度」的形式分散到每一次迭代里，所以它在任何一个季度的报表上都不显著。
- **「形式主义战略」**：最新也最普遍的一种，暴露方式是战略文档完整、术语正确、每个维度都有内容，但没有任何一项指向具体人、具体时点。它的危害在于**占据了战略应有的位置**：当真问题出现时，组织会先回去更新那份文档，而不是改变资源分配。

### 3.6 规模跃迁时模式何时该换

下表的规模档位按团队人数与业务线数量粗略分档（【经验】）；真正可迁移的是「为什么开始疼」与「换成什么」这两列。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 十余人 → 百人 | 口头 + 文档战略 | 新人拿不到判断依据，重复评估已定事项 | Tech Radar + ADR | 评审与归档成为固定组织成本 |
| 百人 → 数百人（多业务线） | 单点选型共识 | 各业务线各自选型，重复建设出现 | Radar 分环位 + 平台化门禁 | 门禁建设与例外处理机制 |
| 回报周期拉长（平台期） | 只看当期 OKR | H3 投入在每次季度盘点被挤掉 | Three Horizons + 不可挪用预算 | 需要长期政治资本支撑 H3 验收口径 |
| 自研比例上升 | 逐案拍板自研 | 自研边界失守，重复造轮子 | Wardley Maps + Build-Buy-Partner | 需业务与技术共同参与画图与复盘 |
| 引入 AI 能力 | 通用技术战略 + 项目制 | 数据与治理欠账在模型效果争议中集中暴露 | AI Strategy Canvas（含门槛判定）+ 决策记录 | 门槛判定周期长，法务与业务需常态化参与 |
| 战略对外公开 | 内部战略文档 | 外部只拿到结论，误读为确定承诺 | Open Strategy（结论 + 理由公开） | 公开内容需长期维护，改口要解释 |

判断是否已跨过阈值，不看人数，而看三件事：**新人能否在不需要口述传承的情况下查到某条选型结论及其理由**、**H3 类投入是否连续两个周期未通过预算**、**技术债的偿还项是否被新功能持续挤走**。第一件说明判断依据没有沉淀，第二、三件说明约束层已经失效——此时换工具没用，要先解决预算归属与验收口径。

- [ ] 每个方向是否配了 2-3 个**可验收的结果**而不是动作清单？只有动作时，战略无法判定成败。
- [ ] H3（未来业务）的预算是否写明「不可挪用」并有归属人？没写死则季度内必被抽调。
- [ ] KR 的口径是否在周期开始前冻结并有版本记录？可中途改口径的 KR 无法作为验收依据。
- [ ] 采纳入某技术前，是否写下了自身约束（数据基础、团队技能、成本线）？只写外部理由即为跟风。
- [ ] 自研 / 采购 / 合作的决策是否给出**规模拐点与退出成本**？只给第一年报价的决策会在规模化后反转。
- [ ] 每条选型结论是否有环位与**复核时点**？无复核时点的结论会静默过期。
- [ ] 关键决策是否记录了「当时已知什么、不知道什么」？只记结果的决策记录无法复盘。
- [ ] 有没有至少一项针对**技术债**的预算与指标落点？没有即说明慢收益项无位置。
- [ ] 战略文档的每一项是否有 Owner 与复核时点？缺任一项即为形式主义战略。
- [ ] 是否设定了半年复核点，并写明「什么条件下改」？三年不变的规划会把规划变成承诺。
- [ ] 对外公开的部分是否包含**取舍理由**？只公开结论会被读成确定承诺。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 判断技术是否值得投产 | Hype Cycle（看位置，不看日期） | 期望与成熟度分轴，热度峰值不等于可用峰值 |
| 组织级选型要一致 | Tech Radar（环位 + 期号） | 每条结论带时间戳与理由，可追溯、可移动 |
| 长回报投入被季度挤掉 | Three Horizons | 三层各自绑定预算与验收口径，移出当期比较 |
| 自研与采购边界不清 | Wardley Maps + Build-Buy-Partner | 策略由演化阶段决定，并强制写出规模拐点与退出成本 |
| 预算受限、需快速分级 | Core-Edge-Spot | 判据是客户可感知，能拦下「也可以自研一个」的冲动 |
| AI 能力规划 | AI Strategy Canvas（门槛先行） | 数据与治理是门槛项，不可由算法得分补偿 |
| 决策要可归因 | Decision Intelligence Strategy | 记录当时依据，才能区分运气与判断 |
| 战略要落地与对齐 | OKR + Balanced Scorecard | OKR 给季度抓手，计分卡的因果链给慢收益项落点 |
| 外部条件实质变化 | Strategic Pivot（预写触发条件） | 判断依据是事先约定的可观测信号，不是当下热度 |
| 需要执行者认同 | Open Strategy（结论 + 理由） | 公开依据使执行者可在自身约束下重新推导 |

> 本节小结：决定技术战略工具选择的**最底层的那条约束**是「**你的考核周期与投入回报周期是否对齐**」——不对齐时，H3 类投入会被季度机制系统性淘汰，换任何画布或雷达都无效；对齐（预算写死、验收口径分开）之后，第二条约束（判断依据来自内部证据还是外部信号）才起决定作用，工具之间的差别也才真正变成效率差别。所以选型的第一问不是「用哪个框架」，而是「这条投入在哪个周期被验收、由谁的钱支付」。
