## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

选型框架这个主题的趋势清单有一类特别隐蔽的错误：它把「AI 让选型更快」当成收益写进去，而**快本身不是选型的目标**。选型的目标是选对，或者在选错之后能便宜地改回来。一张两天做出来的矩阵和一张两周做出来的矩阵，如果结论一样、证据强度一样，那两天的那个确实更好；但如果快的代价是格子里的数字从「采集来的」变成「生成出来的」，那它不是更快，而是**换了一种东西**——长得像矩阵，承载的不是证据。

所以本节对每个方向只问一句「AI 改变了哪个机制」，并且把答案限定在四类里：**改变了成本函数**、**改变了接口边界**、**把人工判断换成了统计判断**、**只是换了前端**。第四类要老实承认——那是接口改良，不是架构变化，写进路线图只会占用预算。

分级判据用三条，三条必须同时成立才算 L1：

- **已 GA 且有正式 release note**——不是产品页的功能列表，是版本发布说明。
- **有第三方（非厂商）公开的生产案例**——厂商自有案例证明功能存在，不证明它在别人的环境里可用。
- **接口稳定**——能被别的系统依赖；接口还在预览期时，你的集成本身就是风险。

由此得到三级，读者该做的事完全不同：

- **L1 生产可用**：可以排进路线图，按正常工程标准做取舍。
- **L2 可试点**：可以做 PoC，**不要做核心依赖**；PoC 的目标是拿到你自己环境下的数据，不是复现厂商的宣称。
- **L3 观望**：只记录，**不要在架构里为它预留假设**——预留假设的成本（接口层的抽象、评分字段的占位）往往比将来重构还贵。

| 演进方向 | 级别 | 判据 | 现在该做什么 |
| --- | :---: | --- | --- |
| AI 辅助选型：候选与维度扩列 + 对比表骨架 | L2 | 组件成熟（长上下文与结构化输出均有正式文档与稳定接口），产物是草稿、漏项可人工补；差第二条判据——缺「选型场景」的第三方生产案例 | 可以做 PoC：先在一个真实选型会上跑一遍，人工补尾部候选；不要设为核心依赖 |
| AI 生成 Trade-off Table | L2 | 同上（与上一行同属**一条能力的两面**，合计一个方向）；它生成的是行列结构，不是数字 | 用它生成骨架，**不要**用它填分数 |
| AI 选型 Review（基于组织级 ADR 库 + Tech Radar） | L2 | 检索组织先例是成熟能力；但「先例是否仍有效」取决于 ADR 的状态链质量 | PoC：只输出「相关先例 + 差异点」，不给结论 |
| AI 选型 Copilot | L3 | 与 Review 的差别在「给结论」，而给结论需要授权；未取得第三方生产案例 | 记录；不要接进选型流程 |
| AI 辅助 Sensitivity Analysis | L3（不必要） | 敏感性是确定性数值计算（∂Score/∂w），模型在此无机制增益且会算错 | 用脚本或表格做，不要用模型 |
| AI 辅助 AHP | L3（不必要） | 求权重与 CR 一致性检验是闭式数值计算；模型可用于整理人的口头判断 | 只让模型做输入采集，权重与 CR 交给脚本 |
| 选型 + RAG / 向量库（历史选型文档向量化复用） | L2 | 向量检索是成熟组件；但「历史选型可复用」的前提是当时记录的约束条件在，而多数记录只有结论 | 先补「约束条件」字段，再谈复用 |
| 选型 + KG / GraphRAG（跨域联合选型推理） | L3 | GraphRAG 是 2024 年的研究原型加开源实现；选型图规模小、关系类型未标准化 | 记录；先把组织级约束写清楚 |
| Decision Intelligence 平台（选型决策图谱 + AI 助手） | L3 | 以厂商路线图与分析师叙事为主；前置条件（结论与后果的结构化回填）通常不成立 | 记录；先让 ADR 的 Considered Options 与 Outcome 字段有内容 |
| Trade-off Framework as Code（DSL + 自动判定） | L3 | 「策略 / 约束即代码」有成熟形态，但「选型框架即代码」没有公认 DSL | 记录；可以先把约束写成 CI 检查 |
| AI Constitutional 选型（用约束清单约束 AI 建议） | L3 | 与「约束即代码」同源，但约束文本尚无标准格式，也无第三方实现 | 把约束写成可执行检查，比写成给模型的提示更可靠 |
| 可解释选型（SHAP / LIME） | L3 | 解释对象错位：它解释的是模型的特征归因，不是权重的授权来源 | 记录；选型要的是可追溯，不是可解释 |
| 跨域联合选型（模型 + 向量库 + Agent 框架 + 数据湖联合决策） | L3 | 联合方案的组合空间随域数指数增长；AI 让你更快生成一个联合方案，不减少耦合 | 记录；逐域论证，最后显式列耦合点 |
| AI 主导选型决策（AI 选 + 人 Review） | L3 | 无可核验实现；且与「权重是授权产物」这一前提直接冲突 | 明确不做（见 §5.7） |

表里最接近 L1 的是「候选与维度扩列 + 对比表骨架」与「AI 生成 Trade-off Table」——它们是**同一条能力的两面**，合计一个方向，且都记为 **L2**，不是 L1。为什么差一级：第一条与第三条判据它其实够了——底层能力（长上下文、结构化输出）都有正式文档与稳定接口，产物又是**草稿**，失败模式是漏项与凑数，人工补一遍就能修，不需要动任何授权；缺的是第二条，本节未能取得针对「选型场景」的第三方公开生产案例。所以这条方向的准确表述是「**组件成熟，但缺选型场景的第三方生产案例**」。读者可以用一次真实的选型会去补这条证据，成本很低——补上它，这个方向就够 L1。

其余方向没能到 L1 的原因里，最值得记住的是两类，这个归类本身就是判断：

- **要动授权的那一类**（AI 选型 Copilot、AI 主导选型、DI 平台给建议）——它们的瓶颈不是模型能力，而是「谁有权把某个分数或结论定下来」。这类方向等三年也还是 L3，因为等的不是技术。
- **算错了也不报错的那一类**（让模型做敏感性分析、求 AHP 权重与 CR）——它们的问题不是不成熟，而是**不该做**：把确定性计算交给概率模型，等于给结果加了一个看不出来的错误源。

还有一条使用提醒：**级别不是永久标签**。它跟着 release note 走。合理的做法是每半年重核一次级别，而不是在选型框架文档里写死一次判断。

读这一节时，三个入口对应三种需求：

- **要排路线图**：看 §5.1 的级别列与 §5.7 的行动表——它们回答「现在能不能投」。
- **要在评审里反驳某个方向**：看 §5.2 的「由此付出的」与 §5.5——它们给出可核验的反对理由，而不是「我觉得不成熟」。
- **要自己验证**：看 §5.4 的判定方法与 §5.6 的信号列——它们给出三年内可观测的证据。

### 5.2 演进方向逐条拆解（核心节）

下面 4 个方向按「**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**」6 项逐条拆解。这一节反复出现同一条主线：选型方法的瓶颈从来不在「算」，而在**格子里的数字从哪来、权重谁定的**；判断一个 AI 方向值不值得投，就看它动的是这两件事中的哪一件。

#### 5.2.1 AI 生成候选与对比表：产能上去了，格子里的数字来源没变

- **旧做法与它的卡点**：一张可用的选型矩阵，成本不在「算」，在两件采集工作。一是把候选找齐——「我们没听说过 X」没有补救路径，而在场人的经验决定了候选的边界。二是把每格填上可追溯的数字——报价单、压测报告、官方文档里的限制条款、以及「团队会不会用」这类需要问人的判断。这两件事按周计。于是矩阵在实践中被降级使用：只在已经吵起来的重大决策上做一次，而且做的时候往往只剩两个候选。
- **AI 改变了什么机制**：它把「生成一份看起来完整的多维对比表」的边际成本压到接近零。注意改变的是**表格的产能**，不是**数字的来源**——模型生成的分数是**生成值**，来自语料里的流行度与常识，不是来自你的报价单和压测。而加权求和（Score = Σ w_j × s_ij）对格子的可信度不做任何区分：它假设每一格代表同一种证据。
- **由此得到的**：因为产能不再是约束，所以「每个候选都过一遍矩阵」第一次在成本上可行——比较的覆盖率可以提上去，尤其是那些过去因为「做表太贵」而没被认真比较过的中等决策。矩阵过去是一种稀缺资源，稀缺性本身在替组织做筛选（只有重要到值得做表的决策才会被做表）；产能释放之后，这道筛选换成了显式的判据。

```text
两类格子：过去只有一种，现在混在一张表里
  ┌────────────────────┬──────────────────┬───────────────────────────┐
  │ 格子类型            │ 来源              │ 在加权求和里被当作        │
  ├────────────────────┼──────────────────┼───────────────────────────┤
  │ 采集值              │ 报价 / 压测 / 官方 │ 同一种证据                │
  │                    │ 限制条款 / 访谈    │ （可追溯到具体来源）      │
  ├────────────────────┼──────────────────┼───────────────────────────┤
  │ 生成值              │ 模型先验与语料频次 │ 同一种证据                │
  │                    │                  │ （追溯链断在模型里）      │
  └────────────────────┴──────────────────┴───────────────────────────┘
  → 总分看起来更精确了，证据强度却更低了，而这个差别在表里看不出来
  → 可行的纪律：生成值只能出现在「待填」列，不能出现在分数格
```

- **由此付出的**：四条代价，前两条是结构性的。
  - **两类格子混进同一张表**：采集值与生成值长得一模一样，加权求和给它们同样的权重。这直接推翻了矩阵的隐式前提——「每一格代表同一种证据」。总分更精确，证据强度更低，而这个变化在表里看不出来。
  - **决策表演的产能被放大**：矩阵过去因为贵，本身带有一层筛选；现在这层筛选消失，一张漂亮的表可以随时为已定结论生产出来。评审者看到的「做过比较」不再是「真的比较过」。
  - **热门坍缩**：模型给的候选来自语料频次分布，热门方案稳定出现，恰好贴合你那条硬约束的冷门方案不会出现——而矩阵的价值恰恰建立在「候选是真候选」上。
  - **凑数选项**：为凑满表格而生成的、没有真实支持者的选项，在评审里被轻易否决，制造了「做过取舍」的假象。
- **证据与来源**：
  - 【公开】加权打分、Pugh Matrix、AHP、TOPSIS、CAP / PACELC、TCO / CBA / NPV 的定义均可在公开教材与原始文献核验（CAP 见 Brewer, PODC 2000；PACELC 见 Abadi, IEEE Computer 2012；AHP 见 Saaty 1970–1980 年代的工作）。
  - 【经验】「AI 降低的是整理成本而不是采集成本」是本节的核心判断，未取得第三方量化数据，故不给百分比；任何「AI 让选型提速 N%」的说法若无来源，应按营销处理。
- **成熟度**：L2。判据：组件成熟、产物可人工复核、不引入新权威，但本节未能取得「选型场景」的第三方生产案例，故记为 L2 而非 L1。它带一条硬前置——**分数必须由人从可追溯来源填入**，模型只填「待填」与理由。任何让模型直接给分的设计，落到 L3（因为它把「证据强度」这个不可见的维度弄丢了，而分析者无法察觉）。

#### 5.2.2 AI 选型 Review 与 Copilot：先例可检索，但先例的有效期没被记录

- **旧做法与它的卡点**：组织级的选型知识有两处，都很弱。一是组织级的 ADR 库（「三年前评估过 X，结论是不用」），问题是先例的**约束条件**没有被记录——「不用 X」是因为当时 X 不支持某个特性，还是因为当时团队没人会 X？不知道，而这两者在新环境下会给出相反结论。二是 Tech Radar 式的组织级前置结论（采用 / 试验 / 评估 / 暂缓），它是**结论**，不带推理过程，且更新周期（年）慢于技术变化。选型的人于是要么重做一遍评估，要么盲从先例。
- **AI 改变了什么机制**：检索把「组织先例」从档案变成约束入口——选型开始时先检索「我们以前对这个门类做过什么决定、因为什么」，机制上把先例从**参考资料**变成**输入约束**。模型还能自动做一件人经常漏掉的事：指出「你这个新决策与某条已有结论的假设冲突」。
- **由此得到的**：因为先例可以按问题检索而不用按编号翻，所以先例第一次在选型过程中真的被用上；组织的选型结论从「只影响写它的人」变成「影响下一个遇到同类问题的人」。对跨域决策尤其有价值：同时检索向量库、Agent 框架、数据湖三个门类的既有结论，指出耦合点——这件事靠人是做不到的，因为很少有人同时在场。
- **由此付出的**：四条代价。
  - **先例的时效性没有载体**：检索器会把一条已被推翻的旧结论和一条有效结论用同样的语气呈现，除非状态链与约束条件被写下来。这在选型场景里比在别处更贵——它会让组织**固化一个已经失效的结论**，而且固化得理直气壮（「我们有历史决策」）。
  - **从「给先例」到「给结论」是一道授权边界**：Copilot 的推荐即使正确，也不该替技术委员会消化分歧，因为分歧通常不在事实而在权重。
  - **前置结论被复述后获得虚假权威**：雷达上「试验」的原意是「可以试」，被组织进推荐文本后会读成「推荐采用」。
  - **新增维护成本**：要先有一份「哪些结论已失效」的清单；这份清单没人愿意维护，而它恰恰决定了这个功能有没有用。

先例分三种记录形态，成本差别很小（多写两行），可复用性差别很大：

| 先例的记录形态 | 记了什么 | 可复用性 |
| --- | --- | --- |
| 只有结论（「不用 X」） | 结论 | 低——环境一变就不适用，而且无法判断环境变了没有 |
| 结论 + 理由 | 结论 + 当天据以判断的事实 | 中——能判断这些事实今天是否还成立 |
| 结论 + 约束条件 + 失效条件 | 结论 + 当时的约束 + 什么条件变了要重评 | 高——可直接作为新决策的输入约束 |

这决定了 AI 选型 Review 的价值来源：它随**第三种形态的占比**上升，而不是随 ADR 数量上升。一个有一千条「只有结论」的 ADR 库，检索出来的东西不能当约束用。

- **证据与来源**：
  - 【公开】Tech Radar 的四环分类（采用 / 试验 / 评估 / 暂缓）与历年归档可在其官方站点核验（ThoughtWorks，2010 年起）。
  - 【公开】Microsoft Research 2024 年发布 GraphRAG（arXiv 预印本，可按标题检索核验），支持「把组织文档建成图做跨文档推理」这一方向。
  - 【经验】本节未取得「AI 选型 Review」的第三方生产案例，故记为 L2 而非 L1。
  - **一处校正**：清单把「2024 年」与「Tech Radar 第 28 期」绑在一起。雷达期号与发布年份的对应关系在其归档页逐年可核，本节不断言具体期号；引用时应以归档页原文为准。
- **成熟度**：L2。判据：检索先例的组件已 GA，但「先例是否仍有效」依赖 ADR 的状态链质量，且无第三方生产案例可引。

#### 5.2.3 形式化方法一侧（AHP / Sensitivity Analysis）：这里没有机制改变，只是换了输入方式

- **旧做法与它的卡点**：AHP 与敏感性分析的真实成本在两个地方。一是两两比较要人做——n 个判据需要 n(n-1)/2 次比较，成本随判据数二次增长，所以实践里常被迫把判据压到 5–7 个【经验】。二是比较结果要能收敛到一致（CR 检验）。真正的卡点是人：让人逐对回答「性能重要还是成本重要」容易疲劳、敷衍，而且会被第一个回答锚定。
- **AI 改变了什么机制**：**没有机制改变。**这是本节最需要说清的一句。CR 是判断矩阵最大特征值的确定性计算，敏感性分析是 Score 对权重的偏导（ΔScore_i / Δw_j = s_ij），两者都是**闭式可复算**的；模型在这两步里没有机制增益。它真正改变的是**输入采集的接口形态**——把人的口语化判断整理成两两比较矩阵。这是接口改良，不是架构变化；把它写进路线图时应当写成「输入采集自动化」，而不是「AI 辅助 AHP」。
- **由此得到的**：因为采集环节的接口变顺，所以判据多的决策第一次不必靠「简化到 5–7 个判据」来省成本——人可以一次说一段话，由模型整理成比较矩阵，再由脚本算权重与 CR。收益是真实的，但它落在输入侧，不在计算侧。
- **由此付出的**：把确定性计算交给概率模型，会引入原本不存在的错误源。
  - **CR 会被算错且看不出来**：模型给出的 CR 通常是一个「看起来合理」的小数，它不对应任何真实特征值。而 CR 的用途恰恰是发现自相矛盾的比较——一个假的 CR 会让矛盾被放行。
  - **权重不可复算**：如果权重是模型给的而不是脚本从矩阵算出来的，「权重从哪来」这条追溯链就断在模型里——而权重正是这个方法唯一需要被审的东西。
  - **可指认的锚点消失**：两两比较的价值在于参与者能在具体的一次比较上说「我不认同这一次」；如果比较由模型从一段话里推断，这个锚点就没了，讨论会退回「我觉得整体不对」这种无法收敛的形态。
- **证据与来源**：
  - 【公开】AHP 由 Saaty 在 1970–1980 年代提出并系统化，权重来自判断矩阵的最大特征向量，一致性比率 CR 与其经验阈值出自该方法原始文献；可在公开教材与原始文献核验。
  - 【经验】「模型算 CR 会给出看似合理但不对应真实特征值的结果」是本节基于机制给出的判断（概率文本模型不是计算器），未取得第三方量化评测，故不引用任何具体错误率。
- **成熟度**：L3——不是「不成熟」，而是**不该用**。正确形态是分工：模型只做输入整理，权重与 CR 一律由脚本计算并可复算。

每个环节能不能交给模型，可以按「确定性 / 授权」两把尺子一次判完：

| 环节 | 计算性质 | 能交给模型吗 | 理由 |
| --- | --- | --- | --- |
| 候选与维度扩列 | 生成 | 能 | 缺项可人工补，错了不产生新权威 |
| 口头判断 → 两两比较矩阵 | 转写 | 能 | 转写错误可见（当事人一眼能看出比较被记反了） |
| 求权重向量 / CR 检验 | 确定性数值计算 | **不能** | 可复算的事没有理由交给概率模型 |
| 敏感性分析 | 确定性数值计算 | **不能** | 同上；模型给的数字无法复算 |
| 权重赋值 | 授权 | **不能** | 权重是价值判断，必须有人负责 |
| 最终结论 | 授权 | **不能** | 结论的效力来自签字，不来自生成 |

#### 5.2.4 组合与自动化一侧（Decision Intelligence / Framework as Code / Constitutional / 跨域联合）

- **旧做法与它的卡点**：选型结论落在 ADR 里，但 ADR 是**一次性文本**：它记了「选了什么」，几乎不记「选的依据在什么条件下会失效」。于是同一门类每两年重新评估一次，每次重新采集一遍事实。第二个卡点是跨域耦合：选模型要知道向量库的选型，选向量库要知道数据湖的选型，逐个决策会把耦合点推到集成阶段才暴露。清单里的四条（DI 平台化、Framework as Code、Constitutional 选型、跨域联合）指向同一个诉求：把「结论」升级成「带条件的约束」。
- **AI 改变了什么机制**：它改变的是**约束的消费方式**——把约束写成可执行的检查（「必须开源」「必须能在指定地域部署」「许可不能进黑名单」），由 CI 或策略引擎在选型提交时校验；模型在这里的位置是把自然语言约束翻译成检查，以及把检索到的先例对齐到这些检查上。而「AI 主导选型」属于另一类主张：它要动的是**权重的授权**，那不是技术机制问题。
- **由此得到的**：因为约束可以被执行，所以「选型结论在什么条件下失效」第一次能自动发现——依赖升级、许可变更、地域合规要求变化时检查会失败并触发重评估，而不是等人两年后想起来。跨域耦合也因此能在提交阶段暴露，而不是在集成阶段。

```text
约束即代码：把选型的失效条件写成可执行检查（示意）
  constraints/tradeoff.yml
    - id: license-whitelist        # 许可不能进黑名单
    - id: region-deployable        # 必须能在指定地域部署
    - id: chinese-support          # 必须支持中文
    - id: tco-ceiling              # 三年 TCO 上限（数值来自采集，不来自模型）
  → CI 在选型提交时逐条校验；某条失败 → 触发重评估并指向对应 ADR
  → 模型的位置：把「我们要求开源」这类自然语言约束翻译成上面这些条目，
    以及把检索到的先例对齐到条目上；它不产生约束，也不判定哪条优先
```

- **由此付出的**：五条代价。
  - **约束的治理成本被低估**：可执行约束的维护成本不低于代码，且它约束所有人的选型。写错一条（例如把「支持中文」写成不可绕过的硬约束）会在很长时间里静默地筛掉合格候选。
  - **可解释选型的对象错位**：SHAP / LIME 解释的是模型的特征归因，而选型要解释的是「这条权重谁定的、被谁审过」。一个能被梯度分解的选型分数，说明它本来就是被某个模型算出来的，而不是被某个委员会定下来的——这恰恰是选型框架要避免的情形。
  - **DI 平台的前置条件**：把选型结论回流成图谱，前提是结论与后果都被结构化成字段；在 Outcome 还是自由文本时，平台只是把三份各自不可信的数据放进同一个界面。
  - **跨域联合的组合爆炸**：n 个域各 m 个候选就是 m^n 个联合方案。AI 让你更快生成一个「看起来协调」的联合方案，但不减少耦合本身；用生成的联合方案替代逐域论证，会把耦合风险藏进最不被审视的那个域。
  - **供应商锁定**：图谱与平台的形态没有标准，迁移成本高于把约束写在 git 里。
- **证据与来源**：
  - 无第三方生产案例可得；厂商侧材料不作为技术事实。
  - 【公开】AWS Well-Architected Framework 及其生成式 AI 视角（2024）可在 AWS 官方文档站核验，它是「把架构评估维度写成可检查清单」这类做法的代表；但要注意它检查的是你提交的答案，不是你的选型结论——形式相似，作用点不同。
  - 【经验】「策略即代码」在权限与合规领域是成熟形态，在选型领域没有公认 DSL。
- **成熟度**：L3。判据：没有公认格式、没有第三方生产案例，且前置条件（结论与后果的结构化回填）通常不成立。

### 5.3 与本主题既有栈的接口在哪

「选型框架 + AI」的落地差别不在模型选型，而在**接口切在哪**。三个必答问题：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 候选与维度扩列 | 模型输出结构化清单（候选 / 维度 / 定性理由），进入矩阵的「待填」行列 | 漏项与凑数选项由选型发起人复核 | L2 |
| 对比表骨架 | 生成 Trade-off Table 的行列结构，分数格留空 | 每个数字必须能指回来源（报价 / 压测 / 官方限制条款） | L2 |
| 权重 | **不由模型产生**：权重是授权产物，来源必须记录（哪次会议、哪份评审、谁签字） | 权重错了由定权重的人负责，模型不承担也不应承担 | 不适用（无接口） |
| 敏感性分析与 CR | 确定性数值计算，走脚本或表格，输入是判断矩阵 | 计算可复算，错误可定位 | L1（但不用模型） |
| 选型 Review | 只读检索 ADR 与 Radar，输出「先例清单 + 与当前约束的差异点」，不给结论 | 先例是否仍有效由技术委员会判断 | L2 |
| 约束即代码 | 把「必须开源 / 支持中文 / 许可白名单」写成 CI 检查 | 约束的修改必须走评审（约束比代码更难改回来） | L3 |
| 结论载体 | 输出一律落到 ADR 的 Considered Options 与 Decision Outcome 字段 | 结论的权威来自 Decision Owner，不来自生成工具 | L2 |

把这张表收成一条硬规则：**模型只允许出现在「格子被填之前」和「格子被填之后」两侧**——填之前扩候选、补维度，填之后找先例、查冲突；**不允许出现在「填格子」这一步中间**，即不允许生成分数、权重、CR 与结论。

理由是加权求和的可信度无关性：它把每一格当作同一种证据，因此只要有一格是生成的，整张表的总分就不再是证据的汇总，而是证据与先验的混合——且混合比例不可见。这条规则的代价很小（人工填格子的时间本来就要花），收益是可复核的。

失败责任也沿这条线切：

- **候选漏了**是**发起人**的问题——他可能没去补尾部，多问两个团队就能避免。
- **分数错了**是**采集人**的问题——数字必须指回来源，指不回去就不该写在格子里。
- **结论错了**是**Decision Owner** 的问题——他签字，就为结论负责；「工具是这么建议的」不构成免责。

还有一条关于数据形态：穿过边界的应当是可读写的**文本 + 显式字段**（矩阵条目、约束条目、ADR 字段），而不是某个平台里的一份私有评测数据。评测数据可以放在平台里，但它必须能导出成文本进入 git —— 否则约束的修改就只发生在平台里，评审时没人看得见改了什么；一旦要换平台，这些约束也带不走。

三种最常见的接口误配，都是把便利放在了可追溯之上：

- **让模型填分数**——矩阵立刻变得好填，但每个格子的来源都断在模型里，评审无法追问「这个 4 分是怎么来的」。
- **让模型给权重**——权重是选型里唯一必须有人负责的东西，交给模型等于把责任交空。
- **把约束只写在平台里**——约束的变更有记录但不在评审视野内，三年后没人说得清某条约束是谁加的、为什么加。

### 5.4 公开进展与文献

**论文与原始文献**

- **Saaty，AHP（1970–1980 年代）** —— 层次分析法：权重来自判断矩阵的最大特征向量，一致性校验用 CR；它是本节「确定性计算不交给概率模型」这条规则的来源。可在公开教材与原始文献核验。【公开】
- **Brewer，《Towards Robust Distributed Systems》（PODC 2000）** —— CAP 的公开表述，常被引作 CAP 定理的原始出处；选型里凡是引用 CAP 的地方，都应对照原文确认「分区期间」这个前提。【公开】
- **Abadi，《Consistency Tradeoffs in Modern Distributed Database System Design》（IEEE Computer，2012）** —— PACELC 的提出处，用于校正「CAP 只讲分区、不讲平时」的常见误用。【公开】
- **Microsoft Research，GraphRAG（2024，arXiv 预印本）** —— 把文档集合抽成实体关系图后做全局问答；它验证的是方向，不是「在你组织的选型语料上值得做」。可按标题在 arXiv 检索核验。【公开】

**官方文档**

- **AWS Well-Architected Framework 及其生成式 AI 视角（2024）** —— 可在 AWS 官方文档站核验；它是把评估维度写成检查清单的代表形态，但检查对象是你提交的答案，不是你的选型结论。【公开】
- **ThoughtWorks Technology Radar 历年归档** —— 四环分类与期号、年份的对应关系可在归档页逐年核验；把某期与某年绑定引用时，以归档页为准。【公开（可核验）】
- **Gartner 战略技术趋势当年清单** —— Decision Intelligence 见于 2022 年清单（官网归档可逐年核验）；若某份材料把它记为 2024 / 2025 年的新趋势，应以当年清单原文为准。【公开（可核验）】

**未能核验（不要当事实引用）**

- 清单里提到的「2024–2025 年 OpenAI / Anthropic / Google 发布企业级 AI 选型助手」「LLM 选型的新维度（幻觉率、合规、成本、上下文窗口）在 2025 年标准化」——这两条在写作时未取得一手来源。判定方法：前者查对应厂商的正式 release note（不是产品页或新闻稿）；后者尤应删去「标准化」这个说法——幻觉率没有统一定义与统一测试集，各厂商自报口径之间不可比（见 §5.5）。
- **第三方生产案例**：本节未列出具体公司。可核验的替代入口是公开的、带选型记录目录（`docs/adr/` 一类）的工程仓库，以及云厂商的公开参考架构文档。判断一份公开选型记录是否可信，看它的每个数字有没有指向可核验来源——这一条比「谁写的」更能说明问题。

本节采用的引用纪律三条，读者核对任何「AI + 选型」材料时都可以照用：

- **只有 release note 才证明某个版本具备某个能力**；产品页的功能列表不证明。
- **只有非厂商的公开生产案例才证明有人做成了**；厂商自有案例证明的是功能存在。
- **每个数字必须能指回来源与年份**；指不回去的，要么删掉，要么降级为【经验】区间并说明这是经验值。

### 5.5 被过度宣传的部分

**说法：「AI 辅助 AHP —— 让模型做两两比较与一致性检验」**

- **实际能做的**：把一段口语化的判断整理成两两比较矩阵，并指出某次比较与另一次不一致（这类提示由人复核，成本很低）。
- **做不到的**：给出正确的权重与 CR。AHP 的后半段是数值线性代数（求最大特征向量、算一致性比率），闭式可复算；而模型输出的是「看起来像正确结果」的文本，两者在形态上无法区分——偏偏 CR 的用途就是发现自相矛盾的比较，一个假 CR 会把矛盾放行。
- **什么时候才会成真**：当工具把模型限定在输入侧、把权重与 CR 交给脚本时。那时这个组合确实有价值，但它已经不是「AI 辅助 AHP」，而是「模型采集 + 脚本计算」——名字换对了，期待才不会错。
- **怎么核验**：拿同一个判断矩阵，让模型报一次 CR、再用脚本算一次。两者不一致，就说明模型那一步不该被信任；这个验证一次就能做完。

**说法：「可解释选型（SHAP / LIME）」**

- **实际是什么**：SHAP / LIME 是模型归因工具，解释的是某个预测由哪些输入特征贡献了多少。
- **为什么放到选型上不成立**：选型要回答的不是「这个分数怎么来的」，而是「这条权重是谁定的、被谁审过、在什么条件下会变」——那是授权与治理问题。反过来说，一个能被梯度分解的选型分数，本身就说明它是被某个模型算出来的，而不是被某个委员会定下来的，这恰恰是选型框架要避免的情形。
- **什么时候才会成真**：把它理解为「每一个格子都能追溯到来源、每一条权重都能追溯到签字」时。那是一种**可追溯性**，不是可解释性；用 SHAP 这个词来描述它，只会让读者以为问题已经被算法解决了。
- **怎么核验**：问一句「这条权重是怎么来的，谁定的」。如果答案是「模型算的」，无论后面跟多少解释性图表，这条选型都没有可被质疑的入口。

**说法：「LLM 选型的新维度：幻觉率可以横向比较」**

- **实际是什么**：幻觉率没有统一定义（是事实错误率、无根据断言率，还是拒答率？分母怎么算？），也没有统一的测试集与解码参数，因此厂商自报的数字之间不可比。公开的学术评测（如 HELM 一类，2022 年起）给出的是**它们选定任务分布**上的排名，与你的任务分布不同。
- **为什么会这样**：幻觉在生成侧由问题分布、提示模板、检索上下文、采样参数共同决定，把它压成一个标量，必然丢掉这些条件——而被丢掉的条件恰恰是选型时唯一相关的那部分。
- **什么时候才会成真**：当评测协议要求提交原始输出、并公开任务集与解码参数时。那之前，正确做法是在**你自己的任务集**上，用固定的提示与解码参数跑一次采样评测，把结果当作「你的环境下的观测值」而不是「这个模型的属性」。
- **怎么核验**：要求供应方给出任务集与解码参数，并允许你在自己的数据上复跑；给不出，这个维度就不该进入选型矩阵。

### 5.6 未来 3–5 年：可证伪的预测

写不出证伪信号的预测不要写。下表每条都给出两侧信号，判断标准很简单：一个说法三年后既不会因某件事被确认、也不会因某件事被推翻，它就不是判断。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 选型矩阵的权重字段会被要求标注来源（谁定的、哪次会议或哪份评审），否则矩阵不被评审接受 | 组织级选型模板出现权重来源字段；评审清单里出现「权重来源」一项 | 三年后模板仍只有权重数值，且从没有人问过权重从哪来 |
| 「候选穷举」会被拆成两步：模型扩列 + 人工补尾部（去问利益不同的两方） | 选型流程文档里出现「尾部候选补充」这一步，或出现基于内部实践而非语料频次的冷门候选推荐 | 团队完全依赖模型给候选，且没有任何「漏掉一个明显更好的方案」的记录 |
| 选型框架会从「文档」变成「可执行约束」，但只在有平台团队的规模化组织里落地 | CI 流水线里出现选型约束检查（许可、地域、开源要求），并在提交阶段拦截 | 约束仍只写在 ADR 正文里，三年后没有任何一条被机器执行 |
| 「AI 主导选型决策（AI 选 + 人 Review）」不会发生，形态会停在「AI 扩列 + 人加权 + 人拍板」 | 被广泛采用的选型工具都不敢默认自动结案（默认配置里没有「直接采纳」），输出形态是待审草稿 | 出现被多组织采用、默认自动结案的选型工具，且有第三方生产案例，并能说清结案后谁负责 |

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 正在做一个跨团队选型 | 以 PoC 形式用模型扩候选与维度（先在一个真实选型会上跑一遍），然后人工补尾部候选；分数一律从可追溯来源填 | 是否真的多出过候选；矩阵里采集值与生成值的比例 | 不要让模型给分数、权重或结论 |
| 判据多、参与方多的战略级选型 | 用模型采集两两比较的输入，权重与 CR 用脚本算并可复算 | 讨论是否能落到「某一次比较」上（可指认的锚点） | 不要让模型算 CR 或给权重 |
| 组织已有 ADR / 技术雷达 | 先给结论补状态链与约束条件字段，再做检索式 Review | 先例被引用的次数；误用过期结论的次数 | 不要在有状态链之前上决策图谱或 DI 平台 |
| 选型总在「重做一遍」 | 把结论写成「结论 + 失效条件」（许可变更、地域合规、依赖升级时重评估） | 是否有任何一条失效条件被自动触发过 | 不要用一次性报告的更新代替失效条件 |
| 团队刚开始用加权打分 | 把格子分成「采集值」与「待填」两类，先只填能指回来源的格子 | 有多少格子最终找不到来源（找不到的应删除，而不是估算） | 不要用「敏感性分析」为已经定好的结论背书 |
| 在评估选型类 AI 产品 | 要它讲清四件事：候选从哪来、分数从哪来、结论谁签字、能不能导出纯文本进 git | 产品是否公开候选来源与打分方式 | 四项拿不到时不要把它作为选型流程的一环 |

「明确不要做」这一列不是保守，而是**机会成本**：这些动作都要占平台侧人力，换来的东西在当下都有更便宜的做法。等 §5.6 的信号出现再投入，通常比现在投入更划算。

### 5.8 小结

> 本节小结：选型框架这个主题下，AI 真正改变的**唯一一条机制**是「填格子」的产能——它把候选扩列与对比表骨架的边际成本压到接近零，这也是本节离 L1 最近的方向（组件成熟，只差第三方生产案例，故记为 L2）。它**没有**改变的是格子里数字的来源与权重的授权。而加权求和（Score = Σ w_j × s_ij）对格子的可信度不做区分，于是产能提升的直接后果是**采集值与生成值混进同一张表**：总分看起来更精确，证据强度更低，且这个差别在表里看不出来。所以 AI 时代的选型工程，重点是把模型限制在「格子被填之前」（扩候选、补维度）与「格子被填之后」（找先例、查冲突）两侧；中间那一步——分数、权重、结论——必须有人和可追溯的来源。
>
> 💡 **思考锚点**：翻出你们最近一份选型矩阵，把每个格子标成「采集值」还是「生成值」——按 §5.3 的硬规则与 §5.8 的加权求和（Score = Σ w_j × s_ij），只要有一格是模型生成的，整张表的总分就成了证据与先验不可见的混合。再追问：这张表的权重那一列，写没写「谁定的、哪次会议、谁签字」（§5.6 第一条预测的成真信号）？
