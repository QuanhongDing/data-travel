## 1. 概念与定位

### 1.1 是什么

**学术定义**：自研 vs 采购（Make or Buy）决策是企业战略管理的经典问题。它源于 Williamson 的交易成本理论（Transaction Cost Economics, TCE）——企业决定是「自己生产」还是「从市场购买」某项产品 / 服务。Vladimir Protsenko（1960s）首次在企业战略层系统化该问题，Rein Peterson（1970s）提出 TCO（Total Cost of Ownership）框架。

**工程定义**：在数据架构师手里，自研 vs 采购决策是一套**「在『掌控感』与『效率』之间找平衡」的方法集**，包含五个核心要素：

1. **能力维度**：核心能力 vs 辅助能力。
2. **成本维度**：TCO 3 年 / 5 年计算。
3. **战略维度**：战略自主性 vs 供应商锁定。
4. **时间维度**：上线时间 vs 长期成本。
5. **风险维度**：技术风险 + 合规风险 + 业务连续性。

### 1.2 为什么需要

**业务 / 工程痛点**：

- **「伪自研」陷阱**：为了「掌控感」自研，结果只是「外壳套了一层的开源」——维护成本爆炸。
- **「盲目采购」**：所有都用 SaaS，结果供应商锁定 + 数据合规失控 + 成本失控。
- **「维护成本爆炸」**：自研组件维护团队人力 = 业务 3 倍，但没人评估。
- **「战略自主性误判」**：把非核心能力当核心能力，结果战略失焦。
- **「上线时间压力」**：因为「采购周期长」而自研，结果质量差、维护差。
- **「TCO 计算错误」**：只看初始成本，忽略 5 年 TCO。

**为什么是「资深架构师」核心能力**：

- P5/P6：写代码——关注「代码正确」。
- P7：模块——关注「模块设计合理」。
- P8：系统——关注「系统稳定」。
- **资深架构师 / 准资深架构师：关注「自研 vs 采购的全局最优 + 长期战略」——这是 P8 → 资深架构师的跃迁点**。

### 1.4 演进历程

- **1960s**：Vladimir Protsenko 提出 Make or Buy 决策。
- **1970s**：TCO（Total Cost of Ownership）框架（Rein Peterson）。
- **1980s**：Williamson 的交易成本理论（TCE）。
- **1990s**：企业 IT 领域 Make or Buy 决策普及（ERP / CRM 选型）。
- **2000s**：SaaS 兴起（Salesforce / Workday），「采购 vs 自研」再次升温。
- **2010s**：开源 vs 自研 vs SaaS 三方对比。
- **2020+**：云原生时代，「采购」从 SaaS 扩展到云服务（DB / Cache / MQ）。
- **2023-2025**：AI / LLM 时代出现新选项——基础模型 API（OpenAI / Anthropic）+ 垂直领域微调 + Agent 框架。

## 2. 核心原理

### 2.1 关键概念定义

- **Make or Buy（自研 vs 采购）**：企业决定「自己生产」还是「从外部购买」的决策。
- **Total Cost of Ownership（TCO）**：总拥有成本 = 初始成本 + 运营成本 + 维护成本 + 培训成本 + 机会成本 + 退役成本。
- **Net Present Value（NPV）**：净现值 = 未来现金流的折现值 - 初始投资。
- **Internal Rate of Return（IRR）**：内部收益率——使 NPV = 0 的折现率。
- **Return on Investment（ROI）**：投资回报率 = (收益 - 成本) / 成本。
- **Strategic Autonomy（战略自主性）**：核心能力不被供应商 / 开源社区「卡脖子」的程度。
- **Vendor Lock-in（供应商锁定）**：难以切换供应商的状态——切换成本极高。
- **Pseudo-Self-Built（伪自研）**：表面「自研」，实际「外壳套了一层开源」——无战略价值。
- **Core Capability（核心能力）**：构成业务差异化的能力（如推荐算法 / 风控模型）。
- **Non-core Capability（非核心能力）**：通用能力（如通用 CRUD / 通用 ETL）。
- **Time-to-Market（TTM）**：上市时间 / 上线时间。
- **Switching Cost（切换成本）**：从方案 A 切换到方案 B 的成本。
- **Open Source（开源）**：自研 / 采购的中间态——有源码但需自己运维。
- **Managed Service（托管服务）**：基于开源的商业托管（如 Confluent Cloud = Kafka 托管）。
- **Build-Operate-Transfer（BOT）**：建设-运营-转让模式（自研 + 后期采购）。
- **Make-Buy-Mix（自研-采购混合）**：核心自研 + 边缘采购的混合模式。
- **Build for Differentiation（差异化自研）**：自研核心能力，构建差异化。
- **Buy for Parity（采购追平）**：采购通用能力，追平对手。
- **Core-Edge-Spot（核心-边缘-机会）**：Gartner 决策框架。
- **Build vs Partner vs Buy**：三选项决策（自研 / 合作 / 采购）。
- **Make-or-Buy Decision Tree**：自研 vs 采购决策树（McKinsey 风格）。

### 2.2 数学 / 形式化基础

**TCO 计算**：

```
TCO_3yr = 初始成本 + Σ (年度运营成本 × 年份) - 残余价值
       = C_init + (C_op + C_maint + C_train) × 3 + C_opp + C_decom - V_residual
```

**NPV / IRR / ROI**：

```
NPV = -C_init + Σ (Benefit_t - Cost_t) / (1 + r)^t
ROI = (Total Benefit - Total Cost) / Total Cost × 100%
IRR：使 NPV = 0 的 r
```

**Payback Period（投资回收期）**：

```
Payback = C_init / (Benefit_per_year - Cost_per_year)
```

**Make-or-Buy Score（McKinsey 简化）**：

```
Score_Make = w1 × (Strategic Value) + w2 × (Capability Fit) + w3 × (TCO Advantage) + w4 × (Time-to-Market)
Score_Buy = w1 × (Vendor Reliability) + w2 × (TCO Advantage) + w3 × (Time-to-Market) + w4 × (Switching Cost Score)

Decision：
- 若 Score_Make > Score_Buy + 1.0 → 自研
- 若 Score_Buy > Score_Make + 1.0 → 采购
- 否则 → 混合（核心自研 + 边缘采购）
```

**风险调整 NPV**：

```
Risk-adjusted NPV = NPV × (1 - P_failure × Loss_factor)
其中 P_failure = 失败概率，Loss_factor = 失败时的损失比例
```

### 2.3 关键算法 / 方法

1. **TCO 计算**——总拥有成本。
2. **NPV / IRR / ROI**——财务量化。
3. **Decision Matrix + Sensitivity Analysis**——多准则打分。
4. **Core-Edge-Spot Framework**——Gartner 核心 / 边缘 / 机会。
5. **Build-Operate-Transfer（BOT）**——分阶段模式。
6. **Risk-adjusted Scoring**——风险调整打分。
7. **Monte Carlo Simulation**——不确定性分析。
8. **Make-or-Buy Decision Tree**——决策树。
9. **Strategic Capability Mapping**——战略能力地图。
10. **Vendor Lock-in Assessment**——供应商锁定评估。
11. **AI-assisted Make-or-Buy**——AI 辅助决策。
12. **Build-vs-Buy-as-Code**——决策即代码（2024+）。

### 2.4 与相邻概念的关系

- **自研 vs 采购 vs 选型**：选型是「在多个产品中选一个」，自研 vs 采购是「自建还是买现成」。
- **自研 vs 采购 vs 合作**：自研（自己建）/ 采购（买现成的）/ 合作（共建 / BOT）。
- **自研 vs 采购 vs 开源**：开源是介于自研与采购之间的中间态——有源码但需自运维。
- **自研 vs 采购 vs SaaS**：SaaS 是采购的现代形态——无需运维、按用量付费。
- **自研 vs 采购 vs 托管**：托管（如 Confluent Cloud）是采购 + 运维外包。

## 3. 设计模式与范式

### 3.1 主要模式

**模式 1：Core-Edge-Spot Framework（Gartner）**

| 类型 | 战略价值 | 推荐策略 |
| --- | --- | --- |
| **Core（核心）** | 业务差异化核心 | **自研**——掌控核心算法 / 数据 |
| **Edge（边缘）** | 必要但不差异化 | **采购 / SaaS**——如数据库、MQ |
| **Spot（机会）** | 暂时性机会 | **SaaS / 合作**——快速验证 |

**示例（智能体平台）**：
- Core：核心 Agent 编排逻辑、领域 RAG 策略 — **自研**。
- Edge：通用向量库、通用 LLM API — **采购 / SaaS**。
- Spot：临时 ChatOps 工具 — **SaaS**。

**模式 2：Make-or-Buy Decision Tree（McKinsey）**

```
需要的能力是什么？
        │
        ├── 是业务核心差异化？
        │       │
        │       ├── 是 + 团队有能力 + 长期投入？
        │       │       └── 是 → 自研
        │       │
        │       ├── 是 + 团队没能力？
        │       │       └── 是 → 采购 + 培养团队（双轨）
        │       │
        │       └── 否 → 进入下一层
        │
        ├── 上线时间紧迫？
        │       │
        │       ├── 是 → 采购 / SaaS（先上线再说）
        │       └── 否 → 进入下一层
        │
        ├── 采购方案成熟？
        │       │
        │       ├── 是 + 切换成本低 → 采购
        │       ├── 是 + 切换成本高 → 自研（BOT）
        │       └── 否 → 自研
        │
        └── 想平衡？
                └── 混合（核心自研 + 边缘采购）
```

**模式 3：Build-Operate-Transfer（BOT）**

| 阶段 | 时间 | 模式 |
| --- | --- | --- |
| Build（建设） | 0-6 个月 | 自研 + 第三方咨询 |
| Operate（运营） | 6-24 个月 | 团队独立运营 |
| Transfer（转让） | 24+ 个月 | 可移交到采购 / 混合 |

适用：核心能力初期自研，成熟后考虑采购。

**模式 4：Strategic Capability Mapping**

把能力按「战略重要性 × 团队能力」二维分类：

```
       战略重要性高
            │
  自研 + 投入 │ 培养 + 合作
            │
 ───────────┼─────────── 团队能力
            │
  采购 / 外包│ 渐进
            │
       战略重要性低
```

**模式 5：TCO 3 年 / 5 年 / 10 年对比**

| 时间维度 | 自研 | 采购 / SaaS |
| --- | --- | --- |
| 初始成本 | 高（人力 + 时间） | 低（订阅） |
| 运营成本 | 高（团队 + 维护） | 中（订阅升级） |
| 切换成本 | 高（迁移成本） | 中（迁移到其他供应商） |
| 长期 | 边际成本递减 | 边际成本恒定 |

→ 一般 3 年内采购 TCO 更低；5 年 + 自研 TCO 更优（视场景）。

**模式 6：Risk-adjusted Make-or-Buy**

考虑风险的决策：
- 自研失败概率 30% × 损失 50% = 风险调整 0.15。
- 采购失败概率 10% × 损失 20% = 风险调整 0.02。
- 即使自研 NPV 更高，风险调整后采购仍胜。

**模式 7：Pseudo-Self-Built（伪自研）检测**

伪自研特征（同时满足 ≥3 项即伪自研）：
- 80%+ 代码是开源复制。
- 仅做薄薄一层 UI / API 包装。
- 没有真正掌握核心算法。
- 团队无法独立维护（靠原社区）。
- 战略价值低（业务不依赖）。

**模式 8：Vendor Lock-in 评估**

| 维度 | 锁定风险 | 检测 |
| --- | --- | --- |
| 数据迁移 | 高 | 数据格式专属 |
| API 兼容 | 高 | 私有 API |
| 工具链 | 中 | 专有工具 |
| 培训 | 中 | 专有技能 |
| 社区 | 低 | 标准化 |

→ 锁定风险高 → 自研（BOT）。

**模式 9：Open Source as Middle Ground**

开源是「自研 + 采购」的中间态：

| 维度 | 开源 | 自研 | 采购 |
| --- | --- | --- | --- |
| 源码可见 | ✅ | ✅ | ❌ |
| 自主可控 | 中 | 高 | 低 |
| 运维成本 | 中 | 高 | 低 |
| 切换成本 | 中 | 高 | 低 |
| 战略价值 | 中 | 高 | 低 |

**模式 10：Make-Buy-Mix（混合模式）**

按组件分层决策：

| 组件 | 决策 | 理由 |
| --- | --- | --- |
| 核心 Agent 框架 | 自研 | 业务差异化 |
| 向量库 | 采购（Pinecone / Milvus 托管） | 通用能力 |
| LLM API | 采购（OpenAI / Anthropic） | 通用能力 |
| 领域微调 | 自研 | 业务差异化 |
| 监控 / 告警 | 采购（Datadog / Grafana Cloud） | 通用能力 |
| 编排调度 | 自研 | 业务差异化 |

### 3.2 适用场景决策表

| 场景 | 推荐策略 | 理由 |
| --- | --- | --- |
| 核心算法 / 业务差异化 | 自研 | 战略自主 |
| 通用 CRUD / ETL | 采购 / SaaS | 追平对手 |
| 上线时间紧迫 | 采购 / SaaS | 速度优先 |
| 团队没能力 + 核心 | 采购 + 培养 | 双轨 |
| 长期（5+ 年）核心能力 | 自研 | TCO + 战略 |
| 短期机会 / 验证 | SaaS | 试错 |
| 合规要求高 | 自研 / 私有化 | 数据可控 |
| 预算紧 | 采购 / 开源 | 成本优先 |

### 3.3 反模式与陷阱

1. **「伪自研」**：外壳套开源，无战略价值。**严格检测 5 项特征**。
2. **「盲目采购」**：所有都 SaaS，结果供应商锁定 + 数据合规失控。**核心能力必须自研**。
3. **「TCO 计算错误」**：只看初始成本。**3-5 年 TCO 必须**。
4. **「战略自主性误判」**：把非核心当核心，结果失焦。**用 Core-Edge-Spot 框架**。
5. **「采购周期长就自研」**：因为采购慢就自研。**评估自研周期是否更长**。
6. **「忽视维护成本」**：自研初期成本低，3 年后维护成本爆炸。**TCO 必须含人力**。
7. **「过度核心化」**：什么都自研。**通用能力坚决采购**。
8. **「不培养团队」**：采购后团队永远学不会。**采购 + 培养并行**。

## 4. 工程实现

### 4.1 落地步骤

**Step 1：识别候选能力 / 组件**

- 列出所有需要的能力 / 组件。
- 按 Core / Edge / Spot 分类。

**Step 2：评估战略价值**

- 业务差异化重要性（1-5）。
- 长期价值（1-5）。

**Step 3：评估团队能力**

- 当前能力（1-5）。
- 学习能力（1-5）。
- 培养周期（人月）。

**Step 4：TCO 3 年 / 5 年计算**

| 维度 | 自研 | 采购 / SaaS |
| --- | --- | --- |
| 初始成本 | 人力 / 时间 | 采购费 / 集成费 |
| 年度运营 | 团队人力 + 维护 | 订阅费 |
| 培训 | 培训费 | 培训费 |
| 切换 | 未来切换成本 | 切换成本 |
| 机会成本 | 业务不能用 | 业务不能用 |

**Step 5：风险评估**

- 自研风险：技术风险 + 团队风险 + 维护风险。
- 采购风险：供应商风险 + 合规风险 + 锁定风险。
- 用 FMEA / Risk Register（详见 §04）。

**Step 6：决策矩阵 + Sensitivity Analysis**

- 多准则加权打分。
- Sensitivity：TCO 波动 / 权重波动 → 决策稳健性。

**Step 7：决策 + ADR**

- 选 make / buy / mix。
- 写 ADR（含 TCO + 决策矩阵）。
- 强制 Owner + 复盘日期。

**Step 8：执行 + 监控**

- 自研：Sprint 计划 + 里程碑。
- 采购：POC + SLA 谈判 + 合同。
- 监控：TCO 实际 vs 预算。

**Step 9：复盘**

- 半年 / 1 年复盘：决策是否正确？
- TCO 实际 vs 预算。
- 更新 Make-or-Buy 决策经验库。

## 6. 落地实践

### 6.1 真实案例

**案例 1：阿里巴巴的数据中台自研**

阿里在 2015 年决定自研数据中台（OneData / OneID / OneService）：

- **战略价值**：核心差异化 → 自研。
- **团队能力**：阿里数据团队规模大 + 能力强 → 自研。
- **TCO 3 年**：自研 5 亿 vs 采购 3 亿 → 自研贵 67%，但战略价值更高 → 选自研。
- **结果**：数据中台成为阿里电商 / 金融 / 云的核心竞争力。

**案例 2：字节跳动的向量库选型**

字节跳动 2023 年向量库选型：

- **战略价值**：RAG 基础设施 → 中等。
- **TCO 3 年**：自研 1.5 亿 vs 采购 Pinecone 0.6 亿 → 自研贵 150%。
- **Vendor Lock-in**：Pinecone 高 → 自研（基于 Milvus 二次开发）。
- **决策**：混合——核心引擎自研 + 边缘 API 采购。

**案例 3：Netflix 的 Kafka 选型**

Netflix 选型 Kafka 时：

- **战略价值**：核心数据管道 → 高。
- **团队能力**：有 Kafka 专家 → 自研运营。
- **采购方案**：Confluent Cloud 托管 → 评估 TCO。
- **决策**：混合——核心自运维 + 边缘业务用 Confluent Cloud。

**案例 4：OpenAI 的自研 vs API（反面案例）**

OpenAI 自 GPT-3 起选择 API 优先：

- **优势**：快速上线 + 商业化快。
- **劣势**：被开源追赶 + 客户锁定 OpenAI。
- **后续**：2024 年推出 GPT Store + 微调，让客户「自建 + 采购」混合。

### 6.2 踩坑与经验

1. **「伪自研」**：外壳套开源，无战略价值。**严格检测 5 项特征**。
2. **「盲目采购」**：所有都 SaaS，结果锁定 + 合规失控。**核心必须自研**。
3. **「TCO 错误」**：只看初始成本。**3-5 年 TCO**。
4. **「战略自主性误判」**：把非核心当核心。**用 Core-Edge-Spot**。
5. **「采购慢就自研」**：因为采购慢就自研。**评估自研周期是否更长**。
6. **「忽视维护成本」**：自研初期便宜，3 年后爆炸。**TCO 含人力**。
7. **「过度核心化」**：什么都自研。**通用能力坚决采购**。
8. **「不培养团队」**：采购后团队永远学不会。**采购 + 培养并行**。

### 6.3 落地路径（0→1, 1→10, 10→100）

**0→1（10 人以下团队）**：

- Core-Edge-Spot 分类；
- 核心能力自研；
- 边缘能力采购 / SaaS；
- TCO 3 年计算。

**1→10（10-50 人）**：

- 引入 Risk-adjusted NPV；
- Sensitivity Analysis；
- Make-or-Buy Decision Tree；
- BOT 模式（核心能力分阶段）；
- ADR 强制。

**10→100（50+ 人）**：

- 组织级 Make-or-Buy 战略；
- AI 辅助决策；
- Decision Intelligence Platform；
- Build-vs-Buy-as-Code；
- 季度复盘。

### 6.4 ROI 评估

**直接收益**：

- 自研 vs 采购最优决策 → 节省 20-40% TCO；
- 战略自主性提升 → 长期竞争优势；
- 伪自研识别 → 节省维护成本 30-50%；
- 决策速度提升 → 30%。

**间接收益**：

- 组织战略对齐；
- 核心能力沉淀；
- 避免供应商锁定。

**成本**：

- 决策时间：每决策 +2-3 小时；
- TCO 计算：1-2 人天 / 决策；
- 培训成本：内部 Workshop。
