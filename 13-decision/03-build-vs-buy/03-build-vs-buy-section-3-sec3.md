## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

自研 vs 采购的模式常被讲成「按场景挑一个方法」：能力重要就用 Core-Edge-Spot 分层，金额大就用 TCO，怕被锁就用退出成本表。这个讲法漏掉了真正起作用的东西——**方法之间的差异不在精度，而在它把哪一部分成本划在了记账边界之外**，而结论偏向哪一边由边界决定，不由计算精度决定。

在本主题下，这条「边界」落到一条很具体的约束上：**这项成本随什么增长**。外购的成本几乎总是随用量线性增长的（订阅、按吞吐计费、按席位），自研的成本是先付一大笔固定投入（人力 + 时间），此后边际成本随用量摊薄。两条曲线斜率不同，必然有交叉点，但交叉点的位置由**你的用量何时涨到把固定成本摊平**决定，而不是由年限决定。

由此推出三个反直觉的结论，它们分别是三种最常见的误判：

- 「长期就该自研」不成立——如果这项能力的半衰期（范式多久换一代）短于回本期，一份按 5 年摊销的自研方案会在第 3 年被推倒重写，摊销期内的成本优势根本来不及兑现。
- 「哪边便宜选哪边」不成立——出事时谁承担责任、数据出境谁背书，这类项不参与比价，只能作为硬约束先筛掉候选。
- 「先自研，不行再换采购」不成立——可逆性不是自然存在的，它要被设计进决策结构里（分阶段、可停、可导出），否则「换」的代价通常等于重做。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 成本函数形状（随用量 / 随人头 / 随组件数增长） | 决定自研的规模阈值在哪 | 「自研长期更便宜」不是普遍规律，只在用量增长足够快时成立 |
| 能力半衰期 vs 回本期 | 决定摊销假设是否成立 | 「长期（5 年+）核心能力就自研」——年数不是理由，回本期长于半衰期就摊不平 |
| 可逆性（走一半能不能停、停下来付什么） | 决定要不要用 BOT / 混合把一次性决策拆成分阶段决策 | 「不行再换」——退出成本不写出来，它就等于无穷大 |
| 责任与合规归属 | 决定哪些能力必须自持、不进成本比较 | 「哪边便宜选哪边」——这类项一旦进比价，就会被便宜的一方赢走 |
| 差异化贡献（是否出现在客户为什么选我们的理由里） | 决定自研能不能回本 | 「技术团队觉得这块很核心」——内部价值感不是客户付费理由 |
| 决策可审计性（结论能否被复盘与追责） | 决定该用哪一档方法（直觉 / TCO / 概率化） | 「小决策要快」——受监管组织里无法复盘的决策等于没做 |

顺序也是约束的一部分：**战略判据决定候选集合，成本判据决定集合内的选择**，颠倒过来就会用省钱的理由砍掉必须自持的能力（§7.6「选型矩阵与组合」的常见组合段给出了同一条原则，可对照阅读）。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 判据分层类：Core-Edge-Spot 与 Strategic Capability Mapping

**被什么约束逼出来**：需要决策的能力有几十项，而团队的时间只能投在少数几项上——必须先分类，再分配。

**结构**：

```text
Strategic Capability Mapping（战略重要性 × 团队能力）与三档默认策略
                    团队有能力            团队没能力
                ┌──────────────────┬──────────────────┐
   战略重要性高 │ 自研 + 持续投入   │ 培养 + 合作互助   │  → Core：默认自持
                ├──────────────────┼──────────────────┤
   战略重要性低 │ 采购 / 外包       │ 渐进（先用托管，  │  → Edge：默认采购
                │                  │ 观察是否真需要）   │  → Spot：默认 SaaS
                └──────────────────┴──────────────────┘

Core-Edge-Spot 三档与缺省动作
  Core（客户为什么选我们的理由之一） → 自研，且允许超支
  Edge（必要但不差异化，如数据库 / MQ）→ 采购 / SaaS
  Spot（阶段性机会）→ SaaS 或合作，快速验证后可弃

示例（智能体平台）
  Core = 核心 Agent 编排、领域 RAG 策略 → 自研
  Edge = 通用向量库、通用 LLM API      → 采购 / SaaS
  Spot = 临时 ChatOps 工具             → SaaS

两轴的接入点：能力地图（Mapping）提供分类，三档提供缺省策略。
```

**为什么这样设计有效**：因为判据是「这项能力是否出现在客户选择我们的理由里」而不是金额，所以它能在没有任何财务数据的情况下把能力表一次切成三档，并给出各档的默认动作——资源分配从「逐项讨论」变成「按档执行」，讨论成本被压到只在跨档争议处发生。

**代价**：它不产出金额。三档的输入里没有任何一条成本数据，所以它只能回答「谁来付、付多久」，回答不了「贵多少」；落到预算上时，Core 档的支出没有上限可依，只能靠差异化换来的溢价兜底——溢价若拿不出客户证据，Core 就是一个没有对标的价格。另一个代价是分类依赖业务侧持续参与：能力地图记录的是上一轮共识，业务漂移时它不会报错，只会过期。这两条机制（记账边界与系统性偏差方向）的展开见 §7.3.1。

**失效点**：当「差异化」由技术团队自评、而不是由客户选择证据（客户为什么选我们、同行上线了几家）支撑时，Edge 会被大量误判为 Core——每一项能力都能找到一个「这很重要」的理由。此时框架从「分层」反转成「全都自研」的许可证，因为它唯一的输入被判据提供方自己定义。

**真实使用**：三档分法在业界广泛流传并常被记在分析机构名下，但其原始出处与年份难以给出单一可引文献（【经验】）。可按 core / edge / spot capability mapping 检索相关机构的公开材料与客户选择证据自行核验。核验自己组织的分类是否可信，只需做一件事：把每个 Core 能力对照「客户为什么选我们」的原文，看这句话里是否真的提到它。

#### 3.2.2 顺序过滤类：Make-or-Buy Decision Tree

**被什么约束逼出来**：常规决策占绝大多数，而逐项做财务模型的时间成本经常超过两个方案之间的金额差异。

**结构**：

```text
按硬约束逐层淘汰（每层只问可核验的事实）
  第 0 层（硬约束，先筛）这件事违反责任与合规归属吗（谁承担责任、数据出境谁背书）？
      是 → 自持（私有化 / 自研），不进成本比较，也不再往下走
      否 → 进入 Q1
  Q1 这项能力是否出现在「客户为什么选我们」的理由里？
      否 → Q2
      是 → Q1b 团队上一次交付同类系统是什么时候（能力有无证据，不是有没有人）？
              有证据 → 自研（核心能力，允许超支）
              无证据 → 采购 + 培养并行（双轨），并把「不培养」列为禁止项
  Q2 上线时间窗是否短于最短的自研交付期？
      是 → 采购 / SaaS（先上线，同时记录这次妥协的范围）
  Q3 采购方案的退出成本能否估出来（数据能否导出、接口是否标准、技能能否重建）？
      能估且可接受 → 采购
      估不出或等于重做 → 自研，或改用 BOT / 混合把它改成可停的决策
  Q4 两边的 TCO 差异是否小于评估本身的人力成本？
      是 → 按第 0 层与 Q1–Q3 的结论执行，不做 TCO
```

层序不是风格问题，它决定结论：合规项若排在差异化之后，一项「既差异化、又承载合规责任、且团队没有同类交付记录」的能力会先走 Q1b 落到「采购 + 培养」，等于把必须自持的合规责任买了出去；把它提到第 0 层，它就在任何成本比较之前被筛掉。这一层序与 §7.5 第 0 层、§7.8「链条最前面是责任与合规归属」一致。

**为什么这样设计有效**：因为第 0 层只淘汰「承载合规责任」这一小类能力，而 Q1 问的差异化对大部分常规能力的答案就是「否」，所以大量决策在前两轮就结束，不会进入成本比较；同时每一层只接受可核验的事实作为证据，避免把「感觉」写进流程。

**代价**：树的顺序本身就是隐含权重——先问的问题拥有否决权。把「上线时间紧迫」提到「是否差异化」之前，时间压力会直接变成决定性因素；把 TCO 放在 Q4，意味着它永远最后才发生作用。第 0 层拿到否决权是刻意的（合规项不该参与比价），但它同时意味着误判不可逆：一项能力一旦被认定承载合规责任，就被永久挡在成本比较之外，纠正它要推翻整条分支而不只是改一个数。树的维护成本也真实存在：阈值（最短交付期、可接受的退出成本）必须定期重估。

**失效点**：当每层的判据本身不可核验（「团队有能力吗」没有任何交付证据支撑）时，决策树会退化成把直觉分步写下来——流程看起来严谨，结论与拍脑袋完全一致，而组织以为自己已经做了分析。

**真实使用**：本书 §7.5 给的是同一条判据链的展开——它同样以合规硬约束为第 0 层、以差异化判据为第 1 层，并为每一层的阈值附上依据或判定方法（本节这棵树只是把中间几层压缩成最少的四问）。案例侧的对照是：Netflix 自建流批平台时把「商业 / 开源方案存在真实能力缺口」与「规模已越过经济性阈值」设为两个必须同时满足的判据，任一不满足就不自建（见 §6 案例；该案例的一手材料按「Netflix Tech Blog，2019 年起」区间标注，可按 Keystone 流批一体平台在该博客检索核对，具体文章标题与发布时间请以该博客当前版本为准，【经验】）。

#### 3.2.3 成本记账类：TCO 3 / 5 / 10 年对比与 Risk-adjusted Make-or-Buy

**被什么约束逼出来**：首期价格与最终花费差距很大，运营、维护、培训、退役这些项不写进决策就会被忽略。

**结构**：

```text
TCO 记账边界
  TCO_n = C_init + Σ_{t=1..n} (C_op + C_maint + C_train)_t + C_opp + C_decom − V_residual
  自研曲线：C_init 高，C_op 随用量摊薄（边际成本递减）
  采购曲线：C_init 低，C_op 随用量线性增长（按吞吐 / 席位计费）

交叉点在哪里（推导链）
  设自研 C_fixed + c_m × 用量，采购 c_b × 用量，且 c_b > c_m
  令两者相等 → 交叉用量 = C_fixed / (c_b − c_m)     【推算】
  结论：交叉点的位置由「用量何时涨到该值」决定，与年限无关。
  年限只是用量的代理变量——用量不涨的团队，等 10 年也等不到交叉点。

Risk-adjusted Make-or-Buy
  Score = NPV × (1 − P_failure × Loss_factor)
  可核验的 P_failure 来源（不是财务模型）：同类系统最近三次交付按期完成几次、
  团队上一次做同等复杂度的事花了多久、依赖的外部组件是否仍在活跃维护。
```

**为什么这样设计有效**：因为 TCO 把未来现金流项显式列出来，所以「首期便宜」不再等于「总花费低」；因为风险调整把失败概率乘进结果，所以它至少强迫决策者在纸上写下 P_failure 这个数——写下来的数可以被质疑，藏在直觉里的数不能被质疑。

**代价**：TCO 的边界是现金流，因此它记不下「自研失败后团队士气与招聘信誉的损耗」这类不进现金流表的成本；这些项恰恰多数落在自研一侧。于是 TCO 在自研失败率高的场景下会系统性偏向自研：所有可量化的项都算进去了，唯独最大的风险项没算。风险调整的代价是它要求两个都很难估的参数（P_failure、Loss_factor），并把整个结论押在它们的乘积上。

**失效点**：当 P_failure 是从「希望」里取的值而不是工程证据（最近三次交付的记录）时，风险调整会反转成一种专业外观的背书——它对输入极端敏感，而最不可核验的恰恰是输入本身。可操作的补救是把期望值与最坏情况并列呈现，让决策者在两个数上分别表态，而不是只在一个加权数上表态。

**真实使用**：使用侧的实例见 §6 案例——Netflix 把自建判据从「技术偏好」换成「能力缺口 + 规模阈值」，并把成本结构的反转（规模越过阈值后自建反而更省）写进决策依据（见 §6 的 Netflix 案例；其一手材料在该处同样按「Netflix Tech Blog，2019–2024」区间标注，可按 Keystone 检索核对，具体标题与发布时间以该博客当前版本为准，【经验】）；另一侧是 §6 的 Snowflake 案例里的「按用量付费 + 零运维」主张，它对应的正是把运营与维护从买方现金流里挪走的那条曲线。方法的思想来源：Coase 在《The Nature of the Firm》里把「企业为什么把一项活动内化」的判据定为「内化的组织成本低于市场交易成本」（【公开】Economica, 1937）；Williamson 沿这条线把它扩展为交易成本经济学（【公开】《Markets and Hierarchies》, 1975；《The Economic Institutions of Capitalism》, 1985）；把不确定性本身当作价值来源的实物期权思想见 Myers（【公开】Journal of Financial Economics, 1977）；IT 采购评估中的 TCO 记账法通常归于 Gartner 的系统化推广（【经验】1980 年代末，无单一可引原始文献）。

#### 3.2.4 中间态类：Open Source as Middle Ground 与 Make-Buy-Mix

**被什么约束逼出来**：既不想被单一供应商锁定，又没有能力（或没有必要）从零自建；而一个平台里核心组件与非核心组件本来就混在一起。

**结构**：

```text
开源作为中间态：把「源码可见」与「运维责任」拆开
  维度        开源        自研        采购
  源码可见    是          是          否（多为闭源）
  自主可控    中          高          低
  运维成本    中（自己运维）高         低（外包给供应方）
  切换成本    中          高          低
  战略价值    中          高          低

Make-Buy-Mix：把决策从系统级降到组件级
  ┌── 控制面（自建，握住不放）────────────────────────┐
  │ 指标定义与语义层 / 数据模型与口径规范 / 治理规则    │
  │ 特征：体量小、价值高、被锁代价极大                │
  └───────────────────────────────────────────────────┘
                 ▲ 语义映射（保持可迁移）
  ┌── 资源层（外购，按用量付费）──────────────────────┐
  │ 存储 / 计算 / 消息 / 通用向量库 / 通用 LLM API     │
  │ 特征：体量大、无差异化、专业方规模效应更强          │
  └───────────────────────────────────────────────────┘
  判据：这块能力被锁住之后，业务定义还拿得回来吗？

  组件级落法（智能体平台）
    核心 Agent 框架 / 领域微调 / 编排调度 → 自研（业务差异化）
    向量库（Pinecone / Milvus 托管）/ LLM API / 监控告警（Datadog / Grafana Cloud）
                                          → 采购（通用能力，供应方规模效应更强）
```

**为什么这样设计有效**：因为开源把源码可见与运维责任拆开了，所以它同时降低了锁定与自建成本，代价被明确标成「自己承担运维」；因为混合把决策从「整个系统」降到「逐个组件」，锁定的暴露面被压缩到少数几个组件上，而语义与口径这类小体量高价值的资产留在自己手里。

**代价**：开源的长期成本集中在自运维——安全补丁、版本升级、兼容性回归，是一条持续人力，它不出现在任何采购价里。混合模式的代价是要一直维护「边界」这份共识：边界一旦随组织变化漂移，就得重新开一轮同样的争论，而这种争论的成本与决策金额无关。

**失效点**：开源自身会反转：当上游项目失去活跃维护，而团队只做过「使用」没做过「发版」时，源码可见带来的自主可控会反转成「看得见但改不动」——因为改得动的前提是拥有构建、测试与发布的能力，而不是拥有源码。此时切换成本反而高于采购方案，因为系统已经架在一个私有分支上。混合模式的反转则出现在边界画错时：把口径与语义层放在外购工具里，锁定的代价会在下一次换供应商时一次性付清。

**真实使用**：Airbnb 的做法是把「控制面自建、资源层外购」作为明确分界线——指标定义与语义层自建并保持可迁移，存储与计算外购按用量付费（见 §6 案例；其一手材料按「Airbnb 工程博客，2019–2024」区间标注，可按 medium.com/airbnb-engineering 上的数据平台相关文章检索核对，具体文章标题与发布时间请以该博客当前版本为准，【经验】）。买方视角的对照案例是 Snowflake 的按用量付费与零运维叙事（见 §6 案例）。核验自己的开源中间态是否保住了自主可控，只需要问一句：上游今天归档，你多久能发出一个包含安全修复的自有版本。

#### 3.2.5 自持真伪类：Pseudo-Self-Built（伪自研）检测

**被什么约束逼出来**：组织对「自主可控」有诉求，而自研是唯一能在预算里表达这一诉求的形式，于是产生了只满足形式、不满足实质的「名义自研」。

**结构**：

```text
伪自研判定：不看代码来源比例，看交付链是否完整
  ① 上游归档后，团队能否独立发版？（有构建 / 测试 / 发布链路，且做过）
  ② 出现安全漏洞时，能否自行修复并回归？（不是等上游或社区）
  ③ 核心算法与关键路径是否由本方掌握？（能说清为什么这么设计，不只是能跑）
  ④ 团队能否在不咨询原作者的前提下定位生产问题？（有排障记录）
  ⑤ 这项能力是否出现在「客户为什么选我们」的理由里？（战略价值）

判定规则：①–④ 中任意两条不成立 → 视为名义自研（即使代码全是自己写的）；
         ⑤ 不成立 → 该能力不是核心能力，自研的边际收益接近零。

常见误判：把「代码里开源占比高」当作伪自研的证据。
  高比例复用是合法的工程手段，fork + 深度二开同样能通过 ①–④；
  反过来，只做了一层薄壳但生成了大量样板代码的项目，
  行数占比看起来「自研成分很高」，却通不过 ①–②。
  比例衡量的是「写了多少代码」，而不是「能不能独立发版」。
```

**为什么这样设计有效**：因为自主可控的实质是「上游停更后你还能不能自己发版」，所以把判据换成交付链上的可验证动作（发过版、修过 CVE、独立排过障）之后，判定不再依赖对代码行数的估算——后者既容易被稀释，也容易被误伤。

**代价**：做这条检查要付人际成本，它等于当面质疑一个团队的产出定性；不做则要在若干年后用维护人力付账——维护账单到来时，当初做决策的人通常已经不在这个团队。另一个代价是①–④都需要证据（发布记录、补丁记录、排障记录），没有留痕的组织做不了这项检查。

**失效点**：当判定被简化成单一比例阈值（例如「复用占比超过某个百分比即判伪自研」）时，它会反转成误伤——真正的伪自研靠样板代码能把比例洗得很低，而合法的深度二开会被误判为伪自研并被迫重写，重写的代价远高于它想避免的维护成本。机制是比例衡量的是代码来源，而风险来自交付能力的缺失，两者不是同一个量。

**真实使用**：这项检查在内部架构评审与开源合规审查中都会做，但形式差异很大（【经验】）。核验自己组织的最短路径是取最近一次上游破坏性变更（或高危 CVE）的时间点，看本方从获知到发版用了多久——这个时长就是自主可控的真实度量。

#### 3.2.6 锁定与退出类：Vendor Lock-in 评估与 Build-Operate-Transfer（BOT）

**被什么约束逼出来**：采购的真实代价不在签约那一刻，而在退出那一刻；而有些时候供应商能力尚未成熟，但业务必须先跑通。

**结构**：

```text
Vendor Lock-in 评估：把每一项折成「退出要多少人力月 / 多久」
  锁定类型        检测方法                          量化产物
  数据迁移        能否全量导出为开放格式              导出工时 + 数据体积 + 校验工时
  接口兼容        是否私有 API / 私有查询语言          重写调用点的数量
  工具链          是否专属 DSL / 专有调度器            重写作业的数量
  技能            技能是否只在对方平台上有价值          重新招聘 / 培训周期
  社区            依赖的生态是否标准化、有无等价开源实现  迁移到替代品的工时
  合同            最短期限、退出条款、数据返还约定      违约成本 + 数据交付时限
  → 每一项给出区间（哪怕很宽），不给区间的一项等于没有评估。

BOT（Build-Operate-Transfer）：把一次性不可逆决策拆成阶段决策
  Build     0–6 个月（【经验】区间）：自建，目标是跑通业务，不追求长期架构
  Operate   6–24 个月（【经验】区间）：团队独立运营，积累真实运维数据
  Transfer  24 个月之后（【经验】区间）：按事先约定的可验证条件
            决定「保留自持」还是「移交 / 替换」
  关键：转让条件必须可验证（如「单位成本低于 X」「上游已支持能力 Y」），
        否则 BOT 会退化成「既付了自建成本，又保持了对供应商的依赖」。
```

**为什么这样设计有效**：因为锁定成本是未来才付的，它天然不进 TCO 的当期现金流；把它单列成一张退出成本表，等于把「不可逆性」摆到决策桌上。BOT 的价值同理不在省钱，而在于它把一次性不可逆决策拆成几个可评估的阶段——每个阶段结束时都有一次真实的「还能停」的机会。

**代价**：锁定评估是纯人工成本，要读合同、做导出试验、估算技能重建周期；BOT 的代价是前 6–24 个月走的是自建的路，却没有自建带来的长期资产（除非阶段结束时真的选择自持），并且它需要事先谈成可验证的转让条件，而这类条款在供应商不成熟时往往谈不下来。

**失效点**：锁定评估自身会反转成形式：当它只列维度不给数字（「数据迁移风险：高」）时，它无法改变任何结论——因为决策者在缺少金额时会退回到采购价那一个数，而「高」不是一个可以比较的量。修法是把每一项折成区间，哪怕区间很宽。BOT 的反转点是转让条件不可验证：一旦条件写成「成熟后移交」，它就会变成一条永远不触发的条款，BOT 于是只剩下了自建的成本与供应商依赖的双重负担。

**真实使用**：BOT 在供应商能力未成熟、但业务窗口不容等待的场景中被采用，工程领域常见于平台建设与外包运营（【经验】）；此类合同的成败几乎完全取决于转让条款是否可验证。锁定评估的核验方法是做一次真实的退出演练：把数据导出一次、按目标格式重建一次，看实际用了多久——演练的工时就是最诚实的退出成本。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 核心算法 / 业务差异化能力 | 自研（Build for Differentiation） | 采购会把差异化交给供应方的路线图，你的溢价变成别人的功能 | 它是否出现在「客户为什么选我们」的理由里 |
| 通用 CRUD / 通用 ETL | 采购 / SaaS（Buy for Parity） | 自研只能追平对手，无法拉开差距，却要长期付维护人力 | 自研能不能说出一个客户会因此付费的点 |
| 上线时间窗短于最短自制期 | 采购 / SaaS | 自研会把时间压力转成质量债，且债在长期才显形 | 最短自制交付期（有交付记录支撑的那个数） |
| 团队没做过 + 核心能力 | 采购 + 培养（双轨） | 只采购则团队永远学不会，只自研则失败概率极高 | 上一次交付同类系统是什么时候 |
| 长期（5 年+）核心能力 | 自研（前提：回本期短于能力半衰期） | 年限本身不是理由：半衰期短于回本期时，摊销期内的优势兑现不了 | 这项能力的范式大约几年换一代 |
| 短期机会 / 需要验证 | SaaS | 自研的固定投入在验证阶段无法回收 | 验证成功与否多久能知道 |
| 合规要求高 / 责任不可外移 | 自研或私有化部署 | 出事时谁担责、数据出境谁背书，这类项不进成本比较 | 有没有外部机构要求你自证数据边界 |
| 预算紧 | 采购 / 开源自运维 | 自研是固定成本前置，预算紧时最容易中途停摆 | 预算能否覆盖到第一个可用版本之后 |
| 供应商能力强 + 退出成本可估且可接受 | 采购 + 定期退出演练 | 自研的重复建设在供应商已成熟时收益趋零 | 导出演练实际花了多久 |

最常被误选的一对是**自研与开源自运维**，两个方向都会错。把开源当采购用（以为「反正是公开的、不用管」），结果是自运维这条持续人力没有出现在任何预算表里，三年后账单以维护团队的形式到来；把开源当自研用（直接 fork 出长期私有分支），结果是既付了自研的维护成本，又失去了上游修复带来的收益，且切换成本比纯采购更高，因为已经有下游绑在私有分支的方言上。判别只需要问一句：**你打算跟上游多久**——跟得紧就用它的接口习惯换低成本，跟不紧就要接受自己发版的全套工程负担。

### 3.4 组合模式：真实系统不会只用一种

**组合一：Core-Edge-Spot + TCO**。职责边界：Core-Edge-Spot 回答「哪些能力必须自持」，TCO 只在它划出的边缘区里比成本。运维代价：能力地图要有人持续更新——它记的是上一轮共识，业务漂移时不会报错，只会让三档分类停在过期的那一版（同一维护机制的展开见 §7.6 常见组合段）。适合规模：能力项达到几十项量级、且每年有新增能力的组织（【经验】量级）；能力项很少时，分类的维护成本高于它带来的秩序。

**组合二：Make-or-Buy Decision Tree + Risk-adjusted NPV**。职责边界：决策树负责把候选按硬约束快速筛到少数几个，风险调整 NPV 只在这少数几个之间做概率化比较。运维代价：P_failure 必须每次重估并留下出处，否则整条链的专业性都挂在一个没人核验的输入上。适合规模：单次金额大到值得做概率化。例外：失败后果不可用金额表达（监管处罚、信任损失）的项目不适用这条组合，这类项要先按责任与合规归属筛掉，再谈金额。

**组合三：Make-Buy-Mix + Vendor Lock-in 评估**。职责边界：混合把决策降到组件级，锁定评估只对少数被外购的组件做退出成本量化（全部组件都评估等于没有评估）。运维代价：边界要一直维护，且每次换组件都要重跑一次退出演练。适合规模：平台从单点试点扩到多业务域（3 个及以上）、外购组件数超过十个的组织（两条线均为【经验】阈值：域数与组件数同时上台阶之后，边界这份共识的维护成本才被摊薄）。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 伪自研 | 上游归档后发不出自己的版本；安全漏洞要等社区 | 既付了自研的固定与维护成本，又没有拿到自主可控 | 组织对自主可控有诉求，而自研是预算里唯一能表达它的形式 | 按交付链 ①–④ 判定，不以代码来源比例判定；判为核心能力才自研 |
| 盲目采购 | 全部能力都用 SaaS；数据导出要提工单，格式不开放 | 供应商锁定与合规失控同时发生，退出成本高到等于无法退出 | 采购是唯一能在一个季度内交付的路径，交付压力压过了边界判断 | 核心能力与合规相关能力必须自持；其余采购前先做一次导出演练 |
| TCO 计算错误 | 决策材料里只有首期价格与年度订阅费 | 结论由被漏掉的项决定，而不是由被算进去的项决定 | 首期价格是最容易拿到的数字，其他项要跨部门问 | 3–5 年 TCO 必做，并把「失败时进不进现金流表」逐行问一遍 |
| 战略自主性误判 | 能力地图上绝大多数能力都被标为 Core | 资源被摊薄到每一项上，真正的核心能力反而得不到投入 | 「差异化」由技术团队自评，缺少客户选择证据 | 用「客户为什么选我们」的原文校验每个 Core；Core 占比应明显低于一半，超过三分之一即逐条复验（【经验】阈值） |
| 采购周期长就自研 | 立项理由写的是「等采购不如自己做」 | 用更长的自制周期换一个更短的等待，且换来了一项长期维护负债 | 采购流程的等待是可见的，自研的工期风险是不可见的 | 先估最短自制交付期，再与采购周期比；两者接近时优先采购 |
| 忽视维护成本 | 自研立项的成本表里只有建设期人力 | 三年后维护人力成为固定支出，且无人为它做过预算 | 建设期有明确交付物，维护期没有里程碑 | TCO 必须含运维与升级人力，并按能力项列出人头 |
| 过度核心化 | 什么都自研，连通用组件也自己写 | 通用能力上的投入无法形成差异化，却持续挤占核心能力的资源 | 自研在组织内更容易立项，也更容易展示技术产出 | 通用能力坚决采购；每新增一个自研项，要求它说出一个客户会付费的理由 |
| 不培养团队 | 采购了三年，团队仍然只会点界面；出问题只能提工单 | 采购从「买能力」退化成「租能力」，议价能力随时间下降 | 培养不产出即时交付物，在交付压力下总被推迟 | 采购 + 培养并行；把「能否独立定位一次生产问题」设为培养的验收条件 |

三个最危险的，按暴露方式不同：

**伪自研**最贵。它在生产中的暴露方式是上游停更或出现高危漏洞的那一刻：团队第一次需要自己发版，才发现构建、测试、发布三条链路从没完整跑通过，于是要么临时外购、要么紧急找外包——此前付掉的自研成本只买到一个名义上的自主可控。

**忽视维护成本**最普遍。它的暴露方式不是一次事故，而是第三年预算表上多出来的一排人头：建设期有交付物、有里程碑、有验收，维护期什么都没有，所以它从不立项，也从不进成本表——决策者以为自己在比较「建设成本 vs 订阅费」，实际比较的是「建设成本 vs 全部成本」，而漏掉的项几乎都落在自研一侧，偏差方向是系统性的。

**战略自主性误判**最隐蔽。它在生产中的暴露方式是「每个项目都很忙、却没有一项拉开差距」：既然半数以上的能力都挂了 Core 标签，资源就只能平均分配，考核上每一项都在推进，几年后回看却发现找不到一项客户因此付费的能力。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的。用量、组织规模或监管环境跨过某个阈值时，原来正确的模式会变成错的。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 用量从「稳定」→「持续增长」 | 采购 / SaaS | 线性计费随用量上涨，而自研的固定成本在同一段用量上逐渐被摊平 | 对高用量组件评估自研，其余保留采购 | 迁移期要双轨运行，两个方案的成本同时发生 |
| 单点试点 → 多业务域推广 | 单点采购 | 每多一个业务域就多一份订阅与一份集成，复购成本按域叠加 | Make-Buy-Mix（控制面自建 + 资源层外购） | 需要先统一语义层，否则外购的资源层无法共用 |
| 决策从部门级 → 组织级 | 直觉 / 单点 TCO | 一次误判的影响面从一个团队扩大到多个团队，无法用事后沟通弥补 | Risk-adjusted NPV + 敏感性分析 | 要求历史 ADR、合同、TCO 表可取齐，取证成本前置 |
| 出现监管 / 审计要求 | 采购优先 | 无法自证数据边界与计算依据 | 合规相关能力改自持（自研或私有化） | 迁移数据与重建审计留痕，历史部分往往补不回来 |
| 供应商能力从「不成熟」→「成熟」 | 自研 / BOT | 自建维护成本照付，而市场方案已经追平甚至超过自建能力 | 供应商评估 + 逐步替换；BOT 进入 Transfer 阶段 | 替换窗口期要双轨，且要处理私有分支上的下游依赖 |
| 能力半衰期缩短（范式一年一变） | 长期自研摊销 | 摊销期没走完就要重写，成本优势兑现不了 | 采购 / 开源自运维（把重写风险转移给上游） | 语义与口径这类不可迁移的资产要先摘出来 |
| 团队从「没做过」→「有交付记录」 | 采购 + 培养 | 双轨的人力成本已经付过一轮，继续双轨等于重复付费 | 核心能力转为自研，非核心能力退出双轨 | 需要把培养期的产出固化成可复用的组件，而不是留在个人经验里 |

### 3.7 自检清单

- [ ] 决策材料里出现的每一个金额，是否都标了它的档位（实测 / 推算 / 经验）与出处？
- [ ] TCO 表里，是否逐行问过「这一行如果失败，成本进不进这张表」？进不去的行就是缺的那一项。
- [ ] 立项理由里写的年限，是否与这项能力的半衰期做过比较？
- [ ] 「差异化」这个判断，能否引用「客户为什么选我们」的原文，而不是内部评价？
- [ ] 能力地图上 Core 档的条目数占比多少？超过三分之一（【经验】阈值）时，是否逐条核验过？
- [ ] 这次采购的退出成本有没有数字（导出工时、重写调用点数量），还是只有「高 / 中 / 低」？
- [ ] 是否做过一次真实的导出演练，而不是只看文档说支持开放格式？
- [ ] 自研项的维护人力有没有写进预算，并明确到人头与年度？
- [ ] P_failure 的取值来自交付记录，还是来自「应该没问题」？
- [ ] 上游项目若明天归档，本团队多久能发出一个包含安全修复的自有版本？
- [ ] 「采购 + 培养」里的培养，有没有可验收的产出（独立定位一次生产问题），还是只有培训计划？
- [ ] 这次决策的结论与依据，半年后能否被第三方按同一份材料复现？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 能力构成客户选择理由 | 自研（Build for Differentiation） | 只有差异化项上的投入能回本 |
| 通用能力、需追平对手 | 采购 / SaaS（Buy for Parity） | 自研的边际收益趋零，维护成本照收 |
| 用量会持续增长、组件复用度高 | 对高用量组件评估自研 | 固定成本被用量摊平，交叉点会到来 |
| 能力半衰期短于回本期 | 采购 / 开源自运维 | 摊销期走不完就重写，成本优势兑现不了 |
| 责任与合规不可外移 | 自持（自研 / 私有化） | 这类项不参与比价，只能作为硬约束 |
| 供应商未成熟但业务窗口不等人 | BOT（转让条件必须可验证） | 把一次性不可逆决策拆成可停的阶段决策 |
| 平台内核心与非核心组件混合 | Make-Buy-Mix（控制面自建 + 资源层外购） | 把锁定暴露面压缩到少数组件 |
| 外购组件多、退出成本不明 | Vendor Lock-in 评估 + 退出演练 | 把未来才付的钱搬到决策桌上 |
| 承认自己可能算错 | Risk-adjusted NPV + 敏感性分析 | 强迫把 P_failure 写下来接受质疑 |

> 本节小结：本主题下决定模式选择的唯一那条约束是**成本函数形状与能力半衰期的相对关系**——外购按用量线性计费、自研先付固定成本再摊薄，所以自研是否正确取决于用量会不会长到把固定成本摊平、以及这项能力能不能撑到那一天；差异化判据不参与这个比较，它只决定候选集合，顺序颠倒就会用省钱的理由砍掉必须自持的能力。

> 💡 **思考锚点**：3.2.3 给了你一个能当场算的式子——**交叉用量 = C_fixed / (c_b − c_m)**，且它明确「年限只是用量的代理变量」。填你自己的三个数（自研固定投入 C_fixed、外购单位成本 c_b、自研单位成本 c_m），再用你真实的用量年增长率推：第几年累计用量才越过这条交叉线？如果那个年份晚于这项能力的半衰期（3.2.6 的锁定与退出评估给出的退出窗口），自研的固定成本就永远摊不平，TCO 3/5/10 年表上它只是更贵。
