## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

「5-20 人用 RACI、20-100 人用 DACI、100-500 人用 RAPID」这类按规模分档的速查表，把跨团队决策讲成了「按人数挑一个」。但真正决定一套方法能不能用的是三条更硬的约束：**决策权有没有收敛到一个能终止它的位置**、**信息朝哪个方向流动**——受影响方是在决定之前被问，还是决定之后被告知——以及**决策的可逆性**。第一条决定「这次讨论有没有终点」，第二条决定「决定的寿命有多长」，第三条决定它该走最轻的还是最重的那一族。人数只是这三条的代理变量，且是很差的代理变量：一个 12 人的团队如果横跨两个 BU 且没有共同上级，用 RACI 也照样定不下来。

第三条约束是**决策的可逆性**，它比「重要性」更能预测该走哪一族。一个上亿元的采购如果是可撤销的，它的流程可以比一个不可逆的小改动更轻；反过来，一次看似不起眼的表结构变更如果不可逆（下游已消费），就值得前置影响面与签字。团队最常犯的判断错误，是用「这件事重要不重要」替代「这件事能不能改回来」，于是把大量可逆决策塞进最重的流程，把真正不可逆的决策按日常流程放行。成本形态则是另一条约束，它由决策频率与单次影响面决定：角色分配与共识技术（RACI / DACI / 工作坊）是**变动成本**，每做一次决策付一次；常设委员会、Agree 角色的评审带宽、技术雷达的维护是**固定成本**，按周期占用人力，与决策数量无关。固定成本类方法只适合少量重大决策——用它处理高频战术决策，等于用最贵的人力做最便宜的事；而绝大多数「流程被绕过」，原因不在人懒，而在流程的成本形态与决策频率不匹配。

本节的组织方式：先给约束表，再逐个模式写清它被什么逼出来、结构长什么样、代价是什么、在什么条件下优点反转成缺点。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 决策权是否收敛到一个可终止的位置 | 决定这套方法有没有能力让一次决策结束 | 「流程越完整决策越可信」——没有明确签字人时，再完整的流程也只是把讨论记录得更详细 |
| 信息流方向（决定前咨询 / 决定后通知） | 决定 C 或 Agree 与 I 的先后 | 「先决定再通知更高效」——受影响方若握有事后否决手段，返工代价远高于事前咨询 |
| 决策的可逆性 | 决定走轻量一族还是常设一族 | 「重要决策都该上委员会」——判据是不可逆性，不是重要性 |
| 决策频率与单次影响面 | 决定成本形态（变动 / 固定） | 「方法可以随便换」——固定成本的方法用在高频决策上必然成为瓶颈 |
| 参与方的组织形态（同公司 / 跨 BU / 跨组织） | 决定僵局时有没有共同的上级可升级 | 「僵局就找老板」——联邦化场景里没有共同上级，只能靠契约与程序 |
| 会议带宽与协作文化 | 决定同步仪式与异步文档的比例 | 「全都异步」——异步往返里，沉默更容易被读成同意 |

### 3.2 模式逐个拆解（核心节）

按本章 [§ 7 与其他方法对比](09-cross-team-decision-section-7-sec7.md) 的四族归类展开：RACI / DACI / RAPID 是**角色分配族**（回答「谁有权」），RFC + ADR / Architecture Board / Tech Radar / Federation 是**过程文档族**（回答「信息怎么留痕与被发现」），Power-Interest Grid / Consensus Workshop / Working Backwards 是**共识技术族**（回答「异议怎么被处理」），Sociocracy / Holacracy 与 Squad 是**组织形态族**（把决策权写进结构）。族内可以换，跨族不能换：用过程文档解决角色问题，只会得到更整齐的记录。

#### 3.2.1 RACI 矩阵

- **被什么约束逼出来**：决策相关方散在多个团队，谁也说不清「谁拍板、谁执行、谁必须在决定前被问」——约束是**参与角色必须被显式登记，且拍板位置唯一**。
- **结构**：每个决策一行、四个角色槽位，其中 A 只能填一格。

```text
RACI 的结构：一行一个决策，A 是唯一键
  decision_id      | R 执行 | A 拍板(唯一) | C 决定前须被问 | I 决定后告知
  -----------------+--------+--------------+----------------+--------------
  adopt-kafka-2024 | 平台组 | 首席架构师   | 业务方、安全   | 全公司
  可检查的约束（写成唯一键与时间戳才拦得住）：
    A 非空且 <= 1 人        -> 拦「无人拍板」与「多人拍板」
    C 名单在决定日之前冻结  -> 决定后才问的人只能记进 I
```

- **为什么这样设计有效**：因为 A 被收敛到一个人，所以任何一次讨论都有终止条件（有人能签字），同时 C 与 I 的存在让「被咨询」与「被通知」这两件常被混为一谈的事分开记账。
- **代价**：A 的评审带宽成为全组织的串行瓶颈；把 C 名单维护成完整清单本身需要跨团队问人，且 A 一旦远离事实（例如由不接触系统的管理者担任），矩阵仍然成立，但判断质量下降。
- **失效点**：当 A 位置上填的是团队名而不是人名时，「有人负责」反转成「没有人负责」，因为团队没有可以签字的手、也没有可以被追责的个人——表现为事故复盘时每个人都能指出「那是我们组的事」而没有人说「那是我决定的」。
- **真实使用**：【公开】RACI 由项目管理体系推广，其角色定义见 PMI《项目管理知识体系指南》（PMBOK 指南）的「责任分配矩阵」（Responsibility Assignment Matrix）相关章节，具体版次与措辞请以 PMI 当前官方出版物为准（可自行核验）；【经验】本章 § 7 已指出这类方法的归属与定义是公开的，但各组织采用后的实际效果没有公开可比数据，本节不对效果做数字断言。

#### 3.2.2 DACI 框架

- **被什么约束逼出来**：RACI 里推动决策的人与批准决策的人常常是同一个，于是「自推自批」；跨团队决策还需要一个专职把流程推完的角色——约束是**推进权与批准权必须分离**。
- **结构**：在 RACI 的 A 上切一刀，拆成 Driver 与 Approver 两个位置。

```text
DACI 的结构：把「推」与「批」拆成两个位置
  Driver       推动流程：定议程、收材料、催收敛（可以不是决策者）
  Approver     批准：通常 1 人；终止条件挂在这里
  Contributor  提供方案与评审意见（可多人，不设否决权）
  Informed     决定后被告知（可事后追加）
  关键约束：Driver != Approver -> 决策不会因为决策者忙而停摆
    代价是多一个交接点：材料「齐了没有」由谁判定必须写清
```

- **为什么这样设计有效**：因为把「谁负责让流程走完」从「谁负责承担后果」里分出来，所以流程进度与责任归属可以各自被考核，避免了「批准人兼任催办人、结果两件事都做不好」。
- **代价**：多一个交接点就多一处可以互相等待的地方；Driver 无权终止、Approver 无义务推进，二者不同步时决策卡在中间，且卡住时双方都有合理的说法。
- **失效点**：当组织已经有一个明确的当家人时，DACI 的拆分反转成额外的协调成本，因为「推进」这件事本来由权力自然完成，拆出来只是把一个动作变成两个动作加一次同步。
- **真实使用**：【公开】由 Atlassian 推广，其官方文档可查到 Driver 与 Approver 的区分（可按官方文档当前版本核验；本章 [§ 7](09-cross-team-decision-section-7-sec7.md) 已登记该归属）。

#### 3.2.3 RAPID 决策框架

- **被什么约束逼出来**：财务、法务、合规这类角色的否决如果在决定之后才出现，前面所有人的工作要重做——约束是**具备否决权的角色必须在决定之前表态**。
- **结构**：相对 DACI 只多一个可否决的 Agree 槽，但多一条「必经节点」规则。

```text
RAPID 的结构（五槽 + 一条时限规则）
  Recommend       推荐方案
  Agree           必须同意才能通过：财务 / 法务 / 合规
                  —— 「同意权」在效果上等于否决权，因此必须前移
  Provide input   提供意见（可以被忽略，这是它和 Agree 的差别）
  Decide          拍板（唯一）
  Input/Informed  被通知
  必经节点：Decide 之前必须收齐全部 Agree 的表态
  补一条否则整族失效的约束：每个 Agree 必须有表态时限
    （【经验】常见 3-5 个工作日）——无时限的把关 = 无限期搁置
```

- **为什么这样设计有效**：因为否决被前移到决策之前，所以「已经决定、被法务打回」这类返工在结构上被消除，合规风险从「事后纠正」变成「事前筛除」。
- **代价**：Agree 角色的队列成为新瓶颈，且瓶颈宽度随合规域数量增长——决策周期与 Agree 数近似线性，每加一个必经角色就多一段等待。
- **失效点**：当 Agree 角色没有表态时限时，「把关」反转成「无限期搁置」，因为否决的收益归把关者（避责）、等待的成本归发起方，而没有任何机制把这份成本记到把关者头上。
- **真实使用**：【公开】由 Bain & Company 提出，其官方工具页可查到 Recommend / Agree / Provide input / Decide 各角色的定义（可按官方页面当前版本核验）。

#### 3.2.4 RFC + ADR

- **被什么约束逼出来**：参与者不在一处、不在一时（跨时区、跨 BU），且人员会流动——约束是**决策的当时约束、备选方案与被否决理由必须能脱离在场者独立存活**。
- **结构**：两个文档、两个时点，前一个处理异议，后一个冻结约束。

```text
RFC + ADR 的结构：决定前一份、决定后一份
  RFC（决定前）  propose -> review（异议窗口）-> accept / reject
     必填字段：问题与约束 / 备选方案与对比 / 影响面与受影响方 / 异议处理结果
     位置约束：读者范围由「默认公开 + 可检索」决定，不是由发起人猜「谁相关」
  ADR（决定后）  context -> decision -> consequences
     consequences 必须含「被否决的选项与理由」
  关键约束：ADR 一经写下不再编辑，结论变更用新 ADR 覆盖旧 ADR
（这条是「半年后能区分判断错了与约束变了」的唯一技术前提）
```

- **为什么这样设计有效**：因为 ADR 不可修改、只能被覆盖，所以决定当时所依据的约束被冻结在同一份文件里，后来的人不必靠回忆去还原当时的取舍空间。
- **代价**：写作与评审是固定成本（跨团队一份 RFC 通常要数天人力），与决策数量无关；把「被否决理由」写全，等于要求提案人主动记录自己方案的弱点，这在激励上是逆人性的。
- **失效点**：当决策频率上升而单份文档成本不降时，「可追溯」反转成「被绕过」，团队回到群里口头决定，因为记录的收益（半年后能追溯）被贴现到接近零，而成本当场支付——表现为 ADR 目录里只有几个样板案例，与实际发生的决策数量对不上。
- **真实使用**：【公开】RFC 这一文档形式源自 IETF 的 RFC 系列（1969 年起，可按 IETF 官方 RFC 档案核验）；【公开】ADR 由 Michael Nygard 于 2011 年提出（可按键名核验）；【公开】把「默认公开的设计文档 + 异议窗口」作为跨团队决策流程的做法见本章 [§ 6 落地实践](09-cross-team-decision-section-6-sec6.md) 的 Google 案例（[Google 公开材料 2014–2024]）。

#### 3.2.5 Architecture Board（架构委员会）

- **被什么约束逼出来**：单个决策的影响跨多个 BU，而不存在任何一个人（包括 CTO）掌握全部事实——约束是**需要一批人组成的位置，且这个位置必须常设**，否则每次都要重新召集与重新解释背景。
- **结构**：常设席位 + 议程制 + 三类输出，权限边界要写死。

```text
架构委员会的结构：常设位置 + 议程制 + 三类输出
  组成    固定 5-10 名资深架构师【经验】（常设，不是按议题临时凑）
  议程    提案进议程前必须交材料：影响面 / 备选 / 成本 / 迁移方案
          会上只做裁决，不在会上做第一次技术讨论
  输出    ① 批准或否决的 ADR（含否决理由）
          ② 技术雷达的档位调整（把裁决转成组织立场）
          ③ 架构约束（白名单 / 禁令，需给复核日期）
  权限边界：委员会否决的是「与架构约束冲突」，不是「某团队的业务判断」
  入会门槛（可判定，不靠感觉）：不可逆 且 跨 >= 2 个 BU 且 无单一 Owner 能承担后果
```

- **为什么这样设计有效**：因为席位常设，所以同类决策在不同 BU 之间口径统一，一次裁决可复用多次；同时材料的强制前置把「先做后报」挡在议程之外。
- **代价**：纯粹的固定成本——委员按周期占用人力，与决策数量无关；议程排队本身变成一个可见的等待队列，且委员的技术判断会随时间与实际系统脱节。
- **失效点**：当提案数量增长而席位不变时，「统一口径」反转成「先做后报」，因为等待的代价由团队即时承担，而违反架构约束的代价滞后、且未必落到同一个团队头上。
- **真实使用**：【经验】多数大型组织设有常设架构评审机构，但公开可比的「决策质量」数据不存在，本节不做效果断言；【公开】把评审结论以 ADR 形式归档的形态见 Nygard 2011。

#### 3.2.6 Tech Radar（技术雷达）

- **被什么约束逼出来**：各团队重复评估同一批技术，结论互不可比，且同一个方案在不同团队的取舍理由互相矛盾——约束是**组织当前立场必须是一份可被引用的公开表态**。
- **结构**：一个二维表态表（四档 × 若干象限），不是打分表。

```text
技术雷达的结构：离散表态 + 生效与复核日期
             Adopt     Trial     Assess    Hold
  语言/框架   ...       ...       ...       ...
  平台/基建   ...       ...       ...       ...
  技术/工具   ...       ...       ...       ...
  每一格必须带：生效日期 + 下次复核日期 + 一句话理由
  两条决定它是否失效的约束：
    未列入 = 未表态（不等于禁止）-> 决定它被当成「参考」还是「审批清单」
    表态必须有复核日期          -> 没有失效日期的表态，效果上等于禁令
```

- **为什么这样设计有效**：因为表态是四档离散值，所以跨团队的选型冲突可以在「同一张表上的档位差」上讨论，而不必每次重做一轮技术调研；引用一条已有档位，比说服一个团队便宜得多。
- **代价**：档位更新滞后于技术演进，且维护这份表需要有人持续投入（固定成本）；「Hold」档在被读者解读时天然带禁令色彩，澄清成本高。
- **失效点**：当雷达没有复核日期时，「选型对齐」反转成「用一份过期的表态否决新方案」，因为雷达是组织级文件，推翻它的成本远高于遵守它——表现为团队绕过雷达做试点，且不再把结论回报给雷达。
- **真实使用**：【公开】ThoughtWorks 的技术雷达是该形式的公开形态（可按其官网当前版本核验；本章 § 7 已登记这一归属）。

#### 3.2.7 Stakeholder Power-Interest Grid

- **被什么约束逼出来**：沟通带宽有限，不可能对所有人做同等深度的沟通——约束是**沟通投入必须按某种可分类的依据差异化**。
- **结构**：权力 × 利益四象限，象限决定沟通深度，不决定决策权。

```text
权力 x 利益 四象限
              利益低              利益高
   权力高     保持满意            重点管理（决定前充分沟通）
   权力低     最小努力            保持告知（决定后通知即可）
  使用约束：象限只决定「沟通投入」，不决定「谁能否决」——当决策权矩阵用会误读成「权力高=可否决」
  自检问题：决定做出之后，谁能让它停下来？（答案常在「权力低、利益高」格）
```

- **为什么这样设计有效**：因为它把有限的沟通资源按「能否阻碍」而不是按「是否友善」分配，所以最可能让决策返工的一方会被优先沟通，而不是最后知道。
- **代价**：象限判定是主观的，且判断依据（谁有权力、谁在乎）随议题变化——同一批人在两个议题上可能落在不同象限，需要逐议题重判。
- **失效点**：当被划入「最小努力」的一方握有事后手段（预算、法务、舆情、招聘）时，「省下沟通成本」反转成「决策被推翻」，因为权力可以从组织外部临时获得，而利益只能由当事方自己知道——表现为决策公告发出后突然出现一个从未参与讨论的反对者。
- **真实使用**：【经验】该矩阵是利益相关方管理中被普遍使用的标准工具（可按「利益相关方管理」「权力-利益矩阵 / power-interest grid」等关键词检索公开教材核验）；本节不给出无法复核的提出年份，也不对该工具的使用效果做断言。

#### 3.2.8 Working Backwards（PR/FAQ）

- **被什么约束逼出来**：决策者不是用户，产品与平台决策容易滑向「技术上能做到什么」——约束是**用户价值必须写在方案之前，且要写得能被外部人检验**。
- **结构**：先写发布公告，再写 FAQ，最后才谈实现。

```text
Working Backwards 的结构：先写「发布当天对客户说什么」
  ① PR（Press Release） 以发布口吻写：客户是谁 / 价值是什么 / 怎么用
        约束：PR 里不许出现内部技术名词
  ② FAQ  外部 FAQ（客户会问什么）+ 内部 FAQ（成本 / 风险 / 依赖 / 明确不做什么）
  ③ Review  在投入之前评审 PR/FAQ —— 写不出来 = 还没想清楚
  判定规则：写不出 PR 的方案不进入排期，而不是「写得差就改改」
```

- **为什么这样设计有效**：因为「能不能写出对客户的公告」被当作「是否想清楚」的判据，所以它把「要不要做」提前到投入之前，剔除了那种技术可行、价值说不清的项目。
- **代价**：它只适用于有外部客户的场景；对内部平台必须先把「客户」重定义为消费方（业务分析师、数据科学家），否则 PR 会退化成技术方案书的另一种排版。
- **失效点**：当决策是成本类或合规类（降低成本、满足监管）而不是价值类时，「从客户价值反推」反转成「为了写出漂亮的公告而夸大收益」，因为 PR 的体例要求讲客户价值，而这类决策的价值本来就不在客户侧。
- **真实使用**：【公开】Amazon 的公开方法论（关于该做法的系统描述见 Colin Bryar 与 Bill Carr 的《Working Backwards》，2021；可按书名核验）。

#### 3.2.9 Consensus Building Workshop（共识工作坊）

- **被什么约束逼出来**：各方立场已经僵住，异步书面往复无法收敛（甚至会把立场越写越硬）——约束是**需要一个受控的同步窗口，把「事实对齐」与「方案取舍」分成两步走**。
- **结构**：中立引导师 + 时间盒 + 四步收敛。

```text
共识工作坊的结构：时间盒 + 判据先公布
  第一步  对齐问题与事实（不讨论方案）——省掉这一步，后面全是空转
  第二步  列选项（先穷举、不评价）：用名义群体法各自写，避免被首个发言者锚定
  第三步  评估：按事先公布的判据，而不是现场发明判据
  第四步  收敛：不是「大家都同意」，而是「没有人认为不可接受」
  约束：引导师不得对方案表态；判据必须在讨论开始前发给所有参与者
```

- **为什么这样设计有效**：因为判据事前公布、选项先各自写，所以会议不会被最先发言者的框架锚定，也不会被现场临时发明的标准带偏；「无不可接受」这一收敛口径比「全票同意」更容易达成，且不要求任何人表态支持。
- **代价**：同步窗口本身昂贵（【经验】1-3 天 × 参与方人数，跨地域还要加差旅与协调），且工作坊**不产生决策权**——它只能输出一个可接受的方案，签字仍需回到 A 或 Decide 位置。
- **失效点**：当参与者不是各自团队里能让步的人时，「深度共识」反转成「回去后各自被推翻」，因为同意的成本落在工作坊现场、反悔的成本落在各团队内部，而后者远大于前者——表现为结论在前一周被推翻，两周后又回到工作坊重开一次。
- **真实使用**：【经验】跨 BU 重大变更与组织调整常用此形态；名义群体法（NGT）与德尔菲法作为「先独立写、再集中讨论」的异议保护技术，属公开的方法（可按方法名自行检索核验），其归属登记见同目录 [§ 2 核心原理](09-cross-team-decision.md) § 2.3 的方法清单。

#### 3.2.10 Sociocracy / Holacracy

- **被什么约束逼出来**：层级结构里没有位置给「受影响但没有职位」的人；同时希望在缺席情况下决策仍能推进——约束是**决策的默认值必须从「不通过」翻成「通过」，同时给反对留一个低成本入口**。
- **结构**：圈子 + 角色 + 等效异议（consent）。

```text
同意决策（consent）的结构：默认通过 + 反对需举证
  ① 提案   某角色提出
  ② 澄清   只问澄清性问题，本轮不允许表态反对
  ③ 反应   每人表态：无异议 / 有「等效异议」（须指出具体负后果）
  ④ 修订   有等效异议 -> 修订提案（不是投票否决提案）
  ⑤ 通过   无进一步等效异议即通过；缺席不构成阻塞
  约束：反对必须附带机制层面的具体负后果，否则不构成等效异议
```

- **为什么这样设计有效**：因为默认值是「通过」且缺席不阻塞，所以决策不会因少数人缺席而停摆，速度显著提升；同时反对的门槛被抬到「必须举证」而不是「不赞成」。
- **代价**：反对的成本被转移到少数方——在大组织里，提出反对的人承担关系成本，于是沉默成了理性选择，而机制把沉默读成同意；此外判定「异议是否等效」需要一个有权威的裁决者，这本身是层级。
- **失效点**：当组织规模超过「圈子里的人互相认识」的规模时，「等效异议」的质量崩塌，因为判断一条反对是否成立依赖共同语境，而共同语境随规模消失——表现为异议记录里被判「不构成等效异议」的比例持续升高，机制退化为「提案自动通过」。群体思维的经典分析见 Irving Janis 的 *Victims of Groupthink*（1972）【公开】。
- **真实使用**：【公开】两者各自的公开治理章程可核验；【经验】实际采用多限于小型组织与社群。

#### 3.2.11 Cross-functional Squad（Spotify 模型）

- **被什么约束逼出来**：交付依赖串行、跨职能交接排队，每个交接点都要等；同时希望决策权写在结构里而不是写在流程文件里——约束是**让做的人自己决定怎么做**。
- **结构**：横向自治单元 + 若干条横向对齐线。

```text
Squad 模型的结构：自治单元 + 三条横向线
  Squad    跨职能小队（产品 / 工程 / 设计在同一队内），自治决定「怎么做」
  Tribe    相关 Squad 的集合，给出协作边界
  Chapter  同专业跨 Squad 的横向线（对抗「各队重复造轮子」）
  Guild    跨 Tribe 的兴趣社群（无权限，纯横向）
  关键约束：自治的边界是「怎么做」；「做什么」由 Tribe / 公司层对齐
    丢掉这条边界，Squad 会退化成「各队各做一套」的碎片化
```

- **为什么这样设计有效**：因为跨职能成员在同一队内，所以交接从「跨部门排队」变成「队内协商」，等待被消除而不是被优化。
- **代价**：横切能力（安全、数据治理、基础设施、一致性）没有天然归属——Chapter 与 Guild 没有权限，只能倡议；且「自治」与「对齐」的张力不会消失，只是从流程问题变成组织问题。
- **失效点**：当团队数量增长、依赖变密时，「自治」反转成「碎片化」，因为自治权是固定的常量，而跨队协调需求随团队对数超线性增长——表现为同一能力被多个队各实现一次，最后不得不靠一次集中治理（重组）来收敛。
- **真实使用**：【公开】Spotify 公开的工程组织描述是该模型的公开形态；值得同时注意的是 Spotify 前成员公开撰文指出该模型在 Spotify 内部并未按公开描述运行（可按 "Failed #SquadGoals" 检索核验）——**模型与组织的实际形态应当分开核验**，引用模型不等于引用其效果。

#### 3.2.12 Federation（联邦化治理）

- **被什么约束逼出来**：组织内没有、也不该有一个单点能管辖所有域（多 BU、跨国、开源基金会），跨域议题不能靠指令只能靠约定——约束是**决策权留在域内，跨域只靠契约**。
- **结构**：自治域 + 契约 + 分级升级程序。

```text
联邦化治理的结构：自治域 + 契约 + 三级升级
  域 A（自主决策）   域 B（自主决策）   域 C（自主决策）
        \_______________ | _______________/
          契约：接口 / 数据口径 / SLA / 变更通知窗口 / 版本兼容期
  跨域议题的三条路径（成本递增）：
    ① 双边契约（两域直接约定）-> ② 共同体规范（接口与口径标准）
    -> ③ 基金会 / 联盟程序（只在 ①② 失败后使用）
  约束：契约必须写明「变更前通知窗口」与「版本兼容期」，否则契约只剩签名
```

- **为什么这样设计有效**：因为每个域掌握自己范围内的事实，决策不必上传，所以本地知识被充分利用、决策速度快；跨域接口的稳定性由契约而不是由上级裁决来保证。
- **代价**：契约不覆盖的地方就是碎片，而契约是逐议题谈判的；谈判成本随域对数量近似组合式增长，这部分成本不体现在任何一个域的预算里。
- **失效点**：当跨域议题频率上升、每个议题都要重新谈判时，「高度自治」反转成「重复谈判」，因为契约是逐议题的、收益（本地最优）却是固定的——表现为跨域会议数量持续上升而结论复用率很低。
- **真实使用**：【公开】Linux Foundation（沿革可追溯至 2000 年的 OSDL，2007 年由 OSDL 与 Free Standards Group 合并为现名）与 CNCF（2015 年由 Linux Foundation 发起）是跨组织联邦化治理的公开形态（可按各自官方 About 页面核验）；【公开】数据网格（Data Mesh）的公开方法论把「联邦计算治理」列为其原则之一（代表作 2022 年出版，可按关键词检索核验）。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 5-20 人、单团队、可逆决策 | 群内共识 + 一份决策纪要 | 不选 RACI：四个角色槽位在同一个团队里是重复记账 | 执行的人是否就是决定的人 |
| 20-100 人、跨职能、需要唯一签字人 | DACI | 不选 RACI：RACI 的 A 常被同时当成执行人，推动与批准混在一处 | 有没有一个人能终止讨论 |
| 100-500 人、合规在前、决策不可逆 | RAPID | 不选 DACI：合规否决若在决定后才出现，代价是返工而不是多一个节点 | 有没有角色能在事后否决 |
| 跨时区、参与者分散 | 异步 RFC + 时限化异议窗口 + ADR | 不选工作坊：同步窗口在跨时区下是数量级的成本差 | 异议窗口是否有截止时间 |
| 500+ 人、多 BU、长期路线 | Architecture Board + Tech Radar | 不选 RAPID：委员会处理高频战术决策会变成瓶颈（固定成本） | 这次决策可逆还是不可逆 |
| 跨 BU 且无共同上级 | 联邦契约 + 升级程序 | 不选「升级找老板」：没有共同上级可升级，僵局没有终止条件 | 僵局出现时谁有权终止 |
| 受影响方无法事先枚举 | 默认公开 + 可检索 + 异议窗口 | 不选「逐一通知」：发起人穷举不了受影响者 | 受影响方能否自己发现自己相关 |
| 立场僵持、需要一次对齐 | 共识工作坊（中立引导 + 判据前置） | 不选纯文档往复：异步往复不收敛，且会把立场越写越硬 | 参与者能否代表本团队让步 |

表里的规模分档为【经验】量级，用于选型分档，不是实测阈值。表里最常被误选的一对是 **RACI 与 DACI / RAPID**：团队需要一个决策框架，却装了 RACI——把「谁参与」当成了「谁拍板」。这个误选不会当场出错：矩阵填得很整齐，会议也开了，问题出在没有人能终止讨论。机制上，RACI 的 A 位在实践中极容易被填成「首席架构师」这类没有到场承诺的虚位，而 C 与 I 又确实被认真执行了（毕竟这两列填起来最容易），于是看起来一切就绪。实际后果是决策以「大家都没意见」的形式通过，然后在执行阶段各团队按自己的理解分头落地；等它暴露出来时，通常表现为各方的数字对不上，而不是立场对立——本章 § 6 的字节案例正是这样诊断「跨团队分歧」的：多数「立场冲突」其实是事实分歧，「把口径分歧当立场分歧处理」是它记录下来的主要失败形态。

### 3.4 组合模式：真实系统不会只用一种

**组合一：角色分配 + 过程文档 + 组织立场（DACI 或 RAPID + RFC/ADR + Tech Radar）**。职责边界：角色分配回答「谁签字」，RFC/ADR 回答「理由怎么留下、谁受影响」，技术雷达回答「同类决策的口径在哪」。运维代价是三处要同步——雷达档位调整时要通知所有引用过它的 ADR，否则归档里的依据会与现行立场打架。适合规模：多 BU、每季度有若干不可逆决策的组织。

**组合二：常设裁决 + 门槛化升级 + 事后抽检（Architecture Board + 轻量流程 + 抽检）**。职责边界：委员会只接「不可逆 × 跨 BU × 无单一 Owner」的提案，其余下放给团队自己的轻量流程；升级门槛写成可判定条件（而不是「觉得重要就上报」），事后按季度抽检被下放的决策并回写结论。运维代价是抽检需要人（但远少于全量评审），且门槛条件需要定期校准，否则会随组织变化失准。适合规模：500 人以上、有明显架构约束诉求的组织。

**组合三：联邦自治 + 一次性对齐 + 契约版本化（Federation + 共识工作坊 + 决策日志）**。职责边界：域内自治，跨域议题先用工作坊一次性对齐（只在议题首次出现时做），结论固化成契约，契约的版本与理由进决策日志。运维代价是契约版本管理本身成为一项长期工作，且工作坊不可复用——每个新议题都要重开一次。适合规模：多 BU、跨国或跨组织（基金会、联盟、数据网格形态）。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 无人拍板 | 会议结束时说不出「谁签的字」；A 栏填的是团队名 | 决策没有终止条件，只能靠时间耗尽或议题自然消失 | 「共识决策」听起来比「某人拍板」更体面 | A 收敛到一个人；把这条写成登记表的约束而不是倡议 |
| 一言堂 | 会上无人反对，会后在私聊里反对 | 反对被推到执行阶段，以消极执行的形式出现 | 拍板者同时是评审会的最高职级者 | 匿名先写意见再开会；指定反对者角色 |
| 扯皮会 | 同一议题第 4 次上会，仍无结论 | 议题包无限扩张，每轮都引入新的相关方 | 没有把「相关」与「有权终止」分开 | 设截止日期与升级条件；超期自动升级而不是继续开会 |
| 形式评审 | 评审记录里没有任何反对意见 | 评审不再筛选方案，只提供「已评审」这个标签 | 记录反对的成本高于附和（尤其对基层） | 强制每位评审人写一条可验证的反对或补充条件 |
| 忽视 Informed | 决定后有人第一次听说，且他的工作已被影响 | 补通知无法撤销已做出的承诺，返工量随知情延迟增长 | I 被当成礼貌环节，而不是影响面的一部分 | 把 I 名单与影响面一起在决定前确定，决定后按名单通知 |
| 跨团队决策不写 ADR | 半年后问「当时为什么这么定」，只有回忆 | 决策寿命短于参与者在职时间，重复决策成本全额重付 | 记录的收益滞后兑现，成本当场支付 | 把 ADR 挂在决定流程的出口（不写不生效），而不是挂在文档规范上 |
| 群体思维 | 会上零反对，且参与者事后都表示「我其实有疑虑」 | 沉默被机制读成同意，风险在无人反对的情况下通过 | 反对的关系成本被个人承担，而收益归集体 | 用「先独立写、再集中讨论」的采集方式；把反对记录为贡献而非异议 |
| 沉默成本陷阱 | 项目连续两次延期，但预算仍在增加 | 沉没成本被计入「已投入」，退出被当成浪费 | 决策者与评估者是同一批人 | 立项时写明退出判据；到期复核时由未参与者评估 |
| 官僚化 | 所有决策都要走完整流程，包括改一个字段名 | 流程成本与决策频率不匹配，团队开始绕过流程 | 流程只按「重要性」分级，没按「可逆性」分级 | 按可逆性与影响面分级；轻量通道要写成默认而不是例外 |
| 无人 Review | 跨团队决策只有本方评审通过 | 受影响方的约束在决定后才被发现 | 邀请评审要跨团队协调，成本即时、收益滞后 | 强制至少一名跨组 Reviewer；把「谁受影响」写进 RFC 必填项 |
| 把 AI 当权责问题的解 | 上了 AI 起草与整理后，「谁签字」仍答不上来 | 材料变齐、讨论变快，但协调成本未被触及，问题被掩盖 | AI 降低的是信息成本，而卡点通常在责任归属 | AI 只做检索先例、整理材料、起草；权责结构保持不变 |

两条最危险的展开：

**「无人拍板」的暴露方式**：它极少以「决策失败」暴露，而以「决策成功但没人认账」暴露。议题以「大家都没意见」通过，三个团队按各自理解分头执行，三个月后对齐时发现三套实现。此时回看会议记录，每一段都写着「一致同意」——**没有 A 位置的决策，其记录看起来与成功的共识完全一样**，这是它比「一言堂」更难被发现的原因。

**「群体思维」的暴露方式**：它在事故复盘中暴露，且暴露形式是「所有人都说有疑虑但没人说」。这是本章 § 7 记录的位置——机制没有制造从众，但它把从众的收益放大了：在「无反对即通过」的规则下，沉默是免费的，发言是收费的。判定方法不是看会上有没有反对，而是看**意见采集方式**：如果意见是在会上口头采集的，零反对不构成共识的证据。

### 3.6 规模跃迁时模式何时该换

下表阈值为【经验】量级，用于判断「什么时候该换」，不是硬性分界。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单团队 → 多团队协作 | 群内共识 + 纪要 | 「谁受影响」无法枚举，争议靠回忆 | RACI 登记（A 唯一）+ 决定后按名单通知 | 引入角色分配仪式，简单决策变重 |
| 多团队 → 多 BU | RACI 表 | 矩阵填得齐但争议仍然没结论，因为 RACI 不回答「怎么决定」 | DACI 或 RAPID + RFC/ADR | 决策周期变长（多一个必经节点） |
| 单地域 → 跨地域 | 同步评审会 | 每次决策多等一个时区往返 | 异步 RFC + 时限化异议窗口 | 异议在异步里更容易被沉默读成同意 |
| 多 BU → 500+ 人长期治理 | 逐议题的 RFC 评审 | 同类决策被反复裁决，评委带宽饱和 | Architecture Board + Tech Radar | 委员会固定成本 + 议程排队 |
| 有共同上级 → 无共同上级 | 升级到上级裁决 | 没有一方能终止僵局 | 联邦契约 + 分级升级程序 | 谈判成本随域对数量增长 |
| 低频重大 → 高频战术 | 常设委员会逐案评 | 委员会成为瓶颈，团队开始「先做后报」 | 门槛化升级 + 下放 + 事后抽检 | 违反架构约束的代价滞后暴露 |
| 人员稳定 → 流动率高 | 口头共识与私下约定 | 决策寿命短于参与者在职时间 | ADR 强制归档（不写不生效） | 每份决策增加写作与评审成本 |

### 3.7 自检清单

- [ ] 这次决策的 A 或 Decide 位置，能不能说出「是哪一个人」？填成团队名即视为没有责任人。
- [ ] C 或 Agree 的名单是在决定日之前冻结的吗？决定之后才被问的人，只能记进 I。
- [ ] 归档里有没有写下被否决的备选方案与理由？只记结论的 ADR 无法区分「判断错了」与「约束变了」。
- [ ] 每份归档是否写明了影响面与被通知人？没有影响面的记录支撑不了事后追溯。
- [ ] 常设机构最近的议题里，可逆且单团队的占多少？超过一半说明该下放，而不是该加人。
- [ ] 每个 Agree 与每个议程项是否有时限？无时限的把关环节等于无限期搁置。
- [ ] 技术雷达的每一格是否标了复核日期？没有失效日期的表态，效果上等于禁令。
- [ ] 有没有统计「先做后报」的比例？需要事后追认的决策占比是流程是否被绕过的直接指标。
- [ ] 会议上的零反对，是在口头采集方式下得到的吗？是则该结论不构成共识的证据。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 参与者都在同一间屋子里，决策可逆 | 群内共识 + 纪要 | 角色登记的成本大于收益，唯一需要的是留痕 |
| 需要唯一签字人，且要有人推动流程 | DACI | 推进权与批准权分离，决策不会因决策者忙而停摆 |
| 有角色能在事后否决 | RAPID | 把否决前移到决定之前，返工在结构上被消除 |
| 参与者分散、人员会流动 | RFC + ADR | ADR 不可修改，决定当时的约束被冻结下来 |
| 影响跨 BU、不可逆、无单一 Owner | Architecture Board + Tech Radar | 固定成本换取同类决策的口径统一 |
| 受影响方无法枚举 | 默认公开 + 异议窗口 | 受影响方能自己发现自己相关，不依赖发起人穷举 |
| 无可升级的共同上级 | 联邦契约 + 分级升级 | 没有终止位置时，只能靠约定与程序 |
| 意见已经僵持，需要一次对齐 | 共识工作坊 | 判据前置 + 先独立写，去掉锚定与从众 |

> 本节小结：决定模式选择的唯一那条约束是**「这次决策有没有一个能终止它的位置」**——有，剩下的问题只是信息怎么流、记录放哪里；没有，再完整的流程也只是把讨论记录得更详细。在这条约束之外，真正决定能不能落地的是两件事：**这个位置是常设的还是临时的**（决定成本形态，也决定它能承受多少决策量），以及**反对意见用什么方式采集**（口头采集下的零反对，不构成共识的证据）。
