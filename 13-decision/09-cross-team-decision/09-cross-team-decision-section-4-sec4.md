## 4. 工程实现

本节主要写给**存量改造**的读者：跨团队决策已经在发生，只是说不清「谁签的字、当时依据什么约束、受到影响的团队在决定前有没有机会说话」。绝大多数组织属于这一类 —— 角色分配、RFC、委员会都不缺「听说过」，缺的是把它们接进正在发生的决策里。**从零搭建**的读者按 §4.1 的 Step 1–3 起步就够，Step 4 之后的常设机构要等真的出现「不可逆 × 跨 BU × 无单一 Owner」的议题再上，否则会先养出一笔固定成本。

落地顺序按 [§3.2](09-cross-team-decision-section-3-sec3.md) 的族序走：**角色分配族 → 过程文档族 → 共识与组织形态族**。理由是 §3 已给出的那条约束——族内可以换、跨族不能换：角色位置不存在时，RFC 与工作坊只能把讨论记录得更详细，结算不了。§4.2 给机制与失效条件，§4.3 给选型判据，§4.4 整节给存量迁移，§4.5 给可直接套用的模板。

### 4.1 落地步骤

**Step 1：建立 RACI / DACI 模板（【经验】1–2 周）**

- 在 Confluence / Notion 建组织级模板：一行一个跨团队决策、四个（或五个）角色槽位。
- 把约束写成**表格校验**而不是倡议：A（Accountable）非空且 ≤ 1 人；DACI 里 Driver ≠ Approver；C 名单在决定日之前冻结。
- 用最近 5 次真实决策把表补填一遍，作为模板的第一次校准。

- **产物**：组织级 RACI / DACI 模板 + 最近 5 次决策的补填记录。
- **判据**：把补填结果摊开数 A 栏 —— 写团队名、或写一个不到场的职级的有几行。只要有一行，「无人拍板」就已经发生过（[§3.5](09-cross-team-decision-section-3-sec3.md)）。
- **为什么必须这一步**：[§3.1](09-cross-team-decision-section-3-sec3.md) 的第一条约束是「决策权有没有收敛到一个能终止它的位置」。这个位置不存在时，后面每一族方法都无法结算。它也是唯一一个**不改任何人的行为、只改登记方式**的动作，所以放第一步。

**Step 2：建立 RFC 流程（【经验】2–4 周，含第一份真实 RFC 走完异议窗口）**

- 建仓库 `docs/rfcs/` 或独立 RFC 平台；模板必填字段：上下文、提议选项、影响分析、回滚方案、Owner、Reviewers。
- PR 化提交 + Reviewers 制度；设截止日期（进入 Final Comment Period，窗口结束即进入决策）。
- 可见性按「默认公开 + 可检索」而不是「发给我认为相关的人」。

- **产物**：RFC 模板 + 仓库 / 平台 + 一份已走完异议窗口的真实 RFC（含评论与逐条回应）。
- **判据**：翻第一份 RFC 的评论者名单，看是否全部来自发起人所在团队；再看窗口期内的异议有没有逐条回应结论。前者暴露可见性，后者暴露「评论会被忽略」。
- **为什么必须这一步**：它必须在 ADR 之前 —— RFC 处理异议、ADR 冻结结论。顺序反过来的话，异议只能在结论归档之后才出现，而 ADR 不可编辑（[§3.2.4](09-cross-team-decision-section-3-sec3.md)），只能再写一份覆盖它。

**Step 3：建立 ADR 归档（【经验】1 周定规则，之后持续）**

- 决策接受后写 ADR：context → decision → consequences；consequences 里必须含被否决的选项与理由。
- ADR 一经写下不再编辑，结论变更用新 ADR 覆盖旧 ADR；ADR Index 打「跨团队决策」标签。
- 把归档挂在流程出口 —— **不写 ADR 的决策不生效**，而不是挂在文档规范上。

- **产物**：ADR 归档目录 + Index（含跨团队标签）+ 「不写不生效」的落地方式（例如合并前的检查项）。
- **判据**：随机抽 3 份 ADR，看 consequences 里有没有被否决的选项与理由。缺的即为「只记结论」，半年后无法区分「判断错了」与「约束变了」（[§3.2.4](09-cross-team-decision-section-3-sec3.md)）。
- **为什么必须这一步**：ADR 是唯一能把「决定当时的约束」冻结下来的载体。没有它，Step 4 的委员会只能靠记忆裁决同类议题，Step 7 的工作坊每开一次都从零开始。

**Step 4：建立 Architecture Board（【经验】4–8 周，含席位确定与首批议程）**

- 5–10 名资深架构师【经验】，含安全 / 数据 / 业务代表；每周或双周会议。
- 入会门槛写成可判定条件：**不可逆且跨 ≥ 2 个 BU 且无单一 Owner 能承担后果**（[§3.2.5](09-cross-team-decision-section-3-sec3.md)）。
- 材料进议程前交齐（影响面 / 备选 / 成本 / 迁移方案）；会上只做裁决，不在会上做第一次技术讨论。
- 评审重大 RFC + ADR；输出三类且都带复核日期：ADR、技术雷达、架构约束。

- **产物**：委员会章程（席位、议程门槛、材料清单、三类输出、复核日期）。
- **判据**：把上一季度上过会的议题按门槛三条件打标，数「可逆且单团队」的占比；超过一半说明该下放，而不是该加人（[§3.7](09-cross-team-decision-section-3-sec3.md)）。
- **为什么必须这一步**：它是**固定成本** —— 委员按周期占人力，与决策数量无关（[§3.1](09-cross-team-decision-section-3-sec3.md)）。所以它要排在 Step 1–3 之后：只有先知道哪些决策真的没有终止位置，才判断得出值不值得养这批席位。

**Step 5：建立 Stakeholder Map（【经验】1–2 周首次，之后逐议题重做）**

- 识别全部相关方（团队 / 个人 / 角色），用 Power-Interest Grid 分类，定沟通策略（管理 / 重点 / 最小 / 告知）。
- 每张表多答一个问题：**决定做出之后，谁能让它停下来。**
- 按议题重判象限，不沿用上一议题的结论。

- **产物**：逐议题的 Power-Interest 表（含沟通策略与「事后能否决者」一行）。
- **判据**：拿一次已完成的决策回看 —— 如果「事后能让它停下来的人」落在「最小努力」格或从未参与讨论的格子里，说明这张表只被用来排会议邀请了（[§3.2.7](09-cross-team-decision-section-3-sec3.md)）。
- **为什么必须这一步**：它要在发决策公告之前做完。权力可以从组织外部临时获得（预算、法务、舆情），利益只有当事方自己知道 —— 这两样都不在发起人的信息里，而漏掉它们要等到公告发出后才暴露。

**Step 6：建立 Escalation 流程（【经验】1 周）**

- 四级阶梯，各级时限为【经验】量级（随决策链长度变化）：团队内部 24 小时 → 跨团队 Lead 协商 48 小时 → Architecture Board 评审 1 周 → 高管决策（CTO / VP）。
- 每级写清「输入什么、输出什么、超时怎么办」；超期自动升级，而不是继续开会。
- 时限写进工单系统的 SLA（Jira Service Management、ServiceNow 一类载体），不只写在文档里。

- **产物**：升级阶梯图 + 每级的时限与终止条件（落在系统里的 SLA 配置）。
- **判据**：数上一季度的升级里有多少次发生在时限之前（主动升级）、多少次等到超期才升。全在时限之后，说明时限没有落到任何系统里、只是文档上的一句话。
- **为什么必须这一步**：冲突的终止条件必须写成「级 + 时限」。没有它，议题会无限扩张 —— 同一议题第 4 次上会仍无结论（[§3.5](09-cross-team-decision-section-3-sec3.md) 的「扯皮会」）。它还要排在委员会之后，因为阶梯的第三级就是那个位置。

**Step 7：建立共识工作坊机制（【经验】每场 2 天–1 周，跨地域再加协调成本）**

- 重大跨团队决策召开工作坊：中立 Facilitator 主持，时间盒【经验】1–3 天。
- 判据在讨论开始前发给所有参与者；选项先各自写（名义群体法）再集中讨论；收敛口径是「没有人认为不可接受」，不是全票同意。
- 会前确认参与者是否有权代表本团队让步。

- **产物**：工作坊剧本（判据前置 + 先独立写 + 时间盒）+ 结论如何回到签字位置的说明。
- **判据**：会后一周回访参与者，问「你在会上同意的方案，回团队后有没有被推翻」。有被推翻的，先查代表权，再查结论质量（[§3.2.9](09-cross-team-decision-section-3-sec3.md)）。
- **为什么必须这一步**：工作坊**不产生决策权**，它只输出一个可接受的方案。所以要等签字位置（Step 1）存在之后再开，否则会出现「共识有了但没人能签字」的中间状态，两周后重开一次。

**Step 8：建立跨团队沟通机制（持续，无终点）**

- 跨团队 Standup（【经验】每周 30 分钟）、跨团队频道、月度跨团队分享会、季度跨团队规划会；载体通常是 Slack / Microsoft Teams / 飞书 / 钉钉，需要同步讨论时用 Zoom / 腾讯会议。
- 频道与会议只是载体：**每条议题要么指向一份 RFC 或 ADR，要么当场登记成一条待归档决策。**

- **产物**：固定节奏的议程模板 + 一条「口头事项 → 归档」的登记规则。
- **判据**：抽 3 周的 Standup 议题清单，数其中有多少条能指回 RFC 或 ADR。全都是口头事项，说明沟通机制没有与决策流挂上 —— 它会持续制造「决定过但没人认账」。
- **为什么必须这一步**：它是把前七步接进日常的那一层。缺了它，RFC 与 ADR 只在「重大决策」时被想起，日常分歧仍然靠扯，而日常分歧的量远大于重大决策。

八步里最常被跳过的是 **Step 3 的 ADR 归档**与 **Step 1 里「A 唯一」这条校验**。跳过的症状在半年后出现：同一个议题第二次上会，且没有任何文件能说明上次为什么这么定 —— 决策寿命短于参与者在职时间，协调成本被全额重付一遍（[§3.5](09-cross-team-decision-section-3-sec3.md)）。

### 4.2 关键技术点

**把权责约束写成表格校验，而不是写进倡议（RACI / DACI 模板：Excel 或 Confluence）**

- **做法**：模板里加三条校验：A 非空且 ≤ 1；DACI 中 Driver ≠ Approver；C 名单的冻结时点 = 决定日。
- **机制**：因为校验发生在**登记那一刻**，所以「无人拍板」会在提交时暴露，而不是三个月后从事故复盘里反推出来；写进倡议则只能在事后追责。
- **失效条件**：**当 A 位置由不接触系统的管理者担任时**，矩阵仍然成立而判断质量下降。症状：事故复盘时每个人都能指出「那是我们组的事」，没有人说「那是我决定的」。
- **档位**：【公开】RACI 由项目管理体系推广、DACI 由 Atlassian 推广（可按各自官方材料当前版本核验）；【经验】本条不涉及需要实测的数字。

**RFC 的字段与时限（GitHub PR / GitLab MR / 自建 RFC 平台）**

- **做法**：RFC 进仓库或平台，PR 化提交 + Reviewers 制度；必填六项（上下文 / 提议选项 / 影响分析 / 回滚方案 / Owner / Reviewers）；设 Final Comment Period 的截止日期。
- **机制**：因为截止日期让「什么时候提还来得及」变成客观事实，异议被前移到决策之前；没有窗口时，受影响方只能在决定之后发声，而那时改动已经承诺出去了。
- **失效条件**：**当可见性只发给「发起人认为相关的人」时，必漏**。症状：公告发出后突然出现一个从未参与讨论的反对者；判定方式是看第一份 RFC 的评论者是否全部来自发起团队。
- **档位**：【公开】RFC 这一文档形式源自 IETF 的 RFC 系列（1969 年起，可按 IETF 官方档案核验）；【推算】跨团队一份 RFC 的人力 ≈ 起草 1 人日 + 每个相关方对齐 0.5 人日，相关方按 4–8 个计，得约 3–5 人日。

**ADR 归档：不可编辑 + 归档绑定出口 + Index 标签（log4brains / MADR / Backstage ADR Plugin）**

- **做法**：ADR 一经写下不再编辑，变更用新 ADR 覆盖；ADR Index 打「跨团队决策」标签；把归档挂在流程出口（不写不生效）。
- **机制**：因为结论不可改、只能被覆盖，决定当时所依据的约束被冻结在同一份文件里 —— 这是「半年后能区分判断错了与约束变了」的唯一技术前提。
- **失效条件**：**当决策频率上升而单份文档成本不降时**，归档会被绕过。症状：ADR 目录里只有几个样板案例，与实际发生的决策数量对不上；团队回到群里口头决定。
- **档位**：【公开】ADR 由 Michael Nygard 于 2011 年提出（可按键名核验）；【推算】单份 ADR 写作 + 评审约 0.5–1 人日，推导：写作 2–4 小时 + 一名非本人评审 1–2 小时。

**委员会的门槛与议程纪律（Confluence + 会议纪要模板 / Jira + Architecture Theme / #arch-board 频道）**

- **做法**：入会门槛写成可判定条件；材料在议程前交齐；会上只裁决；三类输出（ADR / 技术雷达档位 / 架构约束）都带复核日期。
- **机制**：因为材料前置把「先做后报」挡在议程之外，且席位常设使同类决策在不同 BU 之间口径统一 —— 一次裁决可复用多次。
- **失效条件**：**当提案数量增长而席位不变时**，团队会先做后报。症状：需要事后追认的决策占比持续上升；等待的代价由团队即时承担，而违反架构约束的代价滞后。
- **档位**：【推算】席位占用人力 ≈ 席位数 n × 每月 2 次会议 × 2 小时 = 4n 人时/月，n 取 5–10 得 **20–40 人时/月**（不含材料准备，按会议时长的 1–2 倍另计）；【经验】多数大型组织设有常设评审机构，但公开可比的决策质量数据不存在，不做效果断言。

**升级阶梯与时限（Jira Service Management / ServiceNow 一类工单系统承载）**

- **做法**：四级阶梯（团队内部 24h → 跨团队 Lead 48h → 委员会 1 周 → 高管）；每级写明输入、输出与超时行为；超期自动升级。
- **机制**：因为终止条件被写成「级 + 时限」，一次分歧有了确定的终点时间；而「继续开会」没有终点，议题会无限扩张并持续引入新的相关方（[§3.5](09-cross-team-decision-section-3-sec3.md)）。
- **失效条件**：**当每一级都能把议题退回上一级时**，阶梯反转成循环。症状：同一议题第 4 次上会仍无结论；观测信号是「同一议题的上会次数」。
- **档位**：【经验】24 小时 / 48 小时 / 1 周是常见量级，随组织决策链长度变化，不要照抄。

**Stakeholder Map 用来找否决权，不是用来排沟通（Miro / Figma / Lucidchart / Mural）**

- **做法**：逐议题重判象限；表里加一行「决定之后谁能让它停下来」；按四档定沟通策略（管理 / 重点 / 最小 / 告知）。
- **机制**：因为权力可以从组织外部临时获得而利益只有当事方知道，所以沟通资源要按「能否阻碍」而不是按「是否友善」分配 —— 最可能让决策返工的一方会被优先沟通。
- **失效条件**：**当象限只被用来安排会议邀请时**，决策会在公告后被推翻。症状：出现一个从未参与讨论的反对者，且他握有预算、法务或舆情手段。
- **档位**：【经验】该矩阵是利益相关方管理中被普遍使用的标准工具（可按「利益相关方管理 / power-interest grid」自行检索核验），本节不对其效果做断言。

**共识工作坊：判据前置 + 先独立写 + 代表权确认（Miro / FigJam / Klaxoon；投票工具 Mentimeter / Sli.do / Poll Everywhere）**

- **做法**：中立 Facilitator；时间盒；判据在讨论开始前发给所有参与者；选项先各自写（名义群体法）；投票工具只用于这一步的匿名采集，不用于最终裁决。
- **机制**：因为判据事前公布、选项先各自写，会议不会被最先发言者的框架锚定，也不会被现场临时发明的标准带偏；「无不可接受」比「全票同意」更容易达成且不要求任何人公开支持。
- **失效条件**：**当参与者不是各自团队里能让步的人时**，结论会在回去后被推翻。症状：结论在前一周被推翻、两周后重开一次；同意的成本落在工作坊现场，反悔的成本落在各团队内部。
- **档位**：【经验】时间盒 1–3 天 × 参与人数，跨地域另加差旅与协调。

**AI 辅助的边界：只做检索与起草，不动权责（LLM 起草 RFC / AI 协调员 / 共识构建助手）**

- **做法**：AI 用在三处 —— 检索历史 RFC / ADR 先例、起草与整理材料、生成相关方候选清单；不用在「谁签字」上。
- **机制**：因为 AI 降低的是**信息成本**，而跨团队决策的卡点通常在责任归属，所以材料变齐、讨论变快，但协调成本并未被触及；把 AI 当成权责问题的解，只会把问题掩盖起来。
- **失效条件**：**当「已经上了 AI 起草」被当作流程已改善的证据时**。症状：会上「谁签字」仍然答不上来，但流程文档看起来完备多了（[§3.5](09-cross-team-decision-section-3-sec3.md) 的最后一条反模式）。
- **档位**：【经验】——本条的判断依据是「A 栏能否说出一个具体人名」，与该 AI 用哪个模型无关。

### 4.3 工具链与平台

机制层面的对比见 [§7 与其他方法对比](09-cross-team-decision-section-7-sec7.md)。下表只回答一件事：**在你自己的约束下该选哪一类，以及不选它的代价是什么。**

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| RFC / ADR 平台 | GitHub / GitLab PR、Google Docs / Confluence、Notion Database、Log4brains、MADR、Backstage ADR Plugin、自建 RFC 平台（如 GitLab Handbook 形态） | 判据是「半年后还能不能被检索到」与「能不能 diff」：要版本与评审就用仓库 PR；要非技术方参与就用文档平台；ADR 静态站点（Log4brains / MADR）适合已积累大量 ADR 的组织 | 放在不可检索、不可版本化的载体里，等于没有归档：约束半年后还原不出来 |
| 架构委员会载体 | Confluence + 会议纪要模板（Meeting Notes）、Jira + Architecture Theme、#arch-board 频道 | 判据是「决策跟踪能不能脱离会议存在」：议题要有编号与状态，而不是只在纪要里 | 只靠纪要：下次会议时没人知道上次那件事最后怎么定的 |
| 相关方与协作白板 | Miro、Figma、Lucidchart、Mural | 判据是「这张图是一次性讨论素材，还是要长期引用的记录」：只做讨论可以用白板；要长期引用必须落成文档 | 用白板承载决策记录：图片不可 diff、不可检索，白板一归档就失传 |
| 投票与共识 | Mentimeter、Sli.do、Poll Everywhere、Loomio、Pol.is | 判据是「这一步要采集的是意见还是决定」：先独立写选项时用匿名投票；大规模意见聚合（Pol.is 一类）适合公开征集，不适合小范围不可逆决策 | 用投票决定不可逆决策：少数方的等效异议被票数淹没，会后以消极执行的形式回来 |
| 升级与工单 | Jira Service Management、ServiceNow | 判据是「时限能不能写进 SLA 并自动升级」；只有能自动升级的载体才能防止超期后继续开会 | 时限只写在文档里：超期无人触发，阶梯退化成又一轮同步会议 |
| 沟通载体 | Slack、Microsoft Teams、飞书、钉钉；Zoom、腾讯会议 | 判据是「议题能不能从消息里被登记成归档条目」，与品牌无关 | 决策只活在聊天记录里：不可检索、不可追责，人员一流动就断 |
| AI 辅助（2024–2025） | LLM 起草与整理（Claude / GPT-4 一类）、AI 协调员（AI Facilitator）、共识构建助手、Anthropic Constitutional AI、决策图谱类平台（Decision Intelligence Platforms） | 判据是「它降的是信息成本还是协调成本」；只在前者上有效，后者要改权责结构 | 把 AI 当成权责问题的解：材料更齐、会议更快，但 A 栏仍然填不出人名 |

这一类里最容易被误选的是**协作白板（Miro / Figma / Mural / Lucidchart）**：它便宜、会上立刻出图、参与者都熟悉，于是被用来承载 Stakeholder Map 甚至决策结论。问题不在白板本身，而在它的产物形态 —— 一张图**不可 diff、不可检索、不可引用**，而这三件事恰好是「半年后能区分判断错了与约束变了」的全部技术前提（[§3.2.4](09-cross-team-decision-section-3-sec3.md)）。判据很简单：这次的产物，能不能被一个不在场的人在搜索框里找到？

### 4.4 存量迁移

存量改造的读者只有这一节的顺序可循：**先登记、再分类、最后收双轨。**

**① 立刻见效且可回退的三件事。** 一是**给最近 5 次已发生的决策补填 RACI**（只补登记，不改流程）；二是**把已有会议纪要登记成 ADR 索引条目**（每条写三行：结论、当时的约束、被否决的选项），不重写、不复盘；三是**开一个只读的 RFC / ADR 归档目录**并允许全员检索。三件事都不改变任何人的工作方式，任何一件都能在一天内撤销 —— 这是存量改造能用它们开头的原因。

**② 历史资产怎么分类处理。** 全部返工不现实，按「修复时机」分三类：

| 历史资产 | 处理方式 | 判据 |
| --- | --- | --- |
| 已发生但没有记录的决策 | **只登记不复盘**：补写结论 / 约束 / 被否决选项三行，不重新开会 | 挂账条目是否写明了「下次被触碰时补齐」 |
| 有记录但无角色的决策 | 打标挂账，下次被触碰到时补 A 与 C 名单 | 新增决策是否从第一天就带 A 与 C |
| 有角色但 A 栏填团队名的决策 | 逐条确认到人；确认不了的就标成「无人拍板」，列入下季度议程 | 「无人拍板」的条数是否在逐季度下降 |

关键在第三类：**填团队名不是形式问题**。团队没有可以签字的手，也没有可以被追责的个人，所以这类记录在事故复盘里无法使用（[§3.5](09-cross-team-decision-section-3-sec3.md)）。把它们逐条标出来，比重新培训一轮流程有效。

**③ 双轨怎么维持、维持多久。** 双轨 = 新决策走 RFC / ADR，存量决策只登记。维持成本不是人力，而是**两套口径**：一套在会议纪要里、一套在归档里，两者会随各自改动漂移，漂移的表现是「同一个决策在两处写的被否决理由不一样」。所以双轨的时长不能用日历定，要用指标定 —— 真正决定能不能收的是「有记录的新决策占比」这一个数。

**④ 什么信号说明可以退出双轨。** 三个信号同时成立才收：**新发生的跨团队决策 100% 有归档**（连续两个季度）；**「先做后报」（需要事后追认）的比例在下降**；**至少有一个非发起方提出过异议并得到了书面回应**。第三条最容易被当作软指标跳过，但它恰恰是整套机制的验收条件：如果异议窗口从未真正产生过一条被回应的异议，那么流程只完成了「记录」，没有完成「协商」。缺任何一条就延长双轨 —— 提前收的代价是把一次没有记录的决策重新交还给会议与记忆。

### 4.5 模板 / 示例

**模板 1：RACI 矩阵**

| 决策 | R（执行） | A（负责，唯一） | C（咨询，决定前冻结） | I（通知，决定后告知） |
| --- | --- | --- | --- | --- |
| 选型 Kafka vs Pulsar | 数据平台组 | 首席架构师 | 业务方、安全、运维 | 全公司 |
| 合规变更（PII 加密） | 安全团队 | CISO | 法务、业务方、CTO | 董事会、客户 |

**怎么用**：只填你手上真实存在的决策，不要先造一张「组织级 RACI」；A 一栏必须是人名，填不出人名就说明这条决策还没有终止位置。

**模板 2：DACI 框架应用**

```
## DACI for ADR-{编号}：{决策标题}

- D（Driver）：@{推动起草、评审、合并的人}
- A（Approver）：@{最终拍板的人，通常 1 人}
- C（Contributors）：
  - @{角色}——{评估维度：能力 / 业务影响 / 合规 / 成本}
- I（Informed）：{团队 / 部门 / 法务合规}

## 时间表（【经验】量级，随参与方数量变化）
- W1：Driver 起草 DACI + ADR 草稿
- W2：Contributors 评审 + 修改
- W3：Approver 拍板
- W4：ADR 合并 + Informed 通知
```

**怎么用**：D 与 A 必须是两个不同的人，这是这个框架存在的全部理由；`{评估维度}` 一栏要写清每个 C 负责哪一维，写不出维度的 Contributor 只是 Reviewer。

**模板 3：RFC 模板**

```markdown
# RFC-{编号}：{标题}

## 摘要
{一句话提议}

## 动机
{为什么需要这个决策；不做会怎样}

## 提议
{具体方案}

## 选项对比
| 维度 | 选项 A | 选项 B | 选项 C |
| --- | --- | --- | --- |
| 性能 / 成本 / 团队 | ... | ... | ... |

## 影响范围
- 涉及团队：{列表}
- 影响系统：{列表}
- 回滚方案：{描述}

## 风险与缓解
| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |

## Reviewers
- @{必须 Review}
- @{建议 Review}

## 时间表
- Final Comment Period：{日期}
- Approver 拍板：{日期}
- 实施：{日期}

## 开放问题
- {问题 1}
```

**怎么用**：`{...}` 全部是留给你填的空；`选项对比` 与 `开放问题` 两节不要删 —— 只写结论的 RFC 与会议纪要没有区别，半年后无法区分「判断错了」与「约束变了」。

**模板 4：Stakeholder Map（权力 × 利益）**

```
                权力高
                  │
       ┌──────────┼──────────┐
       │  保持满意 │  重点管理 │   ← 决定前充分沟通
   ────┼──────────┼──────────┼──── 利益
       │  最小努力 │  保持告知 │   ← 决定后通知即可
       └──────────┼──────────┘
                  │
                权力低

- 重点管理：{高权力 / 高利益}      保持满意：{高权力 / 低利益}
- 保持告知：{低权力 / 高利益}      最小努力：{低权力 / 低利益}
- 必然填一行：决定之后谁能让它停下来？ → {人名 / 角色}
```

**怎么用**：象限只决定沟通投入，不决定谁能否决；「必然填一行」那一格才是这张表的用途 —— 空格、或者答案落在「最小努力」里，都说明这张表还没做完。

**模板 5：Escalation 阶梯**

```
Level 1  团队内部解决（【经验】24 小时）
  ├── 输入：分歧的具体条款      └── 超时：自动升级到 Level 2
Level 2  跨团队 Lead 协商（【经验】48 小时）
  ├── 输入：双方各自的约束      └── 超时：自动升级到 Level 3
Level 3  Architecture Board 评审（【经验】1 周）
  ├── 输入：影响面 / 备选 / 成本 └── 输出：裁决 ADR（含否决理由）
Level 4  高管决策（CTO / VP）
```

**怎么用**：四级的时限要落在工单系统的 SLA 里而不是文档里；每级的「输出」栏必须写清是一条决策还是一次升级，两者混写会让阶梯退化成又一轮会议。

**模板 6：AI 辅助 Stakeholder 分析**

```python
import os
import anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

def analyze_stakeholders(decision: str) -> str:
    """基于决策描述输出相关方清单与沟通策略。"""
    prompt = f"""你是一名组织行为学专家。请基于以下决策描述做利益相关方分析。

## 决策描述
{decision}

请输出：
1. 利益相关方清单（角色 / 团队 / 个人）；
2. Power-Interest 评分（权力 × 兴趣，1–5）；
3. 沟通策略（管理 / 重点 / 最小努力 / 告知）；
4. 潜在冲突：谁可能反对、为什么；
5. 决定做出之后，谁能让它停下来。

输出 Markdown。"""
    msg = client.messages.create(
        model=os.environ["LLM_MODEL"],  # 模型标识按官方文档当前版本填写
        max_tokens=3000,
        messages=[{"role": "user", "content": prompt}],
    )
    return msg.content[0].text

print(analyze_stakeholders("把主力模型从单一模型迁移到多模型路由，涉及成本、合规与 SLA"))
```

**怎么用**：只改最后一行那句决策描述。输出是**候选清单**而不是结论，尤其第 5 条 —— 模型读不到组织里的非正式权力（谁和谁有历史、谁欠谁一次人情），那一格必须由人填；模型标识从配置读，不写死在代码里。

### 4.6 成本：这套东西的账单

跨团队决策不买服务器，账单几乎全在人时上——它的主项是**协调成本**，不是计算成本。三类成本里只有「人力」真正成立：没有硬件；云账单最多是 RFC / ADR 平台的席位费，通用拆分与 FinOps 方法在 [11-cross-cutting/03-data-cost-finops](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)，本节不复述。

主项是**一次决策吃掉多少个会**。推导：一次跨团队决策的会议人时 ≈ 参与方数 n × 每方到场人数 m × 单次时长 t × 修订轮次 r。以【经验】取值 n=6、m=2、t=1.5h、r=3，得 6×2×1.5×3 = 54 人时；一个工程师一周约 40 人时，即单次决策约 1.4 人周【推算】。这个数随参与方数量线性增长，与决策的技术难度几乎无关——这正是它与「架构选型」成本结构的分水岭：选型的成本随数据量增长，跨团队决策的成本随**能说「不」的人数**增长。

为什么这个主题贵在这里：**它的算法是共识与权责分配**。§2.2 的「最优决策权分配 = 信息 × 激励 × 协调成本」里，唯一能靠流程设计压下去的只有协调成本那一项，而它的分子就是上面那个乘积。§4.4 反复要求 A 栏写到人名，作用就是把「多少方能否决」这个乘数压到 1。

第二项最容易被漏记的是**记录成本**：每条 ADR / RFC 的起草与评审【经验：随变更爆炸半径与合规要求定，无变更历史的旧决策可只登记三行】。它不产出可展示成果，因而最常被省——省掉它，协调成本会在半年后以「同一个决策被重新讨论一遍」的形式回来，且那时的参与方通常比第一次更多。

### 4.7 容灾与故障演练

这里的「容灾」不是跨地域切换：一个会议流程没有可以 failover 的机房，硬做双活只会制造第二套口径。本主题真实的失效形态有三种：**决策单点**、**升级链路断裂**、以及**异议窗口从未产生异议**。所谓演练，就是把这三条逼到台面上。

| 失效模式 | 影响面 | 降级策略 | 演练方案 | 恢复目标 |
| --- | --- | --- | --- | --- |
| A 栏那个人休假 / 离职 | 该决策无限期搁置 | 每个 A 指定一名书面代理 | 抽一个在途议题，问「A 明天不在，谁签字」 | 【经验】代理能答上即视为有人负责；答不上即判定该条无 A |
| 委员会超期不升级 | 议题沉底，无人再提 | 时限写进工单并自动升级 | 翻上季度议程，数超期项有没有被自动升级过 | 【经验】升级要在时限前触发，而不是超期后再开一次会 |
| 异议窗口从未产生异议 | 流程只完成「记录」，未完成「协商」 | 指定一名非发起方做红队 | 数归档里「由非发起方提出、并被书面回应」的异议条数 | 【经验】连续两个季度为零即判定窗口失效 |

RTO / RPO 在这里用【经验】区间，而不是公开指标：它们描述的是「多久恢复决策能力」，不是数据恢复点。跨地域容灾与混沌工程的一般方法论见 [12-architecture/07-disaster-recovery](../../12-architecture/07-disaster-recovery/07-disaster-recovery.md) 与 [12-architecture/06-chaos-engineering](../../12-architecture/06-chaos-engineering/06-chaos-engineering.md)；本节只列跨团队决策特有的这三种失效。

### 4.8 演进路线：0 → 1 → 100

**0 → 1（最小可用）**：一张只填最近 5 次真实决策的 RACI，加一个只读归档目录（§4.4 ①）。几乎不花钱——半个人日即可。**先坏的是 A 栏**：一填就发现写的是团队名，而不是一个能签字的人。这一步的验收标准是「A 栏数得出人名」，不是「表格填满」。

**1 → 100（规模化）**：上 RFC / ADR 平台、委员会，并把升级时限写进工单系统（§4.3）。**变贵的是**平台维护人时与委员会会议人时——成本从「单次决策」变成「一套常设机制」的固定开销；**先坏的是升级链与异议窗口**：委员会一旦不按时限升级，阶梯就退化成又一轮同步会议；异议窗口没人用，流程便只剩记录功能。

**100 →（下一道坎）**：规模上去后，坎不在工具，而在**判断口径**——把「已经上了 AI 起草」当成流程已改善的证据，而 A 栏仍填不出人名。§5 里被点名的 AI 协调员与决策图谱在本主题下都是 L3（只记录、不投入）：不在治理流程里给 AI 协调员预留位置，也不把架构建立在决策图谱的推理结果上。它们共有的坎是**AI 只降信息成本，不降协调成本**——材料更齐、会议更快，但 §2.2 那个乘积里的「谁能终止决策」并未改变。真到没到 100 阶段，只看一个数：被书面回应的异议条数有没有随规模上升。

- [ ] ADR 与决策的绑定是不是在流程出口（不写不生效），还是只写在文档规范里？
- [ ] 上一季度上过会的议题里，「可逆且单团队」的占比是多少？超过一半就该下放。
- [ ] 每个议程项与每个 Agree / C 角色是否有时限？无时限的把关等于无限期搁置。
- [ ] 上一季度的升级里，主动升级（时限前）与超期升级各占多少？
- [ ] 上一次工作坊后一周，有参与者的结论被本团队推翻吗？会前是否确认过代表权？
- [ ] 抽 3 周的跨团队 Standup 议题，有多少条能指回一份 RFC 或 ADR？
- [ ] 抽 3 周的决策公告，公告发出后出现的反对者里，有多少是事后才第一次参与的？
- [ ] 「先做后报」（需要事后追认）的决策占比，比上一季度是升还是降？
- [ ] 归档里有没有一条由非发起方提出、并被书面回应的异议？没有则异议窗口尚未生效。

### 4.10 小结

> 本节小结：整个落地过程里唯一决定成败的环节是 **Step 1 里「A 收敛到一个人名」这条校验** —— 它只是一格表格，却决定了后面七步是「把决策接进治理」还是「把讨论记录得更详细」。判据具体到一个动作：把最近 5 次决策的 A 栏摊开，看有几个人名。其余每一步都更显眼、更容易立项（RFC 平台、委员会、工作坊），但没有一步能替代这个位置；反过来说，A 收不到人时，RFC 与 ADR 仍然值得做 —— 它们至少能让「无人拍板」留下可核对的痕迹。
>
> 💡 **思考锚点**：把最近 5 次跨团队决策的 RACI 表摊开，数 A 栏里有几个人名——这是 4.9 自检清单第一条，也是 4.10 认定的唯一决定成败环节。答不出具体人名的那些决策，你打算先补 RFC / ADR 的留痕，还是先补那一个「能让它停下来」的人名？
