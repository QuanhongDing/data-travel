## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

打分表把「不评审 / Lightweight / Formal / ATAM / AI 辅助」放在同一张 1–5 分的表里，比「评审深度 / 评审速度 / 跨团队对齐 / 反模式识别 / 适用规模 / AI 友好度」六个维度。这个做法有两个结构性错误。

**错误一：这五件不是同一层的产出，而且可以叠加。** 「不评审」是**不做**；「Lightweight / Formal」解决的是**闸门放在哪一层**；「ATAM」解决的是**用什么分析框架**；「AI 辅助」解决的是**谁来做这件事**。一个「由 AI 辅助的正式评审、用 ATAM 做场景分析」是完全成立的组合，而打分表把它做成了五选一的单选项。给它们打分，等价于给「不装锁 / 装门禁 / 装监控 / 装保险柜 / 请保安」打分——它们不是备选项，是五件可以同时装上、且必须按顺序决定的事。

**错误二：同一维度的权重随「失败后果」反转。** 「评审速度」在内部工具与实验性变更上权重接近全部（评审成本 2.5–3.5 人天已经超过变更本身的实施成本，见 7.4 的推算），在资金链路、合规链路、跨系统依赖上权重接近 0（一次事故的代价远超十次评审会）。打分表给 Formal 与 Lightweight 各打一个固定的「评审速度」分，隐含假设是「变更后果相近」；而在关键资产上，正确答案是「慢一点没关系，但必须拦住」。

打分表输出的是**排名**，而架构评审选型要的是「**在我这个组织的约束下，闸门放在哪一层、用什么判定标准、结论挂到哪里**」。更具体地说，本章要回答三个可被验证的问题：**(1) 它拦在缺陷修复成本曲线的哪一段？(2) 覆盖 N 个系统的成本随 N 怎么增长？(3) 结论不被遵守时会发生什么？** 一个不能回答「什么条件下它失效」的选型建议，本质上还是打分表。

**本章采用的 6 条判据**（每条针对架构评审主题具体化）：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 拦下缺陷的时点 | 它发生在缺陷修复成本曲线的哪一段 | 评审不产出功能，全部价值来自时点前移；晚于设计冻结的评审，价值上限是「事后追认」 |
| 可判定性 | 检查项是「是否回答了 X」还是「是否足够好」 | 不可判定的问题在会议上靠音量收敛，产出方差极大且无法被第三方复核 |
| 约束力来源 | 不通过会有什么代价？结论挂在哪个环节 | 零代价的结论在工期压力下必被跳过——这是激励问题，不是态度问题 |
| 覆盖成本函数 | 覆盖 N 个系统的成本随 N 怎么增长 | 可做判断的专家人时近似固定（培养周期以年计），成本线性增长 → 覆盖率必然饱和 |
| 产出物形态 | 输出「通过 / 不通过」还是「带优先级与责任人的改进项」 | 结论式产出引发对抗与辩护，动作式产出可直接执行、可跟踪 |
| 寄生在哪个流程上 | 它挂在 CI、变更单、预算还是审计上 | 评审不是独立系统；不寄生在某个已有流程上的评审会被工期第一个挤掉 |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 不评审（No Review） | 基线：零闸门 | 无判定、无记录，全靠生产反馈暴露问题 | 早期原型、极低后果变更 | — |
| Lightweight Review（PR 审查 + 清单） | 日常闸门 | 异步同侪评审，挂在合并点，不占会议时间 | 多数工程团队 | 开源实践 |
| Formal Review（设计评审会） | 中大型变更闸门 | 材料 + 会议 + 决议，靠在场者的判断与共识 | 企业 IT、金融 | 流程 |
| ATAM（SEI） | 战略级质量属性权衡 | 场景驱动，`Utility = Σ w_i × Score_i`，权重来自干系人共识 | 大型系统、政府 / 国防 | 公开方法论（SEI，2000） |
| CBAM（SEI） | 成本收益排序 | 在 ATAM 的场景上叠加成本估算，用于排序取舍 | 同 ATAM | 公开方法论 |
| ARID | 中间设计的主动评审 | 只评审「正在设计的那一部分」，缩小评审对象规模 | 迭代中的系统 | 公开方法论（SEI） |
| Architecture Review Board（架构委员会） | 组织级治理 | 分层（哪些变更必须上会）+ 例外审批权 | 多 BU 大企业 | 组织机制 |
| AWS Well-Architected Review | 云架构标准化 | 清单 + 评价标准 + 产出模板，团队自助开展 | 云上团队 | 公开框架 |
| Checklist（评审清单） | 可判定化 | 把「好不好」换成「答没答」，标准写在纸面上 | 全体 | 公开实践 |
| Scenario-based Review | 用场景替代抽象维度 | 用具体场景（峰值、故障、扩容、回滚）检验设计 | 全部 | 方法论 |
| Pre-Mortem（事前验尸） | 对抗乐观偏误 | 假设「这事已经失败了」，倒推失败原因 | 高风险项目 | 公开方法论（Klein, HBR 2007） |
| Red Team / Blue Team | 对抗性评审 | 设专门角色主动寻找攻击路径与绕过方式 | 安全敏感系统 | 方法论 |
| ADR | 决策归档 | 把决议连同「被否决的选项与理由」写下来 | 全部 | 轻量实践（Nygard，2011） |
| 评审历史库 / KG | 经验复用 | 把评审结论结构化，供后续检索与比对 | 大型组织 | 自建 |
| AI-assisted Review | 加速 | LLM 做清单覆盖、材料一致性、反模式提示 | 平台团队 | 商业 / 自建 |
| Continuous Review（Living Review） | 常态化 | 评审寄生于 CI/CD，随架构生命周期持续发生 | 平台团队 | 实践 |

这 16 项其实分**五族**：**闸门族**（不评审、Lightweight、Formal、ARB、Continuous）、**分析族**（ATAM、CBAM、ARID、Scenario-based、Pre-Mortem、Red Team）、**标准族**（Checklist、AWS Well-Architected 类框架、ADR）、**复用族**（评审历史库 / KG）、**加速族**（AI 辅助）。

**先分族再选，能省掉一半比较**：你不需要比较「ATAM 和 Checklist 哪个好」——它们回答的是「用什么框架分析」和「判定标准写在哪」两个不同问题，可以叠加。真正需要比较的只有同族内部：「闸门放合并点还是放委员会」「分析用场景法还是对抗法」。决策树把「日常变更 → Lightweight」「中型变更 → Formal」「战略级 → ATAM」「云架构 → AWS WA」「AI 智能体 → AI 辅助」并列成互斥分支，其中前三条是**同一个问题的不同答案（闸门深度）**，而 AWS WA 属于标准族、AI 辅助属于加速族——它们可以与任何一种闸门深度并存，不是并列选项。

上表只列机制，不列「某工具是否支持某检查项」这类静态断言。凡涉及具体能力与产品，请用下面三种判定方法自行核验：

- **闸门是否真的拦得住**：找一个「本应被拦但没被拦」的变更，回溯它在现有流程里经过了哪一步；如果答案是「这一步在流程上不存在」，那么你的闸门只存在于文档里。
- **检查项是否可判定**：把某一条检查项交给两个不同的人，看他们能否给出相同结论。给出不同结论的项，需要补判定标准而不是补培训。
- **评审产出的下落**：跟踪上一季度 10 条评审结论，看有多少条进入了后续跟踪或显式记录为接受风险。数字很低说明评审处于「无挂点」状态。

### 7.3 机制差异：为什么它们表现不同（核心节）

五族之间的表现差异可以完整归因到四个机制维度。选这四个，是因为它们分别对应选型时必须先回答的四个问题：**拦在缺陷成本曲线的哪一段（7.3.1）· 检查项能不能被判定（7.3.2）· 结论有没有代价（7.3.3）· 覆盖成本随系统数怎么变（7.3.4）**。每个维度给出「机制 → 因果 → 公开证据 → 失效条件 → 自验方法」。

#### 7.3.1 时点：评审的全部价值来自缺陷修复成本曲线的斜率

**机制是什么**：架构评审不产出功能，它的唯一产出是「在更早的时点发现问题」。因此它的价值等于「被提前发现的缺陷数 × 该缺陷在两个时点上的修复成本之差」。时点越早，斜率越陡，价值越大。

**各候选的实现差异**：

| 候选 | 评审发生在 | 能前移的缺陷类型 | 到了实施后才发现时 |
| --- | --- | --- | --- |
| 不评审 | 不在任何时点 | 无 | 全部由生产事故与用户反馈暴露 |
| Lightweight（PR） | 代码合并前 | 实现层（接口、依赖、配置、边界） | 代码已写，改动限于本 PR 范围 |
| Formal Review | 设计评审会（常在方案定稿后） | 设计层（分层、边界、数据流） | 方案已获共识，改动要重走一遍评审 |
| ATAM | 需求 / 架构阶段（场景分析） | 质量属性之间的取舍（性能 vs 可用性 vs 安全） | 取舍已固化在架构里，改动等于重构 |
| Pre-Mortem | 方案确定之前 | 「没想到的失败模式」 | 失败模式直接在生产暴露 |
| Continuous Review | 全生命周期 | 架构漂移（每次小改动造成的侵蚀） | 侵蚀累积到无法局部修复 |

**由此必然导出的性质**：**因为**架构缺陷的修复成本随发现时点后移而上升，**所以**一个发生在设计冻结之后的评审，其价值上限就是「事后追认」——它能产出的最好结果也只是「下个版本再改」，而这恰恰是团队在工期压力下不会做的事，于是评审彻底失去意义；**又因为** Formal Review 的排期周期（通常以周计）可能长于部分变更的整个实施周期，**所以**在快速迭代的团队里，正式评审会被自然地推迟到「已经做完」之后——这不是执行不力，而是**排期的时间常数与迭代的时间常数不匹配**。这条机制解释了为什么 ATAM 这类强分析框架在敏捷团队里普遍失效：**ATAM 的分析能力没有问题，它失效在排期上**；这也解释了 ARID 为什么存在——它把评审对象从「完整架构」缩小到「正在设计的那一部分」，本质上是在**缩短从「可评审」到「已实施」的时间差**。

**公开证据**：缺陷修复成本随阶段后移而显著上升，这一结论出自 Boehm《Software Engineering Economics》（1981）【公开，1981】；公开材料常把设计阶段与生产阶段的差距概括为「一个数量级以上」，但**具体倍数随项目差异极大，不应引用精确值**【公开，1981；倍数不可移植】。ATAM 由 SEI 在 2000 年公开（SEI 技术报告）【公开，SEI，2000】。ARID 是 SEI 针对「中间设计」提出的同类方法，但其公开年份在可查材料中并不统一，本节按证据纪律不注具体年份——按方法名检索 SEI 的公开技术说明即可自行核验（交叉引用见主文件 §1.1）。ARID 的出现本身即是对「评审太晚、太重」这一失效的公开回应。

**失效条件**：当变更后果小且可回滚时，把评审时点前移没有净收益（前移的成本高于损失期望）。判断方式：问「如果晚发现，我们损失什么」，若答案只能是「多改几行代码」，就不需要前移。

**自验方法**：抽查最近 10 次变更，记录「评审发生」与「第一行代码写下」的先后顺序。若多数评审发生在代码之后，你的评审在机制上只能做追认——此时提高评审质量是徒劳的，要改的是触发点。

#### 7.3.2 可判定性：清单把「好不好」换成「答没答」

**机制是什么**：一个检查项只有在存在客观判定标准时，才能在不同人之间产生一致答案。清单（Checklist）的作用不是「增加检查点」，而是把「这个架构好不好」这种**不可判定**的问题，替换成一组「是否回答了 X」的**可判定**问题。

**各候选的实现差异**：

| 候选 | 检查项形态 | 判定标准在谁手里 | 结论一致性 |
| --- | --- | --- | --- |
| 无清单的 Formal Review | 「方案是否合理」 | 在场评审人的经验 | 低：随人、随会、随状态变化 |
| Checklist | 「是否定义了降级路径」 | 写在清单里 | 高：可被第三方复核 |
| ATAM | 「场景 S 下该质量属性如何满足」 | 场景 + 权重（干系人共识） | 中高：权重可追溯，但打分仍偏主观 |
| AWS Well-Architected 类支柱清单 | 「某支柱下的某一项是否满足」 | 清单 + 官方文档 | 高：可自助、可横向对比 |
| 评审历史库 / KG | 「上次类似方案出过什么问题」 | 历史案例 | 中：取决于案例质量与检索能力 |

**由此必然导出的性质**：**因为**不可判定的问题在会议上只能靠「谁资历高 / 谁声音大」收敛，**所以**无清单评审的产出质量与「在场者的资历」强相关，方差极大，且结论无法被第三方复核；**一旦把标准显式写进清单**，产出质量就从「依赖在场的人」转为「依赖标准本身」——这正是评审能被**产品化**（让没有顶级架构师的团队自己开展）的机制原因，也是「Formal 跨团队对齐」这个直觉的真正来源：**提供一致性的不是「开会」这个动作，而是写下来的判定标准**。**也因此**，清单的**维护责任**比清单的**存在**更重要——没有维护人的清单会过期，而过期的清单比没有清单更危险，因为它让团队对一个已经失效的标准产生了信任（这也是 §6 案例里「案例库沉淀 + 标准随演进更新」被单独列为核心创新的原因）。

**公开证据**：AWS 把架构评审拆成「清单 + 评价标准 + 产出模板」三件套并让团队自助开展，专家转为抽查、疑难裁决与标准维护；AWS Well-Architected Framework 现列六大支柱（运营卓越 / 安全 / 可靠性 / 性能效率 / 成本优化 / 可持续性），其中可持续性支柱为后期增补【公开，AWS Well-Architected Framework 官方文档，2015 年首版、其后持续修订；支柱清单的中文整理另见 [02-tradeoff-frameworks §6 案例 6.1](../02-tradeoff-frameworks/02-tradeoff-frameworks-section-6-sec6.md)】。可自行核验的判定方法：打开任一支柱，看它的检查项是「是否回答了 X」形态还是「是否足够好」形态——公开文档里几乎全部是前者。

**失效条件**：当检查项本身是错的（把无关项当成必需项）时，清单会产生**系统性的错误一致**——所有人按同一个错误标准放行，这比无清单更危险。判断方式：对每一项问「如果删掉它，我们错过的最坏情况是什么」，答不上来的项应当删除。

**自验方法**：让两个不同团队各拿同一份清单评同一个方案，比较结论差异。差异大说明检查项不可判定（或缺少判定标准），需要重写清单而不是加强培训。

#### 7.3.3 约束力来源：结论挂在哪个环节，决定「遵守」是不是默认

**机制是什么**：评审结论被遵守的程度，不取决于结论的说服力，而取决于**不遵守的代价**。结论挂在哪里（会议纪要 / 合并门禁 / 例外审批 / 跟踪列表 / 系统指标 / 审计），决定了它是否默认被执行。

**各候选的实现差异**：

| 候选 | 结论挂在哪 | 不遵守的代价 | 实际结果 |
| --- | --- | --- | --- |
| 只写会议纪要的 Formal Review | 文档 | 无 | 工期紧张时第一个被跳过 |
| Lightweight（PR + 必填检查项） | 合并门禁 | 无法合并 | 默认执行（不依赖自觉） |
| Architecture Review Board | 例外审批权 | 拿不到例外、项目被卡 | 默认执行（但可能拖慢所有项目） |
| 评审 + ADR | 决策记录 | 无（但可被后人检索） | 弱约束，长期对齐价值 |
| 评审结论进跟踪列表 | 季度回看 | 被点名 | 中等 |
| 评审绑系统指标 | 指标看板 | 指标不达标被看见 | 中等（见 §6 案例 6.3 字节） |

**由此必然导出的性质**：**因为**「违反结论」的代价为 0 时，团队在工期压力下跳过评审是**理性选择**，**所以**把评审走过场归因于「团队不重视」永远不会改善局面——这是激励设计问题，不是态度问题；**反过来**，**因为**把结论挂到合并门禁后「不遵守」在技术上不可能（合并被拒），**所以**同一份清单仅仅换一个挂点，遵守率就会从「看人」变成「看机制」。这一条也解释了 §6 阿里案例里「评审前置」与「分层」为什么必须同时做：**前置解决时点、分层解决覆盖，而两者都需要一个挂点（例外审批权）才具备约束力**——只有前置而没有挂点，评审仍然只是建议。

**公开证据**：门禁型的挂点属于工程实践，可由你自己的 CI 配置立即核验（把某一检查项设为合并的必要条件，看它是否真的拦住了一次变更）。组织层面的对照来自 DORA 的跨行业调研：以「外部审批（变更审批委员会）」作为变更必经环节与交付性能呈**负相关**，而「同侪评审」呈正相关【公开，Forsgren / Humble / Kim《Accelerate》2018 及 DORA 年度报告；这是跨行业调研的相关性结论，不构成因果证明，但与本节的成本函数推导方向一致】。这条证据支持的结论不是「不要评审」，而是：**闸门应由同侪评审承担，委员会应退到例外审批与争议裁决的位置**。

**失效条件**：当挂点过严（例外流程和正常评审一样贵）时，团队会选择**绕过**而不是走例外——例如把一次变更拆成多个「不需要评审」的小变更。判断方式：观察例外申请数与「小变更」数是否同时上升。

**自验方法**：统计上季度评审结论中有多少进入跟踪、多少被显式记录为「接受风险 + 理由」。若两者之和远小于结论总数，说明结论挂在了没有代价的地方。

#### 7.3.4 覆盖成本：专家人时近似固定，系统数线性增长 —— 分层与 AI 的真实位置

**机制是什么**：覆盖率 ≈ 可评审的专家人时 ÷（单次评审人时 × 系统数 × 每系统年变更次数）。分子（有资格做判断的人 × 可投入人时）近似固定——架构判断能力的培养周期以年计；分母随系统数与变更频次增长。

**各候选的实现差异**：

| 候选 | 改的是分子还是分母 | 对覆盖率的作用 |
| --- | --- | --- |
| 专家逐场评审 | 都不改 | 覆盖率 = 专家人时 ÷ 系统数，必然饱和 |
| 分层评审（按失败后果） | 改**分母的加权方式**：把有限人时按影响面分配 | 关键系统覆盖率高，长尾系统交给清单 |
| Checklist + 自助 + 专家抽查 | 改**分母的单次人时**（逐项检查交给团队自己） | 覆盖率随团队数量增长，而非随专家数量增长 |
| 评审历史库 / KG | 提升**分子的等效产出**（同一专家人时覆盖更多「类问题」） | 覆盖率提升，但依赖案例库质量 |
| AI 辅助（清单覆盖检查） | 改**分母的单次人时**中「可枚举部分」 | 覆盖率提升，且只在可枚举项上有效 |

**由此必然导出的性质**：**因为**分子近似固定而分母线性增长，**所以**「每个系统都由专家评审」这条路在系统数增长后**在算术上不成立**——把有限人时平摊下去，每个系统分到的评审时间趋近于零，此时评审必然退化为走过场；**所以**分层不是妥协，是唯一可行解，它的正确做法是把人时**按失败后果加权分配**，而不是平均分配。**又因为** AI 辅助改的是「单次评审人时」中**可枚举**的那一部分（清单项是否被回答、材料是否齐全、字段是否一致、方案描述与图表是否自相矛盾），**并且因为**架构权衡需要「对本组织约束的了解」这类无法从材料里读取的上下文，**所以** AI 在这件事上的正确位置是**清单覆盖率检查与材料一致性检查**，而不是「判断这个架构好不好」——把 AI 放在后者，得到的是无法核验的结论，而且它会以权威形式进入决议，纠错成本高于节省的检查时间。

**公开证据**：AWS 的评审产品化路径与本节推导一致——用「清单 + 标准 + 模板」把逐项检查交给团队，把专家从「逐场到场」转为「抽查 + 疑难裁决 + 标准维护」【公开，AWS Well-Architected Framework 官方文档，2015 年首版、其后持续修订；中文整理另见同目录 §6 案例 6.1】。AI 辅助评审方面，业界公开的能力描述集中在材料检查、清单覆盖与反模式提示，而非替代架构判断【经验，各厂商公开产品说明可直接核验；具体某项能力是否支持，请查其官方文档与 release note，不要引用二手描述】。

**失效条件**：当系统数量少到分层本身的管理成本高于其收益时（典型是 5 个以内的核心系统【经验】），直接全量评审更省事；当 AI 被用在不可枚举的判断项上时，其收益转负（错误结论的纠正成本高于节省的检查时间）。

**自验方法**：列出组织里「有资格做战略级架构判断」的人及其可投入人时，除以「关键变更的年次数」，得到人均负载。若该值超出个人可承受范围，说明分层阈值定得太松（太多变更被标为关键），应上调阈值，而不是在每一场上加深度。

### 7.4 成本结构对比（不是价格表，是成本函数）

各候选的成本**随什么变量增长**：

```
评审总成本 ≈ 材料准备（∝ 变更复杂度）
           + 评审人时（评审人数 × 时长）
           + 等待成本（排期延迟 × 变更被阻塞的时长）   ← 最被低估
           + 改进项落地成本（收益的来源，却最常无人预算）
```

**主导项与隐性成本**：

| 候选族 | 主导项 | 隐性成本 |
| --- | --- | --- |
| 闸门族（不评审 / Lightweight / Formal / ARB / Continuous） | 排期等待 + 评审人时；族内「不评审」这一基线的显性成本为 0 | **绕过行为**：挂点过严时团队会拆小变更绕过闸门；**委员会成为瓶颈**时所有项目一起变慢；选「不评审」则是把**事故成本与返工成本**全额推迟到生产环境——它不是零成本 |
| 分析族 | 材料准备 + 场景讨论人时 | 分析产出**无人消费**——ATAM 的场景清单如果没接进设计文档，就只是一次会议记录 |
| 标准族 | 清单编写与维护 | 清单过期（比没有更危险）；**检查项错误导致系统性错误一致** |
| 复用族 | 案例库的结构化录入 | 案例质量下降后检索结果不可信，专家被迫重新判断 |
| 加速族 | 工具与提示词维护 | **AI 结论被当理由写进 ADR**——理由必须是可核验的机制，不是一段生成文本 |

**为什么把「隐性成本」单列**：显性成本（会议时间、材料撰写、排期延迟）在日历上可见，于是被高估，进而导致「干脆不评审」；隐性成本（绕过、清单过期、分析无人消费、AI 结论混入决议）不出现在任何预算行里，于是被系统性低估。两者的相对量级随**失败后果**反转——**因为**显性成本大致与变更数量成正比（每次评审 2.5–3.5 人天量级，见下），**而**隐性成本里最大的一项是「没拦住的缺陷在生产的修复成本」，它随单次事故的后果放大而不是随次数放大，**所以**在低后果场景上「不评审或轻量评审」是理性的，在高后果场景上「多花几个人天」是明显划算的。这条反转直接给出 7.5 的第一条阈值：**分层依据必须是失败后果，不是变更大小**。

**【推算】数量级示例**（推导链完整给出，参数可替换重算）：

- 一场 5 人 × 2 小时的正式评审，**会议本身 = 5 × 2 = 10 人时**；材料撰写按 2 人 × 3–5 小时 = 6–10 人时、与会者预读按 5 人 × 0.5 小时量级 = 2–4 人时【经验】，决议整理与改进项登记 = 2–4 人时；四项相加 = 10 + (6–10) + (2–4) + (2–4) = **20–28 人时**，按 **8 人时/人天**折算 ≈ **2.5–3.5 人天/次**【推算】。
- 若一个团队每月开 4 次正式评审 → 4 × 2.5–3.5 = **10–14 人天/月** → ×12 = **120–168 人天/年**；按「**1 人年 = 250 工作日**」这一折算基数换算 → 120÷250 ≈ 0.48、168÷250 ≈ 0.67，即 **0.5–0.7 人年/年**【推算；250 工作日/人年是本节给定的基数，若取 220 则得 0.55–0.76 人年/年，参数可替换重算】。
- Lightweight（PR + 清单）评同一个变更：约 2 名评审人 × 2 小时 = 4 人时（含清单填写）→ 比正式评审低约 **5–7 倍**（20–28 人时 ÷ 4 人时）【推算】。这个倍数决定了「日常变更走轻量、关键变更走完整」的分工。
- 由此得到一条可用的门槛：**当一次变更的实施人力 ≤ 评审成本（2.5–3.5 人天）时，走正式评审是净负收益**，除非该变更的失败后果远超实施成本。换言之，**决定要不要上正式评审的变量是「失败后果量级」，不是「变更代码量」**——这条门槛正是「小改动大后果」（改一个字段类型、改一处权限配置）必须被拦住的机制依据，也是 §6 字节案例里把评审绑到系统指标而非代码量的原因。
- 覆盖率上限的推算：若组织里有 3 名可做战略级评审的架构师、每人每年能投入 30 天 → 3 × 30 = **90 人天/年**；一次**战略级**完整评审的参会人数与材料量都高于上面的典型值（跨系统、8–10 人 × 2 小时 + 材料 + 跟进），按 **5 人天/次**计（高于 2.5–3.5 人天/次的典型值，差额来自参会规模）→ 90 ÷ 5 = 每年最多约 **18 次**完整评审【推算】。若关键变更每年有 100 次，覆盖率上限 = 18 ÷ 100 ≈ **18%**——**这就是「全量上会」在算术上不成立的原因**，分层不是态度问题，是唯一可行解。

**不同处境下的主导项不同，所以优先级不是固定的**：

| 你的处境 | 成本公式里的主导项 | 因此第一优先 |
| --- | --- | --- |
| 原型 / 实验性变更 | 评审的固定成本（2.5–3.5 人天 > 变更本身） | 不评审，但登记并设一个「升级为关键时的条件」 |
| 日常 PR 级变更 | 评审人时（可压缩） | Lightweight + 清单，把结论挂到合并门禁 |
| 关键资产（资金 / 合规 / 跨系统） | 未拦住的事故成本 | 完整评审 + 场景分析法 + Pre-Mortem，且必须在设计冻结前 |
| 系统数远超专家容量 | 覆盖率（分子固定、分母增长） | 分层（按失败后果加权）+ 自助清单 + 专家抽查 |
| 评审结论没人执行 | 隐性成本（绕过与遗忘） | 换挂点（合并门禁 / 例外审批 / 跟踪列表），而不是加开会频次 |
| 团队没有资深架构师 | 「等专家」造成的排期等待 | 清单 + 标准 + 模板三件套自助；AI 先上清单覆盖检查 |

### 7.5 决策树（每个分支都要有阈值依据）

```
这次变更要怎么评审？（先按失败后果定深度，再看平台与组织约束定做法）
├─ ① 失败后果 = 资金 / 合规 / 大范围可用性（关键资产）
│    → 完整评审：场景分析（ATAM 式）+ Pre-Mortem + 专家参与
│      · 必须在**设计冻结前**发生，否则只能事后追认（7.3.1）
│      · 结论挂到「例外审批」上，否则只是建议（7.3.3）
├─ ② 失败后果 = 单系统内、可回滚
│    → Lightweight：PR + 清单 + 一名非本团队评审人
│      · 检查项必须挂在合并门禁上（不是评论里）
├─ ③ 失败后果 ≈ 无（内部工具 / 实验）
│    → 不评审，只登记；给它设一个「升级为关键」的触发条件
│      （不给它设流程，但也不能让它永远没有升级路径）
├─ ④ 关键变更的年次数 > 专家可评审容量？
│    ├─ 是 → 分层（按失败后果加权）+ 自助清单 + 专家抽查，不追求全量上会
│    └─ 否 → 关键变更全量走完整评审是可行的
├─ ⑤ 平台形态：公有云为主 / 自建 · 混合云？
│    ├─ 公有云为主 → 用云厂商支柱清单（如 AWS Well-Architected）做基线，再按 ①②③ 加深度
│    └─ 自建 / 混合云 → 自建清单与场景库；直接照搬云厂商支柱会误判（其假设是托管服务）
├─ ⑥ 变更频繁、正式评审排期排不过来？
│    → 拆成「异步材料 + 只有分歧才开会」，或改 Continuous Review（评审寄生于 CI）
│      （因为 Formal 的排期周期可能长于变更的整个实施周期）
├─ ⑦ 安全敏感系统？
│    → 在清单之外加 Red Team / Blue Team 对抗评审
│      （清单只能查「已知的已知」，对抗评审找「已知的未知」）
└─ ⑧ 团队没有资深架构师？
     → 清单 + 标准 + 模板三件套自助 + 专家抽查
       AI 辅助先上「清单覆盖率与材料一致性检查」，不要先上「架构判断」
```

**阈值依据**（编号与树上节点一一对应；④–⑧ 中除 ④ 的容量线外均为**非数值判据**——它们不是阈值，但同样需要给出成立依据，否则树上的分支就是无依据的断言）：

- **① 关键资产走完整评审，判定依据是失败后果而不是变更大小**：由 7.4 的成本函数推出——单次正式评审的成本是**固定量级**（2.5–3.5 人天【推算，见 7.4】），而变更的实施成本差异巨大；因此用「代码量 / 变更大小」分层会漏掉「小改动、大后果」这一类（改一个字段类型、改一处权限），而这类变更恰恰最容易引发跨系统事故。分层阈值应由「后果」这个维度定义，并在变更单上作为必填项。
- **① 必须在设计冻结前**：由缺陷修复成本曲线推出。Boehm 的公开分析给出「修复成本随阶段后移显著上升」这一方向【公开，1981】；ARID 的出现是同一方向的实践回应（其公开年份不统一，故不注具体年份）。晚于设计冻结时，评审产出只能变成「下一版再改」。
- **① 结论挂例外审批、② 检查项挂合并门禁 —— 挂点决定遵守**：由 7.3.3 的机制（有代价才有遵守）与 DORA 的公开相关性结论共同支持【公开，Accelerate 2018；相关性非因果】。委员会仍然需要，但它处理的是**例外与争议**，而不是所有变更。
- **② Lightweight ≈ 正式评审的 1/5–1/7**：由 7.4 的人时推算给出（4 人时 vs 20–28 人时），参数可替换重算【推算】。这个比值决定了分工方式；但不能「全都走轻量」，关键变更走轻量会漏掉跨系统权衡与质量属性取舍，那是轻量评审在机制上覆盖不到的。
- **③ 不评审但登记**：依据来自 7.3.1 的失效条件——这类变更的时点前移收益为负；但登记保留了「未来审计或事故回溯时能找到它」的能力，成本接近于零【经验】。它与 ① 的分界不由代码量决定：只要失败后果触及资金 / 合规 / 大范围可用性，就从 ③ 升到 ①。
- **④ 容量线 = 专家数 × 每人年可投入评审人天 ÷ 单次战略级评审人天**：以 3 名架构师 × 30 天 ÷ 5 人天/次代入 → **18 次/年**【推算，见 7.4】。它不是行业常数，换参数即得你自己的上限。这条线决定 ④ 走哪一支：关键变更年次数超过它，就上调「关键」的门槛或改「分层 + 自助 + 抽查」，而不是在每一场上加深度（7.3.4：分子固定、分母增长）。
- **⑤ 平台形态决定基线清单从哪里来**：依据是 7.3.2 的失效条件——云厂商支柱清单的检查项以**托管服务**为前提（可用区、托管数据库的备份与多副本策略等），在自建 / 混合云语境下这些项要么不可判定，要么把正确做法判成不合规，从而产生「系统性的错误一致」。判定方法：任取支柱中的一条检查项，换到你的机房语境下问「它是否仍然可判定、且答案仍指向同一结论」；答案为否的项，就是不能照搬的部分。
- **⑥ 排期排不过来就换机制，不换态度**：依据是 7.3.1 的时间常数不匹配——Formal 的排期周期以周计，而部分变更的整个实施周期短于它，于是评审必然落在实施之后。触发条件可量化：把「上季度评审从提交到排期的等待天数」与「变更的平均实施天数」相比，前者持续大于后者即命中该分支【经验】。
- **⑦ 安全敏感系统加对抗评审**：依据是 7.3.2 的失效条件——清单只能覆盖「已知的已知」（已被写进清单项的风险），Red Team / Blue Team 覆盖的是「已知的未知」（攻击路径与绕过方式）。命中条件不设数值：资金链路、对外接口、多租户隔离、涉个人信息或密钥的系统属当然命中，其余按暴露面与合规等级判断。
- **⑧ 三件套自助 + 专家抽查；AI 先做清单覆盖，不做架构判断**：主分支的依据是 7.3.4 的覆盖成本函数——分子（专家人时）固定而分母（系统数）增长，唯一能改变斜率的是把**单次评审人时中可枚举的部分**外移给团队自助，这也正是 7.3.2 所说清单的机制作用；专家退到抽查、疑难裁决与标准维护。AI 子项的依据同样是 7.3.4：清单项的判定可枚举、可核验（「是否定义了降级路径」的答案在材料里存在与否可被机器检查），而架构权衡需要组织约束这类材料外上下文，其结论无法被核验【经验】。这条让 AI 的收益先落在低风险区。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 日常 PR 级变更 | Lightweight（PR + 清单，挂合并门禁） | 不评审 | 走 Formal：单次 2.5–3.5 人天的成本已超过变更本身，且排期拖慢所有人 |
| 战略级新平台 / 跨系统改造 | 场景分析（ATAM 式）+ Pre-Mortem | Formal Review | 只走 Formal：产出「通过 / 不通过」，没有质量属性权衡与风险项 |
| 云上架构标准化 | AWS Well-Architected 类支柱清单 + 自助评估 | 自建清单 | 直接照搬支柱：其假设是托管服务，自建 / 混合云场景会误判 |
| 大组织、多 BU | ARB + 分层（按失败后果） | 全量上会 | 全量上会：专家人时固定，覆盖率必然饱和，且拖慢所有项目 |
| 安全敏感系统 | Red Team / Blue Team 对抗评审 | 清单里的安全项 | 只用清单：清单只能查「已知的已知」，找不到绕过路径 |
| 迭代快、正式评审总排不上 | Continuous Review（寄生于 CI） | 异步材料 + 只对分歧开会 | 硬排正式会：排期周期长于迭代周期，评审必然落在实施之后 |
| 团队没有资深架构师 | Checklist + 标准 + 模板自助 + 专家抽查 | 排队等专家 | 等专家：专家成为瓶颈，覆盖率随系统数下降 |
| 评审结论没人执行 | 换挂点（门禁 / 例外审批 / 跟踪列表） | 提高开会频次 | 加开会频次不产生约束力，只产生疲劳与绕过动机 |
| 决策理由三个月后无人记得 | 评审 + ADR（记录被否决的选项与理由） | 会议纪要 | 纪要留结论不留理由，争议时会重新开一遍同样的会 |

**常见组合与其运维代价**（五族各留一个，两两交点即为一条组合。这里列 6 条而不是只列「最常见的」少数几条，是因为**每一处交点对应一种不同的运维代价**，而运维代价恰是组合崩掉的地方；漏掉任一条，都会让某类组织在某个环节断裂）：

1. **Checklist（可判定化）+ ARB（挂点）+ 分层（成本匹配）**：Checklist 让问题可判定，ARB 让结论有代价，分层让成本与后果匹配。边界是 **ARB 只处理例外与争议，不进日常变更**。运维代价：清单必须指定维护人与更新周期——过期清单会产生系统性的错误一致（7.3.2），这比没有清单更危险。
2. **Lightweight（日常）+ 场景分析 / Formal（关键）**：典型的两级闸门。运维代价：分层边界会被人为下移以逃避评审，因此「是否关键」必须由**第三方**按「失败后果」判定，而不是由提出方自评。
3. **评审 + ADR**：评审出决议，ADR 把「为什么这样定」写下来。运维代价：ADR 容易退化成「决定清单」而丢掉**被否决的选项与理由**——后者才是三个月后争议时唯一有价值的部分。
4. **评审 + 改进项跟踪**：评审产出带优先级、责任人与预期收益的改进项，并跟踪到关闭。运维代价：不关闭的项必须显式记录为「接受风险 + 理由 + 复审时间」，否则跟踪列表会长成一张没人看的清单（这也是 §6 案例 6.1 把「未处理须显式记录为接受风险」单列的原因）。
5. **人类评审 + AI 辅助**：AI 做清单覆盖、材料一致性与反模式提示，人做权衡与裁决。运维代价：AI 会把「看起来像反模式」的正确设计标出来（例如刻意的重复以解耦），每一项都需要人复核；且 **AI 的结论不能作为 ADR 里的理由**——理由必须是可核验的机制。
6. **评审 + 评审历史库 / KG**：把结论结构化后可检索，专家人时的等效产出提升。运维代价：案例库质量下降后检索结果不可信，专家会退回到「重新判断」，复用族投入白费——因此案例入库需要标准化的字段（方案类型 / 失效场景 / 结论 / 代价），而不是自由文本堆积。

**组合的共同原则**：**每族只留一个**（闸门选一种深度策略、分析选一种方法、标准用一份清单、复用用一个库、加速按需）→ **评审必须寄生在一个已有流程上**（CI / 变更单 / 预算 / 审计），否则它是「独立活动」，会被工期第一个挤掉 → **为每一条结论指定落点**（跟踪、放行、显式接受风险）→ **每年退役一条从未拦下任何东西的检查项**。一个有效组合的标志不是「流程齐备」，而是「上一季度有一次变更的改动方向，可以被指认是由某次评审改变的」。

### 7.7 选错的代价与迁移成本

下面 6 条反模式各落在**不同的失效环节**上（时点 / 产出形态 / 分层 / 挂点 / 加速 / 清单边界），彼此不重叠，所以不合并——每一条都对应 7.3 里某个机制的一个具体失效点，删掉哪一条都会留下一个无人认领的错误做法。

**反模式：把评审放在实施之后** —— 症状：评审会上讨论的是「已经写好」的方案，材料是完成态的代码与设计文档 → 后果：评审只能输出「下次注意」，架构缺陷继续流向生产，且团队对评审的价值产生怀疑（会议开了但什么都没改变）→ **正确做法**：把评审触发点绑到「设计冻结」或「首行代码之前」，并在变更单上设一个前置检查（没有评审记录不能进入实施）。

**反模式：只输出「通过 / 不通过」** —— 症状：团队把评审当审批关卡，材料写成辩护词，会上争论焦点是「能不能过」 → 后果：评审变成博弈，改进项无人执行，下次评审发现同样的问题 → **正确做法**：产出「改进项 + 优先级 + 责任人 + 预期收益」，把评审从闸门变成体检 + 处方（§6 案例 6.1 的产品化路径）。

**反模式：所有系统走同等深度** —— 症状：核心交易系统与内部脚本工具走同一套评审流程 → 后果：有限的专家人时被内部工具消耗（7.4 的覆盖率推算：3 名架构师每年约 18 次完整评审），关键变更反而排不上队 → **正确做法**：按**失败后果**分层，把专家人时按影响面加权分配。

**反模式：评审结论只写在纪要里** —— 症状：改进项没有跟踪，下一次评审发现同样的风险又出现了 → 后果：评审不产生任何改变，组织逐渐把它视为走过场并开始绕过 → **正确做法**：结论进跟踪列表，未处理项必须显式记录为「接受风险 + 理由」，并在季度回看。

**反模式：用 AI 替代评审人** —— 症状：AI 生成一份「架构风险清单」，无人逐项复核直接进决议 → 后果：LLM 的判断无法被核验（它没有你的组织约束上下文），错误结论以权威形式进入决策，纠错成本高于原先节省的检查时间 → **正确做法**：AI 只做**可枚举项**的检查（清单覆盖率、材料一致性、字段缺失、图文矛盾），权衡与裁决必须有人署名。

**反模式：把「合规通过」当成「架构安全」** —— 症状：清单项全部打勾，架构评审报告结论为「无风险项」 → 后果：清单只能覆盖「已知的已知」（7.3.2 的失效条件），未知风险在积累，而报告给了虚假的信心 → **正确做法**：关键系统在清单之外保留至少一种非清单方法（Pre-Mortem 或对抗评审），并定期用真实事故回灌清单。

**反模式的代价量级**（沿用 7.4 的参数估，不引入外部系数）：

| 反模式 | 代价的量级 | 推导依据 |
| --- | --- | --- |
| 评审放在实施之后 | 一次返工 ≈ 一次重构；且评审的 2.5–3.5 人天全部沉没 | 缺陷修复成本随阶段后移上升【公开，Boehm 1981；倍数不可移植】+ 7.4 的评审成本【推算】 |
| 只输出通过 / 不通过 | 改进项落地率趋零，评审成本 100% 沉没 | 无责任人、无优先级的产出无法被跟踪执行【经验】 |
| 所有系统同等深度 | 专家人时耗尽在长尾；关键变更排不上 | 覆盖率 = 分子固定 ÷ 分母增长（7.4）【推算】 |
| 结论只写纪要 | 同类风险反复出现，每次重复支付评审成本 | 由 7.3.3 的机制链推出：无挂点 → 无代价 → 必被跳过【推算】 |
| 用 AI 替代评审人 | 错误结论的纠错成本 + 决议可信度损失 | 不可核验的结论无法被第三方复核（7.3.4）【经验】 |
| 合规通过当成安全 | 未知风险持续积累，直到一次生产事故暴露 | 清单只覆盖已知项（7.3.2 失效条件）【经验】 |

**换成另一条路线要动什么**：

| 迁移方向 | 历史数据迁移 | 材料与清单改写 | 流程重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 从「不评审」转向「Lightweight」 | 无 | 有（清单从零建） | PR 模板 + CI 钩子 | 清单判定标准 | 2–4 周 |
| 从 Lightweight 转向「分层 + 场景分析 / Formal」 | 无 | 大（场景库与质量属性口径） | 评审排期、决议与例外流程 | ATAM 式场景分析、权衡表达 | 1–2 人月 |
| 从「自建清单」转向「云厂商支柱框架」 | 无 | 中（口径映射与本地化） | 自助评估 + 改进项跟踪 | 支柱定义、风险定级 | 2–6 周 |
| 从 Formal 转向 Continuous Review | 无 | 大（检查项必须能被自动化） | 评审寄生到 CI/CD | 自动化检查的编写 | 2–4 人月 |
| 从「无跟踪」转向「改进项闭环」 | 无 | 少（结论要结构化） | 跟踪列表 + 季度回看 + 风险接受流程 | 优先级与责任人定义 | 2–3 周 |
| 从「专家逐场」转向「自助 + 抽查」 | 无 | 大（清单 + 判定标准 + 产出模板三件套） | 专家角色转为抽查与标准维护 | 清单编写、判定标准校准 | 1–2 人月 |
| 引入 AI 辅助（限清单覆盖） | 无 | 中（清单要结构化到机器可判定） | 提示词 / 规则维护 + 复核职责 | 复核边界、溯源纪律 | 1–3 人月 |

> 量级按「一个熟悉本系统、3–5 人的小组」估算【经验】；其中「从专家逐场转向自助 + 抽查」之所以是一次真正的方法迁移，是因为它改变的是**专家的角色定义**（从做判断到维护标准），而角色变更通常比工具变更更难落地。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 原型 / 实验性变更 | 不评审，只登记 + 设升级条件 | 评审的固定成本（2.5–3.5 人天【推算，见 7.4】）高于变更本身，前移收益为负 |
| 日常 PR 级变更 | Lightweight + 清单，结论挂合并门禁 | 4 人时 vs 20–28 人时【推算，见 7.4】；有代价才有遵守 |
| 关键资产变更 | 场景分析 + Pre-Mortem + 专家，且在冻结前 | 缺陷修复成本随阶段后移上升，晚于冻结只能追认 |
| 云上为主 | 支柱清单做基线 + 按后果加深度 | 支柱清单是可判定的，可直接被第三方复核 |
| 自建 / 混合云 | 自建清单 + 场景库，不要照搬云厂商支柱 | 支柱框架的假设是托管服务，照搬会误判 |
| 系统数远超专家容量 | 分层（按失败后果加权）+ 自助 + 抽查 | 分子固定、分母增长，平摊必然使评审趋零 |
| 评审总排不上队 | 改 Continuous Review，寄生于 CI | 排期周期长于迭代周期时，正式会议永远落在实施之后 |
| 结论没人执行 | 换挂点，而不是加开会频次 | 无代价的结论在工期压力下必被跳过（激励，不是态度） |
| 争议三个月后重现 | 评审 + ADR，写清被否决的选项与理由 | 争议需要的是理由，不是结论 |
| 只有清单、没有对抗 | 关键系统加 Pre-Mortem 或 Red Team | 清单覆盖「已知的已知」，找不到绕过路径与未知失败模式 |
| 想上 AI 加速 | 先上清单覆盖与材料一致性检查 | 可枚举项可核验；权衡判断缺组织上下文，无法核验 |

> 本节小结：这些候选之间**唯一真正起决定作用的差异**不是「评审多深」，而是**闸门放在哪个时点、结论挂在哪个环节**。时点决定了评审能不能拦住那些「改起来很贵」的缺陷（设计冻结之后只能追认）；挂点决定了结论会不会被遵守（无代价则必被跳过）。评审深度、分析框架、清单质量、AI 辅助都只是在这两条之上的增益：**时点错了，深度白费；挂点缺了，结论白写**。因此架构评审的选型顺序是：**先定时点（冻结前）→ 再定挂点（门禁 / 例外 / 跟踪）→ 再按失败后果分层 → 最后才谈用什么分析方法与是否上 AI**。
>
> 💡 **思考锚点**：拿你团队最近一次「每天几十次」的 PR 级变更过一遍 §7.8 的前两行：它该走「不评审，只登记 + 设升级条件」，还是「Lightweight + 清单，结论挂合并门禁」？若给它上完整评审，2.5–3.5 人天【推算】的固定成本相对这次变更本身，是正收益还是负的？
