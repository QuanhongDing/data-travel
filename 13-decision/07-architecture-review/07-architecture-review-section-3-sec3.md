## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

「日常用 PR、重大用 Formal、战略级用 ATAM」——这张对应表读起来像选择题，其实是被两条约束推着走的：**这次决策的不可逆程度**，和**评审者与决策者之间的信息差**。不可逆程度决定评审前置到哪一环（改一个常量与换一套存储引擎，返工量差好几个数量级）；信息差决定谁必须进会场（纯技术评审看不见成本与合规约束）。最容易推翻直觉的一点是：团队规模、会议预算、评审人数都是这两条的派生量，拿它们当第一性约束，就会推出「人少所以不做评审」这类结论。

主文件 §1.2 列的七类痛点里，有一类共享同一个结构：**不是「评审做得不够多」，而是「评审挂在错误的环节上」**——「走过场」是因为这一环对结果没有约束力，「评审滞后」是因为评审排在实施之后，「没有决策」是因为会议没有被要求产出决议，「架构腐烂」是因为把关点排在编码之后。另外三条不属这一结构，成因分别在别处：「一言堂」是会场机制（权威在场且发言顺序由地位决定），「评审标准不一」是工具缺失（没有成文清单，判定标准留在个人经验里），「跨团队盲区」是评审范围（只评本团队视角，下游没有座位）——这三条要换的是会场规则、清单与席位，而不是评审节点。所以本节对每个模式都问同一个问题：它挂在哪一环，那一环能约束什么。

约束还会随阶段移动。同一个团队在十余人时用 PR 评审有效，到百人规模时同一做法失效——不是 PR 评审变差了，而是**跨团队语义变更的比例上升了**，而 PR 的最小评审单位是 diff，diff 里看不到调用方语义。下面这张表列出本主题下最常被误判的几条约束。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 决策不可逆程度 | 评审前置到 RFC / Design Doc / PR / 上线门禁的哪一环 | 「评审越早越好」——早期信息最少，全量评审会因材料不足而走过场 |
| 评审者与决策者的信息差 | 必须到场的角色（业务 / 安全 / 合规 / 运维 / 下游 Owner） | 「架构评审是架构师的事」——成本与合规约束不在架构师视野内 |
| 变更频率与批量 | 会议制（低频、单次深）还是流水线制（高频、单次浅） | 「重要的事必须开会」——高频小变更被会审的结果是被批量跳过 |
| 影响面的可枚举性 | 评审能否给出可信结论（有无依赖清单决定判定的可信度） | 「凭经验估影响面」——跨团队链路上的经验估计系统性偏低 |
| 组织规模与团队数 | 单团队评审 / 跨团队评审 / 评审 + 委员会两级 | 「流程越完备越好」——节点数 × 单节点准备成本，超过团队运维量即退化 |
| 结论的约束力 | 决议是参考、是门禁、还是仅存档 | 「评过了就等于把关了」——无约束力的结论与没评过的结果相同 |

### 3.2 模式逐个拆解（核心节）

以下 10 个模式按同一顺序给出五件事：**被什么约束逼出来 → 结构 → 为什么有效 → 代价 → 失效点**，再加一条真实使用。结构一律用代码块画出，因为代码块会暴露这个模式「到底靠哪几个字段、哪几个状态在运转」——文字描述容易把结构讲成职责说明，而职责说明恰恰是最容易两边都对、却无法执行的那类描述。

#### 3.2.1 ATAM：用效用树把「权衡」变成可比较的打分

- **被什么约束逼出来**：战略级新系统、质量属性互相冲突（性能吃成本、可用性吃一致性），而缺陷一旦进入编码，返工量就远超一次评审的成本。
- **结构**：
```text
评审对象：候选架构 → 质量属性效用树
  Utility ─┬─ 性能   w=0.35 ──┬─ 尖峰流量场景   [重要性 H, 实现难度 H]
           ├─ 可用性 w=0.30 ──┴─ 机房故障场景   [H, M]
           ├─ 成本   w=0.20 ──┬─ 三年 TCO 场景  [M, L]
           └─ 可演化 w=0.15 ──┴─ 需求变更场景   [M, M]
  打分 Score ∈ 1..5；Utility = Σ w_i × Score_i
  两套刻度不要混：方括号里的 H/M/L 是原方法输出的相对排序；
  w 与 Score 是【示例·团队自定】的加权系数（公式见主文件 §2.2），
  原方法不给数值，须由 Stakeholder 共识产生
  步骤链：介绍 ATAM → 业务动机 → 架构陈述 → 方法识别 → 建效用树
          → 属性分析 → 场景头脑风暴 → 场景分析 → 结论
```
- **为什么有效**：因为权重由业务方在树上先定死、再逐场景打分，所以「性能换成本」这类冲突会以两组数字暴露出来，而不是靠会场上的嗓门决定。
- **代价**：一次全量 ATAM 要把全部干系人连续占住；九步走完是**整天量级**（【经验】：按逐步配额的一种常见排法——介绍 ATAM 30 + 业务动机 30 + 架构陈述 60 + 方法识别 30 + 建效用树 60 + 属性分析 120 + 场景头脑风暴 60 + 场景分析 60 + 结论 30 = 480 分钟 ≈ 8 小时，实际在 6–10 小时之间浮动，取决于场景数量与准备程度），外加架构陈述与效用树的准备工时。
- **失效点**：当变更是增量（例如给某组件换缓存策略）时，「把权衡摊开比较」反转成「成本远超收益」，因为效用树要求全部干系人重聚并重估权重，而增量决策的候选空间往往只有一两个方案，不值得开树。
- **真实使用**：ATAM 由 SEI 于 2000 年公开（【公开：SEI 技术报告《ATAM: Method for Architecture Evaluation》, 2000】，可按报告标题检索核验）；实践中多用于系统首次架构评估，日常变更基本不用。

#### 3.2.2 Lightweight Review：把评审降成 diff 上的异步往返

- **被什么约束逼出来**：变更数量大、单次影响小、但必须持续发生；会议制的容量是固定的，塞不下高频变更。
- **结构**：
```text
变更单（PR / MR）
  ├─ 状态：Open → Reviewing → Changes Requested → Approved → Merged
  ├─ 评论挂在具体行上（可追溯到 diff）
  ├─ 门禁：CI 检查（构建 / 测试 / 影响面）通过才可合并
  └─ 评审者自动指派（按目录归属 / CODEOWNERS）
  关键字段：谁批准、批准在哪个 commit 上（防止批准后被追加改动）
```
- **为什么有效**：因为评审单位是 diff、通道是异步的，所以人均评审成本随变更数近似线性增长，而会议制的成本是按会议次数跳变的——这是高频变更唯一可持续的形态。
- **代价**：异步意味着无法处理跨模块语义冲突；意见以行内评论形式散落，结论不沉淀（没有决议记录），事后只能靠翻 PR 重建「当时为什么这么改」。
- **失效点**：当变更跨越多个团队或改变公共语义（改一个公共字段的含义）时，「低成本」反转成「无人对全局负责」，因为评审的最小单位是 diff，而 diff 里看不到调用方语义，每个 Reviewer 都只看到自己那一段。
- **真实使用**：多数工程组织把 PR 式评审作为默认形态（【经验】：人均每周数小时，随 PR 粒度差异很大）；其规模化前提是「变更粒度小」这一纪律本身。

#### 3.2.3 Formal Review：用文档把决策钉在会议之前

- **被什么约束逼出来**：重大变更、干系人多、且必须在事后能回答「谁在什么时候批准了什么」。
- **结构**：
```text
① RFC / Design Doc（会前 3-5 工作日下发）
     ├─ 背景与约束   ├─ 候选方案 ≥2 且含被否方案及理由
     └─ 影响面（下游 / 成本 / 风险 / 回滚）
② 预审（1-2 名资深评审者，先消灭低级问题）
③ 正式评审会（有争议项逐条表决，无争议项跳过）
④ 决议：接受 / 修订 / 拒绝 / 推迟（四选一，具名 Approver）
⑤ ADR 归档（决议 + 依据 + 失效条件）
```
- **为什么有效**：因为方案必须先写成文字、预审在前只把真有争议的部分带进会场，所以会议时间花在分歧上而不是信息同步上，决策也自动带上了日期与具名责任人。
- **代价**：文档前置成本（一份可评审的 RFC 通常要 1 人日以上【经验】）；一次会占住 5–8 名资深人员 2 小时（【经验】），会议容量因此成为组织变更吞吐的上限。
- **失效点**：当组织用它处理所有变更时，「深度」反转成「瓶颈」，因为会场带宽固定而变更数随团队规模增长，队列变长后团队会绕过流程直接上线。
- **真实使用**：关键系统与跨团队变更普遍采用该方法（【经验】）；其成败不取决于流程设计，而取决于「决议是否有约束力」这一条。

#### 3.2.4 AWS Well-Architected Review：把评审标准外置成可比较的支柱清单

- **被什么约束逼出来**：云上架构的失败模式高度重复，而每个团队各自总结经验既慢又不齐，评审结论无法跨团队比较。
- **结构**：
```text
六个支柱（以官方文档当前版本为准）
  Operational Excellence │ Security │ Reliability
  Performance Efficiency │ Cost Optimization │ Sustainability
        │
   每支柱 → 问题清单 → 逐项判定：符合最佳实践 / 存在风险
        │
   高风险项（HRI）→ 必须落到「改进项 + 负责人 + 期限」
  产出：风险清单 + 改进计划（不是评分）
```
- **为什么有效**：因为问题与判定标准来自组织外部且逐项给出「最佳实践 vs 风险」的二值判断，所以两个团队的评审结果可以横向比较，也可以按年度追踪同一条问题是否关闭。
- **代价**：清单覆盖的是通用云架构，数据架构特有的问题（血缘完整性、口径一致性、多租户隔离）不在清单内，需要另行补充；填完清单不等于风险已消除，判定与改进之间的落差由团队自己承担。
- **失效点**：当团队把它当合规打勾时，「标准化」反转成「形式主义」，因为清单本身不产生风险判定——只有每个 HRI 都带上改进项与负责人的那次评审，才真的改变了系统状态。
- **真实使用**：该框架由 AWS 公开发布（【公开：AWS Well-Architected Framework 官方文档；可持续性支柱于 2021 年加入，六支柱构成以官方当前版本为准】），常被用作云上系统上线前的外部评审基线。

#### 3.2.5 Continuous Review：把评审挂在生命周期的不可逆节点上

- **被什么约束逼出来**：架构漂移不是一次决策造成的，而是许多次「顺手改一点」累积的；单次评审拦不住漂移。
- **结构**：
```text
架构设计 → RFC 评审 → 实施期 PR 评审 → 上线门禁（Go-Live）
    → 运营期复盘（Postmortem） → 季度架构评审 → 回到架构设计
每个节点要求：
  · 明确的进入条件（什么变更必须过这一关）
  · 明确的产物（评审记录 / 放行结论 / 改进项）
  · 上一节点未通过则不允许进入下一节点
```
- **为什么有效**：因为每个不可逆节点上都有一次止损机会，整体可靠性不再依赖某一次会议的质量——一次评审漏掉的项，往往会在下一节点被另一批人看到。
- **代价**：流程重、每个节点都要准备材料；每个节点都有固定准备成本，因此只适合有专职评审能力（哪怕兼职）的组织。
- **失效点**：当节点数 × 单节点准备成本超过团队可支配评审时间时，「全生命周期覆盖」反转成「每个节点都是橡皮图章」，因为节点越多、每节点分到的注意力越少，签字变成默认动作。
- **真实使用**：大型组织在关键系统上采用（【经验】）；其可持续的前提是节点少而准，节点逐个增加是这类流程退化的典型路径。

#### 3.2.6 Scenario-based Review：用场景把「非功能需求」变成可复现的判定

- **被什么约束逼出来**：「高可用」「高性能」这类词无法评审——不同人对同一个词有不同预期，必须在会前把它们翻译成具体刺激与响应。
- **结构**：
```text
场景卡（每张卡一个刺激-响应对）
  ├─ 刺激：大促峰值流量达日常 N 倍【经验：N 由历史峰值推定】
  ├─ 环境：主库所在机房不可用
  ├─ 期望响应：读服务降级但下单不中断，恢复时间有承诺
  └─ 判定：架构中哪一层承担该响应？缺少该层即视为缺口
评审输出：场景 × 架构成分的判定矩阵（覆盖 / 部分覆盖 / 未覆盖）
```
- **为什么有效**：因为场景把抽象质量属性翻译成「谁在什么条件下必须做什么」，缺口可以在会议桌上被逐个指认，而不是留到故障当天才发现没人负责。
- **代价**：场景构造依赖历史故障与业务经验，构造质量决定评审质量；场景库需要长期维护，且维护工作通常没有直接产出。
- **失效点**：当团队只评自己构造的场景时，「实战导向」反转成「覆盖幻觉」，因为场景集合是从已知故障归纳出来的，未知故障模式天然不在集合里，而评审结论会被当成完整覆盖。
- **真实使用**：质量属性场景方法见 Bass / Clements / Kazman《Software Architecture in Practice》（【公开：该书提出的质量属性场景方法，版本以当前版次为准】）；高可用系统评审普遍使用同类做法（【经验】）。

#### 3.2.7 Pre-Mortem Review：在方案通过之前先假设它已经失败

- **被什么约束逼出来**：评审会存在确认偏误与权威锚定——方案由提案者讲完，反对意见的发言成本高，于是分歧被压到会后。
- **结构**：
```text
会议前 10-20 分钟【经验】
  ① 主持人口头设定：假设已是 6 个月后，该方案已失败
  ② 所有参与者独立书写失败原因（不讨论、不署名）
  ③ 汇总去重 → 按「可预防 / 需监控 / 接受」三类归档
  ④ 可预防项 → 变成方案修订项（带 Owner）
  关键约束：独立书写必须在汇总之前完成
```
- **为什么有效**：因为「失败已发生」这个前提把归因从「谁的方案」转向「哪个机制」，且独立书写发生在任何人表态之前，所以第一条意见不会锚定后面所有人。
- **代价**：占用会议时间（10–20 分钟量级【经验】）；产出的是假设而非证据，必须先分类再决定投不投入，否则会变成一张无法执行的担忧清单。
- **失效点**：当主持人把独立书写改成口头轮流发言时，「暴露分歧」反转成「复述第一个发言者」，因为口头顺序本身就是锚定，后发言者会围绕先发言者的框架补充而不是另起判断。
- **真实使用**：该方法由 Gary Klein 提出（【公开：Gary Klein, "Performing a Project Premortem", Harvard Business Review, 2007】）；在项目立项与重大方案评审中常见（【经验】）。

#### 3.2.8 Architecture Review Board：让跨团队影响面在同一个会上暴露

- **被什么约束逼出来**：单个团队看不到自己方案对其他团队的破坏，而跨团队协调靠私下沟通无法产生组织级约束。
- **结构**：
```text
成员：跨团队资深者 + 安全 / 数据 / 业务代表（5-10 人）
准入：什么样的方案必须上会（跨团队 / 不可逆 / 超成本阈值）
议题：每期议程公开，方案按准入规则自动进入队列
决议：接受 / 修订 / 拒绝 / 推迟 + 例外记录（谁批的、为什么）
输出：架构决策记录、技术标准、技术雷达（Tech Radar，组织级选型指南——主文件 §2.1）、例外清单
```
- **为什么有效**：因为成员来自不同团队且决议对全组织有效，所以「这个改动会影响谁」会在同一个时间点上被几方同时回答，跨团队影响面不可能被本团队视角漏掉。
- **代价**：委员会带宽固定（例如双周或月度一次【经验】），议程必然排队；成员脱离一线后对具体技术的判断会滞后，需要后备评审机制补位。
- **失效点**：当所有方案都要上会时，「组织级对齐」反转成「决策延迟」，因为带宽固定而候审数量随组织规模增长，等待成本被转移给在队列里等待的团队，团队随后开始找绕道。
- **真实使用**：多出现在数百人以上、多业务线或受监管的组织（【经验】）；有效性高度依赖「准入规则是否严格」——准入宽则退化为排队瓶颈，准入严则有价值的方案反而绕过。

#### 3.2.9 Lightweight ADR + Living Review：把决策记录挂进代码仓库

- **被什么约束逼出来**：重型 RFC 的产出老化得快——代码在变，文档停在评审当天，后人查到的「当时的理由」与实现已经脱节。
- **结构**：
```text
docs/adr/0007-选择列式存储.md
  ├─ 状态：Proposed → Accepted →（Superseded by 00xx）
  ├─ 背景与约束（当时的数据量级、访问模式、成本线）
  ├─ 决策
  ├─ 被否方案 × 各自被否的理由
  └─ 失效条件（什么情况下该重新评估）
PR 检查项：改动是否与在册 ADR 冲突？冲突则要求新增/更新 ADR
```
- **为什么有效**：因为决策记录与代码同仓、随代码一起被审阅和更新，所以「当时的约束」会与实现一同演化，检索入口也就是代码检索入口。
- **代价**：轻量意味着只记结论与理由，不记完整分析过程；ADR 数量增长后需要标签与索引，否则等于一堆难检索的 Markdown。
- **失效点**：当 ADR 只写「决定了什么」而不写「否掉了什么以及为什么」时，「可追溯」反转成「误导后人」，因为后来者只看到被采纳项，会重复评估当年已被否掉的方案，甚至不知道它已被否过。
- **真实使用**：ADR 这一形式由 Michael Nygard 提出（【公开：Michael Nygard, "Documenting Architecture Decisions", 2011 博客，可按标题检索核验】），此后被大量开源项目采用（【经验】）。

#### 3.2.10 AI-assisted Review：把清单初判交给模型、把关留给人

- **被什么约束逼出来**：清单越来越长而评审时间不变，逐项检查成了走过场的主要来源；同时代码量与变更量都在增长。
- **结构**：
```text
变更提交
  ├─ LLM 阶段：对每个 checklist 项产出初判（通过 / 疑似风险 / 不适用）
  │    必须附证据：命中的文件、行、规则名
  ├─ 人类阶段：只处理「疑似风险」与「无证据」的项，做最终判定
  ├─ 记录：AI 初判与人类结论并列存档（用于回看误报与漏报）
  └─ 门禁：AI 结论不单独构成放行依据
```
- **为什么有效**：因为模型能对每一项给出「有证据 / 无证据」的初判，人的注意力可以从逐项检查转移到核查异常项，单位评审时间覆盖的清单项数因此上升。
- **代价**：误报要人工消化（误报率高时反而比人工更慢）；模型判断若不给可追溯理由，人类无法复核；评审标准的语义定义仍然只能由人来做，且这项工作量不会因引入模型而减少。
- **失效点**：当把 AI 初判当结论（自动通过）时，「覆盖面」反转成「漏检放大」，因为模型的漏检是静默的——它不报错、只是没提，而改造后的流程又已经把人从逐项检查上撤走了。
- **真实使用**：AI 辅助代码评审已成为主流平台能力（【经验】：GitHub Copilot 等产品提供 PR 级评审建议，具体能力与版本请以官方文档当前版本为准）；数据架构评审中更多用于清单项初判与反模式识别，人类保留决议权。清单里原有的「AI 红队对抗攻击」一条属对抗性评审轨道，见 [§5 前沿演进](07-architecture-review-section-5-ai.md) 5.2.4 与 [§8 面试真题集](07-architecture-review-section-8-sec8.md)，本模式不承担对抗验证。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 日常开发、单次变更影响面小 | Lightweight Review（PR） | Formal Review 的会议带宽是固定量，塞不下高频变更，结果是评审被批量跳过 | 这个变更能否在一次异步往返内被看完、并回退 |
| 中型变更、单一团队、有既有标准 | Lightweight + 标准 Checklist | ATAM 的效用树要求全部干系人重聚，收益低于成本 | 是否有组织级清单可作为判定依据 |
| 战略级 / 系统首次架构 | ATAM | PR 评审看不见属性之间的权衡，只会对实现细节提意见 | 是否存在互相冲突的质量属性需要一次定权重 |
| 云架构、需要跨团队可比 | Well-Architected Review | 自研清单的结论无法跨团队比较，也无法跨年度追踪 | 是否有外置标准可用，且愿意补组织特有的检查项 |
| 高可用 / 高一致性系统 | Scenario-based Review | 只谈「可用性要好」的评审无法判定缺口归属 | 能否把关键故障写成刺激-响应场景卡 |
| 跨团队、多业务线 | Architecture Review Board | 单团队评审看不见对其他团队的破坏 | 是否有准入规则，能否保证议程不被挤爆 |
| AI / 智能体参与的方案 | AI-assisted Review + Pre-Mortem | 纯人评的清单覆盖随长度下降；纯 AI 评的漏检静默且无责任人 | AI 结论是否附证据，人类是否保留决议权 |

本主题下**最常被误选的一对**是「用 Formal Review 处理日常变更」与「用 Lightweight Review 处理跨团队语义变更」。前者把固定带宽的会议用在低频收益的变更上，队列一长，团队就绕过流程；后者把只看得见 diff 的通道用在需要全局判断的变更上，改动照样上线，事故在几周后才由下游暴露——两者的共同后果是**评审制度失去约束力**，而约束力一旦失去，再补流程也换不回来。

### 3.4 组合模式：真实系统不会只用一种

三种组合分别对应三种组织形态。组合的关键不在于把模式叠加，而在于**划清每个模式管哪一段**——如果两个模式都在管「最终放行」，那么必然有一个是多余的，而且它还会成为绕道的理由。

**组合一：Lightweight ADR + PR Review + 季度 Living Review（小团队主力形态）**
- 职责边界：PR 审「改动是否正确、是否与在册 ADR 冲突」；ADR 记「为什么这么选、什么条件下推翻」；季度会审累积漂移（技术债、口径不一致、依赖收敛）。
- 运维代价：评审时间按周摊销（【经验】：每个工程师每周数小时量级），季度会审需要提前整理漂移清单，否则会开成进度汇报会。
- 适合规模：单产品线、十余人到几十人【经验】。

**组合二：Formal Review + Scenario-based Review + Pre-Mortem（关键系统变更）**
- 职责边界：RFC 定方案与影响面；场景评审验「方案在故障下如何响应」；Pre-Mortem 在决议前挖出方案自身没写出的失败模式。
- 运维代价：一次完整流程要占住核心人员 2 小时以上并叠加材料准备（【经验】），因此必须靠准入规则把它限制在少数变更上。
- 适合规模：几十人到几百人、有明确关键系统的组织【经验】。

**组合三：Architecture Board + Well-Architected + Postmortem 回路（跨团队治理）**
- 职责边界：委员会定准入与例外；支柱清单统一各团队判定口径；事故复盘把新发现的风险回灌进清单与准入规则，形成闭环。
- 运维代价：委员会带宽（双周或月度一次【经验】）+ 清单本地化的维护工作量；回路断掉时清单会迅速与现实脱节。
- 适合规模：数百人以上、多业务线或受监管的组织【经验】。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 「走过场」 | 会议记录里没有一条会导致方案修改的意见 | 评审不改变任何决策，等于没有评审，但对外显示「已评」 | 评审被定义为流程节点而非决策点，评审者无输出要求 | 要求 Reviewer 至少写一条实质意见；无意见则议题回退重准备 |
| 「一言堂」 | 决议由一个人的表态定调，之后无人再提疑点 | 反对信息在会场被压制，风险转到实施期爆发 | 权威在场且发言顺序由地位决定，异议成本高 | Devil's Advocate 角色轮值 + 关键项匿名投票 |
| 「标准不一」 | 同一方案在不同评审者处得到相反结论 | 团队无法从评审中学习，只能猜评审者偏好 | 没有成文清单，判定标准留在个人经验里 | 沉淀 Checklist 并版本化，判定分歧即回写清单 |
| 「评审滞后」 | 评审发生在实施中途或上线前 | 方案已成事实，评审只能修补，返工成本最高的一档 | 评审被排在「有空的时候」，不在交付路径上 | 把评审前置到 RFC / Design Doc 环节并设准入 |
| 「无决议」 | 会议结论是「继续推进」「再讨论」 | 没有责任边界，问题不会有人处理 | 会议纪要只记发言不记结论 | 强制四选一决议（接受 / 修订 / 拒绝 / 推迟）+ 具名 Approver |
| 「无人跟进」 | 行动项没有 Owner 或没有截止日期 | 评审承诺与实施结果之间没有闭环，同类问题反复出现 | 行动项被当成会议副产品，不进任何人的工作队列 | Follow-up 必须带 Owner + 截止日期，并进任务系统 |
| 「群体思维」 | 会上无人异议，会后私下都是异议 | 集体决议质量下降，且异议失去了进入决策的通道 | 会场沉默被当成共识，缺少让分歧安全表达的机制 | 会前独立书面意见 + 明确记录至少一条反对意见 |
| 「业务方缺席」 | 到场全是工程师，成本与合规问题无人提 | 技术最优解可能与业务约束相反，实施后被推翻 | 评审被当作技术内部事务，业务方没有被列为必到角色 | 按影响面把业务 / 安全 / 合规列为必到，缺席则议题延期 |
| 「AI 滥用」 | AI 结论直接作为放行依据，无人类复核记录 | 漏检静默发生且无法归因，评审记录失去可信度 | 引入 AI 的动机是省时间，而不是提高判定质量 | AI 只做初判且必须附证据；人类保留决议权并存档双结论 |
| 「形式主义 Checklist」 | 清单有大量空白或一律通过 | 清单覆盖率虚高，真实风险不在统计口径内 | 清单被当成证据而非工具，填完即可交差 | 每项必须有结论（通过 / 不通过 / 不适用），空白视为未查 |

三个最危险的条目在生产中这样暴露：

- **「走过场」**：它通常不是懒，而是**结构性**的——评审会排在上线前一天，材料当场才看到，评审者唯一的理性选择就是同意。识别信号是「会议时长随方案复杂度上升而下降」：复杂方案讲的比简单方案还短，说明评审已被压缩成签字。
- **「评审滞后」**：表现是事故复盘时有人说「这个当时讨论过」。问题在于讨论发生在实施中途，改动已经落地到多处，此时唯一可用的手段是补丁，而不是换方案——返工量在这一点上被锁死。
- **「AI 滥用」**：最新的一类，暴露方式是评审通过率异常高且无人能解释理由。它比人工走过场更隐蔽，因为记录里每一项都有结论，只是结论没有人类读过。

### 3.6 规模跃迁时模式何时该换

下表的规模档位按团队人数与业务线数量粗略分档（【经验】），不同组织差异很大；真正可迁移的是「疼在哪里」与「换成什么」这两列。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 十余人 → 百人（跨团队依赖出现） | PR Review | diff 里看不到调用方语义，跨团队破坏只能靠下游故障发现 | Formal Review + 变更影响面清单 | 会议容量成为吞吐上限，需要准入规则；文档成本上升 |
| 百人 → 数百人（多业务线） | Formal Review 单点决策 | 议题排队，关键方案等会议，团队开始绕道 | Board + 明确例外机制 | 委员会判断滞后，需要后备评审与例外台账 |
| 单区域 → 多区域 / 多云 | 单一 Well-Architected 清单 | 地区合规、网络与成本约束不同，一份清单判定失真 | 支柱清单 + 地区差异项 | 清单膨胀，维护成本与判定分歧同步上升 |
| 人工系统 → AI / 智能体参与 | 纯人工评审 | 生成量与变更量上升，清单覆盖随长度下降 | AI 初判 + 人类把关 + Pre-Mortem | 误报消化成本 + 评审标准必须显式写出来 |
| 委员会逐案审批 → 平台化治理 | Board 逐案决议 | 带宽固定而方案数增长，队列成为瓶颈 | 把标准编码进门禁（CI / 平台），委员会只处理例外 | 门禁建设与误拦调参；标准写错会全组织放大 |

判断是否已跨过阈值，不看人数，而看三个可观测信号：**评审队列的等待时间是否超过方案本身的实施时间**、**是否出现过绕过流程的变更**、**最近的事故能否追溯到评审记录的漏项**。前两个信号说明当前模式的容量已满，第三个信号说明当前模式的深度已不够。

三个信号的修法方向不同：容量已满要**减节点或加分流**（把低频深审与高频浅审拆成两条通道），深度不够要**加结构**（补影响面清单、把场景写具体）。把深度问题误诊成容量问题，常见后果是继续加人开会——会议人数增加不会提升判定精度，只会推迟决议时间。

### 3.7 自检清单

- [ ] 每个评审议题，能否指出它的**不可逆程度**（事后回退的代价量级）？指不出说明评审被用错了场合。
- [ ] 本次评审的 Reviewer 意见里，是否至少有一条会导致方案修改？零条即为走过场。
- [ ] 会议记录里是否有**四选一的决议**并落到具名 Approver？只写「继续推进」即无决议。
- [ ] 每条行动项是否同时带 Owner 与截止日期？缺任一项即不算行动项。
- [ ] 跨团队影响面是**查出来的**还是**估出来的**？估出来的必须在结论里标明置信度。
- [ ] 评审材料在会前多久下发？会场首次见到材料的议题应改到下次。
- [ ] 记录里是否至少留下一条被认真处理的反对意见？无异议记录时，无法区分共识与沉默。
- [ ] Checklist 每一项是否都有结论（通过 / 不通过 / 不适用）？空白项等于没查。
- [ ] 影响面分析是否挂在发布门禁上？只放在文档里的评审不产生约束力。
- [ ] AI 初判是否附了证据（命中位置 / 规则名）？无证据的初判不能作为通过理由。
- [ ] 最近一次事故能否回溯到某次评审的漏项？回溯不到，说明评审与事故数据之间没有回路。
- [ ] **评审节点数 × 单节点准备工时**，是否超过团队每周可支配的评审时间？超过即必然退化为签字。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 高频小变更、单团队 | Lightweight Review（PR） | 评审单位是 diff、通道异步，成本随变更数近似线性增长 |
| 单一团队、有既有标准 | Lightweight + Checklist | 有外置判定标准时，深度来自清单而非会议人数 |
| 多属性冲突、不可逆 | ATAM | 权重先定、逐场景打分，冲突以数字而非嗓门呈现 |
| 跨团队语义变更 | Formal Review + 影响面清单 | 文档前置 + 预审，分歧才占得住会议时间 |
| 云上系统、需跨团队可比 | Well-Architected Review | 外置标准使结论可横向比较、跨年度追踪 |
| 高可用 / 高一致性 | Scenario-based Review | 场景把抽象属性变成可判定的刺激-响应 |
| 会产生失败模式的新型方案 | Pre-Mortem（在决议前） | 独立书写发生在任何表态之前，锚定效应被消除 |
| 数百人以上多业务线 | Board + 门禁 + 例外台账 | 带宽固定，必须靠准入与例外分流而非全量上会 |

> 本节小结：决定架构评审模式选择的**唯一那条约束**是「**评审挂在哪个环节、那一环对结果有没有约束力**」——挂在文档里就没有约束力，挂在门禁上才有；其余差异（会议、清单、人数）都是这条约束的调节旋钮。所以真正的对标问题不是「该用哪种评审方法」，而是「这次决策不可逆的程度有多大、这一环能不能拦住它」。

> 💡 **思考锚点**：挑最近一次你签字放行的评审，倒推一步——如果那次决策挂的不是文档而是门禁，它会不会把同一处改动拦下来？如果拦不下，你该换的是评审方法，还是它挂载的那个环节？
