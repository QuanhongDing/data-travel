## 6. 落地实践

### 6.1 AWS"**把评审产品化：让没有顶级架构师的团队也能自己做评审**"（2014-2024）

**背景（Why）**

AWS 2014 年面临**"评审能力无法规模化"**：
- **评审需要资深架构师**——**而资深架构师的数量远少于需要评审的系统数量**
- **客户水平差异巨大**——**几十万企业客户中，绝大多数没有专门的架构评审能力**
- **评审结论不可比较**——**每次评审的深度与结论取决于谁来做，无法横向对照**
- **评审做完就结束**——**没有后续跟踪，改进项是否落地无人知晓**

**触发点（What）**

2014 年起 AWS 把架构评审**产品化**（[AWS 公开材料 2014-2024]），目标：
- **可自助开展**——不必等专家
- **结论可比**——同一套方法产出可对照的结果
- **有闭环**——改进项可跟踪

**详细做法（How）**

评审产品化的**5 大核心组件**：

1. **把"专家判断"转化为"可自助执行的流程"（核心创新）**
   - 关键设计：**评审拆成"清单 + 评价标准 + 产出模板"三件套**，团队按清单逐项自评，产出统一格式的评审报告；专家从"逐场评审"转为"抽查与疑难裁决"
   - 关键能力：**评审人力不再随系统数量线性增长**——这是评审能覆盖大量系统的唯一现实路径
   - 关键性质：**可自助开展、专家转为抽查**
   - 关键示意：
     ```text
     评审产品化：把专家能力转化为可复制的流程
       ✗ 专家逐场评审
         系统 N 个 → 需要 N 场专家评审 → 专家数量成为瓶颈
         → 评审覆盖率低，且排队等待拖慢项目
       ✓ 清单 + 标准 + 模板 三件套（团队自助）
         清单：需要回答哪些问题（覆盖固定的维度）
         标准：每个问题的"合格 / 需改进 / 不合格"如何判定
         模板：产出统一格式报告（风险项 / 优先级 / 改进建议 / 责任人）
                    │
         专家角色转变：
           · 从"每场都到场" → "抽查 + 疑难裁决 + 标准维护"
           · 输出从"个体结论" → "标准与案例库"
       ────────────────────────────────────────────────
     关键：产品化不等于降低标准，
           而是把"标准"显式写出来，让达标不再依赖某个人在场
     ```

2. **产出"改进项清单"而非"通过与否"（核心）**
   - 关键设计：**评审产出是一组带优先级、责任人与预期收益的改进项**，而不是结论性判定
   - 关键能力：**评审从"闸门"变成"体检 + 处方"**——团队拿到的是可执行的动作，而不是一个需要争辩的结论
   - 关键性质：**产出可执行、争议显著减少**

3. **评审宽度按系统重要性分层（核心）**
   - 关键设计：**核心系统走完整评审 + 专家参与；一般系统走自助清单；内部工具走轻量检查**
   - 关键能力：**评审成本与系统影响匹配**——所有系统都走完整评审既不经济也做不到
   - 关键性质：**分层评审、资源集中**

4. **改进项闭环跟踪（核心）**
   - 关键设计：**改进项进入跟踪列表，定期回看状态**；未处理的需显式记录为"接受风险"并说明理由
   - 关键能力：**评审不会"开完就忘"**——并区分"遗漏"与"有意识接受"
   - 关键性质：**改进项可跟踪、接受需显式**

5. **案例库与标准演进（核心创新）**
   - 关键设计：**典型问题与处理方式沉淀为案例库**，用于校准判断标准；标准随技术演进更新
   - 关键能力：**评审能力随组织积累**，而不是停留在"当初写的那份清单"
   - 关键性质：**案例可复用、标准可演进**

**AWS 评审产品化关键数字**（[AWS 公开材料 2014-2024]）：

| 指标 | 改前（专家逐场评审） | 改后 | 提升 |
| --- | --- | --- | --- |
| **评审开展方式** | 依赖专家到场 | 清单 + 标准 + 模板自助 | **可规模化** |
| **覆盖能力** | 受专家数量限制 | 团队自行开展 | **大幅扩展** |
| **专家角色** | 逐场评审 | 抽查 + 疑难裁决 + 维护标准 | **能力被放大** |
| **产出形态** | 通过 / 不通过 | 改进项 + 优先级 + 责任人 | **可执行** |
| **结论可比性** | 因人而异 | 同一套标准 | **可对照** |
| **评审分层** | 一刀切 | 按系统重要性分层 | **成本与影响匹配** |
| **闭环程度** | 开完即结束 | 改进项跟踪 + 风险接受显式 | **可闭环** |
| **服务客户规模** | 少数 | 大量企业客户 | **∞** |

**具体数字（How much）**

- 团队规模：AWS 架构 / 解决方案团队数千人，服务大量企业客户
- 关键性质：**三件套自助**；**产出改进项**；**分层评审**；**案例库沉淀**
- 业务影响：把架构评审从"依赖顶级架构师的经验"变成"可自助、可比对、可闭环"的产品化能力

**失败教训**

- 早期「**每场评审都要专家到场**」——专家成为瓶颈、覆盖率低，倒逼**「清单 + 标准 + 模板，团队自助开展」**
- 「**评审产出只是"通过/不通过"**」——团队对抗、改进无处下手，倒逼**「产出改进项清单（含优先级与责任人）」**
- 「**所有系统走同样的评审深度**」——资源被稀释，倒逼**「按系统重要性分层评审」**
- 「**开完会就不管了**」——改进项无跟踪，倒逼**「改进项跟踪 + 未处理须显式记录为接受风险」**
- 「**标准写死不再更新**」——与技术与业务脱节，倒逼**「案例库沉淀 + 标准随演进更新」**

### 6.2 阿里"**集团架构委员会：分层评审与"评审前置"的取舍**"（2014-2024）

**背景（Why）**

阿里 2014 年面临**"评审要么不管用、要么卡死业务"**：
- **25 BU 系统数量巨大**——**所有系统都上集团评审会让流程瘫痪**
- **委员会评审容易形式化**——**材料没看、会上听汇报、结论靠印象**
- **审晚了没用**——**已经开发完的架构，评审只能"事后追认"，改不动**
- **责任边界不清**——**委员会"建议"与团队"决定"的边界模糊，出问题无人负责**

**触发点（What）**

2014 年起阿里构建**分层架构评审体系与集团架构委员会**（[阿里公开材料 2014-2024]），目标：
- **分层评审**——按影响面决定评审级别
- **评审前置**——在可改动的时点评审
- **边界清晰**——委员会关注什么、团队决定什么

**详细做法（How）**

阿里分层评审体系的**5 大核心组件**：

1. **按"影响面 + 不可逆程度"分层（核心创新）**
   - 关键设计：**评审级别由两个维度决定**——**影响多少团队 / 系统**，以及**决策的不可逆程度**（技术选型、数据模型这类改起来极贵的算高不可逆）；只有跨团队且难逆的决策才上集团委员会
   - 关键能力：**评审资源投向真正需要集体决策的事**——把"团队内可逆的决策"也抬到集团评审，是流程瘫痪的常见原因
   - 关键性质：**分层评审、集团级评审聚焦少数**
   - 关键示意：
     ```text
     评审分层：两个维度决定要不要上委员会
                       不可逆程度高         不可逆程度低
       影响面大（跨团队）  集团委员会评审        域级评审
       影响面小（单团队）  域级评审 + 专家咨询    团队自评
     ────────────────────────────────────────────────
     典型归类：
       集团委员会：技术选型（锁定长期）、数据模型定义、跨域接口契约、
                   共享基础设施的引入与下线
       域级评审：  域内服务架构、跨服务依赖调整
       团队自评：  模块内部设计、可逆的实现选择
     ────────────────────────────────────────────────
     关键：把"不可逆"作为独立维度
           因为不可逆决策的修正代价远高于可逆决策，
           即便影响面不大也值得评审（如全局 ID 规则）
     ```

2. **评审前置到"还改得动"的时点（核心）**
   - 关键设计：**评审发生在设计阶段**（方案确定但尚未大规模实现），评审材料是设计方案而非已完成的实现
   - 关键能力：**评审能真正影响结果**——开发完再评审，结论只能是"要么接受，要么推翻重来"，两者都无法被接受
   - 关键性质：**评审前置到设计阶段**

3. **材料驱动而非汇报驱动（核心）**
   - 关键设计：**评审前材料必须提前分发并预读**；会上只讨论分歧点与关键假设，不做完整汇报
   - 关键能力：**会议时间花在实质分歧上**——汇报驱动的评审会，大部分时间在听已经能读到的内容
   - 关键性质：**预读制 + 只议分歧**

4. **明确"谁决定"（核心）**
   - 关键设计：**区分委员会的"否决权"与"建议权"**：涉及跨域契约与不可逆决策，委员会可要求修改；其余情况委员会只提建议，决定权在团队并被记录
   - 关键能力：**责任边界清晰**——避免"委员会建议了但团队没听、出事互相推"的常见扯皮
   - 关键性质：**边界清晰、决定可追溯**

5. **评审产出与决策记录绑定（核心创新）**
   - 关键设计：**评审结论写入架构决策记录**（含被否决的方案与理由），作为后续追溯依据
   - 关键能力：**"当初为什么这么定"可追溯**——也让后续团队不必重新讨论已决事项
   - 关键性质：**结论入决策记录**

**阿里分层评审关键数字**（[阿里公开材料 2014-2024]）：

| 指标 | 改前（一刀切上会） | 改后 | 提升 |
| --- | --- | --- | --- |
| **评审分层依据** | 无明确标准 | 影响面 × 不可逆程度 | **资源投向关键决策** |
| **集团级评审量** | 全部系统 | 仅跨团队且难逆的决策 | **不再瘫痪** |
| **评审时机** | 开发完成后 | 设计阶段（还改得动） | **能影响结果** |
| **会议形式** | 汇报驱动 | 材料预读 + 只议分歧 | **时间用在实质** |
| **决定权边界** | 模糊 | 否决权 / 建议权明确 | **责任清晰** |
| **结论留痕** | 会议纪要 | 写入架构决策记录 | **可追溯** |
| **评审量** | — | 1000+ 评审/年 | **可承载** |
| **重复讨论** | 常见 | 已决事项可查 | **下降** |

**具体数字（How much）**

- 团队规模：阿里架构 / 技术治理团队 100+ 人（含跨 BU 委员会）
- 关键数字：**1000+ 评审/年**；**两维分层**；**评审前置**；**材料预读**；**结论入决策记录**
- 业务影响：让 25 BU 的架构评审既能覆盖关键决策，又不成为业务推进的阻塞点

**失败教训**

- 早期「**所有系统都上集团评审**」——流程瘫痪、排队严重，倒逼**「按影响面与不可逆程度分层」**
- 「**开发完成后才评审**」——只能事后追认或推翻重来，倒逼**「评审前置到设计阶段」**
- 「**会上完整汇报**」——时间浪费在听已能读到的内容，倒逼**「材料预读 + 只议分歧」**
- 「**委员会权限不清**」——出问题互相推责，倒逼**「明确否决权与建议权边界」**
- 「**评审结论只有纪要**」——后续重复讨论已决事项，倒逼**「结论写入架构决策记录」**

### 6.3 字节"**评审绑数据：用指标而不是印象判断架构是否达标**"（2019-2024）

**背景（Why）**

字节 2019 年面临**"评审结论依赖印象与表达能力"**：
- **4 业务架构评审标准不一**——**各业务按自己理解评审，横向不可比**
- **结论靠"讲得好不好"**——**材料漂亮、表达强的团队更容易通过，而不是架构本身更好**
- **架构问题与业务指标脱节**——**评审说"这里有问题"，但说不出会影响哪个业务指标**
- **评审通过后仍出问题**——**评审时无法预判上线后的表现**

**触发点（What）**

2019 年起字节推进**评审与指标绑定的架构 Review**（[字节技术博客 2019-2024]），目标：
- **标准统一**——4 业务共用
- **结论有数据支撑**——不只看设计与表达
- **与业务指标挂钩**——架构问题能对应到业务影响

**详细做法（How）**

字节评审绑数据的**5 大核心组件**：

1. **评审材料必须包含可验证的量化依据（核心创新）**
   - 关键设计：**评审材料除设计外，必须包含**：容量与性能的估算依据、压测或原型数据、关键指标的影响预判（对下单成功率 / 延迟 / 成本的影响估算）
   - 关键能力：**结论建立在数字上而非表达上**——"这个设计能撑住"必须给出估算依据，而不是靠语气
   - 关键数字：**材料含量化依据、4 业务统一**
   - 关键示意：
     ```text
     评审材料清单（把"讲得好"换成"算得出"）
       ① 设计说明      架构、模块、接口、数据流
       ② 容量估算      各层容量来源（按业务漏斗 / 按用户规模 × 行为强度）
                       · 与容量规划同一套模型，评审与规划不脱节
       ③ 性能依据      压测数据或原型验证结果，而不是"预期没问题"
       ④ 影响面预判    对关键业务指标的预估影响（成功率 / 延迟 / 成本）
       ⑤ 风险与降级   已知风险、触发条件、降级预案
       ⑥ 可回滚设计    发布与回滚路径（含不可逆变更的拆分方案）
     ────────────────────────────────────────────────
     关键：②③④ 三项是分水岭
           没有它们，评审只能在"设计是否合理"层面讨论
           有了它们，评审才能问"这个估算站得住吗"
     ```

2. **评审结论与业务指标对应（核心）**
   - 关键设计：**每个评审意见都标注它影响哪个业务指标以及大致影响量**，而不只是"这里需要改进"
   - 关键能力：**评审意见的优先级有业务依据**——影响下单成功率的意见优先于影响内部效率的
   - 关键性质：**意见与业务指标对应、优先级有依据**

3. **4 业务统一评审标准（核心）**
   - 关键设计：**共用同一套评审清单与判定标准**，业务只在"业务指标权重"上差异化
   - 关键能力：**横向可比**，也让"某业务评审较松"无处藏身
   - 关键数字：**4 业务共用同一套清单、横向可比**

4. **评审与容量规划 / 风险清单联动（核心）**
   - 关键设计：**评审输入复用容量规划模型与风险清单**，评审产出的风险项进入风险清单跟踪
   - 关键能力：**评审不是孤立环节**，而是与容量、风险、发布流程串成一条链
   - 关键性质：**与规划 / 风险联动**

5. **评审后的表现回看（核心创新）**
   - 关键设计：**系统上线后回看评审时的估算与实际表现**（容量估算准不准、指标影响预估对不对），并据此校准评审标准
   - 关键能力：**评审能力可被评估与提升**——这是评审从"仪式"变成"能力"的关键
   - 关键性质：**估算准确度可评估、标准可校准**

**字节评审绑数据关键数字**（[字节技术博客 2019-2024]）：

| 指标 | 改前（靠设计与表达） | 改后 | 提升 |
| --- | --- | --- | --- |
| **评审依据** | 设计说明 + 口头表达 | 设计 + 容量估算 + 压测 + 影响预判 | **建立在数据上** |
| **容量估算来源** | 各自估计 | 复用容量规划模型 | **与规划一致** |
| **评审意见** | 只描述问题 | 标注影响的业务指标 | **优先级有依据** |
| **业务间可比性** | 各业务标准不同 | 4 业务统一清单 | **可横向对照** |
| **与风险清单** | 各自独立 | 评审产出进入风险清单跟踪 | **成链** |
| **可回滚设计** | 未要求 | 作为材料必备项 | **发布风险可控** |
| **估算准确度** | 无人回看 | 上线后回看并校准标准 | **评审能力可提升** |
| **评审通过后出问题** | 常见 | 因事先有估算与降级设计 | **显著减少** |

**具体数字（How much）**

- 团队规模：字节架构 / 平台团队 100+ 人，服务 4 业务
- 关键性质：**材料含量化依据**；**意见绑业务指标**；**与容量风险联动**；**上线后回看校准**
- 业务影响：让架构评审从"基于设计与表达的判断"变成"基于数据与业务影响的判断"

**失败教训**

- 早期「**只看设计与表达**」——讲得好的团队更容易过，架构本身的问题被放过，倒逼**「材料必须包含容量估算、性能依据与影响预判」**
- 「**评审意见不绑业务指标**」——优先级无法判断，倒逼**「每条意见标注影响的业务指标与量级」**
- 「**各业务自定评审标准**」——横向不可比且易松，倒逼**「4 业务统一清单，只在指标权重上差异化」**
- 「**评审与容量 / 风险流程割裂**」——重复劳动且结论不一致，倒逼**「复用规划模型，产出进入风险清单」**
- 「**评审完不回看估算准确度**」——评审能力无法提升，倒逼**「上线后回看并校准标准」**

### 6.4 Google"**Design Doc：把评审建立在"写下来"这一步上**"（2014-2024）

**背景（Why）**

Google 2014 年面临**"设计决策只存在于讨论中"**：
- **决策过程不留痕**——**讨论主要在会议与聊天里，结论散落，后来者只能看到最终实现**
- **评审质量取决于参与者是否想清楚**——**没有书面材料时，评审容易停留在表层**
- **跨时区协作困难**——**全球团队无法靠同步会议评审，必须有异步材料**
- **新人无从理解现状**——**"为什么这么设计"没有系统性记录**

**触发点（What）**

2014 年起 Google 推行 **Design Doc 与设计评审**（[Google 公开材料 2014-2024]），目标：
- **写作即思考**——设计必须先写清楚
- **异步可评审**——跨时区可参与
- **决策留痕**——可追溯、可传阅

**详细做法（How）**

Design Doc 机制的**5 大核心组件**：

1. **"必须先写下来"作为评审的前置条件（核心创新）**
   - 关键设计：**任何非平凡的设计必须先产出 Design Doc**（背景与目标 / 备选方案与取舍 / 详细设计 / 风险与边界 / 评审记录），评审基于该文档进行
   - 关键能力：**写作本身逼迫设计想清楚**——很多设计问题在"要把它写明白"的过程中就被作者自己发现了，而不是等到评审会
   - 关键性质：**设计先成文、评审有材料**
   - 关键示意：
     ```text
     Design Doc 的价值有一半发生在"写"的过程中
       写作迫使作者回答：
         · 目标是什么？成功的判据是什么？（写不清说明没想清）
         · 有哪些备选方案？为什么排除它们？（强迫穷举）
         · 关键假设是什么？如果不成立会怎样？（暴露脆弱点）
         · 边界在哪？明确不做什么？（防止范围蔓延）
         · 风险与降级？（把"肯定没问题"逼成可检查项）
       ────────────────────────────────────────────────
       对照"直接开会讨论设计"：
         讨论往往停留在"方案是什么"
         因为会上没有时间穷举备选与推演假设
         → 评审结论容易变成"听起来可以"
     -- 关键：Design Doc 把"想清楚"的负担前移到了作者身上，
           评审则聚焦在"假设是否成立、备选是否穷尽"
     ```

2. **异步评审为主（核心）**
   - 关键设计：**文档先分发，评论异步进行**；只在存在实质分歧或重大决策时才安排同步会议
   - 关键能力：**跨时区与跨团队可参与**，且评论有记录、可回溯
   - 关键性质：**异步为主、会议仅用于分歧**

3. **备选方案必须写（核心）**
   - 关键设计：**文档必须包含被考虑但未采用的方案及排除理由**，只写最终方案视为不合格
   - 关键能力：**迫使作者真正比较过**，也让后来者知道"这条路当初为什么没走"
   - 关键性质：**备选必写、排除理由必写**

4. **评审者的职责是质疑假设而非设计细节（核心）**
   - 关键设计：**明确评审重点在"目标是否清楚、假设是否成立、备选是否穷尽、风险与降级是否覆盖"**，而不是在命名与实现细节上纠缠
   - 关键能力：**评审效率与深度兼得**——细节问题可以在代码评审阶段解决，设计评审应聚焦在成本最高的决策上
   - 关键性质：**评审聚焦假设与取舍**

5. **文档持续更新而非一次性（核心创新）**
   - 关键设计：**设计在实现过程中发生变化时，文档被更新并保留评审记录**；重大变更需重新评审
   - 关键能力：**文档与实现不脱节**——否则文档很快变成无人信的历史材料
   - 关键性质：**文档可更新、重大变更重审**

**Google Design Doc 关键数字**（[Google 公开材料 2014-2024]）：

| 指标 | 改前（会上讨论设计） | 改后 | 提升 |
| --- | --- | --- | --- |
| **设计载体** | 会议与聊天记录 | Design Doc 成文 | **可传阅可追溯** |
| **评审时机** | 会后凭记忆 | 基于文档预读 | **评审有材料** |
| **设计想清楚的时点** | 评审时才暴露问题 | 写作过程中作者自行发现 | **问题更早暴露** |
| **备选方案** | 基本不记录 | 必写并给排除理由 | **避免重复讨论** |
| **评审重点** | 容易落到细节 | 聚焦目标 / 假设 / 备选 / 风险 | **效率与深度兼备** |
| **跨时区参与** | 受会议时间限制 | 异步评论 | **可参与性提升** |
| **文档与实现一致性** | 文档很快过期 | 随实现更新，重大变更重审 | **不过期** |
| **新人理解现状** | 靠口口相传 | 文档 + 评审记录可查 | **显著加快** |

**具体数字（How much）**

- 团队规模：Google 工程团队万人级，设计文档实践被业界广泛采纳
- 关键性质：**设计先成文**；**异步评审为主**；**备选必写**；**评审聚焦假设与取舍**
- 业务影响：让设计决策过程可追溯、可异步协作，并把设计问题在写作阶段就暴露出来

**失败教训**

- 早期「**设计只在会上讨论**」——结论散落、无留痕、后来者无从理解，倒逼**「非平凡设计必须先产出 Design Doc」**
- 「**评审只讨论最终方案**」——无法判断备选是否穷尽、取舍是否合理，倒逼**「备选方案与排除理由必写」**
- 「**评审落到命名与实现细节**」——关键假设与风险反而没被质疑，倒逼**「明确评审重点在目标 / 假设 / 备选 / 风险」**
- 「**依赖同步会议评审**」——跨时区无法参与、评论无记录，倒逼**「异步评审为主，会议仅用于实质分歧」**
- 「**文档写完就不更新**」——与实现脱节、无人再信，倒逼**「随实现更新，重大变更重新评审」**

### 6.5 真实落地路径（基于上述 4 个案例提炼）

**0 → 1 阶段：3-6 个月**

- 选「**一份评审清单 + 设计先成文 + 一条真实评审**」（**最简单**）——**1 个团队**
- 产出：**评审清单（覆盖固定维度）+ 首个成文设计文档 + 一次基于材料的评审记录**
- 团队：**2-3 人**
- 验证标准：**设计先成文再评审（不是口头讨论）**、**文档含备选方案与排除理由**、**评审产出改进项而非只有结论**

**1 → 10 阶段：6-12 个月**

- 扩展到「**10+ 团队 / 分层评审**」
- 引入「**按影响面 × 不可逆程度分层**」——集团 / 域 / 团队三级
- 引入「**评审前置到设计阶段**」+「**材料预读，会议只议分歧**」
- 团队：5-10 人
- 验证标准：**评审在还改得动的时点进行**、**评审资源投向难逆决策**、**会议时间花在实质分歧上**

**10 → 100 阶段：12-24 个月**

- 扩展到「**100+ 团队 / 多业务**」
- 引入「**统一评审标准 + 材料量化要求**」（容量估算 / 性能依据 / 影响预判 / 可回滚设计）
- 引入「**评审意见绑定业务指标**」+「**改进项闭环跟踪（未处理须显式记录为接受风险）**」
- 团队：10-30 人
- 验证标准：**结论建立在数据而非表达上**、**意见优先级有业务依据**、**改进项可跟踪且接受需显式**

**100 → 1000 阶段：12-24 个月**

- 引入「**评审产品化（清单 + 标准 + 模板，团队自助；专家转为抽查与疑难裁决）**」
- 引入「**异步评审为主 + 案例库沉淀 + 标准随演进更新**」
- 引入「**上线后回看估算准确度并校准标准**」+「**评审结论写入架构决策记录**」
- 团队：30-100 人
- 验证标准：**评审可自助开展且可比对**、**评审能力可被评估与提升**、**决策可追溯**、**已决事项不被重复讨论**

### 6.7 ROI 评估（4 个公司真实数据）

| 指标 | 改前 | 改后 | 提升 |
| --- | --- | --- | --- |
| 「**评审覆盖能力**」 | 受专家数量限制 | 清单化自助开展 | **大幅扩展** |
| 「**评审资源投放**」 | 一刀切 | 按影响面 × 不可逆程度分层 | **投向关键决策** |
| 「**评审时机**」 | 开发完成后 | 设计阶段 | **能影响结果** |
| 「**评审结论依据**」 | 设计与表达 | 数据（容量 / 性能 / 影响预判） | **可辩护** |
| 「**意见优先级**」 | 主观 | 绑定业务指标与量级 | **有依据** |
| 「**会议效率**」 | 完整汇报 | 预读 + 只议分歧 | **时间用在实质** |
| 「**结论可比性**」 | 因人而异 | 统一标准 | **可横向对照** |
| 「**闭环程度**」 | 开完即结束 | 改进项跟踪 + 显式风险接受 | **可闭环** |
| 「**决策可追溯性**」 | 会议纪要 | 写入架构决策记录 | **可追溯** |
| 「**评审能力可提升性**」 | 无度量 | 上线后回看估算准确度 | **可评估可校准** |

**关键投资回报**：
- **直接节省**：「**评审产品化（自助 + 分层）+ 前置到设计阶段 + 材料预读**」——**评审的最大成本是"专家时间"与"返工"**：产品化让专家时间从"逐场评审"变成"抽查与标准维护"，前置让问题在还改得动时被发现，两者都是数量级的成本差异
- **业务价值**：「**结论建立在数据上 + 意见绑定业务指标 + 可自助可对照**」——**评审的价值在于"让错误的架构在成本最低时被拦住"**；而当评审依据是数据、意见挂业务指标、标准统一可比时，评审才不再是"谁表达好谁通过"
- **AI 时代关键**：「**量化材料要求 + 评审聚焦假设与取舍 + 上线后回看校准**」——**AI 系统的架构评审需要新的量化维度**（推理成本随请求长度变化、模型质量漂移、训练与推理的资源竞争），这些既不在传统容量模型里也不在传统风险清单里；把"假设与取舍"作为评审焦点、并要求上线后回看估算，是新场景下评审仍能产生判断力的前提

---

> **本节小结**：
> - 4 个真实案例（AWS / 阿里 / 字节 / Google）印证：**架构评审不是「开个评审会」，是「设计先成文 + 按影响面 × 不可逆程度分层 + 前置到设计阶段 + 材料量化 + 改进项闭环并可回看校准」5 件套**。
> - 关键时间线：AWS 10+ 年 / 阿里 10+ 年 / 字节 5+ 年 / Google 10+ 年 —— **评审体系是长期演进的机制**，且**它最容易失效的两种方式是"变成形式"与"卡住业务"**。
> - 选型第一原则：「**一份清单 + 设计先成文 + 一条真实评审**」（**最简单**）——**1 个团队** → 「**分层评审 + 前置到设计阶段 + 材料预读**」（**必须**）→ 「**统一标准 + 材料量化 + 意见绑业务指标 + 改进项闭环**」（**生产**）→ 「**评审产品化 + 异步为主 + 上线后回看校准 + 结论入决策记录**」（**AI 时代**）。
> - 99% 的失败来自「**依赖专家逐场评审 + 一刀切上会 + 开发完才评 + 结论靠表达**」——必须有 **自助化 + 分层 + 前置 + 量化**。
> - 真正的 ROI 来自「**覆盖能力扩展 + 评审投对地方 + 结论可辩护 + 评审能力可提升**」——是**架构评审能否从"仪式"变成"真正拦住错误架构的机制"的分水岭**。

> 💡 **思考锚点**：翻出你团队最近三次评审，按 §7.6 的「影响面 × 不可逆程度分层」给它们各标一个档——三次是同一深度，还是难逆决策被单独拎出来？如果三次都仍是「依赖专家逐场评审 + 开发完成后才评」，你打算先从「设计先成文」还是「材料预读、会议只议分歧」这一件起步？
