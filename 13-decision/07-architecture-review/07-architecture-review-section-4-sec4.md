## 4. 工程实现

本节按「落地步骤 → 关键技术点 → 工具链 → 存量迁移 → 模板 → 自检」组织。术语与主文件 [§ 2 核心原理](07-architecture-review.md) 逐字一致：**Lightweight Review / Formal Review / ATAM / Architecture Board / Checklist / Quality Attributes / Stakeholder / Reviewer / Approver / Decision Outcome / Follow-up Action / ADR / Pre-Mortem / AI-assisted Review** ——在本节里指的就是 §2.1 定义的那几件事，不另立口径。每个模式被什么约束逼出来、代价与失效点见 [§3 设计模式与范式](07-architecture-review-section-3-sec3.md)，本节不复述。读者分两类：**从零搭建**的组织按 §4.1 的 Step 1–4 起步（定对象与准入、定流程、定清单、定委员会），Step 5–8 随规模补，模板直接取 §4.5；**在存量上改造**的组织是多数——已经有系统在跑、已经开过评审会、也已经有了一批没有记录的决策，请把 §4.1 当顺序依据、把 **§4.4 当主路径**。顺序反过来，会在新流程落地前先撞上「历史包袱没人认」的墙。判别自己属于哪一类只需回答一个问题：能不能拿出去年三个重大决策的书面依据。拿不出，就先做 §4.4 的①。

### 4.1 落地步骤

**Step 1：定义评审对象与评审类型（1–2 周【经验】，随待评方案数与是否存在跨团队契约而变）**

- 列一张对应表，只按一个变量分档：这次决策的**不可逆程度**（[§3.1](07-architecture-review-section-3-sec3.md) 给的就是这条根约束）。日常变更 → **Lightweight Review**（PR / MR，异步）；中型变更 → **Formal Review**（评审会，会前有 RFC 或 Design Doc）；战略级、质量属性互相冲突 → **ATAM**。
- 同时列「不上会」的反例（单团队内、一周内可回退、影响面不超出本服务的改动），并指定准入的判定权归谁——必须落在一个人身上，不能是「各团队自己判断」。

- **产物**：一页对应表 + 一页反例清单，放在评审流程文档首页。
- **判据**：拿过去三个月已发生的 10 次变更回测。应上会而未上会的超过 3 次【经验】，说明门槛高于现状，先把强制范围收缩到其中一类；反之，应走 PR 却开了会的超过 3 次，说明分档变量选错了——多半用成了「改动行数」而不是不可逆程度。
- **为什么必须第一步**：流程、清单、委员会都只回答「怎么评」，只有这一步回答「哪些要评」。顺序反过来，第一批进队列的议题由「谁喊得响」决定，队列被低频小变更挤满之后团队就开始绕道，而绕道一旦发生，后面几步再补也换不回约束力。

**Step 2：建立评审流程（2–4 周【经验】，随是否已有 RFC 载体而变）**

- 把链路固定成七段：方案起草 → 提交（RFC / Design Doc）→ 预审（资深架构师）→ 正式评审 → 决议 + Follow-up Action → ADR 归档 → 实施 + 复盘。给每一段写清进入条件与产物：预审的产物是「争议项清单」，正式评审的产物是四选一决议，复盘的产物是回写进 Checklist 的新检查项。
- 时间盒：预审按每项 30 分钟、正式评审 2 小时、到会 5–8 人【经验，随议题复杂度与资质分布浮动】。超时不把会开长，把未审定项退回下次。

- **产物**：一张带进入条件与产物的流程表 + RFC 模板的挂载位置。
- **判据**：抽最近三次会议纪要，看预审有没有留下「争议项清单」。没有，说明预审退化成了过场，正式评审在花时间做信息同步。再看决议是否四选一——出现「继续推进」即判为无决议。
- **为什么必须排在对象定义之后**：流程的每一段都以「什么议题进得来」为前提。准入没定，预审无对象可分，正式评审会变成所有议题的唯一通道。

**Step 3：建立评审 Checklist（2–4 周【经验】，随质量属性条目数与是否按场景分册而变）**

- 按三组展开：**Quality Attributes**（性能 / 可用性 / 安全 / 可扩展性 / 可维护性 / 可治理性）、业务约束（性能 / 成本 / 时间）、反模式（单点 / 过度耦合 / 无降级 / 无监控）。
- 每一项写成能被否证的问题，不给「是否重视」这类口号；每项必须落到三种结论之一：通过 / 不通过 / 不适用。清单进版本库，注明版本号与生效日期。

- **产物**：一份版本化的 Checklist + 一次空白率统计。
- **判据**：抽 3 份最近的评审记录，数「空白项 / 总项」。空白超过两成【经验】说明清单长度已超过单次评审的注意力预算，该拆成通用册 + 场景册；再抽 3 项看结论是否落在三选一上。
- **为什么必须排在流程之后**：清单是判定标准，流程是判定发生的地方。标准先于场所出现，先得到一份没人用的清单；两者顺序颠倒时最典型的症状，是清单被当成「交差证据」而不是判定工具。

**Step 4：建立评审委员会（Architecture Board）（4–8 周【经验】，随业务线数量与例会频率而变）**

- 定成员构成：架构师 + 安全 + 数据 + 业务代表，5–10 人【经验】；定准入：跨团队 / 不可逆 / 超成本阈值的方案才上会，例会按双周或月度【经验】，议程公开。
- 定输出：架构白皮书（组织级技术标准与 **Tech Radar**）+ ADR 审批 + 例外记录（谁批的、为什么）。

- **产物**：一页准入规则 + 一份公开议程 + 一本例外台账。
- **判据**：看例外台账第一条记录产生于何时。台账长期为空，通常意味着准入宽到什么都上会，或者窄到有价值的方案全部绕过——两种一样坏。第二个判据：议程排队时长是否已超过方案本身的实施时长。
- **为什么排在清单之后**：委员会的产出（标准、雷达、例外规则）要靠清单的判定口径才能在团队间比对。清单未成文时，每个成员都用自己的经验判定，同一方案在不同会上会得到相反结论。

**Step 5：建立 ADR 闭环（1–2 周【经验】，随是否复用已有文档库而变）**

- 四选一决议各有去向：接受 → ADR 归档（Status 置 Accepted）；修订 → Author 修改 → 重新评审；拒绝 → 不实施但仍归档并写清被否理由；推迟 → 挂起并写明重新评估的触发条件（时点或事件）。另有一条后置动作不属于决议本身：新决策取代旧 ADR 时，把旧条目标记 Superseded 并指向新条目——它是 Status 的状态迁移，不要把它当成第五种决议。
- 模板与生命周期细则见 [§01 ADR](../01-adr/01-adr-section-3-sec3.md)。

- **产物**：可检索的 ADR 目录 + 状态字段（Proposed / Accepted / Superseded）。
- **判据**：任取一条 ADR，看能否读出三件事：当时的约束、被否的候选、什么条件下应重新评估。缺任一，这份记录就成了误导材料——后来者会重新评估当年已被否掉的方案。再查最近一次 Supersede 有没有把旧条目状态改掉。
- **为什么必须紧跟决议**：决议的记忆半衰期以周计。当天不归档，两周后写出来的「当时为什么这么定」已经是重构过的叙事，不再是记录。

**Step 6：建立 Follow-up 机制（1 周【经验】，随任务系统现状而变）**

- 每条 Follow-up Action 带 Owner 与截止日期，进任务系统，而不是只留在纪要里；季度复盘统计闭环率。
- 明确逾期项怎么处理：回灌到下次议程，而不是自动消失。

- **产物**：任务系统里一条按评审编号聚合的查询 + 每季度一张闭环率曲线。
- **判据**：随机抽 2 条行动项，看它有没有 Owner、有没有截止日期、逾期后有没有升级动作。三项缺任一项，这套机制只是把承诺换了个地方存放。
- **为什么排在 ADR 之后**：归档解决「记下来」，行动项解决「做下去」。顺序反了会出现「任务完成了但没有对应 ADR」的断层，复盘时对不上账。

**Step 7：建立 AI 辅助评审（2–4 周【经验】，随模型接入方式与清单长度而变）**

- 让模型对每个 Checklist 项出初判（通过 / 疑似风险 / 不适用），并附证据：命中文件、行号、规则名；反模式识别的输出是候选清单而不是结论。
- 人的部分只做两件事：处理「疑似风险」与「无证据」的项，签署决议。AI 结论不单独构成放行依据。

- **产物**：一份带证据字段的模型输出 + 一份 AI 初判与人类结论并列的存档。
- **判据**：抽 10 条 AI 初判，统计附了可定点核查证据的比例。低于一半，说明它给的是意见不是线索，人的复核成本会高于自己逐项看。第二个判据：评审通过率是否比引入前异常升高、且无人能解释理由。
- **为什么必须排在清单之后**：模型的输入是清单项。清单未成文时模型只能自由发挥，产出的「风险清单」既不可复核也不可累计。

**Step 8：建立持续评审（持续进行，随在线系统数与上线频率而变）**

- 把四类评审挂到生命周期节点上：PR 级 **Lightweight Review**、上线 **Go-Live Review**、季度 **Architecture Board**、年度 **Strategic Review**；每个节点写清进入条件、产物，以及「上一节点未通过则不允许进入下一节点」。
- 给节点数设上限：节点数 × 单节点准备工时一旦超过团队每周可支配的评审时间，砍节点，而不是加人。

- **产物**：一张生命周期节点图，每个节点标注进入条件与产物。
- **判据**：算一次「节点数 × 单节点准备工时」是否超过团队每周可支配评审时间。超过即必然退化为签字，此时增加的不是把关而是工作量。第二个判据：最近一次事故能否回溯到某个节点的漏项——回溯不到，说明节点只是流程装饰。
- **为什么必须最后一步**：持续评审是把前七步的产物挂到时间轴上。前七步没做实，挂上去的只是四个空节点。

八步里最常被跳过的是 **Step 1 与 Step 6**。Step 1 被跳过的第一个症状不发生在评审会上，而是发生在队列里：三个月后你会发现上会的尽是低频小变更，而两个真正的跨团队契约变更已经悄悄上线。Step 6 被跳过时症状出现在下一次评审：同一类议题被讨论两遍，第一遍的结论没人执行，第二遍的结论与第一遍不同，团队从此不再认真对待决议。

### 4.2 关键技术点

**RFC / Design Doc 模板**

- **做法**：固定字段——背景与约束、候选方案 ≥2（含被否方案与理由）、影响面（下游 / 成本 / 风险 / 回滚）、验收判据。
- **机制**：因为评审者能在会前定向读到「分歧在哪」而不只是「方案是什么」，所以会议时间花在判定上；代价是作者必须提前把没想清的部分写成文字，起草成本高于口头汇报。
- **失效条件**：**当模板字段数超过作者能在会前填满的量时**（典型是十几个段落字段），这条会退化成填空练习——表现为大量字段写着「见方案第一章」或「不适用」，评审者反而要花时间在文档里找信息。症状：会前阅读时长上升，而会上提出的实质意见数不变。
- **档位**：一份可评审的 RFC 起草成本常在 1 人日以上【经验】，随文档长度与是否含数据支撑而变。

**ADR 模板**

- **做法**：Context / Options / Decision / Consequences / Status 五段，Status 走 Proposed → Accepted → Superseded。
- **机制**：因为记录与代码同仓、随代码一起被审阅，所以「当时的约束」会与实现一同演化；代价是轻量记录只留结论与理由，不留完整分析过程。
- **失效条件**：**当 ADR 只写「决定了什么」而不写「否掉了什么、为什么」时**，这条反转成误导后人——后来者重复评估当年已被否掉的方案，甚至不知道它已被否过。症状：同一条 ADR 被反复当作新增决策的依据。
- **档位**：该形式由 Michael Nygard 2011 年提出【公开：Michael Nygard, "Documenting Architecture Decisions", 2011，可按标题检索核验；模板细则见 [§01 ADR](../01-adr/01-adr-section-3-sec3.md)】。

**评审 Checklist 模板**

- **做法**：按 Quality Attributes / 业务约束 / 反模式三组分节，每项写成能被否证的问句，结论三选一，清单进版本库。
- **机制**：因为判定标准写在文档里而不是留在个人经验里，所以同一方案在不同评审者手里能得到可比较的结论；代价是清单需要长期维护，而维护工作没有直接产出。
- **失效条件**：**当清单长度超过单次评审的注意力预算时**，这条退化成打勾——空白项比例上升，或一律通过。症状：覆盖率统计好看，而事故从清单之外的地方长出来。判据是空白率，不是填报率。
- **档位**：空白超过两成即应拆分【经验】，阈值随议题复杂度与会议时长变化。

**评审会议管理**

- **做法**：会前下发材料与议程；会上只对争议项逐条表决，无争议项跳过；会后当日出纪要（决议 + 行动项 + 具名 Approver）。**档位**：一次正式评审常见占住 5–8 名资深人员约 2 小时【经验】，随议题数与资质分布浮动。
- **机制**：因为只有真有争议的部分被带进会场，所以单位会议时间的判定量上升；代价是会议容量成为组织变更吞吐的上限。
- **失效条件**：**当材料下发到开会之间的间隔短于 3 个工作日时**【经验】，这条会失效——评审者当场首次看到材料，唯一的理性选择就是同意。症状：会议时长随方案复杂度上升而下降，复杂方案讲得比简单方案还短。

**评审工具（GitHub / GitLab PR、Atlassian Confluence、Notion）**

- **做法**：轻量评审用 PR / MR 承载，评论挂在具体 diff 行上；正式评审用 Confluence 或 Notion 承载文档与版本。**档位**：本条无需数字档位，判据是「意见能不能定位到具体位置」。
- **机制**：因为意见挂在具体位置上，讨论会后可定位、可追溯；代价是异步意见散成行内评论，结论不自动沉淀。
- **失效条件**：**当评审跨越多个团队时**，PR 通道会失效——评审的最小单位是 diff，而 diff 里看不到调用方语义。症状：跨团队事故回看时，PR 上每条评论都合理，但没有一条提到被破坏的调用方。

**评审日历**

- **做法**：给四类评审各排固定节拍（PR 随提随评、Go-Live 随上线、季度会与年度会预排），写进团队日历而不是临时约。**档位**：季度会与年度会按季度、年度预排【经验】，节奏可按自身交付节拍调整。
- **机制**：因为节拍固定，准备材料的时间被提前摊到日历上，不会全部压在会前；代价是低活动期会出现空转。
- **失效条件**：**当固定节拍被「有事才开」取代时**，这条失效——临时会必然准备不足，准备不足的会必然走过场。症状：会议改期率上升，材料下发时间变短。

**评审 Dashboard**

- **做法**：只放四个数——评审数量、决议分布（接受 / 修订 / 拒绝 / 推迟）、Follow-up 闭环率、例外记录数。**档位**：本条无需数字档位，建议同时看「例外记录数是否非零」。
- **机制**：因为决议分布与例外数暴露的是把关强度而不是活动量，所以管理层看到的是「拦住了什么」；代价是这四个数都需要流程里有结构化记录才拿得到，得先有记录才有看板。
- **失效条件**：**当看板只统计评审数量时**，这条反转成反向激励——数量上升而决议分布不变（全是接受）。症状：通过率长期接近 100%，且事故仍然发生。

**AI 辅助评审工具（GitHub Copilot PR Review、Claude Code Review）**

- **做法**：把 AI 初判限制在清单项与反模式识别两处，输出必须附证据，结论与人类判定并列存档。
- **机制**：因为人的注意力从「逐项检查」转移到「核查异常项」，所以单位评审时间覆盖的清单项数上升；代价是误报要人工消化，误报率高时反而比全人工更慢。
- **失效条件**：**当把 AI 初判当结论（自动通过）时**，这条反转成漏检放大——模型的漏检是静默的，它不报错、只是没提，而流程已经把人从逐项检查上撤走了。症状：评审通过率异常升高且无人能解释理由。
- **档位**：产品能力与版本以各自官方文档当前版本为准；「AI 结论不单独构成放行依据」这条不依赖具体产品。

**评审 Checklist 自动化**

- **做法**：让工具检查清单的**完整性**——每项是否都有结论、是否附了证据——而不是代替人给判定。**档位**：本条无需数字档位。
- **机制**：因为空白项与无证据项可以被机械识别，所以「形式主义 Checklist」能在流程内被发现；代价是清单项必须结构化才可解析，自由文本清单无法自动检查。
- **失效条件**：**当自动化只检查「填了没有」而不检查「有没有证据」时**，这条失效——所有项被填成「通过」，空白率为零。症状：完整性 100%，抽查任一项都拿不出证据。

**评审历史**

- **做法**：所有评审记录（材料、意见、决议、行动项、后续事故）按同一编号体系归档，且与 ADR 编号互指。**档位**：本条无需数字档位。
- **机制**：因为历史可检索，所以「这类问题以前怎么定的」可以回答，评审的学习曲线才能累积；代价是归档需要编号体系与检索入口，纯按时间堆放会变成一堆难检索的文件。
- **失效条件**：**当记录只按时间堆放、没有主题或资产标签时**，这条失效——检索不到的历史等于没有历史。症状：同一议题在一年内被评审两次，且第二次结论与第一次冲突。

### 4.3 工具链与平台

工具在这一节只解决两件事：**承载评审材料**与**承载决议与行动项**。选型判据统一落在三个问题上——材料能不能进版本库、意见能不能定位到具体位置、决议能不能被查询与追踪。

| 类别 | 候选 | 选型判据（在什么约束下选哪个） | 不选它的代价 |
| --- | --- | --- | --- |
| RFC / Design Doc 平台 | GitHub / GitLab PR、Atlassian Confluence + Markdown、Notion Database、Google Docs、Backstage ADR Plugin（Spotify） | 要与代码同仓、要能 diff → PR；读者非工程师、要审批流 → Confluence / Notion；只要轻量起草 → Google Docs；已在用 Backstage 门户 → ADR Plugin | 关键约束是「能不能进版本库」：不能，文档就没有版本历史，也 diff 不出第 3 版改了什么，评审依据在会后无法复核 |
| 评审 Checklist 载体 | Atlassian Confluence Template、Notion Checklist Database、Excel / Google Sheets、GitHub Issue Template、AWS Well-Architected Tool | 要可检索与版本化 → Confluence / Notion；要零门槛先跑起来 → 表格；要与 PR 同步 → Issue Template；云架构要对标外置标准 → Well-Architected Tool | 用表格承载清单的代价是判定无法与具体变更绑定：「这条结论对应哪个 commit」答不出来 |
| 评审会议管理 | Jira + Architecture Theme、Asana / Linear、Slack / Teams Channel、Miro / FigJam | 要决策跟踪与例外台账 → Jira；要轻量任务流 → Asana / Linear；要实时沟通 → IM 频道；要会前看图 → 白板工具 | 只在 IM 里讨论的评审没有决议记录，三周后无法回答「当时定的是哪个」 |
| 评审 Dashboard | Grafana、Jira Dashboard、Atlassian Compass（发布年份与能力以官方说明为准）、Linear / Height | 要与内部数据源打通 → Grafana；要与任务系统同源 → Jira Dashboard / Linear；要看开发者体验与架构健康 → Compass | 看板与流程不同源时四个数要靠人工汇总，季度复盘会因为「数对不上」被跳过 |
| AI 辅助 | GitHub Copilot PR Review、Claude Code Review、CodiumAI / CodeRabbit、Sourcery、Anthropic Constitutional AI | PR 级初判 → 与代码托管同平台的工具；清单项初判与反模式识别 → 支持长上下文与结构化输出的工具；要把评审规则显式写成可引用的判定条件 → 「宪法 / 规则文件」类方法 | 误选的典型后果是把 AI 输出当结论：漏检静默发生，而流程已把人从逐项检查上撤走 |
| 架构治理标准 | AWS Well-Architected Tool、Azure Well-Architected Assessment、Google Cloud Architecture Framework | 云上系统要对标外置标准、且结论需跨团队可比 → 对应云厂商的框架；多云 → 先用一套做基线，再把差异列成补充项 | 自研清单的结论无法跨团队比较，也无法跨年度追踪同一条问题是否关闭 |

这一类里**最容易被误选的是「用 IM 频道承载评审」**：Slack / Teams 用起来零成本，讨论也确实发生过，但它不产生可查询的记录。后果不是评审没做，而是三个月后没人能证明做过什么、定了什么——而这恰好是架构评审唯一需要交付的东西：一份能被追问的决议。

### 4.4 存量迁移

存量组织的问题通常不是「没有评审」，而是**已经有一批系统在跑、开过很多次会、却没有一条可追溯的决议**。这一节给的是补齐顺序。

**① 先做一件立刻见效、且可回退的事（1–2 周【经验】）**

选**三个最贵的已上线决策**（改动会引发跨团队连锁，或已经出过事故的那三个），各补一条 ADR：只写 Context、Decision、被否候选、失效条件，不补完整论证。这一步可回退——写错了删掉即可，不动任何线上系统。判据：三条写完后，找一位当时在场的工程师读一遍，问他「这跟你记得的一样吗」。连续三条被判为基本一致，说明这个组织的决策记忆还在，可以继续往下补；若三条里两条被指出记错，先别扩大范围，改成「只记新决策 + 每次事故补一条回顾」。

**② 历史资产怎么分类处理**

把存量按三类分，而不是一律返工（下表的时间档位是常见取法【经验】，按你们的资产迭代节奏调整）：

| 类别 | 判据 | 处理方式 |
| --- | --- | --- |
| 还会变的核心资产 | 未来 12 个月内有明确的替换、扩缩容或口径变更计划 | 补 ADR + 补影响面清单；下一次变更前必须补齐 |
| 稳定运行、不再动 | 近 12 个月无结构变更、无跨团队依赖新增 | **不返工**，只打标：登记「未评估 / 已知未评审」+ 责任团队 |
| 已经出事或正在腐烂 | 出过事故、已被多次绕过、或已无人维护 | 进季度议题，按事故优先级排，不按资产规模排 |

判据：三类各占多少，用一次抽样（每类抽 10 个资产）估比例【经验，抽样量与比例阈值都随组织历史长度变化】。如果「已经出事」这一类超过三成，要做的不是补记录而是先做一次事故回溯——把事故时间线倒推到当时的决策，比凭空补文档便宜得多。

**③ 迁移期的双轨怎么维持、维持多久**

双轨的内容是：**新决策走新流程（RFC + 决议 + ADR），旧资产挂着「未评估」标签继续运行**。双轨期需要三样东西——一张**未评估资产清单**（带责任团队与登记日期）；一条**规则**：清单上的资产在下一次结构性变更前必须先补评估（把补记录挂在变更上，而不是挂在日历上）；一本**例外台账**：谁批准了「先改后补」，为什么。维持多久取决于变更速率：只要还有资产处在「会被改到但还没评估」的状态，双轨就得维持。判据：看**未评估清单的下降方向**，而不是看绝对值——清单在缩短、同时新登记仍在发生，说明机制在工作；清单长度不变而新增登记为零，说明登记动作已经停了。

**④ 什么信号说明可以退出双轨**

三个信号同时出现才可退出：**（a）** 最近一个季度的结构性变更里，先评后改的比例高于先改后补；**（b）** 未评估清单里「还会变的核心资产」这一类清零；**（c）** 例外台账里的条目能逐条说明原因，而不是同一原因反复出现。同一原因反复出现说明准入规则与现状不符，要改的是规则。退出双轨不是删掉清单，而是把登记动作从「一次性盘点」改成「随变更自动产生」：新资产在创建时登记，存量清单冻结为历史快照。

存量迁移里最常见的两个误判：一是**先补完历史再上新流程**——历史永远补不完，而团队会在补的过程中失去耐心，最后两件事都没做成；二是**把双轨当永久状态**——「旧资产不追溯」一旦变成惯例，新流程很快会被同一条理由绕过（「这个也算旧资产」）。两条误判的共同点，都是把顺序问题当成了工作量问题。

### 4.5 模板 / 示例

**示例 1：架构评审 Checklist（数据架构）**

```markdown
# 架构评审 Checklist：数据平台方案（v1.0）
- [ ] **功能性**｜业务需求覆盖度；数据模型是否建模正确（OneData / 维度 / KG）；ETL / ELT 是否可追溯
- [ ] **性能**｜QPS 预估；P99 延迟；峰值吞吐；数据倾斜风险
- [ ] **可用性**｜SLA 目标；单点故障（SPOF）；容灾（多活 / 双活）；降级 / 限流
- [ ] **安全**｜数据加密（传输 + 存储）；访问控制（RBAC / ABAC）；PII 脱敏；操作审计 + 链路追踪
- [ ] **可扩展性**｜水平扩展；弹性伸缩；3–5 年容量规划
- [ ] **可维护性**｜可观测性（监控 / 告警 / 日志）；可治理性（权限 / 审批 / 变更管理）；可演进性（未来 3–5 年路径）
- [ ] **成本**｜3–5 年 TCO；ROI；资源利用率（CPU / 内存 / 存储）
- [ ] **团队匹配度**｜团队能否维护；学习曲线；招聘可得性
- [ ] **合规**｜数据隐私（GDPR / 个保法 / 数据安全法）；行业合规（等保，以现行级别与版本为准）；AI 合规（AI 治理框架）
- [ ] **风险**｜技术风险（新技术）；供应商风险（锁定）；业务风险（中断）
## 反模式检查
- [ ] 无单点故障；无过度设计；无过度耦合；无硬编码；无未经评审的依赖
## Follow-up Actions
| # | 议题 | Owner | 截止日期 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 容量预估 | {owner} | {date} | 待开始 |
| 2 | 安全评审 | {owner} | {date} | 待开始 |
```

**怎么用**：十一行照留——它们覆盖的是评审的固定维度，删掉某一行等于把该类风险移出判定范围；需要逐项打勾的团队，把每行的「；」拆回独立 checkbox 即可（分组只是为了压到一页）。`3–5 年`、`等保` 这类取值是常见示例【经验】，用途是提示口径，不要照抄。Follow-up 表每行必须落到一个具体的人（不是团队名）与一个具体日期。

**示例 2：评审会议模板**

```markdown
# 评审会议：{方案名}
## 会议信息
- 时间：{日期 时段}｜主持人：{主持人}
- 评审人：{评审人列表}｜缺席：{缺席人 + 原因}
## 议程
1. 方案介绍（{n} 分钟，{提案人}）
2. 质量属性评审（{n} 分钟）：性能（{评审人}）/ 安全（{评审人}）/ 可扩展性（{评审人}）
3. 反模式检查（{n} 分钟）｜4. Pre-Mortem（{n} 分钟）｜5. 决议 + Follow-up（{n} 分钟）
## 评审记录
- 性能 — {评审人}：{意见} → 决议：{谁} 补充 {什么材料}
- 安全 — {评审人}：{意见} → 决议：{谁} 补充 {什么材料}
## Pre-Mortem
- 假设 6 个月后失败，Top 3 原因：{原因一} / {原因二} / {原因三}
## 决议
- 决议：**{接受 / 修订后接受 / 拒绝 / 推迟}**｜ADR：ADR-{编号}
## Follow-up Actions
| # | 议题 | Owner | 截止日期 |
| --- | --- | --- | --- |
| 1 | {议题} | {owner} | {date} |
```

**怎么用**：`{...}` 全部是待填项。三处不要照抄：议程的时间分配要按本次议题数改（上面给的是常见排法【经验】）；「6 个月后失败」的时间窗换成与方案生命周期匹配的窗口；Pre-Mortem 的三条原因必须由参与者**独立书写后再汇总**，由主持人口头收集会让第一条意见锚定全场。

**示例 3：ATAM 简化版（质量属性效用树）**

```text
目标：业务连续
├── 高可用：可用性 ≥ {目标}（示例 99.95%【经验】）
│          RTO ≤ {目标}（示例 30 分钟【经验】）｜RPO ≤ {目标}（示例 5 分钟【经验】）
├── 可扩展：支持 {N}x 流量（示例 10x【经验】）｜{N}x 数据量（示例 100x【经验】）
├── 安全：数据加密｜权限隔离｜审计追溯
└── 性能：P99 延迟 ≤ {目标}（示例 1s【经验】）｜QPS ≥ {目标}（示例 10,000【经验】）
```

**怎么用**：树的形状照用（目标 → 质量属性 → 场景 → 目标的四层是这套方法的固定结构），叶子上的数值全部由外部输入——RTO / RPO 与可用性来自业务连续性要求，扩展倍数来自容量规划，括号里的示例值不要照抄。若四层里缺了「场景」这一层（只写属性、不写刺激与响应），效用树会退化成一张愿望清单。

**示例 4：架构反模式清单**

| 反模式 | 描述 | 检测 |
| --- | --- | --- |
| 单点故障 | 关键组件无冗余 | FMEA + Chaos Engineering |
| 过度耦合 | 服务间强耦合 | 依赖图分析 |
| 大泥球 | 单一巨型服务 | 代码静态分析 |
| 烟囱系统 | 重复建设的独立系统 | 数据流分析 |
| 无监控 | 关键路径无监控 | 监控覆盖率 |
| 无降级 | 故障无降级方案 | Chaos 测试 |
| 无审计 | 操作无审计日志 | 安全审计 |
| 无版本管理 | 模型 / Prompt 无版本 | AI Tech Debt 检测 |

**怎么用**：把「检测」一列换成你们实际能跑的动作——这一列是这张表能不能用的分水岭，写着「依赖图分析」却没有依赖图工具时，该行等于不存在。反模式名照留。这八个是**技术类**反模式，与 [§3.5](07-architecture-review-section-3-sec3.md) 那张**流程类**反模式表（走过场 / 一言堂 / 标准不一 / 无决议 / 无人跟进……）不是同一套词，别拿着本表去 §3.5 对；同样这八行的表另见 [§8.2](07-architecture-review-section-8-sec8.md) Checklist 设计参考答案的「C. 反模式类（一票否决项）」。

**示例 5：AWS Well-Architected Review（6 根支柱）**

```text
Operational Excellence：监控 / 自动化 / 变更管理
Security：身份 / 认证 / 加密 / 审计
Reliability：容错 / 备份 / 恢复
```

**示例 6：AI 辅助架构评审（Python / Claude）**

```python
import os
import anthropic

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])
MODEL = "claude-opus-5-5"  # 模型 ID 以官方文档当前版本为准
PROMPT = """你是一名资深数据架构师，请按要求评审以下架构方案。
## 架构方案
{design_doc}
## 评审 Checklist
{checklist}
执行约束：① 每项给结论（通过 / 部分通过 / 不通过 / 不适用），结论必须附证据（命中位置或「无证据」）；
② 另给 Top 5 风险（概率 / 影响 / 缓解）与 Pre-Mortem（假设 6 个月后失败，Top 3 原因）；
③ 输出是建议而非决议——决议由人类 Approver 签署，两份结论并列存档。"""


def ai_review_architecture(design_doc: str, checklist: list[str]) -> str:
    prompt = PROMPT.format(
        design_doc=design_doc, checklist="\n".join(f"- [ ] {item}" for item in checklist)
    )
    msg = client.messages.create(
        model=MODEL,
        max_tokens=16000,          # 示例值【经验】，按方案长度与输出上限调整
        thinking={"type": "adaptive"},
        output_config={"effort": "high"},
        messages=[{"role": "user", "content": prompt}],
    )
    return "\n".join(b.text for b in msg.content if b.type == "text")


# 用法：design_doc 换成你们的方案正文；checklist 换成 §4.5 示例 1 的条目。
# 下面是「多模型路由迁移」这一场景的形态演示：
review = ai_review_architecture(
    design_doc=open("design.md").read(),
    checklist=["性能：路由增加的 P99 延迟是否可接受？", "成本：多模型是否真的降低总成本？",
               "安全：模型 API Key 如何管理？", "合规：国内业务是否合规？",
               "可扩展：能否接入新模型？", "可维护：团队是否能维护多模型？",
               "可观测：路由决策是否可观测？", "降级：单模型宕机是否降级？"],
)
print(review)
```

**怎么用**：`checklist` 请换成 §4.5 示例 1 里的条目，示例里那八问是「多模型路由迁移」场景的形态演示，按你们的场景重写。另有三处不要照抄：模型 ID 与 `thinking` / `output_config` 这类参数的可取值以官方文档当前版本为准；`max_tokens` 与是否改用流式按方案长度定；初判产出必须与人类结论并列存档，双结论是回看误报与漏报的唯一依据（见 §4.2「评审历史」）。

### 4.6 自检清单

- [ ] 抽 3 个最近上线的重大方案，能否各指出它的不可逆程度（回退要付什么代价）？指不出，说明 Step 1 未落地。
- [ ] 抽 3 份会议纪要，每份是否至少有一条会导致方案修改的意见？零条即为走过场。
- [ ] 抽 3 份纪要，决议是否落在四选一（接受 / 修订 / 拒绝 / 推迟）并有具名 Approver？写「继续推进」即无决议。
- [ ] 抽 3 条 Follow-up，是否同时带 Owner 与截止日期，且能在任务系统里查到？缺任一项即不算行动项。
- [ ] 材料在会前多久下发？间隔短于 3 个工作日的议题，应改到下次评审。
- [ ] 抽 1 条 ADR：能否读出当时的约束、被否的候选、失效条件三件事？缺任一即会误导后人。
- [ ] 抽 1 份 Checklist 记录，数空白项占比；超过两成即需拆分或缩短清单。
- [ ] 跨团队影响面是查出来的还是估出来的？估出来的必须在结论里标明置信度。
- [ ] 最近一次事故能否回溯到某次评审的漏项？回溯不到，说明评审与事故数据之间没有回路。
- [ ] 算一次「评审节点数 × 单节点准备工时」是否超过团队每周可支配的评审时间？超过即必然退化为签字。
- [ ] 若已引入 AI 初判：抽 10 条，附证据的比例是多少？无证据的初判不能作为通过理由。
- [ ] 例外台账最近一条记录是什么？长期为空，说明准入规则与实际不符，需要重定阈值。

### 4.7 小结

> 本节小结：整个落地过程里唯一决定成败的不是哪份清单做得更全，而是**评审有没有被钉在交付路径上**——它由 §4.1 的两步合起来实现：**Step 1** 划出「哪些决策必须评」的准入边界，**Step 8** 把这些决策挂到生命周期节点上并规定「上一节点未通过则不允许进入下一节点」。因为它决定的是评审**会不会被执行**，而其余环节只决定执行得好不好：准入边界没收窄，队列就由「谁喊得响」决定，第一次绕道之后后面几步再补也换不回约束力；没有 Step 8 的节点门禁，前七步的产物只是四个空节点。所以最值得投入的不是把模板做全，而是把「哪些决策必须评」与「评完的结论卡在哪个节点上」这两件事钉死。
>
> 💡 **思考锚点**：按 §4.6 最后两条给你们的评审负载算一次——「评审节点数 × 单节点准备工时」是否已经超过团队每周可支配的评审时间、例外台账最近一条记录是什么？若已经超过，说明评审正在退化为签字，你打算把 Step 1 的准入边界从哪一类决策开始收窄？
