# 故障复盘（Postmortem）

> **核心定位**：讲一个你主导过的**最严重的故障** + 你怎么复盘 + 行动项 —— 考察「系统性思考」与「不甩锅的能力」。

## 答题框架（Blameless + 系统性）

1. **题目选材**：
   - **必须真实**（面试官会追问细节）—— 来自你自己的项目经历
   - 严重程度：影响业务 / 数据正确性 / SLO 违反 / 资金 / 合规
   - 时长：30-60 分钟（不能太短，不够真实；不能太长，不是系统问题）
2. **考察点**：面试官在考「**系统性思考 + 不甩锅 + 持续改进**」三件套。
3. **参考答案框架**（**6 段结构**）：
   - **背景（2 行）**：什么系统、什么时间、什么业务
   - **故障现象（3 行）**：用户/监控看到了什么——用数字（QPS 跌 50% / 数据延迟 2h）
   - **根因（5 行，按 5 Why 深挖）**：不停在表面原因，挖到系统/流程/架构层
   - **止血（3 行）**：当时怎么应急的（限流 / 切流 / 回滚 / 人工补偿）
   - **根治（5 行）**：长期怎么改（代码 / 架构 / 流程 / 监控 / 演练）
   - **反思（3 行）**：从这次学到什么（个人 / 团队 / 组织）
4. **常见陷阱**：
   - ❌ 甩锅给「某个同事写错代码」—— blameless 文化的反面
   - ❌ 只讲「现象」不讲「根因」
   - ❌ 没有量化（只说「很大影响」不说「影响 100 万 GMV」）
   - ❌ 没有「反思」环节
   - ❌ 编造细节（面试官一追问就露馅）
5. **追问预测**：
   - 「如果再做一次，你会怎么改？」
   - 「你的行动项，跟进了吗？效果如何？」
   - 「类似故障还会发生吗？怎么防止？」

## 优秀故障案例的 5 个特征

- **可量化**：影响范围（用户数 / 金额 / 时长）
- **可教学**：根因能映射到「系统设计原则」或「常见反模式」
- **可改进**：行动项明确、可执行、有 deadline
- **可类比**：面试官能从你的案例学到东西
- **真实**：细节经得起追问（具体日志、具体数字、具体决策）

## 推荐的 5 类「高频题源」准备

| 故障类型 | 推荐准备方向 | 案例来源 |
| --- | --- | --- |
| **数据延迟**（离线任务跑慢） | Spark 倾斜 / 小文件 / 调度失败 | 几乎每个数仓团队都遇到过 |
| **数据正确性**（指标错了） | 口径不一致 / SCD 错配 / 上下游时区错位 | 阿里 / 字节 / 美团 / 京东都公开过 |
| **服务可用性**（查询超时） | OLAP 引擎资源耗尽 / 大 Key / 慢 SQL | Netflix / 美团 ClickHouse 慢查询 |
| **AI 系统**（RAG 答非所问） | Embedding 漂移 / 检索漏召 / Prompt 错位 | 字节豆包 / 阿里通义 / Anthropic Claude |
| **变更事故**（上线挂了） | Schema 不兼容 / 灰度配置错 / 回滚失败 | 几乎所有大厂都公开过 |

## 工业案例（推荐主动引用）

- **Netflix 2017-2018 容量事故**（Chaos Engineering 起源）
- **Cloudflare 2019 宕机**（RPKI 路由配置变更）
- **GitLab 2017 数据库误删**（事后写完整 postmortem）
- **AWS S3 2017 一次宕机**（运维误操作 + 监控盲区）
- **阿里双 11 历次 P0 故障**（每年公开复盘）
- **字节春晚红包 20 亿 QPS**（极限保活 / 降级 / 切流）
- **美团外卖大促**（峰值 260 万单 / 分钟）
- **招行 / 微众 / 平安** 金融级容灾演练
