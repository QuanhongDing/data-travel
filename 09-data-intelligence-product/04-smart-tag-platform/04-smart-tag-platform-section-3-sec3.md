## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

标签平台的形态由**五条约束**决定，顺序不能颠倒：

1. **实体体系是否统一**：用户 / 商品 / 内容是否已有稳定的唯一标识（OneID）？**没有它，标签会按来源分裂成几套**——而这一步属于建模侧（[Ch1 §09 OneID](../../01-modeling/09-one-id/09-one-id.md)），一旦缺失，标签平台无论怎么做都会在实体层开始错。
2. **标签是否需要"解释与申诉"**：标签会影响人的待遇吗（额度、准入、优惠）？**是，则口径必须可执行、依据必须可回溯、必须有申诉通道**——这三件决定了平台必须建"口径层"，而不是"一堆 SQL"。
3. **时效要求**：业务要 T+1 还是 T+0？**这一条决定生产层是批、是流，还是两条都要**（两条都要时，一致性成为硬要求）。
4. **消费方式**：给人看（报表 / 圈选）、给系统用（在线点查 / 批量下发），还是两者都有？**给系统用时，标签服务进入关键路径，"可用性"变成第一约束**。
5. **标签规模与治理人力**：标签数会到几百还是几万？**有没有人能维护口径、准入与退役？**（**没有这个人，标签会在一年内膨胀到没人知道哪些还能用**——这是本主题最现实的约束。）

> **判据的用法**：先用 1 决定"实体层能不能开始"；用 2 决定"要不要建口径层"（这一条决定它是平台还是脚本集合）；用 3、4 决定生产与服务的形态；用 5 决定治理的强度。**跳过第 5 条最常见的后果**：标签数上到四位数以后，没有任何人能回答"哪些标签还在用、哪些口径已经过期"，而**过期的标签不会自己失效，它会继续产出看起来合理的值**。

**每条约束的"过关"是可核查的**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 实体统一 | 抽 100 个实体，问"它在你系统里有几个 ID、能不能归并"——归并率是已知数 |
| 2 可解释可申诉 | 随机抽一个标签，能在三分钟内讲清它的口径、依据与申诉路径 |
| 3 时效 | 每个标签都声明了 `event_time` 语义（快照还是最新）与新鲜度分位数 |
| 4 消费方式 | 在线消费的标签有 SLA；关键路径上的标签有降级预案 |
| 5 治理人力 | 口径、准入、退役三项各有 Owner 与评审周期 |

第 2 条是本主题与"特征平台"的分水岭：**它把"标签"从技术资产变成业务资产**。而它的判定很实际——**"三分钟内讲清口径"这件事，如果讲不清，说明口径没有被形式化，只是在一段 SQL 里。**

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 事实标签（可复算、可分档）

**被什么约束逼出来**：需要"可向本人解释"的判定（约束 2），而事实是可核验的。

**结构**：口径表达式（聚合 + 过滤 + 时间窗）→ 批产出到实体级标签表 → 服务层暴露点查与批量。

**为什么这样设计有效**：因为**事实标签的判定链只有"事实 → 分档"一跳**，而这一跳的分界可以由业务确认（"近 30 天登录 ≥ 10 次算活跃"）。由此得到两条实际收益：① **可申诉**——业务规则是可复述的（"你登录了 12 次，标准是 10 次"）；② **可复算**——同一 `τ` 重算永远得到同一个值，因此在争议场景里可以复现。**它的有效性来自"分档边界是人为确认的"这一点**，而不是"数据准"。

**代价**：① **空值与零的语义必须显式**（§2.3 的边界①）——不定义就会在下游出现"没用过"与"用了 0 次"混为一谈；② **迟到数据**（边界②）——分区封板后到达的数据要么被丢弃、要么触发重算，**两种都要写明**；③ **分档边界会随业务漂移**——边界改了，历史标签的含义就变了（因此分档边界要版本化，进口径）。

**失效点**：**把"分档"藏在代码里而不是口径里**——后果是同一个标签在两个实现里用了不同的边界（离线 10 次、实时 12 次），而**不一致集中在边界用户上**（§2.2 的 `u` 算式），业务恰好看的就是这些人。

**判定方法**：把这个标签的口径用一句话复述给一个没参与的人（聚合 + 过滤 + 时间窗 + 分档边界），看他复述出来的判据与表里的值是否对得上；再在明细表里手算三个实体的值，与标签表逐个比对。落点是 §4.9 的第 2、4 项（口径卡在不在、加标签要改几行代码）。

**真实使用**：§6.1 的阿里一例给的是这一模式最完整的形态——把事实标签的口径从宽表列抽成配置，加标签从"改 ETL"变成"加配置"；§4.5 模板 1 的口径卡就是它的载体（"分档边界（业务确认）"那一格正是本模式的分界线）。**"按配置产出"这一侧在书内已有具名工具可对照**：本主题 §4.3 工具链表把"批产出"一行落在"数仓调度 + SQL"，而 `03-data-stack/12-scheduler` 的 §4.3 工具链表把 Apache Airflow / Prefect / Dagster 列在"代码定义的通用编排"一行、把 Apache DolphinScheduler / 阿里云 DataWorks 列在"可视化 / 声明式编排"一行——它们正是这一模式里"配置驱动产出"的那一类。**但"分档边界由业务确认"这一条没有对应的产品物**：判定入口是 §4.5 模板 1 里那一格有没有被业务填过，而不是任何工具的功能清单。【公开】（来源：`03-data-stack/12-scheduler/12-scheduler-section-4-sec4.md` §4.3 工具链表；本主题 §6.1、§4.3 与 §4.5 模板 1）

#### 3.2.2 模型标签（带版本、带置信度）

**被什么约束逼出来**：需要判定"当前状态"（价格敏感度、内容偏好、活跃分层），而这类状态**没有可复述的规则**。

**结构**：特征 → 模型推理 → **分档** → 落标签表（**带模型版本与置信度**）。

**为什么这样设计有效**：因为**它把"不可复述的判定"变成了"可追溯的判定"**——虽然无法用一句规则解释"这位用户为什么是价格敏感型"，但可以回答三个可核验的问题：**用了哪个模型版本、置信度多少、输入特征的上游是什么**。**这三问就是模型标签"可解释性"的工程形态**——它不是可复述，而是**可追溯**。

**代价**：① **模型版本必须进血缘**——否则模型升级后标签含义变化，而无从归因（同 [Ch1 §11 模型管理](../../01-modeling/11-model-management/11-model-management.md) 的版本治理）；② **置信度必须保留**——下游决策常常需要"低置信度时不自动执行"，丢掉置信度等于强迫下游按二值处理；③ **分档边界是业务决定**（0.6 算不算高价值），不是模型决定的。

**失效点**：**把模型分数直接当标签值**——业务会在报表里看到 `0.73` 并自行解读为"73% 高价值"，而实际上分数是**模型的序**（排序用），不是概率。**判据**：标签的取值域是否被业务确认过（枚举分档），还是把模型的原始分数直接暴露给业务。

**判定方法**：取一个模型标签，问三个问题——模型版本是哪个、置信度是多少、输入特征的上游是哪张表；再问"分档边界是谁定的"。三问里有任何一问答不出，就是这个模式少了配套。三问的答案都要能落进口径卡：前两问对应 §4.9 的第 7 项，第三问对应第 3 项。

**真实使用**：§2.3 ② 把这一模式的配套写成三样（模型版本、置信度、业务确认的分档边界），§4.5 模板 1 的口径卡只给"分档边界（业务确认）"留了格——**模型版本与置信度目前只在 §4.9 的第 7 项里被检查、没有落格**，这是模板本身的一处缺口。**"特征输入"这一侧在书内已有具名物可对照**：`02-data-science/01-feature-store` 的 §4.1 Step 3 定下四层边界（离线层 Iceberg / Hive / Delta Lake、在线层 Redis / DynamoDB、物化层 Flink / Spark Streaming、服务层），§4.3 工具链表则把"离线 / 湖仓存储""在线存储""流处理"分列三行——模型标签吃的正是这一层的 Point-in-Time 特征。**两者的差别不在数据源，而在治理项**：本主题 §7.2 的候选表在"特征平台改造"一行写明这一点——「治理语义不匹配——特征不需要准入等级与申诉，标签需要」；这也正是本节把模型标签单列一条的理由。【公开】（来源：`02-data-science/01-feature-store/01-feature-store-section-4-sec4.md` §4.1 Step 3 与 §4.3 工具链表；本主题 §2.3 ②、§4.5 模板 1、§4.9 第 7 项与 §7.2）

#### 3.2.3 预测标签（钉住预测时点）

**被什么约束逼出来**：业务问"未来会不会"（流失、复购、违约），而**这个问题的答案依赖"在哪个时点问"**。

**结构**：观察窗口 + 表现窗口 + **预测时点**（§2.3 的图）→ 模型 → 概率 → 分档 → 落标签表（**带预测时点**）。

**为什么这样设计有效**：因为**它把"预测"这件事的隐含参数显式化了**——业务说的"流失概率"其实隐含了"在什么时候、看多长的窗口"；把这两个窗口与预测时点写进口径，**才使得这个标签可以被复现、被对账、被申诉**。**这条显式化还带来一个工程收益**：模型效果的评估需要"预测时点 + 表现窗口结束"两个时间都过去，**没有显式的预测时点，就无法组织回测**。

**代价**：① **预测时点必须随标签存储**——否则同一个标签在不同时间取到不同值（§2.2 的语义 A / B），而业务会把它当事实读；② **表现窗口的长度与事件的稀疏程度决定模型可用性**——稀疏事件（违约）需要长窗口，而长窗口意味着标签更新慢；③ **概率到分档的切分影响下游动作量**——分档越松，营销触达越多（成本上升）、分档越紧则召回不足。

**失效点**：**只存"最新一次预测结果"而不存预测时点**——后果是"上个月这个人的流失概率是多少"答不出来，而**这类问题在复盘与申诉时必然被问到**。**判据**：标签表里有没有 `prediction_point` 这一列。

**判定方法**：翻一次标签表的结构（或口径卡的填写项），找 `prediction_point` 或等价字段；再报一个三个月前的日期，问"当时这个人的分档是多少"。第一个动作是读表结构，第二个动作答不出就说明预测时点没有落库。两个动作分别对应 §4.9 的第 8 项与 §3.7 的第 8 项。

**真实使用**：§2.3 ③ 把观察窗口 / 表现窗口 / 预测时点画成一段结构，§4.9 的第 8 项直接问"存 `prediction_point` 吗"。**这一项目前只在自检里出现、没有落格**——§4.5 模板 1 的十二个格位里没有它，"时间语义"格写的是 `snapshot（按 dt 取）` 与新鲜度 SLA；这是模板的一处缺口，不是本节漏引。**"钉住时点"在书内已有可对照的具名机制**：`02-data-science/01-feature-store` 的 §4.2 用 `event_time` 与取数约束（只能用标签时点之前可观测的值）保证 Point-in-Time 正确——预测标签的 `prediction_point` 是同一件事的另一侧：特征侧管"只能用当时能看到的数据"，标签侧管"当时判的是什么"。**这一条本节不点名任何产品的字段名**——预测时点是口径层自己的定义项。【公开】（来源：`02-data-science/01-feature-store/01-feature-store-section-4-sec4.md` §4.2 关键技术点的 PIT 取数约束；本主题 §2.3 ③、§4.5 模板 1 与 §4.9 第 8 项）

#### 3.2.4 离线 / 在线同源（一份口径，两条产线）

**被什么约束逼出来**：同一业务既要 T+1（日常运营）又要 T+0（实时风控 / 推荐），而**两份实现必然漂移**（约束 3 + 约束 2）。

**结构**：口径写成**可被两种引擎执行的形态**（DSL 或兼容的 SQL），离线用批引擎执行、在线用流引擎执行；一致性靠**逐个实体的对账**保证（§2.2 的 `u`）。

**为什么这样设计有效**：因为**漂移的根源不是"人写错了"，而是"判定存在两份实现"**——只要有两份实现，它们就会在边界条件上分叉（时间边界、空值、迟到数据），而分叉集中在业务最关注的边界用户上。**同源的机制价值在于把"两份实现"压缩成"一份定义"**：口径只有一份，差异只能来自执行引擎，而那类差异是**可枚举、可测试**的。

**代价**：① **需要一个能被两种引擎执行的表达**——这通常意味着引入 DSL 或限制 SQL 子集（表达力与一致性之间的取舍）；② **流侧的状态与迟到处理更难**（乱序、重放、状态大小）；③ **对账本身要作为常设任务**（不是一次性验证）——**它的成本约"抽 N 个实体逐个比对"，是半天级的动作**。

**失效点**：**只对总量不对个体**——"离线 10 万人、实时 10 万人"看起来一致，而名单可能差两万（§2.2 已说明）。**判据**：对账方式必须是"取同一批实体的两个值逐个比"，而不是"比人数"。

**判定方法**：把 §4.5 模板 3 的那段 SQL 改两个表名跑一次——取同一批实体、同一个 `τ`，看它返回几行（判据是 0 行）；再问一句"这个标签的实时实现，是从哪一份口径生成的"。两个动作合起来就是 §6.2 具体数字里那件"投入产出比最高的检查"。

**真实使用**：§6.2 的字节一例（属 §6 开头的材料纪律所说的"建设方自述"，不构成第三方生产案例）给的是这一模式在书内唯一的具名形态——实时与离线口径同源、**逐实体对账作为上线门禁**；§4.2（2）给出它的代价（必须限制表达力）与"仅 T+1"的显式声明，§4.5 模板 3 给出改两个表名就能用的对账 SQL。**两侧引擎的候选与判据在书内可指**：流引擎这一族见 `03-data-stack/09-realtime-compute` 的 §4.3 工具链表（"流处理引擎"一行，给的是运维维度），机制层选型见同节 §4.1 Step 1，本节不重复。**本模式相对它新增的只有一条**：同源把**两侧引擎表达力的交集**当成口径的上界（§4.2（2）），于是"这个标签能不能实时"由交集决定、而不是由任一引擎的能力决定——这才是"仅 T+1"必须显式声明的原因，也是本模式在流侧真正的困难所在（表达力受双引擎限制、状态与迟到处理更难）。【公开】（来源：`03-data-stack/09-realtime-compute/09-realtime-compute-section-4-sec4.md` §4.3 工具链表与 §4.1 Step 1；本主题 §6.2、§4.2（2）与 §4.5 模板 3）

#### 3.2.5 标签服务（点查 + 批量，且进入关键路径）

**被什么约束逼出来**：标签要给**系统**用（风控、推荐、触达），因此它在关键路径上（约束 4）。

**结构**：**点查**（按实体键取若干标签，毫秒级，带缓存与降级）＋ **批量**（按标签条件圈选实体集，秒到分钟级）＋ **写入**（标签产出侧的批量写）。

**为什么这样设计有效**：因为**两类查询的规模特征完全不同**——点查是"小实体集 × 多标签"（按主键，可用缓存），批量是"大实体集 × 少标签"（按标签值，需要索引与执行计划）。**分开设计让各自取最优**：点查优化命中率与降级，批量优化扫描与计划选择。**若把它们合成一个接口，必然有一侧取不到最优**——通常是批量侧（被点查的延迟预算绑架）。

**代价**：① **缓存与一致性**——点查的缓存要能感知"标签已更新"，否则会返回过期值（**判据**：标签更新后，最坏多久点查能看到新值）；② **可用性**——在线标签服务挂了，风控 / 推荐必须**失败降级**而不是阻塞（**降级策略要事先定义**：用旧值、用默认值、还是放行）；③ **批量查询的执行计划**要按选择率选（§2.3 的判据）。

**失效点**：**把标签服务当成"数据库的 HTTP 封装"**——没有缓存、没有降级、没有超时；结果是数据侧一次抖动直接变成业务侧的事故。**判据**：标签服务的超时与降级策略写下来了吗？关键路径上的消费方知道标签不可用时该怎么做吗？

**判定方法**：在 §4.5 模板 2 上做完三件——① 问它"超时与降级策略写下来了吗"；② 拿一个确定无值的实体试 `getTags`，看它区分"不符合"与"无值"吗；③ 问"口径变更后，点查最坏多久返回新值"。三件的答案分别落在 §4.5 模板 2 的 `on_timeout` 一行、返回三元组的「无值」态、与 `caliber_version` 上。

**真实使用**：§4.2（3）把点查 / 批量 / 写入三件写成可检查的结构（缓存键含口径版本、先写新版再切指针），§4.5 模板 2 给出消费方要读的那一段（`on_missing` / `on_timeout` 与返回三元组），§4.7 的容灾表把"真关一次标签服务，看各消费方行为是否符合声明"写成演练动作。**"低延迟点查"这一侧的存储选型见 Ch2 §01 的 §4.3 工具链表（"在线存储"一行），本节不重复它的判据**；本主题相对它新增的只有一条——**点查的缓存键必须含口径版本**（§4.2（3）），因为"值变了但缓存没失效"是这一类存储本身不会报的错。**本主题不点名任何一款标签服务产品**：§7.2 只把"商业 CDP / 标签平台"作为一族列出而不具名，判定入口因此只能是 §4.5 模板 2 与 §4.7 的"标签服务不可用"演练行。【公开】（来源：`02-data-science/01-feature-store/01-feature-store-section-4-sec4.md` §4.3 工具链表；本主题 §4.2（3）、§4.5 模板 2 与 §4.7）

#### 3.2.6 准入等级（试运行 / 可信 / 已退役）

**被什么约束逼出来**：标签会进入**生产决策路径**（约束 2），而新标签与刚改口径的标签**不可信**。

**结构**：每个标签一个等级；**只有"可信"级可被生产决策消费**；进入可信需满足一组可核查条件（覆盖率、一致性、新鲜度、抽检准确率达标 + 业务确认）。

**为什么这样设计有效**：因为**它把"标签可信"这件事从"默认成立"改成"必须被证明"**——这是标签治理与"宽表加一列"最大的形式差异。由此得到两条实际效果：① **试运行标签可以被安全地观察**（业务能看，但不会自动执行）；② **口径变更可以被管理**——一个"可信"标签改了口径，**它应当自动退回"试运行"**（因为新口径未被验证）。**第二条是这套等级真正的价值**：它让"改口径"这件事有代价，从而抑制随手改。

**代价**：① **等级判定要有人做**（业务确认不可自动化）；② **等级会成为协作摩擦**——业务想尽快用，平台说还没到可信；**缓解办法是把准入条件公示**（让"还差什么"变成可见的），而不是靠人解释；③ **等级要定期复核**（业务变了，原来的判定可能不再合理）。

**失效点**：**等级存在但生产路径不检查它**——业务直接读标签表（绕过服务），于是"试运行"标签照样进了决策。**判据**：生产决策的读取路径是走标签服务，还是直连标签表？后者等于等级没有生效。

**判定方法**：拿一个试运行等级的标签，试着从**生产决策的读取路径**去取它——取得到，就说明等级没有生效（§4.1 Step 6 的判据是"试运行标签无法从生产路径读到"）；再改一次某个标签的口径，看它在同一次操作里有没有退回试运行。第一个动作查服务层的可见性，第二个动作查 §4.2（4）的四件联动是否真的在同一次操作里发生。

**真实使用**：§6.4 的"某银行"一例（匿名案例，见该节来源声明）给的是这一模式最完整的形态——只有"可信"级进信贷决策、**口径变更自动退回试运行**、申诉按字段而不是按流程回答；§4.2（4）把变更传播写成四件联动（版本递增 / 等级退回 / 缓存失效 / 通知），§4.7 的容灾表把"口径被误改"列为本主题唯一会大面积改变结果的失效形态。**"等级挂在资产上、并由生产路径检查"这一形态在书内有一处可对照的具名物**：`11-cross-cutting/05-lineage-and-impact` 的 §4.3 工具链表把 Apache Atlas 记为"Hadoop 生态元数据、强分类分级"——分类分级与准入等级都是挂在资产上、都要能被生产路径检查的登记项。**但本模式真正独有的那一半，Atlas 那类元数据平台没有对应功能**：**口径变更自动退回试运行**（§4.2（4）的四件联动）是标签这一层才有的约束，判定入口只能是 §4.7 的"口径被误改"演练行与 §4.9 的第 9 项。【公开】（来源：`11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-4-sec4.md` §4.3 工具链表；本主题 §6.4、§4.2（4）、§4.7 与 §4.9 第 9 项）

#### 3.2.7 退役与影响分析（标签会腐化）

**被什么约束逼出来**：业务变了、口径过期了、上游字段下线了，而**标签不会自己失效**（约束 5）。

**结构**：**退役流程**（下线申请 → 影响面枚举 → 通知消费方 → 观察期 → 归档）＋ **自动影响分析**（口径解析出依赖，上游变更时列出受影响标签）＋ **使用度指标**（近 N 天被查询 / 被圈选次数）。

**为什么这样设计有效**：因为**"没人用"与"不能用"是两个不同的判据，而只有使用度是可自动测量的**。因此机制上应当分开：**使用度驱动"建议退役"（自动化），影响面驱动"能否退役"（人工确认）**——把两者合成一个人工决定，结果是没人做这个决定。

**代价**：① **影响分析依赖口径可解析**——如果口径是自由 SQL，需借助 SQL 解析才能得到依赖（[Ch11 §05 血缘与影响](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md) 的同一套方法）；② **退役有观察期**（不能立即删除），因此存储成本不会立刻下降；③ **归档后的历史可查性要保持**（申诉可能发生在很久之后）。

**失效点**：**只标记不退役**——"已废弃"标签留在表里继续产出，消费方仍然能查到它。**判据**：退役的标签在服务层是否**返回明确错误**（而不是返回一个旧值）——返回旧值等于没有退役。

**判定方法**：挑一个上游字段（或一张上游表），问"它下线会影响哪些标签、哪些消费方"——能不能**不靠人工登记**、直接从口径表达式解析出来；再随机问一个标签"近 30 天被查过几次"。第一个动作对应 §2.3 ⑥ 的判据，第二个对应 §4.1 Step 7。两个动作分别落在 §3.7 的第 13、14 项。

**真实使用**：§4.3 工具链表把"血缘"一行写成"从口径表达式解析"，选型要点是"上游变更时能否自动列出受影响标签"；§4.4 存量的第四行给出次序（先加使用度埋点 → 观察一个季度 → 建议退役 → 不要直接删），§4.6 说明这条次序的经济理由。**这一模式在书内有一条完整的具名对照链**：`11-cross-cutting/05-lineage-and-impact` 的 §4.1 把"部署 SQL 解析服务、覆盖 Hive / Spark / Trino 三种方言"写成落地步骤，§4.2 的"影响分析（基于 DataHub API）"给出可核验的做法，§4.3 工具链表把 DataHub / Apache Atlas / OpenMetadata 列在"元数据 + 血缘平台"一行、把 OpenLineage / Marquez 列在"血缘规范 + 参考后端"一行——标签的退役影响分析就是这套方法搬到标签这一层（本主题 §3.2.7 的代价①也把这条指向 [Ch11 §05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)）。【公开】（来源：`11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact-section-4-sec4.md` §4.1 / §4.2 / §4.3；本主题 §4.3、§4.4 与 §2.3 ⑥）

#### 3.2.8 人群圈选（标签的查询面，不是标签本身）

**被什么约束逼出来**：业务需要"把满足条件的实体找出来"（触达、投放、分析），而这**是查询不是资产**（约束 5）。

**结构**：条件组合（标签名 + 运算符 + 值 + 时间语义）→ **可解释的执行计划**（按选择率选索引 / 全扫）→ 实体集 → 下发或导出。

**为什么这样设计有效**：因为**分群的生命周期与标签完全不同**——分群是**一次性的查询结果**（今天圈的人明天就变），标签是**被治理的资产**。把两者分开，得到两条实际收益：① **分群可以随时重算、临时创建**（不需要走资产治理流程）；② **标签不必为"被圈选"而增加定义**（否则标签会膨胀成"动作的别名"）。**若把分群当标签存**，标签数会随运营活动线性增长，而治理成本随之失效。

**代价**：① **执行计划要可解释**（否则"圈选很慢"无从优化）；② **一致性语义要显式**（用快照语义圈出的人，与用最新语义圈出的不同——这必须在界面上标明）；③ **分群结果里含个人信息**，导出要有权限与脱敏（[Ch8 §02 数据安全](../../08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance.md)）。

**失效点**：**圈选使用"最新"语义但业务以为是"快照"**——投出去的名单与复盘时重算的名单不同，而**差异无法解释**。**判据**：圈选结果是否带"口径版本 + 时间语义 + 生成时刻"这三项。

**判定方法**：圈一次人，然后查三样——① 结果里有没有带"口径版本 + 时间语义 + 生成时刻"；② 执行计划能不能解释"这次为什么用倒排索引 / 全扫"（§4.2（5）的最小形态是一行 `plan=` 日志）；③ 这次分群保存的是**条件**还是**名单**。三件就是 §4.9 第 15 项问的东西，也是本节这一模式的全部判定入口（无产品可引，理由见下段）。

**真实使用**：§6.3 的"某电商"一例（匿名案例，见该节来源声明）给的是这一模式从反面到正面的一条路——把每个分群注册成标签会让标签数随运营活动线性膨胀，分开之后标签数才只随"被复用的判定"增长；§4.2（5）给出执行计划可解释的最小形态，§7.6 的选型矩阵把"运营侧要快速圈人"一行的首选写成"标签平台 + **独立的分群 / 圈选模块**"、并注明"成品 CDP"作备选。**"成品圈选产品"这一侧本节不具名**：§7.2 只把"商业 CDP / 标签平台"作为一族列出，全书没有指名到产品，因此判定入口就是上面那三样（三元组、可解释计划、保存条件而非名单），而不是任何厂商的功能清单。【经验：本主题内无具名产品可引，故以三样可自测物替代具名】

### 3.4 组合模式：真实系统不会只用一种

1. **口径 + 双产线**：3.2.1 / 3.2.2 / 3.2.3（三类标签）共用**同一套口径层**，再经 3.2.4（离线 / 在线同源）产出——**口径层是这三类标签唯一的共享部件**，把它做薄，三类会各自漂移。
2. **服务 + 等级**：3.2.5（标签服务）+ 3.2.6（准入等级）——**等级必须在服务层生效**（否则生产路径绕过它）；两者的接口就是"该标签对当前调用方是否可见"。
3. **治理闭环**：3.2.6（准入）+ 3.2.7（退役）+ 使用度指标——**准入与退役是同一个生命周期的两端**，二者共用"使用度 + 准确率 + 覆盖/新鲜度"这四个度量（§2.2）。
4. **查询面**：3.2.8（圈选）建在 3.2.5（服务）之上，**且只消费"可信"级标签**——否则圈出来的人群里含有未验证标签造成的不确定性。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 口径散在各实现里 | 同标签离线与实时在边界用户上分叉 |
| 模型标签不带版本 | 模型升级后标签含义变化，无从归因 |
| 预测标签不存预测时点 | 复盘与申诉时答不出"当时的值" |
| 标签服务无降级 | 数据侧抖动直接变成业务事故 |
| 准入等级不接生产路径 | 试运行标签进入生产决策 |
| 退役只标记 | 废弃标签继续被消费 |
| 分群当标签存 | 标签数随运营活动线性膨胀 |
| 圈选不标时间语义 | 投放名单与复盘名单不同且无法解释 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **口径藏在代码里** | 三分钟讲不清某个标签怎么算的 | 多实现必然分叉、无法申诉 | 一开始只是"加一列"，口径没被形式化 |
| **只比总量不比个体** | 两份实现人数相同、名单差两万 | 边界用户被打错标 | 对账口径选了最容易的那个 |
| **模型分数当标签值** | 业务把 `0.73` 读成"73%" | 误读为概率、决策错位 | 分档需要业务确认，不如直接暴露分数省事 |
| **预测时点不落库** | "上月他的流失概率"答不出 | 无法回测、无法申诉 | 只存"最新一次结果" |
| **空值与零不分** | "没用过"与"用了 0 次"混为一谈 | 下游判定错位 | 二值化时省了一步 |
| **标签服务无超时无降级** | 数据侧抖动直接引发业务事故 | 关键路径被数据侧绑定 | 把它当成数据库的封装 |
| **等级不接生产路径** | 试运行标签出现在生产决策里 | 治理形式化 | 业务直连标签表更快 |
| **只标记不退役** | 废弃标签仍可被查到 | 腐化标签继续产出 | 退役要影响分析，先标记着 |
| **分群当标签存** | 标签数随运营活动线增长 | 治理失效 | 运营要"可复用的分群" |
| **圈选语义不标注** | 投放名单与复盘名单不同 | 无法解释差异 | 默认取"最新"，没意识到语义有两种 |
| **实体未统一就做标签** | 同一人身上的标签分成两套 | 覆盖率虚高、人群失真 | 实体治理在别的团队，等不及 |
| **没有使用度指标** | 没人知道哪些标签还有人用 | 退役无从谈起 | 使用度要埋点，被当成后续工作 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 宽表加列 → 标签工厂 | 加一个标签要改一次 ETL | 3.2.1 的口径层 | 口径从 SQL 抽到配置，存量标签逐个迁 |
| 标签工厂 → 标签平台 | 标签要给系统用（不只给人看） | 3.2.5 标签服务 | 服务层建设 + 缓存与降级策略 |
| 只有离线 → 离线 + 实时 | 实时场景（风控 / 推荐）要求 T+0【经验：出现"刚刚发生过"的判定需求即触发】 | 3.2.4 同源 | 口径改写成双引擎可执行 + 建逐实体对账 |
| 标签数破千 | 没人知道哪些还能用 | 3.2.6 + 3.2.7 | 补使用度埋点、准入等级、退役流程 |
| 标签进入生产决策 | 一次口径变更引发生产事故 | 3.2.6 准入 + 变更降级 | 把生产读取收口到服务，并把等级判定公示 |
| 标注来源扩展到非结构化数据 | 会话 / 文档里能产出的标签无法用规则表达 | 3.2.2 模型标签（+ §5.2 的边界） | 置信度与可追溯字段、抽检流程 |

**一条通用判据**：**跃迁的触发点不是"标签数变多"，而是"某个失效形态第一次出现"**——第一次出现"两个人问这个标签怎么算、答得不一样"就该建口径层；第一次出现"离线与实时名单不同"就该建对账；第一次出现"生产决策用错标签"就该上准入等级。**按标签数预设跃迁点，几乎一定过早或过晚。**

### 3.7 自检清单

- [ ] 实体（OneID）统一了吗？抽 100 个实体的归并率是多少？
- [ ] 每个标签的**口径**在哪？能三分钟内讲清"怎么算、依据什么、边界是多少"吗？
- [ ] 分档边界进口径了吗？它有版本吗（边界改了历史标签的含义会变）？
- [ ] 同一标签有几份实现？**逐个实体**对账过吗（不是比人数）？
- [ ] 空值与零定义清楚了吗？迟到数据是丢弃还是重算？
- [ ] 模型标签带模型版本与置信度吗？取值域被业务确认过吗？
- [ ] 预测标签存 `prediction_point` 吗？观察窗口与表现窗口写进口径了吗？
- [ ] 每个标签声明了时间语义（快照 / 最新）吗？业务问"上个月的值"答得出吗？
- [ ] 标签服务有点查 / 批量分离吗？有缓存失效、超时与降级策略吗？
- [ ] 关键路径上的消费方知道标签不可用时该怎么做吗？
- [ ] 准入等级在**生产读取路径**上生效吗（还是业务直连标签表）？
- [ ] 口径变更会自动把标签退回试运行吗？
- [ ] 有使用度指标吗？退役流程有观察期与归档可查性吗？
- [ ] 退役标签在服务上返回明确错误，还是返回旧值？
- [ ] 圈选结果带"口径版本 + 时间语义 + 生成时刻"吗？导出有脱敏吗？

### 3.8 小结

> 本节小结：标签平台的形态由五条约束按序决定——**实体统一 → 是否需要解释与申诉 → 时效 → 消费方式 → 规模与治理人力**；八种模式里，**口径层（3.2.1–3.2.3 共用）与离线 / 在线同源（3.2.4）是这条产线的地基**，**标签服务与准入等级（3.2.5 / 3.2.6）是把标签送进生产决策时必须成对出现的两个部件**（一个提供能力、一个提供约束），**退役与影响分析（3.2.7）与人群圈选（3.2.8）分别管"标签的终点"与"标签的查询面"**。判断这套东西有没有真正建成，只看两条：**同一个标签的多个实现，逐个实体的值是否完全相同**；**业务问"上个月他是不是这个标签"，你能不能答出来**。答不出后者，说明你的标签只有"最新"语义——而**申诉与复盘需要的恰恰是快照语义**。

> 💡 **思考锚点**：拿一个你正在用的标签，做两件最小的事——① 找到它的**所有实现**（离线、实时、规则引擎、模型输入），在同一个时点上**逐个数出十个人的值**，看是否一致；② 查一下它有没有 `prediction_point` 或等价的时点字段。第一件事测的是"口径唯一性"，第二件测的是"可复现性"。两件都不需要一天，但它们的答案决定你下一步该补口径层，还是该补时点字段——你打算先做哪一件？
