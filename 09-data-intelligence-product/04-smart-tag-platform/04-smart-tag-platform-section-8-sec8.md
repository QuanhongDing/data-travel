#### §8.1 你们平台上的"高价值用户"这个标签，有几份实现？你怎么证明它们算出来的名单是同一个？

**1. 考察点**
- 是否理解**"人数相同"不等于"名单相同"**；
- 是否知道不一致**集中在边界用户**上（而边界用户正是业务关注的）；
- 有没有可执行的验证动作（而不是"我们统一了口径"）。
- 是否知道"同一逻辑标签有几份实现"里**最容易被漏掉的那一份**——服务侧的反查索引（它是正查之外的第二份副本，漂移后的表现是"查得到他有这个标签、但按这个标签圈不到他"）；
- 是否理解"能不能做到逐实体对账"是一条**结构性能力**（取决于候选是否同时暴露两份产出），而不是验证力度的选择（§7.3.2）；
- 加分项：知道对账必须**常态化**，并知道"不一致是集中还是分散"这条分布信息本身就指示修法。

**2. 参考答案框架**

**第一层：先数实现份数。** 同一逻辑标签的实现通常有四类：**离线批任务、实时流任务、规则引擎里的硬编码、模型输入侧的加工**。**判据**：四类各取一处，问"这个标签在这里是谁写的"——答不出来的那一处，也是一份实现（只是没人把它当实现）。

**第一层的补充：第五份实现（最容易被漏的那一份）。** 除这四类之外还有一处**结构性的副本**——标签服务侧的**反查索引**。`04-data-assetization/06-one-service` 的 §3.2.2 把标签服务的两套存取结构写成"点查走 KV，圈人走倒排，两套结构缺一不可"，并写明"反查索引还要额外维护一份与正查同源的副本，两者口径漂移后会出现「查得到这个人有 churn 标签、但按 churn 圈人圈不到他」"。**它最容易被漏，是因为它长在同一个服务内部**——看起来像"同一个实现"，实际上是两份各自维护的索引。

**第二层：说明为什么"比人数"不够。** 设两份实现的判定函数为 `t₁`、`t₂`，则

```
不一致率 u = #{e : t₁(e,τ) ≠ t₂(e,τ)} / N
```

**总量相同可能对应 `u` 很大**——"离线 10 万人、实时 10 万人，但名单差两万"是常见形态。而**不一致不是随机分布的**：它集中在**时间边界、空值、迟到数据**三类上，而业务恰恰会盯着边界用户（"这个用户为什么在这个人群里"）。

**为什么"比人数"会被反复选中（机制层面的解释）**：`count(*)` 一条查询就能出，而逐实体对账要落两张表再 `FULL OUTER JOIN`，还要处理空值比较（§4.5 模板 3 里 `COALESCE(..., '<null>')` 那一步就是为它准备的）。**成本差异决定了默认选择**——所以它不是判断力问题，而是**取证成本问题**（§6.2 同段的机制解释也是这一条）。

**第三层：给出验证动作（本题的关键）。** 取同一批实体、同一时点，把两份实现的值 `FULL OUTER JOIN` 并排，**只输出不一致的行**，**门禁判据是该查询返回 0 行**（§4.5 模板 3）。得到非空结果后，**先看不一致实体的分布**：集中在三类边界上 → 对齐边界；分散 → 说明口径本身不同。

**第三层附带的一条取数约定**：对账必须**取同一批实体、同一个 `τ`**，而不是"两边各自取最新"——流侧与批侧的"最新"在时间上不是同一个点，**用两个最新值比对会把时间差算成口径差**。**判据**：对账 SQL 的两侧是不是都带了同一个时点参数（§4.5 模板 3 里的 `:tau`）。这一条还解释了"实时侧没有历史数据怎么对账"的疑问：对账不要求历史，只要求**两侧能各自产出同一时点的值**。

**第四层：把对账变成常态。** 一次性验证挡不住流侧的渐进漂移（迟到数据、状态重建、算子升级）。**因此对账要作为常备任务**——它的成本约半天级，是本主题投入产出比最高的检查。

**第四层的成本形状**：那"半天级"是**一次动作**的耗时【经验】；常备的那部分不是动作，而是**看差异分布的那双眼**——差异的三分类（集中在时间边界 / 空值 / 迟到数据，还是分散）决定修法，而做这个分类的是人而不是 SQL。**判据**：最近三次非零结果分别被归到哪一类、随后改了什么。

**第五层（加分）：把这条判据放进治理闭环。** 逐实体不一致数是本主题的**第一条 KPI**（§5.7 第 4 条）——口径层、服务层、治理层三个部件的健康状况都用它来表达。而它的目标值是**"0 不一致"而不是"接近 0"**（§2.2 要求 `u = 0`）：因为不一致集中在边界，**任何非零都是一个可定位的缺陷**，而不是统计噪声。把它做成门禁还带来第二件收益：它给"新口径能不能上线"提供了一个客观条件，而不是靠评审会上的印象。

**第五层还要说清它的代价**：常态化的逐实体对账是**常备人力**，本主题把它算在"0.3–1 人年量级"的常备投入里【经验】（§4.6）。因此这条判据的正确用法是**挂在"会改变结果的动作"上**（新口径上线、新算子上线、引擎版本变更、流侧状态重建），而不是每天把全量标签跑一遍。**判据**：对账的触发条件是"**有改动**"还是"**到点了**"——前者能定位到一次变更，后者只会积累成一张没人看的差异报表。

**3. 常见陷阱**
- 只答"我们统一了口径"，说不出**验证动作**；
- 用"两边人数一致"当一致性证据；
- 只考虑离线与实时两份，漏掉规则引擎与模型输入侧；
- 认为对账是一次性验证。
- 漏掉服务侧的**反查副本**——它长在同一个服务里，看上去不像"另一份实现"，却是同一个标签的第二条路径；
- 只比总量、不看**分布**——"差异集中还是分散"决定了修法，不看分布等于放弃了这条判据自带的信息；
- 认为"两边用了同一份 SQL"就等于同源——**同源的定义是"一份定义 + 两种执行"，不是"两段长得像的 SQL"**（§3.2.4）；
- 把平台给的"标签质量分"当成一致性证据——**汇总量与逐个实体比不是同一件事**（§7.3.2）。

**4. 追问预测**
- "如果不一致集中在一小撮人上，你怎么判断是边界没对齐还是口径不同？"
- "实时侧没有历史数据，你怎么对账？"
- "对账发现不一致之后，已经投放出去的名单怎么办？"
- "逐实体对账的成本，你打算多久跑一次？"
- "如果两份产出里有一份根本拿不到，你还能证明什么？"（只能证明规模相似——这正是"能不能同时取到两份产出"是一条结构性能力的意思，§7.3.2）

**5. 参考资料**
- 本主题 §2.2（不一致率的算式与"为什么不要求接近 0"）、§3.2.4（离线 / 在线同源）、§4.5 模板 3、§6.2（比人数导致的失败）。
- 本主题 §3.2.5（点查与批量分离：正查 / 反查是两套结构）、§4.1 的 Step 4（对账常态化）与 Step 5（服务三件）、§7.3.2（验证位置是结构性能力）。
- `04-data-assetization/06-one-service/06-one-service-section-3-sec3.md` §3.2.2（标签驱动型：正查走 KV、反查走倒排 / 位图，反查副本漂移后的表现形式）——核验入口是该节的"真实使用"段，它给出"看圈人是在标签服务内完成、还是被转发到数仓跑一条大查询"这一判定。

#### §8.2 业务问"上个月他是高价值用户吗"，你的标签系统答得出来吗？为什么？

**1. 考察点**
- 是否知道时间语义有**两种**（快照 / 最新），且它们是两个资产；
- 是否理解**申诉与复盘发生在决策之后的数周**，因此只有快照能应答；
- 有没有意识到"只存最新值"是**在产出时就覆盖掉了历史**，事后补不回来。

**2. 参考答案框架**

**第一层：直接回答两种语义的差别。**

```
语义 A（快照 / Snapshot）：按 event_time 取那一刻的事实 —— 可复现（同一 τ 永远同一结果）
语义 B（最新 / Latest）：取当前最新一次计算的结果 —— 新鲜优先，但不可复现
```

**判据**：业务问"上个月他是吗"——答得出是 A，只能答"现在是不是"是 B。

**第一层最容易答错的一处：分区不等于快照。** 用 `WHERE dt = '上月末'` 取到的是**"上月末那天算出来的值"**，不是**"上月末的事实"**——两者在**迟到数据到达与历史重算**时会分叉（本主题 §7.3.3 的定性机制表把这条列成宽表形态的典型失败形态）。本主题 §4.5 模板 1 的示例口径卡把时间语义格写成 `snapshot（按 dt 取）`，**这一格本身正处在两者的分界上**：如果口径里没有 `event_time` 这一维，"snapshot"这个词到底指哪一个，**只有写卡的人知道**——这也是 §4.9 会单独问"存不存 `prediction_point`"的原因。

**第二层：说明这条区分为什么是结构性的，而不是功能差异。** 语义 B 的实现**在写入时就覆盖了上一版**——历史不是"没开放"，而是**不存在**。因此从 B 迁到 A **不是加一个接口，而是加时点键 + 保留历史**，而如果上游明细也已不可得，**那段历史永久补不回来**。

**第二层的两个延伸。** ① **"需要时可以查日志"不是答案**——日志记的是"系统做过什么"，它**没有口径版本**，因此回答不了"当时按哪一版口径判的、依据是哪些字段"。本主题对可解释性的定义是**可追溯**（模型版本 / 依据字段 / 置信度落库），而日志不落在标签资产里。② **"补一个历史分区"也要看上游**——重算需要当时的输入明细；迟到数据一旦在分区封板时被丢弃、上游明细又只保留有限期【经验：保留期由存储策略决定，各团队不同】，重算就退化成"用今天的输入算昨天的判定"，而那不是一个快照。

**第三层：给出适用场景的划分。** **风控、信贷、准入、审计、申诉必须用 A**（要能复现当时判定）；**实时推荐、个性化展示用 B**（新鲜度优先）。**同一标签名下的 A 与 B 是两个资产**——口径可能不同、消费者不同、SLA 不同，因此它们应当有各自的版本与等级。

**第三层的建模含义**：同一个标签名既要 A 又要 B 时，**不要在一条记录里"兼用"**——两条语义的消费者不同、失效方式也不同（A 怕历史被覆盖，B 怕新鲜度不够），**共用一个版本号会让"改口径"这件事的含义变得含混**：改了分档边界，A 侧要重算历史、B 侧只要下一次产出生效。可核验的做法是让它们各自带 `time_semantics` 字段（§4.2（1）的口径 YAML 里有这一项），并让缓存键、SLA、准入等级都按这个字段分开。

**第四层：给出实现要点。** 关键是**时点键**：标签表按 `(entity, tag, event_time)` 存储（或按分区 + 可查询的时点），而不是按 `(entity, tag)` 覆盖写。**判据**：标签表的主键里有没有时点维度——没有，就说明只有 B。

**第四层要同时回答"膨胀怎么办"**：保留历史意味着存储按"保留的时点数"放大，而本主题的在线存储量与"实体数 × 在线标签数 × 单值字节 × 副本数"成正比（§4.6）。**这两件事的边界必须分开**：**快照属于产出侧**（放在离线 / 归档层，按需查询），**最新值才属于在线服务侧**（点查要走低延迟存储）。**把快照放进在线服务是一处常见误配**——它既抬高了在线存储，又让"历史可复现"这件事依赖了一个为低延迟设计的部件。**判据**：历史值是从在线服务取，还是从归档层取。

**第五层（加分）：把这条与"缺一期"的语义接起来。** 快照语义下，**"这一期没算出来"必须与"这一期算出来的是无值"分开**——本主题给的纪律是**缺一期要产出 `stale`（保留上期值并标记）而不是 `null`**（§4.7）：因为消费方分不清"这个人不符合"与"这一期没算"，返回空会让未覆盖被静默当成不符合。**这条把时间语义与缺失语义合成同一个判断**：接口返回里必须同时能看出**"哪个时点"与"那一期有没有算出来"**。

**第五层再补一条本主题特有的冲突**：**"最新"与"快照"的矛盾在实时场景里最尖锐**——风控要快照（可申诉）、推荐要最新（新鲜），而它们常常消费的是**同一个标签的同一份产出**（§5.3.3）。**这里要与第三层对齐**：即使两侧最终读的是同一条时点键链路，登记上仍按 §2.2 分成两份资产（各自版本与等级）——**共享一份产出不等于共用一个资产**。**解法不是二选一**，而是产出侧保留时点键、由服务侧按调用方声明的语义返回；**判据是"消费方有没有声明它要哪一种"**，而不是服务端默认给一种——默认给的那一种，对另一半消费方必定是错的。

**3. 常见陷阱**
- 只答"我们存了历史分区"，而分区是"计算日"不是"event_time"（两者在迟到数据与重算时会分叉）；
- 认为加一个 `WHERE dt = '上月末'` 就是快照（那是"上月末算出来的值"，不是"上月末的事实"）；
- 回答"需要时可以查日志"——**日志不是标签，它没有口径版本**；
- 没有意识到"覆盖写"意味着历史不存在。
- 把快照放进在线服务——**历史值与最新值的存储位置本该分开**，混在一起会同时抬高在线存储、又把可复现性绑在一个低延迟部件上；
- 把"这一期没算"与"这一期无值"用同一个返回值表达——两者要能分开，否则未覆盖会被当成不符合（§4.7 的 `stale` 纪律）。

**4. 追问预测**
- "重算历史分区之后，'上个月的值'变了，你怎么解释？"
- "快照语义下，标签体积会膨胀多少？你怎么控制？"
- "如果一个标签既要快照又要最新，你怎么建模？"
- "口径版本与快照时点，哪个先决定？"
- "上游明细只保留有限期，你还能重算多久以前的历史？"（这一问考的是"快照"与"可复现"的差别：明细过期的时点，就是可复现性的边界）

**5. 参考资料**
- 本主题 §2.2（两种语义与判据）、§3.2.3（预测时点必须落库）、§6.4（申诉靠字段不靠流程）、§7.3.3（时间语义的候选差异）。
- 本主题 §4.2（1）（口径 YAML 里的 `time_semantics` 与版本项）、§4.5 模板 1（口径卡的时间语义格，示例写作 `snapshot（按 dt 取）`）、§4.6（在线存储的算式与"低频标签移出在线服务"的动作）、§4.7（"缺一期"要产出 `stale` 而不是 `null`）、§4.9 第 8 项。
- `02-data-science/01-feature-store/01-feature-store-section-4-sec4.md` §4.2（Point-in-Time 取数约束：只能用标签时点之前可观测的值）——**引用时须说明它是特征侧的同一件事**（管"只能用当时能看到的数据"），答的不是"当时判的是什么"。

#### §8.3 一个标签的覆盖率只有 75%，剩下 25% 的人在系统里会怎样？这有什么风险？

**1. 考察点**
- 是否知道**"无值"与"不符合"必须分开**（三态 vs 二值）；
- 是否理解这条差异**在人工场景看不出来、在机器消费场景会变成错误结论**；
- 有没有意识到"未覆盖被静默当成不符合"是**静默的**。

**2. 参考答案框架**

**第一层：先定义两种接口语义。**

```
二值：返回 true / false（或 1 / 0）—— 无值与不符合同值
三态：返回 符合 / 不符合 / 无值（带 missing 标记）—— 三者可区分
```

覆盖率 75% 时，二值语义意味着**那 25% 的人被当成"明确不符合"**。

**第一层要先问一句：这个覆盖率是怎么算出来的。** 分母是"**应标实体**"，而"应标"本身是一个口径决定——实体键缺失的明细算不算在分母里？本主题 §2.3 的边界③把这一类单独列出：**实体键缺失不是"没算出来"，而是"算出来但不知道是谁"**，它应当进**未归属桶**而不是被丢弃。**判据**：这个覆盖率的分母是"全部明细"、"能归并的实体"，还是"被标签表覆盖到的实体"——**三种算法能给出差别很大的覆盖率**，而三个数都可以被诚实地报出来【经验：差异量级随实体归并率而变，请用你自己的归并率校准】。

**第二层：说明为什么这在人工场景里看不出来。** 人拿到"无值"会追问（"为什么没有？"）或保守处理；**而机器不会**——模型 / Agent / 规则引擎会把 `false` 当成事实继续推理，最后产出一个**基于错误前提但看起来合理**的结论（例如"他不是高价值用户，所以不推券"）。**这条错误的特征是静默的**：没有报错、没有告警，只是效果变差或待遇给错。

**第二层还要说清"静默"的三种表现**。① **下游看起来一切正常**——报表有人数、接口有返回、任务没报错；② **发现路径通常是业务侧的异常**（"为什么这批人没收到券"），而不是数据侧的监控；③ **它会被组合放大**——一个打错的标签可能被模型基于它再推出几个结论（§5.3.2），**错误不是被平均掉，而是被乘上去**。这三条合起来解释了为什么"三态"这件事容易被推后：**它的代价不在当下，而在下游的某个结论里。**

**第二层还要能说出"未覆盖"的三类成因**，因为它们的修法完全不同：① **空值与零不分**（明细里没有记录，被当成 0 用了）——修法是在口径卡里把"无记录 → 无值"写死（§4.2（1）的边界①）；② **迟到数据**（本期没到、下期才到）——修法是把迟到处理写进口径，且**"丢弃"与"触发重算"两种都要写明**（边界②）；③ **实体键缺失**（算出来了但不知道是谁）——修法是进未归属桶而不是丢弃（边界③）。**同一句"覆盖率低"，三类成因对应三种修法**；答不出成因，覆盖率就只是一个数。

**第三层：给出修法与代价。** 接口返回里带 `missing` 标记；**消费方要显式声明 `on_missing` 行为**（用默认值 / 跳过 / 拒绝）（§4.5 模板 2）。代价是**消费侧要改**——而这正是它常被跳过的原因。

**第三层要补一条容易漏的分界**：**"无值"与"这一期没算出来"也不一样**。本主题给的纪律是**缺一期要产出 `stale`（保留上期值并标记）而不是 `null`**（§4.7）——否则消费方会把"这一期没跑"读成"这个人不符合"。**因此接口返回至少要能区分三件**：符合 / 不符合 / 无值，**加上一件状态信息**：这个值是本期算的还是上期留的。**判据**：返回里有没有一个字段能表达"这是 stale 值"。

**第三层还要说明"消费侧要改"改到什么程度**：真正的修法不是让每个消费方自己判空，而是**把处理方式写进调用声明**——消费方在调用时声明 `on_missing` 与 `on_timeout`（用默认值 / 跳过 / 拒绝；超时用旧值还是失败），服务端照声明执行（§4.5 模板 2 把这两件事写在同一段，正是因为它们必须成对出现）。**判据**：关键路径上的消费方知不知道标签不可用、或标签没有值时该怎么做——不知道，就等于把这两件事留给了每次调用的临时判断。

**第四层：给出监控判据。** 按标签统计**覆盖率**与**未归属桶大小**（§2.3 的边界③要求守恒：明细总量 = 各实体标签用量 + 未归属用量）。**判据**：覆盖率与未归属规模有数、且有告警。

**第四层的一个可操作补法**：把覆盖率与未归属桶**按标签分别看，不看平台级汇总**——本主题 §2.2 的四个度量（覆盖率 / 一致性 / 新鲜度 / 准确率）**必须按标签给，不给平台级质量分**：一个平台级覆盖率会把"高覆盖但关键的标签"和"低覆盖但长尾的标签"平均到一起，而下游消费的是**某一个标签的某一个实体**。**判据**：能不能拿到一张按标签分组的度量表（§5.4 那张接口表的最后一行把这件事写成"标签平台按标签粒度输出度量"）。

**第五层（加分）：把三态与准入等级接起来。** 覆盖率达标是本主题准入条件**唯一可自动计算的那一项**（与逐实体一致性、新鲜度、抽检准确率并列，§6.4）；**但"达标"不等于"可以进决策"**——因为覆盖率是"有值"的比例，而正确性要靠抽检（人工核对）证明。**这一层的要点是不要把两者混为一谈**：覆盖率告诉你"多少人被覆盖"，抽检告诉你"覆盖到的人里有多少被判对了"，**前者可自动算、后者只能抽样人工核对**，而本主题成熟度判据②核不到的原因正在后者（§5.2）。

**3. 常见陷阱**
- 只答"会返回空"，不问下游怎么处理；
- 认为"返回空"与"返回 false"没区别；
- 没有覆盖率监控（不知道 25% 是哪些人）；
- 忘了实体键缺失这一类（它不是"没算出来"，而是"算出来但不知道是谁"）。
- 报覆盖率时不说是**按哪个分母算的**——分母一变数就变，而三个口径都能被诚实地报出来；
- 把"补一个默认值"当成修法——**接口补了 `missing` 标记、消费方不声明 `on_missing`，等于没改**（§4.5 模板 2 把两件事写在同一段里，正是因为它们必须成对出现）；
- 把覆盖率达标当成"这个标签可以进决策"——覆盖率只说明"有值的比例"，**判对的比例要靠抽检**（§6.4）。

**4. 追问预测**
- "如果标签是风控用的，25% 未覆盖你怎么处理？拒绝服务、放行、还是走人工？"
- "未覆盖的人与覆盖率低的人群有没有系统性偏差？"
- "实体归并率本身不到 100%，那部分人算覆盖还是未覆盖？"
- "你怎么向业务解释'这个标签只覆盖了四分之三的客户'？"
- "这一期任务失败了，消费方看到的是 `null` 还是 `stale`？"（这一问考的是"无值"与"没算"要不要分开——§4.7 的纪律）

**5. 参考资料**
- 本主题 §2.2（覆盖率与守恒）、§2.3（实体键缺失的边界）、§5.3.2（机器消费时的三态要求）、§4.5 模板 2。
- 本主题 §2.2（四个度量"必须按标签给、不给平台级质量分"）、§4.7（"缺一期"要产出 `stale` 而不是 `null`）、§5.4（接口表：标签平台按标签粒度输出度量）、§6.4（准入条件里覆盖率与抽检准确率各管一半）、§7.3.4（缺失语义在候选之间的差别）。

#### §8.4 你们打算用大模型从客服会话里抽标签，怎么做才敢让它进生产？

**1. 考察点**
- 是否理解 LLM 抽取带来的是**"来源扩展"而"可复述性下降"**；
- 是否知道要补哪三样字段（模型版本 / 原文回指 / 置信度）；
- 有没有意识到**抽检成本上升**与**漂移是静默的**。

**2. 参考答案框架**

**第一层：先说清楚它变的是什么。** 它让**以前无法判定的事实变得可判定**（从结构化字段扩展到文本 / 会话），代价是**判定无法用一句规则复述**。因此可解释性的实现方式必须从**可复述**转为**可追溯**。

**第一层要先把"为什么以前没做"讲清楚。** 这类判定在 AI 之前不是"做得差"，而是**根本没有人做**（§5.3.1）：它们只存在于客服会话、工单、访谈文本里，结构化字段里没有对应的列；而**补字段这条路走不通**——人工把文本标注成字段，成本随会话量线性增长，且**标注口径本身也无法复述**。**说清这一点才能回答"这值不值得做"**：只有当"要判定的那类事实只存在于文本里、且它会影响人的待遇或进决策路径"时，它才是唯一解（§5.3.1 的适用条件）。

**第二层：三个必补字段（这是准入的最小条件）。**
- **模型版本**——进标签血缘，否则模型升级后标签含义变化无从归因；
- **原文回指**——依据的是哪段文本（片段级，不是"整个会话"）；
- **置信度**——随标签存储，否则下游被迫按二值处理。

**三样缺任何一样，这个标签就只能停在"试运行"等级**——因为它无法构成申诉（§6.4 的教训）。

**第二层要说清"为什么是这三样"，而不是背清单。** 三样分别回答申诉时的三个问题：**"凭什么这么说"**（原文回指）、**"哪个版本判的"**（模型版本）、**"有多大把握"**（置信度）——**缺哪一样，就有哪一个问题答不出**，而申诉只要有一个问题答不出就不构成解释（§6.4 的字段表把这几行按标签类型排开）。**一处要提前说明的工程缺口**：本主题 §4.5 模板 1 的十二个格里**没有** `model_version` / `confidence` / `prediction_point` 这三行，它们目前只出现在 §4.9 的自检项里（§6.4 的关键示意段也标注了这一点）——**因此"落格"这件事本身是这套模板还需要补的一步**，而不是已经具备的能力。

**第三层：给出准入路径（分档而不是一刀切）。**
- **确定性规则先行**：能规则判的先规则判（硬信号：明确的关键词组合、结构化字段），**模型只处理剩余部分**——反过来做会引入不确定性而得不到新能力；
- **分档使用**：高置信自动、低置信转人工复核；
- **等级分明**：先试运行（可看不可用）→ 抽检达标 → 可信（可进决策）。

**第三层里"规则先行"的判据要写出来**：它不是排序偏好，而是一条可验证的分工——**问"这条判定，规则能不能判"**：能判的部分交给规则，模型只接手规则判不了的那部分（同 [Ch10 §02 §3.2.5](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的规则 + 模型分工）。**反过来做的代价是"用模型去做规则能做的事，只会引入不确定性而得不到新能力"**（§5.5 第 2 条）——而这条错法看起来很像"统一用一套技术栈"，因此在评审时不容易被拦下。

**第四层：两条必须提前承认的代价。** ① **抽检成本比结构化标签高一个量级**（要人工判断语义，不能机械化）；② **漂移是静默的**（客服话术一变，抽取结果整体偏移，而覆盖率与分布会慢慢移动）——**因此要监控分布漂移，而不只是准确率**。

**第四层要补上"人工复核闭环"这一环——它是这类标签在书内唯一有具名做法的地方**：`08-ai-governance/01-ai-data-governance/01-ai-data-governance-section-8-11-8-智能数据治理与-ai-应用.md` 的「智能数据治理与 AI 应用」一节（原题库编号 11.8，见文件名）（该文件的第 8.6 节）在参考资料里记过**京东对商品 / 用户属性自动打标时用"模型打标 + LLM 解释 + 人工复核闭环"**、以及**招商银行用 NER + LLM 识别字段敏感标签后触发权限策略**——两处都是"企业名 + 结论"式条目，**本书给不出可核验文档名，请按【经验】档理解，不要当单点事实引用**。它们对本题的意义只有一条：**复核产出的判定要回流**，否则抽检只是抽样报告，不改变下一次的判定。

**第五层（加分）：把成熟度与退出条件说清。** 这个方向在本主题的定级是 **L2**，卡点全在"有没有第三方（非厂商）公开的生产案例"这一条判据上——**本节需要的是"抽取标签的准确率与不当打标的代价"，而这恰恰是没人公开的部分**：核对结果会直接暴露"系统判错过多少人"（§5.2）。因此**它的落地方式是"可试点、但自带退出条件"**：试点期间如果答不出"怎么申诉"，或抽检成本无法持续投入，就退出（§5.7 第 2 条）。**把退出条件先写下来，是这一类方向唯一不靠乐观假设的推进方式。** 另有一处方向性材料可作对照但**不可反过来当证据**：`08-ai-governance/01-ai-data-governance` 同页列有 LinkedIn DataHub 的 Auto-tagging RFC 与 Mitchell 等《Model Cards for Model Reporting》(FAT* 2019)——后者是"一个模型资产该带哪些元数据"的合规材料来源，**它证的是"该带什么"，不是"打了标的准确率是多少"**。

**3. 常见陷阱**
- 直接说"用大模型抽更准"，说不出准不准怎么验；
- 不提置信度；
- 用模型去做规则本来就能做的判定；
- 没有原文回指，出问题时无法回答"依据什么"；
- 只监控准确率、不监控分布漂移。
- 把"三样字段"当成"上线前的表单"——**它们是产出时就要落库的字段**，事后只能重放当时的输入，而上游文本多数已变（§6.4 的失败教训："流程可以事后建，字段不能事后补"）；
- 认为"抽检做几次通过就可以定级"——**抽检是常备动作**，它是"可信"等级唯一的客观依据（§6.4），断掉就等于等级失去了依据；
- 把厂商材料里的抽取能力当成准入依据——**判据①成立不能替代判据②**（§5.3.1 的证据与来源段）。

**4. 追问预测**
- "抽检怎么抽样？按实体随机、按标签、还是按置信度分层？"
- "低置信转人工之后，人工的判定要不要回流成训练样本？"
- "模型换代之后，历史标签的可比性怎么办？"
- "如果业务要求'必须能解释'，你还能用 LLM 抽吗？"
- "这套东西的试点退出条件是什么？"（考的是有没有把 L2 的"可试点、自带退出条件"当成推进方式，§5.7 第 2 条）

**5. 参考资料**
- 本主题 §5.3.1（LLM 抽取的机制变化与三条代价）、§3.2.2（模型标签的三样配套）、§6.4（可解释靠字段）、[Ch10 §02 §3.2.5](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md)（规则 + 模型的分工）。
- 本主题 §5.2（三条 L1 判据与"本节没有一行达到 L1"的卡点解释）、§5.5 第 2 条（不要用模型做规则能做的事）、§5.7 第 2 条（试点自带退出条件）、§4.5 模板 1 与 §4.9 第 7 项（模型版本与置信度目前只在自检里被检查、没有落格）、§6.4（字段表与"字段不能事后补"）。

#### §8.5 运营要"圈一批人"，产品说"把分群注册成标签，下次还能用"。你怎么处理？

**1. 考察点**
- 是否理解**分群是查询、标签是资产**（生命周期与治理要求不同）；
- 是否知道"可重用"有**保存结果**与**保存条件**两种实现；
- 有没有意识到"把分群当标签存"会让治理台账被淹没。

**2. 参考答案框架**

**第一层：先给出两者的差别表。**

| 维度 | 标签 | 分群 |
| --- | --- | --- |
| 生命周期 | 长期资产（有版本、等级、Owner） | 一次性查询结果（今天圈的人明天就变） |
| 治理要求 | 口径 / 准入 / 退役 / 申诉 | 几乎无（但导出要脱敏） |
| 重用方式 | 被多处消费同一份定义 | 保存**条件**，重算结果 |

**第一层再补一维：过期时的默认行为正好相反。** 标签过期会触发告警与重算（**它是资产**）；分群过期**不自动重算**，要么被显式重跑、要么被丢弃（§6.3 的做法⑤）。**这一维是合并两套台账最先撞上的地方**——把两者混在一张表里，平台只能用一套默认行为，而它对其中一侧必定是错的。**判据**：一个三个月前的分群今天还能不能直接用——能直接用，说明它保存的是名单（而名单已经过期）。

**第二层：给出正确处理。** **分群不注册成标签**；"下次还能用"用**保存查询**实现——保存**条件组合 + 参数**，而不是**名单**。**判据**：保存的是条件还是名单——保存名单在重用时拿到的是过期结果，而业务通常看不出来。

**第二层要顺手回答"那它靠什么被复用"**：分群的重用发生在**查询层**（同一条条件重算一次），不是"在资产层再跑一次"——因此产品上要接受"分群列表会很长、且大多数是一次性的"（§6.3 的代价段）。**判据**：分群列表是按"最近被用过"排序，还是按创建时间堆积——后者说明复用实际没发生，只是没被清理。

**第三层：说明合并的后果（可观测）。** 标签数会**随运营活动线性膨胀**（一场大促几十个"XX 活动人群"），而治理成本随标签数线性增长（§4.6）——**结果是真正的判定型标签被淹没在活动人群里，评审流于形式**。

**第三层补一条"为什么它不会自己停下来"**：膨胀的是**治理成本**（标签数 × 单位维护人力），而不是磁盘——**磁盘涨了会有人提，治理成本涨了不会有人提**，直到评审会因为清单太长而流于形式（§6.3 的触发点段）。这条性质决定了它**必须靠流程约束，不能靠成本信号**。

**第三层再补一条"淹没"的具体机制**：活动人群的**命名与结构天然相似**（"XX 活动人群"），因此在资产搜索与评审清单里**它们互相稀释**——不是某一条特别差，而是**清单变长之后没人逐条看**（§6.3 把症状写成"治理评审会因为清单太长而流于形式"）。**判据**：一次评审会里每条标签平均分到多少时间——分不到一分钟，说明清单已经超出评审容量。

**第四层：给出圈选结果的必备三项。** 结果带**口径版本 + 时间语义 + 生成时刻**——因为投放名单与复盘名单不同时，只有这三样能解释差异；缺了它们，差异会被归因为"数据有问题"。

**第四层再补一件同层的事：导出与下发的边界。** 分群结果里含个人信息，导出要走权限与脱敏（§3.2.8 代价③、[Ch8 §02 数据安全与合规](../../08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance.md)）；**下发给触达系统的是实体键与触达所必需的字段，不是标签明细**。**为什么这件事和"分群不是标签"是同一个问题**：分群与标签分开之后，**"谁能看哪些标签"与"谁能圈哪些人"是两个权限问题**——混在一起时，**圈选会成为绕过标签权限的旁路**（§6.3 的做法④）。**判据**：一次圈选导出的字段清单里，有没有超出触达所需的标签值。**相邻环节有一处具名但容易误读的证据**：投放平台回传的人群包与内部 CRM 是两个 ID 体系，匹配率不高（Ch1 §09 点名巨量、腾讯广告，该节给出的量级请按【经验】档读）——**引用时的正确用法是"两个 ID 体系之间要有可核的匹配口径"，而不是把它当成本主题的圈选性能指标**。

**第五层（加分项）：分层处理。** 少数**反复被复用、并被跨场景消费**的分群条件，值得**升级为标签**（它确实被当资产用了）——**判据是"这个条件在近三个月被几个不同场景引用过"**，而不是"运营觉得它重要"。

**第五层的补充：升级要走完整条流程，不能只补一个 Owner。** 允许提升的路径是"定义口径 → 业务确认分档与语义 → 定 Owner → 定等级（试运行起步）"（§6.3 的做法⑥）；**缺了后半段，提升就退化成"给活动人群补一个 Owner"**——台账上多了一行，口径仍然不在配置里。**判据**：被提升的标签**定义的是条件还是结果**——定义结果的（"上次活动圈的那批人"）不该被提升；判断依据是**"重算一次能不能得到同一批人"**。

**3. 常见陷阱**
- 直接答应"注册成标签，下次能用"；
- 保存名单而不是条件；
- 圈选结果不带口径版本与生成时刻；
- 没有"分群可以升级为标签"的判据，导致要么全升级、要么全不升级。
- 把权限也一起合并——**"谁能看标签"与"谁能圈人"不分开时，圈选会变成绕过标签可见域的旁路**（§6.3 的做法④）；
- 用"磁盘涨得不多"证明"分群当标签存没代价"——**膨胀的是治理成本，它不产生任何存储告警**（§4.6）；
- 升级为标签时只补 Owner、不补口径与等级——**那一行就只是一个名字**（§6.3 的做法⑥）。

**4. 追问预测**
- "分群结果导出给外部投放平台，权限与脱敏怎么管？"
- "如果两个运营分别保存了几乎一样的条件，你怎么治理？"

#### §8.6 你的标签平台怎么决定"哪些标签该退役"？为什么不能直接删？

**1. 考察点**
- 是否知道**"没人用"与"不能用"是两个判据**，而只有前者可自动测量；
- 有没有意识到**废弃标签不会自己失效**，会继续产出看起来合理的值；
- 是否知道退役要有**观察期**与**归档可查**。

**2. 参考答案框架**

**第一层：区分两个判据。** **使用度**（近 N 天被查询 / 被圈选次数）——**可自动测量**，用来驱动"建议退役"；**影响面**（被谁消费、上游依赖什么）——**需要人工确认**，用来决定"能否退役"。**把两者合成一个人工决定，结果是没人做这个决定。**

**第一层要说清"为什么必须分开"**：因为**只有使用度是可自动测量的那一半**——影响面需要枚举"谁在消费它"，而消费方**可能是你不知道的人**（直连标签表的下游、离线任务、外部系统）。因此机制上的分工是：**使用度驱动"建议退役"（自动化），影响面驱动"能否退役"（人工确认）**（§3.2.7）。**判据**：有没有一条按"近 N 天被查询 / 被圈选次数"列出的建议退役清单，以及其中被 Owner 确认过的比例。

**第二层：给出退役流程。** **影响分析 → 通知消费方 → 观察期 → 归档**（不是删除）。**判据**：退役标签在服务层返回**明确错误**——**返回旧值等于没有退役**（消费方仍能查到，只是不知道它已废）。

**第二层要指出"影响分析靠什么自动"**：靠**从口径表达式解析出的依赖**，而不是靠人工登记——本主题 §4.3 把"血缘"一行写成"从口径表达式解析 / 数据目录附带"，选型要点是"**上游变更时能否自动列出受影响标签**"。书内他处可指的一整套做法在 `11-cross-cutting/05-lineage-and-impact` 的 §4.1 / §4.2 / §4.3：该节把"部署 SQL 解析服务、覆盖多种 SQL 方言"写成落地步骤，把"影响分析"写成基于元数据平台 API 的动作，并把候选工具列成"元数据 + 血缘平台（DataHub / Apache Atlas / OpenMetadata）"与"血缘规范 + 参考后端（OpenLineage / Marquez）"两行（该节同时标注了若干已停更项目，**引用时请以各项目仓库当前状态为准**）。**标签的退役影响分析就是这套方法搬到标签这一层**——本主题 §3.2.7 的代价①也把这条指向 [Ch11 §05](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)。

**第三层：说明"为什么不能直接删"。** ① **可能有你不知道的消费方**（直连标签表的下游、离线任务、外部系统）——删掉会让它们静默失败或读到空；② **申诉与审计可能需要历史**——删除等于销毁证据；③ **业务可能季节性使用**（季度结算、年度盘点用的标签，平时使用度为零）。

**第三层再补两条同类的理由**：④ **"零使用"可能只是埋点没建**——没有使用度埋点时的"没人用"，是把"没测量"读成"没人用"（§4.4 存量迁移的第四行因此把次序定成"先加使用度埋点 → 观察一个季度 → 建议退役 → 不要直接删"）；⑤ **下游字段下线导致的"被动退役"与主动退役不是同一条流程**——前者是上游变更引发的影响分析（§4.7 的"上游字段下线"演练行：影响分析给出受影响的标签与消费方，再逐个处置），后者是治理侧的判断。**把两者混成一条流程，结果是上游变更时没人知道要动哪些标签。**

**第四层：给出自动化边界。** 使用度驱动建议（自动），影响面与业务确认驱动决策（人工）。**判据**：有没有一条"建议退役清单"的看板，以及其中被 Owner 确认的比例。

**第四层补一句"误区在哪"**：自动化在这里扩大的**是治理的容量，不是治理的判断力**（§5.3.5）——一个"使用度很低"的标签可能是**低频但关键**的（例如风控里的某个边界标签），因此**建议退役必须由 Owner 确认、不能自动执行**。书内他处有一组同形的具名度量做法可对照：`11-cross-cutting/07-audit-and-compliance/07-audit-and-compliance-section-8-11-7-数据治理体系融合与实践.md` 的「数据治理体系融合与实践」一节（原题库编号 11.7，见文件名）（该文件的第 8.3 节）记过用"数据消费率"衡量治理是否真被业务用起来、以及用"数据可被依赖程度"这类打分量化数据资产的可用性（两处均为"企业名 + 结论"式的【经验】档条目，本书无文档名）——**它们与本节"使用度埋点驱动建议退役"是同一形状**：**用可测量的量驱动治理动作，而不是用印象驱动**。

**第五层：把"先做退役"作为建议。** 在标签数还没上四位数时把使用度埋点与退役流程建起来，成本很低；等需要它时再建，面对的是"几千个没人认领的标签"。

**第五层要给出这条建议的经济理由**：本主题的成本是"**人力随标签数增长 + 存储随在线标签数增长**"（§4.6）——**每多一个在线标签就是一笔可计算的存储与人力增量**，因此退役不是"顺手清理"，它是唯一能让成本曲线掉头的动作。**判据**：按月核算治理与对账抽检的人力占团队比例，看它与标签数的比值是不是在上升（§6.7 把这一项列成"治理成本"的计量口径）。

**3. 常见陷阱**
- 直接删（或直接按"零使用"删）；
- 只标记 "deprecated" 但服务仍返回旧值；
- 没有使用度埋点却想谈退役；
- 忽略季节性使用的标签；
- 把影响分析做成人工盘点。
- 把"没有埋点"读成"没人用"——**这两个都表现为"数不出来"**，而处置完全相反（前者要补测，后者才谈退役）；
- 把上游字段下线引发的被动退役当成主动退役走同一条流程——**一条是影响分析驱动的处置，一条是治理判断**（§4.7 的演练行）；
- 用"归档之后还能查"当借口跳过归档可查性的验证——**申诉可能发生在很久之后**，归档要能按当时的时点与口径版本取回（§6.4）。

**4. 追问预测**
