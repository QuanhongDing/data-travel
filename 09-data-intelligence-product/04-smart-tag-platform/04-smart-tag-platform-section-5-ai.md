## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

1. **机制变了**：标签的**产出方式**或**消费方式**换了工作原理（例如从"规则 / 监督模型打标"变成"用 LLM 从非结构化数据里抽取"，或从"给人看"变成"作为 Agent 的语义层输入"）。**这类变化影响架构决策。**
2. **接口标准变了**：标签的**描述与交换格式**出现跨组织约定（标签的元数据标准、口径的可交换表达）。**这类变化影响"标签能不能被外部消费"。**
3. **只多了产品**：厂商把同一套能力包装成新名词（"标签中台""智能标签工厂""AI 标签引擎"）。**这类变化只在选型表里体现。**

判别方法仍然是那一句：**"换一家厂商，这条结论还成立吗？"**——不成立的是第 3 类。

**本主题的三类分布有一条特殊性**：**第 1 类（机制变了）的入口几乎只有一条**——**LLM 把"可判定的边界"从"结构化字段"扩展到了"非结构化内容"**。其余方向（实时化、服务化、治理）都在这条之外，属于**加固而非机制变化**（§5.3.6 专门讨论这一点）。**这条观察的实用推论**：判断一个标签类"新方向"要不要跟，先问"**它是不是让某类以前无法判定的事实变得可判定了**"——**是，则它是第 1 类**（要认真评估口径与可解释性）；**否，则它大概率是包装**。

### 5.2 判据与分级

沿用三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定、可预期**。

| 演进方向 | 级别 | 机制变了什么 | ① 正式条目 | ② 第三方生产案例 | ③ 接口稳定 |
| --- | --- | --- | --- | --- | --- |
| LLM 从非结构化数据抽取标签 | **L2** | 标签的**来源**从"结构化字段 + 规则"扩展到"文本 / 会话 / 文档" | 成立（各模型厂商的抽取与结构化输出都有正式条目） | **核不到**（企业很少公开"用 LLM 打的标签进了生产决策"的准确率） | 部分成立（抽取口径与输出格式仍在演进） |
| 标签作为 Agent 的语义层输入 | **L2** | 标签从"给人看 / 给规则用"变成"**给模型当上下文**" | 成立（语义层与工具调用的接入都有正式条目） | 核不到 | 部分成立 |
| 实时标签（流式产出 + 在线服务） | **L2** | 判定从"按天批算"变成"随事件更新" | 成立（流引擎与在线特征 / 标签服务均为正式条目） | **核不到**（实时与离线的逐实体一致性几乎无人公开） | 成立（服务接口稳定） |
| 标签口径的可交换表达 | **L3** | 口径从"平台私有配置"变成"可跨平台交换的定义" | 只有提案与局部实践 | 核不到 | 不成立（无通行做法） |
| 标签的自动发现与推荐 | **L3** | 从"人工提需求建标签"变成"系统建议该建哪些标签" | 只有产品演示 | 核不到 | 不成立（价值口径各家不同） |
| 向量化标签（embedding 作为标签值） | **L2** | 标签取值从"枚举 / 数值"扩展到"向量" | 成立（向量检索与相似度接口为正式条目） | 核不到 | 部分成立（语义空间随模型版本漂移） |
| 标签治理的自动化（准入 / 退役） | **L2** | 从"人工评审"变成"按度量自动建议" | 成立（数据目录与质量平台的正式条目） | 核不到 | 成立（度量接口稳定） |
| 差分隐私标签 / 合成人群 | **L3** | 标签与其下游动作在隐私预算下产出 | 只有研究与应用原型 | 核不到 | 不成立（预算口径与应用形态各不相同） |

**本节没有一行达到 L1**——卡点全部在 ②：**标签的生产案例几乎都是建设方自述**（"我们用了多少标签、提升了多少转化"），而**本主题真正需要的证据是"标签的准确率与不当打标的代价"**，后者几乎没人公开。这个空缺有一条具体的解释：**标签的准确率需要人工核对，而核对结果是敏感信息**（它直接暴露了"系统判错过多少人"）。**因此本主题的成熟度判断仍要回到内部判据**：**不看别人用得怎么样，看你自己的抽检结果能不能支撑"可信"这个等级。**

**怎么用这张表（三条动作）**：

- **凡是把"来源"扩展到非结构化的方向，先解决可解释性**——它带来的是"以前判不了的现在能判"，但**判定的可复述性会下降**（§5.3.1），因此必须先有抽检与置信度，再谈上线。
- **凡是被 Agent / 模型消费的方向，先把"缺失语义"定义清楚**——模型不像人，它不会对"我不知道"保持沉默（§5.3.2）。
- **L3 不进架构约束**——口径交换格式、标签自动发现、隐私化标签都还没有通行做法。

### 5.3 演进方向逐条拆解（核心节）

下面六个方向（§5.3.1–§5.3.6）按**同一套六线结构**写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**（判定方法与适用条件另列）。它们各自的级别见 §5.2 的那张表——**表给结论，本节给机制**；只写收益不写代价的方向，在评审时应被直接打回。**其中 §5.3.3、§5.3.5、§5.3.6 会明说"机制与 AI 无关"**：把与 AI 无关的那一半标出来，是为了不让"加固"被当成"新机制"立项。§5.3.6 再把这一套反过来用：本节没列到的新名词，先进那里按 §5.1 的三类判据自判。

#### 5.3.1 LLM 抽取标签：来源扩展了，可复述性下降了

- **旧做法与它的卡点**：标签的判定输入是"**结构化字段 + 显式规则**"（§3.2.1）。卡点有两处：**其一，有一整类事实从原理上判不了**——"是不是在抱怨物流""是不是在问退换货政策"只存在于客服会话、销售记录、访谈、工单文本里，结构化字段里没有对应的列；**其二，补字段这条路走不通**——把这些文本人工标注成字段，成本随会话量线性增长，且标注口径本身无法复述。因此这类判定在 AI 之前不是"做得差"，而是**根本没有人做**。

- **AI 改变了什么机制**：判定的**输入来源**从"结构化字段"扩到**非结构化内容**，判定动作从"执行一条显式规则"换成"**由模型对一段文本给出类别与依据片段**"。**换掉的是判定输入的来源，不是判定的目的**——标签要表达的东西没变（"这位客户属于哪一类"），变的是"从哪儿看出来"和"谁来做这个判断"。它正是本节唯一那条真正的机制入口（§5.1）。

- **由此得到的**：因为文本本身可以被读，**"以前判不了的这一类"第一次可判**——这正是 §5.1 那条判别句的正面例子；又因为抽取结果可以回指到原文片段，**依据第一次可以被引用**：业务拿到的不是"模型说是"，而是"原话是这一句"。

- **由此付出的**：三条，都要提前量。① **抽检成本上升一个量级**——结构化标签抽检可以机械化（对得上就对得上），LLM 标签的抽检需要人工判断语义（§5.2 三条动作的第一条）；② **可复述性下降**——传统标签能说"因为你登录了 12 次"，抽取标签只能回答"用了哪个模型版本、依据哪段文本、置信度多少"，即从**可复述退到可追溯**（§3.2.2 的同一条区分）；**且不确定性必须传到下游**——"置信度偏低的价格敏感"与"置信度很高的价格敏感"在决策上不是一回事，**丢掉置信度等于逼下游按二值处理**；③ **漂移是静默的**——客服话术一调整、新模板一上线，抽取结果的覆盖率与分布会慢慢移动，不设监控看不出来。因此口径卡必须新增三样：**模型版本、原文片段引用（回指）、置信度**——**这三样不是可选项**，没有它们，标签一旦进入"影响人的待遇"的路径就没有申诉的抓手。

- **证据与来源**：【经验】"抽取出来的标签准确率如何、不适当地打标的比例多少"正是没人公开的部分，本节因此不给文档名与年份。【公开】"把非结构化内容交给模型判断"有正式条目支撑，但那是"能力存在"的证据，**不是"用它打标进生产是安全的"的证据**——判据①成立不能替代判据②（来源：本主题 §5.1 第 1 类与 §5.2 的分级表）。

- **成熟度**：**L2**。① 成立（抽取与结构化输出的 API 都是正式条目）；**② 核不到**——这一条尤其致命，本主题真正需要的是"抽取标签准确率与不当打标比例"，而这正是没人公开的部分；③ 部分成立（抽取口径与输出格式仍在演进）。**L2 的动作是"可试点，但自带退出条件"**（§5.7 第 2 条）。

- **判定方法**：取一个已经或打算用 LLM 抽的标签，**走一次申诉流程**——能不能取回"当时依据的是哪段文本、用了哪个模型版本、置信度多少"？三样缺任何一样，它就只能停在试运行等级。

- **什么时候值得做**：需要判定的那类事实**只存在于文本里**（会话、工单、访谈），而它又会影响人的待遇或进决策路径时——这时它是唯一解。

- **什么时候不值得做**：规则已经能判的那一部分——**用模型去做规则能做的事，只会引入不确定性而得不到新能力**（§5.5 第 2 条）。

#### 5.3.2 标签作为 Agent 的语义层输入：从"给人看"到"给模型用"

- **旧做法与它的卡点**：标签的消费者是**人**（报表、看板）与**规则引擎**（`if tag.x == 'high'`）。卡点是**"取值域与缺失语义"只存在于人脑子里**——人写 `if` 之前会去看"高价值"有哪几档、没有值的时候是什么，而这个"看一眼"的动作**无法被自动化**：它写在文档里、口头约定里，或者根本没人写下来。

- **AI 改变了什么机制**：消费者里多了一类"**会自己把标签组合起来推断**"的模型（例如问数 Agent 需要知道"高价值用户"这一维度的取值域）。**换掉的不是标签本身，而是"谁在消费它"**——所以它偏第 2 类（接口变了）；但**有一处是第 1 类**：模型会主动组合（"他既是高价值又是价格敏感，那多半会等促销"），而人不会这么用——这条组合能力带来了新的失效形态。

- **由此得到的**：因为模型是按字面执行的消费者，**"缺失语义"从体验问题变成正确性问题**——人对"标签没值"会保持沉默，模型不会；如果接口把缺失返回成一个默认值，模型会把它当事实继续推理，最后产出一个看起来合理、基于错误前提的结论。因此给 Agent 用的标签接口**必须在返回里区分三种状态**：`符合` / `不符合` / `无值`（§4.5 模板 2 的判据在生产场景里就是为这条服务的）。

- **由此付出的**：① **取值域必须机器可读地暴露**（否则模型只能猜"高价值"有哪几档）——这条把口径层的取值域变成了接口的一部分；② **口径版本要随回答留痕**——Agent 的结论如果基于某个标签，"当时是哪一版口径"必须可回溯；③ **模型会放大错误的组合**——一个标签打错，模型可能基于它再推出三个结论，**错误被组合放大**而不是被平均掉。

- **证据与来源**：【经验】语义层与工具调用的接入都有正式条目，但"模型误读缺失值造成多大代价"没有第三方数据，本节不点名任何产品。【公开】这条要求在书内有可核验落点——§4.5 模板 2 的 `on_missing` / `on_timeout` 与返回三元组就是它的形态（来源：本主题 §4.5 模板 2、§5.2 的第 2 条动作）。

- **成熟度**：**L2**。① 成立（语义层与工具调用都有正式条目）；② 核不到；③ 部分成立（"缺失怎么表达"各家不同，没有统一接口）。

- **判定方法**：检查一次你的标签接口——**它区分"不符合"与"无值"吗**？如果两者都返回 `false` 或空字符串，那么任何消费它的模型都在把"未覆盖"当成"不符合"在用。

- **什么时候值得做**：标签要被模型 / Agent / 规则引擎消费时——尤其是它还要影响对人的待遇时。

- **什么时候不值得做**：标签只给人看报表时——这时缺失语义可以写在文档里，接口改造换不回收益。

#### 5.3.3 实时标签：从"按天批算"到"随事件更新"

- **旧做法与它的卡点**：标签按天批算，T+1 出数（§1.4 的宽表与标签工厂阶段）。卡点在**"刚刚发生过"这类判定给不出来**——批算的产物是"昨天为止的状态"，而风控与推荐要的是"这一刻的状态"（§3.1 约束 3）。把它切成小时批只能缩短延迟，**改变不了"边界就在那儿"这件事**。

- **AI 改变了什么机制**：**机制与 AI 无关**——它换掉的是产线的执行方式（批引擎产出 → 流引擎产出 + 在线服务读最新值），判定函数本身不变。**之所以仍列在本节**：一是它与 AI 消费方（Agent 取数、在线推荐与风控）同时出现，容易被误读成 AI 带来的新能力；二是它的难点——**口径一致从"跑完对一次"变成"必须持续保证"**——恰恰决定上面两条 AI 方向能不能落地：没有实时标签，Agent 拿到的永远是昨天的上下文。

- **由此得到的**：**一致性从一个可以定期检查的性质，变成必须持续保证的性质**——批算可以"跑完对一次"，流侧的漂移却是渐进的（迟到数据、状态重建、算子升级都会引入差异），因此必须有**常态化逐实体对账**（§2.2 的 `u = 0`、§4.5 模板 3）。由此推出一条与直觉相反的结论：**实时标签的准入成本高于离线标签**——它多出一套要常备人力的对账任务（§5.2 表里判据②核不到的原因正在这里）。

- **由此付出的**：① **流侧的状态与迟到处理更难**（乱序、重放、状态大小），且**同源的表达力受双引擎限制**（§4.2（2）），于是必然有一部分标签只能显式声明"仅 T+1"；② **"最新"与"快照"两种语义的冲突在这里最尖锐**——风控要快照（可申诉）、推荐要最新（新鲜），**同一标签名下的两种语义是两个资产**（§2.2）；③ **流任务常驻的成本**——批任务用完即停，流任务是 7×24 占着资源的常驻进程（这条的成本形状见 [Ch3 §09 实时计算](../../03-data-stack/09-realtime-compute/09-realtime-compute.md)）。

- **证据与来源**：【经验】**实时与离线的逐实体一致性几乎无人公开**，而这恰是实时标签唯一会出事的地方，本节因此不给文档名与年份。【公开】流引擎与在线服务都是正式条目，可在 `03-data-stack/09-realtime-compute` 的 §4.3 工具链表核到（"流处理引擎"一行以 Apache Flink / Spark Structured Streaming / Kafka Streams 为主）；那一行给的是运维维度的判据，本节不重复。**本主题相对它新增的只有一条**：**口径一致从"跑完对一次"变成"必须持续保证"**，因此实时标签必须多带一套常态化逐实体对账任务（§4.5 模板 3），而这是"实时"这个方向真正的准入成本。

- **成熟度**：**L2**。① 成立（流引擎与在线服务均为正式条目）；**② 核不到**（实时与离线的逐实体一致性几乎无人公开）；③ 成立（服务接口稳定）。

- **判定方法**：统计两个数——**你有多少实时标签**，以及**其中有多少做过逐实体对账**。第二个数明显小于第一个时，说明你的实时标签处在"看起来对"的状态。

- **什么时候值得做**：出现"刚刚发生过"的判定需求（实时风控、推荐排序、实时触达）时；且要先有离线侧的历史数据可对账（§4.1 的反面：先实时后离线，一致性无从验证）。

- **什么时候不值得做**：业务对"昨天为止"就满意时——流任务的常驻成本与常态化对账是两笔不会自己消失的投入。

#### 5.3.4 向量化标签：取值域从枚举扩展到向量

- **旧做法与它的卡点**：标签值域是枚举 / 数值（`low/mid/high`、`0.73`）。卡点在**有些维度本身没有离散取值**——"兴趣偏好""风格接近度"用几个类目穷尽不了，硬切成枚举必然在边界上失真；换成一串文本又**既不能比较也不能聚合**。

- **AI 改变了什么机制**：标签值从"枚举 / 数值"扩到**向量**，判定它所用的"相等"判据随之从"值相等"换成"**距离小于阈值**"。**换掉的是标签值的类型，以及定义在它之上的运算**——这是一条真正改了"什么能被判定"的方向（按 §5.1 的三类划分属第 1 类，归属见 §5.3.6）。

- **由此得到的**：因为相似度可以在连续空间里计算，**"难离散的维度"第一次可被表达**（兴趣偏好、风格接近度），下游通过近邻而非等值来消费它；相应地，"向量检索与相似度"有了稳定的接口形态（§5.2 表判据①）。

- **由此付出的**：① **不可申诉性更强**——"为什么把我和这组人归在一起"只能给出距离与最近邻，比"为什么给我打这个标"更难解释；② **引入了一条传统标签没有的依赖：嵌入模型的版本**——传统标签口径变了要重算，而向量标签**换一次嵌入模型，所有向量的可比性都会变**（不只是重算，而是新旧向量不可混用），因此必须与嵌入模型版本绑定、升级即全量重建，**这条推论决定了它的成本形状是台阶形，而不是随实体数平摊**；③ **存储与计算**（向量存储远大于枚举）与**阈值不可移植**（距离阈值在不同模型之间不能直接搬用）。

- **证据与来源**：【经验】"向量标签的下游行为如何被一次模型升级静默改变"没有第三方数据，本节不点名产品与版本。【公开】向量这一族的成本形状在书内他处有可核验落点：`02-data-science/01-feature-store` 的 §4.8 演进路线把"换 embedding 的全量向量重算"列为多团队平台化阶段变贵的三件事之一（可在该节自行核验），与本主题 §4.6 的口径一致。

- **成熟度**：**L2**。① 成立（向量检索与相似度接口为正式条目）；② 核不到；③ 部分成立（**语义空间随模型版本漂移**）。

- **判定方法**：查一次你的标签里有没有向量型的；若有，问它**有没有绑定嵌入模型版本**——没有绑定，就意味着一次模型升级会静默改变所有下游行为。

- **什么时候值得做**：需要表达的维度本身没有离散取值，且下游能用"相似 / 近邻"消费它时。

- **什么时候不值得做**：这个维度其实能切成枚举、下游做的是等值判断或聚合时——向量会把它变得既贵又不可申诉。

#### 5.3.5 标签治理的自动化：把"人工评审"拆成可自动化的两步

- **旧做法与它的卡点**：准入与退役全靠人工评审——开会看"这个标签还有没有人用、质量怎么样"。卡点**不在判断本身，而在材料的供给**：评审要的四项（使用度、覆盖率、一致性、准确率）**没有任何一项被自动采集**，于是每次评审都是一次临时统计；而**评审会随标签数线性变长，长到一定程度就流于形式**（§4.6 把治理列为"随标签数线性增长"的人力项之一；§6.3 给出了"治理评审会因为清单太长而流于形式"的实际症状）。

- **AI 改变了什么机制**：**机制与 AI 无关**——它换掉的是治理动作的落点：从"开一次评审会做判断"换成"**度量先算好、系统出建议清单、人只确认例外**"。判定标准（使用度低、质量不达标）没变，变的是**谁来算、什么时候算**。**之所以仍列在本节**：它常被打包进"AI 治理"的话术里，而当 AI 能力会掩盖它真正的前提——**埋点**；另外，"度量先行、建议自动化"这一形态在数据目录与质量平台上确有正式条目（§5.2 表判据①）。

- **由此得到的**：因为度量被常态化采集，**治理从"评审会"变成"看板 + 例外处理"**；又因为使用度可自动测量、而"能不能退役"必须人工确认（§3.2.7 已把两者分开），自动化恰好落在它能负责的那一半——**它扩大的是治理的容量，不是治理的判断力**。

- **由此付出的**：① **度量会误导**——一个"使用度很低"的标签可能是**低频但关键**（例如欺诈识别的某个边界标签），因此建议退役必须由 Owner 确认，**不能自动执行**；② **准入的可自动化程度低**——准确率可以抽检自动化，但"这个标签能不能进决策路径"是业务判断（§3.2.6 代价①）；③ **它的前提是先有埋点**——没有使用度埋点，任何"自动建议退役"都是无源之水，而埋点必须在标签数还少的时候建（§5.7 第 5 条）。

- **证据与来源**：【经验】"自动化治理省下多少人力"没有第三方数据，本节不点名产品与版本。【公开】这类能力的落地形态在书内他处有可核验落点：`11-cross-cutting/01-data-quality` 的 §4.3 工具链表把断言引擎（Great Expectations / Soda Core / Deequ / Apache Griffin 等）与"血缘与元数据（OpenLineage / DataHub）"分列两行，并把后者定位为"定位用"——标签的四个度量（覆盖率 / 一致性 / 新鲜度 / 准确率）正是挂在这一类物上的。

- **成熟度**：**L2**。① 成立（数据目录与质量平台都有相应条目）；② 核不到；③ 成立（度量接口稳定）。**它在本主题里的价值格外高**，因为治理成本恰恰随标签数线性增长（§4.6）。

- **判定方法**：查一下**你有没有使用度埋点**（每个标签近 N 天被查询 / 被圈选的次数）。没有就先补它——它是"标签数上到四位数之后还能治理"的唯一前提。

- **什么时候值得做**：标签数已上百、评审开始排不过来时；**但埋点要提前做**——等到需要时再补，面对的是"几千个没人认领的标签"（§5.7 第 5 条）。

- **什么时候不值得做**：标签数还在个位数、提需求的人就是 Owner 的阶段——这时的"自动化治理"没有对象。

#### 5.3.6 加固类方向：不要把"加厚"误当成"新机制"

- **旧做法与它的卡点**：旧做法是**每个新名词都单独立项**——实时化、服务化、治理自动化、口径交换格式各自排期、各自选型。卡点在于这四条**都落在既有部件上**（实时是流引擎的事、服务是接口层的事、治理是度量与流程的事、口径交换是元数据格式的事），单独立项换来的是重复建设；更贵的一处在评估层——把它们计入"技术前瞻性"，会同时**低估真正需要长期投入的那一项：口径层**（§5.8 把这一条写成小结的第一句）。

- **AI 改变了什么机制**：**机制与 AI 无关**——这四个方向没有一条改变"标签是什么"，它们改变的是标签**被产出的速度**（实时化）、**被消费的方式**（服务化）、**被维护的成本**（治理自动化）与**定义能不能被交换**（口径交换格式）。之所以仍列在本节：它们常与 §5.3.1–§5.3.5 并列出现在"AI 标签中台"一类话术里，**不单独标出来就会被当成机制变化立项**（§5.1 已把这条写成判别句的实用推论）。

- **由此得到的**：一条可直接用的筛法——**回到 §5.1 的三类判据**：它是不是让某类"以前无法判定的事实"变得可判定了（第 1 类）？是不是出现了让标签能被外部消费的跨组织约定（第 2 类）？还是换一家厂商这条结论依旧成立（第 3 类）？**按这条筛一遍本主题**：唯一算"机制变了"的是 §5.3.1（来源扩展到非结构化）与 §5.3.4（取值域扩展到向量）——**它们改的是"什么能被判定"**；**其余都是加固**。

- **由此付出的**：把加固当加固处理也有代价——它们不会进架构决策，只会以"顺手补一下"的形式出现，而这四条各自的失效点**恰恰都是静默的**（实时侧的对账漂移、服务侧的"未覆盖被当成不符合"、治理侧的没有埋点就无从退役），不立项就更没人盯。反过来把加固当新机制处理，代价是排期被重复建设占掉、评估上高估自身前瞻性——而这两笔代价都不报错，只在下一个真正需要长期投入的项（口径层）被推迟时才显形。

- **证据与来源**：【经验】"其余都是加固"是本节对机制位置的判断，无具名出处、不给年份。【公开】四条各自的正式条目与分级见 §5.2 的那张表（实时标签、Agent 语义层、治理自动化三行均为 L2；口径的可交换表达为 L3）；它们在本主题里的落地阶段见 §4.8 的 1 → 10（双产线与服务）与 10 → 100（治理与自服务）。

- **成熟度**：**按单条引 §5.2 的表，不新判级**——实时化（§5.3.3）、服务化（§5.3.2）、治理自动化（§5.3.5）均为 **L2**；口径交换格式为 **L3**、不进架构约束。三条判据逐条说：① 前三条的正式条目成立（流引擎与在线服务、语义层与工具调用、数据目录与质量平台），口径交换格式只有提案与局部实践；② 全部核不到；③ 实时化与服务化为部分成立到成立，治理自动化为成立，口径交换格式不成立（无通行做法）。

### 5.4 与本主题既有栈的接口在哪

标签平台的每一次"接入"，本质都是**把一个判定权交给别人、或从一个来源取走事实**；接口就是这次交接的载体。

| 既有栈 | 接口 | 交接物（谁产出、谁消费） | 谁改 |
| --- | --- | --- | --- |
| [Ch1 §09 OneID](../../01-modeling/09-one-id/09-one-id.md) | 实体唯一标识与归并规则 | OneID 产出 `unified_entity_id`；标签平台消费它做实体级产出 | 标签平台按统一实体产出 |
| [Ch3 数据栈](../../03-data-stack/README.md) | 明细与汇总表（标签的输入） | 数仓产出明细；标签平台产出实体级标签表 | 标签平台加"未归属桶"与守恒校验 |
| [Ch2 §01 特征平台](../../02-data-science/01-feature-store/01-feature-store.md) | 模型标签的特征输入 | 特征平台产出 Point-in-Time 正确的特征；标签平台消费它做模型打标 | 标签平台记录模型版本与置信度 |
| [Ch7 §03 资产管理](../../07-agent-evolution/03-asset-management/03-asset-management.md) | 标签作为一类资产 | 标签平台产出标签的登记项（Owner / 等级 / 版本）；资产管理消费它 | 双方共用一套资产元数据 |
| [Ch9 §01 AI 计算](../01-ai-compute/01-ai-compute.md) / [§02 决策智能](../02-decision-intelligence/02-decision-intelligence.md) | 标签作为模型 / 决策的输入 | 标签平台产出"可信级标签"；消费侧只读可信级 | 消费侧走服务而非直连表 |

**这张表的读法**：**接口的两端都必须有交接物**，只有"我们打通了"而没有具体产物的，是没打通。上表右列每一项都是**今天可以检查是否存在**的东西——例如"标签平台是否真的产出了四个度量（覆盖率 / 一致性 / 新鲜度 / 准确率）"，检查方法就是问它要一张按标签分组的度量表。

### 5.5 被过度宣传的部分

1. **"有了标签平台，标签就能自动生产"**：自动化的边界只到"**按口径产出**"，而**口径本身必须由人（业务）确认**——分档边界、空值语义、时间语义这三件都无法自动化。**可核验的判据**：看新增一个标签的流程里，有几处需要业务确认——**数量为 0，说明口径没有被形式化，只是被默认了**。
2. **"LLM 打标可以替代人工规则"**：它替代的是**"以前无法判定的那部分"**，而不是"规则能判的那部分"。**混用的正确形态是**：确定性规则（硬信号）在前、模型抽取在后（同 [Ch10 §02 §3.2.5](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的规则 + 模型分工）。**用模型去做规则能做的事，只会引入不确定性而得不到新能力。**
3. **"实时标签只是把批任务改成流任务"**：它同时要求**常态化逐实体对账**与**同源的表达限制**——这两件事的成本常常超过流任务本身。
4. **"标签越多，画像越准"**：标签的边际价值递减，而**治理成本线性上升**——这是本主题唯一一条"加得越多越差"的曲线（§4.6）。
5. **"向量标签让标签更智能"**：它让"难离散的维度可被表达"，代价是**可申诉性更弱、且与嵌入模型版本强绑定**——换一次模型等于全量重建。

### 5.6 未来 3–5 年：可证伪的预测

每条都给出**被证伪的信号**（出现即说明判断错了）：

| 预测 | 被证伪的信号 |
| --- | --- |
| 标签的"来源扩展"（LLM 抽取）会**长期停在试运行等级**，难以进入受监管场景的生产决策 | 两年后大量 LLM 抽取的标签直接进入信贷 / 风控 / 准入这类决策，且没有人工复核环节 |
| "快照语义"会成为标签的一等属性，而不是实现细节 | 主流平台仍只提供"最新值"接口，且不存储历史标签值 |
| 标签的准入等级会像数据分级一样成为**强制登记项** | 主流平台仍允许"没有等级"的标签被生产路径消费 |
| 逐实体对账会取代"比人数"成为一致性验证的标准做法 | 主流实践仍以"两边人数一致"作为一致性证据 |
| 标签治理的主要瓶颈会从"技术"转向"业务确认的排队时间" | 新增标签的耗时中，技术实现占主导，业务确认不构成等待 |

**这五条全部是【经验】档**：它们是对机制与组织行为的判断，无具名出处、无推导链——**请按"可被证伪"使用，而不是当结论**。

**怎么用这份预测表**：不要用它做技术选型，用它做**反向检查**——每隔半年回来看一次"被证伪的信号"有没有出现。**第五条尤其值得盯**：如果瓶颈真的转向"业务确认的排队时间"，那么现在能做的准备是**把口径卡标准化**（§4.5 模板 1），让业务确认从"讨论"变成"勾选"——这件事今天做成本很低，而它是唯一能缓解那条瓶颈的做法。

### 5.7 给架构师的行动建议

1. **今年就该做**：统一主实体 + 一个标签的口径卡（五个边界写全）+ 口径层配置化。这三件不依赖任何前沿判断，且是其余一切的前提。
2. **可以试点（每条自带退出条件）**：LLM 抽取标签（退出条件：答不出"怎么申诉"，或抽检成本无法持续）；实时标签（退出条件：逐实体对账跑不起来，或同源表达力不足）；向量标签（退出条件：嵌入模型版本无法绑定，或距离阈值在跨模型上不可移植）。
3. **先别投**：标签口径的跨平台交换格式、标签自动发现、隐私化标签。等出现可比较的通行做法。
4. **无论哪条**：把"**同一标签多实现的逐实体不一致数**"作为这一块的第一条 KPI——它同时是口径层、服务层与治理层健康状况的共同语言（理想值是 0）。
5. **一条反直觉的**：**先做退役，再做新增**——标签平台的容量不是"能建多少"，而是"**能维护多少**"。在标签数还没上四位数时就把使用度埋点与退役流程建起来，成本很低；等到需要它时再建，你要面对的是"几千个没人认领的标签"。

### 5.8 小结

> 本节小结：AI 时代对标签平台的改变**只有两条是机制性的**——**来源从结构化扩展到非结构化（§5.3.1）**、**取值域从枚举扩展到向量（§5.3.4）**；其余方向（实时化、服务化、治理自动化、口径交换）都是加固，**把它们当新机制会低估真正需要长期投入的那一项：口径层**。本节没有一行达到 L1，卡点在 ② 上有一条具体的解释——**标签准确率需要人工核对，而核对结果直接暴露"系统判错过多少人"，因此几乎没人公开**；这决定了本主题的成熟度判断必须回到内部判据：**看你的抽检结果能不能支撑"可信"这个等级**。**给读者的动作**：先统一实体、写一张口径卡、把口径层配置化；然后才谈 LLM 抽取与实时化。

> 💡 **思考锚点**：如果你的标签体系里已经（或即将）有 LLM 抽取出来的标签，做一件事——**取一个这样的标签，尝试走一次"申诉流程"**：你能不能取回"当时依据的是哪段文本、用了哪个模型版本、置信度多少"？三样里缺任何一样，这个标签现在就只能停在试运行等级；**而你打算补哪一样，决定它多久之后能进入生产**。
