## 4. 工程实现

### 4.1 落地步骤

标签平台有一条与其它主题不同的性质：**它的第一个可交付物不是服务，而是口径**——因为口径一旦散进多份实现，后补口径的代价是"回头统一 N 份代码"。

**Step 1：把实体统一做掉（先做这个，哪怕只覆盖主实体）**
选一个主实体（通常是用户），确认唯一标识与归并规则。**判据**：抽 100 个实体，归并率是已知数。**为什么第一步是它**：没有统一实体，标签会按来源分裂，"覆盖率"这个指标从一开始就是假的。

**Step 2：把一个标签的口径形式化，并写清五个边界**
挑一个业务最关心的标签（"高价值用户"之类），把它的口径写成**可执行的定义**，并显式写清五个边界：**空值 vs 零、迟到数据、实体键缺失、时间语义（快照 / 最新）、分档边界**。**判据**：三分钟能讲清它的口径与依据。**这一步的产出物是模板（§4.5 模板 1），不是代码**。

**Step 3：把口径层建起来，让新标签不再改 ETL**
口径表达式 + 数据源 + 调度 + 输出表，全部配置化。**判据**：新增一个事实标签，需要改动的代码行数为 0。

**Step 4：建逐实体的对账任务**
同一标签的多份实现，取同一批实体逐个比对（§2.2 的 `u = 0`）。**判据**：对账任务常态化（不是一次性验证），且不一致样本能定位到边界。

**Step 5：标签服务（点查 + 批量分离）与降级策略**
点查走缓存 + 主键索引；批量按选择率选执行计划；**超时、降级、缓存失效三件都要写下来**。**判据**：数据侧抖动时，关键路径消费方的行为是事先定义的。

**Step 6：准入等级与生产读取收口**
定义等级与准入条件；把生产决策的读取路径收口到服务；**口径变更自动退回试运行**。**判据**：试运行标签无法从生产路径读到。

**Step 7：使用度埋点与退役流程**
记录每个标签近 N 天被查询 / 被圈选的次数；退役走"影响分析 → 通知 → 观察期 → 归档"。**判据**：退役标签在服务上返回明确错误。

**顺序的反面（最常见的错误）**：**先建标签服务、后建口径层**——服务会把当前散在各处的实现"封装"起来，于是**不一致被固化进了接口**（调用方拿到的是"某个实现的值"，而它以为是"标签的值"）；反过来，口径先行时，服务只是口径的一个出口。**第二条反面**：先做实时、后做离线——实时侧没有历史数据可对账，一致性无从验证。

### 4.2 关键技术点

**（1）口径表达式（口径层的载体）**

```yaml
# 一个标签的口径定义：把"怎么算"写成可执行、可版本化的东西
tag: high_value_user
entity: user                      # 实体类型（依赖 OneID）
type: factual                     # factual | model | predictive
version: 7                        # 口径版本（改口径必须递增，并触发退回试运行）
level: trusted                    # 准入等级：trial | trusted | retired
owner: user-growth@

time_semantics: snapshot          # snapshot（按 event_time 取）/ latest（取最新一次）
freshness_sla: "T+1 08:00"        # 新鲜度承诺

source:
  table: dws_user_behavior_daily
  entity_key: unified_user_id
  partition_by: dt

caliber:                          # 判定表达式 —— 这一项是标签与字段的分界
  window: "近 30 天"
  expr: "pay_amt_30d >= 1000 AND login_cnt_30d >= 10"
  bins:                           # 分档边界（业务确认过，随口径版本化）
    - {name: low,  cond: "pay_amt_30d < 200"}
    - {name: mid,  cond: "200 <= pay_amt_30d < 1000"}
    - {name: high, cond: "pay_amt_30d >= 1000"}

edge_cases:                       # 五个边界必须显式，不能留给实现
  empty_vs_zero: "无记录 → 无值（不是 0）"        # 边界①
  late_data: "分区封板后到达的数据触发重算并记重算版本"  # 边界②
  missing_key: "entity_key 为空 → 计入未归属桶"      # 边界③
  # 边界④ 是 time_semantics；边界⑤ 是 bins
```

**判据**：这份 YAML 能回答"三分钟讲清口径"里的每一个问题——**讲不清的部分，就是还没被形式化的部分**。

**机制**：可申诉、可复算的来源见 §3.2.1，本节不重复推导。这里接着写它留在实施层的后果：**边界进了表达式之后，"改边界"就从改代码变成一次带版本号的配置变更**——于是它可回滚、可通知、可退回试运行，下面（4）的四件联动正是为这个动作准备的；反过来说，**边界只要还留在表达式之外，这一整套变更管理就管不到它**。

**失效条件**：**当分档边界留在表达式之外、各实现各写一份时，这份口径定义会退化成"引用了边界、却没有定义边界"的载体**——版本号递增了，各实现的边界却没跟着变，因为边界不在版本管辖范围内；此时表达式看起来形式化了，可核验的却只剩阈值本身，分档那一格永远是空的。症状是**不一致集中在边界用户上**（§2.2 的 `u` 算式；边界差异的后果见 §3.2.1 失效点）——业务恰好看的就是这些人。第二个信号是没人能三分钟讲清它怎么算：**讲不清的那一格，通常正是没被写进表达式的分档边界**。

**档位**：【经验：分档粒度随业务能确认的边界数变——边界越多判定越细，但每加一档都要业务再确认一次，无通用档数】

**（2）离线 / 在线同源的表达限制**

同源要求口径能被两种引擎执行，因此**必须限制表达力**。可用的取舍：

| 取舍 | 做法 | 代价 |
| --- | --- | --- |
| 限制到 SQL 子集 | 只允许双引擎都支持的操作（过滤、聚合、窗口函数） | 复杂判定要拆成多个简单标签组合 |
| 引入 DSL | 自研表达式语言，编译到两种引擎 | 需要编译器与语义一致性测试（成本最高） |
| 双实现 + 强制对账 | 允许两份实现，但把逐实体对账作为门禁 | 一致性靠流程保证，最脆弱 |

**判据**：**先把标签按表达力分两类**——"双引擎可表达"的走同源；"只有批引擎能表达"的（复杂 UDF、图计算）**显式声明为"仅 T+1"**，而不是悄悄让它只有一个实现。

**机制**：同源为什么能压住漂移，见 §3.2.4，本节不重复推导。这里只接它在实施层规定的动作：**口径的表达能力以"两侧引擎表达力的交集"为上界**——一个标签能不能实时由这个交集决定，而不是由其中任一侧的引擎能力决定；"仅 T+1"必须写进口径而不能靠默认，原因就在这里。

**失效条件**：**当同源落地成"双实现 + 强制对账"这一档取舍时，一致性就从结构保证退化成流程保证**——表达式只有一份，但翻译到两侧引擎的代码各有各的边界处理（空值、迟到、时间边界），于是唯一能检出分叉的手段是逐实体对账；对账一旦从常设任务退回一次性验证，分叉就重新变成不可见。第二类同形信号是**离线与线上持续背离且幅度稳定**：稳定背离说明是系统性口径差异、不是数据波动——与同章 §01（AI 计算平台）§4.2 的 Feature Store 块是同一处失效面：那一侧写的是"在线侧被另一套代码重写"，这一侧写的是"两份实现分叉"。**两类都不报错。**

**档位**：对账的抽样与频次【经验：按"取同一批实体逐个比对、半天级动作"核算，频次随标签变更频率与在线消费方数量变，无通用值】

**（3）标签服务的三个必备件**

```text
① 点查：getTags(entity_id, tag_names) → 毫秒级
   - 缓存：按 (entity, tag, caliber_version) 建键；口径变更即整体失效
   - 缺失语义：返回 null 还是默认值？—— 必须显式（同 §4.2（1）的空值语义）
   - 超时 + 降级：用旧值 / 用默认值 / 放行 —— 由消费方声明

② 批量：select(entity_set, tag_conditions) → 秒到分钟级
   - 执行计划按选择率选（§2.3 的判据）
   - 结果带 (caliber_version, time_semantics, generated_at) 三元组

③ 写入：标签产出侧批量写
   - 先写新版再切指针（在线读到的是"某一版口径的完整结果"，不是半成品）
   - 判据：切换瞬间点查不会读到混合两版的结果
```

**机制**：点查与批量为什么必须分开，见 §3.2.5，本节不重复推导。这里接着写它留在实施层的后果：**分开设计等于两条独立的可用性预算**——点查这一侧要逐消费方声明降级语义（模板 2 的 `on_missing` / `on_timeout`），批量那一侧没有这条约束；把两者合成一个接口，等于让所有消费方被迫接受同一个预算，而那个预算由点查的延迟要求定。

**失效条件**：**当降级语义只被写下来、没有落到接口契约上时，降级的决定就被下推到每个调用方的代码里**——同一份策略在 N 个消费方里被实现 N 次且互不一致，服务侧却一切正常：真正失效的是"抖动时各消费方行为是否一致"这件事的可核验性。第二个信号是口径变更后点查长期返回旧值：因为缓存键里没有口径版本，而**这件事是静默的**（服务看起来一切正常）——§4.8 的 1 → 10 阶段把它列为"先坏的是什么"，正是为此。

**档位**：在线存储随"实体数 × 在线标签数"线性上升【推算：同 §4.6 的估算链 E × T_online × B × r，含键索引 1.5–2× 放大——量级随在线标签数变，无通用值；当它越过离线标签表时，正确的动作是把低频标签移出在线服务，而不是扩容】

**（4）口径变更的传播（最容易被漏的一环）**

口径变更要触发四件事：**版本号递增 → 准入等级退回试运行 → 缓存按版本失效 → 消费方收到变更通知**。**判据**：改一次口径，这四件在同一次操作里都发生了吗？**只做版本号递增**，结果是缓存继续返回旧值、生产路径继续用未验证的新口径——而**这四件里任何一件漏掉，变更管理就不成立**。

**机制**：等级为什么让"改口径"开始有代价，见 §3.2.6，本节不重复推导。这里只接它留在实施层的那一层：**四件联动里真正的价值在第二件**——它把"随手改口径"从一个零成本的配置修改，变成一次要重新走准入的动作，从而抑制它；**四件必须在同一次操作里发生，缺一件这条机制就退化成一次普通的版本记录**。

**失效条件**：**当四件里有一件靠"人记得做"而不是靠同一次操作落地时，先漏的通常不是版本号，而是"等级退回试运行"**——版本递增可以由口径配置承担（自动），等级退回却多半是另一个系统里的一次评审动作（人工），于是"改了口径的标签仍在生产路径上被消费"这件事**在任一侧都不报错**。它的观测口是 §4.1 Step 6 的判据（试运行标签无法从生产路径读到）与 §4.7 的"口径被误改"演练行：拿一个刚改过口径的标签，试它还能不能从生产路径取到。

**档位**：准入与复核的节奏【经验：随标签进入决策路径的范围、口径改动频率与消费方数量变，无通用周期数】

**（5）分群执行计划的可解释性**

执行计划要能回答"这次为什么用这个计划"。**最小的可解释形态**是一行日志：`plan=inverted_index(tag=A, sel=0.02) ∩ scan(B) → 候选 2.1 万`。**判据**：用户抱怨"圈选慢"时，能否指出是哪个条件的选择率估计错了。

**机制**：分群为什么不该被当成标签存，见 §3.2.8，本节不重复推导。这里接着写它留在实施层的后果：**可解释性必须由圈选引擎在查询那一刻产出**——标签是预计算的，"怎么算"已经落在口径卡里；而分群的"为什么用这个计划"只在执行时存在，所以实现层要留下的是带选择率的计划日志（上面那行 `plan=`），而不是一份描述文档。

**失效条件**：**当计划只存在于引擎的调试输出、没有被当成产出物留存时，"事后问计划"就答不出来**——圈选结果偏少或偏多时，无法区分是条件写错了、还是选择率估错了，唯一的应对是重跑与加机器。第二个信号与统计信息的新鲜度有关：刚迁进来的标签、还没建好的倒排索引，选择率会被估偏，而**估计错时计划照样返回正确结果、只是更慢**——它不报错，只体现为资源用量上升，此时该改的是计划而不是容量。

**档位**：倒排索引与全扫的交叉点【经验：随候选集规模、条件选择率与索引存储放大变，无通用选择率阈值】

### 4.3 工具链与平台

| 能力 | 自建 / 开源 | 产品化 | 选型要点 |
| --- | --- | --- | --- |
| 口径层 | 自建配置 + 调度；或复用指标平台的口径管理 | 标签平台产品 | **看它是否把口径当一等对象**（能不能导出、能不能版本化） |
| 批产出 | 数仓调度 + SQL（[Ch3 §12 调度](../../03-data-stack/12-scheduler/12-scheduler.md)） | —— | 复用既有调度，不要为标签单起一套 |
| 流产出 | 流引擎（[Ch3 §09 实时计算](../../03-data-stack/09-realtime-compute/09-realtime-compute.md)） | —— | 与批侧共用口径表达式是选型前提 |
| 标签服务 | 自建（缓存 + 索引） | 标签服务平台 | **看点查与批量是否分开**；看有没有降级语义 |
| 圈选引擎 | 自建（倒排 + 执行计划） | CDP / 分群产品 | 看**执行计划可解释**、结果带三元组 |
| 血缘 | 从口径表达式解析 | 数据目录附带 | 看**上游变更时能否自动列出受影响标签** |

**一条选型原则**：**口径的归属比服务的性能重要**。一个性能极好但口径留在产品内部的标签平台，会让你在"换个口径"时付出迁移全部标签的代价；而**口径能导出**的产品，性能差一点可以靠加缓存补。

### 4.4 存量迁移

**（1）存量宽表与脚本怎么办**

| 对象 | 处理 | 注意 |
| --- | --- | --- |
| 宽表里的标签列 | 逐个抽口径 → 写成配置 → 与原值**逐实体比对** | **必须逐实体**：宽表列与配置产出"人数相同"不能证明一致 |
| 散在 ETL 里的口径 | 解析出规则 → 归并为口径定义 | 归并时会出现"同一标签多份不同口径"，**此时问业务哪份为准** |
| 实时脚本 | 与离线口径**逐实体比对**后合入同源 | 不一致集中的边界条件要写进测试用例 |
| 无人维护的标签 | 先加使用度埋点 → 观察一个季度 → 建议退役 | **不要直接删**：可能有你不知道的消费方 |

**（2）迁移的三条验收判据**

- **逐实体一致**：抽 N 个实体，宽表旧值与新口径产出值完全相同（不允许"接近"）。
- **守恒**：明细总量 = 各实体标签用量 + 未归属用量（§2.3 的边界③）。
- **可申诉**：随机抽一个实体，能给出它的标签值、口径版本、依据字段。

### 4.5 模板 / 示例

**模板 1：标签口径卡（每个标签一张，它就是"三分钟讲清口径"的载体）**

```text
| 项 | 内容 |
| --- | --- |
| 标签名 / 实体 | high_value_user / user |
| 类型 | factual |
| 口径（可执行） | 近 30 天 pay_amt >= 1000 AND login_cnt >= 10 |
| 分档边界（业务确认） | low <200 / mid 200-1000 / high >=1000 |
| 时间语义 | snapshot（按 dt 取）；新鲜度 SLA：T+1 08:00 |
| 空值语义 | 无记录 → 无值（不是 0） |
| 迟到数据 | 分区封板后到达 → 触发重算并记重算版本 |
| 实体键缺失 | 计入「未归属」桶，不丢弃 |
| 上游依赖 | dws_user_behavior_daily（entity_key = unified_user_id） |
| 准入等级 / 版本 | trusted / v7 |
| 变更记录 | v6→v7：pay_amt 阈值 800→1000（2024-06，业务确认：增长组） |
| 申诉路径 | 提交工单 → 由 Owner 按本卡解释依据字段 |
```

**模板 2：标签服务的缺失与降级语义（消费方要读的那一段）**

```text
getTags(entity_id, tag_names, on_missing, on_timeout)
  on_missing: null | default(value)     # 无值时的返回形态（不许隐式）
  on_timeout: stale | default | fail    # 超时时的行为（消费方声明）
返回中必带：
  caliber_version   # 这个值是按哪一版口径算的
  time_semantics    # snapshot | latest
  produced_at       # 产出时刻（新鲜度可核）
判据：消费方能区分「这个人不符合」与「这个标签没有值」——
      分不清，就会出现"未覆盖"被当成"不符合"的静默错判
```

**模板 3：逐实体对账（不是比人数）**

```sql
-- 取同一批实体，把两份实现的值并排，只输出不一致的行
WITH a AS (
  SELECT entity_id, tag_name, value, caliber_version
  FROM   tag_batch.result   WHERE tag_name = 'high_value_user' AND dt = :tau
),
b AS (
  SELECT entity_id, tag_name, value, caliber_version
  FROM   tag_stream.result  WHERE tag_name = 'high_value_user' AND ts = :tau
)
SELECT COALESCE(a.entity_id, b.entity_id) AS entity_id,
       a.value AS batch_value, b.value AS stream_value
FROM   a FULL OUTER JOIN b USING (entity_id, tag_name)
WHERE  COALESCE(a.value, '<null>') <> COALESCE(b.value, '<null>');
-- 判据：本查询必须返回 0 行。返回非空时，先看这些实体是否都落在
--       时间边界 / 空值 / 迟到数据这三类上——若是，说明是边界没对齐；
--       若否，说明两份实现的口径本身不同。
```

**一条使用说明**：这三张模板的价值在于**它们都是"可核验"的**——模板 1 让口径可被复述，模板 2 让缺失与降级可被区分，模板 3 让一致性可被证明。**把这三件做出来，标签平台的最小可信集就具备了。**

### 4.6 成本：这套东西的账单

**硬件**：本主题的算力成本主要在**标签产出侧**（批任务与流任务），而它**通常复用数仓与流平台的既有资源**（[Ch3](../../03-data-stack/README.md)），因此很少有专为标签采购的硬件。两处例外：① **在线标签服务的存储**——点查要走低延迟存储，若标签数 × 实体数很大，**在线存储会超过离线标签表**（判据见下）；② **圈选引擎的索引**——倒排索引会带来额外的存储放大。

**在线存储的估算（本主题唯一值得单独算的一项）**：

```
在线存储 ≈ 实体数 E × 有效标签数 T_online × 单值字节数 B × 副本数 r

例【推算：口径为"实体数 × 在线标签数 × 单值字节数 × 副本数"】：
  E = 1 亿用户，T_online = 200，B ≈ 8 字节（枚举 / 数值），r = 2
  → 1e8 × 200 × 8 × 2 ≈ 320 GB
  再加上键与索引开销（通常 1.5–2×）⇒ 约 0.5–0.6 TB
判据：当 T_online 继续增长时，存储线性上升——
      此时正确的动作是「把低频标签移出在线服务」，而不是扩容。
```

**人力（主项）**：本主题的人力集中在三项，且都不是一次性的：

1. **口径维护与业务确认**：每个标签的口径、分档边界、变更都要与业务确认。**成本随标签数线性增长**（这是本主题最主要的人力项）。
2. **对账与抽检**：逐实体对账（半天级）、准确率抽检（按标签抽样核对）。**常备投入在 0.3–1 人年量级**【经验：随标签数与在线消费方数量浮动】。
3. **治理**：准入评审、退役影响分析、申诉处理。**申诉处理是本主题特有的一项**——它随"标签进入决策路径"的范围增长。

**云账单（次项）**：在线存储、圈选索引、流任务常驻资源、标签服务的实例。

**一条推论**：**本主题的成本是"人力随标签数增长 + 存储随在线标签数增长"，而不是"随数据量增长"**。它的规模化压力来自**标签数量的膨胀**（这也是 §3.2.7 的退役机制存在的经济理由）——**每增加 100 个在线标签，就是一笔可计算的存储与人力增量**。

### 4.7 容灾与故障演练

**本主题的"灾"分两类**：① **服务不可用**（在线消费方受影响，直接可见）；② **口径静默出错**（产出的值不对，但系统一切正常——**这类更危险**）。

| 失效形态 | 影响面 | 降级策略 | 演练动作 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 标签服务不可用 | 风控 / 推荐 / 触达 | 按消费方声明：用旧值 / 用默认值 / 放行（**不许隐式阻塞**） | 真关一次标签服务，看各消费方的行为是否符合声明 | RTO：分钟级 |
| 在线存储故障 | 点查 | 切副本；不可用时降级到"读离线快照"（接受更旧的值） | 关一个副本，验证自动切换与降级路径 | RTO：分钟级 |
| 批任务失败 | T+1 标签整体缺一期 | **保留上一期值并标 `stale`**（不是产出空值）；告警 | 让一期批任务失败，验证消费方看到的是 stale 而不是 null | RTO：一期（次日追上） |
| 流任务延迟 | T+0 标签的新鲜度 | 提高告警阈值 + 降级到最近一次批结果 | 人为让流任务积压，看新鲜度告警与降级是否触发 | RTO：小时级 |
| **口径被误改** | 标签值大面积改变 | **回滚口径版本 + 重算受影响分区**；等级退回试运行 | 故意改错一个分档边界，验证能回滚并识别受影响范围 | 天级（重算耗时） |
| 上游字段下线 | 依赖它的标签失效 | 影响分析给出受影响的标签与消费方 → 逐个处置 | 模拟下线一个上游字段，看能否自动列出受影响标签 | 天级 |
| 实体键异常（重复 / 缺失） | 覆盖率与人群失真 | 守恒校验（明细 = 已归属 + 未归属）触发告警 | 注入一批空键明细，看守恒校验是否报警 | 小时级 |

**这套演练的三条纪律**：

1. **"缺一期"要产出 stale 而不是 null**——因为消费方分不清"这个人不符合"与"这一期没算"，返回 null 会让**未覆盖被静默当成不符合**（§4.5 模板 2 的判据）。
2. **口径误改必须能回滚并重算**——它是本主题唯一会"大面积改变结果"的失效形态，没有回滚路径时，一次误改要用一次人工修正全部下游。
3. **每次演练留"演练前 / 演练后"两组数字**——特别是覆盖率与人群规模（口径出错时这两个数会先动）。

### 4.8 演进路线：0 → 1 → 100

**0 → 1：一个标签的口径被形式化**
- **这一步做什么**：统一主实体；把业务最关心的那个标签写成口径卡（§4.5 模板 1）；跑通批产出。
- **变贵的是什么**：**人力（业务确认）**——分档边界、空值语义、时间语义这三件必须由业务拍，而它们都不是技术问题。
- **先坏的是什么**：**先坏的是"边界用户"**——口径卡里没写清的边界（空值、迟到、实体键缺失）会集中体现在一小撮人身上，而业务最先质疑的正是这一小撮。**这一阶段的判据不是"标签跑出来了"，而是"五个边界都写下来了"。**

**1 → 10：口径层与双产线**
- **这一步做什么**：口径配置化（新标签不改 ETL）；建逐实体对账；上标签服务（点查 / 批量分离）；实时标签与离线同源。
- **变贵的是什么**：**一致性验证**——对账要常态化、口径变更要传播到四处（版本 / 等级 / 缓存 / 通知）。**它变贵的不是算力，而是"每次改动都要跑一遍一致性验证"这件事**。
- **先坏的是什么**：**先坏的是缓存**——口径变更后缓存未按版本失效，会持续返回旧值，而**这是静默的**（服务看起来正常）。因此这一阶段的重点是**把口径版本作为缓存键的一部分**。

**10 → 100：治理与自服务**
- **这一步做什么**：准入等级接入生产路径；使用度埋点与退役流程；圈选引擎的可解释执行计划；申诉通道与归档可查。
- **变贵的是什么**：**治理人力随标签数增长**——每个标签都要有 Owner、等级、复核周期。
- **先坏的是什么**：**先坏的是"遗留标签的准确性"**——它们没有 Owner、没人复核，却仍在被消费。因此这一阶段的重点是**先测量、再退役**（使用度指标先行），而不是一次性清理。

**贯穿三阶段的一件事**：**每个阶段都保留"逐个实体对账"的能力**。它是这套产线唯一的健康指标——**标签平台的腐化不会表现为报错，只会表现为"两个实现的值慢慢不一样了"。**

### 4.9 自检清单

- [ ] 主实体统一了吗？抽 100 个实体的归并率是多少？
- [ ] 每个标签有一张口径卡吗？五个边界（空值 / 迟到 / 缺失键 / 时间语义 / 分档）都写了吗？
- [ ] 分档边界是谁确认的？改边界会递增口径版本吗？
- [ ] 新增一个事实标签，需要改动的代码行数是多少？（目标：0）
- [ ] 同一标签的多份实现，做过逐实体对账吗？结果是不是 0 行不一致？
- [ ] 对账是常态任务还是一次性验证？
- [ ] 模型标签带模型版本与置信度吗？取值域业务确认过吗？
- [ ] 预测标签存 `prediction_point` 吗？观察 / 表现窗口写进口径了吗？
- [ ] 口径变更会触发四件事（版本递增 / 等级退回 / 缓存失效 / 通知）吗？
- [ ] 点查的缓存键含口径版本吗？口径变更后多久生效？
- [ ] 标签服务有超时与降级策略吗？消费方声明过 `on_missing` / `on_timeout` 吗？
- [ ] 批量查询的执行计划可解释吗（能看到选择率估计）？
- [ ] 生产决策的读取路径走服务吗（还是直连标签表）？
- [ ] 有使用度埋点吗？退役流程有观察期与归档可查吗？退役标签返回明确错误吗？
- [ ] 圈选结果带"口径版本 + 时间语义 + 生成时刻"吗？导出有脱敏吗？
- [ ] 申诉路径存在吗？最近一次申诉是怎么回答的？

### 4.10 小结

> 本节小结：标签平台的落地顺序**以口径为先**——先统一实体，再把一个标签的口径形式化（五个边界写全），然后配置化口径层、建逐实体对账、上服务与降级、接准入等级、最后做使用度与退役。**变贵的是人力，且它随"标签数"增长，不随"数据量"增长**（§4.6）——因此**退役机制有直接的经济理由**：每多 100 个在线标签就是一笔可算的存储与人力增量。**容灾有一条本主题特有的纪律**：**"缺一期"要产出 `stale` 而不是 `null`**——因为消费方分不清"不符合"与"没有值"，返回空会让未覆盖被静默当成不符合（§4.7）。**三阶段的同一件事**：始终保留"逐个实体对账"的能力——**标签平台的腐化不会报错，只会让两个实现的值慢慢不一样。**

> 💡 **思考锚点**：按 §4.1 的 Step 2 做一个最小动作——把你们最重要的那个标签写成一张口径卡（§4.5 模板 1），**特别是把五个边界逐条填上**。填的过程中会有一两格你答不出来——**那一格就是这套标签体系目前最大的风险点**，而它通常不在你的监控里（因为"没写下来的语义"不会被监控）。你打算先补哪一格？
