## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研标签平台 / 买 CDP / 用特征平台改造 / 用数仓宽表 + 调度 / 开源标签系统 / 指标平台扩展"打分是常见做法，但它有三个结构性问题：

① **同一列在不同处境下方向相反**——"实时能力"对做风控的团队是必需，对做月度运营分析的团队是负担（实时意味着常驻流任务与常态化对账）。
② **打分表隐含"这些选项互斥"**，而真实做法是组合（**数仓宽表 + 口径配置 + 自建服务**是常见组合）。
③ **最关键的判据不是可打分的维度，而是门槛**——**"口径能不能被抽出来并导出"**与**"能不能做到逐实体一致"**这两条是门槛：不满足就直接出局。**一个功能极全但口径锁在产品内部、且只提供"最新值"接口的标签平台，会在你需要申诉或对账时把你卡死。**

**本节采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| **口径可抽出与可导出** | 标签的定义能不能以配置形态存在、能不能导出成不依赖产品的材料？ | **这是门槛不是权重**——口径锁死 → 迁移代价是"重写全部标签" |
| **逐实体一致性** | 它支不支持"同一标签多实现逐个实体比对"？ | 不支持 → 只能比人数 → 名单错误无法发现（§6.2） |
| **缺失语义的表达力** | 接口能不能区分"不符合"与"无值"？ | 不能 → 所有下游都会把未覆盖当不符合（§5.3.2） |
| **时间语义** | 支不支持快照语义（按 `event_time` 取历史值）？ | 不支持 → 申诉与复盘无法应答（§6.4） |
| **分群与资产分离** | 圈选结果是"查询"还是"资产"？ | 不分离 → 台账被活动人群淹没（§6.3） |
| **运维承接** | 谁维护口径、谁做对账与抽检？ | 本主题成本是人力为主（§4.6），**没有承接人的方案半年后失效** |

**这 6 条里，前两条是门槛（不满足直接出局），后四条是权重的输入。**

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| **数仓宽表 + 调度** | 最小起点 | 标签就是宽表的一列，调度产出 | 标签数 &lt; 20、只给人看 | 加标签要改 ETL；口径散在 SQL；**没有服务层** |
| **口径配置 + 自建产出** | 中层形态 | 口径配置化，批 / 流引擎按配置产出，自建服务层 | 多数团队的现实解 | **口径层、服务层、对账都要自己建**（人力为主） |
| **特征平台改造** | 复用既有 | 把标签当作"一类特征"，复用特征平台的产出与服务 | 已有成熟特征平台的团队 | **治理语义不匹配**——特征不需要准入等级与申诉，标签需要 |
| **指标平台扩展** | 复用既有 | 把标签当作"实体维度的指标"，复用指标平台的口径管理 | 已有成熟指标平台的团队 | 指标是聚合口径、标签是实体口径；**时间语义与申诉不在它的模型里** |
| **商业 CDP / 标签平台** | 成品能力 | 口径、产出、服务、圈选一体交付 | 运营驱动、要快上线的团队 | **口径锁在产品内**；快照语义与准入等级未必提供 |
| **全自研** | 控制力最强 | 口径层 + 双产线 + 服务 + 治理全自建 | 标签是核心竞争力、或监管要求高 | 短期投入最大；**对账与抽检是常备人力** |

**这六个候选其实分三族**：

- **复用族**（数仓宽表、特征平台改造、指标平台扩展）——**解决"少建一套"**，代价是**治理语义不匹配**（复用的那套是为别的对象设计的）。
- **独立族**（口径配置 + 自建、全自研）——**解决"标签有自己的治理要求"**，代价是**人力**。
- **成品族**（商业 CDP / 标签平台）——**解决"快速上线"**，代价是**口径与时间语义的掌控权**。

**族内可替换，跨族不可换**：复用族内部换的是"复用了哪一套"；从复用族换到独立族，**不是替换而是补齐**（口径层与治理）；从任一族换到成品族，**等于把口径的定义权交出去**——那不是技术迁移，是资产归属的决策。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 口径的归属：在你的配置里，在别的对象模型里，还是在产品里

**机制是什么**：口径只有三个位置——**你的配置里**（独立族）、**另一个对象模型里**（复用族：当作特征 / 当作指标）、**产品内部**（成品族）。

**它在各候选中的实现差异**：独立族的口径是**一等对象**（有版本、有 Owner、可导出）；复用族的口径**寄生在别的模型上**——当作特征时，它继承特征的属性（点查、Point-in-Time），但**没有"准入等级"与"申诉"这两个概念的挂载点**；当作指标时，它继承指标的口径管理，但**指标模型里没有"实体级取值"与"预测时点"这两个字段**；成品族的口径**在产品内部**，能不能导出取决于产品的开放程度。

**由此必然导出的性质**：因为**复用的对象模型决定了"哪些治理项有地方放"**，所以复用族的代价不是"少几个功能"，而是**某些治理项在模型里根本无处安放**——你会被迫用外部表格、文档或流程去补，而那些补出来的东西**不会自动跟随口径变更**（这正是"半年后失效"的成因）。**这条性质解释了为什么"用特征平台做标签"在早期看起来很好、在需要申诉与准入时突然卡住。**

**失效条件**：当业务问出"这个标签为什么给他打上"或"上个月他是哪一档"时，复用族的模型给不出字段——**此时唯一的修法是把口径搬出来单独管**（即向独立族迁移）。

#### 7.3.2 一致性验证的实现位置：比人数，还是逐实体

**机制是什么**：一致性验证是**在总量层**做（比人数、比分布）还是**在实体层**做（逐个实体比对）。

**它在各候选中的实现差异**：宽表 + 调度的形态通常**只能比人数**（因为只有结果表，没有"两个实现并排"的接口）；口径配置形态**可以逐实体比对**（因为两份产出都有实体键，可以 `FULL OUTER JOIN`）；成品族是否支持取决于它**是否暴露两份产出**（很多产品只给"一个标签接口"，你无法同时取到离线与在线两个值）。

**由此必然导出的性质**：因为**不一致集中在边界用户上**，所以**总量层的验证在原理上发现不了它**——比人数会把差异平均掉，而差异恰恰集中在少数人身上（§2.2）。**因此"能不能逐实体比对"是一个结构性的能力，不是验证力度的选择。**

**失效条件**：当业务发现"两边人数一样但名单不同"时，说明此前所有验证都停在总量层——**此时要补的不是更严的验证流程，而是"能同时取到两份产出"这个能力**。

#### 7.3.3 时间语义：最新值，还是可复现的快照

**机制是什么**：接口返回的是**当前最新一次计算的结果**，还是**按 `event_time` 指定的历史值**。

**它在各候选中的实现差异**：宽表 + 调度的形态**天然是快照**（每天一列 / 每个分区一份，历史可查——但它查的是"那一天的分区"，不是"按 event_time 取"）；口径配置 + 自研**可以两者都支持**（快照靠分区 + 时点键，最新靠服务）；成品族**通常只给最新值**（它的服务模型是为了实时消费设计的，历史值要么不存、要么不开放）。

**由此必然导出的性质**：因为**申诉与复盘发生在决策之后的数周甚至数月**，所以**"只有最新值"的系统在原理上无法应答这些问题**——而这不是性能或成本问题，是**数据在产出时就被覆盖了**。**因此时间语义必须在产出时就决定**：一旦只存最新值，历史就补不回来（同 §6.4 的失败教训）。

**失效条件**：受监管场景（信贷、准入、风控）必须快照语义——**只提供最新值的候选直接出局**，无论其它维度多强。

#### 7.3.4 缺失语义的表达力：二值，还是三态

**机制是什么**：接口把"无值"表达成什么——**与"不符合"同值**（二值），还是**独立的第三态**（三态）。

**它在各候选中的实现差异**：宽表 + 调度常见的是二值（`NULL` 与 `false` 在下游经常被同一个 `if` 吞掉）；口径配置自建可以实现三态（返回结构里带 `missing` 标记）；成品族通常是二值或"返回空对象"——**而空对象在消费侧同样容易被当成"不符合"**。

**由此必然导出的性质**：因为**机器（模型 / Agent）不像人一样对"我不知道"保持沉默**，所以二值语义在 AI 场景里会**把"未覆盖"静默转成"不符合"**（§5.3.2）——而覆盖率通常是 70–90%，意味着**一到三成的人被当成"明确不符合"**。**这条差异在人工消费场景里看不出来（人会追问），在模型消费场景里会直接变成错误结论。**

**失效条件**：当标签被 Agent / 模型消费时，二值语义直接出局——**判据是接口返回里有没有一个区分"无值"的字段。**

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| **复用族** | 人力（适配既有对象模型） | 治理项在模型里无处安放 → 外部表格 / 流程补丁；后期迁移到独立族的重做 | 随**标签数**增长（且增长率高于独立族） |
| **独立族** | 人力（口径 + 对账 + 抽检） | 对账与抽检是常备投入；服务层的高可用与降级 | 随**标签数**增长 |
| **成品族** | 许可 + 订阅 | 口径迁移成本（换产品即重写）；历史值不可得时的补救；产品未覆盖治理项的自行补建 | 随**席位 / 模块**增长 |

**成本函数的三条判据**：

① **复用族的曲线是"低起点 + 高斜率"**——起步省（不用建口径层），但随标签数增长得快（每个治理项都要外部补丁），且在需要申诉 / 准入时有一次**阶跃式**成本（迁移到独立族）。
② **独立族的曲线是"高起点 + 低斜率"**——前几个标签贵（要建口径层与服务），之后每个标签便宜（加配置）。
③ **成品族的曲线是"台阶 + 迁移陷阱"**——许可是台阶，但**口径锁死意味着换产品的成本是"重写全部标签"**，这个成本不体现在曲线上，而是体现为**锁定**。

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：N = 标签数   h = 单标签的年维护人力（人年/标签）
    H0 = 建口径层与服务层的一次性人力（人年）   P = 许可与订阅（万元）
    m = 治理项数（准入 / 申诉 / 快照 / 三态 …）

复用族：  Cost_reuse(N) = N × h_reuse + (模型未覆盖的治理项补丁成本)   ← 斜率大
独立族：  Cost_ind(N)   = N × h_ind + H0                              ← 起点高、斜率小
成品族：  Cost_prod(N)  = P + N × h_prod + 锁定成本(≈ N × 重写单价)    ← 台阶 + 隐性锁定

反直觉的一条【推算】：若 h_reuse > h_ind（复用族的单标签维护人力更高，
因为每个治理项都要补丁），则存在一个 N* 使两条曲线交叉：
    N* = H0 / (h_reuse − h_ind)
    N 小于 N* 时复用划算，大于 N* 时独立划算——而 N* 通常只有几十个标签。
```

**这个式子的用法**：**先估两个斜率**（复用族与独立族的单标签维护人力），再估一次性投入 `H0`。**如果你的路径规划里标签数会超过几十个，交叉点会提前到来**——而"先用特征平台顶一下、以后再抽出来"这个常见决策，实际上是在赌标签数不会增长，而标签数几乎总是会增长（§6.3 的膨胀速率）。

### 7.5 决策树（每个分支都要有阈值依据）

1. **标签会不会被"机器"消费（模型 / Agent / 规则引擎），或会不会进入影响个人待遇的决策？**
   - **会** → **复用族与二值语义的成品族出局**；必须选能表达三态、能存快照、能接准入等级的形态；进入第 3 问。
   - 不会（只给人看报表）→ 进入第 2 问。
2. **标签数会超过几十个吗？**
   - 不会（**20 个以内**且长期稳定）→ **数仓宽表 + 调度就够**：上平台是治理过剩。
   - 会 → 进入第 3 问。
3. **已有成熟的特征平台或指标平台吗？**
   - 有，且**你能接受"用外部机制补治理项"**（准入 / 申诉 / 快照用流程与表格补）→ **复用来顶一段**，但要明确"何时抽出来"（用第 4 问的判据）。
   - 有但要求治理完整 → 进入第 4 问。
   - 没有 → 进入第 4 问。
4. **团队能不能长期维护口径 + 对账 + 抽检（按 0.3–1 人年的常备投入量级估算【经验】）？**
   - 能 → **独立族（口径配置 + 自建服务）**，控制力最强。
   - 不能 → **成品族**，但必须**先压测两件事**：口径能不能导出、支不支持快照语义（§7.1 的门槛）。

**阈值的诚实说明**：上表的"20 个以内"与"0.3–1 人年"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的标签数与排期校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 标签个位数、只给人看 | 数仓宽表 + 调度 | 口径配置 + 自建 | 上平台会引入治理成本而无收益 |
| 标签几十个、给规则引擎用 | 口径配置 + 自建产出 | 特征平台改造 | 复用族的治理项要外部补，几十个标签时补丁还管得住 |
| 标签上百、要给模型 / Agent 用 | 独立族（口径层 + 服务） | 成品族 | 复用族的三态与快照无处安放；成品族未必支持 |
| 受监管场景（信贷 / 准入） | 独立族（**快照语义 + 准入等级 + 申诉字段**） | 成品族（须验快照） | 只提供最新值的候选直接出局 |
| 实时 + 离线同时要 | 独立族（**双引擎同源 + 逐实体对账**） | 复用族（若特征平台支持双产线） | 无逐实体对账能力则名单错误无法发现 |
| 运营侧要快速圈人 | 标签平台 + **独立的分群/圈选模块** | 成品 CDP | 把分群当标签存会让台账膨胀（§6.3） |
| 团队只有 1–2 人 | 成品族 | 数仓宽表 | 独立族的口径与对账人力不会因为它小就消失 |

**组合的两条次序原则**：① **先把口径抽出来（含五个边界），再谈平台**——口径的不变部分应当独立于实现（§4.1 的反面）；② **先把逐实体对账建起来，再上实时**——没有对账能力时上实时，等于把一个无法验证的不一致引入生产。

**第三条原则（方向相反但同样重要）**：③ **先把使用度埋点建起来，再谈治理**——没有埋点，准入与退役都无源之水（§5.3.5）；**而在标签数还少时建埋点，成本极低。**

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 复用族 → 独立族 | 需要申诉 / 准入时模型无处安放 | 把口径搬出来单独管；补快照与三态；重建服务层 | **以季度计**【经验】，且**历史标签值若未存则不可恢复** |
| 宽表 → 口径配置 | 加标签一直在排期 | 逐个抽口径 + 逐实体比对原值 | 以月计，**与标签数成正比** |
| 只存最新值 → 快照 | 申诉与复盘答不出 | 补时点键 + 重算历史（**若上游历史不可得则做不到**） | **部分不可逆**：上游已不可得时，只能从今往后的快照 |
| 比人数 → 逐实体对账 | 名单不一致被发现 | 建对账任务 + 定位边界差异 | 以周计（工具简单，**难在定位与修复**） |
| 分群当标签存 → 分离 | 台账膨胀、治理失效 | 把活动人群迁出资产台账；改为保存条件 | 以月计，**存量清单的人工甄别是主要工作量** |
| 产品锁定的口径 → 可导出 | 换产品要重写全部标签 | 逐标签重写口径 + 重建服务对接 | **以季度计**，且**期间业务不能停** |
| 无使用度 → 有埋点 | 不知道哪些能退 | 补埋点 + 观察一个季度 | 以周计建埋点，**观察期无法压缩** |

**一条硬结论**：七条里最贵的是**"口径锁定之后的收回"**——它不只是重写，还包括**历史值的恢复**（若当时只存最新值，那段历史永久不可得）。**所以第 1 条门槛（口径能不能导出）必须在第一版就判对。**

**第二条硬结论**：上表里有一项的代价**完全不可逆**——"只存最新值 → 快照"里的历史部分。**其余六项都是"要花时间"，这一项是"花时间也拿不回来"**；这决定优先级：**如果只能做一件事，先把时点键与历史留存做上**（成本极低），而不是先把服务性能优化一遍。

### 7.8 小结

> 本节小结：六个候选之间的差异，最终都能归到三问——**口径归谁且能不能导出**（你的配置 / 别的对象模型 / 产品内部）、**一致性验证能不能做到逐个实体**、**时间语义是最新还是可复现的快照**（外加一条 AI 场景的新判据：**缺失语义是二值还是三态**）。四问决定了它们的分族（复用族 / 独立族 / 成品族）与成本曲线形状（复用族低起点高斜率、独立族高起点低斜率、**成品族有隐性锁定成本**）。**选型顺序不可颠倒**：先用"会不会被机器消费 / 会不会影响个人待遇"筛掉不可行，再用"标签数会不会超过几十个"决定要不要平台，最后用团队承接能力在剩下的里选——**把最后一问当权重而不是门槛，是第二年最常见的失效原因**。**本主题有一条与其它主题不同的推论**：**复用族的交叉点通常只有几十个标签**（§7.4 的 `N*`），而标签数几乎总是会增长——因此"先用别的平台顶一下"这个决策，实际上是在赌一个不太可能成立的假设。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次**门槛检查**（不是打分）：口径可抽出与可导出、逐实体一致性、缺失语义表达力、时间语义、分群与资产分离、运维承接——**哪一条是"不满足"而不是"分数低"**？那一条就是你最可能被迫迁移的方向（§7.7）；而你今天的补救成本，是否还落在"以周计 / 以月计"的那几格里？**另一问更具体**：如果明天要换掉现在的标签系统，**你的口径能不能导出来、历史值能不能带走**？答不出，说明你的标签还没有真正掌握在自己手里。
