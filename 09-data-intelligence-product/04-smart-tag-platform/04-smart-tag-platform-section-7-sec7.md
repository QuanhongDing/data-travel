## 7. 与其他方法对比

>
> 阅读顺序：先立判据（7.1）→ 候选分族（7.2）→ 机制差异（7.3，本节重心）→ 成本函数（7.4）→ 决策树与阈值依据（7.5）→ 场景矩阵与组合（7.6）→ 选错的代价（7.7）→ 处境对照（7.8）。

### 7.1 先立判据：为什么打分表会误导

给"自研标签平台 / 买 CDP / 用特征平台改造 / 用数仓宽表 + 调度 / 开源标签系统 / 指标平台扩展"打分是常见做法，但它有三个结构性问题：

① **同一列在不同处境下方向相反**——"实时能力"对做风控的团队是必需，对做月度运营分析的团队是负担（实时意味着常驻流任务与常态化对账）。
② **打分表隐含"这些选项互斥"**，而真实做法是组合（**数仓宽表 + 口径配置 + 自建服务**是常见组合）。
③ **最关键的判据不是可打分的维度，而是门槛**——**"口径能不能被抽出来并导出"**与**"能不能做到逐实体一致"**这两条是门槛：不满足就直接出局。**一个功能极全但口径锁在产品内部、且只提供"最新值"接口的标签平台，会在你需要申诉或对账时把你卡死。**

**本节采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| **口径可抽出与可导出** | 标签的定义能不能以配置形态存在、能不能导出成不依赖产品的材料？ | **这是门槛不是权重**——口径锁死 → 迁移代价是"重写全部标签" |
| **逐实体一致性** | 它支不支持"同一标签多实现逐个实体比对"？ | 不支持 → 只能比人数 → 名单错误无法发现（§6.2） |
| **缺失语义的表达力** | 接口能不能区分"不符合"与"无值"？ | 不能 → 所有下游都会把未覆盖当不符合（§5.3.2） |
| **时间语义** | 支不支持快照语义（按 `event_time` 取历史值）？ | 不支持 → 申诉与复盘无法应答（§6.4） |
| **分群与资产分离** | 圈选结果是"查询"还是"资产"？ | 不分离 → 台账被活动人群淹没（§6.3） |
| **运维承接** | 谁维护口径、谁做对账与抽检？ | 本主题成本是人力为主（§4.6），**没有承接人的方案半年后失效** |

**这 6 条里，前两条是门槛（不满足直接出局），后四条是权重的输入。**

**为什么"门槛"与"权重"必须在原理上分开**：权重是**可补偿**的——这一项低一些、那一项高一些，加权求和仍然能得出一个不低的总分；而门槛**不可补偿**：口径锁在产品内部、或只提供"最新值"，无论其它维度多好，这两条都会在特定场景里直接把你卡死，且代价不是"少一个功能"，而是**迁移全部标签**或**历史永久不可得**（§7.7 里最贵与最不可逆的两格正是这两条）。打分表的结构决定了它只能做加权求和，所以它**在原理上表达不了门槛**——这不是刻度或权重没调好，而是那张表缺一个"先淘汰、再排序"的前置阶段。

**六条判据各自的取用时机**（顺序反了会把门槛当成优点来权衡）：

- 第 1、2 条（口径可抽出与可导出、逐实体一致性）**在立项前就要问**——它们是"这条路能不能走"的问题，答错通常要到第二年才显形；
- 第 3、4 条（缺失语义的表达力、时间语义）**在决定"标签给谁消费"时问**——只给人看报表的标签可以二值、可以只有最新值，这两条在那时并不构成门槛；
- 第 5、6 条（分群与资产分离、运维承接）**在决定"谁来维护这套东西"时问**——它们不决定标签算什么，决定这套东西三年之后还在不在。

**最容易漏掉的是第 5、6 条**，而且它们在 §7.3 里**没有各自的机制单元**：§7.3 的四个单元讲的是前四条在候选之间的差别，而这两条的差别**不在候选之间、在"你把自己当成什么"**——第 5 条问"圈选结果是查询还是资产"，第 6 条问"有没有人做对账与抽检"。它们在实测里的共同点是**失效最晚暴露、却最难补救**：分群被当资产存的那一天没有任何报错，只是台账一年后没人认得全；对账与抽检没有承接人的那一天也没有任何报错，只是两个实现的值慢慢不一样（§4.10 的同一句）。**所以这两条不能靠"上线后观察"发现，只能靠现在问出来。**

**一个功能极全但门槛不合格的候选**是本主题最容易踩的坑：它能覆盖你今天的每一个功能需求，而它把口径留在产品内部、把历史值覆盖掉——**这两件在功能清单上都不显示为"缺失"**，只在你要换产品、或要回溯到某个决策时点时才显形。这也是本节不用打分表的原因：**打分表量的是它有什么，门槛问的是你还能不能走。**

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| **数仓宽表 + 调度** | 最小起点 | 标签就是宽表的一列，调度产出 | 标签数 &lt; 20、只给人看 | 加标签要改 ETL；口径散在 SQL；**没有服务层** |
| **口径配置 + 自建产出** | 中层形态 | 口径配置化，批 / 流引擎按配置产出，自建服务层 | 多数团队的现实解 | **口径层、服务层、对账都要自己建**（人力为主） |
| **特征平台改造** | 复用既有 | 把标签当作"一类特征"，复用特征平台的产出与服务 | 已有成熟特征平台的团队 | **治理语义不匹配**——特征不需要准入等级与申诉，标签需要 |
| **指标平台扩展** | 复用既有 | 把标签当作"实体维度的指标"，复用指标平台的口径管理 | 已有成熟指标平台的团队 | 指标是聚合口径、标签是实体口径；**时间语义与申诉不在它的模型里** |
| **商业 CDP / 标签平台** | 成品能力 | 口径、产出、服务、圈选一体交付 | 运营驱动、要快上线的团队 | **口径锁在产品内**；快照语义与准入等级未必提供 |
| **全自研** | 控制力最强 | 口径层 + 双产线 + 服务 + 治理全自建 | 标签是核心竞争力、或监管要求高 | 短期投入最大；**对账与抽检是常备人力** |

**这六个候选其实分三族**：

- **复用族**（数仓宽表、特征平台改造、指标平台扩展）——**解决"少建一套"**，代价是**治理语义不匹配**（复用的那套是为别的对象设计的）。
- **独立族**（口径配置 + 自建、全自研）——**解决"标签有自己的治理要求"**，代价是**人力**。
- **成品族**（商业 CDP / 标签平台）——**解决"快速上线"**，代价是**口径与时间语义的掌控权**。

**族内可替换，跨族不可换**：复用族内部换的是"复用了哪一套"；从复用族换到独立族，**不是替换而是补齐**（口径层与治理）；从任一族换到成品族，**等于把口径的定义权交出去**——那不是技术迁移，是资产归属的决策。

**族内各行的实际差别（同族不等于同级）**：

- **复用族内部**，**数仓宽表 + 调度**与**特征平台改造、指标平台扩展**的差别不在能力，而在**"有没有一个对象模型可寄生"**——宽表形态连寄生的机会都没有，治理项全在 SQL 与文档里；后两者至少有一个模型，只是那个模型的字段集不是为标签设计的（§7.3.1 给出这个差别为什么是结构性的）。
- **独立族内部**，**口径配置 + 自建产出**与**全自研**的差别是**范围**而不是方式——前者复用数仓与流引擎，只自建口径层、对账与服务；后者连产出链路也自己写。它们的成本曲线起点不同，但**斜率是同一条**（§7.4）。
- **成品族在候选表里只有一行**（"商业 CDP / 标签平台"），因此族内没有可比较的候选——这一族要问的**全在"开放程度"这一条上**：能不能导出口径、能不能取到历史值、准入等级这类治理项是不是产品的一等对象。因此成品族的"选型"实际上只做一件事——**把 §7.1 的两条门槛压测一遍**，功能对比放在其后。

**为什么"第一刀是选族"**：同族内部换一个产品，动的是接口、运维与许可；**跨族换一个形态，动的是"谁是口径的主"**——后者要重写全部标签（§7.7 里以季度计的那一格）。因此候选表的用法不是"挑一行"，而是**先判定自己必须落在哪一族，再在族内挑当时最合适的实现**。

**表里"典型使用者"一列不是用户画像，是约束集的代理量**：写"标签数很少、只给人看"的那一行，它成立的真正前提是**约束集很小**——不需要解释与申诉、不需要给系统用、不需要治理人力（§3.1 的五条约束）。读这一列的方法因此是**把它翻回约束**：如果你的约束集与它不一致，即使你现在的标签数也很少，这一行对你也不成立。**"我用宽表也能跑"这类判断失败的地方通常不是标签数，而是约束集已经在往平台形态走**——而打分的维度里没有"约束集"这一列。

### 7.3 机制差异：为什么它们表现不同（核心节）

下面四个单元对应 §7.1 的**判据 1–4**（口径归属 / 一致性验证位置 / 缺失语义 / 时间语义；本节按机制顺序把后两条排成 §7.3.3 时间语义、§7.3.4 缺失语义）。**§7.1 的第 5、6 条（分群与资产分离、运维承接）不在这里出现**，原因在 §7.1 已说明：它们的差别不在候选之间，而在"你把圈选当查询还是当资产""你有没有人做对账与抽检"——**这两条的判据在 §7.6 的次序原则里，迁移代价见 §7.7 的『分群当标签存→分离』与『无使用度→有埋点』两格。**

四个单元的写法一样：先给一张**定性机制表**（只写入口、谁决定什么、典型失败形态，不含任何量），再用它推出性质，再给公开证据与失效条件。

#### 7.3.1 口径的归属：在你的配置里，在别的对象模型里，还是在产品里

**机制是什么**：口径只有三个位置——**你的配置里**（独立族）、**另一个对象模型里**（复用族：当作特征 / 当作指标）、**产品内部**（成品族）。

**定性机制表**（列是"入口 / 谁决定什么 / 典型失败形态"，不含任何量）：

| 候选 | 口径存在哪（入口） | 谁决定"哪些治理项有地方挂" | 典型失败形态 |
| --- | --- | --- | --- |
| 数仓宽表 + 调度 | 散在 ETL 与 SQL 里，没有独立载体 | 每个写 SQL 的人各自决定 | 同名不同义，差异不报错，只在有人同时看两个下游时暴露 |
| 口径配置 + 自建产出 | 你的配置里，是一等对象 | 你（口径有版本、Owner、可导出） | 配置无人承接，退化成"另一处没人看的配置" |
| 特征平台改造 | 特征的对象模型里 | 特征平台的数据模型 | 准入等级与申诉无处安放，只能靠外部表格补 |
| 指标平台扩展 | 指标的对象模型里 | 指标平台的语义模型 | 实体级取值与预测时点无处安放 |
| 商业 CDP / 标签平台 | 产品内部 | 产品的能力边界与开放程度 | 换产品即重写全部标签；历史值取不回 |
| 全自研 | 你的配置里，是一等对象 | 你 | 与独立族同因（缺承接人则同样退化），只是自建范围更大 |

**它在各候选中的实现差异**：独立族的口径是**一等对象**（有版本、有 Owner、可导出）；复用族的口径**寄生在别的模型上**——当作特征时，它继承特征的属性（点查、Point-in-Time），但**没有"准入等级"与"申诉"这两个概念的挂载点**；当作指标时，它继承指标的口径管理，但**指标模型里没有"实体级取值"与"预测时点"这两个字段**；成品族的口径**在产品内部**，能不能导出取决于产品的开放程度。

**由此必然导出的性质**：因为**复用的对象模型决定了"哪些治理项有地方放"**，所以复用族的代价不是"少几个功能"，而是**某些治理项在模型里根本无处安放**——你会被迫用外部表格、文档或流程去补，而那些补出来的东西**不会自动跟随口径变更**（这正是"半年后失效"的成因）。**这条性质解释了为什么"用特征平台做标签"在早期看起来很好、在需要申诉与准入时突然卡住。**

**失效条件**：当业务问出"这个标签为什么给他打上"或"上个月他是哪一档"时，复用族的模型给不出字段——**此时唯一的修法是把口径搬出来单独管**（即向独立族迁移）。

**公开证据**：本主题内可核的是**形态**而不是产品——§4.3 工具链表把"口径层"一行写成"自建配置 + 调度；或复用指标平台的口径管理"，选型要点是"**看它是否把口径当一等对象**（能不能导出、能不能版本化）"，**这一行不给产品名**；§7.2 的候选表同样只写"标签平台产品"与"商业 CDP"而不具名。书内他处可指的一处同形物是"**口径作为可交换的一等对象**"这一形态：`04-data-assetization/06-one-service` 的 §4.3 工具链表把"指标 / 标签平台"一栏列有阿里 OneService（商业）与 dbt Semantic Layer / Cube / MetricFlow / Transform / Airbnb Minerva，该行的判据原文是「指标有没有独立于 SQL 的定义载体、改口径是产新版本还是原地覆盖、Owner 是否具体到人」——**这三问与本节"口径归谁"是同一件事的三个面**（载体 / 版本 / 承接人）。**但这些产品在"口径能否导出、历史值能否取回"上的具体行为，请以其官方文档当前版本为准，本节不引具体文档作据。** 本主题 §6.1 的阿里一例给的是把口径从宽表列抽成配置的机制形状（引自其数据中台相关公开材料，属建设方自述、不构成第三方生产案例）。**这一格没有"谁做得更好"的公开对照**——各产品都宣称口径可管，而"换产品时口径能不能带走"几乎没有第三方公开验证过。【公开】（来源：本主题 §4.3、§6.1、§7.2；`04-data-assetization/06-one-service/06-one-service-section-4-sec4.md` §4.3 工具链表）

#### 7.3.2 一致性验证的实现位置：比人数，还是逐实体

**机制是什么**：一致性验证是**在总量层**做（比人数、比分布）还是**在实体层**做（逐个实体比对）。

**定性机制表**：

| 候选 | 验证发生在哪一层（入口） | 谁决定"能取到几份产出" | 典型失败形态 |
| --- | --- | --- | --- |
| 数仓宽表 + 调度 | 总量层（只有结果表） | 没有并排取两份产出的接口 | 比人数一直通过，而名单不同 |
| 口径配置 + 自建产出 | 实体层（两份产出都带实体键） | 你（能不能 `FULL OUTER JOIN` 由你决定） | 对账做成一次性验证，流侧漂移无人发现 |
| 特征平台改造 | 取决于平台是否暴露两份产出 | 平台的服务模型 | 只给一个"特征值接口"，无法同时取到两份 |
| 指标平台扩展 | 总量层（指标天然是聚合口径） | 指标模型的粒度 | 指标模型里没有实体级取值，对账无对象 |
| 商业 CDP / 标签平台 | 多数停在总量层 | 产品是否暴露两份产出 | 只能比人数，或只能看平台自己的"质量分" |
| 全自研 | 实体层 | 你 | 与独立族同因 |

**它在各候选中的实现差异**：宽表 + 调度的形态通常**只能比人数**（因为只有结果表，没有"两个实现并排"的接口）；口径配置形态**可以逐实体比对**（因为两份产出都有实体键，可以 `FULL OUTER JOIN`）；成品族是否支持取决于它**是否暴露两份产出**（很多产品只给"一个标签接口"，你无法同时取到离线与在线两个值）。

**由此必然导出的性质**：因为**不一致集中在边界用户上**，所以**总量层的验证在原理上发现不了它**——比人数会把差异平均掉，而差异恰恰集中在少数人身上（§2.2）。**因此"能不能逐实体比对"是一个结构性的能力，不是验证力度的选择。**

**失效条件**：当业务发现"两边人数一样但名单不同"时，说明此前所有验证都停在总量层——**此时要补的不是更严的验证流程，而是"能同时取到两份产出"这个能力**。

**公开证据**：这一条的公开对照最薄，原因与本主题 §5.2 表里判据②核不到是同一条——**多实现的一致性数据几乎无人公开**（它直接暴露"系统判错过多少人"）。本主题内可核的是形态与判据：§4.1 的 Step 4 把"逐实体对账常态化（不是一次性验证）"写成落地步骤，§4.5 模板 3 给出可直接改两个表名执行的 SQL 与它的读法（返回非空时先看是否集中在时间边界 / 空值 / 迟到数据三类），§6.2 记的是这个模式在书内唯一的具名形态——以逐实体对账作为上线门禁（引自其数据平台相关公开材料，属建设方自述），同节还记了它的反面：**第一版用"两边人数一致"当证据，三个月后才发现两份名单的重合约七成**。书内他处可指的相邻形态是"正查与反查是两份副本、漂移后会出现『查得到他有这个标签、但按这个标签圈不到他』"（`04-data-assetization/06-one-service` 的 §3.2.2 与"标签驱动型"结构图）——那是**一致性问题的另一处落点**：同一个标签在服务侧的两条路径之间也会漂移。**本节不引任何产品的"质量分"作为逐实体一致性的证据**——平台的汇总质量分与"逐个实体比"不是同一件事。【公开】（来源：本主题 §4.1 Step 4、§4.5 模板 3、§6.2、§5.2；`04-data-assetization/06-one-service/06-one-service-section-3-sec3.md` §3.2.2）

#### 7.3.3 时间语义：最新值，还是可复现的快照

**机制是什么**：接口返回的是**当前最新一次计算的结果**，还是**按 `event_time` 指定的历史值**。

**定性机制表**：

| 候选 | 历史由什么承载（入口） | 谁决定"能不能回溯" | 典型失败形态 |
| --- | --- | --- | --- |
| 数仓宽表 + 调度 | 每天一列 / 每个分区一份 | 分区策略（保留多久由调度与存储决定） | 查的是"那一天算出来的值"，不是"按 `event_time` 取的值"；重算历史后旧值变了 |
| 口径配置 + 自建产出 | 时点键 + 分区（两者可并存） | 你（产出时就决定，事后补不回） | 只按 `dt` 分区、没有时点键，迟到数据一进来历史就对不上 |
| 特征平台改造 | 特征的 Point-in-Time 取数 | 特征平台的时间列语义 | 特征侧管"只能用当时能看到的数据"，回答不了"当时判的是什么" |
| 指标平台扩展 | 指标模型里没有实体级时点 | 指标模型的粒度 | 只能给"某天的汇总"，给不出"某个实体当时那一档" |
| 商业 CDP / 标签平台 | 通常只有最新值 | 产品的服务模型（历史要么不存、要么不开放） | 申诉与复盘答不出，且这是产出时就覆盖掉的 |
| 全自研 | 时点键 + 分区 | 你 | 与独立族同因 |

**它在各候选中的实现差异**：宽表 + 调度的形态**天然是快照**（每天一列 / 每个分区一份，历史可查——但它查的是"那一天的分区"，不是"按 event_time 取"）；口径配置 + 自研**可以两者都支持**（快照靠分区 + 时点键，最新靠服务）；成品族**通常只给最新值**（它的服务模型是为了实时消费设计的，历史值要么不存、要么不开放）。

**由此必然导出的性质**：因为**申诉与复盘发生在决策之后的数周甚至数月**，所以**"只有最新值"的系统在原理上无法应答这些问题**——而这不是性能或成本问题，是**数据在产出时就被覆盖了**。**因此时间语义必须在产出时就决定**：一旦只存最新值，历史就补不回来（同 §6.4 的失败教训）。

**失效条件**：受监管场景（信贷、准入、风控）必须快照语义——**只提供最新值的候选直接出局**，无论其它维度多强。

**公开证据**：本主题内可核的是判定入口与情形，而不是产品——§2.2 把"同一标签名下的语义 A（快照）与语义 B（最新）是两个资产"写成一句判据，§4.5 模板 1 的口径卡把"时间语义"列为必填的一格（示例取 `snapshot（按 dt 取）`），§4.7 的容灾表则给出这一类语义在故障下的纪律：**"缺一期"要产出 `stale` 而不是 `null`**（因为消费方分不清"这个人不符合"与"这一期没算"）。**这一格在书内没有具名产品可引**：本主题 §4.3 的工具链表把"标签服务"写成能力行、§7.2 的候选表只列到"商业 CDP / 标签平台"一族，两处都不写产品名，因此"某产品支不支持快照"这件事**本节核不到**，只能给判定入口——**看标签表的主键 / 分区里有没有时点维度**（没有，就说明它只有最新语义）。相邻领域有一处可指的同形约束：`02-data-science/01-feature-store` 的 §7 把"先补 `event_time` 与 `label_time`，再谈选型"写成准入项——**那是特征侧的同一件事**（管"只能用当时能看到的数据"），引用时须注意它答的不是"当时判的是什么"。本主题 §6.4 的匿名案例是这一模式在书内唯一的形态示例（匿名案例、不作举证）。【公开】（来源：本主题 §2.2、§4.5 模板 1、§4.7、§6.4；`02-data-science/01-feature-store/01-feature-store-section-7-sec7.md` §7）

#### 7.3.4 缺失语义的表达力：二值，还是三态

**机制是什么**：接口把"无值"表达成什么——**与"不符合"同值**（二值），还是**独立的第三态**（三态）。

**定性机制表**：

| 候选 | "无值"由什么承载（入口） | 谁决定"消费方能不能区分" | 典型失败形态 |
| --- | --- | --- | --- |
| 数仓宽表 + 调度 | `NULL`（表结构本身允许） | 下游每一个 `if` 的写法 | `NULL` 与 `false` 被同一个分支吞掉，报表上表现为"他不符合" |
| 口径配置 + 自建产出 | 返回结构里的 `missing` 标记 | 你（接口契约里要显式写） | 接口写了三态，但消费方没声明 `on_missing`，仍按默认值处理 |
| 特征平台改造 | 特征值的缺失标记 | 特征平台接口的约定 | 特征侧有缺失语义，标签侧把它当"值不存在"，语义在中途丢失 |
| 指标平台扩展 | 聚合口径里没有"单实体无值" | 指标模型的粒度 | 根本表达不了——聚合里"没算到"与"是零"不可分 |
| 商业 CDP / 标签平台 | 二值，或"返回空对象" | 产品的接口约定 | 空对象在消费侧同样容易被当成"不符合" |
| 全自研 | 返回结构里的 `missing` 标记 | 你 | 与独立族同因 |

**它在各候选中的实现差异**：宽表 + 调度常见的是二值（`NULL` 与 `false` 在下游经常被同一个 `if` 吞掉）；口径配置自建可以实现三态（返回结构里带 `missing` 标记）；成品族通常是二值或"返回空对象"——**而空对象在消费侧同样容易被当成"不符合"**。

**由此必然导出的性质**：因为**机器（模型 / Agent）不像人一样对"我不知道"保持沉默**，所以二值语义在 AI 场景里会**把"未覆盖"静默转成"不符合"**（§5.3.2）——而覆盖率通常是 70–90%，意味着**一到三成的人被当成"明确不符合"**。**这条差异在人工消费场景里看不出来（人会追问），在模型消费场景里会直接变成错误结论。**

**失效条件**：当标签被 Agent / 模型消费时，二值语义直接出局——**判据是接口返回里有没有一个区分"无值"的字段。**

**公开证据**：本主题内可核的是接口形态与一条可自测的判据——§4.5 模板 2 把"消费方要读的那一段"写死成 `getTags(entity_id, tag_names, on_missing, on_timeout)` 加上返回必带的三项（口径版本 / 时间语义 / 产出时刻），并给出**本主题反复使用的那条判据**："消费方能区分『这个人不符合』与『这个标签没有值』——分不清，就会出现『未覆盖』被当成『不符合』的静默错判"；§4.7 的容灾表把这条判据延伸成一个演练动作（让一期批任务失败，看消费方看到的是 `stale` 还是 `null`）。**这一格的可见性控制在书内已有具名落点**：本主题 §6.4 ⑤（服务按调用方与该标签的等级决定是否返回，其接口即"该标签对当前调用方是否可见"）。**相邻领域可指的同形结构是"正查与反查是两份各自维护的副本"**：`04-data-assetization/06-one-service` 的 §3.2.2（标签驱动型）把标签服务的两套存取结构写成"正查走 KV 点查、反查走倒排 / 位图"，并给出**判断某个平台的标签服务属于哪种模式的入口**——"看圈人操作是在标签服务内完成，还是被转发到数仓跑一条大查询，后者意味着标签只是宽表的别名"；同节 §4.3 工具链表把"指标 / 标签平台"一栏列为阿里 OneService（商业）与 dbt Semantic Layer / Cube / MetricFlow / Transform / Airbnb Minerva——**这些产品的缺失语义怎么表达，请以其官方文档当前版本为准，本节不引具体文档作据**。**本主题不点名任何一款标签服务产品**：§7.2 只把"商业 CDP / 标签平台"作为一族列出而不具名，因此这一格的判定入口只能是接口返回里那个区分"无值"的字段。【公开】（来源：本主题 §4.5 模板 2、§4.7、§7.2、§6.4 ⑤；`04-data-assetization/06-one-service/06-one-service-section-3-sec3.md` §3.2.2 与 §4.3）

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| **复用族** | 人力（适配既有对象模型） | 治理项在模型里无处安放 → 外部表格 / 流程补丁；后期迁移到独立族的重做 | 随**标签数**增长（且增长率高于独立族） |
| **独立族** | 人力（口径 + 对账 + 抽检） | 对账与抽检是常备投入；服务层的高可用与降级 | 随**标签数**增长 |
| **成品族** | 许可 + 订阅 | 口径迁移成本（换产品即重写）；历史值不可得时的补救；产品未覆盖治理项的自行补建 | 随**席位 / 模块**增长 |

**成本函数的三条判据**：

① **复用族的曲线是"低起点 + 高斜率"**——起步省（不用建口径层），但随标签数增长得快（每个治理项都要外部补丁），且在需要申诉 / 准入时有一次**阶跃式**成本（迁移到独立族）。
② **独立族的曲线是"高起点 + 低斜率"**——前几个标签贵（要建口径层与服务），之后每个标签便宜（加配置）。
③ **成品族的曲线是"台阶 + 迁移陷阱"**——许可是台阶，但**口径锁死意味着换产品的成本是"重写全部标签"**，这个成本不体现在曲线上，而是体现为**锁定**。

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：N = 标签数   h = 单标签的年维护人力（人年/标签）
    H0 = 建口径层与服务层的一次性人力（人年）   P = 许可与订阅（万元）
    m = 治理项数（准入 / 申诉 / 快照 / 三态 …）

复用族：  Cost_reuse(N) = N × h_reuse + (模型未覆盖的治理项补丁成本)   ← 斜率大
独立族：  Cost_ind(N)   = N × h_ind + H0                              ← 起点高、斜率小
成品族：  Cost_prod(N)  = P + N × h_prod + 锁定成本(≈ N × 重写单价)    ← 台阶 + 隐性锁定

反直觉的一条【推算】：若 h_reuse > h_ind（复用族的单标签维护人力更高，
因为每个治理项都要补丁），则存在一个 N* 使两条曲线交叉：
    N* = H0 / (h_reuse − h_ind)
    N 小于 N* 时复用划算，大于 N* 时独立划算——而 N* 通常只有几十个标签。
```

**这个式子的用法**：**先估两个斜率**（复用族与独立族的单标签维护人力），再估一次性投入 `H0`。**如果你的路径规划里标签数会超过几十个，交叉点会提前到来**——而"先用特征平台顶一下、以后再抽出来"这个常见决策，实际上是在赌标签数不会增长，而标签数几乎总是会增长（§6.3 的膨胀速率）。

**成品族的"隐性锁定"怎么代进式子**：它那一项写的是 `锁定成本 ≈ N × 重写单价`，其中**重写单价不是许可费，是"把一个标签的口径从产品语义翻回你自己的语义"所需的人力**——它由三件组成：口径表达式要不要按目标形态重写、历史值能不能带走、消费方的接入要不要改。**这三件里最贵的是第二件**：如果产品只给最新值，那么锁定成本里还含一项**不可恢复的历史**（§7.7 把它单列为唯一完全不可逆的一格）。据此可以给一条不需要任何价格信息的判据：**在评估成品族时，不要问"年费多少"，要问"换掉它需要重写多少个标签、其中多少个带历史值"**——前一个问题有报价，后一个问题没有，而后者才是这条曲线真正的形状。

**一条经验判据**（【经验】）：多数团队在**标签数十到上百个**、且消费方以人为主时，复用族（把标签寄生在既有对象模型上）在用得住的区间内；一旦出现"标签要进生产决策"或"标签要被模型消费"这两个信号，**门槛开始起作用的时点就不再由标签数决定**——第 1、2 条门槛会先于成本曲线把你推到独立族。**这条线是经验线而非定律**，可自行核验的判据是：数一下**过去一年里"因为复用族的模型放不下某个治理项而临时用表格或流程补"的事发生了多少次**——只要这个数不为零且不下降，成本曲线就在按高斜率走。

**成本表里最容易漏的一项**：**误判的代价没有进入任何一条曲线**。"先用宽表顶一下"这个决定在成本上确实便宜，它的问题不在曲线，而在**这套东西会以"看起来正常"的方式产出错误名单**（§2.2 的 `u`、§6.2 的七成重合）——按三条曲线选出来的方案，可能是**成本最低而名单最不准的那一个**。因此成本函数只能用来在**已通过门槛的候选之间**排序，不能用它来选门槛。

### 7.5 决策树（每个分支都要有阈值依据）

1. **标签会不会被"机器"消费（模型 / Agent / 规则引擎），或会不会进入影响个人待遇的决策？**
   - **会** → **复用族与二值语义的成品族出局**；必须选能表达三态、能存快照、能接准入等级的形态；进入第 3 问。
   - 不会（只给人看报表）→ 进入第 2 问。
2. **标签数会超过几十个吗？**
   - 不会（**20 个以内**且长期稳定）→ **数仓宽表 + 调度就够**：上平台是治理过剩。
   - 会 → 进入第 3 问。
3. **已有成熟的特征平台或指标平台吗？**
   - 有，且**你能接受"用外部机制补治理项"**（准入 / 申诉 / 快照用流程与表格补）→ **复用来顶一段**，但要明确"何时抽出来"（用第 4 问的判据）。
   - 有但要求治理完整 → 进入第 4 问。
   - 没有 → 进入第 4 问。
4. **团队能不能长期维护口径 + 对账 + 抽检（按 0.3–1 人年的常备投入量级估算【经验】）？**
   - 能 → **独立族（口径配置 + 自建服务）**，控制力最强。
   - 不能 → **成品族**，但必须**先压测两件事**：口径能不能导出、支不支持快照语义（§7.1 的门槛）。

**阈值的诚实说明**：上表的"20 个以内"与"0.3–1 人年"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的标签数与排期校准，**不要当门槛用**。

**每一问的依据来自哪一节**（树里的分叉不该是偏好，每一条都要能指回本主题的某个判据）：

- **第 1 问（会不会被机器消费 / 会不会影响个人待遇）**：依据是 §7.3.4 与 §7.3.3 的失效条件——二值语义在机器消费下出局、只提供最新值在受监管场景下出局；这一问的作用是**淘汰**而不是排序，所以它必须放在第一层。判据是"生产决策的读取路径里有没有这个标签"，而不是"业务说它重要"。
- **第 2 问（标签数会不会超过几十个）**：依据是 §7.4 的交叉点 `N* = H0 / (h_reuse − h_ind)`——复用族的曲线斜率更高，因此当标签数越过交叉点，独立族的累计成本开始更低。**精确的交叉点取决于你的 `H0` 与两个斜率**，树里的"几十个"只是这个式子在常见取值下的量级投影【经验】。
- **第 3 问（有没有成熟的特征平台或指标平台）**：依据是 §7.3.1 的机制——复用族省下的是"建口径层"，代价是**治理项在模型里无处安放**；所以这一问的真判据不是"有没有这套平台"，而是"**你能不能接受用外部表格与流程补治理项**"，以及**有没有写下"何时抽出来"的条件**。
- **第 4 问（能不能长期维护口径 + 对账 + 抽检）**：依据是 §4.6 的人力三项（口径维护与业务确认、对账与抽检、治理与申诉）——**这三项都不是一次性的，且随标签数增长**。注意这一问的判据是"**有没有人**"，不是"有没有预算"：对账与抽检是常备动作，缺的是承接人而不是钱（§3.2.7 的"只标记不退役"就是同一件事的表现）。
- **第 5 条门槛（不在树里，但决定树能不能用）**：口径能不能导出、历史值能不能带走——它不构成一个分叉，因为它**对所有分支都是同一句话**：不满足就换候选（§7.7 的『产品锁定的口径→可导出』与『只存最新值→快照』两格）。把它放在树外，是因为**它没有"看情况"的余地**，写成一条分叉反而会让它看起来可以和其他条件权衡。

**为什么树里没有"预算"节点**：预算是上面几条判断在账面上的投影，而不是一个独立的筛选条件。把预算当分叉，最常见的后果是**为省许可费选了一个机制上要持续投入人力的形态，两年后发现人力成本更高**【经验】——许可费是一次性的账，口径维护、对账与抽检是按年滚的账（§7.4 的三条曲线形状不同），而立项时只看得到前者。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 标签个位数、只给人看 | 数仓宽表 + 调度 | 口径配置 + 自建 | 上平台会引入治理成本而无收益 |
| 标签几十个、给规则引擎用 | 口径配置 + 自建产出 | 特征平台改造 | 复用族的治理项要外部补，几十个标签时补丁还管得住 |
| 标签上百、要给模型 / Agent 用 | 独立族（口径层 + 服务） | 成品族 | 复用族的三态与快照无处安放；成品族未必支持 |
| 受监管场景（信贷 / 准入） | 独立族（**快照语义 + 准入等级 + 申诉字段**） | 成品族（须验快照） | 只提供最新值的候选直接出局 |
| 实时 + 离线同时要 | 独立族（**双引擎同源 + 逐实体对账**） | 复用族（若特征平台支持双产线） | 无逐实体对账能力则名单错误无法发现 |
| 运营侧要快速圈人 | 标签平台 + **独立的分群/圈选模块** | 成品 CDP | 把分群当标签存会让台账膨胀（§6.3） |
| 团队只有 1–2 人 | 成品族 | 数仓宽表 | 独立族的口径与对账人力不会因为它小就消失 |

**组合的两条次序原则**：① **先把口径抽出来（含五个边界），再谈平台**——口径的不变部分应当独立于实现（§4.1 的反面）；② **先把逐实体对账建起来，再上实时**——没有对账能力时上实时，等于把一个无法验证的不一致引入生产。

**第三条原则（方向相反但同样重要）**：③ **先把使用度埋点建起来，再谈治理**——没有埋点，准入与退役都无源之水（§5.3.5）；**而在标签数还少时建埋点，成本极低。**

**矩阵的读法**：每行结尾的"不选它的原因"**不是能力不足，而是机制不落在收益点上**——复用族不是"功能少"，是治理项在它的模型里没有位置（§7.3.1）；成品族不是"性能差"，是口径与历史值的掌控权换了主人（§7.3.3）。判断矩阵有没有用对，只回答一个问题：**我的痛点是不是恰好出现在我准备引入的那个机制所作用的位置上**。痛点在上游变更的传播、而准备引入的是查询性能优化，这一行的首选就选错了。

**三个常见组合（各说明职责边界与运维代价）**：

1. **口径配置 + 自建产出 + 独立的分群 / 圈选模块**（本主题最常见的形态）：口径层管"判定是什么"，圈选层管"把谁找出来"，两者共用一个服务出口。**职责边界**：圈选只消费"可信"级标签（§3.4 的组合四）。**运维代价**：两套界面（一次查询 + 资产管理）都要维护，且要在界面与文档上把"这个人群是临时的"讲清楚——否则运营仍会按"能复用"的方式去用它（§6.3）。
2. **数仓宽表 + 调度起步，按信号逐步补齐**：先只有宽表列与调度，等到出现第一个失效信号再加部件——第一次"两个人讲不清同一个标签怎么算"就建口径层，第一次"离线与实时名单不同"就建逐实体对账，第一次"生产决策用错标签"就上准入等级。**职责边界**：每一步只补一个部件，不预先平台化。**运维代价**：宽表阶段的标签**没有服务层**，因此"给系统用"这条需求一旦出现，改动不是加缓存而是补一层（§4.1 的 Step 5）。
3. **独立口径层 + 复用既有流引擎作为在线产线**：口径与治理自建，产出复用数仓与流平台的既有资源。**职责边界**：**同源的表达力上界由两侧引擎的交集决定**，超出交集的部分必须显式声明"仅 T+1"（§6.2 与 §4.2（2））。**运维代价**：多出一套常态化的逐实体对账任务与看它的人；另外**两侧引擎的升级节奏不再由你控制**，一次引擎版本变更就可能让某类算子从"双引擎可表达"变成"只有一侧可表达"。

**三个组合的共同点**：**先定口径的归属，再定产出的形态，最后才定圈的界面**——次序反过来（先做圈选，因为"看得见、跑得快"）就是 §6.5 记的第一条反面：查询被当成资产，台账膨胀，而真正的口径仍然散在各处。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 复用族 → 独立族 | 需要申诉 / 准入时模型无处安放 | 把口径搬出来单独管；补快照与三态；重建服务层 | **以季度计**【经验】，且**历史标签值若未存则不可恢复** |
| 宽表 → 口径配置 | 加标签一直在排期 | 逐个抽口径 + 逐实体比对原值 | 以月计，**与标签数成正比** |
| 只存最新值 → 快照 | 申诉与复盘答不出 | 补时点键 + 重算历史（**若上游历史不可得则做不到**） | **部分不可逆**：上游已不可得时，只能从今往后的快照 |
| 比人数 → 逐实体对账 | 名单不一致被发现 | 建对账任务 + 定位边界差异 | 以周计（工具简单，**难在定位与修复**） |
| 分群当标签存 → 分离 | 台账膨胀、治理失效 | 把活动人群迁出资产台账；改为保存条件 | 以月计，**存量清单的人工甄别是主要工作量** |
| 产品锁定的口径 → 可导出 | 换产品要重写全部标签 | 逐标签重写口径 + 重建服务对接 | **以季度计**，且**期间业务不能停** |
| 无使用度 → 有埋点 | 不知道哪些能退 | 补埋点 + 观察一个季度 | 以周计建埋点，**观察期无法压缩** |

**一条硬结论**：七条里最贵的是**"口径锁定之后的收回"**——它不只是重写，还包括**历史值的恢复**（若当时只存最新值，那段历史永久不可得）。**所以第 1 条门槛（口径能不能导出）必须在第一版就判对。**

**第二条硬结论**：上表里有一项的代价**完全不可逆**——"只存最新值 → 快照"里的历史部分。**其余六项都是"要花时间"，这一项是"花时间也拿不回来"**；这决定优先级：**如果只能做一件事，先把时点键与历史留存做上**（成本极低），而不是先把服务性能优化一遍。

**"工作量量级"这一列怎么读**：它写的是**动作本身的耗时**，而一次迁移真正的账单通常不止这个量级——因为下面三笔都要另算【经验】：

- **并行期的成本**：迁移期间业务不能停，因此新旧两套会**同时运行一段**（口径双跑、对账双跑、消费方两边接），这段并行期的维护人力是双份的；
- **重校准的成本**：位置或引擎一变，**原来的阈值与边界要重新验一遍**（离线与实时的边界条件、抽检的抽样口径、告警的阈值），这一步最常被漏掉，表现为迁移之后告警量上升、而没人知道是新问题还是校准问题；
- **团队再学习的成本**：从"写 SQL"到"填口径卡"、从"看结果表"到"看对账差异分布"，**是三种不同的日常工作**——迁移失败的常见形态不是工具没换，而是**换了工具但继续按老习惯用它**（例如口径配置建好了，新标签仍然直接改 SQL）。

**把三笔账加进去之后，七条迁移的相对次序会变**：表里"以周计"的两条（比人数 → 逐实体对账、无使用度 → 有埋点）加完并行期仍然最便宜，因此它们**应当排在最前面**；而"以季度计"的两条（复用族 → 独立族、产品锁定 → 可导出）本来就贵，加上并行期与再学习之后，**它们已经不属于"顺手做一个"的范围，而是需要一次立项的改动**——这也是 §7.5 把门槛放在决策树最前面的现实理由。

### 7.8 小结

**按处境对号入座（不是打分）**：

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 标签会给系统 / 模型用 | 先解决三态与快照，再谈平台选型 | 这两条是门槛：二值与"只有最新值"在机器消费与受监管场景下直接出局（§7.1、§7.3.3、§7.3.4） |
| 标签个位数、只给人看 | 数仓宽表 + 调度就够 | 上平台的收益是治理，而治理成本从这里才刚刚开始 |
| 已有成熟特征 / 指标平台 | 复用来顶，但写下"何时抽出来"的条件 | 复用族省了建口径层，代价是治理项在它的模型里没有位置（§7.3.1） |
| 标签要进生产决策 | 独立族（快照 + 准入等级 + 申诉字段） | 复用族与成品族都可能给不出可复现的当时值 |
| 团队只有一两人 | 成品族，但先压测口径能否导出、历史能否取回 | 独立族的口径与对账人力不会因为团队小而消失（§7.4） |
| 运营要快速圈人 | 分群与资产分成两个台账 | 把分群当资产存，台账会被查询淹没，而这一步没有报错（§7.1 第 5 条） |
| 还没确定要不要上平台 | 先做两件不依赖选型的事：口径卡 + 逐实体对账 | 它们的成本与选型无关，且是其余一切的前提（§6.5） |
| 已经上了成品、正在犹豫换不换 | 数两个数：要重写多少标签、其中多少带历史值 | 锁定成本落在这里，而它不在任何报价单上（§7.4） |
| 只看"哪些能退" | 先补使用度埋点 | 没有埋点，准入与退役都无源之水；标签少时建它最便宜（§7.6 原则③） |

> 本节小结：六个候选之间的差异，最终都能归到三问——**口径归谁且能不能导出**（你的配置 / 别的对象模型 / 产品内部）、**一致性验证能不能做到逐个实体**、**时间语义是最新还是可复现的快照**（外加一条 AI 场景的新判据：**缺失语义是二值还是三态**）。四问决定了它们的分族（复用族 / 独立族 / 成品族）与成本曲线形状（复用族低起点高斜率、独立族高起点低斜率、**成品族有隐性锁定成本**）。**选型顺序不可颠倒**：先用"会不会被机器消费 / 会不会影响个人待遇"筛掉不可行，再用"标签数会不会超过几十个"决定要不要平台，最后用团队承接能力在剩下的里选——**把最后一问当权重而不是门槛，是第二年最常见的失效原因**。**本主题有一条与其它主题不同的推论**：**复用族的交叉点通常只有几十个标签**（§7.4 的 `N*`），而标签数几乎总是会增长——因此"先用别的平台顶一下"这个决策，实际上是在赌一个不太可能成立的假设。**本节还有一条贯穿全节的读法**：四个机制单元（§7.3.1–§7.3.4）讲的是**候选之间的差别**，而 §7.1 的第 5、6 条判据讲的是**你自己的选择**——前者决定你在族内怎么挑，后者决定你会不会在一年后发现台账认不全、或者两个实现的值悄悄不一样了。**两件事都要问，而它们不在同一张表里。**

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次**门槛检查**（不是打分）：口径可抽出与可导出、逐实体一致性、缺失语义表达力、时间语义、分群与资产分离、运维承接——**哪一条是"不满足"而不是"分数低"**？那一条就是你最可能被迫迁移的方向（§7.7）；而你今天的补救成本，是否还落在"以周计 / 以月计"的那几格里？**另一问更具体**：如果明天要换掉现在的标签系统，**你的口径能不能导出来、历史值能不能带走**？答不出，说明你的标签还没有真正掌握在自己手里。
