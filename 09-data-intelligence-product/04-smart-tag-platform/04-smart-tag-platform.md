## 1. 概念与定位

### 1.1 是什么

**工业定义**：标签（Tag）是**对一个实体在某个维度上的、带口径与时点的判定结果**。它的形式化定义比"一个字段"严格得多：

```
Tag = (entity, name, value, caliber, event_time, produce_time, source, owner, level)

  entity       被标注的对象（用户 / 商品 / 内容 / 门店 / 设备）
  name         标签名（如「高价值用户」）
  value        取值（枚举 / 布尔 / 数值 / 向量 / 列表）
  caliber      口径：判定规则本身（可执行、可版本化）——这一项是标签与字段的分界
  event_time   这件事发生在业务上的时刻
  produce_time 这个标签被算出来的时刻
  source       来源（事实 / 模型 / 预测）与依据
  owner        归属人 / 团队
  level        准入等级（试运行 / 可信 / 已退役）
```

**工程定义**：在数据架构师手里，标签平台是**把"从数据到判定"的过程做成一条可复用、可审计的产线**：

- **口径层**：标签的定义（规则 / 模型 / 预测）与版本——**平台的核心资产，也是最容易被忽略的一件**；
- **生产层**：离线（批）与在线（流）两条产线，从同一份口径产出；
- **服务层**：点查（单个实体的标签）与批量（人群圈选 / 分组下发）；
- **治理层**：准入等级、时效声明、血缘、退役与影响分析。

**「标签」与「特征」「指标」的边界**（这是本主题的判据表，也是本主题存在的理由）：

| 维度 | 指标（Metric） | 特征（Feature） | 标签（Tag） |
| --- | --- | --- | --- |
| 回答的问题 | **整体**怎么样 | **喂给模型**什么 | **谁**是什么 |
| 粒度 | 聚合到维度（日 / 渠道 / 类目） | 实体 × 时点（供模型消费） | 实体（供人 / 规则 / 模型消费） |
| 主要消费者 | 人（报表 / 看板） | **模型**（训练与推理） | **人 + 规则引擎 + 模型**（三方共用） |
| 口径要求 | 权威、唯一（[Ch1 §10 指标体系](../../01-modeling/10-metric-system/10-metric-system.md)） | 可复现、无穿越 | **可解释、可申诉**（标签会影响人的待遇） |
| 失效的后果 | 决策基于错的数 | 模型效果下降 | **人被打错标**（申诉、合规风险） |

**一条判据**：**当"这个标签为什么给他打上"必须能向本人解释时，它就不是特征，而是标签。** 这条判据决定了标签平台必须有的三件东西：口径可执行、依据可回溯、结果可申诉——特征平台不需要这三件。

### 1.2 为什么需要

标签平台不是"特征平台的改名"，而是**被四件事逼出来的**：

1. **三方共用同一份判定**：人（运营看人群）、规则引擎（营销 / 风控的 if-else）、模型（作为输入特征）都要用"高价值用户"这个判定。**如果三方各自实现一遍，三份口径必然漂移**——运营圈出 10 万人、风控算出 8 万人，而两个数都自称是"高价值用户"（同 [Ch1 §10 指标体系](../../01-modeling/10-metric-system/10-metric-system.md) 的口径灾难，只是对象从指标变成实体）。
2. **标签会被人消费，因此要能解释与申诉**：一个"低信用"标签会直接影响一个人的额度。这与"特征算错了"是两个量级的事——**它要求口径可解释、依据可回溯、结果可申诉**，而这三件都不是特征平台的职责。
3. **时效是一等需求**：T+1 的标签用于日常运营、T+0 的标签用于实时风控与推荐。**时效不是刷新频率的配置，而是标签定义的一部分**——同一个标签名下的两个时效，是两个不同的资产。
4. **标签会腐化**：业务变了、口径过期了、上游字段下线了，而**标签不会自己失效**——它会继续产出看起来合理的值。因此必须有准入等级与退役机制（§3.2.6、§3.2.7）。

**这四件事的共同点**：它们都不是"算得准不准"的问题，而是**口径、解释、时效与生命周期**问题——这正是标签平台的职责范围。

### 1.3 在 AI 时代数据架构中的位置

```
   [数仓 / 湖仓（明细与汇总）]  ← Ch3 数据栈
              ↓ 口径是判定的唯一来源
   [标签平台 · 本文]  口径层（规则 / 模型 / 预测）+ 生产层（批 / 流）
              ↓                    ↓                    ↓
   [人：人群圈选]        [规则引擎：if-else]     [模型：特征输入]
        ↓                      ↓                      ↓
   运营 / 投放            风控 / 营销            推荐 / 排序

```

### 1.4 演进历程

- **宽表阶段（2005–2012）**：标签就是宽表里的一列，由 ETL 直接写死。**问题**：加一个标签要改一次 ETL，且口径散在 SQL 里无法复用。
- **标签工厂阶段（2012–2018）**：把"标签定义"抽出来做成配置（规则 + 数据源 + 调度），一批标签按配置产出。**这是"标签平台"的起点**；主要收益是"加标签不再改 ETL"。
- **标签 + 在线服务阶段（2015–2020）**：出现标签服务平台（HTTP / RPC 点查与批量查询），标签从"给人看"变成"给系统用"。**同期出现的问题**：在线与离线口径不一致（同一标签两个值）。
- **标签 + 实时阶段（2018 至今）**：实时标签成为一等形态（流式产出 + 在线服务），**同一份口径同时产出离线与在线**成为平台的硬要求（同 [Ch2 §01 特征平台](../../02-data-science/01-feature-store/01-feature-store.md) 的 Point-in-Time 一致性思路）。
- **标签 + 治理与 AI 阶段（2021 至今）**：标签进入治理体系（准入等级、退役、影响分析）；同时**LLM 让"从非结构化数据产出标签"成为新的一支**（从会话 / 文档 / 访谈里抽取标签），但也带来"标签口径不可解释"的新风险（§5.2）。

> 演进的主线只有一句话：**标签的定义从"藏在 SQL 里"移到"配置里"，再从"配置里"移到"带版本、带准入、带时效的资产层"。**

## 2. 核心原理

### 2.1 关键概念定义

- **实体（Entity）**：被标注的对象。**标签平台的第一个决定是实体体系**——用户 / 商品 / 内容 / 门店 / 设备，以及它们之间的关联（"门店的标签"与"门店里的人的标签"是两件事）。
- **事实标签（Factual Tag）**：直接来自可核验的数据事实（近 30 天登录次数、注册渠道、最近一次下单金额）。**特点：可复算、零歧义、可申诉**——"你近 30 天登录了 12 次"是能对的。
- **模型标签（Model Tag）**：由模型打上的**当前状态判定**（价格敏感度分档、内容偏好类目、活跃度分层）。**特点：有置信度、可解释性是概率性的**——因此它必须带模型版本与置信度。
- **预测标签（Predictive Tag）**：对未来事件的预测（流失概率、复购概率、违约概率）。**特点：它依赖"观察窗口 + 表现窗口"两个时间轴的划分**，且**预测的时刻必须钉住**（否则同一个标签在不同时间取到不同值，而业务会把它当事实用）。
- **口径（Caliber）**：标签判定的**可执行定义**（规则表达式 / 模型引用 / 预测配置 + 观察与表现窗口）。**口径是标签与字段的分界**——没有口径的标签只是一个字段别名。
- **时效（Freshness）**：标签的 `event_time` 与 `produce_time` 的关系。**T+1 / T+0 不是刷新频率，而是两类资产**——同一名字的 T+1 与 T+0 标签，口径可能不同、消费者不同、SLA 不同。
- **标签服务（Tag Service）**：对外提供点查（`getTags(entity_id, tag_names)`）与批量查询（按条件圈选实体集）的服务。**它的可用性要求通常高于数据侧**——因为它在关键路径上（风控、推荐、营销触达）。
- **人群 / 分群（Segment）**：由多个标签条件组合出的实体集合。**分群不是标签**——它是**查询**，因此它可以随时重算、可以临时创建，而标签必须是被治理的资产（§3.2.8）。
- **准入等级（Level）**：标签的可信度等级（**试运行 / 可信 / 已退役**）。**判据**：只有"可信"级的标签可以被写入生产决策路径——这条等级是标签治理与指标治理最大的形式差异。
- **血缘（Lineage）**：标签 ← 上游字段 / 模型 ← 上游表。**标签血缘的特殊价值**：上游字段下线时，能立刻回答"哪些标签会失效、哪些业务会受影响"（[Ch11 §09 血缘](../../11-cross-cutting/09-data-lineage/09-data-lineage.md)）。
- **申诉（Appeal）**：对被判定结果提出异议并得到解释的通道。**它是标签（而非特征）独有的需求**，因为标签会影响人的待遇（额度、优惠、准入）。

### 2.2 数学 / 形式化基础

**标签是一个带时点的函数**。给定实体 `e`、标签定义 `t`（口径）、评估时刻 `τ`，标签值为

```
value = t(e, τ)

其中 t 的输入必须只包含 τ 之前可观测的数据（无穿越）
```

**这条约束是所有标签正确性的根源**，且它比特征侧的同一约束更严格——因为**标签会被人当事实读**：

- **特征穿越**的后果是模型效果虚高（离线好、线上差）；
- **标签穿越**的后果是**业务按一个当时不可能知道的事实做了决策**（例如"流失用户"标签用到了"本月已注销"这个未来事实）——而人在报表里看到它时，会认为它是当时就知道的。

**口径的唯一性定理式表述**。设同一逻辑标签有 `k` 份实现（离线批、实时流、规则引擎、模型输入各一份），若它们的判定函数为 `t₁…t_k`，则

```
口径一致 ⟺ ∀e, τ :  t₁(e,τ) = t₂(e,τ) = … = t_k(e,τ)

工程判据（可执行）：抽 N 个实体，在同一个 τ 上比对各实现的值 ——
   不一致率 u = #{e : ∃i,j  tᵢ(e,τ) ≠ tⱼ(e,τ)} / N
   要求 u = 0（不是"接近 0"）
```

**为什么要求 `u = 0` 而不是"接近 0"**：因为不一致的样本**不是随机分布的**——它们集中在边界条件上（时间边界、空值、迟到数据），而**业务恰恰会盯着边界用户**（"这个用户为什么在这个人群里"）。**因此标签口径的一致性检查必须"逐个实体比"，不能只比总量**（总量相同而个体不同的两份实现，是常见且危险的形态：10 万人对 10 万人，但名单差 2 万）。

**时效的两种语义（必须显式声明）**：

```
语义 A（快照 / Snapshot）：标签有明确的 event_time，取的是"那一刻的事实"
    —— 适合风控、审计、申诉（可复现）
语义 B（最新 / Latest）：标签取"当前最新一次计算的结果"
    —— 适合实时推荐、个性化展示（新鲜优先）

同一个标签名下的两种语义是两个资产：
    A 可以重算（同一 τ 永远同一结果），B 不能（重算会得到更新的值）
判据：业务问"上个月他是高价值用户吗"——你的标签能答吗？
      能（按 τ 取快照）→ 语义 A；只能答"现在是不是" → 语义 B
```

**这条区分是本主题最容易被忽略的一条**：多数平台默认语义 B，而**风控与申诉需要语义 A**。把它们当成一个标签，就会出现"申诉时拿不出当时的值"——**而这不是数据丢了，是语义从一开始就没有被表达。**

**人群圈选的规模估算**（决定架构而不是决定体验）：

```
设：标签数 T、实体数 E、单个标签条件的平均选择率 s（命中比例）
等值条件：候选集 ≈ E × s                        —— 与标签数无关，快
多条件组合（AND）：候选集 ≈ E × Πsᵢ              —— 组合越多越小
多条件组合（OR）： 候选集 ≈ E × (1 − Π(1−sᵢ))     —— 组合越多越大

判据：当 s 很小（高选择性标签）时，索引（按标签值建倒排）是必需的；
     当 s 很大时，全扫 + 过滤反而更好 —— 因此分群引擎要能按 s 选执行计划
```

**标签质量的四个度量（必须按标签分别定义）**：

```
覆盖率    coverage  = 有值的实体数 / 应标实体数     —— 空值率是它的补
一致性    consistency = 1 − u（§2.2 的第一式）      —— 多实现之间
新鲜度    freshness = τ_now − produce_time          —— 分位数，不是均值
准确率    accuracy  = 人工核对通过比例              —— 只对抽样可行
```

**一条判据**：**这四个数必须按标签给出，而不是给一个平台级的"标签质量分"**——因为不同标签的失败后果不同（风控标签的准确率与"兴趣偏好"标签的准确率，业务可接受度差一个量级）。

### 2.3 关键算法 / 方法

**① 事实标签的产出（最简，但要处理三个边界）**：

```text
事实标签 = 聚合(明细表, 分区, 实体键, 口径表达式)

三个必须处理的边界：
  ① 空值 vs 零：无记录时是 "0" 还是 "无值"？
       —— 语义不同（"没用过"与"用了 0 次"在业务上是两件事）
  ② 迟到数据：分区到期后又有新数据进来怎么办？
       —— 要么声明"该分区已封板"，要么重算并记录重算版本
  ③ 实体键缺失：明细里主体键为空 —— 进"未归属"桶，不能静默丢弃
       —— 判据：明细总量 = 各实体标签用量 + 未归属用量（守恒）
```

**② 模型标签的产出**：模型打标 = 特征工程 + 模型推理 + **分档**。**平台侧的关键不是模型本身，而是三样配套**：**模型版本**（进了标签的血缘）、**置信度**（作为标签值的一部分或独立列）、**分档边界**（连续分数到枚举的切分，**边界值必须由业务确认**——"0.6 算不算高价值"是业务问题）。

**③ 预测标签的产出（窗口划分是本条的全部难点）**：

```text
观察窗口 (observation window)  ← 用这段时间的特征做预测
表现窗口 (performance window)  ← 在这段时间里观察是否发生了目标事件
预测时点 (prediction point)    ← 两窗的交界，标签必须钉住它

  ├──────── 观察窗口 ────────┼──── 表现窗口 ────┤
                          ↑
                     prediction point（标签"看到"的最晚时刻）

判据（防穿越）：标签的 produce_time 可以晚于 prediction point，
               但它的输入数据不得晚于 prediction point ——
               这条区分是"离线批算"与"穿越"的分界
```

**④ 离线与在线同源的实现路径**（三条，代价递增）：

| 路径 | 做法 | 代价 | 适用 |
| --- | --- | --- | --- |
| **双跑同一 SQL** | 离线批与流任务用同一段口径（同一份 SQL / 同一份 DSL），只是执行引擎不同 | 需要 DSL 或 SQL 方言兼容层 | 多数事实标签 |
| **流批一体引擎** | 用同一套代码在批 / 流两种模式下执行 | 引擎绑定、运维面变化 | 已选流批一体栈的团队 |
| **在线反查 + 增量修正** | 在线取离线快照 + 叠加当日增量 | 一致性靠对账保证，最脆弱 | 过渡期方案 |

**判据**：**选第一条，除非已有流批一体栈。** 第二条的收益（一份代码）通常不抵引擎绑定的代价；第三条只应作为过渡。

**⑤ 人群圈选的执行计划选择**（按 §2.2 的选择率）：

```text
if 条件的选择率 s 很小（高选择性）:
    走倒排索引（按标签值 → 实体集），取交集
elif s 很大（低选择性）:
    全实体扫描 + 逐条件过滤（索引反而更慢）
else:
    混合：先用最小 s 的条件缩小候选，再过滤

判据：分群引擎要能解释"这次为什么选了这个计划"（可解释的执行计划），
     否则用户只会看到"圈选很慢"而无从优化
```

**⑥ 标签血缘的采集**：从**口径表达式**解析依赖（SQL / DSL 的 parse），而不是靠人工登记。**判据**：**上游表下线时，能否自动列出受影响标签**——手工登记的标签血缘一定会在半年内过期（同 [Ch11 §05 血缘与影响](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md) 的结论）。

### 2.4 与相邻概念的关系

- **标签平台 vs [Ch2 §01 特征平台](../../02-data-science/01-feature-store/01-feature-store.md)**：特征平台解决"给模型喂什么"（Point-in-Time 正确、训练线上一致、低延迟读取）；标签平台解决"**这个实体是什么、凭什么这么说**"（口径可解释、依据可回溯、结果可申诉）。**两者会共用同一批底层计算**（很多模型标签的输入就是特征），但**治理要求不同**——特征不需要"申诉通道"，而标签必须要有。
- **标签平台 vs [Ch1 §10 指标体系](../../01-modeling/10-metric-system/10-metric-system.md)**：指标是**聚合**的口径唯一，标签是**实体**的口径唯一。**判据**：一个"标签"如果只在聚合层面被消费（"高价值用户有多少人"），它其实是指标；只有在**需要指名到个体**时才是标签。
- **标签平台 vs [Ch4 §08 数据目录](../../04-data-assetization/08-data-catalog/08-data-catalog.md)**：目录管"有哪些数据资产、谁负责"；标签平台管"标签的定义、产出与准入"。**接口是"标签的登记项"**——标签应当作为一类资产出现在目录里（带 Owner 与准入等级）。
- **标签平台 vs [Ch9 §02 决策智能](../02-decision-intelligence/02-decision-intelligence.md)**：决策智能的输入大量是标签（"对高价值且价格敏感的客户推券"）。**接口是"标签的可信度等级"**——决策侧必须只消费"可信"级标签，否则会把试运行的标签写进生产决策。
- **标签平台 vs 规则引擎**：规则引擎消费标签（`if tag.price_sensitive == 'high' then …`）；**标签平台不执行规则**，它只保证"标签的值与口径一致"。把规则写进标签平台，会让标签变成"动作的别名"，从而无法被多场景复用。
- **标签平台 vs [Ch8 §02 数据安全与合规](../../08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance.md)**：标签里可能含个人信息（"有慢性病""月收入分档"），因此标签本身要分级、要脱敏、要被权限管。**这条关系常被忽略**——标签被认为是"加工后的数据所以不敏感"，而**恰恰是加工后的判定更敏感**（它直接刻画一个人）。

> 💡 **思考锚点**：挑一个你们正在用的标签（"高价值用户""流失风险""价格敏感"任选一个），回答四个问题：① 它的**口径**在哪（一段代码、一个配置，还是一个人的记忆）？② 有没有**第二份实现**（离线一份、实时一份、规则引擎里还有一份），它们的值**逐个实体**比过吗？③ 业务问"上个月他是不是这个标签"，答得出来吗（语义 A 还是 B）？④ 如果一个用户来问"为什么给我打这个标"，你现在能拿出什么？四个问题里最先答不出的那一个，就是下一轮该补的地方——你打算先补哪一个？
