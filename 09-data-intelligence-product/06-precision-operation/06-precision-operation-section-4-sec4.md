## 4. 工程实现

### 4.1 落地步骤

这一块有一条与其它主题不同的性质：**它的第一个可交付物是"一次带对照组的活动"，而不是一个运营平台**——因为**没有对照组，后面所有指标都没有意义**。

**Step 1：把分流做对（先做这个）**
实现**用户级稳定分流**：`group = hash(user_id, campaign_id) % 100 < split_ratio`。**判据**：同一用户在同一活动里永远落同一组；跨活动分流互不相关（正交）。**为什么第一步是它**：它是"能测"的唯一前提，且**实现成本极低**——而它一旦做错（依赖时间戳或随机种子），后面所有增量都是错的，且不可察觉。

- **产物**：**一个只吃 `(user_id, campaign_id)` 两个参数的分流函数**（实现与三种常见错法见 §4.2（1）），外加一条"同一用户跑一百次结果一致"的验证记录。这个产物没有平台形态——它是一段可以被单独指向、也能被单独回滚的代码，因此它是在还没有任何配套设施时就能先落地的那一件。
- **为什么必须这一步 / 为什么在这个位置**：它必须排在 Step 2 之前，因为**后面的每一步都在消费"组别"这一列**——口径卡要定"分母是触达人数还是到达人数"，污染检测要比"对照组被同类触达的次数"，Uplift 要拿 `T=1` 与 `T=0` 两批样本训练。分组这一列一旦会漂移，这些比较就全部建立在一个移动的地基上，而且**它错了不报错**（§3.5 表"分流不稳定"一行：后果是"增量被稀释，且是静默的"）。

**Step 2：把归因的四个一致性固定下来**
**事件口径**（"转化"包含哪些动作）、**时间窗口**（触达后多久内）、**分母**（触达人数还是到达人数）、**剔除规则**（退货 / 作弊 / 机器人）——四项写进一份**归因口径卡**，并在指标平台登记。**判据**：两个部门算同一个活动，得到同一个增量。

- **产物**：**一份归因口径卡**（事件口径 / 时间窗口 / 分母 / 剔除规则四项 + 负向指标 + 窗口敏感性检查项，结构见 §4.2（2）与 §4.5 模板 1），在指标平台**登记并带版本号**——"有没有登记"决定它是一份一次性文档，还是一个之后能被反复引用的口径。
- **为什么必须这一步 / 为什么在这个位置**：它必须紧接 Step 1，因为**它是把"分流"翻译成"增量"的那一步**：有了对照组，两个转化率才成为一个可比量；四项口径则决定这个量叫什么。§6.2 把依赖顺序写死成"分流（①）→ 口径卡（§4.2（2））→ 增益建模（②）"，并注明**这不是排期偏好而是数据依赖**；同节的失败教训（"精准人群"越做报告越好看、净增量没变）正是**"没有对照组时，效果未测"**的后果——§6.2 写明"精准与增量在'转化率'这个屏幕上显示为同一个方向，**只有在补了对照组之后才会分叉**"（§1.1："没有对照组时，它的效果是未测的"）；口径卡在这条链上负责的是把 ① 的产出解释成增量，而不是让两条曲线分叉。

**Step 3：装全局频控（按用户，不按活动）**
上限按 `用户 × 时间窗`（渠道可作为子维度，但不能替代用户维度）＋**被挡留痕并上看板**＋**上限有 Owner**。**判据**：新增一个活动时，用户的接收总量上限不变。

- **产物**：**一套按用户的上限**（`Cap(u)` 的取值 + 它的 Owner + 渠道子维度的上限）+ **一条被挡留痕**（字段结构 `{user, window, allowed[], blocked[], reason}` 见 §4.5 模板 2）+ **一块"被挡条数"上得去的看板**。第三件才是这一步真正的验收物——上限写在哪都不决定它是否生效，被挡条数上不上看板才决定它会不会被反复放宽。
- **为什么必须这一步 / 为什么在这个位置**：它必须排在 Step 4 之前，因为**上限定的是"总量"、优先级表定的是"超限时谁被挡"**——上限不按用户，优先级表就没有裁决对象（§3.2.4 的机制：按活动限则总量随活动数线性上升，按用户限则总量恒定，**新增活动只能抢存量**）。它同时回答了那个绕不开的组织问题：上限一旦按用户，被挡的就必然有人来问，因此**上限必须先有 Owner**，否则临时提额会变成常态（§3.2.4 失效点③）。

**Step 4：治理触发式规则**
建立**统一的互斥与优先级表**；并发触发的**去重窗口**；每条规则的**时效性要求**（延迟预算）。**判据**：一次用户行为最多触发一条即时消息。

- **产物**：**一张统一的互斥与优先级表**（每条规则带 Owner、时效性要求 / 延迟预算、并发去重窗口）+ **一次"让一次行为同时命中多条规则"的裁决记录**（§3.2.3 的判定方法就是这一件事，§4.7"触发规则风暴"一行把它写成演练动作，恢复目标是单请求级）。
- **为什么必须这一步 / 为什么在这个位置**：它必须晚于 Step 3——§3.2.3 的代价③写明**触发式触达天然比批量触达更频繁地命中同一个人，它会放大频控压力**，所以上限要先在（Step 3），规则上量之后才有地方被裁决。它之所以不能拖到后面再补，是因为这一模式只有两件要验的东西，而两件都**必须在上线前写死**：去重窗口（同时命中两条时只发一条，被挡的那条在留痕里查得到）与每条规则的延迟预算（§3.2.3 的真实使用："这一模式要验的只有两件东西，都在本主题内"）。

**Step 5：渠道编排与退订一致性**
按渠道分开核算成本；降级链换渠道时**在数据里标注**；退订在**所有渠道一致生效**（含一次跨渠道演练）。**判据**：在任一渠道退订后，其他渠道不再触达该用户。

- **产物**：**一份合并去重后的权威退订名单**（各渠道订阅同一份）+ **按渠道分开的成本核算**（成本函数与"激励常常是数量级更大的那一项"见 §4.6）+ **一次跨渠道退订演练的留档**。
- **为什么必须这一步 / 为什么在这个位置**：它必须早于 Step 7 的护栏，因为**护栏读的是负向指标（退订率 / 投诉率）的数据完整性**——少一条退订事件，阈值就永远不触发；§6.2 ③ 把这条依赖点明为"这解释了为什么 §4.1 把'退订一致'排在护栏之前（Step 5 在 Step 7 之前）"。它同时是本主题唯一一条**合规性**前置（§3.1 约束 4 的"合规边界"一侧，它的过关标志写的就是"退订在**所有渠道一致生效**（有演练）"）：§3.2.5 把"退订只在一个渠道生效"列为最常见、也最容易被投诉的合规缺陷——它不是靠加监控能补上的，只能靠一次名单合并与一次跨渠道演练。

**Step 6：实验分层与污染控制**
把不同活动放在不同实验层（同层互斥、跨层正交）；**污染检测**（对照组被同类触达的次数）写进常规报告。**判据**：能回答"这次实验的对照组被同类触达命中了几次"。

- **产物**：**一份实验分层方案**（层数、每层容量、层间正交的说明）+ **污染检测写进常规报告的一行**（对照组在实验期内被同类触达命中的次数）——这一行的价值在于它把"实验是否成立"变成报告里一个可以被追问的数。
- **为什么必须这一步 / 为什么在这个位置**：它必须早于 Step 7 的长期 holdout，因为**holdout 只有在"同类触达可以被隔离"的前提下才成立**——§4.8 的 10→100 一栏把"先坏的是 holdout 被穿透"列为这一阶段的首要风险（"整体实验没收益"这个说法的出处是 §3.5 表的"长期 holdout 被穿透"一行，本文件 §4.8 同栏）；§6.3 的案例结论是**holdout 组的留存高于处理组——即整体触达量已经过量**，同节点明 holdout 一旦被其他同类活动触达就会退化成污染样本——**污染是读这条结论的前提，不是它的解释**。**分层是隔离的执行面**，所以它必须先到位；顺序反了，holdout 上线第一天就退化成污染样本。

**Step 7：护栏与长期 holdout**
负向指标设**硬阈值**并指定**有权限暂停活动的人**；留一小部分用户作长期 holdout（不接收某类触达）。**判据**：有过一次"因护栏触发而暂停活动"的记录。

- **产物**：**一张负向指标护栏表**（指标 / 分母 / 观察阈值 / 硬阈值 / 超阈值动作 / 执行人六列，见 §4.5 模板 3）+ **一份长期 holdout 名单** + **至少一条"因护栏触发而暂停活动"的记录**。最后一条才是这套东西的验收物——没有它，前两件都只是配置。
- **为什么必须这一步 / 为什么在这个位置**：它是唯一一步把"**谁有权暂停活动**"写成具名职责的动作（§3.2.8 代价②："它需要有权限暂停活动的人"；这与 Step 3 的上限 Owner 是两项不同的职责）——§3.2.8 的判据就是"最近一次因为护栏触发而暂停活动是什么时候"，答不出说明护栏是装饰。它必须排在 Step 3–4 之后：那时组织里已经有带 Owner 的上限表与规则表，护栏表不是给这两张表加列，而是一张与它们**共用同一套 Owner 与登记位置**的新表（指标 / 分母 / 观察阈值 / 硬阈值 / 超阈值动作 / 执行人六列，见 §4.5 模板 3）。它又必须排在 Step 8 之前，因为**Uplift 决定预算投给谁、护栏决定预算的总量**——在总量已经过量的前提下，更准的投放只是让过量发生得更有效率（§6.3 的动机：单活动的增量都为正，而整体早已过量）。

**Step 8：Uplift 定向（在前面都就位之后）**
从历史实验数据训练增益模型；按触达形式分场景；只触达 `τ(i) > c/v` 的人。**判据**：训练数据里处理组与对照组的样本都充足。

- **产物**：**一个增益模型**（T-learner / S-learner 两条路线与各自的适用条件见 §4.2（4））+ **按触达形式分场景的模型清单** + **`τ(i) > c/v` 的触达规则**。
- **为什么必须这一步 / 为什么在这个位置**：它是唯一一步**没有前面的历史实验数据就做不出来**的动作——训练集要同时有 `T=1` 与 `T=0` 两批样本，而这批样本只有 Step 1 与 Step 2 跑过若干次活动之后才存在（§6.2 的数据依赖："② 需要 ① 产出的 `T=0` 样本"）。§3.2.7 的失效点写得很直白：**训练数据里没有 `T=0` 时，增益模型只能退化成"预测转化概率"**——那时它不回答问题，只是把原来的"高转化人群"换了个名字，而报告会显示一切正常。

**顺序的反面（最常见的错误）**：**先做"更精准的人群"、后做对照组**——人群再精准也无法回答"这次值不值"，而**精准人群反而会让"本来就会转化的人"占比更高**（精准 = 更像目标客户 = 更可能自然转化），因此**在没有对照组的情况下，"人群更精准"会让效果报告更失真**。**第二条反面**：**先做 Uplift、后做 A/B**——没有对照组历史数据，增益模型只能退化成转化概率预测（§3.2.7 的失效点）。

### 4.2 关键技术点

**（1）稳定分流的实现（一行代码，但错了全错）**

```python
# ✅ 稳定且正交：只依赖 (user_id, campaign_id)
def assign(user_id: str, campaign_id: str, split: float) -> str:
    h = int(hashlib.md5(f"{campaign_id}:{user_id}".encode()).hexdigest()[:8], 16)
    return "treatment" if (h % 10_000) / 10_000 < split else "control"

# ❌ 三种常见的错法（后果都是"增量被稀释且不可察觉"）
#   ① 用 random.random()      —— 每次调用结果不同，同一用户跨组漂移
#   ② 用 timestamp 参与哈希   —— 同一用户在不同时刻落不同组
#   ③ 用 (user_id) 单键且活动间复用同一 salt —— 跨活动完全同向，
#      导致"总是同一批人做对照组/处理组"，长期偏置
判据：同一用户在同一活动里的分组，跑一百次结果必须完全一致
```

- **机制**：两组的可比性（"除触达之外的一切"期望相同、随机化发生在触达之前、分组依据与结果无关）见 §3.2.2，本节不复述；§4 只取它的实现推论——分流函数只能吃 `(user_id, campaign_id)` 这两个**在触达之前就已确定**的量，任何与时刻相关、或与结果相关的量一旦进入哈希，那个条件就不再成立（这也是上文三种错法共同的错因）。
- **失效条件**：**当分流依赖了时间戳、随机种子或执行节点时**，同一用户会在不同时刻落进不同组，处理组与对照组的边界模糊——**症状是效果报告"看起来像活动无效"，而系统里没有任何报错**（§3.5 表"分流不稳定"一行：后果是"增量被稀释，且是静默的"）。它难查的原因不是算错了，而是**它不改变任何一个数字的计算过程，只改变这些数字的比较基准**。
- **档位**：【经验：实现层不具名产品，判定入口是"同一用户跑一百次是否落在同一组"】；分流与实验平台一侧的具名清单（GrowthBook / Optimizely / AB Tasty / 自研）与三条选型判据（分流一致性 / 口径可自定义 / 支持 CUPED 类降方差）的原文出处已在 §3.2.2 的"真实使用"里给出，本节不重复。

**（2）归因口径卡（四个一致性）**

```yaml
attribution_card:
  campaign: 618-首购券
  event_definition: "支付成功（status=paid）且非退款"      # ① 事件口径
  window: "触达后 7 天"                                    # ② 时间窗口
  denominator: "触达人数"                                   # ③ 分母（不是到达人数）
  exclusions: ["退款", "风控标记", "机器人"]                 # ④ 剔除规则
  guardrails: ["退订率", "投诉率"]                          # 负向指标
  sensitivity_check: "1d / 3d / 7d / 30d 四窗口各算一遍"     # 窗口敏感性
```

**判据**：两个部门用同一张卡，得到同一个增量。

- **机制**：因为**"增量"不是一个自然存在的量，而是由四个口径选项定义出来的一个量**——事件口径决定"什么算转化"，时间窗口决定"归因期算多长"，分母决定"除以谁的人数"，剔除规则决定"哪些行不算数"。四项写在同一张卡上并登记之后，**"两个部门算出同一个增量"才从一句要求变成一个可执行的检查**：任何分歧都能被定位到卡上的某一行，而不是各自重算一遍再互相质疑。它的第二个作用是长期的——**登记带版本，口径的每一次变更因此留下痕迹**，历史报告可被解释为"当时那版口径下的结论"。
- **失效条件**：**当口径卡只活在某次汇报的附件里、没有登记与版本时**，口径会随汇报人变化：两个部门算出两个增量，而**两边都能在自己的口径下自证正确**（§3.5 表"归因窗口不声明"一行：症状"两个部门算出两个增量"，后果"结论不可比"）。第二条失效更隐蔽：**分母不一致**（退订率按触达人数还是按到达人数）会让同一个阈值在渠道之间不可比（§3.2.8 的失效点）。
- **档位**：四项一致性的具体取值是业务假设【经验：随业务与渠道变；时间窗口按你的决策周期取，并以 1d / 3d / 7d / 30d 各算一遍做敏感性检查（结构见 §4.5 模板 1 的"归因窗口"一行）】。

**（3）增量与样本量（决定"能不能测出"）**

```text
uplift = P(Y=1|T=1) − P(Y=1|T=0)
每组样本 n ≈ 15.7 × p(1−p) / δ²        【推算：两比例检验的正态近似】
例：p = 5%、δ = 0.5pp ⇒ n ≈ 29.8 万/组
     p = 20%、δ = 2pp  ⇒ n ≈ 6,280/组
判据：活动候选集小于所需样本量时，正确结论是"本次未测出"，而不是"无效"
      —— 把"未测出"记为"无效"，会系统性地淘汰小活动（而小活动往往是新方向）
```

- **机制**：因为**两组的转化率之差是一个随机变量**，它的波动幅度由两组各自的样本量决定，所以"能不能测出 δ"是一个**候选集规模的门槛问题，而不是分析方法的高低问题**——候选集小于所需样本量时，换什么估计方法都测不出小增量。这也解释了为什么"把新方向放进小活动里试"的团队会系统性地淘汰新方向：新方向天然候选集小，于是它们**全部落进"测不出"，再被记成"无效"**（§6.2"具体数字（档位标注）"一节把这件事写成量化形态）。
- **失效条件**：**当"未测出"被记成"无效"时**，淘汰不是随机的而是有方向的——被淘汰的恰好是候选集最小的那批活动。**症状是活动库里长期只剩大促一类活动能"被证明有效"**，新方向反复试、反复被记为无效，团队最后得出的结论是"新方向不行"，而真实原因是它们从来没有拿到足够的分流样本。
- **档位**：【推算：两比例检验的正态近似——α=0.05、把握度 80% 时 2×(1.96+0.84)²≈15.7，代入你自己的 p 与 δ 即可重算每组样本量】；"p 与 δ 取多少"是业务假设【经验：所需样本按 δ² 反向增长，δ 减半则样本量约变为四倍】。

**（4）Uplift 的两条路线与它们的适用条件**

```text
T-learner：分别训练处理组模型 P₁、对照组模型 P₀，τ̂ = P₁ − P₀
  适用：样本充足；缺点：两次训练的偏差叠加
S-learner（单模型 + 交互项）：把 T 作为特征并加交互
  适用：样本较少；缺点：交互项需要足够的 T=1 与 T=0 样本
判据：训练数据里 T=0 的样本占比是多少 ——
      低于三成【经验】时，任何 Uplift 建模都不可靠
```

- **机制**："把'本来就会转化的人'从目标里剔除、而这部分人在成熟业务里常常占多数"见 §3.2.7，本节不复述；§4 只补它依赖的那个**可检查的等价物**：`τ̂` 必须在**处理组与对照组都存在的样本上**被估计出来，否则它学到的不是"因触达而转化的概率"，而是"会转化的概率"。§3.2.7 与 §6.2 给了同一个量化形态——**成熟业务里观测转化率往往是增量的数倍**【经验：落差随业务成熟度与人群精准度上升】。
- **失效条件**：**当训练数据里没有 `T=0` 样本时**，任何增益模型都只能退化成转化概率预测——**症状是"增益"的排序与"转化概率"的排序高度相关**（§3.5 表"Uplift 无对照数据"一行：症状"模型给出的'增益'与转化概率高度相关"，后果"优化目标没变"）。此时系统照常出分、活动照常上报，**唯一能发现它的动作是查一个数**：`T=0` 样本占比（判据：低于三成【经验】时不可靠）。第二条失效来自触达形式——**换文案 / 换渠道 / 换激励后 `τ` 的分布会变**，因为模型学的是"这种触达下的增量"，不是"所有触达下的增量"（§3.2.7 的代价③）。
- **档位**：训练数据的组成【经验：`T=0` 占比低于三成时任何 Uplift 建模都不可靠】；"用增益模型决定发不发"的具名落点（X-Learner / CausalML / DML + Causal Forest，以及 uplift curve 与 Qini 的评估口径）已在 §3.2.7 的"真实使用"里给出并标注出处，本节不重复。

**（5）全局频控的三维与处置**

```text
限流条件：Σ 触达(u, W) ≤ Cap(u)        —— 上限按「用户 × 时间窗」
渠道可作为子维度：Cap_push(u) ≤ 2/日、Cap_sms(u) ≤ 1/周
但渠道维度不能替代用户维度 —— 否则多通道叠加绕过上限
超限处置（三选一，必须事先定死）：
  ① 丢弃（最严，用户收不到就是收不到）
  ② 顺延（下一窗口再发，但可能失去时效）
  ③ 合并（把多条合并成一条汇总，通常最优）
判据：被挡下的条数有留痕并上看板 —— 它是"系统在克制"的唯一证据
```

- **机制**：把"推送预算"变成总量有上限的资源、以及"上限按用户不按活动"（按活动限则总量随活动数线性上升，按用户限则总量恒定、新增活动只能抢存量）见 §3.2.4，本节不复述；§4 只留它的工程形态——同一条机制推出的三个条件在实现里各有落点，且都不是可选项：优先级必须写下来成一张表（Step 4，否则退化成"谁嗓门大谁优先"）、被挡必须留痕并上看板（否则被视为"系统漏发"）、上限必须挂在具名 Owner 上（否则临时提额成为常态）。
- **失效条件**：**当频控只按渠道做时**，多通道叠加（推送 + 短信 + 站内信）会绕过上限——症状是"单看每个渠道都合规，看用户收到的总条数已经过量"（§3.5 表"频控按活动限"一行：症状"活动数增加时用户收到的总量上升"，后果"注意力被活动数消耗"）。另两条同源的失效是**被挡条数不上看板**（业务看不到系统在克制，于是不断要求放宽）与**上限没有 Owner**（上限形同虚设）。
- **档位**：【经验：不具名具体的频控产品或 CDP，判定入口是"新增一个活动后，用户接收量分布会不会右移"（§4.5 模板 2 的判据）】。

**（6）实验分层的容量分配**

```text
层（layer）内互斥、层间正交：
  layer A（频控容量）：活动 1 / 活动 2 / 活动 3 共享该层的流量池
  layer B（推荐位）：另一组互斥活动
判据：同一活动不能跨层重复占用同一批用户；每层的容量之和 ≤ 100%
      容量超配会让"分流比例"与"实际触达比例"不一致 —— 而这是静默的
```

- **机制**："两组只在触达上不同"这个前提、以及污染会把有效活动判成无效（假阴性）见 §3.2.6，本节不复述；§4 只补它的工程前提——分层：同层互斥决定"同一批流量不会被两个活动同时占用"，层间正交决定"多个活动的分流互不相关"；两者合起来，"对照组没被同类触达"才从一个假设变成一个可检查的量。
- **失效条件**：**当各层声明的容量之和超配时**（容量之和超过了全部流量），"分流比例"与"实际触达比例"会不一致，而**这是静默的**（容量判据见上）；更常见的是**长期 holdout 被穿透**——其他活动照常触达它，于是报告得出"整体实验没有收益"，而真实原因是污染（§4.7"对照污染"一行、§4.8 的 10→100 一栏）。判据始终是同一个数：**这次实验的对照组，在实验期内被同目标的触达命中了几次**——答不出，说明污染还没有观测面。
- **档位**：【经验：层数与每层容量随活动数变，判定入口是"每层容量之和是否 ≤ 100%"与"能不能报出对照组的被同类触达次数"】；"流量分层"的具名工具面（火山引擎 / Statsig / GrowthBook）已在 §3.2.6 的"真实使用"里给出并标注出处，本节不重复。

### 4.3 工具链与平台

| 能力 | 自建 / 开源 | 产品化 | 选型要点 |
| --- | --- | --- | --- |
| 分流与实验 | 自建（哈希分流 + 分层） | 实验平台 | 看**分流是否稳定**、看**是否支持分层与正交** |
| 触达编排 | 自建（规则 + 队列） | 营销自动化 / 营销云 | 看**频控是按用户还是按活动** |
| 渠道接入 | 各渠道 SDK / 网关 | 营销云自带 | 看**退订是否跨渠道一致** |
| 归因 | 自建（四一致口径 + 指标平台） | 归因产品 | 看**窗口是否可配置并声明**、分母是哪个 |
| Uplift 建模 | 自研 / 开源 uplift 库 | 智能营销产品 | 看**它要什么数据**（无对照数据的方案不可信） |
| 统一频控 | 自建（按用户） | 营销云的频控模块 | **这一项最值得自建**：跨活动上限往往需要打破产品边界 |
| 负向指标护栏 | 自建（阈值 + 暂停权限） | —— | 看**超阈值有没有自动动作** |

**渠道编排的上游是数仓侧的人群与效果写回**：§4.1 Step 5 管的是"按渠道分开算成本、退订一致、降级标注"，而"发什么、发给谁"这个决定常常不在触达系统里——`15-case-studies/08-startup-evolution/08-startup-evolution-section-8-sec8.md` §8.2 把"dbt + 反向 ETL"写成闭环，点名 Hightouch / Census 把最新的事实表写回 Salesforce / HubSpot / Braze（§3.2.5 的"真实使用"同此口径）。它决定名单是由数仓口径产出，还是由各渠道自己拼。【公开】

**一条选型原则**：**频控与归因的归属比发送能力重要**。营销云解决"怎么发"（模板、通道、编排），但**跨活动的统一频控**与**增量口径**往往必须在你的系统里（因为它们要跨产品边界、要接你的指标平台）；一个发送能力很强但频控按活动算的营销云，**会让你在活动数增长时系统性地过度触达**。

### 4.4 存量迁移

**（1）存量活动与名单怎么办**

| 对象 | 处理 | 注意 |
| --- | --- | --- |
| 正在跑的批量活动 | 逐个体检：有无对照组、频控在不在、退订是否一致 | **不要一刀切停掉**（它们可能是业务收入的一部分） |
| 历史"效果报告" | 标注口径（有对照 / 无对照），**不追溯改写结论** | 把"无对照"的历史结论当基线，会污染后续比较 |
| 存量触发规则 | 收进统一优先级表；冲突的合并 | **一次性理清比逐条加更省事** |
| 各渠道退订名单 | 合并去重 → 一份权威名单 → 各渠道订阅 | **这是最高优先级的一项**（合规风险） |
| 存量人群导出 | 加口径版本与时间语义（与 §04 接口对齐） | 否则投放名单与复盘名单对不上 |

**（2）迁移的三条验收判据**

- **同一活动的增量，两个部门算出同一个数**（归因口径统一）。
- **用户接收量上限不随活动数变化**（全局频控生效）。
- **在任一渠道退订，其他渠道不再触达**（一致性演练通过）。

**模板 2：统一频控的裁决逻辑**

```text
用户 u 在窗口 W 内命中活动集合 C = {c₁…cₙ}，优先级 pᵢ，上限 Cap(u)
  1) 按 pᵢ 降序排列
  2) 取前 Cap(u) 个为「允许」，其余为「被挡」
```

### 4.6 成本：这套东西的账单

**硬件**：本主题**几乎无专属硬件成本**——分流是一次哈希、频控是一次计数、归因是一次两组合并查询。三处例外：① **实时触发链路**（流处理常驻，随触发规则数增长，但与 [Ch3 §09](../../03-data-stack/09-realtime-compute/09-realtime-compute.md) 的实时平台共用资源）；② **Uplift 模型训练与在线打分**（训练成本低，**在线打分的量等于候选集大小**，因此随活动规模增长）；③ **曝光与效果数据的事件存储**（量级大，且**保留期要覆盖最长的归因窗口**）。

**触达成本（真正的大头）**：

```
触达成本 = Σ_渠道 (条数 × 渠道单价) + 激励成本
例【推算：口径为"条数 × 单价"按渠道分项求和】：
  短信 50 万条 × 0.04 元 ≈ 2 万元；推送/站内 ≈ 0（但占用注意力）
  带券活动：核销 3 万 × 面额 10 元 ≈ 30 万元   ← 激励常常是数量级更大的那一项
判据：成本必须按渠道与激励分开核算 ——
      混算会让"这次活动很划算"其实只是"大部分量走了便宜渠道"
```

**人力（主项）**：这一块的人力集中在三项：

1. **实验设计与解读**：每个活动要设计分流、算样本量、解读结果、做窗口敏感性检查。**成本随活动数线性增长**。
2. **规则与频控维护**：触发规则、优先级表、频控上限的维护与博弈协调（**"为什么我的活动被挡"这类协调是持续成本**）。
3. **护栏值守**：负向指标监控与暂停决策。**这是本主题特有的常备投入**——它需要有人**在业务压力下执行暂停**（这是它常被跳过的原因）。

**一条推论**：**本主题的成本是"触达成本（含激励）+ 人力随活动数增长"，而人力里最容易被砍掉的是"护栏值守"**——**砍掉它的代价不在当月，而在触达量逐季上升之后**。因此护栏值守的预算应当被当作**保险**而不是**开销**：它的收益是"没有发生的过度触达"。

### 4.7 容灾与故障演练

**本主题的"灾"分两类**：① **发不出去**（影响可见，业务立刻知道）；② **发出去了但不该发**（过度触达、对照污染、退订失效——**这类不可逆，且更危险**）。

| 失效形态 | 影响面 | 降级策略 | 演练动作 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 分流服务不可用 | 无法开新实验 | **失败关闭**：不开实验，**不许"全量发"** | 关一次分流服务，看系统是拒绝还是全量 | 分钟级 |
| 频控服务不可用 | 可能过度触达 | **失败关闭**：拒发或降到最保守上限（如 1 条/日） | 关频控服务，看触达量是否受控 | 分钟级 |
| 渠道部分失败 | 该渠道的触达缺失 | 按降级链换渠道，**并在数据里标注** | 让一个渠道全失败，看降级与标注 | 分钟级 |
| 退订同步延迟 | 已退订用户仍收到 | **退订优先**（同步阻塞，宁可延迟发也不误发） | 注入一个退订，看全渠道多久生效 | 分钟级（**退订必须强一致**） |
| 触发规则风暴 | 一次行为触发多条 | 去重窗口 + 优先级表兜底 | 人为并发触发多条规则，看裁决 | 单请求级 |
| 归因数据迟到 | 效果报告不准 | 报告标注"数据未定格"，**不出最终结论** | 延迟一天的效果数据，看报告是否标注 | 一天级 |
| 对照污染 | 增量被稀释 | 污染检测告警；超阈值时**该实验判"未测出"** | 让对照组也被同类触达，看污染检测是否报警 | 小时级 |
| **误发（不该发的人收到了）** | 不可逆 | **无降级**：只能暂停 + 复盘 + 对受影响用户做补偿性静默 | 用一批测试用户演练"误发后的处置流程" | — |

**这套演练的三条纪律**：

1. **凡是"判定类"机制（分流、频控、退订）不可用，必须失败关闭**——**不许把"频控不可用"降级成"全量发"**：那等于在最需要克制的时刻放开。**退订是强一致要求**（宁可延迟发，不可误发）。
2. **"误发"没有降级，只有流程**——一次误发不可撤回，因此**必须有一个"误发后怎么办"的预案**（暂停、复盘、对受影响用户静默一段时间），而不是临场决定。
3. **每次演练留"演练前 / 演练后"两组数字**——特别是**用户接收量分布**与**退订率**（频控失效时前者右移、后者抬升）。

### 4.8 演进路线：0 → 1 → 100

**0 → 1：一次带对照组的活动**
- **这一步做什么**：实现稳定分流；写一份归因口径卡；跑一次有对照的活动并算出增量。
- **变贵的是什么**：**与业务的沟通**——"为什么不发给他"是社会成本，而不是技术成本。
- **先坏的是什么**：**先坏的是"分流不稳"**（依赖了时间戳或随机种子），它会让增量被稀释而**看起来像"活动无效"**。**这一阶段的判据不是"跑出了显著结果"，而是"同一用户跑一百次落在同一组"。**

**1 → 10：容量与治理**
- **这一步做什么**：全局频控（按用户）+ 触发规则优先级表 + 渠道编排与退订一致性 + 实验分层与污染检测。
- **变贵的是什么**：**协调成本**——优先级与频控本质是在分配稀缺注意力，**每个被挡的活动负责人都会来问**。
- **先坏的是什么**：**先坏的是"被挡条数"的解读**——业务会把它当成"系统故障"要求修复。因此这一阶段的重点是**把被挡条数变成正面指标（系统在克制的证据）并上看板**。

**10 → 100：长期视角与效率进阶**
- **这一步做什么**：长期 holdout + 负向指标硬阈值与执行人；Uplift 定向；归因与指标平台完全对齐（口径唯一）。
- **变贵的是什么**：**护栏值守**（持续人力）与**Uplift 的场景化建模**（按触达形式分场景，模型数增长）。
- **先坏的是什么**：**先坏的是"长期 holdout 被穿透"**——它会让"整体实验没有收益"，而真实原因是其他活动触达了 holdout 人群。因此这一阶段的重点是**让 holdout 与其他活动隔离**（这是组织动作，不是技术动作）。

**贯穿三阶段的一件事**：**保留"对照组分流"的能力与纪律**。它是这一块唯一的健康基础——**运营系统的腐化不会表现为报错，只会表现为"效果报告里的增量慢慢变小，而没有人去查是不是分流坏了"。**

### 4.9 自检清单

- [ ] 分流只依赖 `(user_id, campaign_id)` 的稳定哈希吗？跑一百次结果一致吗？
- [ ] 跨活动分流是否正交（不是"总是同一批人做对照组"）？
- [ ] 归因口径卡的四项（事件口径 / 时间窗口 / 分母 / 剔除规则）写下来了吗？
- [ ] 同一活动的增量，两个部门算出同一个数吗？
- [ ] 做过 1d / 3d / 7d / 30d 的窗口敏感性检查吗？结论会翻转吗？
- [ ] 活动候选集小于所需样本量时，结论记为"未测出"还是"无效"？
- [ ] 全局频控上限**按用户**吗？新增活动后用户接收量分布会右移吗？
- [ ] 被频控挡下的条数上看板了吗？它被当成正面指标还是故障？
- [ ] 触发式规则有统一优先级表与并发去重窗口吗？
- [ ] 渠道降级换渠道时，数据里有标注吗？
- [ ] 退订在所有渠道一致生效吗？多久生效（演练过吗）？
- [ ] 有实验分层吗？每层容量之和 ≤ 100% 吗？
- [ ] 能回答"这次实验的对照组被同类触达命中几次"吗？
- [ ] 有长期 holdout 吗？它有没有被其他活动穿透？
- [ ] 负向指标有硬阈值**与执行人**吗？最近一次暂停活动是什么时候？
- [ ] Uplift 的训练数据里 T=0 样本占比是多少？
- [ ] 效果指标来自指标平台的口径吗？
- [ ] 有"误发后的处置预案"吗（误发不可撤回）？

### 4.10 小结

> 本节小结：精细化运营的落地顺序**以"稳定分流"为先**——一行哈希，但错了全错；然后固定归因的四个一致性、装全局频控（**按用户不按活动**）、治理触发规则、做渠道与退订一致性、实验分层与污染检测、最后加护栏与长期 holdout，Uplift 放在最后（它需要前面的历史数据）。**变贵的是触达成本（含激励，常常是数量级更大的那一项）与人力（实验设计 + 规则协调 + 护栏值守），而其中最容易在预算紧张时被砍掉的是护栏值守**——**砍掉它的代价不在当月，而在触达量逐季上升之后**（§4.6）。**容灾有一条本主题特有的纪律**：**判定类机制（分流 / 频控 / 退订）不可用必须失败关闭**，且**退订是强一致要求**——宁可延迟发，不可误发；而**误发没有降级，只有预案**（§4.7）。**三阶段的同一件事**：保留"对照组分流"的能力与纪律——**这一块的腐化不会报错，只会让效果报告里的增量慢慢变小，而没人去查是不是分流坏了。**

> 💡 **思考锚点**：按 §4.1 的 Step 1–2 做一个最小动作——**给你现在正在跑的一个活动补上分流与口径卡**（哪怕只对照 5%），然后按四窗口各算一遍增量。这一件事的成本是几行代码加一次配置，收益是**你第一次知道"这个活动到底有没有用"**（在此之前，你只有转化率，而转化率里混着自然转化）。**你打算先补这一个活动，还是先把频控做上？**——两者的先后会得到完全不同的下一季度。
