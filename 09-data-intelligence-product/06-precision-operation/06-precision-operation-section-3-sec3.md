## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

精细化运营的形态由**五条约束**决定，顺序不能颠倒：

1. **有没有对照组可用**：能分流吗（候选集够大、触达可延后）？**不能分流，后面所有归因都只能靠假设**——这是决定"能不能测"的第一条。
2. **触达的边际效果是否递减**：同一用户被反复触达时，效果是否下降、反感是否上升？（**绝大多数业务是这样**，因此需要统一频控。）
3. **是否要求实时**：行为触发要分钟级（"刚加购就提醒"）还是天级（"每周汇总推一次"）？**这一条决定触达链路的形态**。
4. **渠道成本与合规边界**：各渠道单价差多少、哪些渠道有同意 / 退订约束？**这一条决定渠道编排与合规动作的位置**。
5. **有没有人负责"看住总量"**：谁维护上线的频控上限、谁看待长期 holdout、谁有权限**暂停一个正在跑的活动**？（**没有这个人，运营系统会稳定地滑向过度触达**。）

> **判据的用法**：先用 1 决定"能不能测"；用 2 决定要不要全局频控；用 3、4 决定链路与渠道；用 5 决定治理强度。**跳过第 5 条最常见的后果**：每个活动的单次指标都好看，而**整体触达量逐季上升、退订率缓慢抬升**，直到某个季度爆发——**而过程中的任何单活动视角都看不到这件事**。

**每条约束的"过关"是可核查的**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 有对照组 | 最近三次活动各自的分流比例、对照组规模、是否被污染的检查结果 |
| 2 边际效果 | 有一条"触达次数 → 增量"的曲线（至少三段），且能看到拐点 |
| 3 实时要求 | 触发式规则的**统一互斥与优先级表**存在 |
| 4 渠道与合规 | 各渠道单价是已知数；退订在**所有渠道一致生效**（有演练） |
| 5 总量负责 | 全局频控上限写在某处、有 Owner；**最近一次主动暂停活动的记录** |

第 5 条的检查特别值得做：**"最近一次因为负向指标而暂停活动"这件事发生过吗**——**从未发生过**，往往意味着护栏只被观察、没被使用（§3.2.8）。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 批量群发（无对照）

**被什么约束逼出来**：候选集太小、或业务不接受"同一批人里有一部分不发"（约束 1 不满足时的现实形态）。

**结构**：规则拉名单 → 全量触达 → 统计转化率（无对照组）。

**为什么这样设计有效**：因为**它的成本最低、可解释性最强**——没有分流就没有"为什么他没收到"的客诉，也没有分流的实现复杂度。**对于纯通知类触达（账单、到期提醒、物流状态），它的有效性是成立的**：这类触达的目标是"告知"而不是"说服"，**不需要证明增量**。

**代价**：**它测不出效果**——观测到的转化率里混着自然转化，而**自然转化的比例不可知**。因此它**不能用来回答"这次值不值"**，只能用来回答"覆盖了多少人"。

**失效点**：**把批量群发的转化率当作效果**去争取更大预算——这会把预算持续投给"本来就会转化的人"，且**无法被发现**（没有对照就无法反驳）。**判据**：这份效果报告里有没有"对照组"这一列——没有，就只是工作量统计。

#### 3.2.2 分群 + A/B（随机分流，对照是基础）

**被什么约束逼出来**：要回答"这次值不值"（约束 1 满足）。

**结构**：候选集 → **用户级随机分流**（处理组 / 对照组）→ 触达处理组 → **同口径、同窗口**比较两组的转化 → 得到增量。

**为什么这样设计有效**：因为**随机分流让两组在"除触达之外的一切"上期望相同**——因此两组的差异可以被归给触达。**这条有效性有一个精确的前提：随机化发生在"触达之前"，且分组的依据与结果无关**。

**代价**：① **对照组占用的名额**（业务会问"为什么不发给他"——这是分流的社会成本，需要提前沟通）；② **它只能测**"这次**这次触达**的效果（换文案 / 换时机就是另一次实验）；③ **它对污染敏感**（§3.2.6）——对照组成员被其他活动触达，两组就不再可比。

**失效点**：**分流不稳定**（同一用户在同一活动里落在两组，或跨活动分流漂移）——后果是**处理组与对照组的边界模糊**，增量被稀释而无人察觉。**判据**：分流函数是否只依赖用户 ID 与活动 ID 的稳定哈希（不依赖时间戳、随机种子、执行节点）。

#### 3.2.3 实时触发式触达

**被什么约束逼出来**：时机相关性（"刚加购未支付"的提醒窗口只有几分钟）（约束 3）。

**结构**：行为事件流 → **规则匹配**（条件 + 去重窗口 + 频控）→ 排队与延迟控制 → 触达。

**为什么这样设计有效**：因为**它把"什么时候发"这个决策交给了用户自己的行为**——时机从"我们选的"变成"他给的"。**这条改变带来的收益不是效率而是转化**：同一文案在事件后几分钟内发出的响应率，通常显著高于按天批量（**但具体倍数必须自己测**，且要按渠道与场景分别测【经验】）。

**代价**：① **规则数量爆炸**（每条行为 × 每个场景都可能是一条规则），**跨规则的去重与频控成为主要工程问题**；② **延迟与准确性取舍**（等太久错过时机，等太短可能上下文不全）；③ **它放大频控压力**——触发式触达天然比批量触达"更频繁地命中同一个人"。

**失效点**：**没有统一的互斥与优先级表**——一次用户行为同时触发五条规则，用户在一分钟内收到五条消息。**判据**：规则是否有统一的优先级表，且**同一事件的并发触发有去重窗口**。

#### 3.2.4 统一频控与优先级

**被什么约束逼出来**：注意力是共享资源（约束 2）——**单个活动看不到跨活动的叠加**。

**结构**：**三维频控**（用户 × 渠道 × 时间窗）＋**跨活动优先级**（按业务价值 / 时效性 / 用户的订阅偏好排序）＋**超限时的处置**（顺延 / 丢弃 / 合并成一条汇总）。

**为什么这样设计有效**：因为**它把"推送预算"变成一个有上限的资源**——每个活动的"多发一条"由系统统一裁决，而不是由各活动的负责人各自决定。**这条机制的关键在于"上限是按用户而不是按活动"**：按活动限，则活动数增加时总量线性上升；按用户限，则总量恒定，**新增活动只能抢存量**（这才是"注意力是稀缺资源"的正确工程表达）。

**代价**：① **优先级必然产生内部博弈**（谁的活动优先）——因此**优先级规则必须写下来、可解释**，否则会退化成"谁嗓门大谁优先"；② **被挡下的触达需要留痕**（否则业务会认为"系统漏发"，反复来问）；③ **频控会降低单活动指标**（这是它生效的表现，而不是它的副作用）。

**失效点**：① **频控只按渠道做**——多通道叠加（推送 + 短信 + 站内信）绕过上限；② **被挡条数不上看板**——业务看不到系统在克制，于是不断要求放宽；③ **上限没有 Owner**——临时提额变成常态，上限形同虚设。

#### 3.2.5 渠道编排与成本

**被什么约束逼出来**：各渠道的成本与效果差一个量级（约束 4）。

**结构**：**渠道分级**（即时渠道只推高优先级；其余进汇总）＋**成本核算**（按渠道单价分开算）＋**降级链**（贵渠道失败时是否走便宜渠道）。

**为什么这样设计有效**：因为**"同一条消息走不同渠道"的成本差异是数量级的，而效果差异不是数量级的**（贵渠道通常更好，但不是好几十倍）。**因此正确的问题不是"哪个渠道最好"，而是"在这个优先级上，哪条渠道的边际收益超过它的边际成本"**。

**代价**：① **渠道能力差异**（模板限制、长度限制、是否支持图片 / 按钮）；② **降级链会让效果不可归因**（用户收到的是"推送失败了走了短信"，而这批人的响应率与纯推送不可比）；③ **合规差异**（各渠道的同意与退订机制不同）。

**失效点**：**退订只在一个渠道生效**——用户在短信里退了订，仍然收到推送。**这是最常见、也最容易被投诉的合规缺陷**。**判据**：退订是否在所有渠道**一致生效**（且有一次跨渠道演练）。

#### 3.2.6 对照组的污染控制

**被什么约束逼出来**：同一批用户会被多个活动命中（约束 2 的实验侧）。

**结构**：**全局实验分层**（不同活动在不同"层"上分流，同层互斥、跨层正交）＋**污染检测**（检查对照组在实验期内是否被同目标的触达命中）＋**必要时隔离**（实验期内对该人群静默其他同类触达）。

**为什么这样设计有效**：因为**增量估计的前提是"两组只在触达上不同"**——一旦对照组也被同类触达，两组的差异就变小（增量被稀释），**而这是会伪装成"活动无效"的**。**这条机制的价值在于它防止的是"假阴性"**：不是漏掉了有效的活动，而是**把有效活动判成无效**，从而永久放弃它。

**代价**：① **隔离会牺牲其他活动的量**（实验期内该人群静默，别的活动少了一批人）；② **分层设计有复杂度**（层数、正交性、容量分配）；③ **污染检测需要数据**（要能查到对照组成员在实验期内被谁触达过）。

**失效点**：**模拟实验与传统 A/B 的精算不一致**——`holdout` 被其他活动穿透，导致"整体实验看起来没有收益"而实际是污染。**判据**：能不能回答"这次实验的对照组，在实验期内被**同目标的**触达命中了几次"。

#### 3.2.7 Uplift 定向（增益建模）

**被什么约束逼出来**：优化目标从"谁会转化"变成"谁会**因触达而**转化"（约束 2 的效果侧）。

**结构**：从历史实验数据（有处理组与对照组）训练增益模型 → 对候选集预测 `τ(i)` → 只触达 `τ(i) > c / v` 的人（§2.2 的判据）。

**为什么这样设计有效**：因为**它把"本来就会转化的人"从目标里剔除掉了**——而在一段成熟业务里，**这部分人常常占多数**。**这条机制的直接收益是预算效率**：同样的触达量，投给高增量人群比投给高转化概率人群的净收益更高。

**代价**：① **它需要实验数据才能训练**（没有历史对照组 → 不可估），因此**必须先有 A/B 的能力**；② **`τ` 的估计方差大**（两个概率的差，噪声被放大），因此要**谨慎下结论**；③ **模型会依赖"本轮触达形式"**——换文案 / 换渠道 / 换激励，`τ` 的分布会变（**模型学的是"这种触达下的增量"，不是"所有触达下的增量"**）。

**失效点**：**把 Uplift 用在"没有对照组历史"的业务上**——此时训练数据里没有 `T=0` 的样本，模型只能退化成"预测转化概率"。**判据**：训练数据里处理组与对照组的样本是否都充足（而不是"大部分是处理组"）。

#### 3.2.8 长期 holdout 与负向指标护栏

**被什么约束逼出来**：单次活动视角看不到"整体触达量是否过度"（约束 5）。

**结构**：**长期 holdout**（一小部分用户长期不接收某类触达，用来测**整体**的长期增量）＋**负向指标护栏**（退订 / 投诉 / 卸载 / 屏蔽）＋**硬阈值**（超过即暂停活动）。

**为什么这样设计有效**：因为**它把测量对象从"单次活动"抬到"一类触达的整体"**——单次活动的增量都为正，不代表**整体**没有过度（因为**边际递减与用户疲劳是跨活动累积的**）。**长期 holdout 是唯一能回答"我们是不是发得太多了"的工具**。

**代价**：① **它牺牲一小部分用户的触达机会**（长期不发，因此这部分人的短期收益归零）；② **它需要有权限暂停活动的人**（阈值触发后谁执行）；③ **结果解读需要耐心**（长期指标的变化缓慢，容易被"本月活动数据好"覆盖）。

**失效点**：**护栏只观察不拦**——负向指标被列进看板但从不触发任何动作。**判据**：**最近一次因为护栏触发而暂停活动，是什么时候**——答不出，说明护栏是装饰。**另一条失效点**：负向指标的**分母不一致**（退订率按触达人数还是按到达人数），导致阈值在渠道之间不可比。

### 3.3 模式选择决策表

| 约束组合 | 推荐形态 | 必须同时上的部件 | 不选它的原因（反面） | 关键判据（可核查） |
| --- | --- | --- | --- | --- |
| 纯通知类（账单 / 到期 / 物流） | 3.2.1 批量群发 | 送达到达率统计、退订一致生效 | 给它分流是浪费（目标是告知不是说服） | 这份触达的目标是告知还是说服 |
| 要回答"值不值" | 3.2.2 分群 + A/B | **稳定分流**（只依赖 ID 与活动 ID 的哈希）、同口径同窗口 | 无对照 → 效果未测，只是工作量 | 效果报告里有没有"对照组"这一列 |
| 时机敏感（刚加购 / 刚浏览） | 3.2.3 实时触发 | **统一互斥与优先级表**、并发去重窗口、延迟控制 | 无优先级表 → 一次行为触发多条消息 | 同时触发多条规则时是否有裁决 |
| 多活动并行 | 3.2.4 统一频控 | **按用户**（不只按渠道）的上限、被挡留痕、上限 Owner | 按活动限 → 活动越多总量越涨 | 上限是按用户还是按活动 |
| 渠道成本差异大 | 3.2.5 渠道编排 | 按渠道分开核算、降级链、合规一致性 | 降级链会让效果不可归因（要用时需标注） | 各渠道单价已知吗；退订跨渠道生效吗 |
| 多活动互相干扰 | 3.2.6 污染控制 | 实验分层（同层互斥 / 跨层正交）、污染检测、必要时隔离 | 不控制 → 有效活动被判无效（假阴性） | 对照组被同类触达命中了几次 |
| 高转化概率人群占比高 | 3.2.7 Uplift 定向 | **有对照组的历史数据**、`τ > c/v` 的阈值、按触达形式分场景 | 无对照数据 → 退化成转化概率预测 | 训练数据里两组样本都充足吗 |
| 长期把控总量 | 3.2.8 长期 holdout | 负向指标**硬阈值**、有权限暂停的人 | 只看不拦 = 没有护栏 | 最近一次因护栏暂停活动是什么时候 |

### 3.4 组合模式：真实系统不会只用一种

1. **测量底座**：3.2.2（A/B）+ 3.2.6（污染控制）——**A/B 给出增量，污染控制保证它可信**；两者缺一，测量都不成立。
2. **容量的三个阀门**：3.2.4（统一频控）+ 3.2.5（渠道编排）+ 3.2.3（触发式）——**触发式产生需求，频控决定发多少，渠道决定怎么发**。
3. **长期视角**：3.2.8（长期 holdout + 负向护栏）——**它是唯一能回答"整体是否过度"的部件**，且它必须独立于单个活动的负责人。
4. **效率进阶**：3.2.7（Uplift）——**建在 3.2.2 之上**（没有历史实验数据就没有增益模型）。
5. **通知类单独处理**：3.2.1（批量群发）——**不参与增量体系**，只统计送达与退订。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 用转化率汇报活动效果 | 预算持续投给"本来就会转化的人" |
| 分流函数依赖时间戳 / 随机种子 | 同一用户跨组漂移，增量被稀释且无人察觉 |
| 频控只按渠道 | 多通道叠加绕过上限 |
| 触发式规则无优先级表 | 一次行为触发多条，用户同分钟收到多条 |
| 对照组被同类活动穿透 | 有效活动被判无效（假阴性） |
| 归因窗口与指标平台不一致 | 同一活动两个部门算出两个增量 |
| 退订只在一个渠道生效 | 合规投诉 |
| Uplift 用在无对照数据的业务上 | 退化成转化概率预测，预算效率没有改善 |
| 护栏只观察不拦 | 触达量逐季上升，退订率缓慢抬升 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **无对照的效果报告** | 报告里只有转化率 | 效果不可测，预算投给本来会转化的人 | 分流有社会成本，能省就省 |
| **分流不稳定** | 同一用户跨组出现 | 增量被稀释，且是静默的 | 分流函数依赖了不稳定输入 |
| **频控按活动限** | 活动数增加时用户收到的总量上升 | 注意力被活动数消耗 | 按活动限实现简单、无内部博弈 |
| **被挡条数不上看板** | 业务认为"系统漏发" | 频控被反复放宽 | 被挡被当成失败而非克制 |
| **触发规则无优先级** | 一次行为触发多条 | 用户体验崩塌 | 规则由不同人各自添加 |
| **污染不检测** | 对照组也在被同类触达 | **假阴性**：有效活动被放弃 | 污染检测要跨活动数据 |
| **归因窗口不声明** | 两个部门算出两个增量 | 结论不可比 | 窗口被当成技术参数 |
| **护栏只观察不拦** | 负向指标看着但没人动 | 触达量缓慢过度 | 暂停活动需要有人担责 |
| **退订跨渠道不一致** | 退订后仍收到其他渠道 | 合规投诉 | 各渠道各自维护退订名单 |
| **Uplift 无对照数据** | 模型给出的"增益"与转化概率高度相关 | 优化目标没变 | 误以为 Uplift 只是"换个模型" |
| **长期 holdout 被穿透** | 整体实验"没收益" | 长期视角缺失 | holdout 未与其他活动隔离 |
| **降级链不标注** | 贵渠道失败走便宜渠道，效果混算 | 该批人的效果不可比 | 降级在实现层，没进数据层 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 批量群发 → 分群 + A/B | 无法回答"这次值不值" | 3.2.2 | 分流实现 + **与业务沟通"为什么不发给他"** |
| 单活动 → 多活动并行 | 用户收到量随活动数上升 | 3.2.4 + 3.2.3 | 全局频控与优先级表（**要处理内部博弈**） |
| 批量 → 实时触发 | 时机敏感场景的效果明显低于预期【经验：出现"要是当时提醒他就好了"即触发】 | 3.2.3 | 规则治理 + 去重窗口 + 频控联动 |
| 单渠道 → 多渠道 | 渠道成本占比失控 | 3.2.5 | 按渠道核算 + 降级链 + 退订一致性 |
| A/B → Uplift | 高转化概率人群占多数、预算效率停滞 | 3.2.7 | 需要**足够的对照组历史**；按触达形式分场景建模 |
| 无护栏 → 有护栏 | 退订率抬升、投诉出现 | 3.2.8 | 长期 holdout + 硬阈值 + **指定有权限暂停的人** |
| 无实验分层 → 有 | 跨活动的假阴性反复出现 | 3.2.6 | 分层设计（层数 / 正交性 / 容量），成本与复杂度上升 |

**一条通用判据**：**跃迁的触发点不是"活动变多"，而是"某个失效形态第一次出现"**——第一次出现"这个活动有没有效果说不清"就该上 A/B；第一次出现"用户抱怨收到太多"就该上全局频控；第一次出现"退订率抬升"就该上护栏。**按活动数预设跃迁点，几乎一定过早或过晚。**

### 3.7 自检清单

- [ ] 最近三次活动的效果报告里，有"对照组"这一列吗？
- [ ] 分流函数只依赖用户 ID 与活动 ID 的**稳定哈希**吗（不依赖时间戳 / 随机种子 / 节点）？
- [ ] 归因的四个一致性（事件口径 / 时间窗口 / 分母 / 剔除规则）两边一致吗？
- [ ] 归因窗口是多少？做过"1d / 3d / 7d / 30d 结论是否翻转"的敏感性检查吗？
- [ ] 全局频控的上限**按用户**还是按渠道？写在哪个文件里？
- [ ] 被频控挡下的条数上看板了吗？业务知道系统在克制吗？
- [ ] 触发式规则的**统一互斥与优先级表**存在吗？并发触发有去重窗口吗？
- [ ] 各渠道单价是已知数吗？降级链换渠道时，数据里标注了吗？
- [ ] 退订在**所有渠道一致生效**吗？做过跨渠道演练吗？
- [ ] 有实验分层吗？能回答"对照组被同类触达命中几次"吗？
- [ ] 有长期 holdout 吗？它有没有被其他活动穿透？
- [ ] 负向指标（退订 / 投诉 / 卸载）有**硬阈值**吗？超阈值谁执行暂停？
- [ ] 最近一次因为护栏暂停活动是什么时候？
- [ ] 有用 Uplift 的话，训练数据里处理组与对照组的样本都充足吗？
- [ ] 效果指标来自指标平台的口径，还是活动系统自己算的？
- [ ] 人群结果带"口径版本 + 时间语义 + 生成时刻"吗（与 §04 的接口）？

### 3.8 小结

> 本节小结：精细化运营的形态由五条约束按序决定——**有没有对照组 → 边际效果是否递减 → 是否要求实时 → 渠道成本与合规 → 有没有人看住总量**；八种模式里，**A/B 与污染控制（3.2.2 / 3.2.6）是"能测"的地基**（缺一，测量都不成立），**统一频控与渠道编排（3.2.4 / 3.2.5）是容量的阀门**（上限必须按用户而不是按活动），**长期 holdout 与负向护栏（3.2.8）是唯一能回答"整体是否过度"的部件**，而 **Uplift（3.2.7）是建在 A/B 之上的效率进阶**（没有对照数据它不成立）。判断这一块有没有真正建成，只看两条：**效果报告里有没有对照组**；**最近一次因为负向指标暂停活动是什么时候**。**本主题最容易被忽略的一条**：**观测转化率高不等于增量高**——**在一段成熟业务里，大部分转化是自然发生的，而"把自然转化算成活动效果"是无法被自查发现的自欺。**

> 💡 **思考锚点**：从 §3.2 里挑一条你系统已有的做法，问三个问题：它**防的是哪一类失效**（无对照 / 污染 / 过载 / 假阴性 / 过度触达）？它的**失效形态是什么**（怎么发现它没起作用）？**有没有一个可执行的检查**能证明它此刻生效？第三个问题通常最有价值——**"频控生效"的证明是"能报出被挡条数"，"护栏生效"的证明是"有过一次暂停"，"分流生效"的证明是"同一用户跨活动稳定落组"**。你打算先补哪一条？
