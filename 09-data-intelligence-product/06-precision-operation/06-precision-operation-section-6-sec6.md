## 6. 落地实践

> **本节的材料纪律（先说清楚）**：运营的公开材料以**产品能力与增长故事**为主，而**增量、污染率、退订曲线这些真正有用的数据几乎无人公开**——它们直接暴露"投出去的钱有多少花在了本来就会发生的事上"。因此本节 4 例的构成是：
>
> - **§6.1–§6.2** 是**公开材料层面的机制复述**（触达量怎么被统一裁决、目标怎么从转化率变成增量），**不是对任何一家公司内部实现的转述**；方括号内是**来源类型 + 年份**，属**建设方自述**，不构成本书 §5 判据里要求的「第三方（非厂商）公开生产案例」。
> - **§6.3–§6.4** 是**匿名案例**（不给可指名的来源），只作机制示例、不作举证。
> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 阿里"**把触达量做成按用户统一裁决的预算：从各活动各自限频到全局频控 5+ 年**"（2019-2024）

**背景（Why）**

大促期间最典型的形态是**活动数量爆发**：每个业务线都有自己的会场、推送、优惠券活动。它们各自限频，于是：

- **用户在同一小时里收到多条**（不同活动各推一次，每条都"合规"）；
- **单活动的指标都好看**（它只看自己触达的那部分人），而**用户的整体感受在任何一个单活动视角里都不存在**；
- **退订与屏蔽缓慢上升**，而它是**跨活动累积**的结果——因此归因到任何一个活动都"证据不足"。
- **约束是"活动不能停"**：大促期间每个业务线的会场与券都是已排期的收入，**一刀切砍活动在组织上不可行**——因此可选的方案必须是"统一裁决"，而不是"限制活动数"。
- **代价被转移给了谁也要说清**：统一裁决把代价从"用户的注意力"转成了"业务方的名额竞争"——**这才是它真正的成本项**（§4.6 把这一项写成"规则与频控维护 + '为什么我的活动被挡'的协调"的持续人力），而不是任何硬件开销。

**触发点（What）**

阿里在其营销与消息体系里把**触达量按用户统一裁决**（[阿里公开材料 2019-2024]，核验入口是其营销与消息相关产品的官方文档，**按当前版本核**；本主题只描述这一类能力的**机制形状**）。它给出的启示是**"注意力预算"这个模型**：

- **上限按用户而不是按活动**——因此新增活动只能**抢存量**，不能扩大总量；
- **优先级必须可解释**——否则会退化成"谁嗓门大谁优先"；
- **被挡下的量是运行数据**，不是故障。
- **它的前提是一个组织动作，不是一个技术动作**：上限与优先级必须有人维护、有人对总量负责（§3.1 约束 5；§4.8 的 1→10 阶段把"协调成本"写成这一阶段变贵的东西）。
- **代价是"单活动指标会变差"**：被裁决挡下的量会让每个活动的触达面变小，而**这是它生效的表现**（§3.2.4 代价③）——若把这一条当成副作用去"修好"，系统会退回按活动限频，总量随即恢复线性上升。

**详细做法（How）**

**① 把"多推一条"从一个局部决策变成一次全局裁决**

- **关键设计**：所有会触达用户的活动在**触达前**经过同一处裁决（按用户上限 + 优先级排序），而不是各自决定后各自发送。
- **关键性质**：**这条改动第一次让"总触达量"成为一个被管理的量**——在此之前，总量只是各活动量的和，没有人对它负责。
- **关键示意**：

  ```text
  两种限频口径带来的两种世界
    ── 按活动限频 ──────────────────────────────────
       活动 A 限 1 条/人/日 → A 发 1 条
       活动 B 限 1 条/人/日 → B 发 1 条
       活动 C 限 1 条/人/日 → C 发 1 条
       用户实际收到：3 条（每个活动都"合规"）
       新增活动 D：总量 → 4 条（线性上升）
    ── 按用户限频 + 优先级 ─────────────────────────
       Cap(user) = 2 条/日（全局）
       A / B / C 按优先级排序 → 保留前 2 条
       第 3 条：合并进汇总或顺延
       新增活动 D：总量不变，D 与 A/C 抢名额
       → 总量恒定；紧张的是名额，不是用户的耐心
    ────────────────────────────────────────────────
   判据：新增一个活动后，用户的接收量分布会右移吗？
        会右移 → 上限没有按用户生效
  ```

- **判据**：新增一个活动后，用户的接收量分布**不应右移**（§4.5 模板 2 的同一判据）。**这条判据的力量在于它不看任何单活动的数字**——它是这一块唯一能看见"总量"的检查，而"总量有没有被管住"恰恰是所有单活动视角都看不见的东西。

**② 被挡条数上看板，并且是正面指标**

- **关键设计**：把"被挡下的条数"做成运营看板上的一个正常指标（它表示系统在克制），而不是"漏发"。**它的字段形态就是 §4.5 模板 2 的留痕结构**——每一条被挡都要能回答"为什么是它被挡、后来去哪了"（以下是**字段示例**，其中的 ID 与日期均为示意，不是任何一家的实测记录）：

  ```text
  裁决留痕（每次裁决写一条）
  { user: u, window: 2025-11-11/00:00-24:00, cap: 2,
    allowed: [c_3, c_7],              # 按优先级排序后保留的前 Cap 个
    blocked: [c_1, c_9],              # 被挡下的
    reason: { c_1: 优先级低于 c_7, c_9: 与 c_3 合并 },
    disposition: { c_9: merged } }    # 丢弃 / 顺延 / 合并（三选一，必须事先定死）
  判据：任取一条被挡记录，能不能说清"它为什么被挡、后来去哪了"
  ```

- **为什么**：**业务看到"被挡"的第一反应是"系统故障"**——如果不把它定义成正面指标，就会有持续的压力要求放宽上限，而**每一次放宽都对应一次总量上升**。
- **判据**：被挡条数**与"被挡 / 应触达"的比例在看板上**，且旁边写着它是"系统在克制"的说明；辅助检查一条——**临时提额有没有留痕**（没有留痕的提额会让上限形同虚设，§3.2.4 失效点③）。
- **关键能力与它的边界**：这一模式**不需要新模型**，它需要的是一件跨产品边界的能力——**在能看到全部活动的那一层做裁决**（§7.3.2 的结论："频控必须落在能看到全部活动的那一层，而那一层通常不在营销云里"）。这也解释了 §4.3 为什么把"统一频控"标成"**这一项最值得自建**"：跨活动上限往往需要打破产品边界，而这在采购里买不到。

**具体数字（档位标注）**

- 触达量随活动数增长的量级：按活动限频时，**用户接收量与活动数近似成正比**【推算：总量 ≈ 活动数 × 单活动触达率 × 命中率，活动数增长时总量线性上升】；按用户限频后总量恒定，**被挡量随活动数上升**——这两条曲线是同一个现象的两种画法。**这个量级决定了什么**：当活动数进到十位数时，"线性上升"意味着**总量翻倍不需要任何新策略，只需要多排几个活动**——因此按活动限频的系统**在规模上必然过度触达**，与运营水平无关。
- 被挡比例的量级：在活动密集期（大促），**被挡比例可以到三成以上**【经验：随活动密度与上限严格程度浮动】——**这个数越高，说明上限越在起作用**。**这个量级决定了什么**：三成以上的被挡量意味着**这一块的价值有一大半体现在"没发出去的那部分"**，而它此前从未出现在任何一张效果报告里（§6.7 因此把它单列为一项收益）。
- **自测动作**：把某个用户一天收到的全部触达列出来（跨渠道、跨活动），看它是否超过你写在文档里的上限。**列不出来，说明你还没有"按用户"的视图。** **这一步的意义**：它把"上限"从一个文档里的数字变成一条可被反问的曲线——**列得出来，总量才第一次可辩**（同 §7.6 的第三条次序原则：先把"用户一天收到多少条"变成可查的数，很多后续决策会自动没有争议）。

**失败教训**

**第一版把频控做成了"每个活动配一个上限"**——理由是"这样各业务线自己管"。结果是活动数量翻倍时用户接收量也翻倍，而**每个活动的复盘都显示"我们只发了 1 条"**。教训：**注意力的稀缺性是按用户计的，不是按活动计的**——**用按活动的上限去管理按用户的稀缺资源，管理层级错了。**

**为什么会写成那样（机制层）**：这一版不是"考虑不周"，而是**能力生长路径的必然结果**——频控通常先长在活动系统里（只有活动系统知道自己发了什么、发给谁），于是"上限"天然被挂在活动对象上；**等到要按用户管理时，上限已经分布在 N 个系统里，而没有任何一个系统能看到全部活动**（§7.3.2 的同一结论）。**所以这条教训的机制层表述是**：**稀缺资源的管理层级必须与它实际的计量单位一致**——按活动限频管理不了按用户计量的稀缺性；而修它要打破的不只是代码（把裁决层提到 N 个系统之上），还有"谁有权限否决别人的活动"这件事（§3.2.4 代价①、§5.3.3 的组织成本）。

### 6.2 字节"**从转化率到增量：把 A/B 与增益建模做成运营的默认口径 4+ 年**"（2020-2024）

**背景（Why）**

增长团队最初的效果汇报是转化率与 GMV——**而在一段成熟业务里，大部分转化是自然发生的**：

- **"精准人群"让效果看起来更好**——越精准的人群里，目标客户的自然转化率越高；
- **于是预算持续投给"本来就会转化的人"**，而补贴给了不需要补贴的人；
- **这件事无法自查**——没有对照，观测到的转化率永远"不错"。
- **约束是"效果要按汇报节奏可见"**：增长团队的汇报节奏通常是周会 / 双周会，而**增量口径要求等归因窗口跑完才出结论**——这决定了落地时必须允许"分流先上、口径后补"的过渡，而不是等统计流程齐备再改口径。
- **代价是"能测的范围变窄"**：留几个百分点的对照意味着**这部分人当期不产生触达收益**，且**小活动会大面积落进"未测出"**（§2.2 的样本量约束：`p=5%`、`δ=0.5pp` 时约 2.98 万/组【推算：§2.2 的算式，代入同样的 p 与 δ 可重算】）——因此口径转换的第一年，汇报里"有效活动"的数量通常会**减少**而不是增加，这一点必须提前和业务说清，否则口径会在第一次汇报难看时被改回去。

**触发点（What）**

字节在其增长与实验体系里把**增量作为效果口径**（[字节公开材料 2020-2024]，核验入口是其增长 / 实验相关的官方文档，**按当前版本核**）。它给出的启示是**口径转换带来的连锁反应**：

- **汇报要改成增量**——而增量必须有对照组，于是**分流成为所有活动的前置**；
- **人群选择的目标要改**——从"高转化概率"改成"高增益"（`τ > c/v`），而**这两类人群不同**；
- **护栏要单独看**——因为触达**可以为负增量**（激怒用户），只看正向指标会系统性过度触达。
- **代价落在两处**：① **组织侧**——每个活动都要解释"为什么不发给他"（§3.2.2 代价①的社会成本）；② **工程侧**——分流标识必须**贯穿到曝光与归因**，而这一环**一旦漏了，报告出不来且没有任何报错**（§7.3.1："没有对照组标识就没有增量"，是在缺这个字段时**不可定义**，不是"做得不够好"）。
- **它把"效果"从一次汇报变成一条流水线**：口径卡、分流标识、归因查询三者要同时就位（§4.1 Step 1–2、§4.2（2））——**这才是它比"换一个更聪明的模型"贵的地方**。

**详细做法（How）**

**① 分流成为默认，不是可选**

- **关键设计**：任何活动上线前**默认留一部分对照**（比例可按活动调整，但**不能为零**）。
- **关键性质**：它把"要不要做对照"从一个**每次都讨论的决策**变成**默认配置**——**这条组织设计比技术实现更关键**：只要"不做对照"仍是一个需要论证的选项，就会有大活动以"影响收入"为由跳过它。
- **判据**：抽最近三次活动，看报告里有没有"分流比例 / 对照组规模"这两项（§4.5 模板 1 的字段）；再做一次流程演练——**试着申请一个"免对照"的大活动**，如果申请通道存在，说明对照仍是可选项。**这条演练比看代码有效**：分流是否默认，是流程属性，不是实现属性。
- **最小实现形态**（与 §4.2（1）同一件事，只多了"下限"这一约束）：

  ```yaml
    # 示例配置：比例与 key 名均为示意值，不是任何一家的实测配置
  campaign: 618-首购券
  split: { treatment: 0.95, control: 0.05 }   # 可调
  min_control_ratio: 0.02                     # 下限：任何活动不得低于它（>0 即不可为零）
  assign_key: [campaign_id, user_id]          # 稳定哈希的两个键，缺一不可
  exposure_log: [user_id, campaign_id, group, ts, channel]
  判据：把 min_control_ratio 改成 0 会不会被系统拒绝；不会 → 它只是文档里的一句话
  ```

**② 增益建模与人群目标的重定义**

- **关键设计**：用历史实验数据（处理组 + 对照组）训练增益模型，触达 `τ(i) > c/v` 的人。
- **关键性质**：**这条改变了"谁是好人群"的定义**——高转化概率的人常常 `τ ≈ 0`（他本来就会买），**因此按转化概率排序会系统性地把钱花在不需要的人身上**。
- **判据**：查训练数据里 `T=0` 的样本占比（§4.2（4）：低于三成时任何 Uplift 建模都不可靠）；再查模型打分与"转化概率"的排序相关性——**高度相关说明它退化成了转化概率预测**。第三条：**按触达形式分场景**（换文案 / 换渠道 / 换激励之后，`τ` 的分布会变，§4.2（4））。
- **关键能力**：这一条**建在前一条之上**（没有对照数据就没有 `T=0` 的样本），因此它是这四例里唯一"不能单独上线"的做法——**先有分流，一年后才谈它**（§4.8 把它排在 0→1→100 的 10→100 阶段）。

**③ 护栏独立成组指标**

- **关键设计**：退订 / 投诉 / 卸载与增量并列汇报，且**设硬阈值**。
- **判据**：**硬阈值这一列必须有值，且必须有执行人**（§4.5 模板 3：观察阈值 / 硬阈值 / 超阈值动作 / 执行人四列齐全）。**只有观察阈值的护栏不构成护栏**——它可以被无限次看着而不产生任何动作。
- **关键能力**：护栏读的是**效果数据与负向数据的完整性**（缺一条退订事件，阈值就永远不触发），因此它的前置是触达记录与退订状态的同源——这也解释了为什么 §4.1 把"退订一致"排在护栏之前（Step 5 在 Step 7 之前）。

**④ 三件事的依赖顺序（顺序错了会白做）**

- **关键设计**：分流（①）→ 口径卡（§4.2（2））→ 增益建模（②），护栏（③）与它们并列常驻。**这不是排期偏好，而是数据依赖**：② 需要 ① 产出的 `T=0` 样本；而 ① 的产出要能被解释成"增量"，则要口径卡的四个一致性。
- **关键性质**：**这条顺序同时解释了"为什么先做精准是错的"**——精准不需要任何前置，因此谁都能先做，而它恰好是唯一会**放大误差**的那一步（§4.1 的"顺序的反面"、本案例的失败教训）。

  ```text
  数据依赖（箭头不可跳过）
    分流（对照组标识）──→ 曝光 / 分流日志含 T 维 ──→ 增益建模（τ 可估）
          │
          └──→ 口径卡（四个一致性）──→ 增量可解释 ──→ 汇报与预算分配
    护栏（负向指标 + 硬阈值）── 与上面并列，但需要"退订一致"先就位
    判据：只做"精准人群"而不做上面的任何一件，会得到什么？
          会得到一个"报告更好看、净增量不变"的系统（本案例的失败教训）
  ```

**具体数字（档位标注）**

- 增量与转化率的典型落差：**在成熟业务里，观测转化率往往是增量的数倍**【经验：落差随业务成熟度与人群精准度上升】——**这是"精准反而让效果报告失真"的量化形态**（人群越准，自然转化占比越高）。**这个量级决定了什么**：当落差是数倍时，**"把转化率当效果"不是一个精度问题，而是一个数量级问题**——按转化率排序选出的高价值活动，可能恰好是增量最低的那一批（因为它选中的是"本来就会买"的人）。
- 样本量约束：要检出小增量需要很大的样本（§2.2 的算式，`p=5%`、`δ=0.5pp` 时约 **2.98 万/组**）——**因此小活动常常"测不出"**，而正确结论是"未测出"而不是"无效"。**这个量级决定了什么**：它把"能不能测"变成了**候选集规模的门槛**，而不是分析方法的高低——小候选集的活动**无论用什么方法都测不出小增量**（这也解释了为什么"把新方向放进小活动试"的团队会系统性地淘汰新方向）。
- **自测动作**：取一次"表现最好"的活动，补上 5% 对照组重跑一次，看增量与转化率的落差。**这一步的意义**：它用一个活动就能校准**你此前所有汇报里的系统性高估幅度**——而这个幅度只能实测，不能推算（它取决于你的业务成熟度与人群精准度）。

**失败教训**

**第一版把"精准人群"当成优化方向**——人群越精准，活动报告越好看，而**净增量没有提升**。追查发现：精准筛选出来的人里，**自然转化占比更高**。教训：**在没有对照组的情况下，"更精准"与"效果更好"是同向的错觉**——精准提高了转化率，同时提高了自然转化的占比；**要判断真实收益，必须先有增量口径，再谈精准。**

**为什么会写成那样（机制层）**：因为**"精准"优化的是 `P(Y=1|i)`，而效果取决于 `τ(i)`，这两个量的相关性可以是负的**——筛选得越像目标客户，命中的就越是"本来就会转化"的人（§2.2 的原话：`P` 高的人往往 `τ` 接近 0）。**更麻烦的是这两件事在观测上不可区分**：精准与增量在"转化率"这个屏幕上显示为同一个方向，只有在补了对照组之后才会分叉——因此**这一版能长期存活，不是因为它对，而是因为它的错误需要一个对照组才能被看见**（§1.1："没有对照组时，它的效果是未测的"）。

### 6.3 某内容平台"**长期 holdout 揭示"整体触达过量"：单活动都有效，整体却过度 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

平台有几十类触达（推送、站内信、弹窗、任务提醒），**每一类的 A/B 都显示正增量**，因此团队持续加密——理由是"每个都是有效的"。

- **约束是"不能靠停某个活动来验证"**：这几十类触达是互补的（停掉任何一个，另外几十个照跑），因此**"整体是否过量"这个问法在单活动实验里没有落点**——这正是它必须新造一种实验形态（长期 holdout）的原因，而不是"把现有实验做得更细"。
- **代价从一开始就要认**：划出去的 holdout 用户**长期不接收这类触达**，**这部分人的短期收益归零**；并且**结论要等以季度计**（§7.7 的迁移成本表把"无长期 holdout → 有"一行的工作量量级定为这一档，并注明观察时间本身压不动）——**这项成本主要是耐心，而不是算力或人力。**

**触发点（What）**

**留存曲线在一个季度内走平并略降**，而同期所有单活动的指标都是正的。团队用了一个此前没用过的工具：**留出 5% 的用户，长期（数月）不接收任何此类触达**（长期 holdout），只看两组的**长期留存**。结果是：**holdout 组的留存高于处理组**——即**整体触达量已经过量**（边际效果被边际反感超过了）。

- **代价是"结论不可归因到单个活动"**：holdout 证明的是**总量**过量，**它不会告诉你该砍掉哪一个**——因此它的输出必须落到"上限"（Cap）而不是"某个活动"（见做法③）。**这一点决定了它的使用者不是活动负责人，而是对总量负责的那个人**（§3.1 约束 5）。
- **它的代价还包括"必须先隔离才能读"**：holdout 人群如果被其他同类活动触达，这个实验就退化成污染样本（§3.2.6 失效点；§4.8 的 10→100 阶段把"先坏的是 holdout 被穿透"列为这一阶段的首要风险）。**换句话说：长期 holdout 要成立，前面几步必须已经在位**——这也是它排在落地路径最后一步的原因。

**详细做法（How）**

**① 单活动的"正增量"与整体的"过量"可以同时成立**

- **关键机制**：**单活动的增量是在"其他活动照常"的前提下测的**（它测的是"多加这一条"的边际效果），而**整体触达量是所有这些"多加一条"的累积**。**每一条单独加都是正的，加起来却不是**——因为反感与疲劳是跨活动累积的，而单活动实验把这一部分**外部化**了。
- **关键性质**：**这解释了为什么"每个活动都有效"不能推出"整体不过量"**——它需要另一种实验形态（长期 holdout）。
- **判据**：把最近 90 天【经验：窗口长度是量级，可按你自己的观察节奏替换】的**触达总量曲线**（按用户平均条数）与留存曲线画在同一张图上——**总量在升而留存不升，就已经是同一个处境**（不需要等 holdout 出结论，见本单元的"自测动作"）。

**② 长期 holdout 的做法与代价**

- **关键设计**：固定一小部分用户**长期不接收某类触达**（不是单次活动的对照），比较**长期指标**（留存 / 活跃 / 退订）。**它与单活动对照的差别只在"处理对象"这一处**：

  ```text
                           处理对象         观察指标        结论指向
    单活动 A/B         ── 一次活动的"多加一条"   当天 / 窗口内转化   这个活动值不值
    实验分层 + 污染检测 ── 再一次 A/B 的可信度    污染命中次数      这次结论可不可信
    长期 holdout      ── 一类触达的"总量"      留存 / 活跃 / 退订   总量该不该降
    ──────────────────────────────────────────────────────────────
    关键差别：三者测的不是同一件事，因此不能互相替代；
              长期 holdout 是三者里唯一把"所有活动的总和"当作处理对象的
  ```

- **判据**：能不能说出"我划出去的那部分人，在过去一个月里被同类触达命中过几次"——**答不出或不为零，说明 holdout 没有被隔离**（§4.2（6）的污染检测同一条判据）。
- **代价**：这部分用户的短期收益归零；**它需要有人长期看着**（结果变化缓慢，容易被月度数据覆盖）。

**③ 用结果去改上限，而不是改"哪个活动"**

- **关键设计**：结论指向的是**总量上限**（Cap 调低），而不是"砍掉某个活动"——因为问题不在某一个活动，在总量。
- **为什么**：改单活动会让结论无法解释（"为什么砍它不砍别的"）；**改总量是有统一判据的动作**。
- **判据**：结论页上写的是"Cap 从 X 调到 Y"还是"停掉活动 Z"——**写后者，说明这份结论被用错了**（它无法被复用：下一次换一批活动，同样的判断还要重做一遍）。
- **关键能力**：这条做法要的不是算法，而是**权限**——调 Cap 的人必须能覆盖所有活动的负责人（§3.1 约束 5、§4.1 Step 7 的"有权限暂停活动的人"）。

**④ 把结论写进例行流程，否则它会过期**

- **关键设计**：holdout 的结果不能停在一次性的报告里——它要变成**周期性复看的机制**（观察期以季度计，复看节奏也按季度定），并且它的输出物是**Cap 的调整记录**，而不是一份分析文档。
- **为什么**：因为**长期指标的变化缓慢，容易被"本月活动数据好"覆盖**（§3.2.8 代价③的原话）——一份没有复看机制的 holdout 报告，在下一个季度的活动压力下会自然失效。
- **判据**：找出最近一次"因 holdout 结论而下调了总量上限"的记录——**找不到，说明这条结论没有落到流程上**（它与 §4.5 模板 3 的"最近一次因护栏暂停活动"是同一种检查，只是时间尺度更长）。

**⑤ 与频控联动：结论落到 Cap 之后，还要能验证它生效**

- **关键设计**：Cap 调低之后的验证动作与 §6.1 是同一条——看新增活动时**用户的接收量分布是否右移**；右移说明调低的 Cap 没有真正生效（可能权限没落到执行链路，或被临时提额抵消）。
- **为什么**：因为**"调 Cap"与"Cap 生效"是两件事**：前者是一次配置变更（可被临时提额覆盖），后者是一条可观测的输出（§3.2.4 失效点③："上限没有 Owner → 临时提额变成常态，上限形同虚设"）。
- **判据**：把"Cap 调整记录"与"用户接收量曲线"对起来看——**调低之后曲线没有下降，说明这次调整只写进了文档**。

**具体数字（档位标注）**

- holdout 比例的常见量级：**几个百分点**【经验：太小则噪声大，太大则收益损失显著】。**这个量级决定了什么**：它把"整体是否过量"这个问题**变成一项可以长期买得起的观测**（几个百分点的触达量，相对于它要防的"整体过度触达"损失，是可以接受的保险费）——**因此这一项几乎不存在"算不过账"的情形，存在的只是"没人愿意长期看"。**
- 观察周期的量级：**以季度计**【经验：长期指标的变化缓慢，月度可能不足】——**成本主要是耐心**。**这个量级决定了什么**：它决定了**这条结论不可能挂在季度考核上**——观察期跨过考核周期，因此它必须由对总量负责的人持有（§4.6 的"护栏值守"人力与 §7.4 的"治理族最容易被砍"是同一处机制）。
- **自测动作**：现在就能做的一件事——**列出你最近 90 天的触达总量曲线**（按用户平均条数）。**如果它在上升而留存没有上升，你就已经在同一个处境里了**，不需要等 holdout。**这一步的意义**：它是本节四条自测里**唯一不需要任何改造、当天就能出结论**的一条——而它给出的结论方向与 holdout 一致（差别只在精度）。

**失败教训**

**把"每个活动都有效"当成"可以继续加密"的理由**——每次实验都显示正增量，于是总量持续上升，直到留存开始下降。教训：**单活动实验测的是边际效果，而边际效果是"在其他都不变的前提下"的**；**整体是否过量，只能用长期 holdout 回答**——**它是唯一把"所有活动的总和"当作处理对象的实验。**

**为什么会写成那样（机制层）**：因为**单活动实验把"反感与疲劳"这一项放进了误差项，而不是放进了处理项**——每个实验都在"其他活动照常"的前提下做，因此**跨活动累积的那部分影响被每一次实验一致地外部化了**。于是"每个活动都有效"与"总量已经过量"在数学上并不矛盾（做法①的机制），而**推理时把前者当成后者的证据，是一个归纳错误**：边际效果为正只能推出"再加一条还有收益"，推不出"过去加的那些加起来仍然有收益"。**这决定了修法不在实验方法，而在实验形态**——必须有一个把总量当作处理对象的实验（这也是 §4.1 把护栏与 holdout 排在最后、而不是排在"更细的 A/B"之后的原因）。

### 6.4 某银行信用卡中心"**退订跨渠道一致性：一次合规投诉带来的改造 2+ 年**"（2022-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证。

**背景（Why）**

多渠道触达（短信、App 推送、电话、邮件）由不同团队各自维护，**退订名单也是各渠道各一份**。

- **约束是"渠道不能先合并"**：四个渠道由不同团队甚至不同供应商维护（短信有通道商、App 推送走自有通道、电话走外呼系统、邮件走第三方），**统一到一套系统要跨团队、跨合同**——因此可行的做法不是"换一个统一平台"，而是**在出口处做一次校验**（做法②）。
- **代价是"宁可延迟发"**：强一致校验意味着**名单服务或校验链路故障时触达要停**（不是"先发后补"）——这条取舍的机制是**代价不对称**（一次投诉 vs 一条触达晚几分钟），而它在运维上表现为"触达可用性下降"（§4.7 因此把它写成"失败关闭"而不是降级发送）。

**触发点（What）**

**一次客户投诉**：客户在短信里回复了"退订"，但**继续收到 App 推送与营销邮件**；客户投诉到监管渠道。团队自查发现：短信渠道的退订名单**没有同步到其他渠道**——**技术上是三份独立的名单。**

- **代价是"改造窗口很短"**：投诉已经进了监管渠道，补救是**被动的、限期的**——§7.7 把"退订各渠道 → 集中"的工作量量级写成"以月计"，并注明它"**往往是合规驱动的紧急改造**"。
- **它牵出的不只是退订**：要证明"一致"，就必须能回答"这个人在每个渠道分别被触达过几次"——因此这次改造顺带补上的是**跨渠道的触达视图**，而它与统一频控（§6.1）需要的是同一张视图：**两件事共用一份"用户 × 渠道 × 时间窗"的计数**。

**详细做法（How）**

**① 退订是强一致要求（宁可延迟发，不可误发）**

- **关键设计**：退订与同意状态**集中管理**；触达前**强一致校验**（校验失败即不发）。
- **为什么是强一致而不是最终一致**：**退订是用户的明确意愿，违反一次就是一次投诉**；而**延迟发一次，代价只是这条触达晚了几分钟**——两者的代价不对称，因此选择"宁可延迟"。
- **判据**：做一次"名单服务停摆"的演练——看系统是**停发**还是**继续发**。**继续发说明它实际是最终一致**（校验失败被当成"放行"）；这条判据比读架构文档可靠，因为一致性是**失败路径上的属性**，成功路径上看不出差别（同 §4.7 的三条纪律第一条：判定类机制不可用必须失败关闭）。
- **关键能力**：它要求退订状态**只有一份权威名单**，且这份名单的**读延迟**是已知数——因为"强一致"在工程上意味着**把校验放在发送前的那一跳**，而不是"让别人尽快同步给我"。

**② 触达前校验要在链路上，不能靠各渠道自觉**

- **关键设计**：同意与退订校验放在**统一的触达出口**（而不是各渠道 SDK 里各做一遍）。
- **为什么**：**各渠道各做一遍 = 新增一个渠道就多一个遗漏点**；放在出口则"新增渠道自动获得校验"（同 [Ch5 §02 §3.2.4](../../05-agent-platform/02-agent-platform-architecture/02-agent-platform-architecture-section-3-sec3.md) 的出口收口）。
- **判据**：数一个数——**当前有几个"发送代码路径"**（不只是几个渠道，而是几条实际调用发送的代码路径）；每条路径上是否都经过同一个校验函数。**新增一个渠道时，校验是"自动获得"还是"记得去加"**——后者说明校验收口没有完成。
- **最小实现形态**（出口校验的入参与出参，与 §4.5 模板 3 的护栏表共用同一份名单）：

  ```text
  发送出口（所有渠道唯一入口）
  send(user_id, channel, template_id, payload):
      1) 查同意状态：consent(user_id, purpose) ∈ {granted, denied, unknown}
      2) 查退订名单：unsub(user_id) 与 unsub_per_channel(user_id, channel)
      3) 判定：denied / unknown / 已退订 → 拒发（记 reason，不记 payload）
               名单服务不可达      → 失败关闭（拒发，并告警）
      4) 通过 → 下发，并写触达留痕 {user_id, channel, ts, template_id, campaign_id}
  判据：任意一条触达记录，都能反查出"它当时依据的同意与退订状态是什么"
  ```

**③ 用一次演练证明一致性**

- **关键设计**：在任一渠道退订 → 验证**其他所有渠道**在下一个触达周期内不再触达该用户。**判据**：演练通过，且**留演练记录**（合规审查会问）。
- **演练记录里至少要有的四项**：**发起退订的渠道**、**观察窗口**、**其余渠道是否全部停止**、**每个渠道的停止时刻**——最后一项决定了"不一致"是不是被**延迟**掩盖了（先停的那个渠道不能代表其余渠道）。
- **判据的二段式**：先跑**测试账号**（成本十分钟，§4.7 的"注入一个退订"，属演练动作），再看**生产数据**里"退订后仍在被同类触达"的计数（观察窗按你自己的触达周期定）——**前者证明机制在，后者证明机制一直在**：机制会随新渠道上线而悄悄失效，而它**不报错**。

**④ 新渠道上线时的检查项（一致性是被"新增"打破的）**

- **关键设计**：把"接入新渠道"做成一份检查单，而不是一次开发任务。**至少要过的四项**：① 该渠道的发送是否只走统一出口（不绕过）；② 该渠道的退订能否被回写到唯一名单；③ 该渠道的触达是否写进跨渠道留痕（供频控与复盘使用）；④ 该渠道是否进入跨渠道演练的覆盖集。
- **为什么**：因为这条链路的失效**不来自代码退化，而来自新增**——每一次新渠道上线都会重新引入一个"各做一遍"的机会（做法②的机制），而**它不会以 bug 的形式出现，只以下一次投诉的形式出现**（§3.2.5 代价③与失效点）。
- **判据**：找一个**最近三个月新上线的渠道**，把上面四项各验一遍——**有任何一项没做，说明这份检查单还不存在，或者存在但没被使用**。

**⑤ 误发之后的处置预案（因为误发不可撤回）**

- **关键设计**：一份**事先写好的动作清单**：暂停该渠道或该活动 → 圈出受影响用户 → 对这一批人做一段**补偿性静默**（不再叠加触达）→ 复盘并留档。**它必须在误发之前就写好**，而不是临场决定。
- **为什么**：因为**触达不可撤回**——§4.7 的失效形态表里，只有"误发（不该发的人收到了）"这一行的降级栏写的是"**无降级**：只能暂停 + 复盘 + 对受影响用户做补偿性静默"；**消息投递出去就收不回来，因此唯一可控的是"接下来还发不发"**。
- **判据**：用一批测试用户演练一次完整处置流程，**并记录每一步的实际耗时**——**没有演练过的预案，在真实投诉到来时会变成现场讨论**（同 §4.7 的第三条纪律：每次演练留"演练前 / 演练后"两组数字）。

**具体数字（档位标注）**

- 误发的规模：退订同步延迟若为小时级，**一次批量触达就是数十万条误发**【推算：误发条数 ≈ 触达速率 × 同步延迟】——**这条算式说明"同步延迟"不是一个可以容忍的量**。**这个量级决定了什么**：它把"同步延迟"从一个**技术参数**变成了**合规敞口**——延迟不是"晚一点生效"，而是"按触达速率线性放大误发条数"（所以正确的问法不是"延迟多久能接受"，而是"这条路要不要允许延迟"）。
- 校验的成本：一次集中校验的延迟通常在**毫秒级**【经验】——**相对于误发的合规代价，这个成本可以忽略**。**这个量级决定了什么**：**两侧的量级差得太远，因此这条取舍不需要精算**（毫秒级 vs 数十万条误发）——这也解释了为什么 §7.3.3 把它写成一条"不对称"的性质，而不是一个可以按场景调的阈值。
- **自测动作**：让一个测试账号在短信渠道退订，然后看它在 App 推送与邮件上是否立即停止。**十分钟能做完，且它是合规审查必问的一条。** **这一步的意义**：它同时验证了三件事——名单**唯一**、校验在**出口**、渠道**全覆盖**；而三者缺一，测试账号就会露出破绽。

**失败教训**

**第一版把退订当成"各渠道的功能"**——每个渠道都实现了退订，于是**每个渠道都认为自己做完了**，而**用户看到的是"我退了但还在收"**。教训：**退订不是渠道的功能，是用户与品牌之间的一次约定**——它必须在**唯一的位置**上被校验，而不是在每个渠道里各实现一遍。

**为什么会写成那样（机制层）**：因为**"实现功能"与"满足约定"在单渠道视角下看不出区别**——每个渠道都做了"退订"这个功能（用户能在它这里退掉它自己），因此**每个负责人都可以诚实地汇报"我们支持退订"**；而约定的失效只发生在**渠道之间**，那是横向的组织缝隙，**不在任何一个渠道负责人的视野里**（§3.2.5 的机制：渠道越各自维护，遗漏点越多）。**所以这条教训的机制层表述是**：**一个跨主体的约定，必须有一个跨主体的执行点**——退订名单的权威性不能由各渠道的自觉叠加而成；修法只有两条同时做：**把名单收成一份**（数据）与**把校验收到出口**（代码），而后者决定了新增渠道时是否会重新长出遗漏点。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条顺序固定的路径，与 §4.1 的八步对应：

1. **先把分流做稳、把口径卡写好**（§6.2）——它是唯一的入场券，且**成本极低**（一行哈希 + 一张卡）。
2. **再把触达量按用户统一裁决**（§6.1）——它防的是"活动越多、用户越烦"，而**它的前提是有一个能对总量负责的人**（这是组织动作）。
3. **然后做退订与同意的强一致校验**（§6.4）——它是合规硬要求，且**代价不对称**（延迟发几分钟 vs 一次投诉）。
4. **最后用长期 holdout 回答"整体是否过量"**（§6.3）——它需要耐心（以季度计），但**它是唯一把"所有活动的总和"当作处理对象的实验**。

**顺序的反面**：**先做"更精准的人群"、后做对照组**（§6.2）——精准会**同时提高转化率与自然转化的占比**，因此在没有对照组时，**越精准的效果报告越失真**。**第二条反面**：**先做全渠道覆盖、后做退订一致性**——渠道越多，退订的遗漏点越多，而**投诉的那一次不会等你把渠道补齐**。

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 频控按活动限 | 活动数增加，用户接收量同比例上升 | 注意力被活动数消耗 | 上限按用户（§6.1） |
| 被挡条数当"漏发" | 业务反复要求放宽上限 | 上限形同虚设 | 被挡上看板，定义为克制（§6.1） |
| 无对照的效果报告 | 报告里只有转化率 | 预算投给本来会转化的人 | 分流成为默认（§6.2） |
| 把"精准"当优化方向 | 活动报告越来越好，净增量不涨 | 自然转化占比被一起抬高 | 先有增量口径再谈精准（§6.2） |
| 护栏只观察不拦 | 触达量逐季上升 | 负向指标缓慢恶化 | 硬阈值 + 执行人（§3.2.8） |
| 只有单活动对照 | 每个活动都有效，整体过量 | 反感与疲劳被单活动实验外部化 | 长期 holdout（§6.3） |
| holdout 被其他活动穿透 | 整体实验"没有收益" | 长期视角失效 | holdout 与其他活动隔离 |
| 退订各渠道各一份 | 退了还收 | 合规投诉 | 集中管理 + 出口强一致校验（§6.4） |
| 退订用最终一致 | 同步延迟期间批量误发 | 数十万条误发 | 强一致（宁可延迟发） |
| 降级换渠道不标注 | 该批人的效果混算 | 效果不可比 | 降级进数据层标注 |
| 归因窗口不声明 | 两个部门算出两个增量 | 结论不可比 | 口径卡 + 窗口敏感性检查 |
| 小活动结论记"无效" | 新方向被系统性淘汰 | 只能做大规模活动 | 结论区分"未测出"与"无效" |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——运营的收益形态是"**预算效率、注意力消耗与合规风险**"，三者都不适合用单一百分比表达。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 预算效率 | 净增量 / 触达成本（按渠道与激励分开） | 从"投给高转化概率的人"到"投给高增益的人"——**改善幅度取决于自然转化占比** | 取一次活动补 5% 对照，算增量与转化率的落差 |
| 口径可信度 | 效果报告里有无对照组 | 从"未测"到"可测" | 检查最近三次报告是否有对照列 |
| 注意力消耗 | 用户平均接收触达条数（跨活动跨渠道） | 从"随活动数上升"到"总量恒定" | 列一个用户一天收到的全部触达 |
| 被挡比例 | 被频控挡下 / 应触达 | 活动密集期可达**三成以上**【经验】 | 统计一周被挡条数与占应触达的比例 |
| 合规风险 | 退订后仍被触达的用户数 | 从"数十万条误发"到"零" | 测试账号退订后观察全渠道 |
| 长期健康度 | holdout 组 vs 处理组的长期留存 | 从"不知道"到"有曲线" | 建 5% 长期 holdout，按季度看 |
| 代价 | 触达成本（含激励）+ 实验与护栏人力 | 激励常是数量级更大的那一项 | 按渠道与激励分开核算月度成本 |

**读法**：前三项是**效率与可信度收益**（预算效率、口径可信、注意力），第四、五项是**约束与合规收益**（被挡比例、退订一致），第六项是**长期视角**（整体是否过量），最后一项是**代价**。**本主题最容易出现的错位是只算"触达带来的 GMV"，不算"投给了本就会转化的人的那部分"**——**前者是规模，后者才是效率**。**另一条读法**：最后一项里"实验与护栏人力"看起来是成本，但它对应的是前两项——**砍掉它，你连"这次值不值"和"整体过不过量"都答不出来**。

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**分流与口径卡先行**（入场券，成本极低），**触达量按用户统一裁决**（防活动数消耗注意力，且它需要有人对总量负责），**退订强一致**（合规硬要求，代价不对称：延迟发几分钟 vs 一次投诉），**长期 holdout 最后**（唯一能回答"整体是否过量"的形态，以季度计）。四次失败教训指向同一件事：**精细化运营的失败几乎都不是"发得不准"，而是"发得对但测不出、或者测得出但总量没人管"**——测不出就没有效率、总量没人管就会过度，而**这两件事在任何一个单活动的视角里都看不见**。

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你处境最像的案例，只做一件最小的事——按它的"判据"跑一次自测（列一个用户一天收到的全部触达 / 补 5% 对照算增量 / 列最近 90 天的触达总量曲线 / 测试账号退订后观察全渠道）。哪一件**今天就能做**就先做它：**运营体系的腐化不会报错，只会让效果报告里的增量慢慢变小、而用户的接收量慢慢变大。**
