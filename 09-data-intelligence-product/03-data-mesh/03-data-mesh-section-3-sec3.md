## 3. 设计模式与范式

> 原 § 3（88 行）为「7 个模式 + 场景对照表 + 10 条反模式提示」，缺结构示意、机制解释与失效分析；本节重写为约 310 行的模式手册，原列出的 7 个模式名与 10 条反模式名全部保留。

### 3.1 先看约束：模式不是选择题，是约束的产物

原清单把 Data Mesh 排成七个模式（最小可行 / 领域驱动 / 产品化 / 平台优先 / 治理优先 / AI 原生 / 联邦 AI），读起来像一张「按组织特征挑一个」的菜单。但把它们并排看就会发现：**前五个不是五种并列架构，而是同一套四原则（领域所有权 / 数据即产品 / 自助平台 / 联邦治理）的五个不同起点**——它们回答的都是「先动哪一环」。后两个（AI 原生 / 联邦 AI）则是在四原则之外**追加了一条外部约束**：数据要多一类程序化消费者，或数据不许出域。

四原则之间存在**单向依赖**，这才是模式选择的真正依据：没有领域所有权，就不存在「谁该为这份数据负责」，数据产品化了也没人认领；没有数据产品化，自助平台产出的只是「表」而不是「可消费的资产」，域自治会退化为各搞各的；没有自助平台，第 N 个域的接入成本不下降，自治无法规模化；没有联邦治理，自治会退化为组织层面的失明。所以真正要问的不是「我像哪种组织」，而是**「这四条里哪一条是我现在最缺、且缺了它其他三条立刻失效」**。

模式是约束的产物，同一句「我们要做 Data Mesh」，在下面 6 条约束里的取值不同，正确的起手式就不同。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 数据所有权能否落到「具体的人」 | 决定先动哪一环：所有权落不下去时，先建平台必然无人承接 | 「先建平台，自治以后再说」——平台建完，产出仍由中央兜底，「自治」没有发生 |
| 数据形态与交付形态（文件 / 表 / 接口 / 流） | 决定数据产品化那一环的**契约形态**，以及门禁能校验什么 | 「数据即产品就是写文档」——文档不阻断发布，契约必须机器可执行 |
| 访问模式（点查 / 联邦扫描 / 聚合） | 决定跨域消费走联邦计算还是集中搬运 | 「跨域分析先搬到一处再算」——搬运成本会被每一次查询重复支付 |
| 变更频率与历史要求 | 决定契约是否必须版本化、是否必须支持快照回溯 | 「口径统一一次就完了」——不版本化的变更会在下游无感知时改掉结果 |
| 一致性要求与合规强度（可否出域、可否举证） | 决定治理放在哪一层、要不要走联邦 AI | 「数据挪出去再加密就行」——约束的是**明文出现在哪台机器上**，不是传输是否加密 |
| 规模与团队技能 | 决定自治域的**边界粒度**，以及谁来维护策略资产 | 「域切得越小越自治」——域过小只是把 JOIN 成本从集中式换成联邦式，且更贵 |

本章 [§1.1](03-data-mesh.md) 给的临界点口径是「通常 50+ 业务域、PB+ 数据」，这是【经验】区间而非硬阈值：真正把集中式拖垮的不是总量，而是**需求队列长度与业务节奏的比值**——总量不大但需求密集的组织，同样会撞上瓶颈。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 最小可行 Data Mesh（Minimum Viable Data Mesh）

- **被什么约束逼出来**：组织对「域自治」没有共识，也没人愿意为第一个域的质量承担后果——把变革面收敛到一个域，是唯一能启动的方式。
- **结构**：

```text
只在一个域里闭环（其余域暂时仍走中央），验证的是"自治能不能成立"
   ┌─────────────── 中央平台（此刻只做基础设施） ───────────────┐
   │  存储 / 计算 / 调度 / 权限 / 目录                          │
   └───────────────────────────┬───────────────────────────────┘
                               │ 自助开通
                    ┌──────────▼──────────┐
                    │  试点域（唯一自治域）│
                    │  · 自己加工          │
                    │  · 自己定口径与 SLA  │
                    │  · 自己担质量        │
                    └──────────┬──────────┘
                               │ 对外交付契约（Owner / Schema / SLA / 密级）
                    ┌──────────▼──────────┐
                    │  消费者（含中央团队） │
                    └─────────────────────┘
   ⚠ 此结构中"跨域"这条边尚未被任何真实用例检验
```

- **为什么这样设计有效**：因为变革面被限制在单一团队边界内，域自治、数据产品化、联邦治理这三件事能在同一批人手里闭环，失败的组织成本被压在一个域里——这使「先试点」成为低风险动作。
- **代价**：域与域之间的契约要等到第二个域接入时才会第一次被真实验证，也就是说这个模式**没有验证它最想验证的那一半（联邦）**；同时必须长期维护「一个域自治、其余域走中央」的双轨，双轨的协调成本随域数量增加。
- **失效点**：当试点域作为「唯一自治域」持续超过 1–2 个迭代周期【经验】时，「风险低」会反转成「组织记忆固化」——因为其余域会把「自治是试点特权」内化，推广时每一次都要重新做一轮组织说服，而不是复制一条已验证的流程。
- **真实使用**：【经验】本章 [§6](03-data-mesh-section-6-sec6.md) 整理的阿里 2020–2024 材料自述的推进顺序是「先域内自治、再跨域联邦」。判定方法对任何组织都通用：问它第一个自治域上线后，第二个域是**复制流程**还是**重新立项**。

#### 3.2.2 领域驱动型 Data Mesh（Domain-Driven Data Mesh）

- **被什么约束逼出来**：业务域边界本身不清楚——多个团队共用一个「大域」，改一处要拉三方评审，谁都不认为自己该对结果负责。
- **结构**：

```text
用限界上下文（Bounded Context）切域，而不是按部门或按系统切
  ✓ 按业务语言的一致性边界切
      销售上下文 ──► 销售数据域    （"订单"在域内只有一个含义）
      履约上下文 ──► 履约数据域
      跨域共享的词（客户 / 商品）→ 显式登记为契约口径，不在域内各自解释

  ✗ 按部门切：财务部要的数据跨三个业务域 → 域边界与责任边界不重合
  ✗ 按系统切：一个域一条链路上的三个系统 → 域内自洽、跨域全是接口
```

- **为什么这样设计有效**：因为限界上下文是按「业务语言的一致性边界」画的，同一个术语在域内只有一个含义，跨域分歧会**在契约层被显式暴露**，而不是在下游报表里变成口径事故。
- **代价**：需要真的做过 DDD 战略设计（不是套用名词），且划分结果会落到组织架构上——按 Conway 定律，域边界一旦确定，团队边界必须跟着调整，这是一次组织变更，周期以季度计。
- **失效点**：当业务语言的变化速度快于域边界调整速度时，「业务对齐」会反转成「结构性滞后」——因为边界是按当时的上下文画的，而新的跨域 JOIN 需求会持续产生，边界不调整就把这些 JOIN 全压给消费者，消费者只能自己做跨域拼接（于是又回到中央搬运）。
- **真实使用**：限界上下文出自 Eric Evans《Domain-Driven Design》（2003）【公开】；Data Mesh 借用它作为域划分依据（本章 [§1.1](03-data-mesh.md) 与 Zhamak Dehghani 2019 / 2021 的公开论述一致）。【经验】本章 §6 的阿里案例（5+ 业务域）与字节案例（4 业务域）均以既有业务域为自治单位。

#### 3.2.3 产品化型 Data Mesh（Product-Driven Data Mesh）

- **被什么约束逼出来**：域已经在自治，但对外交付形态每域一套、无 Owner、无 SLA——下游每接一个域就要学一套，接入成本不随域数量摊薄。
- **结构**：

```sql
-- 数据产品对外契约：每行 = 一条对外交付承诺，缺列即拒绝发布
CREATE TABLE data_product_contract (
  product_id      TEXT          NOT NULL,  -- 数据产品唯一标识
  owner           TEXT          NOT NULL,  -- 具体到人，不是团队
  domain          TEXT          NOT NULL,  -- 归属数据域
  schema_uri      TEXT          NOT NULL,  -- 对外 Schema（含演进规则）
  delivery_format TEXT          NOT NULL,  -- 表格式 / API / 流
  freshness_sla   INTERVAL      NOT NULL,  -- 新鲜度承诺
  availability    NUMERIC(4,3)  NOT NULL,  -- 可用性承诺（如 0.999）
  classification  TEXT          NOT NULL,  -- 密级
  version         TEXT          NOT NULL,  -- 语义化版本
  PRIMARY KEY (product_id, version)
);
-- 关键：这张表是发布门禁的输入，不是给人看的文档
--      校验不通过 → 不允许发布（否则契约退化为文档）
```

- **为什么这样设计有效**：因为对外交付被压成一份可校验的契约，消费者只需依赖契约而不依赖实现，上游换引擎、换调度、换存储对下游透明——这正是「域自治」与「可被消费」能同时成立的机制。
- **代价**：每新增一个对外数据产品就多一份要长期维护的契约；契约一旦对外发布，**删除字段的成本远高于新增字段**，契约面随时间单调增长，最终需要一个弃用流程来回收。
- **失效点**：当契约只在发布时校验一次、而不进入运行时门禁时，「下游按契约消费」会反转成「下游按文档消费」——因为破坏性变更常常发生在 schema 之外的实现层（分区布局、更新时点、补充文件），这些不在 schema 校验覆盖范围内，下游只会在数据错的时候才发现。
- **真实使用**：【经验】本章 [§6](03-data-mesh-section-6-sec6.md) 整理的 Netflix 2019–2024 材料自述「以开放表格式作为交付契约」；阿里 2020–2024 自述「对外数据必须满足产品化标准（Owner / 口径 / SLA / 接口 / 变更通知）」。判定方法：问对方「消费者依赖的是契约还是文档」，看是否存在一个**能阻断发布的校验环节**。

#### 3.2.4 平台优先型 Data Mesh（Platform-First Data Mesh）

- **被什么约束逼出来**：每个域自己搭存储、调度、权限、目录的成本高于任何单域收益——公共能力必须先做出来，否则自治就是重复建设。
- **结构**：

```text
平台先立四类通用能力，域只保留"业务语义 + 加工逻辑"
  平台提供（域不自建）：
    · 存储与计算底座（开放表格式 / 联邦查询入口）
    · 治理能力（策略下发、门禁、抽检）
    · 安全能力（身份、权限、密级、密钥）
    · 目录与血缘（联邦元数据 + 字段级血缘）
  ─────────────────────────────────────────────────
  域保留（平台不代做）：
    · 本域的加工逻辑与业务语义
    · 本域对外数据产品的口径与 SLA
    · 对本域数据质量负责
  ─────────────────────────────────────────────────
  平台优先型唯一的验收指标：
    一个新域从零到发布第一个数据产品，实际花了多少天
  而不是：平台能力清单上有多少项
```

- **为什么这样设计有效**：因为通用能力被下沉到平台、域只保留业务语义，所以第 N 个域接入的边际成本趋近于**配置成本**而不是建设成本——自治的规模效应正是从这里来的。
- **代价**：平台必须先于需求存在，因此有一段「能力已建成、用户还没有」的空窗期；空窗期越长，平台越容易按平台团队自己的假设做设计，做出与域真实痛点错位的能力（典型：平台做了统一调度，而域最痛的是权限申请要走两周）。
- **失效点**：当平台的验收指标是「能力清单完整度」而不是「新域接入耗时」时，「基础扎实」会反转成「平台与业务脱节」——因为能力清单可以无限增长，而域的接入耗时不会因此自动下降。
- **真实使用**：【经验】本章 §6 整理的 LinkedIn 2019–2024 材料自述把元数据与血缘做成公共基础设施；阿里 2020–2024 自述「中央只提供平台与契约」。判定方法同上：量一次新域从零到发布第一个数据产品的实测耗时。

#### 3.2.5 治理优先型 Data Mesh（Governance-First Data Mesh）

- **被什么约束逼出来**：合规审查发生在生产之前，且要求能对监管逐条解释「凭什么允许这条数据被这个目的访问」——策略必须先于数据流存在。
- **结构**：

```rego
package datamesh.access

default allow = false

# 域内访问：本域数据、非受限密级
allow {
  input.user.domain == input.asset.owner_domain
  input.asset.classification != "restricted"
}

# 跨域访问：必须命中已登记的数据产品契约，且用途在授权范围内
allow {
  input.asset.contract_id
  input.purpose in input.asset.allowed_purposes
  input.user.roles[_] == "data_consumer"
}

# 受限密级：无论域内域外，一律要求显式且有效的授权
deny_reason["restricted_requires_grant"] {
  input.asset.classification == "restricted"
  not input.grant.active
}
```

- **为什么这样设计有效**：因为策略以代码形式集中定义、由各域在自己的管道里执行，治理规则的**覆盖范围是全局的**而**执行不经过中央队列**——这就是「规则统一、执行分散」能在不重新造一个审批瓶颈的前提下成立的机制（本章 [§2.2](03-data-mesh.md) 把 Rego 定位为逻辑编程的 Datalog 子集）。
- **代价**：策略即代码强制把大量隐性约定显式化，前期投入集中在「把口径与用途问清楚」而不是「写代码」；且策略语言本身成为一个需要专门技能维护的资产，而域团队通常不具备这种技能，会形成新的中央依赖。
- **失效点**：当策略数量增长而缺少「策略覆盖度」的可观测手段时，「合规优先」会反转成「合规形式化」——因为组织无法回答「哪些真实访问路径没有被任何策略覆盖」，未覆盖路径在评审里看不见，只在事故后出现。
- **真实使用**：【经验】本章 [§6](03-data-mesh-section-6-sec6.md) 整理的 LinkedIn 2019–2024 材料自述把校验放在「发布」这个必经环节。OPA 是 CNCF 毕业项目，Rego 的当前语法与内置函数请以 OPA 官方文档当前版本为准。

#### 3.2.6 AI 原生型 Data Mesh（AI-Native Data Mesh）

- **被什么约束逼出来**：AI / Agent 成为数据的第二类消费者，它按接口消费、且没有「这个数看着不对」的直觉——数据产品必须可被程序化调用，且语义必须机器可读。
- **结构**：

```text
数据产品与 Agent 消费面的映射（协议层映射，不是重建一层元数据）
  数据产品（已有：Owner / 契约 / 可寻址）
        │
        ├──► MCP Server    ←── 一个数据产品 = 一个可被发现的资源域
        ├──► MCP Resource  ←── 对外输出（表 / API / 流）
        └──► MCP Tool      ←── 参数化的查询与聚合
  前提：契约里的口径定义必须是机器可读的（字段含义 / 过滤条件 / 粒度 / 新鲜度），
        否则 Agent 只能看到列名，看不到语义
```

- **为什么这样设计有效**：因为数据产品在定义上已经是「有 Owner、有契约、可寻址」的单元，把它暴露给 Agent 只需加一层协议映射，不必重新治理一遍数据——AI 消费面复用的是既有语义，不是新增的元数据孤岛。
- **代价**：一旦数据产品可被 Agent 调用，「谁消费了什么」从「几个看板」变成**不可枚举的调用**，配额与审计的复杂度上升；同时模型对口径的误用会以「看起来合理的错误结果」呈现，比人看错指标更难被发现。
- **失效点**：当口径契约只对人可读（文档、会议纪要）而没有机器可读定义时，「可直接驱动业务价值」会反转成「错误被自动化放大」——因为 Agent 只按接口返回值继续推理，不会对异常值产生怀疑，一个错的口径会被下游的每一步推理继承。
- **真实使用**：【经验】本章 [§5](03-data-mesh-section-5-ai.md) 把「数据产品作为 MCP Server / Resource / Tool」列为演进方向。MCP（Model Context Protocol）由 Anthropic 于 2024 年公开【公开】，协议细节与版本以 MCP 官方规范当前版本为准。

#### 3.2.7 联邦 AI 型 Data Mesh（Federated AI Data Mesh）

- **被什么约束逼出来**：合规判定的是「明文出现在哪台机器上」，数据不得出域；而模型训练又必须用上多个域的样本。
- **结构**：

```text
跨域训练：数据不动，只有加密中间量在动
  域 A（明文只在 A 内）        域 B（明文只在 B 内）
      │                            │
   ① 隐私集合求交（只得到交集，不泄露各自独有样本）
      │                            │
   ② 本地训练 → 加密中间量（梯度 / 份额）
      │                            │
      └──────────► 聚合 / 协调方 ◄──────────┘
                   （只见中间量，不见明文）
                        │
                        ▼
                  联合模型（各方各自持有可用模型）
```

- **为什么这样设计有效**：因为每一方的明文从未离开自己的边界、只有加密中间量参与跨域计算，所以「数据不出域」这个合规前提与「跨域训练」这个业务目标可以同时成立——协作的合法性由**协议**约束，而不是靠合同约束参与方自觉。
- **代价**：跨域通信量由「参数量 × 轮次 × 参与方数」决定，而不是由数据量决定【推算：参数量 × 轮次 × 参与方数，每一步都要同步一次，因此成本随这三项各自线性增长，乘积主导】；域越多、模型越大，通信与同步越主导总耗时，且各方数据分布差异会让聚合收敛变慢。
- **失效点**：当参与方之间的数据分布差异显著（非 IID）时，「跨域协同」会反转成「模型拖后腿」——因为全局聚合会把分布不同的本地更新平均掉，落在任何单一方的数据上，效果可能不如只用自己数据训练；且仅交换梯度不等于隐私（Zhu, Liu, Han, "Deep Leakage from Gradients", NeurIPS 2019【公开】）。
- **真实使用**：【经验】本章 [§6](03-data-mesh-section-6-sec6.md) 与 [§5](03-data-mesh-section-5-ai.md) 把「联邦 AI + Data Mesh」列为金融 / 医疗 / 政务方向；微众银行 FATE（2018 起）与蚂蚁摩斯（2019 起）是该方向公开可追溯的框架与平台，正式版本以各项目官方发布页为准。横向 / 纵向联邦的结构、代价与失效点，见《隐私计算》一节 [§3 设计模式与范式](../../11-cross-cutting/08-privacy-computing/08-privacy-computing-section-3-sec3.md)。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 第一次尝试、无人愿担第一个域的责任 | 最小可行（3.2.1） | 平台优先会先出现一段无人使用的空窗期；治理优先会把还没想清楚的口径提前固化 | 第一个域上线后，第二个域是复制流程还是重新立项 |
| 业务域边界本身有歧义、跨域口径常打架 | 领域驱动（3.2.2） | 产品化型会先把不稳定的边界固化成对外契约，之后改契约比改边界更贵 | 同一个术语在两个域是否含义不同，且无人能裁决 |
| 域已自治但交付形态混乱、下游逐个对接 | 产品化型（3.2.3） | 平台优先解决的是「域能不能自助」，不解决「交付物长什么样」 | 消费者依赖的是契约还是文档；是否存在能阻断发布的校验 |
| 域数量多、每域自建同一套基础设施 | 平台优先（3.2.4） | 产品化型会让每个域各自发明交付格式，格式分裂的成本随域数上升 | 新域从零到发布第一个数据产品的实测耗时 |
| 强合规、要能对监管逐条解释 | 治理优先（3.2.5） | 最小可行会把未定型的策略写进试点域，后续返工 | 能否列出「哪些访问路径未被任何策略覆盖」 |
| 数据消费者从人扩展到 Agent | AI 原生（3.2.6） | 仅产品化型的契约对人可读但未必机器可读，Agent 只看到列名 | 口径定义是否有机器可读形式（含义 / 过滤 / 粒度 / 新鲜度） |
| 数据明文不许出域，又要联合建模 | 联邦 AI（3.2.7） | 任何依赖集中搬运的模式都不满足合规判定口径 | 跨域通信量是否已按「参数量 × 轮次 × 参与方数」算过 |

**最常被误选的一对是「平台优先」与「产品化型」**：两者都以「先立能力」起手，但立的不是同一种能力——平台优先立的是**基础设施**，产品化型立的是**交付标准**。误选的实际后果不对称：选了平台优先却没立交付标准，会出现「平台很强、域照旧只往外丢表」的局面，消费者仍然逐个对接，投入没有转化为接入成本的下降；选了产品化型却没立平台，会出现「每个域都写出了漂亮的契约，但每份契约背后是各自一套存储与调度」，契约维护成本随域数线性增长，最终没人愿意同步更新契约。

### 3.4 组合模式：真实系统不会只用一种

**组合 A：领域驱动 + 产品化 + 平台优先（大型企业的默认组合）**

- 各自承担什么：领域驱动定**边界**（哪些能力归哪个域），平台优先定**底座**（域用什么建），产品化定**接口**（域怎么对外交付）。
- 运维代价：三套资产要同时维护——域边界文档、平台能力、契约清单；其中**契约清单是唯一会持续增长的**，需要配套的弃用流程，否则三年后会有一批没人敢删也没人用的契约。
- 适合规模：业务域边界稳定、域数量在数十量级的组织。

**组合 B：治理优先 + 领域驱动（强合规行业的组合）**

- 各自承担什么：治理优先定**规则与举证方式**（用哪套策略、留什么审计），领域驱动定**责任主体**（哪条规则由哪个域在自己的管道里执行）。
- 运维代价：策略语言成为一项需要专人维护的资产，域团队要接受策略培训；好处是审计与合规解释可以一次性对齐，而不是每次审查临时拼材料。
- 适合规模：金融 / 医疗 / 政务等审查发生在生产之前的行业。

**组合 C：产品化 + AI 原生 + 联邦 AI（AI 优先且数据不能出域的组合）**

- 各自承担什么：产品化定**可消费接口**，AI 原生把接口映射成 Agent 可调用面，联邦 AI 把跨域计算约束在「明文不出域」的边界内。
- 运维代价：三层叠加后，一次数据访问要同时满足契约、Agent 配额、跨域加密协议三套约束，排障链路变长；收益是同一份数据产品可同时被人、程序、跨域模型消费，不必各建一套。
- 适合规模：模型训练需要多方数据、且法规不允许原始数据出域的组织。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 挂着 Data Mesh 羊头，卖数据中台狗肉 | 域自助发布的入口存在，但需求仍默认提给中央团队排队 | 所有权与加工权都没下放，中央仍是唯一瓶颈；「自治」只停留在目录页 | 组织变革比技术变更难推动，先做技术动作更容易交付成果 | 把中央团队的 KPI 从「产出多少数据」改为「域自治率 / 跨域一致率」 |
| 过早拆分 | 域数在短时间内快速增长，跨域 JOIN 请求同步增长 | 集中式 JOIN 成本被换成联邦式 JOIN 成本，且后者更高（跨网络、跨协议） | 把「拆分」当成了目标而不是手段 | 先有 1–2 个能自我闭环的成熟域，再按查询模式扩展【经验】 |
| 数据产品质量失控 | 消费者踩雷后才知道上游改过；质量事故由下游发现 | 契约缺失使变更的影响面无法事先计算，事故只能事后追责 | 只提自治没提交付标准，自治退化为各搞各的 | 对外交付必须满足产品化标准（Owner / 口径 / SLA / 接口 / 变更通知） |
| 平台能力不足 | 域想自助发布，但权限申请、调度接入仍要人工介入 | 自治的成本没有下降，域仍依赖中央，自治意愿衰减 | 平台按能力清单建设，没有以「新域接入耗时」验收 | 用「新域从零到发布第一个数据产品」的实测耗时作为验收指标 |
| 联邦治理缺失 | 跨域数据对不上口径；组织答不出「公司有哪些数据」 | 各域各自为政，跨域不可互联，联邦计算的输入不可解释 | 治理规则的执行被默认交给中央，而中央又不愿成为瓶颈 | 规则统一、执行分散、中央抽检；字段级密级与血缘登记 |
| 业务域不配合 | 域把数据治理当额外负担，只在被考核时补录元数据 | 元数据与血缘的质量随时间衰减，目录逐渐不可信 | 域没有因提供数据产品获得收益或减免其他负担 | 高层支持 + 域数据所有权与激励绑定，而不是靠发文要求 |
| 目录与血缘缺失 | 找不到表、说不清字段来源；变更前无法列影响面 | 自治退化为失明，没人敢改上游，跨域复用无法发生 | 目录被当成「事后补充的文档」，而不是发布门禁的输入 | 元数据与血缘自动采集为主、人工只做校正，并进入发布校验 |
| 没有 API 化 | 消费者直连存储，读的是物理表而不是产品接口 | 上游换存储或分区布局都会破坏下游，交付契约无法成立 | 把「共享一张表」当成了数据产品交付 | 数据产品必须有稳定接口（REST / GraphQL / 流），物理表是实现细节 |
| 没有 SLA | 消费者不知道数据几点到，只能靠问人 | 下游无法据此设计调度与告警，故障由下游先发现 | SLA 需要有人长期承担，无人愿意承诺 | 契约里显式声明新鲜度与可用性，并纳入可观测与抽检 |
| 盲目联邦化 | 所有数据都被拆成域，跨域查询次数与延迟同步上升 | 每次跨域分析都要跨协议、跨网络协调，成本高于一次性搬运 | 把「联邦」当成了架构终点，而不是按访问模式做的取舍 | 按业务能力与查询模式划分域；高频跨域聚合走物化交换区，而不是硬凑联邦 |

**最危险的三条，生产中的典型暴露方式：**

「挂着 Data Mesh 羊头，卖数据中台狗肉」不会以事故形式出现，它以**指标形式**出现：自助发布入口的调用量长期接近零，而中央团队的排期队列仍然排到下一个季度。它的危险在于所有人的汇报里都写着「已完成 Data Mesh 建设」——问题不是被隐藏了，而是被**指标口径**掩盖了，因为没人量过「域自助发布占比」。

「过早拆分」的典型暴露方式是**跨域查询的性能投诉**：业务方发现一个原本一次 JOIN 就能出的数，现在要走三条联邦链路。它的成因不在技术选型，而在域边界是按组织结构而不是按查询模式画的——所以修法不是优化联邦引擎，而是重新看一遍「哪些 JOIN 是高频的、它们跨越了哪些域」。

「目录与血缘缺失」的典型暴露方式是**没人敢改上游**：一个字段改名要开三次会，因为没人能给出完整的下游清单。它的危险在于这种成本不会体现在任何一次事故里，而是均摊到每一次变更上，最终结果是数据管道停止演进——看起来一切正常，只是再也没有人做结构性的改进。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 1 个域 → 3 个域 | 最小可行 | 「自治是试点特权」被固化，第二个域要求重新立项 | 领域驱动（先把边界与责任主体定下来） | 需要一次组织边界调整，周期以季度计 |
| 3 个域 → 10 个域 | 领域驱动（只定了边界） | 每个域自建存储与调度，重复建设成本开始主导 | 平台优先（把通用能力下沉） | 已建成的域内基础设施要迁移，存在一段双轨运行期 |
| 10 个域 → 30 个域 | 平台优先（只有底座） | 交付形态不统一，下游逐个对接，接入成本不随域数摊薄 | 产品化（契约 + 发布门禁） | 要给存量数据产品补契约，补不齐的必须明确列为「未契约资产」 |
| 30 个域 → 50+ 域 | 产品化（契约只覆盖发布时刻） | schema 之外的破坏性变更绕过校验，事故增多 | 契约进入运行时门禁 + 字段级血缘 + 级联影响面 | 需要自动采集血缘并对存量作业做一次回溯解析 |
| 人消费 → Agent 也消费 | 产品化（契约对人可读） | Agent 只看到列名，看不到口径与用途约束 | AI 原生（机器可读口径 + 配额与审计） | 要把口径从文档改写成结构化定义，工作量大且需要业务确认 |

判据是统一的：**当某个模式的核心收益开始由「随规模摊薄」转为「随规模累积」时，就该换**——平台优先的收益是接入成本摊薄，产品化的收益是接入成本为零沟通，一旦观测到它们不再摊薄，说明约束已经变了。

### 3.7 自检清单

- [ ] 能否说出「这四条原则里我最缺哪一条」？答不出，说明还在按菜单选模式。
- [ ] 每一个对外数据产品是否都有**具体到人**的 Owner？写成团队即视为未通过。
- [ ] 契约是否存在一个**能阻断发布**的校验环节？只在文档里写明的不算。
- [ ] 是否存在 schema 之外、不在校验范围内的对外承诺（分区布局 / 更新时点 / 补充文件）？有则说明契约覆盖不全。
- [ ] 能否给出「新域从零到发布第一个数据产品」的实测耗时？给不出，说明平台的验收指标不是接入成本。
- [ ] 跨域共用的口径是否有清单、是否版本化？有没有只靠会议纪要维护的口径？
- [ ] 字段级血缘是否自动采集？人工登记的血缘会在几个月内过期【经验】。
- [ ] 能否一次查询回答「哪些数据含个人信息」？不能，说明密级没有登记在元数据上。
- [ ] 高频跨域聚合是走联邦计算还是物化交换区？有没有把明显该物化的查询硬做成联邦？
- [ ] 数据产品是否有稳定接口，还是让消费者直连物理表？
- [ ] 每个对外数据产品是否声明了新鲜度与可用性，并被实际监控？
- [ ] 自治域的收益（提供数据产品换来的减免或激励）是否明确？只靠发文要求的自治不会持续。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 无人愿担第一个域的后果 | 最小可行 | 把变革面收敛到一个团队边界内，失败成本可控 |
| 边界本身有歧义 | 领域驱动 | 用业务语言的一致性边界切域，跨域分歧在契约层暴露而非在下游爆发 |
| 交付形态混乱、下游逐个对接 | 产品化 | 消费者只依赖契约不依赖实现，上游实现变更对下游透明 |
| 每域重复建设同一套基础设施 | 平台优先 | 通用能力下沉后，第 N 个域的边际成本趋近配置成本 |
| 强合规且要逐条解释 | 治理优先 | 策略集中定义、分散执行，覆盖全局而执行不经中央队列 |
| 消费者从人扩展到 Agent | AI 原生 | 复用数据产品既有语义做协议映射，不新建元数据孤岛 |
| 明文不许出域却要联合建模 | 联邦 AI | 明文从不离开本方边界，跨域合法性由协议而非合同保证 |

> 本节小结：决定模式选择的**唯一那条约束是「数据所有权能不能落到具体的一个人」**——四原则里其余三条都是它的派生：没有所有权，数据产品没有 Owner，自助平台没有使用者，联邦治理没有责任主体。所有「换上某个模式」的动作，本质都是在为「把所有权落到人」创造条件或收尾；判断模式选对了没有，也只需看一件事：**这一次改动之后，有没有多一个人为某一份数据的质量负责**。
