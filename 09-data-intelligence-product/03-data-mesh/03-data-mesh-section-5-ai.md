## 5. 前沿演进（AI 时代）

### 5.1 先分清四类「前沿」

本主题的清单里混着四种性质不同的东西：**协议映射**（把数据产品挂到某个 Agent 协议上）、**研究形态**（联邦 AI）、**产品特性**（AI 插件、自动生成的数据契约）、以及**标准与制度工作**（行业标准化，以及政务侧的数据安全法与个人信息保护法）。把它们并列成"演进方向"，读者会按同一种方式排期——把研究条目排成平台任务，或者把一层协议映射当成一次架构升级。

Data Mesh 还有一个别的主题没有的陷阱：它天然是**接口与标准类**主题。判断一个接口类方向成不成熟，看的不是"模型多强"，而是**有多少方彼此独立地实现或使用过它**。一个只有提出方自己在推的协议，再合理也不能当依赖。这决定了本节最难满足的是第②条判据。

判一个方向能不能现在规划，本节用 L1 / L2 / L3 三级区分，判据是可核验的三条：

- **L1 生产可用**：**① 已 GA 且有正式 release note；② 有第三方（非厂商）公开生产案例；③ 接口稳定**。三条全中才算，可以排进路线图。
- **L2 可试点**：已可用但接口 / 生态未稳，或只有厂商自有案例，或只在小规模被验证。可做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。记录，不要在架构里预留假设。

**判据声明（只对"非 AI 能力"这一类行生效，本表与 §5.2 的逐项评估完全一致）**：本主题下第②条对**AI 方向**是系统性不可得的——联邦化架构的生产细节（哪个域、什么配额、被谁审计、错在哪儿）分散在各组织内部，公开材料通常只到"某公司做了某实践"，而这类材料绝大多数由产品方自己发布，正是 §2.1 里 L2 定义所指的"仅有厂商自有案例"。由此得到本节最重要的一句话：**没有任何一个 AI 方向达到 L1**。对表中标注"非 AI 能力"的三行（联邦查询与开放表格式、机器可读契约标准、开放血缘与元数据交换标准），本节把第②条替换为：**有多家彼此独立的组织分别实现或部署过该能力，且有可被第三方复核的机制性材料（规范文本 / 事件模型 / 兼容性约定）**；理由是接口类能力的证据形态本就是"多方实现同一套规范"，而不是某一家的运营指标。这三行的①③仍按原样核（读者要能点到正式发布条目，并说清接口为什么是稳的）。按替换后的②逐行去核，**只有两行核得到**——开放表格式与开放血缘都能点到不同组织维护的实现或集成；**机器可读契约标准这一行，本节在标准发布方之外点不出任何实现或采用记录，因此判 L2**。这不是说这条能力不可用，而是说它还不到"可以当依赖"的那一档。

五件最容易混的事，先在这里分开：

- **协议名 vs 能力名**：MCP 是**协议名**（由 Anthropic 在 2024 年公开提出），"MCP Server / MCP Resource / MCP Tool"是**能力位**，不是某家产品的专属命名；各平台把"用自然语言查数"实现成什么接口，互不相同，不要张冠李戴。
- **已发布版本 vs 路线图**：判断某个能力能不能规划，只看一处——**该版本的 release note 或官方文档里有没有对应条目**；产品博客、生态伙伴的转述、演示视频都不算（§5.4 给了本主题的判定入口）。
- **论文原型 vs 产品实现**：联邦 AI 与向量索引联邦在本主题里都有论文形态；能不能在生产里开箱使用是另一回事。判定方法：看官方文档里该能力有没有**配额、计费、SLA** 三项。
- **协议映射 vs 架构变化**：把数据产品暴露给 Agent，逻辑上只是**加一层协议映射**——本章 [§3.2.6](03-data-mesh-section-3-sec3.md) 已写明"AI 消费面复用的是既有语义，不是新增的元数据孤岛"。所有权、契约的约束力、联邦治理的执行方式在映射前后完全一样。**只换了消费前端的地方要说成换前端，不要写成架构升级。**
- **规则清晰的判定 vs 语感判定**：数据网格方向的成熟度容易凭"圈子里的讨论热度"判断，但热度与可依赖性是两回事。可依赖的判定只有三类证据：**版本化规范 / 官方发布条目**（能不能点到具体条目）、**多方独立实现或部署**（是不是只有提出方自己在推）、**接口的兼容性约定**（升级会不会伤人）。三条里缺哪条，就在级别里体现出来。

本节有三件事不做，先说清楚：**不评模型能力**（"模型多聪明"是别章的主题，这里只问它是不是改变了数据供给与消费的机制）；**不评具体厂商产品的选型**（同一能力在不同产品里的成熟度不同，选型看各产品的官方文档与自家实测）；**不做"未来蓝图"式描述**（凡是写不出可观察信号的判断，都不写进 §5.6）。这三条边界决定了本节的结论会显得保守——**在接口类主题上，保守才是准确的**。

读下面这张表时，先看第三列，再看第二列：**判据是可核验的，级别只是它的结论**。如果你不同意某个级别，正确的反驳方式是拿出"某条判据其实满足"的证据（点得开的名字与年份），而不是争辩"这个方向很重要"——本节不按重要性排序，按可依赖性排序。

本节对每个方向都问同一句：**AI 到底改变了哪个机制**？本主题的答案只有一条：**消费端多了一类"按接口消费、且没有『这个数看着不对』直觉"的消费者**（本章 [§1.3](03-data-mesh.md) 把"AI 智能体平台消费数据产品"列为 Data Mesh 的交叉关系，[§1.2](03-data-mesh.md) 列出 RAG / Agent / AI 治理 / 行业大模型四类新诉求）。它改变的是**接口形态与消费的可枚举性**，没有改变**数据所有权、契约的约束力、联邦治理的执行方式**。这正是 L1 全在非 AI 侧的原因：AI 缺的是消费接口，不是治理模型。

| 演进方向 | 级别 | 判据（可核验） | 现在该做什么 |
| --- | :---: | --- | --- |
| 联邦查询引擎 + 开放表格式（把数据产品交成可寻址、可直查的接口；同类引擎实现还有 Starburst、Gluten 等） | **L1**（非 AI 能力） | 按 §5.1 判据声明：① Apache Iceberg 与 Trino 各有官方发布页与持续的版本条目（两条时间线都可回溯：Iceberg 自 2018 年进入 Apache 体系、Trino 的独立线自 2019 年的 PrestoSQL 起，版本号以发布页为准）；② 同一套"跨域直查、不搬数据"的模式被多家彼此独立的组织分别实现与部署（判定入口：Iceberg 的表格式与 REST Catalog 接口规范、Trino 的连接器文档，以及各项目的官方采用者材料——本节 §5.4 已点名的 Apache Polaris 与 Apache Gravitino 就是两个由不同组织维护、按同一套开放表格式接口做的目录实现，各自的规范符合程度以项目页为准）；③ SQL 方言与表格式规范固定，兼容性有公开约定（对应①③） | 先补"数据产品有没有可直查的接口"，这比接任何 Agent 协议都优先 |
| 机器可读的口径与 Schema 契约（Bitol / ODCS 一类标准） | **L2**（非 AI 能力） | 按 §5.1 判据声明：① 契约标准有正式规范版本与公开的版本历史（年份区间：这类标准在 2020–2024 年间先后成型并进入基金会体系，具体版本号与日期以项目发布页为准）；③ 契约是版本化文本对象，接口由规范固定；**②核不到**——判定入口是 Bitol 项目页与 ODCS 规范仓库的生态列表，本节在那里只点得到标准发布方自己，点不出两个以上由彼此独立组织维护的实现或采用记录（同一条机制在《数据质量》[§5.1](../../11-cross-cutting/01-data-quality/01-data-quality-section-5-ai.md) 里也是按"②核不到"判 L2） | 口径先写成机器可读定义；但**不要把某一套契约标准当成跨域依赖**——用自家 schema 加 CI 校验就能落地 |
| 开放血缘与元数据交换标准（OpenLineage 一类事件模型） | **L1**（非 AI 能力） | 按 §5.1 判据声明：① 有正式规范页与发布条目（年份区间：2021 年前后进入基金会体系，1.0 一类的里程碑版本在 2024 年前后，以发布页为准）；② 采集端与消费端由多个彼此独立的组织分别实现（判定入口：规范页列出的集成方清单——采集端集成分属不同的项目方，如 Airflow / Spark / dbt 一类的集成，以规范页当前列表为准）；③ 事件模型由规范固定，向后兼容有公开约定 | 让血缘与元数据以标准形态对外，别让每个 AI 工具各解析一遍 SQL |
| 数据产品作为 Agent 的消费接口 | **L2** | ① 协议层有版本化规范与正式修订，但"把数据产品按该协议暴露"这一层没有独立 release note；② 核不到第三方（非产品方）公开的机制级生产材料；③ 协议仍按日期发破坏性修订，接口面未稳 | 可做 PoC：先接一个只读的目录类数据产品，**不要**一次暴露跨域主数据 |
| AI 起草元数据、文档与契约（"写"的部分：元数据 / 分类 / 文档 / 契约草案 / 质量规则） | **L2** | ① 各目录与质量产品的 AI 能力有正式文档条目（代表项目如 DataHub AI Plugins、Monte Carlo、Anomalo、DataWorks），但生成结果的验收标准无通行做法；② 只有厂商自有材料；③ 输出是人可读文本与描述，没有稳定接口 | 只用于**起草**，进目录或进契约前必须有人签字 |
| AI 自动执行治理动作（**本节推演的下一档**：自动修数 / 自动改口径 / 自动发布契约） | **L3** | 三条判据全不成立：无正式发布条目、无第三方材料、且这类动作会直接改数据与契约，当前公开材料里没有可核验的授权、回滚与追责机制 | 记录；先把"谁授权、怎么回滚、出事追谁"写清楚再谈 |
| RAG 的数据来源联邦化（同组另三条：检索结果可追溯、数据权限统一、数据质量可控） | **L2** | ① 其依赖的权限、目录、血缘、质量四项均有正式条目；② "检索走数据产品"的生产材料以产品方叙述为主；③ 检索层接口仍在快速演进 | 先做权限与出口审计，再谈联邦检索 |
| 向量索引联邦 / Embedding 模型联邦 / 元数据联邦 | **L3** | 只有概念与产品方叙述；"跨域向量检索"在召回率与延迟上的口径无公开对照材料 | 记录；先算清跨域检索的召回与延迟预算 |
| 知识图谱联邦与 GraphRAG 联邦推理 | **L3** | 双重未知：本体对齐本身仍在演进，叠加联邦层后无可核验落地材料 | 记录；不要在架构里预留 |
| 联邦 AI（联邦学习 / 联邦分析 / 联邦推理） | **L3**（本主题的接口面） | 本文件只评估它与 Data Mesh 的接口面（跨域训练的数据供给与责任划分），无公开可核验材料；**隐私求交与纵向联邦这类原语，在《隐私计算》[§5](../../11-cross-cutting/08-privacy-computing/08-privacy-computing-section-5-ai.md) 里已按该主题的判据声明判为 L1（非 AI 能力），本节不重复定级** | 先按《隐私计算》的判定方法算通信量与隐私参数，再谈它与域所有权怎么对接 |
| 行业 Data Mesh 标准化（金融 FIBO / 医疗 SNOMED CT / 制造 IoT / 政务合规） | **L3** | 这是**标准与制度**问题：FIBO、SNOMED CT 是既有标准，但"Data Mesh + 行业本体"的组合无公开落地材料；判定入口是行业标准组织与监管口径，不是技术发布条目 | 先划清跨域交换的字段与责任，不要先建行业联邦本体 |
| 平台侧整合（"X + Data Mesh"整合类条目） | **L2** | ① 各平台把目录 / 治理 / 联邦查询做进自家产品，能力有官方文档条目；② 这些集成公告与文档由产品方自己发布，属厂商自有材料；③ 能力绑在产品版本上，跨产品的接口面不统一 | 用"该产品官方文档里有没有这条能力条目"来核，不要用发布会的介绍页 |
| 成熟度模型与评价框架（本章主文件 [§2.1](03-data-mesh.md) 与 [§8](03-data-mesh-section-8-sec8.md) 的条目，**不在学术 4 条之内**） | **L3** | 三条判据均不成立：给的是评价维度，不是可依赖的能力——无正式发布条目、无第三方采用材料、不构成接口 | 用它做自评可以，不要把它当成排期依据 |
| AI 治理引出的数据合规合流 | **L3** | 三条判据均不成立：合规要求是义务而不是产品能力（无能点开的发布条目）、无第三方材料、不构成接口 | 记录合规约束本身；不要据"联邦治理 = AI 治理"这条等式做架构假设 |
| 「Data Mesh 成为大型企业数据架构事实标准」（集中式数据中台无法扩展） | **L3** | 三条判据均不成立：这是采用率断言，不是可依赖的能力——无能点开的发布条目、无第三方材料、不构成接口（判定入口：各组织公开的架构与组织材料，不是技术发布条目） | 可以据此判断方向，不要当排期依据；要核就核自己组织里的域数量与跨域请求量 |

> 表里两条 L1 **全部是既有接口与既有标准**（联邦查询与开放表格式、开放血缘），没有一条是 AI 方向；同为既有标准、但②点不到独立实现方的**机器可读契约标准判 L2**。AI 方向里最高只到 L2（数据产品作为 Agent 消费接口、AI 起草元数据），与上面那条 L2 的成因不同——AI 方向卡的是"公开材料只有产品方自己发"，契约标准卡的是"规范开放、但没有可点到的独立采用方"。其余方向卡住的原因各不相同：向量索引联邦与 KG 联邦卡在"跨域检索的质量与延迟没有公开口径"；联邦 AI 卡在成本量纲（参数量 × 轮次 × 参与方数）与隐私的不可替代性；行业标准化与政务合规根本不是技术能力问题，判定入口在标准组织与监管口径。

**这三级排法直接决定路线图顺序**：

- **先做的就是上表前三行（两个 L1 与那个卡在②的 L2）**：可直查接口（联邦查询 + 开放表格式，L1）→ 机器可读的口径契约（L2）→ 标准形态的血缘与元数据（L1）。顺序里第二件判 L2，指的是"选哪套契约标准"还没到能当依赖的程度；**"把口径写成机器可读定义"本身不依赖那个标准**，用自家 schema 加 CI 校验就能做。这三件排在所有 AI 方向之前，因为**后面每一个 AI 宣称都要靠它们才能被复核**：没有可直查接口就没有"数据产品可被程序消费"这句话，没有机器可读口径就没有"Agent 理解语义"这句话，没有标准血缘就没有"取数可追溯"这句话。
- **L2 做 PoC，并先测两个数**：Agent 取数的**口径误用率**（抽样比对 Agent 的查询结果与人工口径定义的差异）与出口的**调用画像**（谁、多少次、返回了多少、被拒了多少）。这两个数拿不出来，L2 就停在原地。
- **L3 不排进排期**：向量索引联邦、KG 联邦、联邦 AI 的接口面都属于"等信号"，它们的共同前提（跨域检索的质量与延迟可量化、通信量可接受、本体对齐有人维护）比选哪家框架重要得多。
- **回填机制**：每个域每半年回填一次自己那一行的级别；某个 L2 若一年内仍拿不到自己组织里的实测数字，降 L3 并停止投入。

### 5.2 演进方向逐条拆解（核心节）

下面四个方向按同一套结构写：**旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度**。四个方向共用 §5.1 里的同一条机制（消费端多了一类按接口消费的消费者），差别在**这条机制落在哪一层**——落到消费接口上的是 §5.2.1，落到"谁来写元数据"上的是 §5.2.2，落到跨域计算的成本结构上的是 §5.2.3，落到制度与平台版本上的是 §5.2.4。只写收益不写代价的方向，在评审时应被直接打回。

| 方向 | AI 改变了什么机制 | 这条机制落在哪一层 |
| --- | --- | --- |
| §5.2.1 数据产品作为 Agent 的消费接口 | 消费端从"人按语义消费"换成"程序按接口消费" | **接口形态**（语义必须从文档搬到接口上） |
| §5.2.2 AI 起草的元数据与治理 | "写"的成本换成"审"的成本 | **分工与成本结构**（判断权没有转移） |
| §5.2.3 联邦 AI 与向量 / 图谱的联邦化 | 数据移动换成中间量移动、集中索引换成各域索引 | **成本量纲**（随参数量 × 轮次 × 参与方数，而非随数据量） |
| §5.2.4 行业标准化与平台整合 | 与 AI 无因果关系 | **制度与产品版本** |

读法建议：如果时间只够读一节，读 §5.2.1——它包含本主题里唯一一条**今天就可能存在于你系统里**的新增风险（消费面从人变成程序）；§5.2.2 的收益要等你愿意把抽样复核人力与签字流程配齐时才兑现；§5.2.3 的方向本身没错，但它卡在成本量纲上，先算通信量比选框架重要；§5.2.4 的四条收益都真实，但**没有一条来自模型**。

#### 5.2.1 数据产品作为 Agent 的消费接口

- **旧做法与它的卡点**：数据产品的消费面是人——看板、报表、取数工单。卡点有两处：一是人能从语义上纠正自己（看到"复购率 1000%"会先怀疑口径），程序不会，它按返回值继续推理；二是**很多实现里口径只对人可读**——手册、会议纪要、看板注释里写着这个字段回答什么业务问题，接口上只剩列名（本章 [§2.1](03-data-mesh.md) 的数据合约定义列的是 schema、SLA、版本、所有者、访问控制——口径并不在合约的规定项里，而"写进了合约"本身也不等于机器可读）。
- **AI 改变了什么机制**：**消费端从"人按语义消费"换成"程序按接口消费"**——数据产品第一次需要把"可发现、可寻址"对外开放成程序可读的资源与工具位（本章 [§3.2.6](03-data-mesh-section-3-sec3.md) 给了数据产品到 MCP Server / Resource / Tool 的映射图）。机制的实质是**语义的载体变了**：口径定义、过滤条件、粒度、新鲜度必须写在接口上，否则协议再标准，Agent 拿到的也只是列名。
- **由此得到的**：因为口径与权限可以被程序读取，所以**数据产品的复用第一次可以不经过人**——同一个域的数据产品被另一个域的 Agent 直接消费，不必等取数工单。这是本方向唯一真实的新增能力，也是它与"多加一个报表入口"的区别所在。

| 要暴露什么 | 接口形态 | 暴露不了的 |
| --- | --- | --- |
| 数据产品的目录与定义 | 只读、可发现的资源位（表 / API / 流） | 目录里没有的资产——没有登记就没有接口 |
| 参数化的查询与聚合 | 工具位（带参数、可在服务端注入权限过滤） | 任意 SQL 的自由探索（自由度越高，越难配额与审计） |
| 口径与语义 | 契约里的机器可读定义 | 只在文档里写过的口径（人读得懂，程序读不到） |

- **由此付出的**：**其一，消费从"几个看板"变成不可枚举的调用**，配额与审计的复杂度上升（本章 [§3.2.6](03-data-mesh-section-3-sec3.md) 把这一条写成该模式的代价）；**其二，口径误用会以"看起来合理的错误结果"呈现**——Agent 不会对异常值产生怀疑，一个错的口径会被下游每一步推理继承，比人看错指标更难发现；**其三，协议锁定**：Agent 侧的协议仍在快速演进，接得越深，迁移面越大；**其四，权限模型的落点变了**：从"人对表"变成"程序对接口"，行 / 列级过滤必须落在接口层，而不是靠消费方自觉。
- **证据与来源**：【公开】该协议由 Anthropic 在 2024 年公开，有版本化规范与官方 SDK（判定入口：规范页的修订记录与 SDK 发布页；**判定方法：看规范里有没有协议版本协商机制，以及近一年的修订是否包含破坏性变更**）。"Data Product as a Service（DPaaS）"是概念名，没有对应的正式发布条目。【经验】有没有第三方把跨域数据产品按 Agent 协议暴露到生产，并公开给出配额与审计口径，本节给不出可核验的机制级材料——这正是它停在 L2 的直接原因。
- **成熟度**：**L2**。判据：① 在协议层成立（规范与 SDK 有正式发布），但"数据产品作为 Agent 接口"这一层没有独立 release note；② 只有产品方材料；③ 协议仍发破坏性修订，接口面未稳 → 做 PoC，不要作为核心依赖。
- **判定方法**：三个问题——(1) 契约里的口径（字段含义、过滤条件、粒度、新鲜度）有没有机器可读定义？(2) 调用能不能按调用方做配额与审计？(3) 权限过滤落在接口层还是消费方？三问里任一答不上来，先别接协议。
- **接口面分三档，不要一次全开**：**只读的资源位**（目录与定义，风险最低，先开这一档）→ **参数化的工具位**（带参数查询、服务端注入权限过滤，需要配额）→ **自由探索**（任意 SQL / 任意字段，自由度最高，配额与审计最难做，也最容易把不该出的数据取出去）。**三档的顺序不能倒**：先开第三档再补配额，等于把出口敞着再装锁。
- **什么时候值得做**：你的数据产品已经有 Owner、有契约、有目录登记，且消费方是**程序**而不是人时。此时加一层协议映射是低成本高回报的。
- **什么时候不值得做**：数据产品本身还没有机器可读口径、权限还靠人工审批时——先接协议等于把内部语义不一致的问题直接暴露给一个不会怀疑结果的消费者。

#### 5.2.2 AI 起草的元数据与治理：把"写"的成本换成"审"的成本

- **旧做法与它的卡点**：元数据靠人登记，而人工登记的内容会随资产变化而过期——本书《数据目录》[§6](../../04-data-assetization/08-data-catalog/08-data-catalog-section-6-sec6.md) 把"元数据靠人工填、三个月后就过期"直接写成失败教训。本章 [§6](03-data-mesh-section-6-sec6.md) 的案例给出的是这条卡点的另一种表现：LinkedIn 那条把"域自治后全局不可见"列为失败教训，倒逼"统一元数据目录作为公共基础设施"；字节那条把"契约口径说改就改"倒逼成"版本化 + 影响面 + 变更通知流程"。**卡点在供给量**：联邦化之后每个域都要自己把元数据补齐，人工撰写在规模上不成立。
- **AI 改变了什么机制**：**成本结构改变，判断权没有转移**——生成是概率性的，所以产出必须带一个可验收标准和责任人。"写"从线性人工成本变成"生成 + 抽样复核"，省下的是打字时间，新增的是验收成本。**这一条决定它能不能被算作架构演进：判断权还在人手上时，它改变的是效率，不是治理模型。**
- **由此得到的**：因为生成成本下降，所以**目录与契约可以覆盖长尾资产**——过去只覆盖主干表，长尾那部分靠问人，其占比在每个组织里都不同，可自行统计（做法：随机抽 10 个已登记的数据产品，数其中有机器可读口径定义的比例）。覆盖长尾恰恰是联邦治理的前提：跨域消费要求每个域都能自己把元数据补齐，而不是等中央团队排期。
- **由此付出的**：**其一，错误以"看起来合理的元数据"形式进入目录**，而元数据是所有下游系统的输入（血缘、权限、质量、AI 取数全建在它上面），一处错误会被多处继承；**其二，无人签字的生成结果没有责任主体**，事故复盘时追不到"这条口径是谁定的"——本章 [§2.1](03-data-mesh.md) 把数据产品的质量、SLA、成本责任落在 Owner 身上，而无人签字的生成结果没有可追溯的 Owner，这条责任链就断了；**其三，抽样复核是新的固定成本项**，规模越大越不能省。

| 生成对象 | 谁验收 | 进目录 / 进契约前必须有什么 |
| --- | --- | --- |
| 字段描述与业务含义 | 域内的数据 Owner | 一句话说清"这张表回答什么业务问题"，且被 Owner 确认 |
| 分类分级（密级 / PII） | 安全与合规 | 误标一个字段的后果由谁承担；抽样复核比例写下来 |
| 数据契约草案 | 生产方与消费方双方 | 双方签字位 + 版本号 + 兼容性策略（能否向后兼容） |
| 质量规则 | 规则归属的团队 | 历史数据回放得到的误报率，以及阈值随分布变化的复核周期 |
| 血缘推断 | 平台侧 | 覆盖率与**盲区**（推断不出来的部分）被单独标记并可度量 |

这张表的读法是**看第二列**：生成器可以把第一列填满，但**第二列空着的条目不算完成**。
- **证据与来源**：【公开】各目录与质量产品的 AI 能力有正式文档条目（判定入口：产品文档里该能力标的是 GA 还是预览）。【经验】生成结果的验收标准（"直接可用比例"怎么算、抽多少条）在公开材料里没有通行做法，必须自己定并留存口径。
- **成熟度**：**L2（起草）/ L3（自动执行）**。判据：① 有产品文档条目但生成质量的验收标准无通行做法；② 只有厂商自有材料；③ 输出是人可读文本，没有稳定接口——因此可做 PoC，不要作为核心依赖。
- **判定方法**：抽 50 条生成结果人工核对，算两个比例——"直接可用"与"需要重写"。第二个比例高，说明你省下的是打字时间而不是治理成本；再数一次"有多少条生成结果带具体 Owner 签字"。
- **什么时候值得做**：字段量大、长尾资产多，且你已经有抽样复核人力与发布门禁时。
- **什么时候不值得做**：你的目录本身还没有强制登记与发布门禁——给一个没人看的目录生成内容，只是让它更满。

#### 5.2.3 联邦 AI 与向量 / 图谱的联邦化：成本量纲变了没有

- **旧做法与它的卡点**：跨域要联合建模或分析，旧路是**搬运**——把数据集中到一处再算。卡点不在算力，在**所有权与合规**：明文一旦出域，责任就被转移了，而 Data Mesh 的所有权模型要求责任留在域内（本章 [§2.1](03-data-mesh.md) 的领域所有权原则）。
- **AI 改变了什么机制**：**把"数据移动"换成"中间量移动"**（隐私求交、联邦学习里的梯度 / 份额），以及**把"集中索引"换成"各域维护索引 + 跨域查询"**（向量索引联邦、图谱联邦）。机制变化是真的，但**成本量纲也变了**：通信量随**参数量 × 轮次 × 参与方数**增长，而不是随数据量增长【推算：每一轮每方都要同步一次全量更新量，因此每轮成本 ≈ 参数量 × 每参数字节 × 参与方数，总成本再乘以轮次，三项各自线性、乘积主导】。所以它与"数据不出域"这条收益无关，只与规模有关。
- **由此得到的**：因为明文不出域，所以**跨域协作的合规前提与业务目标第一次能同时成立**——协作的合法性由**协议**约束，而不是靠合同约束参与方自觉（本章 [§3.2.7](03-data-mesh-section-3-sec3.md) 把这一条写成该模式的有效性来源）。
- **由此付出的**：**其一，通信与同步成为主导成本**，域越多、模型越大越明显；**其二，非 IID 分布下聚合可能让模型不如只用自己数据训练**（本章 [§3.2.7](03-data-mesh-section-3-sec3.md) 的失效点）；**其三，"只交换梯度"不等于隐私**（Zhu, Liu, Han, "Deep Leakage from Gradients", NeurIPS 2019【公开】）；**其四，向量索引联邦还要付"索引更新频率与一致性"的代价**——各域索引更新节奏不同时，跨域检索的结果会随查询时刻变化；**其五，图谱联邦要付本体对齐的长期成本**——映射谁维护、映射错了谁负责，这两件事在项目立项时就要有答案。

| 联邦化的对象 | 成本随什么增长 | 在规模上的后果 |
| --- | --- | --- |
| 隐私求交 + 纵向联邦（特征对齐） | 样本量、特征数、参与方数 | 与模型参数量无关，因此是"跨域 + 大模型"组合里仍可用的那一条 |
| 联邦训练（全参数） | 参数量 × 轮次 × 参与方数 | 量级跃迁，通常是不可行的那一条 |
| 联邦训练（参数高效微调） | 适配器参数量 × 轮次 × 参与方数 | 可行得多，但要接受"只适配"的定位，别按"训练大模型"立项 |
| 向量索引联邦 | 索引规模 × 更新频率 × 域数 | 跨域检索质量与延迟随更新节奏波动，需要单独的 SLO |
| 图谱联邦 | 实体与关系规模 × 本体映射数 | 对齐成本长期存在，且随域数超线性增长 |

- **证据与来源**：【公开】联邦学习原语、隐私求交、差分隐私有论文与多个彼此独立的实现（判定入口与文献见《隐私计算》[§5.4](../../11-cross-cutting/08-privacy-computing/08-privacy-computing-section-5-ai.md)）；【经验】"Data Mesh + 联邦 AI"的公开材料以方向叙述为主，**没有给出参与方数量与跨域训练规模的成对口径**。
- **成熟度**：**L3（本主题的接口面：联邦训练与域所有权、责任划分怎么对接；向量索引联邦与图谱联邦的跨域检索质量与延迟）**——这几项都无公开可核验材料；**其可落地部分在《隐私计算》[§5.1](../../11-cross-cutting/08-privacy-computing/08-privacy-computing-section-5-ai.md) 里按该主题的判据声明判为 L1（非 AI 能力）**——本文件不重复定级，两处级别不冲突：那里评的是原语，这里评的是它与 Data Mesh 的接口。
- **判定方法**：先把通信量算出来（参数量 × 轮次 × 参与方数 × 每参数字节），再算它在你网络条件下要多久；同时把隐私参数（ε 或参与方与协议）写成可验收的一对数。两个数里任何一个算不出来，这个方向就还停在 L3。
- **什么时候值得做**：参与方少（个位数）、模型可以做到参数高效、且监管要求必须给出可陈述的隐私参数时。
- **什么时候不值得做**：你真实的约束只是"数据不能出域"——那就该回到隐私求交 + 纵向联邦，而不是上联邦大模型（本章 [§3.2.7](03-data-mesh-section-3-sec3.md) 列的同一条）。**向量索引联邦还要多问一句**：各域的索引更新节奏能不能对齐到一个 SLO；对不齐，跨域检索的结果会随查询时刻变化，这类不一致比查不到更难排查。

#### 5.2.4 与 AI 无因果关系的四条方向（行业标准化、平台侧整合、本章主文件 §2.1 的成熟度模型，以及数据网格与 AI 治理的合流）

这四条都被写进了"AI 时代的 Data Mesh"，但机制与 AI 无关：

| 方向 | 旧做法与卡点 | AI 改变了什么机制 | 由此得到 | 由此付出 | 证据 / 成熟度 |
| --- | --- | --- | --- | --- | --- |
| 行业标准化 | 跨机构交换靠个案谈判，字段含义与责任说不清 | **没有改变机制**：改的是标准与制度，判定入口在标准组织与监管口径 | 若规则稳定，跨域交换的字段与责任第一次有依据 | 标准落地周期以年计；合规解释成本落在法务与安全，不在技术 | 判定入口：FIBO / SNOMED CT 一类既有标准与行业监管口径 → **L3** |
| 平台侧整合（"X + Data Mesh"整合类条目） | 目录与治理能力分散在各工具，跨域要自研 | **与 AI 无因果关系**：是产品的版本演进 | 联邦治理的组件从自研变成采购或直接用 | 能力绑在产品版本上，升级节奏受制于产品方 | ① 有官方文档条目；② 只有厂商自有材料；③ 能力绑在产品版本上（判定入口：各平台官方文档里的能力条目，不是发布会的介绍页） → **L2** |
| 成熟度模型与评价框架（本章主文件 [§2.1](03-data-mesh.md) 与 [§8](03-data-mesh-section-8-sec8.md) 的条目，**不在学术 4 条之内**） | "做到什么程度算 Data Mesh"没有公认答案 | **没有改变机制**：给的是评价维度，不是新能力 | 域自治与产品化的进度可被度量、可横向比较 | 模型本身可能被当作目标，指标好看而治理没变 | 三条判据均不成立：无正式发布条目、无第三方采用材料、不构成接口（判定入口：模型的公开文档与其判定项） → **L3** |
| 数据网格与 AI 治理的合流 | 数据合规与模型合规的材料各写一套 | **与 AI 无因果关系**，但被 AI 的合规压力加速 | 一套材料同时回答"数据怎么用"与"模型用了什么数据" | "联邦治理 = AI 治理"是简化：AI 治理还要问标注、评测与模型行为，联邦治理一条都答不了 | 三条判据均不成立：合规要求是义务而不是产品能力（无能点开的发布条目）、无第三方材料、不构成接口（判定入口：监管口径与本章 [§1.2](03-data-mesh.md) 的合规诉求） → **L3** |

**这四条的共同读法**：收益都真实存在，但**没有一条来自模型**——两条来自制度（行业标准、合规要求），一条来自产品版本，一条来自评价框架。把它们写成"AI 时代的 Data Mesh 演进"，会让真正要做的三件事（补可直查接口、写机器可读口径、定跨域失败责任）一件都排不进排期。

再看一层：这四条里有三条的收益要**外部条件先成立**（标准组织发布规范、监管口径明确、产品方发版本），只有你自己的行动推不动它们。这跟 §5.2.1 与 §5.2.2 的差别很明显：那两条的收益**取决于你什么时候动手**（口径写不写、抽样复核做不做）。排期时应该优先做"取决于自己"的那两条，把它们做成能力；等外部条件的那三条，做的是"跟进度"而不是"抢时间"。

### 5.3 与本主题既有栈的接口在哪

Data Mesh 与 AI 之间不是"结合"关系，而是**交接物**关系：谁把什么交给谁、失败时谁负责。这张表比"能不能用"更能决定它能不能落地。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| Data Mesh ↔ 数据目录（[../../04-data-assetization/08](../../04-data-assetization/08-data-catalog/08-data-catalog.md)） | 交接物 = 数据产品的机器可读定义（口径 / Owner / SLA / 密级）；目录侧保证"登记才可发布"，Mesh 侧保证"每个域都能自己登记" | 目录侧：口径没有机器可读定义时，Agent 只能看到列名 | L1（登记与检索机制）/ L2（跨域口径一致性） |
| Data Mesh ↔ 数据血缘（[数据血缘与影响面](../../11-cross-cutting/05-lineage-and-impact/05-lineage-and-impact.md)） | 交接物 = 字段级血缘与影响面；**改口径前要能列出受影响的数据产品** | 血缘侧：血缘缺失时"改口径破坏了谁"算不出来 | L1（采集机制）/ L2（跨域的血缘贯通率） |
| Data Mesh ↔ 数据质量（[数据质量](../../11-cross-cutting/01-data-quality/01-data-quality.md)） | 交接物 = 每个数据产品的质量分与契约阈值 | 域侧：联邦治理只能定阈值与模板，跑不了每张表的校验 | L1（阈值与契约形态）/ L2（跨域阈值的可比性） |
| Data Mesh ↔ 隐私计算（[隐私计算](../../11-cross-cutting/08-privacy-computing/08-privacy-computing.md)） | 交接物 = 参与方 / 协议 / 隐私参数 / 处理位置 | 协作方共同：一方不遵守协议，全局保证不成立 | L1（原语）/ L2（跨域责任约定） |
| Data Mesh ↔ 数据网关与出口（[../../04-data-assetization/07](../../04-data-assetization/07-data-api-gateway/07-data-api-gateway.md)） | 交接物 = 以调用方为单位的配额、审计与脱敏策略；**出口是接口而不是表** | 网关侧：配额与审计缺位时，Agent 的调用不可枚举 | L2 |
| Data Mesh ↔ 指标与口径（[../../04-data-assetization/10](../../04-data-assetization/10-metric-platform/10-metric-platform.md)） | 交接物 = 跨域统一口径的机器可读定义与版本 | 指标侧：口径只对人可读，Agent 的误用无法归因 | L1（口径定义）/ L2（跨域一致性） |
| Data Mesh ↔ Agent 平台（[../../05-agent-platform/01](../../05-agent-platform/01-data-agent/01-data-agent.md)） | 交接物 = 工具清单与权限上下文（以谁的身份调用、能看哪些域） | 接入方：以服务账号身份直连数据产品，等于绕过域所有权 | L2 |
| Data Mesh ↔ 湖仓与表格式（[../../03-data-stack/03](../../03-data-stack/03-lakehouse/03-lakehouse.md)） | 交接物 = 每个域自己的表与命名空间；**数据产品的物理边界要靠命名空间与目录一起划** | 域侧：命名空间不隔离时，"域所有权"只是组织图上的说法 | L1（表格式机制）/ L2（跨域命名与权限的落地） |
| Data Mesh ↔ 特征与训练数据（[../../02-data-science/01](../../02-data-science/01-feature-store/01-feature-store.md)） | 交接物 = 特征的血缘与新鲜度承诺（同一份数据产品既喂看板也喂训练） | 特征侧与域侧共同：两边对"新鲜度"的理解不同时，训练数据的坑会在离线评测之后才暴露 | L1（特征存储是既有能力）/ L2（跨域承诺的对齐） |

一句话概括：**AI 没有给 Data Mesh 新增任何治理原语，只新增了一个消费面**。这张表里"现状"列的写法与前几节一致：**L1 指机制已稳、可以直接排期；L2 指机制可用但跨域的口径或责任还没统一**——跨域场景下最常出问题的不是技术，而是"两边对同一个字段的理解不一样，谁也没错"。

由此得到三条约定。

**第一条约定：没有机器可读的口径，就不叫"Agent 可用的数据产品"。**数据产品的契约里，字段含义、过滤条件、粒度、新鲜度至少要有一份可被程序读取的定义；只有文档里写过的口径，对程序等于不存在。

**第二条约定：先补接口与出口，再接协议。**顺序是：可直查接口（联邦查询 + 开放表格式）→ 权限与配额落地的出口 → 机器可读口径 → 最后才是协议映射。**顺序反了，最常见的后果是把一个内部语义不一致的问题，暴露给一个不会怀疑结果的消费者。**

**第三条约定：跨域消费的失败处理要事先约定。**配额超限时谁降级、口径变更时谁通知、某个域下线时下游怎么办——这三件事在接入评审时就要有答案，因为**联邦架构里的故障不能靠一个域单方面修复**。

这张接口表的用法是**逐行问"交接物在哪、谁签字"**：一行里如果"接口形态"写不出具体形态（是文件、是接口、还是一个人口头通知），或者"谁负责失败"答不出来，这一行就不能进架构评审。**联邦架构里最多的事故不是技术不可行，而是交接物没有归属。**

**第三方生产案例**

- 说明：本节**未能给出**可核验的、含机制细节（域数量、跨域请求量、配额与审计口径）的第三方"Data Mesh + AI"生产案例。本章 [§6](03-data-mesh-section-6-sec6.md) 的四个案例（阿里 / LinkedIn / 字节 / Netflix）出处标注为"机构名 + 年份区间"、无可检索文档名，划在自述一类——它们能支撑"数据域自治 + 联邦计算 + 统一口径"这一层的做法，**不能充当 AI 方向的第②条**。**这个空白本身是结论**：它正是本节把所有 AI 方向判在 L2 / L3 的直接原因。
- 要补第②类证据，最实际的办法是自己造：把域数量、经联邦查询的跨域请求量、配额与审计的拦截次数、口径误用的复盘结论留存成口径。这四组数在联邦架构评审里的分量，超过任何厂商案例。
- 三类证据里**最容易造假的是"Agent 取数准确率"**：只报"准确率大幅提升"而不给评测集、口径与基线，无法复核。**判定方法：只接受同时给出"评测集来源 / 口径定义 / 基线（人工或旧方案）"三样的数字。**
- 本主题三类证据的分布是不均衡的：**第一类（规范与发布条目）很密**——协议、表格式、契约标准、血缘规范都有正式条目；**第二类（第三方案例）很稀**——联邦化架构的生产材料天然分散在组织内部；**第三类（带口径的对照数据）几乎为零**——跨域取数、联邦训练的规模与代价，公开材料里没有可复算的口径。这个分布不是偶然：**它正是"接口类主题"的典型形态**——接口能被公开，运营数据不能。因此本主题的路线图应该照着"接口型"来定：先把接口与语义做完整，把运营指标留给自己测。

**核验 §5.1 表里各条宣称的最小动作**（都不需要采购）：

1. **数据产品可被程序消费**：让一个外部程序按目录发现一个数据产品并取数，看它能不能读到口径定义（读不到，说明语义还只在文档里）。
2. **口径机器可读**：随机抽 10 个数据产品，数"口径有机器可读定义"的比例。
3. **权限出口**：问一句"Agent 以谁的身份调用、被拒时返回什么"。
4. **调用可枚举**：数一次"最近一周有多少次取数调用来自程序而不是人"。
5. **跨域直查**：问一次"跨域查询是搬数据还是就地算"，看有没有可核验的执行计划或网关日志。
6. **联邦训练**：把通信量算出来（参数量 × 轮次 × 参与方数），看它在你网络条件下的耗时。

### 5.5 被过度宣传的部分

**「Data Mesh + Agent 是架构升级」**——实际是：**加了一层协议映射**。数据产品的定义、Owner、契约在映射前后完全一样（本章 [§3.2.6](03-data-mesh-section-3-sec3.md) 的映射图就建立在这个前提上）。**为什么会这样**：Agent 需要的是"可被程序发现与调用"，这确实是新需求，但它落在**消费面**；架构的变化要看**所有权与治理**有没有动，而这两者一点没动。**它什么时候才会成真**：Agent 的调用被纳入域所有权的责任范围——即"Agent 误用口径"能被追到具体域与具体 Owner 时。**判定方法**：问"Agent 上一周的调用里，有多少次能被归到某个域的责任人"，答不上来就说明它只是接了个前端。

**「联邦学习让数据不出域，所以能训大模型」**——实际是：**收益（数据不出域）与成本（参数量 × 轮次 × 参与方数）是两个独立量纲**，后者在 LLM 规模上是量级跃迁，而且"只交换梯度"并不等于隐私（Deep Leakage from Gradients, NeurIPS 2019）。**为什么会这样**：把"数据不动"读成"规模可以随便放大"，是把合规约束当成了性能约束的解法。**它什么时候才会成真**：公开材料开始给出**参与方数量 + 通信量 + 收敛差距**这一组三件套，且模型规模停在参数高效那一档。**判定方法**：让对方把通信量按参数量 × 轮次 × 参与方数算一遍，算不出来就不是可评估方案。

**「AI 能自动生成契约与元数据，联邦治理就自动化了」**——实际是：**生成器提供的是草稿，不是承诺**。契约的约束力来自双方的责任关系与 CI 里的校验（本章 [§2.1](03-data-mesh.md) 把契约定义为生产消费双方之间的协议），不来自写它的工具。**为什么会这样**：把"产出文本"当成"建立约定"，忽略了约定必须有可判定性与责任主体。**它什么时候才会成真**：生成结果默认带 Owner 签字位、有一条可判定的验收标准（抽样复核的通过率），并且违约时能追到人。**判定方法**：抽三份契约问"上次因为契约被拒的发布是哪一次"——答不出来的那份已经退化成文档。

这三条的共性：**它们都把"某个环节变得更容易"当成了"整套机制已经成立"**——协议映射成立的是调用可达，联邦学习成立的是数据放置，生成器成立的是产出速度。而本主题的判据始终只有一条：**你能不能指出这条宣称改变的是所有权、契约、还是治理执行中的哪一项，并且证明它真的变了。** 三项都没动的，就是接口或效率的改良。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| Agent 消费数据产品的第一个规模化工件不是"数据产品 = 某个协议的服务端"，而是**出口的配额与审计** | 目录与网关的正式发布条目里出现"以调用方为单位的配额与审计"；采购条件里出现"调用可枚举" | 公开案例把 Agent 取数的成功归因于协议覆盖度，而配额与审计缺失也能上线 |
| 联邦 AI 会存活在"少量参与方 + 强监管 + 参数高效"的垂直场景，不会成为跨域数据消费的默认形态 | 公开材料给出参与方数量与通信量的成对口径，且模型规模停在适配器级 | 出现十家以上参与方、全参数规模、并披露通信量与收敛差距的公开生产案例 |
| 数据产品的契约会先收敛到**机器可读的口径**，而不是先收敛到 Schema | 目录与指标平台的正式条目里出现"口径的机器可读定义 + 版本 + 变更通知" | Agent 取数的效果提升被主要归因于模型能力，而不是口径定义的完整度 |
| 行业 Data Mesh 会走"数据交换标准 + 监管口径"路线，不会走"行业本体联邦化"路线 | 行业标准组织发布的是字段级交换与责任约定，而不是跨机构本体映射规范 | 出现被多方采纳的跨机构本体联邦规范，并有可核验的生产部署 |

写这四条时的共同约定：**信号必须是外部可观察的**（正式功能条目、发布说明、带口径的公开案例），而不是"我觉得会"。**被检验得最快的是第三条**——下一批目录与指标平台的发布说明里有没有"口径的机器可读定义"，一年内就能看到；**最慢的是第二条**——它是一种否定式预测，需要有人长期公开参与方规模与通信量对比。

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 有人在推"我们的数据产品要接 Agent" | 先抽查 10 个数据产品的口径有没有机器可读定义 | 观察调用能否按调用方配额与审计 | 不要在口径只对人可读时先接协议——错误会被自动化放大 |
| 数据产品还没有可直查接口 | 先补联邦查询 + 开放表格式这一层（L1） | 观察跨域查询是搬数据还是就地算 | 不要用"先把数据集中一处"当代替方案——它转移了所有权 |
| 想用 LLM 补元数据 | 先定抽样复核比例与验收标准，再定谁签字 | 观察"直接可用比例"是否上升 | 不要让无签字的生成结果直接进目录 |
| 业务方要求"取数自由探索" | 先做出口的配额与审计，再放开参数化查询工具位 | 观察被拒次数与超限次数是否可解释 | 不要一上来就暴露任意 SQL——自由度越高越难管 |
| 有人提出联邦训练大模型 | 先算通信量（参数量 × 轮次 × 参与方数）与隐私参数 | 观察是否把全参数降级为参数高效微调 | 不要在参与方多、模型大的组合里做全参数联邦训练 |
| 跨机构要联合建模 | 先做隐私求交与特征对齐（原语层，见《隐私计算》[§5](../../11-cross-cutting/08-privacy-computing/08-privacy-computing-section-5-ai.md)） | 观察参与方数量与协议是否稳定 | 不要先交换原始数据再"脱敏比对" |
| 想做行业联邦本体 | 先划清跨域交换的字段与责任 | 观察行业标准组织发布的是交换规范还是本体规范 | 不要先建本体——对齐成本长期存在且无人维护 |
| 预算有限，只能做一件事 | 做"机器可读的口径契约"（它同时喂饱目录、血缘、质量与 AI 消费；标准选型可以等，把口径写成定义并进 CI 校验现在就能做） | 观察口径变更能否自动通知到受影响的数据产品 | 不要把预算先花在接协议或买 AI 插件上 |
| 要给管理层一份判断 | 写成三行：域数量 / 跨域请求量 / 调用可枚举比例 | 观察这三行能不能被第三方按口径复核 | 不要用"我们上了 Data Mesh + AI"这种描述代替数字 |
| 团队想做"AI 原生的数据网格"改造 | 先把当前状态按四原则过一遍：所有权在哪、契约有没有机器可读定义、平台能不能自助、治理规则是计算化的还是审批式的 | 观察四项里哪一项真的动了 | 不要在所有权与治理规则没动的情况下宣布"AI 原生"——那是把消费面当成了架构 |

「明确不要做」这一列的共同逻辑：**这些动作的代价是确定的**（改数据放置、动域边界、引入新运维面），**而收益依赖一个尚未成立的假设**（程序会理解语义 / 参数量不影响可行性 / 生成器能替代责任人）。等 §5.6 的信号出现再投入，损失的只是时间。

### 5.8 小结

> 本节小结：本主题下 AI 真正改变的**唯一那条机制**是**消费端的接口形态**——多了一类"按接口消费、且不会怀疑结果"的消费者，于是口径、权限、语义必须从文档搬到接口上。由此才有"数据产品 = 可被程序发现与调用的资源"这一说法，也才有必要把目录、血缘、契约、出口审计从辅助组件提到主线位置。它**没有**改变的是本章 [§1.1](03-data-mesh.md) 的四原则本身：**领域所有权、数据即产品、自助式平台、联邦治理一条都没有被 AI 改写**；也没有改变成本曲线（跨域计算的成本随参数量 × 轮次 × 参与方数，而不是随数据量）。
>
> 判断本主题下任何新提法的快捷方式：**它改变的是"接口与语义的载体"，还是只把旧机制套到一个新的消费者身上？** 前者立刻改变可用性（本节判 L1 / L2 的那几条），后者先要付审计与验收的成本（本节判 L3 的那几条）。第二条同样快的判断：**这件事能不能在没有任何 AI 的前提下先做完**——能做完的（可直查接口、机器可读口径、标准血缘），今天就该排进路线图——其中只有"选哪套契约标准"需要等信号，"把口径写成机器可读定义"不需要。
>
> 如果只能带走一句话：**先把接口与口径做成机器可读的（可直查、可配额、可审计），再谈用哪种协议把它交给 Agent**；顺序反过来，就是把一个内部语义不一致的问题交给一个不会怀疑结果的消费者。
>
> 💡 **思考锚点**：抽 50 条你目录里 AI 起草的字段描述，数两个比例——「直接可用」与「需要重写」各占多少；再数其中有多少条带具体 Owner 签字。如果「需要重写」的比例高、带签字的比例低，那你省下的是打字时间还是治理成本？
