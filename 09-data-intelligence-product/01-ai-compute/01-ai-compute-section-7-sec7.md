## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

第一，打分表把**管着不同对象的几个层次**当成了同一层的并列产品。打分表把「传统数据平台 / 数据中台 / 数据湖·Lakehouse / AI 计算平台 / AI 智能体平台」五者放进一张表，按同一组维度（核心负载、数据形态、算力、治理对象、工具成熟度……）逐项填值。但这五者的**治理对象**分别是：数据表与查询、指标与口径、数据的存在形态、特征与模型、Prompt 与工具与记忆。它们不是同一岗位的五个候选人，而是同一条链上的五个环节——**给它们逐项比较优劣，等于给「仓库、货架、流水线、成品」排一个名次。**

第二，同一维度在不同层上权重相反。「算力」这一维对 AI 计算平台是核心（GPU 是它的成本主体），对传统数据平台是无关项（CPU 换一批不影响架构）；反过来，「工具成熟度」一列对 AI 智能体平台给出的是偏低的取值，这个分差反映的是**「谁先出现」**，不是「谁能力弱」——而「先出现」这条差异会自行消失：**【公开】** 主文件 §1.4 记录 2024–2025 年 AI 计算平台从「传统 ML 平台」演化为「LLM 训练 + 推理 + 微调 + Agent 一体化平台」（年份条目见该节，请以其记录来源为准）。**把一条会消失的差异当成长期选型依据，是这类表最容易造成的误导。**

第三，也是本章最要紧的一条：打分表**看不见成本函数的形状**。AI 计算平台的成本主体是**按容量付**——卡是买来或长期租的，账单随「卡数 × 时间」走，**不随请求数走**；而 Serverless、按量付费的数仓、按 token 计费的模型服务都是**按用量付**。这两种形状的差别不是几分之差，而是**闲置与排队哪一个会出现在你的账上**：按容量付时，利用率低就是纯亏（主文件 §1.1 把它列为第一号痛点与第一号驱动力）；按用量付时，闲置不出现在账上，但单价里含着平台加价。而衡量规模的两条曲线在某个密度点上会交叉（§3.2.3）。

第四，决策树用「我要做什么」提问，而选型的正确入口是「我被什么约束」。判断节点是「我要做 BI」「我要训练模型」「我要做 Agent 编排」这类需求表述，不是约束条件。同一条需求在不同约束下答案会相反：同样一句「我要做 LLM 推理」，流量平稳时自建常驻实例更便宜，峰均比高时只能用弹性资源；同样一句「我要训千亿模型」，落到只有单机 8 卡的团队和落到有机柜级互连域的数据中心，可选路线完全不同。

第五，真正决定成败的约束，在表里一行都没有：**单任务算力下限**（单个模型能否装进一张卡）、**迭代周期**（决定要不要抢占式调度与分钟级检查点）、**数据位置**（决定算力能不能集中，跨域搬数据的时间常超过训练本身）、**监管留痕要求**（决定平台迭代速度的上限）。四条都不在打分维度里。

**本章采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 管理对象 | 你管的是数据、是口径、是形态、是模型与算力，还是 Agent 的运行状态 | 决定平台的元数据模型与门禁形态。管错对象的表现不是「不好用」，而是「平台建好了，但没有任何岗位的职责落在它上面」 |
| 任务时间形态 | 负载是长时独占整卡（训练），还是短时突发可碎片（推理） | 决定两类负载能不能共处一池，也决定调度器要不要 Gang Scheduling（N 卡同时启动）、抢占与拓扑感知 |
| 单任务算力下限 | 单个模型 / 单个任务能否装进一张卡的显存 | 决定要不要并行框架与域内互连；**参数超过单卡显存之后，缺的是域内带宽而不是卡数**——算力归属相同、软件栈相同，仅这一条就能把路线分开（§3.2.1 与 §3.2.2 的判据） |
| 成本形状 | 按容量付还是按用量付，闲置与排队哪个是你的主要损失 | 决定自建与租用的交叉点在哪；这一条在打分表里完全不可见，却是本章金额最大的一项 |
| 数据位置与主权 | 数据能不能跨域、能不能出内网 | 决定算力能否集中。数据位置是硬约束，算力才是可以搬走的那一部分 |
| 治理与留痕 | 是否需要「模型 → 决策 → 留痕」全链可复现 | 决定平台迭代速度的上限：合规是横向约束，平台越大，一次规则变更要连带重训与重审的模型越多 |

> 这 6 条的权重随处境移动：**管理对象**是第一步，它决定后面五条问给谁听；**任务时间形态与算力下限**在你要做训练时同时生效，且不可跳过；**成本形状**在规模上来之后成为主要矛盾（试点期看不出来）；**数据位置**在跨域或多云时才出现；**治理与留痕**在金融 / 医疗 / 政务场景直接决定平台能不能上线。

### 7.2 候选方案全景

先列**平台层**的五个候选，再列 AI 计算平台**内部**的七个模式（同一候选内部的实现选择，见 [§ 3 设计模式与范式](01-ai-compute-section-3-sec3.md)）：

| 层次 | 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- | --- |
| 平台层 | 传统数据平台 | 结构化数据的计算与查询 | 表 + SQL 引擎，负载是聚合与 ETL；算力是 CPU | 数据分析师、数据工程 | 商业数仓 / 开源引擎 |
| 平台层 | 数据中台 | 口径与资产化的中心 | 把指标与标签做成有中心的定义与复用，治理对象是口径 | 数据团队、业务方 | 自建为主 |
| 平台层 | 数据湖 / Lakehouse | 数据的存在形态与多模态底座 | 在对象存储上用表格式（Iceberg / Hudi / Delta）提供事务与 schema，查询与存储在架构上分离 | 数据团队 | 开源表格式 + 商业托管 |
| 平台层 | AI 计算平台 | 模型与算力的生产线 | 把 GPU 池、分布式训练、特征、模型注册、推理服务封成一站式；账单主体是算力容量 | 数据科学家、算法工程、业务开发 | 自建 / 云服务 |
| 平台层 | AI 智能体平台 | Agent 的组装与运行 | 把 LLM + 工具 + 记忆 + 规划做成可编排的运行时，治理对象是 Prompt / 工具 / 记忆 | 业务开发、AI 应用团队 | 自建 / 商业 |
| AI 计算平台内部 | 传统 ML 平台（Classical MLOps） | 小模型、天级迭代 | 模型小、可共置，同一张卡背多个模型的流量，收益来自复用已有算力 | 推荐 / 风控团队 | 自建 / 商业（TFX、MLflow 一类开源件） |
| AI 计算平台内部 | LLM 一体化平台 | 参数超单卡的大模型 | 训练靠并行拓扑（TP / PP / DP + ZeRO），推理靠显存分页与连续批处理 | 大模型团队 | 自建 / 商业 |
| AI 计算平台内部 | Serverless AI 平台 | 按调用付费的推理 | 请求触发实例创建、推理后释放，成本随调用量线性化 | 创业团队、PoC | 商业（Modal / Replicate 一类） |
| AI 计算平台内部 | GPU 算力池化平台 | 一批卡服务两类负载 | MIG 硬切、时间片软切、Gang + 拓扑感知调度，把训练空隙填给推理 | 超大规模训练团队 | 自建 / 商业 |
| AI 计算平台内部 | 垂直行业 AI 平台 | 合规与留痕优先 | 「模型 → 决策 → 留痕」绑成一条链，事后可复现单次决策 | 金融 / 医疗 / 政务 | 自建为主 |
| AI 计算平台内部 | 开源一体化平台 | 自主可控、可逐层替换 | K8s + 调度 + 流水线 + 追踪注册 + 推理服务逐层拼装，最后一公里自补 | 技术强、数据不出内网的团队 | 开源 |
| AI 计算平台内部 | 联邦 / 多云 AI 平台 | 跨域与避免锁定 | 作业与集群解耦，按「数据在哪」就近调度 | 大型跨国企业 | 自建 / 商业 |

这 12 项分**三族**：**数据资产族**（传统数据平台、数据中台、Lakehouse）、**模型与算力族**（AI 计算平台及其七个内部模式）、**Agent 编排族**（AI 智能体平台）。

**先分族再选，能省掉一半比较**：族与族之间不是替代关系，各自的失败方式也不同。**数据资产族死于口径与覆盖**——平台建得再好，业务方找不到、看不懂就回到问熟人；**模型与算力族死于利用率与排队**——卡在那里、任务也在那里，两头都在等对方（主文件 §1.2 痛点清单里的「训练-上线鸿沟」是第 2 条、「GPU 黑盒」是第 4 条，两者是同一根因）；**Agent 编排族死于不可控**——Prompt 与工具版本没有治理，线上行为无法复现。

还有一点必须点明：**三族的边界正在互相侵入**。湖仓厂商向上叠 AI 计算能力（把推理接进 SQL 引擎），AI 计算厂商向下叠 SQL 引擎与目录，智能体平台开始自带模型调用与缓存。所以「选哪一族」这个问法正在变成**「从哪一族的主场开始，往哪一侧扩展」**——而扩展方向由你的主数据在哪一侧决定，不由产品功能清单决定。

### 7.3 机制差异：为什么它们表现不同（核心节）

候选之间的差异看似十几种，但都能归到四条机制上。下表先给出全貌，四条随后逐个展开：

| 机制 | 一句话 | 它主要把谁分开 |
| --- | --- | --- |
| 算力归属 | 卡是谁的、按什么粒度被切给谁 | 独占 / 池化共享 / 按秒租用 / 跨云联合四种取值彼此分开 |
| 任务时间形态与算力下限 | 长时独占还是短时突发、单任务能否装进一张卡 | 传统 ML 平台与 LLM 一体化平台 |
| 治理对象 | 平台的元数据模型描述什么 | 数据资产族 / 模型与算力族 / Agent 编排族 |
| 数据位置 | 数据能不能出内网、能不能跨域 | 单集群与联邦 / 多云；也决定训练启动时间 |

#### 7.3.1 算力归属：独占池、池化共享、按秒租用、跨云联合

**机制是什么**：同一批物理卡的服务方式有四种粒度——**独占**（一个团队或一个任务持有整卡）、**池化共享**（一张卡切成不同粒度给不同任务，如 MIG 硬切与时间片软切）、**按秒租用**（平台按调用创建与释放实例）、**跨云联合**（作业与集群解耦、按数据位置就近调度）。粒度决定成本曲线的形状与隔离性的强弱。

**它在各候选中的实现差异**：

| 取值 | 谁在用 | 成本随什么增长 | 隔离性 | 典型失效方式 |
| --- | --- | --- | --- | --- |
| 独占 | 自建机房 / 单团队采购 | 卡数 × 时间（利用率低即纯亏） | 最强 | 闲置；单团队按峰值配卡，闲时无法给别人用 |
| 池化共享 | GPU 算力池化平台、AI 计算平台主力 | 卡数 × 时间，但被利用率摊薄 | 弱于独占（时间和显存受邻居影响） | 池里没有空闲资源时（单个任务大到整域才放得下）共享假设失效 |
| 按秒租用 | Serverless AI 平台 | 调用量（闲置不出现在账上） | 单实例内定制受限 | 实例长期不缩容时，按秒单价超过折旧摊销 |
| 跨云联合 | 联邦 / 多云 AI 平台 | 各域算力 + 跨域传输 | 按域隔离 | 数据分发与出口费用吃掉算力价差 |

**由此必然导出的性质（因果句）**：因为**池化的有效算力等于「卡数 × 利用率」，而独占的成本等于「卡数 × 时间」**，所以池化带来的收益全部落在乘数的第二项上，且它随时间累积——**这是一条与「换更强的卡」完全不同的增益路径**。代价是**共享粒度必然削弱隔离**：时间片与显存被邻居影响，尾延迟在池化环境下不可预测，而对延迟敏感的业务往往正是最需要确定性的业务。反过来，因为**按秒租用把「闲置」从账上移除**，它在调用稀疏时是最省的选择；但同一机制也决定了它的单价里必须含平台加价，**当实例长期不缩容时，这套账就反转了**（§3.2.3）。跨云联合则把矛盾换了一个位置：因为作业被抽象成与集群无关的描述，容灾与议价能力同时获得，**代价是数据位置成为新的硬约束**——按「哪便宜往哪调度」时，先付的是跨域传输与出口费用。

**公开证据**【公开】：MIG 把 A100 起的 GPU 做成可硬件切分的实例，这一能力可由 NVIDIA 的 MIG 官方文档核验（A100 于 2020 年发布、MIG 随该代产品引入，可按「NVIDIA MIG 文档 + 产品代次」检索核验）；Volcano 为 K8s 补上 Gang Scheduling 等批调度能力，见其官方仓库与 CNCF 项目页的收录记录（开源年份与阶段以该页当前记载为准）；Serverless 形态的四家（Modal、Replicate、AWS Lambda + SageMaker、阿里云 PAI EAS Serverless）见各家官方文档的产品与计费页（这类页随版本迭代、不落固定发布年份，价格与并发上限一律以官方文档当前版本为准）——以上均见 [§ 3 设计模式与范式](01-ai-compute-section-3-sec3.md) 的各模式条目。判定方法：看你的调度器能不能回答「这张卡现在切给了几个任务、各自什么粒度」——答不出，说明你在独占与池化之间；答得出但不含拓扑信息，说明池化做到了、拓扑感知还没做。

**失效条件**：当单个训练任务大到「整域才放得下」时，池化的共享假设被推翻——池里没有可切给推理的空闲资源，此时池化只剩下调度开销。当调用密度高到实例长期驻留时，按秒租用的经济学反转，此时它只剩下弹性价值。

#### 7.3.2 任务时间形态与算力下限：为什么「同一批卡」不是同一件事

**机制是什么**：训练与推理的时间形态相反——训练是**长时、不可抢占、整卡甚至是整域**的任务（抢占就要回滚到检查点），推理是**短时、突发、可碎片**的任务。单任务的算力下限则是另一条独立机制：**一个模型能否装进一张卡的显存**。

**它在各候选中的实现差异**：

| 候选 | 时间形态假设 | 单任务算力下限 | 由此需要的调度能力 |
| --- | --- | --- | --- |
| 传统 ML 平台 | 天级重训、短时推理 | 单卡甚至单卡的一部分 | 队列 + 实验追踪；多模型共置 |
| LLM 一体化平台（训练侧） | 长时独占、不可抢占 | 多卡到多节点（TP 必须在域内） | Gang Scheduling + 拓扑感知 + 检查点 |
| LLM 一体化平台（推理侧） | 短时突发 | 单卡起，但显存是硬约束 | 连续批处理 + 显存分页 |
| Serverless AI 平台 | 突发、稀疏 | 单卡 | 冷启动管理、权重分层缓存 |
| GPU 算力池化平台 | 两类混合 | 都不设限（池里同时容纳） | MIG / 时间片 / 抢占 + 拓扑感知 |

**由此必然导出的性质（因果句）**：因为**训练不可抢占、推理可碎片**，所以「把两类负载放进同一个池」这件事在机制上要求调度器同时具备两种能力（既能给训练留出整域，又能把空隙切给推理），**收益是利用率，代价是调度状态空间与尾延迟的确定性**——这两项都要有人维护（§3.2.4）。而**算力下限**这条机制给出的是更硬的分界：因为**张量并行的 AllReduce 必须落在 NVLink / NVSwitch 域内**，所以「哪些卡能组成一个任务」被物理拓扑锁死，集群会随任务形状碎片化、排队变长；**参数超过单卡显存之后，加卡不能解决问题，缺的是域内带宽**（§3.2.2 的通信拓扑结论）。推理侧还有一条同源的显存账：因为**KV Cache 随上下文长度线性增长**，长上下文的并发上限由显存除以单序列 KV 体积决定，而不是由卡的算力决定——这正是分页与连续批处理要解决的问题。

**公开证据**【公开】：分页注意力机制见 Kwon 等人在 SOSP 2023 的工作，分片优化器状态见 Rajbhandari 等人在 SC 2020 的工作（两处均见 [§ 3 设计模式与范式](01-ai-compute-section-3-sec3.md) 的公开证据条目）；主文件 §2.1 与 §2.3 分别列出 Gang Scheduling、MIG、Time-Slicing、Continuous Batching、PagedAttention 等机制。判定方法：把你最大的一次训练任务的卡数与「这些卡能不能落在同一个互连域内」两个事实摆在一起——卡数够但域装不下，瓶颈就是拓扑而不是采购量。

**失效条件**：当模型小到可以共置、迭代以天计时，并行拓扑与分页显存整套基建都是净开销（§3.2.1）；当推理请求从「长上下文、批量稳定」变成「短请求、突发、长尾」时，分页与连续批处理的收益下降，因为分页收益来自并发序列共享显存块，突发短请求很难凑出稳定的批。

#### 7.3.3 治理对象：表 / 字段 → 指标 / 标签 → 特征 / 模型 / 实验 → Prompt / 工具 / 记忆

**机制是什么**：平台的元数据模型描述什么，就决定了它能对什么设门禁。治理对象在链路上是逐层变的：数据资产族管**表与字段**（也有指标与标签），模型与算力族管**特征、模型、实验、推理服务**，Agent 编排族管**Prompt、工具、记忆**。

**它在各候选中的实现差异**：

| 候选族 | 元数据的核心对象 | 门禁设在什么动作上 | 缺这一层的后果 |
| --- | --- | --- | --- |
| 数据资产族 | 表 / 字段 / 分区 / 血缘 / 指标口径 | 结构变更、口径变更 | 数值口径歧义 |
| 模型与算力族 | 特征 / 样本 / 模型版本 / 实验 / 服务版本 | 上线发布、模型切换 | 「线上跑的是哪个版本」答不出；训练与推理错位 |
| Agent 编排族 | Prompt / 工具清单 / 记忆 / 调用链 | 行为可复现与调用准入 | 线上行为不可复现，工具越权无从追溯 |

**由此必然导出的性质（因果句）**：因为**模型的「口径」由训练数据、特征定义与模型版本三者共同决定**，所以模型族的门禁必须能回答「这次上线改了哪一版特征、用哪一批样本训的、对比的是哪个基线」；而数据族的门禁只需要回答「这列的口径变没变」。**两者的门禁形态不同，不能互相替代**——用血缘系统去管模型发布，会漏掉「换了模型但血缘里看不出来」这一类隐形变更（这类变更在下游表现为语义悄悄变了却不报错）。代价是**治理层数随链路增加而增加**：每多一族，就多一套元数据、多一个需要维护的门禁。

**公开证据**【公开】：主文件 §1.2 把「模型版本失控」与「特征不一致」列为平台要解决的痛点，§2.1 列出模型注册表（版本 / 阶段 / Owner）与特征平台（离线在线一致性）两条治理机制；链路上的四类对象（表 / 指标 / 特征模型 / Prompt 工具记忆），本表沿用该分类并补齐门禁形态。判定方法：问「线上这个模型用的是哪一版特征定义」——答不出，说明治理对象只覆盖到数据层，还没覆盖到特征层。

**失效条件**：当组织里模型数量只有个位数、由同一个团队端到端负责时，跨族门禁是纯负担——靠沟通就能覆盖的风险，不值得再建一套元数据。

#### 7.3.4 数据位置：为什么「算力跟着价格走」通常是错的

**机制是什么**：训练与推理都要读数据。数据的物理位置决定了要不要搬、搬多久、以及能不能搬——而数据位置往往由合规与主权决定，不由成本决定。

**它在各候选中的实现差异**：

| 候选 | 数据在哪 | 是否要先把数据搬到算力侧 | 隐私与合规边界 |
| --- | --- | --- | --- |
| 传统数据平台 / 数据中台 | 数仓内 | 不搬（算在数据上） | 由数仓权限体系承担 |
| Lakehouse | 对象存储上的开放格式 | 不搬（引擎就近读） | 由存储与目录权限承担 |
| AI 计算平台（单集群） | 常需导出到训练集群 | 要搬（或训练直读仓内表） | 训练集群成为新的数据边界 |
| 联邦 / 多云 AI 平台 | 留在各域 | 按「数据在哪」就近调度 | 数据主权逐域遵守 |
| 垂直行业 AI 平台 | 受监管数据域内 | 不搬（域内闭环） | 字段级隔离 + 决策留痕 |

**由此必然导出的性质（因果句）**：因为**跨域搬数据的时间常常超过训练本身**，所以「哪边算力便宜就往哪调度」在数据体量大时会先付出传输与等待，**收益在训练开始之前就已经亏掉了**——数据位置是硬约束，算力是唯一可以搬走的那一部分（§3.2.7）。反过来，因为**把数据导到训练集群意味着训练集群成为一个新的数据边界**，所以「AI in 仓 / 训练直读」这类做法真正的价值不在省一次导出，而在**权限与审计链条没有断点**：数据始终在原有权限体系内被读取，每一次读都可审计。代价是训练算力必须能被挂到仓库上，这会限制你选择算力供应商的自由度。

**公开证据**【公开】：训练直读仓库表、把导出流量与审计链条一起收进仓库权限体系这一形态，见 [§ 6 落地实践](01-ai-compute-section-6-sec6.md) §1.3「阿里 MaxCompute AI 与数据不出仓」案例的组件清单（训练直读、数据零导出、访问全程留在仓库权限体系内）；联邦 / 多云形态见 [§ 3 设计模式与范式](01-ai-compute-section-3-sec3.md) §3.2.7。判定方法：把训练启动的等待时间拆成「排卡 + 搬数据 + 加载」三段量一次——其中「搬数据」这一段就是这条机制在你环境里的价格。

**失效条件**：当数据本来就在算力侧、或数据体量远小于算力价差带来的收益时，「数据不动、算力按价格走」是更优的，此时把算力锁在一个云上反而是损失。

### 7.4 成本结构对比（不是价格表，是成本函数）

各候选的成本函数**形状不同**，这才是选型的核心。写成统一形式：

```
月成本 ≈ 容量成本(卡数 × 单位时间价格 × 时间)
        + 闲置损失(1 − 利用率) × 容量成本          ← 按容量付时才存在
        + 排队的机会成本(任务等待时间 ÷ 迭代周期)   ← 按容量付时的第二项损失
        + 数据搬运(跨域次数 × 数据体积 × 单价)
        + 人力(常驻组件数 × 技能稀缺度)             ← 唯一不随规模下降的一项
        + 合规留痕成本(决策量 × 留痕与复现要求)
```

**先算利用率这一项**【推算】。设卡数不变，把利用率从 20% 提到 50%（这两个端点取自 [§ 3 设计模式与范式](01-ai-compute-section-3-sec3.md) §3.3 补充段的【经验】档：单团队自购 GPU 的闲置率在 50%–80% 区间，即利用率在 20%–50% 区间）：

- 有效算力（卡数 × 利用率）之比 = 0.5 ÷ 0.2 = **2.5 倍**。
- 换成卡数口径是同一件事的另一种说法：要拿到同样的有效算力，利用率到 50% 之后只需原来的 0.2 ÷ 0.5 = **40% 的卡数**（即卡数减少 60%，与上一条的「2.5 倍」互为倒数；同一件事不能一处说「少」、一处说「多」）。

推导链的两端都来自上面写明的两个端点值（20% 与 50%），**2.5 倍是所引闲置率区间之内能拿到的全部空间**——利用率已经高于该区间上界（闲置率低于 50%）时，可压缩的余地随之变小，需要换一条增益路径而不是继续榨利用率。这条推算的意义不在具体倍数，而在于它说明**利用率是乘数项，不是加数项**——它同时作用在你已经付过钱的全部卡上。

**再算迭代速度这一项**【推算】。若把一次完整训练的周期从「两个月」压到「两周」这个量级（周期端点的量级取自 [§ 6 落地实践](01-ai-compute-section-6-sec6.md) 的案例条目，请按其来源核验），一年可做的迭代轮数从 365 ÷ 60 ≈ **6 轮**变成 365 ÷ 14 ≈ **26 轮**。两端都由写明的周期与一年天数推出。**这一项不落在账单上，却决定产品竞争力**：可试次数从 6 到 26 的差别，通常比同样的钱买到更多卡更有价值——这也是「排队的机会成本」必须写进成本函数的原因。

**推理侧的显存账**【推算】：按主文件 §2.2 的 KV 估算，7B 级模型 FP16 下单 token 的 KV 约 0.5 MB（2 × 32 层 × 32 头 × 128 head_dim × 2 字节 = 0.5 MB，推导见 §3.2.2），则 32k 上下文单序列约 0.5 MB × 32768 ≈ **16 GB**；一张 80 GB 卡扣掉 7B 权重（70 亿参数 × 2 字节 ≈ 14 GB）后剩约 66 GB，**长上下文并发上限约 4 个序列**。两端都可从写明的三项前提复算。这解释了为什么推理的成本上限由**显存利用率**决定而不是由算力决定，也解释了分页与连续批处理为何是推理侧的第一优化（§3.2.2）。

**每一项的主导者不同**：

| 候选 | 主导项 | 隐性项 | 调用量翻 10 倍时 |
| --- | --- | --- | --- |
| Serverless AI 平台 | 调用量 | **冷启动**（权重加载是 IO 密集操作） | 线性上涨，且失去议价空间 |
| 自建常驻（独占 / 池化） | 容量 × 时间 | **闲置**与**排队**同时出现 | 账单不变，但排队时间变长 |
| LLM 一体化平台 | 容量 + 域内互连 | **拓扑碎片化**（大任务占满域后，小任务无处安放） | 推理侧显存先见顶 |
| 联邦 / 多云 | 各域容量 + 跨域传输 | **数据分发**（往往比搬算力贵） | 跨域流量先成为瓶颈 |
| 垂直行业 AI 平台 | 容量 + 人力 | **合规连带**（一次规则变更要重训重审一批模型） | 与调用量无关，与模型数相关 |

**唯一不随规模下降的一项是人力**：容量、闲置、搬运都能靠机制压下去（池化、抢占、就近调度），但「常驻组件数 × 技能稀缺度」只随组件数与团队规模增长。**判断方法很简单：把候选方案各自需要常驻维护的组件数列出来**——K8s、调度器、并行框架、推理引擎、配额与审计——乘以团队里能维护它的人，看这个乘积是否超过了你雇他们的理由。开源一体化平台的失效点正在这里（§3.2.6）。

### 7.5 决策树（每个分支都要有阈值依据）

下面的树按**约束**而不是按**需求**分叉：先问「管理对象是哪一层」（决定后面所有问题问给谁听），再问算力下限与时间形态（决定模式），最后问数据位置与合规（决定边界）。**读法**：树上每个判断节点在树后的「阈值依据」里都有一条对应解释，逐条一一对应。

```
[你要建的核心能力属于哪一层？]
   │
   ├── 数据资产层
   │     └── [是「查询与报表 / 指标体系」，还是「多模态与存算分离」？]
   │           ├── 要跨部门统一口径   → 数据中台（口径为中心）+ 传统数据平台
   │           ├── 只在本部门查询报表 → 传统数据平台
   │           └── 多模态 / 存算分离  → Lakehouse（Iceberg / Hudi / Delta）
   │
   ├── 模型与算力层 → AI 计算平台
   │     ├── [单任务能否装进一张卡？]
   │     │     ├── 能 → 传统 ML 平台（多模型共置，天级重训）
   │     │     └── 不能 → LLM 一体化平台（并行拓扑 + 显存分页）
   │     ├── [推理的峰均比是否显著大于 1？]
   │     │     ├── 是 → Serverless AI 平台（按调用付费）
   │     │     └── 否 → 自建常驻 / GPU 算力池化平台
   │     ├── [是否要求单次决策可复现？]
   │     │     ├── 是 → 垂直行业 AI 平台（模型 → 决策 → 留痕）
   │     │     └── 否 → 走上面已选定的模式
   │     └── [团队能否自建配额 / 审计 / 多租户？]
   │           ├── 能 → 开源一体化平台（逐层可替换）
   │           └── 不能 → 商业托管或云服务
   │
   └── Agent 编排层 → AI 智能体平台（消费上面两层的产出）

（以下两问对上述所有分支共用）

[数据能否出内网 / 跨域？]
   ├── 不能出内网 → 算力就近部署；数据域内闭环
   └── 可跨域但受主权限制 → 联邦 / 多云 AI 平台（按「数据在哪」就近调度）

[是否要企业级 AI 全栈？]
   └── 是 → 数据中台 + AI 计算平台 + AI 智能体平台三件套（各自管自己的对象）
```

**阈值依据**（树上每个判断节点在此各有一条，逐条对应）：

- **「你要建的核心能力属于哪一层？」**：依据是 7.1 的「管理对象」判据。这不是规模问题而是职责问题：数据资产层的 KPI 落在「资产可见与口径一致」，模型与算力层落在「迭代速度与单位推理成本」，Agent 层落在「行为可控与可复现」。判定方法：问「这个平台上线后，谁的考核指标会变」——答不出具体岗位，这一层就不该由你建。
- **「是『查询与报表 / 指标体系』，还是『多模态与存算分离』？」**：这一问对应的两条分支各有依据。**查询与报表这一支**的依据是治理对象机制（7.3.3）：数据中台与数据平台的分界不在技术，而在**是否存在跨部门的口径歧义**——只有单个部门用，指标的权威源就是那张表；多部门共用同一个指标名而定义不同时，才需要一个有权裁决口径的中心（这正是数据中台存在的理由）。**多模态与存算分离这一支**的依据是数据存在形态与引擎边界的对应关系：需要 Iceberg / Hudi / Delta 这类开放表格式时，选择的是「schema 与快照由格式持有」这条机制——它让查询引擎可以替换，代价是要接受开放格式的元数据操作特性（清单与小文件的治理成本）。
- **「单任务能否装进一张卡？」**：依据是 7.3.2 的算力下限机制，判据是「单任务算力下限与时间形态」，而不是「模型有多大」这种模糊说法。判定方法：把最大模型的参数量乘以其权重精度字节数，与单卡显存比一次——装不下，就必须走并行路线，此时缺的是域内带宽而非卡数。
- **「推理的峰均比是否显著大于 1？」**：依据是 7.3.1 的算力归属机制。这条线的形式是**比值**而不是绝对 QPS：峰值与均值之比越大，按峰值配置常驻实例浪费得越多，弹性资源的相对优势越明显（§3.3 把「峰值 / 均值比是否显著大于 1」列为该分支的判据，具体倍数应当按自身监控数据核算）。判定方法：取最近两周的 QPS 曲线，算峰值 ÷ 均值这一个数。
- **「是否要求单次决策可复现？」**：依据是治理与留痕判据。这是一条**由外部（监管）给定的约束**，不是可权衡项：一旦要求「一年后仍能复现某一次决策」，就必须走垂直行业 AI 平台那条链（模型 → 决策 → 留痕），事后加插件只能补到访问日志，补不到决策依据（§3.2.5）。
- **「团队能否自建配额 / 审计 / 多租户？」**：依据是开源件的能力边界——开源件默认面向可信用户，配额、多租户、审计与成本分摊需要自建（§3.2.6）。判定方法：数一下团队里能承担 K8s 调度、并行框架、推理引擎三层运维的人有多少；不足，就走托管路线。
- **「数据能否出内网 / 跨域？」**：依据是 7.3.4 的数据位置机制。这一条是**硬约束**：数据主权不是可以用成本去补的项。判定方法：问「训练数据能不能离开这个机房」——不能，算力就必须跟着数据走，跨云联邦这条分支直接出局。
- **「是否要企业级 AI 全栈？」**：依据是 7.2 的分族结论。三件套不是「买三个更保险」，而是三族各管自己的对象：中台管口径、AI 计算平台管模型与算力、智能体平台管 Agent 运行时。**把它们当成可选叠加项，而不是同一件事的三个竞品。**

**上树之前先做的三项验证**（都比选型更重要）：

1. **量一次利用率**：把当前 GPU 的有效使用时长除以持有时间（对应 7.4 的第一条推算）——它决定池化是否有账可算。
2. **量一次训练启动的等待时间，并拆成「排卡 + 搬数据 + 加载」三段**：其中「搬数据」那一段决定数据位置是不是你的真瓶颈（对应 7.3.4）。
3. **量一次推理 QPS 的峰值除以均值**：这一个比值决定自建常驻与弹性的分界（对应 7.5 的峰均比分叉）。

这三项里任意一项算完发现结论与你的直觉相反，都应该先按数字走，而不是先按产品功能清单选型。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| BI / 指标体系 / Ad-hoc，跨部门口径要统一 | 数据中台 + 传统数据平台 | 只用传统数据平台 | 没有有权裁决口径的中心时，同名指标会在各域各算一遍 |
| 单部门查询与报表，无口径争议 | 传统数据平台 | 数据中台 | 中台的固定成本（口径治理 + 组织协调）在这个范围收不回来 |
| 多模态数据、要求引擎可替换 | Lakehouse（Iceberg / Hudi / Delta） | 单一引擎的内置存储 | 内置格式把 schema 权威源钉在该引擎上，换引擎要重做一遍 |
| 推荐 / 风控，模型小、天级迭代 | 传统 ML 平台 | LLM 一体化平台 | 大模型的并行与显存基建在这类负载上是纯开销 |
| 通用 / 行业大模型训练与推理 | LLM 一体化平台 | 传统 ML 平台 | 单任务装不进一张卡时，共置调度假设直接失效 |
| 创业 / PoC / 中小规模推理 | Serverless AI 平台 | 自建常驻实例 | 调用稀疏时，常驻实例大部分时间在计费却不产出 |
| 超大规模训练、训练与推理混部 | GPU 算力池化平台 | 两套独立集群 | 独立集群会让训练与推理各按峰值配置，双侧都闲置 |
| 金融 / 医疗 / 政务，要求决策可复现 | 垂直行业 AI 平台 | 通用平台 + 事后补审计 | 留痕与解释必须内建在「模型 → 决策」链路上，事后补不到 |
| 无采购预算、数据不出内网、团队能运维 | 开源一体化平台 | 商业托管 | 数据出域与深度定制受限；但开源件要自补配额与审计 |
| 多地多云、数据主权与容灾要求 | 联邦 / 多云 AI 平台 | 单云多可用区 | 只有可用性要求时，单云多区更简单也更便宜 |
| Agent 应用（多工具、多轮） | AI 智能体平台 | 在 AI 计算平台上自建编排 | 编排、记忆、工具准入是另一类治理对象，自建等于重做一遍 |

**常见组合**（共 6 条）：

1. **AI 计算平台 + 数据中台**：构成——中台消费原始数据产出指标 / 标签 / 特征，AI 计算平台消费这些产出物训练与推理。职责边界——中台只对**口径**负责，AI 平台只对**模型与算力**负责，两者不互相持有对方的元数据。运维代价——特征口径变更要沿这条边界通知到模型侧，否则会出现「线上模型用的是上一版特征」这类不报错的故障。【经验】
2. **AI 计算平台 + Lakehouse**：构成——Lakehouse 提供多模态数据底座（结构化 + 非结构化），AI 计算平台就近读取训练 / 推理。职责边界——存储与 schema 的权威源在表格式一侧，平台不复制数据。运维代价——小文件与元数据的治理落在存储侧，训练任务的读放大问题要在这里解决，而不是靠加卡。【经验】
3. **AI 计算平台 + AI 智能体平台**：构成——计算平台提供模型、推理端点与工具执行能力，智能体平台在其上构建 LLM + 工具 + 记忆 + 规划。职责边界——计算平台管「模型怎么跑得好」，智能体平台管「Agent 怎么调得对」；Prompt 与工具清单归后者治理。运维代价——两层各有一套版本，Agent 行为不可复现时要能同时回查模型版本与 Prompt 版本。【经验】
4. **AI 计算平台 + 国产 NPU 适配**：构成——NVIDIA GPU 做主力算力，华为昇腾 / 寒武纪 / 燧原等在信创与等保要求下作为替代算力；适配层在算子层屏蔽硬件差异（§ 6 案例的算子适配层形态）。职责边界——适配层负责算子映射、精度对齐与性能调优，上层模型不做硬件分支。运维代价——两套后端的算子覆盖与精度一致性要长期维护，缺失算子需要组合实现或用别的路线绕过，具体硬件的支持范围请以各厂商官方文档当前版本为准。【经验】
5. **AI 计算平台 + Serverless AI**：构成——Serverless 承担 PoC、中小规模推理与突发流量，自建平台承担大规模训练与核心推理。职责边界——按**实例是否会长期驻留**划界：会驻留的放自建，不驻留的放 Serverless。运维代价——两侧各有一次冷启动或扩容的延迟特征，路由规则要写清楚，否则同一个业务会出现两种延迟表现。【经验】
6. **传统数据平台 + AI 计算平台（结果回流）**：构成——AI 平台产出的打分与预测回流到数据平台，与业务数据一起做分析与报表。职责边界——AI 平台是**生产方**，数据平台是**消费与再加工方**；回流表要继承与原表一致的权限与血缘，否则模型产出会成为治理盲区。运维代价——回流链路需要 SLA 与新鲜度约定，因为下游报表会依赖它；回流的每一列都要能回答「由哪版模型生成」。【经验】

> 组合的第一原则是**让每一件管它机制上最适合管的对象**：口径归中台，算力与模型归 AI 计算平台，Agent 运行时归智能体平台，存储形态归 Lakehouse。第二原则是**组合数不超过团队的运维带宽**——上面 6 条组合里，每多一件就多一套版本、多一处新鲜度告警、多一个「两套系统对同一个问题给出不同答案」的战场。

### 7.7 选错的代价与迁移成本

**反模式：把 AI 计算平台当成「买卡 + 装框架」** —— 症状：采购完成、K8s 与训练框架就位，但没有资源池与调度策略，各团队继续独占卡。后果：利用率停在低位而**成本按容量照付**（租的卡不会因为闲置而降价），同时「训练-上线鸿沟」还在——环境不可复现、模型上线要重写一遍推理服务（主文件 §1.2 痛点清单里的「AI 烟囱」与「训练-上线鸿沟」会原样出现）。正确的做法：把**资源池化 + 抢占式调度 + 检查点自动恢复 + 一键发布推理**这四件放在第一批交付里，先要利用率与链路闭环，再谈算法能力。

**反模式：按峰值配置常驻实例来做突发推理** —— 症状：为了让尖峰不掉链子，按峰值买卡或包年租足。后果：均值时段大量闲置，而闲置在按容量付费的模式下是纯亏；反过来若为 PoC 自建常驻实例，同样一笔钱花在只用了很少一段时间的能力上。正确的做法：**先量峰均比**，把它当作唯一判据决定自建与弹性（7.5 的对应分支）；两侧可以并存，但路由规则要写明——**按「实例是否长期驻留」划界，而不是按业务名字划界**。

**反模式：先上线模型，再补可解释与留痕** —— 症状：业务效果不错，平台快速铺开；合规与监管要求「解释这一次为什么拒绝」时才开始补。后果：**留痕必须内建在「模型 → 决策」这条链路上**——事后加插件只能补到访问日志，补不到当时的特征取值与模型版本，于是在需要举证的场合只能重建，而重建出来的不是当时那次决策（§3.2.5）。正确的做法：从第一个进生产的模型起，就把「模型版本 + 输入快照 + 特征贡献」三者一起落盘。

**反模式：用同一套治理层管数据与模型** —— 症状：把模型发布塞进血缘系统的变更门禁，或把表结构门禁当成模型上线门禁。后果：漏掉「换了模型版本但血缘看不出来」这类隐形变更——下游表的语义已经变了却不报错（《LLM in SQL》的 [§ 6 Databricks 案例](../../06-multi-model/02-llm-in-sql/02-llm-in-sql-section-6-sec6.md) 把「换模型是隐形变更」列为独立痛点）。正确的做法：让**模型 / endpoint 成为血缘中的一类节点**，使「换模型会不会影响下游」与「改字段会不会影响下游」是同一类可查询的问题。

| 迁移方向 | 数据侧改动 | 查询 / 推理侧改动 | 运维重建 | 团队再学习 | 量级（【经验】） |
| --- | --- | --- | --- | --- | --- |
| 独占 → 池化共享 | 无需搬迁 | 无需改写 | 新建调度策略、抢占与检查点机制 | 高（Gang / 拓扑 / 抢占语义） | 季级 |
| 自建常驻 → Serverless | 数据留在原地 | 调用从常驻端点改为弹性端点 | 需维护冷启动与权重缓存策略 | 中 | 月级 |
| Serverless → 自建常驻 | 无需搬迁 | 端点切换 | 需自建容量规划、限流与灰度 | 中到高 | 月级 |
| 传统 ML 平台 → LLM 一体化 | 特征与样本继续复用 | 推理侧从常规服务改成连续批处理 + 显存管理 | 新建并行训练与推理引擎的运维面 | 高 | 季级 |
| 单集群 → 联邦 / 多云 | 数据留在各域，需明确主权边界 | 作业描述改成与集群无关 | 统一身份、镜像分发与跨云日志 | 高（从改代码变成谈权责） | 季级 |
| 通用平台 → 垂直行业平台 | 受监管数据域要字段级隔离 | 决策输出要带解释与留痕 | 新增审计链路与复现能力 | 高 | 季级 |
| 数据平台 → 叠加 AI 计算平台 | 需划定特征产出的权威源 | 新增训练与推理入口，原查询不变 | 新增 GPU 池与模型注册 | 中 | 月级到季级 |

> 注意「单集群 → 联邦 / 多云」这一行与直觉相反：它看起来是「多买几家更保险」，实际的迁移动作是**把作业从集群里解耦出来**，代价是接受数据分发成为新的瓶颈。**这类迁移的主要工作量从来不在搬算力，而在重新划定「数据在哪、谁有权动它」。**

### 7.8 小结

AI 计算平台选型的特殊性在于：**它选的是「每一层各自管什么对象」，而不是「哪个平台功能更全」**。数据资产族、模型与算力族、Agent 编排族不是三个竞品，而是同一条链上的三个环节；真正需要先定的是这条链上的**权威源放在哪一层**。而在模型与算力族内部，所有模式差异可以收到两条机制上——**算力归属的粒度**（独占 / 池化共享 / 按秒租用 / 跨云联合）决定成本曲线的形状与闲置和排队的分布，**任务时间形态与单任务算力下限**决定哪些负载能共处一池、需要什么调度能力。

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 跨部门同名指标口径不一致 | 数据中台 + 传统数据平台 | 需要有权裁决口径的中心；技术选型解决不了权责问题 |
| 多模态、要求引擎可替换 | Lakehouse（Iceberg / Hudi / Delta） | schema 权威源由开放表格式持有，引擎可换 |
| 模型小、天级重训、模型数量多 | 传统 ML 平台 | 模型可共置，同一张卡背多个模型，成本随共置数摊薄 |
| 模型装不进一张卡 | LLM 一体化平台 | 超过单卡显存后缺的是域内带宽，不是卡数 |
| 推理峰均比显著大于 1 | Serverless AI 平台（与自建并用） | 按容量付时闲置即纯亏，按调用付把闲置移出账单 |
| 训练与推理混部、卡数规模大 | GPU 算力池化平台 | 有效算力 = 卡数 × 利用率，增益落在乘数上 |
| 要求单次决策可复现 | 垂直行业 AI 平台 | 留痕必须内建在决策链路上，事后补不到 |
| 团队能运维、数据不出内网 | 开源一体化平台 | 逐层可替换；但配额 / 审计 / 多租户要自建 |
| 多地多云、有数据主权要求 | 联邦 / 多云 AI 平台 | 作业与集群解耦，按「数据在哪」就近调度 |
| 面向业务方交付 Agent 应用 | AI 智能体平台（消费上面两层） | 治理对象是 Prompt / 工具 / 记忆，与前两层不同 |

> 本节小结：本章所有候选之间，**唯一真正起决定作用的差异是「每一层各自管理的对象是什么」**——它决定了平台的元数据模型、门禁设在哪个动作上、以及谁的考核指标会因此改变；而在模型与算力层内部，第二决定性的差异是**算力归属的粒度**，因为只有它同时决定了成本曲线的形状（按容量付还是按用量付）与两类负载能否共处一池。其余维度（功能清单、生态丰富度、工具成熟度）都是在确定了这两件事之后才需要精算的第二层问题。
