## 3. 设计模式与范式

> 原 § 3 共 88 行：7 个模式各 4–5 行条目 + 一张 7 行场景决策表 + 10 条反模式，没有结构示意、机制解释与失效点分析。本文件重写为 301 行的模式手册，7 个模式名与 10 条反模式名全部保留并逐条补齐机制与失效条件。

### 3.1 先看约束：模式不是选择题，是约束的产物

AI 计算平台的七个模式看起来是「传统 ML / LLM 一体化 / Serverless / GPU 池化 / 垂直行业 / 开源一体化 / 联邦多云」的并列选项，好像按公司规模挑一个就行。但真实的选型是被**约束**推着走的：同样是「推理」，在「QPS 稳定、模型版本一周一变」与「流量尖峰是均值的十倍、每天上百个模型版本进出」两种约束下，正确模式完全不同——前者自建常驻实例更便宜，后者只能靠 Serverless，因为闲置成本在后者身上无法被摊薄。

七个模式的分歧，主要由**两条机制**决定：**算力归谁拥有与调度**（独占池 / 池化共享 / 按秒租用 / 跨云联合），以及**任务的时间形态**（训练是长时不可抢占的整卡任务，推理是短时突发的可碎片任务）。这两条机制与下表的**六条约束**不是并列关系：任务时间形态本身就是六条约束中的第一条，算力归属则是各模式对全部六条约束的**回答方式**。两条机制定下来，成本曲线、隔离性、排队行为、运维面全都跟着定；**但机制一取同一值的那四个模式（传统 ML、LLM 一体化、垂直行业、开源一体化）算力归属都落在「独占池」，要靠合规与可解释要求、数据位置、团队技能等约束才能进一步分开**（见本节末段）。

所以本节的组织方式是：先立六条约束（下表），再让每个模式自报被哪条约束逼出来，最后用「失效点」说明这条约束一旦改变，模式如何反转成负担。**AI 平台的模式选择比数据平台更硬**：因为算力是资本开支而非带宽费用，选错的代价会以「闲置」或「排队」两种形式长期挂在账上。

还要提醒一点：这七个模式不是互斥的选项，而是**同样两条机制上的不同取值**。机制一（算力归属）只取四个值——独占池 / 池化共享 / 按秒租用 / 跨云联合，其中三个模式正是靠它彼此分开的（Serverless = 按秒租用、GPU 池化 = 池化共享、联邦多云 = 跨云联合）；另外四个模式（传统 ML、LLM 一体化、垂直行业、开源一体化）的算力归属都落在「自有」，所以**只看算力归属（成本结构）区分不开这七个模式**。剩下四个模式的差别靠其余约束来分——软件栈不是与算力归属并列的第二条机制，而是各模式在机制一之上叠的**实现选择**，由机制二（时间形态）与算力下限这类约束推出来：算力归属决定成本曲线，软件栈决定功能与合规边界，二者不是两条并列的轴。传统 ML 用通用 ML 栈，是因为它的负载是「小模型、天级迭代」；LLM 一体化用 LLM 专用栈，是因为它的负载是「参数超单卡、长时训练」；同一份算力归属之上可以叠不同的栈（自建池化集群既跑传统 ML 也跑 LLM 一体化）。也正因如此，这一对的分界不能表述成「栈不同」：按 §3.2.1 的判据，它们的区别是「单模型能否装进一张卡、单次推理是否为短任务」，即单任务算力下限与任务时间形态。垂直行业（行业合规栈）与开源一体化（可替换的开源栈）同理，差别落在合规与可解释要求、数据位置与团队技能这几条约束上，不在栈本身。团队常犯的错误是先选模式再找约束，于是把一个「池化共享」的架构套到「流量每周翻倍」的业务上，然后靠扩容掩盖成本结构的不匹配。正确的顺序是反过来的：先把任务的时间形态、算力下限、数据位置这几条约束写清楚，模式是它们的推论。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 任务时间形态（长时独占 / 短时突发） | 训练任务不可抢占、推理任务可碎片——决定能不能共享同一批卡 | 「池化就能提高利用率」：训练任务占满整域时，池里没有可切的空闲资源 |
| 单任务算力下限（单卡 / 多卡 / 整域） | 模型能否装进单卡显存——决定要不要并行、要不要拓扑感知调度 | 「有卡就能训」：参数超过单卡显存后，缺的是 NVLink 域内带宽而不是卡数 |
| 流量稳定性（平稳 / 尖峰） | 常驻资源 vs 弹性资源的成本分界——决定自建与 Serverless 的交叉点 | 「Serverless 永远更省」：调用密度高到实例长期不缩容时，单价里含平台加价 |
| 合规与可解释要求 | 是否要「模型 → 决策 → 留痕」全链可复现——决定平台迭代速度 | 「先上线再补审计」：合规是横向约束，平台越大，一次规则变更的连带面越大 |
| 数据位置与主权 | 数据能不能跨域、能不能出内网——决定算力能否集中 | 「算力跟着价格走」：跨域搬数据的时间常常超过训练本身，数据位置才是硬约束 |
| 团队技能与运维能力 | K8s / 调度器 / 并行框架 / 推理引擎四层的运维面能否被承担 | 「开源拼起来就是平台」：开源件默认面向可信用户，配额与审计要自己补 |

### 3.2 模式逐个拆解（核心节）

以下 7 个模式，每个都给出结构示意，并回答「被什么逼出来 / 为什么有效 / 代价 / 失效点 / 真实使用」；每个模式末尾另附一条「最容易与谁混」的辨析。读的时候请把每个模式的「失效点」当作它真正的边界——**能说清边界，才算真的理解这个模式**。

#### 3.2.1 传统 ML 平台（Classical MLOps）

- **被什么约束逼出来**：负载以结构化特征 + 树模型 / 中小模型为主（推荐排序、风控评分），单次推理算力需求低、迭代以天计。
- **结构**：特征平台 → 训练作业（队列 + 实验追踪）→ 模型注册（版本 + 阶段）→ 多模型共置的推理服务。
- **为什么这样设计有效**：因为单个模型小、可被共置，所以同一张卡能同时背多个模型的流量，单位推理成本随共置数量下降——收益来自复用既有算力，而不是来自买更强的卡。

```text
传统 ML 平台：模型小、可共置，收益来自复用同一份算力
  特征平台 ──► 训练作业（队列 + 实验追踪）──► 模型注册（版本 / 阶段 / Owner）
                    │                                  │
                    └── 重训（天级，CPU / 小规模 GPU）   ▼
                                            推理服务（多模型共置同一张卡）
                                              ├─ 路由：按 model_id 分发请求
                                              └─ 隔离：按内存 / 线程配额切分
  → 共置的模型越多，分摊到每个模型的算力成本越低
```

- **代价**：强依赖特征平台，特征不一致会直接毁掉效果，而这类问题不会以「报错」形式暴露；模型数量增长后，注册表、监控阈值、上线流程的维护面按模型数线性增长。
- **失效点**：当业务要求小时级重训、或模型换成需要多卡并行的十亿参数级模型时，「共置小模型」的优点反转成「调度假设失效」——因为共置调度按「任务可被抢占、可碎片」设计，而大模型训练不可抢占（每次抢占都要回滚到检查点）。
- **真实使用**：Uber Michelangelo 的平台架构由 Uber 工程博客于 2017 年 9 月公开，Google TFX 于 2017 年开源，二者是这一模式的公开代表【公开：Uber Engineering Blog「Meet Michelangelo: Uber's Machine Learning Platform」（2017-09）；TFX 官方仓库（github.com/tensorflow/tfx）与发布记录，可按仓库名自行检索核验】；Databricks 的 MLflow 于 2018 年 6 月开源，承担同一模式里的实验追踪与模型注册【公开：MLflow 官方仓库（github.com/mlflow/mlflow）首发版本号与日期，可自行核验】；推荐与风控是主要落点【经验】。
- **最容易与谁混**：与 LLM 一体化平台混。判据是「单模型能否装进一张卡、单次推理是否为短任务」，两者皆然时，LLM 平台的并行与 KV 基建全是净开销。

#### 3.2.2 LLM 一体化平台（LLMOps / Foundation Model Platform）

- **被什么约束逼出来**：单模型参数量超过单卡显存，训练必须多卡并行；推理同时要满足高 QPS 与低 token 成本。
- **结构**：训练侧 = 并行策略（TP 组内 / PP 跨节点 / DP + ZeRO 分片）+ 检查点；推理侧 = 专用引擎（KV 分页 + 连续批处理）+ 评估体系。
- **为什么这样设计有效**：因为 KV Cache 被分页管理，显存按块分配而不是按最长序列预留，同一张卡能并发更多序列，吞吐随并发数上升；代价是调度器必须维护块表与抢占逻辑，并承担显存碎片治理。

```text
LLM 一体化：训练靠并行拓扑，推理靠显存分页
  训练：TP 组（同 NVLink 域内） + PP（跨节点） + DP / ZeRO（分片优化器状态）
        └─ 检查点 → 对象存储（断点续训 / 故障恢复）
  推理：请求 ──► 调度器（continuous batching）
                ├─ KV Cache 分页（PagedAttention）：按块分配，不按最长序列预留
                └─ 并发序列数 ↑ → 单位 token 分摊的显存成本 ↓
  ── 结论：训练的性能上限由通信拓扑决定，推理的成本上限由显存利用率决定
```

- **代价**：通信成为训练的第一成本，TP 的 AllReduce 必须落在 NVLink / NVSwitch 域内，于是「哪些卡能组成一个任务」被物理拓扑锁死，集群资源随之碎片化、排队变长；推理侧的显存预算还有一项与上下文长度成正比的开销——按 `2 × 层数 × 头数 × head_dim × 字节数` 估算，7B 级模型 FP16 下单 token 的 KV 约占 0.5 MB，32k 上下文的理论 KV 占用约 16 GB【推算：2(K/V) × 32 层 × 32 头 × 128 head_dim × 2 字节 = 0.5 MB/token；0.5 MB × 32768 ≈ 16 GB，与本章 §2.2 的估算一致】。
- **失效点**：当推理请求从「长上下文、批量稳定」变成「短请求、突发、长尾」时，分页与连续批处理的收益下降——因为分页收益来自并发序列共享显存块，而突发短请求很难凑出稳定的批。
- **真实使用**：vLLM 的 PagedAttention 是这一路线的公开技术起点【公开：Kwon 等，SOSP 2023】；DeepSpeed ZeRO 的分片优化器状态是长时训练侧的公开基石【公开：Rajbhandari 等，SC 2020】；TensorRT-LLM、TGI、SGLang 同属 LLM 专用推理引擎家族【公开：三家官方仓库（NVIDIA/TensorRT-LLM、huggingface/text-generation-inference、sgl-project/sglang）；三者迭代频繁，本书不锚定具体版本号，首个 release 的版本与日期请以各仓库 Releases 页当前记录为准，可按仓库名自行检索核验】。
- **最容易与谁混**：与「GPU 算力池化」混。池化解决的是「卡怎么分给多个任务」，LLM 平台解决的是「一个任务如何跨多卡跑起来」，前者管供给粒度，后者管单任务拓扑。

#### 3.2.3 Serverless AI 平台

- **被什么约束逼出来**：需求不可预测、突发、PoC 阶段；团队无力承担常驻 GPU 的固定成本，也无力承担运维。
- **结构**：请求触发实例创建 → 加载镜像与权重 → 推理 → 释放；按秒计费，平台侧用分层缓存摊薄冷启动。
- **为什么这样设计有效**：因为闲置期间不占卡，成本随调用量近似线性化，试错期的现金流压力最小；代价是延迟里多了一项冷启动，而冷启动的主要成分是权重加载这一 IO 密集操作。

```text
Serverless AI：成本随调用走，延迟里有一项冷启动
  调用到达 ──► [冷启动] 拉镜像 → 加载权重（IO 密集）──► 推理 ──► 释放实例
                  │                                        │
                  └─ 权重分层 / 常驻缓存可摊薄冷启动        └─ 计费：按秒 × 实例数
  ── 成本曲线是一条直线；自建常驻实例的成本曲线是折旧（近似水平线）
  ── 两条线有一个交叉点：调用密度低于交叉点 → Serverless 省
```

- **代价**：冷启动延迟随模型体积增长，权重加载在十秒到分钟量级之间波动【经验】；平台对并发数、单次运行时长、显存规模设有上限，长时间驻留型优化（如跨请求复用 KV）难以实施；单实例内无法做深度定制（自定义算子、特殊拓扑）。
- **失效点**：当调用密度升高、实例长期不缩容时，「按调用付费」的优点反转成「单价高于自建」——因为按秒计费里含着平台加价，而自建的成本是硬件折旧，两条曲线在交叉点之后反转。
- **真实使用**：Modal、Replicate、AWS Lambda + SageMaker、阿里云 PAI EAS Serverless 都在这一模式上提供产品【公开：四家的官方文档页——Modal 的 GPU 与计费文档、Replicate 的硬件与计费文档、AWS 的「Serverless Inference」与 SageMaker 推理文档、阿里云 PAI EAS 的产品与计费文档；这类产品文档随版本迭代、不落固定发布年份，价格、并发上限与计时粒度一律以官方文档当前版本为准，可按「产品名 + serverless 推理 / 计费」自行检索核验】。
- **最容易与谁混**：与「自有池化」混。判据不是延迟而是「实例是否长期驻留」——长期驻留意味着按秒单价会超过折旧摊销，此时 Serverless 只剩弹性价值。

#### 3.2.4 GPU 算力池化平台

- **被什么约束逼出来**：同一批硬件要同时服务「整卡 / 整域的训练任务」和「碎片化的推理任务」，而两类任务的时间形态相反。
- **结构**：池化层用 MIG 硬切、时间片软切、共享调度把一张卡切成不同粒度；调度器叠加 Gang Scheduling（N 卡同时启动）与拓扑感知（TP 组放进同一 NVLink 域）。
- **为什么这样设计有效**：因为推理被切到 MIG 实例或时间片、训练仍能拿到整卡，所以两类负载可以共处一池，训练任务的空隙被推理填上——利用率从「按训练峰值配置」变成「按训练 + 推理的组合」配置。

```text
GPU 算力池化：一张物理卡切成不同粒度的"供给"
  物理 GPU（节点内 8 卡，NVLink / NVSwitch 域）
    ├─ MIG 实例（硬切：独立显存 + 独立算力）   → 小模型推理 / 开发调试
    ├─ 时间片共享（软切：轮转共享算力）        → 突发推理
    └─ 整卡 / 整域（不切）                     → 训练（Gang：N 卡必须同时起）
  调度器 = 队列 + 拓扑感知 + 抢占策略
  ── 池化的前提：池里存在"不属于任何长期任务"的空闲资源
  ── 池化的代价：共享粒度的隔离性弱于独占（尾延迟不可预测）
```

- **代价**：共享粒度引入尾延迟不确定性（时间和显存被邻居影响）；Gang + 拓扑 + 抢占的组合让调度状态空间变大，运维需要专人；MIG 的切分规格受硬件型号限制，不是任意切。
- **失效点**：当单个训练任务大到「整域才放得下」时，池化的共享假设被推翻——池里没有可切给推理的空闲资源，此时池化只剩下调度开销，优点（利用率）消失。
- **真实使用**：NVIDIA 的 MIG 把 A100 起的 GPU 做成可硬件切分的实例【公开：NVIDIA「Multi-Instance GPU (MIG)」官方文档，A100 于 2020 年发布、MIG 随该代产品引入，可按文档名与产品代次自行检索核验】；Volcano 为 K8s 补上 Gang Scheduling 等批调度能力【公开：Volcano 官方仓库（volcano-sh/volcano）与 CNCF 项目页上的收录记录，开源年份与沙箱 / 孵化阶段以该页当前记载为准，可按项目名自行检索核验】；CoreWeave 与 Lambda Labs 把池化的 GPU 按实例对外提供【公开：两家厂商官网的 GPU Cloud 产品页（页内给出实例规格与计费）；产品文档随版本迭代、不落固定发布年份，规格与价格以官方文档当前版本为准】；火山引擎机器学习平台是同一形态在国内的对应产品（字节的 GPU 池化对外产品化）【经验：模式归属为本书归类，产品形态以其官方文档当前版本为准】。
- **最容易与谁混**：与「多模型共置」混。共置是应用层把多个模型放进同一个进程 / 同一张卡（传统 ML 平台的做法），池化是平台层把物理卡切成不同粒度的供给，二者可以叠加但不在同一层。

#### 3.2.5 垂直行业 AI 平台

- **被什么约束逼出来**：金融 / 医疗 / 政务等行业里，合规（数据分级、模型可解释、决策可审计）与行业口径（标签定义、指标语义）比通用算法能力更关键。
- **结构**：受监管数据域（字段级隔离）→ 行业特征 / 标签 → 带版本的模型 → 带解释的决策输出 → 审计留痕。
- **为什么这样设计有效**：因为「模型 → 决策 → 留痕」被绑成一条链，所以事后可以还原单次决策用了哪版模型、哪版特征、依据哪条规则；合规审查从「翻文档」变成「查记录」。

```text
垂直行业 AI 平台：把"模型 → 决策 → 留痕"绑成一条链
  受监管数据域（字段级隔离 + 脱敏 + 最小必要）
        │
  行业特征 / 标签（口径经合规确认，变更需评审）
        │
  模型（版本 + 训练数据快照 + 评估报告）
        │
  决策输出（含解释：哪些特征贡献了多少）
        │
  审计留痕：谁 / 何时 / 用哪版模型 / 对哪个客户 / 依据哪版特征
  ── 目标：一年后仍能复现"这一单当时是怎么判的"
```

- **代价**：平台迭代被合规流程拖慢（模型上线要走评审、特征变更要口径确认）；行业模型与特征不可跨行业迁移，复制成本高；解释性输出往往要求模型结构受限（可解释性换效果）。
- **失效点**：当行业规则或口径发生变更（例如某类特征被禁止使用）时，「可审计」的优点反转成「横向连带」的缺点——合规约束作用在平台上所有模型上，平台越大，一次规则变更需要重训与重审的模型越多。
- **真实使用**：行业头部企业以自建平台为主流选择，被公开点名的形态代表有蚂蚁金融大脑、平安 AI 平台、医联智云——它们把行业口径、决策留痕与合规评审内建在平台上，而不是作为外挂【经验：三家平台的公开产品描述可按名称检索核验；其内部链路细节本书未逐一核实，金融风控与医疗影像类平台普遍采用这一形态亦为经验判断】。
- **最容易与谁混**：与「通用平台 + 合规插件」混。留痕与解释必须内建在「模型 → 决策」这条链路上，事后加插件只能补到访问日志，补不到单次决策的依据。

#### 3.2.6 开源一体化平台

- **被什么约束逼出来**：无外部采购预算、数据不能出内网、需要深度定制；团队有能力承担运维成本。
- **结构**：K8s + 调度、流水线、实验追踪与模型注册、推理服务、对象存储与元数据库，逐层用开源件拼装。
- **为什么这样设计有效**：因为每一环都是可替换组件而不是一体产品，所以能按内网与合规约束替换任何一层；代价是「最后一公里」——配额、多租户、审计、成本分摊——都要自己补。

```text
开源一体化：每一环都可替换，最后一公里要自己补
  调度：Kubernetes（+ KubeRay / Volcano 做分布式训练与批调度）
  流水线：Kubeflow Pipelines / Metaflow / Ray
  追踪与注册：MLflow（实验追踪 + 模型注册）
  服务：KServe / BentoML / Triton
  存储：对象存储 + 元数据库（元数据与实验记录的落点）
  ── 开源件默认面向"可信用户"：RBAC / 配额 / 审计 / 成本分摊需自建
  ── 版本兼容矩阵是这类平台最大的隐性运维成本
```

- **代价**：集成与升级成本高（各组件版本兼容矩阵要自己维护）；企业级特性缺失，意味着平台团队的一半工作量花在非算法功能上；社区支持以「文档 + issue」形式存在，关键故障的响应时间不可控。
- **失效点**：当平台用户规模超过「能靠沟通协调」的程度时，「自主可控」的优点反转成「事故源」——因为开源件默认可信用户假设，而组织一大，用户就不再可信，缺失的配额与审计会以越权与资源抢占的形式暴露。
- **真实使用**：Kubeflow、MLflow、Metaflow、Ray / Anyscale 是这一路线的公开代表，四者于 2017–2019 年陆续开源，到 1.0 级成熟普遍在 2020 年前后【公开：Kubeflow（2017 年底公布，1.0 于 2020）、Ray（2017 年开源）、MLflow（2018 年 6 月开源）、Metaflow（2019 年开源）各自的官方仓库与发布记录，可按项目名自行检索核验】。
- **最容易与谁混**：与「自研一体平台」混。开源路线的特征是每一层都能被替换（可内网化、可换国产件），自研路线的替换点在自有代码里，二者的成本结构完全不同。

#### 3.2.7 联邦 / 多云 AI 平台

- **被什么约束逼出来**：避免单一供应商锁定、跨地域容灾、数据主权（某些数据只能留在本地域）。
- **结构**：统一层承担「与集群无关的作业描述 + 镜像与数据分发 + 统一身份与配额」，下层是各地域 / 各云的独立集群。
- **为什么这样设计有效**：因为作业被抽象成与集群无关的描述，同一训练作业可以提交到任一地域，容灾与议价能力同时获得；代价是数据分发成为新的瓶颈——跨域搬数据往往比搬算力贵。

```text
联邦 / 多云：作业与集群解耦，数据位置才是硬约束
  统一层：作业描述（与集群无关） + 镜像仓库 + 统一身份 / 配额 / 成本归集
                │
     ┌──────────┼──────────┐
     ▼          ▼          ▼
  地域 A 集群  地域 B 集群  云厂商 C 集群
  （数据留在本地域；作业按"数据在哪"就近调度）
  ── 反例：若按"哪便宜往哪调度"，先付的是跨域传输与出口费用
```

- **代价**：跨云网络与出口费用、数据分发与一致性、两套以上调度与 K8s 的运维面、身份与配额要跨云统一；故障排查要跨云追日志与指标。
- **失效点**：当训练数据集体量大于算力价差带来的收益时，「避免锁定与容灾」的优点被传输成本吃掉——因为数据位置才是硬约束，算力只是可搬走的那一部分。
- **真实使用**：Anyscale 的多云 Ray 与 AWS SageMaker + Outposts 都属这一形态【公开：Anyscale Docs 的「Ray on Anyscale」页与 AWS Outposts 官方文档；产品文档随版本迭代、不落固定发布年份，能力边界以官方文档当前版本为准，可按页标题自行检索核验】；阿里云 PAI + 灵骏（灵骏的裸金属算力底座为阿里云神龙架构）也是国内的同形态组合【经验：三者的组合关系为本书归纳，具体能力以其官方文档当前版本为准】。
- **最容易与谁混**：与「单集群多可用区容灾」混。联邦的判据是数据主权与供应商锁定，只有可用性要求时，单云多区更简单也更便宜。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 推荐 / 风控 / 反欺诈 / 智能营销，模型天级更新 | 传统 ML 平台 | LLM 一体化平台的通信与显存开销在这类负载上无收益 | 单次推理能否装进一张卡的碎片？ |
| 通用 LLM / 行业 LLM / Agent | LLM 一体化平台 | 传统平台缺少并行训练与 KV 管理，跑不动大模型 | 参数量是否超过单卡显存？ |
| 创业团队 / PoC / 中小规模推理 | Serverless AI | 自建常驻 GPU 在调用密度低时大部分时间在计费却不产出 | 实例是否会长期不缩容？ |
| 超大规模训练（千卡以上、单一任务跨多节点） | GPU 算力池化 | 不池化会让闲置与排队同时存在；但须先保证拓扑感知调度 | TP 组能否落在同一 NVLink / NVSwitch 域？ |
| 金融 / 医疗 / 政务 | 垂直行业 AI 平台 | 通用平台无法提供决策级留痕与解释 | 一年后能否复现某一次决策？ |
| 技术团队强、自研投入大、数据不出内网 | 开源一体化平台 | 商业平台在数据出域与深度定制上受限 | 团队能否承担配额 / 审计 / 多租户的自建？ |
| 大型跨国企业、多地多云 | 联邦 / 多云平台 | 单云部署无法同时满足数据主权与容灾 | 数据能否跨域迁移？ |
| 推理流量呈强尖峰、模型版本频繁进出 | Serverless AI + 缓存 | 常驻实例按峰值配置会长期闲置 | 峰值 / 均值比是否显著大于 1？【经验：尖峰型业务的峰均比常在数倍以上，具体倍数请按自身监控数据核算】 |
| 训练与推理混部、白天推理多夜间训练多 | GPU 算力池化 + 抢占策略 | 独立集群会使两侧都按峰值配置 | 训练任务能否容忍被抢占（检查点成本）？ |
| 模型数量多、单个模型小 | 传统 ML 平台 + 多模型共置 | 一模型一实例会把碎片算力浪费掉 | 单模型显存占用是否远小于单卡？ |

表后补充：**最常被误选的一对是「自建常驻实例」与「Serverless」**。误选方向的后果不同但都可量化：错选 Serverless 用于稳定高密度推理，账单会随调用量线性上升而失去议价空间；错选自建常驻实例用于 PoC 或尖峰业务，则表现为「利用率长期在低位」——这正是本章 §1.1 所列「算力碎片化、闲置率高」痛点的主要成因【经验：多数单团队自购 GPU 的闲置率在 50%–80% 区间】。

误选的第二个高发组合是**「开源一体化平台」与「自研平台」**：两者都能满足「自主可控」，但开源路线的替换点在组件边界（换一个调度器、换一个推理引擎），自研路线的替换点在自有代码里。把它们混为一谈的后果是低估了运维面——开源件带来的不是「免费的一体产品」，而是「一堆需要自己组合与兜底的部件」。

判断方法很简单：**把候选模式各自的总成本写成三个式子（闲置成本 + 运维人力 + 迁移成本），看哪一项在你的约束下占主导**。闲置成本占主导时选 Serverless，运维人力占主导时选托管商业产品，迁移与合规占主导时选开源栈或联邦模式——这一步做完，候选通常只剩一两个。

### 3.4 组合模式：真实系统不会只用一种

**组合 1：K8s + Volcano + 池化 GPU（自建主力，适合 0 → 1）**

- 构成：K8s 做容器与作业编排，Volcano 补 Gang Scheduling 与队列，池化层负责 MIG 切分与拓扑感知。
- 职责边界：K8s 管生命周期，Volcano 管「多卡同时启动 + 排队公平」，池化层管「一张卡切给谁」。
- 运维代价：三层的配置耦合（队列、优先级、抢占策略）需要专人维护，出错形式是「任务起不来」而非性能下降。
- 适合规模：单数据中心、训练与推理混部、千卡以内。
- 换模式的信号：跨地域数据主权要求出现，或集群规模大到「单个任务占满整域」常态化。

**组合 2：LLM 一体化平台 + Serverless 推理（弹性主力，适合 1 → 10）**

- 构成：训练与微调在池化集群内做，峰值推理交给 Serverless，常态推理走常驻实例。
- 职责边界：池化集群承担不可抢占的长任务，Serverless 承接不可预测的尖峰，常驻实例承接稳定基线。
- 运维代价：三套成本模型（折旧 / 按秒 / 按卡时）必须打平到同一口径，否则成本归因永远说不清。
- 适合规模：LLM 应用为主、流量波动大、需要快速试错的组织。
- 换模式的信号：推理密度稳定到实例长期不缩容，或冷启动延迟开始进 SLA 违约统计。

**组合 3：开源一体化 + 跨云调度 + 行业合规层（企业级，适合 10 → 100）**

- 构成：开源栈做流水线与服务，跨云统一层做作业分发，行业合规层做数据分级、留痕与解释。
- 职责边界：开源栈管工具链，跨云层管作业落点，合规层管「谁能用哪些数据与模型」。
- 运维代价：组件版本矩阵、跨云网络、合规评审三条线同时要人；一次合规规则变更会横向触发多模型重审。
- 适合规模：多地域、多业务线、受监管的大型企业。
- 换模式的信号：合规层的评审时间开始超过算法迭代时间，成为发布周期的实际决定项。

### 3.5 反模式与失效分析

反模式与模式的区别不在技术选型，而在**约束与结构不匹配**：同样是自建 GPU 池，有统一调度入口时是模式，各团队各自采购时就是烟囱式采购。下表的每一条都能从「结构」与「症状」两侧同时对照——症状是团队最早看到的东西，结构才是要改的东西。

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 烟囱式采购 | 各团队自购 GPU，池内总量与在用总量长期背离 | 算力按峰值在各烟囱里重复配置，闲置与排队同时存在 | 采购权分散，没有统一调度入口 | 集中算力 + 统一调度 + 按队列配额分配 |
| Notebook 直接上线 | 线上服务的模型产物没有版本号与注册记录 | 无法回答「线上跑的是哪版模型」，回滚与对比都做不到 | 从 PoC 直接演进到生产，跳过注册环节 | Model Registry + 推理服务化 + A/B 与影子模式 |
| 特征不一致 | 离线与在线同一特征存在两份实现 | 训练与推理输入分布不同，效果断崖且不报错 | 训练侧用数据科学栈、推理侧用工程栈 | 引入特征平台保证 Point-in-Time 与一致性 |
| 盲目上 LLM | 大量本可用小模型解决的分类 / 抽取任务走 LLM | 单位请求成本与延迟上升，收益却不随规模增长 | 把「用大模型」当作能力目标 | 按任务分层：分类 / 召回用小模型，复杂推理用 LLM |
| 推理裸奔 | 直接用框架自带服务，无批处理与显存管理 | GPU 利用率低、单位 token 成本高；QPS 一上来就排队 | 先跑通再优化，优化排期被业务需求挤掉 | 换用专用推理引擎（批处理 + KV 管理 + 量化） |
| 训练-推理不可控 | 训练侧有队列与配额，推理侧无人管资源 | 推理侧成为成本黑洞，容量规划失去依据 | 两条链路由不同团队负责，缺少统一治理 | 训推一体的资源与成本治理（同一套配额与账） |
| 忽略 GPU 拓扑 | 分布式训练扩展性远低于预期，通信占满时间 | TP / 通信组跨了非高速互联域，算力在等网络 | 调度器只按「卡数够不够」匹配 | 拓扑感知调度，把通信密集组放进同一高速互联域 |
| 缺少 MLOps 文化 | 平台功能齐全但使用率低，团队仍私下训练 | 平台上的治理能力（注册 / 监控 / 血缘）被绕过，等于没建 | 平台是技术项目而非组织项目 | 一把手推动 + 把上线路径收敛到平台 |
| 国产化替代盲区 | 只适配单一硬件生态，遇到信创 / 等保要求重做 | 底层算子与推理引擎不可替代，迁移成本被低估 | 采购时未考虑双栈要求 | 双栈适配（训练框架与推理引擎抽象层） |
| 盲目追求万卡集群 | 集群规模很大但利用率长期低位，排队反而更长 | 算力规模超出调度与运维能力，卡在拓扑与故障恢复上 | 规模被当作目标而非手段 | 算力规模与调度 / 故障恢复能力匹配后再扩 |

**最危险的三个反模式**：

**「烟囱式采购」** 的暴露方式是慢性的：单看每个团队的申请都合理（「我们的业务峰值需要这些卡」），但把各烟囱的峰值相加后总容量远超实际需求，表现为「总量很大、人人都说不够用」。它的修法不是买更多卡，而是先建统一调度入口——没有入口，任何容量都会被烟囱按峰值吸走。

**「推理裸奔」** 在生产中的典型暴露方式是 QPS 上升后延迟非线性恶化：没有批处理与显存管理时，单卡并发能力被显存上限锁死，表现为「加卡才顶得住」，而正确的修法往往是在同一批卡上换推理引擎。它常被误判为容量问题，从而引发一次不必要的扩容。

**「忽略 GPU 拓扑」** 的暴露方式是「训练扩展性突然失效」：卡数翻倍而吞吐不增，因为通信组跨出了高速互联域。它属于配置层面的问题，但在扩容时最容易被踩到——调度器只匹配卡数，不会替你检查互联关系。

### 3.6 规模跃迁时模式何时该换

模式不是一劳永逸的：**任务的时间形态或数据位置跨过某个阈值时，原来正确的模式会变成错的**——Gang Scheduling 在单机多卡时是多余约束，到多机多卡时是必需品；常驻实例在流量平稳时最省，在强尖峰时最贵。下表的六条跃迁都遵循同一个判据：**约束变了，模式才该换；只是量变大而形态没变时，应该调参而不是换模式**。

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 单机多卡 → 多机多卡 | 传统 ML 平台（单机训练） | 跨节点通信与故障率上升，单机假设失效 | 传统 ML 平台 + 分布式训练调度（Gang） | 训练代码要适配并行与检查点，重跑基线 |
| 小模型 → 十亿参数以上 | 多模型共置推理 | 单模型装不进碎片显存，「共置」反而互相挤占 | LLM 一体化平台（专用推理引擎 + 分页 KV） | 需重构推理栈并重做容量模型 |
| 稳定流量 → 强尖峰流量 | 常驻实例 | 按峰值配置的常驻资源大部分时间闲置 | 常驻基线 + Serverless 承接尖峰 | 成本口径要统一，冷启动延迟要进 SLA |
| 单云 → 多地域 / 多云 | 单集群池化 | 数据主权与容灾要求出现，单集群无法覆盖 | 联邦 / 多云平台 | 数据分发、跨云网络、身份与配额统一 |
| 通用业务 → 受监管业务 | 通用平台 | 缺少决策级留痕与解释，过不了评审 | 垂直行业 AI 平台（合规层 + 留痕链） | 平台迭代变慢，部分模型需换为可解释结构 |
| 千卡 → 万卡量级 | 池化 + 人工调优 | 故障成为常态（规模越大平均无故障时间越短），人工恢复跟不上 | 池化 + 自动故障检测与重调度、拓扑感知 | 需要投资自动化运维，短期利用率可能不升反降 |

### 3.7 自检清单

以下 12 条都指向可核查的事实，而不是「是否重视」这类口号。任何一条答不上来，对应的模式在本组织就没有真正落地。

- [ ] 集群是否有一个统一调度入口？各团队的 GPU 申请是否都经过它（而不是各自采购）？
- [ ] 能否回答「这张卡上个月被谁用了多久、产出是什么」？成本能否分摊到团队与模型？
- [ ] 集群内的排队时长是否有度量？排队与闲置同时出现时，能否定位是哪一步调度没做？
- [ ] 分布式训练的通信组是否落在同一高速互联域内？调度器是否感知拓扑，还是只匹配卡数？
- [ ] 长任务（训练）与短任务（推理）是否在同一池子里被区分对待（抢占、优先级、Gang）？
- [ ] 是否存在「只在夜里跑训练、白天卡闲置」的时段？闲置时段是否有可填充的推理或离线作业？
- [ ] 线上模型是否有版本号与注册记录？能否回答「线上此刻跑的是哪一版、由谁训练、用哪份数据」？
- [ ] 推理是否用了批处理与 KV 管理？当前 GPU 利用率是否被度量，还是只是「感觉很忙」？
- [ ] 是否存在用 LLM 处理本可用小模型完成的任务？成本差异是否被量化过？
- [ ] 训练与推理是否共用同一套资源配额与成本账？还是训练侧有治理、推理侧裸奔？
- [ ] 模型从训练到上线的路径是否唯一？是否还存在「Notebook 直接上线」的旁路？
- [ ] 受监管场景能否复现某一次历史决策（哪版模型 / 哪版特征 / 哪条规则）？国产硬件替换点是否明确？

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 模型小、更新天级、团队小 | 传统 ML 平台 | 小模型可共置，算力被复用而非被独占，单位成本随共置下降 |
| 参数超单卡显存 | LLM 一体化平台 | 只能靠并行拓扑训练、靠显存分页推理，两类基建都不可省 |
| 流量尖峰、试错期 | Serverless AI | 闲置不占卡让成本随调用线性化，但要接受冷启动进延迟 |
| 任务需整域、混合负载多 | GPU 算力池化 | 硬切 / 软切让推理填训练空隙，前提是池里确有可切资源 |
| 受监管、要决策级留痕 | 垂直行业 AI 平台 | 合规是横向约束，必须把留痕与解释内建进链路 |
| 数据不出内网、需深度定制 | 开源一体化平台 | 每层可替换才可贴合内网，配额与审计需自建 |
| 多地域、多供应商 | 联邦 / 多云平台 | 作业与集群解耦换取容灾与议价，代价是数据分发 |
| 训练与推理混部、有夜间空档 | GPU 算力池化 | 让短任务填长任务的空隙，利用率由两类负载的组合决定 |

> 本节小结：决定这 7 个模式选择的主要是**两条机制 —— 算力归谁拥有与调度（独占池 / 池化共享 / 按秒租用 / 跨云联合），以及任务的时间形态（长时不可抢占的训练，还是短时突发的推理）**。这两条机制与 §3.1 的六条约束不是并列关系：**任务时间形态就是那六条约束中的第一条，算力归属则是各模式对全部六条约束的回答方式**（同样面对「短时突发」的任务形态，自有池化、按秒租用、跨云联合是三种不同的回答）。两条机制定死后，成本曲线、隔离性、排队行为与失效点都是它们的推论；机制一取同一值的四个模式（传统 ML、LLM 一体化、垂直行业、开源一体化，算力归属均为「独占池」）再由合规与可解释要求、数据位置与团队技能等约束细分；规模跃迁之所以要求换模式，本质上是任务的时间形态或数据位置跨过了某个阈值。
