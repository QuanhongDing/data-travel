## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

**第一个问题：趋势清单没有时间维度，而 AI 计算平台的选型周期最长。** 一个推理引擎今天能跑，不等于三年后还能被你换掉；一条路线图里的条目写成既成事实，会直接变成采购单上的一行。同一张清单里，「已在生产里跑」与「厂商演示里跑过一次」并列，读者据此定技术栈就会踩空。

本节用三级划分，判据必须可核验，而不是「感觉成熟」：

- **L1 生产可用**：
  - ① 已 GA 且有正式 release note；
  - ② 有第三方（非厂商）公开生产案例；
  - ③ 接口稳定。
  - 三条全中才算。没有「准 L1」「边界案例」这类说法——②核不到就是 L2。
- **L2 可试点**：已可用但接口 / 生态未稳，或仅有厂商自有案例，或只在小规模被验证。可以做 PoC，不要做核心依赖。
- **L3 观望**：仅路线图 / 论文 / 厂商演示 / 预览特性。记录，不要在架构里预留假设。

**第二个问题：本主题的①要看三类对象，判据不因此放宽。**

- 一类是产品与引擎（调度器、推理引擎、托管服务），有正式 release note，好判；
- 另一类是**方法与格式**（并行策略、量化格式、模型文件格式、注意力内核），它们没有 release note，只有官方文档、论文与公开基准；
- 第三类是**规划与工程类对象**（国家级算力网络 / 东数西算这样的国家工程）：它既不是产品也不是方法，没有 release note 可发。本节显式声明这类对象的①由**主管部门的官方规划与批复文件**承担，理由是它的成熟度不体现在发布说明上，而体现在工程是否已建成、跨枢纽的调度与计费口径是否统一。本主题只有一行属此类。
- 所以 5.1 表里凡是方法 / 格式类对象（并行拓扑、量化、长上下文、MoE 路由），①列写的是「由官方文档、论文与公开基准承担」，判级比照的是这些公开材料里有没有可复核的结果；规划与工程类对象那一行，①列写的是「由官方规划文件承担」。两处都只替换①的证据形态，**②③一律照原样核，不跟着放宽**。
- **③只指接口 / 契约 / 标准的稳定性**（对外 API、模型文件格式、服务协议是否多年不变）。「收益不能线性外推」「换个模型就不适用」都不是③：它们该记在②（缺第三方验证），或写进 5.2 的「由此付出的」。把这类理由塞进③，会让同一列里③的含义一行一个样。

**第三个问题：本主题最容易出的错，是把峰值算力当能力。** 加速器规格页上的峰值（FP4 / FP8 档位）是**格式相关**的数字：同一种芯片在不同精度格式下的峰值相差数倍，是否含结构化稀疏又是一档。它既不是①也不是②，它只是**一个数**。判定方法：把候选数字换成「在与你相同的模型、批大小、序列长度、精度与并行配置下，官方文档或公开基准给出的端到端结果」，换不出来就说明这个数字不能用。

**第四个问题：先问这个方向改的是哪一层。** 四类方向的前沿性来源不同，成熟节奏也不同：

| 类别 | 问的问题 | 代表方向 | 判 L1 的难点 |
| --- | --- | --- | --- |
| 训练侧 | 模型能不能训得动 | 并行拓扑、微调、对齐、MoE、长上下文 | 卡在②：训练细节通常不公开，公开记录多为框架方与平台方自述 |
| 推理侧 | 服务量能不能便宜 | 引擎、量化、算子、端侧 | 卡在②：加速比与吞吐多为厂商与框架方自测 |
| 供给侧 | 算力从哪来、按什么买 | Serverless、GPU 云、可中断、算力网络、边缘 | 卡在②与③：各家实例与调度接口不统一 |
| 编排侧 | 谁来消费模型 | 多模型路由、RAG 组件服务化、工具调用、记忆与状态 | 卡在③：运行时与检索的接口演化快，语义约定仍在演进 |

| 推理量化（INT8 / INT4 / FP8 / NVFP4 一类） | L2 | ①由引擎与硬件发布记录承担、**②缺**、**③缺**：量化格式与算子支持随引擎与硬件世代变化 | 先测后优；位宽不等于收益（5.2.2） |
| 算子融合与注意力内核（FlashAttention、Transformer Engine 一类） | L2 | ①满足、**②缺**、**③缺**：内核接口与框架、硬件版本强绑定 | 跟着上游版本走，不要自己改内核 |
| 端侧推理（llama.cpp / Ollama / MLC / CoreML 一类） | L2 | ①满足、**②缺**、**③缺**：模型格式与运行时不统一 | 只在延迟或数据出域约束下做（5.2.2） |

| 国家级算力网络 / 东数西算 | L2 | ①满足（规划与工程类对象，依据见 5.1 正文：官方规划文件）、**②缺**、**③缺**：跨枢纽调度的接口与计费口径无统一标准 | 只放可中断的离线作业（5.2.3） |
| 边缘 AI 算力（Jetson、Atlas 一类嵌入式加速模块） | L2 | ①满足（产品线长期 GA）、**②缺**、③满足 | 只在延迟或数据出域要求下做 |
| 多模型路由与 LLM 网关（按任务路由大小模型） | L2 | ①满足、**②缺**、**③缺**：路由与配额无标准契约 | PoC，先把配额与降级写进契约（5.2.4） |

| 工具调用与 Agent 运行时的资源模型 | L3 | **①缺**：公开能力以演示与产品页为主，给不出验收标准；**②缺**、**③缺**：运行时接口演化快 | 先统一 Trace 与配额口径（5.2.4） |
| Agent 记忆与状态存储 | L2 | ①满足（向量库与 KV 存储有正式文档）、**②缺**、③满足 | 把记忆当数据资产治理（5.2.4） |
| MoE 架构的训练与推理（稀疏专家路由） | L2 | ①由框架与模型发布记录承担、**②缺**、**③缺**：专家路由与并行配置各家不同，无标准 | 先量通信量与专家负载倾斜（5.2.1） |
| 长上下文训练与推理（位置编码缩放、长上下文微调） | L2 | ①由论文与模型发布记录承担、**②缺**、**③缺**：各模型的位置编码实现不互通 | 先量显存账，再谈上下文长度（5.2.2） |
| 多模态训练与推理（视觉编码器 + LLM） | L2 | ①满足、**②缺**、**③缺**：各家的模态接口与采样口径不统一 | 先统一评估口径 |
| 国产加速器与软件栈（昇腾 + CANN 一类） | L2 | ①满足（厂商发布记录）、**②缺**（第三方非厂商的公开生产记录要具体到「训了什么、结果如何」）、**③缺**：各家算子库与迁移工具链不互通 | 先做一次「同一任务、同一模型」的迁移对照实测（口径见 5.6 表的「国产化」一行） |

**本主题下没有方向同时满足 L1 的三条判据。** 满足①与③、只卡在②的有四行：**推理引擎**、**按需 / 可中断算力**、**边缘 AI 算力**、**Agent 记忆与状态存储**——它们缺的是同一条判据（第三方非厂商的公开生产记录），而能查到的公开记录是引擎方、平台方与云厂商自己的工程博客与客户案例，按判据不计入②。本主题的②特别稀缺有一个结构性原因：**训练与推理的内部细节（模型结构、并行配置、单位成本）本身就是竞争力**，多数团队不会公开；因此这里出现的空缺不是「能力没被验证」，而是「验证过程不公开」。其余各行不够格的原因分两类：**训练侧与推理侧的行普遍缺②**（加速比、吞吐与对齐效果多为自测），其中除推理引擎之外连③也缺（格式与算子、内核接口、专家路由、位置编码实现都随框架与硬件变）；**供给侧与编排侧里除上述四行之外的行则主要缺③**（各自的实例接口、调度接口、运行时接口都还在演化）。

### 5.2 演进方向逐条拆解（核心节）

下面四条覆盖 5.1 的四类：5.2.1 训练侧（模型能不能训得动），5.2.2 推理侧（服务量能不能便宜，也是本节唯一改变了交付物形态的一条），5.2.3 供给侧（算力从哪来、按什么买），5.2.4 编排侧（谁来消费模型）。每条都按同一结构展开：旧做法卡在哪 → AI 改变了什么机制 → 由此得到什么 → 由此付出什么 → 证据与来源 → 成熟度。

#### 5.2.1 分布式训练：可扩展性的上限由互连域决定，不由卡数决定

- **旧做法与它的卡点**：
  - 主文件 §2.2 / §2.3 把数据并行、张量并行、流水并行、ZeRO / FSDP 列成一张方法清单，读起来像选型题；实际上它们是**拓扑约束下的解**：单层参数超过单卡显存，必须做张量并行；张量并行的通信必须落在高带宽互连域内，域外带宽差一个量级。
  - 于是「加卡能不能解决问题」有一个先于算力的答案：**参数超过单卡显存之后，缺的是域内带宽**（这一点在 [§ 7.3.2 任务时间形态与算力下限](01-ai-compute-section-7-sec7.md) 已经从平台侧给过结论）。
  - 数据并行那条账也不轻松：主文件 §2.2 给出 AllReduce 的通信量近似 O(S)（S 为参数量），与卡数无关——卡越多，单位算力的通信占比越高。
- **AI 改变了什么机制**：训练的**可扩展单位**从「卡数」变成「域内互连带宽 × 单卡显存」，成本函数从「算力成本」换成「通信 + 显存 + 排队」。大模型训练因此不是「买更多卡」的问题，而是「任务形状能不能装进一个域」的问题。
- **由此得到的**：
  - 因为张量并行必须落在域内，所以**集群会按任务形状碎片化**：同一批卡对 A 模型可训、对 B 模型不可训，排队变长而你买卡解决不了；
  - 因为优化器状态可以分片（ZeRO / FSDP），所以单卡显存需求近似等于「权重 + 梯度 + 优化器状态 + FP32 主权重副本」四项之和除以分片数（见下方推算），**这是单卡能装下多大模型的直接决定项**；
  - 因为 MoE 只激活部分专家，所以它的瓶颈从算力转到**专家路由的通信与负载均衡**——同一批卡上，MoE 与稠密模型的瓶颈不是一回事；
  - 因为长上下文的显存随序列长度增长，所以长上下文训练的可扩展性同样受显存账支配，而不是受算力支配。
- **由此付出的**：
  - **拓扑锁定**：采购形状错一次，那批卡对某些任务就是不可用，而集群生命周期通常以年计。
  - **状态即成本**：检查点与恢复是大状态问题，被抢占一次可能损失数小时【经验】——这是训练负载不能整体搬到可中断容量、必须先做幂等与重排队的原因（5.2.3）。
  - **超参与并行度绑定**：换模型规模往往要重调并行配置与批大小，复现一次训练结果的成本高于训练本身。
  - **评估口径独立于训练**：训练侧的一切优化都不能替代评估；基准分数不可跨版本比较（5.1 表对应行）。
- **证据与来源**：
  - 【公开】ZeRO 的分片优化器状态（Rajbhandari 等人，SC 2020）；【公开】PyTorch 官方的 FSDP 文档与 DeepSpeed 的官方文档：分片与并行配置的接口与语义（具体行为以官方文档当前版本为准）。
  - 【公开】主文件 §2.2 给出通信量与显存的账（AllReduce 通信量近似 O(S)、KV 与优化器状态的项），本节不重复推导，只把结论接到拓扑上。
  - **②（第三方非厂商的公开生产记录）本节给不出具名来源**：训练细节通常不公开，能查到的材料是框架方与平台方的自述。
- **成熟度**：并行拓扑与参数高效微调为 L2（①满足、②缺、③缺——缺③是因为并行与检查点接口在框架大版本之间会变，适配器格式也随框架变化）；对齐方法为 L2（①满足、②缺、③缺——算法与超参口径仍在演化）；公开评估基准为 L2（①由基准方承担、②缺、③缺——分数不可跨版本比较）。与 5.1 表逐行一致。

```text
训练状态账本【推算，输入参数按公开模型配置核验】
  输入：700 亿参数（7×10^10）的模型，混合精度训练
      权重（FP16/BF16）  7×10^10 × 2 字节   = 140 GB   【推算】
      梯度（FP16/BF16）  同权重，2 字节       = 140 GB   【推算】
      优化器状态（Adam）一阶 + 二阶动量，各 4 字节
                                          = 7×10^10 × 8 = 560 GB 【推算】
      主权重副本（FP32） 7×10^10 × 4 字节   = 280 GB   【推算】
      ────────────────────────────────────────────────
      合计 ≈ 1120 GB（不含激活值与通信缓冲）
  ZeRO / FSDP 全分片到 N 张卡：
      单卡状态 ≈ 1120 GB ÷ N
      N = 8   → 约 140 GB/卡  （单卡装不下 80GB 档的卡）
      N = 64  → 约 17.5 GB/卡 （状态尚可，但激活值与注意力峰值要另算）
  ────────────────────────────────────────────────
  结论一：显存的第一决定项是「几份状态」，不是「参数量」——混合精度下
          主权重仍要留一份 FP32（主文件 §2.2），这一份不能不算
  结论二：分片救的是显存，不是通信——分片数越大，AllReduce 与
          分片通信的总量越大，这就是拓扑成为上限的原因
  结论三：MoE 的活参数与总参数不是一回事，账要按「激活的专家」重算
  复算提示：把 7×10^10 换成你的模型规模，并按你的优化器与精度改这四个
          字节数（如 8-bit 优化器状态、是否保留 FP32 主权重），重算一遍即可
```

#### 5.2.2 推理引擎与量化：交付物从「模型」变成「服务档位」

- **旧做法与它的卡点**：
  - 传统 AI 计算平台按「一模型一实例」部署：模型是交付物，实例是计费单位（主文件 §2.1 的推理服务与 §2.3 的服务化清单都是这个形态）。
  - 于是单位成本是常数：加一个模型就多一份 GPU，成本随模型数线性增长；而模型的实际负载是长尾的，多数模型大部分时间空闲。
  - 每次调用按输入输出长度计费的形态更糟：长上下文请求的显存占用与短问答相差一个数量级，而计费口径看不出来。
- **AI 改变了什么机制**：**分页 KV 缓存 + 连续批处理把显存与算力从「独占」变成「可复用」**，量化把权重与 KV 的字节数变成可调参数。结果是**模型的「单价」不再是常数**：同一个模型在不同量化位宽、批策略、上下文预算下，单位成本与单位延迟都不同。
  - 交付物因此从「模型」上移到「服务档位」——档位由 SLO（延迟目标、上下文上限）与成本共同定义，模型只是实现之一。
- **由此得到的**：
  - 因为吞吐是批大小与序列长度的函数，所以「低延迟档」与「高吞吐档」可以是同一个模型的两种商品，平台第一次能按 SLO 分档售卖而不是按实例售卖（分档口径可回看 §7.3.2 的显存账）；
  - 因为 KV 显存随上下文**线性**增长，所以**上下文长度是一个可独立定价的维度**，而不是「模型能力」的副产品；
  - 因为端侧引擎把权重压进消费级设备，所以推理第一次能被放到**数据出不了域**的现场（这是端侧唯一的架构意义，不是「更便宜」）；
  - 因为量化把「精度」变成可调量，所以带评估闭环的团队可以在质量与成本之间做连续取舍（与 [Ch12 §03 大促保障 §5.2.2 的分级降级](../../12-architecture/03-large-event-readiness/03-large-event-readiness-section-5-ai.md) 同源——但这里的档位是常态定价，不是应急降级）；
  - 因为注意力头数与 KV 头的解耦（分组查询、多查询注意力一类）直接减少 KV 的字节数，所以「上下文上限」与「并发上限」由**模型结构 + 量化 + 分页**三者共同决定：主文件 §2.2 的 KV 公式是「每 token 的 KV 字节数 = 2 × 层数 × 头数 × 头维 × 精度字节数」，**其中的「头数」在采用分组查询 / 多查询注意力的模型上是 K/V 头数、不是查询头数**，代入时必须按模型自己的配置文档确认，否则会把它高估若干倍。
- **由此付出的**：
  - **分母不可信**：单卡吞吐依赖模型、批大小、序列长度、精度、引擎版本与硬件，任何单点数字都不能直接当容量分母；用产品页数字当分母，是本节最常见的事故起点。
  - **批处理恶化了尾延迟**：提高批大小换吞吐，代价是尾延迟分布变长——「平均延迟下降、P99 上升」是最典型的组合。
  - **量化收益非线性**：收益取决于算子覆盖与硬件支持，不按位宽线性外推；覆盖不到的部分会退回未量化路径。
  - **端侧碎片化**：模型格式、运行时与精度支持互不统一，端侧的工程成本主要花在适配而不是推理本身。
- **证据与来源**：
  - 【公开】分页注意力与连续批处理（Kwon 等人，SOSP 2023）：它改变了吞吐分母与显存管理方式。【公开】注意力内核的 IO 优化（Dao 等人，NeurIPS 2022）：它是长上下文推理的显存与带宽前提。
  - 【公开】量化与微调的工作（如 QLoRA，Dettmers 等人，NeurIPS 2023）：低位宽权重与适配器微调是「成本可调」的来源。
  - 【公开】MLPerf Inference（MLCommons，结果与规则版本化）：它是少数可以替代厂商吞吐数字的公开对照来源。
  - 【公开】引擎的公开 release notes：分页 KV、前缀缓存、量化支持这些能力按版本可逐条核对。**引擎的版本号与里程碑（例如某个版本是否被称作 1.0）必须以官方仓库的 release notes 为准**，本节不引用具体版本号。
  - **②本节给不出具名来源**：加速比与吞吐绝大多数来自厂商与框架方自测。
- **成熟度**：推理引擎、量化、注意力内核、端侧推理、长上下文五行均为 L2；其中**推理引擎**是①③满足、②缺，**量化、注意力内核、端侧推理与长上下文**是①满足、②缺、③缺（缺③的原因写在 5.1 表对应行）。判定方法：拿你自己的模型、批大小与序列长度，在候选引擎上量一次吞吐与 P99——两个数一起报，只有一个的不要采信。

| 服务档位 | 由什么参数决定 | 典型代价 | 适合谁 |
| --- | --- | --- | --- |
| 低延迟档 | 小批、短上下文上限、高频预热 | 单位 token 成本最高 | 交互式问答、在线决策 |
| 均衡档 | 中等批、连续批处理、前缀缓存 | 尾延迟随负载波动 | 大多数在线业务 |
| 高吞吐档 | 大批、离线排队、可中断容量 | 延迟无承诺，可被重排 | 批处理、离线标注、离线评测 |
| 端侧档 | 低位宽权重、本地运行时、无网络依赖 | 能力上限低、适配成本高 | 数据不能出域的现场 |

#### 5.2.3 算力供给形态：把「闲置」从账上移除

- **旧做法与它的卡点**：
  - 自建与包年采购的共同要求是「按峰值买」：训练任务长时独占、推理负载短时突发，同一批卡服务两类负载必然一边排队一边闲置（[§ 7.3.1 算力归属](01-ai-compute-section-7-sec7.md) 已经把这四种粒度摊开）。
  - 更硬的是采购周期：算力、带宽、机位的采购周期通常以月计【经验】，而需求变化的周期更短——**按预测买卡的窗口经常来不及**。
  - 于是瓶颈不是「预测得多准」，而是「预备得多灵活」：能不能把一段算力买成「随时可以不要」或「用到才付」。
- **AI 改变了什么机制**：供给被拆成两种商品——**保证可用性**的（常备 / 预留）与**保证低成本**的（按调用、按秒、可中断）。核心机制是把「闲置时不占资源」或「随时可被收回」折进单价，而不是靠规模摊薄。
- **由此得到的**：
  - 因为按调用计费把闲置从账上移除，所以**低频模型的平台化第一次在成本上成立**（此前它们只能共享同一张卡，见 §7.3.1 的池化共享）；
  - 因为可中断容量把失败语义从「报错」换成「迟到」，所以批推理、离线评测、特征回填、索引重建这类**可重排**的作业可以放到最便宜的那一段（与 [Ch12 §04 容量规划](../../12-architecture/04-capacity-planning/04-capacity-planning-section-5-ai.md) 同一条判断）；
  - 因为算力网络把「在哪算」从资产问题变成调度问题，所以跨地域的离线作业有了新的价格区间——**代价是数据位置变成硬约束**（§7.3.4）。
- **由此付出的**：
  - **冷启动**：「秒级」指的是实例分配与调度，**模型加载到显存是分钟级**——把后者当前者，冷启动预算差一个量级。
  - **单价含平台加价，长期驻留时反转**：见下方推算的盈亏平衡点。
  - **中断是外生的**：回收时点与规模由供应商容量池决定，需要中断通知 + 幂等 + 重排队；没有幂等键的作业放上去是在制造重复计算。
  - **跨域传输吃差价**：数据体量大时，「哪便宜往哪调度」在训练开始之前就已经亏掉（§7.3.4）。
  - **供给方的资本结构会变**：AI 专用云从私有走向公开市场之后，长期价格承诺的可依赖度下降（上市信息以该公司投资者关系页与交易所披露为准）。
- **证据与来源**：
  - 【公开】Kubernetes 官方文档的自动扩缩章节（`autoscaling/v2` 于 2021 年 GA）与 KEDA（2021 年进入 CNCF 孵化、2023 年毕业）：按外部指标扩缩的接口与语义（版本与毕业状态以官方页面与项目 release notes 为准）。
  - 【公开】AWS EC2 Spot 的官方文档与 What's New（Spot 实例自 2009 年起提供）：中断通知、容量池模型与折扣表述（以官方页面当前版本为准；「最高可低多少」不等于典型值）。
  - 【公开】ServerlessLLM（OSDI 2024）：面向大模型的低延迟 Serverless 推理的系统工作，说明「冷启动」是这一路线的核心研究问题而不是已解决的问题。
  - 【公开】[§ 7.3.1 算力归属](01-ai-compute-section-7-sec7.md) 的四种粒度与 [§ 7.4 成本函数](01-ai-compute-section-7-sec7.md)：本节沿用它，只补「供给形态变化」这一层。
  - **②本节给不出具名来源**：公开材料以云厂商与平台方文档、客户案例页为主。
- **成熟度**：Serverless 推理、GPU 池化、可中断算力、AI 专用云、算力网络、边缘算力六行均为 L2（都为①满足、②缺；其中 GPU 池化、AI 专用云、算力网络、Serverless 另外缺③，缺③的原因写在 5.1 表对应行）。

【推算】按调用计费与常驻的盈亏平衡点（前提写全，读者可换成自己的数）：

- 设某实例常驻的月成本为 `C = 730 小时 × c`（c 为每小时的全成本，730 小时/月按 24 × 365 ÷ 12 折算）。
- 设按调用计费的小时单价为 `p`，实际占用时长 `T` 小时/月，则月成本为 `p × T`。
- 平衡点：`p × T = C`，即 `T* = C / p = 730 × c / p`。
- 取 `p ≈ 3c`（【经验】：Serverless 类服务的小时单价通常是同规格常驻成本的数倍，倍数随产品与规格变化，请用你们的实际报价替换）：
  - `T* = 730 / 3 ≈ 243 小时/月`，即**占空比约 33%**。
- 结论一：**占空比长期低于这个点，按调用更省；长期高于它，常驻更省**——这与「Serverless 更先进」无关，只与占空比有关。
- 结论二：这个平衡点会随报价变动而移动，所以它必须写成一个**可重算的公式而不是一个结论**；每季度用最新报价重算一次。

#### 5.2.4 Agent 工程化对平台的反作用：治理对象与资源模型同时上移

- **旧做法与它的卡点**：
  - AI 计算平台的元数据模型到「特征 / 模型 / 实验 / 服务版本」为止（[§ 7.3.3 治理对象](01-ai-compute-section-7-sec7.md) 的表里，模型与算力族管的就是这几类）。
  - Agent 让线上行为由 **Prompt + 工具清单 + 记忆**共同决定，这三类对象不在原模型里；于是「换回上一个模型版本」不再等于「换回上一个行为」——**行为回滚失效**，这是编排侧最实际的卡点。
  - 资源模型也变了：一次用户请求变成多次模型调用与工具调用（这条链路的失败形态与超时预算，见 [Ch12 §03 大促保障 §5.2.3](../../12-architecture/03-large-event-readiness/03-large-event-readiness-section-5-ai.md)）。
- **AI 改变了什么机制**：**治理对象上移一层**（从模型到 Prompt / 工具 / 记忆），**资源模型从「一次推理」变成「一条调用链」**。平台要管的东西从「哪个模型在跑」变成「这次行为由哪一版 Prompt、哪几个工具、哪一段记忆共同决定」。
- **由此得到的**：
  - 因为行为由 Prompt 与工具共同决定，所以**可回滚对象必须是三件套**（模型版本、Prompt 版本、工具清单），否则回滚只是一次「看起来生效了」的操作；
  - 因为调用链是有状态、可重放的，所以**记忆成为需要被治理的数据资产**：它有自己的权限、保留期与删除义务，不能只当成缓存；
  - 因为工具调用把平台边界扩到外部系统，所以**准入清单**（谁能被调用、以什么身份、失败怎么办）成为平台侧的门禁，而不是应用侧的自律。
- **由此付出的**：
  - **治理层数增加**：每多一族对象就多一套元数据与门禁要维护，而门禁的价值只在其被真实使用的那一天体现。
  - **记忆的合规成本**：记忆里会沉淀个人信息，保留期、删除与跨境问题会直接落到平台上。
  - **追踪成本与口径漂移**：跨服务追踪 LLM 调用依赖语义约定，而该约定仍在演进（其稳定性状态以 OpenTelemetry 官方文档当前版本为准），升级会造成历史数据不可比。
  - **框架沉没成本**：Agent 运行时框架的接口演化快（多 Agent 协作框架尤其明显：编排原语、状态模型与消息语义各家不同），把业务逻辑绑死在某个框架上是本节最典型的可避免损失。
- **证据与来源**：
  - 【公开】[§ 7.3.3 治理对象](01-ai-compute-section-7-sec7.md) 的表（数据资产族 / 模型与算力族 / Agent 编排族各自管什么、门禁设在哪个动作上）：本节沿用它，只补「三件套回滚」与「记忆即资产」两条推论。
  - 【公开】OpenTelemetry 的 GenAI 语义约定：用于标注模型与工具调用（稳定性状态与属性名以官方文档当前版本为准）。
  - 【公开】向量库与 KV 存储的官方文档：记忆类存储的权限与保留能力（能力与配额以官方文档当前版本为准）。
  - **①②本节给不出可核验的来源**：公开能力以演示与产品页为主，既无验收标准，也无第三方生产记录。
- **成熟度**：工具调用与 Agent 运行时为 L3（①缺、②缺、③缺）；多模型路由与 LLM 网关为 L2（①满足、②缺、③缺）；Agent 记忆与状态存储为 L2（①③满足、②缺）。判定方法：问「换回上一版 Prompt 与工具清单之后，线上行为是否真的回到上一版」——答不出，说明治理对象还没上移到编排层。

### 5.3 与本主题既有栈的接口在哪

不要写「与 X 结合」这种空话。下面写清**接口边界**：谁调用谁、数据以什么形态穿过边界、失败时谁负责。

| 结合点 | 接口形态 | 谁负责失败 | 现状 |
| --- | --- | --- | --- |
| 数据湖 / 仓库 ↔ 训练（[§ 7.3.4](01-ai-compute-section-7-sec7.md)） | 训练直读仓内表或以开放格式读取；导出会新增一个数据边界 | 权限与审计断点由把数据导出的一方负责 | 成熟（见 [§ 6 阿里 MaxCompute AI 案例](01-ai-compute-section-6-sec6.md)） |
| 特征平台 ↔ 训练与推理 | 特征定义版本 + 时间点正确性作为输入 | 训练与推理特征不一致由特征平台与调用方共同负责（门禁设在发布动作上） | 成熟，先做 |
| 向量库 ↔ Embedding 服务 | 批式与流式两条路径，向量与元数据一起交付 | 离线在线不一致由生成向量的服务方负责 | 成熟；要写清重算触发条件 |
| 模型注册表 ↔ 推理服务 | 上线的是「权重 + 配置 + 档位」三元组 | 线上跑的是哪个版本答不出时，由平台负责 | 成熟；档位需纳入注册对象 |
| 智能体平台 ↔ LLM 网关 | 配额、超时预算、降级档位作为契约参数下发 | 未分配预算的调用链由智能体平台负责 | L2，要新增契约（5.2.4） |
| 容量规划（[Ch12 §04](../../12-architecture/04-capacity-planning/04-capacity-planning.md)）↔ AI 平台 | token 吞吐、上下文分布、模型清单作为输入 | 把厂商吞吐数字直接当分母的一方负全责 | L2，需自测（5.2.2） |
| 大促保障（[Ch12 §03](../../12-architecture/03-large-event-readiness/03-large-event-readiness.md)）↔ 推理平台 | 预热池大小、降级档位、可中断备用池 | 冷启动预算错算由给出预算的一方负责 | L2，先拆两个时间尺度 |
| 成本治理（[Ch11 §03](../../11-cross-cutting/03-data-cost-finops/03-data-cost-finops.md)）↔ 算力账单 | 按卡时 / token / 排队时长三种归因口径 | 归因口径不统一由平台负责（业务方看不清自己的成本） | 现状：多数只做卡时 |
| 多云 / 算力网络 ↔ 作业调度 | 作业描述与集群解耦，按数据位置就近调度 | 跨域传输成本由决定调度的一方负责 | L2，先做可迁移性准备 |

这张表按「现在能不能动」分三档读：**数据湖与仓库、特征平台、向量库、模型注册表这几行现在就能动**——它们缺的不是新工具，而是把「三元组」「档位」「重算触发条件」这类契约写清；**成本治理这一行要先改口径**，不把 token 与排队时长纳入归因，前面所有优化都算不出收益；**智能体平台、容量规划、大促保障、多云这几行要新增契约**，它们的共同风险是：契约没写清时，故障表现为「说不清是谁慢、谁贵」。

最容易被忽略的一条接口是**分母由谁负责**：[Ch12 §04 容量规划](../../12-architecture/04-capacity-planning/04-capacity-planning.md) §2.2 给出的 GPU 需求公式（`所需 GPU 数 = 推理 QPS × Token 数/请求 × 1 / (GPU 吞吐 × 利用率)`）里，「GPU 吞吐 × 利用率」这个分母通常由平台方提供、由业务方使用。分母错了，业务方算出来的每一个数都错，而业务方没有能力发现它错——所以这条接口必须写清：分母由平台方提供、带测试条件（模型、批大小、序列长度、精度、硬件、引擎版本）与测试日期，每次硬件或引擎升级后重测一次。

**第三方生产案例（② 侧证据）**

- **本节给不出具名的第三方（非厂商）生产案例**，这不是排版空缺，而是本主题最重要的一个事实：它是 5.1 表里没有一行判到 L1 的直接原因。能查到的两类材料都不算②——引擎方、框架方与云厂商的工程博客与客户案例页属厂商材料；第三方教程与集成文档描述的是「怎么用」，不是「谁在生产里用了、结果如何」。
- 本主题的②有一个结构性稀缺：**训练与推理的内部细节本身就是竞争力**（模型结构、并行配置、单位成本），所以多数团队不公开。读者不应把「查不到」读成「没人用」——正确的读法是「这一行的证据形式不成立，因此按判据记 L2」。
- 自己核验一条方向够不够 L1 的方法：找一份**非厂商、具名、带年份**的工程博客或会议分享，读它有没有写清模型规模、硬件与并行配置、实测吞吐（或训练时间）与其测试条件；写不出这几项，就仍然只能记 L2。检索入口可用「公司名 + LLM serving / training infrastructure + 工程博客」这类组合，命中的厂商产品页与客户案例页直接剔除。

**为什么这里不逐个列名**：论文与方法、通信库、产品与版本三类对象里，凡只有名称、没有被标出会议或年份与测试条件的，单列成条目无法核验能力边界，本节因此不逐条列名，只把它们代表的方向并进 5.1 表对应各行，并把带会议与年份的具名工作放进上面的「论文与公开基准」一栏。比如量化的 AWQ / SmoothQuant、投机解码的 SpecDec / EAGLE、长上下文的 RoPE Scaling / YaRN / LongLoRA 都只落在 5.1 表的方向里；通信库 NCCL / NCCLX 落在「分布式训练的并行拓扑」一行；自建平台与微调库 ByteFSDP / PEFT 另见 [§ 6 落地实践](01-ai-compute-section-6-sec6.md) 的阿里云 PAI 与字节 ByteFSDP 案例。

**怎么用这几类文献**

- 官方文档用来看**接口与承诺边界**（哪些行为稳定、哪些随版本变）；
- 论文用来看**机制**（为什么吞吐会变、显存为什么会爆），不要拿论文的倍率当你的分母——论文的运行条件与你的负载不会一致；
- 基准用来看**量级与可比性**，把候选放进同一套条件里比；
- 三条都不满足的数字（产品页上的峰值、营销文案里的倍率）不要进公式，也不要进采购单。

### 5.5 被过度宣传的部分

- **「算力水电煤气化，初创公司可以零成本启动 AI 项目」**——实际是：**单价下降不等于总成本下降**。单位成本降低的同时，用量被放大：更长的上下文、更多的调用、Agent 的循环与重试，都会把总量乘上去。**为什么会这样**：把按需计费的「无门槛」误读成「无成本」，而按用量计费的账单是**用量 × 单价**，两头都在增长。**什么时候它才会成真**：单位成本与用量同时可观测、且能归因到业务（5.3 成本治理那一行），此时「便宜」才是一个可管理的结论而不是一句判断。
- **「推理引擎把吞吐提升十几倍到几十倍」**——实际是：换批策略提升的是**吞吐**，代价是**尾延迟**与显存；倍率离开条件就没有意义（模型、批大小、序列长度、精度、硬件、引擎版本，缺一项都不可比）。**为什么会这样**：解码阶段是显存带宽受限的，批处理把同一份权重读一次服务多个序列，收益自然巨大——但它同时也把这些序列的完成时间绑在一起。**什么时候它才会成真**：你用同一套条件自测出「吞吐 + P99」两个数，并且能说明你的负载能接受这个尾延迟。
- **「Serverless 已经解决冷启动，P99 可以做到 1 秒以内」**——实际是：**实例分配是秒级，模型权重加载到显存是分钟级**；能进 1 秒的前提是权重已被预热或分层缓存命中，而这个前提本身要靠常驻的资源来维持。**为什么会这样**：Serverless 的计费模型要求「不占用就不收费」，而权重的就绪状态必须被占用——两者天然冲突，所以真正的解法是「用少量常驻换大量按需」。**什么时候它才会成真**：服务把「首 token 延迟」与「模型就绪时间」分开承诺，并给出权重缓存命中率；只承诺总延迟而不给条件的，不要写进 SLO。

### 5.6 未来 3–5 年：可证伪的预测

趋势清单里的句子大多不可证伪（「AI 算力将成为水电煤气」永远正确）。下面把本节可证伪的判断写出来。

| 预测 | 会成真的信号 | 会证伪的信号 |
| --- | --- | --- |
| 推理容量会从「按实例小时」转向「按 SLO 档位 + token 服务质量」计价 | 云与内部平台的计价项里出现延迟档 / 吞吐档的区分，成本归因里出现 token 维度 | 三年后账单仍只按实例小时结算，档位只存在于文档里 |
| 训练与推理会在同一集群上混部，成为调度器的一等场景 | 调度器文档把「训练队形 + 推理填充」写成标准配置；集群容量台账按域而不是按机器管理 | 主流仍是训练集群与推理集群物理隔离 |
| 平台会把 Prompt / 工具 / 记忆纳入元数据模型，与模型版本并列 | 模型注册类产品的正式文档里出现 Prompt 与工具清单的版本对象 | 三年后仍由应用侧各自管理这三类对象的版本 |
| 「国产化」的成败信号会从峰值算力转向算子覆盖与迁移成本 | 公开材料开始报告「同一任务迁移后的端到端时间与改动量」 | 公开对比仍停留在峰值 TFLOPS 与单卡基准 |

### 5.7 给架构师的行动建议

| 你的处境 | 现在就该做 | 一年内观察 | 明确不要做 |
| --- | --- | --- | --- |
| 只有传统 ML 负载（小模型、天级迭代） | 把模型注册与特征一致性补齐（5.3 前四行） | 团队是否需要 LLM 微调能力 | 不要为「大模型」预建并行训练环境；不要引入分页与连续批处理 |
| 有 LLM 微调需求（单机到小队形） | 先固定评估口径；把 LoRA 一类参数高效微调跑通（5.2.1） | 训练框架的分片接口是否还会大改 | 不要在没量清互连域之前买多机；不要用公开榜单分数做上线决策 |
| 有在线推理业务 | 用「吞吐 + P99」两个数自测分母；按 5.2.2 的档位表定义服务档位 | 引擎侧前缀缓存与量化的默认能力 | 不要把厂商吞吐数字写进容量模型；不要只报平均延迟 |
| 推理负载稀疏、波峰波谷明显 | 算一次占空比盈亏平衡点（5.2.3 的推算），决定常驻与按调用的比例 | 报价变动后重算平衡点 | 不要在占空比很低时按峰值常驻；不要把不可中断的作业放到可中断容量 |
| 已有 Agent 应用 | 把 Prompt / 工具清单 / 记忆版本化，纳进注册对象（5.2.4） | GenAI 语义约定的稳定性状态（决定追踪数据能否跨版本比较） | 不要把业务逻辑绑死在某个运行时框架上；不要把记忆只当缓存 |
| 受数据出域或延迟约束 | 评估端侧档（5.2.2 档位表）与边缘算力 | 端侧模型格式与运行时是否开始收敛 | 不要为省单价把数据搬出域（§7.3.4） |

「明确不要做」这一列的判据是：**凡是用不可信分母算出来的卡数、用峰值算力替代端到端能力的判断、以及在治理对象没上移之前就上的 Agent 平台，现在做都是浪费**——它们的成本不会立刻出现，而是在第一次形态变化（新模型结构、更长上下文、新的 Agent 运行时）时集中兑现。

### 5.8 小结

> 本节小结：AI 在本主题下真正改变的**唯一一条机制**，是**把交付物从「模型」上移到「服务档位」**——分页 KV 缓存、连续批处理与量化让同一个模型在不同精度、批策略与上下文预算下成为不同的商品，于是平台的治理对象（模型版本之外还要管档位）、计费单位（从实例小时到 token 与档位）和 SLO 一起跟着变。它**没有**改变的是两条物理与商业约束：数据位置决定算力能不能搬（§7.3.4），以及长期驻留下来的经济学——**算力的账最终由占空比与拓扑决定，而不是由单价决定**。
>
> 因此本章的前沿判断是「训练侧先看拓扑、推理侧先测分母、供给侧先算占空比、编排侧先补治理对象」：前三条现在就能做，不需要新工具；而 Agent 运行时与自动编排（L3）只应该被允许生成建议与摘要，不应该被允许决定线上行为。
>
> 💡 **思考锚点**：算一次你自己推理负载的占空比（平均负载 ÷ 峰值负载），把它代进 §5.2.3 的盈亏平衡点推算——常驻多少、按需多少，才比按峰值全额常驻便宜？如果你的占空比落在很低那一档，现在按峰值常驻的那部分里，有多少是在为一年只出现几次的波峰付费？
