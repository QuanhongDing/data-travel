## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

决策智能的模式表读起来像一份「按场景挑一个」的菜单：规则、模型、实时、因果、在线学习、LLM、Agent、联邦。但真实的决策架构是被约束推出来的，而且推它的那条约束**不是技术偏好，是问责结构**：这个决策做错了以后，代价由谁承担、能不能补救、事后能不能给出理由。同一个「是否放贷」的决策，在可人工复核、金额小、可追回的场景里可以全自动由模型出分；在金额大、不可撤回、要求逐条举证的场景里，同一套模型只能作为建议，前面必须有一层硬规则把零容忍条件拦住（这种分层见 [§ 6 案例 2.1](02-decision-intelligence-section-6-sec6.md)）。

第二条常被忽略的约束是**反馈回来的速度与量**。决策函数 `D: Context × Features → Action` 的参数从哪里来，本质上由反馈决定：反馈要几周才回来、样本一年只有几万条，就只能靠规则或离线模型；反馈以秒计、每天上亿次，才轮得到在线学习与 Contextual Bandit。**决策频率与反馈速度不匹配，是绝大多数「上了在线学习却不敢让它真做决策」的根因**——不是算法不行，是反馈回路撑不起更新频率。

所以下面每个模式都先回答一个问题：**它被哪条约束逼出来**。说不出约束的选择（最常见的是「大模型是趋势」「同行都在做」）不是选型，是试验；而决策系统的试验是有成本的——每一次错误决策都对应真实的业务损失或监管暴露。

| 约束 | 它决定了什么 | 本主题下最容易被它推翻的直觉 |
| --- | --- | --- |
| 决策频率与延迟预算 | 规则 / 模型 / LLM / Agent 谁能进链路 | 「精度最高的方案就该上」——延迟预算百毫秒内时，推理成本高的方案直接出局 |
| 可解释性与举证责任 | 能否用黑盒、解释必须做到什么粒度 | 「有 SHAP 就算可解释」——监管要的是"这次决策命中了哪条依据"，不是特征重要性的平均图 |
| 决策代价与可逆性 | 要不要人工兜底、要不要分态处理 | 「自动化率越高越好」——不可撤回的决策上，自动化率是风险指标而不是效率指标 |
| 反馈延迟与样本量 | 用规则、离线模型还是在线学习 | 「有数据就能训模型」——反馈要三个月才回来时，在线学习学到的是三个月前的世界 |
| 探索空间与试错代价 | 能不能做 A/B 与 Bandit、探索比例上限 | 「都做 A/B 就好了」——探索本身要让一部分人拿到较差的策略，业务未必同意付这笔账 |
| 跨域协同与合规边界 | 集中式、联邦还是各域自治 | 「数据集中起来效果最好」——合规不允许出域时，最优解在可行域之外 |

### 3.2 模式逐个拆解（核心节）

每个模式按同一套模板读：**约束**说明它被什么逼出来；**结构**用一段示意把关键机制画出来；**因果**给一条「因为机制 A，所以性质 B」的句式；**代价**是这套结构必然要付的成本；**失效点**写清优点在什么条件下反转成缺点。

#### 3.2.1 规则驱动决策（Rule-based Decisioning）

- **被什么约束逼出来**：决策依据能被人写成明确条件（限额、名单、年龄、地域），且必须能在事后逐条举证「为什么拒绝」。
- **结构**（决策表：条件是列，动作是行；命中策略决定冲突时谁赢。以下阈值为结构示例，实际取值按业务与监管要求设定，不对应任何机构的真实阈值）：
```text
DMN 决策表（信贷初审，示例）
 ┌── 条件（列） ────────────────────────────┬── 动作（行） ──┐
 │ 分值区间   │ 收入门槛  │ 申请金额         │ 结果           │
 ├────────────┼───────────┼──────────────────┼────────────────┤
 │ ≥750       │ ≥10 万    │ ≤50 万           │ APPROVED       │
 │ 700–749    │ ≥15 万    │ 任意             │ APPROVED       │
 │ 650–699    │ ≥20 万    │ 任意             │ MANUAL_REVIEW  │
 │ <600       │ 任意      │ 任意             │ REJECTED       │
 │ 其他       │ —         │ —                │ MANUAL_REVIEW  │
 └────────────┴───────────┴──────────────────┴────────────────┘
 命中策略必须显式声明（FIRST / PRIORITY / UNIQUE），
 否则规则顺序本身就是一条看不见的业务逻辑
```
- **为什么这样设计有效**：因为规则是被显式存储的一等公民（可版本化、可评审、可单条启停），所以决策依据能脱离代码被审计与修改——业务方能在不发布程序的前提下改口径。
- **代价**：可维护性由**条件维度的组合数**决定，而不是由规则条数决定；规则的顺序与命中策略构成隐性逻辑；每条规则都要配 Owner 与版本，否则半年后没人敢删。
- **失效点**：当条件维度增加到没人能预测改动影响时，「可解释」会反转成「没人敢改」，因为规则之间的交互（优先级、互斥遗漏、兜底分支）无法从任何单条规则读出来——此时系统仍然可解释，但已经没有可维护性。
- **量化判据**：规则条数、条件维度数、最近一次规则变更从提出到上线的评审耗时。三者任一失控，就该把一部分判断下沉到模型，而不是继续加规则。
- **真实使用**：Drools 与 Easy Rules 是公开的规则引擎实现，DMN 是决策表建模的公开标准（Drools 所依赖的 RETE 匹配算法出自 Forgy（1982）【公开】；三者的版本与许可以各自官方仓库与规范文档为准）；蚂蚁把「零容忍」条件放在硬规则层、明确不让模型去学绝对约束【经验】（做法见本章 [§ 6 案例 2.1](02-decision-intelligence-section-6-sec6.md)，属实践方自述，本书不按【公开】档引用；可按「决策大脑规则模型策略分层」一类关键词从公开材料自行检索核验）。

#### 3.2.2 ML 模型驱动决策（ML-based Decisioning）

- **被什么约束逼出来**：决策边界是非线性的、人写不出条件，但有足够历史样本与标签可拟合。
- **结构**（关键是留痕：没有这张表，模型决策无法归因也无法回滚）：
```sql
-- 决策留痕：每次决策一行，是归因、审计与灰度对比的共同基础
CREATE TABLE decision_log (
  decision_id   BIGINT,
  decided_at    TIMESTAMP,
  subject_id    BIGINT,
  feature_snap  JSON,        -- 推理时刻的特征快照（不是回查得到的当前值）
  model_name    VARCHAR,
  model_version VARCHAR,     -- 必须记录，否则无法解释行为漂移
  score         DOUBLE,
  action        VARCHAR,     -- 模型输出经策略映射后的最终动作
  explain       JSON         -- 特征贡献 / 命中分支
);
```
- **为什么这样设计有效**：因为决策函数由样本拟合而非由人编写，所以它能覆盖人写不出的高维交互，且随样本增加自然改进；代价是它不携带「为什么」——理由必须由解释方法事后构造，而解释方法本身有自己的稳定性假设。
- **代价**：需要标注数据、特征管道与离线评估体系；效果随数据分布漂移衰减；上线必须配留痕表与灰度对照，否则回滚只能靠"整体关掉"。
- **失效点**：当业务要求对每一个个体给出可被监管接受的拒绝理由时，「覆盖复杂关系」会反转成「举证成本」，因为模型只输出分数，逐条理由要由解释方法反推，而反推结果依赖于解释方法在分布外的行为——分布外的解释往往不可靠。
- **量化判据**：离线评估与上线效果的迁移差（特征一致性问题的第一指标）、特征分布漂移、同一输入的多次解释是否可复现。判定方法：把线上真实流量的一段特征快照拿回离线复算，看分数是否一致。
- **真实使用**：XGBoost 出自 Chen 与 Guestrin（KDD 2016）【公开】；SHAP 出自 Lundberg 与 Lee（NeurIPS 2017）【公开】；LightGBM 与 DNN 是同一模式下的另两类常用实现【经验】（可按项目名与模型名检索核验）；阿里以多任务多目标建模统一多路推荐决策、字节以长序列建模刻画用户此刻的兴趣【经验】（两处做法见本章 [§ 6 案例 2.2 与 2.3](02-decision-intelligence-section-6-sec6.md)，属实践方自述，本书不按【公开】档引用；可按「多任务多目标建模推荐决策」与「长序列建模用户兴趣」一类关键词自行检索核验）。

#### 3.2.3 实时决策（Real-Time Decisioning, RTD）

- **被什么约束逼出来**：决策要在用户还在等待的窗口内返回，且特征必须反映此刻而不是昨天的状态。
- **结构**（延迟预算必须按段分配，并显式给出超时后的降级分支。下面各段占比是一组示例分配，合计 100%，实际比例按链路实测调整）：
```text
在线决策链路的延迟预算（每段都要有上限与超时动作）
  请求到达
    ├─ ① 在线特征读取（缓存 / 特征存储）  ≤ 预算的 40%
    ├─ ② 硬规则匹配（名单 / 限额）        ≤ 预算的 10%
    ├─ ③ 模型推理（含特征拼接）           ≤ 预算的 30%
    └─ ④ 策略映射 + 回写日志              ≤ 预算的 20%
    （示例分配，四段合计 100%）
  ────────────────────────────────────────────────
  关键：任一段超时 → 走降级分支（保守动作），而不是继续等
       超时不是异常，是设计里必须存在的正常分支
  关键：链路延迟由最慢的依赖决定，不由平均速度决定
```
- **为什么这样设计有效**：因为链路被切成可独立设超时的多段、且每段有降级动作，所以系统在依赖抖动时仍能给出确定的答案（哪怕是保守的），而不会把用户卡在等待里。
- **代价**：常驻集群与在线特征存储的固定成本（按 24 小时计，而业务峰值可能只有几小时）；不可重放的调试难度（同一请求很难原样复现）；影子链路与降级分支本身也要维护。
- **失效点**：当特征需要跨多个在线存储拼装时，「毫秒级响应」会反转成「最慢的那个依赖支配全部预算」，因为链路延迟由最大而不是平均决定——此时唯一的出路是减少在线依赖数，而不是优化单段性能。
- **量化判据**：P99 而不是平均延迟、超时率、降级分支命中率。降级分支命中率长期偏高说明预算给得不合理，业务实际拿到的是保守决策。
- **真实使用**：这一模式的工程栈通常由流处理引擎（如 Flink）、在线特征存储与实时模型服务组成【经验】；蚂蚁的决策流水线在毫秒量级给出可举证的风险决策【经验】（见本章 [§ 6 案例 2.1](02-decision-intelligence-section-6-sec6.md)）；某银行在「拒绝 / 通过 / 转人工」之间做三态取舍【经验】（见 [§ 6 案例 2.4](02-decision-intelligence-section-6-sec6.md)）。两处均属实践方自述，本书不按【公开】档引用，可按「决策大脑毫秒级风控决策」与「三态风控拒绝转人工」一类关键词自行检索核验。

#### 3.2.4 因果决策（Causal Decisioning）

- **被什么约束逼出来**：决策要改变某个结果（发券是否真能提升转化），而观测数据里「发过券的人本来就买得多」，相关性会把决策引向错误方向。
- **结构**（识别因果必须指出混杂变量，并说明它们怎么被处理）：
```text
因果图（DAG）：识别的是"干预"的效果，不是"观测"的差异
        混杂因素（Z）：活跃度 / 历史消费 / 会员等级
              │
              ├──────────────► 处理（T）：是否发券
              │                    │
              └──────────────► 结果（Y）：是否转化
   ────────────────────────────────────────────────
   要估的量：E[Y | do(T=1)] - E[Y | do(T=0)]    ← 干预分布
   不要估的量：E[Y | T=1] - E[Y | T=0]           ← 条件相关，被 Z 污染
   前提：Z 的集合必须可观测完整；无未观测混杂是
         一个无法用数据检验的假设，只能靠设计去支持
```
- **为什么这样设计有效**：因为因果效应被定义为干预分布下的差异而不是条件相关，所以估计量能回答「如果做了会怎样」，这正是决策需要的量；代价是它必须依赖「无未观测混杂」这类不可检验的假设。
- **代价**：需要领域知识画 DAG 并论证假设；异质效应估计对样本量要求更高；很多场景要配合实验或准实验设计才能成立。
- **失效点**：当不存在可用的干预来源（没有实验、也没有可用的工具变量或断点）时，「识别真因果」会反转成「用更复杂的方法估计同一个相关」，因为因果识别需要一个外生变动源，没有它，估计量换的只是计算方式而不是结论的性质。
- **量化判据**：是否存在可用的干预/实验来源；估计对未观测混杂的敏感性（能容忍多大的偏离）。判定方法：把同一份数据用因果估计与普通回归各算一次，两者的差异就是混杂的量级。
- **真实使用**：倾向得分匹配出自 Rosenbaum 与 Rubin（1983）；Double Machine Learning 出自 Chernozhukov 等（2018）；CausalForest 出自 Wager 与 Athey（2018）——均为【公开】；这三类方法的公开实现库主要是微软的 EconML 与 Uber 的 CausalML【公开】（两者均在 2019 年前后开源；首次发布年份、版本与许可以各自官方仓库的 Release 记录为准，可按项目名检索核验）。

#### 3.2.5 在线学习决策（Online Learning Decisioning）

- **被什么约束逼出来**：环境在变（兴趣、竞品、库存），离线训练的策略上线即开始过期；同时决策本身会改变后续拿到的数据分布。
- **结构**（循环本身简单，难的是探索配额与冷启动保护）：
```text
在线学习决策循环（Contextual Bandit 形态）
   上下文 x ──► 策略 π(a|x) ──► 选择动作 a ──► 执行
        ▲                                          │
        │                                          ▼
        └──── 更新 π ◄──── 奖励 r（可能延迟到达）◄──┘
  ────────────────────────────────────────────────
  三个必须显式设置的护栏：
    · 探索配额：ε 或不确定度阈值决定"试错"的份额
    · 冷启动：新动作先给小流量，避免直接进入主流量
    · 延迟反馈：奖励迟到时先记占位，训练时按到达时间对齐
  关键：探索的代价是真实的业务损失，不是训练成本
```
- **为什么这样设计有效**：因为策略在每个反馈到达后立即更新，所以它不需要「先攒够一批样本再上线」，能跟着环境漂移走；代价是这条路径必须持续探索，而探索份额直接对应可观测的业务损失。
- **代价**：短期指标下降（探索）；延迟反馈让更新基于过期上下文；日志与策略耦合会形成反馈回路——只推已被推过的动作，未探索动作的估计永远停在旧值。
- **失效点**：当反馈稀疏或延迟很长时，「在线自适应」会反转成「用噪声更新策略」，因为少量且滞后的奖励不足以区分动作优劣，更新方向由噪声而非信号主导——此时应退回离线策略加周期性评估。
- **量化判据**：单位时间反馈条数、反馈延迟分布（中位数与长尾）、探索份额对应的损失实测值。三者中任一撑不住，就不该让策略真做决策。
- **真实使用**：LinUCB 一类的 Contextual Bandit 方法出自 Li 等（WWW 2010，应用场景为新闻推荐）【公开】；Thompson Sampling 可追溯到 1933 年的原始论文【公开】；深度强化学习方向的代表算法 DQN（Mnih 等，Nature 2015）与 PPO（Schulman 等，2017）【公开】更常用于可大量试错的仿真或游戏环境；要把它们搬进线上决策链路，前提同样是本节「量化判据」里那三个数撑得住，而不是因为它们同属在线学习一族。

#### 3.2.6 LLM 增强决策（LLM-Augmented Decisioning）

- **被什么约束逼出来**：决策依据大量存在于非结构化材料里（政策文本、合同条款、工单、对话记录），先把它们翻译成规则的成本高于直接推理，且结论要用业务能读懂的话表达。
- **结构**（LLM 只产出候选与理由，动作由确定性代码执行——这条边界是模式成立的前提）：
```text
LLM 增强决策的契约（谁能改状态，必须写清）
   输入：非结构化材料 + 结构化上下文（必填字段缺一即拒）
        │
   ┌────▼─────────────────────────────┐
   │ LLM：给出候选动作 + 理由 + 引用原文 │  ← 只读，不写任何状态
   └────┬─────────────────────────────┘
        │  输出必须通过 schema 校验（枚举值 / 区间 / 引用可定位）
        ▼
   校验层：不合法 → 走兜底分支（转人工或保守动作）
        │
        ▼
   确定性代码执行动作 + 记录 提示词版本 / 模型版本 / 引用
   ────────────────────────────────────────────────
   关键：把"生成"和"执行"分开，模型就没有直接改状态的能力
        同一输入不保证同一输出 → 可复现性要靠版本记录补，不能靠模型
```
- **为什么这样设计有效**：因为决策依据可以被表达成自然语言，所以不必先把全部非结构化规则翻译成代码就能用上它们；代价是同一输入不保证同一输出，行为会随模型版本漂移。
- **代价**：单次调用的成本与延迟；模型版本与提示词版本必须与决策一起留痕，否则无法复现；输出是概率生成，校验层与兜底分支是必需组件而不是加分项。
- **失效点**：当决策频率升高到每秒数十次以上时，「自然语言理解」会反转成「成本与延迟不可控」，因为每次决策都要重付一遍推理成本，而规则与模型组件的边际调用成本极低——高频场景应把 LLM 移到离线一侧（生成规则、生成解释），而不是留在在线决策路径上。
- **量化判据**：单次调用成本 × 决策频率、P99 推理延迟、以及可离线批处理的比例。判定方法：把在线调用按频率排序，看前 10% 高频决策贡献了多少推理账单。
- **真实使用**：LLM-as-Decision-Maker（让模型直接出决策）、LLM-as-Rule-Generator（让模型生成规则）与 LLM-as-XAI（让模型生成解释）这三类用法的分野，正在于"谁最终裁决"落在谁身上；它们在 2023 年之后被广泛记录【经验】；这一族的用法划分见 [§ 5 前沿演进](02-decision-intelligence-section-5-ai.md) 的 5.1（那里把这一族列为 Rule-Generator、Decision-Reasoner、Decision-Maker 与 Decision-Auditor 四类），各类用法的能力边界与失败模式可按上述方法名一类关键词自行检索核验。

#### 3.2.7 Agent 决策（Agent-based Decisioning）

- **被什么约束逼出来**：一个决策要跨多个系统、多步执行（查库存 → 算运费 → 改订单 → 通知用户），单次调用或单条规则都无法覆盖。
- **结构**（护栏的每一项都要能独立拒停，而不是靠提示词里的"请不要"）：
```text
Agent 决策的状态循环 + 护栏
   目标 ──► [规划] ──► [选择工具] ──► [执行] ──► [观察] ──┐
     ▲                                                     │
     └──────────────────── 未达成且步数未超限 ─────────────┘
   ────────────────────────────────────────────────
   护栏（每一项都由外部代码强制，不由模型自行遵守）：
     · 工具白名单：能调哪些系统是配置项
     · 步数上限：超过即中止并转人工
     · 金额/范围上限：越界即中止
     · 人工确认点：不可逆动作前必须停下
     · 每步留痕：状态、工具、入参、出参全部记录
   关键：失败模式是组合级的——测试通过不代表路径穷尽
```
- **为什么这样设计有效**：因为决策被表达成「状态 + 工具调用」的循环而不是一段固定流程，所以它能复用既有系统能力、应对流程分支；代价是错误会沿调用链累积，且失败模式是组合级的，难以穷举测试。
- **代价**：可靠性与成本随步数非线性增长；可观测性要求高（每步留痕）；必须有紧急停止与回滚路径；预算通常是"每次任务"而不是"每次调用"，成本波动大。
- **失效点**：当任务从「可拆解的流程」变成「需要长程一致性的承诺」时，「跨系统协同」会反转成「不可控的累积误差」，因为每一步的小偏差都会改变后续可选的状态与工具，而系统内没有全局约束来发现偏离——只能靠外部护栏在中途截停。
- **量化判据**：步数分布（长尾步数决定成本与失败率）、每步失败率、人工接管率、越界中止次数。长尾步数是这个模式最直接的成本指标。
- **真实使用**：支撑这一模式的开源编排框架以微软的 AutoGen、LangChain 的 LangGraph，以及 CrewAI 与 MetaGPT 为代表【公开】（四者均在 2023–2024 年间公开；具体发布年份、能力与许可以各项目官方仓库的当前记录为准，可按项目名检索核验）；面向软件工程任务的自主 Agent 代表是 Cognition Labs 的 Devin【经验】（本节不对其自主程度与可靠性作断言，可按产品名与官方发布材料自行核验）；生产上的共同做法是限制步数并设置人工确认点【经验】。

#### 3.2.8 联邦 / 跨域决策（Federated Decisioning）

- **被什么约束逼出来**：决策价值最高的地方恰是数据不能出域的地方——机构之间、子公司之间、隐私合规边界两侧。
- **结构**（交换的是模型更新，不是样本；但"不搬样本"不等于"不泄露信息"）：
```text
联邦 / 跨域决策：数据留在域内，更新出域
   A 域数据 ──► 本地训练 ──► 参数 / 梯度 ΔA ┐
   B 域数据 ──► 本地训练 ──► 参数 / 梯度 ΔB ┤─► 聚合 ──► 全局模型
   C 域数据 ──► 本地训练 ──► 参数 / 梯度 ΔC ┘         │
                                                      │
                                     下发更新 ◄───────┘
  ────────────────────────────────────────────────
  关键：出域的是"信息"，不是"数据"——中间结果仍可能反推样本
        因此需要额外的隐私预算与攻击面评估，而不是一句"数据没出域"
  关键：各方数据分布不同（Non-IID）会拖慢甚至抵消聚合收益
```
- **为什么这样设计有效**：因为出域的是模型更新而不是原始样本，所以合规边界内的数据也能参与决策能力的共建；代价是隐私保护需要额外机制（如差分隐私的噪声、聚合的安全协议），而这些机制本身会削弱效果。
- **代价**：多方的协调成本（调度频率、掉队处理、退出机制）；通信往往成为瓶颈；各域监控与故障处理要协同，排障链路跨组织。
- **失效点**：当参与方数量少、且各方数据分布差异很大时，「数据不出域」会反转成「全局模型不如任一单方自训模型」，因为各方的本地更新方向互相抵消，聚合把差异当噪声平均掉了——此时增加参与方只会让情况更糟。
- **量化判据**：参与方数量、各方样本量与分布差异、通信轮数；以及隐私预算（例如差分隐私的 ε）与效果下降的对应关系。判定方法：先做一次"集中训练 vs 联邦训练"的离线对照，差值就是这个模式的实际代价。
- **真实使用**：联邦平均（FedAvg）出自 McMahan 等（2017）【公开】；跨域风控、跨域营销与跨域定价是它的主要应用场景【经验】（本章 [§ 8](02-decision-intelligence-section-8-sec8.md) 的微众银行信贷决策即把「联邦学习跨机构特征」列为三层决策链路的一层）；至于隐私边界的具体工程做法（差分隐私预算、安全聚合协议、攻击面评估），可按「跨域风控联邦学习合规」一类关键词从公开材料自行检索核验。

### 3.3 模式选择决策表

| 约束组合 | 推荐模式 | 为什么不选另一个 | 关键判据 |
| --- | --- | --- | --- |
| 强规则、合规优先、必须逐条举证 | 规则驱动（3.2.1） | 不选 ML：举证要靠事后解释，解释本身还要被质疑 | 拒绝理由能否由人预先写出并逐条评审 |
| 边界非线性、样本与标签充足 | ML 模型驱动（3.2.2） | 不选规则：条件组合数随维度爆炸 | 离线评估到线上效果的迁移差 |
| 延迟预算在百毫秒内、特征可在线取 | 实时决策（3.2.3） | 不选批量决策：结果到达时场景已结束 | P99 延迟与降级分支命中率 |
| 要对「做了会怎样」作答 | 因果决策（3.2.4） | 不选预测模型：相关不等于因果 | 是否存在可用的干预或实验来源 |
| 环境快变、反馈即时且量大 | 在线学习（3.2.5） | 不选离线模型：上线即开始过期 | 单位时间反馈量 ÷ 反馈延迟 |
| 依据在非结构化材料、决策频率低 | LLM 增强（3.2.6） | 不选规则：翻译成本高于直接推理 | 单次调用成本 × 决策频率 |
| 决策跨多系统、需要多步执行 | Agent 决策（3.2.7） | 不选单次调用：任务无法一次完成 | 步数分布与人工接管率 |
| 数据不能出域、需多方共建能力 | 联邦 / 跨域（3.2.8） | 不选集中式：合规不允许，最优解在可行域之外 | 参与方数量与分布差异 |

**本主题下最常被误选的一对，是规则驱动与 LLM 增强这两个极端**。在强规则场景（限额、名单、审批门槛）用 LLM，得到的是高昂的单次成本、不可复现的输出，以及一份监管无法接受的举证材料；而在依据大量存在于非结构化材料里的场景（政策解读、工单归类、合同条款比对）硬写规则，得到的是一个永远追不上文本变化的规则库——**两种误选的共同点是：把"约束"当成了"技术偏好"**。判据很简单：如果决策依据能被人预先写成条件并逐条评审，就用规则；如果依据必须先被读懂才能变成条件，就用 LLM 生成候选、由确定性代码裁决。

另一种高频误选是**把离线模型直接接到在线链路**：线下评估良好、线上效果断崖。它通常不是模型问题，而是约束不匹配——离线训练看到的特征分布与线上推理时刻能拿到的特征不一致。识别方法见 3.5 的第三条反模式。

### 3.4 组合模式：真实系统不会只用一种

**组合 1：硬规则兜底 + 模型判别 + 策略映射（三层流水线）**

- **组合构成**：第一层硬规则处理零容忍条件（名单、限额、硬性合规）；第二层模型输出风险概率与特征贡献；第三层策略把概率映射成动作（放行 / 加验证 / 转人工 / 拒绝）。
- **职责边界**：**「必须拦住」归规则，「需要权衡」归模型，「代价取舍」归策略**——三层各自可解释性来源不同（命中规则 ID / 特征贡献 / 命中分支），因此举证时能说出是哪一层做的决定。
- **运维代价**：三层都要有版本与灰度机制；策略层变更频繁，必须与模型版本解耦，否则一次阈值调整会与模型上线混在一起无法归因。
- **适合规模**：决策错误有直接资金或合规后果的场景（金融风控、授信、保险理赔），从中小到超大规模都适用。

**组合 2：离线模型出分 + 在线校准阈值**

- **组合构成**：模型保持离线训练（保证特征一致性与可评估），在线只做校准——按实时反馈调整动作阈值或按比例分配流量。
- **职责边界**：**模型负责排序，校准负责取舍**；在线部分不改变模型的判断，只改变"多少分以上才动作"。
- **运维代价**：需要一套能回填奖励的日志链路；校准策略要有探索配额与熔断，否则会朝短期指标过拟合。
- **适合规模**：反馈延迟以小时到天计、不足以支撑端到端在线学习的场景——这是绝大多数业务的现实状态。

**组合 3：LLM 生成候选 + 规则或模型裁决 + Agent 执行 + 人工确认点**

- **组合构成**：LLM 读懂非结构化材料并给出候选动作与理由；规则或模型做最终裁决；Agent 负责跨系统执行；不可逆动作前设人工确认。
- **职责边界**：**LLM 只读不写、Agent 只执行不裁决、人只在不可逆节点介入**——三者权限分离，任何一环失效都不会直接导致状态被改错。
- **运维代价**：三套组件的版本与留痕要对齐（提示词版本、模型版本、工具版本），排障要能把一次业务结果还原到具体的提示词与裁决分支。
- **适合规模**：低频、高价值、依据文本化的决策（合同审阅、理赔初审、复杂客服工单）。

组合的第一原则是**把"生成"与"执行"分开**：只要有组件能直接改业务状态，就必须有独立于它的裁决与留痕。组合的第二原则是**在不可逆的地方留人**：自动化率在可逆决策上是效率指标，在不可逆决策上是风险指标。

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么团队会写成这样） | 修法 |
| --- | --- | --- | --- | --- |
| 规则膨胀 | 规则条数持续增长，没人说得清某条规则是否还有人依赖；改一条要评审一周 | 规则之间的交互（优先级、互斥遗漏）无法从单条读出，系统仍"可解释"但已不可维护 | 每次业务变更都以"再加一条规则"落地，缺少退出机制 | 建规则治理：Owner + 版本 + 评审 + 定期清理；把部分判断下沉到模型 |
| 模型黑盒上线 | 线上效果回退时只能整体关掉模型；监管问"为什么拒绝"答不出个体理由 | 没有留痕与解释，模型无法归因、无法灰度对照、无法回滚到具体版本 | 交付压力下先上线、解释与留痕留作 TODO | 决策留痕表 + 解释方法 + 影子对照；上线前先能回答"这一条为什么" |
| 离线模型直接实时用 | 线下评估好、线上效果断崖；同一用户线上线下的特征值对不上 | 训练与推理的特征分布不一致，模型在线上看到的是没见过的输入 | 离线与在线两套特征实现，且缺少一致性校验 | 特征同源（同一份定义与同一条加工链路）+ 线上分数与离线复算的一致性监控 |
| 决策与执行脱节 | 决策系统输出清单，运营手动执行；执行结果不回流 | 决策到执行之间没有闭环，效果数据缺失，模型无法迭代 | 决策系统被当成"分析工具"而不是"业务链路的一环" | 决策 → 执行 → 反馈闭环；执行结果必须回写到决策日志 |
| 不可量化 | 决策上线后说不清带来多少收益；指标变动归因不到决策 | 无法判断该保留还是回滚，资源分配靠主观 | 缺少实验框架与效果归因，决策 ROI 没有定义 | 所有决策变更走 A/B 或准实验；定义决策 ROI 并在上线前写明判据 |
| 盲目 LLM 决策 | 推理账单与延迟随流量线性上涨；简单规则类决策也在调用模型 | 每次决策都重付推理成本，而高频场景的边际成本本应极低 | 把"LLM 是趋势"当成选型理由，未按频率与可解释性分场景 | 按场景选型：高频 / 实时 / 规则明确用规则加模型；复杂 / 模糊 / 跨域 / 低频用 LLM（两条判据并存：频率与时效决定它进不进在线链路，依据形态与领域跨度决定它该不该用 LLM） |
| LLM 幻觉决策 | 决策理由引用了不存在的条款；同一输入多次输出不一致 | 输出是概率生成，未经校验的结论会被当成事实执行 | 缺少知识兜底与输出校验，把模型输出直接当结论 | RAG 或知识库兜底 + 输出 schema 校验 + 引用可定位 + 决策审计 |
| Agent 不可控 | 出现超出白名单的工具调用；出事后无法逐步复盘 | 失败模式是组合级的，没有全局约束能发现偏离，只能事后发现 | 把护栏写在提示词里而不是外部代码里 | Human-in-the-Loop + 步数与金额上限 + 全步留痕 + 紧急停止与回滚 |
| A/B 实验缺失 | 决策效果靠"感觉变好了"；两个版本谁更好说不清 | 没有对照组，任何变化都无法归因，策略在噪声上迭代 | 实验框架建设滞后于决策系统建设 | 决策变更必须可 A/B；不可实验的场景用准实验设计与因果估计 |
| 决策与业务脱节 | 系统上线后使用率低，业务仍按老办法走 | 决策没有被嵌入业务流程，反馈链断裂，系统自然衰减 | 立项时按 IT 项目推进，业务方只在验收时出现 | 一把手工程 + 业务深度参与；把决策点写进业务流程与考核 |

最危险的四个反模式是这样暴露在生产里的。

**A/B 实验缺失**（含它导致的「不可量化」）最致命之处在于它让其他所有问题都不可被发现：没有对照组，模型衰减、特征不一致、阈值调错都表现为"指标有些波动"，无法归因，于是系统只能在有人抱怨时才被动调整。**它的暴露方式通常是"所有人都觉得效果在变差，但没人能证明"**——等到能证明时，往往已经过了几个季度。

**规则膨胀**的危险在于它与"可解释"这个卖点反向而行：系统依然能对每一次决策给出理由，但没人能预测改动的后果，于是变更速度降到零，业务绕开系统自行处理例外——**规则库最终变成一份没人维护的合规摆设**。

**LLM 幻觉决策**与**Agent 不可控**是同一类问题的两种尺度：前者是单次输出不可靠，后者是多步累积不可控，共同点是**把模型的输出直接当成了系统的动作**。修法也是同一条原则——**生成与执行分离，且在不可逆动作前留一个确定性校验或一个人**。

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 原模式 | 为什么开始疼 | 换成 | 迁移的代价 |
| --- | --- | --- | --- | --- |
| 频率从每天升到每秒 | 批量决策（离线跑批出清单） | 结果产出时场景已经结束，时效性归零 | 实时决策（3.2.3） | 在线特征存储 + 常驻集群 + 降级分支，运维形态从跑批变成值班 |
| 依据从可枚举变成文本化 | 规则或模型 | 政策与话术变化快于规则更新，每次变更都要一次发布 | LLM 生成候选 + 确定性裁决（3.2.6） | 成本与延迟进入在线链路，需要校验层与版本留痕 |
| 决策从可逆变成不可逆 | 全自动决策 | 错误无法追回，且逐条举证成为硬要求 | 加人工兜底（分态处理，如转人工） | 决策延迟上升、自动化率下降，需要一套"转人工"的运营流程 |
| 反馈从即时变成滞后 | 在线学习 | 奖励迟到，更新方向由噪声主导 | 离线模型 + 周期评估（3.2.2） | 放弃实时自适应，改为主要靠离线迭代与准实验评估 |
| 从单域到跨域 | 集中式训练 | 数据不能出域，最优解落在可行域之外 | 联邦 / 跨域决策（3.2.8） | 通信与协调成本、隐私预算带来的效果折扣 |
| 目标从单一变成多目标 | 单目标模型 | 优化一个目标会牺牲其他目标，模型之间互相打架 | 多任务多目标建模（见 [§ 6 案例 2.2](02-decision-intelligence-section-6-sec6.md)） | 样本与训练成本上升，多目标权重成为需要持续运营的参数 |
| 规则条数从百到万 | 纯规则引擎 | 条件组合数失控，改动影响无法预测 | 规则分层 + 模型承接部分判断 | 需要重新划分"谁判断什么"，并把历史规则逐条判定去留 |

跃迁的共同规律是：**触发点几乎总是"问责结构变了"或"反馈速度变了"，而不是"数据量变大了"**。一个决策从可逆变不可逆，就足以要求引入人工兜底；反馈从即时变滞后，就足以让在线学习退场。所以判断该不该换模式，要问的是：这个决策错了以后谁承担、多久能知道结果。

### 3.7 自检清单

- [ ] 每一个自动执行的决策，都能在事后的日志里还原出「命中的依据 + 当时的特征 + 模型/提示词版本」吗？
- [ ] 决策日志里记录的，是推理时刻的特征快照，还是事后回查得到的当前值？后者不能用于归因。
- [ ] 决策链路里有没有「零容忍」条件被交给模型去学？模型无法保证绝对约束。
- [ ] 在线推理与离线训练用的特征是否同一份定义、同一条加工链路？做过一致性校验吗？
- [ ] 每条规则是否有 Owner、版本与最近一次评审日期？有没有一条"没人敢删"的规则在挡住变更？
- [ ] 每一次决策变更有没有对照组？说不清基线的变更应该视为未验证。
- [ ] 高频决策里有没有混进 LLM 调用？推理账单按决策频率排序后，前 10% 占比多少？
- [ ] LLM 的输出是否经过 schema 校验并能定位到原文引用？校验不通过时有没有兜底分支？
- [ ] Agent 的工具白名单、步数上限、金额上限是写在外部代码里，还是写在提示词里？
- [ ] 不可逆动作之前，是否存在一个人工确认点或确定性校验？没有的话，这一步是谁批的？
- [ ] 模型输出到最终动作之间的策略层，是否与模型版本解耦（阈值改动不必重训模型）？
- [ ] 有没有一个明确的判据，说明「这个决策模式该被换掉」？写不出判据，就等于取消了退出机制。

### 3.8 小结

| 你的约束 | 建议模式 | 关键理由（机制层面） |
| --- | --- | --- |
| 必须逐条举证、条件可预先写出 | 规则驱动（3.2.1） | 依据是显式的一等公民，可版本化、可评审 |
| 边界非线性、举证要求可用解释满足 | ML 模型驱动（3.2.2） | 由样本拟合高维交互；代价是理由需事后构造 |
| 延迟预算百毫秒内 | 实时决策（3.2.3） | 分段超时 + 降级分支，链路延迟由最慢依赖决定 |
| 要回答「做了会怎样」 | 因果决策（3.2.4） | 估的是干预分布下的差异，不是条件相关 |
| 环境快变、反馈即时 | 在线学习（3.2.5） | 反馈到达即更新；代价是探索的业务损失 |
| 依据文本化、频率低 | LLM 增强（3.2.6） | 省掉把非结构化材料翻译成规则的成本 |
| 跨系统多步执行 | Agent 决策（3.2.7） | 状态加工具循环可组合既有能力；代价是组合级失败 |
| 数据不能出域 | 联邦 / 跨域（3.2.8） | 交换更新而非样本；代价是隐私预算与 Non-IID 折损 |

> 本节小结：本主题下决定模式选择的**唯一那条约束，是"决策做错了以后，代价由谁承担、能不能补救、事后能不能举证"**——它同时决定了黑盒能不能用、人工兜底要不要留、LLM 与 Agent 的护栏必须多厚。反馈速度是第二条约束，它决定的是模式能走多快（规则 / 离线模型 / 在线学习），而不是能走多远；把这两条混为一谈，就会得到"上了最前沿的算法，却没人敢让它真做决策"的系统。
