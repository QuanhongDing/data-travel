## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

「决策延迟 5 分 vs 2 分」读起来像是在说某个方案在延迟上"更好"。但延迟从来不是某个技术的属性，而是整条链路的属性：**决策延迟 = 取数延迟 + 推理延迟 + 执行延迟**。规则引擎的推理耗时可以忽略，可它的输入如果是 T+1 的宽表，端到端延迟仍然是小时级；反过来，一个笨重的模型如果输入是内存里的实时特征，端到端反而更快。打分表打的其实是"打分者心里的那个场景"。

同一维度在不同场景里的权重会**相反**。做信贷反欺诈，毫秒级响应是硬约束、可解释性是监管门槛；做优惠券发放，秒级响应完全够用，错发一次可以次日召回，可解释性几乎无人追问。于是「可解释性 4 分还是 5 分」这类结论在你的场景里没有可迁移性。

更隐蔽的一层：打分表的维度是「能力」，候选之间的真实差别却在「机制」。规则引擎的学习能力得低分，不是它"做得差"，而是它的决策函数里根本没有"从数据中学习"这个环节——它的每条分支都是人写下的条件。把它与多臂老虎机放进同一列打分，等于用老虎机的坐标系去量一把尺子。**能力分不告诉你为什么，机制才告诉。**

还有一条副作用：打分表会让人以为选型是"多选一"。真实工程里绝大多数线上决策是分段的——规则管兜底与硬约束、模型管排序、实验负责验证"改了到底有没有用"，三段并存。表格式打分会把讨论引向"该不该整个换成决策智能"，而真正该问的是"这条链路的哪一段该由哪一族负责"（§7.6 给出八种常见组合）。

所以本章改用 6 条判据，它们问的都是"在你的约束下会怎样"，而不是"这个技术有多强"：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| 错误的可逆性 | 决策错了，多久能纠正 | 不可逆错误（放贷、拒保、定价）把可解释性从"加分项"变成"准入条件" |
| 举证义务 | 谁需要解释、向谁举证 | 有外部举证义务时，事后归因不等于决策依据 |
| 决策频率与延迟预算 | 每天多少次、P99 允许多少毫秒 | 频率决定单位成本能否被承受（见 §7.4 成本函数） |
| 反馈闭环速度 | 从决策到看到结果要多久 | 没有回流就没有标签，监督学习无从下手 |
| 选择偏差是否存在 | 历史数据是否只覆盖"被决策过的人" | 监督模型学的是 P(Y\|X)，不是 P(Y\|do(X)) |
| 组织承载能力 | 需要哪几类角色常驻 | 因果与在线学习都要实验平台，没平台就只能停在规则与模型 |

### 7.2 候选方案全景

| 方案 | 定位 | 核心机制（一句话） | 代表实现 / 应用形态或行业使用者 | 许可 / 商业模式 |
| --- | --- | --- | --- | --- |
| 规则引擎 / 决策表 / DMN | 确定性决策 | 事实与规则的增量模式匹配，命中即输出 | Drools、Camunda DMN、IBM ODM、Apache Urule、QLExpress、Aviator、Easy Rules、Groovy | 开源为主，企业版商业 |
| BI / DSS | 人做决策的辅助 | 聚合与可视化，决策权留在人手里 | 报表体系、Cognos、BO、MSTR 等 | 商业软件 |
| ML 模型决策 | 统计拟合决策 | 用参数化函数拟合标签分布 | 信贷评分卡、CTR 预估、反欺诈 | 自研 / 云 AI 平台 |
| 实时决策（RTD） | 秒到毫秒级决策 | 流式特征与在线推理在同一条流水线上 | Flink + 实时规则 + 在线模型（FTRL 系） | 开源 + 自研 |
| 因果决策 | 辨识"做了会怎样" | 用识别策略估计 E[Y\|do(X)] | DML、CausalForest、IV、DID、PSM | 开源库 + 自研 |
| 在线学习决策 | 边决策边学习 | 用探索流量换取新策略的收益估计 | MAB（Epsilon-Greedy / UCB / Thompson Sampling）、Contextual Bandit（LinUCB）、RL（DQN / PPO / SAC） | 开源 + 自研 |
| 推荐系统 | 决策智能在"排序"上的垂直实现 | 召回 + 排序 + 重排的三段式 | 电商、内容、广告 | 自研 |
| 风控系统 | 决策智能在"风险"上的垂直实现 | 规则 + 模型 + 名单 + 人工复核的组合决策 | 银行、支付、保险 | 自研 / 商业风控 |
| LLM 增强决策 | 用语言模型介入决策 | 把决策表达成自然语言推理与生成 | LLM-as-Rule-Generator / Reasoner / Maker、CoT | API 或自部署 |
| Agent 决策 | 多步自主决策 | 由模型规划步骤并调用工具，观察后继续 | AutoGen、CrewAI、LangGraph、MetaGPT | 开源框架 |
| 知识图谱增强 | 决策依赖显式关系 | 把实体与关系显式存起来供推理 | 金融 KG、医疗 KG、制造 KG | 自研 |
| 决策智能平台 | 把上述能力平台化 | 统一决策上下文、决策日志与治理 | Diwo、Aera Technology、Zeta Global、Tellius、Quantiphi、Pecan AI、阿里决策引擎、字节智能决策、蚂蚁决策大脑 | 商业 SaaS / 商业许可 |

（该列按候选各自最可指认的对象填写：规则引擎、Agent、平台类填代表实现或厂商，推荐、风控、知识图谱类填应用形态与行业；横向比较时以「核心机制」列为准，不要跨语义读这一列。表中开源项目与框架的具体许可证，请以各项目仓库的 LICENSE 文件当前版本为准。）

这些候选其实只分四族，分族依据就是 §7.3 的第一条机制——**判断依据落在哪里**：**显式符号族**（规则引擎、决策表、DMN、知识图谱增强，以及 BI/DSS 里被固化成条件的那部分——判断依据都是人写下或人工审核过的符号，只是存放位置从 if-then 换成了决策表或图上的关系模式）、**统计拟合族**（ML 决策、实时决策，以及推荐系统与风控系统这两个垂直实现）、**因果与序贯实验族**（因果决策、A/B 实验、MAB/RL）、**语言与自主族**（LLM 增强、Agent，以及把它们捏合起来的决策智能平台）。同族内部差异小、跨族差异大——先分族再选，能省掉一半比较。

知识图谱增强归入显式符号族而不是语言族，理由在那条机制上：它的价值来自「实体与关系被显式存起来供推理」（见上表），判断依据同样写在系统之外、可被第三方沿着路径复算，这与语言模型的隐式权重不是同一族。正因为它同时落在「匹配方式」与「举证」两个机制维度上，本节在 §7.3.1 与 §7.3.4 各为它留了一行。

四族的成熟时间差得很多，这决定了"能买到什么"：规则引擎商业化在 2005–2010 年前后（主文件 §1.4 的演进线），统计拟合族在 2011 年之后随梯度提升树普及，实时决策与因果方法在 2017–2020 年成型，决策智能作为一个概念被 Gartner 列入十大战略科技趋势（【公开】Gartner, *Top 10 Strategic Technology Trends for 2022*），LLM 与 Agent 决策则集中在 2023 年之后。越靠后的族，公开的工程实践越少、可参考的失败样本也越少——这不是能力差距，而是**时间差距**，选型时要把"我要承担多少没有先例的风险"单独算一笔账。

族内替换通常只需换组件（换一个规则引擎、换一个向量化的打分模型），跨族替换往往要重建上游（从"有标签即可"变成"要有实验平台"，或从"批处理"变成"流式特征"）。这就是为什么 §7.7 的迁移成本表按"跨族"来标量级。

### 7.3 机制差异：为什么它们表现不同

#### 7.3.1 规则的匹配方式：RETE 网络 vs 参数化函数

**机制是什么**：规则族的决策函数是 `if-then-else` 的布尔组合，引擎用 RETE 类算法在事实集合上做增量匹配——把条件拆成 alpha/beta 网络节点并共享中间结果，避免为每条规则重扫全部事实；同族的图谱路线把同一批条件改存成实体与关系，用图上的模式与路径匹配替代 RETE 的增量匹配；ML 族的决策函数是参数化函数 `f(x; θ)`，判断能力被压缩进参数。

**各候选的实现差异**：

| 候选 | 规则的载体 | 判断落在哪里 | 冲突怎么处理 |
| --- | --- | --- | --- |
| 规则引擎 | DRL / 决策表 / DMN 图 | 人写的条件，逐条可读 | 显式的优先级与命中策略 |
| 决策表 | 行 = 决策，列 = 条件 | 表格即依据 | hit-policy（FIRST / PRIORITY 等） |
| 知识图谱增强 | 实体—关系图上的模式与路径 | 人写或人工审核的实体与关系 | 图上的约束与路径优先级 |
| ML 决策 | 特征 + 权重或树结构 | 训练数据，人读不出来 | 概率融合，无显式冲突 |
| LLM 决策 | 提示词 + 模型权重 | 两者都不可逐条核对 | 靠提示词约束，无强制机制 |

```text
显式符号族（规则路线）：判断依据在系统之外（人写的）
  事实（facts）──► alpha 网络（按单个条件筛）──► beta 网络（按条件组合连接）
                                                     │ 共享中间匹配结果
                                                     ▼
                                          命中规则 ──► 冲突消解 ──► 动作
  改一条规则 = 改一次网络结构 = 一次可评审、可回滚的变更

拟合族：判断依据在系统之内（数据学的）
  特征 x ──► f(x; θ) ──► 分数 ──► 阈值 ──► 动作
  "为什么是这个分数" 无法从 θ 里读出来，只能事后归因重建
  ── 举证场景要的不是"模型很准"，是"这一条依据可以被第三方复算"
```

**由此必然导出的性质**：因为规则决策的每个分支都能追到一条人写的条件，所以它天然可以被举证与审计——监管能逐条读懂它为什么拒了这笔申请；代价是规则集的维护成本由人来付，规则数与变更频率相乘就是长期人力，而且新增规则会与既有规则冲突，冲突检测也只能在规则集层面人工或半自动地做。

反过来，因为 ML 决策把判断压进参数，所以它能覆盖人写不出条件的高维交互（几十个特征之间的联合分布），代价是可解释性必须靠事后归因重建（SHAP、LIME、反事实解释），而事后归因刻画的是"模型对这些特征有多敏感"，不等于"这次决策的法定依据"。

图谱路线与规则同源但代价不同：因为它的判断依据也是人写下（或人工审核）的显式符号，所以它的可举证性与规则相当——第三方沿着"实体—关系—实体"的路径就能复算；代价是这份依据的表达力被"关系能表达什么"限制住，需要多个特征联合计算才成立的判断写不出对应的关系模式，而且实体消解一旦出错，路径再清晰也是错的。

**公开证据**：RETE 匹配算法由 Charles Forgy 在 1982 年发表于 *Artificial Intelligence*（【公开】Forgy, 1982）；OMG 的 DMN 把决策模型定义为可交换的图形化标准（【公开】OMG DMN 1.0，2015）；Drools 对 DRL、决策表与 DMN 的支持可在其官方文档中核验。

**失效条件**：当"判断依据"本身必须从数据里学出来——比如欺诈手法的变化速度超过了规则评审周期——规则族的成本优势就消失了：人写规则的速度追不上对手。

#### 7.3.2 延迟由谁决定：在线推理、离线打分，还是人工回路

**机制是什么**：三段的量级差距通常比候选之间的推理速度差距大得多。规则与请求上下文里已有的字段就能完成判断；离线打分要等 T+1 宽表；实时决策把特征计算搬进同一条流；LLM/Agent 则要经过检索或工具调用，且步数不受控。

| 候选 | 取数 | 推理 | 执行 |
| --- | --- | --- | --- |
| 规则引擎 | 通常是请求上下文里的字段 | 微秒到毫秒级 | 同步返回 |
| ML 决策（离线评分） | T+1 宽表 | 批量作业 | 次日生效 |
| 实时决策 | 流式特征（流计算 + 消息队列 + 在线存储） | 在线模型（FTRL 系） | 同步返回 |
| LLM / Agent 决策 | 检索与工具调用 | 数百毫秒到数秒、步数不定 | 同步或异步 |

```text
同一条决策链，延迟落在哪一段决定了谁能上
  请求 ──► 取数 ──────────► 推理 ──────► 执行 ──► 生效
            │                 │
            │                 ├─ 规则：微秒–毫秒     ← 瓶颈不可能在这里
            │                 ├─ 小模型：毫秒–十毫秒  ← 需要批量与并发
            │                 └─ LLM：数百毫秒–数秒    ← 且步数不受控
            │
            ├─ 请求上下文：毫秒
            ├─ 实时特征流：秒
            └─ T+1 宽表：小时      ← 规则再快也救不回这一天
  ── 先量出瓶颈在哪一段，再谈换哪一族；否则换来的只是"更快的那一段更快了"
```

**由此必然导出的性质**：因为规则只需要请求上下文里的字段，所以它的推理延迟可以低到不成为瓶颈，代价是判断能力被限制在"人能写进条件里的特征"上——一旦决策要依赖几千维的实时行为序列，规则就写不出来。

因为实时决策把特征计算放进了同一条流，所以特征与决策之间不再有批处理边界，端到端延迟从小时级压到秒级；代价是训练口径与服务口径必须严格一致（训练-服务偏差），而这条一致性靠纪律维持不住，只能靠特征平台把"同一份定义同时产出离线特征与在线特征"变成机制保证。

因为 LLM 的延迟与 token 成本都随上下文长度增长，所以它在延迟预算里占的是"每步数百毫秒起、且步数不受控"的位置，代价是它很难进入 P99 只有个位数毫秒的主决策路径——阈值推导见 §7.5。

**公开证据**：流式状态与复杂事件处理能力可在 Flink 官方文档中核验；FTRL-Proximal 作为在线学习方案在 CTR 预估场景被公开报告（【公开】McMahan et al., *Ad Click Prediction: a View from the Trenches*, KDD 2013）。

**失效条件**：决策频率低（例如每日一次批量分群）时，实时栈的常驻成本换不来收益，此时离线打分更快也更便宜。

#### 7.3.3 学习信号从哪来：监督标签、反事实，还是在线反馈

**机制是什么**：三族拿到的学习信号根本不同。监督学习拿历史标签，拟合 P(Y|X)；因果方法估计 E[Y|do(X)]——DML 用 Neyman 正交化先把高维混杂残差掉，再估因果系数；在线学习拿交互反馈，每一步都要在探索与利用之间分配流量，RL 则把决策序列当成整体去优化累计回报。

| 族 | 优化目标 | 数据从哪来 | 新策略上线的判据 |
| --- | --- | --- | --- |
| 监督学习 | 拟合 P(Y\|X)，最小化预测损失 | 历史决策日志 + 结果回流 | 离线指标 + 小流量试点 |
| 因果推断 | 估 E[Y\|do(X)]，含人群异质性 | 观察数据 + 识别策略，或实验数据 | 效应显著且方向稳定 |
| MAB / Contextual Bandit | 最大化累计收益，最小化 regret | 在线交互反馈 | 无需事先判据，线上自动收敛 |
| RL | 最大化序贯累计回报 G = Σ γᵗ rₜ | 在线交互 + 奖励函数设计 | 离线策略评估 + 仿真 + 限量上线 |

**由此必然导出的性质**：因为监督模型学的是 P(Y|X) 而不是 P(Y|do(X))，所以当历史数据只覆盖"上一版策略选中过的人"时，它把这些人的结果当成了全部真相——策略一换，样本分布就变，模型精度按定义不再有保证。这就是因果决策存在的理由，不是它的可选加分项。

因为 MAB 必须用掉一部分流量去探索，所以它能在环境变化中学到新策略，代价是探索本身消耗业务指标（regret）：这个比例需要组织层面接受，而不是工程层面调参——很少有人愿意为一个可能要几个月才回本的策略，长期让出可观比例的流量。

**公开证据**：潜在结果框架通常归于 Rubin 1974（【公开】Rubin, *Journal of Educational Psychology*, 1974）；Double Machine Learning 的系统化表述见 Chernozhukov 等（【公开】*The Econometrics Journal*, 2018）；Thompson Sampling 的原始文献是 1933 年发表于 *Biometrika* 的论文（【公开】Thompson, *On the Likelihood that One Unknown Probability Exceeds Another in View of the Evidence of Two Samples*, *Biometrika*, 1933）；UCB 的经典分析见 Auer 等发表于 *Machine Learning* 的论文（【公开】Auer et al., *Finite-time Analysis of the Multiarmed Bandit Problem*, *Machine Learning*, 2002）。

**失效条件**：决策频率过低（一年几十次）时，探索要么看不见效果、要么代价过大，此时只能退回到 A/B 实验加人工评审。

#### 7.3.4 举证责任落在谁身上：谁能解释，解释给谁看

**机制是什么**：可解释性的强度由解释的来源决定。规则的解释就是"命中的那条条件"，第三方读到条件即可复算；加性/评分卡的解释是"各项分值之和"，逐项可核；ML 的解释是事后归因；LLM 的解释是另一段生成文本。

| 解释来源 | 解释的形式 | 第三方能否复算 |
| --- | --- | --- |
| 规则 / DMN | 命中的那条规则 | 可以，读到条件即可 |
| 知识图谱 / 关系路径 | 命中的那条实体—关系—实体路径 | 可以，读到路径即可（前提是图谱版本与本次查询可复现） |
| 评分卡 / 加性模型 | 各项分值之和 | 可以，逐项可核 |
| 树模型 / 深度模型 | SHAP / LIME / 反事实 | 部分可以，依赖归因方法与采样 |
| LLM | 自然语言理由 | 不能，理由与计算之间没有映射关系 |

**由此必然导出的性质**：因为 LLM 给出的理由是"另一个生成结果"而不是对决策计算的逆映射，所以它可以读起来通顺却与实际判据无关，代价是在有举证义务的场景（拒贷理由、保险定价、内容处置申诉）不能单独拿它当依据，必须由规则或可加性模型给出可复算的那一部分。

因为规则、图谱与评分卡的"解释形式"与"计算形式"是同一个东西，所以它们的可解释性没有额外成本；代价是这份解释能力被"能写进表单或写成关系"这件事限制住——需要复杂交互的判断它表达不了。

还有一条所有候选共有的约束：举证与复盘要回答的往往是**回溯性**问题（"三个月前这笔为什么这么判"），所以决策当时的上下文必须与决策结果一起落库——否则几个月后即使有解释方法，也无从重放。代价是决策日志本身变成一项需要长期保留、脱敏与权限治理的数据资产。这一条把"选哪一族"拉回到同一个前提：没有决策日志，任何解释都只是事后重算。

**公开证据**：欧盟 GDPR 对"仅基于自动化处理、并对个人产生法律或重大影响的决策"设有专门约束（【公开】EU GDPR 第 22 条，2018 年 5 月起适用）；《中华人民共和国个人信息保护法》（【公开】2021 年 11 月 1 日施行）对自动化决策提出透明度与说明义务。具体条款请以监管机构发布的现行文本为准。

**失效条件**：内部排序优化、内容推荐这类没有外部举证义务的决策，可解释性的权重会大幅下降——错误代价是"少赚"，不是"违规"。

### 7.4 成本结构对比（不是价格表，是成本函数）

把决策成本写成函数，比给一个总价有用得多：

```
年成本 ≈ 决策量 × 单次推理成本
        + 特征供给成本（平台人力 + 常驻计算）
        + 规则 / 模型维护成本（人力 × 变更频率）
        + 人工复核成本
        + 决策错误的期望损失
```

| 候选 | 主导项（成本随什么增长） | 隐性成本 |
| --- | --- | --- |
| 规则引擎 | 规则集维护人力，随规则数 × 变更频率增长 | 规则冲突与回归测试；线上单点手改造成的口径漂移 |
| ML 决策 | 特征管道与训练流水线的固定团队，推理边际成本趋零 | 训练-服务偏差导致的线上衰减；重训与回滚流程 |
| 实时决策 | 常驻流计算资源（按峰值配置的并行度） | 状态存储与背压治理；同口径特征的离在线双份维护 |
| 因果决策 | 实验流量成本（对照组让出的业务价值）+ 分析人力 | 识别假设被业务变化破坏后的返工 |
| MAB / RL | 探索遗憾 | 探索期指标下滑的组织解释成本 |
| LLM 决策 | token 成本，与上下文长度 × 调用次数成正比 | 延迟不可控、输出不稳定，需要额外兜底与限流 |
| Agent 决策 | 多步工具调用累计的 token + 工具自身成本 | 步数方差大，成本上限难预估 |
| 推荐 / 风控系统（垂直实现） | 与实时决策同构：常驻流计算 + 在线存储 | 垂直系统往往自带一套特征与日志，与平台打通是额外的一次性成本 |

一个关键结论：**只有 LLM/Agent 这一族的单位决策成本是显著非零、且随决策量线性增长的**；其余各族的边际推理成本都趋近于零，成本主要发生在决策之前（建特征、建规则、建实验）。这直接决定了 LLM 该放在链路的哪个位置。

还要把成本表按"峰值 / 均值"的比值重排一次：规则、模型、流计算集群的容量都是按峰值预先配置的（低峰期闲置、高峰期可能被限流），LLM 的账单则按实际发生量结算（高峰期价格不变、但延迟会恶化）。峰值比越大，按容量买的方案越吃亏、按次结算的方案越占优——这是除单价之外的第二个选型变量。

【推算】设单次决策调用前沿档模型，输入约 4,000 token、输出约 500 token，每天 100 万次决策：

```
日成本 = 1,000,000 × (4,000 × P_in + 500 × P_out)
       = 4×10⁹ × P_in + 5×10⁸ × P_out      （P 为每 token 单价）
```

取 P_in = $3 / 百万 token、P_out = $15 / 百万 token（前沿档位的数量级，实际以厂商当期定价页为准），则日成本 ≈ 1.2 万美元 + 0.75 万美元 ≈ **每天 2 万美元量级**；换成小模型档位（单位 token 价格低一到两个量级），同一调用量降到**每天百美元到千美元量级**。而同样 100 万次决策，由规则或小模型承担时，成本是一份被决策量摊薄的固定集群成本，不随决策次数变化。

【推算】实时决策还有一项隐性成本来自峰值配置：若峰值 QPS 是均值的 5 倍，流计算资源按峰值规划，则单位决策摊到的计算成本约为按均值配置的 5 倍——这是"按买峰值的方式买平均吞吐"，只能靠弹性伸缩缓解，不能靠优化算子消除。

### 7.5 决策树（每个分支都要有阈值依据）

```
[这一步决策错了，能在下一个决策周期内纠正吗？]
   │
   ├── 不能，且需要向外部举证
   │      → 规则 / 评分卡给出可复算的依据 + 模型辅助（LLM 不单独决策）
   │
   └── 能纠正
        │
        ├── 决策量 ≥ 每秒千次（P99 预算落在毫秒级）？
        │      ├── 是 → 主路径推理形态锁定为 规则 / 小模型在线打分（LLM 不进主路径）
        │      └── 否 → 主路径推理形态可为模型或 LLM（仍受成本与举证约束）
        │        ── 这一问只约束"谁来算"，不约束"策略怎么学"：两条都继续向下选族
        │
        ├── 能否取回历史决策的结果变量？
        │      ├── 否 → 先建决策日志与结果回流，此阶段不要上监督模型
        │      └── 是 ↓
        ├── 历史数据是否只覆盖"被上一版策略选中过的人"（存在选择偏差）？
        │      ├── 是 → 因果决策（识别策略 + A/B 验证）
        │      └── 否 ↓
        ├── 环境变化是否快于你的重训周期？
        │      ├── 是 → 在线学习（MAB / Contextual Bandit）＋按上面锁定的推理形态服务
        │      └── 否 → 定期批量重训足够
        └── 决策步骤能否事先枚举？
               ├── 否 → Agent 决策 + 规则兜底（硬约束与紧急停止）
               └── 是 → 工作流 / DAG 编排，不必上 Agent
```

**阈值依据**：

读这棵树的方式是自上而下：第一问决定"你被允许用哪一族"，第二问只决定主路径上"谁来算"（推理形态），其后各问才在族内做细分工。如果第一问的答案是"不可逆且要举证"，后面几问的答案不改变结论——这就是"判据有先后"与"打分表可加权平均"的根本区别。第一问是一个合取条件（不可逆 **且** 要举证），它的两个子条件在下文各有一条依据。

- **「能在下一个决策周期内纠正」**：不是规模阈值，而是错误代价的结构——发错券可在次日回收，放错贷只能核销或转让。落地测试是：这笔损失能否在业务闭环的下一个周期里被自动逆转。
- **「需要向外部举证」**：判据不是"我能不能解释"，而是"依据要不要由组织之外的第三方复算"。落地测试是：把这次决策留存的记录（用了哪些字段、命中了哪条依据、结论是什么）交给监管、客户或申诉受理方，他们能否不依赖你的模型独立算出同一个结论——能，就是外部举证义务；只有内部复盘才说得清，就不算。判定成立的标志是"举证对象认可该记录足以复算"，而不是"解释读起来合理"；这一条也是树上唯一通向"LLM 不单独决策"的入口。
- **「每秒千次」**（约束的是主路径的推理形态，不是族的选择）：由延迟预算倒推。按 Little 定律，常驻并发 ≈ 到达率 × 单次处理时间；若允许的常驻推理并发为 10，则 1,000 QPS 对应单次处理时间上限 ≈ 10ms（10 / 1,000 秒）。规则匹配与训练好的小模型（GBDT、小型网络，以及 LinUCB 这类线性打分）可以批量落在这个量级，而 LLM 单次调用的端到端延迟通常在数百毫秒到数秒（以厂商文档与自测为准），差两到三个数量级——因此这条排除的是"把 LLM 放进逐次决策"，不排除在线学习：MAB 的服务形态同样是一次轻量打分。若你的 P99 预算比 10ms 宽，这条约束随之放宽，需要按同一算法重算你的并发上限。
- **「能否取回结果变量」**：无阈值，是能力边界。落地测试是"对过去一个完整反馈周期（以你的业务效果稳定所需的时间为准）内的决策，能否取回结果"。
- **「存在选择偏差」**：由数据生成机制决定，不是比例阈值。落地测试是：把历史决策分成"被选中"与"未被选中"两组，比较两组在关键特征上的分布——分布差异明显，就说明你的历史数据不是随机样本，监督模型的离线指标会被系统性高估。
- **「环境变化快于重训周期」**：比较的是两个时间尺度。若数据分布明显漂移的周期长于你的重训周期（例如每天重训），批式重训已经追得上，此时上 MAB 只是多付探索成本。【经验】多数业务的用户特征分布以月为尺度变化，只有大促、舆情、竞对动作这类事件驱动才会到周级。
- **「决策步骤能否事先枚举」**：能力边界而非阈值。步骤可枚举时，工作流 / DAG 更便宜且天然可审计；步骤不可枚举（要按中间结果决定下一步查哪个系统）时，Agent 的规划能力才有价值。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 信贷审批（不可逆 + 举证） | 规则 + 评分卡 + 模型辅助 | GBDT + 归因解释 | LLM 单独决策：理由与计算无映射，举证不成立 |
| 交易反欺诈（毫秒级 + 对抗性） | 实时规则 + 在线模型 | 图特征 + ML | 离线 T+1 打分：延迟量级就不对 |
| 优惠券发放（可逆 + 高频） | ML 决策或 Contextual Bandit | LLM 生成候选策略、人工选定 | LLM 逐次决策：成本随决策量线性增长 |
| 动态定价（可逆 + 需因果） | 因果决策 + A/B 验证 | MAB | 纯监督模型：选择偏差下离线指标不可信 |
| 跨系统运营处置（步骤不可枚举） | Agent + 规则兜底 | 人工 + 工作流 | 纯工作流：处理不了"看完再决定查什么" |
| 战略 / 长周期决策（低频、高价值） | 决策智能平台 + KG + LLM | 人工评审 + BI | 全自动执行：错误不可逆且无法举证 |
| 内容推荐（可逆 + 高频 + 环境漂移） | 实时决策 + 在线学习（MAB） | 定期重训的排序模型 | 漂移快于重训周期时，模型会静默失效 |

八种常见组合的职责边界与运维代价：

1. **规则 + 模型**：规则管硬约束（合规底线、名单、金额上限），模型管软判断（个性化、概率排序）。运维代价是两套口径必须一起版本化——规则的单点手改是最常见的线上事故来源。
2. **实时决策 + 在线学习**：实时决策负责把特征与推理放到同一条流上，在线学习负责在流上更新参数。运维代价是稳定性风险叠加：模型变与数据变同时发生，出问题很难归因到哪一边。
3. **因果决策 + A/B 实验**：因果方法（DML、CausalForest）给出效应估计与人群异质性，A/B 实验做最终确认。运维代价是需要一个可信的实验平台，没有平台这套组合只剩纸面价值。
4. **LLM 增强 + XAI**：LLM 负责把规则与结果翻译成人能读的策略叙述，XAI 负责给出可复算的依据。运维代价是两者可能叙述不一致，必须事先定好优先级：一律以可复算的一侧为准。
5. **Agent 决策 + 规则兜底**：兜底规则承担硬约束与紧急停止（限额、禁投、熔断）。运维代价是兜底覆盖面要持续维护，否则会出现"Agent 绕过硬约束"的路径。
6. **决策智能 + 行业知识图谱**：KG 提供显式关系（交易对手、上下游、药物相互作用），决策引擎消费这些关系。运维代价是实体消解与图谱更新属于长期人力投入，且质量难以量化。
7. **推荐系统 + 风控系统同源特征**：两者都在消费用户与商品的实时行为特征，共用一份特征定义可以避免"推荐侧改了特征口径、风控侧静默失效"。运维代价是特征的所有权要明确到人，跨团队改特征需走同一套评审。
8. **BI + 决策智能平台**：BI 继续承担"人做决策"的场景（口径讨论、归因复盘），决策平台承担"系统自动决策"的场景。运维代价是两条口径必须对齐——报表数与决策日志对不上时，先信哪一边必须有明文规定。

### 7.7 选错的代价与迁移成本

**反模式：把 LLM 放进主决策路径**——症状：决策量上涨后账单与 P99 延迟同时恶化，扩容只能加钱。根因是它的单位成本随决策量线性增长，无法被固定集群摊薄。正确做法：把 LLM 放在低频、高价值、容忍秒级的环节——规则生成、决策解释、疑难件升级、策略候选生成。

**反模式：用监督模型替代因果判断**——症状：离线评估很好，新策略一上线反而变差。根因是模型学的分布来自上一版策略的选择结果，策略一换分布就变。正确做法：把"能不能上线"的判断交给因果识别或 A/B 实验，而不是交给离线指标。

**反模式：规则与特征各自维护一份口径**——症状：线上规则被单点手改、模型特征管道另一路更新，出现"规则改了但特征没改"。根因是两者的决策上下文没有共用同一份定义。正确做法：把决策上下文（用哪些字段、什么口径、什么时效）做成一份被规则与特征共同引用的定义。

**反模式：先上 Agent，再补护栏**——症状：Agent 上线后出现了绕过限额、重复调用下游系统的路径，事后靠人工捞回。根因是 Agent 的行动空间默认是开放的，约束必须由外部强制而不是由提示词要求。正确做法：先落地硬约束层（限额、白名单、幂等键、熔断与回滚），再让 Agent 在受限的动作空间内规划。

这四条反模式有共同的结构：**把某一族的长处当成了全链路的答案**。LLM 的长处是理解与生成，不是高频廉价判断；因果方法的长处是识别效应，不是预测精度；Agent 的长处是步骤不可枚举时的规划，不是执行任何动作本身。选型失败大多能还原成这一类错配。

| 迁移 | 数据迁移 | 逻辑改写 | 运维重建 | 团队再学习 | 工作量量级 |
| --- | --- | --- | --- | --- | --- |
| 规则 → ML 决策 | 需决策日志与特征管道（多为从无到有） | 条件转特征，中 | 训练与重训流程，大 | 需要算法能力 | 中–大 |
| ML → 实时决策 | 离线特征改流式，需双份维护 | 特征计算重写，大 | 常驻流集群 + 在线存储，大 | 需要流计算能力 | 大 |
| 监督 ML → 因果 | 复用现有数据，补实验数据 | 目标从预测改为效应估计，中 | 实验平台，大 | 因果方法论 | 中（人力密集） |
| 规则 → Agent | 逻辑从条件变为提示与工具 | 语义不可逐条比对，大 | 增加工具层与护栏，中 | 提示与评估能力 | 大 |
| 任一 → 决策智能平台 | 统一决策上下文与日志，中 | 各决策改用统一接口，中 | 平台组件，中 | 平台使用与治理 | 中–大 |

迁移成本的量级由两件事决定，而不是由代码量决定：**上游的数据形态要不要变**（有没有决策日志、特征是不是流式的、有没有实验平台），以及**判断依据能否继续被第三方复算**。前者决定工期，后者决定能不能通过评审。凡是"数据形态要变 + 举证方式要变"的迁移，都应该按独立项目立项，而不是当成一次技术升级。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 决策不可逆、需向监管举证 | 规则或评分卡给依据，模型做辅助 | 只有"计算形式即解释形式"的一族能被第三方复算 |
| 决策量在每秒千次以上 | 主路径用规则 + 小模型在线打分；策略仍按回流与漂移判据选（可用在线学习） | 单位成本不随决策量线性增长，延迟落在毫秒预算内；这条排除的是 LLM 逐次决策，不排除 MAB（其服务形态同样是轻量打分） |
| 没有结果回流 | 先建决策日志与回流，暂不上模型 | 监督学习的输入是标签，没有回流就是无源 |
| 历史数据有选择偏差 | 因果识别 + A/B 验证 | 监督模型学 P(Y\|X)，不学 P(Y\|do(X)) |
| 环境漂移快于重训周期 | 在线学习（MAB / Contextual Bandit） | 只有探索流量能在线上获得新策略的收益估计 |
| 步骤不可枚举的跨系统处置 | Agent + 规则兜底 | 规划能力只在步骤无法预先写出时才产生价值 |
| 有外部举证义务的自动化决策 | 依据与当时的上下文一起落库，保证可重放 | 事后归因替代不了当时的判据 |
| 峰谷比很大的决策流量 | 混合容量：平峰靠固定集群，高峰按次结算 | 成本函数的第二个变量是"决策量的分布"，不是均值 |

> 本节小结：这些候选之间唯一真正起决定作用的差异，是**决策错误的代价能否被逆转、以及谁承担举证义务**——它不回答"哪个技术更强"，只回答"你被允许用哪一族"；延迟、成本、精度都是选定族之后再排的次级问题。
>
> 💡 **思考锚点**：把你系统里的自动决策逐条过一遍：哪些落在 GDPR 第 22 条 / 个保法说的「对个人产生法律或重大影响」里、哪些只是内部排序？只有前一类扛外部**举证义务**——你现在给这两类留的决策日志，粒度一样吗，还是只对其中一类做了「依据与上下文一起落库」？
