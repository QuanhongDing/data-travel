## 3. 设计模式与范式

### 3.1 先看约束：模式不是选择题，是约束的产物

智能 BI 的形态由**五条约束**决定，顺序不能颠倒：

1. **口径是否已经唯一**：同一个业务词（"GMV""活跃"）在你们组织里是否已落到**唯一一个定义**？**没有它，任何自然语言入口都会把它变成"每次问可能落在不同口径上"**——这一步属于指标体系（[Ch1 §10](../../01-modeling/10-metric-system/10-metric-system.md)），缺失时后面的模式都无从谈起。
2. **错误的代价**：错一个数会被写进汇报 / 影响决策吗？**是，则"猜"绝对不可接受**——系统必须能在映射不到时**明确拒绝**（§2.2 的 `unmapped` 分支）。
3. **用户是谁**：业务方（不懂 SQL）、数据分析师（懂 SQL、要复核）、还是系统（Agent 取数）？**这一条决定"口径回显"要做到多重**——给业务方要自然语言 + 可点开；给分析师要**可见的 SQL**；给系统要**结构化的口径字段**。
4. **数据规模与查询成本**：目标是数仓明细（可自由查询）还是大集群（一次误查代价高）？**这一条决定沙箱的上限设置**（行数 / 超时 / 扫描量）。
5. **有没有人能维护语义层**：指标定义、同义词、别名会持续增长，**有没有人负责增删与冲突处理**？**没有这个人，语义层会在半年内出现大量同名歧义**——而歧义会静默地让同一个问题得到不同答案。

> **判据的用法**：先用 1 决定"能不能开始"；用 2 决定"要不要建拒绝分支"（这一条把"猜"从系统行为里删掉）；用 3 决定回显深度；用 4 决定沙箱；用 5 决定自动化到什么程度。**跳过第 1 条最常见的后果**：系统上线了、答得也快，但**同一个"GMV"在两次提问里落到两个口径**，而没有任何人发现——因为两次都"有数"。

**每条约束的"过关"是可核查的**：

| 约束 | 过关的可核查标志（不是"我们考虑了"，而是"我们量过"） |
| --- | --- |
| 1 口径唯一 | 抽 20 个高频业务词，逐个数"它映射到几个指标"——歧义词数是已知数 |
| 2 错误代价 | 系统有"无法映射 → 明确拒绝"的路径，且该路径**被测试覆盖** |
| 3 用户分层 | 三种用户看到的回显形态不同（业务方：口径说明；分析师：可见 SQL；系统：结构化字段） |
| 4 查询成本 | 沙箱的**行数 / 超时 / 扫描量三个上限里至少设了两个** |
| 5 语义层维护 | 指标与同义词有 Owner、有增删流程、有最近的冲突处理记录 |

第 1 条的检查是本主题所有工作里**投入产出比最高的**：抽 20 个高频词数歧义，**半小时的事**，而它决定后面所有模块能不能真正可信。

### 3.2 模式逐个拆解（核心节）

#### 3.2.1 直连 NL2SQL（模型直接生成 SQL）

**被什么约束逼出来**：**没有语义层**，或口径尚未统一，但业务已经要求自然语言入口（约束 1 不满足时的现实选择）。

**结构**：schema（或 schema 子集）+ 自然语言问题 → 模型生成 SQL → 执行 → 返回结果。

**为什么这样设计有效**：因为**它绕过了"先建语义层"这个前置条件**——在口径尚未统一的组织里，它是唯一能先跑起来、先积累使用数据的形态。**它的有效性来自"不要求前置治理"这一点**：先用起来，再拿真实问题去反推该建哪些指标。

**代价（是要付出代价的，且代价与"什么时候补语义层"强相关）**：① **口径错是静默的**（§2.2 的错误分类 ④⑤），业务方看不出；② **不可复现**——同一个问题两次生成可能不同 SQL，而两次都"有数"；③ **schema 暴露**——把表结构喂给模型，等于把数据资产的形状暴露出去（对内部还好，对外部模型就是信息泄漏）；④ **难以评测**——没有口径参照，`EX` 高不代表对。

**失效点**：**把它当长期形态**。它的合理生命周期是"**过渡期**"：用它收集真实问题分布 → 反推高频可归纳的指标 → 建语义层 → 迁到 Text2Metrics。**判据**：有没有一份"高频问题 → 是否已被语义层覆盖"的清单——没有，说明系统在过渡期里停住了。

#### 3.2.2 语义层映射（Text2Metrics）

**被什么约束逼出来**：口径已唯一（约束 1），且错误代价高（约束 2）——**必须让"猜"不可能发生**。

**结构**：意图 → **映射到语义层条目**（指标 + 参数）→ **由语义层编译查询**（不是模型写 SQL）→ 执行 → 结果带回口径。

**为什么这样设计有效**：因为**它把"正确性"从模型的概率能力移到了语义层的确定性定义上**——模型的任务从"写一段正确的 SQL"退化为"从 N 个指标里选出正确的几个并填参数"，而后一个任务**有明确的对错参照**（选错就是选错，可以测）。由此得到两条推论：① **准确率上限由指标覆盖率决定**（§1.1 的判据表），而不是由模型能力决定；② **新增一个口径的成本变成"在语义层加一条定义"**——这个成本是可控的、可排期的，而"提升模型能力"是不可控的。

**代价**：① **语义层是常备资产**，需要人维护（约束 5）；② **覆盖不到的问题会被拒绝**（而这**正是它可信的来源**，但业务一开始会觉得"它能答的比 NL2SQL 少"）；③ **表达能力受限**——需要复杂计算的临时分析做不了（此时应引导到"自助分析 / 导出"路径，而不是让自然语言入口硬答）。

**失效点**：**语义层条目里没有同义词**——用户说"成交额"而语义层里只有"gmv"，于是映射失败。**判据**：同义词表的规模与更新记录；**没有同义词的语义层，覆盖率在真实问题上会低得惊人**，而团队通常把原因误判为"模型不行"。

#### 3.2.3 Schema / 口径检索增强（RAG over schema）

**被什么约束逼出来**：表与字段数量远超上下文窗口（约束 4 的规模侧）。

**结构**：把 schema、指标定义、口径文档、同义词建成检索索引 → 按问题检索相关条目 → 只把检索结果放进上下文 → 生成 / 映射。

**为什么这样设计有效**：因为**它把"上下文预算"从"schema 有多大"解耦成"这个问题需要几张表"**——大 schema 的组织里，全量 schema 根本塞不进上下文，而**塞一半进去会让模型在错误的前提下生成**（它看不到相关的表，就会用不相关的表凑）。检索增强的有效性来自**"只给相关的"**，而不是"给得更多"。

**代价**：① **检索错了，后面全错**（且错误形态是"用了不相关的表"，看起来仍然合理）；② **索引要随 schema 与指标变更更新**（滞后会给出过时定义）；③ **检索的粒度**（按表 / 按字段 / 按指标）要选，粒度不对会让上下文变成噪声。

**失效点**：**检索对象是原始 schema 而不是语义层条目**——在 Text2Metrics 形态下，**检索的应当是"指标与口径"，不是"表与列"**；检索表结构会让模型倾向于"自由拼 SQL"（回到 NL2SQL 的口径风险）。**判据**：上下文里出现的是指标定义还是表 DDL。

#### 3.2.4 执行反馈自纠

**被什么约束逼出来**：第一次生成不完美是常态，而**报错信息是可用的信号**。

**结构**：执行查询 → 拿到报错或结果 → 回灌给模型 → 修正 → 再执行（**有轮次上界**）→ 超出上界升级为人工或明确失败。

**为什么这样设计有效**：因为**报错把"不可见的错误"变成了"可见的信号"**——语法错、不存在的列、类型不匹配都能被自动发现并修正（§2.2 的分类 ①）。**这条闭环的价值集中在"语法/工程类错误"上**，而它之所以有效，恰恰因为**这类错误有确定性判据**（跑不跑得起来）。

**代价**：① **轮次成本**（每次都消耗调用与查询资源）；② **必须设轮次上界**，否则会出现"反复试不同写法"的循环；③ **它掩盖不了口径错**——**这是最需要说清的一点**：多轮修正会把一段错误口径的 SQL 改得**更像真的**（跑得通、数看着合理），因此**闭环越顺，口径错越隐蔽**。

**失效点**：**把执行反馈用于"试不同口径直到有数"**——这会把"口径不确定"自动化成"挑一个能出数的口径"，是本主题最危险的一种用法。**判据**：反馈循环里修改的对象是"语法与表列"还是"指标与口径"——后者必须走澄清，不能走重试。

#### 3.2.5 多轮精修与澄清

**被什么约束逼出来**：意图含糊（"最近的销售情况"），而系统不许猜（约束 2）。

**结构**：**歧义 / 未解析 → 澄清提问**（给出候选，让用户选）→ 用户选择 → 继续。**澄清必须是结构化的**（选项来自语义层，而不是开放提问）。

**为什么这样设计有效**：因为**"问一次"的成本远低于"答错一次"**——尤其当错误会被写进汇报时。**它的有效性来自把 `ambiguous` 与 `unmapped` 从"静默处理"改成"显式交互"**（§2.2 的两个分支）：系统不再需要猜，而是把判断权交回给最清楚的人。

**代价**：① **多一次交互**（对熟练用户是摩擦）——因此澄清要**只在必要时触发**（高置信直接答，低置信才问）；② **澄清要有次数上界**（连续三次澄清仍不清楚，应转人工或引导到自助分析）；③ **澄清的候选质量决定体验**——候选不全会让用户被迫选一个近似项（于是又回到"猜"）。

**失效点**：**把澄清做成开放式追问**（"您能说得更具体吗"）——用户不知道要具体到什么粒度，结果是又一轮含糊。**判据**：澄清提问里有没有可点的候选。

#### 3.2.6 口径回显与依据可点开

**被什么约束逼出来**：业务方要拿数去做决策，而**"模型说是这样"不构成依据**（约束 3）。

**结构**：结果返回时附带——**用了哪个指标（含定义）、哪段时间语义、哪些过滤、生成时刻、以及可点开的定义页**。分析方法师可见 SQL。

**为什么这样设计有效**：因为**它把"信任"从"相信系统"转移到"可以自己核对"**（同 [Ch10 §02 §3.2.6](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的引用回指同一机制）。**这条转换的价值与模型准确率无关**——即使模型完全准确，没有口径回显的数也无法在组织里被采用，因为它**无法被复核**。

**代价**：① **界面复杂度上升**（每个数都要带一段说明）；② **回显内容要跟随口径变更**（否则回显的是旧定义，比不回显更糟）；③ **对分析师要给 SQL**，而对业务方给 SQL 是噪声——**分层是不同的实现，不是同一个开关**。

**失效点**：**回显的是"提示词里怎么说的"而不是"这次实际用了哪个口径"**——**回显必须来自实际执行的那个指标对象**（含版本），否则它在口径变更后会说谎。**判据**：改一次口径定义，界面上的说明跟着变了吗。

#### 3.2.7 权限与可见域前置裁剪

**被什么约束逼出来**：查询会触达受权限保护的数据（约束 2 的安全侧）。

**结构**：在**召回与生成之前**解析调用者的可见集（可查的表 / 列 / 行范围、可见的指标）→ 下推为检索与生成的条件 → 只生成**在可见集内**的查询。

**为什么这样设计有效**：因为**"先生成再拦截"会把无权对象写进查询**——即使最终不执行，**它已经出现在生成内容、日志与上下文里**（同 [Ch8 §02 §3.2.6](../../08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance-section-3-sec3.md) 的"读出来再删 ≠ 不读出来"）。**前置裁剪的另一层收益**：**可见的指标集合本身被裁剪后，映射空间变小，歧义也随之减少**（这是安全与准确率在这里同向的一次少见情形）。

**代价**：① **可见集要接唯一权威源**（自建一份会出现第二个权限源）；② **可见集为空时要明确提示**（"你的权限下无匹配指标"），**不允许回退为"不过滤"**；③ **裁决要留痕**（谁、何时、用了哪条策略）。

**失效点**：**只裁剪"返回给用户的列"**——生成阶段仍在完整 schema 上工作。**判据**：用一个无权账号提问，去查这次请求的**检索上下文与生成内容**里有没有出现无权对象。

#### 3.2.8 沙箱执行与结果校验

**被什么约束逼出来**：查询是**模型产物**，而集群是共享资源（约束 4）。

**结构**：**沙箱**（只读账号、超时、行数上限、扫描量上限、敏感列脱敏）＋ **结果校验**（空结果分类、量级合理性、口径回显，§2.3 的④）。

**为什么这样设计有效**：因为**它把"模型生成的查询"从"不可信的执行体"变成"受限的请求"**——沙箱不判断查询对不对，它保证**最坏情况下也不会造成不可接受的代价**（拖垮集群、拉出全表、看到敏感列）。**这是"允许模型生成查询"这个决定能够成立的前提**：不是因为模型不会写坏查询，而是因为**坏查询的代价被限制住了**。

**代价**：① **上限设置要按集群容量反推**（行数 / 超时 / 扫描量三者至少设两个，§2.2 的算法）；② **脱敏在结果层做会破坏聚合**（一列被脱敏后，基于它的分组可能失真——**因此敏感列的处理要在语义层声明"不可用于分组"**）；③ **空结果分类需要额外信息**（权限裁空 vs 条件过严，要在执行时记录）。

**失效点**：**只设超时不设扫描量**——一个聚合查询可以在超时内扫过全表，把集群 IO 打满而不触发任何限制。**判据**：三个上限里设了几个（少于两个即为不足）。

### 3.4 组合模式：真实系统不会只用一种

1. **过渡组合**：3.2.1（直连 NL2SQL）+ 高频问题清单——**用真实问题分布驱动语义层建设**，而不是先猜该建哪些指标。
2. **生产组合**：3.2.2（语义层映射）+ 3.2.6（口径回显）+ 3.2.7（前置裁剪）——**这三件是"可信"的最小充分集**：口径来自语义层、依据来自回显、边界来自裁剪。
3. **纠错组合**：3.2.4（执行反馈）+ 3.2.5（澄清）——**语法类错误走重试，口径类歧义走澄清**；**把这两条通道分开是关键**（合并会让口径歧义被"重试"吞掉）。
4. **安全组合**：3.2.7（前置裁剪）+ 3.2.8（沙箱）——前者限制"能生成什么"，后者限制"生成之后的代价"；**两者缺一，都留下一个可被利用的缺口**。
5. **主动组合**：3.2.8 的结果校验 + 自动洞察（§2.3 的⑥）——洞察的输入是"已经算出来的指标结果"，而不是"自由查询"，因此**它必须建在语义层之上**。

**常见误配**（每条对应一个可观测的后果）：

| 误配 | 后果（可观测） |
| --- | --- |
| 语义层没有同义词 | 映射失败率高，被误判为"模型能力不足" |
| 检索原始 schema | 模型退回自由拼 SQL，口径错回流 |
| 执行反馈用于试口径 | "挑一个能出数的口径"，错得最难发现 |
| 澄清做成开放追问 | 用户不知道要具体到什么程度，第二轮仍含糊 |
| 回显来自提示词 | 口径变更后界面说明说谎 |
| 后置过滤权限 | 无权对象出现在生成内容与日志里 |
| 沙箱只设超时 | 大扫描在超时内打满集群 IO |
| 空结果不分类 | 用户把"权限裁空"当成"真的没有数据" |
| 自动洞察无采纳率指标 | 洞察稳定退化为噪声源 |

### 3.5 反模式与失效分析

| 反模式 | 症状（怎么发现它） | 后果（机制层面的后果） | 成因（为什么会写成这样） |
| --- | --- | --- | --- |
| **NL2SQL 当长期形态** | 同一问题两次不同 SQL、两次都有数 | 口径错静默、不可复现、不可审计 | 它不要求前置治理，先跑起来最省事 |
| **没有同义词表** | 业务说的词映射不到 | 覆盖率高估、被误判为模型问题 | 同义词要人维护，先不做 |
| **歧义词任选一个** | 同一问题不同时间得到不同口径 | 静默不一致，最难发现 | 选一个比问一次体验好 |
| **执行反馈试口径** | 反复换口径直到出数 | 把"不确定"自动化成"挑一个" | 反馈闭环顺手能改一切 |
| **回显提示词而非实际口径** | 口径改了界面说明没变 | 回显说谎，比不回显更糟 | 提示词更容易拿到 |
| **后置过滤权限** | 无权对象出现在上下文与日志 | 暴露面已存在 | 后置过滤实现简单 |
| **沙箱只设超时** | 集群 IO 被打满但无查询超时 | 共享资源被单次查询拖垮 | 超时是最容易想到的那个 |
| **空结果不分类** | 用户以为"真的没有数据" | 结论方向性错误 | 分类需要在执行时记录额外信息 |
| **把 SQL 给业务方看** | 业务方看不懂、不敢用 | 可解释性做了但没起作用 | 没区分用户分层 |
| **自动洞察不分级下发** | 洞察被忽略 | 稳定退化为噪声源 | 发现异常比控制误报容易 |
| **口径回显不跟版本** | 变更后历史回显与当时不符 | 复核时对不上 | 回显没带指标定义版本 |
| **只报执行准确率 EX** | 指标好看但业务不信任 | 评测偏差掩盖口径错 | EX 是最容易测的那个 |

### 3.6 规模跃迁时模式何时该换

| 跃迁 | 开始疼的信号 | 换成 | 迁移的代价 |
| --- | --- | --- | --- |
| 无入口 → 直连 NL2SQL | 取数需求排队、同质问题重复 | 3.2.1 | schema 接入 + 沙箱上限设置 |
| 直连 → 语义层映射 | 同一问题两次不同口径、或错数进了汇报【经验：出现"这个数跟上次不一样"即触发】 | 3.2.2 | **建语义层（含同义词）** + 高频问题清单反推指标 + 拒绝分支 |
| 无检索 → 有检索 | schema 塞不进上下文 | 3.2.3 | 建索引（对象改为指标与口径）+ 更新机制 |
| 无反馈 → 有反馈 | 语法类错误占比不可忽略 | 3.2.4 | 轮次上界与升级路径（**不许用于试口径**） |
| 单轮 → 多轮澄清 | 含糊问题被静默猜掉 | 3.2.5 | 结构化候选 + 触发阈值调优 |
| 信任模型 → 回显依据 | 业务不敢用（"模型说的"不构成依据） | 3.2.6 | 回显接实际指标对象 + 用户分层 |
| 无权限边界 → 有 | 出现跨权限的数据访问 | 3.2.7 | 可见集下推改造（**生成前**） |
| 被动查询 → 主动洞察 | 业务希望"不用问也能知道" | 自动洞察 + 分级下发 | 采纳率指标 + 频控（**必须先有分级**） |

**一条通用判据**：**跃迁的触发点不是"用户变多"，而是"某个失效形态第一次出现"**——第一次出现"这个数跟上次不一样"就该上语义层；第一次出现"业务说看不懂"就该上回显；第一次出现"模型写的查询扫了全表"就该上沙箱。**按用户量预设跃迁点，几乎一定过早或过晚。**

### 3.7 自检清单

- [ ] 抽 20 个高频业务词，各自映射到几个指标？（歧义词数是 0 吗）
- [ ] 语义层里有同义词表吗？最近一次更新是什么时候？
- [ ] 系统有"无法映射 → 明确拒绝"的路径吗？它有测试覆盖吗？
- [ ] `ambiguous`（多个候选）是否被显式处理（澄清），还是静默选了一个？
- [ ] 检索的对象是**指标与口径**，还是原始表结构？
- [ ] 执行反馈的轮次上界是多少？它会不会被用来"试口径"？
- [ ] 澄清提问里有没有**可点的候选**？连续澄清几次后怎么升级？
- [ ] 口径回显来自**实际执行的指标对象**吗？带版本吗？改一次定义界面会变吗？
- [ ] 对分析师可见 SQL 吗？对业务方只给口径说明吗？（分层了没有）
- [ ] 可见域在**生成之前**裁剪吗？空集时是明确提示还是回退为不过滤？
- [ ] 沙箱上限设置了几个（行数 / 超时 / 扫描量，至少两个）？
- [ ] 敏感列在语义层声明了"不可用于分组"吗？
- [ ] 空结果区分了"权限裁空 / 条件过严 / 真的没有"三类吗？
- [ ] 评测报的是 `EX` 还是同时报 `CR`（口径落对率）与 `HR`（诚实拒绝率）？
- [ ] 有自动洞察的话，它的采纳率有指标吗？按重要性分级下发吗？

### 3.8 小结

> 本节小结：智能 BI 的形态由五条约束按序决定——**口径是否唯一 → 错误代价 → 用户是谁 → 查询成本 → 语义层有没有人维护**；八种模式里，**语义层映射（3.2.2）与前置裁剪（3.2.7）是"可信"的地基**（一个保证口径、一个保证边界），**口径回显（3.2.6）把信任从"相信系统"转移到"可以自己核对"**，而 **执行反馈（3.2.4）只能修语法类错误——它修不了口径错，反而会把口径错改得更像真的**。判断这一块有没有真正建成，只看两条：**同一个问题问两次，落到的口径是否同一个**；**业务方拿到数时，能不能看到它用的是什么口径**。**本主题最容易被忽略的一条**：`ambiguous`（多个候选）比 `unmapped`（映射不到）危险——**前者会静默选一个，而后者会明确报错**。

> 💡 **思考锚点**：从 §3.2 里挑一条你系统已有的做法，问三个问题：它**在链路的哪一段**生效？它对**哪一类错误**有效（语法 / 连接 / 聚合 / 口径 / 权限）？**它会不会让另一类错误更隐蔽**？第三个问题通常最有价值——**执行反馈会让口径错更隐蔽，口径回显会让"回显与实际不一致"更隐蔽**。你打算先补哪一段？
