## 4. 工程实现

### 4.1 落地步骤

这一块有一条与其它主题不同的性质：**它的第一个交付物是"一份高频问题清单"，而不是一个系统**——因为你不知道该建哪些指标，除非先知道大家在问什么。

**Step 1：收集真实问题分布（先做这个）**
从历史取数工单、聊天记录、报表访问日志里抽出**真实问题文本**，归并成问题类型，统计频次。

- **产物**：一张「高频问题 → 是否可归纳为指标」的清单（含频次与问题类型）。
- **为什么必须这一步 / 为什么在这个位置**：它是全流程的输入——不先有真实问题分布，语义层会按"我们觉得重要"来建，而**覆盖率会在真实问题上低得惊人**；它必须是第一步，则是因为 Step 2 要数的词与 Step 8 评测集里的样本都从这份清单里出，没有它，后面每一步的输入都只能靠猜。

**Step 2：抽 20 个高频词，数歧义**
对最高频的 20 个业务词，逐个数"它映射到几个指标"。**判据**：歧义词数。**这一步只需半小时**，但它决定后面所有模块能不能可信——歧义词不处理，系统必然在某些问题上静默选一个。

- **产物**：一张「高频词 → 它映射到几个指标」的对照表，歧义词单列出来。本文件内有三处判据都读这张表：§4.4 的三条验收判据第 2 条（"歧义词数为 0"）、§4.8 的 0 → 1 阶段判据（"歧义词数为 0 且拒绝路径可用"）、§4.9 自检第 2 条；本主题 §3.2.2 的判定方法也以它为判据。
- **为什么必须这一步 / 为什么在这个位置**：它必须早于 Step 3 建语义层，因为**一个歧义词消解成"一个指标"还是"两个指标"是先决问题**——先建条目再数歧义，每个歧义词都要返工一次定义，而返工意味着重新找业务确认口径。它排在 Step 1 之后，则是因为歧义只能在"真实问题里出现过的词"上数，在词典里数是另一回事。

**Step 3：建语义层（含同义词），并留出拒绝分支**
把高频可归纳的部分写成指标定义（口径 + 维度 + 时间粒度 + 同义词）；**同时把"映射不到"的路径实现出来**——明确告诉用户"这个指标未定义"，并给出最接近的候选。**判据**：新增一个指标是"加一条定义"，不是"改提示词"。

- **产物**：语义层条目集合（每条形如 §4.5 模板 1：口径定义 + 维度 + 时间粒度 + 同义词 + `caveats` + 版本号）与**拒绝分支**（`unmapped` 时明确拒绝 + 最接近的候选 + 引导到自助分析，返回形态见 §4.5 模板 2）。
- **为什么必须这一步 / 为什么在这个位置**：口径唯一性是后面每一步的输入——Step 4 的可见集要按指标裁剪、Step 6 的回显要指向指标对象的版本、Step 8 的 `CR` 要拿它当参照。反过来先做生成与界面，用户的预期已经建立，回头补语义层会被读成"功能变少"（见本节末的"顺序的反面"）。

**Step 4：接可见域，在生成前裁剪**
解析调用者的可见集（可查指标 / 可查表列 / 行范围），下推为映射与检索的条件。**判据**：无权账号的请求里**不会出现**无权对象（查检索上下文与生成内容，不只看返回结果）。

- **产物**：一张「调用者 → 可查指标 / 可查表列 / 行范围」的可见集，以及它到映射与检索条件的**下推规则**——注意产物是"每次请求执行前必须走一遍的那段代码"，不是一份静态权限清单。
- **为什么必须这一步 / 为什么在这个位置**：它必须早于对真实用户开放，因为"先生成再拦截"会把无权对象写进检索上下文、生成内容与日志，而**写出去的东西事后删不掉**（同 §3.2.7 引的"读出来再删 ≠ 不读出来"）。它排在 Step 3 之后，则是因为没有指标集合就没有可裁剪的对象——可见集裁的是指标、表列与行范围三样，前两样都依赖 Step 3 的产出。

**Step 5：装沙箱与结果校验**
行数 / 超时 / 扫描量三条上限至少设两条；结果侧做空结果分类、量级合理性提示、口径回显。**判据**：一次误查最多消耗多少资源（能算出来）。

- **产物**：沙箱三条上限的取值及其**反推依据**（§4.2 第（5）点的推导链）＋结果侧的校验器（空结果分类 / 量级合理性提示 / 口径回显）。
- **为什么必须这一步 / 为什么在这个位置**：上限必须装在对真实用户开放之前——**它是"允许模型生成查询"这个决定成立的前提**（机制见 §3.2.8），事后再加会被读成"现在开始限制你"，而一开始就定规矩不会被读成收紧。它也必须早于 Step 8：评测要有边界地跑，否则测出来的失败把"超限被拒"与"答错"混在一起，`EX` 就无法解释。

**Step 6：分层回显**
业务方看到口径说明（可点开定义）；分析师看到 SQL；系统调用拿到结构化口径字段。**判据**：改一次指标定义，三种回显是否都跟着变。

- **产物**：三种回显形态（业务方口径说明 / 分析师可见 SQL / 系统结构化字段），以及它们共同的取数来源——**实际执行的那个指标对象及其 `caliber_version`**（字段清单见 §4.2 第（6）点）。
- **为什么必须这一步 / 为什么在这个位置**：它是"数可以被采用"的前提，而这个前提在模型再准也换不来——**无法被复核的数不会进决策**（机制见 §3.2.6）。它排在 Step 5 之后、Step 8 之前：回显一旦上线就会被当作复核依据，而它绑错来源（提示词 / 缓存）时不会报任何错，所以必须在评测与推广之前先把"版本对齐"这件事做完。

**Step 7：多轮澄清与执行反馈（各管一类错误）**
**语法类错误走执行反馈（带上界）**；**口径类歧义走澄清（带结构化候选）**。**判据**：这两条通道在实现上是分开的吗——合并会让口径歧义被"重试"吞掉。

- **产物**：两条独立通道及其**路由表**——执行反馈（带上界与升级路径）与澄清（带结构化候选与次数上界），分流形态见 §4.2 第（4）点。
- **为什么必须这一步 / 为什么在这个位置**：分流不是可以后补的开关。两条通道合并之后，口径歧义会被重试吞掉，而**合并后的系统看起来更"顺"**（每次都给出一个数、不打断用户），等业务方拿它做过汇报再返工，得先把已经发出去的数收回来。它排在 Step 6 之后，是因为澄清给出的候选本身就是一次面向用户的回显——口径必须显出来（§4.5 模板 2 的话术里两行候选各带一个口径版本：口径 v8 / v5），因此候选的呈现形态由 Step 6 定；而候选里的指标与版本号本身来自 Step 3 的语义层条目，没有 Step 3 的产出就给不出这种候选。

**Step 8：评测与监控**
建私有评测集（来自步骤 1 的真实问题 + 期望口径），报 `EX` / `CR` / `HR` 三个指标；监控**映射失败率**与**澄清率**的变化趋势。**判据**：口径落对率（`CR`）有数吗——只报 `EX` 是常见偏差（§2.2）。

- **产物**：私有评测集（`question` / `expected_metric` / `expected_filters` / `expected_time` / `expected_result_hash`，形态见 §4.5 模板 3）＋ `EX` / `CR` / `HR` 三个指标 ＋ 映射失败率与澄清率的趋势（后两个是上线后才有的量，评测集给不了）。
- **为什么必须这一步 / 为什么在这个位置**：它是唯一能证明前面七步兑现了的环节，也是最容易被降级成"上线前跑一次"的环节。放在最后**不是因为它可以后补**：没有迁移前的基线，后面所有优化都无法证明是优化（§4.4 的验收判据同此）；而 `CR` 一旦停测，"同一个问题慢慢落到不同口径上"这件事就再也没有观测手段（§4.8 的贯穿三阶段的那件事）。

**顺序的反面（最常见的错误）**：**先做 NL2SQL 与漂亮的界面、后建语义层**——界面会把"生成能力"变成用户预期，而**用户预期一旦建立，回头做语义层就意味着"功能变少"**（原来能答的自由问题现在被拒绝了），组织阻力陡增。**第二条反面**：**先做自动洞察、后做语义层**——洞察的输入必须是有口径的结果，建在自由查询上的洞察会把噪声放大成结论。

### 4.2 关键技术点

**（1）意图解析：抽不出的部分要显式标注**

```text
解析产物（意图对象）——每一格都必须有值，无值要标 unresolved
{
  metric:      "gmv" | null,
  dimensions:  ["region", "channel"],          # 未识别到维度 → []
  filters:     [{field: "region", op: "=", value: "华东"}],
  time_range:  {type: "relative", expr: "上个月", resolved: ["2024-06-01","2024-06-30"]},
  grain:       "day",
  unresolved:  ["同比"]                        # ← 关键字段：说了但没解析出来的部分
}
判据：unresolved 非空 → 走澄清分支，不许用默认值把它填掉
```

**为什么 `unresolved` 是必需字段**：它把"解析器不会的部分"从**静默丢弃**变成**显式交互**。丢弃会让系统给出一个**看起来回答了问题、实际忽略了限定条件**的结果（"同比"被丢掉，用户拿到一个绝对值而以为拿到了同比）。

- **机制**：因为意图对象把"解析到的"与"没解析到的"放进**同一张结构**（`unresolved` 是必填格），系统不必在解析阶段回答"缺的这一格该不该猜"——这个判断被推迟到有确定判据的地方（非空即澄清）。由此得到一条性质：**解析能力下降时系统变慢、但不变错**——答不出会变成一次提问，而不是一个错数。
- **失效条件**：当 `unresolved` 被默认值兜底时（"最近"被填成默认窗口、"同比"被静默丢弃），系统会给出看起来回答了问题、实际忽略了限定条件的结果，而且**不报任何错**；症状是同一个问题两次得到不同解释，两次都"有数"。
- **档位**：字段结构与其必填性属【经验】（本书按可复算的最小结构给出，落地形态见 §4.5 模板 2）；解析器本身的准确率**没有公开基线，须用自己的私有评测集测**——本主题 §5.2 的表里，② 第三方生产案例对全部方向都"核不到"。

**（2）时间表达式的解析（边界最多的一段）**

| 表达 | 常见误解析 | 正确做法 |
| --- | --- | --- |
| "上周" | 与"最近 7 天"混同（一个是自然周、一个是滚动窗口） | 两者都要有，并按业务口径选择，**不能混用** |
| "上个月" | 与"上月同期"混同（后者是去年前月） | 口径里区分 `last_period` / `last_year_same_period` |
| "最近" | 默认天数（7 天？30 天？） | **无默认**：`unresolved` 或按指标定义里的默认窗口（写进指标，不写进解析器） |
| "Q1" | 财年 Q1 与自然年 Q1 | 财年偏移必须可配置 |

**判据**：时间边界的测试用例覆盖了自然周 / 滚动窗口 / 自然月 / 财年四种吗——**这四种混用是本主题最常见的静默错误之一**。

- **机制**：因为"上周""最近""Q1"在业务语言里本来就有多种合理解释，解析器的职责不是选中一个，而是**把选择权交回到定义上**——凡口径里能定的（自然周还是滚动窗口、财年偏移、默认窗口）都写进指标定义，解析器只负责识别与引用（§4.5 模板 1 的 `default_window` 就是这一格的落点）。因此同一句话在不同指标上可以有不同的"最近"，而系统仍然自洽。
- **失效条件**：当解析器自带默认值、而指标定义里也有默认窗口时，**两个默认会互相覆盖，且没有任何一方会报错**；症状是"最近"在 A 指标上落到一个窗口、在 B 指标上落到另一个窗口，而两次回显的时间语义都写着"最近"——用户看到的两份说明完全一样，数不一样。
- **档位**：【经验】——本节不为时间词的语义引外部文档作据；四类边界的覆盖度自己数（§4.9 自检第 5 条）。财年偏移属组织口径，只能从你们自己的日历配置里读，没有可抄的通行取值。

**（3）评测集与三个指标**

```text
评测集构造（私有，来自真实问题）：
  (question, expected_metric, expected_filters, expected_result)
  —— 注意要记 expected_metric：EX 相同而 metric 不同的样本才是关键样本

三个指标必须分开报：
  EX  执行准确率  = 结果集完全一致的比例
  CR  口径落对率  = 落到 expected_metric 的比例     ← 本主题真正关心的
  HR  诚实拒绝率  = 无法映射时明确拒绝的比例        ← "不猜"的证据
判据：一个把"GMV"落到错误口径上的系统可以有很高的 EX —— 因此只报 EX 是评测偏差
```

- **机制**：因为样本里多记了一格 `expected_metric`，同一个结果集就能被归到"口径对了"与"口径错了"两类——这正是把"SQL 写对了"与"口径落对了"分开度量的地方。`HR` 的存在则让**拒绝从失败变成可计分的正确行为**，否则一个把所有问题都硬答的系统在 `EX` 上并不吃亏。
- **失效条件**：当评测集只标 `expected_result` 而不标 `expected_metric` 时，**口径错而结果碰巧相同的样本会被记成通过**，于是最该被抓的失效形态在评测里不可见；症状是 `EX` 逐季上升，而业务方对数的投诉不降。
- **档位**：【公开】——评测形态本身有可指名的基准：Spider（EMNLP 2018）、BIRD（NeurIPS 2023）、Spider 2.0（arXiv 预印本 2024），本书他处已登记（Spider / BIRD 见 `01-modeling/12-hands-on/12-hands-on-section-5-ai.md` §5.4；Spider 2.0 见 `01-modeling/02-dimensional-modeling/02-dimensional-modeling-section-5-ai.md` §5.4）；但三者的设定并不相同：Spider 是单库、schema 干净的一类，BIRD 与 Spider 2.0 已分别朝"贴近真实库、含脏数据"与"多库、多步的企业级工作流"推进（出处同上）；它们共同缺的不是规模，而是**你的业务口径**，因此只能用来说明"评测怎么做"，不能替代私有集（§3.2.1 记过 Spider 一类"单库、schema 干净、无业务口径"的设定，§5.5 第 2 条给出同一条判据：拿自己的私有评测集测、报 `CR` 而不是 `EX`）。`CR` 与 `HR` 本身没有公开基线，§5.2 的表里 ②（第三方生产案例）对全部方向"核不到"。

**（4）多轮精修与澄清的分流（两条通道，不许合并）**

```text
错误发生
  ├── 执行报错（语法 / 列不存在 / 类型不符）→ 执行反馈，带上界（如 ≤ 3 轮）
  │     判据：修改对象是"语法与表列"
  └── 语义歧义（多候选 / unresolved）      → 澄清，给结构化候选
        判据：修改对象是"指标与口径"
  ────────────────────────────────────────────────
  禁止：用执行反馈去"试不同口径直到有数" —— 那是把不确定性自动化
```

- **机制**：因为两类错误的判据在物理上是两种东西——语法错的判据是"跑不跑得起来"（引擎会给确定答案，可自动校验），口径歧义的判据是"该用哪个指标"（只有人能答）——所以分流等于**让每条通道只处理自己有判据的那类问题**。这也是为什么执行反馈可以做成闭环自动化，而澄清必须回到人。
- **失效条件**：当两条通道合并成"重试到有数为止"时，口径不确定性被自动化成"挑一个能出数的口径"，而且**这条路走起来比澄清更顺**（不打断用户、每次都给出一个数）——因此合并后的系统看起来更好用、错误却更隐蔽（同 §3.2.4 的失效点：闭环越顺，口径错越隐蔽）。症状是反馈日志里出现"换一个指标名再试一次"这类记录。
- **档位**：【经验】，机制侧可对照本书 `05-agent-platform/01-data-agent/01-data-agent-section-3-sec3.md` §3.2.3 记的反思型闭环（该处记作 Reflexion（反思）；"Self-Correction / Reflexion"的并称见 `05-agent-platform/01-data-agent/01-data-agent-section-4-sec4.md` §4.2 第 4 点）；成熟度按本主题 §5.2 表「执行反馈自纠」行为 **L2**——正式条目成立、轮次与升级策略各家不同、第三方生产案例核不到。

**（5）沙箱上限的反推**

```text
从集群容量反推上限：
  设集群可承受的单查询扫描预算 = B GB
  设平均吞吐 = T MB/s
  → 超时 ≈ B × 1024 / T（秒）【推算：口径为"扫描预算 ÷ 吞吐"】
  例：B = 10 GB、T = 100 MB/s ⇒ 超时 ≈ 102 秒
  再设行数上限（如 100 万行）与扫描量上限（如 10 GB）
判据：三个上限至少设两个 —— 只设超时挡不住大扫描，只设行数挡不住全表聚合
```

- **机制**：因为上限是从**本集群容量倒推**出来的，它就不是一个拍出来的安全值，而是一条随容量变化的约束——扩容时上限跟着放大，不需要重新辩论"该不该放开"。这也是"允许模型生成查询"这个决定能成立的前提：不是模型不会写坏查询，而是**坏查询的代价被限住了**（§3.2.8 的机制）。
- **失效条件**：当三条上限是从别处抄来的一组数、而不是从本集群容量推出来的时候，它在你的集群上既可能太松（挡不住大扫描）也可能太紧（正常查询被拒）——**两种都不报错**，只以"超时提示"或"偶发拒绝"的形态出现。症状是超时阈值被改过多次，而每次改动都没有留下计算依据；这件事的检查入口是 §4.9 自检第 9 条（"上限是从集群容量反推的吗？"）。
- **档位**：【推算】——上面这条链的入参（扫描预算 B、平均吞吐 T）由你替换后重算，本书示例值只作量纲参考；上限本身没有行业通行取值。引擎侧的落地参照【公开】：Trino 的资源组文档提供按执行时间或扫描量终止单条查询的查询级配置（`04-data-assetization/06-one-service/06-one-service-section-7-sec7.md` §7 的公开证据段，配置项以当前版本文档为准）。

**（6）口径回显的实现要求**

```text
回显必须来自"实际执行的指标对象"，不是提示词、不是检索片段：
{
  metric: "gmv", caliber_version: 12,      # ← 版本必须带
  definition: "sum(pay_amt) where order_status in ('paid','shipped')",
  time_semantics: "snapshot", time_range: ["2024-06-01","2024-06-30"],
  filters: [{region = 华东}], generated_at: "2024-07-01T09:12:33+08:00",
  sql: "SELECT ..."                         # 仅对分析师角色返回
}
判据：改一次指标定义（version 递增），界面上的说明必须跟着变 ——
      不跟，说明回显来自别处（提示词 / 缓存），它会在变更后说谎
```

- **机制**：因为回显的原料是**这次实际执行的那个指标对象**（含 `caliber_version`）、而不是提示词与检索片段，回显的正确性就与模型无关——即使模型完全准确，没有回显的数也无法在组织里被采用，因为它**无法被复核**；反过来，只要版本对齐，回显在模型换代后依然成立（§3.2.6 的机制）。
- **失效条件**：当回显从提示词或缓存取数时，它在口径变更后**会说谎，而且说得和以前一样自信**——这条失效不产生任何错误日志。症状是把某个指标的定义版本递增一次而界面上的说明不变；它只能靠一次主动的版本递增演练被发现（§4.7 表的「口径回显与实际不一致」行）。
- **档位**：【公开】——可作为形态参照的具名产品在本书他处已登记：Salesforce Tableau GPT（2023）、Microsoft Copilot for Power BI（2024）、ThoughtSpot Sage（2023）、Snowflake Cortex Analyst（2024）（`05-agent-platform/01-data-agent/01-data-agent-section-4-sec4.md` §4.3「国际平台」行）；本节只引名字，**不对其回显粒度做断言**。回显机制的适用条件本身属【经验】。

### 4.3 工具链与平台

| 能力 | 自建 / 开源 | 产品化 | 选型要点 |
| --- | --- | --- | --- |
| 语义层 / 指标定义 | 指标平台（[Ch4 §10](../../04-data-assetization/10-metric-platform/10-metric-platform.md)）、Cube / dbt Semantic Layer / MetricFlow | 商业 BI 的语义层 | **看能不能导出**（口径锁在产品里就换不掉） |
| 意图解析 / 映射 | 自建（词典 + 规则 + 模型） | 商业智能 BI | 看**同义词与歧义处理**是否产品化 |
| 查询编译 | 复用查询网关（[Ch4 §09](../../04-data-assetization/09-unified-query-gateway/09-unified-query-gateway.md)） | —— | 生成**逻辑计划**而非物理 SQL，由网关编译 |
| 检索 | 向量 + 关键词（[Ch4 §04 混合检索](../../04-data-assetization/04-hybrid-search/04-hybrid-search.md)） | —— | **检索对象是指标与口径**，不是表 DDL |
| 沙箱执行 | 引擎侧资源组 / 只读账号 | 数据网关的查询治理 | 看**扫描量**能不能限（不只是行数与超时） |
| 评测 | 自建（私有集） | —— | 看它报不报**口径落对率**，只报 `EX` 的不够 |

**一条选型原则**：**语义层的归属比生成能力重要**。一个生成能力很强但口径锁在产品里的智能 BI，会让你在"换个口径""导出指标"时付出迁移全部定义的代价；而**口径能导出**的产品，即使生成能力弱一档，也可以用更强的模型补上。

### 4.4 存量迁移

**（1）已有报表与自助 BI 怎么办**

| 对象 | 处理 | 注意 |
| --- | --- | --- |
| 存量报表里的口径 | 抽成指标定义（与原口径**逐条比对**） | 同一指标在多个报表口径不同的，**问业务哪份为准**，不自行合并 |
| 自助 BI 的数据集 | 映射为语义层的指标 + 维度集合 | 数据集里的计算字段往往藏着口径，要抽出来 |
| 已有的自然语言入口（若有） | 用它跑一遍私有评测集，得到迁移前的 `EX` / `CR` 基线 | **没有基线就无法证明迁移有收益** |
| 业务方的习惯叫法 | 收进同义词表 | **这是最容易漏的一步**：业务说的是"成交额"而不是"gmv" |

**（2）迁移的三条验收判据**

- **口径落对率不低于基线**（`CR` 在私有评测集上对比）。
- **歧义词数为 0**（高频词逐个核过）。
- **无权对象不出现**（无权账号的检索上下文与生成内容各查一次）。

### 4.5 模板 / 示例

**模板 1：指标定义（语义层条目）**

```yaml
metric: gmv
display_name: 成交额
caliber_version: 12
definition: "sum(pay_amt) where order_status in ('paid','shipped')"
dimensions: [region, channel, category, is_new_user]
time_grain: [day, week, month]
time_semantics: snapshot          # 业务问"上月是多少"要能按事件时间取
owner: trade-analytics@
synonyms: ["成交额", "销售额", "GMV", "交易额", "大盘"]
default_window: 近 30 天          # 用户说"最近"时用哪个窗口 —— 写在指标里，不写在解析器里
caveats:
  - "含全渠道；不含已退款订单"
  - "不含跨境业务（口径见 gmv_cross_border）"
restricted_dimensions: []         # 敏感列：不允许用于分组
```

**判据**：`synonyms` 与 `caveats` 这两项**有没有**——没有同义词，映射会大面积失败；没有 caveats，用户会把口径的边界当成"数据不全"。

**模板 2：意图对象与澄清触发**

```text
解析 → 意图对象（含 unresolved）
映射 → 三种结果：
  ① unique    → 直接生成，回显口径
  ② ambiguous → 澄清（给候选，让用户选）
  ③ unmapped  → 明确拒绝 + 最接近的候选 + 引导到自助分析

澄清话术模板（结构化候选）：
  "「收入」在你的权限下对应两个指标，请选择：
     1) 确认收入（sum(recognized_amt)，口径 v8）
     2) 回款收入（sum(cash_in_amt)，口径 v5）
   或：查看全部含「收入」的指标"
判据：澄清里必须有可点选项；没有选项的追问等于把问题退回给用户
```

**模板 3：评测样本的形态**

```json
{
  "question": "上个月华东的成交额同比是多少",
  "expected_metric": "gmv",
  "expected_filters": [{"field": "region", "op": "=", "value": "华东"}],
  "expected_time": {"range": "2024-06", "compare": "yoy"},
  "expected_result_hash": "…",
  "note": "关键样本：EX 相同但 metric 不同的反例必须收进集合"
}
```

**一条使用说明**：模板 1 与模板 3 的价值在于**它们把口径与评测绑定**——没有 `expected_metric` 的评测集只能验 SQL 能力，验不了口径。**把这两张表建起来，"可信"这件事才有可量化的依据。**

### 4.6 成本：这套东西的账单

**硬件**：本主题**几乎没有专属硬件成本**——它是"一层薄薄的编译与判定 + 一次本就该发生的查询"。三处例外：① **语义层的在线存储与缓存**（点查指标定义，量很小）；② **检索索引**（指标与口径文档的向量索引，量小）；③ **沙箱的资源组隔离**（若用独立资源组，会有常驻的容量预留成本）。

**相对成本的大头在"查询本身"**：一次自然语言取数最终会变成一次真实查询，**而它可能比业务手动写的那次查询更贵**（模型生成的查询可能扫描更多数据）。**这条推论给出一个可算的判据**：

```
自然语言取数的真实成本 ≈ 模型调用成本 + 查询执行成本
其中查询执行成本可能占大头，且它随「沙箱上限设得多松」变化

判据：把「一次提问的平均扫描量」与「业务手写查询的平均扫描量」比一下——
      倍数高于一到两倍【经验】时，先收紧沙箱上限（扫描量），再谈优化模型成本
```

**人力（主项）**：这一块的人力集中在三项：

1. **语义层维护**：指标定义、同义词、caveats、冲突处理。**成本随高频问题的覆盖面增长**——这是主要投入项。
2. **评测与监控**：私有评测集的维护（真实问题会变）、三个指标的定期复测、映射失败率的趋势分析。**常备投入在 0.2–0.5 人年量级**【经验：随指标数与用户数浮动】。
3. **澄清与拒绝的运营**：被拒绝的问题会被反馈回来（"为什么答不了"），需要有人判断"这是该补指标，还是该引导到自助分析"。**这项在其它主题里没有对应物**——它是"诚实拒绝"这个设计的必然成本。

**云账单（次项）**：模型调用（意图解析与澄清话术）、查询执行、在线存储与缓存。

**一条推论**：**本主题的成本是"人力随指标覆盖率增长 + 查询成本随沙箱松紧变化"，而不是"随提问量线性增长"**。因此它的规模化压力来自**指标覆盖的广度**——这也解释了为什么它是"先把高频词覆盖好"而不是"把语义层建全"：**覆盖长尾指标的边际收益远低于维护成本**。

### 4.7 容灾与故障演练

**本主题的"灾"分两类**：① **服务不可用**（用户问不了数——影响可见，可容忍度较高，因为业务有别的取数路径）；② **答错了但看起来正常**（影响不可见，**更危险**）。

| 失效形态 | 影响面 | 降级策略 | 演练动作 | 恢复目标 |
| --- | --- | --- | --- | --- |
| 语义层服务不可用 | 全部自然语言取数 | **失败关闭**：明确报"暂不可用"，**不许回退到直连 NL2SQL** | 关一次语义层，看系统是拒绝还是降级成自由生成 | RTO：分钟级 |
| 语义层定义被误改 | 一批指标的口径 | 回滚版本 + 重算受影响结果；**提示"口径已变更"** | 故意改一个口径，验证能回滚并识别受影响指标 | 小时级 |
| 检索索引滞后 | 映射到过时定义 | 索引延迟告警；滞后超过阈值时**拒绝而非猜测** | 停掉索引更新，看系统是否会在滞后时拒绝 | 小时级 |
| 沙箱执行超时/拒绝 | 单次查询 | 明确告知"查询超出资源上限"并**给出缩小范围的建议** | 提交一个必然超限的查询，看提示是否有用 | 单请求级 |
| 可见域服务不可用 | 权限裁剪 | **失败关闭**（不许"不过滤"）；给出明确错误 | 关一次可见域服务，验证请求被拒而非放行 | 分钟级 |
| 模型调用不可用 | 意图解析 | 降级到"只用词典匹配"（能答高频问题，答不了复杂表述） | 断掉模型调用，看降级路径是否可用 | 分钟级 |
| 口径回显与实际不一致 | 复核依据 | 告警（这是回显机制的失效，不是查询的失效） | 比对回显的 `caliber_version` 与实际执行版本 | 小时级 |

**这套演练的三条纪律**：

1. **凡是"判定类"机制（语义层、可见域）不可用，必须失败关闭**——尤其**不许把"语义层不可用"降级成"直连 NL2SQL"**：那等于在故障期间把口径保障全部关掉（同 [Ch8 §02 §4.7](../../08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance-section-4-sec4.md) 的"失败关闭"纪律）。
2. **口径被误改要能回滚并识别影响范围**——本主题唯一会"大面积改变结果"的失效形态。
3. **每次演练留"演练前 / 演练后"两组数字**——特别是 `CR`（口径落对率）与映射失败率，口径出错时它们先动。

### 4.8 演进路线：0 → 1 → 100

**0 → 1：高频问题被口径覆盖**
- **这一步做什么**：收集真实问题分布 → 抽 20 个高频词数歧义 → 建语义层（含同义词）→ 留拒绝分支。
- **变贵的是什么**：**人力（口径梳理与业务确认）**——它需要业务确认"这个口径对不对"，而这不是技术能做主的。
- **先坏的是什么**：**先坏的是"能答的范围看起来变小了"**——原来自由生成什么问题都能给个答案，现在一部分被明确拒绝。**这一阶段的判据不是"覆盖率多高"，而是"歧义词数为 0 且拒绝路径可用"。**

**1 → 10：依据与边界**
- **这一步做什么**：接可见域（生成前裁剪）；装沙箱与结果校验；分层回显（业务方 / 分析师 / 系统）；建私有评测集与三个指标。
- **变贵的是什么**：**评测与监控**——评测集要随真实问题演进而更新，这是常备投入。
- **先坏的是什么**：**先坏的是回显与实际的偏差**——口径变更后回显没跟上，界面开始说谎（而这是静默的）。因此这一阶段的重点是**把回显绑到实际执行的指标对象版本上**。

**10 → 100：主动与规模化**
- **这一步做什么**：多轮澄清与执行反馈（两条通道分开）；自动洞察（分级下发 + 采纳率）；把语义层的口径作为接口对外（供 Agent / 其它产品消费）。
- **变贵的是什么**：**指标覆盖的广度 + 澄清与拒绝的运营**——"为什么答不了"会持续被反馈回来。
- **先坏的是什么**：**先坏的是长尾指标的维护成本**——覆盖长尾的边际收益远低于维护成本（§4.6）。因此这一阶段的重点是**明确"不覆盖什么"**，并把不覆盖的场景**引导到自助分析**，而不是继续堆指标。

**贯穿三阶段的一件事**：**保留"口径落对率（`CR`）"的测量能力**。它是这一块唯一的健康指标——**智能 BI 的腐化不会表现为报错，只会表现为"同一个问题慢慢落到不同的口径上"。**

### 4.10 小结

> 本节小结：智能 BI 的落地顺序**以"高频问题清单"为先**——先知道大家在问什么，再决定建哪些指标；然后抽 20 个高频词数歧义、建语义层（含同义词与 caveats）、留拒绝分支、接可见域（生成前裁剪）、装沙箱与结果校验、分层回显、把执行反馈与澄清分成两条通道、最后建评测与监控。**变贵的是人力（口径梳理 + 评测）与查询成本（随沙箱松紧），而不是随提问量线性增长**（§4.6）——因此覆盖长尾指标的边际收益远低于维护成本，**明确"不覆盖什么"比继续堆指标更重要**。**容灾有一条本主题特有的纪律**：**语义层不可用时必须失败关闭，绝不许降级成"直连 NL2SQL"**——那等于在故障期间把口径保障全部关掉（§4.7）。**三阶段的同一件事**：始终保留 `CR`（口径落对率）的测量能力——**这一块的腐化不会报错，只会让同一个问题慢慢落到不同的口径上。**

> 💡 **思考锚点**：按 §4.1 的 Step 1–2 做一个最小动作——**收集一周内你们团队真实被问到的取数问题，归并成类型并数出高频词，然后对前 20 个词逐个数"映射到几个指标"**。第二个数字（歧义词数）往往比你预期的高，而**每一个歧义词都对应一个"同一问题不同口径"的隐患**。数完之后再决定：是先处理歧义，还是先建指标——你打算先做哪一个？
