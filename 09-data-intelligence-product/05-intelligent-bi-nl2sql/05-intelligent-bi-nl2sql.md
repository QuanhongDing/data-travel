# 智能 BI 与 NL2SQL（Intelligent BI & NL2SQL）

> **一句话定位**：把"用自然语言问一个数"做成**可信任、可解释、可追责**的产品——难点不在把自然语言翻成 SQL，而在**让翻出来的查询落在被认可的口径上**，以及**让业务方看得懂它为什么这么查**。

> 本文是 data-travel 项目 [Ch9 · 数据智能产品](../../README.md) 的子章节（**05 智能 BI 与 NL2SQL**）。覆盖 **R5 数据智能类产品认知** 中"智能 BI（自然语言查询 NL2SQL / 自动洞察）"相关的语义层设计、生成与校验链路、执行反馈闭环与评测实践。本主题**不**重复讲 Data Agent 的整体架构与 Agent 化编排（那是 [Ch5 §01 Data Agent](../../05-agent-platform/01-data-agent/01-data-agent.md) 的内容），只讲**"自然语言 → 可执行查询"这一段本身**——语义层怎么承载口径、生成的查询怎么被验证、以及它凭什么被业务方信任。

## 1. 概念与定位

### 1.1 是什么

**工业定义**：智能 BI 是**面向业务用户的、以自然语言为入口的数据消费界面**。它的输出不是一个数，而是**"数 + 口径 + 依据 + 可复现路径"**四件。缺了后三件，它只是一个更好用的查询框。

**工程定义**：在数据架构师手里，这一块是**三段链路 + 一层语义**：

- **理解段**：把自然语言解析成**结构化的查询意图**（指标 / 维度 / 过滤 / 时间 / 粒度 / 口径限定）；
- **语义层**（本主题的核心）：把意图**映射到已定义的指标与维度**，由它生成查询——**这一层是"可信"的来源**；
- **执行段**：在**受控的沙箱**内执行查询（权限、超时、行数、敏感列），返回结果；
- **解释段**：把结果还原成业务语言（口径说明、对比基准、异常提示、可点开的依据）。

**「NL2SQL」与「Text2Metrics」的差别**（这是本主题最重要的判据表）：

| 维度 | NL2SQL（自由生成） | Text2Metrics（映射到指标） |
| --- | --- | --- |
| 模型的任务 | **写出一段 SQL** | **从已有指标里选出几个并填参数** |
| 正确性的来源 | 模型的 SQL 能力 | **语义层的完备度** |
| 错误形态 | **语法对但口径错**（最难发现） | **映射不到 → 明确说"这个指标未定义"** |
| 业务方能看出错吗 | **看不出**（SQL 能跑、数看着合理） | 能（"未定义"是明确信号） |
| 上限由什么决定 | 模型能力 | **指标覆盖率** |
| 新增一个口径的成本 | 改提示 / 微调 | **在语义层加一个指标定义** |

**一条判据**：**当"这一次查询用的是什么口径"说不清时，这个数就不该出现在业务面前。** NL2SQL 的失败恰恰是"语法层面全对、口径层面全错"——而这类错误业务方看不出（[Ch5 §01 §6.1](../../05-agent-platform/01-data-agent/01-data-agent-section-6-sec6.md) 给了同一判断的案例）。

### 1.2 为什么需要

智能 BI 不是"加个自然语言入口"，而是**被四件事逼出来的**：

1. **取数需求的量与数据团队的产能不匹配**：临时性取数占用数据团队大量精力，而这些需求**大部分是"换维度看同一个指标"**——这类需求高度同质，正是可用口径覆盖的部分。
2. **同一个问题在不同人手里有不同答案**：业务说"GMV"，财务、运营、增长各自的口径不同。**自然语言入口会把这个问题放大**——它必须显式地落到某个口径上，否则每次问都可能落在不同口径上（同 [Ch1 §10 指标体系](../../01-modeling/10-metric-system/10-metric-system.md) 的口径灾难）。
3. **生成的查询必须能被业务方看懂**：业务方要拿着数去做决策，**"模型说是这样"不构成依据**。因此查询要可见、口径要可点开——这是可解释性要求的工程形态。
4. **错误的代价不对称**：一个口径错的数被写进汇报，纠正成本远高于"没有这个数"。**因此系统宁可说"这个指标未定义"，也不能猜一个**。

**这四件事的共同点**：它们都不是"模型能不能写出 SQL"的问题，而是**口径、可解释与不可猜**的问题——这正是语义层存在的理由。

### 1.3 在 AI 时代数据架构中的位置

```
   [业务用户：自然语言问题]
              ↓ 理解段（意图解析）
   [语义层 · 本主题核心]  ← 指标 / 维度 / 口径 / 时间语义 / 权限可见域
              ↓ 映射（Text2Metrics）或生成（NL2SQL）

   [解释段：口径说明 / 对比基准 / 异常提示 / 依据可点开]

```

### 1.4 演进历程

- **报表工具阶段（2005–2014）**：拖拽式 BI（自助报表），业务方在**已定义的数据集**上操作。**关键遗产**：它天然受限于数据集定义——**这与语义层的思路同源**。
- **NL2SQL 研究阶段（2017–2021）**：WikiSQL（2017）、Spider（2018）等基准把"自然语言到 SQL"变成可量化任务。**关键局限**：这些基准是**单库、schema 干净、无业务口径**的设定——**它们的成绩不能外推到企业场景**（这一点在 §5.2 会有专门讨论）。
- **语义层 + 自然语言阶段（2020–2023）**：Headless BI 与指标平台兴起，自然语言入口改为**先映射到指标**（Text2Metrics）。**这一阶段确立了"先语义层、后生成"的顺序**。
- **Agent 化与执行反馈阶段（2023 至今）**：引入**执行反馈自纠**（跑一次、看报错与结果、再改），把"一次生成"变成"多轮修正"。同期出现"Agentic BI"（自动拆解多步分析）与"自动洞察"（不等人问就给出异常与归因）。**新问题**：多轮修正会掩盖口径错误（它把"语法错"改对了，而"口径错"仍留着）。

> 演进的主线只有一句话：**准确性来源从"模型的 SQL 能力"移到"语义层的完备度 + 执行反馈的闭环"。**

## 2. 核心原理

### 2.1 关键概念定义

- **语义层（Semantic Layer）**：指标、维度、时间语义、口径、可见域、同义词的**机器可读定义集合**。它是"意图 → 查询"的唯一映射来源。
- **指标（Metric）**：带口径的度量（`gmv = sum(pay_amt) where order_status in ('paid','shipped')`），含维度集合、时间粒度、同义词（[Ch1 §10](../../01-modeling/10-metric-system/10-metric-system.md)）。
- **意图（Intent）**：自然语言解析后的结构化表示——`(metric, dimensions[], filters[], time_range, grain, caliber_hint)`。**意图是链路的中间产物，也是排障与评测的对象**。
- **映射（Mapping）**：把意图落到语义层对象上。**两种结果必须都可表达**：① 映射成功（给出指标 + 参数）；② **无法映射（明确告诉用户"这个指标未定义"）**。**第二种是本主题的关键设计**——它把"猜一个"变成"诚实地拒绝"。
- **生成（Generation）**：由映射结果编译出可执行查询（语义层生成 SQL，而不是模型生成 SQL）。
- **执行反馈（Execution Feedback）**：把查询结果或报错回灌给模型，用于**自纠**（[Ch5 §01 §3.2.4](../../05-agent-platform/01-data-agent/01-data-agent-section-3-sec3.md) 的同一机制）。
- **口径可见性（Caliber Transparency）**：把"这次查询用了什么口径"显式返回给用户，并允许点开定义。**它是可解释性的工程形态**。
- **自动洞察（Automated Insight）**：不等提问，主动给出**异常检测 + 归因**（"这个指标本周下降 12%，主要来自华东渠道"）。**它的难点不是发现异常，而是控制误报**——即"这条洞察是否值得打断用户"。
- **执行沙箱（Query Sandbox）**：查询执行的受控环境——**只读账号、查询超时、行数上限、敏感列脱敏、扫描量上限**。它是"让模型生成查询"这一决定的安全前提。
- **评测集（Eval Set）**：从**你自己的历史取数问题**构造的（问题, 期望结果）对。**判据**：它的来源决定了它的可信度——公共基准测的是"SQL 能力"，私有集测的是"口径落对率"。

### 2.2 数学 / 形式化基础

**链路的错误分解**。设一次查询的四段为理解 `U`、映射 `M`、生成 `G`、执行 `X`，则端到端成功率为

```
P(成功) = P(U) × P(M|U) × P(G|M) × P(X|G)
```

**这条分解的用途是"把优化投到该投的地方"**：

- 若 `P(M)` 很低（语义层覆盖不足），**优化 `P(U)` 或换更强的模型几乎没有收益**——因为瓶颈在覆盖率；
- 若 `P(M)` 很高而 `P(U)` 低，说明词汇映射（同义词）不够，**加同义词与别名的收益最大**；
- 若三者都高而端到端仍差，**看 `P(X)`**——通常是权限裁剪把结果裁空、或沙箱超时。

**统一口径的判定（Text2Metrics 的核心判据）**：

```
给定意图 i，语义层 S
  mapped(i, S) = 1  若存在唯一指标 m ∈ S 使得 i 可解释为 m 的参数化实例
  ambiguous(i,S) = 1 若存在多个 m 都可解释 i（同义词冲突 / 口径分叉）
  unmapped(i, S) = 1 若不存在

要求：ambiguous 必须被显式处理（向用户澄清），不许任选一个
```

**`ambiguous` 是本主题最容易被吞掉的一类**——它比 `unmapped` 危险：`unmapped` 会报错，而 `ambiguous` 会**静默选一个**（通常是字典序第一个或置信度最高那个），于是"同一个问题不同时间问得到不同答案"。

**Text2SQL 的错误分类**（决定评测与修法）：

```
① 语法错（SQL 跑不起来）           —— 执行反馈可自动发现
② 语义错 · 表/列选错               —— 执行可能成功，结果错；需结果校验或人工
③ 语义错 · 连接错（join 错）        —— 结果量级异常，可被"结果合理性"检查捕获
④ 语义错 · 聚合错（粒度错）         —— 最难发现：数看着合理
⑤ 口径错（用了别的口径的同名指标）  —— 业务方看不出，危害最大
⑥ 权限错（查了不该查的数据）        —— 安全事件，必须前置拦截
```

**一条判据**：**执行反馈只能闭环 ①③（部分）；④⑤ 必须靠语义层与可见口径，⑥ 必须靠前置裁剪。** 因此"加了执行反馈就稳了"是错的——**它把语法错改对了，而口径错会留着，还可能因为多轮修正而变得更"看起来合理"。**

**评测指标（必须分开报）**：

```
执行准确率 EX  = 结果集与期望完全一致的比例        —— 严，但对口径错不敏感
口径落对率 CR  = 落在业务认可口径上的比例          —— 本主题真正关心的指标
澄清率 CL      = 系统主动要求澄清的比例            —— 高不等于差（含糊问题就该澄清）
诚实拒绝率 HR  = 无法映射时明确拒绝的比例          —— 它是"不猜"的证据
```

**判据**：**只报 `EX` 是常见的评测偏差**——一个把"GMV"落到错误口径上的系统可以有很高的 `EX`（因为期望结果也是那么算的）。**`CR` 与 `HR` 必须一起报**，它们才是"可信"的度量。

**Sandbox 的成本与安全性**（决定它能拦什么）：

```
扫描量上限 ≈ 查询可用的最大扫描字节数
若设 scan_limit = 10 GB，则在 100 MB/s 的吞吐下最长执行 ≈ 100 秒【推算】
判据：行数上限 / 超时 / 扫描量三者必须至少两个同时设置 ——
      只设超时，一个大扫描会拖垮集群；只设行数，聚合查询仍可扫全表
```

### 2.3 关键算法 / 方法

**① 意图解析（理解段）**：从自然语言抽出 `(指标 / 维度 / 过滤 / 时间 / 粒度)`。**三类信息的抽取难度不同**：**指标与维度靠词典匹配 + 别名（最容易）**、**时间表达式靠规则 + 日历（中等，但边界多：上周 vs 最近 7 天）**、**过滤条件靠语义（最难，且错得最隐蔽）**。**工程判据**：**抽不出的部分要显式标注为"未解析"**，而不是给个默认值——未解析会让系统走澄清分支，默认值会让它猜。

**② 映射（语义层）**：把意图落到指标上。**关键设计是"同义词表 + 冲突检测"**：一个词（"收入"）可能映射到多个指标（"确认收入 / 回款收入"）——**此时必须问，不许选**（§2.2 的 `ambiguous`）。

**③ 查询编译（生成段）**：**由语义层生成 SQL**，而不是模型生成。**这条是 Text2Metrics 与 NL2SQL 的分界**：生成的查询是**确定的函数**（同样的意图 → 同样的 SQL），因此可测试、可复现、可审计。

**④ 执行与结果校验**：

```text
结果校验（在把结果交给用户之前必跑）：
  ① 空结果的原因分类：条件过严 / 权限裁空 / 数据真的没有
     —— 三者的用户提示完全不同，混在一起会让用户以为"就是没有数据"
  ② 量级合理性：与同期 / 同类对比，偏离过大时提示（不是拦截）
  ③ 口径回显：本次用了哪个指标定义、哪个时间语义
判据：空结果必须区分三类原因 —— 权限裁空不提示，用户会得出错误结论
```

**⑤ 多轮精修与执行反馈的边界**：反馈闭环用于修 ①③（§2.2 的分类），**不用于"尝试不同口径直到有数"**——那会把"口径不确定"变成"挑一个能出数的口径"，是本主题最危险的一种自动化。

**⑥ 自动洞察的误报控制**：洞察的价值 = `命中重要异常的收益 − 误报带来的注意力成本`。**因此它必须按"重要性"分级下发**：高重要性（显著偏离 + 可归因）即时推送，中低重要性进"待看"列表。**判据**：有没有一个"洞察被采纳率"的指标——没有它，自动洞察会稳定地退化成噪声源（同 [Ch10 §02 §3.2.7](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的频控问题）。

### 2.4 与相邻概念的关系

- **本主题 vs [Ch5 §01 Data Agent](../../05-agent-platform/01-data-agent/01-data-agent.md)**：Data Agent 管**整体架构**（多轮对话、工具编排、评测、沙箱、与业务系统集成）；本主题管**"自然语言 → 查询"这一段**（语义层承载、生成与校验、口径可见）。**关系是"一段与整体"**：Data Agent 里的 Text2SQL 组件就是本主题的内容，本主题不重复讲 Agent 编排。
- **本主题 vs [Ch1 §10 指标体系](../../01-modeling/10-metric-system/10-metric-system.md)**：指标体系解决"指标怎么定义、怎么唯一、怎么治理"；本主题解决"定义怎么被自然语言命中、命中结果怎么被验证"。**接口是"指标定义 + 同义词表"**——同义词表是两者之间最容易被漏的交接物。
- **本主题 vs [Ch4 §09 统一查询网关](../../04-data-assetization/09-unified-query-gateway/09-unified-query-gateway.md)**：查询网关负责"跨源编译与下推执行"；本主题负责"生成什么样的逻辑查询"。**接口是"逻辑查询计划"**——生成段应产出逻辑计划（而非物理 SQL），由网关编译到具体引擎。
- **本主题 vs [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture.md)**：RAG 解决"从大量 schema / 文档里检索出相关上下文"；本主题解决"用这些上下文生成什么"。**关系是"检索是生成的前置"**——但在 Text2Metrics 形态下，**检索的对象是语义层条目，不是原始 schema**（这是它比 NL2SQL 更可控的原因之一）。
- **本主题 vs 传统自助 BI**：自助 BI 受限于"已定义的数据集"，但它**天然不猜**；自然语言入口扩大了可达范围，也引入了"猜"的风险。**本主题的全部设计都是在把"可达范围"扩大回来的同时，把"猜"约束住**。
- **本主题 vs [Ch8 §02 数据安全](../../08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance.md)**：可见域与脱敏必须在**召回 / 生成之前**下推（不是结果过滤）——这是同一套"前置裁剪"的要求。

> 💡 **思考锚点**：找一个你系统里被问得最多的数（"昨天的 GMV""活跃用户数"任选），回答三个问题：① 这个词在你的系统里能映射到**唯一**一个指标吗？还是有两个候选（两个口径）？② 如果业务方问"这个数是怎么算的"，你的界面能给出**可点开的定义**吗？③ 如果某个问题映射不到（"上上月的环比同比复合增长率"这种），系统会**明确说未定义**，还是会猜一个？三问里最先答不出的那一个，决定你下一步该补语义层、补口径回显，还是补"诚实拒绝"——你打算先补哪一个？
