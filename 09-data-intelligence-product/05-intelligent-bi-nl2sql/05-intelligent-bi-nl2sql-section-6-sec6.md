> - 文中数字一律标注档位：有具名出处的标【公开】，有推导链的标【推算】，只有量级与条件的标【经验】。凡本节没有给出可核验出处的精确数值，请以你自己的实测口径为准。

### 6.1 ThoughtSpot"**把自然语言查询做成"带口径的搜索"：先有语义模型，再谈对话 5+ 年**"（2019-2024）

**背景（Why）**

业务用户想"像搜索一样查数"时，最先撞上的是**"同一个词指什么"**：

- **业务词与物理字段不是一对一**——"成交额"可能对应多个物理口径；
- **用户的表述不固定**——同一个人这次说"成交额"、下次说"销售额"、再下次说"大盘"；
- **一旦允许自由生成 SQL，口径就脱离了控制**——而业务方看不出生成的 SQL 用了哪个口径。

另两条约束决定了这件事**不能靠"先做出来再补"**：

- **错误的代价不对称**：一个数被拿去汇报 / 进决策时，"错"的代价远高于"答不出来"的代价——因此**"猜一个"这条路要从设计上关掉**，而不是靠提示词劝模型别猜（§3.1 约束 2）。
- **交互形态是"搜索"**：搜索的体验预期是"立刻有话回"，没有"提工单等排期"这个中间态——**因此答案必须来自一个已经定义好的集合**，现场生成的查询在体验上也无处安放。
- **三条约束叠起来的结论**：**口径必须先存在，搜索才可能可信**。顺序颠倒时（先做搜索、后补口径），系统会在"每次都能给个数"的同时，**把口径的不确定性一起交付出去**——而这一步没有报错，也不会有人来投诉，只会慢慢表现为"同一个问题两次问出不同的数"。

**触发点（What）**

ThoughtSpot 一类搜索式分析产品把**语义模型（semantic model / worksheet）作为前置对象**（[ThoughtSpot 公开材料 2019-2024]，核验入口是其官方文档，**按当前版本核**）：用户查到的是**模型里已定义的对象**，而不是任意 SQL。它给出的判断是**"搜索"这个交互形态要求口径先行**：

- **能搜到的范围 = 语义模型的范围**——这是限制，也是**可信的来源**；
- **搜不到时给出的是"未定义"，不是猜一个**；
- **同义词是把"业务词"接进"语义对象"的唯一通道**。

**这条顺序判断的代价出现在上线当天**：能答的问题**比自由生成形态少**（搜不到就是"未定义"，不给你一个大概的数），因此业务的第一反应通常是"怎么还不如以前"。**而这正是它可信的来源**（§3.2.2 的代价一栏）——把"答不了"做成一个**明确状态**，而不是让它变成一次猜测；代价是要在上线前把这件事与业务说清楚，否则它会以"系统不好用"的形式被反馈回来。

**详细做法（How）**

**① 语义模型是产品的核心资产，不是配置**

- **关键设计**：指标、维度、时间粒度、口径、同义词都在模型里定义；用户交互的产物是**"选了哪几个对象 + 什么过滤"**，而不是一段 SQL。
- **关键能力**：**把"正确性"从生成环节挪到定义环节**——生成环节只做"选对象 + 填参数"，这两件事有明确对错（选错就是选错，可以测），而"写一段正确的 SQL"没有可测的对错参照（§3.2.2 的机制）。因此**准确率的上限由模型的完备度决定，而不由生成模型的能力决定**——这一条决定了后续所有的排期方式：缺什么补什么，而不是换模型。
- **关键性质**：**模型之外的问题会明确失败**——这条限制在产品上是"能力边界"，在工程上是**让"猜"不可能发生**（本主题 §3.2.2 的机制）。
- **关键示意**：

  ```text
  "搜索式查数"为什么要求口径先行（两种交互的可信性来源不同）
    ── 自由 SQL 形态 ────────────────────────────────
       用户："上个月华东成交额"
       系统：生成一段 SQL → 跑出来一个数
       用户看到的：一个数
       看不到的：这段 SQL 用了哪个口径
       → 正确性不可核对 → 业务不敢用
    ── 语义模型形态 ────────────────────────────────
       用户："上个月华东成交额"
       系统：映射到 metric=gmv（口径 v12）+ region=华东 + time=2024-06
       → 由模型编译查询
       用户看到的：一个数 + 用了哪个口径（可点开定义）
       → 正确性可核对 → 业务敢用
    ────────────────────────────────────────────────
   判据：用户能不能在界面上指出"这个数用的是什么口径"
  ```

  **判据**：随便挑一个界面上给出的数，**能不能在不问任何人的前提下指出它用的是什么口径**（口径名 + 版本）——能在界面上指出，说明"用户交互的产物是对象"这件事真的成立；指不出，说明它仍然产出了一段 SQL。

**② 同义词决定"能不能搜到"**

- **关键设计**：同义词不是可选项——它是"业务语言"与"语义对象"之间的唯一接口。
- **关键能力**：**它把"覆盖率"从一个不可见的量变成一个可以数的量**——每个指标补了几条同义词、哪些业务词一个都没接上，都是可以列出来的；而没有这张表时，映射失败只会被读成"搜索不好用"。
- **关键性质**：**定义对 ≠ 能搜到**——定义是对的，但用户说的词接不上，效果与"没定义"一样；这也是它与"指标定义做对了没有"分开检查的原因。
- **字段示意**（形态同本主题 §4.5 模板 1，字段名可照用）：

  ```text
  指标侧的三个字段决定"能不能搜到"（缺一个都会漏）
    synonyms: ["成交额", "销售额", "GMV", "交易额", "大盘"]
      → 缺它：用户说的词接不上，覆盖率被误判为"搜索能力不足"
    caveats:  ["含全渠道；不含已退款订单", "不含跨境业务（口径见 gmv_cross_border）"]
      → 缺它：用户把口径的边界当成"数据不全"，去追问数据团队
    default_window: 近 30 天
      → 缺它：用户说"最近"时，窗口由解析器临时决定，同一个词两次问出两个区间
    ────────────────────────────────────────────────
  判据：这三项在语义层里是"每个指标都有"，还是"只有个别指标有"
  ```

- **为什么它最容易被漏**：**它在指标定义里看不见**（定义是对的，但用户说的词接不上），因此覆盖率问题会被误判为"搜索能力不足"。

**具体数字（档位标注）**

> **先说清楚这一段的性质**：本案例的材料是**产品文档层面的机制复述**，**团队规模与内部实测值都没有可指名来源**——因此下面不给"某团队 N 人"这类数字（宁可留空，也不填一个看起来合理的区间）。要量自己这一格，用最后一条自测动作。

- 覆盖率的量级：搜索式分析在**高频同质问题**上的覆盖面可以很高，而在**长尾与复杂分析**上迅速下降【经验：随组织的取数需求集中度浮动】。**这个量级决定了什么**：它决定**该系统能承接的是"重复性问题"而不是"探索性问题"**——因此项目的收益口径要按"重复问题的接单量"算，而不是按"能不能替代分析师"算（§5.5 第 1 条）。
- 同义词规模的量级：**每个指标通常需要数条同义词**才能覆盖常见表述【经验：随业务术语的扩散程度浮动】，而这项工作**只做一次、长期受益**。**这个量级决定了什么**：它决定了**维护成本随指标数线性增长、而不随提问量增长**（§6.7 的最后一项）——所以同义词是"前期一次性投入"，不补的代价则是每次提问都要付（映射失败）。
- **自测动作**：找一份你们真实的取数问题清单，逐条问"这个词在语义模型里能不能搜到"。**搜不到的比例就是你的覆盖率缺口。** 再补一条：把"每个指标的同义词条数"与"每个指标被问到的频次"并排看一次——**频次高而同义词少的那些指标，就是最先该补的几个**（这也是估算"要几个人维护语义层"的唯一可靠办法：用你自己的增量指标数与人均可维护指标数，而不是对标本案例的团队规模）。

**失败教训**

**第一版把"能搜到"当成搜索能力问题**——于是不断优化检索与排序，而真实原因是**同义词没建**：用户说"成交额"，语义模型里只有 `gmv`。

**为什么会写成这样（机制层）**：因为**检索这一侧有现成的度量，而映射那一侧没有**——召回率、排序质量都是能立刻跑出来的数，而"业务词覆盖率"在没有同义词表之前**根本不是一个可数的量**。于是优化动作自然流向"能被度量的那个部件"：不是判断错了，而是**只有一侧有仪表盘**。这条机制解释了为什么它会稳定复发——**换一个团队、换一个产品，只要同义词仍然不可数，优化就还会流向检索**。

教训：**搜索式分析的瓶颈几乎总在"业务词到语义对象的映射"，不在检索算法**——**先把同义词补齐，比调排序有效得多。** **判据**：把"同义词条数 / 指标数"这个比值做进日常看板；这个数不涨而检索侧的调参还在继续，说明团队正在重复这个错误。

### 6.2 网易有数"**在指标体系上做自然语言取数：口径唯一是前提，不是结果 4+ 年**"（2020-2024）

**背景（Why）**

国内企业的取数场景里，"指标口径"往往已经有一套治理（指标平台 / 指标字典），而自然语言入口是**加在它之上**的一层。这一层的位置由三条约束给定：

- **口径已经有权威源**——指标平台 / 指标字典是既成的治理产物，**自然语言层不能成为第二个口径源**，否则治理成果会在入口处被复制一遍并很快分叉；
- **口径问题会被自然语言放大**——入口让同一句话触达更多人、更快，**因此一个口径分歧的传播速度也同步变快**（先建口径再开入口，抢的就是这段速度差）；
- **拒绝是有成本的**——业务被拒绝一次就会退回原来的路径（找数据团队提工单），所以拒绝必须带替代路径，否则等于把入口作废。

**触发点（What）**

网易有数一类产品把自然语言取数**建在指标体系之上**（[网易公开材料 2020-2024]，核验入口是其官方文档，**按当前版本核**）。它给出的判断是一条**顺序判断**：

- **先有口径唯一，再谈自然语言**——反过来做，自然语言入口会把口径问题放大（同一个词的不同口径被更快地、更广泛地传播出去）；
- **指标体系是输入，不是竞争者**——自然语言层不重新定义指标，它只做"从语言到指标"的映射。

**这条顺序判断的代价，是把入口的能力上限交给另一个团队的排期**：入口能答什么，取决于指标体系建了多少——**自然语言层自己再怎么优化也不会越过这条线**。反过来做的诱因很具体：入口侧可以先看到效果，而指标建设是慢活；**代价要到"业务问了入口答不上来、又回去提工单"时才显现**（§6.7 的「数据团队负载」（临时取数工单条数）与「覆盖率」（能映射到指标的问题占比）两行度量的正是这两件事）。

**详细做法（How）**

**① 指标口径作为映射的目标集合**

- **关键设计**：映射的候选集合**就是指标平台里的指标**（含维度与时间粒度），因此**"能不能答"直接等于"指标覆盖了多少高频问题"**。
- **关键能力**：**它把"答不上来"从一次失败变成一条需求**——每一次拒绝都携带"缺的是哪个指标"，于是指标建设的输入来自真实频次，而不是内部会议里的印象（§4.1 Step 1 与它同源）。
- **关键性质**：**这条设计让"该补什么"变得可计算**——把被拒绝的问题按"缺哪个指标"归集，就得到了指标建设的排期清单（这比"我们觉得该建哪些指标"可靠得多）。
- **归集的字段示意**（这是"拒绝"要留下来才能用的东西）：

  ```text
  一次拒绝要记录什么，才可能变成需求（缺任何一项，归集就做不成）
    问句原样       "上个月的同学录转化"
    失败原因       unmapped / ambiguous（两类要分开，混在一起就归错人）
    ↓ 若是 unmapped
    最接近的候选   [metric: lead_conversion_rate, metric: contract_convert_rate]
    缺什么         缺指标（要新建）/ 缺同义词（定义已有，词没接上）
    ↓ 若是 ambiguous
    候选各自的口径与版本  （这就是澄清要展示的那两个选项）
    用户最终选了谁        （没选就应记为"仍未定义"，不许替他选）
    ────────────────────────────────────────────────
  判据：这张表能不能按月导出，并按"缺什么"分组计数
  ```
- **判据**：按"缺指标 / 缺同义词"两类分开计数——**两类混在一起时，团队会去新建指标，而真正缺的可能只是几条同义词**（成本差一个数量级）。

**② 拒绝与引导是一等交互**

- **关键设计**：映射不到时给出**最接近的指标候选**，并引导到"自助分析"路径。
- **关键能力**：**它保住了入口的使用量**——只用"答不了"处理拒绝，业务会退回提工单，而**退回之后你就再也看不到真实问题了**（覆盖率随之失去观测面，§5.7 第 5 条）。
- **关键性质**：**替代路径的质量决定拒绝是不是"一等交互"**——给候选是把用户推向正确口径，只报失败则是把用户推回原路。
- **为什么**：如果只报"答不了"，业务会认为系统没用；**给出候选与替代路径，把"答不了"变成"这里没有，但你可以这样拿到"**。
- **判据**：被拒绝的那批提问里，**有多少比例在同一次会话内被用户用候选或替代路径解决**——这个比例决定"拒绝"是被接受的分流，还是被当成故障。

**具体数字（档位标注）**

> **先说清楚这一段的性质**：本案例可举证的部分只有**机制与年份区间**，**团队规模与内部实测值都没有可指名来源**——因此下面不给"某团队 N 人"这类数字。要量自己这一格，用最后一条自测动作。

- 被拒绝问题的归集收益：**每一条被拒绝的问题都是一条指标需求**——按"缺哪个指标"归集后，指标建设的优先级**由真实频次决定**，而不是由主观判断【推算：归集成本 ≈ 一次问题分类；收益 ≈ 指标排期的准确度提升，两者都随问题量增长】。**这个量级决定了什么**：它决定了**排期这件事可以从"讨论"变成"取数"**——归集的成本随问题量线性增长，而排期的准确度提升是一次性的、可复用的，所以问题量越大，这笔账越划算。
- 映射失败率的正常区间：**上线初期较高是正常的**（同义词与指标都不全），关键是**它是否随指标补充而下降**【经验：请用你自己的失败率趋势线判断，而不是对标一个数字】。**这个量级决定了什么**：它决定了**判据只能是"趋势"而不是"绝对值"**——拿一个行业数字来对标，会把"上线第二周"的正常状态判成故障，也会把"指标停更三个月"的停滞判成正常。
- **自测动作**：把最近一个月的"答不了"问题导出，按"缺哪个指标 / 缺哪条同义词"归集一次——**归集结果就是你下一季度的指标建设清单**。再补一条：给这张清单加一列"问到的频次"，**频次最高的前十条就是这一季度的全部排期**；要估"要几个人"，用你自己的增量指标数除以人均可维护指标数。

**失败教训**

**第一版把映射失败当成"模型能力不足"**——于是换模型、调提示，失败了三个月；真正的原因是**指标只覆盖了不到一半的高频问题**。

**为什么会写成这样（机制层）**：因为**"换模型"是这一层唯一一个可以立刻动手、且有现成对照的旋钮**——提示词改完就能重跑一批样本，模型换完就能看到一个数；而"指标覆盖了多少高频问题"**要先有归集表才可数**，它在第一版里根本不存在。于是**可动的旋钮被动了，不可见的原因没被动**——三个月的时间花在了唯一能立刻看见反馈的那个方向上。这与 §6.1 的机制是同一个：**优化总是流向"有仪表盘的那一侧"。**

教训：**映射失败率是"覆盖率"的度量，不是"模型能力"的度量**——**先看被拒绝的问题集中在哪些指标上，再决定优化方向。** **判据**：优化动作与"被拒绝问题的 Top 指标"是否对得上；对不上，就是又回到调模型了。

### 6.3 Metabase"**把生成的查询展示给用户：可解释性来自可见的 SQL 3+ 年**"（2019-2024）

**背景（Why）**

自助分析工具有一类用户是**分析师**——他们**不满足于"系统给的数"**，他们要**看到数是怎么来的**：

- 分析师要复核口径（"你这里 join 对了没有"）；
- 分析师要改造查询（"加一个维度看看"）；
- 分析师要向业务解释（"这个数是这么算的"）。

但"可解释性"不是一档东西，这一节的位置由三条约束给定：

- **使用者不是一个角色，而是三个**——业务方、分析师、以及（后来的）Agent / 系统调用，"什么算依据"对三者完全不同；
- **每一档回显都是一套实现**——给业务方的口径说明、给分析师的 SQL、给系统的结构化字段**不是同一个开关的三档**，而是三条要分别维护的产出（§3.2.6 的代价③）；
- **复核必须发生在当时**——数被引用之后再去追口径，成本已经随场景（会议、汇报）上去了，因此**依据要跟着结果一起到达**。

**触发点（What）**

Metabase 一类工具把**"查询可见、可编辑、可保存"**作为核心交互（[Metabase 公开材料 2019-2024]，核验入口是其官方文档 / 仓库，**按当前版本核**）。它给出的判断是**用户分层**：

- **对业务方**：给结果 + 口径说明（SQL 是噪声）；
- **对分析师**：**给 SQL**（这是他们信任的来源，也是他们改造的起点）；
- **对系统**：给结构化的口径字段（指标名 + 版本 + 过滤）。

**这条分层判断的代价是"三套产出要同时成立"**：少一套，就有一类角色拿不到他要的依据（§3.2.6 的失效点）；而**三套都做对之后，还有一条更隐蔽的代价——它们必须绑在同一个版本上**：口径改一次，三处都要跟着变，否则**回显在变更后会说谎，比不回显更糟**（§3.2.6、§4.2 第（6）点要求回显带 `caliber_version`）。

**详细做法（How）**

**① 同一份结果，三种回显**

- **关键设计**：回显内容**按角色分层**，而不是同一个开关。
- **关键能力**：**它把"信任"从"相信系统"转移到"可以自己核对"**（§3.2.6 的机制）——这一点与模型准确率无关：即使系统完全准确，**没有依据的数在组织里也无法被采用，因为它无从复核**。
- **关键性质**：**分层不是"温和一点"，而是"同一个数对三种角色各交付一次"**——回显粒度的差异来自三个角色"拿它去做什么"的差异，而不是舒适度差异。
- **结构示意**（同一份结果的三种交付形态）：

  ```text
  一份结果 → 三条交付路径（少一条，就有一类角色拿不到依据）
    业务方   口径说明 + 可点开的定义页
             用它做什么：做决策、向别人解释这个数
             给了 SQL 会怎样：看不懂 → 可解释性做了但没起作用
    分析师   可见 / 可编辑的 SQL + 指标名与版本
             用它做什么：复核 join 与过滤、改造成新查询
             只给口径说明会怎样：他还是自己写一遍 SQL
    系统 / Agent   结构化字段（指标名 + caliber_version + 过滤 + 时间语义）
             用它做什么：跨系统传递"这个数是什么"，而不是转述一段话
    ────────────────────────────────────────────────
  判据：改一次口径定义（版本 +1），三处是否都跟着变
  ```

- **为什么**：把 SQL 给业务方看是**做了可解释性却没起作用**（看不懂 ≠ 可核对）；而对分析师只给口径说明是**不给他干活需要的东西**（他要改）。**分层的判据是"这个角色要用它做什么"。**

**② 查询可保存、可复用**

- **关键设计**：查询（含参数）可以保存与分享，**分享的是"查询"而不是"结果"**。
- **关键能力**：**它让"可复用"从"可重看"变成"可重算"**——同一条分析下个月还能跑出当月的数，而不是把一张过期的截图转来转去。
- **关键性质**：**保存物决定它的保鲜期**——保存结果，保鲜期由上游变更频率给定（变了就过期，且不报错）；保存查询，保鲜期只受定义本身约束。
- **为什么**：结果会过期，查询可以重算。**这条与 [Ch9 §04 §3.2.8](../04-smart-tag-platform/04-smart-tag-platform-section-3-sec3.md) 的"分群保存条件而不是名单"是同一条理**——它把"可复用"实现成了"可重算"。
- **判据**：看被分享出去的是"查询（含参数）"还是"结果快照"——**过一段时间回访，前者仍能重算，后者已经对不上上游**；这也是判断一个自助分析工具做到哪一层的现成入口。

**具体数字（档位标注）**

> **先说清楚这一段的性质**：本例的可举证部分是**开源工具的产品交互形态**（可核验入口是其官方文档 / 仓库），**团队规模不是本案例的判据**，因此不给"某团队 N 人"这类数字；两条量级只标注档位，请用最后一条自测动作换成你自己的数。

- 分析师的复核成本：把查询展示出来后，**"这个数怎么来的"从"问数据团队"变成"自己看一眼"**【经验：单次耗时从小时级降到分钟级】。**这个量级决定了什么**：它决定了**复核可以从"一次请求"变成"一个动作"**——只有落在分钟级，复核才可能发生在"用这个数之前"；留在小时级（要排队、要等回复）时，复核在实际流程里会被跳过，而**被跳过的复核等于没有可解释性**。
- 保存查询 vs 保存结果的差异：**结果会随上游变化而过期，而查询不会**【推算：过期风险的来源是上游表与口径的变更频率，两者都可观测】。**这个量级决定了什么**：它决定了**过期风险是一个可以提前算出来的量**——用你自己的上游变更频率（表变更次数 / 口径版本迭代次数）乘上被分享出去的保存物数量，就得到过期风险的总量级；**它随上游变更频率增长，而不随用户数增长**，所以治理动作应该放在"改了多少上游"，而不是"用了多少人"。
- **自测动作**：问一个分析师——"你上次复核一个数，花了多久？中间有没有问过数据团队？"**答案决定你的可解释性做到了哪一层。** 再补一条：数一数你们分享出去的分析里，保存的是"查询"还是"结果截图"——**前者的比例，就是可复用做到位的比例**。

**失败教训**

**第一版只给了"口径说明"**——业务方看不懂、分析师不满足（他要改）。结果是**可解释性做了但没用起来**：业务仍来问数据团队，分析师仍自己写 SQL。

**为什么会写成这样（机制层）**：因为**"口径说明"是三种回显里唯一一个不需要理解使用者就能产出的**——它由系统的指标对象直接渲染而来，写一次就都有了；而"给分析师 SQL"要求系统愿意把生成的查询暴露出去（涉及安全与"看得懂的人会不会挑出问题"的顾虑），"给系统结构化字段"要求先把口径做成一等字段（而不是界面文案）。**于是实现成本最低的那一档被做完了，而它恰好只服务其中一个角色。**这与 §6.2、§6.1 是同一条机制：**做的人会先做那个不需要与别人协商的部件。**

教训：**可解释性要按角色分层**——**同一份依据，对不同的人要用不同的形态交付。** **判据**：三种形态各自有没有被真实使用过（业务方点开过定义页、分析师用回显的 SQL 改出过新查询、系统字段被下游消费过）；**只要有一档从没被用过，就说明它其实没被交付到那一类人手里。**

### 6.4 某零售企业"**先建指标语义层、再上 NL2SQL：顺序反了要重做 3+ 年**"（2021-2024）

> **来源声明**：本例为**匿名案例**——不给可指名的来源，只作机制示例、不作举证（同 [Ch4 §05 RAG 架构](../../04-data-assetization/05-rag-architecture/05-rag-architecture-section-6-sec6.md) 对匿名案例的处理口径）。

**背景（Why）**

业务方希望"直接问系统"，数据团队于是先做了**自由生成 SQL** 的版本（schema 喂给模型 + 执行沙箱）。这一节的处境由三条约束给定：

- **口径当时不唯一**——"成交额"在组织里至少有两个理解（下单金额 / 确认收入），**而这一点在系统里没有任何地方被表达出来**；
- **用户预期是在使用中建立的，不是在上线文档里**——上线时写"能力有限"没人读，用户预期由"他上一次问到了什么"给定；
- **这类系统没有错误信号**——错口径的查询**跑得通、数看着合理、也没有告警**，因此它不会自己暴露，只会被外部（财务、审计）发现。

**触发点（What）**

**一次数进错了汇报**：系统把"成交额"落到了"下单金额"的口径上（语法完全正确、数看着合理），业务方拿着它做了汇报，事后被财务指出口径不对。**追查时发现的不是 bug，而是结构问题**——系统从来没有"口径"这个概念，每次问都是一个独立的生成结果。

**这条触发点的代价有两层，第二层比第一层贵**：第一层是那次汇报本身（数错了）；**第二层是追查**——因为每次问都是独立生成，**没有"上一次用的是什么口径"这个字段**，所以既无法证明"只有这一次错"，也无法找出"还有多少次同样错了"。**一个错误之所以能变成一次事故，是因为它不可枚举**（§2.2 的错误分类 ④⑤：口径错没有客观判据，因此也不会留下可检索的痕迹）。

**详细做法（How）**

**① 先把口径立起来（顺序修正）**

- **关键设计**：先建语义层（指标定义 + 同义词 + caveats），**把自然语言入口的目标集合从"schema"改成"指标"**；再让模型只做"选指标 + 填参数"。
- **关键能力**：**它把"错得静默"换成"答不了"**——修正前的系统没有失败状态（永远能生成一段 SQL），修正后**"未定义"成为一个可见状态**，于是覆盖率第一次可测（§5.7 第 5 条：先有拒绝，覆盖率才是一个可测量的数）。
- **结构示意**（顺序修正改的是哪一步）：

  ```text
  修正前：问题 →（schema 全量）→ 模型自由生成 SQL → 执行 → 一个数
                       ↑
                  口径在这条链路上没有任何位置
  ────────────────────────────────────────────────
  修正后：问题 → 映射到指标（含口径与版本）→ 语义层编译查询 → 执行 → 数 + 口径
                       ↑                        ↑
                  口径在这里被选中          这里的 SQL 不由模型写
                  （选不中就是 unmapped）     （因此没有"猜"这个动作）
  ────────────────────────────────────────────────
  顺序修正的关键是：把"口径"从一个事后解释改成链路里的一个必填字段
  ```
- **判据**：抽一次提问的执行记录，**能不能读出"用了哪个指标的哪个版本"**——读不出，说明修正只做在界面层，链路里仍然没有口径的位置。
- **为什么顺序不能反**：**自由生成阶段积累的是"用户预期"**——用户已经习惯了"什么都能问"，回头做语义层意味着**功能变少**（一部分问题会被明确拒绝），组织阻力显著上升。**本例中这一步的沟通成本超过了技术成本。**

**② 把已积累的高频问题作为语义层的输入**

- **关键设计**：把自由生成阶段记录的真实问题**导出、归并、按频次排序**，作为指标建设清单。
- **关键能力**：**它把过渡期从"技术债"变成"需求采集期"**——同一批问题在修正后既是被拒绝的那批，也是排期的输入；**前提是它在自由生成阶段就被记下来了**（没记录时这段产出为零，见 §6.6 坑表"自由生成阶段无记录"）。
- **关键性质**：**这份清单的价值与它来得早晚无关，只与它真不真实有关**——它是唯一一份来自真实使用、而不是来自会议的问题分布。
- **为什么**：这让"过渡期"变成**有产出的一段**——它不是白做，它产出了**最准确的需求清单**（这是自由生成形态唯一的不可替代价值，§3.2.1）。
- **判据**：这份清单在修正后有没有真的被用来排期（指标定义里能否指认出"它来自哪条高频问题"）；**指认不出来的，就是白采了一场**。

**③ 拒绝路径与引导**

- **关键设计**：映射不到时明确拒绝 + 给候选 + 引导自助分析。
- **关键能力**：**它把"回流"堵在入口**——没有它，用户会自己找路，而找到的那条路（自由生成 / 换个说法再问一次）**恰好是口径风险最强的入口**。
- **关键性质**：**拒绝必须是终点，而不是提示**——所以它同时要给候选（近的）与自助分析（远的），否则用户只会换一种说法重试。
- **为什么必须**：否则用户会继续在自由生成的路径上想办法（"换个说法再问一次"），而**那正是口径风险回流的入口**。
- **判据**：数一数"连续换说法重试"的会话比例——**这个比例上升，说明拒绝被当成了障碍而不是分流**。

**具体数字（档位标注）**

> **先说清楚这一段的性质**：本例是**匿名案例，不给可指名的来源、不作举证**（见本节开头的来源声明），**团队规模同样没有来源**——因此下面不给"某团队 N 人"这类数字，只给量级与可自测的推导链。

- 迁移期的"能力感知下降"：从自由生成迁到语义层后，**能答的问题数量会先下降**（未覆盖的从"总能给个数"变成"明确拒绝"）【经验：下降幅度取决于原覆盖率】，**因此需要提前与业务沟通口径**。**这个量级决定了什么**：它决定了**这次迁移在体感上是一次"功能下线"而不是"功能升级"**——所以它必须配一次沟通，而沟通的对象是已经形成预期的用户，不是新用户。
- 口径错的事故成本：本例中一次错口径进入汇报，处理耗时以人周计，且**影响了数据团队的可信度**【经验：随汇报层级与对外程度上浮】。**这个量级决定了什么**：它决定了**上限不由技术团队控制**——同一处错误在团队内部是一小时的事，进了对外汇报就是以人周计的事，**因此"要不要拒绝"这个决定应该按最坏场景定，而不是按平均场景定**（§3.1 约束 2：错误代价高时，"猜"绝对不可接受）。
- **自测动作**：如果你的系统现在是自由生成形态，导出最近一个月的问题清单，**看有多少能归纳成可定义的指标**——那个比例就是迁到语义层的覆盖率上限。再补一条：把这份清单里**"同一句话被不同人问过"的条数**数出来——**这类重复的条数越多，迁移的收益越早兑现**（它们是最先被语义层接住的部分）。

**失败教训**

**把"先跑起来"理解成"先做生成"**——技术上是先跑起来了，但它**同时建立了一个错误的用户预期**，而预期是最难回退的东西。

**为什么会写成这样（机制层）**：因为**"先做生成"是所有路径里唯一一条当天就能演示的**——schema 一喂，问题一问，屏幕上就出来一个数；而"先收集问题、再建口径"的第一天产出是一张清单，**它不能演示、也不能说明系统聪明**。于是**演示压力选了那条看起来更快、其实把代价推到后期的路**。这条机制与团队水平无关：**只要评审方式还是"看演示"，这条路就会被再选一次。**

教训：**在口径尚未统一的组织里，正确的"先跑起来"应该是"先收集问题、再建口径"，而不是"先让模型自由生成"**——两者都能快，但前者产出的需求清单可以在后期直接用，后者产出的预期必须在后期被撤回。**判据**：立项时问一句"第一天要演示什么"——**如果答案必须是一个能答对的数，那这条路径的起点就已经选错了**；正确的第一天演示物是**问题清单 + 歧义词名单**（它同样能演示，只是它证明的是"我们量过"，而不是"系统会答"）。

### 6.5 真实落地路径（基于上述 4 个案例提炼）

四个案例拼起来是一条顺序固定的路径，与 §4.1 的八步对应：

1. **先收集真实问题分布**（§6.4 的修正动作）——这一步不依赖任何技术选型，且产出物（问题清单）在后面每一步都有用。
2. **再建语义层（含同义词与 caveats）**，把目标集合从 schema 换到指标（§6.1、§6.2）——它是"可信"的来源；**同义词是这一步最容易被漏、而影响最大的一项**。
3. **然后装拒绝路径与引导**（§6.2、§6.4）——**先有拒绝，覆盖率才是一个可测量的数**（否则系统会把没覆盖的也答出来）。
4. **最后按角色分层回显**（§6.3）——业务方看口径、分析师看 SQL、系统看字段；**回显要绑到实际执行的指标版本**。

**顺序的反面**：**先做自由生成、后建语义层**（§6.4）——技术上的代价可接受，**真正的代价是用户预期**：从"什么都能问"退回"一部分明确拒绝"，这一步的沟通成本常常超过技术成本。**第二条反面**：**先做回显、后做语义层**——回显的来源如果是"提示词"，它在口径变更后会说谎；**回显必须来自语义层的实际执行对象。**

### 6.6 踩坑与经验（4 个案例提炼）

| 坑 | 症状 | 机制层面的后果 | 修法 |
| --- | --- | --- | --- |
| 同义词没建 | 业务词搜不到 | 覆盖率被误判为"搜索能力不足" | 每个指标补同义词（§6.1） |
| 把映射失败当模型问题 | 反复换模型与调提示 | 真实瓶颈（覆盖率）没被看见 | 归集被拒绝的问题到"缺哪个指标"（§6.2） |
| 先自由生成后建语义层 | 用户预期已建立，回退时阻力大 | 功能感知下降 + 沟通成本高 | 先收集问题、再建口径（§6.4） |
| 只给口径说明不给 SQL | 分析师仍自己写 SQL | 可解释性做了但没用起来 | 按角色分层回显（§6.3） |
| 只给 SQL 不给口径说明 | 业务方看不懂、不敢用 | 可解释性对业务无效 | 同上 |
| 回显来自提示词 | 口径变了界面说明没变 | 回显说谎，比不回显更糟 | 绑到实际执行的指标版本 |
| 拒绝只报"答不了" | 用户认为系统没用 | 拒绝路径被绕过（换个说法再问） | 给候选 + 引导自助分析 |
| 没有 `unresolved` 字段 | 限定条件被静默丢弃 | 结果看起来回答了问题、实则忽略了条件 | 意图对象加 `unresolved` 并触发澄清 |
| 时间边界混用 | "上周"与"最近 7 天"混同 | 静默的数值偏差 | 四种时间语义都要有测试用例 |
| 自由生成阶段无记录 | 迁到语义层时没有需求清单 | 过渡期的产出被浪费 | 从第一天起记录真实问题 |
| 语义层无 Owner | 半年后出现大量歧义词 | 同一问题不同口径 | 指标与同义词有 Owner 与增删流程 |
| 校验只报 EX | 指标好看但业务不信任 | 评测偏差掩盖口径错 | 同时报 `CR` 与 `HR` |

### 6.7 ROI 评估（4 个案例的量级账，**非实测**）

> **声明**：下表是**量级口径的估算框架**，用于说明"收益落在哪一块"，**不是任何一家组织的实测数据**；每项都给出可自测的动作，请用你自己的基线替换。本节不给"某公司实测提升 N%"这类数字——智能 BI 的收益形态是"取数时长、口径一致性、可核对性"，前两者可量，第三者只能用"能不能答"来判。

| 收益项 | 计量口径 | 量级（【经验】） | 自测动作 |
| --- | --- | --- | --- |
| 取数时长 | 从提问到拿到可用数的端到端时长 | 高频同质问题从**小时到天级（排队）**降到**分钟级** | 抽 20 个高频问题测端到端时长 |
| 数据团队负载 | 临时取数工单的条数 | 高频同质部分显著下降；**长尾不变**（且被明确拒绝） | 统计一周内工单数与其中"同类重复"比例 |
| 口径一致性 | 同一问题在不同时间 / 不同人问到的口径是否相同 | 从**不可控**到**唯一**（歧义词数 0） | 抽 20 个高频词数歧义 |
| 可核对性 | 用户能否看到"这个数怎么来的" | 业务方：口径可点开；分析师：SQL 可见 | 问一个分析师上次复核花了多久 |
| 覆盖率 | 能映射到指标的问题占比 | 无通用值；**关键是它能被测量**（有拒绝路径之后） | 导出被拒绝的问题并归集 |
| 口径错的事故 | 错口径进入汇报 / 决策的次数 | 从**偶发**到"由语义层从机制上排除" | 数最近一年此类事件 |
| 代价 | 语义层维护 + 评测 + 澄清与拒绝的运营 | **人力随指标覆盖广度增长**，不随提问量增长 | 按月核算这类人力占团队比例 |

**读法**：前三项是**效率与一致性收益**（取数时长、团队负载、口径唯一），第四、五项是**可达性收益**（能不能核对、覆盖率能不能测量），第六项是**风险收益**（错口径事故）。**本主题最容易出现的错位是只算"能答多少问题"，不算"口径唯一与可核对"**——前者是覆盖面，后者才是业务敢用它的原因。**另一条读法**：最后一项里"澄清与拒绝的运营"看起来是成本，但它对应的是第五项（覆盖率可测量）——**砍掉它，你就失去了唯一能看见覆盖率的手段。**

> 本节小结：四个案例的先后顺序不是偏好而是依赖——**先收集真实问题分布**（它决定后面所有排期），**再建语义层含同义词**（可信的来源），**然后装拒绝路径**（先有拒绝，覆盖率才可测），**最后按角色分层回显**（可核对性是业务敢用的原因）。四次失败教训指向同一件事：**智能 BI 的失败几乎都不是"模型写不出 SQL"，而是"数出来了但说不清用了什么口径、或者根本不该答而答了"**——说不清就没有信任、不该答而答了就是静默的口径风险。

> 💡 **思考锚点**：从 §6.1–§6.4 里挑一个与你处境最像的案例，只做一件最小的事——按它的"判据"跑一次自测（找一份真实问题清单逐条查能否搜到 / 导出被拒绝的问题归集 / 问分析师上次复核多久 / 数 20 个高频词的歧义）。哪一件**今天就能做**就先做它：**智能 BI 的腐化不会报错，只会让同一个问题慢慢落到不同的口径上。**
