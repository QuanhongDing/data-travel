#### §8.1 业务问了一句"上个月华东的成交额同比是多少"，你们的系统会怎么答？怎么保证这个数可信？

**1. 考察点**
- 是否理解链路的四段（理解 / 映射 / 生成 / 执行）与各自的错误形态；
- 是否知道**口径是可信的来源**，而不是模型；
- 有没有可核对的依据（口径回显）。

**2. 参考答案框架**

**第一层：给出链路与每一格可能出的错。**

```
"上个月华东的成交额同比是多少"
  → 理解：抽 metric / filters(region=华东) / time(2024-06, compare=yoy) / grain
       错法：把"同比"漏掉（→ 结果看起来回答了、实则忽略了限定）
  → 映射：落到语义层的 gmv（口径 v12）
       错法：落到"下单金额"（语法全对、口径全错）
  → 生成：由语义层编译（不是模型写 SQL）
  → 执行：沙箱 + 权限裁剪
       错法：权限裁空却提示"没有数据"
```

**第二层：说明可信从哪里来。** **不是"模型更准"，而是"这次用了哪个口径可被指出"**——所以返回里必须带 `metric` + `caliber_version` + `time_semantics` + `filters`，并允许点开定义。**判据**：用户在界面上能不能指出"这个数用的是什么口径"。

**第三层：给出可复现性。** 口径版本固定 + 时间语义为快照 ⇒ **同一问题在不同时间问到同一个数**。若系统对它两次生成不同 SQL，则**不可复现**——而"两次都看着合理"正是最危险的情形。

**第四层：给出拒绝与澄清。** "同比"若解析不出 → `unresolved` 非空 → **澄清**（而不是丢掉）；"成交额"若映射到多个指标 → `ambiguous` → **澄清（给候选）**（而不是静默选一个）。

**3. 常见陷阱**
- 只答"模型会生成 SQL 并执行"，不谈口径；
- 把"同比"当默认值处理（丢掉限定）；
- 没有口径回显，或回显来自提示词；
- 不提 `ambiguous` / `unmapped` 两条分支。

**4. 追问预测**
- "如果同一个问题两次生成不同 SQL 但都对，这算不算问题？"
- "澄清与执行反馈，你会怎么分工？"
- "口径版本变了之后，用户看到的说明怎么跟着变？"
- "这个数被写进汇报之后，财务说口径不对，你怎么处理？"

**5. 参考资料**
- 本主题 §2.2（链路错误分解与错误分类）、§2.3（结果校验）、§3.2.2（语义层映射）、§3.2.6（口径回显）、§4.2（6）（回显实现要求）。

#### §8.2 NL2SQL 与 Text2Metrics，你会选哪个？为什么"先建语义层"是唯一正确的顺序？

**1. 考察点**
- 是否知道两者的**正确性来源不同**（模型能力 vs 语义层完备度）；
- 是否理解 NL2SQL 的失败形态（**语法对、口径错**）业务方看不出；
- 有没有顺序意识（先跑起来 ≠ 先做生成）。

**2. 参考答案框架**

**第一层：给出对照。** NL2SQL 让模型**写 SQL**，正确性来自模型能力，错误形态是"语法对但口径错"；Text2Metrics 让模型**从已有指标里选**，正确性来自**语义层完备度**，映射不到时**明确说"未定义"**。

**第二层：说明为什么口径错最危险。** 三类错误里——语法错会报错、连接错会导致量级异常、**口径错什么都不会发生**（SQL 能跑、数看着合理），而它会直接进入决策。**因此"业务方能看出错吗"这条判据把 NL2SQL 排除在长期形态之外。**

**第三层：给出顺序论证。** 反过来做（先做生成）的代价不是技术性的，而是**用户预期**：先上线自由生成，用户习惯"什么都能问"；回头做语义层意味着**一部分问题被明确拒绝 → 功能变少**，沟通成本常常超过技术成本。**而在"先收集问题、再建口径"的路径里，同样的时间产出的是需求清单**（后期直接可用）。

**第四层：给出过渡方案。** 口径未统一时并非不能动——**可以上直连 NL2SQL 作过渡，但从第一天起记录真实问题**，并声明它是过渡态（有"高频问题 → 是否已被语义层覆盖"的清单）。**没有这张清单，过渡期会变成终点。**

**3. 常见陷阱**
- 只比较"准确率"，不谈错误形态；
- 认为"模型再强一点就能解决"（公共基准是单库、schema 干净、无业务口径的设定，不能外推）；
- 把"先跑起来"理解成"先做生成"；
- 上了直连 NL2SQL 但没记录真实问题。

**4. 追问预测**
- "过渡期多长算合理？判据是什么？"
- "如果业务坚持要自由生成，你怎么处理？"
- "语义层的覆盖率上不去，是模型问题还是维护问题？"
- "Text2Metrics 做不了的复杂分析，怎么引导？"

**5. 参考资料**
- 本主题 §1.1（对照表与判据）、§1.4（演进历程）、§3.2.1（直连的过渡定位）、§6.4（顺序反了的案例）、§5.5（公共基准不能外推）。

#### §8.3 系统生成了一段 SQL，怎么判断它写得对不对？执行报错能修，口径错了怎么办？

**1. 考察点**
- 是否知道**执行反馈只能闭环语法类错误**；
- 是否理解"多轮修正会让口径错更隐蔽"；
- 有没有把"错误分流"设计出来。

**2. 参考答案框架**

**第一层：先把错误分类，再说各自的闭环手段。**

```
① 语法错      → 执行报错即可发现 → 反馈闭环可修
② 表/列选错   → 执行可能成功、结果错 → 需结果校验或人工
③ 连接错      → 量级异常 → "结果合理性"检查可捕获一部分
④ 聚合/粒度错 → 数看着合理 → 最难发现
⑤ 口径错      → 业务方看不出 → **必须靠语义层与口径回显**
⑥ 权限错      → 必须前置拦截
```

**第二层：给出结论。** **执行反馈能闭环的是 ①③（部分）；④⑤ 闭环不了，必须靠语义层；⑥ 必须靠前置裁剪。** 因此"加了反馈就稳了"是错的。

**第三层：说清反馈的危险面。** 多轮修正会把一段**错误口径**的 SQL 改得**更像真的**（跑得通、数合理、还加了注释），**因此反馈闭环越顺，口径错越隐蔽**。**判据**：反馈循环修改的对象是"语法与表列"还是"指标与口径"——后者必须走澄清。

**第四层：给出两条通道的分工。** 语法类错误 → 执行反馈（带轮次上界）；口径类歧义 → 澄清（给结构化候选）。**两条通道在实现上必须分开**——合并会让"用反馈试口径"自然发生。

**3. 常见陷阱**
- 把执行反馈说成能解决所有错误；
- 没有轮次上界；
- 用反馈去"试不同口径直到有数"；
- 不做结果合理性检查（③会被漏掉）；
- 权限用结果过滤而不是前置裁剪。

**4. 追问预测**
- "结果合理性检查怎么实现？阈值怎么定？"
- "反馈轮次上界设多少？超界之后怎么办？"
- "怎么发现口径错？有自动手段吗？"
- "语义层映射形态下还会不会有③④类错误？"

**5. 参考资料**
- 本主题 §2.2（错误分类与能闭环的范围）、§3.2.4（执行反馈的失效点）、§3.2.5（澄清）、§4.2（4）（两通道分流）。

#### §8.4 你们准备上线"自动洞察"（主动推送异常）。你怎么判断它会不会变成噪声源？

**1. 考察点**
- 是否理解**发现异常容易、"该不该打断用户"很难**；
- 有没有把**采纳率**当成前置指标；
- 是否知道它必须建在语义层之上。

**2. 参考答案框架**

**第一层：先承认卡点在哪。** 发现异常是统计问题（有客观判据）；**判断"这条洞察是否值得打断用户"是注意力分配问题**（取决于用户当前在做什么）。这一条没有通用答案，因此本方向停在 L3（§5.3.4）。

**第二层：给出前置条件（缺一不可）。**
- **必须建在语义层之上**——建在自由查询上会把口径噪声放大成结论；
- **必须有采纳率指标**——没有它，洞察会稳定退化为噪声源（同 [Ch10 §02 §3.2.7](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的频控问题）；
- **必须分级下发**——高重要性（显著偏离 + 可归因）即时推送，中低重要性进"待看"列表。

**第三层：给出最小版本。** **先不做主动推送**，只做"把异常放进待看列表"，统计采纳率；**采纳率稳定在可接受水平之上，再谈推送**。这条路径的代价极低，而它能**在没有打扰任何人的前提下**回答"这个洞察值不值得推"。

**第四层：给出归因的口径要求。** "主要来自华东"要说清是**相关**还是**因果**，以及归因基于什么维度分解——**否则用户会把一个统计现象当成原因。**

**3. 常见陷阱**
- 直接上推送，不设采纳率；
- 把"发现了多少异常"当成成功指标（那是发生率，不是价值）；
- 洞察建在自由查询上；
- 归因不区分相关与因果；
- 没有分级，所有洞察同等推送。

**4. 追问预测**
- "采纳率怎么定义？用户看了算采纳吗？"
- "异常检测的阈值怎么定才不会天天报警？"
- "归因用哪些维度？维度组合爆炸怎么办？"
- "如果洞察和用户已有的报表重复，怎么处理？"

**5. 参考资料**
- 本主题 §2.3（自动洞察的误报控制）、§3.4（主动组合）、§5.3.4（为什么停在 L3）、§4.8（10→100 阶段）。

#### §8.5 一个分析师说"我不信这个数"，你会给他看什么？如果换成业务方呢？

**1. 考察点**
- 是否理解可解释性要**按角色分层**；
- 是否知道"给业务方看 SQL"是无效的；
- 有没有把回显绑到**实际执行的指标版本**。

**2. 参考答案框架**

**第一层：给出分层。**
- **分析师**：给**可见 SQL**（他要复核 join 与聚合，也要改造）；加口径说明；
- **业务方**：给**口径说明 + 可点开的定义**（不含 SQL）；给对比基准与异常提示；
- **系统 / Agent**：给**结构化字段**（`metric` / `caliber_version` / `time_semantics` / `filters`）。

**第二层：说明为什么单一形态无效。** 只给口径说明 → 分析师仍自己写 SQL（可解释性没作用）；只给 SQL → 业务方看不懂（"可核对"没实现）。**判据是"这个角色要用它做什么"。**

**第三层：给出回显的实现要求。** 回显**必须来自实际执行的指标对象**（带 `caliber_version`），不是提示词、不是检索片段。**判据**：改一次指标定义，界面说明**跟着变**——不跟，说明回显来自别处，它会在口径变更后说谎。

**第四层：给出"不信"的最强回应。** 除了回显，还有两件：**可复现**（同一问题问到同一个数，且带生成时刻）与**可重算**（分析师能拿着 SQL 自己跑一遍）。**三者合起来才构成"可核对"。**

**3. 常见陷阱**
- 给业务方看 SQL；
- 只给口径说明不给 SQL；
- 回显来自提示词或缓存；
- 回显不带口径版本（变更后对不上）；
- 拿"模型很准"来回答"我不信"。

**4. 追问预测**
- "回显里的 SQL 与语义层编译出来的 SQL 是同一段吗？"
- "如果分析师改了 SQL 再跑，结果不同，怎么解释？"
- "口径变更后，历史结果的回显怎么办？"
- "面向 Agent 的回显要哪些字段？"

**5. 参考资料**
- 本主题 §2.1（口径可见性）、§3.2.6（口径回显）、§4.2（6）（回显实现要求）、§6.3（Metabase 的分层做法）。

#### §8.6 自然语言取数的成本，你觉得大头在哪？怎么控制？

**1. 考察点**
- 是否知道**一次自然语言取数最终是一次真实查询**，而查询成本可能是大头；
- 有没有"沙箱上限是从集群容量反推的"这个意识；
- 会不会默认把成本问题理解成模型问题。

**2. 参考答案框架**

**第一层：给出成本分解。**

```
一次自然语言取数的真实成本 = 模型调用成本（入口族）+ 查询执行成本（执行族）
其中：查询执行成本 ∝ 提问量 × 平均扫描量
判据：把「模型生成查询的平均扫描量」与「业务手写查询的平均扫描量」比一下
```

**第二层：给出结论。** **模型调用通常只是小项；大头常常在执行族**——因为模型生成的查询形状不可预期，可能比人写的扫得更多。**因此"让模型更准"这个方向的成本收益比，往往低于"把沙箱上限设紧"。**

**第三层：给出控制手段（按收益排序）。**
1. **扫描量上限**（按集群容量反推，§4.2（5））；
2. **行数上限**（防拉全表）；
3. **超时**（防长尾）——**但只设超时挡不住大扫描**；
4. 缓存高频问题结果（口径版本变即失效）；
5. 最后才是模型侧的调优（合并调用、减少轮次）。

**第四层：给出可测的量。** **平均扫描量、扫描量 P95、超限拒绝率**——这三个数决定成本，而它们都可以从执行侧直接测量。

**3. 常见陷阱**
- 直接把成本问题当成模型成本；
- 沙箱只设超时；
- 上限不是从集群容量反推的（拍脑袋）；
- 没有测量"平均扫描量"；
- 用缓存但不绑口径版本（缓存返回旧口径的结果）。

**4. 追问预测**
- "扫描量上限设多少？怎么算出来的？"
- "缓存高频问题，命中率与口径版本怎么联动？"
- "如果业务要求'能查明细'，扫描量上限会不会影响它？"
- "模型生成的查询为什么比人写的扫得多？"

**5. 参考资料**
- 本主题 §4.6（成本账单与扫描量判据）、§4.2（5）（沙箱上限反推）、§7.4（三条成本曲线与"大头在执行族"的推论）、§3.2.8（沙箱三上限）。
