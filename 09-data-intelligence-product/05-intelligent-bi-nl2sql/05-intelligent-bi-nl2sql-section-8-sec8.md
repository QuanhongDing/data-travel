#### §8.1 业务问了一句"上个月华东的成交额同比是多少"，你们的系统会怎么答？怎么保证这个数可信？

**1. 考察点**
- 是否理解链路的四段（理解 / 映射 / 生成 / 执行）与各自的错误形态；
- 是否知道**口径是可信的来源**，而不是模型；
- 有没有可核对的依据（口径回显）；
- 是否知道这条链路上有三处**不许猜**的分支（`unresolved` / `ambiguous` / `unmapped`），且它们在实现上是三条不同的路径；
- 加分项：能给出"这个数能不能被复核"的**可执行判据**（改一次口径看界面跟不跟、同一个问题连问两次看落点是否同一），而不是回答"我们做了可解释性"。

**2. 参考答案框架**

**第一层：给出链路与每一格可能出的错。**

```
"上个月华东的成交额同比是多少"
  → 理解：抽 metric / filters(region=华东) / time(2024-06, compare=yoy) / grain
       错法：把"同比"漏掉（→ 结果看起来回答了、实则忽略了限定）
  → 映射：落到语义层的 gmv（口径 v12）
       错法：落到"下单金额"（语法全对、口径全错）
       错法：歧义词静默选一个（ambiguous 被吞掉，而它不报错）
  → 生成：由语义层编译（不是模型写 SQL）
  → 执行：沙箱 + 权限裁剪
       错法：权限裁空却提示"没有数据"
  → 解释：口径说明 + 依据可点开
       错法：说明来自提示词，口径改了它不变
```

四段与 §2.2 的错误分类可以对齐：理解段常见的是把限定条件丢掉（等于悄悄换了一个问题），映射段是口径错，执行段是权限错与量级异常，**解释段本身不产生数字错误，但一旦它错了，前面几段的错误就无法被发现**——这正是"解释段也是链路的一部分，不是包装"的意思。

**第二层：说明可信从哪里来。** **不是"模型更准"，而是"这次用了哪个口径可被指出"**——所以返回里必须带 `metric` + `caliber_version` + `time_semantics` + `filters`，并允许点开定义。**判据**：用户在界面上能不能指出"这个数用的是什么口径"。**一个附加判据**：把这个指标的版本递增一次，界面上的说明是否跟着变——不变说明这段说明来自提示词或缓存，那它会在变更后说谎（§4.2 第（6）点）。

**第三层：给出可复现性。** 口径版本固定 + 时间语义为快照 ⇒ **同一问题在不同时间问到同一个数**。若系统对它两次生成不同 SQL，则**不可复现**——而"两次都看着合理"正是最危险的情形。这一层有两个容易漏的细节：**其一，"同比"这类比较项也要进回显与评测样本**（否则复核者只看到"用了哪个指标"，看不到"跟谁比"）；**其二，时间语义要显式声明是快照还是最新**——业务问"上月是多少"，在快照语义下答案是确定的，在最新语义下会随上游回刷变化，而这两种都可以是对的，**说不清哪一种才是错的**。

**第四层：给出拒绝与澄清。** "同比"若解析不出 → `unresolved` 非空 → **澄清**（而不是丢掉）；"成交额"若映射到多个指标 → `ambiguous` → **澄清（给候选）**（而不是静默选一个）。这里要说清一条本主题特有的判断：**`ambiguous` 比 `unmapped` 危险**——后者会明确报错，前者会静默选一个（通常是置信度最高或字典序第一个），于是"同一个问题不同时间问得到不同答案"。**澄清必须是结构化的**：给出可点候选（把"收入"展开为"确认收入（口径 v8）/ 回款收入（口径 v5）"），并给连续几次澄清之后的升级路径（转人工或引导到自助分析）。

**第五层：给出结果侧的两道校验，并说清这一层的边界。** 结果侧至少要做两件：**空结果的原因分类**（权限裁空 / 条件过严 / 真的没有——三者的用户提示完全不同，混在一起会让用户以为"就是没有数据"）与**量级合理性提示**（与同期或同类对比，偏离过大时提示，而不是拦截）。**这一层的失效条件**：如果上游缺了东西（没有口径版本、没有空结果分类、回显来自提示词），那么"这个数可信"这句话补不回来——**它只能在链路上游被保证，不能在结果侧被补救**。

**这一层的自查动作（用已有的系统与一个测试账号就能做完）**：挑一个高频指标，把它定义里的某一个过滤条件改掉（口径版本随之递增），回到界面看三处是否**一起**变——业务方的口径说明、分析师可见的 SQL、系统拿到的结构化字段；三处里有一处不变，就说明那一处的依据不是来自执行对象。第二个动作：把同一个问题在同一分钟内问两次，比较两次落到的指标名与时间区间是否完全一致——**不一致就说明这条链路上还有没收敛的 `ambiguous`**。

**3. 常见陷阱**
- 只答"模型会生成 SQL 并执行"，不谈口径；
- 把"同比"当默认值处理（丢掉限定）；
- 没有口径回显，或回显来自提示词；
- 不提 `ambiguous` / `unmapped` 两条分支。

**4. 追问预测**
- "如果同一个问题两次生成不同 SQL 但都对，这算不算问题？"
- "澄清与执行反馈，你会怎么分工？"
- "口径版本变了之后，用户看到的说明怎么跟着变？"
- "这个数被写进汇报之后，财务说口径不对，你怎么处理？"
- "如果指标定义本身写错了（例如漏了一个过滤条件），这套链路能发现吗？"——答：不能。链路保证的是"这次用的确实是那一版定义"，**不保证那一版定义是对的**；后者属于口径确认与指标评审的范畴（本主题的第 1 条判据正是"口径是否唯一"），**这也说明口径的唯一性责任在指标体系，而不在入口**。

**5. 参考资料**
- 本主题 §2.2（链路错误分解 `P(成功)=P(U)×P(M|U)×P(G|M)×P(X|G)`、mapped / ambiguous / unmapped 三态、Text2SQL 错误分类①–⑥、`EX` / `CR` / `CL` / `HR` 四个评测指标）。
- 主文件 §1.3（位置图与上下游清单：上游是指标体系与查询网关，下游是 Data Agent 与决策智能）与 §4.1 的 Step 1–8（本题答案对应的交付顺序：Step 3 的拒绝分支与 Step 7 的两通道对应第四层，Step 5 的沙箱与结果校验对应第五层，Step 6 的分层回显对应第二层）。

- 本主题 §4.2（1）意图对象的 `unresolved` 字段、（2）时间表达式四类边界、（6）回显实现要求（核验入口是"改一次定义看回显跟不跟"）。

#### §8.2 NL2SQL 与 Text2Metrics，你会选哪个？为什么"先建语义层"是唯一正确的顺序？

**1. 考察点**
- 是否知道两者的**正确性来源不同**（模型能力 vs 语义层完备度）；
- 是否理解 NL2SQL 的失败形态（**语法对、口径错**）业务方看不出；
- 有没有顺序意识（先跑起来 ≠ 先做生成）；
- 是否知道顺序问题的代价**不在技术上**（建语义层是可以排期的工程），而在**用户预期**——它决定了你要不要撤回一个已经建立起来的承诺；
- 加分项：能说清"过渡态"的**退出判据**（什么时候必须迁、拿什么数判断），而不只是说"先跑着"。

**2. 参考答案框架**

**第一层：给出对照。** 并且把对照落在判据上：NL2SQL 让模型**写 SQL**，正确性来自模型能力，错误形态是"语法对但口径错"；Text2Metrics 让模型**从已有指标里选**，正确性来自**语义层完备度**，映射不到时**明确说"未定义"**。两者的差别可以拆成六个维度——**模型的任务 / 正确性的来源 / 错误形态 / 业务方能看出错吗 / 上限由什么决定 / 新增一个口径的成本**。**其中真正决定选型的是第四个维度**：其它五个都只是它的成因；因为**一个业务方看不出的错误，无法在组织里被纠正**——它会被直接拿去用。

**第二层：说明为什么口径错最危险。** 三类错误里——语法错会报错、连接错会导致量级异常、**口径错什么都不会发生**（SQL 能跑、数看着合理），而它会直接进入决策。**因此"业务方能看出错吗"这条判据把 NL2SQL 排除在长期形态之外。**这里有一条常被追问的连线：**执行反馈只能闭环语法与工程类错误**（§2.2 的分类①与部分③），它修不了口径错，反而会把一段错误口径的 SQL 改得更像真的（跑得通、数合理、还可能补上注释）——**闭环越顺，口径错越隐蔽**。所以"加一个自纠循环"不能替代语义层，**它只改变了错误的可见性，没有改变错误的存在**。

**第三层：给出顺序论证。** 反过来做（先做生成）的代价不是技术性的，而是**用户预期**：先上线自由生成，用户习惯"什么都能问"；回头做语义层意味着**一部分问题被明确拒绝 → 功能变少**，沟通成本常常超过技术成本。**而在"先收集问题、再建口径"的路径里，同样的时间产出的是需求清单**（后期直接可用）。**这一层的判据不是工程进度，而是一个可以提前回答的问题**：这套系统上线一年后，如果被要求"每一条被拒绝的问题都要能解释为什么"，你现在攒下的东西能不能支撑那次解释？

**第四层：给出过渡方案。** 口径未统一时并非不能动——**可以上直连 NL2SQL 作过渡，但从第一天起记录真实问题**，并声明它是过渡态（有"高频问题 → 是否已被语义层覆盖"的清单）。**没有这张清单，过渡期会变成终点。**过渡态至少要配三件：**沙箱的上限**（模型生成的查询形状不可预期）、**可见的 SQL**（让分析师能复核）、**真实问题清单**（它是唯一能把过渡转成建设的产物）。**退出判据**：用同一批真实问题连问两次，数"两次落到不同口径"的比例——**这个比例不下降到可以接受的水平，说明语义层还没接上**。

**第五层：说清顺序结论的边界（它也有失效条件）。** 顺序论证成立的前提是**需求的主体是高频、同质、可归纳成指标的**；如果你们的主要取数需求是**一次性的、探索性的、每次都不一样的**，那么先建语义层的边际收益很低——那些问题本来就该由分析师用自助分析解决，而不是由自然语言入口承接。**这一层失效时会出现的信号是**：语义层建成之后，被拒绝的问题里"无法归纳成指标"的比例居高不下，而这不说明语义层没建好，说明**这类需求不该走这条路**。此时正确的动作是**明确"不覆盖什么"并引导到自助分析**，而不是继续堆指标。

**这一层的自查动作**：把最近一段时间的问题日志抽一批（不必全量），对每条问一个问题——"它能不能被写成一条指标定义（口径 + 维度 + 时间粒度）"；**能归纳的比例决定语义层的覆盖上限，不能归纳的比例决定该引导到自助分析的需求规模**。两个比例都拿得出来，才谈得上"先建语义层是否值得"；只统计"系统答了多少"这一个数时，**长尾需求会被误算成覆盖缺口**，于是投入会持续流向覆盖不动的部分。

**3. 常见陷阱**
- 只比较"准确率"，不谈错误形态；
- 认为"模型再强一点就能解决"（公共基准是单库、schema 干净、无业务口径的设定，不能外推）；
- 把"先跑起来"理解成"先做生成"；
- 上了直连 NL2SQL 但没记录真实问题；
- 把"执行反馈闭环"当成语义层的替代品（它只能修语法类错误，且会让口径错更隐蔽）。

**4. 追问预测**
- "过渡期多长算合理？判据是什么？"——答：不给时间，给判据：高频词歧义词数是否已归零、同一问题两次提问是否落到同一口径。
- "如果业务坚持要自由生成，你怎么处理？"——答：接受它作为过渡形态，但把它变成有边界的：沙箱三上限、SQL 可见、问题清单从第一天记录；用清单推动语义层，而不是用界面承诺更多。
- "语义层的覆盖率上不去，是模型问题还是维护问题？"——答：先看同义词与歧义处理（覆盖率的两个最大漏点都在维护侧），再看映射实现；**只测 `EX` 会把这个问题误判为模型问题**。
- "Text2Metrics 做不了的复杂分析，怎么引导？"——答：明确拒绝并给最近似的候选，把场景引导到自助分析 / 导出；**不要为了覆盖它而让自然语言入口硬答**。
- "如果组织里连'哪个口径为准'都定不下来，第一步做什么？"——答：**先不建系统**，先做口径裁决：把高频词逐个交给业务方确认哪个口径为准（本主题第 1 条判据的范畴，属指标体系）；在裁决完成之前上任何入口，都会**把分歧自动化**——每次提问都会落到某一个口径上，而没有人知道落得对不对。

**5. 参考资料**
- 本主题 §1.1（NL2SQL 与 Text2Metrics 的六维对照表与一条判据："这次查询用的是什么口径说不清时，这个数就不该出现在业务面前"）。
- 本主题 §1.2（被四件事逼出来的动机：量与产能不匹配、同一问题不同答案、必须可看懂、代价不对称）与 §3.6（"直连 → 语义层"跃迁的开始疼的信号，可与第四层的退出判据对照）。

#### §8.3 系统生成了一段 SQL，怎么判断它写得对不对？执行报错能修，口径错了怎么办？

**1. 考察点**
- 是否知道**执行反馈只能闭环语法类错误**；
- 是否理解"多轮修正会让口径错更隐蔽"；
- 有没有把"错误分流"设计出来；
- 是否知道**"跑得通"与"写得对"是两件事**——前者的判据是执行成功，后者的判据是落到了被认可的口径上，两者之间没有蕴含关系；
- 加分项：能说清每条通道的**上界与升级路径**（反馈轮次用完怎么办、澄清连续几次之后怎么办）；
- 加分项：能区分"数看着合理"的两类错误——**聚合错是同一个指标算错了范围或粒度，口径错是落到了另一个指标上**，两者的修法完全不同。

**2. 参考答案框架**

**第一层：先把错误分类，再说各自的闭环手段。**

```
① 语法错      → 执行报错即可发现 → 反馈闭环可修
② 表/列选错   → 执行可能成功、结果错 → 需结果校验或人工
③ 连接错      → 量级异常 → "结果合理性"检查可捕获一部分
④ 聚合/粒度错 → 数看着合理 → 最难发现
⑤ 口径错      → 业务方看不出 → **必须靠语义层与口径回显**
⑥ 权限错      → 必须前置拦截
```

**第二层：给出结论。** **执行反馈能闭环的是 ①③（部分）；④⑤ 闭环不了，必须靠语义层；⑥ 必须靠前置裁剪。** 因此"加了反馈就稳了"是错的。**一条更细的判据**：这段 SQL"写得对不对"，**不能由"它跑通了"回答**——跑通只说明语法与对象存在，它同时把①②③④⑤⑥里的五种问题放行。要回答"对不对"，需要的是**口径落对率**这一类的评测（拿带 `expected_metric` 的私有评测集去测），而不是执行日志。

**第三层：说清反馈的危险面。** 多轮修正会把一段**错误口径**的 SQL 改得**更像真的**（跑得通、数合理、还加了注释），**因此反馈闭环越顺，口径错越隐蔽**。**判据**：反馈循环修改的对象是"语法与表列"还是"指标与口径"——后者必须走澄清。**这里还有一个反直觉的推论**：加了反馈之后，系统的"看起来跑通了"的比例会上升，而这个比例**经常被当成质量改善上报**——它改善的是①③，而它会掩盖④⑤。

**第四层：给出两条通道的分工。** 语法类错误 → 执行反馈（带轮次上界）；口径类歧义 → 澄清（给结构化候选）。**两条通道在实现上必须分开**——合并会让"用反馈试口径"自然发生。上界要两头都写清：**反馈的轮次用完之后怎么办**（书内给的示例上界是 ≤ 3 轮，**这是示例值不是行业标准**——用完之后必须升级为明确失败或转人工，而不是继续试）；**澄清连续几次之后怎么办**（同样要有升级路径：转人工或引导到自助分析）。

**第五层：说清"口径错能不能被自动发现"，并给出这一层的失效条件。** 诚实回答：**在当前形态下，口径错没有自动判定的信号**——它跑得通、数合理、业务方看不出，因此只能靠三件事合起来兜住：**评测**（私有评测集报口径落对率，用带 `expected_metric` 的样本，关键样本恰恰是那些"结果相同但落到了别的指标"的反例）、**回显**（把这次用的口径与版本摆到用户面前，让业务方成为最后一道判据）、**抽检**（定期把真实问题与落点人工过一遍，重点看那些"数看着没问题"的）。**这一层的失效条件**：如果评测集只有"结果对不对"、没有"落到哪个指标"，那么它测的是 SQL 能力，不是口径落对率——**这样的评测集会把口径错系统地漏掉**。

**这一层的自查动作**：从评测集里挑"结果相同、但落到了别的指标"的样本——**如果一条都挑不出来，说明这个集合测不了口径**；再从最近一个月的真实提问里抽一批，把系统落到的指标名与人工判断的指标名逐条对照，**差异率就是口径错的可见比例**（要记住它是下界：抽不到的那些仍然存在）。

**3. 常见陷阱**
- 把执行反馈说成能解决所有错误；
- 没有轮次上界；
- 用反馈去"试不同口径直到有数"；
- 不做结果合理性检查（③会被漏掉）；
- 权限用结果过滤而不是前置裁剪；
- 把"跑通率"当成质量指标上报（它上升不代表口径错减少）。

**4. 追问预测**
- "结果合理性检查怎么实现？阈值怎么定？"——答：**与同期 / 同类对比，偏离过大时给提示而不是拦截**（§2.3 ④）。它是"多看一眼"的信号，不是判定对错的门槛：挡的是③（连接错 → 量级异常）这一类，而挡得够不够只能靠抽检（本题第五层的自查动作），不能靠阈值本身。
- "反馈轮次上界设多少？超界之后怎么办？"——答：上界是一个示例值（书内给的是 ≤ 3 轮），关键不在数字而在**超界之后的行为**：明确失败或转人工，绝不允许"再试一次"。
- "怎么发现口径错？有自动手段吗？"——答：没有可靠的自动手段；只能靠带 `expected_metric` 的评测集、回显让业务能核对、以及定期抽检三件合起来。
- "语义层映射形态下还会不会有③④类错误？"——答：会减少，但不会消失：口径对不代表 join 与聚合粒度一定对，这部分要落在结果校验与语义层的维度/粒度定义上。
- "反馈重试会不会把一次错误的口径变更固化下来？"——答：会，而且是叠加型风险：先"试"出一个能出数的口径，再被缓存、或被用户保存成可复用查询，**错误就从一次性的变成常驻的**——所以缓存必须绑口径版本，保存下来的查询要能显示它当时绑的是哪一版（§4.7 的容灾表里"口径回显与实际不一致"就属于同一族）。
- "口径错和聚合错都是'数看着合理'，怎么区分它们？"——答：看**落点**而不是看结果——聚合错是同一个指标算错了粒度或范围，口径错是落到了另一个指标上；**修法完全不同**（前者落在维度与粒度定义、结果校验上，后者只能靠口径回显与评测集里的落点字段发现）。

#### §8.4 你们准备上线"自动洞察"（主动推送异常）。你怎么判断它会不会变成噪声源？

**1. 考察点**
- 是否理解**发现异常容易、"该不该打断用户"很难**；
- 有没有把**采纳率**当成前置指标；
- 是否知道它必须建在语义层之上；
- 是否分得清这条流水线上哪一半与 AI 无关（异常检测的统计机制）——把与 AI 无关的那一半当成新机制，会同时高估它的前瞻性、低估真正要长期投入的语义层；
- 加分项：能给出这条路径的**退出条件**（拿不出什么数就不该上线）；
- 加分项：分得清"发生率"与"采纳率"——发生率只说明系统说了多少次，采纳率才说明说了多少次是对的；
- 加分项：知道这条路径**不该一开始就覆盖所有指标**——覆盖面越大，误报的绝对数量越大，而误报的代价由用户的注意力支付；覆盖顺序应当由"错了会不会进汇报"决定，而不是由一份指标重要度列表决定。

**2. 参考答案框架**

**第一层：先承认卡点在哪。** 这里要把两个问题分开：发现异常是统计问题（阈值、同环比、离群点都有客观判据，**这一半与 AI 无关**）；**判断"这条洞察是否值得打断用户"是注意力分配问题**（取决于用户当前在做什么），这一半没有通用答案。AI 真正改变的是**归因与自然语言表达**（不等提问就给出"这个指标本周下降，主要来自某个渠道"这类可读结论）以及**"系统主动开口"这件事的成本**——它把"该不该打断用户"从一个可以不回答的问题，变成了一个必须回答的问题。这一条没有通行做法，因此本方向停在 L3（§5.3.4）。

**第二层：给出前置条件（缺一不可）。**
- **必须建在语义层之上**——建在自由查询上会把口径噪声放大成结论；
- **必须有采纳率指标**——没有它，洞察会稳定退化为噪声源（同 [Ch10 §02 §3.2.7](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的频控问题）；
- **必须分级下发**——高重要性（显著偏离 + 可归因）即时推送，中低重要性进"待看"列表。

**第三层：给出最小版本。** **先不做主动推送**，只做"把异常放进待看列表"，统计采纳率；**采纳率稳定在可接受水平之上，再谈推送**。这条路径的代价极低，而它能**在没有打扰任何人的前提下**回答"这个洞察值不值得推"。**"采纳率"必须定义清楚**：是"看过了算采纳"，还是"据此做了一次动作算采纳"——两种定义会得出完全不同的结论，而且**第二种更接近价值、第一种更容易测**；选哪一种要写下来，**不然半年后没人说得清这个数为什么涨了**。

**第四层：给出归因的口径要求。** "主要来自华东"要说清是**相关**还是**因果**，以及归因基于什么维度分解——**否则用户会把一个统计现象当成原因**。两个附加约束：**分解维度来自语义层的维度定义**（不要另起一套口径），**维度组合要有上界**（否则归因本身会变成一次全表扫描式的高成本查询）。

**第五层：给出否决条件与这一层的失效边界。** **一票否决的一条：拿不出采纳率的洞察不该上线**（这是 §5.7 给的退出条件的直接应用）。**这一层的失效条件**：当业务本身处于高频促销或强季节性的节奏里，异常检测的误报会自然升高，此时"降低阈值"不是解法——**要么按业务日历切分窗口，要么退回"待看列表"这个更弱的形态**。另一条边界也必须说：**洞察的价值与"发现了多少异常"无关**，发生率不是价值指标；把发生率当成绩上报，会把系统推向"多报无妨"的方向，而它的代价由用户的注意力支付。

**这一层的自查动作**：先把"待看列表"上线，统计两周里的三件事——**被点开的比例、被标记为有用的比例、被标记为误报的比例**；三者合起来才知道这套检测在你的业务节奏下有没有用。**三个比例都要连同分母记下来**——分母取"进了待看列表的条目数"还是"触发了检测的条目数"，会让同一个比例读出相反的结论。

**一个附加的埋点要求**：无论采用哪种定义，"采纳"都必须落成一个**可埋点的动作**——"据此发生了后续动作"要能被事件流接住（打开明细、发起追问、转给他人各记一个事件），"点开看过"则只需要一次曝光事件。**选定义的标准就是它连不连得上后续动作**：连不上的定义，最后只能靠问卷回答采纳率。

**3. 常见陷阱**
- 直接上推送，不设采纳率；
- 把"发现了多少异常"当成成功指标（那是发生率，不是价值）；
- 洞察建在自由查询上；
- 归因不区分相关与因果；
- 没有分级，所有洞察同等推送；
- 把"异常检测"当成 AI 带来的新机制（它的统计判定部分本来就与 AI 无关）。

**4. 追问预测**
- "采纳率怎么定义？用户看了算采纳吗？"——答：**先说清定义，再谈目标值**——同一个目标值挂在两种定义上会得出相反的结论，所以目标值只能连同定义一起给（两种定义的取舍见本题第三层，埋点要求见本题的"附加的埋点要求"一段）。
- "异常检测的阈值怎么定才不会天天报警？"——答：**没有通行做法**——触发阈值与归因口径都缺统一判据（§5.3.4，本方向因此停在 L3）；能做的只有把阈值调到"进待看列表而不推送"，再在待看列表里量误报率（本题第三层）。
- "归因用哪些维度？维度组合爆炸怎么办？"——答：维度从语义层的维度定义里取，并对组合数设上界；归因要声明是相关还是因果。
- "如果洞察和用户已有的报表重复，怎么处理？"——答：重复本身不是问题，**问题是没有去重口径**——把"这条洞察是否已被某人看过/已在报表里"记下来，否则采纳率会被重复项稀释。
- "洞察要不要写回语义层？"——答：要——**归因用到的维度与口径必须来自语义层**；否则同一条洞察会在两处解释里给出不同的算法，它在"值不值得信"这个问题上会被立刻质疑。
- "自动洞察要不要覆盖所有指标？"——答：不要。**先覆盖那些"错了会进汇报"的指标**，其余进待看列表；扩覆盖面的前提是这一批的采纳率站得住——**在拿不出采纳率之前扩大覆盖面，等于先把噪声铺开**。

#### §8.5 一个分析师说"我不信这个数"，你会给他看什么？如果换成业务方呢？

**1. 考察点**
- 是否理解可解释性要**按角色分层**；
- 是否知道"给业务方看 SQL"是无效的；
- 有没有把回显绑到**实际执行的指标版本**；
- 是否知道"不信"这个问题有三种不同的答法（可核对 / 可复现 / 可重算），而它们对应三种不同的工程产物；
- 加分项：能说出回显本身的失效形态（口径变更后它开始说谎），以及这件事**不会报错**。

**2. 参考答案框架**

**第一层：给出分层。**
- **分析师**：给**可见 SQL**（他要复核 join 与聚合，也要改造）；加口径说明；
- **业务方**：给**口径说明 + 可点开的定义**（不含 SQL）；给对比基准与异常提示；
- **系统 / Agent**：给**结构化字段**（`metric` / `caliber_version` / `time_semantics` / `filters`）。

**第二层：说明为什么单一形态无效。** 只给口径说明 → 分析师仍自己写 SQL（可解释性没作用）；只给 SQL → 业务方看不懂（"可核对"没实现）。**判据是"这个角色要用它做什么"**：业务方要的是"这个数算的是什么"，分析师要的是"这个数是怎么算出来的"，系统要的是"把它接进下一个动作"。**三者是三种产物，不是一个开关的三种措辞。**

**第三层：给出回显的实现要求。** 回显**必须来自实际执行的指标对象**（带 `caliber_version`），不是提示词、不是检索片段。**判据**：改一次指标定义，界面说明**跟着变**——不跟，说明回显来自别处，它会在口径变更后说谎。**这里要补一条容易被忽略的边界**：回显本身也是一个**泄露面**——SQL 里带着表名与列名，结构化字段里也可能带维度取值，因此回显同样受可见域约束（本主题与 [Ch8 §02](../../08-ai-governance/02-data-security-and-compliance/02-data-security-and-compliance.md) 的接口就在这一层：安全侧产出可见集，本主题在生成前消费它，§5.4 接口表第五行）。

**第四层：给出"不信"的最强回应。** 除了回显，还有两件：**可复现**（同一问题问到同一个数，且带生成时刻与时间语义——快照还是最新要显式声明）与**可重算**（分析师能拿着 SQL 自己跑一遍）。**三者合起来才构成"可核对"**：回显回答"用了什么口径"，可复现回答"下次还是不是这个数"，可重算回答"我自己算一遍对不对"。**再加一层兜底**：空结果要能区分"权限裁空 / 条件过严 / 真的没有"——**"我不信"有时其实是"我没有数据"**，而把权限裁空提示成"没有数据"，会让用户得出方向性错误的结论。

**第五层：说清这一层的失效条件。** 回显是**下游机制**：它只能把上游已经存在的口径与边界显示出来，**不能补出上游没有的东西**——没有口径版本时，回显只能是一段会过期的说明；没有可见域时，回显会连带把无权对象显示给不该看的人。**因此"给分析师看什么"这个问题，真正的答案取决于"你们的语义层里有没有可回显的对象"**；如果答案是没有，那么先补的是语义层的版本字段（成本极低、以周计的那一格），而不是回显的界面。

**这一层的自查动作**：把某个指标的 `caliber_version` 递增一次，然后查三处是否**一起**变——业务方界面的说明、分析师拿到的 SQL、系统接口返回的结构化字段；**再单独验证一次历史**：翻出一个口径变更之前的旧结果，看它显示的是当时的版本还是当前的版本。**第二件事做不到，就说明历史不可回溯**——它是本主题里唯一"花时间也拿不回来"的一项。

**3. 常见陷阱**
- 给业务方看 SQL；
- 只给口径说明不给 SQL；
- 回显来自提示词或缓存；
- 回显不带口径版本（变更后对不上）；
- 拿"模型很准"来回答"我不信"；
- 把回显当成纯前端问题（它绑的是执行对象与版本，不是文案）。

**4. 追问预测**
- "回显里的 SQL 与语义层编译出来的 SQL 是同一段吗？"——答：应当是同一次执行的产物；如果两者可能不同，说明回显没有绑到实际执行的对象上，那它在被追问时会成为第二个不一致源。
- "如果分析师改了 SQL 再跑，结果不同，怎么解释？"——答：正好说明口径边界被人为改变；这是预期行为，**但要能指出改了哪里**（这也要求 SQL 对分析师可见）。
- "口径变更后，历史结果的回显怎么办？"——答：这是本主题里唯一部分不可逆的一项——没有版本字段时，历史结果无法回溯核对；有版本字段时，历史结果能显示"当时用的是哪一版"。
- "面向 Agent 的回显要哪些字段？"——答：`metric` / `caliber_version` / `time_semantics` / `filters` 与生成时刻；这些字段同时是 Agent 继续动作的输入，缺了它们，Agent 会把一个口径不明的数接进下一步。
- "如果业务方要的不是'口径'，而是'为什么是这个数'，怎么回？"——答：那是一层解释，不是一份依据——**先给口径与依据，再给一段解释**；反过来（先给解释）会把"可核对"降级成"听起来合理"，而后者在真正有争议时没有用。
- "如果同一个指标在不同报表里显示的口径说明不一致，怎么处理？"——答：这是**两套回显源**的问题，不是文案问题——回显必须只有一个来源（实际执行的指标对象）；两处不一致时，先查哪一处不是从执行对象取的版本，而不是先改文字。

#### §8.6 自然语言取数的成本，你觉得大头在哪？怎么控制？

**1. 考察点**
- 是否知道**一次自然语言取数最终是一次真实查询**，而查询成本可能是大头；
- 有没有"沙箱上限是从集群容量反推的"这个意识；
- 会不会默认把成本问题理解成模型问题；
- 是否分得清两笔不同的账——**常备人力**与**运行账单**，它们服从不同的增长规律；
- 加分项：能给出**可测的量**（平均扫描量、扫描量 P95、超限拒绝率），而不是只给结论。

**2. 参考答案框架**

**第一层：给出成本分解。** 先分开两笔账，再算运行账单。

```
一次自然语言取数的真实成本 = 模型调用成本（入口族）+ 查询执行成本（执行族）
其中：查询执行成本 ∝ 提问量 × 平均扫描量
判据：把「模型生成查询的平均扫描量」与「业务手写查询的平均扫描量」比一下
```

**但要先加入第三笔账，它在总额里往往是主项**：**语义层维护 + 评测与监控 + 澄清与拒绝的运营**（§4.6）。这三项的共同点是**随覆盖的指标数增长，不随提问量摊薄**，其中评测与监控的常备投入书内给的量级是 0.2–0.5 人年【经验】。**两笔账回答的是不同的问题**："哪一笔运行账单最大"与"总额里哪一项最大"——前者通常在执行族，后者在人力侧；**把它们混成一句话，就会得出"把模型换便宜一点就能省钱"这种错结论。**

**第二层：给出结论。** **在运行账单内部，模型调用通常只是小项；大头常常在执行族**——因为模型生成的查询形状不可预期，可能比人写的扫得更多。**因此"让模型更准"这个方向的成本收益比，往往低于"把沙箱上限设紧"。**这里要给出**杠杆而不是数字**：先量 `s_model` 与 `s_human` 的比值，**它高于一到两倍【经验】时，成本问题在执行侧，不在模型侧**。

**第三层：给出控制手段（按收益排序）。**
1. **扫描量上限**（按集群容量反推，§4.2（5））；
2. **行数上限**（防拉全表）；
3. **超时**（防长尾）——**但只设超时挡不住大扫描**；
4. 缓存高频问题结果（口径版本变即失效）；
5. 最后才是模型侧的调优（合并调用、减少轮次）。

**第四层：给出可测的量与它们的读法。** **平均扫描量、扫描量 P95、超限拒绝率**——这三个数决定成本，而它们都可以从执行侧直接测量。**三条读法**：平均扫描量与手写查询对比，决定要不要收紧上限；**P95 与平均值的差距**决定上限要不要按最坏情况校准（平均值好看而 P95 已经打满，说明上限在放行长尾）；**超限拒绝率上升**说明上限开始与真实需求冲突，此时要看被拒绝的是"确实过分的查询"还是"正常但被误伤的明细查询"。

**第五层：说清收紧沙箱的两条副作用与这一层的失效条件。** **副作用一：上限会误伤正常需求**——业务要查明细、分析师要做探索，都可能被行数或扫描量上限挡住；处置不是放宽上限，而是**按角色区分上限**并把被拒绝的请求记下来（它们就是"另开一条路径"的需求证据）。**副作用二：缓存能省钱，但缓存与口径版本必须联动**——不绑版本的缓存会把旧口径的结果返回给用户，而这类错误比多花的那点算力贵得多（§4.7 的"口径回显与实际不一致"是同一个失效家族）。**这一层的失效条件**：当集群本身是弹性计费、且查询彼此隔离时，单次查询的代价被吸收掉了，"收紧上限"的收益会明显变小——**此时成本的主要矛盾回到人力侧（覆盖广度），而不是沙箱侧。**

**这一层的自查动作**：在集群侧量三件事——**自然语言入口发出的查询的平均扫描量、它的 P95、以及被上限拒绝的次数**，再拿业务手写查询的平均扫描量做对照；三个数加一个对照值，就能判断"成本问题在不在执行侧"。**第二件事**：把语义层维护与评测的投入按季度记一次（记人天即可）——**它是总额里的主项，却最容易被记进"其它工作"而看不见**，等到第二年要扩容时才发现钱和时间都花在了没有名字的地方。

**3. 常见陷阱**
- 直接把成本问题当成模型成本；
- 沙箱只设超时；
- 上限不是从集群容量反推的（拍脑袋）；
- 没有测量"平均扫描量"；
- 用缓存但不绑口径版本（缓存返回旧口径的结果）；
- 只盯运行账单、不算语义层维护与评测的常备人力（它是总额里的主项）。

**4. 追问预测**
- "扫描量上限设多少？怎么算出来的？"——答：从集群可承受的单查询扫描预算与平均吞吐反推（书内示例口径是"扫描预算 ÷ 吞吐"：扫描量 10 GB、吞吐 100 MB/s ⇒ 单查询最长约 102 秒【推算】），**读数随你自己的集群参数变化**；关键是这个数是**反推出来的**，不是拍出来的。
- "缓存高频问题，命中率与口径版本怎么联动？"——答：键里带指标与口径版本；版本递增即失效。**命中率是收益指标，版本联动是正确性前提。**
- "如果业务要求'能查明细'，扫描量上限会不会影响它？"——答：会。做法是按角色区分上限并把被拒请求记下来——它是"另开一条受控路径"的需求证据，而不是要放宽全局上限的理由。
- "模型生成的查询为什么比人写的扫得多？"——答：人写查询时带着"要花多少代价"的经验，会主动加过滤与限定；模型优化的是"生成一个能回答问题的查询"，没有成本直觉——**这正是沙箱必须由使用者而不是生成者设定的原因**。
- "沙箱上限设紧了，业务的探索性分析怎么办？"——答：分成两条路径——入口侧收紧上限，探索性分析走分析师的自助分析（口径与权限仍然对齐，但不受取数入口的上限约束）。**把"不能答"与"不该在这里答"分开**，是这套设计能不能长期维持的关键。
- "怎么判断沙箱上限已经收紧过头？"——答：看**超限拒绝率**与被拒查询的性质——被拒的若是"确实过分的查询"，紧一点无所谓；若是正常明细查询，说明上限与真实需求冲突，此时应按角色分层设上限或另开受控路径，**而不是把上限整体放宽**。
