## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研语义层 + 自建入口 / 买智能 BI 产品 / 开源 BI 改造 / 直连 NL2SQL / 用 Agent 平台承载 / 只做自助 BI 不上自然语言"打分是常见做法，但它有三个结构性问题：

① **同一列在不同处境下方向相反**——"生成能力强"对**口径已统一**的团队是锦上添花（映射是主路径，生成只是兜底），对**口径未统一**的团队是**风险放大器**（它让口径错更快地扩散）。
② **打分表隐含"这些选项互斥"**，而真实做法是组合（**语义层用指标体系、入口用产品、执行用查询网关**是常见组合）。
③ **最关键的判据不是可打分的维度，而是门槛**——**"口径能不能导出"**与**"有没有拒绝路径"**这两条是门槛：不满足就直接出局。**一个生成能力极强但口径锁在产品里、且从不说"答不了"的智能 BI，会在你需要审计或复核时把你卡死。**

**本节采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| **口径可导出** | 指标定义、同义词、口径说明能不能导出成不依赖产品的材料？ | **这是门槛不是权重**——锁死 → 迁移代价是"重写全部口径" |
| **拒绝路径** | 映射不到时会不会明确说"未定义"？ | 不会 → 它在猜 → 覆盖率不可测、口径风险不可见 |
| **口径回显** | 结果里有没有"这次用了哪个口径 + 版本"？ | 没有 → 业务无法核对 → 数不可用 |
| **可见域前置** | 权限是在生成前裁剪还是结果过滤？ | 后置 → 无权对象进入生成与日志 |
| **沙箱三上限** | 行数 / 超时 / 扫描量设了几个？ | 少于两个 → 一次误查可打满共享集群 |
| **运维承接** | 谁维护指标与同义词、谁处理"答不了"的反馈？ | 本主题成本是人力为主，没有承接人的方案半年后出现大量歧义 |

**这 6 条里，前两条是门槛（不满足直接出局），后四条是权重的输入。**

这三条问题的共同点，是它们都不在"候选之间怎么排"这一层，而在"用什么筛掉候选"这一层——**打分表列的全是候选自己的属性（生成能力强、社区活跃、准确率高），而本节拿来筛候选的是本组织自己的两条约束：口径是否已经唯一、错一个数的代价能不能撤回（§3.1 的约束 1、2）**。这两条不是"打多少分"的问题，而是"过不过"的问题：**口径不唯一时，任何入口都会把"同一问题不同答案"放大**（§3.5 的"歧义词任选一个"），这正是本节先给判据、再谈候选的原因。

**判据的用法有顺序**：先用前两条门槛把不可行的候选删掉——**它们问的是"这个候选能不能被信任"，不是"它好不好"**；再用后四条比较剩下的候选。**把门槛当权重用，是这一块第二年最常见的失效原因**：一个生成能力极强、但没有拒绝路径的产品，等权相加之后仍然会排在前面，而它在你需要审计或复核时会把整个项目卡住。

**6 条判据与 §7.3 的四个机制单元不是一一对应的**：口径可导出对应 7.3.1（口径与边界的归属）、拒绝路径对应 7.3.2（覆盖率能不能被测量）、口径回显对应 7.3.3（回显粒度）、沙箱三上限对应 7.3.4（上限限住了什么）。剩下两条落在别处——**可见域前置与 7.3.1 同源**（口径与可见集是同一类东西：**都必须在生成之前就已经存在**，一个是"能落到哪个口径"，一个是"能看见哪些对象"），因此它的机制差异写在 7.3.1 的那张表里；**运维承接不对应任何机制差异**，它只决定 7.4 的成本曲线与 7.7 的迁移代价（谁维护指标与同义词、谁处理"答不了"的反馈）。**一条判定经验**：一条判据如果找不到对应的机制差异，说明它没有"选型"空间，只有"做没做"——这类判据最容易被写进清单、也最容易被跳过。

**关于排序**：本节的每一处顺序都落在相邻列的机制依据上——7.4 的成本函数给成本依据、7.5 的决策树给阈值依据、7.6 的矩阵给"不选它的原因"；本节的顺序只反映"能不能过 §7.1 的门槛"，不反映候选的能力高下。

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| **只做自助 BI（不上自然语言）** | 最稳 | 业务在已定义数据集上拖拽 | 口径尚未统一、取数压力可承受 | 不解决"业务不会拖"的那部分需求 |
| **直连 NL2SQL** | 最快 | schema + 问题 → 模型写 SQL → 沙箱执行 | 口径未统一但要先跑起来的团队 | **口径错静默**、不可复现、覆盖率不可测 |
| **自建语义层 + 自建入口** | 控制力最强 | 语义层承载口径，模型只做映射，入口自己写 | 高频取数需求大、要长期自主 | 短期投入最大（语义层 + 入口 + 评测） |
| **买智能 BI 产品** | 最快见效 | 产品自带语义层与入口 | 要快上线、业务自助诉求强 | **口径锁在产品内**；拒绝与回显的粒度由它定 |
| **开源 BI 改造** | 折中 | 开源 BI 的数据模型 + 自建自然语言入口 | 已有开源 BI 应用、团队能改造 | 数据模型不是语义层（**缺口径版本与时间语义**） |
| **用 Agent 平台承载** | 复用 | 把取数做成一个工具，由 Agent 编排调用 | 已有智能体平台（[Ch5 §01](../../05-agent-platform/01-data-agent/01-data-agent.md)） | 平台解决"编排"，**不解决"口径"**——口径仍要语义层 |

**这六个候选其实分三族**：

- **口径族**（自建语义层、买产品自带语义层、开源 BI 的数据模型）——**解决"口径从哪来"**，差别在**口径的归属与可导出性**。
- **入口族**（自然语言入口 / 搜索式入口 / Agent 调用）——**解决"怎么问"**，差别在**交互形态与消费方**。
- **执行族**（沙箱、查询网关、只读账号）——**解决"怎么安全地跑"**。

**族内可替换，跨族不可换**：入口族内部换（搜索式 ↔ 对话式 ↔ Agent 调用）代价小，**因为映射逻辑可以复用**；口径族之间换代价大（口径要重写、要重新确认）；而**执行族不能被前两族替代**——再好的口径与入口，没有沙箱就都不能上共享集群。

**选型的第一刀是选族，不是选产品**：跨族的差别是机制差别（口径在谁手里、能不能拒绝、成本随什么增长），**同族内部的差别多数是交互形态与运维形态的差别**。因此 7.5 的前几问都在选族，7.6 的矩阵才用来选具体形态——**先认准了一个产品名称、再回头为它找机制理由，是这类项目最常见的返工来源**。

**表里最后一列（主要代价）常被当成采购问题，其实它是机制问题**：**你要问的不是"贵不贵"，而是"这份代价的增长方式与我的增长方式是否同向"**。口径族随指标覆盖广度增长、入口族随提问量增长、执行族随"提问量 × 平均扫描量"增长（7.4）——**你的业务是"问的人变多"还是"要覆盖的指标变多"，决定了哪一族的账单会先失控**。判断方法是把候选的主要代价与 7.4 的成本表并排看：**两者一旦反向，选型就等于给自己埋了一笔按年滚的账**。

**还有一条与其它主题不同的观察**：本主题的公开材料形态几乎全是**产品文档与演示**，而真正能用来比较效果的几个数（口径落对率、诚实拒绝率、洞察采纳率）几乎无人公开。这不是"资料没查到"，而是**这类效果数据在结构上不可公开**——它们都需要私有评测集，而私有评测集本身含业务口径（§5.2、§5.3.1）。**这条观察直接决定选型的做法**：只能靠门槛判据加自己的评测集，**不能靠厂商给出的准确率数字**；反过来，一个能把"答不了"作为一等状态返回的候选，比一个宣称回答率很高的候选更值得继续谈（§7.1 的拒绝路径）。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 口径的归属：你的语义层、产品的语义层，还是没有语义层

**机制是什么**：口径只有三个位置——**你的语义层**（自建 / 开源可改）、**产品的语义层**（买产品）、**不存在**（直连 NL2SQL）。

**它在各候选中的实现差异**：自建族的语义层是**你的资产**（可导出、可版本化、可被别的系统消费）；产品的语义层**在产品内部**，能不能导出取决于开放程度；而直连 NL2SQL **没有这个对象**——口径隐含在每次生成里。

| 候选 | 口径这个对象在哪 | 可见集（边界）在哪 | 谁在决定"这个问题能不能答" | 典型失败形态 |
| --- | --- | --- | --- | --- |
| 自建语义层 + 自建入口 | 你的定义文件里：可导出、可版本化 | 你的权限源，可下推为映射与检索的条件 | **你**（映射不到就拒绝） | 口径维护欠账；没有同义词时覆盖率被误判成"模型不行" |
| 买智能 BI 产品 | 产品内部，能不能导出取决于它的开放程度 | 产品内部，下推时机由它定 | **产品**（允不允许"答不了"由它定） | 换工具时口径要全部重写；拒绝与回显粒度不可控 |
| 开源 BI 改造 | 数据模型里——**它不是语义层**：缺口径版本与时间语义 | 复用开源 BI 既有的权限模型 | 你，但对象模型不完整 | 复核时对不上：没有可回溯的版本字段 |
| 直连 NL2SQL | **不存在**——口径隐含在每次生成里 | **不存在**——没有可见集，只有结果过滤 | **没有一方在决定**：它总能生成一段能跑的 SQL | 口径错静默、不可复现、覆盖率不可测量 |
| 用 Agent 平台承载 | 取决于被调用的取数工具背后有没有语义层 | 取决于平台与数据侧的权限接口 | 平台只做编排，**不替你做这个决定** | 把"编排能力"误当成"口径能力" |

**由此必然导出的性质**：因为**"没有语义层"意味着"口径不是对象"**，所以直连形态下**无法回答"这个数用了什么口径"，也无法统计覆盖率**——这两件事不是"没做好"，而是**在没有这个对象时不可定义**。**这条性质解释了为什么直连 NL2SQL 不能作为长期形态**：它缺的不是精度，是**判定口径的依据**。

**公开证据**：这一格能落到两层，两层都必须标出。**第一层是"语义层作为独立消费接口"的公开产品形态**：本主题 §4.3 的工具链表首行把"指标平台 / Cube / dbt Semantic Layer / MetricFlow"与"商业 BI 的语义层"并列，选型要点只有一条——**看能不能导出**（§4.3）；全书他处对开源语义层有更细的年份与一条可自查的判据：`01-modeling/10-metric-system/10-metric-system-section-4-sec4.md` 的「开源语义层」行记有 dbt Semantic Layer（2023 GA，由 MetricFlow 引擎驱动；MetricFlow 2022 开源）、Cube（2017 开源，MetricQL）、LookML，并给出"看它的文档里『指标定义文件』与『查询接口』是否分成两节"这一判据（可在该表自行核验）【公开】。**第二层是"没有这个对象"的一侧**，可在本主题内核验：§1.4 把 2017–2021 年记为 WikiSQL（2017）与 Spider（2018）所代表的直连形态，其设定是单库、schema 干净、无业务口径（主文件 §1.4）；§6.4 的匿名案例给出的是同一形态的落地与它的失败——先把 schema 交给模型自由生成，再回头补语义层（§6.4）。**本节不对任何产品的导出能力做断言**：各产品的定义格式、许可与版本以其官方文档当前版本为准；**唯一可靠的判定入口是你自己做一次导出演练**——把 10 个指标定义连同同义词导成不依赖产品的材料，导不出来就说明这一格属于"产品的语义层"。

**失效条件**：当业务问"这个数怎么算的"或审计问"你怎么保证口径一致"时，没有语义层的形态给不出答案——**此时唯一的修法是补语义层，而不是优化生成。**

#### 7.3.2 拒绝路径的有无：覆盖率能不能被测量

**机制是什么**：映射不到时，系统是**明确拒绝**还是**尽力给一个数**。

**它在各候选中的实现差异**：自建语义层族**天然有拒绝**（候选集合是有限的指标）；产品族**可能有也可能没有**（取决于产品是否允许"答不了"）；直连 NL2SQL **几乎没有**（它总能生成一段能跑的 SQL）。

| 候选 | 映射不到时会发生什么 | 覆盖率能不能被测量 | 谁承担"没有这个答案"的后果 | 典型失败形态 |
| --- | --- | --- | --- | --- |
| 自建语义层 | 明确拒绝 + 给最接近的候选 + 引导到自助分析 | **能**——"不能映射"是分母里显式的一类 | 你（被拒绝的问题会回流成指标需求） | 拒绝做了但候选质量差，用户被迫选一个近似项 |
| 买智能 BI 产品 | 由产品的交互设计定：有的允许"答不了"，有的不允许 | 取决于它是否把"答不了"作为一等状态返回 | 产品（你拿不到被拒绝问题的清单） | 高回答率被当成能力，实际是把"不知道"答成了"知道" |
| 直连 NL2SQL | 几乎总是给一个数——它总能生成一段能跑的 SQL | **不能**——分母已经被答成了分子 | 没有人 | 高回答率是假象；发现时已经是"某个数其实是错的" |

**由此必然导出的性质**：因为**覆盖率 = 能映射的问题数 / 总问题数**，所以**没有拒绝路径时，分母里的"不能映射"已经被答成了"能映射"**——覆盖率在原理上不可测量。**换句话说：直视 NL2SQL 的"高回答率"是假象，它把"不知道"包装成了"知道"。**

**公开证据**：这一格的公开材料是**设计意图**而不是效果数。本主题 §4.5 的模板 2 给出的是可以直接抄的实现形态——意图对象的三种映射结果（`unique` / `ambiguous` / `unmapped`）加一段结构化澄清话术（把"收入"展开为"确认收入（口径 v8）/ 回款收入（口径 v5）"两个可点候选）（§4.5）；§6.2 记的国内落地形态把"拒绝与引导"写成一等交互——只报"答不了"会被绕过，所以要给最接近的候选并引导到自助分析（§6.2，建设方自述）；§6.1 的搜索式形态给的是同一条的另一种说法：**能搜到的范围就是语义模型的范围，模型之外的问题会明确失败**（§6.1，建设方自述）【公开】。**效果侧核不到，而且核不到的原因是结构性的**：诚实拒绝率与覆盖率分母都需要私有评测集，而私有评测集本身含业务口径、不能公开（§5.2）。因此这一格没有可引的效果数字，**判定入口只能是你自己的系统**——拿一个必然映射不到的词（例如某个跨口径的复合口径问法）问一次，看它拒绝、还是给了一个数。**给数就是没建成。**

**失效条件**：当业务发现"某个数其实是错的"时，说明此前的"高回答率"里混着猜测——**此时要补的不是准确率，而是拒绝。**

#### 7.3.3 回显的粒度：口径说明、SQL，还是结构化字段

**机制是什么**：结果附带的依据是**自然语言的口径说明**、**可见的 SQL**、还是**结构化字段**（指标名 + 版本 + 时间语义）。

**它在各候选中的实现差异**：产品族通常给"口径说明"（面向业务方）；开源 BI **天然给 SQL**（它的交互就是查询）；自建族**可以三者都给并按角色分层**。

| 候选 | 默认给什么依据 | 谁能拿它做事 | 口径变更后会发生什么 | 典型失败形态 |
| --- | --- | --- | --- | --- |
| 买产品（口径说明为主） | 自然语言的口径说明 | 业务方：能核对，不能改造 | 说明跟着产品内部的定义走，**你在外面看不到它跟没跟** | 分析师仍然来问"这个数怎么算的" |
| 开源 BI（SQL 为主） | 可见、可编辑、可保存的查询 | 分析师：能复核、能改造 | 查询本身不会过期，但口径边界仍要人判断 | 业务方看不懂 SQL——"可核对"没实现 |
| 自建（三种都给） | 口径说明 + 可见 SQL + 结构化字段，按角色分层 | 三种都能 | 只要回显绑的是**实际执行的指标对象**，三种会一起变 | 回显来自提示词或缓存——变更后界面开始说谎 |
| 直连 NL2SQL | 生成的 SQL | 分析师 | 每次生成的 SQL 都不同，"上次那个数"无法复现 | 把"看得见的 SQL"当成"可核对的依据"（其实没有口径对象） |

**由此必然导出的性质**：因为**不同角色要用依据做不同的事**（业务方核对口径、分析师改造、系统消费），所以**单一形态的回显必然对某一类角色无效**——只给口径说明则分析师仍自己写 SQL；只给 SQL 则业务方看不懂。**这条性质决定了回显是一个"分层"设计，不是一个开关。**

**公开证据**：分层这件事在本主题内有可核的实现要求——§4.2 第（6）点写死三条：回显必须来自**实际执行的指标对象**、字段必须带 `caliber_version`、`sql` 字段仅对分析师角色返回，判据是"改一次指标定义（version 递增），界面上的说明必须跟着变"（§4.2）；§4.5 的模板 1 里 `caliber_version` 与 `caveats` 就是这一格要回显的原料（§4.5）。落地形态见 §6.3 的 Metabase 一例：同一份结果三种回显（业务方拿口径说明、分析师拿可见 SQL、系统拿结构化字段），并把"查询可保存可复用"与 `09-data-intelligence-product/04-smart-tag-platform/04-smart-tag-platform-section-3-sec3.md` 的"保存条件而非名单"并列为同一条理（§6.3，建设方自述）。**具名产品在全书他处可核，但本节不对它们的回显粒度做断言**：`05-agent-platform/01-data-agent/01-data-agent-section-4-sec4.md` 的「国际平台」行记有 ThoughtSpot Sage（2023）、Salesforce Tableau GPT（2023）、Microsoft Copilot for Power BI（2024）、Snowflake Cortex Analyst（2024）等（可在该表自行核验）【公开】——**名字可核不等于粒度可核**，回显给了哪些字段、按什么角色分层，请以各产品官方文档当前版本为准。**判定入口**：把某个指标的版本递增一次，看三种回显是否都跟着变。

**失效条件**：当分析师仍来问数据团队"这个数怎么算的"时，说明回显对他是无效的（形态不对，不是内容不对）。

#### 7.3.4 沙箱的上限：能不能限住"最坏的一次查询"

**机制是什么**：沙箱限制的是**行数 / 超时 / 扫描量**中的哪几项。

**它在各候选中的实现差异**：开源 BI 通常**只限行数**（它的用户是人，写不出极端查询）；直连 NL2SQL 族**最需要三个都限**（查询是模型产物，形状不可预期）；产品族与自建族取决于实现，**扫描量是其中最常被漏的那一项**。

| 候选 | 三个上限里通常有哪几个 | 上限是怎么定出来的 | 最坏的一次查询能造成什么 | 典型失败形态 |
| --- | --- | --- | --- | --- |
| 开源 BI（查询由人写） | 通常只有行数 | 由界面与导出需求定 | 一个聚合查询扫过全表 | 行数上限看起来生效，IO 仍被单次查询打满 |
| 直连 NL2SQL（查询是模型产物） | 最需要三个都限 | 必须按集群可承受的单查询扫描预算反推 | 形状不可预期的查询反复并发 | 漏掉扫描量——它是最常被漏的那一项 |
| 买产品 / 自建 | 取决于实现 | 取决于是否从集群容量反推，还是拍一个数 | 取决于漏了哪一项 | 只设超时：大扫描在超时窗口内把 IO 打满而不触发任何限制 |
| 用 Agent 平台承载 | 取决于平台或取数工具自己的沙箱 | 通常由被调用工具所在引擎定 | **多步编排会把一次超限放大成连续超限** | 把"平台有资源管理"当成"取数有沙箱" |

**它比其它三个机制单元多一层反推关系**：上限不是一个可以"自信地拍一个数"的参数，而是**从两个可测量的量反推出来的**——集群可承受的单查询扫描预算，与集群的平均吞吐。**这条反推关系决定了"上限设得对不对"是一个可以回答的问题**：隔离掉一个上限（例如只留行数），看这次查询实际扫了多少；扫出来的量与你的预算对不上，就说明这一项还没被约束住。

**由此必然导出的性质**：因为**聚合查询可以在很小的行数上限内扫过全表**，所以**只限行数挡不住"最坏的一次查询"**；而只限超时则**允许在超时窗口内把 IO 打满**。**两者的组合（行数 + 扫描量，或超时 + 扫描量）才构成有效上限**——这是"模型生成的查询"与"人写的查询"在资源风险上的根本差异。

**公开证据**：本主题可引的实现落在"引擎侧资源约束"这一层，且全书他处有公开落点可核：`04-data-assetization/06-one-service/06-one-service-section-7-sec7.md` 的 §7 记有 **Trino 的资源组**——按用户组与队列约束并发和内存，并提供按执行时间或扫描量终止单条查询的查询级配置（同一段还记有 dbt Semantic Layer 与 Cube 的查询接口把入参限定为"指标 + 维度 + 过滤 + 时间范围"，超出即在接口层不可表达）【公开】（可在该文件 §7 的公开证据段自行核验）。这正是"扫描量能不能限"这一项的公开落点。本主题内可核的是**上限的来源**：§4.2 第（5）点给出反推算法——设单查询扫描预算 B GB、平均吞吐 T MB/s ⇒ 超时 ≈ B × 1024 / T 秒，书内示例给的是 B = 10 GB、T = 100 MB/s ⇒ 约 102 秒【推算：口径为"扫描预算 ÷ 吞吐"，读数随你的集群参数变化】；主文件 §2.2 用同一算式给出"10 GB 扫描在 100 MB/s 下最长执行约 100 秒"，并收成一条判据——行数 / 超时 / 扫描量三者必须至少两个同时设置（主文件 §2.2、§4.2）；§4.3 的工具链表把沙箱执行记为"引擎侧资源组 / 只读账号"与"数据网关的查询治理"，选型要点就是看扫描量能不能限（§4.3）。**具体引擎的资源组与扫描量限制怎么写，以该引擎官方文档当前版本为准。**

**失效条件**：当集群出现"没有慢查询告警但 IO 持续饱和"时，说明上限没有覆盖扫描量。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| **口径族** | 人力（口径梳理 + 同义词 + 冲突处理） | 口径确认的排队时间、口径变更的传播、被拒绝问题的归集运营 | 随**指标覆盖广度**增长 |
| **入口族** | 模型调用 + 交互设计 | 澄清与拒绝的运营、提示与映射的持续调优 | 随**提问量**增长（量级小） |
| **执行族** | 集群资源 | 沙箱上限设得越松，查询成本越高（**往往是大头**） | 随**提问量 × 平均扫描量**增长 |

**成本函数的三条判据**：

① **口径族的曲线是"高起点 + 低斜率"**——先把高频问题覆盖完是集中投入，之后每个新指标便宜；**它的规模化压力来自覆盖广度，而不是提问量**。
② **入口族的曲线很小**——模型调用成本相对查询成本通常可以忽略；**它不是成本的主要来源，但它是体验与正确性的来源**。
③ **执行族的曲线可能是最大的一项**——**一次自然语言取数最终是一次真实查询**，而模型生成的查询**可能比人写的扫得更多**（§4.6 的判据）。

**每一族的隐性成本都值得单独点出**（它们的共同点是：上线时不计入，第二年才计入）：

| 族 | 隐性成本是什么 | 为什么它在立项时看不见 |
| --- | --- | --- |
| 口径族 | **口径确认的排队时间**、**被拒绝问题的归集运营** | 它们表现成"业务在等"和"有人在回答为什么答不了"，不进任何技术账单；而后者是"诚实拒绝"这个设计的必然成本，其它主题没有对应物（§4.6） |
| 入口族 | 澄清与拒绝的运营、提示与映射的持续调优 | 它量级小，但它是**体验与正确性**的来源——调优停了，覆盖率不会掉，歧义会 |
| 执行族 | **沙箱上限越松，查询成本越高** | 它的增长不需要任何人做错事，只需要提问量自然增长；而"查询成本"在多数组织里记账在数据平台，不记在智能 BI 项目上 |

**一条与其它主题不同的判断**：多数数据系统的成本随**数据量**增长，本主题的成本随**"覆盖的指标数"与"提问量 × 平均扫描量"**增长——**这两个量都可以在不新上线任何功能的前提下单独测量**，因此本主题的成本是可以先算再立项的。

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：N = 覆盖率内的指标数   Q = 月提问量   s_model = 模型生成查询的平均扫描量
    s_human = 业务手写查询的平均扫描量   c_unit = 单位扫描量成本   P = 许可与订阅（万元）

口径族：  Cost_caliber(N) = N × 单指标维护成本 + 口径确认排队成本     ← 随 N 线性（低起点高斜率）
入口族：  Cost_entry(Q)   = Q × (模型调用单价 × 平均轮次)            ← 随 Q 线性（量级小）
执行族：  Cost_exec(Q)    = Q × s_model × c_unit + P                 ← 随 Q × s_model 线性
                                          ↑
              当 s_model / s_human > 一到两倍【经验】时，先收紧沙箱上限量，再谈优化模型成本

反直觉的一条【推算】：三个家族里，"让模型更准"通常只影响入口族（最小的那一项）；
真正的大头常常在执行族，而它的杠杆是"把沙箱上限设紧"而不是"把模型换强"。
```

**这个式子的用法**：**先量 `s_model / s_human` 这个比值**。它高于一到两倍时，**你的成本问题在执行侧，不在模型侧**——此时收紧扫描量上限的收益，大于任何模型优化。**这一条常被忽略，因为"模型"这个词把注意力吸引到了入口族。**

**三条量级推导（读者可代入自己的数）**：

1. **语义层维护的年人力**（【推算】）。设覆盖率内的指标数为 N、每个指标的年维护工时为 w（同义词与 caveats 的补充、口径变更的传播、冲突处理），则年人力 ≈ N × w。取 w 为一到两人天/年（【经验】假设，随口径变更频率浮动），N 为数百个指标时（按 200–900 计），折算下来是**约 1–7 人年之间的一段**（按每人年 250 工作日折算）——**这条链的关键不是那个数，而是它随 N 线性增长、且不随提问量摊薄**。它与 §4.6 给的"评测与监控的常备投入 0.2–0.5 人年"（【经验】）是**两笔不同的账**，要分开算、加在一起看。
2. **执行族的扫描量账**（【推算】）。设月提问量为 Q、模型生成查询的平均扫描量为 `s_model`，则月扫描量 ≈ Q × `s_model`。把 `s_model` 与业务手写查询的平均扫描量 `s_human` 比一下：**比值高于一到两倍【经验】时，先收紧扫描量上限再谈模型优化**——收紧之后同样的 Q 产生的扫描量被上限截住，而"换一个更强的模型"只影响入口族（三项里最小的一项）。**这条推导的用法是排序而非计算**：它告诉你先动哪一根杠杆。
3. **一次误查的时间上界**（【推算】，承 §4.2 第（5）点）。若扫描量上限设为 B GB、集群平均吞吐为 T MB/s，则单次查询的最长执行时间 ≈ B × 1024 / T 秒——书内示例给的是 B = 10 GB、T = 100 MB/s ⇒ 约 102 秒。**这个式子的用法是反向的**：不是先拍一个超时再希望它够用，而是**先定"你能接受的最坏一次查询"（它是扫描量的函数），再由它反推超时**。

**一条经验判据（【经验】）**：覆盖的指标数还在**数十到数百**这一档时，先把高频问题覆盖完的边际收益最高；进入**数千**这一档之后，长尾指标的维护成本开始主导口径族，此时结构上应该把不覆盖的场景**明确引导到自助分析**，而不是继续堆指标。这条线是经验线而非定律，**可自查的判据是**：统计最近一个季度新增的指标数与被命中的次数，若新增指标里"季度命中数为个位数"的占比在上升，说明已经在覆盖长尾（§4.6、§4.8 的 10 → 100 阶段）。

还有一项常被忽略的成本：**未被命中的指标与过期的同义词带来的清理成本**。指标没人用、同义词写歪了、caveats 落后于口径变更——这些都不会报错，**但会让映射在我们最不希望的地方出错**：一个不再被维护的同义词，会把问题引到一个仍在生效、但口径已经不是当初那个的指标上。**语义层越大，这类"僵尸条目"的绝对数量越多**，而它们会让覆盖率的数字看起来比实际更好。判断方法是随机抽 20 个同义词，逐条问"它上次被命中是什么时候、命中的那个指标口径最近改过吗"。

### 7.5 决策树（每个分支都要有阈值依据）

1. **你们的高频业务词，是否已经落到唯一口径上？**
   - **没有** → **不要上自然语言入口**（或只上直连 NL2SQL 作过渡，并**从第一天起记录真实问题**）；先把口径理顺（[Ch1 §10](../../01-modeling/10-metric-system/10-metric-system.md)）。
   - 有 → 进入第 2 问。
2. **错误代价高吗（错一个数会进汇报 / 影响决策）？**
   - 高 → **直连 NL2SQL 出局**；必须选**有语义层 + 有拒绝路径**的形态；进入第 3 问。
   - 低（内部探索性分析）→ 直连可以继续用，但要加沙箱三上限。
3. **你的用户里有分析师（要复核、要改）吗？**
   - 有 → 回显必须**同时**给口径说明与可见 SQL（分层）；进入第 4 问。
   - 只有业务方 → 给口径说明即可（SQL 是噪声）。
4. **团队能不能长期维护指标与同义词（按 0.2–0.5 人年的常备投入量级估算【经验】）？**
   - 能 → **自建语义层 + 自建入口**（控制力最强，口径可导出）。
   - 不能 → **买产品**，但必须**先压测两条门槛**：口径能不能导出、有没有拒绝路径（§7.1）。
5. **你们已经有一个指标平台 / 指标中台吗？**
   - 有 → **在它之上做映射层**，不要另建一套语义层——另建会让两套口径并存（§7.6 矩阵）。
   - 没有 → 进入第 6 问。
6. **有外部用户或多租户（不同的人看不同的数据）吗？**
   - 有 → **可见域前置是硬门槛**：必须在映射与检索之前下推可见集，且服务不可用时**失败关闭**（不许回退为"不过滤"）。此时"买产品"这条路要先验它的下推时机，而不是先看它的生成能力。
   - 没有（全内部、权限边界简单）→ 按现有权限模型下推即可，它不构成选型分水岭。
7. **要过审计、或被要求"这个数是怎么来的"要能复现吗？**
   - 要 → **口径版本与时间语义是门槛**：回显必须带版本（§7.3.3），时间语义（快照 / 最新）必须显式声明。缺这两项时，复核会在口径变更后对不上历史（§7.7 里唯一部分不可逆的一项）。
   - 不要 → 回显按角色给到"能解释清楚"即可。
8. **已经有查询网关或 Agent 平台了吗？**
   - 有网关 → 生成段只出**逻辑计划**，物理编译与下推交给网关（本主题不写物理 SQL，§2.4）。
   - 有 Agent 平台 → 把取数做成一个被调用的工具即可，**但口径仍然要语义层**——平台解决编排，不解决口径（§7.2 最后一行的代价栏）。

**阈值的诚实说明**：上表的"0.2–0.5 人年"与"一到两倍"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的排期与扫描量数据校准，**不要当门槛用**。

**每个分支的阈值依据**：

- **①「口径是否唯一」**：判据是**可数的**——抽 20 个高频业务词，逐个数它映射到几个指标，**歧义词数为 0** 才算过关（§3.1 过关表第一行、§4.1 Step 2）。它不设"多少算多"的阈值，因为**任何一个歧义词都会变成一个"同一问题不同答案"的隐患**。
- **②「错误代价」**：判据不是金额，而是一个可判定的问题——**这个数错了之后能不能撤回**（进过汇报、驱动过决策的数，撤回的代价远高于得到它的代价）。能撤回的链路，事后发现是可接受的。
- **③「有没有分析师」**：判据是**复核动作由谁做**——谁会去核对这个数。有，则回显必须同时给口径说明与可见 SQL；没有，则给 SQL 是噪声（§7.3.3）。
- **④「0.2–0.5 人年」**：这是**量级线不是门槛**——它来自 §4.6 的评测与监控常备投入（【经验】），用来区分"有专人承接"与"没有专人承接"两档；校准方法是拿你自己最近一个季度的指标新增数与变更数去折算。
- **⑤「已有指标平台」**：依据是 §7.6 矩阵里"已有指标平台"那一行的反面——**另建一套会让两套口径并存**，代价不在技术，而在**并存期间的解释成本**与随后"以哪套为准"的裁决。
- **⑥「多租户」**：依据是 §7.3.1 的机制——可见集与口径一样，是**必须在生成之前就存在的受控对象**；没有它时，无权对象会出现在检索上下文与生成内容里，而结果过滤挡不住这一层（§4.1 Step 4 的判据是查上下文，不是查返回结果）。
- **⑦「审计与复现」**：依据是 §7.7 里唯一部分不可逆的一项——**没有版本字段时，历史结果在口径变更后无法回溯核对**；"花时间也拿不回来"决定了它的优先级排在入口体验之前。
- **⑧「已有网关 / Agent 平台」**：依据是 §2.4 划的界——网关负责跨源编译与下推（接口是逻辑查询计划），Agent 平台负责多轮与编排；**两者都不承载口径**，因此这一问只会改变承载方式，不会改变"要不要语义层"。

**这棵树由两组彼此独立的判断组成**：**①–② 选"能不能做"**（口径是否唯一、错误代价高不高），**③–⑧ 选"做成什么样"**（团队、平台、边界、审计、承载方式）。两组不能互相替代——一个已经有了指标平台、也有分析师的大团队，如果口径还没唯一，仍然要先回到第 1 问，而不是直接从第 5 问挑一个承载方式。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 口径未统一、取数压力可承受 | 只做自助 BI | 直连 NL2SQL（过渡） | 自然语言入口会把口径问题放大 |
| 口径未统一、但业务催得急 | 直连 NL2SQL（**过渡 + 记录真实问题**） | 先建最小语义层 | 长期用它则口径错静默、覆盖率不可测 |
| 口径已统一、错误代价高 | 自建语义层 + 自建入口 | 买产品（须可导出口径） | 产品锁死则换工具要重写全部口径 |
| 已有指标平台 | **在其上做映射层** | 自建完整语义层 | 另建一套会与指标平台两套口径 |
| 已有 Agent 平台 | 语义层 + 把取数做成工具 | 自建独立入口 | Agent 平台解决编排、不解决口径 |
| 已有开源 BI | 开源 BI 的数据模型 + 自建入口 | 买产品 | 开源 BI 的数据模型**缺口径版本与时间语义** |
| 团队只有 1–2 人 | 买产品 | 自助 BI | 自建族的指标与同义词维护不会因为它小就消失 |
| 要过审计 / 需复现 | 自建（**带口径版本与时间语义**） | 买产品（须验这两项） | 无口径版本则复核时对不上 |
| 多租户 / 有外部用户 | 自建（可见集前置下推） | 买产品（须先验下推时机） | 后置过滤会把无权对象写进生成内容与日志 |
| 要主动发现异常（没人盯着看板） | 语义层 + 待看列表 + 采纳率统计 | 报表订阅 / 阈值告警 | 没有采纳率的主动推送会稳定退化为噪声源 |

**组合的两条次序原则**：① **先把口径立起来，再选入口**——入口是可替换的，口径是资产（§7.3.1）；② **先把拒绝路径与沙箱上限装上，再放开用户量**——这两件是"放开"的前置条件，缺它们时用户越多、口径风险越大。

**第三条原则（方向相反但同样重要）**：③ **先把"真实问题清单"收集起来，再谈建什么**——它不依赖任何选型，且在任何路径下都有用（§4.1 的 Step 1）。

**四个常见组合**（各说明职责边界与运维代价）：

1. **指标平台 + 映射层 + 查询网关**（已有指标体系的组织）：指标平台出口径与指标定义，本主题做同义词、意图映射与口径回显，网关做跨源编译与下推。运维代价：**同义词与 caveats 是这套组合里唯一没有天然归属的交接物**（§5.4 接口表首行把它列为本主题最常见的欠账），没人认领时覆盖率会在真实问题上打折——**而它不会报错，只会表现为"很多话听不懂"。**
2. **语义层 + 检索增强 + 沙箱**（大 schema 组织）：检索缩小上下文、语义层决定落点、沙箱限制最坏一次查询的代价。运维代价：**索引必须随指标与 schema 变更更新**，滞后会给出过时定义且不报错；而"被检索到的旧定义现在归谁维护"这一步，会在索引上线之后第一次变成一个真问题（§7.3.1 的归属问题在这里二次出现）。
3. **语义层 + 执行反馈 + 澄清**（生成错误率不低的场景）：语法类错误走反馈（带上界），口径类歧义走澄清（给结构化候选）。运维代价：**两条通道必须分开实现**——合并之后"用反馈试口径"会自然发生；此外澄清会带来"多一次交互"的摩擦，触发阈值要调（§4.2 第（4）点）。
4. **语义层 + 待看列表 + 采纳率**（想从"人问"走到"系统先说"）：洞察的输入必须是已经算出来的指标结果，因此它必须建在语义层之上。运维代价：**误报的代价是注意力**，用户屏蔽之后真异常也看不到；没有采纳率指标时，这套组合会退化为噪声源（§2.3 的⑥、§5.3.4）。

四个组合的共同点是**先把口径立住、再往外接**：向外接的每一件（检索、网关、Agent、洞察）都只是消费同一个语义层。**反过来设计——先接入再补口径——是本主题最常见的形态错误**（§4.1 的"顺序的反面"）：入口会把"生成能力"变成用户预期，而预期一旦建立，补口径就意味着"功能变少"。

**矩阵的读法**：**先用"口径是否唯一"筛掉不可行，再用"错误代价"决定要不要拒绝路径，最后才按团队承接能力在剩下里选**（§7.5）。判断这张矩阵用对了没有，只需回答一个问题：**我的痛点是否出现在我准备引入的机制所作用的位置上**——如果痛点是"同一个问题两次不同答案"，而你准备引入的机制是"一个更强的模型"，那么无论选哪一行都不会有效。

### 7.7 选错的代价与迁移成本

**反模式：把"回答率"当能力指标** —— 症状是汇报里写"系统对提问的回答率是多少"，而且这个数很漂亮 → 后果是**分母里的"不能映射"已经被答成了"能映射"**，回答率越接近满分，口径风险越不可见 → 机制上这是把**可度量的量**当成了**要度量的量**：没有拒绝路径时，"未覆盖"不产生任何信号（§7.3.2）→ 正确做法：**先做拒绝路径，让覆盖率成为一个可测量的数**，再谈覆盖率高低。

**反模式：先做入口，后做口径** —— 症状是先上线自由生成与漂亮的交互，语义层"下一期再说" → 后果是**用户预期已经建立**（"什么都能问"），回头做语义层意味着"功能变少"，组织阻力陡增，而**规范预期的沟通成本常常超过技术成本**（§4.1 的"顺序的反面"、§6.4）→ 机制上这是把**入口的可替换性**当成了**口径的紧迫性**：入口族之间换代价小，口径族的欠账会按年滚 → 正确做法：从第一天起收集真实问题清单——**它不依赖任何选型，在任何路径下都有用**。

**反模式：让模型去"试口径"直到有数** —— 症状是反馈循环里反复换指标名或换过滤条件，直到某一次跑出了数 → 后果是把"口径不确定"自动化成"挑一个能出数的口径"，**这是本主题最危险的一种自动化**，因为它同时产出"有数"与"不可复核" → 机制上这是把执行反馈的作用范围（语法与工程类错误）擅自扩大到了语义层（§4.2 第（4）点、§5.3.2）→ 正确做法：两条通道分开——语法走反馈、歧义走澄清，且反馈带上界。

**反模式：把回显做成一句话说明** —— 症状是每个数都带一段自然语言描述，看着很贴心 → 后果是**分析师仍然要自己写 SQL**（说明对他是无效形态），而口径变更后这段说明可能还在说旧定义 → 机制上回显是一个**分层设计**（业务方 / 分析师 / 系统三类消费方），不是一个文案开关（§7.3.3）→ 正确做法：三种形态都给，且**都绑到实际执行的指标对象版本上**；判据是改一次定义，三种回显是否一起变。

四个反模式的共同点是**它们都在机制层面改变了"成本或风险随什么增长"**：回答率替代了覆盖率，入口替代了口径，试错替代了澄清，文案替代了结构化字段。评估一次智能 BI 建设方案时，看的不是它列了多少能力，而是**它有没有让 7.4 表里"成本随什么增长"那一列换项**。

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 直连 NL2SQL → 语义层 | 口径错进汇报、同一问题不同口径 | 建语义层（含同义词）+ 把已积累问题归并成指标清单 + **沟通"功能变少"** | **以季度计**，且**沟通成本常超技术成本** |
| 产品锁定 → 自建 | 换产品要重写全部口径 | 逐指标重写定义与同义词；重建入口与回显 | **以季度计**，且**期间业务不能停** |
| 无拒绝 → 有拒绝 | 覆盖率一直不可测 | 加拒绝分支 + 归集被拒绝问题 | 以周计（**代码量小，但会暴露真实覆盖率**） |
| 无口径版本 → 有 | 复核时对不上历史 | 补口径版本 + 回显绑定版本 | 以月计，**历史结果无法回溯** |
| 只限行数 → 三上限 | 集群 IO 被单次查询打满 | 加扫描量上限（按集群容量反推） | 以周计 |
| 回显来自提示词 → 来自执行对象 | 口径变更后界面说谎 | 回显改绑执行对象 + 加版本字段 | 以周计 |
| 后置过滤权限 → 前置裁剪 | 无权对象进入生成与日志 | 可见集下推改造 | 以月计 |
| 同义词缺失 → 补齐 | 覆盖率被误判为模型问题 | 逐指标补同义词（含别称与缩写） | **以周计，收益立竿见影** |

这张表最容易被低估的是**中间四行**（拒绝路径、口径版本、沙箱上限、回显来源）——它们的**代码量最小、暴露的问题最多**：加上拒绝分支会立刻让真实覆盖率显形（"为什么答不了"会成批回流），加上版本字段会让历史结果与当前口径的差异显形。**它们都是"以周计"的工作，却决定另外几件的收益能不能被测量**。另一条规律：**"从有到有"的迁移（产品与自建互换）代价集中在口径重写，"从无到有"的迁移（无拒绝、无版本、无上限）代价集中在机制补齐**——后者的成本低得多，但**它的收益只有在补完之后才看得见**，这正是它总被推迟的原因。

**一条硬结论**：八条里最贵的是**"直连 NL2SQL 之后补语义层"**——它的技术代价（建语义层）是可控的，**真正的代价是用户预期**：从"什么都能问"退回"一部分明确拒绝"。**所以第 1 条判据（口径是否唯一）必须在第一版就判对**——不是因为它决定技术方案，而是因为**它决定你什么时候要撤回一个已经建立起来的预期**。

**第二条硬结论**：上表里有一项的代价**部分不可逆**——"无口径版本 → 有"里的历史部分：**没有版本字段，历史结果在口径变更后无法回溯核对**。**其余七项都是"要花时间"，这一项是"花时间也拿不回来"**；这决定优先级：**如果只能做一件事，先把口径版本字段加上**（成本极低），而不是先优化入口体验。

### 7.8 小结

| 你的处境 | 建议 | 关键理由（机制层面） |
| --- | --- | --- |
| 高频业务词还没落到唯一口径 | 先只做自助 BI（或直连作过渡 + 记录真实问题） | 口径不唯一时，任何入口都会把"同一问题不同答案"放大 |
| 错误代价高（数会进汇报） | 语义层映射 + 拒绝路径 + 口径回显 | 猜不可接受；可信要能自己核对 |
| 已有指标平台 | 在其上做映射层 | 另建一套会让两套口径并存，裁决成本落在你身上 |
| 有外部用户 / 多租户 | 可见域前置下推 + 失败关闭 | 后置过滤挡不住生成内容与日志里的无权对象 |
| 要过审计 / 要复现 | 口径版本 + 显式时间语义 | 没有版本字段，历史结果无法回溯核对（部分不可逆） |
| 集群共享、查询是模型产物 | 沙箱三上限至少设两个（含扫描量） | 行数挡不住聚合，超时挡不住大扫描 |
| 团队只有 1–2 人 | 买产品（先压测两条门槛） | 语义层维护不因团队小就消失 |
| 生成错误率不低 | 执行反馈（带上界）+ 澄清，两条通道分开 | 反馈只能修语法类错误，合并会诱发"试口径" |
| 想从"人问"走到"系统先说" | 先只做待看列表 + 采纳率 | 没有采纳率，主动推送会稳定退化为噪声源 |

> 本节小结：六个候选之间的差异，最终都能归到四问——**口径归谁且能不能导出**（你的语义层 / 产品的 / 没有）、**有没有拒绝路径**（覆盖率可不可测）、**回显的粒度**（口径说明 / SQL / 结构化字段）、**沙箱限住了什么**（行数 / 超时 / 扫描量）。四问决定了它们的分族（口径族 / 入口族 / 执行族）与成本曲线（口径族随覆盖广度增长、入口族随提问量但量级小、**执行族常常是大头且杠杆在沙箱而非模型**）。**选型顺序不可颠倒**：先用"口径是否唯一"筛掉不可行，再用"错误代价"决定要不要拒绝路径，最后才用团队承接能力在剩下的里选——**把最后一问当权重而不是门槛，是第二年最常见的失效原因**。**本主题有一条与其它主题不同的推论**：**"让模型更准"通常只影响最小的那一项（入口族）**，而真正的大头在执行族，它的杠杆是"把沙箱上限设紧"（§7.4）。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次**门槛检查**（不是打分）：口径可导出、拒绝路径、口径回显、可见域前置、沙箱三上限、运维承接——**哪一条是"不满足"而不是"分数低"**？那一条就是你最可能被迫迁移的方向（§7.7）；而你今天的补救成本，是否还落在"以周计 / 以月计"的那几格里？**另一问更具体**：如果明天换掉现在的智能 BI，**你的指标定义、同义词与口径说明能不能带走**？答不出，说明你的口径还没有真正掌握在自己手里。
