## 7. 与其他方法对比

### 7.1 先立判据：为什么打分表会误导

给"自研语义层 + 自建入口 / 买智能 BI 产品 / 开源 BI 改造 / 直连 NL2SQL / 用 Agent 平台承载 / 只做自助 BI 不上自然语言"打分是常见做法，但它有三个结构性问题：

① **同一列在不同处境下方向相反**——"生成能力强"对**口径已统一**的团队是锦上添花（映射是主路径，生成只是兜底），对**口径未统一**的团队是**风险放大器**（它让口径错更快地扩散）。
② **打分表隐含"这些选项互斥"**，而真实做法是组合（**语义层用指标体系、入口用产品、执行用查询网关**是常见组合）。
③ **最关键的判据不是可打分的维度，而是门槛**——**"口径能不能导出"**与**"有没有拒绝路径"**这两条是门槛：不满足就直接出局。**一个生成能力极强但口径锁在产品里、且从不说"答不了"的智能 BI，会在你需要审计或复核时把你卡死。**

**本节采用的 6 条判据**：

| 判据 | 问的问题 | 为什么它决定了选型 |
| --- | --- | --- |
| **口径可导出** | 指标定义、同义词、口径说明能不能导出成不依赖产品的材料？ | **这是门槛不是权重**——锁死 → 迁移代价是"重写全部口径" |
| **拒绝路径** | 映射不到时会不会明确说"未定义"？ | 不会 → 它在猜 → 覆盖率不可测、口径风险不可见 |
| **口径回显** | 结果里有没有"这次用了哪个口径 + 版本"？ | 没有 → 业务无法核对 → 数不可用 |
| **可见域前置** | 权限是在生成前裁剪还是结果过滤？ | 后置 → 无权对象进入生成与日志 |
| **沙箱三上限** | 行数 / 超时 / 扫描量设了几个？ | 少于两个 → 一次误查可打满共享集群 |
| **运维承接** | 谁维护指标与同义词、谁处理"答不了"的反馈？ | 本主题成本是人力为主，没有承接人的方案半年后出现大量歧义 |

**这 6 条里，前两条是门槛（不满足直接出局），后四条是权重的输入。**

### 7.2 候选方案全景

| 候选 | 定位 | 核心机制（一句话） | 典型使用者 | 主要代价 |
| --- | --- | --- | --- | --- |
| **只做自助 BI（不上自然语言）** | 最稳 | 业务在已定义数据集上拖拽 | 口径尚未统一、取数压力可承受 | 不解决"业务不会拖"的那部分需求 |
| **直连 NL2SQL** | 最快 | schema + 问题 → 模型写 SQL → 沙箱执行 | 口径未统一但要先跑起来的团队 | **口径错静默**、不可复现、覆盖率不可测 |
| **自建语义层 + 自建入口** | 控制力最强 | 语义层承载口径，模型只做映射，入口自己写 | 高频取数需求大、要长期自主 | 短期投入最大（语义层 + 入口 + 评测） |
| **买智能 BI 产品** | 最快见效 | 产品自带语义层与入口 | 要快上线、业务自助诉求强 | **口径锁在产品内**；拒绝与回显的粒度由它定 |
| **开源 BI 改造** | 折中 | 开源 BI 的数据模型 + 自建自然语言入口 | 已有开源 BI 应用、团队能改造 | 数据模型不是语义层（**缺口径版本与时间语义**） |
| **用 Agent 平台承载** | 复用 | 把取数做成一个工具，由 Agent 编排调用 | 已有智能体平台（[Ch5 §01](../../05-agent-platform/01-data-agent/01-data-agent.md)） | 平台解决"编排"，**不解决"口径"**——口径仍要语义层 |

**这六个候选其实分三族**：

- **口径族**（自建语义层、买产品自带语义层、开源 BI 的数据模型）——**解决"口径从哪来"**，差别在**口径的归属与可导出性**。
- **入口族**（自然语言入口 / 搜索式入口 / Agent 调用）——**解决"怎么问"**，差别在**交互形态与消费方**。
- **执行族**（沙箱、查询网关、只读账号）——**解决"怎么安全地跑"**。

**族内可替换，跨族不可换**：入口族内部换（搜索式 ↔ 对话式 ↔ Agent 调用）代价小，**因为映射逻辑可以复用**；口径族之间换代价大（口径要重写、要重新确认）；而**执行族不能被前两族替代**——再好的口径与入口，没有沙箱就都不能上共享集群。

### 7.3 机制差异：为什么它们表现不同（核心节）

#### 7.3.1 口径的归属：你的语义层、产品的语义层，还是没有语义层

**机制是什么**：口径只有三个位置——**你的语义层**（自建 / 开源可改）、**产品的语义层**（买产品）、**不存在**（直连 NL2SQL）。

**它在各候选中的实现差异**：自建族的语义层是**你的资产**（可导出、可版本化、可被别的系统消费）；产品的语义层**在产品内部**，能不能导出取决于开放程度；而直连 NL2SQL **没有这个对象**——口径隐含在每次生成里。

**由此必然导出的性质**：因为**"没有语义层"意味着"口径不是对象"**，所以直连形态下**无法回答"这个数用了什么口径"，也无法统计覆盖率**——这两件事不是"没做好"，而是**在没有这个对象时不可定义**。**这条性质解释了为什么直连 NL2SQL 不能作为长期形态**：它缺的不是精度，是**判定口径的依据**。

**失效条件**：当业务问"这个数怎么算的"或审计问"你怎么保证口径一致"时，没有语义层的形态给不出答案——**此时唯一的修法是补语义层，而不是优化生成。**

#### 7.3.2 拒绝路径的有无：覆盖率能不能被测量

**机制是什么**：映射不到时，系统是**明确拒绝**还是**尽力给一个数**。

**它在各候选中的实现差异**：自建语义层族**天然有拒绝**（候选集合是有限的指标）；产品族**可能有也可能没有**（取决于产品是否允许"答不了"）；直连 NL2SQL **几乎没有**（它总能生成一段能跑的 SQL）。

**由此必然导出的性质**：因为**覆盖率 = 能映射的问题数 / 总问题数**，所以**没有拒绝路径时，分母里的"不能映射"已经被答成了"能映射"**——覆盖率在原理上不可测量。**换句话说：直视 NL2SQL 的"高回答率"是假象，它把"不知道"包装成了"知道"。**

**失效条件**：当业务发现"某个数其实是错的"时，说明此前的"高回答率"里混着猜测——**此时要补的不是准确率，而是拒绝。**

#### 7.3.3 回显的粒度：口径说明、SQL，还是结构化字段

**机制是什么**：结果附带的依据是**自然语言的口径说明**、**可见的 SQL**、还是**结构化字段**（指标名 + 版本 + 时间语义）。

**它在各候选中的实现差异**：产品族通常给"口径说明"（面向业务方）；开源 BI **天然给 SQL**（它的交互就是查询）；自建族**可以三者都给并按角色分层**。

**由此必然导出的性质**：因为**不同角色要用依据做不同的事**（业务方核对口径、分析师改造、系统消费），所以**单一形态的回显必然对某一类角色无效**——只给口径说明则分析师仍自己写 SQL；只给 SQL 则业务方看不懂。**这条性质决定了回显是一个"分层"设计，不是一个开关。**

**失效条件**：当分析师仍来问数据团队"这个数怎么算的"时，说明回显对他是无效的（形态不对，不是内容不对）。

#### 7.3.4 沙箱的上限：能不能限住"最坏的一次查询"

**机制是什么**：沙箱限制的是**行数 / 超时 / 扫描量**中的哪几项。

**它在各候选中的实现差异**：开源 BI 通常**只限行数**（它的用户是人，写不出极端查询）；直连 NL2SQL 族**最需要三个都限**（查询是模型产物，形状不可预期）；产品族与自建族取决于实现，**扫描量是其中最常被漏的那一项**。

**由此必然导出的性质**：因为**聚合查询可以在很小的行数上限内扫过全表**，所以**只限行数挡不住"最坏的一次查询"**；而只限超时则**允许在超时窗口内把 IO 打满**。**两者的组合（行数 + 扫描量，或超时 + 扫描量）才构成有效上限**——这是"模型生成的查询"与"人写的查询"在资源风险上的根本差异。

**失效条件**：当集群出现"没有慢查询告警但 IO 持续饱和"时，说明上限没有覆盖扫描量。

### 7.4 成本结构对比（不是价格表，是成本函数）

| 方案家族 | 主导项 | 隐性成本（上线时不计入、第二年计入） | 成本随什么增长 |
| --- | --- | --- | --- |
| **口径族** | 人力（口径梳理 + 同义词 + 冲突处理） | 口径确认的排队时间、口径变更的传播、被拒绝问题的归集运营 | 随**指标覆盖广度**增长 |
| **入口族** | 模型调用 + 交互设计 | 澄清与拒绝的运营、提示与映射的持续调优 | 随**提问量**增长（量级小） |
| **执行族** | 集群资源 | 沙箱上限设得越松，查询成本越高（**往往是大头**） | 随**提问量 × 平均扫描量**增长 |

**成本函数的三条判据**：

① **口径族的曲线是"高起点 + 低斜率"**——先把高频问题覆盖完是集中投入，之后每个新指标便宜；**它的规模化压力来自覆盖广度，而不是提问量**。
② **入口族的曲线很小**——模型调用成本相对查询成本通常可以忽略；**它不是成本的主要来源，但它是体验与正确性的来源**。
③ **执行族的曲线可能是最大的一项**——**一次自然语言取数最终是一次真实查询**，而模型生成的查询**可能比人写的扫得更多**（§4.6 的判据）。

**把三条曲线写成式子（读者可代入自己的数）**：

```text
设：N = 覆盖率内的指标数   Q = 月提问量   s_model = 模型生成查询的平均扫描量
    s_human = 业务手写查询的平均扫描量   c_unit = 单位扫描量成本   P = 许可与订阅（万元）

口径族：  Cost_caliber(N) = N × 单指标维护成本 + 口径确认排队成本     ← 随 N 线性（低起点高斜率）
入口族：  Cost_entry(Q)   = Q × (模型调用单价 × 平均轮次)            ← 随 Q 线性（量级小）
执行族：  Cost_exec(Q)    = Q × s_model × c_unit + P                 ← 随 Q × s_model 线性
                                          ↑
              当 s_model / s_human > 一到两倍【经验】时，先收紧沙箱上限量，再谈优化模型成本

反直觉的一条【推算】：三个家族里，"让模型更准"通常只影响入口族（最小的那一项）；
真正的大头常常在执行族，而它的杠杆是"把沙箱上限设紧"而不是"把模型换强"。
```

**这个式子的用法**：**先量 `s_model / s_human` 这个比值**。它高于一到两倍时，**你的成本问题在执行侧，不在模型侧**——此时收紧扫描量上限的收益，大于任何模型优化。**这一条常被忽略，因为"模型"这个词把注意力吸引到了入口族。**

### 7.5 决策树（每个分支都要有阈值依据）

1. **你们的高频业务词，是否已经落到唯一口径上？**
   - **没有** → **不要上自然语言入口**（或只上直连 NL2SQL 作过渡，并**从第一天起记录真实问题**）；先把口径理顺（[Ch1 §10](../../01-modeling/10-metric-system/10-metric-system.md)）。
   - 有 → 进入第 2 问。
2. **错误代价高吗（错一个数会进汇报 / 影响决策）？**
   - 高 → **直连 NL2SQL 出局**；必须选**有语义层 + 有拒绝路径**的形态；进入第 3 问。
   - 低（内部探索性分析）→ 直连可以继续用，但要加沙箱三上限。
3. **你的用户里有分析师（要复核、要改）吗？**
   - 有 → 回显必须**同时**给口径说明与可见 SQL（分层）；进入第 4 问。
   - 只有业务方 → 给口径说明即可（SQL 是噪声）。
4. **团队能不能长期维护指标与同义词（按 0.2–0.5 人年的常备投入量级估算【经验】）？**
   - 能 → **自建语义层 + 自建入口**（控制力最强，口径可导出）。
   - 不能 → **买产品**，但必须**先压测两条门槛**：口径能不能导出、有没有拒绝路径（§7.1）。

**阈值的诚实说明**：上表的"0.2–0.5 人年"与"一到两倍"都是【经验】档——它们用来区分"这一档"与"那一档"，请用你自己的排期与扫描量数据校准，**不要当门槛用**。

### 7.6 选型矩阵与组合

| 场景 | 首选 | 备选 | 不选它的原因 |
| --- | --- | --- | --- |
| 口径未统一、取数压力可承受 | 只做自助 BI | 直连 NL2SQL（过渡） | 自然语言入口会把口径问题放大 |
| 口径未统一、但业务催得急 | 直连 NL2SQL（**过渡 + 记录真实问题**） | 先建最小语义层 | 长期用它则口径错静默、覆盖率不可测 |
| 口径已统一、错误代价高 | 自建语义层 + 自建入口 | 买产品（须可导出口径） | 产品锁死则换工具要重写全部口径 |
| 已有指标平台 | **在其上做映射层** | 自建完整语义层 | 另建一套会与指标平台两套口径 |
| 已有 Agent 平台 | 语义层 + 把取数做成工具 | 自建独立入口 | Agent 平台解决编排、不解决口径 |
| 已有开源 BI | 开源 BI 的数据模型 + 自建入口 | 买产品 | 开源 BI 的数据模型**缺口径版本与时间语义** |
| 团队只有 1–2 人 | 买产品 | 自助 BI | 自建族的指标与同义词维护不会因为它小就消失 |
| 要过审计 / 需复现 | 自建（**带口径版本与时间语义**） | 买产品（须验这两项） | 无口径版本则复核时对不上 |

**组合的两条次序原则**：① **先把口径立起来，再选入口**——入口是可替换的，口径是资产（§7.3.1）；② **先把拒绝路径与沙箱上限装上，再放开用户量**——这两件是"放开"的前置条件，缺它们时用户越多、口径风险越大。

**第三条原则（方向相反但同样重要）**：③ **先把"真实问题清单"收集起来，再谈建什么**——它不依赖任何选型，且在任何路径下都有用（§4.1 的 Step 1）。

### 7.7 选错的代价与迁移成本

| 选错的方向 | 症状 | 迁移动作 | 工作量量级 |
| --- | --- | --- | --- |
| 直连 NL2SQL → 语义层 | 口径错进汇报、同一问题不同口径 | 建语义层（含同义词）+ 把已积累问题归并成指标清单 + **沟通"功能变少"** | **以季度计**，且**沟通成本常超技术成本** |
| 产品锁定 → 自建 | 换产品要重写全部口径 | 逐指标重写定义与同义词；重建入口与回显 | **以季度计**，且**期间业务不能停** |
| 无拒绝 → 有拒绝 | 覆盖率一直不可测 | 加拒绝分支 + 归集被拒绝问题 | 以周计（**代码量小，但会暴露真实覆盖率**） |
| 无口径版本 → 有 | 复核时对不上历史 | 补口径版本 + 回显绑定版本 | 以月计，**历史结果无法回溯** |
| 只限行数 → 三上限 | 集群 IO 被单次查询打满 | 加扫描量上限（按集群容量反推） | 以周计 |
| 回显来自提示词 → 来自执行对象 | 口径变更后界面说谎 | 回显改绑执行对象 + 加版本字段 | 以周计 |
| 后置过滤权限 → 前置裁剪 | 无权对象进入生成与日志 | 可见集下推改造 | 以月计 |
| 同义词缺失 → 补齐 | 覆盖率被误判为模型问题 | 逐指标补同义词（含别称与缩写） | **以周计，收益立竿见影** |

**一条硬结论**：八条里最贵的是**"直连 NL2SQL 之后补语义层"**——它的技术代价（建语义层）是可控的，**真正的代价是用户预期**：从"什么都能问"退回"一部分明确拒绝"。**所以第 1 条判据（口径是否唯一）必须在第一版就判对**——不是因为它决定技术方案，而是因为**它决定你什么时候要撤回一个已经建立起来的预期**。

**第二条硬结论**：上表里有一项的代价**部分不可逆**——"无口径版本 → 有"里的历史部分：**没有版本字段，历史结果在口径变更后无法回溯核对**。**其余七项都是"要花时间"，这一项是"花时间也拿不回来"**；这决定优先级：**如果只能做一件事，先把口径版本字段加上**（成本极低），而不是先优化入口体验。

### 7.8 小结

> 本节小结：六个候选之间的差异，最终都能归到四问——**口径归谁且能不能导出**（你的语义层 / 产品的 / 没有）、**有没有拒绝路径**（覆盖率可不可测）、**回显的粒度**（口径说明 / SQL / 结构化字段）、**沙箱限住了什么**（行数 / 超时 / 扫描量）。四问决定了它们的分族（口径族 / 入口族 / 执行族）与成本曲线（口径族随覆盖广度增长、入口族随提问量但量级小、**执行族常常是大头且杠杆在沙箱而非模型**）。**选型顺序不可颠倒**：先用"口径是否唯一"筛掉不可行，再用"错误代价"决定要不要拒绝路径，最后才用团队承接能力在剩下的里选——**把最后一问当权重而不是门槛，是第二年最常见的失效原因**。**本主题有一条与其它主题不同的推论**：**"让模型更准"通常只影响最小的那一项（入口族）**，而真正的大头在执行族，它的杠杆是"把沙箱上限设紧"（§7.4）。

> 💡 **思考锚点**：拿 §7.1 的六条判据给你现在的方案做一次**门槛检查**（不是打分）：口径可导出、拒绝路径、口径回显、可见域前置、沙箱三上限、运维承接——**哪一条是"不满足"而不是"分数低"**？那一条就是你最可能被迫迁移的方向（§7.7）；而你今天的补救成本，是否还落在"以周计 / 以月计"的那几格里？**另一问更具体**：如果明天换掉现在的智能 BI，**你的指标定义、同义词与口径说明能不能带走**？答不出，说明你的口径还没有真正掌握在自己手里。
