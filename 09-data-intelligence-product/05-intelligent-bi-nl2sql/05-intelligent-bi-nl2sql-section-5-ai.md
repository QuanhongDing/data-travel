## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

1. **机制变了**：正确性的来源换了位置（例如从"模型写 SQL"变成"映射到语义层"），或**反馈的来源**换了（例如引入执行反馈闭环）。**这类变化影响架构决策。**
2. **接口标准变了**：查询语言与语义定义出现跨工具约定（语义层的可交换定义、指标定义的互操作）。**这类变化影响"口径能不能换工具带走"。**
3. **只多了产品**：厂商把同一套能力包装成新名词（"对话式 BI""AI 分析师""数据 Copilot"）。**这类变化只在选型表里体现。**

判别方法仍然是那一句：**"换一家厂商，这条结论还成立吗？"**——不成立的是第 3 类。

**本主题的三类分布有一条特殊性**：**第 1 类（机制变了）只出现过一次，而且已经发生过**——**从"模型写 SQL"到"映射到语义层"**（§1.4 的第三阶段）。此后所有方向（执行反馈、Agentic、自动洞察、检索增强）**都是在这条之上的加固**。**这条观察的实用推论**：判断一个智能 BI 类"新方向"要不要跟，先问"**它是不是又把正确性的来源挪了一次位置**"——**不是，那它多半是加固或包装**。

### 5.2 判据与分级

沿用三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定、可预期**。

| 演进方向 | 级别 | 机制变了什么 | ① 正式条目 | ② 第三方生产案例 | ③ 接口稳定 |
| --- | --- | --- | --- | --- | --- |
| 语义层映射（Text2Metrics） | **L2** | 正确性来源从"模型能力"移到"语义层完备度" | 成立（Headless BI 与指标平台均有正式条目） | **核不到**（企业很少公开口径落对率） | 成立（指标定义结构稳定） |
| 执行反馈自纠 | **L2** | 引入"跑一次再改"的闭环 | 成立（工具调用与执行反馈是正式能力） | 核不到 | 部分成立（轮次与升级策略各家不同） |
| Schema / 口径检索增强 | **L2** | 上下文从"全量 schema"变成"检索到的相关条目" | 成立（检索类接口普遍提供） | 核不到 | 成立 |
| 自动洞察（异常检测 + 归因） | **L3** | 从"被动答问"变成"主动提示值得看的异常" | 只有产品演示与内部实现 | 核不到（**误报率与采纳率几乎无人公开**） | 不成立（触发阈值与归因口径无通行做法） |
| Agentic BI（多步分析自动拆解） | **L3** | 从"一次问一次答"变成"自动拆成多步子问题再汇总" | 只有演示与框架 | 核不到 | 不成立 |
| 语义层定义的可交换格式 | **L3** | 指标定义从"平台私有"变成"可跨工具交换" | 只有提案与局部实现 | 核不到 | 不成立 |
| 自然语言入口面向 Agent（机器取数） | **L2** | 消费方从"人"变成"Agent / 系统调用" | 成立（工具调用与语义层接口均为正式条目） | 核不到 | 部分成立 |
| 从对话直接产出看板 / 报表 | **L3** | 从"给一个数"变成"给一页分析" | 只有产品演示 | 核不到 | 不成立 |

**本节没有一行达到 L1**——卡点全部在 ②：**智能 BI 的效果数据（口径落对率、诚实拒绝率、采纳率）几乎全部由建设方自述**，而**本主题真正需要的证据正是这几个数**。这个空缺有一条具体的解释：**口径落对率需要私有评测集，而私有评测集本身含业务口径，不能公开**。因此本主题的成熟度判断必须回到内部判据：**你自己的评测集上，`CR`（口径落对率）是多少、`HR`（诚实拒绝率）是多少。**

**怎么用这张表（三条动作）**：

- **语义层映射已经发生过了**——所以现在的问题不是"要不要跟"，而是"**跟得完不完整**"（同义词、caveats、可见域）。这一条不是前沿，是**欠账**。
- **对"主动"类方向（自动洞察、Agentic）保持更高门槛**——它们的失效形态是**误报**，而误报的代价是注意力，**没有采纳率指标就不该上线**。
- **L3 不进架构约束**——可交换格式、Agentic 拆解、对话产出看板都还没有通行做法。

### 5.3 演进方向逐条拆解（核心节）

下面六个方向（§5.3.1–§5.3.6）按**同一套六线结构**写：**旧做法与它的卡点 → AI 改变了什么机制 → 由此得到的 → 由此付出的 → 证据与来源 → 成熟度**（判定方法与适用条件按需另列）。它们各自的级别见 §5.2 的那张表——**表给结论，本节给机制**；只写收益不写代价的方向，在评审时应被直接打回。**其中 §5.3.3、§5.3.4、§5.3.6 会明说"机制与 AI 无关"**：把与 AI 无关的那一半标出来，是为了不让"加固"被当成"新机制"立项。§5.3.6 把同一套结构反过来用：遇到本节没列到的新名词，用那几步自己判。

#### 5.3.1 语义层映射：唯一一次"机制变了"，而它已经发生

- **旧做法与它的卡点**：AI 之前的"让业务自己取数"是拖拽式自助 BI——**业务方只在已定义的数据集上操作**（主文件 §1.4 的报表工具阶段），口径其实是先行的。卡点出现在把它换成"自然语言直接生成 SQL"之后：**其一，"语法全对、口径全错"这种错误业务方看不出**（§2.2 的错误分类 ④⑤）；**其二，同一个问题两次生成可能落到两个口径**，而两次都"有数"——正确性被挂在了一个不可控的变量上。

- **AI 改变了什么机制**：正确性的来源从**模型的 SQL 生成能力**移到**语义层的完备度**——模型只负责"选指标 + 填参数"，查询由语义层编译。**它换掉的是"哪个部件为正确性负责"**：不再要求模型写对 SQL，而要求语义层把口径定义清楚；顺带产出的是"答不了"这个正当结果。

- **由此得到的**：因为口径对错由定义决定而不由生成决定，**准确率从一个不可控的变量变成一个可排期的资产**——模型能力波动不影响口径对错，而**新增一个口径的成本是"在语义层加一条定义"**（§3.2.2）。由此推出三件事：① 评测的指标要从 `EX` 换成 `CR`（§2.2）；② 语义层成为**必须长期维护的资产**（有 Owner、有版本、有同义词）；③ **"答不了"变成一种正当结果**（诚实拒绝），因此要设计拒绝路径与引导。**它属于第 1 类（机制变了）**：它改变的是"错误从哪来、能不能被发现"，**因此值得进架构决策，而不是只在选型表里体现**。

- **由此付出的**：① 覆盖不到的问题被拒绝，**业务一开始会觉得"能力变小"**；② 复杂临时分析做不了（应引导到自助分析 / 导出，而不是让自然语言硬答）；③ **同义词是不可省的**——没有它，覆盖率在真实问题上会低得惊人，而团队通常误判为"模型不行"（§3.2.2 失效点）；④ 语义层从此是一项**常备运营成本**（§3.1 约束 5：有没有人负责增删与冲突处理）。

- **证据与来源**：【公开】指标定义结构的正式条目与开源实现可在书内他处核验——`01-modeling/10-metric-system/10-metric-system-section-4-sec4.md` 的「开源语义层」行记有 dbt Semantic Layer（2023 GA，由 MetricFlow 引擎驱动）、Cube（2017 开源，MetricQL）、LookML 等，并给出同一张表的判据"看它的文档里『指标定义文件』与『查询接口』是否分成两节"；【公开】国内落地形态见本主题 §6.2（把自然语言取数建在指标体系之上）。**② 核不到，而且这次核不到是有具体原因的**：企业很少公开口径落对率。

- **成熟度**：**L2**。① 成立（Headless BI 与指标平台均有正式条目）；**② 核不到**（口径落对率需要私有评测集，而私有评测集含业务口径、不能公开，§5.2）；③ 成立（指标定义结构稳定）。

- **判定方法**：抽 20 个高频业务词，数"映射到几个指标"。**歧义词数与"没有同义词"的比例，决定你这一步欠了多少账**（§3.1 过关表第一行、§4.1 Step 2）。

#### 5.3.2 执行反馈自纠：能修语法，修不了口径

- **旧做法与它的卡点**：AI 之前与 AI 之初的做法都是"**一次生成**"——跑不起来就由人来改，或直接失败。卡点在于**语法、列不存在、类型不符这类错误的占比不可忽略**，而每一次都要人看一遍报错、再改一遍；这类失败虽然是可见的（报错就停），人力却被固定消耗在机械修正上（§2.2 分类①）。

- **AI 改变了什么机制**：报错从"不可见的错误"变成"**可回灌的信号**"，生成 → 执行 → 修正成为带轮次上界的闭环。**它偏加固而不是第 1 类机制变化**：它**没有改变"正确性从哪来"**，只是把"一次生成"变成"多次尝试"（§4.2 第（4）点）。但它有一个机制性的后果——**它让口径错更隐蔽**。

- **由此得到的**：因为语法类错误有确定性判据（跑不跑得起来），这类错误可以自动闭环（§2.2 分类①）。与之配套的是一项必须显式做的设计——**"错误分流"**：语法类错误走反馈重试，口径类歧义走澄清，两条通道不能合并（§3.2.4 失效点、§4.2 第（4）点的两通道分流图）。**这不是优化，而是必要条件**：一旦合并，"用反馈去试口径"就会自然发生。

- **由此付出的**：① 轮次成本（每次都消耗调用与查询资源）；② **必须设轮次上界**，否则会出现"反复试不同写法"的循环；③ **最容易被忽略的一条——它会让"看起来跑通了"的比例上升**，从而**掩盖真实的口径落对率**：多轮修正会把一段错误口径的 SQL 改得**更像真的**（跑得通、数看着合理），**闭环越顺，口径错越隐蔽**。

- **证据与来源**：【公开】工具调用与执行反馈是正式能力（§5.2 分级表把它记为 L2，①栏成立）；机制同构的单元在书内他处可对照——`05-agent-platform/01-data-agent/01-data-agent-section-3-sec3.md` 的 §3.2.3 把同一件事记作 **Reflexion（反思）**（Ch5 §01 在 `05-agent-platform/01-data-agent/01-data-agent-section-4-sec4.md` §4.2 第 4 点把两者并称「Self-Correction / Reflexion」），本主题 §2.4 已按"一段与整体"给它划界（多轮与编排归 Ch5 §01）。【经验】轮次上界只有量级——本主题 §4.2 给的示例上界是 ≤ 3 轮，各家公开材料不给统一口径；**② 核不到**。

- **成熟度**：**L2**。① 成立（工具调用与执行反馈是正式能力）；**② 核不到**；③ 部分成立（轮次与升级策略各家不同，没有统一的接口约定）。

- **判定方法**：去看一眼你的反馈循环日志——**它改得最多的是哪一类**？如果出现"换了一个指标名再试一次"这种记录，说明两条通道已经合并了（§3.2.4 判据）。

#### 5.3.3 Schema / 口径检索增强：检索对象决定生成形态

- **旧做法与它的卡点**：旧做法是把**全量 schema（或截一半）塞进上下文**。卡点是大 schema 组织里表与字段数量远超上下文窗口——**全量塞不进，塞一半会让模型在错误的前提下生成**：它看不到相关的表，就会用不相关的表凑（§3.2.3）。

- **AI 改变了什么机制**：上下文预算从"schema 有多大"解耦成"**这个问题需要几张表**"。**这条要明说：召回与索引本身与 AI 无关**（向量检索、关键词检索都是既有技术）——把它列在本节，是因为 AI 相关的那一半改变了**生成形态**：**检索到什么，就决定它生成什么**。检索表 DDL，模型倾向自由拼 SQL（口径风险回流）；检索指标与口径，它才落在映射形态上。

- **由此得到的**：大 schema 的组织里第一次可以"只给相关的"（§3.2.3 机制）；更关键的是，**索引对象从表 DDL 改为指标与口径之后，模型的落点从"拼 SQL"变成"选指标"**（§5.4 接口表**混合检索**那一行要求"索引对象从 DDL 改为指标与口径"）——同一次改动，收益同时落在成本与口径两侧，这是它值得单列的原因。

- **由此付出的**：① **检索错了，后面全错**，且错误形态是"用了不相关的表"，看起来仍然合理；② **索引要随 schema 与指标变更更新**，滞后会给出过时定义（而它不报错）；③ **检索的粒度**（按表 / 按字段 / 按指标）要选，粒度不对会让上下文变成噪声；④ **检索质量本身没有错误信号**——它不报错，只可能靠固定问题集证明（同 `04-data-assetization/04-hybrid-search` 的纪律）。

- **证据与来源**：【公开】检索服务与向量库产品清单在书内他处可核——`05-agent-platform/01-data-agent/01-data-agent-section-4-sec4.md` §4.3 的「向量数据库（Schema RAG）」行记有 Milvus / Qdrant / Weaviate / Pinecone / Chroma / pgvector，并给出同一失效形态（"索引过期后的表现是偶尔漏表"）；本主题 §4.3 工具链表的「检索」行把实现记为"向量 + 关键词"。【公开】"索引对象应为指标与口径"是本主题 §5.4 的明确要求。【公开】"检索质量不报错、只能靠固定问题集证明"在 `04-data-assetization/04-hybrid-search/04-hybrid-search-section-3-sec3.md` 有可核验落点（该节记了"固定问题集"的建法，其反模式表的后果栏原文为"没有固定评测集时，调参把噪声当收益，且无法回归"）。**② 核不到。**

- **成熟度**：**L2**。① 成立（检索类接口普遍提供）；**② 核不到**；③ 成立（检索与向量接口是稳定接口）。

- **判定方法**：看一次你的检索上下文里出现的是什么——**指标定义，还是表 DDL**？这是成本极低的一次检查（§3.2.3 判据）。

- **什么时候不值得做**：schema 条目少到能整段塞进上下文时——此时建索引与维护索引的成本，高于它省下的那点预算（承 §3.1 约束 4 的规模侧）。

#### 5.3.4 自动洞察：为什么停在 L3

- **旧做法与它的卡点**：旧做法是报表与看板**等人来看**——异常要靠人主动发现。卡点不在算法，而在**人的注意力是这件事里唯一的稀缺品**：指标越多，能被看住的越少，而"没被看到的异常"不产生任何信号（§2.3 的⑥把它的输出定义为"洞察"，因此它天生要与注意力竞争）。

- **AI 改变了什么机制**：**这一条要明说——异常检测本身的统计机制与 AI 无关**（阈值、同环比、离群点都有客观判据，AI 之前就能算）。AI 改变的是两件事：**归因与自然语言表达**（不等提问就给出"这个指标本周下降 12%，主要来自华东渠道"这类可读结论——**示例话术，非实测数字**），以及**"系统主动开口"这件事的成本**。它仍列在本节的理由是：**它把"该不该打断用户"变成一个产品级决策，而这是注意力分配问题，不是统计问题**——前者有客观判据，后者**取决于用户当前在做什么、没有通用答案**；这正是 AI 让"主动"变便宜之后才必须回答的问题。

- **由此得到的**：异常可以被更早发现，并附一段可读的归因（§5.2 表把它记为"从被动答问变成主动提示"）；同时约束被写死——**它必须建在语义层之上**：建在自由查询上的洞察会把口径噪声放大成结论（§3.4 组合 5）。

- **由此付出的**：① **误报的代价是注意力**——用户屏蔽之后，真异常也看不到；② **归因的因果性要说清**（"主要来自华东"是相关还是因果）；③ **发现异常容易，判断"这条洞察是否值得打断用户"很难**，而后者没有通行做法。**这与 [Ch10 §02 §3.2.7](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的频控问题同构**：不是技术做不到，而是"该不该推"缺少可比较的口径。

- **证据与来源**：【经验】这个方向真正需要的证据是**误报率与采纳率**，而这两个数几乎无人公开（§5.2 的 ②栏"核不到"对本方向尤其致命）；【公开】触发阈值与归因口径无通行做法（§5.2 的 ③栏不成立）。机制同构的对照见 `10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md` §3.2.7 的频控问题，可在该节自行核验。

- **成熟度**：**L3**。① 只有产品演示与内部实现（不成立）；**② 核不到**（它真正需要的证据正是误报率与采纳率）；③ 不成立（触发阈值与归因口径无通行做法）。

- **什么时候值得做**：**先只做最小版本**——不做主动推送，只做"**把异常放在待看列表里**"，并统计**采纳率**；采纳率稳定在可接受水平之上，再谈推送（§5.7 行动建议 2 给这一条配的退出条件就是"采纳率拿不出数"）。

#### 5.3.5 Agentic BI 与自然语言产出看板：为什么停在 L3

这两项停在 L3 的原因不同，下面按同一套六线各自判。

- **旧做法与它的卡点**：旧做法是"**一次一问一答**"（多步分析靠人串），看板由人从零搭。卡点有两处：**多步分析的拆解与汇总全靠人**——拆成哪几步、每步看什么，是分析师的隐形技能；**产出物的质量没有可比的判据**——同一份分析可以做成十种样子，而"哪种更好"没有标准答案。

- **AI 改变了什么机制**：从"一次问一次答"变成"**自动拆成多步子问题再汇总**"；从"给一个数"变成"**给一页分析**"。**这是形态变化，不是正确性来源变化**——正确性仍然来自语义层（§5.3.1），被改变的是分析过程的走法与交付物的形态（§5.2 表把两项分别记为 L3）。

- **由此得到的**：分析过程可以自动走完，人从"串流程"退到"做判断"；产出物形态更接近业务要的"一页"，嵌进已有工作流之后可达性还会再提高一档。

- **由此付出的**：两条卡点都还在，只是换了说法。**Agentic BI 的失败形态是"过程看起来合理、结论无从核对"**——拆解方案有无穷多种，而"哪种拆法正确"没有标准答案；**产出看板的失败形态是"什么算好的一页分析"不可比**——它是**排版与叙事**的问题，而不是正确性问题，各家的标准不可比。

- **证据与来源**：【公开】编排框架本身是正式条目——书内他处记有 LangChain / LangGraph / LlamaIndex / AutoGen / CrewAI / MetaGPT 等（`05-agent-platform/01-data-agent/01-data-agent-section-4-sec4.md` §4.3 的「Agent 编排框架」行，该行同时记了它的误选顺序）。**但"框架有正式文档"不等于"Agentic BI 有判据"**：框架是多智能体编排的条目，不是"自动拆解多步分析"的条目，因此本节的成熟度不因它上调。【经验】两项都没有可比较的判据（§5.2 表的这两行，②③ 两栏均不成立）。

- **成熟度**：**L3**（两项分别判）。*Agentic BI*：① 只有演示与框架（不成立）；**② 核不到**；③ 不成立（拆得对不对无判据）。*从对话直接产出看板 / 报表*：① 只有产品演示（不成立）；**② 核不到**；③ 不成立（"什么算好的一页分析"不可比）。

- **什么时候值得做**：**两者今天的最小版本**——Agentic 只做"**拆解结果先给人确认再执行**"（人是判据）；产出看板只做"**从已确认的查询生成初稿 + 人编辑**"（不追求一次成型）。**这两个最小版本不依赖通行做法，且能把失控风险挡住。**

- **什么时候不值得做**：等出现可比较的判据再投——§5.7 第 3 条"先别投"指的就是这两项；今天要投，只投上面那两个最小版本。

#### 5.3.6 加固类方向：不要把"加厚"误当成"新机制"

- **旧做法与它的卡点**：**这条的"旧做法"其实是常见误判**——把执行反馈、检索增强、可见域前置、口径回显、评测指标从 `EX` 换到 `CR` 这五件当成五条"新方向"**单独立项**。卡点在于它们**都落在既有部件上**（反馈是循环控制、检索是索引、裁剪是权限接口、回显是响应字段），单独立项会同时浪费排期与评估，并**低估真正需要长期投入的那一项——语义层（同义词、口径、覆盖）**。

- **AI 改变了什么机制**：**机制与 AI 无关**——这五条一条都没有改变"正确性从哪来"，它们改变的是**效率、上下文、边界与可验证性**。仍然列在本节的唯一理由是：**AI 让其中两条的失效形态变新了**——生成内容里会留下无权对象（§3.2.7）、回显会在口径变更后说谎（§3.2.6），**这两件事在 AI 之前不构成独立风险**。

- **由此得到的**：一条现成的问法——**"它是不是又把正确性的来源挪了一次位置？"** 不是，就按加固处理、挂到既有部件上（§5.1 的实用推论）；是，才是真的机制变化。**按这条问法筛一遍：本主题里唯一算"机制变了"的是 §5.3.1 的语义层映射，而它已经发生。此后都是加固。**

- **由此付出的**：如果照"新方向"处理，会付出两类代价——**排期上**给它们单独立项（重复建设）；**评估上**高估自身的前瞻性，同时**低估语义层**这一项的长期投入。反过来，把加固当加固处理也有代价：它们不会进架构决策，只会以"顺手补一下"的形式出现——**而这五个失效点（无权对象、说谎的回显、全表扫描、上限没设够、只报 `EX`）恰恰都是静默的**，不立项就更没人盯。

- **证据与来源**：【公开】五条各自的正式落点都可指——§4.2 第（4）（5）（6）点（两通道分流、沙箱上限的反推、回显字段带版本）、§4.3 工具链表的「检索」「沙箱执行」「评测」三行、§7.1 判据表；【经验】"此后都是加固"是本书对机制位置的判断，无具名出处（§5.1 已把它写成一条实用推论）。

- **成熟度**：**按单条引 §5.2 的表，不新判级**——执行反馈 **L2**、检索增强 **L2**；可见域前置与口径回显**未见独立分级**（按本主题口径属既有能力，不判 L 级）；评测指标从 `EX` 到 `CR` 属**方法**而非能力（不判级）。三条判据逐条说：① 执行反馈与检索增强成立（正式条目可核），可见域裁剪与回显在 AI 之前即有正式实现、不构成前沿；**② 全部核不到**；③ 执行反馈部分成立，其余成立或不适用。

### 5.5 被过度宣传的部分

1. **"对话式 BI 让业务不再需要数据团队"**：它让**高频、同质**的问题自助化，而**长尾与复杂分析**仍需要人（且系统会明确拒绝它们）。**可核验的判据**：看一家宣称"替代数据团队"的产品，它的**诚实拒绝率**是多少——**拒绝率为 0 的产品，说明它在猜**。
2. **"大模型让 NL2SQL 准确率足够高"**：公共基准（Spider / BIRD 一类）是**单库、schema 干净、无业务口径**的设定，**成绩不能外推到企业场景**。**判据**：拿你自己的私有评测集测一次，报 `CR` 而不是 `EX`。
3. **"自动洞察能发现业务没注意到的问题"**：它**确实能发现异常**，但**判断"值不值得打断"没有通用答案**——没有采纳率指标时，它会稳定退化为噪声源。
4. **"加了执行反馈就稳了"**：反馈只能闭环语法类错误；**它会修不了口径错，并且会把口径错改得更像真的**。
5. **"语义层是技术债，可以直接让模型读 schema"**：这一条把"口径"这件事从系统里删掉了——**它不是省了债，是把债换成了更贵的一种**（不可复现、不可审计、错得静默）。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 被证伪的信号 |
| --- | --- |
| "口径落对率 `CR`"会取代 `EX` 成为企业自评智能 BI 的标准指标 | 三年后企业的评测仍只报执行准确率或"回答正确率" |
| 诚实拒绝会成为**产品卖点**（"它知道自己不知道"） | 主流产品仍以"什么都能答"作为卖点，且拒绝率被当作缺陷上报 |
| 语义层会与指标体系合并（一套定义同时服务报表、取数与 Agent） | 三年后企业仍维护两套口径（报表一套、取数一套） |
| 自动洞察会收敛为"待看列表 + 采纳率驱动"的形态，而不是默认推送 | 主流产品仍默认推送洞察，且不提供采纳率 |
| 时间语义（快照 / 最新）会成为自然语言接口的一等字段 | 主流接口仍只返回"当前最新的数"，不标注时间语义 |

**这五条全部是【经验】档**：它们是对机制与组织行为的判断，无具名出处、无推导链——**请按"可被证伪"使用，而不是当结论**。

**怎么用这份预测表**：不要用它做技术选型，用它做**反向检查**——每隔半年回来看一次"被证伪的信号"有没有出现。**第二条尤其值得盯**：如果"诚实拒绝"真的成了卖点，那么**现在补拒绝路径就是提前布局**；而如果它没成，你补的拒绝路径也不是浪费——**它是你自己判断「这个数可不可信」的唯一依据。**

### 5.7 给架构师的行动建议

1. **今年就该做**：高频问题清单 + 抽 20 个词数歧义 + 语义层（**含同义词与 caveats**）+ 拒绝路径。这四件不依赖任何前沿判断，而且**语义层映射这一次"机制变化"已经发生过了，不做就是欠账**。
2. **可以试点（每条自带退出条件）**：执行反馈（退出条件：日志里出现"换指标名重试"，说明通道已合并）；自动洞察（退出条件：采纳率拿不出数）；检索增强（退出条件：检索对象退回表 DDL）。
3. **先别投**：Agentic BI 的多步自动拆解、从对话直接产出看板、语义层的可交换格式。等出现可比较的判据。
4. **无论哪条**：把"**口径落对率 `CR`**"作为这一块的第一条 KPI——它同时是语义层、映射与评测三者的共同语言（只报 `EX` 会系统性高估）。
5. **一条反直觉的**：**先做"拒绝"，再做"覆盖"**——拒绝路径（明确说"未定义"）的成本是几行代码，而它一旦缺失，**你连"覆盖率有多低"都不知道**（因为系统会把没覆盖的也答出来）。**先有拒绝，覆盖率才是一个可测量的数。**

### 5.8 小结

> 本节小结：AI 时代对智能 BI 的改变**只有一条是机制性的——语义层映射（正确性来源从模型能力移到语义层完备度），而它已经发生**；此后所有方向（执行反馈、检索增强、自动洞察、Agentic、可见域、回显、指标从 `EX` 换到 `CR`）都是加固，**把它们当新机制会低估真正需要长期投入的那一项：语义层的覆盖与维护**。本节没有一行达到 L1，卡点在 ② 上有一条具体的解释——**口径落对率需要私有评测集，而私有评测集含业务口径、不能公开**；因此成熟度判断必须回到内部判据：**你自己的评测集上 `CR` 与 `HR` 是多少**。**给读者的动作**：先做拒绝路径与高频词覆盖；再谈反馈、洞察与 Agentic。

> 💡 **思考锚点**：如果你今天给系统加一条"无法映射就明确拒绝"的路径，一周后你会收到一批"为什么答不了"的反馈——**那批反馈就是你的真实覆盖率**。做这件事的成本是几行代码，收益是**你第一次知道自己的覆盖率是多少**（在此之前，系统会把没覆盖的也答出来，而你看不到）。**你打算先加拒绝路径，还是先补指标？**——这两个顺序会得到完全不同的下一年。
