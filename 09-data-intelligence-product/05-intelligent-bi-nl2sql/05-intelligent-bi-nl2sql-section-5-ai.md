## 5. 前沿演进（AI 时代）

### 5.1 先分清三类「前沿」

1. **机制变了**：正确性的来源换了位置（例如从"模型写 SQL"变成"映射到语义层"），或**反馈的来源**换了（例如引入执行反馈闭环）。**这类变化影响架构决策。**
2. **接口标准变了**：查询语言与语义定义出现跨工具约定（语义层的可交换定义、指标定义的互操作）。**这类变化影响"口径能不能换工具带走"。**
3. **只多了产品**：厂商把同一套能力包装成新名词（"对话式 BI""AI 分析师""数据 Copilot"）。**这类变化只在选型表里体现。**

判别方法仍然是那一句：**"换一家厂商，这条结论还成立吗？"**——不成立的是第 3 类。

**本主题的三类分布有一条特殊性**：**第 1 类（机制变了）只出现过一次，而且已经发生过**——**从"模型写 SQL"到"映射到语义层"**（§1.4 的第三阶段）。此后所有方向（执行反馈、Agentic、自动洞察、检索增强）**都是在这条之上的加固**。**这条观察的实用推论**：判断一个智能 BI 类"新方向"要不要跟，先问"**它是不是又把正确性的来源挪了一次位置**"——**不是，那它多半是加固或包装**。

### 5.2 判据与分级

沿用三条 L1 判据：**① 已 GA 且有正式文档 / 发布条目**；**② 有第三方（非厂商）公开的生产案例**；**③ 接口稳定、可预期**。

| 演进方向 | 级别 | 机制变了什么 | ① 正式条目 | ② 第三方生产案例 | ③ 接口稳定 |
| --- | --- | --- | --- | --- | --- |
| 语义层映射（Text2Metrics） | **L2** | 正确性来源从"模型能力"移到"语义层完备度" | 成立（Headless BI 与指标平台均有正式条目） | **核不到**（企业很少公开口径落对率） | 成立（指标定义结构稳定） |
| 执行反馈自纠 | **L2** | 引入"跑一次再改"的闭环 | 成立（工具调用与执行反馈是正式能力） | 核不到 | 部分成立（轮次与升级策略各家不同） |
| Schema / 口径检索增强 | **L2** | 上下文从"全量 schema"变成"检索到的相关条目" | 成立（检索类接口普遍提供） | 核不到 | 成立 |
| 自动洞察（异常检测 + 归因） | **L3** | 从"被动答问"变成"主动提示值得看的异常" | 只有产品演示与内部实现 | 核不到（**误报率与采纳率几乎无人公开**） | 不成立（触发阈值与归因口径无通行做法） |
| Agentic BI（多步分析自动拆解） | **L3** | 从"一次问一次答"变成"自动拆成多步子问题再汇总" | 只有演示与框架 | 核不到 | 不成立 |
| 语义层定义的可交换格式 | **L3** | 指标定义从"平台私有"变成"可跨工具交换" | 只有提案与局部实现 | 核不到 | 不成立 |
| 自然语言入口面向 Agent（机器取数） | **L2** | 消费方从"人"变成"Agent / 系统调用" | 成立（工具调用与语义层接口均为正式条目） | 核不到 | 部分成立 |
| 从对话直接产出看板 / 报表 | **L3** | 从"给一个数"变成"给一页分析" | 只有产品演示 | 核不到 | 不成立 |

**本节没有一行达到 L1**——卡点全部在 ②：**智能 BI 的效果数据（口径落对率、诚实拒绝率、采纳率）几乎全部由建设方自述**，而**本主题真正需要的证据正是这几个数**。这个空缺有一条具体的解释：**口径落对率需要私有评测集，而私有评测集本身含业务口径，不能公开**。因此本主题的成熟度判断必须回到内部判据：**你自己的评测集上，`CR`（口径落对率）是多少、`HR`（诚实拒绝率）是多少。**

**怎么用这张表（三条动作）**：

- **语义层映射已经发生过了**——所以现在的问题不是"要不要跟"，而是"**跟得完不完整**"（同义词、caveats、可见域）。这一条不是前沿，是**欠账**。
- **对"主动"类方向（自动洞察、Agentic）保持更高门槛**——它们的失效形态是**误报**，而误报的代价是注意力，**没有采纳率指标就不该上线**。
- **L3 不进架构约束**——可交换格式、Agentic 拆解、对话产出看板都还没有通行做法。

### 5.3 演进方向逐条拆解（核心节）

#### 5.3.1 语义层映射：唯一一次"机制变了"，而它已经发生

**机制**：正确性的来源从**模型的 SQL 生成能力**移到**语义层的完备度**——模型只负责"选指标 + 填参数"，查询由语义层编译。

**证据到哪一步**：① 成立；③ 成立（指标定义的结构稳定）；② 核不到。**它是第 1 类**：它改变了"错误从哪来、能不能被发现"，因此值得进架构决策。

**它对架构决策的影响**：**它把"准确率"从一个不可控的变量变成一个可排期的资产**——模型能力波动不影响口径对错，而**新增一个口径的成本是"在语义层加一条定义"**。由此推出三件事：① 评测的指标要从 `EX` 换成 `CR`（§2.2）；② 语义层成为**必须长期维护的资产**（有 Owner、有版本、有同义词）；③ **"答不了"变成一种正当结果**（诚实拒绝），因此要设计拒绝路径与引导。

**代价与边界**：① 覆盖不到的问题被拒绝（业务一开始会觉得"能力变小"）；② 复杂临时分析做不了（应引导到自助分析，而不是让自然语言硬答）；③ **同义词是不可省的**——没有它，覆盖率在真实问题上会低得惊人，而团队通常误判为"模型不行"。

**读者今天该做什么**：抽 20 个高频业务词，数"映射到几个指标"。**歧义词数与"没有同义词"的比例，决定你这一步欠了多少账。**

#### 5.3.2 执行反馈自纠：能修语法，修不了口径

**机制**：执行结果与报错回灌给模型，形成"生成 → 执行 → 修正"的闭环（有轮次上界）。

**证据到哪一步**：① 成立；③ 部分成立（轮次与升级策略各家不同）；② 核不到。**它是第 1 类还是加固**？——**偏加固**：它没有改变"正确性的来源"，只是把"一次生成"变成"多次尝试"。但**它有一个机制性的后果**：**它让口径错更隐蔽**（多轮修正会把错误口径的 SQL 改得更像真的）。

**它对架构决策的影响**：**它决定了"错误分流"必须显式设计**——语法类错误走反馈重试，口径类歧义走澄清，两条通道不能合并（§3.2.4 的失效点）。**这条要求不是优化，而是必要条件**：一旦合并，"用反馈去试口径"就会自然发生。

**代价与边界**：轮次成本；轮次上界；**以及最容易被忽略的一条——它会让"看起来跑通了"的比例上升**，从而**掩盖真实的口径落对率**。**判据**：反馈循环修改的对象是"语法与表列"还是"指标与口径"。

**读者今天该做什么**：去看一眼你的反馈循环日志——**它改得最多的是哪一类**？如果出现"换了一个指标名再试一次"这种记录，说明两条通道已经合并了。

#### 5.3.3 Schema / 口径检索增强：检索对象决定生成形态

**机制**：上下文从"全量 schema"变成"检索到的相关条目"。

**证据到哪一步**：① 成立；③ 成立；② 核不到。**它是加固**——它解决"塞不进上下文"，不改变正确性来源。但**它有一个机制性的副作用**：**检索对象的选择会决定生成形态**——检索表 DDL 会让模型倾向自由拼 SQL（口径风险回流），检索指标与口径会让它落在映射形态上。

**代价与边界**：① 检索错了后面全错，且错误形态看起来合理；② 索引要随 schema 与指标变更更新；③ 粒度（按表 / 按字段 / 按指标）要选。

**读者今天该做什么**：看一次你的检索上下文里出现的是什么——**指标定义，还是表 DDL**？这是成本极低的一次检查。

#### 5.3.4 自动洞察：为什么停在 L3

**机制**：不等提问，主动给出异常检测与归因（"这个指标本周下降 12%，主要来自华东渠道"）。

**证据到哪一步**：① 只有产品演示与内部实现；③ 不成立（触发阈值与归因口径无通行做法）；② **核不到——而这一条对本方向尤其致命**：它真正需要的证据是**误报率与采纳率**，而这两个数几乎无人公开。因此它是 **L3**。

**卡点的实质**：**发现异常容易，判断"这条洞察是否值得打断用户"很难**——前者是统计问题（有客观判据），后者是**注意力分配问题**（取决于用户当前在做什么，没有通用答案）。**这与 [Ch10 §02 §3.2.7](../../10-industry-agent/02-industry-intelligence-agent/02-industry-intelligence-agent-section-3-sec3.md) 的频控问题同构**：不是技术做不到，而是**"该不该推"缺少可比较的口径**。

**代价与边界**：① **误报的代价是注意力**（用户屏蔽后，真异常也看不到）；② **归因的因果性**（"主要来自华东"是相关还是因果，口径要说清）；③ **它必须建在语义层之上**——建在自由查询上的洞察会把口径噪声放大成结论。

**给读者的动作**：**先只做最小版本**——不做主动推送，只做**"把异常放在待看列表里"**，并统计**采纳率**。采纳率稳定在可接受水平之上，再谈推送。

#### 5.3.5 Agentic BI 与自然语言产出看板：为什么停在 L3

这两项停在 L3 的原因不同：

- **Agentic BI**（自动把问题拆成多步子问题再汇总）缺的是**"拆得对不对"的判据**——拆解方案有无穷多种，而"哪种拆法正确"没有标准答案；因此它的失败形态是"**过程看起来合理、结论无从核对**"。
- **从对话直接产出看板 / 报表**缺的是**"什么算好的一页分析"的判据**——它是**排版与叙事**的问题，而不是正确性问题；各家的标准不可比。

**两者今天的最小版本**：Agentic 只做"**拆解结果先给人确认再执行**"（人是判据）；产出看板只做"**从已确认的查询生成初稿 + 人编辑**"（不追求一次成型）。**这两个最小版本不依赖通行做法，且能把失控风险挡住。**

#### 5.3.6 加固类方向：不要把"加厚"误当成"新机制"

执行反馈、检索增强、可见域前置、口径回显、评测指标从 `EX` 到 `CR`——这五个方向**都不改变"正确性从哪来"**，它们改变的是**效率、上下文、边界与可验证性**。把它们当"新方向"会引发两类浪费：

- **排期上**：会给它们单独立项（而它们其实落在既有部件上：反馈是循环控制、检索是索引、裁剪是权限接口、回显是响应字段）；
- **评估上**：会高估自身的前瞻性，同时**低估真正需要长期投入的那一项——语义层（同义词、口径、覆盖）**。

**本主题里唯一算"机制变了"的，是 §5.3.1 的语义层映射，而它已经发生。此后都是加固。**

### 5.5 被过度宣传的部分

1. **"对话式 BI 让业务不再需要数据团队"**：它让**高频、同质**的问题自助化，而**长尾与复杂分析**仍需要人（且系统会明确拒绝它们）。**可核验的判据**：看一家宣称"替代数据团队"的产品，它的**诚实拒绝率**是多少——**拒绝率为 0 的产品，说明它在猜**。
2. **"大模型让 NL2SQL 准确率足够高"**：公共基准（Spider / BIRD 一类）是**单库、schema 干净、无业务口径**的设定，**成绩不能外推到企业场景**。**判据**：拿你自己的私有评测集测一次，报 `CR` 而不是 `EX`。
3. **"自动洞察能发现业务没注意到的问题"**：它**确实能发现异常**，但**判断"值不值得打断"没有通用答案**——没有采纳率指标时，它会稳定退化为噪声源。
4. **"加了执行反馈就稳了"**：反馈只能闭环语法类错误；**它会修不了口径错，并且会把口径错改得更像真的**。
5. **"语义层是技术债，可以直接让模型读 schema"**：这一条把"口径"这件事从系统里删掉了——**它不是省了债，是把债换成了更贵的一种**（不可复现、不可审计、错得静默）。

### 5.6 未来 3–5 年：可证伪的预测

| 预测 | 被证伪的信号 |
| --- | --- |
| "口径落对率 `CR`"会取代 `EX` 成为企业自评智能 BI 的标准指标 | 三年后企业的评测仍只报执行准确率或"回答正确率" |
| 诚实拒绝会成为**产品卖点**（"它知道自己不知道"） | 主流产品仍以"什么都能答"作为卖点，且拒绝率被当作缺陷上报 |
| 语义层会与指标体系合并（一套定义同时服务报表、取数与 Agent） | 三年后企业仍维护两套口径（报表一套、取数一套） |
| 自动洞察会收敛为"待看列表 + 采纳率驱动"的形态，而不是默认推送 | 主流产品仍默认推送洞察，且不提供采纳率 |
| 时间语义（快照 / 最新）会成为自然语言接口的一等字段 | 主流接口仍只返回"当前最新的数"，不标注时间语义 |

**这五条全部是【经验】档**：它们是对机制与组织行为的判断，无具名出处、无推导链——**请按"可被证伪"使用，而不是当结论**。

**怎么用这份预测表**：不要用它做技术选型，用它做**反向检查**——每隔半年回来看一次"被证伪的信号"有没有出现。**第二条尤其值得盯**：如果"诚实拒绝"真的成了卖点，那么**现在补拒绝路径就是提前布局**；而如果它没成，你补的拒绝路径也不是浪费——**它是你自己判断「这个数可不可信」的唯一依据。**

### 5.7 给架构师的行动建议

1. **今年就该做**：高频问题清单 + 抽 20 个词数歧义 + 语义层（**含同义词与 caveats**）+ 拒绝路径。这四件不依赖任何前沿判断，而且**语义层映射这一次"机制变化"已经发生过了，不做就是欠账**。
2. **可以试点（每条自带退出条件）**：执行反馈（退出条件：日志里出现"换指标名重试"，说明通道已合并）；自动洞察（退出条件：采纳率拿不出数）；检索增强（退出条件：检索对象退回表 DDL）。
3. **先别投**：Agentic BI 的多步自动拆解、从对话直接产出看板、语义层的可交换格式。等出现可比较的判据。
4. **无论哪条**：把"**口径落对率 `CR`**"作为这一块的第一条 KPI——它同时是语义层、映射与评测三者的共同语言（只报 `EX` 会系统性高估）。
5. **一条反直觉的**：**先做"拒绝"，再做"覆盖"**——拒绝路径（明确说"未定义"）的成本是几行代码，而它一旦缺失，**你连"覆盖率有多低"都不知道**（因为系统会把没覆盖的也答出来）。**先有拒绝，覆盖率才是一个可测量的数。**

### 5.8 小结

> 本节小结：AI 时代对智能 BI 的改变**只有一条是机制性的——语义层映射（正确性来源从模型能力移到语义层完备度），而它已经发生**；此后所有方向（执行反馈、检索增强、自动洞察、Agentic、可见域、回显、指标从 `EX` 换到 `CR`）都是加固，**把它们当新机制会低估真正需要长期投入的那一项：语义层的覆盖与维护**。本节没有一行达到 L1，卡点在 ② 上有一条具体的解释——**口径落对率需要私有评测集，而私有评测集含业务口径、不能公开**；因此成熟度判断必须回到内部判据：**你自己的评测集上 `CR` 与 `HR` 是多少**。**给读者的动作**：先做拒绝路径与高频词覆盖；再谈反馈、洞察与 Agentic。

> 💡 **思考锚点**：如果你今天给系统加一条"无法映射就明确拒绝"的路径，一周后你会收到一批"为什么答不了"的反馈——**那批反馈就是你的真实覆盖率**。做这件事的成本是几行代码，收益是**你第一次知道自己的覆盖率是多少**（在此之前，系统会把没覆盖的也答出来，而你看不到）。**你打算先加拒绝路径，还是先补指标？**——这两个顺序会得到完全不同的下一年。
